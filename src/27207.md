## 元コミット内容

`cmd/vet: added some missing copylock checks`

このコミットは、`go vet` ツールに不足していたロックのコピー検出チェックを追加します。
具体的には、Issue #14664 で報告された問題に対応し、ロックが値渡しされる新たなケースを検出できるように `copylock` アナライザを強化しています。

## 変更の背景

Go言語では、`sync.Mutex` や `sync.RWMutex`、`sync.Once` といった同期プリミティブは、その内部状態を管理するためにポインタとして扱われるべきです。これらの型を値としてコピーすると、元のロックとコピーされたロックがそれぞれ独立した状態を持つことになり、意図しないデッドロックや競合状態（race condition）を引き起こす可能性があります。例えば、構造体の中に `sync.Mutex` が埋め込まれており、その構造体が値渡しされると、構造体内のミューテックスもコピーされてしまいます。これにより、異なるゴルーチンがそれぞれ異なるミューテックスインスタンスをロックしようとし、期待通りの排他制御が行われなくなります。

`go vet` は、このような潜在的なバグをコンパイル時ではなく静的に検出するためのツールです。以前の `copylock` チェッカーは、関数呼び出しの引数や `range` ステートメント、関数リテラル、代入ステートメントの一部でロックのコピーを検出できましたが、変数宣言や複合リテラル内でのコピーといった、より複雑なケースを見逃していました。

Issue #14664 は、まさにこのような見逃されていたケースを指摘しており、このコミットはその問題を解決し、`go vet` の検出能力を向上させることを目的としています。これにより、開発者がより多くのロックコピーの誤用パターンを早期に特定し、修正できるようになります。

## 前提知識の解説

### `go vet` とは

`go vet` はGo言語の標準的な静的解析ツールです。コンパイラでは検出できないが、コードの品質や正確性に影響を与える可能性のある疑わしい構造を報告します。例えば、到達不能なコード、誤った書式指定文字列、構造体タグの誤り、そして本コミットの主題であるロックの誤用などが含まれます。`go vet` はGoのビルドプロセスの一部として実行されることが多く、CI/CDパイプラインに組み込むことで、コードレビューの前に潜在的な問題を自動的に検出できます。

### `sync.Mutex` と `sync.Once`

*   **`sync.Mutex`**: Go言語で最も基本的な排他ロックプリミティブです。複数のゴルーチンが共有リソースに同時にアクセスするのを防ぎ、競合状態を回避するために使用されます。`Lock()` メソッドでロックを取得し、`Unlock()` メソッドでロックを解放します。`Mutex` はその性質上、内部状態（ロックされているかどうか、待機中のゴルーチンがあるかなど）を持つため、常にポインタとして扱われるべきです。
*   **`sync.Once`**: ある処理がプログラムの実行中に一度だけ実行されることを保証するためのプリミティブです。例えば、初期化処理などで使用されます。`Do(f func())` メソッドを呼び出すと、引数 `f` が一度だけ実行されることが保証されます。`sync.Once` の内部には `sync.Mutex` が含まれており、同様に値渡しされると問題が発生します。

### ロックの値渡しが問題となる理由

`sync.Mutex` や `sync.Once` のような同期プリミティブは、内部に状態（例えば、ロックが取得されているか否かを示すフラグや、待機中のゴルーチンを管理するキューなど）を持っています。これらを値渡しすると、その状態も一緒にコピーされてしまいます。

例えば、以下のようなコードを考えます。

```go
type Counter struct {
    mu    sync.Mutex
    count int
}

func (c Counter) Increment() { // 値レシーバ
    c.mu.Lock() // コピーされたミューテックスをロック
    c.count++
    c.mu.Unlock()
}

func main() {
    var c Counter
    c.Increment() // 別のミューテックスをロックしているため、排他制御が機能しない
}
```

この `Increment` メソッドは `Counter` を値レシーバとして受け取っているため、`c.mu` もコピーされます。結果として、`Increment` メソッド内でロックされるのは `main` 関数で宣言された `c` の `mu` ではなく、`Increment` 関数に渡された `c` のコピーに含まれる `mu` です。これにより、複数のゴルーチンが `Increment` を呼び出した場合でも、それぞれが異なるミューテックスをロックするため、排他制御が全く機能せず、競合状態が発生します。

正しい実装は、ポインタレシーバを使用することです。

```go
func (c *Counter) Increment() { // ポインタレシーバ
    c.mu.Lock() // 元のミューテックスをロック
    c.count++
    c.mu.Unlock()
}
```

このコミットは、このような値渡しによるロックの誤用を `go vet` がより広範なケースで検出できるようにするためのものです。

### GoのAST (Abstract Syntax Tree)

`cmd/vet` はGoのソースコードを解析するために、Goコンパイラが生成する抽象構文木（AST）を利用します。ASTはソースコードの構造を木構造で表現したもので、`vet` はこのASTを走査して特定のパターン（この場合はロックの値渡し）を探します。

*   `ast.Node`: ASTの各要素を表すインターフェース。
*   `ast.FuncDecl`: 関数宣言を表すノード。
*   `ast.RangeStmt`: `for ... range` ステートメントを表すノード。
*   `ast.FuncLit`: 関数リテラル（匿名関数）を表すノード。
*   `ast.AssignStmt`: 代入ステートメントを表すノード。
*   `ast.GenDecl`: `var`, `const`, `type` などの一般的な宣言を表すノード。
*   `ast.CompositeLit`: 複合リテラル（構造体、配列、スライス、マップなどの初期化）を表すノード。

このコミットでは、`genDecl` (一般的な宣言、特に `var` 宣言) と `compositeLit` (複合リテラル) のケースが `copylock` チェッカーの対象に追加されています。

## 技術的詳細

このコミットの主要な変更点は、`src/cmd/vet/copylock.go` 内の `checkCopyLocks` 関数が、より多くのASTノードタイプを処理するように拡張されたことです。

以前は、`checkCopyLocks` は `funcDecl`, `rangeStmt`, `funcLit`, `assignStmt` のみを対象としていました。このコミットにより、`genDecl` (汎用宣言、特に `var` 宣言) と `compositeLit` (複合リテラル) が新たに追加され、これらのコンテキストでのロックのコピーも検出できるようになりました。

### 新たに追加されたチェック

1.  **`genDecl` (汎用宣言) のチェック**:
    *   `checkCopyLocksGenDecl` 関数が新設されました。
    *   この関数は `ast.GenDecl` ノードを受け取り、それが `var` 宣言 (`gd.Tok == token.VAR`) である場合に処理を進めます。
    *   `var` 宣言内の各 `ValueSpec` (変数名と値のペア) を走査し、初期値 (`valueSpec.Values`) がロックをコピーしているかどうかを `lockPathRhs` 関数を使ってチェックします。
    *   もしロックのコピーが検出された場合、`f.Badf` を呼び出して警告メッセージを生成します。

    **例**:
    ```go
    var z = sync.Mutex{} // このような宣言が検出されるようになる
    ```

2.  **`compositeLit` (複合リテラル) のチェック**:
    *   `checkCopyCompositeLit` 関数が新設されました。
    *   この関数は `ast.CompositeLit` ノードを受け取り、その要素 (`cl.Elts`) を走査します。
    *   要素が `ast.KeyValueExpr` (キーと値のペア、例: `Field: Value`) の場合は、その値 (`node.Value`) をチェック対象とします。それ以外の場合は要素自体をチェック対象とします。
    *   `lockPathRhs` 関数を使って、複合リテラル内でロックがコピーされているかどうかをチェックします。
    *   ロックのコピーが検出された場合、`f.Badf` を呼び出して警告メッセージを生成します。

    **例**:
    ```go
    w := struct{ L sync.Mutex }{
        L: *x, // 構造体のフィールド初期化でロックがコピーされるケース
    }
    q := map[int]Tlock{
        1: t, // マップの値としてロックを含む構造体がコピーされるケース
    }
    yy := []Tlock{
        t, // スライスの要素としてロックを含む構造体がコピーされるケース
    }
    ```

### `lockPathRhs` 関数の導入

*   `lockPathRhs` というヘルパー関数が新しく追加されました。
*   この関数は、右辺の式 (`ast.Expr`) がロックをコピーしているかどうかを判断します。
*   特に、右辺が `ast.CompositeLit` (複合リテラル) の場合は、そのリテラル自体がロックのコピー元ではないため、`nil` を返してチェックをスキップします。これは、複合リテラル内の個々の要素は `checkCopyCompositeLit` で別途処理されるためです。
*   それ以外の式については、既存の `lockPath` 関数を呼び出し、その式の型がロックを含んでいるかどうかを判断します。

### `checkCopyLocksAssign` の修正

*   既存の `checkCopyLocksAssign` 関数も修正されました。
*   以前は代入の左辺 (`as.Lhs`) を見ていましたが、ロックのコピーは右辺の値から発生するため、右辺 (`as.Rhs`) を走査するように変更されました。
*   `lockPathRhs` を使用して右辺の式がロックをコピーしているかをチェックし、対応する左辺の変数にコピーされる場合に警告を発するように修正されています。

これらの変更により、`go vet` はより多くの一般的なGoのコードパターンにおいて、ロックの値渡しによる誤用を検出できるようになり、開発者がより安全な並行処理コードを書くための支援が強化されました。

## コアとなるコードの解説

### `src/cmd/vet/copylock.go` の変更点

1.  **`init()` 関数の `register` 呼び出しの変更**:
    *   `register` 関数は、`copylocks` チェッカーがどのASTノードタイプを処理するかを登録します。
    *   変更前: `funcDecl, rangeStmt, funcLit, assignStmt`
    *   変更後: `funcDecl, rangeStmt, funcLit, assignStmt, genDecl, compositeLit`
    *   これにより、`checkCopyLocks` 関数が `ast.GenDecl` (汎用宣言) と `ast.CompositeLit` (複合リテラル) のノードタイプも受け取るようになります。

2.  **`checkCopyLocks` 関数の `switch` ステートメントの拡張**:
    *   `checkCopyLocks` は、受け取った `ast.Node` の具体的な型に基づいて適切な処理をディスパッチします。
    *   新たに `case *ast.GenDecl:` と `case *ast.CompositeLit:` が追加され、それぞれ `checkCopyLocksGenDecl` と `checkCopyCompositeLit` という新しい関数が呼び出されるようになりました。

3.  **`checkCopyLocksAssign` 関数の修正**:
    *   この関数は代入ステートメント (`ast.AssignStmt`) におけるロックのコピーをチェックします。
    *   変更前は `as.Lhs` (左辺) をイテレートしていましたが、ロックのコピーは右辺の値から左辺の変数に伝播するため、`as.Rhs` (右辺) をイテレートするように修正されました。
    *   `lockPathRhs(f, x)` を使用して右辺の式 `x` がロックを含んでいるかを判断し、そのロックが左辺の `as.Lhs[i]` にコピーされる場合にエラーを報告します。

4.  **`checkCopyLocksGenDecl` 関数の追加**:
    *   `ast.GenDecl` (汎用宣言) ノード、特に `var` 宣言を処理します。
    *   `gd.Tok != token.VAR` でない場合は早期リターンします。
    *   `gd.Specs` (宣言の仕様、例: `var a, b int = 1, 2` の `a, b int = 1, 2` の部分) を走査します。
    *   各 `ValueSpec` (変数名と値のペア) の `valueSpec.Values` (初期値) を `lockPathRhs` でチェックし、ロックのコピーがあればエラーを報告します。

5.  **`checkCopyCompositeLit` 関数の追加**:
    *   `ast.CompositeLit` (複合リテラル) ノードを処理します。
    *   `cl.Elts` (リテラルの要素) を走査します。
    *   要素が `ast.KeyValueExpr` (例: `Key: Value`) の場合は、その `Value` 部分をチェック対象とします。それ以外の場合は要素自体をチェック対象とします。
    *   `lockPathRhs` を使用して、リテラル内の要素がロックをコピーしているかを判断し、エラーを報告します。

6.  **`lockPathRhs` ヘルパー関数の追加**:
    *   この関数は、与えられた式 `x` がロックをコピーしているパスを返します。
    *   もし `x` が `ast.CompositeLit` であれば、そのリテラル自体はコピー元ではないため `nil` を返します。これは、複合リテラル内の個々の要素は `checkCopyCompositeLit` で既に処理されているためです。
    *   それ以外の場合、既存の `lockPath` 関数を呼び出して、式の型がロックを含んでいるかを判断します。

### `src/cmd/vet/testdata/copylock.go` の変更点

*   このファイルは `copylock` チェッカーのテストケースを含んでいます。
*   `OkFunc()` には、ロックのコピーが発生しない正しいコード例が追加されています。
    *   `var z = sync.Mutex{}` や `w := sync.Mutex{}` のような宣言は、このコミットで検出対象となるパターンですが、`OkFunc` に追加されているのは、これらの宣言が `BadFunc` でエラーとして検出されることを示すための対比的な例です。`OkFunc` 内ではこれらの変数が値渡しで使われていないため、`vet` はエラーを報告しません。
*   `BadFunc()` には、このコミットで新たに追加された検出パターンに対応する、ロックが誤ってコピーされるコード例が多数追加されています。
    *   `y := *x` (ポインタのデリファレンスによるロックのコピー)
    *   `var z = t` (変数宣言時のロックを含む構造体のコピー)
    *   構造体リテラル内でのロックのコピー (`L: *x`)
    *   マップの値としてのロックを含む構造体のコピー (`1: t`)
    *   スライスの要素としてのロックを含む構造体のコピー (`t`)
    *   これらの行には `// ERROR "..."` というコメントが付加されており、`go vet` がこれらのパターンを検出して期待通りのエラーメッセージを出力することをテストしています。

これらの変更とテストケースの追加により、`go vet` の `copylock` チェッカーは、Go言語におけるロックの誤用パターンをより網羅的に検出できるようになり、開発者がより堅牢な並行処理コードを記述する上で非常に有用なツールとなります。

# [インデックス 26681] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）とランタイム（`runtime`）におけるマップ（`hmap`、`hiter`）および`select`文のケース（`scase`）の内部型定義の管理方法を大幅に変更するものです。具体的には、これらの型定義を`builtin.go`および`builtin/runtime.go`に集約し、マップ型ごとに個別の`hiter`および`hmap`型を生成する仕組みを廃止しました。これにより、コンパイラのコード生成が簡素化され、生成されるバイナリのサイズが削減されています。

変更された主なファイルは以下の通りです。

- `src/cmd/compile/internal/gc/builtin.go`: ランタイムの組み込み型定義の追加。
- `src/cmd/compile/internal/gc/builtin/runtime.go`: `hmap`, `hiter`, `scase`構造体の具体的な定義の追加。
- `src/cmd/compile/internal/gc/fmt.go`: マップ関連の内部型フォーマット処理の削除。
- `src/cmd/compile/internal/gc/go.go`: `Type`構造体から`Hmap`および`Hiter`フィールドの削除。
- `src/cmd/compile/internal/gc/range.go`: `range`ループにおけるマップイテレータの型解決ロジックの変更。
- `src/cmd/compile/internal/gc/reflect.go`: `hmap`および`hiter`の型生成ロジックの削除。
- `src/cmd/compile/internal/gc/select.go`: `select`文のケース型生成ロジックの簡素化。
- `src/cmd/compile/internal/gc/subr.go`: 型のディープコピーに関する変更。
- `src/cmd/compile/internal/gc/walk.go`: `makemap`呼び出しにおける`hmap`型の参照方法の変更。
- `src/reflect/type.go`: `mapType`構造体から`hmap`フィールドの削除。
- `src/runtime/hashmap.go`: `hmap`および`hiter`構造体のコメント更新と`makemap`関数の変更。
- `src/runtime/runtime2.go`: `sudog`構造体に関するコメントの削除。
- `src/runtime/select.go`: `hselect`および`scase`構造体に関するコメントの更新。
- `src/runtime/type.go`: `maptype`構造体から`hmap`フィールドの削除。

## 元コミット内容

このコミットは、Goコンパイラにおいて、ハッシュマップのイテレータ（`hiter`）、ハッシュマップのヘッダ（`hmap`）、および`select`文のケース（`scase`）の定義を`builtin.go`ファイルに移動させるものです。

さらに、この変更は、各マップ型に対して個別の`hiter`および`hmap`型を生成する仕組みを廃止します。これらの型は実際には個別に必要とされていなかったためです。これに伴い、`reflect`パッケージと`runtime`パッケージも適切に更新されています。

この変更の結果、`golang.org/x/tools/cmd/godoc`コマンドのテキストセグメントサイズが約170KB削減されました。これは、コンパイラが生成するコードの効率化とバイナリサイズの最適化に貢献しています。

このコミットは、Issue #6853に関連する更新です。

## 変更の背景

Go言語のコンパイラは、プログラムのコンパイル時にランタイムが使用する内部構造体（例えば、マップやチャネルの内部表現）の型情報を知る必要があります。以前のGoコンパイラでは、マップのヘッダ（`hmap`）やイテレータ（`hiter`）の型定義が、コンパイラ内部で動的に、かつマップの型ごとに生成されていました。これは、異なるキーと値の型を持つマップに対して、それぞれ異なる`hmap`や`hiter`の型がコンパイラによって「構築」されることを意味します。

しかし、`hmap`や`hiter`といったランタイムの内部構造体は、そのフィールド構成自体はマップのキーや値の型に依存せず、汎用的なものです。マップのキーや値の具体的な型は、これらの構造体内のポインタが指す先のデータによって表現されます。したがって、マップ型ごとにこれらの構造体の型定義をコンパイラが動的に生成する必要性は薄く、むしろ冗長なコード生成につながっていました。

この冗長な型生成は、特に`godoc`のような多くの型情報を扱うツールにおいて、生成されるバイナリのテキストセグメントサイズを不必要に増加させる原因となっていました。コミットメッセージに記載されているように、`godoc`のテキストセグメントが約170KB削減されたことは、この最適化の大きな成果を示しています。

この変更の主な目的は、コンパイラのコード生成を簡素化し、Goプログラムのバイナリサイズを削減することにあります。ランタイムの内部構造体である`hmap`、`hiter`、`scase`の定義を`builtin.go`に一元化することで、コンパイラはこれらの型を動的に生成する代わりに、あらかじめ定義された単一の型を参照するようになります。これにより、コンパイラの複雑性が軽減され、より効率的なコード生成が可能になります。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の内部動作に関する知識が必要です。

1.  **Goコンパイラ (`cmd/compile`)**: Goソースコードを機械語に変換するツールです。コンパイラは、Goプログラムが使用するランタイムの内部構造体や関数について、そのシグネチャやレイアウトを知っている必要があります。
2.  **Goランタイム (`runtime`)**: Goプログラムの実行を管理するライブラリです。ガベージコレクション、スケジューリング、マップやチャネルなどの組み込み型の実装が含まれます。
3.  **`hmap`**: Goのマップ（`map`）型の内部表現のヘッダ構造体です。マップの要素数、バケットのポインタ、ハッシュシードなどの情報を含みます。`src/runtime/hashmap.go`で定義されています。
4.  **`hiter`**: Goのマップを`range`ループでイテレートする際に使用される内部イテレータ構造体です。現在のキー、値、マップヘッダへのポインタなどの情報を含みます。`src/runtime/hashmap.go`で定義されています。
5.  **`scase`**: Goの`select`文の各`case`句を表現する内部構造体です。チャネル、送受信する要素へのポインタ、`case`の種類などの情報を含みます。`src/runtime/select.go`で定義されています。
6.  **`builtin.go`**: コンパイラ内部で、ランタイムの組み込み関数や型を定義するためのファイルです。コンパイラは、Goのソースコードには直接現れないが、ランタイムが提供する低レベルな機能（例えば、`newobject`、`makemap`など）を呼び出すために、これらの定義を利用します。
7.  **型リフレクション (`reflect`パッケージ)**: 実行時にGoの型情報を検査・操作するためのパッケージです。コンパイラは、リフレクションがランタイムの内部型を正しく解釈できるように、これらの型のレイアウトを正確に知っている必要があります。
8.  **テキストセグメント**: 実行可能バイナリファイルの一部で、プログラムの機械語コードが格納される領域です。このサイズが削減されることは、バイナリ全体のサイズ削減に直結します。

以前のコンパイラでは、`hmap`や`hiter`のような構造体の型定義が、`reflect.go`内でマップの型ごとに動的に構築されていました。これは、`map[int]string`と`map[string]float64`のように異なるマップ型がある場合、それぞれに対応する`hmap`や`hiter`の型情報がコンパイラによって個別に生成されることを意味します。しかし、これらの構造体自体のレイアウトは汎用であり、キーや値の型はポインタとして内部で扱われるため、個別の型定義は不要でした。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラがランタイムの内部構造体（`hmap`, `hiter`, `scase`）の型定義をどのように扱うかを変更した点にあります。

**変更前**:
- コンパイラは、`src/cmd/compile/internal/gc/reflect.go`内で、Goプログラムに登場する各マップ型（例: `map[K]V`）に対して、対応する`hmap`と`hiter`の内部型定義を動的に生成していました。これは、`Type`構造体の`Hmap`および`Hiter`フィールドを通じて管理されていました。
- `src/cmd/compile/internal/gc/select.go`では、`scase`構造体も同様に、`selecttype`関数内で動的に構築されていました。
- これらの動的な型生成は、コンパイラが生成する型情報（`_type`構造体など）の重複や冗長性を生み出し、結果として最終的なバイナリのテキストセグメントサイズを増加させていました。

**変更後**:
- `hmap`, `hiter`, `scase`の構造体定義が、`src/cmd/compile/internal/gc/builtin/runtime.go`に直接記述されるようになりました。これらの定義は、ランタイムの実際の定義（`src/runtime/hashmap.go`や`src/runtime/select.go`）と同期が取られています。
- `src/cmd/compile/internal/gc/builtin.go`には、これらの型をコンパイラが認識するための宣言が追加されました。具体的には、`runtimeimport`文字列内に`type @"".hbucket uint8`、`type @"".hmap struct { ... }`などの形式で、これらの型の抽象的な定義が埋め込まれています。コンパイラは、この`runtimeimport`文字列をパースすることで、ランタイムの内部型を知ることができます。
- `src/cmd/compile/internal/gc/reflect.go`から、`hmap`および`hiter`の型を動的に構築する関数（`hmap(t *Type)`、`hiter(t *Type)`）が削除されました。
- `src/cmd/compile/internal/gc/go.go`の`Type`構造体から、`Hmap`および`Hiter`フィールドが削除されました。これにより、マップ型ごとにこれらの内部型を保持する必要がなくなりました。
- `src/cmd/compile/internal/gc/select.go`では、`scase`構造体を動的に構築する代わりに、`syslook("scase", 0)`というヘルパー関数を使って、`builtin.go`で定義された`scase`型を参照するようになりました。
- `src/cmd/compile/internal/gc/range.go`や`src/cmd/compile/internal/gc/walk.go`など、これらの内部型を参照していた箇所は、新しい一元化された定義を参照するように変更されました。例えば、`hiter(t)`の呼び出しは`syslook("hiter", 0).Type`に置き換えられています。
- `src/reflect/type.go`と`src/runtime/type.go`からも、`mapType`構造体内の`hmap`フィールドが削除されました。これは、リフレクションシステムも`hmap`の型情報をマップ型ごとに持つ必要がなくなったことを意味します。

この変更により、コンパイラは`hmap`、`hiter`、`scase`といったランタイムの内部構造体の型定義を、Goプログラムの型情報とは独立した、単一の組み込み型として扱うようになります。これにより、コンパイラが生成する型情報の重複が排除され、結果としてバイナリのテキストセグメントサイズが削減されます。`godoc`の例で示された170KBの削減は、この最適化がもたらす具体的なメリットです。

## コアとなるコードの解説

上記の変更箇所は、Goコンパイラの型システムとコード生成の根本的な変更を反映しています。

1.  **`builtin.go`への型定義の移動**:
    `runtimeimport`文字列は、コンパイラがGoのランタイムパッケージからインポートされるかのように扱うための擬似的なGoコードの断片です。ここに`hmap`、`hiter`、`scase`の型定義を直接記述することで、コンパイラはこれらの型を「既知の」組み込み型として扱えるようになります。これにより、コンパイラはこれらの型のレイアウトを動的に推論したり、マップ型ごとに個別の型情報を生成したりする必要がなくなります。これは、コンパイラの起動時または初期化時に一度だけパースされ、その情報がコンパイラ全体で共有されることになります。

2.  **`builtin/runtime.go`での具体的な構造体定義**:
    このファイルは、コンパイラがランタイムの内部構造体の正確なメモリレイアウトを知るために使用されます。`builtin.go`の`runtimeimport`内の定義は抽象的な宣言ですが、`builtin/runtime.go`の定義は実際のGoの構造体定義であり、コンパイラがコード生成を行う際に参照します。このファイルに定義を置くことで、コンパイラはランタイムの内部構造体と完全に同期した型情報を持つことができます。コメントにあるように、`src/runtime/hashmap.go`や`src/runtime/select.go`の定義と同期を保つことが重要です。

3.  **`reflect.go`からの動的型生成関数の削除**:
    以前は、`hmap(t *Type)`や`hiter(t *Type)`といった関数が、特定のマップ型`t`に基づいて`hmap`や`hiter`の内部型を動的に構築していました。これは、マップのキーや値の型に応じて、これらの内部構造体の型情報も異なるとコンパイラが考えていたためです。しかし、実際には`hmap`や`hiter`のフィールドは汎用的なポインタ型であり、キーや値の具体的な型はポインタの指す先で表現されるため、これらの構造体自体のレイアウトはマップ型に依存しません。これらの関数を削除することで、コンパイラは冗長な型生成ロジックから解放され、コードベースが簡素化されます。

4.  **`go.go`の`Type`構造体からのフィールド削除**:
    `Type`構造体は、Goコンパイラがプログラム内のあらゆる型を表現するために使用する中心的なデータ構造です。以前は、マップ型を表す`Type`インスタンスが、そのマップに対応する`Hmap`と`Hiter`の内部型へのポインタを保持していました。これらのフィールドが削除されたことは、コンパイラがマップ型ごとに`hmap`や`hiter`の型情報を個別に管理する必要がなくなったことを明確に示しています。これにより、`Type`構造体のメモリフットプリントがわずかに削減され、型システムの複雑性も軽減されます。

これらの変更は、Goコンパイラがランタイムの内部構造体をより効率的かつ一貫した方法で扱うための重要なステップです。これにより、コンパイラのコードベースが簡素化され、生成されるバイナリのサイズが削減されるという具体的なメリットがもたらされました。

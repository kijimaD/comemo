このコミットは、GoランタイムのWindows固有のコード、具体的には`src/runtime/os1_windows.go`ファイルに対する変更です。このファイルは、GoプログラムがWindowsオペレーティングシステム上で動作する際の低レベルなシステムコールや例外処理を扱う部分を定義しています。

## 元コミット内容

このコミットは、Windows XP および Windows Server 2003 (amd64アーキテクチャ) 上で、Windows Error Reporting (WER) ダイアログが無効になっている場合に `AddVectoredContinueHandler` が正しく機能しない問題を修正します。新しいバージョンのWindowsでは、WERの設定に関わらずこのハンドラが正常に動作するため、古いOSバージョンに特化した対応が導入されました。

## 変更の背景

Goランタイムは、プログラム実行中に発生する例外（例えば、不正なメモリアクセスなど）を捕捉し、適切に処理するためのメカニズムを持っています。Windows環境では、この例外処理にVectored Exception Handling (VEH) というOSの機能を利用することがあります。VEHは、アプリケーションが例外発生時に独自のハンドラを登録し、例外を処理したり、実行を継続したりすることを可能にします。

しかし、Windows XPおよびWindows Server 2003の64ビット版において、Windows Error Reporting (WER) ダイアログ（エラー発生時にMicrosoftにエラー報告を送信するかどうかを尋ねるダイアログ）が無効化されている特定の条件下で、`AddVectoredContinueHandler` を使用して登録されたハンドラが呼び出されないという問題が報告されました（Issue #10162）。これは、Goプログラムがクラッシュした際に、Goランタイムが期待する例外処理フローが中断され、デバッグやリカバリが困難になる可能性を意味します。

この問題は、これらの古いOSバージョンに特有のものであり、Windows Vista以降の新しいOSではWERの設定に関わらず`AddVectoredContinueHandler`が正常に動作することが確認されていました。そのため、Goランタイムは、古いWindowsバージョンでのみ異なる例外処理メカニズム（`SetUnhandledExceptionFilter`）を使用するように変更する必要がありました。

## 前提知識の解説

### Windowsの例外処理メカニズム

Windowsオペレーティングシステムには、プログラム実行中に発生する様々な例外（ハードウェア例外、ソフトウェア例外など）を処理するための複数のメカニズムがあります。

1.  **Structured Exception Handling (SEH)**: Windowsのネイティブな例外処理メカニズムです。`__try`, `__except`, `__finally` などのキーワードを使用して、C/C++コード内で例外を処理します。
2.  **Vectored Exception Handling (VEH)**: SEHよりも高レベルで、アプリケーション全体で例外を捕捉できるメカニズムです。`AddVectoredExceptionHandler` と `AddVectoredContinueHandler` の2つの関数が主要です。
    *   `AddVectoredExceptionHandler`: 例外が発生した際に最初に呼び出されるハンドラを登録します。これは、例外が処理される前にアプリケーションが介入できる機会を提供します。
    *   `AddVectoredContinueHandler`: 例外ハンドラが例外を処理した後、実行を継続する際に呼び出されるハンドラを登録します。これは、例外から回復し、プログラムの実行を再開するシナリオで重要です。
3.  **`SetUnhandledExceptionFilter`**: アプリケーションが処理しない例外（unhandled exception）が発生した場合に呼び出される最後の手段のハンドラを設定します。通常、クラッシュダンプの生成やエラーログの記録などに使用されます。デバッガがアタッチされている場合、このハンドラは呼び出されないことがあります。

### Windows Error Reporting (WER)

Windows Error Reporting (WER) は、アプリケーションのクラッシュやハングアップなどのエラー情報を収集し、Microsoftに送信するためのWindowsの機能です。ユーザーはエラー報告を送信するかどうかを選択でき、このダイアログが表示されるかどうかの設定はシステム管理者によって制御できます。WERダイアログが無効化されている環境では、ユーザーにエラー報告の選択肢が提示されません。

### Windowsのバージョン番号

Windowsのバージョンは、メジャーバージョンとマイナーバージョンで識別されます。
*   Windows XP: メジャーバージョン 5, マイナーバージョン 1 (5.1)
*   Windows Server 2003: メジャーバージョン 5, マイナーバージョン 2 (5.2)
*   Windows Vista: メジャーバージョン 6, マイナーバージョン 0 (6.0)
*   Windows 7: メジャーバージョン 6, マイナーバージョン 1 (6.1)
*   Windows 8: メジャーバージョン 6, マイナーバージョン 2 (6.2)
*   Windows 8.1: メジャーバージョン 6, マイナーバージョン 3 (6.3)
*   Windows 10: メジャーバージョン 10, マイナーバージョン 0 (10.0)

このコミットでは、メジャーバージョンが6未満のWindows（つまりWindows XP/2003）を特別扱いしています。

## 技術的詳細

Goランタイムは、Windows上で例外が発生した際に、まず `AddVectoredExceptionHandler` を使用してGo独自の例外ハンドラを登録します。これにより、Goのランタイムが例外を捕捉し、Goのスケジューラやスタック管理と連携して処理を行うことができます。

問題となったのは `AddVectoredContinueHandler` の挙動です。通常、例外が処理された後に実行を継続する場合、このハンドラが呼び出されることを期待します。しかし、Windows XP/2003 (amd64) でWERダイアログが無効になっていると、このハンドラが呼び出されず、Goランタイムが例外からの回復処理を適切に行えない状況が発生しました。

この問題に対処するため、コミットでは以下のロジックが導入されました。
1.  Goランタイムが起動する際に、現在のWindowsのメジャーバージョンを取得します。
2.  もしWindowsのメジャーバージョンが6未満（つまりWindows XPまたはWindows Server 2003）であれば、`AddVectoredContinueHandler` の代わりに `SetUnhandledExceptionFilter` を使用して、最後の手段の例外ハンドラを登録します。
3.  これにより、古いWindowsバージョンでの特定の条件下での `AddVectoredContinueHandler` の問題を回避し、Goプログラムの安定性を向上させます。

`SetUnhandledExceptionFilter` は、デバッガがアタッチされている場合には呼び出されないという特性がありますが、これは開発環境でのデバッグ時には問題となりにくく、本番環境でのクラッシュ時の挙動を改善することを目的としています。

## コアとなるコードの解説

1.  **`//go:cgo_import_dynamic runtime._GetVersion GetVersion%0 "kernel32.dll"` の追加**:
    *   これはGoのCgo機能を使って、Windowsの`kernel32.dll`から`GetVersion`関数を動的にインポートするためのディレクティブです。`GetVersion`は、現在のOSのバージョン情報を取得するために使用されます。`%0`は引数の数を示します（この関数は引数を取りません）。

2.  **`_GetVersion` 変数の追加**:
    *   インポートされた`GetVersion`関数のポインタを保持するための変数`_GetVersion`が`var`ブロックに追加されました。

3.  **`getVersion() (major, minor byte)` 関数の追加**:
    *   この新しい関数は、`_GetVersion`を呼び出してOSのバージョン情報を取得します。
    *   `stdcall0(_GetVersion)`: 引数なしで`_GetVersion`関数を呼び出します。`GetVersion`は`DWORD`型の値を返します。この値の下位16ビットにマイナーバージョンとメジャーバージョンがパックされています。
    *   `v := uint32(stdcall0(_GetVersion))`: 戻り値を`uint32`にキャストして`v`に格納します。
    *   `low := uint16(v)`: `v`の下位16ビット（`LOWORD`）を取得します。この`uint16`値の下位8ビットがマイナーバージョン、上位8ビットがメジャーバージョンです。
    *   `return byte(low), byte(low >> 8)`: `low`の下位8ビットをマイナーバージョン、`low`を8ビット右シフトした値（上位8ビット）をメジャーバージョンとして返します。

4.  **`osinit()` 関数内の条件分岐の変更**:
    *   `osinit()` はGoランタイムがOS固有の初期化を行う関数です。
    *   `major, _ := getVersion()`: 新しく追加された`getVersion`関数を呼び出し、現在のWindowsのメジャーバージョンを取得します。
    *   `if _AddVectoredContinueHandler == nil || unsafe.Sizeof(&_AddVectoredContinueHandler) == 4 || major < 6 { ... }`:
        *   既存の条件 `_AddVectoredContinueHandler == nil` (VectoredContinueHandlerが利用できない場合) または `unsafe.Sizeof(&_AddVectoredContinueHandler) == 4` (32ビット環境の場合) に加えて、`major < 6` という新しい条件が追加されました。
        *   この `major < 6` の条件が、Windows XP (5.1) や Windows Server 2003 (5.2) のようなメジャーバージョンが5であるOSをターゲットにしています。
        *   この条件が真の場合、つまりVectoredContinueHandlerが利用できない、32ビット環境である、またはWindowsのメジャーバージョンが6未満である場合、Goランタイムは `stdcall1(_SetUnhandledExceptionFilter, funcPC(lastcontinuetramp))` を呼び出して `SetUnhandledExceptionFilter` を使用します。
        *   それ以外の場合（新しいWindowsバージョンでVectoredContinueHandlerが利用可能な場合）は、引き続き `stdcall2(_AddVectoredContinueHandler, 1, funcPC(lastcontinuetramp))` を使用します。

この変更により、Goランタイムは古いWindowsバージョンでの特定の例外処理のバグを回避し、より堅牢な動作を実現しています。

# [インデックス 22028] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ（GC）におけるワークバッファ管理を、より抽象化された`gcWork`および`gcWorkProducer`メカニズムに移行するものです。これにより、GCの内部動作が整理され、より効率的かつ堅牢なメモリ管理が実現されます。

## コミット

```
commit 02dcdba7c8d2c180ce2f4aa9e7bf805967b9d74d
Author: Austin Clements <austin@google.com>
Date:   Tue Feb 17 10:53:31 2015 -0500

    runtime: switch to gcWork abstraction

    This converts the garbage collector from directly manipulating work
    buffers to using the new gcWork abstraction.

    The previous management of work buffers was rather ad hoc.  As a
    result, switching to the gcWork abstraction changes many details of
    work buffer management.

    If greyobject fills a work buffer, it can now pull from work.partial
    in addition to work.empty.

    Previously, gcDrain started with a partial or empty work buffer and
    fetched an empty work buffer if it filled its current buffer (in
    greyobject).  Now, gcDrain starts with a full work buffer and fetches
    an partial or empty work buffer if it fills its current buffer (in
    greyobject).  The original behavior was bad because gcDrain would
    immediately drop the empty work buffer returned by greyobject and
    fetch a full work buffer, which greyobject was likely to immediately
    overflow, fetching another empty work buffer, etc.  The new behavior
    isn't great at the start because greyobject is likely to immediately
    overflow the full buffer, but the steady-state behavior should be more
    stable.  Both before and after this change, gcDrain fetches a full
    work buffer if it drains its current buffer.  Basically all of these
    choices are bad; the right answer is to use a dual work buffer scheme.

    Previously, shade always fetched a work buffer (though usually from
    m.currentwbuf), even if the object was already marked.  Now it only
    fetches a work buffer if it actually greys an object.

## 元コミット内容

このコミットは、Goのガベージコレクタがワークバッファを直接操作する方式から、新しい`gcWork`抽象化を使用する方式へと変更します。

以前のワークバッファ管理は、かなりアドホック（場当たり的）でした。その結果、`gcWork`抽象化への切り替えにより、ワークバッファ管理の多くの詳細が変更されます。

`greyobject`がワークバッファを満たした場合、`work.empty`に加えて`work.partial`からも取得できるようになりました。

以前は、`gcDrain`は部分的に満たされた、または空のワークバッファから開始し、現在のバッファが満たされた場合（`greyobject`内）、空のワークバッファを取得していました。現在は、`gcDrain`は満たされたワークバッファから開始し、現在のバッファが満たされた場合（`greyobject`内）、部分的に満たされた、または空のワークバッファを取得します。元の動作は、`gcDrain`が`greyobject`によって返された空のワークバッファをすぐに破棄し、満たされたワークバッファを取得し、`greyobject`がそれをすぐにオーバーフローさせ、別の空のワークバッファを取得する、といった悪循環に陥る可能性があったため、良くありませんでした。新しい動作も開始時には`greyobject`が満たされたバッファをすぐにオーバーフローさせる可能性があり、完璧ではありませんが、定常状態の動作はより安定するはずです。この変更の前後で、`gcDrain`は現在のバッファを使い切った場合、満たされたワークバッファを取得します。これらの選択肢は基本的にすべて良くありません。正しい解決策は、デュアルワークバッファスキームを使用することです。

以前は、`shade`はオブジェクトがすでにマークされている場合でも、常にワークバッファを取得していました（通常は`m.currentwbuf`から）。現在は、実際にオブジェクトをグレイ化する場合にのみワークバッファを取得します。

## 変更の背景

Goのガベージコレクタは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行してガベージコレクションを行います。このプロセスにおいて、GCはヒープ上のオブジェクトを走査し、到達可能なオブジェクトをマークするために「ワークバッファ」と呼ばれる一時的なデータ構造を使用します。これらのワークバッファには、走査すべきオブジェクトへのポインタが格納されます。

このコミット以前は、ワークバッファの管理が「アドホック」、つまり特定の状況に合わせて場当たり的に実装されており、統一された抽象化が欠けていました。これにより、以下のような問題が発生していました。

1.  **複雑なロジック**: ワークバッファの取得、解放、再利用のロジックが様々なGC関連関数に散在し、コードの可読性や保守性が低下していました。
2.  **非効率なバッファ利用**: `gcDrain`や`greyobject`のような関数がワークバッファを非効率的に利用するケースがありました。例えば、`gcDrain`が空のバッファを受け取った直後にそれを破棄し、新しいバッファを要求するといった無駄な操作が発生していました。これは、GCのパフォーマンスに悪影響を与える可能性がありました。
3.  **冗長な操作**: `shade`関数のように、オブジェクトが既にマーク済みであるにもかかわらず、無条件にワークバッファを取得するような冗長な処理が存在していました。

これらの問題を解決し、GCのワークバッファ管理をより体系的かつ効率的にするために、`gcWork`という新しい抽象化が導入されました。この抽象化は、ワークバッファのライフサイクル管理を一元化し、GCコード全体の健全性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクタの基本的な概念と、それに伴う用語を理解しておく必要があります。

### Goのガベージコレクタ (GC)

GoのGCは、主に以下のフェーズで動作します。

*   **マークフェーズ (Mark Phase)**: プログラムが使用しているオブジェクト（到達可能なオブジェクト）を特定し、マークします。GoのGCは並行マークを採用しており、アプリケーションの実行と並行してマーク処理を進めます。
*   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不可能なオブジェクト、つまりガベージ）を解放し、メモリを再利用可能にします。

### ワークバッファ (Work Buffer)

マークフェーズにおいて、GCはヒープ上のオブジェクトを走査し、そこから参照されている他のオブジェクトを「グレイ化」（走査待ちの状態にする）します。グレイ化されたオブジェクトは、後で走査されるために一時的に「ワークバッファ」に格納されます。ワークバッファは、GCワーカーゴルーチン間で共有されるキューのような役割を果たします。

*   **`greyobject`**: オブジェクトをグレイ化し、ワークバッファに追加する関数。
*   **`gcDrain`**: ワークバッファからグレイオブジェクトを取り出し、それらを走査（ブラック化）する関数。
*   **`work.empty`**: 空のワークバッファのプール。
*   **`work.partial`**: 部分的に満たされたワークバッファのプール。
*   **`work.full`**: 完全に満たされたワークバッファのプール。

### ポインタ走査 (Pointer Scanning)

GCは、オブジェクト内のポインタを識別し、それらが指すオブジェクトもマークする必要があります。このプロセスをポインタ走査と呼びます。

*   **`scanobject`**: 特定のオブジェクトを走査し、その中のポインタを識別してグレイ化する関数。
*   **`scanblock`**: メモリブロックを走査し、その中のポインタを識別してグレイ化する関数。

### ライトバリア (Write Barrier)

並行GCでは、アプリケーションがGC中にヒープを変更する可能性があります。この変更によってGCがオブジェクトを見落とすことを防ぐために、「ライトバリア」が使用されます。ライトバリアは、ポインタの書き込み時に特定の処理（例えば、新しい参照先のオブジェクトをグレイ化する）を実行するメカニズムです。

*   **`shade`**: ライトバリアの一部として機能し、ポインタの書き込み時に新しい参照先のオブジェクトをグレイ化する関数。

### `m.currentwbuf`

各M（Machine、OSスレッドに相当）は、GC作業のために自身のローカルなワークバッファ（`m.currentwbuf`）を持つことができます。これにより、グローバルなワークキューへのアクセス競合を減らし、キャッシュ効率を向上させます。

## 技術的詳細

このコミットの核心は、GCのワークバッファ管理を`gcWork`および`gcWorkProducer`という新しい構造体にカプセル化することです。これにより、ワークバッファの取得、解放、オブジェクトの追加、取得といった操作が、これらの抽象化を通じて行われるようになります。

### `gcWork`と`gcWorkProducer`

コミットの差分からは、`gcWork`と`gcWorkProducer`が導入されたことがわかります。具体的な構造体の定義はこのコミットの範囲外ですが、その使用方法から役割を推測できます。

*   **`gcWorkProducer`**: 主にオブジェクトをワークバッファに追加する（`put`）役割を担うインターフェースまたは構造体。`greyobject`や`scanobject`といった、オブジェクトをグレイ化してキューに入れる関数がこれを使用します。`initFromCache()`で初期化され、`dispose()`または`disposeToCache()`でリソースを解放します。
*   **`gcWork`**: 主にワークバッファからオブジェクトを取得する（`get`、`tryGet`）役割を担うインターフェースまたは構造体。`gcDrain`のような、ワークバッファを消費してオブジェクトを走査する関数がこれを使用します。また、`balance()`のようなワークのバランスを取る機能も提供するようです。

### ワークバッファ管理の変更点

1.  **`greyobject`の変更**:
    *   以前は`*workbuf`を引数に取り、`*workbuf`を返していました。これは、`greyobject`がワークバッファが満杯になった場合に新しいワークバッファを取得し、それを呼び出し元に返すという責任を負っていたことを意味します。
    *   変更後、`gcw *gcWorkProducer`を引数に取り、`void`を返します。ワークバッファの管理は`gcw`内部に抽象化され、`greyobject`は単に`gcw.put(obj)`を呼び出すだけでよくなりました。これにより、`greyobject`のロジックが簡素化され、ワークバッファの取得・解放の複雑さが隠蔽されます。
    *   オブジェクトが既にマークされている場合や、走査不要なオブジェクトの場合、以前は`wbuf`をそのまま返していましたが、変更後は単に`return`するだけになりました。これは、`gcWorkProducer`が内部でこれらのケースを適切に処理するか、あるいは`put`操作自体が不要になることを示唆しています。

2.  **`scanobject`、`scanblock`の変更**:
    *   これらの関数も`*workbuf`の代わりに`gcw *gcWorkProducer`を受け取るようになり、`void`を返すようになりました。これにより、オブジェクト走査の過程で発見されたポインタのグレイ化が、`gcWorkProducer`の抽象化を通じて行われるようになります。

3.  **`gcDrain`の変更**:
    *   以前は`*workbuf`を引数に取り、ワークバッファが空になった場合に`getfull`で新しいバッファを取得していました。
    *   変更後、`gcw *gcWork`を引数に取り、`gcw.get()`でオブジェクトを取得するようになりました。`gcw.get()`は、ワークがなくなった場合に`0`を返すことで、`gcDrain`のループを終了させます。
    *   `work.nwait > 0 && work.full == 0`の場合に`gcw.balance()`を呼び出すようになりました。これは、他のプロセッサがワークを待っている場合に、現在のワークをグローバルキューにバランスさせる（共有する）ためのメカニズムです。以前の`handoff`関数に相当する機能が、`gcWork`抽象化の内部に組み込まれたと考えられます。
    *   コミットメッセージにある「`gcDrain`が満たされたワークバッファから開始し、現在のバッファが満たされた場合（`greyobject`内）、部分的に満たされた、または空のワークバッファを取得する」という動作は、`gcWork`抽象化が内部でこれらのバッファプール（`work.partial`, `work.empty`, `work.full`）をより賢く管理するようになったことを示唆しています。

4.  **`gcDrainN`の変更**:
    *   `gcDrain`と同様に、`gcw *gcWork`を引数に取り、`gcw.tryGet()`でオブジェクトを取得するようになりました。`tryGet()`は、ワークがない場合に`0`を返すことで、`gcDrainN`の処理を終了させます。

5.  **`markroot`、`scanstack`、`shade`、`gchelpwork`、`gchelper`、`gcmark_m`、`gc`の変更**:
    *   これらの関数は、GCの様々なフェーズやコンテキストでワークバッファを操作する部分です。
    *   以前は`m.currentwbuf`を直接操作したり、`getpartialorempty`、`getfull`、`putfull`、`putempty`といった低レベルの関数を呼び出したりしていました。
    *   変更後、これらの関数は`gcWork`または`gcWorkProducer`のインスタンスをローカルで作成し、`initFromCache()`で初期化し、`dispose()`または`disposeToCache()`で終了処理を行うようになりました。これにより、ワークバッファのライフサイクル管理が`gcWork`抽象化に委譲され、コードが大幅に簡素化されました。特に、`xchguintptr(&getg().m.currentwbuf, 0)`のような直接的なポインタ操作がなくなりました。

### 変更の意図と効果

*   **コードのモジュール化と簡素化**: ワークバッファ管理のロジックが`gcWork`抽象化に集約されたことで、GC関連の各関数の責任が明確になり、コードの可読性と保守性が向上しました。
*   **効率的なワークバッファ利用**: `gcWork`抽象化は、内部でワークバッファのプール（`empty`, `partial`, `full`）をより効率的に管理し、無駄なバッファの取得や解放を減らすことを目的としています。特に、`gcDrain`の動作変更は、定常状態でのバッファ利用の安定化を目指しています。
*   **正確性の向上**: ワークバッファ管理の複雑さが抽象化の背後に隠蔽されることで、GCのロジックにおける潜在的なバグのリスクが低減されます。
*   **ライトバリアの最適化**: `shade`関数が実際にオブジェクトをグレイ化する場合にのみワークバッファを取得するようになったことで、不要なワークバッファの取得が削減され、ライトバリアのオーバーヘッドが軽減される可能性があります。

コミットメッセージで言及されている「デュアルワークバッファスキーム」は、このコミットの時点ではまだ完全には実装されていない理想的な解決策として示唆されています。このコミットは、その将来的な改善に向けた基盤を築くものと言えます。

## 変更の背景

Goのガベージコレクタは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行してガベージコレクションを行います。このプロセスにおいて、GCはヒープ上のオブジェクトを走査し、到達可能なオブジェクトをマークするために「ワークバッファ」と呼ばれる一時的なデータ構造を使用します。これらのワークバッファには、走査すべきオブジェクトへのポインタが格納されます。

このコミット以前は、ワークバッファの管理が「アドホック」、つまり特定の状況に合わせて場当たり的に実装されており、統一された抽象化が欠けていました。これにより、以下のような問題が発生していました。

1.  **複雑なロジック**: ワークバッファの取得、解放、再利用のロジックが様々なGC関連関数に散在し、コードの可読性や保守性が低下していました。
2.  **非効率なバッファ利用**: `gcDrain`や`greyobject`のような関数がワークバッファを非効率的に利用するケースがありました。例えば、`gcDrain`が空のバッファを受け取った直後にそれを破棄し、新しいバッファを要求するといった無駄な操作が発生していました。これは、GCのパフォーマンスに悪影響を与える可能性がありました。
3.  **冗長な操作**: `shade`関数のように、オブジェクトが既にマーク済みであるにもかかわらず、無条件にワークバッファを取得するような冗長な処理が存在していました。

これらの問題を解決し、GCのワークバッファ管理をより体系的かつ効率的にするために、`gcWork`という新しい抽象化が導入されました。この抽象化は、ワークバッファのライフサイクル管理を一元化し、GCコード全体の健全性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクタの基本的な概念と、それに伴う用語を理解しておく必要があります。

### Goのガベージコレクタ (GC)

GoのGCは、主に以下のフェーズで動作します。

*   **マークフェーズ (Mark Phase)**: プログラムが使用しているオブジェクト（到達可能なオブジェクト）を特定し、マークします。GoのGCは並行マークを採用しており、アプリケーションの実行と並行してマーク処理を進めます。
*   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不可能なオブジェクト、つまりガベージ）を解放し、メモリを再利用可能にします。

### ワークバッファ (Work Buffer)

マークフェーズにおいて、GCはヒープ上のオブジェクトを走査し、そこから参照されている他のオブジェクトを「グレイ化」（走査待ちの状態にする）します。グレイ化されたオブジェクトは、後で走査されるために一時的に「ワークバッファ」に格納されます。ワークバッファは、GCワーカーゴルーチン間で共有されるキューのような役割を果たします。

*   **`greyobject`**: オブジェクトをグレイ化し、ワークバッファに追加する関数。
*   **`gcDrain`**: ワークバッファからグレイオブジェクトを取り出し、それらを走査（ブラック化）する関数。
*   **`work.empty`**: 空のワークバッファのプール。
*   **`work.partial`**: 部分的に満たされたワークバッファのプール。
*   **`work.full`**: 完全に満たされたワークバッファのプール。

### ポインタ走査 (Pointer Scanning)

GCは、オブジェクト内のポインタを識別し、それらが指すオブジェクトもマークする必要があります。このプロセスをポインタ走査と呼びます。

*   **`scanobject`**: 特定のオブジェクトを走査し、その中のポインタを識別してグレイ化する関数。
*   **`scanblock`**: メモリブロックを走査し、その中のポインタを識別してグレイ化する関数。

### ライトバリア (Write Barrier)

並行GCでは、アプリケーションがGC中にヒープを変更する可能性があります。この変更によってGCがオブジェクトを見落とすことを防ぐために、「ライトバリア」が使用されます。ライトバリアは、ポインタの書き込み時に特定の処理（例えば、新しい参照先のオブジェクトをグレイ化する）を実行するメカニズムです。

*   **`shade`**: ライトバリアの一部として機能し、ポインタの書き込み時に新しい参照先のオブジェクトをグレイ化する関数。

### `m.currentwbuf`

各M（Machine、OSスレッドに相当）は、GC作業のために自身のローカルなワークバッファ（`m.currentwbuf`）を持つことができます。これにより、グローバルなワークキューへのアクセス競合を減らし、キャッシュ効率を向上させます。

## 技術的詳細

このコミットの核心は、GCのワークバッファ管理を`gcWork`および`gcWorkProducer`という新しい構造体にカプセル化することです。これにより、ワークバッファの取得、解放、オブジェクトの追加、取得といった操作が、これらの抽象化を通じて行われるようになります。

### `gcWork`と`gcWorkProducer`

コミットの差分からは、`gcWork`と`gcWorkProducer`が導入されたことがわかります。具体的な構造体の定義はこのコミットの範囲外ですが、その使用方法から役割を推測できます。

*   **`gcWorkProducer`**: 主にオブジェクトをワークバッファに追加する（`put`）役割を担うインターフェースまたは構造体。`greyobject`や`scanobject`といった、オブジェクトをグレイ化してキューに入れる関数がこれを使用します。`initFromCache()`で初期化され、`dispose()`または`disposeToCache()`でリソースを解放します。
*   **`gcWork`**: 主にワークバッファからオブジェクトを取得する（`get`、`tryGet`）役割を担うインターフェースまたは構造体。`gcDrain`のような、ワークバッファを消費してオブジェクトを走査する関数がこれを使用します。また、`balance()`のようなワークのバランスを取る機能も提供するようです。

### ワークバッファ管理の変更点

1.  **`greyobject`の変更**:
    *   以前は`*workbuf`を引数に取り、`*workbuf`を返していました。これは、`greyobject`がワークバッファが満杯になった場合に新しいワークバッファを取得し、それを呼び出し元に返すという責任を負っていたことを意味します。
    *   変更後、`gcw *gcWorkProducer`を引数に取り、`void`を返します。ワークバッファの管理は`gcw`内部に抽象化され、`greyobject`は単に`gcw.put(obj)`を呼び出すだけでよくなりました。これにより、`greyobject`のロジックが簡素化され、ワークバッファの取得・解放の複雑さが隠蔽されます。
    *   オブジェクトが既にマークされている場合や、走査不要なオブジェクトの場合、以前は`wbuf`をそのまま返していましたが、変更後は単に`return`するだけになりました。これは、`gcWorkProducer`が内部でこれらのケースを適切に処理するか、あるいは`put`操作自体が不要になることを示唆しています。

2.  **`scanobject`、`scanblock`の変更**:
    *   これらの関数も`*workbuf`の代わりに`gcw *gcWorkProducer`を受け取るようになり、`void`を返すようになりました。これにより、オブジェクト走査の過程で発見されたポインタのグレイ化が、`gcWorkProducer`の抽象化を通じて行われるようになります。

3.  **`gcDrain`の変更**:
    *   以前は`*workbuf`を引数に取り、ワークバッファが空になった場合に`getfull`で新しいバッファを取得していました。
    *   変更後、`gcw *gcWork`を引数に取り、`gcw.get()`でオブジェクトを取得するようになりました。`gcw.get()`が`0`を返した場合、ワークがなくなったと判断してループを終了します。
    *   `work.nwait > 0 && work.full == 0`の場合に`gcw.balance()`を呼び出すようになりました。これは、他のプロセッサがワークを待っている場合に、現在のワークをグローバルキューにバランスさせる（共有する）ためのメカニズムです。以前の`handoff`関数に相当する機能が、`gcWork`抽象化の内部に組み込まれたと考えられます。
    *   コミットメッセージにある「`gcDrain`が満たされたワークバッファから開始し、現在のバッファが満たされた場合（`greyobject`内）、部分的に満たされた、または空のワークバッファを取得する」という動作は、`gcWork`抽象化が内部でこれらのバッファプール（`work.partial`, `work.empty`, `work.full`）をより賢く管理するようになったことを示唆しています。

4.  **`gcDrainN`の変更**:
    *   `gcDrain`と同様に、`gcw *gcWork`を引数に取り、`gcw.tryGet()`でオブジェクトを取得するようになりました。`tryGet()`は、ワークがない場合に`0`を返すことで、`gcDrainN`の処理を終了させます。

5.  **`markroot`、`scanstack`、`shade`、`gchelpwork`、`gchelper`、`gcmark_m`、`gc`の変更**:
    *   これらの関数は、GCの様々なフェーズやコンテキストでワークバッファを操作する部分です。
    *   以前は`m.currentwbuf`を直接操作したり、`getpartialorempty`、`getfull`、`putfull`、`putempty`といった低レベルの関数を呼び出したりしていました。
    *   変更後、これらの関数は`gcWork`または`gcWorkProducer`のインスタンスをローカルで作成し、`initFromCache()`で初期化し、`dispose()`または`disposeToCache()`で終了処理を行うようになりました。これにより、ワークバッファのライフサイクル管理が`gcWork`抽象化に委譲され、コードが大幅に簡素化されました。特に、`xchguintptr(&getg().m.currentwbuf, 0)`のような直接的なポインタ操作がなくなりました。

### 変更の意図と効果

*   **コードのモジュール化と簡素化**: ワークバッファ管理のロジックが`gcWork`抽象化に集約されたことで、GC関連の各関数の責任が明確になり、コードの可読性と保守性が向上しました。
*   **効率的なワークバッファ利用**: `gcWork`抽象化は、内部でワークバッファのプール（`empty`, `partial`, `full`）をより効率的に管理し、無駄なバッファの取得や解放を減らすことを目的としています。特に、`gcDrain`の動作変更は、定常状態でのバッファ利用の安定化を目指しています。
*   **正確性の向上**: ワークバッファ管理の複雑さが抽象化の背後に隠蔽されることで、GCのロジックにおける潜在的なバグのリスクが低減されます。
*   **ライトバリアの最適化**: `shade`関数が実際にオブジェクトをグレイ化する場合にのみワークバッファを取得するようになったことで、不要なワークバッファの取得が削減され、ライトバリアのオーバーヘッドが軽減される可能性があります。

コミットメッセージで言及されている「デュアルワークバッファスキーム」は、このコミットの時点ではまだ完全には実装されていない理想的な解決策として示唆されています。このコミットは、その将来的な改善に向けた基盤を築くものと言えます。

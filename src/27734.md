# [インデックス 27734] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおいて、構造体（struct）が分解される際のフィールドの命名規則を改善するものです。具体的には、構造体の各フィールドがSSA形式で個別の変数として扱われる際に、そのフィールド名が適切に反映されるように変更されています。これにより、特にデバッグ時や、コンパイラがこれらの分解された変数をメモリに「スピル」（退避）させる際に、より意味のある名前が使用されるようになります。

## コミット

```
cmd/compile: fix naming of decomposed structs

When a struct is SSAable, we will name its component parts
by their field names. For example,
type T struct {
     a, b, c int
}
If we ever need to spill a variable x of type T, we will
spill its individual components to variables named x.a, x.b,
and x.c.

Change-Id: I857286ff1f2597f2c4bbd7b4c0b936386fb37131
Reviewed-on: https://go-review.googlesource.com/21389
Reviewed-by: David Chase <drchase@google.com>
```

## 変更の背景

Goコンパイラは、最適化のためにソースコードをSSA（Static Single Assignment）形式という中間表現に変換します。このSSA変換の過程で、構造体やスライス、文字列、インターフェースなどの複合型は、その内部の基本型（プリミティブ型）のコンポーネントに分解されることがあります。例えば、`struct { a int; b int }`という構造体は、SSA内部では`a`と`b`という2つの独立した`int`型変数として扱われることがあります。

この分解されたコンポーネントが、レジスタに収まらずメモリに退避される（スピルされる）場合、コンパイラはこれらのコンポーネントに内部的な名前を割り当てます。しかし、以前の実装では、これらの内部名が元のソースコードのフィールド名（例: `x.a`）と直接的に対応していない場合がありました。これにより、デバッグ時に特定の構造体フィールドの値を確認しようとした際に、コンパイラ内部の抽象的な名前しか表示されず、デバッグ体験が損なわれる可能性がありました。

このコミットの目的は、分解された構造体フィールドに、元のソースコードのフィールド名に基づいた、より意味のある名前を割り当てることで、コンパイラの内部表現とソースコードの対応関係を強化し、特にデバッグの利便性を向上させることにあります。

## 前提知識の解説

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換するプログラムです。複数のステージを経てコンパイルが行われます。
*   **SSA (Static Single Assignment) 形式**: コンパイラ最適化の分野で広く用いられる中間表現（IR）の一種です。SSA形式では、各変数がプログラム中で一度だけ代入されるという特性を持ちます。これにより、データフロー解析が容易になり、様々な最適化（例: 共通部分式除去、定数伝播）が効率的に行えるようになります。
*   **複合型の分解 (Decomposition)**: SSA変換の過程で、構造体、スライス、文字列、複素数、インターフェースなどの複合データ型は、その内部のより基本的な構成要素（フィールドやポインタ、長さなど）に分解されます。これにより、コンパイラは個々の要素に対してより細かい最適化を適用できるようになります。
*   **スピル (Spilling)**: コンパイラが変数をレジスタに割り当てられない場合（レジスタが不足している場合など）、その変数をメモリ（通常はスタック）に退避させる処理を指します。スピルされた変数は、必要に応じてメモリからレジスタにロードし直されます。
*   **`LocalSlot`**: GoコンパイラのSSAバックエンドにおける概念で、ソースコード上の変数やその一部（構造体フィールドなど）が、実行時にメモリ上のどこに配置されるか（スタック上のオフセットやレジスタなど）を示す抽象的な「場所」を表します。SSA形式では、`LocalSlot`が変数の「名前」として機能し、SSA値（実際のデータ）と関連付けられます。
*   **`NamedValues`**: SSAの`Func`（関数）オブジェクト内に存在するマップで、`LocalSlot`（変数の名前）と、その`LocalSlot`に対応するSSA `Value`（計算結果）のリストを関連付けます。これは、ソースコードの変数とSSA内部の値を結びつけるために重要です。

## 技術的詳細

このコミットは、Goコンパイラの`cmd/compile/internal/gc`パッケージ（フロントエンドの一部）と`cmd/compile/internal/ssa`パッケージ（SSAバックエンド）にまたがる変更を導入しています。

1.  **`src/cmd/compile/internal/gc/type.go`の変更**:
    *   `Type`構造体に`FieldName(i int) string`メソッドが追加されました。このメソッドは、構造体の`i`番目のフィールドの名前を文字列として返します。これは、SSAバックエンドが分解されたフィールドに意味のある名前を付けるために必要となる情報です。

2.  **`src/cmd/compile/internal/ssa/config.go`の変更**:
    *   `Frontend`インターフェースに`SplitStruct(LocalSlot, int) LocalSlot`メソッドが追加されました。これは、SSAバックエンドがフロントエンドに対して、特定の`LocalSlot`（構造体全体を表す）とフィールドインデックス`i`に基づいて、その構造体の`i`番目のフィールドに対応する新しい`LocalSlot`を生成するよう要求するためのインターフェースです。

3.  **`src/cmd/compile/internal/gc/ssa.go`の変更**:
    *   `ssaExport`構造体に`SplitStruct(name ssa.LocalSlot, i int) ssa.LocalSlot`メソッドが実装されました。このメソッドは、`Frontend`インターフェースで定義された`SplitStruct`の実装です。
    *   この実装の核心は、分解されたフィールドの`LocalSlot`を生成する際に、`name.N.Sym.Name + "." + st.FieldName(i)`という形式で名前を構築する点です。ここで`name.N.Sym.Name`は元の構造体変数の名前（例: `x`）、`st.FieldName(i)`は`i`番目のフィールド名（例: `a`）を指し、結果として`x.a`のような名前が生成されます。
    *   `PAUTO`（自動変数）かつ`Addrtaken`でない（アドレスが取られていない）場合には、新しい名前付き自動変数（`namedAuto`）が作成され、その`LocalSlot`が返されます。これにより、デバッガが認識しやすい名前が割り当てられます。それ以外の場合は、元の`LocalSlot`のオフセットを調整してフィールドを指すようにします。

4.  **`src/cmd/compile/internal/ssa/decompose.go`の変更**:
    *   `decomposeUser`関数が大幅に修正されました。この関数は、ユーザー定義の構造体をSSA形式で分解する役割を担います。
    *   構造体型の場合、`t.NumFields()`でフィールド数を取得し、各フィールドに対して`f.Config.fe.SplitStruct(name, i)`を呼び出して、フィールドごとの`LocalSlot`（名前）を取得します。
    *   元の構造体全体を表す`LocalSlot`に対応する`NamedValues`のエントリは削除され、代わりに各フィールドの`LocalSlot`とそれに対応するSSA `Value`が`NamedValues`に追加されます。
    *   `f.Names`スライス（関数内のすべての`LocalSlot`のリスト）も更新され、元の構造体の`LocalSlot`が削除され、分解されたフィールドの`LocalSlot`が追加されます。
    *   同様に、`decomposeBuiltIn`関数も、複素数、文字列、スライス、インターフェースなどの組み込み型が分解される際に、`f.Names`と`f.NamedValues`の管理を改善し、元の複合型の`LocalSlot`を削除し、そのコンポーネントの`LocalSlot`に置き換えるように変更されています。

これらの変更により、SSAバックエンドは、構造体のフィールドを分解する際に、よりセマンティックな名前を内部的に使用できるようになり、コンパイラのデバッグ情報がより正確で分かりやすいものになります。

## コアとなるコードの変更箇所

### `src/cmd/compile/internal/gc/ssa.go`

```go
 func (e *ssaExport) SplitStruct(name ssa.LocalSlot, i int) ssa.LocalSlot {
 	n := name.N.(*Node)
 	st := name.Type
 	ft := st.FieldType(i)
 	if n.Class == PAUTO && !n.Addrtaken {
 		// Note: the _ field may appear several times.  But
 		// have no fear, identically-named but distinct Autos are
 		// ok, albeit maybe confusing for a debugger.
 		x := e.namedAuto(n.Sym.Name+"."+st.FieldName(i), ft)
 		return ssa.LocalSlot{x, ft, 0}
 	}
 	return ssa.LocalSlot{n, ft, name.Off + st.FieldOff(i)}
 }
```

```go
 func (t *Type) FieldName(i int) string {

 }
```

## コアとなるコードの解説

このコミットの核心は、GoコンパイラのSSA中間表現において、構造体のフィールドが分解される際に、そのフィールドにソースコード上の名前を反映させるメカニズムを導入した点にあります。

1.  **`Type.FieldName(i int)`の追加**:
    *   これは、構造体の型情報から、特定のインデックス`i`を持つフィールドのシンボル名を取得するための基本的なユーティリティメソッドです。このメソッドがなければ、SSAバックエンドはフィールドのソースコード上の名前を知ることができません。

2.  **`Frontend.SplitStruct`インターフェースと`ssaExport.SplitStruct`の実装**:
    *   `Frontend`インターフェースに`SplitStruct`が追加されたことで、SSAバックエンドはフロントエンドに対して、構造体の特定のフィールドに対応する`LocalSlot`を要求できるようになりました。
    *   `ssaExport.SplitStruct`の実装は、この要求に応えるものです。特に重要なのは、`e.namedAuto(n.Sym.Name+"."+st.FieldName(i), ft)`という行です。ここで、元の構造体変数名（例: `x`）とフィールド名（例: `a`）を結合して`x.a`のような新しい名前を生成し、これを新しい`LocalSlot`に割り当てています。これにより、SSA内部で`x.a`という名前が認識され、デバッグ情報に反映されるようになります。
    *   `PAUTO`（自動変数）かつ`Addrtaken`でない場合の特別な処理は、コンパイラが一時的に生成する変数（アドレスが取られないため、最適化の対象になりやすい）に対して、より明確な名前を付けることを意図しています。

3.  **`decomposeUser`および`decomposeBuiltIn`の変更**:
    *   これらの関数は、実際に複合型をSSA形式のコンポーネントに分解する場所です。
    *   `decomposeUser`では、構造体型が検出されると、`SplitStruct`メソッドを使って各フィールドの`LocalSlot`を取得し、それらを`f.NamedValues`マップに登録します。これにより、元の構造体全体ではなく、個々のフィールドがSSA値と関連付けられるようになります。
    *   `f.Names`スライスの更新は、関数内で認識されるすべての`LocalSlot`のリストを正確に保つために行われます。元の構造体の`LocalSlot`は削除され、その代わりに分解されたフィールドの`LocalSlot`が追加されます。
    *   `decomposeBuiltIn`でも同様のロジックが適用され、複素数、文字列、スライス、インターフェースといった組み込みの複合型についても、分解されたコンポーネントが適切に命名され、`f.Names`と`f.NamedValues`に反映されるようになります。

これらの変更により、GoコンパイラのSSAバックエンドは、より詳細で意味のある変数名（特に構造体フィールドの場合）を内部的に保持できるようになり、デバッグ時の可視性が向上し、将来的なコンパイラ最適化の可能性も広がる可能性があります。

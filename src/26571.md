## 変更の背景

GoコンパイラのSSAバックエンドにおける共通部分式除去（CSE）の最適化処理には、以前から潜在的なバグが存在していました。このバグは、SSA `Value`をその`Aux`値に基づいてグループ化（パーティショニング）する際に、その`Aux`値の順序が適切に考慮されていない場合に発生する可能性がありました。具体的には、同じ`Aux`値を持つ複数の`Value`が存在する場合、それらの`Value`が処理される順序が非決定論的になり、CSEが共通部分式を正しく識別・除去できない状況が生じ得ました。

このコミットは、この特定のバグパターンを再現し、将来的に同様のバグが再発しないようにするためのテストケースを追加することで、コンパイラの堅牢性を向上させることを目的としています。コンパイラの最適化は非常に複雑であり、このようなエッジケースを捉えるテストは、長期的なコード品質とパフォーマンスの安定に不可欠です。

## 前提知識の解説

### 1. GoコンパイラとSSA (Static Single Assignment)

Goコンパイラは、ソースコードを機械語に変換する多段階のプロセスを経ます。その中で、最適化の重要なフェーズの一つとして、SSA（Static Single Assignment）形式への変換と、SSA形式上での様々な最適化があります。

*   **SSA形式**: プログラム中の各変数が一度だけ代入されるように変換された中間表現です。これにより、データフロー解析や最適化が非常に容易になります。Goコンパイラでは、抽象構文木（AST）からSSA形式に変換され、その後、多数の最適化パス（処理段階）が適用されます。SSA形式は、変数の定義と使用の関係を明確にし、コンパイラがプログラムの振る舞いをより正確に理解するのに役立ちます。

### 2. 共通部分式除去 (Common Subexpression Elimination, CSE)

CSEは、コンパイラの最も基本的な最適化手法の一つです。プログラム内で同じ計算が複数回行われている場合に、その計算を一度だけ行い、結果を再利用することで冗長な計算を排除し、実行速度を向上させます。

*   **例**: `x = a + b; y = c + d; z = a + b;` というコードがあった場合、`a + b`という計算は2回行われています。CSEはこれを `temp = a + b; x = temp; y = c + d; z = temp;` のように変換し、`a + b`の計算を1回に減らします。
*   **SSAにおけるCSE**: SSA形式では、各`Value`（計算結果）が一意であるため、同じ演算子（`Op`）、同じオペランド（`Args`）、同じ型（`Type`）、そして同じ補助情報（`Aux`値）を持つ`Value`は共通部分式と見なされ、除去の対象となります。

### 3. SSA `Value`と`Aux`値

GoコンパイラのSSAバックエンドでは、プログラムの各操作や計算結果が`Value`という構造体で表現されます。`Value`は、その操作の種類（`Op`）、型（`Type`）、オペランド（`Args`）、そして補助情報（`Aux`）などの重要なフィールドを持ちます。

*   **`Op`**: 実行される操作の種類を定義します（例: `OpAdd64`は64ビット整数の加算、`OpLoad`はメモリからの読み込み）。
*   **`Type`**: `Value`の計算結果の型を示します（例: `TypeInt64`は64ビット整数型）。
*   **`Args`**: `Value`の入力となる他の`Value`への参照です。例えば、`OpAdd64`の`Args`は加算される2つの数値を指します。
*   **`Aux`**: 特定の`Op`に対して追加の定数情報やメタデータを提供するフィールドです。`Aux`は、`Value`の同一性を判断する上で非常に重要です。
    *   例えば、`OpLoad`や`OpStore`のようなメモリ操作では、`Aux`フィールドはアクセスするメモリのオフセットや、グローバル変数などのシンボル情報を保持することがあります。
    *   `OpArg`（関数の引数）のような操作では、引数の名前や識別子を保持することがあります。
    *   CSEの文脈では、`Op`、`Type`、`Args`が同じであっても、`Aux`値が異なれば、それらの`Value`は異なるものと見なされます。逆に、`Aux`値が同じであれば、その`Value`はより「同じ」であると判断され、共通部分式として除去の対象となる可能性が高まります。

### 4. パーティショニングとソート

CSEのアルゴリズムでは、共通部分式を見つけるために`Value`をグループ化（パーティショニング）することが一般的です。このグループ化は、`Op`、`Type`、`Args`、`Aux`などの属性に基づいて行われます。

*   **パーティショニング**: 特定の属性（例: `Op`と`Aux`）が同じ`Value`を一つのグループにまとめるプロセスです。これにより、比較対象となる`Value`の数を減らし、効率的に共通部分式を探索できます。
*   **ソート**: グループ内の`Value`を特定の基準（例: `Aux`値やオペランドのハッシュ値）で順序付けることです。このコミットで言及されているバグは、`Aux`値でパーティショニングはするものの、そのパーティション内で`Aux`値によるソートが欠けていたために発生しました。これにより、同じ`Aux`値を持つ`Value`が異なる順序で処理され、CSEが期待通りに機能しない可能性がありました。ソートが欠けていると、アルゴリズムが同じ`Value`を異なるタイミングで異なるグループに配置してしまい、共通部分式を見落とす原因となります。

## 技術的詳細

このコミットが対処しようとしているバグは、GoコンパイラのSSA最適化パスにおけるCSEの実装に深く関連しています。CSEは、同じ演算、同じオペランド、同じ型、そして同じ`Aux`値を持つ`Value`を識別し、冗長な計算を排除することで、生成されるコードの効率を高めます。

問題の核心は、CSEが`Value`を比較する際に、`Aux`値に基づいて`Value`をグループ化（パーティショニング）するものの、そのグループ内で`Value`が処理される順序が`Aux`値によってソートされていなかった点にありました。これにより、特定の`Aux`値を持つ`Value`が複数存在し、それらがSSAグラフに特定の非決定論的な順序で現れると、CSEがそれらを共通部分式として正しく認識できない状況が発生しました。

具体的には、`OpAdd64`のような演算で、`Aux`値が`nil`の場合、オペランドの順序が異なっても結果が同じになる可能性があります（例: `arg1 + arg2` と `arg2 + arg1`）。しかし、`Aux`値が`nil`でない場合（例えば、`OpArg`のように引数の識別子を持つ場合）、`Aux`値自体が`Value`の一意性を決定する重要な要素となります。このバグは、`Aux`値が`nil`でない`Value`が複数存在し、それらがSSAグラフ内で特定の非最適な順序で配置された場合に顕在化します。CSEアルゴリズムが`Aux`値でパーティショニングする際に、そのパーティション内の`Value`の順序が非決定論的であると、一部の共通部分式が見過ごされることになります。これは、最適化の機会を失うだけでなく、コンパイラの出力が非決定論的になる可能性も示唆していました。

追加されたテストケース`TestCSEAuxPartitionBug`は、このシナリオを意図的に構築しています。複数の`OpAdd64`演算が、`OpArg`によって定義された`arg1`, `arg2`, `arg3`という引数をオペランドとして使用し、これらの`OpArg`がそれぞれ異なる`Aux`値（`arg1Aux`, `arg2Aux`, `arg3Aux`）を持つように設定されています。テストコードは、`r1`, `r2`, `r3`がすべて`arg1 + arg2`に相当し、`r4`, `r5`が`r1 + r2`に相当するような`Value`のシーケンスを生成します。

CSEが正しく機能すれば、`r1`, `r2`, `r3`のうち2つが除去され、`r4`, `r5`のうち1つが除去されるべきです。テストは、`cse(fun.f)`と`deadcode(fun.f)`を実行した後、`fun.values`マップを走査し、`OpInvalid`とマークされた`Value`の数をカウントすることで、期待される除去が行われたかどうかを検証します。`OpInvalid`は、SSA最適化パスによって除去された`Value`に設定される状態であり、その`Value`がもはや有効な計算ではないことを示します。

このテストは、`Aux`値によるパーティショニングとソートの不整合が、どのようにCSEの失敗につながるかを示す具体的な例を提供し、コンパイラの最適化ロジックの正確性を保証する上で重要な役割を果たします。このような詳細なテストケースは、コンパイラの複雑な最適化パスにおける微妙なバグを特定し、修正するために不可欠です。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/cse_test.go` の `TestCSEAuxPartitionBug`

このテスト関数は、GoコンパイラのSSAバックエンドにおけるCSEのバグを再現し、検出するために設計されています。

1.  **テスト環境のセットアップ**:
    *   `c := testConfig(t)`: テスト用のコンフィギュレーションを初期化し、テスト実行に必要な環境を準備します。
    *   `arg1Aux := "arg1-aux"`, `arg2Aux := "arg2-aux"`, `arg3Aux := "arg3-aux"`: `OpArg`操作に割り当てるユニークな`Aux`値を定義します。これらの`Aux`値は、CSEが`Value`を区別する際に重要な役割を果たし、バグの再現に不可欠です。

2.  **SSAグラフの構築**:
    *   `fun := Fun(c, "entry", ...)`: テスト用のSSA関数を構築します。この関数は、`entry`ブロックと`exit`ブロックを持ち、その中に一連のSSA `Value`が定義されます。
    *   `Valu(...)`: SSA `Value`を定義します。ここで重要なのは、`OpAdd64`と`OpArg`の組み合わせです。
        *   `Valu("arg1", OpArg, TypeInt64, 0, arg1Aux)`: `arg1`という名前の引数を定義し、`arg1Aux`という`Aux`値を割り当てます。`arg2`, `arg3`も同様に定義され、それぞれ異なる`Aux`値を持つことで、CSEのパーティショニングロジックをテストします。
        *   `Valu("r7", OpAdd64, TypeInt64, 0, nil, "arg3", "arg1")`: `arg3 + arg1`の計算を表す`Value`です。
        *   `Valu("r1", OpAdd64, TypeInt64, 0, nil, "arg1", "arg2")`: `arg1 + arg2`の計算を表す`Value`です。
        *   `Valu("r2", OpAdd64, TypeInt64, 0, nil, "arg1", "arg2")`: `r1`と同じ`arg1 + arg2`の計算を表す別の`Value`です。
        *   `Valu("r3", OpAdd64, TypeInt64, 0, nil, "arg1", "arg2")`: `r1`, `r2`と同じ`arg1 + arg2`の計算を表すさらに別の`Value`です。
        *   `Valu("r4", OpAdd64, TypeInt64, 0, nil, "r1", "r2")`: `r1 + r2`の計算を表す`Value`です。
        *   `Valu("r5", OpAdd64, TypeInt64, 0, nil, "r2", "r3")`: `r2 + r3`の計算を表す`Value`です。
    *   この構築されたグラフでは、`r1`, `r2`, `r3`はすべて論理的に同じ計算（`arg1 + arg2`）を表しています。同様に、`r4`と`r5`も論理的に同じ計算（`r1 + r2`または`r2 + r3`）を表しています。CSEが正しく機能すれば、これらの冗長な`Value`は除去されるべきです。テストは、これらの冗長な`Value`が特定の順序で配置されることで、バグが顕在化するように設計されています。

3.  **CSEの実行と検証**:
    *   `CheckFunc(fun.f)`: 関数の整合性をチェックし、SSAグラフが有効な状態であることを確認します。
    *   `cse(fun.f)`: 共通部分式除去（CSE）最適化パスを実行します。このパスがバグを含んでいる場合、期待される最適化が行われません。
    *   `deadcode(fun.f)`: デッドコード除去パスを実行します。CSEによって冗長と判断された`Value`は、このパスで最終的に除去され、`OpInvalid`とマークされます。
    *   `CheckFunc(fun.f)`: 再度、関数の整合性をチェックし、最適化後のグラフが有効であることを確認します。

4.  **結果の検証**:
    *   `s1Cnt := 2`: `r1`, `r2`, `r3`の中から除去されるべき`Value`の期待数（3つのうち2つが除去され、1つが残る）。
    *   `s2Cnt := 1`: `r4`, `r5`の中から除去されるべき`Value`の期待数（2つのうち1つが除去され、1つが残る）。
    *   `for k, v := range fun.values`: 構築されたSSA関数内のすべての`Value`を反復処理します。
    *   `if v.Op == OpInvalid`: `OpInvalid`は、最適化によって除去された`Value`に設定されるオペレーションです。この条件で、除去された`Value`を特定します。
    *   `switch k`: 除去された`Value`の名前（`k`）に基づいて、`s1Cnt`または`s2Cnt`をデクリメントします。
    *   `t.Errorf(...)`: 期待される除去が行われなかった場合、または予期しない`Value`が除去された場合にエラーを報告します。
    *   `if s1Cnt != 0 || s2Cnt != 0`: 最終的に、すべての期待される除去が行われたかどうかを確認します。この条件が真の場合、CSEが正しく機能しなかったことを意味し、テストは失敗します。

このテストは、`Aux`値のパーティショニングとソートの不整合によってCSEが失敗する特定のケースを巧妙に再現し、コンパイラの最適化ロジックの正確性を保証する上で非常に重要です。このようなテストは、コンパイラの進化とメンテナンスにおいて不可欠な安全網となります。

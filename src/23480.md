# [インデックス 23480] ファイルの概要

このコミットは、Goランタイムのスケジューラにおけるワークスティーリング（work stealing）メカニズムを最適化するものです。具体的には、他のプロセッサ（P）からゴルーチン（G）を奪う際に使用されていた中間バッファ `runqvictims` を廃止し、直接ターゲットのPの実行キュー（runq）にゴルーチンを配置するように変更することで、コピー処理と中間バッファの必要性を排除しています。これにより、ワークスティーリングの効率が向上し、ランタイムのオーバーヘッドが削減されます。

## 元コミット内容

```
runtime: eliminate runqvictims and a copy from runqsteal

Currently, runqsteal steals Gs from another P into an intermediate
buffer and then copies those Gs into the current P's run queue. This
intermediate buffer itself was moved from the stack to the P in commit
c4fe503 to eliminate the cost of zeroing it on every steal.

This commit follows up c4fe503 by stealing directly into the current
P's run queue, which eliminates the copy and the need for the
intermediate buffer. The update to the tail pointer is only committed
once the entire steal operation has succeeded, so the semantics of
stealing do not change.
```

## 変更の背景

Goランタイムのスケジューラは、複数の論理プロセッサ（P）間でゴルーチン（G）の負荷を分散するためにワークスティーリングというメカニズムを使用します。これは、アイドル状態のPが、過負荷状態の他のPからゴルーチンを「盗む」ことで、システム全体のスループットを向上させる手法です。

このコミット以前の `runqsteal` 関数では、ゴルーチンを盗む際に、まずターゲットのPからゴルーチンを `runqvictims` と呼ばれる中間バッファにコピーし、その後、その中間バッファから現在のPのローカル実行キュー（`runq`）に再度コピーするという二段階の処理が行われていました。

以前のコミット `c4fe503` では、この `runqvictims` バッファがスタックからPの構造体内に移動されました。これは、スタック上のバッファを毎回ゼロクリアするコストを削減するためでした。しかし、この変更後も、中間バッファへのコピーとそこからの再コピーという非効率な処理は残っていました。

本コミットの目的は、この残された非効率性を解消することです。中間バッファ `runqvictims` を完全に排除し、ゴルーチンを盗む際に直接現在のPの `runq` に配置することで、不要なコピー処理をなくし、ワークスティーリングのパフォーマンスをさらに向上させることを目指しています。これにより、メモリコピーのオーバーヘッドが削減され、スケジューラの応答性が向上します。

## 前提知識の解説

### Goランタイムスケジューラ (M, P, G)

Goランタイムスケジューラは、M（Machine/OSスレッド）、P（Processor/論理プロセッサ）、G（Goroutine）の3つの主要な要素で構成されます。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。OSスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行できます。
*   **P (Processor)**: 論理プロセッサを表し、Goコードを実行するためのコンテキストを提供します。PはMにアタッチされ、Gの実行キュー（`runq`）を管理します。Pの数は通常、CPUコアの数に設定されます（`GOMAXPROCS`）。
*   **M (Machine)**: OSスレッドを表します。MはPにアタッチされ、Pが管理するGを実行します。Mがブロックされると、ランタイムは別のMを起動して別のPにアタッチし、Gの実行を継続します。

### ローカル実行キュー (runq) とワークスティーリング

各Pは、自身が実行すべきゴルーチンのローカル実行キュー（`runq`）を持っています。通常、Pは自身の`runq`からゴルーチンを取り出して実行します。

しかし、あるPの`runq`が空になり、実行すべきゴルーチンがない場合、そのPはアイドル状態になります。このとき、ランタイムスケジューラは**ワークスティーリング**というメカニズムを発動します。アイドル状態のPは、他のPの`runq`からゴルーチンの一部を「盗み」、自身の`runq`に追加して実行を再開します。これにより、CPUリソースの有効活用と全体的なスループットの向上が図られます。

### `runqvictims` の役割（変更前）

本コミット以前は、ワークスティーリングの際に、ゴルーチンを盗むPは、ターゲットのPからゴルーチンを一時的に `runqvictims` という配列に格納していました。これは、盗んだゴルーチンを一度集めてから、自身の`runq`にまとめてコピーするための「中間バッファ」として機能していました。

### アトミック操作 (`atomicload`, `cas`, `atomicstore`)

Goランタイムは並行処理環境であり、複数のPが同時に共有データ構造（例: `runq`のヘッド/テールポインタ）にアクセスする可能性があります。このような状況でデータの整合性を保つために、アトミック操作が不可欠です。

*   **`atomicload`**: 指定されたメモリ位置から値をアトミックに読み込みます。他のスレッドからの書き込みと競合することなく、常に最新の値を読み込むことが保証されます。
*   **`cas` (Compare-And-Swap)**: 指定されたメモリ位置の値が期待値と一致する場合にのみ、その値を新しい値に更新します。この操作はアトミックであり、複数のスレッドが同時に更新を試みても、1つのスレッドのみが成功し、他のスレッドは失敗します。これにより、ロックなしで安全に共有データを更新できます。
*   **`atomicstore`**: 指定されたメモリ位置に値をアトミックに書き込みます。他のスレッドからの読み込みと競合することなく、書き込みが完全に完了することが保証されます。

これらの操作は、メモリバリア（memory barrier）を伴うことが多く、異なるCPUコア間でのメモリ操作の順序付けを保証し、可視性（visibility）の問題を防ぎます。

## 技術的詳細

このコミットの核心は、`runqsteal` 関数におけるゴルーチンのコピー処理を排除し、`runqvictims` 中間バッファを不要にすることです。

### `runqsteal` 関数の変更

変更前:
1.  `runqsteal` は、ターゲットP (`p2`) からゴルーチンを `_p_.runqvictims` に `runqgrab` を使って取得します。
2.  `runqvictims` に格納されたゴルーチンを、現在のP (`_p_`) の `runq` に一つずつコピーします。

変更後:
1.  `runqsteal` は、`runqgrab` を呼び出す際に、`_p_.runq` 自体と、現在の`runq`のテールポインタ `t` を `batchHead` として渡します。
2.  `runqgrab` は、盗んだゴルーチンを直接 `_p_.runq` の `t` から始まる位置に配置します。
3.  `runqsteal` は、`runqgrab` が成功した後に、`atomicstore` を使って `_p_.runqtail` を新しい値に更新します。これにより、盗んだゴルーチンが他のコンシューマ（P）から見えるようになります。

この変更により、`runqvictims` から `_p_.runq` への明示的なコピーループが削除され、メモリコピーのオーバーヘッドがなくなります。

### `runqgrab` 関数の変更

`runqgrab` 関数は、指定されたPからゴルーチンのバッチを取得する役割を担います。

変更前:
*   `func runqgrab(_p_ *p, batch []*g, stealRunNextG bool) uint32`
*   `batch` はスライスとして渡され、盗んだゴルーチンを格納する汎用的なバッファとして機能していました。

変更後:
*   `func runqgrab(_p_ *p, batch *[256]*g, batchHead uint32, stealRunNextG bool) uint32`
*   `batch` は、Pの`runq`である `[256]*g` 型の配列へのポインタとして渡されます。
*   `batchHead` は、ゴルーチンを配置し始める`runq`内のオフセット（現在の`runqtail`）を示します。
*   これにより、`runqgrab`は、盗んだゴルーチンを直接呼び出し元のPの`runq`の適切な位置に書き込むことができます。

### `_p_.runqvictims` の削除

`src/runtime/runtime2.go` の `p` 構造体から `runqvictims [128]*g` フィールドが削除されました。これは、中間バッファが不要になったためです。これにより、P構造体のメモリフットプリントがわずかに削減されます。

### テールポインタの更新のコミット

コミットメッセージにある「The update to the tail pointer is only committed once the entire steal operation has succeeded」という点は重要です。
`runqsteal` 関数では、`runqgrab` がゴルーチンを `_p_.runq` に書き込んだ後、最後に `atomicstore(&_p_.runqtail, t+n)` を実行します。このアトミックストア操作によって、初めて盗んだゴルーチンが現在のPの`runq`の有効なエントリとして認識されます。
もし、ゴルーチンを`runq`に書き込んでいる途中でPがクラッシュしたり、他の問題が発生したりした場合でも、テールポインタが更新されていない限り、それらのゴルーチンはまだ「有効な」状態ではないため、データの一貫性が保たれます。これは、ワークスティーリング操作の原子性を保証し、競合状態を防ぐための重要な設計です。

### リングバッファとしての `runq` の利用

`_p_.runq` は `[256]*g` という固定サイズの配列であり、`runqhead` と `runqtail` ポインタによってリングバッファとして機能します。ゴルーチンは `(head + i) % len(runq)` や `(tail + i) % len(runq)` のようにインデックスを計算してアクセスされます。これにより、キューの先頭と末尾が配列の境界に達しても、配列の先頭に戻って利用を継続できます。

## コアとなるコードの解説

### `src/runtime/proc1.go` の変更点

1.  **`runqgrab` 関数のシグネチャ変更**:
    *   変更前: `func runqgrab(_p_ *p, batch []*g, stealRunNextG bool) uint32`
    *   変更後: `func runqgrab(_p_ *p, batch *[256]*g, batchHead uint32, stealRunNextG bool) uint32`
    *   `batch` 引数が `[]*g` (スライス) から `*[256]*g` (配列へのポインタ) に変更されました。これは、`_p_.runq` 自体を指すようにするためです。
    *   `batchHead` 引数が追加され、これはゴルーチンを書き込む開始位置（リングバッファのオフセット）を示します。

2.  **`runqgrab` 内でのゴルーチン配置ロジックの変更**:
    *   `batch[0] = next.ptr()` が `batch[batchHead%uint32(len(batch))] = next.ptr()` に変更されました。
        *   `runnext` からゴルーチンを盗む場合、直接 `batchHead` で指定された位置に配置します。
    *   `batch[i] = _p_.runq[(h+i)%uint32(len(_p_.runq))]` が `g := _p_.runq[(h+i)%uint32(len(_p_.runq))]` と `batch[(batchHead+i)%uint32(len(batch))] = g` に変更されました。
        *   ターゲットPの`runq`からゴルーチンを読み込み (`g := ...`)、それを直接呼び出し元のPの`runq`の `batchHead` から始まる位置に書き込みます。これにより、中間バッファへのコピーが不要になります。

3.  **`runqsteal` 関数の変更**:
    *   `n := runqgrab(p2, _p_.runqvictims[:], stealRunNextG)` が `t := _p_.runqtail; n := runqgrab(p2, &_p_.runq, t, stealRunNextG)` に変更されました。
        *   `_p_.runqvictims` を使用する代わりに、現在のPの`runq`のテールポインタ `t` を取得し、その`t`を`batchHead`として`_p_.runq`自体を`runqgrab`に渡します。
    *   `gp := _p_.runqvictims[n]` が `gp := _p_.runq[(t+n)%uint32(len(_p_.runq))]` に変更されました。
        *   盗んだゴルーチンのうち1つを返す際も、`runqvictims` からではなく、直接`_p_.runq`から取得します。
    *   `for i := uint32(0); i < n; i++ { _p_.runq[(t+i)%uint32(len(_p_.runq))] = _p_.runqvictims[i] }` のループが削除されました。
        *   これが中間バッファからのコピー処理であり、`runqgrab`が直接`_p_.runq`に書き込むようになったため不要になりました。
    *   `atomicstore(&_p_.runqtail, t+n)` は残されており、盗んだゴルーチンが`runq`に書き込まれた後に、テールポインタをアトミックに更新することで、それらのゴルーチンがスケジューラから利用可能になったことを通知します。

### `src/runtime/runtime2.go` の変更点

1.  **`p` 構造体からの `runqvictims` フィールドの削除**:
    *   `runqvictims [128]*g // Used to stage victims from another p's runq` の行が削除されました。
    *   これにより、`p` 構造体のメモリフットプリントが削減され、ランタイムのメモリ使用効率が向上します。

これらの変更により、ワークスティーリングのパスから不要なメモリコピーと中間バッファが排除され、Goランタイムスケジューラの効率とパフォーマンスが向上します。

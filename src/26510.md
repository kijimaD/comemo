## 変更の背景

この変更は、Go 1.5 リリースで導入されたベンダー実験機能において、「go run」コマンドで発生したリグレッション（退行バグ）を修正するために行われました。具体的には、シンボリックリンクが絡むパスにおいて、`cmd/go` ツールが `internal` パッケージや `vendor` パッケージの可視性チェックを誤って行い、エラーを報告してしまう問題がありました。

Go 1.5 では、`GO15VENDOREXPERIMENT=1` 環境変数を通じてベンダーディレクトリのサポートが実験的に導入されました。これにより、プロジェクトのルートにある `vendor/` ディレクトリ内のパッケージが、そのプロジェクト内のコードからインポートできるようになりました。また、`internal/` ディレクトリ内のパッケージは、その親ディレクトリのツリー内からのみインポート可能という制約があります。これらのパス解決ロジックがシンボリックリンクを適切に扱えず、実際のファイルシステム上のパスと論理的なパスの乖離が問題を引き起こしていました。

コミットメッセージによると、この変更はリリースサイクル終盤に行われたため、リスクを最小限に抑えるために「エラーが報告される場合にのみシンボリックリンクを展開する」という戦略が取られました。これにより、既存の正常な動作に影響を与えず、問題のあるケースのみを修正することを目指しています。

## 前提知識の解説

### Go Modules と GOPATH (2016年時点)

このコミットが作成された2016年時点では、Go Modules はまだ存在せず、Go のプロジェクト管理は主に **GOPATH** に依存していました。GOPATH は Go のワークスペースのルートディレクトリを指し、ソースコード、コンパイル済みパッケージ、実行可能ファイルが特定のディレクトリ構造で配置されていました。

### Vendor ディレクトリ (`vendor/`)

Go 1.5 で実験的に導入され、Go 1.6 でデフォルトで有効になった **Vendor ディレクトリ** は、プロジェクトが依存する外部パッケージをプロジェクト自身のディレクトリツリー内にコピーして管理する仕組みです。これにより、依存関係の解決がより予測可能になり、ビルドの再現性が向上しました。`vendor/` ディレクトリ内のパッケージは、その親プロジェクト内からのみインポート可能です。

### Internal パッケージ (`internal/`)

Go 1.4 で導入された **Internal パッケージ** は、特定のパッケージをその親ディレクトリのツリー内からのみインポート可能にするための仕組みです。`internal/` ディレクトリの下に配置されたパッケージは、その `internal/` ディレクトリを含むモジュール（または GOPATH のルート）の外部からはインポートできません。これは、ライブラリの内部実装を外部に公開しないための強力なメカニズムです。

### シンボリックリンク (Symbolic Links)

**シンボリックリンク**（またはソフトリンク）は、ファイルシステム上の別のファイルやディレクトリへの参照（ポインタ）です。シンボリックリンク自体はデータを含まず、参照先のパス情報のみを持ちます。Go のツールチェーンがパスを解決する際に、シンボリックリンクを物理的なパスに展開せずに論理的なパスとして扱ってしまうと、`internal` や `vendor` の可視性ルールが正しく適用されないことがあります。例えば、シンボリックリンクを介して `internal` パッケージにアクセスしようとした場合、ツールがシンボリックリンクを辿らずに論理パスで判断すると、本来許可されないインポートが許可されたり、逆に許可されるべきインポートが拒否されたりする可能性があります。

### `go run`, `go build`, `go install` コマンド

*   **`go run`**: ソースファイルをコンパイルし、すぐに実行します。一時的な実行可能ファイルを生成し、実行後に削除します。
*   **`go build`**: ソースファイルをコンパイルし、実行可能ファイルまたはパッケージアーカイブを生成します。
*   **`go install`**: ソースファイルをコンパイルし、生成された実行可能ファイルまたはパッケージアーカイブを GOPATH (または Go Modules の場合は GOBIN) の適切な場所にインストールします。

これらのコマンドは、Go のパッケージ解決ロジックに深く依存しており、シンボリックリンクの扱いはその正確性に直接影響します。

### `filepath.EvalSymlinks` 関数

Go の標準ライブラリ `path/filepath` パッケージに含まれる `EvalSymlinks` 関数は、与えられたパスに含まれるすべてのシンボリックリンクを評価し、そのパスの最終的な物理的なパスを返します。この関数は、シンボリックリンクを解決して実際のファイルシステム上の場所を特定するために使用されます。

## 技術的詳細

このコミットの核心は、`cmd/go` ツールが `internal` および `vendor` パッケージの可視性チェックを行う際に、シンボリックリンクが絡むパスを正しく解決できるようにすることです。

変更の戦略は以下の通りです。

1.  **`expandPath` 関数の導入**: `src/cmd/go/main.go` に `expandPath` という新しいヘルパー関数が追加されました。この関数は `filepath.EvalSymlinks` を呼び出し、与えられたパスのシンボリックリンクを解決した物理パスを返します。シンボリックリンクの解決に失敗した場合は、元のパスをそのまま返します。
2.  **エラーパスでのみシンボリックリンクを展開**: `src/cmd/go/pkg.go` 内の `vendoredImportPath`、`disallowInternal`、`disallowVendorVisibility` といった、パッケージの可視性チェックを行う関数が修正されました。これらの関数は、パスのプレフィックスチェック（`hasFilePathPrefix`）が失敗した場合、つまりエラーが報告される可能性がある場合にのみ、`expandPath` を使用して関連するパス（`dir`, `root`, `srcDir`, `parent` など）のシンボリックリンクを展開するように変更されました。
3.  **既存の動作への影響を最小限に**: このアプローチにより、シンボリックリンクが存在しないか、シンボリックリンクがあっても既存のロジックで正しく解決されるケースでは、余分な `EvalSymlinks` の呼び出しが発生しません。これにより、パフォーマンスへの影響を抑えつつ、Go 1.5 のリグレッションを修正することが可能になりました。

具体的には、`hasFilePathPrefix(dir, root)` のようなパスの包含関係をチェックする際に、シンボリックリンクによって論理的なパスが期待通りでない場合に、物理パスに展開して再チェックすることで、正しい可視性判断を下せるようになります。

    func expandPath(p string) string {
        x, err := filepath.EvalSymlinks(p)
        if err == nil {
            return x
        }
        return p
    }

    		// Look for symlinks before reporting error.
    		dir = expandPath(dir)
    		root = expandPath(root)

    	if !hasFilePathPrefix(dir, root) || len(dir) <= len(root) || dir[len(root)] != filepath.Separator {

    	parent = expandPath(parent)

    	}

    	}

## コアとなるコードの解説

このコミットの主要な変更は、`src/cmd/go/main.go` に追加された `expandPath` 関数と、それが `src/cmd/go/pkg.go` 内のパッケージ解決ロジックに組み込まれた点です。

`expandPath` 関数は、Go の `path/filepath` パッケージが提供する `EvalSymlinks` 関数をラップしています。`EvalSymlinks` は、与えられたパスに含まれるシンボリックリンクをすべて解決し、そのパスの最終的な物理的な場所を返します。これにより、例えば `/home/user/project/symlink_to_src` のようなパスが、実際の `/home/user/project/src` という物理パスに変換されます。`expandPath` は、`EvalSymlinks` がエラーを返した場合（例えば、リンクが壊れている場合など）には元のパスをそのまま返すことで、堅牢性を確保しています。

`src/cmd/go/pkg.go` 内の `vendoredImportPath`、`disallowInternal`、`disallowVendorVisibility` の各関数は、Go のパッケージシステムにおける重要な可視性ルールを強制します。

*   `vendoredImportPath`: `vendor/` ディレクトリ内のパッケージが、その親プロジェクトからのみインポートされることを保証します。
*   `disallowInternal`: `internal/` パッケージが、その親ディレクトリツリー内からのみインポートされることを保証します。
*   `disallowVendorVisibility`: `vendor/` ディレクトリの可視性ルールを適用します。

これらの関数は、通常、`hasFilePathPrefix` のような関数を使って、あるパスが別のパスのサブディレクトリであるかどうかをチェックすることで、可視性ルールを適用します。しかし、シンボリックリンクが存在する場合、論理的なパスと物理的なパスが異なるため、このチェックが誤った結果を返す可能性がありました。

このコミットでは、これらのチェックが「エラーを報告する可能性のある」状況、つまり `hasFilePathPrefix` が最初に失敗した場合にのみ、`expandPath` を呼び出してパスを物理パスに展開し、再度チェックを行うように変更されました。この「エラーパスでのみ展開する」という戦略は、シンボリックリンクの解決に伴うオーバーヘッドを最小限に抑えつつ、シンボリックリンクが原因で発生する誤ったエラー報告を修正する効果的な方法です。

これにより、`go run`、`go build`、`go install` などのコマンドが、シンボリックリンクが使用されているプロジェクトにおいても、`internal` および `vendor` パッケージの可視性ルールを正しく適用し、Go 1.5 で発生したリグレッションが解消されました。

*   **`go build`**: ソースファイルをコンパイルし、実行可能ファイルまたはパッケージアーカイブを生成します。
*   **`go install`**: ソースファイルをコンパイルし、生成された実行可能ファイルまたはパッケージアーカイブを GOPATH (または Go Modules の場合は GOBIN) の適切な場所にインストールします。

これらのコマンドは、Go のパッケージ解決ロジックに深く依存しており、シンボリックリンクの扱いはその正確性に直接影響します。

### `filepath.EvalSymlinks` 関数

Go の標準ライブラリ `path/filepath` パッケージに含まれる `EvalSymlinks` 関数は、与えられたパスに含まれるすべてのシンボリックリンクを評価し、そのパスの最終的な物理的なパスを返します。この関数は、シンボリックリンクを解決して実際のファイルシステム上の場所を特定するために使用されます。

## 技術的詳細

このコミットの核心は、`cmd/go` ツールが `internal` および `vendor` パッケージの可視性チェックを行う際に、シンボリックリンクが絡むパスを正しく解決できるようにすることです。

変更の戦略は以下の通りです。

1.  **`expandPath` 関数の導入**: `src/cmd/go/main.go` に `expandPath` という新しいヘルパー関数が追加されました。この関数は `filepath.EvalSymlinks` を呼び出し、与えられたパスのシンボリックリンクを解決した物理パスを返します。シンボリックリンクの解決に失敗した場合は、元のパスをそのまま返します。
2.  **エラーパスでのみシンボリックリンクを展開**: `src/cmd/go/pkg.go` 内の `vendoredImportPath`、`disallowInternal`、`disallowVendorVisibility` といった、パッケージの可視性チェックを行う関数が修正されました。これらの関数は、パスのプレフィックスチェック（`hasFilePathPrefix`）が失敗した場合、つまりエラーが報告される可能性がある場合にのみ、`expandPath` を使用して関連するパス（`dir`, `root`, `srcDir`, `parent` など）のシンボリックリンクを展開するように変更されました。
3.  **既存の動作への影響を最小限に**: このアプローチにより、シンボリックリンクが存在しないか、シンボリックリンクがあっても既存のロジックで正しく解決されるケースでは、余分な `EvalSymlinks` の呼び出しが発生しません。これにより、パフォーマンスへの影響を抑えつつ、Go 1.5 のリグレッションを修正することが可能になりました。

具体的には、`hasFilePathPrefix(dir, root)` のようなパスの包含関係をチェックする際に、シンボリックリンクによって論理的なパスが期待通りでない場合に、物理パスに展開して再チェックすることで、正しい可視性判断を下せるようになります。

## コアとなるコードの変更箇所

### `src/cmd/go/go_test.go`

*   `TestSymlinksDoNotConfuseGoList` が `TestSymlinksList` にリネームされました。
*   **`TestSymlinksVendor`** という新しいテスト関数が追加されました。このテストは、シンボリックリンクが `vendor` ディレクトリの解決を混乱させないことを確認します。具体的には、シンボリックリンクされたディレクトリ内で `go run`, `go build`, `go install` を実行し、`vendor` パッケージのインポートが正しく機能することを確認します。
*   **`TestSymlinksInternal`** という新しいテスト関数が追加されました。このテストは、シンボリックリンクが `internal` パッケージの解決を混乱させないことを確認します。`TestSymlinksVendor` と同様に、シンボリックリンクされたディレクトリ内で `go run`, `go build`, `go install` を実行し、`internal` パッケージのインポートが正しく機能することを確認します。

### `src/cmd/go/main.go`

*   **`expandPath` 関数が追加されました。**
    ```go
    // expandPath returns the symlink-expanded form of path.
    func expandPath(p string) string {
        x, err := filepath.EvalSymlinks(p)
        if err == nil {
            return x
        }
        return p
    }
    ```

### `src/cmd/go/pkg.go`

*   **`vendoredImportPath` 関数が修正されました。**
    `hasFilePathPrefix(dir, root)` が失敗した場合に、`dir` と `root` を `expandPath` で展開してから再チェックするロジックが追加されました。
    ```go
    	if !hasFilePathPrefix(dir, root) {
    		// Look for symlinks before reporting error.
    		dir = expandPath(dir)
    		root = expandPath(root)
    	}
    	if !hasFilePathPrefix(dir, root) || len(dir) <= len(root) || dir[len(root)] != filepath.Separator {
    		fatalf("invalid vendoredImportPath: dir=%q root=%q separator=%q", dir, root, string(filepath.Separator))
    	}
    ```
*   **`disallowInternal` 関数が修正されました。**
    `srcDir` が `parent` のツリー外にあると判断された場合に、`srcDir` と `parent` を `expandPath` で展開してから `hasFilePathPrefix` で再チェックするロジックが追加されました。
    ```go
    	// Look for symlinks before reporting error.
    	srcDir = expandPath(srcDir)
    	parent = expandPath(parent)
    	if hasFilePathPrefix(filepath.Clean(srcDir), filepath.Clean(parent)) {
    		return p
    	}
    ```
*   **`disallowVendorVisibility` 関数が修正されました。**
    `srcDir` が `parent` のツリー外にあると判断された場合に、`srcDir` と `parent` を `expandPath` で展開してから `hasFilePathPrefix` で再チェックするロジックが追加されました。
    ```go
    	// Look for symlinks before reporting error.
    	srcDir = expandPath(srcDir)
    	parent = expandPath(parent)
    	if hasFilePathPrefix(filepath.Clean(srcDir), filepath.Clean(parent)) {
    		return p
    	}
    ```

## コアとなるコードの解説

このコミットの主要な変更は、`src/cmd/go/main.go` に追加された `expandPath` 関数と、それが `src/cmd/go/pkg.go` 内のパッケージ解決ロジックに組み込まれた点です。

`expandPath` 関数は、Go の `path/filepath` パッケージが提供する `EvalSymlinks` 関数をラップしています。`EvalSymlinks` は、与えられたパスに含まれるシンボリックリンクをすべて解決し、そのパスの最終的な物理的な場所を返します。これにより、例えば `/home/user/project/symlink_to_src` のようなパスが、実際の `/home/user/project/src` という物理パスに変換されます。`expandPath` は、`EvalSymlinks` がエラーを返した場合（例えば、リンクが壊れている場合など）には元のパスをそのまま返すことで、堅牢性を確保しています。

`src/cmd/go/pkg.go` 内の `vendoredImportPath`、`disallowInternal`、`disallowVendorVisibility` の各関数は、Go のパッケージシステムにおける重要な可視性ルールを強制します。

*   `vendoredImportPath`: `vendor/` ディレクトリ内のパッケージが、その親プロジェクトからのみインポートされることを保証します。
*   `disallowInternal`: `internal/` パッケージが、その親ディレクトリツリー内からのみインポートされることを保証します。
*   `disallowVendorVisibility`: `vendor/` ディレクトリの可視性ルールを適用します。

これらの関数は、通常、`hasFilePathPrefix` のような関数を使って、あるパスが別のパスのサブディレクトリであるかどうかをチェックすることで、可視性ルールを適用します。しかし、シンボリックリンクが存在する場合、論理的なパスと物理的なパスが異なるため、このチェックが誤った結果を返す可能性がありました。

このコミットでは、これらのチェックが「エラーを報告する可能性のある」状況、つまり `hasFilePathPrefix` が最初に失敗した場合にのみ、`expandPath` を呼び出してパスを物理パスに展開し、再度チェックを行うように変更されました。この「エラーパスでのみ展開する」という戦略は、シンボリックリンクの解決に伴うオーバーヘッドを最小限に抑えつつ、シンボリックリンクが原因で発生する誤ったエラー報告を修正する効果的な方法です。

これにより、`go run`、`go build`、`go install` などのコマンドが、シンボリックリンクが使用されているプロジェクトにおいても、`internal` および `vendor` パッケージの可視性ルールを正しく適用し、Go 1.5 で発生したリグレッションが解消されました。

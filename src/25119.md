# [インデックス 25119] ファイルの概要

このコミットは、`cmd/cgo` ツールにおける `gccgo` でのエクスポートされた関数の宣言方法を修正するものです。具体的には、Go関数をCコードから呼び出す際に生成されるヘッダーファイルとCコードの間のシンボル解決の仕組みを簡素化し、`buildmode=c-archive` や `c-shared` といったビルドモードでの問題を解決します。以前の複雑なマクロ定義と解除のプロセスを廃止し、C関数をヘッダーファイルで直接宣言し、`__asm__` 宣言をCコード側に移動することで、より直接的で堅牢な方法に変更しています。

## 変更の背景

Go言語の `cgo` ツールは、GoコードとC/C++コードの間で相互運用を可能にするための重要な機能です。特に `gccgo` コンパイラを使用する場合、Go関数をCから呼び出せるようにエクスポートする際に、特定の課題がありました。

以前の実装では、`gccgo` を使ってGo関数をCにエクスポートする際、`cgo` は2つの関数を生成していました。一つは `Cgoexp_` というプレフィックスを持つ実際のGo関数で、もう一つはそのGo関数を呼び出すC関数です。Go関数の名前はCの命名規則に合わないため、Cコードからは `__asm__` 修飾子を使ってGo関数の名前を指定する必要がありました。

この `__asm__` 宣言は、以前はエクスポートされるヘッダーファイル (`_cgo_export.h`) に含まれていました。しかし、このヘッダーファイルをインクルードするCコードが、エクスポートされたC関数を指すマクロ定義 (`#define`) を見てしまう問題がありました。これにより、Cコードは本来呼び出すべきC関数ではなく、直接Go関数を呼び出してしまう可能性がありました。この問題を回避するため、実際のCコードではそのマクロを `#undef` するという回りくどい方法が取られていました。

この「回りくどい」プロセスは、通常のビルドでは問題なく機能していました。しかし、`buildmode=c-archive` や `c-shared` といった、GoコードをCライブラリとしてビルドするモードでヘッダーファイルがエクスポートされるようになると、問題が顕在化しました。これらのビルドモードでは、Cコードが `_cgo_export.h` をインクルードした際に、マクロ定義によってGo関数が直接呼び出されてしまうことがありました。

なぜこれが問題かというと、Go関数を呼び出すC関数は、通常 `_cgo_wait_runtime_init_done` という関数を呼び出してGoランタイムの初期化が完了するのを待つという重要な処理を行っているからです。Go関数が直接呼び出されると、この初期化待ちの処理がスキップされ、Goランタイムが完全に準備できていない状態でGo関数が実行されてしまい、予期せぬ動作やクラッシュを引き起こす可能性がありました。

この問題は、`gccgo` を使用したテストが不足していたため、これまで表面化していませんでした。このコミットは、この複雑なプロセスを簡素化し、`buildmode` を使用する際の堅牢性を向上させることを目的としています。

## 前提知識の解説

### cgo
`cgo` はGo言語のツールであり、GoプログラムがC言語のコードを呼び出したり、C言語のコードからGo関数を呼び出したりすることを可能にします。これにより、既存のCライブラリをGoから利用したり、Goの機能をC/C++アプリケーションに組み込んだりすることができます。`cgo` は、GoとCの間のデータ変換やスタック管理などを自動的に処理するための接着コードを生成します。

### gccgo
`gccgo` は、Go言語のコンパイラ実装の一つで、GCC (GNU Compiler Collection) のフロントエンドとして機能します。Go言語の公式コンパイラである `gc` (Go Compiler) とは異なり、`gccgo` はGCCの最適化バックエンドを利用するため、生成されるバイナリの特性が異なる場合があります。`cgo` と連携してGo関数をCにエクスポートする際、`gccgo` は `gc` とは異なるコード生成戦略を取ることがあります。

### `__asm__` qualifier (GCC拡張)
`__asm__` 修飾子（または `asm` キーワード）は、GCC (GNU Compiler Collection) の拡張機能であり、C/C++コード内でアセンブリ言語の命令を直接記述したり、シンボルのリンケージ名を制御したりするために使用されます。このコミットの文脈では、Go関数がCの命名規則に合わない名前を持つ場合、CコードからそのGo関数を呼び出すために、`__asm__` を使ってCのシンボル名とGoのシンボル名をマッピングします。例えば、`extern void myGoFunc() __asm__("package.myGoFunc");` のように記述することで、Cコードからは `myGoFunc` という名前でGoの `package.myGoFunc` 関数を呼び出せるようになります。

### `_cgo_wait_runtime_init_done`
GoプログラムがCgoを介してCコードから呼び出される際、Goランタイムは適切に初期化されている必要があります。`_cgo_wait_runtime_init_done` は、Goランタイムの初期化が完了するまで待機するための内部関数です。Cgoによって生成されるC関数は、Go関数を呼び出す前にこの関数を呼び出すことで、Goランタイムが安全に利用できる状態であることを保証します。このステップをスキップすると、Goランタイムが未初期化の状態でGo関数が実行され、クラッシュや未定義の動作につながる可能性があります。

### `buildmode=c-archive` および `c-shared`
Goコンパイラには、Goコードを異なる形式でビルドするための `-buildmode` オプションがあります。
*   **`-buildmode=c-archive`**: GoパッケージをCアーカイブライブラリ (`.a` ファイル) としてビルドします。このアーカイブは、C/C++アプリケーションにリンクしてGo関数を呼び出すことができます。
*   **`-buildmode=c-shared`**: GoパッケージをC共有ライブラリ (`.so` または `.dylib` ファイル) としてビルドします。この共有ライブラリは、C/C++アプリケーションから動的にロードしてGo関数を呼び出すことができます。
これらのビルドモードは、Goの機能を既存のC/C++プロジェクトに統合する際に非常に有用ですが、Goランタイムの初期化やシンボル解決に関して特別な考慮が必要になります。

## 技術的詳細

このコミットが解決しようとしている問題は、`gccgo` を使用してGo関数をCにエクスポートする際のシンボル解決の複雑さに起因します。

1.  **Go関数の生成**: `cgo` は、エクスポートされるGo関数に対して `Cgoexp_` というプレフィックスを付けたGo関数を生成します。例えば、`MyGoFunc` というGo関数がエクスポートされる場合、内部的には `Cgoexp_MyGoFunc` のような名前のGo関数が生成されます。
2.  **C関数の生成**: 同時に、`cgo` はこの `Cgoexp_` プレフィックス付きGo関数を呼び出すためのC関数も生成します。このC関数は、エクスポートされるGo関数と同じ名前（例: `MyGoFunc`）を持ちます。このC関数は、Go関数を呼び出す前に `_cgo_wait_runtime_init_done` を呼び出す責任があります。
3.  **シンボル名のマッピング**: `Cgoexp_` プレフィックス付きGo関数の名前は、Cのリンカが直接認識できる形式ではないため、Cコードからは `__asm__` 修飾子を使って、Cのシンボル名とGoのシンボル名をマッピングする必要がありました。具体的には、`extern void Cgoexp_MyGoFunc() __asm__("package.Cgoexp_MyGoFunc");` のような宣言が生成されます。

**以前の「回りくどい」プロセス**:
*   `_cgo_export.h` ヘッダーファイルには、エクスポートされるC関数（例: `MyGoFunc`）の宣言と、`Cgoexp_` プレフィックス付きGo関数への `__asm__` 宣言の両方が含まれていました。
*   さらに、`#define MyGoFunc Cgoexp_MyGoFunc` のようなマクロ定義がヘッダーファイルに挿入されていました。これは、`_cgo_export.h` をインクルードするCコードが、エクスポートされたC関数をその名前（`MyGoFunc`）で参照したときに、自動的に `Cgoexp_MyGoFunc` (Go関数) を呼び出すようにするためでした。
*   しかし、実際のC関数を定義する `_cgo_export.c` ファイルでは、このマクロ定義が邪魔になるため、`#undef MyGoFunc` を使ってマクロを解除していました。これにより、`_cgo_export.c` 内では `MyGoFunc` がC関数として正しく定義され、`_cgo_wait_runtime_init_done` を呼び出すことができました。

**問題点**:
`buildmode=c-archive` や `c-shared` でビルドされたGoライブラリを使用するC/C++アプリケーションが `_cgo_export.h` をインクルードすると、そのアプリケーションのCコードは `#define MyGoFunc Cgoexp_MyGoFunc` を見てしまいます。その結果、アプリケーションは `MyGoFunc` を呼び出すつもりで、実際には `Cgoexp_MyGoFunc` (Go関数) を直接呼び出してしまいます。これにより、`_cgo_wait_runtime_init_done` がスキップされ、Goランタイムの初期化が不完全な状態でGo関数が実行される可能性がありました。

**このコミットによる解決策**:
このコミットは、この複雑なマクロのトリックを廃止し、より直接的なアプローチを採用します。
1.  `_cgo_export.h` ヘッダーファイルには、エクスポートされるC関数（例: `MyGoFunc`）の通常の宣言のみを記述します。これにより、ヘッダーファイルをインクルードするCコードは、常にC関数を正しく参照するようになります。
2.  `Cgoexp_` プレフィックス付きGo関数への `__asm__` 宣言は、`_cgo_export.c` ファイルに移動されます。これにより、`_cgo_export.c` 内でのみGo関数のシンボル名マッピングが行われ、外部のCコードには影響を与えません。

この変更により、Cコードは常に `_cgo_wait_runtime_init_done` を呼び出すC関数を介してGo関数を呼び出すようになり、Goランタイムの初期化が保証されます。

## コアとなるコードの解説

このコミットの核心は、`_cgo_export.h` (fgcch) と `_cgo_export.c` (fgcc) の両方に書き込まれるコードの変更にあります。

1.  **ヘッダーファイル (`fgcch`) からの変更**:
    *   削除された行:
        ```go
        fmt.Fprintf(fgcch, `extern %s %s %s __asm__("%s.%s");`, cRet, goName, cParams, gccgoSymbolPrefix, goName)
        fmt.Fprint(fgcch, "\n")
        fmt.Fprintf(fgcch, "#define %s %s\\n", exp.ExpName, goName)
        ```
        これらの行は、`Cgoexp_` プレフィックス付きGo関数への `__asm__` 宣言と、C関数名からGo関数名へのマクロ定義をヘッダーファイルに書き込んでいました。これらが削除されたことで、ヘッダーファイルはGo関数への直接的な参照やマクロによるリダイレクトを含まなくなります。
    *   追加された行:
        ```go
        fmt.Fprintf(fgcch, "extern %s %s %s;\\n", cRet, exp.ExpName, cParams)
        ```
        この行は、エクスポートされるC関数（`exp.ExpName`）の通常の `extern` 宣言をヘッダーファイルに書き込みます。これにより、ヘッダーファイルをインクルードするCコードは、期待通りにC関数を宣言し、参照できるようになります。

2.  **Cコードファイル (`fgcc`) への変更**:
    *   削除された行:
        ```go
        fmt.Fprintf(fgcc, "#undef %s\\n", exp.ExpName)
        ```
        この行は、`_cgo_export.c` ファイル内で、ヘッダーファイルで定義されたマクロを解除していました。ヘッダーファイルからマクロ定義が削除されたため、この `#undef` も不要となり削除されました。
    *   追加された行:
        ```go
        fmt.Fprintf(fgcc, `extern %s %s %s __asm__("%s.%s");`, cRet, goName, cParams, gccgoSymbolPrefix, goName)
        fmt.Fprint(fgcc, "\n")
        ```
        この行は、`Cgoexp_` プレフィックス付きGo関数への `__asm__` 宣言を `_cgo_export.c` ファイルに移動させます。これにより、Go関数へのシンボルマッピングは、C関数が実際に定義されている場所でのみ行われ、外部のCコードには影響を与えなくなります。

**変更の意図**:
この変更の主な意図は、シンボル解決のプロセスを簡素化し、`buildmode=c-archive` や `c-shared` のような特定のビルドモードでの問題を解決することです。ヘッダーファイルから `__asm__` 宣言とマクロ定義を削除し、C関数への通常の宣言のみを残すことで、外部のCコードは常にC関数を呼び出すようになります。そして、`_cgo_export.c` 内で `__asm__` 宣言を行うことで、C関数がGo関数を正しく呼び出せるようにします。これにより、`_cgo_wait_runtime_init_done` が常に実行されることが保証され、Goランタイムの初期化に関する問題が回避されます。

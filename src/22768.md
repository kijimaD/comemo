# [インデックス 22768] ファイルの概要

このコミットは、Go言語のARM64アーキテクチャ向けリンカおよびアセンブラにおいて、`.text`セクション（コードセクション）内の絶対アドレス指定を廃止し、PC相対アドレス指定に移行するための変更を導入しています。具体的には、新しいリロケーションタイプ `R_ADDRARM64` を導入し、ARM64の `ADRP` および `ADD` 命令の組み合わせを用いてアドレスを解決するようにリンカの挙動を修正しています。これにより、生成されるバイナリの柔軟性と互換性が向上します。

## 元コミット内容

`cmd/internal/obj/arm64`, `cmd/internal/ld`, `cmd/7l`: `.text`セクションにおける絶対アドレス指定を削除。
この変更は、`R_ADDRPOWER`に類似した`R_ADDRARM64`を導入するものです。
Issue #10112 を修正します。

## 変更の背景

この変更の主な背景には、現代のシステムにおけるバイナリの柔軟性とセキュリティ要件があります。

1.  **Position-Independent Code (PIC) の重要性**:
    *   **共有ライブラリ**: 共有ライブラリ（.soファイルなど）は、複数のプロセスによって異なるメモリ位置にロードされる可能性があります。絶対アドレス指定を使用すると、ロード時にアドレスを修正する「再配置」が必要になり、これはオーバーヘッドが大きく、メモリ効率も悪くなります。PC相対アドレス指定を用いるPICは、ロードアドレスに依存しないため、共有ライブラリに不可欠です。
    *   **Address Space Layout Randomization (ASLR)**: ASLRは、セキュリティ強化のためにプログラムのメモリレイアウトをランダム化する技術です。絶対アドレス指定はASLRと相性が悪く、攻撃者が予測可能なアドレスを利用するのを防ぐことができません。PC相対アドレス指定は、ASLRが有効な環境でも問題なく動作します。

2.  **ARM64アーキテクチャの特性**:
    *   ARM64アーキテクチャは、命令セットレベルでPC相対アドレス指定を強力にサポートしています。特に、`ADRP` (Address Page Relative) と `ADD` 命令の組み合わせは、64ビットのアドレス空間全体を効率的にPC相対で参照するための標準的なメカニズムです。
    *   以前のGoリンカでは、ARM64の`.text`セクションで絶対アドレス指定を使用していた可能性がありますが、これはARM64の設計思想や現代のOSの要件とは乖離していました。このコミットは、GoのARM64バイナリがより「慣用的」で効率的なアドレス指定メカニズムを使用するように調整するものです。

3.  **Issue #10112 の修正**:
    *   コミットメッセージに「Fixes #10112」とあることから、この変更が特定のバグや問題の解決を目的としていることがわかります。通常、このような問題は、絶対アドレス指定が原因で発生するリンカエラー、実行時エラー、または互換性の問題に関連しています。

これらの背景から、このコミットはGoのARM64バイナリの堅牢性、互換性、およびセキュリティを向上させるための重要なステップであると言えます。

## 前提知識の解説

### リロケーション (Relocation)

リロケーションとは、コンパイルされたオブジェクトファイル内のシンボリックな参照（関数名や変数名など）を、最終的な実行可能ファイルや共有ライブラリにおける実際のメモリ上のアドレスに解決するプロセスです。リンカは、このリロケーション情報に基づいて、コード内のアドレス参照を修正します。

### 絶対アドレス指定 (Absolute Addressing)

絶対アドレス指定は、メモリ上の特定の固定されたアドレスを直接参照する方法です。例えば、「アドレス `0x10000` にあるデータにアクセスする」といった形式です。これはシンプルですが、プログラムが常に同じメモリ位置にロードされることを前提とします。

### PC相対アドレス指定 (PC-relative Addressing)

PC相対アドレス指定は、プログラムカウンタ (PC) の現在値からの相対的なオフセットを用いてアドレスを指定する方法です。例えば、「現在の命令から100バイト先のデータにアクセスする」といった形式です。この方法は、コードがメモリ上のどこにロードされても正しく動作するため、Position-Independent Code (PIC) の実現に不可欠です。

### ELF (Executable and Linkable Format)

ELFは、Unix系オペレーティングシステム（Linuxなど）で広く使用されている、実行可能ファイル、オブジェクトファイル、共有ライブラリなどのバイナリファイルフォーマットです。ELFファイルには、コード、データ、シンボルテーブル、リロケーション情報などが含まれます。

### ARM64アーキテクチャ

ARM64は、ARMv8-Aアーキテクチャに基づく64ビットの命令セットアーキテクチャです。スマートフォン、タブレット、サーバーなど、幅広いデバイスで採用されています。ARM64は、効率的なPC相対アドレス指定をサポートするための特定の命令を提供しています。

#### `ADRP` (Address Page Relative) 命令

`ADRP`命令は、ARM64におけるPC相対アドレス指定の重要な構成要素です。これは、指定されたシンボルが存在する4KBのメモリページのベースアドレスを計算し、その結果をレジスタに格納します。
*   `ADRP Xd, <label>`: `Xd` レジスタに `<label>` が存在するページのベースアドレスをロードします。計算は現在のPCからの相対オフセットで行われます。

#### `ADD` 命令

`ADD`命令は、`ADRP`命令と組み合わせて使用され、`ADRP`で計算されたページベースアドレスに、ページ内の正確なオフセットを加算して、最終的な目的のアドレスを生成します。
*   `ADD Xd, Xd, :lo12:<label>`: `Xd` レジスタに格納されているページベースアドレスに、`<label>` のアドレスの下位12ビット（ページ内オフセット）を加算します。

この`ADRP`と`ADD`の2命令シーケンスにより、ARM64は広範囲のPC相対アドレスを効率的に表現できます。

### Goリンカ (`cmd/ld`)

Go言語のツールチェーンの一部であり、Goのソースコードから生成されたオブジェクトファイル（`.o`ファイル）を結合して、実行可能ファイルや共有ライブラリを生成する役割を担います。リンカは、リロケーション情報を処理し、最終的なバイナリ内のアドレスを解決します。

## 技術的詳細

このコミットの核心は、GoのARM64リンカがアドレス解決を行う方法を、絶対アドレス指定からPC相対アドレス指定へと変更した点にあります。

1.  **`R_ADDRARM64` リロケーションタイプの導入**:
    *   Goリンカは、独自のリロケーションタイプを定義しています。このコミットでは、ARM64アーキテクチャ専用の新しいリロケーションタイプ `R_ADDRARM64` が `cmd/internal/ld/link.go` および `cmd/internal/obj/link.go` に追加されました。
    *   この `R_ADDRARM64` は、コミットメッセージにあるように `R_ADDRPOWER` に類似しています。`R_ADDRPOWER` はPowerPCアーキテクチャで2つの命令（通常は `addis` と `add`）を組み合わせてアドレスを構築するリロケーションです。`R_ADDRARM64` も同様に、ARM64の `ADRP` と `ADD` の2つの命令を組み合わせてアドレスを構築することを意図しています。

2.  **ELFリロケーションタイプとのマッピング**:
    *   Goリンカは、内部のリロケーションタイプをELFファイルフォーマットが規定するリロケーションタイプにマッピングする必要があります。
    *   `src/cmd/internal/ld/elf.go` に、ARM64のELFリロケーションタイプである `R_AARCH64_ADR_PREL_PG_HI21` と `R_AARCH64_ADD_ABS_LO12_NC` が追加されました。
        *   `R_AARCH64_ADR_PREL_PG_HI21`: `ADRP` 命令のページ相対オフセット（上位21ビット）を解決するために使用されます。
        *   `R_AARCH64_ADD_ABS_LO12_NC`: `ADD` 命令のページ内オフセット（下位12ビット）を解決するために使用されます。`_NC` (No Check) は、このオフセットが常に12ビットに収まるため、オーバーフローチェックが不要であることを示します。
    *   `src/cmd/7l/asm.go` の `elfreloc1` 関数内で、`R_ADDRARM64` がこれら2つのELFリロケーションタイプに変換され、リンカが最終的なバイナリに書き込むリロケーションエントリが生成されます。

3.  **アセンブラの変更**:
    *   `src/cmd/internal/obj/arm64/asm7.go` は、GoのアセンブラがARM64命令を生成する方法を定義しています。
    *   このコミットでは、`AMOVW` (Move Word) や `AMOVD` (Move Double Word) のような命令がアドレスをロードする際に、直接的な絶対アドレス指定ではなく、`ADRP` と `ADD` 命令のシーケンスに変換されるように変更されました。これにより、アセンブラレベルでPC相対アドレス指定が強制されます。

4.  **アドレス解決ロジックの変更**:
    *   `src/cmd/7l/asm.go` の `archreloc` 関数は、実際のリロケーション処理を行います。`R_ADDRARM64` のケースが追加され、シンボルのアドレスと現在のPCからの相対オフセットに基づいて、`ADRP` と `ADD` 命令のオペランドが計算されます。
    *   この計算では、シンボルのアドレスをページアドレスとページ内オフセットに分割し、それぞれを `ADRP` と `ADD` 命令の適切なフィールドにエンコードします。

これらの変更により、GoのARM64バイナリは、より現代的で効率的なPC相対アドレス指定を利用するようになり、共有ライブラリとしての利用やASLRが有効な環境での動作が改善されます。

## コアとなるコードの解説

### `src/cmd/7l/asm.go` の変更

このファイルは、GoリンカのARM64バックエンドにおけるアセンブリとリロケーション処理の核心部分です。

#### `elfreloc1` 関数

```go
func elfreloc1(r *ld.Reloc, sectoff int64) int {
	// ... 既存のコード ...

	case ld.R_ADDRARM64:
		// two relocations: R_AARCH64_ADR_PREL_PG_HI21 and R_AARCH64_ADD_ABS_LO12_NC
		ld.Thearch.Vput(ld.R_AARCH64_ADR_PREL_PG_HI21 | uint64(elfsym)<<32)
		ld.Thearch.Vput(uint64(r.Xadd))
		ld.Thearch.Vput(uint64(sectoff + 4))
		ld.Thearch.Vput(ld.R_AARCH64_ADD_ABS_LO12_NC | uint64(elfsym)<<32)

	// ... 既存のコード ...
}
```
`elfreloc1` は、Goリンカの内部リロケーションタイプをELFリロケーションタイプに変換し、ELFファイルに書き込むリロケーションエントリを生成します。
`ld.R_ADDRARM64` の場合、2つのELFリロケーションエントリを生成します。
1.  `R_AARCH64_ADR_PREL_PG_HI21`: `ADRP` 命令のページ相対オフセットを解決するためのリロケーション。
2.  `R_AARCH64_ADD_ABS_LO12_NC`: `ADD` 命令のページ内オフセットを解決するためのリロケーション。
`ld.Thearch.Vput` は、リロケーション情報をELFファイルに書き込むためのヘルパー関数です。`r.Xadd` はリロケーションの加算値（オフセット）を含み、`sectoff + 4` は2番目の命令（`ADD`）のアドレスを示します。

#### `archreloc` 関数

```go
func archreloc(r *ld.Reloc, s *ld.LSym, val *int64) int {
	// ... 既存のコード ...

	case ld.R_ADDRARM64:
		r.Done = 0

		// the first instruction is always at the lower address, this is endian neutral;
		// but note that o0 and o1 should still use the target endian.
		o0 := ld.Thelinkarch.ByteOrder.Uint32(s.P[r.Off : r.Off+4])
		o1 := ld.Thelinkarch.ByteOrder.Uint32(s.P[r.Off+4 : r.Off+8])

		// when laid out, the instruction order must always be o1, o2.
		if ld.Ctxt.Arch.ByteOrder == binary.BigEndian {
			*val = int64(o0)<<32 | int64(o1)
		} else {
			*val = int64(o1)<<32 | int64(o0)
		}

		// set up addend for eventual relocation via outer symbol.
		rs := r.Sym
		r.Xadd = r.Add
		for rs.Outer != nil {
			r.Xadd += ld.Symaddr(rs) - ld.Symaddr(rs.Outer)
			rs = rs.Outer
		}

		if rs.Type != ld.SHOSTOBJ && rs.Sect == nil {
			ld.Diag("missing section for %s", rs.Name)
		}
		r.Xsym = rs

		return 0

	// ... 既存のコード ...

	case ld.R_ADDRARM64:
		t := ld.Symaddr(r.Sym) + r.Add - ((s.Value + int64(r.Off)) &^ 0xfff)
		if t >= 1<<32 || t < -1<<32 {
			ld.Diag("program too large, address relocation distance = %d", t)
		}

		// the first instruction is always at the lower address, this is endian neutral;
		// but note that o0 and o1 should still use the target endian.
		o0 := ld.Thelinkarch.ByteOrder.Uint32(s.P[r.Off : r.Off+4])
		o1 := ld.Thelinkarch.ByteOrder.Uint32(s.P[r.Off+4 : r.Off+8])

		o0 |= (uint32((t>>12)&3) << 29) | (uint32((t>>12>>2)&0x7ffff) << 5)
		o1 |= uint32(t&0xfff) << 10

		// when laid out, the instruction order must always be o1, o2.
		if ld.Ctxt.Arch.ByteOrder == binary.BigEndian {
			*val = int64(o0)<<32 | int64(o1)
		} else {
			*val = int64(o1)<<32 | int64(o0)
		}
		return 0

	// ... 既存のコード ...
}
```
`archreloc` 関数は、実際のリロケーション処理を実行し、命令のオペランドを修正します。
`ld.R_ADDRARM64` の最初のケースでは、リロケーションの準備を行います。`r.Xadd` にシンボルへのオフセットを設定し、外部シンボルがある場合はそのアドレスも考慮に入れます。
2番目の `ld.R_ADDRARM64` のケースが、`ADRP` と `ADD` 命令のオペランドを計算し、命令のビットパターンを修正する核心部分です。
*   `t` は、ターゲットシンボルアドレスと現在の命令アドレス（PC）からの相対オフセットを計算します。
*   `o0` と `o1` は、それぞれ `ADRP` と `ADD` 命令の元のビットパターンを表します。
*   `o0 |= ...` と `o1 |= ...` の行で、計算された相対オフセット `t` を `ADRP` と `ADD` 命令の適切なビットフィールドにエンコードします。
    *   `ADRP` はページ相対オフセット（`t` の上位ビット）をエンコードします。
    *   `ADD` はページ内オフセット（`t` の下位12ビット）をエンコードします。
*   最終的に、修正された命令のビットパターンが `*val` に格納されます。

### `src/cmd/internal/obj/arm64/asm7.go` の変更

このファイルはARM64アセンブラの命令エンコーディングを定義しています。

#### `asmout` 関数

```go
func asmout(ctxt *obj.Link, p *obj.Prog, o *Optab, out []uint32) {
	// ... 既存のコード ...

	case 64: /* movT R,addr -> adrp + add + movT R, (REGTMP) */
		o1 = ADR(1, 0, REGTMP)
		o2 = opirr(ctxt, AADD) | REGTMP&31<<5 | REGTMP&31
		rel := obj.Addrel(ctxt.Cursym)
		rel.Off = int32(ctxt.Pc)
		rel.Siz = 8
		rel.Sym = p.To.Sym
		rel.Add = p.To.Offset
		rel.Type = obj.R_ADDRARM64
		o3 = olsr12u(ctxt, int32(opstr12(ctxt, int(p.As))), 0, REGTMP, int(p.From.Reg))

	case 65: /* movT addr,R -> adrp + add + movT (REGTMP), R */
		o1 = ADR(1, 0, REGTMP)
		o2 = opirr(ctxt, AADD) | REGTMP&31<<5 | REGTMP&31
		rel := obj.Addrel(ctxt.Cursym)
		rel.Off = int32(ctxt.Pc)
		rel.Siz = 8
		rel.Sym = p.From.Sym
		rel.Add = p.From.Offset
		rel.Type = obj.R_ADDRARM64
		o3 = olsr12u(ctxt, int32(opldr12(ctxt, int(p.As))), 0, REGTMP, int(p.To.Reg))

	case 68: /* movT $vconaddr(SB), reg -> adrp + add + reloc */
		if p.As == AMOVW {
			ctxt.Diag("invalid load of 32-bit address: %v", p)
		}
		o1 = ADR(1, 0, uint32(p.To.Reg))
		o2 = opirr(ctxt, AADD) | uint32(p.To.Reg&31)<<5 | uint32(p.To.Reg&31)
		rel := obj.Addrel(ctxt.Cursym)
		rel.Off = int32(ctxt.Pc)
		rel.Siz = 8
		rel.Sym = p.From.Sym
		rel.Add = p.From.Offset
		rel.Type = obj.R_ADDRARM64

	// ... 既存のコード ...
}
```
`asmout` 関数は、Goのアセンブリ命令を実際の機械語命令に変換する役割を担います。
`case 64`, `case 65`, `case 68` は、それぞれ異なる形式のメモリアクセス命令（例: `MOV` 命令でアドレスをロード/ストアする）を処理します。
これらのケースでは、もはや単一の命令で絶対アドレスを扱うのではなく、以下のようなシーケンスを生成します。
1.  `ADR(1, 0, REGTMP)`: `ADRP` 命令を生成し、一時レジスタ (`REGTMP`) にページベースアドレスをロードします。
2.  `opirr(ctxt, AADD) | ...`: `ADD` 命令を生成し、`REGTMP` にページ内オフセットを加算します。
3.  `obj.Addrel(ctxt.Cursym)`: `R_ADDRARM64` タイプのリロケーションエントリをリンカに追加します。これにより、リンカが最終的なアドレスを解決する際に、この `ADRP` と `ADD` のペアを適切に処理できるようになります。

この変更により、アセンブラはアドレス参照を自動的にPC相対形式に変換し、リンカがそのリロケーションを処理するという、ARM64の慣用的なアプローチに準拠するようになります。

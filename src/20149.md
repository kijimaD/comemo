# [インデックス 20149] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）のトレース（`gctrace`）機能使用時に発生していたデッドロックを修正するものです。特に、`ReadMemStats`関数が`stoptheworld`（STW）操作を実行する際に、`m0`（メインのM）がロックを保持している状況がデッドロックの原因となっていました。この修正は、STW操作の安全性を高め、特定の状況下でのデッドロックを回避することを目的としています。

## 元コミット内容

このコミットは、Goランタイムにおいて`gctrace`が有効な場合に発生するデッドロックを修正します。デッドロックの原因は、`ReadMemStats`関数が`stoptheworld`操作を実行する際に、`m0`（メインのOSスレッド）がロックを保持していることでした。ロックを保持したまま`stoptheworld`を呼び出すことはデッドロックの温床となるため、この状況を避けるための変更が加えられました。また、`g0`（スケジューラ用のゴルーチン）上で`stoptheworld`を呼び出すことについても、その動作が保証されていないため、チェックが追加されました。この修正により、スカベンジャー（メモリ解放プロセス）が出力する統計情報の一部（ヒープからのスタック使用量の減算）が不正確になる可能性がありますが、デッドロックを回避できる方が重要であると判断されています。

## 変更の背景

Goランタイムのガベージコレクション（GC）は、プログラムの実行を一時停止させる「Stop-the-World (STW)」フェーズを含みます。このSTWフェーズ中、すべてのユーザーゴルーチンは停止し、GCが安全にメモリを操作できるようになります。`stoptheworld`関数は、このSTWフェーズを開始するためのGoランタイム内部の重要な関数です。

問題は、`gctrace`（GCの動作を詳細に出力するデバッグ機能）が有効な場合に、`ReadMemStats`関数が呼び出されることでした。`ReadMemStats`は、メモリ統計情報を収集するために内部的に`stoptheworld`を呼び出すことがあります。しかし、この呼び出しが`m0`（GoランタイムのメインOSスレッド）が既に何らかのロックを保持している状況で発生すると、デッドロックが発生する可能性がありました。

デッドロックは、複数のプロセスやスレッドが互いに相手が保持しているリソースの解放を待機し、結果としてどのプロセスも進行できなくなる状態です。このケースでは、`m0`がロックを保持したままSTWを開始しようとすると、他のOSスレッド（M）がそのロックを待機している可能性があり、STWが完了できず、システム全体が停止してしまうという問題がありました。

また、`g0`（GoランタイムのスケジューラやGCなどの内部処理を実行するための特別なゴルーチン）上で`stoptheworld`を呼び出すことについても、その動作が十分にテストされておらず、予期せぬ問題を引き起こす可能性がありました。

このコミットは、これらのデッドロックの可能性を排除し、ランタイムの安定性を向上させることを目的としています。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステムです。スケジューラ、ガベージコレクタ、メモリ管理、システムコールインターフェースなどが含まれます。Goプログラムは、OS上で直接実行されるのではなく、このランタイム上で動作します。
*   **ガベージコレクション (Garbage Collection, GC)**: プログラムが不要になったメモリを自動的に解放するプロセスです。GoのGCは並行（concurrent）に動作しますが、一部のフェーズではすべてのユーザーゴルーチンを一時停止させる「Stop-the-World (STW)」メカニズムを使用します。
*   **Stop-the-World (STW)**: GCの特定のフェーズ（例えば、マークフェーズの開始やスイープフェーズの終了など）で、すべてのユーザーゴルーチンを一時的に停止させるメカニズムです。これにより、GCはメモリの状態が変化しないことを保証しながら安全に作業を行うことができます。STWは、Goプログラムのレイテンシに影響を与える可能性があるため、GoランタイムはSTWの時間を最小限に抑えるように設計されています。
*   **`gctrace`**: Goランタイムのデバッグオプションの一つで、GCの動作に関する詳細なログを標準エラー出力に出力します。GCの実行時間、ヒープサイズ、STWの時間などが含まれ、GCのパフォーマンスを分析する際に役立ちます。
*   **M (Machine)**: GoランタイムのスケジューラにおけるOSスレッドを表す構造体です。MはP（Processor）にアタッチされ、PはG（Goroutine）を実行します。`m0`は、Goプログラムが起動した際に最初に作成されるメインのOSスレッドです。
*   **G (Goroutine)**: Goにおける軽量な実行単位です。OSスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行できます。`g0`は、各Mに紐付けられた特別なゴルーチンで、スケジューラやGCなどのランタイム内部の処理を実行するために使用されます。ユーザーコードは`g0`上では実行されません。
*   **`stoptheworld`関数**: Goランタイム内部で、すべてのユーザーゴルーチンを停止させるために呼び出される関数です。この関数が呼び出されると、ランタイムはすべてのPを停止させ、新しいゴルーチンの実行をブロックします。
*   **ロック (Locks)**: 複数のスレッドやゴルーチンが共有リソースに同時にアクセスするのを防ぐための同期メカニズムです。ロックが保持されている間は、他のスレッドはそのリソースにアクセスできません。
*   **デッドロック (Deadlock)**: 複数のプロセスやスレッドが、互いに相手が保持しているリソースの解放を待機し、結果としてどのプロセスも進行できなくなる状態です。
*   **`ReadMemStats`関数**: `runtime`パッケージで提供される関数で、Goプログラムの現在のメモリ統計情報（ヒープの使用量、GCの回数など）を`runtime.MemStats`構造体に読み込みます。
*   **スカベンジャー (Scavenger)**: Goランタイムのメモリ管理の一部で、不要になったメモリページをOSに解放する役割を担います。これにより、Goプログラムが使用する物理メモリの量を削減できます。

## 技術的詳細

このコミットの核心は、Goランタイムの並行処理とメモリ管理におけるデッドロックの回避です。

1.  **デッドロックの原因**:
    *   `gctrace`が有効な場合、`scavenge`関数内で`runtime.ReadMemStats`が呼び出されていました。
    *   `runtime.ReadMemStats`は、正確なメモリ統計情報を取得するために、内部的に`stoptheworld`操作を実行することがあります。
    *   問題は、この`stoptheworld`が`m0`（メインのOSスレッド）上で、かつ`m0`が既に何らかのランタイム内部ロック（例えば、スケジューラのロックなど）を保持している状態で呼び出される可能性があったことです。
    *   `stoptheworld`は、すべてのM（OSスレッド）を停止させる必要がありますが、もし他のMが`m0`が保持しているロックを待機している場合、`stoptheworld`は完了できません。同時に、`m0`はSTWが完了するまでロックを解放できないため、循環的な待機が発生し、デッドロックに陥ります。

2.  **`g0`上での`stoptheworld`の問題**:
    *   `g0`はランタイム内部処理専用のゴルーチンであり、ユーザーゴルーチンとは異なる特殊なコンテキストで動作します。
    *   `stoptheworld`が`g0`上で呼び出された場合の動作は、十分にテストされておらず、予期せぬ挙動を引き起こす可能性がありました。このコミットでは、このような呼び出しを明示的に禁止することで、ランタイムの堅牢性を高めています。

3.  **修正アプローチ**:
    *   **ロック保持中の`stoptheworld`の禁止**: `proc.c`に新しいチェックが追加され、`g->m->locks > 0`（現在のMがロックを保持している）の場合に`stoptheworld`が呼び出されると`throw`（パニックに似たランタイムエラー）が発生するようにしました。これにより、デッドロックの根本原因を排除します。
    *   **`g0`上での`stoptheworld`の禁止**: 同様に、`g == g->m->g0`（現在のゴルーチンが`g0`である）の場合に`stoptheworld`が呼び出されると`throw`が発生するようにしました。
    *   **`scavenge`からの`ReadMemStats`呼び出しの変更**: `mheap.c`の`scavenge`関数内で`runtime.ReadMemStats`を呼び出すのをやめ、代わりにグローバルな`mstats`変数から直接統計情報を取得するように変更しました。これにより、`scavenge`がロックを保持している可能性のある状況で`stoptheworld`が間接的に呼び出されることを防ぎます。
    *   **`gogc`におけるMの解放と再取得**: `malloc.go`の`gogc`関数において、`stoptheworld`を呼び出す前に現在のMを解放し（`releasem(mp)`）、STW後に再度取得する（`acquirem()`）ように変更しました。これにより、STW中にMが他の処理に再スケジュールされる可能性を考慮し、`stoptheworld`が安全に実行されることを保証します。もし再スケジュールされた場合は`gothrow("gogc: rescheduled")`でエラーを発生させます。
    *   **`heapdump.c`におけるロックカウンタの調整**: `runtime∕debug·WriteHeapDump`関数内で、`stoptheworld`の呼び出し前後に`g->m->locks`カウンタのインクリメント/デクリメントのタイミングが調整されました。これは、`stoptheworld`がロックを保持していない状態で呼び出されることを保証するためです。

4.  **トレードオフ**:
    *   `scavenge`関数内で`ReadMemStats`を呼び出さないようにした結果、`gctrace`が出力するスカベンジャー関連の統計情報（特にヒープからのスタック使用量の減算）が不正確になる可能性があるとコミットメッセージに記載されています。これは、正確な統計情報を取得するためにSTWが必要である一方で、STWがデッドロックを引き起こすリスクがあるため、安定性を優先したトレードオフです。デッドロックを回避できることの方が、一時的な統計情報の不正確さよりも重要であるという判断がなされています。

この修正は、Goランタイムの並行処理モデルとGCの複雑な相互作用を理解し、潜在的な競合状態やデッドロックを特定して解決する、高度なデバッグと設計の成果と言えます。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

1.  **`src/pkg/runtime/heapdump.c`**:
    *   `runtime∕debug·WriteHeapDump`関数内で、`stoptheworld()`呼び出し前の`g->m->locks++;`が削除され、`starttheworld()`呼び出し後の`g->m->locks++;`が追加されました。

2.  **`src/pkg/runtime/malloc.go`**:
    *   `gogc`関数内で、`stoptheworld()`呼び出しの直前に`releasem(mp)`が追加され、`mp = nil`が設定されます。
    *   `stoptheworld()`呼び出し後、`if mp != acquirem() { gothrow("gogc: rescheduled") }`というチェックが追加されました。
    *   `gogc`関数の最後で、`releasem(mp)`の後に`mp = nil`が追加されました。

3.  **`src/pkg/runtime/mheap.c`**:
    *   `scavenge`関数内で、`MStats stats;`の宣言と`runtime·ReadMemStats(&stats);`の呼び出しが削除されました。
    *   `runtime·printf`の呼び出しで、`stats.heap_inuse`などが`mstats.heap_inuse`に直接変更されました。
    *   `// TODO(dvyukov): these stats are incorrect as we don't subtract stack usage from heap. // But we can't call ReadMemStats on g0 holding locks.`というコメントが追加されました。

4.  **`src/pkg/runtime/proc.c`**:
    *   `runtime·stoptheworld`関数内に、以下の2つの`throw`チェックが追加されました。
        *   `if(g->m->locks > 0) { runtime·throw("stoptheworld: holding locks"); }`
        *   `if(g == g->m->g0) { runtime·throw("stoptheworld: on g0"); }`

## コアとなるコードの解説

各変更箇所の意図と、それがデッドロック修正にどのように寄与するかを解説します。

1.  **`src/pkg/runtime/heapdump.c` の変更**:
    *   **変更前**: `stoptheworld()`を呼び出す直前に`g->m->locks++`を実行していました。これは、`stoptheworld`が実行される時点で、現在のMがロックを保持している状態になることを意味します。
    *   **変更後**: `g->m->locks++`を`stoptheworld()`の呼び出し後、かつ`starttheworld()`の呼び出し前に移動しました。
    *   **意図**: この変更により、`stoptheworld()`が呼び出される際には、現在のMが`locks`カウンタをインクリメントしていない（つまり、明示的にロックを保持していない）状態であることを保証します。これは、`proc.c`で追加された「ロック保持中の`stoptheworld`禁止」チェックと連携し、デッドロックの発生を防ぎます。`g->m->gcing = 1;`はGC中であることを示すフラグであり、`g->m->locks`とは異なる目的で使用されます。

2.  **`src/pkg/runtime/malloc.go` の変更**:
    *   **`releasem(mp)` と `mp = nil` の追加**: `gogc`関数はGCの主要なロジックを含み、ここから`stoptheworld()`が呼び出されます。`stoptheworld()`の直前に現在のM（`mp`）を解放し、`mp`を`nil`に設定することで、`stoptheworld`が実行される際に、このゴルーチンが特定のMに強く紐付けられていない状態にします。これにより、STW中にMが他の処理に再スケジュールされる可能性を考慮し、より安全なSTWの開始を試みます。
    *   **`if mp != acquirem() { gothrow("gogc: rescheduled") }` のチェック**: `stoptheworld()`が完了した後、再度Mを取得し、それがSTW前に解放したMと同じであるかを確認します。もし異なるMが割り当てられた場合（つまり、STW中にMが再スケジュールされた場合）、これは予期せぬ状態であるため、`gothrow`でランタイムエラーを発生させます。これは、`stoptheworld`の呼び出し元が、STWの前後で同じMコンテキストを期待している場合に、その期待が満たされていることを保証するためのアサーションです。
    *   **最後の `mp = nil`**: `gogc`の処理が完了した後も、Mを解放し、`mp`を`nil`に設定することで、不要なMへの参照をクリアします。

3.  **`src/pkg/runtime/mheap.c` の変更**:
    *   **`MStats stats;` と `runtime·ReadMemStats(&stats);` の削除**: `scavenge`関数は、メモリのスカベンジング（解放）を行う際に、`gctrace`が有効な場合にメモリ統計情報を出力していました。この統計情報を取得するために`runtime·ReadMemStats`を呼び出していましたが、これが間接的に`stoptheworld`を呼び出し、デッドロックの原因となっていました。
    *   **`mstats` の直接使用**: `runtime·ReadMemStats`の呼び出しを削除し、代わりにランタイムが内部的に保持しているグローバルな`mstats`変数から直接統計情報を取得するように変更しました。`mstats`は常に最新の状態に保たれているわけではないため、この変更により出力される統計情報が完全に正確ではなくなる可能性があります（特にスタック使用量がヒープから減算されない点）。
    *   **コメントの追加**: `// TODO(dvyukov): these stats are incorrect as we don't subtract stack usage from heap. // But we can't call ReadMemStats on g0 holding locks.` というコメントは、このトレードオフを明示しています。デッドロックを回避するために、統計情報の正確性を一部犠牲にしたことを示しています。

4.  **`src/pkg/runtime/proc.c` の変更**:
    *   **`stoptheworld: holding locks` チェック**: `runtime·stoptheworld`関数が呼び出された際に、現在のMが`g->m->locks > 0`である場合、つまり何らかのロックを保持している場合に、`runtime·throw`を発生させます。これは、ロックを保持したままSTWを開始しようとするとデッドロックが発生する可能性が高いため、そのような危険な状態でのSTWを明示的に禁止するガードレールです。
    *   **`stoptheworld: on g0` チェック**: 同様に、現在のゴルーチンが`g0`である場合に`runtime·throw`を発生させます。`g0`はランタイム内部の特別なゴルーチンであり、その上で`stoptheworld`が呼び出されることは想定されておらず、その動作も保証されていません。このチェックは、予期せぬ動作を防ぐための安全策です。

これらの変更は、Goランタイムの並行処理とメモリ管理の複雑な相互作用を考慮し、デッドロックの発生条件を特定し、それを回避するための具体的なメカニズムを導入しています。特に、`stoptheworld`の呼び出し条件を厳格化し、危険な状況での実行を防止することで、ランタイムの安定性と堅牢性を大幅に向上させています。

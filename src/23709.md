# [インデックス 23709] ファイルの概要

このコミットは、Goランタイムのガベージコレクタにおけるスタック管理、特にスタックバリアのインストールに関するバグ修正です。`src/runtime/mgcmark.go` ファイルは、Goのガベージコレクタのマーキングフェーズにおいて、ゴルーチンのスタックをスキャンし、必要に応じてスタックバリアをインストールするロジックを含んでいます。スタックバリアは、GCがスタックをスキャンしている間に、ゴルーチンがスタックを変更するのを防ぐ、または変更を検出するための重要なメカニズムです。

Author: Austin Clements <austin@google.com>
Date:   Fri Jun 5 11:07:21 2015 -0400

    runtime: use correct SP when installing stack barriers

    Currently the stack barriers are installed at the next frame boundary
    after gp.sched.sp + 1024*2^n for n=0,1,2,... However, when a G is in a
    system call, we set gp.sched.sp to 0, which causes stack barriers to
    be installed at *every* frame. This easily overflows the slice we've
    reserved for storing the stack barrier information, and causes a
    "slice bounds out of range" panic in gcInstallStackBarrier.

    Fix this by using gp.syscallsp instead of gp.sched.sp if it's
    non-zero. This is the same logic that gentraceback uses to determine
    the current SP.

    Fixes #11049.

## 元コミット内容

Goランタイムにおいて、スタックバリアをインストールする際に正しいスタックポインタ (SP) を使用するように修正します。

現在、スタックバリアは `gp.sched.sp + 1024*2^n` (n=0,1,2,...) の次のフレーム境界にインストールされています。しかし、ゴルーチン (G) がシステムコール中にいる場合、`gp.sched.sp` は0に設定されます。これにより、スタックバリアが「すべての」フレームにインストールされてしまい、スタックバリア情報を格納するために予約されたスライスが容易にオーバーフローし、`gcInstallStackBarrier` で "slice bounds out of range" パニックを引き起こしていました。

この問題を修正するため、`gp.syscallsp` が非ゼロの場合は `gp.syscallsp` を使用するように変更します。これは、`gentraceback` が現在のSPを決定するために使用しているロジックと同じです。

Issue #11049 を修正します。

## 変更の背景

Goのガベージコレクタ (GC) は、プログラムの実行と並行して動作します。GCがゴルーチンのスタックをスキャンしている最中に、そのゴルーチンがスタックを変更すると、GCの正確性が損なわれる可能性があります。これを防ぐために「スタックバリア」というメカニズムが導入されています。スタックバリアは、特定のスタックフレームに目印をつけ、GCがその目印を検出した際に適切な処理（例えば、スタックの再スキャンやゴルーチンの停止）を行うことで、GCとプログラム実行の並行性を保ちます。

このコミット以前のGoランタイムでは、スタックバリアをインストールする際に、ゴルーチンのスケジューラが管理するスタックポインタ `gp.sched.sp` を基準にしていました。しかし、ゴルーチンがシステムコール（OSの機能呼び出し）を実行している間、Goランタイムは `gp.sched.sp` を一時的に0に設定していました。これは、システムコール中はGoのスケジューラが直接スタックを管理しないためです。

この `gp.sched.sp` が0になるという特殊な状況が問題を引き起こしました。スタックバリアのインストールロジックは、`gp.sched.sp` を基準にスタックのオフセットを計算していましたが、`gp.sched.sp` が0になると、計算されるオフセットが常に非常に小さくなり、結果としてスタックの「すべての」フレームにスタックバリアをインストールしようとしました。スタックバリア情報を格納するための内部スライスには限りがあるため、すべてのフレームにバリアをインストールしようとすると、このスライスがすぐに満杯になり、「slice bounds out of range」というパニックが発生していました。これは、特にシステムコールを頻繁に利用するアプリケーションで発生しやすい深刻なバグでした。

## 前提知識の解説

### Goのガベージコレクション (GC) の概要

GoのGCは、並行マーク・スイープ方式を採用しています。これは、プログラムの実行と並行してオブジェクトの到達可能性をマークし、不要になったオブジェクトを解放する方式です。GCサイクル中には、プログラムの実行を一時停止する「ストップ・ザ・ワールド (STW)」フェーズもありますが、その時間は最小限に抑えられています。スタックスキャンはGCの重要なフェーズの一つで、実行中のゴルーチンのスタックを走査し、スタック上に存在するポインタを特定して、それらが参照するヒープオブジェクトをマークします。

### スタックバリア (Stack Barriers)

スタックバリアは、Goの並行GCにおいて、スタックスキャン中のゴルーチンのスタック変更を安全に処理するためのメカニズムです。GCがゴルーチンのスタックをスキャンしている最中に、そのゴルーチンが関数呼び出しや戻りによってスタックポインタを移動させたり、スタック上の値を変更したりすると、GCが誤った情報を基にオブジェクトをマークしたり、マークし損ねたりする可能性があります。

スタックバリアは、スタックフレームの特定の場所に「バリア」を設置することで機能します。GCがスタックをスキャンする際、このバリアに到達すると、GCはゴルーチンを一時停止させ、スタックの状態を安定させたり、必要な情報を記録したりします。これにより、GCはスタックの整合性を保ちつつ、並行して動作することができます。

### `gp.sched.sp` と `gp.syscallsp`

Goランタイムは、各ゴルーチン (`g` 構造体) の状態を管理しています。その中で、スタックポインタに関連する重要なフィールドが `gp.sched.sp` と `gp.syscallsp` です。

*   **`gp.sched.sp`**: これは「スケジューラが認識するスタックポインタ」です。Goのスケジューラがゴルーチンを管理し、Goコードを実行している際に使用されるスタックの現在のトップを指します。通常のGoコード実行中は、この値がゴルーチンの現在のスタックポインタを示します。
*   **`gp.syscallsp`**: これは「システムコール中のスタックポインタ」です。ゴルーチンがシステムコールに入ると、Goランタイムはスタックをシステムコール用に切り替えることがあります。このとき、`gp.syscallsp` はシステムコールに入る直前のGoスタックのスタックポインタを保持します。システムコール中は `gp.sched.sp` が0に設定されることがあり、`gp.syscallsp` が実際のGoスタックのコンテキストを保持する役割を担います。システムコールから戻ると、`gp.sched.sp` は元の値に戻されます。

### Goのゴルーチンとシステムコールの関係

Goのゴルーチンは軽量なスレッドであり、Goランタイムによってスケジューリングされます。ゴルーチンがファイルI/Oやネットワーク通信などのシステムコールを実行する場合、OSのカーネルモードに移行します。この際、Goランタイムはゴルーチンの状態を適切に管理する必要があります。特に、システムコール中はGoのスケジューラが直接ゴルーチンのスタックを管理しないため、`gp.sched.sp` のような値が一時的に無効になることがあります。

## 技術的詳細

このバグは、`src/runtime/mgcmark.go` 内の `scanstack` 関数で発生していました。この関数は、GCのマークフェーズ中にゴルーチンのスタックをスキャンし、必要に応じてスタックバリアをインストールします。

スタックバリアのインストール位置は、`gp.sched.sp` を基準に計算されていました。具体的には、`nextBarrier = gp.sched.sp + barrierOffset` のように、`gp.sched.sp` にオフセットを加算して次のバリア位置を決定していました。`barrierOffset` は最初は `firstStackBarrierOffset` であり、その後 `barrierOffset *= 2` のように指数関数的に増加していきます。これにより、スタックの深い位置から徐々に間隔を広げてバリアが設置されることを意図していました。

しかし、ゴルーチンがシステムコール中にいる場合、`gp.sched.sp` は0に設定されます。この状態で `nextBarrier = gp.sched.sp + barrierOffset` が計算されると、`nextBarrier` は常に `barrierOffset` と同じ値になります。`barrierOffset` はスタックの最下部からの相対オフセットとして機能するため、`gp.sched.sp` が0の場合、`nextBarrier` はスタックの非常に低いアドレスを指すことになります。

`scanstack` 関数は、スタックフレームを一つずつ遡りながら、現在のフレームのスタックポインタが `nextBarrier` を超えた場合に `gcInstallStackBarrier` を呼び出してバリアをインストールします。`gp.sched.sp` が0の場合、`nextBarrier` が常にスタックの非常に低い位置を指すため、ほとんどすべてのスタックフレームが `nextBarrier` を超えていると判断され、結果として「すべての」スタックフレームにスタックバリアをインストールしようとします。

スタックバリアの情報は、ゴルーチン (`g` 構造体) 内の `stkbar` というスライスに格納されます。このスライスは有限の容量しか持たないため、すべてのフレームにバリアをインストールしようとすると、`stkbar` スライスの容量を超過し、「slice bounds out of range」というパニックが発生していました。

この問題を解決するために、コミットでは `gp.syscallsp` を使用するように変更されました。`gp.syscallsp` は、ゴルーチンがシステムコール中にいる場合でも、システムコールに入る直前のGoスタックの有効なスタックポインタを保持しています。したがって、`gp.syscallsp` が非ゼロ（つまり、ゴルーチンがシステムコール中である可能性が高い）の場合は、`gp.syscallsp` をスタックバリアの基準点として使用することで、正しいスタックポインタに基づいてバリア位置が計算されるようになります。

この修正は、`gentraceback` 関数が現在のSPを決定する際に `gp.syscallsp` を使用するロジックと同じアプローチを取っており、一貫性があります。`gentraceback` はスタックトレースを生成する際に、システムコール中のゴルーチンのスタックを正しく辿るために `gp.syscallsp` を利用しています。

## コアとなるコードの解説

変更の核心は、`scanstack` 関数内でスタックポインタ `sp` を決定する新しいロジックです。

1.  **新しい `sp` 変数の導入**:
    ```go
    var sp, barrierOffset, nextBarrier uintptr
    ```
    `gp.sched.sp` を直接使用する代わりに、`sp` という新しい変数を導入し、この変数に適切なスタックポインタの値を設定するようにしました。

2.  **`gp.syscallsp` の優先使用**:
    ```go
    if gp.syscallsp != 0 {
        sp = gp.syscallsp
    } else {
        sp = gp.sched.sp
    }
    ```
    この条件分岐が最も重要な変更点です。
    *   `gp.syscallsp != 0` の場合、これはゴルーチンがシステムコール中であるか、またはシステムコールから戻ったばかりで `gp.syscallsp` が有効なスタックポインタを保持していることを意味します。この場合、`sp` に `gp.syscallsp` の値が設定されます。これにより、システムコール中のゴルーチンに対しても正しいスタックの基準点が提供されます。
    *   `gp.syscallsp == 0` の場合、ゴルーチンは通常のGoコードを実行しており、`gp.syscallsp` は使用されていません。この場合、従来通り `gp.sched.sp` の値が `sp` に設定されます。

3.  **`sp` 変数の使用**:
    以前は `gp.sched.sp` を直接使用していた箇所が、すべて新しく導入された `sp` 変数を使用するように変更されました。
    *   `nextBarrier = sp + barrierOffset`
    *   `print("rescan below ", hex(nextBarrier), " in [", hex(sp), ",", hex(gp.stack.hi), ") goid=", gp.goid, "\n")`

この変更により、ゴルーチンがシステムコール中に `gp.sched.sp` が0になる問題が回避され、スタックバリアが正しい位置に、適切な間隔でインストールされるようになりました。結果として、「slice bounds out of range」パニックが解消され、GCの安定性が向上しました。

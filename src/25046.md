# [インデックス 25046] ファイルの概要

このコミットは、Goアセンブラ（`cmd/asm`）におけるシンボル参照のパースエラー処理を改善するものです。特に、`amd64`アーキテクチャにおいて、装飾されていないシンボル参照（unadorned symbol reference）が不正なアドレッシングモードとして扱われる際に、より正確なエラーメッセージを出力するように修正されました。以前は、このようなケースで汎用的な「notfound」エラーが発生していましたが、この変更により「illegal addressing mode for symbol」という、より具体的なパースエラーが報告されるようになります。この修正は、`arm64`アーキテクチャにおける同様の問題の解決（#12632）に依存していました。

## 変更の背景

Goのアセンブラ（`cmd/asm`）は、Goプログラムが低レベルのハードウェア操作を必要とする場合に、Goコードとアセンブリコードを連携させるための重要なツールです。このコミット以前は、`amd64`アーキテクチャ向けのアセンブリコードにおいて、シンボルが適切に修飾されていない（例えば、即値を示す`$`や間接参照を示す`*`などのプレフィックスがない）場合に、アセンブラが誤解を招くエラーメッセージを出力していました。

具体的には、`ADDQ R520, R1`のような命令で`R520`がレジスタではなく未定義のシンボルとして扱われるべき場合、アセンブラはこれを`obj`パッケージに渡してしまい、結果として「`asm: doasm: notfound ft=23 tt=23 00000 (x.s:2) ADDQ 0, 0 23 23`」といった、シンボルが見つからないことを示す汎用的なエラーを出力していました。このエラーメッセージは、問題がシンボルの未定義ではなく、アドレッシングモードの誤用にあることを明確に示していませんでした。

この問題は、アセンブラのパースロジックが、ジャンプ命令とそれ以外の命令におけるシンボル参照の扱いを十分に区別していなかったことに起因します。ジャンプ命令の場合、シンボルは通常、ジャンプ先のアドレス（ラベル）を指しますが、一般的なデータ操作命令では、シンボルはメモリ上のアドレスや即値を指すため、適切なアドレッシングモードの指定が必要です。

このコミットは、この曖昧さを解消し、よりユーザーフレンドリーで正確なエラーメッセージを提供することを目的としています。コミットメッセージにあるように、この修正は`arm64`アーキテクチャ向けに先行して行われた同様の修正（#12632）に依存しており、その知見が`amd64`にも適用された形です。

## 前提知識の解説

### Goアセンブラ (`cmd/asm`)

Go言語は、必要に応じてアセンブリ言語で記述されたコードをGoプログラムに組み込むことができます。これは、特定のパフォーマンス要件を満たすためや、ハードウェア固有の機能にアクセスするために利用されます。`cmd/asm`は、Goツールチェーンの一部として提供されるアセンブラで、Go独自のPlan 9アセンブリ構文を使用します。このアセンブラは、`.s`ファイル（アセンブリソースファイル）をオブジェクトファイルにコンパイルし、GoリンカがGoコードとリンクできるようにします。

### Plan 9アセンブリ構文

Goのアセンブリは、AT&T構文やIntel構文とは異なるPlan 9アセンブリ構文を採用しています。主な特徴は以下の通りです。
- **レジスタ名**: `AX`, `BX`などではなく、`R0`, `R1`などの汎用レジスタ名が使われることが多いです（アーキテクチャによって異なる）。`amd64`では`AX`, `BX`なども使われますが、Goアセンブラでは`R`プレフィックスのレジスタも内部的に扱われます。
- **シンボル参照**: シンボル（変数、関数、ラベルなど）は、通常、`SB` (Static Base)、`FP` (Frame Pointer)、`PC` (Program Counter)、`SP` (Stack Pointer) といった擬似レジスタからのオフセットで参照されます。
    - `SYMBOL(SB)`: グローバルシンボル。プログラムの静的ベースからのオフセット。
    - `SYMBOL(FP)`: 関数のフレームポインタからのオフセット。引数やローカル変数にアクセスする際に使用。
    - `SYMBOL(PC)`: プログラムカウンタからのオフセット。主にジャンプ命令のターゲットとして使用。
    - `SYMBOL(SP)`: スタックポインタからのオフセット。ローカル変数や一時的なデータにアクセスする際に使用。
- **アドレッシングモード**: メモリへのアクセス方法を定義します。
    - `$`プレフィックス: 即値（リテラル値）を示します。例: `ADDQ $8, R1` (R1に8を加算)
    - `(REG)`: レジスタが指すアドレスの内容。例: `MOVQ (RSP), R1` (RSPが指すアドレスの内容をR1に移動)
    - `OFFSET(REG)`: レジスタが指すアドレスにオフセットを加えたアドレスの内容。例: `MOVQ 8(RSP), R1` (RSP+8のアドレスの内容をR1に移動)
    - `SYMBOL(SB)`: シンボルが指すグローバルアドレス。

### `amd64`アーキテクチャ

`amd64`は、Intel 64（x86-64）としても知られる64ビット命令セットアーキテクチャです。Goは、このアーキテクチャを主要なターゲットの一つとしています。レジスタ、命令セット、アドレッシングモードなど、多くの詳細がありますが、このコミットの文脈では、アセンブラがこれらの要素をどのようにパースし、解釈するかが重要です。

### `obj.Prog`と`obj.Addr`

Goのアセンブラは、アセンブリソースコードをパースした後、内部的に`obj.Prog`構造体のリストに変換します。`obj.Prog`は、単一のアセンブリ命令（オペコード、オペランドなど）を表す構造体です。各オペランドは`obj.Addr`構造体で表現され、レジスタ、シンボル、オフセット、即値などの情報を保持します。アセンブラの役割は、ソースコードのテキスト表現をこれらの内部データ構造に正確にマッピングすることです。

### 装飾されていないシンボル参照 (Unadorned Symbol Reference)

このコミットの文脈における「装飾されていないシンボル参照」とは、`R520`のように、レジスタ名ではないが、`$`や`(`などのアドレッシングモードを示すプレフィックスや括弧が付いていないシンボルを指します。Goアセンブラの構文では、このような形式は通常、有効なアドレッシングモードではありません。しかし、ジャンプ命令のターゲット（ラベル）の場合、シンボル名のみで参照されることがあります。この区別がパース時に重要となります。

## コアとなるコードの解説

### `Parser`構造体への`isJump`フィールド追加

`isJump`フィールドは、`Parser`が現在処理しているアセンブリ命令がジャンプ命令であるかどうかを示す状態変数です。アセンブリ言語では、ジャンプ命令（例: `JMP`, `CALL`）のオペランドとして指定されるシンボルは、通常、コード内のラベルを指し、特定のアドレッシングモードの指定を必要としません。しかし、データ操作命令（例: `ADDQ`, `MOVQ`）のオペランドとしてシンボルが使用される場合、それはメモリ上のアドレスを指すことが多く、`SYMBOL(SB)`や`$SYMBOL`のような適切なアドレッシングモードの指定が必要です。この`isJump`フィールドを導入することで、アセンブラはこれらの異なるコンテキストを区別し、シンボル参照の解釈とエラー報告をより正確に行えるようになります。

### `instruction`メソッド内の`isJump`の扱い変更

`instruction`メソッドは、アセンブリ命令のオペコードとオペランドをパースする中心的なロジックです。
- `p.isJump = p.arch.IsJump(word)`: ここで、`p.arch.IsJump(word)`関数が現在の命令のニーモニック（`word`）がジャンプ命令であるかを判断し、その結果を`Parser`構造体の`p.isJump`フィールドに格納します。これにより、この情報が`Parser`の状態として保持され、他のメソッドからアクセス可能になります。
- `if !p.isJump && addr.Reg < 0`: この条件は、現在の命令がジャンプ命令ではなく、かつオペランドが擬似レジスタ（`addr.Reg < 0`は擬似レジスタを示す内部表現）である場合にエラーを報告します。ジャンプ命令は`PC`などの擬似レジスタを参照することが許容されるため、このチェックはジャンプ命令ではない場合にのみ適用されます。
- `if p.isJump`: このブロックは、命令がジャンプ命令である場合に、ジャンプ命令特有の処理（`p.asmJump`）を呼び出すために使用されます。

これらの変更により、`instruction`メソッドは、命令の種類に応じて`p.isJump`の状態を正確に設定し、その後のパース処理がこの情報に基づいて適切に動作するように準備します。

### `symbolReference`メソッド内のエラー処理ロジックの変更

`symbolReference`メソッドは、アセンブリコード内のシンボル名（例: `R520`）を`obj.Addr`構造体に変換する際に呼び出されます。
- `if p.peek() == scanner.EOF`: この条件は、シンボル名の後に何も続いていない（つまり、`R520`のように単独でシンボルが記述されている）場合に真となります。
- `if prefix == 0 && p.isJump`: この新しい条件が、このコミットの核心的な変更点です。
    - `prefix == 0`: シンボルに`$`（即値）や`*`（間接参照）のようなプレフィックスが付いていないことを意味します。
    - `p.isJump`: 現在の命令がジャンプ命令であることを意味します。
    - この両方が真である場合、そのシンボルはジャンプ命令のターゲットとなるラベルであると解釈され、有効な参照として扱われるため、エラーを発生させずに処理を終了します。
- `p.errorf("illegal or missing addressing mode for symbol %s", name)`: 上記の条件に合致しない場合（つまり、プレフィックスがないがジャンプ命令ではない、またはプレフィックスがあるが不正なアドレッシングモードである場合）、このエラーメッセージが出力されます。これは、以前の汎用的な「notfound」エラーよりも、問題がアドレッシングモードの誤用にあることを明確に示しています。

この修正により、アセンブラはジャンプ命令のラベル参照を正しく認識し、それ以外の文脈で不正なシンボル参照があった場合には、より具体的で役立つエラーメッセージを開発者に提供できるようになりました。

このコミットは、Goアセンブラ（`cmd/asm`）におけるシンボル参照のパースエラー処理を改善するものです。特に、`amd64`アーキテクチャにおいて、装飾されていないシンボル参照（unadorned symbol reference）が不正なアドレッシングモードとして扱われる際に、より正確なエラーメッセージを出力するように修正されました。以前は、このようなケースで汎用的な「notfound」エラーが発生していましたが、この変更により「illegal addressing mode for symbol」という、より具体的なパースエラーが報告されるようになります。この修正は、`arm64`アーキテクチャにおける同様の問題の解決（#12632）に依存していました。

## 変更の背景

Goのアセンブラ（`cmd/asm`）は、Goプログラムが低レベルのハードウェア操作を必要とする場合に、Goコードとアセンブリコードを連携させるための重要なツールです。このコミット以前は、`amd64`アーキテクチャ向けのアセンブリコードにおいて、シンボルが適切に修飾されていない（例えば、即値を示す`$`や間接参照を示す`*`などのプレフィックスがない）場合に、アセンブラが誤解を招くエラーメッセージを出力していました。

具体的には、`ADDQ R520, R1`のような命令で`R520`がレジスタではなく未定義のシンボルとして扱われるべき場合、アセンブラはこれを`obj`パッケージに渡してしまい、結果として「`asm: doasm: notfound ft=23 tt=23 00000 (x.s:2) ADDQ 0, 0 23 23`」といった、シンボルが見つからないことを示す汎用的なエラーを出力していました。このエラーメッセージは、問題がシンボルの未定義ではなく、アドレッシングモードの誤用にあることを明確に示していませんでした。

この問題は、アセンブラのパースロジックが、ジャンプ命令とそれ以外の命令におけるシンボル参照の扱いを十分に区別していなかったことに起因します。ジャンプ命令の場合、シンボルは通常、ジャンプ先のアドレス（ラベル）を指しますが、一般的なデータ操作命令では、シンボルはメモリ上のアドレスや即値を指すため、適切なアドレッシングモードの指定が必要です。

このコミットは、この曖昧さを解消し、よりユーザーフレンドリーで正確なエラーメッセージを提供することを目的としています。コミットメッセージにあるように、この修正は`arm64`アーキテクチャ向けに先行して行われた同様の修正（#12632）に依存しており、その知見が`amd64`にも適用された形です。

## 前提知識の解説

### Goアセンブラ (`cmd/asm`)

Go言語は、必要に応じてアセンブリ言語で記述されたコードをGoプログラムに組み込むことができます。これは、特定のパフォーマンス要件を満たすためや、ハードウェア固有の機能にアクセスするために利用されます。`cmd/asm`は、Goツールチェーンの一部として提供されるアセンブラで、Go独自のPlan 9アセンブリ構文を使用します。このアセンブラは、`.s`ファイル（アセンブリソースファイル）をオブジェクトファイルにコンパイルし、GoリンカがGoコードとリンクできるようにします。

### Plan 9アセンブリ構文

Goのアセンブリは、AT&T構文やIntel構文とは異なるPlan 9アセンブリ構文を採用しています。主な特徴は以下の通りです。
- **レジスタ名**: `AX`, `BX`などではなく、`R0`, `R1`などの汎用レジスタ名が使われることが多いです（アーキテクチャによって異なる）。`amd64`では`AX`, `BX`なども使われますが、Goアセンブラでは`R`プレフィックスのレジスタも内部的に扱われます。
- **シンボル参照**: シンボル（変数、関数、ラベルなど）は、通常、`SB` (Static Base)、`FP` (Frame Pointer)、`PC` (Program Counter)、`SP` (Stack Pointer) といった擬似レジスタからのオフセットで参照されます。
    - `SYMBOL(SB)`: グローバルシンボル。プログラムの静的ベースからのオフセット。
    - `SYMBOL(FP)`: 関数のフレームポインタからのオフセット。引数やローカル変数にアクセスする際に使用。
    - `SYMBOL(PC)`: プログラムカウンタからのオフセット。主にジャンプ命令のターゲットとして使用。
    - `SYMBOL(SP)`: スタックポインタからのオフセット。ローカル変数や一時的なデータにアクセスする際に使用。
- **アドレッシングモード**: メモリへのアクセス方法を定義します。
    - `$`プレフィックス: 即値（リテラル値）を示します。例: `ADDQ $8, R1` (R1に8を加算)
    - `(REG)`: レジスタが指すアドレスの内容。例: `MOVQ (RSP), R1` (RSPが指すアドレスの内容をR1に移動)
    - `OFFSET(REG)`: レジスタが指すアドレスにオフセットを加えたアドレスの内容。例: `MOVQ 8(RSP), R1` (RSP+8のアドレスの内容をR1に移動)
    - `SYMBOL(SB)`: シンボルが指すグローバルアドレス。

### `amd64`アーキテクチャ

`amd64`は、Intel 64（x86-64）としても知られる64ビット命令セットアーキテクチャです。Goは、このアーキテクチャを主要なターゲットの一つとしています。レジスタ、命令セット、アドレッシングモードなど、多くの詳細がありますが、このコミットの文脈では、アセンブラがこれらの要素をどのようにパースし、解釈するかが重要です。

### `obj.Prog`と`obj.Addr`

Goのアセンブラは、アセンブリソースコードをパースした後、内部的に`obj.Prog`構造体のリストに変換します。`obj.Prog`は、単一のアセンブリ命令（オペコード、オペランドなど）を表す構造体です。各オペランドは`obj.Addr`構造体で表現され、レジスタ、シンボル、オフセット、即値などの情報を保持します。アセンブラの役割は、ソースコードのテキスト表現をこれらの内部データ構造に正確にマッピングすることです。

### 装飾されていないシンボル参照 (Unadorned Symbol Reference)

このコミットの文脈における「装飾されていないシンボル参照」とは、`R520`のように、レジスタ名ではないが、`$`や`(`などのアドレッシングモードを示すプレフィックスや括弧が付いていないシンボルを指します。Goアセンブラの構文では、このような形式は通常、有効なアドレッシングモードではありません。しかし、ジャンプ命令のターゲット（ラベル）の場合、シンボル名のみで参照されることがあります。この区別がパース時に重要となります。

## コアとなるコードの解説

### `Parser`構造体への`isJump`フィールド追加

`isJump`フィールドは、`Parser`が現在処理しているアセンブリ命令がジャンプ命令であるかどうかを示す状態変数です。アセンブリ言語では、ジャンプ命令（例: `JMP`, `CALL`）のオペランドとして指定されるシンボルは、通常、コード内のラベルを指し、特定のアドレッシングモードの指定を必要としません。しかし、データ操作命令（例: `ADDQ`, `MOVQ`）のオペランドとしてシンボルが使用される場合、それはメモリ上のアドレスを指すことが多く、`SYMBOL(SB)`や`$SYMBOL`のような適切なアドレッシングモードの指定が必要です。この`isJump`フィールドを導入することで、アセンブラはこれらの異なるコンテキストを区別し、シンボル参照の解釈とエラー報告をより正確に行えるようになります。

### `instruction`メソッド内の`isJump`の扱い変更

`instruction`メソッドは、アセンブリ命令のオペコードとオペランドをパースする中心的なロジックです。
- `p.isJump = p.arch.IsJump(word)`: ここで、`p.arch.IsJump(word)`関数が現在の命令のニーモニック（`word`）がジャンプ命令であるかを判断し、その結果を`Parser`構造体の`p.isJump`フィールドに格納します。これにより、この情報が`Parser`の状態として保持され、他のメソッドからアクセス可能になります。
- `if !p.isJump && addr.Reg < 0`: この条件は、現在の命令がジャンプ命令ではなく、かつオペランドが擬似レジスタ（`addr.Reg < 0`は擬似レジスタを示す内部表現）である場合にエラーを報告します。ジャンプ命令は`PC`などの擬似レジスタを参照することが許容されるため、このチェックはジャンプ命令ではない場合にのみ適用されます。
- `if p.isJump`: このブロックは、命令がジャンプ命令である場合に、ジャンプ命令特有の処理（`p.asmJump`）を呼び出すために使用されます。

これらの変更により、`instruction`メソッドは、命令の種類に応じて`p.isJump`の状態を正確に設定し、その後のパース処理がこの情報に基づいて適切に動作するように準備します。

### `symbolReference`メソッド内のエラー処理ロジックの変更

`symbolReference`メソッドは、アセンブリコード内のシンボル名（例: `R520`）を`obj.Addr`構造体に変換する際に呼び出されます。
- `if p.peek() == scanner.EOF`: この条件は、シンボル名の後に何も続いていない（つまり、`R520`のように単独でシンボルが記述されている）場合に真となります。
- `if prefix == 0 && p.isJump`: この新しい条件が、このコミットの核心的な変更点です。
    - `prefix == 0`: シンボルに`$`（即値）や`*`（間接参照）のようなプレフィックスが付いていないことを意味します。
    - `p.isJump`: 現在の命令がジャンプ命令であることを意味します。
    - この両方が真である場合、そのシンボルはジャンプ命令のターゲットとなるラベルであると解釈され、有効な参照として扱われるため、エラーを発生させずに処理を終了します。
- `p.errorf("illegal or missing addressing mode for symbol %s", name)`: 上記の条件に合致しない場合（つまり、プレフィックスがないがジャンプ命令ではない、またはプレフィックスがあるが不正なアドレッシングモードである場合）、このエラーメッセージが出力されます。これは、以前の汎用的な「notfound」エラーよりも、問題がアドレッシングモードの誤用にあることを明確に示しています。

この修正により、アセンブラはジャンプ命令のラベル参照を正しく認識し、それ以外の文脈で不正なシンボル参照があった場合には、より具体的で役立つエラーメッセージを開発者に提供できるようになりました。

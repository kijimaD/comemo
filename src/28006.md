## 変更の背景

Goコンパイラ (`cmd/compile`) は、Go言語のソースコードを解析し、抽象構文木 (AST) を構築します。このASTは `Node` と呼ばれる構造体で表現され、コンパイラの様々なフェーズ（型チェック、最適化、コード生成など）で処理されます。

スライス式（例: `a[low:high]` や `a[low:high:max]`）は、Go言語の強力な機能の一つですが、コンパイラ内部でのその表現は複雑でした。特に、スライスの境界 (`low`, `high`, `max`) は、`Node` の `Left` や `Right` フィールド、さらには `OKEY` という特殊なノードを介してネストされた形で表現されていました。このため、スライス式を扱う各コンパイラフェーズのコードは、その内部構造を直接的に解析し、境界値を取り出す必要がありました。これはコードの重複、可読性の低下、そして将来的な変更への対応の難しさにつながっていました。

このコミットの主な目的は、スライス式の内部表現をカプセル化し、コンパイラの他の部分がスライス境界にアクセスするための統一されたAPIを提供することです。これにより、スライス式を扱うコードの複雑さを軽減し、保守性を向上させることが目指されました。コミットメッセージにあるように、これはGo 1.8でのより大きな変更（`OKEY` の代わりに `Node.List` を使用する）に向けた「試行的な実行」でもありました。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`) の構造とAST

Goコンパイラは、複数のフェーズに分かれて動作します。

1.  **字句解析 (Lexing)**: ソースコードをトークンに分割します。
2.  **構文解析 (Parsing)**: トークン列から抽象構文木 (AST) を構築します。
3.  **型チェック (Type Checking)**: ASTの各ノードの型を検証し、型情報を付与します。
4.  **中間表現 (IR) への変換**: ASTをSSA (Static Single Assignment) 形式などのより低レベルな中間表現に変換します。
5.  **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用します。
6.  **コード生成 (Code Generation)**: 最適化された中間表現から機械語コードを生成します。

このコミットが関連するのは、主に構文解析後のASTの操作と、それに続く型チェック、順序付け、コード生成などのフェーズです。

### 抽象構文木 (AST) と `Node`

Goコンパイラでは、ソースコードの構造を `Node` というデータ構造で表現します。各 `Node` は、演算子 (`Op`)、左の子 (`Left`)、右の子 (`Right`)、型 (`Type`) などの情報を持っています。

*   **`Op`**: `Node` が表す操作の種類（例: `OADD` (加算), `OCALL` (関数呼び出し), `OSLICE` (スライス)）。
*   **`Left`, `Right`**: 子ノードへのポインタ。二項演算や単項演算などで使用されます。
*   **`OKEY`**: 以前のスライス表現で、複数の値を一つの `Node` にまとめるために使われていた特殊な演算子。例えば、`a[low:high]` の `low` と `high` は `OKEY` ノードの子として格納されていました。`a[low:high:max]` の場合は、さらに `OKEY` がネストされていました。

### Goのスライス式

Go言語のスライス式には、以下の3つの形式があります。

1.  **`a[low:high]` (Simple Slice Expression)**: `low` から `high-1` までの要素を含む新しいスライスを作成します。`low` が省略された場合は `0`、`high` が省略された場合は元のスライスの長さ (`len(a)`) がデフォルト値となります。
2.  **`a[low:high:max]` (Full Slice Expression)**: `low` から `high-1` までの要素を含む新しいスライスを作成し、その容量 (`cap`) を `max - low` に設定します。`max` は `high` 以上でなければなりません。`max` が省略された場合は元のスライスの容量 (`cap(a)`) がデフォルト値となります。この形式は、新しいスライスの容量を明示的に制限したい場合に使用されます。

コンパイラ内部では、これらのスライス式はそれぞれ異なる `Op` で表現されます。

*   `OSLICE`: `a[low:high]` 形式のスライス式（スライス、配列、ポインタに対するもの）。
*   `OSLICE3`: `a[low:high:max]` 形式のスライス式（スライス、配列、ポインタに対するもの）。
*   `OSLICESTR`: 文字列に対する `a[low:high]` 形式のスライス式。
*   `OSLICEARR`: 配列へのポインタに対する `a[low:high]` 形式のスライス式。
*   `OSLICE3ARR`: 配列へのポインタに対する `a[low:high:max]` 形式のスライス式。

これらの `OSLICE*` ノードは、その `Left` フィールドにスライスされる元の式を、`Right` フィールドにスライス境界を表すノードを持っていました。特に `Right` フィールドは、`OKEY` ノードを介して `low`, `high`, `max` の値を保持していました。

## 技術的詳細

このコミットの核心は、`src/cmd/compile/internal/gc/subr.go` に `Node` 型の新しいメソッド `SliceBounds()`, `SetSliceBounds()`, および `Op` 型のヘルパーメソッド `IsSlice3()` を導入したことです。

### `Node.SliceBounds()` メソッド

このメソッドは、スライス式を表す `Node` から `low`, `high`, `max` の3つの境界値を抽出します。

*   `OSLICE`, `OSLICEARR`, `OSLICESTR` のような2インデックススライスの場合、`max` は `nil` を返します。
*   `OSLICE3`, `OSLICE3ARR` のような3インデックススライスの場合、`low`, `high`, `max` の全てを返します。

このメソッドの内部では、`Node.Right` フィールドに格納されている `OKEY` ノードの構造を解析し、適切な子ノードを返します。これにより、コンパイラの他の部分では `OKEY` ノードのネスト構造を意識することなく、統一的にスライス境界にアクセスできるようになります。

### `Node.SetSliceBounds()` メソッド

このメソッドは、スライス式を表す `Node` の `low`, `high`, `max` の境界値を設定します。

*   `SliceBounds()` と同様に、`OSLICE*` の種類に応じて内部の `OKEY` ノード構造を適切に構築または更新します。
*   2インデックススライス (`OSLICE`, `OSLICEARR`, `OSLICESTR`) に対して `max` が `nil` でない場合は、`Fatalf` でエラーを発生させます。

### `Op.IsSlice3()` メソッド

このメソッドは、与えられた `Op` が3インデックススライス (`OSLICE3`, `OSLICE3ARR`) を表すかどうかを判定するシンプルなヘルパーです。

### コンパイラ各フェーズへの影響

これらの新しいメソッドの導入により、コンパイラの様々なフェーズでスライス式を扱うコードが大幅に簡素化されました。

*   **`bexport.go` / `bimport.go` (バイナリ形式でのエクスポート/インポート)**: ASTをバイナリ形式でエクスポート・インポートする際に、スライス境界の読み書きに `SliceBounds()` と `SetSliceBounds()` が使用されるようになりました。これにより、内部表現の詳細がこれらのモジュールから隠蔽されます。
*   **`cgen.go` (コード生成)**: スライス操作のコードを生成する際に、`n.SliceBounds()` を呼び出して境界値を取得するようになりました。
*   **`fmt.go` (ASTの文字列化)**: ASTをデバッグ目的で文字列に変換する際に、`SliceBounds()` を使用してスライス式を正しくフォーマットするようになりました。
*   **`order.go` (順序付け)**: 式の評価順序を決定するフェーズで、スライス境界の各部分式 (`low`, `high`, `max`) を順序付ける際に `SliceBounds()` と `SetSliceBounds()` が利用されます。
*   **`parser.go` (構文解析)**: ソースコードからスライス式を解析し、ASTノードを構築する際に、`SetSliceBounds()` を使用して境界値を設定するようになりました。これにより、`OKEY` ノードを直接構築するロジックが `parser.go` から取り除かれました。
*   **`racewalk.go` (データ競合検出)**: データ競合検出のためのインストゥルメンテーションを行う際に、スライス境界の各部分式を再帰的に処理するために `SliceBounds()` と `SetSliceBounds()` が使われます。
*   **`sinit.go` (静的初期化)**: スライスの静的初期化に関連するコードで、スライス式の構築に `SetSliceBounds()` が使われるようになりました。
*   **`ssa.go` (SSA変換)**: ASTをSSA形式に変換する際に、スライス操作をSSA値に変換するロジックが `SliceBounds()` を使用するように変更されました。
*   **`typecheck.go` (型チェック)**: スライス式の型チェックを行う際に、`SliceBounds()` で境界値を取得し、`SetSliceBounds()` で更新するようになりました。特に、文字列に対する3インデックススライスがエラーとなるべきケースのチェックが `IsSlice3()` を使って簡潔に記述されています。
*   **`walk.go` (ASTウォーク)**: ASTを走査し、最適化や変換を行うフェーズで、スライス式の簡約化（例: `x[0:j]` を `x[:j]` に、`x[i:j:cap(x)]` を `x[i:j]` に）を行う際に、`SliceBounds()` と `SetSliceBounds()` が活用されています。

これらの変更により、スライス式の内部表現の詳細が `subr.go` に集約され、他のファイルではより高レベルな抽象化されたAPIを通じてスライス式を扱えるようになりました。これにより、コンパイラコード全体のモジュール性が向上し、将来的な変更（例えば、Go 1.8で予定されている `Node.List` への移行）が容易になります。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、`src/cmd/compile/internal/gc/subr.go` に追加された以下のメソッドです。

```go
// src/cmd/compile/internal/gc/subr.go

// SliceBounds returns n's slice bounds: low, high, and max in expr[low:high:max].
// n must be a slice expression. max is nil if n is a simple slice expression.
func (n *Node) SliceBounds() (low, high, max *Node) {
	switch n.Op {
	case OSLICE, OSLICEARR, OSLICESTR:
		if n.Right == nil {
			return nil, nil, nil
		}
		if n.Right.Op != OKEY {
			Fatalf("SliceBounds right %s", opnames[n.Right.Op])
		}
		return n.Right.Left, n.Right.Right, nil
	case OSLICE3, OSLICE3ARR:
		if n.Right.Op != OKEY || n.Right.Right.Op != OKEY {
			Fatalf("SliceBounds right %s %s", opnames[n.Right.Op], opnames[n.Right.Right.Op])
		}
		return n.Right.Left, n.Right.Right.Left, n.Right.Right.Right
	}
	Fatalf("SliceBounds op %s: %v", n.Op, n)
	return nil, nil, nil
}

// SetSliceBounds sets n's slice bounds, where n is a slice expression.
// n must be a slice expression. If max is non-nil, n must be a full slice expression.
func (n *Node) SetSliceBounds(low, high, max *Node) {
	switch n.Op {
	case OSLICE, OSLICEARR, OSLICESTR:
		if max != nil {
			Fatalf("SetSliceBounds %s given three bounds", n.Op)
		}
		if n.Right == nil {
			n.Right = Nod(OKEY, low, high)
			return
		}
		n.Right.Left = low
		n.Right.Right = high
		return
	case OSLICE3, OSLICE3ARR:
		if n.Right == nil {
			n.Right = Nod(OKEY, low, Nod(OKEY, high, max))
		}
		n.Right.Left = low
		n.Right.Right.Left = high
		n.Right.Right.Right = max
		return
	}
	Fatalf("SetSliceBounds op %s: %v", n.Op, n)
}

// IsSlice3 reports whether o is a slice3 op (OSLICE3, OSLICE3ARR).
// o must be a slicing op.
func (o Op) IsSlice3() bool {
	switch o {
	case OSLICE, OSLICEARR, OSLICESTR:
		return false
	case OSLICE3, OSLICE3ARR:
		return true
	}
	Fatalf("IsSlice3 op %v", o)
	return false
}
```

これらのメソッドは、`Node` の `Right` フィールドにネストされた `OKEY` ノードを介してスライス境界がどのように格納されているかという詳細を抽象化します。

例えば、`src/cmd/compile/internal/gc/typecheck.go` では、以前は以下のような直接的な `Node.Right` のアクセスがありました。

```go
// 変更前 (typecheck.go の OSLICE ケースの一部)
n.Right.Left = typecheck(n.Right.Left, Erv)
n.Right.Right = typecheck(n.Right.Right, Erv)
// ...
lo := n.Right.Left
hi := n.Right.Right
```

これが、新しい `SliceBounds()` と `SetSliceBounds()` を使用するように変更されました。

```go
// 変更後 (typecheck.go の OSLICE, OSLICE3 ケースの一部)
low, high, max := n.SliceBounds()
hasmax := n.Op.IsSlice3()
low = typecheck(low, Erv)
high = typecheck(high, Erv)
max = typecheck(max, Erv)
// ...
low = indexlit(low)
high = indexlit(high)
max = indexlit(max)
n.SetSliceBounds(low, high, max)
```

同様に、`src/cmd/compile/internal/gc/walk.go` でも、スライス式の簡約化ロジックが新しいAPIを使用するように変更されています。

```go
// 変更前 (walk.go の OSLICE, OSLICEARR, OSLICESTR ケースの一部)
n.Right.Left = walkexpr(n.Right.Left, init)
// ...
n.Right.Right = walkexpr(n.Right.Right, init)
n = reduceSlice(n)

// 変更前 (walk.go の OSLICE3, OSLICE3ARR ケースの一部)
n.Right.Left = walkexpr(n.Right.Left, init)
// ...
n.Right.Right.Left = walkexpr(n.Right.Right.Left, init)
n.Right.Right.Right = walkexpr(n.Right.Right.Right, init)
```

これが以下のように変更されました。

```go
// 変更後 (walk.go の OSLICE, OSLICEARR, OSLICESTR, OSLICE3, OSLICE3ARR ケースの一部)
low, high, max := n.SliceBounds()
low = walkexpr(low, init)
// ...
high = walkexpr(high, init)
max = walkexpr(max, init)
n.SetSliceBounds(low, high, max)
```

## コアとなるコードの解説

### `Node.SliceBounds()`

このメソッドは、GoコンパイラのASTノード `Node` がスライス式を表す場合に、そのスライス境界 (`low`, `high`, `max`) を取得するための統一されたインターフェースを提供します。

*   **`switch n.Op`**: `Node` の操作 (`Op`) に応じて、スライス式の種類を判別します。
    *   `OSLICE`, `OSLICEARR`, `OSLICESTR` (2インデックススライス): これらの操作では、`n.Right` が `OKEY` ノードであり、その `Left` が `low`、`Right` が `high` を表します。`max` は存在しないため `nil` を返します。
    *   `OSLICE3`, `OSLICE3ARR` (3インデックススライス): これらの操作では、`n.Right` が `OKEY` ノードであり、その `Left` が `low`、`Right` がさらにネストされた `OKEY` ノードです。このネストされた `OKEY` ノードの `Left` が `high`、`Right` が `max` を表します。
*   **エラーハンドリング**: `n.Right` が `nil` であったり、期待される `OKEY` ノードでなかったりする場合には、`Fatalf` を呼び出してコンパイラを異常終了させます。これは、ASTの構造が期待通りでない場合に早期に問題を検出するためです。

このメソッドの導入により、コンパイラの他の部分では、スライス式の内部表現が2インデックスか3インデックスか、あるいは `OKEY` ノードがどのようにネストされているかといった詳細を知る必要がなくなりました。単に `n.SliceBounds()` を呼び出すだけで、必要な境界値を取得できます。

### `Node.SetSliceBounds()`

このメソッドは、`Node` が表すスライス式の境界値を設定するための統一されたインターフェースを提供します。

*   **`switch n.Op`**: `SliceBounds()` と同様に、`Node` の操作 (`Op`) に応じて、スライス式の種類を判別します。
    *   `OSLICE`, `OSLICEARR`, `OSLICESTR`: `max` が `nil` でない場合はエラーとします。`n.Right` がまだ存在しない場合は新しい `OKEY` ノードを作成し、`low` と `high` をその子として設定します。既に `n.Right` が存在する場合は、その `Left` と `Right` を更新します。
    *   `OSLICE3`, `OSLICE3ARR`: `n.Right` がまだ存在しない場合は、`low`、`high`、`max` を適切にネストされた `OKEY` ノードとして設定します。既に `n.Right` が存在する場合は、その子ノードを更新します。
*   **エラーハンドリング**: `SliceBounds()` と同様に、予期せぬ `Op` の場合は `Fatalf` を呼び出します。

このメソッドにより、スライス式のASTを構築または変更する際に、`OKEY` ノードの複雑なネスト構造を直接操作する必要がなくなりました。コンパイラの各フェーズは、`SetSliceBounds(low, high, max)` のように、よりセマンティックなレベルでスライス境界を扱えるようになります。

### `Op.IsSlice3()`

このメソッドは、特定の `Op` が3インデックススライス (`OSLICE3` または `OSLICE3ARR`) を表すかどうかを簡潔にチェックするためのヘルパーです。これにより、型チェックなどで文字列に対する3インデックススライスを禁止するようなロジックがより明確に記述できるようになりました。

これらの変更は、Goコンパイラの内部構造をよりクリーンでモジュール化されたものにし、将来的な機能拡張やメンテナンスを容易にするための重要なステップです。特に、スライス式の内部表現が変更される可能性のあるGo 1.8に向けて、このカプセル化は非常に有効な準備となりました。

## 変更の背景

Goコンパイラ (`cmd/compile`) は、Go言語のソースコードを解析し、抽象構文木 (AST) を構築します。このASTは `Node` と呼ばれる構造体で表現され、コンパイラの様々なフェーズ（型チェック、最適化、コード生成など）で処理されます。

スライス式（例: `a[low:high]` や `a[low:high:max]`）は、Go言語の強力な機能の一つですが、コンパイラ内部でのその表現は複雑でした。特に、スライスの境界 (`low`, `high`, `max`) は、`Node` の `Left` や `Right` フィールド、さらには `OKEY` という特殊なノードを介してネストされた形で表現されていました。このため、スライス式を扱う各コンパイラフェーズのコードは、その内部構造を直接的に解析し、境界値を取り出す必要がありました。これはコードの重複、可読性の低下、そして将来的な変更への対応の難しさにつながっていました。

このコミットの主な目的は、スライス式の内部表現をカプセル化し、コンパイラの他の部分がスライス境界にアクセスするための統一されたAPIを提供することです。これにより、スライス式を扱うコードの複雑さを軽減し、保守性を向上させることが目指されました。コミットメッセージにあるように、これはGo 1.8でのより大きな変更（`OKEY` の代わりに `Node.List` を使用する）に向けた「試行的な実行」でもありました。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`) の構造とAST

Goコンパイラは、複数のフェーズに分かれて動作します。

1.  **字句解析 (Lexing)**: ソースコードをトークンに分割します。
2.  **構文解析 (Parsing)**: トークン列から抽象構文木 (AST) を構築します。
3.  **型チェック (Type Checking)**: ASTの各ノードの型を検証し、型情報を付与します。
4.  **中間表現 (IR) への変換**: ASTをSSA (Static Single Assignment) 形式などのより低レベルな中間表現に変換します。
5.  **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用します。
6.  **コード生成 (Code Generation)**: 最適化された中間表現から機械語コードを生成します。

このコミットが関連するのは、主に構文解析後のASTの操作と、それに続く型チェック、順序付け、コード生成などのフェーズです。

### 抽象構文木 (AST) と `Node`

Goコンパイラでは、ソースコードの構造を `Node` というデータ構造で表現します。各 `Node` は、演算子 (`Op`)、左の子 (`Left`)、右の子 (`Right`)、型 (`Type`) などの情報を持っています。

*   **`Op`**: `Node` が表す操作の種類（例: `OADD` (加算), `OCALL` (関数呼び出し), `OSLICE` (スライス)）。
*   **`Left`, `Right`**: 子ノードへのポインタ。二項演算や単項演算などで使用されます。
*   **`OKEY`**: 以前のスライス表現で、複数の値を一つの `Node` にまとめるために使われていた特殊な演算子。例えば、`a[low:high]` の `low` と `high` は `OKEY` ノードの子として格納されていました。`a[low:high:max]` の場合は、さらに `OKEY` がネストされていました。

### Goのスライス式

Go言語のスライス式には、以下の3つの形式があります。

1.  **`a[low:high]` (Simple Slice Expression)**: `low` から `high-1` までの要素を含む新しいスライスを作成します。`low` が省略された場合は `0`、`high` が省略された場合は元のスライスの長さ (`len(a)`) がデフォルト値となります。
2.  **`a[low:high:max]` (Full Slice Expression)**: `low` から `high-1` までの要素を含む新しいスライスを作成し、その容量 (`cap`) を `max - low` に設定します。`max` は `high` 以上でなければなりません。`max` が省略された場合は元のスライスの容量 (`cap(a)`) がデフォルト値となります。この形式は、新しいスライスの容量を明示的に制限したい場合に使用されます。

コンパイラ内部では、これらのスライス式はそれぞれ異なる `Op` で表現されます。

*   `OSLICE`: `a[low:high]` 形式のスライス式（スライス、配列、ポインタに対するもの）。
*   `OSLICE3`: `a[low:high:max]` 形式のスライス式（スライス、配列、ポインタに対するもの）。
*   `OSLICESTR`: 文字列に対する `a[low:high]` 形式のスライス式。
*   `OSLICEARR`: 配列へのポインタに対する `a[low:high]` 形式のスライス式。
*   `OSLICE3ARR`: 配列へのポインタに対する `a[low:high:max]` 形式のスライス式。

これらの `OSLICE*` ノードは、その `Left` フィールドにスライスされる元の式を、`Right` フィールドにスライス境界を表すノードを持っていました。特に `Right` フィールドは、`OKEY` ノードを介して `low`, `high`, `max` の値を保持していました。

## 技術的詳細

このコミットの核心は、`src/cmd/compile/internal/gc/subr.go` に `Node` 型の新しいメソッド `SliceBounds()`, `SetSliceBounds()`, および `Op` 型のヘルパーメソッド `IsSlice3()` を導入したことです。

### `Node.SliceBounds()` メソッド

このメソッドは、スライス式を表す `Node` から `low`, `high`, `max` の3つの境界値を抽出します。

*   `OSLICE`, `OSLICEARR`, `OSLICESTR` のような2インデックススライスの場合、`max` は `nil` を返します。
*   `OSLICE3`, `OSLICE3ARR` のような3インデックススライスの場合、`low`, `high`, `max` の全てを返します。

このメソッドの内部では、`Node.Right` フィールドに格納されている `OKEY` ノードの構造を解析し、適切な子ノードを返します。これにより、コンパイラの他の部分では `OKEY` ノードのネスト構造を意識することなく、統一的にスライス境界にアクセスできるようになります。

### `Node.SetSliceBounds()` メソッド

このメソッドは、スライス式を表す `Node` の `low`, `high`, `max` の境界値を設定します。

*   `SliceBounds()` と同様に、`OSLICE*` の種類に応じて内部の `OKEY` ノード構造を適切に構築または更新します。
*   2インデックススライス (`OSLICE`, `OSLICEARR`, `OSLICESTR`) に対して `max` が `nil` でない場合は、`Fatalf` でエラーを発生させます。

### `Op.IsSlice3()` メソッド

このメソッドは、与えられた `Op` が3インデックススライス (`OSLICE3`, `OSLICE3ARR`) を表すかどうかを判定するシンプルなヘルパーです。

### コンパイラ各フェーズへの影響

これらの新しいメソッドの導入により、コンパイラの様々なフェーズでスライス式を扱うコードが大幅に簡素化されました。

*   **`bexport.go` / `bimport.go` (バイナリ形式でのエクスポート/インポート)**: ASTをバイナリ形式でエクスポート・インポートする際に、スライス境界の読み書きに `SliceBounds()` と `SetSliceBounds()` が使用されるようになりました。これにより、内部表現の詳細がこれらのモジュールから隠蔽されます。
*   **`cgen.go` (コード生成)**: スライス操作のコードを生成する際に、`n.SliceBounds()` を呼び出して境界値を取得するようになりました。
*   **`fmt.go` (ASTの文字列化)**: ASTをデバッグ目的で文字列に変換する際に、`SliceBounds()` を使用してスライス式を正しくフォーマットするようになりました。
*   **`order.go` (順序付け)**: 式の評価順序を決定するフェーズで、スライス境界の各部分式 (`low`, `high`, `max`) を順序付ける際に `SliceBounds()` と `SetSliceBounds()` が利用されます。
*   **`parser.go` (構文解析)**: ソースコードからスライス式を解析し、ASTノードを構築する際に、`SetSliceBounds()` を使用して境界値を設定するようになりました。これにより、`OKEY` ノードを直接構築するロジックが `parser.go` から取り除かれました。
*   **`racewalk.go` (データ競合検出)**: データ競合検出のためのインストゥルメンテーションを行う際に、スライス境界の各部分式を再帰的に処理するために `SliceBounds()` と `SetSliceBounds()` が使われます。
*   **`sinit.go` (静的初期化)**: スライスの静的初期化に関連するコードで、スライス式の構築に `SetSliceBounds()` が使われるようになりました。
*   **`ssa.go` (SSA変換)**: ASTをSSA形式に変換する際に、スライス操作をSSA値に変換するロジックが `SliceBounds()` を使用するように変更されました。
*   **`typecheck.go` (型チェック)**: スライス式の型チェックを行う際に、`SliceBounds()` で境界値を取得し、`SetSliceBounds()` で更新するようになりました。特に、文字列に対する3インデックススライスがエラーとなるべきケースのチェックが `IsSlice3()` を使って簡潔に記述されています。
*   **`walk.go` (ASTウォーク)**: ASTを走査し、最適化や変換を行うフェーズで、スライス式の簡約化（例: `x[0:j]` を `x[:j]` に、`x[i:j:cap(x)]` を `x[i:j]` に）を行う際に、`SliceBounds()` と `SetSliceBounds()` が活用されています。

これらの変更により、スライス式の内部表現の詳細が `subr.go` に集約され、他のファイルではより高レベルな抽象化されたAPIを通じてスライス式を扱えるようになりました。これにより、コンパイラコード全体のモジュール性が向上し、将来的な機能拡張やメンテナンスを容易にします。

```go
// src/cmd/compile/internal/gc/subr.go

// SliceBounds returns n's slice bounds: low, high, and max in expr[low:high:max].
// n must be a slice expression. max is nil if n is a simple slice expression.
func (n *Node) SliceBounds() (low, high, max *Node) {
	switch n.Op {
	case OSLICE, OSLICEARR, OSLICESTR:
		if n.Right == nil {
			return nil, nil, nil
		}
		if n.Right.Op != OKEY {
			Fatalf("SliceBounds right %s", opnames[n.Right.Op])
		}
		return n.Right.Left, n.Right.Right, nil
	case OSLICE3, OSLICE3ARR:
		if n.Right.Op != OKEY || n.Right.Right.Op != OKEY {
			Fatalf("SliceBounds right %s %s", opnames[n.Right.Op], opnames[n.Right.Right.Op])
		}
		return n.Right.Left, n.Right.Right.Left, n.Right.Right.Right
	}
	Fatalf("SliceBounds op %s: %v", n.Op, n)
	return nil, nil, nil
}

// SetSliceBounds sets n's slice bounds, where n is a slice expression.
// n must be a slice expression. If max is non-nil, n must be a full slice expression.
func (n *Node) SetSliceBounds(low, high, max *Node) {
	switch n.Op {
	case OSLICE, OSLICEARR, OSLICESTR:
		if max != nil {
			Fatalf("SetSliceBounds %s given three bounds", n.Op)
		}
		if n.Right == nil {
			n.Right = Nod(OKEY, low, high)
			return
		}
		n.Right.Left = low
		n.Right.Right = high
		return
	case OSLICE3, OSLICE3ARR:
		if n.Right == nil {
			n.Right = Nod(OKEY, low, Nod(OKEY, high, max))
		}
		n.Right.Left = low
		n.Right.Right.Left = high
		n.Right.Right.Right = max
		return
	}
	Fatalf("SetSliceBounds op %s: %v", n.Op, n)
}

// IsSlice3 reports whether o is a slice3 op (OSLICE3, OSLICE3ARR).
// o must be a slicing op.
func (o Op) IsSlice3() bool {
	switch o {
	case OSLICE, OSLICEARR, OSLICESTR:
		return false
	case OSLICE3, OSLICE3ARR:
		return true
	}
	Fatalf("IsSlice3 op %v", o)
	return false
}

## コアとなるコードの解説

### `Node.SliceBounds()`

このメソッドは、GoコンパイラのASTノード `Node` がスライス式を表す場合に、そのスライス境界 (`low`, `high`, `max`) を取得するための統一されたインターフェースを提供します。

*   **`switch n.Op`**: `Node` の操作 (`Op`) に応じて、スライス式の種類を判別します。
    *   `OSLICE`, `OSLICEARR`, `OSLICESTR` (2インデックススライス): これらの操作では、`n.Right` が `OKEY` ノードであり、その `Left` が `low`、`Right` が `high` を表します。`max` は存在しないため `nil` を返します。
    *   `OSLICE3`, `OSLICE3ARR` (3インデックススライス): これらの操作では、`n.Right` が `OKEY` ノードであり、その `Left` が `low`、`Right` がさらにネストされた `OKEY` ノードです。このネストされた `OKEY` ノードの `Left` が `high`、`Right` が `max` を表します。
*   **エラーハンドリング**: `n.Right` が `nil` であったり、期待される `OKEY` ノードでなかったりする場合には、`Fatalf` を呼び出してコンパイラを異常終了させます。これは、ASTの構造が期待通りでない場合に早期に問題を検出するためです。

このメソッドの導入により、コンパイラの他の部分では、スライス式の内部表現が2インデックスか3インデックスか、あるいは `OKEY` ノードがどのようにネストされているかといった詳細を知る必要がなくなりました。単に `n.SliceBounds()` を呼び出すだけで、必要な境界値を取得できます。

### `Node.SetSliceBounds()`

このメソッドは、`Node` が表すスライス式の境界値を設定するための統一されたインターフェースを提供します。

*   **`switch n.Op`**: `SliceBounds()` と同様に、`Node` の操作 (`Op`) に応じて、スライス式の種類を判別します。
    *   `OSLICE`, `OSLICEARR`, `OSLICESTR`: `max` が `nil` でない場合はエラーとします。`n.Right` がまだ存在しない場合は新しい `OKEY` ノードを作成し、`low` と `high` をその子として設定します。既に `n.Right` が存在する場合は、その `Left` と `Right` を更新します。
    *   `OSLICE3`, `OSLICE3ARR`: `n.Right` がまだ存在しない場合は、`low`、`high`、`max` を適切にネストされた `OKEY` ノードとして設定します。既に `n.Right` が存在する場合は、その子ノードを更新します。
*   **エラーハンドリング**: `SliceBounds()` と同様に、予期せぬ `Op` の場合は `Fatalf` を呼び出します。

このメソッドにより、スライス式のASTを構築または変更する際に、`OKEY` ノードの複雑なネスト構造を直接操作する必要がなくなりました。コンパイラの各フェーズは、`SetSliceBounds(low, high, max)` のように、よりセマンティックなレベルでスライス境界を扱えるようになります。

### `Op.IsSlice3()`

このメソッドは、特定の `Op` が3インデックススライス (`OSLICE3` または `OSLICE3ARR`) を表すかどうかを簡潔にチェックするためのヘルパーです。これにより、型チェックなどで文字列に対する3インデックススライスを禁止するようなロジックがより明確に記述できるようになりました。

これらの変更は、Goコンパイラの内部構造をよりクリーンでモジュール化されたものにし、将来的な機能拡張やメンテナンスを容易にするための重要なステップです。特に、スライス式の内部表現が変更される可能性のあるGo 1.8に向けて、このカプセル化は非常に有効な準備となりました。

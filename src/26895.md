## 変更の背景

Go言語には、コードの潜在的な問題を検出するための静的解析ツール `go vet` が標準で提供されています。`go vet` は、コンパイラでは検出できないが、バグや意図しない動作につながる可能性のある疑わしいコード構造を報告します。

このコミットは、`net` パッケージ内のテストコードで `go vet` が報告していた警告を修正することを目的としています。具体的には、`testing` パッケージの `t.Error` および `t.Fatal` 関数が、フォーマット文字列（例: `%d`, `%v`）と共に使用されている箇所が問題となっていました。

`t.Error` や `t.Fatal` は、引数をそのまま出力する設計であり、フォーマット文字列を解釈しません。そのため、`t.Error("unpacked different amount than packed: got n = %d, want = %d", n, len(buf))` のように使用すると、`%d` がそのまま出力され、期待通りのフォーマットされたメッセージが表示されないだけでなく、`go vet` によって警告が発せられます。

この問題を解決し、`go vet` の警告を解消するために、フォーマット文字列を扱うことができる `t.Errorf` および `t.Fatalf` への変更が必要とされました。これにより、テストの出力が意図通りにフォーマットされ、コードの品質が向上します。

## 前提知識の解説

*   **`go vet`**: Go言語の標準ツールチェーンに含まれる静的解析ツールです。コードを検査し、コンパイラが検出できないが、バグや非効率なコードにつながる可能性のある疑わしい構造（例: unreachable code, printf format errors, struct tags）を報告します。開発者がより堅牢でクリーンなコードを書くのに役立ちます。
*   **Goの`testing`パッケージ**: Go言語でユニットテストやベンチマークテストを記述するための標準パッケージです。テスト関数は `func TestXxx(t *testing.T)` の形式で定義され、`*testing.T` 型の引数 `t` を通じてテストの失敗を報告したり、テストの実行を制御したりします。
    *   **`t.Error(args ...interface{})`**: テスト失敗を報告しますが、テストの実行は継続します。引数はスペース区切りで出力されます。フォーマット文字列は解釈されません。
    *   **`t.Errorf(format string, args ...interface{})`**: テスト失敗を報告し、テストの実行は継続します。最初の引数にフォーマット文字列（`fmt.Sprintf` と同様の書式）を取り、それに続く引数をフォーマットして出力します。
    *   **`t.Fatal(args ...interface{})`**: テスト失敗を報告し、現在のテスト関数を即座に終了させます（`runtime.Goexit` を呼び出すため、`defer` 関数は実行されます）。引数はスペース区切りで出力されます。フォーマット文字列は解釈されません。
    *   **`t.Fatalf(format string, args ...interface{})`**: テスト失敗を報告し、現在のテスト関数を即座に終了させます。最初の引数にフォーマット文字列を取り、それに続く引数をフォーマットして出力します。
*   **フォーマット指定子 (Format Specifiers)**: Go言語の `fmt` パッケージ（および `testing` パッケージの `Errorf`/`Fatalf`）で使用される特殊な記号で、変数の値を特定の形式で文字列に変換するために使われます。
    *   `%d`: 整数を10進数で表示します。
    *   `%v`: 値をデフォルトのフォーマットで表示します。構造体など、あらゆる型に適しています。
    *   `%+v`: 構造体の場合、フィールド名も表示します。
    *   `%q`: 文字列やバイトスライスを引用符で囲んで表示します。

## 技術的詳細

このコミットの技術的な核心は、`go vet` が検出する「`t.Error` や `t.Fatal` にフォーマット文字列が渡されている」という誤用を修正することにあります。

`t.Error` と `t.Fatal` は、可変長引数 `args ...interface{}` を受け取りますが、これらの引数は `fmt.Sprint` を使って結合されるため、`%d` のようなフォーマット指定子が含まれていても、それは単なるリテラル文字列として扱われます。例えば、`t.Error("Value is %d", 10)` は "Value is %d 10" と出力され、`%d` が `10` に置換されることはありません。

一方、`t.Errorf` と `t.Fatalf` は、最初の引数をフォーマット文字列として扱い、それに続く引数を `fmt.Sprintf` と同様の方法で処理します。これにより、`t.Errorf("Value is %d", 10)` は "Value is 10" と正しく出力されます。

このコミットでは、既存のテストコード内で `t.Error` や `t.Fatal` がフォーマット指定子と共に使われている箇所を特定し、それらをそれぞれ `t.Errorf` や `t.Fatalf` に置き換えることで、`go vet` の警告を解消し、テスト出力の正確性を保証しています。これは、コードの機能的な変更ではなく、コード品質と可読性の向上を目的としたリファクタリングです。

## コアとなるコードの解説

変更は非常にシンプルで、`t.Error` を `t.Errorf` に、`t.Fatal` を `t.Fatalf` に置き換えるものです。

例として、`src/net/dnsmsg_test.go` の変更を見てみましょう。

変更前:
```go
if n != len(buf) {
    t.Error("unpacked different amount than packed: got n = %d, want = %d", n, len(buf))
}
```
このコードでは、`t.Error` にフォーマット文字列 `"%d"` が含まれています。しかし、`t.Error` はフォーマット文字列を解釈しないため、テストが失敗した場合、出力は `unpacked different amount than packed: got n = %d, want = %d 10 20` のようになる可能性があります（`n` と `len(buf)` がそれぞれ `10` と `20` の場合）。`%d` が数値に置換されず、そのまま表示されてしまいます。

変更後:
```go
if n != len(buf) {
    t.Errorf("unpacked different amount than packed: got n = %d, want = %d", n, len(buf))
}
```
`t.Errorf` に変更することで、最初の引数がフォーマット文字列として正しく解釈され、`n` と `len(buf)` の値が `%d` に適切に置換されます。これにより、テスト失敗時の出力は `unpacked different amount than packed: got n = 10, want = 20` のようになり、より分かりやすく正確な情報が提供されます。

同様に、`t.Fatal` から `t.Fatalf` への変更も、フォーマット文字列の正しい解釈と、それによる正確なエラーメッセージの生成を目的としています。`t.Fatal` と `t.Fatalf` の違いは、エラー報告後にテストを即座に終了させる点にありますが、フォーマット文字列の扱いは `t.Error` と `t.Errorf` の関係と同じです。

これらの変更は、Goのテストコードの品質と保守性を向上させ、`go vet` のような静的解析ツールが提供する恩恵を最大限に活用するためのものです。

# [インデックス 27735] ファイルの概要

このコミットは、Go言語のプロファイリングツールである`go tool trace`が、Go 1.5で生成されたトレースファイルを正しく解析できるようにするための変更を導入しています。具体的には、トレースヘッダーからバージョン情報を抽出し、Go 1.5のトレース形式に対応した解析ロジックを復元し、さらにスタックトレースのシンボル化機能を追加しています。これにより、古いバージョンのGoで生成されたトレースファイルも、最新の`go tool trace`で分析できるようになります。

## 元コミット内容

このコミットの目的は、`internal/trace`パッケージがGo 1.5で生成されたトレースファイルを解析できるようにすることです。主な変更点は以下の通りです。

1.  トレースヘッダーからバージョン情報を解析するようにしました。
2.  Go 1.5のトレース形式の処理を復元しました。
3.  トレースのオプションのシンボル化機能を復元しました。
4.  回帰テストのために、いくつかのGo 1.5トレース（HTTPベンチマークトレース、`runtime/trace`ストレスストレーストレース、およびタイムスタンプが壊れたもの）を追加しました。

## 変更の背景

Go言語の実行トレース（execution trace）は、Goプログラムのランタイム動作を詳細に記録したデータです。これは、パフォーマンス分析、デッドロック検出、スケジューリングの理解などに非常に有用です。`go tool trace`コマンドは、これらのトレースファイルを解析し、視覚化するためのツールを提供します。

Goのバージョンアップに伴い、トレースファイルの内部フォーマットも進化することがあります。このコミットが作成された時点では、Go 1.7（またはそれ以降）のトレースツールがGo 1.5で生成されたトレースファイルを正しく扱えない問題が発生していたと考えられます。特に、トレースヘッダーにバージョン情報が明示的に含まれていなかったり、スタックトレースの表現方法が異なったりすることが原因で、互換性が失われていた可能性があります。

この変更の背景には、以下のニーズがあったと推測されます。

*   **後方互換性の維持**: ユーザーが古いバージョンのGoで生成したトレースファイルも、最新のツールで分析できるようにすること。
*   **トレースフォーマットの進化への対応**: 将来的なトレースフォーマットの変更にも柔軟に対応できるよう、バージョン管理を導入すること。
*   **デバッグと分析の改善**: スタックトレースのシンボル化は、トレースデータから具体的な関数名、ファイル名、行番号を特定するために不可欠であり、分析の効率を大幅に向上させます。

## 前提知識の解説

### Go実行トレース (Go Execution Trace)

Go実行トレースは、Goプログラムのランタイムイベント（ゴルーチンの生成・終了、スケジューリング、GC、システムコール、ネットワークI/Oなど）を時系列で記録したバイナリファイルです。`runtime/trace`パッケージを使用して生成され、`go tool trace`コマンドで解析・視覚化されます。

### トレースヘッダーとバージョン情報

トレースファイルは通常、そのファイルのフォーマットバージョンを示すヘッダー情報から始まります。このバージョン情報に基づいて、パーサーはファイルの残りの部分をどのように解釈するかを決定します。Go 1.5のトレースファイルは、ヘッダーに「go 1.5 trace」という文字列を含んでいましたが、このコミット以前のパーサーは、このバージョン情報を適切に利用していなかったか、あるいは特定のバージョンのみを想定していた可能性があります。

### スタックトレースのシンボル化 (Symbolization)

Goの実行トレースには、イベント発生時のゴルーチンのスタックトレースが含まれることがあります。これらのスタックトレースは、通常、プログラムカウンタ（PC）と呼ばれるメモリアドレスのリストとして記録されます。PC値は、そのままでは人間が理解できる情報ではありません。これを関数名、ファイル名、行番号に変換するプロセスを「シンボル化」と呼びます。

シンボル化には、元のプログラムのバイナリファイルが必要です。バイナリファイルには、PC値とソースコード上の位置をマッピングするためのデバッグ情報が含まれています。Goでは、`go tool addr2line`というコマンドがこのシンボル化の役割を担います。このツールは、PC値のリストを入力として受け取り、対応する関数名、ファイル名、行番号を出力します。

### `go tool addr2line`

`go tool addr2line`は、Goのツールチェーンに含まれるユーティリティで、実行可能バイナリとPCアドレスのリストから、対応するソースコードのファイル名、行番号、関数名を解決します。これは、デバッグやプロファイリングにおいて、低レベルなアドレス情報を人間が理解できる情報に変換するために不可欠です。

### `internal/trace`パッケージ

`internal/trace`パッケージは、Goの標準ライブラリの一部であり、Go実行トレースファイルの解析ロジックを実装しています。このパッケージは、トレースファイルを読み込み、イベントを構造化されたデータに変換し、さらにイベント間の関係性を構築する役割を担います。

## 技術的詳細

このコミットの技術的な核心は、`src/internal/trace/parser.go`におけるトレースファイルのバージョン管理と、それに伴う解析ロジックの適応、そして`go tool addr2line`を利用したスタックトレースのシンボル化の導入です。

1.  **トレースヘッダーからのバージョン解析**:
    *   `readTrace`関数が変更され、トレースファイルの先頭16バイトからバージョン情報を抽出する`parseHeader`関数を呼び出すようになりました。
    *   `parseHeader`関数は、ヘッダー文字列（例: "go 1.5 trace"）を解析し、`1005`や`1007`といった整数値に変換します。これにより、将来のバージョンにも柔軟に対応できる基盤が作られました。
    *   未知のバージョンや不正なヘッダーに対してはエラーを返すようになっています。

2.  **Go 1.5トレースの処理復元**:
    *   `parseEvents`関数がバージョン情報(`ver`)を受け取るようになり、イベントの解析ロジックがバージョンに応じて分岐するようになりました。
    *   特に`EvStack`イベントの処理において、Go 1.5とGo 1.7以降でスタックフレームの表現方法が異なるため、このバージョン情報に基づいて適切な解析が行われるよう修正されました。Go 1.5ではPC値のみが記録されていたのに対し、Go 1.7以降ではPC、関数名、ファイル名、行番号が直接記録されるようになりました。このコミットでは、Go 1.5形式のスタックフレーム（PC値のみ）を後でシンボル化するパスが追加されています。
    *   `EventDescriptions`構造体にも`minVersion`フィールドが追加され、特定のイベントタイプが導入された最小バージョンを記録することで、古いバージョンのトレースファイルに存在しないイベントタイプを検出できるようになりました。

3.  **オプションのシンボル化機能の復元**:
    *   `Parse`関数に`bin`（プログラムバイナリのパス）引数が追加されました。この引数が空でない場合、かつトレースバージョンがGo 1.7未満（`ver < 1007`）の場合に、新しく導入された`symbolize`関数が呼び出されます。
    *   `symbolize`関数は、トレース内のすべてのPC値を収集し、重複を排除します。
    *   収集したPC値を`go tool addr2line`コマンドの標準入力に渡し、その標準出力からシンボル化された関数名、ファイル名、行番号を読み取ります。
    *   最終的に、解析されたイベントのスタックフレーム内のPC値を、`addr2line`によって解決された詳細な`Frame`情報（PC、Fn、File、Line）で置き換えます。これにより、Go 1.5トレースのPC値のみのスタックトレースが、人間が読める形式に変換されます。

4.  **回帰テストの追加**:
    *   `src/internal/trace/testdata`ディレクトリに、Go 1.5で生成された実際のトレースファイル（正常なもの、タイムスタンプが順不同なものなど）が追加されました。
    *   `src/internal/trace/parser_test.go`に`TestParseCanned`と`TestParseVersion`という新しいテスト関数が追加され、これらのGo 1.5トレースが正しく解析されること、およびバージョン解析が正しく機能することが検証されます。

5.  **`src/runtime/trace.go`の変更**:
    *   `ReadTrace`関数が生成するトレースファイルのヘッダーが「go 1.5 trace」から「go 1.7 trace」に変更されました。これは、このコミットが適用されたランタイムがGo 1.7以降のトレースフォーマットを生成することを示唆しています。

これらの変更により、`go tool trace`はGo 1.5のトレースファイルを解析する際に、そのバージョンを認識し、適切な解析ロジックを適用し、必要に応じて`go tool addr2line`を使用してスタックトレースをシンボル化できるようになりました。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/internal/trace/parser.go`内の`Parse`、`readTrace`、`parseHeader`、`parseEvents`、`postProcessTrace`、そして新しく追加された`symbolize`関数に集約されます。

1.  **`Parse(r io.Reader, bin string) ([]*Event, error)`**:
    *   トレース解析のエントリポイントです。`io.Reader`からトレースデータを読み込み、`bin`引数で指定されたプログラムバイナリを使用してスタックトレースをシンボル化します。
    *   `readTrace`を呼び出して、生のイベントとバージョン情報を取得します。
    *   `parseEvents`を呼び出して、生のイベントを構造化された`Event`オブジェクトに変換します。
    *   `postProcessTrace`を呼び出して、イベント間の関係性を構築し、整合性を検証します。
    *   **`if ver < 1007 && bin != ""`**: この条件が重要です。トレースのバージョンがGo 1.7未満であり、かつバイナリパスが指定されている場合にのみ、`symbolize`関数が呼び出されます。これは、Go 1.7以降のトレースフォーマットではスタックフレームにシンボル情報が直接含まれるようになったため、外部シンボル化が不要になったことを意味します。Go 1.5などの古いトレースでは、PC値のみが記録されているため、`addr2line`によるシンボル化が必要になります。

2.  **`readTrace(r io.Reader) (ver int, events []rawEvent, strings map[uint64]string, err error)`**:
    *   トレースファイルのワイヤーフォーマットを解析し、生のイベントデータを読み込みます。
    *   ファイルの先頭16バイトを読み込み、`parseHeader`を呼び出してトレースのバージョンを抽出します。
    *   抽出されたバージョンが`1005`（Go 1.5）または`1007`（Go 1.7）以外の場合、エラーを返します。これにより、サポートされていないバージョンのトレースファイルが拒否されます。
    *   イベントループ内で、各イベントのタイプと引数を読み込みます。`EvString`イベント（文字列辞書エントリ）の処理もここで行われます。
    *   `EventDescriptions[typ].minVersion > ver`というチェックが追加され、現在のトレースバージョンでサポートされていないイベントタイプが検出された場合にエラーを返すようになりました。

3.  **`parseHeader(buf []byte) (int, error)`**:
    *   トレースヘッダー（例: "go 1.7 trace\\x00\\x00\\x00\\x00"）を解析し、バージョン番号を整数値（例: 1007）として返します。
    *   ヘッダーの形式が期待通りでない場合や、バージョン番号が不正な場合はエラーを返します。

4.  **`parseEvents(ver int, rawEvents []rawEvent, strings map[uint64]string) (events []*Event, stacks map[uint64][]*Frame, err error)`**:
    *   `readTrace`で読み込まれた生のイベント(`rawEvent`)を、より意味のある`Event`構造体に変換します。
    *   `EvStack`イベントの処理において、`ver < 1007`の条件分岐が追加されました。
        *   Go 1.7以降のトレースでは、スタックフレームはPC、関数名、ファイル名、行番号の4つの引数で構成されます。
        *   Go 1.5のトレースでは、スタックフレームはPC値のみで構成されます。この場合、`stk[i] = &Frame{PC: raw.args[2+i]}`のようにPC値のみを格納し、後で`symbolize`関数によって詳細な情報が補完されます。

5.  **`symbolize(events []*Event, bin string) error`**:
    *   この関数は、Go 1.7未満のトレースファイルに対して、スタックトレースのPC値をシンボル化するために導入されました。
    *   **PC値の収集と重複排除**: まず、すべてのイベントからスタックトレースに含まれるPC値を抽出し、`map[uint64]*Frame`を使用して重複を排除します。
    *   **`go tool addr2line`の起動**: `exec.Command("go", "tool", "addr2line", bin)`を実行して、`addr2line`プロセスを起動します。`bin`は解析対象のプログラムバイナリのパスです。
    *   **PC値の送信**: 収集したPC値を`addr2line`プロセスの標準入力に16進数形式で書き込みます。`pc-1`としているのは、`addr2line`が通常、呼び出し元のPCではなく、呼び出された関数のエントリポイントのPCを期待するためです。
    *   **シンボル情報の読み取り**: `addr2line`の標準出力から、対応する関数名、ファイル名、行番号を読み取ります。`addr2line`は通常、関数名、ファイル:行番号のペアを2行で出力します。
    *   **`Frame`構造体の更新**: 読み取ったシンボル情報で`Frame`構造体を構築し、元のPC値に対応するマップに格納します。ファイル名にコロンが含まれる場合（例: `file.go:123`）、ファイル名と行番号を分離します。
    *   **イベントのスタックフレームの更新**: 最後に、すべてのイベントを再度走査し、`ev.Stk`内の`Frame`ポインタを、シンボル化された情報を含む`pcs`マップからの`Frame`ポインタで置き換えます。

これらの変更により、`go tool trace`はGo 1.5のトレースファイルを解析し、スタックトレースを人間が読める形式で表示できるようになり、後方互換性と分析能力が向上しました。

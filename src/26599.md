## 変更の背景

このコミットは、Goコンパイラにおける特定のバグを修正するために行われました。このバグは、関数がインライン化された際に、その関数内で宣言された構造体のフィールドに付与された「タグ」（struct tags）が正しく出力されないというものでした。

問題の根本は、以前のコミット `golang.org/cl/18217` で `#13777` の修正を試みた際に導入されたものでした。この修正は、エスケープ解析の注釈が関数型に誤って適用されるのを抑制することを目的としていましたが、その過程で、インライン化された関数本体内の変数宣言における構造体タグの出力も抑制してしまうという意図しない副作用が生じました。

Go 1.5ではこのケースは正しくインライン化されていたため、インライン化を無効にするというアプローチは、パフォーマンスの退行を招く可能性がありました。そのため、インライン化を維持しつつ、構造体タグが正しく出力されるようにコンパイラのロジックを修正する方針が採られました。

具体的には、コンパイラが型情報をフォーマットする際に、構造体フィールドのタグを抑制すべきではない状況で抑制してしまう条件式が問題でした。このコミットは、その条件式をより正確にすることで、構造体タグが常に適切に表示されるように修正することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびGoコンパイラに関する知識が必要です。

1.  **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換するツールです。型チェック、最適化、コード生成など、コンパイルの全工程を担います。
2.  **インライン化 (Inlining)**: コンパイラ最適化の一種で、小さな関数の呼び出しを、その関数の本体のコードで直接置き換えることです。これにより、関数呼び出しのオーバーヘッドが削減され、プログラムの実行速度が向上する可能性があります。
3.  **構造体タグ (Struct Tags)**: Goの構造体フィールドに付与できる文字列リテラルです。リフレクションAPI (`reflect`パッケージ) を通じて実行時にアクセスでき、主にJSONエンコーディング/デコーディング、データベースマッピング、バリデーションなどのメタデータとして利用されます。例: `type User struct { Name string `json:"user_name"` }`
4.  **`obj.FmtShort`**: コンパイラ内部で使用されるフラグの一つで、型を短縮形式でフォーマットするかどうかを制御します。
5.  **`fmtbody`**: `typefmt` 関数内で使用されるブール型フラグで、関数本体内で型をフォーマットしているかどうかを示します。このフラグは、主にエスケープ解析の注釈など、特定のコンテキストでのみ意味を持つ情報を抑制するために使用されます。
6.  **`t.Funarg`**: `Type`構造体のフィールドで、その型が関数引数（または戻り値）であるかどうかを示すブール値です。
7.  **`t.Note`**: `Type`構造体のフィールドで、型に関連付けられた追加の注釈（例えば、構造体タグの文字列）を保持します。構造体フィールドの場合、ここにタグの文字列が格納されます。
8.  **エスケープ解析 (Escape Analysis)**: コンパイラ最適化の一種で、変数がヒープに割り当てられるべきか、スタックに割り当てられるべきかを決定します。変数が関数のスコープ外に「エスケープ」するかどうかを分析します。エスケープ解析の結果は、コンパイラによって注釈として出力されることがあります。

## 技術的詳細

このコミットの核心は、`src/cmd/compile/internal/gc/fmt.go` 内の `typefmt` 関数における条件式の変更です。この関数は、Goコンパイラが型情報を文字列としてフォーマットする際に使用されます。

変更前のコードでは、構造体タグ（`t.Note` に格納されている）を出力するかどうかの条件が以下のようになっていました。

```go
if flag&obj.FmtShort == 0 && !fmtbody && t.Note != nil {
    str += " " + strconv.Quote(*t.Note)
}
```

この条件は、「短縮形式でない (`flag&obj.FmtShort == 0`)」かつ「関数本体内でフォーマットしていない (`!fmtbody`)」場合にのみ、`t.Note`（構造体タグ）を出力するというものでした。

問題は、関数がインライン化されると、その関数本体内の変数宣言がコンパイラによって「関数本体内でフォーマットしている」と見なされ、`fmtbody` が `true` になることでした。これにより、`!fmtbody` の条件が満たされなくなり、結果として構造体タグが出力されなくなっていました。これは、エスケープ解析の注釈を抑制するための `fmtbody` フラグの意図とは異なる挙動でした。構造体タグは、エスケープ解析の注釈とは異なり、関数本体内であろうとなかろうと、常に型情報の一部として出力されるべきものです。

このコミットでは、条件式が以下のように変更されました。

```go
if flag&obj.FmtShort == 0 && (!fmtbody || !t.Funarg) && t.Note != nil {
    str += " " + strconv.Quote(*t.Note)
}
```

新しい条件 `(!fmtbody || !t.Funarg)` は、「関数本体内でフォーマットしていない (`!fmtbody`)」**または**「型が関数引数ではない (`!t.Funarg`)」場合に `t.Note` を出力することを意味します。

この変更の意図は以下の通りです。

*   **`fmtbody` の役割の明確化**: `fmtbody` フラグは、主にエスケープ解析の注釈のように、関数本体のコンテキストでのみ抑制すべき情報を制御するためのものです。構造体タグはこれに該当しません。
*   **`t.Funarg` の導入**: `t.Funarg` は、型が関数引数または戻り値である場合に `true` になります。関数引数や戻り値の型には構造体タグは通常付与されません（構造体型自体にはタグがありますが、関数引数としての型表現にはタグは含まれません）。したがって、`!t.Funarg` は、型が関数引数ではないことを意味し、この場合に構造体タグを出力しても問題ないことを示唆します。
*   **論理和 (`||`) の使用**: `!fmtbody || !t.Funarg` という条件は、以下のいずれかの状況で `true` になります。
    *   `!fmtbody` が `true` の場合（関数本体外でフォーマットしている場合）。
    *   `!t.Funarg` が `true` の場合（型が関数引数ではない場合）。
    これにより、たとえ `fmtbody` が `true`（関数本体内でフォーマットしている）であっても、その型が関数引数でなければ（つまり、通常の構造体フィールドなどであれば）、構造体タグが出力されるようになります。これは、インライン化された関数本体内の変数宣言が `fmtbody=true` となる状況でも、構造体タグが正しく出力されるようにするための重要な変更です。

コミットメッセージでは、この変更が条件を「緩和しすぎないか」という懸念が述べられています。つまり、以前は抑制されていたが抑制すべきではない情報（構造体タグ）を出力するようになる一方で、以前から抑制すべき情報（エスケープ解析の注釈など）を誤って出力してしまう可能性がないか、という点です。しかし、テストによって、この新しい条件が `issue13777.go` と `issue14331.go` の両方の制約を満たし、正しい挙動を示すことが確認されています。

## コアとなるコードの解説

変更は `src/cmd/compile/internal/gc/fmt.go` ファイル内の `typefmt` 関数にあります。この関数は、Goコンパイラの型システムにおいて、特定の型 (`*Type` t) を文字列形式で表現する役割を担っています。

具体的には、`typefmt` 関数内で構造体フィールドのタグ (`t.Note`) を出力するかどうかを決定する `if` 文の条件が変更されました。

**変更前:**

```go
if flag&obj.FmtShort == 0 && !fmtbody && t.Note != nil {
```

この条件は、以下の3つの条件がすべて真である場合に構造体タグを出力していました。
1.  `flag&obj.FmtShort == 0`: 型を短縮形式でフォーマットしない場合。
2.  `!fmtbody`: 関数本体内で型をフォーマットしていない場合。
3.  `t.Note != nil`: 型に注釈（この場合は構造体タグ）が存在する場合。

**変更後:**

```go
if flag&obj.FmtShort == 0 && (!fmtbody || !t.Funarg) && t.Note != nil {
```

変更された条件は、2番目の条件 `!fmtbody` が `(!fmtbody || !t.Funarg)` に置き換えられました。

この新しい条件 `(!fmtbody || !t.Funarg)` は、以下のいずれかの条件が真であれば全体として真となります。
*   `!fmtbody`: 関数本体内で型をフォーマットしていない場合。
*   `!t.Funarg`: 型が関数引数ではない場合。

この変更により、たとえ `fmtbody` が `true`（つまり、インライン化された関数本体内で型をフォーマットしている状況）であっても、その型が関数引数でなければ（`!t.Funarg` が `true`）、構造体タグが正しく出力されるようになりました。

コメントで説明されているように、`fmtbody` フラグは本来、関数本体内で使用される関数型のエスケープ解析の注釈を抑制するためのものでした。しかし、このフラグが構造体フィールドのタグまで抑制してしまうのは意図しない挙動でした。今回の修正は、`fmtbody` の本来の意図を尊重しつつ、構造体タグの出力が不当に抑制されないようにするためのものです。

新しいテストケース `issue14331.dir/a.go` と `issue14331.dir/b.go` は、この修正が正しく機能することを確認するために追加されました。`a.go` ではタグ付き構造体 `S` が定義され、`F()` 関数がそのフィールドにアクセスします。`b.go` では `a.F()` を呼び出す `G()` 関数が定義されており、インライン化のシナリオをテストしています。

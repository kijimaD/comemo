# [インデックス 202] ファイルの概要

このコミットは、Go言語のランタイムにおいて、パニック発生時に基本的なスタックトレースを出力する機能を追加するものです。これにより、プログラムが予期せぬエラーで終了した場合に、どこで何が起こったのかをデバッグするための初期的な情報が提供されるようになりました。

## 変更の背景

Go言語は、その設計初期段階から堅牢なエラーハンドリングとデバッグ機能を目指していました。このコミットが行われた2008年6月は、Go言語がまだ一般に公開される前の非常に初期の段階であり、ランタイムの基本的な機能が構築されている最中でした。

プログラムが「パニック」（panic）を起こして異常終了する際、その原因を特定するためには、プログラムがどのような関数の呼び出し順序を経てその状態に至ったかを示す「スタックトレース」が不可欠です。このコミット以前は、パニック発生時に単にエラーメッセージが表示されるだけで、詳細な実行コンテキストが提供されていませんでした。

この変更は、開発者がパニックの原因をより効率的に特定し、デバッグ作業を容易にするための、Goランタイムにおけるデバッグ機能の基礎を築く一歩でした。特に、Go言語の設計思想である「エラーは明示的に処理するべきだが、回復不能なエラーはパニックとして扱う」という考え方に基づき、パニック発生時の情報提供を強化する必要がありました。

## 前提知識の解説

### Goにおけるpanicとrecover

Go言語には、エラーハンドリングのための2つの主要なメカニズムがあります。

1.  **エラー (error)**: 予期されるが、通常は回復可能な問題（例: ファイルが見つからない、ネットワーク接続の失敗）に対して使用されます。関数は`error`型の値を返すことでエラーを通知し、呼び出し元はこれを明示的にチェックして処理します。
2.  **パニック (panic)**: プログラムが回復不能な状態に陥った場合（例: 配列の範囲外アクセス、nilポインタのデリファレンス）に発生します。パニックが発生すると、現在の関数の実行は停止し、遅延関数（`defer`）が実行され、呼び出し元の関数へとスタックを巻き戻しながら伝播していきます。最終的にスタックの最上位まで到達すると、プログラムは異常終了します。`recover`組み込み関数を使用することで、パニックを捕捉し、プログラムの実行を継続させることも可能ですが、これは通常、サーバーのクラッシュを防ぐなどの特定のシナリオでのみ推奨されます。

このコミットは、パニックが発生した際に、その原因究明に役立つスタックトレースを出力する機能を追加するものです。

### スタックトレース

スタックトレース（またはバックトレース）は、プログラムの実行中に特定の時点（通常はエラーや例外が発生した時点）で、現在実行中の関数から、その関数を呼び出した関数、さらにその関数を呼び出した関数…と遡って、関数の呼び出し履歴（コールスタック）を一覧表示したものです。

スタックトレースは、デバッグにおいて極めて重要な情報を提供します。
*   **エラー発生箇所の特定**: どの関数でエラーが発生したか。
*   **実行パスの理解**: エラーに至るまでにどのような関数の流れがあったか。
*   **コンテキストの把握**: 各関数の呼び出し時の引数やローカル変数の状態（このコミットでは限定的ですが）。

### Goランタイムの初期段階と`runtime.c`

このコミットが行われた2008年当時、Go言語のランタイムは現在のようにGo言語自身で書かれている部分が少なく、多くの部分がC言語で実装されていました。`src/runtime/runtime.c`は、当時のGoランタイムの核心部分であり、メモリ管理、スケジューリング、プリミティブなI/O、そしてパニック処理といった低レベルな機能がC言語で記述されていました。

このため、このコミットで追加されたスタックトレースのロジックもC言語で書かれており、ポインタ演算を多用してスタックフレームを直接解析する、非常に低レベルな実装となっています。これは、当時のGoランタイムがまだ成熟しておらず、OSやハードウェアとの直接的なインタラクションがC言語で行われていたことを示しています。

### `sys_panicl`関数と`sys_print*`関数

*   **`sys_panicl(int32 lno)`**: この関数は、Goプログラム内でパニックが発生した際に、ランタイムによって呼び出される低レベルなパニックハンドラです。引数`lno`は、パニックが発生したソースコードの行番号を示します。このコミットでは、この関数内にスタックトレース出力ロジックが追加されました。
*   **`sys_print*`関数**: `prints` (文字列出力), `sys_printint` (整数出力), `sys_printpointer` (ポインタ値出力) などは、Goランタイムが提供する非常にプリミティブな出力関数です。これらは、標準ライブラリの`fmt`パッケージなどが利用できない、ランタイムの非常に初期の段階やデバッグ目的で使用されます。OSのシステムコールを直接呼び出すことで、コンソールに情報を出力します。

## 技術的詳細

このコミットの核心は、`sys_panicl`関数内にスタックトレースを生成し出力するロジックを追加した点にあります。

1.  **初期情報の出力**:
    まず、パニックが発生した行番号と、その行番号の変数`lno`のアドレス（`sys_printpc(&lno)`）が出力されます。これは、パニックの直接的な発生源を示す情報です。

2.  **スタックポインタとプログラムカウンタの初期化**:
    *   `sp = (uint8*)&lno;`: 現在のスタックポインタ（`sp`）を、`sys_panicl`関数のローカル変数`lno`のアドレスに初期化します。これは、スタックトレースの探索を開始する基準点となります。
    *   `pc = (uint8*)sys_panicl;`: プログラムカウンタ（`pc`）を`sys_panicl`関数の開始アドレスに初期化します。これは、現在の実行中の関数（`sys_panicl`自身）のコード領域を指します。

3.  **スタックフレームの探索ループ**:
    `while((pc = ((uint8**)sp)[-1]) > (uint8*)0x1000)`: このループは、スタックを遡り、呼び出し元の関数のリターンアドレス（プログラムカウンタ）を見つけることで、スタックフレームを探索します。
    *   `((uint8**)sp)[-1]`: これは、現在のスタックポインタ`sp`から1ワード（ポインタサイズ）前のメモリ位置をポインタとして解釈し、その値を`pc`に代入しています。C言語の呼び出し規約では、通常、関数呼び出し時にリターンアドレスがスタックにプッシュされます。このコードは、そのリターンアドレスを探索しようとしています。
    *   `> (uint8*)0x1000`: これは、取得した`pc`の値が有効なコードアドレスであるかどうかの非常に粗いチェックです。`0x1000`は、NULLポインタや非常に低いアドレス（通常はOSが予約している領域）ではないことを確認するためのマジックナンバーです。当時のGoランタイムでは、メモリ保護やアドレス空間のレイアウトが現在ほど厳密ではなかったため、このようなシンプルなチェックが用いられていた可能性があります。

4.  **スタック内容のダンプ（デバッグ用）**:
    `for(i = 0; i < 3; i++){ ... }`: 各スタックフレームの探索中に、現在のスタックポインタ`sp`の周辺の3ワード分の内容を、`int32`と`void*`としてダンプしています。これは、デバッグ目的でスタック上の値を確認するためのものです。

5.  **リターンアドレスとスタックオフセットの特定**:
    *   `retpc = pc;`: 探索で見つかったリターンアドレスを`retpc`に保存します。
    *   `spmark[] = "\\xa7\\xf1\\xd9\\x2a\\x82\\xc8\\xd8\\xfe";`: この`spmark`は、スタックオフセットを特定するための「マジックバイト列」です。Goのコンパイラ（またはアセンブラ）が、関数プロローグ（関数の開始部分）に特定のバイト列とそれに続くスタックフレームのサイズを埋め込むことで、ランタイムが動的にスタックフレームのサイズを特定できるようにしていたと考えられます。
    *   `while(pc > (uint8*)0x1000+11)`: `pc`をデクリメントしながら、`spmark`と一致するバイト列をコード領域内で検索します。
    *   `for(spp = spmark; *spp != '\0' && *pc++ == (uint8)*spp++; )`: `pc`をインクリメントしながら`spmark`と比較しています。これは、`pc`が指すコードが`spmark`と一致するかをチェックしています。
    *   `if(*spp == '\0')`: `spmark`全体が一致した場合、その直後に続く3バイトがスタックオフセット（`spoff`）として読み取られます。
    *   `spoff = *pc++; spoff += *pc++ << 8; spoff += *pc++ << 16;`: 3バイトを結合して`spoff`を計算します。これは、リトルエンディアン形式でスタックフレームのサイズをエンコードしていることを示唆しています。
    *   `prints((int8*)pc); prints("+"); sys_printint(pc-retpc); prints("?zi\\n");`: ここで、関数名（またはその一部）と、リターンアドレスからのオフセットを出力しようとしています。`?zi`は、当時のデバッグ情報が不完全であったり、シンボル解決がまだ実装されていなかったりしたため、プレースホルダーとして出力されていた可能性があります。
    *   `sp += spoff + 8;`: 次のスタックフレームを探索するために、スタックポインタ`sp`を計算された`spoff`と追加の8バイト（おそらくリターンアドレスとフレームポインタのサイズ）だけ進めます。

6.  **トレースの制限**:
    `if(counter++ > 100){ ... break; }`: 無限ループを防ぐため、スタックトレースの深さを100フレームに制限しています。

7.  **最終的なクラッシュ**:
    `*(int32*)0 = 0;`: スタックトレースの出力後、意図的にNULLポインタをデリファレンスすることで、プログラムをクラッシュさせます。これは、パニックが最終的にプログラムの異常終了を引き起こすことを保証するためのものです。

この実装は、現在のGoランタイムのスタックトレース生成と比較すると非常にプリミティブであり、C言語のポインタ演算とマジックバイトに大きく依存しています。これは、Go言語がまだ初期段階であり、より洗練されたデバッグ情報やランタイムの自己記述能力が不足していた時代の名残と言えます。

```diff
--- a/src/runtime/runtime.c
+++ b/src/runtime/runtime.c
@@ -102,11 +102,61 @@ sys_printpc(void *p)
 void

+	uint8 *pc;
+	uint8 *sp;
+	uint8 *retpc;
+	int32 spoff;
+	static int8 spmark[] = "\xa7\xf1\xd9\x2a\x82\xc8\xd8\xfe";
+	int8* spp;
+	int32 counter;
+	int32 i;
+
 	prints("\npanic on line ");
 	sys_printint(lno);
 	prints(" ");
 	sys_printpc(&lno);

+	sp = (uint8*)&lno;
+	pc = (uint8*)sys_panicl;
+	counter = 0;
+	while((pc = ((uint8**)sp)[-1]) > (uint8*)0x1000) {
+		for(i = 0; i < 3; i++){
+			prints("\tint32[");
+			sys_printint(i);
+			prints("]=");
+			sys_printint(((uint32*)sp)[i]);
+			prints("\tint64*[");
+			sys_printint(i);
+			prints("]=");
+			sys_printpointer(((void**)sp)[i]);
+			prints("\n");
+		}
+		prints("0x");
+		sys_printpointer(pc);
+		prints(" ");
+		/* next word down on stack is PC */
+		retpc = pc;
+		/* find SP offset by stepping back through instructions to SP offset marker */
+		while(pc > (uint8*)0x1000+11) {
+			for(spp = spmark; *spp != '\0' && *pc++ == (uint8)*spp++; )
+				;
+			if(*spp == '\0'){

+				spoff += *pc++ << 8;
+				spoff += *pc++ << 16;
+				prints((int8*)pc);
```

## コアとなるコードの解説

追加されたコードは、`sys_panicl`関数内に実装されています。

1.  **変数の宣言**:
    `uint8 *pc;`, `uint8 *sp;`, `uint8 *retpc;`, `int32 spoff;`, `static int8 spmark[] = "\xa7\xf1\xd9\x2a\x82\xc8\xd8\xfe";`, `int8* spp;`, `int32 counter;`, `int32 i;`
    スタックトレースの解析に必要なポインタ、オフセット、カウンタ、ループ変数などが宣言されています。`spmark`は、スタックフレームの境界を識別するためのマジックバイト列です。

2.  **パニック発生行の出力**:
    `prints("\npanic on line "); sys_printint(lno); prints(" "); sys_printpc(&lno); prints("\n");`
    パニックが発生した行番号と、その行番号を保持する変数`lno`のアドレスを出力します。

3.  **スタックポインタとプログラムカウンタの初期化**:
    `sp = (uint8*)&lno;`
    `pc = (uint8*)sys_panicl;`
    スタックトレースの開始点として、現在のスタックポインタを`lno`のアドレスに、プログラムカウンタを`sys_panicl`関数の開始アドレスに設定します。

4.  **スタックトレースループ**:
    `while((pc = ((uint8**)sp)[-1]) > (uint8*)0x1000)`
    このループは、スタックを遡り、各関数のリターンアドレスを見つけることでスタックフレームを特定します。`((uint8**)sp)[-1]`は、現在のスタックポインタの1ワード前の値をリターンアドレスとして取得しようとします。`> (uint8*)0x1000`は、取得したアドレスが有効なコード領域内にあるかどうかの基本的なチェックです。

5.  **スタック内容のデバッグ出力**:
    `for(i = 0; i < 3; i++){ ... }`
    各スタックフレームの処理中に、現在のスタックポインタ`sp`の周辺の3ワード分の内容を`int32`と`void*`として出力します。これは、デバッグ時にスタックの状態を把握するためのものです。

6.  **リターンアドレスとスタックオフセットの特定**:
    `retpc = pc;`
    `while(pc > (uint8*)0x1000+11)`
    `for(spp = spmark; *spp != '\0' && *pc++ == (uint8)*spp++; )`
    `if(*spp == '\0'){ ... }`
    この部分がスタックトレースの核心です。`pc`をデクリメントしながら、`spmark`で定義されたマジックバイト列をコード領域内で検索します。このマジックバイト列は、Goコンパイラが生成する関数プロローグの一部であり、その直後にスタックフレームのサイズ情報が埋め込まれていると推測されます。
    マジックバイト列が見つかると、その直後の3バイトを読み取り、`spoff`（スタックオフセット）として解釈します。これは、現在のスタックフレームのサイズを示します。

7.  **関数名とオフセットの出力**:
    `prints((int8*)pc); prints("+"); sys_printint(pc-retpc); prints("?zi\n");`
    `spmark`が見つかった位置から`pc`が指す文字列（おそらく関数名の一部）と、リターンアドレス`retpc`からのオフセットを出力します。`?zi`は、シンボル解決がまだ不完全であったことを示唆するプレースホルダーです。

8.  **スタックポインタの更新**:
    `sp += spoff + 8;`
    次のスタックフレームを探索するために、スタックポインタ`sp`を、特定されたスタックオフセット`spoff`と追加の8バイト（リターンアドレスとフレームポインタのサイズに相当すると考えられる）だけ進めます。

9.  **トレースの深さ制限**:
    `if(counter++ > 100){ prints("stack trace terminated\n"); break; }`
    無限ループや過剰なトレースを防ぐため、スタックトレースの深さを100フレームに制限しています。

10. **最終的なクラッシュ**:
    `*(int32*)0 = 0;`
    スタックトレースの出力後、意図的にNULLポインタをデリファレンスすることで、プログラムをクラッシュさせます。これは、パニックが最終的にプログラムの異常終了を引き起こすことを保証するためのものです。

このコードは、Go言語の初期のランタイムが、C言語の低レベルなポインタ操作と、コンパイラが生成する特定のバイトパターンを利用して、スタックトレースという複雑なデバッグ情報をどのように生成していたかを示す貴重な例です。

## 元コミット内容

このコミットの元の内容は、定数評価に関するバグを報告したものです。同時に、`usr/gri/src/scanner.go` ファイルにおいて、Go言語の字句解析器（スキャナー）の機能強化とリファクタリングが行われています。具体的には、トークンの文字列表現の変更、UTF-8文字のサポート、およびキーワードの初期化ロジックの改善が含まれます。

## 変更の背景

Go言語は2008年当時、まだ開発の初期段階にあり、言語仕様やコンパイラの各コンポーネントが活発に構築・改善されていました。この時期には、言語の基本的な機能（字句解析、構文解析、型チェック、定数評価など）が確立されていく過程で、多くのバグが発見され、機能が追加されていました。

このコミットの背景には、以下の主要な動機があったと考えられます。

1.  **定数評価の正確性向上**: `const c = 0 ^ 0` のような単純な定数式がコンパイルエラーとなる問題が発見されました。これは、コンパイラが定数式を正しく評価できないことを示しており、言語の基本的な信頼性に関わる問題でした。このコミットは、このバグを「報告」するものであり、直接的な修正は含まれていない可能性がありますが、問題意識の表れです。
2.  **スキャナーの堅牢性向上**: 初期のスキャナーは、ASCII文字のみを想定している部分がありました（`panic "UTF-8 not handled"`というコードが存在）。Go言語が国際的な利用を視野に入れる上で、UTF-8エンコーディングされたソースコードを正しく処理できることは必須でした。
3.  **コードの保守性向上**: `scanner.go` 内の `TokenName` 関数や `Init` 関数のリファクタリングは、コードの可読性、保守性、拡張性を高めることを目的としています。特に、トークンの文字列表現を実際のシンボルに合わせることで、デバッグやエラーメッセージの生成がより直感的になります。また、キーワードの初期化を自動化することで、将来的なキーワードの追加・削除が容易になります。

## 前提知識の解説

このコミットを理解するためには、以下の概念が役立ちます。

*   **字句解析 (Lexical Analysis)**: コンパイラの最初の段階で、ソースコードを意味のある最小単位（トークン）に分割するプロセスです。このコミットで変更されている `scanner.go` は、この字句解析を担当します。
    *   **トークン (Token)**: プログラミング言語における最小の意味単位です。例えば、`if`、`=`、`myVariable`、`123` などがトークンです。
*   **UTF-8**: Unicode文字を可変長でエンコードするための文字エンコーディング方式です。ASCII文字は1バイトで表現され、それ以外の多くの文字は2バイト以上で表現されます。Go言語のソースコードはUTF-8で記述されることが標準です。
*   **定数評価 (Constant Evaluation)**: コンパイル時に定数式（例: `1 + 2`、`"hello" + "world"`）の値を計算することです。これにより、実行時の計算コストを削減し、コンパイルエラーを早期に検出できます。
*   **Go言語の初期開発**: 2008年頃のGo言語は、まだ一般公開されておらず、Google社内で開発が進められていました。言語仕様は流動的で、コンパイラも基本的な機能の実装とバグ修正が繰り返されていました。この時期のコミットは、言語の根幹を形成する重要な変更が多く含まれています。
*   **`iota`**: Go言語における定数宣言で、連続する定数に自動的に値を割り当てるための特殊な識別子です。このコミットの `scanner.go` でも `iota` が使用されており、トークン定数の定義に利用されています。

## 技術的詳細

このコミットにおける技術的な変更点は多岐にわたります。

1.  **`TokenName` 関数の変更**:
    *   以前は `ILLEGAL` や `EOF` のようなトークンに対して `"ILLEGAL"`、`"EOF"` といった大文字の文字列を返していました。
    *   変更後は、`ILLEGAL` は `"illegal"`、`EOF` は `"eof"` と小文字になり、演算子（`ADD`, `XOR` など）や区切り文字（`COMMA`, `LPAREN` など）については、それぞれ `"+"`, `"^"`, `","`, `"("` といった実際のシンボルを返すようになりました。
    *   この変更は、主にデバッグ出力やエラーメッセージの可読性を向上させることを目的としています。コンパイラの内部処理でトークンを識別する数値定数自体は変更されていませんが、その文字列表現がより直感的になりました。

2.  **`Scanner.Next()` 関数のUTF-8対応**:
    *   この関数は、ソースコードから次の文字（rune）を読み取る役割を担っています。
    *   変更前は、ASCII範囲外の文字（`S.ch >= 128`）を検出すると `panic "UTF-8 not handled"` を発生させていました。これは、初期のスキャナーがUTF-8マルチバイト文字を正しく処理できなかったことを示しています。
    *   変更後は、UTF-8エンコーディングの仕様に基づいて、1バイト、2バイト、3バイトの文字シーケンスを適切にデコードするロジックが追加されました。
        *   `Bit1`, `Bitx`, `Bit2`, `Bit3`, `Bit4` などの定数は、UTF-8のバイト構造を解析するためのビットマスクやシフト量を定義しています。
        *   `T1`, `Tx`, `T2`, `T3`, `T4` は、UTF-8シーケンスの開始バイトを識別するためのマスクです。
        *   `Rune1`, `Rune2`, `Rune3` は、デコードされたルーンが有効な範囲内にあるかを確認するための境界値です。
        *   `Maskx`, `Testx` は、後続バイトがUTF-8の継続バイトの形式（`10xxxxxx`）に合致するかをチェックするためのマスクです。
        *   `Bad` は、不正なUTF-8シーケンスが検出された場合に割り当てられるエラー値（`0xFFFD`、UnicodeのReplacement Character）です。
    *   この変更により、Go言語のソースコード内で非ASCII文字（例: 日本語、絵文字など）を文字列リテラルやコメント、あるいは（将来的に）識別子として使用できるようになるための基盤が築かれました。

3.  **`Init()` 関数のキーワード初期化の改善**:
    *   以前は、`Keywords` マップに各キーワード（`"break"`, `"case"` など）とそのトークン定数を手動で一つずつ追加していました。
    *   変更後は、`KEYWORDS_BEG` から `KEYWORDS_END` までの範囲を `for` ループで反復し、`TokenName(i)` を呼び出してキーワードの文字列を取得し、それをマップに登録するように変更されました。
    *   このアプローチは、キーワードの追加や削除があった場合に `Init()` 関数を修正する手間を省き、コードの重複を減らし、保守性を大幅に向上させます。`iota` を利用してトークン定数を定義しているため、この自動化が可能になります。

4.  **定数評価のバグ報告**:
    *   `test/bugs/bug063.go` が追加され、`const c = 0 ^ 0` というコードがコンパイルエラーとなる問題が示されています。
    *   `golden.out` に記録されたエラーメッセージは、「`bugs/bug063.go:4: illegal combination of literals XOR 7`」や「`bugs/bug063.go:4: expression must be a constant`」といったもので、コンパイラの定数評価ロジックがビット排他的論理和（XOR）演算子を伴う定数式を正しく処理できていないことを明確に示しています。
    *   このコミット自体はバグを修正するものではなく、その存在を公式に記録し、今後の修正を促すためのものです。

## コアとなるコードの解説

### `TokenName` 関数の変更

この変更は、Go言語のトークンが外部に表示される際の表現方法を標準化するものです。例えば、エラーメッセージで「`XOR`」ではなく「`^`」と表示されることで、開発者はより直感的に問題箇所を特定できるようになります。これは、コンパイラのユーザーインターフェース（エラー報告）の品質向上に寄与します。

### `Scanner.Next()` 関数のUTF-8対応

この変更は、Go言語の国際化対応における重要な一歩です。
`Scanner.Next()` は、ソースコードのバイト列から次のUnicodeコードポイント（rune）を抽出します。UTF-8は可変長エンコーディングであるため、1バイトで表現されるASCII文字だけでなく、2バイト、3バイト（さらには4バイト）で表現される文字も正しく読み取る必要があります。

新しい実装では、以下のロジックでUTF-8シーケンスを解析します。

1.  **1バイトシーケンス (ASCII)**: 最初のバイトが `0xxxxxxx` の形式であれば、それは1バイトのASCII文字として扱われます。
2.  **マルチバイトシーケンスの識別**: 最初のバイトが `110xxxxx` (2バイト)、`1110xxxx` (3バイト)、`11110xxx` (4バイト) の形式であれば、それぞれ2バイト、3バイト、4バイトのシーケンスとして認識されます。
3.  **継続バイトの検証**: マルチバイトシーケンスの場合、後続のバイトが `10xxxxxx` の形式であるかを検証します。これが満たされない場合や、デコードされたルーンが有効なUnicode範囲外である場合は、不正なエンコーディングとして `Bad` ルーン（`0xFFFD`）が返されます。
4.  **`goto` ステートメント**: この初期のGoコードでは、エラー処理やEOF処理のために `goto` ステートメントが使用されています。これは、当時のGo言語のイディオムの一部であり、後のバージョンではより構造化されたエラーハンドリングに置き換えられることが一般的です。

このUTF-8対応により、Go言語のコンパイラは、世界中の多様な文字セットで書かれたソースコードを正しく処理できるようになりました。

### `Init()` 関数のキーワード初期化の改善

この変更は、Go言語のキーワードリストが変更された際に、`scanner.go` のコードをより簡単に更新できるようにするためのものです。`iota` を使用してキーワードのトークン定数を定義し、その定数範囲をループで回して `TokenName` から文字列を取得することで、キーワードの追加・削除時に `Init()` 関数内の手動リストを更新する必要がなくなります。これは、コードの自動生成やメタプログラミングに近いアプローチであり、大規模なプロジェクトにおけるコードの保守性を高める上で非常に有効です。

### 定数評価のバグ

`const c = 0 ^ 0` のバグは、コンパイラのセマンティック分析フェーズ、特に定数式の評価ロジックに問題があったことを示唆しています。`XOR` 演算子（`^`）は整数リテラルに対して有効な演算ですが、当時のコンパイラはこれを正しく認識できていなかったか、あるいは定数コンテキストでの評価ルールに不備があったと考えられます。このコミットはバグを報告するものであり、このバグの修正は後続のコミットで行われた可能性が高いです。

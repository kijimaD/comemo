## 元コミット内容

このコミットは、Goの`testing`パッケージにおけるベンチマークの実行フローを変更し、特にサブベンチマークの検出方法を改善します。以前は`probe`という関数がベンチマークにサブベンチマークがあるかを調べるために使用されていましたが、このコミットではそのロジックが`run1`という新しい関数に集約され、`N=1`（1回のイテレーション）でベンチマーク関数を実行するように変更されています。これにより、サブベンチマークがない場合でも、`benchFunc`が以前と同じ回数だけ呼び出されるようになります。また、既存のベンチマークツールとの互換性を保つため、ベンチマーク名は最初のイテレーション後にのみ出力される「リーフ」ベンチマークに対してのみ表示されるようになります。

## 変更の背景

この変更の背景には、Goのベンチマーク機能におけるサブベンチマークの扱いと、ベンチマーク結果の出力に関する課題がありました。`Issue #14863`で報告された問題は、おそらくベンチマークの初期実行（プローブ）が、サブベンチマークの有無によって`benchFunc`の呼び出し回数に不整合を生じさせていたこと、またはベンチマーク名の出力タイミングが既存ツールと合致していなかったことに関連していると考えられます。

具体的には、ベンチマークがサブベンチマークを持つかどうかを判断するために、一度ベンチマーク関数を実行する必要がありました。この「プローブ」の段階で、`N`（イテレーション回数）がどのように設定されるか、そしてその結果が後続のベンチマーク実行や結果出力にどう影響するかが問題となっていました。特に、サブベンチマークを持たないベンチマークの場合、プローブの実行が余分な`benchFunc`の呼び出しとなったり、あるいは期待される回数と異なったりする可能性がありました。

また、ベンチマーク結果を解析する既存のツールは、特定の形式で出力されるベンチマーク名を期待していました。サブベンチマークの検出ロジックの変更に伴い、ベンチマーク名の出力タイミングや条件を調整し、これらのツールとの互換性を維持する必要がありました。このコミットは、これらの問題を解決し、ベンチマークの実行ロジックをより堅牢で予測可能なものにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語のベンチマークに関する前提知識が必要です。

1.  **`go test -bench`**: Go言語でベンチマークを実行するためのコマンドです。`go test -bench=.`のように実行すると、プロジェクト内のすべてのベンチマーク関数が実行されます。
2.  **`testing`パッケージ**: Goの標準ライブラリで、テストとベンチマーク機能を提供します。
3.  **`*testing.B`**: ベンチマーク関数に渡される構造体で、ベンチマークの制御（例: `b.N`、`b.ResetTimer()`、`b.Run()`) を行います。
4.  **`b.N`**: ベンチマーク関数が実行されるイテレーション回数を示します。`testing`パッケージは、指定された`benchTime`（デフォルト1秒）内にベンチマークが完了するように、`b.N`の値を動的に調整します。
5.  **`b.benchFunc(b *B)`**: ユーザーが記述する実際のベンチマークロジックを含む関数です。
6.  **サブベンチマーク (`b.Run`)**: `b.Run("sub-benchmark-name", func(b *B){ ... })`のように使用することで、一つのベンチマーク関数内で複数のサブベンチマークを定義できます。これにより、関連する複数のシナリオを一つのベンチマークグループとしてテストできます。
7.  **リーフベンチマーク**: サブベンチマークを持たない、またはサブベンチマークの階層構造の最下層にあるベンチマークを指します。ベンチマーク結果の出力は通常、これらのリーフベンチマークに対して行われます。
8.  **`runtime.GOMAXPROCS`**: Goプログラムが使用できるOSスレッドの最大数を設定します。ベンチマークは通常、異なる`GOMAXPROCS`値で複数回実行され、並行処理性能を評価します。

## 技術的詳細

このコミットの技術的詳細は、主に`src/testing/benchmark.go`内の`*B`構造体のメソッドの変更に集約されます。

### `probe()` から `run1()` への変更

*   **旧実装 (`probe()`):** 以前は`probe()`というメソッドが存在し、その目的は「ベンチマーク関数がサブベンチマークを持っているかどうかを調べる」ことでした。このメソッドは`b.N = 0`を設定し、`b.benchFunc(b)`を呼び出していました。`b.N = 0`であるにもかかわらず`b.benchFunc`が呼び出されるのは、`b.Run`が呼び出されることで`b.hasSub`フラグが設定されることを期待していたためです。しかし、`b.N=0`での実行は、`benchFunc`が実際に何らかの処理を行うことを保証せず、また`benchFunc`が`b.N`に依存するロジックを含んでいた場合に予期せぬ挙動を引き起こす可能性がありました。
*   **新実装 (`run1()`):** `probe()`は`run1()`に改名され、そのロジックが大幅に変更されました。
    *   `b.N = 0`の代わりに、`b.runN(1)`が呼び出されるようになりました。これは、ベンチマーク関数を明示的に1回だけ実行することを意味します。
    *   `run1()`は`bool`値を返すようになり、`!b.hasSub`（サブベンチマークがない場合）を返します。これにより、呼び出し元はベンチマークがサブベンチマークを持つかどうかを簡単に判断し、後続の処理を決定できます。
    *   この変更により、`benchFunc`は常に少なくとも1回は`N=1`で実行されることが保証されます。これにより、サブベンチマークの検出がより確実になり、`benchFunc`が`N`に依存する初期化ロジックを含んでいても安全に実行できるようになります。

### `launch()` メソッドの変更

*   **旧実装:** `launch()`メソッドは、ベンチマークのイテレーション回数を徐々に増やして`benchTime`を満たすように調整する役割を担っていました。以前は、最初に`n = 1`として`b.runN(n)`を呼び出し、その後ループ内で`n`を増やしていました。
*   **新実装:** `run1()`が導入されたことで、`launch()`の初期`b.runN(n)`の呼び出しが削除されました。代わりに、`launch()`のコメントに「`run1`が`b`に対して呼び出されている必要がある」と明記されています。これは、`run1()`が既に最初の1回のイテレーションを実行しているため、`launch()`内で再度`N=1`で実行する必要がなくなったことを意味します。ループの初期化も`for n := 1; ...`に変更され、`n`の初期値が1から始まるようになりました。

### `processBench()` メソッドの変更

*   `processBench()`は、異なる`GOMAXPROCS`設定でベンチマークを実行し、結果を出力する役割を担っています。
*   このコミットでは、`cpuList`の最初の要素（`i == 0`）以外の`GOMAXPROCS`設定でベンチマークを実行する際に、`b.run1()`が明示的に呼び出されるようになりました。
*   これは、`GOMAXPROCS`が変わるたびに新しい`*B`インスタンスが作成され、その新しいインスタンスに対してサブベンチマークの検出（`hasSub`フラグの設定）を再度行う必要があるためです。`run1()`を呼び出すことで、各`GOMAXPROCS`設定でのベンチマーク実行前に、サブベンチマークの有無が正しく検出されるようになります。

### `Run()` メソッドの変更

*   `b.Run()`はサブベンチマークを定義するために使用されます。
*   **旧実装:** `sub.probe()`を呼び出し、`!sub.hasSub`であれば`sub.run()`を実行していました。
*   **新実装:** `sub.run1()`を呼び出し、その戻り値が`true`（サブベンチマークがない場合）であれば`sub.run()`を実行するように変更されました。
*   この変更は、`probe()`が`run1()`に置き換えられたことに伴う直接的な修正です。`run1()`が`N=1`で実行されるため、`b.Run`が呼び出されたベンチマーク自体は測定されず、`N=1`で一度だけ呼び出されるというコメントも追加されています。

### `src/testing/sub_test.go` の変更

*   `TestBRun`関数内で、`root.run()`が`root.runN(1)`に変更されました。これは、テストケース内でベンチマークの初期実行をシミュレートする際に、`N=1`での実行がより適切であることを示しています。

これらの変更により、ベンチマークの初期プローブが`N=1`で統一され、サブベンチマークの検出ロジックがより明確かつ堅牢になりました。また、ベンチマークの実行回数に関する不整合が解消され、既存のベンチマークツールとの互換性が向上しています。

## コアとなるコードの解説

### `src/testing/benchmark.go`

1.  **`func (b *B) run1() bool`**:
    *   この関数は、以前の`probe()`関数を置き換えるものです。
    *   目的は、ベンチマーク関数`b.benchFunc`を1回だけ実行し、そのベンチマークがサブベンチマークを持つかどうかを検出することです。
    *   `b.runN(1)`を呼び出すことで、`b.benchFunc`が`N=1`で実行されます。これにより、`b.Run`が呼び出された場合に`b.hasSub`フラグが正しく設定されることが保証されます。
    *   `return !b.hasSub`は、このベンチマークがサブベンチマークを持たない場合に`true`を返します。これは、呼び出し元がこのベンチマークを通常のベンチマークとして実行すべきかどうかを判断するために使用されます。

2.  **`func (b *B) launch()`**:
    *   この関数は、ベンチマークのイテレーション回数`n`を`benchTime`に基づいて動的に調整するメインのループを含んでいます。
    *   変更点として、初期の`n = 1`での`b.runN(n)`の呼び出しが削除されました。これは、`launch()`が呼び出される前に`b.run1()`が既に実行されていることを前提としているためです。
    *   ループの初期化が`for n := 1; ...`に変更され、`n`が1から始まるようになりました。

3.  **`func (ctx *benchContext) processBench(b *B)`**:
    *   この関数は、異なる`GOMAXPROCS`設定でベンチマークを実行するロジックを含んでいます。
    *   `for i, procs := range cpuList`ループ内で、`i > 0`の場合（つまり、最初の`GOMAXPROCS`設定以外の場合）に新しい`*B`インスタンスを作成し、そのインスタンスに対して`b.run1()`を呼び出すようになりました。
    *   これは、`GOMAXPROCS`設定が変わるたびにベンチマークのコンテキストがリセットされるため、新しいコンテキストでサブベンチマークの検出を再度行う必要があるためです。

4.  **`func (b *B) Run(name string, f func(b *B)) bool`**:
    *   サブベンチマークを定義するためのメソッドです。
    *   `sub.probe()`の呼び出しが`sub.run1()`に置き換えられました。
    *   `if sub.run1() { sub.run() }`という条件分岐により、サブベンチマークを持たない（`run1()`が`true`を返す）場合にのみ、そのサブベンチマークが通常のベンチマークとして実行されます。
    *   コメントが更新され、「`b.Run`が少なくとも一度呼び出されたベンチマークはそれ自体は測定されず、`N=1`で一度だけ呼び出される」という説明が追加されました。これは、親ベンチマークがサブベンチマークのコンテナとして機能し、実際の測定はサブベンチマークで行われるという意図を明確にしています。

### `src/testing/sub_test.go`

1.  **`func TestBRun(t *T)`**:
    *   このテスト関数内で、`root.run()`の呼び出しが`root.runN(1)`に変更されました。
    *   これは、`b.Run`の挙動をテストする際に、ベンチマークの初期実行を`N=1`でシミュレートすることが、新しい`run1()`のロジックと整合性が取れるためです。

これらの変更は、Goのベンチマークシステムにおけるサブベンチマークの検出と実行のロジックをより一貫性のあるものにし、`benchFunc`の呼び出し回数を予測可能にすることで、ベンチマークの信頼性と既存ツールとの互換性を向上させています。

## 元コミット内容

このコミットは、Goの`testing`パッケージにおけるベンチマークの実行フローを変更し、特にサブベンチマークの検出方法を改善します。以前は`probe`という関数がベンチマークにサブベンチマークがあるかを調べるために使用されていましたが、このコミットではそのロジックが`run1`という新しい関数に集約され、`N=1`（1回のイテレーション）でベンチマーク関数を実行するように変更されています。これにより、サブベンチマークがない場合でも、`benchFunc`が以前と同じ回数だけ呼び出されるようになります。また、既存のベンチマークツールとの互換性を保つため、ベンチマーク名は最初のイテレーション後にのみ出力される「リーフ」ベンチマークに対してのみ表示されるようになります。

## 変更の背景

この変更の背景には、Goのベンチマーク機能におけるサブベンチマークの扱いと、ベンチマーク結果の出力に関する課題がありました。`Issue #14863`で報告された問題は、おそらくベンチマークの初期実行（プローブ）が、サブベンチマークの有無によって`benchFunc`の呼び出し回数に不整合を生じさせていたこと、またはベンチマーク名の出力タイミングが既存ツールと合致していなかったことに関連していると考えられます。

具体的には、ベンチマークがサブベンチマークを持つかどうかを判断するために、一度ベンチマーク関数を実行する必要がありました。この「プローブ」の段階で、`N`（イテレーション回数）がどのように設定されるか、そしてその結果が後続のベンチマーク実行や結果出力にどう影響するかが問題となっていました。特に、サブベンチマークを持たないベンチマークの場合、プローブの実行が余分な`benchFunc`の呼び出しとなったり、あるいは期待される回数と異なったりする可能性がありました。

また、ベンチマーク結果を解析する既存のツールは、特定の形式で出力されるベンチマーク名を期待していました。サブベンチマークの検出ロジックの変更に伴い、ベンチマーク名の出力タイミングや条件を調整し、これらのツールとの互換性を維持する必要がありました。このコミットは、これらの問題を解決し、ベンチマークの実行ロジックをより堅牢で予測可能なものにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語のベンチマークに関する前提知識が必要です。

1.  **`go test -bench`**: Go言語でベンチマークを実行するためのコマンドです。`go test -bench=.`のように実行すると、プロジェクト内のすべてのベンチマーク関数が実行されます。
2.  **`testing`パッケージ**: Goの標準ライブラリで、テストとベンチマーク機能を提供します。
3.  **`*testing.B`**: ベンチマーク関数に渡される構造体で、ベンチマークの制御（例: `b.N`、`b.ResetTimer()`、`b.Run()`) を行います。
4.  **`b.N`**: ベンチマーク関数が実行されるイテレーション回数を示します。`testing`パッケージは、指定された`benchTime`（デフォルト1秒）内にベンチマークが完了するように、`b.N`の値を動的に調整します。
5.  **`b.benchFunc(b *B)`**: ユーザーが記述する実際のベンチマークロジックを含む関数です。
6.  **サブベンチマーク (`b.Run`)**: `b.Run("sub-benchmark-name", func(b *B){ ... })`のように使用することで、一つのベンチマーク関数内で複数のサブベンチマークを定義できます。これにより、関連する複数のシナリオを一つのベンチマークグループとしてテストできます。
7.  **リーフベンチマーク**: サブベンチマークを持たない、またはサブベンチマークの階層構造の最下層にあるベンチマークを指します。ベンチマーク結果の出力は通常、これらのリーフベンチマークに対して行われます。
8.  **`runtime.GOMAXPROCS`**: Goプログラムが使用できるOSスレッドの最大数を設定します。ベンチマークは通常、異なる`GOMAXPROCS`値で複数回実行され、並行処理性能を評価します。

## 技術的詳細

このコミットの技術的詳細は、主に`src/testing/benchmark.go`内の`*B`構造体のメソッドの変更に集約されます。

### `probe()` から `run1()` への変更

*   **旧実装 (`probe()`):** 以前は`probe()`というメソッドが存在し、その目的は「ベンチマーク関数がサブベンチマークを持っているかどうかを調べる」ことでした。このメソッドは`b.N = 0`を設定し、`b.benchFunc(b)`を呼び出していました。`b.N = 0`であるにもかかわらず`b.benchFunc`が呼び出されるのは、`b.Run`が呼び出されることで`b.hasSub`フラグが設定されることを期待していたためです。しかし、`b.N=0`での実行は、`benchFunc`が実際に何らかの処理を行うことを保証せず、また`benchFunc`が`b.N`に依存するロジックを含んでいた場合に予期せぬ挙動を引き起こす可能性がありました。
*   **新実装 (`run1()`):** `probe()`は`run1()`に改名され、そのロジックが大幅に変更されました。
    *   `b.N = 0`の代わりに、`b.runN(1)`が呼び出されるようになりました。これは、ベンチマーク関数を明示的に1回だけ実行することを意味します。
    *   `run1()`は`bool`値を返すようになり、`!b.hasSub`（サブベンチマークがない場合）を返します。これにより、呼び出し元はベンチマークがサブベンチマークを持つかどうかを簡単に判断し、後続の処理を決定できます。
    *   この変更により、`benchFunc`は常に少なくとも1回は`N=1`で実行されることが保証されます。これにより、サブベンチマークの検出がより確実になり、`benchFunc`が`N`に依存する初期化ロジックを含んでいても安全に実行できるようになります。

### `launch()` メソッドの変更

*   **旧実装:** `launch()`メソッドは、ベンチマークのイテレーション回数を徐々に増やして`benchTime`を満たすように調整する役割を担っていました。以前は、最初に`n = 1`として`b.runN(n)`を呼び出し、その後ループ内で`n`を増やしていました。
*   **新実装:** `run1()`が導入されたことで、`launch()`の初期`b.runN(n)`の呼び出しが削除されました。代わりに、`launch()`のコメントに「`run1`が`b`に対して呼び出されている必要がある」と明記されています。これは、`run1()`が既に最初の1回のイテレーションを実行しているため、`launch()`内で再度`N=1`で実行する必要がなくなったことを意味します。ループの初期化も`for n := 1; ...`に変更され、`n`の初期値が1から始まるようになりました。

### `processBench()` メソッドの変更

*   `processBench()`は、異なる`GOMAXPROCS`設定でベンチマークを実行し、結果を出力する役割を担っています。
*   このコミットでは、`cpuList`の最初の要素（`i == 0`）以外の`GOMAXPROCS`設定でベンチマークを実行する際に、新しい`*B`インスタンスを作成し、そのインスタンスに対して`b.run1()`が明示的に呼び出されるようになりました。
*   これは、`GOMAXPROCS`が変わるたびにベンチマークのコンテキストがリセットされるため、新しいコンテキストでサブベンチマークの検出（`hasSub`フラグの設定）を再度行う必要があるためです。

### `Run()` メソッドの変更

*   `b.Run()`はサブベンチマークを定義するために使用されます。
*   **旧実装:** `sub.probe()`を呼び出し、`!sub.hasSub`であれば`sub.run()`を実行していました。
*   **新実装:** `sub.run1()`を呼び出し、その戻り値が`true`（サブベンチマークがない場合）であれば`sub.run()`を実行するように変更されました。
*   この変更は、`probe()`が`run1()`に置き換えられたことに伴う直接的な修正です。`run1()`が`N=1`で実行されるため、`b.Run`が呼び出されたベンチマーク自体は測定されず、`N=1`で一度だけ呼び出されるというコメントも追加されています。

### `src/testing/sub_test.go` の変更

*   `TestBRun`関数内で、`root.run()`の呼び出しが`root.runN(1)`に変更されました。これは、テストケース内でベンチマークの初期実行をシミュレートする際に、`N=1`での実行がより適切であることを示しています。

これらの変更は、Goのベンチマークシステムにおけるサブベンチマークの検出と実行のロジックをより一貫性のあるものにし、`benchFunc`の呼び出し回数を予測可能にすることで、ベンチマークの信頼性と既存ツールとの互換性を向上させています。

## コアとなるコードの解説

### `src/testing/benchmark.go`

1.  **`func (b *B) run1() bool`**:
    *   この関数は、以前の`probe()`関数を置き換えるものです。
    *   目的は、ベンチマーク関数`b.benchFunc`を1回だけ実行し、そのベンチマークがサブベンチマークを持つかどうかを検出することです。
    *   `b.runN(1)`を呼び出すことで、`b.benchFunc`が`N=1`で実行されます。これにより、`b.Run`が呼び出された場合に`b.hasSub`フラグが正しく設定されることが保証されます。
    *   `return !b.hasSub`は、このベンチマークがサブベンチマークを持たない場合に`true`を返します。これは、呼び出し元がこのベンチマークを通常のベンチマークとして実行すべきかどうかを判断するために使用されます。

2.  **`func (b *B) launch()`**:
    *   この関数は、ベンチマークのイテレーション回数`n`を`benchTime`に基づいて動的に調整するメインのループを含んでいます。
    *   変更点として、初期の`n = 1`での`b.runN(n)`の呼び出しが削除されました。これは、`launch()`が呼び出される前に`b.run1()`が既に実行されていることを前提としているためです。
    *   ループの初期化が`for n := 1; ...`に変更され、`n`が1から始まるようになりました。

3.  **`func (ctx *benchContext) processBench(b *B)`**:
    *   この関数は、異なる`GOMAXPROCS`設定でベンチマークを実行するロジックを含んでいます。
    *   `for i, procs := range cpuList`ループ内で、`i > 0`の場合（つまり、最初の`GOMAXPROCS`設定以外の場合）に新しい`*B`インスタンスを作成し、そのインスタンスに対して`b.run1()`を呼び出すようになりました。
    *   これは、`GOMAXPROCS`設定が変わるたびにベンチマークのコンテキストがリセットされるため、新しいコンテキストでサブベンチマークの検出を再度行う必要があるためです。

4.  **`func (b *B) Run(name string, f func(b *B)) bool`**:
    *   サブベンチマークを定義するためのメソッドです。
    *   `sub.probe()`の呼び出しが`sub.run1()`に置き換えられました。
    *   `if sub.run1() { sub.run() }`という条件分岐により、サブベンチマークを持たない（`run1()`が`true`を返す）場合にのみ、そのサブベンチマークが通常のベンチマークとして実行されます。
    *   コメントが更新され、「`b.Run`が少なくとも一度呼び出されたベンチマークはそれ自体は測定されず、`N=1`で一度だけ呼び出される」という説明が追加されました。これは、親ベンチマークがサブベンチマークのコンテナとして機能し、実際の測定はサブベンチマークで行われるという意図を明確にしています。

### `src/testing/sub_test.go`

1.  **`func TestBRun(t *T)`**:
    *   このテスト関数内で、`root.run()`の呼び出しが`root.runN(1)`に変更されました。これは、`b.Run`の挙動をテストする際に、ベンチマークの初期実行を`N=1`でシミュレートすることが、新しい`run1()`のロジックと整合性が取れるためです。

これらの変更は、Goのベンチマークシステムにおけるサブベンチマークの検出と実行のロジックをより一貫性のあるものにし、`benchFunc`の呼び出し回数を予測可能にすることで、ベンチマークの信頼性と既存ツールとの互換性を向上させています。

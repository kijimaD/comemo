## 変更の背景

この変更の背景には、Go言語の静的解析ツールである`go vet`の機能改善があります。Goのアセンブリコードでは、スタック上の変数や引数にアクセスするために、スタックポインタ（SP）からのオフセットを使用する`nn(SP)`形式と、フレームポインタ（FP）からのオフセットを使用する`name+(NN)FP`形式の2種類のアドレス指定方法が存在します。

以前は、`nn(SP)`形式が広く使われていましたが、この形式はスタックフレームのサイズ変更や、関数呼び出し規約の変更があった場合に、オフセット値がずれてしまい、バグの原因となる可能性がありました。特に、`go vet`のような静的解析ツールが、アセンブリコード内のスタックアクセスが正しいかどうかを検証する際に、`nn(SP)`形式では正確な解析が困難でした。

この問題を解決するため、Goチームはアセンブリコードにおけるスタックアクセスを`name+(NN)FP`形式に統一する方針を打ち出しました。`name+(NN)FP`形式は、関数内の特定の変数や引数に名前を付けてアクセスするため、スタックフレームのレイアウト変更に対してより堅牢であり、`go vet`がより正確な静的解析を行えるようになります。

このコミットは、その方針に基づき、`src/syscall/asm_linux_386.s`ファイル内のLinux/386アーキテクチャ向けシステムコールのアセンブリコードを、`go vet`によって生成された推奨形式に修正したものです。

## 前提知識の解説

### Goアセンブリ言語

Go言語は、パフォーマンスが重要な部分や、OSとの低レベルなインタラクションが必要な場合に、Goアセンブリ言語（Plan 9アセンブリの派生）を使用します。Goアセンブリは、一般的なx86アセンブリとは異なる独自の構文を持っています。

*   **TEXTディレクティブ**: 関数の定義を開始します。例: `TEXT ·Syscall(SB),NOSPLIT,$0-28`
    *   `·Syscall(SB)`: 関数名。`·`はパッケージローカルなシンボルを示し、`SB`は静的ベースポインタ（Static Base pointer）を示します。
    *   `NOSPLIT`: スタックの拡張チェックを行わないことを示します。システムコールのような低レベルな関数で使われることが多いです。
    *   `$0-28`: スタックフレームのサイズと引数のサイズを示します。`$0`はローカル変数のためのスタック領域が0バイトであることを意味し、`-28`は引数が28バイトであることを意味します。
*   **レジスタ**:
    *   `AX`, `BX`, `CX`, `DX`, `SI`, `DI`, `BP`: x86アーキテクチャの汎用レジスタ。
    *   `SP` (Stack Pointer): 現在のスタックトップを指すレジスタ。
    *   `FP` (Frame Pointer): 現在のスタックフレームのベースを指すレジスタ。Goアセンブリでは、関数の引数やローカル変数へのアクセスにFPが使われることがあります。
*   **アドレス指定モード**:
    *   `nn(SP)`: スタックポインタ`SP`からのオフセット`nn`でメモリにアクセスします。これは、スタック上の相対位置を指定します。
    *   `name+(NN)FP`: フレームポインタ`FP`からのオフセット`NN`で、`name`というシンボルに関連付けられたメモリにアクセスします。これは、関数内の特定の引数やローカル変数に名前でアクセスする、よりセマンティックな方法です。

### `go vet`

`go vet`は、Go言語のソースコードを静的に解析し、潜在的なバグや疑わしい構造を報告するツールです。コンパイルエラーにはならないが、実行時に問題を引き起こす可能性のあるコードパターンを検出します。例えば、フォーマット文字列の不一致、到達不能なコード、ロックの誤用などを検出できます。

このコミットの文脈では、`go vet`はGoアセンブリコード内のスタックアクセスが正しいかどうかを検証する機能を持っており、`name+(NN)FP`形式を使用することでその検証精度が向上します。

### システムコール (Syscall)

システムコールは、ユーザー空間のプログラムがオペレーティングシステム（OS）のカーネル空間の機能にアクセスするためのインターフェースです。ファイルI/O、ネットワーク通信、プロセス管理など、OSが提供する多くの機能はシステムコールを通じて利用されます。Go言語の`syscall`パッケージは、これらのシステムコールをGoプログラムから呼び出すための低レベルなインターフェースを提供します。

Linux/386アーキテクチャでは、システムコールは通常、特定のレジスタにシステムコール番号と引数を設定し、`int $0x80`命令（または`sysenter`/`syscall`命令）を実行することで行われます。

## 技術的詳細

このコミットの主要な変更点は、`src/syscall/asm_linux_386.s`ファイル内のアセンブリコードにおいて、スタック上の引数や戻り値へのアクセス方法を`nn(SP)`形式から`name+(NN)FP`形式へ変更したことです。

具体的には、以下のような変更が行われています。

*   **`Syscall`関数**:
    *   `4(SP)`が`trap+0(FP)`に
    *   `8(SP)`が`a1+4(FP)`に
    *   `12(SP)`が`a2+8(FP)`に
    *   `16(SP)`が`a3+12(FP)`に
    *   `20(SP)`が`r1+16(FP)`に
    *   `24(SP)`が`r2+20(FP)`に
    *   `28(SP)`が`err+24(FP)`に
*   **`Syscall6`関数**: 同様に、引数`a1`から`a6`、戻り値`r1`, `r2`, `err`へのアクセスが`name+(NN)FP`形式に変更されています。
*   **`RawSyscall`および`RawSyscall6`関数**: `Syscall`および`Syscall6`と同様の変更が適用されています。
*   **`socketcall`および`rawsocketcall`関数**: `call`引数、`a0`引数、戻り値`n`, `err`へのアクセスが変更されています。
*   **`seek`関数**: `fd`, `offset_lo`, `offset_hi`, `whence`引数、戻り値`newoffset_lo`, `newoffset_hi`, `err`へのアクセスが変更されています。

この変更は、Goアセンブリのコーディング規約の統一と、`go vet`による静的解析の精度向上に貢献します。`name+(NN)FP`形式を使用することで、アセンブリコードの可読性が向上し、将来的なスタックレイアウトの変更に対する堅牢性が高まります。また、`go vet`がスタックフレームの構造をより正確に理解できるようになるため、アセンブリコード内の潜在的なバグを早期に発見できるようになります。

この変更は、Goのツールチェインがアセンブリコードの品質を向上させるために、静的解析の力を活用している良い例と言えます。

## コアとなるコードの変更箇所

このコミットで変更されたコアとなるコードは、`src/syscall/asm_linux_386.s`ファイルです。このファイルは、Linux/386アーキテクチャにおけるGoのシステムコール実装のアセンブリコードを含んでいます。

具体的な変更は、スタック上の変数や引数へのアクセスに使用されるアドレス指定モードの変更です。

**変更前 (例: `Syscall`関数の一部)**:

	MOVL	8(SP), BX
	MOVL	12(SP), CX
	MOVL	16(SP), DX
...
	MOVL	$-1, 20(SP)	// r1
	MOVL	$0, 24(SP)	// r2
...
	MOVL	AX, 20(SP)	// r1
	MOVL	DX, 24(SP)	// r2
	MOVL	$0, 28(SP)	// errno
```

**変更後 (例: `Syscall`関数の一部)**:

```assembly

	MOVL	a1+4(FP), BX
	MOVL	a2+8(FP), CX
	MOVL	a3+12(FP), DX

同様の変更が、`Syscall6`, `RawSyscall`, `RawSyscall6`, `socketcall`, `rawsocketcall`, `seek`といった他のシステムコール関連のアセンブリ関数にも適用されています。

## コアとなるコードの解説

この変更は、Goアセンブリコードの保守性と静的解析の精度を向上させるための重要なステップです。

*   **`nn(SP)`から`name+(NN)FP`への移行**:
    *   `nn(SP)`は、スタックポインタ`SP`からのバイトオフセットでメモリ位置を指定します。これは非常に低レベルな指定方法であり、関数の引数やローカル変数のレイアウトが変更されると、オフセット値が容易にずれてしまいます。これにより、アセンブリコードの変更が難しくなり、バグが混入するリスクが高まります。
    *   `name+(NN)FP`は、フレームポインタ`FP`を基準とし、特定の引数やローカル変数に割り当てられた名前（例: `trap`, `a1`, `r1`, `err`など）と、その名前に関連付けられたオフセット`NN`を使用します。この形式は、スタックフレームのレイアウト変更に対してより堅牢です。例えば、新しいローカル変数が追加されても、既存の引数や戻り値の`name+(NN)FP`形式のアドレス指定は影響を受けにくいです。
*   **`go vet`との連携**:
    *   `go vet`は、Goアセンブリコードの静的解析を行う際に、スタックフレームの構造を理解する必要があります。`nn(SP)`形式では、`go vet`がスタック上のどの位置がどの変数に対応しているかを正確に判断するのが困難でした。
    *   `name+(NN)FP`形式に統一することで、`go vet`はアセンブリコード内のスタックアクセスが、Goの関数シグネチャと一致しているかをより正確に検証できるようになります。これにより、アセンブリコードとGoコード間の不整合による潜在的なバグ（例: 引数の渡し間違い、戻り値の読み取り間違い）を早期に検出できるようになります。
*   **可読性と保守性**:
    *   `name+(NN)FP`形式は、`nn(SP)`形式よりもコードの意図が明確になります。例えば、`trap+0(FP)`は「`trap`という引数にアクセスしている」ということが一目でわかりますが、`4(SP)`だけではその意味を理解するために文脈を深く読み解く必要があります。
    *   これにより、アセンブリコードの可読性が向上し、将来的なメンテナンスやデバッグが容易になります。

この変更は、Go言語のランタイムとツールチェインが、低レベルなアセンブリコードの品質と信頼性を高めるために継続的に改善されていることを示しています。

この変更は、Goアセンブリのコーディング規約の統一と、`go vet`による静的解析の精度向上に貢献します。`name+(NN)FP`形式を使用することで、アセンブリコードの可読性が向上し、将来的なスタックレイアウトの変更に対する堅牢性が高まります。また、`go vet`がスタックフレームの構造をより正確に理解できるようになるため、アセンブリコード内の潜在的なバグを早期に発見できるようになります。

この変更は、Goのツールチェインがアセンブリコードの品質を向上させるために、静的解析の力を活用している良い例と言えます。

## コアとなるコードの変更箇所

このコミットで変更されたコアとなるコードは、`src/syscall/asm_linux_386.s`ファイルです。このファイルは、Linux/386アーキテクチャにおけるGoのシステムコール実装のアセンブリコードを含んでいます。

具体的な変更は、スタック上の変数や引数へのアクセスに使用されるアドレス指定モードの変更です。

**変更前 (例: `Syscall`関数の一部)**:

```assembly
	MOVL	4(SP), AX	// syscall entry
	MOVL	8(SP), BX
	MOVL	12(SP), CX
	MOVL	16(SP), DX
...
	MOVL	$-1, 20(SP)	// r1
	MOVL	$0, 24(SP)	// r2
...
	MOVL	AX, 20(SP)	// r1
	MOVL	DX, 24(SP)	// r2
	MOVL	$0, 28(SP)	// errno
```

**変更後 (例: `Syscall`関数の一部)**:

```assembly
	MOVL	trap+0(FP), AX	// syscall entry
	MOVL	a1+4(FP), BX
	MOVL	a2+8(FP), CX
	MOVL	a3+12(FP), DX
...
	MOVL	$-1, r1+16(FP)
	MOVL	$0, r2+20(FP)
...
	MOVL	AX, r1+16(FP)
	MOVL	DX, r2+20(FP)
	MOVL	$0, err+24(FP)
```

同様の変更が、`Syscall6`, `RawSyscall`, `RawSyscall6`, `socketcall`, `rawsocketcall`, `seek`といった他のシステムコール関連のアセンブリ関数にも適用されています。

また、ファイルの先頭にあった以下のコメントが削除されています。これは、このコミットによって`TODO`が完了したことを示唆しています。

```assembly

// so that go vet can check that they are correct.
```

## コアとなるコードの解説

この変更は、Goアセンブリコードの保守性と静的解析の精度を向上させるための重要なステップです。

*   **`nn(SP)`から`name+(NN)FP`への移行**:
    *   `nn(SP)`は、スタックポインタ`SP`からのバイトオフセットでメモリ位置を指定します。これは非常に低レベルな指定方法であり、関数の引数やローカル変数のレイアウトが変更されると、オフセット値が容易にずれてしまいます。これにより、アセンブリコードの変更が難しくなり、バグが混入するリスクが高まります。
    *   `name+(NN)FP`は、フレームポインタ`FP`を基準とし、特定の引数やローカル変数に割り当てられた名前（例: `trap`, `a1`, `r1`, `err`など）と、その名前に関連付けられたオフセット`NN`を使用します。この形式は、スタックフレームのレイアウト変更に対してより堅牢です。例えば、新しいローカル変数が追加されても、既存の引数や戻り値の`name+(NN)FP`形式のアドレス指定は影響を受けにくいです。
*   **`go vet`との連携**:
    *   `go vet`は、Goアセンブリコードの静的解析を行う際に、スタックフレームの構造を理解する必要があります。`nn(SP)`形式では、`go vet`がスタック上のどの位置がどの変数に対応しているかを正確に判断するのが困難でした。
    *   `name+(NN)FP`形式に統一することで、`go vet`はアセンブリコード内のスタックアクセスが、Goの関数シグネチャと一致しているかをより正確に検証できるようになります。これにより、アセンブリコードとGoコード間の不整合による潜在的なバグ（例: 引数の渡し間違い、戻り値の読み取り間違い）を早期に検出できるようになります。
*   **可読性と保守性**:
    *   `name+(NN)FP`形式は、`nn(SP)`形式よりもコードの意図が明確になります。例えば、`trap+0(FP)`は「`trap`という引数にアクセスしている」ということが一目でわかりますが、`4(SP)`だけではその意味を理解するために文脈を深く読み解く必要があります。
    *   これにより、アセンブリコードの可読性が向上し、将来的なメンテナンスやデバッグが容易になります。

この変更は、Go言語のランタイムとツールチェインが、低レベルなアセンブリコードの品質と信頼性を高めるために継続的に改善されていることを示しています。

# [インデックス 24150] ファイルの概要

このコミットは、Goランタイムにおける非x86アーキテクチャ（ARM、ARM64、PPC64）でのシグナルハンドリング時のスタックトレースの品質を改善することを目的としています。特に、無効なプログラムカウンタ（PC）へのジャンプが発生した場合に、より有用なトレースバック情報を提供するための修正が含まれています。

## 変更の背景

このコミットは、Goプログラムがシグナルを受け取った際に、特に無効なプログラムカウンタ（PC）アドレスにジャンプした場合に発生する、不完全または誤解を招くスタックトレースの問題に対処しています。これはGitHub Issue #11656「runtime: jump to bad PC missing good traceback」で報告された問題の再修正（"again"）です。

Goランタイムは、プログラムがクラッシュしたり、予期せぬシグナルを受け取ったりした際に、デバッグのためにスタックトレースを生成します。このスタックトレースは、問題発生時のプログラムの実行パスを理解するために不可欠です。しかし、特定の状況下、特にGoコードではない領域（例えば、無効なメモリ領域やCコードなど）へのジャンプが発生した場合、Goランタイムは正確なPCを特定できず、結果としてスタックトレースが途切れたり、意味のない情報になったりすることがありました。

この問題は、特に非x86アーキテクチャ（ARM、ARM64、PPC64など）で顕著でした。これらのアーキテクチャでは、関数呼び出しの際にリターンアドレスを保持するリンクレジスタ（LR）の役割がx86とは異なるため、PCが不正な場合にLRがより信頼性の高い情報源となることがあります。

このコミットは、シグナルハンドラ内でPCがGoコードを指していないが、LRがGoコードを指している場合に、PCを意図的にゼロに設定することで、スタックトレースの生成メカニズムがLRの情報を優先するように誘導し、より有用なコンテキストを提供することを目指しています。

## 前提知識の解説

### Goランタイムとシグナルハンドリング

Goプログラムは、オペレーティングシステムからシグナル（例: `SIGSEGV` (セグメンテーション違反)、`SIGILL` (不正命令)）を受け取ることがあります。Goランタイムはこれらのシグナルを捕捉し、`sighandler` と呼ばれる内部関数で処理します。シグナルハンドラは、シグナル発生時のCPUの状態（レジスタの値など）を保存し、デバッグ情報（スタックトレースなど）を生成する役割を担います。

### プログラムカウンタ (PC) とリンクレジスタ (LR)

*   **プログラムカウンタ (PC)**: 現在実行中の命令のアドレスを指すCPUレジスタです。シグナル発生時には、PCはシグナルを引き起こした命令のアドレスを示します。
*   **リンクレジスタ (LR)**: 関数呼び出しの際に、呼び出し元に戻るためのアドレス（リターンアドレス）を保持するCPUレジスタです。特にARMやARM64などのRISCアーキテクチャで重要な役割を果たします。x86アーキテクチャでは、リターンアドレスは通常スタックにプッシュされますが、ARM系ではLRが使用されます。

スタックトレースを生成する際には、PCとLRの両方が、プログラムの実行フローを再構築するための重要な情報源となります。

### スタックアンワインドとトレースバック

スタックアンワインドとは、プログラムの実行スタックを逆方向にたどり、関数呼び出しの履歴を再構築するプロセスです。このプロセスによって、プログラムがクラッシュした時点までの関数呼び出しの連鎖（スタックトレースバック）が生成されます。正確なスタックトレースは、デバッグにおいて問題の根本原因を特定するために不可欠です。

### `findfunc` 関数

Goランタイムには、特定のアドレスがGoの関数コード内にあるかどうかを判断するための内部関数 `findfunc` が存在します。この関数は、Goの実行可能ファイルに含まれる関数情報（シンボルテーブルなど）を参照して、与えられたアドレスが有効なGoコードの範囲内にあるかをチェックします。`findfunc(addr) == nil` は、`addr` がGoコードではないことを意味します。

## 技術的詳細

このコミットの技術的詳細な変更は、`src/runtime/signal_arm.go`、`src/runtime/signal_arm64.go`、`src/runtime/signal_ppc64x.go` の `sighandler` 関数内に導入された新しいロジックにあります。

`sighandler` 関数は、シグナルが発生した際に呼び出され、CPUのコンテキスト（レジスタの状態など）を `c` (mcontext_t) オブジェクトから取得し、現在のgoroutine (`gp`) の情報と組み合わせて処理を行います。

変更前のコードでは、`gp.sigpc`（シグナル発生時のプログラムカウンタ）がゼロでない場合に、その値をリンクレジスタに設定していました。これは、スタックトレースを生成する際に、シグナル発生時のPCを優先的に使用しようとする意図がありました。

しかし、`gp.sigpc` が無効なアドレス（Goコードではない領域）を指している場合、このアプローチは問題を引き起こしました。`findfunc(gp.sigpc)` が `nil` を返すような状況では、そのPCはスタックトレースにおいて意味のある情報を提供できません。一方で、リンクレジスタ (`c.lr()` または `c.link()`) は、直前の有効な関数呼び出しのリターンアドレスを保持しているため、より有用なコンテキストを提供できる可能性があります。

新しいロジックは以下の条件をチェックします。

```go
		pc := uintptr(gp.sigpc)

		// If we don't recognize the PC as code
		// but we do recognize the link register as code,
		// then assume this was a call to non-code and treat like
		// pc == 0, to make unwinding show the context.
		if pc != 0 && findfunc(pc) == nil && findfunc(uintptr(c.lr())) != nil {
			pc = 0
		}
```

このコードブロックは、以下の3つの条件がすべて真である場合に `pc` を `0` に設定します。

1.  `pc != 0`: シグナル発生時のPCがゼロではない。
2.  `findfunc(pc) == nil`: シグナル発生時のPCがGoコードの範囲外を指している。
3.  `findfunc(uintptr(c.lr())) != nil`: リンクレジスタがGoコードの範囲内を指している。

この条件が満たされるということは、プログラムがGoコードではない領域でシグナルを受け取ったが、その直前の呼び出し元はGoコードであった可能性が高いことを意味します。例えば、Goの関数が `nil` ポインタを介して関数を呼び出そうとした結果、不正なアドレスにジャンプしてシグナルが発生した場合などがこれに該当します。

`pc` を `0` に設定することで、その後のスタックトレース生成ロジックは、`pc` がゼロであると判断し、代わりにリンクレジスタ (`c.lr()` または `c.link()`) の値を優先的に使用するようになります。これにより、無効なPCによって途切れることなく、直前の有効なGo関数呼び出しのコンテキストがスタックトレースに表示され、デバッグの助けとなります。

この修正が非x86アーキテクチャに特化しているのは、これらのアーキテクチャにおけるLRの役割と、Goランタイムがシグナルハンドリング時にレジスタの状態をどのように解釈するかの違いに起因します。x86では、リターンアドレスはスタックに保存されるため、この問題の発生メカニズムが異なります。

## コアとなるコードの解説

1.  **`pc := uintptr(gp.sigpc)`**: まず、シグナル発生時のプログラムカウンタ `gp.sigpc` を `pc` というローカル変数にコピーします。これにより、元の `gp.sigpc` の値を直接変更することなく、条件付きで `pc` の値を調整できるようになります。

2.  **新しい条件分岐**:
    ```go
    if pc != 0 && findfunc(pc) == nil && findfunc(uintptr(c.lr())) != nil {
        pc = 0
    }
    ```
    この `if` 文がこのコミットの核心です。
    *   `pc != 0`: シグナル発生時のPCが有効なアドレス（ゼロ以外）であることを確認します。ゼロPCは通常、特別な意味を持つか、既に処理されている可能性があります。
    *   `findfunc(pc) == nil`: `pc` がGoランタイムによって認識される有効なGoコードのアドレスではないことをチェックします。これは、PCが不正なメモリ領域や、Goランタイムが管理していない外部コードを指している可能性を示唆します。
    *   `findfunc(uintptr(c.lr())) != nil`: リンクレジスタ (`c.lr()` for ARM/ARM64, `c.link()` for PPC64) が指すアドレスが、有効なGoコード内であることをチェックします。これは、シグナルが発生した直前の呼び出し元がGoコードであったことを意味します。

    これら3つの条件がすべて満たされた場合、`pc = 0` が実行されます。これは、現在のPCが無効であるため、スタックトレースの生成においてこのPCを無視し、代わりにリンクレジスタが提供するより信頼性の高いリターンアドレス情報を使用するように、後続のロジックにヒントを与えるためのものです。

3.  **リンクレジスタの設定ロジックの変更**:
    ```go
    // Don't bother saving PC if it's zero, which is
    // probably a call to a nil func: the old link register
    // is more useful in the stack trace.
    -		if gp.sigpc != 0 {
    -			c.set_lr(uint32(gp.sigpc))
    +		if pc != 0 {
    +			c.set_lr(uint32(pc))
    		}
    ```
    この部分では、リンクレジスタに設定する値のソースが `gp.sigpc` から、上記の新しいロジックで調整された `pc` 変数に変更されています。
    もし新しいロジックによって `pc` が `0` に設定された場合、この `if pc != 0` の条件は偽となり、`c.set_lr` は呼び出されません。これにより、`c.lr()`（または `c.link()`）に元々保存されていた、より有用なリターンアドレスがそのまま保持され、スタックトレースに反映されるようになります。

この一連の変更により、非x86アーキテクチャにおいて、不正なPCへのジャンプによって発生する不完全なスタックトレースの問題が緩和され、デバッグ時の情報がより豊富で正確になります。

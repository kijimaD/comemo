## 変更の背景

このコミットの背景には、Goコンパイラ（特に当時の`6g`コンパイラ）が生成するコードにおいて、特定の操作やコンパイラが内部的に生成する要素に行番号情報が適切に付与されていないという問題があったと考えられます。

ソースコードの行番号情報は、プログラミング言語のコンパイラにとって極めて重要です。
1.  **エラー報告**: コンパイルエラーや実行時エラーが発生した際に、どのソースコードの行で問題が起きたかを正確にユーザーに伝えるために必要です。行番号が欠落していると、エラーメッセージが不正確になり、デバッグが困難になります。
2.  **デバッグ**: デバッガがソースコードレベルでステップ実行したり、ブレークポイントを設定したりするためには、機械語命令とソースコードの行番号とのマッピングが必要です。行番号情報が不完全だと、デバッグ体験が著しく損なわれます。
3.  **プロファイリング**: 実行時のパフォーマンスプロファイリングにおいて、どのソースコードの行がボトルネックになっているかを特定するためにも行番号情報が利用されます。

このコミットメッセージ「more line numbers」は、以前は行番号が不足していた箇所に、より多くの行番号情報を追加したことを示唆しています。特に、コンパイラが内部的に生成する一時変数、レジスタ操作、スタック操作、リテラル値など、直接ソースコードに記述されないがコード生成過程で不可欠な要素に対して、適切な行番号を関連付けることが目的だったと推測されます。これにより、コンパイラが生成するバイナリのデバッグ情報がより正確になり、開発者がGoプログラムをデバッグする際の利便性が向上します。

## 前提知識の解説

### Goコンパイラ (6g)

Go言語の初期のコンパイラは、ターゲットアーキテクチャごとに異なる名前を持っていました。`6g`は、x86-64 (AMD64) アーキテクチャ向けのGoコンパイラを指します。当時のGoコンパイラは、C言語で書かれており、`gc` (Go Compiler) と総称されるコンパイラ群の一部でした。

コンパイラの一般的な処理フローは以下のようになります。
1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（予約語、識別子、演算子など）の列に変換します。
2.  **構文解析 (Syntax Analysis)**: トークンの列を解析し、プログラムの構造を抽象構文木 (AST) として構築します。
3.  **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、名前解決、スコープチェックなどの意味的な正当性を検証します。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTから、機械語に依存しない中間表現 (IR) を生成します。
5.  **コード最適化 (Code Optimization)**: 中間コードを最適化し、実行効率を向上させます。
6.  **コード生成 (Code Generation)**: 最適化された中間コードから、ターゲットアーキテクチャの機械語（アセンブリコード）を生成します。

このコミットで変更されている`gen.c`や`gsubr.c`は、主に中間コード生成からコード生成の段階に関わるファイルです。

### `lineno` (行番号)

`lineno`は、コンパイラが現在処理しているソースコードの行番号を追跡するための変数またはフィールドです。コンパイラの内部データ構造（ASTノード、中間表現、アセンブリ命令など）にこの`lineno`を付与することで、生成されるバイナリのデバッグ情報にソースコードの行番号を含めることができます。これにより、デバッガが機械語命令とソースコードの対応付けを行うことが可能になります。

### `Node`構造体

Goコンパイラ内部では、ソースコードの様々な要素（変数、定数、式、関数呼び出し、型など）を表現するために`Node`という汎用的なデータ構造が使われます。`Node`構造体は、ASTの各ノードや、中間表現の要素を表すために利用されます。この`Node`構造体には、通常、そのノードがソースコードのどの位置（ファイル名、行番号、列番号）に対応するかを示すフィールドが含まれています。このコミットでは、特定の種類の`Node`が生成される際に、`lineno`フィールドが適切に設定されるように修正されています。

### `Prog`構造体

`Prog`構造体は、Goコンパイラが生成するアセンブリ命令を表現するためのデータ構造です。各`Prog`インスタンスは、特定のアセンブリ命令（例: `MOV`, `ADD`, `CALL`）とそのオペランド、そして関連するメタデータ（例: 行番号）を保持します。`Prog`構造体に行番号情報を含めることで、生成されたアセンブリコードの各命令が、元のソースコードのどの行に対応するかをデバッガが知ることができます。

### `D_SP` (Stack Pointer)

`D_SP`は、スタックポインタレジスタ（x86-64アーキテクチャでは通常`RSP`）を抽象的に表す定数です。スタックポインタは、プログラムの実行スタックの現在のトップを指し示します。関数呼び出し時の引数のプッシュ、戻りアドレスの保存、ローカル変数の確保などに利用されます。コンパイラは、関数呼び出しやローカル変数へのアクセスに関連するコードを生成する際に、スタックポインタを基準としたメモリアドレス指定を行います。

### `Node`の`op`フィールドで使われる定数

`Node`構造体には、そのノードがどのような種類の操作や要素を表すかを示す`op`フィールドがあります。このコミットの差分に登場する主な定数は以下の通りです。

*   **`OINDREG`**: レジスタによる間接参照（例: `*RSP` のように、レジスタが指すメモリ位置へのアクセス）を表します。スタック上の変数や引数へのアクセスによく使われます。
*   **`OREGISTER`**: レジスタ自体（例: `RAX`, `RBX`）を表します。
*   **`OLITERAL`**: リテラル値（定数、例: `10`, `"hello"`）を表します。
*   **`PAUTO`**: 自動変数（ローカル変数）を表します。

これらの定数が行番号と関連付けられることで、コンパイラが生成するスタック操作、レジスタ操作、定数ロード、ローカル変数アクセスといった低レベルな命令が、元のソースコードのどの行に由来するのかを正確に追跡できるようになります。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラのコード生成フェーズにおいて、これまで行番号情報が欠落していたり、不正確であったりした内部的な`Node`構造体や`Prog`構造体に対して、現在のソースコード行番号（`lineno`変数で保持されている）を明示的に設定するように修正した点にあります。

具体的には、以下の種類のコード生成処理において`lineno`が追加されています。

1.  **スタックポインタ (`D_SP`) を利用した間接参照ノードの生成**:
    *   `cgen_callret` 関数内: 関数呼び出しの戻り値を処理する際に、スタックポインタを基準としたメモリアクセスノード (`nod`) が生成されます。このノードに`nod.lineno = lineno;`が追加されました。
    *   `cgen_aret` 関数内: 関数呼び出しの引数を処理する際に、同様にスタックポインタを基準としたメモリアクセスノード (`nod1`) が生成されます。このノードにも`nod1.lineno = lineno;`が追加されました。
    これらの変更により、関数呼び出しに関連するスタック操作が、ソースコードのどの行で行われたかを正確にデバッグ情報に反映できるようになります。

2.  **アセンブリ命令 (`Prog`) の生成**:
    *   `prog` 関数内: アセンブリ命令 (`Prog`) を生成する際に、`p->lineno = lineno;`が設定されます。これにより、個々のアセンブリ命令がソースコードのどの行に対応するかが明確になります。
    *   さらに、`if(lineno == 0) warn("line 0 %P\\n", p);`という警告が追加されています。これは、行番号が`0`（通常、行番号が未設定または不明であることを示す）の`Prog`が生成された場合に警告を発することで、行番号の欠落を早期に検出するためのデバッグ支援メカニズムです。

3.  **特定の種類の`Node`の生成**:
    *   `nodreg` 関数内: レジスタを表す`Node` (`n`) を生成する際に、`n->lineno = lineno;`が追加されました。
    *   `nodarg` 関数内: 関数引数を表す`Node` (`n`) を生成する際に、`n->lineno = lineno;`が追加されました。
    *   `nodconst` 関数内: リテラル定数を表す`Node` (`n`) を生成する際に、`n->lineno = lineno;`が追加されました。
    *   `tempname` 関数内: 一時変数（コンパイラが内部的に生成する変数）を表す`Node` (`n`) を生成する際に、`n->lineno = lineno;`が追加されました。
    これらの変更により、レジスタの使用、引数の参照、定数の利用、一時変数の生成といった、ソースコードの直接的な記述からは見えにくいが、コンパイラが内部的に行う操作に対しても、適切なソースコード行番号が関連付けられるようになります。

これらの修正は、コンパイラが生成するデバッグ情報（DWARFなど）の品質を向上させ、デバッガがより正確なソースコード行を表示できるようにするために不可欠です。特に、最適化によってソースコードの構造と機械語命令の対応が複雑になる場合でも、正確な行番号情報があれば、デバッグの難易度を下げることができます。

## 変更の背景

このコミットの背景には、Goコンパイラ（特に当時の`6g`コンパイラ）が生成するコードにおいて、特定の操作やコンパイラが内部的に生成する要素に行番号情報が適切に付与されていないという問題があったと考えられます。

ソースコードの行番号情報は、プログラミング言語のコンパイラにとって極めて重要です。
1.  **エラー報告**: コンパイルエラーや実行時エラーが発生した際に、どのソースコードの行で問題が起きたかを正確にユーザーに伝えるために必要です。行番号が欠落していると、エラーメッセージが不正確になり、デバッグが困難になります。
2.  **デバッグ**: デバッガがソースコードレベルでステップ実行したり、ブレークポイントを設定したりするためには、機械語命令とソースコードの行番号とのマッピングが必要です。行番号情報が不完全だと、デバッグ体験が著しく損なわれます。
3.  **プロファイリング**: 実行時のパフォーマンスプロファイリングにおいて、どのソースコードの行がボトルネックになっているかを特定するためにも行番号情報が利用されます。

このコミットメッセージ「more line numbers」は、以前は行番号が不足していた箇所に、より多くの行番号情報を追加したことを示唆しています。特に、コンパイラが内部的に生成する一時変数、レジスタ操作、スタック操作、リテラル値など、直接ソースコードに記述されないがコード生成過程で不可欠な要素に対して、適切な行番号を関連付けることが目的だったと推測されます。これにより、コンパイラが生成するバイナリのデバッグ情報がより正確になり、開発者がGoプログラムをデバッグする際の利便性が向上します。

## 前提知識の解説

### Goコンパイラ (6g)

Go言語の初期のコンパイラは、ターゲットアーキテクチャごとに異なる名前を持っていました。`6g`は、x86-64 (AMD64) アーキテクチャ向けのGoコンパイラを指します。当時のGoコンパイラは、C言語で書かれており、`gc` (Go Compiler) と総称されるコンパイラ群の一部でした。

コンパイラの一般的な処理フローは以下のようになります。
1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（予約語、識別子、演算子など）の列に変換します。
2.  **構文解析 (Syntax Analysis)**: トークンの列を解析し、プログラムの構造を抽象構文木 (AST) として構築します。
3.  **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、名前解決、スコープチェックなどの意味的な正当性を検証します。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTから、機械語に依存しない中間表現 (IR) を生成します。
5.  **コード最適化 (Code Optimization)**: 中間コードを最適化し、実行効率を向上させます。
6.  **コード生成 (Code Generation)**: 最適化された中間コードから、ターゲットアーキテクチャの機械語（アセンブリコード）を生成します。

このコミットで変更されている`gen.c`や`gsubr.c`は、主に中間コード生成からコード生成の段階に関わるファイルです。

### `lineno` (行番号)

`lineno`は、コンパイラが現在処理しているソースコードの行番号を追跡するための変数またはフィールドです。コンパイラの内部データ構造（ASTノード、中間表現、アセンブリ命令など）にこの`lineno`を付与することで、生成されるバイナリのデバッグ情報にソースコードの行番号を含めることができます。これにより、デバッガが機械語命令とソースコードの対応付けを行うことが可能になります。

### `Node`構造体

Goコンパイラ内部では、ソースコードの様々な要素（変数、定数、式、関数呼び出し、型など）を表現するために`Node`という汎用的なデータ構造が使われます。`Node`構造体は、ASTの各ノードや、中間表現の要素を表すために利用されます。この`Node`構造体には、通常、そのノードがソースコードのどの位置（ファイル名、行番号、列番号）に対応するかを示すフィールドが含まれています。このコミットでは、特定の種類の`Node`が生成される際に、`lineno`フィールドが適切に設定されるように修正されています。

### `Prog`構造体

`Prog`構造体は、Goコンパイラが生成するアセンブリ命令を表現するためのデータ構造です。各`Prog`インスタンスは、特定のアセンブリ命令（例: `MOV`, `ADD`, `CALL`）とそのオペランド、そして関連するメタデータ（例: 行番号）を保持します。`Prog`構造体に行番号情報を含めることで、生成されたアセンブリコードの各命令が、元のソースコードのどの行に対応するかをデバッガが知ることができます。

### `D_SP` (Stack Pointer)

`D_SP`は、スタックポインタレジスタ（x86-64アーキテクチャでは通常`RSP`）を抽象的に表す定数です。スタックポインタは、プログラムの実行スタックの現在のトップを指し示します。関数呼び出し時の引数のプッシュ、戻りアドレスの保存、ローカル変数の確保などに利用されます。コンパイラは、関数呼び出しやローカル変数へのアクセスに関連するコードを生成する際に、スタックポインタを基準としたメモリアドレス指定を行います。

### `Node`の`op`フィールドで使われる定数

`Node`構造体には、そのノードがどのような種類の操作や要素を表すかを示す`op`フィールドがあります。このコミットの差分に登場する主な定数は以下の通りです。

*   **`OINDREG`**: レジスタによる間接参照（例: `*RSP` のように、レジスタが指すメモリ位置へのアクセス）を表します。スタック上の変数や引数へのアクセスによく使われます。
*   **`OREGISTER`**: レジスタ自体（例: `RAX`, `RBX`）を表します。
*   **`OLITERAL`**: リテラル値（定数、例: `10`, `"hello"`）を表します。
*   **`PAUTO`**: 自動変数（ローカル変数）を表します。

これらの定数が行番号と関連付けられることで、コンパイラが生成するスタック操作、レジスタ操作、定数ロード、ローカル変数アクセスといった低レベルな命令が、元のソースコードのどの行に由来するのかを正確に追跡できるようになります。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラのコード生成フェーズにおいて、これまで行番号情報が欠落していたり、不正確であったりした内部的な`Node`構造体や`Prog`構造体に対して、現在のソースコード行番号（`lineno`変数で保持されている）を明示的に設定するように修正した点にあります。

具体的には、以下の種類のコード生成処理において`lineno`が追加されています。

1.  **スタックポインタ (`D_SP`) を利用した間接参照ノードの生成**:
    *   `cgen_callret` 関数内: 関数呼び出しの戻り値を処理する際に、スタックポインタを基準としたメモリアクセスノード (`nod`) が生成されます。このノードに`nod.lineno = lineno;`が追加されました。
    *   `cgen_aret` 関数内: 関数呼び出しの引数を処理する際に、同様にスタックポインタを基準としたメモリアクセスノード (`nod1`) が生成されます。このノードにも`nod1.lineno = lineno;`が追加されました。
    これらの変更により、関数呼び出しに関連するスタック操作が、ソースコードのどの行で行われたかを正確にデバッグ情報に反映できるようになります。

2.  **アセンブリ命令 (`Prog`) の生成**:
    *   `prog` 関数内: アセンブリ命令 (`Prog`) を生成する際に、`p->lineno = lineno;`が設定されます。これにより、個々のアセンブリ命令がソースコードのどの行に対応するかが明確になります。
    *   さらに、`if(lineno == 0) warn("line 0 %P\\n", p);`という警告が追加されています。これは、行番号が`0`（通常、行番号が未設定または不明であることを示す）の`Prog`が生成された場合に警告を発することで、行番号の欠落を早期に検出するためのデバッグ支援メカニズムです。

3.  **特定の種類の`Node`の生成**:
    *   `nodreg` 関数内: レジスタを表す`Node` (`n`) を生成する際に、`n->lineno = lineno;`が追加されました。
    *   `nodarg` 関数内: 関数引数を表す`Node` (`n`) を生成する際に、`n->lineno = lineno;`が追加されました。
    *   `nodconst` 関数内: リテラル定数を表す`Node` (`n`) を生成する際に、`n->lineno = lineno;`が追加されました。
    *   `tempname` 関数内: 一時変数（コンパイラが内部的に生成する変数）を表す`Node` (`n`) を生成する際に、`n->lineno = lineno;`が追加されました。
    これらの変更により、レジスタの使用、引数の参照、定数の利用、一時変数の生成といった、ソースコードの直接的な記述からは見えにくいが、コンパイラが内部的に行う操作に対しても、適切なソースコード行番号が関連付けられるようになります。

これらの修正は、コンパイラが生成するデバッグ情報（DWARFなど）の品質を向上させ、デバッガがより正確なソースコード行を表示できるようにするために不可欠です。特に、最適化によってソースコードの構造と機械語命令の対応が複雑になる場合でも、正確な行番号情報があれば、デバッグの難易度を下げることができます。

## コアとなるコードの解説

このコミットでは、Goコンパイラのコード生成ロジックにおいて、`lineno`（現在のソースコード行番号）を様々な内部データ構造に明示的に設定する変更が行われています。これにより、コンパイラが生成するデバッグ情報の精度が向上します。

1.  **`src/cmd/6g/gen.c` の変更点**:
    *   **`cgen_callret` 関数内**:
        ```c
        	nod.op = OINDREG;
        	nod.val.vval = D_SP;
        	nod.addable = 1;
        	nod.lineno = lineno; // 追加
        ```
        `cgen_callret`は、関数呼び出しの戻り値を処理する際に、スタックポインタ(`D_SP`)を基準とした間接参照ノード(`OINDREG`)を生成します。このノードは、戻り値がスタック上のどこに配置されるかを示します。追加された`nod.lineno = lineno;`により、このスタック操作がソースコードのどの行に対応するかが記録されるようになります。
    *   **`cgen_aret` 関数内**:
        ```c
        	nod1.op = OINDREG;
        	nod1.val.vval = D_SP;
        	nod1.addable = 1;
        	nod1.lineno = lineno; // 追加
        ```
        `cgen_aret`は、関数呼び出しの引数を処理する際に、同様にスタックポインタ(`D_SP`)を基準とした間接参照ノード(`OINDREG`)を生成します。このノードは、引数がスタック上のどこに配置されるかを示します。`nod1.lineno = lineno;`の追加により、引数処理に関連するスタック操作の行番号情報が保持されます。

2.  **`src/cmd/6g/gsubr.c` の変更点**:
    *   **`prog` 関数内**:
        ```c
        	p->as = as;
        	p->lineno = lineno;
        	p->link = pc;
        if(lineno == 0) // 追加
        warn("line 0 %P\\n", p); // 追加
        	return p;
        ```
        `prog`関数は、実際のアセンブリ命令(`Prog`構造体)を生成する役割を担います。`p->lineno = lineno;`は、生成されるすべてのアセンブリ命令に現在のソースコード行番号を付与することを保証します。
        `if(lineno == 0) warn("line 0 %P\\n", p);`の追加は、行番号が`0`（未設定または不明を示すことが多い）の命令が生成された場合に、コンパイラが警告を発するようにするためのデバッグ/検証メカニズムです。これにより、行番号の欠落が早期に発見され、修正される可能性が高まります。
    *   **`nodreg` 関数内**:

        ```

    *   **`nodarg` 関数内**:
        ```c
        	n->sym = t->sym;
        	n->xoffset = t->width;
        	n->addable = 1;
        	n->lineno = lineno; // 追加

        `nodarg`は、関数引数を表す`Node`を生成します。`n->lineno = lineno;`の追加により、引数に関連するノードに行番号情報が付与されます。
    *   **`nodconst` 関数内**:

    *   **`tempname` 関数内**:

# [インデックス 24821] ファイルの概要

このコミットは、Go言語のアセンブラツールである `cmd/asm` において、不正な入力が与えられた際に発生していた複数のパニック（プログラムの異常終了）を修正するものです。特に、擬似命令（pseudo-instructions）のパース処理における堅牢性を向上させ、エラー処理を改善しています。

## 元コミット内容

このコミットは、Goのアセンブラツール `cmd/asm` における複数のパニックを修正します。`cmd/asm` のパーサーは、可能な限り多くの情報を読み取ろうとし、必要に応じてエラーを発行しますが、通常はパースを停止しませんでした。しかし、特定の「病的な」入力（不正な形式の擬似命令）が与えられた場合、エラーメッセージの構築時や次のオペランドのパース時に様々なパニックを引き起こす可能性がありました。

具体的には、`TEXT`, `FUNCDATA`, `DATA`, `GLOBL`, `PCDATA` といった擬似命令に対して、オペランドが不足している、形式が誤っているなどの不正な入力が与えられた際にパニックが発生していました。このコミットでは、これらの問題を解決するために以下の変更が導入されました。

1.  **エラーメッセージキャプチャのためのライター導入**: テスト目的でエラーメッセージをキャプチャするために、パーサーに `io.Writer` が導入されました。デフォルトでは `os.Stderr` に出力されます。
2.  **シンボル名表示時の明示的なチェック**: シンボル名が表示できない場合にパニックが発生しないよう、明示的なチェックが追加されました。
3.  **擬似命令のオペランド数不正時の早期パース中断**: 擬似命令に対してオペランドの数が間違っている場合、早期にパースを中断するようになりました。これにより、後続の不正なオペランドのパースがスキップされるため、動作が変更されますが、1行につき最初のエラーのみが考慮されるため許容できると判断されています。

これらの変更により、`cmd/asm` は不正な入力に対する堅牢性が向上し、パニックの発生が抑制されます。関連するテストも追加され、修正が検証されています。

## 変更の背景

Go言語のツールチェインの一部である `cmd/asm` は、Goプログラムが利用するアセンブリコードを処理する役割を担っています。アセンブリコードは低レベルな操作を記述するため、その構文は厳密ですが、ユーザーが手書きしたり、他のツールが生成したりする過程で、誤った形式のコードが入力される可能性があります。

このコミット以前の `cmd/asm` のパーサーは、エラーが発生しても可能な限りパースを続行しようとする設計でした。これは、一度のエラーで処理を中断するのではなく、複数の問題を一度に報告できるという利点があります。しかし、この設計が仇となり、特定の「病的な」入力、特に擬似命令（`TEXT`, `DATA`, `GLOBL` など）のオペランドが不正な場合に、パーサー内部で予期せぬ状態に陥り、結果としてパニックを引き起こすことが判明しました。

パニックはGoプログラムの実行を即座に停止させるため、開発者体験を著しく損ないます。特に、アセンブリコードのデバッグ中にツールがパニックを起こすと、問題の特定が困難になります。この問題は、GitHubのIssue #11765, #11760, #11759 として報告されており、これらのパニックを修正し、`cmd/asm` の堅牢性を高めることが喫緊の課題となっていました。

この変更の背景には、Goツールチェイン全体の品質と安定性を向上させるという目標があります。ユーザーが安心してツールを利用できるよう、不正な入力に対しても適切にエラーを報告し、パニックを回避する堅牢なパーサーが求められていました。

## 前提知識の解説

### Goのアセンブラ (`cmd/asm`)

Go言語は、そのランタイムや一部の標準ライブラリでパフォーマンスが重要な部分にアセンブリコードを使用しています。Goのアセンブリは、一般的なCPUアーキテクチャ（x86-64, ARMなど）のネイティブアセンブリとは異なり、Go独自の擬似命令（pseudo-instructions）と擬似レジスタ（pseudo-registers）を使用する抽象化されたアセンブリ言語です。この抽象化により、異なるアーキテクチャ間で比較的共通の構文でアセンブリコードを記述できるという利点があります。

`cmd/asm` は、このGo独自のアセンブリ言語をオブジェクトファイルに変換するツールです。Goコンパイラ (`cmd/compile`) と連携して動作し、最終的に実行可能なバイナリを生成します。

### 擬似命令 (Pseudo-instructions) と擬似レジスタ (Pseudo-registers)

Goのアセンブリにおける擬似命令は、直接的なCPU命令に対応しない、アセンブラによって解釈・変換される特別なディレクティブです。これらは、関数定義、データセグメントの宣言、スタックフレームの管理など、高レベルな概念をアセンブリレベルで表現するために用いられます。

主要な擬似命令には以下のようなものがあります。

*   **`TEXT`**: 関数の開始を宣言します。関数名、フラグ（例: `NOSPLIT`）、引数と戻り値のサイズ情報などを指定します。
*   **`DATA`**: 初期化されたデータセグメントを定義します。シンボル名と値、サイズなどを指定します。
*   **`GLOBL`**: グローバルシンボルを宣言します。データや関数の可視性を制御します。
*   **`FUNCDATA`**: 関数に関連するデータ（例: ガベージコレクションのためのポインタ情報）を定義します。
*   **`PCDATA`**: プログラムカウンタデータ（例: ガベージコレクションのためのスタックマップ情報）を定義します。

また、Goアセンブリには以下の4つの仮想擬似レジスタがあります。これらは実際のハードウェアレジスタとは異なり、Goのランタイムやコンパイラがメモリ管理や関数呼び出し規約を抽象化するために使用します。

*   **`FP` (Frame Pointer)**: 関数の引数を参照するために使用されます。`arg+0(FP)` のように記述し、スタック上の引数にアクセスします。
*   **`PC` (Program Counter)**: プログラムカウンタを表し、主にジャンプや分岐命令で使用されます。
*   **`SB` (Static Base Pointer)**: グローバルシンボル（関数やデータ）の基準アドレスを参照するために使用されます。`symbol(SB)` はグローバルシンボル `symbol` のアドレスを意味します。`symbol<>(SB)` は現在のファイルにローカルなシンボルを示します。
*   **`SP` (Stack Pointer)**: 現在の関数のローカルスタックフレームの最上位アドレスを指します。ローカル変数は `var-8(SP)` のように負のオフセットでアクセスされます。ハードウェアのSPレジスタと区別するために、通常はシンボル名がプレフィックスとして必要です。

これらの擬似命令や擬似レジスタは、Goのアセンブリコードを記述する上で不可欠な要素であり、`cmd/asm` はこれらを正しく解釈し、適切な機械語に変換する責任を負っています。本コミットは、これらの擬似命令のパース処理におけるエラー耐性を向上させるものです。

## 技術的詳細

このコミットは、`cmd/asm` のパーサーが不正な入力に遭遇した際の挙動を改善するために、主に以下の3つの技術的アプローチを採用しています。

1.  **エラー出力の抽象化 (`errorWriter` の導入)**:
    *   `src/cmd/asm/internal/asm/parse.go` に `errorWriter io.Writer` フィールドが `Parser` 構造体に追加されました。
    *   `NewParser` 関数で、この `errorWriter` はデフォルトで `os.Stderr` に設定されます。
    *   `errorf` メソッド（エラーメッセージを出力する関数）は、これまでの `fmt.Fprintf(os.Stderr, ...)` の代わりに `fmt.Fprintf(p.errorWriter, ...)` を使用するように変更されました。
    *   この変更により、エラーメッセージの出力先を柔軟に制御できるようになり、特にテストコード内でエラー出力をキャプチャして検証することが容易になりました。`pseudo_test.go` では `bytes.Buffer` を `errorWriter` として設定し、エラーメッセージの内容を検証しています。

2.  **シンボル名表示の安全性の向上 (`symbolName` 関数の導入)**:
    *   `src/cmd/asm/internal/asm/asm.go` に `symbolName(addr *obj.Addr) string` というヘルパー関数が追加されました。
    *   この関数は、`obj.Addr` 構造体に含まれる `Sym` フィールドが `nil` でない場合に `addr.Sym.Name` を返します。
    *   `Sym` が `nil` の場合（つまり、シンボル情報が不正または欠落している場合）は、`"<erroneous symbol>"` というエラー文字列を返します。
    *   これにより、`validateSymbol` メソッド内でエラーメッセージを構築する際に、`addr.Sym.Name` に直接アクセスしてパニックを引き起こす可能性があった箇所が、`symbolName(addr)` を介することで安全に処理されるようになりました。例えば、`TEXT symbol %q must be a symbol(SB)` の `%q` に不正なシンボル名が渡されても、パニックではなく `"<erroneous symbol>"` が表示されるようになります。

3.  **擬似命令のオペランド数チェックと早期中断**:
    *   `src/cmd/asm/internal/asm/asm.go` 内の各擬似命令（`asmText`, `asmData`, `asmGlobl`, `asmPCData`, `asmFuncData`）を処理する関数において、オペランドの数をチェックする初期段階で `p.errorf(...)` を呼び出した後、`return` ステートメントが追加されました。
    *   例えば、`asmText` 関数では `if len(operands) != 2 && len(operands) != 3` のチェックの後、`p.errorf(...)` に続いて `return` が追加されています。
    *   これにより、オペランドの数が期待されるものと異なる場合、それ以降のオペランドのパース処理は実行されずに、その擬似命令の処理が早期に中断されます。
    *   コミットメッセージにもあるように、これは動作変更を伴います。以前は、オペランド数が不正でも可能な限りパースを続けようとしていましたが、この変更により、最初のエラーが検出された時点でその擬似命令の処理は打ち切られます。しかし、Goのアセンブラは通常、1行につき最初のエラーのみを報告するため、この変更は実用上問題ないと判断されています。この早期中断により、不正なオペランドをさらにパースしようとすることで発生していたパニックが回避されます。

これらの変更は、`cmd/asm` のパーサーが不正なアセンブリコードに対してより堅牢に振る舞うように設計されており、開発者が遭遇する可能性のあるパニックを大幅に削減します。

## コアとなるコードの解説

### `src/cmd/asm/internal/asm/asm.go` の変更点

```go
// validateSymbol checks that addr represents a valid name for a pseudo-op.
func (p *Parser) validateSymbol(pseudo string, addr *obj.Addr, offsetOk bool) {
	if addr.Name != obj.NAME_EXTERN && addr.Name != obj.NAME_STATIC || addr.Scale != 0 || addr.Reg != 0 {
		// 変更前: p.errorf("%s symbol %q must be a symbol(SB)", pseudo, addr.Sym.Name)
		p.errorf("%s symbol %q must be a symbol(SB)", pseudo, symbolName(addr)) // symbolNameを使用
	}
	if !offsetOk && addr.Offset != 0 {
		// 変更前: p.errorf("%s symbol %q must not be offset from SB", pseudo, addr.Sym.Name)
		p.errorf("%s symbol %q must not be offset from SB", pseudo, symbolName(addr)) // symbolNameを使用
	}
}

// ... (中略) ...

func (p *Parser) asmText(word string, operands [][]lex.Token) {
	if len(operands) != 2 && len(operands) != 3 {
		p.errorf("expect two or three operands for TEXT")
		return // 早期リターンを追加
	}
	// ... (後続のパースロジック) ...
	nameAddr := p.address(operands[0])
	p.validateSymbol("TEXT", &nameAddr, false)
	// 変更前: name := nameAddr.Sym.Name
	name := symbolName(&nameAddr) // symbolNameを使用
	// ... (後続のパースロジック) ...
}

// ... (asmData, asmGlobl, asmPCData, asmFuncData も同様に早期リターンとsymbolNameの適用) ...

// symbolName returns the symbol name, or an error string if none if available.
func symbolName(addr *obj.Addr) string {
	if addr.Sym != nil {
		return addr.Sym.Name
	}
	return "<erroneous symbol>" // シンボル情報がない場合にエラー文字列を返す
}
```
`validateSymbol` 関数では、エラーメッセージを生成する際に `addr.Sym.Name` に直接アクセスする代わりに、新しく追加された `symbolName` ヘルパー関数を呼び出すように変更されました。これにより、`addr.Sym` が `nil` の場合に発生する可能性があったパニックが回避され、代わりに `"<erroneous symbol>"` という安全な文字列がエラーメッセージに埋め込まれます。
また、`asmText` や他の擬似命令処理関数では、オペランド数の初期チェックでエラーが検出された場合、`p.errorf` でエラーを報告した直後に `return` するように変更されました。これにより、不正なオペランドが後続のパースロジックで処理されることを防ぎ、それによって引き起こされる可能性のあるパニックを未然に防ぎます。

### `src/cmd/asm/internal/asm/parse.go` の変更点

```go
type Parser struct {
	// ... (既存フィールド) ...
	errorWriter   io.Writer // 新しく追加されたエラー出力先
}

func NewParser(ctxt *obj.Link, ar *arch.Arch, lexer lex.TokenReader) *Parser {
	return &Parser{
		// ... (既存フィールドの初期化) ...
		errorWriter: os.Stderr, // デフォルトでos.Stderrに設定
	}
}

func (p *Parser) errorf(format string, args ...interface{}) {
	if p.errorCount > 0 && p.errorLine == p.histLineNum {
		return
	}
	p.errorLine = p.histLineNum
	if p.lex != nil { // p.lexがnilでない場合のみファイルと行情報を追加
		format = "%s:%d: " + format + "\n"
		args = append([]interface{}{p.lex.File(), p.lineNum}, args...)
	}
	fmt.Fprintf(p.errorWriter, format, args...) // os.Stderrではなくp.errorWriterに出力
	p.errorCount++
	// ... (エラーカウントのチェック) ...
}
```
`Parser` 構造体に `errorWriter` フィールドが追加され、エラーメッセージの出力先が抽象化されました。`NewParser` でデフォルト値が設定され、`errorf` メソッドがこの `errorWriter` を使用するように変更されています。これにより、テスト時にエラー出力をバッファにリダイレクトして内容を検証することが可能になります。また、`p.lex` が `nil` の場合（例えば、パーサーの初期化が不完全な場合など）にファイル名や行番号の取得でパニックにならないよう、条件付きで追加するようになりました。

### `src/cmd/asm/internal/asm/pseudo_test.go` の追加

このファイルは、以前パニックを引き起こしていた不正な入力パターンを網羅する新しいテストケース `TestErroneous` を導入しています。

```go
func TestErroneous(t *testing.T) {
	tests := []struct {
		pseudo   string
		operands string
		expected string
	}{
		{"TEXT", "", "expect two or three operands for TEXT"},
		{"TEXT", "%", "expect two or three operands for TEXT"},
		{"TEXT", "1, 1", "TEXT symbol \"<erroneous symbol>\" must be a symbol(SB)"},
		// ... (他の不正な入力パターン) ...
		{"PCDATA", "1", "expect two operands for PCDATA"},
	}

	parser := newParser("amd64")
	var buf bytes.Buffer
	parser.errorWriter = &buf // errorWriterをbytes.Bufferに設定
	
	for _, test := range tests {
		buf.Reset() // 各テストケースでバッファをリセット
		parser.errorCount = 0
		parser.lineNum++
		parser.histLineNum++
		op, ok := arch.Pseudos[test.pseudo]
		if !ok {
			t.Fatalf("Wrong pseudo-instruction: %s", test.pseudo)
		}
		parser.pseudo(op, test.pseudo, tokenize(test.operands))
		errorLine := buf.String() // 出力されたエラーメッセージをキャプチャ
		if !strings.Contains(errorLine, test.expected) { // 期待されるエラーメッセージが含まれているか検証
			t.Errorf("Unexpected error %q; expected to contain %q", errorLine, test.expected)
		}
	}
}
```
このテストコードは、`newParser` でパーサーを初期化し、その `errorWriter` を `bytes.Buffer` に設定することで、`p.errorf` から出力されるエラーメッセージを捕捉します。その後、定義された不正な入力パターン (`tests` スライス) をループで処理し、各入力に対して `parser.pseudo` を呼び出します。`buf.String()` でキャプチャされたエラーメッセージが、`test.expected` に含まれる文字列と一致するか（または含むか）を検証することで、パーサーが正しくエラーを報告し、パニックを起こさないことを確認しています。

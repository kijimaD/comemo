# [インデックス 2247] ファイルの概要

このコミットは、Goコンパイラ（`6g`、当時のx86-64アーキテクチャ向けコンパイラ）における文字列の静的初期化に関する変更を導入しています。具体的には、コンパイル時に文字列リテラルがどのようにデータセクションに配置され、そのポインタと長さがどのように表現されるかを扱っています。

## 変更の背景

Go言語の初期段階において、コンパイラは様々なデータ型や構造のメモリ上での表現方法を確立していく必要がありました。特に文字列は、その不変性や効率的なアクセスが求められるため、コンパイル時にどのように静的に初期化され、実行ファイルに埋め込まれるかは重要な課題でした。

このコミット以前は、文字列リテラルの静的初期化が適切に処理されていなかったか、あるいは現在のGoの文字列表現（ポインタと長さのペア）に最適化されていなかった可能性があります。この変更は、文字列リテラルがデータセクションに効率的に配置され、そのアドレスと長さがプログラム内で正しく参照されるようにするための基盤を構築することを目的としています。これにより、文字列操作のパフォーマンス向上と、コンパイラの堅牢性の向上が図られます。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造とGo言語の基本的な概念に関する知識が必要です。

*   **Go言語の文字列表現**: Go言語において、文字列は不変なバイトのシーケンスであり、内部的にはポインタと長さ（バイト数）のペアとして表現されます。例えば、`"hello"`という文字列は、データセクション内の`'h', 'e', 'l', 'l', 'o'`というバイト列へのポインタと、長さ`5`という情報で構成されます。
*   **コンパイラのフェーズ**: コンパイラは通常、字句解析、構文解析、意味解析、中間コード生成、最適化、コード生成といった複数のフェーズを経てソースコードを実行可能なバイナリに変換します。このコミットは主に「コード生成」フェーズに関わっています。
*   **データセクション (Data Section)**: 実行可能ファイルには、プログラムのコード（テキストセクション）とは別に、初期化されたグローバル変数や静的変数、文字列リテラルなどが格納されるデータセクションが存在します。
*   **`6g`コンパイラ**: Go言語の初期のコンパイラの一つで、x86-64アーキテクチャ（64-bit Intel/AMDプロセッサ）をターゲットとしていました。`cmd/6g`ディレクトリはそのコンパイラのソースコードを含んでいます。
*   **`gen.c`**: Goコンパイラのバックエンドにおけるコード生成を担当するファイルの一つです。AST（抽象構文木）を走査し、ターゲットアーキテクチャの機械語命令やデータ定義を生成します。
*   **`gg.h`**: `6g`コンパイラで使用される共通の定義や関数プロトタイプが宣言されているヘッダファイルです。
*   **`gins`関数**: Goコンパイラ内部で、アセンブリ命令を生成するための関数です。`ADATA`はデータセクションへの命令生成を示します。
*   **`Node`構造体**: コンパイラ内部で、ソースコードの要素（変数、定数、式など）を表現する抽象構文木のノードです。`nr->val.u.sval->s`は文字列リテラルの実際のバイト列を、`nr->val.u.sval->len`はその長さを指します。
*   **`Addr`構造体**: メモリ上のアドレスを表現するための構造体です。
*   **型システム**: `types[tptr]`はポインタ型、`types[TINT32]`は32ビット整数型を表します。Goの文字列はポインタと長さのペアなので、ポインタのサイズと整数のサイズが重要になります。

## 技術的詳細

このコミットは、`src/cmd/6g/gen.c`の`case TSTRING:`ブロックに新しいコードを追加し、`src/cmd/6g/gg.h`に`datastring`関数のプロトタイプを追加しています。

変更の核心は、Goの文字列リテラル（`TSTRING`型）がコンパイル時にどのようにデータセクションに配置され、その参照が生成されるかという点にあります。

1.  **文字列データの配置**:
    *   `p = gins(ADATA, &nam, N);`
        *   これは、データセクション（`ADATA`）に新しいエントリを生成するための命令です。`nam`はシンボル名、`N`は初期値がないことを示します。
    *   `datastring(nr->val.u.sval->s, nr->val.u.sval->len, &p->to);`
        *   `datastring`関数は、実際の文字列バイト列（`nr->val.u.sval->s`）とその長さ（`nr->val.u.sval->len`）をデータセクションに書き込みます。`p->to`は、このデータが書き込まれるアドレス情報を受け取ります。
        *   この`datastring`関数は、`src/cmd/6g/obj.c`（オブジェクトファイル生成関連のコード）で定義されていると推測されます。`gg.h`へのプロトタイプ追加がそれを裏付けています。
    *   `p->from.scale = types[tptr]->width;`
        *   生成されるデータエントリのサイズをポインタの幅（`types[tptr]->width`）に設定します。これは、文字列のポインタ部分を格納するためです。
    *   `p->to.index = p->to.type; p->to.type = D_ADDR;`
        *   これは、`p->to`が指すアドレスが、データセクション内の特定のアドレス（`D_ADDR`）であることを示します。つまり、文字列データ自体のアドレスがここに格納されます。

2.  **文字列の長さの配置**:
    *   `nodconst(&nod1, types[TINT32], nr->val.u.sval->len);`
        *   文字列の長さ（`nr->val.u.sval->len`）を32ビット整数型（`TINT32`）の定数ノード`nod1`として作成します。
    *   `p = gins(ADATA, &nam, &nod1);`
        *   データセクションに、この長さの定数値を格納するための命令を生成します。
    *   `p->from.scale = types[TINT32]->width;`
        *   生成されるデータエントリのサイズを32ビット整数の幅に設定します。
    *   `p->from.offset += types[tptr]->width;`
        *   この長さのデータは、文字列ポインタの直後に配置されるため、オフセットをポインタの幅分進めます。
    *   次の`gins`呼び出しも同様に、文字列の長さのコピーを配置しているように見えますが、コメントアウトされた`print`文がないため、正確な意図はコードだけでは判断しにくいです。しかし、Goの文字列がポインタと長さのペアであることを考えると、この2つの`gins`呼び出しでポインタと長さがデータセクションに連続して配置されることを意図していると考えられます。

この変更により、Goコンパイラは文字列リテラルを効率的に静的データとして扱い、実行時にそのポインタと長さを迅速に取得できるようになります。これは、Goの文字列が値型のように振る舞いつつも、内部的には参照渡しに近い効率的なメカニズムを持つための重要なステップです。

## コアとなるコードの解説

`src/cmd/6g/gen.c`の変更は、`lit:`ラベル内の`switch`文に`case TSTRING:`ブロックを追加しています。これは、コンパイラが文字列リテラル（`TSTRING`）を処理する際の具体的なコード生成ロジックを定義しています。

1.  **文字列ポインタの生成**:
    *   最初の`gins(ADATA, &nam, N)`は、データセクションに文字列データへのポインタを格納するための領域を確保します。
    *   `datastring`関数が呼び出され、実際の文字列バイト列がデータセクションのどこかに書き込まれ、そのアドレスが`p->to`に設定されます。
    *   `p->from.scale = types[tptr]->width;`は、この領域がポインタのサイズであることを示します。
    *   `p->to.index = p->to.type; p->to.type = D_ADDR;`は、`p->to`がデータセクション内のアドレスを指すように設定します。

2.  **文字列長さの生成**:
    *   `nodconst(&nod1, types[TINT32], nr->val.u.sval->len);`で、文字列の長さを表す定数ノードを作成します。
    *   続く2つの`gins`呼び出しは、この文字列の長さをデータセクションに格納します。
    *   `p->from.offset += types[tptr]->width;`は、長さがポインタの直後に配置されるようにオフセットを調整します。
    *   Goの文字列はポインタと長さのペアであるため、このコードは文字列リテラルがメモリ上で`[ポインタ][長さ]`という形式で表現されるようにデータを配置していると考えられます。

`src/cmd/6g/gg.h`の変更は、`datastring`関数のプロトタイプ宣言を追加しています。これは、`datastring`関数が`obj.c`（オブジェクトファイル関連の処理を行うファイル）で定義されており、`gen.c`から呼び出されることを示唆しています。この関数の役割は、実際の文字列バイト列をデータセクションに書き込むことです。

これらの変更により、Goコンパイラは文字列リテラルを効率的に静的データとして扱い、実行時にそのポインタと長さを迅速に取得できるようになります。これは、Goの文字列が値型のように振る舞いつつも、内部的には参照渡しに近い効率的なメカニズムを持つための重要なステップです。

# [インデックス 25734] ファイルの概要

このコミットは、GoランタイムにおけるCgoによって作成されたスレッドと非同期シグナル処理に関する競合状態を修正するものです。具体的には、CgoスレッドがGoランタイムの`g`（ゴルーチン）および`m`（OSスレッド）構造体との関連付けを切り替える際に、不適切なタイミングでシグナルが到着すると、Goシグナルハンドラが安全でない状態で実行され、「不正なシグナルスタック」を引き起こす可能性があった問題を解決します。この修正は、スレッドの状態遷移中にすべてのシグナルをマスクすることで、この競合状態を回避します。

## 元コミット内容

Goランタイムにおいて、Cgoによって生成されたスレッドがGoの`g`（ゴルーチン）と`m`（OSスレッド）の関連付けを持つ状態と持たない状態の間を遷移する際に、非同期シグナルが到着すると問題が発生する可能性がありました。この遷移中にシグナルが到着した場合、ランタイムはGoシグナルハンドラを実行しても安全であると誤解し、実際には適切なシグナルスタック設定やその他のデータが準備されていない状態でハンドラが実行されることで、クラッシュや予期せぬ動作を引き起こす可能性がありました。このコミットは、この競合状態を回避するために、遷移期間中にすべてのシグナルをマスクする（ブロックする）ように変更を加えています。

## 変更の背景

Goランタイムは、独自のスケジューラとメモリ管理を持ち、OSスレッド（`m`）上でゴルーチン（`g`）を実行します。Cgoを使用すると、GoプログラムはC言語のコードを呼び出すことができ、CコードがOSスレッドを直接作成することもあります。これらのCgoによって作成されたスレッドは、Goランタイムの管理下に入ったり出たりする際に、Goの`g`と`m`構造体との関連付けを動的に変更します。

このコミットが修正しようとしている問題は、この「関連付けの遷移」のタイミングで発生する競合状態です。具体的には、GoランタイムがOSスレッドをGoコード実行のために準備する（`needm`関数）際や、Goコード実行から解放する（`dropm`関数）際に、スレッドのシグナルハンドリングに関する状態が一時的に不安定になります。この不安定な期間中に非同期シグナル（例えば、`SIGSEGV`や`SIGTERM`など）がスレッドに送信されると、Goランタイムはシグナルを処理しようとしますが、その時点ではシグナルハンドラが使用するべき代替シグナルスタック（`sigaltstack`）やその他の重要なコンテキストがまだ適切に設定されていない可能性があります。結果として、シグナルハンドラが不正なスタックで実行され、プログラムがクラッシュする原因となっていました。

この問題は、Go issue #12277として報告されており、Cgoと非同期シグナルの組み合わせが特定の条件下でランタイムの不安定性を引き起こすことが認識されていました。

## 前提知識の解説

このコミットの理解には、以下の概念が不可欠です。

1.  **Goランタイムスケジューラ (M, P, G)**:
    *   **G (Goroutine)**: Goにおける軽量スレッドの単位。Goプログラムの並行処理の基本です。
    *   **M (Machine)**: OSスレッドを表します。Goランタイムは、OSスレッドを抽象化して`m`として扱います。`m`はOSスレッドと1対1で対応し、Goコードを実行するためのコンテキスト（スタック、レジスタなど）を持ちます。
    *   **P (Processor)**: 論理プロセッサを表し、`g`を`m`上で実行するためのリソースを提供します。`p`は`g`と`m`の間の仲介役となり、`g`が`m`上で実行されるためのコンテキストを管理します。
    Cgoスレッドは、Goコードを実行する際に`m`と`g`を一時的に「借用」または「関連付け」ます。

2.  **Cgo**:
    GoプログラムからC言語の関数を呼び出したり、C言語のコードにGoの関数を公開したりするためのメカニズムです。Cgoを使用すると、Goランタイムの管理外でOSスレッドが作成されることがあります。これらのスレッドがGoコードを実行する必要がある場合、Goランタイムはそれらを既存の`m`にアタッチするか、新しい`m`を作成してアタッチします。

3.  **Unixシグナルとシグナルマスク**:
    *   **シグナル**: プロセスに対して非同期に通知されるイベントです（例: `SIGINT` (Ctrl+C), `SIGSEGV` (セグメンテーション違反), `SIGTERM` (終了要求)）。
    *   **非同期シグナル**: プログラムの実行フローとは独立していつでも発生しうるシグナルです。
    *   **シグナルマスク**: プロセスまたはスレッドが現在ブロックしているシグナルのセットです。ブロックされたシグナルは、マスクが解除されるまで保留されます。`sigprocmask`システムコールは、シグナルマスクを変更するために使用されます。

4.  **代替シグナルスタック (`sigaltstack`)**:
    シグナルハンドラが実行される際に、通常のプログラムスタックとは別のスタックを使用するようにOSに指示するメカニズムです。これは、シグナルがスタックオーバーフローの状況で発生した場合でも、シグナルハンドラが安全に実行されることを保証するために重要です。Goランタイムは、シグナルハンドラのために独自の代替シグナルスタックを設定します。

5.  **`//go:nosplit` ディレクティブ**:
    Goコンパイラに対する指示で、この関数がスタックの分割チェック（スタックが足りなくなった場合にスタックを拡張する処理）を含まないことを意味します。これは、スタックの状態が非常にデリケートな低レベルのランタイム関数、特にシグナルハンドリングに関連する関数で重要です。スタックの拡張処理自体がシグナルハンドリング中に問題を引き起こす可能性があるため、`nosplit`関数は固定された小さなスタックフレーム内で実行されることが期待されます。

## 技術的詳細

このコミットの核心は、CgoスレッドがGoランタイムのコンテキスト（`g`と`m`）に出入りする際のシグナル処理の安全性を確保することです。

Goランタイムでは、`m`（OSスレッド）がGoコードを実行する準備ができたとき（`needm`関数内）や、Goコードの実行を終了して`m`を解放するとき（`dropm`関数内）に、シグナルハンドリングのコンテキストが設定または解除されます。この設定・解除の期間は、シグナルハンドラが安全に実行できる状態ではありません。

修正前は、この期間中にシグナルが到着すると、ランタイムが不完全なシグナルハンドリングコンテキスト（例えば、`sigaltstack`が未設定または不適切）でシグナルハンドラを起動しようとし、結果として「不正なシグナルスタック」エラーやクラッシュが発生していました。

このコミットでは、以下の変更によってこの問題を解決しています。

1.  **シグナルブロックの導入**:
    *   `msigsave(mp *m)`: 現在のOSスレッドのシグナルマスクを保存します。
    *   `msigrestore(mp *m)`: 保存されたシグナルマスクを復元します。
    *   `sigblock()`: すべてのシグナルをブロックするようにシグナルマスクを設定します。これにより、重要な遷移期間中にシグナルがスレッドに配信されるのを防ぎます。

2.  **`needm`関数での変更**:
    *   `needm`は、OSスレッドをGoコード実行のために準備する関数です。
    *   新しい`g`（ゴルーチン）をインストールし、スタック境界を設定する**前**に、`msigsave(mp)`で現在のシグナルマスクを保存し、`sigblock()`ですべてのシグナルをブロックするように変更されました。
    *   これにより、`g`がインストールされ、`minit`（OSスレッドの初期化）が完了してシグナルハンドリングコンテキストが完全に設定されるまでの間、シグナルがブロックされます。`minit`の最後でシグナルはブロック解除されます。

3.  **`dropm`関数での変更**:
    *   `dropm`は、OSスレッドがGoコードの実行を終了し、`m`を解放する関数です。
    *   `unminit`（OSスレッドの初期化解除）と`setg(nil)`（`g`の関連付け解除）の**前**に、`sigblock()`ですべてのシグナルをブロックするように変更されました。
    *   `unminit`はシグナルハンドリングスタックの登録を解除し、`setg(nil)`はシグナルハンドラがGoハンドラを実行しないようにする合図です。これらのステップの間にシグナルが処理されないように、シグナルがブロックされます。
    *   `setg(nil)`の**後**に、`msigrestore(mp)`で元のシグナルマスクが復元されます。

4.  **OS固有のファイル (`os1_*.go`, `os3_*.go`) の変更**:
    *   各OS固有のランタイムファイルに、`msigrestore`と`sigblock`関数が追加されました。これらの関数は、各OSの`sigprocmask`システムコールを適切に呼び出すように実装されています。
    *   `msigsave`関数には`//go:nosplit`ディレクティブが追加され、スタックの分割チェックなしで実行されることが保証されます。
    *   `unminit`関数から、以前行っていたシグナルマスクの復元ロジックが削除されました。これは、`dropm`内で`msigrestore`が明示的に呼び出されるようになったためです。

これらの変更により、CgoスレッドがGoランタイムのコンテキストに出入りする際のシグナル処理のタイミングが厳密に制御され、シグナルハンドラが常に安全な環境で実行されることが保証されます。

## コアとなるコードの解説

### `src/runtime/proc.go` の変更

*   **`needm` 関数**:
    *   `msigsave(mp)` と `sigblock()` が、`g`のインストールとスタック境界の設定より前に移動されました。これは、GoランタイムがOSスレッドをGoコード実行のために完全に準備する前に、すべてのシグナルを一時的にブロックすることで、シグナルハンドリングコンテキストが不完全な状態でシグナルが到着するのを防ぐためです。
    *   コメントで「Once g is installed, any incoming signals will try to execute, but we won't have the sigaltstack settings and other data set up appropriately until the end of minit, which will unblock the signals.」と説明されており、`minit`が完了するまでシグナルハンドリングの準備が整わないことが強調されています。

*   **`dropm` 関数**:
    *   `sigblock()` が `unminit()` と `setg(nil)` の前に呼び出されるようになりました。これは、`unminit`がシグナルハンドリングスタックの登録を解除し、`setg(nil)`が`g`をクリアすることで、シグナルハンドラがGoハンドラを実行しないようにする重要なステップの間に、シグナルが処理されないようにするためです。
    *   `msigrestore(mp)` が `setg(nil)` の後に呼び出されるようになりました。これにより、`m`がGoランタイムのコンテキストから完全に解放された後に、元のシグナルマスクが安全に復元されます。

### `src/runtime/os1_*.go` および `src/runtime/os3_*.go` の変更

*   **`msigrestore(mp *m)` 関数**:
    *   新しく追加された関数で、`mp->sigmask`に保存されているシグナルマスクをOSに復元する役割を担います。これは、`sigprocmask(_SIG_SETMASK, smask, nil)`（またはOS固有の同等な呼び出し）を通じて行われます。
    *   `//go:nosplit` ディレクティブが付与されており、スタックの分割チェックなしで実行されることが保証されます。

*   **`sigblock()` 関数**:
    *   新しく追加された関数で、すべてのシグナルをブロックするようにOSのシグナルマスクを設定します。これは、`sigprocmask(_SIG_SETMASK, &sigset_all, nil)`（またはOS固有の同等な呼び出し）を通じて行われます。`sigset_all`はすべてのシグナルを含むシグナルセットです。
    *   `//go:nosplit` ディレクティブが付与されており、スタックの分割チェックなしで実行されることが保証されます。

*   **`msigsave(mp *m)` 関数**:
    *   既存の関数ですが、`//go:nosplit` ディレクティブが追加されました。これは、現在のシグナルマスクを`mp->sigmask`に保存する際に、スタックの分割チェックを避けるためです。

*   **`unminit()` 関数**:
    *   以前は`_g_.m.sigmask`を復元するロジックが含まれていましたが、このコミットで削除されました。シグナルマスクの復元は、`dropm`関数内で`msigrestore`が明示的に呼び出されるようになったため、`unminit`の役割から分離されました。

これらの変更は、GoランタイムがCgoスレッドのライフサイクルとシグナル処理の間の同期をより厳密に管理し、潜在的な競合状態を排除することを目的としています。

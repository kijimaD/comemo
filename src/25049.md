# [インデックス 25049] ファイルの概要

このコミットは、Go言語の標準ライブラリ `bufio` パッケージ内の `Scanner` 型に機能追加と修正を施しています。具体的には、`Scanner` がトークンをバッファリングするために使用するメモリを、ユーザーが明示的に指定できるようにする `Buffer` メソッドが追加されました。また、`Scan` メソッドが呼び出された後に `Buffer` または `Split` メソッドが呼び出された場合にパニックを発生させる検証ロジックも導入されています。

## 変更の背景

この変更は、Goの `bufio.Scanner` が内部的に使用するバッファの管理に関する柔軟性を向上させるために行われました。特に、大きなトークン（例えば、非常に長い行や巨大なデータブロック）を処理する際に、`Scanner` のデフォルトのバッファサイズ (`MaxScanTokenSize`、通常は64KB) を超えるデータを扱う必要が生じることがありました。

従来の `Scanner` は、トークンがバッファに収まらない場合に内部的にバッファを拡張しようとしますが、そのサイズには上限がありました。この上限を超えるトークンは `ErrTooLong` エラーを引き起こし、処理を中断させていました。

Issue #11702 (https://github.com/golang/go/issues/11702) では、この問題が議論されており、ユーザーが `Scanner` に独自のバッファを提供し、最大トークンサイズを制御できるメカニズムが求められていました。これにより、ユーザーはメモリ割り当てをより細かく制御し、アプリケーションの特定の要件に合わせて `Scanner` の動作を最適化できるようになります。例えば、非常に大きなファイルを読み込む際に、メモリ使用量を予測可能にし、不要な再割り当てを防ぐことが可能になります。

また、`Split` メソッドと同様に、`Buffer` メソッドも `Scan` が呼び出される前に設定されるべきであるという設計意図を明確にするため、`Scan` 呼び出し後の `Buffer` または `Split` の呼び出しでパニックを発生させるようになりました。これは、`Scanner` の状態が既に確立された後にこれらの設定を変更することによる予期せぬ動作を防ぐための措置です。

## 前提知識の解説

### `bufio` パッケージと `Scanner`

`bufio` パッケージは、I/O操作を効率化するためのバッファリング機能を提供します。特に `bufio.Scanner` は、`io.Reader` からデータを読み込み、指定された区切り関数 (`SplitFunc`) に基づいてトークン（単語、行、カスタム区切り文字など）に分割するためのユーティリティです。

`Scanner` の基本的な使用方法は以下の通りです。

1.  `bufio.NewScanner(reader)` で `Scanner` インスタンスを作成します。
2.  `scanner.Scan()` をループで呼び出し、次のトークンがあるかを確認します。
3.  `scanner.Text()` または `scanner.Bytes()` で現在のトークンを取得します。
4.  `scanner.Err()` でエラーを確認します。

### `SplitFunc`

`SplitFunc` は、`Scanner` が入力ストリームをどのようにトークンに分割するかを定義する関数です。`bufio` パッケージには `ScanBytes`, `ScanRunes`, `ScanWords`, `ScanLines` といった標準の `SplitFunc` が用意されていますが、ユーザーは独自の `SplitFunc` を定義することも可能です。

### `Scanner` のバッファリング

`Scanner` は、入力データを効率的に処理するために内部バッファを使用します。デフォルトでは、このバッファは `MaxScanTokenSize` (64KB) を上限として自動的に拡張されます。トークンがこの上限を超えると、`Scanner` は `ErrTooLong` エラーを返します。これは、メモリの過剰な使用を防ぐための安全策ですが、特定のユースケースではこの制限が問題となることがありました。

## 技術的詳細

このコミットの主要な変更点は、`Scanner` に `Buffer` メソッドを追加し、ユーザーがバッファリングの挙動をより詳細に制御できるようにしたことです。

### `Scanner.Buffer(buf []byte, max int)` メソッドの追加

-   **目的**: ユーザーが `Scanner` に独自のバイトスライス (`buf`) を提供し、トークンをバッファリングするために使用させることができます。また、`Scanner` が内部的に割り当てる可能性のあるバッファの最大サイズ (`max`) を設定することもできます。
-   **引数**:
    -   `buf []byte`: `Scanner` がトークンを格納するために使用する初期バッファ。`Scanner` はこのスライスの容量 (`cap(buf)`) を利用します。
    -   `max int`: `Scanner` がトークンをバッファリングするために割り当てることができる最大メモリサイズ。この値は `cap(buf)` と比較され、より大きい方が実際の最大トークンサイズとして考慮されます。もし `max <= cap(buf)` であれば、`Scanner` は提供された `buf` のみを使用し、追加のメモリ割り当ては行いません。
-   **デフォルトの挙動の変更**: 以前は `Scanner` は常に `make([]byte, 4096)` で初期バッファを作成していましたが、`Buffer` メソッドが導入されたことで、ユーザーが明示的にバッファを提供しない限り、内部バッファの初期化ロジックが変更されました。
-   **パニック条件**: `Buffer` メソッドは、`Scanner.Scan()` が一度でも呼び出された後に呼び出されるとパニック (`"Buffer called after Scan"`) を発生させます。これは、`Scanner` が既にデータを読み込み始めている状態でバッファ設定を変更すると、内部状態が矛盾する可能性があるためです。

### `Scanner.Split(split SplitFunc)` メソッドのパニック条件追加

-   以前の `Split` メソッドは、`Scan` 呼び出し後に呼び出された場合の動作についてコメントで警告していましたが、実際のパニックは発生しませんでした。
-   このコミットでは、`Buffer` メソッドと同様に、`Scan` が呼び出された後に `Split` が呼び出された場合にもパニック (`"Split called after Scan"`) を発生させるようになりました。これにより、`Scanner` の設定は `Scan` が開始される前に完了させるべきであるという設計原則が強制されます。

### `Scanner` 構造体への `scanCalled` フィールドの追加

-   `bool` 型の `scanCalled` フィールドが `Scanner` 構造体に追加されました。
-   このフィールドは、`Scanner.Scan()` メソッドが初めて呼び出されたときに `true` に設定されます。
-   `Buffer` および `Split` メソッドはこの `scanCalled` フィールドをチェックし、`true` の場合はパニックを発生させます。

### バッファ拡張ロジックの変更

-   `Scan` メソッド内で、トークンが現在のバッファに収まらない場合のバッファ拡張ロジックが微調整されました。
-   `newSize := len(s.buf) * 2` の行に `// See protection against overflow in Buffer.` というコメントが追加され、`Buffer` メソッドで設定された `maxTokenSize` がオーバーフロー保護にどのように関連するかを示唆しています。
-   `newSize == 0` の場合に `newSize = startBufSize` を設定するロジックが追加されました。これは、初期バッファが空の場合（例えば、`Buffer([]byte{}, max)` のように呼び出された場合）に、適切な初期サイズでバッファを割り当てるためのものです。

## コアとなるコードの解説

### `Scanner` 構造体

```go
type Scanner struct {
	// ... 既存のフィールド ...
	scanCalled   bool      // Scan has been called; buffer is in use.
}
```
`scanCalled` フィールドは、`Scanner` の `Scan` メソッドが一度でも呼び出されたかどうかを追跡します。これにより、`Buffer` や `Split` のような設定メソッドが、`Scanner` が既に動作を開始した後に呼び出されるのを防ぎます。

### `MaxScanTokenSize` のコメント更新と `startBufSize`

```go
const (
	// MaxScanTokenSize is the maximum size used to buffer a token
	// unless the user provides an explicit buffer with Scan.Buffer.
	// The actual maximum token size may be smaller as the buffer
	// may need to include, for instance, a newline.
	MaxScanTokenSize = 64 * 1024

	startBufSize = 4096 // Size of initial allocation for buffer.
)
```
`MaxScanTokenSize` のコメントが更新され、ユーザーが `Buffer` メソッドで明示的なバッファを提供した場合、この上限が適用されない可能性があることが明確にされました。`startBufSize` は、`Scanner` が内部的にバッファを初期化または拡張する際に使用するデフォルトの開始サイズを定義します。

### `NewScanner` からの初期バッファ割り当ての削除

```go
func NewScanner(r io.Reader) *Scanner {
	return &Scanner{
		r:            r,
		split:        ScanLines,
		maxTokenSize: MaxScanTokenSize,
		// buf:          make([]byte, 4096), // Plausible starting size; needn't be large. (削除された行)
	}
}
```
`NewScanner` から `buf` フィールドの初期化が削除されました。これは、`Scanner` が必要に応じてバッファを遅延割り当てするか、ユーザーが `Buffer` メソッドで提供するバッファを使用するように変更されたためです。

### `Scan` メソッド内の `scanCalled` 設定とバッファ拡張ロジック

```go
func (s *Scanner) Scan() bool {
	s.scanCalled = true // Scanが呼び出されたことを記録
	// ...
	for {
		// ...
		// バッファ拡張ロジック
		newSize := len(s.buf) * 2 // See protection against overflow in Buffer.
		if newSize == 0 {
			newSize = startBufSize // バッファが空の場合、初期サイズを設定
		}
		if newSize > s.maxTokenSize {
			newSize = s.maxTokenSize
		}
		// ...
	}
}
```
`Scan` メソッドの冒頭で `s.scanCalled = true` が設定され、`Buffer` や `Split` メソッドが `Scan` 呼び出し後に使用されるのを防ぐためのフラグとして機能します。バッファ拡張ロジックでは、`newSize` が `0` の場合に `startBufSize` を使用することで、バッファが初期化されていない状態からでも適切に拡張が開始されるようにしています。

### `Buffer` メソッド

```go
func (s *Scanner) Buffer(buf []byte, max int) {
	if s.scanCalled {
		panic("Buffer called after Scan")
	}
	s.buf = buf[0:cap(buf)]
	// Guarantee no overflow: we multiply len(s.buf) by two in Scan,
	// but only if it exceeds maxTokenSize.
	const maxInt = int(^uint(0) >> 1)
	if max > maxInt {
		max = maxInt
	}
	s.maxTokenSize = max
}
```
この新しいメソッドは、ユーザーが提供するバッファ `buf` を `s.buf` に設定し、`max` を `s.maxTokenSize` に設定します。`s.scanCalled` が `true` の場合はパニックを発生させ、`Scan` 呼び出し後の設定変更を禁止します。`max` の値が `int` の最大値を超えないように保護するロジックも含まれています。

### `Split` メソッドのパニック条件

```go
func (s *Scanner) Split(split SplitFunc) {
	if s.scanCalled {
		panic("Split called after Scan")
	}
	s.split = split
}
```
`Split` メソッドにも `s.scanCalled` のチェックが追加され、`Scan` 呼び出し後の `Split` の変更がパニックを引き起こすようになりました。これにより、`Scanner` の動作の一貫性が保たれます。

### `TestHugeBuffer`

```go
func TestHugeBuffer(t *testing.T) {
	text := strings.Repeat("x", 2*MaxScanTokenSize)
	s := NewScanner(strings.NewReader(text + "\\n"))
	s.Buffer(make([]byte, 100), 3*MaxScanTokenSize)
	for s.Scan() {
		token := s.Text()
		if token != text {
			t.Errorf("scan got incorrect token of length %d", len(token))
		}
	}
	if s.Err() != nil {
		t.Fatal("after scan:", s.Err())
	}
}
```
このテストは、`Buffer` メソッドが正しく機能し、`MaxScanTokenSize` をはるかに超えるサイズのトークンでも、十分な容量を持つユーザー提供バッファと適切な `max` 設定があれば処理できることを確認します。これにより、`Scanner` の柔軟性が向上したことが実証されます。

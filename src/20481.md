# [インデックス 20481] ファイルの概要

このコミットは、Go言語のコードフォーマッタである`gofmt`およびその基盤となる`go/printer`パッケージにおける、マップリテラルのエントリのアライメント（整列）に関する不規則な入力に対する挙動を修正するものです。特に、一行に複数のキー:値ペアが存在する場合の不自然なアライメントを解消し、より予測可能で視覚的に自然なフォーマットを実現します。

## 元コミット内容

```
go/printer, gofmt: don't align map entries for irregular inputs

Details: Until now, when we saw a key:value pair that fit onto
a single line, we assumed that it should be formatted with a
vtab after the ':' for alignment of its value. This leads to
odd behavior if there are more than one such pair on a line.
This CL changes the behavior such that alignment is only used
for the first pair on a line. This preserves existing behavior
(in the std lib we have composite literals where the last line
contains multiple entries and the first entry's value is aligned
with the values on previous lines), and resolves this issue.

No impact on formatting of std lib, go.tools, go.exp, go.net.

Fixes #8685.

LGTM=adonovan
R=adonovan
CC=golang-codereviews
https://golang.org/cl/139430043
```

## 変更の背景

このコミットは、Go言語の公式フォーマッタである`gofmt`が、マップリテラル内のキー:値ペアを整形する際の既存の不具合（Issue #8685）を修正するために導入されました。

これまでの`gofmt`の挙動では、一行に収まるキー:値ペアを見つけると、その値が垂直に整列するようにコロン`:`の後に`vtab`（垂直タブ）を挿入して整形しようとしていました。このアライメントロジックは、通常はコードの可読性を高めるために機能しますが、**一行に複数のキー:値ペアが存在するような「不規則な入力」の場合に、奇妙で不自然なアライメントを引き起こす**という問題がありました。

具体的には、以下のような状況で問題が発生していました。

```go
// 修正前: 不自然なアライメントの例
var _ = T{
    333: 333, 1234: 12, 12345: 0, // 1234: 12 と 12345: 0 のアライメントが崩れる
}
```

このような場合、`gofmt`は最初のペア（`333: 333`）の値は適切にアライメントしようとしますが、同じ行にある後続のペア（`1234: 12`, `12345: 0`）に対しては、そのアライメントロジックが意図しない結果を生み出していました。この不自然な整形は、コードの視覚的な一貫性を損ない、開発者にとって混乱の原因となっていました。

このコミットの目的は、この「奇妙な挙動」を解消し、アライメントが一行の最初のペアにのみ適用されるように変更することです。これにより、既存の標準ライブラリのコード（例えば、最後の行に複数のエントリが含まれ、最初の行の値が前の行の値と整列している複合リテラル）の整形挙動を維持しつつ、Issue #8685で報告された問題を解決します。

## 前提知識の解説

このコミットの理解には、以下のGo言語の概念とツールに関する知識が役立ちます。

### 1. `gofmt`

`gofmt`は、Go言語のソースコードを自動的に整形するためのコマンドラインユーティリティです。Go言語の設計哲学の一つに「意見のある（opinionated）ツール」というものがあり、`gofmt`はその最たる例です。開発者がコードの整形スタイルについて議論する時間をなくし、Goコミュニティ全体で一貫したコードスタイルを維持することを目的としています。`gofmt`は、インデント、スペース、改行、アライメントなどをGoの公式スタイルガイドラインに従って自動的に調整します。

### 2. `go/printer`パッケージ

`go/printer`パッケージは、`gofmt`の内部で利用されるGo標準ライブラリの一部です。このパッケージは、Goの抽象構文木（AST: Abstract Syntax Tree）を「整形して出力する（pretty-print）」機能を提供します。`gofmt`は、まずGoのソースコードをASTにパースし、次に`go/printer`パッケージを使用してそのASTをGoの整形ルールに従って再びソースコードに変換します。つまり、`gofmt`はユーザーが直接操作するツールであり、`go/printer`は実際の整形ロジックを実装する基盤ライブラリです。

### 3. 複合リテラル (Composite Literals)

Go言語において、複合リテラルは、構造体、配列、スライス、マップなどの複合型の値を直接初期化するために使用される構文です。
例えば、マップリテラルは`map[KeyType]ValueType{key1: value1, key2: value2, ...}`のように記述されます。

### 4. マップ (Map)

マップは、キーと値のペアを格納するGoの組み込みデータ構造です。キーは一意であり、値にアクセスするために使用されます。マップリテラルは、マップの初期値を定義する際に使用されます。

### 5. コードのアライメント (Alignment)

コードのアライメントは、コードの特定の要素（この場合はマップのキーと値）を垂直方向に揃えることで、コードの可読性を向上させる整形手法です。`gofmt`は、特に複合リテラルにおいて、コロンや値などを揃えることで、視覚的に構造を理解しやすくするアライメントを適用します。

### 6. `vtab` (Vertical Tab)

`vtab`は垂直タブを意味し、特定の文字位置に垂直に揃えるために使用される制御文字です。`go/printer`では、アライメントを実現するために内部的にこの概念が用いられています。

## 技術的詳細

このコミットが修正する問題は、`go/printer`パッケージがマップリテラルのキー:値ペアを整形する際のアライメントロジックにありました。

**旧来の挙動の問題点:**
これまでの`go/printer`は、一行に収まる`key:value`ペアを見つけると、その`value`を他の行の`value`と垂直に揃えるために、`:`の直後に`vtab`を挿入するという仮定に基づいていました。このアライメント戦略は、各キー:値ペアが独立した行にある場合にはうまく機能します。

しかし、以下のような「不規則な入力」、つまり**一行に複数のキー:値ペアが記述されている場合**に問題が発生しました。

```go
// 旧来のgofmtの挙動（問題発生時）
var _ = T{
    333: 333, 1234: 12, 12345: 0,
}
```

この場合、`gofmt`は最初のペア`333: 333`に対しては適切にアライメントを適用しようとしますが、同じ行にある後続のペア`1234: 12`や`12345: 0`に対しても、同様のアライメントルールを適用しようとします。しかし、これらはすでに同じ行に存在するため、`vtab`の挿入が意図しないスペースを生み出し、結果として不自然な、あるいは崩れたアライメントとなっていました。特に、`1234: 12`と`12345: 0`の`:`や`value`が揃わないという視覚的な不整合が生じていました。

**新しい挙動と修正:**
このコミットは、この問題を解決するために、アライメントの適用条件を変更します。新しい挙動では、**アライメントは一行の最初のキー:値ペアにのみ適用される**ようになります。

変更の核心は、`src/go/printer/nodes.go`内の`exprList`関数にあります。この関数は、複合リテラル内の要素（この場合はマップのエントリ）を処理する役割を担っています。

修正前は、`isPair && size > 0 && len(list) > 1`という条件でアライメントを適用していました。これは「キー:値ペアであり、サイズが0より大きく、リストに複数のエントリがある場合」という条件です。この条件では、同じ行に複数のペアがあっても、それぞれに対してアライメントを試みていました。

修正後は、条件に`needsLinebreak`が追加されました。`needsLinebreak`は、現在の要素が前の要素とは異なる新しい行に開始している場合に`true`となるフラグです。

```go
// 修正後の条件 (src/go/printer/nodes.go)
if len(list) > 1 && isPair && size > 0 && needsLinebreak {
    // ... アライメントロジック ...
} else {
    p.expr0(x, depth) // アライメントしない場合
}
```

この変更により、アライメントは以下の条件をすべて満たす場合にのみ適用されます。
1.  リストに複数のエントリがある (`len(list) > 1`)
2.  現在の要素がキー:値ペアである (`isPair`)
3.  要素のサイズが0より大きい (`size > 0`)
4.  **現在の要素が前の要素とは異なる新しい行に開始している (`needsLinebreak`)**

特に4番目の条件が重要です。これにより、同じ行に複数のキー:値ペアが存在する場合、最初のペアのみがアライメントの対象となり、後続のペアはアライメントされなくなります。これにより、不自然なスペースの挿入が回避され、より自然な整形結果が得られるようになります。

この修正は、既存の標準ライブラリの整形挙動（例えば、複合リテラルの最後の行に複数のエントリが含まれ、最初の行の値が前の行の値と整列しているケース）を維持しつつ、不規則な入力に対する`gofmt`の挙動を改善します。

これらのファイルは、`gofmt`のテストデータです。`declarations.input`は整形前のコード、`declarations.golden`は`gofmt`によって整形された期待される出力です。

このコミットでは、Issue #8685で報告された問題の具体的なテストケースが追加され、それらのケースが新しいアライメントロジックによって正しく整形されることを確認しています。特に、一行に複数のマップエントリがある場合の挙動が修正され、期待される出力が`declarations.golden`に反映されています。

例えば、以下のようなテストケースが追加されています。

```go

var _ = T{0: 0} // not aligned
var _ = T{0: 0, // not aligned
	1: 1, // aligned
	22: 22, // aligned
	333: 333, 1234: 12, 12345: 0, // first on line aligned
}

// test cases form issue 8685
// not aligned
var _ = map[int]string{1: "spring", 2: "summer",
	3: "autumn", 4: "winter"}

// not aligned
var _ = map[string]string{"a": "spring", "b": "summer",
	"c": "autumn", "d": "winter"}

// aligned
var _ = map[string]string{"a": "spring",
	"b": "summer",
	"c": "autumn",
	"d": "winter"}
```
これらのテストケースは、新しいアライメントルールが正しく適用され、一行に複数のエントリがある場合には最初の要素のみがアライメントされ、それ以外はアライメントされないことを示しています。

## コアとなるコードの解説

`src/go/printer/nodes.go`の`exprList`関数は、Goの複合リテラル（構造体、配列、スライス、マップ）の要素を整形する際の中心的なロジックを含んでいます。この関数は、各要素のASTノードを受け取り、それらを適切なフォーマットで出力します。

変更の核心は、マップのキー:値ペアのアライメントを制御する`if`文の条件式にあります。

```go
// 変更前 (簡略化)
// if isPair && size > 0 && len(list) > 1 {
//     // アライメント処理
// } else {
//     // 通常の出力
// }

// 変更後 (簡略化)
// if len(list) > 1 && isPair && size > 0 && needsLinebreak {
//     // アライメント処理
// } else {
//     // 通常の出力
// }
```

ここで追加された`needsLinebreak`変数が、アライメントの挙動を大きく変える鍵となります。

*   **`prevLine := prev.Line`**: ループの開始前に、前の要素の行番号を`prevLine`に格納します。これにより、現在の要素が新しい行に開始しているかどうかを正確に判断するための基準が得られます。
*   **`needsLinebreak := 0 < prevLine && prevLine < line`**: この行は、現在の要素（`x`）が前の要素（`prev`）とは異なる新しい行に存在するかどうかを判断します。
    *   `0 < prevLine`: `prevLine`が有効な行番号であることを確認します（0は無効な行番号を示すことがあります）。
    *   `prevLine < line`: 現在の要素の行番号が前の要素の行番号よりも大きい場合、それは新しい行に開始していることを意味します。
*   **`if len(list) > 1 && isPair && size > 0 && needsLinebreak`**:
    *   `len(list) > 1`: リストに複数のエントリがあることを確認します。単一のエントリの場合はアライメントの必要がありません。
    *   `isPair`: 現在の要素が`key:value`のペア（`ast.KeyValueExpr`）であることを確認します。
    *   `size > 0`: 要素のサイズが0より大きいことを確認します。
    *   **`needsLinebreak`**: **この条件が最も重要です。** これにより、現在のキー:値ペアが前の要素とは異なる新しい行に開始している場合にのみ、アライメント処理（`p.print(pair.Colon, token.COLON, vtab)`による`vtab`の挿入）が実行されます。

このロジックの変更により、一行に複数のキー:値ペアが存在する場合、最初のペアのみが`needsLinebreak`が`true`となるためアライメントの対象となり、同じ行にある後続のペアは`needsLinebreak`が`false`となるためアライメントされなくなります。これにより、不自然な空白の挿入が回避され、`gofmt`の出力がより自然で予測可能なものになります。

*   **`prevLine = line`**: ループの最後に、現在の要素の行番号を`prevLine`に更新します。これは、次のイテレーションで現在の要素が「前の要素」となるため、その行番号を正しく参照できるようにするためです。

この修正は、`gofmt`がGoコードを整形する際の「意見のある」アプローチを維持しつつ、特定のコーナーケースにおける視覚的な不整合を解消する、洗練された改善と言えます。

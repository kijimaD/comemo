## 変更の背景

Goコンパイラは、コードの最適化と効率的なマシンコード生成のためにSSA (Static Single Assignment) フォームを中間表現として利用しています。SSAバックエンドは複雑なシステムであり、継続的な改善とメンテナンスが必要です。このコミットの背景には、以下の目的があります。

1.  **SSA表現の最適化と簡素化**: `ArrayIndex`操作のインデックスを`Value`から`AuxInt`に移行することで、SSAグラフのノード数を減らし、データフロー解析を簡素化し、結果としてコンパイラの最適化パス（特に境界チェックの削除 (Bounds Check Elimination, BCE)）をより効率的に実行できるようにします。`AuxInt`は定数値を直接埋め込むことができるため、インデックスが定数の場合にSSA`Value`として表現する必要がなくなり、SSAグラフがよりコンパクトになります。
2.  **TODOリストの健全化**: 開発プロセスにおいて、TODOリストは未解決の問題や将来の改善点を追跡するために重要です。このコミットでは、対応済みのTODOを削除し、すぐに着手できない、あるいはより詳細な追跡が必要なTODOをバグトラッカーに移行することで、TODOリストの鮮度と実用性を高めています。これは、開発チームが優先順位を明確にし、リソースを適切に配分するために不可欠です。
3.  **コード生成の精度向上**: AMD64アーキテクチャにおけるレジスタクロバリング情報の修正は、コンパイラが生成するアセンブリコードの正確性と効率性を向上させます。特に`FLAGS`レジスタのクロバリングに関する誤った情報が修正されることで、レジスタ割り当て器がより正確な情報を基に動作し、不必要なレジスタの保存・復元を避け、より最適な命令スケジューリングが可能になります。

これらの変更は、Goコンパイラの全体的な性能、保守性、および生成されるコードの品質を向上させることを目的としています。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) フォーム

SSA (Static Single Assignment) は、コンパイラ最適化で広く用いられる中間表現 (IR) の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、以下のような様々な最適化を容易に適用できるようになります。

*   **共通部分式の削除 (Common Subexpression Elimination, CSE)**: 同じ計算が複数回行われている場合、一度だけ計算して結果を再利用する。
*   **デッドコードの削除 (Dead Code Elimination, DCE)**: プログラムの実行に影響を与えないコードを削除する。
*   **定数畳み込み (Constant Folding)**: コンパイル時に計算可能な定数式を事前に計算する。
*   **境界チェックの削除 (Bounds Check Elimination, BCE)**: 配列やスライスへのアクセスが常に有効な範囲内であることが証明できる場合、実行時の境界チェックを省略する。

Goコンパイラは、AST (Abstract Syntax Tree) からSSA形式に変換し、SSA上で多数の最適化パスを実行した後、最終的にマシンコードを生成します。

### `Value`と`AuxInt`

GoコンパイラのSSAバックエンドにおいて、プログラムの各操作は`Value`という構造体で表現されます。`Value`は、操作の種類（`Op`）、型、引数（他の`Value`への参照）、そして補助情報を持つことができます。

*   **`Value`**: SSAグラフのノードであり、特定の操作（例: 加算、ロード、配列アクセス）を表します。`Value`は、その操作の結果を表す値そのものであり、他の`Value`の引数として使用されます。
*   **`AuxInt`**: `Value`構造体の一部であり、整数型の補助情報を格納するために使用されます。これは、操作の種類によっては、その操作に付随する定数（例: オフセット、サイズ、インデックス）を直接埋め込むことで、SSAグラフを簡素化し、特定の最適化を容易にするために使われます。例えば、`OpConst`のような定数値を表す`Value`では、その定数自体が`AuxInt`に格納されます。

このコミットでは、`ArrayIndex`操作のインデックスを`Value`としてではなく、`AuxInt`として直接格納するように変更しています。これにより、インデックスが定数である場合に、そのインデックスを表す別の`Value`ノードを作成する必要がなくなり、SSAグラフがよりコンパクトになります。

### `ArrayIndex`操作

`ArrayIndex`は、GoコンパイラのSSAにおいて、配列やスライスから要素にアクセスする操作を表す`Op`（オペレーションコード）です。例えば、`a[i]`のようなコードは、SSAでは`ArrayIndex`操作として表現されます。この操作は通常、配列（またはスライス）のベースアドレスとインデックスの2つの引数を取ります。

### レジスタクロバリング (Register Clobbering)

レジスタクロバリングとは、ある命令が実行される際に、特定のCPUレジスタの内容が変更（破壊）されることを指します。コンパイラがアセンブリコードを生成し、レジスタ割り当てを行う際には、各命令がどのレジスタをクロバーするか（つまり、どのレジスタの内容を上書きするか）を正確に把握している必要があります。

*   **`FLAGS`レジスタ**: x86-64 (AMD64) アーキテクチャには`FLAGS`レジスタがあり、これは算術演算や比較演算の結果（ゼロフラグ、キャリーフラグ、オーバーフローフラグなど）を格納します。これらのフラグは、条件分岐命令などで利用されます。特定の命令が`FLAGS`レジスタをクロバーするかどうかは、後続の命令が`FLAGS`レジスタの値を正しく利用するために非常に重要です。誤ったクロバリング情報は、不正確なコード生成や、不必要なレジスタの保存・復元を引き起こし、性能低下につながる可能性があります。

### Bounds Check Elimination (BCE)

境界チェックの削除 (BCE) は、Goコンパイラの重要な最適化の一つです。Go言語は、配列やスライスへのアクセス時に実行時境界チェックを義務付けており、これによりメモリ安全性が保証されます。しかし、このチェックはオーバーヘッドを伴います。BCEは、コンパイラが静的に、ある配列アクセスが常に有効な範囲内で行われることを証明できる場合に、その実行時チェックを削除する最適化です。

例えば、ループ内で`for i := 0; i < len(s); i++ { s[i] = ... }`のようなコードがある場合、コンパイラは`i`が常に`0`以上`len(s)`未満であることを推論し、`s[i]`へのアクセスに対する境界チェックを削除できます。`ArrayIndex`操作のインデックスが`AuxInt`として直接埋め込まれることで、コンパイラはより容易にインデックスの値を把握し、BCEを適用できる機会が増える可能性があります。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにいくつかの重要な技術的変更を導入しています。

1.  **`ArrayIndex`操作のインデックス表現の変更**:
    *   以前の`ArrayIndex`操作は、配列（またはスライス）とインデックスの両方を`Value`として受け取っていました。これは、インデックスが変数である場合には適切ですが、インデックスが定数である場合でも、その定数を表す`Value`ノードをSSAグラフ内に作成する必要がありました。
    *   このコミットでは、`ArrayIndex`操作のインデックスを`AuxInt`フィールドに直接格納するように変更しています。これにより、`ArrayIndex`は配列（またはスライス）を表す`Value`を1つだけ引数として取り、インデックスは`AuxInt`として埋め込まれます。
    *   この変更の主な利点は、SSAグラフのノード数を削減し、グラフを簡素化できる点です。特に、インデックスが定数である場合に、余分な`Value`ノードが不要になります。これにより、SSAパスの処理が高速化され、コンパイラのメモリ使用量も削減される可能性があります。
    *   また、インデックスが`AuxInt`として直接利用可能になることで、境界チェックの削除 (BCE) などの最適化パスが、インデックスの定数性をより容易に認識し、適用できる機会が増えることが期待されます。

2.  **SSA TODOリストの整理**:
    *   `src/cmd/compile/internal/ssa/TODO`ファイルは、SSAバックエンドに関する未解決の問題や改善点をリストアップしていました。
    *   このコミットでは、このTODOリストから多くの項目が削除されています。これは、一部の項目が既に解決されたか、あるいはより正式なバグトラッカー（GoのIssueトラッカーなど）に移行されたことを意味します。
    *   TODOリストの整理は、開発チームが現在の作業に集中し、未解決の問題をより効果的に管理するために重要です。これにより、開発の優先順位が明確になり、コンパイラの改善がより体系的に進められます。

3.  **AMD64レジスタクロバリング情報の修正**:
    *   `src/cmd/compile/internal/ssa/gen/AMD64Ops.go`および`src/cmd/compile/internal/ssa/opGen.go`において、特定のAMD64命令（例: `DUFFCOPY`）のレジスタクロバリング情報が修正されています。
    *   具体的には、`DUFFCOPY`のような操作が`FLAGS`レジスタをクロバーしないにもかかわらず、以前はクロバーすると誤ってマークされていました。この修正により、`FLAGS`レジスタがクロバーリストから削除されます。
    *   この変更は、レジスタ割り当て器がより正確な情報に基づいて動作することを保証します。`FLAGS`レジスタが不必要に保存・復元されることを防ぎ、生成されるアセンブリコードの効率を向上させます。これは、特にパフォーマンスが重要な低レベルの操作において、わずかながらも実行速度の改善に寄与する可能性があります。

4.  **SSAリライトルールの更新**:
    *   `src/cmd/compile/internal/ssa/gen/generic.rules`および`src/cmd/compile/internal/ssa/rewritegeneric.go`では、`ArrayIndex`操作の定義変更に伴い、SSAリライトルールが更新されています。
    *   リライトルールは、SSAグラフ内の特定のパターンをより最適化されたパターンに変換するために使用されます。`ArrayIndex`が`AuxInt`を使用するように変更されたため、これに対応するように既存のリライトルールが調整されています。
    *   例えば、`ArrayIndex (Load ptr mem) idx`のようなパターンが、新しい`ArrayIndex`の形式に合わせて`ArrayIndex <t> [0] (Load ptr mem)`のように変更されています。これにより、コンパイラは新しい`ArrayIndex`の表現を正しく処理し、引き続き適切な最適化を適用できます。

これらの技術的変更は、GoコンパイラのSSAバックエンドの内部構造を改善し、より効率的で正確なコード生成を可能にすることで、Goプログラム全体のパフォーマンス向上に貢献します。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更

`s.newValue2(ssa.OpArrayIndex, data.Type.Elem(), data, s.constInt(Types[TINT], 0))` から `s.newValue1I(ssa.OpArrayIndex, data.Type.Elem(), 0, data)` への変更は、`ArrayIndex`操作の構築方法が根本的に変わったことを示しています。
*   `newValue2`は2つの`Value`引数を取る関数です。以前は`ArrayIndex`が配列データとインデックス（`s.constInt(...)`で生成された定数`Value`）の2つの`Value`を引数としていました。
*   `newValue1I`は1つの`Value`引数と1つの`AuxInt`引数を取る関数です。新しい実装では、`ArrayIndex`は配列データ（`data`）を`Value`引数として取り、インデックス`0`を`AuxInt`として直接埋め込んでいます。これは、`ArrayIndex`のインデックスが`AuxInt`として表現されるようになったという、このコミットの主要な変更点を反映しています。

### `src/cmd/compile/internal/ssa/TODO` の変更

このファイルは、GoコンパイラのSSAバックエンドに関するTODOリストでした。多くの行が削除されていることから、これらの項目が解決されたか、あるいはGoのIssueトラッカーなどのより適切な場所に移されたことがわかります。特に、`- OpArrayIndex should take its index in AuxInt, not a full value.` という項目が削除されているのは、まさにこのコミットでその変更が実装されたことを示しています。また、`- remove FLAGS from REP instruction clobbers` も削除されており、これもこのコミットで対応された内容です。

### `src/cmd/compile/internal/ssa/gen/AMD64Ops.go` および `src/cmd/compile/internal/ssa/opGen.go` の変更

これらのファイルは、AMD64アーキテクチャ固有のSSA操作の定義と、一般的なSSA操作の定義を生成するためのものです。
*   `AMD64Ops.go`では、`DUFFCOPY`のような特定の操作の`regInfo`構造体内の`clobbers`フィールドから`FLAGS`が削除されています。これは、これらの操作が実際には`FLAGS`レジスタを破壊しないことを正確に反映するための修正です。これにより、レジスタ割り当て器は`FLAGS`レジスタの値をより長く保持できると判断し、不必要な保存・復元命令を減らすことで、生成されるコードの効率が向上します。
*   `opGen.go`では、`opcodeTable`内の`ArrayIndex`エントリが更新され、`auxType: auxInt64`と`argLen: 1`が設定されています。これは、`ArrayIndex`が`Int64`型の`AuxInt`を持ち、`Value`引数を1つだけ取るという新しい定義を明示しています。

### `src/cmd/compile/internal/ssa/gen/generic.rules` および `src/cmd/compile/internal/ssa/rewritegeneric.go` の変更

これらのファイルは、SSAグラフを最適化するためのリライトルールを定義しています。
*   `generic.rules`では、`ArrayIndex`に関連するリライトルールが変更されています。以前の `(ArrayIndex (Load ptr mem) idx)` というパターンは、インデックス`idx`が`Value`として表現されていることを前提としていました。新しい `(ArrayIndex <t> [0] (Load ptr mem))` というパターンは、`ArrayIndex`が`AuxInt`としてインデックス`0`（この例では定数インデックス）を持つことを示しています。これは、`ArrayIndex`の内部表現の変更に合わせて、リライトルールも適応されたことを意味します。
*   `rewritegeneric.go`の`rewriteValuegeneric_OpArrayIndex`関数も、同様に新しい`ArrayIndex`の形式に対応するように変更されています。特に、`v.AuxInt != 0`のチェックが追加され、`v.Args[1]`（以前のインデックス`Value`）の参照が削除されています。これにより、`ArrayIndex`が`AuxInt`に定数インデックスを持つ場合に、`Load`操作に変換するリライトが正しく適用されるようになります。

これらの変更は、SSAバックエンドの内部的な整合性を保ちつつ、`ArrayIndex`操作の表現をより効率的かつ最適化しやすい形に進化させていることを示しています。

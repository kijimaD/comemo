# [インデックス 26019] ファイルの概要

このコミットは、Goランタイムにおけるワーカーゴルーチン（M）のスレッド起動メカニズムを最適化し、不要なスレッドのウェイクアップを削減することを目的としています。特に、スケジューラがアイドル状態のP（プロセッサ）を見つけた際に、常に新しいワーカーMを起動するのではなく、既にスピンしているMのみが新しいスピンMを起動するように変更することで、システムコール（futex）の発生を大幅に減らし、CPUリソースの消費を抑えています。

## 変更の背景

Goランタイムのスケジューラは、利用可能なハードウェア並列性を最大限に活用するために、必要に応じてOSスレッド（M）を起動します。しかし、以前の実装では、スケジューラが実行可能なゴルーチンを見つけられず、かつ`nmspinning`（スピン中のワーカーMの数）が0の場合に、無条件に新しいワーカーMを起動していました。この挙動は、特に`runtime.Gosched()`のように頻繁にゴルーチンが自発的にCPUを明け渡すようなシナリオにおいて、大量の不要なスレッドウェイクアップを引き起こしていました。

不要なスレッドウェイクアップは、OSのコンテキストスイッチやシステムコール（特に`futex`）のオーバーヘッドを増大させ、プログラムの実行時間を不必要に長くしていました。コミットメッセージに示されているベンチマーク結果は、この問題が顕著であることを明確に示しています。`runtime.Gosched()`を1000万回呼び出す単純なプログラムで、変更前は`futex`システムコールが260万回以上発生し、実行時間も4秒以上かかっていました。これは、Goランタイムの効率性に大きな影響を与えていました。

このコミットは、この非効率性を解消し、スレッドのウェイクアップをより賢く、必要最小限に抑えることで、ランタイムのパフォーマンスを向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスケジューラに関するいくつかの基本的な概念を理解しておく必要があります。

*   **G (Goroutine)**: Goランタイムによって管理される軽量な実行単位です。OSスレッドよりもはるかに軽量で、数百万個作成することも可能です。
*   **M (Machine/OS Thread)**: オペレーティングシステムのスレッドです。GoのゴルーチンはM上で実行されます。MはOSによってスケジューリングされます。
*   **P (Processor)**: 論理プロセッサ、またはコンテキストです。MとGの間の仲介役として機能します。Pは実行可能なGのローカルキューを持ち、MはPにアタッチされてGを実行します。`GOMAXPROCS`環境変数によってPの数を設定できます。
*   **スケジューラ**: GをMに割り当て、実行を管理するGoランタイムのコンポーネントです。
*   **スピン (Spinning)**: Mが実行可能なGを見つけるために、Pのローカルキュー、グローバルキュー、ネットワークポーラーなどを積極的に探し回る状態を指します。この間、MはCPUを占有し、他のMがGを見つけるのを妨げる可能性がありますが、Gがすぐに利用可能になる場合には、OSスレッドのコンテキストスイッチのオーバーヘッドを避けることができます。
*   **`nmspinning`**: スピン中のMの数を追跡するカウンタです。この値は、スケジューラが新しいMを起動すべきかどうかを判断する際に使用されます。
*   **`futex` (Fast Userspace muTEX)**: Linuxカーネルが提供するシステムコールで、ユーザー空間のロックや同期プリミティブを効率的に実装するために使用されます。Goランタイムは、Mのパーク（休止）とアンパーク（再開）に`futex`を利用します。Mが実行可能なGを見つけられない場合、`futex`を使って自身をパークし、Gが利用可能になったときに別のMによってアンパークされます。`futex`の呼び出し回数が多いということは、それだけ多くのMがパークとアンパークを繰り返していることを意味し、これはオーバーヘッドとなります。
*   **`runtime.Gosched()`**: 現在のゴルーチンがCPUを自発的に明け渡し、他のゴルーチンが実行される機会を与える関数です。これはスケジューラに制御を戻します。

## 技術的詳細

このコミットの核心は、GoスケジューラにおけるワーカーMの起動ポリシーの変更です。以前は、`nmspinning == 0`（スピン中のMがいない）の状態でスケジューラが実行された場合、新しいワーカーMが起動される可能性がありました。これは、たとえ実行可能なゴルーチンが一時的に不足しているだけであっても、Mが頻繁に起動・パークされる原因となっていました。

新しいポリシーでは、**スピン中のMのみが新しいスピンMを起動する**ように変更されました。これにより、以下のメカニズムが導入されています。

1.  **`proc.go`の新しいコメントブロック**: `proc.go`の冒頭に「Worker thread parking/unparking」という詳細なコメントブロックが追加されました。これは、ワーカーMのパーク/アンパークに関する設計思想、過去に検討されたが却下されたアプローチ（集中型スケジューラ状態、直接的なゴルーチンハンドオフ、過剰なスレッド起動）、そして現在の採用されたアプローチについて説明しています。
    *   **現在の採用アプローチ**: 新しいゴルーチンが準備され、かつアイドルなPがあり、かつスピン中のワーカーMがいない場合にのみ、追加のMがアンパークされます。アンパークされたMは「スピン中」と見なされ、すぐに仕事を見つけられない場合はパークされます。
    *   **`nmspinning`の役割**: `nmspinning`が1以上の場合（つまり、少なくとも1つのスピン中のMが存在する場合）、新しいゴルーチンが準備されても新しいMはアンパークされません。これを補うため、最後にスピンしていたMが仕事を見つけてスピンを停止した場合、そのMが新しいスピンMをアンパークする責任を負います。
    *   **競合状態の考慮**: スピン状態から非スピン状態へのMの遷移と、新しいゴルーチンの投入が同時に発生する可能性があり、どちらか一方が新しいMをアンパークしないと、CPUが十分に活用されない状態に陥る可能性があります。このため、`nmspinning`のデクリメントとPキューの再チェックの順序、およびメモリバリアの重要性が強調されています。

2.  **`startm`関数の変更**: `startm`関数は、新しいMを起動または既存のMを再開する役割を担います。この関数に`spinning`引数が追加され、呼び出し元が`nmspinning`をインクリメントしたかどうかを伝達するようになりました。
    *   `_p_ == nil`（アイドルなPがない）の場合、`spinning`が`true`であれば、`nmspinning`のインクリメントを元に戻す（デクリメントする）ようになりました。これは、新しいMを起動しても仕事がないため、不要なスピンMを避けるためです。
    *   新しいMを起動する際に、`spinning`が`true`であれば、そのMの`m.spinning`フラグが設定されるようになりました。

3.  **`stopm`および`gcstopm`関数の変更**: これらの関数はMを停止させる際に呼び出されます。以前は`m.spinning`が`true`の場合に`nmspinning`をデクリメントしていましたが、新しいロジックでは`stopm`内で`m.spinning`が`true`であることはエラー（`throw("stopm spinning")`）とされ、`gcstopm`では`nmspinning`のデクリメントがより慎重に行われるようになりました。

4.  **`findrunnable`関数の変更**: `findrunnable`は、実行可能なゴルーチンを見つけるための主要な関数です。この関数内で、Mがスピン状態から非スピン状態に遷移する際のロジックが大幅に修正されました。
    *   `_g_.m.spinning`が`true`の場合、まず`nmspinning`をデクリメントし、その後でPキューを再チェックするようになりました。これは、新しいゴルーチンが投入される競合状態を考慮したものです。
    *   もし新しい仕事が見つかり、かつMが以前スピンしていた場合、`m.spinning`を再度`true`に設定し、`nmspinning`をインクリメントして、新しいワーカーMをアンパークするシグナルを送る可能性があります。

5.  **`resetspinning`関数の変更**: `resetspinning`は、Mがスピン状態を終了する際に呼び出されます。この関数は、Mがスピン状態を終了したときに、必要に応じて別のMをウェイクアップする役割を担います。
    *   以前は`_g_.m.spinning`が`false`の場合でも`nmspinning`をロードしていましたが、変更後は`_g_.m.spinning`が`true`でない場合はエラーをスローするようになりました。
    *   `nmspinning`が0になり、かつアイドルなPが存在する場合にのみ`wakep()`を呼び出すことで、ウェイクアップの条件がより厳格になりました。

6.  **`proc_test.go`への新しいテストケース**: `TestGoroutineParallelism2`が追加されました。このテストは、`GOMAXPROCS`を4に設定し、`runtime.Gosched()`を多用するシナリオや、ネットワークポーリングが有効なシナリオなど、様々な条件下でスケジューラの並列処理能力を検証します。これにより、新しいスケジューリングロジックが意図通りに機能し、デッドロックやパフォーマンス低下を引き起こさないことを確認します。

これらの変更により、Goランタイムは、特にゴルーチンが頻繁にCPUを明け渡すような状況で、より効率的にOSスレッドを管理できるようになりました。結果として、不要な`futex`システムコールの呼び出しが劇的に減少し、全体的なパフォーマンスが向上しています。

## コアとなるコードの解説

このコミットの主要な変更は、`src/runtime/proc.go`内のスケジューリングロジック、特に`startm`、`findrunnable`、`resetspinning`関数に集中しています。

1.  **`startm`の`spinning`引数**:
    `func startm(_p_ *p, spinning bool)`
    この引数は、`startm`が呼び出された時点で、呼び出し元が既に`nmspinning`をインクリメントしているかどうかを示します。これにより、`startm`は新しいMを起動する際に、そのMがスピン状態であるべきかを適切に設定できます。特に、アイドルなPがない場合、`nmspinning`のインクリメントを元に戻すことで、不要なスピンMの起動を防ぎます。

2.  **`findrunnable`におけるスピン状態遷移の「デリケートなダンス」**:
    `findrunnable`関数は、実行可能なゴルーチンを見つけるためにMが呼び出す中心的な関数です。この関数内で、Mがスピン状態から非スピン状態に遷移する際のロジックが非常に重要です。
    *   `wasSpinning := _g_.m.spinning`：現在のMがスピン中であったかを記録します。
    *   `if _g_.m.spinning { _g_.m.spinning = false; atomic.Xadd(&sched.nmspinning, -1) }`：Mがスピン状態であれば、まず`m.spinning`を`false`にし、`nmspinning`をデクリメントします。この順序が重要で、`nmspinning`を先にデクリメントすることで、他のスレッドが新しいゴルーチンを投入した際に、誰もMをアンパークしないという競合状態を防ぎます。
    *   その後、Pのローカルキューやグローバルキューを再チェックし、新しい仕事がないか確認します。
    *   `if wasSpinning { _g_.m.spinning = true; atomic.Xadd(&sched.nmspinning, 1) }`：もし新しい仕事が見つかり、かつMが以前スピンしていた場合、`m.spinning`を`true`に戻し、`nmspinning`をインクリメントします。これは、複数のゴルーチンが飢餓状態にある可能性があるため、別のワーカーMをアンパークする必要があることを`resetspinning`に伝えるシグナルとなります。ただし、システムが完全にロードされており、アイドルなPがない場合は、現在のスレッドをパークしても問題ありません。

3.  **`resetspinning`の厳格化**:
    `resetspinning`は、Mがスピン状態を終了する際に呼び出されます。変更前は、Mがスピン状態であるかどうかにかかわらず`nmspinning`を操作する可能性がありましたが、変更後は`if !_g_.m.spinning { throw("resetspinning: not a spinning m") }`というチェックが追加され、Mがスピン状態である場合にのみこの関数が呼び出されることを保証します。
    また、`if nmspinning == 0 && atomic.Load(&sched.npidle) > 0 { wakep() }`という条件により、`nmspinning`が0になり、かつアイドルなPが存在する場合にのみ`wakep()`（新しいMを起動する可能性のある関数）が呼び出されるようになりました。これにより、不要なMのウェイクアップがさらに抑制されます。

これらの変更は、GoスケジューラがOSスレッドをより効率的に管理し、特に`runtime.Gosched()`のような頻繁なゴルーチン切り替えが発生するシナリオでのシステムコールオーバーヘッドを大幅に削減することに貢献しています。

## 変更の背景

Goランタイムのスケジューラは、利用可能なハードウェア並列性を最大限に活用するために、必要に応じてOSスレッド（M）を起動します。しかし、以前の実装では、スケジューラが実行可能なゴルーチンを見つけられず、かつ`nmspinning`（スピン中のワーカーMの数）が0の場合に、無条件に新しいワーカーMを起動していました。この挙動は、特に`runtime.Gosched()`のように頻繁にゴルーチンが自発的にCPUを明け渡すようなシナリオにおいて、大量の不要なスレッドウェイクアップを引き起こしていました。

不要なスレッドウェイクアップは、OSのコンテキストスイッチやシステムコール（特に`futex`）のオーバーヘッドを増大させ、プログラムの実行時間を不必要に長くしていました。コミットメッセージに示されているベンチマーク結果は、この問題が顕著であることを明確に示しています。`runtime.Gosched()`を1000万回呼び出す単純なプログラムで、変更前は`futex`システムコールが260万回以上発生し、実行時間も4秒以上かかっていました。これは、Goランタイムの効率性に大きな影響を与えていました。

このコミットは、この非効率性を解消し、スレッドのウェイクアップをより賢く、必要最小限に抑えることで、ランタイムのパフォーマンスを向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスケジューラに関するいくつかの基本的な概念を理解しておく必要があります。

*   **G (Goroutine)**: Goランタイムによって管理される軽量な実行単位です。OSスレッドよりもはるかに軽量で、数百万個作成することも可能です。
*   **M (Machine/OS Thread)**: オペレーティングシステムのスレッドです。GoのゴルーチンはM上で実行されます。MはOSによってスケジューリングされます。
*   **P (Processor)**: 論理プロセッサ、またはコンテキストです。MとGの間の仲介役として機能します。Pは実行可能なGのローカルキューを持ち、MはPにアタッチされてGを実行します。`GOMAXPROCS`環境変数によってPの数を設定できます。
*   **スケジューラ**: GをMに割り当て、実行を管理するGoランタイムのコンポーネントです。
*   **スピン (Spinning)**: Mが実行可能なGを見つけるために、Pのローカルキュー、グローバルキュー、ネットワークポーラーなどを積極的に探し回る状態を指します。この間、MはCPUを占有し、他のMがGを見つけるのを妨げる可能性がありますが、Gがすぐに利用可能になる場合には、OSスレッドのコンテキストスイッチのオーバーヘッドを避けることができます。
*   **`nmspinning`**: スピン中のMの数を追跡するカウンタです。この値は、スケジューラが新しいMを起動すべきかどうかを判断する際に使用されます。
*   **`futex` (Fast Userspace muTEX)**: Linuxカーネルが提供するシステムコールで、ユーザー空間のロックや同期プリミティブを効率的に実装するために使用されます。Goランタイムは、Mのパーク（休止）とアンパーク（再開）に`futex`を利用します。Mが実行可能なGを見つけられない場合、`futex`を使って自身をパークし、Gが利用可能になったときに別のMによってアンパークされます。`futex`の呼び出し回数が多いということは、それだけ多くのMがパークとアンパークを繰り返していることを意味し、これはオーバーヘッドとなります。
*   **`runtime.Gosched()`**: 現在のゴルーチンがCPUを自発的に明け渡し、他のゴルーチンが実行される機会を与える関数です。これはスケジューラに制御を戻します。

## 技術的詳細

このコミットの核心は、GoスケジューラにおけるワーカーMの起動ポリシーの変更です。以前は、`nmspinning == 0`（スピン中のMがいない）の状態でスケジューラが実行された場合、新しいワーカーMが起動される可能性がありました。これは、たとえ実行可能なゴルーチンが一時的に不足しているだけであっても、Mが頻繁に起動・パークされる原因となっていました。

新しいポリシーでは、**スピン中のMのみが新しいスピンMを起動する**ように変更されました。これにより、以下のメカニズムが導入されています。

1.  **`proc.go`の新しいコメントブロック**: `proc.go`の冒頭に「Worker thread parking/unparking」という詳細なコメントブロックが追加されました。これは、ワーカーMのパーク/アンパークに関する設計思想、過去に検討されたが却下されたアプローチ（集中型スケジューラ状態、直接的なゴルーチンハンドオフ、過剰なスレッド起動）、そして現在の採用されたアプローチについて説明しています。
    *   **現在の採用アプローチ**: 新しいゴルーチンが準備され、かつアイドルなPがあり、かつスピン中のワーカーMがいない場合にのみ、追加のMがアンパークされます。アンパークされたMは「スピン中」と見なされ、すぐに仕事を見つけられない場合はパークされます。
    *   **`nmspinning`の役割**: `nmspinning`が1以上の場合（つまり、少なくとも1つのスピン中のMが存在する場合）、新しいゴルーチンが準備されても新しいMはアンパークされません。これを補うため、最後にスピンしていたMが仕事を見つけてスピンを停止した場合、そのMが新しいスピンMをアンパークする責任を負います。
    *   **競合状態の考慮**: スピン状態から非スピン状態へのMの遷移と、新しいゴルーチンの投入が同時に発生する可能性があり、どちらか一方が新しいMをアンパークしないと、CPUが十分に活用されない状態に陥る可能性があります。このため、`nmspinning`のデクリメントとPキューの再チェックの順序、およびメモリバリアの重要性が強調されています。

2.  **`startm`関数の変更**: `startm`関数は、新しいMを起動または既存のMを再開する役割を担います。この関数に`spinning`引数が追加され、呼び出し元が`nmspinning`をインクリメントしたかどうかを伝達するようになりました。
    *   `_p_ == nil`（アイドルなPがない）の場合、`spinning`が`true`であれば、`nmspinning`のインクリメントを元に戻す（デクリメントする）ようになりました。これは、新しいMを起動しても仕事がないため、不要なスピンMを避けるためです。
    *   新しいMを起動する際に、`spinning`が`true`であれば、そのMの`m.spinning`フラグが設定されるようになりました。

3.  **`stopm`および`gcstopm`関数の変更**: これらの関数はMを停止させる際に呼び出されます。以前は`m.spinning`が`true`の場合に`nmspinning`をデクリメントしていましたが、新しいロジックでは`stopm`内で`m.spinning`が`true`であることはエラー（`throw("stopm spinning")`）とされ、`gcstopm`では`nmspinning`のデクリメントがより慎重に行われるようになりました。

4.  **`findrunnable`関数の変更**: `findrunnable`は、実行可能なゴルーチンを見つけるための主要な関数です。この関数内で、Mがスピン状態から非スピン状態に遷移する際のロジックが大幅に修正されました。
    *   `_g_.m.spinning`が`true`の場合、まず`nmspinning`をデクリメントし、その後でPキューを再チェックするようになりました。これは、新しいゴルーチンが投入される競合状態を考慮したものです。
    *   もし新しい仕事が見つかり、かつMが以前スピンしていた場合、`m.spinning`を再度`true`に設定し、`nmspinning`をインクリメントして、新しいワーカーMをアンパークするシグナルを送る可能性があります。ただし、システムが完全にロードされており、アイドルなPがない場合は、現在のスレッドをパークしても問題ありません。

5.  **`resetspinning`関数の変更**: `resetspinning`は、Mがスピン状態を終了する際に呼び出されます。この関数は、Mがスピン状態を終了したときに、必要に応じて別のMをウェイクアップする役割を担います。
    *   以前は`_g_.m.spinning`が`false`の場合でも`nmspinning`をロードしていましたが、変更後は`_g_.m.spinning`が`true`でない場合はエラーをスローするようになりました。
    *   `nmspinning`が0になり、かつアイドルなPが存在する場合にのみ`wakep()`を呼び出すことで、ウェイクアップの条件がより厳格になりました。

6.  **`proc_test.go`への新しいテストケース**: `TestGoroutineParallelism2`が追加されました。このテストは、`GOMAXPROCS`を4に設定し、`runtime.Gosched()`を多用するシナリオや、ネットワークポーリングが有効なシナリオなど、様々な条件下でスケジューラの並列処理能力を検証します。これにより、新しいスケジューリングロジックが意図通りに機能し、デッドロックやパフォーマンス低下を引き起こさないことを確認します。

これらの変更により、Goランタイムは、特にゴルーチンが頻繁にCPUを明け渡すような状況で、より効率的にOSスレッドを管理できるようになりました。結果として、不要な`futex`システムコールの呼び出しが劇的に減少し、全体的なパフォーマンスが向上しています。

## コアとなるコードの解説

このコミットの主要な変更は、`src/runtime/proc.go`内のスケジューリングロジック、特に`startm`、`findrunnable`、`resetspinning`関数に集中しています。

1.  **`startm`の`spinning`引数**:
    `func startm(_p_ *p, spinning bool)`
    この引数は、`startm`が呼び出された時点で、呼び出し元が既に`nmspinning`をインクリメントしているかどうかを示します。これにより、`startm`は新しいMを起動する際に、そのMがスピン状態であるべきかを適切に設定できます。特に、アイドルなPがない場合、`nmspinning`のインクリメントを元に戻すことで、不要なスピンMの起動を防ぎます。

2.  **`findrunnable`におけるスピン状態遷移の「デリケートなダンス」**:
    `findrunnable`関数は、実行可能なゴルーチンを見つけるためにMが呼び出す中心的な関数です。この関数内で、Mがスピン状態から非スピン状態に遷移する際のロジックが非常に重要です。
    *   `wasSpinning := _g_.m.spinning`：現在のMがスピン中であったかを記録します。
    *   `if _g_.m.spinning { _g_.m.spinning = false; atomic.Xadd(&sched.nmspinning, -1) }`：Mがスピン状態であれば、まず`m.spinning`を`false`にし、`nmspinning`をデクリメントします。この順序が重要で、`nmspinning`を先にデクリメントすることで、他のスレッドが新しいゴルーチンを投入した際に、誰もMをアンパークしないという競合状態を防ぎます。
    *   その後、Pのローカルキューやグローバルキューを再チェックし、新しい仕事がないか確認します。
    *   `if wasSpinning { _g_.m.spinning = true; atomic.Xadd(&sched.nmspinning, 1) }`：もし新しい仕事が見つかり、かつMが以前スピンしていた場合、`m.spinning`を`true`に戻し、`nmspinning`をインクリメントします。これは、複数のゴルーチンが飢餓状態にある可能性があるため、別のワーカーMをアンパークする必要があることを`resetspinning`に伝えるシグナルとなります。ただし、システムが完全にロードされており、アイドルなPがない場合は、現在のスレッドをパークしても問題ありません。

3.  **`resetspinning`の厳格化**:
    `resetspinning`は、Mがスピン状態を終了する際に呼び出されます。変更前は、Mがスピン状態であるかどうかにかかわらず`nmspinning`を操作する可能性がありましたが、変更後は`if !_g_.m.spinning { throw("resetspinning: not a spinning m") }`というチェックが追加され、Mがスピン状態である場合にのみこの関数が呼び出されることを保証します。
    また、`if nmspinning == 0 && atomic.Load(&sched.npidle) > 0 { wakep() }`という条件により、`nmspinning`が0になり、かつアイドルなPが存在する場合にのみ`wakep()`（新しいMを起動する可能性のある関数）が呼び出されるようになりました。これにより、不要なMのウェイクアップがさらに抑制されます。

これらの変更は、GoスケジューラがOSスレッドをより効率的に管理し、特に`runtime.Gosched()`のような頻繁なゴルーチン切り替えが発生するシナリオでのシステムコールオーバーヘッドを大幅に削減することに貢献しています。

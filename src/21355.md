# [インデックス 21355] ファイルの概要

このコミットは、GoランタイムにおけるWindowsシステムコール（syscall）の処理方法に関する重要な変更を導入しています。具体的には、`src/runtime/thunk_windows.s` というアセンブリファイルが削除され、その機能が `src/runtime/syscall_windows.go` 内のGoコードに `//go:linkname` ディレクティブを使用して統合されました。

## コミット

このコミットは、Windows環境におけるGoのシステムコール実装から、中間的なアセンブリサンク（thunk）ファイル `thunk_windows.s` を削除し、その機能を `syscall_windows.go` 内のGoコードに直接リンクさせるように変更しました。これにより、コードの簡素化と保守性の向上が図られています。

## 変更の背景

Go言語は、クロスプラットフォーム対応を重視しており、各オペレーティングシステム（OS）のネイティブ機能にアクセスするためのメカニズムを提供しています。Windows環境では、GoプログラムがWindows APIを呼び出すために、`syscall` パッケージが使用されます。

以前のGoのWindowsシステムコール実装では、`syscall` パッケージの公開関数（例: `syscall.Syscall`）が、`runtime` パッケージ内の対応する非公開関数（例: `runtime.syscall_Syscall`）を呼び出すために、`thunk_windows.s` というアセンブリファイルに定義された「サンク（thunk）」と呼ばれる小さなアセンブリコードの断片を介していました。このサンクは、`syscall` パッケージから `runtime` パッケージへの呼び出しを仲介する役割を担っていました。

このアセンブリサンクの存在は、以下のような課題を抱えていました。

1.  **複雑性の増加**: アセンブリコードは、Goコードに比べて可読性が低く、デバッグやメンテナンスが困難になる傾向があります。
2.  **ビルドプロセスの複雑化**: アセンブリファイルは、Goコンパイラとは異なるアセンブラによって処理される必要があり、ビルドプロセスに余分なステップを追加します。
3.  **最適化の機会の損失**: 中間的なアセンブリサンクを介することで、コンパイラが直接リンクする場合に比べて、最適化の機会が失われる可能性がありました。

このコミットの目的は、`thunk_windows.s` のアセンブリサンクを削除し、Goコンパイラが提供する `//go:linkname` ディレクティブを利用して、`syscall` パッケージから `runtime` パッケージの関数へ直接リンクさせることで、これらの課題を解決し、コードベースを簡素化することにありました。

## 前提知識の解説

### 1. システムコール (System Call)

システムコールは、オペレーティングシステム（OS）のカーネルが提供するサービスを、ユーザー空間のプログラムが利用するためのインターフェースです。ファイル操作、メモリ管理、プロセス制御、ネットワーク通信など、OSの基本的な機能のほとんどはシステムコールを通じて提供されます。Go言語では、`syscall` パッケージがこれらのOS固有のシステムコールへのアクセスを提供します。

### 2. サンク (Thunk)

サンクは、主にアセンブリ言語で記述された小さなコードの断片で、ある関数呼び出しを別の関数呼び出しに変換したり、異なる呼び出し規約を持つ関数間で引数を調整したりするために使用されます。Windowsプログラミング、特にCOM（Component Object Model）やDLL（Dynamic Link Library）の呼び出しにおいて、異なるモジュール間や言語間でのインターフェースを橋渡しするためによく用いられます。この文脈では、`syscall` パッケージから `runtime` パッケージの関数への呼び出しを仲介する役割を担っていました。

### 3. `//go:linkname` ディレクティブ

`//go:linkname` はGoコンパイラに対する特殊なディレクティブ（指示）です。これは、Goのリンカに対して、特定のシンボル（関数や変数）を、通常のエクスポートルールに反して、別のパッケージのシンボルにリンクさせるように指示します。

通常、Goではパッケージ間でエクスポートされていない（小文字で始まる）シンボルに直接アクセスすることはできません。しかし、`//go:linkname` を使用すると、この制約をバイパスし、非公開の関数や変数にアクセスできるようになります。これは、Goの標準ライブラリ、特に `runtime` パッケージと他の低レベルパッケージ（`syscall` など）の間で、パフォーマンスや実装の都合上、密接な連携が必要な場合に利用されます。

構文は以下の通りです。

```go
//go:linkname localname importpath.name
```

-   `localname`: 現在のパッケージ内のシンボル名。
-   `importpath.name`: リンクしたい外部パッケージのシンボル名（`importpath` はパッケージのパス、`name` はシンボル名）。

このディレクティブは、Goの言語仕様の一部ではなく、コンパイラ固有の機能であり、通常はGoの内部実装や低レベルのシステムプログラミングでのみ使用されます。誤用すると、予期せぬ動作や将来のGoバージョンの変更による互換性の問題を引き起こす可能性があるため、注意が必要です。

### 4. Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するGo言語の不可欠な部分です。これには、ガベージコレクション、ゴルーチン（軽量スレッド）のスケジューリング、チャネル通信、メモリ割り当て、システムコールインターフェースなどが含まれます。Goプログラムは、OSと直接やり取りするのではなく、ランタイムを介してOSサービスを利用します。

## 技術的詳細

このコミットの技術的な核心は、Windowsシステムコール呼び出しのパスからアセンブリサンク `thunk_windows.s` を排除し、`//go:linkname` ディレクティブによってGoコード内で直接リンクを確立した点にあります。

以前は、`syscall` パッケージの関数（例: `syscall.Syscall`）が呼び出されると、その呼び出しは `thunk_windows.s` 内のアセンブリコードにジャンプしていました。このアセンブリコードは、引数を適切に設定し、最終的に `runtime` パッケージ内の対応する非公開関数（例: `runtime.syscall_Syscall`）にジャンプしていました。これは、Goのリンカが異なるパッケージ間の非公開シンボルを直接リンクできないという制約を回避するための一般的な手法でした。

このコミットでは、`thunk_windows.s` が完全に削除されました。代わりに、`src/runtime/syscall_windows.go` 内の `runtime` パッケージの関数定義の直前に、以下のような `//go:linkname` ディレクティブが追加されました。

```go
//go:linkname compileCallback syscall.compileCallback
//go:linkname syscall_loadlibrary syscall.loadlibrary
//go:linkname syscall_getprocaddress syscall.getprocaddress
//go:linkname syscall_Syscall syscall.Syscall
//go:linkname syscall_Syscall6 syscall.Syscall6
//go:linkname syscall_Syscall9 syscall.Syscall9
//go:linkname syscall_Syscall12 syscall.Syscall12
//go:linkname syscall_Syscall15 syscall.Syscall15
```

これらのディレクティブは、Goコンパイラとリンカに対して、`runtime` パッケージ内の対応する関数（例: `runtime.compileCallback`）が、`syscall` パッケージ内の同じ名前の関数（例: `syscall.compileCallback`）と実質的に同じシンボルとして扱われるべきであることを指示します。これにより、`syscall` パッケージから `syscall.Syscall` などを呼び出す際に、中間のアセンブリサンクを介することなく、直接 `runtime.syscall_Syscall` の実装にジャンプできるようになります。

この変更の利点は以下の通りです。

*   **コードの簡素化**: アセンブリコードの削除により、GoのコードベースがよりGoらしいコードに統一され、可読性とメンテナンス性が向上します。
*   **ビルドプロセスの効率化**: アセンブリファイルのコンパイルステップが不要になり、ビルド時間がわずかに短縮される可能性があります。
*   **パフォーマンスの向上**: アセンブリサンクを介する間接的なジャンプがなくなることで、ごくわずかではありますが、システムコール呼び出しのオーバーヘッドが削減される可能性があります。
*   **Goコンパイラの進化**: `//go:linkname` のようなコンパイラディレクティブが成熟し、以前はアセンブリでしか実現できなかった低レベルのリンキングをGoコード内で直接行えるようになったことを示しています。

この変更は、GoのWindowsポートの成熟と、Goコンパイラおよびランタイムの内部実装の洗練を反映しています。

## コアとなるコードの解説

この変更の核心は、`//go:linkname` ディレクティブの導入によって、Goのリンカが異なるパッケージ間の非公開シンボルを直接解決できるようになったことです。

以前の `thunk_windows.s` ファイルは、`syscall` パッケージの公開関数（例: `syscall.Syscall`）が呼び出されたときに、`runtime` パッケージの対応する非公開関数（例: `runtime.syscall_Syscall`）に制御を移すためのアセンブリジャンプ命令を含んでいました。これは、Goのリンカがデフォルトではパッケージ境界を越えて非公開シンボルをリンクしないため、必要な仲介役でした。

`//go:linkname` ディレクティブが `src/runtime/syscall_windows.go` に追加されたことで、Goコンパイラとリンカは、`runtime` パッケージ内の特定の関数（例: `runtime.syscall_Syscall`）が、`syscall` パッケージ内の同じ名前の関数（例: `syscall.Syscall`）と「同じ実体」であると認識するようになります。これにより、`syscall` パッケージから `syscall.Syscall` が呼び出された際に、リンカは直接 `runtime` パッケージ内の `syscall_Syscall` の実装に解決し、アセンブリサンクを介する必要がなくなりました。

この変更は、Goのコンパイラとリンカの機能が進化し、より洗練された低レベルのリンキングをGoコード内で直接表現できるようになったことを示しています。これにより、アセンブリコードの量を減らし、Goのコードベース全体の一貫性と保守性を向上させることができます。

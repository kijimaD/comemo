# [インデックス 21386] ファイルの概要

このコミットは、GoランタイムにおけるPlan 9固有のビルド問題を解決するために、`atoi`関数の名前を`_atoi`に変更するものです。以前の変更で`goatoi`が`atoi`にリネームされた結果、Plan 9のシステムライブラリに存在する`atoi`関数との名前衝突が発生しました。このコミットは、その衝突を解消し、Plan 9上でのGoのビルドを可能にします。

## 元コミット内容

Goランタイムにおいて、`atoi`関数をPlan 9向けに`_atoi`にリネームする。これは、以前の変更（Change 2154）で`goatoi`関数が`atoi`にリネームされたことに起因する。この新しい`atoi`の定義が、Plan 9ランタイムに存在する`atoi`関数（`string`ではなく`[]byte`を引数にとる）と衝突するため、Plan 9でのビルドが失敗していた。この変更により、Plan 9でのビルドが修正される。

## 変更の背景

このコミットの背景には、Go言語のランタイムが異なるオペレーティングシステム（OS）環境で正しく動作するための互換性の問題があります。具体的には、Goの内部で文字列を整数に変換する`atoi`（ASCII to Integer）という名前の関数が、Plan 9という特定のOS環境で提供されている同名の関数と衝突したことが原因です。

以前のコミット（Change 2154）で、Goランタイム内の`goatoi`という関数が、より一般的な名前である`atoi`にリネームされました。これは、Goのコードベース全体での一貫性や可読性を向上させるための変更だったと推測されます。しかし、このリネームがPlan 9環境に特有の問題を引き起こしました。

Plan 9は、ベル研究所で開発された分散オペレーティングシステムであり、そのC言語の標準ライブラリには、文字列を整数に変換するための`atoi`関数が既に存在します。このPlan 9の`atoi`関数は、Goの`string`型とは異なる`[]byte`（バイトスライス）を引数として受け取るシグネチャを持っています。

Goランタイム内で`atoi`という名前の関数が定義された際、Plan 9のビルドプロセスは、Goが定義した`atoi`とPlan 9システムが提供する`atoi`のどちらを使用すべきか判断できなくなり、名前衝突（シンボル衝突）が発生しました。この衝突により、Plan 9環境でGoのプログラムをコンパイルする際にビルドエラーが発生し、Goの移植性が損なわれる事態となりました。

このコミットは、この特定の名前衝突を解消し、GoがPlan 9上で引き続き正しくビルドされ、動作するようにするための修正です。

## 前提知識の解説

### `atoi`関数とは

`atoi`は "ASCII to Integer" の略で、文字列形式の数値を整数型に変換するための関数です。多くのプログラミング言語やC言語の標準ライブラリで提供されており、例えば"123"という文字列を数値の123に変換する際に使用されます。

### Go言語における`string`と`[]byte`

Go言語には、文字列を扱うための主要な2つの型があります。
*   **`string`型**: Goの`string`は不変なバイトスライスであり、通常はUTF-8エンコードされたテキストを表します。文字列リテラル（例: `"hello"`）は`string`型です。
*   **`[]byte`型**: バイトスライスは可変なバイトのシーケンスです。ファイルの内容の読み書き、ネットワーク通信、バイナリデータの処理など、生のバイトデータを扱う際によく使用されます。`string`と`[]byte`は相互に変換可能ですが、異なる型として扱われます。

### Plan 9オペレーティングシステム

Plan 9は、ベル研究所で開発された分散オペレーティングシステムです。Unixの概念をさらに推し進め、すべてのリソース（ファイル、デバイス、ネットワーク接続など）をファイルシステムとして表現するという特徴を持っています。Go言語は、Unix系OSだけでなく、Plan 9のような他のOS環境への移植性も重視しており、Goランタイムは各OSの特性に合わせて調整されています。Plan 9のC言語環境では、標準ライブラリの関数シグネチャが他のUnix系OSと異なる場合があります。

### Goランタイムの役割

Goランタイムは、Goプログラムの実行を管理する低レベルのコンポーネントです。ガベージコレクション、スケジューリング、メモリ管理、システムコールインターフェースなど、Goプログラムが動作するために必要な多くの機能を提供します。OS固有の処理は、ランタイム内のOS固有のファイル（例: `src/runtime/os1_plan9.go`）で実装されます。

### 以前の変更 (Change 2154)

コミットメッセージに記載されている「Change 2154」は、Goのコードレビューシステム（Gerrit）における変更セットのIDを指します。この変更で、Goランタイム内部の`goatoi`という関数が`atoi`という名前にリネームされました。このリネーム自体は、Goのコードベース内での命名規則の統一や、より直感的な関数名への変更を目的としていたと考えられます。しかし、この変更がPlan 9環境での名前衝突を引き起こすことになりました。

## 技術的詳細

この問題の核心は、Goのランタイムが内部的に使用する`atoi`関数のシグネチャと、Plan 9のシステムライブラリが提供する`atoi`関数のシグネチャが異なる点にあります。

1.  **Goランタイムの`atoi` (リネーム後)**: 以前の`goatoi`が`atoi`にリネームされた際、この関数はGoの`string`型を引数として受け取るように設計されていた可能性が高いです。Goの標準ライブラリでは、`strconv.Atoi`が`string`を引数にとるのが一般的です。Goランタイム内部の`atoi`も、これに準拠していたと考えられます。

2.  **Plan 9のシステム`atoi`**: Plan 9のC言語環境における`atoi`関数は、C言語の文字列（`char *`）を引数として受け取ります。Goの文脈では、これは`[]byte`型に相当します。つまり、Plan 9の`atoi`は`func atoi([]byte) int`のようなシグネチャを持つと解釈できます。

3.  **名前衝突とビルドエラー**: GoのプログラムがPlan 9上でコンパイルされる際、Goランタイムは`src/runtime/os1_plan9.go`のようなOS固有のコードをリンクします。このとき、Goランタイムが定義した`atoi`と、Plan 9のシステムライブラリが提供する`atoi`が両方とも同じ名前で存在するため、リンカがどちらの`atoi`を使用すべきか判断できなくなり、シンボル衝突エラーが発生します。これは、関数名が同じであるにもかかわらず、期待される引数の型（`string` vs `[]byte`）が異なるために、互換性のない定義が複数存在することになります。

4.  **解決策**: この問題を解決するためには、GoランタイムがPlan 9向けに定義する`atoi`関数の名前を変更し、Plan 9システムライブラリの`atoi`との衝突を避ける必要があります。このコミットでは、Goランタイム内の`atoi`を`_atoi`にリネームすることで、この衝突を解消しています。これにより、GoのコードはGoランタイムが提供する`_atoi`を使用し、Plan 9システムライブラリの`atoi`とは明確に区別されるようになります。

この修正は、Goのクロスプラットフォーム対応において、各OSのシステムライブラリとの潜在的な名前衝突を考慮することの重要性を示しています。

## コアとなるコードの変更箇所

変更は`src/runtime/os1_plan9.go`ファイルに集中しています。

```diff
--- a/src/runtime/os1_plan9.go
+++ b/src/runtime/os1_plan9.go
@@ -70,7 +70,7 @@ func getpid() uint64 {
 	for c[0] == ' ' || c[0] == '\t' {
 		c = c[1:]
 	}
-	return uint64(atoi(c))
+	return uint64(_atoi(c))
 }

 func osinit() {
@@ -254,7 +254,7 @@ func badsignal2() {
 	exits(&_badsignal[0])
 }

-func atoi(b []byte) int {
+func _atoi(b []byte) int {
 	n := 0
 	for len(b) > 0 && '0' <= b[0] && b[0] <= '9' {
 		n = n*10 + int(b[0]) - '0'
```

具体的には、以下の2箇所が変更されています。

1.  `getpid()`関数内で`atoi(c)`を呼び出していた箇所が`_atoi(c)`に変更されました。
2.  `func atoi(b []byte) int`として定義されていた関数が`func _atoi(b []byte) int`にリネームされました。

## コアとなるコードの解説

このコミットの目的は、GoランタイムがPlan 9向けに提供する`atoi`関数と、Plan 9のシステムライブラリが提供する`atoi`関数との間の名前衝突を解決することです。

*   **`func atoi(b []byte) int` から `func _atoi(b []byte) int` へのリネーム**:
    これがこのコミットの主要な変更点です。Goランタイム内部で定義されていた`atoi`関数（これは`[]byte`を引数にとる、Plan 9の`atoi`とシグネチャが一致するGoの内部関数）の名前が`_atoi`に変更されました。これにより、Goのコードがこの内部関数を呼び出す際に、Plan 9システムライブラリの`atoi`と混同されることがなくなります。アンダースコア（`_`）をプレフィックスとして付けることは、Goの慣習として、パッケージ外からはエクスポートされない（内部的に使用される）関数であることを示すためにも使われますが、この場合は特に名前衝突を避けるための明確な意図があります。

*   **`getpid()`関数内の呼び出し箇所の変更**:
    `getpid()`関数は、現在のプロセスのIDを取得するためのOS固有の処理を行う関数です。この関数内で、文字列形式のプロセスIDを整数に変換するために、Goランタイム内部の`atoi`関数が使用されていました。関数名が`_atoi`に変更されたため、この呼び出し箇所も`atoi(c)`から`_atoi(c)`に更新されました。これにより、`getpid()`関数は正しくリネームされた内部関数を呼び出すようになります。

この変更により、Goのビルドシステムは、Plan 9のシステムライブラリが提供する`atoi`と、Goランタイムが内部的に使用する`_atoi`を明確に区別できるようになり、Plan 9環境でのコンパイルエラーが解消されます。これは、Goのクロスプラットフォーム互換性を維持するための、細部にわたる調整の一例です。

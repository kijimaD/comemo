## 変更の背景

Go言語は、様々なアーキテクチャで動作するように設計されています。一部のCPUアーキテクチャ、特に古いARMv5/ARMv6のような組み込みシステム向けのものは、ハードウェアによる浮動小数点演算ユニット（FPU）を持たないか、非常に限定的なFPUしか持たない場合があります。このような環境では、浮動小数点演算をソフトウェアでエミュレートする必要があり、これを「ソフトフロート」と呼びます。

Goランタイムには、このような環境で浮動小数点演算をサポートするためのソフトフロート実装が含まれていました。初期のGoランタイムでは、パフォーマンス上の理由や既存のコードベースの再利用のために、一部の低レベルな処理がC言語で実装されていることがありました。しかし、Go言語の成熟とコンパイラの最適化の進歩に伴い、C言語で書かれた部分を純粋なGoコードに置き換えることで、コードベースの一貫性、保守性、そしてGoツールチェーンとの統合性を向上させることが可能になります。

このコミットの背景には、以下の目的があったと考えられます。

1.  **コードベースの統一性向上**: C言語とGo言語が混在するコードは、ビルドシステムやデバッグの複雑さを増す可能性があります。Go言語への統一は、開発プロセスを簡素化します。
2.  **保守性の向上**: Go言語のコードは、Goのツール（フォーマッタ、リンタなど）によって一貫したスタイルが保たれやすく、Go開発者にとって理解しやすい傾向があります。
3.  **`goto`文の削減**: `goto`文は、コードの制御フローを複雑にし、理解を困難にすることがあります。特に大規模なコードベースでは、`goto`の使用は推奨されません。このコミットでは、`goto`をより構造化された制御フロー（`switch`文のフォールスルーの排除や`return`文の活用）に置き換えることで、コードの可読性を高めています。
4.  **古い実装の残骸の削除**: 過去のC言語ベースの実装が完全に置き換えられた後も、その名残のコードが残っていることがあります。これらを削除することで、コードベースを整理し、将来的な混乱を防ぎます。

## 前提知識の解説

### 1. ソフトフロート (Softfloat)

ソフトフロートとは、CPUが浮動小数点演算をハードウェアで直接実行できない場合や、特定の浮動小数点標準（例: IEEE 754）に厳密に従う必要がある場合に、ソフトウェアで浮動小数点演算をエミュレートする技術です。Goランタイムでは、ARMv5/ARMv6のようなFPUを持たない、または限定的なFPUしか持たないARMプロセッサ向けにソフトフロートが実装されていました。これにより、これらの環境でもGoプログラムが浮動小数点演算を正確に実行できるようになります。

### 2. `stepflt` 関数

`stepflt`関数は、ARMアーキテクチャにおける浮動小数点命令のエミュレーションに関連する関数です。ARMプロセッサの命令セットには、浮動小数点演算を行うための特定の命令（VFP/NEON命令など）があります。FPUを持たないCPUでこれらの命令が実行されようとした場合、通常は未定義命令例外が発生します。`stepflt`のような関数は、この例外を捕捉し、該当する浮動小数点命令を解析して、ソフトウェアでその演算を実行する役割を担います。これは、命令のデコード、オペランドの取得、ソフトフロートライブラリ関数へのディスパッチ、結果のレジスタへの書き込みなどを含みます。

### 3. GoランタイムとC言語の相互運用性

Go言語は、C言語との相互運用性（cgo）をサポートしており、GoコードからC関数を呼び出したり、CコードからGo関数を呼び出したりすることが可能です。初期のGoランタイムでは、既存のCライブラリや、Goで実装するのが困難だった低レベルな処理にcgoが利用されることがありました。このコミットで削除された`fadd64c`のような関数は、C言語から呼び出されることを意図したGo関数のラッパーであったと考えられます。これらは、Goの内部的なソフトフロート関数（例: `fadd64`）をC言語の呼び出し規約に合わせるためのものでした。

### 4. `goto` 文

`goto`文は、プログラムの実行フローをコード内の任意のラベルに直接ジャンプさせる制御構造です。アセンブリ言語やC言語のような低レベル言語では比較的よく使われますが、高レベル言語ではコードの可読性や保守性を著しく低下させる可能性があるため、その使用は一般的に推奨されません。Go言語では`goto`文は存在しますが、エラーハンドリングやループからの多重脱出など、非常に限定的な状況でのみ使用が検討されます。このコミットでは、`goto`を排除することで、より構造化されたコードに改善しています。

## 技術的詳細

このコミットの主要な変更点は、`src/runtime/softfloat64.go`と`src/runtime/softfloat_arm.go`の2つのファイルにわたります。

### `src/runtime/softfloat64.go` の変更

このファイルからは、`fadd64c`, `fsub64c`, `fmul64c`, `fdiv64c`, `fneg64c`, `f32to64c`, `f64to32c`, `fcmp64c`, `fintto64c`, `f64tointc` といった関数が削除されています。これらの関数は、Goの内部的なソフトフロート演算関数（例: `fadd64`）をC言語から呼び出すためのラッパーでした。

例:
- `func fadd64c(f, g uint64, ret *uint64) { *ret = fadd64(f, g) }`

これらの関数が削除されたということは、Goランタイムのこの部分がもはやC言語から直接呼び出される必要がなくなったことを意味します。これは、`stepflt`の実装が完全にGo言語に移行し、C言語ベースの`stepflt`が完全に廃止されたことの証拠です。Goの内部でこれらの演算が必要な場合は、直接`fadd64`などの関数を呼び出すようになり、余分なラッパー層が不要になりました。

### `src/runtime/softfloat_arm.go` の変更

このファイルは、ARMアーキテクチャにおけるソフトフロート命令のエミュレーションロジックを含んでいます。

1.  **変数宣言の簡素化**:
    変更前は、`stepflt`関数内で複数の変数が個別に宣言されていましたが、変更後は同じ型の変数がまとめて宣言されています。
    例:
    ```go
    // 変更前
    var (
        i, opc, regd, regm, regn, cpsr uint32
        cmp, delta                     int32
        uval                           uint64
        sval                           int64
        nan, ok                        bool
    )
    // 変更後
    var i, opc, regd, regm, regn, cpsr uint32
    ```
    これは機能的な変更ではなく、コードのスタイルと簡潔さの改善です。

2.  **`goto`文の削除と制御フローの変更**:
    `stepflt`関数内には、`goto stage1`, `goto stage2`, `goto stage3`, `goto done`といった`goto`文が多数存在し、複雑な制御フローを形成していました。これらの`goto`文はすべて削除され、代わりに`switch`文の各`case`ブロックの最後に`return 1`が追加されています。
    変更前は、`switch`文の`case`がマッチした場合でも`break`で`switch`を抜け、その後の`goto`で次の処理ステージにジャンプしていました。変更後は、各`case`が処理を完了したら即座に`return 1`で関数を終了するように変更されています。これは、各`case`が独立した命令処理パスを表しており、一つの命令処理が完了すれば、`stepflt`関数はその命令が占めるワード数（通常は1ワード）を返して終了するという、より直接的な制御フローに変わったことを示しています。
    また、`default`ケースで`goto`を使っていた部分も削除され、`switch`文が網羅的でない場合は、その`switch`文の後に続くコードが実行されるようになっています。

3.  **C-callableラッパー関数の直接呼び出しへの変更**:
    `softfloat64.go`から`fadd64c`などのC-callableラッパー関数が削除されたことに伴い、`softfloat_arm.go`内のこれらのラッパー関数への呼び出しも、対応するGoの内部関数への直接呼び出しに置き換えられています。

    例:
    - `fadd64c(fgetd(regn), fgetd(regm), &uval)` が `fputd(regd, fadd64(fgetd(regn), fgetd(regm)))` に変更。
        - 変更前は、`fadd64c`に結果を格納するポインタ`&uval`を渡し、その後に`uval`を`fputd`でレジスタに書き込んでいました。
        - 変更後は、`fadd64`の戻り値を直接`fputd`に渡すことで、中間変数`uval`とラッパー関数`fadd64c`が不要になっています。
    - `fcmp64c(fgetd(regd), fgetd(regm), &cmp, &nan)` が `cmp, nan := fcmp64(fgetd(regd), fgetd(regm))` に変更。
        - 変更前は、`fcmp64c`に結果を格納するポインタ`&cmp`と`&nan`を渡していました。
        - 変更後は、`fcmp64`が複数の戻り値を返すGoのイディオムに沿って、直接`cmp`と`nan`に代入しています。
    - `fintto64c(int64(-cmp), &uval)` が `fintto64(int64(-cmp))` に変更。
        - 同様に、`fintto64c`ラッパー関数が削除され、`fintto64`の戻り値が直接使用されています。

これらの変更は、Goランタイムのソフトフロート実装が、より純粋なGoのスタイルに統一され、C言語との相互運用性のためのオーバーヘッドが削減されたことを示しています。

## コアとなるコードの解説

### `src/runtime/softfloat64.go` の変更点

このファイルから削除された`fadd64c`などの関数群は、Goのソフトフロート演算関数をC言語から呼び出すための薄いラッパーでした。これらの関数は、C言語のポインタ引数（`ret *uint64`など）を受け取り、Goの内部関数（`fadd64`など）の戻り値をそのポインタが指すメモリ位置に書き込むという役割を担っていました。これらの削除は、Goランタイムの`stepflt`実装が完全にGo言語に移行し、C言語との直接的な相互運用が必要なくなったことを明確に示しています。これにより、コードベースから不要な抽象化レイヤーが取り除かれ、Goコードの純粋性が高まりました。

### `src/runtime/softfloat_arm.go` の変更点

1.  **変数宣言の変更**:
    `stepflt`関数の冒頭での変数宣言が、より簡潔な一行形式に整理されました。これは機能的な変更ではなく、Goのコーディングスタイルガイドラインに沿った整形です。

2.  **`goto`文の削除と`return 1`への置き換え**:
    最も顕著な変更は、`goto stage1`, `goto stage2`, `goto stage3`, `goto done`といった`goto`文が完全に削除されたことです。
    変更前は、`switch`文の各`case`ブロックの最後に`break`があり、`switch`を抜けた後に`goto`で次の処理ステージにジャンプする構造でした。これは、命令のデコードと実行が複数の「ステージ」に分かれていたことを示唆しています。
    変更後は、各`case`ブロックの最後に`return 1`が追加されています。これは、`stepflt`関数がARMの浮動小数点命令をエミュレートする際に、一つの命令を処理し終えたら、その命令が占めるワード数（通常は1ワード）を返して関数を終了するという、より直接的でモジュール化されたアプローチに移行したことを意味します。これにより、コードの制御フローが直線的になり、特定の命令がどのように処理されるかを追跡しやすくなりました。

3.  **C-callableラッパー関数の直接呼び出しへの変更**:
    `softfloat64.go`からC-callableラッパー関数が削除されたため、`softfloat_arm.go`内のこれらのラッパー関数への呼び出しも、対応するGoの内部関数への直接呼び出しに置き換えられました。
    例えば、`fadd64c(fgetd(regn), fgetd(regm), &uval)` のようなパターンは、`fputd(regd, fadd64(fgetd(regn), fgetd(regm)))` のように変更されています。これは、`fadd64c`のようなラッパー関数が不要になり、Goの関数が直接値を返すイディオムに沿ってコードが書き直されたことを示しています。これにより、中間変数`uval`の宣言と使用も不要になり、コードがさらに簡潔になりました。
    同様に、`fcmp64c`や`f64tointc`のような関数も、Goの多値戻り（multiple return values）の機能を利用して、`cmp, nan := fcmp64(...)` や `sval, ok := f64toint(...)` のように直接結果を受け取る形に変更されています。これはGo言語の強力な機能の一つであり、C言語のポインタ渡しによる結果取得よりも、より安全で読みやすいコードになります。

これらの変更は全体として、Goランタイムのソフトフロート実装をよりGoらしい（idiomatic Go）コードに近づけ、C言語との依存関係を減らし、コードの可読性と保守性を大幅に向上させるものです。

## 変更の背景

Go言語は、様々なアーキテクチャで動作するように設計されています。一部のCPUアーキテクチャ、特に古いARMv5/ARMv6のような組み込みシステム向けのものは、ハードウェアによる浮動小数点演算ユニット（FPU）を持たないか、非常に限定的なFPUしか持たない場合があります。このような環境では、浮動小数点演算をソフトウェアでエミュレートする必要があり、これを「ソフトフロート」と呼びます。

Goランタイムには、このような環境で浮動小数点演算をサポートするためのソフトフロート実装が含まれていました。初期のGoランタイムでは、パフォーマンス上の理由や既存のコードベースの再利用のために、一部の低レベルな処理がC言語で実装されていることがありました。しかし、Go言語の成熟とコンパイラの最適化の進歩に伴い、C言語で書かれた部分を純粋なGoコードに置き換えることで、コードベースの一貫性、保守性、そしてGoツールチェーンとの統合性を向上させることが可能になります。

このコミットの背景には、以下の目的があったと考えられます。

1.  **コードベースの統一性向上**: C言語とGo言語が混在するコードは、ビルドシステムやデバッグの複雑さを増す可能性があります。Go言語への統一は、開発プロセスを簡素化します。
2.  **保守性の向上**: Go言語のコードは、Goのツール（フォーマッタ、リンタなど）によって一貫したスタイルが保たれやすく、Go開発者にとって理解しやすい傾向があります。
3.  **`goto`文の削減**: `goto`文は、コードの制御フローを複雑にし、理解を困難にすることがあります。特に大規模なコードベースでは、`goto`の使用は推奨されません。このコミットでは、`goto`をより構造化された制御フロー（`switch`文のフォールスルーの排除や`return`文の活用）に置き換えることで、コードの可読性を高めています。
4.  **古い実装の残骸の削除**: 過去のC言語ベースの実装が完全に置き換えられた後も、その名残のコードが残っていることがあります。これらを削除することで、コードベースを整理し、将来的な混乱を防ぎます。

## 前提知識の解説

### 1. ソフトフロート (Softfloat)

ソフトフロートとは、CPUが浮動小数点演算をハードウェアで直接実行できない場合や、特定の浮動小数点標準（例: IEEE 754）に厳密に従う必要がある場合に、ソフトウェアで浮動小数点演算をエミュレートする技術です。Goランタイムでは、ARMv5/ARMv6のようなFPUを持たない、または限定的なFPUしか持たないARMプロセッサ向けにソフトフロートが実装されていました。これにより、これらの環境でもGoプログラムが浮動小数点演算を正確に実行できるようになります。

### 2. `stepflt` 関数

`stepflt`関数は、ARMアーキテクチャにおける浮動小数点命令のエミュレーションに関連する関数です。ARMプロセッサの命令セットには、浮動小数点演算を行うための特定の命令（VFP/NEON命令など）があります。FPUを持たないCPUでこれらの命令が実行されようとした場合、通常は未定義命令例外が発生します。`stepflt`のような関数は、この例外を捕捉し、該当する浮動小数点命令を解析して、ソフトウェアでその演算を実行する役割を担います。これは、命令のデコード、オペランドの取得、ソフトフロートライブラリ関数へのディスパッチ、結果のレジスタへの書き込みなどを含みます。

### 3. GoランタイムとC言語の相互運用性

Go言語は、C言語との相互運用性（cgo）をサポートしており、GoコードからC関数を呼び出したり、CコードからGo関数を呼び出したりすることが可能です。初期のGoランタイムでは、既存のCライブラリや、Goで実装するのが困難だった低レベルな処理にcgoが利用されることがありました。このコミットで削除された`fadd64c`のような関数は、C言語から呼び出されることを意図したGo関数のラッパーであったと考えられます。これらは、Goの内部的なソフトフロート関数（例: `fadd64`）をC言語の呼び出し規約に合わせるためのものでした。

### 4. `goto` 文

`goto`文は、プログラムの実行フローをコード内の任意のラベルに直接ジャンプさせる制御構造です。アセンブリ言語やC言語のような低レベル言語では比較的よく使われますが、高レベル言語ではコードの可読性や保守性を著しく低下させる可能性があるため、その使用は一般的に推奨されません。Go言語では`goto`文は存在しますが、エラーハンドリングやループからの多重脱出など、非常に限定的な状況でのみ使用が検討されます。このコミットでは、`goto`を排除することで、より構造化されたコードに改善しています。

例:
- `func fadd64c(f, g uint64, ret *uint64) { *ret = fadd64(f, g) }`

これらの関数が削除されたということは、Goランタイムのこの部分がもはやC言語から直接呼び出される必要がなくなったことを意味します。これは、`stepflt`の実装が完全にGo言語に移行し、C言語ベースの`stepflt`が完全に廃止されたことの証拠です。Goの内部でこれらの演算が必要な場合は、直接`fadd64`などの関数を呼び出すようになり、余分なラッパー層が不要になりました。

### `src/runtime/softfloat_arm.go` の変更

このファイルは、ARMアーキテクチャにおけるソフトフロート命令のエミュレーションロジックを含んでいます。

1.  **変数宣言の簡素化**:
    変更前は、`stepflt`関数内で複数の変数が個別に宣言されていましたが、変更後は同じ型の変数がまとめて宣言されています。
    例:
    ```go
    // 変更前
    var (
        i, opc, regd, regm, regn, cpsr uint32
        cmp, delta                     int32
        uval                           uint64
        sval                           int64
        nan, ok                        bool
    )
    // 変更後
    var i, opc, regd, regm, regn, cpsr uint32
    ```
    これは機能的な変更ではなく、コードのスタイルと簡潔さの改善です。

2.  **`goto`文の削除と制御フローの変更**:
    `stepflt`関数内には、`goto stage1`, `goto stage2`, `goto stage3`, `goto done`といった`goto`文が多数存在し、複雑な制御フローを形成していました。これらの`goto`文はすべて削除され、代わりに`switch`文の各`case`ブロックの最後に`return 1`が追加されています。
    変更前は、`switch`文の`case`がマッチした場合でも`break`で`switch`を抜け、その後の`goto`で次の処理ステージにジャンプしていました。変更後は、各`case`が処理を完了したら即座に`return 1`で関数を終了するように変更されています。これは、各`case`が独立した命令処理パスを表しており、一つの命令処理が完了すれば、`stepflt`関数はその命令が占めるワード数（通常は1ワード）を返して終了するという、より直接的な制御フローに変わったことを示しています。
    また、`default`ケースで`goto`を使っていた部分も削除され、`switch`文が網羅的でない場合は、その`switch`文の後に続くコードが実行されるようになっています。

3.  **C-callableラッパー関数の直接呼び出しへの変更**:
    `softfloat64.go`からC-callableラッパー関数が削除されたため、`softfloat_arm.go`内のこれらのラッパー関数への呼び出しも、対応するGoの内部関数への直接呼び出しに置き換えられました。

    例えば、`fadd64c(fgetd(regn), fgetd(regm), &uval)` のようなパターンは、`fputd(regd, fadd64(fgetd(regn), fgetd(regm)))` のように変更されています。これは、`fadd64c`のようなラッパー関数が不要になり、Goの関数が直接値を返すイディオムに沿ってコードが書き直されたことを示しています。これにより、中間変数`uval`の宣言と使用も不要になり、コードがさらに簡潔になりました。
    同様に、`fcmp64c`や`f64tointc`のような関数も、Goの多値戻り（multiple return values）の機能を利用して、`cmp, nan := fcmp64(...)` や `sval, ok := f64toint(...)` のように直接結果を受け取る形に変更されています。これはGo言語の強力な機能の一つであり、C言語のポインタ渡しによる結果取得よりも、より安全で読みやすいコードになります。

これらの変更は全体として、Goランタイムのソフトフロート実装をよりGoらしい（idiomatic Go）コードに近づけ、C言語との依存関係を減らし、コードの可読性と保守性を大幅に向上させるものです。

## コアとなるコードの解説

### `src/runtime/softfloat64.go` の変更点

このファイルから削除された`fadd64c`などの関数群は、Goのソフトフロート演算関数をC言語から呼び出すための薄いラッパーでした。これらの関数は、C言語のポインタ引数（`ret *uint64`など）を受け取り、Goの内部関数（`fadd64`など）の戻り値をそのポインタが指すメモリ位置に書き込むという役割を担っていました。これらの削除は、Goランタイムの`stepflt`実装が完全にGo言語に移行し、C言語との直接的な相互運用が必要なくなったことを明確に示しています。これにより、コードベースから不要な抽象化レイヤーが取り除かれ、Goコードの純粋性が高まりました。

### `src/runtime/softfloat_arm.go` の変更点

1.  **変数宣言の変更**:
    `stepflt`関数の冒頭での変数宣言が、より簡潔な一行形式に整理されました。これは機能的な変更ではなく、Goのコーディングスタイルガイドラインに沿った整形です。

2.  **`goto`文の削除と`return 1`への置き換え**:
    最も顕著な変更は、`goto stage1`, `goto stage2`, `goto stage3`, `goto done`といった`goto`文が完全に削除されたことです。
    変更前は、`switch`文の各`case`ブロックの最後に`break`があり、`switch`を抜けた後に`goto`で次の処理ステージにジャンプする構造でした。これは、命令のデコードと実行が複数の「ステージ」に分かれていたことを示唆しています。
    変更後は、各`case`ブロックの最後に`return 1`が追加されています。これは、`stepflt`関数がARMの浮動小数点命令をエミュレートする際に、一つの命令を処理し終えたら、その命令が占めるワード数（通常は1ワード）を返して関数を終了するという、より直接的でモジュール化されたアプローチに移行したことを意味します。これにより、コードの制御フローが直線的になり、特定の命令がどのように処理されるかを追跡しやすくなりました。

3.  **C-callableラッパー関数の直接呼び出しへの変更**:
    `softfloat64.go`からC-callableラッパー関数が削除されたため、`softfloat_arm.go`内のこれらのラッパー関数への呼び出しも、対応するGoの内部関数への直接呼び出しに置き換えられました。
    例えば、`fadd64c(fgetd(regn), fgetd(regm), &uval)` のようなパターンは、`fputd(regd, fadd64(fgetd(regn), fgetd(regm)))` のように変更されています。これは、`fadd64c`のようなラッパー関数が不要になり、Goの関数が直接値を返すイディオムに沿ってコードが書き直されたことを示しています。これにより、中間変数`uval`の宣言と使用も不要になり、コードがさらに簡潔になりました。
    同様に、`fcmp64c`や`f64tointc`のような関数も、Goの多値戻り（multiple return values）の機能を利用して、`cmp, nan := fcmp64(...)` や `sval, ok := f64toint(...)` のように直接結果を受け取る形に変更されています。これはGo言語の強力な機能の一つであり、C言語のポインタ渡しによる結果取得よりも、より安全で読みやすいコードになります。

これらの変更は全体として、Goランタイムのソフトフロート実装をよりGoらしい（idiomatic Go）コードに近づけ、C言語との依存関係を減らし、コードの可読性と保守性を大幅に向上させるものです。

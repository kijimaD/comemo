# [インデックス 24468] ファイルの概要

このコミットは、GoランタイムにおけるARMアーキテクチャでのソフトウェア除算/剰余演算の呼び出しシーケンスを変更し、スタックを修正しないようにするものです。これにより、スタックトレースの取得に関する様々なバグが修正され、特に`NOSPLIT`関数での除算/剰余演算が禁止されるようになりました。

## 元コミット内容

Goランタイムにおいて、ARMアーキテクチャでのソフトウェアによる除算/剰余演算の呼び出しシーケンスを変更し、スタックを修正しないようにする。

以前は、除数（denominator）の引数をスタックにプッシュしていたが、この変更により、除数は`m`構造体を通じて渡されるようになった。

この変更は、ソフトウェア除算/剰余ルーチンの途中からスタックトレースを逆方向に取得しようとした際に発生する様々なバグを修正する。過去には一部のバグは回避策で対応されてきたが、未解決のものも存在した。このコミットは、スタックを破壊した後に修正を試みるのではなく、スタックを破壊しないようにすることで問題を根本的に解決する。

このコミットは、以前の変更（`https://golang.org/cl/19810043`）の更新版であり、その変更は`https://golang.org/cl/20350043`でロールバックされていた。

元の変更における問題は、`m`構造体が利用できない不適切なタイミングで除算が行われることがあった点である。これらは、Cコードまたはアセンブリコードにおける定数除数による除算であった。Goコンパイラは定数除数に対する除算を乗算に変換する方法を知っていたが、Cコンパイラはそうではなかった。現在ではCコードは存在しないため、この問題は解消されている。また、`runtime.usleep`（アセンブリ）に問題のある`DIV`命令が1つあったが、これは`https://golang.org/cl/12898`で対応済みである。これにより、今回の新しいアプローチは安全になった。

将来的に同様の問題が再発するのを防ぐため、`NOSPLIT`関数内での`DIV`/`MOD`命令を拒否する。

この変更は、Issue #6681、#6699、#10486を修正する。

## 変更の背景

Goランタイムは、特定のアーキテクチャ（特にARMv5/v6のような古いARMプロセッサ）において、ハードウェアによる除算命令が利用できない場合、ソフトウェアで除算および剰余演算を実装する必要があります。これらのソフトウェアルーチンは、通常、引数をスタックにプッシュして処理を行います。

しかし、このスタックへの引数プッシュが問題を引き起こしていました。具体的には、ソフトウェア除算ルーチンが実行されている最中に、デバッガやパニック発生時のスタックトレース取得など、スタックの状態を正確に把握する必要がある状況で問題が発生しました。ソフトウェア除算ルーチンがスタックを一時的に変更するため、スタックトレースを逆方向に辿る際に、期待されるスタックフレームの構造と実際の構造が異なり、誤った情報が取得されたり、クラッシュが発生したりする可能性がありました。

過去には、これらの問題の一部に対して場当たり的な修正（kludge）が適用されてきましたが、根本的な解決には至っていませんでした。特に、Issue #6681、#6699、#10486といったバグが報告されており、これらはスタックトレースの不正確さや、除算関連のパニック処理の失敗に関連していました。

以前にも同様の修正が試みられましたが（`https://golang.org/cl/19810043`）、その際は`m`構造体が利用できない状況での定数除数による除算が問題となり、ロールバックされました（`https://golang.org/cl/20350043`）。この問題は、Cコードやアセンブリコードで発生していましたが、Goコンパイラは定数除算を乗算に最適化できる一方で、Cコンパイラはそうではありませんでした。このコミットが提案された時点では、GoランタイムからCコードが排除され、また`runtime.usleep`内の問題のあるアセンブリ除算も修正済み（`https://golang.org/cl/12898`）であったため、`m`構造体を利用する新しいアプローチが安全に導入できる状況になりました。

この変更の目的は、ソフトウェア除算ルーチンがスタックを一時的に変更する動作をなくし、除数を`m`構造体経由で渡すことで、スタックトレースの信頼性を向上させ、関連するバグを根本的に解決することです。さらに、将来的な問題の再発を防ぐため、スタックを拡張しない（`NOSPLIT`）関数内での除算/剰余演算をコンパイル時に検出してエラーとする仕組みも導入されました。

## 前提知識の解説

### Goランタイムの`g`と`m`構造体

Goランタイムは、ゴルーチン（`g`）とOSスレッド（`m`）の2つの主要な抽象化を用いて並行性を管理します。
- **`g` (goroutine)**: Goの軽量スレッド。Goプログラム内で実行される独立した処理単位。各`g`は独自のスタックを持ちます。
- **`m` (machine)**: OSスレッド。Goランタイムは、OSスレッド上でゴルーチンを実行します。`m`は、現在実行中の`g`や、スケジューリングに関する情報など、OSスレッド固有のコンテキストを保持します。`m`構造体は、Goランタイムの内部で非常に重要な役割を果たし、特定のCPUレジスタやスレッドローカルストレージのようなものとして利用されることがあります。

### ARMアーキテクチャにおけるソフトウェア除算

ARMプロセッサの古いバージョン（ARMv5TEJやARMv6など）には、ハードウェアによる整数除算命令がありませんでした。これらのプロセッサで除算を行う場合、コンパイラはソフトウェアで除算ルーチンを生成するか、ランタイムライブラリの除算関数を呼び出す必要がありました。Goランタイムも、これらの環境で動作するために、ソフトウェアによる除算/剰余演算ルーチン（例: `_divu`, `_modu`, `_div`, `_mod`）を提供しています。

### スタックトレースとスタックフレーム

- **スタック**: プログラムの実行中に、関数呼び出しの引数、ローカル変数、戻りアドレスなどが一時的に格納されるメモリ領域です。
- **スタックフレーム**: 各関数呼び出しに対応するスタック上の領域で、その関数の実行に必要な情報（引数、ローカル変数、戻りアドレスなど）が格納されます。
- **スタックトレース**: プログラムの実行中に、現在実行中の関数から呼び出し元の関数へと遡って、一連の関数呼び出しの履歴（スタックフレームの連なり）を表示するものです。デバッグやエラー解析において非常に重要です。スタックトレースを正確に取得するためには、各スタックフレームの構造がランタイムの期待する形式と一致している必要があります。

### `NOSPLIT`関数

Goランタイムには、スタックの拡張（stack split）を行わない特別な関数があります。これらは`NOSPLIT`関数と呼ばれ、非常に短い処理や、スタックの拡張自体が問題を引き起こす可能性のある低レベルなランタイムコードで使われます。`NOSPLIT`関数は、スタックのオーバーフローチェックや拡張ロジックをスキップするため、実行速度が速いという利点がありますが、その代わり、関数内で使用できるスタック領域が非常に限られています。そのため、`NOSPLIT`関数内でスタックを大きく消費するような操作（例えば、引数をスタックにプッシュするようなソフトウェア除算ルーチン）を行うと、スタックオーバーフローや予期せぬ動作を引き起こす可能性があります。

### `obj.Link`と`obj.LSym`

これらはGoコンパイラおよびリンカの内部構造体です。
- `obj.Link`: リンカのコンテキストを表します。
- `obj.LSym`: リンカシンボルを表し、関数や変数などの情報を含みます。`cursym.Text.From3.Offset`は、関数の属性（例: `NOSPLIT`フラグ）を格納するために使用されることがあります。

### `REGTMP`, `REGSP`, `REGG`

これらはGoアセンブリにおけるレジスタのエイリアスです。
- `REGTMP`: 一時的な値を保持するために使用される汎用レジスタ。
- `REGSP`: スタックポインタレジスタ。スタックの現在位置を示します。
- `REGG`: 現在のゴルーチン（`g`）構造体へのポインタを保持するレジスタ。

## 技術的詳細

このコミットの核心は、ARMアーキテクチャにおけるソフトウェア除算/剰余演算ルーチンが、除数（denominator）をスタックにプッシュする従来の方式から、`m`構造体（OSスレッドのコンテキスト）の専用フィールドに格納する方式へと変更された点にあります。

### 1. スタック破壊の回避

従来のソフトウェア除算ルーチンでは、除数をスタックにプッシュしていました。これにより、除算ルーチンが実行されている間、スタックの構造が一時的に変更されます。この変更は、特にデバッガがスタックトレースを逆方向に辿ろうとしたり、パニック発生時にランタイムがスタック情報を収集しようとしたりする際に問題を引き起こしました。スタックフレームの期待されるレイアウトと実際のレイアウトが異なるため、スタックトレースが壊れたり、誤った情報が報告されたり、最悪の場合クラッシュにつながる可能性がありました。

このコミットでは、除数をスタックではなく、現在の`m`構造体（`runtime.m`）に新しく追加された`divmod`フィールドに格納するように変更しました。これにより、ソフトウェア除算ルーチンがスタックを一時的に変更することがなくなり、スタックトレースの信頼性が大幅に向上します。

### 2. `m`構造体への`divmod`フィールドの追加

`src/runtime/runtime2.go`において、`m`構造体に`divmod uint32`フィールドが追加されました。このフィールドは、ARMアーキテクチャにおけるソフトウェア除算/剰余演算の除数を一時的に保持するために使用されます。`g`構造体から`m`へのポインタが移動されたのも、この変更に関連しています。以前は`g`構造体にも`m`へのポインタがありましたが、デバッガ向けであり、ハードコードされたオフセットではなかったため、`m`構造体へのアクセス方法が変更されたことを示唆しています。

### 3. アセンブリコードの変更

`src/runtime/vlop_arm.s`内のソフトウェア除算/剰余ルーチン（`_divu`, `_modu`, `_div`, `_mod`）が修正されました。
- 以前は`den+0(FP)`（フレームポインタからのオフセット）を使ってスタックから除数を読み込んでいましたが、これが`g_m(g), Rq`と`m_divmod(Rq), Rq`というシーケンスに置き換えられました。これは、現在のゴルーチン`g`から`m`構造体へのポインタを取得し、その`m`構造体の`divmod`フィールドから除数を読み込むことを意味します。
- `udiv_by_0`ルーチンも簡素化され、スタックを操作する複雑なロジックが削除されました。これは、スタック破壊の問題が解消されたため、不要になったためです。
- `TEXT _divu(SB), NOSPLIT, $16` のように、`NOSPLIT`関数に`NO_LOCAL_POINTERS`ディレクティブが追加されました。これは、この関数がローカルポインタを持たないことをランタイムに通知し、ガベージコレクションの際にスタックをスキャンする必要がないことを示します。これは、スタックが拡張されない`NOSPLIT`関数の特性と、スタック破壊がなくなったことと合わせて、より安全なコードパスを保証します。

### 4. `NOSPLIT`関数での除算の禁止

`src/cmd/internal/obj/arm/obj5.go`のコンパイラバックエンドにおいて、`ADIV`, `ADIVU`, `AMOD`, `AMODU`命令が`NOSPLIT`関数内で使用された場合にエラーを生成するチェックが追加されました。
- `cursym.Text.From3.Offset&obj.NOSPLIT != 0`という条件で、現在のシンボル（関数）が`NOSPLIT`属性を持っているかをチェックします。
- もし`NOSPLIT`関数内で除算/剰余命令が検出された場合、`ctxt.Diag("cannot divide in NOSPLIT function")`というエラーメッセージを出力し、コンパイルを失敗させます。
この変更は、将来的に開発者が誤って`NOSPLIT`関数内でスタックを破壊する可能性のある除算操作を導入するのを防ぐための予防策です。`NOSPLIT`関数はスタック領域が限られているため、除算のような複雑な操作は避けるべきです。

### 5. 以前のロールバックからの教訓

このコミットは、以前にロールバックされた同様の変更（`https://golang.org/cl/19810043`）の再実装です。以前の問題は、`m`構造体が利用できない状況（特にCコードやアセンブリコードでの定数除数による除算）で除算が行われることでした。このコミットの時点では、GoランタイムからCコードが排除され、また`runtime.usleep`内の問題のあるアセンブリ除算も修正済みであったため、`m`構造体を利用するアプローチが安全に適用できるようになりました。Goコンパイラは定数除算を乗算に最適化できるため、Goコードではこの問題は発生しません。

これらの変更により、ARMアーキテクチャにおけるソフトウェア除算/剰余演算の堅牢性が向上し、スタックトレースの正確性が保証され、Goランタイム全体の安定性が高まりました。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/cmd/internal/obj/arm/obj5.go`**: GoコンパイラのARMバックエンドにおけるアセンブリ命令のプリプロセス処理。`NOSPLIT`関数内での除算/剰余命令の使用を検出するロジックが追加され、除算ルーチンへの引数渡し方法が変更されています。
2.  **`src/runtime/runtime2.go`**: Goランタイムの主要な型定義ファイル。`g`構造体と`m`構造体の定義が変更され、`m`構造体に`divmod`フィールドが追加されています。
3.  **`src/runtime/vlop_arm.s`**: ARMアーキテクチャ向けのソフトウェア除算/剰余演算のアセンブリ実装。除数をスタックからではなく`m`構造体から取得するように変更されています。
4.  **`test/fixedbugs/issue10486.go`**: 新しいテストファイル。除算によるゼロ除算パニック時のスタックウォークが正しく機能するかを確認します。

## 元コミット内容

Goランタイムにおいて、ARMアーキテクチャでのソフトウェアによる除算/剰余演算の呼び出しシーケンスを変更し、スタックを修正しないようにする。

以前は、除数（denominator）の引数をスタックにプッシュしていたが、この変更により、除数は`m`構造体を通じて渡されるようになった。

この変更は、ソフトウェア除算/剰余ルーチンの途中からスタックトレースを逆方向に取得しようとした際に発生する様々なバグを修正する。過去には一部のバグは回避策で対応されてきたが、未解決のものも存在した。このコミットは、スタックを破壊した後に修正を試みるのではなく、スタックを破壊しないようにすることで問題を根本的に解決する。

このコミットは、以前の変更（`https://golang.org/cl/19810043`）の更新版であり、その変更は`https://golang.org/cl/20350043`でロールバックされていた。

元の変更における問題は、`m`構造体が利用できない不適切なタイミングで除算が行われることがあった点である。これらは、Cコードまたはアセンブリコードにおける定数除数による除算であった。Goコンパイラは定数除数に対する除算を乗算に変換する方法を知っていたが、Cコンパイラはそうではなかった。現在ではCコードは存在しないため、この問題は解消されている。また、`runtime.usleep`（アセンブリ）に問題のある`DIV`命令が1つあったが、これは`https://golang.org/cl/12898`で対応済みである。これにより、今回の新しいアプローチは安全になった。

将来的に同様の問題が再発するのを防ぐため、`NOSPLIT`関数内での`DIV`/`MOD`命令を拒否する。

この変更は、Issue #6681、#6699、#10486を修正する。

## 変更の背景

Goランタイムは、特定のアーキテクチャ（特にARMv5/v6のような古いARMプロセッサ）において、ハードウェアによる除算命令が利用できない場合、ソフトウェアで除算および剰余演算を実装する必要があります。これらのソフトウェアルーチンは、通常、引数をスタックにプッシュして処理を行います。

しかし、このスタックへの引数プッシュが問題を引き起こしていました。具体的には、ソフトウェア除算ルーチンが実行されている最中に、デバッガやパニック発生時のスタックトレース取得など、スタックの状態を正確に把握する必要がある状況で問題が発生しました。ソフトウェア除算ルーチンがスタックを一時的に変更するため、スタックトレースを逆方向に辿る際に、期待されるスタックフレームの構造と実際の構造が異なり、誤った情報が取得されたり、クラッシュが発生したりする可能性がありました。

過去には、これらの問題の一部に対して場当たり的な修正（kludge）が適用されてきましたが、根本的な解決には至っていませんでした。特に、Issue #6681、#6699、#10486といったバグが報告されており、これらはスタックトレースの不正確さや、除算関連のパニック処理の失敗に関連していました。

以前にも同様の修正が試みられましたが（`https://golang.org/cl/19810043`）、その際は`m`構造体が利用できない状況での定数除数による除算が問題となり、ロールバックされました（`https://golang.org/cl/20350043`）。この問題は、Cコードやアセンブリコードで発生していましたが、Goコンパイラは定数除算を乗算に最適化できる一方で、Cコンパイラはそうではありませんでした。このコミットが提案された時点では、GoランタイムからCコードが排除され、また`runtime.usleep`内の問題のあるアセンブリ除算も修正済み（`https://golang.org/cl/12898`）であったため、`m`構造体を利用する新しいアプローチが安全に導入できる状況になりました。

この変更の目的は、ソフトウェア除算ルーチンがスタックを一時的に変更する動作をなくし、除数を`m`構造体経由で渡すことで、スタックトレースの信頼性を向上させ、関連するバグを根本的に解決することです。さらに、将来的な問題の再発を防ぐため、スタックを拡張しない（`NOSPLIT`）関数内での除算/剰余演算をコンパイル時に検出してエラーとする仕組みも導入されました。

## 前提知識の解説

### Goランタイムの`g`と`m`構造体

Goランタイムは、ゴルーチン（`g`）とOSスレッド（`m`）の2つの主要な抽象化を用いて並行性を管理します。
- **`g` (goroutine)**: Goの軽量スレッド。Goプログラム内で実行される独立した処理単位。各`g`は独自のスタックを持ちます。
- **`m` (machine)**: OSスレッド。Goランタイムは、OSスレッド上でゴルーチンを実行します。`m`は、現在実行中の`g`や、スケジューリングに関する情報など、OSスレッド固有のコンテキストを保持します。`m`構造体は、Goランタイムの内部で非常に重要な役割を果たし、特定のCPUレジスタやスレッドローカルストレージのようなものとして利用されることがあります。

### ARMアーキテクチャにおけるソフトウェア除算

ARMプロセッサの古いバージョン（ARMv5TEJやARMv6など）には、ハードウェアによる整数除算命令がありませんでした。これらのプロセッサで除算を行う場合、コンパイラはソフトウェアで除算ルーチンを生成するか、ランタイムライブラリの除算関数を呼び出す必要がありました。Goランタイムも、これらの環境で動作するために、ソフトウェアによる除算/剰余演算ルーチン（例: `_divu`, `_modu`, `_div`, `_mod`）を提供しています。

### スタックトレースとスタックフレーム

- **スタック**: プログラムの実行中に、関数呼び出しの引数、ローカル変数、戻りアドレスなどが一時的に格納されるメモリ領域です。
- **スタックフレーム**: 各関数呼び出しに対応するスタック上の領域で、その関数の実行に必要な情報（引数、ローカル変数、戻りアドレスなど）が格納されます。
- **スタックトレース**: プログラムの実行中に、現在実行中の関数から呼び出し元の関数へと遡って、一連の関数呼び出しの履歴（スタックフレームの連なり）を表示するものです。デバッグやエラー解析において非常に重要です。スタックトレースを正確に取得するためには、各スタックフレームの構造がランタイムの期待する形式と一致している必要があります。

### `NOSPLIT`関数

Goランタイムには、スタックの拡張（stack split）を行わない特別な関数があります。これらは`NOSPLIT`関数と呼ばれ、非常に短い処理や、スタックの拡張自体が問題を引き起こす可能性のある低レベルなランタイムコードで使われます。`NOSPLIT`関数は、スタックのオーバーフローチェックや拡張ロジックをスキップするため、実行速度が速いという利点がありますが、その代わり、関数内で使用できるスタック領域が非常に限られています。そのため、`NOSPLIT`関数内でスタックを大きく消費するような操作（例えば、引数をスタックにプッシュするようなソフトウェア除算ルーチン）を行うと、スタックオーバーフローや予期せぬ動作を引き起こす可能性があります。

### `obj.Link`と`obj.LSym`

これらはGoコンパイラおよびリンカの内部構造体です。
- `obj.Link`: リンカのコンテキストを表します。
- `obj.LSym`: リンカシンボルを表し、関数や変数などの情報を含みます。`cursym.Text.From3.Offset`は、関数の属性（例: `NOSPLIT`フラグ）を格納するために使用されることがあります。

### `REGTMP`, `REGSP`, `REGG`

これらはGoアセンブリにおけるレジスタのエイリアスです。
- `REGTMP`: 一時的な値を保持するために使用される汎用レジスタ。
- `REGSP`: スタックポインタレジスタ。スタックの現在位置を示します。
- `REGG`: 現在のゴルーチン（`g`）構造体へのポインタを保持するレジスタ。

## 技術的詳細

このコミットの核心は、ARMアーキテクチャにおけるソフトウェア除算/剰余演算ルーチンが、除数（denominator）をスタックにプッシュする従来の方式から、`m`構造体（OSスレッドのコンテキスト）の専用フィールドに格納する方式へと変更された点にあります。

### 1. スタック破壊の回避

従来のソフトウェア除算ルーチンでは、除数をスタックにプッシュしていました。これにより、除算ルーチンが実行されている間、スタックの構造が一時的に変更されます。この変更は、特にデバッガがスタックトレースを逆方向に辿ろうとしたり、パニック発生時にランタイムがスタック情報を収集しようとしたりする際に問題を引き起こしました。スタックフレームの期待されるレイアウトと実際のレイアウトが異なるため、スタックトレースが壊れたり、誤った情報が報告されたり、最悪の場合クラッシュにつながる可能性がありました。

このコミットでは、除数をスタックではなく、現在の`m`構造体（`runtime.m`）に新しく追加された`divmod`フィールドに格納するように変更しました。これにより、ソフトウェア除算ルーチンがスタックを一時的に変更することがなくなり、スタックトレースの信頼性が大幅に向上します。

### 2. `m`構造体への`divmod`フィールドの追加

`src/runtime/runtime2.go`において、`m`構造体に`divmod uint32`フィールドが追加されました。このフィールドは、ARMアーキテクチャにおけるソフトウェア除算/剰余演算の除数を一時的に保持するために使用されます。`g`構造体から`m`へのポインタが移動されたのも、この変更に関連しています。以前は`g`構造体にも`m`へのポインタがありましたが、デバッガ向けであり、ハードコードされたオフセットではなかったため、`m`構造体へのアクセス方法が変更されたことを示唆しています。

### 3. アセンブリコードの変更

`src/runtime/vlop_arm.s`内のソフトウェア除算/剰余ルーチン（`_divu`, `_modu`, `_div`, `_mod`）が修正されました。
- 以前は`den+0(FP)`（フレームポインタからのオフセット）を使ってスタックから除数を読み込んでいましたが、これが`g_m(g), Rq`と`m_divmod(Rq), Rq`というシーケンスに置き換えられました。これは、現在のゴルーチン`g`から`m`構造体へのポインタを取得し、その`m`構造体の`divmod`フィールドから除数を読み込むことを意味します。
- `udiv_by_0`ルーチンも簡素化され、スタックを操作する複雑なロジックが削除されました。これは、スタック破壊の問題が解消されたため、不要になったためです。
- `TEXT _divu(SB), NOSPLIT, $16` のように、`NOSPLIT`関数に`NO_LOCAL_POINTERS`ディレクティブが追加されました。これは、この関数がローカルポインタを持たないことをランタイムに通知し、ガベージコレクションの際にスタックをスキャンする必要がないことを示します。これは、スタックが拡張されない`NOSPLIT`関数の特性と、スタック破壊がなくなったことと合わせて、より安全なコードパスを保証します。

### 4. `NOSPLIT`関数での除算の禁止

`src/cmd/internal/obj/arm/obj5.go`のコンパイラバックエンドにおいて、`ADIV`, `ADIVU`, `AMOD`, `AMODU`命令が`NOSPLIT`関数内で使用された場合にエラーを生成するチェックが追加されました。
- `cursym.Text.From3.Offset&obj.NOSPLIT != 0`という条件で、現在のシンボル（関数）が`NOSPLIT`属性を持っているかをチェックします。
- もし`NOSPLIT`関数内で除算/剰余命令が検出された場合、`ctxt.Diag("cannot divide in NOSPLIT function")`というエラーメッセージを出力し、コンパイルを失敗させます。
この変更は、将来的に開発者が誤って`NOSPLIT`関数内でスタックを破壊する可能性のある除算操作を導入するのを防ぐための予防策です。`NOSPLIT`関数はスタック領域が限られているため、除算のような複雑な操作は避けるべきです。

### 5. 以前のロールバックからの教訓

このコミットは、以前にロールバックされた同様の変更（`https://golang.org/cl/19810043`）の再実装です。以前の問題は、`m`構造体が利用できない状況（特にCコードやアセンブリコードでの定数除数による除算）で除算が行われることでした。このコミットの時点では、GoランタイムからCコードが排除され、また`runtime.usleep`内の問題のあるアセンブリ除算も修正済みであったため、`m`構造体を利用するアプローチが安全に適用できるようになりました。Goコンパイラは定数除算を乗算に最適化できるため、Goコードではこの問題は発生しません。

			p.To.Type = obj.TYPE_REG
			p.To.Reg = REGTMP

			/* MOV a,m_divmod(REGTMP) */ // 除数aをm.divmodに格納
			p = obj.Appendp(ctxt, p)
			p.As = AMOVW
			p.Lineno = q1.Lineno
			p.From.Type = obj.TYPE_REG
			p.From.Reg = q1.From.Reg
			p.To.Type = obj.TYPE_MEM
			p.To.Reg = REGTMP
			p.To.Offset = 8 * 4 // offset of m.divmod

			// ... (残りの除算ルーチン呼び出しコード)

			// 以前のスタック操作（ADD $8,SPなど）は削除されている
			// ...
```
- `ADIV`, `ADIVU`, `AMOD`, `AMODU`命令（除算/剰余）を処理する部分に、`NOSPLIT`関数内での使用を禁止するチェックが追加されました。`cursym.Text.From3.Offset&obj.NOSPLIT != 0`は、現在の関数が`NOSPLIT`属性を持つかどうかを判断します。
- 除算ルーチンへの引数渡しが変更されました。以前はスタックにプッシュしていましたが、`g`レジスタから`m`構造体へのポインタを取得し（`MOV m(g),REGTMP`）、その`m`構造体の`divmod`フィールドに除数を格納する（`MOV a,m_divmod(REGTMP)`）ように変更されました。これにより、スタックを破壊することなく除数を渡せるようになります。
- 以前のスタックポインタ操作（`ADD $8,SP`など）は削除されています。

### `src/runtime/vlop_arm.s`

```assembly
// ... (既存のコード)

udiv_by_0:
	// 以前の複雑なスタック操作は削除され、panicdivideへの直接ジャンプに変更
	MOVW	$runtime·panicdivide(SB), R11
	B 	(R11)

// ... (既存のコード)

TEXT _divu(SB), NOSPLIT, $16-0
	NO_LOCAL_POINTERS // ローカルポインタがないことを宣言
	// ... (レジスタの保存)

	MOVW	RTMP, Rr		/* numerator */
	MOVW	g_m(g), Rq      // gからmへのポインタをRqにロード
	MOVW	m_divmod(Rq), Rq	/* denominator */ // m.divmodから除数をRqにロード
	BL  	udiv<>(SB)
	MOVW	Rq, RTMP
	// ... (レジスタの復元)
	RET

TEXT _modu(SB), NOSPLIT, $16-0
	NO_LOCAL_POINTERS
	// ...
	MOVW	RTMP, Rr		/* numerator */
	MOVW	g_m(g), Rq
	MOVW	m_divmod(Rq), Rq	/* denominator */
	BL  	udiv<>(SB)
	MOVW	Rr, RTMP
	// ...
	RET

TEXT _div(SB),NOSPLIT,$16-0
	NO_LOCAL_POINTERS
	// ...
	MOVW	RTMP, Rr		/* numerator */
	MOVW	g_m(g), Rq
	MOVW	m_divmod(Rq), Rq	/* denominator */
	// ...
	RET

TEXT _mod(SB),NOSPLIT,$16-0
	NO_LOCAL_POINTERS
	// ...
	MOVW	RTMP, Rr		/* numerator */
	MOVW	g_m(g), Rq
	MOVW	m_divmod(Rq), Rq	/* denominator */
	// ...
	RET
```
- `udiv_by_0`ルーチンが大幅に簡素化されました。以前はスタックをアンワインドし、LR（リンクレジスタ）を操作する複雑なロジックがありましたが、スタック破壊の問題が解消されたため、`runtime·panicdivide`への直接ジャンプに置き換えられました。
- `_divu`, `_modu`, `_div`, `_mod`といったソフトウェア除算/剰余ルーチンにおいて、除数（denominator）の取得方法が変更されました。以前は`den+0(FP)`（フレームポインタからのオフセット）でスタックから取得していましたが、`g_m(g)`で現在の`g`から`m`へのポインタをロードし、`m_divmod(Rq)`でその`m`構造体の`divmod`フィールドから除数を取得するように変更されました。
- これらのルーチンには`NO_LOCAL_POINTERS`ディレクティブが追加されました。これは、これらの関数がローカルポインタを持たないことをランタイムに通知し、ガベージコレクションの際にスタックをスキャンする必要がないことを示します。これは、`NOSPLIT`関数であり、スタック破壊がなくなったことと合わせて、より効率的で安全なコードパスを保証します。

### `test/fixedbugs/issue10486.go`

```go
// run

// Copyright 2015 The Go Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

// Issue 10486.
// Check stack walk during div by zero fault,
// especially on software divide systems.

package main

import "runtime"

var A, B int

func divZero() int {
	defer func() {
		if p := recover(); p != nil {
			var pcs [512]uintptr
			runtime.Callers(2, pcs[:]) // スタックトレースを取得
			runtime.GC()
		}
	}()
	return A / B // ゼロ除算を発生させる
}

func main() {
	A = 1
	divZero()
}
```
- このテストは、ゼロ除算が発生した際のスタックウォーク（スタックトレースの取得）が、特にソフトウェア除算システムで正しく機能するかどうかを検証するために追加されました。
- `divZero`関数内でゼロ除算を意図的に発生させ、`defer`関数内で`recover()`と`runtime.Callers()`を使ってスタックトレースを取得しています。このテストが成功することで、ソフトウェア除算ルーチンがスタックを破壊しなくなった結果、パニック発生時でも正確なスタックトレースが取得できるようになったことが確認されます。

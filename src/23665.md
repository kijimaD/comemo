# [インデックス 23665] ファイルの概要

このコミットは、Goコンパイラ（`cmd/internal/gc`）において、マップリテラルのキー部分で複合リテラルを使用する際に、その複合リテラルの型を省略できるようにする変更を導入します。これにより、マップリテラルの記述がより簡潔になり、Go言語の型推論の原則に沿った柔軟性が向上します。

## 元コミット内容

Goコンパイラ（`cmd/internal/gc`）が、マップリテラルにおいてキーの型が省略された複合リテラルを受け入れるように変更されました。これにより、関連する問題 #10209 が修正されます。

## 変更の背景

Go言語では、構造体リテラルや配列リテラルなどの複合リテラルにおいて、その型が文脈から推論できる場合に型名を省略できるという簡潔な記法が提供されています。例えば、`var s = []S{{A: 1}, {A: 2}}` のように、`S{A: 1}` の `S` を省略して `{A: 1}` と書くことができます。

しかし、このコミット以前は、マップリテラルのキーが複合型である場合、そのキーの複合リテラルにおいて型名を省略することができませんでした。例えば、`map[struct{X int}]string` 型のマップに要素を追加する際、`m[struct{X: 1}] = "value"` のように、キーの複合リテラル `struct{X: 1}` の `struct{X int}` を明示する必要がありました。これは、値の複合リテラルで型名を省略できるのと比較して一貫性がなく、冗長でした。

このコミットは、マップリテラルのキーにおいても、文脈から型が推論できる場合に型名を省略できるようにすることで、この一貫性の欠如を解消し、コードの簡潔性を向上させることを目的としています。これは、Go言語の設計哲学である「簡潔さと明瞭さ」に沿った改善と言えます。

## 前提知識の解説

### Goのマップリテラル (Map Literals)

Goのマップリテラルは、`map[KeyType]ValueType{key1: value1, key2: value2, ...}` の形式でマップの初期値を宣言するために使用されます。例えば、`m := map[string]int{"apple": 1, "banana": 2}` のように記述します。
マップの値が複合型である場合、その複合リテラルの型は文脈から推論できるため、型名を省略できます。
例:
```go
type Fruit struct {
    Color string
    Weight int
}
fruits := map[string]Fruit{
    "apple":  {"red", 100}, // Fruit{"red", 100} の Fruit を省略
    "banana": {"yellow", 120},
}
```

### 複合リテラル (Composite Literals)

複合リテラルは、構造体、配列、スライス、マップなどの複合型の値を構築するための構文です。`Type{...}` の形式を取り、`{...}` の部分が `LiteralValue` と呼ばれます。`LiteralValue` 内の各要素は、`KeyedElement` として `[Key:]Value` の形式を取ることができます。

### 型推論 (Type Inference)

Go言語は、変数の宣言や複合リテラルにおいて、コンパイラが文脈から型を自動的に判断する「型推論」の機能を持っています。これにより、開発者は冗長な型宣言を省略し、より簡潔なコードを書くことができます。

### Goコンパイラ (`cmd/internal/gc`) と文法解析

Goコンパイラは、Go言語のソースコードを機械語に変換するツールチェーンの一部です。`cmd/internal/gc` は、その主要なコンパイラ実装の一つです。
Goコンパイラのフロントエンドは、ソースコードを解析するためにYacc (Yet Another Compiler Compiler) のようなツールを使用しています。
*   **`go.y`**: これはYaccの文法定義ファイルに相当し、Go言語の構文規則が記述されています。コンパイラはこれを基にソースコードを解析します。
*   **`y.go`**: `go.y`からYaccツールによって自動生成されるGoのソースファイルで、パーサーの実装を含みます。
*   **`typecheck.go`**: 型チェックのロジックが含まれるファイルです。構文解析されたAST (Abstract Syntax Tree) を走査し、Go言語の型規則に違反がないか検証します。

## 技術的詳細

このコミットの技術的な変更は、主にGo言語の文法定義と型チェックロジックに集中しています。

1.  **`src/cmd/compile/internal/gc/go.y` の変更**:
    *   `keyval` ルールの定義が `expr ':' complitexpr` から `complitexpr ':' complitexpr` に変更されました。
    *   これは、マップリテラルのキー部分 (`keyval` の `:` の左側) が、以前は一般的な `expr` (式) でなければならなかったのに対し、この変更後は `complitexpr` (複合リテラル式) であっても良いことを意味します。
    *   この文法変更により、`map[struct{X int}]string{{X: 1}: "value"}` のように、キーの型 `struct{X int}` を省略した `{X: 1}` という複合リテラルをキーとして記述することが文法的に許容されるようになります。

2.  **`src/cmd/compile/internal/gc/typecheck.go` の変更**:
    *   `typecheckcomplit` 関数内で、マップキーの型チェックロジックが修正されました。
    *   具体的には、`l.Left` (マップキーを表すノード) を直接 `typecheck` するのではなく、一時変数 `r` に代入し、`pushtype(r, t.Down)` を呼び出してから `typecheck(&r, Erv)` を実行するように変更されています。
    *   `pushtype` は、型チェックのコンテキストにおいて、期待される型情報（この場合はマップのキー型 `t.Down`）をノード `r` に伝達する役割を果たします。これにより、コンパイラはマップキーの複合リテラルが持つべき型を事前に知り、その情報に基づいて複合リテラルの型推論を適切に行うことができるようになります。
    *   この変更は、文法変更によって許容された新しい記法（キーの複合リテラルで型名を省略する）が、Goの型規則に則って正しく型チェックされることを保証するために不可欠です。

3.  **`src/cmd/compile/internal/gc/y.go` および `src/cmd/compile/internal/gc/y.output` の変更**:
    *   `go.y` ファイルの文法変更に伴い、Yaccツールが再実行され、パーサーの実装ファイルである `y.go` が更新されました。
    *   `y.output` ファイルは、Yaccのデバッグ出力ファイルであり、パーサーの状態遷移や競合情報などが記述されています。このファイルが削除されたのは、おそらくビルドプロセスにおいて不要になったか、あるいは別の形式でデバッグ情報が管理されるようになったためと考えられます。`y.go` の変更は、`go.y` の変更を反映した自動生成コードの更新です。

## コアとなるコードの解説

### `go.y` の変更

この変更により、マップリテラルのキー部分に複合リテラルを直接記述する際の文法的な制約が緩和されました。
**変更前**:
```go
type Point struct { X, Y int }
m := map[Point]string{
    Point{1, 2}: "first", // キーの複合リテラルで型名 Point を明示する必要があった
}
```
**変更後**:
```go
type Point struct { X, Y int }
m := map[Point]string{
    {1, 2}: "first", // キーの複合リテラルで型名 Point を省略できるようになった
}
```
`keyval` ルールが `expr` ではなく `complitexpr` を受け入れるようになったことで、`{1, 2}` のような型名が省略された複合リテラルがマップのキーとして文法的に有効になりました。

### `typecheck.go` の変更

`typecheckcomplit` 関数は、複合リテラルの型チェックを担当します。この関数内の変更は、`go.y` で導入された新しい文法に対応し、マップキーの複合リテラルの型を正確に推論し、検証するために行われました。

1.  `r = l.Left`: マップキーを表すノード `l.Left` を一時変数 `r` に格納します。
2.  `pushtype(r, t.Down)`: ここが重要な変更点です。`t.Down` は、現在のマップリテラルが期待するキーの型（この例では `Point` 型）を表します。`pushtype` は、この期待される型情報を `r` (キーの複合リテラル) に伝達します。これにより、`{1, 2}` のような型名が省略された複合リテラルが、文脈から `Point` 型であると推論されるようになります。
3.  `typecheck(&r, Erv)`: 期待される型情報が与えられた `r` に対して型チェックを実行します。これにより、`{1, 2}` の要素が `Point` 型のフィールドと互換性があるかなどが検証されます。
4.  `defaultlit(&r, t.Down)`: 複合リテラル内の数値リテラルなどにデフォルトの型を適用します。
5.  `l.Left = assignconv(r, t.Down, "map key")`: 型チェックと変換が完了した `r` を `l.Left` に戻し、必要に応じてマップのキー型への代入可能性チェックと変換を行います。

この一連の変更により、Goコンパイラはマップリテラルのキーとして型名が省略された複合リテラルを正しく解析し、型チェックできるようになりました。

# [インデックス 24446] ファイルの概要

このコミットは、Goコンパイラの`cmd/compile`パッケージにおけるARM64アーキテクチャのスタックフレームアライメントに関するバグ修正です。具体的には、ARM64のスタックフレームサイズが正しくアラインされていない場合に発生する、ガベージコレクション（GC）の問題を解決します。

## コミット

`cmd/compile: align arm64 stack frames correctly`

## GitHub上でのコミットページへのリンク

## 元コミット内容

```
cmd/compile: align arm64 stack frames correctly

If the compiler doesn't do it, cmd/internal/obj/arm64 will,
and that will break the zeroing of ambiguously live values
done in zerorange, which in turn produces uninitialized
pointer cells that the GC trips over.

For #9880.

## 変更の背景

この変更は、GoコンパイラがARM64アーキテクチャ向けに生成するスタックフレームのサイズが、特定の条件下でARM64のABI（Application Binary Interface）要件を満たさないために発生するバグを修正するものです。

問題の根本は、Goランタイムのガベージコレクタ（GC）が、スタック上の「曖昧に生きている値」（ambiguously live values）をゼロクリアする`zerorange`という処理にありました。スタックフレームが正しくアラインされていないと、`zerorange`が期待通りに機能せず、初期化されていないポインタセルが生成される可能性がありました。このような初期化されていないポインタセルは、GCがヒープをスキャンする際に不正なメモリ参照として検出され、クラッシュや予期せぬ動作を引き起こす原因となります。

コミットメッセージにある`For #9880`は、この問題がGoのIssueトラッカーで報告されたIssue 9880に関連していることを示しています。このIssueでは、ARM64環境で特定のGoプログラムがクラッシュするという報告がされており、その原因がスタックアライメントの不備とGCの相互作用にあることが特定されました。

コンパイラがこのアライメントを保証しない場合、`cmd/internal/obj/arm64`（Goのアセンブラバックエンド）がアライメントを試みる可能性がありますが、それが`zerorange`の動作を妨げ、結果としてGCの問題を引き起こすという状況でした。したがって、コンパイラ自身がスタックフレームを正しくアラインすることが、この問題を根本的に解決するために必要とされました。

## 前提知識の解説

### 1. スタックフレームとスタックアライメント

-   **スタックフレーム**: 関数が呼び出されるたびに、その関数のローカル変数、引数、リターンアドレスなどを格納するためにスタック上に確保されるメモリ領域です。
-   **スタックアライメント**: 多くのCPUアーキテクチャ（特に64ビットアーキテクチャ）では、メモリへのアクセス効率を最大化するために、特定のデータ型が特定のメモリアドレス境界に配置されることを要求します。これを「アライメント」と呼びます。スタックフレーム全体も、特定のバイト数（例えば16バイト）の倍数のアドレスにアラインされている必要があります。ARM64アーキテクチャでは、スタックポインタ（SP）が16バイト境界にアラインされていることが一般的です。

### 2. ARM64 ABI (Application Binary Interface)

-   ABIは、オペレーティングシステムとプログラム、またはプログラムの異なるモジュール間で、どのように関数が呼び出され、引数が渡され、戻り値が返され、スタックが管理されるかなどを定義する一連の規約です。
-   ARM64のABIでは、スタックポインタが16バイト境界にアラインされていることが厳密に要求されます。これは、特にSIMD（Single Instruction, Multiple Data）命令など、特定の命令が16バイトアラインされたデータにアクセスすることを前提としているためです。スタックフレームのサイズも、このアライメント要件に影響されます。

### 3. Goのガベージコレクション (GC)

-   Goは自動メモリ管理（ガベージコレクション）を採用しています。GCは、プログラムが動的に確保したメモリのうち、もはや到達不可能になったオブジェクトを自動的に解放する役割を担います。
-   **ポインタスキャン**: GCは、ヒープ上のオブジェクトがまだ使用されているかどうかを判断するために、ルート（グローバル変数、レジスタ、スタック上のポインタなど）から到達可能なオブジェクトをスキャンします。
-   **曖昧なポインタ (Ambiguous Pointers)**: GoのGCは、スタック上の値がポインタであるか、それとも単なる整数などの非ポインタ値であるかを常に正確に識別できるわけではありません。このような値を「曖昧なポインタ」と呼びます。
-   **`zerorange`**: Goランタイムには、GCがスキャンする前に、スタック上の特定のメモリ範囲（特に、関数呼び出し後に使用されなくなる可能性のある領域や、曖昧なポインタが含まれる可能性のある領域）をゼロクリアする`zerorange`という最適化があります。これにより、GCが古い、無効なポインタ値を誤って参照することを防ぎ、メモリ安全性を高めます。

### 4. `cmd/compile`と`cmd/internal/obj/arm64`

-   **`cmd/compile`**: Go言語のコンパイラ本体です。Goのソースコードを中間表現に変換し、最終的に各アーキテクチャ（x86-64, ARM64など）向けのアセンブリコードまたはオブジェクトコードを生成します。
-   **`cmd/internal/obj/arm64`**: Goコンパイラのバックエンドの一部で、ARM64アーキテクチャ固有のアセンブリコード生成を担当します。これは、Goのアセンブラ（`cmd/asm`）の内部パッケージでもあります。

## 技術的詳細

このコミットの技術的な核心は、ARM64アーキテクチャにおけるスタックフレームのサイズ調整ロジックにあります。ARM64のABIでは、スタックフレームのサイズ（リターンアドレスを保存するためのLRレジスタの領域を除く）が、0であるか、または16の倍数に8を加えた値（`8 mod 16`）である必要があります。これは、スタックポインタが常に16バイトアラインされることを保証するための要件です。

具体的には、関数呼び出し規約において、スタックポインタ（SP）は常に16バイト境界にアラインされている必要があります。関数がスタックフレームを割り当てる際、そのフレームサイズがこのアライメント要件を維持するように調整されなければなりません。

コミット前のGoコンパイラ（`cmd/compile`）は、このARM64固有のスタックフレームアライメント要件を常に満たしているわけではありませんでした。その結果、生成されたコードのスタックフレームサイズが不適切になり、以下の問題を引き起こしました。

1.  **`zerorange`の誤動作**: `zerorange`は、スタック上の特定の範囲をゼロクリアすることで、GCが古いポインタ値を誤って参照するのを防ぎます。スタックフレームのアライメントが崩れると、`zerorange`が意図しないメモリ領域をゼロクリアしたり、ゼロクリアすべき領域をスキップしたりする可能性がありました。
2.  **未初期化ポインタセルの生成**: `zerorange`が正しく機能しないと、スタック上に以前の関数呼び出しの残骸や、未初期化のポインタ値が残存する可能性があります。これらの値は、GCがヒープをスキャンする際に有効なポインタとして解釈され、不正なメモリアドレスへのアクセスを試みることで、プログラムのクラッシュ（セグメンテーション違反など）を引き起こします。

このコミットは、`cmd/compile`がスタックフレームサイズを計算する際に、明示的にARM64のアライメント要件を満たすようにパディングを追加することで、この問題を解決します。これにより、`zerorange`が常に正しいメモリ範囲を処理し、GCが安全に動作することが保証されます。

## コアとなるコードの解説

変更は`defframe`関数内で行われています。この関数は、Goコンパイラが関数のスタックフレームを定義する際に呼び出されます。

1.  `frame := uint32(gc.Rnd(gc.Stksize+gc.Maxarg, int64(gc.Widthreg)))`
    -   この行は、現在の関数のスタックフレームの基本的なサイズを計算しています。`gc.Stksize`はローカル変数に必要なスタックサイズ、`gc.Maxarg`は関数が呼び出す他の関数に渡す引数に必要な最大スタックサイズです。`gc.Rnd`は、指定されたサイズを次のアライメント境界に丸める関数です。ここでは、レジスタ幅（`gc.Widthreg`、通常は8バイト）にアラインしています。

2.  `// arm64 requires that the frame size (not counting saved LR)`
    `// be empty or be 8 mod 16. If not, pad it.`
    -   このコメントは、ARM64のスタックフレームアライメント要件を明確に説明しています。スタックフレームサイズ（リターンアドレスを保存するLRレジスタの領域を含まない）は、0であるか、または16で割った余りが8である必要があります。

3.  `if frame != 0 && frame%16 != 8 {`
    `    frame += 8`
    `}`
    -   この`if`ブロックが追加されたパディングロジックです。
    -   `frame != 0`: スタックフレームが空でない場合（つまり、何らかのスタック領域が割り当てられている場合）にのみ、アライメントチェックを行います。空のフレームはアライメントの問題を引き起こしません。
    -   `frame%16 != 8`: 計算された`frame`サイズが、ARM64の要件である「16で割った余りが8」を満たしていない場合。
    -   この両方の条件が真の場合、`frame += 8`によってスタックフレームサイズに8バイトが追加されます。これにより、`frame`サイズは次の「16で割った余りが8」となる値に調整されます。例えば、`frame`が16の倍数だった場合、8を加えることで`8 mod 16`を満たすようになります。

この変更により、`ptxt.To.Offset = int64(frame)`で設定される最終的なスタックフレームサイズが、常にARM64のABI要件を満たすようになり、`zerorange`の誤動作とそれに伴うGCの問題が解決されます。

 	ptxt.To.Offset = int64(frame)

## コアとなるコードの解説

変更は`defframe`関数内で行われています。この関数は、Goコンパイラが関数のスタックフレームを定義する際に呼び出されます。

1.  `frame := uint32(gc.Rnd(gc.Stksize+gc.Maxarg, int64(gc.Widthreg)))`
    -   この行は、現在の関数のスタックフレームの基本的なサイズを計算しています。`gc.Stksize`はローカル変数に必要なスタックサイズ、`gc.Maxarg`は関数が呼び出す他の関数に渡す引数に必要な最大スタックサイズです。`gc.Rnd`は、指定されたサイズを次のアライメント境界に丸める関数です。ここでは、レジスタ幅（`gc.Widthreg`、通常は8バイト）にアラインしています。

2.  `// arm64 requires that the frame size (not counting saved LR)`
    `// be empty or be 8 mod 16. If not, pad it.`
    -   このコメントは、ARM64のスタックフレームアライメント要件を明確に説明しています。スタックフレームサイズ（リターンアドレスを保存するLRレジスタの領域を含まない）は、0であるか、または16で割った余りが8である必要があります。

3.  `if frame != 0 && frame%16 != 8 {`
    `    frame += 8`
    `}`
    -   この`if`ブロックが追加されたパディングロジックです。
    -   `frame != 0`: スタックフレームが空でない場合（つまり、何らかのスタック領域が割り当てられている場合）にのみ、アライメントチェックを行います。空のフレームはアライメントの問題を引き起こしません。
    -   `frame%16 != 8`: 計算された`frame`サイズが、ARM64の要件である「16で割った余りが8」を満たしていない場合。
    -   この両方の条件が真の場合、`frame += 8`によってスタックフレームサイズに8バイトが追加されます。これにより、`frame`サイズは次の「16で割った余りが8」となる値に調整されます。例えば、`frame`が16の倍数だった場合、8を加えることで`8 mod 16`を満たすようになります。

この変更により、`ptxt.To.Offset = int64(frame)`で設定される最終的なスタックフレームサイズが、常にARM64のABI要件を満たすようになり、`zerorange`の誤動作とそれに伴うGCの問題が解決されます。

## 変更の背景

コンパイラがソースコードを中間表現に変換する際、特に条件分岐の処理において、論理的には冗長な制御フローが生成されることがあります。例えば、`if`文の`then`ブロックと`else`ブロックがどちらも同じターゲットブロックへジャンプするだけの場合、その`if`文自体が不要になり、条件判定の後に直接ターゲットブロックへ進むことができます。

元のコード例:
```go
func f(a bool, x int) int {
        v := 0
        if a {
                v = -1
        } else {
                v = -1
        }
        return x | v
}
```
この関数では、`a`の値に関わらず`v`は最終的に`-1`になります。しかし、コンパイラが単純にこのコードをSSA形式に変換すると、`if`文に対応する分岐ブロックが生成され、両方の分岐が同じ後続ブロックへジャンプする形になります。これは「デジェネレートな制御ブロック」と呼ばれ、実行時には無駄な分岐命令やブロックのオーバーヘッドを発生させる可能性があります。

このコミットは、このような冗長な制御フローを検出し、より効率的な形に変換することで、生成されるアセンブリコードのサイズを削減し、実行性能を向上させることを目的としています。

## 前提知識の解説

### SSA (Static Single Assignment)

SSA (Static Single Assignment) は、コンパイラの最適化段階で用いられる中間表現の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が大幅に簡素化されます。例えば、`x = a + b; x = c + d;` のようなコードは、SSA形式では `x1 = a + b; x2 = c + d;` のように変換され、各代入が新しい「バージョン」の変数を生成します。

### GoコンパイラのSSAバックエンド

Goコンパイラは、Go 1.7以降、最適化の主要な部分にSSA形式の中間表現を使用しています。ソースコードはまずAST (Abstract Syntax Tree) にパースされ、その後SSA形式に変換されます。SSA形式に変換されたコードは、様々な最適化パス（デッドコード削除、定数伝播、共通部分式除去など）を経て、最終的に機械語に変換されます。`cmd/compile/internal/ssa` パッケージは、このSSA形式の生成と最適化を担当するGoコンコンパイラの重要な部分です。

### 制御フローグラフ (Control Flow Graph - CFG)

制御フローグラフ (CFG) は、プログラムの実行可能なパスを抽象的に表現したグラフ構造です。
- **基本ブロック (Basic Block)**: 常に先頭から末尾まで実行される命令のシーケンスです。分岐命令やジャンプ命令は基本ブロックの末尾にのみ現れ、ラベルは基本ブロックの先頭にのみ現れます。
- **エッジ (Edge)**: 基本ブロック間の制御フローの遷移を表します。例えば、`if`文は条件判定ブロックから二つの後続ブロックへのエッジを持ちます。
- **先行ブロック (Predecessor)**: あるブロックに制御を渡す可能性のあるブロック。
- **後続ブロック (Successor)**: あるブロックから制御を受け取る可能性のあるブロック。

### デジェネレートな制御ブロック (Degenerate Control Blocks)

このコミットの文脈における「デジェネレートな制御ブロック」とは、論理的には不要であるにもかかわらず、制御フローグラフ上に存在するブロックを指します。特に、`if`文の両方の分岐が同じターゲットブロックに到達する場合や、単一のジャンプ命令しか含まない空のブロックが連鎖している場合などが該当します。これらはコードの可読性には影響しませんが、コンパイラが生成する中間表現や最終的な機械語において冗長な命令や分岐を招く可能性があります。

### Phi関数 (Phi Functions)

SSA形式において、複数の制御フローパスが合流する点（例えば`if-else`文の後に続くブロック）では、異なるパスで代入された同じ論理変数（SSA形式では異なるバージョンを持つ）の値を結合する必要があります。この結合を行うのがPhi関数です。Phi関数は、どのパスから制御が来たかに応じて適切な変数のバージョンを選択します。このコミットの最適化では、Phi関数が存在しない、または単純化可能な場合にのみ適用されます。これは、Phi関数が存在すると、変数の値がパスによって異なる可能性があり、単純なブロックの結合ができないためです。

### クリティカルエッジ (Critical Edges)

クリティカルエッジとは、複数の先行ブロックを持つブロックへのエッジのうち、その先行ブロックが複数の後続ブロックを持つ場合のエッジを指します。つまり、「多対多」の接続を持つエッジです。多くのコンパイラ最適化では、クリティカルエッジが存在すると複雑になるため、通常はクリティカルエッジを分割（エッジ間に新しい空のブロックを挿入）して「多対一」または「一対多」の形に変換します。このコミットの最適化では、クリティカルエッジを導入しないように注意が払われています。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/ssa/fuse.go` ファイル内の`fuse`関数を拡張し、制御フローグラフの簡素化をより積極的に行います。

### `fuse`関数の変更点

以前の`fuse`関数は、`BlockPlain`（無条件ジャンプ）ブロックが単一の先行ブロックを持つ後続ブロックに接続されている場合にのみ、それらを結合する単純な最適化を行っていました。このコミットでは、`fuse`関数がループ構造に変更され、`fuseBlockIf`と`fuseBlockPlain`という二つの新しいヘルパー関数を繰り返し呼び出すようになりました。これにより、最適化が固定点に達するまで（つまり、それ以上変更がなくなるまで）繰り返し適用されます。

```go
func fuse(f *Func) {
	for changed := true; changed; { // 変更がなくなるまでループ
		changed = false
		for _, b := range f.Blocks {
			changed = fuseBlockIf(b) || changed // BlockIfの最適化
			changed = fuseBlockPlain(b) || changed // BlockPlainの最適化
		}
	}
}
```

### `fuseBlockIf`関数

`fuseBlockIf`関数は、`BlockIf`（条件分岐）ブロックの最適化を担当します。特に、以下のような「デジェネレートな制御ブロック」のパターンを検出して簡素化します。

```
   b       b          b
  / \      | \      / |
 s0  s1    |  s1   s0 |
  \ /      | /      \ |
   ss      ss        ss
```

ここで、`b`は`BlockIf`ブロック、`s0`と`s1`は`b`の二つの後続ブロック、`ss`は`s0`と`s1`が合流するブロックです。

この関数は、以下の条件が満たされる場合に最適化を適用します。
1.  `b`が`BlockIf`である。
2.  `s0`と`s1`がどちらも空の`BlockPlain`ブロックである（値を持たず、単一の先行ブロックを持つ）。または、片方のみが空の`BlockPlain`である。
3.  `s0`と`s1`が最終的に同じブロック`ss`に合流する。
4.  合流先のブロック`ss`がPhi関数を含まない。Phi関数が存在する場合、異なるパスから来た変数の値を結合する必要があるため、単純な結合はできません。

これらの条件が満たされる場合、`b`から`s0`と`s1`を経由して`ss`へ向かう制御フローは、`b`から直接`ss`へ向かう制御フローに置き換えられます。これにより、`s0`と`s1`のブロックは不要となり、`BlockInvalid`としてマークされ、削除されます。`b`の`Kind`は`BlockPlain`に変更され、`Control`は`nil`に、`Succs`は`ss`のみを含むように更新されます。この変更により、`b`は単一の後続ブロックを持つことになり、クリティカルエッジは導入されません。

### `fuseBlockPlain`関数

`fuseBlockPlain`関数は、以前の`fuse`関数のロジックをカプセル化したものです。`BlockPlain`ブロック（無条件ジャンプ）が、単一の先行ブロックを持つ後続ブロック`c`に接続されている場合に、`b`と`c`を結合します。
1.  `b`が`BlockPlain`である。
2.  `b`の唯一の後続ブロック`c`が、`b`を唯一の先行ブロックとして持つ。

これらの条件が満たされる場合、`b`の持つすべての値は`c`に移動され、`b`の先行ブロックは`c`の先行ブロックとして設定されます。その後、`b`は`BlockInvalid`としてマークされ、削除されます。これにより、`b`と`c`は一つのブロックにマージされ、制御フローが簡素化されます。

### 最適化の例の解説

コミットメッセージに示された関数`f`の例を再掲します。
```go
func f(a bool, x int) int {
        v := 0
        if a {
                v = -1
        } else {
                v = -1
        }
        return x | v
}
```
この関数では、`if a { v = -1 } else { v = -1 }` の部分がデジェネレートな制御ブロックの典型例です。`a`が`true`でも`false`でも、`v`は`-1`に設定されます。

**変更前 (Before this change):**
SSA形式では、`if`文に対応する条件分岐ブロックが生成され、`a`の評価結果に基づいて二つのパスに分岐します。しかし、両方のパスが最終的に`v = -1`を実行するブロックに合流するため、無駄な分岐と合流が発生します。アセンブリコードの抜粋では、`JEQ 2824`という条件ジャンプ命令が見られます。これは、`a`が`false`の場合にラベル`2824`へジャンプすることを示しており、`if`文の分岐が実際に存在していることを意味します。

**変更後 (After this change):**
`fuseBlockIf`の最適化により、`if`文の分岐が冗長であると判断され、削除されます。結果として、`v = -1`の代入が直接実行されるようになり、条件分岐命令がなくなります。アセンブリコードの抜粋では、`JEQ 2824`命令が消え、`MOVQ $-1, "".~r2+16(FP)`（`v = -1`に相当）が直接実行されるようになっています。これにより、命令数が削減され、より効率的なコードが生成されます。

### `fuseBlockIf`関数 (新規追加)

```go
func fuseBlockIf(b *Block) bool {
	if b.Kind != BlockIf {
		return false
	}

	var ss0, ss1 *Block
	s0 := b.Succs[0]
	// s0が空のBlockPlainであるかチェック
	if s0.Kind != BlockPlain || len(s0.Preds) != 1 || len(s0.Values) != 0 {
		s0, ss0 = nil, s0 // s0が条件を満たさない場合、s0はnil、ss0は元のs0
	} else {
		ss0 = s0.Succs[0] // s0が条件を満たす場合、ss0はs0の後続
	}
	s1 := b.Succs[1]
	// s1が空のBlockPlainであるかチェック
	if s1.Kind != BlockPlain || len(s1.Preds) != 1 || len(s1.Values) != 0 {
		s1, ss1 = nil, s1 // s1が条件を満たさない場合、s1はnil、ss1は元のs1
	} else {
		ss1 = s1.Succs[0] // s1が条件を満たす場合、ss1はs1の後続
	}

	if ss0 != ss1 { // 両方のパスが同じブロックに合流しない場合は最適化しない
		return false
	}
	ss := ss0 // 合流先のブロック

	// ssにPhi関数がある場合は最適化しない
	for _, v := range ss.Values {
		if v.Op == OpPhi {
			return false
		}
	}

	// s0とs1が空のBlockPlainであれば、ssからそれらの先行ブロックとしての参照を削除
	if s0 != nil {
		ss.removePred(s0)
	}
	if s1 != nil {
		ss.removePred(s1)
	}
	if s0 != nil && s1 != nil {
		// 両方のエッジが削除された場合、bからssへの新しいエッジを追加
		ss.Preds = append(ss.Preds, b)
	}
	b.Kind = BlockPlain // bをBlockPlainに変更
	b.Control = nil     // 制御値をクリア
	b.Succs = append(b.Succs[:0], ss) // 後続をssのみに設定

	// s0とs1を無効化（ゴミとしてマーク）
	if s0 != nil {
		s0.Kind = BlockInvalid
		s0.Values = nil
		s0.Succs = nil
		s0.Preds = nil
	}
	if s1 != nil {
		s1.Kind = BlockInvalid
		s1.Values = nil
		s1.Succs = nil
		s1.Preds = nil
	}
	return true // 変更があったことを示す
}
```
この関数は、`BlockIf`ブロック`b`が、その両方の分岐（`s0`と`s1`）が最終的に同じブロック`ss`に合流し、かつ`s0`と`s1`が空の`BlockPlain`である場合に、`b`を直接`ss`に接続する`BlockPlain`に変換します。`ss`にPhi関数がないことを確認することで、値のセマンティクスが維持されます。`removePred`は、ブロックの先行ブロックリストから特定のブロックを削除するヘルパー関数です。最後に、不要になった`s0`と`s1`ブロックは`BlockInvalid`としてマークされ、ガベージコレクションの対象となります。

### `fuseBlockPlain`関数 (既存ロジックの再実装)

```go
func fuseBlockPlain(b *Block) bool {
	if b.Kind != BlockPlain {
		return false
	}

	c := b.Succs[0] // bの唯一の後続ブロック
	if len(c.Preds) != 1 { // cが単一の先行ブロックを持つ場合のみ
		return false
	}

	// bの持つすべての値をcに移動
	for _, v := range b.Values {
		v.Block = c
		c.Values = append(c.Values, v)
	}

	// b->cのエッジをpreds(b) -> cに置き換え
	c.predstorage[0] = nil
	if len(b.Preds) > len(b.predstorage) {
		c.Preds = b.Preds
	} else {
		c.Preds = append(c.predstorage[:0], b.Preds...)
	}
	for _, p := range c.Preds {
		for i, q := range p.Succs {
			if q == b {
				p.Succs[i] = c // bの先行ブロックからcへのエッジを更新
			}
		}
	}
	if f := b.Func; f.Entry == b { // bがエントリブロックの場合、cを新しいエントリブロックに設定
		f.Entry = c
	}

	// bを無効化（ゴミとしてマーク）
	b.Kind = BlockInvalid
	b.Values = nil
	b.Preds = nil
	b.Succs = nil
	return true // 変更があったことを示す
}
```
この関数は、`BlockPlain`ブロック`b`と、その唯一の後続ブロック`c`を結合します。ただし、`c`が`b`を唯一の先行ブロックとして持つ場合に限ります。これにより、`b`の命令は`c`に移動され、`b`は削除されます。これは、連続する二つのブロックを一つにまとめる基本的な最適化です。

## 変更の背景

コンパイラがソースコードを中間表現に変換する際、特に条件分岐の処理において、論理的には冗長な制御フローが生成されることがあります。例えば、`if`文の`then`ブロックと`else`ブロックがどちらも同じターゲットブロックへジャンプするだけの場合、その`if`文自体が不要になり、条件判定の後に直接ターゲットブロックへ進むことができます。

元のコード例:
```go
func f(a bool, x int) int {
        v := 0
        if a {
                v = -1
        } else {
                v = -1
        }
        return x | v
}
```
この関数では、`a`の値に関わらず`v`は最終的に`-1`になります。しかし、コンパイラが単純にこのコードをSSA形式に変換すると、`if`文に対応する分岐ブロックが生成され、両方の分岐が同じ後続ブロックへジャンプする形になります。これは「デジェネレートな制御ブロック」と呼ばれ、実行時には無駄な分岐命令やブロックのオーバーヘッドを発生させる可能性があります。

このコミットは、このような冗長な制御フローを検出し、より効率的な形に変換することで、生成されるアセンブリコードのサイズを削減し、実行性能を向上させることを目的としています。

## 前提知識の解説

### SSA (Static Single Assignment)

SSA (Static Single Assignment) は、コンパイラの最適化段階で用いられる中間表現の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が大幅に簡素化されます。例えば、`x = a + b; x = c + d;` のようなコードは、SSA形式では `x1 = a + b; x2 = c + d;` のように変換され、各代入が新しい「バージョン」の変数を生成します。

### GoコンパイラのSSAバックエンド

Goコンパイラは、Go 1.7以降、最適化の主要な部分にSSA形式の中間表現を使用しています。ソースコードはまずAST (Abstract Syntax Tree) にパースされ、その後SSA形式に変換されます。SSA形式に変換されたコードは、様々な最適化パス（デッドコード削除、定数伝播、共通部分式除去など）を経て、最終的に機械語に変換されます。`cmd/compile/internal/ssa` パッケージは、このSSA形式の生成と最適化を担当するGoコンコンパイラの重要な部分です。

### 制御フローグラフ (Control Flow Graph - CFG)

制御フローグラフ (CFG) は、プログラムの実行可能なパスを抽象的に表現したグラフ構造です。
- **基本ブロック (Basic Block)**: 常に先頭から末尾まで実行される命令のシーケンスです。分岐命令やジャンプ命令は基本ブロックの末尾にのみ現れ、ラベルは基本ブロックの先頭にのみ現れます。
- **エッジ (Edge)**: 基本ブロック間の制御フローの遷移を表します。例えば、`if`文は条件判定ブロックから二つの後続ブロックへのエッジを持ちます。
- **先行ブロック (Predecessor)**: あるブロックに制御を渡す可能性のあるブロック。
- **後続ブロック (Successor)**: あるブロックから制御を受け取る可能性のあるブロック。

### デジェネレートな制御ブロック (Degenerate Control Blocks)

このコミットの文脈における「デジェネレートな制御ブロック」とは、論理的には不要であるにもかかわらず、制御フローグラフ上に存在するブロックを指します。特に、`if`文の両方の分岐が同じターゲットブロックに到達する場合や、単一のジャンプ命令しか含まない空のブロックが連鎖している場合などが該当します。これらはコードの可読性には影響しませんが、コンパイラが生成する中間表現や最終的な機械語において冗長な命令や分岐を招く可能性があります。

### Phi関数 (Phi Functions)

SSA形式において、複数の制御フローパスが合流する点（例えば`if-else`文の後に続くブロック）では、異なるパスで代入された同じ論理変数（SSA形式では異なるバージョンを持つ）の値を結合する必要があります。この結合を行うのがPhi関数です。Phi関数は、どのパスから制御が来たかに応じて適切な変数のバージョンを選択します。このコミットの最適化では、Phi関数が存在しない、または単純化可能な場合にのみ適用されます。これは、Phi関数が存在すると、変数の値がパスによって異なる可能性があり、単純なブロックの結合ができないためです。

### クリティカルエッジ (Critical Edges)

クリティカルエッジとは、複数の先行ブロックを持つブロックへのエッジのうち、その先行ブロックが複数の後続ブロックを持つ場合のエッジを指します。つまり、「多対多」の接続を持つエッジです。多くのコンパイラ最適化では、クリティカルエッジが存在すると複雑になるため、通常はクリティカルエッジを分割（エッジ間に新しい空のブロックを挿入）して「多対一」または「一対多」の形に変換します。このコミットの最適化では、クリティカルエッジを導入しないように注意が払われています。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/ssa/fuse.go` ファイル内の`fuse`関数を拡張し、制御フローグラフの簡素化をより積極的に行います。

### `fuse`関数の変更点

以前の`fuse`関数は、`BlockPlain`（無条件ジャンプ）ブロックが単一の先行ブロックを持つ後続ブロックに接続されている場合にのみ、それらを結合する単純な最適化を行っていました。このコミットでは、`fuse`関数がループ構造に変更され、`fuseBlockIf`と`fuseBlockPlain`という二つの新しいヘルパー関数を繰り返し呼び出すようになりました。これにより、最適化が固定点に達するまで（つまり、それ以上変更がなくなるまで）繰り返し適用されます。

```go
func fuse(f *Func) {
	for changed := true; changed; { // 変更がなくなるまでループ
		changed = false
		for _, b := range f.Blocks {
			changed = fuseBlockIf(b) || changed // BlockIfの最適化
			changed = fuseBlockPlain(b) || changed // BlockPlainの最適化
		}
	}
}
```

### `fuseBlockIf`関数

`fuseBlockIf`関数は、`BlockIf`（条件分岐）ブロックの最適化を担当します。特に、以下のような「デジェネレートな制御ブロック」のパターンを検出して簡素化します。

```
   b       b          b
  / \      | \      / |
 s0  s1    |  s1   s0 |
  \ /      | /      \ |
   ss      ss        ss
```

ここで、`b`は`BlockIf`ブロック、`s0`と`s1`は`b`の二つの後続ブロック、`ss`は`s0`と`s1`が合流するブロックです。

この関数は、以下の条件が満たされる場合に最適化を適用します。
1.  `b`が`BlockIf`である。
2.  `s0`と`s1`がどちらも空の`BlockPlain`ブロックである（値を持たず、単一の先行ブロックを持つ）。または、片方のみが空の`BlockPlain`である。
3.  `s0`と`s1`が最終的に同じブロック`ss`に合流する。
4.  合流先のブロック`ss`がPhi関数を含まない。Phi関数が存在する場合、異なるパスから来た変数の値を結合する必要があるため、単純な結合はできません。

これらの条件が満たされる場合、`b`から`s0`と`s1`を経由して`ss`へ向かう制御フローは、`b`から直接`ss`へ向かう制御フローに置き換えられます。これにより、`s0`と`s1`のブロックは不要となり、`BlockInvalid`としてマークされ、削除されます。`b`の`Kind`は`BlockPlain`に変更され、`Control`は`nil`に、`Succs`は`ss`のみを含むように更新されます。この変更により、`b`は単一の後続ブロックを持つことになり、クリティカルエッジは導入されません。

### `fuseBlockPlain`関数

`fuseBlockPlain`関数は、以前の`fuse`関数のロジックをカプセル化したものです。`BlockPlain`ブロック（無条件ジャンプ）が、単一の先行ブロックを持つ後続ブロック`c`に接続されている場合に、`b`と`c`を結合します。
1.  `b`が`BlockPlain`である。
2.  `b`の唯一の後続ブロック`c`が、`b`を唯一の先行ブロックとして持つ。

これらの条件が満たされる場合、`b`の持つすべての値は`c`に移動され、`b`の先行ブロックは`c`の先行ブロックとして設定されます。その後、`b`は`BlockInvalid`としてマークされ、削除されます。これにより、`b`と`c`は一つのブロックにマージされ、制御フローが簡素化されます。

### 最適化の例の解説

コミットメッセージに示された関数`f`の例を再掲します。
```go
func f(a bool, x int) int {
        v := 0
        if a {
                v = -1
        } else {
                v = -1
        }
        return x | v
}
```
この関数では、`if a { v = -1 } else { v = -1 }` の部分がデジェネレートな制御ブロックの典型例です。`a`が`true`でも`false`でも、`v`は`-1`に設定されます。

**変更前 (Before this change):**
SSA形式では、`if`文に対応する条件分岐ブロックが生成され、`a`の評価結果に基づいて二つのパスに分岐します。しかし、両方のパスが最終的に`v = -1`を実行するブロックに合流するため、無駄な分岐と合流が発生します。アセンブリコードの抜粋では、`JEQ 2824`という条件ジャンプ命令が見られます。これは、`a`が`false`の場合にラベル`2824`へジャンプすることを示しており、`if`文の分岐が実際に存在していることを意味します。

**変更後 (After this change):**
`fuseBlockIf`の最適化により、`if`文の分岐が冗長であると判断され、削除されます。結果として、`v = -1`の代入が直接実行されるようになり、条件分岐命令がなくなります。アセンブリコードの抜粋では、`JEQ 2824`命令が消え、`MOVQ $-1, "".~r2+16(FP)`（`v = -1`に相当）が直接実行されるようになっています。これにより、命令数が削減され、より効率的なコードが生成されます。

## コアとなるコードの解説

### `fuse`関数 (変更後)

```go
func fuse(f *Func) {
	for changed := true; changed; { // 変更がなくなるまでループ
		changed = false
		for _, b := range f.Blocks {
			changed = fuseBlockIf(b) || changed // BlockIfの最適化を試行
			changed = fuseBlockPlain(b) || changed // BlockPlainの最適化を試行
		}
	}

```
この関数は、`changed`フラグが`true`である限り、`f.Blocks`内のすべてのブロックに対して`fuseBlockIf`と`fuseBlockPlain`を繰り返し適用します。いずれかのヘルパー関数が`true`を返した場合（つまり最適化が適用された場合）、`changed`フラグが`true`に設定され、次のイテレーションが実行されます。これにより、連鎖的な最適化が固定点に達するまで行われます。

### `fuseBlockIf`関数 (新規追加)

```go
func fuseBlockIf(b *Block) bool {
	if b.Kind != BlockIf {
		return false
	}

	var ss0, ss1 *Block
	s0 := b.Succs[0]
	// s0が空のBlockPlainであるかチェック
	if s0.Kind != BlockPlain || len(s0.Preds) != 1 || len(s0.Values) != 0 {
		s0, ss0 = nil, s0 // s0が条件を満たさない場合、s0はnil、ss0は元のs0
	} else {
		ss0 = s0.Succs[0] // s0が条件を満たす場合、ss0はs0の後続
	}
	s1 := b.Succs[1]
	// s1が空のBlockPlainであるかチェック
	if s1.Kind != BlockPlain || len(s1.Preds) != 1 || len(s1.Values) != 0 {
		s1, ss1 = nil, s1 // s1が条件を満たさない場合、s1はnil、ss1は元のs1
	} else {
		ss1 = s1.Succs[0] // s1が条件を満たす場合、ss1はs1の後続
	}

	if ss0 != ss1 { // 両方のパスが同じブロックに合流しない場合は最適化しない
		return false
	}
	ss := ss0 // 合流先のブロック

	// ssにPhi関数がある場合は最適化しない
	for _, v := range ss.Values {
		if v.Op == OpPhi {
			return false
		}
	}

	// s0とs1が空のBlockPlainであれば、ssからそれらの先行ブロックとしての参照を削除
	if s0 != nil {
		ss.removePred(s0)
	}
	if s1 != nil {
		ss.removePred(s1)
	}
	if s0 != nil && s1 != nil {
		// 両方のエッジが削除された場合、bからssへの新しいエッジを追加
		ss.Preds = append(ss.Preds, b)
	}
	b.Kind = BlockPlain // bをBlockPlainに変更
	b.Control = nil     // 制御値をクリア
	b.Succs = append(b.Succs[:0], ss) // 後続をssのみに設定

	// s0とs1を無効化（ゴミとしてマーク）
	if s0 != nil {
		s0.Kind = BlockInvalid
		s0.Values = nil
		s0.Succs = nil
		s0.Preds = nil
	}
	if s1 != nil {
		s1.Kind = BlockInvalid
		s1.Values = nil
		s1.Succs = nil
		s1.Preds = nil
	}
	return true // 変更があったことを示す
}
```
この関数は、`BlockIf`ブロック`b`が、その両方の分岐（`s0`と`s1`）が最終的に同じブロック`ss`に合流し、かつ`s0`と`s1`が空の`BlockPlain`である場合に、`b`を直接`ss`に接続する`BlockPlain`に変換します。`ss`にPhi関数がないことを確認することで、値のセマンティクスが維持されます。`removePred`は、ブロックの先行ブロックリストから特定のブロックを削除するヘルパー関数です。最後に、不要になった`s0`と`s1`ブロックは`BlockInvalid`としてマークされ、ガベージコレクションの対象となります。

### `fuseBlockPlain`関数 (既存ロジックの再実装)

```go
func fuseBlockPlain(b *Block) bool {
	if b.Kind != BlockPlain {
		return false
	}

	c := b.Succs[0] // bの唯一の後続ブロック
	if len(c.Preds) != 1 { // cが単一の先行ブロックを持つ場合のみ
		return false
	}

	// bの持つすべての値をcに移動
	for _, v := range b.Values {
		v.Block = c
		c.Values = append(c.Values, v)
	}

	// b->cのエッジをpreds(b) -> cに置き換え
	c.predstorage[0] = nil
	if len(b.Preds) > len(b.predstorage) {
		c.Preds = b.Preds
	} else {
		c.Preds = append(c.predstorage[:0], b.Preds...)
	}
	for _, p := range c.Preds {
		for i, q := range p.Succs {
			if q == b {
				p.Succs[i] = c // bの先行ブロックからcへのエッジを更新
			}
		}
	}
	if f := b.Func; f.Entry == b { // bがエントリブロックの場合、cを新しいエントリブロックに設定
		f.Entry = c
	}

	// bを無効化（ゴミとしてマーク）
	b.Kind = BlockInvalid
	b.Values = nil
	b.Preds = nil
	b.Succs = nil
	return true // 変更があったことを示す
}
```
この関数は、`BlockPlain`ブロック`b`と、その唯一の後続ブロック`c`を結合します。ただし、`c`が`b`を唯一の先行ブロックとして持つ場合に限ります。これにより、`b`の命令は`c`に移動され、`b`は削除されます。これは、連続する二つのブロックを一つにまとめる基本的な最適化です。

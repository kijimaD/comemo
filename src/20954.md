# [インデックス 20954] ファイルの概要

このコミットは、Goランタイムにおけるスタックトレースの最初のスタックフレームの行番号が正しく表示されない問題を修正します。特に、プログラムカウンタ（PC）の解釈が、シグナルハンドリングと通常の関数呼び出しで異なることに起因する不整合を解消します。

## 元コミット内容

Goランタイムのスタックトレース機能において、最初のスタックフレームの行番号が誤って表示される問題を修正します。この問題は、プログラムカウンタ（PC）の解釈が、シグナルハンドリングと通常の関数呼び出しで異なることに起因していました。

元々、`traceback`関数は主に予期せぬシグナル（例：セグメンテーション違反）が発生した際にスタックを出力するために使用されていました。この場合、初期PCはシグナルから直接取得され、そのまま使用されるべきでした。なぜなら、シグナルによって中断された時点の正確な命令ポインタを示すからです。

しかし、通常の関数呼び出し（`getcallerpc`、`gp->sched.pc`、`gp->syscallpc`など）の場合、PCは呼び出し元へのリターンアドレスを示します。Goのスタックトレースでは、通常、関数呼び出しが行われた`CALL`命令の行番号を表示することが期待されます。リターンアドレスは`CALL`命令の直後の命令のアドレスを指すため、正確な`CALL`命令の行番号を得るためにはPCから1を減算する必要がありました。

問題は、`traceback`コードがシグナルハンドリングの時代から引き継がれた「初期PCから1を減算しない」という厳格なルールを持っていたことです。これにより、通常の関数呼び出しから生成されるスタックトレースで、最初のフレームの行番号が1行ずれて表示されるというバグが発生していました。

## 変更の背景

この変更の背景には、Goランタイムのスタックトレース機能の利用範囲が拡大したことがあります。初期のGoランタイムでは、スタックトレースは主にクラッシュ時のデバッグ情報として、予期せぬシグナル（例：パニック）が発生した際にのみ生成されていました。このシナリオでは、シグナルによって中断された命令のPCがそのままスタックトレースの起点となるため、PCを調整する必要はありませんでした。

しかし、Goの進化とともに、スタックトレースはより多様な目的で利用されるようになりました。例えば、`runtime.Stack`関数によるプログラマティックなスタックトレースの取得、プロファイリングツール、ガベージコレクタのスタック走査などです。これらの新しい利用シナリオでは、スタックトレースの起点となるPCは、シグナルによる中断ではなく、通常の関数呼び出しのリターンアドレスや、ゴルーチンのスケジューリング情報から取得されることがほとんどでした。

このような状況下で、従来の「初期PCから1を減算しない」というルールが足かせとなり、特に`runtime.Stack`のような関数で取得されるスタックトレースの最初のフレームの行番号が、期待される`CALL`命令の行ではなく、その次の命令の行を指してしまうという不正確な情報を提供するようになりました。これは、デバッグやプロファイリングの際に混乱を招く原因となっていました。

この不整合を解消し、スタックトレースの正確性を向上させることが、このコミットの主要な目的です。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

*   **プログラムカウンタ (PC)**: CPUが次に実行する命令のアドレスを保持するレジスタです。スタックトレースでは、各関数呼び出し時点でのPCが記録され、どのコードが実行されていたかを示します。
*   **スタックポインタ (SP)**: 現在のスタックフレームの最上位（または最下位、アーキテクチャによる）のアドレスを指すレジスタです。関数呼び出しごとにスタックフレームが積まれ、SPが更新されます。
*   **リターンアドレス**: 関数が呼び出された際、呼び出し元の関数に戻るべき命令のアドレスです。通常、`CALL`命令の直後の命令のアドレスがリターンアドレスとしてスタックにプッシュされます。
*   **トラップ (Trap)**: CPUが例外的な状況（例：ゼロ除算、無効なメモリアクセス、シグナル）に遭遇した際に発生するイベントです。トラップが発生すると、CPUは現在の実行フローを中断し、特定のハンドラ（トラップハンドラやシグナルハンドラ）に制御を移します。トラップ時のPCは、トラップが発生した命令のアドレスを指します。
*   **スタックトレース**: プログラムの実行中に、現在アクティブな関数呼び出しの連鎖（コールスタック）を一覧表示したものです。各エントリは、関数名、ファイル名、行番号、およびPC（命令アドレス）を含みます。デバッグやエラー解析に不可欠な情報です。
*   **`CALL`命令とリターンアドレスの関係**: 多くのCPUアーキテクチャでは、`CALL`命令は次の命令のアドレス（リターンアドレス）をスタックにプッシュし、その後、呼び出される関数のエントリポイントにジャンプします。関数が終了すると、スタックからリターンアドレスをポップし、そのアドレスにジャンプして呼び出し元に戻ります。したがって、リターンアドレスは`CALL`命令の「次の行」を指すことになります。スタックトレースで`CALL`命令の行番号を表示するためには、リターンアドレスから1を減算して`CALL`命令のアドレスに戻る必要があります。

## 技術的詳細

このコミットの技術的詳細は、スタックトレース生成のコアロジックである`gentraceback`関数の引数変更と、それに関連するヘルパー関数の導入に集約されます。

1.  **`gentraceback`関数のシグネチャ変更**:
    *   変更前: `gentraceback(pc0 uintptr, sp0 uintptr, lr0 uintptr, gp *g, skip int, pcbuf *uintptr, max int, callback func(*stkframe, unsafe.Pointer) bool, v unsafe.Pointer, printall bool) int`
    *   変更後: `gentraceback(pc0 uintptr, sp0 uintptr, lr0 uintptr, gp *g, skip int, pcbuf *uintptr, max int, callback func(*stkframe, unsafe.Pointer) bool, v unsafe.Pointer, flags uint) int`
    *   最後の`printall bool`引数が`flags uint`に変更されました。これにより、`gentraceback`関数は単に「全て表示するかどうか」だけでなく、より柔軟な動作指定が可能になります。
    *   新しい`flags`には、以下の定数が定義されました（`src/runtime/runtime.h`で定義）：
        *   `TraceRuntimeFrames = 1<<0`: ランタイム内部関数フレームを含めるかどうか。
        *   `TraceTrap = 1<<1`: 初期PCとSPがトラップ（シグナルなど）から取得されたものであり、通常の関数呼び出しのリターンアドレスではないことを示すフラグ。

2.  **`TraceTrap`フラグの導入とPC調整ロジックの変更**:
    *   `gentraceback`関数内で、スタックフレームのPCを調整するロジックが変更されました。
    *   変更前は、`printall`が`true`でない限り、`frame.pc`が`f.entry`より大きく、かつ`waspanic`でない場合に`tracepc--`（PCを1減算）していました。
    *   変更後、この条件は`(n > 0 || flags&_TraceTrap == 0) && frame.pc > f.entry && !waspanic`となりました。
    *   重要なのは`flags&_TraceTrap == 0`の部分です。これは、`TraceTrap`フラグが設定されていない（つまり、初期PCがリターンアドレスであると想定される）場合にのみ、PCを1減算して`CALL`命令の行番号に合わせるようにします。`TraceTrap`が設定されている場合は、PCはそのまま使用されます。

3.  **`traceback`と`tracebacktrap`の導入**:
    *   既存の`traceback`関数は、`traceback1`という新しい内部関数を呼び出すように変更されました。`traceback`は、デフォルトで`flags`に`0`（`TraceTrap`なし）を渡します。これは、ほとんどのスタックトレースがリターンアドレスから始まるという一般的なケースに対応します。
    *   新しく`tracebacktrap`関数が導入されました。この関数も`traceback1`を呼び出しますが、`flags`に`_TraceTrap`を渡します。これは、シグナルハンドラなど、初期PCがトラップから取得された場合にのみ使用されます。

4.  **シグナルハンドラでの`tracebacktrap`の使用**:
    *   `src/runtime/os_plan9_386.c`, `src/runtime/os_plan9_amd64.c`, `src/runtime/os_windows_386.c`, `src/runtime/os_windows_amd64.c`, `src/runtime/signal_386.c`, `src/runtime/signal_amd64x.c`, `src/runtime/signal_arm.c`など、各OSおよびアーキテクチャのシグナルハンドラ内で、`runtime·traceback`の呼び出しが`runtime·tracebacktrap`に変更されました。これにより、シグナルによって中断された際のスタックトレースが正しく生成されるようになります。

5.  **その他の`gentraceback`呼び出しの更新**:
    *   `src/runtime/heapdump.c`, `src/runtime/mgc0.c`, `src/runtime/mprof.go`, `src/runtime/proc.c`, `src/runtime/stack.c`など、`gentraceback`を呼び出している他の箇所も、`printall`引数を`0`（または`TraceTrap`が不要な場合は`0`）に更新されました。

これらの変更により、Goランタイムは、スタックトレースの起点となるPCが「リターンアドレス」であるか「トラップPC」であるかによって、適切な行番号の調整を行うことができるようになり、スタックトレースの正確性が向上しました。

## コアとなるコードの解説

### `src/runtime/runtime.h`の変更

*   `enum`ブロックが追加され、`TraceRuntimeFrames`と`TraceTrap`という2つのフラグが定義されました。これらは`gentraceback`関数の新しい`flags`引数で使用されるビットフラグです。
    *   `TraceRuntimeFrames = 1<<0`: ランタイム内部のフレームをスタックトレースに含めるかどうかを制御します。
    *   `TraceTrap = 1<<1`: 初期PCがトラップ（シグナルなど）によって取得されたものであり、リターンアドレスではないことを示します。このフラグが重要で、PCの調整ロジックに影響を与えます。
*   `runtime·gentraceback`の宣言が更新され、最後の引数が`bool`から`uintgo`（Goの`uint`に対応するCの型）に変更されました。
*   `runtime·tracebacktrap`という新しい関数の宣言が追加されました。

### `src/runtime/traceback.go`の変更

1.  **`gentraceback`関数のシグネチャ変更**:
    *   `func gentraceback(..., printall bool) int` から `func gentraceback(..., flags uint) int` へと変更されました。これにより、`gentraceback`はより汎用的なスタックトレース生成ロジックを提供できるようになります。

2.  **PC調整ロジックの変更**:
    *   `gentraceback`関数内のスタックフレームのPCを調整する部分が変更されました。
    *   旧: `if printall || showframe(f, gp) { ... if n > 0 && frame.pc > f.entry && !waspanic { tracepc-- } }`
    *   新: `if (flags&_TraceRuntimeFrames) != 0 || showframe(f, gp) { ... if (n > 0 || flags&_TraceTrap == 0) && frame.pc > f.entry && !waspanic { tracepc-- } }`
    *   この変更の核心は、`tracepc--`（PCを1減算して`CALL`命令の行番号に合わせる処理）の条件に`flags&_TraceTrap == 0`が追加されたことです。
        *   `TraceTrap`フラグが設定されていない場合（`flags&_TraceTrap == 0`が真）、これは初期PCがリターンアドレスであると見なされ、`CALL`命令の行番号を得るために`tracepc`がデクリメントされます。
        *   `TraceTrap`フラグが設定されている場合（`flags&_TraceTrap == 0`が偽）、`tracepc`はデクリメントされず、トラップが発生した正確な命令のアドレスが使用されます。

3.  **`traceback`、`tracebacktrap`、`traceback1`の導入**:
    *   `traceback`関数は、新しい内部ヘルパー関数`traceback1`を呼び出すように変更されました。`traceback`は`traceback1`に`flags`として`0`を渡します。これは、通常のスタックトレース（リターンアドレスから始まる）のデフォルト動作となります。
    *   `tracebacktrap`関数が新しく追加されました。この関数も`traceback1`を呼び出しますが、`flags`として`_TraceTrap`を渡します。これにより、シグナルハンドラなど、トラップから始まるスタックトレースで正しいPCの解釈が行われます。
    *   `traceback1`関数は、`traceback`と`tracebacktrap`の両方から呼び出される共通のロジックをカプセル化します。この関数内で、ゴルーチンがシステムコールでブロックされている場合（`_Gsyscall`状態）に、`gp.syscallpc`と`gp.syscallsp`を使用してPCとSPを上書きし、さらに`flags &^= _TraceTrap`によって`_TraceTrap`フラグをクリアするロジックが追加されています。これは、システムコールからのPCはリターンアドレスとして扱われるべきであるためです。

4.  **`callers`と`gcallers`の更新**:
    *   `runtime.Callers`関数（Go言語から呼び出される）に対応する`callers`関数と、ゴルーチンのスタックを走査する`gcallers`関数も、`gentraceback`の最後の引数を`false`から`0`に変更しています。これは、これらの関数が取得するPCが通常リターンアドレスであるため、`TraceTrap`フラグは不要であることを示します。

### `test/fixedbugs/issue7690.go`の解説

このテストは、`runtime.Stack`関数が連続する行で呼び出された場合に、スタックトレースの最初のフレームの行番号が正しく報告されることを検証します。

```go
func main() {
	buf1 := make([]byte, 1000)
	buf2 := make([]byte, 1000)

	runtime.Stack(buf1, false)      // CALL is last instruction on this line
	n := runtime.Stack(buf2, false) // CALL is followed by load of result from stack

	// ... (バッファの調整と正規表現による行番号の抽出)

	n1, _ := strconv.Atoi(m1[1])
	n2, _ := strconv.Atoi(m2[1])
	if n1+1 != n2 {
		println("BUG: expect runtime.Stack on back to back lines, have", n1, n2)
		println(string(buf1))
		println(string(buf2))
	}
}
```

*   `runtime.Stack(buf1, false)`と`runtime.Stack(buf2, false)`が連続する2つの異なる行で呼び出されています。
*   コメントに「`CALL is last instruction on this line`」と「`CALL is followed by load of result from stack`」とあるように、`runtime.Stack`の呼び出しがそれぞれ異なる命令配置を持つことを示唆しています。
*   テストの目的は、`buf1`で取得したスタックトレースの`main.main`の行番号（`n1`）と、`buf2`で取得したスタックトレースの`main.main`の行番号（`n2`）が、`n1 + 1 == n2`という関係を満たすことを確認することです。
*   もし修正前のバグが存在していれば、`runtime.Stack`がリターンアドレスを`CALL`命令の行番号に調整しないため、`n1`と`n2`が期待通りに1行差にならない（例えば、両方とも同じ行を指してしまう、あるいは意図しない行を指す）可能性があります。
*   このテストは、`gentraceback`がリターンアドレスを正しく`CALL`命令の行番号に変換するようになったことを検証するものです。

## 元コミット内容

Goランタイムのスタックトレース機能において、最初のスタックフレームの行番号が誤って表示される問題を修正します。この問題は、プログラムカウンタ（PC）の解釈が、シグナルハンドリングと通常の関数呼び出しで異なることに起因していました。

元々、`traceback`関数は主に予期せぬシグナル（例：セグメンテーション違反）が発生した際にスタックを出力するために使用されていました。この場合、初期PCはシグナルから直接取得され、そのまま使用されるべきでした。なぜなら、シグナルによって中断された時点の正確な命令ポインタを示すからです。

しかし、通常の関数呼び出し（`getcallerpc`、`gp->sched.pc`、`gp->syscallpc`など）の場合、PCは呼び出し元へのリターンアドレスを示します。Goのスタックトレースでは、通常、関数呼び出しが行われた`CALL`命令の行番号を表示することが期待されます。リターンアドレスは`CALL`命令の直後の命令のアドレスを指すため、正確な`CALL`命令の行番号を得るためにはPCから1を減算する必要がありました。

問題は、`traceback`コードがシグナルハンドリングの時代から引き継がれた「初期PCから1を減算しない」という厳格なルールを持っていたことです。これにより、通常の関数呼び出しから生成されるスタックトレースで、最初のフレームの行番号が1行ずれて表示されるというバグが発生していました。

## 変更の背景

この変更の背景には、Goランタイムのスタックトレース機能の利用範囲が拡大したことがあります。初期のGoランタイムでは、スタックトレースは主にクラッシュ時のデバッグ情報として、予期せぬシグナル（例：パニック）が発生した際にのみ生成されていました。このシナリオでは、シグナルによって中断された命令のPCがそのままスタックトレースの起点となるため、PCを調整する必要はありませんでした。

しかし、Goの進化とともに、スタックトレースはより多様な目的で利用されるようになりました。例えば、`runtime.Stack`関数によるプログラマティックなスタックトレースの取得、プロファイリングツール、ガベージコレクタのスタック走査などです。これらの新しい利用シナリオでは、スタックトレースの起点となるPCは、シグナルによる中断ではなく、通常の関数呼び出しのリターンアドレスや、ゴルーチンのスケジューリング情報から取得されることがほとんどでした。

このような状況下で、従来の「初期PCから1を減算しない」というルールが足かせとなり、特に`runtime.Stack`のような関数で取得されるスタックトレースの最初のフレームの行番号が、期待される`CALL`命令の行ではなく、その次の命令の行を指してしまうという不正確な情報を提供するようになりました。これは、デバッグやプロファイリングの際に混乱を招く原因となっていました。

この不整合を解消し、スタックトレースの正確性を向上させることが、このコミットの主要な目的です。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

*   **プログラムカウンタ (PC)**: CPUが次に実行する命令のアドレスを保持するレジスタです。スタックトレースでは、各関数呼び出し時点でのPCが記録され、どのコードが実行されていたかを示します。
*   **スタックポインタ (SP)**: 現在のスタックフレームの最上位（または最下位、アーキテクチャによる）のアドレスを指すレジスタです。関数呼び出しごとにスタックフレームが積まれ、SPが更新されます。
*   **リターンアドレス**: 関数が呼び出された際、呼び出し元の関数に戻るべき命令のアドレスです。通常、`CALL`命令の直後の命令のアドレスがリターンアドレスとしてスタックにプッシュされます。
*   **トラップ (Trap)**: CPUが例外的な状況（例：ゼロ除算、無効なメモリアクセス、シグナル）に遭遇した際に発生するイベントです。トラップが発生すると、CPUは現在の実行フローを中断し、特定のハンドラ（トラップハンドラやシグナルハンドラ）に制御を移します。トラップ時のPCは、トラップが発生した命令のアドレスを指します。
*   **スタックトレース**: プログラムの実行中に、現在アクティブな関数呼び出しの連鎖（コールスタック）を一覧表示したものです。各エントリは、関数名、ファイル名、行番号、およびPC（命令アドレス）を含みます。デバッグやエラー解析に不可欠な情報です。
*   **`CALL`命令とリターンアドレスの関係**: 多くのCPUアーキテクチャでは、`CALL`命令は次の命令のアドレス（リターンアドレス）をスタックにプッシュし、その後、呼び出される関数のエントリポイントにジャンプします。関数が終了すると、スタックからリターンアドレスをポップし、そのアドレスにジャンプして呼び出し元に戻ります。したがって、リターンアドレスは`CALL`命令の「次の行」を指すことになります。スタックトレースで`CALL`命令の行番号を表示するためには、リターンアドレスから1を減算して`CALL`命令のアドレスに戻る必要があります。

    *   `traceback`関数は、新しい内部ヘルパー関数`traceback1`を呼び出すように変更されました。`traceback`は`traceback1`に`flags`として`0`を渡します。これは、通常のスタックトレース（リターンアドレスから始まる）のデフォルト動作となります。
    *   `tracebacktrap`関数が新しく追加されました。この関数も`traceback1`を呼び出しますが、`flags`として`_TraceTrap`を渡します。これにより、シグナルハンドラなど、トラップから始まるスタックトレースで正しいPCの解釈が行われます。
    *   `traceback1`関数は、`traceback`と`tracebacktrap`の両方から呼び出される共通のロジックをカプセル化します。この関数内で、ゴルーチンがシステムコールでブロックされている場合（`_Gsyscall`状態）に、`gp.syscallpc`と`gp.syscallsp`を使用してPCとSPを上書きし、さらに`flags &^= _TraceTrap`によって`_TraceTrap`フラグをクリアするロジックが追加されています。これは、システムコールからのPCはリターンアドレスとして扱われるべきであるためです。

4.  **`callers`と`gcallers`の更新**:
    *   `runtime.Callers`関数（Go言語から呼び出される）に対応する`callers`関数と、ゴルーチンのスタックを走査する`gcallers`関数も、`gentraceback`の最後の引数を`false`から`0`に変更しています。これは、これらの関数が取得するPCが通常リターンアドレスであるため、`TraceTrap`フラグは不要であることを示します。

### `test/fixedbugs/issue7690.go`の解説

このテストは、`runtime.Stack`関数が連続する行で呼び出された場合に、スタックトレースの最初のフレームの行番号が正しく報告されることを検証します。

```go
func main() {
	buf1 := make([]byte, 1000)
	buf2 := make([]byte, 1000)

	runtime.Stack(buf1, false)      // CALL is last instruction on this line
	n := runtime.Stack(buf2, false) // CALL is followed by load of result from stack

	// ... (バッファの調整と正規表現による行番号の抽出)

	n1, _ := strconv.Atoi(m1[1])
	n2, _ := strconv.Atoi(m2[1])
	if n1+1 != n2 {
		println("BUG: expect runtime.Stack on back to back lines, have", n1, n2)
		println(string(buf1))
		println(string(buf2))
	}
}
```

*   `runtime.Stack(buf1, false)`と`runtime.Stack(buf2, false)`が連続する2つの異なる行で呼び出されています。
*   コメントに「`CALL is last instruction on this line`」と「`CALL is followed by load of result from stack`」とあるように、`runtime.Stack`の呼び出しがそれぞれ異なる命令配置を持つことを示唆しています。
*   テストの目的は、`buf1`で取得したスタックトレースの`main.main`の行番号（`n1`）と、`buf2`で取得したスタックトレースの`main.main`の行番号（`n2`）が、`n1 + 1 == n2`という関係を満たすことを確認することです。
*   もし修正前のバグが存在していれば、`runtime.Stack`がリターンアドレスを`CALL`命令の行番号に調整しないため、`n1`と`n2`が期待通りに1行差にならない（例えば、両方とも同じ行を指してしまう、あるいは意図しない行を指す）可能性があります。
*   このテストは、`gentraceback`がリターンアドレスを正しく`CALL`命令の行番号に変換するようになったことを検証するものです。

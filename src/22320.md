# [インデックス 22320] ファイルの概要

このコミットは、Goコンパイラのアセンブラバックエンド、特にx86アーキテクチャ向けのコード生成において、`CMPPS`などのSIMD浮動小数点数比較命令の第3引数に関する型解釈の不整合を修正するものです。具体的には、アセンブリファイル内で定数として記述されているにもかかわらず、Goのアセンブラがそれをメモリ参照として誤って解釈してしまう問題を解決し、内部表現を修正することで、アセンブラのテーブルが期待する形式に合わせます。

## 元コミット内容

`cmd/internal/obj/x86`パッケージにおいて、`CMPPS`などの命令の第3引数で`TYPE_MEM`が渡された場合に対応するように変更します。これは、実際のアセンブリファイルが定数に`$`記号を付けずに記述しているためです。

## 変更の背景

Goコンパイラは、Go言語のソースコードを機械語に変換する過程で、中間表現を生成し、最終的にターゲットアーキテクチャ（この場合はx86）のアセンブリコードを生成します。この過程で、Go独自の「Plan 9 Assembly」と呼ばれるアセンブリ言語が使用されます。

このコミットの背景にある問題は、`CMPPS`（Compare Packed Single-Precision Floating-Point Values）のようなSIMD命令の第3引数に関するものです。通常、アセンブリ言語では即値（定数）を表現する際に特定の記号（例えばIntel構文では`$`、AT&T構文では`$`）を付加することが一般的です。しかし、Goのアセンブリファイルでは、これらの命令の第3引数に定数を記述する際に、この`$`記号が付加されていないケースがありました。

Goのアセンブラの内部処理では、命令のオペランド（引数）を`obj.TYPE_CONST`（定数）や`obj.TYPE_MEM`（メモリ参照）といった内部型で表現します。アセンブリファイルに`$`記号なしで記述された定数は、アセンブラの構文解析器によって誤ってメモリ参照（`TYPE_MEM`）として解釈されてしまう可能性がありました。

この誤った解釈は、アセンブラのバックエンドが命令を処理する際に問題を引き起こします。バックエンドは、命令のオペランドの型に基づいて適切な機械語コードを生成するための「テーブル」を参照しますが、このテーブルは定数には`TYPE_CONST`を、メモリ参照には`TYPE_MEM`を期待しています。もし定数が`TYPE_MEM`として渡されてしまうと、テーブルとの不整合が生じ、正しく機械語を生成できないか、あるいは誤ったコードを生成してしまう恐れがありました。

このコミットは、この「アセンブリファイルが実際に記述している形式（定数に`$`がない）」と「アセンブラの内部処理が期待する形式（定数は`TYPE_CONST`）」との間のギャップを埋めることを目的としています。

## 前提知識の解説

### Goのアセンブラ (Plan 9 Assembly)

Go言語は、独自のツールチェインを持ち、その中には独自のアセンブラが含まれています。このアセンブラが解釈するアセンブリ言語は「Plan 9 Assembly」として知られており、一般的なIntel構文やAT&T構文とは異なる特徴を持っています。

*   **構文**: Plan 9 Assemblyは、ソースオペランドが先に、デスティネーションオペランドが後に来るという、Intel構文とは逆の順序を採用しています（例: `MOVQ $1, AX` は `AX = 1` を意味する）。また、レジスタ名や命令名も独特です。
*   **目的**: Goのアセンブラは、Goランタイムや標準ライブラリのパフォーマンスクリティカルな部分、あるいは特定のハードウェア機能にアクセスする必要がある部分を記述するために使用されます。
*   **内部表現**: アセンブラは、アセンブリコードを解析し、`obj.Prog`（プログラム命令）のような内部データ構造に変換します。この`obj.Prog`は、命令の種類、オペランドの型、値などを保持します。

### Goの`obj`パッケージ

`cmd/internal/obj`パッケージは、Goコンパイラとアセンブラのバックエンドで、命令の抽象的な表現を扱うための重要なパッケージです。このパッケージは、アセンブリ命令のオペランドの型を定義する定数を含んでいます。

*   **`obj.TYPE_MEM`**: オペランドがメモリ位置を参照していることを示します。例えば、`MOVQ (AX), BX` の `(AX)` のような形式です。
*   **`obj.TYPE_CONST`**: オペランドが即値（定数）であることを示します。例えば、`MOVQ $1, AX` の `$1` のような形式です。
*   **`obj.TYPE_REG`**: オペランドがレジスタを参照していることを示します。例えば、`MOVQ AX, BX` の `AX` や `BX` のような形式です。

これらの型は、アセンブラが命令を正しく解釈し、機械語に変換するために不可欠です。

### x86 SIMD命令 (SSE, CMPPS)

SIMD (Single Instruction, Multiple Data) 命令は、単一の命令で複数のデータ要素に対して同じ操作を実行できる命令セットです。これにより、特にマルチメディア処理や科学技術計算など、大量のデータ並列処理が必要な場面で高いパフォーマンスを発揮します。

*   **SSE (Streaming SIMD Extensions)**: Intelによって導入されたSIMD命令セットの拡張です。浮動小数点数演算や整数演算を高速化するための命令が含まれています。
*   **`CMPPS` (Compare Packed Single-Precision Floating-Point Values)**: SSE命令セットの一部であり、パックされた単精度浮動小数点数（通常はXMMレジスタに格納された4つの単精度浮動小数点数）を比較する命令です。この命令は、2つのソースオペランドの対応する要素を比較し、結果（通常は真偽を示すマスク値）をデスティネーションオペランドに書き込みます。例えば、`CMPPS $0, X0, X1` のように使用され、X0レジスタの各要素と即値0を比較し、結果をX1レジスタに格納します。

### アセンブラにおける定数とメモリ参照

アセンブリ言語では、数値が即値（定数）として扱われるのか、それともメモリのアドレスやオフセットとして扱われるのかを明確に区別する必要があります。多くのx86アセンブラ構文では、即値の前に`$`記号を付けることで、それが定数であることを明示します。例えば、`MOV $10, %eax` は「即値10をEAXレジスタに移動する」という意味になります。一方、`MOV 10(%ebp), %eax` は「EBPレジスタの値に10を加えたアドレスにあるメモリの内容をEAXレジスタに移動する」という意味になり、`10`はオフセットとしてメモリ参照の一部と解釈されます。

GoのPlan 9 Assemblyでは、この`$`記号の有無が、オペランドが定数であるかメモリ参照であるかを区別する重要な手がかりとなります。しかし、今回の問題のように、特定の命令（`CMPPS`など）の文脈では、`$`記号なしで記述された数値が定数として意図されているにもかかわらず、アセンブラのフロントエンドがそれをメモリ参照として誤って解釈してしまうケースが存在しました。

## 技術的詳細

このコミットは、Goコンパイラのアセンブラにおける`CMPPS`、`ACMPPD`、`ACMPSD`、`ACMPSS`といったSIMD比較命令の第3引数（即値）の扱いに関する不整合を解消します。

問題の核心は、Goのアセンブリファイル内でこれらの命令の第3引数に定数を記述する際に、一般的なアセンブラ構文で即値を示す`$`記号が付加されていないことでした。例えば、`CMPPS $0, X0, X1` と書かれるべきところが、`CMPPS 0, X0, X1` のように記述されていた場合、アセンブラの構文解析器（`a.y`と`y.go`）は、この`0`をメモリ参照（`obj.TYPE_MEM`）として誤って解釈してしまう可能性がありました。

しかし、アセンブラのバックエンド（`obj6.go`）が命令を機械語に変換する際には、これらの命令の第3引数は定数（`obj.TYPE_CONST`）として扱われることを期待しています。この期待値と、フロントエンドでの誤った解釈との間にギャップが生じていました。

このコミットは、このギャップを埋めるために二段階のアプローチを取っています。

1.  **構文解析器の変更 (`a.y`, `y.go`)**:
    `CMPPS`などの命令の構文解析ルール（`spec8`）が変更されました。以前は第3引数を直接`$$.to`に割り当てていましたが、新しい`$$.from3`というフィールドを導入し、そこに第3引数を格納するようにしました。そして、`$$.to.Type`を一時的に`obj.TYPE_MEM`に設定しています。これは、構文解析の段階ではまだその引数が最終的に定数として扱われるべきかメモリ参照として扱われるべきかを完全に判断できないため、一旦メモリ型として受け入れるという設計思想に基づいています。この「to give library something to do」というコメントは、この一時的な設定が後続の処理（ライブラリ、つまりバックエンドの`obj6.go`）で適切に処理されることを示唆しています。

2.  **バックエンドの修正 (`obj6.go`)**:
    `progedit`関数は、Goのアセンブラが生成した命令（`obj.Prog`）を最終的な機械語に変換する前に、様々な後処理や最適化を行う場所です。この関数に新しいロジックが追加されました。
    この新しいロジックは、`ACMPPD`, `ACMPPS`, `ACMPSD`, `ACMPSS`命令を対象としています。もし命令のデスティネーションオペランド（`p.To`）の型が`obj.TYPE_MEM`であり、かつそのメモリ参照が実質的に「ゼロ」である（つまり、`Name`, `Reg`, `Index`, `Sym`のいずれも設定されていない）場合、それは本来定数として扱われるべきものであると判断し、`p.To.Type`を`obj.TYPE_CONST`に書き換えます。
    この修正により、フロントエンドで一時的に`TYPE_MEM`として解釈された定数が、バックエンドで正しく`TYPE_CONST`として認識され、アセンブラのテーブルが期待する形式に合致するようになります。これにより、正しい機械語コードが生成されるようになります。

要するに、このコミットは、アセンブリコードの記述スタイルとアセンブラの内部処理の間の不整合を、構文解析器とバックエンドの両方で調整することで解決しています。フロントエンドは柔軟に受け入れ、バックエンドで最終的な型を確定させるという、Goコンパイラの堅牢な設計パターンを示しています。

## コアとなるコードの解説

### `src/cmd/internal/obj/x86/obj6.go` の変更

このファイルは、Goコンパイラのアセンブラバックエンドの一部であり、x86アーキテクチャ固有の命令処理を担当しています。`progedit`関数は、アセンブリ命令のプログラム表現（`obj.Prog`）を編集・変換する役割を担います。

追加されたコードブロックは、`ACMPPD`, `ACMPPS`, `ACMPSD`, `ACMPSS`というSIMD浮動小数点数比較命令に特化しています。これらの命令は、通常、第3引数に即値（定数）を取ります。

```go
switch p.As {
case ACMPPD, ACMPPS, ACMPSD, ACMPSS:
	if p.To.Type == obj.TYPE_MEM && p.To.Name == obj.NAME_NONE && p.To.Reg == REG_NONE && p.To.Index == REG_NONE && p.To.Sym == nil {
		p.To.Type = obj.TYPE_CONST
	}
}
```

この`if`文の条件は非常に重要です。
*   `p.To.Type == obj.TYPE_MEM`: 命令のデスティネーションオペランド（`p.To`）がメモリ型として解釈されていることを確認します。
*   `p.To.Name == obj.NAME_NONE && p.To.Reg == REG_NONE && p.To.Index == REG_NONE && p.To.Sym == nil`: これは、そのメモリ参照が実際にはどのレジスタ、インデックス、シンボル、名前にも関連付けられていない、つまり「実質的にゼロオフセットのメモリ参照」であることを意味します。アセンブリファイルで`$`記号なしで記述された定数（例: `0`）が、構文解析器によってこのような「空のメモリ参照」として誤って解釈されるケースに対応しています。

これらの条件がすべて満たされる場合、それは本来定数として扱われるべきオペランドが誤ってメモリ型として認識されている状況であると判断し、`p.To.Type = obj.TYPE_CONST`によって、そのオペランドの型を`obj.TYPE_CONST`（定数）に修正します。これにより、後続の機械語生成プロセスで、このオペランドが正しく定数として扱われるようになります。

### `src/cmd/old6a/a.y` および `src/cmd/old6a/y.go` の変更

これらのファイルは、Goのアセンブラのフロントエンド、特に構文解析器（Yacc/Bisonによって生成されたパーサー）に関連しています。`a.y`はYaccのソースファイルであり、`y.go`はその`a.y`から生成されたGoのソースファイルです。

変更された`spec8`ルールは、`CMPPS`や`CMPPD`のような命令の構文を定義しています。

```yacc
spec8:	/* CMPPS/CMPPD */
 	rem ',' reg ',' con
 	{
 		$$.from = $1;
-		$$.to = $3;
+		$$.from3 = $3;
+		$$.to.Type = obj.TYPE_MEM; // to give library something to do
 		$$.to.Offset = $5;
 	}
```

以前は、第3引数（`$3`、`con`トークンに対応）が直接`$$.to`に割り当てられていました。しかし、この変更では、
*   `$$.from3 = $3;`: 新しいフィールド`from3`が導入され、第3引数がそこに格納されます。これは、命令によっては3つのオペランドを持つものがあり、その3番目のオペランドを明示的に扱うための構造的な変更です。
*   `$$.to.Type = obj.TYPE_MEM; // to give library something to do`: ここが重要なポイントです。構文解析の段階では、第3引数が定数であるにもかかわらず、一旦`obj.TYPE_MEM`としてマークされます。コメントにある「to give library something to do」は、この一時的な型設定が、後続の処理（つまり、`obj6.go`の`progedit`関数のようなバックエンドの「ライブラリ」）によって適切に修正されることを意図していることを示しています。これは、アセンブラのフロントエンドとバックエンドの間で、オペランドの型に関する責任を分担する設計パターンです。フロントエンドは構文的に可能な限り解釈し、バックエンドが最終的なセマンティックな修正を行うという流れです。

`y.go`の変更は、`a.y`の変更がGoコードに反映されたものであり、主に`yyVAL.addr2.from3`への割り当てと、`yyVAL.addr2.to.Type = obj.TYPE_MEM`の設定、そしてコードの追加による行番号のずれの修正が含まれています。

これらの変更により、Goのアセンブラは、`CMPPS`などの命令における定数の記述方法の多様性に対応できるようになり、より堅牢なコード生成が可能になりました。

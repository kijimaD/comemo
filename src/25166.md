# [インデックス 25166] ファイルの概要

このコミットは、Goランタイムにおける`amd64p32`アーキテクチャ向けの`memmove`および`memclr`アセンブリルーチンの最適化とバグ修正に関するものです。具体的には、これらのメモリ操作関数がポインタの整合性を損なう可能性のある挙動を修正し、ガベージコレクタが部分的にコピーされたポインタを観測するのを防ぎます。

## コミット

Author: Austin Clements <austin@google.com>
Date:   Fri Oct 2 18:17:54 2015 -0400

    runtime: use 4 byte writes in amd64p32 memmove/memclr

    Currently, amd64p32's memmove and memclr use 8 byte writes as much as
    possible and 1 byte writes for the tail of the object. However, if an
    object ends with a 4 byte pointer at an 8 byte aligned offset, this
    may copy/zero the pointer field one byte at a time, allowing the
    garbage collector to observe a partially copied pointer.

    Fix this by using 4 byte writes instead of 8 byte writes.

    Updates #12552.

## 元コミット内容

`amd64p32`アーキテクチャにおける`memmove`および`memclr`関数は、可能な限り8バイト単位で書き込みを行い、残りの部分（末尾）を1バイト単位で処理していました。しかし、このアプローチには問題がありました。オブジェクトの末尾が8バイトアラインされたオフセットに4バイトのポインタで終わる場合、そのポインタフィールドが1バイトずつコピーまたはゼロクリアされる可能性がありました。これにより、ガベージコレクタが「部分的にコピーされたポインタ」を観測する可能性があり、これはガベージコレクションの正確性や安全性に深刻な影響を与える可能性があります。

このコミットは、この問題を解決するために、8バイト書き込みの代わりに4バイト書き込みを使用するように変更します。

## 変更の背景

Goのガベージコレクタは、プログラムの実行中に到達可能なオブジェクトを正確に識別し、不要になったメモリを解放することでメモリリークを防ぎます。このプロセスにおいて、ポインタの整合性は極めて重要です。ポインタが部分的にコピーされたり、ゼロクリアされたりすると、ガベージコレクタは誤ったメモリ位置を参照したり、有効なオブジェクトを誤って解放したりする可能性があります。

`amd64p32`は、64ビットのレジスタとアドレス空間を持つ`amd64`アーキテクチャ上で、32ビットのポインタを使用する特殊な環境です。これは、例えばGoogle Native Client (NaCl)のようなサンドボックス環境で利用されることがあります。このような環境では、ポインタのサイズが通常の`amd64`（8バイトポインタ）とは異なるため、メモリ操作ルーチンもそれに合わせて調整する必要があります。

元の実装では、パフォーマンスのために8バイト単位の操作が優先されていましたが、これが32ビットポインタの特性と衝突し、特定の条件下でポインタの原子性（不可分性）が損なわれる可能性がありました。ガベージコレクタは、ポインタが常に完全に有効な状態か、完全に無効な状態かのいずれかであることを期待します。中間的な「部分的にコピーされた」状態は、ガベージコレクタのロジックを混乱させ、メモリ安全性に関するバグを引き起こす原因となります。

このコミットは、この潜在的なメモリ安全性の問題を解決し、ガベージコレクタが常に整合性の取れたポインタを観測できるようにすることを目的としています。

## 前提知識の解説

*   **`amd64p32`**: `amd64` (x86-64) アーキテクチャ上で32ビットポインタを使用する実行環境を指します。通常の`amd64`は64ビットポインタを使用しますが、`amd64p32`はアドレス空間を32ビットに制限することで、特定の用途（例: Google Native Client）でメモリ使用量を削減したり、互換性を提供したりします。この環境では、レジスタは64ビット幅ですが、ポインタは32ビット幅です。
*   **`memmove`**: メモリブロックをコピーする標準ライブラリ関数です。コピー元とコピー先のメモリ領域が重なっていても正しく動作することが保証されています。
*   **`memclr`**: メモリブロックをゼロで埋める関数です。
*   **ガベージコレクタ (GC)**: プログラムが動的に割り当てたメモリのうち、もはや到達不可能になった（どの変数からも参照されなくなった）メモリ領域を自動的に解放するシステムです。GoのGCは、ポインタを追跡して到達可能なオブジェクトを特定します。ポインタの整合性が損なわれると、GCは誤動作する可能性があります。
*   **ポインタの原子性**: ポインタは、ガベージコレクタや他の並行処理から見て、常に完全に有効な値であるか、完全に無効な値であるかのいずれかであるべきです。部分的に書き込まれたり読み込まれたりする状態は、データ競合やGCの誤動作を引き起こす可能性があります。
*   **アラインメント**: メモリ上のデータが特定のバイト数の倍数のアドレスに配置されることを指します。例えば、8バイトアラインメントとは、データが8の倍数のアドレスに配置されることを意味します。これにより、CPUが効率的にデータにアクセスできます。
*   **アセンブリ命令**:
    *   `MOVSQ` (Move String Quadword): `RSI` (ソースインデックス) から `RDI` (デスティネーションインデックス) へ8バイト（クアッドワード）をコピーします。
    *   `MOVSL` (Move String Doubleword): `RSI` から `RDI` へ4バイト（ダブルワード）をコピーします。
    *   `STOSQ` (Store String Quadword): `RAX` レジスタの8バイト値を `RDI` が指すメモリ位置にストアし、`RDI` をインクリメントします。
    *   `STOSL` (Store String Doubleword): `EAX` レジスタの4バイト値を `RDI` が指すメモリ位置にストアし、`RDI` をインクリメントします。
    *   `REP`: 繰り返しプレフィックス。`RCX` (または`ECX`) レジスタが示す回数だけ、続く文字列操作命令を繰り返します。
    *   `SHR` (Shift Right): ビットを右にシフトします。`SHRQ $3, CX` は `CX` を8で割ることに相当し、`SHRQ $2, CX` は `CX` を4で割ることに相当します。
    *   `AND`: ビットごとの論理積。`ANDQ $7, BX` は `BX` の下位3ビット（`BX % 8`）を取得し、`ANDQ $3, BX` は `BX` の下位2ビット（`BX % 4`）を取得します。これらは、残りのバイト数を計算するために使用されます。

## 技術的詳細

このコミットの核心は、`amd64p32`環境におけるポインタのサイズ（4バイト）と、`memmove`/`memclr`ルーチンが使用するメモリ操作の粒度（元の8バイト）とのミスマッチを解消することにあります。

元の実装では、`memmove`と`memclr`は、まず可能な限り8バイト単位でデータを処理し、残りの部分（オブジェクトの末尾）を1バイト単位で処理していました。これは、`amd64`アーキテクチャでは8バイト操作が効率的であるため、一般的な最適化手法です。

しかし、`amd64p32`環境ではポインタが4バイトです。もしオブジェクトが4バイトのポインタで終わり、かつそのポインタが8バイトアラインされたオフセットに配置されている場合、8バイト単位の操作ではポインタの半分（最初の4バイト）がコピーされた後、残りの4バイトが別の操作（例えば1バイト単位の処理）でコピーされる可能性があります。この「部分的にコピーされた」状態は、ガベージコレクタがそのポインタをスキャンする際に問題を引き起こします。ガベージコレクタは、ポインタが常に有効なオブジェクトを指しているか、あるいは完全にゼロである（無効な）状態であることを期待します。中間的な状態は、GCが誤ったメモリを解放したり、クラッシュを引き起こしたりする原因となります。

このコミットでは、この問題を解決するために、8バイト単位の操作を4バイト単位の操作に切り替えています。

*   **`memclr`の変更**:
    *   `STOSQ` (Store Quadword) を `STOSL` (Store Doubleword) に変更。これにより、8バイトではなく4バイト単位でゼロクリアが行われます。
    *   ループのカウンタ計算も、8バイト単位から4バイト単位に変更されます (`SHRQ $3` -> `SHRQ $2`、`ANDQ $7` -> `ANDQ $3`)。
*   **`memmove`の変更**:
    *   `MOVSQ` (Move Quadword) を `MOVSL` (Move Doubleword) に変更。これにより、8バイトではなく4バイト単位でメモリコピーが行われます。
    *   ループのカウンタ計算も、8バイト単位から4バイト単位に変更されます (`SHRL $3` -> `SHRL $2`、`ANDL $7` -> `ANDL $3`)。
    *   ポインタの調整も、8バイト単位から4バイト単位に変更されます (`SUBL $8, DI` -> `SUBL $4, DI`、`ADDL $7, DI` -> `ADDL $3, DI` など)。

この変更により、4バイトポインタは常にアトミック（不可分）な単位でコピーまたはゼロクリアされるようになります。これにより、ガベージコレクタが部分的にコピーされたポインタを観測する可能性がなくなり、メモリ安全性が向上します。パフォーマンスへの影響は、`amd64p32`環境では4バイト操作がポインタサイズと一致するため、むしろ改善されるか、少なくとも許容範囲内であると考えられます。

## コアとなるコードの解説

### `src/runtime/asm_amd64p32.s` (`runtime·memclr`)

このファイルは、`amd64p32`アーキテクチャ向けの`memclr`（メモリゼロクリア）関数のアセンブリ実装を含んでいます。

*   `MOVL ptr+0(FP), DI`: ゼロクリアするメモリ領域の開始アドレスを`DI`レジスタにロードします。
*   `MOVL n+4(FP), CX`: ゼロクリアするバイト数`n`を`CX`レジスタにロードします。
*   `MOVQ CX, BX`: `CX`の値を`BX`にコピーします。`BX`は残りのバイト数を計算するために使用されます。
*   `ANDQ $3, BX` (変更点): 元々は`ANDQ $7, BX`でした。これは、合計バイト数`n`を4で割った余り（`n % 4`）を`BX`に格納します。つまり、4バイト単位で処理した後に残るバイト数です。
*   `SHRQ $2, CX` (変更点): 元々は`SHRQ $3, CX`でした。これは、合計バイト数`n`を4で割った商（`n / 4`）を`CX`に格納します。つまり、4バイト単位で処理する回数です。
*   `MOVQ $0, AX`: ゼロを`AX`レジスタにロードします。`STOSL`命令はこの`AX`レジスタの下位4バイト（`EAX`）を使用します。
*   `CLD`: 方向フラグをクリアし、文字列操作命令が前方（アドレス増加方向）に動作するように設定します。
*   `REP STOSL` (変更点): 元々は`REP STOSQ`でした。`REP`プレフィックスにより、`CX`がゼロになるまで`STOSL`命令を繰り返します。`STOSL`は`EAX`（ゼロ）を`DI`が指すメモリ位置に4バイト書き込み、`DI`を4インクリメントします。これにより、メモリ領域が4バイト単位で効率的にゼロクリアされます。
*   `MOVQ BX, CX`: 4バイト単位で処理した後に残ったバイト数（`n % 4`）を`CX`にロードします。
*   `REP STOSB`: `CX`がゼロになるまで`STOSB`命令を繰り返します。`STOSB`は`AL`（ゼロ）を`DI`が指すメモリ位置に1バイト書き込み、`DI`を1インクリメントします。これにより、残りの1〜3バイトがゼロクリアされます。

### `src/runtime/memmove_nacl_amd64p32.s` (`runtime·memmove`)

このファイルは、`amd64p32`アーキテクチャ向けの`memmove`（メモリコピー）関数のアセンブリ実装を含んでいます。

*   **追加されたコメント**: `// This could use MOVSQ, but we use MOVSL so that if an object ends in // a 4 byte pointer, we copy it as a unit instead of byte by byte.`
    このコメントは、変更の意図を明確に示しています。`MOVSQ`（8バイトコピー）も可能だが、4バイトポインタで終わるオブジェクトの場合に、ポインタをアトミックな単位でコピーするために`MOVSL`（4バイトコピー）を使用していることを説明しています。

*   **`forward`セクション (前方コピー)**:
    *   `MOVL BX, CX`: コピーするバイト数`n`を`CX`にロードします。
    *   `SHRL $2, CX` (変更点): 元々は`SHRL $3, CX`でした。`n`を4で割った商を`CX`に格納し、4バイト単位でコピーする回数を設定します。
    *   `ANDL $3, BX` (変更点): 元々は`ANDL $7, BX`でした。`n`を4で割った余りを`BX`に格納し、4バイト単位でコピーした後に残るバイト数を設定します。
    *   `REP; MOVSL` (変更点): 元々は`REP; MOVSQ`でした。`REP`プレフィックスにより、`CX`がゼロになるまで`MOVSL`命令を繰り返します。`MOVSL`は`SI`が指すメモリから4バイトを`DI`が指すメモリにコピーし、`SI`と`DI`を4インクリメントします。
    *   残りのバイトは`REP; MOVSB`で1バイトずつコピーされます。

*   **`back`セクション (後方コピー)**:
    メモリ領域が重なっている場合に、破壊を避けるために後方からコピーするロジックです。
    *   `STD`: 方向フラグを設定し、文字列操作命令が後方（アドレス減少方向）に動作するように設定します。
    *   `SHRL $2, CX` (変更点): 元々は`SHRL $3, CX`でした。4バイト単位でコピーする回数を設定します。
    *   `ANDL $3, BX` (変更点): 元々は`ANDL $7, BX`でした。残りのバイト数を設定します。
    *   `SUBL $4, DI` (変更点): 元々は`SUBL $8, DI`でした。`DI`（デスティネーションポインタ）を4バイト戻します。これは、`MOVSL`がコピー後にポインタをインクリメントするため、コピー開始位置を調整するためです。
    *   `SUBL $4, SI` (変更点): 元々は`SUBL $8, SI`でした。`SI`（ソースポインタ）を4バイト戻します。
    *   `REP; MOVSL` (変更点): 元々は`REP; MOVSQ`でした。`REP`プレフィックスにより、`CX`がゼロになるまで`MOVSL`命令を繰り返します。`MOVSL`は`SI`が指すメモリから4バイトを`DI`が指すメモリにコピーし、`SI`と`DI`を4デクリメントします（`STD`フラグのため）。
    *   `ADDL $3, DI` (変更点): 元々は`ADDL $7, DI`でした。`DI`を3バイト進めます。これは、`MOVSL`がコピー後に`DI`をデクリメントするため、残りの1バイト処理の開始位置を調整するためです。
    *   `ADDL $3, SI` (変更点): 元々は`ADDL $7, SI`でした。`SI`を3バイト進めます。
    *   残りのバイトは`REP; MOVSB`で1バイトずつコピーされます。
    *   `CLD`: 方向フラグをクリアし、後続の操作が前方（アドレス増加方向）に動作するように戻します。

これらの変更により、`amd64p32`環境における`memmove`と`memclr`は、ポインタのサイズに合わせた4バイト単位での主要な操作を行うようになり、ガベージコレクタの正確性とメモリ安全性が保証されます。

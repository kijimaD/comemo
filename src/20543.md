# [インデックス 20543] ファイルの概要

このコミットは、GoコンパイラおよびランタイムにおけるARMアーキテクチャ関連のビルド問題を修正するものです。具体的には、Goのスタックマップ情報を埋め込む`liblink`の処理がARM向けに正しく機能していなかった点と、`sync/atomic`パッケージがARM固有のアセンブリ関数に対するGoプロトタイプ宣言を欠いていた点を修正しています。これにより、ARM環境でのGoプログラムのビルドと実行の安定性が向上します。

## 変更の背景

このコミットは、Go言語のARMアーキテクチャ向けビルドにおける2つの主要な問題を解決するために行われました。

1.  **`liblink`におけるFUNCDATAとスタックマップの不整合**: Goランタイムは、ガベージコレクション（GC）のために各関数のスタックフレーム内のポインタの位置を正確に知る必要があります。この情報は「スタックマップ」として表現され、コンパイル時に生成されてバイナリに埋め込まれます。`FUNCDATA`は、これらのスタックマップ情報へのポインタを含むデータ構造です。`liblink`（Goリンカの一部）は、Goのプロトタイプ（Goコードで定義された関数）からこの`FUNCDATA`を生成し、バイナリに挿入する役割を担っています。しかし、ARMアーキテクチャの場合、このデータ構造のレイアウトが他のアーキテクチャ（例えばx86/x64）と異なっていたため、`liblink`が生成する`FUNCDATA`が不正となり、ビルドエラーやランタイムエラーを引き起こしていました。

2.  **`sync/atomic`パッケージのARM固有関数のプロトタイプ欠如**: `sync/atomic`パッケージは、アトミック操作（不可分操作）を提供し、並行プログラミングにおいて共有データへの安全なアクセスを保証します。これらの操作の一部は、特定のアーキテクチャに最適化されたアセンブリ言語で実装されています。ARMアーキテクチャには、`CompareAndSwapUint32`や`CompareAndSwapUint64`といったアトミック操作を効率的に実行するための特定のアセンブリルーチンが存在します。しかし、これらのARM固有のアセンブリ関数に対応するGoのプロトタイプ宣言が不足していました。Goのツールチェーンは、アセンブリ関数がGoコードから呼び出される際に、その関数の引数や戻り値の型、そしてスタックマップ情報を正しく解決するために、対応するGoプロトタイプ宣言を必要とします。この欠如が、ARMビルド時の問題を引き起こしていました。

これらの問題は、GoがARMベースのシステム（Raspberry Pi、モバイルデバイスなど）で広く利用されるようになるにつれて、その安定性と互換性を確保するために修正が不可欠でした。

## 前提知識の解説

### `liblink`
`liblink`はGoツールチェーンの一部であり、Goプログラムのリンク処理を担当するライブラリです。コンパイルされたオブジェクトファイルを結合し、実行可能なバイナリを生成する際に、シンボル解決、再配置、そしてランタイムに必要なメタデータ（FUNCDATAなど）の埋め込みを行います。

### `FUNCDATA`とスタックマップ
Goのガベージコレクタは、正確なGC（Precise GC）を実現するために、スタック上に存在するポインタを正確に識別する必要があります。各Go関数には、そのスタックフレーム内のどの位置にポインタが存在するかを示す「スタックマップ」が関連付けられています。このスタックマップ情報は、`FUNCDATA`というデータ構造を通じてランタイムに提供されます。`FUNCDATA`は、特定の関数に関連するスタックマップやその他のランタイムメタデータへのポインタの配列です。

### `sync/atomic`パッケージ
`sync/atomic`パッケージは、低レベルのアトミック操作（例: `AddInt32`, `CompareAndSwapUint64`）を提供します。これらの操作は、複数のゴルーチンが同時に共有メモリにアクセスする際に、競合状態（race condition）を防ぐために不可分（atomic）に実行されることを保証します。多くの場合、これらの操作はCPUの特殊な命令（例: Compare-and-swap, Load-link/Store-conditional）を利用して、ロックを使用せずに高いパフォーマンスを実現します。

### ARMアーキテクチャ
ARM（Advanced RISC Machine）は、モバイルデバイス、組み込みシステム、そして最近ではサーバーやデスクトップPCでも広く使用されているRISC（Reduced Instruction Set Computer）ベースのプロセッサアーキテクチャです。x86/x64アーキテクチャとは異なる命令セット、レジスタ構成、メモリモデル、そしてABI（Application Binary Interface）を持っています。これらの違いが、コンパイラやリンカが生成するコードやデータ構造のレイアウトに影響を与えます。

### `D_EXTERN`と`D_OREG`
これらはGoリンカ（`liblink`）内部で使用されるシンボルタイプまたはアドレス指定モードに関連する定数です。
-   `D_EXTERN`: 外部シンボル、つまり現在のコンパイル単位の外部で定義されているシンボルを参照する際に使用されます。
-   `D_OREG`: オフセットレジスタ（Offset Register）を意味し、特定のレジスタからのオフセットでアドレスを指定する際に使用される可能性があります。ARMのようなRISCアーキテクチャでは、メモリへのアクセスがレジスタとオフセットの組み合わせで表現されることが一般的であり、これがx86/x64とは異なるデータ構造のレイアウトやアドレス指定方法に影響を与えることがあります。

## 技術的詳細

このコミットは、前述の2つの問題を解決するために、主に`liblink`のコードと`sync/atomic`パッケージのARM固有コードに修正を加えています。

1.  **`liblink`におけるFUNCDATAの修正**:
    *   問題の核心は、`src/liblink/objfile.c`内の`writeobj`関数にありました。この関数は、オブジェクトファイルを書き出す際に、Go関数の`FUNCDATA`エントリを処理します。
    *   特に、スタックマップ情報（`FUNCDATA_ArgsPointerMaps`）へのポインタを指す`Prog`構造体の`p->to.type`フィールドの設定方法に問題がありました。
    *   x86（`thechar == '6'`）およびx64（`thechar == '8'`）アーキテクチャでは、`p->to.type`は`ctxt->arch->D_EXTERN`に設定されていました。これは、スタックマップが外部シンボルとして参照されることを意味します。
    *   しかし、ARMアーキテクチャでは、この参照方法が正しくありませんでした。ARMでは、スタックマップへの参照が`D_OREG`（オフセットレジスタ）タイプとして扱われ、さらにその`p->to.name`フィールドに`D_EXTERN`が設定されるべきでした。これは、ARMのABIやメモリ参照の仕組みがx86/x64と異なるためです。
    *   この修正により、ARM向けに生成される`FUNCDATA`のデータ構造が正しくなり、ガベージコレクタがスタックマップ情報を正確に読み取れるようになりました。

2.  **`sync/atomic`パッケージのARM固有関数のプロトタイプ追加**:
    *   `src/sync/atomic/64bit_arm.go`ファイルに、ARM固有のアセンブリルーチンに対応するGoの関数プロトタイプが追加されました。
    *   具体的には、`armCompareAndSwapUint32`, `armCompareAndSwapUint64`, `generalCAS64`の3つの関数宣言が追加されています。
    *   これらの宣言は、Goコンパイラとリンカに対して、対応するアセンブリ関数が存在し、それらがどのような引数を取り、どのような値を返すのかを伝えます。
    *   これにより、Goツールチェーンはこれらのアセンブリ関数を正しくリンクし、また、これらの関数がスタックマップ情報を必要とする場合に、その情報を正しく生成できるようになります。コメントにもあるように、「アセンブリルーチンに引数に対する正しいスタックマップを与えるため」の宣言です。

これらの修正は、Goのクロスコンパイルとマルチアーキテクチャサポートの成熟度を高める上で重要なステップでした。

この変更が、`liblink`におけるFUNCDATAのスタックマップ参照の修正の核心です。
`writeobj`関数内で、`FUNCDATA_ArgsPointerMaps`（引数ポインタマップ）を指す`Prog`構造体`p`の`p->to.type`を設定するロジックが変更されました。
*   `ctxt->arch->thechar == '6'` (x86) または `ctxt->arch->thechar == '8'` (x64) の場合、これまで通り`p->to.type = ctxt->arch->D_EXTERN;`が使用されます。
*   それ以外のアーキテクチャ（この文脈では主にARM）の場合、`p->to.type = ctxt->arch->D_OREG;`が設定され、さらに`p->to.name = ctxt->arch->D_EXTERN;`が設定されます。
これは、ARMアーキテクチャにおけるスタックマップへの参照が、直接的な外部シンボル参照ではなく、オフセットレジスタを介した外部シンボル参照として表現される必要があるためです。この修正により、ARMバイナリにおけるスタックマップ情報の埋め込みが正しく行われるようになりました。

これらの宣言は、対応するアセンブリ実装が存在することをGoツールチェーンに伝え、コンパイラがこれらの関数を呼び出す際に正しい型チェックとスタックマップ情報の生成を行えるようにします。特にコメントにあるように、「アセンブリルーチンに引数に対する正しいスタックマップを与えるため」に重要です。これにより、`sync/atomic`パッケージがARM上で正しく機能するようになりました。

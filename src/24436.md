`cmd/go: fix go get -u with vendoring`

このコミットは、`go get -u` コマンドがベンダー機能と組み合わされた際の不具合を修正します。
Issue #11864 を修正します。

## 変更の背景

Go言語の依存関係管理において、ベンダー（vendoring）はプロジェクトの依存関係をプロジェクト自身のディレクトリ内にコピーして管理する手法です。これにより、ビルドの一貫性が保たれ、外部リポジトリの変更に影響されにくくなります。`go get -u` コマンドは、指定されたパッケージとその依存関係を最新バージョンに更新するために使用されます。

このコミットが修正する問題は、`go get -u` がベンダーされた依存関係を適切に処理できないというものでした。具体的には、ベンダーディレクトリ内のパッケージが正しく更新されない、またはベンダー機能が有効な環境で `go get -u` を実行した際に予期せぬエラーや動作が発生する可能性がありました。これは、`go get` コマンドがパッケージのインポートパスを解決し、ダウンロードする際のロジックが、ベンダーの概念を十分に考慮していなかったためと考えられます。

Issue #11864 は、この問題がユーザーによって報告されたものであり、Goツールの安定性とベンダー機能の正確な動作を保証するために、この修正が必要とされました。

## 前提知識の解説

*   **`go get`**: Go言語のパッケージ管理コマンドの一つで、リモートリポジトリからGoパッケージをダウンロードし、インストールします。
*   **`go get -u`**: `go get` コマンドのオプションで、指定されたパッケージとその依存関係を最新バージョンに「更新」します。
*   **Vendoring (ベンダー)**: Go 1.5で導入された依存関係管理のメカニズムです。プロジェクトの依存関係を `vendor/` ディレクトリ内にコピーして管理することで、ビルドの再現性と安定性を向上させます。Goツールは、インポートパスを解決する際に、まず現在のモジュールの `vendor/` ディレクトリ内を探し、次に `$GOPATH/src`、最後に `$GOROOT/src` を探します。
*   **Import Path (インポートパス)**: Goパッケージを一意に識別するための文字列です。例えば、`"github.com/user/repo/package"` のようになります。
*   **`loadImport` 関数**: `cmd/go` パッケージ内で、指定されたインポートパスに対応するパッケージ情報をロードする役割を担う関数です。この関数は、インポートパスの解決、ベンダーパスの処理、パッケージのビルド情報の取得などを行います。
*   **`download` 関数**: `cmd/go` パッケージ内で、`go get` コマンドのダウンロード部分を処理する関数です。リモートリポジトリからパッケージを取得し、ローカルに配置します。

## 技術的詳細

このコミットの主要な変更点は、`go get` コマンドの内部ロジック、特にパッケージのダウンロードとインポートパスの解決に関する部分に、ベンダー機能の考慮をより深く組み込んだことです。

1.  **`mode` パラメータの導入**:
    *   `download` 関数と `loadImport` 関数に、`mode` という新しい整数型パラメータが導入されました。これは、パッケージのロードやダウンロードの際に、どのような振る舞いをすべきかを制御するためのビットフラグとして機能します。
    *   `pkg.go` に `useVendor` と `getTestDeps` という定数が定義されました。
        *   `useVendor`: `loadImport` がベンダー拡張（`vendor/` ディレクトリ内のパッケージを優先的に解決する）を行うべきであることを示します。これは、ソースファイルから読み込まれたインポートパスがまだベンダー拡張されていない場合に設定されます。
        *   `getTestDeps`: `go get -t` オプションが指定された場合に、テスト依存関係もフェッチすべきであることを示します。

2.  **`download` 関数の変更**:
    *   以前は `getTestDeps` というブーリアン値でテスト依存関係の取得を制御していましたが、これが `mode` パラメータに置き換えられました。
    *   `download` 関数内で `load` 関数を呼び出す際、この `mode` パラメータが渡されるようになりました。
    *   特に、パッケージの通常の依存関係をダウンロードする際には `mode` を `0` (ベンダー拡張なし) で呼び出し、テスト依存関係をダウンロードする際には `useVendor` フラグを立てて呼び出すように変更されました。これは、通常の依存関係は既にベンダー拡張されていると見なされるのに対し、テスト依存関係は `p.load` がベンダー拡張を行わないため、`loadImport` でベンダー拡張が必要となるためです。

3.  **`loadImport` 関数の変更**:
    *   `loadImport` 関数も `mode` パラメータを受け取るようになりました。
    *   ベンダーパスの解決 (`vendoredImportPath`) と、`vendor/` ディレクトリへの直接的なインポートを禁止するロジック (`disallowVendor`) が、`mode&useVendor != 0` の場合にのみ適用されるようになりました。これにより、ベンダー拡張が不要な状況や、既にベンダー拡張されたパスを処理する際に、不必要なベンダー関連のチェックをスキップできるようになります。
    *   `loadPackage` や `Package.load` といった他のパッケージロード関連の関数も、`loadImport` を呼び出す際に適切な `mode` を渡すように修正されました。

これらの変更により、`go get -u` がパッケージを更新する際に、ベンダーディレクトリ内の依存関係が正しく識別され、適切なバージョンのパッケージがフェッチされるようになります。特に、`useVendor` フラグの導入は、インポートパスがソースファイルから直接読み込まれたものか、それとも既にベンダー拡張されたものかを区別し、Goツールがベンダーパスの解決をより正確に行うことを可能にしています。

## コアとなるコードの解説

このコミットの核心は、`go get -u` コマンドがベンダーされた依存関係を更新する際の挙動を正確に制御するために、パッケージのロードとダウンロードのロジックに `mode` パラメータを導入した点にあります。

`download` 関数は、パッケージのダウンロードと依存関係の解決を担当します。以前は `getTestDeps` というブーリアンフラグでテスト依存関係の処理を切り替えていましたが、これをより汎用的な `mode` 整数に置き換えることで、複数の挙動（ベンダー拡張の有無、テスト依存関係の有無など）をビットフラグで同時に制御できるようになりました。

`loadImport` 関数は、Goパッケージのインポートパスを解決し、パッケージ情報をロードするGoツールの重要な内部関数です。この関数に `mode` パラメータが追加されたことで、インポートパスがどこから来たのか（例：通常のソースファイルからのインポートか、既にベンダー拡張されたパスか）に応じて、ベンダー関連のロジック（`vendoredImportPath` や `disallowVendor`）を適用するかどうかを細かく制御できるようになりました。

特に重要なのは `useVendor` フラグです。
*   `useVendor` が設定されている場合、`loadImport` はインポートパスに対してベンダー拡張を試みます。これは、ソースコードに記述されたインポートパスが、プロジェクトの `vendor/` ディレクトリ内のパッケージを指すように解決されることを意味します。
*   `useVendor` が設定されていない場合、`loadImport` はベンダー拡張を行いません。これは、既にベンダー拡張されたパス（例：`example.com/project/vendor/dep` のようなパス）を処理する場合や、ベンダー機能が適用されないコンテキスト（例：`go get` がトップレベルのパッケージをダウンロードする場合）に利用されます。

この変更により、`go get -u` がベンダーされた依存関係を更新する際に、Goツールがインポートパスを正しく解決し、ベンダーディレクトリ内のパッケージを適切に更新できるようになります。新しいテストケース `TestVendorGetUpdate` は、この修正が意図通りに機能することを検証するために追加されました。

## 元コミット内容

`cmd/go: fix go get -u with vendoring`

このコミットは、`go get -u` コマンドがベンダー機能と組み合わされた際の不具合を修正します。
Issue #11864 を修正します。

## 変更の背景

Go言語の依存関係管理において、ベンダー（vendoring）はプロジェクトの依存関係をプロジェクト自身のディレクトリ内にコピーして管理する手法です。これにより、ビルドの一貫性が保たれ、外部リポジトリの変更に影響されにくくなります。`go get -u` コマンドは、指定されたパッケージとその依存関係を最新バージョンに更新するために使用されます。

このコミットが修正する問題は、`go get -u` がベンダーされた依存関係を適切に処理できないというものでした。具体的には、ベンダーディレクトリ内のパッケージが正しく更新されない、またはベンダー機能が有効な環境で `go get -u` を実行した際に予期せぬエラーや動作が発生する可能性がありました。これは、`go get` コマンドがパッケージのインポートパスを解決し、ダウンロードする際のロジックが、ベンダーの概念を十分に考慮していなかったためと考えられます。

Issue #11864 は、この問題がユーザーによって報告されたものであり、Goツールの安定性とベンダー機能の正確な動作を保証するために、この修正が必要とされました。

## 前提知識の解説

*   **`go get`**: Go言語のパッケージ管理コマンドの一つで、リモートリポジトリからGoパッケージをダウンロードし、インストールします。
*   **`go get -u`**: `go get` コマンドのオプションで、指定されたパッケージとその依存関係を最新バージョンに「更新」します。
*   **Vendoring (ベンダー)**: Go 1.5で導入された依存関係管理のメカニズムです。プロジェクトの依存関係を `vendor/` ディレクトリ内にコピーして管理することで、ビルドの再現性と安定性を向上させます。Goツールは、インポートパスを解決する際に、まず現在のモジュールの `vendor/` ディレクトリ内を探し、次に `$GOPATH/src`、最後に `$GOROOT/src` を探します。
*   **Import Path (インポートパス)**: Goパッケージを一意に識別するための文字列です。例えば、`"github.com/user/repo/package"` のようになります。
*   **`loadImport` 関数**: `cmd/go` パッケージ内で、指定されたインポートパスに対応するパッケージ情報をロードする役割を担う関数です。この関数は、インポートパスの解決、ベンダーパスの処理、パッケージのビルド情報の取得などを行います。
*   **`download` 関数**: `cmd/go` パッケージ内で、`go get` コマンドのダウンロード部分を処理する関数です。リモートリポジトリからパッケージを取得し、ローカルに配置します。

## 技術的詳細

このコミットの主要な変更点は、`go get` コマンドの内部ロジック、特にパッケージのダウンロードとインポートパスの解決に関する部分に、ベンダー機能の考慮をより深く組み込んだことです。

1.  **`mode` パラメータの導入**:
    *   `download` 関数と `loadImport` 関数に、`mode` という新しい整数型パラメータが導入されました。これは、パッケージのロードやダウンロードの際に、どのような振る舞いをすべきかを制御するためのビットフラグとして機能します。
    *   `pkg.go` に `useVendor` と `getTestDeps` という定数が定義されました。
        *   `useVendor`: `loadImport` がベンダー拡張（`vendor/` ディレクトリ内のパッケージを優先的に解決する）を行うべきであることを示します。これは、ソースファイルから読み込まれたインポートパスがまだベンダー拡張されていない場合に設定されます。
        *   `getTestDeps`: `go get -t` オプションが指定された場合に、テスト依存関係もフェッチすべきであることを示します。

2.  **`download` 関数の変更**:
    *   以前は `getTestDeps` というブーリアン値でテスト依存関係の取得を制御していましたが、これが `mode` パラメータに置き換えられました。
    *   `download` 関数内で `load` 関数を呼び出す際、この `mode` パラメータが渡されるようになりました。
    *   特に、パッケージの通常の依存関係をダウンロードする際には `mode` を `0` (ベンダー拡張なし) で呼び出し、テスト依存関係をダウンロードする際には `useVendor` フラグを立てて呼び出すように変更されました。これは、通常の依存関係は既にベンダー拡張されていると見なされるのに対し、テスト依存関係は `p.load` がベンダー拡張を行わないため、`loadImport` でベンダー拡張が必要となるためです。

3.  **`loadImport` 関数の変更**:
    *   `loadImport` 関数も `mode` パラメータを受け取るようになりました。
    *   ベンダーパスの解決 (`vendoredImportPath`) と、`vendor/` ディレクトリへの直接的なインポートを禁止するロジック (`disallowVendor`) が、`mode&useVendor != 0` の場合にのみ適用されるようになりました。これにより、ベンダー拡張が不要な状況や、既にベンダー拡張されたパスを処理する際に、不必要なベンダー関連のチェックをスキップできるようになります。
    *   `loadPackage` や `Package.load` といった他のパッケージロード関連の関数も、`loadImport` を呼び出す際に適切な `mode` を渡すように修正されました。

これらの変更により、`go get -u` がパッケージを更新する際に、ベンダーディレクトリ内の依存関係が正しく識別され、適切なバージョンのパッケージがフェッチされるようになります。特に、`useVendor` フラグの導入は、インポートパスがソースファイルから直接読み込まれたものか、それとも既にベンダー拡張されたものかを区別し、Goツールがベンダーパスの解決をより正確に行うことを可能にしています。

## コアとなるコードの解説

このコミットの核心は、`go get -u` コマンドがベンダーされた依存関係を更新する際の挙動を正確に制御するために、パッケージのロードとダウンロードのロジックに `mode` パラメータを導入した点にあります。

`download` 関数は、パッケージのダウンロードと依存関係の解決を担当します。以前は `getTestDeps` というブーリアンフラグでテスト依存関係の処理を切り替えていましたが、これをより汎用的な `mode` 整数に置き換えることで、複数の挙動（ベンダー拡張の有無、テスト依存関係の有無など）をビットフラグで同時に制御できるようになりました。

`loadImport` 関数は、Goパッケージのインポートパスを解決し、パッケージ情報をロードするGoツールの重要な内部関数です。この関数に `mode` パラメータが追加されたことで、インポートパスがどこから来たのか（例：通常のソースファイルからのインポートか、既にベンダー拡張されたパスか）に応じて、ベンダー関連のロジック（`vendoredImportPath` や `disallowVendor`）を適用するかどうかを細かく制御できるようになりました。

特に重要なのは `useVendor` フラグです。
*   `useVendor` が設定されている場合、`loadImport` はインポートパスに対してベンダー拡張を試みます。これは、ソースコードに記述されたインポートパスが、プロジェクトの `vendor/` ディレクトリ内のパッケージを指すように解決されることを意味します。
*   `useVendor` が設定されていない場合、`loadImport` はベンダー拡張を行いません。これは、既にベンダー拡張されたパス（例：`example.com/project/vendor/dep` のようなパス）を処理する場合や、ベンダー機能が適用されないコンテキスト（例：`go get` がトップレベルのパッケージをダウンロードする場合）に利用されます。

この変更により、`go get -u` がベンダーされた依存関係を更新する際に、Goツールがインポートパスを正しく解決し、ベンダーディレクトリ内のパッケージを適切に更新できるようになります。新しいテストケース `TestVendorGetUpdate` は、この修正が意図通りに機能することを検証するために追加されました。

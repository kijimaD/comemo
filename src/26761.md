# [インデックス 26761] ファイルの概要

このコミットは、Goランタイムに新しいAPI `runtime.Frames` を導入し、`runtime.Callers` が返すプログラムカウンタ (PC) のスライスから、より正確で扱いやすい関数、ファイル名、行番号の情報を取得できるようにするものです。これにより、特にプロファイリングツール (`runtime/pprof`) におけるスタックトレースの解析が改善され、以前 `runtime/pprof` が `runtime.gopanic` を誤って探していた問題を `runtime.sigpanic` を正しく識別するように修正しています。

## 変更の背景

この変更の背景には、主に二つの側面があります。

1.  **`runtime.Callers` の情報取得の複雑さの解消**: 従来の `runtime.Callers` 関数は、呼び出しスタック上のプログラムカウンタ (PC) のスライスを返しますが、これらのPC値から正確な関数名、ファイル名、行番号を取得するには、`runtime.FuncForPC` や `Func.FileLine` といった関数を組み合わせる必要がありました。さらに、PC値は通常、呼び出し命令の「次の」命令を指すため、正確な呼び出し元の行番号を得るためには `pc-1` のような調整が必要でした。この調整はアーキテクチャによって異なる場合もあり、特にパニック発生時のPC値の扱いはさらに複雑でした。この複雑さを解消し、より使いやすく、正確なスタックフレーム情報を提供する統一されたAPIが求められていました。

2.  **`runtime/pprof` における `gopanic` と `sigpanic` の誤認識の修正**: Goのプロファイリングツールである `pprof` は、スタックトレースを解析する際に、パニック発生時の特殊なスタックフレームを識別する必要がありました。以前の `pprof` の実装では、パニックの起点として `runtime.gopanic` を探していましたが、これは誤りでした。Goランタイムでは、`panic()` 組み込み関数によって明示的に発生するパニックは `runtime.gopanic` を経由しますが、nilポインタ参照や配列の範囲外アクセスなど、ランタイムが検出する致命的なエラー（シグナルによって捕捉されることが多い）は `runtime.sigpanic` を経由します。`pprof` がプロファイル中に捕捉するパニックの多くは後者の `runtime.sigpanic` に起因するものであり、これを正しく識別できないと、スタックトレースの解析が不正確になる可能性がありました。このコミットは、新しい `Frames` APIの導入を通じて、この `gopanic` と `sigpanic` の誤認識を間接的に修正しています。

コミットメッセージに記載されている `Update #11432` は、この問題に関連する内部トラッキング番号であると考えられます。

## 前提知識の解説

### Goのスタックトレースとプログラムカウンタ (PC)

Goプログラムが実行される際、関数呼び出しの履歴はスタックに積まれていきます。この履歴を「スタックトレース」と呼びます。`runtime.Callers` 関数は、現在のゴルーチンの呼び出しスタック上のPC値（`uintptr` 型）のスライスを取得するために使用されます。PC値は、実行中の命令のアドレスを示すもので、スタックトレースの各エントリは通常、関数呼び出し命令の直後の命令のアドレスを指します。

### `runtime.FuncForPC` と `Func.FileLine`

`runtime.Callers` が返すPC値は生のアドレスであり、人間が理解できる関数名、ファイル名、行番号に変換する必要があります。
- `runtime.FuncForPC(pc uintptr) *Func`: 指定されたPC値に対応する `*runtime.Func` オブジェクトを返します。`*Func` オブジェクトには、関数名 (`Func.Name()`) や関数のエントリポイント (`Func.Entry()`) などの情報が含まれます。
- `Func.FileLine(pc uintptr) (file string, line int)`: `*Func` オブジェクトとPC値から、対応するソースコードのファイル名と行番号を返します。

これらの関数を使用する際、PC値が呼び出し命令の「次の」命令を指すという特性のため、正確な呼び出し元の行番号を得るには `pc-1` のようにPC値を調整する必要がありました。これは、デバッグ情報が通常、命令の開始点ではなく、その命令が完了した後の次の命令の開始点に関連付けられているためです。

### `runtime.gopanic` と `runtime.sigpanic`

Goランタイムにおけるパニック処理は、大きく分けて二つの経路があります。
- **`runtime.gopanic`**: ユーザーコードが `panic()` 組み込み関数を明示的に呼び出した場合に経由するランタイム関数です。これは、プログラムが意図的に異常終了を通知する際に使われます。
- **`runtime.sigpanic`**: ランタイムが検出する致命的なエラー（例: nilポインタ参照、配列の範囲外アクセス、スタックオーバーフローなど）が発生し、OSからのシグナル（例: SIGSEGV）によって捕捉された場合に経由するランタイム関数です。これは、プログラムのバグや予期せぬ状態によって引き起こされることが多いです。

`pprof` のようなツールがスタックトレースを解析する際には、これらのパニックのタイプを正確に識別し、それに応じてスタックトレースの表示を調整することが重要になります。特に `sigpanic` の場合、PC値はエラーを引き起こした命令のアドレスを直接指すため、通常の `pc-1` の調整は不要、あるいは不適切になることがあります。

### `runtime/pprof`

`runtime/pprof` パッケージは、Goプログラムのプロファイリングデータ（CPU使用率、メモリ割り当て、ゴルーチンスタックトレースなど）を生成するための機能を提供します。これらのプロファイルは、プログラムのパフォーマンスボトルネックを特定したり、デバッグ情報を収集したりするのに役立ちます。スタックトレースは、どの関数がどのくらいの時間CPUを使用しているか、またはどの関数がメモリを割り当てているかを示す上で不可欠な情報です。

## 技術的詳細

このコミットの主要な技術的変更は、`runtime` パッケージに `Frames` と `Frame` という新しい型を導入し、`runtime.Callers` が返すPC値の処理を抽象化・簡素化した点にあります。

### `runtime.Frames` と `runtime.Frame`

-   **`type Frames struct`**: `runtime.Callers` から得られたPC値のスライス (`callers []uintptr`) を保持し、スタックフレーム情報をイテレートするための状態を管理します。`wasPanic` というフィールドを持ち、直前のフレームがパニックに関連するものだったかどうかを追跡します。これは、`sigpanic` のような特殊なケースでPC値の調整ロジックを変更するために使用されます。
-   **`type Frame struct`**: 各スタックフレームの詳細な情報（PC値、`*Func` オブジェクト、関数名、ファイル名、行番号、関数のエントリポイント）を保持する構造体です。これにより、ユーザーはPC値から直接、整形された情報を取得できるようになります。

### `runtime.CallersFrames` 関数

`func CallersFrames(callers []uintptr) *Frames` は、`runtime.Callers` が返したPC値のスライスを受け取り、新しい `*Frames` オブジェクトを初期化して返します。これにより、PC値のスライスを直接操作する代わりに、`Frames` オブジェクトを通じてフレーム情報を取得するイテレータパターンが提供されます。

### `Frames.Next()` メソッド

`func (ci *Frames) Next() (frame Frame, more bool)` は、`Frames` オブジェクトの主要なメソッドであり、スタックフレームを一つずつイテレートします。
1.  `ci.callers` スライスから次のPC値を取得します。
2.  `runtime.FuncForPC` を使用して `*Func` オブジェクトを取得します。
3.  **PC値の調整ロジック**:
    -   通常の関数呼び出しの場合 (`xpc > entry && !ci.wasPanic`)、PC値は `xpc--` と調整されます。これは、PCが呼び出し命令の次の命令を指すため、呼び出し命令自体の行番号を得るための一般的な慣習です。
    -   しかし、`ci.wasPanic` が `true` の場合（つまり、直前のフレームがパニックに関連していた場合）、PC値の調整は行われません。これは、`sigpanic` のようなパニックではPC値がエラー発生命令を直接指すため、`pc-1` の調整が不適切になるためです。
4.  `Func.FileLine(xpc)` を使用してファイル名と行番号を取得します。
5.  `Frame` 構造体を構築し、`more` フラグ（さらにフレームがあるかどうか）と共に返します。
6.  `ci.wasPanic` フラグは、現在のフレームの関数が `sigpanicPC`（`runtime.sigpanic` のエントリポイント）であるかどうかに基づいて更新されます。これにより、次のフレームのPC値調整ロジックが適切に適用されます。

### `runtime/pprof` の修正

`src/runtime/pprof/pprof.go` の `printStackRecord` 関数は、スタックトレースを整形して出力する役割を担っています。このコミットでは、従来のPC値の直接操作と `FuncForPC`/`FileLine` の呼び出しを、新しく導入された `Frames` APIの使用に置き換えています。

```go
// 変更前
for i, pc := range stk {
    f := runtime.FuncForPC(pc)
    // ...
    tracepc := pc
    if i > 0 && pc > f.Entry() && !wasPanic {
        // Back up to call instruction.
        // ... architecture specific pc-- or pc-=4 ...
    }
    file, line := f.FileLine(tracepc)
    name := f.Name()
    wasPanic = name == "runtime.gopanic" // ここが問題
    // ...
}

// 変更後
frames := runtime.CallersFrames(stk)
for {
    frame, more := frames.Next()
    name := frame.Function
    // ...
    // wasPanic のロジックは Frames.Next() 内部にカプセル化された
    // runtime.gopanic のチェックは不要になった
    // ...
    if !more {
        break
    }
}
```

この変更により、`printStackRecord` はPC値の調整ロジック（`pc-1` や `pc-=4`）や `gopanic`/`sigpanic` の特殊処理を直接扱う必要がなくなり、コードが大幅に簡素化されました。`Frames.Next()` がこれらの複雑な詳細を内部で処理するため、`pprof` はより正確なスタックトレース情報を取得できるようになりました。特に、`wasPanic = name == "runtime.gopanic"` という誤ったチェックが不要になり、`Frames` 内部で `sigpanicPC` を参照することで、`runtime.sigpanic` を正しく識別できるようになりました。

### `src/runtime/extern.go` の変更

`runtime.Callers` 関数のコメントが更新され、PC値からファイル/行情報を取得する際の複雑さ（`pc[i]-1` の調整や `sigpanic` の例外）について言及しつつ、新しい `Frames` APIを使用することでこれらの問題を簡単に解決できることが明記されました。

### `src/runtime/callers_test.go` の追加

新しいテストファイル `src/runtime/callers_test.go` が追加され、`Frames` APIの正確性を検証しています。特に、通常の関数呼び出しとパニック発生時の両方で、期待されるファイル名と行番号が正しく取得されることを確認しています。これにより、`Frames` APIがPC値の調整ロジックと `sigpanic` の特殊処理を正しく実装していることが保証されます。

## コアとなるコードの解説

このコミットの核心は、Goのスタックトレース情報の取得と解析を、より堅牢で使いやすい方法に進化させた点にあります。

-   **`Frames` と `Frame`**: これらは、生のスライス `[]uintptr` であったスタックトレース情報を、より意味のある構造化されたデータ (`Frame`) のシーケンス (`Frames`) として提供します。これにより、開発者はPC値の低レベルな詳細（`pc-1` の調整やアーキテクチャ依存のオフセット）を意識することなく、直接的に関数名、ファイル名、行番号を取得できるようになります。
-   **`Frames.Next()` の内部ロジック**: このメソッドは、スタックトレース解析における最も複雑な部分、すなわちPC値の調整とパニック時の特殊処理をカプセル化しています。特に、`wasPanic` フラグと `sigpanicPC` の利用により、`runtime.sigpanic` によって引き起こされたパニックのスタックフレームに対してはPC値の調整を行わないという、正確な挙動を実現しています。これにより、`pprof` のようなツールがパニックの根本原因をより正確に特定できるようになります。
-   **`pprof` の簡素化と正確性の向上**: `pprof` が `Frames` APIを利用することで、スタックトレースの生成ロジックが大幅に簡素化されました。以前は `gopanic` を誤って探していた問題も、`Frames` APIが `sigpanic` を正しく識別する機能を提供することで、間接的に修正されました。これにより、`pprof` が生成するプロファイルデータ、特にパニックに関連するスタックトレースの正確性と信頼性が向上しました。

要するに、このコミットは、GoランタイムのスタックトレースAPIを現代化し、より使いやすく、より正確なものにすることで、デバッグやプロファイリングのツールがより効果的に機能するための基盤を強化したと言えます。

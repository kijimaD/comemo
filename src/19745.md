# [インデックス 19745] ファイルの概要

このコミットは、Go言語のリンカ（`cmd/ld`）とデバッグ情報読み取りパッケージ（`debug/dwarf`）における、DWARFデバッグ情報での配列型の表現方法の変更に関するものです。

-   `src/cmd/ld/dwarf.c`: Goリンカの一部であり、コンパイルされたGoプログラムの実行可能ファイルにDWARFデバッグ情報を生成する役割を担っています。このファイルでは、配列の型情報をDWARFに書き出すロジックが変更されました。
-   `src/pkg/debug/dwarf/type.go`: Go標準ライブラリの`debug/dwarf`パッケージの一部で、DWARFデバッグ情報を解析し、Goの型システムにマッピングする役割を担っています。このファイルでは、配列の型情報をDWARFから読み取るロジックが変更されました。

## 変更の背景

この変更の背景には、DWARFデバッグ情報における配列の表現方法と、Go言語の特性が関係しています。

DWARF（Debugging With Attributed Record Formats）は、コンパイルされたプログラムのデバッグ情報を記述するための標準フォーマットです。このフォーマットでは、配列の次元や範囲を記述するために`DW_TAG_subrange_type`というタグが使用されます。このタグには、配列のサイズを示す属性として主に二つの方法があります。

1.  **`DW_AT_upper_bound`**: 配列のインデックスの最大値を示します。例えば、要素数Nの配列の場合、インデックスは0からN-1までなので、`DW_AT_upper_bound`はN-1となります。
2.  **`DW_AT_count`**: 配列の要素数を直接示します。要素数Nの配列の場合、`DW_AT_count`はNとなります。

DWARF標準では、どちらか一方のみが必須とされています。しかし、`DW_AT_upper_bound`を使用する場合、要素数が0の配列（0-length array）を表現する際に問題が生じます。要素数0の配列の`upper_bound`は-1となりますが、これは一部のデバッガやツールで正しく解釈されない可能性や、特殊なケースとして扱われる必要がありました。

Go言語では、特にスライスにおいて、基盤となる配列が0-lengthであるケースが頻繁に発生します。例えば、`make([]int, 0)`のように、長さ0のスライスを作成することは一般的です。このような0-length配列のデバッグ情報が正しく表現されないと、デバッガで変数の内容を検査する際に問題が生じる可能性があります。

このコミットは、`DW_AT_upper_bound`の代わりに`DW_AT_count`を使用することで、0-length配列をより自然かつ明確に表現できるようにし、デバッグ情報の正確性と互換性を向上させることを目的としています。

## 前提知識の解説

### DWARF (Debugging With Attributed Record Formats)

DWARFは、コンパイラやリンカによって生成される実行可能ファイルに埋め込まれるデバッグ情報の標準フォーマットです。この情報には、ソースコードの行番号と実行可能コードのアドレスのマッピング、変数名とそのメモリ上の位置、データ型定義、関数呼び出しスタック情報などが含まれます。デバッガはこれらのDWARF情報を使用して、実行中のプログラムの状態をソースコードレベルで表示・操作します。

### Goリンカ (`cmd/ld`)

Go言語のツールチェインの一部であるリンカは、Goコンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、最終的な実行可能ファイルを生成します。この過程で、Goの型情報やシンボル情報に基づいてDWARFデバッグ情報も生成され、実行可能ファイルに埋め込まれます。`src/cmd/ld/dwarf.c`は、このDWARFデバッグ情報生成ロジックのC言語実装部分です。

### `debug/dwarf`パッケージ

`debug/dwarf`はGo標準ライブラリの一部であり、Goプログラムの実行可能ファイルに埋め込まれたDWARFデバッグ情報を読み取り、解析するためのAPIを提供します。このパッケージは、デバッガやプロファイラ、その他の分析ツールがGoバイナリの内部構造を理解するために利用されます。

### DWARFの属性とタグ

-   **`DW_TAG_subrange_type`**: DWARFでは、配列の次元や部分範囲を記述するために使用されるタグです。例えば、`int[10]`のような配列型を表現する際に、その配列のサイズやインデックス範囲を定義するためにこのタグが使われます。
-   **`DW_AT_upper_bound`**: `DW_TAG_subrange_type`の属性の一つで、配列のインデックスの最大値を示します。例えば、`int[10]`の場合、インデックスは0から9なので、`DW_AT_upper_bound`は9となります。
-   **`DW_AT_count`**: `DW_TAG_subrange_type`の属性の一つで、配列の要素数を直接示します。例えば、`int[10]`の場合、`DW_AT_count`は10となります。

### 0-length配列

要素数が0の配列を指します。Go言語では、スライス（`[]T`）が基盤となる配列を参照しますが、この基盤配列が要素数0である場合があります。例えば、`var s []int`や`make([]int, 0)`のように宣言されたスライスは、長さが0です。デバッグ時にこれらの配列の情報を正確に取得できることは重要です。

## 技術的詳細

このコミットの技術的な核心は、DWARFデバッグ情報における配列の長さの表現を`DW_AT_upper_bound`から`DW_AT_count`へ移行すること、そしてその移行に伴う互換性の維持です。

1.  **リンカ側の変更 (`src/cmd/ld/dwarf.c`)**:
    *   Goリンカは、Goの型情報から配列の長さを取得し、それをDWARFデバッグ情報として出力します。
    *   以前は、この長さを`DW_AT_upper_bound`属性として書き出していました。例えば、長さ`N`の配列であれば、`N-1`という値を`DW_AT_upper_bound`に設定していました。
    *   今回の変更により、リンカは`DW_AT_upper_bound`の代わりに`DW_AT_count`属性を使用するようになりました。これにより、長さ`N`の配列であれば、直接`N`という値を`DW_AT_count`に設定します。
    *   特に、`decodetype_arraylen(gotype)`関数がGoの型情報から配列の実際の長さを取得するため、その結果をそのまま`DW_AT_count`に渡すことで、0-length配列（長さ0）も正確に`DW_AT_count = 0`として表現できるようになります。

2.  **`debug/dwarf`パッケージ側の変更 (`src/pkg/debug/dwarf/type.go`)**:
    *   `debug/dwarf`パッケージは、既存のGoバイナリのDWARFデバッグ情報を読み取る役割を担っています。
    *   新しいリンカで生成されたバイナリは`DW_AT_count`を使用しますが、古いリンカで生成されたバイナリは`DW_AT_upper_bound`を使用しています。
    *   このため、`debug/dwarf`パッケージは両方の形式に対応する必要があります。
    *   変更後のロジックでは、まず`DW_AT_count`属性の値を読み取ろうとします。
    *   もし`DW_AT_count`が存在しない（または読み取れない）場合、それは古い形式のバイナリであると判断し、`DW_AT_upper_bound`属性の値を読み取ります。
    *   `DW_AT_upper_bound`から読み取った値は、配列のインデックスの最大値であるため、実際の要素数を得るためには`+1`の補正が必要です（例: `upper_bound = 9`であれば`count = 10`）。この補正を行うことで、古い形式のデバッグ情報も正しく要素数として解釈できるようになります。
    *   これにより、新しいリンカでビルドされたGoプログラムも、古いリンカでビルドされたGoプログラムも、`debug/dwarf`パッケージを通じて一貫した方法で配列の長さを取得できるようになります。

この変更は、Goのデバッグ体験を向上させ、特に0-length配列のようなGo特有の概念がデバッガでより正確に表現されるようにするための重要なステップです。

## コアとなるコードの解説

### `src/cmd/ld/dwarf.c` の変更点

このファイルでは、DWARFデバッグ情報を生成するリンカ側のロジックが変更されています。

-   **`DWAbbrev`構造体の変更**:
    `DW_TAG_subrange_type`を定義する`DWAbbrev`構造体において、以前は`DW_AT_upper_bound`を使用すると宣言されていましたが、これが`DW_AT_count`に変更されました。これは、リンカが今後`DW_AT_count`属性を生成することを示すメタデータ定義です。

-   **`defgotype`関数内の`newattr`呼び出し**:
    Goの配列型をDWARFに変換する`defgotype`関数内で、配列の長さを設定する部分が変更されました。
    以前は`newattr(fld, DW_AT_upper_bound, DW_CLS_CONSTANT, decodetype_arraylen(gotype)-1, 0);`のように、`decodetype_arraylen(gotype)`（Goの型情報から配列の長さを取得する関数）の結果から1を引いた値を`DW_AT_upper_bound`として設定していました。これは、`upper_bound`がインデックスの最大値を示すためです。
    変更後は`newattr(fld, DW_AT_count, DW_CLS_CONSTANT, decodetype_arraylen(gotype), 0);`となり、`decodetype_arraylen(gotype)`の戻り値をそのまま`DW_AT_count`として設定するようになりました。これにより、0-length配列の場合も`count`が0として正確に表現されます。コメント`// use actual length not upper bound; correct for 0-length arrays.`がこの意図を明確に示しています。

-   **`synthesizemaptypes`関数内の`newattr`呼び出し**:
    マップ型に関連するDWARF情報を生成する`synthesizemaptypes`関数内でも同様に、`DW_AT_upper_bound`が`DW_AT_count`に置き換えられ、`BucketSize`が直接`DW_AT_count`に渡されるようになりました。これは、マップの内部構造における配列のような要素の表現にも一貫性を持たせるためです。

### `src/pkg/debug/dwarf/type.go` の変更点

このファイルでは、DWARFデバッグ情報を読み取る`debug/dwarf`パッケージ側のロジックが変更されています。

-   **`readType`関数内の`TagSubrangeType`処理**:
    `readType`関数は、DWARF情報からGoの型を再構築する主要な関数です。この関数内で`DW_TAG_subrange_type`（配列の次元を示すタグ）を処理する`switch`文の`case`が変更されました。
    以前は`max, ok := kid.Val(AttrUpperBound).(int64)`のように、`AttrUpperBound`属性から配列の最大インデックスを読み取っていました。
    変更後は、まず`count, ok := kid.Val(AttrCount).(int64)`のように、`AttrCount`属性から配列の要素数を読み取ろうとします。
    もし`AttrCount`の読み取りに失敗した場合（`!ok`）、それは古いリンカで生成されたバイナリである可能性が高いため、`// Old binaries may have an upper bound instead.`というコメントの通り、`count, ok = kid.Val(AttrUpperBound).(int64)`として`AttrUpperBound`を読み取ろうとします。
    `AttrUpperBound`から値が読み取れた場合、その値はインデックスの最大値なので、実際の要素数を得るために`count++`（`Length is one more than upper bound.`）という補正が行われます。
    どちらの属性からも値が読み取れなかった場合（例えば、可変長配列など）、`count`は`-1`に設定されます（`// As in x[].`）。
    最終的に、取得した`count`の値が`t.Count`（配列の要素数）に設定されるか、多次元配列の場合はネストされた`ArrayType`の`Count`に設定されます。

この変更により、`debug/dwarf`パッケージは、新しいリンカが生成する`DW_AT_count`ベースのデバッグ情報と、古いリンカが生成する`DW_AT_upper_bound`ベースのデバッグ情報の両方を透過的に処理できるようになり、後方互換性が確保されます。

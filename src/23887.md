## 変更の背景

Go言語のCgoは、GoコードからCコードを呼び出したり、CコードからGoコードを呼び出したりするための強力なメカニズムを提供します。しかし、Cgoの特定の利用パターン、特にGo関数をCにエクスポートする`//export`ディレクティブを使用する際には、C言語のリンケージ規則とCgoの内部動作を理解していないと、予期せぬリンカーエラーに遭遇することがあります。

このコミットの背景には、ユーザーがCgoを使用してGo関数をCにエクスポートする際に、Cの宣言と定義を同じCgoプリアンブル（Goファイルの`import "C"`の前のコメントブロック）に記述してしまうという一般的な誤解がありました。このような記述方法は、結果としてリンカーが「重複シンボル (duplicate symbol)」エラーを報告する原因となります。

コミットメッセージにもあるように、「This edit is based on opening issue #11263 erroneously.」とあり、これはユーザーが誤って重複シンボルに関する問題を報告したことがきっかけで、既存のドキュメントがこの点について十分に明確ではないと判断されたことを示唆しています。この変更は、このようなエラーに遭遇したユーザーが、関連するキーワードで検索した際に、より明確な説明を見つけられるようにすることを目的としています。

## 前提知識の解説

### Cgoとは

Cgoは、GoプログラムがC言語のコードを呼び出すことを可能にするGoツールチェーンの一部です。また、CgoはGo関数をCコードにエクスポートし、CコードからGo関数を呼び出すことも可能にします。これは、既存のCライブラリを利用したり、パフォーマンスが重要な部分をCで記述したりする場合に非常に有用です。

Cgoを使用するには、Goソースファイル内で`import "C"`という特別なインポート宣言を行います。この宣言の直前のコメントブロックは「Cgoプリアンブル」と呼ばれ、C言語のコード（宣言、定義、インクルードなど）を記述できます。

### C言語における宣言と定義

C言語（およびC++）において、**宣言 (declaration)** と **定義 (definition)** は異なる概念です。

*   **宣言**: 変数や関数の名前、型、引数リストなどをコンパイラに知らせるものです。これにより、コンパイラはその名前がどのように使用されるべきかを知り、型チェックを行うことができます。宣言は複数回行うことができます。
    *   例（関数宣言）: `int add(int a, int b);`
    *   例（変数宣言）: `extern int global_var;`
*   **定義**: 変数にメモリを割り当て、初期値を設定したり、関数の具体的な実装（本体）を提供したりするものです。定義はプログラム全体で一度だけ行われる必要があります（One Definition Rule: ODR）。
    *   例（関数定義）:
        ```c
        int add(int a, int b) {
            return a + b;
        }
        ```
    *   例（変数定義）: `int global_var = 10;`

### 重複シンボルエラー (Duplicate Symbol Error)

リンカーは、コンパイルされたオブジェクトファイル（`.o`ファイルなど）を結合して実行可能ファイルやライブラリを作成するツールです。リンカーは、プログラム内で使用されるすべてのシンボル（関数名、変数名など）が、最終的な実行可能ファイル内で一意の定義を持つことを期待します。

もし、同じシンボルに対して複数の定義が見つかった場合、リンカーは「重複シンボルエラー」を報告し、リンク処理を停止します。これは、リンカーがどの定義を使用すべきか判断できないためです。

## 技術的詳細

Cgoが`//export`ディレクティブを含むGoファイルを処理する際、その動作は通常のCgoの動作とは少し異なります。

1.  **`//export`ディレクティブの役割**: `//export MyGoFunction`のように記述されたGo関数は、CgoによってC言語から呼び出し可能な関数としてエクスポートされます。Cgoは、このGo関数に対応するC言語のラッパー関数を生成します。

2.  **Cgoの内部処理**: `//export`ディレクティブが存在する場合、CgoはGoソースファイル内のCgoプリアンブルを**2つの異なるCソースファイル**にコピーします。
    *   一つは、GoコードからC関数を呼び出すための通常のCgo処理で使用されるCファイル。
    *   もう一つは、エクスポートされたGo関数に対応するCラッパー関数を定義し、GoランタイムとCコード間の橋渡しをするためのCファイル。

3.  **重複シンボルの発生**:
    *   もしCgoプリアンブルにC関数の**宣言のみ**が含まれている場合（例: `void myCFunction();`）、この宣言は両方のC出力ファイルにコピーされても問題ありません。宣言は複数回行われても重複シンボルエラーにはなりません。
    *   しかし、もしCgoプリアンブルにC関数の**定義**が含まれている場合（例: `void myCFunction() { /* ... */ }`）、この定義は両方のC出力ファイルにコピーされてしまいます。結果として、リンカーは`myCFunction`というシンボルに対して2つの定義を見つけることになり、重複シンボルエラーが発生します。

このため、`//export`を使用するファイルでは、CgoプリアンブルにはCの**宣言のみ**を記述し、**定義は含めない**という厳格なルールがあります。Cの定義が必要な場合は、別のCソースファイル（`.c`ファイルなど）に記述するか、`//export`を使用しないGoファイルのCgoプリアンブルに記述する必要があります。

## コアとなるコードの解説

変更は`src/cmd/cgo/doc.go`ファイル内のCgoドキュメントの一部です。具体的には、`//export`ディレクティブに関する説明が修正されています。

**変更前**:
```
Using //export in a file places a restriction on the preamble:
since it is copied into two different C output files, it must not
contain any definitions, only declarations. Definitions must be
placed in preambles in other files, or in C source files.
```
この記述は、`//export`を使用するファイルのプリアンブルには定義を含めず、宣言のみを記述すべきであるというルールを述べています。また、定義は他のファイルのプリアンブルかCソースファイルに置くべきであると指示しています。

**変更後**:
```
Using //export in a file places a restriction on the preamble:
since it is copied into two different C output files, it must not
contain any definitions, only declarations. If a file contains both
definitions and declarations, then the two output files will produce
duplicate symbols and the linker will fail. To avoid this, definitions
must be placed in preambles in other files, or in C source files.
```
変更点は、以下の文が追加されたことです。
`If a file contains both definitions and declarations, then the two output files will produce duplicate symbols and the linker will fail. To avoid this, definitions must be placed in preambles in other files, or in C source files.`

この追加により、ドキュメントは単に「定義を含めるな」と指示するだけでなく、**なぜ定義を含めてはいけないのか**という理由（「2つの出力ファイルが重複シンボルを生成し、リンカーが失敗する」）を明確に説明しています。これにより、ユーザーは問題の根本原因を理解し、将来的に同様のエラーに遭遇した際に、より効果的にデバッグできるようになります。

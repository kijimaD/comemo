## 元コミット内容

このコミットは、Goランタイムの`Callers`関数のコメントを更新するものです。`Callers`が報告するプログラムカウンタ（PC）を、開発者が実際に知りたいファイル名と行番号に変換する方法に関する混乱を解消しようと試みています。この変更は、Issue #7690を修正するものです。

## 変更の背景

Go言語の`runtime`パッケージには、現在のゴルーチンのスタックトレースを取得するための`Callers`関数が提供されています。この関数は、呼び出し元の関数のプログラムカウンタ（PC）のリストを返します。しかし、開発者がこれらのPC値を使ってファイル名や行番号を取得しようとした際に、期待する結果と異なる場合があるという混乱が生じていました。

具体的には、`Callers`が返すPC値は、関数呼び出し命令の直後の命令のアドレスを指していました。そのため、`runtime.Func`の`FileLine`メソッドなどを使ってPC値からファイル名と行番号を取得すると、呼び出しが行われた場所ではなく、呼び出しから戻った直後のコードの場所が報告されてしまうという問題がありました。この挙動は、特にデバッグやエラー報告の際に、開発者が直感的に期待する情報と異なっていたため、多くの混乱を招いていました。

このコミットは、この長年の混乱を解消するために、`Callers`関数のドキュメンテーションを改善し、PC値の正しい解釈方法を明確に説明することを目的としています。

## 前提知識の解説

### プログラムカウンタ (Program Counter, PC)

プログラムカウンタ（PC）は、CPUが次に実行する命令のアドレスを保持するレジスタです。Go言語のコンテキストでは、スタックトレースやプロファイリングにおいて、特定のコード実行位置を示すためにPC値が用いられます。

### `runtime.Callers`関数

`runtime.Callers`は、現在のゴルーチンのコールスタック上の関数呼び出しのプログラムカウンタを収集するためのGo標準ライブラリ関数です。
`func Callers(skip int, pc []uintptr) int`
- `skip`: スタックフレームをスキップする数を指定します。`0`は`Callers`関数自身のフレームを指し、`1`は`Callers`の呼び出し元のフレームを指します。
- `pc`: プログラムカウンタを格納するための`uintptr`型のスライスです。
- 戻り値: `pc`スライスに書き込まれたエントリの数を返します。

### `runtime.Func`と`FileLine`メソッド

`runtime.Func`型は、Goの関数に関する情報（名前、ファイル名、行番号など）を提供します。`(*runtime.Func).FileLine(pc uintptr)`メソッドは、与えられたプログラムカウンタ`pc`に対応するファイル名と行番号を返します。

### 呼び出し規約とPC値の特性

多くのCPUアーキテクチャやコンパイラにおいて、関数呼び出し（`CALL`命令など）が実行される際、リターンアドレス（呼び出し元に戻るべきアドレス）はスタックにプッシュされます。このリターンアドレスは、通常、呼び出し命令の直後の命令のアドレスを指します。Goの`Callers`関数が返すPC値は、このリターンアドレスに相当するため、`FileLine`メソッドでそのまま使用すると、呼び出し命令自体ではなく、呼び出しから戻った後の命令のファイルと行が報告されるという特性がありました。

## 技術的詳細

このコミットの技術的な詳細は、`runtime.Callers`関数のドキュメンテーションの更新に集約されています。以前のコメントでは、`Callers`が返すPC値が「関数呼び出しのプログラムカウンタ」であると漠然と説明されていましたが、これが誤解を招いていました。

新しいコメントでは、以下の重要な点が明確にされています。

1.  **戻りプログラムカウンタ (Return Program Counter)**: `Callers`が返す各`pc[i]`は、関数呼び出しの「戻りプログラムカウンタ」であると明記されました。これは、呼び出し命令の直後の命令のアドレスを意味します。

2.  **`FileLine`の挙動**: `pc[i]`をそのまま`(*Func).FileLine`に渡すと、呼び出し命令の直後の命令のファイル名と行番号が返されることが明確に説明されています。

3.  **正しいファイル/行番号の取得方法**: 開発者が実際に知りたい「呼び出し命令自体のファイル名と行番号」を取得するためには、`pc[i]-1`を使用する必要があることが指示されています。これは、呼び出し命令が通常1バイト以上の長さを持つため、その直前のアドレス（つまり呼び出し命令のアドレス）を指すようにPC値をデクリメントするというテクニックです。

4.  **`runtime.sigpanic`の例外**: このルールには重要な例外が設けられています。もし`pc[i-1]`が`runtime.sigpanic`関数に対応する場合、`pc[i]`はフォールト（障害）を起こした命令のプログラムカウンタであるため、減算せずにそのまま使用すべきであるとされています。`runtime.sigpanic`は、Goランタイムがパニックを処理する際に内部的に使用される関数であり、このコンテキストではPC値が特殊な意味を持つため、この例外が設けられました。

このコメントの更新により、`Callers`の挙動に関する曖昧さが解消され、開発者がより正確なスタックトレース情報を取得できるようになりました。

## コアとなるコードの解説

変更は`Callers`関数のドキュメンテーションコメントに限定されています。コードのロジック自体は変更されていません。

以前のコメント:
`// Callers fills the slice pc with the program counters of function invocations`
（Callersは、関数呼び出しのプログラムカウンタをpcスライスに格納します）

新しいコメント:
`// Callers fills the slice pc with the return program counters of function invocations`
（Callersは、関数呼び出しの戻りプログラムカウンタをpcスライスに格納します）

この変更により、「プログラムカウンタ」という曖昧な表現が「戻りプログラムカウンタ」と具体化され、PC値が呼び出し命令の直後のアドレスを指すという事実が明確にされました。

さらに、以下の詳細な説明が追加されました。
- `pc[i]`を`(*Func).FileLine`で使用すると、呼び出しの直後の命令のファイルと行が返されること。
- 呼び出し命令自体のファイルと行を取得するには`pc[i]-1`を使用すること。
- `runtime.sigpanic`の場合のみ、`pc[i]`を減算せずにそのまま使用するという例外ルール。

これらの追加説明は、`Callers`関数の利用者がPC値を正しく解釈し、期待するスタックトレース情報を取得できるようにするための重要なガイダンスとなります。

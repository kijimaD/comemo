# [インデックス 23239] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）がスタックフレーム、グローバルデータセクション（`.data`）、およびBSSセクション（`.bss`）内のポインタ情報を追跡するために使用するビットマップの表現を最適化するものです。具体的には、以前はポインタあたり2ビットを使用していたビットマップを、1ビットに削減しています。これにより、バイナリサイズが約1.1%削減され、メモリ使用量が減少します。パフォーマンスへの影響はほぼありませんが、将来的なさらなる最適化の道を開く変更です。

## 変更の背景

Goのガベージコレクタ（GC）は、メモリ内のポインタを正確に識別し、到達可能なオブジェクトを追跡するためにビットマップを使用します。以前のGoランタイムでは、スタックフレーム、グローバルデータセクション（`.data`）、およびBSSセクション（`.bss`）内のポインタ情報を表現するために、ポインタあたり2ビットのビットマップを使用していました。この2ビット表現は、スカラー値、ポインタ、マルチワード構造、そして未初期化値とスカラー値を区別するために設計されていました。

しかし、コミットメッセージによると、GCの観点からは「マルチワード構造」という概念がなくなったため、これらの領域でポインタと非ポインタ（スカラー、未初期化、デッド）を区別するだけで十分になりました。GCが本当に必要とする情報は、そのメモリ位置が「ライブポインタ」であるかどうかだけであり、それ以上の詳細な区別は不要でした。

この冗長な情報表現は、バイナリサイズとメモリ使用量の無駄につながっていました。特に、スタックフレームのビットマップはバイナリの読み取り専用データ（rodata）セクションに直接格納されるため、ビットマップのサイズ削減はバイナリ全体のサイズに直接影響します。このコミットは、この冗長性を排除し、より効率的な1ビット表現に切り替えることで、バイナリサイズとメモリ使用量を削減することを目的としています。

## 前提知識の解説

### Goのガベージコレクション（GC）とポインタビットマップ

GoのGCは、並行性、非世代性、非圧縮性のマーク＆スイープアルゴリズムを採用しています。GCは、プログラムが使用しているメモリ（ヒープ）を自動的に管理し、不要になったオブジェクトを解放します。このプロセスにおいて、GCはどのメモリ位置がポインタを含んでいるかを正確に知る必要があります。この情報を提供するために、Goランタイムは「ポインタビットマップ」を使用します。

*   **GCルート**: GCは、プログラムの実行中に常に到達可能であると見なされる「ルート」からオブジェクトグラフの走査を開始します。主なGCルートには、グローバル変数（`.data`および`.bss`セクション）、ゴルーチンのスタックフレーム、およびCPUレジスタが含まれます。
*   **ビットマップの種類**:
    *   **1ビットビットマップ**: 主にスタックフレームとグローバル変数（`.data`および`.bss`セクション）で使用されます。各ポインタサイズのワードに対して1ビットが割り当てられます。`1`はライブポインタを示し、`0`はスカラー値、未初期化値、またはGCにとって無関係な値を示します。
    *   **2ビットビットマップ**: 主にヒープメモリで使用されます。各ポインタサイズのワードに対して2ビットが割り当てられ、より詳細な情報（例: `typeScalar`、`typePointer`、`typeDead`、`typePointerCheckmarked`）をエンコードします。
        *   `typeDead` (00): ポインタではない、またはオブジェクトの記述が終了したことを示す。
        *   `typeScalar` (01): スカラー値（ポインタではない）。
        *   `typePointer` (10): ライブポインタ。
        *   `typePointerCheckmarked` (11): GC内部のチェックマーク用ポインタ。
    *   **4ビットビットマップ**: コミットメッセージには「4-bit heap bitmaps」という言及がありますが、これはGCのポインタ追跡におけるビットマップの直接的な種類ではなく、ヒープのより高レベルなビットマップ表現や、特定の内部的な用途を指す可能性があります。GoのGCにおけるポインタ追跡の文脈では、主に1ビットと2ビットのビットマップが中心です。

### スタックフレーム

Goでは、各ゴルーチンが独自のスタックを持っています。関数が呼び出されると、その関数のローカル変数、引数、戻りアドレスなどを格納するための「スタックフレーム」がスタックにプッシュされます。関数が終了すると、スタックフレームはポップされ、そのメモリは自動的に解放されます。スタックフレーム内のポインタはGCルートとして扱われ、GCはこれらのポインタを走査してヒープ上のオブジェクトの到達可能性を判断します。

### データセクションとBSSセクション

プログラムのメモリレイアウトには、主に以下のセクションがあります。

*   **`.data`セクション**: 初期化されたグローバル変数や静的変数が格納されます。プログラムの開始時に値が設定されています。
*   **`.bss`セクション**: 初期化されていないグローバル変数や静的変数が格納されます。プログラムの開始時にゼロで初期化されます。

これらのセクションに格納されるグローバル変数もGCルートであり、GCはこれらのセクションをスキャンしてヒープ上のポインタを識別します。

### マルチワード構造

Goにおける「マルチワード構造」とは、単一のCPUワード（32ビットシステムでは4バイト、64ビットシステムでは8バイト）よりも多くのメモリを占めるデータ構造を指します。これには、構造体、配列、スライス、マップ、インターフェース、文字列などが含まれます。GCは、これらの構造体内に埋め込まれたポインタを正確に識別するために、型情報とビットマップを利用します。

## 技術的詳細

このコミットの核心は、スタックフレーム、`.data`、`.bss`セクションのポインタビットマップを2ビットから1ビットに削減することです。

**変更前（2ビット表現）**:
以前は、これらの領域の各ポインタサイズのワードに対して2ビットが使用されていました。
*   `typeScalar` (01): スカラー値
*   `typePointer` (10): ポインタ
*   `typeDead` (00): 未初期化またはデッドな値

GCの観点からすると、`typeScalar`と`typeDead`はどちらも「ポインタではない」という情報しか必要ありませんでした。GCは、これらの値がヒープ上のオブジェクトを指しているかどうかだけを気にします。したがって、スカラーと未初期化を区別するための追加のビットは冗長でした。

**変更後（1ビット表現）**:
このコミットでは、スタックフレーム、`.data`、`.bss`セクションのビットマップを1ビット表現に簡素化します。
*   `1`: ライブポインタ
*   `0`: ポインタではない（スカラー、未初期化、デッドのいずれか）

この変更により、GCは「ライブポインタか否か」という必要最低限の情報のみをビットマップから取得できるようになります。

**2ビットから1ビットへの変換ロジック**:
コミットメッセージには、2ビット形式から1ビット形式への変換は `x>>1` で、1ビット形式から2ビット形式への変換は `x+1` で行えると説明されています。
*   2ビット形式 (`typeScalar`=01, `typePointer`=10) を1ビット形式に変換する場合:
    *   `typeScalar` (01) `>> 1` -> `0`
    *   `typePointer` (10) `>> 1` -> `1`
    これは、`typeScalar`と`typeDead`が`0`になり、`typePointer`が`1`になることを意味し、GCが必要とする「ポインタか否か」の情報に合致します。
*   1ビット形式 (`0`, `1`) を2ビット形式に変換する場合:
    *   `0` `+ 1` -> `1` (これは`typeScalar`に相当)
    *   `1` `+ 1` -> `2` (これは`typePointer`に相当)
    この変換は、`reflect`データなど、まだ2ビット表現を必要とする箇所との互換性を保つために使用されます。

**影響**:
*   **バイナリサイズの削減**: スタックフレームのビットマップはバイナリのrodataセクションに直接埋め込まれるため、ビットマップのサイズが半分になることで、`6g`（Goコンパイラ）のバイナリサイズが約1.1%削減されます。
*   **メモリ使用量の削減**: ランタイムがスタックフレームやグローバル変数のポインタ情報を格納するために使用するメモリ量が減少します。
*   **パフォーマンス**: ベンチマーク結果を見ると、全体的なパフォーマンスへの影響はほとんどありません（"basically a wash"）。一部のベンチマークではわずかな改善が見られ、一部ではわずかな悪化が見られますが、統計的に有意な大きな変化ではありません。
*   **将来の最適化**: この変更は、他のビットマップの削減やGCのさらなる最適化を可能にする基盤となります。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   `src/cmd/internal/gc/pgen.go`: コンパイラのコード生成部分。引数や戻り値のポインタマップを生成する関数で、`twobitwalktype1`から`onebitwalktype1`への呼び出しに変更されています。

*   `src/cmd/internal/gc/reflect.go`: コンパイラの`reflect`データ生成部分。GCマスクを生成する際に`twobitwalktype1`から`onebitwalktype1`への呼び出しに変更され、1ビット表現からGCビットエンコーディング（2ビット）への変換ロジックが更新されています。
*   `src/cmd/internal/gc/walk.go`: コンパイラのASTウォーク処理部分。ライトバリア関連の処理で、ビットマップのサイズ計算と`twobitwalktype1`から`onebitwalktype1`への呼び出しが変更されています。
*   `src/runtime/gcinfo_test.go`: GC情報に関するテストファイル。`nonStackInfo`ラッパーが削除され、期待されるビットマップ表現が2ビットから1ビットのロジックに合わせて更新されています。特に、`infoString`、`infoSlice`、`infoBigStruct`などのビットマップ定義が変更されています。

*   `src/runtime/mbitmap.go`: メモリビットマップの定義と操作。`typeBitsWidth`が2ビットのまま維持されつつ、スタック、データ、BSSのビットマップが1ビット表現を使用することがコメントで明記されています。`unrollgcprog1`関数内で、`sparse`フラグが`false`の場合（データ/BSS用）に1ビット表現に変換するロジックが追加されています。また、`getgcmask`関数内で、データ/BSSセクションのビットマップを読み取る際に1ビットから2ビットへの変換 (`bits += 1`) が行われるようになっています。

*   `src/runtime/mgcmark.go`: GCのマークフェーズ。`oneptr`が`oneptrmask`にリネームされ、その値が`typePointer`から`1`に変更されています。`scanblock`および`scanobject`関数が変更され、ポインタビットマップの処理が1ビット表現に対応するように修正されています。特に`scanblock`は、明示的なポインタビットマップを使用するようになり、`scanobject`はヒープオブジェクトの先頭を指すことを前提とするようになりました。

## コアとなるコードの解説

### `src/cmd/internal/gc/plive.go` の変更

このファイルでは、ポインタビットマップを生成する主要な関数が`twobitwalktype1`から`onebitwalktype1`にリネームされ、そのロジックが簡素化されています。

```go
// 変更前:
// func twobitwalktype1(t *Type, xoffset *int64, bv Bvec) {
// ...
// 	bvset(bv, int32(((*xoffset+i)/int64(Widthptr))*obj.BitsPerPointer)) // 1 = live scalar (BitsScalar)
// ...
// 	bvset(bv, int32((*xoffset/int64(Widthptr))*obj.BitsPerPointer+1)) // 2 = live ptr (BitsPointer)

// 変更後:
func onebitwalktype1(t *Type, xoffset *int64, bv Bvec) {
	// ...
	// スカラー型の場合、ビットマップ設定のロジックが削除された。
	// 以前はスカラーもビットマップに記録していたが、1ビット表現ではポインタのみを記録するため不要。
	// ...
	case TPTR32,
		TPTR64,
		TCHAN,
		TMAP:
		if *xoffset&int64(Widthptr-1) != 0 {
			Fatal("onebitwalktype1: invalid alignment, %v", t)
		}
		bvset(bv, int32(*xoffset/int64(Widthptr))) // pointer (1ビット表現では単にインデックスを設定)
		*xoffset += t.Width
	// ...
}
```
`twobitwalktype1`では`obj.BitsPerPointer`（2）を乗算して2ビット単位でビットマップを操作していましたが、`onebitwalktype1`ではこれが削除され、ポインタサイズのワードごとに1ビットを直接設定するようになっています。スカラー型に対するビットマップ設定ロジックも削除され、ポインタ型のみがビットマップに記録されるようになりました。

### `src/runtime/mbitmap.go` の変更

このファイルでは、ビットマップの定数と、GCプログラムを展開してビットマップを生成するロジックが変更されています。

```go
// 変更前:
// const (
// 	typeBitsWidth   = 2 // # of type bits per pointer-sized word
// 	typeMask        = 1<<typeBitsWidth - 1
// 	typeBitmapScale = ptrSize * (8 / typeBitsWidth) // number of data bytes per type bitmap byte
// )

// 変更後:
const (
	typeBitsWidth = 2 // # of type bits per pointer-sized word (これはreflectデータなどのために2のまま)
	typeMask      = 1<<typeBitsWidth - 1
	// typeBitmapScale は削除された
)

// コメントの追加:
// Stack, data, and bss bitmaps
// Not handled in this file, but worth mentioning: stack frames and global data
// in the data and bss sections are described by 1-bit bitmaps in which 0 means
// scalar or uninitialized or dead and 1 means pointer to visit during GC.
// Comparing this 1-bit form with the 2-bit form described below, 0 represents
// both the 2-bit 00 and 01, while 1 represents the 2-bit 10.
// Therefore conversions between the two (until the 2-bit form is gone)
// can be done by x>>1 for 2-bit to 1-bit and x+1 for 1-bit to 2-bit.

// unrollgcprog1 関数内の変更:
// 変更前:
// 				} else {
// 					// 2-bits per word
// 					v <<= pos % 8
// 					mask[pos/8] |= v
// 					pos += typeBitsWidth
// 				}
// 変更後:
				} else {
					// 1 bit per word, for data/bss bitmap
					v >>= 1 // convert typePointer to 1, others to 0
					mask[pos/8] |= v << (pos % 8)
					pos++
				}

// getgcmask 関数内のデータ/BSSセクションのビットマップ読み取りロジック:
// 変更前:
// 				bits := (*(*byte)(add(unsafe.Pointer(datap.gcdatamask.bytedata), off/typeBitsPerByte)) >> ((off % typeBitsPerByte) * typeBitsWidth)) & typeMask
// 				*(*byte)(add(unsafe.Pointer(*mask), i/ptrSize)) = bits
// 変更後:
				bits := (*addb(datap.gcdatamask.bytedata, off/8) >> (off % 8)) & 1
				bits += 1 // convert 1-bit to 2-bit
				*addb(*mask, i/ptrSize) = bits
```
`mbitmap.go`では、`typeBitsWidth`自体は`2`のままですが、これは`reflect`データなど、まだ2ビット表現を必要とする箇所のためです。しかし、スタック、データ、BSSセクションのビットマップは1ビット表現を使用することが明示され、`unrollgcprog1`関数内でGCプログラムを展開する際に、データ/BSS用のビットマップを生成する際には2ビット値を1ビット値に変換（`v >>= 1`）して格納するロジックが追加されています。また、`getgcmask`関数では、データ/BSSの1ビットビットマップを読み取った後、必要に応じて2ビット表現に変換（`bits += 1`）して返すようになっています。

### `src/runtime/gcinfo_test.go` の変更

このテストファイルでは、期待されるGC情報ビットマップの定義が、2ビット表現から1ビット表現のロジックに合わせて更新されています。

```go
// 変更前:
// 	infoString = []byte{typePointer, typeDead}
// 	infoSlice  = []byte{typePointer, typeDead, typeDead}

// 変更後:
	infoString = []byte{typePointer, typeScalar} // typeDeadがtypeScalarに置き換えられた
	infoSlice  = []byte{typePointer, typeScalar, typeScalar} // typeDeadがtypeScalarに置き換えられた
```
`typeDead`が`typeScalar`に置き換えられているのは、1ビット表現では「ポインタではない」という情報しか持たないため、以前の`typeDead`が表していた「未初期化」や「デッド」といった区別が不要になり、単に「スカラー」（ポインタではない）として扱われるようになったことを示唆しています。

これらの変更は、Goランタイムがメモリ内のポインタ情報をよりコンパクトかつ効率的に表現するための重要なステップであり、バイナリサイズとメモリ使用量の削減に貢献します。

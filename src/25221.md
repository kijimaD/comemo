## 変更の背景

このコミットは、Goランタイムのガベージコレクタ（GC）における`gcAssistAlloc`関数のコメントの誤りを修正することを目的としています。`gcAssistAlloc`は、ユーザープログラム（ミューテーター）がメモリを割り当てる際に、GCの作業を補助（アシスト）するためのメカニズムです。このアシストは、GCがバックグラウンドで進行している間に、ミューテーターが過剰にメモリを割り当ててGCの進行を妨げないようにするために重要です。

元のコメントでは、`gcAssistAlloc`が呼び出されるべき条件として`gcAssistAlloc != 0`と記述されていました。しかし、実際のランタイムのロジックでは、GCの「ブラックニング」（オブジェクトをマークするフェーズ）が有効になっているかどうかを示す`gcBlackenEnabled`というフラグが、このアシスト処理の有効性を制御していました。このコメントの不一致は、コードの理解を妨げ、将来的なメンテナンスで混乱を招く可能性がありました。

Go 1.5で導入された新しいコンカレントGCは、ミューテーターとGCが並行して動作することを前提としており、このようなアシストメカニズムはGCのレイテンシを低減し、スループットを向上させる上で不可欠です。したがって、この重要な関数のコメントを正確に保つことは、ランタイムの正確な動作を反映し、開発者がGCの内部動作を理解する上で非常に重要でした。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goのガベージコレクションは、プログラムが使用しなくなったメモリを自動的に解放する仕組みです。Go 1.5では、従来のストップ・ザ・ワールド（STW）方式から、より低レイテンシなコンカレント（並行）GCへと大きく進化しました。この新しいGCは、ほとんどのGC作業をユーザープログラム（ミューテーター）と並行して実行することで、STWポーズ時間を大幅に短縮しました。

### コンカレントGCのフェーズ

GoのコンカレントGCは、主に以下のフェーズで構成されます。

1.  **マーク開始 (Mark Start)**: 短いSTWポーズでGCを開始します。ルートオブジェクトをスキャンし、GCワーカーを起動します。
2.  **並行マーク (Concurrent Mark)**: GCワーカーがユーザープログラムと並行して、到達可能なオブジェクトをマーク（ブラックニング）します。このフェーズ中にミューテーターが新しいオブジェクトを割り当てたり、既存のオブジェクトへのポインタを変更したりすると、GCの正確性を保つために「Write Barrier」が使用されます。
3.  **マーク終了 (Mark Termination)**: 短いSTWポーズで並行マークフェーズを終了し、残りのマーク作業を完了します。
4.  **並行スイープ (Concurrent Sweep)**: GCワーカーがユーザープログラムと並行して、マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放します。

### ミューテーターアシスト (Mutator Assist)

並行マークフェーズ中、ミューテーターが大量のメモリを割り当て続けると、GCワーカーがマークするよりも速く新しいオブジェクトが生成され、GCが追いつかなくなる可能性があります。これを防ぐために導入されたのが「ミューテーターアシスト」です。

ミューテーターアシストは、ミューテーターが一定量のメモリを割り当てた際に、GC作業の一部を強制的に実行させるメカニズムです。これにより、ミューテーターは自身の割り当てによって発生するGCの負担の一部を肩代わりし、GCの進行を助けます。これは、GCが完了する前にヒープが枯渇するのを防ぎ、GCの全体的なスループットとレイテンシのバランスを取る上で重要です。

### `gcAssistAlloc` と `gcBlackenEnabled`

*   **`gcAssistAlloc`**: Goランタイム内部の関数で、ミューテーターがメモリを割り当てる際にGCアシストを実行します。この関数は、ミューテーターが割り当てたバイト数に応じて、GCマーク作業を強制的に実行させます。
*   **`gcBlackenEnabled`**: Goランタイム内部のグローバル変数（またはフラグ）で、GCのブラックニング（マーク）フェーズが現在有効であるかどうかを示します。このフラグが`0`でない（つまり`true`）場合、GCはオブジェクトのマーク作業を行っている状態であり、ミューテーターアシストが必要となる可能性があります。

## 技術的詳細

このコミットで修正されたコメントは、`gcAssistAlloc`関数の直前に位置しており、この関数の呼び出し条件について説明していました。

元のコメント:
`// It should only be called if gcAssistAlloc != 0.`
（これは`gcAssistAlloc`が0でない場合にのみ呼び出されるべきである。）

修正後のコメント:
`// It should only be called if gcBlackenEnabled != 0.`
（これは`gcBlackenEnabled`が0でない場合にのみ呼び出されるべきである。）

この変更の技術的な意味合いは以下の通りです。

1.  **`gcAssistAlloc`は関数名であり、フラグではない**: `gcAssistAlloc`はGCアシストを実行する関数の名前であり、それ自体がGCアシストが有効かどうかを示すフラグではありません。コメントで`gcAssistAlloc != 0`と記述することは、関数名とフラグを混同しており、誤解を招く表現でした。
2.  **GCアシストの有効性制御**: ミューテーターアシストが実際に必要となるのは、GCがオブジェクトのマーク（ブラックニング）フェーズにあるときだけです。`gcBlackenEnabled`フラグは、まさにこのブラックニングフェーズが有効であるかどうかを示すものです。したがって、`gcAssistAlloc`が呼び出されるべき適切な条件は、`gcBlackenEnabled`が`0`でない（つまり、ブラックニングが進行中である）ことでした。
3.  **コードの正確な反映**: この修正は、Goランタイムの実際のGCロジックとコメントの整合性を保つものです。ランタイムのコードベースでは、`gcAssistAlloc`の呼び出しは`gcBlackenEnabled`の状態に依存しており、コメントがその事実を正確に反映するように更新されました。
4.  **可読性とメンテナンス性**: 正確なコメントは、Goランタイムの複雑なGCメカニズムを理解しようとする開発者にとって非常に重要です。この修正により、コードの可読性が向上し、将来的なGCの変更やデバッグ作業において、誤った前提に基づく判断を避けることができます。

この修正は、Go 1.5で導入された新しいコンカレントGCの内部動作をより正確に文書化する上で、小さながらも重要な改善でした。

## コアとなるコードの解説

変更された箇所は、`src/runtime/mgcmark.go`ファイル内の`gcAssistAlloc`関数の直前にあるコメントブロックです。

*   **元のコメント行**: `// It should only be called if gcAssistAlloc != 0.`
    *   この行は、「`gcAssistAlloc`は、`gcAssistAlloc`が0でない場合にのみ呼び出されるべきである」と述べていました。しかし、`gcAssistAlloc`は関数名であり、その値が0かどうかをチェックするようなフラグではありません。これは論理的に誤った記述でした。
*   **修正後のコメント行**: `// It should only be called if gcBlackenEnabled != 0.`
    *   この行は、「`gcAssistAlloc`は、`gcBlackenEnabled`が0でない場合にのみ呼び出されるべきである」と修正されました。
    *   `gcBlackenEnabled`は、GCのブラックニング（マーク）フェーズが現在アクティブであるかどうかを示すランタイム内部のフラグです。GCアシストは、このブラックニングフェーズ中にミューテーターがGC作業を補助するために行われるため、このフラグが`true`（0でない）であることが`gcAssistAlloc`を呼び出す適切な条件となります。

この修正は、コードの動作自体を変更するものではなく、その動作を説明するコメントの正確性を向上させるものです。これにより、GoランタイムのGCメカニズムを理解する上での混乱が解消され、コードベースの整合性が保たれます。

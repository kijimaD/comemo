## 変更の背景

Base64エンコーディングとデコーディングは、データをテキスト形式で安全に転送するために広く使用される操作です。特にネットワーク通信やデータストレージにおいて頻繁に利用されます。Go言語の標準ライブラリである `encoding/base64` パッケージは、これらの機能を提供しますが、大量のデータを扱う場合や、パフォーマンスがクリティカルなアプリケーションにおいては、その処理速度がボトルネックとなる可能性があります。

このコミットの背景には、既存のBase64エンコード/デコード処理の効率を向上させ、より高速なデータ変換を実現するという明確な目的があります。ベンチマーク結果が示すように、エンコードで約1.3倍、デコードで約1.9倍の速度向上は、特に高スループットが求められるシステムにおいて大きなメリットをもたらします。

具体的な改善点としては、以前の実装が文字列操作やバイトスライス操作において、不要なメモリ割り当てや関数呼び出しのオーバーヘッドを伴っていた可能性が考えられます。これらの非効率性を排除し、より低レベルなバイト操作とビット演算を直接利用することで、CPUキャッシュの利用効率を高め、全体的な実行時間を短縮することが目指されました。

## 前提知識の解説

### Base64エンコーディング

Base64は、バイナリデータをASCII文字列の形式に変換するエンコーディング方式です。主に、バイナリデータをテキストベースのプロトコル（例: 電子メール、HTTP）で安全に転送するために使用されます。

- **原理**: 3バイト（24ビット）のバイナリデータを、4つの6ビットのグループに分割し、それぞれの6ビット値をBase64アルファベット（A-Z, a-z, 0-9, +, /）のいずれかの文字にマッピングします。
- **パディング**: 入力データが3バイトの倍数でない場合、出力の最後に `=` 文字が追加され、データの長さを4の倍数に調整します。
- **Go言語の `encoding/base64` パッケージ**: Goの標準ライブラリとして提供されており、`StdEncoding` (標準Base64) や `URLEncoding` (URLセーフなBase64) など、様々なBase64エンコーディングをサポートしています。`EncodeToString` はバイトスライスをBase64文字列にエンコードし、`DecodeString` はBase64文字列をバイトスライスにデコードします。

### Go言語におけるパフォーマンス最適化の考慮事項

Go言語では、ガベージコレクション（GC）のオーバーヘッドを最小限に抑えるために、不要なメモリ割り当て（アロケーション）を避けることがパフォーマンス最適化の重要な要素となります。

- **アロケーションの削減**: 新しいスライスや文字列を頻繁に作成する操作は、ヒープアロケーションを引き起こし、GCの頻度と時間を増加させます。可能な限り既存のバッファを再利用したり、インプレースでデータを操作したりすることで、アロケーションを削減できます。
- **関数呼び出しのオーバーヘッド**: 小さな関数を頻繁に呼び出すことは、その都度スタックフレームの作成やレジスタの保存/復元といったオーバーヘッドを伴います。インライン化可能な処理はコンパイラによって最適化されますが、複雑なロジックやインターフェースを介した呼び出しはオーバーヘッドが大きくなる傾向があります。
- **ビット演算とバイト操作**: 低レベルなビット演算やバイト操作は、Go言語において非常に高速な処理を実現できます。特に、エンコーディング/デコーディングのようなデータ変換処理では、これらの操作を効率的に利用することがパフォーマンス向上に直結します。
- **`bytes.Map` と `strings.Map`**: これらの関数は、入力スライス/文字列の各要素に関数を適用し、新しいスライス/文字列を返します。これは便利ですが、新しいメモリを割り当てるため、パフォーマンスが重要なパスではボトルネックになる可能性があります。

## 技術的詳細

このコミットにおける主要な技術的最適化は以下の点に集約されます。

1.  **`Encoding.encode` フィールドの型変更**:
    - 変更前: `encode string`
    - 変更後: `encode [64]byte`
    - Base64アルファベットを文字列として保持する代わりに、固定サイズのバイト配列 `[64]byte` として保持するように変更されました。文字列はGoにおいて不変であり、その内部表現はバイトスライスですが、固定サイズの配列にすることで、アルファベットへのアクセスがより直接的かつ効率的になります。`NewEncoding` 関数では、入力されたエンコーダ文字列を `copy` 関数を使ってこのバイト配列にコピーするようになりました。これにより、エンファレンス時のオーバーヘッドが削減されます。

2.  **`Encode` 関数の実装の抜本的な見直し**:
    - 変更前は、`for len(src) > 0` ループ内で `switch len(src)` を使用し、入力データの残りの長さに応じて異なるロジックで3バイトを4文字にエンコードしていました。このアプローチは汎用的ですが、条件分岐が多く、バイトごとの処理が複雑でした。
    - 変更後:
        - `di, si := 0, 0` で出力と入力のインデックスを管理。
        - `n := (len(src) / 3) * 3` で、3バイトの完全なブロックの数を計算し、メインループでこれらのブロックを効率的に処理します。
        - メインループ `for si < n` 内では、3つの入力バイト `src[si+0]`, `src[si+1]`, `src[si+2]` を `uint` 型の `val` に結合します。
            ```go
            val := uint(src[si+0])<<16 | uint(src[si+1])<<8 | uint(src[si+2])
            ```
            このビットシフトと論理和の操作により、3バイトのデータが1つの整数値に効率的にパックされます。
        - その後、この `val` から6ビットずつ抽出し、`enc.encode` バイト配列を使って対応するBase64文字を直接 `dst` に書き込みます。
            ```go
            dst[di+0] = enc.encode[val>>18&0x3F]
            dst[di+1] = enc.encode[val>>12&0x3F]
            dst[di+2] = enc.encode[val>>6&0x3F]
            dst[di+3] = enc.encode[val&0x3F]
            ```
            この直接的なビット演算と配列アクセスは、以前の複雑な条件分岐やバイトごとの処理よりもはるかに高速です。
        - 最後に、残りの不完全なブロック（1バイトまたは2バイト）を `switch remain` で個別に処理し、必要に応じてパディング文字を追加します。
    - この変更により、ループ内の条件分岐が減り、ビット演算による高速なデータ変換が可能になりました。

3.  **`decode` 関数における改行文字の直接処理と最適化**:
    - 変更前は、`Decode` および `DecodeString` 関数が `bytes.Map` や `strings.Map` を使用して、入力データから改行文字 (`\r`, `\n`) を事前に除去していました。`removeNewlinesMapper` というヘルパー関数がそのために使われていました。
    - 変更後:
        - `bytes.Map` と `strings.Map` の使用が削除されました。これにより、改行文字を除去するために新しいスライスや文字列を割り当てるオーバーヘッドがなくなりました。
        - `decode` 関数自体が、入力 `src` スライスを走査する際に改行文字をスキップするロジックを内部に持つようになりました。
            ```go
            // skip over newlines
            for si < len(src) && (src[si] == '\n' || src[si] == '\r') {
                si++
            }
            ```
            この変更により、デコード処理全体が単一のパスで完結し、効率が向上しました。
        - デコードロジックも `Encode` と同様に、4つのBase64文字を1つの `uint` に結合し、そこから3バイトのバイナリデータを抽出するビット演算に最適化されました。
            ```go
            val := uint(dbuf[0])<<18 | uint(dbuf[1])<<12 | uint(dbuf[2])<<6 | uint(dbuf[3])
            // ...
            dst[2] = byte(val >> 0)
            dst[1] = byte(val >> 8)
            dst[0] = byte(val >> 16)
            ```
        - `CorruptInputError` のオフセット計算も、改行文字のスキップを考慮して `si` (現在のソースインデックス) を基準にするように修正され、より正確なエラー位置を報告できるようになりました。

これらの変更は、メモリ割り当ての削減、関数呼び出しのオーバーヘッドの排除、そして低レベルなビット演算とバイト操作の活用という、Go言語における典型的なパフォーマンス最適化手法を効果的に適用したものです。

## コアとなるコードの解説

### `Encoding` 構造体の変更と `NewEncoding`

`Encoding` 構造体の `encode` フィールドが `string` から `[64]byte` に変更されたことは、Base64アルファベットへのアクセス方法が根本的に変わったことを意味します。Goの文字列は不変であり、その要素アクセスにはわずかなオーバーヘッドが伴う可能性があります。一方、固定サイズのバイト配列 `[64]byte` は、コンパイル時にサイズが決定され、より直接的なメモリレイアウトを持つため、インデックスアクセスが非常に高速です。

`NewEncoding` 関数で `copy(e.encode[:], encoder)` を使用することで、入力文字列 `encoder` の内容が `e.encode` バイト配列に効率的にコピーされます。これにより、エンコード処理中に文字列からバイトへの変換や、文字列の不変性による潜在的なオーバーヘッドを回避できます。また、`len(encoder) != 64` のチェックが追加されたことで、不正な長さのエンコーダ文字列が渡された場合に早期にパニックを発生させ、堅牢性が向上しました。

### `Encode` 関数の最適化

以前の `Encode` 関数は、入力 `src` の残りの長さに応じて `switch` 文で分岐し、バイトを一つずつ処理するようなロジックでした。これは柔軟性がありますが、ループ内の条件分岐やバイトごとの操作がパフォーマンスのボトルネックとなっていました。

新しい `Encode` 関数は、以下の点で大幅に改善されています。

1.  **バッチ処理**: `n := (len(src) / 3) * 3` を計算することで、入力データを3バイトの完全なブロックに分割し、メインループでこれらのブロックをまとめて処理します。これにより、ループの反復回数が減り、オーバーヘッドが削減されます。
2.  **ビット演算による高速変換**:
    - `val := uint(src[si+0])<<16 | uint(src[si+1])<<8 | uint(src[si+2])`
        この行は、3つの8ビットバイトを1つの24ビット `uint` 値に結合します。これは、Base64エンコーディングの基本的な操作であり、非常に効率的なビット演算によって実現されます。
    - `dst[di+0] = enc.encode[val>>18&0x3F]` など
        結合された `val` から、右シフト (`>>`) とビットマスク (`& 0x3F`、つまり `& 0b111111`) を用いて6ビットのチャンクを抽出し、それを直接 `enc.encode` バイト配列のインデックスとして使用して対応するBase64文字を取得します。この直接的なマッピングは、以前の複雑な条件分岐や中間変数なしに、非常に高速に実行されます。
3.  **アロケーションの削減**: この新しい実装では、中間的なスライスや文字列の作成がほとんどなく、既存の `dst` バッファに直接書き込むため、ガベージコレクションの負担が大幅に軽減されます。

### `decode` 関数の最適化と改行処理の統合

以前の `Decode` および `DecodeString` 関数は、`bytes.Map` や `strings.Map` を使用して入力から改行文字を事前に除去していました。これらの `Map` 関数は新しいスライスや文字列を生成するため、メモリ割り当てとコピーのオーバーヘッドが発生していました。

新しい `decode` 関数は、以下の点で改善されています。

1.  **改行処理のインライン化**: `for si < len(src) && (src[si] == '\n' || src[si] == '\r') { si++ }` というループをデコード処理の内部に組み込むことで、入力データを読み込みながら同時に改行文字をスキップできるようになりました。これにより、`bytes.Map` や `strings.Map` の呼び出しとそれに伴うアロケーションが不要になり、処理が単一のパスで完結するため効率が向上します。
2.  **ビット演算による高速変換**: `Encode` 関数と同様に、4つのBase64文字に対応するデコードマップ値 (`dbuf`) を1つの `uint` に結合し、そこから3バイトのバイナリデータを抽出するビット演算が導入されました。
    - `val := uint(dbuf[0])<<18 | uint(dbuf[1])<<12 | uint(dbuf[2])<<6 | uint(dbuf[3])`
        これは、4つの6ビット値を1つの24ビット `uint` にパックする操作です。
    - `dst[2] = byte(val >> 0)`, `dst[1] = byte(val >> 8)`, `dst[0] = byte(val >> 16)`
        パックされた `val` から、右シフトを用いて元の3バイトのバイナリデータを抽出します。
3.  **正確なエラー報告**: `CorruptInputError` のオフセット計算が `si` (現在のソースインデックス) を基準にするように変更されたことで、改行文字のスキップを考慮した正確なエラー位置が報告されるようになりました。

これらの変更により、`encoding/base64` パッケージは、より高速でメモリ効率の良いBase64エンコード/デコード機能を提供するようになりました。

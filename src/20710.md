# [インデックス 20710] ファイルの概要

このコミットは、Go言語の標準ライブラリである `encoding/json` パッケージにおける、不正なマップ引数（具体的には、キーが文字列型ではないマップ）が与えられた際にパニック（panic）を引き起こすバグを修正するものです。JSONオブジェクトのキーは常に文字列であるというJSON仕様に準拠し、パニックではなく適切なエラーを返すように挙動が変更されました。

## 元コミット内容

`encoding/json: don't panic on incorrect map argument`
`Fixes #8305.`

このコミットは、`encoding/json` パッケージが、マップのキーが文字列ではない場合にパニックを起こす問題を修正します。これはGoのIssue #8305を解決するものです。

## 変更の背景

Goの `encoding/json` パッケージは、JSONデータをGoのデータ構造にエンコード（Marshal）およびデコード（Unmarshal）するための機能を提供します。JSONの仕様では、オブジェクト（Goのマップに相当）のキーは常に文字列でなければなりません。しかし、Goのマップは任意の比較可能な型をキーとして持つことができます。

このコミット以前は、`json.Unmarshal` 関数がJSONオブジェクトをGoのマップにデコードしようとした際、そのマップのキーの型が `string` ではない場合（例: `map[int]string` や `map[time.Time]string`）、`encoding/json` パッケージはパニックを引き起こしていました。これは、ライブラリが予期しない入力に対してパニックを起こすべきではないというGoの設計原則に反していました。パニックは回復不可能なエラーやプログラミング上のバグを示すために使用されるべきであり、入力データの検証エラーのような回復可能な状況では、適切なエラーを返すことが期待されます。

Issue #8305は、この特定のパニック挙動を報告しており、開発者は `encoding/json` がこのような状況でパニックするのではなく、`UnmarshalTypeError` のような適切なエラーを返すことを求めていました。

## 前提知識の解説

*   **JSON (JavaScript Object Notation)**: 軽量なデータ交換フォーマット。人間が読み書きしやすく、機械が解析・生成しやすい。JSONオブジェクトはキーと値のペアの集合であり、キーは必ず文字列でなければなりません。
*   **Goの `encoding/json` パッケージ**: Go言語でJSONデータを扱うための標準ライブラリ。`json.Marshal` はGoの値をJSONに変換し、`json.Unmarshal` はJSONデータをGoの値に変換します。
*   **Goの `reflect` パッケージ**: Goのプログラムが実行時に自身の構造を検査（リフレクション）するための機能を提供します。`reflect.Value` はGoの変数の実行時の値を表し、`reflect.Type` はその変数の型を表します。`Kind()` メソッドは、その型がプリミティブ型（`int`, `string` など）か、複合型（`struct`, `map` など）かを示します。
*   **Goの `panic`**: Goにおける回復不可能なエラーメカニズム。プログラムの実行を即座に停止させ、スタックトレースを出力します。通常、プログラミング上のバグや、回復不能なシステムエラーを示すために使用されます。ライブラリは、ユーザーの入力ミスのような回復可能なエラーに対してはパニックではなくエラー値を返すことが推奨されます。
*   **`UnmarshalTypeError`**: `encoding/json` パッケージが返すエラー型の一つ。JSONデータとGoのターゲット型の間に型ミスマッチがある場合に発生します。例えば、JSONの数値がGoの文字列にデコードされようとした場合などです。

## 技術的詳細

このコミットの技術的な核心は、`encoding/json` パッケージのデコード処理、特にJSONオブジェクトをGoのマップにデコードする際の挙動の変更にあります。

`json.Unmarshal` がJSONオブジェクトをGoのマップにデコードする際、内部的には `decodeState` 構造体の `object` メソッドが呼び出されます。このメソッドは、デコード対象のGoのマップのキーの型が `string` であることを期待します。

変更前は、`object` メソッド内でマップのキーの型をチェックし、それが `reflect.String` でない場合に `d.saveError` を呼び出した後、`break` ステートメントでループを抜けていました。しかし、この `break` の後、デコードの状態が不正なまま処理が続行され、結果としてパニックを引き起こす可能性がありました。

修正では、この `break` の代わりに以下の処理が追加されました。

1.  `d.saveError(&UnmarshalTypeError{"object", v.Type()})`: `UnmarshalTypeError` を保存し、型ミスマッチのエラーを記録します。
2.  `d.off--`: 現在の読み取りオフセットを1つ戻します。これは、直前に読み取った `{` 文字の位置に戻るためです。
3.  `d.next() // skip over { } in input`: `next()` メソッドを呼び出すことで、入力ストリーム中の `{` から `}` までのJSONオブジェクト全体をスキップします。これにより、不正なJSONオブジェクトのブロックを安全に読み飛ばし、デコード処理を続行できるようにします。
4.  `return`: `object` メソッドから即座にリターンします。これにより、不正なマップキーを持つオブジェクトの処理がそこで終了し、パニックが回避されます。

この変更により、`encoding/json` は、JSON仕様に反する（キーが文字列ではない）Goのマップ型へのデコードを試みた際に、パニックする代わりに `UnmarshalTypeError` を適切に返し、デコード処理を安全に継続できるようになりました。

また、この修正を検証するために、`decode_test.go` に新しいテストケースが追加されました。このテストケースは、`map[time.Time]string{}` のような、キーが文字列ではないマップ型に対してJSONオブジェクトをデコードしようとします。このテストは、パニックではなく `UnmarshalTypeError` が返されることを期待するように記述されています。

## コアとなるコードの解説

### `src/encoding/json/decode.go` の変更

`func (d *decodeState) object(v reflect.Value)` メソッドは、JSONオブジェクトをGoの `reflect.Value` にデコードする主要なロジックを含んでいます。

変更前のコード:
```go
		if t.Key().Kind() != reflect.String {
			d.saveError(&UnmarshalTypeError{"object", v.Type()})
			break // ここでループを抜けるが、状態が不正なまま処理が続く可能性があった
		}
```
この `break` は、マップのキーが `string` でない場合にエラーを記録しますが、デコード処理が完全に停止するわけではありませんでした。結果として、後続の処理で不正な状態を参照し、パニックを引き起こす可能性がありました。

変更後のコード:
```go
		if t.Key().Kind() != reflect.String {
			d.saveError(&UnmarshalTypeError{"object", v.Type()})
			d.off-- // '{' の位置に戻る
			d.next() // '{' から '}' までをスキップ
			return // メソッドから即座にリターン
		}
```
この修正により、マップのキーが `string` でないことが検出された場合、以下の安全な処理が行われます。
1.  `UnmarshalTypeError` を記録し、エラー状態を明確にします。
2.  `d.off--` でデコード中の入力ストリームのオフセットを1つ戻し、直前に読み込んだ `{` の位置に戻ります。
3.  `d.next()` を呼び出すことで、現在のJSONオブジェクトの開始 `{` から終了 `}` までの全てのデータを読み飛ばします。これにより、不正なJSONオブジェクトのブロック全体が安全にスキップされ、デコード処理がそのブロックの影響を受けなくなります。
4.  `return` で `object` メソッドの実行を終了します。これにより、不正なマップキーを持つオブジェクトの処理が完全に終了し、パニックが回避されます。

### `src/encoding/json/decode_test.go` の変更

新しいテストケースが `unmarshalTests` スライスに追加されました。

```go
	// issue 8305
	{
		in:  `{"2009-11-10T23:00:00Z": "hello world"}`,
		ptr: &map[time.Time]string{},
		err: &UnmarshalTypeError{"object", reflect.TypeOf(map[time.Time]string{})},
	},
```
このテストケースは、以下のシナリオを検証します。
*   `in`: JSON文字列 `{"2009-11-10T23:00:00Z": "hello world"}`。このJSONオブジェクトのキー `"2009-11-10T23:00:00Z"` は文字列ですが、デコード先のGoのマップのキー型は `time.Time` です。
*   `ptr`: デコード先のGoの型を `&map[time.Time]string{}` と指定しています。`time.Time` は文字列ではないため、JSONオブジェクトのキーとしては不正なGoのマップキー型です。
*   `err`: 期待されるエラーは `UnmarshalTypeError` です。これは、JSONオブジェクトのキーが文字列であるにもかかわらず、Goのターゲットマップのキー型が `string` ではないために発生する型ミスマッチを示します。

また、`TestUnmarshal` 関数内のエラーチェックロジックも微修正されています。

```diff
-		if err := dec.Decode(v.Interface()); !reflect.DeepEqual(err, tt.err) {
-			t.Errorf("#%d: %v want %v", i, err, tt.err)
-		} else if err != nil {
+		if err := dec.Decode(v.Interface()); !reflect.DeepEqual(err, tt.err) {
+			t.Errorf("#%d: %v, want %v", i, err, tt.err)
+			continue // エラーが期待と異なる場合でもテストを続行
+		} else if err != nil {
 			continue
 		}
```
`t.Errorf` のメッセージが微調整され、エラーが期待と異なる場合でも `continue` するように変更されています。これにより、テストがより堅牢になり、特定のエラーケースでテストが停止することなく、他のテストケースの実行を継続できるようになります。

これらの変更により、`encoding/json` パッケージは、不正なマップキー型が指定された場合にパニックする代わりに、予測可能で適切なエラーを返すようになり、ライブラリの堅牢性が向上しました。

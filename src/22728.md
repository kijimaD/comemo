# [インデックス 22728] ファイルの概要

`src/runtime/mgc.go`は、Goランタイムにおけるガベージコレクション（GC）の主要なロジックを実装しているファイルです。このファイルには、メモリ管理、GCサイクルのトリガー、ヒープ統計の維持に関する機能が含まれています。Goのメモリ管理戦略の中核をなす部分であり、ヒープの成長を監視し、適切なタイミングでGCを実行することで、メモリ使用量を効率的に管理します。

    runtime: make next_gc be heap size to trigger GC at

    In the STW collector, next_gc was both the heap size to trigger GC at
    as well as the goal heap size.

    Early in the concurrent collector's development, next_gc was the goal
    heap size, but was also used as the heap size to trigger GC at. This
    meant we always overshot the goal because of allocation during
    concurrent GC.

    Currently, next_gc is still the goal heap size, but we trigger
    concurrent GC at 7/8*GOGC heap growth. This complicates
    shouldtriggergc, but was necessary because of the incremental
    maintenance of next_gc.

    Now we simply compute next_gc for the next cycle during mark
    termination. Hence, it's now easy to take the simpler route and
    redefine next_gc as the heap size at which the next GC triggers. We
    can directly compute this with the 7/8 backoff during mark termination
    and shouldtriggergc can simply test if the live heap size has grown
    over the next_gc trigger.

    This will also simplify later changes once we start setting next_gc in
    more sophisticated ways.

## 変更の背景

このコミットは、Goランタイムのガベージコレクタ（GC）における`next_gc`変数の意味と計算方法の変更を目的としています。変更の背景には、GoのGCがStop-The-World（STW）方式から並行（Concurrent）方式へと進化する過程で生じた課題があります。

元々、GoのSTWコレクタでは、`next_gc`はGCをトリガーするヒープサイズであると同時に、GCが目指す目標ヒープサイズでもありました。しかし、並行コレクタの開発初期段階では、`next_gc`は引き続き目標ヒープサイズとして扱われましたが、GCのトリガーにも使用されていました。この設計では、並行GC中にアロケーションが発生するため、常に目標ヒープサイズを超過してしまうという問題がありました。

この問題を緩和するため、一時的に並行GCは`GOGC`で指定されたヒープ成長の7/8の時点でトリガーされるように変更されました。これにより、`shouldtriggergc`関数のロジックが複雑化し、`next_gc`の段階的なメンテナンスが必要となりました。

このコミットの時点で、`next_gc`は次のGCサイクルでマーク終了時に単純に計算されるようになりました。この変更により、`next_gc`を「次のGCがトリガーされるヒープサイズ」として再定義することが容易になりました。これにより、マーク終了時に7/8のバックオフを考慮して`next_gc`を直接計算できるようになり、`shouldtriggergc`は単にライブヒープサイズが`next_gc`トリガーを超えたかどうかをテストするだけのシンプルなロジックに変わりました。

この変更は、GCトリガーロジックを簡素化するだけでなく、将来的に`next_gc`をより洗練された方法で設定するための基盤を築くものです。

## 前提知識の解説

このコミットの変更内容を理解するためには、Goのガベージコレクションに関するいくつかの基本的な概念と用語を理解しておく必要があります。

*   **ガベージコレクション (GC)**: プログラムが動的に確保したメモリのうち、もはや使用されていない（参照されていない）領域を自動的に解放するプロセスです。これにより、メモリリークを防ぎ、開発者が手動でメモリ管理を行う負担を軽減します。
*   **Stop-The-World (STW) コレクタ**: GCの一種で、GCが実行されている間、アプリケーションのすべてのゴルーチン（軽量スレッド）を一時停止させる方式です。これにより、GCは一貫性のあるメモリ状態を安全に操作できますが、アプリケーションの応答性が一時的に低下する「ポーズ時間」が発生します。Goの初期のGCはSTW方式でした。
*   **並行 (Concurrent) コレクタ**: GCの一種で、GCの一部または大部分のフェーズをアプリケーションのゴルーチンと並行して実行する方式です。これにより、STWコレクタに比べてポーズ時間を大幅に短縮できます。Goの現代のGCは並行コレクタであり、ポーズ時間の短縮に重点を置いています。
*   `next_gc`: Goランタイムのメモリ統計（`memstats`）に含まれる変数で、次のGCサイクルがトリガーされるべきヒープサイズ、またはGCが目指す目標ヒープサイズを示します。このコミットの核心は、この変数の意味が「目標」から「トリガー」へと変更された点です。
*   `heap_live`: 現在のライブヒープサイズ、つまりアプリケーションが実際に使用しているメモリの量を示します。
*   `gcpercent`: 環境変数`GOGC`によって設定される値で、GCの動作を制御します。デフォルト値は100です。これは、前回のGC終了時のライブヒープサイズに対して、ヒープが`gcpercent`パーセント成長したら次のGCをトリガーするという意味です。例えば、`GOGC=100`の場合、ライブヒープサイズが前回のGC終了時の2倍になったら次のGCがトリガーされます。
*   `shouldtriggergc()`: Goランタイム内の関数で、現在のメモリ使用状況に基づいてGCをトリガーすべきかどうかを判断します。この関数は、アロケーションが発生するたびに呼び出され、GCの必要性を評価します。
*   **マーク終了 (Mark Termination)**: Goの並行GCにおけるフェーズの一つです。並行マークフェーズが完了した後、GCはマーク終了フェーズに入ります。このフェーズでは、マークフェーズで収集された情報を最終処理し、次のGCサイクルの準備を行います。このコミットでは、`next_gc`の計算がこのフェーズで行われるようになりました。
*   **7/8ths バックオフ**: 並行GC中にアロケーションが発生し続けることを考慮し、`gcpercent`で許容されるヒープ成長の全量ではなく、その7/8の時点でGCをトリガーするメカニズムです。これにより、GCが完了する前にヒープが過度に成長し、メモリ不足に陥るリスクを軽減します。

これらの概念を理解することで、`next_gc`の再定義がGoのGCの効率性と予測可能性にどのように貢献するかが明確になります。

## 技術的詳細

このコミットの技術的な核心は、`memstats.next_gc`変数のセマンティクス（意味）の変更と、それに伴うGCトリガーロジックの簡素化です。

**`next_gc`のセマンティクス変更:**
以前は、`next_gc`は「次のGCが目指す目標ヒープサイズ」として機能していました。しかし、並行GCの特性上、GCが実行されている間もアプリケーションはメモリをアロケーションし続けるため、目標ヒープサイズを設定しても、GCが完了するまでにその目標を「オーバーシュート」してしまう問題がありました。これを解決するため、このコミットでは`next_gc`を「次のGCがトリガーされるヒープサイズ」として再定義しました。

**GCトリガーロジックの簡素化:**
このセマンティクス変更により、`shouldtriggergc()`関数のロジックが大幅に簡素化されました。変更前は、`triggerratio`（8に設定されていた）と`memstats.next_gc`、`memstats.heap_live`を用いた複雑な計算式でGCのトリガーを判断していました。これは、`next_gc`が目標ヒープサイズでありながら、7/8の成長でトリガーするという矛盾を解消するためのものでした。

変更後は、`shouldtriggergc()`は単に`memstats.heap_live`（現在のライブヒープサイズ）が`memstats.next_gc`（次のGCトリガーヒープサイズ）以上になったかどうかをチェックするだけになりました。これにより、GCトリガーの条件が直感的で理解しやすくなりました。

**`next_gc`の計算場所と方法の変更:**
`next_gc`の計算は、GCの「マーク終了（mark termination）」フェーズで行われるようになりました。このフェーズは、GCのマークフェーズが完了し、次のGCサイクルの準備が行われるタイミングです。

新しい`next_gc`の計算式は以下の通りです。
`memstats.next_gc = memstats.heap_live + (memstats.heap_live * uint64(gcpercent) / 100) * 7 / 8`

この式は、現在のライブヒープサイズ（`memstats.heap_live`）に、`gcpercent`で許容されるヒープ成長の7/8を加算した値を`next_gc`として設定します。具体的には、`memstats.heap_live * uint64(gcpercent) / 100`が`gcpercent`で許容されるヒープの最大成長量を示し、その7/8の時点でGCをトリガーするように`next_gc`を設定します。この7/8という係数は、並行GC中に発生するアロケーションを考慮し、GCが完了する前にヒープが過度に成長するのを防ぐための「バックオフ」メカニズムです。

この変更により、`next_gc`は常に次のGCが開始されるべき具体的なヒープサイズを示すようになり、GCのトリガーがより予測可能かつ効率的になりました。また、将来的にGCのトリガー戦略をより洗練されたものにするための柔軟性も提供します。

## コアとなるコードの解説

### `triggerratio`変数の削除

*   **変更前**: `triggerratio`は、並行GC中にミューテータ（アプリケーションのゴルーチン）がアロケーションを行うための十分なメモリを確保するためのスキームの一部として導入されました。具体的には、`1/triggerratio`のメモリが利用可能になったときにGCをトリガーするという意図がありました。
*   **変更後**: `next_gc`のセマンティクスが「GCトリガーヒープサイズ」に再定義されたことで、この`triggerratio`は不要になりました。GCトリガーのロジックが`next_gc`の直接的な比較に簡素化されたため、この補助的な比率は役割を終えました。これにより、コードの複雑性が軽減され、GCトリガーの仕組みがより明確になりました。

### `shouldtriggergc()`関数の条件式の変更

*   **変更前**: `return triggerratio*(int64(memstats.next_gc)-int64(memstats.heap_live)) <= int64(memstats.next_gc) && atomicloaduint(&bggc.working) == 0`
    この式は、`triggerratio`と`next_gc`（目標ヒープサイズ）、`heap_live`（現在のライブヒープサイズ）を組み合わせて、GCをトリガーすべきかどうかを判断していました。これは、`next_gc`が目標値であるにもかかわらず、並行アロケーションを考慮して早めにトリガーする必要があったため、複雑な計算が必要でした。
*   **変更後**: `return memstats.heap_live >= memstats.next_gc && atomicloaduint(&bggc.working) == 0`
    `next_gc`が「GCトリガーヒープサイズ」として再定義されたため、GCをトリガーする条件は非常にシンプルになりました。現在のライブヒープサイズ（`memstats.heap_live`）が、次のGCがトリガーされるべきヒープサイズ（`memstats.next_gc`）以上になったらGCをトリガーするという、直感的で直接的な比較になりました。`atomicloaduint(&bggc.working) == 0`は、GCがすでに動作中でないことを確認する条件であり、これは変更されていません。

### `gcMark()`関数内での`memstats.next_gc`の計算ロジックの変更

*   **変更前**: `memstats.next_gc = memstats.heap_live + memstats.heap_live*uint64(gcpercent)/100`
    この計算式では、`next_gc`は現在のライブヒープサイズに`gcpercent`で許容される成長量を単純に加算した値として設定されていました。これは、`next_gc`が目標ヒープサイズであった頃の計算方法です。
*   **変更後**: `memstats.next_gc = memstats.heap_live + (memstats.heap_live*uint64(gcpercent)/100)*7/8`
    新しい計算式では、`next_gc`は現在のライブヒープサイズに、`gcpercent`で許容されるヒープ成長量の7/8を加算した値として設定されます。
    *   `memstats.heap_live*uint64(gcpercent)/100`：これは、`gcpercent`に基づいて許容されるヒープの最大成長量を示します。
    *   `*7/8`：この係数は、並行GC中にミューテータがメモリをアロケーションし続けることを考慮した「バックオフ」です。これにより、GCが完了する前にヒープが過度に成長し、メモリ不足に陥ることを防ぎます。`next_gc`がトリガーポイントとして機能するため、この7/8の時点でトリガーすることで、GCが完了するまでの間に十分な余裕を持たせることができます。
*   **コメントの更新**: `// compute next_gc`という一般的なコメントから、`// Trigger the next GC cycle when the allocated heap has // reached 7/8ths of the growth allowed by gcpercent.`という具体的な説明に更新されました。これは、`next_gc`の新しい役割を明確に示しています。

これらの変更により、GoのGCはより予測可能で効率的なトリガーメカニズムを持つようになり、並行GCの特性に合わせた適切なヒープ管理が可能になりました。

## 変更の背景

このコミットは、Goランタイムのガベージコレクタ（GC）における`next_gc`変数の意味と計算方法の変更を目的としています。変更の背景には、GoのGCがStop-The-World（STW）方式から並行（Concurrent）方式へと進化する過程で生じた課題があります。

元々、GoのSTWコレクタでは、`next_gc`はGCをトリガーするヒープサイズであると同時に、GCが目指す目標ヒープサイズでもありました。しかし、並行コレクタの開発初期段階では、`next_gc`は引き続き目標ヒープサイズとして扱われましたが、GCのトリガーにも使用されていました。この設計では、並行GC中にアロケーションが発生するため、常に目標ヒープサイズを超過してしまうという問題がありました。

この問題を緩和するため、一時的に並行GCは`GOGC`で指定されたヒープ成長の7/8の時点でトリガーされるように変更されました。これにより、`shouldtriggergc`関数のロジックが複雑化し、`next_gc`の段階的なメンテナンスが必要となりました。

このコミットの時点で、`next_gc`は次のGCサイクルでマーク終了時に単純に計算されるようになりました。この変更により、`next_gc`を「次のGCがトリガーされるヒープサイズ」として再定義することが容易になりました。これにより、マーク終了時に7/8のバックオフを考慮して`next_gc`を直接計算できるようになり、`shouldtriggergc`は単にライブヒープサイズが`next_gc`トリガーを超えたかどうかをテストするだけのシンプルなロジックに変わりました。

この変更は、GCトリガーロジックを簡素化するだけでなく、将来的に`next_gc`をより洗練された方法で設定するための基盤を築くものです。

## 前提知識の解説

このコミットの変更内容を理解するためには、Goのガベージコレクションに関するいくつかの基本的な概念と用語を理解しておく必要があります。

*   **ガベージコレクション (GC)**: プログラムが動的に確保したメモリのうち、もはや使用されていない（参照されていない）領域を自動的に解放するプロセスです。これにより、メモリリークを防ぎ、開発者が手動でメモリ管理を行う負担を軽減します。
*   **Stop-The-World (STW) コレクタ**: GCの一種で、GCが実行されている間、アプリケーションのすべてのゴルーチン（軽量スレッド）を一時停止させる方式です。これにより、GCは一貫性のあるメモリ状態を安全に操作できますが、アプリケーションの応答性が一時的に低下する「ポーズ時間」が発生します。Goの初期のGCはSTW方式でした。
*   **並行 (Concurrent) コレクタ**: GCの一種で、GCの一部または大部分のフェーズをアプリケーションのゴルーチンと並行して実行する方式です。これにより、STWコレクタに比べてポーズ時間を大幅に短縮できます。Goの現代のGCは並行コレクタであり、ポーズ時間の短縮に重点を置いています。
*   `next_gc`: Goランタイムのメモリ統計（`memstats`）に含まれる変数で、次のGCサイクルがトリガーされるべきヒープサイズ、またはGCが目指す目標ヒープサイズを示します。このコミットの核心は、この変数の意味が「目標」から「トリガー」へと変更された点です。
*   `heap_live`: 現在のライブヒープサイズ、つまりアプリケーションが実際に使用しているメモリの量を示します。
*   `gcpercent`: 環境変数`GOGC`によって設定される値で、GCの動作を制御します。デフォルト値は100です。これは、前回のGC終了時のライブヒープサイズに対して、ヒープが`gcpercent`パーセント成長したら次のGCをトリガーするという意味です。例えば、`GOGC=100`の場合、ライブヒープサイズが前回のGC終了時の2倍になったら次のGCがトリガーされます。
*   `shouldtriggergc()`: Goランタイム内の関数で、現在のメモリ使用状況に基づいてGCをトリガーすべきかどうかを判断します。この関数は、アロケーションが発生するたびに呼び出され、GCの必要性を評価します。
*   **マーク終了 (Mark Termination)**: Goの並行GCにおけるフェーズの一つです。並行マークフェーズが完了した後、GCはマーク終了フェーズに入ります。このフェーズでは、マークフェーズで収集された情報を最終処理し、次のGCサイクルの準備を行います。このコミットでは、`next_gc`の計算がこのフェーズで行われるようになりました。
*   **7/8ths バックオフ**: 並行GC中にアロケーションが発生し続けることを考慮し、`gcpercent`で許容されるヒープ成長の全量ではなく、その7/8の時点でGCをトリガーするメカニズムです。これにより、GCが完了する前にヒープが過度に成長し、メモリ不足に陥るリスクを軽減します。

これらの概念を理解することで、`next_gc`の再定義がGoのGCの効率性と予測可能性にどのように貢献するかが明確になります。

## 技術的詳細

このコミットの技術的な核心は、`memstats.next_gc`変数のセマンティクス（意味）の変更と、それに伴うGCトリガーロジックの簡素化です。

**`next_gc`のセマンティクス変更:**
以前は、`next_gc`は「次のGCが目指す目標ヒープサイズ」として機能していました。しかし、並行GCの特性上、GCが実行されている間もアプリケーションはメモリをアロケーションし続けるため、目標ヒープサイズを設定しても、GCが完了するまでにその目標を「オーバーシュート」してしまう問題がありました。これを解決するため、このコミットでは`next_gc`を「次のGCがトリガーされるヒープサイズ」として再定義しました。

**GCトリガーロジックの簡素化:**
このセマンティクス変更により、`shouldtriggergc()`関数のロジックが大幅に簡素化されました。変更前は、`triggerratio`（8に設定されていた）と`memstats.next_gc`、`memstats.heap_live`を用いた複雑な計算式でGCのトリガーを判断していました。これは、`next_gc`が目標ヒープサイズでありながら、7/8の成長でトリガーするという矛盾を解消するためのものでした。

変更後は、`shouldtriggergc()`は単に`memstats.heap_live`（現在のライブヒープサイズ）が`memstats.next_gc`（次のGCトリガーヒープサイズ）以上になったかどうかをチェックするだけになりました。これにより、GCトリガーの条件が直感的で理解しやすくなりました。

**`next_gc`の計算場所と方法の変更:**
`next_gc`の計算は、GCの「マーク終了（mark termination）」フェーズで行われるようになりました。このフェーズは、GCのマークフェーズが完了し、次のGCサイクルの準備が行われるタイミングです。

新しい`next_gc`の計算式は以下の通りです。
`memstats.next_gc = memstats.heap_live + (memstats.heap_live * uint64(gcpercent) / 100) * 7 / 8`

この式は、現在のライブヒープサイズ（`memstats.heap_live`）に、`gcpercent`で許容されるヒープ成長の7/8を加算した値を`next_gc`として設定します。具体的には、`memstats.heap_live * uint64(gcpercent) / 100`が`gcpercent`で許容されるヒープの最大成長量を示し、その7/8の時点でGCをトリガーするように`next_gc`を設定します。この7/8という係数は、並行GC中に発生するアロケーションを考慮し、GCが完了する前にヒープが過度に成長するのを防ぐための「バックオフ」メカニズムです。

この変更により、`next_gc`は常に次のGCが開始されるべき具体的なヒープサイズを示すようになり、GCのトリガーがより予測可能かつ効率的になりました。また、将来的にGCのトリガー戦略をより洗練されたものにするための柔軟性も提供します。

## コアとなるコードの解説

### `triggerratio`変数の削除

*   **変更前**: `triggerratio`は、並行GC中にミューテータ（アプリケーションのゴルーチン）がアロケーションを行うための十分なメモリを確保するためのスキームの一部として導入されました。具体的には、`1/triggerratio`のメモリが利用可能になったときにGCをトリガーするという意図がありました。
*   **変更後**: `next_gc`のセマンティクスが「GCトリガーヒープサイズ」に再定義されたことで、この`triggerratio`は不要になりました。GCトリガーのロジックが`next_gc`の直接的な比較に簡素化されたため、この補助的な比率は役割を終えました。これにより、コードの複雑性が軽減され、GCトリガーの仕組みがより明確になりました。

### `shouldtriggergc()`関数の条件式の変更

*   **変更前**: `return triggerratio*(int64(memstats.next_gc)-int64(memstats.heap_live)) <= int64(memstats.next_gc) && atomicloaduint(&bggc.working) == 0`
    この式は、`triggerratio`と`next_gc`（目標ヒープサイズ）、`heap_live`（現在のライブヒープサイズ）を組み合わせて、GCをトリガーすべきかどうかを判断していました。これは、`next_gc`が目標値であるにもかかわらず、並行アロケーションを考慮して早めにトリガーする必要があったため、複雑な計算が必要でした。
*   **変更後**: `return memstats.heap_live >= memstats.next_gc && atomicloaduint(&bggc.working) == 0`
    `next_gc`が「GCトリガーヒープサイズ」として再定義されたため、GCをトリガーする条件は非常にシンプルになりました。現在のライブヒープサイズ（`memstats.heap_live`）が、次のGCがトリガーされるべきヒープサイズ（`memstats.next_gc`）以上になったらGCをトリガーするという、直感的で直接的な比較になりました。`atomicloaduint(&bggc.working) == 0`は、GCがすでに動作中でないことを確認する条件であり、これは変更されていません。

### `gcMark()`関数内での`memstats.next_gc`の計算ロジックの変更

*   **変更前**: `memstats.next_gc = memstats.heap_live + memstats.heap_live*uint64(gcpercent)/100`
    この計算式では、`next_gc`は現在のライブヒープサイズに`gcpercent`で許容される成長量を単純に加算した値として設定されていました。これは、`next_gc`が目標ヒープサイズであった頃の計算方法です。
*   **変更後**: `memstats.next_gc = memstats.heap_live + (memstats.heap_live*uint64(gcpercent)/100)*7/8`
    新しい計算式では、`next_gc`は現在のライブヒープサイズに、`gcpercent`で許容されるヒープ成長量の7/8を加算した値として設定されます。
    *   `memstats.heap_live*uint64(gcpercent)/100`：これは、`gcpercent`に基づいて許容されるヒープの最大成長量を示します。
    *   `*7/8`：この係数は、並行GC中にミューテータがメモリをアロケーションし続けることを考慮した「バックオフ」です。これにより、GCが完了する前にヒープが過度に成長し、メモリ不足に陥ることを防ぎます。`next_gc`がトリガーポイントとして機能するため、この7/8の時点でトリガーすることで、GCが完了するまでの間に十分な余裕を持たせることができます。
*   **コメントの更新**: `// compute next_gc`という一般的なコメントから、`// Trigger the next GC cycle when the allocated heap has // reached 7/8ths of the growth allowed by gcpercent.`という具体的な説明に更新されました。これは、`next_gc`の新しい役割を明確に示しています。

これらの変更により、GoのGCはより予測可能で効率的なトリガーメカニズムを持つようになり、並行GCの特性に合わせた適切なヒープ管理が可能になりました。

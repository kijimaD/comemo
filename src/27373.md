# [インデックス 27373] ファイルの概要

このコミットは、Go言語の標準ライブラリ`net/http/httptest`パッケージに、HTTPハンドラのテストを容易にするための新しいヘルパー関数`NewRequest`を追加します。これにより、テストコード内でHTTPサーバーへの受信リクエストをシミュレートする`*http.Request`オブジェクトを簡単に生成できるようになります。具体的には、`httptest.go`という新しいファイルに`NewRequest`関数が実装され、その動作を検証するためのテストコードが`httptest_test.go`に新規追加されています。また、既存の`recorder.go`からはパッケージコメントが削除され、新しく作成された`httptest.go`に移動されています。

## 変更の背景

Go言語でHTTPハンドラ（`http.Handler`インターフェースを実装する型）をテストする際、通常は`httptest.NewRecorder`と`http.NewRequest`を組み合わせて使用します。しかし、`http.NewRequest`は主にHTTPクライアントが送信する「発信リクエスト」を構築するために設計されており、サーバーが受信する「着信リクエスト」をシミュレートするには、いくつかのフィールドを手動で設定する必要がありました。例えば、`RemoteAddr`や`TLS`接続の状態など、サーバー側で利用される情報が`http.NewRequest`だけでは適切に設定されませんでした。

このコミットは、このギャップを埋めることを目的としています。コミットメッセージにある`Fixes #14199`は、この問題に対する以前の議論や要望を示唆しています。関連するGoのIssue #26083の議論によると、`#14199`は`http.ReadRequest`が発信リクエスト向けであるという意図に関連しており、テスト時に着信リクエストを簡単に作成できるヘルパーの必要性が認識されていました。

`NewRequest`ヘルパーの導入により、開発者はより少ないコードで、より現実的な受信HTTPリクエストオブジェクトを生成できるようになり、HTTPハンドラの単体テストの記述が大幅に簡素化されます。これにより、テストの可読性と保守性が向上し、GoのHTTPアプリケーションのテスト容易性が高まります。

## 前提知識の解説

このコミットの理解には、以下のGo言語の標準ライブラリとHTTPプロトコルに関する知識が役立ちます。

-   **`net/http`パッケージ**: Go言語におけるHTTPクライアントとサーバーの実装を提供するコアパッケージです。HTTPリクエスト、レスポンス、ハンドラなどの基本的な型と機能が含まれています。
-   **`http.Request`構造体**: HTTPリクエストのすべての側面（メソッド、URL、ヘッダー、ボディ、プロトコルバージョン、リモートアドレスなど）をカプセル化するGoの構造体です。サーバーが受信するリクエストとクライアントが送信するリクエストの両方を表します。
-   **`http.Handler`インターフェース**: `ServeHTTP(ResponseWriter, *Request)`メソッドを定義するインターフェースです。このインターフェースを実装する型は、HTTPリクエストを処理するハンドラとして機能します。GoのHTTPサーバーは、このハンドラを呼び出してリクエストを処理します。
-   **`net/http/httptest`パッケージ**: `net/http`パッケージを使用するコードのテストを支援するために設計されたユーティリティパッケージです。例えば、`httptest.ResponseRecorder`は、`http.ResponseWriter`インターフェースを実装し、HTTPハンドラからのレスポンスを記録するために使用されます。
-   **RFC 7230 "request-target"**: HTTP/1.1メッセージ構文を定義するRFC（Request for Comments）ドキュメントの一部です。`request-target`は、リクエストの対象となるリソースを識別する部分で、パス形式（例: `/path/to/resource`）や絶対URI形式（例: `http://example.com/path`）などがあります。
-   **`io.Reader`インターフェース**: Goの標準ライブラリ`io`パッケージで定義されているインターフェースで、`Read(p []byte) (n int, err error)`メソッドを持ちます。これは、バイトストリームからデータを読み出すための一般的な抽象化を提供し、HTTPリクエストボディのデータソースとしてよく使用されます。
-   **`io.ReadCloser`インターフェース**: `io.Reader`と`io.Closer`（`Close() error`メソッドを持つ）の両方を組み合わせたインターフェースです。リソースを読み出し、かつ閉じることができるオブジェクトを表します。HTTPリクエストボディは通常、このインターフェースとして扱われます。
-   **`ioutil.NopCloser`**: `io/ioutil`パッケージ（Go 1.16以降は`io`パッケージに移動）のヘルパー関数で、任意の`io.Reader`を`io.ReadCloser`にラップします。この`ReadCloser`の`Close`メソッドは何もせず、常に`nil`を返します。これは、ボディが`io.Reader`として提供された場合に、`http.Request.Body`フィールドが`io.ReadCloser`を期待するため、その要件を満たすために使用されます。
-   **`crypto/tls`パッケージ**: TLS (Transport Layer Security) プロトコルを実装するGoの標準ライブラリです。HTTPSリクエストでは、このパッケージの`tls.ConnectionState`構造体がTLS接続の状態を表します。
-   **`panic`とテスト**: Goのテストでは、予期せぬエラーや無効な状態が発生した場合に`panic`を使用することが許容される場合があります。これは、テストが失敗したことを明確に示し、テストスイートの実行を停止させるためです。

## 技術的詳細

このコミットで追加された`httptest.NewRequest`関数は、`http.Handler`のテスト用に特別に調整された`*http.Request`オブジェクトを生成します。その実装は、いくつかの重要な側面を考慮しています。

1.  **リクエストの初期パース**:
    `NewRequest`は、まず`method`と`target`引数を使用して、`"METHOD TARGET HTTP/1.0\r\n\r\n"`という形式のダミーのHTTPリクエストラインを作成します。この文字列は`strings.NewReader`と`bufio.NewReader`を介して`http.ReadRequest`関数に渡されます。`http.ReadRequest`は、実際のネットワークから読み込むかのようにリクエストをパースし、基本的な`*http.Request`構造体を構築します。このアプローチにより、URLのパースやヘッダーの初期化など、`http.Request`の多くのフィールドが`net/http`パッケージの内部ロジックに従って適切に設定されます。
    もし`http.ReadRequest`がエラーを返した場合、`NewRequest`は`panic`します。これはテストヘルパー関数としての性質上、無効な引数で呼び出された場合はテストを即座に失敗させるのが適切であるという設計思想に基づいています。

2.  **プロトコルバージョンの調整**:
    `http.ReadRequest`はHTTP/1.0形式のリクエストラインをパースするため、生成された`*http.Request`オブジェクトの`Proto`、`ProtoMajor`、`ProtoMinor`フィールドはHTTP/1.0を示します。しかし、現代のHTTPサーバーは通常HTTP/1.1を処理するため、`NewRequest`はこれらのフィールドを`"HTTP/1.1"`、`1`、`1`にそれぞれ上書きします。また、`req.Close`は`false`に設定され、接続が持続的であることをシミュレートします。

3.  **リクエストボディの処理**:
    `body`引数（`io.Reader`型）が`nil`でない場合、`NewRequest`はリクエストボディを処理します。
    -   `*bytes.Buffer`、`*bytes.Reader`、`*strings.Reader`のいずれかの型である場合、その`Len()`メソッドから`ContentLength`を正確に取得し、`req.ContentLength`フィールドに設定します。これにより、サーバーがボディの長さを事前に知ることができます。
    -   それ以外の`io.Reader`型の場合、`ContentLength`は`-1`に設定されます。これは、ボディの長さが不明であることを示し、サーバーはチャンク転送エンコーディングなどを期待する可能性があります。
    -   `body`が既に`io.ReadCloser`インターフェースを実装している場合（例: `os.File`）、それは直接`req.Body`に設定されます。
    -   そうでない場合、`ioutil.NopCloser(body)`を使用して`body`を`io.ReadCloser`にラップし、`req.Body`に設定します。これにより、`req.Body`が常に`Close`メソッドを持つことが保証されますが、`NopCloser`の`Close`は実質的に何もしません。

4.  **リモートアドレスとホストの設定**:
    -   `req.RemoteAddr`フィールドは、テスト目的で`"192.0.2.1:1234"`という固定値に設定されます。`192.0.2.0/24`はRFC 5737で「TEST-NET」として予約されており、ドキュメントや例で使用するためのIPアドレス範囲です。これにより、テストの再現性が保証され、実際のネットワークアドレスに依存しないようになります。
    -   `req.Host`フィールドは、`target`が絶対URLの場合、そのURLのホスト名が使用されます。`req.Host`が空の場合（`target`がパス形式の場合など）、デフォルトで`"example.com"`が設定されます。

5.  **HTTPSリクエストのシミュレーション**:
    `target`が`"https://"`で始まる場合、`NewRequest`は`req.TLS`フィールドにダミーの`*tls.ConnectionState`構造体を設定します。これにより、ハンドラがHTTPSリクエストを処理しているかのように振る舞うことをテストできます。設定される`ConnectionState`には、`Version: tls.VersionTLS12`、`HandshakeComplete: true`、`ServerName: req.Host`が含まれます。

## コアとなるコードの解説

### `src/net/http/httptest/httptest.go` の `NewRequest` 関数

```go
func NewRequest(method, target string, body io.Reader) *http.Request {
	if method == "" {
		method = "GET"
	}
	// HTTP/1.0形式のダミーリクエストラインを作成し、http.ReadRequestでパース
	req, err := http.ReadRequest(bufio.NewReader(strings.NewReader(method + " " + target + " HTTP/1.0\r\n\r\n")))
	if err != nil {
		panic("invalid NewRequest arguments; " + err.Error()) // テストヘルパーのためpanic
	}

	// プロトコルバージョンをHTTP/1.1に修正
	req.Proto = "HTTP/1.1"
	req.ProtoMajor = 1
	req.ProtoMinor = 1
	req.Close = false // 接続は持続的と仮定

	if body != nil {
		switch v := body.(type) {
		case *bytes.Buffer:
			req.ContentLength = int64(v.Len())
		case *bytes.Reader:
			req.ContentLength = int64(v.Len())
		case *strings.Reader:
			req.ContentLength = int64(v.Len())
		default:
			req.ContentLength = -1 // 長さ不明
		}
		if rc, ok := body.(io.ReadCloser); ok {
			req.Body = rc
		} else {
			req.Body = ioutil.NopCloser(body) // io.Readerをio.ReadCloserにラップ
		}
	}

	// テスト用のリモートアドレスを設定 (RFC 5737 TEST-NET)
	req.RemoteAddr = "192.0.2.1:1234"

	if req.Host == "" {
		req.Host = "example.com" // デフォルトホスト
	}

	// HTTPSリクエストの場合、TLS接続状態をシミュレート
	if strings.HasPrefix(target, "https://") {
		req.TLS = &tls.ConnectionState{
			Version:           tls.VersionTLS12,
			HandshakeComplete: true,
			ServerName:        req.Host,
		}
	}

	return req
}
```
この関数は、HTTPハンドラのテストに必要な`*http.Request`オブジェクトを生成するための中心的なロジックを含んでいます。特に注目すべきは、`http.ReadRequest`を利用してリクエストの基本的なパースを行うことで、URLのエンコーディングやパスの正規化といった複雑な処理を`net/http`パッケージに任せている点です。その後、テストシナリオに合わせてプロトコルバージョン、ボディの長さ、リモートアドレス、ホスト、TLS接続状態などのフィールドを調整しています。

### `src/net/http/httptest/httptest_test.go` の `TestNewRequest` 関数

このテストファイルでは、`NewRequest`関数の様々な挙動を検証するための構造化されたテストスイートが定義されています。`tests`という名前の構造体スライスを使用し、各テストケースで`method`、`uri`、`body`の入力と、期待される`*http.Request`オブジェクトの状態（`want`）およびボディの内容（`wantBody`）を定義しています。

例えば、以下のテストケースは、空のメソッドが`GET`として扱われ、パス形式のURIが正しくパースされることを検証しています。

```go
		0: {
			method: "",
			uri:    "/",
			body:   nil,
			want: &http.Request{
				Method:     "GET",
				Host:       "example.com",
				URL:        &url.URL{Path: "/"},
				Header:     http.Header{},
				Proto:      "HTTP/1.1",
				ProtoMajor: 1,
				ProtoMinor: 1,
				RemoteAddr: "192.0.2.1:1234",
				RequestURI: "/",
			},
			wantBody: "",
		},
```

また、HTTPSリクエストのテストケースでは、`req.TLS`フィールドが適切に設定されることを確認しています。

```go
		2: {
			method: "GET",
			uri:    "https://foo.com/path/",
			body:   nil,
			want: &http.Request{
				Method: "GET",
				Host:   "foo.com",
				URL: &url.URL{
					Scheme: "https",
					Path:   "/path/",
					Host:   "foo.com",
				},
				Header:     http.Header{},
				Proto:      "HTTP/1.1",
				ProtoMajor: 1,
				ProtoMinor: 1,
				RemoteAddr: "192.0.2.1:1234",
				RequestURI: "https://foo.com/path/",
				TLS: &tls.ConnectionState{ // TLSフィールドが設定される
					Version:           tls.VersionTLS12,
					HandshakeComplete: true,
					ServerName:        "foo.com",
				},
			},
			wantBody: "",
		},
```

テストの実行時には、`NewRequest`で生成された`*http.Request`オブジェクトと期待される`*http.Request`オブジェクトの各フィールド（特に`URL`、`Header`、`TLS`）が`reflect.DeepEqual`を用いて厳密に比較されます。これにより、`NewRequest`が様々な入力に対して正確な`*http.Request`オブジェクトを生成することを保証しています。

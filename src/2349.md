## 前提知識の解説

### 1. Yacc/Bisonと文法定義ファイル (`.y`)

`go.y`ファイルは、Yacc（Yet Another Compiler Compiler）またはBison（YaccのGNU版）というツールで使用される文法定義ファイルです。これらのツールは、BNF（Backus-Naur Form）に似た形式で記述された文法規則を読み込み、その文法に従って入力（ソースコード）を解析するパーサー（構文解析器）を自動生成します。

- **文法規則**: `go.y`には、Go言語の各構文要素（例: `if`文、`switch`文、`select`文、式など）がどのように構成されるかを定義する規則が記述されています。
- **トークン**: `LFOR`, `LSWITCH`, `LIF`, `LCASE`などは、字句解析器（lexer）によって識別されるキーワードや記号などの「トークン」を表します。
- **非終端記号**: `complex_stmt`, `if_stmt`, `switch_stmt`などは、複数のトークンや他の非終端記号から構成される文法要素を表す「非終端記号」です。
- **アクション**: 各文法規則には、その規則が適用されたときに実行されるC言語のコードブロック（アクション）が関連付けられています。これにより、構文木（AST）の構築や意味解析の初期段階が行われます。

### 2. 抽象構文木 (AST)

ASTは、ソースコードの構文構造を木構造で表現したものです。コンパイラは、ソースコードを字句解析してトークンの列にし、次に構文解析してASTを構築します。ASTは、プログラムの意味を理解し、最適化やコード生成を行うための基盤となります。

- **ノード**: ASTの各要素は「ノード」と呼ばれ、演算子、変数、関数呼び出し、制御フロー文などを表します。
- **`Node *`**: 変更箇所に見られる`Node *`は、ASTのノードを指すポインタであり、コンパイラ内部でASTを操作するために使用されます。

### 3. コンパイラのフェーズ

コンパイラは通常、以下のフェーズで動作します。

1.  **字句解析 (Lexical Analysis)**: ソースコードをトークンのストリームに変換します。
2.  **構文解析 (Syntactic Analysis)**: トークンのストリームを解析し、ASTを構築します（`go.y`が関与）。
3.  **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、名前解決、エラー検出など、プログラムの意味に関するチェックを行います（`walk.c`が関与）。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTから、機械語に近いがまだ特定のCPUに依存しない中間表現を生成します。
5.  **最適化 (Optimization)**: 中間コードを最適化し、実行効率を高めます。
6.  **コード生成 (Code Generation)**: 最適化された中間コードから、ターゲットCPUの機械語を生成します。

このコミットは、主に構文解析（`go.y`）と意味解析（`swt.c`, `walk.c`）のフェーズに影響を与えています。

### 4. Go言語の制御フロー文

-   **`if`文**: 条件に基づいてコードブロックを実行します。
-   **`switch`文**: 式の値に基づいて複数の`case`の中から一つを選択して実行します。`fallthrough`キーワードがない限り、`case`ブロックの実行後には自動的に`switch`文を抜けます。
-   **`select`文**: 複数の通信操作（チャネルの送受信）の中から準備ができたものを一つ選択して実行します。`select`文はGoの並行処理において非常に重要な役割を果たします。

## 技術的詳細

### `src/cmd/gc/go.y` の変更点

これらの変更は、Go言語の文法が進化する中で、制御フロー文の構文解析をより堅牢で一貫性のあるものにするためのリファクタリングであると考えられます。

## コアとなるコードの解説

### `src/cmd/gc/go.y` の解説

`go.y`の変更は、Go言語の構文解析器が`if`、`switch`、`select`文をどのように解釈するかを根本的に再定義しています。

-   **`complex_stmt`の抽象化**: 以前は`complex_stmt`が各制御フロー文のキーワード（`LFOR`, `LSWITCH`など）を直接含んでいましたが、変更後は`for_stmt`, `switch_stmt`, `select_stmt`, `if_stmt`というより具体的な非終端記号に処理を委譲しています。これにより、文法規則がよりクリーンになり、各文の定義が独立して管理されるようになりました。これは、文法が複雑になるにつれて、保守性と拡張性を高めるための一般的なプラクティスです。
-   **`if_stmt`、`switch_stmt`、`select_stmt`の構造化**: 各文が自身のキーワード（`LIF`, `LSWITCH`, `LSELECT`）と、それに続くヘッダー（`if_header`）および本体（`compound_stmt`または`switch_body`）を持つように明確に定義されました。特に、`markdcl()`と`popdcl()`の呼び出しが各文の開始と終了に配置されたことで、これらの文がそれぞれ独立したスコープを持つことが文法レベルで保証されるようになりました。これは、変数宣言の有効範囲を正確に管理するために不可欠です。
-   **`switch_body`と`caseblock`の導入**: `switch`文と`select`文の本体を構成する`case`ブロックの構造を共通化するために、`switch_body`と`caseblock`という新しい非終端記号が導入されました。これにより、`case`のリスト（`ocaseblock_list`）が`switch_body`内で処理され、各`caseblock`が`case`キーワードとそれに続くステートメントリスト（`ostmt_list`）を持つことが明確になりました。この共通化は、コードの重複を減らし、将来的な変更を容易にします。`nod(OEMPTY, N, N)`は、空の`switch`または`select`本体を表現するためのノードです。

これらの変更は、Go言語の制御フロー文の構文解析をより堅牢にし、コンパイラがこれらの構造をより正確にASTに変換できるようにするためのものです。

### `src/cmd/gc/swt.c` の解説

`swt.c`の`casebody`関数は、`switch`文の`case`ブロックを意味解析し、中間表現に変換する役割を担っています。

-   **`goto`から`for`への移行**: 最も顕著な変更は、`case`ブロックの反復処理に`goto`文を使用していた古いスタイルが、より現代的で読みやすい`for`ループに置き換えられたことです。これにより、コードのフローが直線的になり、理解しやすくなりました。
-   **`OXCASE`から`OCASE`への変換とエラーチェック**: `for`ループ内で、各ノードが`OXCASE`（構文解析器が生成した一時的な`case`ノード）であることを確認し、`OCASE`（意味解析後の最終的な`case`ノード）に変換しています。`OXCASE`でない場合は`fatal`エラーを発生させることで、不正なAST構造に対する堅牢性が向上しています。
-   **`default`ケースの処理**: `case`の式が`N`（nil）である場合を`default`ケースとして扱い、複数の`default`ケースが存在しないことを`yyerror`でチェックしています。
-   **多値`case`の展開**: `case`が複数の値を指定している場合（例: `case 1, 2, 3:`）、これらを個別の`OCASE`ノードに展開するロジックが引き続き存在します。
-   **`case`本体のステートメント処理**: `n->nbody`から`case`ブロック内のステートメントリストを取得し、`stat`リストに追加しています。これにより、`case`ブロック内の実際のコードが正しく処理されるようになります。
-   **`fallthrough`の処理**: `os != N && os->op == OXFALL`のチェックにより、`fallthrough`キーワードが正しく処理されるようにしています。`fallthrough`がない場合は、`OBREAK`ノードを追加して`case`ブロックの実行後に`switch`文を抜けるようにします。

これらの変更は、`switch`文の`case`ブロックのセマンティクスをより正確に実装し、特に`fallthrough`の挙動や`default`ケースの処理を堅牢にするためのものです。

### `src/cmd/gc/walk.c` の解説

`walk.c`の`walkselect`関数は、`select`文の意味解析と中間表現への変換を行います。

-   **空の`select`文の検出**: `select`文の最初のケースを処理する前に、`select`文が空であるかどうか（`n == N || n->op == OEMPTY`）をチェックし、空であれば`yyerror`でエラーを報告して早期に処理を終了します。これは、無効な`select`文に対するコンパイラの応答性を向上させます。
-   **`select`ケースの`OXCASE`チェック**: `switch`文と同様に、`select`文の各ケースが`OXCASE`であることを確認し、そうでない場合は`fatal`エラーを発生させることで、`select`文のケース処理の堅牢性を高めています。
-   **`case x := <-ch:`形式の変換の改善**: `case`が代入を伴う受信操作（`OAS`）である場合、`a = recv(chan)`という構文を`recv(a, chan)`という内部表現に変換するロジックが引き続き存在します。
    -   特に重要なのは、`if(n->ninit != N && n->ninit->op == ODCL)`のブロックです。これは、`case x := foo:`のような形式で変数が宣言されている場合、その変数の宣言（`ODCL`）を一時変数（`!tmpselect!`）に置き換え、実際の代入（`OAS`）を`select`文がこのブランチを選択した後に実行されるように遅延させるものです。これにより、変数がヒープに割り当てられる必要がある場合でも、`select`文が実際にそのケースを選択するまで割り当てを遅らせることができ、メモリ効率が向上する可能性があります。
-   **`select`ケース本体の処理**: `for(n1 = listfirst(&iter1, &n->nbody); n1 != N; n1 = listnext(&iter1))`ループにより、`select`ケースの本体（`n->nbody`）に含まれるすべてのステートメントを`nbod`リストに集めます。その後、`nbod`リストの最後に`OBREAK`ノードを追加し、`oc->nbody = rev(nbod)`で逆順にして`select`ケースの本体として設定します。これにより、各`select`ケースが実行された後に`select`文全体を抜けるというGoのセマンティクスが正しく実装されます。

これらの変更は、`select`文の複雑なセマンティクス、特に変数宣言と代入、そしてケース本体の実行フローを正確に処理するために不可欠です。

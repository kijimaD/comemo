## 変更の背景

Go言語は、その強力な並行処理モデルとシンプルな構文により、多くの開発者に利用されています。しかし、既存のC/C++ベースのシステムにGoの機能を組み込みたいというニーズも存在します。Go 1.5（2015年8月リリース）で導入された `-buildmode=c-shared` オプションは、GoのパッケージをC言語の共有ライブラリ（Linuxでは `.so`、Windowsでは `.dll`、macOSでは `.dylib`）としてコンパイルすることを可能にし、この相互運用性のギャップを埋める重要な機能でした。

Goには主に2つのコンパイラ実装があります。一つは公式の `gc` (Go Compiler) で、もう一つはGCCのフロントエンドとして実装された `gccgo` です。`gc` はGo言語の最新機能を迅速に取り入れ、高速なコンパイルを特徴とします。一方、`gccgo` はGCCの広範な最適化機能と多様なアーキテクチャサポートを享受できる利点があります。

このコミットが作成された2015年4月時点では、`gc` コンパイラにおける `-buildmode=c-shared` のサポートが進められていましたが、`gccgo` における同機能のサポートはまだ不十分でした。共有ライブラリを生成する際には、Position-Independent Code (PIC) の生成が必須であり、また、Goランタイムの初期化やC言語とのリンケージに関する `gccgo` 固有のリンカフラグが必要となります。

このコミットの背景には、`gccgo` ユーザーも `c-shared` 機能を利用できるようにし、Go言語の共有ライブラリとしての利用範囲を拡大するという目的がありました。特に、`gccgo` がサポートする幅広いプラットフォームでGoの共有ライブラリを生成できるようにするためには、`gccgo` 固有のビルドプロセスへの対応が不可欠でした。

## 前提知識の解説

### Go言語のビルドモード (`-buildmode`)

Go言語の `go build` コマンドには、様々なビルドモードを指定できる `-buildmode` オプションがあります。主要なビルドモードには以下のようなものがあります。

*   **`exe` (デフォルト)**: 実行可能ファイルを生成します。
*   **`archive`**: Goアーカイブファイル（`.a`）を生成します。
*   **`c-archive`**: C言語からリンク可能な静的ライブラリ（`.a`）とCヘッダファイルを生成します。
*   **`c-shared`**: C言語からリンク可能な共有ライブラリ（`.so`, `.dll`, `.dylib`）とCヘッダファイルを生成します。Go 1.5で導入されました。
*   **`shared`**: 複数のGoプログラム間で共有可能なGo共有ライブラリ（`.so`）を生成します。これはGoプログラム間でのみ利用され、C言語からの利用は想定されていません。

### `gccgo` コンパイラ

`gccgo` は、GNU Compiler Collection (GCC) の一部として実装されたGo言語のコンパイラです。標準の `gc` コンパイラとは異なる特徴を持ちます。

*   **GCCの最適化**: `gccgo` はGCCの強力な最適化バックエンドを利用するため、生成されるバイナリが `gc` よりも最適化される場合があります。
*   **幅広いプラットフォームサポート**: GCCがサポートする全てのプロセッサアーキテクチャとオペレーティングシステムでGoコードをコンパイルできます。
*   **動的リンク**: `gccgo` は `libgo` というGoランタイムライブラリに対して動的にリンクするバイナリを生成できます。これにより、実行ファイルのサイズを小さくできますが、ターゲットシステムに `libgo` が存在する必要があります。
*   **C言語との相互運用性**: `gccgo` はC言語との直接的な相互運用機能を提供しますが、`gc` が `cgo` を通じて提供する機能とは異なるアプローチを取ります。

### Position-Independent Code (PIC)

共有ライブラリは、プログラムのメモリ空間内の任意のアドレスにロードされる可能性があります。そのため、共有ライブラリ内のコードは、絶対アドレスではなく、相対アドレスを使用してデータや他のコードを参照する必要があります。このようなコードを「Position-Independent Code (PIC)」と呼びます。PICを生成するためには、コンパイラに `-fPIC` フラグを渡すのが一般的です。

### リンカフラグ

リンカは、コンパイルされたオブジェクトファイルやライブラリを結合して最終的な実行可能ファイルやライブラリを生成するツールです。共有ライブラリをビルドする際には、以下のような特定のリンカフラグが使用されます。

*   **`-shared`**: 共有ライブラリを生成することをリンカに指示します。
*   **`-nostdlib`**: 標準ライブラリをリンクしないように指示します。これは、Goランタイムのような特定のライブラリを明示的にリンクする場合に役立ちます。
*   **`-Wl,--whole-archive` / `-Wl,--no-whole-archive`**: これらのフラグは、特定のアーカイブファイル（静的ライブラリ）内の全てのオブジェクトファイルをリンクするようにリンカに指示します。通常、必要なシンボルのみをリンクしますが、共有ライブラリではGoランタイムの全てのコンポーネントが必要になるため、このフラグが使われます。
*   **`-l<library>`**: 特定のライブラリをリンクします（例: `-lgo` は `libgo` をリンク）。

## 技術的詳細

このコミットの技術的詳細な変更点は、主に `src/cmd/go/build.go` ファイル内の `buildModeInit` 関数と `gccgoToolchain` のメソッド群に集中しています。

### `buildModeInit` 関数における変更

`buildModeInit` 関数は、ビルドモードに応じてコンパイルおよびリンクのフラグを設定する役割を担っています。

1.  **`gccgo` 判定の導入**:
    ```go
    _, gccgo := buildToolchain.(gccgoToolchain)
    ```
    この行が追加され、現在のビルドツールチェインが `gccgoToolchain` のインスタンスであるかどうかが判定されます。これにより、`gccgo` 固有の処理を条件分岐で記述できるようになります。

2.  **`c-shared` ビルドモードの `gccgo` 対応**:
    以前は `c-shared` モードでは、`gc` コンパイラ向けに `linux/amd64` や `linux/arm` といったプラットフォーム固有の `codegenArg` (例: `-shared`) が設定されていました。
    このコミットでは、`gccgo` の場合に `codegenArg = "-fPIC"` が設定されるようになりました。これは、`gccgo` が共有ライブラリをビルドする際にPosition-Independent Code (PIC) を生成するために `-fPIC` フラグを必要とすることを示しています。`gc` コンパイラは内部的にPICを生成するメカニズムを持っているため、明示的な `-fPIC` は不要ですが、`gccgo` はGCCのフロントエンドであるため、GCCの慣習に従います。

3.  **`shared` ビルドモードの `gccgo` 対応**:
    `c-shared` と同様に、`shared` ビルドモードでも `gccgo` の場合に `codegenArg = "-fPIC"` が設定されます。`gc` の場合は `-dynlink` が使用されます。

4.  **`buildLinkshared` オプションの `gccgo` 対応**:
    `buildLinkshared` オプションは、Goの共有ライブラリを動的にリンクする際に使用されます。ここでも `gccgo` の場合は `codegenArg = "-fPIC"` が設定され、`gc` の場合は `-dynlink` と `-linkshared`, `-w` (デバッグ情報なし) といったリンカフラグが追加されます。

5.  **`codegenArg` の適用方法の変更**:
    `codegenArg` が設定された場合、以前は `buildAsmflags` と `buildGcflags` の両方に追加されていました。
    このコミットでは、`gccgo` の場合は `buildGccgoflags` に `codegenArg` が追加されるように変更されました。これは、`gccgo` が独自のフラグセットを持っているため、適切なフラグリストに引数を渡す必要があることを示しています。

### `gccgoToolchain` メソッドにおける変更

`gccgoToolchain` は `gccgo` コンパイラ固有のビルドステップを定義するインターフェースです。

1.  **`asm` および `cc` メソッドへの `maybePIC` 呼び出し**:
    `asm` (アセンブラ) および `cc` (Cコンパイラ) メソッド内で、`defs = tools.maybePIC(defs)` が追加されました。これにより、アセンブリコードやCコードをコンパイルする際にも、必要に応じて `-fPIC` フラグが追加されるようになります。これは、共有ライブラリ内の全てのコードが位置独立である必要があるためです。

2.  **`ld` (リンカ) メソッドの変更**:
    *   **`c-archive` と `c-shared` の共通処理**: `ldBuildmode` が `c-archive` または `c-shared` の場合、`-Wl,--whole-archive` と `-Wl,--no-whole-archive` リンカフラグが追加されるようになりました。これは、Goランタイムの全てのコンポーネントを共有ライブラリに含めるために、静的ライブラリ内の全てのオブジェクトファイルを強制的にリンクする必要があるためです。
    *   **`c-shared` 固有のリンカフラグ**: `ldBuildmode` が `c-shared` の場合、以下の重要なリンカフラグが追加されます。
        *   `-shared`: 共有ライブラリを生成することを指示します。
        *   `-nostdlib`: 標準ライブラリの自動リンクを抑制します。
        *   `-Wl,--whole-archive`, `-lgolibbegin`, `-Wl,--no-whole-archive`, `-lgo`, `-lgcc_s`, `-lgcc`: これらは `gccgo` がGo共有ライブラリを正しくビルドするために必要なGoランタイムライブラリ (`libgo`, `libgolibbegin`) およびGCCのサポートライブラリ (`libgcc_s`, `libgcc`) をリンクするためのフラグです。特に `libgolibbegin` はGoランタイムの初期化に関連する重要なライブラリです。
    *   **C++/Objective-C ライブラリの条件付きリンク**: 以前は `cxx` (C++) や `objc` (Objective-C) が使用されている場合に常に `-lstdc++` や `-lobjc` がリンクされていましたが、このコミットでは `ldBuildmode` が `exe` または `c-shared` の場合にのみこれらのライブラリがリンクされるように変更されました。これにより、不要なライブラリのリンクが避けられ、よりクリーンなビルドが可能になります。

3.  **`maybePIC` ヘルパー関数の追加**:
    `gccgoToolchain` に `maybePIC` という新しいメソッドが追加されました。この関数は、現在の `buildBuildmode` が `c-shared` または `shared` の場合に、引数リストに `-fPIC` を追加します。このヘルパー関数により、PICフラグの追加ロジックが一元化され、コードの重複が排除されています。

これらの変更により、`gccgo` を使用してGoのコードをC言語から呼び出し可能な共有ライブラリとしてビルドする際の、コンパイルおよびリンクのプロセスが正確に設定されるようになりました。

## コアとなるコードの解説

このコミットの主要な変更は、`gccgo` コンパイラが `-buildmode=c-shared` および `-buildmode=shared` で共有ライブラリを生成する際の挙動を調整することにあります。

1.  **`buildModeInit` 関数内の `gccgo` 判定と `codegenArg` の設定**:
    `buildModeInit` 関数は、ビルドモードに応じてコンパイル時に渡すべき引数 (`codegenArg`) を決定します。このコミットでは、`buildToolchain.(gccgoToolchain)` を用いて現在のツールチェインが `gccgo` であるかを判定し、その結果に基づいて `codegenArg` を設定します。
    *   `c-shared` および `shared` モードの場合、`gccgo` であれば `codegenArg` に `"-fPIC"` を設定します。これは、`gccgo` が共有ライブラリをビルドする際に位置独立コード (PIC) を生成するために必要なフラグです。`gc` コンパイラは内部的にPICを生成するため、明示的な `-fPIC` は不要です。
    *   `buildLinkshared` オプションが指定された場合も同様に、`gccgo` であれば `codegenArg` に `"-fPIC"` を設定します。
    *   最終的に `codegenArg` が設定された場合、`gccgo` であれば `buildGccgoflags` に追加され、`gc` であれば `buildAsmflags` と `buildGcflags` に追加されます。これにより、各コンパイラに適切なフラグが渡されます。

2.  **`gccgoToolchain` の `asm` および `cc` メソッドにおける `maybePIC` の利用**:
    `gccgoToolchain` の `asm` (アセンブラ) および `cc` (Cコンパイラ) メソッドは、それぞれアセンブリファイルとCファイルをコンパイルする際に呼び出されます。これらのメソッド内で `defs = tools.maybePIC(defs)` が追加されました。
    `maybePIC` は新しく追加されたヘルパー関数で、`buildBuildmode` が `c-shared` または `shared` の場合に、引数リストに `"-fPIC"` を追加します。これにより、共有ライブラリを構成する全てのアセンブリコードおよびCコードが位置独立コードとしてコンパイルされることが保証されます。

3.  **`gccgoToolchain` の `ld` (リンカ) メソッドにおける変更**:
    `ld` メソッドは、最終的な実行可能ファイルやライブラリをリンクする役割を担います。
    *   **`c-archive` と `c-shared` の共通処理**: `ldBuildmode` が `c-archive` または `c-shared` の場合、`-Wl,--whole-archive` と `-Wl,--no-whole-archive` がリンカフラグに追加されます。これは、Goランタイムの全てのコンポーネントを共有ライブラリに含めるために、静的ライブラリ内の全てのオブジェクトファイルを強制的にリンクするためのGCCリンカのオプションです。
    *   **`c-shared` 固有のリンカフラグ**: `ldBuildmode` が `c-shared` の場合、以下の重要なリンカフラグが追加されます。
        *   `-shared`: 共有ライブラリを生成することをリンカに指示します。
        *   `-nostdlib`: 標準ライブラリの自動リンクを抑制し、必要なライブラリのみを明示的にリンクします。
        *   `-Wl,--whole-archive`, `-lgolibbegin`, `-Wl,--no-whole-archive`, `-lgo`, `-lgcc_s`, `-lgcc`: これらは `gccgo` がGo共有ライブラリを正しくビルドするために必要なGoランタイムライブラリ (`libgo`, `libgolibbegin`) およびGCCのサポートライブラリ (`libgcc_s`, `libgcc`) をリンクするためのフラグです。特に `libgolibbegin` はGoランタイムの初期化に関連する重要なライブラリです。
    *   **C++/Objective-C ライブラリの条件付きリンク**: 以前は無条件にリンクされていたC++ (`-lstdc++`) や Objective-C (`-lobjc`) のライブラリが、`ldBuildmode` が `exe` または `c-shared` の場合にのみリンクされるように変更されました。これにより、不要な依存関係が削減されます。

これらの変更は、`gccgo` コンパイラがGoの共有ライブラリを生成する際の、コンパイルとリンクの複雑な要件を満たすために不可欠です。特に、PICの生成、Goランタイムの適切なリンク、およびC言語との相互運用に必要なリンカフラグの設定が、このコミットによって実現されています。

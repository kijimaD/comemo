# [インデックス 24865] ファイルの概要

このコミットは、Go言語のネットワークパッケージ（`net`）におけるソケットリスニングの挙動を改善するものです。特に、IPv4がサポートされていない環境において、ワイルドカードアドレス（例: `":port"`）でのリスニングが適切にIPv6ソケットを使用するように修正しています。これにより、IPv4が無効化された実験的なカーネル環境など、特殊なネットワーク設定下でのGoアプリケーションの互換性と堅牢性が向上します。

## 元コミット内容

このコミットは、Goの`net`パッケージにおいて、`Listen(":port")`のようなワイルドカードアドレスでのリスニングが、IPv4がサポートされていない環境で失敗する問題を解決します。具体的には、IPv4が利用できない場合に、自動的にIPv6ソケット（`AF_INET6`）を使用するようにロジックを変更しています。

コミットメッセージでは、この問題が発生する「実験的なカーネルでIPv4が無効化された環境」は現状では稀であると述べつつも、通常のLinux環境でこの問題を再現させるための具体的な手順（`supportsIPv4`を`false`に設定するなど）が示されています。

また、`server_test.go`内のテストログ出力におけるアロー記号の向きを`->`から`<-`に変更するという、可読性向上のための軽微な変更も含まれています。

この変更は、Issue #12510を修正するものです。

## 変更の背景

Goの`net`パッケージは、`Listen`関数を使用してネットワーク接続をリッスンする際に、指定されたアドレスに基づいて適切なネットワークプロトコル（IPv4またはIPv6）とソケットタイプ（`AF_INET`または`AF_INET6`）を自動的に選択します。

従来の実装では、`Listen(":port")`のようにIPアドレスが指定されないワイルドカードリスニングの場合、システムがIPv6とIPv4-mapping（IPv6ソケットでIPv4通信を処理する機能）をサポートしていれば、`AF_INET6`ソケットが使用され、`IPV6_V6ONLY=0`オプションが設定されてIPv4とIPv6の両方に対応する動作が期待されました。しかし、そうでない場合は、IPv4ワイルドカードアドレスでのリスニング（`AF_INET`ソケット）が優先されるロジックになっていました。

このロジックには、IPv4自体がシステムでサポートされていない（例えば、カーネルレベルでIPv4が無効化されている）という特殊なケースが考慮されていませんでした。このような環境では、`Listen(":port")`がIPv4ソケットを作成しようとして失敗し、アプリケーションが起動できないという問題が発生していました。

このコミットは、このようなエッジケースに対応し、IPv4が利用できない環境でもGoアプリケーションがワイルドカードアドレスで正常にリスニングできるようにするために導入されました。

## 前提知識の解説

このコミットを理解するためには、以下のネットワークおよびGo言語の概念に関する知識が必要です。

### 1. IPアドレスとソケットアドレスファミリー

*   **IPv4 (Internet Protocol version 4)**: 現在広く使われているIPアドレスのバージョン。32ビットのアドレスを使用します（例: `192.168.1.1`）。
*   **IPv6 (Internet Protocol version 6)**: IPv4の後継として開発されたIPアドレスのバージョン。128ビットのアドレスを使用し、より多くのアドレス空間を提供します（例: `2001:0db8:85a3:0000:0000:8a2e:0370:7334`）。
*   **ソケットアドレスファミリー (Address Family)**: ソケットプログラミングにおいて、どのネットワークプロトコル（IPv4, IPv6など）を使用するかを指定する定数です。
    *   `AF_INET`: IPv4プロトコルファミリーを表します。
    *   `AF_INET6`: IPv6プロトコルファミリーを表します。

### 2. ワイルドカードアドレス

*   ネットワークリスニングにおいて、特定のIPアドレスを指定せずに、利用可能なすべてのネットワークインターフェースからの接続を受け入れるために使用されるアドレスです。
    *   IPv4では`0.0.0.0`がワイルドカードアドレスとして使われます。
    *   IPv6では`::`がワイルドカードアドレスとして使われます。
*   Goの`net.Listen`関数で`":port"`のようにIPアドレスを省略した場合、Goランタイムが適切なワイルドカードアドレスを自動的に選択します。

### 3. IPv4-mapping (IPv6 Dual-Stack Socket)

*   IPv6ソケット（`AF_INET6`）がIPv4アドレスからの接続も受け入れることができる機能です。これは、IPv6ソケットに`IPV6_V6ONLY`ソケットオプションを`0`に設定することで実現されます。
*   この機能が有効な場合、一つのIPv6ソケットでIPv4とIPv6の両方のクライアントからの接続を処理できるため、サーバーアプリケーションの実装が簡素化されます。
*   ただし、この機能のサポートはオペレーティングシステムに依存します。

### 4. `supportsIPv4`, `supportsIPv6`, `supportsIPv4map`

*   Goの`net`パッケージ内部で使用されるブール型の変数で、現在のシステムがそれぞれIPv4、IPv6、およびIPv4-mapping機能をサポートしているかどうかを示します。
*   これらの変数は、Goランタイムが起動時にシステムのネットワーク機能をプローブして設定されます。

### 5. `net.Listen`関数の内部動作

*   `net.Listen(network, address)`は、指定されたネットワークタイプ（例: `"tcp"`, `"udp"`）とアドレスに基づいて、ネットワークリスナーを作成します。
*   アドレスがワイルドカードの場合、Goは`favoriteAddrFamily`のような内部関数を使って、どのソケットアドレスファミリー（`AF_INET`または`AF_INET6`）を優先的に使用するかを決定します。この決定は、システムのネットワーク機能（`supportsIPv4`, `supportsIPv6`, `supportsIPv4map`）に依存します。

## 技術的詳細

このコミットの核心は、`src/net/ipsock_posix.go`内の`favoriteAddrFamily`関数のロジック変更にあります。この関数は、ワイルドカードアドレスでのリスニング（例: `":port"`）において、どのソケットアドレスファミリー（`AF_INET`または`AF_INET6`）を使用すべきかを決定します。

変更前のロジックは以下のようでした：
「プラットフォームがIPv6とIPv4-mappingの両方をサポートしている場合、ユーザーは`AF_INET6`ソケットと`IPV6_V6ONLY=0`を使用してIPv4とIPv6の両方のワイルドカードアドレスでリスニングしたいと仮定する。そうでなければ、`AF_INET`ソケットでのIPv4ワイルドカードアドレスリスニングを優先する。」

このロジックの問題点は、システムがIPv4-mappingをサポートしていないが、IPv4自体もサポートしていない（`supportsIPv4`が`false`）という状況を適切に扱えないことでした。このような場合、従来のロジックでは`AF_INET`ソケットが優先され、結果としてIPv4が利用できないシステムでリスニングが失敗していました。

このコミットによる変更は、この条件に`!supportsIPv4`（IPv4がサポートされていない場合）を追加することで、この問題を解決しています。

変更後のロジック：
「プラットフォームがIPv6とIPv4-mappingの両方をサポートしている**か、またはIPv4をサポートしていない場合**、ユーザーは`AF_INET6`ソケットと`IPV6_V6ONLY=0`を使用してIPv4とIPv6の両方のワイルドカードアドレスでリスニングしたいと仮定する。そうでなければ、`AF_INET`ソケットでのIPv4ワイルドカードアドレスリスニングを優先する。」

これにより、IPv4がサポートされていない環境でも、Goランタイムは`AF_INET6`ソケットを選択し、IPv6経由でのリスニングを試みるようになります。これは、IPv4が利用できない状況下でのGoアプリケーションの堅牢性を高める重要な変更です。

また、`src/net/platform_test.go`の`testableListenArgs`関数内の条件も調整されています。この関数は、特定のネットワーク設定でのリスニングがテスト可能かどうかを判断するために使用されます。変更前は`!supportsIPv4map`という条件がありましたが、これに`supportsIPv4`が追加されました。これは、IPv4-mappingがサポートされていないがIPv4はサポートされている場合にのみ、特定のテストケースが実行されるようにするための調整であり、メインのロジック変更と整合性を保つためのものです。

`src/net/server_test.go`の変更は、テストログの可読性向上を目的としたもので、機能的な変更ではありません。

## コアとなるコードの解説

### `src/net/ipsock_posix.go` の変更

このファイルは、POSIX互換システム（Linux, macOSなど）におけるIPソケット関連の低レベルな処理を扱います。

変更の中心は、`favoriteAddrFamily`関数の以下の行です。

```go
-		if supportsIPv4map {
+		if supportsIPv4map || !supportsIPv4 {
			return syscall.AF_INET6, false
		}
```

*   **変更前 (`if supportsIPv4map`)**:
    *   この条件は、「システムがIPv4-mappingをサポートしている場合」に`AF_INET6`ソケットを優先することを示していました。
    *   もし`supportsIPv4map`が`false`であれば、この条件は満たされず、後続のロジック（このスニペットには含まれていませんが、通常は`AF_INET`ソケットを優先する）が実行されていました。
    *   問題は、`supportsIPv4map`が`false`であり、かつ`supportsIPv4`も`false`である（IPv4自体が利用できない）場合に、`AF_INET`ソケットが選択されてしまい、リスニングが失敗することでした。

*   **変更後 (`if supportsIPv4map || !supportsIPv4`)**:
    *   この条件は、「システムがIPv4-mappingをサポートしている場合」**または**「IPv4がサポートされていない場合」に`AF_INET6`ソケットを優先するように拡張されました。
    *   `!supportsIPv4`が追加されたことで、IPv4が利用できない環境では、たとえIPv4-mappingがサポートされていなくても、明示的に`AF_INET6`ソケットが選択されるようになります。
    *   これにより、IPv4が無効化されたシステムでも、ワイルドカードアドレスでのリスニングがIPv6ソケットを通じて正常に行われるようになります。`return syscall.AF_INET6, false`は、`AF_INET6`ソケットを使用し、`IPV6_V6ONLY=0`（`false`）を設定してIPv4-mappingを有効にする（もし可能であれば）ことを意味します。

### `src/net/platform_test.go` の変更

このファイルは、Goの`net`パッケージが様々なプラットフォームのネットワーク機能をどのようにサポートしているかをテストするためのユーティリティ関数を含んでいます。

変更された行は以下の通りです。

```go
-	if !supportsIPv4map && (network == "tcp" || network == "udp" || network == "ip") && wildcard {
+	if !supportsIPv4map && supportsIPv4 && (network == "tcp" || network == "udp" || network == "ip") && wildcard {
```

*   **変更前 (`!supportsIPv4map`)**:
    *   この条件は、「IPv4-mappingがサポートされていない場合」に特定のテストケースを実行するかどうかを判断していました。
    *   このテストケースは、`AF_INET6`ソケットを使用したIPv4通信の機能に関するものでした。

*   **変更後 (`!supportsIPv4map && supportsIPv4`)**:
    *   条件に`supportsIPv4`が追加されました。
    *   これは、「IPv4-mappingはサポートされていないが、IPv4自体はサポートされている場合」にのみ、このテストケースが実行されるべきであることを明確にしています。
    *   もしIPv4自体がサポートされていない環境であれば、IPv4通信のテストは意味がないため、この条件によってテストがスキップされるようになります。これは、`ipsock_posix.go`での主要な変更と整合性を保つためのテスト側の調整です。

### `src/net/server_test.go` の変更

このファイルには、TCP、UDP、Unixgramサーバーのテストが含まれています。

変更は以下の行に見られます。

```diff
-\t\tt.Logf(\"skipping %s test\", tt.snet+\" \"+tt.saddr+\"->\"+tt.taddr)\n+\t\tt.Logf(\"skipping %s test\", tt.snet+\" \"+tt.saddr+\"<-\"+tt.taddr)\n```

これは、テストがスキップされた際にログに出力されるメッセージのアロー記号の向きを`->`から`<-`に変更したものです。コミットメッセージにもあるように、「`server<-client`の方が読みやすい」という理由によるもので、機能的な変更ではなく、単なる可読性向上のための修正です。

## 変更の背景

Goの`net`パッケージは、`Listen`関数を使用してネットワーク接続をリッスンする際に、指定されたアドレスに基づいて適切なネットワークプロトコル（IPv4またはIPv6）とソケットタイプ（`AF_INET`または`AF_INET6`）を自動的に選択します。

従来の実装では、`Listen(":port")`のようにIPアドレスが指定されないワイルドカードリスニングの場合、システムがIPv6とIPv4-mapping（IPv6ソケットでIPv4通信を処理する機能）をサポートしていれば、`AF_INET6`ソケットが使用され、`IPV6_V6ONLY=0`オプションが設定されてIPv4とIPv6の両方に対応する動作が期待されました。しかし、そうでない場合は、IPv4ワイルドカードアドレスでのリスニング（`AF_INET`ソケット）が優先されるロジックになっていました。

このロジックには、IPv4自体がシステムでサポートされていない（例えば、カーネルレベルでIPv4が無効化されている）という特殊なケースが考慮されていませんでした。このような環境では、`Listen(":port")`がIPv4ソケットを作成しようとして失敗し、アプリケーションが起動できないという問題が発生していました。

このコミットは、このようなエッジケースに対応し、IPv4が利用できない環境でもGoアプリケーションがワイルドカードアドレスで正常にリスニングできるようにするために導入されました。

## 前提知識の解説

このコミットを理解するためには、以下のネットワークおよびGo言語の概念に関する知識が必要です。

### 1. IPアドレスとソケットアドレスファミリー

*   **IPv4 (Internet Protocol version 4)**: 現在広く使われているIPアドレスのバージョン。32ビットのアドレスを使用します（例: `192.168.1.1`）。
*   **IPv6 (Internet Protocol version 6)**: IPv4の後継として開発されたIPアドレスのバージョン。128ビットのアドレスを使用し、より多くのアドレス空間を提供します（例: `2001:0db8:85a3:0000:0000:8a2e:0370:7334`）。
*   **ソケットアドレスファミリー (Address Family)**: ソケットプログラミングにおいて、どのネットワークプロトコル（IPv4, IPv6など）を使用するかを指定する定数です。
    *   `AF_INET`: IPv4プロトコルファミリーを表します。
    *   `AF_INET6`: IPv6プロトコルファミリーを表します。

### 2. ワイルドカードアドレス

*   ネットワークリスニングにおいて、特定のIPアドレスを指定せずに、利用可能なすべてのネットワークインターフェースからの接続を受け入れるために使用されるアドレスです。
    *   IPv4では`0.0.0.0`がワイルドカードアドレスとして使われます。
    *   IPv6では`::`がワイルドカードアドレスとして使われます。
*   Goの`net.Listen`関数で`":port"`のようにIPアドレスを省略した場合、Goランタイムが適切なワイルドカードアドレスを自動的に選択します。

### 3. IPv4-mapping (IPv6 Dual-Stack Socket)

*   IPv6ソケット（`AF_INET6`）がIPv4アドレスからの接続も受け入れることができる機能です。これは、IPv6ソケットに`IPV6_V6ONLY`ソケットオプションを`0`に設定することで実現されます。
*   この機能が有効な場合、一つのIPv6ソケットでIPv4とIPv6の両方のクライアントからの接続を処理できるため、サーバーアプリケーションの実装が簡素化されます。
*   ただし、この機能のサポートはオペレーティングシステムに依存します。

### 4. `supportsIPv4`, `supportsIPv6`, `supportsIPv4map`

*   Goの`net`パッケージ内部で使用されるブール型の変数で、現在のシステムがそれぞれIPv4、IPv6、およびIPv4-mapping機能をサポートしているかどうかを示します。
*   これらの変数は、Goランタイムが起動時にシステムのネットワーク機能をプローブして設定されます。

### 5. `net.Listen`関数の内部動作

*   `net.Listen(network, address)`は、指定されたネットワークタイプ（例: `"tcp"`, `"udp"`）とアドレスに基づいて、ネットワークリスナーを作成します。
*   アドレスがワイルドカードの場合、Goは`favoriteAddrFamily`のような内部関数を使って、どのソケットアドレスファミリー（`AF_INET`または`AF_INET6`）を優先的に使用するかを決定します。この決定は、システムのネットワーク機能（`supportsIPv4`, `supportsIPv6`, `supportsIPv4map`）に依存します。

## 技術的詳細

このコミットの核心は、`src/net/ipsock_posix.go`内の`favoriteAddrFamily`関数のロジック変更にあります。この関数は、ワイルドカードアドレスでのリスニング（例: `":port"`）において、どのソケットアドレスファミリー（`AF_INET`または`AF_INET6`）を使用すべきかを決定します。

変更前のロジックは以下のようでした：
「プラットフォームがIPv6とIPv4-mappingの両方をサポートしている場合、ユーザーは`AF_INET6`ソケットと`IPV6_V6ONLY=0`を使用してIPv4とIPv6の両方のワイルドカードアドレスでリスニングしたいと仮定する。そうでなければ、`AF_INET`ソケットでのIPv4ワイルドカードアドレスリスニングを優先する。」

このロジックの問題点は、システムがIPv4-mappingをサポートしていないが、IPv4自体もサポートしていない（`supportsIPv4`が`false`）という状況を適切に扱えないことでした。このような場合、従来のロジックでは`AF_INET`ソケットが優先され、結果としてIPv4が利用できないシステムでリスニングが失敗していました。

このコミットによる変更は、この条件に`!supportsIPv4`（IPv4がサポートされていない場合）を追加することで、この問題を解決しています。

変更後のロジック：
「プラットフォームがIPv6とIPv4-mappingの両方をサポートしている**か、またはIPv4をサポートしていない場合**、ユーザーは`AF_INET6`ソケットと`IPV6_V6ONLY=0`を使用してIPv4とIPv6の両方のワイルドカードアドレスでリスニングしたいと仮定する。そうでなければ、`AF_INET`ソケットでのIPv4ワイルドカードアドレスリスニングを優先する。」

これにより、IPv4がサポートされていない環境でも、Goランタイムは`AF_INET6`ソケットを選択し、IPv6経由でのリスニングを試みるようになります。これは、IPv4が利用できない状況下でのGoアプリケーションの堅牢性を高める重要な変更です。

また、`src/net/platform_test.go`の`testableListenArgs`関数内の条件も調整されています。この関数は、特定のネットワーク設定でのリスニングがテスト可能かどうかを判断するために使用されます。変更前は`!supportsIPv4map`という条件がありましたが、これに`supportsIPv4`が追加されました。これは、IPv4-mappingがサポートされていないがIPv4はサポートされている場合にのみ、特定のテストケースが実行されるようにするための調整であり、メインのロジック変更と整合性を保つためのものです。

`src/net/server_test.go`の変更は、テストログの可読性向上を目的としたもので、機能的な変更ではありません。

## コアとなるコードの解説

### `src/net/ipsock_posix.go` の変更

このファイルは、POSIX互換システム（Linux, macOSなど）におけるIPソケット関連の低レベルな処理を扱います。

変更の中心は、`favoriteAddrFamily`関数の以下の行です。

```go
-		if supportsIPv4map {
+		if supportsIPv4map || !supportsIPv4 {
			return syscall.AF_INET6, false
		}
```

*   **変更前 (`if supportsIPv4map`)**:
    *   この条件は、「システムがIPv4-mappingをサポートしている場合」に`AF_INET6`ソケットを優先することを示していました。
    *   もし`supportsIPv4map`が`false`であれば、この条件は満たされず、後続のロジック（このスニペットには含まれていませんが、通常は`AF_INET`ソケットを優先する）が実行されていました。
    *   問題は、`supportsIPv4map`が`false`であり、かつ`supportsIPv4`も`false`である（IPv4自体が利用できない）場合に、`AF_INET`ソケットが選択されてしまい、リスニングが失敗することでした。

*   **変更後 (`if supportsIPv4map || !supportsIPv4`)**:
    *   この条件は、「システムがIPv4-mappingをサポートしている場合」**または**「IPv4がサポートされていない場合」に`AF_INET6`ソケットを優先するように拡張されました。
    *   `!supportsIPv4`が追加されたことで、IPv4が利用できない環境では、たとえIPv4-mappingがサポートされていなくても、明示的に`AF_INET6`ソケットが選択されるようになります。
    *   これにより、IPv4が無効化されたシステムでも、ワイルドカードアドレスでのリスニングがIPv6ソケットを通じて正常に行われるようになります。`return syscall.AF_INET6, false`は、`AF_INET6`ソケットを使用し、`IPV6_V6ONLY=0`（`false`）を設定してIPv4-mappingを有効にする（もし可能であれば）ことを意味します。

### `src/net/platform_test.go` の変更

このファイルは、Goの`net`パッケージが様々なプラットフォームのネットワーク機能をどのようにサポートしているかをテストするためのユーティリティ関数を含んでいます。

変更された行は以下の通りです。

```go
-	if !supportsIPv4map && (network == "tcp" || network == "udp" || network == "ip") && wildcard {
+	if !supportsIPv4map && supportsIPv4 && (network == "tcp" || network == "udp" || network == "ip") && wildcard {
```

*   **変更前 (`!supportsIPv4map`)**:
    *   この条件は、「IPv4-mappingがサポートされていない場合」に特定のテストケースを実行するかどうかを判断していました。
    *   このテストケースは、`AF_INET6`ソケットを使用したIPv4通信の機能に関するものでした。

*   **変更後 (`!supportsIPv4map && supportsIPv4`)**:
    *   条件に`supportsIPv4`が追加されました。
    *   これは、「IPv4-mappingはサポートされていないが、IPv4自体はサポートされている場合」にのみ、このテストケースが実行されるべきであることを明確にしています。
    *   もしIPv4自体がサポートされていない環境であれば、IPv4通信のテストは意味がないため、この条件によってテストがスキップされるようになります。これは、`ipsock_posix.go`での主要な変更と整合性を保つためのテスト側の調整です。

### `src/net/server_test.go` の変更

このファイルには、TCP、UDP、Unixgramサーバーのテストが含まれています。

変更は以下の行に見られます。

```diff
-\t\tt.Logf(\"skipping %s test\", tt.snet+\" \"+tt.saddr+\"->\"+tt.taddr)\n+\t\tt.Logf(\"skipping %s test\", tt.snet+\" \"+tt.saddr+\"<-\"+tt.taddr)\n```

これは、テストがスキップされた際にログに出力されるメッセージのアロー記号の向きを`->`から`<-`に変更したものです。コミットメッセージにもあるように、「`server<-client`の方が読みやすい」という理由によるもので、機能的な変更ではなく、単なる可読性向上のための修正です。

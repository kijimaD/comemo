# [インデックス 24356] ファイルの概要

このコミットは、Go言語の `internal/singleflight` パッケージ内の `TestDoDupSuppress` というテストの信頼性を向上させるためのものです。`singleflight` パッケージは、複数のGoroutineが同じキーで同じ処理を同時に実行しようとした際に、その処理が一度だけ実行されるように調整するメカニズムを提供します。このコミットは、特に並行処理のタイミングに依存して稀に失敗していたテストの「flakiness」（不安定さ）を解消することを目的としています。

## コミット

Date:   Sun Jul 26 16:03:13 2015 -0400

    internal/singleflight: deflake TestDoDupSuppress
    
    Currently TestDoDupSuppress can fail if the goroutines created by its
    loop run sequentially. This is rare, but it has caused failures on the
    dashboard and in stress testing.
    
    While I think there's no way to eliminate all possible thread
    schedules that could make this test fail because it depends on waiting
    until a Group.Do blocks, it is possible to make it much more robust.
    
    This commit deflakes this test by forcing at least one invocation of
    fn to start and all goroutines to reach the line just before the Do
    call before allowing fn to proceed. fn then waits 10 milliseconds
    before returning to allow the goroutines to pass through the Do.
    
    With this change, in 50,000 runs of the stress testing configuration,
    the number of calls to fn never even exceeded 1.

## 元コミット内容

`internal/singleflight: deflake TestDoDupSuppress`

このコミットは、`internal/singleflight` パッケージ内の `TestDoDupSuppress` テストの不安定性（flakiness）を解消することを目的としています。

現在の `TestDoDupSuppress` は、ループによって作成されたGoroutineが順次実行された場合に失敗する可能性があります。これは稀なケースですが、ダッシュボードやストレステストで失敗を引き起こしていました。

`Group.Do` がブロックするまで待機することに依存しているため、このテストが失敗する可能性のあるすべてのスレッドスケジュールを排除する方法はないと考えられますが、テストをはるかに堅牢にすることは可能です。

このコミットは、`fn` の呼び出しが少なくとも1回開始され、すべてのGoroutineが `Do` 呼び出しの直前の行に到達するまで強制的に待機させることで、このテストの不安定性を解消します。その後、`fn` は10ミリ秒待機してから戻り、Goroutineが `Do` を通過できるようにします。

この変更により、ストレステスト構成で50,000回実行した結果、`fn` の呼び出し回数が1を超えることはありませんでした。

Fixes #11784.

## 変更の背景

`internal/singleflight` パッケージは、Go言語において、複数のGoroutineが同じ処理を同時に実行しようとした際に、その処理が一度だけ実行されるように調整するためのユーティリティを提供します。これにより、重複する作業を避け、リソースの無駄遣いを防ぐことができます。

`TestDoDupSuppress` は、この `singleflight` パッケージの主要な機能である「重複抑制（duplicate suppression）」が正しく機能するかを検証するテストです。具体的には、複数のGoroutineが同時に `Group.Do` を呼び出した場合でも、基となる関数 (`fn`) が一度だけ実行されることを確認します。

しかし、このテストは並行処理のタイミングに非常に敏感であり、特定のGoroutineのスケジューリングによっては、`fn` が複数回呼び出されてしまうという誤った結果を出すことがありました。これはテストの「flakiness」として知られ、テストがコードの変更とは無関係に、実行環境やタイミングによって成功したり失敗したりする現象です。このような不安定なテストは、開発者がコードの品質を信頼する上で大きな障害となります。

コミットメッセージによると、この問題はGoのダッシュボード（継続的インテグレーションシステム）やストレステストで実際に報告されており、修正が必要とされていました。特に、複数のGoroutineが `Group.Do` を呼び出す前に `fn` が完了してしまうと、後続のGoroutineが新しい `Group.Do` の呼び出しとして `fn` を再度実行してしまう可能性がありました。

このコミットの目的は、テストのロジックを調整し、Goroutineの実行順序がどうであれ、`singleflight` の重複抑制メカニズムが意図通りに機能することを確実に検証できるようにすることです。

## 前提知識の解説

### Go言語の並行処理とGoroutine

Go言語は、軽量なスレッドである「Goroutine」と、Goroutine間の通信を安全に行うための「チャネル」によって、強力な並行処理をサポートしています。

*   **Goroutine**: Goランタイムによって管理される軽量な実行単位です。数千、数万のGoroutineを同時に実行してもオーバーヘッドが少ないのが特徴です。`go` キーワードを使って関数を呼び出すことでGoroutineが起動します。
*   **チャネル (Channel)**: Goroutine間で値を送受信するための通信メカニズムです。チャネルは、データの受け渡しだけでなく、Goroutine間の同期にも利用されます。バッファなしチャネルは、送信と受信が同時に行われるまでブロックします。

### `sync.WaitGroup`

`sync.WaitGroup` は、複数のGoroutineの完了を待機するための同期プリミティブです。

*   `Add(delta int)`: 待機するGoroutineの数を `delta` だけ増やします。
*   `Done()`: Goroutineが完了したことを通知し、内部カウンタを1減らします。
*   `Wait()`: 内部カウンタが0になるまでブロックします。

このコミットでは、`sync.WaitGroup` を用いて、テスト内の特定のGoroutineが特定の実行ポイントに到達するまでメインのGoroutineをブロックすることで、テストのタイミングを制御しています。

### `atomic` パッケージ

`sync/atomic` パッケージは、低レベルのアトミック操作（不可分操作）を提供します。これにより、複数のGoroutineから共有変数にアクセスする際に、競合状態（race condition）を避けることができます。

*   `atomic.AddInt32(&val, delta int32)`: `val` に `delta` をアトミックに加算し、新しい値を返します。
*   `atomic.LoadInt32(&val)`: `val` の値をアトミックに読み込みます。

このコミットでは、`atomic.AddInt32` を使用して、`fn` が何回呼び出されたかを正確にカウントしています。

### `internal/singleflight` パッケージ

`singleflight` パッケージは、Goの標準ライブラリの一部ですが、`internal` ディレクトリにあるため、外部からの直接利用は推奨されていません。しかし、その機能はGoの内部実装や、他のGoプロジェクトで同様のパターンを実装する際の参考になります。

`singleflight.Group` は、同じキーに対する複数のリクエストを単一の実行にまとめ、その結果をすべてのリクエスタにブロードキャストする機能を提供します。これにより、例えばキャッシュのウォームアップや、外部APIへの重複するリクエストなどを防ぐことができます。

*   `Group.Do(key string, fn func() (interface{}, error)) (v interface{}, err error, shared bool)`: 指定された `key` に対して `fn` を実行します。もし同じ `key` で既に `fn` が実行中であれば、その完了を待機し、結果を共有します。`shared` は、結果が共有されたものかどうかを示します。

### テストのFlakiness (不安定性)

テストのFlakinessとは、コードの変更がないにもかかわらず、テストが成功したり失敗したりする現象を指します。これは、並行処理のタイミング、外部リソースの可用性、環境のばらつきなど、様々な要因によって引き起こされます。Flakyなテストは、開発者の信頼を損ない、CI/CDパイプラインの効率を低下させるため、可能な限り排除することが重要です。

このコミットは、まさにこのようなFlakinessを解消するための典型的な例です。

## 技術的詳細

このコミットは、`TestDoDupSuppress` テストの並行処理のタイミングをより厳密に制御することで、テストの信頼性を向上させています。

元のテストでは、複数のGoroutineが `Group.Do` を呼び出す前に、メインGoroutineが `time.Sleep` を使ってGoroutineが `Do` に到達するのを待っていました。しかし、`time.Sleep` は非決定的な要素であり、Goroutineスケジューラの挙動によっては、`fn` が複数回実行されてしまう可能性がありました。

新しいテストロジックでは、`sync.WaitGroup` を2つ (`wg1`, `wg2`) 導入し、`fn` の実行とGoroutineの `Do` 呼び出し前の同期をより精密に行っています。

1.  **`wg1` の導入**:
    *   `wg1.Add(1)`: メインGoroutineが `wg1.Wait()` で待機する準備をします。
    *   各Goroutineは `go func()` の開始時に `wg1.Add(1)` を呼び出し、`Group.Do` の直前で `wg1.Done()` を呼び出します。
    *   `fn` の最初の呼び出し時にも `wg1.Done()` を呼び出します。
    *   メインGoroutineは `wg1.Wait()` を呼び出すことで、**少なくとも1つのGoroutineが `fn` の実行を開始し、かつ、すべてのGoroutineが `Group.Do` 呼び出しの直前の行に到達する**までブロックされます。これにより、すべてのGoroutineが `singleflight` の重複抑制の対象となる準備が整った状態で `fn` の実行が開始されることが保証されます。

2.  **`fn` 内での `time.Sleep`**:
    *   `fn` の中で `time.Sleep(10 * time.Millisecond)` が追加されました。これは、`fn` の最初の実行が完了する前に、他のGoroutineが `Group.Do` を呼び出し、その結果を共有できるようにするための時間的猶予を与えます。これにより、`singleflight` の重複抑制メカニズムが正しく機能する機会が増えます。

3.  **`wg2` の導入**:
    *   各Goroutineは `go func()` の開始時に `wg2.Add(1)` を呼び出し、`defer wg2.Done()` でGoroutineの終了時にカウンタを減らします。
    *   メインGoroutineは `wg2.Wait()` を呼び出すことで、**すべてのGoroutineが `Group.Do` の呼び出しと結果の受け取りを完了する**までブロックされます。これにより、テストの評価がすべての並行処理が終了した後に行われることが保証されます。

これらの変更により、テストはGoroutineのスケジューリングに起因するタイミングの問題を回避し、`singleflight` の重複抑制機能が意図通りに動作することをより確実に検証できるようになりました。特に、`fn` の呼び出し回数が `0 < calls < n` の範囲に収まることを検証するアサーションが、より信頼性の高いものとなっています。

## コアとなるコードの解説

### `var wg1, wg2 sync.WaitGroup`

*   `wg1`: Goroutineが `Group.Do` を呼び出す直前のポイントに到達したこと、および `fn` が少なくとも一度実行を開始したことを同期するために使用されます。
*   `wg2`: すべてのGoroutineが `Group.Do` の呼び出しと結果の受け取りを完了したことを同期するために使用されます。

### `if atomic.AddInt32(&calls, 1) == 1 { wg1.Done() }`

`fn` 関数内で、`atomic.AddInt32(&calls, 1)` は `calls` カウンタをアトミックにインクリメントします。その結果が `1` である場合（つまり、`fn` が最初に呼び出された場合）、`wg1.Done()` が呼び出されます。これにより、メインGoroutineは `fn` の実行が開始されたことを認識できます。

### `time.Sleep(10 * time.Millisecond)`

`fn` の中で、結果をチャネル `c` に書き込んだ後、10ミリ秒の遅延が追加されました。この遅延は、`fn` の最初の実行が完了する前に、他のGoroutineが `Group.Do` を呼び出し、`singleflight` の重複抑制メカニズムによって結果を共有する機会を与えるために重要です。これにより、`fn` が複数回実行される可能性が大幅に減少します。

### `wg1.Add(1)` (ループ外) と `wg1.Add(1)` (ループ内)

*   ループ外の `wg1.Add(1)` は、`fn` の最初の呼び出しを待つためのものです。
*   ループ内の `wg1.Add(1)` は、`n` 個のGoroutineそれぞれが `Group.Do` の直前の行に到達するのを待つためのものです。

### `defer wg2.Done()` と `wg1.Done()` (Goroutine内)

各Goroutineは、`Group.Do` を呼び出す直前に `wg1.Done()` を呼び出します。これにより、そのGoroutineが `Group.Do` の呼び出し準備ができたことを `wg1` に通知します。
また、`defer wg2.Done()` により、Goroutineが終了する際に `wg2` のカウンタが減らされ、メインGoroutineがすべてのGoroutineの完了を待つことができます。

### `wg1.Wait()` と `wg2.Wait()`

*   `wg1.Wait()`: メインGoroutineは、`fn` が一度実行を開始し、かつ、すべてのGoroutineが `Group.Do` の直前の行に到達するまでここでブロックされます。これにより、テストの開始条件が厳密に制御されます。
*   `wg2.Wait()`: メインGoroutineは、すべてのGoroutineが `Group.Do` の呼び出しと結果の受け取りを完了するまでここでブロックされます。これにより、テストの評価がすべての並行処理が終了した後に行われることが保証されます。

### エラーメッセージの修正

`t.Errorf` のメッセージが `want over 0 and less than n` から `want over 0 and less than %d` に変更され、`n` の値が動的に表示されるようになりました。これは機能的な変更ではなく、デバッグ時の可読性を向上させるためのものです。

これらの変更により、`TestDoDupSuppress` はGoroutineのスケジューリングに起因する非決定的な失敗を回避し、`singleflight` パッケージのコア機能である重複抑制をより堅牢に検証できるようになりました。

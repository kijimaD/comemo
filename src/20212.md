## 元コミット内容

`runtime: round channel size in allocation instead of using system-specific pad field`

## 変更の背景

この変更の背景には、Goランタイムがチャネル（`hchan`構造体）をメモリに割り当てる際のメモリ配置とアライメントの問題がありました。以前のGoランタイムでは、`hchan`構造体の後に続くチャネルのバッファが適切にアライメントされるように、特定のアーキテクチャ（特に`amd64`以外）で`uint32 pad;`というシステム固有のパディングフィールドを使用していました。

しかし、このようなシステム固有のパディングは、コードの移植性や保守性を低下させる可能性があります。異なるアーキテクチャやコンパイラ設定によって、パディングの必要性やサイズが変動するリスクがありました。このコミットは、このようなシステム固有のパディングフィールドに依存するのではなく、チャネルのサイズ自体を割り当て時に汎用的な方法でアライメント境界に丸めることで、この問題を解決しようとしています。

コミットメッセージにある「Followup to CL 128700043」は、この変更が以前の関連するコミット（CL 128700043）の続きであることを示唆しています。おそらく、その先行コミットでチャネルのメモリ割り当てに関する何らかの変更が行われ、このコミットはその変更をさらに改善し、より堅牢でポータブルなアライメント戦略を導入したと考えられます。

## 前提知識の解説

### Go Channels (チャネル)
Go言語におけるチャネルは、ゴルーチン間で値を送受信するための主要な通信メカニズムです。チャネルは、同期的な通信（バッファなしチャネル）と非同期的な通信（バッファありチャネル）の両方をサポートします。内部的には、チャネルは`runtime`パッケージの`hchan`構造体によって表現されます。

### `hchan` 構造体
`hchan`はGoチャネルの内部表現であり、チャネルのバッファ、送受信キュー、ロック、要素の型とサイズなど、チャネルの動作に必要なすべての情報を含んでいます。Goランタイムは、`make(chan T, capacity)`のようなチャネル作成時に、この`hchan`構造体と、もしバッファ付きチャネルであればそのバッファのためのメモリを割り当てます。

### メモリのアライメント (Memory Alignment)
メモリのアライメントとは、データがメモリ内で特定のバイト境界に配置されることを指します。CPUは通常、特定のバイト境界（例えば4バイト、8バイトなど）に配置されたデータにアクセスする方が効率的です。データが適切にアライメントされていない場合、CPUは複数のメモリ読み取り操作を実行する必要があるか、パフォーマンスが低下する可能性があります。構造体をメモリに割り当てる際、その構造体のフィールドや、構造体の後に続くデータが適切にアライメントされるように、コンパイラやランタイムがパディング（詰め物）を追加することがあります。

### `unsafe.Sizeof`
Goの`unsafe`パッケージは、Goの型システムの安全性をバイパスする操作を可能にします。`unsafe.Sizeof(x)`は、Goの式`x`が占めるメモリのバイト数を返します。これはコンパイル時に決定される定数です。

### `uintptr`
`uintptr`は、ポインタを保持するのに十分な大きさの符号なし整数型です。これは、ポインタ演算を行う際に使用されますが、ガベージコレクタは`uintptr`型の値をポインタとして扱わないため、注意が必要です。

## 技術的詳細

このコミットの核心は、`hchan`構造体のメモリ割り当てサイズを計算する方法の変更にあります。以前は、`hchan`構造体の直後に続くチャネルのバッファが適切にアライメントされるように、一部のアーキテクチャで明示的なパディングフィールド（`uint32 pad;`）を使用していました。しかし、これはアーキテクチャ固有の解決策であり、コードの複雑性を増し、移植性を損なう可能性がありました。

新しいアプローチでは、`hchan`構造体自体のサイズを、`maxAlign`（通常は8バイト）の倍数に「丸める」ことで、この問題を解決します。これにより、`hchan`構造体の直後に割り当てられるバッファは、常に適切なアライメント境界から開始されることが保証されます。この「丸め」は、`hchanSize`の計算式にビット演算を導入することで実現されています。

具体的には、`unsafe.Sizeof(hchan{})`で得られる`hchan`構造体の実際のサイズに、必要なパディングバイト数を加算しています。このパディングバイト数は、`hchan`構造体のサイズを`maxAlign`の倍数にするために必要な最小値です。この計算により、`hchan`構造体とそれに続くバッファが単一の連続したメモリブロックとして割り当てられる際に、バッファの開始アドレスが常に`maxAlign`の倍数になるように保証されます。

この変更により、システム固有のパディングフィールドが不要になり、`chan.h`から削除されました。これにより、Goランタイムのチャネル割り当てロジックがより汎用的で、アーキテクチャに依存しないものとなり、コードの簡素化と移植性の向上が図られています。

## コアとなるコードの解説

### `src/pkg/runtime/chan.go` の変更

最も重要な変更は、`hchanSize`定数の定義です。

**変更前:**
```go
hchanSize = unsafe.Sizeof(hchan{})
```
これは単に`hchan`構造体のサイズをそのまま使用していました。このサイズが`maxAlign`の倍数でない場合、その直後に続くメモリ領域（チャネルのバッファなど）が適切にアライメントされない可能性がありました。

**変更後:**
```go
hchanSize = unsafe.Sizeof(hchan{}) + uintptr(-int(unsafe.Sizeof(hchan{}))&(maxAlign-1))
```
この新しい計算式は、`hchan`構造体のサイズを`maxAlign`の倍数に「切り上げ」るためのものです。

-   `unsafe.Sizeof(hchan{})`: `hchan`構造体の実際のサイズ（バイト単位）を取得します。
-   `int(unsafe.Sizeof(hchan{}))`: `hchan`構造体のサイズを`int`型にキャストします。
-   `-int(unsafe.Sizeof(hchan{}))`: サイズの負の値を取ります。
-   `& (maxAlign - 1)`: ここがアライメントの肝です。
    -   `maxAlign`は通常8です。したがって、`maxAlign - 1`は7（バイナリで`0111`）になります。
    -   任意の数値`X`に対して、`X & (N-1)`は`X`を`N`で割った余り（`X % N`）を計算します。ただし、これは`N`が2のべき乗の場合にのみ機能します。`maxAlign`は2のべき乗（8 = 2^3）なので、このトリックが使えます。
    -   したがって、`(-int(unsafe.Sizeof(hchan{}))) & (maxAlign-1)`は、`hchan`構造体のサイズを`maxAlign`で割った余りの負の値を計算します。
    -   例: `hchanSize`が28バイト（`maxAlign`=8）の場合、`28 % 8 = 4`。
        -   `-28`の2の補数表現は`...11100100`。
        -   `7`は`00000111`。
        -   `(-28) & 7`は`...11100100 & 00000111 = 00000100`、つまり`4`になります。
    -   この結果（`4`）は、`hchan`構造体のサイズを`maxAlign`の倍数にするために必要な「追加のバイト数」を示します。
-   `uintptr(...)`: 計算結果を`uintptr`型にキャストします。
-   `unsafe.Sizeof(hchan{}) + ...`: 最後に、元の`hchan`構造体のサイズにこの追加のバイト数を加算することで、`hchanSize`が`maxAlign`の倍数に切り上げられます。

この計算により、`hchanSize`は常に`maxAlign`の倍数となり、`hchan`構造体の直後に続くメモリ領域が適切にアライメントされることが保証されます。

また、`// TODO: make hchan.buf an unsafe.Pointer, not a *uint8` のコメントが `// TODO(khr): make hchan.buf an unsafe.Pointer, not a *uint8` に変更されています。これは機能的な変更ではなく、TODOの担当者を示唆するマイナーなコメントの修正です。

### `src/pkg/runtime/chan.h` の変更

**変更前:**
```c
#ifndef GOARCH_amd64
	uint32	pad;			// ensures proper alignment of the buffer that follows Hchan in memory
#endif
```
このコードブロックは、`GOARCH_amd64`（AMD64アーキテクチャ）以外の場合に、`hchan`構造体内に`pad`という32ビットのパディングフィールドを明示的に含めていました。このフィールドの目的は、`hchan`構造体の直後に続くチャネルバッファがメモリ内で適切にアライメントされるようにすることでした。これはアーキテクチャ固有のハックであり、`amd64`では不要でした。

**変更後:**
このブロック全体が削除されています。

`chan.go`での`hchanSize`の計算方法が汎用的なアライメント切り上げロジックに変更されたため、`chan.h`で定義されていたシステム固有の`pad`フィールドは不要になりました。これにより、コードが簡素化され、異なるアーキテクチャ間でのチャネルのメモリレイアウトの整合性が向上しました。

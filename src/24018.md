# [インデックス 24018] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）とスタックメモリ管理の間の重要な同期問題を解決するためのものです。具体的には、GCが実行されている最中にスタックスパンが解放されることで発生する可能性のあるデータ競合と、それに伴う未初期化オブジェクトの誤ったマーキングを防ぐための変更が導入されています。

## コミット

```
commit d57056ba2619ed75a8b1c0255d318ac1dc9a1bb1
Author: Austin Clements <austin@google.com>
Date:   Mon Jun 22 10:24:50 2015 -0400

    runtime: don't free stack spans during GC
    
    Memory for stacks is manually managed by the runtime and, currently
    (with one exception) we free stack spans immediately when the last
    stack on a span is freed. However, the garbage collector assumes that
    spans can never transition from non-free to free during scan or mark.
    This disagreement makes it possible for the garbage collector to mark
    uninitialized objects and is blocking us from re-enabling the bad
    pointer test in the garbage collector (issue #9880).
    
    For example, the following sequence will result in marking an
    uninitialized object:
    
    1. scanobject loads a pointer slot out of the object it's scanning.
       This happens to be one of the special pointers from the heap into a
       stack. Call the pointer p and suppose it points into X's stack.
    
    2. X, running on another thread, grows its stack and frees its old
       stack.
    
    3. The old stack happens to be large or was the last stack in its
       span, so X frees this span, setting it to state _MSpanFree.
    
    4. The span gets reused as a heap span.
    
    5. scanobject calls heapBitsForObject, which loads the span containing
       p, which is now in state _MSpanInUse, but doesn't necessarily have
       an object at p. The not-object at p gets marked, and at this point
       all sorts of things can go wrong.
    
    We already have a partial solution to this. When shrinking a stack, we
    put the old stack on a queue to be freed at the end of garbage
    collection. This was done to address exactly this problem, but wasn't
    a complete solution.
    
    This commit generalizes this solution to both shrinking and growing
    stacks. For stacks that fit in the stack pool, we simply don't free
    the span, even if its reference count reaches zero. It's fine to reuse
    the span for other stacks, and this enables that. At the end of GC, we
    sweep for cached stack spans with a zero reference count and free
    them. For larger stacks, we simply queue the stack span to be freed at
    the end of GC. Ideally, we would reuse these large stack spans the way
    we can small stack spans, but that's a more invasive change that will
    have to wait until after the freeze.
    
    Fixes #11267.
```

## 元コミット内容

このコミットは、GoランタイムがGC中にスタックスパンを即座に解放しないように変更します。これにより、GCが未初期化オブジェクトを誤ってマークする可能性のある競合状態が解消され、GC内の不良ポインタテスト（issue #9880）を再有効化できるようになります。

変更の主な内容は以下の通りです。

1.  **スタックスパンの解放タイミングの変更**: GCがアクティブな間は、スタックスパンの即時解放を停止し、GC終了時まで解放を遅延させます。
2.  **スタックプール内のスパン管理の改善**: スタックプールに収まる小さなスタックについては、参照カウントがゼロになっても即座に解放せず、GC終了時にまとめて解放します。これにより、スパンの再利用が容易になります。
3.  **大きなスタックのスパン管理**: 大きなスタックについては、GC終了時に解放されるキューに追加されます。
4.  **`shrinkfinish`関数のリファクタリング**: `freeStackSpans`に名称変更され、GC終了時のスタックスパン解放ロジックが統合・改善されました。
5.  **`mheap.go`における`MSpan`状態遷移の制約の明文化**: GC中に`MSpan`が`stack`または`in-use`から`free`に遷移してはならないという重要な制約がコメントとして追加されました。

## 変更の背景

Goランタイムのガベージコレクタ（GC）は、メモリのスキャンおよびマークフェーズ中に、メモリ領域（スパン、`MSpan`）の状態が「非解放（non-free）」から「解放済み（free）」に変化しないことを前提として動作していました。しかし、Goランタイムのスタック管理は、スタックが解放されると、そのスタックが属するスパンを即座に解放する挙動を持っていました。この前提の不一致が、GCの正確性に深刻な問題を引き起こしていました。

具体的には、GCがオブジェクトをスキャンしている最中に、そのオブジェクトが指すスタックが別のゴルーチンによって解放され、そのスタックが属するスパンが解放済みとなり、さらに別のヒープオブジェクトに再利用されるという競合状態が発生する可能性がありました。この状況下でGCが元のポインタを追跡しようとすると、既にヒープとして再利用された領域をスタックの一部として誤って解釈し、未初期化のメモリをマークしてしまう恐れがありました。これは、GCの健全性を損なうだけでなく、Goのメモリ安全性保証を危うくするものでした。

この問題は、特にissue #9880で言及されている「不良ポインタテスト」の再有効化を妨げていました。このテストは、GCが不正なポインタをマークしないことを確認するための重要なテストであり、この問題が解決されない限り、テストを有効にすることができませんでした。

以前にも、スタックの縮小時に古いスタックをGC終了時まで解放を遅延させる部分的な解決策が導入されていましたが、これは完全な解決には至っていませんでした。このコミットは、この問題をより包括的に解決し、GCの堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念に関する知識が必要です。

1.  **ガベージコレクション (GC)**: GoのGCは、不要になったメモリを自動的に回収する仕組みです。主に「マーク＆スイープ」アルゴリズムをベースにしており、オブジェクトグラフを辿って到達可能なオブジェクトをマークし、マークされなかったオブジェクトを解放します。GoのGCは並行（concurrent）かつ低遅延（low-latency）を目指しており、GCのマークフェーズ中にアプリケーションの実行が完全に停止する「Stop-The-World (STW)」時間は最小限に抑えられています。
    *   **GCフェーズ**: GCは複数のフェーズに分かれます。
        *   `_GCoff`: GCがアクティブでない状態。この期間にスイープ（sweep）が行われます。
        *   `_GCmark`: オブジェクトグラフを辿って到達可能なオブジェクトをマークするフェーズ。
        *   `_GCscan`: マークされたオブジェクトのポインタをスキャンするフェーズ。
    *   **`scanobject`**: GCのマークフェーズ中にオブジェクトをスキャンし、そこに含まれるポインタを識別してマークする関数。
    *   **`heapBitsForObject`**: 特定のメモリアドレスがヒープオブジェクトの一部であるかどうか、およびそのオブジェクトのメタデータ（ポインタ情報など）を取得するための関数。

2.  **メモリ管理と`MSpan`**: Goランタイムは、メモリを`mheap`という構造で管理しています。`mheap`は、メモリを`MSpan`と呼ばれる連続したページ群に分割して管理します。
    *   **`MSpan`**: 連続したメモリページの塊を表す構造体。`MSpan`は様々な状態を持ちます。
        *   `_MSpanInUse`: ヒープオブジェクトのために割り当てられているスパン。
        *   `_MSpanStack`: ゴルーチンのスタックのために割り当てられているスパン。
        *   `_MSpanFree`: どの用途にも割り当てられていない、解放済みのスパン。
    *   **`mHeap_FreeStack`**: スタックとして使用されていた`MSpan`を解放し、`mheap`のフリーリストに戻す関数。

3.  **ゴルーチンスタック管理**: Goのゴルーチンは、可変サイズのスタックを使用します。必要に応じてスタックは自動的に拡大・縮小されます。
    *   **スタックの拡大・縮小**: ゴルーチンが関数呼び出しを深く行うとスタックは拡大し、関数から戻るとスタックは縮小することがあります。
    *   **`stackpool`**: 小さなスタックを効率的に再利用するためのプール。
    *   **`stackfree`**: スタックを解放する関数。
    *   **`copystack`**: スタックの拡大・縮小時に、古いスタックの内容を新しいスタックにコピーする関数。

4.  **`gclinkptr`**: GCがポインタを扱う際に使用する型。

5.  **`SudoG`**: Goランタイム内部で使用される、ゴルーチン（`g`）へのポインタを保持する構造体。GCが`SudoG`をスキャンする際に、その`elem`フィールドが指すスタック上のポインタをマークしようとします。

## 技術的詳細

このコミットの核心は、GCの「マーク」フェーズ中に`MSpan`の状態が`_MSpanStack`または`_MSpanInUse`から`_MSpanFree`に遷移することを防ぐことです。GCは、ポインタを読み取った後、そのポインタが指すメモリが有効なオブジェクトの一部であるかどうかを判断するために、そのメモリが属する`MSpan`の状態を参照します。もしGCがポインタを読み取った直後にその`MSpan`が解放され、別の用途（特にヒープ）に再利用されてしまうと、GCは古いポインタを誤って解釈し、未初期化のメモリをマークしてしまう可能性があります。

この問題を解決するために、コミットは以下の主要な変更を導入しています。

1.  **`MSpan`状態遷移の制約の明文化 (`src/runtime/mheap.go`)**:
    `mheap.go`に新しいコメントブロックが追加され、GCがアクティブな間（`gcphase != _GCoff`）は、`MSpan`が`_MSpanStack`または`_MSpanInUse`から`_MSpanFree`に遷移してはならないという制約が明確に記述されました。これは、並行GCがポインタを読み取り、その後そのスパンを検索する可能性があるため、スパンの状態は単調でなければならないという原則に基づいています。

2.  **スタックスパン解放の遅延 (`src/runtime/stack1.go`)**:
    *   **`stackpoolfree`関数の変更**: 以前は、スタックプール内のスパンの参照カウント（`s.ref`）がゼロになると即座に`mHeap_FreeStack`を呼び出してスパンを解放していました。このコミットでは、この条件に`gcphase == _GCoff`（GCがアクティブでない状態、つまりスイープ中）というチェックが追加されました。これにより、GCがアクティブな間は、参照カウントがゼロになってもスパンは即座に解放されず、スタックプール内にキャッシュされたままになります。
        *   この変更の理由として、GCが`SudoG`をスキャンし、その`elem`ポインタをマークする前にスタックがコピーされ、古いスタックが解放され、そのスパンが`_MSpanFree`になり、その後GCがそのポインタをマークしようとすると失敗するというシナリオが詳細に説明されています。解放を遅延させることで、この競合状態を防ぎます。
    *   **`stackfree`関数の変更**: 大きなスタック（スタックプールに収まらないもの）を解放する`stackfree`関数も同様に変更されました。GCがアクティブでない場合は即座に解放しますが、GCがアクティブな場合は、`stackFreeQueue`という新しいキューにスパンを追加し、GC終了時まで解放を遅延させます。
        *   `stackFreeQueue`は、以前の`stackfreequeue`（`stack`型）から`mspan`型に変更され、`mSpanList`として管理されるようになりました。これにより、より汎用的なスパンのリスト管理が可能になります。

3.  **`copystack`関数の簡素化 (`src/runtime/stack1.go`)**:
    スタックの拡大・縮小時に`copystack`が呼び出されます。以前は、スタックの拡大時には即座に解放し、縮小時にはキューに入れるという複雑なロジックがありました。このコミットでは、`stackfree(old, oldsize)`を常に呼び出すように簡素化されました。`stackfree`関数自体がGCフェーズに応じて解放を遅延させるロジックを持つようになったため、`copystack`側で特別な処理をする必要がなくなりました。

4.  **`shrinkfinish`から`freeStackSpans`への変更と機能拡張 (`src/runtime/mgc.go`, `src/runtime/stack1.go`)**:
    *   `gcMark`関数内で呼び出されていた`shrinkfinish()`が`freeStackSpans()`に置き換えられました。
    *   `freeStackSpans()`は、GC終了時に呼び出され、以下の2つの処理を行います。
        *   `stackpool`内のすべてのスタックプールをスキャンし、参照カウントがゼロになった（つまり、どのスタックにも使用されていない）スパンを解放します。
        *   `stackFreeQueue`にキューイングされていたすべてのスタックスパンを解放します。
    *   これにより、GC中に解放が遅延されたすべてのスタックスパンが、GCの安全な終了フェーズでまとめて解放されるようになります。

この変更により、GCのマークフェーズ中にスタックメモリが予期せず解放され、ヒープに再利用されるという競合状態が完全に排除されます。これにより、GCの正確性が保証され、issue #9880で言及されていた「不良ポインタテスト」を安全に再有効化できるようになります。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更

*   `gcMark`関数はGCのマークフェーズの主要なエントリポイントです。以前は`shrinkfinish()`を呼び出していましたが、このコミットで`freeStackSpans()`に置き換えられました。
*   `freeStackSpans()`は、GCのマークフェーズが完了した後、GCの終了処理の一部として呼び出されます。これにより、GC中に遅延されていたスタックスパンの解放が、GCが安全な状態になった後に行われることが保証されます。
*   追加された`TODO`コメント（issue #11465）は、`freeStackSpans()`の呼び出しをSTW（Stop-The-World）フェーズから外し、GCサイクルが完了するまでブロックするだけで済むようにする将来的な最適化の可能性を示唆しています。これは、STW時間をさらに短縮するための検討事項です。

### `src/runtime/mheap.go` の変更

*   `MSpan`の状態遷移に関する新しいコメントブロックは、Goランタイムのメモリ管理における重要な不変条件を明文化しています。
*   特に重要なのは、「GC中（`gcphase != _GCoff`）は、スパンが`stack`または`in-use`から`free`に遷移してはならない」という制約です。これは、並行GCがポインタを読み取った後、そのポインタが指すスパンの状態をルックアップする際に、スパンの状態が突然変化してGCの判断を誤らせることを防ぐためです。この制約は、このコミットの変更の根本的な理由を説明しています。

### `src/runtime/stack1.go` の変更

*   **`stackFreeQueue`の導入**: 以前は`stackfreequeue`という`stack`型の変数で解放待ちのスタックを管理していましたが、`mspan`型の`stackFreeQueue`に置き換えられ、`mSpanList`として初期化されるようになりました。これにより、より汎用的な`MSpan`のリストとして解放待ちのスパンを管理できるようになります。
*   **`stackpoolfree`の変更**:
    *   `if s.ref == 0`という条件に`gcphase == _GCoff`が追加されました。これは、スタックプール内のスパンが完全に空になった場合でも、GCがアクティブな間は即座に解放せず、GC終了時まで待機させることを意味します。
    *   追加された詳細なコメントは、GC中に即座に解放すると発生する可能性のある競合状態（`SudoG.elem`ポインタの誤ったマーキング）を具体的に説明しており、この変更の必要性を強調しています。
*   **`stackfree`の変更**:
    *   大きなスタックを解放する`stackfree`関数も、`gcphase == _GCoff`の場合にのみ`mHeap_FreeStack`を即座に呼び出すように変更されました。
    *   GCがアクティブな場合は、`stackpoolmu`ロックを取得し、`mSpanList_Insert(&stackFreeQueue, s)`を呼び出して、スパンを`stackFreeQueue`に追加します。これにより、大きなスタックのスパンもGC終了時まで解放が遅延されます。
    *   ここにも`TODO`コメント（issue #11466）があり、将来的には小さなスタックスパンと同様に、大きなスタックスパンも再利用できるようにする検討が示唆されています。
*   **`copystack`の簡素化**:
    *   スタックの拡大・縮小時に呼び出される`copystack`関数から、スタックの解放に関する複雑な条件分岐が削除されました。
    *   `stackfree(old, oldsize)`が常に呼び出されるようになり、解放の遅延ロジックは`stackfree`関数内部に一元化されました。これにより、コードがよりシンプルで理解しやすくなりました。
*   **`shrinkfinish`から`freeStackSpans`への変更**:
    *   `shrinkfinish`関数は`freeStackSpans`に名称変更され、その実装が大幅に更新されました。
    *   新しい`freeStackSpans`は、まず`stackpool`内のすべてのスタックプールをイテレートし、参照カウントがゼロのスパン（`s.ref == 0`）を`mHeap_FreeStack`で解放します。これは、GC中に解放が遅延されていた小さなスタックスパンを処理します。
    *   次に、`stackFreeQueue`にキューイングされていたすべてのスパンをイテレートし、それらも`mHeap_FreeStack`で解放します。これは、GC中に解放が遅延されていた大きなスタックスパンを処理します。
    *   これらの処理はすべて`stackpoolmu`ロックの下で行われ、スレッドセーフティが確保されています。

これらの変更により、GoランタイムはGCのマークフェーズ中にスタックスパンが解放されることによる競合状態を効果的に回避し、GCの堅牢性と正確性を大幅に向上させています。

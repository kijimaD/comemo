# [インデックス 26123] ファイルの概要

このコミットは、Goの`net/http`パッケージにおけるHTTP/2の実装を更新し、特に`http.Response.Body`が閉じられた後にそのボディを読み取ろうとした際の挙動に関するテストを追加・修正しています。主な変更は、`src/net/http/clientserver_test.go`に新しいテストケースが追加され、`src/net/http/h2_bundle.go`内の`http2pipe`構造体とその関連メソッドが修正された点です。

## コミット

このコミットは、`net/http`パッケージにバンドルされているHTTP/2実装を更新し、`http.Response.Body`が`Close()`された後にそのボディを読み取ろうとした場合のテストを追加します。これにより、`Body.Close()`が呼び出された後に`Body.Read()`が予期せず成功する可能性のあるバグ（Issue 13648）が修正されます。具体的には、`http2pipe`に`breakErr`という新しいエラー状態を導入し、即座に読み取りを中断させるメカニズムを追加しています。

## 変更の背景

この変更の背景には、Goの`net/http`パッケージが提供する`http.Response.Body`の挙動に関する潜在的な問題がありました。通常、`io.ReadCloser`インターフェースを実装する`Body`は、読み取り操作（`Read`）とリソース解放操作（`Close`）を提供します。期待される挙動としては、`Close()`が呼び出された後には、それ以降の`Read()`呼び出しはエラーを返すか、少なくともデータが読み取られないべきです。

しかし、HTTP/2の実装において、`Body.Close()`が呼び出された後でも、内部バッファにデータが残っている場合や、エラー状態が適切に伝播されない場合に、`Body.Read()`が成功してしまう可能性がありました。これは、アプリケーションがリソースを適切に解放したと認識しているにもかかわらず、実際にはデータが読み取られ続けてしまうという、予期せぬ動作やリソースリーク、あるいはデータ破損につながる可能性を秘めていました。

Issue 13648は、この特定のシナリオ、すなわち`http.Response.Body`を閉じた後に読み取ろうとした際の挙動の不整合を指摘していました。このコミットは、この問題を解決し、`Body.Close()`が呼び出された後には、それ以降の`Read()`呼び出しが確実にエラーを返すようにするためのものです。これにより、`net/http`パッケージの堅牢性と予測可能性が向上します。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびネットワークプログラミングに関する知識が役立ちます。

*   **Goの`net/http`パッケージ**: Go言語でHTTPクライアントおよびサーバーを構築するための標準ライブラリです。HTTPリクエストの送信、レスポンスの受信、HTTPサーバーの構築など、HTTP通信の基本的な機能を提供します。
*   **HTTP/2プロトコル**: HTTP/1.1の後継となるプロトコルで、多重化（複数のリクエスト/レスポンスを単一のTCP接続で並行して処理）、ヘッダー圧縮、サーバープッシュなどの機能により、パフォーマンスの向上を目指しています。Goの`net/http`パッケージは、HTTP/2を透過的にサポートしています。`h2_bundle.go`は、このHTTP/2プロトコルの実装の一部をバンドルしています。
*   **`io.Reader`インターフェース**: Go言語におけるデータの読み込み操作を抽象化するインターフェースです。`Read([]byte) (n int, err error)`メソッドを持ち、バイトスライスにデータを読み込み、読み込んだバイト数とエラーを返します。`http.Response.Body`はこのインターフェースを実装しており、レスポンスボディのデータを読み取るために使用されます。
*   **`io.Closer`インターフェース**: リソースの解放操作を抽象化するインターフェースです。`Close() error`メソッドを持ち、ファイルハンドル、ネットワーク接続、HTTPレスポンスボディなどのリソースを閉じます。`http.Response.Body`もこのインターフェースを実装しており、レスポンスボディの読み取りが完了した際や、不要になった際に呼び出され、関連するリソースを解放します。
*   **`http.Response.Body`のライフサイクル**: HTTPクライアントがレスポンスを受信すると、そのボディは`io.ReadCloser`として提供されます。アプリケーションは`Read`メソッドを使ってボディの内容を読み取り、読み取りが完了したら（またはエラーが発生したら）`Close`メソッドを呼び出してリソースを解放する必要があります。`Close`を呼び出さないと、ネットワーク接続が適切に閉じられず、リソースリークにつながる可能性があります。
*   **`sync.Mutex`と`sync.Cond`**: Go言語における並行処理の同期プリミティブです。
    *   `sync.Mutex`: 共有リソースへのアクセスを排他的に制御するためのロックメカニズムです。複数のゴルーチンが同時にリソースにアクセスするのを防ぎます。
    *   `sync.Cond`: 特定の条件が満たされるまでゴルーチンを待機させたり、条件が満たされたときに待機中のゴルーチンを再開させたりするためのメカニズムです。`sync.Mutex`と組み合わせて使用され、より複雑な同期パターンを実装します。`http2pipe`では、データの読み書きの同期に利用されています。
*   **`io.Pipe`**: Goの標準ライブラリ`io`パッケージにある、メモリ内で`io.Reader`と`io.Writer`を接続するパイプの実装です。`io.PipeReader`と`io.PipeWriter`のペアで構成され、`Writer`に書き込まれたデータが`Reader`から読み取れるようになります。`http2pipe`は、この`io.Pipe`に似た概念で、HTTP/2ストリームのボディデータを扱うために内部的に使用されるバッファリングメカニズムです。ただし、`io.Pipe`が常にバッファなしであるのに対し、`http2pipe`はより柔軟なバッファリングを可能にするように設計されています。

## 技術的詳細

このコミットの技術的な詳細な変更点は、主に`src/net/http/h2_bundle.go`内の`http2pipe`構造体とその関連メソッド、そして`src/net/http/clientserver_test.go`に追加されたテストにあります。

### `http2pipe`構造体の変更

`http2pipe`は、HTTP/2のレスポンスボディを扱うための内部的なパイプ実装です。このコミットでは、`http2pipe`構造体に新しいフィールド`breakErr error`が追加されました。

```go
type http2pipe struct {
	mu       sync.Mutex
	c        sync.Cond // c.L lazily initialized to &p.mu
	b        http2pipeBuffer
	err      error         // read error once empty. non-nil means closed.
	breakErr error         // immediate read error (caller doesn't see rest of b)
	donec    chan struct{} // closed on error
	readFn   func()        // optional code to run in Read before error
}
```

*   **`err`**: 以前から存在し、パイプが空になった後に返されるエラーを保持します。これは、ストリームの終了や通常のクローズによって設定されるエラーです。
*   **`breakErr`**: 新しく追加されたフィールドで、`http2pipe`が閉じられた際に、バッファに残っているデータがあっても即座に読み取りを中断し、このエラーを返すためのものです。これは、`Body.Close()`が呼び出された直後に`Body.Read()`がエラーを返すことを保証するために導入されました。

### `http2pipe.Read`メソッドの変更

`Read`メソッドは、`http2pipe`からデータを読み取るためのものです。このメソッドに`breakErr`をチェックするロジックが追加されました。

```go
func (p *http2pipe) Read(d []byte) (n int, err error) {
	p.mu.Lock()
	defer p.mu.Unlock()
	if p.c.L == nil {
		p.c.L = &p.mu
	}
	for {
		if p.breakErr != nil { // ★追加されたロジック
			return 0, p.breakErr
		}
		if p.b.Len() > 0 {
			return p.b.Read(d)
		}
		// ... (既存の待機ロジック) ...
	}
}
```

この変更により、`breakErr`が`nil`でない場合、`Read`メソッドはバッファにデータが残っていても、即座に`0`バイトと`breakErr`を返します。これにより、`Body.Close()`が呼び出された後に`Read()`が試みられた際に、すぐにエラーが返されるようになります。

### `http2pipe.CloseWithError`と`BreakWithError`メソッドの変更/追加

既存の`CloseWithError`メソッドが修正され、新しい`BreakWithError`メソッドが追加されました。また、これらのメソッドが内部的に使用する`closeWithError`というヘルパー関数が導入されました。

```go
// CloseWithError は、パイプが空になった後に返されるエラーを設定します。
func (p *http2pipe) CloseWithError(err error) { p.closeWithError(&p.err, err, nil) }

// BreakWithError は、次のRead呼び出し（現在ブロックされているReadも含む）が
// 未読データがあっても、提供されたエラーを即座に返すようにします。
func (p *http2pipe) BreakWithError(err error) { p.closeWithError(&p.breakErr, err, nil) }

// closeWithErrorAndCode はCloseWithErrorに似ていますが、エラーを返す前に
// 呼び出し元のゴルーチンで実行するコードも設定できます。
func (p *http2pipe) closeWithErrorAndCode(err error, fn func()) { p.closeWithError(&p.err, err, fn) }

func (p *http2pipe) closeWithError(dst *error, err error, fn func()) {
	if err == nil {
		panic("err must be non-nil")
	}
	p.mu.Lock()
	defer p.mu.Unlock()
	if p.c.L == nil {
		p.c.L = &p.mu
	}
	defer p.c.Signal()
	if *dst != nil { // ★変更: p.err ではなく *dst をチェック
		return
	}
	p.readFn = fn
	*dst = err // ★変更: p.err ではなく *dst にエラーを設定
	p.closeDoneLocked()
}
```

*   **`BreakWithError(err error)`**: この新しいメソッドは、`http2pipe`を即座に「ブレーク」状態にします。これは、`breakErr`フィールドにエラーを設定し、`Read`メソッドがすぐにそのエラーを返すようにします。これは、`http.Response.Body.Close()`が呼び出されたときに、残りのボディデータを無視して即座に読み取りを停止させるために使用されます。
*   **`closeWithError`ヘルパー関数**: `CloseWithError`と`BreakWithError`の両方で共通のロジックをカプセル化するために導入されました。`dst *error`引数により、`p.err`または`p.breakErr`のどちらにエラーを設定するかを柔軟に選択できるようになりました。

### `http2pipe.Err`メソッドの変更

`Err`メソッドは、設定されたエラーを返します。このメソッドも`breakErr`を優先するように変更されました。

```go
func (p *http2pipe) Err() error {
	p.mu.Lock()
	defer p.mu.Unlock()
	if p.breakErr != nil { // ★追加されたロジック
		return p.breakErr
	}
	return p.err
}
```

これにより、`BreakWithError`が呼び出された場合、そのエラーが`Err()`によって優先的に報告されるようになります。

### `http2pipe.Done`メソッドの変更

`Done`メソッドは、パイプが閉じられたときにクローズされるチャネルを返します。このメソッドも`breakErr`を考慮するように変更されました。

```go
func (p *http2pipe) Done() <-chan struct{} {
	p.mu.Lock()
	defer p.mu.Unlock()
	if p.donec == nil {
		p.donec = make(chan struct{})
		if p.err != nil || p.breakErr != nil { // ★変更: p.breakErr も考慮
			p.closeDoneLocked()
		}
	}
	return p.donec
}
```

### `http2transportResponseBody.Close()`メソッドの変更

`http2transportResponseBody`は、HTTP/2のレスポンスボディの実装です。その`Close()`メソッドが、`http2pipe`の新しい`BreakWithError`メソッドを使用するように変更されました。

```go
var http2errClosedResponseBody = errors.New("http2: response body closed") // ★追加

func (b http2transportResponseBody) Close() error {
	cs := b.cs
	if cs.bufPipe.Err() != io.EOF {
		// ... (既存のストリームリセットロジック) ...
	}
	cs.bufPipe.BreakWithError(http2errClosedResponseBody) // ★変更
	return nil
}
```

*   **`http2errClosedResponseBody`**: `http2: response body closed`という新しいエラーが定義されました。
*   `cs.bufPipe.BreakWithError(http2errClosedResponseBody)`: `http2transportResponseBody.Close()`が呼び出されると、内部の`http2pipe`に対して`BreakWithError`が呼び出され、`http2errClosedResponseBody`が設定されます。これにより、`Body.Close()`が呼び出された後、それ以降の`Body.Read()`は即座にこのエラーを返すことが保証されます。

## コアとなるコードの解説

### `http2pipe`構造体への`breakErr`の追加

`http2pipe`構造体に`breakErr error`フィールドが追加されました。これは、`http.Response.Body.Close()`が呼び出された際に、`http2pipe`の読み取りを即座に中断させるための特別なエラーを保持します。従来の`err`フィールドは、パイプが空になった後に返されるエラー（例えば、ストリームの正常終了や、読み取り中に発生したエラー）を意図していましたが、`breakErr`はバッファにデータが残っていても強制的に読み取りを停止させるためのものです。

### `http2pipe.Read`メソッドにおける`breakErr`のチェック

`http2pipe.Read`メソッドのループの先頭に`if p.breakErr != nil { return 0, p.breakErr }`というチェックが追加されました。これにより、`breakErr`が設定されている場合、`Read`はバッファにデータがあるかどうかに関わらず、即座に`0`バイトと`breakErr`を返します。これは、`Body.Close()`が呼び出された後に`Read()`が試みられた際に、すぐにエラーが返されるという期待される挙動を保証します。

### `BreakWithError`メソッドの導入と`closeWithError`ヘルパー関数

*   **`BreakWithError(err error)`**: この新しい公開メソッドは、`http2pipe`を「ブレーク」状態にするための主要なインターフェースです。内部的には、新しく導入された`closeWithError`ヘルパー関数を呼び出し、`p.breakErr`フィールドに指定されたエラーを設定します。これにより、`Read`メソッドが即座にエラーを返すようになります。
*   **`closeWithError(dst *error, err error, fn func())`**: このヘルパー関数は、`CloseWithError`、`BreakWithError`、`closeWithErrorAndCode`の共通ロジックをカプセル化します。`dst *error`引数を受け取ることで、`p.err`または`p.breakErr`のどちらのフィールドにエラーを設定するかを動的に選択できるようになりました。これにより、コードの重複が削減され、エラー設定ロジックが一元化されました。また、`panic("err must be non-nil")`というチェックが追加され、`nil`エラーでこれらのメソッドが呼び出されることを防ぎます。

### `http2pipe.Err`メソッドにおける`breakErr`の優先

`http2pipe.Err`メソッドは、`p.breakErr`が設定されている場合はそれを優先して返すように変更されました。これは、`BreakWithError`が呼び出された場合、そのエラーがパイプの現在のエラー状態として即座に反映されることを意味します。

### `http2pipe.Done`メソッドにおける`breakErr`の考慮

`http2pipe.Done`メソッドは、`p.err`だけでなく`p.breakErr`も考慮して`donec`チャネルを閉じるように変更されました。これにより、`breakErr`によってパイプが閉じられた場合でも、`Done`チャネルが適切にシグナルを送るようになります。

### `http2transportResponseBody.Close()`での`BreakWithError`の利用

`http2transportResponseBody.Close()`メソッドは、`http.Response.Body.Close()`が呼び出されたときに実行されるロジックを含んでいます。このメソッド内で、`cs.bufPipe.BreakWithError(http2errClosedResponseBody)`が呼び出されるようになりました。
*   `http2errClosedResponseBody`という新しいエラー定数が定義され、`Body`が閉じられたことを示す具体的なエラーとして使用されます。
*   `BreakWithError`を呼び出すことで、`http2pipe`は即座に「ブレーク」状態になり、それ以降の`Read`呼び出しは`http2errClosedResponseBody`を返します。これにより、`Body.Close()`後の`Read()`が確実に失敗するという要件が満たされます。

### `clientserver_test.go`へのテスト追加

`TestResponseBodyReadAfterClose_h1`と`TestResponseBodyReadAfterClose_h2`という新しいテストが追加されました。これらのテストは、HTTP/1.1とHTTP/2の両方で、以下のシナリオを検証します。
1.  HTTPリクエストを送信し、レスポンスを受信する。
2.  `res.Body.Close()`を呼び出してレスポンスボディを閉じる。
3.  閉じた後に`ioutil.ReadAll(res.Body)`を呼び出して、ボディからデータを読み取ろうとする。
4.  `ioutil.ReadAll`が空のデータと非`nil`のエラーを返すことをアサートする。

このテストの追加により、`Body.Close()`後の`Read()`がエラーを返すという修正された挙動が、将来の変更によって壊れないことが保証されます。

これらの変更は、`http.Response.Body`の`Close()`操作のセマンティクスを明確にし、アプリケーションがより予測可能で堅牢なコードを書けるようにするために重要です。

# [インデックス 25759] ファイルの概要

このコミットは、Go言語のコマンドラインツール `cmd/go` がmacOS (OS X) 上で実行可能ファイルからビルドIDを読み込む際の信頼性を向上させるための修正です。特に、Mach-O形式の実行可能ファイルにおいて、ビルドIDの検出ロジックを強化しています。

## 元コミット内容

このコミットは、macOS (当時はOS X) 上でGoの実行可能ファイルからビルドIDを読み込む際の不具合を修正します。具体的には、以下の2つのアプローチを組み合わせてビルドIDの検出を強化しています。

1.  **Mach-Oファイルのパース**: Mach-Oファイルフォーマットを解析し、`__text`セクションを特定してその中からビルドIDを探す、より正確な方法を導入しました。
2.  **読み込みサイズの増加**: 実行可能ファイルの先頭から読み込むデータ量を8KBから32KBに増やし、その範囲内でもビルドIDをスキャンするようにしました。これは、`__text`セクションの名前が将来変更される可能性への懸念と、より堅牢な検出のための「ベルトとサスペンダー」的なアプローチです。

この修正は、Issue #12327 に対応するものです。

## 変更の背景

Goのビルドシステムでは、ビルドされたバイナリに一意の「ビルドID」を埋め込みます。このビルドIDは、ビルドキャッシュの最適化や、特定のバイナリがどのソースコードから生成されたかを識別するために使用されます。

しかし、macOS (OS X) の実行可能ファイル形式であるMach-Oでは、ビルドIDが常に予測可能な位置に配置されるとは限りませんでした。特に、以前の実装では実行可能ファイルの先頭から固定の小さなサイズ（8KB）を読み込み、その範囲内でビルドIDのパターンを検索していました。Mach-Oファイルでは、`__text`セクション（実行可能コードが格納される場所）の前に任意の量のメタデータや他のセクションが存在する可能性があり、ビルドIDがこの8KBの範囲外に配置されることがありました。これにより、`cmd/go`がGoバイナリのビルドIDを正しく読み取れないという問題が発生していました。

このコミットは、この信頼性の問題を解決し、macOS上でのGoツールの動作をより堅牢にすることを目的としています。

## 前提知識の解説

### Go Build ID (ビルドID)

GoのビルドIDは、Goプログラムのビルド時に生成される一意の識別子です。これは通常、`actionID/contentID` の形式で構成されます。
*   **`actionID`**: ビルドアーティファクトを生成するために使用された入力（ソースコード、Goバージョン、ビルド設定、依存関係のビルドIDなど）のハッシュです。ビルドキャッシュが再ビルドを避けるために使用します。
*   **`contentID`**: ビルドアクションの実際の出力（コンパイルされたアーカイブや最終的な実行可能ファイル）のハッシュです。

ビルドIDは、Goのビルドキャッシュを効率的に機能させ、依存関係の変更を正確に追跡するために不可欠です。`go tool buildid <file>` コマンドで確認できます。

### Mach-O (Mach Object) ファイルフォーマット

Mach-Oは、macOS、iOS、watchOS、tvOSなどのApple製オペレーティングシステムで使用される実行可能ファイル、オブジェクトコード、共有ライブラリ、ダイナミックライブラリ、およびコアダンプのファイルフォーマットです。ELF (Executable and Linkable Format) やPE (Portable Executable) と同様に、プログラムの構造を定義します。

Mach-Oファイルは、以下の主要な部分で構成されます。
*   **ヘッダ (Header)**: ファイルの基本的な情報（CPUアーキテクチャ、ファイルタイプなど）を含みます。
*   **ロードコマンド (Load Commands)**: オペレーティングシステムがプログラムをメモリにロードする方法を記述します。これには、セグメントの定義、共有ライブラリの依存関係などが含まれます。
*   **セグメント (Segments)**: 実行可能コードやデータが格納されるメモリ領域を定義します。各セグメントは1つ以上のセクションを含みます。

### `__text` セクション

Mach-Oファイルにおいて、`__TEXT`セグメントは通常、実行可能コードと読み取り専用データを格納します。この`__TEXT`セグメント内に存在する`__text`セクションは、プログラムの実際の機械語コード（CPUが実行する命令）を格納する場所です。つまり、Goプログラムのコンパイルされた関数などがこのセクションに配置されます。このセクションは通常、読み取り専用かつ実行可能としてマークされ、セキュリティとメモリ効率のために重要な役割を果たします。

## 技術的詳細

このコミットの技術的詳細には、以下の点が挙げられます。

1.  **`debug/macho` パッケージの導入**: `src/cmd/dist/deps.go` と `src/cmd/go/note.go` の変更から、`debug/macho` パッケージが `cmd/go` の依存関係に追加されていることがわかります。このパッケージは、Go言語でMach-Oファイルを解析するための標準ライブラリの一部であり、Mach-Oファイルの構造をプログラム的に読み取る機能を提供します。これにより、`cmd/go` はMach-Oファイルのヘッダ、ロードコマンド、セグメント、セクションといった内部構造にアクセスできるようになります。

2.  **`readMachoGoBuildID` 関数の追加**: `src/cmd/go/note.go` に `readMachoGoBuildID` という新しい関数が追加されました。この関数は、Mach-O形式の実行可能ファイルからGoのビルドIDを抽出するロジックをカプセル化しています。
    *   まず、既存の `readRawGoBuildID` 関数を使って、ファイル先頭のバッファ（後述の32KB）からビルドIDを検索します。これは、Mach-Oパースが失敗した場合や、ビルドIDがたまたま先頭近くにある場合のフォールバック/最適化として機能します。
    *   次に、`macho.NewFile(f)` を使用してファイルディスクリプタ `f` からMach-Oファイルを解析し、`mf.Section("__text")` を呼び出して `__text` セクションを特定します。
    *   `__text` セクションが見つかった場合、そのオフセットとサイズを利用して、セクションの先頭から最大 `BuildIDReadSize` (32KB) までのデータを読み込みます。
    *   最後に、この読み込んだバッファに対して再度 `readRawGoBuildID` を呼び出し、ビルドIDのパターンを検索します。

3.  **`BuildIDReadSize` の増加**: `src/cmd/go/pkg.go` では、`ReadBuildIDFromBinary` 関数内でバイナリファイルから読み込む初期データサイズが `16*1024` (16KB) から `BuildIDReadSize` (デフォルト32KB) に変更されました。これは、Mach-Oパースに加えて、より広い範囲をスキャンすることでビルドIDの検出率を高めるための変更です。`BuildIDReadSize` はテストのために変更可能な変数として定義されています。

4.  **Mach-Oマジックバイトの追加**: `src/cmd/go/pkg.go` に `machoPrefixes` というバイトスライスが追加され、Mach-Oファイルのヘッダ（マジックバイト）を識別するためのパターンが定義されました。これにより、`ReadBuildIDFromBinary` 関数は、ファイルの先頭バイトをチェックして、それがMach-Oファイルであるかどうかを正確に判断できるようになります。

5.  **テストの追加と強化**: `src/cmd/go/note_test.go` に `TestNoteReading2K` という新しいテストケースが追加されました。このテストは、`BuildIDReadSize` を2KBに設定して、Mach-Oパースロジックがより厳密に機能するかどうかを検証します。これは、Mach-Oパースが主要な検出メカニズムとして機能することを保証するための重要なテストです。

これらの変更により、`cmd/go` はmacOS上のGoバイナリからビルドIDをより確実に抽出し、ビルドシステムの堅牢性を向上させています。

## コアとなるコードの解説

このコミットの核となる変更は、`src/cmd/go/note.go` に追加された `readMachoGoBuildID` 関数と、`src/cmd/go/pkg.go` の `ReadBuildIDFromBinary` 関数におけるMach-Oファイルの識別と処理ロジックです。

`ReadBuildIDFromBinary` 関数は、まずファイルの先頭から `BuildIDReadSize` (32KB) のデータを読み込みます。次に、このデータがELFファイル、Mach-Oファイル、またはその他の形式であるかをマジックバイト（`elfPrefix` や `machoPrefixes`）で判定します。

もしMach-Oファイルであると判定された場合、`readMachoGoBuildID` 関数が呼び出されます。
1.  `readMachoGoBuildID` は、まず読み込んだ初期バッファ `data` 内でビルドIDを検索します (`readRawGoBuildID` を使用)。これは、ビルドIDがたまたま初期バッファ内に存在する場合の高速パスであり、またMach-Oパースが将来的に失敗する可能性への備えでもあります。
2.  初期バッファでビルドIDが見つからなかった場合、`debug/macho` パッケージを使用してファイル `f` をMach-Oファイルとして解析します (`macho.NewFile(f)`)。
3.  解析後、`mf.Section("__text")` を呼び出して、実行可能コードが格納されている `__text` セクションの情報を取得します。
4.  `__text` セクションが見つかった場合、そのセクションのオフセット (`sect.Offset`) とサイズ (`sect.Size`) を利用して、セクションの先頭から最大 `BuildIDReadSize` までのデータをファイルから直接読み込みます (`f.ReadAt(buf, int64(sect.Offset))`)。
5.  最後に、この `__text` セクションから読み込んだバッファに対して再度 `readRawGoBuildID` を呼び出し、ビルドIDのパターンを検索して返します。

この二重のアプローチ（初期バッファスキャンとMach-Oパースによる`__text`セクションスキャン）により、macOS上でのGoバイナリのビルドID検出の信頼性が大幅に向上しました。

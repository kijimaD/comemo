# [インデックス 25495] ファイルの概要

このコミットは、Goランタイムの並行マークフェーズにおけるガベージコレクションワーカーの動作を改善することを目的としています。具体的には、専用マークワーカーが `getfull` バリアに参加するのをやめさせ、ガベージコレクションの効率性、堅牢性、およびWindows環境での互換性を向上させています。

## コミット

```
commit 62ba520b237afebd16e5c55113523f1511643fb1
Author: Austin Clements <austin@google.com>
Date:   Mon Oct 26 16:29:25 2015 -0400

    runtime: eliminate getfull barrier from concurrent mark
    
    Currently dedicated mark workers participate in the getfull barrier
    during concurrent mark. However, the getfull barrier wasn't designed
    for concurrent work and this causes no end of headaches.
    
    In the concurrent setting, participants come and go. This makes mark
    completion susceptible to live-lock: since dedicated workers are only
    periodically polling for completion, it's possible for the program to
    be in some transient worker each time one of the dedicated workers
    wakes up to check if it can exit the getfull barrier. It also
    complicates reasoning about the system because dedicated workers
    participate directly in the getfull barrier, but transient workers
    must instead use trygetfull because they have exit conditions that
    aren't captured by getfull (e.g., fractional workers exit when
    preempted). The complexity of implementing these exit conditions
    contributed to #11677. Furthermore, the getfull barrier is inefficient
    because we could be running user code instead of spinning on a P. In
    effect, we're dedicating 25% of the CPU to marking even if that means
    we have to spin to make that 25%. It also causes issues on Windows
    because we can't actually sleep for 100µs (#8687).
    
    Fix this by making dedicated workers no longer participate in the
    getfull barrier. Instead, dedicated workers simply return to the
    scheduler when they fail to get more work, regardless of what others
    workers are doing, and the scheduler only starts new dedicated workers
    if there's work available. Everything that needs to be handled by this
    barrier is already handled by detection of mark completion.
    
    This makes the system much more symmetric because all workers and
    assists now use trygetfull during concurrent mark. It also loosens the
    25% CPU target so that we can give some of that 25% back to user code
    if there isn't enough work to keep the mark worker busy. And it
    eliminates the problematic 100µs sleep on Windows during concurrent
    mark (though not during mark termination).
    
    The downside of this is that if we hit a bottleneck in the heap graph
    that then expands back out, the system may shut down dedicated workers
    and take a while to start them back up. We'll address this in the next
    commit.
    
    Updates #12041 and #8687.
    
    No effect on the go1 benchmarks. This slows down the garbage benchmark
    by 9%, but we'll more than make it up in the next commit.
```

## 元コミット内容

Goランタイムの並行マークフェーズにおいて、専用マークワーカーが `getfull` バリアに参加するのを廃止する変更です。これにより、並行処理におけるライブロックの可能性、システム推論の複雑さ、非効率性、およびWindows環境での問題が解消されます。専用ワーカーは、作業がなくなるとスケジューラに戻るようになり、スケジューラは作業がある場合にのみ新しい専用ワーカーを起動します。この変更により、すべてのワーカーとアシストが `trygetfull` を使用するようになり、システムがより対称的になります。また、CPU使用率の目標（25%）が緩和され、作業が少ない場合にはユーザーコードにCPU時間を割り当てられるようになります。Windowsでの問題となっていた100µsのスリープも解消されます。ただし、ヒープグラフにボトルネックが生じた場合、専用ワーカーがシャットダウンし、再起動に時間がかかる可能性があるという欠点があり、これは次のコミットで対処される予定です。この変更は、#12041 と #8687 の問題を更新します。ベンチマークでは `XBenchGarbage-12` が9%遅くなりますが、これも次のコミットで改善される見込みです。

## 変更の背景

Goのガベージコレクタ（GC）は、プログラムの実行と並行して動作する「並行GC」を採用しています。この並行GCの重要なフェーズの一つが「マークフェーズ」です。マークフェーズでは、到達可能なオブジェクトを特定し、マークします。このプロセスには、専用のGCワーカーと、ユーザーコードの実行中にGCを手伝う「アシスト」ワーカーが関与します。

このコミット以前は、専用マークワーカーも `getfull` バリアという同期メカニズムに参加していました。`getfull` バリアは、すべての参加者が特定のポイントに到達するまで待機する仕組みです。しかし、並行マークフェーズのようにワーカーが動的に参加・離脱する環境では、この `getfull` バリアがいくつかの深刻な問題を引き起こしていました。

1.  **ライブロックの可能性**: 専用ワーカーは完了を定期的にポーリングしますが、その間にプログラムが一時的なワーカーの状態にあると、専用ワーカーがバリアを抜け出せるかどうかをチェックするたびに、他のワーカーがまだバリアに参加していると誤認し、永久に待機し続ける「ライブロック」状態に陥る可能性がありました。
2.  **システム推論の複雑さ**: 専用ワーカーは `getfull` に直接参加する一方で、一時的なワーカー（例：プリエンプト時に終了するフラクショナルワーカー）は `trygetfull` を使用する必要がありました。これは、`getfull` が捕捉しない独自の終了条件を持つためです。この異なる動作がシステムの推論を複雑にし、バグ（#11677）の原因となっていました。
3.  **非効率性**: `getfull` バリアは、すべてのワーカーが揃うまでCPUをスピン（空回り）させる可能性があり、これはユーザーコードを実行できる貴重なCPU時間を浪費していました。Go GCはCPUの25%をマークフェーズに割り当てることを目標としていますが、このスピンによって、たとえ作業がなくても25%を消費してしまうことがありました。
4.  **Windowsでの問題**: Windows環境では、特定の短い時間（100µs）のスリープが正確に機能しないことがあり（#8687）、これが `getfull` バリアの動作に悪影響を与えていました。

これらの問題に対処し、Go GCの並行マークフェーズをより堅牢で効率的、かつプラットフォームに依存しないものにするために、この変更が導入されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびガベージコレクションに関する概念を理解しておく必要があります。

### Goのガベージコレクション (GC)

GoのGCは、主に以下のフェーズで構成される「トライカラーマーク＆スイープ」アルゴリズムをベースにしています。

*   **マークフェーズ (Mark Phase)**: プログラムが使用しているオブジェクト（到達可能なオブジェクト）を特定し、マークします。
    *   **マーク開始 (Mark Start)**: GCが開始され、一部のP（プロセッサ）がGCワーカーとして割り当てられます。
    *   **並行マーク (Concurrent Mark)**: プログラムの実行と並行して、GCワーカーが到達可能なオブジェクトを探索し、マークします。これがこのコミットの主要な対象です。
    *   **マーク終了 (Mark Termination)**: 並行マークが完了した後、プログラムの実行を一時停止（STW: Stop The World）して、マークフェーズの最終処理を行います。
*   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不能なオブジェクト）を解放し、メモリを再利用可能にします。これも並行して行われます。

### GCワーカーの種類

Go GCには主に2種類のワーカーが存在します。

1.  **専用マークワーカー (Dedicated Mark Workers)**: GCがアクティブな間、GC作業に専念するために割り当てられるP（論理プロセッサ）上で動作するゴルーチンです。これらはGCの主要な作業を担います。
2.  **フラクショナルワーカー / アシスト (Fractional Workers / Assists)**: ユーザーコードを実行しているゴルーチンが、ヒープに新しいオブジェクトを割り当てようとした際に、GCの進行が遅れている場合にGC作業を手伝うものです。これらはユーザーコードの実行を一時的に中断してGC作業を行い、GCの進行を加速させます。

### P (プロセッサ)

GoランタイムにおけるPは、OSスレッド上でGoのゴルーチンを実行するための論理プロセッサです。Goスケジューラは、M（OSスレッド）上でPを介してG（ゴルーチン）を実行します。GCワーカーもP上で実行されます。

### `getfull` と `trygetfull` バリア

これはGoランタイム内部の同期プリミティブに関連する概念です。
*   **バリア (Barrier)**: 複数の並行プロセスが特定のポイントに到達するまで、他のプロセスが先に進むのを待機させる同期メカニズムです。GCにおいては、特定のフェーズの完了を待つために使用されます。
*   **`getfull`**: すべての参加者がバリアに到達するまでブロック（待機）するような、より厳密なバリアメカニズムを指します。
*   **`trygetfull`**: バリアに到達しようと試みますが、ブロックせずにすぐに結果を返す（またはタイムアウトする）ような、より柔軟なバリアメカニズムを指します。これは、ワーカーが他の条件（例：プリエンプト）で終了する必要がある場合に特に有用です。

### ライブロック (Live-lock)

デッドロックに似ていますが、プロセスがブロックされるのではなく、互いに相手の行動を待って状態を変化させ続けるため、実質的に何も進まない状態を指します。リソースを消費し続けるため、デッドロックよりも検出が難しい場合があります。

### `gcDrain` 関数

Go GCにおいて、マーク作業キューからオブジェクトを取り出してマークする主要な関数です。この関数は、マーク作業がなくなるまで、または特定の条件（例：プリエンプト）が満たされるまで実行されます。

## 技術的詳細

このコミットの核心は、Goランタイムの並行マークフェーズにおける専用マークワーカーの同期戦略の変更です。

### 変更前の問題点と `getfull` バリアの動作

変更前は、専用マークワーカーは `getfull` バリアに参加していました。これは、すべての専用ワーカーがマーク作業を完了し、バリアに到達するまで、他のワーカーが待機するような動作を意味していました。しかし、並行GCの性質上、ワーカーは動的に生成・終了するため、この「全員が揃うまで待つ」というモデルは不適切でした。

*   **ライブロック**: 専用ワーカーが完了をポーリングする際、他のワーカーが一時的な状態にあると、バリアが完了したと判断できず、無限にポーリングを繰り返す可能性がありました。
*   **非効率なスピン**: 作業がない場合でも、`getfull` バリアの完了を待つためにCPUをスピンさせることがあり、これはリソースの無駄でした。Go GCはCPUの25%をGCに割り当てることを目標としていますが、作業がないのにこの目標を達成するためにスピンするのは非効率です。
*   **Windowsでの問題**: `getfull` バリアの実装には、特定の短い時間（100µs）のスリープが含まれていました。Windowsのスケジューラはこのような短いスリープを正確に保証できないため、GCの動作が不安定になる原因となっていました。

### 変更後の新しい同期戦略

このコミットでは、専用マークワーカーが `getfull` バリアに直接参加するのをやめさせます。代わりに、以下の新しいアプローチが採用されます。

1.  **作業がなくなったらスケジューラに戻る**: 専用マークワーカーは、マーク作業キューからこれ以上作業を取得できなくなったら、他のワーカーの状態に関わらず、すぐにGoスケジューラに制御を返します。
2.  **スケジューラによるワーカーの起動**: スケジューラは、マーク作業が利用可能である場合にのみ、新しい専用マークワーカーを起動します。これにより、作業がないのにワーカーがCPUを占有する状況が回避されます。
3.  **`trygetfull` の統一**: この変更により、すべてのGCワーカー（専用ワーカー、フラクショナルワーカー、アシスト）が、並行マークフェーズ中に `trygetfull` に相当する動作をするようになります。これは、ワーカーが独自の終了条件（例：プリエンプト）に基づいて柔軟にGC作業を中断できることを意味します。
4.  **マーク完了検出の活用**: `getfull` バリアが担っていた「マーク完了の検出」は、既存のマーク完了検出ロジックによって既に適切に処理されているため、`getfull` バリアの廃止は問題ありません。

### 変更のメリット

*   **対称性の向上**: すべてのワーカーが同様のメカニズム（`trygetfull` 的な動作）でGC作業に参加するようになり、システムの推論が容易になります。
*   **CPU利用率の改善**: 作業がない場合に専用ワーカーがCPUをスピンするのをやめるため、GCに割り当てられたCPU時間の一部をユーザーコードに解放できるようになります。これにより、GCのCPU目標（25%）がより柔軟に適用され、全体的なスループットが向上する可能性があります。
*   **Windowsでの問題解消**: 100µsスリープの問題が解消され、Windows環境でのGCの安定性が向上します。
*   **ライブロックの回避**: 専用ワーカーがバリアに固執しなくなるため、ライブロックの可能性がなくなります。

### 変更のデメリットと今後の課題

コミットメッセージには、この変更のデメリットも記載されています。
*   **ボトルネック時のワーカー再起動遅延**: ヒープグラフに一時的なボトルネックが生じ、その後作業が再び増えた場合、システムは一度シャットダウンした専用ワーカーを再起動するのに時間がかかる可能性があります。これは、GCの反応性を低下させる可能性があります。この問題は、次のコミットで対処される予定です。

### ベンチマーク結果

このコミット単体では、`XBenchGarbage-12` ベンチマークで9%の性能低下が見られます。これは、ワーカーの起動・停止のオーバーヘッドや、一時的な作業不足によるGCの遅延が原因と考えられます。しかし、この性能低下は一時的なものであり、次のコミットで改善されることが示唆されています。

## コアとなるコードの変更箇所

変更は主に `src/runtime/mgc.go` と `src/runtime/mgcmark.go` の2つのファイルで行われています。

### `src/runtime/mgc.go`

*   `gcMarkWorkerDedicatedMode` のコメント変更:
    *   変更前: `// worker should run without preemption until concurrent mark // is done.`
    *   変更後: `// worker should run without preemption.`
    *   専用ワーカーが並行マークの完了まで実行されるという制約が削除され、単にプリエンプトされないことが強調されています。これは、専用ワーカーが `getfull` バリアに依存しなくなることを反映しています。
*   `gcControllerState.findRunnableGCWorker` 関数の変更:
    *   `gcMarkWorkAvailable(_p_)` のチェックと、それに続くマーク完了処理のロジックが、`else` ブロックの外に移動し、より早い段階で実行されるようになりました。これにより、作業がない場合にワーカーを起動しないという新しい戦略が実装されています。
    *   以前の `if !gcMarkWorkAvailable(_p_)` ブロックが削除され、専用ワーカーが作業がない場合にスケジューラに戻るという動作が明確化されています。
*   `gcBgMarkWorker` 関数の変更:
    *   `gcMarkWorkerDedicatedMode` のケースで `gcDrain` の呼び出しが変更されました。
        *   変更前: `gcDrain(&p.gcw, gcDrainBlock|gcDrainFlushBgCredit)`
        *   変更後: `gcDrain(&p.gcw, gcDrainNoBlock|gcDrainFlushBgCredit)`
        *   `gcDrainBlock` フラグが `gcDrainNoBlock` に変更されています。これは、専用ワーカーがマーク完了までブロック（待機）するのではなく、作業がなくなったらすぐに戻ることを意味します。
    *   `done` 変数の計算ロジックが変更され、`incnwait == work.nproc && !gcMarkWorkAvailable(nil)` という条件でマーク完了が判断されるようになりました。これは、`getfull` バリアに依存しないマーク完了検出ロジックです。

### `src/runtime/mgcmark.go`

*   `gcDrainFlags` の定義変更:
    *   `gcDrainNoBlock` という新しいフラグが追加されました。
    *   `gcDrainBlock` のコメントが更新され、`gcDrainUntilPreempt` または `gcDrainNoBlock` のどちらでもない場合のデフォルト値であることが明記されました。
*   `gcDrain` 関数の変更:
    *   `blocking` 変数の計算ロジックが変更されました。
        *   変更前: `blocking := flags&gcDrainUntilPreempt == 0`
        *   変更後: `preemtible := flags&gcDrainUntilPreempt != 0; blocking := flags&(gcDrainUntilPreempt|gcDrainNoBlock) == 0`
        *   `gcDrainNoBlock` フラグが考慮されるようになり、`gcDrainUntilPreempt` と `gcDrainNoBlock` の両方が設定されていない場合にのみ `blocking` が `true` になるようになりました。
    *   `for` ループの条件が変更されました。
        *   変更前: `for blocking || !gp.preempt {`
        *   変更後: `for !(preemtible && gp.preempt) {`
        *   これにより、`gcDrainUntilPreempt` が設定されており、かつゴルーチンがプリエンプトされた場合にループを終了するようになりました。これは、`gcDrainNoBlock` の動作と組み合わさって、ワーカーが柔軟に終了できることを保証します。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更点

`gcMarkWorkerDedicatedMode` のコメント変更は、専用ワーカーの役割が「並行マーク完了まで実行される」から「プリエンプトされない」へと、より一般的なものに変わったことを示しています。これは、専用ワーカーが特定のバリアに縛られず、作業がある限り実行されるという新しい哲学を反映しています。

`gcControllerState.findRunnableGCWorker` での `gcMarkWorkAvailable` のチェックの移動は、スケジューラがGCワーカーを起動する前に、そもそも作業があるかどうかを確認するようになったことを意味します。これにより、作業がないのにワーカーを起動してすぐに終了させるという無駄がなくなります。

`gcBgMarkWorker` 関数における `gcDrain` のフラグ変更が最も重要です。
`gcDrain(&p.gcw, gcDrainBlock|gcDrainFlushBgCredit)` から `gcDrain(&p.gcw, gcDrainNoBlock|gcDrainFlushBgCredit)` への変更は、専用ワーカーが `gcDrain` を呼び出す際に、もはや「ブロックしてマーク完了を待つ」のではなく、「ブロックせずに、作業がなくなったらすぐに戻る」という動作になったことを明確に示しています。
これにより、専用ワーカーは `getfull` バリアに依存せず、自律的に作業を処理し、作業がなくなればスケジューラに制御を戻すことができます。

`done` 変数の計算ロジックの変更も、`getfull` バリアに依存しないマーク完了検出の新しい方法を確立しています。`incnwait == work.nproc && !gcMarkWorkAvailable(nil)` は、「すべてのワーカーが待機状態に入り、かつ利用可能なマーク作業がもうない」という条件でマークが完了したと判断します。

### `src/runtime/mgcmark.go` の変更点

`gcDrainFlags` に `gcDrainNoBlock` が追加されたことで、`gcDrain` 関数に「ブロックせずに作業を処理し、すぐに戻る」という新しい動作モードが導入されました。

`gcDrain` 関数内の `blocking` 変数の計算ロジックの変更は、`gcDrainNoBlock` フラグが設定されている場合に `blocking` が `false` になるように調整されています。これにより、`gcDrainNoBlock` が指定されたワーカーは、他のワーカーの完了を待つことなく、自身の作業がなくなればすぐに終了できるようになります。

`for` ループの条件 `for !(preemtible && gp.preempt)` は、`gcDrainUntilPreempt` フラグが設定されており、かつ現在のゴルーチンがプリエンプトされた場合にループを終了することを保証します。これは、フラクショナルワーカーやアシストがユーザーコードの実行を妨げないように、必要に応じてGC作業を中断できるメカニズムです。専用ワーカーが `gcDrainNoBlock` を使用する場合、このループは作業がなくなるか、プリエンプトされるまで実行されますが、他のワーカーの完了を待つことはありません。

これらの変更により、Goの並行GCは、ワーカーの動的な参加・離脱により適応し、より効率的で堅牢な動作を実現しています。

## 変更の背景

Go言語のランタイムは、メモリ管理のためにガベージコレクション（GC）を採用しています。このコミットが作成された2014年頃は、GoのGCがストップ・ザ・ワールド（STW）時間を最小限に抑えるための並行GC（Concurrent GC）への移行期にありました。並行GCでは、GCのマークフェーズ（到達可能なオブジェクトを識別する段階）がアプリケーションの実行と並行して行われます。

並行GCの正確性を保証するためには、「ライトバリア（Write Barrier）」というメカニズムが不可欠です。ライトバリアは、アプリケーションがポインタを書き換える際にGCに通知する役割を果たします。これにより、GCがオブジェクトグラフを走査している最中に、アプリケーションがポインタを変更してオブジェクトが誤って回収されてしまう（「見逃し」問題）ことを防ぎます。

このコミットの背景には、並行マークフェーズが有効な状態でテストを実行した際に発生した`TestGoexitCrash-2`というテストの失敗があります。これは、特定のシナリオ（ゴルーチンの生成、プリエンプション、終了）において、ライトバリアが適切に適用されていない、または不適切に適用されているために、GCの正確性が損なわれていたことを示唆しています。特に、ゴルーチンのスタックやスケジューリングコンテキストといった内部状態のポインタ操作が、並行GCのマークフェーズと競合し、問題を引き起こしていたと考えられます。

## 前提知識の解説

### 1. ガベージコレクション (GC)

ガベージコレクションは、プログラムが動的に確保したメモリ領域のうち、もはやプログラムから到達不可能になった（参照されなくなった）領域を自動的に解放する仕組みです。これにより、プログラマは手動でのメモリ管理から解放され、メモリリークやダングリングポインタといった問題のリスクを低減できます。

### 2. GoのGCと並行マーク・アンド・スイープ

GoのGCは、主に「マーク・アンド・スイープ（Mark-and-Sweep）」アルゴリズムをベースにしています。
*   **マークフェーズ**: GCはルート（グローバル変数、スタック上の変数など）から開始し、到達可能なすべてのオブジェクトに「マーク」を付けます。
*   **スイープフェーズ**: マークされなかった（到達不可能な）オブジェクトのメモリを解放します。

初期のGoのGCは、マークフェーズ中にアプリケーションの実行を完全に停止させる「ストップ・ザ・ワールド（STW）」方式を採用していました。しかし、これによりアプリケーションの応答性が低下するという問題がありました。Go 1.5以降、GoはSTW時間を大幅に短縮するために、並行GCを導入しました。並行GCでは、マークフェーズの一部または大部分がアプリケーションの実行と並行して行われます。

### 3. ライトバリア (Write Barrier)

並行GCにおいて、アプリケーションがオブジェクトグラフを変更する（ポインタを書き換える）際に、GCの正確性を保証するために使用される技術がライトバリアです。
並行マーク中にアプリケーションがポインタ`A`から`B`への参照を`A`から`C`への参照に書き換えた場合を考えます。もしGCが`B`をマークした後でこの書き換えが発生し、かつ`C`が他のどこからも参照されなくなった場合、GCは`C`を見逃して誤って回収してしまう可能性があります。
ライトバリアは、このような「見逃し」問題を解決するために、ポインタの書き換え操作をGCに通知し、GCがオブジェクトグラフの変更を適切に追跡できるようにします。Goのライトバリアは、通常、ポインタの書き込み時に特定のコード（バリアコード）を実行し、GCが必要な処理（例えば、変更されたポインタの古い値と新しい値の両方をマークする）を行うようにします。

### 4. ゴルーチン (Goroutine) のライフサイクル

Goにおけるゴルーチンは、軽量な並行実行単位です。OSのスレッドよりもはるかに軽量であり、数百万のゴルーチンを同時に実行することも可能です。ゴルーチンは以下のライフサイクルを持ちます。
*   **生成**: `go`キーワードによって新しいゴルーチンが作成されます。この際、新しいスタックとスケジューリングコンテキストが割り当てられます。
*   **実行**: スケジューラによってCPU上で実行されます。
*   **プリエンプション**: 長時間実行されるゴルーチンは、他のゴルーチンにCPUを譲るためにプリエンプト（中断）されることがあります。これは、協調的プリエンプション（関数呼び出し時など）や、より新しいGoのバージョンでは非同期プリエンプションによって行われます。プリエンプション時には、ゴルーチンの状態（レジスタ、スタックポインタなど）が保存されます。
*   **終了**: ゴルーチンが関数の実行を完了するか、パニックによって終了します。

このコミットは、特にゴルーチンの生成時、プリエンプション時、および終了時における内部ポインタの操作とライトバリアの相互作用に焦点を当てています。

## 技術的詳細

このコミットは、Goの並行GCにおけるライトバリアの適用漏れや不適切な適用を修正することで、GCの正確性を向上させています。

1.  **新規ゴルーチン初期化時のライトバリアの追加**:
    新しいゴルーチンが作成される際、その内部状態（特にスケジューリングコンテキスト`gp->sched.ctxt`）が初期化されます。この初期化はポインタの書き込みを伴いますが、並行GCが有効な場合、この書き込みに対してライトバリアが適用されていないと、GCが新しいゴルーチンの参照を正しく追跡できない可能性があります。コミットは、この初期化時に`runtime·writebarrierptr_nostore`を呼び出すことで、ライトバリアを明示的に適用しています。これにより、GCが新しいゴルーチンの状態を正確にマークできるようになります。

2.  **ゴルーチンプリエンプション時のライトバリアの追加**:
    ゴルーチンがプリエンプトされる際、その状態が保存され、後で復元されます。`morestack`関数は、スタックの拡張やプリエンプションの処理中に、ゴルーチンのスケジューリングコンテキスト`gp->sched.ctxt`を書き込むことがあります。この書き込みもポインタ操作であるため、並行GCの正確性を保つためにはライトバリアが必要です。コミットは、`runtime·newstack`内で`gp->sched.ctxt`が書き込まれた後に、再度`runtime·writebarrierptr_nostore`を呼び出すことで、このプリエンプション時のライトバリアを保証しています。コミットメッセージにある「It is not possible to be preempted between then and now, so it's okay.」というコメントは、このライトバリアが遅れて適用されても問題ないことを示しています。

3.  **ゴルーチン終了時のライトバリアの無効化**:
    ゴルーチンがパニックによって終了する際、`dopanic`関数がポインタの書き込みを行います。しかし、ゴルーチンが終了する段階では、そのゴルーチンが参照しているオブジェクトはもはや到達可能である必要がないため、ライトバリアを適用する必要はありません。むしろ、ライトバリアが有効なままだと、終了処理が複雑になったり、不要なオーバーヘッドが発生したりする可能性があります。このコミットでは、`mp.dying > 0`という条件を追加することで、ゴルーチンが終了処理中（`dying`状態）の場合にはライトバリアを無効にしています。これにより、終了処理の効率を維持しつつ、GCの正確性も損なわないようにしています。

これらの変更は、Goの並行GCがより堅牢に動作し、特定のコーナーケース（ゴルーチンのライフサイクルイベント）においてもメモリの安全性を保証するために不可欠です。

## コアとなるコードの解説

### `src/runtime/mgc0.go` の変更

```go
 // old
-	if mp.inwb {
 // new
+	if mp.inwb || mp.dying > 0 {
```
`writebarrierptr_nostore`関数は、ポインタの書き込み時にライトバリアのロジックを実行するかどうかを決定します。`mp.inwb`は、現在のM（OSスレッド）がライトバリアモードにあるかどうかを示します。この変更では、`mp.dying > 0`という条件が追加されました。これは、現在のMがゴルーチンの終了処理中（`dying`状態）である場合に、ライトバリアを無効にすることを意味します。ゴルーチンが終了する際には、そのゴルーチンが参照していたオブジェクトはもはや到達可能である必要がないため、ライトバリアのオーバーヘッドを避けるために無効化されます。

### `src/runtime/runtime.h` の変更

```c
+void	runtime·writebarrierptr_nostore(void*, void*);
```
`runtime·writebarrierptr_nostore`関数のプロトタイプ宣言が追加されました。これは、CコードからこのGo関数を呼び出すために必要です。

### `src/runtime/stack.c` の変更

```c
 // old
 // new
+	if(gp->sched.ctxt != nil) {
+		// morestack wrote sched.ctxt on its way in here,
+		// without a write barrier. Run the write barrier now.
+		// It is not possible to be preempted between then
+		// and now, so it's okay.
+		runtime·writebarrierptr_nostore(&gp->sched.ctxt, gp->sched.ctxt);
+	}
```
`runtime·newstack`関数は、スタックの拡張やゴルーチンのプリエンプション時に呼び出されます。この変更は、`gp->sched.ctxt`（ゴルーチンのスケジューリングコンテキスト）が`morestack`によって書き込まれた後に、明示的にライトバリアを適用しています。`gp->sched.ctxt`はポインタであり、その書き込みはGCのマークフェーズ中に発生する可能性があるため、GCの正確性を保つためにライトバリアが必要です。コメントは、このライトバリアが少し遅れて適用されても、その間にプリエンプションが発生しないため安全であることを説明しています。

### `src/runtime/sys_x86.c` の変更

```c
 // old
 	gobuf->ctxt = ctxt;
 // new
 	gobuf->ctxt = ctxt;
+	runtime·writebarrierptr_nostore(&gobuf->ctxt, ctxt);
```
`runtime·gostartcall`関数は、新しいゴルーチンが開始される際に呼び出され、そのゴルーチンの初期状態（`Gobuf`）を設定します。この中で、`gobuf->ctxt`（ゴルーチンのコンテキストポインタ）が初期化されます。この初期化もポインタの書き込みであるため、並行GCの正確性を保証するためにライトバリアが必要です。この変更により、`gobuf->ctxt`が設定された直後に`runtime·writebarrierptr_nostore`が呼び出され、ライトバリアが適用されます。

    新しいゴルーチンが作成される際、その内部状態（特にスケジューリングコンテキスト`gp->sched.ctxt`）が初期化されます。この初期化はポインタの書き込みを伴いますが、並行GCが有効な場合、この書き込みに対してライトバリアが適用されていないと、GCが新しいゴルーチンの参照を正しく追跡できない可能性があります。コミットは、この初期化時に`runtime·writebarrierptr_nostore`を呼び出すことで、ライトバリアを明示的に適用しています。これにより、GCが新しいゴルーチンの状態を正確にマークできるようになります。

2.  **ゴルーチンプリエンプション時のライトバリアの追加**:
    ゴルーチンがプリエンプトされる際、その状態が保存され、後で復元されます。`morestack`関数は、スタックの拡張やプリエンプションの処理中に、ゴルーチンのスケジューリングコンテキスト`gp->sched.ctxt`を書き込むことがあります。この書き込みもポインタ操作であるため、並行GCの正確性を保つためにはライトバリアが必要です。コミットは、`runtime·newstack`内で`gp->sched.ctxt`が書き込まれた後に、再度`runtime·writebarrierptr_nostore`を呼び出すことで、このプリエンプション時のライトバリアを保証しています。コミットメッセージにある「It is not possible to be preempted between then and now, so it's okay.」というコメントは、このライトバリアが遅れて適用されても問題ないことを示しています。

3.  **ゴルーチン終了時のライトバリアの無効化**:
    ゴルーチンがパニックによって終了する際、`dopanic`関数がポインタの書き込みを行います。しかし、ゴルーチンが終了する段階では、そのゴルーチンが参照しているオブジェクトはもはや到達可能である必要がないため、ライトバリアを適用する必要はありません。むしろ、ライトバリアが有効なままだと、終了処理が複雑になったり、不要なオーバーヘッドが発生したりする可能性があります。このコミットでは、`mp.dying > 0`という条件を追加することで、ゴルーチンが終了処理中（`dying`状態）の場合にはライトバリアを無効にしています。これにより、終了処理の効率を維持しつつ、GCの正確性も損なわないようにしています。

これらの変更は、Goの並行GCがより堅牢に動作し、特定のコーナーケース（ゴルーチンのライフサイクルイベント）においてもメモリの安全性を保証するために不可欠です。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下のファイルに集中しています。

*   `src/runtime/mgc0.c`: `runtime·gcmarkwb_m`関数から不要なローカル変数`slot`の宣言を削除。これは直接的な機能変更ではなく、クリーンアップ。
*   `src/runtime/mgc0.go`: `writebarrierptr_nostore`関数において、ライトバリアを無効にする条件に`mp.dying > 0`を追加。
*   `src/runtime/runtime.h`: `runtime·writebarrierptr_nostore`関数のプロトタイプ宣言を追加。
*   `src/runtime/stack.c`: `runtime·newstack`関数内で、`gp->sched.ctxt`の書き込み後に`runtime·writebarrierptr_nostore`を呼び出すコードを追加。
*   `src/runtime/sys_x86.c`: `runtime·gostartcall`関数内で、`gobuf->ctxt`の書き込み後に`runtime·writebarrierptr_nostore`を呼び出すコードを追加。

## コアとなるコードの解説

### `src/runtime/mgc0.go` の変更

```go
 // old
-	if mp.inwb {
 // new
+	if mp.inwb || mp.dying > 0 {
```
`writebarrierptr_nostore`関数は、ポインタの書き込み時にライトバリアのロジックを実行するかどうかを決定します。`mp.inwb`は、現在のM（OSスレッド）がライトバリアモードにあるかどうかを示します。この変更では、`mp.dying > 0`という条件が追加されました。これは、現在のMがゴルーチンの終了処理中（`dying`状態）である場合に、ライトバリアを無効にすることを意味します。ゴルーチンが終了する際には、そのゴルーチンが参照していたオブジェクトはもはや到達可能である必要がないため、ライトバリアのオーバーヘッドを避けるために無効化されます。

### `src/runtime/runtime.h` の変更

```c
+void	runtime·writebarrierptr_nostore(void*, void*);
```
`runtime·writebarrierptr_nostore`関数のプロトタイプ宣言が追加されました。これは、CコードからこのGo関数を呼び出すために必要です。

### `src/runtime/stack.c` の変更

```c
 // old
 // new
+	if(gp->sched.ctxt != nil) {
+		// morestack wrote sched.ctxt on its way in here,
+		// without a write barrier. Run the write barrier now.
+		// It is not possible to be preempted between then
+		// and now, so it's okay.
+		runtime·writebarrierptr_nostore(&gp->sched.ctxt, gp->sched.ctxt);
+	}
```
`runtime·newstack`関数は、スタックの拡張やゴルーチンのプリエンプション時に呼び出されます。この変更は、`gp->sched.ctxt`（ゴルーチンのスケジューリングコンテキスト）が`morestack`によって書き込まれた後に、明示的にライトバリアを適用しています。`gp->sched.ctxt`はポインタであり、その書き込みはGCのマークフェーズ中に発生する可能性があるため、GCの正確性を保つためにライトバリアが必要です。コメントは、このライトバリアが少し遅れて適用されても、その間にプリエンプションが発生しないため安全であることを説明しています。

### `src/runtime/sys_x86.c` の変更

```c
 // old
 	gobuf->ctxt = ctxt;
 // new
 	gobuf->ctxt = ctxt;
+	runtime·writebarrierptr_nostore(&gobuf->ctxt, ctxt);
```
`runtime·gostartcall`関数は、新しいゴルーチンが開始される際に呼び出され、そのゴルーチンの初期状態（`Gobuf`）を設定します。この中で、`gobuf->ctxt`（ゴルーチンのコンテキストポインタ）が初期化されます。この初期化もポインタの書き込みであるため、並行GCの正確性を保証するためにライトバリアが必要です。この変更により、`gobuf->ctxt`が設定された直後に`runtime·writebarrierptr_nostore`が呼び出され、ライトバリアが適用されます。

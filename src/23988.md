# [インデックス 23988] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション (GC) のビットマップ生成ロジックのバグ修正に関するものです。具体的には、GCプログラム (GCprog) を持つ型のスライスに対してヒープビットマップを生成する際に、ビットマップの繰り返し回数が1回多く計算されていた問題を修正しています。この誤りにより、ヒープのビットマップが破損したり、メモリ領域外への書き込みが発生し、セグメンテーション違反を引き起こす可能性がありました。

## 変更の背景

Goのガベージコレクタは、ヒープ上のオブジェクトがポインタを含むかどうかを効率的に判断するために「ヒープビットマップ」を使用します。特に、スライスのような可変長データ構造や、複雑な構造体のようにポインタの配置が一定でない型（GCprogを持つ型）の場合、そのビットマップの生成には特殊なロジックが必要です。

このコミット以前のGoランタイムでは、GCprogを持つ型のスライスに対してヒープビットマップを生成する際、スライスの各要素のビットマップを繰り返して構築していました。この繰り返し処理において、GCプログラムが「一度実行され、その後`n`回繰り返される」というロジックになっていました。しかし、これは実際には「一度実行され、その後`n-1`回繰り返される」べきでした。結果として、ビットマップが`n+1`回繰り返され、本来よりも1回多くビットが書き込まれていました。

この「1回多い繰り返し」は深刻な問題を引き起こしました。
1.  **ヒープビットマップの破損**: スライスの直後に続くヒープ領域のビットマップが誤って上書きされ、GCがオブジェクトを正しく認識できなくなる可能性がありました。これにより、本来到達可能なオブジェクトが誤って回収されたり、到達不可能なオブジェクトが回収されずにメモリリークが発生したりする可能性があります。
2.  **セグメンテーション違反 (Segfault)**: ビットマップの書き込みが割り当てられたメモリ領域を超えて行われると、保護されたメモリ領域にアクセスしようとしてセグメンテーション違反が発生し、プログラムがクラッシュする原因となります。

このバグはIssue #11430として報告されており、このコミットはその問題を解決するために導入されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **ガベージコレクション (GC)**: GoのGCは、プログラムが不要になったメモリを自動的に解放する仕組みです。GoのGCは並行・世代別・三色マーク＆スイープ方式を採用しており、ヒープ上のオブジェクトを追跡し、到達可能なオブジェクトを特定します。
2.  **ヒープビットマップ (Heap Bitmap)**: GoのGCは、ヒープ上の各メモリワードがポインタであるか、あるいはポインタを含まないデータであるかを識別するためにビットマップを使用します。これにより、GCはヒープをスキャンする際に、どのメモリ位置をポインタとして追跡すべきかを効率的に判断できます。
    *   各オブジェクトの先頭には、そのオブジェクトのレイアウト（どのオフセットにポインタがあるか）を示す情報が関連付けられています。
3.  **GCプログラム (GCprog)**: 複雑な型（例えば、複数のフィールドを持つ構造体や、ポインタを含む配列など）の場合、その型のメモリレイアウトをビットマップで直接表現するのは非効率的または不可能になることがあります。このような場合、Goランタイムは「GCプログラム」と呼ばれるバイトコードのような小さなプログラムを生成します。このGCprogは、GCがオブジェクトをスキャンする際に実行され、そのオブジェクト内のポインタの位置を動的に計算してビットマップを生成します。
    *   GCprogは、特に可変長データ構造（スライスなど）の要素のビットマップを効率的に生成するために使用されます。スライスの各要素は同じ型を持つため、その要素のGCprogを繰り返して実行することで、スライス全体のビットマップを構築できます。
4.  **スライス (Slice)**: Goのスライスは、配列のセグメントを参照するデータ構造です。スライス自体はポインタ、長さ、容量の3つのフィールドを持ちますが、スライスが参照する基底配列の要素がポインタを含む場合、GCはその要素のポインタを追跡する必要があります。スライスの要素がGCprogを持つ型である場合、そのスライス全体のビットマップは、要素のGCprogをスライスの長さ分だけ繰り返して適用することで生成されます。

## 技術的詳細

このバグは、`src/runtime/mbitmap.go` 内の `heapBitsSetTypeGCProg` 関数に関連しています。この関数は、GCprogを持つ型のヒープビットマップを設定する役割を担っています。

問題の核心は、スライスの要素のビットマップを繰り返すロジックにありました。スライスが`count`個の要素を持つ場合、各要素のビットマップを`count`回繰り返す必要があります。しかし、既存の実装では、GCprogを一度実行してビットマップを生成した後、さらに`n`回（ここで`n`は`count`に等しい）繰り返していました。これにより、合計で`1 + n`回、つまり`count + 1`回ビットマップが繰り返されていました。

例えば、`count = 3` のスライスがあったとします。
*   本来は、要素1、要素2、要素3のビットマップを生成し、合計3回繰り返す必要があります。
*   しかし、バグのある実装では、まずGCprogを1回実行して最初の要素のビットマップを生成し、その後`n`回（この場合`3`回）繰り返していました。
*   結果として、合計`1 + 3 = 4`回ビットマップが繰り返され、スライスの実際のサイズよりも1要素分多くビットマップが書き込まれていました。

この過剰な書き込みは、スライスの直後のメモリ領域のビットマップを破壊し、GCの誤動作やセグメンテーション違反を引き起こす原因となっていました。

修正は、この繰り返し回数を調整することです。GCprogを一度実行した後、残りの`count - 1`回だけ繰り返すように変更することで、合計の繰り返し回数が`1 + (count - 1) = count`回となり、正しいビットマップが生成されるようになります。

## コアとなるコードの解説

変更された行は `n = count - 1` です。

*   `heapBitsSetTypeGCProg` 関数は、GCprogを持つ型のヒープビットマップを設定する際に呼び出されます。
*   `count` 変数は、スライスの要素数（または、GCprogを繰り返す必要がある回数）を表します。
*   変更前のコード `n = count` は、GCprogを一度実行した後、さらに`count`回繰り返すことを意図していました。しかし、これは合計で`count + 1`回の繰り返しを意味していました。
*   変更後のコード `n = count - 1` は、GCprogを一度実行した後、残りの`count - 1`回だけ繰り返すように修正しています。これにより、合計の繰り返し回数は `1 (最初の実行) + (count - 1) (追加の繰り返し) = count` となり、スライスの要素数と正確に一致するようになります。
*   `for ; n >= 0x80; n >>= 7` ループは、`n`の値を可変長エンコーディングで`trailer`バイト配列に書き込むためのものです。このループに入る前の`n`の値が、GCprogの繰り返し回数を決定します。

このシンプルな変更により、GCビットマップの生成ロジックのオフバイワンエラーが修正され、ヒープの破損やセグメンテーション違反のリスクが排除されました。

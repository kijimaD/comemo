# [インデックス 26325] ファイルの概要

このコミットは、Goランタイムにおける特定の問題、特に`arm`、`arm64`、`ppc64`、`mips64`アーキテクチャでの`dropm`関数の呼び出し漏れを修正するものです。これにより、CgoコールバックのシナリオでOSスレッド（M）が適切に解放されず、リソースリークや非効率なリソース利用が発生する可能性がありました。

## 変更の背景

Goランタイムは、Goroutine（G）、論理プロセッサ（P）、OSスレッド（M）という3つの主要な抽象化を用いて並行性を管理しています。Cgo（GoとC言語の相互運用機能）を使用する際、GoコードからCコードを呼び出し、さらにCコードからGoコードへコールバックするようなシナリオが発生します。このようなCgoコールバックの過程で、GoランタイムはOSスレッド（M）を一時的に取得し、Goコードを実行します。

問題は、`arm`、`arm64`、`ppc64`、`mips64`といった特定のアーキテクチャにおいて、Cgoコールバックが完了した際に、Goランタイムが取得したOSスレッド（M）を適切に解放する`dropm`関数が呼び出されないケースがあったことです。これにより、不要になったMがランタイムのMプールに戻されず、OSスレッドがリークし、システムリソースを不必要に消費する可能性がありました。この問題はIssue #13881として報告されていました。

このコミットは、これらのアーキテクチャにおけるCgoコールバック処理のロジックを修正し、`dropm`が確実に呼び出されるようにすることで、リソースリークを防ぎ、ランタイムの安定性と効率性を向上させることを目的としています。

## 前提知識の解説

### Goランタイムスケジューラ (M, P, G)

Goランタイムのスケジューラは、以下の3つの主要な要素で構成されます。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。数KBのスタックを持ち、数百万個作成しても問題ありません。Goプログラムの並行処理の主役です。
*   **P (Processor)**: 論理プロセッサを表します。GをM上で実行するためのコンテキストを提供します。Pの数は通常、CPUのコア数に設定され、Goプログラムが同時に実行できるGoコードの数を制限します。Pは、実行可能なGのキューを保持しています。
*   **M (Machine/OS Thread)**: OSスレッドを表します。GoコードはM上で実行されます。MはOSによって管理され、Goランタイムは必要に応じてMをOSに要求したり、解放したりします。MはGを実行するためにPと関連付けられます。

Goランタイムは、GをPにディスパッチし、PはM上でGを実行します。MがGoコードを実行していない場合（例えば、システムコールでブロックされている場合や、Cgo呼び出しでCコードを実行している場合）、そのMはPから切り離され、別のMがPと関連付けられてGの実行を継続できます。

### Cgoと`dropm`

**Cgo**は、GoプログラムからC言語の関数を呼び出したり、C言語の関数からGoの関数を呼び出したりするためのメカニズムです。Cgoを使用すると、GoのランタイムとCのランタイムの間でコンテキストの切り替えが発生します。

Cgoコールバック（CコードからGoコードを呼び出す場合）では、GoランタイムはGoコードを実行するためにOSスレッド（M）を必要とします。もし現在のOSスレッドがGoランタイムによって管理されていない場合、Goランタイムは新しいMを取得するか、既存のアイドルなMを再利用してGoコードを実行します。Goコードの実行が完了し、再びCコードに戻る際には、GoランタイムはMを解放する必要があります。このMを解放し、ランタイムのMプールに戻す役割を担うのが`dropm`関数です。

`dropm`が適切に呼び出されないと、GoランタイムはMがまだ使用中であると誤解し、そのMを再利用可能なプールに戻しません。これにより、OSスレッドがリークし、システムリソースの枯渇やパフォーマンスの低下につながる可能性があります。

## 技術的詳細

このコミットの核心は、Cgoコールバックの入り口であるアセンブリコード（`cgocallback_gofunc`）において、現在のGoroutine（`g`）が有効なMを持っているかどうかを正確に判断し、必要に応じて`runtime.needm`を呼び出すロジックを修正することです。

以前の実装では、`g`が`nil`でない場合に無条件に`havem`ラベルにジャンプしていました。しかし、`g`が`nil`でない場合でも、その`g`が現在Mに関連付けられていない（つまり、`g.m`が`nil`である）状況が発生し得ました。このような場合、Goコードを実行するためには新しいMを取得するか、既存のMを再利用する必要があるため、`runtime.needm`を呼び出してMを確保するべきです。

修正後のロジックでは、`g`が`nil`であるかどうかに加えて、`g.m`が`nil`であるかどうかもチェックします。
1.  `g`が`nil`の場合、これはGoランタイムが管理していないスレッドからのコールバックであり、Mが確実に必要となるため、`needm`パスに進みます。
2.  `g`が`nil`でない場合でも、`g.m`が`nil`であれば、そのGoroutineは現在Mに関連付けられていないため、同様に`needm`パスに進みます。
3.  `g`が`nil`でなく、かつ`g.m`も`nil`でない場合（つまり、有効なMが既に存在する場合）にのみ、`havem`パスに進みます。

`needm`パスでは、`runtime.needm`関数が呼び出され、Goコードを実行するためのMが確保されます。この`runtime.needm`の呼び出しは、最終的に`dropm`が適切に呼び出されることを保証するGoランタイムのメカニズムの一部です。

また、このコミットでは、`runtime.getm`というテスト用のヘルパー関数が`proc.go`に追加されています。これは、現在のGoroutineが関連付けられているMのポインタを`uintptr`として返すもので、テストコードがMの同一性を確認するために使用されます。

新しいテストファイル`dropm.go`と`dropm_stub.go`は、Cgoコールバックが連続して行われた際に、常に同じMが使用されることを検証します。これは、`dropm`が適切に機能し、Mが不必要に解放されたり、新しいMが不必要に取得されたりしないことを保証するための重要なテストです。

## コアとなるコードの解説

変更の核心は、各アーキテクチャのアセンブリファイルにおける`cgocallback_gofunc`（または類似のCgoコールバックエントリポイント）のロジックです。

例えば、`src/runtime/asm_arm.s`の変更を見てみましょう。

**変更前:**
```assembly
	CMP	$0, g
	B.NE	havem
```
これは、「`g`が`nil`でなければ`havem`にジャンプする」というロジックでした。しかし、`g`が`nil`でなくても`g.m`が`nil`である可能性が考慮されていませんでした。

**変更後:**
```assembly
	CMP	$0, g
	B.EQ	needm

	MOVW	g_m(g), R8
	MOVW	R8, savedm-4(SP)
	B	havem

needm:
	MOVW	g, savedm-4(SP) // g is zero, so is m.
	MOVW	$runtime·needm(SB), R0
	BL	(R0)
```
この修正では、まず`g`が`nil`かどうかをチェックし、`nil`であれば`needm`ラベルにジャンプします。
`g`が`nil`でない場合、`g_m(g)`（`g.m`フィールド）をレジスタ`R8`にロードし、それをスタックに保存します。これにより、`g.m`が有効なMを指していることが確認されます。その後、`havem`ラベルにジャンプします。
もし`g`が`nil`であった場合、または`g.m`が`nil`であった場合（これは`needm`ラベルにジャンプする前の`g_m(g)`のロードで`R8`が`nil`になることで間接的に処理される）、`needm`ラベルに到達します。
`needm`ラベルでは、`runtime.needm`関数が呼び出されます。この関数は、Goコードを実行するために必要なMを確保し、現在のGoroutine（`g`）と関連付けます。これにより、CgoコールバックがGoコードを実行する際に常に適切なMが利用可能になり、かつそのMが最終的に`dropm`によって解放されるパスが保証されます。

`proc.go`に追加された`getm()`関数は、テストの目的で現在のMを取得するために使用されます。
```go
// A helper function for EnsureDropM.
func getm() uintptr {
	return uintptr(unsafe.Pointer(getg().m))
}
```
この関数は、`getg()`で現在のGoroutineを取得し、その`m`フィールド（現在のGoroutineが実行されているM）を`uintptr`として返します。これにより、テストコードはCgoコールバック中にMが変化しないことを検証できます。

`dropm.go`の`GoCheckM`関数は、CgoコールバックからGoに制御が戻るたびに呼び出され、`runtime_getm_for_test()`（`getm()`のテスト用ラッパー）を使って現在のMを取得し、以前に保存されたMと比較します。これにより、連続するCgoコールバックが同じM上で実行されていることを確認し、Mの不適切な解放や再取得がないことを検証します。

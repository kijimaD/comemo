# [インデックス 2009] ファイルの概要

このコミットは、Go言語の初期の`template`パッケージにおける重要なリファクタリングと、それに伴う`godoc`ツールの変更を含んでいます。主な目的は、テンプレートコードにパーサーのスタブ（骨格）を追加し、テンプレートエンジンの書き換えを可能にすることでした。これにより、テンプレートの解析と実行の責務が分離され、より柔軟で再利用可能なテンプレート処理が実現されました。また、`pretty`ツール（`godoc`の一部）における標準出力（stdout）から標準エラー出力（stderr）へのログ出力の変更も行われています。

## 元コミット内容

`template`コードに（スタブ）パーサーを追加し、書き換えを可能にする。
`pretty`を更新してそれを使用するようにする。
`pretty`の標準出力を標準エラー出力に変更する。

## 変更の背景

このコミットが行われた2009年4月は、Go言語がまだ一般に公開される前の初期開発段階でした。当時の`template`パッケージは、現在の`text/template`や`html/template`パッケージとは異なり、よりシンプルな構造を持っていたと考えられます。

コミットメッセージにある「(stub) parser to template code, enabling rewrite」という記述は、当時のテンプレートエンジンが、テンプレート文字列の解析（パース）と実行（エグゼキューション）のプロセスが密接に結合していた可能性を示唆しています。このような設計では、テンプレートの再利用性や、異なるデータソースでの複数回の実行が非効率になることがあります。

この変更の背景には、以下のような意図があったと推測されます。

1.  **責務の分離**: テンプレートの「解析」と「実行」という異なる責務を明確に分離することで、コードのモジュール性、保守性、テスト容易性を向上させる。
2.  **再利用性の向上**: 一度解析されたテンプレート構造をメモリ上に保持し、異なるデータや出力先に対して複数回実行できるようにする。これにより、テンプレートの再解析のオーバーヘッドを削減し、パフォーマンスを向上させる。
3.  **将来の拡張性**: パーサーのスタブを導入することで、将来的にテンプレート構文の拡張や、より高度な機能（例: テンプレートの継承、ブロック定義など）の実装に向けた基盤を構築する。
4.  **ログ出力の標準化**: `godoc`ツールにおけるログ出力を、通常のアプリケーション出力と区別するために、標準出力（stdout）から標準エラー出力（stderr）に切り替える。これは、UNIX系のシステムにおける一般的な慣習であり、スクリプトなどでの出力の扱いを容易にする。

特に、`template`パッケージの変更は、Go言語の設計哲学である「シンプルさ」と「効率性」を追求する初期段階において、重要なアーキテクチャ上の決定であったと言えます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の基本的な概念と、当時の`template`パッケージの役割に関する知識が必要です。

1.  **Go言語の`io`パッケージ**:
    *   `io.Writer`インターフェース: データを書き込むための抽象的なインターフェースです。ファイル、ネットワーク接続、標準出力など、様々な出力先を統一的に扱うために使用されます。このコミットでは、テンプレートの出力先として`io.Writer`が使われています。
    *   `os.Stdout`と`os.Stderr`: Go言語の`os`パッケージで提供される、標準出力と標準エラー出力への`io.Writer`の実装です。
        *   `os.Stdout`: プログラムの通常の出力（結果、情報メッセージなど）に使用されます。
        *   `os.Stderr`: エラーメッセージや診断情報など、プログラムの補助的な出力に使用されます。UNIX系のシステムでは、これらをリダイレクトして、通常の出力とエラー出力を分離して扱うことが一般的です。

2.  **Go言語の`reflect`パッケージ**:
    *   `reflect`パッケージは、実行時にGoの型情報（構造体、配列、インターフェースなど）を検査し、操作するための機能を提供します。
    *   `reflect.Value`: Goの任意の型の値を表す構造体です。これにより、型が不明なデータに対しても、フィールドの取得、メソッドの呼び出しなど、リフレクションによる操作が可能になります。
    *   `reflect.StructValue`, `reflect.ArrayValue`: `reflect.Value`の具体的な型であり、それぞれ構造体や配列の値を表します。
    *   `reflect.Indirect`: ポインタが指す先の値を取得するために使用されます。
    *   このコミットでは、テンプレートに渡されるデータ（`data interface{}`）を動的に検査し、その構造体フィールドや配列要素にアクセスするために`reflect`パッケージが多用されています。

3.  **Go言語の`template`パッケージ（初期の概念）**:
    *   このコミット当時の`template`パッケージは、現在の`text/template`や`html/template`の前身にあたります。その目的は、Goのデータ構造（特に構造体）を基にして、テキスト出力を生成することでした。
    *   テンプレートは、プレースホルダー（例: `{変数名}`）や制御構造（例: `{ .section データ }`、`{ .repeated セクション }`）を含むテキスト文字列として定義されます。
    *   エンジンは、これらのプレースホルダーを、提供されたデータ構造の対応する値で置き換え、制御構造に基づいて条件付きの出力や繰り返し処理を行います。
    *   「パーサー」は、テンプレート文字列を解析し、内部的な表現（抽象構文木など）に変換する部分です。
    *   「実行エンジン」は、解析された内部表現と提供されたデータを使って、最終的な出力を生成する部分です。

4.  **並行処理と`chan`**:
    *   Go言語の並行処理の基本要素であるゴルーチン（`go func() {}`）とチャネル（`chan`）が使用されています。
    *   `chan *os.Error`: エラーを非同期に通知するためのチャネルです。テンプレートの実行中に発生したエラーを、メインの処理に伝えるために使用されます。
    *   `sys.Goexit()`: 現在のゴルーチンを終了させるために使用されます。エラー発生時にテンプレートの生成を停止する目的で使われています。

これらの概念を理解することで、コミットで行われた変更の意図と技術的な詳細をより深く把握することができます。

## 技術的詳細

このコミットの最も重要な技術的変更は、`src/lib/template/template.go`におけるテンプレートエンジンのアーキテクチャの再設計です。

### 1. `template`構造体と`state`構造体の分離

*   **旧設計**: 以前の`template`構造体は、テンプレートの定義（`buf`, `p`, `fmap`）と、その実行状態（`errorchan`, `linenum`, `parent`, `data`, `wr`）の両方を持っていました。これは、テンプレートの解析と実行が密接に結合していることを意味します。
*   **新設計**:
    *   `Template`構造体（旧`template`がリネーム）は、テンプレートの定義（`fmap`, `buf`, `p`, `linenum`）のみを保持するようになりました。`linenum`は、テンプレートの入力における現在の行番号を追跡するためのものです。
    *   新たに`state`構造体が導入されました。この構造体は、特定のテンプレート実行の「状態」をカプセル化します。これには、親の`state`（ネストされたテンプレート用）、エラーチャネル、現在のデータ（`reflect.Value`）、および出力先（`io.Write`）が含まれます。
    *   これにより、`Template`オブジェクトは一度パースされれば、異なる`state`オブジェクト（異なるデータや出力先）を使って複数回実行できるようになります。

### 2. エラーハンドリングの変更

*   以前は`(*template).error`メソッドがエラーを処理していましたが、この責務が`(*state).error`メソッドに移されました。
*   これにより、エラーは特定の実行コンテキスト（`state`）に関連付けられ、テンプレート定義自体からは切り離されます。

### 3. テンプレート生成関数の変更

*   **`newTemplate`**:
    *   旧: `newTemplate(ch chan *os.Error, linenum *int, buf []byte, data reflect.Value, fmap FormatterMap, wr io.Write) *template`
    *   新: `newTemplate(buf []byte, fmap FormatterMap) *Template`
    *   新しい`newTemplate`は、テンプレートの定義に必要な情報（`buf`, `fmap`）のみを受け取り、実行状態に関する引数（`ch`, `linenum`, `data`, `wr`）は削除されました。`linenum`は`Template`構造体内に移動し、`new(int)`で初期化されます。
*   **`childTemplate`**:
    *   旧: `childTemplate(parent *template, buf []byte, data reflect.Value) *template`
    *   新: `childTemplate(parent *Template, buf []byte) *Template`
    *   同様に、`childTemplate`も実行状態に関する引数が削除され、親の`Template`から`fmap`と`linenum`を継承するようになりました。

### 4. `Parse`関数の導入

*   新たに`Parse`関数が導入されました: `func Parse(s string, fmap FormatterMap) (*Template, *os.Error, int)`
*   この関数は、テンプレート文字列（`s`）とフォーマッターマップ（`fmap`）を受け取り、解析された`Template`オブジェクトを返します。
*   `Parse`関数内でゴルーチンが起動され、`t.parse()`（現在はスタブ）が実行されます。これは、将来的に非同期でテンプレートを解析する可能性を示唆しています。
*   この変更により、テンプレートの「解析」と「実行」が明確に分離されました。ユーザーはまず`Parse`でテンプレートを解析し、その後に`Execute`メソッドを呼び出すことになります。

### 5. `Execute`関数の変更

*   旧: `func Execute(s string, data interface{}, fmap FormatterMap, wr io.Write) *os.Error`
*   新: `func (t *Template) Execute(data interface{}, wr io.Write) *os.Error`
*   `Execute`はグローバル関数から`Template`構造体のメソッドになりました。これは、`Template`オブジェクトが解析済みのテンプレート表現を保持し、それに対して実行を行うという新しい設計を反映しています。
*   `Execute`メソッドは、実行に必要なデータ（`data`）と出力先（`wr`）を受け取り、内部で新しい`state`オブジェクトを作成して、`t.execute(&state{nil, ch, val, wr})`のように実行を開始します。

### 6. メソッドシグネチャの変更

*   `nextItem`, `analyze`, `executeRepeated`, `executeSection`, `varValue`, `writeVariable`, `execute`といった、テンプレートの解析と実行に関わる多くのメソッドのシグネチャが変更され、`*state`引数を受け取るようになりました。
*   これにより、これらのメソッドは、テンプレート定義（`Template`）と実行コンテキスト（`state`）の両方にアクセスできるようになります。特に、エラー報告や変数解決（`findVar`, `varValue`）は、現在の実行状態（`state.data`や`state.errorchan`）に依存するようになりました。

### 7. `godoc.go`におけるログ出力の変更

*   `usr/gri/pretty/godoc.go`ファイルでは、`log.Stdoutf`の呼び出しがすべて`log.Stderrf`に変更されました。
*   これは、`godoc`が生成する通常のドキュメント出力と、エラーや診断メッセージを明確に分離するための変更です。これにより、`godoc`の出力をパイプで他のコマンドに渡す際に、エラーメッセージが混入するのを防ぐことができます。

### 8. `godoc.go`におけるテンプレートAPIの更新

*   `godoc.go`内の`servePage`関数で、テンプレートの実行方法が新しいAPIに準拠するように変更されました。
*   旧: `template.Execute(godoc_html, &d, nil, c);`
*   新:
    ```go
    templ, err, line := template.Parse(godoc_html, nil);
    if err != nil {
        log.Stderrf("template error %s:%d: %s\\n", title, line, err);
    } else {
        templ.Execute(&d, c);
    }
    ```
*   この変更は、まず`template.Parse`でテンプレートを解析し、エラーがなければその`Template`オブジェクトの`Execute`メソッドを呼び出すという、新しいテンプレートエンジンの利用パターンを示しています。

これらの変更は、Go言語の`template`パッケージが、より堅牢で、効率的で、拡張性の高い設計へと進化する上での重要な一歩でした。特に、解析と実行の分離は、現代の多くのテンプレートエンジンで見られる一般的な設計パターンであり、Go言語の標準ライブラリが初期段階からこのようなベストプラクティスを取り入れていたことを示しています。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、`src/lib/template/template.go`ファイルに集中しています。特に、`template`構造体のリネームと`state`構造体の導入、そして`Parse`関数の追加が重要です。

```go
// src/lib/template/template.go

// State for executing a Template
type state struct {
	parent	*state;	// parent in hierarchy
	errorchan	chan *os.Error;	// for erroring out
	data	reflect.Value;	// the driver data for this section etc.
	wr	io.Write;	// where to send output
}

// Report error and stop generation.
func (st *state) error(err *os.Error, args ...) {
	st.errorchan <- err;
	sys.Goexit();
}

type Template struct {
	fmap	FormatterMap;	// formatters for variables
	buf	[]byte;	// input text to process
	p	int;	// position in buf
	linenum	*int;	// position in input
}

// Create a top-level template
func newTemplate(buf []byte, fmap FormatterMap) *Template {
	t := new(Template);
	t.buf = buf;
	t.p = 0;
	t.fmap = fmap;
	t.linenum = new(int);
	return t;
}

// Create a template deriving from its parent
func childTemplate(parent *Template, buf []byte) *Template {
	t := new(Template);
	t.buf = buf;
	t.p = 0;
	t.fmap = parent.fmap;
	t.linenum = parent.linenum;
	return t;
}

func (t *Template) execute(st *state)
func (t *Template) executeSection(w []string, st *state)

// ... (many methods like nextItem, analyze, executeRepeated, executeSection, varValue, writeVariable now take `st *state` argument) ...

func (t *Template) parse() {
	// stub for now
}

func Parse(s string, fmap FormatterMap) (*Template, *os.Error, int) {
	ch := make(chan *os.Error);
	t := newTemplate(io.StringBytes(s), fmap);
	go func() {
		t.parse();
		ch <- nil;	// clean return;
	}();
	err := <-ch;
	if err != nil {
		return nil, err, *t.linenum
	}
	return t, nil, 0
}

func (t *Template) Execute(data interface{}, wr io.Write) *os.Error {
	// Extract the driver struct.
	val := reflect.Indirect(reflect.NewValue(data));
	sval, ok1 := val.(reflect.StructValue);
	if !ok1 || sval.Kind() != reflect.StructKind {
		return ErrNotStruct
	}
	ch := make(chan *os.Error);
	go func() {
		t.execute(&state{nil, ch, val, wr});
		ch <- nil;	// clean return;
	}();
	return <-ch;
}
```

## コアとなるコードの解説

上記のコード変更は、Go言語の`template`パッケージの設計思想を根本的に変えるものです。

1.  **`Template`と`state`の分離**:
    *   以前は`template`という単一の構造体が、テンプレートの静的な定義（テンプレート文字列、フォーマッターマップ）と、動的な実行状態（現在のデータ、出力先、エラーチャネル、親テンプレート）の両方を保持していました。
    *   新しい設計では、`Template`構造体はテンプレートの静的な定義のみを保持します。これは、一度パースされたテンプレートが、その後の実行で再利用されることを可能にします。
    *   `state`構造体は、特定のテンプレート実行の動的なコンテキスト（データ、出力先、エラーハンドリング）をカプセル化します。これにより、同じ`Template`オブジェクトを異なるデータや出力先で並行して実行することが可能になります。これは、Webサーバーなどで複数のリクエストに対して同じテンプレートを効率的にレンダリングする際に非常に重要です。

2.  **`Parse`関数の導入**:
    *   `Parse`関数は、テンプレート文字列を受け取り、それを解析して`Template`オブジェクトを生成する役割を担います。この関数は、テンプレートの構文解析（パース）フェーズを明確に定義し、実行フェーズから分離します。
    *   `t.parse()`は現在スタブですが、これは将来的に本格的なパーサーがここに実装されることを示唆しています。この分離により、テンプレートの構文解析エラーは実行時ではなく、解析時に捕捉できるようになります。
    *   `Parse`がゴルーチン内で`t.parse()`を呼び出し、チャネルを通じてエラーを返す設計は、非同期での解析処理を可能にするための初期の試みであったと考えられます。

3.  **`Template.Execute`メソッドへの変更**:
    *   以前のグローバルな`Execute`関数は、テンプレート文字列を毎回受け取り、その場で解析・実行を行っていました。
    *   新しい`Template.Execute`メソッドは、既に解析済みの`Template`オブジェクトに対して呼び出されます。これにより、テンプレートの解析コストを一度だけ支払い、複数回実行できる「プリコンパイルされたテンプレート」のような振る舞いが実現されます。
    *   `Execute`メソッドは、内部で新しい`state`オブジェクトを作成し、その`state`を引数として`t.execute`（テンプレートの実際の実行ロジック）を呼び出します。これにより、実行コンテキストが明確に渡され、テンプレートの実行が`state`に依存するようになります。

4.  **エラーハンドリングの改善**:
    *   `error`メソッドが`state`に移動したことで、エラーは特定の実行コンテキストに関連付けられます。これにより、どのテンプレートのどの実行中にエラーが発生したかをより正確に追跡できるようになります。
    *   `sys.Goexit()`の使用は、エラーが発生したゴルーチンを即座に終了させ、テンプレートの生成を停止するためのものです。

これらの変更は、Go言語の`template`パッケージが、よりスケーラブルで、効率的で、堅牢なテンプレートエンジンへと進化するための基盤を築きました。特に、解析と実行の分離は、現代の多くのプログラミング言語におけるテンプレートエンジンの標準的な設計パターンであり、Go言語が初期段階からこの方向性を取り入れていたことは注目に値します。

## 変更の背景

このコミットは、Goの`net`パッケージにおける`TestLookupDotsWithLocalSource`というテストが、一部のシステム環境で失敗するという問題（Issue #14050）を解決するために導入されました。このテストは、ローカルのホスト名解決（例えば`/etc/hosts`ファイルを使用する場合）において、ホスト名の末尾にドットが付いている場合（例: `localhost.`）の挙動を検証することを目的としていました。

問題の核心は、一部のシステムでは、`localhost.`のようなクエリに対して、`localhost.`だけでなく`localhost`も同時に解決結果として返すことがありました。元のテストロジックでは、末尾にドットが付いているホスト名が返された場合、それがドットなしの形式（例: `localhost`）に変換されることを期待しており、もしドット付きの形式がそのまま残っていたり、予期せぬ形式で返されたりするとエラーとしていました。しかし、システムによっては、`127.0.0.1 localhost localhost.`のように、ドット付きとドットなしの両方の形式を返すことが正当な挙動であるため、テストが過度に厳格であると判断されました。

このコミットは、このようなシステム固有の挙動を許容するようにテストの検証ロジックを緩和し、テストの信頼性を向上させることを目的としています。

## 前提知識の解説

### 1. DNSとホスト名解決
コンピュータがネットワーク上の他のデバイスと通信する際、人間が覚えやすいホスト名（例: `www.example.com`）を、コンピュータが理解できるIPアドレス（例: `93.184.216.34`）に変換する必要があります。このプロセスを「ホスト名解決」と呼びます。
ホスト名解決には主に以下の方法があります。
*   **`/etc/hosts`ファイル（Linux/macOS）または`hosts`ファイル（Windows）**: ローカルに保存された静的なマッピングファイルで、DNSサーバーに問い合わせる前に参照されます。
*   **DNS (Domain Name System)**: ドメイン名とIPアドレスを対応させる分散データベースシステムです。

### 2. FQDN (Fully Qualified Domain Name) と末尾のドット
FQDNは、インターネット上のホストを一意に識別する完全なドメイン名です。例えば、`www.example.com.`のように、末尾にドットが付くのが正式なFQDNの表記です。この末尾のドットは、その名前がルートドメインからの絶対パスであることを示します。しかし、多くのアプリケーションやユーザーは、利便性のため末尾のドットを省略して使用します（例: `www.example.com`）。DNSリゾルバは通常、この省略された形式を自動的に補完して処理します。

### 3. Go言語の`net`パッケージ
Go言語の標準ライブラリである`net`パッケージは、ネットワークI/Oのプリミティブを提供します。これには、TCP/IP、UDP、IPアドレスの操作、そしてホスト名解決（DNSルックアップ）のための機能が含まれます。`net.LookupHost`や`net.LookupIP`などの関数がホスト名解決を担当します。これらの関数は、システムのDNS設定や`/etc/hosts`ファイルを参照して名前解決を行います。

### 4. Go言語のテストフレームワーク
Go言語には、`testing`パッケージという組み込みのテストフレームワークがあります。テスト関数は`Test`で始まり、`*testing.T`型の引数を取ります。`t.Errorf`はテストが失敗したことを報告し、指定されたメッセージを出力します。

## 技術的詳細

`TestLookupDotsWithLocalSource`テストは、`net`パッケージがローカルソース（`/etc/hosts`など）からホスト名を解決する際の挙動、特に末尾のドットの扱いを検証します。このテストは、`localhost.`のような名前をルックアップした際に、返されるホスト名リストに`localhost.`が含まれていて、かつそれが`localhost`に変換されていない場合にエラーを報告するように設計されていました。

しかし、一部のシステム（特に`/etc/hosts`ファイルの設定によっては）では、`localhost.`をルックアップした際に、結果として`localhost.`と`localhost`の両方が返されることがあります。これは、システムが両方の形式を同じエントリに関連付けているためです。元のテストロジックでは、`strings.Index(name, ".") == len(name)-1`という条件で末尾にドットがある名前を検出し、それがドットなしの形式に変換されていない場合にエラーとしていました。この厳格なチェックが、正当なシステム挙動を誤ってエラーとして検出してしまっていたのです。

このコミットによる修正は、このテストの厳格さを緩和し、システムが`localhost.`と`localhost`の両方を返す場合でもテストが成功するようにします。具体的には、末尾にドットがある名前（例: `localhost.`）が見つかった場合、その名前からドットを取り除いた形式（例: `localhost`）が、解決結果のリスト内に存在するかどうかを確認します。もし存在すれば、それは許容される挙動とみなし、エラーを報告せずにテストを続行します。これにより、テストはより現実的なシステム環境に対応できるようになります。

## コアとなるコードの解説

変更の中心は、`for _, name := range names`ループが`for i, name := range names`に変更され、その内部に新しいネストされたループと`loop:`ラベルが追加された点です。

1.  **`loop:`ラベルの追加**:
    `loop:`というラベルが外側の`for`ループに付けられています。これは、内側のループから特定の条件で外側のループ全体をスキップするために使用されます。

2.  **内側の`for`ループの追加**:
    ```go
    for j := range names {
        if j == i {
            continue
        }
        if names[j] == name[:len(name)-1] {
            // It's OK if we find the name without the dot,
            // as some systems say 127.0.0.1 localhost localhost.
            continue loop
        }
    }
    ```
    この新しいループは、現在の`name`（末尾にドットが付いていると仮定）に対して、解決結果のリスト`names`全体を再度走査します。
    *   `if j == i { continue }`: 現在処理している`name`自身との比較を避けるための条件です。
    *   `if names[j] == name[:len(name)-1]`: ここが修正の核心です。もし、現在の`name`から末尾のドットを取り除いた形式（例: `localhost`）が、解決結果のリスト`names`のどこかに存在する場合、この条件が真となります。
    *   `continue loop`: 上記の条件が真となった場合、つまり、ドット付きの名前とドットなしの名前の両方が解決結果に含まれている場合は、現在の`name`に対するエラーチェックをスキップし、外側の`for`ループの次の要素の処理に移ります。これは、`127.0.0.1 localhost localhost.`のように、システムが両方の形式を返すことが許容されるためです。

この変更により、テストは「末尾にドットが付いたホスト名が返された場合、ドットなしの対応するホスト名も同時に返されていればOK」という、より柔軟な検証ロジックを持つことになります。これにより、特定のシステム環境での誤ったテスト失敗が解消され、テストの堅牢性が向上しました。

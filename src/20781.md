# [インデックス 20781] ファイルの概要

このコミット（インデックス 20781、ハッシュ `17a108ba079cd3e94fa4d847d651d3a813569a9b`）は、GoランタイムがWindows環境で発生するあらゆる種類の例外をより包括的に処理できるようにすることを目的としていました。具体的には、WindowsのVectored Exception Handling (VEH) メカニズムをGoランタイムに統合し、未処理の例外によってGoプログラムが予期せず終了するのを防ぐための改善が試みられました。

しかし、このコミットは後に `golang.org/cl/154180043` によってリバートされました。その主な理由は、Goのビルドシステム（特にWindows環境）でのビルド失敗と、パフォーマンスベンチマークにおける顕著な性能低下が確認されたためです。この事実は、低レベルのランタイムにおける変更が、システムの安定性と性能に与える影響の大きさを浮き彫りにしています。

## 変更の背景

GoプログラムがWindows上で実行される際、様々な種類の例外（例: ゼロ除算、無効なメモリアクセスなど）が発生する可能性があります。これらの例外がGoランタイムによって適切に捕捉・処理されない場合、プログラムはクラッシュし、予期せぬ終了を引き起こします。このコミットは、GoランタイムがWindowsのネイティブな例外処理メカニズムをより深く統合することで、このようなクラッシュを防ぎ、Goアプリケーションの堅牢性を向上させることを目指しました。

コミットメッセージにある "Fixes #8006" は、Goの内部的な課題追跡システムにおける特定の未処理例外に関する問題を示唆しています。この変更は、Goのパニック/リカバリモデルとWindowsの例外処理をよりシームレスに連携させ、GoプログラムがOSレベルの例外をGoのランタイムエラーとして適切に処理できるようにすることを意図していました。

しかし、前述の通り、この変更は最終的にリバートされました。これは、Goのビルドシステムにおける互換性の問題や、特に `windows-amd64-perf` ビルダーでのパフォーマンス低下（`json-1` で3.21%、`json-2` で3.59%、`json-4` で4.42%のCPU時間増加など）が確認されたためです。Goプロジェクトは性能を非常に重視しており、このような性能劣化は許容されなかったため、変更は取り消されました。

## 前提知識の解説

このコミットを理解するためには、Windowsの例外処理メカニズムとGoランタイムの基本的な動作に関する知識が必要です。

### Windowsの例外処理メカニズム

Windowsオペレーティングシステムは、プログラムの実行中に発生する異常なイベント（例外）を処理するための複数のメカニズムを提供しています。

1.  **Structured Exception Handling (SEH)**:
    SEHは、Windowsにおける基本的な例外処理メカニズムです。C/C++言語の `__try`, `__except`, `__finally` ブロックなどを用いて、特定のコードブロック内で発生した例外を捕捉・処理します。SEHはスタックベースであり、例外が発生した時点のコールスタックを遡って適切なハンドラを探します。

2.  **Vectored Exception Handling (VEH)**:
    VEHはWindows XPで導入された、SEHよりも高レベルで柔軟な例外処理メカニズムです。`AddVectoredExceptionHandler` 関数を使用して登録されるVEHハンドラは、プロセス全体にわたって機能し、SEHハンドラよりも**先に**呼び出されます。これにより、アプリケーションはOSが例外を処理する前に、またはデバッガが例外を捕捉する前に、例外をインターセプトして独自の処理を行うことができます。
    *   `AddVectoredExceptionHandler(First, VectoredHandler)`: 例外ハンドラを登録します。`First` パラメータが非ゼロの場合、ハンドラはリストの先頭に追加され、最初に呼び出されます。ゼロの場合、リストの末尾に追加されます。
    *   VEHハンドラは、例外を処理した後に `EXCEPTION_CONTINUE_EXECUTION` を返すことで実行を継続させたり、`EXCEPTION_CONTINUE_SEARCH` を返すことで次のハンドラに処理を委ねたりすることができます。

3.  **`SetUnhandledExceptionFilter`**:
    この関数は、プロセス内で発生した例外が、他のどの例外ハンドラ（SEHやVEHなど）によっても処理されずに最終的に未処理となった場合に呼び出される、単一のトップレベル例外ハンドラを設定します。通常、クラッシュレポートの生成やクリーンアップ処理のために使用されます。デバッガがアタッチされている場合、このハンドラは通常呼び出されず、例外はデバッガに直接渡されます。

### Goランタイムのシグナルハンドリングと `sigtramp`

Goランタイムは、OSからのシグナル（Unix系OSのシグナルやWindowsの例外など）をGoのパニックメカニズムに変換して処理します。

*   **`sigtramp` (Signal Trampoline)**:
    `sigtramp` は、Goランタイム内の低レベルなアセンブリコードのエントリポイントです。OSがGoプログラムにシグナル（Windowsの場合は例外）を送信すると、実行はまずカーネル空間に入り、その後ユーザー空間のシグナルハンドラに遷移します。`sigtramp` は、この最初のユーザー空間コードであり、適切なゴルーチン (`g`) コンテキストを設定するなど、Goランタイム環境を準備してから、より高レベルのGoシグナルハンドリング関数（例: `sighandler` や `exceptionhandler`）を呼び出します。これは、OSからの非同期イベントをGoの実行モデルに橋渡しする重要な役割を担っています。

## 技術的詳細

このコミットは、GoランタイムがWindowsの例外を捕捉し、Goのパニックとして処理するメカニズムを強化するために、主に以下の変更を導入しました。

1.  **VEHハンドラの導入**:
    従来のGoランタイムは、Windowsの例外処理に対して `SetUnhandledExceptionFilter` を使用するか、限定的なVEHハンドラを登録していました。このコミットでは、`AddVectoredExceptionHandler` を用いて、より包括的なVEHハンドラを登録するように変更されました。
    *   `runtime·exceptiontramp`: メインの例外ハンドラとして登録されます。Goのコード内で発生した例外を捕捉し、Goの `panic` メカニズムに変換することを目的としています。
    *   `runtime·firstcontinuetramp`: `AddVectoredContinueHandler` (もし利用可能であれば) を使って登録される最初の継続ハンドラです。これは、`exceptiontramp` が例外を処理した場合に、それ以降の継続ハンドラの検索を停止させる役割を担います。
    *   `runtime·lastcontinuetramp`: 最後の継続ハンドラとして登録されます。Goランタイムが例外を処理できなかった場合に、クラッシュ情報を出力してプログラムを終了させる役割を持ちます。これは、`SetUnhandledExceptionFilter` が利用できない場合のフォールバックとしても機能します。

2.  **`defs_windows.go` およびヘッダファイルの変更**:
    Windows APIの定数である `EXCEPTION_CONTINUE_EXECUTION` と `EXCEPTION_CONTINUE_SEARCH` がGoランタイムの定義に追加されました。これらはVEHハンドラが例外処理後にOSに返す値であり、それぞれ「実行を継続する」または「次のハンドラを検索する」ことを意味します。

3.  **`os_windows.c` の変更**:
    *   `runtime·SetUnhandledExceptionFilter` の `dynimport` が追加され、このAPIが動的にロードされるようになりました。
    *   `runtime·osinit` 関数内で、例外ハンドラの登録ロジックが変更されました。
        *   以前は `runtime·sigtramp` を `AddVectoredExceptionHandler` に登録していました。
        *   変更後は、まず `runtime·exceptiontramp` を `AddVectoredExceptionHandler` に登録します。
        *   次に、`kernel32.dll` から `AddVectoredContinueHandler` を動的に取得しようとします。
        *   `AddVectoredContinueHandler` が利用可能であれば、`runtime·firstcontinuetramp` と `runtime·lastcontinuetramp` を登録します。
        *   利用できない場合は、フォールバックとして `runtime·SetUnhandledExceptionFilter` を使って `runtime·lastcontinuetramp` を登録します。これは、デバッグ中に `SetUnhandledExceptionFilter` ハンドラが呼び出されないという注意書きがあります。
    *   `runtime·initsig` 関数では、新しいハンドラ関数 (`exceptiontramp`, `firstcontinuetramp`, `lastcontinuetramp`) がリンカによって削除されないように `USED` マクロで参照されています。

4.  **`os_windows_386.c` および `os_windows_amd64.c` の変更**:
    *   `runtime·sighandler` 関数が `runtime·exceptionhandler` にリネームされ、その戻り値の型が `uint32` に変更され、`EXCEPTION_CONTINUE_EXECUTION` または `EXCEPTION_CONTINUE_SEARCH` を返すようになりました。
    *   `runtime·isgoexception` という新しいヘルパー関数が導入され、例外がGoの実行範囲内で発生したものであり、Goが処理すべきシグナルであるかを判断するようになりました。
    *   `runtime·lastcontinuehandler` という新しい関数が追加され、Goランタイムが例外を処理できなかった場合の最終的な処理（クラッシュ情報の出力と終了）を担うようになりました。
    *   `runtime·firstcontinuehandler` (amd64のみ) が追加され、`exceptionhandler` が例外を処理した場合に、それ以降の継続ハンドラの検索を停止させる役割を担います。

5.  **`sys_windows_386.s` および `sys_windows_amd64.s` の変更**:
    *   `runtime·sigtramp` アセンブリルーチンが汎用化され、特定のハンドラ関数を直接呼び出すのではなく、レジスタ (`AX` または `R15`) に格納されたハンドラアドレスを呼び出すように変更されました。これにより、`sigtramp` は `exceptiontramp`, `firstcontinuetramp`, `lastcontinuetramp` といった異なるハンドラのエントリポイントとして機能できるようになりました。
    *   `runtime·exceptiontramp`, `runtime·firstcontinuetramp`, `runtime·lastcontinuetramp` という新しいアセンブリルーチンが追加されました。これらはそれぞれ対応するC言語のハンドラ関数 (`runtime·exceptionhandler`, `runtime·firstcontinuehandler`, `runtime·lastcontinuehandler`) を呼び出すための薄いラッパーとして機能します。

6.  **`syscall_windows_test.go` の変更**:
    *   `TestRaiseException` と `TestZeroDivisionException` という新しいテストが追加されました。これらは、Goプログラム内で意図的にWindows例外（`RaiseException` によるカスタム例外とゼロ除算例外）を発生させ、Goランタイムがそれらを適切に捕捉し、Goのパニックとして処理できることを検証するためのものです。

このコミットは、GoランタイムがWindowsの低レベルな例外処理メカニズムとより深く連携し、Goのパニック/リカバリモデルとの統合を強化しようとする試みでした。しかし、その複雑さと、Goのクロスプラットフォームな性質における互換性および性能への影響が大きかったため、最終的にはリバートされることになりました。

特に、`os_windows.c`、`os_windows_386.c`、`os_windows_amd64.c` はWindows固有のランタイム処理を記述しており、例外ハンドラの登録ロジックが変更されています。また、`sys_windows_386.s` と `sys_windows_amd64.s` は、OSからの例外通知を受け取るアセンブリレベルの `sigtramp` ルーチンが、新しいVEHハンドラを呼び出すように修正されています。

## コアとなるコードの解説

### `src/runtime/os_windows.c` (および `os_windows_386.c`, `os_windows_amd64.c`)

これらのファイルでは、Goランタイムの初期化 (`runtime·osinit`) 時にWindowsの例外ハンドラを登録するロジックが変更されました。

*   **変更前**: 主に `runtime·sigtramp` を `AddVectoredExceptionHandler` に登録していました。
*   **変更後**:
    *   `runtime·exceptiontramp` を最初のVEHハンドラとして登録します。これは、Goの実行コンテキスト内で発生した例外を捕捉し、Goのパニックに変換する主要な役割を担います。
    *   `AddVectoredContinueHandler` の存在を確認し、利用可能であれば `runtime·firstcontinuetramp` と `runtime·lastcontinuetramp` を継続ハンドラとして登録します。
    *   `AddVectoredContinueHandler` が利用できない場合、`SetUnhandledExceptionFilter` を使用して `runtime·lastcontinuetramp` を最終的な未処理例外ハンドラとして設定します。
    *   `runtime·exceptionhandler` (旧 `runtime·sighandler`) 関数は、例外がGoのコード範囲内で発生したものであるか (`runtime·isgoexception`) を確認し、Goが処理すべき例外であれば、現在のゴルーチン (`g`) のコンテキストに例外情報を設定し、`runtime·sigpanic` を呼び出すようにスタックを操作します。これにより、Windowsのネイティブ例外がGoのパニックとして扱われます。
    *   `runtime·lastcontinuehandler` は、Goランタイムが例外を処理できなかった場合の最終手段として、クラッシュ情報を出力し、プログラムを終了させます。

### `src/runtime/sys_windows_386.s` および `src/runtime/sys_windows_amd64.s`

これらのアセンブリファイルでは、`runtime·sigtramp` ルーチンが汎用化されました。

*   **変更前**: `runtime·sigtramp` は直接 `runtime·sighandler` を呼び出していました。
*   **変更後**: `runtime·sigtramp` は、呼び出し元から渡されたハンドラのアドレス（レジスタ `AX` または `R15` に格納）を間接的に呼び出すように変更されました。これにより、`runtime·osinit` で登録された `runtime·exceptiontramp`、`runtime·firstcontinuetramp`、`runtime·lastcontinuetramp` といった異なるハンドラが、`sigtramp` を介して実行されるようになりました。
*   新しく追加された `runtime·exceptiontramp`, `runtime·firstcontinuetramp`, `runtime·lastcontinuetramp` アセンブリルーチンは、それぞれ対応するC言語のハンドラ関数へのジャンプ命令を含んでいます。これらは、WindowsのVEHメカニズムがアセンブリレベルのエントリポイントを必要とするための中間層として機能します。

これらの変更は、GoランタイムがWindowsの例外処理パイプラインに深く介入し、OSレベルの例外をGoのランタイムエラーとして一元的に管理しようとする意図を示しています。

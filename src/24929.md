## 元コミット内容

`html/template: preserve attr in stateBeforeValue`

このコミットは、`html/template` パッケージにおいて、`stateBeforeValue` ステート（属性値の読み取り前）に `attr` コンテキストを保持するように変更します。これは、`<script type="text/template">` の内容がJavaScriptとして扱われ、`//` が正規表現として解釈される問題（Issue #12149）に対処するための準備です。この変更により、属性値を読み取る際に正しい属性コンテキストが利用可能になります。実際のバグ修正は次のコミットで行われます。

## 変更の背景

この変更の背景には、Goの `html/template` パッケージが提供する自動エスケープ機能の正確性に関する問題があります。特に、Issue #12149で報告された問題は、`<script type="text/template">` のような特定のHTML要素の内容が、テンプレートエンジンによって誤ってJavaScriptコードとして解釈されてしまうというものでした。

`html/template` パッケージは、クロスサイトスクリプティング（XSS）攻撃を防ぐために、出力されるHTMLコンテンツを自動的にエスケープします。このエスケープ処理は、現在のコンテキスト（HTMLタグ内、属性値内、JavaScriptコード内、CSSコード内など）に応じて異なるルールを適用する必要があります。例えば、HTML属性値としてURLが期待される場合と、JavaScriptコードが期待される場合では、エスケープの仕方が異なります。

問題は、テンプレートエンジンが `<script type="text/template">` のようなタグの内容を処理する際に、その `type="text/template"` 属性を正しく認識せず、内部のコンテンツをJavaScriptとして扱ってしまった点にあります。JavaScriptコンテキストでは、`//` は行コメントの開始を意味しますが、これが正規表現リテラルの開始と誤解釈される可能性があり、結果としてエスケープ処理が不適切になり、セキュリティ上の脆弱性につながる恐れがありました。

このコミットは、この根本的な問題に対処するための直接的な修正ではなく、その後の修正を可能にするための基盤となる変更です。具体的には、属性値を解析する際に、その属性がどのような種類（URL、JavaScriptイベントハンドラ、CSSスタイルなど）であるかを示す `context.attr` フィールドが、状態遷移の過程で失われないようにすることで、より正確なコンテキスト認識を可能にしようとしています。

## 前提知識の解説

### Go言語の `html/template` パッケージ

`html/template` パッケージは、Go言語の標準ライブラリの一部であり、HTML出力を生成するためのテンプレートエンジンを提供します。このパッケージの最大の特徴は、**コンテキストに応じた自動エスケープ**機能です。これにより、開発者が明示的にエスケープ処理を記述しなくても、XSSなどのWeb脆弱性からアプリケーションを保護することができます。

テンプレートエンジンは、入力されたテンプレートとデータに基づいて最終的なHTMLを生成する際に、出力される各部分がHTMLドキュメントのどのコンテキストに位置するかを内部的に追跡します。例えば、`<a href="...">` の `...` の部分はURLコンテキスト、`<script>...</script>` の `...` の部分はJavaScriptコンテキスト、`<style>...</style>` の `...` の部分はCSSコンテキストと判断されます。このコンテキスト情報に基づいて、適切なエスケープ処理（例: HTMLエンティティへの変換、URLエンコード、JavaScript文字列リテラルエスケープなど）が適用されます。

### エスケープ処理における「コンテキスト」と「状態遷移」

`html/template` のエスケープ処理は、ステートマシン（状態機械）として実装されています。HTMLドキュメントを解析する際、パーサーは現在の位置に応じて様々な「状態（state）」を遷移します。例えば、`stateText`（通常のテキスト）、`stateTag`（タグ内）、`stateAttrName`（属性名内）、`stateBeforeValue`（属性値の開始前）、`stateURL`（URL属性値内）、`stateJS`（JavaScriptコンテキスト内）、`stateCSS`（CSSコンテキスト内）などがあります。

これらの状態に加えて、`context` 構造体は、現在のエスケープ処理に必要な追加情報（例: 属性の種類 `attr`、区切り文字 `delim`、URLのどの部分か `urlPart` など）を保持します。

*   **`context.attr`**: 現在処理中のHTML属性の種類を示します。例えば、`attrURL`（`href`属性など）、`attrScript`（`onclick`属性など）、`attrStyle`（`style`属性など）といった値を取ります。この情報は、属性値の内容をどのようにエスケープすべきかを決定するために非常に重要です。
*   **`stateBeforeValue`**: HTMLタグ内で属性名が解析された後、その属性の値が始まる直前の状態を指します。例えば、`<a href=` の `=` の直後や、`<a href =` の `=` の直後のスペースの後などがこの状態に該当します。

### Issue #12149 の問題点

`<script type="text/template">` のようなタグは、ブラウザによってJavaScriptとして実行されることを意図していません。しかし、`html/template` のエスケープロジックが `type="text/template"` 属性を正しく解釈できず、内部のコンテンツをJavaScriptコンテキストとして扱ってしまった場合、以下のような問題が発生します。

1.  **誤ったエスケープ**: テンプレート内の `//` がJavaScriptの行コメント開始として扱われるべきか、あるいは正規表現リテラルの開始として扱われるべきか、といった判断が誤る可能性があります。
2.  **セキュリティリスク**: 最悪の場合、この誤解釈がエスケープのバイパスにつながり、悪意のあるスクリプトが実行されるXSS脆弱性を引き起こす可能性があります。

このコミットは、`stateBeforeValue` に遷移する際に `context.attr` の情報が失われることで、後続の属性値の解析が不正確になることを防ぐためのものです。`context.attr` が正しく保持されれば、テンプレートエンジンは属性値のコンテキストをより正確に判断できるようになり、結果として適切なエスケープ処理を適用できるようになります。

## 技術的詳細

このコミットの技術的な核心は、`html/template` パッケージのステートマシンにおける `context` 構造体の `attr` フィールドのライフサイクル管理の改善にあります。

### `src/html/template/context.go` の変更

`attr` 型のコメントが変更されています。

変更前:
```go
// attr identifies the most recent HTML attribute when inside a start tag.
```

変更後:
```go
// attr identifies the current HTML attribute when inside the attribute,
// that is, starting from stateAttrName until stateTag/stateText (exclusive).
```

このコメント変更は、`attr` フィールドの役割と有効範囲をより明確に定義しています。以前は「最も最近のHTML属性」とされていましたが、変更後は「属性内にある現在のHTML属性」であり、その有効期間が `stateAttrName` から `stateTag`/`stateText` に遷移するまで（排他的に）であることを示しています。これは、`attr` 情報が属性値の解析中も継続して必要とされるという、このコミットの意図を反映しています。

### `src/html/template/escape_test.go` の変更

このファイルでは、`TestEscapeText` 関数内の多数のテストケースが更新されています。具体的には、`context` 構造体の初期化において、`attr` フィールドが明示的に設定されるようになっています。

例:
変更前:
```go
			context{state: stateURL, delim: delimSpaceOrTagEnd, urlPart: urlPartPreQuery},
```
変更後:
```go
			context{state: stateURL, delim: delimSpaceOrTagEnd, urlPart: urlPartPreQuery, attr: attrURL},
```

この変更は、エスケープ処理のテストにおいて、`attr` フィールドがコンテキストの一部として重要であることを示しています。以前は `attr` がデフォルト値（`attrNone`）のままであったか、あるいはテストで考慮されていなかったケースでも、今後はその属性の種類を明示的に指定することで、より厳密な状態管理が求められるようになったことを意味します。これにより、`stateBeforeValue` などの状態遷移後も `attr` が正しく保持されているかを検証できるようになります。

特に、`onclick` 属性に関連するテストケースでは `attr: attrScript` が、`style` 属性に関連するテストケースでは `attr: attrStyle` が追加されており、JavaScriptやCSSコンテキストにおける属性の識別が強化されていることがわかります。

### `src/html/template/transition.go` の変更

`tBeforeValue` 関数が変更されています。この関数は、属性値の開始直前の状態 (`stateBeforeValue`) に遷移する際のロジックを扱います。

変更前:
```go
	c.state, c.delim, c.attr = attrStartStates[c.attr], delim, attrNone
```

変更後:
```go
	c.state, c.delim = attrStartStates[c.attr], delim
```

この変更がこのコミットの最も重要な部分です。変更前は、`stateBeforeValue` に遷移する際に `c.attr` が `attrNone` にリセットされていました。これは、属性値の解析が始まる直前で、その属性が何であったかという情報が失われてしまうことを意味します。

変更後は、`c.attr = attrNone` の部分が削除されています。これにより、`tBeforeValue` 関数が呼び出された時点での `c.attr` の値がそのまま保持されるようになります。つまり、`stateAttrName` から `stateBeforeValue` に遷移しても、`attr` の情報（例: `attrURL`, `attrScript`, `attrStyle`）が失われずに次の状態に引き継がれることになります。

この `attr` 情報の保持は、属性値の内容を解析する際に、その属性がどのような種類であるかに基づいて適切なエスケープルールを適用するために不可欠です。例えば、`onclick` 属性の値はJavaScriptとして、`href` 属性の値はURLとして解析されるべきであり、この判断には `attr` の値が利用されます。

### 変更の全体的な影響

このコミット自体は、直接的なバグ修正を行うものではありませんが、`html/template` のエスケープエンジンがコンテキスト情報をより正確に、かつ継続的に保持できるようにするための重要な基盤変更です。`attr` 情報が `stateBeforeValue` で失われなくなることで、後続のコミットでIssue #12149のような問題（`<script type="text/template">` の内容が誤ってJavaScriptとして扱われるなど）を修正するための正確なコンテキスト判断が可能になります。これは、テンプレートエンジンの堅牢性とセキュリティを向上させる上で不可欠なステップです。

## コアとなるコードの解説

このコミットの最も重要な変更は `src/html/template/transition.go` の `tBeforeValue` 関数にあります。

```go
// transition.go の tBeforeValue 関数内の変更
// 変更前:
// 	c.state, c.delim, c.attr = attrStartStates[c.attr], delim, attrNone
// 変更後:
// 	c.state, c.delim = attrStartStates[c.attr], delim
```

この変更は、`html/template` のエスケープ処理における状態遷移ロジックの核心に触れています。`tBeforeValue` 関数は、HTMLタグ内で属性名が解析され、その属性値が始まる直前の状態 (`stateBeforeValue`) に入る際に呼び出されます。

変更前は、この関数が実行されると、`context` 構造体の `attr` フィールドが `attrNone` に明示的にリセットされていました。これは、属性値の解析が始まる時点で、その属性が `href` なのか `onclick` なのか `style` なのかといった重要な情報が失われてしまうことを意味します。

例えば、`<a onclick=` のように `onclick` 属性が検出された後、`stateBeforeValue` に遷移する際に `attr` が `attrScript` から `attrNone` にリセットされてしまうと、その後の属性値（JavaScriptコード）の解析時に、それがJavaScriptコンテキストであるという情報が失われ、誤ったエスケープ処理が適用される可能性がありました。

変更後は、`c.attr = attrNone` が削除されたため、`tBeforeValue` が呼び出される前の `c.attr` の値がそのまま保持されます。これにより、属性値の解析中も、その属性がどのような種類であるかというコンテキスト情報が常に利用可能になります。

この `attr` 情報の保持は、特に以下のようなシナリオで重要です。

*   **JavaScript属性 (`onclick`, `onmouseover` など)**: 属性値がJavaScriptコードとして解析されるべきであることを正確に識別し、JavaScriptのエスケープルールを適用します。
*   **URL属性 (`href`, `src` など)**: 属性値がURLとして解析されるべきであることを識別し、URLエンコードなどのルールを適用します。
*   **CSS属性 (`style` など)**: 属性値がCSSコードとして解析されるべきであることを識別し、CSSのエスケープルールを適用します。

`src/html/template/escape_test.go` でのテストケースの更新は、この `attr` フィールドの重要性を反映しており、エスケープ処理の各段階で `attr` が正しく伝播されているかを検証するためのものです。

このコミットは、直接的なバグ修正というよりも、エスケープエンジンの内部状態管理をより正確にし、将来的なバグ修正（Issue #12149のような問題）のための前提条件を整える「準備的な変更」であると言えます。

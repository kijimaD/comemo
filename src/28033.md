# [インデックス 28033] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるスタックバリアの管理方法を変更し、特に並行マークフェーズ中のスタックバリアの削除タイミングを最適化するものです。これにより、GCの「Stop-The-World (STW)」フェーズのコストを削減し、クリーンなスタックのスキャンを効率化することを目指しています。

## コミット

```
commit 269c969c81774d1579e80a8c35edbd0ebea065a7
Author: Austin Clements <austin@google.com>
Date:   Wed Mar 2 14:52:08 2016 -0500

    runtime: remove stack barriers during concurrent mark
    
    Currently we remove stack barriers during STW mark termination, which
    has a non-trivial per-goroutine cost and means that we have to touch
    even clean stacks during mark termination. However, there's no problem
    with leaving them in during the sweep phase. They just have to be out
    by the time we install new stack barriers immediately prior to
    scanning the stack such as during the mark phase of the next GC cycle
    or during mark termination in a STW GC.
    
    Hence, move the gcRemoveStackBarriers from STW mark termination to
    just before we install new stack barriers during concurrent mark. This
    removes the cost from STW. Furthermore, this combined with concurrent
    stack shrinking means that the mark termination scan of a clean stack
    is a complete no-op, which will make it possible to skip clean stacks
    entirely during mark termination.
    
    This has the downside that it will mess up anything outside of Go that
    tries to walk Go stacks all the time instead of just some of the time.
    This includes tools like GDB, perf, and VTune. We'll improve the
    situation shortly.
```

## 元コミット内容

Goランタイムにおいて、スタックバリアの削除タイミングをSTW (Stop-The-World) マーク終了フェーズから、並行マークフェーズで新しいスタックバリアをインストールする直前に移動します。これにより、STWのコストを削減し、クリーンなスタックのスキャンを完全にスキップできる可能性が生まれます。ただし、GDBやperf、VTuneなどの外部ツールがGoスタックを常にウォークしようとする場合に問題を引き起こす可能性がありますが、これは後で改善される予定です。

## 変更の背景

Goのガベージコレクション（GC）は、アプリケーションの実行を一時停止する「Stop-The-World (STW)」フェーズを最小限に抑えるように設計されています。以前の実装では、スタックバリアの削除がSTWマーク終了フェーズで行われていました。この処理はゴルーチンごとに無視できないコストがかかり、GCが既に「クリーン」であると判断したスタック（つまり、GCの対象となるポインタの変更がないことが確認されたスタック）であっても、そのスタックに触れる必要がありました。

しかし、スタックバリアはスイープフェーズ中には問題を引き起こしません。新しいスタックバリアがインストールされる直前（例えば、次のGCサイクルのマークフェーズ中や、STW GCのマーク終了中）までに削除されていれば十分です。この認識に基づき、スタックバリアの削除をSTWフェーズから移動することで、STWの時間をさらに短縮し、GCの全体的なパフォーマンスを向上させることが可能になります。特に、並行スタック縮小機能と組み合わせることで、クリーンなスタックに対するマーク終了スキャンを完全に不要にできるという大きなメリットが期待されました。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクション（GC）の基本的な仕組みと、特に「スタックバリア」の概念について知っておく必要があります。

*   **Goのガベージコレクション (GC)**: GoのGCは、主に「三色マーク・アンド・スイープ」アルゴリズムをベースにした並行GCです。これは、プログラムの実行と並行して不要なメモリを特定し、解放しようとします。GCサイクルは通常、以下のフェーズで構成されます。
    *   **マークフェーズ (Mark Phase)**: ライブオブジェクト（プログラムから到達可能なオブジェクト）を特定します。Goでは、このフェーズの大部分がユーザープログラムと並行して実行されます（並行マーク）。
    *   **マーク終了フェーズ (Mark Termination Phase)**: 並行マークフェーズの最終処理を行う短いSTWフェーズです。このフェーズで、GCはマーク処理を完了させ、次のフェーズへの移行準備をします。
    *   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（デッドオブジェクト）がメモリから解放されます。このフェーズも大部分が並行して実行されます。
*   **Stop-The-World (STW)**: GCの特定のフェーズで、すべてのゴルーチン（Goの軽量スレッド）の実行が一時的に停止される期間を指します。STWはGCの正確性を保証するために必要ですが、アプリケーションの応答性を低下させるため、GoのGCはSTW時間を最小限に抑えるように設計されています。
*   **スタックバリア (Stack Barriers)**: GoのGCが並行して動作する際、ユーザープログラムがスタック上のポインタを書き換える可能性があります。この書き換えがGCのマーク処理と競合すると、GCがオブジェクトを誤ってデッドと判断してしまう可能性があります。これを防ぐために導入されたのがスタックバリアです。スタックバリアは、特定のスタックフレームに設定され、そのフレーム内のポインタが書き換えられる際にGCに通知する（ライトバリアをトリガーする）役割を果たします。これにより、GCは並行実行中でもスタック上のポインタの変更を正確に追跡できます。
*   **クリーンなスタック (Clean Stacks)**: GCによって既にスキャンされ、そのスタック上に「グレーオブジェクト」（まだ参照先が完全にスキャンされていないオブジェクト）が存在しないことが確認されたスタックを指します。理論的には、これらのスタックはGCのマーク終了フェーズで再スキャンする必要がありません。
*   **並行スタック縮小 (Concurrent Stack Shrinking)**: Goランタイムの機能の一つで、ゴルーチンのスタックが過剰に大きい場合に、実行中にスタックをより小さなサイズに縮小するものです。これもGCの効率化に寄与します。

## 技術的詳細

このコミットの核心は、`gcRemoveStackBarriers`関数の呼び出しタイミングの変更です。

以前は、`gcRemoveStackBarriers`は主に`_GCmarktermination`フェーズ（STWフェーズの一部）で`scanstack`関数内から呼び出されていました。これは、GCがマーク処理を完了し、次のサイクルに備えるために、すべてのスタックからバリアを削除する必要があるためです。しかし、このアプローチは以下の問題点がありました。

1.  **STWコストの増加**: `gcRemoveStackBarriers`の実行には、ゴルーチンごとに一定のオーバーヘッドがあります。STWフェーズ中にこれを行うと、STW時間が長くなり、アプリケーションのレイテンシに悪影響を与えます。
2.  **クリーンなスタックの不必要な処理**: GCが既にクリーンであると判断したスタックであっても、バリアを削除するために`scanstack`が呼び出され、スタックに触れる必要がありました。これは無駄な処理です。

このコミットでは、`gcRemoveStackBarriers`の呼び出しを、STWマーク終了フェーズから、**並行マークフェーズ中に新しいスタックバリアをインストールする直前**に移動します。

具体的には、`scanstack`関数内で`_GCmark`フェーズに入った際に、新しいスタックバリアをインストールする前に、まず既存のスタックバリアを削除するように変更されます。これにより、以下の利点が得られます。

*   **STWコストの削減**: `gcRemoveStackBarriers`の処理がSTWフェーズから並行フェーズに移動するため、STW時間が短縮されます。
*   **効率の向上**: 新しいスタックバリアをインストールする直前に古いバリアを削除することで、バリアのライフサイクル管理がより論理的になります。
*   **クリーンなスタックの最適化**: この変更と並行スタック縮小の組み合わせにより、マーク終了フェーズでのクリーンなスタックのスキャンが完全に「no-op」（何もしない）になる可能性が生まれます。これにより、GCはクリーンなスタックを完全にスキップできるようになり、GCの効率が大幅に向上します。

また、`gcRemoveStackBarriers`関数自体の内部からも`gcLockStackBarriers`と`gcUnlockStackBarriers`の呼び出しが削除されています。これは、`gcRemoveStackBarriers`を呼び出す側が、スタックバリアのロック/アンロックの責任を持つべきであることを示唆しています。これにより、ロックの粒度をより細かく制御し、不必要なロック/アンロックを避けることができます。

ただし、この変更には一時的な欠点も指摘されています。GDB、perf、VTuneなどの外部デバッグ・プロファイリングツールは、Goのスタックウォークに依存している場合があります。スタックバリアの存在はこれらのツールがスタックを正確に解釈するのに役立つことがありますが、この変更によりバリアが一時的に存在しない期間が生じるため、これらのツールがGoスタックを常にウォークしようとすると、誤動作する可能性があります。コミットメッセージでは、この問題は「まもなく改善される」と述べられており、一時的なトレードオフとして受け入れられています。

## コアとなるコードの変更箇所

### `src/runtime/mgcmark.go`

*   `scanstack`関数内の`_GCmarktermination`フェーズから、`gcRemoveStackBarriers(gp)`の呼び出しが削除されました。
*   `scanstack`関数内の`_GCmark`フェーズにおいて、新しいスタックバリアをインストールするロジックの前に、`gcRemoveStackBarriers(gp)`が追加されました。これにより、新しいバリアを設置する前に古いバリアが確実に削除されます。
*   `_GCmarktermination`フェーズに、`!work.markrootDone`の場合に`gcRemoveStackBarriers(gp)`を呼び出す条件付きロジックが追加されました。これは、STW GCの場合など、マークフェーズを経由しなかった場合に古いスタックバリアが存在する可能性があるためです。
*   `scanstack`関数の最後に、`gcUnlockStackBarriers(gp)`が`_GCmark`フェーズの条件なしで呼び出されるようになりました。

### `src/runtime/mstkbar.go`

*   `gcRemoveStackBarriers`関数から、`gcLockStackBarriers(gp)`と`gcUnlockStackBarriers(gp)`の呼び出しが削除されました。
*   `gcRemoveStackBarriers`関数のコメントに「`gp's stack barriers must be locked.`」が追加され、呼び出し元がロックの責任を持つことが明示されました。

## コアとなるコードの解説

### `src/runtime/mgcmark.go`の変更点

`scanstack`関数は、特定のゴルーチン`gp`のスタックをスキャンし、GCのマーク処理やスタックバリアの管理を行います。

```go
// 変更前: _GCmarkterminationフェーズでスタックバリアを削除
func scanstack(gp *g) {
    if gp.gcscanvalid {
        if gcphase == _GCmarktermination {
            gcRemoveStackBarriers(gp) // ここで削除されていた
        }
        return
    }
    // ...
}
```

このコミットでは、上記の`gcRemoveStackBarriers(gp)`の呼び出しが削除され、代わりに`_GCmark`フェーズに移動しました。

```go
// 変更後: _GCmarkフェーズで新しいバリアをインストールする前に削除
case _GCmark:
    // ...
    // Remove any existing stack barriers before we
    // install new ones.
    gcRemoveStackBarriers(gp) // ここに移動
    // gcLockStackBarriers(gp) はこの直後に移動し、新しいバリアのインストールロジックが続く
```

この変更により、スタックバリアの削除がSTWフェーズから並行マークフェーズに移行し、STW時間の短縮に貢献します。

また、`_GCmarktermination`フェーズには、STW GCの場合（並行マークフェーズを経由しない場合）に備えて、古いスタックバリアを削除するロジックが追加されました。

```go
// 変更後: _GCmarkterminationフェーズでの条件付き削除
case _GCmarktermination:
    if !work.markrootDone {
        // This is a STW GC. There may be stale stack
        // barriers from an earlier cycle since we
        // never passed through mark phase.
        gcRemoveStackBarriers(gp) // STW GCの場合に削除
    }
    // ...
```

### `src/runtime/mstkbar.go`の変更点

`gcRemoveStackBarriers`関数は、ゴルーチン`gp`のスタックにインストールされているすべてのスタックバリアを削除する役割を担います。

```go
// 変更前: 関数内でロック/アンロックを行っていた
func gcRemoveStackBarriers(gp *g) {
    // ...
    gcLockStackBarriers(gp) // 関数内でロック
    // ...バリア削除ロジック...
    gcUnlockStackBarriers(gp) // 関数内でアンロック
}
```

このコミットでは、`gcLockStackBarriers(gp)`と`gcUnlockStackBarriers(gp)`の呼び出しが`gcRemoveStackBarriers`関数内から削除されました。

```go
// 変更後: 呼び出し元がロックの責任を持つ
// gp's stack barriers must be locked.
func gcRemoveStackBarriers(gp *g) {
    // ...
    // ロック/アンロックの呼び出しは削除された
    // ...バリア削除ロジック...
}
```

これにより、`gcRemoveStackBarriers`を呼び出す側（この場合は`scanstack`関数）が、スタックバリアの操作全体を囲むロックの管理を行うことになります。これは、より柔軟なロック戦略を可能にし、不必要なロック/アンロックのオーバーヘッドを削減する可能性があります。

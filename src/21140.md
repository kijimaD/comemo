# [インデックス 21140] ファイルの概要

## 変更の背景

このコミットの主な背景は、GoランタイムのC言語で書かれた部分をGo言語に移行するという、Go開発チームの継続的な取り組みの一環です。Goランタイムは、Goプログラムの実行を支える低レベルな機能（スケジューリング、メモリ管理、ガベージコレクション、システムコールなど）を提供します。歴史的に、これらの機能の一部はパフォーマンスやOSとの連携の必要性からC言語やアセンブリ言語で実装されていました。

しかし、C言語とGo言語の混在は、ビルドプロセスの複雑化、クロスコンパイルの困難さ、Cgo（GoからC言語のコードを呼び出すメカニズム）のオーバーヘッド、そしてGoのツールチェイン（リンカ、デバッガなど）との統合の課題を引き起こします。Go言語でランタイムを記述することで、これらの問題を緩和し、Go言語の持つ安全性、可読性、保守性の恩恵をランタイム自身にも適用することが可能になります。

このコミットは、特にPowerPC 64ビットアーキテクチャ（`power64`および`power64le`）に特化した部分に焦点を当てています。コミットメッセージにある「The power64 equivalent of CL 174860043」という記述は、他のアーキテクチャ（例えばx86-64）でも同様のC/HからGoへの変換が行われており、このコミットがPowerPC版の対応であることを示唆しています。これは、Goランタイム全体のC言語依存を減らすという、より大きな目標に向けた一歩です。

## 前提知識の解説

### Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理する低レベルなコンポーネント群です。これには、ゴルーチン（軽量スレッド）のスケジューリング、メモリ割り当てとガベージコレクション（GC）、チャネル通信、システムコールインターフェースなどが含まれます。Goプログラムは、OS上で直接実行されるのではなく、Goランタイムの上で動作します。ランタイムは、Go言語の並行処理モデルやメモリ管理モデルを実現するために不可欠な存在です。

### PowerPC 64ビットアーキテクチャ (`power64`, `power64le`)
PowerPCはIBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャです。`power64`は64ビット版のPowerPCアーキテクチャを指し、`power64le`はその中でもリトルエンディアン（Little-Endian）形式を採用しているバリアントを指します。
*   **ビッグエンディアン (Big-Endian):** データの最上位バイトがメモリアドレスの最も小さい位置に格納される方式。
*   **リトルエンディアン (Little-Endian):** データの最下位バイトがメモリアドレスの最も小さい位置に格納される方式。
Go言語は、異なるエンディアンのシステムでも動作するように、アーキテクチャ固有の定数や処理を適切に扱う必要があります。

### Goコンパイラディレクティブ (`//go:noescape`, `//go:nosplit`)
Go言語のソースコードには、コンパイラに対する特別な指示（ディレクティブ）をコメント形式で記述することができます。
*   `//go:noescape`: この関数内のポインタがヒープにエスケープしないことをコンパイラに伝えます。これにより、スタック上に変数を割り当てることが可能になり、ガベージコレクションのオーバーヘッドを減らすことができます。ランタイムの低レベルなコードで頻繁に使用されます。
*   `//go:nosplit`: この関数がスタックの拡張（スプリット）を行わないことをコンパイラに伝えます。スタックの拡張は、関数呼び出し時に現在のスタックフレームが小さすぎる場合に発生しますが、ランタイムのクリティカルなパスでは、このオーバーヘッドを避けるためにスタック拡張を禁止することがあります。

### `unsafe.Pointer`
Go言語の`unsafe`パッケージは、Goの型システムが提供する安全性をバイパスする機能を提供します。`unsafe.Pointer`は、任意の型のポインタを保持できる特殊なポインタ型で、C言語の`void*`に似ています。これにより、型変換のルールを無視してメモリを直接操作することが可能になりますが、その使用は非常に慎重に行う必要があります。ランタイムのような低レベルなコードでは、メモリレイアウトを直接制御するために使用されることがあります。

### アトミック操作 (Atomic Operations)
アトミック操作は、複数のCPUコアやゴルーチンから同時にアクセスされた場合でも、その操作全体が不可分（アトミック）であることを保証する操作です。つまり、操作の途中で他の操作によって中断されることがなく、常に一貫した状態を保ちます。Goランタイムでは、スケジューラやメモリ管理において共有データ構造を安全に操作するために、`xadd`（アトミック加算）、`xchg`（アトミック交換）、`cas`（比較交換）などのアトミック操作が不可欠です。

### `gobuf`
`gobuf`は、Goランタイム内でゴルーチンの実行コンテキスト（レジスタの状態、スタックポインタ、プログラムカウンタなど）を保存・復元するために使用される構造体です。ゴルーチンの切り替え（コンテキストスイッチ）時に、現在のゴルーチンの状態を`gobuf`に保存し、次に実行するゴルーチンの状態を`gobuf`から復元します。

### `morestack`
`morestack`は、Goランタイムにおけるスタック拡張のメカニズムです。Goのゴルーチンは、最初は小さなスタックで開始し、必要に応じて自動的にスタックを拡張します。関数が呼び出された際にスタックが不足している場合、ランタイムは`morestack`関数を呼び出し、より大きなスタックを割り当てて、元の関数に処理を戻します。

## 技術的詳細

このコミットの技術的な核心は、PowerPC 64ビットアーキテクチャ向けのランタイムコードをC言語からGo言語へ移植することです。これにより、Goのビルドシステムとツールチェインとの統合が強化され、Cgoの依存関係が減少します。

具体的には、以下のファイルが変更されています。

1.  **`src/runtime/arch_power64.h` と `src/runtime/arch_power64le.h` の削除:**
    これらのヘッダファイルは、PowerPC 64ビットアーキテクチャ固有の定数（例: `_BigEndian`, `_CacheLineSize`, `_PhysPageSize`）をC言語の`enum`で定義していました。

2.  **`src/runtime/arch1_power64.go` と `src/runtime/arch1_power64le.go` の新規追加:**
    削除されたヘッダファイルの内容が、Go言語の`const`宣言としてこれらのファイルに移行されました。
    *   `arch1_power64.go`: ビッグエンディアン (`_BigEndian = 1`) 向けの定数。
    *   `arch1_power64le.go`: リトルエンディアン (`_BigEndian = 0`) 向けの定数。
    これにより、アーキテクチャ固有の定数がGo言語のコードベースに直接組み込まれ、Cgoを介したアクセスが不要になります。

3.  **`src/runtime/sys_power64x.c` の削除:**
    このC言語ファイルには、`gostartcall`と`rewindmorestack`というGoランタイムの重要な関数が実装されていました。これらは、ゴルーチンのコンテキスト管理やスタック拡張の巻き戻しに関連する低レベルな処理です。

4.  **`src/runtime/sys_power64x.go` の新規追加:**
    削除された`sys_power64x.c`の機能が、Go言語で再実装されました。
    *   `gostartcall`: `gobuf`を調整し、指定された関数を呼び出すかのようにコンテキストを設定します。これは、新しいゴルーチンを開始する際などに使用されます。
    *   `rewindmorestack`: `morestack`呼び出しによって中断された関数の実行を、その関数の先頭に巻き戻すための処理です。これは、スタック拡張後に元の関数に戻る際に必要となります。
    Go言語での実装では、`unsafe.Pointer`を使用してポインタを操作したり、`uintptr`でアドレスを扱ったりすることで、C言語での低レベルなメモリ操作を模倣しています。また、`gothrow`（Goのパニックに相当）を使用してエラーハンドリングを行っています。

5.  **`src/runtime/atomic_power64x.go` の新規追加:**
    このファイルは、PowerPC 64ビットアーキテクチャ向けのアトミック操作をGo言語で定義しています。
    *   `xadd`, `xadd64`: アトミック加算。
    *   `xchg`, `xchg64`, `xchgp`, `xchguintptr`: アトミック交換。
    *   `atomicload`, `atomicload64`, `atomicloadp`: アトミックロード。
    *   `atomicor8`: アトミックOR。
    *   `cas64`: 比較交換（Compare And Swap）。
    これらの関数は、`//go:noescape`や`//go:nosplit`といったコンパイラディレクティブと共に宣言されており、Goコンパイラがこれらの操作を効率的に、かつ安全に処理できるように指示しています。特に`xchgp`や`atomicstorep`のように、`unsafe.Pointer`を扱う関数では、エスケープ解析の誤りを避けるための特別なコメントとラッパー関数が追加されています。これは、Goのコンパイラがポインタのエスケープを正確に判断し、最適なコードを生成するために重要です。

全体として、この変更はGoランタイムのC言語依存を減らし、Go言語のコードベースの一貫性を高め、将来的なメンテナンス性やクロスコンパイルの改善に寄与します。

```go
// Copyright 2014 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

// +build power64 power64le

package runtime

import "unsafe"

// adjust Gobuf as if it executed a call to fn with context ctxt
// and then did an immediate Gosave.
func gostartcall(buf *gobuf, fn, ctxt unsafe.Pointer) {
	if buf.lr != 0 {
		gothrow("invalid use of gostartcall")
	}
	buf.lr = buf.pc
	buf.pc = uintptr(fn)
	buf.ctxt = ctxt
}

// Called to rewind context saved during morestack back to beginning of function.
// To help us, the linker emits a jmp back to the beginning right after the
// call to morestack. We just have to decode and apply that jump.
func rewindmorestack(buf *gobuf) {
	var inst uint32
	if buf.pc&3 == 0 && buf.pc != 0 {
		inst = *(*uint32)(unsafe.Pointer(buf.pc))
		if inst>>24 == 0x4b && inst&3 == 0 {
			//print("runtime: rewind pc=", hex(buf.pc), " to pc=", hex(uintptr(buf.pc + int32(inst<<8)>>8)), "\n");
			buf.pc += uintptr(int32(inst<<8) >> 8)
			return
		}
	}
	print("runtime: pc=", hex(buf.pc), " ", hex(inst), "\n")
	gothrow("runtime: misuse of rewindmorestack")
}
```

// +build power64 power64le

package runtime

import "unsafe"

//go:noescape
func xadd(ptr *uint32, delta int32) uint32

//go:noescape
func xadd64(ptr *uint64, delta int64) uint64

//go:noescape
func xchg(ptr *uint32, new uint32) uint32

//go:noescape
func xchg64(ptr *uint64, new uint64) uint64

// xchgp cannot have a go:noescape annotation, because
// while ptr does not escape, new does. If new is marked as
// not escaping, the compiler will make incorrect escape analysis
// decisions about the value being xchg'ed.
// Instead, make xchgp a wrapper around the actual atomic.
// When calling the wrapper we mark ptr as noescape explicitly.

//go:nosplit
func xchgp(ptr unsafe.Pointer, new unsafe.Pointer) unsafe.Pointer {
	return xchgp1(noescape(ptr), new)
}

func xchgp1(ptr unsafe.Pointer, new unsafe.Pointer) unsafe.Pointer

//go:noescape
func xchguintptr(ptr *uintptr, new uintptr) uintptr

//go:noescape
func atomicload(ptr *uint32) uint32

//go:noescape
func atomicload64(ptr *uint64) uint64

//go:noescape
func atomicloadp(ptr unsafe.Pointer) unsafe.Pointer

//go:noescape
func atomicor8(ptr *uint8, val uint8)

//go:noescape
func cas64(ptr *uint64, old, new uint64) bool

//go:noescape
func atomicstore(ptr *uint32, val uint32)

//go:noescape
func atomicstore64(ptr *uint64, val uint64)

## コアとなるコードの解説

### `src/runtime/arch1_power64.go` と `src/runtime/arch_power64.h` の比較
`arch1_power64.go`は、C言語のヘッダファイル`arch_power64.h`で定義されていたアーキテクチャ固有の定数をGo言語の`const`として再定義したものです。
*   `thechar = '9'`: Goの内部でPowerPC 64ビットアーキテクチャを識別するための文字です。
*   `_BigEndian = 1` (または `0` for `power64le`): 当該アーキテクチャがビッグエンディアン（またはリトルエンディアン）であることを示します。
*   `_CacheLineSize = 64`: CPUのキャッシュラインサイズ（バイト単位）です。メモリのアライメントやアトミック操作の効率に影響します。
*   `_RuntimeGogoBytes = 64`: Goランタイムの内部で使用される特定のバッファサイズです。
*   `_PhysPageSize = 65536`: 物理メモリページのサイズ（64KB）です。メモリ管理ユニット（MMU）が扱う最小単位です。
*   `_PCQuantum = 4`: プログラムカウンタ（PC）の量子サイズです。命令のアドレスがこの値の倍数であることを示します。PowerPCでは通常4バイトです。
*   `_Int64Align = 8`: 64ビット整数がメモリ上で8バイト境界にアライメントされることを示します。

これらの定数をGo言語で定義することで、Goコンパイラやランタイムが直接これらの値を利用できるようになり、Cgoを介した間接的なアクセスが不要になります。

### `src/runtime/sys_power64x.go` と `src/runtime/sys_power64x.c` の比較
`sys_power64x.go`は、C言語で実装されていた`gostartcall`と`rewindmorestack`関数をGo言語で書き直したものです。

#### `gostartcall`
この関数は、ゴルーチンのコンテキスト（`gobuf`）を操作し、あたかも特定の関数（`fn`）が呼び出され、その直後に`Gosave`（コンテキスト保存）が行われたかのように設定します。
*   C言語版では、`Gobuf *gobuf, void (*fn)(void), void *ctxt`というCのポインタと関数ポインタを引数に取っていました。
*   Go言語版では、`buf *gobuf, fn, ctxt unsafe.Pointer`と、Goのポインタと`unsafe.Pointer`を使用しています。
*   `buf.lr = buf.pc`: リンクレジスタ（`lr`）に現在のプログラムカウンタ（`pc`）を保存します。これは、関数呼び出しからの戻りアドレスを保存する一般的なパターンです。
*   `buf.pc = uintptr(fn)`: プログラムカウンタを呼び出したい関数のアドレスに設定します。
*   `buf.ctxt = ctxt`: コンテキストポインタを設定します。
*   `if buf.lr != 0 { gothrow("invalid use of gostartcall") }`: `lr`が0でない場合（つまり、既に何らかの呼び出し元がある場合）は不正な使用としてパニックを発生させます。これは、`gostartcall`が通常、新しいゴルーチンの初期化など、クリーンな状態から呼び出されることを想定しているためです。

#### `rewindmorestack`
この関数は、`morestack`（スタック拡張）の呼び出しによって中断された関数の実行を、その関数の先頭に巻き戻すために使用されます。
*   C言語版では、`*(uint32*)gobuf->pc`のように直接メモリを読み込み、PowerPCの命令（`jmp`命令）をデコードしてジャンプ先を計算していました。
*   Go言語版でも同様に、`*(*uint32)(unsafe.Pointer(buf.pc))`を使用してプログラムカウンタが指すメモリ位置から命令を読み込みます。
*   `if inst>>24 == 0x4b && inst&3 == 0`: PowerPCの`b`（ブランチ）命令のオペコードと形式をチェックしています。`0x4b`は`b`命令のオペコードの一部で、`inst&3 == 0`は命令が4バイト境界にアライメントされていることを確認しています。
*   `buf.pc += uintptr(int32(inst<<8) >> 8)`: 命令から相対ジャンプオフセットを抽出し、プログラムカウンタに加算して、元の関数の先頭アドレスに巻き戻します。
*   `gothrow("runtime: misuse of rewindmorestack")`: 期待される命令パターンが見つからない場合、不正な使用としてパニックを発生させます。

これらの関数をGo言語で実装することで、GoランタイムのC言語部分への依存がさらに減少し、Goのツールチェインによる分析や最適化の恩恵を受けやすくなります。

### `src/runtime/atomic_power64x.go`
このファイルは、PowerPC 64ビットアーキテクチャ向けのアトミック操作のGo言語インターフェースを定義しています。これらの関数は、Goコンパイラによって適切なアセンブリ命令に変換されるか、またはアセンブリ言語で実装されたランタイム関数を呼び出します。

*   `//go:noescape` ディレクティブは、引数として渡されるポインタがヒープにエスケープしないことをコンパイラに伝えます。これにより、コンパイラはこれらのポインタが指すデータをスタック上に割り当てることができ、ガベージコレクションの負担を軽減します。
*   `//go:nosplit` ディレクティブは、関数がスタックの拡張を行わないことを保証します。これは、ランタイムのクリティカルなパスで、スタック拡張によるオーバーヘッドを避けるために重要です。
*   `xchgp` と `atomicstorep` のラッパー関数: `unsafe.Pointer`を引数に取るこれらの関数では、`//go:noescape`を直接適用できないため、ラッパー関数（`xchgp1`, `atomicstorep1`）を介して`noescape`を明示的に呼び出しています。これは、`new`引数がエスケープする可能性がある一方で、`ptr`引数はエスケープしないという複雑なエスケープ解析のケースに対応するためです。

これらのアトミック操作は、Goランタイム内で共有されるデータ構造（例: スケジューラのキュー、メモリ割り当てのフリーリスト）を複数のゴルーチンやCPUコアから安全に操作するために不可欠です。C言語の代わりにGo言語でこれらのインターフェースを定義することで、Goの型システムとコンパイラの最適化の恩恵を受けつつ、低レベルな並行処理を安全に実現しています。

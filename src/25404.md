# [インデックス 25404] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおけるメモリコピー操作の最適化に関するものです。特に、AMD64アーキテクチャにおいて、`REP MOVSB`（バイト単位の繰り返し移動命令）に依存していたコピー処理を、より効率的な複数の手法（チャンクコピー、Duff's Device、`REP MOVSQ`）に置き換えることで、生成されるコードのパフォーマンス向上を図っています。この変更には、16バイト単位の移動を可能にする`MOVO`オペコードと、それに対応する`Int128`型の導入が含まれます。

## 元コミット内容

Goコンパイラ（`cmd/compile`）のSSAバックエンドにおいて、メモリコピーの生成コードを改善します。具体的には、`REP MOVSB`命令を使用していたコピー処理を、旧コンパイラで用いられていたチャンクコピーやDuff's Deviceなどの様々な最適化されたコピー手法に置き換えます。この変更の一環として、16バイト単位のデータ移動をサポートするために`MOVO`オペコードと`Int128`型が導入されます。

## 変更の背景

Goコンパイラは、プログラムのソースコードを機械語に変換する際に、様々な最適化を適用します。メモリコピーは、構造体の代入、スライスのコピー、インターフェース値の作成など、Goプログラムの多くの場所で発生する非常に一般的な操作です。これらのコピー操作が効率的であることは、Goプログラム全体のパフォーマンスに直接影響します。

以前のGoコンパイラのSSAバックエンドでは、メモリコピーに主に`REP MOVSB`というx86アセンブリ命令を使用していました。この命令は、指定されたバイト数だけメモリをコピーする汎用的な命令ですが、特定の条件下ではパフォーマンスが最適ではありませんでした。特に、コピーするデータのサイズが小さい場合や、特定のサイズ（例えば、CPUのレジスタサイズやキャッシュラインサイズ）にアラインされている場合、より特化した命令や手法を用いることで、より高速なコピーが可能になります。

このコミットの背景には、以下の課題意識があったと考えられます。

1.  **`REP MOVSB`の非効率性**: `REP MOVSB`は汎用性が高い反面、オーバーヘッドが存在し、特に小規模なコピーでは、個別のロード/ストア命令を組み合わせる方が高速な場合があります。
2.  **既存の最適化手法の活用**: 旧コンパイラでは、コピーサイズに応じて様々な最適化手法が適用されていました。SSAバックエンドでもこれらの実績ある手法を取り入れることで、コード生成の品質を向上させる必要がありました。
3.  **現代のCPUアーキテクチャへの対応**: 現代のCPUは、一度に多くのデータを処理できるSIMD（Single Instruction, Multiple Data）命令や、キャッシュ効率を最大化するようなデータアクセスパターンを好みます。`REP MOVSB`だけでは、これらの特性を十分に活かせませんでした。特に、16バイト（128ビット）単位のデータ移動は、SSE/AVX命令セットを活用する上で重要です。

このコミットは、これらの課題に対処し、Goコンパイラが生成するメモリコピーコードの効率を大幅に向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が役立ちます。

1.  **SSA (Static Single Assignment) 形式**:
    コンパイラ最適化の中間表現の一つで、各変数が一度だけ代入されるようにする形式です。これにより、データフロー解析が容易になり、最適化の機会が増えます。Goコンパイラは、Go 1.7以降、SSAバックエンドを導入し、より高度な最適化を可能にしました。
2.  **x86-64 アセンブリ命令**:
    -   **`MOV`命令群**: データをレジスタ間、レジスタとメモリ間、メモリ間で移動させる基本的な命令です。
        -   `MOVB`: 1バイト移動
        -   `MOVW`: 2バイト移動 (Word)
        -   `MOVL`: 4バイト移動 (Double Word)
        -   `MOVQ`: 8バイト移動 (Quad Word)
    -   **`REP`プレフィックス**: `MOVSB`, `MOVSW`, `MOVSD`, `MOVSQ`などの文字列操作命令と組み合わせて使用され、`CX`レジスタで指定された回数だけ操作を繰り返します。
        -   `REP MOVSB`: `CX`回、1バイトずつメモリをコピーします。
        -   `REP MOVSQ`: `CX`回、8バイトずつメモリをコピーします。これは、このコミットで`REP MOVSB`の代わりに導入された、より効率的な命令です。
    -   **`MOVUPS`命令**: SSE（Streaming SIMD Extensions）命令セットの一部で、アラインされていないメモリからXMMレジスタ（128ビット）へ、またはその逆へ、16バイトのデータを移動します。このコミットで導入された`MOVO`オペコードは、この命令にマッピングされます。
3.  **Duff's Device (ダフのデバイス)**:
    C言語のコンパイラ最適化テクニックの一つで、ループアンローリングと`switch`文の組み合わせにより、ループのオーバーヘッドを削減し、高速なメモリコピーやゼロフィルを実現します。Goランタイムでも、特定のサイズのコピーやゼロフィルにDuff's Deviceがアセンブリコードで実装されています。これは、コンパイラが生成するコードから呼び出される形で利用されます。
4.  **チャンクコピー**:
    コピーするデータのサイズに応じて、最適な単位（バイト、ワード、クアッドワード、16バイトなど）でデータをコピーする手法です。例えば、8バイトのコピーには`MOVQ`を、1バイトのコピーには`MOVB`を使用するといった具合です。これにより、CPUのデータパスを効率的に利用し、`REP`プレフィックスのオーバーヘッドを回避できます。
5.  **アラインメント**:
    メモリ上のデータが特定のバイト境界（例: 4バイト、8バイト、16バイト）に配置されていることです。CPUはアラインされたデータへのアクセスを高速に処理できますが、アラインされていないデータへのアクセスはパフォーマンスが低下したり、特別な命令が必要になったりすることがあります。`MOVUPS`はアラインされていないアクセスを許容しますが、アラインされたアクセスの方が一般的に高速です。
6.  **`Int128`型**:
    Goコンパイラの内部で、128ビット（16バイト）の整数値を表現するために導入された型です。これは、`MOVO`オペコードが扱う16バイトのデータを抽象化するために使用されます。

## 技術的詳細

このコミットの核となるのは、GoコンパイラのSSAバックエンドが、`Move`オペレーション（メモリコピー）をどのように機械語に変換するか、そのルールを大幅に拡張・改善した点です。

具体的には、コピーするデータのサイズに応じて、以下の戦略を使い分けます。

1.  **サイズ0バイト**:
    -   `Move [0] dst src mem` は、実質的に何もコピーしないため、`mem`（メモリの状態）をそのまま返すノーオペレーションとして扱われます。
2.  **小規模なコピー (1〜16バイト)**:
    -   **1, 2, 4, 8バイト**: それぞれ`MOVBstore`/`MOVBload`、`MOVWstore`/`MOVWload`、`MOVLstore`/`MOVLload`、`MOVQstore`/`MOVQload`といった、対応するサイズのロード/ストア命令のペアに変換されます。これにより、`REP`プレフィックスのオーバーヘッドなしに、CPUのネイティブなデータパスを最大限に活用します。
    -   **16バイト**: 新しく導入された`MOVOstore`/`MOVOload`オペコードに変換されます。これらはAMD64の`MOVUPS`命令にマッピングされ、16バイトのデータを効率的に移動します。
    -   **3, 5, 6, 7バイト**: これらのサイズは、より小さいロード/ストア命令の組み合わせで処理されます。例えば、3バイトのコピーは1バイトと2バイトのコピーに分解されます。
    -   **9〜15バイト**: 8バイトの`MOVQ`と、残りのバイト数に応じた`MOVQ`（オフセット付き）の組み合わせで処理されます。例えば、15バイトのコピーは、最初の8バイトを`MOVQ`でコピーし、残りの7バイトをオフセット付きの`MOVQ`でコピーします。これは、8バイト境界でのコピーを優先しつつ、残りを効率的に処理する手法です。
    -   **17〜31バイト (16バイトの倍数でない場合)**: まず、残りのバイト数（`size % 16`）に応じて`MOVQstore`または`MOVOstore`で端数を処理し、残りの16バイトの倍数部分を再帰的に`Move`オペレーションとして処理します。
3.  **中規模なコピー (32〜1024バイト、16バイトの倍数)**:
    -   `size >= 32 && size <= 16*64 && size%16 == 0` の条件を満たすコピーは、`DUFFCOPY`オペコードに変換されます。これは、Goランタイムに実装されているDuff's Deviceのアセンブリルーチンを呼び出すためのものです。Duff's Deviceは、ループアンローリングによってループの分岐予測ミスやループ制御のオーバーヘッドを削減し、高速なコピーを実現します。`AMD64.rules`ファイルには、`DUFFCOPY`の`AuxInt`が`14*(64-size/16)`というマジックナンバーで計算されることが示されており、これは`src/runtime/duff_amd64.s:duffcopy`のアセンブリコードの構造と密接に関連しています。
4.  **大規模なコピー (1024バイト超、8バイトの倍数)**:
    -   `size > 16*64 && size%8 == 0` の条件を満たすコピーは、`REPMOVSQ`オペコードに変換されます。これは、`REP MOVSQ`アセンブリ命令にマッピングされ、8バイト（クアッドワード）単位で大量のデータを効率的にコピーします。元の`REP MOVSB`と比較して、一度に8バイトを処理するため、特に大量のデータコピーにおいて高いパフォーマンスを発揮します。

これらの最適化は、`src/cmd/compile/internal/ssa/gen/AMD64.rules`および`src/cmd/compile/internal/ssa/rewriteAMD64.go`ファイルに定義されたSSAリライトルールによって実現されます。コンパイラは、SSA中間表現の`Move`オペレーションを、これらのルールに基づいてより低レベルで効率的な機械語命令のシーケンスに変換します。

また、このコミットでは、`src/cmd/compile/internal/ssa/gen/AMD64Ops.go`で`MOVOload`、`MOVOstore`、`DUFFCOPY`、`REPMOVSQ`といった新しいSSAオペコードが定義され、それぞれ対応するアセンブリ命令やランタイム関数にマッピングされています。`MOVO`オペコードは、128ビットのXMMレジスタを使用し、`MOVUPS`命令を生成します。

`src/cmd/compile/internal/gc/testdata/gen/copyGen.go`は、これらのコピー最適化が正しく機能するかを検証するためのテストコードを自動生成するツールです。1バイトから1041バイトまでの様々なサイズのコピーをテストすることで、各最適化パスが意図通りに動作し、メモリの破損がないことを確認します。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は、GoコンパイラのSSAバックエンドの以下のファイルに集中しています。

1.  **`src/cmd/compile/internal/gc/ssa.go`**:
    -   `genValue`関数に`ssa.OpAMD64MOVOload`、`ssa.OpAMD64MOVOstore`、`ssa.OpAMD64DUFFCOPY`のケースが追加され、これらのSSAオペコードが対応するアセンブリ命令（`MOVUPS`や`ADUFFCOPY`）に変換されるようになりました。
    -   `ssa.OpAMD64REPMOVSB`が`ssa.OpAMD64REPMOVSQ`に置き換えられ、バイト単位の繰り返し移動からクアッドワード単位の繰り返し移動に変更されました。

2.  **`src/cmd/compile/internal/ssa/gen/AMD64.rules`**:
    -   `Move`オペレーションに対する新しいリライトルールが多数追加されました。
        -   サイズ0、1、2、4、8、16バイトの直接的なロード/ストア命令への変換ルール。
        -   サイズ3、5、6、7バイトの、より小さいロード/ストア命令の組み合わせへの変換ルール。
        -   サイズ8〜16バイト未満の、2つの`MOVQ`命令によるコピーへの変換ルール。
        -   サイズ16バイト超で16の倍数でない場合の、端数処理と残りの再帰的な`Move`への変換ルール。
        -   サイズ32〜1024バイト（16の倍数）の`DUFFCOPY`への変換ルール。
        -   サイズ1024バイト超（8の倍数）の`REPMOVSQ`への変換ルール。
    -   `MOVOload`および`MOVOstore`に対するアドレスオフセットの畳み込み（folding）ルールが追加されました。

3.  **`src/cmd/compile/internal/ssa/gen/AMD64Ops.go`**:
    -   `MOVOload`、`MOVOstore`、`DUFFCOPY`、`REPMOVSQ`の新しいSSAオペコードが定義されました。
    -   `MOVOload`と`MOVOstore`は、アセンブリ命令`MOVUPS`にマッピングされ、`Int128`型を扱うように設定されました。
    -   `DUFFCOPY`と`REPMOVSQ`のレジスタ使用規則（入力、出力、破壊されるレジスタ）が定義されました。

4.  **`src/cmd/compile/internal/ssa/opGen.go`**:
    -   `OpAMD64MOVOload`、`OpAMD64MOVOstore`、`OpAMD64DUFFCOPY`、`OpAMD64REPMOVSQ`が新しいオペコードとして列挙に追加されました。
    -   `OpAMD64REPMOVSB`が削除されました。

5.  **`src/cmd/compile/internal/ssa/rewriteAMD64.go`**:
    -   `rewriteValueAMD64`関数内に、`OpAMD64MOVOload`、`OpAMD64MOVOstore`、および`OpMove`オペレーションに対する詳細なリライトロジックが実装されました。これは、`AMD64.rules`で定義された抽象的なルールを具体的なSSA値の変換として実現する部分です。

6.  **`src/cmd/compile/internal/ssa/type.go`**:
    -   `CompilerType`構造体に`Int128`フィールドが追加され、`TypeInt128`が定義されました。これにより、SSAバックエンドが128ビット整数型を認識し、処理できるようになりました。

## コアとなるコードの解説

このコミットの最も重要な部分は、`src/cmd/compile/internal/ssa/gen/AMD64.rules`と`src/cmd/compile/internal/ssa/rewriteAMD64.go`における`Move`オペレーションのリライトルールです。

例えば、`AMD64.rules`の以下の部分を見てみましょう。

```
// Small moves
(Move [0] _ _ mem) -> mem
(Move [1] dst src mem) -> (MOVBstore dst (MOVBload src mem) mem)
(Move [16] dst src mem) -> (MOVOstore dst (MOVOload src mem) mem)

// Medium copying uses a duff device.
(Move [size] dst src mem) && size >= 32 && size <= 16*64 && size%16 == 0 ->
	(DUFFCOPY [14*(64-size/16)] dst src mem)

// Large copying uses REP MOVSQ.
(Move [size] dst src mem) && size > 16*64 && size%8 == 0 ->
	(REPMOVSQ dst src (MOVQconst [size/8]) mem)
```

-   **`Move [0] _ _ mem) -> mem`**: これは、サイズが0のコピーは実質的に何もしないため、メモリの状態をそのまま次のオペレーションに渡すことを示しています。
-   **`Move [1] dst src mem) -> (MOVBstore dst (MOVBload src mem) mem)`**: 1バイトのコピーは、ソースから1バイトをロードし（`MOVBload`）、それをデスティネーションにストアする（`MOVBstore`）という2つの命令に変換されます。これは`REP MOVSB`よりも効率的です。
-   **`Move [16] dst src mem) -> (MOVOstore dst (MOVOload src mem) mem)`**: 16バイトのコピーは、新しく導入された`MOVOload`と`MOVOstore`命令のペアに変換されます。これらは`MOVUPS`アセンブリ命令に対応し、128ビットのXMMレジスタを利用して高速な16バイト移動を実現します。
-   **`DUFFCOPY`ルール**: `size >= 32 && size <= 16*64 && size%16 == 0` (32バイトから1024バイトまでの16の倍数) のコピーは、`DUFFCOPY`オペレーションに変換されます。`[14*(64-size/16)]`という`AuxInt`は、Goランタイムのアセンブリコード`src/runtime/duff_amd64.s`にある`duffcopy`関数のエントリポイントへのオフセットを計算するためのものです。このオフセットは、Duff's Deviceのループアンローリング構造において、コピーサイズに応じた適切な開始点にジャンプするために使用されます。
-   **`REPMOVSQ`ルール**: `size > 16*64 && size%8 == 0` (1024バイト超で8の倍数) のコピーは、`REPMOVSQ`オペレーションに変換されます。これは`REP MOVSQ`アセンブリ命令にマッピングされ、`size/8`回、8バイト単位でコピーを実行します。これにより、従来の`REP MOVSB`よりも大幅に高速な大規模コピーが可能になります。

これらのルールは、`src/cmd/compile/internal/ssa/rewriteAMD64.go`内の`rewriteValueAMD64`関数で実際に適用されます。この関数は、SSA値のオペレーションタイプと補助情報（サイズなど）に基づいて、適切な低レベルのSSAオペレーションに変換するロジックを含んでいます。例えば、`OpMove`のケースでは、`v.AuxInt`（コピーサイズ）をチェックし、上記のルールに従って新しいSSA値のグラフを構築します。

この変更により、Goコンパイラは、コピーするデータのサイズとアラインメントの特性を考慮し、最も効率的な機械語命令シーケンスを動的に選択できるようになりました。これは、Goプログラムの実行時パフォーマンス、特にメモリを頻繁に操作するアプリケーションにおいて、顕著な改善をもたらします。

# [インデックス 2501] ファイルの概要

このコミットは、GoランタイムのARMアーキテクチャサポートにおける初期段階の重要な進展を示しています。特に、GoプログラムがARM上で起動するための基盤、ゴルーチンのスタック管理、コンテキストスイッチ、および基本的なメモリ操作関数の実装に焦点を当てています。

## コミット

GoランタイムがダミーのCプログラムをターゲットとして起動するようになりました。
- `morestack` および `gosave`/`gogo`/`gocall` のサポートが追加されました。
- Inferno OS由来の `memclr` および `memset` が導入されました。
- `_rt0_arm` にバグ修正が適用されました。

## 変更の背景

このコミットは、Go言語がARMアーキテクチャ上で動作するための初期の基盤構築の一環として行われました。当時のGoは主にx86アーキテクチャを対象としていましたが、モバイルデバイスや組み込みシステムでの利用を視野に入れ、ARMサポートの必要性が高まっていました。

具体的には、以下の機能が不足しており、それらを実装することが目的でした。
1.  **ランタイムの初期化**: ARMプロセッサ上でGoプログラムが実行を開始するためのエントリポイント (`_rt0_arm`) の確立と、基本的なランタイム環境のセットアップ。
2.  **スタック管理**: Goの軽量スレッドであるゴルーチンは、必要に応じてスタックを動的に拡張する「スプリットスタック」というメカニズムを使用します。このための `morestack` 関連の機能がARM向けに必要でした。
3.  **コンテキストスイッチ**: ゴルーチン間の切り替え（スケジューリング）には、現在のゴルーチンの状態を保存し、別のゴルーチンの状態を復元するメカニズムが必要です。これが `gosave`, `gogo`, `gocall` に相当します。
4.  **基本的なメモリ操作**: `memset` や `memclr` といった低レベルのメモリ操作関数は、ランタイムの様々な場所で利用されるため、効率的なARMアセンブリ実装が必要でした。
5.  **システムコール**: Linux/ARM環境でのシステムコールを正しく呼び出すためのラッパーの実装。

これらの機能は、Goランタイムが特定のアーキテクチャ上で動作するために不可欠な要素であり、このコミットはARMサポートの実現に向けた大きな一歩でした。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する部分です。ガベージコレクション、ゴルーチン管理、スケジューリング、チャネル通信など、Go言語の並行処理モデルを支える低レベルな機能を提供します。
*   **ARMアーキテクチャ**: Advanced RISC Machineの略で、主にモバイルデバイスや組み込みシステムで広く使用されているCPUアーキテクチャです。RISC (Reduced Instruction Set Computer) の原則に基づき、シンプルで高速な命令セットが特徴です。
*   **`_rt0_arm`**: Goプログラムの実行開始時に最初に呼び出されるアセンブリコードのエントリポイントです。C言語における `_start` や `main` 関数に相当しますが、より低レベルで、OSからの制御を受け取った直後にランタイムの初期化を行います。スタックのセットアップ、`g` (goroutine) および `m` (machine) レジスタの初期化、スケジューラの起動などを行います。
*   **ゴルーチン (Goroutine)**: Go言語の軽量な並行処理単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行できます。Goランタイムがゴルーチンのスケジューリングとスタック管理を行います。
*   **スプリットスタック (Split Stack)**: Goのゴルーチンが採用しているスタック管理方式です。ゴルーチンのスタックは最初は小さく確保され、必要に応じて動的に拡張されます。これにより、大量のゴルーチンを起動してもメモリを効率的に利用できます。スタックの拡張が必要な場合に `morestack` が呼び出されます。
*   **`morestack`**: ゴルーチンのスタックが不足した際に呼び出される関数です。新しいスタック領域を確保し、現在の実行コンテキストを新しいスタックに移動させます。
*   **`gosave`/`gogo`/`gocall`**: これらはゴルーチンのコンテキストスイッチ（状態の保存と復元）を行うためのアセンブリ関数です。
    *   `gosave`: 現在のゴルーチンのレジスタ状態（プログラムカウンタ、スタックポインタなど）を `Gobuf` 構造体に保存します。C言語の `setjmp` に似ています。
    *   `gogo`: `Gobuf` に保存されたレジスタ状態を復元し、その状態から実行を再開します。C言語の `longjmp` に似ています。
    *   `gocall`: `Gobuf` に状態を保存しつつ、指定された関数を呼び出します。呼び出し元に戻る際には `Gobuf` の状態が復元されます。
*   **`memset`/`memclr`**:
    *   `memset`: 指定されたメモリ領域を特定の値で埋める標準Cライブラリ関数です。
    *   `memclr`: Goランタイム内部で使用される関数で、メモリ領域をゼロでクリアする目的で使用されます。多くの場合、`memset` を呼び出してゼロで埋めることで実装されます。
*   **Inferno OS**: ベル研究所で開発された分散オペレーティングシステムです。Go言語の設計思想や一部のコードベースに影響を与えています。このコミットでは、Inferno OSのARM向け `memset` 実装がGoランタイムに移植されています。
*   **`5l`**: GoのARMアーキテクチャ向けリンカです。Goのコンパイラツールチェーンの一部であり、オブジェクトファイルを結合して実行可能ファイルを生成します。

## 技術的詳細

このコミットは、GoランタイムのARMサポートを確立するための複数の低レベルな変更を含んでいます。

1.  **`_rt0_arm` の修正と初期化**:
    *   `src/pkg/runtime/arm/asm.s` 内の `_rt0_arm` 関数が大幅に修正されました。これはGoプログラムがARM上で起動する際のエントリポイントです。
    *   スタックフレームのサイズが `$0` から `$-4` に変更され、LR (Link Register) のスタックへの保存を抑制しています。これは、`_rt0_arm` がOSから直接呼び出されるため、通常の関数呼び出し規約とは異なる場合があるためです。
    *   `SP` (Stack Pointer) の代わりに `R13` レジスタを使用してスタック操作を行うことで、リンカによるオフセット書き換えを回避しています。これは、リンカが `SP` への相対アドレスを特別扱いする可能性があるためです。
    *   `g0` (スケジューラゴルーチン) と `m0` (初期マシン) の初期化が `R10` と `R9` レジスタに直接ロードされるようになりました。以前は `MOVW $g0(SB), R10` のようにシンボルを直接参照していましたが、新しいコードでは `g` と `m` というエイリアスが定義され、より読みやすくなっています。
    *   `g_stackguard` と `g_stackbase` の設定により、ゴルーチンのスタックガードとベースポインタが初期化されます。これはスプリットスタックの機能に不可欠です。
    *   `argc` と `argv` の処理も `R13` を基準に行われるよう変更され、`args`, `osinit`, `schedinit` などの初期化関数が呼び出されます。
    *   `mainstart` ゴルーチンを起動し、`mstart` で現在のM (Machine) を開始することで、Goスケジューラが本格的に動作を開始します。

2.  **スタック管理 (`morestack` 関連)**:
    *   `src/cmd/5l/noop.c` では、リンカが生成するスタックチェックコードのロジックが変更されました。特に、`sys·morestackx` の呼び出しに関するアセンブリ命令のコメントが更新され、`g_stackguard(g)` との比較、`args` と `autosize` のレジスタへのロード、そして条件付き分岐 (`BL.LT sys·morestackx(SB)`) が示されています。
    *   `src/pkg/runtime/arm/asm.s` に `sys·morestack` と `sys·morestackx` の実装が追加されました。
        *   `sys·morestack` は、スケジューラスタック (`m->g0`) からの呼び出しでないことを確認し、現在のゴルーチンのフレームサイズ (`R1`) と引数サイズ (`R2`) を `m` (Machine) 構造体に保存します。そして、現在のゴルーチンのコンテキスト (`PC`, `SP`, `g`) を `m->morebuf` に保存し、`m->morepc` に現在の `LR` を保存します。最終的に `m_g0` に切り替えて `newstack` 関数を呼び出します。
        *   `sys·morestackx` は、`sys·morestack` の最適化されたラッパーであり、引数を適切に設定して `sys·morestack` を呼び出します。
    *   `sys·lessstack` も追加され、スタックから戻る際の処理を定義しています。これは `m->cret` に戻り値を保存し、`m_g0` に切り替えて `oldstack` 関数を呼び出します。

3.  **コンテキストスイッチ (`gosave`/`gogo`/`gocall`)**:
    *   `src/pkg/runtime/arm/asm.s` に `gosave`, `gogo`, `gogocall` の実装が追加されました。
    *   `gosave`: `Gobuf` 構造体 (`R0` で渡される) に現在の `SP`、`LR` (PC)、および `g` (現在のゴルーチンポインタ) を保存します。
    *   `gogo`: `Gobuf` (`R1` で渡される) から `g`、`SP`、`PC` を復元し、実行を再開します。
    *   `gogocall`: `Gobuf` (`R0` で渡される) から `g` と `SP` を復元し、`Gobuf` に保存された `PC` を `LR` に設定した後、指定された関数 (`R1` で渡される `fn`) を呼び出します。これにより、関数呼び出し後に `Gobuf` に保存されたコンテキストに戻ることができます。

4.  **メモリ操作 (`memset`/`memclr`)**:
    *   `src/pkg/runtime/arm/memset.s` が新規追加され、Inferno OS由来のARM向け `memset` が実装されました。このアセンブリコードは、指定されたメモリ領域をバイト単位で効率的にクリア（または特定の値で埋める）します。4バイトアライメントを考慮し、32バイトチャンクで高速に処理するロジックが含まれています。
    *   `src/pkg/runtime/arm/asm.s` の `sys·memclr` は、この `memset` を呼び出すように変更されました。`m` と `g` レジスタが `memset` によって破壊される可能性があるため、呼び出し前後でこれらのレジスタをスタックに保存・復元する処理が追加されています。

5.  **システムコール (`sys.s`)**:
    *   `src/pkg/runtime/linux/arm/sys.s` では、Linux/ARM環境でのシステムコール番号が `#define` で定義されました (`SYS_BASE`, `SYS_exit`, `SYS_write`, `SYS_mmap2`)。
    *   `write`, `exit`, `sys·mmap` 関数がこれらの定義を使用するように更新され、`SWI` (Software Interrupt) 命令を使ってシステムコールを呼び出すようになりました。特に `sys·mmap` は以前 `abort` を呼び出していたダミー実装から、実際の `mmap2` システムコールを呼び出すように変更されました。

6.  **Makefileの変更**:
    *   `src/pkg/runtime/Makefile` に `memset.$O` が `OFILES_arm` に追加され、新しく追加された `memset.s` がビルドプロセスに含まれるようになりました。
    *   `CFLAGS_arm=-N` が追加されました。これはARMアーキテクチャ向けのCコンパイル時に最適化を無効にするフラグです。コミットメッセージのコメント (`TODO(kaib): fix register allocation to honor extern register so we can enable optimizations again.`) から、当時のARMコンパイラのレジスタ割り当てに問題があり、デバッグや安定性のために一時的に最適化を無効にしたものと推測されます。

これらの変更は、GoランタイムがARM上で安定して動作するための低レベルな基盤を構築する上で不可欠なものでした。

## コアとなるコードの解説

### `src/cmd/5l/noop.c` の変更

このファイルはGoのARMリンカ (`5l`) の一部であり、主にスタックチェックコードの生成方法を定義しています。変更点は、`autosize` (関数のスタックフレームサイズ) が `StackBig` (大きなスタックフレームの閾値) より小さい場合のスタックチェックロジックのコメントと、それに続くアセンブリ命令の生成ロジックの更新です。

以前のコメントでは `callmorestack(SB)` を直接呼び出すような記述がありましたが、新しいコメントとコードでは `sys·morestackx(SB)` を呼び出すように変更されています。これは、`sys·morestackx` が `sys·morestack` のラッパーとして導入され、スタック拡張処理の引数渡しを最適化しているためです。

具体的には、以下のレジスタに値を設定してから `sys·morestackx` を条件付きで呼び出します。
*   `R1`: `g_stackguard(g)` (現在のゴルーチンのスタックガード値)
*   `R2`: `$args` (関数の引数サイズ)
*   `R3`: `R14` (LR, 呼び出し元のPC)

そして、`CMP R1, $-autosize(SP)` でスタックガードと現在のスタックポインタを比較し、スタックが不足している場合 (`LT` - Less Than) に `sys·morestackx` を呼び出します。これにより、Goの動的なスタック拡張メカニズムがARM上で機能するようになります。

### `src/pkg/runtime/arm/asm.s` の変更

このファイルはGoランタイムのARMアセンブリコードの核心部分です。

*   **`_rt0_arm`**:
    *   `TEXT _rt0_arm(SB),7,$-4`: スタックフレームサイズを `$-4` に設定し、LRの保存を抑制します。
    *   `MOVW $g0(SB), g` と `MOVW $m0(SB), m`: `g` と `m` というエイリアスを使用して、グローバルな `g0` と `m0` をそれぞれ `R10` と `R9` にロードします。これにより、コードの可読性が向上します。
    *   `MOVW g, m_g0(m)`: `m` 構造体の `g0` フィールドに `g` (つまり `g0`) を保存します。
    *   `MOVW $(-8192+104)(R13), R0` と `MOVW R0, g_stackguard(g)`: 初期スタックガードを設定します。`R13` を使用することで、リンカによる `SP` へのオフセット書き換えを回避しています。
    *   `MOVW R13, g_stackbase(g)`: スタックベースを設定します。
    *   `MOVW $12(R13), R13`: `mainstart` ゴルーチン起動後のスタッククリーンアップも `R13` を使用して行われます。

*   **`gosave`, `gogo`, `gogocall`**:
    *   `gosave`: `Gobuf` 構造体への `SP`, `LR` (PC), `g` の保存を実装します。これにより、現在のゴルーチンの実行コンテキストを保存できます。
    *   `gogo`: `Gobuf` から `g`, `SP`, `PC` を復元し、保存されたコンテキストで実行を再開します。
    *   `gogocall`: `Gobuf` から `g`, `SP` を復元し、`Gobuf` の `PC` を `LR` に設定した後、指定された関数を呼び出します。関数から戻ると `LR` に保存された `Gobuf` の `PC` に戻るため、コンテキストスイッチと関数呼び出しを組み合わせた動作を実現します。

*   **`sys·morestack`, `sys·lessstack`, `sys·morestackx`**:
    *   `sys·morestack`: スタック拡張のメインロジックです。スケジューラスタックからの呼び出しでないことを確認し、現在のゴルーチンの状態 (`PC`, `SP`, `g`) を `m->morebuf` に保存します。その後、`m_g0` に切り替えて `newstack` を呼び出し、スタック拡張処理を行います。
    *   `sys·lessstack`: スタックから戻る際の処理です。戻り値を `m->cret` に保存し、`m_g0` に切り替えて `oldstack` を呼び出します。
    *   `sys·morestackx`: `sys·morestack` のラッパーで、引数を適切に設定して呼び出します。

*   **`sys·memclr`**:
    *   `sys·memclr` は、新しく追加された `memset` 関数を呼び出すように変更されました。
    *   `m` と `g` レジスタが `memset` によって破壊される可能性があるため、`memset` 呼び出しの前後でこれらのレジスタをスタックに保存・復元するコードが追加されています。これは、低レベルのアセンブリ関数が呼び出し規約に厳密に従わない場合に、呼び出し元がレジスタの保存・復元を行う必要がある典型的な例です。

### `src/pkg/runtime/arm/memset.s` の新規追加

このファイルは、Inferno OSから移植されたARM向け `memset` のアセンブリ実装です。
*   `TO`, `TOE`, `N`, `TMP` などのレジスタエイリアスを定義し、コードの可読性を高めています。
*   `memset` 関数は、`R0` (アドレス), `data+4(FP)` (埋める値), `n+8(FP)` (サイズ) を引数として受け取ります。
*   まず、埋める値 (`R4`) を32ビットワード全体に複製します (`AND $0xFF, R(4)`, `SLL $8, R(4), R(TMP)`, `ORR R(TMP), R(4)` など)。
*   次に、メモリ領域の先頭が4バイトアライメントされていることを確認し、アライメントされていない場合はバイト単位で埋めてアライメントを合わせます (`_4align` ループ)。
*   アライメントが揃った後、32バイトチャンク (`_f32loop`) で高速にメモリを埋めます。`MOVM.IA.W [R4-R11], (R(TO))` 命令は、複数のレジスタの値を一度にメモリに書き込むARMの命令で、効率的なメモリ操作を可能にします。
*   残りのワード (`_4tail` ループ) とバイト (`_1tail` ループ) を処理し、関数を終了します。
*   `TODO(kaib)` コメントで、`memset` が `R9` と `R10` (Goランタイムの `m` と `g` レジスタ) を破壊する可能性があり、これに対処する必要があることが指摘されています。これは `sys·memclr` で `m` と `g` を保存・復元する理由と一致します。

## 変更の背景

このコミットの背景には、Go言語の `compress/lzw` パッケージを使用する開発者が、LZW圧縮アルゴリズムの `litWidth` パラメータの挙動について誤解したり、その重要な制約を見落としたりする可能性があったという問題があります。特に、以下の2点がドキュメントで十分に説明されていなかったと考えられます。

1.  **`litWidth` と入力バイトの制限**: `litWidth` はリテラルコード（初期辞書のエントリ）のビット幅を定義しますが、これは入力されるバイトデータの値の範囲に直接的な制限を課します。例えば、`litWidth` が8の場合、0から255までのバイト値を表現できますが、`litWidth` が7の場合、0から127までのバイト値しか直接表現できません。この関係が不明確だと、開発者が意図しないデータ損失やエラーに遭遇する可能性がありました。
2.  **圧縮時と解凍時の `litWidth` の一致**: LZW圧縮では、圧縮時に使用された `litWidth` と全く同じ `litWidth` を解凍時にも使用する必要があります。これが一致しない場合、解凍プロセスが失敗するか、破損したデータが生成されます。この重要な要件がドキュメントに明記されていなかったため、相互運用性の問題やデバッグの困難さを引き起こす可能性がありました。

これらの問題は、`Fixes #11142` で言及されているイシューで報告されたものと推測されます。このコミットは、これらの潜在的な問題を解決し、開発者が `compress/lzw` パッケージをより正確かつ安全に使用できるようにするために、ドキュメントの明確化を行いました。

## 前提知識の解説

### LZW (Lempel-Ziv-Welch) 圧縮アルゴリズム

LZWは、可逆データ圧縮アルゴリズムの一種で、特にGIF画像形式などで広く利用されています。基本的な原理は、入力データストリームから繰り返し現れるバイトシーケンス（文字列）を辞書に登録し、そのシーケンスをより短い「コード」に置き換えることでデータを圧縮するというものです。

1.  **初期辞書**: LZWアルゴリズムは、まず既知のシンボル（通常は単一のバイト値）で構成される初期辞書から始まります。例えば、8ビットのバイトデータを扱う場合、辞書には0から255までの各バイト値がそれぞれのエントリとして登録されます。
2.  **辞書の拡張**: 圧縮処理中に、アルゴリズムは入力ストリームから新しいシーケンスを検出し、それを辞書に追加していきます。例えば、「AB」というシーケンスが頻繁に現れる場合、これを新しいコード（例えば256番目のコード）として辞書に登録し、以降の「AB」の出現をそのコードに置き換えます。
3.  **コードの出力**: 圧縮器は、入力ストリームを読み込み、辞書内で最長一致するシーケンスを見つけ、そのシーケンスに対応するコードを出力します。
4.  **解凍**: 解凍器は、圧縮器が構築した辞書と全く同じ辞書を、受信したコードストリームから再構築しながらデータを復元します。

### `litWidth` (Literal Width)

`litWidth` は、LZW圧縮において「リテラルコードのビット幅」を指します。これは、初期辞書に登録される単一の入力シンボル（通常はバイト）を表現するために使用されるビット数です。

*   **役割**: `litWidth` は、初期辞書がいくつのエントリを持つかを決定します。例えば、`litWidth` が8の場合、初期辞書は `2^8 = 256` 個のエントリ（0から255までのバイト値）を持ちます。`litWidth` が2の場合、初期辞書は `2^2 = 4` 個のエントリ（0から3までの値）を持ちます。
*   **入力バイトとの関係**: `litWidth` は、LZWアルゴリズムが直接処理できる入力バイトの値の範囲を暗黙的に定義します。入力バイトの値は `0` から `(1 << litWidth) - 1` の範囲に収まっている必要があります。例えば、`litWidth=8` なら `0` から `255`、`litWidth=7` なら `0` から `127` です。この範囲を超えるバイト値が入力された場合、LZWアルゴリズムは正しく動作しません。
*   **コードの拡張**: LZWアルゴリズムは、圧縮が進むにつれて辞書を拡張し、より長いシーケンスを表現するためにコードのビット幅を動的に増やしていきます。しかし、`litWidth` はあくまで初期辞書のリテラルコードのビット幅を指し、動的に変化するコードのビット幅とは異なります。

### Go言語の `compress/lzw` パッケージ

Go言語の標準ライブラリ `compress/lzw` パッケージは、LZW圧縮および解凍機能を提供します。このパッケージには、`NewReader` 関数と `NewWriter` 関数があり、それぞれ `io.Reader` と `io.Writer` インターフェースを実装したストリームに対してLZW圧縮/解凍を適用します。これらの関数は `litWidth` パラメータを受け取り、LZWアルゴリズムの初期設定を行います。

## 技術的詳細

このコミットは、`compress/lzw` パッケージの `NewReader` および `NewWriter` 関数のドキュメントに、`litWidth` パラメータに関する重要な技術的制約を明記することで、開発者の誤用を防ぎ、より堅牢なコード作成を促します。

### `litWidth` の一致要件

LZW圧縮は、圧縮器と解凍器が同じ辞書構築ロジックを共有していることに依存します。`litWidth` は初期辞書のサイズと構造を決定するため、圧縮時に使用された `litWidth` と解凍時に使用される `litWidth` が異なると、両者の辞書が同期しなくなり、結果として解凍が失敗します。

例えば、圧縮器が `litWidth=8` で動作し、初期辞書に256個の単一バイトエントリと、それに続くクリアコード、停止コードを定義したとします。もし解凍器が誤って `litWidth=7` で初期化された場合、初期辞書は128個の単一バイトエントリしか持たず、クリアコードや停止コードの値も異なります。この不一致により、解凍器は圧縮器が出力したコードストリームを正しく解釈できなくなり、データ破損やエラーが発生します。

このコミットでは、`NewReader` のドキュメントに「`It must equal the litWidth used during compression.`」（圧縮時に使用された `litWidth` と一致しなければならない）という文言を追加することで、この必須要件を明確にしています。

### `litWidth` と入力バイトの制限

`litWidth` は、LZWアルゴリズムが直接処理できる入力バイトの値の範囲を決定します。具体的には、入力されるバイト値は `0` から `(1 << litWidth) - 1` の範囲内である必要があります。

例えば、`litWidth` が8の場合、`1 << 8 = 256` なので、入力バイトは0から255までの値を取ることができます。これは一般的な8ビットバイトデータに適しています。しかし、もし `litWidth` が7に設定された場合、`1 << 7 = 128` なので、入力バイトは0から127までの値しか許容されません。もし128以上のバイト値が入力された場合、LZWアルゴリズムはそれをリテラルコードとして正しく扱えず、予期せぬ動作やエラーを引き起こす可能性があります。

このコミットでは、`NewWriter` のドキュメントに「`Input bytes must be less than 1<<litWidth.`」（入力バイトは `1<<litWidth` 未満でなければならない）という文言を追加することで、この入力値の制約を明確にしています。これにより、開発者は `litWidth` の選択が入力データの特性と合致していることを確認できるようになります。

これらのドキュメントの追加は、LZW圧縮の内部動作を理解していない開発者でも、`litWidth` パラメータの適切な使用法と潜在的な落とし穴を把握できるようにするための重要な改善です。

## コアとなるコードの解説

### `src/compress/lzw/reader.go` の変更点

`NewReader` 関数のドキュメントコメントに、以下の文言が追加されました。

```
It must equal the litWidth used during compression.
```

これは、LZWデータを解凍する際に `NewReader` に渡す `litWidth` の値が、そのデータを圧縮する際に `NewWriter` に渡された `litWidth` の値と**完全に一致しなければならない**という、極めて重要な制約を明示しています。この制約はLZWアルゴリズムの性質上不可欠であり、不一致は解凍エラーやデータ破損に直結します。この追加により、開発者はこの相互運用性の要件を明確に理解し、適切な `litWidth` を使用するよう促されます。

### `src/compress/lzw/writer.go` の変更点

`NewWriter` 関数のドキュメントコメントの既存の行が、以下の文言に変更されました。

```
// range [2,8] and is typically 8. Input bytes must be less than 1<<litWidth.
```

変更前は「`// range [2,8] and is typically 8.`」とだけ書かれていましたが、変更後は「`Input bytes must be less than 1<<litWidth.`」という文言が追加されています。

この追加は、`litWidth` の選択が、圧縮される入力バイトデータの値に暗黙的な上限を課すことを明確にしています。具体的には、入力される各バイトの値は `(1 << litWidth) - 1` 以下でなければなりません。例えば、`litWidth=8` の場合、入力バイトは0から255の範囲である必要があります。もし `litWidth` を小さく設定しすぎると（例: `litWidth=7`）、255のような大きなバイト値は正しく圧縮されません。この制約を明記することで、開発者は `litWidth` を設定する際に、処理する入力データの最大バイト値を考慮する必要があることを理解できます。

これらのドキュメントの変更は、コードの動作自体を変更するものではなく、`compress/lzw` パッケージのAPIの正しい使用法に関する重要な情報を提供し、開発者が陥りやすい間違いを防ぐことを目的としています。

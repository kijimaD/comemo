# [インデックス 25118] ファイルの概要

このコミットは、Go言語のテストスイート内の `test/fixedbugs/issue11656.go` ファイルに対する変更です。このファイルは、Goランタイムが不正なプログラムカウンタ (PC) 値へのジャンプや不正な命令の実行によって発生するクラッシュに対して、正確なスタックトレースを生成できるかを検証するためのテストケースを含んでいます。変更の目的は、このテストの決定論的な動作を保証することです。

## コミット

## 変更の背景

この変更の背景には、Goランタイムが不正なメモリ領域を実行しようとした際に、その結果が予測不可能であるという問題がありました。元の `issue11656.go` テストは、意図的に不正なメモリ領域（具体的には、構造体 `f` のアドレス）を関数ポインタとしてキャストし、それを実行することでクラッシュを誘発していました。しかし、このメモリ領域の内容は不定であり、もしそのメモリが実行可能としてマークされていた場合、どのような命令が実行されるかは環境やタイミングによって異なり、テストの挙動が非決定論的になっていました。

特に、`#11910` で詳細に議論されたように、この非決定性はテストの信頼性を損ねていました。例えば、`arm64` アーキテクチャでは「illegal instruction」が発生するものの、データが実行可能である理由や、スタックトレースが正しく行われない理由が不明確でした。また、`darwin/386`、`openbsd/386`、`netbsd/386`、`windows` など、特定のOS/アーキテクチャの組み合わせではテストが失敗することが知られており、これはテストの不安定さを示していました。

この問題を解決するため、テストを決定論的にするために、各アーキテクチャで既知のトラップ命令（不正命令）を実行するように変更されました。これにより、テストは常に期待されるクラッシュ（不正命令例外）を発生させ、Goランタイムがそのクラッシュに対して正しいスタックトレースを生成できるかを確実に検証できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念が役立ちます。

1.  **不正命令 (Illegal Instruction)**: CPUが認識できない、または現在の特権レベルで実行が許可されていない命令のことです。このような命令が実行されると、通常はCPUが例外（トラップ）を発生させ、オペレーティングシステム（OS）に制御が渡されます。OSは、この例外をシグナル（例: SIGILL）としてプロセスに通知し、プロセスは通常クラッシュします。
2.  **トラップ命令 (Trap Instruction)**: 意図的に例外を発生させるために設計された命令です。デバッガやシステムコールなどで利用されます。例えば、x86アーキテクチャの `ud2` (Undefined Instruction) は、常に不正命令例外を発生させるために使用されます。ARMアーキテクチャの `brk` (Breakpoint) やPowerPCの `trap` 命令も同様の目的で使われます。
3.  **スタックトレース (Stack Trace)**: プログラムがクラッシュした際などに、その時点での関数呼び出しの履歴（コールスタック）を表示するものです。デバッグにおいて、どこで何が起こったかを特定するために非常に重要です。Goランタイムは、クラッシュ時に正確なスタックトレースを提供することが期待されます。
4.  **`unsafe` パッケージ**: Go言語の `unsafe` パッケージは、型安全性をバイパスして低レベルのメモリ操作を可能にします。`unsafe.Pointer` は任意の型のポインタを保持でき、異なる型のポインタ間で変換することができます。これにより、Goの型システムでは通常許されない操作（例: `uintptr` と関数ポインタ間の変換）が可能になりますが、その使用は慎重に行う必要があります。
5.  **`runtime.GOARCH`**: Goプログラムがコンパイルされているターゲットアーキテクチャを示す文字列定数です（例: "amd64", "arm", "arm64", "ppc64"）。この定数を利用することで、特定のアーキテクチャに依存するコードを条件付きでコンパイルしたり、実行時に異なるロジックを適用したりできます。
6.  **`encoding/binary` パッケージ**: Go言語の `encoding/binary` パッケージは、数値データをバイト列に変換したり、その逆を行ったりするための機能を提供します。特に、リトルエンディアン (Little Endian) やビッグエンディアン (Big Endian) といったバイトオーダーを指定して変換できます。CPUの命令は特定のバイトオーダーでメモリに格納されるため、不正命令をバイト列としてメモリに書き込む際にこのパッケージが利用されます。
7.  **メモリの実行権限**: 現代のOSとCPUは、メモリ領域に対して読み取り、書き込み、実行の各権限を設定できます。データセクションは通常、書き込み可能ですが実行不可です。コードセクションは実行可能ですが、通常は書き込み不可です。元のテストでは、データセクションのメモリを実行しようとしていたため、そのメモリが実行可能であるかどうかが環境によって異なり、問題を引き起こしていました。

## 技術的詳細

このコミットの主要な技術的変更は、`issue11656.go` テストがクラッシュを誘発する方法を、非決定論的な「未知のメモリ内容の実行」から、決定論的な「特定のアーキテクチャで既知の不正命令の実行」へと変更した点にあります。

以前のテストでは、`f.x = uintptr(unsafe.Pointer(&f))` のように、構造体 `f` 自体のアドレスを `uintptr` に変換し、それを関数ポインタとして実行しようとしていました。この `&f` が指すメモリ領域はデータセクションに属し、その内容はGoの構造体データで埋められています。このデータがCPUによって命令として解釈されると、その結果は予測不能でした。もしOSがデータセクションを実行不可として設定していれば、即座にセグメンテーション違反（SIGSEGV）が発生する可能性がありましたが、そうでない場合は、不定なバイト列が命令として実行され、たまたま有効な命令として解釈されたり、あるいは不正命令として解釈されたりする可能性がありました。この非決定性がテストの信頼性を低下させていました。

新しいアプローチでは、以下の手順で決定論的なクラッシュを誘発します。

1.  **不正命令のバイト列の準備**: `ill := make([]byte, 64)` でバイトスライスを確保します。このスライスに、各アーキテクチャで確実に不正命令例外を発生させるバイト列を書き込みます。
2.  **アーキテクチャごとの命令選択**: `switch runtime.GOARCH` を使用して、現在の実行環境のCPUアーキテクチャを判別します。
    *   **`386`, `amd64`**: `0x0b0f` (リトルエンディアンで `0f 0b`) は `ud2` 命令です。これは「Undefined Instruction」を意味し、常に不正命令例外を発生させるために設計されています。
    *   **`arm`**: `0xe7f000f0` はARMアーキテクチャにおいて「permanently undefined」とされる命令です。これは、将来の拡張でも使用されないことが保証されており、常に不正命令例外を発生させます。
    *   **`arm64`**: `0xd4207d00` は `brk #1000` 命令です。`brk` はブレークポイント命令であり、デバッガが捕捉するトラップを発生させます。デバッガがアタッチされていない場合は、通常不正命令例外として扱われます。
    *   **`ppc64`, `ppc64le`**: `0x7fe00008` はPowerPCアーキテクチャの `trap` 命令です。これは意図的にシステムトラップを発生させます。`ppc64` はビッグエンディアン、`ppc64le` はリトルエンディアンですが、命令のバイト列自体は同じです。
3.  **バイトオーダーの適用**: `encoding/binary` パッケージの `LittleEndian` または `BigEndian` を使用して、選択した不正命令のバイト列を `ill` スライスに書き込みます。これにより、メモリに正しいバイト順序で命令が配置されます。
4.  **不正命令の実行**: `f.x = uintptr(unsafe.Pointer(&ill[0]))` を使用して、`ill` スライスの先頭アドレスを関数ポインタとしてキャストし、`fn()` を呼び出すことでその不正命令を実行します。

この変更により、テストは常に既知の不正命令を実行するため、その結果は予測可能となり、Goランタイムが不正命令例外をどのように処理し、正確なスタックトレースを生成できるかを確実に検証できるようになりました。また、以前のテストで存在した、特定のOS/アーキテクチャでのビルドタグによる除外（`+build !darwin !386` など）も不要になり、テストの適用範囲が広がりました。

## コアとなるコードの解説

変更されたコアとなるコードブロックは以下の部分です。

```go
	// We want to force an illegal instruction, to get a crash
	// at a PC value != 0.
	// Not all systems make the data section non-executable.
	ill := make([]byte, 64)
	switch runtime.GOARCH {
	case "386", "amd64":
		binary.LittleEndian.PutUint16(ill, 0x0b0f) // ud2
	case "arm":
		binary.LittleEndian.PutUint32(ill, 0xe7f000f0) // no name, but permanently undefined
	case "arm64":
		binary.LittleEndian.PutUint32(ill, 0xd4207d00) // brk #1000
	case "ppc64":
		binary.BigEndian.PutUint32(ill, 0x7fe00008) // trap
	case "ppc64le":
		binary.LittleEndian.PutUint32(ill, 0x7fe00008) // trap
	default:\n		// Just leave it as 0 and hope for the best.
	}

	f.x = uintptr(unsafe.Pointer(&ill[0]))
	fn := *(*func())(unsafe.Pointer(&f))
	fn()
```

1.  **`ill := make([]byte, 64)`**: 64バイトのバイトスライス `ill` を作成します。このスライスは、不正命令のバイト列を格納するために使用されます。サイズが64バイトであるのは、将来的な命令の拡張やアラインメントの要件を考慮している可能性がありますが、今回の命令自体は数バイトです。
2.  **`switch runtime.GOARCH`**: 現在のGoプログラムが実行されているCPUアーキテクチャに基づいて処理を分岐させます。これにより、各アーキテクチャに最適な不正命令を選択できます。
    *   **`case "386", "amd64": binary.LittleEndian.PutUint16(ill, 0x0b0f)`**: x86およびx86-64アーキテクチャの場合、`0x0b0f` (リトルエンディアンで `0f 0b`) は `ud2` 命令です。`PutUint16` は2バイトの値をリトルエンディアンで `ill` スライスの先頭に書き込みます。
    *   **`case "arm": binary.LittleEndian.PutUint32(ill, 0xe7f000f0)`**: ARMアーキテクチャの場合、`0xe7f000f0` は「permanently undefined」命令です。`PutUint32` は4バイトの値をリトルエンディアンで書き込みます。
    *   **`case "arm64": binary.LittleEndian.PutUint32(ill, 0xd4207d00)`**: ARM64アーキテクチャの場合、`0xd4207d00` は `brk #1000` 命令です。`PutUint32` は4バイトの値をリトルエンディアンで書き込みます。
    *   **`case "ppc64": binary.BigEndian.PutUint32(ill, 0x7fe00008)`**: PowerPC 64-bit (ビッグエンディアン) の場合、`0x7fe00008` は `trap` 命令です。`PutUint32` は4バイトの値をビッグエンディアンで書き込みます。
    *   **`case "ppc64le": binary.LittleEndian.PutUint32(ill, 0x7fe00008)`**: PowerPC 64-bit (リトルエンディアン) の場合、`0x7fe00008` は `trap` 命令です。`PutUint32` は4バイトの値をリトルエンディアンで書き込みます。
    *   **`default: // Just leave it as 0 and hope for the best.`**: 上記のいずれのアーキテクチャにも該当しない場合、`ill` スライスは初期値の0のままになります。これは、0x00バイトが不正命令として扱われることを期待するか、あるいはそのようなアーキテクチャではこのテストが重要でないことを示唆しています。
3.  **`f.x = uintptr(unsafe.Pointer(&ill[0]))`**: `ill` スライスの先頭アドレスを `uintptr` に変換し、それを構造体 `f` のフィールド `x` に代入します。これにより、`f.x` は不正命令が格納されたメモリ領域を指すようになります。
4.  **`fn := *(*func())(unsafe.Pointer(&f))`**: 構造体 `f` のアドレスを `unsafe.Pointer` を介して `func()` 型のポインタに変換し、そのポインタが指す関数を `fn` に代入します。この操作は、Goの型システムをバイパスして、任意のメモリ位置を関数として実行するための典型的なパターンです。
5.  **`fn()`**: `fn` を呼び出すことで、`ill` スライスに書き込まれた不正命令が実行され、意図的にクラッシュが誘発されます。

この一連の処理により、テストは常に特定の不正命令を実行し、Goランタイムがその結果として発生する例外（シグナル）を適切に処理し、正確なスタックトレースを生成できるかを検証します。

# [インデックス 21093] ファイルの概要

このコミットは、Go言語のツールチェインの一部である`src/cmd/9l/9.out.h`ファイルに対する変更です。`9.out.h`は、Goのリンカである`9l`（PowerPC 64-bitアーキテクチャ向けのリンカ）が使用するヘッダーファイルであり、主にアセンブラ命令やレジスタ、データ型などの定義を含んでいます。Goのビルドプロセスにおいて、アセンブリコードとGoコードをリンクする際に必要なシンボルや定数を定義する役割を担っています。

## コミット

このコミットは、`9l`リンカのヘッダーファイル`src/cmd/9l/9.out.h`から、特定の`enum`定義のタグ（`as`）を削除するものです。これは、`c2go`ツールとの互換性を確保し、他のコンパイラとの一貫性を保つためのクリーンアップ作業の一環として行われました。また、コメントの修正も含まれています。

## 変更の背景

この変更は、Go言語のツールチェインがC言語のコードベースからGo言語への移行（`c2go`変換）を進める過程で発生した互換性の問題に対処するために行われました。

Go言語の初期のツールチェインは、Plan 9というオペレーティングシステムのツールチェインをベースにしており、その一部はC言語で書かれていました。Go言語が成熟するにつれて、これらのC言語で書かれた部分をGo言語に移植する作業（`c2go`）が進められました。

このコミットの時点では、`9l`リンカのヘッダーファイル`9.out.h`内に定義されていた`enum`に`as`というタグが付与されていました。しかし、他のコンパイラ（おそらくGoの他のアーキテクチャ向けコンパイラや、`c2go`がターゲットとするGoのコンパイラ）では、この特定の`enum`にタグが付いていませんでした。この不一致が`c2go`ツールによる変換の際に問題を引き起こす可能性があったため、互換性を確保し、将来的なクリーンアップを見越して、このタグを削除する必要がありました。

コミットメッセージにある「Cleaning all of this up to use proper types will happen after the conversion.」という記述は、この変更が一時的なものであり、最終的にはより適切な型定義に整理される予定であることを示唆しています。

## 前提知識の解説

### Go言語のツールチェインと`9l`リンカ

Go言語は、独自のコンパイラ、アセンブラ、リンカを含む完全なツールチェインを持っています。
*   **コンパイラ**: Goのソースコードをアセンブリコードに変換します。
*   **アセンブラ**: アセンブリコードをオブジェクトファイルに変換します。
*   **リンカ**: 複数のオブジェクトファイルやライブラリを結合して実行可能ファイルを生成します。

`9l`は、Goのリンカの一つで、特にPowerPC 64-bit (power64) アーキテクチャ向けのリンカを指します。Goのツールチェインは、異なるアーキテクチャやOSに対応するために、それぞれに特化したコンポーネントを持つことがあります。`9l`の「9」は、Plan 9というオペレーティングシステムに由来しており、GoのツールチェインがPlan 9の設計思想や一部のコードベースを継承していることを示しています。

### `c2go`ツール

`c2go`は、C言語で書かれたコードをGo言語のコードに自動変換することを目的としたツールです。Go言語の初期段階では、既存のC言語のコードベースをGoに移行するためにこのようなツールが開発されました。これは、Go言語の自己ホスト化（Goコンパイラ自体をGoで書くこと）や、既存のシステムコードをGoで書き直すプロジェクトにおいて重要な役割を果たしました。

### C言語の`enum`（列挙型）

C言語の`enum`は、整数定数のセットを定義するために使用されるデータ型です。`enum`には、タグ（tag）を付けることができます。

*   **タグ付き`enum`**: `enum TagName { ... };` のように、`enum`キーワードの後に識別子（タグ名）を付けます。このタグ名は、その`enum`型を参照するために使用できます（例: `enum TagName myVar;`）。
*   **匿名`enum`**: `enum { ... };` のように、`enum`キーワードの後にタグ名を付けないで定義します。この場合、その`enum`型自体を参照することはできませんが、その中で定義された列挙子（定数）は直接使用できます。

このコミットで問題となったのは、`enum as`という形式で、`as`がタグとして認識されていたことです。

## 技術的詳細

このコミットの技術的な核心は、C言語の`enum`定義における「タグ」の有無が、異なるコンパイラや変換ツール（特に`c2go`）間で互換性の問題を引き起こす可能性があるという点にあります。

元のコードでは、以下のような`enum`定義がありました。

```c
enum as
{
    AXXX,
    AADD,
    // ...
};
```

ここで、`as`は`enum`のタグとして機能しています。しかし、コミットメッセージによると「None of the other compilers have a tag for this enum.」（他のどのコンパイラもこの`enum`にタグを持っていない）とあります。これは、Goの他のツールチェインコンポーネントや、`c2go`がターゲットとするGoのコンパイラが、この`enum`を匿名`enum`として、つまりタグなしで扱っていたことを示唆しています。

C言語の標準では、タグ付き`enum`と匿名`enum`は異なるエンティティとして扱われます。タグ付き`enum`は新しい型を定義しますが、匿名`enum`は単に一連の整数定数をスコープに導入するだけです。`c2go`のような自動変換ツールは、C言語のコードをGo言語のコードに正確にマッピングする必要があります。もしC言語のソースコードでタグ付き`enum`として扱われているものが、Goのターゲット環境では匿名`enum`として扱われると、型システムやシンボル解決の不一致が生じ、変換エラーや予期せぬ動作につながる可能性があります。

このコミットでは、`enum as`から`as`タグを削除することで、この`enum`を匿名`enum`として扱われるように変更しました。これにより、`c2go`ツールがこのコードをGoに変換する際に、他のコンパイラが期待する形式と一致させ、互換性の問題を解消することができました。

また、コメントの変更も行われています。

```diff
-/* reg names iff type is D_SPR */
+/* reg names in offset field iff type is D_SPR */
```

これは、レジスタ名が`D_SPR`型の場合に、それらが「オフセットフィールド」に格納されることをより正確に記述するための修正です。これはコードの機能には直接影響しませんが、コードの可読性と正確な理解を助けるためのドキュメンテーションの改善です。

## コアとなるコードの変更箇所

`src/cmd/9l/9.out.h`ファイルにおける変更は以下の通りです。

```diff
--- a/src/cmd/9l/9.out.h
+++ b/src/cmd/9l/9.out.h
@@ -131,7 +131,7 @@ enum
 	C_NCLASS,\t/* must be the last */
 };
 
-enum	as
+enum
 {
 	AXXX,
 	AADD,
@@ -501,7 +501,7 @@ enum

```

## コアとなるコードの解説

1.  **`enum as` から `enum` への変更**:
    *   変更前: `enum as`
    *   変更後: `enum`
    *   この変更により、`AXXX`, `AADD` などの列挙子を定義している`enum`が、タグ付き`enum` (`as`というタグを持つ) から匿名`enum`に変わりました。これにより、この`enum`は新しい型を定義するのではなく、単に一連の整数定数を導入するだけになります。これは、`c2go`ツールがこのCコードをGoに変換する際に、他のコンパイラが期待する形式（タグなし`enum`）と一致させるために必要でした。

2.  **コメントの修正**:
    *   変更前: `/* reg names iff type is D_SPR */`
    *   変更後: `/* reg names in offset field iff type is D_SPR */`
    *   この変更は、コメントの正確性を向上させるものです。`D_SPR`型の場合のレジスタ名が、単に「レジスタ名」として扱われるのではなく、「オフセットフィールド内のレジスタ名」として扱われることを明確にしています。これは、コードの動作には影響しませんが、コードを理解する開発者にとってより正確な情報を提供します。

これらの変更は、Goツールチェインの内部的な整合性を高め、特にC言語からGo言語への移行プロセスを円滑に進めるための重要なステップでした。

# [インデックス 23399] ファイルの概要

このコミットは、GoランタイムのPlan 9固有の実装において、`exit`関数が生成する終了ステータスバッファがヌル終端されていなかった問題を修正します。具体的には、`src/runtime/os1_plan9.go`ファイル内の変更であり、終了コードを文字列に変換したバイトスライスに明示的にヌル文字（`0`）を追加することで、この問題を解決しています。

## 元コミット内容

GoランタイムのPlan 9向け実装において、`exit`関数がプロセス終了時に生成するステータスバッファがヌル終端されていませんでした。このバッファは、`exits`システムコールを通じてオペレーティングシステムに渡される際に、ヌル終端されていることを期待されるため、問題を引き起こす可能性がありました。

## 変更の背景

この変更は、GoプログラムがPlan 9上で終了する際に、その終了ステータスが正しく処理されるようにするために行われました。具体的には、Goの`exit`関数が内部で構築するステータス文字列が、Plan 9の`exits`システムコールが期待する形式（ヌル終端された文字列）に合致していなかったため、予期せぬ動作やエラーが発生する可能性がありました。コミットメッセージにある `Fixes #10789` は、この問題がGitHubのIssueトラッカーで報告され、その修正としてこのコミットが作成されたことを示しています。

## 前提知識の解説

### Plan 9 from Bell Labs

Plan 9 from Bell Labsは、Unixの設計者の一部によって開発された分散オペレーティングシステムです。Unixの「全てをファイルとして扱う」という哲学をさらに推し進め、デバイス、プロセス、ネットワークサービスなど、システム内のあらゆるリソースをファイルとして表現し、9Pプロトコルという独自のファイルプロトコルを通じてアクセスします。Go言語は、初期からPlan 9をサポートしており、そのランタイムにはPlan 9固有のコードが含まれています。

### プロセス終了ステータスと`exits`システムコール

オペレーティングシステムにおいて、プロセスが終了する際には、その終了理由や結果を示すステータスコードを親プロセスやシステムに伝達するのが一般的です。Unix系システムでは通常、整数値の終了コードが使われますが、Plan 9ではより詳細な文字列メッセージを`exits`システムコールを通じて提供できます。この`exits`システムコールは、引数としてヌル終端された文字列を期待します。

### ヌル終端文字列

C言語や多くのシステムプログラミングの文脈では、文字列は一連の文字の後にヌル文字（ASCII値0、`\0`）を配置することで終端されます。これにより、文字列の長さを明示的に保持することなく、文字列の終わりを識別できます。ヌル終端されていない文字列を期待するAPIに渡すと、バッファオーバーリードや予期せぬデータ解釈などのセキュリティ脆弱性やバグにつながる可能性があります。

### Goの`itoa`関数（ランタイム内部）

Goの標準ライブラリには`strconv.Itoa`がありますが、Goランタイム内部には、`uint64`型の数値をバイトスライスに変換するための低レベルな`itoa`関数が存在します。これは、ランタイムの内部処理（エラーメッセージの生成など）で効率的に数値文字列を扱うために使用されます。この内部`itoa`関数は、変換結果を既存のバイトスライスに書き込み、そのスライスを返します。

## 技術的詳細

このコミットの核心は、GoランタイムがPlan 9の`exits`システムコールに渡す終了ステータス文字列の生成方法にあります。

元のコードでは、`exit`関数内で終了コード`e`を文字列に変換するために、以下のような処理が行われていました。

1.  `var tmp [32]byte`: 32バイトの固定長バッファ`tmp`を宣言。
2.  `itoa(tmp[:len(tmp)-1], uint64(e))`: 内部`itoa`関数を呼び出し、`e`の値を`tmp`バッファの最後の1バイトを除いた部分に書き込みます。これにより、`tmp`の最後のバイトは未使用のまま残ります。
3.  `&itoa(...)[0]`: `itoa`が返したバイトスライスの先頭アドレスを取得します。
4.  `gostringnocopy(...)`: この関数は、与えられたバイトポインタと長さからGoの文字列を生成するランタイム内部関数です。通常、Cスタイルのヌル終端文字列をGoの文字列に変換する際に使用されます。
5.  `[]byte(...)`: 生成されたGoの文字列を再度バイトスライスに変換し、`status`変数に代入します。

この一連の処理では、`itoa`関数が数値をバイトスライスに変換するだけで、ヌル文字を自動的に追加するわけではありません。また、`gostringnocopy`は、与えられたバイト列がヌル終端されているか、またはその長さが正確に管理されていることを前提とします。しかし、このケースでは、`itoa`が書き込んだバイトスライスにはヌル終端がされておらず、結果として`status`バッファもヌル終端されない状態でした。

Plan 9の`exits`システムコールはヌル終端文字列を期待するため、ヌル終端されていない`status`バッファを渡すと、システムコールがバッファの終わりを正しく認識できず、不正なメモリ領域を読み込んだり、予期せぬエラーを引き起こしたりする可能性がありました。

## コアとなるコードの変更箇所

`src/runtime/os1_plan9.go`ファイルの`exit`関数内の以下の行が変更されました。

```diff
--- a/src/runtime/os1_plan9.go
+++ b/src/runtime/os1_plan9.go
@@ -177,7 +177,7 @@ func exit(e int) {
 	} else {
 		// build error string
 		var tmp [32]byte
-		status = []byte(gostringnocopy(&itoa(tmp[:len(tmp)-1], uint64(e))[0]))
+		status = append(itoa(tmp[:len(tmp)-1], uint64(e)), 0)
 	}
 	goexitsall(&status[0])
 	exits(&status[0])
```

## コアとなるコードの解説

変更後のコードは以下のようになります。

```go
status = append(itoa(tmp[:len(tmp)-1], uint64(e)), 0)
```

この変更のポイントは以下の通りです。

1.  `itoa(tmp[:len(tmp)-1], uint64(e))`: 以前と同様に、終了コード`e`を`tmp`バッファの最後の1バイトを除いた部分に数値文字列として書き込みます。この時点で、`itoa`が返したバイトスライスは数値の文字列表現を含んでいますが、ヌル終端はされていません。
2.  `append(..., 0)`: ここが重要な変更点です。`append`関数を使用して、`itoa`が返したバイトスライスの末尾に明示的にヌル文字（`0`）を追加しています。これにより、`status`変数に代入されるバイトスライスは、常にヌル終端された状態になります。

この修正により、`status`バッファはPlan 9の`exits`システムコールが期待するヌル終端文字列の形式に合致するようになり、Goプログラムの終了ステータスがPlan 9上で正しく処理されることが保証されます。

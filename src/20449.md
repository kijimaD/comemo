# [インデックス 20449] ファイルの概要

このコミットは、Go言語のパーサー（`go/parser`パッケージ）における、複合リテラルと配列の長さの式が絡む特定の「病理学的（pathological）」なコーナーケースのバグ修正に関するものです。具体的には、制御句（`if`文など）内で、型名で始まる複合リテラルが配列の長さの式として使用される場合に発生する構文解析の問題を解決します。

## 元コミット内容

Goパーサー: (病理学的) コーナーケースを修正

制御句（`if ... {}`）内では、型名で始まる複合リテラルは括弧で囲む必要があります。
配列複合リテラルの配列長式で使用される複合リテラルは、すでに括弧で囲まれています。
有効なプログラムではありませんが、構文的には受け入れられるべきです。

## 変更の背景

Go言語の構文解析器は、コードの曖昧さを解消するために特定のルールを持っています。その一つに、「制御句（`if`文や`for`文の条件式など）内で、型名で始まる複合リテラルを使用する場合、その複合リテラルは括弧で囲む必要がある」というものがあります。例えば、`if T{}`というコードは、`if (T{})`（複合リテラルを条件式として使用）と`if T {}`（型`T`の宣言とそれに続く空のブロック）という二通りの解釈が可能であり、この曖昧さを避けるために括弧が義務付けられています。

しかし、このコミットが修正しようとしているのは、このルールが適用されるべきではない、しかしパーサーが誤って適用してしまう「病理学的」なコーナーケースです。具体的には、配列の型定義における長さの式として複合リテラルが使われる場合です。例えば、`[T{}.n]int{}`のような構文です。ここで`T{}`は複合リテラルであり、そのフィールド`n`にアクセスしています。この`T{}.n`全体が配列の長さとして機能しています。

問題は、`[T{}.n]int{}`という構文自体が、`T{}`が配列の長さの式の一部としてすでに「括弧で囲まれている」と見なされるべきであるにもかかわらず、パーサーが制御句のルールを誤って適用し、追加の括弧を要求してしまう点にありました。これは、Go言語の仕様上は構文的に有効であるべきコードが、パーサーによってエラーとされてしまうというバグでした。この修正は、このような稀な、しかし有効な構文が正しく解析されるようにするために行われました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラの基本的な概念を理解しておく必要があります。

1.  **Go言語の構文解析 (Parsing)**:
    *   Goコンパイラの最初の段階であり、ソースコードの文字列を抽象構文木 (AST: Abstract Syntax Tree) と呼ばれる構造に変換するプロセスです。
    *   `go/parser`パッケージは、Go言語のソースコードを解析し、ASTを生成するための機能を提供します。
    *   **トークン (Token)**: 構文解析の最小単位。キーワード（`if`, `for`）、識別子（変数名、関数名）、演算子（`+`, `-`）、リテラル（数値、文字列、複合リテラル）などがあります。
    *   **制御句 (Control Clause)**: `if`文、`for`文、`switch`文などの条件式や初期化ステートメントが記述される部分を指します。

2.  **複合リテラル (Composite Literal)**:
    *   構造体、配列、スライス、マップなどの複合型を初期化するための構文です。
    *   例: `Point{X: 1, Y: 2}` (構造体リテラル), `[]int{1, 2, 3}` (スライスリテラル), `[3]int{1, 2, 3}` (配列リテラル)。
    *   型名と波括弧`{}`で構成されます。

3.  **配列の長さの式 (Array Length Expression)**:
    *   配列型を定義する際に、その長さを指定する部分です。角括弧`[]`の中に記述されます。
    *   例: `[10]int` の `10`、`[...]int` の `...`。
    *   この長さは定数式である必要があります。

4.  **`exprLev` (Expression Level)**:
    *   `go/parser`パッケージの内部で使われていた、パーサーが現在どの程度の「式」の深さにいるかを追跡するための変数（または概念）です。
    *   これは、構文解析のコンテキストを管理し、特定の構文ルール（例えば、制御句内での複合リテラルの括弧の要件）を適切に適用するために使用されます。
    *   `exprLev`が負の値の場合、パーサーが制御句内にいることを示し、0以上の場合は一般的な式を解析していることを示していました。

## 技術的詳細

このコミットの技術的な核心は、`go/parser`パッケージ内の`parseArrayType`関数における`exprLev`変数の操作にあります。

`parseArrayType`関数は、配列型（例: `[N]T`）を解析する責任を負っています。この関数内で、配列の長さ`N`を解析するために`p.parseRhs()`が呼び出されます。`p.parseRhs()`は、右辺の式を解析するための汎用的な関数です。

問題となっていたのは、`if [T{}.n]int{} {}`のようなコードが制御句内に現れた場合です。
1.  パーサーは`if`文の条件式を解析しているため、`exprLev`は負の値になっています。
2.  `[T{}.n]int{}`という配列型リテラルを解析する際に、その中の`T{}.n`という配列の長さの式を解析しようとします。
3.  この`T{}.n`の`T{}`は複合リテラルです。Goの構文ルールでは、制御句内のトップレベルの複合リテラルは曖昧さ回避のために括弧で囲む必要があります。
4.  しかし、`T{}.n`は配列の長さの式の一部であり、この文脈では`T{}`はすでに「括弧で囲まれている」と見なされるべきです。つまり、`[ (T{}).n ]int{}`のように、配列の角括弧が暗黙的に括弧の役割を果たしていると解釈されるべきです。
5.  にもかかわらず、`exprLev`が負のままであるため、パーサーは`T{}`に対して「制御句内の複合リテラルは括弧が必要」というルールを誤って適用し、構文エラーを報告していました。

この修正は、`parseArrayType`関数が配列の長さの式を解析する直前に`p.exprLev`をインクリメントし、解析後にデクリメントすることで、この問題を解決します。
*   `p.exprLev++`: これにより、配列の長さの式を解析している間だけ、パーサーのコンテキストが「制御句内」から「一般的な式内」へと一時的に変更されます。これにより、複合リテラルの括弧に関する厳格なルールが緩和されます。
*   `p.exprLev--`: 配列の長さの式の解析が完了した後、`exprLev`を元の値に戻し、パーサーのコンテキストを復元します。

この変更により、`if [T{}.n]int{} {}`のような、構文的には有効だがパーサーが誤って拒否していたコードが正しく解析されるようになります。これは、Go言語のパーサーがより堅牢になり、言語仕様に厳密に準拠するようになったことを意味します。

## コアとなるコードの解説

`src/go/parser/parser.go`の変更は、Goパーサーが配列型を解析する際の挙動を微調整するものです。

`parseArrayType`関数は、`[`トークン（`token.LBRACK`）を期待し、その後に配列の長さを解析します。
*   `lbrack := p.expect(token.LBRACK)`: 左角括弧`[`を期待して読み込みます。
*   `p.exprLev++`: ここが重要な変更点です。配列の長さの式（`len`）を解析する直前に、パーサーの式レベルカウンター`exprLev`を1増やします。これにより、パーサーは一時的に「制御句内」の厳格な複合リテラル括弧ルールから解放され、配列の長さの式がより柔軟に解析されるようになります。
*   `len = p.parseRhs()`: 配列の長さの式を解析します。この式の中に、問題となっていた`T{}.n`のような複合リテラルが含まれる可能性があります。`exprLev`がインクリメントされているため、`T{}`がすでに配列の角括弧によって「囲まれている」と正しく認識され、追加の括弧が不要と判断されます。
*   `p.exprLev--`: 配列の長さの式の解析が完了した後、`exprLev`を元の値に戻します。これにより、パーサーは通常のコンテキストに戻り、他の構文解析に影響を与えません。

この修正は、Go言語の構文解析器が、特定の文脈における複合リテラルの扱いについて、より正確な判断を下せるようにするためのものです。これにより、言語仕様に準拠した、しかし以前はエラーとされていた有効なコードが、正しく解析されるようになりました。

`src/go/parser/short_test.go`に追加されたテストケース`package p; func _() { if [T{}.n]int{} {} }`は、この修正が意図通りに機能することを確認するためのものです。このコードは、`if`文の条件式内で、`[T{}.n]int{}`という配列型リテラルを使用しています。修正前は、`T{}`が括弧で囲まれていないためにパーサーエラーが発生していましたが、修正後はこのテストが成功するようになります。

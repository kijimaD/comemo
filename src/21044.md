## 変更の背景

Go言語のガベージコレクタ（GC）は、アプリケーション（ミューテーター）と並行して動作するコンカレントGCを採用しています。このようなシステムでは、GCがメモリをスキャンしている間にミューテーターがポインタを書き換えることで、GCがオブジェクトを見落とし、誤って解放してしまう「ポインタの消失」問題が発生する可能性があります。これを防ぐために「ライトバリア」が導入されています。

このコミットの背景には、従来のDijkstraライトバリアの複雑さと、それに伴う性能上の課題がありました。Dijkstraのライトバリアは、ポインタの書き込み時に特定の条件（例えば、書き込まれる先のオブジェクトが黒色であるかなど）に基づいて処理を分岐させていました。しかし、この条件分岐は、特に並行性の高い環境において、予測不能なパフォーマンスのオーバーヘッドや、メモリバリアの挿入によるコスト増大を招く可能性がありました。

コミットメッセージで言及されている「IRIW (Independent Reads of Independent Writes)」の問題は、複数のスレッドが独立したメモリ位置に書き込み、その後独立したメモリ位置から読み取る際に、ハードウェアのメモリモデルによっては予期せぬ結果が生じる可能性があることを示唆しています。このような複雑な並行性の問題に対処するためには、ライトバリアのロジックを簡素化し、より堅牢にすることが求められました。

この変更は、ライトバリアのロジックを「粗くする（Coarsen）」ことで、条件分岐をなくし、常に宛先オブジェクトをグレーにマークするようにすることで、これらの課題に対処しようとするものです。これにより、GCの正確性を維持しつつ、並行実行時のパフォーマンスを安定させることを目指しています。

## 前提知識の解説

### 1. 三色マーキング (Tri-Color Marking)

Goのガベージコレクタは、Dijkstraが1978年に提唱した三色マーキングアルゴリズムをベースにしています。このアルゴリズムでは、メモリ上のオブジェクトを以下の3つの色で分類します。

*   **白色 (White)**: GCによってまだ訪問されていないオブジェクト。GCサイクルの開始時には、すべてのオブジェクトが白色と見なされます。最終的に白色のまま残ったオブジェクトは、到達不可能と判断され、ガベージとして回収されます。
*   **灰色 (Grey)**: GCによって訪問されたが、そのオブジェクトが参照している他のオブジェクト（ポインタ）がまだスキャンされていないオブジェクト。灰色オブジェクトは、GCの作業キューに入れられ、順次スキャンされます。
*   **黒色 (Black)**: GCによって訪問され、そのオブジェクトが参照しているすべてのオブジェクトもスキャン済みであるオブジェクト。黒色オブジェクトは、到達可能であり、ガベージではないと判断されます。

GCの目標は、到達可能なすべてのオブジェクトを黒色にすることです。

### 2. Dijkstraのライトバリア (Dijkstra's Write Barrier)

コンカレントGCでは、GCがマークフェーズを実行している間も、ミューテーター（アプリケーションの実行スレッド）がオブジェクトグラフを変更し続けます。このとき、ミューテーターがポインタを書き換えることで、GCが既にスキャンした黒色オブジェクトから、まだスキャンされていない白色オブジェクトへの参照が作成される可能性があります。このような状況を「ポインタの消失」と呼び、GCの正確性を損なう原因となります。

Dijkstraのライトバリアは、このポインタの消失を防ぐためのメカニズムです。基本的なDijkstraのライトバリアは、「黒色オブジェクトから白色オブジェクトへのポインタの作成を禁止する」という原則に基づいています。具体的には、ミューテーターがポインタを書き込む際、もし書き込まれる先のオブジェクト（`ptr`）が白色であれば、そのオブジェクトを直ちに灰色にマークします。これにより、GCがそのオブジェクトをスキャンし、そこから到達可能な他のオブジェクトを見つけることが保証されます。

### 3. IRIW (Independent Reads of Independent Writes)

IRIWは「Independent Reads of Independent Writes」の略で、並行プログラミングにおけるメモリモデルの概念の一つです。これは、複数のスレッドがそれぞれ異なるメモリ位置に書き込みを行い、その後、それぞれ異なるメモリ位置から読み取りを行うシナリオを指します。

コミットメッセージの例では、ミューテーターとGCスレッドがそれぞれ独立したメモリ位置（`[slot]`と`[slotmark]`）に書き込み、その後読み取りを行う状況が示されています。

```
Mutator thread          GC thread
st [slot], ptr          st [slotmark], 1

ld r1, [slotmark]       ld r2, [slot]
```

この例は、メモリバリアなしでは`r1==r2==0`（両方の読み取りが初期値のnilを返す）という結果が許容される可能性があることを示唆しています。これは、書き込みと読み取りの順序がハードウェアレベルで保証されない場合に発生しうる競合状態の一例です。このような問題は、GCの正確性に直接影響を与える可能性があり、ライトバリアの設計において考慮すべき重要な要素となります。高価なメモリバリアを挿入することなく、この問題を回避するために、ライトバリアのロジックを簡素化するアプローチが取られました。

## 技術的詳細

このコミットの主要な技術的変更は、Goランタイムのライトバリアのロジックを「粗くする（Coarsen）」ことです。従来のDijkstraライトバリアは、ポインタの書き込み時に、書き込まれる先のオブジェクト（`ptr`）が白色である場合にのみ`shade`関数を呼び出して灰色にマークしていました。これは、`shaded((byte*)slot)`という条件によって制御されていました。

しかし、この条件付きの処理にはいくつかの課題がありました。

1.  **パフォーマンスのオーバーヘッド**: 条件分岐は、CPUのパイプライン予測を困難にし、分岐予測ミスによる性能低下を招く可能性があります。
2.  **並行性の複雑さ**: ミューテーターとGCスレッドが同時に動作する環境では、`slot`の色（黒色か白色か）を正確に判断し、その状態がライトバリアの実行中に変化しないことを保証することが非常に困難です。特に、`slot`を保持するオブジェクトがGCによって並行して黒色に変化する可能性があり、これをミューテーターが検知できないと問題が生じます。コミットメッセージのIRIWの例は、この並行性の問題を示しています。メモリバリアを挿入することで解決できますが、これは高価な操作です。

このコミットでは、これらの課題に対処するため、ライトバリアのロジックを簡素化し、`shaded((byte*)slot)`という条件を削除しました。これにより、`ptr`が`nil`でなく、ヒープ内に存在する場合、**常に** `shade(ptr)`が呼び出され、`ptr`が灰色にマークされるようになります。

この「粗くする」アプローチの利点は以下の通りです。

*   **ロジックの簡素化**: 条件分岐がなくなるため、ライトバリアのコードがよりシンプルになり、理解しやすくなります。
*   **パフォーマンスの安定化**: 分岐予測ミスが減少し、メモリバリアの必要性が緩和されることで、ライトバリアの実行コストがより予測可能になります。
*   **堅牢性の向上**: `slot`の色の並行的な変化を考慮する必要がなくなるため、並行GCの正確性が向上します。

一方で、この変更にはトレードオフもあります。`ptr`が既に灰色または黒色である場合でも`shade`関数が呼び出されるため、一部の`shade`呼び出しは冗長になる可能性があります。しかし、この冗長性によるオーバーヘッドは、条件分岐や複雑な並行性制御によるオーバーヘッドよりも小さいと判断されました。

結論として、この変更は、GoのコンカレントGCにおけるライトバリアの正確性とパフォーマンスのバランスを最適化するための重要なステップであり、特に並行性の高い環境での安定性を向上させることを目的としています。

## コアとなるコードの変更箇所

変更は`src/runtime/mgc0.c`ファイル内の`runtime·gcmarkwb_m()`関数に集中しています。

具体的には、`GCmark`と`GCmarktermination`のケースにおける`if`文の条件が変更されました。

**変更前:**

```c
	case GCmark:
		if(ptr != nil && inheap(ptr) && shaded((byte*)slot))
			shade(ptr);
		break;
	case GCmarktermination:
		if(ptr != nil && inheap(ptr) && shaded((byte*)slot))
			shade(ptr);
		break;
```

**変更後:**

```c
	case GCmark:
		if(ptr != nil && inheap(ptr))
			shade(ptr);
		break;
	case GCmarktermination:
		if(ptr != nil && inheap(ptr))
			shade(ptr);
		break;
```

`shaded((byte*)slot)`という条件が削除され、`ptr`が`nil`でなく、ヒープ内に存在する場合に常に`shade(ptr)`が呼び出されるようになりました。

## コアとなるコードの解説

`runtime·gcmarkwb_m()`関数は、Goランタイムにおけるライトバリアの実装の一部です。この関数は、ミューテーターがポインタを書き込む際に呼び出され、GCの正確性を維持するための処理を実行します。

変更前のコードでは、`GCmark`（マークフェーズ）と`GCmarktermination`（マーク終了フェーズ）において、`ptr`が`nil`でなく、ヒープ内に存在し、かつ`slot`が`shaded`（つまり、`slot`が黒色である）場合にのみ`shade(ptr)`を呼び出していました。`shaded`関数は、オブジェクトが既にGCによってスキャンされ、黒色にマークされているかどうかをチェックします。

この条件は、Dijkstraのライトバリアの原則「黒色から白色へのポインタの作成を禁止する」を直接反映したものでした。つまり、既にスキャン済みの黒色オブジェクトのフィールドに白色オブジェクトへのポインタが書き込まれる場合にのみ、その白色オブジェクトを灰色にマークしてGCが追跡できるようにしていました。

しかし、このコミットによって`shaded((byte*)slot)`条件が削除されたことで、`runtime·gcmarkwb_m()`は、`ptr`が有効なヒープオブジェクトである限り、**常に** `shade(ptr)`を呼び出すようになりました。

`shade(ptr)`関数は、指定されたオブジェクト`ptr`を灰色にマークし、GCの作業キュー（`wbuf`）に追加する役割を担っています。これにより、GCは後でこのオブジェクトをスキャンし、そこから到達可能な他のオブジェクトを探索します。

この変更により、ライトバリアはよりシンプルかつアグレッシブになりました。ポインタが書き込まれるたびに、宛先オブジェクトがGCによって確実に追跡されるようになります。これにより、並行GCにおけるポインタ消失のリスクが低減され、メモリモデルの複雑性（IRIWなど）による潜在的な問題を回避しやすくなります。

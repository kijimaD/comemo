## 元コミット内容

Goコンパイラの内部SSAパッケージにおいて、`fuse`最適化パスがPhi関数を適切に処理するように変更されました。これにより、条件分岐後のブロック結合において、Phi関数の引数が同一である場合にブロックを結合できるようになります。

## 変更の背景

Goコンパイラは、プログラムの最適化のためにSSA (Static Single Assignment) 形式を使用します。SSA形式では、各変数は一度だけ代入されるという特性を持ちます。しかし、条件分岐などで複数のパスが合流する際には、異なるパスで同じ論理変数に異なる値が代入される可能性があります。この問題を解決するために導入されるのが「Phi関数」です。Phi関数は、合流点において、どのパスから来たかによって適切な値を選択する役割を担います。

`fuse`最適化は、コンパイラが生成する中間表現（IR）のブロック（基本的な実行単位）を結合することで、コードの冗長性を減らし、後続の最適化パスの効率を高めることを目的としています。特に、条件分岐（`BlockIf`）の後に続く空のブロック（`BlockPlain`）を結合するケースが一般的です。

このコミット以前の`fuseBlockIf`関数は、合流先のブロック（`ss`）にPhi関数が存在しない場合にのみブロックの結合を試みていました。しかし、Phi関数が存在する場合でも、そのPhi関数が異なるパスから同じ値を受け取るのであれば、実質的にPhi関数は不要であり、ブロックを結合してもセマンティクスは変化しません。この制限は、最適化の機会を逃していました。

この変更の背景には、より積極的な最適化を適用し、生成されるコードの効率を向上させたいという意図があります。Phi関数が同一の引数を持つ場合でもブロックを結合できるようにすることで、コンパイラはより多くの冗長なブロックを削除し、より簡潔な制御フローグラフを生成できるようになります。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において広く用いられる中間表現の形式です。この形式では、プログラム中のすべての変数に対して、ただ一度だけ値が代入されることが保証されます。もし同じ論理変数に複数回代入が行われる場合、SSA形式では新しい「バージョン」の変数が導入されます（例: `x1 = ...`, `x2 = ...`）。

SSA形式の主な利点は以下の通りです。
*   **データフロー解析の簡素化**: 各変数の定義と使用が明確になるため、データフロー解析が容易になります。
*   **最適化の機会の増加**: 共通部分式除去、定数伝播、デッドコード除去などの多くの最適化がSSA形式上で効率的に行えます。

### 2. Phi関数 (Φ関数)

SSA形式におけるPhi関数は、複数の制御フローパスが合流する地点（例: `if-else`文の終わり、ループの合流点）で、どのパスから来たかによって適切な変数の値を選択するために導入される特殊な命令です。

例えば、以下のGoコードを考えます。

```go
var x int
if condition {
    x = 1
} else {
    x = 2
}
// ここで x の値は？
```

SSA形式では、`x`は`x1`と`x2`に分かれます。

```
if condition {
    x1 = 1
} else {
    x2 = 2
}
x3 = Φ(x1, x2) // Phi関数が x1 または x2 を選択
```

Phi関数は、合流する各パスからの引数を取り、実行時にどのパスが選択されたかに応じてそのパスに対応する引数の値を返します。

### 3. コンパイラのブロックと制御フローグラフ (CFG)

コンパイラは、プログラムを「基本ブロック (Basic Block)」と呼ばれる単位に分割します。基本ブロックは、入り口が一つで出口が一つであり、内部に分岐を含まない一連の命令です。これらの基本ブロックと、それらの間の制御フロー（どのブロックからどのブロックへ実行が移るか）の関係をグラフで表現したものが「制御フローグラフ (Control Flow Graph, CFG)」です。

*   `BlockIf`: 条件分岐（`if`文）を表すブロック。通常、2つの後続ブロック（`Succs`）を持ちます。
*   `BlockPlain`: 無条件ジャンプ（`goto`）を表すブロック。通常、1つの後続ブロックを持ちます。
*   `BlockInvalid`: 無効化されたブロック。最適化によって削除されたブロックがこの状態になります。

### 4. `fuse`最適化

`fuse`最適化は、CFGを簡素化し、冗長なジャンプや空のブロックを削除することを目的とした最適化パスです。特に、`if`文の後に続く空のブロックを結合するケースが対象となります。

例えば、以下のようなCFGがあったとします。

```
   b
  / \
 s0  s1
  \ /
   ss
```

ここで、`b`は条件分岐ブロック、`s0`と`s1`は空のプレーンブロック、`ss`は合流後のブロックです。`s0`と`s1`が何の処理も行わない場合、`b`から直接`ss`にジャンプできるように変更することで、`s0`と`s1`を削除し、CFGを簡素化できます。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/ssa/fuse.go` 内の `fuseBlockIf` 関数に焦点を当てています。この関数は、`BlockIf` タイプのブロック `b` が、その後に続く空の `BlockPlain` を持つ場合に、それらを結合（フューズ）しようとします。

変更前の `fuseBlockIf` は、合流先のブロック `ss` に `OpPhi` (Phi関数) が存在する場合、ブロックの結合を諦めていました。これは、Phi関数が異なるパスからの異なる値を処理する可能性があるため、安易にブロックを結合するとプログラムのセマンティクスが変化してしまう恐れがあったためです。

しかし、このコミットでは、Phi関数が存在する場合でも、そのPhi関数が受け取る引数が、結合しようとしている2つのパス（`s0`と`s1`）において**同一の値**であるならば、ブロックを結合しても問題ないという洞察に基づいています。もし`s0`と`s1`のどちらのパスを通ってもPhi関数が同じ値を選択するのであれば、そのPhi関数は実質的に不要であり、ブロックを結合しても結果は変わりません。

具体的な変更点は以下の通りです。

1.  **Phi関数の引数比較ロジックの追加**:
    `fuseBlockIf` 関数内で、合流先のブロック `ss` に含まれるすべての `OpPhi` 命令を走査します。
    各 `OpPhi` 命令 `v` について、`s0` に対応する引数 (`v.Args[i0]`) と `s1` に対応する引数 (`v.Args[i1]`) を比較します。
    もしこれらの引数が異なる (`v.Args[i0] != v.Args[i1]`) 場合、ブロックの結合は安全ではないと判断し、`false` を返してフュージョンを中止します。
    これにより、Phi関数が異なる値を処理する可能性がある場合に、誤ってブロックが結合されることを防ぎます。

2.  **ブロック削除ロジックの修正**:
    以前は、`s0` と `s1` の両方が存在する場合にのみ、`ss.Preds = append(ss.Preds, b)` を使って `b` から `ss` へのエッジを追加していました。
    新しいロジックでは、`s0 != b && s1 != b` (つまり、`s0` と `s1` の両方が実際に存在する空ブロックである場合) に、`b` から `s1` へのエッジを `b` から `ss` へのエッジに置き換える処理が追加されました。これは、`b.Succs` と `ss.Preds` の両方を更新することで実現されます。
    また、`s0` または `s1` のいずれか一方のみが空ブロックである場合（図の2番目、3番目のケース）、対応するプレーンブロックを `ss` の先行ブロックリストから削除する処理がより明確に記述されています。

3.  **テストケースの追加**:
    `src/cmd/compile/internal/ssa/fuse_test.go` に `TestFuseHandlesPhis` という新しいテストケースが追加されました。このテストは、Phi関数が存在し、かつその引数が同一である場合に `fuseBlockIf` が正しくブロックを結合し、空のブロック (`then` と `else`) を削除することを確認します。これにより、新しいロジックの正確性が保証されます。

この変更により、コンパイラはより多くのケースで `fuse` 最適化を適用できるようになり、結果として生成される機械語コードの効率が向上する可能性があります。特に、冗長なジャンプ命令が削減され、キャッシュ効率の改善や命令パイプラインの詰まりの軽減に寄与することが期待されます。

## コアとなるコードの解説

`fuseBlockIf` 関数は、以下のような制御フローパターンを最適化対象とします。

```
   b (BlockIf)
  / \
 s0  s1 (BlockPlain, 空のブロック)
  \ /
   ss (合流後のブロック)
```

この関数は、`b` が条件分岐ブロックであり、その両方または片方の後続が空の `BlockPlain` `s0` または `s1` であり、それらが最終的に同じ `ss` ブロックに合流する場合に呼び出されます。

変更の核心は、`ss` ブロック内の `OpPhi` 命令の処理です。

1.  **先行ブロックのインデックス特定**:
    まず、`ss` ブロックの先行ブロックリスト (`ss.Preds`) を走査し、`s0` と `s1` に対応するインデックス (`i0`, `i1`) を特定します。これは、Phi関数がどの引数がどの先行ブロックに対応するかを識別するために必要です。

2.  **Phi関数の引数比較**:
    `ss.Values` (ブロック内の命令リスト) を走査し、`OpPhi` 命令 (`v`) を見つけます。
    `if v.Op == OpPhi && v.Args[i0] != v.Args[i1]` の条件で、`s0` から来る値 (`v.Args[i0]`) と `s1` から来る値 (`v.Args[i1]`) が異なるかどうかをチェックします。
    もし異なっていれば、このPhi関数は異なるパスからの異なる値を処理しているため、`s0` と `s1` を削除して `b` から `ss` へ直接ジャンプするように変更すると、プログラムのセマンティクスが変化してしまいます。したがって、この場合はフュージョンを中止し、`false` を返します。

3.  **ブロック結合とエッジ更新**:
    Phi関数の引数がすべて同一である（またはPhi関数が存在しない）と判断された場合、フュージョンが安全であるとみなされます。
    *   `s0 != b && s1 != b` の場合（`s0` と `s1` の両方が実際に存在する空ブロックの場合）：
        `ss` から `s0` の先行エッジを削除します (`ss.removePred(s0)`)。
        `b` から `s1` へのエッジを `b` から `ss` へのエッジに置き換えます。これは、`b.Succs` と `ss.Preds` の両方を更新することで行われます。これにより、`b` から `ss` への直接的なパスが確立されます。
    *   `s0 != b` の場合（`s0` のみが空ブロックの場合）：
        `ss` から `s0` の先行エッジを削除します。
    *   `s1 != b` の場合（`s1` のみが空ブロックの場合）：
        `ss` から `s1` の先行エッジを削除します。

4.  **`b` ブロックの変換**:
    `b` ブロックの種類を `BlockPlain` に変更し、制御情報 (`b.Control`) を `nil` に設定します。
    `b` の後続ブロックを `ss` のみに設定します (`b.Succs = append(b.Succs[:0], ss)`)。これにより、`b` は単一の後続を持つ無条件ジャンプブロックになります。

5.  **空ブロックの無効化**:
    フュージョンによって不要になった `s0` および `s1` ブロックは、`BlockInvalid` に設定され、その値、後続、先行ブロックリストがクリアされます。これにより、これらのブロックはコンパイラの以降のパスで無視され、最終的に削除されます。

この一連の処理により、Phi関数がセマンティクスを維持できる場合に限り、条件分岐後の冗長な空ブロックが削除され、制御フローグラフが簡素化されます。

## 元コミット内容

Goコンパイラの内部SSAパッケージにおいて、`fuse`最適化パスがPhi関数を適切に処理するように変更されました。これにより、条件分岐後のブロック結合において、Phi関数の引数が同一である場合にブロックを結合できるようになります。

## 変更の背景

Goコンパイラは、プログラムの最適化のためにSSA (Static Single Assignment) 形式を使用します。SSA形式では、各変数は一度だけ代入されるという特性を持ちます。しかし、条件分岐などで複数のパスが合流する際には、異なるパスで同じ論理変数に異なる値が代入される可能性があります。この問題を解決するために導入されるのが「Phi関数」です。Phi関数は、合流点において、どのパスから来たかによって適切な値を選択する役割を担います。

`fuse`最適化は、コンパイラが生成する中間表現（IR）のブロック（基本的な実行単位）を結合することで、コードの冗長性を減らし、後続の最適化パスの効率を高めることを目的としています。特に、条件分岐（`BlockIf`）の後に続く空のブロック（`BlockPlain`）を結合するケースが一般的です。

このコミット以前の`fuseBlockIf`関数は、合流先のブロック（`ss`）にPhi関数が存在しない場合にのみブロックの結合を試みていました。しかし、Phi関数が存在する場合でも、そのPhi関数が異なるパスから同じ値を受け取るのであれば、実質的にPhi関数は不要であり、ブロックを結合してもセマンティクスは変化しません。この制限は、最適化の機会を逃していました。

この変更の背景には、より積極的な最適化を適用し、生成されるコードの効率を向上させたいという意図があります。Phi関数が同一の引数を持つ場合でもブロックを結合できるようにすることで、コンパイラはより多くの冗長なブロックを削除し、より簡潔な制御フローグラフを生成できるようになります。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において広く用いられる中間表現の形式です。この形式では、プログラム中のすべての変数に対して、ただ一度だけ値が代入されることが保証されます。もし同じ論理変数に複数回代入が行われる場合、SSA形式では新しい「バージョン」の変数が導入されます（例: `x1 = ...`, `x2 = ...`）。

SSA形式の主な利点は以下の通りです。
*   **データフロー解析の簡素化**: 各変数の定義と使用が明確になるため、データフロー解析が容易になります。
*   **最適化の機会の増加**: 共通部分式除去、定数伝播、デッドコード除去などの多くの最適化がSSA形式上で効率的に行えます。

### 2. Phi関数 (Φ関数)

SSA形式におけるPhi関数は、複数の制御フローパスが合流する地点（例: `if-else`文の終わり、ループの合流点）で、どのパスから来たかによって適切な変数の値を選択するために導入される特殊な命令です。

例えば、以下のGoコードを考えます。

```go
var x int
if condition {
    x = 1
} else {
    x = 2
}
// ここで x の値は？
```

SSA形式では、`x`は`x1`と`x2`に分かれます。

```
if condition {
    x1 = 1
} else {
    x2 = 2
}
x3 = Φ(x1, x2) // Phi関数が x1 または x2 を選択
```

Phi関数は、合流する各パスからの引数を取り、実行時にどのパスが選択されたかに応じてそのパスに対応する引数の値を返します。

### 3. コンパイラのブロックと制御フローグラフ (CFG)

コンパイラは、プログラムを「基本ブロック (Basic Block)」と呼ばれる単位に分割します。基本ブロックは、入り口が一つで出口が一つであり、内部に分岐を含まない一連の命令です。これらの基本ブロックと、それらの間の制御フロー（どのブロックからどのブロックへ実行が移るか）の関係をグラフで表現したものが「制御フローグラフ (Control Flow Graph, CFG)」です。

*   `BlockIf`: 条件分岐（`if`文）を表すブロック。通常、2つの後続ブロック（`Succs`）を持ちます。
*   `BlockPlain`: 無条件ジャンプ（`goto`）を表すブロック。通常、1つの後続ブロックを持ちます。
*   `BlockInvalid`: 無効化されたブロック。最適化によって削除されたブロックがこの状態になります。

### 4. `fuse`最適化

`fuse`最適化は、CFGを簡素化し、冗長なジャンプや空のブロックを削除することを目的とした最適化パスです。特に、`if`文の後に続く空のブロックを結合するケースが対象となります。

例えば、以下のようなCFGがあったとします。

```
   b
  / \
 s0  s1
  \ /
   ss
```

ここで、`b`は条件分岐ブロック、`s0`と`s1`は空のプレーンブロック、`ss`は合流後のブロックです。`s0`と`s1`が何の処理も行わない場合、`b`から直接`ss`にジャンプできるように変更することで、`s0`と`s1`を削除し、CFGを簡素化できます。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/ssa/fuse.go` 内の `fuseBlockIf` 関数に焦点を当てています。この関数は、`BlockIf` タイプのブロック `b` が、その後に続く空の `BlockPlain` を持つ場合に、それらを結合（フューズ）しようとします。

変更前の `fuseBlockIf` は、合流先のブロック `ss` に `OpPhi` (Phi関数) が存在する場合、ブロックの結合を諦めていました。これは、Phi関数が異なるパスからの異なる値を処理する可能性があるため、安易にブロックを結合するとプログラムのセマンティクスが変化してしまう恐れがあったためです。

しかし、このコミットでは、Phi関数が存在する場合でも、そのPhi関数が受け取る引数が、結合しようとしている2つのパス（`s0`と`s1`）において**同一の値**であるならば、ブロックを結合しても問題ないという洞察に基づいています。もし`s0`と`s1`のどちらのパスを通ってもPhi関数が同じ値を選択するのであれば、そのPhi関数は実質的に不要であり、ブロックを結合しても結果は変わりません。

具体的な変更点は以下の通りです。

1.  **Phi関数の引数比較ロジックの追加**:
    `fuseBlockIf` 関数内で、合流先のブロック `ss` に含まれるすべての `OpPhi` 命令を走査します。
    各 `OpPhi` 命令 `v` について、`s0` に対応する引数 (`v.Args[i0]`) と `s1` に対応する引数 (`v.Args[i1]`) を比較します。
    もしこれらの引数が異なる (`v.Args[i0] != v.Args[i1]`) 場合、ブロックの結合は安全ではないと判断し、`false` を返してフュージョンを中止します。
    これにより、Phi関数が異なる値を処理する可能性がある場合に、誤ってブロックが結合されることを防ぎます。

2.  **ブロック削除ロジックの修正**:
    以前は、`s0` と `s1` の両方が存在する場合にのみ、`ss.Preds = append(ss.Preds, b)` を使って `b` から `ss` へのエッジを追加していました。
    新しいロジックでは、`s0 != b && s1 != b` (つまり、`s0` と `s1` の両方が実際に存在する空ブロックである場合) に、`b` から `s1` へのエッジを `b` から `ss` へのエッジに置き換える処理が追加されました。これは、`b.Succs` と `ss.Preds` の両方を更新することで実現されます。
    また、`s0` または `s1` のいずれか一方のみが空ブロックである場合（図の2番目、3番目のケース）、対応するプレーンブロックを `ss` の先行ブロックリストから削除する処理がより明確に記述されています。

3.  **テストケースの追加**:
    `src/cmd/compile/internal/ssa/fuse_test.go` に `TestFuseHandlesPhis` という新しいテストケースが追加されました。このテストは、Phi関数が存在し、かつその引数が同一である場合に `fuseBlockIf` が正しくブロックを結合し、空のブロック (`then` と `else`) を削除することを確認します。これにより、新しいロジックの正確性が保証されます。

この変更により、コンパイラはより多くのケースで `fuse` 最適化を適用できるようになり、結果として生成される機械語コードの効率が向上する可能性があります。特に、冗長なジャンプ命令が削減され、キャッシュ効率の改善や命令パイプラインの詰まりの軽減に寄与することが期待されます。

## コアとなるコードの解説

`fuseBlockIf` 関数は、以下のような制御フローパターンを最適化対象とします。

```
   b (BlockIf)
  / \
 s0  s1 (BlockPlain, 空のブロック)
  \ /
   ss (合流後のブロック)
```

この関数は、`b` が条件分岐ブロックであり、その両方または片方の後続が空の `BlockPlain` `s0` または `s1` であり、それらが最終的に同じ `ss` ブロックに合流する場合に呼び出されます。

変更の核心は、`ss` ブロック内の `OpPhi` 命令の処理です。

1.  **先行ブロックのインデックス特定**:
    まず、`ss` ブロックの先行ブロックリスト (`ss.Preds`) を走査し、`s0` と `s1` に対応するインデックス (`i0`, `i1`) を特定します。これは、Phi関数がどの引数がどの先行ブロックに対応するかを識別するために必要です。

2.  **Phi関数の引数比較**:
    `ss.Values` (ブロック内の命令リスト) を走査し、`OpPhi` 命令 (`v`) を見つけます。
    `if v.Op == OpPhi && v.Args[i0] != v.Args[i1]` の条件で、`s0` から来る値 (`v.Args[i0]`) と `s1` から来る値 (`v.Args[i1]`) が異なるかどうかをチェックします。
    もし異なっていれば、このPhi関数は異なるパスからの異なる値を処理しているため、`s0` と `s1` を削除して `b` から `ss` へ直接ジャンプするように変更すると、プログラムのセマンティクスが変化してしまいます。したがって、この場合はフュージョンを中止し、`false` を返します。

3.  **ブロック結合とエッジ更新**:
    Phi関数の引数がすべて同一である（またはPhi関数が存在しない）と判断された場合、フュージョンが安全であるとみなされます。
    *   `s0 != b && s1 != b` の場合（`s0` と `s1` の両方が実際に存在する空ブロックの場合）：
        `ss` から `s0` の先行エッジを削除します (`ss.removePred(s0)`)。
        `b` から `s1` へのエッジを `b` から `ss` へのエッジに置き換えます。これは、`b.Succs` と `ss.Preds` の両方を更新することで行われます。これにより、`b` から `ss` への直接的なパスが確立されます。
    *   `s0 != b` の場合（`s0` のみが空ブロックの場合）：
        `ss` から `s0` の先行エッジを削除します。
    *   `s1 != b` の場合（`s1` のみが空ブロックの場合）：
        `ss` から `s1` の先行エッジを削除します。

4.  **`b` ブロックの変換**:
    `b` ブロックの種類を `BlockPlain` に変更し、制御情報 (`b.Control`) を `nil` に設定します。
    `b` の後続ブロックを `ss` のみに設定します (`b.Succs = append(b.Succs[:0], ss)`)。これにより、`b` は単一の後続を持つ無条件ジャンプブロックになります。

5.  **空ブロックの無効化**:
    フュージョンによって不要になった `s0` および `s1` ブロックは、`BlockInvalid` に設定され、その値、後続、先行ブロックリストがクリアされます。これにより、これらのブロックはコンパイラの以降のパスで無視され、最終的に削除されます。

この一連の処理により、Phi関数がセマンティクスを維持できる場合に限り、条件分岐後の冗長な空ブロックが削除され、制御フローグラフが簡素化されます。

# [インデックス 24149] ファイルの概要

このコミットは、Go言語の標準ライブラリ `os/exec` パッケージにおける、子プロセスへの標準入力 (stdin) パイプへの書き込みエラー処理を改善するものです。具体的には、子プロセスが正常に完了した場合に発生する `EPIPE` (Broken pipe) エラーを無視するように変更し、不必要なエラー報告を抑制します。

## 変更の背景

この変更の背景には、`os/exec` パッケージを使用して外部コマンドを実行する際に発生する特定のシナリオでの不適切なエラー報告があります。

Unix系システムでは、プロセス間通信にパイプがよく利用されます。親プロセスが子プロセスの標準入力にデータを書き込み、子プロセスがそれを読み取るという構図です。しかし、子プロセスが標準入力からすべてのデータを読み取る前に終了してしまうことがあります。例えば、`head` コマンドのように、入力の一部だけを処理して終了するコマンドが典型的な例です。

このような場合、親プロセスがパイプへの書き込みを継続しようとすると、子プロセスがパイプの読み取り側を閉じているため、`EPIPE` (Broken pipe) エラーが発生します。このエラーは、通常、書き込み側が読み取り側を失ったことを示すもので、多くの場合、エラーとして適切に処理されるべきです。

しかし、子プロセスが**正常に**完了した場合、つまり、子プロセスが意図的に早期終了し、親プロセスが書き込もうとしていた残りのデータが不要であった場合、この `EPIPE` エラーは実質的に問題ではありません。親プロセスがこの `EPIPE` エラーを捕捉し、それを「真のエラー」として報告してしまうと、アプリケーションは実際には成功している操作に対して誤ったエラー状態を認識してしまいます。

このコミットは、この特定のケース（子プロセスが正常終了した場合の `EPIPE` エラー）を識別し、それを無視することで、`os/exec` パッケージの堅牢性と使いやすさを向上させることを目的としています。コミットメッセージにある `Fixes #9173` は、この問題がGoのIssueトラッカーで報告され、修正が必要とされていたことを示しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **`os/exec` パッケージ**: Go言語で外部コマンドを実行するための標準ライブラリパッケージです。`Cmd` 構造体を通じて、コマンドの実行、標準入出力のリダイレクト、環境変数の設定などを行います。
2.  **パイプ (Pipe)**: Unix系OSにおけるプロセス間通信 (IPC) の一種です。一方のプロセスがパイプに書き込み、もう一方のプロセスがパイプから読み取ります。データはFIFO (First-In, First-Out) 形式で流れます。
3.  **標準入力 (Stdin)**: プロセスがデータを受け取るための標準的な入力ストリームです。`os/exec` では、`Cmd.Stdin` フィールドを通じて子プロセスの標準入力を設定できます。
4.  **`io.Copy`**: Go言語の `io` パッケージにある関数で、`Reader` から `Writer` へデータをコピーします。このコミットでは、親プロセスの `Cmd.Stdin` (Reader) から子プロプロセスの標準入力パイプ (Writer) へデータをコピーするために使用されています。
5.  **`EPIPE` (Broken pipe) エラー**: Unix系システムで発生するエラーコードの一つで、`syscall.EPIPE` としてGoで表現されます。これは、パイプの書き込み側が、読み取り側が閉じられたパイプに書き込もうとしたときに発生します。シグナル `SIGPIPE` も同時に発生することがあります。
6.  **`*os.PathError`**: Go言語でファイルシステム操作中に発生するエラーを表す構造体です。`Op` (操作の種類、例: "write"), `Path` (操作対象のパス、例: "|1" はパイプのファイルディスクリプタを示すことが多い), `Err` (基となるシステムコールエラー) のフィールドを持ちます。
7.  **`syscall` パッケージ**: Go言語で低レベルのシステムコールにアクセスするためのパッケージです。`syscall.EPIPE` は、`EPIPE` エラーのシステムコール定数です。

## 技術的詳細

このコミットの技術的な核心は、`os/exec` パッケージ内で子プロセスの標準入力パイプへの書き込みを処理するゴルーチンに、特定の条件付きエラーハンドリングを追加することです。

`os/exec.Cmd` 構造体には、子プロセスの標準入力として `io.Reader` を設定できる `Stdin` フィールドがあります。`Cmd.Run()` や `Cmd.Start()` が呼び出されると、内部的に新しいゴルーチンが起動され、この `Cmd.Stdin` から子プロセスの標準入力パイプへデータを `io.Copy` を使ってコピーします。

問題は、子プロセスが `Cmd.Stdin` からのデータをすべて読み取る前に終了した場合に発生します。このとき、子プロセスは標準入力パイプの読み取り側を閉じます。親プロセス側の `io.Copy` が引き続きパイプに書き込もうとすると、`EPIPE` エラーが発生します。

このコミットでは、`io.Copy` が返したエラーが `EPIPE` エラーであるかどうかをチェックします。具体的には、以下の条件を検証します。

1.  エラーが `*os.PathError` 型であること。
2.  `PathError` の `Op` フィールドが "write" であること。これは書き込み操作中にエラーが発生したことを示します。
3.  `PathError` の `Path` フィールドが "|1"` であること。これは、標準入力パイプへの書き込みを示唆する慣例的な表現です（ファイルディスクリプタ1は通常標準出力ですが、内部的なパイプ処理では異なる意味を持つことがあります）。
4.  `PathError` の `Err` フィールドが `syscall.EPIPE` であること。これは、まさに「Broken pipe」エラーであることを示します。

これらの条件がすべて満たされた場合、かつ子プロセスが正常に完了している場合（このコミットのコードスニペットからは直接判断できませんが、コミットメッセージの意図からそう解釈されます）、`EPIPE` エラーは無視され、`err` 変数は `nil` に設定されます。これにより、`io.Copy` が `EPIPE` を返しても、`Cmd.Run()` などはエラーを報告せずに正常終了するようになります。

この変更は、子プロセスが意図的に早期終了するようなシナリオ（例: `head` コマンドが最初の数行だけを読み取って終了する場合）で、親プロセスが不必要なエラーを受け取らないようにするために重要です。

## コアとなるコードの解説

### `src/os/exec/exec.go` の変更

`(*Cmd).stdin()` メソッド内で、`io.Copy(pw, c.Stdin)` が実行された直後にエラーチェックが追加されています。

```go
		_, err := io.Copy(pw, c.Stdin)

		// Ignore EPIPE errors copying to stdin if the program
		// completed successfully otherwise.
		// See Issue 9173.
		if pe, ok := err.(*os.PathError); ok &&
			pe.Op == "write" && pe.Path == "|1" &&
			pe.Err == syscall.EPIPE {
			err = nil
		}
```

-   `_, err := io.Copy(pw, c.Stdin)`: `c.Stdin` からパイプの書き込み側 `pw` へデータをコピーします。ここで `EPIPE` エラーが発生する可能性があります。
-   `if pe, ok := err.(*os.PathError); ok && ...`: `io.Copy` が返したエラーが `*os.PathError` 型であり、かつその `Op` が "write"、`Path` が "|1"`、そして内部エラー `Err` が `syscall.EPIPE` である場合にのみ、以下の処理を実行します。
-   `err = nil`: 上記の条件がすべて満たされた場合、`err` 変数を `nil` に上書きします。これにより、この特定の `EPIPE` エラーは無視され、後続のエラー処理（`pw.Close()` のエラーとの結合など）に影響を与えなくなります。

この変更により、子プロセスが正常に終了し、かつ標準入力パイプを早期に閉じたために発生した `EPIPE` エラーは、`os/exec` パッケージの利用者には報告されなくなります。これは、このような状況が「正常な動作」と見なされるべきであるという設計思想に基づいています。

### `src/os/exec/exec_test.go` の追加テスト

`TestIgnorePipeErrorOnSuccess` テストケースは、この変更が意図通りに機能することを確認するために追加されました。

```go
func TestIgnorePipeErrorOnSuccess(t *testing.T) {
	testenv.MustHaveExec(t)

	// We really only care about testing this on Unixy things.
	if runtime.GOOS == "windows" || runtime.GOOS == "plan9" {
		t.Skipf("skipping test on %q", runtime.GOOS)
	}

	cmd := helperCommand(t, "echo", "foo")
	var out bytes.Buffer
	cmd.Stdin = strings.NewReader(strings.Repeat("x", 10<<20)) // 10MBの大量の入力
	cmd.Stdout = &out
	if err := cmd.Run(); err != nil { // エラーが発生しないことを期待
		t.Fatal(err)
	}
	if got, want := out.String(), "foo\\n"; got != want {
		t.Errorf("output = %q; want %q", got, want)
	}
}
```

-   `testenv.MustHaveExec(t)`: 外部コマンド実行が可能な環境であることを確認します。
-   `runtime.GOOS == "windows" || runtime.GOOS == "plan9"`: このテストはUnix系OSのパイプ動作に特化しているため、WindowsやPlan 9ではスキップされます。`EPIPE` はUnix系OS特有のエラーです。
-   `cmd := helperCommand(t, "echo", "foo")`: `echo foo` コマンドを実行する `Cmd` オブジェクトを作成します。`echo` コマンドは引数を標準出力に出力し、その後すぐに終了します。標準入力はほとんど読み込みません。
-   `cmd.Stdin = strings.NewReader(strings.Repeat("x", 10<<20))`: 子プロセスに10MBという大量のデータを標準入力として与えます。`echo` コマンドはこれらすべてを読み込むことなく終了するため、親プロセスがパイプに書き込みを続けると `EPIPE` エラーが発生する状況を作り出します。
-   `if err := cmd.Run(); err != nil`: `cmd.Run()` を実行し、エラーが返されないことを期待します。もしこのコミットの変更がなければ、`EPIPE` エラーがここで捕捉され、テストは失敗するでしょう。
-   `if got, want := out.String(), "foo\\n"; got != want`: `echo` コマンドの出力が期待通りであることを確認します。

このテストは、子プロセスが標準入力のすべてを消費する前に終了しても、親プロセスが `EPIPE` エラーで失敗しないことを効果的に検証しています。

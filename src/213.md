# [インデックス 213] ファイルの概要

このコミットは、Goコンパイラの初期バージョン（C言語で書かれていた時代）における重要なバグ修正です。具体的には、コンパイラがコード生成の際に使用する「Ullman値」の計算が、メソッド呼び出し（`CALLMETH`および`DOTMETH`）のケースで誤っていた問題を修正しています。この修正は、コンパイラのコード生成の正確性と効率性に直接影響を与えるものです。

## 変更の背景

このコミットは、Goコンパイラの初期開発段階で発見されたバグを修正するために行われました。Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現（IR）を操作し、様々な最適化を行います。その中で、式の評価に必要なレジスタ数を最小化するための「Ullman値」という概念が用いられます。

このバグは、特にメソッド呼び出し（`CALLMETH`や`DOTMETH`といったコンパイラ内部の操作）において、このUllman値の計算が誤っていたことに起因します。Ullman値の誤った計算は、コンパイラが生成するコードの効率性（レジスタの使用効率）だけでなく、場合によってはコードの正しさにも影響を及ぼす可能性があります。例えば、必要なレジスタ数を過小評価すると、レジスタ不足によるスピル（メモリへの退避）が増えたり、最悪の場合、コンパイルエラーや不正なコード生成につながる可能性がありました。

この修正は、Goコンパイラの安定性と信頼性を向上させるための、初期の重要なステップの一つと言えます。

## 前提知識の解説

### 1. コンパイラの基本構造とフェーズ

コンパイラは、ソースコードを機械語に変換するソフトウェアです。一般的に以下の主要なフェーズに分かれます。

*   **字句解析 (Lexical Analysis)**: ソースコードをトークン（単語のようなもの）のストリームに分解します。
*   **構文解析 (Syntax Analysis)**: トークンのストリームから抽象構文木 (AST) を構築し、プログラムの構造を表現します。
*   **意味解析 (Semantic Analysis)**: 型チェックや名前解決などを行い、プログラムの意味的な正しさを検証します。
*   **中間コード生成 (Intermediate Code Generation)**: ASTを、機械語に近いがまだ特定のアーキテクチャに依存しない中間表現 (IR) に変換します。
*   **最適化 (Optimization)**: 中間コードを分析し、より効率的なコードに変換します。
*   **コード生成 (Code Generation)**: 最適化された中間コードをターゲットアーキテクチャの機械語またはアセンブリコードに変換します。

このコミットで触れられているファイル (`cgen.c`, `gen.c`, `subr.c`, `walk.c`) は、Goコンパイラの初期バージョン（C言語で実装されていた頃）において、主に意味解析、中間コード生成、最適化、コード生成のフェーズに関わっていました。

### 2. Ullman値 (Sethi-Ullman Number)

Ullman値（またはSethi-Ullman数）は、コンパイラのコード生成において、式の評価に必要なレジスタ数を決定するために使用される概念です。これは、Ravi SethiとJeffrey D. Ullmanによって考案されたアルゴリズム（Sethi-Ullmanアルゴリズム）に基づいています。

抽象構文木 (AST) の各ノードに対してUllman値を計算することで、そのノードが表すサブツリーを評価するために最低限必要なレジスタの数がわかります。

*   **葉ノード (オペランド)**: 定数や変数など、それ自体がレジスタを必要としない（または1つのレジスタにロードできる）場合、Ullman値は通常1です。
*   **内部ノード (演算子)**: 子ノードのUllman値に基づいて計算されます。例えば、二項演算子の場合、左右の子ノードのUllman値が異なる場合は大きい方に1を加算し、同じ場合は大きい方に1を加算します。これは、一方の子を評価してレジスタに格納し、その後もう一方の子を評価するために追加のレジスタが必要になることを反映しています。

このUllman値を利用することで、コンパイラはレジスタ割り当てを最適化し、レジスタスピル（レジスタの内容をメモリに退避させること）を最小限に抑えることができます。

コミットメッセージにある `UINF` は、おそらく「無限大」を意味し、そのノードの評価には通常のレジスタ割り当てでは対応できない、または非常に多くのレジスタが必要となる（例えば、関数呼び出しのように、評価結果がレジスタに直接収まらない、あるいは副作用を伴う）ことを示唆していると考えられます。

### 3. `CALLMETH` と `DOTMETH`

これらはGoコンパイラの内部で使われる、メソッド呼び出しに関連する中間表現のノードまたは操作です。

*   **`DOTMETH`**: オブジェクトのメンバーにアクセスする「ドット演算子」(`.`) を介したメソッドの選択を表すと考えられます。例えば `obj.Method()` の `obj.Method` の部分です。コンパイラはまず、この操作によってどのメソッドが呼び出されるべきかを解決します。
*   **`CALLMETH`**: 実際にメソッドを呼び出す操作を表すと考えられます。`DOTMETH`で解決されたメソッドを、引数を渡して実行する段階です。

これらの内部表現は、Goのインターフェースやメソッドセットの複雑さを扱うためにコンパイラが使用するものです。

## 技術的詳細

このコミットの技術的詳細は、Ullman値の計算が`CALLMETH`および`DOTMETH`のケースで誤っていたという点に集約されます。

Goコンパイラのコード生成フェーズでは、式の評価順序やレジスタ割り当てを決定するために、各ノードのUllman値が計算されます。関数呼び出しやメソッド呼び出しのような操作は、通常、多くのレジスタを消費したり、レジスタ割り当てのルールが複雑になったりするため、特別な扱いが必要です。

コミットの差分を見ると、`src/cmd/gc/subr.c` の `ullmancalc` 関数に `OCALLMETH` と `OCALLINTER` (インターフェースメソッド呼び出し) が追加され、これらの操作のUllman値が `UINF` (無限大) に設定されています。これは、これらの操作がレジスタ割り当ての観点から特殊であり、通常の式評価とは異なる扱いが必要であることを示しています。`UINF`に設定することで、コンパイラはこれらの操作に対して、レジスタを大量に消費する可能性や、レジスタ割り当ての制約が強いことを認識し、適切なコード生成戦略（例えば、結果をメモリにスピルする、あるいは専用の呼び出し規約に従うなど）を選択できるようになります。

また、`src/cmd/6g/cgen.c` では、`ullman >= UINF` のチェックが追加され、ノードと結果の両方が関数呼び出しである場合に `fatal` エラーを発生させるようになっています。これは、Ullman値が無限大であるような複雑な操作が、さらに別の複雑な操作の結果として現れるような、コンパイラが扱いきれないケースを早期に検出するためのガードレールと考えられます。

`src/cmd/gc/walk.c` では、`OCALLMETH` の処理において、`ullmancalc(n->left)` が呼び出されています。これは、メソッド呼び出しのレシーバ（`n->left`）のUllman値を再計算することで、レシーバの評価に必要なレジスタ情報を正確に把握しようとしていることを示唆しています。

全体として、この修正は、メソッド呼び出しという複雑な操作におけるUllman値の計算を正確にし、それによってコンパイラがより堅牢で効率的なコードを生成できるようにするためのものです。

## コアとなるコードの変更箇所

このコミットでは、主に以下の4つのファイルが変更されています。

1.  **`src/cmd/6g/cgen.c`**:
    *   `ullman >= UINF` のチェックが強化され、ノードと結果の両方が関数呼び出しである場合に `fatal` エラーを発生させるようになりました。
    *   `lno = dynlineno;` と `dynlineno = n->lineno;` の行の順序が変更され、診断のための行番号の更新が `ullman` チェックの前に来るようになりました。
2.  **`src/cmd/6g/gen.c`**:
    *   `cgen_aret` 関数内の `fatal("cgen_aret");` というデバッグ用の行が削除されました。
    *   ポインタ型のチェックが `t->etype == TPTR32 || t->etype == TPTR64` から `isptr[t->etype]` に変更され、より汎用的なポインタ型判定になりました。
    *   `cgen_callret` 関数内の `fatal` メッセージが `cgen_aret: nil` から `cgen_callret: nil` に修正されました。
3.  **`src/cmd/gc/subr.c`**:
    *   `ullmancalc` 関数において、`OCALLMETH` と `OCALLINTER` のケースが追加され、これらの操作のUllman値が `UINF` に設定されるようになりました。
4.  **`src/cmd/gc/walk.c`**:
    *   `ONAME` や `OLITERAL` などのノードタイプに対する `ullmancalc(n)` の呼び出しが削除されました。これは、`ullmancalc` の呼び出しタイミングが変更されたことを示唆しています。
    *   `OCALLMETH` の処理において、レシーバ (`n->left->left`) のUllman値を再計算するために `ullmancalc(n->left)` が呼び出されるようになりました。
    *   `OCALLMETH` のコメントが削除され、`n->left->left = N;` が追加されました。

## コアとなるコードの解説

### `src/cmd/gc/subr.c` の `ullmancalc` 関数

```c
 // 変更前
 	case OI2S:
 	case OI2I:
 	case OCALL:
 	\tul = UINF;
 	\tgoto out;
 	}

 // 変更後
 	case OI2S:
 	case OI2I:
 	case OCALL:
+	case OCALLMETH:
+	case OCALLINTER:
 	\tul = UINF;
 	\tgoto out;
 	}
```
この変更がこのコミットの核心です。`ullmancalc` 関数は、ASTノードのUllman値を計算する役割を担っています。変更前は、通常の関数呼び出し (`OCALL`) のみが `UINF` (無限大) のUllman値を持つとされていました。しかし、メソッド呼び出し (`OCALLMETH`) やインターフェースメソッド呼び出し (`OCALLINTER`) もまた、レジスタ割り当ての観点から複雑な操作であり、通常の式評価とは異なる扱いが必要です。これらのケースも `UINF` に設定することで、コンパイラはこれらの操作がレジスタを大量に消費する可能性や、レジスタ割り当ての制約が強いことを認識し、適切なコード生成戦略を選択できるようになります。これにより、コンパイラはこれらの複雑な呼び出しに対してより堅牢なコードを生成できるようになります。

### `src/cmd/6g/cgen.c` の `cgen` 関数

```c
 // 変更前
 \tif(n->ullman >= UINF) {
 \t\tif(n->op == OINDREG)
 \t\t\tfatal("cgen: this is going to misscompile");
-\t\tif(res->ullman >= UINF)
-\t\t\tfatal("cgen: fun both sides");
+\t\tif(res->ullman >= UINF) {
+\t\t\tdump("fncalls", n);
+\t\t\tfatal("cgen: node and result functions");
+\t\t}
 \t}

 // 変更後
 \tif(n->ullman >= UINF) {
 \t\tif(n->op == OINDREG)
 \t\t\tfatal("cgen: this is going to misscompile");
+\t\tif(res->ullman >= UINF) {
+\t\t\tdump("fncalls", n);
+\t\t\tfatal("cgen: node and result functions");
+\t\t}
 \t}
```
この変更は、`ullman >= UINF` のチェックをより厳密にしています。特に、ノード (`n`) と結果 (`res`) の両方が `UINF` のUllman値を持つ場合（つまり、両方が関数呼び出しのような複雑な操作である場合）に `fatal` エラーを発生させるようになりました。これは、コンパイラが扱いきれないような非常に複雑なケースを早期に検出し、デバッグを容易にするためのガードレールです。`dump("fncalls", n)` の追加は、エラー発生時にデバッグ情報を出力するためのものです。

### `src/cmd/gc/walk.c` の `OCALLMETH` 処理

```c
 // 変更前
 \t\tcase OCALLMETH:
-\t\t\t// add this-pointer to the arg list
-\t\t\t// this is bad - if not a simple
-\t\t\t// should make a temp copy rather
-\t\t\t// than recalculate it.
 \t\t\tl = ascompatte(n->op, getinarg(t), &n->right, 0);
 \t\t\tr = ascompatte(n->op, getthis(t), &n->left->left, 0);
 \t\t\tif(l != N)
 \t\t\t\tr = nod(OLIST, r, l);
+\t\t\tn->left->left = N;
+\t\t\tullmancalc(n->left);
 \t\t\tn->right = reorder1(r);
 \t\t\tbreak;
 \t\t}

 // 変更後
 \t\tcase OCALLMETH:
 \t\t\tl = ascompatte(n->op, getinarg(t), &n->right, 0);
 \t\t\tr = ascompatte(n->op, getthis(t), &n->left->left, 0);
 \t\t\tif(l != N)
 \t\t\t\tr = nod(OLIST, r, l);
+\t\t\tn->left->left = N;
+\t\t\tullmancalc(n->left);
 \t\t\tn->right = reorder1(r);
 \t\t\tbreak;
 \t\t}
```
この変更では、`OCALLMETH` の処理において、レシーバ (`n->left->left`) のUllman値を再計算するために `ullmancalc(n->left)` が呼び出されるようになりました。これは、メソッド呼び出しのレシーバの評価に必要なレジスタ情報を正確に把握し、その後のコード生成に役立てるためのものです。また、`n->left->left = N;` の追加は、レシーバのノードをクリアすることで、重複した処理や誤った参照を防ぐためのクリーンアップと考えられます。

### `src/cmd/gc/walk.c` の `ullmancalc` 呼び出しの削除

```c
 // 変更前 (例: ONAME)
 \t\tif(top != Erv)
 \t\t\tgoto nottop;
 \t\tn->addable = 1;
-\t\tullmancalc(n);
 \t\tgoto ret;

 // 変更後 (例: ONAME)
 \t\tif(top != Erv)
 \t\t\tgoto nottop;
 \t\tn->addable = 1;
 \t\tgoto ret;
```
`walk.c` の複数の箇所で、`ullmancalc(n)` の直接的な呼び出しが削除されています。これは、Ullman値の計算が、`walk` フェーズの特定のノード処理の直後ではなく、より適切なタイミング（例えば、中間表現の構築後や、コード生成の直前など）で行われるように、コンパイラの内部ロジックが変更されたことを示唆しています。これにより、Ullman値の計算がより効率的かつ正確に行われるようになった可能性があります。

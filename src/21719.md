# [インデックス 21719] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）、リンカ（`cmd/ld`）、および共通リンキングライブラリ（`liblink`）における内部データ構造の重要なリファクタリングを目的としています。具体的には、`Prog`（プログラム命令）と`Addr`（アドレス）構造体に関連する型定義と名前定義を、アーキテクチャ固有の`arch`構造体から切り離し、よりポータブルで汎用的な定数（`TYPE_XXX`や`NAME_XXX`）に移行しています。これにより、コンパイラとリンカのコードベースの可搬性、一貫性、および保守性が向上します。

## 変更の背景

Goコンパイラとリンカは、様々なCPUアーキテクチャをサポートするために、アーキテクチャ固有のコードと共通のコードを組み合わせています。以前の設計では、`Prog`（プログラム命令）や`Addr`（アドレス）といったコンパイラとリンカの内部表現における型や名前の識別子が、`arch`（アーキテクチャ）構造体の中に定義されていました（例: `arch.D_BRANCH`, `arch.D_AUTO`）。

この設計は、アーキテクチャごとにこれらの識別子をカスタマイズできる柔軟性を提供する一方で、多くの識別子が実際にはアーキテクチャに依存しない汎用的な意味を持つため、冗長性や不必要な依存関係を生み出していました。例えば、分岐命令のタイプや自動変数、パラメータといった概念は、どのアーキテクチャでも共通して存在します。

このコミットの背景にあるのは、これらの汎用的な型や名前の定義をアーキテクチャ固有のコンテキストから切り離し、よりポータブルで共通の定数として扱うことで、コードベースの保守性を高め、将来的なアーキテクチャサポートの追加を容易にすることです。これにより、コンパイラとリンカのコアロジックがアーキテクチャの詳細からより独立し、コードの重複を減らし、全体的な設計を簡素化できます。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラとリンカの基本的な構造、特に中間表現（IR）とシンボル管理に関する知識が必要です。

1.  **Goコンパイラ (`cmd/gc`)**: Goソースコードをアセンブリコード（またはオブジェクトファイル）に変換する役割を担います。この過程で、GoのAST（抽象構文木）を`Prog`と呼ばれる低レベルの命令列に変換します。
2.  **Goリンカ (`cmd/ld`)**: コンパイラによって生成されたオブジェクトファイルやライブラリを結合し、実行可能なバイナリを生成します。リンカは、シンボル解決、再配置、および最終的なバイナリのレイアウトを担当します。
3.  **`liblink`**: `cmd/gc`と`cmd/ld`の両方で使用される共通のリンキングライブラリです。アセンブリコードの生成、オブジェクトファイルの読み書き、シンボル管理など、リンキングに関連する多くの低レベル機能を提供します。
4.  **`Prog`構造体**: Goコンパイラとリンカの内部で、単一のアセンブリ命令を表すために使用される構造体です。これには、命令の種類（オペコード）、ソースオペランド、デスティネーションオペランドなどが含まれます。
5.  **`Addr`構造体**: `Prog`構造体の一部として、命令のオペランド（例えば、レジスタ、メモリ位置、定数、シンボルなど）を表すために使用される構造体です。`Addr`は、そのオペランドの種類を示す`type`フィールドや、関連するシンボルを示す`sym`フィールドなどを含みます。
6.  **`arch`構造体**: 各CPUアーキテクチャ（例: amd64, arm）に固有の関数ポインタや定数を含む構造体です。これには、アーキテクチャ固有の命令セットの定義や、特定のオペランドタイプに関する情報が含まれることがあります。
7.  **`D_AUTO`, `D_BRANCH`, `D_NONE`, `D_PARAM`, `D_CONST`, `D_ADDR`など**: これらは、`Addr`構造体の`type`フィールドで使用される定数で、オペランドの種類を示します。
    *   `D_AUTO`: 自動変数（スタック上のローカル変数）
    *   `D_BRANCH`: 分岐命令のターゲットアドレス
    *   `D_NONE`: オペランドがないことを示す
    *   `D_PARAM`: 関数パラメータ
    *   `D_CONST`: 定数
    *   `D_ADDR`: アドレス（シンボルへの参照など）
    *   `D_FCONST`, `D_SCONST`: 浮動小数点定数、文字列定数

このコミットの変更は、これらの`D_XXX`定数が`arch`構造体から切り離され、より汎用的な`TYPE_XXX`や`NAME_XXX`といった定数に置き換えられることを意味します。

## 技術的詳細

このコミットの核心は、Goコンパイラとリンカの内部表現における型と名前の識別子を、アーキテクチャ固有の`arch`構造体から、より汎用的なグローバル定数に移行することです。

以前は、`Prog`や`Addr`構造体で使用されるオペランドの型やシンボルの種類を示す定数（例: `D_BRANCH`, `D_AUTO`）が、`ctxt->arch->D_BRANCH`のように`arch`構造体のメンバーとしてアクセスされていました。これは、これらの定数がアーキテクチャによって異なる可能性があるという仮定に基づいています。

しかし、実際には、これらの定数の多くはアーキテクチャに依存せず、Goのコンパイラとリンカのすべてのターゲットで共通の意味を持ちます。例えば、「分岐ターゲット」や「自動変数」といった概念は、CPUアーキテクチャに関わらず存在します。

このコミットでは、以下の主要な変更が行われています。

1.  **`arch`構造体からの`D_XXX`定数の削除**: `src/cmd/gc/go.h`から`D_AUTO`, `D_BRANCH`, `D_NONE`, `D_PARAM`といった定義が削除されています。これは、これらの定数がもはや`arch`構造体のメンバーではないことを意味します。
2.  **`TYPE_XXX`定数への移行**: `p->to.type == arch.D_BRANCH`のようなコードは、`p->to.type == TYPE_BRANCH`のように変更されています。これは、オペランドの型を示す定数が、`arch`構造体を介さずに直接`TYPE_`プレフィックスを持つグローバル定数として参照されるようになったことを示します。同様に、`D_FCONST`, `D_SCONST`, `D_CONST`, `D_ADDR`もそれぞれ`TYPE_FCONST`, `TYPE_SCONST`, `TYPE_CONST`, `TYPE_ADDR`に置き換えられています。
3.  **`NAME_XXX`定数への移行**: シンボルの種類を示す定数（例: `A_AUTO`, `A_PARAM`）は、`a->type`から`a->name`への変更と、`arch.D_AUTO`から`NAME_AUTO`への変更を伴っています。これは、シンボルの「名前」に関連する識別子が`NAME_`プレフィックスを持つグローバル定数として扱われるようになったことを示唆しています。
4.  **`addstacksplit`から`preprocess`への変更**: `src/liblink/objfile.c`で、`ctxt->arch->addstacksplit(ctxt, s)`が`ctxt->arch->preprocess(ctxt, s)`に置き換えられています。これは、スタックスプリット（Goランタイムがスタックを動的に拡張するメカニズム）の処理が、アーキテクチャ固有の`preprocess`フェーズの一部として統合されたことを示唆しています。これにより、リンカの処理フローがより汎用的になり、特定の最適化や処理がアーキテクチャ固有のフックを通じて行われるようになります。

これらの変更により、コンパイラとリンカのコードは、アーキテクチャに依存しない共通の概念を表現する際に、よりクリーンで一貫した方法を使用できるようになります。これにより、コードの可読性が向上し、新しいアーキテクチャのサポートや既存のアーキテクチャのメンテナンスが容易になります。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   **`src/cmd/gc/go.h`**: `arch`構造体から`D_AUTO`, `D_BRANCH`, `D_NONE`, `D_PARAM`の定義が削除されています。
*   **`src/cmd/gc/pgen.c`, `src/cmd/gc/plive.c`, `src/cmd/gc/popt.c`**: `arch.D_BRANCH`が`TYPE_BRANCH`に、`arch.D_NONE`が`TYPE_NONE`に、`arch.D_AUTO`が`NAME_AUTO`に、`arch.D_PARAM`が`NAME_PARAM`に置き換えられています。
*   **`src/cmd/ld/dwarf.c`, `src/cmd/ld/lib.c`**: `a->type`が`a->name`に、`A_AUTO`や`A_PARAM`のチェックが変更されています。
*   **`src/liblink/data.c`**: `arch.D_FCONST`, `arch.D_SCONST`, `arch.D_CONST`, `arch.D_ADDR`がそれぞれ`TYPE_FCONST`, `TYPE_SCONST`, `TYPE_CONST`, `TYPE_ADDR`に置き換えられています。
*   **`src/liblink/objfile.c`**: `p->from.type`の`arch.D_CONST`が`TYPE_CONST`に、`p->to.type`の`arch.D_D_EXTERN`が`TYPE_MEM`と`NAME_EXTERN`に置き換えられています。また、`ctxt->arch->addstacksplit`の呼び出しが`ctxt->arch->preprocess`に変更されています。
*   **`src/liblink/pass.c`**: `ctxt->arch->D_BRANCH`が`TYPE_BRANCH`に、`ctxt->arch->D_NONE`が`TYPE_NONE`に置き換えられています。
*   **`src/liblink/pcln.c`**: `ctxt->arch->D_CONST`が`TYPE_CONST`に置き換えられています。

これらの変更は、コンパイラとリンカのコードベース全体にわたって、`Prog`と`Addr`の型および名前の識別子が一貫して新しい汎用的な定数を使用するように更新されたことを示しています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`Prog`と`Addr`構造体におけるオペランドの型やシンボルの種類を識別するための定数の参照方法の変更です。

例えば、`src/cmd/gc/plive.c`の以下の行を見てみましょう。

変更前:
```c
if(p->to.type == arch.D_BRANCH) {
```
変更後:
```c
if(p->to.type == TYPE_BRANCH) {
```

これは、`p->to.type`が示すオペランドの型が「分岐ターゲット」であるかどうかをチェックするコードです。以前は、この`D_BRANCH`という定数が`arch`構造体（現在のアーキテクチャの定義）のメンバーとしてアクセスされていました。しかし、この変更により、`TYPE_BRANCH`というグローバルな定数として直接参照されるようになりました。

同様に、`src/cmd/gc/plive.c`の別の箇所では、自動変数やパラメータのチェックに関連して以下の変更が見られます。

変更前:
```c
if(p->from.type == arch.D_AUTO)
    checkauto(fn, p, p->from.node);
if(p->from.type == arch.D_PARAM)
    checkparam(fn, p, p->from.node);
```
変更後:
```c
if(p->from.name == NAME_AUTO)
    checkauto(fn, p, p->from.node);
if(p->from.name == NAME_PARAM)
    checkparam(fn, p, p->from.node);
```

ここでは、`p->from.type`が`p->from.name`に変わり、`arch.D_AUTO`が`NAME_AUTO`に、`arch.D_PARAM`が`NAME_PARAM`に置き換えられています。これは、オペランドが参照するシンボルの「種類」を識別するために、`type`フィールドではなく`name`フィールドを使用し、その値として`NAME_`プレフィックスを持つ定数を使用するようになったことを示しています。これにより、型と名前の概念がより明確に分離され、コードの意図がより分かりやすくなります。

これらの変更は、`TYPE_BRANCH`, `TYPE_CONST`, `NAME_AUTO`などの新しい定数が、Goコンパイラとリンカの共通ヘッダーファイル（おそらく`src/cmd/gc/go.h`や`src/liblink/link.h`のようなファイル）で定義されていることを前提としています。これにより、これらの定数はすべてのアーキテクチャで一貫して利用可能となり、アーキテクチャ固有のコードから独立して扱えるようになります。

全体として、このコミットはGoコンパイラとリンカの内部表現をよりモジュール化し、アーキテクチャに依存しない共通の概念をより適切に表現するための重要なステップです。

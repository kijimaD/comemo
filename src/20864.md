# [インデックス 20864] ファイルの概要

このコミットは、GoランタイムがPlan 9オペレーティングシステム上で環境変数を扱う際の挙動を修正するものです。具体的には、Plan 9の環境変数文字列が必ずしもNULL終端されていないという特性に対応し、Goランタイムがこれらの文字列を正しく読み取れるように変更が加えられました。これにより、Plan 9環境でのGoプログラムの安定性と互換性が向上します。

## 変更の背景

この変更の背景には、GoランタイムがPlan 9オペレーティングシステム上で環境変数を読み取る際の、文字列終端に関する誤った仮定がありました。

一般的なUnix系システムやWindowsでは、C言語の文字列と同様に、文字列の終端はヌル文字（`\0`、ASCIIコード0）で示される「NULL終端文字列」が広く用いられています。Go言語のランタイムも、内部的にC言語のライブラリやシステムコールと連携する際、このNULL終端の慣習を前提とすることが多くあります。

しかし、Plan 9オペレーティングシステムでは、環境変数を含む多くの文字列が必ずしもNULL終端されているわけではありません。Plan 9では、文字列の長さが別途管理されるか、あるいは特定のプロトコルやデータ構造によって文字列の範囲が定義されることが一般的です。

GoのコミッターであるRuss Cox氏が、Plan 9における環境変数文字列のこの特性を指摘しました。Goランタイムの`gogetenv`関数（環境変数を取得する内部関数）は、Plan 9の環境変数ファイルを読み取る際に、文字列がNULL終端されていると誤って仮定していました。この誤った仮定により、環境変数文字列の長さを計算する際に、本来の文字列の範囲を超えて読み取ってしまう可能性や、不正なメモリ領域にアクセスしてしまう可能性がありました。結果として、GoプログラムがPlan 9上で環境変数を正しく取得できない、あるいはクラッシュするなどの問題が発生する可能性がありました。

このコミットは、このPlan 9特有の文字列終端の慣習に対応し、Goランタイムが環境変数を安全かつ正確に読み取れるようにするために行われました。

## 前提知識の解説

### Plan 9 from Bell Labs

Plan 9 from Bell Labsは、ベル研究所で開発された分散オペレーティングシステムです。Unixの後継として設計され、Unixの概念をさらに推し進めたシステムとして知られています。主な特徴は以下の通りです。

*   **すべてがファイル**: Plan 9では、デバイス、プロセス、ネットワーク接続など、システム内のあらゆるリソースがファイルとして表現されます。これにより、統一されたインターフェースでシステムを操作できます。
*   **名前空間**: 各プロセスは独自の「名前空間」を持ち、ファイルシステムツリーを自由に構成できます。これにより、リソースの共有や分離が柔軟に行えます。
*   **UTF-8の採用**: 早期からUTF-8をシステム全体の文字エンコーディングとして採用していました。
*   **シンプルなプロトコル**: 複雑なAPIではなく、シンプルなファイルシステムプロトコル（9P）を通じてリソースにアクセスします。

Go言語の開発者の一部はPlan 9の開発にも携わっており、Go言語の設計思想にはPlan 9の影響が見られます。特に、Goの標準ライブラリにおけるI/Oの扱い方や、並行処理のモデル（goroutineとchannel）には、Plan 9の哲学が反映されていると言われています。

### 環境変数 (Environment Variables)

環境変数は、オペレーティングシステムがプロセスに提供する動的な名前付き値の集合です。プログラムの実行環境を設定するために使用されます。例えば、`PATH`環境変数は実行可能ファイルの検索パスを定義し、`HOME`環境変数はユーザーのホームディレクトリを示します。

プログラムは、これらの環境変数を読み取ることで、実行時に外部から設定された情報に基づいて動作を変更できます。Go言語では、`os.Getenv`関数などを使用して環境変数を取得します。

### NULL終端文字列 (Null-terminated strings)

NULL終端文字列は、文字列の終端をヌル文字（`\0`）で示す方式です。C言語で広く採用されており、文字列の長さを明示的に保持するのではなく、ヌル文字が見つかるまで文字を読み進めることで文字列の終端を判断します。

例: "hello\0"
この文字列は、メモリ上では 'h', 'e', 'l', 'l', 'o', '\0' の順に格納されます。文字列を処理する関数は、ヌル文字に到達した時点で文字列の終わりと判断します。

この方式の利点は、文字列の長さを別途管理する必要がないことですが、欠点としては、ヌル文字が文字列の途中に含まれるとそこで文字列が途切れてしまうことや、ヌル文字を書き忘れるとメモリの範囲外を読み込んでしまう（バッファオーバーリード）危険性があることです。

### Goランタイム (Go runtime)

Goランタイムは、Goプログラムの実行を管理するソフトウェア層です。これには、ガベージコレクタ、スケジューラ（goroutineの管理）、メモリ管理、システムコールインターフェースなどが含まれます。Goプログラムがオペレーティングシステムと対話する際、ランタイムがその仲介役となります。環境変数の取得のようなOS固有の操作も、ランタイムがOSのAPIを呼び出すことで実現されます。

## 技術的詳細

このコミットが修正する問題は、Goランタイムの`src/runtime/env_plan9.go`ファイル内の`gogetenv`関数に起因していました。この関数は、Plan 9の環境変数を読み取るために、`open`、`seek`、`read`といったシステムコールを使用していました。

従来のコードでは、環境変数のファイルサイズを取得する際に、`seek(fd, 0, 2) - 1`という計算を行っていました。ここで`seek(fd, 0, 2)`はファイルの終端にシークし、そのオフセット（つまりファイルサイズ）を返します。`- 1`という操作は、ファイルがNULL終端されていることを前提とし、最後のNULL文字を除外して有効な文字列長を得ようとする意図があったと考えられます。

しかし、Plan 9の環境変数文字列はNULL終端が必須ではないため、この`- 1`の操作は誤りでした。もし文字列がNULL終端されていない場合、この計算では文字列の実際の長さよりも1バイト短い長さが返され、結果として文字列の最後の文字が欠落するか、あるいは文字列の終端を正しく認識できない可能性がありました。

さらに、文字列をメモリに読み込んだ後、Goの文字列型に変換する際に、この誤った長さが使用されると、Goの文字列が不完全になったり、不正なデータを含んだりする可能性がありました。

このコミットは、以下の2つの主要な変更によってこの問題を解決しています。

1.  **ファイルサイズの正確な取得**: `seek(fd, 0, 2) - 1`を`seek(fd, 0, 2)`に変更することで、ファイルの実際のサイズを正確に取得するようにしました。これにより、文字列の長さ計算の初期段階での誤りを排除します。
2.  **NULL終端の有無の動的なチェック**: ファイルから読み込んだバイト列の末尾がNULL文字であるかどうかを明示的にチェックするロジックを追加しました。`if p[r-1] == 0 { r-- }`というコードは、読み込んだバイト列の最後の文字がNULL文字であれば、そのNULL文字を文字列の有効な部分から除外するために長さを1減らします。これにより、文字列がNULL終端されている場合でも、されていない場合でも、Goの文字列として正しく扱えるようになります。

この修正により、GoランタイムはPlan 9の環境変数文字列の特性に柔軟に対応できるようになり、文字列の終端がNULLであるかどうかにかかわらず、常に正しい環境変数値をGoプログラムに提供できるようになりました。

## コアとなるコードの解説

### 1. `n := seek(fd, 0, 2) - 1` から `n := seek(fd, 0, 2)` への変更

*   **変更前**: `n := seek(fd, 0, 2) - 1`
    *   `seek(fd, 0, 2)`は、ファイルディスクリプタ`fd`の読み書き位置をファイルの終端（オフセット0、基準2は`SEEK_END`に相当）に移動させ、その時点でのオフセット（つまりファイルサイズ）を返します。
    *   `- 1`という減算は、読み取るべき文字列の末尾にNULL文字が存在することを前提とし、そのNULL文字を文字列の有効な長さから除外しようとする意図がありました。
*   **変更後**: `n := seek(fd, 0, 2)`
    *   `- 1`が削除されました。これにより、`n`はファイルの実際のサイズを正確に表すようになります。Plan 9の環境変数文字列がNULL終端されていない場合でも、この`n`の値は文字列の真の長さを反映します。

### 2. 新たに追加されたNULL終端チェック

```go
	if p[r-1] == 0 {
		r--
	}
```

*   このコードブロックは、ファイルから読み込んだバイト列`p`の末尾（`r-1`インデックス）がNULL文字（`0`）であるかどうかをチェックします。
*   `r`は、`read(fd, &p[0], n)`システムコールによって実際に読み込まれたバイト数を示します。
*   **`p[r-1] == 0`**: これは、読み込んだデータ（`p`）の最後のバイトがNULL文字であるかを判定しています。
*   **`r--`**: もし最後のバイトがNULL文字であれば、それは文字列のデータの一部ではなく終端を示すマーカーであるため、有効な文字列長`r`を1減らします。これにより、Goの文字列として変換される際に、このNULL文字が文字列の内容に含まれないようにします。

この2つの変更を組み合わせることで、GoランタイムはPlan 9の環境変数文字列がNULL終端されているかどうかにかかわらず、常に正しい長さを認識し、正確な文字列をGoプログラムに提供できるようになります。これは、堅牢性と互換性を高めるための重要な修正です。

# [インデックス 26462] ファイルの概要

このコミットは、Goコンパイラのx86バックエンドにおける最適化の問題を修正し、`Prog`構造体の`Mark`フィールドの利用方法を改善するものです。具体的には、レジスタをゼロクリアする際に`MOV $0, AX`命令が`XOR AX, AX`命令に自動的に書き換えられる最適化が、フラグレジスタの状態を破壊してしまうケースを回避するための変更が加えられています。

## 元コミット内容

[dev.ssa] cmd/compile: disable xor clearing when flags must be preserved

The x86 backend automatically rewrites MOV $0, AX to
XOR AX, AX. That rewrite isn't ok when the flags register
is live across the MOV. Keep track of which moves care
about preserving flags, then disable this rewrite for them.

On x86, Prog.Mark was being used to hold the length of the
instruction. We already store that in Prog.Isize, so no
need to store it in Prog.Mark also. This frees up Prog.Mark
to hold a bitmask on x86 just like all the other architectures.

Update #12405

## 変更の背景

Goコンパイラのx86バックエンドでは、レジスタをゼロクリアする一般的な最適化として、`MOV $0, AX`（AXレジスタに0を移動）命令を`XOR AX, AX`（AXレジスタとAXレジスタの排他的論理和）命令に自動的に書き換える処理が行われていました。この`XOR`命令によるゼロクリアは、命令サイズが小さく、現代のCPUではマイクロアーキテクチャレベルで最適化されており、非常に高速に実行されるため、通常は推奨される最適化手法です。

しかし、この最適化には重要な副作用があります。`MOV`命令はフラグレジスタ（CPUの状態を示すフラグ群）に影響を与えないのに対し、`XOR AX, AX`命令はゼロフラグ（ZF）、サインフラグ（SF）、パリティフラグ（PF）、キャリーフラグ（CF）、オーバーフローフラグ（OF）など、多くのフラグを特定の状態に設定（特にZFを1に、CF/OF/SFを0に）してしまいます。

問題は、もし`MOV $0, AX`命令の直後に、その命令によって変更される前のフラグレジスタの状態に依存する命令（例えば条件分岐など）が存在する場合、`XOR AX, AX`への書き換えによってプログラムの動作が不正になる可能性がある点です。コンパイラは、このような状況でフラグレジスタが「ライブ」（後続の命令でその値が使用される可能性がある）であるかどうかを正確に把握し、不適切な最適化を避ける必要があります。

また、Goコンパイラの内部構造において、`obj.Prog`構造体の`Mark`フィールドがx86アーキテクチャでのみ命令の長さを格納するために使用されていました。しかし、命令の長さは既に`Prog.Isize`フィールドに格納されているため、これは冗長であり、`Mark`フィールドの汎用的な利用を妨げていました。他のアーキテクチャでは`Mark`フィールドはビットマスクとして利用されており、x86でも同様に汎用的なフラグ格納に利用できるようにする必要がありました。このコミットは、これらの問題を解決することを目的としています。

## 前提知識の解説

### x86アセンブリにおけるレジスタとフラグレジスタ

*   **汎用レジスタ (General-Purpose Registers)**: `AX`, `BX`, `CX`, `DX`などのレジスタは、データの一時的な格納や演算に使用されます。
*   **フラグレジスタ (FLAGS Register)**: CPUの現在の状態や、直前の算術・論理演算の結果に関する情報（フラグ）を格納する特殊なレジスタです。
    *   **ゼロフラグ (ZF)**: 演算結果が0の場合に1に設定されます。
    *   **サインフラグ (SF)**: 演算結果の最上位ビット（符号ビット）が1の場合に1に設定されます。
    *   **キャリーフラグ (CF)**: 算術演算で最上位ビットからの桁上がり（または桁借り）が発生した場合に1に設定されます。
    *   **オーバーフローフラグ (OF)**: 符号付き算術演算でオーバーフローが発生した場合に1に設定されます。
    *   これらのフラグは、条件分岐命令（例: `JZ` (Jump if Zero), `JC` (Jump if Carry)）などで利用され、プログラムの制御フローを決定します。

### MOV命令とXOR命令

*   **`MOV reg, 0`**: 指定されたレジスタに即値0を移動します。この命令は**フラグレジスタに影響を与えません**。
*   **`XOR reg, reg`**: 指定されたレジスタ自身との排他的論理和を取ります。任意の値を自身とXORすると結果は必ず0になるため、レジスタをゼロクリアする効果があります。この命令は**フラグレジスタに影響を与え**、特に以下のフラグを設定します。
    *   ZF = 1 (結果が0のため)
    *   CF = 0
    *   OF = 0
    *   SF = 0 (結果が0のため)
    *   PF = 1 (結果が0であり、セットされたビット数が偶数のため)
    現代のx86プロセッサでは、`XOR reg, reg`は「ゼロ化イディオム」として認識され、非常に効率的に実行されます。命令のバイト数が少なく、データ依存関係を解消する効果もあるため、パフォーマンス上の利点があります。

### GoコンパイラのSSA (Static Single Assignment) 形式

SSAは、コンパイラがプログラムを最適化するために使用する中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されることが保証されます。これにより、データフロー解析や最適化が容易になります。Goコンパイラは、ソースコードをSSA形式に変換し、様々な最適化パスを適用した後、最終的に機械語命令に変換します。

### `obj.Prog`構造体

`obj.Prog`は、Goコンパイラのバックエンドで使用される構造体で、アセンブラに渡される個々の機械語命令（またはその抽象表現）を表します。この構造体には、命令の種類（`As`）、オペランド（`From`, `To`）、レジスタ情報（`Reg`）など、命令に関する様々なメタデータが含まれます。

*   **`Prog.Isize`**: 命令のバイトサイズを格納します。
*   **`Prog.Mark`**: 本来はアーキテクチャ固有の汎用的なフラグやメタデータをビットマスクとして格納するために設計されています。

### ライブネス解析 (Liveness Analysis)

コンパイラのデータフロー解析の一種で、プログラムの特定のポイントにおいて、ある変数やレジスタの値が「ライブ」であるかどうかを判断します。値がライブであるとは、その値が将来のどこかの時点で読み取られる可能性があることを意味します。このコミットの文脈では、フラグレジスタがライブであるかどうかを判断することが重要になります。

## 技術的詳細

このコミットの技術的詳細は、主に以下の2つの側面から構成されます。

1.  **フラグレジスタのライブネスに基づく`MOV $0, AX`最適化の抑制**:
    *   GoコンパイラのSSAバックエンドは、`MOV $0, AX`のような定数0をレジスタに移動する命令を、より効率的な`XOR AX, AX`に書き換える最適化を行います。
    *   しかし、この最適化は、`MOV`命令の前後でフラグレジスタの状態が保持される必要がある場合に問題を引き起こします。
    *   このコミットでは、SSAのフラグアロケータ（`flagalloc`）が、ブロックの終端でフラグレジスタがライブであるかどうか（`FlagsLiveAtEnd`）を追跡するように拡張されます。
    *   新しい関数`markMoves`が導入され、ブロック内の`MOVconst`命令（`MOVWconst`, `MOVLconst`, `MOVQconst`など）を逆順に走査します。もしフラグレジスタがライブである場合、これらの`MOVconst`命令に特別なマーク（`v.Aux`に非nil値を設定）を付けます。
    *   コード生成フェーズ（`genValue`）において、このマークが設定された`MOVconst`命令に対して、`Prog.Mark`フィールドに新しいフラグ`x86.PRESERVEFLAGS`を設定します。
    *   アセンブラのコード生成ロジック（`oclass`関数）は、`PRESERVEFLAGS`が設定されている`Prog`命令に対しては、`MOV $0, AX`を`XOR AX, AX`に書き換える最適化を行わないように変更されます。これにより、フラグレジスタの意図しない変更が防止されます。

2.  **`Prog.Mark`フィールドの汎用的なビットマスクとしての利用**:
    *   以前のx86バックエンドでは、`obj.Prog`構造体の`Mark`フィールドが命令のバイト長を格納するために誤って使用されていました。しかし、命令のバイト長は既に`Prog.Isize`フィールドに格納されており、これは冗長でした。
    *   このコミットにより、`Prog.Mark`フィールドはx86アーキテクチャでも他のアーキテクチャと同様に、汎用的なビットマスクとして利用できるようになります。
    *   `src/cmd/internal/obj/x86/a.out.go`で`PRESERVEFLAGS`という新しいビットマスク定数が定義され、`Prog.Mark`を通じて命令に付加的な情報を伝えるために使用されます。
    *   `src/cmd/internal/obj/x86/asm6.go`の`span6`関数など、以前`p.Mark`を命令長として扱っていた箇所は、`p.Isize`を使用するように修正されます。
    *   `src/cmd/internal/obj/x86/obj6.go`では、`p.Mark`の利用箇所がビットマスク操作（`p.Mark |= DONE`, `p.Mark & DONE == 0`など）に更新され、`DONE`フラグ（命令が処理済みであることを示す）と共存できるようになります。

これらの変更により、Goコンパイラはx86アーキテクチャにおいて、フラグレジスタのライブネスを考慮したより安全で正確なコード生成を行うことができるようになります。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラがx86アーキテクチャで`MOV $0, AX`を`XOR AX, AX`に最適化する際に、フラグレジスタのライブネスを考慮に入れるようにした点と、`Prog.Mark`フィールドの役割を明確化した点にあります。

1.  **`src/cmd/compile/internal/gc/ssa.go`における`markMoves`と`PRESERVEFLAGS`の設定**:
    ```go
    // markMoves marks any MOVXconst ops that need to avoid clobbering flags.
    func (s *genState) markMoves(b *ssa.Block) {
    	flive := b.FlagsLiveAtEnd // ブロックの終端でフラグがライブか
    	if b.Control != nil && b.Control.Type.IsFlags() {
    		flive = true // 制御フローがフラグに依存する場合もライブとみなす
    	}
    	for i := len(b.Values) - 1; i >= 0; i-- { // ブロック内の命令を逆順に走査
    		v := b.Values[i]
    		// フラグがライブであり、かつMOVconst命令の場合
    		if flive && (v.Op == ssa.OpAMD64MOVWconst || v.Op == ssa.OpAMD64MOVLconst || v.Op == ssa.OpAMD64MOVQconst) {
    			// The "mark" is any non-nil Aux value.
    			v.Aux = v // v.Auxに非nil値を設定してマーク
    		}
    		if v.Type.IsFlags() {
    			flive = false // フラグを生成する命令の場合、それ以前のフラグは非ライブになる
    		}
    		for _, a := range v.Args {
    			if a.Type.IsFlags() {
    				flive = true // フラグを引数として使用する命令の場合、フラグはライブになる
    			}
    		}
    	}
    }
    ```
    この`markMoves`関数は、SSAブロックを逆順に走査し、フラグレジスタがライブである期間中に発生する`MOVconst`命令を特定します。これらの命令には`v.Aux = v`という形でマークが付けられます。
    その後、`genValue`関数内で、このマーク（`v.Aux != nil`）が検出された場合、生成される`obj.Prog`命令の`Mark`フィールドに`x86.PRESERVEFLAGS`ビットを設定します。

2.  **`src/cmd/internal/obj/x86/asm6.go`における`oclass`関数での最適化抑制**:
    ```go
    // ...
    	if v == 0 {
    		if p.Mark&PRESERVEFLAGS != 0 {
    			// If PRESERVEFLAGS is set, avoid MOV $0, AX turning into XOR AX, AX.
    			return Yu7 // Yu7はMOV命令の特定の形式を示す
    		}
    		return Yi0 // Yi0はXOR命令の特定の形式を示す
    	}
    // ...
    ```
    `oclass`関数は、アセンブラが命令のオペランドのタイプを分類し、適切な機械語命令の形式を選択する際に使用されます。ここで、定数`v`が0である場合、通常は`XOR AX, AX`に相当する`Yi0`を返して最適化を行います。しかし、`p.Mark`に`PRESERVEFLAGS`ビットが設定されている場合は、この最適化を避け、`MOV $0, AX`に相当する`Yu7`を返すように変更されました。これにより、フラグレジスタの意図しない変更が防止されます。

3.  **`Prog.Mark`の役割変更**:
    *   `src/cmd/internal/obj/link.go`では、`Prog`構造体の`Mark`フィールドのコメントが「bitmask of arch-specific items」に変更され、その汎用的な役割が明示されました。
    *   `src/cmd/internal/obj/x86/a.out.go`で`PRESERVEFLAGS`が定義されたことで、`Mark`フィールドが複数のフラグをビットマスクとして保持できるようになったことが示されます。
    *   `src/cmd/internal/obj/x86/obj6.go`では、`p.Mark`の参照が`p.Mark |= DONE`や`p.Mark & DONE == 0`といったビット演算に置き換えられ、`Mark`が単一の値ではなく複数の状態を表現するビットマスクとして扱われるようになったことが明確に示されています。

これらの変更により、Goコンパイラはより洗練されたコード生成ロジックを獲得し、特定の状況下での潜在的なバグを回避できるようになりました。

## 変更の背景

このコミットは、`src/go/types.bash` というスクリプトが「もはや不要」になったため削除するものです。このスクリプトは、`golang.org/x/tools` リポジトリにある `go/exact`、`go/types`、`go/gcimporter` といったパッケージを、Go標準ライブラリの `src/go` ディレクトリ配下にベンダー（コピー）するために使用されていました。

Go言語の初期のパッケージ管理は、`GOPATH` に依存しており、外部パッケージの依存関係を管理する公式な仕組みがありませんでした。そのため、プロジェクトによっては依存パッケージのソースコードを自身のレポジトリ内にコピーする「ベンダー化」という手法が用いられることがありました。特に、Go標準ライブラリ自体が `x/tools` の一部のパッケージを内部的に利用する場合、そのパッケージの特定のバージョンを標準ライブラリ内に取り込むためにこのようなスクリプトが使われていたと考えられます。

しかし、コミットメッセージにある「not useful anymore」という記述と、`NOTE(adonovan)` のコメント「the standard packages have intentionally diverged from x/tools, so this script is a unlikely to be useful. Upstream changes should be cherry-picked in to the standard library.」から、以下の背景が推測されます。

1.  **パッケージの分離と独立**: `go/exact` や `go/types` といったパッケージが、`x/tools` のバージョンとGo標準ライブラリのバージョンで意図的に乖離するようになった。これは、標準ライブラリの安定性と `x/tools` の実験的な性質とのバランスを取るためと考えられます。
2.  **手動での管理への移行**: 自動ベンダー化スクリプトではなく、必要に応じて `x/tools` からの変更を手動で選択的に取り込む（cherry-pick）運用に切り替わったことを示唆しています。これにより、標準ライブラリのコードベースに対するより厳密な管理が可能になります。
3.  **パッケージ管理の進化**: 2015年という時期は、Goコミュニティが公式なパッケージ管理ソリューション（後のGo Modules）を模索し始める過渡期にあたります。このスクリプトの削除は、より洗練された依存関係管理への移行の一環、あるいはその前段階として、一時的なベンダー化スクリプトの役割が終了したことを示している可能性があります。

要するに、このスクリプトは特定の時期におけるGo標準ライブラリと `x/tools` パッケージ間の依存関係を管理するための一時的な手段であり、その役割を終えたため削除された、ということです。

## 前提知識の解説

### Go言語のパッケージと依存関係管理

Go言語では、コードは「パッケージ」という単位で整理されます。関連する機能は同じパッケージにまとめられ、他のパッケージからインポートして利用します。

*   **GOPATH**: Go 1.11以前のGo言語における主要なワークスペースおよび依存関係管理の仕組みでした。すべてのGoプロジェクトは `GOPATH` 環境変数で指定されたディレクトリ内に配置され、依存パッケージも `GOPATH/src` 以下にダウンロードされていました。この仕組みでは、異なるプロジェクトで同じパッケージの異なるバージョンを管理することが困難でした。
*   **ベンダー化 (Vendoring)**: `GOPATH` の制約を回避し、プロジェクト固有の依存関係を管理するためにコミュニティで生まれた手法の一つです。依存する外部パッケージのソースコードを、自身のプロジェクト内の `vendor/` ディレクトリにコピーして管理します。これにより、プロジェクトは外部の変更に影響されにくくなり、ビルドの再現性が向上します。このコミットで削除されたスクリプトは、Go標準ライブラリが `x/tools` のパッケージをベンダー化するために使われていたものです。
*   **Go Modules**: Go 1.11で導入され、Go 1.13でデフォルトとなった公式の依存関係管理システムです。`go.mod` ファイルと `go.sum` ファイルを使用して、プロジェクトの依存関係とそのバージョンを明確に定義します。Go Modulesの登場により、ベンダー化は依然としてオプションとして利用可能ですが、多くのプロジェクトでは `go.mod` を介した依存管理が主流となりました。

### `golang.org/x/tools`

`golang.org/x/tools` は、Go言語の公式ツール群（例: `go vet`, `gofmt`, `gorename` など）や、Go言語のコードを解析・操作するためのライブラリ（例: `go/ast`, `go/parser`, `go/types` など）を含むリポジトリです。これらのツールやライブラリは、Goコンパイラやランタイムとは別に開発・リリースされることが多く、Go言語の進化に合わせて頻繁に更新されます。

### `go/exact`, `go/types`, `go/gcimporter` パッケージ

これらは `golang.org/x/tools` に含まれる、Go言語の型システムやコンパイラ関連の機能を提供する重要なパッケージです。

*   **`go/types`**: Go言語の型システムを表現し、型チェックを行うためのライブラリです。GoコンパイラやIDE、リンターなどのツールがGoのコードを静的に解析する際に利用されます。
*   **`go/exact`**: Go言語の定数式（例: `1 + 2` や `true && false`）の値を正確に表現・計算するためのライブラリです。型チェックの過程で定数式の評価が必要な場合に使用されます。
*   **`go/gcimporter`**: Goコンパイラ（`gc`）が生成するオブジェクトファイルから型情報をインポートするためのライブラリです。これにより、異なるパッケージ間で型情報を共有し、型チェックを正確に行うことができます。

これらのパッケージは、Go言語のセマンティックな解析を行う上で不可欠であり、Goコンパイラ自体や、`gopls` のような言語サーバー、あるいは静的解析ツールなど、多くのGoツールで利用されています。Go標準ライブラリがこれらのパッケージを内部的に利用していたのは、コンパイラや関連ツールがGoの型システムを理解し、処理するために必要だったからです。

## 技術的詳細

削除された `src/go/types.bash` スクリプトは、`vendor()`、`install()`、`test()` の3つのシェル関数を定義していました。

*   **`vendor()` 関数**:
    *   `$GOPATH/src/golang.org/x/tools/$1` (ソースディレクトリ) から `$GODIR/$2` (ターゲットディレクトリ、例: `$GOROOT/src/go/exact`) へファイルをコピーします。
    *   特に重要なのは `sed` コマンドによるインポートパスの書き換えです。
        *   `"golang.org/x/tools/go/exact"` を `"go/exact"` に
        *   `"golang.org/x/tools/go/types"` を `"go/types"` に
        *   `"golang.org/x/tools/go/gcimporter"` を `"go/internal/gcimporter"` に
        *   それぞれ変更していました。これは、`x/tools` リポジトリ内のパッケージが標準ライブラリ内にコピーされた際に、内部的なインポートパスが正しく解決されるようにするためです。
    *   `testdata` ディレクトリも存在すればコピーしていました。
*   **`install()` 関数**: 指定されたパッケージを `go install` コマンドでビルド・インストールします。
*   **`test()` 関数**: 指定されたパッケージを `go test` コマンドでテストします。

スクリプトの実行順序は以下の通りでした。

1.  `go/exact` をベンダー化、テスト、インストール。
2.  `go/types` をベンダー化、インストール（`gcimporter` が必要なのでテストは後回し）。
3.  `go/gcimporter` をベンダー化、テスト、インストール。
4.  `go/types` をテスト（`gcimporter` が利用可能になったため）。

このスクリプトの削除は、Go標準ライブラリが `x/tools` のこれらのパッケージを直接ベンダー化するのではなく、別の方法で依存関係を管理するようになったことを意味します。前述の通り、これはパッケージの独立性の向上や、手動でのcherry-pickによる変更管理への移行を示唆しています。

この変更により、Go標準ライブラリのビルドプロセスから、`x/tools` の特定のバージョンに依存する自動ベンダー化ステップがなくなりました。これは、Go標準ライブラリのコードベースがより自己完結的になり、外部リポジトリの変更に直接的に影響されにくくなったことを意味します。

`golang.org/x/tools` は、Go言語の公式ツール群（例: `go vet`, `gofmt`, `gorename` など）や、Go言語のコードを解析・操作するためのライブラリ（例: `go/ast`, `go/parser`, `go/types` など）を含むリポジトリです。これらのツールやライブラリは、Goコンパイラやランタイムとは別に開発・リリースされることが多く、Go言語の進化に合わせて頻繁に更新されます。

### `go/exact`, `go/types`, `go/gcimporter` パッケージ

これらは `golang.org/x/tools` に含まれる、Go言語の型システムやコンパイラ関連の機能を提供する重要なパッケージです。

*   **`go/types`**: Go言語の型システムを表現し、型チェックを行うためのライブラリです。GoコンパイラやIDE、リンターなどのツールがGoのコードを静的に解析する際に利用されます。
*   **`go/exact`**: Go言語の定数式（例: `1 + 2` や `true && false`）の値を正確に表現・計算するためのライブラリです。型チェックの過程で定数式の評価が必要な場合に使用されます。
*   **`go/gcimporter`**: Goコンパイラ（`gc`）が生成するオブジェクトファイルから型情報をインポートするためのライブラリです。これにより、異なるパッケージ間で型情報を共有し、型チェックを正確に行うことができます。

これらのパッケージは、Go言語のセマンティックな解析を行う上で不可欠であり、Goコンパイラ自体や、`gopls` のような言語サーバー、あるいは静的解析ツールなど、多くのGoツールで利用されています。Go標準ライブラリがこれらのパッケージを内部的に利用していたのは、コンパイラや関連ツールがGoの型システムを理解し、処理するために必要だったからです。

## 技術的詳細

削除された `src/go/types.bash` スクリプトは、`vendor()`、`install()`、`test()` の3つのシェル関数を定義していました。

*   **`vendor()` 関数**:
    *   `$GOPATH/src/golang.org/x/tools/$1` (ソースディレクトリ) から `$GODIR/$2` (ターゲットディレクトリ、例: `$GOROOT/src/go/exact`) へファイルをコピーします。
    *   特に重要なのは `sed` コマンドによるインポートパスの書き換えです。
        *   `"golang.org/x/tools/go/exact"` を `"go/exact"` に
        *   `"golang.org/x/tools/go/types"` を `"go/types"` に
        *   `"golang.org/x/tools/go/gcimporter"` を `"go/internal/gcimporter"` に
        *   それぞれ変更していました。これは、`x/tools` リポジトリ内のパッケージが標準ライブラリ内にコピーされた際に、内部的なインポートパスが正しく解決されるようにするためです。
    *   `testdata` ディレクトリも存在すればコピーしていました。
*   **`install()` 関数**: 指定されたパッケージを `go install` コマンドでビルド・インストールします。
*   **`test()` 関数**: 指定されたパッケージを `go test` コマンドでテストします。

スクリプトの実行順序は以下の通りでした。

1.  `go/exact` をベンダー化、テスト、インストール。
2.  `go/types` をベンダー化、インストール（`gcimporter` が必要なのでテストは後回し）。
3.  `go/gcimporter` をベンダー化、テスト、インストール。
4.  `go/types` をテスト（`gcimporter` が利用可能になったため）。

このスクリプトの削除は、Go標準ライブラリがこれらのパッケージを直接ベンダー化するのではなく、別の方法で依存関係を管理するようになったことを意味します。前述の通り、これはパッケージの独立性の向上や、手動でのcherry-pickによる変更管理への移行を示唆しています。

この変更により、Go標準ライブラリのビルドプロセスから、`x/tools` の特定のバージョンに依存する自動ベンダー化ステップがなくなりました。これは、Go標準ライブラリのコードベースがより自己完結的になり、外部リポジトリの変更に直接的に影響されにくくなったことを意味します。

## コアとなるコードの解説

このコミットは、`src/go/types.bash` ファイル全体を削除するものです。したがって、コアとなるコードの変更は、このスクリプトが提供していた機能がGo標準ライブラリのビルドプロセスから完全に除去されたこと自体にあります。

具体的には、以下の機能が削除されました。

1.  **`golang.org/x/tools` からのパッケージの自動ベンダー化**:
    *   `go/exact` パッケージが `$GOROOT/src/go/exact` へ。
    *   `go/types` パッケージが `$GOROOT/src/go/types` へ。
    *   `go/gcimporter` パッケージが `$GOROOT/src/go/internal/gcimporter` へ。
    これらのパッケージが `x/tools` から自動的にコピーされ、インポートパスが修正されるプロセスがなくなりました。
2.  **ベンダー化されたパッケージの自動テストとインストール**:
    *   ベンダー化された `go/exact`、`go/gcimporter`、`go/types` パッケージに対する `go test` および `go install` の自動実行がなくなりました。

この削除は、Go標準ライブラリがこれらのパッケージを `x/tools` から直接ベンダー化する必要がなくなったことを明確に示しています。これは、これらのパッケージがGo標準ライブラリの一部として完全に統合されたか、あるいは `x/tools` との依存関係の管理方法が変更され、手動での同期や、より洗練されたビルドシステムによって管理されるようになったことを意味します。

特に、スクリプト内の `NOTE(adonovan)` のコメントが示唆するように、標準パッケージと `x/tools` の間で意図的な乖離が生じたため、自動ベンダー化スクリプトはもはや適切ではなくなり、必要に応じて変更をcherry-pickする運用に切り替わったと考えられます。これにより、Go標準ライブラリの安定性と独立性がさらに強化されたと言えるでしょう。

# [インデックス 21465] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/ld`) において、2バイトのリロケーション（再配置）をサポートするための変更を導入しています。特に、PowerPC 64ビット (ppc64) アーキテクチャがこのような2バイトのリロケーションを多用するため、そのサポートが不可欠でした。これにより、リンカがより広範なアーキテクチャとリロケーションタイプに対応できるようになり、Goプログラムのクロスコンパイル能力と実行時の正確性が向上します。

## 変更の背景

Go言語のリンカ (`cmd/ld`) は、コンパイルされたオブジェクトファイルを結合して実行可能ファイルを生成する役割を担っています。このプロセスにおいて、プログラム内のシンボル（関数や変数など）のアドレスは、最終的な実行可能ファイル内の実際のアドレスに「再配置」される必要があります。この再配置の処理を「リロケーション」と呼びます。

従来、Goリンカは主に4バイトのリロケーションをサポートしていましたが、特定のアーキテクチャ、特にPowerPC 64ビット (ppc64) では、2バイトのリロケーションが頻繁に使用されます。例えば、特定の命令が2バイトのオフセットしか扱えない場合などです。2バイトのリロケーションがサポートされていないと、ppc64アーキテクチャ向けのGoプログラムを正しくリンクできず、実行可能ファイルを生成することができませんでした。

このコミットは、ppc64のようなアーキテクチャでGo言語が適切に動作するために、リンカが2バイトのリロケーションを正確に処理できるようにするためのものです。これにより、Go言語のクロスプラットフォーム対応能力が向上し、より多くの環境でGoプログラムが利用可能になります。

## 前提知識の解説

### Goリンカ (cmd/ld)

`cmd/ld` はGo言語のツールチェインの一部であり、Goコンパイラによって生成されたオブジェクトファイル（`.o` ファイル）を結合し、最終的な実行可能ファイルや共有ライブラリを生成するリンカです。リンカの主な役割は以下の通りです。

1.  **シンボル解決**: 異なるオブジェクトファイルに分散している関数や変数の定義と参照を解決し、それらを一意のアドレスにマッピングします。
2.  **リロケーションの適用**: コンパイル時には不明だった最終的なメモリアドレスを、実行可能ファイル内の実際のオフセットに置き換える処理（リロケーション）を行います。
3.  **セクションの結合**: コード、データ、読み取り専用データなどの異なるセクションを結合し、実行可能ファイルの構造を構築します。
4.  **実行可能ファイルの生成**: OSがロードして実行できる形式（ELF, Mach-O, PEなど）で最終的なファイルを出力します。

### リロケーション (Relocation)

リロケーションとは、コンパイル時にアドレスが確定できないシンボル（関数呼び出しのターゲットアドレス、グローバル変数のアドレスなど）について、リンカが最終的な実行可能ファイル内で正しいアドレスに修正するプロセスです。

-   **なぜ必要か**: コンパイラは通常、各ソースファイル（またはオブジェクトファイル）を独立してコンパイルします。この段階では、他のファイルで定義されている関数や変数の最終的なメモリアドレスは分かりません。また、プログラムがメモリ上のどこにロードされるかも実行時まで確定しません。リロケーションは、これらの「未解決の参照」を、リンカがすべてのオブジェクトファイルを結合した後に確定する実際のアドレスに置き換えるために必要です。
-   **リロケーションエントリ**: オブジェクトファイルには、リロケーションが必要な箇所とその方法を示す「リロケーションエントリ」が含まれています。各エントリは、修正すべき場所（オフセット）、修正の種類（リロケーションタイプ）、参照するシンボル、そして追加のオフセット（加算値、addend）などを含みます。
-   **リロケーションタイプ**: リロケーションには様々なタイプがあります。
    -   **R_ADDR**: シンボルの絶対アドレスを直接埋め込む。
    -   **R_PCREL**: プログラムカウンタ（PC）からの相対アドレスを埋め込む。これは位置独立コード (PIC) の生成に重要です。
    -   **R_CALL**: 関数呼び出し命令のターゲットアドレスを修正する。
    -   **R_SIZE**: シンボルのサイズを埋め込む。
    -   **バイトサイズ**: リロケーションが適用されるデータのサイズ（1バイト、2バイト、4バイト、8バイトなど）も重要な要素です。これは、命令セットアーキテクチャ（ISA）によって、命令が参照できるオフセットのサイズが異なるためです。

### ppc64アーキテクチャ

PowerPC 64ビット (ppc64) は、IBMによって開発されたRISC（Reduced Instruction Set Computer）アーキテクチャです。特徴としては以下のような点が挙げられます。

-   **命令セット**: 固定長の命令（通常4バイト）を持ち、ロード/ストアアーキテクチャです。
-   **リロケーションの特性**: ppc64アーキテクチャの命令セットには、特定の命令が2バイトのオフセットしか扱えない場合があります。例えば、分岐命令やロード/ストア命令の一部は、ターゲットアドレスへのオフセットを16ビット（2バイト）で表現することがあります。そのため、リンカはこれらの2バイトオフセットを正確に計算し、埋め込む必要があります。
-   **エンディアンネス**: ppc64は通常ビッグエンディアンですが、リトルエンディアンモードでも動作可能です。リンカは、リロケーションを適用する際に、ターゲットアーキテクチャのエンディアンネスを考慮してバイト順を正しく配置する必要があります。

### バイトサイズのリロケーション

リロケーションが適用されるデータのサイズは、命令セットアーキテクチャの制約によって決まります。

-   **1バイトリロケーション**: 非常に小さなオフセットやフラグなどを埋め込む場合に使用されます。
-   **2バイトリロケーション**: ppc64のように、命令が16ビットのオフセットを必要とする場合に使用されます。このコミットの主要な焦点です。
-   **4バイトリロケーション**: 32ビットシステムや、64ビットシステムで32ビットのオフセットを扱う場合によく使用されます。Goリンカが元々主にサポートしていたサイズです。
-   **8バイトリロケーション**: 64ビットシステムで64ビットの絶対アドレスやオフセットを扱う場合に使用されます。

リンカは、リロケーションエントリに指定されたサイズに基づいて、対象のメモリ領域を正確に修正する必要があります。サイズが合わない場合、データが破損したり、プログラムが正しく動作しなくなったりします。

### エンディアンネス (Endianness)

エンディアンネスとは、複数バイトのデータをメモリに格納する際のバイト順序の規則です。

-   **ビッグエンディアン**: 最上位バイト（最も大きな値を持つバイト）が最も小さいアドレスに格納されます。人間が数字を読む順序に似ています（例: `0x12345678` は `12 34 56 78` の順で格納）。
-   **リトルエンディアン**: 最下位バイト（最も小さな値を持つバイト）が最も小さいアドレスに格納されます。Intel x86/x64アーキテクチャで一般的です（例: `0x12345678` は `78 56 34 12` の順で格納）。

リンカは、リロケーションを適用する際に、ターゲットアーキテクチャのエンディアンネスを考慮して、バイトデータを正しく配置する必要があります。`inuxi2` のような配列は、このバイト順序の変換を助けるために使用されます。

## 技術的詳細

このコミットは、Goリンカの2つの主要なファイル、`src/cmd/ld/data.c` と `src/cmd/ld/ldelf.c` に変更を加えています。

### `src/cmd/ld/data.c` の変更点

`data.c` は、シンボルのデータセクションにリロケーションを適用するロジックを含んでいます。特に `relocsym` 関数が修正されています。

-   **`relocsym` 関数**: この関数は、与えられたシンボル `s` のリロケーションエントリを処理し、シンボルのデータ `s->p` に適切な値を書き込みます。
-   **2バイトリロケーションの追加**: 以前は1バイト、4バイト、8バイトなどのリロケーションサイズに対応していましたが、このコミットで `case 2:` が追加されました。
    -   `if(o != (int16)o)`: リロケーションによって計算されたオフセット値 `o` (vlong型、64ビット整数) が、`int16` の範囲に収まるかどうかをチェックします。`int16` は-32768から32767までの範囲です。もし `o` がこの範囲を超えている場合、2バイトでは表現できないため、「relocation address is too big」という診断メッセージを出力し、エラーを報告します。これは、リロケーションの正確性を保証するために非常に重要です。
    -   `i16 = o;`: `o` が `int16` の範囲内であれば、`int16` 型の変数 `i16` に代入されます。
    -   `cast = (uchar*)&i16;`: `i16` のアドレスを `uchar*` (符号なし1バイト整数へのポインタ) にキャストします。これにより、`i16` のバイトデータに直接アクセスできるようになります。
    -   `for(i=0; i<2; i++) s->p[off+i] = cast[inuxi2[i]];`: ここがエンディアンネスを考慮したバイト書き込みの核心です。
        -   `inuxi2` は、ターゲットアーキテクチャのエンディアンネスに応じて、2バイトデータのバイト順序を決定するためのインデックス配列です。例えば、ビッグエンディアンであれば `[0, 1]`、リトルエンディアンであれば `[1, 0]` のようになる可能性があります（実際の定義はアーキテクチャ依存）。
        -   このループは、`i16` の2バイトを、`inuxi2` で指定された順序で `s->p` の `off` から始まる位置に書き込みます。これにより、ターゲットアーキテクチャがビッグエンディアンでもリトルエンディアンでも、正しいバイト順で値が格納されます。

### `src/cmd/ld/ldelf.c` の変更点

`ldelf.c` は、ELF形式のオブジェクトファイルからリロケーションエントリを読み込む部分を扱っています。

-   **`ldelf` 関数**: この関数はELFファイルを解析し、リロケーションエントリを読み込みます。
-   **`rp->add` のキャスト**: リロケーションエントリの `rp->add` (加算値、addend) は、リロケーションの計算に使用されるオフセット値です。
    -   `if(rp->siz == 2) rp->add = (int16)rp->add;`: この行は、リロケーションのサイズが2バイトである場合、`rp->add` を `int16` にキャストしています。これは、`rp->add` がより大きな型（例えば `int64` や `vlong`）である可能性がある場合に、2バイトリロケーションに必要な範囲に値を収めるためのものです。これにより、後続のリロケーション計算で正しいサイズの加算値が使用されることが保証されます。

これらの変更により、Goリンカは2バイトのリロケーションを正確に解釈し、適用できるようになり、ppc64のようなアーキテクチャでのGoプログラムのリンクが可能になりました。

## コアとなるコードの解説

### `src/cmd/ld/data.c` の `relocsym` 関数における変更

追加された `case 2:` ブロックは、2バイトのリロケーションを処理します。

```c
		case 2:
			// リロケーションによって計算された値 'o' が int16 の範囲に収まるかチェック
			if(o != (int16)o)
				// 収まらない場合、エラーメッセージを出力
				diag("relocation address is too big: %#llx", o);
			// 値を int16 型にキャスト
			i16 = o;
			// int16 型の変数のアドレスを uchar* にキャストし、バイト単位でアクセスできるようにする
			cast = (uchar*)&i16;
			// 2バイトをループで処理
			for(i=0; i<2; i++)
				// シンボルのデータ 's->p' に、エンディアンネスを考慮した順序でバイトを書き込む
				s->p[off+i] = cast[inuxi2[i]];
			break;
```

このコードは、リロケーションの計算結果 `o` が2バイト（`int16`）で表現できる範囲内にあることを確認し、もし範囲外であればエラーを報告します。これは、リロケーションが正しく適用されるための重要なバリデーションです。その後、`o` を `int16` に変換し、`inuxi2` 配列を使用してターゲットアーキテクチャのエンディアンネスに従ってバイト順を調整しながら、シンボルのデータ領域に書き込みます。`inuxi2` は、例えばビッグエンディアンでは `[0, 1]`、リトルエンディアンでは `[1, 0]` のように定義され、バイトの読み書き順序を制御します。

### `src/cmd/ld/ldelf.c` の `ldelf` 関数における変更

追加された行は、ELFファイルから読み込んだリロケーションエントリの加算値 `rp->add` を、そのリロケーションのサイズに応じて適切にキャストします。

```c
			if(rp->siz == 2)
				rp->add = (int16)rp->add;
```

この行は、リロケーションのサイズ `rp->siz` が2バイトである場合、`rp->add` を `int16` にキャストします。`rp->add` は通常、より大きな型（例えば `int64`）で保持されている可能性があるため、このキャストは2バイトリロケーションのコンテキストで加算値が正しく解釈されることを保証します。これにより、後続のリロケーション計算で、加算値が適切なビット幅で扱われるようになります。

これらの変更により、Goリンカは2バイトのリロケーションを正確に処理できるようになり、ppc64のようなアーキテクチャでGoプログラムをビルドする際の互換性と正確性が大幅に向上しました。

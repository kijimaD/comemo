## 変更の背景

Goコンパイラは、最適化のためにプログラムのSSA（Static Single Assignment）形式を使用します。SSA形式では、プログラムの制御フローは「ブロック」に分割され、各ブロックは一連の操作（「値」）を含みます。コンパイラの最適化フェーズでは、到達不能なコード（デッドコード）を特定し、削除する「デッドコード除去」が行われます。

`BlockDead`状態は、かつてデッドコード除去の過程で、あるブロックが到達不能であると判断されたものの、まだ完全に削除されていない一時的な状態を示すために存在していました。しかし、このコミットのメッセージによると、この`BlockDead`状態は実際には使用されていなかったとのことです。未使用のコードや状態は、コンパイラのコードベースを不必要に複雑にし、理解や保守を困難にするため、削除することが望ましいとされます。このコミットは、コードベースの整理と簡素化を目的としています。

## 前提知識の解説

### 1. GoコンパイラのSSA (Static Single Assignment) 形式

Goコンパイラは、Go 1.7以降、最適化の主要な中間表現としてSSA形式を採用しています。SSA形式は、プログラム内の各変数が一度だけ定義されるように変換された表現です。これにより、データフロー解析が大幅に簡素化され、以下のような様々な最適化を効率的に適用できるようになります。

*   **データフロー解析の容易さ**: 各変数の定義が一つしかないため、値の伝播や利用箇所を追跡しやすくなります。
*   **最適化の簡素化**: 定数畳み込み、共通部分式除去、デッドコード除去、レジスタ割り当てなどの最適化が、SSA形式上でより直接的に実装できます。

SSA形式では、プログラムは「関数」として表現され、関数は「ブロック」の集合から構成されます。各ブロックは、一連の「値」（命令や演算）を含み、制御フローのエッジによって他のブロックと接続されます。

### 2. 基本ブロック (Basic Block)

コンパイラ最適化における基本ブロックは、以下の特性を持つ命令のシーケンスです。

*   **単一のエントリポイント**: 実行は常にブロックの先頭から開始されます。
*   **単一の終了ポイント**: 実行は常にブロックの末尾で終了し、次のブロックへ制御が移ります。
*   **内部に分岐なし**: ブロックの内部には、条件分岐やループの開始・終了といった制御フローの変更点はありません。

GoコンパイラのSSAバックエンドでは、これらの基本ブロックが`Block`構造体として表現され、`BlockKind`という列挙型でその種類（例: `BlockPlain`, `BlockIf`, `BlockExit`など）が定義されます。

### 3. デッドコード除去 (Dead Code Elimination, DCE)

デッドコード除去は、プログラムの実行結果に影響を与えないコード（デッドコード）を特定し、削除する最適化手法です。デッドコードには、以下のようなものがあります。

*   **到達不能なコード**: 制御フローによって決して実行されないコード。
*   **結果が使用されない計算**: 計算は行われるが、その結果がプログラムのどこでも利用されないコード。

SSA形式は、データフローと制御フローが明確に表現されるため、デッドコード除去を非常に効果的に行うことができます。コンパイラは、プログラムのエントリポイントから到達可能なブロックと、そのブロック内で計算され、最終的にプログラムの出力に影響を与える値のみを「生きている」と判断し、それ以外のコードをデッドコードとして削除します。

### 4. `BlockDead`状態の意図

このコミットが削除する`BlockDead`は、GoコンパイラのSSAバックエンドにおいて、デッドコード除去の過程で一時的に使用されることを意図したブロックの状態でした。具体的には、あるブロックがデッドコードであると判断されたが、まだSSAグラフから完全に削除されていない段階を示すために設けられていたと考えられます。しかし、実際のコンパイラのロジックでは、この中間状態を明示的に持つ必要がなく、他のメカニズム（例えば、到達可能性解析の結果に基づいて直接ブロックを削除する）で処理されていたため、未使用となっていたと推測されます。

## 技術的詳細

GoコンパイラのSSAバックエンドは、`src/cmd/compile/internal/ssa`パッケージに実装されています。このパッケージには、SSA形式の定義、構築、最適化パス、および検証ツールが含まれています。

*   **`Block`構造体**: SSA形式における基本ブロックを表します。`Kind`フィールドはブロックの種類（例: `BlockPlain`, `BlockIf`, `BlockExit`など）を定義します。
*   **`BlockKind`列挙型**: `Block`の`Kind`フィールドに設定される定数群です。このコミットでは、`BlockDead`という定数が削除されています。
*   **`check.go`**: SSA形式の整合性をチェックするためのコードが含まれています。`checkFunc`関数は、SSA関数の各ブロックが正しい状態にあるかを検証します。`BlockDead`状態が削除されたため、この状態に関する検証ロジックも削除されました。
*   **`gen/genericOps.go`**: SSAオペレーションとブロックの種類に関するメタデータを生成するためのファイルです。`genericBlocks`配列には、各ブロックの種類に関する情報が定義されています。ここから`Dead`ブロックに関する記述が削除されました。
*   **`opGen.go`**: SSAオペレーションとブロックの種類に関する定数や文字列表現を生成するためのファイルです。`BlockDead`定数とその文字列表現が削除されました。
*   **`rewrite.go`**: SSAの書き換えルールを適用するロジックが含まれています。`applyRewrite`関数内で、`BlockDead`のブロックをスキップするロジックが削除されました。これは、`BlockDead`状態のブロックが存在しなくなるため、そのチェックが不要になったことを意味します。

この変更は、コンパイラのSSAバックエンドが`BlockDead`状態を実際に利用していなかったことを示しており、コードの冗長性を排除し、コンパイラの内部構造をよりシンプルに保つためのクリーンアップ作業です。

## コアとなるコードの解説

このコミットの核心は、GoコンパイラのSSA中間表現から`BlockDead`という概念を完全に排除することです。

*   **`check.go`の変更**: `BlockDead`状態のブロックが特定のプロパティ（サクセッサ、プレデセッサなど）を持つことを禁止する検証ロジックが削除されました。これは、`BlockDead`状態のブロックがもはや存在しないため、その整合性をチェックする必要がなくなったことを意味します。コンパイラの健全性チェックから不要なルールが取り除かれ、コードが簡潔になりました。
*   **`gen/genericOps.go`と`opGen.go`の変更**: これらはSSAのブロックの種類に関する定義やメタデータを生成するファイルです。`BlockDead`の定義がこれらのファイルから削除されたことで、コンパイラのSSAバックエンド全体でこの状態が認識されなくなります。これは、コンパイラの内部モデルから未使用の概念が取り除かれたことを示しています。
*   **`rewrite.go`の変更**: `applyRewrite`関数は、SSAグラフに対して最適化の書き換えルールを適用する主要な場所の一つです。以前は、`BlockDead`状態のブロックに対しては書き換え処理をスキップするロジックが存在しました。このロジックが削除されたということは、`BlockDead`状態のブロックがSSAグラフに存在しないことが保証されるため、特別なハンドリングが不要になったことを意味します。これにより、書き換え処理のロジックも簡素化されました。

全体として、このコミットは、GoコンパイラのSSAバックエンドにおけるデッドコード除去のメカニズムが、`BlockDead`という中間状態を必要としない形で進化または設計されていたことを示唆しています。未使用のコードや状態を削除することで、コンパイラのコードベースはよりクリーンで理解しやすくなり、将来の開発やメンテナンスが容易になります。これは、大規模なソフトウェアプロジェクトにおいて、コードの品質と保守性を維持するための重要なプラクティスです。

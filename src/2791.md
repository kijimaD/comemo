# [インデックス 2791] ファイルの概要

このコミットは、Goコンパイラにおけるスライスや文字列の`len()`および`cap()`組み込み関数の評価方法に関する最適化を導入しています。具体的には、これらの操作がレジスタを介さずに直接メモリアドレスを計算できるようにすることで、コード生成の効率を向上させています。

## 変更の背景

Go言語の初期開発段階において、コンパイラはコード生成の効率とパフォーマンスの最適化に継続的に取り組んでいました。このコミットは、スライスや文字列の`len()`（長さ）および`cap()`（容量）を計算する際のオーバーヘッドを削減することを目的としています。

従来のコンパイラの実装では、`len(x)`や`cap(x)`のような操作を行う際に、まず対象となるスライスや文字列`x`の情報をレジスタにロードし、そのレジスタから長さや容量の値を読み出すという手順を踏んでいた可能性があります。しかし、スライスや文字列は内部的にポインタ、長さ、容量の3つのフィールドを持つ構造体として表現されます。もし`x`自体がメモリアドレスを持つ（`addable`な）変数である場合、その長さや容量は`x`のメモリアドレスからの固定オフセットに格納されています。

このコミットの背景にあるのは、このような場合にわざわざレジスタを経由せず、直接メモリアドレス計算によって長さや容量の値にアクセスすることで、生成されるアセンブリコードをより効率的かつ高速にすることです。特に、`x`がエスケープしないローカル変数である場合など、そのアドレスがコンパイル時に確定できる状況では、この最適化は大きな効果を発揮します。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造と概念に関する知識が必要です。

1.  **Goコンパイラのアーキテクチャ (5g, 6g, 8g)**:
    *   Go言語の初期のコンパイラは、ターゲットアーキテクチャごとに異なる名前を持っていました。
        *   `5g`: ARMアーキテクチャ向けコンパイラ
        *   `6g`: x86-64 (AMD64) アーキテクチャ向けコンパイラ
        *   `8g`: x86 (32-bit Intel) アーキテクチャ向けコンパイラ
    *   これらのコンパイラは、それぞれのアセンブリコード生成部分が異なるものの、フロントエンド（構文解析、型チェック、中間表現生成）は共通のコードベースを共有していました。このコミットで複数の`cgen.c`と`gsubr.c`が変更されているのは、これらのコンパイラが共通のコード生成ロジックの一部を共有しているためです。
2.  **スライスと文字列の内部表現**:
    *   Goのスライスは、内部的には以下の3つのフィールドを持つ構造体です。
        *   データへのポインタ (Pointer to the underlying array)
        *   長さ (Length)
        *   容量 (Capacity)
    *   文字列も同様に、データへのポインタと長さの2つのフィールドを持つ構造体として扱われます。
    *   これらのフィールドは、構造体の先頭から固定のオフセットに配置されます。コミットのコードでは`Array_nel`（number of elements、長さ）と`Array_cap`（capacity、容量）という定数がそのオフセットを示唆しています。
3.  **コンパイラのAST (Abstract Syntax Tree) とノード**:
    *   Goコンパイラはソースコードを解析し、抽象構文木（AST）を構築します。ASTの各要素は`Node`構造体で表現されます。
    *   `n->op`: `Node`の操作タイプを示します。`OLEN`は`len()`操作、`OCAP`は`cap()`操作を表します。
    *   `n->left`: ASTノードの左の子ノードを指します。`len(x)`の場合、`n->left`は`x`を表すノードになります。
    *   `n->addable`: このフラグは、ノードが表す値がメモリアドレスを持つ（つまり、直接アドレス指定可能である）かどうかを示します。`addable`な値は、レジスタにロードせずに直接メモリからアクセスできます。
4.  **`cgen.c`と`gsubr.c`**:
    *   `cgen.c` (Code Generation): ASTを走査し、中間コードや最終的なアセンブリコードを生成する主要なロジックが含まれています。
    *   `gsubr.c` (General Subroutines): コード生成プロセスで利用される汎用的なサブルーチンやヘルパー関数が含まれています。`gmove`（値の移動）、`naddr`（ノードのアドレス計算）、`ismem`（ノードがメモリ上の値であるかどうかの判定）などがここに定義されています。
5.  **エスケープ解析 (Escaping Analysis)**:
    *   Goコンパイラは、変数がスタックに割り当てられるべきか、ヒープに割り当てられるべきかを決定するためにエスケープ解析を行います。変数が関数スコープを超えて参照される可能性がある場合（「エスケープする」と呼ばれる）、ヒープに割り当てられます。エスケープしないローカル変数はスタックに割り当てられ、そのアドレスはコンパイル時に確定しやすいため、`addable`な特性を活かした最適化が適用されやすくなります。

## 技術的詳細

このコミットの核心は、`len(x)`や`cap(x)`のような操作が、対象`x`がアドレス指定可能な（`addable`な）場合に、レジスタを介さずに直接メモリから値を読み出すようにコンパイラのコード生成ロジックを変更することです。

具体的には、以下の変更が行われています。

1.  **`cgen.c`における`addable`プロパティの伝播**:
    *   `cgen`関数はASTを走査し、各ノードの特性を決定します。
    *   `OLEN`（`len()`）および`OCAP`（`cap()`）操作のノードに対して、その左の子ノード（`n->left`、つまり`len(x)`の`x`）がスライスまたは文字列であり、かつ`addable`である場合、`OLEN`/`OCAP`ノード自身も`addable`であるとマークされます。
    *   この処理は、`n->left`がエスケープするローカル変数である場合に`n->left->addable`が変更される可能性があるため、`walk`フェーズではなく`cgen`フェーズで行われます。これにより、`len`や`cap`の結果が直接メモリから取得できる可能性がコンパイラに伝えられます。
2.  **`gsubr.c`における`ismem`関数の拡張**:
    *   `ismem`関数は、与えられたノードがメモリ上の値を表すかどうかを判定します。
    *   このコミットにより、`OLEN`と`OCAP`ノードも`ismem`が`true`を返すケースに追加されました。これは、`len`や`cap`の結果が直接メモリから読み取れるようになったことをコンパイラの他の部分に通知する役割を果たします。
3.  **`gsubr.c`における`naddr`関数の拡張**:
    *   `naddr`関数は、与えられたノードのメモリアドレスを計算します。
    *   `OLEN`ノードの場合、`n->left`（スライスまたは文字列`x`）のアドレスを計算し、それに`Array_nel`オフセットを加算することで、`x`の長さフィールドのメモリアドレスを直接取得します。
    *   `OCAP`ノードの場合も同様に、`n->left`のアドレスに`Array_cap`オフセットを加算することで、`x`の容量フィールドのメモリアドレスを直接取得します。
    *   これにより、`len`や`cap`の値を取得するために、まずスライス/文字列全体をレジスタにロードし、そこからフィールドを抽出するという間接的な手順が不要になります。直接、長さや容量が格納されているメモリ位置にアクセスできるようになります。

これらの変更により、コンパイラは`len(x)`や`cap(x)`の呼び出しを、`x`がアドレス指定可能な場合に、より効率的なメモリアクセス命令に変換できるようになります。これは、特に頻繁に`len`や`cap`が使用されるループ内などで、生成されるコードのパフォーマンス向上に寄与します。

## コアとなるコードの変更箇所

### `src/cmd/{5g,6g,8g}/cgen.c`

```c
 // update addressability for string, slice
 // can't do in walk because n->left->addable
 // changes if n->left is an escaping local variable.
 switch(n->op) {
 case OLEN:
  if(isslice(n->left->type) || istype(n->left->type, TSTRING))
   n->addable = n->left->addable;
  break;
 case OCAP:
  if(isslice(n->left->type))
   n->addable = n->left->addable;
  break;
 }
```
このコードブロックは、`cgen`関数内で、`OLEN`または`OCAP`操作のノード`n`が、その対象（`n->left`）がスライスまたは文字列であり、かつ`addable`である場合に、自身も`addable`であるとマークするように変更しています。これにより、`len`や`cap`の結果が直接メモリから取得可能であることをコンパイラに伝えます。

### `src/cmd/{5g,6g,8g}/gsubr.c`

```c
 case OLEN:
 case OCAP:
```
`ismem`関数内の`switch(n->op)`に`OLEN`と`OCAP`が追加されました。これは、`len`や`cap`操作の結果がメモリ上の値として扱われ得ることを示します。

```c
 case OLEN:
  // len of string or slice
  naddr(n->left, a);
  a->offset += Array_nel;
  break;

 case OCAP:
  // cap of string or slice
  naddr(n->left, a);
  a->offset += Array_cap;
  break;
```
`naddr`関数内の`switch(n->op)`に`OLEN`と`OCAP`が追加されました。`OLEN`の場合、`n->left`のアドレスに`Array_nel`オフセットを加算して長さフィールドのアドレスを計算します。`OCAP`の場合、`n->left`のアドレスに`Array_cap`オフセットを加算して容量フィールドのアドレスを計算します。これにより、`len`や`cap`の値を直接メモリから読み出すためのアドレスが生成されます。

## コアとなるコードの解説

このコミットの主要な変更は、Goコンパイラのバックエンドにおける`len`と`cap`組み込み関数の処理方法を最適化することです。

1.  **`cgen.c`の変更**:
    *   `cgen`はコード生成のフェーズであり、ASTノードを走査して機械語命令に変換する準備をします。
    *   `n->addable = n->left->addable;`という行は非常に重要です。これは、`len(x)`や`cap(x)`のような操作の結果が、`x`がアドレス指定可能であれば、その結果もアドレス指定可能であるとコンパイラに伝えています。つまり、`x`がメモリ上の特定の場所にある場合、その長さや容量も`x`のメモリレイアウト内の既知のオフセットにあるため、`len(x)`や`cap(x)`の結果もメモリ上の特定のアドレスに直接対応付けられる、ということです。
    *   コメントにある「`can't do in walk because n->left->addable changes if n->left is an escaping local variable.`」は、エスケープ解析の結果によって`n->left`の`addable`プロパティが変化する可能性があるため、`walk`フェーズ（より早いAST走査フェーズ）ではなく、`cgen`フェーズでこの`addable`プロパティの伝播を行う必要があることを示しています。これにより、最新のエスケープ解析の結果が反映された正確な`addable`情報に基づいて最適化が適用されます。

2.  **`gsubr.c`の`ismem`関数の変更**:
    *   `ismem`関数は、あるノードがメモリ上の値を参照しているかどうかを判断するためにコンパイラの他の部分で利用されます。
    *   `OLEN`と`OCAP`が`ismem`のケースに追加されたことで、コンパイラは`len`や`cap`の結果が直接メモリから取得できる可能性があることを認識し、それに応じてより効率的なコードパスを選択できるようになります。

3.  **`gsubr.c`の`naddr`関数の変更**:
    *   `naddr`関数は、ASTノードに対応するメモリアドレスを計算する役割を担います。
    *   `OLEN`と`OCAP`の新しいケースでは、`naddr(n->left, a)`によってまず対象のスライス/文字列`x`のベースアドレス`a`を取得します。
    *   次に、`a->offset += Array_nel;`または`a->offset += Array_cap;`によって、そのベースアドレスに固定オフセット（`Array_nel`は長さ、`Array_cap`は容量のオフセット）を加算します。これにより、`len(x)`や`cap(x)`が評価されるべきメモリ上の正確なアドレスが直接計算されます。
    *   この直接的なアドレス計算により、中間的なレジスタへのロードが不要となり、生成されるアセンブリコードが簡潔かつ高速になります。例えば、`MOV`命令一つで直接メモリから値をレジスタにロードできるようになる可能性があります。

これらの変更は、Goコンパイラがスライスや文字列の内部構造を深く理解し、その知識を活用して、一般的な操作である`len`や`cap`の呼び出しをより効率的な機械語命令に変換するための初期の最適化努力の一環です。

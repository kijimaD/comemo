# [インデックス 25302] ファイルの概要

このコミットは、Goリンカにおけるスタックの固定部分のサイズに関する知識を一元化することを目的としています。特に、`ppc64le`アーキテクチャにおける共有ライブラリの要件に対応するため、リンカ内の関連コードがスタックフレームの固定サイズを取得するための共通関数`FixedFrameSize()`を呼び出すように変更されています。これにより、将来的なABI変更やアーキテクチャ固有のスタック要件への対応が容易になります。

## 変更の背景

この変更の主な背景は、`ppc64le`アーキテクチャにおける共有ライブラリのサポート強化です。`ppc64le`のABI（Application Binary Interface）では、関数呼び出し時にTOC（Table of Contents）ポインタが特定のスタックオフセット（`24(R1)`）で利用可能であることを義務付けています。これは、共有ライブラリが正しく機能するために必要な要件であり、結果としてより大きな最小スタックフレームが必要となります。

Goリンカは、プログラムの実行に必要なスタックサイズを正確に計算する必要があります。これまでの実装では、スタックの固定部分のサイズに関する知識がリンカ内の複数の場所に散在しており、`ppc64le`のような特定のアーキテクチャのABI要件に対応する際に、コードの重複や保守性の問題が生じる可能性がありました。

このコミットは、このようなアーキテクチャ固有のスタックフレーム要件をリンカがより適切に、かつ一元的に管理できるようにするための準備作業の一環です。具体的には、「スタックの固定部分のサイズ」に関する知識を`FixedFrameSize()`という単一の関数に集約することで、将来的な変更や異なるアーキテクチャへの対応を容易にすることを目指しています。これは、`ppc64le`における共有ライブラリサポートに向けた「パート2b」と位置づけられています。

## 前提知識の解説

### スタックフレーム (Stack Frame)

関数が呼び出されるたびに、その関数に必要な情報（ローカル変数、引数、戻りアドレス、レジスタの退避領域など）を格納するために、メモリ上に確保される領域をスタックフレームと呼びます。スタックフレームはスタック上に積まれ、関数が終了すると解放されます。

### スタックポインタ (Stack Pointer, SP)

スタックポインタは、現在のスタックフレームの先頭（または末尾、アーキテクチャによる）を指すレジスタです。`ppc64le`では、R1レジスタがスタックポインタとして使用され、スタックはアドレスが低い方向（下方）に成長します。

### リンクレジスタ (Link Register, LR)

多くのRISCアーキテクチャ（PowerPCを含む）では、関数呼び出し時に戻りアドレスを格納するためにリンクレジスタが使用されます。関数プロローグ（関数の開始部分）で、このリンクレジスタの値がスタックに退避されることがあります。

### TOC (Table of Contents) ポインタ

`ppc64le`のようなPowerPCアーキテクチャでは、TOC（Table of Contents）は、グローバル変数や関数のアドレスを格納する重要なデータ構造です。特に、PC相対アドレッシングが制限される環境や、共有ライブラリにおいて、TOCはコードからデータや他の関数へのアクセスを仲介します。R2レジスタがTOCポインタとして専用に用いられます。

### `ppc64le` ABI (Application Binary Interface)

ABIは、オペレーティングシステムとプログラム、またはプログラムの異なるモジュール間（例えば、アプリケーションと共有ライブラリ）で、どのようにデータがやり取りされ、関数が呼び出されるかなどを定義する規約です。`ppc64le`のABIは、スタックフレームのレイアウト、レジスタの使用規約、関数呼び出し規約などを詳細に定めています。

特に、`ppc64le`のABIでは、関数呼び出し時にTOCポインタ（R2）がスタックフレーム内の特定のオフセット（`24(R1)`）で利用可能であることを要求します。これは、共有ライブラリが動的にロードされ、TOCを介してシンボルを解決する必要がある場合に重要となります。この要件を満たすためには、スタックフレームの固定部分にTOCポインタを保存するための領域が含まれる必要があり、結果として最小スタックフレームサイズが増加します。

### Goリンカ (`cmd/link`)

Go言語のリンカは、コンパイルされたオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリを生成するツールです。この過程で、関数呼び出しの解決、メモリレイアウトの決定、スタックフレームサイズの計算など、様々な低レベルの処理を行います。リンカは、ターゲットアーキテクチャのABIに準拠したバイナリを生成する責任を負います。

## 技術的詳細

このコミットの核心は、Goリンカがスタックフレームの固定部分のサイズを決定する方法を変更することにあります。以前は、このサイズに関するロジックが`dwarf.go`や`lib.go`などの複数のファイルに分散しており、アーキテクチャ固有の条件分岐（例: `haslinkregister()`関数）によって処理されていました。

新しいアプローチでは、`cmd/link/internal/ld/link.go`に`(*Link).FixedFrameSize()`という新しいメソッドが導入されます。このメソッドは、現在のリンカコンテキスト（`Ctxt`）がターゲットとするアーキテクチャに基づいて、スタックの固定フレームサイズを返します。

`FixedFrameSize()`メソッドの実装は以下の通りです。

```go
func (ctxt *Link) FixedFrameSize() int64 {
	switch ctxt.Arch.Thechar {
	case '6', '8': // x86 (32-bit), x86-64
		return 0
	default: // Other architectures, including ppc64le
		return int64(ctxt.Arch.Ptrsize)
	}
}
```

この関数は、`x86`および`x86-64`アーキテクチャ（`Thechar`が`'6'`または`'8'`）の場合、固定フレームサイズを`0`と返します。これは、これらのアーキテクチャでは、リンクレジスタの退避やTOCポインタの特別な扱いが不要であるため、スタックの固定部分に特別なオーバーヘッドがないことを意味します。

しかし、それ以外のアーキテクチャ（`ppc64le`など）の場合、`ctxt.Arch.Ptrsize`（ポインタのサイズ、通常は8バイト）を返します。これは、リンクレジスタの退避領域や、`ppc64le`のABIで要求されるTOCポインタの保存領域など、アーキテクチャ固有の固定オーバーヘッドを考慮したものです。`ppc64le`の場合、TOCポインタが`24(R1)`で利用可能であるというABI要件を満たすために、この`Ptrsize`分の領域がスタックフレームの固定部分として確保されることになります。

この`FixedFrameSize()`関数を導入することで、スタックの固定部分のサイズに関するロジックが一元化され、リンカ内の他の部分はこの関数を呼び出すだけで、正しい固定フレームサイズを取得できるようになります。これにより、コードの重複が排除され、保守性が向上し、将来的なABI変更への対応が容易になります。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/cmd/link/internal/ld/dwarf.go`**:

    *   以前は`haslinkregister()`の結果に基づいて`Thearch.Ptrsize`を加算していましたが、新しい`Ctxt.FixedFrameSize()`を呼び出すように変更されました。
    *   `offs = int64(a.Aoffset) + Ctxt.FixedFrameSize()`

2.  **`src/cmd/link/internal/ld/lib.go`**:
    *   `haslinkregister()`関数の実装が変更されました。
    *   以前は特定のアーキテクチャ文字（`'5'`, `'9'`, `'7'`）を直接チェックしていましたが、`Ctxt.FixedFrameSize() != 0`をチェックするように変更されました。これにより、リンクレジスタの有無ではなく、固定フレームサイズが存在するかどうかで判断するようになりました。
    *   `stkcheck()`関数内で、スタック制限の計算が変更されました。
    *   以前は`haslinkregister()`の結果に基づいて`Thearch.Regsize`を加算していましたが、新しい`Ctxt.FixedFrameSize()`を呼び出すように変更されました。
    *   `limit = int(obj.StackLimit+s.Locals) + int(Ctxt.FixedFrameSize())`

3.  **`src/cmd/link/internal/ld/link.go`**:
    *   `Link`構造体に新しいメソッド`FixedFrameSize()`が追加されました。
    *   このメソッドは、リンカコンテキストのアーキテクチャに基づいて、スタックの固定フレームサイズを計算して返します。`x86`および`x86-64`では`0`を返し、それ以外のアーキテクチャでは`ctxt.Arch.Ptrsize`を返します。

## コアとなるコードの解説

このコミットのコアとなる変更は、`src/cmd/link/internal/ld/link.go`に追加された`FixedFrameSize()`メソッドです。

```go
// The smallest possible offset from the hardware stack pointer to a local
// variable on the stack. Architectures that use a link register save its value
// on the stack in the function prologue and so always have a pointer between
// the hardware stack pointer and the local variable area.
func (ctxt *Link) FixedFrameSize() int64 {
	switch ctxt.Arch.Thechar {
	case '6', '8': // x86 (32-bit), x86-64
		return 0
	default: // Other architectures, including ppc64le
		return int64(ctxt.Arch.Ptrsize)
	}
}
```

このメソッドは、ハードウェアスタックポインタからスタック上のローカル変数までの最小オフセット、つまりスタックフレームの固定部分のサイズを計算します。

*   **`ctxt *Link`**: これはGoリンカの主要なコンテキスト構造体であり、現在のリンカセッションに関するすべての情報（ターゲットアーキテクチャ、シンボルテーブルなど）を保持しています。
*   **`ctxt.Arch.Thechar`**: これはターゲットアーキテクチャを識別する文字です。
    *   `'6'`は`x86`（32ビット）を、`'8'`は`x86-64`を指します。これらのアーキテクチャでは、通常、リンクレジスタの概念がなく、TOCポインタの特別な扱いも不要なため、固定フレームサイズは`0`となります。
    *   `default`ケースは、それ以外のすべてのアーキテクチャ（`ppc64le`、`arm`、`arm64`など）をカバーします。これらのアーキテクチャでは、リンクレジスタの退避や、`ppc64le`のTOCポインタのように、スタックフレームの固定部分にポインタサイズの領域が必要となる場合があります。そのため、`ctxt.Arch.Ptrsize`（ポインタのサイズ、通常は4バイトまたは8バイト）が返されます。

この`FixedFrameSize()`メソッドが導入されたことで、`dwarf.go`と`lib.go`内のスタックサイズ計算ロジックは、直接アーキテクチャ固有の条件分岐を行う代わりに、この共通のメソッドを呼び出すようになりました。これにより、スタックフレームの固定部分のサイズに関する知識が`FixedFrameSize()`に一元化され、リンカ全体のコードの可読性、保守性、および拡張性が向上します。特に、`ppc64le`の共有ライブラリサポートに必要なスタックフレームの拡張が、この一元化されたメカニズムを通じて容易に実現できるようになります。

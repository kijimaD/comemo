## 変更の背景

このコミットの背景には、Goコンパイラのコードベースの健全性を維持し、最適化するという目的があります。コンパイラのような大規模なソフトウェアプロジェクトでは、時間の経過とともにコードが進化し、一部のデータ構造のフィールドが不要になることがあります。

不要な（"dead"）フィールドを削除することには、いくつかの利点があります。

1.  **コードの明確化と保守性の向上**: 使用されていないフィールドは、コードを読解する際に混乱を招く可能性があります。それらを削除することで、コードの意図がより明確になり、将来の保守が容易になります。
2.  **メモリ使用量の削減**: 構造体からフィールドを削除することで、その構造体のインスタンスが占めるメモリ量が減少します。コンパイラは大量のデータ構造を扱うため、これはパフォーマンスに寄与する可能性があります。
3.  **バグの潜在的な原因の排除**: 未使用のフィールドが誤って使用されたり、意図しない副作用を引き起こしたりする可能性を排除します。
4.  **コンパイル時間の短縮**: わずかではありますが、構造体のサイズが小さくなることで、コンパイラ自身のコンパイル時間や、コンパイラが生成するコードの処理速度に影響を与える可能性があります。

この特定のケースでは、`yySymType`という構造体からいくつかのフィールドが削除されており、これはGoコンパイラの開発過程で、これらのフィールドが字句解析器や構文解析器の現在の実装ではもはや必要ないと判断されたことを示唆しています。これは、コンパイラの内部構造のリファクタリングや最適化の一環であると考えられます。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識があると役立ちます。

### 1. コンパイラの基本構造

コンパイラは、ソースコードを機械が実行できる形式に変換するプログラムです。一般的なコンパイラは、以下の主要なフェーズで構成されます。

*   **字句解析（Lexical Analysis / Lexing）**: ソースコードを読み込み、意味のある最小単位（トークン）に分解します。例えば、`var x = 10;`というコードは、`var`（キーワード）、`x`（識別子）、`=`（演算子）、`10`（リテラル）、`;`（区切り文字）といったトークンに分解されます。
*   **構文解析（Syntactic Analysis / Parsing）**: 字句解析器が生成したトークンのストリームを受け取り、言語の文法規則に従って構文木（Abstract Syntax Tree: AST）を構築します。これにより、コードの構造が表現されます。
*   **意味解析（Semantic Analysis）**: 構文木を走査し、型チェック、変数宣言の解決、その他の意味的な制約のチェックを行います。
*   **中間コード生成（Intermediate Code Generation）**: 構文木から、ターゲットマシンに依存しない中間表現（IR）を生成します。
*   **コード最適化（Code Optimization）**: 中間コードを分析し、より効率的なコードに変換します。
*   **コード生成（Code Generation）**: 最適化された中間コードから、ターゲットマシン固有の機械語コードを生成します。

### 2. `yacc`とセマンティックアクション

`yacc`（Yet Another Compiler Compiler）は、構文解析器ジェネレータの一種で、文法規則を記述したファイルからC言語などのソースコードを生成します。`yacc`はLALR(1)パーサーを生成し、字句解析器（通常は`lex`によって生成される）と連携して動作します。

`yacc`ベースのパーサーでは、字句解析器がトークンを生成し、そのトークンに関連する「セマンティック値」を構文解析器に渡します。構文解析器は、文法規則がマッチした際に「セマンティックアクション」を実行し、これらのセマンティック値を使って構文木を構築したり、他の処理を行ったりします。

`yySymType`は、`yacc`によって生成されるパーサーにおいて、これらのセマンティック値を保持するために使用される共用体（Union）または構造体です。字句解析器は、認識したトークンの種類に応じて、この`yySymType`構造体の適切なフィールドに値を格納し、構文解析器に渡します。構文解析器の各文法規則は、スタック上の`yySymType`インスタンスから必要なフィールドを取り出して処理を行います。

### 3. Goコンパイラにおける`gc`パッケージ

Goコンパイラ（`cmd/compile`）は、Go言語で書かれており、その主要な部分が`internal/gc`パッケージにあります。このパッケージは、Go言語のフロントエンド（字句解析、構文解析、意味解析）とバックエンド（中間コード生成、最適化、コード生成）の大部分を実装しています。`lex.go`ファイルは、この`gc`パッケージの一部として、字句解析に関連する機能を提供しています。

### 4. Goコンパイラ内部のデータ構造

Goコンパイラは、ソースコードを処理するために様々な内部データ構造を使用します。

*   **`Node`**: 構文木（AST）のノードを表す汎用的な構造体。変数、定数、式、文など、Goプログラムのあらゆる要素が`Node`として表現されます。
*   **`NodeList`**: `Node`のリスト。例えば、関数の引数リストや文のブロックなどを表現するのに使われます。
*   **`Type`**: Go言語の型システムにおける型（int, string, structなど）を表す構造体。
*   **`Sym`**: シンボル（識別子）を表す構造体。変数名、関数名、型名などがこれに該当し、スコープ情報や型情報などを持ちます。
*   **`Val`**: 定数値を表す構造体。数値、文字列、ブール値などのリテラル値を保持します。
*   **`Op`**: 演算子（+,-,*,/など）や、ASTノードの種類を表す列挙型（または定数）。

これらのデータ構造は、コンパイラの各フェーズでソースコードの情報を表現し、変換するために不可欠です。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/gc/lex.go` ファイル内の `yySymType` 構造体から、いくつかのフィールドを削除しています。

`yySymType` 構造体は、Goコンパイラの字句解析器と構文解析器の間でセマンティックな値をやり取りするために使用されます。これは、`yacc`のようなパーサージェネレータが生成するパーサーの典型的なパターンです。字句解析器がトークンを認識すると、そのトークンに関連する情報をこの `yySymType` 構造体に格納し、構文解析器に渡します。構文解析器は、文法規則に基づいてこれらの値を取り出し、ASTの構築などの処理を行います。

削除されたフィールドは以下の通りです。

*   `yys int`
*   `node *Node`
*   `list *NodeList`
*   `typ *Type`

残されたフィールドは以下の通りです。

*   `sym *Sym`
*   `val Val`
*   `op Op`

この変更は、Goコンパイラの進化、特に`gc`パッケージ内のパーサーとAST構築ロジックのリファクタリングの結果であると推測されます。具体的には、以下の可能性が考えられます。

1.  **パーサーの内部構造の変更**: 以前は`yySymType`を通じて`Node`、`NodeList`、`Type`といったAST関連のオブジェクトが直接やり取りされていたが、コンパイラの設計変更により、これらのオブジェクトの生成や管理がパーサーのセマンティックアクション内で直接行われるようになった、あるいは別のメカニズムを通じて行われるようになった。例えば、パーサーがASTノードを構築する際に、`yySymType`から直接`*Node`を受け取るのではなく、`Sym`、`Val`、`Op`などのよりプリミティブな情報を使って新しい`Node`を生成するようになった、などが考えられます。
2.  **未使用フィールドの特定**: コードベースの分析ツールや手動レビューによって、これらのフィールドが実際に使用されていない「デッドコード」であることが特定された。コンパイラの開発者は、コードの複雑性を減らし、メモリフットプリントを最適化するために、未使用のフィールドを積極的に削除します。
3.  **`yys int` の役割**: `yys`フィールドは、`yacc`が生成するパーサーにおいて、スタックの状態番号を保持するために使用されることがあります。このフィールドが削除されたということは、パーサーの内部状態管理のメカニズムが変更されたか、あるいはこの特定の`yySymType`のインスタンスでは状態番号を保持する必要がなくなったことを示唆しています。

残された `sym *Sym`、`val Val`、`op Op` フィールドは、引き続き字句解析器が識別子（シンボル）、定数値、演算子（またはノードの種類）といった基本的なセマンティック情報を構文解析器に渡すために必要であると考えられます。これらの情報は、ASTの葉ノードや基本的な構成要素を形成するために不可欠です。

このコミットは、Goコンパイラの内部実装が成熟し、より効率的で保守しやすい形に継続的に改善されていることを示しています。

## コアとなるコードの解説

`yySymType` 構造体は、Goコンパイラの字句解析器（lexer）と構文解析器（parser）の間で、トークンに関連するセマンティックな情報を伝達するためのデータコンテナです。`yacc`のようなツールを使用するコンパイラでは、字句解析器がソースコードからトークンを抽出し、そのトークンの種類と関連する値（セマンティック値）をこの構造体に格納して構文解析器に渡します。構文解析器は、これらのセマンティック値を使って抽象構文木（AST）を構築したり、型チェックを行ったりします。

削除されたフィールドは以下の通りです。

*   `yys int`: このフィールドは、`yacc`が生成するパーサーの内部状態管理に関連する可能性があります。パーサーのスタックの状態番号を保持するために使われることがありますが、Goコンパイラのパーサーの進化により、この特定の`yySymType`インスタンスで状態を追跡する必要がなくなったか、別の方法で管理されるようになったと考えられます。
*   `node *Node`: `Node`はGoコンパイラのASTの基本的な構成要素です。このフィールドが削除されたということは、字句解析器が直接`Node`オブジェクトを生成して渡すのではなく、構文解析器のセマンティックアクションが`sym`、`val`、`op`などのより基本的な情報から`Node`を構築するようになったことを示唆しています。これにより、AST構築のロジックがパーサー側に集約され、よりクリーンな設計になった可能性があります。
*   `list *NodeList`: `NodeList`は`Node`のリストを表します。`node *Node`と同様に、このフィールドの削除は、リスト構造の構築がパーサーのセマンティックアクション内で直接行われるようになったか、あるいは`yySymType`を通じてリスト全体を渡す必要がなくなったことを意味します。
*   `typ *Type`: `Type`はGo言語の型情報を表します。このフィールドが削除されたことは、字句解析の段階で型情報を`yySymType`に格納して渡す必要がなくなったことを示唆しています。型チェックや型推論は通常、構文解析後の意味解析フェーズで行われるため、`yySymType`が直接型情報を持つ必要性は低いと判断されたのかもしれません。

残されたフィールドは以下の通りです。

*   `sym *Sym`: `Sym`は識別子（変数名、関数名など）のシンボル情報を保持します。これは、ソースコード中の名前を識別し、その属性（型、スコープなど）を解決するために不可欠です。
*   `val Val`: `Val`は定数値（リテラル）を保持します。数値、文字列、ブール値などのリテラルは、プログラムの基本的なデータ要素であり、字句解析器がこれらを認識して構文解析器に渡す必要があります。
*   `op Op`: `Op`は演算子やASTノードの種類を表す列挙型です。例えば、`+`、`-`、`*`などの演算子や、特定のキーワード（`if`、`for`など）がトークンとして認識された際に、その種類を`Op`として表現し、構文解析器に伝達します。

これらの変更は、Goコンパイラの内部設計がより洗練され、不要なデータ伝達が排除されたことを示しており、結果としてコンパイラの効率性と保守性が向上していると考えられます。

# [インデックス 23978] ファイルの概要

このコミットは、Go言語のランタイムにおけるスライス（slice）の`append`操作時の容量拡張ロジックの修正に関するものです。具体的には、`append`のインライン化されたコードが`growslice`関数に渡す引数の解釈の誤りを修正し、スライスの容量拡張が意図した2倍成長に近づくように調整しています。この修正により、`growslice`のシグネチャが変更され、既存の呼び出し元のために`growslice_n`という新しい関数が導入されました。

## 変更の背景

Go言語のスライスは、要素を追加する際に容量が不足した場合、自動的に新しいより大きな配列を割り当てて既存の要素をコピーします。この容量拡張の戦略は、通常、パフォーマンスを最適化するために、現在の容量の約2倍に設定されています。

このコミットが行われる前、`append`関数のインライン化されたコードは、`growslice`というランタイム関数を呼び出してスライスの容量を拡張していました。このインライン化されたコードは、`growslice`に「新しい最小容量（desired new cap）」を渡すことを想定していました。しかし、`growslice`関数自体は、その引数を「追加される新しい要素の数（number of new elements）」として解釈していました。

この解釈の不一致により、`growslice`は常に「新しい最小容量」に「追加される新しい要素の数」を足し合わせた値に基づいて容量を計算していました。結果として、スライスの容量は意図された2倍成長よりも大きく（具体的には「2倍 + 1」を次のメモリブロックサイズに切り上げた値）拡張されていました。これはメモリの無駄遣いにつながる可能性がありました。

コミットの作者であるRuss Coxは、当初、他の`growslice`の呼び出し元も「新しい最小容量」を渡すように変更するつもりでしたが、既に多くのコードがそのように書かれており、変更するには手遅れであると判断しました。そのため、このコミットでは、インライン化された`append`（一般的なケース）が正しい引数で`growslice`を呼び出すようにし、既存の呼び出し元のために「追加される新しい要素の数」を引数として受け取る`growslice_n`という新しい関数を導入することで、この問題を解決しました。

## 前提知識の解説

### Goのスライスと容量拡張

Goのスライスは、可変長シーケンスを表現するためのデータ構造です。内部的には、基盤となる配列、スライスの長さ（`len`）、および容量（`cap`）の3つの要素で構成されます。
- **長さ (len)**: スライスに含まれる要素の数。
- **容量 (cap)**: スライスが参照している基盤配列の最大容量。

`append`関数を使用してスライスに要素を追加する際、現在の容量が不足すると、Goランタイムは新しい基盤配列を割り当て、既存の要素を新しい配列にコピーし、追加する要素を格納します。この新しい配列の容量を決定するロジックが容量拡張戦略です。一般的に、Goではスライスの容量が1024未満の場合は2倍、1024以上の場合は1.25倍に拡張されることが多いですが、これは実装の詳細であり、バージョンによって異なる場合があります。このコミットの時点では、主に2倍成長が期待されていました。

### `append`関数のインライン化

Goコンパイラは、パフォーマンス最適化のために、特定の組み込み関数（`append`もその一つ）をインライン化することがあります。インライン化とは、関数呼び出しをその関数の本体のコードで直接置き換えることで、関数呼び出しのオーバーヘッドを削減する技術です。`append`がインライン化される場合、コンパイラは直接`growslice`のようなランタイムヘルパー関数を呼び出すコードを生成します。

### `growslice`関数の役割

`growslice`はGoランタイムに存在する内部関数で、スライスの容量が不足した際に新しい基盤配列を割り当て、既存の要素をコピーする処理を担当します。この関数は、新しいスライスの型情報、古いスライス、そして新しい容量を計算するための情報を受け取ります。

### `malloc`ブロックサイズ

Goランタイムは、メモリを効率的に管理するために、特定のサイズのブロック単位でメモリを割り当てます。`growslice`が新しい容量を計算する際、最終的な容量はこれらの`malloc`ブロックサイズに合わせて切り上げられることがあります。

## 技術的詳細

このコミットの核心は、`growslice`関数の引数の意味論の不一致を解消することにあります。

1.  **`growslice`のシグネチャ変更**:
    元の`growslice`は、`growslice(t *slicetype, old slice, n int) slice`というシグネチャで、`n`は「追加される新しい要素の数」として解釈されていました。
    このコミットにより、`growslice`のシグネチャは`growslice(t *slicetype, old slice, cap int) slice`に変更され、`cap`は「新しい最小容量」として解釈されるようになりました。これにより、`append(slice, elem...)`のように単一の要素を追加するインライン化された`append`は、直接「新しい最小容量」を`growslice`に渡すことができるようになります。

2.  **`growslice_n`の導入**:
    `growslice`の引数解釈が変更されたため、既存の`growslice`を呼び出していたコード（特に`append(slice, slice...)`のようにスライス全体を追加するケース）は、引き続き「追加される新しい要素の数」を渡す必要がありました。この互換性を保つために、`growslice_n(t *slicetype, old slice, n int) slice`という新しい関数が導入されました。
    `growslice_n`は、`n`（追加される新しい要素の数）を受け取り、内部で`old.cap + n`を計算して、新しい`growslice`関数に「新しい最小容量」として渡します。

3.  **コンパイラ (`src/cmd/compile/internal/gc/walk.go`) の変更**:
    *   `append(slice, slice...)` のケースでは、以前`growslice`を呼び出していた箇所が`growslice_n`を呼び出すように変更されました。これにより、既存のロジック（追加される要素数に基づいて容量を計算する）が維持されます。
    *   `append(slice, elem...)` のケースでは、`growslice`を呼び出す際の引数が変更されました。以前は「追加される要素数」を渡していましたが、新しい`growslice`のシグネチャに合わせて「現在の長さ + 追加される要素数」を計算し、それを「新しい最小容量」として`growslice`に渡すように修正されました。

この変更により、`append`のインライン化されたコードは、`growslice`に正しい意味の引数を渡すようになり、スライスの容量拡張が意図した2倍成長（またはそれに近い値）に修正されました。

## コアとなるコードの解説

### `src/runtime/slice.go` の変更

-   **`growslice`関数のシグネチャとセマンティクスの変更**:
    変更前: `func growslice(t *slicetype, old slice, n int) slice`
    変更後: `func growslice(t *slicetype, old slice, cap int) slice`
    以前の`n`は「追加される要素の数」を意味していましたが、新しい`cap`は「新しいスライスの最小容量」を意味します。これにより、`growslice`は直接、必要な最小容量を受け取って処理できるようになりました。関数のコメントも、この新しいセマンティクスを反映するように更新されています。

-   **`growslice_n`関数の導入**:
    `func growslice_n(t *slicetype, old slice, n int) slice`
    この新しい関数は、以前の`growslice`と同じ引数（`n`は追加される要素の数）を受け取ります。内部では、`old.cap + n`を計算し、これを新しい`growslice`関数の`cap`引数として渡しています。これにより、`append(slice, slice...)`のように複数の要素を追加する既存の呼び出し元は、`growslice_n`を呼び出すことで、変更された`growslice`のセマンティクスに適応できます。コメントには、将来的にはコンパイラが`growslice_n`を直接`growslice`に置き換えるべきであるというTODOが記載されています（issue #11419）。

### `src/cmd/compile/internal/gc/walk.go` の変更

このファイルはGoコンパイラのバックエンドの一部であり、`append`組み込み関数の処理方法を定義しています。

-   **`append(slice, slice...)` のケース (`appendslice`関数内)**:
    以前は`growslice(s, n)`を呼び出していましたが、`growslice_n(s, n)`に変更されました。ここで`n`は`len(l1) + len(l2) - cap(s)`、つまり追加される要素の総数を表します。これは、`growslice_n`が「追加される要素の数」を引数として受け取るため、正しい変更です。

-   **`append(slice, elem...)` のケース (`walkappend`関数内)**:
    以前は`growslice(s, argc)`を呼び出していましたが、`growslice(s, len(s)+argc)`に変更されました。ここで`argc`は追加される単一の要素の数を表します。新しい`growslice`は「新しい最小容量」を期待するため、`len(s) + argc`（現在の長さ + 追加される要素数）を計算して渡すように修正されました。これにより、`growslice`は正しい最小容量に基づいてスライスを拡張するようになります。

### `src/runtime/runtime_test.go` の変更

`TestAppendGrowth`と`TestAppendSliceGrowth`という2つの新しいテスト関数が追加されました。これらのテストは、`append`操作後のスライスの容量（`cap`）が期待通りに成長しているかを確認します。特に、容量が2倍成長のパターン（`i&(i-1) == 0`、つまり`i`が2の冪乗のときに容量が`2*i`になる）に従っていることを検証しています。これにより、今回の修正がスライスの容量拡張戦略を正しく機能させていることが保証されます。

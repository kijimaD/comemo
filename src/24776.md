# [インデックス 24776] ファイルの概要

このコミットは、Go言語の `crypto/tls` パッケージにおける `tls.Listen` 関数の挙動を修正するものです。具体的には、TLS設定 (`tls.Config`) において、証明書が `Certificates` フィールドに直接指定されていない場合でも、`GetCertificate` コールバックが提供されていれば `tls.Listen` が正しく機能するように変更されました。Go 1.5で `GetCertificate` の柔軟性が向上したにもかかわらず、`tls.Listen` がその変更に追従していなかった問題を解決します。

## コミット

crypto/tls: `GetCertificate` のみが提供されている場合に `tls.Listen` を許可

## 変更の背景

Go 1.5では、`crypto/tls` パッケージにおいて、TLS接続の確立時に使用するサーバー証明書を動的に選択する機能が強化されました。具体的には、`tls.Config` 構造体の `GetCertificate` フィールドにコールバック関数を設定することで、クライアントからの接続要求（`ClientHello`）に基づいて適切な証明書をその場で提供できるようになりました。これは、特にSNI (Server Name Indication) を利用したバーチャルホスティングや、サーバーを停止せずに証明書を更新する「ヒットレス証明書ローテーション」といった高度なシナリオで非常に有用です。

しかし、このコミット以前の `tls.Listen` 関数は、`tls.Config` の `Certificates` フィールドが空の場合、`GetCertificate` が設定されていてもエラーを返していました。これは、`tls.Listen` が `tls.Config.Certificates` が非空であることを必須とする古いロジックに固執していたためです。その結果、`GetCertificate` の柔軟性を活用して動的に証明書を提供するサーバーを `tls.Listen` で構築しようとすると、不必要なエラーが発生し、開発者は回避策を講じる必要がありました。このコミットは、この不整合を解消し、`tls.Listen` が `GetCertificate` の存在を正しく認識するようにすることで、Go 1.5で導入された柔軟性を完全に利用できるようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Go言語の `crypto/tls` パッケージにおける以下の概念を理解しておく必要があります。

1.  **`tls.Config` 構造体**:
    TLSサーバーまたはクライアントの設定を保持する主要な構造体です。証明書、鍵、プロトコルバージョン、暗号スイートなど、TLS接続に関するあらゆる設定が含まれます。

2.  **`tls.Config.Certificates` フィールド**:
    `[]tls.Certificate` 型のスライスで、サーバーが使用する静的な証明書と秘密鍵のペアのリストを保持します。通常、サーバーはここに含まれる証明書の中から、クライアントが要求する証明書を選択して提示します。

3.  **`tls.Config.GetCertificate` フィールド**:
    `func(*ClientHelloInfo) (*Certificate, error)` 型のコールバック関数です。この関数が設定されている場合、TLSハンドシェイク中にクライアントから `ClientHello` メッセージを受信した際に呼び出されます。このコールバックは、`ClientHelloInfo` (クライアントが要求するSNIホスト名などの情報を含む) を引数として受け取り、その情報に基づいて動的に `*tls.Certificate` を生成または選択して返します。これにより、単一のサーバーが複数のドメインの証明書を処理したり、証明書を動的に更新したりすることが可能になります。

4.  **`tls.Listen` 関数**:
    `net.Listener` インターフェースを実装するTLSリスナーを作成するための関数です。指定されたネットワークアドレスで着信接続を待ち受け、各接続に対してTLSハンドシェイクを実行します。この関数は、内部で `tls.Config` を使用してTLS接続の設定を行います。

このコミットの核心は、`tls.Listen` が `tls.Config` を検証する際に、`Certificates` フィールドが空であっても `GetCertificate` フィールドが設定されていれば有効な設定とみなすべきである、という点にあります。

## 技術的詳細

`tls.Listen` 関数は、TLSリスナーを初期化する際に、提供された `tls.Config` が有効であるかどうかの基本的なチェックを行います。このチェックの目的は、サーバーがクライアントに提示するための有効な証明書を持っていることを保証することです。

コミット前のコードでは、このチェックは以下の条件で行われていました。
`config == nil || len(config.Certificates) == 0`

これは、「`config` が `nil` であるか、または `config.Certificates` が空である場合、エラーを返す」という意味です。このロジックは、`GetCertificate` コールバックの存在を考慮していませんでした。つまり、`Certificates` が空であっても `GetCertificate` が設定されていれば、サーバーは動的に証明書を提供できるにもかかわらず、`tls.Listen` はそれを認識せず、設定エラーとして扱っていたのです。

このコミットによる変更は、この条件を以下のように修正しました。
`config == nil || (len(config.Certificates) == 0 && config.GetCertificate == nil)`

新しい条件は、「`config` が `nil` であるか、または (`config.Certificates` が空 *かつ* `config.GetCertificate` も `nil` である) 場合、エラーを返す」という意味になります。これにより、`Certificates` が空であっても `GetCertificate` が設定されていれば、全体の条件は `false` となり、`tls.Listen` はエラーを返さずにリスナーの作成に進むことができるようになります。

この変更は、`tls.Listen` の内部的な設定検証ロジックを、`crypto/tls` パッケージ全体の証明書ハンドリングの柔軟性（特にGo 1.5で強化された `GetCertificate` の機能）と整合させるものです。これにより、開発者は `GetCertificate` を利用した動的な証明書管理を `tls.Listen` を通じて直接行えるようになり、より柔軟で効率的なTLSサーバーの実装が可能になります。

## コアとなるコードの解説

変更されたのは、`tls.Listen` 関数の冒頭にある設定検証の `if` 文の条件式と、それに伴うエラーメッセージです。

**変更前:**
```go
if config == nil || len(config.Certificates) == 0 {
    return nil, errors.New("tls.Listen: no certificates in configuration")
}
```
このコードは、`config` が `nil` であるか、または `config.Certificates` スライスが空である場合にエラーを返していました。つまり、`GetCertificate` コールバックが設定されていても、`Certificates` が空であればエラーとなっていました。

**変更後:**
```go
if config == nil || (len(config.Certificates) == 0 && config.GetCertificate == nil) {
    return nil, errors.New("tls: neither Certificates nor GetCertificate set in Config")
}
```
この新しい条件式は、より正確な検証を行います。エラーが返されるのは、以下のいずれかの条件が満たされた場合です。
1.  `config` が `nil` である。
2.  `config.Certificates` が空 *かつ* `config.GetCertificate` も `nil` である。

この変更により、`config.Certificates` が空であっても、`config.GetCertificate` が非 `nil` であれば、`if` 文の条件は `false` となり、`tls.Listen` は正常に処理を続行できるようになります。これは、`GetCertificate` を使用して動的に証明書を提供する意図がある場合に、`tls.Listen` がその意図を正しく解釈し、不必要なエラーを発生させないようにするための重要な修正です。

また、エラーメッセージも「`tls: neither Certificates nor GetCertificate set in Config`」に変更され、`Certificates` と `GetCertificate` の両方が設定されていない場合に問題があることを明確に示しています。

## 変更の背景

このコミットの主な背景は、Go 1.7で導入された`testing.T.Run`および`testing.B.Run`メソッドの準備です。これらのメソッドは、テストやベンチマーク内でさらに小さなテスト（サブテスト）やベンチマーク（サブベンチマーク）を定義し、実行できるようにするために設計されました。

それまでのGoのテストフレームワークでは、各テスト関数は独立して実行され、階層的なテスト構造を表現する直接的な方法がありませんでした。これにより、関連するテストケースをグループ化したり、セットアップ/ティアダウンロジックを共有したりすることが困難でした。同様に、ベンチマークにおいても、異なるシナリオや設定でのベンチマークを効率的に管理する機能が不足していました。

このコミットは、`Run`メソッドの導入に先立ち、既存のテストおよびベンチマーク実行ロジックをリファクタリングし、階層構造をサポートするための内部的な変更を加えています。特に、テストやベンチマークの「ネストの深さ（level）」を管理するフィールドの追加や、ベンチマークのコンテキストを分離するための構造体の導入がその準備段階として行われました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の`testing`パッケージに関する知識が役立ちます。

1.  **`testing`パッケージ**: Go言語の標準ライブラリで、ユニットテストとベンチマークテストをサポートします。
2.  **`*testing.T`**: テスト関数（`func TestXxx(*testing.T)`）に渡される型で、テストの失敗報告、ログ出力、サブテストの実行などの機能を提供します。
3.  **`*testing.B`**: ベンチマーク関数（`func BenchmarkXxx(*testing.B)`）に渡される型で、ベンチマークの実行制御、タイマーのリセット、サブベンチマークの実行などの機能を提供します。
4.  **`common`構造体**: `testing`パッケージ内で`*testing.T`と`*testing.B`が共有する内部的な基底構造体です。テストやベンチマークの名前、親への参照、シグナルチャネルなどの共通情報を保持します。
5.  **サブテスト/サブベンチマーク (Go 1.7以降)**: `t.Run("subtest_name", func(t *testing.T) { ... })`や`b.Run("subbenchmark_name", func(b *testing.B) { ... })`のように、テストやベンチマークの内部でさらにテストやベンチマークを定義・実行できる機能です。これにより、テストの構造化、共通のセットアップ/ティアダウン、特定のテストケースの選択的実行などが容易になります。このコミットは、この機能が導入される前の準備段階です。
6.  **`runtime.GOMAXPROCS`**: Goプログラムが同時に実行できるOSスレッドの最大数を制御する関数です。ベンチマークでは、異なる`GOMAXPROCS`設定でのパフォーマンスを測定するために、この値を変更して実行することがよくあります。

## 技術的詳細

このコミットは、主に`src/testing/testing.go`と`src/testing/benchmark.go`の2つのファイルにわたる内部的なリファクタリングです。

**`src/testing/testing.go`における変更点:**

*   **`common`構造体への`level`フィールドの追加**:
    *   `common`構造体は`*testing.T`と`*testing.B`の両方に埋め込まれているため、この変更はテストとベンチマークの両方に影響します。
    *   `level`フィールドは、テストまたはベンチマークのネストの深さを示す整数です。トップレベルのテスト/ベンチマークは`level=0`、その中のサブテスト/サブベンチマークは`level=1`といった具合に増加します。
    *   これは、サブテスト/サブベンチマークの階層構造を管理し、名前の生成（例: `TestFoo/SubTestBar`）や出力のインデントなどに利用されるための基盤となります。
*   **`t.run`メソッドの導入**:
    *   以前は`RunTests`関数内で直接行われていた個々のテストの実行ロジックが、`(*T).run`という新しいメソッドに抽出されました。
    *   この`t.run`メソッドは、与えられた名前と関数`f`を使ってサブテストとして実行し、成功したかどうかを返します。
    *   このメソッド内で、新しい`*T`インスタンスが作成され、`common`フィールドの`parent`と`level`が適切に設定されます。これにより、サブテストが親テストとの関係性を持ち、階層的なコンテキスト内で実行されるようになります。
    *   `RunTests`関数内のループは、この新しい`t.run`メソッドを呼び出すように変更され、コードの重複が削減され、将来の`T.Run`メソッドへの移行が容易になりました。

**`src/testing/benchmark.go`における変更点:**

*   **`benchContext`構造体の導入**:
    *   `benchContext`は、ベンチマーク実行に関するコンテキスト情報を保持するための新しい構造体です。現時点では`maxLen`（ベンチマーク名の最大長）のみを含みますが、将来的にベンチマークの振る舞いを区別するための中心的な役割を果たすことが意図されています。
    *   `*testing.B`構造体に`context *benchContext`フィールドが追加され、ベンチマークインスタンスがこのコンテキストにアクセスできるようになりました。
*   **`expandCPU`関数の導入**:
    *   以前は`runBenchmarksInternal`関数内に直接記述されていた、異なる`GOMAXPROCS`設定でのベンチマーク実行ロジックが、`expandCPU`という新しい関数に抽出されました。
    *   この関数は、親の`*B`インスタンスと`InternalBenchmark`を受け取り、`cpuList`（異なる`GOMAXPROCS`値のリスト）をイテレートして、それぞれの設定でベンチマークを実行します。
    *   コミットメッセージによると、`expandCPU`は「通常の処理内で呼び出される`Run`メソッドの処理フック」として進化する予定です。
*   **`b.runBench`メソッドの導入**:
    *   `runBenchmarksInternal`関数内で個々のベンチマークを実行していたロジックが、`(*B).runBench`という新しいメソッドに抽出されました。
    *   このメソッドは、与えられた名前と関数`f`を使ってサブベンチマークとして実行し、結果の`*B`インスタンスを返します。
    *   `t.run`と同様に、新しい`*B`インスタンスが作成され、`common`フィールドの`parent`と`level`が設定されます。また、`benchContext`も親から引き継がれます。
    *   コミットメッセージによると、`runBench`は「`Run`メソッドに進化する」予定です。

これらの変更は、既存のテスト/ベンチマーク実行フローを、より汎用的で再利用可能なコンポーネントに分解し、将来の`Run`メソッドがこれらのコンポーネントを呼び出すことで、サブテスト/サブベンチマークの機能を実現できるようにするための基盤を構築しています。

## コアとなるコードの解説

### `src/testing/testing.go`

*   **`common`構造体への`level`フィールド追加**:
    *   `level int // Nesting depth of test or benchmark.`
    *   このフィールドは、テストまたはベンチマークがどの程度の深さでネストされているかを示すために導入されました。`T.Run`や`B.Run`が呼び出されるたびに`level`がインクリメントされ、階層的なテスト構造を追跡できるようになります。これは、テスト名の整形（例: `Parent/Child`）や、将来的なテスト実行の制御に不可欠です。

*   **`(*T).run`メソッドの導入と`RunTests`の変更**:
    *   `func (t *T) run(name string, f func(t *T)) bool`
    *   このメソッドは、特定のテスト関数`f`を`name`という名前のサブテストとして実行するための内部的なヘルパーです。
    *   重要なのは、新しい`*T`インスタンスが作成され、その`common`フィールドの`parent`が現在の`t`の`common`を指し、`level`が`t.level + 1`に設定される点です。これにより、サブテストが親テストのコンテキストを継承し、階層的な関係が確立されます。
    *   `RunTests`関数内のテスト実行ループは、以前はテストインスタンスを直接作成して`tRunner`を呼び出していましたが、このコミットにより`t.run(test.Name, test.F)`を呼び出すように変更されました。これにより、テスト実行ロジックが`(*T).run`に集約され、コードのモジュール性が向上し、将来の`T.Run`メソッドの実装がこの`t.run`を内部的に利用できるようになります。

### `src/testing/benchmark.go`

*   **`benchContext`構造体と`*B`への`context`フィールド追加**:
    *   `type benchContext struct { maxLen int }`
    *   `context *benchContext`
    *   `benchContext`は、ベンチマーク実行全体で共有されるコンテキスト情報をカプセル化するために導入されました。現時点ではベンチマーク名の最大長`maxLen`のみを保持していますが、これはベンチマーク出力の整形に利用されます。将来的に、ベンチマークの振る舞いを制御するためのより多くの情報がここに追加される可能性があります。`*B`にこのコンテキストへのポインタが追加されたことで、すべてのベンチマークインスタンスが共通のコンテキストにアクセスできるようになります。

*   **`expandCPU`関数の導入と`runBenchmarksInternal`の変更**:
    *   `func expandCPU(parent *B, Benchmark InternalBenchmark) bool`
    *   この関数は、与えられた`InternalBenchmark`を、`cpuList`で定義された異なる`GOMAXPROCS`設定で実行するロジックをカプセル化します。
    *   以前は`runBenchmarksInternal`内に直接あったこのループが`expandCPU`に「吊り上げ」られたことで、`runBenchmarksInternal`のコードが簡潔になり、`expandCPU`が独立した再利用可能なコンポーネントとして機能するようになりました。
    *   `expandCPU`は、各`GOMAXPROCS`設定で`parent.runBench`を呼び出し、実際のベンチマーク実行を委譲します。

*   **`(*B).runBench`メソッドの導入**:
    *   `func (b *B) runBench(name string, f func(b *B)) *B`
    *   このメソッドは、特定のベンチマーク関数`f`を`name`という名前のサブベンチマークとして実行するための内部的なヘルパーです。
    *   `(*T).run`と同様に、新しい`*B`インスタンスが作成され、その`common`フィールドの`parent`と`level`が設定されます。また、親の`benchContext`も新しいサブベンチマークに引き継がれます。
    *   このメソッドは、サブベンチマークの実行ロジックを抽象化し、将来の`B.Run`メソッドがこの`runBench`を内部的に利用できるようにするための重要なステップです。

これらの変更は、Goの`testing`パッケージがより柔軟で強力なテスト・ベンチマークフレームワークへと進化するための、重要な内部的な基盤整備と言えます。

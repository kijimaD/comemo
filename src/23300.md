# [インデックス 23300] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/ld`) の内部パッケージである `src/cmd/internal/ld/data.go` ファイルに対する変更です。`data.go` は、Goプログラムのリンク処理において、データセクションの配置やシンボルの処理など、ELF (Executable and Linkable Format) 形式の実行ファイルを生成する際の重要な役割を担っています。具体的には、リロケーション情報を含むセクションの管理に関わる部分が変更されています。

## コミット

`cmd/ld`: `.rela` および `.rela.plt` セクションを連続させる

ELFは通常これを要求しており、Solarisのランタイムローダーはこれを行わないとクラッシュする。

Solarisビルドを修正。

## 変更の背景

この変更の主な背景は、Go言語でビルドされたプログラムがSolarisオペレーティングシステム上で正しく動作しないという問題の解決です。具体的には、Solarisのランタイムローダーが、ELF実行ファイル内の特定のリロケーションセクション（`.rela` と `.rela.plt`）が連続して配置されていることを要求するという、ELFのABI (Application Binary Interface) の厳格な解釈に起因していました。

Goのリンカ (`cmd/ld`) は、それまでこれらのセクションを連続して配置していなかったため、Solaris上でプログラムをロードしようとするとランタイムローダーがクラッシュしていました。このコミットは、このSolaris固有の要件を満たすようにリンカの挙動を修正し、Solaris上でのGoプログラムのビルドと実行を可能にすることを目的としています。

## 前提知識の解説

### ELF (Executable and Linkable Format)

ELFは、Unix系オペレーティングシステム（Linux, Solaris, BSDなど）で広く使用されている、実行可能ファイル、オブジェクトファイル、共有ライブラリ、コアダンプファイルの標準的なファイル形式です。プログラムのコード、データ、シンボル、リロケーション情報などが構造化されて格納されています。

### リンカ (Linker) と Goの `cmd/ld`

リンカは、コンパイラによって生成された複数のオブジェクトファイルやライブラリを結合し、最終的な実行可能ファイルや共有ライブラリを生成するツールです。Go言語では、`cmd/ld` がGoプログラム専用のリンカとして機能します。`cmd/ld` は、Goの特殊なランタイム要件やクロスコンパイルのニーズに合わせて設計されており、生成されるバイナリの構造を決定します。

### リロケーション (Relocation)

リロケーションとは、プログラムがメモリにロードされる際に、コードやデータ内のアドレス参照を修正するプロセスです。コンパイル時には、関数呼び出しやグローバル変数へのアクセスのアドレスは最終的なものではなく、相対アドレスやプレースホルダーが使用されます。リンカやランタイムローダーは、これらのプレースホルダーを実際のメモリ上のアドレスに置き換えることで、プログラムが正しく実行できるようにします。

### .rela, .rel.plt, .rela.plt セクション

ELFファイルには、リロケーション情報を格納するための特別なセクションがあります。
*   **`.rel` および `.rela`**: これらは一般的なリロケーション情報を格納するセクションです。`.rel` は加算を伴わないリロケーションエントリを、`.rela` は加算を伴うリロケーションエントリを格納します。Goのリンカは通常 `.rela` 形式を使用します。これらのセクションは、プログラム内のデータやコードが、他のモジュールやライブラリのシンボルを参照する際のアドレス解決に使用されます。
*   **`.rel.plt` および `.rela.plt`**: これらはPLT (Procedure Linkage Table) のリロケーションに特化したセクションです。動的リンクされた共有ライブラリの関数を呼び出す際に必要となる情報を含んでいます。

### PLT (Procedure Linkage Table) と GOT (Global Offset Table)

動的リンクされたプログラムが共有ライブラリの関数を呼び出す際、その関数のアドレスは実行時まで確定しません。これを解決するために、PLTとGOTが使用されます。
*   **PLT (Procedure Linkage Table)**: 共有ライブラリ内の関数を呼び出すための小さなコードの断片です。最初の呼び出し時には、GOTを介してランタイムローダーに制御を渡し、実際のアドレスを解決させます。
*   **GOT (Global Offset Table)**: 共有ライブラリ内の関数やデータのアドレスを格納するテーブルです。PLTはGOTを参照し、GOTに格納されたアドレスを使って共有ライブラリの関数にジャンプします。

### Solaris Runtime Loader

Solarisのランタイムローダーは、ELF標準に対して非常に厳格な解釈と実装を持つことで知られています。他のUnix系システム（Linuxなど）では許容されるようなELFファイルの構造でも、Solarisではエラーとなる場合があります。このコミットのケースでは、`.rela` と `.rela.plt` セクションの連続性がその厳格な要件の一つでした。

## 技術的詳細

このコミットが対処している技術的な問題は、ELFのABIにおけるリロケーションセクションの配置に関する特定の要件です。一般的に、ELF仕様自体は `.rela` と `.rela.plt` のような異なるリロケーションセクションが物理的に連続していることを厳密には要求していません。しかし、Solarisのランタイムローダーは、これらのセクションがメモリ上で連続して配置されていることを期待します。これは、ローダーがリロケーション情報を処理する際に、特定の最適化や簡略化されたアルゴリズムを使用しているためと考えられます。

Goのリンカは、これまでこれらのセクションを必ずしも連続して配置していませんでした。その結果、Solaris上でGoのバイナリをロードしようとすると、ランタイムローダーが期待する構造と実際のバイナリの構造が一致せず、不正なメモリアクセスや処理ロジックの不整合が発生し、最終的にクラッシュに至っていました。

この修正は、GoのリンカがELFバイナリを生成する際に、`.rela` (または `.rel`) セクションの直後に `.rela.plt` (または `.rel.plt`) セクションを強制的に配置するように変更することで、Solarisのランタイムローダーの要件を満たします。これにより、Solaris上でもGoプログラムが正しくロードされ、実行できるようになります。

## コアとなるコードの変更箇所

変更は `src/cmd/internal/ld/data.go` ファイルの `dodata()` 関数内に追加されています。

```diff
--- a/src/cmd/internal/ld/data.go
+++ b/src/cmd/internal/ld/data.go
@@ -1267,6 +1267,27 @@ func dodata() {
 
 	datap = listsort(datap, datcmp, listnextp)
 
+	if Iself {
+		// Make .rela and .rela.plt contiguous, the ELF ABI requires this
+		// and Solaris actually cares.
+		var relplt *LSym
+		for l = &datap; *l != nil; l = &(*l).Next {
+			if (*l).Name == ".rel.plt" || (*l).Name == ".rela.plt" {
+				relplt = (*l)
+				*l = (*l).Next
+				break
+			}
+		}
+		if relplt != nil {
+			for s = datap; s != nil; s = s.Next {
+				if s.Name == ".rel" || s.Name == ".rela" {
+					relplt.Next = s.Next
+					s.Next = relplt
+				}
+			}
+		}
+	}
+
 	/*
 	 * allocate sections.  list is sorted by type,
 	 * so we can just walk it for each piece we want to emit.
```

## コアとなるコードの解説

追加されたコードブロックは、`Iself` というフラグが真（つまり、ELF形式のバイナリを生成する場合）である場合にのみ実行されます。

1.  **`.rel.plt` または `.rela.plt` セクションの検索と抽出**:
    *   `var relplt *LSym` で `relplt` という `LSym` (リンカシンボル) 型のポインタを宣言します。これは `.rel.plt` または `.rela.plt` セクションへの参照を保持するために使われます。
    *   `for l = &datap; *l != nil; l = &(*l).Next { ... }` ループは、リンカが管理するシンボルリスト `datap` を走査します。`datap` は、Goのリンカが処理するすべてのセクションやシンボルを含むリストです。
    *   `if (*l).Name == ".rel.plt" || (*l).Name == ".rela.plt"` の条件で、現在のシンボルが `.rel.plt` または `.rela.plt` セクションであるかをチェックします。
    *   該当するセクションが見つかった場合、`relplt = (*l)` でそのセクションへのポインタを `relplt` に保存します。
    *   `*l = (*l).Next` によって、リストからそのセクションを削除します。これにより、一時的に `.rel.plt` または `.rela.plt` がリストから切り離されます。
    *   `break` でループを終了します。

2.  **`.rel` または `.rela` セクションの直後への挿入**:
    *   `if relplt != nil { ... }` は、`.rel.plt` または `.rela.plt` セクションが見つかり、抽出された場合にのみ実行されます。
    *   `for s = datap; s != nil; s = s.Next { ... }` ループは、再びシンボルリスト `datap` を走査します。
    *   `if s.Name == ".rel" || s.Name == ".rela"` の条件で、現在のシンボルが `.rel` または `.rela` セクションであるかをチェックします。
    *   該当するセクションが見つかった場合、以下の操作で `relplt` をその直後に挿入します。
        *   `relplt.Next = s.Next`: `relplt` の次のポインタを、`.rel` または `.rela` の現在の次のシンボルに設定します。
        *   `s.Next = relplt`: `.rel` または `.rela` の次のポインタを `relplt` に設定します。
    *   これにより、`.rel` または `.rela` の直後に `relplt` が挿入され、両セクションが連続するようになります。

このロジックにより、GoのリンカはELFバイナリを生成する際に、Solarisのランタイムローダーが要求する `.rela` と `.rela.plt` セクションの連続性を保証します。

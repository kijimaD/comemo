# [インデックス 26452] ファイルの概要

このコミットは、Goの `net/http` パッケージにおいて、HTTP/2トランスポートが `http.Request` オブジェクトへの参照を不必要に保持し、ガベージコレクション（GC）を妨げていた問題を修正します。これにより、HTTP/2を使用するクライアントアプリケーションでメモリリークが発生する可能性がありました。具体的には、`Transport` の `RoundTrip` メソッド内で、HTTP/2パスにおいて `Request` オブジェクトのキャンセラー設定を `nil` にすることで、参照が解放され、GCが可能になります。

## 変更の背景

この変更は、Goの `net/http` パッケージにおける `Transport` のHTTP/2実装が、完了した `http.Request` オブジェクトへの参照を不適切に保持してしまうという問題（Issue #14084）を解決するために行われました。

通常、HTTPリクエストが完了し、その `http.Request` オブジェクトが不要になった場合、Goのガベージコレクタによってメモリが解放されるべきです。しかし、HTTP/2を使用する際に `Transport` が `http.Request` オブジェクトへの参照を内部的に保持し続けてしまうと、そのオブジェクトはガベージコレクションの対象とならず、メモリリークを引き起こす可能性がありました。特に、多数のHTTP/2リクエストを連続して行うようなアプリケーションでは、この問題が顕著になり、時間とともにメモリ使用量が増大する原因となります。

このコミットは、HTTP/2パスにおいて `http.Request` オブジェクトが不要になった時点で、`Transport` が保持するそのオブジェクトへの参照を明示的に解除することで、このメモリリークを防止することを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC) と `runtime.SetFinalizer`

Goは自動メモリ管理（ガベージコレクション）を採用しており、開発者が手動でメモリを解放する必要はありません。ガベージコレクタは、どのオブジェクトも参照されなくなったと判断すると、そのオブジェクトが占めていたメモリを自動的に解放します。

`runtime.SetFinalizer` は、Goの標準ライブラリ `runtime` パッケージが提供する関数で、特定のオブジェクトがガベージコレクションされる直前に実行される関数（ファイナライザ）を設定するために使用されます。このファイナライザは、オブジェクトがメモリから解放される前に、リソースのクリーンアップ（例：ファイルハンドルのクローズ、ネットワーク接続の切断など）を行うのに役立ちます。このコミットで追加されたテストコードでは、`runtime.SetFinalizer` を使用して `http.Request` オブジェクトがGCされたことを検出しています。

### `net/http` パッケージの `Transport` と `RoundTrip` メソッド

`net/http` パッケージは、GoでHTTPクライアントとサーバーを構築するための主要なパッケージです。
`http.Client` はHTTPリクエストを送信するためのクライアントであり、その内部で `http.RoundTripper` インターフェースを実装する `Transport` を使用して実際のネットワーク通信を行います。

`http.Transport` は、HTTPリクエストの送信、レスポンスの受信、接続の再利用、プロキシの処理などを担当します。`RoundTrip` メソッドは `http.RoundTripper` インターフェースの唯一のメソッドであり、`http.Request` を受け取り、`http.Response` を返す役割を担います。このメソッド内で、HTTP/1.1とHTTP/2のどちらを使用するかに応じて異なる処理パスが実行されます。

### HTTP/1 と HTTP/2 の違い、特に `Transport` における処理の違い

*   **HTTP/1.1**: 1つのTCP接続につき1つのリクエスト/レスポンスが基本です（パイプライン処理はありますが、ヘッドオブラインブロッキングの問題があります）。`Transport` は接続プールを管理し、リクエストごとに接続を再利用します。
*   **HTTP/2**: 1つのTCP接続上で複数のリクエスト/レスポンスを多重化（multiplexing）できます。これにより、ヘッドオブラインブロッキングが解消され、パフォーマンスが向上します。`Transport` はHTTP/2の接続管理とストリーム管理を内部的に行います。

このコミットの問題は、特にHTTP/2のパスで発生していました。HTTP/2の内部処理において、`Transport` が `http.Request` オブジェクトへの参照を、リクエスト処理が完了した後も不必要に保持し続けていたことが原因です。

### `http.Request` のライフサイクル

`http.Request` オブジェクトは、クライアントがHTTPリクエストを構築する際に作成され、`http.Client.Do` や `http.Transport.RoundTrip` メソッドに渡されます。リクエストが送信され、レスポンスが受信されると、通常は `http.Request` オブジェクトは役割を終え、ガベージコレクションの対象となるべきです。しかし、内部的な参照が残っていると、GCされずにメモリ上に残り続けます。

### `CancelRequest` メソッドの役割と非推奨化の背景

`http.Transport.CancelRequest` メソッドは、進行中のHTTPリクエストをキャンセルするために使用されていました。これは、リクエストに関連付けられたネットワーク接続を閉じることでキャンセルを実現します。しかし、このメソッドはいくつかの問題がありました。

1.  **粒度の粗さ**: 接続全体を閉じるため、同じ接続を共有する他のリクエストも影響を受ける可能性がありました。
2.  **HTTP/2との非互換性**: HTTP/2では1つの接続で複数のストリーム（リクエスト）を多重化するため、接続を閉じるだけでは特定のリクエストを適切にキャンセルできません。HTTP/2では、個々のストリームをキャンセルするメカニズムが必要です。
3.  **`context` パッケージの登場**: Go 1.7で導入された `context` パッケージは、リクエストのキャンセル、タイムアウト、デッドラインの設定など、リクエストスコープの値を伝播するためのより汎用的で強力なメカニズムを提供します。`context` を使用することで、`CancelRequest` よりも柔軟かつ安全にリクエストをキャンセルできるようになりました。

このコミットの変更点にもあるように、`CancelRequest` は「Deprecated: Use Request.Cancel instead. CancelRequest can not cancel HTTP/2 requests.」とコメントが更新され、HTTP/2リクエストをキャンセルできないことが明記されています。これは、`context` パッケージの利用を推奨し、`CancelRequest` がHTTP/2の設計と合致しないことを示しています。

## 技術的詳細

このコミットの核心は、`net/http` パッケージの `Transport` が、HTTP/2プロトコルでリクエストを処理する際に、`http.Request` オブジェクトへの内部参照を不必要に保持していた点にあります。

`http.Transport` は、リクエストのキャンセルを管理するために `reqCanceler` という内部マップを使用しています。このマップは `map[*Request]chan struct{}` のような構造で、`*Request` をキーとして、そのリクエストのキャンセルを通知するためのチャネルを値として保持します。`Transport.RoundTrip` メソッドがリクエストを受け取ると、このマップにエントリを追加し、`CancelRequest` メソッドが呼び出されたときにそのチャネルをクローズすることでリクエストをキャンセルします。

問題は、HTTP/2のパスでは `CancelRequest` メソッドが機能しない（または意図されていない）にもかかわらず、`reqCanceler` マップに `*http.Request` への参照が追加されたままになっていたことです。HTTP/2では、リクエストのキャンセルは `context` パッケージを通じて行われるべきであり、`Transport` の `CancelRequest` メカニズムはHTTP/2リクエストには適用されません。

したがって、HTTP/2リクエストが完了しても、`reqCanceler` マップ内の `*http.Request` への参照が残り続け、その `http.Request` オブジェクトがガベージコレクションの対象から外れてしまっていました。これにより、リクエストオブジェクトがメモリ上に残り続け、メモリリークが発生していました。

このコミットでは、HTTP/2パスに入った直後に `t.setReqCanceler(req, nil)` を呼び出すことで、この問題を解決しています。`setReqCanceler` は `reqCanceler` マップを操作する内部ヘルパー関数であり、`nil` を渡すことで、指定された `req` (つまり現在の `http.Request` オブジェクト) に関連付けられたキャンセラーエントリをマップから削除します。これにより、HTTP/2パスで処理される `http.Request` オブジェクトは、`Transport` の内部マップから参照されなくなり、リクエスト処理完了後に適切にガベージコレクションされるようになります。

## コアとなるコードの解説

### `src/net/http/transport.go` の変更

*   **`t.setReqCanceler(req, nil)` の追加**:
    `Transport.RoundTrip` メソッド内で、`pconn.alt != nil` の条件分岐はHTTP/2接続が使用されていることを示します。このHTTP/2パスに入った直後に `t.setReqCanceler(req, nil)` が呼び出されます。
    `setReqCanceler` は `Transport` の内部マップ `reqCanceler` を操作する関数です。`req` (現在の `http.Request` オブジェクト) をキーとして、`nil` を値として渡すことで、`reqCanceler` マップからこの `http.Request` に関連付けられたエントリを削除します。
    これにより、HTTP/2リクエストが処理されている間、`Transport` は `http.Request` オブジェクトへの不要な参照を保持しなくなり、リクエスト完了後に `http.Request` オブジェクトが適切にガベージコレクションされるようになります。

*   **`CancelRequest` メソッドのコメント更新**:
    `CancelRequest` メソッドのドキュメンテーションコメントが更新され、「Deprecated: Use Request.Cancel instead. CancelRequest can not cancel HTTP/2 requests.」という記述が追加されました。これは、`CancelRequest` がHTTP/2リクエストに対しては機能しないことを明確にし、`context` パッケージを使用したキャンセルメカニズムへの移行を促すものです。この変更は、上記の `setReqCanceler` の追加と合わせて、HTTP/2におけるリクエストキャンセルの正しいアプローチを強調しています。

### `src/net/http/clientserver_test.go` の変更

*   **`TestTransportGCRequest_h1` と `TestTransportGCRequest_h2` の追加**:
    このコミットでは、`Transport` が `http.Request` オブジェクトへの参照を保持しないことを検証するための新しいテスト関数 `testTransportGCRequest` が追加されました。このテストは、HTTP/1 (`h1Mode`) と HTTP/2 (`h2Mode`) の両方で実行されます。

*   **`testTransportGCRequest` 関数の詳細**:
    1.  **テストサーバーのセットアップ**: `newClientServerTest` を使用して、簡単なHTTPサーバーとクライアントをセットアップします。サーバーはリクエストボディを読み込み、「Hello.」を返します。
    2.  **`runtime.SetFinalizer` の設定**: 匿名関数内で `http.NewRequest` を使用して `req` オブジェクトを作成します。この `req` オブジェクトに対して `runtime.SetFinalizer` を設定します。ファイナライザは、`req` がガベージコレクションされるときに `didGC` チャネルをクローズするようになっています。
    3.  **リクエストの実行**: `cst.c.Do(req)` を呼び出してHTTPリクエストを送信し、レスポンスを処理します。リクエストとレスポンスのボディを読み込み、クローズします。この匿名関数が終了すると、`req` オブジェクトへの直接的な参照はなくなります。
    4.  **GCの待機と強制**: `for` ループ内で、`didGC` チャネルがクローズされるのを待ちます。`time.After` を使用して100ミリ秒ごとに `runtime.GC()` を明示的に呼び出し、ガベージコレクションを強制的に実行します。これにより、`req` オブジェクトがGCされる機会を与えます。
    5.  **タイムアウト**: 5秒のタイムアウトを設定し、その間に `req` オブジェクトがGCされなかった場合はテストを失敗させます。

このテストは、`http.Request` オブジェクトがリクエスト処理完了後に適切にGCされることを、`runtime.SetFinalizer` を用いて間接的に検証する非常に効果的な方法です。特に `TestTransportGCRequest_h2` は、HTTP/2パスにおけるメモリリーク修正が正しく機能していることを保証します。

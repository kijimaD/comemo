## 元コミット内容

`cmd/doc: the builtin package should always show unexported symbols`

このコミットは、`cmd/doc` ツールが `builtin` パッケージのドキュメントを生成する際に、通常は非表示となる非公開シンボル（unexported symbols）も常に表示するように修正するものです。これは「些細な修正」とされており、`builtin` パッケージに対して `unexported=true` を設定することで実現されます。`Godoc` 自体も同様のハックを使用していることが言及されています。

この変更は Issue #12541 を修正するものです。

## 変更の背景

Go言語では、通常、パッケージのドキュメントを生成する際に、外部からアクセス可能な公開シンボル（exported symbols）のみが表示され、パッケージ内部でのみ使用される非公開シンボル（unexported symbols）は表示されません。これは、APIの利用者に不要な詳細を隠蔽し、ドキュメントを簡潔に保つための一般的な慣習です。

しかし、`builtin` パッケージはGo言語のランタイムに組み込まれた基本的な型や関数（例: `int`, `bool`, `make`, `new`, `panic` など）を定義しており、その性質上、これらのシンボルはGo言語の基本的な動作を理解するために非常に重要です。これらのシンボルの中には、Go言語の仕様上は非公開として扱われるものもありますが、その存在と機能は開発者にとって不可欠な情報です。

従来の `cmd/doc` の動作では、`builtin` パッケージの非公開シンボルがドキュメントから除外されてしまい、Go言語のコアな要素に関する情報が不足するという問題がありました。このコミットは、この情報不足を解消し、`builtin` パッケージのドキュメントがより完全なものとなるように、非公開シンボルも表示するよう変更されました。これは、Go言語の学習者や開発者が `builtin` パッケージの全容を正確に把握できるようにするための重要な改善です。

## 前提知識の解説

*   **`cmd/doc` (godoc)**: Go言語の公式ドキュメンテーションツールです。Goのソースコードからコメントを解析し、HTML形式やプレーンテキスト形式でパッケージのドキュメントを生成します。開発者がGoのパッケージやAPIの情報を参照する際に広く利用されます。
*   **`builtin` パッケージ**: Go言語のランタイムに組み込まれている特別なパッケージです。Go言語の基本的な型（`int`, `string`, `bool` など）、組み込み関数（`make`, `new`, `len`, `cap`, `panic`, `recover` など）、および定数（`true`, `false`, `iota` など）を定義しています。このパッケージは明示的にインポートする必要がなく、常に利用可能です。
*   **公開シンボル (Exported Symbols)**: Go言語では、識別子（変数名、関数名、型名など）の最初の文字が大文字で始まる場合、そのシンボルはパッケージ外からアクセス可能な「公開シンボル」となります。
*   **非公開シンボル (Unexported Symbols)**: 識別子の最初の文字が小文字で始まる場合、そのシンボルはパッケージ内でのみアクセス可能な「非公開シンボル」となります。通常、ドキュメントツールは非公開シンボルを隠蔽します。
*   **ドキュメンテーション生成**: ソースコード内のコメントや構造から、自動的にAPIリファレンスなどのドキュメントを作成するプロセスです。Goの `godoc` はこの典型的な例です。

## 技術的詳細

`cmd/doc` ツールは、Goのソースコードを解析し、パッケージ構造、型、関数、変数などの情報を抽出します。この際、通常は公開シンボルのみを対象としてドキュメントを生成します。これは、内部実装の詳細を隠蔽し、ユーザーがAPIの利用に集中できるようにするためです。

しかし、`builtin` パッケージは特殊な存在です。このパッケージに含まれるシンボルの中には、Go言語の仕様上は非公開（小文字で始まる）として扱われるものの、その機能や存在がGo言語の基本的な動作に不可欠であり、開発者にとって知るべき情報であるものが多数存在します。例えば、`error` インターフェースや `nil` などは、Go言語の根幹をなす要素ですが、これらが通常の非公開シンボルとして扱われると、ドキュメントから漏れてしまいます。

このコミットでは、`cmd/doc` の内部ロジックにフックを追加し、現在処理しているパッケージが `builtin` パッケージであるかどうかをチェックします。もし `builtin` パッケージであれば、ドキュメント生成の際に「非公開シンボルも表示する」というフラグ（`unexported`）を強制的に `true` に設定します。これにより、`builtin` パッケージ内のすべてのシンボル（公開・非公開問わず）がドキュメントに含められるようになります。

このアプローチは、`builtin` パッケージの特殊性を認識し、通常のドキュメンテーションルールを一時的に緩和することで、そのパッケージの完全な情報を提供することを目的としています。コミットメッセージで「Godoc itself has a similar hack」と述べられているように、これは `godoc` ツールが `builtin` パッケージを特別扱いする既存の慣習に沿ったものです。

## コアとなるコードの解説

追加されたコードは非常にシンプルですが、その影響は大きいです。

1.  `if pkg.build.ImportPath == "builtin" { ... }`:
    *   この条件文は、現在 `cmd/doc` が処理しているパッケージのインポートパスが `"builtin"` であるかどうかをチェックします。`pkg.build.ImportPath` は、解析中のパッケージの完全なインポートパス（例: `"fmt"`, `"net/http"`, `"builtin"`）を保持しています。
    *   もし現在のパッケージが `builtin` であれば、条件が真となり、ブロック内のコードが実行されます。

2.  `unexported = true`:
    *   この行が、このコミットの核心です。`unexported` は `cmd/doc` ツール内で使用されるグローバルな（またはスコープ内の）フラグ変数であると推測されます。このフラグは、ドキュメント生成時に非公開シンボルを含めるかどうかを制御します。
    *   通常、このフラグはコマンドライン引数（例: `godoc -unexported`）によって設定されるか、デフォルトで `false` になっています。しかし、`builtin` パッケージの場合に限り、このフラグを強制的に `true` に設定することで、非公開シンボルもドキュメントに表示されるようになります。

この変更により、`cmd/doc` は `builtin` パッケージに対してのみ、通常のドキュメント生成ルールをオーバーライドし、すべてのシンボルを網羅的に表示するようになります。これにより、Go言語の基本的な要素に関するドキュメントの完全性が向上しました。

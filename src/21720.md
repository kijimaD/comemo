# [インデックス 21720] ファイルの概要

このコミットは、Go言語のツールチェイン（具体的にはアセンブラ `cmd/5a`、コンパイラ `cmd/5g`、リンカ `cmd/5l`、および `liblink`）における `Prog` および `Addr` 型のポータビリティ（移植性）を向上させるための変更です。これにより、これらの型が特定のアーキテクチャに依存しない、より汎用的な表現を持つようになります。

## 変更の背景

Go言語は、その設計当初からクロスコンパイルとマルチアーキテクチャサポートを重視してきました。しかし、初期のツールチェインの実装では、アセンブラ、コンパイラ、リンカが内部的に使用する命令（`Prog`）やアドレス（`Addr`）の表現が、特定のCPUアーキテクチャ（この場合はARMアーキテクチャ、`5`はARMを指す）に強く結びついている部分がありました。

このようなアーキテクチャ固有の表現は、新しいアーキテクチャのサポートを追加する際に、ツールチェインの各コンポーネントで同様の変更を繰り返す必要があり、開発のオーバーヘッドとなっていました。また、コードの再利用性や保守性も低下させます。

このコミットの背景には、Goツールチェインの内部構造をより抽象化し、アーキテクチャ非依存な設計へと移行させるという、より大きな目標がありました。これにより、将来的な新しいアーキテクチャへの対応が容易になり、ツールチェイン全体の堅牢性と拡張性が向上します。特に、`Prog`と`Addr`は、アセンブラが生成する命令やリンカが扱うシンボルアドレスの基本的な構成要素であるため、これらをポータブルにすることは、ツールチェインの基盤を強化する上で不可欠なステップでした。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の内部構造とツールチェインに関する知識が必要です。

1.  **Goツールチェインの構成要素**:
    *   **`cmd/5a` (アセンブラ)**: Goのアセンブリ言語（Plan 9アセンブリに似ている）を機械語に変換します。`5`はARMアーキテクチャを指します。
    *   **`cmd/5g` (コンパイラ)**: Goのソースコードをアセンブリコード（またはオブジェクトファイル）に変換します。
    *   **`cmd/5l` (リンカ)**: オブジェクトファイルを結合し、実行可能ファイルを生成します。
    *   **`liblink`**: リンカの共通ライブラリであり、アーキテクチャに依存しないリンキングのロジックを提供します。

2.  **`Prog` 型**:
    *   `Prog`は"Program"の略で、Goツールチェインの内部で命令を表す構造体です。アセンブラがアセンブリコードを解析して生成し、コンパイラがGoコードから生成する中間表現の一部でもあります。リンカはこれらの`Prog`オブジェクトを操作して最終的なバイナリを生成します。
    *   初期の`Prog`型は、特定のアーキテクチャの命令セットの特性を直接反映している部分がありました。例えば、ARMアーキテクチャの命令には、条件コードやシフト操作など、他のアーキテクチャにはない特有のフィールドが存在します。

3.  **`Addr` 型**:
    *   `Addr`は"Address"の略で、Goツールチェインの内部でメモリアドレスやシンボル参照を表す構造体です。命令のオペランドとして使用されることが多く、レジスタ、オフセット、シンボルへの参照など、様々な種類のアドレス指定モードを表現します。
    *   `Addr`型もまた、特定のアーキテクチャのアドレス指定モードに強く依存している部分がありました。例えば、ARMのロード/ストア命令には、ベースレジスタ、インデックスレジスタ、オフセット、プリ/ポストインクリメントなどの複雑なアドレス指定モードがあります。

4.  **Plan 9ツールチェインの影響**:
    *   Goの初期のツールチェインは、Bell LabsのPlan 9オペレーティングシステムのツールチェイン（`8a`, `8g`, `8l`など）から大きな影響を受けています。Plan 9のツールチェインは、シンプルでモジュール化された設計が特徴で、Goもその哲学を受け継いでいます。しかし、Plan 9のツールチェインは、Goがサポートする多様なアーキテクチャや現代的な言語機能に対応するために進化する必要がありました。

5.  **ポータビリティ（移植性）**:
    *   ソフトウェアが異なるハードウェアプラットフォームやオペレーティングシステム上で動作する能力を指します。Goツールチェインの文脈では、`Prog`や`Addr`のような内部データ構造が、ARM、x86、x86-64、MIPSなど、様々なCPUアーキテクチャ間で共通の表現を持つことを意味します。これにより、アーキテクチャ固有のロジックを最小限に抑え、ツールチェインのコードベースをよりクリーンで保守しやすくすることができます。

これらの型をポータブルにするということは、アーキテクチャ固有の情報をこれらの型から分離し、必要に応じてアーキテクチャ固有のコードで処理するように変更することを意味します。これにより、共通のコードベースでより多くのアーキテクチャをサポートできるようになります。

## 技術的詳細

このコミットの技術的な核心は、`Prog`と`Addr`構造体からアーキテクチャ固有のフィールドを抽象化し、より汎用的な表現に置き換えることです。具体的には、ARMアーキテクチャのアセンブラ（`cmd/5a`）とリンカ（`liblink`）のコードが大幅に変更されています。

変更の主なポイントは以下の通りです。

1.  **`Addr`型のフィールド名の変更と抽象化**:
    *   コミットの差分を見ると、`D_CONST`, `D_OREG`, `D_REG`, `D_FREG`, `D_BRANCH`, `D_SCONST`, `D_FCONST`, `D_REGREG2`, `D_SHIFT`といった定数（おそらく`Addr`型の`type`フィールドの値を定義するもの）が、`TYPE_CONST`, `TYPE_MEM`, `TYPE_REG`, `TYPE_BRANCH`, `TYPE_SCONST`, `TYPE_FCONST`, `TYPE_REGREG2`, `TYPE_SHIFT`といったより汎用的な名前に変更されています。
    *   同様に、`D_AUTO`, `D_EXTERN`, `D_PARAM`, `D_STATIC`といったシンボルタイプを示す定数も、`NAME_AUTO`, `NAME_EXTERN`, `NAME_PARAM`, `NAME_STATIC`に変更されています。
    *   これは、これらの定数が単なる「データ型」や「アドレス指定モード」ではなく、より抽象的な「型」や「名前」を表現するように意図されていることを示唆しています。これにより、異なるアーキテクチャがそれぞれ独自のアドレス指定モードを持っていても、共通の`Addr`型でそれらを表現できるようになります。

2.  **`outcode`関数の引数変更**:
    *   `src/cmd/5a/a.y`の変更を見ると、`outcode`関数（アセンブリ命令をエンコードする関数）の引数から`NREG`が削除され、`0`に置き換えられています。
    *   `outcode($1, $2, &$3, NREG, &$5);` が `outcode($1, $2, &$3, 0, &$5);` に変更されています。
    *   `NREG`は通常、"No Register"を意味する定数で、特定のレジスタが使用されない場合にプレースホルダーとして使われていました。これを`0`に置き換えることで、`outcode`関数がレジスタに関するアーキテクチャ固有の知識を直接持つことを避け、より汎用的な命令エンコードロジックに集中できるようにしています。これは、レジスタの概念がアーキテクチャによって異なるため、ポータビリティを高めるための重要なステップです。

3.  **レジスタ定義の抽象化**:
    *   `src/cmd/5a/lex.c`では、`R0`から`R15`、`F0`から`F15`などのレジスタ定義が、具体的な数値（0, 1, ...）から`REG_R0`, `REG_R1`, ..., `REG_F0`, `REG_F1`, ...といったシンボリック定数に置き換えられています。
    *   `CPSR`, `SPSR`, `FPSR`, `FPCR`といった特殊レジスタも同様に`REG_CPSR`, `REG_SPSR`, `REG_FPSR`, `REG_FPCR`に変更されています。
    *   これにより、レジスタの実際の数値マッピングがアーキテクチャ固有のヘッダーファイルや定義に委ねられ、アセンブラの字句解析器（lexer）はレジスタ名を抽象的に扱うことができるようになります。

4.  **`nullgen`の初期化変更**:
    *   `src/cmd/5a/lex.c`の`cinit`関数で、`nullgen`（`Addr`型のゼロ値）の初期化が`nullgen.type = D_NONE; nullgen.name = D_NONE; nullgen.reg = NREG;`から`nullgen.type = TYPE_NONE; nullgen.name = NAME_NONE;`に変更されています。
    *   `nullgen.reg = NREG;`が削除されたのは、`NREG`がアーキテクチャ固有のレジスタ概念に結びついていたため、よりポータブルな`Addr`型では不要になったことを示しています。

5.  **Yacc/Bison文法ファイルの変更**:
    *   `src/cmd/5a/a.y`と`src/cmd/5a/y.tab.c`は、アセンブラの文法定義ファイルと、それから生成されたCコードです。これらのファイルが変更されているのは、`Prog`や`Addr`型の内部表現の変更に伴い、アセンブリ命令の解析ロジックも更新されたためです。特に、`y.tab.c`の変更は、文法規則の数や状態数がわずかに減少していることから、文法がよりシンプルになったか、あるいは特定のアーキテクチャ固有の規則が抽象化されたことを示唆しています。

これらの変更は、Goツールチェインの内部で命令とアドレスを表現する方法を、特定のCPUアーキテクチャから切り離し、より抽象的で汎用的なものにすることで、将来的な拡張性と保守性を高めることを目的としています。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、主に以下のファイル群に集中しています。

*   `src/cmd/5a/a.y`: ARMアセンブラのYacc文法定義ファイル。`Prog`と`Addr`の内部表現の変更に伴い、命令の解析規則が更新されています。特に、`outcode`関数の呼び出しにおける`NREG`の削除と、`Addr`型で使用される定数名の変更が顕著です。
*   `src/cmd/5a/lex.c`: ARMアセンブラの字句解析器の定義ファイル。レジスタ名や特殊レジスタの定義が、具体的な数値から抽象的なシンボリック定数に置き換えられています。また、`nullgen`の初期化も変更されています。
*   `src/cmd/5a/y.tab.c`: `a.y`から生成されるCコード。文法定義の変更が直接反映されています。
*   `src/cmd/5g/`以下のファイル群 (`cgen.c`, `cgen64.c`, `ggen.c`, `gobj.c`, `gsubr.c`, `peep.c`, `reg.c`など): ARMコンパイラのコード生成、オブジェクトファイル生成、レジスタ割り当て、最適化などに関連するファイル。`Prog`と`Addr`の変更が、これらのコンポーネントでの命令やアドレスの扱い方に影響を与えています。
*   `src/cmd/5l/5.out.h`: ARMリンカの出力ファイル形式に関連するヘッダーファイル。`Prog`と`Addr`の内部構造の変更が、オブジェクトファイルのフォーマットにも影響を与えている可能性があります。
*   `src/liblink/`以下のファイル群 (`asm5.c`, `list5.c`, `obj5.c`など): リンカの共通ライブラリおよびARMアーキテクチャ固有のリンキングロジック。`Prog`と`Addr`のポータブル化に伴い、これらの型を扱うリンカの内部ロジックが調整されています。

これらのファイル全体で、`D_CONST`のようなアーキテクチャ固有の定数名が`TYPE_CONST`のような汎用的な名前に変更され、`NREG`のようなレジスタ関連の定数が削除または抽象化されています。

## コアとなるコードの解説

このコミットの核心は、Goツールチェインの内部で命令とアドレスを表現する`Prog`と`Addr`という2つの主要なデータ構造の抽象化です。

**`Addr`型の変更**:
`Addr`型は、命令のオペランド（引数）として使用されるメモリアドレスやレジスタ、定数などを表現します。以前は、`D_CONST` (定数)、`D_OREG` (オフセットレジスタ)、`D_REG` (レジスタ)、`D_FREG` (浮動小数点レジスタ) など、特定のアーキテクチャ（この場合はARM）のレジスタやアドレス指定モードを直接反映した定数を使用していました。

このコミットでは、これらの定数名が以下のように変更されています。

*   `D_CONST` -> `TYPE_CONST`: 汎用的な定数。
*   `D_OREG` -> `TYPE_MEM`: メモリ参照（オフセットレジスタを含む）。
*   `D_REG` -> `TYPE_REG`: 汎用レジスタ。
*   `D_FREG` -> `TYPE_REG`: 浮動小数点レジスタも汎用レジスタとして扱われる。
*   `D_BRANCH` -> `TYPE_BRANCH`: 分岐先アドレス。
*   `D_SCONST` -> `TYPE_SCONST`: 文字列定数。
*   `D_FCONST` -> `TYPE_FCONST`: 浮動小数点定数。
*   `D_REGREG2` -> `TYPE_REGREG2`: 2つのレジスタを含むアドレス指定モード。
*   `D_SHIFT` -> `TYPE_SHIFT`: シフト操作を含むアドレス指定モード。

また、シンボルタイプを示す定数も変更されています。

*   `D_AUTO` -> `NAME_AUTO`: 自動変数。
*   `D_EXTERN` -> `NAME_EXTERN`: 外部シンボル。
*   `D_PARAM` -> `NAME_PARAM`: パラメータ。
*   `D_STATIC` -> `NAME_STATIC`: 静的シンボル。

これらの変更により、`Addr`型は特定のアーキテクチャのレジスタセットやアドレス指定モードに直接依存することなく、より抽象的な「型」として情報を保持できるようになります。これにより、異なるアーキテクチャ間で`Addr`型の定義を共有しやすくなり、ツールチェインのコードベースの重複を減らすことができます。

**`Prog`型の変更と`outcode`関数の調整**:
`Prog`型は、アセンブリ命令の内部表現です。`src/cmd/5a/a.y`（ARMアセンブラの文法定義）では、アセンブリ命令を機械語に変換する`outcode`関数の呼び出しが多数存在します。以前は、この関数に`NREG`という引数が渡されていました。`NREG`は"No Register"を意味し、命令にレジスタオペランドがない場合にプレースホルダーとして使用されていました。

このコミットでは、`outcode`関数の呼び出しから`NREG`が削除され、代わりに`0`が渡されています。
例: `outcode($1, $2, &$3, NREG, &$5);` が `outcode($1, $2, &$3, 0, &$5);` に変更。

これは、`outcode`関数がレジスタの有無に関するアーキテクチャ固有の知識を直接持つことを避け、より汎用的な命令エンコードロジックに集中できるようにするためです。レジスタの概念やそのエンコード方法はアーキテクチャによって大きく異なるため、この変更は`Prog`型のポータビリティを高める上で重要です。

**レジスタ定義の抽象化**:
`src/cmd/5a/lex.c`では、アセンブラが認識するレジスタ名（例: `R0`, `F0`, `CPSR`）が、具体的な数値から`REG_R0`, `REG_F0`, `REG_CPSR`といったシンボリック定数に置き換えられています。これにより、レジスタの実際の数値マッピングは、アーキテクチャ固有のヘッダーファイル（例: `src/cmd/5l/5.out.h`）で定義されるようになり、アセンブラの字句解析器はレジスタ名を抽象的に扱うことができます。

これらの変更は、Goツールチェインの内部データ構造をより汎用的にすることで、新しいアーキテクチャのサポートを容易にし、コードベースの保守性を向上させるための重要な基盤整備です。

    *   **`cmd/5g` (コンパイラ)**: Goのソースコードをアセンブリコード（またはオブジェクトファイル）に変換します。
    *   **`cmd/5l` (リンカ)**: オブジェクトファイルを結合し、実行可能ファイルを生成します。
    *   **`liblink`**: リンカの共通ライブラリであり、アーキテクチャに依存しないリンキングのロジックを提供します。

2.  **`Prog` 型**:
    *   `Prog`は"Program"の略で、Goツールチェインの内部で命令を表す構造体です。アセンブラがアセンブリコードを解析して生成し、コンパイラがGoコードから生成する中間表現の一部でもあります。リンカはこれらの`Prog`オブジェクトを操作して最終的なバイナリを生成します。
    *   初期の`Prog`型は、特定のアーキテクチャの命令セットの特性を直接反映している部分がありました。例えば、ARMアーキテクチャの命令には、条件コードやシフト操作など、他のアーキテクチャにはない特有のフィールドが存在します。

3.  **`Addr` 型**:
    *   `Addr`は"Address"の略で、Goツールチェインの内部でメモリアドレスやシンボル参照を表す構造体です。命令のオペランドとして使用されることが多く、レジスタ、オフセット、シンボルへの参照など、様々な種類のアドレス指定モードを表現します。
    *   `Addr`型もまた、特定のアーキテクチャのアドレス指定モードに強く依存している部分がありました。例えば、ARMのロード/ストア命令には、ベースレジスタ、インデックスレジスタ、オフセット、プリ/ポストインクリメントなどの複雑なアドレス指定モードがあります。

4.  **Plan 9ツールチェインの影響**:
    *   Goの初期のツールチェインは、Bell LabsのPlan 9オペレーティングシステムのツールチェイン（`8a`, `8g`, `8l`など）から大きな影響を受けています。Plan 9のツールチェインは、シンプルでモジュール化された設計が特徴で、Goもその哲学を受け継いでいます。しかし、Plan 9のツールチェインは、Goがサポートする多様なアーキテクチャや現代的な言語機能に対応するために進化する必要がありました。

5.  **ポータビリティ（移植性）**:
    *   ソフトウェアが異なるハードウェアプラットフォームやオペレーティングシステム上で動作する能力を指します。Goツールチェインの文脈では、`Prog`や`Addr`のような内部データ構造が、ARM、x86、x86-64、MIPSなど、様々なCPUアーキテクチャ間で共通の表現を持つことを意味します。これにより、アーキテクチャ固有のロジックを最小限に抑え、ツールチェインのコードベースをよりクリーンで保守しやすくすることができます。

これらの型をポータブルにするということは、アーキテクチャ固有の情報をこれらの型から分離し、必要に応じてアーキテクチャ固有のコードで処理するように変更することを意味します。これにより、共通のコードベースでより多くのアーキテクチャをサポートできるようになります。

## 技術的詳細

このコミットの技術的な核心は、`Prog`と`Addr`構造体からアーキテクチャ固有のフィールドを抽象化し、より汎用的な表現に置き換えることです。具体的には、ARMアーキテクチャのアセンブラ（`cmd/5a`）とリンカ（`liblink`）のコードが大幅に変更されています。

変更の主なポイントは以下の通りです。

1.  **`Addr`型のフィールド名の変更と抽象化**:
    *   コミットの差分を見ると、`D_CONST`, `D_OREG`, `D_REG`, `D_FREG`, `D_BRANCH`, `D_SCONST`, `D_FCONST`, `D_REGREG2`, `D_SHIFT`といった定数（おそらく`Addr`型の`type`フィールドの値を定義するもの）が、`TYPE_CONST`, `TYPE_MEM`, `TYPE_REG`, `TYPE_BRANCH`, `TYPE_SCONST`, `TYPE_FCONST`, `TYPE_REGREG2`, `TYPE_SHIFT`といったより汎用的な名前に変更されています。
    *   同様に、`D_AUTO`, `D_EXTERN`, `D_PARAM`, `D_STATIC`といったシンボルタイプを示す定数も、`NAME_AUTO`, `NAME_EXTERN`, `NAME_PARAM`, `NAME_STATIC`に変更されています。
    *   これは、これらの定数が単なる「データ型」や「アドレス指定モード」ではなく、より抽象的な「型」や「名前」を表現するように意図されていることを示唆しています。これにより、異なるアーキテクチャがそれぞれ独自のアドレス指定モードを持っていても、共通の`Addr`型でそれらを表現できるようになります。

2.  **`outcode`関数の引数変更**:
    *   `src/cmd/5a/a.y`の変更を見ると、`outcode`関数（アセンブリ命令をエンコードする関数）の引数から`NREG`が削除され、`0`に置き換えられています。
    *   `outcode($1, $2, &$3, NREG, &$5);` が `outcode($1, $2, &$3, 0, &$5);` に変更されています。
    *   `NREG`は通常、"No Register"を意味する定数で、特定のレジスタが使用されない場合にプレースホルダーとして使われていました。これを`0`に置き換えることで、`outcode`関数がレジスタに関するアーキテクチャ固有の知識を直接持つことを避け、より汎用的な命令エンコードロジックに集中できるようにしています。これは、レジスタの概念がアーキテクチャによって異なるため、ポータビリティを高めるための重要なステップです。

3.  **レジスタ定義の抽象化**:
    *   `src/cmd/5a/lex.c`では、`R0`から`R15`、`F0`から`F15`などのレジスタ定義が、具体的な数値（0, 1, ...）から`REG_R0`, `REG_R1`, ..., `REG_F0`, `REG_F1`, ...といったシンボリック定数に置き換えられています。
    *   `CPSR`, `SPSR`, `FPSR`, `FPCR`といった特殊レジスタも同様に`REG_CPSR`, `REG_SPSR`, `REG_FPSR`, `REG_FPCR`に変更されています。
    *   これにより、レジスタの実際の数値マッピングがアーキテクチャ固有のヘッダーファイルや定義に委ねられ、アセンブラの字句解析器（lexer）はレジスタ名を抽象的に扱うことができるようになります。

4.  **`nullgen`の初期化変更**:
    *   `src/cmd/5a/lex.c`の`cinit`関数で、`nullgen`（`Addr`型のゼロ値）の初期化が`nullgen.type = D_NONE; nullgen.name = D_NONE; nullgen.reg = NREG;`から`nullgen.type = TYPE_NONE; nullgen.name = NAME_NONE;`に変更されています。
    *   `nullgen.reg = NREG;`が削除されたのは、`NREG`がアーキテクチャ固有のレジスタ概念に結びついていたため、よりポータブルな`Addr`型では不要になったことを示しています。

5.  **Yacc/Bison文法ファイルの変更**:
    *   `src/cmd/5a/a.y`と`src/cmd/5a/y.tab.c`は、アセンブラの文法定義ファイルと、それから生成されたCコードです。これらのファイルが変更されているのは、`Prog`や`Addr`型の内部表現の変更に伴い、アセンブリ命令の解析ロジックも更新されたためです。特に、`y.tab.c`の変更は、文法規則の数や状態数がわずかに減少していることから、文法がよりシンプルになったか、あるいは特定のアーキテクチャ固有の規則が抽象化されたことを示唆しています。

これらの変更は、Goツールチェインの内部で命令とアドレスを表現する方法を、特定のCPUアーキテクチャから切り離し、より抽象的で汎用的なものにすることで、将来的な拡張性と保守性を高めることを目的としています。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、主に以下のファイル群に集中しています。

*   `src/cmd/5a/a.y`: ARMアセンブラのYacc文法定義ファイル。`Prog`と`Addr`の内部表現の変更に伴い、命令の解析規則が更新されています。特に、`outcode`関数の呼び出しにおける`NREG`の削除と、`Addr`型で使用される定数名の変更が顕著です。
*   `src/cmd/5a/lex.c`: ARMアセンブラの字句解析器の定義ファイル。レジスタ名や特殊レジスタの定義が、具体的な数値から抽象的なシンボリック定数に置き換えられています。また、`nullgen`の初期化も変更されています。
*   `src/cmd/5a/y.tab.c`: `a.y`から生成されるCコード。文法定義の変更が直接反映されています。
*   `src/cmd/5g/`以下のファイル群 (`cgen.c`, `cgen64.c`, `ggen.c`, `gobj.c`, `gsubr.c`, `peep.c`, `reg.c`など): ARMコンパイラのコード生成、オブジェクトファイル生成、レジスタ割り当て、最適化などに関連するファイル。`Prog`と`Addr`の変更が、これらのコンポーネントでの命令やアドレスの扱い方に影響を与えています。
*   `src/cmd/5l/5.out.h`: ARMリンカの出力ファイル形式に関連するヘッダーファイル。`Prog`と`Addr`の内部構造の変更が、オブジェクトファイルのフォーマットにも影響を与えている可能性があります。
*   `src/liblink/`以下のファイル群 (`asm5.c`, `list5.c`, `obj5.c`など): リンカの共通ライブラリおよびARMアーキテクチャ固有のリンキングロジック。`Prog`と`Addr`のポータブル化に伴い、これらの型を扱うリンカの内部ロジックが調整されています。

これらのファイル全体で、`D_CONST`のようなアーキテクチャ固有の定数名が`TYPE_CONST`のような汎用的な名前に変更され、`NREG`のようなレジスタ関連の定数が削除または抽象化されています。

## コアとなるコードの解説

このコミットの核心は、Goツールチェインの内部で命令とアドレスを表現する`Prog`と`Addr`という2つの主要なデータ構造の抽象化です。

**`Addr`型の変更**:
`Addr`型は、命令のオペランド（引数）として使用されるメモリアドレスやレジスタ、定数などを表現します。以前は、`D_CONST` (定数)、`D_OREG` (オフセットレジスタ)、`D_REG` (レジスタ)、`D_FREG` (浮動小数点レジスタ) など、特定のアーキテクチャ（この場合はARM）のレジスタやアドレス指定モードを直接反映した定数を使用していました。

このコミットでは、これらの定数名が以下のように変更されています。

*   `D_CONST` -> `TYPE_CONST`: 汎用的な定数。
*   `D_OREG` -> `TYPE_MEM`: メモリ参照（オフセットレジスタを含む）。
*   `D_REG` -> `TYPE_REG`: 汎用レジスタ。
*   `D_FREG` -> `TYPE_REG`: 浮動小数点レジスタも汎用レジスタとして扱われる。
*   `D_BRANCH` -> `TYPE_BRANCH`: 分岐先アドレス。
*   `D_SCONST` -> `TYPE_SCONST`: 文字列定数。
*   `D_FCONST` -> `TYPE_FCONST`: 浮動小数点定数。
*   `D_REGREG2` -> `TYPE_REGREG2`: 2つのレジスタを含むアドレス指定モード。
*   `D_SHIFT` -> `TYPE_SHIFT`: シフト操作を含むアドレス指定モード。

また、シンボルタイプを示す定数も変更されています。

*   `D_AUTO` -> `NAME_AUTO`: 自動変数。
*   `D_EXTERN` -> `NAME_EXTERN`: 外部シンボル。
*   `D_PARAM` -> `NAME_PARAM`: パラメータ。
*   `D_STATIC` -> `NAME_STATIC`: 静的シンボル。

これらの変更により、`Addr`型は特定のアーキテクチャのレジスタセットやアドレス指定モードに直接依存することなく、より抽象的な「型」として情報を保持できるようになります。これにより、異なるアーキテクチャ間で`Addr`型の定義を共有しやすくなり、ツールチェインのコードベースの重複を減らすことができます。

**`Prog`型の変更と`outcode`関数の調整**:
`Prog`型は、アセンブリ命令の内部表現です。`src/cmd/5a/a.y`（ARMアセンブラの文法定義）では、アセンブリ命令を機械語に変換する`outcode`関数の呼び出しが多数存在します。以前は、この関数に`NREG`という引数が渡されていました。`NREG`は"No Register"を意味し、命令にレジスタオペランドがない場合にプレースホルダーとして使用されていました。

このコミットでは、`outcode`関数の呼び出しから`NREG`が削除され、代わりに`0`が渡されています。
例: `outcode($1, $2, &$3, NREG, &$5);` が `outcode($1, $2, &$3, 0, &$5);` に変更。

これは、`outcode`関数がレジスタの有無に関するアーキテクチャ固有の知識を直接持つことを避け、より汎用的な命令エンコードロジックに集中できるようにするためです。レジスタの概念やそのエンコード方法はアーキテクチャによって大きく異なるため、この変更は`Prog`型のポータビリティを高める上で重要です。

**レジスタ定義の抽象化**:
`src/cmd/5a/lex.c`では、アセンブラが認識するレジスタ名（例: `R0`, `F0`, `CPSR`）が、具体的な数値から`REG_R0`, `REG_F0`, `REG_CPSR`といったシンボリック定数に置き換えられています。これにより、レジスタの実際の数値マッピングは、アーキテクチャ固有のヘッダーファイル（例: `src/cmd/5l/5.out.h`）で定義されるようになり、アセンブラの字句解析器はレジスタ名を抽象的に扱うことができます。

これらの変更は、Goツールチェインの内部データ構造をより汎用的にすることで、新しいアーキテクチャのサポートを容易にし、コードベースの保守性を向上させるための重要な基盤整備です。

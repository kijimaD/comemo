# [インデックス 24441] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ（GC）における並行マークフェーズの効率を改善し、Stop-The-World（STW）マーク終了フェーズの時間を短縮することを目的としています。具体的には、ミューテータ（アプリケーションコード）がGCのワークバッファをGCから「隠してしまう」可能性のあるシナリオを修正し、GCがすべてのポインタを効率的に追跡できるようにします。

## 変更の背景

Goのガベージコレクタ（GC）は、アプリケーションの実行と並行して動作する「並行マークフェーズ」を採用することで、アプリケーションの一時停止時間（Stop-The-World: STW）を最小限に抑えることを目指しています。しかし、この並行処理の性質上、GCがオブジェクトグラフを走査している間に、アプリケーション（ミューテータ）がポインタを変更する可能性があります。この変更をGCに適切に通知するために「ライトバリア」が使用されます。

このコミットが修正しようとしている問題は、スケジューラ、ワークバッファの解放（`dispose`）、およびライトバリアが連携して、GCの並行マークフェーズからポインタを「隠してしまう」可能性があったことです。具体的には、以下のシナリオが発生していました。

1.  **`dispose`がワークバッファを`partial`キューに配置する**: ミューテータが使用済みのワークバッファをGCに返却する際、それを`partial`キュー（部分的に満たされたバッファを格納するキュー）に置きます。
2.  **GCがすぐに処理しない**: GCが他のタスクで忙しい場合、`partial`キューに置かれたワークバッファをすぐに取り出して処理することができません。
3.  **ミューテータがワークバッファを再取得する**: その間にスケジューラが別のミューテータを実行し、そのミューテータのライトバリアが`partial`キューから同じワークバッファを再取得してしまう可能性があります。

この繰り返しにより、GCは並行マークフェーズ中に特定のポインタを認識できず、そのポインタが参照する大量のオブジェクトをマークする作業が、GCの最終段階であるSTWマーク終了フェーズまで持ち越されてしまいます。結果として、STWフェーズが不必要に長くなり、アプリケーションの応答性に悪影響を与える可能性がありました。この問題は、特にそのポインタが大量のマーク作業への唯一のパスである場合に顕著でした。

この変更は、このような「共謀」を防ぎ、GCが並行フェーズ中にすべてのポインタを確実に追跡できるようにすることで、STW時間の短縮とGC効率の向上を目指しています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションに関するいくつかの基本的な概念を理解しておく必要があります。

*   **Goのガベージコレクション (GC)**: GoのGCは、不要になったメモリを自動的に解放するシステムです。主に三色マーク＆スイープアルゴリズムをベースにしており、アプリケーションの実行と並行して動作することで、STW（Stop-The-World）ポーズを最小限に抑えるように設計されています。
*   **並行マークフェーズ (Concurrent Mark Phase)**: GCの主要なフェーズの一つで、アプリケーション（ミューテータ）が実行されている間に、GCが到達可能なオブジェクトをマークします。これにより、アプリケーションの実行を長時間停止させることなく、GC作業を進めることができます。
*   **Stop-The-World (STW) フェーズ**: GCの特定の段階で、アプリケーションの実行が一時的に完全に停止される期間です。GoのGCはSTW時間を極力短くするように設計されていますが、完全にゼロにすることはできません。マーク終了フェーズやスイープ準備フェーズなどで発生します。
*   **ライトバリア (Write Barrier)**: 並行GCにおいて非常に重要なメカニズムです。ミューテータがヒープ上のポインタを書き換える際に、コンパイラによって自動的に挿入される小さなコードスニペットです。これにより、GCがオブジェクトグラフを走査している間にポインタが変更されても、GCがその変更を追跡し、オブジェクトが誤って回収されるのを防ぎます。Goのライトバリアは、ポインタが変更される前に古い値と新しい値の両方を記録し、GCがそれらをマークできるようにします。
*   **ワークバッファ (Work Buffer)**: GCがマーク作業を行う際に使用する一時的なバッファです。ライトバリアによって記録されたポインタや、GCが走査中に発見したポインタは、これらのワークバッファに格納されます。GCワーカーゴルーチンは、これらのバッファからポインタを取り出し、さらに走査を進めます。これにより、GC作業の並行処理と効率化が図られます。
*   **GCのキュー (Partial Queue, Full Queue)**: ワークバッファを管理するためのキューです。
    *   **`partial`キュー**: 部分的に満たされたワークバッファや、ミューテータが使用を終えてGCに返却したワークバッファが一時的に置かれる場所です。
    *   **`full`キュー**: 完全に満たされたワークバッファや、GCがすぐに処理すべきワークバッファが置かれる場所です。通常、`full`キューに入れられたバッファは、GCワーカーによって優先的に処理されます。

## 技術的詳細

このコミットが解決する問題は、Goの並行GCにおけるワークバッファの管理とライトバリアの相互作用に起因します。

GoのGCは、ミューテータがポインタを書き換える際にライトバリアを介してポインタ情報をワークバッファに記録します。これらのワークバッファは、GCワーカーが後で処理するためにキューに置かれます。問題は、ミューテータが`dispose`関数を呼び出してワークバッファをGCに返却する際に、そのバッファを`partial`キューに置いていた点にありました。

シナリオの再確認：
1.  ミューテータがポインタを書き換え、ライトバリアが発動し、ポインタ情報がワークバッファに記録されます。
2.  ミューテータがワークバッファを使い終え、`dispose`を呼び出して`partial`キューに返却します。
3.  GCが忙しく、すぐに`partial`キューからこのバッファを取り出して処理できません。
4.  その間に、別のミューテータが実行され、そのライトバリアが`partial`キューから、GCがまだ処理していない同じワークバッファを再取得してしまいます。

この「共謀」により、GCの並行マークフェーズは、本来マークすべきポインタがワークバッファ内で循環しているため、そのポインタを「見失う」ことになります。結果として、GCはマーク作業を完了できず、最終的にSTWマーク終了フェーズに入ってから、ようやくこれらのポインタを発見し、大量のマーク作業を一度に行う必要が生じます。これはSTW時間の増加に直結し、アプリケーションのレイテンシに悪影響を与えます。

このコミットの解決策は、非常にシンプルかつ効果的です。ミューテータがワークバッファを`dispose`する際に、`partial`キューではなく**`full`キュー**に置くように変更します。

なぜこれが機能するのか：
*   **ライトバリアの動作**: ライトバリアは、新しいポインタ情報を記録するためにワークバッファを要求しますが、通常は`full`キューからバッファを取得することはありません。ライトバリアは、主に`empty`キューから新しいワークバッファを取得するか、既存の`partial`バッファを再利用します。
*   **`full`キューの優先度**: `full`キューに置かれたワークバッファは、GCワーカーによって優先的に処理されます。

したがって、ミューテータがワークバッファを`full`キューに置くことで、そのバッファはGCワーカーによって迅速に処理され、ミューテータのライトバリアがそれを再取得してGCから隠すというシナリオが不可能になります。これにより、GCは並行マークフェーズ中にすべてのポインタを確実に追跡できるようになり、STWマーク終了フェーズでの予期せぬ長いポーズを防ぐことができます。

## コアとなるコードの解説

このコミットの核心は、`src/runtime/mgcwork.go`内の`gcWork.dispose()`メソッドの変更にあります。

以前のコードでは、ミューテータが使用済みのワークバッファをGCに返却する際に、`putpartial(wbuf.ptr(), 167)`を呼び出していました。`putpartial`は、ワークバッファを`partial`キューに配置する関数です。前述の「変更の背景」で説明したように、この動作がGCの並行マークフェーズ中にポインタが隠される原因となっていました。

新しいコードでは、この行が`putfull(wbuf.ptr(), 166)`に置き換えられています。`putfull`は、ワークバッファを`full`キューに配置する関数です。この変更により、ミューテータが返却したワークバッファは`full`キューに直接送られるため、GCワーカーによって迅速に処理されることが保証されます。ライトバリアは通常`full`キューからバッファを再取得しないため、ミューテータがGCが処理する前にバッファを「奪い返す」ことができなくなります。これにより、GCは並行マークフェーズ中にすべてのポインタを確実にマークできるようになり、STWマーク終了フェーズでの作業量が大幅に削減されます。

また、`if wbuf.ptr().nobj == 0 { throw("dispose: workbuf is empty") }`というチェックが追加されています。`nobj`はワークバッファ内のオブジェクトの数を表すと考えられます。このチェックは、`dispose`が呼び出されたときにワークバッファが空であるという予期せぬ状態を防ぐためのアサーションであり、ランタイムの堅牢性を高めるものです。空のバッファを`full`キューに入れることは意味がなく、潜在的なバグを示唆するため、ここで`throw`（Goランタイムにおけるパニックに相当）することで早期に問題を検出します。

`src/runtime/mgc.go`の`work`構造体に追加されたコメント`// TODO(rlh): partial no longer used, remove. (issue #11922)`は、`partial`キューがこの変更によってその役割を失い、将来的には完全に削除される可能性があることを示唆しています。これは、このコミットがGCのワークバッファ管理戦略におけるより広範な変更の一部であることを示唆しています。

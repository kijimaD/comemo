## 元コミット内容

`cmd/compile: free時に定数キャッシュから値を削除`

定数である可能性のある値に対して `freeValue` を呼び出す際、それらをキャッシュからも削除する。

## 変更の背景

GoコンパイラのSSAバックエンドでは、最適化の過程で中間表現である `Value` オブジェクトを生成・再利用します。特に定数（例: `true`, `false`, 整数リテラル）は頻繁に利用されるため、パフォーマンス向上のためにキャッシュされます。このキャッシュは、同じ定数値を表す `Value` オブジェクトが複数回生成されるのを防ぎ、メモリ使用量を削減し、コンパイル時間を短縮する役割を担っています。

しかし、以前の実装では、`freeValue` メソッドが `Value` オブジェクトを解放し、再利用可能な状態にする際に、それが定数キャッシュにまだ残っている可能性がありました。もし、解放された `Value` がキャッシュに残ったままで、その後別の目的で再利用された場合、キャッシュからその `Value` が取得されると、その `Value` は古い情報（例えば、`AuxInt`フィールドに格納されている定数値）を持っている可能性があります。これにより、コンパイラが誤った定数値を処理したり、予期せぬ動作を引き起こしたりするバグが発生するリスクがありました。

このコミットは、このような潜在的なバグを防ぎ、定数キャッシュの整合性を保つことを目的としています。`Value` が解放される際に、それが定数キャッシュに存在する場合は、キャッシュからも適切に削除することで、古い `Value` が誤って再利用されることを防ぎます。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを抽象構文木 (AST) に変換した後、中間表現としてSSA形式を使用します。SSA形式は、各変数が一度だけ代入されるようにする表現であり、データフロー解析や最適化を容易にします。SSA形式では、プログラム内のすべての値（定数、変数、メモリ操作など）が `Value` オブジェクトとして表現されます。

### `Value` オブジェクト

SSA形式における基本的な構成要素です。各 `Value` は、特定の操作 (`Op`)、型 (`Type`)、および追加情報 (`AuxInt`, `Aux`) を持ちます。
- **`Op`**: その `Value` が表す操作の種類（例: `OpConstBool` (ブール定数), `OpAdd` (加算), `OpLoad` (メモリからのロード)）。
- **`Type`**: その `Value` の型（例: `TypeBool`, `TypeInt64`）。
- **`AuxInt`**: 整数定数の値、オフセット、シフト量など、`Op` に応じた追加の整数情報。定数 `Value` の場合、このフィールドに実際の定数値が格納されることが多いです。
- **`Aux`**: ポインタやシンボルなど、`AuxInt` では表現できない追加情報。

### 定数キャッシュ (`f.constants`)

GoコンパイラのSSAバックエンドでは、`Func` オブジェクト（コンパイル中の関数を表す）内に `constants` というマップを持っています。これは、`AuxInt` の値（定数値）をキーとし、その定数値を表す `Value` オブジェクトのスライスを値とするキャッシュです。これにより、同じ定数値を表す `Value` オブジェクトが繰り返し生成されるのを防ぎます。

### `freeValue` メカニズム

コンパイラは、SSA形式の最適化中に不要になった `Value` オブジェクトを `freeValue` メソッドを使って解放します。これは、ガベージコレクションのオーバーヘッドを避けるために、`Value` オブジェクトをプールし、再利用可能にするためのメカニズムです。解放された `Value` は、新しい `Value` が必要になったときに再利用されます。

## 技術的詳細

このコミットが解決しようとしている問題は、`freeValue` が呼び出された `Value` が、まだ `f.constants` キャッシュに残っている場合に発生します。

1.  **問題のシナリオ**:
    *   ある定数 `C` を表す `Value` オブジェクト `v` が生成され、`f.constants` キャッシュに格納されます。
    *   その後、`v` が不要になり、`freeValue(v)` が呼び出されます。このとき、`v` は再利用可能な状態になりますが、`f.constants` からは削除されません。
    *   しばらくして、別の `Value` オブジェクト `v'` が必要になり、`v` が再利用されて `v'` となります。この `v'` は、全く異なる目的（例えば、別の種類の操作や別の定数）で使用される可能性があります。
    *   もし、コンパイラが再び定数 `C` を必要とし、`constVal` メソッドが `f.constants` キャッシュを検索した場合、古い `v`（現在は `v'` として再利用されている）が返される可能性があります。この `v'` は、もはや定数 `C` を表すものではなく、その `AuxInt` フィールドも `C` とは異なる値になっているかもしれません。
    *   これにより、コンパイラは誤った定数値を処理し、不正なコードを生成する可能性があります。

2.  **コミットによる解決策**:
    *   `freeValue` メソッド内で、解放される `Value` が引数を持たない（`nArgs == 0`）場合、それは定数である可能性が高いと判断します。
    *   その場合、`v.AuxInt` をキーとして `f.constants` キャッシュを検索し、解放される `Value` `v` と一致するエントリがあれば、そのエントリをキャッシュから削除します。これにより、解放された `Value` がキャッシュに残存することを防ぎます。
    *   `constVal` メソッドには、キャッシュから取得した `Value` の `AuxInt` が期待される定数値 `c` と一致しない場合に `panic` を発生させるアサーションが追加されました。これは、万が一キャッシュの整合性が破られた場合に早期に問題を検出するための安全策です。

この変更により、定数キャッシュは常に有効な `Value` オブジェクトのみを保持するようになり、コンパイラの堅牢性が向上します。

## コアとなるコードの解説

### `func.go` の変更点

1.  **`freeValue` メソッド内**:
    *   `nArgs := opcodeTable[v.Op].argLen` で、解放される `Value` `v` のオペコードが取る引数の数を取得します。
    *   `if nArgs == 0` の条件は、`v` が引数を取らないオペコード（例: `OpConstBool`, `OpConstInt` など、定数を表すことが多い）である場合に真となります。
    *   `vv := f.constants[v.AuxInt]` で、`v` の `AuxInt` をキーとして定数キャッシュから対応する `Value` のスライスを取得します。
    *   `for i, cv := range vv` ループで、スライス `vv` の中から解放対象の `Value` `v` と同じポインタを持つ `cv` を探します。
    *   `if v == cv` で一致が見つかった場合、`vv[i] = vv[len(vv)-1]` と `f.constants[v.AuxInt] = vv[0 : len(vv)-1]` によって、スライスから `v` を削除します。これは、スライスから要素を削除する一般的なGoのイディオムで、削除対象の要素をスライスの末尾の要素で上書きし、その後スライスを短縮することで実現されます。
    *   `break` でループを抜けます。

2.  **`constVal` メソッド内**:
    *   `if setAux && v.AuxInt != c` という新しい条件が追加されました。
        *   `setAux` は、`AuxInt` が設定されるべきかどうかを示すフラグです。
        *   `v.AuxInt != c` は、キャッシュから取得した `Value` `v` の `AuxInt` が、現在要求されている定数値 `c` と一致しない場合に真となります。
    *   この条件が真の場合、`panic` が発生します。これは、キャッシュから取得された `Value` が期待される定数値を保持していないという、コンパイラの内部的な不整合を即座に検出するためのアサーションです。

### `func_test.go` の変更点

1.  **`TestConstCache` の追加**:
    *   このテストは、定数キャッシュが解放された `Value` を誤って返さないことを保証するために追加されました。
    *   `f.f.ConstBool(0, TypeBool, false)` と `f.f.ConstBool(0, TypeBool, true)` を呼び出して、2つのブール定数 `v1` と `v2` を作成します。これらは内部的に定数キャッシュに格納されます。
    *   `f.f.freeValue(v1)` と `f.f.freeValue(v2)` を呼び出して、これらの `Value` を解放します。このコミットの変更により、これらの `Value` は定数キャッシュからも削除されます。
    *   再度 `f.f.ConstBool(0, TypeBool, false)` と `f.f.ConstBool(0, TypeBool, true)` を呼び出して、`v3` と `v4` を作成します。このとき、キャッシュが正しく機能していれば、新しい `Value` が生成されるか、適切に初期化された `Value` が返されるはずです。
    *   `if v3.AuxInt != 0` と `if v4.AuxInt != 1` のアサーションにより、`v3` と `v4` の `AuxInt` がそれぞれ正しい定数値（0と1）を保持していることを確認します。これにより、解放された `Value` がキャッシュから誤って再利用され、古い `AuxInt` 値を保持したまま返されるという問題が解決されたことを検証します。

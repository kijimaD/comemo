# [インデックス 21900] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）における`qsort`（クイックソート）の比較関数を「全順序（totally ordered）」にする変更を導入しています。これにより、異なる`qsort`の実装が使用された場合でも、ソート結果の順序が常に一意に定まるようになり、結果として生成されるコンパイル済みオブジェクトファイルの一貫性が保証されます。これは、再現可能なビルド（Reproducible Builds）を実現するための重要な改善です。

## コミット

cmd/gc: make qsort comparisons totally ordered

Otherwise different qsort implementations might result
in different sort orders and therefore different compiled
object files.

## 変更の背景

この変更の主な背景は、Goコンパイラが生成するオブジェクトファイルの「再現性（reproducibility）」を確保することにあります。

`qsort`のような比較ベースのソートアルゴリズムは、比較関数が等価な要素に対して0を返す場合、それらの要素の相対的な順序を保証しません。つまり、`a == b`である2つの要素`a`と`b`があった場合、ソート後の配列で`a`が`b`の前に来るか、`b`が`a`の前に来るかは、使用される`qsort`の実装や、場合によってはメモリ上の配置、スレッドの実行順序など、様々な要因によって異なり得ます。

Goコンパイラは、コンパイルプロセス中に様々な内部データ構造をソートします。もしこのソートが非決定論的であると、同じソースコードを同じコンパイラバージョンでコンパイルしても、異なる環境（異なるOS、異なるCPUアーキテクチャ、あるいは単に異なるメモリレイアウト）でビルドした場合に、生成されるオブジェクトファイルのバイト列が異なる可能性があります。これは、ビルドの再現性を損ないます。

再現可能なビルドは、ソフトウェアのサプライチェーンセキュリティ、監査可能性、およびデバッグの容易さにとって非常に重要です。ユーザーが同じソースコードから常に同じバイナリを生成できることは、信頼性を高め、悪意のある改ざんや意図しない差異の検出を容易にします。このコミットは、Goコンパイラが生成する成果物の決定論性を高めるための具体的なステップです。

## 前提知識の解説

### 1. `qsort`と比較関数

`qsort`はC標準ライブラリで提供される汎用的なクイックソート関数です。ソート対象の配列と、2つの要素を比較するための比較関数（`compar`）を引数に取ります。比較関数は、`a < b`なら負の値、`a == b`なら0、`a > b`なら正の値を返します。

重要なのは、比較関数が`a == b`の場合に0を返すことです。この「等価」の定義が、ソートアルゴリズムの安定性（等価な要素の相対順序を保持するかどうか）や、非決定論的な挙動に影響を与えます。`qsort`は一般的に安定ソートではありません。

### 2. 全順序（Total Order）

数学における「全順序」とは、集合内の任意の2つの要素`a`と`b`について、以下のいずれか一つが必ず成り立つ関係を指します。
*   `a < b`
*   `a = b`
*   `a > b`

そして、この関係が推移律（`a < b`かつ`b < c`ならば`a < c`）を満たす必要があります。
ソートの文脈では、「全順序」な比較関数とは、等価な要素であっても、何らかの補助的な基準（例えば、オブジェクトのメモリアドレス、ユニークなID、あるいは文字列の辞書順など）を用いて、常にどちらか一方を「小さい」または「大きい」と見なすように定義された比較関数を指します。これにより、比較関数が0を返すことがなくなり、ソート結果が常に一意に定まるようになります。

### 3. Goコンパイラ (`cmd/gc`)

`cmd/gc`は、Go言語の公式コンパイラです。Goのソースコードを機械語に変換する役割を担っています。コンパイルの過程で、シンボルテーブルの管理、型チェック、最適化、コード生成など、様々な処理が行われます。これらの処理の一部で、内部的なデータ構造（例えば、変数、関数、型などの定義）をソートする必要が生じることがあります。

### 4. 再現可能なビルド（Reproducible Builds）

再現可能なビルドとは、特定のソースコード、ビルド環境、およびビルド手順が与えられた場合、常にビット単位で同一の出力バイナリ（またはオブジェクトファイル）が生成されることを保証するプロセスです。これは、ソフトウェアの信頼性を高め、サプライチェーン攻撃（ビルドプロセス中に悪意のあるコードが挿入されるなど）のリスクを軽減するために非常に重要です。非決定論的なソートは、再現可能なビルドを妨げる一般的な原因の一つです。

## 技術的詳細

このコミットは、Goコンパイラ内部で使用される`qsort`の比較関数に、補助的な比較基準を追加することで「全順序」を導入しています。具体的には、主要な比較基準（例: `start`時間や`cost`）が等しい場合に、要素のユニークなIDやシンボル名といった、より詳細な情報を用いて比較を続行し、最終的に0以外の値を返すように変更されています。

変更されたファイルは以下の2つです。

1.  `src/cmd/gc/popt.c`: このファイルは、Goコンパイラの最適化フェーズの一部であるプロパゲーション（propagation）に関連するコードを含んでいます。`startcmp`関数は、おそらくプロパゲーションの対象となるノードや変数をソートするために使用されます。
2.  `src/cmd/gc/reg.c`: このファイルは、レジスタ割り当て（register allocation）に関連するコードを含んでいます。`rcmp`関数は、レジスタ割り当ての際に使用される領域（Region）をソートするために使用されます。

これらの比較関数において、従来の比較基準が等しい場合に、以下の補助的な基準が追加されました。

*   `src/cmd/gc/popt.c`の`startcmp`関数:
    *   `a->def != b->def`の場合、`a->def->id - b->def->id`で比較。`def`は定義を指し、`id`はユニークな識別子と考えられます。
    *   `a->node != b->node`の場合、`strcmp(a->node->sym->name, b->node->sym->name)`で比較。`node`は抽象構文木のノードを指し、`sym->name`はシンボル名です。
*   `src/cmd/gc/reg.c`の`rcmp`関数:
    *   `p1->cost != p2->cost`の場合、`p2->cost - p1->cost`で比較（コストの降順）。
    *   `p1->varno != p2->varno`の場合、`p2->varno - p1->varno`で比較（変数番号の降順）。
    *   `p1->enter != p2->enter`の場合、`p2->enter->id - p1->enter->id`で比較（エントリIDの降順）。

これらの追加された比較基準は、比較対象のオブジェクトが完全に同一でない限り、必ずどちらか一方を「小さい」または「大きい」と判断できるように設計されています。これにより、比較関数が0を返すケースが、比較対象のオブジェクトが完全に同一である場合に限定され、`qsort`のソート結果が常に決定論的になります。

結果として、コンパイラが内部的にソートするデータ構造の順序が常に一意に定まるため、生成されるオブジェクトファイルのバイト列も、同じソースコードとコンパイラバージョンであれば、常に同一になることが保証されます。

## コアとなるコードの解説

### `src/cmd/gc/popt.c` の `startcmp` 関数

元の`startcmp`関数は、`a->start`と`b->start`を比較し、これらが等しい場合に`0`を返していました。これは、`start`値が同じ複数の要素が存在する場合、それらの相対的な順序が`qsort`の実装に依存することを意味します。

変更後、`start`値が等しい場合（`return 0;`に到達する前）に、以下の追加の比較が行われます。

1.  `if(a->def != b->def)`: `def`フィールドが異なる場合、`a->def->id`と`b->def->id`の差を返します。`def`はおそらく定義（例: 変数定義）を指し、`id`はその定義に割り当てられたユニークな識別子です。これにより、異なる定義は常に順序付けられます。
2.  `if(a->node != b->node)`: `node`フィールドが異なる場合、`a->node->sym->name`と`b->node->sym->name`を`strcmp`で比較します。`node`は抽象構文木のノードを指し、`sym->name`はそのノードに関連付けられたシンボルの名前です。これにより、異なるノードはシンボル名に基づいて順序付けられます。

これらの追加された比較により、`start`値が同じであっても、`def`や`node`が異なる場合は必ず非ゼロの値が返され、ソート順序が決定論的になります。最終的に`return 0;`が実行されるのは、比較対象の2つの要素が`start`、`def`、`node`の全てにおいて等しい場合のみです。

### `src/cmd/gc/reg.c` の `rcmp` 関数

元の`rcmp`関数は、`Rgn`（Region）構造体の`cost`と`varno`（変数番号）を比較していました。`cost`が等しい場合は`varno`で比較し、これらも等しい場合は`0`を返していました。これもまた、等価な要素の相対順序が非決定論的になる原因でした。

変更後、`cost`と`varno`が等しい場合（`if`ブロックを通過した後）に、以下の追加の比較が行われます。

1.  `if(p1->cost != p2->cost)`: `cost`が異なる場合、`p2->cost - p1->cost`を返します（降順ソート）。
2.  `if(p1->varno != p2->varno)`: `varno`が異なる場合、`p2->varno - p1->varno`を返します（降順ソート）。
3.  `if(p1->enter != p2->enter)`: `enter`フィールドが異なる場合、`p2->enter->id - p1->enter->id`を返します。`enter`はおそらく領域のエントリポイントを指し、`id`はそのエントリポイントのユニークな識別子です。

これらの変更により、`cost`と`varno`が同じであっても、`enter`が異なる場合は必ず非ゼロの値が返され、ソート順序が決定論的になります。最終的に`return 0;`が実行されるのは、比較対象の2つの`Rgn`が`cost`、`varno`、`enter`の全てにおいて等しい場合のみです。

これらの変更は、Goコンパイラの内部的なデータ構造のソートが、実行環境や`qsort`の実装に依存せず、常に同じ結果を生成するようにするためのものです。これにより、Goのビルドプロセス全体の再現性が向上します。

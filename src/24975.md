## 変更の背景

Goコンパイラの最適化フェーズの一つであるデッドストアエリミネーション（DSE）は、プログラムの実行に影響を与えない不要なメモリ書き込み（ストア）を削除することで、生成されるコードの効率を向上させます。しかし、このコミット以前は、GoコンパイラのSSAバックエンドにおいて、`vardef`（変数定義）と`varkill`（変数破棄）という特定のSSA操作が、メモリへの「書き込み」だけでなく「読み込み」としても誤って認識されていました。

DSEは、あるメモリ位置への書き込みが行われた後、そのメモリ位置が次に読み込まれることなく、別の書き込みによって上書きされるか、変数のスコープが終了する場合に、最初の書き込みを「デッドストア」と判断し削除します。`vardef`や`varkill`がメモリの読み込みとして扱われると、DSEのアルゴリズムは、これらの操作が実際にはメモリの内容を使用しないにもかかわらず、メモリが「読み込まれた」と誤解してしまいます。その結果、本来削除されるべきデッドストアが削除されずに残り、コンパイラの最適化能力が低下していました。

このコミットは、この誤認識を修正し、`vardef`と`varkill`をメモリの読み込みとして扱わないようにすることで、DSEが意図通りに機能し、より効果的な最適化が行われるようにすることを目的としています。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において広く用いられる中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データのフロー解析が大幅に簡素化され、デッドコードエリミネーション、共通部分式除去、レジスタ割り当てなどの様々な最適化が容易になります。Goコンパイラも、最適化の主要な段階でSSA形式を使用しています。

### 2. GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木（AST）に変換した後、中間表現としてSSA形式に変換します。このSSA形式のコードに対して、様々な最適化パス（例: デッドコードエリミネーション、インライン化、スケジューリング、レジスタ割り当てなど）が適用されます。本コミットが関連するのは、このSSA形式に対する最適化パスの一つであるデッドストアエリミネーションです。

### 3. デッドストアエリミネーション (Dead Store Elimination: DSE)

DSEは、コンパイラ最適化の一種で、プログラムの実行結果に影響を与えないメモリへの書き込み（ストア）を特定し、削除します。具体的には、あるメモリ位置に値が書き込まれた後、その値が読み出されることなく、別の値で上書きされるか、そのメモリ位置がスコープ外になる場合、最初の書き込みは「デッドストア」とみなされ、削除されます。これにより、不要なメモリ操作が減り、プログラムの実行速度が向上し、コードサイズが削減される可能性があります。

### 4. `vardef` と `varkill` 操作

GoコンパイラのSSA形式において、`vardef`と`varkill`は、変数のライフタイム管理に関連する特殊な操作です。これらは、実際のデータ操作（値の読み書き）ではなく、コンパイラが変数のスタック上の位置を確保したり解放したりするタイミングを示すために使用されます。

*   **`OpVarDef` (vardef)**: 変数が定義され、そのためのスタック上の領域が確保されることを示します。これは、変数が「生きている」状態になる開始点です。
*   **`OpVarKill` (varkill)**: 変数がスコープを抜け、そのスタック上の領域が解放されることを示します。これは、変数が「死んでいる」状態になる終了点です。

これらの操作は、メモリの割り当てや解放の概念をSSAグラフ上で表現するために存在しますが、変数の「値」を読み出す操作ではありません。

## 技術的詳細

このコミットの技術的詳細の中心は、`src/cmd/compile/internal/ssa/deadstore.go` ファイル内の `dse` 関数における条件式の変更です。`dse` 関数は、デッドストアエリミネーションのロジックを実装しています。

DSEのアルゴリズムでは、メモリ操作を分析し、どの操作がメモリを「読み込み」または「書き込み」しているかを追跡します。このコミット以前は、`dse` 関数内でメモリ操作を分析する際に、`v.Op != OpStore && v.Op != OpZero` という条件で、`OpStore`（書き込み）と`OpZero`（ゼロ埋め書き込み）以外の操作を、メモリの「読み込み」として `loadUse` セットに追加していました。

しかし、前述の通り、`OpVarDef`と`OpVarKill`はメモリの値を読み出す操作ではありません。これらが`loadUse`セットに追加されると、DSEは「このメモリ位置は`vardef`または`varkill`によって読み込まれた」と誤解し、その前のデッドストアを削除できなくなっていました。

このコミットでは、この条件式を `v.Op != OpStore && v.Op != OpZero && v.Op != OpVarDef && v.Op != OpVarKill` に変更しました。これにより、`OpVarDef`と`OpVarKill`が明示的にメモリの読み込み操作から除外されます。結果として、DSEはこれらの操作をメモリの読み込みとして考慮しなくなり、本来デッドストアとして削除されるべき書き込みを正しく特定し、削除できるようになります。

この修正は、GoコンパイラのSSAバックエンドにおけるメモリ操作のセマンティクスをより正確に反映させ、最適化の有効性を向上させるものです。

## コアとなるコードの解説

変更された行は、`src/cmd/compile/internal/ssa/deadstore.go` ファイル内の `dse` 関数にあります。

元のコード:
```go
if v.Op != OpStore && v.Op != OpZero {
    // CALL, DUFFCOPY, etc. are both
    // reads and writes.
    loadUse.add(a.ID)
}
```

変更後のコード:
```go
if v.Op != OpStore && v.Op != OpZero && v.Op != OpVarDef && v.Op != OpVarKill {
    // CALL, DUFFCOPY, etc. are both
    // reads and writes.
    loadUse.add(a.ID)
}
```

このコードスニペットは、SSA値 `v` がメモリ操作を表す場合に、それがメモリの「読み込み」であるかどうかを判断するロジックの一部です。

*   `v.Args` は、現在のSSA値 `v` の引数（オペランド）のリストです。
*   `a.Block == b && a.Type.IsMemory()` は、引数 `a` が現在のブロック `b` に属し、かつメモリ型（`TypeMemory`）であるかどうかをチェックしています。これは、メモリの状態を表すSSA値（メモリチェーン）を追跡するために重要です。
*   `storeUse.add(a.ID)` は、引数 `a` がメモリへの書き込み（ストア）として使用されていることを記録します。

問題の箇所は、`loadUse.add(a.ID)` が実行される条件です。
変更前は、`v.Op` が `OpStore`（通常のストア）または `OpZero`（ゼロ埋めストア）でない限り、その操作はメモリの読み込み（`loadUse`）として扱われていました。しかし、`OpVarDef`や`OpVarKill`はストア操作ではありませんが、メモリを読み出す操作でもありません。

変更後は、条件に `&& v.Op != OpVarDef && v.Op != OpVarKill` が追加されました。これにより、`OpVarDef`と`OpVarKill`が明示的にメモリの読み込み操作から除外されます。つまり、これらの操作は `loadUse` セットに追加されなくなり、DSEはこれらの操作をメモリの読み込みとして誤解することがなくなります。

この修正により、`vardef`や`varkill`によってデッドストアエリミネーションが妨げられることがなくなり、コンパイラはより多くの不要なメモリ書き込みを削除できるようになります。コメント `// CALL, DUFFCOPY, etc. are both // reads and writes.` は、`OpStore`, `OpZero`, `OpVarDef`, `OpVarKill` 以外の操作（例えば関数呼び出しやメモリコピー操作）は、メモリを読み込みつつ書き込む可能性があるため、引き続き `loadUse` に追加されることを示唆しています。

# [インデックス 23191] ファイルの概要

## 変更の背景

この変更の背景には、Go言語の`net`パッケージにおけるDNS TXTレコードのパース処理が、DNSの標準仕様であるRFC 1035に完全に準拠していなかったという問題があります。

RFC 1035のセクション3.3.14では、TXT (Text) レコードのRDATA (Resource Data) フォーマットについて定義されており、そこには「1つまたは複数の`<character-string>`を含むことができる」と明記されています。`<character-string>`とは、長さを示す1バイトのオクテットと、それに続くその長さのテキストデータから構成される形式です。

しかし、Goの既存の実装では、TXTレコードが複数の`<character-string>`を含んでいる場合に、それを正しく解釈できず、「no such host」という誤ったエラーを返していました。これは、例えばSPF (Sender Policy Framework) レコードやDKIM (DomainKeys Identified Mail) レコードなど、複数の文字列を連結して長いテキスト情報を表現するTXTレコードの利用において問題となります。この不正確な挙動は、GoアプリケーションがDNSベースの認証メカニズムやサービスディスカバリなどを利用する際に、予期せぬ失敗を引き起こす可能性がありました。

この問題はGoのIssue #10482として報告されており、本コミットはその問題を修正し、GoのDNSパーサーをRFC 1035の仕様に適合させることを目的としています。

## 前提知識の解説

### DNS (Domain Name System)

DNSは、インターネット上のコンピュータやサービスを識別するための階層的な分散型命名システムです。人間が覚えやすいドメイン名（例: `example.com`）を、コンピュータが理解できるIPアドレス（例: `192.0.2.1`）に変換する役割を主に担っています。

### DNSレコードタイプ

DNSには様々なレコードタイプがあり、それぞれ異なる種類の情報を保持しています。
*   **Aレコード**: ドメイン名をIPv4アドレスにマッピングします。
*   **AAAAレコード**: ドメイン名をIPv6アドレスにマッピングします。
*   **MXレコード**: ドメインのメールサーバーを指定します。
*   **CNAMEレコード**: ドメインの別名を指定します。
*   **NSレコード**: ドメインのネームサーバーを指定します。
*   **TXTレコード**: ドメインに関連付けられた任意のテキスト情報を保持します。SPFやDKIM、DMARCなどのメール認証情報、あるいはサービスディスカバリのための情報など、多岐にわたる用途で利用されます。

### TXTレコードのフォーマット (RFC 1035 3.3.14)

TXTレコードのRDATAフィールドは、1つまたは複数の`<character-string>`のシーケンスで構成されます。各`<character-string>`は以下の形式です。

`[length byte][text data]`

*   **length byte**: 1バイトのオクテットで、それに続く`text data`の長さを指定します。値は0から255までです。
*   **text data**: `length byte`で指定された長さのテキストデータです。

例えば、`"v=spf1"`と`"include:_spf.google.com"`という2つの文字列を持つTXTレコードは、DNSパケット内では以下のように表現されます（簡略化された例）：

`[0x06]v=spf1[0x14]include:_spf.google.com`

ここで、`0x06`は`v=spf1`の長さ（6バイト）、`0x14`は`include:_spf.google.com`の長さ（20バイト）を示します。Goの以前の実装では、最初の`[0x06]v=spf1`しか正しくパースできず、その後の文字列を無視するか、パースエラーとして扱っていました。

### Go言語の`net`パッケージ

Go言語の標準ライブラリである`net`パッケージは、ネットワークI/Oのプリミティブを提供します。これには、TCP/IP、UDP、IP、Unixドメインソケットなどのネットワークプロトコルを扱う機能や、DNSルックアップを行う機能が含まれます。DNS関連の処理は、このパッケージ内の`dnsmsg.go`などのファイルで実装されています。

## 技術的詳細

このコミットの技術的な核心は、`src/net/dnsmsg.go`ファイル内の`dnsRR_TXT`構造体の`Walk`メソッドの修正にあります。

`dnsRR_TXT`構造体は、DNSのTXTレコードを表します。`Walk`メソッドは、DNSメッセージのパース処理中に、レコードの各フィールドを「ウォーク」（走査）し、その値を抽出するために使用されます。

修正前は、`dnsRR_TXT.Walk`メソッドはTXTレコードのRDATAから最初の`<character-string>`しか読み取っていませんでした。これは、`f(&rr.Txt, "Txt", "")`という呼び出しが一度しか行われず、`rr.Txt`フィールドに最初の文字列のみが設定されていたためです。

RFC 1035の仕様では、TXTレコードのRDATAは複数の`<character-string>`を連結したものであるため、RDATA全体の長さ（`rr.Hdr.Rdlength`）が、個々の`<character-string>`の長さの合計と一致する必要があります。

新しい実装では、`Walk`メソッド内にループが導入されました。このループは、RDATAの残りのバイト数（`rr.Hdr.Rdlength - n`）がまだ存在し、かつ次の`<character-string>`の長さを読み取るのに十分なバイトがある限り繰り返されます。

ループ内で、`f(&txt, "Txt", "")`を呼び出すことで、次の`<character-string>`が`txt`変数に読み込まれます。その後、読み込まれた`txt`の長さと、その長さを表す1バイト（`+ 1`）を`n`に加算し、`rr.Txt`に連結していきます。これにより、TXTレコード内のすべての`<character-string>`が正しく連結され、`rr.Txt`フィールドに完全なテキストデータとして格納されるようになります。

また、パース中のデータ整合性チェックも強化されています。
*   `rr.Hdr.Rdlength-n < uint16(len(txt))+1`：これは、残りのRDATAの長さが、現在読み取ろうとしている文字列の長さと、その長さを表す1バイトの合計よりも短い場合に`false`を返し、パースを中断します。これにより、不正なフォーマットのTXTレコードに対する堅牢性が向上します。

テストファイル`src/net/dnsmsg_test.go`には、複数の`<character-string>`を含むTXTレコードのテストケースが追加され、この修正が正しく機能することを確認しています。特に、`TestDNSParseTXTReply`関数は、単一および複数の文字列を含むTXTレコードが正しくパースされることを検証しています。また、不正な長さ情報を持つTXTレコードに対するテストケース（`TestDNSParseTXTCorruptDataLengthReply`, `TestDNSParseTXTCorruptTXTLengthReply`）も追加され、エラーハンドリングの堅牢性も確認されています。

## コアとなるコードの解説

`src/net/dnsmsg.go`の`dnsRR_TXT.Walk`メソッドの変更は、DNS TXTレコードのパースロジックを根本的に修正しています。

変更前:
```go
func (rr *dnsRR_TXT) Walk(f func(v interface{}, name, tag string) bool) bool {
	return rr.Hdr.Walk(f) && f(&rr.Txt, "Txt", "")
}
```
このコードは、`rr.Hdr.Walk(f)`が成功した後、`f(&rr.Txt, "Txt", "")`を一度だけ呼び出していました。`f`関数は、DNSメッセージのバイト列から指定された型のデータを読み取る役割を担っています。この単一の呼び出しでは、TXTレコードのRDATAから最初の`<character-string>`しか読み取ることができませんでした。

変更後:
```go
func (rr *dnsRR_TXT) Walk(f func(v interface{}, name, tag string) bool) bool {
	if !rr.Hdr.Walk(f) {
		return false
	}
	var n uint16 = 0
	for n < rr.Hdr.Rdlength {
		var txt string
		if !f(&txt, "Txt", "") {
			return false
		}
		// more bytes than rr.Hdr.Rdlength said there woudld be
		if rr.Hdr.Rdlength-n < uint16(len(txt))+1 {
			return false
		}
		n += uint16(len(txt)) + 1
		rr.Txt += txt
	}
	return true
}
```
1.  `if !rr.Hdr.Walk(f) { return false }`: まず、レコードヘッダのウォーク処理を試みます。これが失敗した場合は、それ以上処理を進めずに`false`を返します。
2.  `var n uint16 = 0`: `n`は、これまでに読み込んだRDATAのバイト数を追跡するための変数です。
3.  `for n < rr.Hdr.Rdlength`: このループが変更の核心です。`n`がRDATA全体の長さ（`rr.Hdr.Rdlength`）に達するまで、つまりRDATAのすべてのバイトを処理し終えるまでループを続けます。
4.  `var txt string`: 各イテレーションで、新しい`<character-string>`を一時的に保持するための`txt`変数を宣言します。
5.  `if !f(&txt, "Txt", "") { return false }`: ここで`f`関数を呼び出し、次の`<character-string>`を`txt`に読み込みます。この`f`関数は、DNSメッセージのバイト列から、まず1バイトの長さフィールドを読み取り、次にその長さのテキストデータを読み取って`txt`に格納します。読み込みが失敗した場合は、`false`を返して処理を終了します。
6.  `if rr.Hdr.Rdlength-n < uint16(len(txt))+1 { return false }`: これは重要なバリデーションチェックです。残りのRDATAのバイト数（`rr.Hdr.Rdlength-n`）が、現在読み込んだ`txt`の長さと、その長さを表す1バイト（`+1`）の合計よりも小さい場合、これはデータが破損しているか、不正なフォーマットであることを意味します。この場合も`false`を返して処理を終了し、不正なデータによるパニックや予期せぬ動作を防ぎます。
7.  `n += uint16(len(txt)) + 1`: 正常に読み込んだ`txt`の長さと、その長さを表す1バイトを`n`に加算し、次に読み込むべき位置を更新します。
8.  `rr.Txt += txt`: 読み込んだ`txt`を、`dnsRR_TXT`構造体の`Txt`フィールドに連結します。これにより、複数の`<character-string>`が1つの文字列として結合されます。

このループとバリデーションにより、GoのDNSパーサーはRFC 1035に準拠し、複数の`<character-string>`を含むTXTレコードを正しく解釈できるようになりました。

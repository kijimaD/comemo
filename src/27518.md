# [インデックス 27518] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）とランタイム（`runtime`）における、整数から文字列への変換処理の厳密な修正に関するものです。特に、整数値が有効なUnicodeコードポイントの範囲外である場合に、Go言語の仕様に従って正しく`\uFFFD`（Unicode置換文字）を生成するように動作を改善しています。

## 元コミット内容

以前の`cmd/compile`は、定数の整数から文字列への変換において、整数値が`int`型に収まらない場合に変換を拒否していました。また、`runtime`は64ビット値を32ビットに誤って切り捨ててから、それが有効なUnicodeコードポイントであるかをチェックしていました。Go言語の仕様によれば、これらのケースはいずれも`"\uFFFD"`を生成すべきです。このコミットはこれらの問題を修正します。

Fixes #15039.

## 変更の背景

この変更は、Go言語の仕様に厳密に準拠するためのものです。Go言語では、整数値を直接`string`型にキャストすると、その整数値はUnicodeコードポイントとして解釈され、対応する文字のUTF-8エンコードされたバイト列を持つ文字列が生成されます。しかし、この処理において、以下のような問題がありました。

1.  **`cmd/compile`における定数変換の不備**: コンパイル時に行われる定数の整数から文字列への変換で、その整数値がGoの組み込み型`int`の範囲を超えている場合、コンパイラはエラーとして処理し、変換を拒否していました。しかし、Goの仕様では、有効なUnicodeコードポイントの範囲外の整数値が`string`に変換される場合、エラーではなくUnicode置換文字である`\uFFFD`（U+FFFD）を生成することが求められています。
2.  **`runtime`における64ビット値の誤った処理**: ランタイムにおける`int64`から`string`への変換処理では、入力された64ビット整数値が、有効なUnicodeコードポイントの範囲（通常U+0000からU+10FFFF）を超えていた場合、その値を32ビットに切り捨ててから有効性チェックを行っていました。これにより、本来`\uFFFD`となるべき無効なコードポイントが、誤って別の有効なコードポイントとして扱われたり、あるいは不正な動作を引き起こす可能性がありました。

これらの不整合は、Go言語の仕様（特に[Go Language Specification - Conversions](https://go.dev/ref/spec#Conversions)の「Conversions to and from a string type」セクション）に違反しており、一貫性のない挙動を招いていました。`issue #15039`で報告されたこの問題は、Goプログラムの予測可能性と移植性を高めるために修正が必要でした。

## 前提知識の解説

### Unicodeとコードポイント

*   **Unicode**: 世界中の文字を統一的に扱うための文字コード標準です。
*   **コードポイント**: Unicodeにおいて、各文字に割り当てられた一意の数値です。例えば、`'A'`はU+0041、`'あ'`はU+3042といったコードポイントを持ちます。
*   **有効なUnicodeコードポイントの範囲**: U+0000からU+10FFFFまでです。この範囲外の数値は、有効なUnicode文字としては扱われません。

### Go言語における`rune`と`string`

*   **`rune`型**: Go言語では、`rune`はUnicodeコードポイントを表す組み込み型であり、`int32`のエイリアスです。
*   **`string`型**: Go言語の`string`は、UTF-8でエンコードされたバイト列の読み取り専用スライスです。
*   **整数から`string`への変換**: Goにおいて、整数値を`string`型に直接キャスト（例: `string(i)`）すると、その整数値はUnicodeコードポイントとして解釈されます。
    *   もし整数値が有効なUnicodeコードポイントであれば、そのコードポイントに対応する文字のUTF-8エンコードされたバイト列を持つ文字列が生成されます。
    *   もし整数値が有効なUnicodeコードポイントの範囲外（U+0000未満またはU+10FFFF超）であれば、Goの仕様により、Unicode置換文字`\uFFFD`（U+FFFD）が生成されます。これは、無効な文字を視覚的に示すための標準的な方法です。

### `\uFFFD` (Unicode Replacement Character)

`\uFFFD`は、Unicodeの置換文字（Replacement Character）です。これは、テキスト処理において、エンコーディングエラーや無効な文字シーケンスが検出された際に、その無効な文字の代わりに表示される特殊な文字です。この文字が生成されることで、プログラムは不正な入力に対してもクラッシュすることなく、問題があることを明示的に示すことができます。

## 技術的詳細

このコミットは、Goコンパイラとランタイムの2つの異なる場所で、整数から文字列への変換ロジックを修正しています。

1.  **`src/cmd/compile/internal/gc/const.go`の修正**:
    *   このファイルはGoコンパイラの定数評価部分を担当しています。以前は、定数`int`から`string`への変換で、整数値が`int`型の最大値や最小値を超えるとエラー（`Yyerror("overflow in int -> string")`）を発生させていました。
    *   修正後は、まずデフォルトで`\uFFFD`のコードポイントである`0xFFFD`を`i`に設定します。
    *   次に、変換対象の整数値`u`が`TUINT32`（`uint32`型）の範囲内にある場合にのみ、その値を`i`に代入します。`TUINT32`の範囲は、有効なUnicodeコードポイントの範囲をカバーするのに十分です。
    *   最終的に、`string(i)`として変換を行います。これにより、有効なUnicodeコードポイントの範囲内の値は対応する文字に、範囲外の値は`\uFFFD`に変換されるようになります。コンパイル時のエラーは発生しなくなります。

2.  **`src/runtime/string.go`の修正**:
    *   このファイルはGoランタイムの文字列操作、特に`intstring`関数（整数値を文字列に変換する内部関数）を含んでいます。以前の`intstring`関数は、`int64`型の入力`v`を`rune(v)`として直接`rune`型にキャストしていました。`rune`は`int32`のエイリアスであるため、このキャストは64ビット値の上位32ビットを暗黙的に切り捨てていました。その結果、非常に大きな64ビット値が無効なUnicodeコードポイントであるにもかかわらず、切り捨てられた下位32ビットが有効なコードポイントとして扱われる可能性がありました。
    *   修正では、`if int64(rune(v)) != v`というチェックが追加されました。これは、元の`int64`値`v`を`rune`にキャストし、その`rune`を再度`int64`にキャストした結果が元の`v`と異なる場合、つまり`rune`へのキャストによって値が切り捨てられた（情報が失われた）ことを意味します。
    *   この条件が真の場合、`v`は`runeerror`（`\uFFFD`のコードポイント）に設定されます。これにより、64ビット値が`rune`の範囲を超えていた場合でも、Goの仕様に従って`\uFFFD`が生成されるようになります。

これらの変更により、コンパイル時とランタイム時の両方で、整数から文字列への変換がGoの仕様に厳密に準拠し、無効なUnicodeコードポイントに対しては一貫して`\uFFFD`が生成されるようになりました。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/const.go`の変更点

*   **変更前**:
    ```go
    if v.U.(*Mpint).Cmp(Minintval[TINT]) < 0 || v.U.(*Mpint).Cmp(Maxintval[TINT]) > 0 {
        Yyerror("overflow in int -> string")
    }
    r := uint(v.U.(*Mpint).Int64())
    v.U = string(r)
    ```
    ここでは、定数`v`が`int`型の範囲を超えている場合にコンパイルエラーを発生させていました。そして、`uint`にキャストしてから`string`に変換していました。これはGoの仕様に反していました。

*   **変更後**:
    ```go
    var i int64 = 0xFFFD
    if u := v.U.(*Mpint); u.Cmp(Minintval[TUINT32]) >= 0 && u.Cmp(Maxintval[TUINT32]) <= 0 {
        i = u.Int64()
    }
    v.U = string(i)
    ```
    1.  `var i int64 = 0xFFFD`: まず、変換結果のデフォルト値を`\uFFFD`のコードポイント（`0xFFFD`）に設定します。
    2.  `if u := v.U.(*Mpint); u.Cmp(Minintval[TUINT32]) >= 0 && u.Cmp(Maxintval[TUINT32]) <= 0`: 定数`u`が`uint32`の範囲内にあるかどうかをチェックします。`uint32`の範囲は、有効なUnicodeコードポイントの範囲（U+0000からU+10FFFF）を十分にカバーします。
    3.  `i = u.Int64()`: `u`が`uint32`の範囲内であれば、その値を`i`に代入します。
    4.  `v.U = string(i)`: 最終的に`i`を`string`に変換します。これにより、有効なコードポイントは対応する文字に、無効なコードポイント（`uint32`の範囲外）は`\uFFFD`に変換されるようになります。

### `src/runtime/string.go`の変更点

*   **変更前**:
    ```go
    // ...
    n := runetochar(b, rune(v))
    return s[:n]
    ```
    `intstring`関数は、`int64`型の`v`を直接`rune(v)`にキャストしていました。`rune`は`int32`のエイリアスであるため、`v`が`int32`の範囲を超えている場合、上位ビットが切り捨てられていました。

*   **変更後**:
    ```go
    // ...
    if int64(rune(v)) != v {
        v = runeerror
    }
    n := runetochar(b, rune(v))
    return s[:n]
    ```
    1.  `if int64(rune(v)) != v`: この条件式が追加されました。
        *   `rune(v)`: `int64`値`v`を`rune`（`int32`）にキャストします。このとき、`v`が`int32`の範囲を超えていると値が切り捨てられます。
        *   `int64(rune(v))`: 切り捨てられた可能性のある`rune`値を再度`int64`にキャストします。
        *   `!= v`: この再キャストされた`int64`値が元の`v`と異なる場合、それは`rune`へのキャスト時に情報が失われた（つまり、元の`v`が`rune`の範囲を超えていた）ことを意味します。
    2.  `v = runeerror`: もし情報が失われていた場合、`v`を`runeerror`（`\uFFFD`のコードポイント）に設定します。
    3.  `n := runetochar(b, rune(v))`: 修正された`v`（または元の有効な`v`）を`rune`にキャストし、`runetochar`関数でUTF-8バイト列に変換します。

### `test/fixedbugs/issue15039.go`の追加

このテストファイルは、上記の2つの修正が正しく機能することを確認するために追加されました。

*   `u := uint64(0x10001f4a9)`: `uint64`で非常に大きな値（有効なUnicodeコードポイントの範囲をはるかに超える）を定義し、`string(u)`で変換します。この結果が`\uFFFD`になることを期待します。これは`runtime`の修正をテストします。
*   `const huge = string(1<<100)`: `1<<100`という非常に大きな定数（`int`の範囲をはるかに超える）を定義し、`string(1<<100)`で変換します。この結果が`\uFFFD`になることを期待します。これは`cmd/compile`の修正をテストします。

これらのテストケースは、以前のバグが修正され、Goの仕様に準拠した動作が実現されたことを検証します。

# [インデックス 27241] ファイルの概要

## コミット

このコミットは、Goリンカ（`cmd/link`）において、重複シンボル（`.dup`シンボル）が`Allsym`リストに誤って追加される問題を修正します。この問題は、共有ライブラリのビルド時に`Allsym`内のすべてのシンボルが到達可能としてマークされるため、`.dup`シンボルがデッドコード削除の仮定を破り、不適切な動作を引き起こす可能性がありました。この変更により、`.dup`シンボルが`Allsym`に追加されなくなり、リンカの処理が効率化され、共有ライブラリのサイズが削減される可能性があります。また、`.dup`シンボルがランタイム共有ライブラリに含まれないことを保証するテストが追加されました。

## 変更の背景

Go言語のリンカ（`cmd/link`）は、プログラムのビルドプロセスにおいて、複数のオブジェクトファイルやライブラリからシンボルを収集し、最終的な実行可能ファイルや共有ライブラリを生成します。この過程で、リンカは`Allsym`というリストにすべてのシンボルを保持します。

問題は、共有ライブラリをビルドする際に発生していました。複数のパッケージファイルから「`dupok`」シンボルが読み込まれると、リンカは内部的に「`.dup`」という名前の重複シンボルを作成していました。これらの`.dup`シンボルも`Allsym`リストに追加されていました。

しかし、共有ライブラリのビルド時には、`Allsym`リスト内のすべてのシンボルが「到達可能（reachable）」としてマークされます。これは、デッドコード削除（dead code elimination）のプロセスにおいて、到達可能なコードは削除されないという仮定に基づいています。`.dup`シンボルは本来、リンカの内部的な処理で生成される一時的なものであり、最終的なバイナリには含まれるべきではありませんでした。

デッドコード削除のロジックがこれらの`.dup`シンボルに対して誤った仮定を置いたため、共有ライブラリのビルドが壊れるという問題が発生しました。具体的には、`.dup`シンボルが不必要にバイナリに含まれることで、共有ライブラリのサイズが増加したり、リンカの処理が非効率になったりする可能性がありました。このコミットは、この根本的な問題を解決し、リンカの健全性と効率性を向上させることを目的としています。

## 前提知識の解説

*   **Goリンカ (`cmd/link`)**: Goプログラムをコンパイルした後、複数のオブジェクトファイルやライブラリを結合して実行可能ファイルや共有ライブラリを生成するツールです。シンボルの解決、アドレスの割り当て、デッドコード削除などを行います。
*   **シンボル (Symbol)**: プログラム内の関数、変数、型などの名前と、それらがメモリ上のどこに配置されるかを示す情報です。リンカはこれらのシンボルを管理し、参照を解決します。
*   **`Allsym`**: Goリンカの内部データ構造で、リンカが処理するすべてのシンボルを保持するリストです。リンカは、このリストを繰り返し処理して、シンボルの解決や最適化を行います。
*   **`.dup` シンボル**: リンカが複数のパッケージファイルから同じ「`dupok`」シンボルを読み込んだ際に、内部的に生成する重複シンボルです。これらは通常、リンカの内部処理のための一時的なものであり、最終的なバイナリには含まれるべきではありません。
*   **`dupok` シンボル**: Goリンカにおける特定の種類のシンボルで、複数の定義が存在しても問題ないとされるものです。例えば、一部の組み込み型や共通の定数などがこれに該当することがあります。
*   **共有ライブラリ (Shared Library)**: 複数のプログラムで共有されるコードやデータを含むライブラリです（例: `.so`ファイル、`.dll`ファイル）。これにより、ディスクスペースの節約やメモリ使用量の削減が可能です。
*   **デッドコード削除 (Dead Code Elimination)**: コンパイラやリンカの最適化手法の一つで、プログラムの実行に決して到達しない、または影響を与えないコード（デッドコード）を最終的なバイナリから削除することです。これにより、バイナリサイズが削減され、起動時間や実行効率が向上します。
*   **到達可能性 (Reachability)**: プログラムの実行フローにおいて、特定のコードやデータがアクセス可能であるかどうかを示す概念です。デッドコード削除では、到達不可能なコードは削除の対象となります。

## 技術的詳細

このコミットの核心は、Goリンカが`.dup`シンボルを`Allsym`リストに追加しないようにすることです。これにより、共有ライブラリのビルド時にこれらのシンボルが誤って到達可能とマークされ、デッドコード削除のロジックを混乱させることを防ぎます。

具体的な変更点は以下の通りです。

1.  **`readsym` 関数における `.dup` シンボルの生成**:
    *   `src/cmd/link/internal/ld/objfile.go` 内の `readsym` 関数は、オブジェクトファイルからシンボルを読み込む際に、重複する`dupok`シンボルを見つけると、新しい`.dup`シンボルを作成します。
    *   変更前は、`linknewsym`関数を呼び出す際に、`readsym_ndup`というカウンタを使用して一意のバージョン番号を割り当てていました。
    *   変更後は、`linknewsym`関数を呼び出す際に、`.dup`シンボルに対してはバージョン番号として`-1`を渡すようになりました。これは、このシンボルが`Allsym`に追加されるべきではないことを示す特別な値として機能します。

2.  **`linknewsym` 関数における `Allsym` への追加ロジックの変更**:
    *   `src/cmd/link/internal/ld/sym.go` 内の `linknewsym` 関数は、新しいシンボルを作成し、`ctxt.Allsym`リストに追加する役割を担っています。
    *   変更前は、すべての新しいシンボルが無条件に`ctxt.Allsym`に追加されていました。
    *   変更後は、シンボルのバージョン番号`v`が`-1`でない場合にのみ、シンボルを`ctxt.Allsym`に追加するようになりました。これにより、`readsym`から`-1`で渡された`.dup`シンボルは`Allsym`リストから除外されます。
    *   また、`v < -1`の場合には診断メッセージを出力するエラーチェックも追加されました。

3.  **`decodetype_methods` 関数におけるパニックメッセージの改善**:
    *   `src/cmd/link/internal/ld/decodesym.go` 内の `decodetype_methods` 関数で発生するパニックメッセージが、より詳細な情報（シンボルの名前と参照先のシンボルの名前）を含むように改善されました。これは直接的なバグ修正ではありませんが、デバッグ情報の質を向上させます。

4.  **テストの追加**:
    *   `misc/cgo/testshared/shared_test.go` に `TestNoDupSymbols` という新しいテストが追加されました。
    *   このテストは、ビルドされた共有ライブラリ（`libstd.so`など）をELF形式で開き、そのシンボルテーブルを走査します。
    *   もし共有ライブラリ内に「`.dup`」という名前のシンボルが見つかった場合、テストは失敗し、リンカが`.dup`シンボルを適切に除外できていないことを示します。これにより、将来的に同様の問題が再発するのを防ぎます。

これらの変更により、リンカは`.dup`シンボルを`Allsym`リストに含めなくなり、共有ライブラリのビルドプロセスにおけるデッドコード削除の仮定が正しく機能するようになります。結果として、共有ライブラリのサイズが最適化され、リンカの全体的なパフォーマンスが向上する可能性があります。

## コアとなるコードの解説

### `src/cmd/link/internal/ld/objfile.go` の変更

*   `readsym_ndup` 変数が削除されました。これは、`.dup`シンボルに一意のバージョン番号を割り当てるために使用されていましたが、新しいアプローチでは不要になりました。
*   `linknewsym(ctxt, ".dup", readsym_ndup)` の呼び出しが `linknewsym(ctxt, ".dup", -1)` に変更されました。これにより、`.dup`シンボルが作成される際に、バージョン番号として`-1`が明示的に渡されるようになります。この`-1`は、後述の`linknewsym`関数で特別な意味を持ちます。

### `src/cmd/link/internal/ld/sym.go` の変更

*   `linknewsym` 関数内で、`ctxt.Allsym = append(ctxt.Allsym, s)` の行が条件付きのブロックに変更されました。
*   `if v != -1` という条件が追加され、渡されたバージョン番号`v`が`-1`でない場合にのみ、シンボル`s`が`ctxt.Allsym`リストに追加されるようになりました。
*   これにより、`objfile.go`の`readsym`関数から`-1`のバージョン番号で渡された`.dup`シンボルは、`Allsym`リストに追加されなくなります。
*   `else if v < -1` というエラーチェックも追加され、無効なバージョン番号が渡された場合にリンカが診断メッセージを出力するようになりました。

### `misc/cgo/testshared/shared_test.go` の変更

*   `TestNoDupSymbols` という新しいテスト関数が追加されました。
*   このテストは、`filepath.Join(gorootInstallDir, soname)` を使用して、ビルドされた共有ライブラリのパスを構築します。
*   `elf.Open(sopath)` を呼び出して、ELF形式の共有ライブラリファイルを開きます。
*   `f.Symbols()` を使用して、共有ライブラリ内のすべてのシンボルを読み込みます。
*   読み込んだシンボルをループで走査し、`s.Name == ".dup"` という条件でシンボル名が「`.dup`」であるかどうかをチェックします。
*   もし「`.dup`」という名前のシンボルが見つかった場合、`t.Fatalf` を呼び出してテストを失敗させます。これは、リンカが`.dup`シンボルを共有ライブラリに含めてしまったことを意味し、修正が正しく機能していないことを示します。

これらの変更は連携して機能し、Goリンカが`.dup`シンボルを`Allsym`リストや最終的な共有ライブラリに含めないようにすることで、共有ライブラリのビルドにおけるデッドコード削除の正確性を保証し、リンカの効率を向上させます。

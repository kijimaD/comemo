# [インデックス 22566] ファイルの概要

## 変更の背景

Go言語のビルドシステムは、通常、独自のリンカ (`cmd/link`、以前は `6l`/`8l` など) を使用して実行ファイルを生成します。しかし、`cgo` を使用してC言語のコードをGoプログラムに組み込む場合や、特定のクロスコンパイル環境では、外部のリンカ、特にGNU Binutilsに含まれる `GNU ld` が使用されることがあります。

`cmd/go` ツールは、ビルドプロセス中に様々な種類のオブジェクトファイル（アーカイブ、ELF、Mach-O、PEなど）を識別するために、ファイルの先頭にある特定のマジックバイト（シグネチャ）をチェックします。このコミット以前は、Goの `cmd/go` がPEファイルを識別するために使用していたマジックバイトのパターンが、GNU ldによって生成されたPEファイルと完全に一致しない場合がありました。

この不一致により、GNU ldでリンクされたPEファイルが `cmd/go` によって正しくオブジェクトファイルとして認識されず、ビルドエラーや予期せぬ動作を引き起こす可能性がありました。このコミットは、この問題を解決し、GoツールチェーンがGNU ldによって生成されたPEファイルをより堅牢に識別できるようにすることを目的としています。

## 前提知識の解説

### PE (Portable Executable) フォーマット

PEは、Windowsオペレーティングシステムで使用される実行可能ファイル、オブジェクトコード、DLL (Dynamic Link Library) などのファイル形式です。PEファイルは、MS-DOS互換のヘッダ、PEヘッダ（NTヘッダとも呼ばれる）、セクションヘッダ、および実際のコードとデータを含むセクションで構成されます。

*   **DOSヘッダ**: PEファイルの先頭に位置し、MS-DOSとの後方互換性を提供します。このヘッダの先頭2バイトは常に `0x4D 0x5A` (ASCIIで "MZ") というマジックバイトを持ちます。
*   **PEヘッダ (NTヘッダ)**: DOSヘッダの後に続き、PEファイルの主要な情報（ファイルタイプ、タイムスタンプ、オプションヘッダへのオフセットなど）を含みます。
*   **オプションヘッダ**: PEヘッダの一部であり、実行可能ファイルの特性（エントリポイント、ベースアドレス、セクションのアライメントなど）を定義します。このヘッダ内にも、32ビットPEファイルの場合は `0x10B`、64ビットPEファイルの場合は `0x20B` といったマジックバイトが存在します。

Goの `cmd/go` がオブジェクトファイルを識別する際に参照するマジックバイトは、通常、DOSヘッダの "MZ" シグネチャと、それに続くPEヘッダの特定の部分の組み合わせです。

### GNU ld (GNU Linker)

GNU ldは、GNU Binutilsプロジェクトの一部であるリンカです。リンカは、コンパイラによって生成されたオブジェクトファイル（コンパイルされたソースコード）とライブラリを結合して、実行可能ファイルや共有ライブラリを作成するツールです。

Go言語は通常、独自のリンカを使用しますが、`cgo` を介してC/C++コードをGoプログラムに統合する場合、GoツールチェーンはシステムにインストールされているC/C++コンパイラとリンカ（例えばMinGW環境下のGCCとGNU ld）を利用することがあります。この場合、GNU ldが最終的なPEファイルを生成する役割を担うことになります。

### オブジェクトファイルのマジックバイト

コンピュータシステムでは、様々な種類のファイル（実行可能ファイル、アーカイブ、画像など）を識別するために、ファイル形式の先頭に特定の一連のバイト（マジックバイトまたはファイルシグネチャ）を配置することが一般的です。Goの `cmd/go` ツールも、ビルドプロセス中にこれらのマジックバイトを使用して、入力ファイルがどの種類のオブジェクトファイルであるかを判断します。

`src/cmd/go/build.go` 内の `objectMagic` 変数は、Goが認識する様々なオブジェクトファイル形式のマジックバイトのリストを定義しています。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/go/build.go` ファイル内の `objectMagic` 変数におけるPEファイルのマジックバイトの定義の変更です。

変更前:
```go
{0x4d, 0x5a, 0x90, 0x00, 0x03, 0x00, 0x04, 0x00}, // PE (Windows) as generated by 6l/8l
```
このマジックバイトは、Go独自のリンカ (`6l`/`8l`、現在の `cmd/link` の前身) によって生成されるPEファイルを識別するために使用されていました。このバイト列は、DOSヘッダの `0x4d 0x5a` ("MZ") に続き、DOSスタブの特定のバイト列 (`0x90 0x00 0x03 0x00 0x04 0x00`) を含んでいます。

変更後:
```go
{0x4d, 0x5a, 0x90, 0x00, 0x03, 0x00},      // PE (Windows) as generated by 6l/8l and gcc
```
変更点として、マジックバイトのシーケンスから末尾の `0x04, 0x00` が削除されています。これにより、PEファイルのマジックバイトのパターンが短縮され、より汎用的なものになりました。

この変更の理由は、GNU ld (GCCツールチェーンの一部として使用されることが多い) が生成するPEファイルのDOSスタブ部分が、Goのリンカが生成するものと完全に同じではない場合があるためです。特に、`0x04, 0x00` の部分がGNU ldによって生成されたファイルでは異なるか、存在しない可能性がありました。

マジックバイトのパターンを短縮することで、`cmd/go` は、Go独自のリンカによって生成されたPEファイルだけでなく、GNU ldによって生成されたPEファイルも正しく「PEファイルである」と識別できるようになります。これにより、Goツールチェーンと外部リンカ（特にWindows環境でのクロスコンパイルや `cgo` の使用時）との互換性が向上します。

## コアとなるコードの解説

`src/cmd/go/build.go` ファイルには、Goのビルドプロセスにおける様々な処理が定義されています。このファイル内の `objectMagic` 変数は、Goツールが異なる種類のオブジェクトファイルを識別するために使用するバイトシーケンスの配列です。

`objectMagic` は `[][]byte` 型で、各要素が特定のファイル形式の先頭バイト（マジックバイト）を表しています。`isObject` 関数は、この `objectMagic` 配列を使用して、与えられたファイルが認識可能なオブジェクトファイルであるかどうかをチェックします。

このコミットでは、`objectMagic` 配列のPE (Windows) ファイルに対応するエントリが変更されました。

*   **変更前**: `objectMagic` のPEエントリは `0x4d, 0x5a, 0x90, 0x00, 0x03, 0x00, 0x04, 0x00` でした。これは、PEファイルのDOSヘッダの "MZ" (`0x4d 0x5a`) に続き、DOSスタブの特定のバイト列を期待していました。コメントには「6l/8lによって生成されたPE (Windows)」と記載されており、Go独自のリンカが生成するファイルに特化していたことを示唆しています。
*   **変更後**: PEエントリは `0x4d, 0x5a, 0x90, 0x00, 0x03, 0x00` に短縮されました。末尾の `0x04, 0x00` が削除されています。コメントも「6l/8lとgccによって生成されたPE (Windows)」に変更され、GNU ld (gccツールチェーンの一部) によって生成されたファイルも対象に含める意図が明確に示されています。

この変更により、`isObject` 関数がPEファイルを識別する際のパターンマッチングがより柔軟になり、GNU ldが生成するPEファイルも正しく認識できるようになりました。これは、Goのビルドシステムが外部ツールとの連携を強化し、より多様なビルド環境に対応するための重要な改善です。

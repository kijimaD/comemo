## 変更の背景

`text/scanner` パッケージは、Go言語のツールチェインやその他のテキスト処理アプリケーションで広く利用される基本的なコンポーネントです。このパッケージの `Mode` フィールドは、スキャナーの動作を制御するためのビットフラグのセットであり、`ScanIdents`、`ScanInts`、`SkipComments` などのオプションが含まれています。

しかし、これらのモードがどのように相互作用し、特に「認識されないトークン」がどのように扱われるかについてのドキュメンテーションが不足していました。例えば、`SkipComments` が設定されている場合のコメントの扱い、または `ScanStrings` が設定されていない場合に文字列リテラルがどのようにトークン化されるかといった挙動は、ユーザーにとって直感的ではない可能性がありました。

このコミットは、これらの曖昧さを解消し、`Mode` フィールドの挙動、特にコメントのスキップと未認識トークンの処理に関する明確な説明を追加することで、パッケージの使いやすさと理解度を向上させることを目的としています。これにより、開発者が `text/scanner` をより正確かつ効率的に使用できるようになります。

## 前提知識の解説

### 字句解析（Lexical Analysis）とスキャナー

字句解析は、コンパイラやインタプリタの最初のフェーズであり、ソースコードや入力テキストを、意味を持つ最小単位である「トークン」のシーケンスに変換するプロセスです。このプロセスを実行するプログラムは「字句アナライザ」または「スキャナー（scanner）」と呼ばれます。

スキャナーは、入力ストリームを読み込み、定義されたパターン（正規表現など）に基づいてトークンを識別します。例えば、`if` はキーワードトークン、`myVariable` は識別子トークン、`123` は整数リテラルトークン、`"hello"` は文字列リテラルトークンとして認識されます。

### `text/scanner` パッケージ

Go言語の `text/scanner` パッケージは、このような字句解析の基本的な機能を提供します。このパッケージは、Go言語のソースコードだけでなく、一般的なテキストファイルの解析にも使用できます。

主要なコンポーネントは `scanner.Scanner` 型です。この型は、入力ソース（`io.Reader` から読み込む）と、スキャン動作を制御する `Mode` フィールドを持ちます。

### `Mode` フィールドとビットフラグ

`scanner.Scanner` の `Mode` フィールドは、`int` 型であり、複数のオプションを同時に設定するためにビットフラグとして使用されます。各オプションは `1 << N` の形式で定義され、特定のビット位置に対応します。複数のオプションを有効にするには、ビットごとのOR演算子 (`|`) を使用します。

このコミットで言及されている主なモードは以下の通りです。

*   **`ScanIdents`**: 識別子（変数名、関数名など）をトークンとしてスキャンします。
*   **`ScanInts`**: 整数リテラルをトークンとしてスキャンします。
*   **`ScanStrings`**: 文字列リテラルをトークンとしてスキャンします。このコミットの文脈では、`ScanStrings` が設定されていない場合の挙動が重要になります。
*   **`SkipComments`**: コメントをスキップし、トークンストリームに含めないようにします。

### 未認識トークンの扱い

スキャナーが入力テキストを処理する際、定義されたどのトークンパターンにも一致しない文字シーケンスに遭遇することがあります。これらは「未認識トークン」または「不正なトークン」と呼ばれます。スキャナーの実装によっては、これらのトークンをエラーとして報告したり、個々の文字として返したり、あるいは完全に無視したりする場合があります。`text/scanner` パッケージの挙動は、このコミットで明確化されています。

## 技術的詳細

このコミットは、`src/pkg/text/scanner/scanner.go` ファイルの `Mode` 定義の直前に、6行の新しいコメントを追加しています。この追加されたコメントは、`text/scanner` パッケージの `Mode` フィールドの挙動、特に `SkipComments` オプションと、未認識トークンの処理方法について、以前は暗黙的であった、あるいは不明瞭であった側面を明確にしています。

具体的には、以下の2つの重要な点を説明しています。

1.  **コメントのスキップ**: `SkipComments` フラグが設定されている場合、コメントはスキャナーによって完全にスキップされ、結果として生成されるトークンストリームには含まれません。これは、コメントがプログラムの実行には影響しないため、通常は字句解析の段階で無視されるべきであるという一般的な慣行に沿っています。
2.  **未認識トークンの処理**: `SkipComments` が設定されている場合を除き、スキャナーが認識できないトークンに遭遇した場合の挙動が明確化されています。
    *   スキャナーは、これらの未認識トークンを無視するのではなく、それぞれの個別の文字（または場合によってはサブトークン）を返します。
    *   具体的な例として、`Mode` が `ScanIdents` に設定されており、`ScanStrings` が設定されていない場合、文字列 `"foo"` は単一の文字列トークンとしてではなく、`'`（シングルクォート）、`Ident`（識別子 `foo`）、`'`（シングルクォート）というトークンシーケンスとしてスキャンされることが示されています。これは、`ScanStrings` が有効でない限り、スキャナーが引用符で囲まれたシーケンスを特別な文字列リテラルとして扱わないことを意味します。

これらの説明は、`text/scanner` を使用する開発者が、特定の設定下でスキャナーがどのように動作するかを正確に理解するのに役立ちます。特に、予期しないトークンシーケンスや、文字列リテラルが期待通りに解析されない問題に直面した場合のデバッグに貢献します。

## 変更の背景

`text/scanner` パッケージは、Go言語のツールチェインやその他のテキスト処理アプリケーションで広く利用される基本的なコンポーネントです。このパッケージの `Mode` フィールドは、スキャナーの動作を制御するためのビットフラグのセットであり、`ScanIdents`、`ScanInts`、`SkipComments` などのオプションが含まれています。

## 前提知識の解説

### 字句解析（Lexical Analysis）とスキャナー

字句解析は、コンパイラやインタプリタの最初のフェーズであり、ソースコードや入力テキストを、意味を持つ最小単位である「トークン」のシーケンスに変換するプロセスです。このプロセスを実行するプログラムは「字句アナライザ」または「スキャナー（scanner）」と呼ばれます。

スキャナーは、入力ストリームを読み込み、定義されたパターン（正規表現など）に基づいてトークンを識別します。例えば、`if` はキーワードトークン、`myVariable` は識別子トークン、`123` は整数リテラルトークン、`"hello"` は文字列リテラルトークンとして認識されます。

### `text/scanner` パッケージ

Go言語の `text/scanner` パッケージは、このような字句解析の基本的な機能を提供します。このパッケージは、Go言語のソースコードだけでなく、一般的なテキストファイルの解析にも使用できます。

主要なコンポーネントは `scanner.Scanner` 型です。この型は、入力ソース（`io.Reader` から読み込む）と、スキャン動作を制御する `Mode` フィールドを持ちます。

### `Mode` フィールドとビットフラグ

`scanner.Scanner` の `Mode` フィールドは、`int` 型であり、複数のオプションを同時に設定するためにビットフラグとして使用されます。各オプションは `1 << N` の形式で定義され、特定のビット位置に対応します。複数のオプションを有効にするには、ビットごとのOR演算子 (`|`) を使用します。

このコミットで言及されている主なモードは以下の通りです。

*   **`ScanIdents`**: 識別子（変数名、関数名など）をトークンとしてスキャンします。
*   **`ScanInts`**: 整数リテラルをトークンとしてスキャンします。
*   **`ScanStrings`**: 文字列リテラルをトークンとしてスキャンします。このコミットの文脈では、`ScanStrings` が設定されていない場合の挙動が重要になります。
*   **`SkipComments`**: コメントをスキップし、トークンストリームに含めないようにします。

### 未認識トークンの扱い

スキャナーが入力テキストを処理する際、定義されたどのトークンパターンにも一致しない文字シーケンスに遭遇することがあります。これらは「未認識トークン」または「不正なトークン」と呼ばれます。スキャナーの実装によっては、これらのトークンをエラーとして報告したり、個々の文字として返したり、あるいは完全に無視したりする場合があります。`text/scanner` パッケージの挙動は、このコミットで明確化されています。

## 技術的詳細

このコミットは、`src/pkg/text/scanner/scanner.go` ファイルの `Mode` 定義の直前に、6行の新しいコメントを追加しています。この追加されたコメントは、`text/scanner` パッケージの `Mode` フィールドの挙動、特に `SkipComments` オプションと、未認識トークンの処理方法について、以前は暗黙的であった、あるいは不明瞭であった側面を明確にしています。

具体的には、以下の2つの重要な点を説明しています。

1.  **コメントのスキップ**: `SkipComments` フラグが設定されている場合、コメントはスキャナーによって完全にスキップされ、結果として生成されるトークンストリームには含まれません。これは、コメントがプログラムの実行には影響しないため、通常は字句解析の段階で無視されるべきであるという一般的な慣行に沿っています。
2.  **未認識トークンの処理**: `SkipComments` が設定されている場合を除き、スキャナーが認識できないトークンに遭遇した場合の挙動が明確化されています。

    *   具体的な例として、`Mode` が `ScanIdents` に設定されており、`ScanStrings` が設定されていない場合、文字列 `"foo"` は単一の文字列トークンとしてではなく、`'`（シングルクォート）、`Ident`（識別子 `foo`）、`'`（シングルクォート）というトークンシーケンスとしてスキャンされることが示されています。これは、`ScanStrings` が有効でない限り、スキャナーが引用符で囲まれたシーケンスを特別な文字列リテラルとして扱わないことを意味します。

これらの説明は、`text/scanner` を使用する開発者が、特定の設定下でスキャナーがどのように動作するかを正確に理解するのに役立ちます。特に、予期しないトークンシーケンスや、文字列リテラルが期待通りに解析されない問題に直面した場合のデバッグに貢献します。

## コアとなるコードの解説

追加されたコメントは、`Mode` 定数の定義の直前に配置されており、`Mode` フィールドの動作に関する重要な補足説明を提供しています。

```go
// With the exceptions of comments, which are skipped if SkipComments is
// set, unrecognized tokens are not ignored. Instead, the scanner simply
// returns the respective individual characters (or possibly sub-tokens).
// For instance, if the mode is ScanIdents (not ScanStrings), the string
// "foo" is scanned as the token sequence '"' Ident '"'.
```

このコメントは以下の点を明確にしています。

1.  **コメントの例外処理**: `SkipComments` フラグが `Mode` に設定されている場合、コメントはスキャナーによって完全にスキップされます。これは、コメントがトークンストリームの一部として返されないことを意味します。
2.  **未認識トークンのデフォルト挙動**: コメントのスキップという例外を除き、スキャナーが認識できない文字シーケンスに遭遇した場合、それらは無視されません。代わりに、スキャナーはそれらの文字を個別のトークンとして返します。これは、スキャナーが「不明な」入力に対してエラーを発生させるのではなく、可能な限り詳細な情報を返すという設計思想を示しています。
3.  **`ScanStrings` がない場合の文字列処理の例**: 非常に具体的な例として、`Mode` に `ScanIdents` は含まれるが `ScanStrings` は含まれない場合、文字列リテラル `"foo"` がどのように処理されるかが説明されています。この場合、スキャナーは `"foo"` を単一の文字列トークンとして認識せず、代わりに `"` (引用符)、`Ident` (識別子 `foo`)、`"` (引用符) という3つの個別のトークンとして返します。これは、`ScanStrings` が設定されていない限り、引用符で囲まれたテキストが特別な意味を持つ文字列リテラルとして扱われないことを明確に示しています。

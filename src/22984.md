# [インデックス 22984] ファイルの概要

このコミットは、Goランタイムにおける`readyExecute`関数内のダングリングポインタの問題を修正するものです。具体的には、`mcall`に渡されるクロージャがスタック上に確保され、そのクロージャが実行中に無効になる可能性があった問題を解決します。

変更されたファイルは以下の通りです。

*   `src/runtime/proc1.go`: `readyExecute`関数の修正が含まれます。
*   `src/runtime/runtime2.go`: `g`構造体に新しいフィールド`readyg`が追加されます。
*   `src/runtime/stubs.go`: `mcall`関数の`go:noescape`アノテーションが削除されます。

    runtime: fix dangling pointer in readyExecute
    
    readyExecute passes a closure to mcall that captures an argument to
    readyExecute. Since mcall is marked noescape, this closure lives on
    the stack of the calling goroutine. However, the closure puts the
    calling goroutine on the run queue (and switches to a new
    goroutine). If the calling goroutine gets scheduled before the mcall
    returns, this stack-allocated closure will become invalid while it's
    still executing. One consequence of this we've observed is that the
    captured gp variable can get overwritten before the call to
    execute(gp), causing execute(gp) to segfault.
    
    Fix this by passing the currently captured gp variable through a field
    in the calling goroutine's g struct so that the func is no longer a
    closure.
    
    To prevent problems like this in the future, this change also removes
    the go-noescape annotation from mcall. Due to a compiler bug, this
    will currently cause a func closure passed to mcall to be implicitly
    allocated rather than refusing the implicit allocation. However, this
    is okay because there are no other closures passed to mcall right now
    and the compiler bug will be fixed shortly.

## 変更の背景

このコミットは、Goランタイムの`readyExecute`関数における深刻なバグを修正するために行われました。このバグは、`mcall`関数に渡されるクロージャが原因で発生するダングリングポインタの問題に起因します。

`readyExecute`関数は、特定のゴルーチン（`gp`）を実行可能状態にし、現在のゴルーチンをプリエンプトして、`gp`を実行するために使用されます。これは、特にGC（ガベージコレクション）がトリガーされた際に、GCを迅速に開始するために利用されます。

問題の核心は、`readyExecute`が`mcall`にクロージャを渡す際に、`readyExecute`の引数である`gp`をそのクロージャがキャプチャしていた点にあります。`mcall`は`go:noescape`アノテーションが付与されていたため、このクロージャは呼び出し元のゴルーチンのスタック上に確保されていました。

しかし、このクロージャは、呼び出し元のゴルーチンをランキュー（実行待ち行列）に入れ、新しいゴルーチンに切り替えるという処理を行います。もし、`mcall`が戻る前に呼び出し元のゴルーチンが再度スケジュールされてしまった場合、スタック上に確保されたこのクロージャは、まだ実行中であるにもかかわらず無効になってしまう可能性がありました。

この問題の結果として、キャプチャされた`gp`変数が上書きされ、`execute(gp)`の呼び出し時にセグメンテーション違反（segfault）が発生する、という現象が観測されていました。これは、Goランタイムの安定性と信頼性に直接影響を与える重大なバグでした。

この修正は、将来的に同様の問題が発生するのを防ぐため、`mcall`から`go:noescape`アノテーションを削除するという追加の変更も行っています。これは、コンパイラのバグにより、`go:noescape`が付与された関数にクロージャが渡された場合に、暗黙的なヒープアロケーションが拒否されずに発生してしまうという問題があったためです。このコンパイラのバグは後に修正される予定でしたが、このコミット時点では、`mcall`に渡される他のクロージャが存在しないため、この変更は安全であると判断されました。

## 前提知識の解説

このコミットの理解には、Goランタイムの内部動作、特にスケジューラ、メモリ管理、および特定のコンパイラディレクティブに関する知識が不可欠です。

### Goランタイムとスケジューラ (M, P, G)

Goランタイムは、Goプログラムの実行を管理するシステムです。その中核をなすのがスケジューラであり、ゴルーチン（Goにおける軽量スレッド）の実行を効率的に管理します。Goスケジューラは、M（Machine）、P（Processor）、G（Goroutine）という3つの主要なエンティティで構成されるMPGモデルを採用しています。

*   **Goroutine (G)**: Goにおける並行実行の単位です。非常に軽量で、数百万個のゴルーチンを同時に実行できます。各ゴルーチンは独自のスタックを持ちます。
*   **Machine (M)**: オペレーティングシステム（OS）のスレッドに相当します。MはPとGを実行します。MはOSスケジューラによってスケジュールされます。
*   **Processor (P)**: 論理プロセッサを表します。MとGの間の仲介役として機能し、実行可能なゴルーチンをMに提供します。Pの数は通常、CPUのコア数に等しく、同時に実行できるゴルーチンの数を制限します。

Goスケジューラは、GをPに割り当て、PがM上でGを実行するという形で動作します。これにより、OSスレッドの数を最小限に抑えつつ、多数のゴルーチンを効率的に管理できます。

### `mcall` 関数

`mcall`はGoランタイムの非常に低レベルな関数であり、主にアセンブリ言語で実装されています。その主な役割は、スタックの切り替えを行うことです。具体的には、ユーザーゴルーチンのスタックから、現在のOSスレッド（M）のシステムスタック（`g0`スタックとも呼ばれる）に実行コンテキストを切り替えます。

このスタック切り替えは、以下のような操作を行う際に不可欠です。

*   プリエンプション（横取り）不可能な操作。
*   ユーザーゴルーチンのスタックを成長させてはならない操作。
*   異なるユーザーゴルーチン間の切り替えを伴う操作。

`mcall`は引数として関数を受け取り、その関数を`g0`スタック上で実行します。これは、Goスケジューラの操作、特にゴルーチンの完了時や、ゴルーチンがプロセッサを譲る際に重要な役割を果たします。

### `go:noescape` ディレクティブ

`go:noescape`はGoコンパイラに対するディレクティブ（指示）であり、関数の宣言の前に`//go:noescape`というコメント形式で記述されます。このディレクティブは、コンパイラの「エスケープ解析」に対して、その関数に渡されるポインタ引数のいずれもヒープに「エスケープ」しない、あるいは関数から返されないことを保証します。

エスケープ解析は、Goコンパイラが変数をスタックに割り当てるか、ヒープに割り当てるかを決定するためのプロセスです。スタック割り当てはヒープ割り当てよりも高速であり、ガベージコレクションの負担も軽減されるため、パフォーマンスの最適化に繋がります。

`go:noescape`は通常、Goのボディを持たない関数（アセンブリ言語などで実装された関数）に適用されます。このディレクティブを使用することで、コンパイラは不要なヒープ割り当てを回避し、パフォーマンスを向上させることができます。しかし、このディレクティブが誤って使用されたり、コンパイラのバグがあったりすると、スタック上に確保されたデータが、そのデータへのポインタがまだ有効であるにもかかわらず、スタックフレームが解放されてしまうという「ダングリングポインタ」の問題を引き起こす可能性があります。

### クロージャとスタックアロケーション

Goにおけるクロージャは、それが定義された環境の変数を「キャプチャ」できる関数です。クロージャがキャプチャする変数は、クロージャが実行される際にそのスコープ外にあってもアクセス可能です。

Goコンパイラのエスケープ解析は、クロージャがキャプチャする変数がヒープにエスケープする必要があるかどうかを判断します。もし変数がクロージャのライフタイムを超えて存在する必要がある場合（例えば、クロージャが別のゴルーチンに渡される場合など）、その変数はヒープに割り当てられます。しかし、変数がクロージャのライフタイム内でしか必要とされない場合、コンパイラはそれをスタックに割り当てることができます。

今回の問題では、`mcall`に渡されるクロージャが`go:noescape`アノテーションのためにスタックに割り当てられましたが、そのクロージャが呼び出し元のゴルーチンをランキューに入れ、新しいゴルーチンに切り替えるという動作が、スタックに割り当てられたクロージャの有効性を損なう可能性がありました。

## 技術的詳細

このコミットが修正する問題は、Goランタイムのスケジューリングとメモリ管理の間の微妙な相互作用に起因します。

`readyExecute`関数は、特定のゴルーチン`gp`をすぐに実行させるために設計されています。この関数は、`mcall`を呼び出し、その引数として無名関数（クロージャ）を渡します。このクロージャの目的は、`gp`をランキューに入れ、現在のゴルーチンをプリエンプトし、`gp`を実行することです。

問題は、このクロージャが`readyExecute`の引数である`gp`をキャプチャしていた点にあります。そして、`mcall`関数には`//go:noescape`ディレクティブが付与されていました。このディレクティブは、コンパイラに対して、`mcall`に渡される引数（この場合はクロージャ）がヒープにエスケープしないことを保証します。その結果、コンパイラはこのクロージャを呼び出し元のゴルーチンのスタック上に割り当てました。

しかし、このクロージャの内部では、現在のゴルーチン（`_g_`）をランキューに入れ、別のゴルーチンに切り替える処理が行われます。ここで危険なシナリオが発生します。

1.  `readyExecute`が`mcall`を呼び出し、スタック上に確保されたクロージャを渡す。
2.  `mcall`内のクロージャが実行を開始する。
3.  クロージャは、現在のゴルーチンをランキューに入れる。
4.  クロージャは、新しいゴルーチンに切り替える。
5.  **問題点**: もし、`mcall`が完全に終了し、呼び出し元のゴルーチンのスタックフレームが解放される前に、ランキューに入れられた呼び出し元のゴルーチンがOSスケジューラによって再度スケジュールされてしまった場合、そのゴルーチンは既に無効になっているスタック上のクロージャにアクセスしようとします。これにより、ダングリングポインタが発生し、特にクロージャがキャプチャしていた`gp`変数が上書きされ、最終的にセグメンテーション違反を引き起こす可能性がありました。

この問題は、`gp`変数がクロージャによってキャプチャされ、そのクロージャがスタック上に存在するという事実と、Goスケジューラがゴルーチンをプリエンプトして別のゴルーチンを実行できるという事実の組み合わせによって引き起こされました。

この修正は、この問題を2つの側面から解決します。

1.  **`gp`変数の安全な伝達**: `gp`変数をクロージャでキャプチャする代わりに、現在のゴルーチン（`_g_`）の`g`構造体（`runtime2.go`で定義されている`g`型）に一時的なフィールド`readyg`を追加し、そこに`gp`を格納するように変更しました。これにより、`mcall`に渡される関数はもはやクロージャではなくなり、`gp`はスタックではなく`g`構造体を通じて安全にアクセスできるようになります。`g`構造体はヒープに割り当てられるため、ダングリングポインタの問題は発生しません。
2.  **`mcall`からの`go:noescape`の削除**: 将来的に同様の問題が発生するのを防ぐため、`src/runtime/stubs.go`の`mcall`関数から`//go:noescape`アノテーションが削除されました。これは、コンパイラのバグにより、`go:noescape`が付与された関数にクロージャが渡された場合に、暗黙的なヒープアロケーションが拒否されずに発生してしまうという問題があったためです。この変更により、`mcall`にクロージャが渡された場合、コンパイラは適切にヒープアロケーションを行うか、あるいはコンパイルエラーを発生させるようになります。コミット時点では、`mcall`に渡される他のクロージャは存在しないため、この変更は安全でした。

## コアとなるコードの解説

### `src/runtime/proc1.go`の変更

*   **`getg().readyg = gp`**: `readyExecute`関数内で、`mcall`に渡す`gp`（実行対象のゴルーチン）を、現在のゴルーチン（`getg()`で取得）の`g`構造体の新しいフィールド`readyg`に一時的に保存しています。これにより、`mcall`に渡される無名関数は`gp`をクロージャとしてキャプチャする必要がなくなり、ダングリングポインタの問題を回避できます。
*   **`gp := _g_.readyg`**: `mcall`に渡された無名関数（`func(_g_ *g)`）の内部で、`_g_`（現在のゴルーチン）の`readyg`フィールドから`gp`を取得しています。
*   **`_g_.readyg = nil`**: `gp`を取得した後、`readyg`フィールドを`nil`に設定してクリーンアップしています。

この変更により、`gp`はスタック上のクロージャによってキャプチャされるのではなく、ヒープ上に存在する`g`構造体を通じて安全に渡されるようになります。

### `src/runtime/runtime2.go`の変更

*   **`readyg *g // scratch for readyExecute`**: `g`構造体に新しいフィールド`readyg`が追加されました。このフィールドは、`readyExecute`関数が`gp`を一時的に保存するためのスクラッチ領域として使用されます。`g`構造体はヒープに割り当てられるため、このフィールドに保存された`gp`へのポインタは、スタック上のクロージャのように無効になることはありません。

### `src/runtime/stubs.go`の変更

*   **`//go:noescape`アノテーションの削除**: `mcall`関数の宣言から`//go:noescape`アノテーションが削除されました。
    *   **削除の理由**: コミットメッセージに記載されているように、コンパイラのバグにより、`go:noescape`が付与された関数にスタックアロケーションされるべきクロージャが渡された場合、コンパイラが暗黙的なヒープアロケーションを拒否せずに許可してしまう問題がありました。このアノテーションを削除することで、`mcall`にクロージャが渡された場合、コンパイラはより厳密なエスケープ解析を行い、必要に応じてヒープアロケーションを強制するか、コンパイルエラーを発生させるようになります。
    *   **コメントの追加**: `mcall`の新しいコメントは、`go:noescape`を削除した理由を明確に説明しています。「もし`fn`がスタックに割り当てられたクロージャであり、`fn`が`g`をランキューに入れ、`fn`が戻る前に`g`が実行された場合、クロージャはまだ実行中であるにもかかわらず無効になる」という問題点を指摘しています。

これらの変更により、`readyExecute`におけるダングリングポインタの問題が根本的に解決され、Goランタイムの堅牢性が向上しました。

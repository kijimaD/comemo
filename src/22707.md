# [インデックス 22707] ファイルの概要

このコミットは、GoコンパイラのARM64アーキテクチャ向けバックエンド（`cmd/7g`）において、特定のレジスタ（R26からR32）を予約し、コンパイラがこれらを汎用レジスタとして誤って使用することを防ぐための修正です。これにより、コンパイラのクラッシュや、実行時にGoランタイムの重要なGレジスタが上書きされる問題が解決され、特に`linux/arm64`環境でのビルドの安定性が向上しました。

## 変更の背景

この変更は、GoコンパイラがARM64アーキテクチャ上で特定のレジスタを誤って使用しようとしたことによって引き起こされる深刻な問題を解決するために導入されました。具体的には、以下の2つの主要な問題がありました。

1.  **コンパイラのクラッシュ**: ARM64にはZero Register (ZR) と呼ばれる特殊なレジスタが存在します。このレジスタは常に値0を保持し、書き込みは破棄されます。Goコンパイラ（`cmd/7g`）がZRレジスタを汎用レジスタとして扱おうとすると、予期せぬ動作やクラッシュが発生していました。これは、コンパイラがレジスタの特性を正しく認識していなかったためです。
2.  **Gレジスタの上書きによる実行時エラー**: Goランタイムは、現在実行中のgoroutineに関する情報（`g`構造体へのポインタ）を効率的にアクセスするために、特定のレジスタ（通称「Gレジスタ」）を使用します。コンパイラがプログラムで使用できないレジスタを誤って割り当ててしまうと、そのレジスタがGoランタイムによってGレジスタとして使用されている場合に、プログラムの実行中にGレジスタの内容が上書きされ、「大混乱（cause havoc）」を引き起こしていました。これにより、プログラムが予期せぬ動作をしたり、クラッシュしたりする可能性がありました。

これらの問題は、特に`linux/arm64`環境でのGoプログラムのビルドと実行に影響を与え、Issue #10304とIssue #10320として報告されていました。このコミットは、これらの問題を修正し、ARM64環境でのGoの安定性と信頼性を向上させることを目的としています。

## 前提知識の解説

### ARM64アーキテクチャにおけるレジスタ

ARM64（AArch64）は、64ビットのARM命令セットアーキテクチャです。このアーキテクチャには、汎用レジスタ（General Purpose Registers: GPRs）が31個（X0からX30）と、特殊な目的を持つレジスタがいくつか存在します。

*   **汎用レジスタ (X0-X30)**: データやアドレスを格納するために使用されます。
*   **スタックポインタ (SP)**: 現在のスタックフレームの最上位アドレスを指します。
*   **Zero Register (ZR/WZR/XZR)**: ARM64アーキテクチャの重要な特徴の一つです。レジスタ番号31は、命令の種類によってスタックポインタ（SP）またはゼロレジスタ（ZR）として機能します。
    *   **ZRとしての機能**: 汎用レジスタとしてアクセスされた場合、常に0を返します。また、ZRへの書き込みは破棄され、値は変更されません。これは、定数0を効率的に取得したり、レジスタをクリアしたりする際に非常に便利です。
    *   **SPとしての機能**: スタック操作命令で使用される場合は、スタックポインタとして機能します。

### GoランタイムにおけるGレジスタ

Go言語は、軽量な並行処理の単位である「goroutine」を特徴としています。Goランタイムは、これらのgoroutineを効率的に管理するために、G-M-Pスケジューリングモデルを採用しています。

*   **G (Goroutine)**: Goランタイムによって管理される軽量な実行スレッドです。各goroutineは、`runtime.g`構造体によって表現され、スタック情報、現在の状態、スケジューラが実行を管理するために必要なその他のデータを含んでいます。
*   **M (Machine)**: オペレーティングシステム（OS）のスレッドです。MはGoコードを実行し、P（Processor）と連携してgoroutineをスケジュールします。
*   **P (Processor)**: 論理的なプロセッサであり、MがGoコードを実行するためのコンテキストを提供します。各Pは、実行準備ができたgoroutineのローカルキューを持っています。

Goランタイムは、現在実行中のgoroutineの`g`構造体へのポインタを非常に高速にアクセスできるように最適化されています。これは、多くの場合、特定のハードウェアレジスタ（通称「Gレジスタ」）に`g`構造体へのポインタを格納するか、スレッドローカルストレージ（TLS）のようなメカニズムを使用することによって実現されます。この高速アクセスは、Goの効率的なコンカレンシーモデルの基盤であり、OSレベルのスレッドコンテキストスイッチのオーバーヘッドなしに、goroutine間の迅速なコンテキストスイッチを可能にします。

このコミットで言及されている「Gレジスタ」は、Goランタイムが内部的に使用する、現在のgoroutineの`g`構造体へのポインタを保持するレジスタを指します。このレジスタが誤って上書きされると、Goランタイムの動作が不安定になり、プログラムのクラッシュや誤動作につながります。

## 技術的詳細

このコミットの核心は、GoコンパイラのARM64バックエンド（`cmd/7g`）が、プログラムが使用すべきではない特定のレジスタを、誤って汎用レジスタとして割り当ててしまう問題を修正することにあります。

問題のレジスタはR26からR32です。ARM64アーキテクチャにおいて、これらのレジスタの一部は特殊な機能を持ち、汎用レジスタとして自由に使用することはできません。特に、レジスタ31はZero Register (ZR) またはスタックポインタ (SP) として機能します。

コミットメッセージによると、この問題は2つのシナリオで現れていました。

1.  **ZRレジスタの誤用**: コンパイラがZRレジスタを汎用レジスタとして扱おうとすると、コンパイラ自体がクラッシュしていました。これは、ZRレジスタが常に0を返し、書き込みが破棄されるという特性を持つため、通常のレジスタ操作が期待通りに行えないことに起因します。
2.  **Gレジスタの上書き**: 他のプログラムでは、コンパイルは成功するものの、実行時に問題が発生していました。これは、コンパイラがプログラムで使用できないレジスタ（例えば、GoランタイムがGレジスタとして内部的に使用しているレジスタ）を誤って割り当ててしまい、その結果、GoランタイムのGレジスタの内容が上書きされてしまうためでした。Gレジスタは現在のgoroutineのコンテキストを指すため、その内容が破壊されると、スケジューラやランタイムの動作が破綻し、プログラム全体が不安定になります。

この修正は、`src/cmd/7g/reg.go`ファイル内の`excludedregs()`関数を変更することで行われました。この関数は、コンパイラがコード生成時に汎用レジスタとして使用してはならないレジスタを定義する役割を担っています。修正前は、R26からR31までのレジスタが適切に除外されていなかったため、コンパイラがこれらを誤って使用する可能性がありました。

このコミットによって、`excludedregs()`関数にR26からR31までのレジスタを明示的に除外するロジックが追加されました。これにより、コンパイラはこれらの特殊なレジスタを汎用レジスタとして割り当てなくなり、前述のクラッシュやGレジスタ上書きの問題が解決されました。結果として、`linux/arm64`環境でのGoプログラムのビルドと実行の安定性が大幅に向上しました。

## コアとなるコードの解説

### `src/cmd/7g/reg.go` の変更

`excludedregs()`関数は、Goコンパイラがコード生成時に汎用レジスタとして使用してはならないレジスタのビットマスクを返す役割を担っています。この関数は、特定のハードウェアレジスタが特殊な目的（例えば、スタックポインタ、フレームポインタ、またはGoランタイムが内部的に使用するレジスタ）のために予約されている場合に、コンパイラがそれらを誤って割り当てないようにするために重要です。

追加されたコードブロックは以下の通りです。

```go
	// Exclude R26 - R31.
	for r := arm64.REGMAX + 1; r <= arm64.REGZERO; r++ {
		regbits |= RtoB(r)
	}
```

*   `arm64.REGMAX + 1`: これは、ARM64アーキテクチャにおける汎用レジスタの最大番号（X30）の次、つまりR31（ZR/SP）に近いレジスタからループを開始するための定数です。
*   `arm64.REGZERO`: これは、ARM64のZero Register (ZR) に対応するレジスタ番号（R31）を指す定数です。
*   `for r := ...; r <= ...; r++`: このループは、R26からR31までの範囲のレジスタを順に処理します。
*   `regbits |= RtoB(r)`: `RtoB(r)`は、レジスタ番号`r`を対応するビットマスクに変換するヘルパー関数です。このビットマスクは`regbits`変数にOR演算で追加されます。これにより、`regbits`はR26からR31までのすべてのレジスタに対応するビットがセットされた状態になり、`excludedregs()`関数が返すビットマスクに含まれるようになります。

この変更により、GoコンパイラはR26からR31までのレジスタを、汎用レジスタとして割り当て可能なレジスタのプールから除外するようになります。これにより、ZRレジスタの誤用によるコンパイラのクラッシュや、GoランタイムのGレジスタの上書きといった問題が根本的に解決されます。

### `test/fixedbugs/issue10320.go` の追加

このファイルは、Issue #10320で報告された問題が修正されたことを検証するための回帰テストです。

```go
package main

func main() {
	var x00, x01, x02, x03, x04, x05, x06, x07, x08, x09 int
	var x10, x11, x12, x13, x14, x15, x16, x17, x18, x19 int
	var x20, x21, x22, x23, x24, x25, x26, x27, x28, x29 int
	var x30, x31, x32 int

	_ = x00
	// ... (中略) ...
	_ = x32
}
```

このテストケースの目的は、多数の`int`型変数を宣言することによって、コンパイラが多くのレジスタを割り当てる必要がある状況を作り出すことです。特に、`x26`から`x32`までの変数が宣言されており、これらは問題となっていたR26からR32までのレジスタに対応する可能性があります。

`_ = xXX`という形式は、変数を宣言したが使用しない場合にコンパイラのエラーを回避するためのGoの慣用的な方法です。これにより、コンパイラはこれらの変数にレジスタを割り当てる必要性を認識しますが、実際にその値を使用することはありません。

このテストが成功するということは、コンパイラがR26からR32までのレジスタを正しく除外し、これらの変数に他の利用可能なレジスタを割り当てるか、またはスタックに格納するなどの適切な処理を行っていることを意味します。もし修正が不完全であれば、このテストはコンパイルエラーになったり、実行時にクラッシュしたりするでしょう。このテストの追加は、将来的に同様の問題が再発しないことを保証するための重要なステップです。

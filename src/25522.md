## 元コミット内容

このコミットがリバートしている元のコミット `8e496f1d6923172291658f0a785bdb47cc152325` は、Goランタイムにおけるバッファ付きチャネルの実装を簡素化することを目的としていました。具体的には、`chansend` (チャネルへの送信) および `chanrecv` (チャネルからの受信) 関数において、バッファ付きチャネルとバッファなしチャネルの処理ロジックをより統合し、コードの重複を減らそうと試みました。

元の簡素化では、チャネルのバッファリング状態（`c.dataqsiz`）に基づいて処理を分岐させるのではなく、より一般的なロジックで送信者や受信者をキューイングし、バッファの操作を抽象化しようとしたと考えられます。これにより、コードベースの保守性を向上させ、潜在的なバグを減らすことを目指していた可能性があります。また、`send` や `recv` といったヘルパー関数の役割を見直したり、`select` ステートメントの内部処理も簡素化されたチャネルロジックに合わせて変更されたと推測されます。

## 変更の背景

このコミットは、以前の「バッファ付きチャネルの簡素化」コミットをリバートするものです。リバートの主な理由は、コミットメッセージに「`#13169` が理解されるまで一時的に戻す」と明記されている通り、その簡素化によって予期せぬ問題が発生し、その問題の根本原因がすぐに特定・解決できなかったためです。

`#13169` の具体的な内容は公開されているGoリポジトリでは見つかりませんでしたが、一般的にGoランタイムのような低レベルの並行処理プリミティブの変更は、非常にデリケートであり、以下のような問題を引き起こす可能性があります。

1.  **デッドロックやライブロック**: 並行処理のロジック変更は、ゴルーチンが互いに待ち状態になり、処理が進まなくなるデッドロックや、常に処理を試みるが成功しないライブロックを引き起こす可能性があります。
2.  **レースコンディション**: 複数のゴルーチンが共有リソース（この場合はチャネルの内部状態）に同時にアクセスする際の同期が不適切になると、データの破損や予期せぬ動作につながるレースコンディションが発生します。
3.  **パフォーマンスの低下**: 簡素化が必ずしもパフォーマンス向上につながるとは限りません。特定のシナリオでチャネル操作のオーバーヘッドが増加し、アプリケーション全体のパフォーマンスに悪影響を与える可能性があります。
4.  **セマンティクスの変更**: 意図せずチャネルのセマンティクス（例えば、クローズされたチャネルからの受信動作や、`select` ステートメントの挙動）が変わってしまい、既存のGoプログラムが正しく動作しなくなる可能性があります。

これらの問題は、Goの並行処理モデルの根幹に関わるため、原因が不明な場合は、安全策として一度安定した状態に戻す（リバートする）ことが賢明な判断となります。このリバートは、問題の徹底的な調査と解決のための時間を確保するための措置と言えます。

## 前提知識の解説

このコミットの変更を理解するためには、Goのチャネルとランタイムの基本的な概念を理解しておく必要があります。

### Goのチャネル

Goのチャネルは、ゴルーチン間で値を送受信するための通信メカニズムです。チャネルには「バッファなしチャネル」と「バッファ付きチャネル」の2種類があります。

-   **バッファなしチャネル (Synchronous Channel)**: バッファサイズが0のチャネルです。送信操作は受信操作が完了するまでブロックし、受信操作は送信操作が完了するまでブロックします。つまり、送信者と受信者が同時に準備ができて初めて値の受け渡しが行われます（同期通信）。
-   **バッファ付きチャネル (Asynchronous Channel)**: バッファサイズが1以上のチャネルです。バッファに空きがある場合、送信操作はブロックせずに値をバッファに書き込みます。バッファが満杯の場合のみ、送信操作はブロックします。同様に、バッファに値がある場合、受信操作はブロックせずに値を取り出します。バッファが空の場合のみ、受信操作はブロックします（非同期通信）。

### `hchan` 構造体

Goランタイム内部では、チャネルは `hchan` 構造体で表現されます。この構造体には、チャネルのタイプ、要素サイズ、バッファサイズ (`dataqsiz`)、現在のバッファ内の要素数 (`qcount`)、送受信キュー (`sendq`, `recvq`) など、チャネルの状態を管理するための情報が含まれています。

### `sudog` 構造体と送受信キュー (`sendq`, `recvq`)

`sudog` (scheduler utility goroutine) 構造体は、チャネル操作によってブロックされたゴルーチンを表します。チャネルの送受信キュー (`sendq` と `recvq`) は、それぞれチャネルへの送信を待っているゴルーチンと、チャネルからの受信を待っているゴルーチンのリストを管理します。ゴルーチンがチャネル操作でブロックされると、そのゴルーチンに対応する `sudog` が適切なキューに追加されます。

### `select` ステートメント

`select` ステートメントは、複数のチャネル操作を同時に待機し、準備ができた最初の操作を実行するためのGoの構文です。どのチャネル操作も準備ができていない場合、`select` はブロックするか、`default` ケースがあればそれを実行します。

### Goランタイムのスケジューリングプリミティブ

-   **`lock`/`unlock`**: チャネルの内部状態を保護するためのミューテックス操作です。
-   **`getg()`**: 現在実行中のゴルーチン (`g`) を取得します。
-   **`goparkunlock()`**: 現在のゴルーチンをパーク（一時停止）させ、チャネルのロックを解除します。ゴルーチンは、他のゴルーチンによって `goready()` が呼ばれるまで実行を再開しません。
-   **`goready()`**: パークされたゴルーチンを実行可能状態に戻し、スケジューラがそのゴルーチンをいつか実行するようにします。
-   **`acquireSudog()` / `releaseSudog()`**: `sudog` 構造体のプールからの取得と解放を行います。

### メモリ操作関数

-   **`typedmemmove()`**: 型情報に基づいてメモリをコピーします。ガベージコレクタがポインタを正しく追跡できるように、型情報が重要です。
-   **`memclr()`**: 指定されたメモリ領域をゼロクリアします。
-   **`memmove()`**: 生のメモリをコピーします。
-   **`typeBitsBulkBarrier()`**: ガベージコレクタのライトバリアを呼び出し、ポインタの移動をGCに通知します。

### レース検出 (`raceenabled`) とメモリサニタイザ (`msanenabled`)

Goランタイムには、並行処理のバグを検出するためのツールが組み込まれています。

-   **`raceenabled`**: レースコンディション検出器が有効な場合に真となります。チャネル操作におけるメモリの読み書きを追跡し、レースコンディションを報告します。
-   **`msanenabled`**: メモリサニタイザが有効な場合に真となります。初期化されていないメモリへのアクセスを検出します。

これらの概念は、チャネルの内部動作、特にゴルーチンの同期、データの受け渡し、およびエラーハンドリングを理解する上で不可欠です。

## 技術的詳細

このリバートコミットは、`src/runtime/chan.go` と `src/runtime/select.go` の2つのファイルに影響を与えています。主な変更点は、以前のコミットで統合されたバッファ付きチャネルとバッファなしチャネルの処理ロジックが、再び明確に分離されたことです。

### `src/runtime/chan.go` の変更

#### `chansend` 関数 (チャネル送信)

-   **バッファなしチャネルの処理の分離**:
    -   リバート前は、`c.recvq.dequeue()` で受信者を検索し、見つかれば直接送信、見つからなければバッファに空きがあるか確認、という流れで、バッファなしチャネルとバッファ付きチャネルの処理が混在していました。
    -   リバート後（現在のコード）では、`if c.dataqsiz == 0 { ... }` という明確な条件分岐が導入され、バッファなしチャネルの送信ロジックが独立したブロックに切り出されました。これにより、同期チャネルの送信は、待機中の受信者がいるかどうかに直接依存するようになります。
    -   待機中の受信者がいない場合、送信ゴルーチンは `c.sendq` に自身をキューイングし、`goparkunlock` でパークされます。
-   **バッファ付きチャネルの処理の分離**:
    -   リバート後、バッファ付きチャネルの送信ロジックは `c.dataqsiz == 0` の `else` ブロックで処理されます。
    -   バッファが満杯の場合、送信ゴルーチンは `c.sendq` に自身をキューイングし、`goparkunlock` でパークされます。
    -   バッファに空きがある場合、データは直接バッファに書き込まれ (`typedmemmove`)、`c.sendx` と `c.qcount` が更新されます。その後、待機中の受信者がいれば (`c.recvq.dequeue()`)、その受信者を `goready` で起こします。
-   **`send` ヘルパー関数の復活**:
    -   リバート前は、`send` 関数が削除またはインライン化されていた可能性があります。
    -   リバート後、`send` 関数が復活し、待機中の受信者が見つかった場合に、送信値を直接受信者にコピーし、受信者を起こす処理を担当します。これは、バッファなしチャネルや、バッファ付きチャネルで待機中の受信者がいる場合に、バッファを介さずに直接通信を行うための重要な最適化です。
-   **`syncsend` 関数の導入/復活**:
    -   `syncsend` 関数は、バッファなしチャネルでの直接送信、またはバッファ付きチャネルで待機中の受信者がいる場合の直接送信において、送信元から受信先のメモリへデータをコピーする役割を担います。特に、ガベージコレクタのライトバリア (`typeBitsBulkBarrier`) を適切に呼び出すことで、GCの正確性を保証します。

#### `chanrecv` 関数 (チャネル受信)

-   **バッファなしチャネルの処理の分離**:
    -   `chansend` と同様に、`if c.dataqsiz == 0 { ... }` によってバッファなしチャネルの受信ロジックが独立しました。
    -   待機中の送信者がいる場合 (`c.sendq.dequeue()`)、受信者は送信者から直接値を受け取り、送信者を `goready` で起こします。
    -   待機中の送信者がいない場合、受信ゴルーチンは `c.recvq` に自身をキューイングし、`goparkunlock` でパークされます。
-   **バッファ付きチャネルの処理の分離**:
    -   バッファ付きチャネルの受信ロジックは `c.dataqsiz == 0` の `else` ブロックで処理されます。
    -   バッファが空の場合、受信ゴルーチンは `c.recvq` に自身をキューイングし、`goparkunlock` でパークされます。
    -   バッファに値がある場合、データはバッファから受信者のメモリにコピーされ (`typedmemmove`)、バッファ内のスロットはゼロクリアされます (`memclr`)。`c.recvx` と `c.qcount` が更新されます。その後、待機中の送信者がいれば (`c.sendq.dequeue()`)、その送信者を `goready` で起こします。
-   **`recv` ヘルパー関数の復活**:
    -   `recv` 関数が復活し、待機中の送信者が見つかった場合に、送信者から値を受け取り、受信者にコピーし、送信者を起こす処理を担当します。バッファ付きチャネルの場合、バッファから受信し、送信者の値をバッファに書き込むという、いわゆる「バッファの回転」処理も行います。
-   **`recvclosed` ヘルパー関数の導入/復活**:
    -   チャネルがクローズされている場合に受信者が行うべきクリーンアップ処理をカプセル化します。

### `src/runtime/select.go` の変更

-   **チャネルタイプに基づく明確な分岐**:
    -   `selectgoImpl` 関数内で、各 `case` の処理において、`c.dataqsiz > 0` (バッファ付き) と `c.dataqsiz == 0` (バッファなし) に基づく明確な条件分岐が復活しました。
    -   これにより、`select` ステートメントがチャネルのタイプに応じて、待機中の送信者/受信者のキューをチェックするか、バッファの空き/データ有無をチェックするかが、より明示的に区別されるようになりました。
-   **`goto` ラベルの変更**:
    -   以前の簡素化では `bufrecv` や `bufsend` といったラベルが使われていた箇所が、リバートによって `asyncrecv` や `asyncsend` に変更されました。これは、バッファ付きチャネルの非同期的な性質をより明確に反映しています。
    -   同様に、`recv` や `send` といったラベルが `syncrecv` や `syncsend` に変更され、バッファなしチャネルの同期的な性質を強調しています。
-   **`futile` フラグの利用**:
    -   `gopark` や `goparkunlock` の呼び出しにおいて、`futile` フラグが使用されるようになりました。これは、トレースイベントの際に、そのゴルーチンのパークが「無駄なウェイクアップ」によるものかどうかを示すために使われます。これは、簡素化によって発生した可能性のある、不必要なゴルーチンのウェイクアップをデバッグするための情報として役立つ可能性があります。

これらの変更は、Goのチャネル実装が、バッファ付きとバッファなしのチャネルで異なる特性を持つため、それぞれのケースに特化した最適化と正確な同期ロジックが必要であることを示唆しています。簡素化の試みは、これらの微妙な違いを抽象化しようとした結果、予期せぬ副作用（`#13169`）を引き起こしたと考えられます。リバートは、この複雑さを再導入することで、既知の安定した動作を優先したものです。

## コアとなるコードの解説

このリバートは、Goのチャネル実装における「簡素化」が、実際にはGoの並行処理モデルの複雑な側面を十分に考慮していなかった可能性を示唆しています。

Goのチャネルは、単なるデータキューではなく、ゴルーチン間の同期メカニズムでもあります。特にバッファなしチャネルは、送信者と受信者の厳密な同期を保証し、デッドロックやレースコンディションを防ぐ上で非常に重要です。バッファ付きチャネルは非同期性を提供しますが、バッファが満杯または空になった場合には、やはりゴルーチンのブロックとアンブロックが必要となり、ここでも正確な同期ロジックが求められます。

元の簡素化は、これらの異なるチャネルタイプ間のコードの共通化を図ったものと思われますが、その過程で以下のような問題が発生した可能性があります。

1.  **同期保証の破綻**: バッファなしチャネルの同期保証が、簡素化されたロジックによって意図せず破綻した可能性があります。例えば、送信者が受信者を待たずに進行してしまったり、その逆のケースが発生したりするかもしれません。
2.  **`select` ステートメントの複雑性**: `select` ステートメントは、複数のチャネル操作を原子的に処理する必要があるため、その内部ロジックは非常に複雑です。簡素化されたチャネルロジックが `select` の内部状態管理やゴルーチンのウェイクアップメカニズムと衝突し、予期せぬ挙動を引き起こした可能性があります。特に、`select` がチャネルのクローズを検出した際の挙動や、複数のケースが同時に準備できた場合の非決定的な選択ロジックは、非常にデリケートです。
3.  **レースコンディションの導入**: 簡素化によって、チャネルの内部状態 (`qcount`, `sendx`, `recvx` など) へのアクセスが適切にロックされていなかったり、複数のゴルーチンが同時にこれらの状態を変更しようとしたりするレースコンディションが導入された可能性があります。これは、特に `raceenabled` ビルドで検出されやすい問題です。
4.  **デバッグの困難さ**: 低レベルの並行処理バグは、再現性が低く、デバッグが非常に困難です。`#13169` が「理解されるまで」という表現は、問題の根本原因がすぐには特定できなかったことを示唆しています。このような場合、安定したバージョンに戻すことが、問題解決のための最善策となります。

リバートによって、`chansend` と `chanrecv` は、バッファなしチャネルとバッファ付きチャネルの処理を明確に分離し、それぞれの特性に合わせた専用のロジックを持つようになりました。これにより、各チャネルタイプが持つべき同期保証とセマンティクスが確実に維持されます。また、`send` や `recv` といったヘルパー関数の復活は、特定のチャネル操作（例えば、待機中のゴルーチンとの直接通信）をより明確に、かつ安全に処理するための構造を提供します。

`selectgoImpl` における `goto` ラベルの変更も、この分離を反映しています。`asyncrecv`/`asyncsend` はバッファ付きチャネルのバッファ操作を、`syncrecv`/`syncsend` はバッファなしチャネルの直接通信を指すようになり、コードの意図がより明確になりました。`futile` フラグの追加は、将来的なデバッグやプロファイリングのために、不必要なウェイクアップイベントを追跡するのに役立つでしょう。

結論として、このリバートは、Goランタイムの安定性と正確性を最優先し、複雑な並行処理プリミティブの変更には慎重なアプローチが必要であることを示しています。簡素化の試みは重要ですが、それがGoの強力な並行処理モデルの基盤を損なうものであってはなりません。

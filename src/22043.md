## 元コミット内容

Rob Pikeによるこのコミットは、Goのアセンブラ（`cmd/asm`）のPowerPC 64-bit (ppc64) サポートを、Plan 9の`9a`アセンブラの挙動と同期させることを目的としています。コミットメッセージによると、Rob Pikeは`9a/a.y`（`9a`アセンブラの文法定義ファイル）に含まれる全ての命令とオペランドの生成を網羅する`.s`ファイルを作成し、`9a`とGoの`cmd/asm`がビット単位で同一の結果を生成することを確認しました。この検証プロセス中に、Goのアセンブラがサポートしていなかった特定のアドレッシングモード（`R1+R2`）が発見され、このコミットで修正されました。

また、`9a`の文法が受け入れるにもかかわらず、Goのリンカライブラリである`liblink`が拒否する命令がいくつか見つかったことも報告されています。これらの不一致は別途対応される予定であり、検証に使用したテストファイルも最終的には正式なテストとして追加されることが示唆されています。

## 変更の背景

Go言語のツールチェインは、その設計思想や実装においてPlan 9オペレーティングシステムのツールチェインから大きな影響を受けています。特に、Goのアセンブラ（`cmd/asm`）は、Plan 9のアセンブラ（例えば`amd64`向けの`9a`）の構文と設計原則を強く踏襲しています。

このコミットの背景には、Goの`ppc64`アセンブラが、参照元である`9a`アセンブラの完全な機能セットをまだ網羅していなかったという問題があります。アセンブラの正確性と網羅性は、Goプログラムが特定のアーキテクチャ上で正しくコンパイルされ、実行されるために不可欠です。特に、アセンブラがサポートするアドレッシングモードや命令セットが不完全であると、コンパイラが生成するアセンブリコードや、手書きのアセンブリコードが正しく処理されず、最終的なバイナリの生成に問題が生じる可能性があります。

このコミットは、`ppc64`アーキテクチャにおけるGoのアセンブラの堅牢性を向上させ、`9a`アセンブラとの互換性を高めることで、Go言語のクロスプラットフォーム対応を強化する一環として行われました。

## 前提知識の解説

*   **Go言語のツールチェイン**: Go言語は、独自のコンパイラ、アセンブラ（`cmd/asm`）、リンカ（`liblink`）を含む自己完結型のツールチェインを持っています。これにより、Goは外部のCコンパイラやアセンブラに依存することなく、様々なプラットフォーム向けにバイナリを生成できます。
*   **`cmd/asm`**: Goのアセンブラです。Goの独特なアセンブリ構文（Plan 9アセンブラに由来）を解釈し、リンカが処理できる形式に変換します。Goのアセンブリ言語は、基盤となるマシンの命令セットを直接的に1対1で表現するものではなく、Goコンパイラの内部動作と連携するように設計されています。
*   **`9a`アセンブラ**: Plan 9オペレーティングシステムにおける`amd64`アーキテクチャ向けのアセンブラを指します。Goのアセンブラは、その構文や設計思想において`9a`を含むPlan 9アセンブラから大きな影響を受けています。このコミットでは、`9a`が`ppc64`アセンブラの挙動の「基準」として用いられています。
*   **`liblink`**: Goツールチェイン内で使用されるリンカライブラリです。コンパイラやアセンブラの出力（オブジェクトファイル）を結合し、実行可能なバイナリを生成する役割を担います。
*   **`ppc64` (PowerPC 64-bit)**: IBMが開発したPowerPCアーキテクチャの64ビット版です。Goツールチェインは、`ppc64`（および`ppc64le`）を公式にサポートしており、このアーキテクチャ上で動作するシステム向けに実行ファイルを生成できます。
*   **アドレッシングモード**: CPUがメモリ上のデータにアクセスする方法を定義するものです。例えば、`R1+R2`は、レジスタ`R1`とレジスタ`R2`の内容を足し合わせたアドレスにアクセスするアドレッシングモードを示します。アセンブラは、これらのアドレッシングモードを正しく解釈し、対応する機械語に変換する必要があります。

## 技術的詳細

このコミットの技術的詳細は、主にGoのアセンブラ（`cmd/asm`）が`ppc64`アーキテクチャのアセンブリコードをどのようにパースし、内部表現に変換するかに焦点を当てています。

1.  **`ppc64.go`における`IsPPC64NEG`関数の追加**:
    `src/cmd/asm/internal/arch/ppc64.go`ファイルに`IsPPC64NEG`関数が追加されました。この関数は、`ppc64.A*`定数で定義されるオペレーションが、特殊なハンドリングを必要とする`NEG`（否定）のような命令であるかどうかを報告します。具体的には、`AADDMECC`, `AADDMEVCC`, `AADDMEV`, `AADDME`, `AADDZECC`, `AADDZEVCC`, `AADDZEV`, `AADDZE`, `ACNTLZDCC`, `ACNTLZD`, `ACNTLZWCC`, `ACNTLZW`, `AEXTSBCC`, `AEXTSB`, `AEXTSHCC`, `AEXTSH`, `AEXTSWCC`, `AEXTSW`, `ANEGCC`, `ANEGVCC`, `ANEGV`, `ANEG`, `ASLBMFEE`, `ASLBMFEV`, `ASLBMTE`, `ASUBMECC`, `ASUBMEVCC`, `ASUBMEV`, `ASUBME`, `ASUBZECC`, `ASUBZEVCC`, `ASUBZEV`, `ASUBZE`といった命令が対象となります。これらの命令は、Goのアセンブラが内部的に処理する際に、オペランドの解釈やレジスタの割り当てに関して特別なロジックを必要とする可能性があります。

2.  **`asm.go`におけるオペランド処理の改善**:
    `src/cmd/asm/internal/asm/asm.go`ファイルでは、アセンブリ命令のパースと内部表現への変換ロジックが修正されています。
    *   **ジャンプ命令の2オペランドおよび3オペランド処理の調整**: `p.arch.Thechar == '9'`（`ppc64`アーキテクチャを示す）の場合のジャンプ命令の処理が変更されました。特に、2オペランドのジャンプ命令（例: `BCTR`）や3オペランドのジャンプ命令（例: `BC`）において、`prog.From`や`prog.To`フィールドへのオペランドの割り当てが調整されています。これにより、`ppc64`特有のジャンプ命令の構文が正しく解釈されるようになります。
    *   **`NEG`命令の特殊ハンドリング**: `IsPPC64NEG`関数が導入されたことにより、`NEG`のような命令に対して、`prog.From`と`prog.To`の両方に同じオペランド（`a[0]`）を割り当てる特殊な処理が追加されました。これは、これらの命令が単一のソースオペランドを変換して結果を同じレジスタに格納するようなセマンティクスを持つためと考えられます。
    *   **`ppc64`における`R1+R2`アドレッシングモードのサポート**: コミットメッセージで言及されている`R1+R2`アドレッシングモードのサポートが追加されました。これは、`p.arch.Thechar == '9'`の場合の2オペランド命令処理内で、`a[0].Scale != 0`または`a[1].Scale != 0`の条件で`prog.Reg`にレジスタを割り当てるロジックによって実現されています。このアドレッシングモードは、PowerPCのインデックス付きアドレッシングモード（ベースレジスタとインデックスレジスタの和をアドレスとする）に対応します。
    *   **5オペランド命令の処理（`RLD`命令など）**: `ppc64`アーキテクチャにおける5オペランド命令（例: `RLD` - Rotate Left Doubleword）の処理が追加されました。これらの命令は、レジスタ、レジスタ、定数、定数、レジスタという形式のオペランドを取ります。特に、定数オペランドからマスク値を計算し、`prog.From3`フィールドに格納するロジックが実装されています。これは、`RLD`命令がビットフィールド操作を行う際に使用するマスクをアセンブラが正しく生成するために必要です。

3.  **`operand_test.go`におけるテストケースの追加**:
    `src/cmd/asm/internal/asm/operand_test.go`ファイルに、`PPC64OperandParser`のテストケースが追加されました。特に、`(R1+R2)`という特殊なアドレッシングモードのパースが正しく行われることを検証するテストが含まれています。これは、このコミットの主要な修正点の一つである`R1+R2`アドレッシングモードのサポートを保証するためのものです。

4.  **`parse.go`におけるレジスタパースの拡張**:
    `src/cmd/asm/internal/asm/parse.go`ファイルでは、レジスタのパースロジックが拡張されています。
    *   **`R1+R2`構文の認識**: `register`関数において、`:`や`,`に加えて`+`文字も2番目のレジスタを示す区切り文字として認識されるようになりました。これにより、`ppc64`特有の`(R1+R2)`形式のアドレッシングモードが正しくパースされます。
    *   **`registerIndirect`関数の`ppc64`特殊処理**: `registerIndirect`関数において、`ppc64`（`p.arch.Thechar == '9'`）の場合に`R1+R2`形式のレジスタペアを処理するための特殊なロジックが追加されました。このロジックは、`a.Type`を`obj.TYPE_MEM`に設定し、`a.Scale`に2番目のレジスタの値を格納することで、このアドレッシングモードをGoのオブジェクトファイル形式にエンコードします。

これらの変更は、`ppc64`アセンブラがより多くのPowerPC命令とアドレッシングモードを正確に解釈し、Goの内部表現に変換できるようにすることで、Goコンパイラが`ppc64`向けに生成するコードの品質と、手書きアセンブリコードの記述能力を向上させます。

```go
// IsPPC64NEG reports whether the op (as defined by an ppc64.A* constant) is
// one of the NEG-like instructions that require special handling.
func IsPPC64NEG(op int) bool {
	switch op {
	case ppc64.AADDMECC, ppc64.AADDMEVCC, ppc64.AADDMEV, ppc64.AADDME,
		ppc64.AADDZECC, ppc64.AADDZEVCC, ppc64.AADDZEV, ppc64.AADDZE,
		ppc64.ACNTLZDCC, ppc64.ACNTLZD, ppc64.ACNTLZWCC, ppc64.ACNTLZW,
		ppc64.AEXTSBCC, ppc64.AEXTSB, ppc64.AEXTSHCC, ppc64.AEXTSH,
		ppc64.AEXTSWCC, ppc64.AEXTSW, ppc64.ANEGCC, ppc64.ANEGVCC,
		ppc64.ANEGV, ppc64.ANEG, ppc64.ASLBMFEE, ppc64.ASLBMFEV,
		ppc64.ASLBMTE, ppc64.ASUBMECC, ppc64.ASUBMEVCC, ppc64.ASUBMEV,
		ppc64.ASUBME, ppc64.ASUBZECC, ppc64.ASUBZEVCC, ppc64.ASUBZE:
		return true
	}
	return false
}
```
この関数は、与えられたオペレーションコード（`op`）が、PowerPC 64-bitアーキテクチャにおいて特殊な処理を必要とする「NEG-like」な命令であるかを判定します。これらの命令は、通常、単一のソースオペランドを取り、その結果を同じレジスタに格納するようなセマンティクスを持つため、アセンブラの内部処理で特別な扱いが必要です。

### `src/cmd/asm/internal/asm/asm.go`

```go
// asmInstruction assembles an instruction.
// MOVW R9, (R10)
func (p *Parser) asmInstruction(op int, cond string, a []obj.Addr) {
	// ... (既存コード) ...

	case 1:
		// ... (既存コード) ...
		if p.arch.Thechar == '9' && arch.IsPPC64NEG(op) {
			// NEG: From and To are both a[0].
			prog.To = a[0]
			prog.From = a[0]
			break
		}
	case 2:
		// ... (既存コード) ...
		switch p.arch.Thechar {
		case '6', '8': // x86, arm
			// ... (既存コード) ...
		case '9': // ppc64
			var reg0, reg1 int16
			// Handle (R1+R2)
			if a[0].Scale != 0 {
				reg0 = int16(a[0].Scale)
				prog.Reg = reg0
			} else if a[1].Scale != 0 {
				reg1 = int16(a[1].Scale)
				prog.Reg = reg1
			}
			if reg0 != 0 && reg1 != 0 {
				p.errorf("register pair cannot be both left and right operands")
			}
		}
		prog.From = a[0]
		prog.To = a[1]
	case 5: // ppc64 RLD instruction
		if p.arch.Thechar == '9' && arch.IsPPC64RLD(op) { // IsPPC64RLDはコミットにはないが、RLD命令の処理を示唆
			// Always reg, reg, con, con, reg.  (con, con is a 'mask').
			prog.From = a[0]
			prog.Reg = p.getRegister(prog, op, &a[1])
			mask1 := p.getConstant(prog, op, &a[2])
			mask2 := p.getConstant(prog, op, &a[3])
			var mask uint32
			if mask1 < mask2 {
				mask = (^uint32(0) >> uint(mask1)) & (^uint32(0) << uint(31-mask2))
			} else {
				mask = (^uint32(0) >> uint(mask2+1)) & (^uint32(0) << uint(31-(mask1-1)))
			}
			prog.From3 = obj.Addr{
				Type:   obj.TYPE_CONST,
				Offset: int64(mask),
			}
			prog.To = a[4]
			break
		}
		p.errorf("can't handle %s instruction with 5 operands", p.arch.Aconv(op))
	// ... (既存コード) ...
}
```
`asmInstruction`関数は、アセンブリ命令をパースし、Goの内部表現である`obj.Prog`構造体に変換する中心的なロジックを含んでいます。
*   1オペランドの場合、`IsPPC64NEG`が`true`を返す命令（例: `NEG`）に対しては、ソースとデスティネーションのオペランドが同じ（`a[0]`）として扱われます。
*   2オペランドの場合、`ppc64`アーキテクチャ（`Thechar == '9'`）では、`(R1+R2)`のようなアドレッシングモードを処理するために、`a[0].Scale`や`a[1].Scale`（`parse.go`で設定される）からレジスタ情報を抽出し、`prog.Reg`に設定します。これは、PowerPCのインデックス付きアドレッシングモードを表現するためのものです。
*   5オペランドの場合、`ppc64`の`RLD`（Rotate Left Doubleword）のような命令を処理します。この命令は、2つの定数オペランドからビットマスクを生成し、それを`prog.From3`フィールドに格納します。これは、`RLD`命令がビット操作を行う際に、どのビット範囲を操作するかをマスクで指定するためです。

```go
func (p *Parser) register(name string, prefix rune) (r1, r2 int16, scale int8, ok bool) {
	// R1 or R(1) R1:R2 R1,R2 R1+R2, or R1*scale.
	r1, ok = p.registerReference(name)
	if !ok {
		return
	}
	if prefix != 0 {
		p.errorf("prefix %c not allowed for register: $%s", prefix, name)
	}
	c := p.peek()
	if c == ':' || c == ',' || c == '+' { // '+'が追加された
		// 2nd register; syntax (R1:R2) etc. No two architectures agree.
		// Check the architectures match the syntax.
		char := p.arch.Thechar
		switch p.next().ScanToken {
		case ':':
			// ... (既存コード) ...
		case ',':
			// ... (既存コード) ...
		case '+': // ppc64 only
			if char != '9' { // '9'はppc64を示す

}
```
`register`関数は、アセンブリコード中のレジスタ参照をパースします。このコミットでは、レジスタペアの区切り文字として`+`が追加され、`ppc64`アーキテクチャでのみこの構文が許可されるように制限されています。これにより、`(R1+R2)`のような形式が正しく認識されます。

`registerIndirect`関数は、間接アドレッシングモード（例: `(R1)`や`(R1+R2)`）をパースします。`ppc64`アーキテクチャの場合、`(R1+R2)`形式のレジスタペアが検出されると、`obj.Addr`構造体の`Type`を`obj.TYPE_MEM`に設定し、2番目のレジスタ（`R2`）を`Scale`フィールドにエンコードします。これは、Goのオブジェクトファイル形式でこの特定のアドレッシングモードを表現するための慣習的な方法です。コミットメッセージの`TODO`コメントが示すように、このエンコーディング方法は将来的に改善の余地があると考えられています。

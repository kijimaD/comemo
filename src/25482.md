# [インデックス 25482] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ（GC）におけるワークバッファの管理方法を改善し、特にグローバルなワークリストへの競合を削減することを目的としています。GCワーカーがポインタを処理する際に、ローカルキャッシュとして2つのワークバッファを使用するように変更することで、パフォーマンスのボトルネックとなる可能性のある「フラッピング」現象を緩和します。

## 変更の背景

Goのガベージコレクタ（GC）は、並行マークフェーズ中に、各プロセッサ（P）に割り当てられた`gcWork`構造体を通じてマーク作業を管理します。以前の実装では、`gcWork`はポインタを一時的に格納するためのワークバッファを1つだけキャッシュしていました。

この単一バッファの設計には、特定のシナリオでパフォーマンス上の問題がありました。GCワーカーがワークバッファの境界で頻繁にポインタの追加（put）と取得（get）を繰り返す場合、バッファがすぐに満杯になったり空になったりするため、ワーカーはグローバルなワークバッファリストから新しいバッファを取得したり、使用済みのバッファを返却したりする操作を頻繁に行う必要がありました。この「フラッピング」と呼ばれる現象は、グローバルなワークリストに対する競合を大幅に増加させ、GCの効率を低下させる可能性がありました。

このコミットは、このような最悪のケースのパフォーマンス問題を緩和するために導入されました。特に、ワークロードによってはこの競合が顕著になり、GCのレイテンシやスループットに悪影響を与える可能性があったため、改善が求められました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびガベージコレクタに関する前提知識が必要です。

*   **Goのガベージコレクタ (GC)**: GoのGCは、並行（concurrent）かつ低レイテンシなマーク＆スイープ方式を採用しています。プログラムの実行と並行してGCのマークフェーズが動作し、アプリケーションの一時停止（STW: Stop-The-World）時間を最小限に抑えることを目指しています。
*   **マークフェーズ**: GCの主要なフェーズの一つで、到達可能なオブジェクト（プログラムから参照されているオブジェクト）を特定し、マークするプロセスです。このフェーズ中に、ヒープ上のポインタが走査され、参照されているオブジェクトが「生きている」とマークされます。
*   **`gcWork`**: Goランタイムにおいて、各論理プロセッサ（P）に割り当てられるGC作業のローカルキャッシュを管理する構造体です。GCワーカー（ゴルーチン）は、この`gcWork`を通じて、マーク対象のポインタを一時的に格納したり、取得したりします。これにより、グローバルな共有データ構造へのアクセスを減らし、競合を緩和します。
*   **ワークバッファ (workbuf)**: `gcWork`がポインタをキャッシュするために使用する固定サイズのバッファです。GCワーカーは、マーク中に発見したポインタをこのローカルバッファに格納し、バッファが満杯になるとグローバルなワークリストにフラッシュします。また、ローカルバッファが空になると、グローバルなワークリストから新しいバッファを取得します。
*   **P (Processor)**: Goスケジューラにおける論理プロセッサの抽象化です。各Pは、Goルーチンを実行するためのコンテキストを提供し、GC作業を含む様々なランタイムタスクを処理します。
*   **競合 (Contention)**: 複数のゴルーチンやPが同時に共有リソース（この場合はグローバルなワークバッファリスト）にアクセスしようとするときに発生する状況です。競合が高いと、ロックの取得や待機が増え、パフォーマンスが低下します。
*   **ヒステリシス (Hysteresis)**: システムが状態を切り替える際に、その切り替えを安定させるための遅延や閾値を導入する概念です。この文脈では、ワークバッファの切り替えをすぐにではなく、ある程度の作業が完了するまで遅延させることで、頻繁な状態変更を防ぎます。

## 技術的詳細

このコミットの核心は、`gcWork`構造体が単一のワークバッファではなく、**2つのワークバッファ (`wbuf1`, `wbuf2`) をキャッシュする**ように変更された点にあります。この変更により、GCワーカーはポインタの追加と取得の際に、より効率的にバッファを管理できるようになります。

具体的なメカニズムは以下の通りです。

1.  **二重バッファリング**: `gcWork`は、`wbuf1`と`wbuf2`という2つのワークバッファを保持します。これらは、概念的にはポインタのスタックとして連結されていると考えることができます。
2.  **ヒステリシス導入**:
    *   **ポインタの追加 (`put`)**: ワーカーはまず`wbuf1`にポインタを追加します。`wbuf1`が満杯になった場合、すぐにグローバルリストにフラッシュするのではなく、`wbuf1`と`wbuf2`を入れ替えます（`wbuf1`が以前の`wbuf2`になり、以前の`wbuf1`が新しい`wbuf2`になる）。そして、新しい`wbuf1`（以前の`wbuf2`）にポインタを追加し続けます。もし新しい`wbuf1`も満杯であれば、そのバッファをグローバルリストにフラッシュし、新しい空のバッファを`wbuf1`として取得します。このプロセスにより、バッファの切り替えが頻繁に行われる「フラッピング」が抑制されます。
    *   **ポインタの取得 (`tryGet`, `get`)**: ワーカーはまず`wbuf1`からポインタを取得します。`wbuf1`が空になった場合、すぐにグローバルリストから新しいバッファを取得するのではなく、`wbuf1`と`wbuf2`を入れ替えます。そして、新しい`wbuf1`（以前の`wbuf2`）からポインタを取得し続けます。もし新しい`wbuf1`も空であれば、そのバッファをグローバルリストに返却し、グローバルリストから新しい満杯のバッファを`wbuf1`として取得します。
3.  **競合の削減**: この二重バッファリングとヒステリシスにより、ワーカーがグローバルなワークリストにアクセスする頻度が減少します。バッファが満杯になったり空になったりするたびにグローバルリストにアクセスするのではなく、少なくとも1つのバッファ分の作業を償却（amortize）できるため、グローバルリストへのロック競合が緩和されます。
4.  **`_WorkbufSize`の変更**: コミットでは、`_WorkbufSize`が4096バイトから2048バイトに削減されています。一般的に、ワークバッファのサイズが大きいほど競合は減少するとされていますが、この変更は二重バッファリングの導入と合わせて考慮された可能性があります。考えられる理由としては、以下の点が挙げられます。
    *   **キャッシュ効率**: バッファサイズを小さくすることで、CPUキャッシュの局所性が向上し、全体的なアクセス速度が改善される可能性があります。
    *   **メモリフットプリント**: 2つのバッファを保持するため、合計のメモリ使用量を考慮して、個々のバッファサイズを調整した可能性があります。
    *   **最適なバランス**: 二重バッファリングによる競合削減効果が大きいため、単一バッファの場合よりも小さいサイズで十分なパフォーマンスが得られると判断された可能性があります。

ベンチマーク結果では、グローバルワークリストへの最大書き込み/秒が32Kから25Kに、中央値が6Kから5Kに減少しており、競合が実際に緩和されていることが示されています。また、`XBenchGarbage`や`BinaryTree17`などのベンチマークでわずかながら速度向上が見られます。

## コアとなるコードの解説

### `src/runtime/mgcwork.go`

#### `_WorkbufSize`

```go
const (
	_Debugwbufs  = false // if true check wbufs consistency
	_WorkbufSize = 2048  // in bytes; larger values result in less contention
)
```
ワークバッファのサイズが4096バイトから2048バイトに半減されました。これは、2つのバッファを同時に保持することによるメモリフットプリントの増加を相殺するため、または新しい二重バッファリング戦略においてこのサイズが最適なバランスを提供すると判断されたためと考えられます。コメントは「より大きな値は競合を減らす」と述べていますが、これは一般的な原則であり、この特定の変更では、二重バッファリングの導入が競合削減の主要なメカニズムとなり、バッファサイズは他の要因（キャッシュ効率など）とのトレードオフで決定された可能性があります。

#### `gcWork` 構造体

```go
type gcWork struct {
	// wbuf1 and wbuf2 are the primary and secondary work buffers.
	//
	// This can be thought of as a stack of both work buffers'
	// pointers concatenated. When we pop the last pointer, we
	// shift the stack up by one work buffer by bringing in a new
	// full buffer and discarding an empty one. When we fill both
	// buffers, we shift the stack down by one work buffer by
	// bringing in a new empty buffer and discarding a full one.
	// This way we have one buffer's worth of hysteresis, which
	// amortizes the cost of getting or putting a work buffer over
	// at least one buffer of work and reduces contention on the
	// global work lists.
	//
	// wbuf1 is always the buffer we're currently pushing to and
	// popping from and wbuf2 is the buffer that will be discarded
	// next.
	//
	// Invariant: Both wbuf1 and wbuf2 are nil or neither are.
	wbuf1, wbuf2 wbufptr

	// ... (他のフィールドは省略)
}
```
`gcWork`構造体は、単一の`wbuf`フィールドから`wbuf1`と`wbuf2`の2つの`wbufptr`フィールドを持つように変更されました。`wbuf1`は現在ポインタの追加/取得が行われているプライマリバッファであり、`wbuf2`は次に破棄される（または入れ替えられる）セカンダリバッファとして機能します。このコメントは、2つのバッファがどのように連携してヒステリシスを提供し、グローバルワークリストへの競合を削減するかを明確に説明しています。

#### `init()` メソッド

```go
func (w *gcWork) init() {
	w.wbuf1 = wbufptrOf(getempty(101))
	wbuf2 := trygetfull(102)
	if wbuf2 == nil {
		wbuf2 = getempty(103)
	}
	w.wbuf2 = wbufptrOf(wbuf2)
}
```
`gcWork`が初期化される際に呼び出され、`wbuf1`と`wbuf2`をセットアップします。`wbuf1`は常に空のバッファとして取得されます。`wbuf2`は、可能であれば満杯のバッファ（既にGC作業が含まれているバッファ）を`trygetfull`で取得しようとします。もし満杯のバッファがなければ、空のバッファを取得します。これにより、初期状態からある程度の作業をローカルで処理できる可能性が高まります。

#### `put(obj uintptr)` メソッド

```go
func (ww *gcWork) put(obj uintptr) {
	w := (*gcWork)(noescape(unsafe.Pointer(ww)))

	wbuf := w.wbuf1.ptr()
	if wbuf == nil {
		w.init()
		wbuf = w.wbuf1.ptr()
		// wbuf is empty at this point.
	} else if wbuf.nobj == len(wbuf.obj) { // wbuf1が満杯の場合
		w.wbuf1, w.wbuf2 = w.wbuf2, w.wbuf1 // wbuf1とwbuf2を入れ替える
		wbuf = w.wbuf1.ptr()
		if wbuf.nobj == len(wbuf.obj) { // 新しいwbuf1も満杯の場合
			putfull(wbuf, 132) // 新しいwbuf1をグローバルリストにフラッシュ
			wbuf = getempty(133) // 新しい空のバッファを取得
			w.wbuf1 = wbufptrOf(wbuf)
		}
	}

	wbuf.obj[wbuf.nobj] = obj
	wbuf.nobj++
}
```
ポインタを`gcWork`に追加するロジックです。
1.  まず`wbuf1`にポインタを追加しようとします。
2.  もし`wbuf1`が初期化されていなければ`init()`を呼び出します。
3.  `wbuf1`が満杯の場合、`wbuf1`と`wbuf2`を入れ替えます。これにより、以前の`wbuf2`が新しい`wbuf1`となり、そこにポインタを追加し続けます。
4.  もし入れ替えた後の新しい`wbuf1`も満杯であれば、そのバッファを`putfull`でグローバルリストに返却し、`getempty`で新しい空のバッファを取得して`wbuf1`に設定します。
このロジックにより、`wbuf1`が満杯になってもすぐにグローバルリストにアクセスするのではなく、`wbuf2`を一時的に利用することで、グローバルリストへのアクセス頻度を減らしています。

#### `tryGet()` および `get()` メソッド

```go
func (ww *gcWork) tryGet() uintptr {
	w := (*gcWork)(noescape(unsafe.Pointer(ww)))

	wbuf := w.wbuf1.ptr()
	if wbuf == nil {
		w.init()
		wbuf = w.wbuf1.ptr()
		// wbuf is empty at this point.
	}
	if wbuf.nobj == 0 { // wbuf1が空の場合
		w.wbuf1, w.wbuf2 = w.wbuf2, w.wbuf1 // wbuf1とwbuf2を入れ替える
		wbuf = w.wbuf1.ptr()
		if wbuf.nobj == 0 { // 新しいwbuf1も空の場合
			owbuf := wbuf
			wbuf = trygetfull(167) // グローバルリストから満杯のバッファを取得しようとする
			if wbuf == nil {
				return 0 // 取得できなければ0を返す
			}
			putempty(owbuf, 166) // 以前の空のwbuf1をグローバルリストに返却
			w.wbuf1 = wbufptrOf(wbuf)
		}
	}

	wbuf.nobj--
	return wbuf.obj[wbuf.nobj]
}

func (ww *gcWork) get() uintptr {
	// tryGetと類似のロジックだが、getfullでブロックしてでもバッファを取得しようとする
	// ... (詳細はtryGetと類似)
}
```
ポインタを`gcWork`から取得するロジックです。`put`と同様に、`wbuf1`が空になった場合、すぐにグローバルリストにアクセスするのではなく、`wbuf1`と`wbuf2`を入れ替えます。入れ替えた後の新しい`wbuf1`も空であれば、初めてグローバルリストから満杯のバッファを取得しようとします。`tryGet`は取得できなければ0を返しますが、`get`はブロックしてでも取得しようとします。

```go
func (w *gcWork) dispose() {
	if wbuf := w.wbuf1.ptr(); wbuf != nil {
		if wbuf.nobj == 0 {
			putempty(wbuf, 212)
		} else {
			putfull(wbuf, 214)
```

#### `empty()` メソッド

```go

	return w.wbuf1 == 0 || (w.wbuf1.ptr().nobj == 0 && w.wbuf2.ptr().nobj == 0)
}
```

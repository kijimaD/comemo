## 変更の背景

Go言語の`net`パッケージは、ホスト名の解決（DNSルックアップ）を行う際に、Goネイティブのリゾルバを使用するか、Cgoを介してシステムのCライブラリ（通常は`libc`）のリゾルバを使用するかを選択できます。この挙動は、環境変数やビルドタグによって制御されることがあります。

`GODEBUG`環境変数には、Goランタイムのデバッグや特定の挙動を制御するための様々なオプションが含まれています。その一つに`netdns=cgo`があり、これはDNSルックアップにおいてCgoベースのリゾルバを強制することを意図していました。しかし、このオプションを設定しても、実際にはCgoが強制されないというバグが存在しました。

コミットメッセージによると、「It wasn't working. The wrong variable was used.」（機能していなかった。間違った変数が使われていた。）とあり、これは`src/net/conf.go`内の初期化ロジックにおいて、`GODEBUG=netdns=cgo`の設定を反映すべき変数が正しく参照されていなかったことが原因でした。この問題はIssue #11816として報告されていました。

このコミットは、この変数の参照ミスを修正し、`GODEBUG=netdns=cgo`が期待通りにCgoベースのDNSルックアップを強制するようにすることで、ユーザーがデバッグや特定の環境要件に合わせてDNS解決の挙動を制御できるようにすることを目的としています。

## 前提知識の解説

### Goの`net`パッケージとDNS解決

Go言語の標準ライブラリである`net`パッケージは、ネットワーク通信に関する機能を提供します。その中核的な機能の一つが、ホスト名からIPアドレスへの変換（DNS解決）です。GoのDNS解決には主に2つのモードがあります。

1.  **Goネイティブなリゾルバ**: Go言語自体が実装しているDNSクライアントです。これは、`resolv.conf`などの設定ファイルを直接読み込み、DNSプロトコルに従って名前解決を行います。クロスプラットフォームで一貫した挙動を提供し、Cgoのオーバーヘッドがないためパフォーマンス上有利な場合があります。
2.  **Cgoベースのリゾルバ**: Cgo（GoとC言語の相互運用機能）を介して、オペレーティングシステムが提供するCライブラリ（例: Linuxの`glibc`）のリゾルバ機能（例: `getaddrinfo`）を呼び出します。これにより、システムのDNS設定（例: `/etc/nsswitch.conf`、LDAP、NISなど）に完全に準拠した名前解決が可能になります。特定の環境では、このCgoベースのリゾルバを使用することが必須となる場合があります。

どちらのリゾルバを使用するかは、ビルドタグ（例: `netgo`、`osusergo`）や環境変数（例: `GODEBUG`）によって制御されます。

### Cgo

Cgoは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。これにより、既存のCライブラリをGoプロジェクトで再利用したり、Goでは実装が難しい低レベルの操作を行ったりすることが可能になります。DNS解決の文脈では、CgoはGoの`net`パッケージがシステムのCライブラリのリゾルバ機能を利用するために使われます。

### `GODEBUG`環境変数

`GODEBUG`は、Goランタイムのデバッグオプションや特定の挙動を制御するための環境変数です。`GODEBUG=key=value,key2=value2`のような形式で複数のオプションを設定できます。例えば、ガベージコレクションの動作を詳細に出力したり、スケジューラの挙動を変更したり、今回のように`net`パッケージのDNS解決方法を制御したりするために使用されます。

### `GODEBUG=netdns=cgo`

この特定の`GODEBUG`オプションは、Goの`net`パッケージに対して、DNSルックアップを強制的にCgoベースのリゾルバで行うように指示します。これは、Goネイティブのリゾルバでは解決できないような複雑なシステム設定（例: `/etc/nsswitch.conf`による名前解決順序のカスタマイズ、LDAPやNISによるホスト名解決）を持つ環境で特に有用です。

### `confVal`構造体

`src/net/conf.go`ファイルには、`confVal`というグローバルな構造体（またはそれに準ずるもの）が存在し、`net`パッケージのDNS解決に関する様々な設定値を保持しています。これには、Cgoの使用を強制するかどうかといったフラグも含まれます。この構造体は、`net`パッケージが初期化される際に、環境変数やシステム設定に基づいて値が設定されます。

## 技術的詳細

このコミットの技術的な核心は、`src/net/conf.go`ファイル内の`initConfVal`関数における変数参照の誤りです。

`initConfVal`関数は、`net`パッケージが使用するDNS解決関連の設定値を初期化する役割を担っています。この関数内で、`GODEBUG=netdns=cgo`環境変数の設定を読み取り、CgoベースのDNS解決を強制するかどうかを決定するロジックが含まれていました。

問題の箇所は、条件分岐の`if`文の中にありました。

```go
// 変更前
if os.Getenv("RES_OPTIONS") != "" ||
	os.Getenv("HOSTALIASES") != "" ||
	netCgo || // ここが問題
	localDomainDefined {
	confVal.forceCgoLookupHost = true
	return
}
```

ここで`netCgo`という変数が参照されていますが、これは`initConfVal`関数内で定義されたローカル変数でした。このローカル変数`netCgo`は、`GODEBUG=netdns=cgo`の設定を直接反映する`confVal.netCgo`とは異なる値を保持している可能性がありました。具体的には、`confVal.netCgo`は`GODEBUG`の設定に基づいて適切に初期化されるべきでしたが、`if`文の条件式では、その`confVal.netCgo`ではなく、別のローカル変数`netCgo`が使われてしまっていたのです。

結果として、`GODEBUG=netdns=cgo`を設定しても、`confVal.netCgo`が`true`になっていても、`if`文の条件式が`true`にならず、`confVal.forceCgoLookupHost = true`が実行されないという事態が発生していました。`confVal.forceCgoLookupHost`は、CgoベースのDNS解決を強制するための最終的なフラグです。

このコミットは、この参照ミスを修正し、`if`文の条件式で`confVal`構造体のフィールドである`confVal.netCgo`を正しく参照するように変更しました。

## コアとなるコードの変更箇所

変更は`src/net/conf.go`ファイルの一箇所のみです。

```diff
--- a/src/net/conf.go
+++ b/src/net/conf.go
@@ -80,7 +80,7 @@ func initConfVal() {
 	_, localDomainDefined := syscall.Getenv("LOCALDOMAIN")
 	if os.Getenv("RES_OPTIONS") != "" ||
 	\tos.Getenv("HOSTALIASES") != "" ||
-		netCgo ||
+		confVal.netCgo ||
 		localDomainDefined {
 		confVal.forceCgoLookupHost = true
 		return
```

## コアとなるコードの解説

変更された行は以下の通りです。

*   **変更前**: `-		netCgo ||`
*   **変更後**: `+		confVal.netCgo ||`

この変更により、`if`文の条件式で参照される変数が、ローカルスコープの`netCgo`から、`net`パッケージ全体の設定を保持する`confVal`構造体のフィールドである`confVal.netCgo`に修正されました。

`confVal.netCgo`は、`GODEBUG=netdns=cgo`が設定されている場合に`true`となるように、`initConfVal`関数の別の箇所で適切に初期化されています。この修正によって、`GODEBUG=netdns=cgo`が`true`である場合に、`if`文の条件が正しく評価され、`confVal.forceCgoLookupHost`が`true`に設定されるようになります。

`confVal.forceCgoLookupHost`が`true`になると、`net`パッケージはホスト名解決の際にCgoベースのリゾルバを強制的に使用するようになります。これにより、`GODEBUG=netdns=cgo`というデバッグオプションが、その意図通りに機能するようになりました。

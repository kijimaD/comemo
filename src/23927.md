# [インデックス 23927] ファイルの概要

このコミットは、Goランタイムにおけるヒープビットマップのバグ修正に関するものです。具体的には、大きなスカラーテールを持つ型（`typ.ptrdata < typ.size`）のヒープビットマップを繰り返し処理する際に、ガベージコレクタがポインタを誤ってスカラーとしてマークしてしまう問題を解決します。これにより、本来参照されているオブジェクトが誤って解放される可能性がありました。

    (typ.ptrdata < typ.size), it lays out the tail upon reaching the end
    of the source bitmap by simply increasing the number of bits claimed
    to be in the incoming bit buffer. This causes later iterations to read
    the appropriate number of zeros out of the bit buffer before starting
    on the next repeat of the source bitmap.

    from the source bitmap *regardless of the number of bits currently in
    the bit buffer*. The bit buffer can only hold 32 or 64 bits, so if the
    scalar tail is large and the padding bits exceed the size of the bit
    buffer, the read from the source bitmap on the next iteration will
    shift the incoming bits into oblivion when it attempts to put them in
    the bit buffer. When the buffer does eventually shift down to where
    these bits were supposed to be, it will contain zeros. As a result,
    words that should be marked as pointers on later repetitions are
    marked as scalars, so the garbage collector does not trace them. If
    this is the only reference to an object, it will be incorrectly freed.
    
    Fix this by adding logic to drain the bit buffer down if it is large
    instead of reading more bits from the source bitmap.

## 変更の背景

Goのガベージコレクタ（GC）は、ヒープ上のオブジェクトがポインタを含むかどうかを効率的に判断するためにヒープビットマップを使用します。このビットマップは、オブジェクトのメモリレイアウトをビット列で表現し、どのワードがポインタであるかを示します。

`heapBitsSetType` 関数は、特定の型のヒープビットマップを生成し、それをヒープ上の実際のメモリ領域に適用する役割を担っています。この関数が、ある型のビットマップを繰り返し適用する際に、特に「スカラーテール」（`typ.ptrdata < typ.size`、つまり型の先頭部分にポインタが含まれるが、末尾部分にはポインタが含まれない純粋なスカラーデータが続く場合）を持つ型で問題が発生していました。

問題は、スカラーテールがある場合、`heapBitsSetType` はビットバッファにゼロビット（スカラーを示す）を詰め込むことでテールを表現します。しかし、このゼロビットの量がビットバッファの容量（32ビットまたは64ビット）を超えると、次のビットマップの繰り返しを読み込む際に、バッファ内の既存のゼロビットが適切に処理されず、新しいポインタ情報が失われてしまうというものでした。結果として、本来ポインタであるべきワードがスカラーとして誤ってマークされ、GCがそのポインタを追跡できなくなり、オブジェクトが早期に解放されてしまう可能性がありました。これは、プログラムのクラッシュやデータ破損につながる重大なバグです。

## 前提知識の解説

### Goのガベージコレクション (GC) の基本

Goのガベージコレクタは、並行マーク＆スイープ方式を採用しています。これは、プログラムの実行と並行して不要なメモリを特定し、解放する仕組みです。GCの効率は、ヒープ上のオブジェクトがポインタを含むかどうかを正確かつ迅速に判断できるかに大きく依存します。

### ヒープビットマップ (Heap Bitmap) の役割と構造

ヒープビットマップは、GoのGCがヒープ上のメモリ領域をスキャンする際に使用するメタデータです。各オブジェクトのメモリレイアウトに対応するビット列で構成され、どのワードがポインタ（他のオブジェクトへの参照）であり、どのワードがスカラー（数値、文字列データなど）であるかを示します。これにより、GCはポインタのみを追跡し、スカラーデータは無視することで、スキャン範囲を限定し効率を高めます。

例えば、`struct { *int; int }` のような型の場合、最初のフィールドはポインタなのでビットマップでは `1`、次のフィールドはスカラーなので `0` といった形で表現されます。

### ポインタとスカラー (Pointer and Scalar) の区別

*   **ポインタ**: 他のメモリ位置を指し示す値。GCはポインタをたどって、到達可能なオブジェクトを特定します。
*   **スカラー**: ポインタではない値。GCはスカラー値を追跡しません。

GCがポインタをスカラーと誤認すると、そのポインタが指すオブジェクトは到達不可能と判断され、誤って解放されてしまいます。

### `_type` 構造体と `typ.ptrdata`, `typ.size` の意味

Goのランタイムには、各型のメタデータが格納された `_type` 構造体が存在します。
*   `typ.size`: その型のインスタンスが占めるメモリの総バイト数。
*   `typ.ptrdata`: その型のインスタンスの先頭から、ポインタを含む最後のバイトまでのオフセット。つまり、`typ.ptrdata` バイト目以降は純粋なスカラーデータのみが続くことを示します。

「スカラーテール」とは、`typ.ptrdata < typ.size` の状態を指します。これは、型のメモリレイアウトの末尾にポインタを含まないデータが存在することを意味します。

### `heapBitsSetType` 関数の目的

`heapBitsSetType` 関数は、特定の型のヒープビットマップを、ヒープ上の指定されたメモリ領域に設定する役割を担います。これは、新しいオブジェクトがアロケートされた際や、GCがヒープの状態を更新する際に呼び出されます。この関数は、型のビットマップ定義を読み取り、それを実際のメモリブロックのビットマップに変換して書き込みます。

## 技術的詳細

このバグは、`heapBitsSetType` 関数が型のビットマップを繰り返し適用する際の内部ロジックに起因していました。

1.  **ビットマップの繰り返しとスカラーテール**: `heapBitsSetType` は、オブジェクトのメモリレイアウトに対応するビットマップを、必要に応じて複数回繰り返して適用します。型にスカラーテール（`typ.ptrdata < typ.size`）がある場合、型のビットマップのポインタ部分が終わった後、残りのスカラーテール部分にはポインタが存在しないため、ビットマップ上ではゼロが続きます。

2.  **ビットバッファ (`b`) の使用**: `heapBitsSetType` 関数は、ビットマップの処理を効率化するために、一時的なビットバッファ (`b`) を使用します。このバッファは通常32ビットまたは64ビットのサイズを持ち、ビットマップのビットを一時的に保持し、そこから必要なビットを取り出してヒープビットマップに書き込みます。`nb` 変数は、このビットバッファ `b` に現在格納されているビット数を示します。

3.  **バグの発生メカニズム**:
    *   スカラーテールがある場合、`heapBitsSetType` は、ソースビットマップの終わりに達すると、ビットバッファ `b` に「ゼロビット」を詰め込むことでスカラーテールを表現します。これにより、`nb` の値が増加し、ビットバッファが多くのゼロビットで満たされます。
    *   問題は、ループの次のイテレーションで、**ビットバッファ `b` にどれだけのビットが残っているかに関わらず**、常にソースビットマップから新しいビットを読み込もうとしていた点です。
    *   もしスカラーテールが非常に大きく、ビットバッファに詰め込まれたゼロビットの量がバッファの容量（32/64ビット）を超えていた場合、次にソースビットマップからビットを読み込もうとすると、既存のビットが「消滅」してしまいます。具体的には、新しいビットを `b` にシフトして入れようとした際に、`b` の上位ビットが切り捨てられ、本来保持されるべきゼロビットが失われます。
    *   結果として、ビットバッファが最終的にシフトダウンして、本来ポインタ情報が格納されるべき位置に到達したとき、そこには誤ってゼロ（スカラーを示す）が格納されてしまいます。
    *   これにより、後続の繰り返しでポインタとしてマークされるべきワードがスカラーとしてマークされ、GCがそれらを追跡できなくなり、オブジェクトが誤って解放されるという致命的な結果を招きました。

4.  **修正**: このコミットでは、ビットバッファ `b` に大量のビット（特にゼロビット）が溜まっている場合に、ソースビットマップから新しいビットを読み込む前に、まずバッファを「ドレイン」（消費）するロジックを追加することでこの問題を解決しました。これにより、ビットバッファのオーバーフローが防止され、ポインタ情報が正確に保持されるようになります。

## コアとなるコードの変更箇所

変更は `src/runtime/mbitmap.go` ファイルの `heapBitsSetType` 関数内にあります。

```diff
--- a/src/runtime/mbitmap.go
+++ b/src/runtime/mbitmap.go
@@ -978,8 +978,16 @@ func heapBitsSetType(x, size, dataSize uintptr, typ *_type) {
 			// nb unmodified: we just loaded 8 bits,
 			// and the next iteration will consume 8 bits,
 			// leaving us with the same nb the next time we're here.
-			b |= uintptr(*p) << nb
-			p = add1(p)
+			if nb < 8 {
+				b |= uintptr(*p) << nb
+				p = add1(p)
+			} else {
+				// Reduce the number of bits in b.
+				// This is important if we skipped
+				// over a scalar tail, since nb could
+				// be larger than the bit width of b.
+				nb -= 8
+			}
 		} else if p == nil {
 			// Almost as fast path: track bit count and refill from pbits.
 			// For short repetitions.
```

この変更は、`heapBitsSetType` 関数内のビットマップ処理ループの一部です。

*   元のコードでは、`b |= uintptr(*p) << nb` と `p = add1(p)` が無条件に実行されていました。これは、常にソースビットマップ `p` から8ビットを読み込み、それをビットバッファ `b` に追加しようとするものです。
*   修正後のコードでは、`if nb < 8` という条件が追加されています。
    *   `nb < 8` の場合（ビットバッファ `b` に残っているビット数が8未満の場合）、これまで通りソースビットマップ `p` から8ビットを読み込み、`b` に追加します。これは通常の処理パスです。
    *   `else` ブロック、つまり `nb >= 8` の場合（ビットバッファ `b` に8ビット以上が残っている場合）は、ソースビットマップから新しいビットを読み込む代わりに、`nb -= 8` を実行して `b` から8ビットを「消費」したことにします。これは、ビットバッファに既に十分なビット（特にスカラーテール由来のゼロビット）が溜まっているため、新しいビットを読み込む必要がない、あるいは読み込むとオーバーフローする可能性がある状況に対応するためのものです。

また、このコミットにはバグを再現するためのテストケース `test/fixedbugs/issue11286.go` も追加されています。このテストケースは、大きなスカラーテールを持つ構造体 `T` を定義し、そのインスタンスを複数作成してマップフィールドに値を設定した後、GCを実行して値が保持されていることを確認します。

```go
// test/fixedbugs/issue11286.go
package main

import "runtime"

const D = 57

type T struct {
	a [D]float64 // large scalar tail
	b map[string]int // pointer field
	c [D]float64 // large scalar tail
}

var ts []T

func main() {
	ts = make([]T, 4)
	for i := range ts {
		ts[i].b = make(map[string]int)
	}
	ts[3].b["abc"] = 42
	runtime.GC()
	if ts[3].b["abc"] != 42 {
		panic("bad field value")
	}
}
```
このテストでは、`[D]float64` という大きなスカラー配列を `T` 型に含めることで、スカラーテールが大きくなる状況を意図的に作り出しています。`b` フィールドはポインタ（マップ）であり、これがGC後に正しく保持されていることを確認することで、バグが修正されたことを検証します。

## コアとなるコードの解説

`if nb < 8` の条件分岐がこのバグ修正の核心です。

*   **`nb < 8` の場合**: これは、ビットバッファ `b` にまだ8ビット分の空きがあるか、あるいは8ビット未満のビットしか残っていない通常のケースです。この場合、ソースビットマップ `p` から次の8ビットを読み込み、`b` に追加します。これは、ビットマップを順次処理していく標準的な動作です。

*   **`else` ブロック (`nb >= 8`) の場合**: このケースは、特にスカラーテールを処理した後に発生する可能性が高いです。スカラーテールによってビットバッファ `b` に大量のゼロビットが詰め込まれ、`nb` が8以上になっている状態です。このとき、もし無条件に `uintptr(*p) << nb` を実行すると、`nb` が大きすぎるために `*p` から読み込んだ新しいビットが `b` の上位ビットにシフトされ、結果として失われてしまう（オーバーフローする）可能性があります。
    *   `nb -= 8` という処理は、ソースビットマップから実際にビットを読み込むことなく、ビットバッファ `b` から8ビットを「消費した」と見なします。これにより、ビットバッファ `b` の内容が適切にシフトダウンされ、次にソースビットマップからビットを読み込む際に、`b` のオーバーフローを防ぎます。
    *   この「消費」は、スカラーテールによって既にビットバッファに十分なゼロビットが供給されているため、実際にソースから読み込む必要がない、という状況を反映しています。これにより、ビットバッファ内のポインタ情報（またはゼロビット）が正しく保持され、GCがオブジェクトのポインタを正確に識別できるようになります。

この修正により、Goのガベージコレクタは、大きなスカラーテールを持つ型であっても、ヒープビットマップを正確に生成し、ポインタを誤ってスカラーとしてマークする問題を回避できるようになりました。

# [インデックス 26498] ファイルの概要

このコミットは、GoランタイムにおけるDarwin/386アーキテクチャでのシグナル転送（`sigfwd`）時のスタックアライメントの問題を修正するものです。特に、C言語で書かれたシグナルハンドラにシグナルを転送する際に、スタックが適切にアライメントされていないと問題が発生する可能性があり、それが`testcarchive`テストのハングアップ（SIGSEGVの無限ループ）を引き起こしていました。この変更は、スタックを16バイト境界にアライメントすることで、Cコードとの互換性を確保し、この問題を解決します。

## 変更の背景

このコミットの背景には、GoプログラムがC言語で書かれたライブラリ（特にCgoを介して利用されるもの）と連携する際の、シグナルハンドリングにおけるスタックアライメントの要件があります。

Goランタイムは、プログラムの実行中に発生する様々なシグナル（例えば、不正なメモリアクセスを示す`SIGSEGV`など）を処理します。Goの内部シグナルハンドラがこれらのシグナルを捕捉し、必要に応じてGoのランタイムが処理したり、元のシグナルハンドラ（Cコードによって設定されたものを含む）に転送したりします。

問題は、Darwin/386（macOS上の32ビットx86）環境において、GoランタイムがシグナルをC言語のシグナルハンドラに転送する際に、スタックポインタ（`SP`レジスタ）がC言語のABI（Application Binary Interface）が要求する特定の境界にアライメントされていない可能性があったことです。C言語の関数呼び出し規約では、パフォーマンス上の理由や特定のCPU命令（例: SSE命令）の要件から、スタックが16バイトや4バイトなどの特定の境界にアライメントされていることを前提とすることが一般的です。

スタックが適切にアライメントされていない状態でCシグナルハンドラが実行されると、不正なメモリアクセスが発生し、それが再び`SIGSEGV`を引き起こすという無限ループに陥ることがありました。コミットメッセージにある「`testcarchive`テストがSIGSEGVの無限シリーズでハングアップしていた」という記述は、この問題が実際に発生していたことを示しています。`testcarchive`はCgoアーカイブテストであり、GoとCの連携を検証するテストスイートの一部です。

この問題を解決するためには、`sigfwd`関数（シグナルを転送するGoランタイムの内部関数）がCシグナルハンドラを呼び出す前に、スタックをC ABIが要求するアライメントに調整する必要がありました。

## 前提知識の解説

### 1. スタックアライメント (Stack Alignment)

コンピュータのアーキテクチャでは、メモリ上のデータが特定のバイト境界に配置されていることを「アライメントされている」と言います。特にスタックは、関数呼び出し時にローカル変数や引数を格納するために使用されるメモリ領域であり、そのポインタ（`SP`レジスタ）が特定の境界にアライメントされていることが重要です。

*   **なぜ必要か？**:
    *   **パフォーマンス**: CPUは、アライメントされたデータにアクセスする方が高速です。非アライメントアクセスは、追加のサイクルを必要としたり、ハードウェア例外を引き起こしたりする可能性があります。
    *   **SIMD命令**: SSE (Streaming SIMD Extensions) などの一部のCPU命令は、16バイト境界にアライメントされたデータに対してのみ動作するように設計されています。
    *   **ABI (Application Binary Interface)**: オペレーティングシステムやコンパイラは、異なる言語やコンパイルされたコード間で互換性を保つために、特定のABIを定義しています。ABIは、関数呼び出し規約、レジスタの使用方法、スタックのレイアウト、スタックアライメント要件などを規定します。C言語のABIでは、多くの場合、スタックポインタが16バイト境界にアライメントされていることを要求します。

*   **32ビットx86 (i386) アーキテクチャ**: このアーキテクチャでは、スタックは通常4バイト境界にアライメントされますが、特定のABI（特にmacOS/Darwin）やコンパイラ設定では、関数呼び出し前にスタックを16バイト境界にアライメントすることが求められることがあります。これは、特にSSE命令を使用するコードとの互換性を確保するためです。

### 2. シグナルハンドリング (Signal Handling)

シグナルは、Unix系OSにおいてプロセスに非同期イベントを通知するメカニズムです。

*   **一般的なシグナル**:
    *   `SIGSEGV` (Segmentation Violation): プロセスが不正なメモリアドレスにアクセスしようとしたときに発生します。
    *   `SIGINT` (Interrupt): Ctrl+Cなどでプロセスを中断するときに発生します。
    *   `SIGTERM` (Terminate): プロセスを終了させる要求です。
*   **シグナルハンドラ**: シグナルが発生したときに実行される特別な関数です。Goランタイムは、自身の内部処理のために一部のシグナルを捕捉し、処理します。しかし、Cgoを介してCライブラリを使用している場合、Cライブラリが独自のシグナルハンドラを設定していることがあります。Goランタイムは、これらのCハンドラにシグナルを「転送」する場合があります。

### 3. GoランタイムとCgo

GoはC言語のコードと連携するための`cgo`ツールを提供しています。`cgo`を使用すると、GoプログラムからC関数を呼び出したり、CプログラムからGo関数を呼び出したりできます。この連携には、GoとCの間のABIの差異を適切に処理する必要があります。シグナルハンドリングもその一つで、Goランタイムがシグナルを捕捉した後、Cのシグナルハンドラに制御を渡す際には、CのABIに準拠した環境（特にスタックアライメント）を提供する必要があります。

### 4. アセンブリ言語の基本（x86）

このコミットの変更はアセンブリ言語で行われているため、基本的な命令を理解することが重要です。

*   **レジスタ**:
    *   `SP` (Stack Pointer): スタックの現在のトップを指すレジスタ。
    *   `FP` (Frame Pointer): 現在のスタックフレームのベースを指すレジスタ（Goでは`BP`レジスタが使われることもありますが、ここでは`FP`が引数アクセスに使われています）。
    *   `AX`, `BX`, `CX`, `DX`, `SI` など: 汎用レジスタ。
*   **命令**:
    *   `MOVL src, dest`: 32ビットの値を`src`から`dest`へ移動します。
    *   `SUBL val, reg`: `reg`から`val`を減算します（スタックはアドレスが減少する方向に伸びるため、スタックに領域を確保する際に`SP`を減算します）。
    *   `ANDL val, reg`: `reg`と`val`のビットごとのAND演算を行い、結果を`reg`に格納します。`ANDL $~15, SP`は、`SP`の下位4ビットをクリアすることで、`SP`を16バイト境界にアライメントする一般的な手法です（`~15`はビットマスクで、下位4ビットが0になります）。
    *   `CALL target`: `target`アドレスの関数を呼び出します。リターンアドレスをスタックにプッシュし、`target`へジャンプします。
    *   `RET`: 関数からリターンします。スタックからリターンアドレスをポップし、そのアドレスへジャンプします。
    *   `TEXT symbol(SB), flags, $framesize-argsize`: Goのアセンブリ構文で関数を定義します。`SB`はStatic Baseレジスタで、グローバルシンボルへのオフセット計算に使われます。`$framesize`はローカル変数用のスタックフレームサイズ、`argsize`は引数のサイズです。

## 技術的詳細

このコミットは、`src/runtime/sys_darwin_386.s`ファイル内の`runtime·sigfwd`関数を変更しています。この関数は、Goランタイムがシグナルを捕捉した後、元のシグナルハンドラ（C言語で書かれている可能性がある）にシグナルを転送するために使用されます。

変更の核心は、C言語のシグナルハンドラを呼び出す前に、スタックポインタ（`SP`）を16バイト境界にアライメントすることです。

元のコードでは、`sigfwd`関数は引数（`sig`, `info`, `ctx`）をスタックにプッシュし、直接`CALL AX`（`fn`レジスタに格納されたシグナルハンドラのアドレス）を実行していました。この際、スタックのアライメントは保証されていませんでした。

変更後のコードでは、以下の手順でスタックアライメントを確保しています。

1.  **引数のレジスタへの退避**: `fn`, `sig`, `info`, `ctx`の各引数を、それぞれ`AX`, `BX`, `CX`, `DX`レジスタに退避します。これは、スタック操作中にこれらの値が上書きされるのを防ぐためです。
2.  **現在のスタックポインタの保存**: `MOVL SP, SI`により、現在のスタックポインタ`SP`の値を`SI`レジスタに保存します。これは、シグナルハンドラからのリターン後に元のスタック状態を復元するために必要です。
3.  **スタック領域の確保とアライメント**:
    *   `SUBL $32, SP`: スタックポインタを32バイト減算します。これは、シグナルハンドラに渡す引数（3つで12バイト）と、元の`SP`を保存するための領域（4バイト）、そして将来的な拡張やアライメント調整のための余裕を考慮したものです。
    *   `ANDL $~15, SP`: スタックポインタを16バイト境界にアライメントします。`~15`は`0xFFFFFFF0`（32ビットの場合）に相当し、`SP`の下位4ビットを強制的に0にすることで、`SP`が16の倍数になるようにします。これにより、C言語のABIが要求するスタックアライメントが満たされます。
4.  **引数のプッシュ**: 退避しておいた`sig`, `info`, `ctx`の値を、アライメントされた新しいスタックフレームの適切な位置にプッシュします。
    *   `MOVL BX, 0(SP)`: `sig`を`SP+0`に。
    *   `MOVL CX, 4(SP)`: `info`を`SP+4`に。
    *   `MOVL DX, 8(SP)`: `ctx`を`SP+8`に。
    *   `MOVL SI, 12(SP)`: 元のスタックポインタ`SI`を`SP+12`に保存します。これは、シグナルハンドラがリターンした後に`SP`を復元するために使用されます。
5.  **Cシグナルハンドラの呼び出し**: `CALL AX`を実行し、`AX`に格納されたCシグナルハンドラを呼び出します。この時点で、スタックはC ABIの要件に従ってアライメントされています。
6.  **スタックポインタの復元**: Cシグナルハンドラからリターンした後、`MOVL 12(SP), AX`で保存しておいた元のスタックポインタの値を`AX`にロードし、`MOVL AX, SP`で`SP`を元の値に戻します。これにより、`sigfwd`関数が呼び出される前のスタック状態が復元されます。
7.  **関数からのリターン**: `RET`命令で`runtime·sigfwd`関数からリターンします。

この一連の操作により、GoランタイムがCシグナルハンドラを呼び出す際に、Cコードが期待するスタックアライメントが保証され、`SIGSEGV`の無限ループが回避されます。

## コアとなるコードの解説

変更されたのは`runtime·sigfwd`関数です。

**変更前:**

```assembly
TEXT runtime·sigfwd(SB),NOSPLIT,$12-16
	MOVL	sig+4(FP), AX
	MOVL	AX, 0(SP)
	MOVL	info+8(FP), AX
	MOVL	AX, 4(SP)
	MOVL	ctx+12(FP), AX
	MOVL	AX, 8(SP)
	MOVL	fn+0(FP), AX // fnのアドレスをAXにロード
	CALL	AX           // fnを呼び出す
	RET
```
このコードは、`sig`, `info`, `ctx`の3つの引数をスタックにプッシュし、`fn`（シグナルハンドラのアドレス）を`AX`レジスタにロードして`CALL`命令で呼び出しています。この際、スタックポインタ`SP`のアライメントは特に調整されていません。`$12-16`は、この関数が12バイトのスタックフレームを使用し、16バイトの引数を受け取ることを示しています（GoのABIでは、引数は呼び出し元がスタックにプッシュするため、呼び出される関数側ではフレームサイズに含めません）。

**変更後:**

```assembly
TEXT runtime·sigfwd(SB),NOSPLIT,$0-16 // スタックフレームサイズが$0に変更
	MOVL	fn+0(FP), AX  // fnのアドレスをAXにロード
	MOVL	sig+4(FP), BX // sigをBXに退避
	MOVL	info+8(FP), CX // infoをCXに退避
	MOVL	ctx+12(FP), DX // ctxをDXに退避
	MOVL	SP, SI        // 現在のSPをSIに保存
	SUBL	$32, SP		// スタックを32バイト減らす
	ANDL	$~15, SP	// SPを16バイト境界にアライメント
	MOVL	BX, 0(SP)   // sigを新しいスタックの0オフセットにプッシュ
	MOVL	CX, 4(SP)   // infoを新しいスタックの4オフセットにプッシュ
	MOVL	DX, 8(SP)   // ctxを新しいスタックの8オフセットにプッシュ
	MOVL	SI, 12(SP)  // 保存した元のSPを新しいスタックの12オフセットにプッシュ
	CALL	AX          // fnを呼び出す
	MOVL	12(SP), AX  // スタックに保存した元のSPをAXにロード
	MOVL	AX, SP      // SPを元の値に戻す
	RET
```
変更後のコードでは、`TEXT`ディレクティブのスタックフレームサイズが`$12`から`$0`に変更されています。これは、ローカル変数をスタックに直接確保するのではなく、レジスタに退避したり、一時的にスタックを操作して引数を配置したりするためです。

1.  `MOVL fn+0(FP), AX`: シグナルハンドラのアドレス`fn`を`AX`レジスタにロードします。
2.  `MOVL sig+4(FP), BX`, `MOVL info+8(FP), CX`, `MOVL ctx+12(FP), DX`: `sig`, `info`, `ctx`の各引数をそれぞれ`BX`, `CX`, `DX`レジスタに退避します。これは、スタック操作中にこれらの値が失われないようにするためです。
3.  `MOVL SP, SI`: 現在のスタックポインタ`SP`の値を`SI`レジスタに保存します。これは、Cシグナルハンドラから戻った後に`SP`を元の位置に戻すために必要です。
4.  `SUBL $32, SP`: スタックポインタを32バイト減算します。これにより、スタック上に32バイトの領域が確保されます。スタックはアドレスが減少する方向に伸びるため、減算することで領域を確保します。
5.  `ANDL $~15, SP`: スタックポインタ`SP`を16バイト境界にアライメントします。`~15`はビットマスク`0xFFFFFFF0`であり、`SP`の下位4ビットをクリアすることで、`SP`が16の倍数になるように強制します。これにより、C言語のABIが要求するスタックアライメントが満たされます。
6.  `MOVL BX, 0(SP)`, `MOVL CX, 4(SP)`, `MOVL DX, 8(SP)`: 退避しておいた`sig`, `info`, `ctx`の値を、アライメントされた新しいスタックフレームの先頭から順に配置します。これらはCシグナルハンドラへの引数となります。
7.  `MOVL SI, 12(SP)`: 保存しておいた元のスタックポインタ`SI`の値を、新しいスタックフレームの`SP+12`の位置に保存します。
8.  `CALL AX`: `AX`レジスタに格納されているCシグナルハンドラを呼び出します。この呼び出しは、スタックが適切にアライメントされた状態で行われます。
9.  `MOVL 12(SP), AX`: Cシグナルハンドラからリターンした後、スタックの`SP+12`に保存しておいた元のスタックポインタの値を`AX`レジスタにロードします。
10. `MOVL AX, SP`: `AX`レジスタの値を`SP`に移動し、スタックポインタを`sigfwd`関数が呼び出される前の元の位置に復元します。
11. `RET`: `runtime·sigfwd`関数からリターンします。

この変更により、GoランタイムとC言語のシグナルハンドラ間の互換性が向上し、Darwin/386環境での安定性が確保されました。

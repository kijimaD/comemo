# [インデックス 24585] ファイルの概要

このコミットは、Goランタイムにおける特定の条件下で発生する「leftover stack barriers」パニックを修正します。具体的には、`runtime.Goexit()`がゴルーチン終了スタブである`goexit()`を呼び出す代わりに、実際にゴルーチン終了処理を実装している`goexit1()`を直接呼び出すように変更することで、この問題を解決しています。また、将来的な同様の問題を防ぐため、`goexit()`関数のプロトタイプが変更され、意図しない呼び出しを困難にしています。

```
       stack shrinking, but not past X.
    
    4. Goroutine A calls runtime.Goexit(), which calls goexit(), which
       calls goexit1().

       performs a stack shrink, which calls gentraceback.

    only two frames up at this point, even though there may really be many
    frames above it. More to the point, the stack barrier at X is above

    the end of gentraceback, it checks that it saw all of the stack

    of exiting a goroutine, rather than goexit, the exit stub.

    prototype to ensure this wouldn't happen again rather than pollute the
```

## 変更の背景

このコミットは、Goランタイムにおいて特定の状況下で発生する「leftover stack barriers」というパニックを解決するために導入されました。このパニックは、ガベージコレクタ（GC）のスタックバリアとゴルーチンのスタック管理、特にスタック縮小処理との間の相互作用の不整合によって引き起こされます。

問題の発生シーケンスは以下の通りです。

1.  **大きなスタックを持つゴルーチンA**: まず、ある程度の大きさのスタックを持つゴルーチンAが存在します。
2.  **GCによるスタックバリアの設置**: ガベージコレクタのスキャンフェーズが実行され、ゴルーチンAのスタック内にスタックバリアが設置されます。このとき、最も上位のスタックバリアがアドレスXに配置されたとします。
3.  **スタックの巻き戻しと縮小候補**: ゴルーチンAがスタックを十分に巻き戻し、スタック縮小の候補となりますが、アドレスXより下には巻き戻しません。
4.  **`runtime.Goexit()`の呼び出し**: ゴルーチンAが`runtime.Goexit()`を呼び出します。この関数は、当時`goexit()`（ゴルーチン終了スタブ）を呼び出し、さらに`goexit()`が`goexit1()`を呼び出すという連鎖がありました。
5.  **GCのマーク終了フェーズ**: ガベージコレクタがマーク終了フェーズに入ります。
6.  **プリエンプションとスタック縮小**: `goexit1()`のプロローグでゴルーチンAがプリエンプトされ、スタック縮小が実行されます。このスタック縮小の過程で`gentraceback`関数が呼び出されます。

ここで問題が発生します。`gentraceback`はスタックをトレースする際に`goexit`フレームを検出すると、そこでスタックトレースを停止するように設計されていました。しかし、この時点では`goexit`フレームはスタックの比較的浅い位置（`goexit1()`の2フレーム上）にあり、本来トレースされるべきスタックバリアXは`goexit`フレームよりも上位に存在していました。結果として、`gentraceback`はスタックバリアXを検出できず、処理の最後にすべてのスタックバリアが検出されたことを確認するチェックで失敗し、「leftover stack barriers」パニックを引き起こしていました。

この問題は、`runtime.Goexit()`がゴルーチン終了処理の「スタブ」である`goexit()`を介して「実体」である`goexit1()`を呼び出すという間接的な構造が原因でした。

## 前提知識の解説

このコミットの理解には、以下のGoランタイムの概念が不可欠です。

*   **`runtime.Goexit()`**:
    *   現在のゴルーチンを終了させるために使用される関数です。`panic`や`recover`とは異なり、`Goexit()`が呼び出されると、そのゴルーチン内の遅延関数（`defer`）は実行されますが、`recover`によってパニックを捕捉して実行を継続することはできません。
    *   主に、特定のゴルーチンを明示的に終了させたい場合に使用されます。
*   **ゴルーチン終了スタブ (`goexit`)**:
    *   Goランタイムが各ゴルーチンのスタックの最上位に配置する特別な関数です。
    *   ゴルーチンのエントリポイント関数（ユーザーが`go`キーワードで起動した関数）が正常に終了すると、この`goexit`スタブに制御が戻ります。
    *   `goexit`の役割は、ゴルーチンの終了処理（`goexit1`の呼び出し）をトリガーすることです。
*   **`goexit1()`**:
    *   実際にゴルーチンの終了処理（スタックの解放、スケジューラへの通知など）を行うランタイム関数です。`goexit`スタブから呼び出されることを想定しています。
*   **スタックバリア (Stack Barriers)**:
    *   Goのコンカレントガベージコレクタが、ゴルーチンのスタックをスキャンする際に使用するメカニズムです。
    *   GCがスタックをスキャンしている間、スタックの一部が変更されないように保護するために、特定のメモリ領域に「バリア」を設置します。これにより、GCが正確な情報を取得し、データ競合を防ぎます。
    *   バリアは、GCのスキャンフェーズ中に設置され、マーク終了フェーズでチェックされます。
*   **ガベージコレクタ (Garbage Collector - GC)**:
    *   Goの自動メモリ管理システムです。不要になったメモリを自動的に解放します。
    *   **スキャンフェーズ (Scan Phase)**: GCがルート（グローバル変数、ゴルーチンのスタック、レジスタなど）から到達可能なオブジェクトを特定し、マークするフェーズです。このフェーズでスタックバリアが設置されることがあります。
    *   **マーク終了フェーズ (Mark Termination)**: オブジェクトのマーク付けが完了し、次のフェーズ（スイープ）に移行する前の最終処理を行うフェーズです。このフェーズでスタックバリアの整合性がチェックされることがあります。
*   **スタック縮小 (Stack Shrinking)**:
    *   Goのゴルーチンスタックは動的に拡張されますが、不要になったメモリを解放するために縮小されることもあります。
    *   ゴルーチンが大量のスタックメモリを一時的に使用した後、その必要がなくなった場合に、ランタイムがスタックをより小さなサイズに縮小します。これはGCサイクル中やゴルーチンがプリエンプトされた際に行われることがあります。
*   **`gentraceback`**:
    *   Goランタイムの内部関数で、ゴルーチンのスタックトレースを生成するために使用されます。
    *   デバッグ情報やプロファイリング、パニック発生時のスタックダンプなどで呼び出されます。
    *   スタックフレームを一つずつ遡り、各関数の呼び出し元を特定します。この過程でスタックバリアの存在も考慮する必要があります。

## 技術的詳細

この問題の核心は、`runtime.Goexit()`がゴルーチン終了処理の「スタブ」である`goexit()`を呼び出し、その`goexit()`が「実体」である`goexit1()`を呼び出すという二段階の呼び出し構造にありました。この間接的な呼び出しパスが、ガベージコレクタのスタックバリアとスタックトレース機構（`gentraceback`）との間で予期せぬ相互作用を引き起こしました。

具体的な問題点は以下の通りです。

1.  **スタックバリアの設置**: GCのスキャンフェーズ中に、ゴルーチンAのスタックにスタックバリアが設置されます。これらのバリアは、GCがスタックを安全にスキャンするために重要です。
2.  **`gentraceback`の挙動**: `gentraceback`は、スタックを遡る際に`goexit`フレームを検出すると、そこでスタックトレースを停止するように実装されていました。これは、`goexit`がゴルーチンスタックの論理的な終端を示すため、通常は問題ありません。
3.  **タイミングの問題**:
    *   ゴルーチンAが`runtime.Goexit()`を呼び出し、`goexit()`を介して`goexit1()`のプロローグに到達した直後、GCのマーク終了フェーズ中にプリエンプトされます。
    *   このプリエンプション中にスタック縮小がトリガーされ、その過程で`gentraceback`が呼び出されます。
    *   この時点でのスタックの状態は、`goexit1()`が呼び出される直前であり、`goexit`フレームはスタックの比較的浅い位置に存在します。
    *   しかし、GCによって設置されたスタックバリアの中には、`goexit`フレームよりもさらに上位（つまり、`goexit`フレームがスタックの論理的な終端として認識されるべき位置よりも「上」）に存在するものがまだ残っていました。
4.  **バリアの未検出とパニック**: `gentraceback`は`goexit`フレームでトレースを停止するため、その上位に残っていたスタックバリアを検出できませんでした。`gentraceback`の終了時に、すべてのスタックバリアが検出されたかどうかの整合性チェックが行われ、未検出のバリアが存在したために「leftover stack barriers」パニックが発生しました。

**解決策**:

この問題に対する修正は二つの側面から行われました。

1.  **`runtime.Goexit()`から`goexit1()`への直接呼び出し**:
    *   `runtime.Goexit()`が、中間的な`goexit()`スタブを介さずに、ゴルーチン終了処理の実体である`goexit1()`を直接呼び出すように変更されました。
    *   これにより、`runtime.Goexit()`が呼び出された際に、`goexit`フレームがスタックトレースの途中に現れることがなくなり、`gentraceback`がスタックバリアを正しく検出できるようになります。
2.  **`goexit`関数のプロトタイプ変更**:
    *   将来的に同様の問題が誤って再導入されることを防ぐため、`goexit`関数のシグネチャが変更されました。具体的には、`goexit()`は引数として`neverCallThisFunction`という型のダミー引数を取るようになりました (`func goexit(neverCallThisFunction)`)。
    *   この変更により、`goexit`を直接呼び出すには、この特殊な型を明示的に渡す必要があり、意図しない呼び出しが非常に困難になります。これは、`goexit`がランタイムによってスタックの最上位に配置される特殊なスタブであり、直接呼び出されるべきではないという設計意図をコードレベルで強制するものです。

この修正により、GCのスタックバリアとスタックトレース機構の間の整合性が保たれ、特定のタイミングで発生していたパニックが解消されました。

## コアとなるコードの解説

### `src/runtime/panic.go` の変更点

*   `func Goexit()` 内で、`goexit()` の呼び出しが `goexit1()` に変更されました。
    *   **変更前**: `goexit()`
    *   **変更後**: `goexit1()`
*   この変更により、`runtime.Goexit()`がゴルーチン終了処理の「スタブ」である`goexit()`を介さず、直接「実体」である`goexit1()`を呼び出すようになります。これにより、前述の問題発生シーケンスにおける`gentraceback`の誤ったスタックトレース停止が回避され、スタックバリアの整合性チェックが正しく行われるようになります。

### `src/runtime/stubs.go` の変更点

*   `goexit` 関数の宣言が変更されました。
    *   **変更前**: `func goexit()`
    *   **変更後**:
        ```go
        type neverCallThisFunction struct{}
        func goexit(neverCallThisFunction)
        ```
*   `neverCallThisFunction`という空の構造体が定義され、`goexit`関数がこの型の引数を取るように変更されました。これは、`goexit`がランタイムによって特殊な方法でスタックに配置されるスタブであり、開発者が直接呼び出すべきではないことを明示的に示すためのものです。この変更により、誤って`goexit`を直接呼び出そうとするとコンパイルエラーが発生し、将来的な同様の問題の再発を防ぎます。
*   `goexit`関数のコメントが追加・更新され、その役割（ゴルーチンスタックの最上位にあるリターンスタブ）、`goexit1`を呼び出すこと、そして**直接呼び出すべきではない**こと、`gentraceback`が`goexit`をスタックの終端と見なすこと、直接呼び出すとパニックを引き起こす可能性があることが詳細に説明されています。

これらの変更は、Goランタイムの内部的なスタック管理とガベージコレクションのメカニズムの間の繊細な相互作用を修正し、システムの安定性を向上させるものです。

```
at the right places in the runtime, but chose to change the goexit
prototype to ensure this wouldn't happen again rather than pollute the
runtime with ugly testing code.
```

## 変更の背景

このコミットは、Goランタイムにおいて特定の状況下で発生する「leftover stack barriers」というパニックを解決するために導入されました。このパニックは、ガベージコレクタ（GC）のスタックバリアとゴルーチンのスタック管理、特にスタック縮小処理との間の相互作用の不整合によって引き起こされます。

問題の発生シーケンスは以下の通りです。

1.  **大きなスタックを持つゴルーチンA**: まず、ある程度の大きさのスタックを持つゴルーチンAが存在します。
2.  **GCによるスタックバリアの設置**: ガベージコレクタのスキャンフェーズが実行され、ゴルーチンAのスタック内にスタックバリアが設置されます。このとき、最も上位のスタックバリアがアドレスXに配置されたとします。
3.  **スタックの巻き戻しと縮小候補**: ゴルーチンAがスタックを十分に巻き戻し、スタック縮小の候補となりますが、アドレスXより下には巻き戻しません。
4.  **`runtime.Goexit()`の呼び出し**: ゴルーチンAが`runtime.Goexit()`を呼び出します。この関数は、当時`goexit()`（ゴルーチン終了スタブ）を呼び出し、さらに`goexit()`が`goexit1()`を呼び出すという連鎖がありました。
5.  **GCのマーク終了フェーズ**: ガベージコレクタがマーク終了フェーズに入ります。
6.  **プリエンプションとスタック縮小**: `goexit1()`のプロローグでゴルーチンAがプリエンプトされ、スタック縮小が実行されます。このスタック縮小の過程で`gentraceback`関数が呼び出されます。

ここで問題が発生します。`gentraceback`はスタックをトレースする際に`goexit`フレームを検出すると、そこでスタックトレースを停止するように設計されていました。しかし、この時点では`goexit`フレームはスタックの比較的浅い位置（`goexit1()`の2フレーム上）にあり、本来トレースされるべきスタックバリアXは`goexit`フレームよりも上位に存在していました。結果として、`gentraceback`はスタックバリアXを検出できず、処理の最後にすべてのスタックバリアが検出されたことを確認するチェックで失敗し、「leftover stack barriers」パニックを引き起こしていました。

この問題は、`runtime.Goexit()`がゴルーチン終了処理の「スタブ」である`goexit()`を介して「実体」である`goexit1()`を呼び出すという間接的な構造が原因でした。

## 前提知識の解説

このコミットの理解には、以下のGoランタイムの概念が不可欠です。

*   **`runtime.Goexit()`**:
    *   現在のゴルーチンを終了させるために使用される関数です。`panic`や`recover`とは異なり、`Goexit()`が呼び出されると、そのゴルーチン内の遅延関数（`defer`）は実行されますが、`recover`によってパニックを捕捉して実行を継続することはできません。
    *   主に、特定のゴルーチンを明示的に終了させたい場合に使用されます。
*   **ゴルーチン終了スタブ (`goexit`)**:
    *   Goランタイムが各ゴルーチンのスタックの最上位に配置する特別な関数です。
    *   ゴルーチンのエントリポイント関数（ユーザーが`go`キーワードで起動した関数）が正常に終了すると、この`goexit`スタブに制御が戻ります。
    *   `goexit`の役割は、ゴルーチンの終了処理（`goexit1`の呼び出し）をトリガーすることです。
*   **`goexit1()`**:
    *   実際にゴルーチンの終了処理（スタックの解放、スケジューラへの通知など）を行うランタイム関数です。`goexit`スタブから呼び出されることを想定しています。
*   **スタックバリア (Stack Barriers)**:
    *   Goのコンカレントガベージコレクタが、ゴルーチンのスタックをスキャンする際に使用するメカニズムです。
    *   GCがスタックをスキャンしている間、スタックの一部が変更されないように保護するために、特定のメモリ領域に「バリア」を設置します。これにより、GCが正確な情報を取得し、データ競合を防ぎます。
    *   バリアは、GCのスキャンフェーズ中に設置され、マーク終了フェーズでチェックされます。
*   **ガベージコレクタ (Garbage Collector - GC)**:
    *   Goの自動メモリ管理システムです。不要になったメモリを自動的に解放します。
    *   **スキャンフェーズ (Scan Phase)**: GCがルート（グローバル変数、ゴルーチンのスタック、レジスタなど）から到達可能なオブジェクトを特定し、マークするフェーズです。このフェーズでスタックバリアが設置されることがあります。
    *   **マーク終了フェーズ (Mark Termination)**: オブジェクトのマーク付けが完了し、次のフェーズ（スイープ）に移行する前の最終処理を行うフェーズです。このフェーズでスタックバリアの整合性がチェックされることがあります。
*   **スタック縮小 (Stack Shrinking)**:
    *   Goのゴルーチンスタックは動的に拡張されますが、不要になったメモリを解放するために縮小されることもあります。
    *   ゴルーチンが大量のスタックメモリを一時的に使用した後、その必要がなくなった場合に、ランタイムがスタックをより小さなサイズに縮小します。これはGCサイクル中やゴルーチンがプリエンプトされた際に行われることがあります。
*   **`gentraceback`**:
    *   Goランタイムの内部関数で、ゴルーチンのスタックトレースを生成するために使用されます。
    *   デバッグ情報やプロファイリング、パニック発生時のスタックダンプなどで呼び出されます。
    *   スタックフレームを一つずつ遡り、各関数の呼び出し元を特定します。この過程でスタックバリアの存在も考慮する必要があります。

## 技術的詳細

この問題の核心は、`runtime.Goexit()`がゴルーチン終了処理の「スタブ」である`goexit()`を呼び出し、その`goexit()`が「実体」である`goexit1()`を呼び出すという二段階の呼び出し構造にありました。この間接的な呼び出しパスが、ガベージコレクタのスタックバリアとスタックトレース機構（`gentraceback`）との間で予期せぬ相互作用を引き起こしました。

具体的な問題点は以下の通りです。

1.  **スタックバリアの設置**: GCのスキャンフェーズ中に、ゴルーチンAのスタックにスタックバリアが設置されます。これらのバリアは、GCがスタックを安全にスキャンするために重要です。
2.  **`gentraceback`の挙動**: `gentraceback`は、スタックを遡る際に`goexit`フレームを検出すると、そこでスタックトレースを停止するように実装されていました。これは、`goexit`がゴルーチンスタックの論理的な終端を示すため、通常は問題ありません。
3.  **タイミングの問題**:
    *   ゴルーチンAが`runtime.Goexit()`を呼び出し、`goexit()`を介して`goexit1()`のプロローグに到達した直後、GCのマーク終了フェーズ中にプリエンプトされます。
    *   このプリエンプション中にスタック縮小がトリガーされ、その過程で`gentraceback`が呼び出されます。
    *   この時点でのスタックの状態は、`goexit1()`が呼び出される直前であり、`goexit`フレームはスタックの比較的浅い位置に存在します。
    *   しかし、GCによって設置されたスタックバリアの中には、`goexit`フレームよりもさらに上位（つまり、`goexit`フレームがスタックの論理的な終端として認識されるべき位置よりも「上」）に存在するものがまだ残っていました。
4.  **バリアの未検出とパニック**: `gentraceback`は`goexit`フレームでトレースを停止するため、その上位に残っていたスタックバリアを検出できませんでした。`gentraceback`の終了時に、すべてのスタックバリアが検出されたかどうかの整合性チェックが行われ、未検出のバリアが存在したために「leftover stack barriers」パニックが発生しました。

**解決策**:

この問題に対する修正は二つの側面から行われました。

1.  **`runtime.Goexit()`から`goexit1()`への直接呼び出し**:
    *   `runtime.Goexit()`が、中間的な`goexit()`スタブを介さずに、ゴルーチン終了処理の実体である`goexit1()`を直接呼び出すように変更されました。
    *   これにより、`runtime.Goexit()`が呼び出された際に、`goexit`フレームがスタックトレースの途中に現れることがなくなり、`gentraceback`がスタックバリアを正しく検出できるようになります。
2.  **`goexit`関数のプロトタイプ変更**:
    *   将来的に同様の問題が誤って再導入されることを防ぐため、`goexit`関数のシグネチャが変更されました。具体的には、`goexit()`は引数として`neverCallThisFunction`という型のダミー引数を取るようになりました (`func goexit(neverCallThisFunction)`)。
    *   この変更により、`goexit`を直接呼び出すには、この特殊な型を明示的に渡す必要があり、意図しない呼び出しが非常に困難になります。これは、`goexit`がランタイムによってスタックの最上位に配置される特殊なスタブであり、直接呼び出されるべきではないという設計意図をコードレベルで強制するものです。

この修正により、GCのスタックバリアとスタックトレース機構の間の整合性が保たれ、特定のタイミングで発生していたパニックが解消されました。

## コアとなるコードの解説

### `src/runtime/panic.go` の変更点

*   `func Goexit()` 内で、`goexit()` の呼び出しが `goexit1()` に変更されました。
    *   **変更前**: `goexit()`
    *   **変更後**: `goexit1()`
*   この変更により、`runtime.Goexit()`がゴルーチン終了処理の「スタブ」である`goexit()`を介さず、直接「実体」である`goexit1()`を呼び出すようになります。これにより、前述の問題発生シーケンスにおける`gentraceback`の誤ったスタックトレース停止が回避され、スタックバリアの整合性チェックが正しく行われるようになります。

### `src/runtime/stubs.go` の変更点

*   `goexit` 関数の宣言が変更されました。
    *   **変更前**: `func goexit()`
    *   **変更後**:
        ```go
        type neverCallThisFunction struct{}
        func goexit(neverCallThisFunction)
        ```
*   `neverCallThisFunction`という空の構造体が定義され、`goexit`関数がこの型の引数を取るように変更されました。これは、`goexit`がランタイムによって特殊な方法でスタックに配置されるスタブであり、開発者が直接呼び出すべきではないことを明示的に示すためのものです。この変更により、誤って`goexit`を直接呼び出そうとするとコンパイルエラーが発生し、将来的な同様の問題の再発を防ぎます。
*   `goexit`関数のコメントが追加・更新され、その役割（ゴルーチンスタックの最上位にあるリターンスタブ）、`goexit1`を呼び出すこと、そして**直接呼び出すべきではない**こと、`gentraceback`が`goexit`をスタックの終端と見なすこと、直接呼び出すとパニックを引き起こす可能性があることが詳細に説明されています。

これらの変更は、Goランタイムの内部的なスタック管理とガベージコレクションのメカニズムの間の繊細な相互作用を修正し、システムの安定性を向上させるものです。

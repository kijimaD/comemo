## 元コミット内容

このコミット自体は、既存の最適化を一時的に無効化するものです。したがって、「元コミット内容」とは、この最適化が導入された際の意図を指します。

Goコンパイラは、`append`組み込み関数に対して「インプレースアペンド最適化」と呼ばれる最適化を適用します。これは、スライスに要素を追加する際に、既存の基盤配列に十分な容量がある場合、新しい配列を割り当てることなく、その場で（インプレースで）スライスを変更するものです。これにより、メモリ割り当てを減らし、パフォーマンスを向上させることができます。

この最適化は、コンパイラのSSA (Static Single Assignment) バックエンドで処理されます。`append`操作は`OAPPEND`ノードとして表現され、コンパイラは`inplace`フラグを使用して、インプレースで処理できるかどうかを判断します。`inplace`が`true`の場合、コンパイラは既存のスライスを直接変更し、長さのみを更新します。

## 変更の背景

この変更は、Goコンパイラの`append`関数のインプレース最適化に関連するバグを修正するために行われました。

*   **Fixes #15246**: このコミットは、Issue #15246で報告されたバグを修正します。このバグは、インプレースアペンド最適化が特定の条件下で誤ったコードを生成し、プログラムのクラッシュや不正な動作を引き起こす可能性があったことを示唆しています。
*   **Re-opens #14969**: このコミットは、Issue #14969を再オープンします。これは、以前に修正されたはずのバグが、今回のインプレースアペンド最適化の関連問題によって再発した可能性を示しています。コンパイラの最適化は複雑であり、一つの修正が別の問題を引き起こしたり、既存のバグを再表面化させたりすることがあります。この場合、インプレースアペンドの特殊ケースを一時的に無効にすることで、これらのバグの根本原因を特定し、より堅牢な解決策を開発するための時間を稼ぐ目的があったと考えられます。

コンパイラの最適化はパフォーマンス向上に不可欠ですが、同時に正確性を損なわないように細心の注意を払う必要があります。バグが発見された場合、一時的に最適化を無効化して安全性を確保し、その間に根本的な原因を究明し修正するというアプローチは、ソフトウェア開発において一般的なプラクティスです。

## 前提知識の解説

### Go言語の`append`関数

Go言語の`append`関数は、スライスに要素を追加するために使用される組み込み関数です。そのシグネチャは`func append(slice []T, elems ...T) []T`です。`append`は、追加後の新しいスライスを返します。

*   **容量が十分な場合**: スライスの基盤配列に十分な容量がある場合、`append`は既存の配列の空きスペースに要素を追加し、スライスの長さを更新して、同じ基盤配列を参照する新しいスライスヘッダを返します。この操作は「インプレース」で行われます。
*   **容量が不足する場合**: スライスの基盤配列に十分な容量がない場合、`append`はより大きな新しい基盤配列を割り当て、既存の要素と新しい要素をその新しい配列にコピーし、新しい基盤配列を参照するスライスヘッダを返します。

### GoコンパイラのSSA (Static Single Assignment) フォーム

SSA (Static Single Assignment) フォームは、コンパイラ最適化の中間表現（IR: Intermediate Representation）の一種です。SSAでは、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。

Goコンパイラは、Go 1.7以降でSSAバックエンドを導入し、より高度な最適化を可能にしました。SSA形式に変換されたコードは、レジスタ割り当て、デッドコード削除、共通部分式除去など、様々な最適化パスを通過します。

### インプレースアペンド最適化

前述の通り、Goコンパイラは`append`関数が既存の基盤配列に要素を追加できる場合、新しい配列の割り当てを避ける「インプレースアペンド最適化」を行います。これは、メモリ割り当てのオーバーヘッドを削減し、ガベージコレクションの負荷を軽減することで、プログラムの実行速度を向上させます。

コンパイラは、`append`操作をSSA形式に変換する際に、この最適化を適用できるかどうかを判断します。具体的には、`OAPPEND`ノードが処理される際に、`inplace`フラグが設定され、インプレースで処理可能であれば、既存のスライスを直接変更するコードが生成されます。

### ライトバリア (Write Barriers)

ライトバリアは、ガベージコレクタが正確に動作するために必要なメカニズムです。Goのガベージコレクタは、並行マーク＆スイープ方式を採用しており、プログラムが実行中にヒープ上のオブジェクトグラフを変更する可能性があります。

ライトバリアは、ポインタがヒープ上のオブジェクトに書き込まれる際に実行される小さなコードスニペットです。これにより、ガベージコレクタはオブジェクトグラフの変更を追跡し、誤って到達可能なオブジェクトを回収してしまうことを防ぎます。

インプレースアペンド最適化とライトバリアの関係は、スライスがスタック上に割り当てられているか、ヒープ上に割り当てられているかによって変わります。スタック上のスライスはガベージコレクションの対象外であるため、ライトバリアは不要です。しかし、ヒープ上のスライスに対してインプレースアペンドが行われる場合、ガベージコレクタの正確性を保つためにライトバリアが適切に機能する必要があります。コミットメッセージのコメントにある「If the slice can be SSA'd, it'll be on the stack, so there will be no write barriers, so there's no need to attempt to prevent them.」は、この関係性を示唆しています。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/gc/ssa.go`ファイル内の`stmt`メソッド、特に`OAPPEND`（`append`操作を表すASTノード）を処理する部分を変更しています。

変更前のコードでは、以下の条件が満たされた場合にインプレースアペンドの特殊ケースが適用されていました。

```go
if samesafeexpr(n.Left, rhs.List.First()) && !s.canSSA(n.Left) {
    s.append(rhs, true)
    return
}
```

*   `samesafeexpr(n.Left, rhs.List.First())`: これは、`append`の左辺（スライス）と右辺の最初の要素が同じ安全な式であるかどうかをチェックします。つまり、`s = append(s, x)`のような形式で、スライス`s`が自身に追加されるケースを指します。
*   `!s.canSSA(n.Left)`: これは、左辺のスライスがSSA形式に変換できない（つまり、スタック上に割り当てられない）ことを意味します。もしスライスがSSA形式に変換可能であれば、それはスタック上に割り当てられ、ライトバリアは不要になります。この条件は、ヒープ上に割り当てられたスライスに対するインプレースアペンドのケースを扱っていることを示唆しています。

この条件が真の場合、`s.append(rhs, true)`が呼び出され、インプレースアペンドが実行されていました。

このコミットでは、この条件の前に`const doInPlaceAppend = false`という定数を導入し、その定数を使ってインプレースアペンドの特殊ケースを無効化しています。

```go
const doInPlaceAppend = false // issue 15246
if doInPlaceAppend && samesafeexpr(n.Left, rhs.List.First()) && !s.canSSA(n.Left) {
    s.append(rhs, true)
    return
}
```

`doInPlaceAppend`が`false`であるため、`if`文の条件全体が常に`false`となり、インプレースアペンドの特殊ケースは実行されなくなります。これにより、Issue #15246で報告されたバグが回避され、Issue #14969の再発も防がれます。

この変更は一時的なものであり、コメントに`// issue 15246`と明記されていることから、バグの根本原因が特定され、より恒久的な修正が適用されるまでの間に、安全性を確保するための措置として導入されたと考えられます。

## コアとなるコードの解説

変更は`src/cmd/compile/internal/gc/ssa.go`ファイルの699行目付近にあります。

*   `- if samesafeexpr(n.Left, rhs.List.First()) && !s.canSSA(n.Left) {`
    *   これは変更前のコードで、インプレースアペンドの特殊ケースを適用するための条件分岐です。
    *   `n.Left`は`append`関数の第一引数（スライス）、`rhs.List.First()`は`append`関数の第二引数以降の最初の要素を指します。
    *   `samesafeexpr`は、これら二つの式が同じで安全な式であるかをチェックします。
    *   `!s.canSSA(n.Left)`は、スライスがSSA形式に変換できない（つまり、スタック上に割り当てられない）ことを確認します。
    *   この条件が真の場合、`s.append(rhs, true)`が呼び出され、インプレースアペンドが実行されていました。

*   `+ const doInPlaceAppend = false // issue 15246`
    *   この行が新しく追加されました。`doInPlaceAppend`という名前の定数を`false`で定義しています。
    *   コメント`// issue 15246`は、この定数がIssue #15246に関連するバグを回避するために導入されたことを示しています。

*   `+ if doInPlaceAppend && samesafeexpr(n.Left, rhs.List.First()) && !s.canSSA(n.Left) {`
    *   変更後の条件分岐です。元の条件の前に`doInPlaceAppend &&`が追加されています。
    *   `doInPlaceAppend`が`false`であるため、この`if`文の条件全体は常に`false`になります。
    *   結果として、この条件分岐内のコード（`s.append(rhs, true)`）は実行されなくなり、インプレースアペンドの特殊ケースが一時的に無効化されます。

この変更により、コンパイラは特定の条件下でのインプレースアペンド最適化を行わなくなり、関連するバグの発生を防ぎます。これは、バグの根本的な修正が行われるまでの間、コンパイラの安定性を確保するための安全策です。

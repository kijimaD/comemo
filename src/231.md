# [インデックス 231] ファイルの概要

このコミットは、Go言語のランタイムライブラリのビルドシステムを改善し、より構造化されたアプローチを導入することを目的としています。具体的には、ランタイムライブラリを個別のオブジェクトファイルではなく、単一のアーカイブファイル（`.a`）として構築するように変更し、そのビルドプロセスを`Makefile`によって管理するようにしました。これにより、リンカ（`6l`）がランタイムライブラリをより効率的に利用できるようになります。また、以前の変更で欠落していた`fakeobj.c`ファイルが追加されています。

## 変更の背景

このコミットが行われた2008年という時期は、Go言語がまだ開発の初期段階にあり、そのビルドシステムが進化している最中でした。以前のビルドプロセスでは、Goランタイムのコンパイル済みオブジェクトファイル（`.6`拡張子を持つファイル）が個別にリンカに渡されていました。`src/cmd/6l/obj.c`内のコメント「`BUG: these should be an archive or pulled via pragmas in rt0_*.6`」が示すように、この方法は非効率であり、管理が煩雑になるという問題がありました。

このコミットの主な背景は以下の通りです。

1.  **ビルドプロセスの合理化**: 個別のオブジェクトファイルを扱う代わりに、それらを単一のアーカイブファイル（ライブラリ）にまとめることで、ビルドコマンドを簡素化し、依存関係の管理を容易にすることが目的でした。
2.  **リンカの効率化**: リンカが多数の小さなオブジェクトファイルを個別に処理するよりも、単一のアーカイブファイルから必要なシンボルを抽出する方が効率的です。
3.  **標準的なビルドツールの導入**: `Makefile`を導入することで、Goランタイムのビルドプロセスを標準的なUnix/Linux環境でのソフトウェアビルドの慣習に合わせ、自動化と再現性を高めることが意図されました。
4.  **欠落ファイルの追加**: 以前のコミットで誤って含まれていなかった`fakeobj.c`ファイルを追加し、ビルドの完全性を確保する必要がありました。

これらの変更は、Go言語のビルドシステムをより堅牢で保守しやすいものにするための初期の重要なステップでした。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **Go言語の初期ビルドツール (`6l`, `6c`, `6a`)**:
    *   **`6l` (リンカ)**: Go言語のオブジェクトファイル（`.6`）やアーカイブファイル（`.a`）を結合して実行可能ファイルを生成するツールです。`6`はamd64アーキテクチャを指します（当時のGoツールチェインはPlan 9の命名規則に倣っていました）。
    *   **`6c` (コンパイラ)**: Go言語のソースコード（`.c`や`.go`）をamd64アーキテクチャ用のオブジェクトファイル（`.6`）にコンパイルするツールです。
    *   **`6a` (アセンブラ)**: Go言語のアセンブリコード（`.s`）をamd64アーキテクチャ用のオブジェクトファイル（`.6`）にアセンブルするツールです。
*   **`Makefile`**: `make`ユーティリティが使用する設定ファイルで、ソースコードのコンパイル、リンク、インストールなどのビルドプロセスを自動化するためのルールと依存関係を記述します。これにより、複雑なビルド手順を簡潔に定義し、変更があったファイルのみを再ビルドするなどの効率的な処理が可能になります。
*   **アーカイブファイル (`.a`ファイル)**: 複数のオブジェクトファイル（`.o`や`.6`）を一つにまとめた静的ライブラリファイルです。リンカは、このアーカイブファイルから、実行可能ファイルの生成に必要なオブジェクトコードのみを選択的に取り込むことができます。Unix/Linuxシステムでは、`ar`コマンド（アーカイブユーティリティ）によって作成・管理されます。
*   **Goランタイムライブラリ**: Goプログラムが実行されるために必要な低レベルの機能（ガベージコレクション、スケジューラ、メモリ管理、プリミティブなI/Oなど）を提供するライブラリです。Goプログラムは、コンパイル時にこのランタイムライブラリとリンクされます。
*   **`rt0`**: Goランタイムの初期化コードを含むオブジェクトファイルです。プログラムのエントリポイントであり、Goランタイムの起動処理（スタックの設定、スケジューラの初期化など）を行います。通常、他のランタイムコードとは別に扱われます。
*   **`GOROOT`, `GOARCH`, `GOOS`**:
    *   **`GOROOT`**: Goのインストールディレクトリのルートパスを示す環境変数です。
    *   **`GOARCH`**: ターゲットとするCPUアーキテクチャ（例: `amd64`、`arm`）を示す環境変数です。
    *   **`GOOS`**: ターゲットとするオペレーティングシステム（例: `linux`、`darwin`）を示す環境変数です。
    これらの変数は、クロスコンパイルや特定の環境向けのビルドパスを決定するために使用されます。
*   **`obj.c`**: リンカ（`6l`）のソースコードの一部で、オブジェクトファイルの読み込みや処理に関連するロジックが含まれています。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのビルドとリンクの方法を根本的に変更した点にあります。

1.  **`src/runtime/Makefile`の導入**:
    *   この新しい`Makefile`は、Goランタイムのビルドプロセスを定義します。
    *   `O=6`は、使用するツールチェインがamd64用であることを示します（`6c`, `6a`, `6ar`など）。
    *   `LIB=lib_$(GOARCH)_$(GOOS).a`という変数定義により、ランタイムライブラリが`lib_amd64_linux.a`のような命名規則のアーカイブファイルとして生成されることが明確になります。
    *   `RT0OFILES`には`rt0_$(GOARCH)_$(GOOS).$O`（例: `rt0_amd64_linux.6`）が含まれ、これは`rt0`が引き続き個別のオブジェクトファイルとして扱われることを示しています。
    *   `LIBOFILES`には`rt1_$(GOARCH)_$(GOOS).$O`と`rt2_$(GOARCH).$O`が含まれ、これらがアーカイブファイルにまとめられる対象となります。
    *   `$(LIB): $(LIBOFILES)`ターゲットでは、`$(O)ar rc $(LIB) $(LIBOFILES)`コマンドを使用して、`LIBOFILES`で指定されたオブジェクトファイルを`$(LIB)`というアーカイブファイルにまとめる処理が行われます。`rc`オプションは、アーカイブを作成（`r`）し、既存のアーカイブを置き換える（`c`）ことを意味します。
    *   `install`ターゲットは、生成された`rt0`オブジェクトファイルとランタイムアーカイブファイルを`$(GOROOT)/lib`ディレクトリにコピーします。
    *   `%.$(O): %.c`と`%.$(O): %.s`というパターンルールは、Cソースファイル（`.c`）を`6c`で、アセンブリソースファイル（`.s`）を`6a`でそれぞれ対応するオブジェクトファイル（`.6`）にコンパイル/アセンブルする方法を定義しています。

2.  **`src/cmd/6l/obj.c`の変更**:
    *   リンカの`main`関数内で、ランタイムライブラリをロードする部分が変更されました。
    *   以前は`rt1_*.6`、`rt2_*.6`といった個別のオブジェクトファイルを`objfile()`関数でロードしていましたが、この変更により、`sprintf(a, "%s/lib/lib_%s_%s.a", goroot, goarch, goos);`という形式で生成される単一のアーカイブファイル（例: `lib_amd64_linux.a`）をロードするように変更されました。
    *   これにより、リンカはランタイムの個々のコンポーネントを意識する必要がなくなり、より抽象化された形でライブラリを利用できるようになりました。

3.  **`src/libmach_amd64/fakeobj.c`の追加**:
    *   このファイルは、`mach_amd64.h`などのヘッダファイルに依存する、AMD64アーキテクチャ向けのオブジェクトファイル処理に関するスタブ関数やダミー関数を提供しているようです。コミットメッセージにある「missing from prior change」という記述から、以前の変更で必要とされたが、誤って含まれていなかったファイルであることが示唆されます。これらの関数は、特定のオブジェクトファイル形式の識別や読み込みに関連するプレースホルダーとして機能している可能性があります。

4.  **`src/runtime/clean.bash`と`src/runtime/make.bash`の更新**:
    *   これらのシェルスクリプトは、Goランタイムのクリーンアップとビルドを行うためのものです。
    *   以前は個別の`6a`や`6c`コマンドを直接呼び出していましたが、この変更により、新しく導入された`Makefile`の`make clean`と`make install`ターゲットを呼び出すように簡素化されました。これにより、ビルドスクリプトの可読性と保守性が向上し、ビルドロジックが一元化されました。

これらの変更は、Go言語のビルドシステムが、よりモジュール化され、標準的なライブラリ管理の手法を取り入れる方向へと進化したことを示しています。

### `src/runtime/Makefile`の新規追加

```makefile
# Copyright 2009 The Go Authors.  All rights reserved.
# Use of this source code is governed by a BSD-style
# license that can be found in the LICENSE file.

CFLAGS=
O=6
CC=$(O)c
AS=$(O)a

LIB=lib_$(GOARCH)_$(GOOS).a

RT0OFILES=\
	rt0_$(GOARCH)_$(GOOS).$O\

LIBOFILES=\
	rt1_$(GOARCH)_$(GOOS).$O\
	rt2_$(GOARCH).$O\

OFILES=$(RT0OFILES) $(LIBOFILES)
HFILES=

install: rt0 $(LIB)
	cp $(RT0OFILES) $(GOROOT)/lib
	cp $(LIB) $(GOROOT)/lib

rt0:	$(RT0OFILES)

$(LIB): $(LIBOFILES)
	$(O)ar rc $(LIB) $(LIBOFILES)

$(OFILES): $(HFILES)

clean:
	rm -f *.$(O) *.a

%.$O:	%.c
	$(CC) $<

%.$O:	%.s
	$(AS) $<
```

この`Makefile`は、Goランタイムのビルド手順を明確に定義しています。
*   `LIB`変数は、生成されるアーカイブファイルの名前を定義します。`$(GOARCH)`と`$(GOOS)`を使用することで、ターゲットアーキテクチャとOSに応じたファイル名が動的に生成されます。
*   `RT0OFILES`は`rt0`のオブジェクトファイルを指定し、これはアーカイブには含まれず、個別に扱われます。これは、`rt0`がプログラムのエントリポイントであり、特別なリンキング要件を持つためと考えられます。
*   `LIBOFILES`は、`rt1`と`rt2`のオブジェクトファイルを指定しており、これらがアーカイブにまとめられる対象となります。
*   `$(LIB): $(LIBOFILES)`というルールは、`LIBOFILES`で指定されたすべてのオブジェクトファイルが変更された場合に、`$(O)ar rc $(LIB) $(LIBOFILES)`コマンドを実行して`$(LIB)`アーカイブを再作成することを意味します。`$(O)ar`は、`6ar`（amd64アーキテクチャ用の`ar`コマンド）を指します。
*   `install`ターゲットは、ビルドされた`rt0`オブジェクトファイルと`lib_*.a`アーカイブファイルを`$(GOROOT)/lib`ディレクトリにコピーし、Goツールチェインがこれらを見つけられるようにします。
*   `%.$O: %.c`と`%.$O: %.s`は、Cソースファイルとアセンブリソースファイルをそれぞれ`6c`と`6a`でコンパイル/アセンブルするための汎用的なルールです。

この`Makefile`の導入により、Goランタイムのビルドプロセスは、手動でのコマンド実行から、標準的な`make`ユーティリティによる自動化された、より堅牢なシステムへと移行しました。

    *   **`6c` (コンパイラ)**: Go言語のソースコード（`.c`や`.go`）をamd64アーキテクチャ用のオブジェクトファイル（`.6`）にコンパイルするツールです。
    *   **`6a` (アセンブラ)**: Go言語のアセンブリコード（`.s`）をamd64アーキテクチャ用のオブジェクトファイル（`.6`）にアセンブルするツールです。
*   **`Makefile`**: `make`ユーティリティが使用する設定ファイルで、ソースコードのコンパイル、リンク、インストールなどのビルドプロセスを自動化するためのルールと依存関係を記述します。これにより、複雑なビルド手順を簡潔に定義し、変更があったファイルのみを再ビルドするなどの効率的な処理が可能になります。
*   **アーカイブファイル (`.a`ファイル)**: 複数のオブジェクトファイル（`.o`や`.6`）を一つにまとめた静的ライブラリファイルです。リンカは、このアーカイブファイルから、実行可能ファイルの生成に必要なオブジェクトコードのみを選択的に取り込むことができます。Unix/Linuxシステムでは、`ar`コマンド（アーカイブユーティリティ）によって作成・管理されます。
*   **Goランタイムライブラリ**: Goプログラムが実行されるために必要な低レベルの機能（ガベージコレクション、スケジューラ、メモリ管理、プリミティブなI/Oなど）を提供するライブラリです。Goプログラムは、コンパイル時にこのランタイムライブラリとリンクされます。
*   **`rt0`**: Goランタイムの初期化コードを含むオブジェクトファイルです。プログラムのエントリポイントであり、Goランタイムの起動処理（スタックの設定、スケジューラの初期化など）を行います。通常、他のランタイムコードとは別に扱われます。
*   **`GOROOT`, `GOARCH`, `GOOS`**:
    *   **`GOROOT`**: Goのインストールディレクトリのルートパスを示す環境変数です。
    *   **`GOARCH`**: ターゲットとするCPUアーキテクチャ（例: `amd64`、`arm`）を示す環境変数です。
    *   **`GOOS`**: ターゲットとするオペレーティングシステム（例: `linux`、`darwin`）を示す環境変数です。
    これらの変数は、クロスコンパイルや特定の環境向けのビルドパスを決定するために使用されます。
*   **`obj.c`**: リンカ（`6l`）のソースコードの一部で、オブジェクトファイルの読み込みや処理に関連するロジックが含まれています。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのビルドとリンクの方法を根本的に変更した点にあります。

1.  **`src/runtime/Makefile`の導入**:
    *   この新しい`Makefile`は、Goランタイムのビルドプロセスを定義します。
    *   `O=6`は、使用するツールチェインがamd64用であることを示します（`6c`, `6a`, `6ar`など）。
    *   `LIB=lib_$(GOARCH)_$(GOOS).a`という変数定義により、ランタイムライブラリが`lib_amd64_linux.a`のような命名規則のアーカイブファイルとして生成されることが明確になります。
    *   `RT0OFILES`には`rt0_$(GOARCH)_$(GOOS).$O`（例: `rt0_amd64_linux.6`）が含まれ、これは`rt0`が引き続き個別のオブジェクトファイルとして扱われることを示しています。
    *   `LIBOFILES`には`rt1_$(GOARCH)_$(GOOS).$O`と`rt2_$(GOARCH).$O`が含まれ、これらがアーカイブファイルにまとめられる対象となります。
    *   `$(LIB): $(LIBOFILES)`ターゲットでは、`$(O)ar rc $(LIB) $(LIBOFILES)`コマンドを使用して、`LIBOFILES`で指定されたオブジェクトファイルを`$(LIB)`というアーカイブファイルにまとめる処理が行われます。`rc`オプションは、アーカイブを作成（`r`）し、既存のアーカイブを置き換える（`c`）ことを意味します。
    *   `install`ターゲットは、生成された`rt0`オブジェクトファイルとランタイムアーカイブファイルを`$(GOROOT)/lib`ディレクトリにコピーします。
    *   `%.$(O): %.c`と`%.$(O): %.s`というパターンルールは、Cソースファイル（`.c`）を`6c`で、アセンブリソースファイル（`.s`）を`6a`でそれぞれ対応するオブジェクトファイル（`.6`）にコンパイル/アセンブルする方法を定義しています。

2.  **`src/cmd/6l/obj.c`の変更**:
    *   リンカの`main`関数内で、ランタイムライブラリをロードする部分が変更されました。
    *   以前は`rt1_*.6`、`rt2_*.6`といった個別のオブジェクトファイルを`objfile()`関数でロードしていましたが、この変更により、`sprintf(a, "%s/lib/lib_%s_%s.a", goroot, goarch, goos);`という形式で生成される単一のアーカイブファイル（例: `lib_amd64_linux.a`）をロードするように変更されました。
    *   これにより、リンカはランタイムの個々のコンポーネントを意識する必要がなくなり、より抽象化された形でライブラリを利用できるようになりました。

3.  **`src/libmach_amd64/fakeobj.c`の追加**:
    *   このファイルは、`mach_amd64.h`などのヘッダファイルに依存する、AMD64アーキテクチャ向けのオブジェクトファイル処理に関するスタブ関数やダミー関数を提供しているようです。コミットメッセージにある「missing from prior change」という記述から、以前の変更で必要とされたが、誤って含まれていなかったファイルであることが示唆されます。これらの関数は、特定のオブジェクトファイル形式の識別や読み込みに関連するプレースホルダーとして機能している可能性があります。

4.  **`src/runtime/clean.bash`と`src/runtime/make.bash`の更新**:
    *   これらのシェルスクリプトは、Goランタイムのクリーンアップとビルドを行うためのものです。
    *   以前は個別の`6a`や`6c`コマンドを直接呼び出していましたが、この変更により、新しく導入された`Makefile`の`make clean`と`make install`ターゲットを呼び出すように簡素化されました。これにより、ビルドスクリプトの可読性と保守性が向上し、ビルドロジックが一元化されました。

これらの変更は、Go言語のビルドシステムが、よりモジュール化され、標準的なライブラリ管理の手法を取り入れる方向へと進化したことを示しています。

### `src/runtime/Makefile`の新規追加

```makefile
# Copyright 2009 The Go Authors.  All rights reserved.
# Use of this source code is governed by a BSD-style
# license that can be found in the LICENSE file.

CFLAGS=
O=6
CC=$(O)c
AS=$(O)a

LIB=lib_$(GOARCH)_$(GOOS).a

RT0OFILES=\
	rt0_$(GOARCH)_$(GOOS).$O\

LIBOFILES=\
	rt1_$(GOARCH)_$(GOOS).$O\
	rt2_$(GOARCH).$O\

OFILES=$(RT0OFILES) $(LIBOFILES)
HFILES=

install: rt0 $(LIB)
	cp $(RT0OFILES) $(GOROOT)/lib
	cp $(LIB) $(GOROOT)/lib

rt0:	$(RT0OFILES)

$(LIB): $(LIBOFILES)
	$(O)ar rc $(LIB) $(LIBOFILES)

$(OFILES): $(HFILES)

clean:
	rm -f *.$(O) *.a

%.$O:	%.c
	$(CC) $<

%.$O:	%.s
	$(AS) $<
```

この`Makefile`は、Goランタイムのビルド手順を明確に定義しています。
*   `LIB`変数は、生成されるアーカイブファイルの名前を定義します。`$(GOARCH)`と`$(GOOS)`を使用することで、ターゲットアーキテクチャとOSに応じたファイル名が動的に生成されます。
*   `RT0OFILES`は`rt0`のオブジェクトファイルを指定し、これはアーカイブには含まれず、個別に扱われます。これは、`rt0`がプログラムのエントリポイントであり、特別なリンキング要件を持つためと考えられます。
*   `LIBOFILES`は、`rt1`と`rt2`のオブジェクトファイルを指定しており、これらがアーカイブにまとめられる対象となります。
*   `$(LIB): $(LIBOFILES)`というルールは、`LIBOFILES`で指定されたすべてのオブジェクトファイルが変更された場合に、`$(O)ar rc $(LIB) $(LIBOFILES)`コマンドを実行して`$(LIB)`アーカイブを再作成することを意味します。`$(O)ar`は、`6ar`（amd64アーキテクチャ用の`ar`コマンド）を指します。
*   `install`ターゲットは、ビルドされた`rt0`オブジェクトファイルと`lib_*.a`アーカイブファイルを`$(GOROOT)/lib`ディレクトリにコピーし、Goツールチェインがこれらを見つけられるようにします。
*   `%.$O: %.c`と`%.$O: %.s`は、Cソースファイルとアセンブリソースファイルをそれぞれ`6c`と`6a`でコンパイル/アセンブルするための汎用的なルールです。

この`Makefile`の導入により、Goランタイムのビルドプロセスは、手動でのコマンド実行から、標準的な`make`ユーティリティによる自動化された、より堅牢なシステムへと移行しました。

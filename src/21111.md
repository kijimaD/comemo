# [インデックス 21111] ファイルの概要

このコミットは、Goコンパイラおよびリンカの内部構造である `Prog` (プログラム命令) と `Addr` (アドレス) の詳細なデバッグ情報出力機能を追加するものです。既存の「きれいな」出力ではこれらの構造体のフィールド内容を理解するのが困難であったため、各フィールドの正確な内容を表示する「醜い」フォーマッタ（詳細なデバッグ用フォーマッタ）が導入されました。これにより、Goの内部コードの理解とデバッグが容易になります。

## 変更の背景

Goコンパイラとリンカは、プログラムのコンパイルとリンクの過程で `Prog` と `Addr` といった内部データ構造を多用します。これらはそれぞれ、アセンブリ命令とメモリアドレスやオペランドを表現するためのものです。従来、これらの構造体を文字列として出力する「きれいな」フォーマッタは存在していましたが、それは人間が読みやすいように抽象化された情報を提供していました。

しかし、コンパイラやリンカのデバッグ、あるいはGoの内部動作を深く理解しようとする開発者にとっては、この抽象化が障壁となることがありました。特に、構造体の各フィールドにどのような値が格納されているのか、その生の情報を正確に把握する必要がある場合、既存のフォーマッタでは不十分でした。

このコミットは、このような背景から、`Prog` と `Addr` 構造体の各フィールドの値をそのまま、詳細かつ網羅的に表示する新しいフォーマッタ（コミットメッセージでは「ugly printers」と表現）を導入することで、デバッグと内部解析の効率を向上させることを目的としています。

## 前提知識の解説

### Goコンパイラとリンカの命名規則

Goの初期のコンパイラとリンカは、ターゲットアーキテクチャに基づいて命名されていました。
- `5g`, `5l`: ARM (32-bit) 用のコンパイラとリンカ
- `6g`, `6l`: AMD64 (64-bit x86) 用のコンパイラとリンカ
- `8g`, `8l`: 386 (32-bit x86) 用のコンパイラとリンカ
- `9g`, `9l`: ARM64 (64-bit ARM) 用のコンパイラとリンカ

このコミットでは主に `6g` (amd64) と `9g` (arm64) のリンカ (`liblink/list6.c`, `liblink/list9.c`) に変更が加えられています。

### `Prog` 構造体

`Prog` 構造体は、Goのリンカが扱う個々のアセンブリ命令を表現します。主要なフィールドには以下のようなものがあります。
- `pc`: プログラムカウンタ（命令のアドレス）
- `lineno`: ソースコードの行番号
- `as`: 命令の種類（例: `ADATA`, `ATEXT`, `AMOV` など）
- `from`: 命令のソースオペランド（`Addr` 構造体）
- `to`: 命令のデスティネーションオペランド（`Addr` 構造体）
- `reg`: レジスタ番号（特定の命令で使用）
- `from3`: 3オペランド命令の3番目のソースオペランド（`Addr` 構造体、一部アーキテクチャで使用）

### `Addr` 構造体

`Addr` 構造体は、`Prog` 構造体内で使用されるオペランド（アドレス、定数、レジスタなど）を表現します。主要なフィールドには以下のようなものがあります。
- `type`: アドレスの種類（例: `D_NONE`, `D_REG`, `D_MEM`, `D_CONST`, `D_BRANCH` など）
- `offset`: オフセット値（メモリ参照や定数で使用）
- `sym`: シンボルへのポインタ（グローバル変数や関数名など）
- `reg`: レジスタ番号
- `etype`: 要素の型（データ型など）
- `width`: 幅（バイト数など）
- `class`: アドレスのクラス（スタック変数、グローバル変数など）
- `u.branch`: 分岐命令の場合のターゲット `Prog` へのポインタ

### `fmt` パッケージと `FmtSharp` フラグ

Go言語の標準ライブラリ `fmt` パッケージは、様々な型の値を文字列にフォーマットするための機能を提供します。`fmt.Printf` などの関数で使用されるフォーマット動詞には、追加のフラグを指定できます。
- `%v`: 値のデフォルト表現
- `%#v`: 値のGo構文表現（構造体の場合、フィールド名と値が明示的に表示される）

このコミットで導入された「醜い」フォーマッタは、`fmt` パッケージの内部で使われる `FmtSharp` フラグ（`%#v` に対応）を利用しています。`FmtSharp` フラグが設定されている場合、`Pconv` や `Dconv` といった変換関数は、より詳細なデバッグ情報を出力するように動作します。

### `liblink`

`liblink` はGoリンカの共通ライブラリであり、アーキテクチャに依存しないリンカのコア機能を提供します。`src/liblink/list6.c` と `src/liblink/list9.c` は、それぞれAMD64とARM64アーキテクチャ向けのリンカのリスト出力（デバッグ情報やアセンブリリストの生成）に関連するC言語のソースファイルです。

### `D_NONE`, `D_INDIR`, `D_LAST`

これらは `Addr` 構造体の `type` フィールドで使用される定数で、アドレスの種類を示します。
- `D_NONE`: アドレスが指定されていない状態。
- `D_INDIR`: 間接参照を示すフラグ。例えば `D_INDIR + D_REG` はレジスタによる間接参照を意味します。
- `D_LAST`: このコミットで追加された定数で、`Addr` の `type` の列挙型における最後の有効な値の次を示します。これは、`dnames` 配列（アドレスタイプ名を文字列に変換するための配列）のサイズを決定するために使用されます。

## 技術的詳細

このコミットの主要な変更は、Goリンカのリスト出力部分、具体的には `src/liblink/list6.c` と `src/liblink/list9.c` にある `Pconv` 関数（`Prog` 構造体のフォーマット）と `Dconv` 関数（`Addr` 構造体のフォーマット）に、`FmtSharp` フラグをチェックするロジックを追加したことです。

### `Pconv` および `Dconv` 関数の変更

これらの関数は、`Fmt` 構造体（フォーマットの状態を保持する）へのポインタ `fp` を引数として受け取ります。`fp->flags` に `FmtSharp` フラグが設定されているかどうかをチェックし、設定されている場合は、通常の「きれいな」出力ではなく、各フィールドの値を明示的に表示する詳細なデバッグ出力を生成します。

例えば、`Pconv` 関数では、`Prog` 構造体の `pc`, `lineno`, `as`, `from`, `reg`, `to`, `from3` (9lの場合) といったフィールドが個別に `sprint` 関数（文字列へのフォーマット出力）を使って文字列に変換され、連結されます。`from` や `to` のような `Addr` 型のフィールドは、再帰的に `Dconv` 関数を呼び出し、その際にも `FmtSharp` フラグを渡すことで、`Addr` 構造体の詳細も表示されるようになっています（`{%#D}` フォーマット動詞を使用）。

`Dconv` 関数では、`Addr` 構造体の `type`, `offset`, `etype`, `width`, `class`, `reg`, `sym`, `u.branch` といったフィールドが詳細に表示されます。特に `type` フィールドは、`dnames` 配列（`dnames6` や `dnames9`）を使って対応する文字列名に変換されます。`D_INDIR` のようなフラグも個別に検出して表示されます。

### `D_LAST` の追加と `buildgc.c` の変更

`D_LAST` 定数は、`src/cmd/5l/5.out.h`, `src/cmd/6l/6.out.h`, `src/cmd/8l/8.out.h`, `src/cmd/9l/9.out.h` といった各アーキテクチャのリンカのヘッダファイルに追加されました。これは、`Addr` の `type` フィールドが取りうる値の範囲を正確に定義するために使用されます。

`src/cmd/dist/buildgc.c` は、Goのビルドシステムの一部であり、コンパイラやリンカが使用する様々な定数やデータ構造を生成する役割を担っています。このコミットでは、`buildgc.c` が `dnames` 配列（アドレスタイプ名を文字列にマッピングする配列）を生成する際に、`D_LAST` を配列のサイズとして使用するように変更されました。これにより、`dnames` 配列が `Addr` のすべての `type` 値を適切にカバーできるようになり、新しい詳細フォーマッタが正しく機能することが保証されます。具体的には、`dnames%c[]` の宣言が `dnames%c[D_LAST]` に変更されています。また、`D_LAST` 自体は `dnames` に含める必要がないため、`mkanames` 関数で `xstrcmp(p, "LAST") == 0` のチェックが追加され、`D_LAST` が `dnames` 配列に誤って追加されないようにしています。

- `if(fp->flags & FmtSharp)`: ここが新しいデバッグ出力の分岐点です。`FmtSharp` フラグが設定されている場合（Goの `%#v` フォーマット動詞に対応）、以下の詳細出力ロジックが実行されます。

- `s += sprint(s, "%.5lld (%L) %A", p->pc, p->lineno, p->as);`: `Prog` の基本的な情報であるプログラムカウンタ (`p->pc`)、行番号 (`p->lineno`)、命令の種類 (`p->as`) を出力します。`%A` は命令の種類を文字列に変換する別のフォーマット動詞です。
- `if(p->from.type != D_NONE) s += sprint(s, " from={%#D}", &p->from);`: `from` オペランドが存在する場合、`from={...}` の形式で出力します。ここで注目すべきは `{%#D}` です。これは `Addr` 構造体を詳細にフォーマットするために `Dconv` 関数を呼び出し、その際にも `FmtSharp` フラグを渡すことを意味します。これにより、`Addr` 構造体の内部も再帰的に詳細表示されます。
- `if(p->reg) s += sprint(s, " reg=%d", p->reg);`: レジスタ情報が存在する場合、`reg=...` の形式で出力します。
- `if(p->to.type != D_NONE) s += sprint(s, " to={%#D}", &p->to);`: `to` オペランドが存在する場合、`to={...}` の形式で出力します。ここでも `{%#D}` が使用され、`Addr` の詳細表示が行われます。
- `return fmtstrcpy(fp, str);`: 構築された文字列をフォーマットコンテキストにコピーして返します。この `if` ブロックが実行された場合、その後の `switch` 文による既存の「きれいな」出力ロジックはスキップされます。

- `if(fp->flags & FmtSharp)`: ここも `FmtSharp` フラグが設定されている場合の分岐です。
- `s += sprint(s, "type=");`: まず `type=` というプレフィックスを出力します。
- `if(i == D_NONE) { sprint(s, "NONE"); goto brk; }`: `Addr` のタイプが `D_NONE` の場合、`NONE` と出力して処理を終了します。
- `if(i >= D_INDIR) { i -= D_INDIR; s += sprint(s, "INDIR+"); }`: `D_INDIR` フラグが設定されている場合、`INDIR+` と出力し、`i` から `D_INDIR` を引いて実際のタイプ値を取得します。これにより、間接参照の有無が明示されます。
- `if(i >= 0 && i < D_LAST && dnames6[i] != nil) s += sprint(s, "%s ", dnames6[i]); else s += sprint(s, "%d ", i);`: `i` の値が `D_LAST` の範囲内であり、かつ `dnames6` 配列に対応する文字列が存在する場合、その文字列（例: `D_REG` なら "REG"）を出力します。そうでない場合は、数値のまま出力します。`D_LAST` がここで配列の境界チェックに使われている点が重要です。
- `s += sprint(s, "offset=%ld etype=%E width=%d", a->offset, a->etype, a->width);`: `offset`, `etype`, `width` といったフィールドの値を直接出力します。
- `if(a->class != 0) s += sprint(s, " class=%s", cnames9[a->class]);`: `class` フィールドが存在する場合、`cnames9` 配列（クラス名を文字列に変換）を使って出力します。
- `if(a->sym != nil) s += sprint(s, " sym=%s", a->sym->name);`: シンボルが存在する場合、その名前を出力します。
- `if(a->type == D_BRANCH && a->u.branch != nil) s += sprint(s, " branch=%.5lld", a->u.branch->pc);`: `D_BRANCH` タイプの場合、分岐先のプログラムカウンタを出力します。
- `goto brk;`: 構築された文字列を返します。

これらの変更により、Goのコンパイラやリンカの内部で `Prog` や `Addr` 構造体がどのように表現されているかを、より詳細かつ正確に把握できるようになりました。これは、Goのランタイムやコンパイラの開発者にとって、デバッグや最適化の作業において非常に有用な機能となります。

## 変更の背景

Goコンパイラとリンカは、プログラムのコンパイルとリンクの過程で `Prog` と `Addr` といった内部データ構造を多用します。これらはそれぞれ、アセンブリ命令とメモリアドレスやオペランドを表現するためのものです。従来、これらの構造体を文字列として出力する「きれいな」フォーマッタは存在していましたが、それは人間が読みやすいように抽象化された情報を提供していました。

しかし、コンパイラやリンカのデバッグ、あるいはGoの内部動作を深く理解しようとする開発者にとっては、この抽象化が障壁となることがありました。特に、構造体の各フィールドにどのような値が格納されているのか、その生の情報を正確に把握する必要がある場合、既存のフォーマッタでは不十分でした。

このコミットは、このような背景から、`Prog` と `Addr` 構造体の各フィールドの値をそのまま、詳細かつ網羅的に表示する新しいフォーマッタ（コミットメッセージでは「ugly printers」と表現）を導入することで、デバッグと内部解析の効率を向上させることを目的としています。

## 前提知識の解説

### Goコンパイラとリンカの命名規則

Goの初期のコンパイラとリンカは、ターゲットアーキテクチャに基づいて命名されていました。
- `5g`, `5l`: ARM (32-bit) 用のコンパイラとリンカ
- `6g`, `6l`: AMD64 (64-bit x86) 用のコンパイラとリンカ
- `8g`, `8l`: 386 (32-bit x86) 用のコンパイラとリンカ
- `9g`, `9l`: ARM64 (64-bit ARM) 用のコンパイラとリンカ

このコミットでは主に `6g` (amd64) と `9g` (arm64) のリンカ (`liblink/list6.c`, `liblink/list9.c`) に変更が加えられています。

### `Prog` 構造体

`Prog` 構造体は、Goのリンカが扱う個々のアセンブリ命令を表現します。主要なフィールドには以下のようなものがあります。
- `pc`: プログラムカウンタ（命令のアドレス）
- `lineno`: ソースコードの行番号
- `as`: 命令の種類（例: `ADATA`, `ATEXT`, `AMOV` など）
- `from`: 命令のソースオペランド（`Addr` 構造体）
- `to`: 命令のデスティネーションオペランド（`Addr` 構造体）
- `reg`: レジスタ番号（特定の命令で使用）
- `from3`: 3オペランド命令の3番目のソースオペランド（`Addr` 構造体、一部アーキテクチャで使用）

### `Addr` 構造体

`Addr` 構造体は、`Prog` 構造体内で使用されるオペランド（アドレス、定数、レジスタなど）を表現します。主要なフィールドには以下のようなものがあります。
- `type`: アドレスの種類（例: `D_NONE`, `D_REG`, `D_MEM`, `D_CONST`, `D_BRANCH` など）
- `offset`: オフセット値（メモリ参照や定数で使用）
- `sym`: シンボルへのポインタ（グローバル変数や関数名など）
- `reg`: レジスタ番号
- `etype`: 要素の型（データ型など）
- `width`: 幅（バイト数など）
- `class`: アドレスのクラス（スタック変数、グローバル変数など）
- `u.branch`: 分岐命令の場合のターゲット `Prog` へのポインタ

### `fmt` パッケージと `FmtSharp` フラグ

Go言語の標準ライブラリ `fmt` パッケージは、様々な型の値を文字列にフォーマットするための機能を提供します。`fmt.Printf` などの関数で使用されるフォーマット動詞には、追加のフラグを指定できます。
- `%v`: 値のデフォルト表現
- `%#v`: 値のGo構文表現（構造体の場合、フィールド名と値が明示的に表示される）

このコミットで導入された「醜い」フォーマッタは、`fmt` パッケージの内部で使われる `FmtSharp` フラグ（`%#v` に対応）を利用しています。`FmtSharp` フラグが設定されている場合、`Pconv` や `Dconv` といった変換関数は、より詳細なデバッグ情報を出力するように動作します。

### `liblink`

`liblink` はGoリンカの共通ライブラリであり、アーキテクチャに依存しないリンカのコア機能を提供します。`src/liblink/list6.c` と `src/liblink/list9.c` は、それぞれAMD64とARM64アーキテクチャ向けのリンカのリスト出力（デバッグ情報やアセンブリリストの生成）に関連するC言語のソースファイルです。

### `D_NONE`, `D_INDIR`, `D_LAST`

これらは `Addr` 構造体の `type` フィールドで使用される定数で、アドレスの種類を示します。
- `D_NONE`: アドレスが指定されていない状態。
- `D_INDIR`: 間接参照を示すフラグ。例えば `D_INDIR + D_REG` はレジスタによる間接参照を意味します。
- `D_LAST`: このコミットで追加された定数で、`Addr` の `type` の列挙型における最後の有効な値の次を示します。これは、`dnames` 配列（アドレスタイプ名を文字列に変換するための配列）のサイズを決定するために使用されます。

## 技術的詳細

このコミットの主要な変更は、Goリンカのリスト出力部分、具体的には `src/liblink/list6.c` と `src/liblink/list9.c` にある `Pconv` 関数（`Prog` 構造体のフォーマット）と `Dconv` 関数（`Addr` 構造体のフォーマット）に、`FmtSharp` フラグをチェックするロジックを追加したことです。

### `Pconv` および `Dconv` 関数の変更

これらの関数は、`Fmt` 構造体（フォーマットの状態を保持する）へのポインタ `fp` を引数として受け取ります。`fp->flags` に `FmtSharp` フラグが設定されているかどうかをチェックし、設定されている場合は、通常の「きれいな」出力ではなく、各フィールドの値を明示的に表示する詳細なデバッグ出力を生成します。

例えば、`Pconv` 関数では、`Prog` 構造体の `pc`, `lineno`, `as`, `from`, `reg`, `to`, `from3` (9lの場合) といったフィールドが個別に `sprint` 関数（文字列へのフォーマット出力）を使って文字列に変換され、連結されます。`from` や `to` のような `Addr` 型のフィールドは、再帰的に `Dconv` 関数を呼び出し、その際にも `FmtSharp` フラグを渡すことで、`Addr` 構造体の詳細も表示されるようになっています（`{%#D}` フォーマット動詞を使用）。

`Dconv` 関数では、`Addr` 構造体の `type`, `offset`, `etype`, `width`, `class`, `reg`, `sym`, `u.branch` といったフィールドが詳細に表示されます。特に `type` フィールドは、`dnames` 配列（`dnames6` や `dnames9`）を使って対応する文字列名に変換されます。`D_INDIR` のようなフラグも個別に検出して表示されます。

### `D_LAST` の追加と `buildgc.c` の変更

`D_LAST` 定数は、`src/cmd/5l/5.out.h`, `src/cmd/6l/6.out.h`, `src/cmd/8l/8.out.h`, `src/cmd/9l/9.out.h` といった各アーキテクチャのリンカのヘッダファイルに追加されました。これは、`Addr` の `type` フィールドが取りうる値の範囲を正確に定義するために使用されます。

`src/cmd/dist/buildgc.c` は、Goのビルドシステムの一部であり、コンパイラやリンカが使用する様々な定数やデータ構造を生成する役割を担っています。このコミットでは、`buildgc.c` が `dnames` 配列（アドレスタイプ名を文字列にマッピングする配列）を生成する際に、`D_LAST` を配列のサイズとして使用するように変更されました。これにより、`dnames` 配列が `Addr` のすべての `type` 値を適切にカバーできるようになり、新しい詳細フォーマッタが正しく機能することが保証されます。具体的には、`dnames%c[]` の宣言が `dnames%c[D_LAST]` に変更されています。また、`D_LAST` 自体は `dnames` に含める必要がないため、`mkanames` 関数で `xstrcmp(p, "LAST") == 0` のチェックが追加され、`D_LAST` が `dnames` 配列に誤って追加されないようにしています。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

1.  **`src/cmd/5l/5.out.h`**, **`src/cmd/6l/6.out.h`**, **`src/cmd/8l/8.out.h`**, **`src/cmd/9l/9.out.h`**:
    - `enum` 定数に `D_LAST` が追加されました。これは `Addr` の `type` フィールドの列挙型の範囲を定義します。

2.  **`src/cmd/dist/buildgc.c`**:
    - `mkanames` 関数内で、`dnames` 配列の宣言が `char* dnames%c[]` から `char* dnames%c[D_LAST]` に変更され、配列のサイズが `D_LAST` に基づくようになりました。
    - `D_LAST` が `dnames` 配列に誤って追加されないように、`if(xstrcmp(p, "LAST") == 0) continue;` のチェックが追加されました。

3.  **`src/liblink/list6.c`** (AMD64リンカのリスト出力):
    - `Pconv` 関数に `if(fp->flags & FmtSharp)` ブロックが追加され、`Prog` の詳細なデバッグ出力が実装されました。
    - `Dconv` 関数に `if(fp->flags & FmtSharp)` ブロックが追加され、`Addr` の詳細なデバッグ出力が実装されました。

4.  **`src/liblink/list9.c`** (ARM64リンカのリスト出力):
    - `Pconv` 関数に `if(fp->flags & FmtSharp)` ブロックが追加され、`Prog` の詳細なデバッグ出力が実装されました。
    - `Dconv` 関数に `if(fp->flags & FmtSharp)` ブロックが追加され、`Addr` の詳細なデバッグ出力が実装されました。

## コアとなるコードの解説

### `Pconv` 関数 (`Prog` 構造体のフォーマット)

```

- `if(fp->flags & FmtSharp)`: ここが新しいデバッグ出力の分岐点です。`FmtSharp` フラグが設定されている場合（Goの `%#v` フォーマット動詞に対応）、以下の詳細出力ロジックが実行されます。
- `char *s = str;`: 出力文字列を構築するためのポインタ `s` を初期化します。`str` は出力バッファです。
- `s += sprint(s, "%.5lld (%L) %A", p->pc, p->lineno, p->as);`: `Prog` の基本的な情報であるプログラムカウンタ (`p->pc`)、行番号 (`p->lineno`)、命令の種類 (`p->as`) を出力します。`%A` は命令の種類を文字列に変換する別のフォーマット動詞です。
- `if(p->from.type != D_NONE) s += sprint(s, " from={%#D}", &p->from);`: `from` オペランドが存在する場合、`from={...}` の形式で出力します。ここで注目すべきは `{%#D}` です。これは `Addr` 構造体を詳細にフォーマットするために `Dconv` 関数を呼び出し、その際にも `FmtSharp` フラグを渡すことを意味します。これにより、`Addr` 構造体の内部も再帰的に詳細表示されます。
- `if(p->reg) s += sprint(s, " reg=%d", p->reg);`: レジスタ情報が存在する場合、`reg=...` の形式で出力します。
- `if(p->to.type != D_NONE) s += sprint(s, " to={%#D}", &p->to);`: `to` オペランドが存在する場合、`to={...}` の形式で出力します。ここでも `{%#D}` が使用され、`Addr` の詳細表示が行われます。
- `return fmtstrcpy(fp, str);`: 構築された文字列をフォーマットコンテキストにコピーして返します。この `if` ブロックが実行された場合、その後の `switch` 文による既存の「きれいな」出力ロジックはスキップされます。

### `Dconv` 関数 (`Addr` 構造体のフォーマット)

- `if(fp->flags & FmtSharp)`: ここも `FmtSharp` フラグが設定されている場合の分岐です。
- `s += sprint(s, "type=");`: まず `type=` というプレフィックスを出力します。
- `if(i == D_NONE) { sprint(s, "NONE"); goto brk; }`: `Addr` のタイプが `D_NONE` の場合、`NONE` と出力して処理を終了します。
- `if(i >= D_INDIR) { i -= D_INDIR; s += sprint(s, "INDIR+"); }`: `D_INDIR` フラグが設定されている場合、`INDIR+` と出力し、`i` から `D_INDIR` を引いて実際のタイプ値を取得します。これにより、間接参照の有無が明示されます。
- `if(i >= 0 && i < D_LAST && dnames6[i] != nil) s += sprint(s, "%s ", dnames6[i]); else s += sprint(s, "%d ", i);`: `i` の値が `D_LAST` の範囲内であり、かつ `dnames6` 配列に対応する文字列が存在する場合、その文字列（例: `D_REG` なら "REG"）を出力します。そうでない場合は、数値のまま出力します。`D_LAST` がここで配列の境界チェックに使われている点が重要です。
- `s += sprint(s, "offset=%ld etype=%E width=%d", a->offset, a->etype, a->width);`: `offset`, `etype`, `width` といったフィールドの値を直接出力します。
- `if(a->class != 0) s += sprint(s, " class=%s", cnames9[a->class]);`: `class` フィールドが存在する場合、`cnames9` 配列（クラス名を文字列に変換）を使って出力します。
- `if(a->sym != nil) s += sprint(s, " sym=%s", a->sym->name);`: シンボルが存在する場合、その名前を出力します。
- `if(a->type == D_BRANCH && a->u.branch != nil) s += sprint(s, " branch=%.5lld", a->u.branch->pc);`: `D_BRANCH` タイプの場合、分岐先のプログラムカウンタを出力します。
- `goto brk;`: 構築された文字列を返します。

これらの変更により、Goのコンパイラやリンカの内部で `Prog` や `Addr` 構造体がどのように表現されているかを、より詳細かつ正確に把握できるようになりました。これは、Goのランタイムやコンパイラの開発者にとって、デバッグや最適化の作業において非常に有用な機能となります。

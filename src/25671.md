## 変更の背景

2015年頃、Goコンパイラ（`cmd/compile`）は、それまでのYacc/Bisonベースのパーサーから、Go言語で手書きされた再帰下降型パーサーへの移行を進めていました。この移行は、Go 1.5（2015年8月リリース）でコンパイラ自体がGoで書かれた最初のバージョンとなった時期と重なります。新しいパーサーの導入に伴い、ユーザーが遭遇する構文エラーの報告方法と、エラー発生時のパーサーの挙動を改善する必要がありました。

このコミットは、特に以下の課題に対処するために行われました。

1.  **エラーメッセージの質の向上:** 曖昧なエラーメッセージは開発者のデバッグ作業を困難にします。より具体的で分かりやすいメッセージを提供することが求められました。
2.  **エラー回復の改善:** 構文エラーが発生した際に、パーサーがすぐに処理を中断するのではなく、エラー箇所をスキップして可能な限り解析を続行し、複数のエラーを一度に報告できるようにすることが重要でした。これにより、開発者は一度のコンパイルでより多くの問題を把握できるようになります。
3.  **パーサーの進行保証:** エラー回復の過程で、パーサーが無限ループに陥ったり、全く進行しなくなったりする事態を防ぐ必要がありました。

これらの改善は、新しいパーサーの堅牢性を高め、Go言語開発者にとってより良い開発体験を提供することを目的としていました。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

*   **コンパイラ (Compiler):** ソースコードを機械が実行できる形式（機械語など）に変換するプログラムです。GoコンパイラはGo言語のソースコードをコンパイルします。
*   **字句解析 (Lexical Analysis / Tokenization):** ソースコードを意味のある最小単位（トークン）に分割するプロセスです。例えば、`var x = 10;`というコードは、`var` (キーワード)、`x` (識別子)、`=` (演算子)、`10` (リテラル)、`;` (区切り文字) といったトークンに分割されます。
*   **構文解析 (Syntax Analysis / Parsing):** 字句解析で生成されたトークンの並びが、言語の文法規則に合致しているかを検証し、通常は抽象構文木（AST: Abstract Syntax Tree）と呼ばれるツリー構造を構築するプロセスです。
*   **パーサー (Parser):** 構文解析を行うコンパイラのコンポーネントです。
*   **再帰下降パーサー (Recursive Descent Parser):** 文法規則の各非終端記号に対応する関数を定義し、それらの関数が再帰的に呼び出されることで構文解析を行うパーサーの一種です。手書きで実装されることが多く、柔軟なエラーハンドリングが可能です。
*   **エラー回復 (Error Recovery):** 構文エラーが検出された後、パーサーが処理を中断せずに、エラー箇所をスキップして解析を続行しようとするメカニニズムです。これにより、単一の構文エラーが原因で後続の有効なコードが解析されないことを防ぎ、複数のエラーを報告できます。
*   **トークン (Token):** 字句解析によって識別される、ソースコードの最小単位です。例えば、キーワード、識別子、演算子、リテラルなどがトークンとなります。
*   **`EOF` (End Of File):** ファイルの終端を示す特別なトークンです。
*   **`Yyerror`:** Goコンパイラの内部でエラーを報告するために使用される関数です。

## 技術的詳細

このコミットの主要な技術的変更点は、`src/cmd/compile/internal/gc/parser.go` 内の構文エラーハンドリングロジックの再構築にあります。

1.  **`syntax_error` 関数の変更と `p.syntax_error` メソッドの導入:**
    *   以前はグローバル関数 `syntax_error(msg string)` が存在しましたが、これが `parser` 型のメソッド `(p *parser) syntax_error(msg string)` に変更されました。これにより、エラー報告がパーサーの状態（現在のトークン `p.tok` など）にアクセスできるようになり、よりコンテキストに応じたエラーメッセージの生成が可能になりました。
    *   `p.syntax_error` メソッド内では、エラーメッセージ `msg` に応じて適切な句読点や前置詞（"in", "at", "after", "expecting"）を追加するロジックが導入されました。これにより、エラーメッセージがより自然で分かりやすくなります。
    *   特に、`LLITERAL` (リテラル)、`LNAME` (名前)、`LASOP` (代入演算子) などのトークンタイプに応じて、具体的なトークン文字列（例: リテラル値、シンボル名、演算子）をエラーメッセージに含めるようになりました。これにより、「unexpected token」のような一般的なメッセージではなく、「unexpected "foo"」のように具体的な情報が提供されます。

2.  **`p.advance` メソッドの導入によるエラー回復の強化:**
    *   新しい `(p *parser) advance(stoplist ...int32)` メソッドが導入されました。このメソッドは、エラー発生時にパーサーが現在のトークンを消費し、指定された `stoplist`（停止トークンのリスト）に含まれるトークンが見つかるまでトークンを読み飛ばす役割を担います。
    *   `stoplist` が空の場合、`advance` は単に次のトークンを消費します。
    *   このメカニズムにより、パーサーは構文エラーの発生箇所を「スキップ」し、後続のコードの解析を試みることができます。これにより、単一のエラーが原因でコンパイルが完全に停止するのを防ぎ、複数のエラーを一度に報告できるようになります。これは、コンパイラのエラー回復戦略において非常に重要な改善です。

3.  **`p.error` メソッドの廃止と `p.syntax_error` および `p.advance` への置き換え:**
    *   以前の `(p *parser) error(context string)` メソッドは削除され、その呼び出し箇所は新しい `p.syntax_error` と `p.advance` の組み合わせに置き換えられました。
    *   これにより、エラー報告とエラー回復のロジックが明確に分離され、より構造化されたエラーハンドリングが実現されました。例えば、`p.want(tok int32)` メソッド内では、期待するトークンが見つからなかった場合に `p.syntax_error("")` を呼び出した後、`p.advance()` を呼び出して次のトークンに進むことで、パーサーの進行を保証しています。

4.  **パーサーの進行保証:**
    *   `p.advance` メソッドの導入により、エラー発生時でもパーサーがトークンを消費し続けることが保証されます。これにより、パーサーが無限ループに陥るリスクが低減され、常に何らかの進行が行われるようになります。
    *   以前のコードにあった、`lexlineno` の変化を監視して無限ループを検出する実験的なゴルーチン（コメントアウトされている部分）は削除されました。これは、新しいエラー回復メカニズムがより効果的であると判断されたためと考えられます。

5.  **`litbuf` 変数の役割の明確化:**
    *   `src/cmd/compile/internal/gc/go.go` において、`var litbuf string` のコメントが `// LLITERAL value for use in syntax error messages` と変更され、`litbuf` が構文エラーメッセージでリテラル値を表現するために使用されることが明確化されました。これは、`p.syntax_error` メソッドで `LLITERAL` トークンの具体的な値をエラーメッセージに含めるために利用されます。

これらの変更は、Goコンパイラの新しいパーサーがより堅牢でユーザーフレンドリーなエラー報告と回復機能を持つことを保証するために不可欠でした。

## コアとなるコードの解説

このコミットの核となる変更は、`parser.go`における構文エラーハンドリングのロジックの再設計です。

1.  **`func (p *parser) syntax_error(msg string)`:**
    *   このメソッドは、構文エラーが発生した際に呼び出されます。
    *   `p.tok == EOF && nerrors > 0` のチェックは、ファイルの終端に達しており、既にエラーが報告されている場合に、無意味な追随エラーを避けるためのものです。
    *   `switch` 文は、提供されたエラーメッセージ `msg` の内容に基づいて、適切な前置詞や句読点を追加し、より自然な英語のメッセージを生成します。例えば、`"expecting"` で始まるメッセージには `, ` が追加されます。
    *   最も重要なのは、現在のトークン `p.tok` の種類に応じて、エラーメッセージに含めるトークン文字列を決定する部分です。
        *   `LLITERAL` の場合、`litbuf` グローバル変数に格納されている実際のリテラル値が使用されます。
        *   `LNAME` の場合、シンボル名 (`p.sym_.Name`) があればそれを使用し、なければ一般的な `"name"` を使用します。
        *   `LASOP` (代入演算子) の場合、`goopnames[p.op] + "="` の形式で具体的な演算子（例: `+=`）を生成します。
        *   その他のトークンについては、`tokstring(p.tok)` を使用して一般的なトークン名を変換します。
    *   最終的に、`Yyerror("syntax error: unexpected " + tok + msg)` を呼び出して、詳細なエラーメッセージを報告します。これにより、単に「構文エラー」とだけ表示されるのではなく、「unexpected identifier "foo"」のように、何が予期されなかったのかが明確になります。

2.  **`func (p *parser) advance(stoplist ...int32)`:**
    *   このメソッドは、エラー回復の主要なメカニズムを提供します。
    *   `stoplist` は、パーサーが読み飛ばしを停止すべきトークンのリストです。例えば、ステートメントの終わりを示すセミコロンや、ブロックの終わりを示す閉じブレースなどが指定されます。
    *   `len(stoplist) == 0` の場合、単に次のトークンを消費し、最小限の進行を保証します。
    *   `for p.tok != EOF` ループは、ファイルの終端に達するまでトークンを読み飛ばし続けます。
    *   内部の `for _, stop := range stoplist` ループは、現在のトークン `p.tok` が `stoplist` 内のいずれかのトークンと一致するかをチェックします。一致した場合、読み飛ばしを停止し、メソッドを終了します。
    *   `p.next()` は、現在のトークンを消費し、次のトークンを読み込みます。
    *   このメソッドにより、パーサーは構文エラーの発生箇所を効率的にスキップし、後続の有効な構文要素の解析を再開できる可能性が高まります。これにより、コンパイルエラーが連鎖的に発生するのを防ぎ、より多くのエラーを一度に報告できるようになります。

これらの変更は、Goコンパイラの新しいパーサーが、よりユーザーフレンドリーで堅牢なエラーハンドリングを提供するための重要なステップでした。

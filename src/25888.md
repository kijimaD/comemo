# [インデックス 25888] ファイルの概要

このコミットは、Go言語の標準ライブラリである`net/mail`パッケージにおいて、メールアドレスの解析時に非ASCII文字が適切にエンコードされていない場合に、より具体的で分かりやすいエラーメッセージを返すように改善するものです。以前は一般的な「invalid string」エラーが返されていましたが、この変更により「unencoded non-ASCII text in address」という明確なエラーが報告されるようになります。

## 元コミット内容

これにより、Issue #12492が修正されます。

## 変更の背景

電子メールアドレスの構文は、主にRFC 5322などの標準によって定義されており、その多くはASCII文字セットに基づいています。特に、メールアドレスのローカルパート（`@`の前の部分）やドメインパートを構成する「atom」と呼ばれる要素は、通常、特定のASCII文字の集合で構成されることが期待されます。

しかし、現実世界では、非ASCII文字（例えば、日本語、ドイツ語のウムラウト、その他の特殊文字）を含むメールアドレスが存在します。これらの非ASCII文字をメールヘッダ（From, Toなど）やアドレス自体に含める場合、RFC 2047で定義されている「encoded-word」構文（例: `=?UTF-8?B?base64_encoded_text?=`) を使用してエンコードする必要があります。

このコミット以前の`net/mail`パッケージの`ParseAddress`関数は、エンコードされていない非ASCII文字がメールアドレスの「atom」部分に現れた場合、それを一般的な「mail: invalid string」エラーとして処理していました。このエラーメッセージは、問題の根本原因（非ASCII文字の存在）を特定するのに十分な情報を提供せず、開発者がデバッグする際に混乱を招く可能性がありました。

この変更の目的は、非ASCII文字が不適切にエンコードされた状態でアドレスに現れた場合に、より具体的で診断しやすいエラーメッセージ（「mail: unencoded non-ASCII text in address」）を返すことで、開発者の利便性を向上させることです。これにより、問題の種類が明確になり、適切なエンコーディングの適用や入力の修正が容易になります。

## 前提知識の解説

### RFC 5322 (Internet Message Format)

電子メールメッセージの基本的なフォーマットを定義する標準です。これには、ヘッダフィールド（From, To, Subjectなど）やメッセージ本文の構造が含まれます。メールアドレスの構文もRFC 5322で定義されており、特にローカルパートとドメインパートを構成する文字セットに言及しています。基本的にはASCII文字が想定されており、特殊な文字は引用符で囲むか、後述のRFC 2047でエンコードする必要があります。

### RFC 2047 (MIME (Multipurpose Internet Mail Extensions) Part Three: Message Header Extensions for Non-ASCII Text)

MIMEの一部であり、電子メールヘッダフィールド（Subject, From, Toなど）で非ASCII文字を使用するためのメカニズムを定義しています。これは「encoded-word」構文として知られ、`=?charset?encoding?encoded_text?=` の形式を取ります。例えば、`=?UTF-8?B?44GZ44KC44GS?= <user@example.com>` のように、表示名に非ASCII文字を含める場合に使用されます。メールアドレスのローカルパートやドメインパート自体に非ASCII文字を直接含めることは、RFC 5322の厳密な解釈では許容されず、国際化ドメイン名 (IDN) や国際化メールアドレス (EAI) のような別のメカニズムが必要です。このコミットは、そのようなエンコードされていない非ASCII文字が誤ってアドレスの「atom」として解釈されようとした場合の挙動を改善するものです。

### メールアドレスの「Atom」

RFC 5322において、メールアドレスのローカルパート（`@`の左側）やドメインパート（`@`の右側）は、いくつかの「atom」と呼ばれる構成要素から成り立っています。「atom」は、特定のASCII文字（英数字、一部の記号など）の連続です。例えば、`user.name@example.com`というアドレスでは、`user`、`name`、`example`、`com`がそれぞれatomと見なせます。これらのatom内には、エンコードされていない非ASCII文字は含まれてはなりません。

### `net/mail`パッケージ

Go言語の標準ライブラリ`net/mail`は、RFC 5322に準拠した電子メールメッセージの解析と生成を目的としています。このパッケージは、メールヘッダの解析、アドレスのパース、メッセージ本文の読み取りなどの機能を提供します。`ParseAddress`関数は、与えられた文字列から単一のメールアドレスを解析するために使用されます。

### `isAtext`関数

`net/mail`パッケージの内部で使用されるヘルパー関数で、与えられたバイトがメールアドレスの「atom」を構成する有効なASCII文字（`atext`）であるかどうかを判定します。この関数は、RFC 5322で定義された`atext`文字セットに基づいており、非ASCII文字は`atext`とは見なされません。

## 技術的詳細

このコミットの主要な変更は、`src/net/mail/message.go`ファイル内の`addrParser`構造体の`consumeAtom`メソッドにあります。このメソッドは、メールアドレス文字列から「atom」を解析する役割を担っています。

変更前の`consumeAtom`メソッドは、まず`p.peek()`で次の文字を調べ、それが`isAtext`関数によって有効な`atext`文字であるかを確認していました。もし`isAtext`が`false`を返した場合、それは有効な`atext`文字ではないと判断され、`errors.New("mail: invalid string")`という一般的なエラーが返されていました。

この挙動の問題点は、`isAtext`関数が非ASCII文字に対して`false`を返すため、非ASCII文字が検出された場合でも、それが単に無効なASCII文字なのか、それともエンコードされていない非ASCII文字なのかを区別できなかった点です。

変更後の`consumeAtom`メソッドでは、この点を改善するために以下のロジックが追加されました。

1.  **新しいエラー変数の導入**: `var errNonASCII = errors.New("mail: unencoded non-ASCII text in address")` という新しいエラー変数が定義されました。これにより、非ASCII文字に特化したエラーメッセージを提供できます。

2.  **最初の文字のチェックの強化**:
    ```go
    if c := p.peek(); !isAtext(c, false) {
        if c > 127 {
            return "", errNonASCII
        }
        return "", errors.New("mail: invalid string")
    }
    ```
    `p.peek()`で取得した文字`c`が`isAtext`ではない場合、さらに`c > 127`（つまり非ASCII文字であるか）をチェックします。もし非ASCII文字であれば、新しく定義された`errNonASCII`を返します。そうでなければ、以前と同様に一般的な「invalid string」エラーを返します。これにより、atomの開始文字が非ASCIIである場合に、より具体的なエラーが報告されるようになります。

3.  **atomの途中の文字のチェックの強化**:
    ```go
    for ; i < p.len() && isAtext(p.s[i], dot); i++ {
    }
    if i < p.len() && p.s[i] > 127 {
        return "", errNonASCII
    }
    ```
    `isAtext`文字を連続して読み取るループの後、`i < p.len()`（まだ文字列の終端に達していない）かつ`p.s[i] > 127`（次の文字が非ASCII文字である）という条件が満たされた場合、`errNonASCII`を返します。これは、有効なatomの直後にエンコードされていない非ASCII文字が続くケースを捕捉するためのものです。例えば、`userµ@example.com`のような場合に、`user`は有効なatomですが、その直後の`µ`が非ASCII文字であるため、このチェックでエラーが検出されます。

これらの変更により、`net/mail`パッケージは、メールアドレスの解析時に非ASCII文字の不適切な使用をより正確に検出し、開発者にとって有用なエラーメッセージを提供するようになりました。

## コアとなるコードの解説

### `src/net/mail/message.go`

1.  **`var errNonASCII = errors.New("mail: unencoded non-ASCII text in address")`**:
    この行では、新しいグローバルエラー変数`errNonASCII`が定義されています。このエラーは、メールアドレスの解析中にエンコードされていない非ASCII文字が検出された場合に返される、具体的なエラーメッセージを保持します。これにより、一般的な「invalid string」エラーではなく、問題の性質を直接示すエラーを提供できるようになります。

2.  **`if c := p.peek(); !isAtext(c, false) { ... }` ブロック内の変更**:
    `consumeAtom`関数は、まず`p.peek()`で現在のパーサー位置の文字`c`を読み取ります。
    変更前は、`!isAtext(c, false)`が真であればすぐに一般的なエラーを返していました。
    変更後は、`!isAtext(c, false)`が真の場合に、さらに`if c > 127`という条件で`c`が非ASCII文字であるかをチェックします。
    -   もし`c`が非ASCII文字（ASCII値が127より大きい）であれば、`return "", errNonASCII`として、新しく定義された非ASCIIエラーを返します。
    -   そうでなければ（`c`がASCII文字だが`atext`ではない場合）、`return "", errors.New("mail: invalid string")`として、以前と同じ一般的なエラーを返します。
    この変更により、atomの開始文字が非ASCIIである場合に、より正確なエラーが即座に報告されるようになります。

3.  **`for ; i < p.len() && isAtext(p.s[i], dot); i++ { ... }` ループ後の追加チェック**:
    このループは、有効な`atext`文字を連続して読み取り、atomを構築します。ループが終了した後、`i`はatomの直後の文字のインデックスを指します。
    追加された`if i < p.len() && p.s[i] > 127 { return "", errNonASCII }`という行は、atomの直後に文字列がまだ存在し（`i < p.len()`）、かつその文字が非ASCII文字である場合（`p.s[i] > 127`）に、`errNonASCII`を返します。
    これは、例えば`"userµ@example.com"`のようなケースで、`user`は有効なatomとして解析されますが、その直後の`µ`が非ASCII文字であるため、このチェックによってエラーが検出されるようになります。これにより、atomの途中に非ASCII文字が混入している場合も適切にエラーを報告できます。

### `src/net/mail/message_test.go`

1.  **`func TestAddressParsingErrorUnquotedNonASCII(t *testing.T)`**:
    この新しいテスト関数は、上記の`consumeAtom`の変更が正しく機能することを検証するために追加されました。
    -   `const txt = "µ <micro@example.net>"`: テストケースとして、表示名にエンコードされていない非ASCII文字`µ`を含むメールアドレス文字列を定義しています。
    -   `_, err := ParseAddress(txt)`: `net/mail.ParseAddress`関数を呼び出して、この不正なアドレスを解析しようとします。
    -   `if err == nil || !strings.Contains(err.Error(), "unencoded non-ASCII text in address") { ... }`:
        このアサーションは、`ParseAddress`がエラーを返し（`err == nil`でないこと）、かつそのエラーメッセージが「unencoded non-ASCII text in address」という文字列を含んでいることを確認します。これにより、非ASCII文字に対する新しいエラーハンドリングが期待通りに動作していることが保証されます。

これらの変更は、`net/mail`パッケージの堅牢性を高め、開発者がメールアドレスの構文エラー、特に非ASCII文字の不適切な使用に関連する問題をより効率的に診断できるようにすることを目的としています。

## 変更の背景

Go言語のランタイムは、ガベージコレクション (GC) の正確性と効率性を保証するためにライトバリア (Write Barrier) を使用します。ライトバリアは、GCが実行中にプログラムがポインタを書き換える際に、GCがオブジェクトグラフの変更を正しく追跡できるようにするためのメカニズムです。

このコミットの背景には、GoコンパイラのSSA (Static Single Assignment) バックエンドで採用されていたライトバリアの実装に問題があったことが挙げられます。具体的には、`_nostore`という接尾辞を持つライトバリアが使用されていましたが、これがCGO (GoとC言語の相互運用機能) のポインタチェッカーと互換性がありませんでした。

CGOは、Goのメモリ管理とC言語のメモリ管理という異なるモデル間でポインタを安全にやり取りするために厳格なルールを設けています。GoのGCはGoヒープ上のポインタのみを追跡するため、GoのポインタがC言語が管理するメモリ領域に誤って書き込まれると、GCがそのポインタを追跡できなくなり、メモリリークやクラッシュなどの深刻な問題を引き起こす可能性があります。この問題を検出するために「Ian's cgo checker」のようなツールやメカニズムが存在しますが、`_nostore`ライトバリアは、このチェッカーが必要とする情報を提供できなかったり、特定のポインタ書き込みを適切に処理できなかったりしたため、CGOのポインタ整合性チェックが正しく機能しない原因となっていました。

この問題を解決するため、SSAバックエンドのライトバリアを、デフォルトのコンパイラが使用しているより堅牢なパターンに合わせる必要がありました。この新しいパターンは、実装がより複雑になるものの、CGOとの互換性を確保しつつ、より効率的なライトバリア処理を実現することが期待されています。

## 前提知識の解説

### ガベージコレクション (GC) とライトバリア

Go言語は、並行かつ低遅延なガベージコレクタを採用しています。GoのGCは、主に「三色マーキング (Tri-color marking)」アルゴリズムをベースにしており、オブジェクトを白（未訪問）、灰（訪問済みだが参照先は未訪問）、黒（訪問済みで参照先も訪問済み）のいずれかの色で分類します。

GCが実行中にプログラム（ミューテーター）がポインタを書き換えることを許容するためには、「強い三色不変条件 (Strong Tri-color Invariant)」を維持する必要があります。これは「黒いオブジェクトが白いオブジェクトを指してはならない」という条件です。この不変条件を維持するために導入されるのがライトバリアです。

ライトバリアは、プログラムがポインタを書き換える際に、その書き込みをインターセプトし、GCがオブジェクトグラフの変更を正しく追跡できるようにするコードスニペットです。Go 1.8以降では、Yuasaスタイルの削除バリアとDijkstraスタイルの挿入バリアを組み合わせたハイブリッドライトバリアが導入されています。これにより、ポインタが上書きされるオブジェクトを「灰色」にしたり、新しい参照先を「灰色」にしたりすることで、GCがオブジェクトを見落とすことなく、安全にメモリを回収できるようになります。

### SSA (Static Single Assignment) 形式

SSA (Static Single Assignment) 形式は、コンパイラの最適化段階で中間表現として使用されるプログラム表現形式の一つです。SSA形式では、各変数がプログラム内で一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が大幅に簡素化されます。

Goコンパイラは、Go 1.7からSSAバックエンドを導入し、コード生成と最適化の能力を向上させました。SSA形式は、変数のライフタイムや使用箇所を明確にするため、レジスタ割り当て、デッドコード削除、共通部分式除去などの最適化をより効果的に行うことができます。しかし、SSA形式でのライトバリアの挿入は、通常のAST (Abstract Syntax Tree) ベースのコンパイラとは異なるアプローチが必要となるため、その実装は複雑になることがあります。

### CGO

CGOは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。これにより、既存のCライブラリをGoプログラムで利用したり、パフォーマンスが重要な部分をCで記述したりすることが可能になります。

しかし、CGOはGoのメモリ管理とC言語のメモリ管理の間に複雑な相互作用をもたらします。GoのGCはGoヒープ上のオブジェクトのみを管理し、C言語が`malloc`などで確保したメモリはGoのGCの管理外です。このため、GoのポインタをCのメモリに直接書き込んだり、CのポインタをGoのポインタとして誤って扱ったりすると、GoのGCが混乱し、メモリの破損やクラッシュを引き起こす可能性があります。

CGOのポインタルールは非常に厳格であり、GoのポインタがCのメモリにエスケープすることを防ぐためのチェックがランタイムやコンパイラによって行われます。このコミットで言及されている「Ian's cgo checker」は、このようなポインタの整合性を検証するメカニズムの一つと考えられます。

### `_nostore`ライトバリアの概念

`_nostore`という接尾辞を持つライトバリアは、Goランタイムの内部で特定の最適化パスとして使用されることがあります。これは、通常のライトバリアのロジックを短絡させたり、完全に省略したりするものです。例えば、ポインタの書き込み元と書き込み先が同じである場合（`*dst == src`）、実際のポインタの変更は発生しないため、完全なライトバリアの処理は不要と判断されることがあります。このようなケースで`_nostore`バリアが使用されることで、ライトバリアのオーバーヘッドを削減し、パフォーマンスを向上させることが目的でした。

しかし、CGOのようなGoと外部メモリ管理システムが混在する環境では、このような最適化が問題を引き起こす可能性があります。`_nostore`バリアが特定のポインタ書き込みをスキップすることで、CGOチェッカーが必要とする情報が失われたり、CGOのポインタルールに違反する操作が見過ごされたりするリスクがあったと考えられます。

## 技術的詳細

このコミットの主要な目的は、SSAバックエンドにおけるライトバリアの実装を、CGOのポインタチェッカーと互換性のある、より堅牢なものにすることです。

### `_nostore`ライトバリアの問題点

以前のSSAバックエンドでは、`typedmemmove_nostore`のような`_nostore`バージョンのライトバリアが使用されていました。これらのバリアは、特定の条件下でライトバリアの処理を最適化し、オーバーヘッドを削減することを意図していました。しかし、CGOのポインタチェッカーは、GoのポインタがCのメモリに書き込まれることを厳しく監視しています。`_nostore`バリアが特定のポインタ書き込みを「最適化」してしまった結果、CGOチェッカーがGoのポインタの不正な使用を検出できなかったり、あるいは誤った検出を引き起こしたりする可能性がありました。これは、GoのGCが管理するポインタがCのメモリに「エスケープ」するのを防ぐというCGOの重要な安全機構を損なうものでした。

### 新しいライトバリアパターンへの移行

このコミットでは、`_nostore`バージョンのライトバリアを廃止し、デフォルトのコンパイラが使用しているライトバリアパターンに移行します。これは、より明示的で詳細なライトバリアの適用を意味します。

1.  **`typedmemmove_nostore`の削除と`writebarrierptr`の導入**:
    *   `src/cmd/compile/internal/gc/builtin.go` および `src/cmd/compile/internal/gc/builtin/runtime.go` から `typedmemmove_nostore` の宣言が削除されました。
    *   `src/cmd/compile/internal/gc/go.go` および `src/cmd/compile/internal/gc/pgen.go` では、`typedmemmove_nostore` の代わりに `writebarrierptr` と `typedmemmove` がランタイム関数として登録されるようになりました。
    *   `src/runtime/mbarrier.go` からも `typedmemmove_nostore` 関数自体が削除されています。

2.  **`insertWBmove`と`insertWBstore`の導入**:
    *   `src/cmd/compile/internal/gc/ssa.go` に、`insertWBmove` と `insertWBstore` という2つの新しい関数が導入されました。これらは、以前の汎用的な`insertWB`関数を置き換えるものです。
    *   `insertWBmove(t *Type, left, right *ssa.Value, line int32)`: `*left = *right` のようなメモリ間ムーブ操作にライトバリアを挿入します。これは、`typedmemmove`ランタイム関数を呼び出すことで実現されます。
    *   `insertWBstore(t *Type, left, right *ssa.Value, line int32)`: `*left = right` のようなストア操作にライトバリアを挿入します。この関数は、割り当てられる型`t`に応じて、より詳細な処理を行います。
        *   **構造体**: 構造体の場合は、各フィールドを再帰的に処理し、ポインタを含むフィールドに対してのみライトバリアを適用します。
        *   **ポインタ、マップ、チャネル**: これらの型はポインタそのものであるため、`writebarrierptr`ランタイム関数を呼び出します。
        *   **文字列、スライス**: これらの型は内部にポインタを持つため、文字列のデータポインタやスライスのデータポインタを抽出し、それに対して`writebarrierptr`を適用します。
        *   **インターフェース**: インターフェースのデータ部分（`idata`）がポインタである場合、そのポインタに対して`writebarrierptr`を適用します。
    *   これらの関数は、`writeBarrier.enabled`フラグをチェックし、ライトバリアが有効な場合にのみランタイム関数を呼び出す条件分岐を生成します。これにより、ライトバリアのオーバーヘッドを最小限に抑えつつ、必要な場合にのみバリアが適用されるようになります。

3.  **`assign`関数の変更**:
    *   `src/cmd/compile/internal/gc/ssa.go` の `assign` 関数のシグネチャが変更され、`wb` (write barrier) と `deref` (dereference) という新しいブール型パラメータが追加されました。
    *   `wb`パラメータは、その代入操作にライトバリアが必要かどうかを示します。
    *   `deref`パラメータは、右辺がポインタのデリファレンスであるかどうかを示し、`left = *right`のような操作を区別するために使用されます。
    *   `assign`関数は、これらのパラメータと割り当てられる型に基づいて、`insertWBmove`または`insertWBstore`を適切に呼び出すようになりました。

### 効率性の向上

コミットメッセージには「It's a bit trickier to code up but should be more efficient.」とあります。これは、新しいライトバリアの実装が、型に応じたよりきめ細やかな処理を必要とするため、コードが複雑になることを認めています。しかし、その複雑さの代償として、以下の点で効率性が向上すると考えられます。

*   **より正確なライトバリアの適用**: `_nostore`バリアがスキップしていた可能性のあるCGO関連のポインタ書き込みを確実に捕捉できるようになります。これにより、GCの正確性が向上し、デバッグが困難なメモリ関連のバグを防ぐことができます。
*   **不要なバリアの回避**: `writeBarrier.enabled`フラグによる条件分岐や、型に応じた詳細な処理により、ポインタを含まないデータ型や、GCが不要な状況でのライトバリアの適用を回避できます。これにより、全体的な実行時オーバーヘッドが削減されます。
*   **CGOとの互換性**: CGOのポインタチェッカーが期待する動作と一致するライトバリアパターンを採用することで、CGOを使用するGoプログラムの安定性と信頼性が向上します。

## コアとなるコードの解説

### `assign`関数の変更

`assign`関数は、SSAバックエンドにおいて代入操作を処理する中心的な関数です。このコミットでは、そのシグネチャが`func (s *state) assign(left *Node, right *ssa.Value, wb, deref bool, line int32)`に変更されました。

*   `wb` (write barrier): この代入がライトバリアを必要とするかどうかを示すブール値です。`OASWB` (Write Barrierを伴う代入) のような操作で`true`になります。
*   `deref` (dereference): 右辺がポインタのデリファレンスであるかどうかを示すブール値です。例えば、`left = *right`のような操作で`true`になります。

この変更により、`assign`関数は代入の種類とライトバリアの必要性に応じて、より適切なライトバリア処理を選択できるようになりました。具体的には、`left`がSSA化可能でない（つまりメモリ上の変数である）場合、`deref`が`true`であれば`insertWBmove`を、そうでなければ`insertWBstore`を呼び出すようにロジックが変更されています。

### `insertWBmove`関数

`insertWBmove`関数は、`*left = *right`のようなメモリからメモリへの値の移動（ムーブ）操作に対してライトバリアを挿入します。

```go
func (s *state) insertWBmove(t *Type, left, right *ssa.Value, line int32) {
    bThen := s.f.NewBlock(ssa.BlockPlain)
    bElse := s.f.NewBlock(ssa.BlockPlain)
    bEnd := s.f.NewBlock(ssa.BlockPlain)

    // writeBarrier.enabled のチェック
    flag := s.newValue2(ssa.OpLoad, Types[TBOOL], flagaddr, s.mem())
    b := s.endBlock()
    b.Kind = ssa.BlockIf
    b.Likely = ssa.BranchUnlikely // ライトバリアが有効なケースは稀であると仮定
    b.Control = flag
    b.AddEdgeTo(bThen) // writeBarrier.enabled が true の場合
    b.AddEdgeTo(bElse) // writeBarrier.enabled が false の場合

    s.startBlock(bThen)
    // ライトバリアが有効な場合、typedmemmove ランタイム関数を呼び出す
    taddr := s.newValue1A(ssa.OpAddr, Types[TUINTPTR], &ssa.ExternSymbol{Types[TUINTPTR], typenamesym(t)}, s.sb)
    s.rtcall(typedmemmove, true, nil, taddr, left, right)
    s.endBlock().AddEdgeTo(bEnd)

    s.startBlock(bElse)
    // ライトバリアが無効な場合、通常のメモリ移動 (OpMove) を行う
    s.vars[&memVar] = s.newValue3I(ssa.OpMove, ssa.TypeMem, t.Size(), left, right, s.mem())
    s.endBlock().AddEdgeTo(bEnd)

    s.startBlock(bEnd)
    // ... (デバッグ出力など) ...
}
```

この関数は、`writeBarrier.enabled`というグローバルフラグをチェックし、ライトバリアが有効な場合は`runtime.typedmemmove`関数を呼び出します。`typedmemmove`は、指定された型`t`に基づいて、`src`から`dst`へメモリを移動し、その過程でポインタの書き込みをGCに通知します。ライトバリアが無効な場合は、通常の`OpMove`命令でメモリを移動します。

### `insertWBstore`関数

`insertWBstore`関数は、`*left = right`のようなストア操作に対してライトバリアを挿入します。この関数は、割り当てられる型`t`に応じて、より複雑なロジックを持ちます。

```go
func (s *state) insertWBstore(t *Type, left, right *ssa.Value, line int32) {
    // 構造体の場合、各フィールドを再帰的に処理
    if t.IsStruct() {
        // ... (各フィールドに対して insertWBstore を再帰的に呼び出す) ...
        return
    }

    // スカラーフィールドのストア（ポインタを含まない部分）
    // ... (文字列長、スライス長/容量、インターフェースのitabフィールドなど) ...

    bThen := s.f.NewBlock(ssa.BlockPlain)
    bElse := s.f.NewBlock(ssa.BlockPlain)
    bEnd := s.f.NewBlock(ssa.BlockPlain)

    // writeBarrier.enabled のチェック (insertWBmove と同様)
    flag := s.newValue2(ssa.OpLoad, Types[TBOOL], flagaddr, s.mem())
    b := s.endBlock()
    b.Kind = ssa.BlockIf
    b.Likely = ssa.BranchUnlikely
    b.Control = flag
    b.AddEdgeTo(bThen)
    b.AddEdgeTo(bElse)

    // ライトバリアが有効な場合
    s.startBlock(bThen)
    switch {
    case t.IsPtr() || t.IsMap() || t.IsChan():
        // ポインタ、マップ、チャネルは writebarrierptr を呼び出す
        s.rtcall(writebarrierptr, true, nil, left, right)
    case t.IsString():
        // 文字列のデータポインタに対して writebarrierptr を呼び出す
        ptr := s.newValue1(ssa.OpStringPtr, Ptrto(Types[TUINT8]), right)
        s.rtcall(writebarrierptr, true, nil, left, ptr)
    case t.IsSlice():
        // スライスのデータポインタに対して writebarrierptr を呼び出す
        ptr := s.newValue1(ssa.OpSlicePtr, Ptrto(Types[TUINT8]), right)
        s.rtcall(writebarrierptr, true, nil, left, ptr)
    case t.IsInterface():
        // インターフェースのデータ部分 (idata) に対して writebarrierptr を呼び出す
        idata := s.newValue1(ssa.OpIData, Ptrto(Types[TUINT8]), right)
        idataAddr := s.newValue1I(ssa.OpOffPtr, Ptrto(Types[TUINT8]), s.config.PtrSize, left)
        s.rtcall(writebarrierptr, true, nil, idataAddr, idata)
    default:
        s.Fatalf("bad write barrier type %s", t)
    }
    s.endBlock().AddEdgeTo(bEnd)

    // ライトバリアが無効な場合（通常のストア）
    s.startBlock(bElse)
    switch {
    case t.IsPtr() || t.IsMap() || t.IsChan():
        // 通常のポインタストア
        s.vars[&memVar] = s.newValue3I(ssa.OpStore, ssa.TypeMem, s.config.PtrSize, left, right, s.mem())
    // ... (文字列、スライス、インターフェースの通常のストア処理) ...
    default:
        s.Fatalf("bad write barrier type %s", t)
    }
    s.endBlock().AddEdgeTo(bEnd)

    s.startBlock(bEnd)
    // ... (デバッグ出力など) ...
}
```

この関数も`writeBarrier.enabled`フラグをチェックしますが、その後の処理は型によって大きく異なります。

*   **ポインタを含む型**: `t.IsPtr()`, `t.IsMap()`, `t.IsChan()` のようなポインタ型、および文字列、スライス、インターフェースのように内部にポインタを持つ型の場合、`runtime.writebarrierptr`関数が呼び出されます。`writebarrierptr`は、単一のポインタの書き込みに対してライトバリアを適用する、より低レベルな関数です。文字列やスライス、インターフェースの場合は、その内部のデータポインタを抽出し、そのポインタに対して`writebarrierptr`を適用します。
*   **構造体**: 構造体の場合、`insertWBstore`は再帰的に自身を呼び出し、構造体の各フィールドに対してライトバリアを適用します。これにより、構造体内のポインタフィールドのみがライトバリアの対象となります。
*   **スカラーフィールド**: ポインタを含まないスカラーフィールド（例：文字列の長さ、スライスの容量、インターフェースの`itab`フィールドなど）は、ライトバリアの対象外として通常のストア命令で処理されます。

この詳細な型ごとの処理により、ライトバリアは必要なポインタ書き込みにのみ正確に適用され、CGOのポインタチェッカーが期待する動作と一致するようになります。

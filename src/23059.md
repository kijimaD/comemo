## 元コミット内容

このコミットの元の内容は、「net: サーバーテストを置き換える」というものです。Go 1リリース後に導入された、ランタイム統合型ネットワークポーラーや`Dialer`といった新機能を必要とする新しいテストに、既存のサーバーテストを置き換えることを意図しています。

## 変更の背景

Go 1のリリース後、Goのネットワークスタックは継続的に進化してきました。特に重要な変更点として、**ランタイム統合型ネットワークポーラー**の導入と、`net.Dialer`の機能強化が挙げられます。

Go 1.1（2013年3月リリース）以降、GoのネットワークI/Oモデルは大きく改善されました。それ以前は、ネットワークポーラーは主に`net`パッケージ内で純粋なGoで実装されており、チャネルを介してネットワークファイルディスクリプタの準備状況を通知していました。しかし、Go 1.1以降、ネットワークポーラーはGoランタイムスケジューラと深く統合されました。これにより、ネットワーク操作でブロックするゴルーチンはスケジューラによって直接管理されるようになり、`epoll`（Linux）、`kqueue`（macOS/BSD）、I/O Completion Ports（IOCP）（Windows）といったOSレベルのイベント通知メカニズムを効率的に利用できるようになりました。この統合により、コンテキストスイッチのオーバーヘッドが削減され、ネットワークイベントを待つゴルーチンの管理がより効率的になり、パフォーマンスが大幅に向上しました。

また、`net.Dialer`は、ネットワーク接続を確立するためのより柔軟な方法を提供するようになりました。初期の`net`パッケージは基本的な`Dial`関数を提供していましたが、`net.Dialer`構造体の導入により、`Timeout`や`Deadline`といった接続パラメータをより細かく制御できるようになりました。特に`DialContext`メソッドの追加は、コンテキストオブジェクトを介して接続タイムアウトのより詳細な制御や、ダイヤル試行のキャンセルを可能にし、複雑なアプリケーションでの接続管理を容易にしました。

これらの新機能は、Goのネットワークプログラミングをより強力で効率的なものにしましたが、既存のテストスイートはこれらの新しいアーキテクチャや機能に対応しきれていませんでした。古いテストは、Go 1以前のネットワークモデルに基づいていたため、新しいポーラーや`Dialer`の挙動を適切に検証することが困難でした。そのため、これらの新機能を最大限に活用し、Goのネットワークスタックの現在の状態を正確に反映する新しいテストが必要とされました。このコミットは、その必要性に応えるものです。

## 前提知識の解説

*   **Goの`net`パッケージ**: Go言語の標準ライブラリの一部で、TCP/IP、UDP、UnixドメインソケットなどのネットワークI/O機能を提供します。サーバーの構築、クライアントの接続、データの送受信など、ネットワークプログラミングの基本的な機能が網羅されています。
*   **`net.Listen`**: 指定されたネットワークアドレスで着信接続をリッスンするための`Listener`インターフェースを返します。サーバーアプリケーションの開始点となります。
*   **`net.Dial` / `net.Dialer`**: `net.Dial`は、指定されたネットワークアドレスへの接続を確立するためのシンプルな関数です。`net.Dialer`は、より高度な接続設定（タイムアウト、ローカルアドレスの指定など）を可能にする構造体で、`Dial`メソッドを提供します。
*   **`net.PacketConn`**: UDPやUnixグラムソケットのようなパケット指向のネットワーク接続を表すインターフェースです。`ReadFrom`や`WriteTo`メソッドを使用して、データグラムの送受信を行います。
*   **`net.Conn`**: TCPやUnixストリームソケットのようなストリーム指向のネットワーク接続を表すインターフェースです。`Read`や`Write`メソッドを使用して、データの送受信を行います。
*   **ランタイム統合型ネットワークポーラー**: Goランタイムの重要なコンポーネントで、OSのI/O多重化メカニズム（Linuxの`epoll`、macOS/BSDの`kqueue`など）と連携し、多数のネットワーク接続を効率的に処理します。GoのゴルーチンがネットワークI/Oでブロックされた場合、ポーラーがそのゴルーチンを一時停止させ、I/Oが準備できたときにスケジューラに再開を通知します。これにより、Goは「1接続につき1スレッド」モデルのオーバーヘッドを回避し、高い並行性を実現します。
*   **`context.Context`**: Go 1.7で導入されたパッケージで、API境界を越えてデッドライン、キャンセルシグナル、その他のリクエストスコープの値を伝播するために使用されます。`net.Dialer`の`DialContext`メソッドなどで利用され、接続試行のタイムアウトやキャンセルを柔軟に制御できます。
*   **`testing`パッケージ**: Goの標準テストフレームワークです。`*testing.T`型はテスト関数に渡され、テストの失敗を報告したり、ログを出力したりするために使用されます。
*   **`os.Remove`**: ファイルシステムから指定されたパスを削除する関数です。Unixドメインソケットのテストでは、ソケットファイルが残らないようにテストの前後で削除するために使用されます。

## 技術的詳細

このコミットの主要な技術的変更は、Goの`net`パッケージのテストスイートを、Go 1リリース後に導入された新しいネットワーク機能（特にランタイム統合型ネットワークポーラーと`net.Dialer`）をより効果的に検証できるように再構築した点にあります。

以前のテストは、`runStreamConnServer`や`runDatagramPacketConnServer`といった汎用的なサーバー関数と、それに対応するクライアント関数`runStreamConnClient`や`runDatagramConnClient`を使用していました。これらの関数は、チャネルを介してサーバーの起動や終了を同期し、単純なエコーサーバーとして機能していました。しかし、これらのテストは、新しい`Dialer`の機能や、ポーラーがどのようにゴルーチンを管理するかといった、より複雑なシナリオを十分にカバーしていませんでした。

新しいテストスイートでは、以下の点が改善されています。

1.  **テスト構造の明確化**:
    *   `tcpServerTests`, `unixAndUnixpacketServerTests`, `udpServerTests`, `unixgramServerTests`といった、ネットワークタイプごとに特化したテストケースの構造体が導入されました。これにより、各テストケースがどのネットワークプロトコルとアドレスタイプを対象としているかが一目でわかるようになりました。
    *   各テストケースは、サーバー側とクライアント側のエンドポイント情報（`snet`, `saddr`, `tnet`, `taddr`）を保持し、テストの意図がより明確になっています。

2.  **`localServer`と`localPacketServer`の導入**:
    *   テストヘルパーとして`localServer`と`localPacketServer`という構造体が導入されました。これらは、それぞれ`net.Listener`と`net.PacketConn`をラップし、テストサーバーのセットアップとティアダウン（`buildup`と`teardown`）をカプセル化します。これにより、テストコードの重複が減り、サーバーのライフサイクル管理が簡素化されました。
    *   これらのヘルパーは、テスト中に複数の並行接続を処理するための`N`個のサーバーインスタンスを起動する機能も提供します。

3.  **`transponder`と`transceiver`の導入**:
    *   `transponder`はサーバー側で接続を受け入れ、受信したデータをそのまま送信元に返す（エコーバックする）役割を担います。これは、新しいテストフレームワークにおけるサーバー側の汎用的なハンドラとして機能します。
    *   `transceiver`はクライアント側でデータを送信し、その応答を受信する役割を担います。これにより、クライアントとサーバー間のデータフローをテストします。
    *   これらの関数はチャネルを使用してエラーを報告するため、テストの並行実行中に発生したエラーを効率的に収集できます。

4.  **`net.Dialer`の活用**:
    *   クライアント側の接続確立に`net.Dialer`が積極的に使用されています。これにより、タイムアウト設定（`someTimeout`）など、`Dialer`の機能がテストされるようになりました。
    *   特に`TestUDPServer`や`TestUnixgramServer`では、`Dialer`の`LocalAddr`オプションを使用して、クライアント側のローカルアドレスを指定するテストケースも追加されています。

5.  **並行テストの強化**:
    *   `const N = 3`のように、複数の並行接続を同時にテストする構造が導入されました。これにより、Goのランタイム統合型ネットワークポーラーが多数の同時接続をどのように効率的に処理するかを検証できます。
    *   複数のゴルーチンが同時にネットワークI/Oを行うシナリオをシミュレートすることで、競合状態やデッドロックなどの問題を早期に発見しやすくなります。

6.  **`timeout_test.go`の更新**:
    *   `timeout_test.go`も、新しい`localServer`や`localPacketListener`といったヘルパー関数を使用するように更新されました。これにより、タイムアウトテストのセットアップが簡素化され、`net`パッケージの他のテストとの一貫性が保たれています。

これらの変更により、テストはよりモジュール化され、読みやすく、そしてGoの現代的なネットワークスタックの挙動をより正確に反映するようになりました。特に、ランタイム統合型ネットワークポーラーの効率性や`Dialer`の柔軟性を検証するための基盤が強化されています。

## コアとなるコードの変更箇所

このコミットでは、主に以下の2つのファイルが変更されています。

*   `src/net/server_test.go`: サーバーテストの主要なロジックが定義されているファイルです。
*   `src/net/timeout_test.go`: ネットワーク操作のタイムアウトに関するテストが定義されているファイルです。

具体的な変更点としては、

**`src/net/server_test.go`:**

*   古いテストケース定義（`streamConnServerTests`, `seqpacketConnServerTests`, `datagramPacketConnServerTests`）が、新しいテストケース定義（`tcpServerTests`, `unixAndUnixpacketServerTests`, `udpServerTests`, `unixgramServerTests`）に置き換えられました。新しい定義は、サーバーとクライアントのエンドポイントをより明確に分離し、`Dialer`の使用を考慮しています。
*   古いテスト実行関数（`TestStreamConnServer`, `TestSeqpacketConnServer`, `runStreamConnServer`, `runStreamConnClient`, `runDatagramPacketConnServer`, `runDatagramConnClient`, `runDatagramPacketConnClient`）が削除され、新しいテスト実行関数（`TestTCPServer`, `TestUnixAndUnixpacketServer`, `TestUDPServer`, `TestUnixgramServer`）が追加されました。
*   新しいテストヘルパー構造体`localServer`と`localPacketServer`、およびそれらのメソッド（`newLocalServer`, `buildup`, `teardown`）が導入されました。
*   新しい汎用的なサーバーハンドラ`transponder`とクライアント側送受信関数`transceiver`、`packetTransceiver`が追加されました。
*   `io`パッケージや`time`パッケージのインポートが削除され、テストに必要な最小限のインポートに整理されました。

**`src/net/timeout_test.go`:**

*   `TestTimeoutUDP`と`TestTimeoutTCP`関数内で、サーバーのセットアップに古い`runDatagramPacketConnServer`や`runStreamConnServer`の呼び出しが削除され、新しい`newLocalPacketListener`や`newLocalServer`といったヘルパー関数が使用されるようになりました。これにより、タイムアウトテストのセットアップが簡素化されています。

これらの変更により、テストコードの構造が大幅に改善され、Goの新しいネットワーク機能に対応したテストが記述されています。

## コアとなるコードの解説

このコミットのコアとなる変更は、Goの`net`パッケージのテストを、Go 1リリース後に導入されたランタイム統合型ネットワークポーラーや`net.Dialer`といった新機能をより効果的に検証できるように再設計した点にあります。

### `src/net/server_test.go` の変更点

**新しいテストケース定義:**

```go
var tcpServerTests = []struct {
	snet, saddr string // server endpoint
	tnet, taddr string // target endpoint for client
}{
	// ... 多数のTCPテストケース ...
}

var unixAndUnixpacketServerTests = []struct {
	network, address string
}{
	// ... Unixドメインソケットのテストケース ...
}

var udpServerTests = []struct {
	snet, saddr string // server endpoint
	tnet, taddr string // target endpoint for client
	dial        bool   // test with Dial
}{
	// ... UDPテストケース ...
}

var unixgramServerTests = []struct {
	saddr string // server endpoint
	caddr string // client endpoint
	dial  bool   // test with Dial
}{
	// ... Unixグラムソケットのテストケース ...
}
```
これらの構造体は、各ネットワークプロトコル（TCP, Unixドメインソケット, UDP, Unixグラムソケット）に特化したテストシナリオを定義します。サーバー側とクライアント側のネットワークタイプとアドレスを明確に指定することで、テストの意図がより分かりやすくなっています。特に`udpServerTests`と`unixgramServerTests`には`dial`フィールドが追加され、`net.Dial`を使用するケースと`net.ListenPacket`を使用するケースの両方をテストできるようになっています。

**`localServer` と `localPacketServer` ヘルパー:**

```go
// streamListener は net.Listener をラップし、テストヘルパーを生成する
type streamListener struct {
	Listener
}

func (sl *streamListener) newLocalServer() (*localServer, error) {
	// ... localServer の初期化ロジック ...
}

// localServer はテスト用のストリーム指向サーバーを管理する
type localServer struct {
	// ... フィールド定義 ...
}

func (ls *localServer) buildup(handler func(*localServer, Listener)) error {
	// ... サーバーの起動ロジック ...
}

func (ls *localServer) teardown() {
	// ... サーバーの停止ロジック ...
}

// packetListener は net.PacketConn をラップし、テストヘルパーを生成する
type packetListener struct {
	PacketConn
}

func (pl *packetListener) newLocalServer() (*localPacketServer, error) {
	// ... localPacketServer の初期化ロジック ...
}

// localPacketServer はテスト用のパケット指向サーバーを管理する
type localPacketServer struct {
	// ... フィールド定義 ...
}

func (ls *localPacketServer) buildup(handler func(*localPacketServer, PacketConn)) error {
	// ... サーバーの起動ロジック ...
}

func (ls *localPacketServer) teardown() {
	// ... サーバーの停止ロジック ...
}
```
これらのヘルパー構造体は、テストサーバーのセットアップとクリーンアップのプロセスをカプセル化します。`buildup`メソッドはサーバーを起動し、`teardown`メソッドはリソースを解放します。これにより、各テスト関数内でサーバーの起動・停止ロジックを繰り返し記述する必要がなくなり、テストコードの可読性と保守性が向上しています。特に、複数の並行接続をテストするために、`N`個のサーバーインスタンスを起動する機能が組み込まれています。

**`transponder` と `transceiver` 関数:**

```go
func transponder(ln Listener, ch chan<- error) {
	// ... サーバー側で接続を受け入れ、データをエコーバックするロジック ...
}

func packetTransponder(c PacketConn, ch chan<- error) {
	// ... パケット指向サーバー側でデータグラムを受け入れ、エコーバックするロジック ...
}

func transceiver(c Conn, wb []byte, ch chan<- error) {
	// ... クライアント側でデータを送信し、応答を受信するロジック ...
}

func packetTransceiver(c PacketConn, wb []byte, ra Addr, ch chan<- error) {
	// ... パケット指向クライアント側でデータグラムを送信し、応答を受信するロジック ...
}
```
`transponder`と`packetTransponder`は、それぞれストリーム指向とパケット指向のサーバー側で、受信したデータをそのままクライアントにエコーバックする汎用的なハンドラとして機能します。これにより、テストの目的（データが正しく送受信されるか）に集中できます。
`transceiver`と`packetTransceiver`は、クライアント側でデータを送信し、サーバーからの応答を受信します。これらの関数は、チャネルを介してエラーを報告するため、並行テスト中に発生した問題を効率的に捕捉できます。

**新しいテスト関数 (`TestTCPServer`, `TestUnixAndUnixpacketServer`, `TestUDPServer`, `TestUnixgramServer`):**

```go

	const N = 3 // 並行接続数
	for i, tt := range tcpServerTests {
		// ... Listener の Listen とエラーハンドリング ...
		var lss []*localServer // 複数のローカルサーバーインスタンス
		var tpchs []chan error // transponder からのエラーチャネル
		for i := 0; i < N; i++ {
			// ... localServer の生成と buildup ...
		}
		// ... クライアント側の Dial と transceiver の実行 ...
		// ... エラーチャネルの監視 ...
	}
}
// 他のテスト関数も同様の構造
```
これらのテスト関数は、`N`個の並行接続を確立し、`localServer`や`localPacketServer`ヘルパーを使用してサーバーを起動し、`transceiver`や`packetTransceiver`を使用してクライアント側の送受信を行います。これにより、Goのランタイム統合型ネットワークポーラーが多数の同時接続をどのように効率的に処理するかを検証できます。`net.Dialer`がクライアント接続の確立に利用され、タイムアウトなどの機能がテストされます。

### `src/net/timeout_test.go` の変更点

```go
func TestTimeoutUDP(t *testing.T) {
	// ...
	c, err := newLocalPacketListener("udp") // 新しいヘルパー関数を使用
	if err != nil {
		t.Fatal(err)
	}
	// ...
	c.Close()
}

func TestTimeoutTCP(t *testing.T) {
	// ...
	handler := func(ls *localServer, ln Listener) { // 新しいハンドラ形式
		for {
			c, err := ln.Accept()
			if err != nil {
				break
			}
			defer c.Close()
		}
	}
	ls, err := newLocalServer("tcp") // 新しいヘルパー関数を使用
	if err != nil {
		t.Fatal(err)
	}
	defer ls.teardown()
	if err := ls.buildup(handler); err != nil {
		t.Fatal(err)
	}
	// ...
}
```
`timeout_test.go`では、サーバーのセットアップに`newLocalPacketListener`や`newLocalServer`といった新しいヘルパー関数が使用されるようになりました。これにより、タイムアウトテストのセットアップが簡素化され、`net`パッケージの他のテストとの一貫性が保たれています。特に`TestTimeoutTCP`では、`localServer`の`buildup`メソッドに渡すハンドラ関数が、新しいテストフレームワークのスタイルに合わせて記述されています。

これらの変更は、Goのネットワークスタックの進化に合わせてテストインフラを近代化し、より堅牢で信頼性の高いテストを可能にすることを目的としています。

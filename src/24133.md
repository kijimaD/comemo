# [インデックス 24133] ファイルの概要

このコミットは、Go言語の `image/png` パッケージにおけるバグ修正です。具体的には、インターレースされたPNG画像をデコードする際に、幅または高さがゼロとなる「空の」インターレースパスに対して、誤ってフィルタバイトを読み込もうとする問題を解決します。これにより、特定の条件下で不正なPNG画像を処理した際に発生する可能性のあるエラーやクラッシュを防ぎ、デコーダの堅牢性を向上させます。

## 変更の背景

PNG画像は、プログレッシブ表示を可能にするために、Adam7インターレースアルゴリズムを使用してインターレースされることがあります。このアルゴリズムは画像を複数のパス（最大7つのサブ画像）に分割し、これらのパスを順次デコードして表示することで、低解像度から徐々に詳細な画像を表示します。

しかし、特定の画像サイズ（特に幅や高さが小さい画像）の場合、Adam7アルゴリズムによって生成される一部のインターレースパスが、結果的に幅または高さがゼロとなる「空の」パスになることがあります。

Goの `image/png` デコーダは、これらの空のパスに対しても、各スキャンラインの先頭に存在するフィルタタイプバイトを読み込もうとしていました。スキャンラインが存在しない（幅または高さがゼロの）パスに対してフィルタバイトを読み込もうとすると、予期せぬ動作、例えば `io.EOF` エラーやバッファオーバーフロー、あるいはデコード処理のクラッシュを引き起こす可能性がありました。

この問題は、Go issue #11604として報告されており、このコミットはその問題を解決するために導入されました。コミットメッセージには、Goプログラムで生成されたシンプルなグレースケール画像 (`gray-gradient.png`) をImageMagickでインターレース (`gray-gradient.interlaced.png`) する例が示されており、このような画像が問題を引き起こす可能性のあるシナリオを具体的に示唆しています。

## 前提知識の解説

*   **PNG (Portable Network Graphics) 画像フォーマット**:
    PNGは、可逆圧縮を特徴とするビットマップ画像フォーマットです。ウェブ上で広く利用されており、透明度（アルファチャンネル）をサポートし、特許フリーであることが大きな利点です。PNG画像は、チャンクと呼ばれるデータブロックの集まりで構成され、画像データ自体は通常、Deflateアルゴリズムで圧縮されます。

*   **インターレース (Adam7アルゴリズム)**:
    インターレースは、画像データを複数回に分けて転送・描画することで、画像全体が徐々に鮮明になっていくように見せる技術です。これにより、低速なネットワーク環境でもユーザーは画像の全体像を早期に把握できます。PNGではAdam7アルゴリズムが採用されており、画像を7つのパスに分割します。各パスは、元の画像から特定のピクセルを抽出して構成されるサブ画像であり、これらのパスが順番にデコードされることで、最終的な画像が再構築されます。
    Adam7アルゴリズムのパスの例:
    *   パス1: 8x8のブロックの左上隅のピクセル
    *   パス2: 8x8のブロックの2列目と4行目のピクセル
    *   ...
    *   パス7: 残りのすべてのピクセル

*   **PNGフィルタリング**:
    PNG画像データは、Deflate圧縮される前に、圧縮効率を高めるための「フィルタリング」処理が施されます。フィルタリングは、各スキャンライン（画像の1行分のピクセルデータ）に対して適用され、隣接するピクセルとの差分を取ることで、データの冗長性を減らします。PNGには以下の5種類の標準フィルタがあります。
    *   None (0): フィルタなし
    *   Sub (1): 左隣のピクセルとの差分
    *   Up (2): 上のピクセルとの差分
    *   Average (3): 左と上のピクセルの平均との差分
    *   Paeth (4): 左、上、左上のピクセルから最も近い予測値との差分
    各スキャンラインの先頭には、そのスキャンラインに適用されたフィルタの種類を示す1バイトの「フィルタタイプバイト」が付与されます。

*   **スキャンラインとフィルタバイト**:
    PNGの画像データ（IDATチャンク内）は、フィルタタイプバイトとそれに続くピクセルデータのシーケンスで構成されます。インターレースされたPNGの場合、各インターレースパスは独立した画像として扱われるため、各パス内の各スキャンラインにも個別のフィルタタイプバイトが付与されます。

## 技術的詳細

このコミットが対処する問題は、インターレースされたPNG画像のデコードにおけるエッジケースに起因します。Adam7インターレースアルゴリズムは、元の画像の寸法によっては、一部のパスが幅または高さがゼロになることがあります。例えば、非常に細長い画像や小さい画像の場合、特定のパスには実際に描画すべきピクセルが存在しないことがあります。

Goの `image/png` デコーダは、インターレースパスを処理する際に、各パスを独立した画像として扱い、そのパスの幅と高さを計算します。しかし、以前の実装では、計算された幅または高さがゼロであるにもかかわらず、そのパスのスキャンラインが存在すると仮定して、フィルタタイプバイトを読み込もうとしていました。

フィルタタイプバイトは、データストリームの先頭に1バイトとして存在し、その後にピクセルデータが続きます。もしパスの幅や高さがゼロであれば、そのパスにはスキャンラインが存在しないため、フィルタタイプバイトも存在しないはずです。それにもかかわらずデコーダが読み込みを試みると、以下のような問題が発生する可能性がありました。

1.  **`io.EOF` エラー**: データストリームの終端に達しているにもかかわらず、存在しないバイトを読み込もうとしてエラーが発生する。
2.  **不正なデータ読み込み**: フィルタタイプバイトとして、本来は別のデータ（次のチャンクのヘッダなど）であるはずのバイトを誤って解釈してしまう。
3.  **デコーダのクラッシュ**: 読み込んだ不正なフィルタタイプバイトに基づいて、存在しないメモリ領域にアクセスしようとしたり、不正な計算を行ったりすることで、プログラムがクラッシュする。

このコミットは、`readImagePass` 関数内でパスの幅と高さを計算した後、それらがゼロであるかどうかを明示的にチェックすることで、この問題を解決します。幅または高さがゼロの場合、そのパスは空であると判断し、フィルタバイトの読み込みやピクセルデータの処理をスキップして早期に終了します。これにより、デコーダは不正なPNGデータに対してより堅牢になります。

## コアとなるコードの解説

### `src/image/png/reader.go` の変更点

1.  **`readImagePass` 関数内の変更**:
    ```go
    // ... (既存のコード) ...
    if d.interlace {
        // Add the multiplication factor and subtract one, effectively rounding up.
        width = (width - p.xOffset + p.xFactor - 1) / p.xFactor
        height = (height - p.yOffset + p.yFactor - 1) / p.yFactor
        // A PNG image can't have zero width or height, but for an interlaced
        // image, an individual pass might have zero width or height. If so, we
        // shouldn't even read a per-row filter type byte, so return early.
        if width == 0 || height == 0 {
            return nil, nil
        }
    }
    // ... (既存のコード) ...
    ```
    この変更がこのコミットの核心です。インターレースされた画像の場合 (`d.interlace` が `true`)、現在のパスの `width` と `height` が計算された後、`if width == 0 || height == 0` という条件でチェックされます。もしどちらかがゼロであれば、そのパスは空であると判断され、`return nil, nil` によって早期に処理を終了します。これにより、存在しないスキャンラインのフィルタタイプバイトを読み込もうとする試みが回避されます。`nil` が返されることで、このパスには有効な画像データがないことが呼び出し元に伝えられます。

2.  **`decode` 関数内の変更**:
    ```go
    // ... (既存のコード) ...
    for pass := 0; pass < 7; pass++ {
        // ... (既存のコード) ...
        imagePass, err := d.readImagePass(r, pass, false)
        if err != nil {
            return nil, err
        }
        if imagePass != nil { // この行が追加された
            d.mergePassInto(img, imagePass, pass)
        }
    }
    // ... (既存のコード) ...
    ```
    `readImagePass` が `nil, nil` を返す可能性があるため、`decode` 関数では `imagePass` が `nil` でない場合にのみ `d.mergePassInto` を呼び出すように変更されました。これは、空のパスから返された `nil` の画像オブジェクトをマージしようとすることで発生する可能性のあるパニックやエラーを防ぐためのガードです。

### `src/image/png/reader_test.go` の変更点

```go
// ... (既存のテストコード) ...

func TestInterlaced(t *testing.T) {
    a, err := readPNG("testdata/gray-gradient.png")
    if err != nil {
        t.Fatal(err)
    }
    b, err := readPNG("testdata/gray-gradient.interlaced.png")
    if err != nil {
        t.Fatal(err)
    }
    if !reflect.DeepEqual(a, b) {
        t.Fatalf("decodings differ:\nnon-interlaced:\n%#v\ninterlaced:\n%#v", a, b)
    }
}

// ... (既存のテストコード) ...
```
`TestInterlaced` という新しいテスト関数が追加されました。このテストは、非インターレースのPNG画像 (`gray-gradient.png`) と、それと視覚的に同じ内容を持つインターレースされたPNG画像 (`gray-gradient.interlaced.png`) をそれぞれデコードします。そして、`reflect.DeepEqual` を使用して、両者のデコード結果が完全に一致することを確認します。
このテストの目的は、インターレース処理が正しく機能し、特に空のパスの処理が、最終的な画像データに悪影響を与えないことを検証することです。これにより、バグ修正が意図しない副作用を引き起こしていないことを保証します。

## 元コミット内容

`net/internal/socktest: new package`

このコミットは、ソケットテストのためのユーティリティを提供する `socktest` パッケージを新規に導入します。

このパッケージは、`net` パッケージ内のテストケースが、宛先アドレスが解決可能/発見可能であるにもかかわらず、ネットワーク層でルーティング不可能/到達不可能であるといった、複雑なネットワーク条件をシミュレートすることを可能にします。これらの条件は、タイムアウト機能や複数のアドレスファミリーのテストに必要とされます。

## 変更の背景

Go言語の `net` パッケージは、ネットワークI/Oのための移植性の高いインターフェースを提供しており、その堅牢性は非常に重要です。ネットワークプログラミングにおいては、正常な通信だけでなく、様々な異常系やエッジケースを考慮したテストが不可欠です。特に、以下のような状況をシミュレートすることは、実際のネットワーク環境での挙動を正確に検証するために重要です。

*   **到達不可能なホスト**: DNS解決はできるが、IP層でルーティングできない、またはファイアウォールによってブロックされている場合。
*   **タイムアウト**: ネットワークの遅延やパケットロスによって、接続やデータ送受信が一定時間内に完了しない場合。
*   **複数のアドレスファミリー**: IPv4とIPv6の両方に対応するアプリケーションが、それぞれの環境で正しく動作するかどうか。

しかし、これらの複雑なネットワーク条件を実際の環境で再現することは困難であり、テストの自動化や再現性を阻害します。従来のテスト手法では、OSのネットワーク設定を変更したり、特殊なネットワークツールを使用したりする必要があり、テスト環境の構築と管理が煩雑でした。

このコミットで導入される `net/internal/socktest` パッケージは、Goの `net` パッケージの内部テストハーネスとして機能し、ソケットシステムコールをインターセプトして、これらの複雑なシナリオをプログラム的にシミュレートすることを目的としています。これにより、`net` パッケージのテストカバレッジと信頼性を向上させ、より堅牢なネットワーク機能を提供するための基盤を強化します。

## 前提知識の解説

このコミットの理解には、以下の概念に関する知識が役立ちます。

*   **ソケット (Socket)**: ネットワーク通信のエンドポイントを抽象化したものです。アプリケーションはソケットを通じてデータを送受信します。Go言語では、`net` パッケージがソケット操作のための高レベルなインターフェースを提供しています。
*   **システムコール (System Call)**: オペレーティングシステムが提供するサービスを、ユーザー空間のプログラムが利用するためのインターフェースです。ネットワーク操作（ソケットの作成、接続、データの送受信、クローズなど）の多くは、内部的にOSのシステムコールを呼び出しています。例えば、Unix系システムでは `socket()`, `connect()`, `send()`, `recv()`, `close()` などが該当します。
*   **アドレスファミリー (Address Family)**: ネットワークアドレスの種類を識別するための定数です。例えば、`syscall.AF_INET` はIPv4、`syscall.AF_INET6` はIPv6を表します。
*   **ソケットタイプ (Socket Type)**: ソケットの通信特性を定義します。`syscall.SOCK_STREAM` はTCPのような信頼性の高いストリーム通信、`syscall.SOCK_DGRAM` はUDPのようなデータグラム通信を表します。
*   **プロトコル (Protocol)**: 通信プロトコルを識別する番号です。`syscall.IPPROTO_TCP` はTCP、`syscall.IPPROTO_UDP` はUDPを表します。
*   **内部パッケージ (`internal` package)**: Go言語の特殊なパッケージパスです。`internal` ディレクトリ内のパッケージは、その親ディレクトリのパッケージからのみインポート可能です。つまり、`net/internal/socktest` は `net` パッケージ内からのみ使用でき、外部のGoプログラムからは直接インポートできません。これは、ライブラリの内部実装の詳細を隠蔽し、APIの安定性を保つためのGoの設計原則です。
*   **テストハーネス (Test Harness)**: ソフトウェアテストにおいて、テスト対象のコンポーネントを実行し、テストケースを適用し、結果を検証するためのフレームワークや環境のことです。`socktest` は `net` パッケージのテストハーネスの一部として機能します。
*   **ネットワーク層での到達可能性**: ネットワーク通信は複数の層（レイヤー）で構成されます。IPアドレスの解決（DNS）はアプリケーション層やトランスポート層に近い概念ですが、実際にそのIPアドレスを持つホストにパケットが到達できるかどうかは、ネットワーク層（IP層）でのルーティングやファイアウォール設定に依存します。`socktest` は、このネットワーク層での到達可能性をシミュレートすることを目指しています。

## 技術的詳細

`net/internal/socktest` パッケージは、Goの `net` パッケージが内部的に使用するソケット関連のシステムコールをフック（横取り）し、その挙動を制御するためのメカニズムを提供します。これにより、テスト中に特定のシステムコールが失敗したり、遅延したりする状況を意図的に作り出すことができます。

主要なコンポーネントは以下の通りです。

1.  **`Switch` 構造体**:
    *   このパッケージの核となる構造体で、ソケットシステムコールの呼び出しパスを切り替えるためのスイッチとして機能します。
    *   `fltab` (filter table): `FilterType` に応じた `Filter` 関数を格納するマップです。
    *   `sotab` (socket table): ソケットディスクリプタ（またはハンドル）と、それに対応する `Status` 情報を格納するマップです。
    *   `stats`: ソケットのオープン、クローズ、接続、受け入れなどの統計情報を記録します。
    *   `sync.Once`, `sync.RWMutex`: 並行処理における安全性を確保するための同期プリミティブです。

2.  **`Cookie` 型**:
    *   ソケットの3つの主要な属性（アドレスファミリー、ソケットタイプ、プロトコル番号）を単一の `uint64` 値にパックしたものです。これにより、ソケットを一意に識別し、統計情報やフィルタリングのキーとして使用できます。

3.  **`Status` 構造体**:
    *   個々のソケットの状態を表します。`Cookie` に加えて、システムコール実行時のエラー (`Err`) や、`SO_ERROR` オプションで取得できるソケットのエラー状態 (`SocketErr`) を保持します。

4.  **`FilterType` 列挙型**:
    *   どのソケットシステムコールに対してフィルタを適用するかを識別します。例えば、`FilterSocket` は `socket()` システムコール、`FilterConnect` は `connect()` システムコールに対応します。

5.  **`Filter` および `AfterFilter` 関数型**:
    *   `Filter`: システムコールが実行される「前」に呼び出される関数です。`*Status` オブジェクトを受け取り、`AfterFilter` とエラーを返します。エラーを返すと、システムコールの実行がキャンセルされます。
    *   `AfterFilter`: システムコールが実行された「後」に呼び出される関数です。`*Status` オブジェクトを受け取り、エラーを返します。

6.  **システムコールラッパー**:
    *   `Switch` 構造体には、`syscall` パッケージの対応する関数をラップしたメソッド（例: `Socket`, `Close`, `Connect`, `Accept`, `GetsockoptInt`）が含まれています。これらのラッパーメソッドは、実際のシステムコールを呼び出す前後に、登録された `Filter` および `AfterFilter` を適用します。
    *   プラットフォーム固有の実装 (`sys_unix.go`, `sys_windows.go`, `sys_cloexec.go`) があり、それぞれのOSのシステムコールを適切にラップしています。

このメカニズムにより、`net` パッケージのテストコードは、`socktest.Switch` を介してソケット操作を行うことで、特定のシステムコールが失敗するように設定したり、特定の条件でエラーを注入したりすることが可能になります。例えば、`FilterConnect` を設定して、`connect()` システムコールが常に `ECONNREFUSED` エラーを返すようにシミュレートすることで、接続拒否のシナリオをテストできます。

## コアとなるコードの解説

`src/net/internal/socktest/switch.go` に定義されている `Switch` 構造体と、それを操作するメソッドがこのパッケージの核心です。

```go
// A Switch represents a callpath point switch for socket system
// calls.
type Switch struct {
	once sync.Once

	fmu   sync.RWMutex
	fltab map[FilterType]Filter // フィルタ関数を格納するマップ

	smu   sync.RWMutex
	sotab Sockets               // ソケットディスクリプタとStatusを格納するマップ
	stats stats                 // ソケット統計情報
}

// Set deploys the socket system call filter f for the filter type t.
func (sw *Switch) Set(t FilterType, f Filter) {
	sw.once.Do(func() { switchInit(sw) }) // 初回呼び出し時に初期化
	sw.fmu.Lock()
	sw.fltab[t] = f // 指定されたFilterTypeにフィルタ関数を登録
	sw.fmu.Unlock()
}
```

`Switch.Set` メソッドは、特定の `FilterType` (例: `FilterSocket`, `FilterConnect`) に対して、カスタムの `Filter` 関数を登録するために使用されます。これにより、テストコードは特定のシステムコールの挙動を動的に変更できます。

`src/net/internal/socktest/sys_unix.go` (Unix系) や `src/net/internal/socktest/sys_windows.go` (Windows系) にあるシステムコールラッパーの例を見てみましょう。

```go
// Socket wraps syscall.Socket.
func (sw *Switch) Socket(family, sotype, proto int) (s int, err error) {
	so := &Status{Cookie: cookie(family, sotype, proto)} // 新しいStatusオブジェクトを作成
	sw.fmu.RLock()
	f, _ := sw.fltab[FilterSocket] // FilterSocketに対応するフィルタを取得
	sw.fmu.RUnlock()

	af, err := f.apply(so) // システムコール実行前のフィルタを適用
	if err != nil {
		return -1, err // フィルタがエラーを返したら、システムコールは実行されない
	}
	s, so.Err = syscall.Socket(family, sotype, proto) // 実際のシステムコールを呼び出し
	if err = af.apply(so); err != nil { // システムコール実行後のフィルタを適用
		if so.Err == nil {
			syscall.Close(s) // 後処理フィルタがエラーを返した場合、ソケットをクローズ
		}
		return -1, err
	}

	if so.Err != nil {
		return -1, so.Err // システムコール自体がエラーを返した場合
	}
	sw.smu.Lock()
	nso := sw.addLocked(s, family, sotype, proto) // 新しいソケットをsotabに追加
	sw.stats.getLocked(nso.Cookie).Opened++ // 統計情報を更新
	sw.smu.Unlock()
	return s, nil
}
```

この `Socket` メソッドのフローは、他の `Connect`, `Close`, `Accept`, `GetsockoptInt` などのラッパーメソッドでも同様です。

1.  **`Status` オブジェクトの作成**: 現在のソケット操作に関する情報（アドレスファミリー、ソケットタイプ、プロトコルなど）を含む `Status` オブジェクトが作成されます。
2.  **前処理フィルタの適用**: `Switch.fltab` から対応する `Filter` 関数が取得され、`f.apply(so)` を通じて実行されます。このフィルタがエラーを返した場合、実際のシステムコールは実行されずに、そのエラーが呼び出し元に返されます。これにより、システムコールを「失敗させる」シナリオをシミュレートできます。
3.  **実際のシステムコール呼び出し**: `syscall.Socket` (または他の `syscall` 関数) が呼び出され、その結果が `s` と `so.Err` に格納されます。
4.  **後処理フィルタの適用**: `af.apply(so)` を通じて `AfterFilter` が実行されます。これもエラーを返すことができ、その場合、システムコールの結果が上書きされる可能性があります。
5.  **ソケット状態の更新と統計**: システムコールが成功した場合、新しいソケットディスクリプタが `Switch.sotab` に追加され、`stats` が更新されます（例: `Opened` カウンタのインクリメント）。

この一連の処理により、`net` パッケージのテストは、実際のネットワーク環境に依存することなく、様々なソケット操作の成功/失敗、タイムアウト、エラー注入といった複雑なシナリオを再現し、コードの堅牢性を検証することが可能になります。

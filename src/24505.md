## 変更の背景

このコミットの背景には、Go言語の公式仕様書に記載されているコード例の正確性と明確性を向上させるという目的があります。コミットメッセージによると、これらの修正はPeter Olsen氏からの提案に基づいており、GitHub issue #11964を解決するものです。仕様書は言語の規範的な定義であるため、そこに掲載されるコード例は完全に正確であり、誤解を招かないものである必要があります。特に、`fmt.Sprintf`のフォーマット指定子の使用法、チャネル操作のセマンティクス、およびGoのメソッド呼び出し規則は、Goプログラミングにおいて重要な概念であり、これらの例が不正確であると、学習者や開発者に混乱を招く可能性があります。このコミットは、これらの潜在的な問題を解消し、仕様書の品質を向上させるために実施されました。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語に関する前提知識が必要です。

1.  **Go言語の仕様書 (The Go Programming Language Specification)**: Go言語の構文、セマンティクス、および標準ライブラリの動作を定義する公式文書です。Go言語の「真実の源」であり、言語のあらゆる側面について権威ある情報を提供します。このコミットは、この仕様書自体を修正しています。
2.  **`fmt.Sprintf` とフォーマット動詞**: `fmt` パッケージは、Go言語におけるフォーマットI/Oを提供します。`Sprintf` 関数は、フォーマット指定子（フォーマット動詞）を使用して文字列を生成します。
    *   `%d`: 整数値を10進数でフォーマットします。
    *   `%+d`: 整数値を10進数でフォーマットし、常に符号（正の場合は`+`、負の場合は`-`）を表示します。
3.  **Go言語のメソッドとレシーバ**: Goのメソッドは、特定の型に関連付けられた関数です。メソッドはレシーバ（メソッドが操作する値）を持ち、レシーバは値型またはポインタ型にすることができます。
    *   **値レシーバ**: メソッドがレシーバのコピーを受け取ります。メソッド内でレシーバのフィールドを変更しても、元の値には影響しません。
    *   **ポインタレシーバ**: メソッドがレシーバへのポインタを受け取ります。メソッド内でレシーバのフィールドを変更すると、元の値も変更されます。
    *   **メソッド呼び出し規則**: Goでは、値型の変数に対してポインタレシーバを持つメソッドを呼び出す場合、コンパイラは自動的に変数のアドレスを取得してポインタを渡します（例: `t.M()` は `(&t).M()` と解釈される）。同様に、ポインタ型の変数に対して値レシーバを持つメソッドを呼び出す場合、コンパイラは自動的にポインタをデリファレンスします（例: `p.M()` は `(*p).M()` と解釈される）。
    *   **埋め込みフィールド (Embedded Fields)**: Goの構造体は、他の構造体やインターフェースを匿名フィールドとして埋め込むことができます。これにより、埋め込まれた型のメソッドが外側の構造体から直接呼び出せるようになります。
4.  **Go言語のチャネル (Channels)**: Goのチャネルは、ゴルーチン間で値を送受信するための通信メカニズムです。
    *   `<-chan int`: 読み取り専用のチャネル型。
    *   `for i := range c`: チャネル `c` から値が送信されるたびにループを反復します。チャネルが閉じられるとループは終了します。
    *   `x := <-c`: チャネル `c` から値を読み取ります。チャネルに値がない場合、値が送信されるまでゴルーチンはブロックされます。

## 技術的詳細

このコミットで行われた技術的な変更は、主にGo言語の仕様書内のコード例の正確性と一貫性を向上させることに焦点を当てています。

1.  **仕様書のバージョン日付の更新**:
    *   `Subtitle` の日付が "Version of July 30, 2015" から "Version of July 31, 2015" へと更新されました。これは、コミットが適用された日付を反映する単純なメタデータの変更です。

2.  **`fmt.Sprintf` のフォーマット指定子の修正**:
    *   変更前: `fmt.Sprintf("GMT+%dh", tz)`
    *   変更後: `fmt.Sprintf("GMT%+dh", tz)`
    *   この変更は、`fmt.Sprintf` のフォーマット動詞 `%d` に `+` フラグを追加したものです。`%d` は整数を10進数で表示しますが、正の数には符号を表示しません。`%+d` を使用すると、正の数にも明示的に `+` 符号が表示されるようになります（例: `GMT+5h`）。これにより、`TimeZone` の `String()` メソッドが常に符号付きのオフセットを返すようになり、出力の一貫性が向上します。例えば、`tz` が `5` の場合、変更前は `GMT+5h` となりますが、`tz` が `0` の場合、変更前は `GMT0h` となり、符号がありませんでした。変更後は `GMT+0h` となり、常に符号が表示されます。

3.  **不正確なチャネル操作の例の置き換え**:
    *   元のコード例 (`func findMarker(c <-chan int) int`) は、チャネルからの読み取りに関する誤解を招く可能性がありました。
        ```go
        func findMarker(c <-chan int) int {
            for i := range c { // ここでチャネルから値を読み取り、iに代入
                if x := <-c; isMarker(x) { // ここで再度チャネルから値を読み取ろうとしている
                    return x
                }
            }
            // invalid: missing return statement.
        }
        ```
        このコードでは、`for i := range c` がチャネル `c` から値を読み取って `i` に代入しているにもかかわらず、ループ本体内で `x := <-c` と再度チャネルから値を読み取ろうとしています。これは、意図しない動作やデッドロックを引き起こす可能性があり、Goのチャネル操作の正しい例としては不適切でした。
    *   この例は、より適切で一般的な `func IndexRune(s string, r rune) int` という関数に置き換えられました。
        ```go
        func IndexRune(s string, r rune) int {
            for i, c := range s {
                if c == r {
                    return i
                }
            }
            // invalid: missing return statement
        }
        ```
        この新しい例は、文字列内のルーンを検索する一般的なパターンを示しており、`for` ループの後に `return` ステートメントがない場合にコンパイラが「missing return statement」エラーを報告する状況を正確に示しています。これにより、「return文の欠落」という仕様書のポイントをより明確に説明できるようになりました。

4.  **メソッド呼び出しの例の修正**:
    *   Goのメソッド呼び出し、特にポインタレシーバと埋め込みフィールドに関する例が修正されました。Goでは、値型の変数に対してポインタレシーバを持つメソッドを呼び出す場合、コンパイラは自動的に変数のアドレスを取得します。また、埋め込みフィールドのメソッドは、外側の構造体から直接呼び出すことができます。これらの規則を正確に反映するように例が調整されました。
    *   変更前後の具体的な差分は以下の通りです。
        ```diff
        -p.M2()       // p.M2()              M2 expects *T2 receiver
        +p.M0()       // ((*p).T0).M0()      M0 expects *T0 receiver
        p.M1()       // ((*p).T1).M1()      M1 expects T1 receiver
        -p.M0()       // ((&(*p).T0)).M0()   M0 expects *T0 receiver, see section on Calls
        +p.M2()       // p.M2()              M2 expects *T2 receiver
        +t.M2()       // (&t).M2()           M2 expects *T2 receiver, see section on Calls
        ```
    *   これらの変更は、特にポインタレシーバを持つメソッドが、値型の変数から呼び出されたときにどのように動作するか、そして埋め込みフィールドを介したメソッドの解決がどのように行われるかを、より正確に説明するためのものです。例えば、`p.M0()` の呼び出しが `((*p).T0).M0()` と解釈されることを明示することで、ポインタのデリファレンスと埋め込みフィールドへのアクセスがどのように組み合わされるかを明確にしています。また、`t.M2()` の例を追加することで、値型の変数 `t` からポインタレシーバを持つメソッド `M2` を呼び出す際に、コンパイラが暗黙的に `&t` を渡すことを示しています。

これらの修正は、Go言語の仕様書が提供する情報が常に最新かつ正確であることを保証し、Goプログラマーが言語のセマンティクスを正しく理解するのに役立ちます。

## コアとなるコードの解説

上記の変更箇所は、Go言語の仕様書における重要なセクションを改善しています。

1.  **仕様書の日付更新**: これは、仕様書が最後に更新された日付を正確に反映するための形式的な変更です。読者に対して、参照している仕様書のバージョンがいつのものであるかを明確に示します。

2.  **`fmt.Sprintf` のフォーマット指定子修正**:
    *   `fmt.Sprintf("GMT+%dh", tz)` から `fmt.Sprintf("GMT%+dh", tz)` への変更は、`fmt` パッケージのフォーマット動詞の正確な使用法を示しています。`%+d` は、数値が正の場合でも常に符号（`+`）を表示することを保証します。これにより、`TimeZone` の `String()` メソッドの出力が、`GMT+5h` や `GMT+0h` のように、常に符号付きの形式で一貫して表示されるようになります。これは、APIの出力の一貫性を保つ上で重要であり、仕様書がこの細部まで正確に記述されていることは、言語の厳密性を示すものです。

3.  **チャネル操作の例の置き換え**:
    *   元の `findMarker` 関数の例は、`for i := range c` と `x := <-c` の両方でチャネルから読み取ろうとするという、Goのチャネル操作の誤ったパターンを示していました。`range` を使ったチャネルからの読み取りは、チャネルが閉じるまで値を順次受け取りますが、ループ内でさらに `<-c` を行うと、次の値が来るまでブロックされるか、チャネルが閉じている場合はゼロ値を受け取ることになります。これは、意図しない動作やデッドロックを引き起こす可能性があり、仕様書の例としては不適切でした。
    *   新しい `IndexRune` 関数の例は、文字列をイテレートし、特定のルーンを検索する一般的なGoのパターンを示しています。この関数の後に `// invalid: missing return statement` というコメントを付記することで、関数がすべての実行パスで値を返すことを保証する必要があるというGoのコンパイラの要件を明確に示しています。この変更により、仕様書は「return文の欠落」という概念をより正確かつ理解しやすい形で説明できるようになりました。

4.  **メソッド呼び出しの例の修正**:
    *   Goのメソッド呼び出し規則、特にポインタレシーバと埋め込みフィールドに関する部分は、初心者にとって混乱しやすいことがあります。このコミットでは、これらの規則をより正確に反映するように例が調整されました。
    *   `p.M0() // ((*p).T0).M0() M0 expects *T0 receiver` のように、ポインタ `p` が持つ埋め込みフィールド `T0` のメソッド `M0` を呼び出す際に、コンパイラがどのようにポインタのデリファレンスとフィールドアクセスを解決するかを明示しています。
    *   `t.M2() // (&t).M2() M2 expects *T2 receiver, see section on Calls` の追加は、値型の変数 `t` からポインタレシーバを持つメソッド `M2` を呼び出す際に、コンパイラが自動的に `t` のアドレス `&t` を取得してメソッドに渡すというGoの便利な機能を示しています。
    *   これらの修正は、Goのメソッド呼び出しのセマンティクスを正確に理解するために不可欠であり、仕様書がこれらの詳細を明確にすることで、開発者がより堅牢で正しいGoコードを書くのに役立ちます。

これらの変更は、Go言語の仕様書が提供する情報が常に最新かつ正確であることを保証し、Goプログラマーが言語のセマンティクスを正しく理解するのに役立ちます。

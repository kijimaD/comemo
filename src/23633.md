# [インデックス 23633] ファイルの概要

このコミットは、Goコンパイラの内部で使用される抽象構文木（AST）の`Node`構造体から、`Nincr`、`Nelse`、および`Initplan`の3つのフィールドを削除するものです。これにより、`Node`構造体のメモリフットプリントが削減され、コンパイラのパフォーマンス向上が期待されます。

## 変更の背景

Goコンパイラは、ソースコードを解析して抽象構文木（AST）を構築し、それに対して様々な最適化やコード生成を行います。ASTの各ノードは`Node`構造体で表現されます。この`Node`構造体はコンパイラ全体で頻繁に利用されるため、そのサイズはコンパイラのメモリ使用量とパフォーマンスに大きな影響を与えます。

このコミットの背景には、`Node`構造体のメモリフットプリントを削減し、コンパイラの効率を向上させるという目的があります。特に、`Nincr`、`Nelse`、`Initplan`といったフィールドは、特定の種類のASTノードでのみ使用され、他の多くのノードでは未使用のままメモリを占有していました。このような「スパースな」フィールドを構造体から削除し、より効率的な方法で管理することで、全体のメモリ使用量を削減し、コンパイラの実行速度を向上させることができます。コミットメッセージにある`$ sizeof -p cmd/compile/internal/gc Node`の出力「Node 288」は、この最適化がメモリ使用量に焦点を当てていることを明確に示しています。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

*   **Goコンパイラの構造**: Goコンパイラは、主に以下のフェーズで構成されます。
    *   **字句解析 (Lexing)**: ソースコードをトークンに分割します。
    *   **構文解析 (Parsing)**: トークンから抽象構文木（AST）を構築します。
    *   **型チェック (Type Checking)**: ASTの各ノードの型を検証します。
    *   **中間表現 (IR) 生成**: ASTをより低レベルの中間表現に変換します。
    *   **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用します。
    *   **コード生成 (Code Generation)**: 最適化された中間表現から機械語コードを生成します。
*   **抽象構文木 (AST)**: プログラムのソースコードの抽象的な構文構造を木構造で表現したものです。Goコンパイラでは、`cmd/compile/internal/gc`パッケージ内の`Node`構造体がASTの各ノードを表します。
*   **`Node`構造体**: GoコンパイラのASTにおける基本的な構成要素です。`if`文、`for`ループ、変数宣言、関数呼び出しなど、プログラムのあらゆる要素が`Node`として表現されます。`Node`構造体には、そのノードの種類（`Op`フィールド）、子ノードへのポインタ（`Left`, `Right`, `Nbody`など）、型情報、シンボル情報など、様々な情報が含まれます。
*   **メモリフットプリントとコンパイラパフォーマンス**: コンパイラは大量のASTノードをメモリ上に保持するため、`Node`構造体のサイズが小さいほど、メモリ使用量が削減され、キャッシュ効率が向上し、結果としてコンパイル速度が向上します。
*   **スパースなデータ構造の最適化**: 多くのインスタンスで特定のフィールドがほとんど使用されない場合、そのフィールドを構造体内に直接持つことはメモリの無駄になります。このような場合、フィールドを構造体から外し、必要に応じてマップなどの別のデータ構造で管理する手法が用いられます。

## 技術的詳細

このコミットは、`Node`構造体から以下の3つのフィールドを削除し、その機能を再設計することでメモリ効率を向上させています。

1.  **`Node.Nincr`の削除**:
    *   `Nincr`は主に`for`ループのインクリメント部分（例: `for i := 0; i < N; i++` の `i++`）を表すために使用されていました。
    *   このコミットでは、`OFOR`（forループ）ノードの場合、既存の`Node.Right`フィールドが`Nincr`の役割を兼ねるように変更されました。これは、`OFOR`ノードにおいて`Node.Right`が他の目的で使用されていなかったか、あるいはその用途が`Nincr`と統合可能であったことを示唆しています。
    *   これにより、`Node`構造体から`Nincr`フィールド分のメモリが削減されます。

2.  **`Node.Nelse`の削除**:
    *   `Nelse`は主に`if-else`文の`else`ブロックを表すために使用されていました。
    *   このコミットでは、`OIF`（if文）ノードの場合、既存の`Node.Rlist`フィールドが`Nelse`の役割を兼ねるように変更されました。`Rlist`は通常、戻り値のリストなどに使用されますが、`if`文のコンテキストでは`else`ブロックのステートメントリストとして再利用されます。
    *   これにより、`Node`構造体から`Nelse`フィールド分のメモリが削減されます。

3.  **`Node.Initplan`の削除**:
    *   `Initplan`は、複合リテラル（例: `[]int{1, 2, 3}` や `struct{A int}{A: 1}`）の初期化計画を保持するために使用されていました。
    *   複合リテラルはASTノード全体のごく一部であり、すべての`Node`が`Initplan`を持つ必要はありませんでした。そのため、`Initplan`フィールドを`Node`構造体内に直接持つことは、多くのノードにとって無駄なメモリ消費となっていました。
    *   このコミットでは、`Initplan`フィールドは`Node`構造体から削除され、代わりに`initplans`というグローバルな`map[*Node]*InitPlan`に移動されました。これにより、`Initplan`が必要な`Node`に対してのみ、マップを介して動的に割り当てられるようになり、メモリ使用量が大幅に削減されます。これは、スパースなデータ構造を最適化する一般的な手法です。

これらの変更は、コンパイラの様々なフェーズ（エスケープ解析、エクスポート、フォーマット、コード生成、インライン化、順序付け、競合検出、range文、select文、静的初期化、型チェック、ASTウォーク）に影響を与えますが、それぞれのフェーズで`Node`構造体のフィールド参照が新しいセマンティクスに合わせて更新されています。

## コアとなるコードの解説

*   **`syntax.go`における`Node`構造体の変更**:
    *   `Nincr *Node`、`Nelse *NodeList`、`Initplan *InitPlan`の各フィールドが`Node`構造体から削除されています。これにより、`Node`構造体のインスタンスが占めるメモリ量が直接的に削減されます。
    *   `Node`構造体のサイズが288バイトから減少したことがコミットメッセージで示されており、この変更がメモリ効率の向上に貢献していることがわかります。

*   **`go.y`における構文解析規則の変更**:
    *   `for_header`規則では、`Nincr`に割り当てられていた`$5`（for文の3番目の式、例: `i++`）が`$$.Right`に割り当てられるように変更されています。これは、`OFOR`ノードの`Right`フィールドがインクリメント式を保持する役割を担うようになったことを意味します。
    *   `if_stmt`規則では、`else`ブロックを表す`nn.N`が`n.Nelse`ではなく`n.Rlist`に割り当てられるように変更されています。これは、`OIF`ノードの`Rlist`フィールドが`else`ブロックのステートメントリストを保持する役割を担うようになったことを意味します。

*   **`sinit.go`における`Initplan`の管理変更**:
    *   `initplans = make(map[*Node]*InitPlan)`というグローバルマップが導入され、`Initplan`が`Node`構造体から独立して管理されるようになりました。
    *   `staticcopy`、`staticassign`、`initplan`、`addvalue`などの関数内で、`n.Initplan`への直接アクセスが`initplans[n]`へのアクセスに置き換えられています。
    *   `initplan`関数は、特定の`Node`に対して`InitPlan`が必要になった場合に、このマップに新しい`InitPlan`インスタンスを生成して格納する役割を担います。これにより、`Initplan`が必要ない`Node`は余分なメモリを消費しなくなります。

これらの変更は、GoコンパイラのAST表現をよりコンパクトにし、メモリ使用量を最適化するための重要なステップです。既存のフィールドを再利用したり、スパースなデータをマップに移動したりすることで、コードのセマンティクスを維持しつつ、コンパイラの全体的な効率を向上させています。

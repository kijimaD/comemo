## 変更の背景
このコミットは、Go言語の `net` パッケージにおける `TestDialTimeout` テストの不安定性（flakiness）を解消することを目的としています。特に、様々なプラットフォーム、とりわけWindows環境でのタイムアウト挙動の不整合が問題となっていました。

具体的には、以下のGoイシューがこの変更に関連しています。

*   **Issue 5380 / 5349 (net: on windows, net.Dial with udp times out immediately)**: これらのイシューは、Windows環境で `net.Dial` をUDP接続で使用した際に、即座にタイムアウトが発生するという問題点を指摘していました。これは、テストが期待するタイムアウト挙動と実際の挙動が異なる原因となっていました。
*   **Issue 3016 (isDomainName should be exported)**: このイシュー自体は `DialTimeout` と直接関係ありませんが、`src/net/dial_test.go` 内のコメントでWindowsでのタイムアウト問題に言及されており、このコミットがその側面も考慮している可能性があります。
*   **Issue 3307 (google/appengine: change managed VMs context to context.Context)**: このイシューは `net` パッケージとは無関係であり、このコミットとの直接的な関連性は低いと考えられます。
*   **Issue 3867 (net: Addr/LocalAddr on both TCPListener and UDPConn with wildcard address doesn't return proper address)**: このイシューは `net` パッケージに関連しますが、`DialTimeout` の挙動とは直接関係ありません。

主要な背景は、`TestDialTimeout` が特定の環境（特にWindows）で不安定であり、その原因が `net.Dial` のタイムアウト挙動のプラットフォーム依存性、特にUDP接続における即時タイムアウト問題（Issue 5380, 5349）にあったことです。このコミットは、テストの信頼性を向上させ、Goのネットワーク機能が様々なプラットフォームで一貫して動作することを保証するために行われました。

## 前提知識の解説

### `net.DialTimeout`
`net.DialTimeout` は、Go言語の `net` パッケージが提供する関数で、指定されたネットワークアドレスへの接続を試み、指定されたタイムアウト期間内に接続が確立されない場合にエラーを返す機能です。ネットワーク接続は、様々な要因（ネットワークの遅延、サーバーの応答なし、ファイアウォールなど）によって時間がかかったり、失敗したりする可能性があるため、タイムアウトを設定することはアプリケーションの応答性と堅牢性を保つ上で非常に重要です。

### `listenerBacklog`
`listenerBacklog` は、TCPリスナーが受け入れ待ち状態にできる接続の最大数を指します。オペレーティングシステムによって実装が異なり、通常は `listen()` システムコールの `backlog` 引数に対応します。この値を超えて接続要求が来ると、新しい接続は拒否されるか、キューで待機することになります。テストでは、このバックログを意図的に小さく設定することで、接続がタイムアウトするシナリオをシミュレートすることがあります。

### `socktest` パッケージ
`net/internal/socktest` パッケージは、Goの `net` パッケージの内部テストで使用されるユーティリティです。これは、ソケット操作（接続、読み書きなど）の挙動をフックし、テスト中に特定の条件（例えば、意図的な遅延やエラー）を注入することを可能にします。これにより、ネットワークの様々なエッジケースやエラーシナリオを再現し、テストの信頼性と網羅性を高めることができます。

### `testHookDialChannel`
`testHookDialChannel` は、`net` パッケージの内部で定義されているテスト用のフック関数です。これは、`dialChannel` 関数（Goの純粋なGo実装のダイヤルロジック）の内部で呼び出されます。このフックを使用することで、テスト中に `dialChannel` の特定のポイントで追加の処理（例えば、意図的な遅延）を挿入し、特定の競合状態やタイムアウトシナリオをシミュレートすることができます。これは、特にプラットフォーム間で挙動が異なる可能性のあるタイムアウトテストにおいて、テストの再現性を高めるために重要です。

### テストの不安定性（Flakiness）
テストの不安定性（Flakiness）とは、同じコードに対して同じテストを複数回実行した際に、成功と失敗が非決定的に混在する現象を指します。これは、テストが外部要因（ネットワークの遅延、OSのスケジューリング、リソースの競合など）に依存している場合や、テストロジックに競合状態が含まれている場合に発生しやすいです。不安定なテストは、開発者がコードの変更が実際にバグを修正したのか、あるいは新たなバグを導入したのかを判断することを困難にし、開発プロセスを遅延させます。

## 技術的詳細
このコミットの主要な目的は、`TestDialTimeout` の不安定性を解消し、特にWindows環境での `net.Dial` のタイムアウト挙動の不整合に対処することです。

以前の `TestDialTimeout` は、プラットフォームごとに異なるアプローチを取っていました。
*   **Linux**: `listenerBacklog` を小さく設定し、多数の接続を試みることで、カーネルのバックログを埋め、一部の接続がタイムアウトするシナリオを期待していました。
*   **Darwin (macOS), Plan 9, Windows**: 存在しないIPアドレス（例: `127.0.71.111:49151`）への接続を試みることで、タイムアウトを発生させていました。しかし、このアプローチはWindowsでタイムアウトが期待通りに発生しない（Issue 3016, 5380, 5349）という問題がありました。

このコミットでは、これらのプラットフォーム依存のテストロジックを廃止し、より堅牢でプラットフォームに依存しないテストメカニズムを導入しています。

### 新しいテストアプローチ
新しい `TestDialTimeout` は、以下の要素を組み合わせてテストの信頼性を高めています。

1.  **`testHookDialChannel` の活用**:
    *   `dial_gen.go` から `testingIssue5349` というテスト用のグローバル変数が削除され、代わりに `testHookDialChannel` という関数が導入されました。
    *   `hook_plan9.go` と `hook_windows.go` では、`testHookDialChannel` が `time.Sleep(time.Millisecond)` を実行するように設定されています。これにより、`dialChannel` が接続を試みる際に意図的な遅延が挿入され、タイムアウトシナリオを確実に再現できるようになります。
    *   `hook_unix.go` では、`testHookDialChannel` はデフォルトで何もしない関数 (`func() {}`) として定義されていますが、必要に応じてテストで上書き可能です。

2.  **`net/internal/socktest` パッケージの利用**:
    *   `timeout_test.go` の新しい `TestDialTimeout` では、`socktest` パッケージが導入されています。
    *   `socktest.FilterConnect` を使用して、接続試行時に意図的な遅延 (`2 * T`) とエラー (`errTimeout`) を注入します。これにより、実際のネットワーク状況に依存することなく、接続がタイムアウトする状況をプログラム的に制御できます。
    *   この `socktest` のフックは、Plan 9 と Windows 以外のプラットフォームで適用されます。Plan 9 と Windows では、`testHookDialChannel` を使用した遅延が主なメカニズムとなります。

### 変更のメリット
*   **プラットフォーム非依存性**: 以前のテストが抱えていたプラットフォームごとの挙動の違いによる不安定性を解消し、より一貫したテスト結果を提供します。
*   **テストの再現性**: `testHookDialChannel` と `socktest` を用いることで、ネットワークの遅延やエラーといった外部要因をテスト内でシミュレートできるようになり、テストの再現性が大幅に向上します。これにより、不安定なテストが減少し、開発者はコードの変更がもたらす影響をより正確に評価できるようになります。
*   **クリーンなテストコード**: 以前の `dial_test.go` にあった複雑なプラットフォームごとの条件分岐や、`listenerBacklog` を操作するようなテストロジックが削除され、テストコードがよりシンプルで理解しやすくなりました。

## コアとなるコードの解説

### `src/net/dial_gen.go` の変更
以前は `testingIssue5349` というブール変数を使って、テスト時に `dialChannel` 内に意図的な遅延を挿入していました。この変更では、より汎用的な `testHookDialChannel` 関数に置き換えられました。これにより、テストのフックポイントが明確になり、プラットフォーム固有の遅延注入ロジックを各 `hook_*.go` ファイルに集約できるようになりました。

```go
// 変更前
// var testingIssue5349 bool // used during tests
// ...
// if testingIssue5349 {
// 	time.Sleep(time.Millisecond)
// }

// 変更後
import "time" // timeパッケージのインポートは残る
// ...
// testHookDialChannel() // 新しいフック関数の呼び出し
```

### `src/net/dial_gen_test.go` の削除
このファイルは、`testingIssue5349` を `true` に設定するためだけに存在していました。`testHookDialChannel` の導入により、この変数が不要になったため、ファイル自体が削除されました。これにより、テストコードの冗長性が解消されました。

### `src/net/dial_test.go` から `TestDialTimeout` の削除
古い `TestDialTimeout` は、プラットフォームごとに異なる複雑なロジックを持っており、特にWindowsでの不安定性が問題でした。このテストは完全に削除され、より堅牢な新しいテストが `src/net/timeout_test.go` に実装されました。これにより、テストの関心事が分離され、コードの保守性が向上しました。

### `src/net/hook_plan9.go`, `src/net/hook_windows.go` の追加/変更
これらのファイルでは、`testHookDialChannel` が具体的な遅延処理を持つように定義されています。これは、Plan 9 と Windows 環境における `DialTimeout` のテストで、接続試行時に意図的な遅延を発生させることで、タイムアウトシナリオを確実にトリガーするために重要です。

```go
// src/net/hook_plan9.go (新規ファイル) および src/net/hook_windows.go (変更)
package net

import "time"

var testHookDialChannel = func() { time.Sleep(time.Millisecond) } // see golang.org/issue/5349
```

### `src/net/hook_unix.go` の変更
Unix系システムでは、`testHookDialChannel` はデフォルトで何もしない関数として定義されています。これは、Unix系システムでは `socktest` パッケージによるフックが主要なテストメカニズムとなるためです。

```go
// src/net/hook_unix.go
package net

// ...
var (
	testHookDialChannel = func() {} // see golang.org/issue/5349
	// ...
)
```

### `src/net/timeout_test.go` の新しい `TestDialTimeout`
このファイルに新しく追加された `TestDialTimeout` は、このコミットの核心部分です。
*   `const T = 100 * time.Millisecond` で基準となるタイムアウト時間を定義。
*   Plan 9 と Windows では、`testHookDialChannel` を一時的に上書きして、より長い遅延 (`2 * T`) を挿入します。これにより、`DialTimeout` が確実にタイムアウトするようにします。
*   その他のプラットフォームでは、`net/internal/socktest` パッケージの `socktest.FilterConnect` を使用します。このフィルターは、接続試行時に `2 * T` の遅延を挿入し、さらに `errTimeout` を返すことで、接続がタイムアウトする状況をシミュレートします。
*   `DialTimeout` を非同期で呼び出し、結果をチャネルで受け取ります。
*   `time.NewTimer` を使用して、テスト自体がハングアップしないように全体のタイムアウトを設定します。
*   返されたエラーが `net.Error` インターフェースを実装しており、かつ `Timeout()` メソッドが `true` を返すことを確認します。

```go
// src/net/timeout_test.go (抜粋)
func TestDialTimeout(t *testing.T) {
	const T = 100 * time.Millisecond

	switch runtime.GOOS {
	case "plan9", "windows":
		origTestHookDialChannel := testHookDialChannel
		testHookDialChannel = func() { time.Sleep(2 * T) }
		defer func() { testHookDialChannel = origTestHookDialChannel }()
		if runtime.GOOS == "plan9" {
			break
		}
		fallthrough // Windowsの場合、socktestも適用される
	default:
		// socktest.FilterConnect を設定し、接続試行時に遅延とエラーを注入
		sw.Set(socktest.FilterConnect, func(so *socktest.Status) (socktest.AfterFilter, error) {
			time.Sleep(2 * T)
			return nil, errTimeout
		})
		defer sw.Set(socktest.FilterConnect, nil)
	}

	ch := make(chan error)
	go func() {
		// 意図的にタイムアウトする接続を試みる
		c, err := DialTimeout("tcp", "127.0.0.1:0", T)
		if err == nil {
			err = fmt.Errorf("unexpectedly established: tcp:%s->%s", c.LocalAddr(), c.RemoteAddr())
			c.Close()
		}
		ch <- err
	}()
	tmo := time.NewTimer(3 * T)
	defer tmo.Stop()
	select {
	case <-tmo.C:
		t.Fatal("dial has not returned") // テストがハングアップした場合
	case err := <-ch:
		nerr, ok := err.(Error)
		if !ok {
			t.Fatalf("got %v; want error implements Error interface", err)
		}
		if !nerr.Timeout() {
			t.Fatalf("got %v; want timeout error", err)
		}
		// タイムアウトエラーが期待通りに発生したことを確認
	}
}
```

この新しいテストは、実際のネットワーク状態に依存することなく、プログラム的にタイムアウトシナリオを制御できるため、テストの信頼性と再現性が大幅に向上しました。

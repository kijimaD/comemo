# [インデックス 27292] ファイルの概要

このコミットは、GoコンパイラのAMD64 (x86-64) バックエンドにおける命令の書き換えルールを修正し、64ビット命令が32ビット符号付き定数オフセットしか受け付けないというx86アーキテクチャの制約を厳密に適用するものです。これにより、生成されるアセンブリコードの正確性と堅牢性が向上します。また、アセンブラがオフセットが命令に収まらない場合に失敗するよう変更され、コンパイルエラーがある場合にはそのアセンブラエラーを抑制するロジックも追加されています。

## 変更の背景

このコミットの主な背景は、x86-64アーキテクチャにおける命令の定数オフセットに関する制約です。多くの64ビットx86命令（特にメモリ操作に関連するもの）は、アドレス指定に際して、ベースレジスタやインデックスレジスタに加えて、32ビット符号付きの定数オフセットしか使用できません。これは、64ビットのアドレス空間全体を直接オフセットで指定できないことを意味します。

GoコンパイラのSSA (Static Single Assignment) バックエンドは、最適化とコード生成の過程で、高レベルの操作を低レベルの機械語命令に変換します。この変換プロセスにおいて、定数オフセットが32ビットの範囲を超える場合、コンパイラは複数の命令に分割したり、より複雑なアドレス指定モードを使用したりして対応する必要があります。

以前のGoコンパイラのSSA書き換えルールでは、この32ビット符号付き定数オフセットの制約が十分に厳密に適用されていなかった可能性があります。その結果、コンパイラが生成した中間表現（SSA値）が、最終的な機械語命令に変換される際に、ハードウェアの制約に違反するオフセットを持つ命令を生成しようとする問題が発生していました。これは、コンパイルエラーや、場合によっては不正なコード生成につながる可能性がありました。

Issue #14862は、この問題が顕在化した具体的なケースを報告しています。このコミットは、その問題を解決するために、SSA書き換えルールを修正し、アセンブラレベルでのチェックを強化することで、このアーキテクチャ上の制約を確実に遵守するようにしています。

## 前提知識の解説

### x86-64アーキテクチャとアドレス指定モード

x86-64 (AMD64) は、64ビットの汎用レジスタと64ビットのアドレス空間を持つCPUアーキテクチャです。しかし、メモリへのアクセスに使用される多くのアドレス指定モードでは、オフセット値として32ビット符号付き整数しか使用できません。
例えば、`MOV RAX, [RBX + 0x12345678]` のような命令では、`0x12345678` は32ビット符号付き整数として扱われます。この範囲は `-2^31` から `2^31 - 1` (約 -2GB から +2GB) です。もしオフセットがこの範囲を超える場合、例えば `0x100000000` (4GB) のような値は、単一の命令で直接アドレス指定できません。このような大きなオフセットを扱うには、オフセット値をレジスタにロードしてからそのレジスタを使用するなど、複数の命令が必要になります。

### GoコンパイラのSSA (Static Single Assignment)

Goコンパイラは、コード生成の過程でSSA形式の中間表現を使用します。SSAは、各変数が一度だけ代入されるようにする表現形式で、データフロー解析や最適化を容易にします。
SSAバックエンドでは、GoのソースコードがSSA値のグラフに変換され、その後、ターゲットアーキテクチャ（この場合はAMD64）の命令セットにマッピングされます。このマッピングの過程で、「書き換えルール (rewrite rules)」が適用されます。書き換えルールは、特定のSSA値のパターンを、より効率的な、またはターゲットアーキテクチャに特化したSSA値のパターン（最終的には機械語命令に対応）に変換するものです。

### LEAQ命令 (Load Effective Address)

`LEAQ` (Load Effective Address Quadword) は、x86-64アーキテクチャの命令の一つです。この命令は、オペランドのアドレスを計算し、その結果をレジスタに格納します。メモリからデータをロードするわけではありません。
`LEAQ` は、複雑なアドレス計算を単一の命令で行えるため、ポインタ演算やアライメント調整、小さな定数乗算など、様々な最適化に利用されます。例えば、`LEAQ (%RAX, %RBX, 4), %RCX` は `RCX = RAX + RBX * 4` を計算します。
`LEAQ` 命令も、多くの場合、オフセットとして32ビット符号付き定数しか受け付けません。

### Goのアセンブラ (`cmd/internal/obj/x86/asm6.go`)

Goコンパイラは、最終的にGo独自のPlan 9アセンブラ形式でアセンブリコードを生成します。`cmd/internal/obj/x86/asm6.go` は、x86アーキテクチャ向けのアセンブラのバックエンドの一部であり、SSAバックエンドから出力された命令を実際の機械語に変換する役割を担います。この層で、命令のオペランドがハードウェアの制約（例えば、オフセットのサイズ）に適合するかどうかの最終的なチェックが行われます。

## 技術的詳細

このコミットの技術的詳細は、主に以下の2つの側面から構成されます。

1.  **SSA書き換えルールの修正 (`src/cmd/compile/internal/ssa/gen/AMD64.rules`, `src/cmd/compile/internal/ssa/rewriteAMD64.go`)**:
    *   既存のSSA書き換えルールに、定数オフセットが32ビット符号付き整数の範囲に収まることを確認する条件 `&& is32Bit(offset)` が追加されました。
    *   `is32Bit` 関数は、与えられた64ビット整数が32ビット符号付き整数の範囲内にあるかどうかをチェックするものです。具体的には、`-2^31 <= offset <= 2^31 - 1` の範囲を確認します。
    *   例えば、`OffPtr [off] ptr` (ポインタにオフセットを加える操作) の書き換えルールは、以前は無条件に `ADDQconst [off] ptr` (定数を加算する命令) に変換されていました。しかし、`ADDQconst` のオフセットが32ビットに収まらない場合、これは不正な命令になります。
    *   修正後、`OffPtr [off] ptr` は `is32Bit(off)` が真の場合にのみ `ADDQconst [off] ptr` に変換され、そうでない場合は `ADDQ (MOVQconst [off]) ptr` (オフセットをレジスタにロードしてから加算する、より安全だが複数命令になるパターン) に変換されるようになりました。
    *   同様に、`LEAQ` 命令やメモリロード/ストア命令 (`MOVQload`, `MOVLstore` など) の書き換えルールも、オフセットの合計が `is32Bit` の条件を満たす場合にのみ、単一の命令に畳み込むように変更されました。これにより、コンパイラはハードウェアの制約を尊重したコードを生成するようになります。
    *   `src/cmd/compile/internal/ssa/rewrite.go` から `addOff` 関数が削除されました。これは、オフセットのオーバーフローチェックを行っていましたが、新しい `is32Bit` チェックと、オーバーフローしないようにオフセットを直接加算するロジックに置き換えられたためです。

2.  **アセンブラの変更とエラー抑制 (`src/cmd/internal/obj/x86/asm6.go`, `src/cmd/compile/internal/gc/dcl.go`)**:
    *   `src/cmd/internal/obj/x86/asm6.go` では、アセンブラが命令を生成する際に、オフセット値が命令の許容範囲（例えば32ビット符号付き）に収まっているかをより厳密にチェックするようになりました。もし収まらない場合、アセンブラはエラーを報告して失敗します。
    *   この厳密なチェックにより、一部の「奇妙なテストコード」でアセンブラエラーが発生することが判明しました。これらのテストコードは、コンパイラ自体が既にエラーを生成しているような状況で、アセンブラのエラーが冗長になるか、または混乱を招く可能性がありました。
    *   これを解決するため、`src/cmd/compile/internal/gc/dcl.go` の `funccompile` 関数にロジックが追加されました。`nerrors != 0` (コンパイラが既にエラーを検出している場合) の条件で、アセンブラのエラー報告メカニズム (`Ctxt.DiagFunc`) を空の関数で上書きし、アセンブラ/リンカのエラーを抑制するようにしました。これにより、コンパイラが本質的なエラーを報告している場合に、アセンブラの追加エラーで出力が乱れるのを防ぎます。

これらの変更により、Goコンパイラはx86-64アーキテクチャの定数オフセット制約をより正確に扱い、より堅牢なコード生成を実現します。

## コアとなるコードの解説

### `is32Bit` 条件の導入

SSA書き換えルールにおける `is32Bit(offset)` 条件の導入は、Goコンパイラのコード生成の正確性を大幅に向上させます。
`is32Bit(val int64) bool` 関数は、`val >= -1<<31 && val <= 1<<31-1` のように実装され、64ビット整数 `val` が32ビット符号付き整数の範囲内にあるかを判定します。

*   **`OffPtr [off] ptr` の書き換え**:
    *   `is32Bit(off)` が真の場合: `(ADDQconst [off] ptr)` に変換されます。これは、オフセットが小さい場合に単一の `ADD` 命令で処理できるため、効率的です。
    *   `is32Bit(off)` が偽の場合: `(ADDQ (MOVQconst [off]) ptr)` に変換されます。この場合、まず大きなオフセット値 `off` を `MOVQconst` 命令でレジスタにロードし、そのレジスタを使って `ADDQ` 命令でポインタに加算します。これにより、オフセットが32ビット範囲を超えても正しくアドレス計算が行われますが、命令数が増えるため、わずかに効率が低下する可能性があります。

*   **`LEAQ` 命令の畳み込み**:
    *   `LEAQ` 命令は、複数の加算やシフトを単一の命令にまとめる強力な最適化手段です。しかし、そのオフセットも32ビット符号付きの制約を受けます。
    *   例えば、`(ADDQconst [c] (LEAQ [d] {s} x))` のようなパターンは、`c+d` が `is32Bit` の範囲内にある場合にのみ `(LEAQ [c+d] {s} x)` に畳み込まれます。範囲外の場合は、畳み込みが行われず、より多くの命令が生成されることになります。これにより、不正な `LEAQ` 命令が生成されるのを防ぎます。

### アセンブラエラーの抑制

`src/cmd/compile/internal/gc/dcl.go` での `Ctxt.DiagFunc` の上書きは、コンパイラのユーザーエクスペリエンスを向上させるためのものです。
Goコンパイラは多段階の処理を経てコードを生成します。もし初期段階でGoの構文エラーや型エラーなどのコンパイルエラーが発生した場合、その後のSSA生成やアセンブラ段階に進んでも、生成される中間コードは既に不正である可能性があります。このような状況で、アセンブラがさらにオフセットの制約違反などのエラーを報告しても、それは根本的な問題ではなく、最初のコンパイルエラーの派生に過ぎません。
`nerrors != 0` のチェックにより、既にコンパイルエラーがある場合はアセンブラのエラー報告を無効にすることで、ユーザーは最も根本的なエラーメッセージに集中でき、冗長なエラー出力に惑わされることがなくなります。

これらの変更は、Goコンパイラが生成する機械語コードが、ターゲットアーキテクチャの低レベルな制約を常に遵守するようにするための重要なステップであり、コンパイラの堅牢性と信頼性を高めます。

### GoコンパイラのSSA (Static Single Assignment)

Goコンパイラは、コード生成の過程でSSA形式の中間表現を使用します。SSAは、各変数が一度だけ代入されるようにする表現形式で、データフロー解析や最適化を容易にします。
SSAバックエンドでは、GoのソースコードがSSA値のグラフに変換され、その後、ターゲットアーキテクチャ（この場合はAMD64）の命令セットにマッピングされます。このマッピングの過程で、「書き換えルール (rewrite rules)」が適用されます。書き換えルールは、特定のSSA値のパターンを、より効率的な、またはターゲットアーキテクチャに特化したSSA値のパターン（最終的には機械語命令に対応）に変換するものです。

### LEAQ命令 (Load Effective Address)

`LEAQ` (Load Effective Address Quadword) は、x86-64アーキテクチャの命令の一つです。この命令は、オペランドのアドレスを計算し、その結果をレジスタに格納します。メモリからデータをロードするわけではありません。
`LEAQ` は、複雑なアドレス計算を単一の命令で行えるため、ポインタ演算やアライメント調整、小さな定数乗算など、様々な最適化に利用されます。例えば、`LEAQ (%RAX, %RBX, 4), %RCX` は `RCX = RAX + RBX * 4` を計算します。
`LEAQ` 命令も、多くの場合、オフセットとして32ビット符号付き定数しか受け付けません。

### Goのアセンブラ (`cmd/internal/obj/x86/asm6.go`)

Goコンパイラは、最終的にGo独自のPlan 9アセンブラ形式でアセンブリコードを生成します。`cmd/internal/obj/x86/asm6.go` は、x86アーキテクチャ向けのアセンブラのバックエンドの一部であり、SSAバックエンドから出力された命令を実際の機械語に変換する役割を担います。この層で、命令のオペランドがハードウェアの制約（例えば、オフセットのサイズ）に適合するかどうかの最終的なチェックが行われます。

## 技術的詳細

このコミットの技術的詳細は、主に以下の2つの側面から構成されます。

1.  **SSA書き換えルールの修正 (`src/cmd/compile/internal/ssa/gen/AMD64.rules`, `src/cmd/compile/internal/ssa/rewriteAMD64.go`)**:
    *   既存のSSA書き換えルールに、定数オフセットが32ビット符号付き整数の範囲に収まることを確認する条件 `&& is32Bit(offset)` が追加されました。
    *   `is32Bit` 関数は、与えられた64ビット整数が32ビット符号付き整数の範囲内にあるかどうかをチェックするものです。具体的には、`-2^31` から `2^31 - 1` の範囲を確認します。
    *   例えば、`OffPtr [off] ptr` (ポインタにオフセットを加える操作) の書き換えルールは、以前は無条件に `ADDQconst [off] ptr` (定数を加算する命令) に変換されていました。しかし、`ADDQconst` のオフセットが32ビットに収まらない場合、これは不正な命令になります。
    *   修正後、`OffPtr [off] ptr` は `is32Bit(off)` が真の場合にのみ `ADDQconst [off] ptr` に変換され、そうでない場合は `ADDQ (MOVQconst [off]) ptr` (オフセットをレジスタにロードしてから加算する、より安全だが複数命令になるパターン) に変換されるようになりました。
    *   同様に、`LEAQ` 命令やメモリロード/ストア命令 (`MOVQload`, `MOVLstore` など) の書き換えルールも、オフセットの合計が `is32Bit` の条件を満たす場合にのみ、単一の命令に畳み込むように変更されました。これにより、コンパイラはハードウェアの制約を尊重したコードを生成するようになります。
    *   `src/cmd/compile/internal/ssa/rewrite.go` から `addOff` 関数が削除されました。これは、オフセットのオーバーフローチェックを行っていましたが、新しい `is32Bit` チェックと、オーバーフローしないようにオフセットを直接加算するロジックに置き換えられたためです。

2.  **アセンブラの変更とエラー抑制 (`src/cmd/internal/obj/x86/asm6.go`, `src/cmd/compile/internal/gc/dcl.go`)**:
    *   `src/cmd/internal/obj/x86/asm6.go` では、アセンブラが命令を生成する際に、オフセット値が命令の許容範囲（例えば32ビット符号付き）に収まっているかをより厳密にチェックするようになりました。もし収まらない場合、アセンブラはエラーを報告して失敗します。
    *   この厳密なチェックにより、一部の「奇妙なテストコード」でアセンブラエラーが発生することが判明しました。これらのテストコードは、コンパイラ自体が既にエラーを生成しているような状況で、アセンブラのエラーが冗長になるか、または混乱を招く可能性がありました。
    *   これを解決するため、`src/cmd/compile/internal/gc/dcl.go` の `funccompile` 関数にロジックが追加されました。`nerrors != 0` (コンパイラが既にエラーを検出している場合) の条件で、アセンブラのエラー報告メカニズム (`Ctxt.DiagFunc`) を空の関数で上書きし、アセンブラ/リンカのエラーを抑制するようにしました。これにより、コンパイラが本質的なエラーを報告している場合に、アセンブラの追加エラーで出力が乱れるのを防ぎます。

これらの変更により、Goコンパイラはx86-64アーキテクチャの定数オフセット制約をより正確に扱い、より堅牢なコード生成を実現します。

## コアとなるコードの解説

### `is32Bit` 条件の導入

SSA書き換えルールにおける `is32Bit(offset)` 条件の導入は、Goコンパイラのコード生成の正確性を大幅に向上させます。
`is32Bit(val int64) bool` 関数は、`val >= -1<<31 && val <= 1<<31-1` のように実装され、64ビット整数 `val` が32ビット符号付き整数の範囲内にあるかを判定します。

*   **`OffPtr [off] ptr` の書き換え**:
    *   `is32Bit(off)` が真の場合: `(ADDQconst [off] ptr)` に変換されます。これは、オフセットが小さい場合に単一の `ADD` 命令で処理できるため、効率的です。
    *   `is32Bit(off)` が偽の場合: `(ADDQ (MOVQconst [off]) ptr)` に変換されます。この場合、まず大きなオフセット値 `off` を `MOVQconst` 命令でレジスタにロードし、そのレジスタを使って `ADDQ` 命令でポインタに加算します。これにより、オフセットが32ビット範囲を超えても正しくアドレス計算が行われますが、命令数が増えるため、わずかに効率が低下する可能性があります。

*   **`LEAQ` 命令の畳み込み**:
    *   `LEAQ` 命令は、複数の加算やシフトを単一の命令にまとめる強力な最適化手段です。しかし、そのオフセットも32ビット符号付きの制約を受けます。
    *   例えば、`(ADDQconst [c] (LEAQ [d] {s} x))` のようなパターンは、`c+d` が `is32Bit` の範囲内にある場合にのみ `(LEAQ [c+d] {s} x)` に畳み込まれます。範囲外の場合は、畳み込みが行われず、より多くの命令が生成されることになります。これにより、不正な `LEAQ` 命令が生成されるのを防ぎます。

### アセンブラエラーの抑制

`src/cmd/compile/internal/gc/dcl.go` での `Ctxt.DiagFunc` の上書きは、コンパイラのユーザーエクスペリエンスを向上させるためのものです。
Goコンパイラは多段階の処理を経てコードを生成します。もし初期段階でGoの構文エラーや型エラーなどのコンパイルエラーが発生した場合、その後のSSA生成やアセンブラ段階に進んでも、生成される中間コードは既に不正である可能性があります。このような状況で、アセンブラがさらにオフセットの制約違反などのエラーを報告しても、それは根本的な問題ではなく、最初のコンパイルエラーの派生に過ぎません。
`nerrors != 0` のチェックにより、既にコンパイルエラーがある場合はアセンブラのエラー報告を無効にすることで、ユーザーは最も根本的なエラーメッセージに集中でき、冗長なエラー出力に惑わされることがなくなります。

これらの変更は、Goコンパイラが生成する機械語コードが、ターゲットアーキテクチャの低レベルな制約を常に遵守するようにするための重要なステップであり、コンパイラの堅牢性と信頼性を高めます。

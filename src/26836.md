# [インデックス 26836] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドに、冗長な制御フローチェックを削除する新しい最適化パス「prove」を導入します。具体的には、配列の境界チェックやnilポインタチェック、論理式の冗長な評価など、既に証明されている条件分岐を排除することで、生成されるコードのサイズと実行効率を向上させます。

## 変更の背景

コンパイラ最適化の重要な目標の一つは、プログラムのセマンティクスを維持しつつ、生成されるコードの効率を最大化することです。GoコンパイラのSSA (Static Single Assignment) バックエンドは、コードをSSA形式に変換し、様々な最適化パスを適用します。このコミットの背景には、特に以下の問題意識がありました。

1.  **冗長な境界チェックの排除**: Go言語はメモリ安全性を重視するため、配列やスライスのアクセス時には常に境界チェックが行われます。しかし、多くの場合、同じ条件がコードの異なる場所で繰り返しチェックされることがあります。例えば、`a[i]`にアクセスした後、すぐに再度`a[i]`にアクセスする場合、2回目の境界チェックは1回目で既に安全性が保証されているため、冗長となります。このような冗長なチェックは、実行時のオーバーヘッドを増加させます。
2.  **冗長な条件分岐の簡素化**: 論理演算子（`&&`, `||`）を含む複雑な条件式において、一部の条件が既に真または偽であることが確定している場合、その後の評価は不要になります。例えば、`a || (a || b)`のような式では、最初の`a`が真であれば、残りの部分は評価する必要がありません。
3.  **既存の最適化との連携**: 既に存在する境界チェック、nilチェック、定数伝播などの最適化パスと連携し、より広範な最適化を可能にすること。特に、CL 12960（境界、nil、定数伝播を行うコミット）との相乗効果が期待されていました。

この「prove」パスは、これらの冗長な制御フローを静的に分析し、実行時に不要なチェックを削除することで、コンパイルされたバイナリのサイズを削減し、実行速度を向上させることを目的としています。

## 前提知識の解説

このコミットの技術的詳細を理解するためには、以下の概念が不可欠です。

1.  **SSA (Static Single Assignment) 形式**:
    *   SSAは、コンパイラ最適化で広く用いられる中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、最適化の精度が向上します。
    *   Goコンパイラは、AST (Abstract Syntax Tree) からSSA形式に変換し、その上で様々な最適化パス（例: 共通部分式除去、デッドコード除去、インライン化など）を適用します。
    *   SSA形式では、プログラムは「ブロック (Block)」と「値 (Value)」のグラフとして表現されます。ブロックは基本的な制御フローの単位であり、値は計算結果を表します。

2.  **制御フローグラフ (Control Flow Graph, CFG)**:
    *   プログラムの実行可能なパスを表現するグラフです。ノードは「基本ブロック (Basic Block)」を表し、エッジはブロック間の制御フローの遷移を表します。
    *   基本ブロックは、入り口が一つで出口が一つであり、内部に分岐を含まない一連の命令です。
    *   条件分岐（`if`文など）は、一つのブロックから複数の後続ブロックへのエッジとして表現されます。

3.  **ドミネータ (Dominator)** と **ドミネータツリー (Dominator Tree)**:
    *   CFGにおいて、ノードAがノードBをドミネートするとは、CFGのエントリノードからBへのすべてのパスがAを通過することを意味します。
    *   ドミネータツリーは、各ノードがその直接のドミネータ（immediate dominator）を親とするツリー構造です。ドミネータツリーは、プログラムの構造を理解し、到達可能性や制御依存性を分析するために非常に有用です。
    *   このコミットでは、`dominators(f)`関数でドミネータツリーを構築し、`sdom` (sparse dominator tree) を利用して、ブロック間のドミネータ関係を効率的にクエリしています。

4.  **境界チェック (Bounds Checking)**:
    *   Go言語では、配列やスライスにアクセスする際に、インデックスが有効な範囲内にあるかを実行時にチェックします。これにより、C/C++のような言語で発生しがちなバッファオーバーフローなどのメモリ安全性の問題を防ぎます。
    *   `OpIsInBounds`や`OpIsSliceInBounds`といったSSA操作は、これらの境界チェックを表します。

5.  **デッドコード除去 (Dead Code Elimination, DCE)**:
    *   プログラムの実行結果に影響を与えないコード（デッドコード）を削除する最適化です。このコミットで導入される「prove」パスは、冗長な条件分岐を削除することで、結果的にデッドコード（到達不能なブロック）を生成し、その後のデッドコード除去パスによって最終的に削除されます。

## 技術的詳細

「prove」パスは、ドミネータツリー上での深さ優先探索 (DFS) を利用して、プログラムの各ポイントで既知の変数間の関係（制約）を追跡します。

1.  **制約の表現**:
    *   `rangeMask` (`lt`, `eq`, `gt`): 2つの変数の間に「より小さい」「等しい」「より大きい」という関係があることを表すビットマスクです。
    *   `typeMask` (`signed`, `unsigned`, `pointer`): 変数の型（符号付き整数、符号なし整数、ポインタ）を表し、同じビット表現でも型によって意味が異なるため、制約の適用範囲を限定します。
    *   `control`構造体: `typeMask`と2つの変数のID (`a0`, `a1`) の組で、特定の型における変数ペアの制約を識別します。
    *   `mask`マップ: `map[control]rangeMask`として実装され、現在のドミネータツリーのパス上で既知となっている変数ペア間の制約を保持します。例えば、`mask[{signed, X, Y}] = lt`は、現在の実行パスでは`X < Y`が成立していることを意味します。

2.  **制約の伝播**:
    *   `prove`関数は、ドミネータツリーをDFSで走査します。
    *   `getRestrict`関数は、`BlockIf`（条件分岐ブロック）から後続ブロックへの遷移時に、その分岐が成立したことによって新たに判明する制約を`typeRangeTable`から取得します。例えば、`if a < b`という条件分岐の「真」のパスに入った場合、`a < b`という制約が新たに加わります。
    *   `updateRestrictions`関数は、`mask`マップを更新し、現在のブロックで新たに判明した制約を既存の制約と結合（ビットAND演算）します。これにより、より厳密な制約が導き出されます。
    *   `restoreRestrictions`関数は、DFSのバックトラック時に、そのブロックで追加された制約を`mask`マップから元に戻します。これにより、異なる実行パスでの制約が混同されるのを防ぎます。

3.  **冗長な制御の削除 (`simplifyBlock`)**:
    *   `simplifyBlock`関数は、現在のブロックが`BlockIf`である場合に、その条件が`mask`マップに格納されている既知の制約によって既に「真」または「偽」であることが証明できるかをチェックします。
    *   具体的には、現在の条件分岐が要求する`rangeMask` (`tr.r`) と、`mask`マップに格納されている既知の`rangeMask` (`m`) を比較します。
        *   もし`m`が`tr.r`に完全に含まれる場合 (`tr.r & m == m`)、その条件は常に真であり、正の分岐が常に取られることが証明されます。
        *   もし`m`が`tr.r`の補集合に完全に含まれる場合 (`((lt|eq|gt)^tr.r) & m == m`)、その条件は常に偽であり、負の分岐が常に取られることが証明されます。
    *   条件が証明された場合、その`BlockIf`ブロックは`BlockFirst`ブロック（無条件ジャンプ）に変換され、冗長な条件チェックが削除されます。これにより、コンパイラは不要な分岐命令を生成しなくなります。
    *   また、`OpIsInBounds`や`OpIsSliceInBounds`のような境界チェックにおいて、定数インデックスが既に安全であることが証明できる場合も同様に最適化されます。

このパスは、SSA形式の特性とドミネータツリーを活用することで、プログラムの実行パス上で静的に推論可能な制約を最大限に利用し、コンパイラがより効率的なコードを生成することを可能にします。

## コアとなるコードの変更箇所

このコミットの主要な変更は、以下の3つのファイルにわたります。

1.  **`src/cmd/compile/internal/ssa/compile.go`**:
    *   SSA最適化パスのリスト`passes`に、新しく`{name: "prove", fn: prove}`が追加されました。
    *   パスの実行順序を定義する`passOrder`に、`prove`パスの依存関係が追加されました。
        *   `{"generic cse", "prove"}`: 共通部分式除去 (CSE) の後に`prove`を実行することで、`prove`が最大の効果を発揮できるようにします。CSEによって冗長な計算が削除され、変数間の関係がより明確になるためです。
        *   `{"prove", "generic deadcode"}`: `prove`によって冗長な条件分岐が削除されると、到達不能なブロック（デッドコード）が生成される可能性があります。そのため、`prove`の後にデッドコード除去パスを実行することで、これらのデッドブロックをクリーンアップします。

2.  **`src/cmd/compile/internal/ssa/prove.go`**:
    *   このファイルは新規作成され、`prove`最適化パスの全てのロジックを含んでいます。
    *   `rangeMask`, `typeMask`, `typeRange`, `control`といった、変数間の関係と制約を表現するための型定義が含まれます。
    *   `typeRangeTable`マップは、SSAの比較演算子（`OpEq8`, `OpLess64`, `OpIsInBounds`など）が、その条件が真であった場合にどのような`typeRange`（型と関係の組み合わせ）を導き出すかを示します。
    *   `prove(f *Func)`関数がメインのエントリポイントであり、ドミネータツリー上でのDFSを管理します。
    *   `getRestrict`, `updateRestrictions`, `restoreRestrictions`関数は、DFS中に制約を伝播・管理する役割を担います。
    *   `simplifyBlock`関数は、既知の制約に基づいて冗長な`BlockIf`を`BlockFirst`に変換する核心的なロジックを含みます。

3.  **`test/prove.go`**:
    *   このファイルも新規作成され、`prove`パスの動作を検証するためのテストケースが含まれています。
    *   `errorcheck`ディレクティブと`// ERROR "..."`コメントを使用して、コンパイラが特定の境界チェックや条件分岐を「Proved」（証明済み）または「Disproved」（反証済み）として削除したことを検証します。
    *   テストケースは、以下のようなシナリオをカバーしています。
        *   同じ配列要素への連続アクセスにおける冗長な境界チェックの削除 (`f0`, `f1`, `f2`, `f7`)。
        *   ループ内の境界チェックの削除 (`f2`, `f3`)。
        *   複雑な条件分岐における論理的な簡素化 (`f4a`から`f4f`, `f5`, `f8`)。
        *   定数インデックスに対する境界チェックの最適化 (`f1`の`a[5] = 1 // ERROR "Proved constant IsInBounds$"`)。
        *   常に真または偽となる比較の削除 (`f6a`から`f6e`)。

## コアとなるコードの解説

`src/cmd/compile/internal/ssa/prove.go` の `simplifyBlock` 関数がこのコミットの核心です。

```go
func simplifyBlock(mask map[control]rangeMask, b *Block) {
	if b.Kind != BlockIf {
		return
	}

	tr, has := typeRangeTable[b.Control.Op]
	if !has {
		return
	}

	succ := -1
	a0 := b.Control.Args[0].ID
	a1 := b.Control.Args[1].ID
	if a0 > a1 {
		tr.r = reverseBits[tr.r]
		a0, a1 = a1, a0
	}

	for t := typeMask(1); t <= tr.t; t <<= 1 {
		if t&tr.t == 0 {
			continue
		}

		// tr.r represents in which case the positive branch is taken.
		// m.r represents which cases are possible because of previous relations.
		// If the set of possible relations m.r is included in the set of relations
		// need to take the positive branch (or negative) then that branch will
		// always be taken.
		// For shortcut, if m.r == 0 then this block is dead code.
		i := control{t, a0, a1}
		m := mask[i]
		if m != 0 && tr.r&m == m {
			// ... (debug logging)
			succ = 0 // Proved positive branch
			break
		}
		if m != 0 && ((lt|eq|gt)^tr.r)&m == m {
			// ... (debug logging)
			succ = 1 // Proved negative branch
			break
		}
	}

	if succ == -1 {
		// HACK: If the first argument of IsInBounds or IsSliceInBounds
		// is a constant and we already know that constant is smaller (or equal)
		// to the upper bound than this is proven. Most useful in cases such as:
		// if len(a) <= 1 { return }
		// do something with a[1]
		c := b.Control
		if (c.Op == OpIsInBounds || c.Op == OpIsSliceInBounds) &&
			c.Args[0].Op == OpConst64 && c.Args[0].AuxInt >= 0 {
			m := mask[control{signed, a0, a1}]
			if m != 0 && tr.r&m == m {
				// ... (debug logging)
				succ = 0
			}
		}
	}

	if succ != -1 {
		b.Kind = BlockFirst
		b.Control = nil
		b.Succs[0], b.Succs[1] = b.Succs[succ], b.Succs[1-succ]
	}
}
```

この関数は、以下のステップで冗長な条件分岐を削除します。

1.  **対象ブロックの確認**: まず、現在のブロック`b`が`BlockIf`（条件分岐）であるかを確認します。そうでなければ、最適化の対象外なので処理を終了します。
2.  **制御オペレーションの解析**: `b.Control.Op`（ブロックの制御を決定するSSA操作、例: `OpLess64`）に対応する`typeRange`を`typeRangeTable`から取得します。`typeRange`は、この条件が真であった場合に成立する関係（`lt`, `eq`, `gt`）と、その関係が適用される型（`signed`, `unsigned`, `pointer`）を示します。
3.  **変数の正規化**: 比較対象の2つの変数`a0`, `a1`のIDを正規化（`a0.ID <= a1.ID`となるように並べ替え）し、必要に応じて`tr.r`（関係マスク）を反転させます。これにより、`mask`マップのキーが一貫性を保ちます。
4.  **既知の制約との比較**:
    *   `mask`マップには、現在の実行パスで既に証明されている変数間の制約が格納されています。
    *   `simplifyBlock`は、`typeRangeTable`から得られた現在の条件分岐の`tr.r`と、`mask`マップから得られた既知の制約`m`を比較します。
    *   **正の分岐が証明された場合**: `m != 0 && tr.r&m == m`
        *   これは、「既知の制約`m`が、現在の条件が真であるために必要な関係`tr.r`に完全に含まれる」ことを意味します。つまり、現在の条件は常に真であることが証明されます。この場合、`succ`は`0`（正の分岐）に設定されます。
    *   **負の分岐が証明された場合**: `m != 0 && ((lt|eq|gt)^tr.r)&m == m`
        *   これは、「既知の制約`m`が、現在の条件が偽であるために必要な関係（`tr.r`の補集合）に完全に含まれる」ことを意味します。つまり、現在の条件は常に偽であることが証明されます。この場合、`succ`は`1`（負の分岐）に設定されます。
5.  **特殊な境界チェックの最適化**:
    *   `succ`がまだ`-1`（証明されていない）の場合、`OpIsInBounds`または`OpIsSliceInBounds`操作で、かつ最初の引数（インデックス）が定数である場合に、追加のチェックを行います。これは、`if len(a) <= 1 { return }` の後に `a[1]` にアクセスするようなケースで、定数インデックスが既に安全であることが証明できる場合に最適化を適用するためです。
6.  **ブロックの変換**:
    *   もし`succ`が`0`または`1`に設定された場合（つまり、条件分岐が証明された場合）、ブロック`b`は`BlockFirst`（無条件ジャンプ）に変換されます。
    *   `b.Control`は`nil`に設定され、`b.Succs`（後続ブロック）は証明された分岐先にのみ向かうように変更されます。これにより、冗長な条件チェックがコンパイルされたコードから完全に削除されます。

このメカニズムにより、コンパイラは実行時に不要な比較や分岐をスキップし、より高速でコンパクトなコードを生成できるようになります。

## 変更の背景

コンパイラ最適化の重要な目標の一つは、プログラムのセマンティクスを維持しつつ、生成されるコードの効率を最大化することです。GoコンパイラのSSA (Static Single Assignment) バックエンドは、コードをSSA形式に変換し、様々な最適化パスを適用します。このコミットの背景には、特に以下の問題意識がありました。

1.  **冗長な境界チェックの排除**: Go言語はメモリ安全性を重視するため、配列やスライスのアクセス時には常に境界チェックが行われます。しかし、多くの場合、同じ条件がコードの異なる場所で繰り返しチェックされることがあります。例えば、`a[i]`にアクセスした後、すぐに再度`a[i]`にアクセスする場合、2回目の境界チェックは1回目で既に安全性が保証されているため、冗長となります。このような冗長なチェックは、実行時のオーバーヘッドを増加させます。
2.  **冗長な条件分岐の簡素化**: 論理演算子（`&&`, `||`）を含む複雑な条件式において、一部の条件が既に真または偽であることが確定している場合、その後の評価は不要になります。例えば、`a || (a || b)`のような式では、最初の`a`が真であれば、残りの部分は評価する必要がありません。
3.  **既存の最適化との連携**: 既に存在する境界チェック、nilチェック、定数伝播などの最適化パスと連携し、より広範な最適化を可能にすること。特に、CL 12960（境界、nil、定数伝播を行うコミット）との相乗効果が期待されていました。

この「prove」パスは、これらの冗長な制御フローを静的に分析し、実行時に不要なチェックを削除することで、コンパイルされたバイナリのサイズを削減し、実行速度を向上させることを目的としています。

## 前提知識の解説

このコミットの技術的詳細を理解するためには、以下の概念が不可欠です。

1.  **SSA (Static Single Assignment) 形式**:
    *   SSAは、コンパイラ最適化で広く用いられる中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、最適化の精度が向上します。
    *   Goコンパイラは、AST (Abstract Syntax Tree) からSSA形式に変換し、その上で様々な最適化パス（例: 共通部分式除去、デッドコード除去、インライン化など）を適用します。
    *   SSA形式では、プログラムは「ブロック (Block)」と「値 (Value)」のグラフとして表現されます。ブロックは基本的な制御フローの単位であり、値は計算結果を表します。

2.  **制御フローグラフ (Control Flow Graph, CFG)**:
    *   プログラムの実行可能なパスを表現するグラフです。ノードは「基本ブロック (Basic Block)」を表し、エッジはブロック間の制御フローの遷移を表します。
    *   基本ブロックは、入り口が一つで出口が一つであり、内部に分岐を含まない一連の命令です。
    *   条件分岐（`if`文など）は、一つのブロックから複数の後続ブロックへのエッジとして表現されます。

3.  **ドミネータ (Dominator)** と **ドミネータツリー (Dominator Tree)**:
    *   CFGにおいて、ノードAがノードBをドミネートするとは、CFGのエントリノードからBへのすべてのパスがAを通過することを意味します。
    *   ドミネータツリーは、各ノードがその直接のドミネータ（immediate dominator）を親とするツリー構造です。ドミネータツリーは、プログラムの構造を理解し、到達可能性や制御依存性を分析するために非常に有用です。
    *   このコミットでは、`dominators(f)`関数でドミネータツリーを構築し、`sdom` (sparse dominator tree) を利用して、ブロック間のドミネータ関係を効率的にクエリしています。

4.  **境界チェック (Bounds Checking)**:
    *   Go言語では、配列やスライスにアクセスする際に、インデックスが有効な範囲内にあるかを実行時にチェックします。これにより、C/C++のような言語で発生しがちなバッファオーバーフローなどのメモリ安全性の問題を防ぎます。
    *   `OpIsInBounds`や`OpIsSliceInBounds`といったSSA操作は、これらの境界チェックを表します。

5.  **デッドコード除去 (Dead Code Elimination, DCE)**:
    *   プログラムの実行結果に影響を与えないコード（デッドコード）を削除する最適化です。このコミットで導入される「prove」パスは、冗長な条件分岐を削除することで、結果的にデッドコード（到達不能なブロック）を生成し、その後のデッドコード除去パスによって最終的に削除されます。

## 技術的詳細

「prove」パスは、ドミネータツリー上での深さ優先探索 (DFS) を利用して、プログラムの各ポイントで既知の変数間の関係（制約）を追跡します。

1.  **制約の表現**:
    *   `rangeMask` (`lt`, `eq`, `gt`): 2つの変数の間に「より小さい」「等しい」「より大きい」という関係があることを表すビットマスクです。
    *   `typeMask` (`signed`, `unsigned`, `pointer`): 変数の型（符号付き整数、符号なし整数、ポインタ）を表し、同じビット表現でも型によって意味が異なるため、制約の適用範囲を限定します。
    *   `control`構造体: `typeMask`と2つの変数のID (`a0`, `a1`) の組で、特定の型における変数ペアの制約を識別します。
    *   `mask`マップ: `map[control]rangeMask`として実装され、現在のドミネータツリーのパス上で既知となっている変数ペア間の制約を保持します。例えば、`mask[{signed, X, Y}] = lt`は、現在の実行パスでは`X < Y`が成立していることを意味します。

2.  **制約の伝播**:
    *   `prove`関数は、ドミネータツリーをDFSで走査します。
    *   `getRestrict`関数は、`BlockIf`（条件分岐ブロック）から後続ブロックへの遷移時に、その分岐が成立したことによって新たに判明する制約を`typeRangeTable`から取得します。例えば、`if a < b`という条件分岐の「真」のパスに入った場合、`a < b`という制約が新たに加わります。
    *   `updateRestrictions`関数は、`mask`マップを更新し、現在のブロックで新たに判明した制約を既存の制約と結合（ビットAND演算）します。これにより、より厳密な制約が導き出されます。
    *   `restoreRestrictions`関数は、DFSのバックトラック時に、そのブロックで追加された制約を`mask`マップから元に戻します。これにより、異なる実行パスでの制約が混同されるのを防ぎます。

3.  **冗長な制御の削除 (`simplifyBlock`)**:
    *   `simplifyBlock`関数は、現在のブロックが`BlockIf`である場合に、その条件が`mask`マップに格納されている既知の制約によって既に「真」または「偽」であることが証明できるかをチェックします。
    *   具体的には、現在の条件分岐が要求する`rangeMask` (`tr.r`) と、`mask`マップに格納されている既知の`rangeMask` (`m`) を比較します。
        *   もし`m`が`tr.r`に完全に含まれる場合 (`tr.r & m == m`)、その条件は常に真であり、正の分岐が常に取られることが証明されます。
        *   もし`m`が`tr.r`の補集合に完全に含まれる場合 (`((lt|eq|gt)^tr.r) & m == m`)、その条件は常に偽であり、負の分岐が常に取られることが証明されます。
    *   条件が証明された場合、その`BlockIf`ブロックは`BlockFirst`ブロック（無条件ジャンプ）に変換され、冗長な条件チェックが削除されます。これにより、コンパイラは不要な分岐命令を生成しなくなります。
    *   また、`OpIsInBounds`や`OpIsSliceInBounds`のような境界チェックにおいて、定数インデックスが既に安全であることが証明できる場合も同様に最適化されます。

このパスは、SSA形式の特性とドミネータツリーを活用することで、プログラムの実行パス上で静的に推論可能な制約を最大限に利用し、コンパイラがより効率的なコードを生成することを可能にします。

## コアとなるコードの変更箇所

このコミットの主要な変更は、以下の3つのファイルにわたります。

1.  **`src/cmd/compile/internal/ssa/compile.go`**:
    *   SSA最適化パスのリスト`passes`に、新しく`{name: "prove", fn: prove}`が追加されました。
    *   パスの実行順序を定義する`passOrder`に、`prove`パスの依存関係が追加されました。
        *   `{"generic cse", "prove"}`: 共通部分式除去 (CSE) の後に`prove`を実行することで、`prove`が最大の効果を発揮できるようにします。CSEによって冗長な計算が削除され、変数間の関係がより明確になるためです。
        *   `{"prove", "generic deadcode"}`: `prove`によって冗長な条件分岐が削除されると、到達不能なブロック（デッドコード）が生成される可能性があります。そのため、`prove`の後にデッドコード除去パスを実行することで、これらのデッドブロックをクリーンアップします。

2.  **`src/cmd/compile/internal/ssa/prove.go`**:
    *   このファイルは新規作成され、`prove`最適化パスの全てのロジックを含んでいます。
    *   `rangeMask`, `typeMask`, `typeRange`, `control`といった、変数間の関係と制約を表現するための型定義が含まれます。
    *   `typeRangeTable`マップは、SSAの比較演算子（`OpEq8`, `OpLess64`, `OpIsInBounds`など）が、その条件が真であった場合にどのような`typeRange`（型と関係の組み合わせ）を導き出すかを示します。
    *   `prove(f *Func)`関数がメインのエントリポイントであり、ドミネータツリー上でのDFSを管理します。
    *   `getRestrict`, `updateRestrictions`, `restoreRestrictions`関数は、DFS中に制約を伝播・管理する役割を担います。
    *   `simplifyBlock`関数は、既知の制約に基づいて冗長な`BlockIf`を`BlockFirst`に変換する核心的なロジックを含みます。

3.  **`test/prove.go`**:
    *   このファイルも新規作成され、`prove`パスの動作を検証するためのテストケースが含まれています。
    *   `errorcheck`ディレクティブと`// ERROR "..."`コメントを使用して、コンパイラが特定の境界チェックや条件分岐を「Proved」（証明済み）または「Disproved」（反証済み）として削除したことを検証します。
    *   テストケースは、以下のようなシナリオをカバーしています。
        *   同じ配列要素への連続アクセスにおける冗長な境界チェックの削除 (`f0`, `f1`, `f2`, `f7`)。
        *   ループ内の境界チェックの削除 (`f2`, `f3`)。
        *   複雑な条件分岐における論理的な簡素化 (`f4a`から`f4f`, `f5`, `f8`)。
        *   定数インデックスに対する境界チェックの最適化 (`f1`の`a[5] = 1 // ERROR "Proved constant IsInBounds$"`)。
        *   常に真または偽となる比較の削除 (`f6a`から`f6e`)。

## コアとなるコードの解説

`src/cmd/compile/internal/ssa/prove.go` の `simplifyBlock` 関数がこのコミットの核心です。

```go
func simplifyBlock(mask map[control]rangeMask, b *Block) {
	if b.Kind != BlockIf {
		return
	}

	tr, has := typeRangeTable[b.Control.Op]
	if !has {
		return
	}

	succ := -1
	a0 := b.Control.Args[0].ID
	a1 := b.Control.Args[1].ID
	if a0 > a1 {
		tr.r = reverseBits[tr.r]
		a0, a1 = a1, a0
	}

	for t := typeMask(1); t <= tr.t; t <<= 1 {
		if t&tr.t == 0 {
			continue
		}

		// tr.r represents in which case the positive branch is taken.
		// m.r represents which cases are possible because of previous relations.
		// If the set of possible relations m.r is included in the set of relations
		// need to take the positive branch (or negative) then that branch will
		// always be taken.
		// For shortcut, if m.r == 0 then this block is dead code.
		i := control{t, a0, a1}
		m := mask[i]
		if m != 0 && tr.r&m == m {
			// ... (debug logging)
			succ = 0 // Proved positive branch
			break
		}
		if m != 0 && ((lt|eq|gt)^tr.r)&m == m {
			// ... (debug logging)
			succ = 1 // Proved negative branch
			break
		}
	}

	if succ == -1 {
		// HACK: If the first argument of IsInBounds or IsSliceInBounds
		// is a constant and we already know that constant is smaller (or equal)
		// to the upper bound than this is proven. Most useful in cases such as:
		// if len(a) <= 1 { return }
		// do something with a[1]
		c := b.Control
		if (c.Op == OpIsInBounds || c.Op == OpIsSliceInBounds) &&
			c.Args[0].Op == OpConst64 && c.Args[0].AuxInt >= 0 {
			m := mask[control{signed, a0, a1}]
			if m != 0 && tr.r&m == m {
				// ... (debug logging)
				succ = 0
			}
		}
	}

	if succ != -1 {
		b.Kind = BlockFirst
		b.Control = nil
		b.Succs[0], b.Succs[1] = b.Succs[succ], b.Succs[1-succ]
	}
}
```

この関数は、以下のステップで冗長な条件分岐を削除します。

1.  **対象ブロックの確認**: まず、現在のブロック`b`が`BlockIf`（条件分岐）であるかを確認します。そうでなければ、最適化の対象外なので処理を終了します。
2.  **制御オペレーションの解析**: `b.Control.Op`（ブロックの制御を決定するSSA操作、例: `OpLess64`）に対応する`typeRange`を`typeRangeTable`から取得します。`typeRange`は、この条件が真であった場合に成立する関係（`lt`, `eq`, `gt`）と、その関係が適用される型（`signed`, `unsigned`, `pointer`）を示します。
3.  **変数の正規化**: 比較対象の2つの変数`a0`, `a1`のIDを正規化（`a0.ID <= a1.ID`となるように並べ替え）し、必要に応じて`tr.r`（関係マスク）を反転させます。これにより、`mask`マップのキーが一貫性を保ちます。
4.  **既知の制約との比較**:
    *   `mask`マップには、現在の実行パスで既に証明されている変数間の制約が格納されています。
    *   `simplifyBlock`は、`typeRangeTable`から得られた現在の条件分岐の`tr.r`と、`mask`マップから得られた既知の制約`m`を比較します。
    *   **正の分岐が証明された場合**: `m != 0 && tr.r&m == m`
        *   これは、「既知の制約`m`が、現在の条件が真であるために必要な関係`tr.r`に完全に含まれる」ことを意味します。つまり、現在の条件は常に真であることが証明されます。この場合、`succ`は`0`（正の分岐）に設定されます。
    *   **負の分岐が証明された場合**: `m != 0 && ((lt|eq|gt)^tr.r)&m == m`
        *   これは、「既知の制約`m`が、現在の条件が偽であるために必要な関係（`tr.r`の補集合）に完全に含まれる」ことを意味します。つまり、現在の条件は常に偽であることが証明されます。この場合、`succ`は`1`（負の分岐）に設定されます。
5.  **特殊な境界チェックの最適化**:
    *   `succ`がまだ`-1`（証明されていない）の場合、`OpIsInBounds`または`OpIsSliceInBounds`操作で、かつ最初の引数（インデックス）が定数である場合に、追加のチェックを行います。これは、`if len(a) <= 1 { return }` の後に `a[1]` にアクセスするようなケースで、定数インデックスが既に安全であることが証明できる場合に最適化を適用するためです。
6.  **ブロックの変換**:
    *   もし`succ`が`0`または`1`に設定された場合（つまり、条件分岐が証明された場合）、ブロック`b`は`BlockFirst`（無条件ジャンプ）に変換されます。
    *   `b.Control`は`nil`に設定され、`b.Succs`（後続ブロック）は証明された分岐先にのみ向かうように変更されます。これにより、冗長な条件チェックがコンパイルされたコードから完全に削除されます。

このメカニズムにより、コンパイラは実行時に不要な比較や分岐をスキップし、より高速でコンパクトなコードを生成できるようになります。

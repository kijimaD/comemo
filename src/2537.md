## 変更の背景

Go言語は、その開発初期から複数のアーキテクチャをターゲットとすることを目指していました。このコミットが行われた2009年当時、Goコンパイラはまだ発展途上にあり、特にARMアーキテクチャのような新しいターゲットへの対応は継続的な作業が必要でした。

`5g`は、Go言語の初期のコンパイラであり、Plan 9のツールチェインをベースにしていました。`5g`はGoのソースコードをオブジェクトファイルに変換する役割を担い、`5l`はそれらのオブジェクトファイルをリンクして実行可能ファイルを生成しました。ARMアーキテクチャは、モバイルデバイスや組み込みシステムで広く利用されており、Goがこれらのプラットフォームで動作するためには、コンパイラがARM固有の命令セット、レジスタ、アドレッシングモードなどを正しく扱う必要がありました。

このコミットは、`5g`コンパイラが生成するコードがARMの規約に沿うように、内部データ構造の初期化、オブジェクトファイルのフォーマット、アセンブリリストの出力方法などを調整することを目的としています。特に、命令の条件コードやレジスタの扱いに関する変更が多く見られます。

## 前提知識の解説

### Goの初期コンパイラ (5g, 5l)

*   **5g (Goコンパイラ)**: Go言語のソースコードを、特定のアーキテクチャ（この場合はARM）向けのオブジェクトファイルにコンパイルする役割を担っていました。Plan 9のツールチェインから派生しており、Go言語の初期のクロスコンパイル能力を支えていました。
*   **5l (Goリンカ)**: `5g`によって生成されたオブジェクトファイルと必要なライブラリを結合し、最終的な実行可能バイナリを生成する役割を担っていました。

現在のGoでは、これらのツールは`go tool compile`および`go tool link`として統合されていますが、このコミットの時点では`5g`と`5l`という名称で存在していました。

### ARMアーキテクチャの基本 (レジスタ、条件コード)

ARMアーキテクチャは、RISC（Reduced Instruction Set Computer）ベースの命令セットアーキテクチャです。

*   **レジスタ**: ARMプロセッサは、汎用レジスタ（R0-R15など）と特殊レジスタ（プログラムカウンタPC、スタックポインタSP、リンクレジスタLRなど）を持っています。これらのレジスタは、データの格納やアドレスの計算に使用されます。
*   **条件コード (Condition Codes)**: ARM命令の多くは、条件付きで実行することができます。これは、直前の演算結果に基づいて設定されるフラグ（N: 負、Z: ゼロ、C: キャリー、V: オーバーフロー）をチェックすることで実現されます。これらのフラグは、CPSR (Current Program Status Register) または APSR (Application Program Status Register) に格納されます。例えば、`ADDEQ R0, R1, R2`という命令は、Zフラグがセットされている（直前の演算結果がゼロだった）場合にのみ実行されます。`C_SCOND_NONE`は、条件なしで命令を実行することを示す定数です。

### Goコンパイラ内部構造 (`Prog`と`Addr`構造体)

Goコンパイラのバックエンドでは、アセンブリコードを生成するために`Prog`と`Addr`という主要な内部データ構造が使用されます。

*   **`Prog`構造体**: 単一のアセンブリ命令を表します。命令のオペコード（例: `MOV`, `ADD`, `CALL`）、ソースオペランド、デスティネーションオペランド、分岐ターゲット、ソースコードの行番号など、命令に関するすべての情報を含みます。
*   **`Addr`構造体**: オペランドのアドレスまたは値を表します。オペランドの種類（レジスタ、メモリ、即値、スタックフレームポインタ、グローバルシンボルなど）、関連するレジスタ、オフセット、シンボルへの参照、インデックス付きアドレッシングモードのためのスケールとインデックスなどの情報を含みます。

コンパイラのバックエンドは、`Prog`構造体のシーケンスを構築し、各`Prog`は`Addr`構造体を使用してそのオペランドを定義します。この`Prog`命令のシーケンスがアセンブラに渡され、最終的なマシンコードに変換されます。

## 技術的詳細

このコミットは、主に`Prog`および`Addr`構造体の初期化と、それらの情報をオブジェクトファイルに書き込む際、およびアセンブリリストとして表示する際の挙動をARMアーキテクチャに合わせて調整しています。

1.  **`src/cmd/5g/galign.c` (`betypeinit`関数)**:
    *   `zprog`というグローバルな`Prog`構造体の初期化において、`zprog.scond = C_SCOND_NONE;`と`zprog.reg = NREG;`、`zprog.from.reg = NREG;`が追加されました。これは、新しい`Prog`構造体が作成される際に、条件コードとレジスタフィールドがデフォルトで「なし」または「未指定」の状態に初期化されることを保証します。これにより、ARMの条件付き実行命令やレジスタの使用が正しく扱われるようになります。

2.  **`src/cmd/5g/ggen.c` (`compile`関数)**:
    *   `ptxt->reg = 0; // flags`が追加されました。`ptxt`は現在の関数のテキストセグメントを表す`Prog`構造体であり、その`reg`フィールドがフラグとして使用される場合があるため、明示的に0に初期化することで、予期せぬ値が設定されるのを防ぎます。

3.  **`src/cmd/5g/gobj.c` (`zhist`, `zaddr`関数)**:
    *   `zhist`関数は、オブジェクトファイルに履歴情報（ソースコードの行番号など）を書き込む際に、`AHISTORY`命令の後に`C_SCOND_NONE`と`NREG`を書き込むように変更されました。これは、履歴情報にも条件コードやレジスタの概念が導入されたことを示唆しています。
    *   `zaddr`関数は、`Addr`構造体をオブジェクトファイルに書き込む際に、`D_EXTERN`と`D_PARAM`のタイプが`D_OREG`（オフセット付きレジスタ）として扱われるように順序が変更されました。また、`D_REG`, `D_FREG`, `D_PSR`のケースから`D_EXTERN`と`D_PARAM`が削除され、`D_STATIC`, `D_AUTO`のケースに`D_EXTERN`と`D_PARAM`が追加されました。これは、これらのアドレスタイプがARMのレジスタベースのアドレッシングモードとどのようにマッピングされるかに関する調整です。

4.  **`src/cmd/5g/gsubr.c` (`clearp`関数)**:
    *   `Prog`構造体をクリアする`clearp`関数において、`p->reg = NREG;`, `p->scond = C_SCOND_NONE;`, `p->from.reg = NREG;`, `p->to.reg = NREG;`が追加されました。これは、`Prog`構造体のすべての関連フィールドが、新しい命令のために適切にリセットされることを保証します。

5.  **`src/cmd/5g/list.c` (`listinit`, `Dconv`関数)**:
    *   `listinit`関数から`fmtinstall('R', Rconv);`が削除されました。これは、レジスタ番号を文字列に変換する`Rconv`関数が不要になったことを意味します。
    *   `Rconv`関数自体が削除されました。
    *   `Dconv`関数は、`Addr`構造体をアセンブリリストとして表示する際に、レジスタ番号を直接出力するように変更されました。以前は`%R`フォーマット指定子を使用して`Rconv`を呼び出していましたが、変更後は`R%d`という形式でレジスタ番号を直接表示するようになりました。これは、アセンブリリストの出力形式がARMの慣習に合わせられたか、あるいはレジスタ名のマッピングが簡素化されたことを示唆しています。

6.  **`src/cmd/5l/5.out.h`**:
    *   `C_SCOND_NONE`と`C_SCOND_NV`という新しい定数が追加されました。`C_SCOND_NONE`は条件なし実行を、`C_SCOND_NV`はオーバーフローなし（No Overflow）の条件コードを表すと考えられます。これにより、リンカがARMの条件コードをより正確に解釈・処理できるようになります。

7.  **`src/cmd/5l/span.c` (`oplook`関数)**:
    *   `oplook`関数内のエラーメッセージが変更されました。以前は`p->as, a1, a2, a3`のみを出力していましたが、変更後は`p->as, a1, a2, a3, p->from.type, p->to.type`と、`Prog`構造体のソースとデスティネーションのタイプも出力するようになりました。これは、不正な命令の組み合わせが発生した際に、デバッグ情報を増やすことで問題の特定を容易にするための改善です。

これらの変更は全体として、GoコンパイラがARMアーキテクチャの特性（特に条件コードとレジスタの扱い）をより正確に反映し、適切なオブジェクトコードとアセンブリリストを生成できるようにするための基盤を強化しています。

## コアとなるコードの解説

### `src/cmd/5g/galign.c` の `betypeinit` 関数における `zprog` の初期化

`betypeinit`関数は、コンパイラのバックエンドが型情報を初期化する際に呼び出されます。ここで`zprog`という`Prog`構造体が初期化されます。`zprog`は、新しい命令を生成する際のテンプレートとして機能することが多いです。

追加された行:
*   `zprog.scond = C_SCOND_NONE;`
*   `zprog.reg = NREG;`
*   `zprog.from.reg = NREG;`

これらの変更は、`Prog`構造体の条件コード(`scond`)とレジスタフィールド(`reg`, `from.reg`)が、デフォルトで「条件なし」(`C_SCOND_NONE`)および「レジスタなし」(`NREG`)に設定されることを保証します。ARMアーキテクチャでは、ほとんどの命令が条件付きで実行できるため、明示的な条件が指定されない限り、命令は無条件で実行されるべきです。また、オペランドにレジスタが使用されない場合も、そのフィールドが適切に初期化されている必要があります。これにより、ARM向けのコード生成において、命令のデフォルトの状態が正しく設定され、予期せぬ動作を防ぎます。

### `src/cmd/5g/list.c` の `Rconv` 削除と `Dconv` 修正

`list.c`は、コンパイラが生成するアセンブリリストのフォーマットを担当するファイルです。

*   **`Rconv`関数の削除**: 以前は`Rconv`関数がレジスタ番号を`R0`, `R1`などの文字列に変換していました。この関数が削除されたということは、レジスタの表示方法が変更されたことを意味します。
*   **`Dconv`関数の修正**: `Dconv`関数は`Addr`構造体を文字列に変換し、アセンブリリストに表示します。修正後、`Addr`タイプが`D_OREG`（オフセット付きレジスタ）の場合、`"$%d(R%d)"`という形式でオフセットとレジスタ番号を直接出力するようになりました。それ以外の場合でレジスタが関与する場合は`"R%d"`という形式でレジスタ番号を直接出力します。

この変更は、ARMアセンブリの慣習に合わせてレジスタの表示を簡素化し、`Rconv`のような中間変換層をなくすことで、コードの複雑さを軽減し、より直接的なレジスタ表現を可能にしていると考えられます。

### `src/cmd/5l/5.out.h` における `C_SCOND_NONE` と `C_SCOND_NV` の追加

`5.out.h`は、リンカが使用するオブジェクトファイルのフォーマットや定数を定義するヘッダファイルです。

追加された行:
*   `#define C_SCOND_NONE 14`
*   `#define C_SCOND_NV 15`

これらの定数は、ARMの条件コードを表すために導入されました。`C_SCOND_NONE`は、命令が無条件で実行されることを示す条件コードです。`C_SCOND_NV`は、"No Overflow"（オーバーフローなし）を意味する条件コードである可能性が高いです。ARMアーキテクチャでは、条件コードは命令の実行フローを制御するために非常に重要であり、これらの定数を定義することで、リンカがオブジェクトファイル内の命令の条件コードを正しく解釈し、最終的なバイナリを生成できるようになります。

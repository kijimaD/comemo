# [インデックス 23391] ファイルの概要

このコミットは、Goの共有ライブラリ（shared library）におけるABI（Application Binary Interface）の不一致を検出し、実行時にプログラムを異常終了させるメカニズムを導入するものです。これにより、互換性のない共有ライブラリがロードされることによる未定義の動作やクラッシュを防ぎ、Goプログラムの堅牢性を向上させます。

## 変更の背景

Go言語は、その内部ABI（Application Binary Interface）が安定していないという特徴があります。これは、Goコンパイラやランタイムの最適化、内部構造の変更が頻繁に行われるためです。この不安定なABIは、特に共有ライブラリやプラグインを使用する際に問題を引き起こします。

具体的には、Goプログラムが特定のバージョンのGoツールチェインでコンパイルされた共有ライブラリにリンクされている場合、その共有ライブラリが異なるバージョンのGoツールチェインで再コンパイルされると、ABIの不一致が発生する可能性があります。このような不一致は、プログラムのクラッシュ、未定義の動作、またはセキュリティ上の脆弱性につながる可能性があります。

このコミット以前は、GoのツールチェインはこのようなABIの不一致を自動的に検出するメカニズムを持っていませんでした。そのため、開発者は手動で共有ライブラリの互換性を管理する必要があり、エラーが発生しやすい状況でした。この変更は、共有ライブラリのABI不一致を早期に、かつ確実に検出することで、Goプログラムの信頼性と安定性を向上させることを目的としています。

## 前提知識の解説

### ABI (Application Binary Interface)
ABIは、コンパイルされたプログラム（バイナリ）が、オペレーティングシステムや他のライブラリとどのようにやり取りするかを定義する一連の規約です。これには、関数呼び出し規約、データ構造のメモリレイアウト、レジスタの使用方法などが含まれます。ABIが異なると、バイナリレベルでの互換性が失われ、プログラムが正しく動作しなくなります。Goの場合、内部ABIはGoのバージョン間で安定しておらず、これが共有ライブラリ利用時の課題となります。

### Goのリンカ (`cmd/internal/ld`)
Goは独自のリンカ（`go tool link`、内部的には`cmd/internal/ld`パッケージ）を使用します。これは、C/C++などで一般的に使用されるシステムリンカ（`ld`）とは異なり、Goの特定のニーズに合わせて設計されています。Goリンカは、Goのオブジェクトファイル形式を理解し、シンボル解決、アドレス割り当て、リロケーション処理、そして`moduledata`のようなランタイムに必要なデータ構造の構築を行います。

### Goの共有ライブラリ (`buildmode=shared`, `-linkshared`)
Go 1.5以降、`buildmode=shared`オプションを使用してGoパッケージを共有ライブラリとしてビルドできるようになりました。これにより、複数のGoプログラムが同じ共有ライブラリを動的にリンクし、メモリを節約したり、デプロイメントを簡素化したりできます。`-linkshared`フラグは、Goプログラムをこれらの共有ライブラリにリンクするために使用されます。

### `moduledata`
`moduledata`はGoランタイムの内部データ構造で、実行可能ファイルのレイアウトに関する重要なメタデータを含んでいます。これには、関数、型情報、ガベージコレクションのための情報、スタックトレースのための情報などが含まれます。リンカによって生成され、ランタイムの初期化時に使用されます。共有ライブラリを使用する場合、各共有ライブラリも独自の`moduledata`を持つことができ、これらがリンクされてチェーンを形成します。

### `__.PKGDEF`
`__.PKGDEF`は、Goのコンパイル済みパッケージアーカイブ（`.a`ファイルなど）内に含まれる内部的な定義ファイルです。これは、パッケージの公開API（エクスポートされた型、関数、変数など）の構造を記述しており、他のパッケージがそのパッケージをインポートする際に必要となる情報を提供します。このファイルの内容は、パッケージのABIを定義する上で非常に重要です。

### ELF (Executable and Linkable Format)
ELFは、Unix系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリの標準的なファイル形式です。ELFファイルは、ヘッダ、セクション、セグメントなどで構成され、プログラムのコード、データ、シンボルテーブル、リロケーション情報などが格納されます。

*   **シンボルテーブル**: プログラム内の関数や変数などのシンボルに関する情報（名前、アドレス、型、バインディングなど）を格納します。
*   **`SHT_PROGBITS`**: ELFセクションのタイプの一つで、プログラムが定義する情報（コードや初期化済みデータなど）を含むセクションを示します。
*   **`STT_NOTYPE`**: シンボルのタイプが指定されていないことを示すシンボルタイプです。
*   **`STT_SECTION`**: シンボルがELFファイル内の特定のセクションに関連付けられていることを示すシンボルタイプです。
*   **`STB_GLOBAL`**: シンボルのバインディングの一つで、そのシンボルがグローバルであり、リンク時に他のオブジェクトファイルから参照可能であることを示します。

## 技術的詳細

このコミットは、Goのリンカ（`cmd/internal/ld`）とランタイム（`runtime`）にまたがる変更を導入し、共有ライブラリのABI不一致を検出する5つの主要なステップで構成されています。

1.  **パッケージのABIハッシュの定義**:
    各GoパッケージのABIハッシュは、そのパッケージの`__.PKGDEF`ファイルのSHA1ハッシュとして定義されます。`__.PKGDEF`はパッケージのエクスポートされたインターフェースを記述するため、その内容が変更されればABIも変更されたと見なされます。リンカは、パッケージを処理する際にこのハッシュを計算し、`Library`構造体（`src/cmd/internal/ld/link.go`で定義）に格納します。

2.  **共有ライブラリのABIハッシュの定義**:
    共有ライブラリ全体のABIハッシュは、その共有ライブラリに含まれるすべてのパッケージのABIハッシュを結合し、その結果をSHA1ハッシュすることで定義されます。この際、パッケージのインポートパスでソートすることで、ハッシュの計算順序を決定し、再現性を保証します。これにより、共有ライブラリ内のいずれかのパッケージのABIが変更された場合、共有ライブラリ全体のハッシュも変更されます。

3.  **共有ライブラリビルド時のハッシュ埋め込み**:
    `buildmode=shared`で共有ライブラリをビルドする際、リンカは計算された共有ライブラリのABIハッシュをGo文字列として定義し、`go.link.abihashbytes`というグローバルシンボルとしてライブラリの`.rodata`セクションに埋め込みます。このシンボルは、後で実行可能ファイルが共有ライブラリをロードする際に、そのABIハッシュを取得するために使用されます。

4.  **実行可能ファイルリンク時のハッシュ参照**:
    実行可能ファイルが共有ライブラリにリンクされる際、リンカは以下の2つのハッシュ情報を`moduledata`構造体（`src/runtime/symtab.go`で定義）に格納します。
    *   **リンク時ハッシュ (`linktimehash`)**: 共有ライブラリにリンクした時点で、その共有ライブラリから読み取ったABIハッシュの値。
    *   **ランタイムハッシュへの参照 (`runtimehash`)**: 共有ライブラリ内に埋め込まれた`go.link.abihashbytes`シンボルへのポインタ。これは、実行時に共有ライブラリが実際にロードされた後に、その時点でのABIハッシュを取得するために使用されます。

5.  **ランタイム初期化時のハッシュ検証**:
    Goプログラムのランタイム初期化フェーズ（`runtime.moduledataverify1`関数内）で、`moduledata`に格納された各共有ライブラリについて、`linktimehash`と`runtimehash`が指す値が一致するかどうかがチェックされます。もし両者が一致しない場合、つまり、リンク時と実行時で共有ライブラリのABIが変更されている場合、ランタイムは「abi mismatch detected」というメッセージを出力し、プログラムを異常終了（`throw("abi mismatch")`）させます。

このメカニズムにより、Goプログラムは、互換性のない共有ライブラリがロードされることを防ぎ、予期せぬ動作やクラッシュから保護されます。

## コアとなるコードの解説

### `src/cmd/internal/ld/data.go` の `addgostring` 関数

```go
// addgostring adds str, as a Go string value, to s. symname is the name of the
// symbol used to define the string data and must be unique per linked object.
func addgostring(s *LSym, symname, str string) {
	sym := Linklookup(Ctxt, symname, 0)
	if sym.Type != obj.Sxxx {
		Diag("duplicate symname in addgostring: %s", symname)
	}
	sym.Reachable = true
	sym.Local = true
	sym.Type = obj.SRODATA
	sym.Size = int64(len(str))
	sym.P = []byte(str)
	Addaddr(Ctxt, s, sym)
	adduint(Ctxt, s, uint64(len(str)))
}
```
この`addgostring`関数は、GoのリンカがGo文字列をバイナリに埋め込むためのユーティリティです。指定された文字列`str`を`symname`という名前のシンボルとして、読み取り専用データセクション（`obj.SRODATA`）に追加します。文字列のデータ自体と、その長さがシンボル`s`に追加されます。この関数は、共有ライブラリのABIハッシュをGo文字列としてバイナリに埋め込むために利用されます。

### `src/cmd/internal/ld/lib.go` の `objfile` 関数とハッシュ計算

```go
func objfile(lib *Library) {
	// ...
	if Buildmode == BuildmodeShared {
		before := obj.Boffset(f)
		pkgdefBytes := make([]byte, atolwhex(arhdr.size))
		obj.Bread(f, pkgdefBytes)
		hash := sha1.Sum(pkgdefBytes)
		lib.hash = hash[:]
		obj.Bseek(f, before, 0)
	}
	// ...
}
```
`objfile`関数は、Goのオブジェクトファイル（パッケージアーカイブ）をリンカが読み込む際に呼び出されます。`Buildmode == BuildmodeShared`（共有ライブラリをビルドしている場合）のブロックが追加され、ここで`__.PKGDEF`の内容を読み取り、`sha1.Sum`でハッシュを計算しています。計算されたハッシュは、`lib.hash`フィールドに格納されます。これは、各パッケージのABIハッシュを定義するステップ1の実装です。

### `src/cmd/internal/ld/symtab.go` の `symtab` 関数と共有ライブラリハッシュの埋め込み

```go
// ...
type byPkg []*Library
// ... sort.Interfaceの実装 ...

func symtab() {
	// ...
	if Buildmode == BuildmodeShared {
		sort.Sort(byPkg(Ctxt.Library)) // パッケージをインポートパスでソート
		h := sha1.New()
		for _, l := range Ctxt.Library {
			h.Write(l.hash) // 各パッケージのハッシュを結合
		}
		abihashgostr := Linklookup(Ctxt, "go.link.abihash."+filepath.Base(outfile), 0)
		abihashgostr.Reachable = true
		abihashgostr.Type = obj.SRODATA
		var hashbytes []byte
		addgostring(abihashgostr, "go.link.abihashbytes", string(h.Sum(hashbytes))) // 共有ライブラリ全体のハッシュを埋め込み
	}
	// ...
	if len(Ctxt.Shlibs) > 0 {
		// ... moduledataに共有ライブラリのハッシュ情報を格納 ...
		for i, shlib := range Ctxt.Shlibs {
			// modulehashes[i].modulename
			modulename := filepath.Base(shlib.Path)
			addgostring(modulehashes, fmt.Sprintf("go.link.libname.%d", i), modulename)

			// modulehashes[i].linktimehash
			addgostring(modulehashes, fmt.Sprintf("go.link.linkhash.%d", i), string(shlib.Hash))

			// modulehashes[i].runtimehash (シンボルへの参照)
			abihash := Linklookup(Ctxt, "go.link.abihash."+modulename, 0)
			abihash.Reachable = true
			Addaddr(Ctxt, modulehashes, abihash)
		}
		// ...
	}
}
```
`symtab`関数は、リンカがシンボルテーブルを構築する際に呼び出されます。
`Buildmode == BuildmodeShared`のブロックでは、まず`Ctxt.Library`（リンクされるパッケージのリスト）をインポートパスでソートし、各パッケージのハッシュを結合して共有ライブラリ全体のABIハッシュを計算します。そして、`addgostring`を使ってこのハッシュを`go.link.abihashbytes`というグローバルシンボルとして共有ライブラリに埋め込みます。これはステップ2と3の実装です。

また、`len(Ctxt.Shlibs) > 0`のブロックでは、実行可能ファイルがリンクする各共有ライブラリについて、その名前、リンク時に読み取ったハッシュ（`shlib.Hash`）、そして共有ライブラリ内に埋め込まれたランタイムハッシュシンボル（`go.link.abihash.` + `modulename`）への参照を`moduledata`に格納します。これはステップ4の実装です。

### `src/runtime/symtab.go` の `moduledata` と `moduledataverify1`

```go
type moduledata struct {
	// ...
	modulename   string
	modulehashes []modulehash
	// ...
}

type modulehash struct {
	modulename   string
	linktimehash string
	runtimehash  *string
}

func moduledataverify1(datap *moduledata) {
	// ...
	for _, modulehash := range datap.modulehashes {
		if modulehash.linktimehash != *modulehash.runtimehash {
			println("abi mismatch detected between", datap.modulename, "and", modulehash.modulename)
			throw("abi mismatch")
		}
	}
}
```
`moduledata`構造体には、このコミットで`modulename`と`modulehashes`フィールドが追加されました。`modulehashes`は`modulehash`構造体のスライスで、各`modulehash`は共有ライブラリの名前、リンク時に記録されたハッシュ、そしてランタイム時に共有ライブラリから取得されるハッシュへのポインタを保持します。

`moduledataverify1`関数は、Goランタイムの初期化中に呼び出され、`moduledata`の整合性を検証します。このコミットにより、`modulehashes`スライスをイテレートし、`linktimehash`と`runtimehash`が指す値が一致するかどうかをチェックするロジックが追加されました。もし不一致が検出された場合、`abi mismatch`メッセージを出力し、`throw`関数を呼び出してプログラムを異常終了させます。これはステップ5の実装であり、ABI不一致検出の最終的なトリガーとなります。

# [インデックス 27131] ファイルの概要

このコミットは、Goコンパイラの内部における`structpkg`というグローバル変数を削除し、その役割をローカルな引数として渡す形に変更するリファクタリングです。これにより、コンパイラのコードのモジュール性が向上し、グローバル状態への依存が減らされます。

## コミット

`cmd/compile: remove structpkg global variable`

`structpkg`グローバル変数は、インポート中にメソッドを宣言する際の内部的な整合性検証にのみ使用されていました。この変更では、その値をパーサーとバイナリインポーター内で直接追跡し、関連する関数に引数として渡すようにします。

## 変更の背景

Goコンパイラ（`cmd/compile`）の内部では、型情報やシンボル情報を処理する際に、様々なグローバル変数が使用されていました。しかし、グローバル変数はコードの理解を難しくし、予期せぬ副作用を引き起こす可能性があり、並行処理の際に競合状態の原因となることもあります。

`structpkg`というグローバル変数は、特にパッケージのインポート処理中にメソッドを宣言する際、そのメソッドが属するパッケージの整合性を検証するために使われていました。具体的には、インポートされたメソッドの名前が、そのメソッドが宣言された型（構造体など）のパッケージと一致するかどうかを確認するために利用されていました。

このコミットの背景にあるのは、このような限定的な用途のグローバル変数を排除し、よりクリーンで保守性の高いコードベースを目指すというGoコンパイラ開発チームの継続的な取り組みです。グローバル変数を関数の引数として渡すことで、データの流れが明確になり、特定の変数がどこでどのように使われているかが追いやすくなります。これは、コンパイラの複雑なロジックをデバッグし、将来的に拡張していく上で非常に重要な改善です。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの概念と一般的なプログラミングの知識が必要です。

1.  **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。Goのツールチェインの一部として提供されます。
2.  **パッケージ (`Pkg`)**: Go言語におけるコードの組織化単位です。関連する型、関数、変数などをまとめます。コンパイラ内部では、各パッケージが`Pkg`構造体として表現されます。
3.  **シンボル (`Sym`)**: コンパイラが識別子（変数名、関数名、型名など）を内部的に表現するためのデータ構造です。シンボルは、その識別子の名前、型、属するパッケージなどの情報を含みます。
4.  **メソッド宣言**: Goにおいて、レシーバを持つ関数はメソッドと呼ばれます。メソッドは特定の型に関連付けられ、その型の値に対して操作を行います。
5.  **インポート処理**: Goコンパイラが他のパッケージの定義（型、関数、メソッドなど）を読み込み、現在のコンパイル単位で利用可能にするプロセスです。バイナリインポートは、コンパイル済みのパッケージ情報（`.a`ファイルなど）を読み込むことを指します。
6.  **グローバル変数**: プログラムのどこからでもアクセス可能な変数です。利便性がある一方で、状態管理が複雑になり、意図しない変更や競合状態のリスクを高めます。
7.  **ローカル変数と引数**: 関数内で宣言される変数（ローカル変数）や、関数に渡される値（引数）は、その関数のスコープ内でのみ有効です。これにより、データのカプセル化が促進され、副作用が限定されます。
8.  **整合性検証**: プログラムの内部状態が期待される規則や制約を満たしていることを確認するプロセスです。コンパイラにおいては、型システムの一貫性やシンボル解決の正確性などを保証するために行われます。
9.  **`parser`構造体**: Goコンパイラの字句解析および構文解析を担当する部分で、ソースコードを解析して抽象構文木（AST）を構築します。`parser`構造体は、解析の状態を保持します。
10. **`bimport` (Binary Importer)**: コンパイル済みのGoパッケージのバイナリ形式を読み込み、その型情報やシンボル情報を現在のコンパイルセッションに統合するモジュールです。

## 技術的詳細

このコミットの核心は、Goコンパイラの`gc`（Go Compiler）パッケージ内で使用されていた`structpkg`という`*Pkg`型のグローバル変数を廃止することです。この変数は、主に以下の目的で使用されていました。

*   **メソッド宣言時の整合性検証**: パッケージをインポートする際に、メソッドが宣言されると、そのメソッドのシンボルが属するパッケージが、`structpkg`が指すパッケージと一致するかどうかを検証していました。これは、インポートされたメソッドが正しいパッケージに属していることを保証するための内部チェックでした。

変更の具体的なアプローチは以下の通りです。

1.  **`structpkg`グローバル変数の削除**: `src/cmd/compile/internal/gc/go.go`から`var structpkg *Pkg`の宣言が削除されます。
2.  **`parser`構造体へのフィールド追加**: `src/cmd/compile/internal/gc/parser.go`の`parser`構造体に、一時的に`structpkg *Pkg`フィールドが追加されます。コミットメッセージには`// TODO(gri) remove this once we switch to binary export format`とあり、これは将来的にバイナリエクスポート形式が変更された際にこのフィールドも不要になることを示唆しています。このフィールドは、パーサーがメソッドを処理する際に、そのメソッドが属するパッケージ情報を一時的に保持するために使われます。
3.  **`addmethod`関数のシグネチャ変更**: `src/cmd/compile/internal/gc/dcl.go`にある`addmethod`関数のシグネチャが変更され、`tpkg *Pkg`という新しい引数が追加されます。
    *   変更前: `func addmethod(sf *Sym, t *Type, local bool, nointerface bool)`
    *   変更後: `func addmethod(msym *Sym, t *Type, tpkg *Pkg, local, nointerface bool)`
    この`tpkg`引数は、メソッドが宣言された型が属するパッケージ情報（インポート時のみ関連）を直接受け取る役割を担います。これにより、`addmethod`関数はグローバル変数に依存することなく、必要なパッケージ情報を取得できるようになります。
4.  **呼び出し箇所の更新**: `bimport.go`、`parser.go`、`typecheck.go`内の`addmethod`関数の呼び出し箇所が、新しいシグネチャに合わせて更新されます。
    *   `bimport.go`では、バイナリインポート中にメソッドを追加する際に、`tsym.Pkg`（型シンボルが属するパッケージ）を`addmethod`に渡すようになります。
    *   `parser.go`では、`hidden_pkg_importsym`関数内で`p.structpkg = s.Pkg`としてパッケージ情報を`parser`構造体に保存し、`hidden_fndcl`関数内で`p.structpkg`を`addmethod`に渡します。
    *   `typecheck.go`では、ローカルで宣言されたメソッドの場合、`tpkg`引数に`nil`を渡すようになります。これは、ローカルメソッドの場合はグローバルな`structpkg`による整合性検証が不要であるためです。
5.  **整合性検証ロジックの変更**: `addmethod`関数内の整合性検証ロジックも、`structpkg`グローバル変数ではなく、新しく追加された`tpkg`引数を使用するように変更されます。
    *   変更前: `if importpkg != nil && f.Sym != nil && !exportname(f.Sym.Name) && f.Sym.Pkg != structpkg { ... }`
    *   変更後: `if tpkg != nil && f.Sym != nil && !exportname(f.Sym.Name) && f.Sym.Pkg != tpkg { ... }`
    これにより、インポートされた非公開メソッドの名前が、そのメソッドが属するパッケージと一致しない場合に`Fatalf`（致命的なエラー）を発生させるという検証ロジックが、より局所的な情報に基づいて行われるようになります。

この変更は、コンパイラの内部設計において、グローバル状態への依存を減らし、関数の純度を高めるという重要な原則に従っています。これにより、コードの可読性、テスト容易性、および並行処理の安全性が向上します。

## コアとなるコードの解説

このコミットの主要な変更は、`structpkg`というグローバル変数を廃止し、その代わりに必要な情報を関数の引数として渡す、または関連する構造体（`parser`）のフィールドとして保持するようにした点です。

1.  **グローバル変数の削除 (`src/cmd/compile/internal/gc/go.go`)**:
    `var structpkg *Pkg`の行が削除されたことで、コンパイラのコードベースから一つのグローバル状態が取り除かれました。これは、コードの依存関係を減らし、特定の処理がどのグローバル変数に影響を与えるかを追跡する手間を省く上で非常に重要です。

2.  **`addmethod`関数のシグネチャ変更と役割の明確化 (`src/cmd/compile/internal/gc/dcl.go`)**:
    `addmethod`関数は、Goの型にメソッドを追加する役割を担っています。変更前は、この関数が内部で`structpkg`グローバル変数に依存していましたが、新しいシグネチャ`func addmethod(msym *Sym, t *Type, tpkg *Pkg, local, nointerface bool)`では、`tpkg *Pkg`という引数が追加されました。
    *   `msym *Sym`: 追加するメソッドのシンボル。
    *   `t *Type`: メソッドの関数型（レシーバを含む）。
    *   `tpkg *Pkg`: メソッドを宣言している型が属するパッケージ。これはインポート時にのみ関連し、整合性検証のために使用されます。ローカルで宣言されたメソッドの場合は`nil`が渡されます。
    *   `local bool`: メソッドがローカルで宣言されたものかどうかのフラグ。
    *   `nointerface bool`: インターフェースに含めないメソッドかどうかのフラグ。

    この変更により、`addmethod`関数は、必要なすべての情報を引数として受け取る「より純粋な」関数になりました。特に、インポートされた非公開メソッドのパッケージ整合性チェック（`if tpkg != nil && f.Sym != nil && !exportname(f.Sym.Name) && f.Sym.Pkg != tpkg`）が、グローバル変数ではなく`tpkg`引数に基づいて行われるようになり、データの流れが明確になりました。

3.  **`bimport.go`における`addmethod`の呼び出し変更**:
    バイナリインポーターは、コンパイル済みのパッケージからメソッド情報を読み込む際に`addmethod`を呼び出します。以前は`structpkg`を一時的に設定・復元するブロックがありましたが、これが削除され、`addmethod(sym, tn.Type, tsym.Pkg, false, false)`のように、型シンボル`tsym`が属するパッケージを直接`tpkg`引数として渡すようになりました。これにより、インポート処理中のメソッド追加が、より直接的かつグローバル状態に依存しない形で行われます。

4.  **`parser.go`における`structpkg`フィールドの導入と利用**:
    `parser`構造体に`structpkg *Pkg`フィールドが追加され、`hidden_pkg_importsym`関数内でインポートされたシンボルのパッケージがこのフィールドに保存されるようになりました。そして、`hidden_fndcl`関数内でメソッドを宣言する際に、`addmethod(s4, ss.Type, p.structpkg, false, false)`として、`parser`インスタンスが保持するパッケージ情報を渡すようになりました。これは、パーサーが解析中に一時的に必要なパッケージ情報を自身の状態として保持することで、グローバル変数への依存を回避するアプローチです。`TODO`コメントがあることから、これは将来的なバイナリエクスポート形式の変更に伴い、さらに洗練される可能性が示唆されています。

5.  **`typecheck.go`における`addmethod`の呼び出し変更**:
    型チェックフェーズでローカルに宣言されたメソッドを処理する際、`addmethod(n.Func.Shortname.Sym, t, nil, true, n.Func.Nname.Nointerface)`のように、`tpkg`引数に`nil`が渡されるようになりました。これは、ローカルメソッドの場合、インポート時の整合性検証は不要であるため、`tpkg`に有効なパッケージ情報を渡す必要がないことを示しています。

これらの変更は、Goコンパイラの内部構造をよりモジュール化し、グローバル状態を減らすことで、コードの保守性と理解度を高めるための重要なステップです。

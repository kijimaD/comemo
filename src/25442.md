## 元コミット内容

`cmd/compile`: `go:noinline`ディレクティブのサポートを追加

一部のテストでは、関数のインライン化を無効にする必要がありました。これは現在、いくつかの方法（関数呼び出しの追加、空のswitch文、またはdefer文）で行われていますが、これらは脆弱な方法です。インライン化を防ぐ、より堅牢な`go:noinline`ディレクティブのサポートを追加します。

Fixes #12312

## 変更の背景

Goコンパイラは、プログラムのパフォーマンスを向上させるために、小さな関数を呼び出し元に直接展開する「インライン化」という最適化を行います。しかし、特定のシナリオ、特にテストコードやデバッグにおいて、このインライン化を無効にしたい場合があります。

コミットメッセージによると、この変更以前は、インライン化を無効にするために以下のような「脆弱な」ハックが用いられていました。

1.  **関数呼び出しの追加**: 意図的に余分な関数呼び出しを追加することで、コンパイラが関数をインライン化しないように仕向ける。
2.  **空のswitch文**: 関数内に意味のない空の`switch`文を挿入することで、コンパイラのインライン化ヒューリスティックを回避する。
3.  **defer文**: `defer`文は関数の実行フローに影響を与えるため、インライン化を抑制する効果がある場合がある。

これらの方法は、コードの意図を不明瞭にし、将来のコンパイラの変更によって効果が失われる可能性がありました。また、コードの可読性や保守性も低下させます。このコミットは、このような問題に対処し、インライン化を無効にするための公式かつ堅牢なメカニズムとして`go:noinline`ディレクティブを導入することを目的としています。これにより、特にベンチマークやプロファイリング、特定のテストケースにおいて、関数のインライン化挙動をより正確に制御できるようになります。

## 前提知識の解説

### コンパイラの最適化とインライン化

**コンパイラ**は、人間が書いたソースコードをコンピュータが実行できる機械語に変換するプログラムです。この変換プロセス中に、コンパイラはプログラムの実行速度を向上させたり、メモリ使用量を削減したりするための様々な**最適化**を行います。

**インライン化 (Inlining)** は、コンパイラが行う最も一般的な最適化の一つです。これは、小さな関数が呼び出される際に、その関数の本体を呼び出し元のコードに直接コピー＆ペーストするような処理です。

**インライン化のメリット:**
*   **関数呼び出しのオーバーヘッド削減**: 関数呼び出しには、スタックフレームのセットアップ、引数のプッシュ、戻りアドレスの保存などのオーバーヘッドが伴います。インライン化により、これらのオーバーヘッドがなくなります。
*   **さらなる最適化の機会**: 関数本体が呼び出し元に統合されることで、コンパイラはより大きなコードブロック全体を見て、レジスタ割り当ての改善、デッドコードの削除、定数伝播などの追加の最適化を適用できるようになります。
*   **キャッシュ効率の向上**: コードが連続して配置されることで、CPUの命令キャッシュの効率が向上する可能性があります。

**インライン化のデメリット:**
*   **コードサイズの増加**: 関数本体が複数回コピーされるため、最終的な実行可能ファイルのサイズが増加する可能性があります。これにより、命令キャッシュミスが増える可能性もあります。
*   **コンパイル時間の増加**: コンパイラがより多くのコードを処理し、より複雑な最適化を行うため、コンパイル時間が増加する可能性があります。
*   **デバッグの複雑化**: インライン化された関数は、ソースコード上の関数呼び出しと機械語の実行パスが直接対応しないため、デバッガでのステップ実行が難しくなることがあります。

Goコンパイラは、関数のサイズや複雑さに基づいて、自動的にインライン化を行うかどうかを決定します。通常、非常に小さな関数（例: ゲッター/セッター）はインライン化されやすい傾向があります。

### Goコンパイラの構造

Goコンパイラ（`cmd/compile`）は、複数のステージで構成されています。
1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換します。`src/cmd/compile/internal/gc/lex.go`が関連します。
2.  **構文解析 (Syntactic Analysis)**: トークンのストリームを解析し、プログラムの構造を抽象構文木 (AST) として構築します。`src/cmd/compile/internal/gc/go.y` (Yacc/Bisonの入力ファイル) とそれから生成される`src/cmd/compile/internal/gc/y.go`が関連します。
3.  **型チェックと意味解析 (Type Checking and Semantic Analysis)**: ASTを走査し、型の整合性をチェックし、名前解決などの意味的な検証を行います。
4.  **中間表現 (IR) 生成**: ASTをコンパイラ内部の中間表現に変換します。
5.  **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用します。インライン化はこの段階で行われます。`src/cmd/compile/internal/gc/inl.go`が関連します。
6.  **コード生成 (Code Generation)**: 最適化された中間表現をターゲットアーキテクチャの機械語に変換します。

### Goのコンパイラディレクティブ (Pragmas)

Go言語には、コンパイラの挙動を制御するための特別なコメント形式のディレクティブ（プラグマ）があります。これらは`//go:`で始まり、特定の関数や変数宣言の直前に記述されます。例としては、`//go:noescape`（ポインタがヒープにエスケープしないことを保証）、`//go:nosplit`（関数がスタックを分割しないことを保証）などがあります。これらはコンパイラにヒントを与え、より積極的な最適化を可能にしたり、特定の制約を強制したりするために使用されます。

## 技術的詳細

このコミットは、Goコンパイラのフロントエンドと最適化パスに`go:noinline`ディレクティブを統合します。

1.  **字句解析器 (`lex.go`) の変更**:
    *   `getlinepragma()`関数に、`//go:noinline`という文字列を認識するロジックが追加されます。
    *   このディレクティブが検出されると、グローバル変数`noinline`が`true`に設定されます。この`noinline`変数は、次に続く関数宣言にこの属性を適用するために使用されます。

2.  **構文解析器 (`go.y`, `y.go`) の変更**:
    *   Yaccの文法定義ファイル`go.y`が更新され、関数宣言の処理中に`noinline`フラグが考慮されるようになります。
    *   具体的には、関数宣言を処理するルールにおいて、`noinline`グローバル変数の値が、現在解析中の関数の抽象構文木ノード（`Node`）の`Func`フィールド内の`Noinline`属性にコピーされます。
    *   関数宣言の処理が完了した後、`noinline`グローバル変数は`false`にリセットされ、次の関数宣言に誤って適用されないようにします。これは、他のディレクティブ（`noescape`, `norace`, `nosplit`, `nowritebarrier`, `systemstack`）と同様のパターンです。

3.  **AST構造 (`syntax.go`) の変更**:
    *   `src/cmd/compile/internal/gc/syntax.go`内の`Func`構造体に、`Noinline bool`フィールドが追加されます。このフィールドは、その関数がインライン化されるべきではないことを示すブール値フラグとして機能します。

4.  **インライン化ロジック (`inl.go`) の変更**:
    *   `caninl(fn *Node)`関数は、特定の関数`fn`がインライン化可能かどうかを判断するGoコンパイラの主要な関数です。
    *   この関数に新しいチェックが追加されます。`if fn.Func.Noinline { return }`という行が挿入され、もし関数の`Noinline`フラグが`true`であれば、その関数はインライン化の候補から除外され、即座に`caninl`関数からリターンします。これにより、`go:noinline`ディレクティブが指定された関数は、他のインライン化の条件を満たしていても強制的にインライン化されなくなります。

これらの変更により、`//go:noinline`コメントがソースコードに記述されると、字句解析器がそれを認識し、構文解析器がその情報を関数のASTノードに付与し、最終的にインライン化パスがそのフラグを尊重してインライン化を行わない、という一連のフローが確立されます。

## コアとなるコードの解説

このコミットの核となる変更は、Goコンパイラが`//go:noinline`という特殊なコメントを認識し、それによってマークされた関数をインライン化しないようにするメカニズムを導入することです。

1.  **`lex.go`におけるディレクティブの認識**:
    `getlinepragma()`関数は、ソースコード中の`//go:`で始まるコメント（プラグマ）を解析する役割を担っています。このコミットでは、`verb == "go:noinline"`という条件が追加され、もしこの文字列が検出された場合、グローバル変数`noinline`が`true`に設定されます。これは、次に続く関数宣言がインライン化を無効にする必要があることをコンパイラの他の部分に伝える一時的なフラグとして機能します。

2.  **`go.y`と`syntax.go`における属性の伝播**:
    `go.y`はGo言語の文法を定義するYaccファイルです。関数宣言が解析される際（`xfndcl`ルール）、`noinline`グローバル変数の現在の値が、その関数の抽象構文木（AST）ノードの`Func`構造体内の`Noinline`フィールドにコピーされます。`syntax.go`で定義されている`Func`構造体は、関数の様々な属性（例: `Norace`, `Nosplit`など）を保持するためのものです。`Noinline`フィールドが追加されたことで、各関数がインライン化を無効にすべきかどうかという情報が、その関数のASTノードに永続的に関連付けられるようになります。関数宣言の処理後、`noinline`グローバル変数は`false`にリセットされ、次の関数に誤って影響を与えないようにします。

3.  **`inl.go`におけるインライン化の抑制**:
    `caninl(fn *Node)`関数は、コンパイラの最適化フェーズにおいて、特定の関数`fn`をインライン化すべきかどうかを決定するロジックを含んでいます。この関数は、インライン化を妨げる様々な条件（例: 関数が大きすぎる、再帰的である、特定の言語機能を使用しているなど）をチェックします。このコミットでは、これらのチェックの冒頭に`if fn.Func.Noinline { return }`という行が追加されました。これは、もし関数のASTノードに`Noinline`フラグが設定されていれば、他のインライン化条件に関わらず、その関数はインライン化されずに即座に処理を終了することを意味します。

これらの変更が連携することで、開発者はソースコードに`//go:noinline`と記述するだけで、Goコンパイラがその関数をインライン化しないように強制できるようになります。これは、コンパイラの最適化挙動をより細かく制御したい場合に非常に有用な機能です。

**インライン化 (Inlining)** は、コンパイラが行う最も一般的な最適化の一つです。これは、小さな関数が呼び出される際に、その関数の本体を呼び出し元のコードに直接コピー＆ペーストするような処理です。

**インライン化のメリット:**
*   **関数呼び出しのオーバーヘッド削減**: 関数呼び出しには、スタックフレームのセットアップ、引数のプッシュ、戻りアドレスの保存などのオーバーヘッドが伴います。インライン化により、これらのオーバーヘッドがなくなります。
*   **さらなる最適化の機会**: 関数本体が呼び出し元に統合されることで、コンパイラはより大きなコードブロック全体を見て、レジスタ割り当ての改善、デッドコードの削除、定数伝播などの追加の最適化を適用できるようになります。
*   **キャッシュ効率の向上**: コードが連続して配置されることで、CPUの命令キャッシュの効率が向上する可能性があります。

**インライン化のデメリット:**
*   **コードサイズの増加**: 関数本体が複数回コピーされるため、最終的な実行可能ファイルのサイズが増加する可能性があります。これにより、命令キャッシュミスが増える可能性もあります。
*   **コンパイル時間の増加**: コンパイラがより多くのコードを処理し、より複雑な最適化を行うため、コンパイル時間が増加する可能性があります。
*   **デバッグの複雑化**: インライン化された関数は、ソースコード上の関数呼び出しと機械語の実行パスが直接対応しないため、デバッガでのステップ実行が難しくなることがあります。

Goコンパイラは、関数のサイズや複雑さに基づいて、自動的にインライン化を行うかどうかを決定します。通常、非常に小さな関数（例: ゲッター/セッター）はインライン化されやすい傾向があります。

### Goコンパイラの構造

Goコンパイラ（`cmd/compile`）は、複数のステージで構成されています。
1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換します。`src/cmd/compile/internal/gc/lex.go`が関連します。
2.  **構文解析 (Syntactic Analysis)**: トークンのストリームを解析し、プログラムの構造を抽象構文木 (AST) として構築します。`src/cmd/compile/internal/gc/go.y` (Yacc/Bisonの入力ファイル) とそれから生成される`src/cmd/compile/internal/gc/y.go`が関連します。
3.  **型チェックと意味解析 (Type Checking and Semantic Analysis)**: ASTを走査し、型の整合性をチェックし、名前解決などの意味的な検証を行います。
4.  **中間表現 (IR) 生成**: ASTをコンパイラ内部の中間表現に変換します。
5.  **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用します。インライン化はこの段階で行われます。`src/cmd/compile/internal/gc/inl.go`が関連します。
6.  **コード生成 (Code Generation)**: 最適化された中間表現をターゲットアーキテクチャの機械語に変換します。

### Goのコンパイラディレクティブ (Pragmas)

Go言語には、コンパイラの挙動を制御するための特別なコメント形式のディレクティブ（プラグマ）があります。これらは`//go:`で始まり、特定の関数や変数宣言の直前に記述されます。例としては、`//go:noescape`（ポインタがヒープにエスケープしないことを保証）、`//go:nosplit`（関数がスタックを分割しないことを保証）などがあります。これらはコンパイラにヒントを与え、より積極的な最適化を可能にしたり、特定の制約を強制したりするために使用されます。

## 技術的詳細

このコミットは、Goコンパイラのフロントエンドと最適化パスに`go:noinline`ディレクティブを統合します。

1.  **字句解析器 (`lex.go`) の変更**:
    *   `getlinepragma()`関数に、`//go:noinline`という文字列を認識するロジックが追加されます。
    *   このディレクティブが検出されると、グローバル変数`noinline`が`true`に設定されます。この`noinline`変数は、次に続く関数宣言にこの属性を適用するために使用されます。

2.  **構文解析器 (`go.y`, `y.go`) の変更**:
    *   Yaccの文法定義ファイル`go.y`が更新され、関数宣言の処理中に`noinline`フラグが考慮されるようになります。
    *   具体的には、関数宣言を処理するルールにおいて、`noinline`グローバル変数の値が、現在解析中の関数の抽象構文木ノード（`Node`）の`Func`フィールド内の`Noinline`属性にコピーされます。
    *   関数宣言の処理が完了した後、`noinline`グローバル変数は`false`にリセットされ、次の関数宣言に誤って適用されないようにします。これは、他のディレクティブ（`noescape`, `norace`, `nosplit`, `nowritebarrier`, `systemstack`）と同様のパターンです。

3.  **AST構造 (`syntax.go`) の変更**:
    *   `src/cmd/compile/internal/gc/syntax.go`内の`Func`構造体に、`Noinline bool`フィールドが追加されます。このフィールドは、その関数がインライン化されるべきではないことを示すブール値フラグとして機能します。

4.  **インライン化ロジック (`inl.go`) の変更**:
    *   `caninl(fn *Node)`関数は、特定の関数`fn`がインライン化可能かどうかを判断するGoコンパイラの主要な関数です。
    *   この関数に新しいチェックが追加されます。`if fn.Func.Noinline { return }`という行が挿入され、もし関数の`Noinline`フラグが`true`であれば、その関数はインライン化の候補から除外され、即座に`caninl`関数からリターンします。これにより、`go:noinline`ディレクティブが指定された関数は、他のインライン化の条件を満たしていても強制的にインライン化されなくなります。

これらの変更により、`//go:noinline`コメントがソースコードに記述されると、字句解析器がそれを認識し、構文解析器がその情報を関数のASTノードに付与し、最終的にインライン化パスがそのフラグを尊重してインライン化を行わない、という一連のフローが確立されます。

## コアとなるコードの解説

このコミットの核となる変更は、Goコンパイラが`//go:noinline`という特殊なコメントを認識し、それによってマークされた関数をインライン化しないようにするメカニズムを導入することです。

1.  **`lex.go`におけるディレクティブの認識**:
    `getlinepragma()`関数は、ソースコード中の`//go:`で始まるコメント（プラグマ）を解析する役割を担っています。このコミットでは、`verb == "go:noinline"`という条件が追加され、もしこの文字列が検出された場合、グローバル変数`noinline`が`true`に設定されます。これは、次に続く関数宣言がインライン化を無効にする必要があることをコンパイラの他の部分に伝える一時的なフラグとして機能します。

2.  **`go.y`と`syntax.go`における属性の伝播**:
    `go.y`はGo言語の文法を定義するYaccファイルです。関数宣言が解析される際（`xfndcl`ルール）、`noinline`グローバル変数の現在の値が、その関数の抽象構文木（AST）ノードの`Func`構造体内の`Noinline`フィールドにコピーされます。`syntax.go`で定義されている`Func`構造体は、関数の様々な属性（例: `Norace`, `Nosplit`など）を保持するためのものです。`Noinline`フィールドが追加されたことで、各関数がインライン化を無効にすべきかどうかという情報が、その関数のASTノードに永続的に関連付けられるようになります。関数宣言の処理後、`noinline`グローバル変数は`false`にリセットされ、次の関数に誤って影響を与えないようにします。

3.  **`inl.go`におけるインライン化の抑制**:
    `caninl(fn *Node)`関数は、コンパイラの最適化フェーズにおいて、特定の関数`fn`をインライン化すべきかどうかを決定するロジックを含んでいます。この関数は、インライン化を妨げる様々な条件（例: 関数が大きすぎる、再帰的である、特定の言語機能を使用しているなど）をチェックします。このコミットでは、これらのチェックの冒頭に`if fn.Func.Noinline { return }`という行が追加されました。これは、もし関数のASTノードに`Noinline`フラグが設定されていれば、他のインライン化条件に関わらず、その関数はインライン化されずに即座に処理を終了することを意味します。

これらの変更が連携することで、開発者はソースコードに`//go:noinline`と記述するだけで、Goコンパイラがその関数をインライン化しないように強制できるようになります。これは、コンパイラの最適化挙動をより細かく制御したい場合に非常に有用な機能です。

# [インデックス 19756] ファイルの概要

このコミットは、Go言語の標準ライブラリにおいて、Windowsオペレーティングシステムでのシンボリックリンク（symlink）およびハードリンク（hard link）のサポートを実装するものです。これまでWindows環境ではGoの`os`パッケージがシンボリックリンクの作成や読み取りを直接サポートしていませんでしたが、この変更により、Windowsのファイルシステムが提供するシンボリックリンク機能がGoプログラムから利用可能になります。これにより、Goアプリケーションのクロスプラットフォーム互換性が向上し、Windows上でのファイル操作の柔軟性が増します。

## 変更の背景

この変更の背景には、Go言語がクロスプラットフォーム開発を強く意識しているにもかかわらず、Windows環境におけるシンボリックリンクのサポートが不十分であったという問題があります。コミットメッセージにある`Fixes #5750`が示すように、この機能はGoのIssue 5750（`https://code.google.com/p/go/issues/detail?id=5750`）で報告されていた課題に対応するものです。

従来のGoの`os`パッケージでは、Unix系システムではシンボリックリンクを扱う機能が提供されていましたが、Windowsではこれらの機能が未実装または限定的でした。これにより、Windows上で動作するGoプログラムがシンボリックリンクを必要とするシナリオ（例えば、開発環境のセットアップ、ビルドシステム、特定のファイル管理ツールなど）で、互換性の問題や機能の制限が生じていました。

Windows Vista以降のWindows OSは、NTFSファイルシステム上でシンボリックリンクとハードリンクをサポートしています。しかし、これらの機能はUnix系OSのそれとは異なるAPI（Win32 API）を通じて提供されます。このコミットは、Goの標準ライブラリがこれらのWindows固有のAPIを適切に呼び出し、Goの抽象化されたファイルシステム操作インターフェースを通じてシンボリックリンク機能を提供できるようにすることを目的としています。これにより、Go開発者はWindows環境でもUnix系OSと同様の感覚でシンボリックリンクを扱えるようになり、Goプログラムの移植性と機能性が向上します。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

### 1. シンボリックリンク (Symbolic Link / Symlink)
シンボリックリンクは、ファイルシステム上の別のファイルやディレクトリへの参照（ポインタ）として機能する特殊なファイルです。Unix系OSでは「ソフトリンク」とも呼ばれます。シンボリックリンクをたどると、参照先のファイルやディレクトリにアクセスできます。参照元が削除されてもシンボリックリンク自体は残りますが、参照先がなくなると「壊れたリンク」となります。

### 2. ハードリンク (Hard Link)
ハードリンクは、ファイルシステム上の同じデータブロックを指す複数のエントリ（ファイル名）です。元のファイルとハードリンクは、ファイルシステム上では区別されず、どちらか一方を削除してもデータブロックが参照され続ける限りファイルは存在し続けます。すべてのハードリンクが削除されたときに初めてデータブロックが解放されます。ハードリンクは同じファイルシステム内でのみ作成可能で、ディレクトリに対しては作成できません（Unix系OSの場合）。

### 3. Windowsにおけるリンクの種類とAPI
Windowsでは、シンボリックリンクとハードリンクはNTFSファイルシステムでサポートされています。
*   **シンボリックリンク**: `CreateSymbolicLink` Win32 APIを使用して作成されます。ファイルとディレクトリの両方に対して作成できます。作成には管理者権限が必要な場合があります（開発者モードが有効な場合は不要）。
*   **ハードリンク**: `CreateHardLink` Win32 APIを使用して作成されます。ファイルに対してのみ作成可能で、ディレクトリには作成できません。
*   **ジャンクションポイント (Junction Point)**: ディレクトリ専用のシンボリックリンクのようなもので、`CreateSymbolicLink`とは異なるAPIで作成されますが、Goの`os`パッケージではシンボリックリンクとして扱われることがあります。
*   **リパースポイント (Reparse Point)**: Windowsファイルシステムが提供する拡張機能で、ファイルやディレクトリに特別な属性（リパースタグ）とデータを関連付けることができます。シンボリックリンクやジャンクションポイントは、このリパースポイントのメカニズムを利用して実装されています。`FILE_ATTRIBUTE_REPARSE_POINT`属性や`IO_REPARSE_TAG_SYMLINK`タグがこれに該当します。

### 4. Go言語の`os`パッケージと`syscall`パッケージ
*   **`os`パッケージ**: Goプログラムがオペレーティングシステムと対話するための基本的な機能を提供します。ファイル操作（作成、読み書き、削除）、ディレクトリ操作、プロセス管理、環境変数へのアクセスなどが含まれます。`os.Symlink`や`os.Link`のような高レベルな関数は、このパッケージで定義されます。
*   **`syscall`パッケージ**: オペレーティングシステム固有の低レベルなシステムコールへのアクセスを提供します。`os`パッケージの多くの関数は、内部的に`syscall`パッケージの関数を呼び出してOSの機能を利用しています。Windowsの場合、`syscall`パッケージはWin32 APIのラッパーを提供します。

### 5. `Stat`と`Lstat`
ファイル情報を取得する際に、Unix系OSでは`stat`と`lstat`という2つの異なるシステムコールがあります。
*   **`stat`**: パスがシンボリックリンクを指している場合、そのリンクが指す実際のファイル（リンクのターゲット）の情報を返します。つまり、リンクを「たどる」動作をします。
*   **`lstat`**: パスがシンボリックリンクを指している場合、そのシンボリックリンク自体の情報を返します。リンクを「たどらない」動作をします。

このコミットでは、WindowsにおいてもこれらのセマンティクスをGoの`os`パッケージで実現するために、`Stat`と`Lstat`の挙動が調整されています。

## 技術的詳細

このコミットの技術的詳細は、主に以下の点に集約されます。

1.  **Windows固有のシンボリックリンク/ハードリンクAPIの統合**:
    *   Goの`syscall`パッケージに、Windowsの`CreateSymbolicLinkW`、`CreateHardLinkW`、`DeviceIoControl`などのWin32 APIが追加されました。これらは、それぞれシンボリックリンクの作成、ハードリンクの作成、およびリパースポイント（シンボリックリンクの実体）の情報を取得するために使用されます。
    *   `Readlink`関数もWindows向けに実装され、`DeviceIoControl`を使ってリパースポイントのデータを読み取り、シンボリックリンクのターゲットパスを抽出します。

2.  **`os`パッケージのプラットフォーム分離と実装**:
    *   `src/pkg/os/file_posix.go`から`Link`と`Symlink`の定義が削除され、`src/pkg/os/file_unix.go`に移動されました。これにより、Unix系OSとWindowsで異なる実装を持つことが明確化されました。
    *   `src/pkg/os/file_windows.go`に、Windows固有の`os.Link`と`os.Symlink`の実装が追加されました。
        *   `os.Link`は`syscall.CreateHardLink`を呼び出します。
        *   `os.Symlink`は`syscall.CreateSymbolicLink`を呼び出します。この際、ターゲットがディレクトリであるかどうかの判定（`Lstat`を使用）を行い、`SYMBOLIC_LINK_FLAG_DIRECTORY`フラグを適切に設定します。また、Windowsのパス区切り文字がバックスラッシュ（`\`）であるため、入力パスのフォワードスラッシュ（`/`）をバックスラッシュに変換する`fromSlash`ヘルパー関数が導入されています。

3.  **`Stat`と`Lstat`のセマンティクス調整**:
    *   `src/pkg/os/stat_windows.go`において、`Stat`関数がシンボリックリンクをたどるように変更されました。これは、`Lstat`でファイル情報を取得し、それがシンボリックリンク（`ModeSymlink`フラグを持つ）であれば、`Readlink`でターゲットパスを取得し、そのターゲットに対して再度`Stat`を呼び出すというループによって実現されます。
    *   `Lstat`関数は、シンボリックリンク自体（リパースポイント）の情報を返すように変更されました。以前のWindows実装では`Lstat`が`Stat`を呼び出しており、リンクをたどってしまっていましたが、この変更によりUnix系OSの`lstat`と同様の挙動になりました。
    *   `src/pkg/os/types_windows.go`の`fileStat.Mode()`メソッドに、`syscall.FILE_ATTRIBUTE_REPARSE_POINT`属性が設定されている場合に`os.ModeSymlink`フラグを返すロジックが追加されました。これにより、Goの`FileInfo`インターフェースを通じてシンボリックリンクを識別できるようになります。

4.  **パス処理の改善**:
    *   `src/pkg/path/filepath/symlink.go`の`walkSymlinks`関数（シンボリックリンクをたどる汎用ロジック）が、Windowsのパス区切り文字（`\`）も考慮するように修正されました。
    *   `src/pkg/path/filepath/symlink_windows.go`では、`evalSymlinks`が`walkSymlinks`を呼び出した後、Windowsのショートパス（8.3形式）への変換を行う`toShort`関数を呼び出すことで、互換性を確保しています。

5.  **テストの追加と修正**:
    *   `src/pkg/os/os_windows_test.go`が新規追加され、Windows環境でのシンボリックリンクサポートの有無を検出する初期化ロジック（`supportsSymlinks`変数）が導入されました。これにより、シンボリックリンクがサポートされていないWindowsバージョン（例: Vista以前）や、権限がない場合にテストをスキップできるようになりました。
    *   既存のテストファイル（`os_test.go`, `path_test.go`, `match_test.go`など）が、Windowsでのシンボリックリンクサポートを考慮して修正され、`supportsSymlinks`変数に基づいてテストの実行/スキップを制御するようになりました。

これらの変更により、GoはWindows上でもシンボリックリンクとハードリンクをネイティブに、かつクロスプラットフォームなAPIを通じて扱えるようになりました。

## コアとなるコードの解説

### `src/pkg/os/file_windows.go` の `Symlink` 関数

```go
func Symlink(oldname, newname string) error {
	// CreateSymbolicLink is not supported before Windows Vista
	if syscall.LoadCreateSymbolicLink() != nil {
		return &LinkError{"symlink", oldname, newname, syscall.EWINDOWS}
	}

	// '/' does not work in link's content
	oldname = fromSlash(oldname)

	// need the exact location of the oldname when its relative to determine if its a directory
	destpath := oldname
	if !isAbs(oldname) {
		destpath = dirname(newname) + `\` + oldname
	}

	fi, err := Lstat(destpath)
	isdir := err == nil && fi.IsDir()

	n, err := syscall.UTF16PtrFromString(newname)
	if err != nil {
		return &LinkError{"symlink", oldname, newname, err}
	}
	o, err := syscall.UTF16PtrFromString(oldname)
	if err != nil {
		return &LinkError{"symlink", oldname, newname, err}
	}

	var flags uint32
	if isdir {
		flags |= syscall.SYMBOLIC_LINK_FLAG_DIRECTORY
	}
	err = syscall.CreateSymbolicLink(n, o, flags)
	if err != nil {
		return &LinkError{"symlink", oldname, newname, err}
	}
	return nil
}
```
この`Symlink`関数は、Windows上でシンボリックリンクを作成するGoの主要なインターフェースです。
1.  まず、`syscall.LoadCreateSymbolicLink()`を呼び出して、実行環境が`CreateSymbolicLink` APIをサポートしているか（Windows Vista以降か）を確認します。サポートされていない場合はエラーを返します。
2.  Windowsのパス区切り文字が`\`であるため、`oldname`（リンクのターゲット）内の`/`を`\`に変換するために`fromSlash`関数を呼び出します。
3.  `oldname`が相対パスの場合、`newname`（作成されるリンク）からの相対位置を正確に解決するために`destpath`を構築します。
4.  `Lstat(destpath)`を呼び出して、リンクのターゲットがディレクトリであるかどうかを判定します。この情報は、`CreateSymbolicLink` APIに渡すフラグ（`SYMBOLIC_LINK_FLAG_DIRECTORY`）を決定するために必要です。
5.  `newname`と`oldname`をUTF-16形式のポインタに変換します。これはWin32 APIがUTF-16文字列を期待するためです。
6.  `syscall.CreateSymbolicLink`を呼び出して、実際にシンボリックリンクを作成します。`flags`には、ターゲットがディレクトリであれば`SYMBOLIC_LINK_FLAG_DIRECTORY`が設定されます。
7.  エラーが発生した場合は、`os.LinkError`型でラップして返します。

### `src/pkg/os/stat_windows.go` の `Stat` 関数

```go
func Stat(name string) (fi FileInfo, err error) {
	for {
		fi, err = Lstat(name)
		if err != nil {
			return
		}
		if fi.Mode()&ModeSymlink == 0 {
			return
		}
		name, err = Readlink(name)
		if err != nil {
			return
		}
	}
	return fi, err // Unreachable, but for completeness
}
```
この`Stat`関数は、Goの`os.Stat`のWindows向け実装で、シンボリックリンクをたどる挙動を実現します。
1.  無限ループに入ります。
2.  まず、`Lstat(name)`を呼び出して、指定されたパス`name`のファイル情報を取得します。`Lstat`はシンボリックリンク自体をたどらずにその情報を返します。
3.  エラーが発生した場合は、そのエラーを返します。
4.  取得したファイル情報`fi`のモードが`ModeSymlink`フラグを持たない場合（つまり、シンボリックリンクではない場合）、それが最終的なファイルであるため、`fi`を返してループを終了します。
5.  `fi`が`ModeSymlink`フラグを持つ場合（つまり、シンボリックリンクである場合）、`Readlink(name)`を呼び出して、そのシンボリックリンクが指すターゲットパスを取得します。
6.  `Readlink`でエラーが発生した場合は、そのエラーを返します。
7.  取得したターゲットパスを新たな`name`として、ループの先頭に戻り、再度`Lstat`を呼び出します。これにより、シンボリックリンクの連鎖をたどって最終的なファイルに到達するまで処理が繰り返されます。

この実装により、Goの`os.Stat`はWindows上でもUnix系OSと同様にシンボリックリンクを透過的に解決し、最終的なファイルの情報を提供するようになります。

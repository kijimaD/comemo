# [インデックス 25421] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおける値書き換え（value rewrite）処理の構造を改善するものです。具体的には、単一の巨大な書き換え関数を、オペレーション（Op）ごとに分割された複数の小さな関数に再編成しています。これにより、コンパイラが巨大な関数を処理する際に発生していたメモリ不足や分岐オフセットの制限といった問題を解消し、コンパイラ自身のビルドの安定性と効率を向上させています。

## 元コミット内容

このコミットの元のメッセージは以下の通りです。

```
[dev.ssa] cmd/compile: split op rewrites into separate functions

The single value rewrite function is too big. Some compilers
fail on it (out of memory, branch offset too large). Break it
up into a rewrite function per op.
```

これは、単一の巨大な値書き換え関数が、一部のコンパイラでメモリ不足や分岐オフセットの制限によりコンパイルに失敗するという問題に直面していたことを明確に示しています。解決策として、オペレーション（Op）ごとに書き換え関数を分割することが提案されています。

## 変更の背景

Goコンパイラは、プログラムの最適化と機械語への変換のためにSSA（Static Single Assignment）形式の中間表現を使用しています。SSAバックエンドでは、プログラムの各操作（オペレーション、`Op`）に対して、より効率的な機械語命令シーケンスに変換するための「書き換えルール（rewrite rules）」が適用されます。これらのルールは、`src/cmd/compile/internal/ssa/gen/rulegen.go`というツールによって生成され、`rewriteAMD64.go`や`rewritegeneric.go`のようなファイルに出力されます。

元々、これらの書き換えルールは、`rewriteValueAMD64`や`rewriteValuegeneric`といった単一の大きな関数内の巨大な`switch`文として実装されていました。この`switch`文は、GoがサポートするすべてのSSAオペレーション（数千に及ぶ可能性があります）に対応するケースを含んでおり、その結果、生成されるGoソースコードの関数が非常に大きくなっていました。

この巨大な関数は、Goコンパイラ自身をコンパイルする際に問題を引き起こしていました。特に、一部のCコンパイラ（GoコンパイラはC言語で書かれた部分も含む）や、古いバージョンのGoコンパイラが、このような巨大な関数を処理する際に、以下のような問題に直面していました。

1.  **メモリ不足 (Out of memory)**: 巨大な関数を解析・最適化するために、コンパイラが大量のメモリを消費し、システムメモリを使い果たしてしまう。
2.  **分岐オフセットが大きすぎる (Branch offset too large)**: `switch`文の各ケースへのジャンプ命令が、CPUの命令セットが許容する相対分岐オフセットの範囲を超えてしまう。これは、特にx86/x64アーキテクチャにおいて、近接ジャンプ（short jump）命令が特定の範囲内のアドレスにしかジャンプできないという制約があるためです。

これらの問題は、Goコンパイラの開発サイクルにおいて、コンパイラ自身のビルドを不安定にしたり、特定の環境でのビルドを不可能にしたりする原因となっていました。このコミットは、この根本的な問題を解決するために導入されました。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSAは、コンパイラ最適化で広く用いられる中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が容易になり、より強力な最適化（例：共通部分式除去、定数伝播、デッドコード除去など）が可能になります。Goコンパイラも、最適化パスの大部分でSSA形式を使用しています。

### 2. GoコンパイラのバックエンドとSSA

Goコンパイラのバックエンドは、フロントエンドが生成した抽象構文木（AST）をSSA形式に変換し、様々な最適化を適用した後、最終的にターゲットアーキテクチャの機械語に変換します。この過程で、SSAオペレーションは、ターゲットアーチャテクチャのより具体的な命令（例：AMD64の`ADDQ`、`MOVLconst`など）に「書き換え（rewrite）」されます。

### 3. 書き換えルール (Rewrite Rules)

書き換えルールは、特定のSSAオペレーションのパターンを検出し、それをより効率的な別のSSAオペレーションのシーケンスや、直接的な機械語命令に変換するための規則です。例えば、「`ADD`オペレーションの引数の一つが定数である場合、`ADDconst`オペレーションに変換する」といったルールがあります。これらのルールは、`rulegen.go`というGoプログラムによって、Goのソースコードとして自動生成されます。

### 4. `rulegen.go`

`rulegen.go`は、Goコンパイラのビルドプロセスの一部として実行されるコードジェネレータです。このツールは、`.rules`ファイル（例：`amd64.rules`）に記述された高レベルな書き換え規則を読み込み、それをGoのソースコード（例：`rewriteAMD64.go`）に変換します。生成されたGoコードは、コンパイラのSSAバックエンドで実際に使用され、最適化処理を行います。

### 5. `Value`と`Op`

GoコンパイラのSSA形式では、プログラム中の各計算結果が`Value`オブジェクトとして表現されます。各`Value`は、それが実行する操作の種類を示す`Op`（オペレーションコード）を持っています。例えば、`OpAdd64`は64ビット整数の加算を表し、`OpAMD64ADDQ`はAMD64アーキテクチャでの64ビット加算命令を表します。

### 6. コンパイラのコンパイル問題

GoコンパイラはGo言語で書かれていますが、そのビルドプロセスはブートストラップ（bootstrap）と呼ばれる多段階のプロセスを含みます。初期のGoコンパイラはC言語で書かれており、新しいGoコンパイラをビルドするためには、既存のコンパイラ（またはCコンパイラ）が必要です。このコミットが作成された時点では、Goコンパイラの一部がCコンパイラによってコンパイルされる可能性があり、そのCコンパイラが巨大なGo関数を処理できないという問題が発生していました。また、Goコンパイラ自身が巨大な関数を処理する際にも、内部的な制限に達することがありました。

## 技術的詳細

このコミットの核心は、`rulegen.go`が生成する書き換え関数の構造変更にあります。

**変更前**:
`rewriteValueAMD64` (または `rewriteValuegeneric`) 関数は、以下のような構造をしていました。

```go
func rewriteValueAMD64(v *Value, config *Config) bool {
    b := v.Block
    switch v.Op {
    case OpAMD64ADDB:
        // OpAMD64ADDB の書き換えルール群
        // ...
    case OpAMD64ADDL:
        // OpAMD64ADDL の書き換えルール群
        // ...
    // ... 数千の Op ごとのケースが続く
    }
    return false
}
```

この単一の関数内に、すべてのSSAオペレーションに対する書き換えロジックが巨大な`switch`文として集約されていました。各`case`ブロック内には、特定のオペレーションに対する複数の書き換えルールが記述されており、それぞれが`if`条件と`goto`文を多用して実装されていました。

**変更後**:
このコミットでは、`rulegen.go`が以下のようにコードを生成するように変更されました。

1.  **ディスパッチャ関数**: `rewriteValueAMD64` (または `rewriteValuegeneric`) 関数は、各オペレーションに対応する個別の書き換え関数を呼び出すだけのシンプルなディスパッチャになります。

    ```go
    func rewriteValueAMD64(v *Value, config *Config) bool {
        switch v.Op {
        case OpAMD64ADDB:
            return rewriteValueAMD64_OpAMD64ADDB(v, config)
        case OpAMD64ADDL:
            return rewriteValueAMD64_OpAMD64ADDL(v, config)
        // ... 各 Op ごとに個別の関数呼び出し
        }
        return false
    }
    ```

2.  **オペレーションごとの書き換え関数**: 各SSAオペレーションに対して、専用の書き換え関数が生成されます。例えば、`OpAMD64ADDB`に対する書き換えルールは、`rewriteValueAMD64_OpAMD64ADDB`という新しい関数に移動します。

    ```go
    func rewriteValueAMD64_OpAMD64ADDB(v *Value, config *Config) bool {
        b := v.Block
        _ = b // b が使用されない場合があるため
        // OpAMD64ADDB の書き換えルール群 (変更前の case ブロックの内容)
        // ...
        return false
    }
    ```

この変更により、元の巨大な`rewriteValueAMD64`関数は、多数の小さな関数に分割されます。これにより、各関数のサイズが大幅に縮小され、コンパイラがそれらを個別に処理できるようになります。結果として、コンパイラのメモリ使用量が削減され、分岐オフセットの制限も回避されます。

`rulegen.go`の変更点としては、`genRules`関数内で、まずすべてのオペレーション名をソートし、そのリストを使ってメインの`rewriteValue%s`関数（ディスパッチャ）と、各オペレーションごとの`rewriteValue%s_%s`関数を生成するようにロジックが変更されています。

## コアとなるコードの変更箇所

### `src/cmd/compile/internal/ssa/gen/rulegen.go`

このファイルは、SSA書き換えルールを生成するコードジェネレータです。主な変更点は以下の通りです。

*   **オペレーションリストのソート**: `oprules`マップからオペレーション名を抽出し、`sort.Strings(ops)`でソートしています。これにより、生成される関数の順序が安定します。
*   **メイン書き換え関数の変更**:
    *   以前は、`rewriteValue%s`関数内にすべてのオペレーションの`case`文と書き換えロジックが含まれていました。
    *   変更後は、`rewriteValue%s`関数は、`switch v.Op`文を持ち、各`case`で対応するオペレーション固有の書き換え関数（例: `rewriteValue%s_%s(v, config)`）を呼び出すように変更されました。
*   **オペレーションごとの書き換え関数の生成**:
    *   `for _, op := range ops`ループ内で、各オペレーションに対して`func rewriteValue%s_%s(v *Value, config *Config) bool { ... }`という形式の新しい関数が生成されるようになりました。
    *   以前の`case`ブロック内の書き換えロジックが、これらの新しい関数内に移動しました。

### `src/cmd/compile/internal/ssa/rewriteAMD64.go`

このファイルは、AMD64アーキテクチャ固有のSSA書き換えルールが記述された（`rulegen.go`によって生成される）ファイルです。

*   **`rewriteValueAMD64`関数の簡素化**: 以前は巨大な`switch`文とそれに続く大量の書き換えロジックを含んでいましたが、変更後は各`Op`に対して対応する`rewriteValueAMD64_Op<OpName>`関数を呼び出すだけのシンプルなディスパッチャ関数になりました。
    *   例: `case OpAMD64ADDB:` の下にあった複雑なロジックが、`return rewriteValueAMD64_OpAMD64ADDB(v, config)` の呼び出しに置き換えられています。
*   **新しいオペレーションごとの関数の追加**: `rewriteValueAMD64_OpAMD64ADDB`, `rewriteValueAMD64_OpAMD64ADDL`, `rewriteValueAMD64_OpAMD64ADDQ` など、各オペレーションに対応する多数の新しい関数が追加されています。これらの関数は、以前の`rewriteValueAMD64`関数内の各`case`ブロックの内容をそのまま引き継いでいます。

### `src/cmd/compile/internal/ssa/rewritegeneric.go`

このファイルは、アーキテクチャに依存しない汎用的なSSA書き換えルールが記述された（`rulegen.go`によって生成される）ファイルです。

*   `rewriteAMD64.go`と同様に、`rewriteValuegeneric`関数がディスパッチャとなり、各オペレーションに対応する`rewriteValuegeneric_Op<OpName>`関数が新しく生成されています。変更のパターンは`rewriteAMD64.go`と同一です。

## コアとなるコードの解説

変更の核心は、`rulegen.go`が生成するコードの構造にあります。

**`src/cmd/compile/internal/ssa/gen/rulegen.go` の変更点**:

```go
 // Main rewrite routine is a switch on v.Op.
 fmt.Fprintf(w, "func rewriteValue%s(v *Value, config *Config) bool {\\n", arch.name)
-fmt.Fprintln(w, "b := v.Block") // 削除
-
-// generate code for each rule
 fmt.Fprintf(w, "switch v.Op {\\n")
-var ops []string // 削除
-for op := range oprules { // 削除
-    ops = append(ops, op) // 削除
-} // 削除
-sort.Strings(ops) // 削除
 for _, op := range ops {
     fmt.Fprintf(w, "case %s:\\n", opName(op, arch))
     fmt.Fprintf(w, "return rewriteValue%s_%s(v, config)\\n", arch.name, opName(op, arch))
 }
 fmt.Fprintf(w, "}\\n")
 fmt.Fprintf(w, "return false\\n")
 fmt.Fprintf(w, "}\\n")

 // Generate a routine per op.  Note that we don't make one giant routine
 // because it is too big for some compilers.
 for _, op := range ops {
     fmt.Fprintf(w, "func rewriteValue%s_%s(v *Value, config *Config) bool {\\n", arch.name, opName(op, arch))
     fmt.Fprintln(w, "b := v.Block")
     fmt.Fprintln(w, "_ = b") // b が使用されない場合のコンパイラ警告を回避
     for _, rule := range oprules[op] {
         // ... 各ルールの生成ロジック ...
     }
     fmt.Fprintf(w, "return false\\n")
     fmt.Fprintf(w, "}\\n")
```

このスニペットは、`rulegen.go`がどのように新しい構造のコードを生成するかを示しています。

1.  `rewriteValue%s`関数（例: `rewriteValueAMD64`）は、`v.Op`に基づいて、対応するオペレーション固有の関数（例: `rewriteValueAMD64_OpAMD64ADDB`）を呼び出すだけのシンプルなディスパッチャになります。
2.  各オペレーション（`op`）に対して、`rewriteValue%s_%s`という新しい関数が生成されます。この関数内に、そのオペレーションに特化したすべての書き換えルールが含まれます。

この変更により、各生成関数のサイズが大幅に削減され、コンパイラがそれらを個別に処理できるようになります。これにより、コンパイラが巨大な関数をコンパイルする際に発生していたメモリ不足や分岐オフセットの制限といった問題が解消されます。

**`src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更例**:

変更前は、`rewriteValueAMD64`関数内に以下のようなコードが直接含まれていました。

```go
case OpAMD64ADDB:
    // match: (ADDB x (MOVBconst [c]))
    // cond:
    // result: (ADDBconst [c] x)
    {
        x := v.Args[0]
        if v.Args[1].Op != OpAMD64MOVBconst {
            goto endab690db69bfd8192eea57a2f9f76bf84
        }
        c := v.Args[1].AuxInt
        v.Op = OpAMD64ADDBconst
        v.AuxInt = 0
        v.Aux = nil
        v.resetArgs()
        v.AuxInt = c
        v.AddArg(x)
        return true
    }
    goto endab690db69bfd8192eea57a2f9f76bf84
endab690db69bfd8192eea57a2f9f76bf84:
    ;
    // ... 他の ADDB ルール ...
```

変更後は、これが`rewriteValueAMD64_OpAMD64ADDB`という新しい関数に移動し、`rewriteValueAMD64`関数からはその関数が呼び出されるだけになります。

```go

    switch v.Op {
    case OpAMD64ADDB:
        return rewriteValueAMD64_OpAMD64ADDB(v, config)
    // ...
    }
    return false
}

func rewriteValueAMD64_OpAMD64ADDB(v *Value, config *Config) bool {
    b := v.Block
    _ = b
    // match: (ADDB x (MOVBconst [c]))
    // cond:

    {
        x := v.Args[0]

        }

        v.Op = OpAMD64ADDBconst
        v.AuxInt = 0
        v.Aux = nil
        v.resetArgs()
        v.AuxInt = c
        v.AddArg(x)
        return true
    }
    goto endab690db69bfd8192eea57a2f9f76bf84
endab690db69bfd8192eea57a2f9f76bf84:
    ;
    // ... 他の ADDB ルール ...
```

この構造変更は、コードの可読性や保守性にも寄与しますが、主な目的はコンパイラ自身のコンパイル問題を解決することにありました。

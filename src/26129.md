## 元コミット内容

`cmd/go: for go get -insecure, do not fall back to HTTP for non-200 responses`

このコミットは、`go get -insecure` コマンドが、HTTPSリクエストで200以外のステータスコードを受け取った場合に、HTTPへのフォールバックを行わないように変更します。通常の操作でHTTPSからの非200応答を許可しているため、`-insecure` 操作でそれらを拒否するのは不自然であるという理由に基づいています。これはIssue #13037 の修正（再修正）です。

## 変更の背景

Goのパッケージ管理ツールである `go get` は、指定されたリポジトリからソースコードを取得するために使用されます。通常、`go get` はHTTPSを優先して使用し、セキュアな通信を保証します。しかし、自己署名証明書を使用している場合や、開発環境などでHTTPSが適切に設定されていない場合など、HTTPSでの接続が困難な状況も存在します。

このような状況に対応するため、`go get` には `-insecure` オプションが用意されています。このオプションは、HTTPSでの接続が失敗した場合に、HTTPへのフォールバックを許可することで、セキュアでない接続でもパッケージの取得を可能にします。

このコミット以前の動作では、`go get -insecure` を使用している場合でも、HTTPSでのリクエストがエラー（`err != nil`）または非200のステータスコード（`res.StatusCode != 200`）を返した場合にのみHTTPへのフォールバックが行われていました。しかし、コミットメッセージにあるように、通常のHTTPS操作では非200応答も許容される場合があります（例えば、リダイレクトや認証エラーなど）。このような状況で `-insecure` オプションが有効になっているにもかかわらず、非200応答を理由にHTTPへのフォールバックをトリガーするのは、一貫性に欠けるという問題がありました。

この不整合は、Issue #13037 で報告されており、このコミットはその問題を再度修正するものです。以前の修正が完全ではなかったか、新たなシナリオが発見された可能性があります。

## 前提知識の解説

*   **`go get` コマンド**: Go言語のパッケージ管理ツールの一つで、リモートリポジトリからGoパッケージのソースコードをダウンロードし、インストールするために使用されます。依存関係の解決も行います。
*   **`-insecure` オプション**: `go get` コマンドのオプションで、HTTPS接続が失敗した場合にHTTPへのフォールバックを許可します。これにより、自己署名証明書や無効な証明書を持つサーバーからのパッケージも取得できるようになりますが、セキュリティリスクを伴います。
*   **HTTPS (Hypertext Transfer Protocol Secure)**: HTTPにSSL/TLSプロトコルを組み合わせることで、通信の暗号化、認証、データ整合性の保護を提供するセキュアな通信プロトコルです。
*   **HTTP (Hypertext Transfer Protocol)**: ウェブサーバーとクライアントの間で情報をやり取りするためのプロトコルです。HTTPSとは異なり、通信は暗号化されません。
*   **HTTPステータスコード**: ウェブサーバーからの応答の状態を示す3桁の数字です。
    *   **200 OK**: リクエストが成功し、要求されたリソースが返されたことを示します。
    *   **非200応答**: 200以外のステータスコードは、リクエストの処理中に何らかの問題が発生したか、特別な状態であることを示します（例: 301 Moved Permanently, 404 Not Found, 500 Internal Server Errorなど）。
*   **フォールバック (Fallback)**: あるシステムやプロセスが失敗した場合に、代替のシステムやプロセスに切り替えることです。この文脈では、HTTPS接続が失敗した場合にHTTP接続に切り替えることを指します。
*   **`log.Printf`**: Go言語の標準ライブラリ `log` パッケージの関数で、フォーマットされた文字列を標準エラー出力にログとして出力します。`buildV` は詳細なビルド情報を出力するかどうかを制御するフラグと考えられます。
*   **`closeBody(res)`**: HTTPレスポンスボディを閉じるための関数です。リソースリークを防ぐために重要です。

## 技術的詳細

このコミットは、`src/cmd/go/http.go` ファイル内の `httpsOrHTTP` 関数を変更しています。この関数は、指定されたインポートパスに対してHTTPSでのフェッチを試み、必要に応じてHTTPへのフォールバックを処理する役割を担っています。

変更前のコードでは、HTTPSでのフェッチ結果を評価する条件が `if err != nil || res.StatusCode != 200` となっていました。これは、ネットワークエラーが発生した場合 (`err != nil`) またはHTTPSリクエストが200以外のステータスコードを返した場合 (`res.StatusCode != 200`) に、HTTPへのフォールバックを検討するというロジックでした。

このロジックの問題点は、`go get -insecure` オプションが指定されている場合でも、非200応答がHTTPフォールバックのトリガーになっていたことです。通常のHTTPS通信では、リダイレクト（3xx）や認証要求（401）など、非200応答が正当なケースとして扱われることがあります。`-insecure` オプションは、セキュリティ上の懸念を一時的に緩和してでもパッケージを取得したいという意図があるため、非200応答を即座に失敗と見なし、HTTPにフォールバックさせるのは、ユーザーの意図と異なる動作となる可能性がありました。特に、HTTPSでリダイレクトが発生した場合、そのリダイレクト先がHTTPSであれば問題ありませんが、HTTPにフォールバックしてしまうと、意図せずセキュアでない通信経路を選択してしまうことになります。

このコミットでは、この条件を `if err != nil` に変更しています。これにより、HTTPへのフォールバックは、HTTPSでのフェッチ中に**ネットワークエラーが発生した場合にのみ**行われるようになります。HTTPSリクエストが成功し、サーバーから応答が返された場合（たとえそれが非200ステータスコードであっても）、`go get -insecure` はその応答をそのまま処理しようとします。これは、通常のHTTPS操作で非200応答が許容されるのと同様の振る舞いを `-insecure` オプションでも実現し、一貫性を保つための変更です。

また、変更前のコードには、`if buildV && res.StatusCode != 200 { log.Printf("https fetch: status %s", res.Status) }` というログ出力がありましたが、これも削除されています。これは、非200応答がもはやHTTPフォールバックの直接的なトリガーではなくなったため、そのステータスコードを特別にログに記録する必要がなくなったためと考えられます。

## コアとなるコードの解説

変更された行は以下の通りです。

**変更前:**
```go
	if err != nil || res.StatusCode != 200 {
		if buildV && err != nil {
			log.Printf("https fetch failed: %v", err)
		}
		if security == insecure {
			if buildV && res.StatusCode != 200 {
				log.Printf("https fetch: status %s", res.Status)
			}
			closeBody(res)
			urlStr, res, err = fetch("http")
		}
```

**変更後:**
```go
	if err != nil { // ここが変更された
		if buildV { // ここも変更された (err != nil の条件が削除)
			log.Printf("https fetch failed: %v", err)
		}
		if security == insecure {
			// 以下の行が削除された
			// if buildV && res.StatusCode != 200 {
			// 	log.Printf("https fetch: status %s", res.Status)
			// }
			closeBody(res)
			urlStr, res, err = fetch("http")
		}
```

この変更により、`httpsOrHTTP` 関数は以下のロジックで動作します。

1.  まず、`fetch("https")` を呼び出してHTTPS経由でリソースの取得を試みます。
2.  HTTPSでのフェッチ中に**ネットワークエラー (`err != nil`) が発生した場合のみ**、以下の処理に進みます。
    *   `buildV` フラグが立っている場合、HTTPSフェッチが失敗したことをログに出力します。
    *   `security == insecure` (つまり `-insecure` オプションが指定されている) 場合、HTTPへのフォールバックを試みます。
        *   既存のレスポンスボディ (`res`) があれば `closeBody(res)` で閉じます。
        *   `fetch("http")` を呼び出してHTTP経由でリソースの取得を試み、その結果を返します。
3.  HTTPSでのフェッチ中にネットワークエラーが発生せず、サーバーから応答が返された場合（`err == nil`）、たとえその応答のステータスコードが200以外であっても、HTTPへのフォールバックは行われません。そのHTTPS応答がそのまま呼び出し元に返されます。

この修正により、`go get -insecure` は、HTTPS接続自体が確立できない場合にのみHTTPにフォールバックするようになり、HTTPS接続が確立できたが非200応答が返された場合は、そのHTTPS応答を優先して処理するようになります。これにより、`go get -insecure` の動作がより予測可能で、通常のHTTPS動作と一貫性のあるものになります。

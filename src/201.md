# [インデックス 201] ファイルの概要

このコミットは、Go言語のAMD64アーキテクチャ向けリンカである`6l`におけるスタックオフセット情報の取り扱い方法を根本的に変更するものです。具体的には、関数のスタックフレームサイズに関するメタデータを、コードストリームに直接埋め込む古い方式から、より構造化された専用のバイトシーケンスとして関数の先頭に挿入する新しい方式へと移行しています。これにより、リンカがスタック情報をより堅牢かつ柔軟に管理できるようになります。

## 変更の背景

このコミットは、Go言語の初期開発段階におけるリンカの進化の一部です。元のコミットメッセージは非常に簡潔ですが、「stack offset」という記述から、リンカが生成するバイナリに、各関数のスタックフレームに関する情報をどのように埋め込むか、というメカニズムの改善が目的であることが推測されます。

初期のGoリンカでは、関数のスタックオフセット（ローカル変数や引数に割り当てられるスタック領域のサイズ）を、特定の「マジックナンバー」や特殊な命令タイプ（`Ztext`）を用いて、コードストリームの一部として直接埋め込んでいたと考えられます。しかし、このような方法は、以下のような課題を抱える可能性があります。

1.  **堅牢性の欠如**: マジックナンバーが単なる数値である場合、他のデータと衝突する可能性があり、誤認識のリスクがあります。
2.  **柔軟性の欠如**: スタック情報がコードと密接に結合しているため、将来的に追加のメタデータ（例: GC情報、インライン化情報など）を埋め込む際に、拡張が困難になる可能性があります。
3.  **デバッグ・解析の困難さ**: コードとメタデータが混在していると、デバッガやプロファイラが正確なスタック情報を抽出するのが難しくなることがあります。

このコミットは、これらの課題に対処するため、スタックオフセット情報をより明確に識別可能で、かつ構造化された形式で埋め込む新しいアプローチを導入しています。これにより、リンカの内部処理が整理され、将来的な機能拡張やデバッグツールの改善に貢献することが期待されます。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の概念について基本的な知識が必要です。

1.  **Go言語のビルドプロセスとリンカ (6l)**:
    *   Go言語のソースコードは、まずコンパイラ（例: `6g` for AMD64）によってアセンブリコード（または中間表現）に変換されます。
    *   次に、アセンブラによってオブジェクトファイル（`.o`ファイル）が生成されます。
    *   最後に、リンカ（例: `6l` for AMD64）がこれらのオブジェクトファイルを結合し、必要なライブラリとリンクして実行可能なバイナリを生成します。
    *   `6l`は、Goの初期のツールチェインにおけるAMD64アーキテクチャ向けのリンカの名称です。GoのツールチェインはPlan 9のツールチェインをベースにしており、リンカは`{arch}l`（例: `6l`, `8l`, `5l`）という命名規則を持っていました。

2.  **スタックフレームとスタックオフセット**:
    *   関数が呼び出されると、その関数専用のメモリ領域がスタック上に確保されます。これを「スタックフレーム」と呼びます。
    *   スタックフレームには、関数の引数、ローカル変数、呼び出し元のリターンアドレスなどが格納されます。
    *   「スタックオフセット」とは、スタックフレームの基準点（通常はスタックポインタ）から、特定の変数やデータが配置されている位置までの距離を指します。この情報は、デバッガが変数の値を参照したり、ガベージコレクタがスタック上のポインタをスキャンしたりする際に不可欠です。

3.  **ATEXT命令**:
    *   Goのアセンブラ（およびリンカの内部表現）において、`ATEXT`は関数の開始を示す擬似命令（pseudo-instruction）です。これは実際の機械語命令を生成するわけではなく、リンカに対して「ここから新しい関数が始まる」という情報を提供します。
    *   リンカは`ATEXT`命令を解析し、関数のコードセクションを適切に配置し、関連するメタデータ（スタックサイズなど）を処理します。

4.  **マジックナンバー/マジック文字列**:
    *   プログラムやファイル形式において、特定のデータブロックや構造の開始、または種類を識別するために用いられる、あらかじめ決められたバイト列のことです。
    *   このコミットでは、以前は数値（`SOFmark`）が使われていたものが、より複雑なバイト列（`\xa7\xf1\xd9\x2a\x82\xc8\xd8\xfe`）に変更されています。これにより、偶然他のデータと一致する可能性が低くなり、識別がより堅牢になります。

5.  **`Prog`構造体**:
    *   Goリンカの内部では、アセンブリ命令やデータ、およびそれらに関連する属性（アドレス、シンボル、行番号など）を表現するために`Prog`というデータ構造が使われます。リンカは`Prog`のリストを操作して、最終的なバイナリを生成します。
    *   `p->link`は次の`Prog`へのポインタ、`p->pcond`は条件付きジャンプのターゲットなど、リンカが内部的な連結や制御フローのために使用するポインタです。

## 技術的詳細

このコミットの核心は、リンカがスタックオフセット情報をバイナリに埋め込む方法の変更にあります。

**変更前のアプローチ（推測）**:
*   `SOFmark`という数値定数（`11`）が、スタックオフセット情報の「マジックナンバー」として使われていました。
*   `src/cmd/6l/asm.c`や`src/cmd/6l/span.c`では、`ATEXT`命令のプログラムカウンタ（`p->pc`）を`SOFmark`分だけ進める、という処理が見られます。これは、スタックオフセット情報が関数の開始位置に直接埋め込まれ、その分だけコードの開始位置がずれる、という実装を示唆しています。
*   `src/cmd/6l/optab.c`には`Ztext`という特殊な命令タイプがあり、これがスタックオフセット情報を埋め込むために使われていたようです。`src/cmd/6l/span.c`の`asmins`関数内の`case Ztext:`ブロックがその処理を担っていました。このブロックでは、スタックオフセット値が3バイトでエンコードされ、その後に`SOFmark`で定義されたマジックバイト列が続く形で、コードストリームに直接書き込まれていました。

**変更後のアプローチ**:
このコミットでは、上記の問題点を解決するために、より構造化された新しいメカニズムが導入されました。

1.  **`SOFmark`の変更**:
    *   `src/cmd/6l/6.out.h`で、`SOFmark`が数値定数`11`から、`"\xa7\xf1\xd9\x2a\x82\xc8\xd8\xfe"`という8バイトのマジック文字列に変更されました。これにより、識別子の衝突リスクが大幅に低減され、より明確なメタデータマーカーとして機能します。

2.  **新しいスタック情報埋め込みロジックの導入 (`src/cmd/6l/pass.c`)**:
    *   `pass.c`に`byteq`、`markstk`、`addstackmark`という3つの新しい関数が追加されました。
    *   `byteq(int v)`: 単一のバイトをデータとして持つ`Prog`構造体（命令）を生成するヘルパー関数です。
    *   `addstackmark(void)`: リンカのメイン処理フローから呼び出される関数で、すべての関数（`textp`リスト）を走査し、それぞれの関数に対して`markstk`を呼び出します。
    *   `markstk(Prog *l)`: この関数が新しいスタック情報埋め込みの核心です。
        *   引数`l`は、処理対象の関数の`ATEXT`命令（`Prog`構造体）です。
        *   まず、元の`ATEXT`命令のコピー（`p0`）を作成します。この`p0`が、新しく挿入されるメタデータブロックの開始点となります。
        *   次に、以下の情報をバイト列として連続して挿入します。これらのバイト列は、`byteq`関数を使って個別の`Prog`命令として生成され、互いに`link`ポインタで連結されます。
            1.  **新しい`SOFmark` (マジック文字列)**: 8バイト。リンカやデバッガがこのメタデータブロックを識別するための署名です。
            2.  **スタックオフセット**: 3バイト。関数のスタックフレームサイズを表します。`l->to.offset`から取得されます。
            3.  **関数名**: ヌル終端文字列。`s->name`から取得されます。
        *   これらのバイト列の最後に、`ARET`（リターン命令）を挿入します。これは、このメタデータブロックが論理的に独立した「関数のような」構造を持つことを示唆している可能性があります。
        *   最も重要なのは、`Prog`構造体の`link`と`pcond`ポインタを巧みに操作して、この新しく生成されたメタデータブロックを元の関数の`ATEXT`命令の直前に「挿入」するロジックです。
            *   `l->pcond = p0;`: 元の`ATEXT`命令の`pcond`（通常は関数の次の命令を指す）を、新しく生成したメタデータブロックの開始点`p0`に設定します。
            *   `p->link = r; p0->pcond = r;`: メタデータブロックの終端を、元の関数の本体の開始点（`r`）にリンクし直します。
            *   `for(p=l;; p=q) { q = p->link; if(q == r) { p->link = p0; return; } }`: これは、元の関数本体の終端を見つけ、その終端から新しいメタデータブロックの開始点`p0`に逆向きにリンクを張ることで、リンカが関数を処理する際に、まずこのメタデータブロックを通過するようにします。

3.  **古いロジックの削除 (`src/cmd/6l/asm.c`, `src/cmd/6l/span.c`, `src/cmd/6l/optab.c`)**:
    *   `src/cmd/6l/asm.c`と`src/cmd/6l/span.c`から、`SOFmark`を使ったプログラムカウンタの調整ロジックが削除されました。これは、スタック情報がコードの一部として扱われなくなったことを明確に示しています。
    *   `src/cmd/6l/span.c`の`asmins`関数から、`case Ztext:`ブロック全体が削除されました。これにより、古いスタックオフセット埋め込み命令の処理が完全に廃止されました。
    *   `src/cmd/6l/optab.c`では、`ytext`配列内で`Ztext`が`Zpseudo`に置き換えられました。これは、`Ztext`命令タイプがもはや使用されないことを示します。
    *   `src/cmd/6l/l.h`から`Ztext`の定義が削除されました。

この変更により、スタックオフセット情報は、実行可能なコードとは分離された、しかし論理的には関数に属するメタデータとして扱われるようになります。これは、リンカの内部構造をクリーンにし、将来的なデバッグ情報やプロファイリング情報の拡張を容易にするための重要なステップです。

    void
    markstk(Prog *l)
    {
        Prog *p0, *p, *q, *r;
        long i, n, line;
        Sym *s;

        version++;
        s = lookup(l->from.sym->name, version);
        s->type = STEXT;
        line = l->line;

        // start with fake copy of ATEXT
        p0 = prg();
        p = p0;
        *p = *l;    // note this gets p->pcond and p->line

        p->from.type = D_STATIC;
        p->from.sym = s;
        p->to.offset = 0;

        // put out magic sequence
        n = strlen(SOFmark);
        for(i=0; i<n; i++) {
            q = byteq(SOFmark[i]);
            q->line = line;
            p->link = q;
            p = q;
        }

        // put out stack offset
        n = l->to.offset;
        if(n < 0)
            n = 0;
        for(i=0; i<3; i++) {
            q = byteq(n);
            q->line = line;
            p->link = q;
            p = q;
            n = n>>8;
        }

        // put out null terminated name
        for(i=0;; i++) {
            n = s->name[i];
            q = byteq(n);
            q->line = line;
            p->link = q;
            p = q;
            if(n == 0)
                break;
        }

        // put out return instruction
        q = prg();
        q->as = ARET;
        q->line = line;
        p->link = q;
        p = q;

        r = l->pcond;
        l->pcond = p0;
        p->link = r;
        p0->pcond = r;

        // hard part is linking end of
        // the text body to my fake ATEXT
        for(p=l;; p=q) {
            q = p->link;
            if(q == r) {
                p->link = p0;
                return;
            }
        }
    }

    // 新しく追加された addstackmark 関数
    void
    addstackmark(void)
    {
        Prog *p;

        if(debug['v'])
            Bprint(&bso, "%5.2f stkmark\\n", cputime());
        Bflush(&bso);

        for(p=textp; p!=P; p=p->pcond) {
            markstk(p);     // splice in new body
            p = p->pcond;       // skip the one we just put in
        }
    }

## コアとなるコードの解説

このコミットの最も重要な部分は、`src/cmd/6l/pass.c`に追加された`markstk`関数とその呼び出し元である`addstackmark`関数です。

1.  **`SOFmark`の変更**:
    `SOFmark`が単なる数値から、より複雑なバイト列（`\xa7\xf1\xd9\x2a\x82\xc8\\xd8\\xfe`）に変更されたことは、リンカが特定のメタデータブロックを識別する際の堅牢性を大幅に向上させます。このバイト列は、Goのリンカが生成するバイナリ内で、関数のスタック情報が格納されている場所を示す「署名」として機能します。

2.  **`markstk`関数**:
    この関数は、各関数の`ATEXT`命令（`Prog`構造体`l`）を受け取り、その関数のスタック情報をバイナリに埋め込むための新しいバイトシーケンスを生成し、元の関数の命令リストに「挿入」します。

    *   `p0 = prg(); *p = *l;`: まず、元の関数の`ATEXT`命令のコピー`p0`を作成します。この`p0`が、新しく挿入されるメタデータブロックの論理的な開始点となります。
    *   **マジック文字列の挿入**:
        ```c
        n = strlen(SOFmark);
        for(i=0; i<n; i++) {
            q = byteq(SOFmark[i]);
            q->line = line;
            p->link = q;
            p = q;
        }
        ```
        ここで、新しい`SOFmark`（マジック文字列）の各バイトが、`byteq`関数によって個別の`ABYTE`命令（単一バイトのデータ）として生成され、`p->link = q; p = q;`によって連結されていきます。これにより、バイナリのこの位置にマジック文字列が連続したバイト列として配置されます。
    *   **スタックオフセットの挿入**:
        ```c
        n = l->to.offset;
        if(n < 0)
            n = 0;
        for(i=0; i<3; i++) {
            q = byteq(n);
            q->line = line;
            p->link = q;
            p = q;
            n = n>>8;
        }
        ```
        関数のスタックオフセット（`l->to.offset`）が3バイトでエンコードされ、同様に`ABYTE`命令として挿入されます。`n = n>>8;`によって、オフセット値がバイトごとに分割されて書き込まれます。
    *   **関数名の挿入**:
        ```c
        for(i=0;; i++) {
            n = s->name[i];
            q = byteq(n);
            q->line = line;
            p->link = q;
            p = q;
            if(n == 0)
                break;
        }
        ```
        関数のシンボル名（`s->name`）がヌル終端文字列としてバイトごとに挿入されます。これにより、デバッグ時に関数名とスタック情報を関連付けることが容易になります。
    *   **`ARET`命令の挿入**:
        ```c
        q = prg();
        q->as = ARET;
        q->line = line;
        p->link = q;
        p = q;
        ```
        メタデータブロックの最後に`ARET`（リターン命令）が挿入されます。これは、このメタデータブロックが論理的に独立した「関数のような」構造を持つことを示唆している可能性があります。デバッグツールがこのブロックを独立したエンティティとして認識しやすくするためかもしれません。
    *   **命令リストの連結操作**:
        ```c
        r = l->pcond;
        l->pcond = p0;
        p->link = r;
        p0->pcond = r;

        for(p=l;; p=q) {
            q = p->link;
            if(q == r) {
                p->link = p0;
                return;
            }
        }
        ```
        この部分は、リンカの内部的な`Prog`リストの連結を操作する最も複雑なロジックです。
        *   `r = l->pcond;`: 元の`ATEXT`命令の`pcond`（通常は関数の実際のコードの開始を指す）を保存します。
        *   `l->pcond = p0;`: 元の`ATEXT`命令の`pcond`を、新しく生成したメタデータブロックの開始点`p0`に設定します。これにより、リンカが関数を処理する際に、まずこのメタデータブロックを「実行」するように見えます。
        *   `p->link = r; p0->pcond = r;`: 新しいメタデータブロックの終端（`p`が指す`ARET`命令）を、元の関数の本体の開始点`r`にリンクします。また、`p0`の`pcond`も`r`に設定します。
        *   最後の`for`ループは、元の関数の命令リストを走査し、その終端（`q == r`となる点）を見つけます。そして、その終端の`link`を`p0`（新しいメタデータブロックの開始点）に繋ぎ直します。
        この一連の操作により、リンカが関数を処理する際に、まずマジック文字列、スタックオフセット、関数名を含むメタデータブロックを通過し、その後に実際の関数コードが続く、という構造がバイナリ内に構築されます。

3.  **`addstackmark`関数**:
    この関数は、リンカのメインパス（`src/cmd/6l/obj.c`の`main`関数から呼び出される）で、すべての関数（`textp`というグローバルリストに格納されている）に対して`markstk`を適用するエントリポイントです。これにより、生成されるすべての関数に新しい形式のスタック情報が埋め込まれることが保証されます。

これらの変更は、Goのリンカがスタック情報をより明確に、かつ構造化された形でバイナリに埋め込むための重要な進化を示しています。これにより、デバッグ、プロファイリング、ガベージコレクションなどのランタイム機能が、より正確で堅牢なスタック情報にアクセスできるようになります。

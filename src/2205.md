## 元コミット内容

このコミットの元のメッセージは以下の通りです。

> A comparison of two values with a type equivalent to string
> gives an type mismatch error, although both values appear to
> have the same type.

これは、「`string`型と等価な型を持つ2つの値を比較すると、両方の値が同じ型であるように見えても、型ミスマッチエラーが発生する」という問題を示しています。

## 変更の背景

このコミットは、Go言語の初期段階（2009年）における型システム、特にコンパイラの型チェックロジックの成熟過程で発見されたバグに対応しています。Go言語は静的型付け言語であり、厳密な型チェックは言語の安全性と堅牢性を保証する上で非常に重要です。しかし、初期のコンパイラでは、基底型が同じであるにもかかわらず、カスタム型とインターフェースの組み合わせにおいて、比較演算子（`<`）が誤って型ミスマッチを報告するケースが存在しました。

この特定のバグは、ユーザーが定義した基底型が`string`であるカスタム型（例: `type S string`）と、インターフェース型を介した型アサーションを組み合わせた比較において発生しました。コンパイラが、カスタム型と基底型（`string`）の間の関係性を正しく解決できず、比較演算子のオペランドの型が異なると判断してしまったため、不正なエラーが報告されていました。

このコミットは、このバグが修正されたことを確認するための回帰テストを追加することで、将来的に同様の問題が再発しないようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の基本的な概念を理解しておく必要があります。

*   **型システム (Type System)**: Goは静的型付け言語であり、変数は使用前に型を宣言する必要があります。型は、その変数が保持できる値の種類と、その値に対して実行できる操作を決定します。
*   **基底型 (Underlying Type)**: Goでは、既存の型から新しい型を宣言できます（例: `type MyString string`）。この場合、`MyString`は新しい型ですが、その基底型は`string`です。基底型が同じであっても、異なる型として扱われます。ただし、特定の操作（例: 比較、変換）においては、基底型が考慮されることがあります。
*   **インターフェース (Interfaces)**: インターフェースは、メソッドのシグネチャの集合を定義します。Goのインターフェースは暗黙的に満たされます。つまり、ある型がインターフェースで定義されたすべてのメソッドを実装していれば、その型はそのインターフェースを満たします。
*   **空インターフェース (`interface{}` または `any`)**: メソッドを一つも持たないインターフェースは、あらゆる型の値を保持できます。これは、Goにおけるポリモーフィズムの強力なメカニズムです。
*   **型アサーション (Type Assertion)**: インターフェース型の値が、特定の基底型を持つかどうかをチェックし、もしそうであればその基底型の値として抽出する操作です。構文は `value.(Type)` です。例えば、`e.(S)` は、インターフェース変数`e`が型`S`の値を保持している場合、その値を型`S`として返します。
*   **比較演算子 (Comparison Operators)**: Goでは、`==`, `!=`, `<`, `<=`, `>`, `>=` などの比較演算子が提供されています。これらの演算子は、オペランドの型が互換性がある場合にのみ使用できます。文字列型の場合、辞書順での比較が行われます。

このバグの核心は、`type S string`で定義されたカスタム型`S`と、`Empty interface{}`を介した型アサーション`e.(S)`の組み合わせにおいて、コンパイラが`v < e.(S)`のような比較を正しく処理できなかった点にあります。

## 技術的詳細

このバグは、Goコンパイラの型チェックフェーズにおける、カスタム型、基底型、インターフェース、そして型アサーションの相互作用の複雑さに起因していました。

問題のコードスニペットは以下の通りです。

```go
type S string
type Empty interface {}

func (v S) Less(e Empty) bool {
	return v < e.(S);
}
```

ここで、`S`は`string`を基底型とする新しい型です。`Less`メソッドは`S`型のレシーバ`v`を持ち、`Empty`インターフェース型の引数`e`を受け取ります。メソッド内部では、`e`が`S`型であるとアサートされ（`e.(S)`）、その結果と`v`が比較されています。

本来、`v`は`S`型であり、`e.(S)`も型アサーションによって`S`型になります。`S`の基底型は`string`であるため、この比較は`string`同士の比較として有効であるべきです。しかし、バグのあるコンパイラは、この比較を「`string`型と`S`型の間の不正な比較」と誤って解釈していました。

コミットメッセージに記載されているエラーメッセージ`illegal types for operand: CALL string S`は、この誤解釈を明確に示しています。コンパイラは、`v`をその基底型である`string`として扱い、`e.(S)`をカスタム型`S`として扱ってしまったため、両者の型が異なると判断し、比較演算子`<`に対して不正なオペランドであると報告したのです。

これは、コンパイラが型アサーションの結果の型と、カスタム型の基底型との間の関係性を、比較演算子の文脈で適切に解決できていなかったことを意味します。Goの型システムでは、カスタム型は基底型とは異なる型として扱われますが、特定の操作（特に比較や代入）においては、基底型との互換性が考慮されるべきです。このバグは、その互換性チェックが不完全であったことを露呈しました。

このコミットは、この問題が修正されたことを検証するためのテストケースを追加しています。テストが成功するということは、コンパイラが`v < e.(S)`のような比較を、基底型が`string`である`S`型同士の有効な比較として正しく認識し、コンパイルできるようになったことを意味します。

## コアとなるコードの解説

`test/bugs/bug151.go`の主要なコードは以下の部分です。

```go
package main

type S string

type Empty interface {}

func (v S) Less(e Empty) bool {
	return v < e.(S);
}
```

*   `type S string`: これは、Goの型宣言構文を使用して、既存の組み込み型`string`を基底型とする新しい型`S`を定義しています。`S`は`string`とは異なる型ですが、その基底となるデータ表現は`string`と同じです。
*   `type Empty interface {}`: これは、メソッドを一切持たないインターフェースです。Goでは、すべての型が少なくとも0個のメソッドを持つため、`Empty`インターフェースはあらゆる型の値を保持できます。これは、Javaの`Object`型やC#の`object`型に似た汎用的な型として機能します。
*   `func (v S) Less(e Empty) bool`: これは、`S`型に`Less`という名前のメソッドを定義しています。
    *   `v S`: `Less`メソッドのレシーバであり、`S`型の値です。
    *   `e Empty`: `Less`メソッドの引数であり、`Empty`インターフェース型の値です。
    *   `return v < e.(S)`: この行がバグを再現する核心部分です。
        *   `e.(S)`: これは型アサーションです。引数`e`が`S`型の値を保持していることをアサートし、その値を`S`型として抽出します。もし`e`が`S`型でなければ、ランタイムパニックが発生します。
        *   `v < e.(S)`: ここで`S`型の値`v`と、型アサートされた`S`型の値`e.(S)`が比較されています。Goの仕様では、基底型が同じであれば、カスタム型同士の比較は許可されるべきです。`S`の基底型は`string`であるため、この比較は`string`の辞書順比較として機能するはずです。

バグのあるコンパイラは、この`v < e.(S)`の比較において、`v`をその基底型である`string`として、`e.(S)`をカスタム型`S`として認識し、両者の型が異なるため比較できないと判断していました。このテストケースは、この誤った型チェックの挙動を捉え、修正後にコンパイルが成功することを確認するために設計されました。

`test/golden.out`への変更は、この新しいテストケースが追加されたことと、そのテストが以前はどのようなエラーを発生させていたかを示すためのものです。テストスイートが実行されると、`bug151.go`がコンパイルされ、もしバグが修正されていれば、エラーは発生せず、テストは成功と見なされます。

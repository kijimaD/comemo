# [インデックス 21110] ファイルの概要

このコミットは、Goランタイムのロックフリースタック実装における重要な改善と拡張を目的としています。具体的には、AMD64アーキテクチャにおいてアドレス空間の上位半分に位置するポインタが正しく扱われない問題を修正し、同時にLinux/Power64アーキテクチャに対するサポートを追加しています。これにより、Goランタイムの堅牢性と移植性が向上しています。

## 変更の背景

このコミットの変更は、主に以下の二つの背景に基づいています。

1.  **AMD64アーキテクチャにおけるアドレス空間上位半分でのポインタ処理の修正**:
    Goランタイムのロックフリースタック（`lfstack`）は、ポインタとABAカウンタを単一の`uint64`値にパッキングして使用します。これは、ロックフリーデータ構造で発生しうるABA問題を解決するための一般的な手法です。しかし、AMD64アーキテクチャでは、仮想アドレスが通常48ビットであり、これが64ビットレジスタに格納される際に符号拡張（sign extension）されます。もしアドレスが48ビット空間の上位半分（すなわち、64ビット値として最上位ビットが1になる範囲）にある場合、既存のパッキング/アンパッキングロジックがこの符号拡張を正しく扱えず、ポインタが破損したり、不正なアドレスとして解釈されたりする可能性がありました。このコミットは、この特定のケースにおける`lfstack`の動作を修正することを目的としています。

2.  **Linux/Power64アーキテクチャへのサポート追加**:
    Goは様々なアーキテクチャをサポートしており、その範囲を広げ続けています。このコミットは、既存のロックフリースタックのメカニズムをLinux上で動作するPower64アーキテクチャにも対応させることを目的としています。Power64もまた、そのアドレス空間の特性（Linux上ではユーザーアドレス空間が43ビットに制限されるなど）を考慮した、ポインタとABAカウンタのパッキング/アンパッキングロジックを必要とします。この追加により、GoランタイムのPower64環境での安定性と効率性が確保されます。

これらの変更は、Goランタイムの低レベルな並行処理プリミティブの正確性と移植性を高める上で不可欠でした。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の技術的な概念を把握しておく必要があります。

*   **ロックフリーデータ構造 (Lock-Free Data Structures)**:
    複数のスレッドが同時にアクセスしても、ミューテックスなどのロック機構を使用せずに正しく動作するデータ構造です。ロックの競合によるパフォーマンス低下やデッドロックのリスクを回避できるため、Goランタイムのような高並行性が求められるシステムで利用されます。しかし、その実装は非常に複雑で、アトミック操作やメモリバリアなどの低レベルなプリミティブを正確に扱う必要があります。

*   **ABA問題 (ABA Problem)**:
    ロックフリーアルゴリズム、特にCAS (Compare-And-Swap) 操作を用いる際に発生する並行性の問題です。あるメモリ位置の値が `A` から `B` に変化し、その後再び `A` に戻った場合、CAS操作は値が変化していないと誤認してしまう可能性があります。これにより、古いポインタを誤って参照したり、データ構造の整合性が損なわれたりする危険性があります。この問題を解決するためには、ポインタと一緒に「バージョンカウンタ」や「ABAカウンタ」と呼ばれる値を更新し、CAS操作の対象に含めるのが一般的です。ポインタとカウンタを結合して単一のワードとして扱うことで、値が `A` に戻ったとしても、カウンタが異なるためCASが失敗し、安全性が保たれます。

*   **ポインタのパッキングとアンパッキング (Pointer Packing and Unpacking)**:
    ABA問題を解決するために、ポインタ（メモリアドレス）とABAカウンタを1つの固定サイズのデータ型（例: `uint64`）に結合（パッキング）し、必要に応じて分離（アンパッキング）する技術です。
    *   **パッキング**: ポインタが使用するビット数と、カウンタが使用するビット数を考慮し、これらを`uint64`などの単一の整数型に効率的に格納します。通常、ポインタはアドレス空間の全ビットを使用しないため、未使用のビット領域をカウンタに割り当てます。
    *   **アンパッキング**: パッキングされた`uint64`値から、元のポインタとカウンタを正確に抽出します。
    この操作は、アーキテクチャ固有のアドレス空間の特性（例: 仮想アドレスのビット数、アラインメント要件）に強く依存します。

*   **アトミック操作 (Atomic Operations)**:
    複数のスレッドから同時にアクセスされても、その操作が中断されずに完全に実行されることを保証する操作です。Goランタイムでは、`sync/atomic`パッケージが提供するようなアトミック操作が、ロックフリーデータ構造の構築に不可欠です。このコミットでは、`atomicload64`（64ビット値をアトミックに読み込む）や`cas64`（64ビット値に対してCompare-And-Swapを実行する）といった操作が使用されています。

*   **AMD64アーキテクチャの仮想アドレス空間 (AMD64 Architecture Virtual Address Space)**:
    x86-64（AMD64）アーキテクチャでは、64ビットのレジスタを使用しますが、現在のところ、一般的なOS（Linuxなど）では仮想アドレス空間は通常48ビットに制限されています。この48ビットアドレスは、64ビットのレジスタに格納される際に、最上位ビット（ビット47）が符号拡張（sign extension）されます。つまり、アドレスが`0x0000_8000_0000_0000`から`0xFFFF_7FFF_FFFF_FFFF`の範囲にある場合、64ビット値としては上位ビットが1で埋められます。この符号拡張の挙動を正しく理解し、パッキング/アンパッキングロジックに反映させることが、アドレス空間の上位半分にあるポインタを扱う上で重要となります。

*   **Power64アーキテクチャの仮想アドレス空間 (Power64 Architecture Virtual Address Space)**:
    IBMが開発したPowerPCアーキテクチャの64ビット版です。Linux環境では、Power64のユーザーアドレス空間が通常43ビットに制限されることがあります（これはカーネルの構成やハードウェアに依存します）。AMD64と同様に、このアドレス空間の特性を考慮して、ポインタとABAカウンタを効率的かつ正確にパッキング/アンパッキングするロジックを設計する必要があります。

これらの概念は、Goランタイムがどのように低レベルなメモリ管理と並行処理を実装しているかを理解する上で基盤となります。

## 技術的詳細

このコミットの主要な技術的変更は、ロックフリースタックのポインタとABAカウンタのパッキング/アンパッキングロジックを、アーキテクチャ固有の関数`lfstackPack`と`lfstackUnpack`に抽象化した点にあります。これにより、`lfstack.go`の共通ロジックは簡潔になり、各アーキテクチャの特殊なアドレス空間の扱いはそれぞれのファイルにカプセル化されました。

### `src/runtime/lfstack.go` の変更

*   以前は`lfPtrBits`や`lfCountMask`といった定数がこのファイルで定義され、直接ビット操作が行われていました。これらは削除され、各アーキテクチャ固有のファイルで定義されるようになりました。
*   `lfstackpush`関数と`lfstackpop`関数内で、ポインタとカウンタの結合（パッキング）および分離（アンパッキング）の処理が、それぞれ`lfstackPack`と`lfstackUnpack`関数への呼び出しに置き換えられました。
    *   例:
        *   `new := uint64(unode) | (uint64(node.pushcnt)&lfCountMask)<<lfPtrBits`
            ↓
            `new := lfstackPack(node, node.pushcnt)`
        *   `node.next = (*lfnode)(unsafe.Pointer(uintptr(old & lfPtrMask)))`
            ↓
            `node.next, _ = lfstackUnpack(old)`
    この変更により、`lfstack.go`はアーキテクチャの詳細から解放され、より汎用的なロジックを記述できるようになりました。

### `src/runtime/lfstack_32bit.go` の変更

32ビットシステム向けの実装です。32ビットシステムでは、ポインタは32ビット、カウンタも32ビットとして扱われます。

*   `func lfstackPack(node *lfnode, cnt uintptr) uint64`:
    ```go
    return uint64(uintptr(unsafe.Pointer(node)))<<32 | uint64(cnt)
    ```
    ポインタ（`node`）を`uintptr`に変換し、それを64ビット値の上位32ビットにシフトします。そして、カウンタ（`cnt`）を下位32ビットにそのまま配置し、両者をビットORで結合します。

*   `func lfstackUnpack(val uint64) (node *lfnode, cnt uintptr)`:
    ```go
    node = (*lfnode)(unsafe.Pointer(uintptr(val >> 32)))
    cnt = uintptr(val)
    return
    ```
    結合された`val`から、上位32ビットを右シフトしてポインタを抽出し、下位32ビットをそのままカウンタとして抽出します。

### `src/runtime/lfstack_amd64.go` の変更

AMD64システム向けの実装です。AMD64の仮想アドレス空間の特性を考慮した、このコミットの主要な修正箇所の一つです。

*   コメントによる説明:
    "On AMD64, virtual addresses are 48-bit numbers sign extended to 64. We shift the address left 16 to eliminate the sign extended part and make room in the bottom for the count. In addition to the 16 bits taken from the top, we can take 3 from the bottom, because node must be pointer-aligned, giving a total of 19 bits of count."
    （AMD64では、仮想アドレスは48ビットであり、64ビットに符号拡張されます。アドレスを左に16ビットシフトすることで、符号拡張された部分を排除し、下位にカウンタのためのスペースを作ります。上位から取られた16ビットに加えて、`node`がポインタアラインされているため、下位から3ビットを取ることができ、合計で19ビットをカウンタに利用できます。）

*   `func lfstackPack(node *lfnode, cnt uintptr) uint64`:
    ```go
    return uint64(uintptr(unsafe.Pointer(node)))<<16 | uint64(cnt&(1<<19-1))
    ```
    ポインタを左に16ビットシフトします。これにより、64ビット値の上位16ビット（符号拡張によって埋められた部分）がクリアされ、同時に下位16ビットが空きます。`cnt&(1<<19-1)`は、カウンタを19ビットにマスクします。ポインタは通常8バイトアラインされているため、そのアドレスの下位3ビットは常に0です。この3ビットと、シフトによって空いた16ビットを合わせて、合計19ビットをABAカウンタとして利用します。

*   `func lfstackUnpack(val uint64) (node *lfnode, cnt uintptr)`:
    ```go
    node = (*lfnode)(unsafe.Pointer(uintptr(int64(val) >> 19 << 3)))
    cnt = uintptr(val & (1<<19 - 1))
    return
    ```
    `val >> 19`でカウンタ部分を削除します。`int64(val)`にキャストすることで、符号拡張されたアドレスを正しく扱い、`>> 19`でカウンタ部分をシフトアウトした後、`<< 3`でポインタを元の位置に戻します（ポインタが8バイトアラインされているため、下位3ビットは常に0であり、右シフトで失われたビットを補う形になります）。カウンタは`val & (1<<19 - 1)`で下位19ビットをマスクして抽出します。

### `src/runtime/lfstack_linux_power64x.go` の新規追加

Power64 Linuxシステム向けの実装です。

*   コメントによる説明:
    "On Power64, Linux limits the user address space to 43 bits. (https://www.kernel.org/doc/ols/2001/ppc64.pdf) In addition to the 21 bits taken from the top, we can take 3 from the bottom, because node must be pointer-aligned, giving a total of 24 bits of count."
    （Power64では、Linuxはユーザーアドレス空間を43ビットに制限します。上位から取られた21ビットに加えて、`node`がポインタアラインされているため、下位から3ビットを取ることができ、合計で24ビットをカウンタに利用できます。）

*   `func lfstackPack(node *lfnode, cnt uintptr) uint64`:
    ```go
    return uint64(uintptr(unsafe.Pointer(node)))<<21 | uint64(cnt&(1<<24-1))
    ```
    ポインタを左に21ビットシフトします。これにより、64ビット値の上位21ビットがクリアされ、下位21ビットが空きます。`cnt&(1<<24-1)`は、カウンタを24ビットにマスクします。AMD64と同様に、ポインタが8バイトアラインされているため、下位3ビットは常に0であり、この3ビットとシフトで空いた21ビットを合わせて、合計24ビットをABAカウンタとして利用します。

*   `func lfstackUnpack(val uint64) (node *lfnode, cnt uintptr)`:
    ```go
    node = (*lfnode)(unsafe.Pointer(uintptr(val >> 24 << 3)))
    cnt = uintptr(val & (1<<24 - 1))
    return
    ```
    `val >> 24`でカウンタ部分を削除し、`<< 3`でポインタを元の位置に戻します。カウンタは`val & (1<<24 - 1)`で下位24ビットをマスクして抽出します。

これらの変更により、Goランタイムのロックフリースタックは、異なるアーキテクチャの仮想アドレス空間の特性を正確に考慮し、ポインタとABAカウンタを安全かつ効率的に管理できるようになりました。

これらの変更により、ロックフリースタックの共通ロジックとアーキテクチャ固有のビット操作ロジックが明確に分離され、コードの保守性と移植性が向上しました。

## コアとなるコードの解説

このコミットの核心は、`lfstackPack`と`lfstackUnpack`という二つのヘルパー関数を導入し、それらを各アーキテクチャの特性に合わせて実装した点にあります。

*   **`lfstackPack(node *lfnode, cnt uintptr) uint64`**:
    この関数は、ロックフリースタックのノードポインタ（`node`）と、ABA問題を解決するためのバージョンカウンタ（`cnt`）を受け取り、これらを単一の`uint64`値に結合して返します。各アーキテクチャの`lfstackPack`実装は、そのアーキテクチャの仮想アドレス空間のビット幅と、ポインタのアラインメント（通常8バイトアラインメントにより下位3ビットが常に0であること）を考慮して、ポインタとカウンタを効率的にビットシフトおよびビットマスクで結合します。これにより、限られた`uint64`のビット空間を最大限に活用しつつ、ポインタとカウンタの情報を失うことなく格納します。

*   **`lfstackUnpack(val uint64) (node *lfnode, cnt uintptr)`**:
    この関数は、`lfstackPack`によって結合された`uint64`値を受け取り、そこから元のノードポインタ（`node`）とバージョンカウンタ（`cnt`）を正確に分離して返します。パッキング時と同様に、各アーキテクチャの`lfstackUnpack`実装は、そのアーキテクチャ固有のビット操作ロジックを用いて、結合された値からポインタとカウンタを抽出します。特にAMD64の場合、48ビット仮想アドレスの符号拡張を考慮した`int64`へのキャストとビットシフトが、ポインタを正しく復元するために重要です。

これらの関数は、`src/runtime/lfstack.go`内の`lfstackpush`と`lfstackpop`という、ロックフリースタックの主要な操作関数から呼び出されます。これにより、`lfstackpush`と`lfstackpop`は、ポインタとカウンタの具体的なパッキング/アンパッキング方法を知る必要がなくなり、よりクリーンで汎用的なロジックを維持できます。

この設計変更は、Goランタイムが異なるCPUアーキテクチャ上で、高性能かつ堅牢なロックフリーデータ構造を維持するための重要なステップです。アーキテクチャ固有の複雑なビット操作を抽象化することで、コードの可読性と保守性が大幅に向上し、将来的な新しいアーキテクチャへの対応も容易になります。

## 変更の背景

この変更の主な背景は、将来的な`android/amd64`プラットフォームでのPIEの必要性を見越したものです。コミットメッセージにもあるように、コミット作成者自身はすぐにこの機能を使用する予定はなかったものの、`android/amd64`がPIEを要求することになるため、そのサポートがどの程度困難であるかを確認するために実装されました。

PIEは、Address Space Layout Randomization (ASLR) と組み合わせて使用されることで、セキュリティを向上させる重要な技術です。ASLRは、実行可能ファイルやライブラリがメモリにロードされるアドレスをランダム化することで、攻撃者が特定のコードやデータを予測して悪用するのを困難にします。PIEは、実行可能ファイル自体がメモリ上の任意のアドレスにロードされても正しく動作するように設計されており、ASLRの効果を最大限に引き出すために不可欠です。

Go言語は、その設計思想からセキュリティを重視しており、このようなOSレベルのセキュリティ機能への対応は自然な流れと言えます。特にモバイルプラットフォームでは、セキュリティ要件が厳しくなる傾向があるため、`android/amd64`への対応はGoの適用範囲を広げる上で重要でした。

## 前提知識の解説

### Position Independent Executable (PIE)

Position Independent Executable (PIE) は、実行可能ファイルがメモリ上の任意のアドレスにロードされても正しく動作するようにビルドされた実行可能形式です。通常、実行可能ファイルは特定の固定されたメモリ位置にロードされることを前提としていますが、PIEはコード内のアドレス参照を相対的なものにすることで、この制約を取り除きます。

PIEは、Address Space Layout Randomization (ASLR) と組み合わせて使用されることで、セキュリティを大幅に向上させます。ASLRは、プログラムの実行時に、スタック、ヒープ、ライブラリ、そして実行可能ファイル自体のメモリ上の配置をランダム化する技術です。これにより、攻撃者がバッファオーバーフローなどの脆弱性を利用して特定のコード（例えばシェルコード）を実行しようとする際に、そのコードがメモリ上のどこに配置されているかを予測することを困難にします。

PIEがなければ、実行可能ファイルは常に同じベースアドレスにロードされるため、ASLRが適用されても実行可能ファイルのアドレスは予測可能になってしまいます。PIEを使用することで、実行可能ファイル自体もランダムなアドレスにロードされるようになり、ASLRの保護範囲が拡大し、攻撃の成功率を低下させることができます。

### 外部リンキング (External Linking) と内部リンキング (Internal Linking)

Go言語のビルドプロセスには、主に「内部リンキング」と「外部リンキング」の2つのリンキングモードがあります。

*   **内部リンキング (Internal Linking)**: GoコンパイラとリンカがGoのランタイム、標準ライブラリ、およびユーザーコードをすべて単一の静的バイナリに結合するデフォルトのモードです。このモードでは、C言語のライブラリ（libcなど）への依存が最小限に抑えられ、生成されるバイナリは非常にポータブルになります。しかし、Cgoを使用する場合や、特定のOS機能（例えばスレッドローカルストレージ (TLS) の高度な利用）が必要な場合には、制約が生じることがあります。

*   **外部リンキング (External Linking)**: Goコンパイラが生成したオブジェクトファイルを、システムのCリンカ（通常はgccやclang）に渡して最終的な実行可能ファイルを生成するモードです。このモードは、Cgoを使用する場合や、Goのランタイムが提供しない特定のシステムライブラリや機能に依存する場合に必要となります。外部リンキングを使用すると、生成されるバイナリはシステムのリンカの機能に依存するため、内部リンキングよりもポータビリティが低下する可能性がありますが、より複雑なシステム統合が可能になります。

このコミットでは、PIEのサポートが「外部リンキングに依存する」と明記されており、Goの内部リンカだけではPIEの生成に必要な特定のリンキング要件（特にTLS_IEのようなスレッドローカルストレージのインダイレクトアクセス）を満たすのが困難であったことが示唆されます。

### `cmd/go` と `cmd/link`

*   **`cmd/go`**: Goコマンドラインツールの中核であり、Goプログラムのビルド、テスト、インストール、フォーマットなど、様々な操作を統括します。ユーザーが`go build`などのコマンドを実行すると、`cmd/go`が適切なコンパイラやリンカを呼び出し、ビルドプロセス全体を管理します。
*   **`cmd/link`**: Goのリンカです。コンパイラが生成したオブジェクトファイル（`.o`ファイル）を結合し、最終的な実行可能ファイルやライブラリを生成します。内部リンキングの場合、`cmd/link`がGoのランタイムとユーザーコードを結合します。外部リンキングの場合、`cmd/link`は中間オブジェクトファイルを生成し、それをシステムのCリンカに渡します。

このコミットでは、`cmd/go`が新しいビルドモード`-buildmode=pie`を認識し、それに応じてビルドプロセスを調整するように変更され、`cmd/link`はPIEの生成に必要なリンキングロジックを実装するように変更されています。

    *   `misc/cgo/testshared/shared_test.go`に、生成されたバイナリがPIEであること、および`DT_TEXTREL`フラグが設定されていないことを検証するテストが追加されています。

        *   `TestTrivialPIE`と`TestCgoPIE`は、それぞれGoのみのプログラムとCgoを使用するプログラムを`-buildmode=pie`でビルドし、`checkPIE`関数で検証します。

これらの変更により、Goツールチェーンは`linux/amd64`上でPIEを生成する能力を獲得し、ASLRによるセキュリティ強化の恩恵を受けられるようになりました。

### `misc/cgo/testshared/shared_test.go` の変更

```go
func checkPIE(t *testing.T, name string) {
	f, err := elf.Open(name)
	if err != nil {
		t.Fatal("elf.Open failed: ", err)
	}
	defer f.Close()
	if f.Type != elf.ET_DYN {
		t.Errorf("%s has type %v, want ET_DYN", name, f.Type)
	}
	if hasDynTag(f, elf.DT_TEXTREL) {
		t.Errorf("%s has DT_TEXTREL set", name)
	}
}

func TestTrivialPIE(t *testing.T) {
	name := "trivial_pie"
	goCmd(t, "build", "-buildmode=pie", "-o="+name, "trivial")
	defer os.Remove(name)
	run(t, name, "./"+name)
	checkPIE(t, name)
}

func TestCgoPIE(t *testing.T) {
	name := "cgo_pie"
	goCmd(t, "build", "-buildmode=pie", "-o="+name, "execgo")
	defer os.Remove(name)
	run(t, name, "./"+name)
	checkPIE(t, name)
}
```
`checkPIE`関数は、ELF形式の実行ファイルがPIEであるかを検証する重要な部分です。
*   `elf.Open(name)`: 指定されたファイル名のELFバイナリを開きます。
*   `f.Type != elf.ET_DYN`: ELFヘッダの`e_type`フィールドが`ET_DYN`（Dynamic Shared Object、つまりPIEまたは共有ライブラリ）でない場合、エラーを報告します。PIEは共有ライブラリと同様に動的にロードされるため、このタイプを持ちます。
*   `hasDynTag(f, elf.DT_TEXTREL)`: `DT_TEXTREL`は、テキストセクション（コード）に実行時再配置が必要であることを示す動的タグです。PIEは通常、テキストセクションが完全に位置独立であるため、このタグを持つべきではありません。このタグが存在すると、セキュリティ上の問題（書き込み可能なテキストセクション）やパフォーマンス上の問題（ロード時の再配置オーバーヘッド）を示唆する可能性があります。

`TestTrivialPIE`と`TestCgoPIE`は、それぞれGoのみのシンプルなプログラムとCgoを使用するプログラムを`-buildmode=pie`でビルドし、その結果が`checkPIE`の条件を満たすことを確認します。これにより、PIEビルドが正しく機能していることが保証されます。

func (p *Package) load(stk *importStack, bp *build.Package, err error) *Package {

このコードスニペットは、メインパッケージをビルドする際に、ビルドモードが`c-shared`、`pie`、または`-linkshared`のいずれかである場合に、`runtime/cgo`パッケージのインポートを強制します。これは、これらのビルドモードが外部リンキングを必要とし、外部リンキングがGoのCgoランタイムに依存するためです。`runtime/cgo`は、GoとCの間の相互運用に必要なコードを含んでいます。

### `src/cmd/link/internal/ld/lib.go` の変更

func (mode *BuildMode) Set(s string) error {
	// ...
	case "pie":
		switch goos {
		case "android", "linux": // <-- ここが変更点

		}

	// ...
	// Force external linking for PIE executables, as

`BuildMode.Set`関数は、リンカがビルドモードを設定する際に呼び出されます。`goos`が`"linux"`の場合に`"pie"`モードが許可されるように変更されています。

`loadlib`関数は、リンカがライブラリをロードする際に呼び出される初期化関数です。ここで、`Buildmode == BuildmodePIE`の場合に`Linkmode = LinkExternal`が強制されます。このコメントにあるように、「内部リンキングは`TLS_IE`をサポートしない」ため、PIEの生成には外部リンキングが必要であることが明確に示されています。`TLS_IE`は、スレッドローカルストレージへの間接的なアクセスを可能にするリンキングメカニズムであり、PIEのような位置独立なコードでスレッドローカル変数にアクセスするために重要です。

### Position Independent Executable (PIE)

Position Independent Executable (PIE) は、実行可能ファイルがメモリ上の任意のアドレスにロードされても正しく動作するようにビルドされた実行可能形式です。通常、実行可能ファイルは特定の固定されたメモリ位置にロードされることを前提としていますが、PIEはコード内のアドレス参照を相対的なものにすることで、この制約を取り除きます。

PIEは、Address Space Layout Randomization (ASLR) と組み合わせて使用されることで、セキュリティを大幅に向上させます。ASLRは、プログラムの実行時に、スタック、ヒープ、ライブラリ、そして実行可能ファイル自体のメモリ上の配置をランダム化する技術です。これにより、攻撃者がバッファオーバーフローなどの脆弱性を利用して特定のコード（例えばシェルコード）を実行しようとする際に、そのコードがメモリ上のどこに配置されているかを予測することを困難にします。

PIEがなければ、実行可能ファイルは常に同じベースアドレスにロードされるため、ASLRが適用されても実行可能ファイルのアドレスは予測可能になってしまいます。PIEを使用することで、実行可能ファイル自体もランダムなアドレスにロードされるようになり、ASLRの保護範囲が拡大し、攻撃の成功率を低下させることができます。

### 外部リンキング (External Linking) と内部リンキング (Internal Linking)

Go言語のビルドプロセスには、主に「内部リンキング」と「外部リンキング」の2つのリンキングモードがあります。

*   **内部リンキング (Internal Linking)**: GoコンパイラとリンカがGoのランタイム、標準ライブラリ、およびユーザーコードをすべて単一の静的バイナリに結合するデフォルトのモードです。このモードでは、C言語のライブラリ（libcなど）への依存が最小限に抑えられ、生成されるバイナリは非常にポータブルになります。しかし、Cgoを使用する場合や、特定のOS機能（例えばスレッドローカルストレージ (TLS) の高度な利用）が必要な場合には、制約が生じることがあります。

*   **外部リンキング (External Linking)**: Goコンパイラが生成したオブジェクトファイルを、システムのCリンカ（通常はgccやclang）に渡して最終的な実行可能ファイルを生成するモードです。このモードは、Cgoを使用する場合や、Goのランタイムが提供しない特定のシステムライブラリや機能に依存する場合に必要となります。外部リンキングを使用すると、生成されるバイナリはシステムのリンカの機能に依存するため、内部リンキングよりもポータビリティが低下する可能性がありますが、より複雑なシステム統合が可能になります。

このコミットでは、PIEのサポートが「外部リンキングに依存する」と明記されており、Goの内部リンカだけではPIEの生成に必要な特定のリンキング要件（特にTLS_IEのようなスレッドローカルストレージのインダイレクトアクセス）を満たすのが困難であったことが示唆されます。

### `cmd/go` と `cmd/link`

*   **`cmd/go`**: Goコマンドラインツールの中核であり、Goプログラムのビルド、テスト、インストール、フォーマットなど、様々な操作を統括します。ユーザーが`go build`などのコマンドを実行すると、`cmd/go`が適切なコンパイラやリンカを呼び出し、ビルドプロセス全体を管理します。
*   **`cmd/link`**: Goのリンカです。コンパイラが生成したオブジェクトファイル（`.o`ファイル）を結合し、最終的な実行可能ファイルやライブラリを生成します。内部リンキングの場合、`cmd/link`がGoのランタイムとユーザーコードを結合します。外部リンキングの場合、`cmd/link`は中間オブジェクトファイルを生成し、それをシステムのCリンカに渡します。

このコミットでは、`cmd/go`が新しいビルドモード`-buildmode=pie`を認識し、それに応じてビルドプロセスを調整するように変更され、`cmd/link`はPIEの生成に必要なリンキングロジックを実装するように変更されています。

## コアとなるコードの解説

### `misc/cgo/testshared/shared_test.go` の変更

```go
func checkPIE(t *testing.T, name string) {
	f, err := elf.Open(name)
	if err != nil {
		t.Fatal("elf.Open failed: ", err)
	}
	defer f.Close()
	if f.Type != elf.ET_DYN {
		t.Errorf("%s has type %v, want ET_DYN", name, f.Type)
	}
	if hasDynTag(f, elf.DT_TEXTREL) {
		t.Errorf("%s has DT_TEXTREL set", name)
	}
}

func TestTrivialPIE(t *testing.T) {
	name := "trivial_pie"
	goCmd(t, "build", "-buildmode=pie", "-o="+name, "trivial")
	defer os.Remove(name)
	run(t, name, "./"+name)
	checkPIE(t, name)
}

func TestCgoPIE(t *testing.T) {
	name := "cgo_pie"
	goCmd(t, "build", "-buildmode=pie", "-o="+name, "execgo")
	defer os.Remove(name)
	run(t, name, "./"+name)
	checkPIE(t, name)
}
```
`checkPIE`関数は、ELF形式の実行ファイルがPIEであるかを検証する重要な部分です。
*   `elf.Open(name)`: 指定されたファイル名のELFバイナリを開きます。
*   `f.Type != elf.ET_DYN`: ELFヘッダの`e_type`フィールドが`ET_DYN`（Dynamic Shared Object、つまりPIEまたは共有ライブラリ）でない場合、エラーを報告します。PIEは共有ライブラリと同様に動的にロードされるため、このタイプを持ちます。
*   `hasDynTag(f, elf.DT_TEXTREL)`: `DT_TEXTREL`は、テキストセクション（コード）に実行時再配置が必要であることを示す動的タグです。PIEは通常、テキストセクションが完全に位置独立であるため、このタグを持つべきではありません。このタグが存在すると、セキュリティ上の問題（書き込み可能なテキストセクション）やパフォーマンス上の問題（ロード時の再配置オーバーヘッド）を示唆する可能性があります。

`TestTrivialPIE`と`TestCgoPIE`は、それぞれGoのみのシンプルなプログラムとCgoを使用するプログラムを`-buildmode=pie`でビルドし、その結果が`checkPIE`の条件を満たすことを確認します。これにより、PIEビルドが正しく機能していることが保証されます。

		if buildToolchain == "gccgo" {

`buildModeInit`関数は、ビルドモードが初期化される際に呼び出されます。`platform`変数（`GOOS/GOARCH`の形式）が`"linux/amd64"`の場合に`-buildmode=pie`が許可されるように変更されています。`codegenArg = "-shared"`は、コンパイラに共有ライブラリ（PIEも含む）を生成するための適切なコード生成オプションを渡すことを意味します。

### `src/cmd/go/pkg.go` の変更

```go
func (p *Package) load(stk *importStack, bp *build.Package, err error) *Package {
	// ...
	// Currently build modes c-shared, pie, and -linkshared force
	// external linking mode, and external linking mode forces an
	// import of runtime/cgo.
	if p.Name == "main" && !p.Goroot && (buildBuildmode == "c-shared" || buildBuildmode == "pie" || buildLinkshared) { // <-- ここが変更点
		importPaths = append(importPaths, "runtime/cgo")
	}
	// ...
}
```
このコードスニペットは、メインパッケージをビルドする際に、ビルドモードが`c-shared`、`pie`、または`-linkshared`のいずれかである場合に、`runtime/cgo`パッケージのインポートを強制します。これは、これらのビルドモードが外部リンキングを必要とし、外部リンキングがGoのCgoランタイムに依存するためです。`runtime/cgo`は、GoとCの間の相互運用に必要なコードを含んでいます。

### `src/cmd/link/internal/ld/lib.go` の変更

```go
func (mode *BuildMode) Set(s string) error {
	// ...
	case "pie":
		switch goos {
		case "android", "linux": // <-- ここが変更点
		default:
			return badmode()
		}
		*mode = BuildmodePIE
	// ...
}

func loadlib() {
	// ...
	// Force external linking for PIE executables, as
	// internal linking does not support TLS_IE.
	if Buildmode == BuildmodePIE { // <-- ここが追加されたロジック
		Linkmode = LinkExternal
	}
	// ...
}
```
`BuildMode.Set`関数は、リンカがビルドモードを設定する際に呼び出されます。`goos`が`"linux"`の場合に`"pie"`モードが許可されるように変更されています。

`loadlib`関数は、リンカがライブラリをロードする際に呼び出される初期化関数です。ここで、`Buildmode == BuildmodePIE`の場合に`Linkmode = LinkExternal`が強制されます。このコメントにあるように、「内部リンキングは`TLS_IE`をサポートしない」ため、PIEの生成には外部リンキングが必要であることが明確に示されています。`TLS_IE`は、スレッドローカルストレージへの間接的なアクセスを可能にするリンキングメカニズムであり、PIEのような位置独立なコードでスレッドローカル変数にアクセスするために重要です。

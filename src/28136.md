# [インデックス 28136] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ(GC)におけるヒープビットマップの管理方法を最適化し、オブジェクトの最初のワードにおけるスキャン/デッドビットの利用を改善するものです。これにより、GC関連のコードが簡素化され、特定のベンチマークでパフォーマンスが向上しています。

    runtime: reclaim scan/dead bit in first word
    
    With the switch to separate mark bitmaps, the scan/dead bit for the
    first word of each object is now unused. Reclaim this bit and use it
    as a scan/dead bit, just like words three and on. The second word is
    still used for checkmark.
    
    This dramatically simplifies heapBitsSetTypeNoScan and hasPointers,
    since they no longer need different cases for 1, 2, and 3+ word
    objects. They can instead just manipulate the heap bitmap for the
    first word and be done with it.
    
    In order to enable this, we change heapBitsSetType and runGCProg to
    always set the scan/dead bit to scan for the first word on every code
    path. Since these functions only apply to types that have pointers,
    there's no need to do this conditionally: it's *always* necessary to
    set the scan bit in the first word.
    
    We also change every place that scans an object and checks if there
    are more pointers. Rather than only checking morePointers if the word
    is >= 2, we now check morePointers if word != 1 (since that's the
    checkmark word).
    
    Looking forward, we should probably reclaim the checkmark bit, too,
    but that's going to be quite a bit more work.
    
    Tested by setting doubleCheck in heapBitsSetType and running all.bash
    on both linux/amd64 and linux/386, and by running GOGC=10 all.bash.

## 元コミット内容

Goランタイム: オブジェクトの最初のワードにおけるスキャン/デッドビットを再利用する。

マークビットマップが分離されたことにより、各オブジェクトの最初のワードにおけるスキャン/デッドビットが未使用になっていた。このビットを再利用し、3番目以降のワードと同様にスキャン/デッドビットとして使用する。2番目のワードは引き続きチェックマークに使用される。

これにより、`heapBitsSetTypeNoScan`と`hasPointers`が大幅に簡素化される。これらの関数は、1ワード、2ワード、3ワード以上のオブジェクトに対して異なるケースを考慮する必要がなくなり、最初のワードのヒープビットマップを操作するだけで済むようになる。

これを可能にするため、`heapBitsSetType`と`runGCProg`は、ポインタを持つ型に適用されるすべてのコードパスで、最初のワードのスキャン/デッドビットを常にスキャン状態に設定するように変更される。これらの関数はポインタを持つ型にのみ適用されるため、条件付きでこれを行う必要はない。最初のワードのスキャンビットを設定することは常に必要である。

また、オブジェクトをスキャンし、さらにポインタがあるかどうかをチェックするすべての箇所も変更される。ワードが2以上の場合にのみ`morePointers`をチェックするのではなく、ワードが1でない場合（チェックマークワードであるため）に`morePointers`をチェックするように変更される。

将来的にはチェックマークビットも再利用すべきだが、それはかなり多くの作業が必要になるだろう。

`heapBitsSetType`で`doubleCheck`を設定し、`linux/amd64`と`linux/386`の両方で`all.bash`を実行し、`GOGC=10 all.bash`を実行してテスト済み。

この変更は、`noscan`アロケーションを大量に行う`FmtFprintf*` go1ベンチマークを特に改善する。

ベンチマーク結果の詳細は上記コミット内容を参照。全体的な幾何平均で-1.00%の改善が見られる。

## 変更の背景

Goのガベージコレクタは、ヒープ上のオブジェクトがポインタを含むかどうか、そしてそのポインタがどこにあるかを追跡するためにヒープビットマップを使用します。以前のGoランタイムでは、マークビットマップとスキャン/デッドビットの管理方法に特定の制約がありました。

このコミットの背景には、Goランタイムが「分離されたマークビットマップ (separate mark bitmaps)」に切り替わったという重要な変更があります。この変更により、各オブジェクトの最初のワードに対応するヒープビットマップ内の特定のビットが、スキャン/デッド情報を格納するために使われなくなりました。これは、リソースの無駄であり、GCのロジックを不必要に複雑にする原因となっていました。

具体的には、オブジェクトのサイズ（1ワード、2ワード、3ワード以上）に応じて、ヒープビットマップの解釈や操作に異なるロジックが必要とされ、`heapBitsSetTypeNoScan`や`hasPointers`といったGC関連の重要な関数が複雑になっていました。この複雑さは、コードの保守性を低下させ、最適化の機会を逃していました。

このコミットは、この未使用のビットを再利用することで、GCの内部動作を簡素化し、効率を向上させることを目的としています。特に、`noscan`（ポインタを含まない）オブジェクトの割り当てが多いシナリオでのパフォーマンス改善が期待されました。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのガベージコレクタとヒープ管理に関するいくつかの概念を理解しておく必要があります。

1.  **Goのガベージコレクタ (GC)**: Goは並行マーク＆スイープ型のGCを採用しています。これは、プログラムの実行と並行してガベージコレクションを行うことで、STW (Stop-The-World) 時間を最小限に抑えることを目指しています。GCの主要なフェーズには、マークフェーズ（到達可能なオブジェクトを識別する）とスイープフェーズ（到達不能なオブジェクトのメモリを解放する）があります。
2.  **ヒープビットマップ (Heap Bitmap)**: Goランタイムは、ヒープ上の各オブジェクトに関するメタデータを格納するためにヒープビットマップを使用します。このビットマップは、オブジェクト内のどのワードがポインタであるか、オブジェクトがGCによってマークされているか、オブジェクトがスキャン済みか、あるいはオブジェクトが「デッド」（これ以上ポインタを含まない）であるかなどの情報を示します。これにより、GCはヒープを効率的に走査し、ポインタをたどることができます。
3.  **2ビットエントリ**: Goのヒープビットマップは、通常、各ワードに対して2ビットのエントリを使用します。
    *   **下位ビット (Low Bit)**: オブジェクトのそのワードがポインタであるかどうかを示します（0: ポインタではない、1: ポインタである）。
    *   **上位ビット (High Bit)**: そのワードの位置によって異なる意味を持ちます。
        *   **スキャン/デッドビット**: オブジェクトの残りの部分がGCにとって興味深いものであるか（スキャンが必要か）、「デッド」（これ以上ポインタを含まない）であるかを示します。このビットが00の場合、残りのワードはスカラー（ポインタを含まない）であると見なされ、GCはそれ以上スキャンを停止できます。
        *   **チェックマークビット (Checkmark Bit)**: 特定のGCフェーズで使用される特別なビットで、オブジェクトが特定の条件を満たしているか（例えば、GCが完了したか）をマークするために使われます。
4.  **オブジェクトのワード構造**: Goのヒープ上のオブジェクトは、複数のワード（通常は`sys.PtrSize`、32ビットシステムでは4バイト、64ビットシステムでは8バイト）で構成されます。オブジェクトの最初のワード、2番目のワード、3番目以降のワードでは、ヒープビットマップの解釈が異なる場合があります。
5.  **`noscan`オブジェクト**: ポインタを一切含まないオブジェクトは`noscan`オブジェクトと呼ばれます。これらのオブジェクトはGCがポインタをスキャンする必要がないため、GCのオーバーヘッドを削減できます。
6.  **`heapBitsSetType`**: オブジェクトがヒープに割り当てられる際に、その型情報に基づいてヒープビットマップを設定する関数です。
7.  **`heapBitsSetTypeNoScan`**: `noscan`オブジェクトに対してヒープビットマップを設定する関数です。
8.  **`hasPointers`**: オブジェクトがポインタを含むかどうかを判断する関数です。GCがオブジェクトをスキャンする必要があるかどうかを決定するために使用されます。
9.  **`morePointers`**: 現在のワード以降にさらにポインタが存在するかどうかを示すヒープビットマップのビットをチェックする関数です。

このコミットは、特にヒープビットマップの2ビットエントリにおける上位ビットの役割と、オブジェクトの最初のワードの扱いに関する変更に焦点を当てています。

## 技術的詳細

このコミットの核心は、Goランタイムのヒープビットマップにおけるオブジェクトの最初のワードのメタデータ表現の変更です。

以前の「分離されたマークビットマップ」への切り替え後、オブジェクトの最初のワードに対応するヒープビットマップの「上位ビット」が未使用の状態でした。このコミットでは、この未使用ビットを「スキャン/デッドビット」として再利用します。これにより、オブジェクトの最初のワードも、3番目以降のワードと同様に、その上位ビットがオブジェクトの残りの部分がGCにとって興味深いかどうか（スキャンが必要か）を示すために使用されるようになります。

ただし、オブジェクトの2番目のワードの上位ビットは、引き続き「チェックマークビット」として特別な目的で使用されます。これは、GCの特定の段階でオブジェクトの状態をマークするために使われるものです。

この変更がもたらす主な技術的影響は以下の通りです。

1.  **`heapBitsSetTypeNoScan`の簡素化**:
    *   以前は、`noscan`オブジェクトのサイズ（1ワード、2ワード、3ワード以上）に応じて、`heapBitsSetTypeNoScan`は複雑な条件分岐ロジックを持っていました。
    *   変更後、オブジェクトの最初のワードのスキャン/デッドビットを操作するだけで、`noscan`オブジェクトであることを表現できるようになりました。これにより、関数が大幅に簡素化され、コード量が削減されました。
2.  **`hasPointers`の簡素化**:
    *   `hasPointers`関数も、オブジェクトのサイズに応じた複雑なロジックを持っていました。
    *   変更後、オブジェクトの最初のワードのヒープビットマップを直接チェックするだけで、オブジェクトがポインタを含むかどうかを判断できるようになりました。これにより、コードがより直接的で効率的になりました。
3.  **`morePointers`のロジック変更**:
    *   オブジェクトをスキャンする際に、現在のワード以降にさらにポインタがあるかを判断する`morePointers`の呼び出し箇所が変更されました。
    *   以前は「ワードが2以上の場合」に`morePointers`をチェックしていましたが、これは「ワードが1でない場合」（ワード1はチェックマークビットが格納されているため）にチェックするように変更されました。これは、最初のワードがスキャン/デッドビットを持つようになった新しいセマンティクスに合わせたものです。
4.  **`heapBitsSetType`と`runGCProg`の動作変更**:
    *   ポインタを持つ型に対しては、`heapBitsSetType`と`runGCProg`が、オブジェクトの最初のワードのスキャン/デッドビットを常に「スキャン」状態に設定するように変更されました。これは、ポインタを持つオブジェクトは常にスキャンされる必要があるため、条件分岐なしで一貫して設定できるようになったためです。
5.  **パフォーマンスへの影響**:
    *   `noscan`オブジェクトの割り当てが多いシナリオ（例: `FmtFprintf*`ベンチマーク）で、GCのヒープビットマップ操作が簡素化されたことにより、パフォーマンスが向上しました。これは、GCがオブジェクトのポインタ情報をより効率的に処理できるようになったためです。
    *   ベンチマーク結果では、多くの`FmtFprintf*`関連のテストで顕著な改善が見られ、全体的な幾何平均でもわずかながら改善が確認されています。

この変更は、GoのGCの内部実装をよりクリーンで効率的なものにし、将来的なGCの最適化や機能追加のための基盤を強化するものです。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/runtime/mbitmap.go`内の`hasPointers`関数と`heapBitsSetTypeNoScan`関数の簡素化、およびヒープビットマップのセマンティクス変更です。

### `hasPointers`関数の簡素化

以前の`hasPointers`関数は、オブジェクトのサイズ（1ワード、2ワード、3ワード以上）に応じて、ヒープビットマップの異なる部分をチェックする複雑なロジックを持っていました。これは、最初のワードの上位ビットが未使用であったり、2番目のワードがチェックマークビットであったりといった、ワードごとのビットの役割の違いに起因していました。

変更後、`hasPointers`は以下のように劇的に簡素化されました。

```go
func (h heapBits) hasPointers(size uintptr) bool {
	if size == sys.PtrSize { // 1-word objects are always pointers
		return true
	}
	return (*h.bitp>>h.shift)&bitMarked != 0
}
```

この変更は、オブジェクトの最初のワードの上位ビットが「スキャン/デッドビット」として再利用されるようになったため可能になりました。これにより、オブジェクトがポインタを含むかどうかは、その最初のワードに対応するヒープビットマップエントリの`bitMarked`（実質的にはスキャンビット）が設定されているかどうかをチェックするだけで判断できるようになりました。もし`bitMarked`が設定されていれば、オブジェクトはポインタを含み、GCスキャンが必要です。設定されていなければ、オブジェクトはスカラー（ポインタなし）であると判断できます。

### `heapBitsSetTypeNoScan`関数の簡素化

`heapBitsSetTypeNoScan`関数は、ポインタを含まない`noscan`オブジェクトのヒープビットマップを設定するために使用されます。以前は、この関数もオブジェクトのサイズに応じて複雑なロジックを持っていました。

変更後、この関数は以下のように簡素化されました。

```go
func heapBitsSetTypeNoScan(x uintptr) {
	h := heapBitsForAddr(uintptr(x))
	*h.bitp &^= (bitPointer | bitMarked) << h.shift
}
```

この新しい実装では、`noscan`オブジェクトの最初のワードに対応するヒープビットマップエントリの`bitPointer`と`bitMarked`の両方をクリアします。`bitPointer`をクリアすることで、そのワードがポインタではないことを示し、`bitMarked`（スキャンビット）をクリアすることで、オブジェクトが「デッド」（これ以上スキャンする必要がない）であることを示します。これにより、GCは`noscan`オブジェクトをスキャンする必要がないと即座に判断でき、効率が向上します。

### ヒープビットマップのセマンティクス変更

`src/runtime/mbitmap.go`のコメント更新が示すように、ヒープビットマップの2ビットエントリにおける上位ビットの役割が明確化されました。

*   **最初のワード**: 上位ビットは「スキャン/デッドビット」として機能し、オブジェクトの残りの部分がGCにとって興味深いかどうかを示します。
*   **2番目のワード**: 上位ビットは引き続き「チェックマークビット」として機能します。
*   **3番目以降のワード**: 上位ビットは「スキャン/デッドビット」として機能します。

この一貫性の向上により、GCのロジックがよりシンプルになり、特定のオブジェクトサイズに対する特殊なケース処理が不要になりました。

これらの変更は、GoのGCがヒープ上のオブジェクトのポインタ情報をより効率的かつ統一的に管理できるようにすることで、GCのオーバーヘッドを削減し、全体的なランタイムパフォーマンスを向上させることに貢献しています。

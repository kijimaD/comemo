# [インデックス 23141] ファイルの概要

このコミットは、Goランタイムにおけるメモリ統計、特にスタック使用量の計上方法に関するバグ修正です。`runtime.MemStats`構造体を通じて公開されるメモリ統計において、スタックメモリの計上が内部的なランタイムの挙動と一致しない問題を解決します。具体的には、`readmemstats_m`関数が`StackSys`（システムから取得したスタックメモリ）が常にゼロであると誤って仮定していたために発生していた、`StackSys`と`HeapSys`の合計値の不整合を修正します。

## コミット

Date:   Mon Apr 27 14:50:42 2015 -0400

    runtime: fix stack use accounting
    
    ReadMemStats accounts for stacks slightly differently than the runtime
    does internally. Internally, only stacks allocated by newosproc0 are
    accounted in memstats.stacks_sys and other stacks are accounted in
    heap_sys. readmemstats_m shuffles the statistics so all stacks are
    accounted in StackSys rather than HeapSys.
    
    However, currently, readmemstats_m assumes StackSys will be zero when
    it does this shuffle. This was true until commit 6ad33be. If it isn't
    (e.g., if something called newosproc0), StackSys+HeapSys will be
    different before and after this shuffle, and the Sys sum that was
    computed earlier will no longer agree with the sum of its components.
    
    Fix this by making the shuffle in readmemstats_m not assume that
    StackSys is zero.
    
    Fixes #10585.

## 元コミット内容

`runtime: fix stack use accounting`

`ReadMemStats`は、ランタイムが内部的にスタックを計上する方法とわずかに異なる方法でスタックを計上します。内部的には、`newosproc0`によって割り当てられたスタックのみが`memstats.stacks_sys`に計上され、その他のスタックは`heap_sys`に計上されます。`readmemstats_m`は、すべてのスタックが`HeapSys`ではなく`StackSys`に計上されるように統計をシャッフルします。

しかし、現在、`readmemstats_m`はこのシャッフルを行う際に`StackSys`がゼロであると仮定しています。これはコミット`6ad33be`までは真でした。もしゼロでない場合（例えば、`newosproc0`が呼び出された場合）、このシャッフル前後で`StackSys+HeapSys`が異なり、以前計算された`Sys`の合計がその構成要素の合計と一致しなくなります。

`readmemstats_m`でのシャッフルが`StackSys`がゼロであると仮定しないようにすることで、これを修正します。

Fixes #10585.

## 変更の背景

Goランタイムは、プログラムのメモリ使用状況を詳細に追跡し、`runtime.MemStats`構造体を介してその統計情報を公開しています。この統計は、アプリケーションのパフォーマンス監視やメモリリークのデバッグに不可欠です。

このコミットが修正する問題は、`runtime.MemStats`がスタックメモリの使用量を報告する方法と、ランタイムが内部的にスタックメモリを管理する方法との間に不整合があったことです。

具体的には、以下の点が問題でした：
1.  **内部的な計上方法**: Goランタイムの内部では、`newosproc0`（新しいOSスレッドを作成する際に呼び出される関数）によって割り当てられたスタックは`memstats.stacks_sys`という専用のフィールドで追跡されていました。しかし、それ以外の通常のGoルーチンのスタックは、一般的なヒープメモリとして`heap_sys`に計上されていました。
2.  **`ReadMemStats`の調整**: `runtime.ReadMemStats`関数が呼び出されると、内部的な統計情報がユーザーが利用できる`MemStats`構造体にコピーされます。この際、`readmemstats_m`という内部関数が、すべてのスタックメモリが`MemStats.StackSys`に統一して計上されるように、`HeapSys`からスタック関連の値を`StackSys`に「シャッフル」する処理を行っていました。これは、ユーザーにとってスタックメモリの総量を一箇所で確認できるようにするための配慮です。
3.  **誤った仮定**: しかし、この`readmemstats_m`関数は、シャッフル処理を行う前に`MemStats.StackSys`の値が常にゼロであると誤って仮定していました。この仮定は、過去の特定のコミット（`6ad33be`）までは正しかったのですが、そのコミット以降、`newosproc0`のような特定の条件下で`MemStats.StackSys`がゼロ以外の値を持つ可能性が生じました。
4.  **統計の不整合**: `StackSys`がゼロでない状態でシャッフル処理が行われると、`StackSys`に`StackInuse`（現在使用中のスタックメモリ量）が加算される際に、既存の`StackSys`の値が二重に計上される形になってしまいました。これにより、`StackSys`と`HeapSys`の合計値（システムから取得した総メモリ量）が、シャッフル処理の前後で異なってしまい、メモリ統計の信頼性が損なわれるという問題が発生していました。

この不整合は、Goアプリケーションのメモリ使用量を正確に把握しようとするユーザーやツールにとって混乱の原因となり、誤った最適化やデバッグにつながる可能性がありました。このコミットは、この計上ロジックのバグを修正し、メモリ統計の正確性を回復することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理と統計に関する以下の概念を理解しておく必要があります。

1.  **Goランタイム (Go Runtime)**:
    Goプログラムは、Goランタイムと呼ばれる軽量な実行環境上で動作します。Goランタイムは、ガベージコレクション、スケジューリング（Goルーチンの管理）、メモリ割り当てなど、プログラムの実行に必要な多くの低レベルなタスクを処理します。

2.  **Goルーチン (Goroutine)**:
    GoルーチンはGoにおける軽量な並行処理の単位です。OSスレッドよりもはるかに軽量で、数百万のGoルーチンを同時に実行することも可能です。各Goルーチンは独自のスタックを持ち、このスタックは必要に応じて動的に拡大・縮小します。

3.  **スタック (Stack)**:
    スタックは、関数呼び出しの際にローカル変数や引数、戻りアドレスなどを格納するために使用されるメモリ領域です。Goルーチンのスタックは、通常、ヒープから割り当てられます。

4.  **ヒープ (Heap)**:
    ヒープは、プログラムが実行時に動的にメモリを割り当てるために使用されるメモリ領域です。Goでは、`make`や`new`などの組み込み関数によって割り当てられるオブジェクトや、Goルーチンのスタックもヒープから割り当てられます。

5.  **`runtime.MemStats`**:
    `runtime`パッケージが提供する`MemStats`構造体は、Goランタイムのメモリ使用状況に関する包括的な統計情報を含んでいます。この構造体には、ヒープの使用量、スタックの使用量、ガベージコレクションの統計など、多岐にわたる情報が含まれます。
    主要なフィールドには以下のようなものがあります：
    *   `Alloc`: 現在割り当てられているオブジェクトの合計バイト数。
    *   `TotalAlloc`: 起動以降に割り当てられたオブジェクトの合計バイト数。
    *   `Sys`: システムから取得したメモリの合計バイト数。これは`HeapSys`、`StackSys`、`MSpanSys`、`MCacheSys`などの合計です。
    *   `HeapAlloc`: ヒープに割り当てられているオブジェクトの合計バイト数。
    *   `HeapSys`: ヒープのためにシステムから取得したメモリの合計バイト数。
    *   `StackSys`: スタックのためにシステムから取得したメモリの合計バイト数。

6.  **`runtime.ReadMemStats()`**:
    この関数は、現在のGoランタイムのメモリ統計を`runtime.MemStats`構造体に読み込みます。アプリケーションは、この関数を呼び出すことで、メモリ使用状況をプログラム的に監視できます。

7.  **`newosproc0`**:
    Goランタイムの内部関数で、新しいOSスレッド（M: Machine）を作成する際に呼び出されます。この関数によって割り当てられるスタックは、通常のGoルーチンのスタックとは異なる方法で計上されることがあります。

8.  **メモリ計上の「シャッフル」**:
    Goランタイムは、内部的にはスタックメモリの一部をヒープの一部として管理することがあります。しかし、`MemStats`をユーザーに公開する際には、スタック関連のメモリを`StackSys`という専用のフィールドに集約して報告することで、ユーザーがスタックの使用量をより直感的に理解できるようにしています。この集約プロセスが、コミットメッセージで言及されている「シャッフル」です。

## 技術的詳細

このコミットの核心は、`src/runtime/mstats.go`ファイル内の`readmemstats_m`関数における`StackSys`の計上ロジックの変更です。

Goランタイムは、メモリ統計を内部的な`memstats`構造体で管理しています。`runtime.ReadMemStats`が呼び出されると、この内部的な`memstats`のデータが、ユーザーに公開される`runtime.MemStats`構造体（引数`stats`として渡される）にコピーされます。

このコピー後、`readmemstats_m`関数は、スタック関連のメモリ統計を調整します。
元のコードは以下のようになっていました：

```go
// Stack numbers are part of the heap numbers, separate those out for user consumption
stats.StackSys = stats.StackInuse
stats.HeapInuse -= stats.StackInuse
stats.HeapSys -= stats.StackInuse
```

このコードの意図は、「スタックの数値はヒープの数値の一部なので、ユーザーが利用できるようにそれらを分離する」というものです。
1.  `stats.StackSys = stats.StackInuse`: `StackSys`に現在使用中のスタックメモリ量（`StackInuse`）を代入しています。これは、`StackSys`がシャッフル処理の開始時点でゼロであるという暗黙の仮定に基づいています。
2.  `stats.HeapInuse -= stats.StackInuse`: ヒープの使用中メモリからスタックの使用中メモリを減算します。
3.  `stats.HeapSys -= stats.StackInuse`: システムから取得したヒープメモリからスタックの使用中メモリを減算します。

問題は、コミットメッセージにもあるように、`newosproc0`のような特定の状況下で、`readmemstats_m`が実行される前に`stats.StackSys`が既にゼロ以外の値を持っている可能性があったことです。これは、`newosproc0`によって割り当てられたスタックが、内部的には`memstats.stacks_sys`に計上され、それが`stats.StackSys`に初期コピーされるためです。

`stats.StackSys`がゼロでない状態で`stats.StackSys = stats.StackInuse`が実行されると、既存の`stats.StackSys`の値が上書きされてしまい、その結果、`Sys`の合計（`HeapSys + StackSys + ...`）が不正確になります。特に、`StackSys`に`StackInuse`が「加算」されるべきところで「代入」されてしまうため、以前に計上されていた`StackSys`の値が失われ、全体の`Sys`の合計が減少する可能性がありました。

修正は非常にシンプルですが、効果的です。`stats.StackSys = stats.StackInuse`を`stats.StackSys += stats.StackInuse`に変更することで、`StackSys`がゼロであるという仮定を排除し、既存の`StackSys`の値に`StackInuse`を正しく加算するようにしました。

これにより、`newosproc0`によって既に計上されているスタックメモリと、`readmemstats_m`がヒープから分離しようとしているスタックメモリの両方が、`MemStats.StackSys`に適切に反映されるようになります。結果として、`Sys`の合計値がシャッフル処理の前後で一貫性を保ち、メモリ統計の正確性が保証されます。

## コアとなるコードの解説

変更された行は以下の通りです。

**変更前:**
```go
stats.StackSys = stats.StackInuse
```
この行は、`MemStats`構造体の`StackSys`フィールドに、現在使用中のスタックメモリ量である`StackInuse`の値を「代入」していました。これは、`readmemstats_m`関数が実行される時点で`stats.StackSys`が常に`0`であるという前提に立っていました。もし`stats.StackSys`が既に`0`以外の値（例えば、`newosproc0`によって割り当てられたスタックメモリ）を持っていた場合、その既存の値は`StackInuse`によって上書きされてしまい、結果としてメモリ統計の合計値に不整合が生じていました。

**変更後:**
```go
stats.StackSys += stats.StackInuse
```
この行は、`MemStats`構造体の`StackSys`フィールドに、現在使用中のスタックメモリ量である`StackInuse`の値を「加算」しています。この変更により、`stats.StackSys`が`0`であるという前提が不要になります。`newosproc0`などによって既に`stats.StackSys`に値が計上されている場合でも、`StackInuse`がその既存の値に正しく追加されるため、スタックメモリの総計が正確に反映されるようになります。

この修正によって、`MemStats.Sys`（システムから取得した総メモリ量）が、その構成要素（`HeapSys`、`StackSys`など）の合計と常に一致するようになり、Goランタイムのメモリ統計の信頼性が向上しました。

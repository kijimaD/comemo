# [インデックス 20290] ファイルの概要

このコミットは、GoランタイムがSolarisシステムコールを呼び出す方法を改善することを目的としています。具体的には、Goコードから直接SysV呼び出し規約に従う関数を呼び出せるように、既存の`sysvicall6`関数を引数の数に応じた複数の`sysvicallN`関数（`sysvicall0`から`sysvicall6`まで）に分割し、Goで実装し直しています。これにより、システムコール呼び出しの柔軟性と効率が向上します。

## 変更の背景

Goランタイムは、オペレーティングシステム（OS）の機能を利用するためにシステムコールを呼び出す必要があります。特にSolarisのようなUNIX系システムでは、システムコールはSysV呼び出し規約（System V Application Binary Interface）に従って実装されています。Goランタイムは、これらのC言語で書かれたシステムコールを呼び出すためのメカニズムを持っていましたが、このコミット以前は、引数の数が異なるシステムコールに対して、汎用的な`sysvicall6`という単一のC関数を使用していました。

`sysvicall6`は、最大6つの引数を受け取り、引数の数を`count`パラメータで指定する形式でした。しかし、このアプローチにはいくつかの課題がありました。

1.  **柔軟性の欠如**: 引数の数が6つ未満のシステムコールを呼び出す場合でも、`sysvicall6`を使用する必要があり、余分な引数処理が発生する可能性がありました。
2.  **型安全性の欠如**: `uintptr`型で引数を渡すため、コンパイル時の型チェックが限定的でした。
3.  **Goからの直接呼び出しの制限**: C言語で実装された`sysvicall6`は、Goランタイムの内部で利用されていましたが、Goコードから直接、より自然な形でシステムコールを呼び出すための抽象化が不足していました。
4.  **最適化の機会**: 引数の数に応じた専用の関数を用意することで、より効率的なコード生成や最適化が可能になる可能性があります。

このコミットは、これらの課題を解決し、GoランタイムがSolarisシステムコールをより効率的かつGoらしい方法で呼び出せるようにするために行われました。特に、Goコードから直接SysV呼び出し規約の関数を呼び出せるようにすることで、ランタイムの可読性と保守性を向上させることを目指しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

### 1. Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理するGo言語の一部です。ガベージコレクション、スケジューリング、システムコールインターフェース、メモリ管理など、Goプログラムが動作するために必要な低レベルの機能を提供します。Goプログラムは、OSと直接対話するのではなく、ランタイムを介してOSのサービスを利用します。

### 2. システムコール (System Call)
システムコールは、ユーザー空間で実行されているプログラムが、カーネル空間で実行されているOSのサービスを要求するためのメカニズムです。ファイルI/O、ネットワーク通信、メモリ管理、プロセス管理など、OSが提供するほとんどの機能はシステムコールを介して利用されます。

### 3. SysV呼び出し規約 (System V Application Binary Interface - SysV ABI)
SysV ABIは、UNIX系システム（Linux、Solarisなど）で広く採用されている、関数呼び出しに関する標準的な規約です。これには、引数の渡し方（レジスタまたはスタック）、戻り値の扱い、スタックフレームのレイアウトなどが定義されています。GoランタイムがC言語で書かれたOSの関数を呼び出す際には、この規約に従う必要があります。

### 4. `asmcgocall`
`asmcgocall`はGoランタイム内部で使用される特殊なアセンブリ関数で、GoルーチンからCコード（またはアセンブリコード）を呼び出す際に使用されます。これは、GoのスタックとCのスタックの間で切り替えを行い、レジスタの状態を保存・復元する役割を担います。GoのスケジューラはGoルーチンを管理しますが、Cコードの実行中はGoのスケジューラから制御が外れるため、この切り替えが重要になります。

### 5. `go:nosplit`
`go:nosplit`はGoコンパイラに対する指示（プラグマ）で、その関数がスタックを拡張しないことを保証します。Go関数は通常、必要に応じてスタックを自動的に拡張しますが、`go:nosplit`が指定された関数は、スタック拡張のためのチェックを行いません。これは、非常に低レベルのランタイム関数や、スタック拡張が許されないコンテキスト（例えば、スタックの切り替え中など）で使用されます。

### 6. `libcFunc`
このコミットで導入された`libcFunc`は、`byte`型のエイリアスとして定義されていますが、これは主に型システムを介して、Cライブラリ関数へのポインタであることを示すためのマーカーとして機能します。`unsafe.Pointer`と組み合わせて、型安全性を損なわずにC関数ポインタを扱うためのGoの慣用的な方法です。

### 7. `uintptr`
`uintptr`は、ポインタを保持するのに十分な大きさの符号なし整数型です。Goでは、ポインタ演算は通常許可されていませんが、`unsafe`パッケージと`uintptr`を組み合わせることで、低レベルのメモリ操作や、C言語との相互運用が可能になります。システムコールへの引数や戻り値は、しばしば`uintptr`として扱われます。

### 8. `unsafe.Pointer`
`unsafe.Pointer`は、任意の型のポインタを保持できる特殊なポインタ型です。Goの型システムをバイパスして、異なる型のポインタ間で変換を行ったり、ポインタ演算を行ったりすることを可能にします。しかし、その名の通り「unsafe（安全でない）」であり、誤用するとメモリ破壊やクラッシュを引き起こす可能性があるため、慎重に使用する必要があります。

### 9. `getg().m.libcall`
Goランタイムでは、各Goルーチン（`g`）は、実行中のOSスレッド（`m`）に関連付けられています。`getg()`は現在のGoルーチンを取得し、`m`はそのGoルーチンが実行されているOSスレッドの構造体です。`libcall`は`m`構造体内のフィールドで、Cライブラリ関数を呼び出す際の引数、関数ポインタ、戻り値などを一時的に保持するために使用される構造体です。`asmcgocall`はこの`libcall`構造体を利用してC関数を呼び出します。

## 技術的詳細

このコミットの主要な変更点は、Solarisシステムコールを呼び出すためのメカニズムを、C言語で実装された単一の汎用関数`runtime·sysvicall6`から、Go言語で実装された引数の数に応じた複数の専用関数（`sysvicall0`から`sysvicall6`）に移行したことです。

**変更前のアプローチ (`runtime·sysvicall6` in C):**
変更前は、`src/pkg/runtime/os_solaris.c`に`runtime·sysvicall6`というC関数が存在しました。この関数は、呼び出すC関数のアドレス、引数の数、そして可変長引数として実際の引数を受け取りました。内部では、`g->m->libcall`構造体に必要な情報を設定し、`runtime·asmcgocall`を呼び出してCスタックに切り替え、実際のC関数を呼び出していました。

```c
// 変更前のos_solaris.cの一部 (削除されたコード)
uintptr
runtime·sysvicall6(uintptr fn, int32 count, ...)
{
    runtime·memclr((byte*)&g->m->scratch, sizeof(g->m->scratch));
    g->m->libcall.fn = (void*)fn;
    g->m->libcall.n = (uintptr)count;
    for(;count; count--)
        g->m->scratch.v[count - 1] = *((uintptr*)&count + count);
    g->m->libcall.args = (uintptr*)&g->m->scratch.v[0];
    runtime·asmcgocall(runtime·asmsysvicall6, &g->m->libcall);
    return g->m->libcall.r1;
}
```
このC関数は、可変長引数リストを処理するために、`g->m->scratch`という一時的なスクラッチ領域に引数をコピーしていました。これは、引数の数に関わらず常に同じパスを通るため、オーバーヘッドが発生する可能性がありました。

**変更後のアプローチ (Goで実装された`sysvicallN`関数群):**
このコミットでは、`runtime·sysvicall6`のC実装を削除し、代わりに`src/pkg/runtime/os_solaris.go`に`sysvicall0`から`sysvicall6`までのGo関数が新しく追加されました。これらの関数は、それぞれ0個から6個までの引数を直接受け取ります。

```go
// 新しく追加されたos_solaris.goの一部 (例: sysvicall3)
//go:nosplit
func sysvicall3(fn *libcFunc, a1, a2, a3 uintptr) uintptr {
	libcall := &getg().m.libcall
	libcall.fn = unsafe.Pointer(fn)
	libcall.n = 3
	libcall.args = noescape(unsafe.Pointer(&a1)) // 引数の先頭アドレスを渡す
	asmcgocall(unsafe.Pointer(&asmsysvicall6), unsafe.Pointer(libcall))
	return libcall.r1
}
```
各`sysvicallN`関数は、以下の共通のロジックを持っています。
1.  `getg().m.libcall`構造体へのポインタを取得します。
2.  呼び出すC関数のポインタを`libcall.fn`に設定します。
3.  引数の数を`libcall.n`に設定します（例: `sysvicall3`なら`3`）。
4.  最初の引数のアドレスを`libcall.args`に設定します。`noescape`は、このポインタがヒープにエスケープしないことをコンパイラに指示するためのGoの組み込み関数です。これにより、スタック上に確保された引数がGCの対象とならないようにします。
5.  `asmcgocall`を呼び出し、Cスタックに切り替えて実際のC関数を実行します。
6.  `libcall.r1`（戻り値）を返します。

**この変更の利点:**

*   **効率の向上**: 引数の数に応じて専用の関数が用意されたため、不要な引数処理や可変長引数リストの解析が不要になり、より直接的で効率的なシステムコール呼び出しが可能になりました。
*   **Goからの直接呼び出し**: Goコードから直接`sysvicallN`関数を呼び出せるようになり、ランタイムの他の部分からシステムコールを呼び出す際のコードが簡潔になりました。
*   **型安全性の改善**: `sysvicallN`関数は、引数を`uintptr`として受け取りますが、呼び出し側では引数の数が明確になり、より意図が伝わりやすくなりました。
*   **保守性の向上**: CとGoの境界をより明確にし、GoランタイムのGo部分でのシステムコール呼び出しのロジックを集中させることで、コードの保守性が向上します。
*   **`runtime.h`と`os_solaris.h`の変更**: Cヘッダーファイルから`runtime·sysvicall6`の宣言が削除され、Goヘッダーファイルに新しい`sysvicallN`関数の宣言が追加されました。これにより、インターフェースがより明確になりました。
*   **`netpoll_solaris.c`と`os_solaris.c`の変更**: これらのCファイル内の既存のシステムコール呼び出しが、新しい`sysvicallN`関数を使用するように更新されました。例えば、`runtime·fcntl`は`runtime·sysvicall6`から`runtime·sysvicall3`を呼び出すように変更されています。

このコミットは、GoランタイムのSolarisポートにおけるシステムコール呼び出しの基盤を強化し、将来的な改善のための道を開くものです。

## コアとなるコードの解説

### `src/pkg/runtime/os_solaris.c` からの `runtime·sysvicall6` の削除
この変更の最も重要な部分は、C言語で実装されていた汎用的な`runtime·sysvicall6`関数の削除です。この関数は、引数の数を`count`パラメータで受け取り、可変長引数として実際の引数を処理していました。この削除により、GoランタイムはC言語の可変長引数処理の複雑さから解放され、よりGoらしい方法でシステムコールを呼び出す基盤が作られました。

### `src/pkg/runtime/os_solaris.go` への `sysvicallN` 関数群の追加
削除されたC関数に代わり、Go言語で`sysvicall0`から`sysvicall6`までの関数が追加されました。これらの関数は、それぞれ対応する数の引数を直接受け取ります。

*   **`//go:nosplit`**: これらの関数には`//go:nosplit`プラグマが付与されています。これは、これらの関数が実行中にスタックを拡張しないことをコンパイラに保証するものです。システムコール呼び出しのような低レベルの操作では、スタックの切り替えやアセンブリコードとの連携があるため、スタック拡張による予期せぬ動作を避けるために重要です。
*   **`libcall := &getg().m.libcall`**: 各関数は、現在のGoルーチン（`g`）が実行されているOSスレッド（`m`）に関連付けられた`libcall`構造体へのポインタを取得します。この`libcall`構造体は、C関数を呼び出すためのコンテキスト（関数ポインタ、引数の数、引数へのポインタ、戻り値）を保持します。
*   **`libcall.fn = unsafe.Pointer(fn)`**: 呼び出すC関数のアドレスを`libcall.fn`に設定します。`unsafe.Pointer`を使用することで、`*libcFunc`型から汎用ポインタ型への変換を安全に行います。
*   **`libcall.n = N`**: `N`は引数の数を表します（例: `sysvicall3`では`3`）。これにより、`asmcgocall`が呼び出すC関数に渡される引数の数が明確になります。
*   **`libcall.args = noescape(unsafe.Pointer(&a1))`**: 最初の引数`a1`のアドレスを`libcall.args`に設定します。`noescape`は、`&a1`がヒープにエスケープしないことをコンパイラに指示します。これにより、スタック上に確保された引数がガベージコレクタによって誤って参照されることを防ぎます。`asmcgocall`は、この`libcall.args`が指すメモリ領域から引数を読み取り、C関数に渡します。
*   **`asmcgocall(unsafe.Pointer(&asmsysvicall6), unsafe.Pointer(libcall))`**: 実際のC関数呼び出しは、`asmcgocall`を介して行われます。`asmsysvicall6`は、GoとCのスタックを切り替え、`libcall`構造体から情報を読み取ってC関数を呼び出すアセンブリルーチンです。
*   **`return libcall.r1`**: C関数からの戻り値は`libcall.r1`に格納され、それがGo関数から返されます。

### `src/pkg/runtime/netpoll_solaris.c` および `src/pkg/runtime/os_solaris.c` の変更
これらのCファイルでは、既存のシステムコール呼び出しが、新しいGoで実装された`sysvicallN`関数を使用するように変更されました。例えば、`runtime·fcntl`は以前`runtime·sysvicall6(libc·fcntl, 3, ...)`を呼び出していましたが、変更後は`runtime·sysvicall3(libc·fcntl, ...)`を呼び出すようになっています。これにより、Cコード側での引数カウントの指定が不要になり、より簡潔な記述が可能になりました。

### `src/pkg/runtime/runtime.h` の `LibCall` 構造体の変更
`LibCall`構造体の`fn`フィールドの型が`void (*fn)(void*)`（関数ポインタ）から`void* fn`（汎用ポインタ）に変更されました。これは、Go側で`unsafe.Pointer`を使用して関数ポインタを扱うようになったため、C側でもより柔軟なポインタ型で受け取れるようにするための変更です。

これらの変更により、GoランタイムはSolarisシステムコールをより効率的かつGoのイディオムに沿った形で呼び出せるようになり、ランタイムの内部構造が改善されました。

## 変更の背景

Goランタイムは、オペレーティングシステム（OS）の機能を利用するためにシステムコールを呼び出す必要があります。特にSolarisのようなUNIX系システムでは、システムコールはSysV呼び出し規約（System V Application Binary Interface）に従って実装されています。Goランタイムは、これらのC言語で書かれたシステムコールを呼び出すためのメカニズムを持っていましたが、このコミット以前は、引数の数が異なるシステムコールに対して、汎用的な`sysvicall6`という単一のC関数を使用していました。

`sysvicall6`は、最大6つの引数を受け取り、引数の数を`count`パラメータで指定する形式でした。しかし、このアプローチにはいくつかの課題がありました。

1.  **柔軟性の欠如**: 引数の数が6つ未満のシステムコールを呼び出す場合でも、`sysvicall6`を使用する必要があり、余分な引数処理が発生する可能性がありました。
2.  **型安全性の欠如**: `uintptr`型で引数を渡すため、コンパイル時の型チェックが限定的でした。
3.  **Goからの直接呼び出しの制限**: C言語で実装された`sysvicall6`は、Goランタイムの内部で利用されていましたが、Goコードから直接、より自然な形でシステムコールを呼び出すための抽象化が不足していました。
4.  **最適化の機会**: 引数の数に応じた専用の関数を用意することで、より効率的なコード生成や最適化が可能になる可能性があります。

このコミットは、これらの課題を解決し、GoランタイムがSolarisシステムコールをより効率的かつGoらしい方法で呼び出せるようにするために行われました。特に、Goコードから直接SysV呼び出し規約の関数を呼び出せるようにすることで、ランタイムの可読性と保守性を向上させることを目指しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

### 1. Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理するGo言語の一部です。ガベージコレクション、スケジューリング、システムコールインターフェース、メモリ管理など、Goプログラムが動作するために必要な低レベルの機能を提供します。Goプログラムは、OSと直接対話するのではなく、ランタイムを介してOSのサービスを利用します。

### 2. システムコール (System Call)
システムコールは、ユーザー空間で実行されているプログラムが、カーネル空間で実行されているOSのサービスを要求するためのメカニズムです。ファイルI/O、ネットワーク通信、メモリ管理、プロセス管理など、OSが提供するほとんどの機能はシステムコールを介して利用されます。

### 3. SysV呼び出し規約 (System V Application Binary Interface - SysV ABI)
SysV ABIは、UNIX系システム（Linux、Solarisなど）で広く採用されている、関数呼び出しに関する標準的な規約です。これには、引数の渡し方（レジスタまたはスタック）、戻り値の扱い、スタックフレームのレイアウトなどが定義されています。GoランタイムがC言語で書かれたOSの関数を呼び出す際には、この規約に従う必要があります。

### 4. `asmcgocall`
`asmcgocall`はGoランタイム内部で使用される特殊なアセンブリ関数で、GoルーチンからCコード（またはアセンブリコード）を呼び出す際に使用されます。これは、GoのスタックとCのスタックの間で切り替えを行い、レジスタの状態を保存・復元する役割を担います。GoのスケジューラはGoルーチンを管理しますが、Cコードの実行中はGoのスケジューラから制御が外れるため、この切り替えが重要になります。

### 5. `go:nosplit`
`go:nosplit`はGoコンパイラに対する指示（プラグマ）で、その関数がスタックを拡張しないことを保証します。Go関数は通常、必要に応じてスタックを自動的に拡張しますが、`go:nosplit`が指定された関数は、スタック拡張のためのチェックを行いません。これは、非常に低レベルのランタイム関数や、スタック拡張が許されないコンテキスト（例えば、スタックの切り替え中など）で使用されます。

### 6. `libcFunc`
このコミットで導入された`libcFunc`は、`byte`型のエイリアスとして定義されていますが、これは主に型システムを介して、Cライブラリ関数へのポインタであることを示すためのマーカーとして機能します。`unsafe.Pointer`と組み合わせて、型安全性を損なわずにC関数ポインタを扱うためのGoの慣用的な方法です。

### 7. `uintptr`
`uintptr`は、ポインタを保持するのに十分な大きさの符号なし整数型です。Goでは、ポインタ演算は通常許可されていませんが、`unsafe`パッケージと`uintptr`を組み合わせることで、低レベルのメモリ操作や、C言語との相互運用が可能になります。システムコールへの引数や戻り値は、しばしば`uintptr`として扱われます。

### 8. `unsafe.Pointer`
`unsafe.Pointer`は、任意の型のポインタを保持できる特殊なポインタ型です。Goの型システムをバイパスして、異なる型のポインタ間で変換を行ったり、ポインタ演算を行ったりすることを可能にします。しかし、その名の通り「unsafe（安全でない）」であり、誤用するとメモリ破壊やクラッシュを引き起こす可能性があるため、慎重に使用する必要があります。

### 9. `getg().m.libcall`
Goランタイムでは、各Goルーチン（`g`）は、実行中のOSスレッド（`m`）に関連付けられています。`getg()`は現在のGoルーチンを取得し、`m`はそのGoルーチンが実行されているOSスレッドの構造体です。`libcall`は`m`構造体内のフィールドで、Cライブラリ関数を呼び出す際の引数、関数ポインタ、戻り値などを一時的に保持するために使用される構造体です。`asmcgocall`はこの`libcall`構造体を利用してC関数を呼び出します。

## 技術的詳細

このコミットの主要な変更点は、Solarisシステムコールを呼び出すためのメカニズムを、C言語で実装された単一の汎用関数`runtime·sysvicall6`から、Go言語で実装された引数の数に応じた複数の専用関数（`sysvicall0`から`sysvicall6`）に移行したことです。

**変更前のアプローチ (`runtime·sysvicall6` in C):**
変更前は、`src/pkg/runtime/os_solaris.c`に`runtime·sysvicall6`というC関数が存在しました。この関数は、呼び出すC関数のアドレス、引数の数、そして可変長引数として実際の引数を受け取りました。内部では、`g->m->libcall`構造体に必要な情報を設定し、`runtime·asmcgocall`を呼び出してCスタックに切り替え、実際のC関数を呼び出していました。

```c
// 変更前のos_solaris.cの一部 (削除されたコード)
uintptr
runtime·sysvicall6(uintptr fn, int32 count, ...)
{
    runtime·memclr((byte*)&g->m->scratch, sizeof(g->m->scratch));
    g->m->libcall.fn = (void*)fn;
    g->m->libcall.n = (uintptr)count;
    for(;count; count--)
        g->m->scratch.v[count - 1] = *((uintptr*)&count + count);
    g->m->libcall.args = (uintptr*)&g->m->scratch.v[0];
    runtime·asmcgocall(runtime·asmsysvicall6, &g->m->libcall);
    return g->m->libcall.r1;
}
```
このC関数は、可変長引数リストを処理するために、`g->m->scratch`という一時的なスクラッチ領域に引数をコピーしていました。これは、引数の数に関わらず常に同じパスを通るため、オーバーヘッドが発生する可能性がありました。

**変更後のアプローチ (Goで実装された`sysvicallN`関数群):**
このコミットでは、`runtime·sysvicall6`のC実装を削除し、代わりに`src/pkg/runtime/os_solaris.go`に`sysvicall0`から`sysvicall6`までのGo関数が新しく追加されました。これらの関数は、それぞれ0個から6個までの引数を直接受け取ります。

```go
// 新しく追加されたos_solaris.goの一部 (例: sysvicall3)
//go:nosplit
func sysvicall3(fn *libcFunc, a1, a2, a3 uintptr) uintptr {
	libcall := &getg().m.libcall
	libcall.fn = unsafe.Pointer(fn)
	libcall.n = 3
	libcall.args = noescape(unsafe.Pointer(&a1)) // 引数の先頭アドレスを渡す
	asmcgocall(unsafe.Pointer(&asmsysvicall6), unsafe.Pointer(libcall))
	return libcall.r1
}
```
各`sysvicallN`関数は、以下の共通のロジックを持っています。
1.  `getg().m.libcall`構造体へのポインタを取得します。
2.  呼び出すC関数のポインタを`libcall.fn`に設定します。
3.  引数の数を`libcall.n`に設定します（例: `sysvicall3`なら`3`）。
4.  最初の引数のアドレスを`libcall.args`に設定します。`noescape`は、このポインタがヒープにエスケープしないことをコンパイラに指示するためのGoの組み込み関数です。これにより、スタック上に確保された引数がGCの対象とならないようにします。
5.  `asmcgocall`を呼び出し、Cスタックに切り替えて実際のC関数を実行します。
6.  `libcall.r1`（戻り値）を返します。

**この変更の利点:**

*   **効率の向上**: 引数の数に応じて専用の関数が用意されたため、不要な引数処理や可変長引数リストの解析が不要になり、より直接的で効率的なシステムコール呼び出しが可能になりました。
*   **Goからの直接呼び出し**: Goコードから直接`sysvicallN`関数を呼び出せるようになり、ランタイムの他の部分からシステムコールを呼び出す際のコードが簡潔になりました。
*   **型安全性の改善**: `sysvicallN`関数は、引数を`uintptr`として受け取りますが、呼び出し側では引数の数が明確になり、より意図が伝わりやすくなりました。
*   **保守性の向上**: CとGoの境界をより明確にし、GoランタイムのGo部分でのシステムコール呼び出しのロジックを集中させることで、コードの保守性が向上します。
*   **`runtime.h`と`os_solaris.h`の変更**: Cヘッダーファイルから`runtime·sysvicall6`の宣言が削除され、Goヘッダーファイルに新しい`sysvicallN`関数の宣言が追加されました。これにより、インターフェースがより明確になりました。
*   **`netpoll_solaris.c`と`os_solaris.c`の変更**: これらのCファイル内の既存のシステムコール呼び出しが、新しい`sysvicallN`関数を使用するように更新されました。例えば、`runtime·fcntl`は`runtime·sysvicall6`から`runtime·sysvicall3`を呼び出すように変更されています。

このコミットは、GoランタイムのSolarisポートにおけるシステムコール呼び出しの基盤を強化し、将来的な改善のための道を開くものです。

## コアとなるコードの解説

### `src/pkg/runtime/os_solaris.c` からの `runtime·sysvicall6` の削除
この変更の最も重要な部分は、C言語で実装されていた汎用的な`runtime·sysvicall6`関数の削除です。この関数は、引数の数を`count`パラメータで受け取り、可変長引数として実際の引数を処理していました。この削除により、GoランタイムはC言語の可変長引数処理の複雑さから解放され、よりGoらしい方法でシステムコールを呼び出す基盤が作られました。

### `src/pkg/runtime/os_solaris.go` への `sysvicallN` 関数群の追加
削除されたC関数に代わり、Go言語で`sysvicall0`から`sysvicall6`までの関数が追加されました。これらの関数は、それぞれ対応する数の引数を直接受け取ります。

*   **`//go:nosplit`**: これらの関数には`//go:nosplit`プラグマが付与されています。これは、これらの関数が実行中にスタックを拡張しないことをコンパイラに保証するものです。システムコール呼び出しのような低レベルの操作では、スタックの切り替えやアセンブリコードとの連携があるため、スタック拡張による予期せぬ動作を避けるために重要です。
*   **`libcall := &getg().m.libcall`**: 各関数は、現在のGoルーチン（`g`）が実行されているOSスレッド（`m`）に関連付けられた`libcall`構造体へのポインタを取得します。この`libcall`構造体は、C関数を呼び出すためのコンテキスト（関数ポインタ、引数の数、引数へのポインタ、戻り値）を保持します。
*   **`libcall.fn = unsafe.Pointer(fn)`**: 呼び出すC関数のアドレスを`libcall.fn`に設定します。`unsafe.Pointer`を使用することで、`*libcFunc`型から汎用ポインタ型への変換を安全に行います。
*   **`libcall.n = N`**: `N`は引数の数を表します（例: `sysvicall3`では`3`）。これにより、`asmcgocall`が呼び出すC関数に渡される引数の数が明確になります。
*   **`libcall.args = noescape(unsafe.Pointer(&a1))`**: 最初の引数`a1`のアドレスを`libcall.args`に設定します。`noescape`は、`&a1`がヒープにエスケープしないことをコンパイラに指示します。これにより、スタック上に確保された引数がガベージコレクタによって誤って参照されることを防ぎます。`asmcgocall`は、この`libcall.args`が指すメモリ領域から引数を読み取り、C関数に渡します。
*   **`asmcgocall(unsafe.Pointer(&asmsysvicall6), unsafe.Pointer(libcall))`**: 実際のC関数呼び出しは、`asmcgocall`を介して行われます。`asmsysvicall6`は、GoとCのスタックを切り替え、`libcall`構造体から情報を読み取ってC関数を呼び出すアセンブリルーチンです。
*   **`return libcall.r1`**: C関数からの戻り値は`libcall.r1`に格納され、それがGo関数から返されます。

### `src/pkg/runtime/netpoll_solaris.c` および `src/pkg/runtime/os_solaris.c` の変更
これらのCファイルでは、既存のシステムコール呼び出しが、新しいGoで実装された`sysvicallN`関数を使用するように変更されました。例えば、`runtime·fcntl`は以前`runtime·sysvicall6(libc·fcntl, 3, ...)`を呼び出していましたが、変更後は`runtime·sysvicall3(libc·fcntl, ...)`を呼び出すようになっています。これにより、Cコード側での引数カウントの指定が不要になり、より簡潔な記述が可能になりました。

### `src/pkg/runtime/runtime.h` の `LibCall` 構造体の変更
`LibCall`構造体の`fn`フィールドの型が`void (*fn)(void*)`（関数ポインタ）から`void* fn`（汎用ポインタ）に変更されました。これは、Go側で`unsafe.Pointer`を使用して関数ポインタを扱うようになったため、C側でもより柔軟なポインタ型で受け取れるようにするための変更です。

これらの変更により、GoランタイムはSolarisシステムコールをより効率的かつGoのイディオムに沿った形で呼び出せるようになり、ランタイムの内部構造が改善されました。

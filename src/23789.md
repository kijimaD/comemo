## 元コミット内容

このコミットは、GoコンパイラのSSAバックエンドにおいて、ブロックの制御値がスケジューリングパスによってブロックの末尾以外の場所に移動されてしまう問題を修正します。この問題は、制御値と他の値の間に明確な値の依存関係がない場合に発生していました。修正は、PHI関数と同様に制御値を特別に扱うことで実現されています。

## 変更の背景

Goコンパイラは、最適化のためにプログラムをSSA形式に変換します。SSA形式では、各変数は一度だけ代入されるという特性を持ちます。SSAバックエンドの重要なフェーズの一つに「スケジューリング」があります。スケジューリングは、SSA形式で表現された命令（値）の実行順序を決定するプロセスです。このプロセスは、レジスタ割り当ての効率化やパイプラインの最適化など、生成される機械語コードの性能に大きく影響します。

特定のブロック（基本的な実行単位）には、「制御値（control value）」と呼ばれる特殊な値が存在します。これは、そのブロックの実行フローを決定する条件分岐やループの終了条件などに関連する値です。例えば、`if`文の条件式の結果や、ループの継続条件などがこれに該当します。これらの制御値は、通常、ブロックの実行の最後に評価され、次のブロックへの遷移を決定します。

しかし、スケジューリングパスにおいて、制御値とブロック内の他の値との間に明示的なデータ依存関係がない場合、最適化アルゴリズムが制御値をブロックの末尾（EOB: End Of Block）以外の場所に移動させてしまう可能性がありました。制御値がEOBにない場合、そのブロックの実行フローが正しく決定されず、コンパイルされたプログラムの動作が不正になる可能性があります。このコミットは、この潜在的なバグを修正することを目的としています。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの最適化で広く用いられる中間表現です。この形式では、プログラム中の各変数への代入が一度だけ行われるように変換されます。これにより、データフロー解析が容易になり、様々な最適化（例: 共通部分式除去、定数伝播、デッドコード除去）を効率的に適用できます。

例:
```go
x = 1
x = x + 2
y = x * 3
```
SSA形式では、`x`への2回目の代入は新しい変数として扱われます。
```
x1 = 1
x2 = x1 + 2
y1 = x2 * 3
```

### 2. PHI関数 (Φ関数)

SSA形式において、複数の制御フローパスが合流する点（例: `if-else`文の合流点やループの先頭）で、異なるパスで代入された同じ論理的な変数の値を結合するために使用される特殊な関数です。PHI関数は、そのブロックの先頭で実行されると見なされます。

例:
```go
if cond {
    x = 1
} else {
    x = 2
}
y = x + 3
```
SSA形式では、`if-else`の合流点でPHI関数が導入されます。
```
if cond {
    x1 = 1
} else {
    x2 = 2
}
x3 = Φ(x1, x2) // x3はx1またはx2のいずれか
y1 = x3 + 3
```

### 3. スケジューリングパス

コンパイラのバックエンドにおける最適化フェーズの一つで、SSA形式の命令（値）の実行順序を決定します。目的は、レジスタの利用効率を最大化したり、プロセッサのパイプラインを最適化したりして、生成される機械語コードの性能を向上させることです。命令の順序は、データ依存関係（ある命令の結果が別の命令の入力となる関係）と制御依存関係（ある命令の実行が別の命令の実行を決定する関係）に基づいて決定されます。

### 4. 制御値 (Control Value)

SSA形式のブロックにおいて、そのブロックの実行フローを決定する役割を持つ値です。例えば、条件分岐（`if`文）の条件式の結果や、ループの終了条件などがこれに該当します。これらの値は、ブロックの最後に評価され、次にどのブロックへ遷移するかを決定するために使用されます。

### 5. データ依存関係

ある命令の出力が別の命令の入力として使用される場合、それらの命令間にはデータ依存関係があります。スケジューリングでは、データ依存関係が満たされるように命令の順序を決定する必要があります。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/ssa/schedule.go` ファイル内の `schedule` 関数を変更しています。この関数は、各ブロック内のSSA値の実行順序を決定するスケジューリングアルゴリズムを実装しています。

問題の核心は、スケジューリングアルゴリズムが、ブロックの制御値（`b.Control`）を、そのブロックの末尾（EOB）以外の場所に移動させてしまう可能性があったことです。これは、制御値とブロック内の他の値との間に明示的なデータ依存関係がない場合に発生しやすかったと考えられます。制御値はブロックの実行フローを決定するため、その評価はブロックの最後に位置すべきです。

コミットの修正は、PHI関数が特別に扱われるのと同様に、制御値も特別に扱うことでこの問題を解決しています。PHI関数は、その性質上、常にブロックの先頭に配置される必要があります。このコミットでは、制御値をPHI関数に似た方法で扱い、スケジューリングの対象から一時的に除外し、最後に明示的にブロックの末尾に追加することで、その位置を保護しています。

具体的には、以下の変更が行われています。

1.  **制御値の初期スキップ**: ブロック内の値をトポロジカルソートする際に、`b.Control` が見つかった場合、一時的にスキップして `order` リストに追加しないようにします。
2.  **依存関係グラフからの除外**: 依存関係を探索する際に、`b.Control` への依存関係を考慮しないようにします。これにより、制御値が他の値の依存関係によって誤って早期にスケジューリングされることを防ぎます。
3.  **制御値の最終追加**: ブロック内のすべての値がスケジューリングされた後、`b.Control` が存在する場合は、明示的に `order` リストの末尾に追加します。これにより、制御値が常にブロックの最後に配置されることが保証されます。

このアプローチにより、制御値は他の通常のSSA値とは異なるライフサイクルで扱われ、その評価タイミングがブロックの実行フローのセマンティクスと一致するように強制されます。

問題の核心は、スケジューリングアルゴリズムが、ブロックの制御値（`b.Control`）を、そのブロックの末尾（EOB）以外の場所に移動させてしまう可能性があったことです。これは、制御値とブロック内の他の値との間に明示的なデータ依存関係がない場合に発生しやすかったと考えられます。制御値はブロックの実行フローを決定するため、その評価はブロックの最後に位置すべきです。

コミットの修正は、PHI関数が特別に扱われるのと同様に、制御値も特別に扱うことでこの問題を解決しています。PHI関数は、その性質上、常にブロックの先頭に配置される必要があります。このコミットでは、制御値をPHI関数に似た方法で扱い、スケジューリングの対象から一時的に除外し、最後に明示的にブロックの末尾に追加することで、その位置を保護しています。

具体的には、以下の変更が行われています。

1.  **制御値の初期スキップ**: ブロック内の値をトポロジカルソートする際に、`b.Control` が見つかった場合、一時的にスキップして `order` リストに追加しないようにします。
2.  **依存関係グラフからの除外**: 依存関係を探索する際に、`b.Control` への依存関係を考慮しないようにします。これにより、制御値が他の値の依存関係によって誤って早期にスケジューリングされることを防ぎます。
3.  **制御値の最終追加**: ブロック内のすべての値がスケジューリングされた後、`b.Control` が存在する場合は、明示的に `order` リストの末尾に追加します。これにより、制御値が常にブロックの最後に配置されることが保証されます。

このアプローチにより、制御値は他の通常のSSA値とは異なるライフサイクルで扱われ、その評価タイミングがブロックの実行フローのセマンティクスと一致するように強制されます。

## コアとなるコードの解説

変更は `schedule` 関数内で行われています。この関数は、各基本ブロック `b` に対して、その中のSSA値 `v` の実行順序を決定します。

1.  **制御値の初期スキップ**:
    ```go
    		for _, v := range b.Values {
    			if v == b.Control {
    				continue
    			}
    ```
    `b.Values` はブロック内のすべてのSSA値のリストです。このループはこれらの値を順に処理し、トポロジカルソートされた `order` リストを構築します。ここで、もし現在の値 `v` がブロックの制御値 `b.Control` と同じであれば、`continue` してこの値の処理をスキップします。これにより、制御値は通常のスケジューリングプロセスから一時的に除外されます。

2.  **依存関係グラフからの除外**:
    ```go
    					for _, w := range v.Args {
    -						if w.Block == b && w.Op != OpPhi && state[w.ID] == unmarked {
    +						if w.Block == b && w.Op != OpPhi && w != b.Control && state[w.ID] == unmarked {
    							state[w.ID] = found
    							queue = append(queue, w)
    						}
    					}
    					for _, w := range additionalEdges[v.ID] {
    -						if w.Block == b && w.Op != OpPhi && state[w.ID] == unmarked {
    +						if w.Block == b && w.Op != OpPhi && w != b.Control && state[w.ID] == unmarked {
    							state[w.ID] = found
    							queue = append(queue, w)
    						}
    ```
    この部分は、値 `v` の引数（`v.Args`）や追加のエッジ（`additionalEdges`）を探索し、依存関係のある他の値 `w` をキューに追加して処理するためのものです。修正前は `w.Op != OpPhi` という条件でPHI関数を除外していましたが、修正後は `w != b.Control` という条件が追加されています。これにより、制御値 `b.Control` も依存関係の探索から除外され、他の値が制御値に依存していると誤って解釈されることを防ぎます。これは、制御値がブロックの最後に配置されるべきであり、他の値のスケジューリングに影響を与えるべきではないという原則を強化します。

3.  **制御値の最終追加**:
    ```go
    		if b.Control != nil {
    			order = append(order, b.Control)
    		}
    		copy(b.Values, order)
    ```
    ブロック内のすべての通常のSSA値とPHI関数が `order` リストにトポロジカルソートされた後、このコードが実行されます。もしブロックに制御値 `b.Control` が存在する場合（`nil` でない場合）、その制御値を `order` リストの末尾に明示的に追加します。これにより、制御値は常にブロックの最後に配置されることが保証され、ブロックの実行フローを正しく決定する役割を果たすことができます。最後に、構築された `order` リストが `b.Values` にコピーされ、ブロック内の値の新しい順序が設定されます。

これらの変更により、GoコンパイラのSSAバックエンドは、制御値のセマンティクスを正しく維持し、より堅牢なコード生成を実現します。

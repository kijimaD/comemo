# [インデックス 27785] ファイルの概要

このコミットは、Goコンパイラの共通部分式除去（CSE: Common Subexpression Elimination）最適化において、`runtime.newobject`関数の呼び出し結果が常に新しいオブジェクトを返すという特性を考慮に入れるように変更を加えるものです。これにより、特にポインタを含む大規模な静的データ構造のコンパイル時間が大幅に改善されました。

## 変更の背景

このコミットの背景には、Goコンパイラが大規模な静的データ構造、特にポインタを含むマップやスライスをコンパイルする際の性能問題がありました。具体的には、GoコンパイラのSSA（Static Single Assignment）バックエンドで行われる共通部分式除去（CSE）最適化が、`runtime.newobject`の呼び出し結果を不適切に共通部分式として扱ってしまうことが原因でした。

`runtime.newobject`は、Goランタイムが新しいオブジェクトをヒープに割り当てるために使用する内部関数です。この関数の重要な特性は、呼び出されるたびに必ず新しい、ユニークなメモリ領域へのポインタを返すという点です。しかし、従来のCSEは、この特性を認識せず、同じ引数で複数回呼び出された`runtime.newobject`を共通部分式と誤認し、冗長な計算を排除しようと試みていました。

この誤った最適化は、実際には異なるメモリ位置を指すポインタを同じものとして扱ってしまうため、コンパイル時に不必要な複雑さや処理のオーバーヘッドを引き起こしていました。特に、Issue #15112（大規模な静的データ構造のコンパイルが遅い）やIssue #15235（ポインタを含む大規模な静的データ構造のコンパイルが遅い）で報告されたように、大量のポインタを含むデータ構造を初期化する際に、この問題が顕著なコンパイル時間の増加を招いていました。

このコミットは、`runtime.newobject`の呼び出し結果が常にユニークであることをCSEに「教える」ことで、この問題を解決し、コンパイル時間を大幅に短縮することを目的としています。コミットメッセージに示されているベンチマーク結果は、特にIssue #15235のケースでコンパイル時間が約80%削減されるなど、劇的な改善を示しています。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを中間表現に変換し、その中間表現に対して様々な最適化を適用します。その最適化フェーズの一つに、SSA（Static Single Assignment）形式を用いた最適化があります。SSA形式とは、プログラム中の各変数が一度だけ代入されるように変換された表現です。これにより、データフロー解析が容易になり、コンパイラはより効果的な最適化（例えば、共通部分式除去、デッドコード除去、レジスタ割り当てなど）を実行できるようになります。Goコンパイラのバックエンドは、このSSA形式を利用してコード生成と最適化を行います。

### 共通部分式除去 (CSE: Common Subexpression Elimination)

共通部分式除去（CSE）は、コンパイラ最適化の一種で、プログラム内で複数回計算される同じ式（共通部分式）を一度だけ計算し、その結果を再利用することで、冗長な計算を排除し、実行速度を向上させることを目的とします。

例えば、`a = (b + c) * d` と `e = (b + c) * f` というコードがあった場合、`(b + c)` は共通部分式です。CSEはこれを一度だけ計算し、その結果を一時変数に格納し、両方の式でその一時変数を利用するように変換します。

しかし、CSEが正しく機能するためには、「同じ式が常に同じ結果を返す」という前提が重要です。副作用を持つ関数呼び出しや、呼び出しごとに異なる結果を返す関数（例えば、乱数生成関数やメモリ割り当て関数）の場合、単純なCSEを適用するとプログラムの動作が変わってしまう可能性があります。

### `runtime.newobject`

`runtime.newobject`は、Goランタイム内部で使用される関数で、新しいオブジェクトをヒープに割り当てる役割を担います。Go言語で`new(T)`式や複合リテラル（例: `&T{...}`）を使って新しい値をヒープに割り当てる場合、最終的にはこの`runtime.newobject`のようなランタイム関数が呼び出されます。

この関数の最も重要な特性は、**呼び出されるたびに、必ず新しい、ユニークなメモリ領域を確保し、そのアドレス（ポインタ）を返す**という点です。つまり、`runtime.newobject`を複数回呼び出しても、それらの呼び出しが返すポインタは決して同じメモリ位置を指すことはありません。これは、Goのメモリモデルとガベージコレクションの動作において非常に重要な保証です。

### Goのポインタとメモリモデル

Go言語では、ポインタはメモリ上の特定のアドレスを指します。`newobject`が常に新しいメモリを返すという事実は、Goの型システムとメモリ安全性において不可欠です。もし`newobject`が既存のメモリを再利用して同じポインタを返してしまうと、異なる変数やデータ構造が意図せず同じメモリを共有することになり、データ破壊や予測不能な動作を引き起こす可能性があります。したがって、`newobject`の呼び出し結果は、常に「ユニークな値」として扱われる必要があります。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおけるCSEが、`runtime.newobject`の呼び出し結果を「共通部分式ではない」と正しく認識するように修正することです。

従来のCSEは、オペレーションの種類と引数に基づいて値の等価性を判断していました。`runtime.newobject`の呼び出しは、同じ型を引数として受け取った場合、CSEはそれらを同じ「式」と見なし、その結果が共通であると誤って判断する可能性がありました。しかし、前述の通り、`runtime.newobject`は常に新しいメモリを割り当てるため、その呼び出し結果は決して共通ではありません。

この問題を解決するために、以下の技術的変更が導入されました。

1.  **`gc.Sym.IsRuntimeCall` メソッドの追加**:
    `src/cmd/compile/internal/gc/subr.go` に `IsRuntimeCall(name string) bool` メソッドが追加されました。このメソッドは、与えられたシンボルが特定のランタイム関数（例: "newobject"）への呼び出しであるかどうかを判定します。これにより、コンパイラの異なる部分がランタイム関数呼び出しを識別できるようになります。

2.  **`ssa.GCSym` インターフェースの導入**:
    `src/cmd/compile/internal/ssa/config.go` に `GCSym` インターフェースが定義されました。このインターフェースは、`gc.Sym` 型が実装する `IsRuntimeCall` メソッドを抽象化します。これにより、`ssa` パッケージが `gc` パッケージに直接依存することなく、シンボルのランタイム呼び出し特性をチェックできるようになり、パッケージ間の循環依存を防ぎます。

3.  **CSEにおける`newobject`の特別扱い**:
    `src/cmd/compile/internal/ssa/cse.go` の `cmpVal` 関数が修正されました。`cmpVal`は、2つのSSA値が等しいかどうかを比較する関数で、CSEが共通部分式を識別するために使用します。
    変更点では、`v.Op` が `OpStaticCall` (または特定のアーキテクチャ固有の静的呼び出しオペレーション) である場合に、その呼び出しが `runtime.newobject` であるかどうかをチェックします。
    具体的には、`v.Aux` (オペレーションの補助情報、この場合は呼び出される関数のシンボル) を `GCSym` インターフェースとしてキャストし、`IsRuntimeCall("newobject")` を呼び出します。
    もしそれが `runtime.newobject` への呼び出しであれば、その値は他のいかなる値とも共通部分式ではないと判断されます。この場合、`v.ID < w.ID` に基づいて比較結果を返すことで、`newobject`の呼び出し結果が常にユニークな値として扱われるようにします。これにより、CSEは`runtime.newobject`の呼び出しを最適化の対象から除外し、誤った共通部分式除去を防ぎます。

この修正により、コンパイラは`runtime.newobject`のセマンティクスを正しく理解し、不必要な比較や最適化の試みを回避できるようになりました。結果として、特にポインタを多用する大規模なデータ構造のコンパイルにおいて、コンパイル時間の劇的な短縮が実現されました。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/subr.go` の変更

`*Sym` 型に `IsRuntimeCall` メソッドが追加されました。
`Sym` はコンパイラがシンボル（変数名、関数名など）を表現するために使用する構造体です。
このメソッドは、レシーバである `Sym` が `Runtimepkg` パッケージに属し、かつその名前が引数 `name` と一致する場合に `true` を返します。
これにより、特定のシンボルがGoランタイムの特定の関数（この場合は `newobject`）を表しているかどうかを効率的に判定できるようになります。

### `src/cmd/compile/internal/ssa/config.go` の変更

`GCSym` という新しいインターフェースが定義されました。
このインターフェースは、`IsRuntimeCall(name string) bool` という単一のメソッドを要求します。
このインターフェースの導入は、`ssa` パッケージが `gc` パッケージの具体的な型（`*gc.Sym`）に直接依存するのを避けるためのものです。Goコンパイラの設計では、パッケージ間の循環依存を避けることが重要であり、インターフェースはそのための一般的なパターンです。
`*gc.Sym` はこの `GCSym` インターフェースを暗黙的に実装するため、`ssa` パッケージは `gc` パッケージのシンボルを `GCSym` として扱うことができます。

### `src/cmd/compile/internal/ssa/cse.go` の変更

`cmpVal` 関数は、SSA値 `v` と `w` が等しいかどうかを比較し、共通部分式除去の判断基準となるものです。
追加された `switch` ステートメントは、`v.Op` が静的関数呼び出し（`OpStaticCall` や特定のアーキテクチャ固有の静的呼び出し）である場合に特別な処理を行います。
1.  `sym := v.Aux.(GCSym)`: 呼び出される関数のシンボル情報が `v.Aux` に格納されており、これを `GCSym` インターフェースとして型アサートします。
2.  `if sym.IsRuntimeCall("newobject")`: 取得したシンボルが `runtime.newobject` であるかどうかを `IsRuntimeCall` メソッドを使ってチェックします。
3.  `return lt2Cmp(v.ID < w.ID)`: もし `v` が `runtime.newobject` への呼び出しであれば、その結果は他のいかなる値とも共通部分式ではないと判断されます。この場合、`v.ID < w.ID` に基づいて比較結果を返します。これは、`newobject`の呼び出し結果が常にユニークな値として扱われるようにするための慣例的な方法です。これにより、CSEは`runtime.newobject`の呼び出しを共通部分式として扱わず、常に新しい値が生成されるものとして処理します。

これらの変更により、GoコンパイラのSSAバックエンドは、`runtime.newobject`の特殊なセマンティクスを正しく理解し、大規模なデータ構造のコンパイル時に発生していた不必要な最適化の試みとそれに伴う性能劣化を回避できるようになりました。

## 変更の背景

このコミットの背景には、Goコンパイラが大規模な静的データ構造、特にポインタを含むマップやスライスをコンパイルする際の性能問題がありました。具体的には、GoコンパイラのSSA（Static Single Assignment）バックエンドで行われる共通部分式除去（CSE）最適化が、`runtime.newobject`の呼び出し結果を不適切に共通部分式として扱ってしまうことが原因でした。

`runtime.newobject`は、Goランタイムが新しいオブジェクトをヒープに割り当てるために使用する内部関数です。この関数の重要な特性は、呼び出されるたびに必ず新しい、ユニークなメモリ領域へのポインタを返すという点です。しかし、従来のCSEは、この特性を認識せず、同じ引数で複数回呼び出された`runtime.newobject`を共通部分式と誤認し、冗長な計算を排除しようと試みていました。

この誤った最適化は、実際には異なるメモリ位置を指すポインタを同じものとして扱ってしまうため、コンパイル時に不必要な複雑さや処理のオーバーヘッドを引き起こしていました。特に、Issue #15112（大規模な静的データ構造のコンパイルが遅い）やIssue #15235（ポインタを含む大規模な静的データ構造のコンパイルが遅い）で報告されたように、大量のポインタを含むデータ構造を初期化する際に、この問題が顕著なコンパイル時間の増加を招いていました。

このコミットは、`runtime.newobject`の呼び出し結果が常にユニークであることをCSEに「教える」ことで、この問題を解決し、コンパイル時間を大幅に短縮することを目的としています。コミットメッセージに示されているベンチマーク結果は、特にIssue #15235のケースでコンパイル時間が約80%削減されるなど、劇的な改善を示しています。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを中間表現に変換し、その中間表現に対して様々な最適化を適用します。その最適化フェーズの一つに、SSA（Static Single Assignment）形式を用いた最適化があります。SSA形式とは、プログラム中の各変数が一度だけ代入されるように変換された表現です。これにより、データフロー解析が容易になり、コンパイラはより効果的な最適化（例えば、共通部分式除去、デッドコード除去、レジスタ割り当てなど）を実行できるようになります。Goコンパイラのバックエンドは、このSSA形式を利用してコード生成と最適化を行います。

### 共通部分式除去 (CSE: Common Subexpression Elimination)

共通部分式除去（CSE）は、コンパイラ最適化の一種で、プログラム内で複数回計算される同じ式（共通部分式）を一度だけ計算し、その結果を再利用することで、冗長な計算を排除し、実行速度を向上させることを目的とします。

例えば、`a = (b + c) * d` と `e = (b + c) * f` というコードがあった場合、`(b + c)` は共通部分式です。CSEはこれを一度だけ計算し、その結果を一時変数に格納し、両方の式でその一時変数を利用するように変換します。

しかし、CSEが正しく機能するためには、「同じ式が常に同じ結果を返す」という前提が重要です。副作用を持つ関数呼び出しや、呼び出しごとに異なる結果を返す関数（例えば、乱数生成関数やメモリ割り当て関数）の場合、単純なCSEを適用するとプログラムの動作が変わってしまう可能性があります。

### `runtime.newobject`

`runtime.newobject`は、Goランタイム内部で使用される関数で、新しいオブジェクトをヒープに割り当てる役割を担います。Go言語で`new(T)`式や複合リテラル（例: `&T{...}`）を使って新しい値をヒープに割り当てる場合、最終的にはこの`runtime.newobject`のようなランタイム関数が呼び出されます。

この関数の最も重要な特性は、**呼び出されるたびに、必ず新しい、ユニークなメモリ領域を確保し、そのアドレス（ポインタ）を返す**という点です。つまり、`runtime.newobject`を複数回呼び出しても、それらの呼び出しが返すポインタは決して同じメモリ位置を指すことはありません。これは、Goのメモリモデルとガベージコレクションの動作において非常に重要な保証です。

### Goのポインタとメモリモデル

Go言語では、ポインタはメモリ上の特定のアドレスを指します。`newobject`が常に新しいメモリを返すという事実は、Goの型システムとメモリ安全性において不可欠です。もし`newobject`が既存のメモリを再利用して同じポインタを返してしまうと、異なる変数やデータ構造が意図せず同じメモリを共有することになり、データ破壊や予測不能な動作を引き起こす可能性があります。したがって、`newobject`の呼び出し結果は、常に「ユニークな値」として扱われる必要があります。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおけるCSEが、`runtime.newobject`の呼び出し結果を「共通部分式ではない」と正しく認識するように修正することです。

従来のCSEは、オペレーションの種類と引数に基づいて値の等価性を判断していました。`runtime.newobject`の呼び出しは、同じ型を引数として受け取った場合、CSEはそれらを同じ「式」と見なし、その結果が共通であると誤って判断する可能性がありました。しかし、前述の通り、`runtime.newobject`は常に新しいメモリを割り当てるため、その呼び出し結果は決して共通ではありません。

この問題を解決するために、以下の技術的変更が導入されました。

1.  **`gc.Sym.IsRuntimeCall` メソッドの追加**:
    `src/cmd/compile/internal/gc/subr.go` に `IsRuntimeCall(name string) bool` メソッドが追加されました。このメソッドは、与えられたシンボルが特定のランタイム関数（例: "newobject"）への呼び出しであるかどうかを判定します。これにより、コンパイラの異なる部分がランタイム関数呼び出しを識別できるようになります。

2.  **`ssa.GCSym` インターフェースの導入**:
    `src/cmd/compile/internal/ssa/config.go` に `GCSym` インターフェースが定義されました。このインターフェースは、`IsRuntimeCall(name string) bool` という単一のメソッドを要求します。
    このインターフェースの導入は、`ssa` パッケージが `gc` パッケージの具体的な型（`*gc.Sym`）に直接依存するのを避けるためのものです。Goコンパイラの設計では、パッケージ間の循環依存を避けることが重要であり、インターフェースはそのための一般的なパターンです。
    `*gc.Sym` はこの `GCSym` インターフェースを暗黙的に実装するため、`ssa` パッケージは `gc` パッケージのシンボルを `GCSym` として扱うことができます。

3.  **CSEにおける`newobject`の特別扱い**:
    `src/cmd/compile/internal/ssa/cse.go` の `cmpVal` 関数が修正されました。`cmpVal`は、2つのSSA値が等しいかどうかを比較する関数で、CSEが共通部分式を識別するために使用します。
    変更点では、`v.Op` が `OpStaticCall` (または特定のアーキテクチャ固有の静的呼び出しオペレーション) である場合に、その呼び出しが `runtime.newobject` であるかどうかをチェックします。
    具体的には、`v.Aux` (オペレーションの補助情報、この場合は呼び出される関数のシンボル) を `GCSym` インターフェースとしてキャストし、`IsRuntimeCall("newobject")` を呼び出します。
    もしそれが `runtime.newobject` への呼び出しであれば、その値は他のいかなる値とも共通部分式ではないと判断されます。この場合、`v.ID < w.ID` に基づいて比較結果を返すことで、`newobject`の呼び出し結果が常にユニークな値として扱われるようにします。これにより、CSEは`runtime.newobject`の呼び出しを最適化の対象から除外し、誤った共通部分式除去を防ぎます。

この修正により、コンパイラは`runtime.newobject`のセマンティクスを正しく理解し、不必要な比較や最適化の試みとそれに伴う性能劣化を回避できるようになりました。結果として、特にポインタを多用する大規模なデータ構造のコンパイルにおいて、コンパイル時間の劇的な短縮が実現されました。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/subr.go` の変更

`*Sym` 型に `IsRuntimeCall` メソッドが追加されました。
`Sym` はコンパイラがシンボル（変数名、関数名など）を表現するために使用する構造体です。
このメソッドは、レシーバである `Sym` が `Runtimepkg` パッケージに属し、かつその名前が引数 `name` と一致する場合に `true` を返します。
これにより、特定のシンボルがGoランタイムの特定の関数（この場合は `newobject`）を表しているかどうかを効率的に判定できるようになります。

### `src/cmd/compile/internal/ssa/config.go` の変更

`GCSym` という新しいインターフェースが定義されました。
このインターフェースは、`IsRuntimeCall(name string) bool` という単一のメソッドを要求します。
このインターフェースの導入は、`ssa` パッケージが `gc` パッケージの具体的な型（`*gc.Sym`）に直接依存するのを避けるためのものです。Goコンパイラの設計では、パッケージ間の循環依存を避けることが重要であり、インターフェースはそのための一般的なパターンです。
`*gc.Sym` はこの `GCSym` インターフェースを暗黙的に実装するため、`ssa` パッケージは `gc` パッケージのシンボルを `GCSym` として扱うことができます。

### `src/cmd/compile/internal/ssa/cse.go` の変更

`cmpVal` 関数は、SSA値 `v` と `w` が等しいかどうかを比較し、共通部分式除去の判断基準となるものです。
追加された `switch` ステートメントは、`v.Op` が静的関数呼び出し（`OpStaticCall` や特定のアーキテクチャ固有の静的呼び出し）である場合に特別な処理を行います。
1.  `sym := v.Aux.(GCSym)`: 呼び出される関数のシンボル情報が `v.Aux` に格納されており、これを `GCSym` インターフェースとして型アサートします。
2.  `if sym.IsRuntimeCall("newobject")`: 取得したシンボルが `runtime.newobject` であるかどうかを `IsRuntimeCall` メソッドを使ってチェックします。
3.  `return lt2Cmp(v.ID < w.ID)`: もし `v` が `runtime.newobject` への呼び出しであれば、その結果は他のいかなる値とも共通部分式ではないと判断されます。この場合、`v.ID < w.ID` に基づいて比較結果を返します。これは、`newobject`の呼び出し結果が常にユニークな値として扱われるようにするための慣例的な方法です。これにより、CSEは`runtime.newobject`の呼び出しを共通部分式として扱わず、常に新しい値が生成されるものとして処理します。

これらの変更により、GoコンパイラのSSAバックエンドは、`runtime.newobject`の特殊なセマンティクスを正しく理解し、大規模なデータ構造のコンパイル時に発生していた不必要な最適化の試みとそれに伴う性能劣化を回避できるようになりました。

# [インデックス 20121] ファイルの概要

このコミットは、Go言語のリンカ（`liblink`）におけるAMD64（x86-64）コード生成時のメモリ参照の扱いに関する変更です。具体的には、すべてのメモリ参照においてPC相対アドレッシング（Program Counter Relative Addressing）を使用するように統一することを目的としています。これにより、生成されるコードのポータビリティと効率が向上し、特に共有ライブラリや位置独立コード（PIC）の生成がよりシンプルになります。

## 元コミット内容

このコミットの目的は、`liblink`が生成するAMD64コードにおいて、すべてのメモリ参照にPC相対アドレッシングを使用することです。これにより、リンカの複雑性が軽減され、特に共有ライブラリや位置独立実行可能ファイル（PIE）の生成が容易になります。

## 変更の背景

Go言語のリンカは、異なるオペレーティングシステムやアーキテクチャ向けに実行可能ファイルを生成します。AMD64アーキテクチャでは、メモリ参照の方法として絶対アドレッシングとPC相対アドレッシングの2つが主要です。

*   **絶対アドレッシング**: メモリ上の特定のアドレスを直接指定する方法です。プログラムがロードされるメモリ上の固定位置が既知である場合に有効です。
*   **PC相対アドレッシング**: 現在のプログラムカウンタ（PC）の値からのオフセットでメモリ位置を指定する方法です。これにより、プログラムがメモリ上のどこにロードされても正しく動作する「位置独立コード（PIC）」を生成できます。共有ライブラリや、ASLR（Address Space Layout Randomization）が有効な現代のシステムでは、PICが必須または推奨されます。

以前のGoリンカでは、共有ライブラリ（`flag_shared`）やNaCl（Native Client）のような特定の環境でのみPC相対アドレッシングを強制していました。しかし、それ以外の通常の実行可能ファイルでは、絶対アドレッシングを使用する可能性がありました。このアプローチは、リンカのロジックを複雑にし、異なるコンテキストでのコード生成の一貫性を損なう可能性がありました。

このコミットの背景には、AMD64コード生成におけるアドレッシングモードの統一化と簡素化があります。すべてのメモリ参照をPC相対アドレッシングにすることで、リンカはよりシンプルで一貫したコード生成ロジックを持つことができ、将来的な最適化や機能追加が容易になります。また、現代のシステムではPICが広く利用されており、この変更はGoの実行可能ファイルの互換性とセキュリティを向上させることにも寄与します。

## 前提知識の解説

*   **PC相対アドレッシング (Program Counter Relative Addressing)**: CPUの命令ポインタ（プログラムカウンタ、PC）の現在値からの相対的なオフセットを用いてメモリ上のアドレスを指定するアドレッシングモードです。例えば、「PCの現在値から100バイト先のデータ」といった形でアクセスします。この方式の最大の利点は、生成されたコードがメモリ上のどこにロードされても正しく動作する「位置独立コード (Position-Independent Code, PIC)」になる点です。これは、共有ライブラリ（DLLや.soファイル）や、ASLR（Address Space Layout Randomization）が有効な現代の実行可能ファイル（PIE: Position-Independent Executable）において不可欠です。

*   **Goリンカ (`liblink`, `cmd/6l`, `cmd/ld`)**: Go言語のコンパイラツールチェーンの一部であり、Goのソースコードから生成されたオブジェクトファイルを結合し、実行可能ファイルやライブラリを生成する役割を担います。
    *   `liblink`: リンカのコアロジックを提供するライブラリです。
    *   `cmd/6l`: AMD64アーキテクチャ向けのリンカコマンドです。
    *   `cmd/ld`: リンカの共通部分を扱うコマンドです。
    これらのツールは、シンボル解決、再配置（relocation）、セクションの結合など、実行可能ファイルを生成するために必要な様々なタスクを実行します。

*   **再配置 (Relocation)**: コンパイル時にアドレスが確定できないシンボル（例えば、別のオブジェクトファイルや共有ライブラリに定義されている関数や変数）について、リンカが最終的な実行可能ファイルを生成する際に、正しいメモリ上のアドレスを埋め込む処理です。再配置エントリ（Reloc）は、どのシンボルを、どの種類のアドレッシングモードで、どのオフセットに埋め込むかといった情報を含みます。
    *   `R_PCREL`: PC相対再配置を示すタイプです。
    *   `R_CALL`: 関数呼び出しの再配置を示すタイプです。
    *   `R_ADDR`: 絶対アドレス再配置を示すタイプです。
    *   `R_X86_64_PC32`: ELF形式におけるx86-64の32ビットPC相対再配置タイプです。
    *   `MACHO_X86_64_RELOC_BRANCH`, `MACHO_X86_64_RELOC_SIGNED`, `MACHO_X86_64_RELOC_UNSIGNED`: Mach-O形式におけるx86-64の再配置タイプです。

*   **シンボルタイプ (`SHOSTOBJ`, `SDYNIMPORT`, `STLSBSS`)**: リンカが扱うシンボルの種類です。
    *   `SHOSTOBJ`: ホストシステム（OS）のオブジェクトファイルからインポートされるシンボル。
    *   `SDYNIMPORT`: 動的にインポートされるシンボル（共有ライブラリから）。
    *   `STLSBSS`: スレッドローカルストレージ（TLS）のBSSセクションにあるシンボル。

*   **アドレッシングモードのクラス (`Yiauto`, `Yi32`)**: `liblink`内部で、特定のアドレッシングモードがどのクラスに属するかを示す識別子です。
    *   `Yiauto`: PC相対アドレッシングなど、自動的にオフセットが計算されるアドレッシングモード。
    *   `Yi32`: 32ビットの即値オフセットを使用するアドレッシングモード。

## 技術的詳細

このコミットの核心は、AMD64アーキテクチャにおけるメモリ参照の再配置ロジックを、PC相対アドレッシングに統一することです。これまでの実装では、共有ライブラリ（`flag_shared`）やNaCl環境でのみPC相対アドレッシングが強制されていましたが、この変更により、それ以外の通常の実行可能ファイルにおいてもPC相対アドレッシングがデフォルトとなります。

具体的な変更点は以下の通りです。

1.  **再配置タイプの分離と統一**:
    *   `src/cmd/6l/asm.c`では、ELFおよびMach-O形式の再配置処理において、`R_CALL`と`R_PCREL`の再配置タイプが明確に分離されました。以前は`R_CALL`と`R_PCREL`が同じケースで処理されることがありましたが、これにより`R_PCREL`が独立した再配置タイプとして扱われ、より正確なPC相対オフセットの計算と適用が可能になります。
    *   ELF形式では、`R_PCREL`に対して明示的に`R_X86_64_PC32`再配置タイプが使用されるようになりました。これは、32ビットのPC相対オフセットを埋め込むための標準的なELF再配置タイプです。
    *   Mach-O形式では、`R_PCREL`に対して`MACHO_X86_64_RELOC_SIGNED`が設定され、PC相対ビット（`1<<24`）が立てられます。これにより、Mach-Oバイナリでも符号付きPC相対オフセットが正しく扱われます。

2.  **`liblink`内部のアドレッシングモード選択の簡素化**:
    *   `src/liblink/asm6.c`の`oclass`関数では、`D_EXTERN`（外部シンボル）および`D_STATIC`（静的シンボル）のアドレッシングモードを決定するロジックが簡素化されました。以前は`ctxt->flag_shared`や`ctxt->headtype == Hnacl`といった条件に基づいて`Yiauto`（PC相対）または`Yi32`（32ビット即値）を選択していましたが、この条件が削除され、常に`Yiauto`を返すようになりました。これは、「すべてのメモリ参照にPC相対アドレッシングを使用する」という方針を直接的に反映したものです。

3.  **デフォルトの再配置タイプとしての`R_PCREL`の採用**:
    *   `src/liblink/asm6.c`の`vaddr`関数では、外部シンボルや静的シンボルに対する再配置タイプの設定が変更されました。以前は`ctxt->flag_shared`や`ctxt->headtype == Hnacl`の条件に応じて`R_PCREL`または`R_ADDR`を選択していましたが、この条件が削除され、常に`r->type = R_PCREL;`が設定されるようになりました。これにより、Goリンカが生成するAMD64コードでは、デフォルトでPC相対再配置が使用されることになります。

4.  **Mach-OにおけるPC相対オフセット計算の調整**:
    *   `src/cmd/ld/data.c`の`relocsym`関数では、Darwin（Mach-O）環境におけるPC相対オフセットの計算ロジックが修正されました。特に`R_CALL`タイプ以外の再配置（つまり、新しい`R_PCREL`のケース）では、オフセットの計算方法が調整され、より正確なPC相対オフセットが適用されるようになりました。これは、PC相対アドレッシングの統一化に伴う、既存のリンカロジックとの整合性を保つための重要な変更です。

これらの変更により、GoのAMD64バイナリは、より一貫して位置独立コードとして振る舞うようになります。これは、現代のOS環境におけるセキュリティ機能（ASLR）との親和性を高め、共有ライブラリとしての利用をよりスムーズにする効果があります。

## コアとなるコードの解説

### `src/cmd/6l/asm.c` の変更

このファイルは、リンカがELFおよびMach-O形式の実行可能ファイルを生成する際の再配置処理を定義しています。

*   **`elfreloc1` 関数**: ELF形式の再配置を処理します。
    *   以前は`R_CALL`と`R_PCREL`が同じ`case`ブロックで処理されていましたが、`R_PCREL`が独立した`case`として分離されました。
    *   新しい`R_PCREL`の`case`では、`VPUT(R_X86_64_PC32 | (uint64)elfsym<<32);`が追加されました。これは、AMD64のELFバイナリにおいて、32ビットのPC相対オフセットを埋め込むための標準的な再配置タイプ`R_X86_64_PC32`を使用することを明示しています。これにより、PC相対アドレッシングがより正確に適用されます。

*   **`machoreloc1` 関数**: Mach-O形式の再配置を処理します。
    *   `if(rs->type == SHOSTOBJ)`の条件が`if(rs->type == SHOSTOBJ || r->type == R_PCREL)`に変更されました。これは、`R_PCREL`タイプの再配置もホストオブジェクトと同様に扱われるべきであることを示唆しています。
    *   `R_CALL`と`R_PCREL`が分離され、`R_PCREL`の新しい`case`が追加されました。この新しい`case`では、`v |= 1<<24; // pc-relative bit`と`v |= MACHO_X86_64_RELOC_SIGNED<<28;`が設定されます。これは、Mach-OバイナリにおいてPC相対ビットを立て、符号付きのPC相対オフセットを使用することを指定しています。

これらの変更は、`R_PCREL`再配置をより厳密に、かつプラットフォーム固有の適切な方法で処理するためのものです。

### `src/cmd/ld/data.c` の変更

このファイルは、リンカがシンボルを再配置する際のデータ処理を扱います。

*   **`relocsym` 関数**: シンボルの再配置値を計算します。
    *   `HEADTYPE == Hdarwin`（Mach-O）の場合のPC相対オフセット計算ロジックが変更されました。
    *   以前は`o -= r->off;`という一般的なオフセット調整がありましたが、新しいコードでは`if(r->type == R_CALL)`という条件が追加されました。
    *   `R_CALL`の場合のみ`o -= r->off;`が適用され、それ以外（つまり、新しい`R_PCREL`のケース）では`o += r->siz;`が適用されます。これは、関数呼び出しと一般的なデータ参照のPC相対オフセット計算が異なることを考慮し、より正確な再配置値を生成するための修正です。

### `src/liblink/asm6.c` の変更

このファイルは、AMD64アーキテクチャ向けのGoアセンブラ（`liblink`の一部）のコアロジックを含んでいます。

*   **`oclass` 関数**: アドレスのアドレッシングモードクラスを決定します。
    *   `D_EXTERN`（外部シンボル）と`D_STATIC`（静的シンボル）の場合のロジックが大幅に簡素化されました。
    *   以前は`ctxt->flag_shared || ctxt->headtype == Hnacl`という条件に基づいて`Yiauto`（PC相対）または`Yi32`（32ビット即値）を返していましたが、この条件が削除され、常に`return Yiauto; // use pc-relative addressing`が実行されるようになりました。これは、すべてのメモリ参照にPC相対アドレッシングを強制するというコミットの目的を直接的に実現するものです。

*   **`vaddr` 関数**: アドレスの仮想アドレスを計算し、再配置情報を設定します。
    *   `r->type = R_PCREL;`の行が、以前の`if(ctxt->flag_shared || ctxt->headtype == Hnacl)`ブロックの外に移動しました。これにより、`flag_shared`や`Hnacl`のコンテキストに関わらず、外部シンボルや静的シンボルに対するデフォルトの再配置タイプが`R_PCREL`に設定されるようになりました。以前存在した`else r->type = R_ADDR;`のパスは削除されました。

*   **`asmandsz` 関数**: アセンブリ命令のオペランドサイズを処理します。
    *   `D_STATIC`と`D_EXTERN`の`case`ブロックが削除されました。以前はこれらのケースで`goto bad`や`v = vaddr(...)`といった処理がありましたが、`oclass`や`vaddr`での変更により、これらの特殊な処理が不要になったことを示しています。
    *   `if((ctxt->flag_shared || ctxt->headtype == Hnacl) && t == D_NONE && (a->type == D_STATIC || a->type == D_EXTERN) || ctxt->asmode != 64)`という複雑な条件が、`if(t == D_NONE && (a->type == D_STATIC || a->type == D_EXTERN) || ctxt->asmode != 64)`に簡素化されました。これもまた、`flag_shared`や`Hnacl`といった特定のコンテキストに依存せず、PC相対アドレッシングを適用するという方針を反映しています。

これらの変更は、GoリンカがAMD64コードを生成する際の内部ロジックを大幅に簡素化し、PC相対アドレッシングをデフォルトかつ一貫した動作として確立するためのものです。

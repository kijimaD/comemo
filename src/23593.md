# [インデックス 23593] ファイルの概要

このコミットは、Goコンパイラおよびアセンブラの内部構造体である`Prog`のメモリ使用量を最適化するための変更です。具体的には、`Prog`構造体内の`From3`フィールドの型を、値型である`obj.Addr`からポインタ型である`*obj.Addr`に変更しています。これにより、`From3`がほとんど使用されない場合に、不要なメモリ割り当てを削減し、`Prog`構造体全体のサイズを縮小しています。

## 元コミット内容

`cmd/internal/obj: Prog.From3 をポインタにする`

`From3`はほとんど設定されず、`Addr`は大きいため、`Prog`内に完全な構造体があるとほとんどの場合メモリを浪費します。

（64ビットシステムでの）変更前:
```
$ sizeof -p cmd/internal/obj Addr Prog
Addr 80
Prog 376
$
```

変更後:
```
$ sizeof -p cmd/internal/obj Addr Prog
Addr 80
Prog 304
$
```

## 変更の背景

Goコンパイラとアセンブラのバックエンドでは、プログラムの命令を表現するために`obj.Prog`構造体が使用されます。この`Prog`構造体には、命令のオペランド（引数）を表すために`obj.Addr`型のフィールドがいくつか含まれています。その一つが`From3`フィールドです。

コミットメッセージによると、この`From3`フィールドは「ほとんど設定されない」にもかかわらず、`obj.Addr`構造体自体が80バイトと比較的大きなサイズを持っていました。`Prog`構造体内に`From3`が値型として含まれていると、`From3`が使用されない場合でも常に80バイトのメモリが割り当てられてしまいます。これは、多数の`Prog`インスタンスが生成されるコンパイルプロセスにおいて、無駄なメモリ消費につながります。

このコミットの目的は、`From3`をポインタ型（`*obj.Addr`）に変更することで、`From3`が実際に必要とされる場合にのみ`obj.Addr`構造体のメモリを割り当てるようにし、デフォルトでは`nil`（ポインタ）としてメモリを節約することです。これにより、`Prog`構造体自体のサイズが376バイトから304バイトに削減され、全体的なメモリ効率が向上します。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラ/アセンブラの基本的な概念を知っておく必要があります。

1.  **Go言語の構造体とポインタ**:
    *   **構造体 (Struct)**: 複数のフィールド（変数）をまとめた複合データ型です。構造体は値型であり、変数に代入されると内容がコピーされます。
    *   **ポインタ (Pointer)**: 変数のメモリアドレスを保持する変数です。ポインタは参照型であり、ポインタを介して元の変数の値を操作できます。ポインタ自体のサイズは、通常、システムのアドレス幅（32ビットシステムなら4バイト、64ビットシステムなら8バイト）に依存します。
    *   **メモリ効率**: 値型を構造体に含めると、その値型のサイズが構造体全体のサイズに直接加算されます。一方、ポインタ型を含めると、ポインタ自体のサイズ（通常8バイト）のみが構造体全体のサイズに加算され、ポインタが指すデータはヒープなどに別途割り当てられます。データがほとんど使われない場合、ポインタ型にすることでメモリを節約できます。

2.  **Goコンパイラ/アセンブラの内部構造**:
    *   **`cmd/internal/obj`パッケージ**: Goのコンパイラとアセンブラが共通して使用する低レベルのオブジェクトファイル生成に関するユーティリティを提供するパッケージです。アセンブリ命令の抽象的な表現や、シンボル、アドレスなどの情報が定義されています。
    *   **`obj.Prog`構造体**: アセンブリ命令（プログラム命令）を表現する構造体です。命令の種類（`As`）、行番号（`Lineno`）、オペランド（`From`, `To`, `From3`など）、レジスタ（`Reg`）などの情報を含みます。
    *   **`obj.Addr`構造体**: アセンブリ命令のオペランド（アドレス、レジスタ、定数など）を表現する構造体です。型（`Type`）、オフセット（`Offset`）、シンボル（`Sym`）、レジスタ（`Reg`）、インデックス（`Index`）など、様々な情報を含みます。コミットメッセージによると、この`Addr`構造体は80バイトのサイズがあります。
    *   **`sizeof -p`コマンド**: Goの内部ツールで、指定されたパッケージ内の型（構造体など）のメモリサイズを報告するために使用されます。

3.  **コンパイルプロセスにおけるメモリ使用**:
    *   コンパイラはソースコードを解析し、中間表現を経て最終的な機械語コードを生成します。この過程で、多数の`Prog`構造体のような内部データ構造が生成され、メモリ上に保持されます。
    *   これらの内部データ構造のサイズが大きくなると、コンパイル時のメモリ使用量が増加し、コンパイル速度やシステム全体のパフォーマンスに影響を与える可能性があります。特に、`Prog`のように頻繁に生成される構造体の場合、わずかなサイズ削減でも全体として大きな効果をもたらします。

## 技術的詳細

このコミットの主要な変更点は、`src/cmd/internal/obj/link.go`ファイル内の`Prog`構造体の定義です。

変更前:
```go
type Prog struct {
    // ...
    From3    Addr
    // ...
}
```

変更後:
```go
type Prog struct {
    // ...
    From3    *Addr // optional
    // ...
}
```

この変更に伴い、`From3`フィールドへのアクセス方法が変更されました。
*   以前は`p.From3.Type`のように直接フィールドにアクセスできましたが、ポインタ型になったため、`p.From3.Type`はコンパイルエラーになります。
*   `From3`が`nil`である可能性があるため、アクセスする前に`nil`チェックが必要になります。
*   この変更に対応するため、`Prog`構造体に新しいメソッド`From3Type()`が追加されました。これは`From3`が`nil`の場合に`obj.TYPE_NONE`を返し、それ以外の場合は`p.From3.Type`を返します。これにより、`From3`の型に安全にアクセスできるようになります。

```go
// From3Type returns From3.Type, or TYPE_NONE when From3 is nil.
func (p *Prog) From3Type() int16 {
    if p.From3 == nil {
        return TYPE_NONE
    }
    return p.From3.Type
}
```

また、`From3`に`obj.Addr`の値を設定する際には、`new(obj.Addr)`を使って新しい`Addr`構造体を割り当て、そのポインタを`From3`に代入する必要があります。

```go
// newAddr returns a new(Addr) initialized to x.
func newAddr(x obj.Addr) *obj.Addr {
    p := new(obj.Addr)
    *p = x
    return p
}
```

この変更は、`cmd/asm`（アセンブラ）、`cmd/compile`（コンパイラ）、および`cmd/internal/obj`パッケージ内の多数のファイルに影響を与えています。具体的には、`Prog.From3`を参照している箇所すべてで、ポインタへの変更に対応するための修正が行われています。これには、`nil`チェックの追加、`From3Type()`メソッドの使用、または`new(obj.Addr)`による明示的な割り当てが含まれます。

コミットメッセージにある`sizeof`コマンドの出力は、この変更によるメモリ削減効果を明確に示しています。
*   `Addr`構造体は80バイト。
*   変更前、`Prog`構造体は`From3 Addr`を含んでいたため、376バイト。
*   変更後、`Prog`構造体は`From3 *Addr`（ポインタ）を含むため、ポインタのサイズ（64ビットシステムで8バイト）のみが加算され、`Prog`構造体は304バイトに削減。
*   削減されたメモリは`376 - 304 = 72`バイトであり、これは`Addr`構造体のサイズ80バイトからポインタのサイズ8バイトを引いた値と一致します。

## コアとなるコードの変更箇所

主要な変更は以下のファイルに集中しています。

*   `src/cmd/internal/obj/link.go`: `Prog`構造体の`From3`フィールドの型定義が`Addr`から`*Addr`に変更され、`From3Type()`ヘルパーメソッドが追加されました。
*   `src/cmd/asm/internal/asm/asm.go`: アセンブラが`Prog`構造体を生成する際に、`From3`に値を設定する箇所で`&obj.Addr{...}`や`newAddr(a[1])`のようにポインタを生成するよう変更されました。
*   `src/cmd/compile/internal/gc/*.go`: コンパイラの各バックエンド（`arm64`, `ppc64`など）で`Prog.From3`にアクセスする箇所が`p.From3.Type`から`p.From3Type()`に変更されました。また、`new(obj.Addr)`を使って`From3`を初期化する箇所が追加されました。
*   `src/cmd/internal/obj/arm64/asm7.go`, `src/cmd/internal/obj/ppc64/asm9.go`, `src/cmd/internal/obj/x86/asm6.go`, `src/cmd/internal/obj/x86/obj6.go`: 各アーキテクチャ固有のアセンブラコードで、`From3`へのアクセスや操作がポインタ型に対応するように修正されました。特に、`nil`チェックが追加されたり、`From3Type()`が使用されたりしています。
*   `src/cmd/internal/obj/go.go`: `Nopout`関数で`Prog`を初期化する際に、`p.From3 = nil`と設定するよう変更されました。
*   `src/cmd/internal/obj/pass.go`: `linkpatch`関数で`From3`をチェックする際に、`nil`チェックが追加されました。
*   `src/cmd/internal/obj/util.go`: `Prog.String()`メソッドで`From3`を文字列化する際に、`From3Type()`を使用し、`nil`の場合の処理が考慮されました。
*   `src/cmd/old*a/*.y`, `src/cmd/old*a/lex.go`: 古いアセンブラ（`5a`, `6a`, `8a`, `9a`）のYacc/Lexerファイルでも、`Prog.From3`へのアクセスや割り当てがポインタ型に対応するように修正されました。

## コアとなるコードの解説

最も重要な変更は`src/cmd/internal/obj/link.go`にあります。

```go
// src/cmd/internal/obj/link.go
type Prog struct {
    // ... 既存のフィールド ...
    From     Addr
    From3    *Addr // optional // ここが変更点
    To       Addr
    // ... 既存のフィールド ...
}

// From3Type returns From3.Type, or TYPE_NONE when From3 is nil.
func (p *Prog) From3Type() int16 {
    if p.From3 == nil {
        return TYPE_NONE
    }
    return p.From3.Type
}
```
`From3`が`*Addr`になったことで、`Prog`構造体自体は`Addr`構造体全体を保持するのではなく、`Addr`構造体へのポインタ（メモリアドレス）のみを保持するようになりました。これにより、`From3`が`nil`の場合、`Addr`構造体分のメモリは割り当てられず、`Prog`構造体のサイズが小さくなります。

`From3Type()`メソッドは、`From3`が`nil`である可能性を考慮し、安全に`Type`フィールドにアクセスするためのユーティリティです。これにより、コードの他の部分で毎回`nil`チェックを書く手間が省けます。

他のファイルでの変更例としては、`src/cmd/asm/internal/asm/asm.go`の`asmInstruction`関数内での`From3`の割り当てが挙げられます。

```go
// src/cmd/asm/internal/asm/asm.go (抜粋)
// 変更前:
// prog.From3 = a[1]
// 変更後:
prog.From3 = newAddr(a[1]) // newAddrはobj.Addrを*obj.Addrに変換するヘルパー関数
```
ここで`newAddr`ヘルパー関数が導入され、`obj.Addr`型の値を受け取り、それをヒープにコピーして`*obj.Addr`型のポインタを返します。これにより、`From3`に値を設定する際に、明示的にメモリを割り当ててポインタを渡すというGoの慣用的な方法が採用されています。

また、`src/cmd/compile/internal/arm64/peep.go`のようなコンパイラの最適化パスでは、`From3`の型にアクセスする際に`From3Type()`が使用されています。

```go
// src/cmd/compile/internal/arm64/peep.go (抜粋)
// 変更前:
// if p.From3.Type != obj.TYPE_NONE {
// 変更後:
if p.From3Type() != obj.TYPE_NONE {
    // ...
}
```
これは、`From3`がポインタになったことで、直接`.Type`にアクセスするとパニック（`nil`ポインタ参照）が発生する可能性があるため、安全なアクセス方法として導入されたものです。

これらの変更は、Goコンパイラとアセンブラの内部で、命令の表現方法におけるメモリ管理をより効率的にするための重要なステップです。

# [インデックス 27213] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）における関数パラメータの解析処理を高速化し、メモリ使用量を削減することを目的としています。具体的には、パラメータの妥当性チェックをパーサー内で直接行うように変更し、複数回のパスを2パスに簡素化することで、`OKEY`ノードおよび一部の`ONONAME`ノードの生成を不要にしています。これにより、コンパイル時のノード割り当て総数を約1.2%削減しています。

## 変更の背景

Goコンパイラ（`cmd/compile`）の内部では、ソースコードを解析して抽象構文木（AST）を構築する際に、様々な種類のノードが生成されます。関数やメソッドのパラメータリストを解析する過程もその一つであり、この処理の効率はコンパイル時間やメモリ使用量に直接影響します。

このコミット以前のパラメータ解析ロジックは、特にパラメータの妥当性チェックにおいて非効率な点がありました。具体的には、`OKEY`ノードと呼ばれる中間ノードを生成し、複数のパスでパラメータリストを走査してチェックを行っていました。この「複数回のパス」は、最悪の場合、パラメータの数に対して二次曲線的な計算量（O(N^2)）となる可能性があり、大規模なコードベースや多数のパラメータを持つ関数においてパフォーマンスのボトルネックとなる恐れがありました。

また、`OKEY`ノードや一部の`ONONAME`ノードの生成は、コンパイラが使用するメモリ量を増加させます。コンパイラのメモリフットプリントを削減し、全体的なコンパイル速度を向上させることは、Go言語の継続的な改善目標の一つです。

このコミットは、「パラメータ解析の合理化」という一連の取り組みの「ステップ2」として位置づけられており、より効率的なパラメータ解析メカニズムを導入することで、これらの問題を解決しようとしています。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`) の構造と役割

Goコンパイラは、Go言語のソースコードを機械語に変換するツールチェーンの中核をなす部分です。`cmd/compile`は、主に以下のフェーズで動作します。

1.  **字句解析 (Lexing)**: ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換します。
2.  **構文解析 (Parsing)**: トークンのストリームを解析し、プログラムの構造を抽象構文木（AST）として構築します。
3.  **型チェック (Type Checking)**: ASTを走査し、型の一貫性や正当性を検証します。
4.  **中間表現 (IR) への変換**: ASTを、より低レベルで最適化に適した中間表現に変換します。
5.  **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用し、生成されるコードの効率を高めます。
6.  **コード生成 (Code Generation)**: 最適化された中間表現から、ターゲットアーキテクチャの機械語コードを生成します。

このコミットは、主に構文解析フェーズと、それに続く型チェックや中間表現構築に影響を与える部分に焦点を当てています。

### 抽象構文木 (AST) とノード

Goコンパイラは、ソースコードの構造を表現するために独自のASTを使用します。このASTは、`go/ast`パッケージで公開されているものとは異なり、コンパイラ内部で定義されたノード型（`Op`）とデータ構造（`Node`）で構成されます。

-   **`Node`**: ASTの基本的な構成要素であり、プログラムの各要素（式、文、宣言など）を表します。各ノードは`Op`フィールドを持ち、そのノードが何を表すかを示します。
-   **`Op` (Operation)**: ノードの種類を定義する列挙型です。例えば、`OADD`は加算演算、`ODCLFIELD`はフィールド宣言を表します。

このコミットで言及されているノードは以下の通りです。

-   **`OKEY`**: 以前のパラメータ解析において、名前と型のペア（例: `i int`）を表現するために使用されていた中間ノードと考えられます。キーと値のペアを抽象的に表現する際に用いられることが多いです。
-   **`ONONAME`**: 名前がない、または一時的な名前を持つ要素を表すノードです。例えば、型のみのパラメータ（例: `int`）や、コンパイラ内部で一時的に生成される匿名要素などに使用されることがあります。
-   **`ODCLFIELD`**: 宣言されたフィールドを表すノードです。関数のパラメータも、内部的にはフィールド宣言として扱われるため、最終的なパラメータリストの構築に使用されます。

### Goの関数パラメータの構文とルール

Go言語の関数パラメータリストには、いくつかの構文ルールがあります。

-   **名前付きパラメータと型**: `func(a int, b string)` のように、名前と型を明示的に指定します。
-   **型のみのパラメータ**: `func(int, string)` のように、型のみを指定し、名前を省略できます。
-   **グループ化されたパラメータ**: `func(a, b int, c string)` のように、同じ型を持つ複数のパラメータをカンマで区切って宣言できます。この場合、`a`と`b`は`int`型、`c`は`string`型となります。
-   **混合パラメータの禁止**: Goの仕様では、パラメータリスト内で名前付きパラメータと型のみのパラメータを混在させることはできません。例えば、`func(a int, string)` は不正です。ただし、`func(a, b int, c string)` のように、グループ化されたパラメータ内で名前と型が明示されている場合は問題ありません。
-   **可変長引数 (`...`)**: `func(args ...int)` のように、最後のパラメータとして可変長引数を指定できます。これはスライスとして関数本体に渡されます。可変長引数はパラメータリストの最後にのみ配置できます。

これらの構文ルールと妥当性チェックは、コンパイラがパラメータリストを正しく解釈し、エラーを報告するために不可欠です。

## 技術的詳細

### 旧実装の問題点と`dcl.go`の役割

このコミット以前は、`src/cmd/compile/internal/gc/dcl.go`内の`checkarglist`関数が、パラメータリストの妥当性チェックと最終的な`ODCLFIELD`ノードへの変換を担当していました。

`checkarglist`関数は、以下のようなロジックで動作していました。

1.  **`OKEY`ノードの検出**: パラメータリスト内に`OKEY`ノード（名前と型のペアを表す）が存在するかどうかを最初に確認し、名前付きパラメータが存在するかを判断していました。
2.  **混合パラメータのチェック**: 名前付きパラメータと型のみのパラメータが混在していないかをチェックしていました。このチェックは、パラメータリストを複数回走査する必要がありました。
3.  **型の伝播と`ODCLFIELD`への変換**: `a, b, c int` のようなグループ化されたパラメータの場合、`int`型を`a`と`b`に伝播させる処理を行っていました。この処理も、`findtype`関数を呼び出すことで、パラメータリストを繰り返し走査する可能性がありました。
4.  **可変長引数 (`...`) のチェック**: 可変長引数が正しく使用されているか（最後のパラメータであるかなど）をチェックしていました。

この`checkarglist`関数は、パラメータリストを複数回走査する可能性があり、特に`findtype`関数がリストの残りを毎回スキャンするような実装であった場合、理論的には二次曲線的な計算量（O(N^2)）になる可能性がありました。また、`OKEY`ノードを生成すること自体が、メモリ割り当てのオーバーヘッドとなっていました。

### 新実装のアプローチと`parser.go`への移行

このコミットでは、パラメータ解析のロジックを`dcl.go`から`src/cmd/compile/internal/gc/parser.go`へ移行し、より効率的なアプローチを採用しています。主な変更点は以下の通りです。

1.  **パーサー内での妥当性チェック**: パラメータの構文解析と同時に、妥当性チェックもパーサー内で直接行われるようになりました。これにより、後続のフェーズでの追加の走査が不要になります。
2.  **`OKEY`ノードの廃止**: パラメータの名前と型を直接`parser.param`関数で抽出し、`OKEY`ノードを介さずに処理することで、その生成とそれに伴うメモリ割り当てを完全に排除しました。
3.  **2パス処理への簡素化**: パラメータリストの処理を、以下の2つの論理的なパスに簡素化しました。
    *   **第1パス**: `parser.param`関数で各パラメータの名前と型を抽出し、一時的な`param`構造体のスライスに格納します。この際、名前付きパラメータの数を`named`変数でカウントします。
    *   **第2パス**: `param_list`関数内で、`named`変数の値に基づいてパラメータリスト全体を一度だけ走査し、型の伝播、混合パラメータのチェック、可変長引数のチェックを行い、最終的な`ODCLFIELD`ノードのリストを構築します。
4.  **メモリ割り当ての削減**: `OKEY`ノードおよび一部の`ONONAME`ノードの生成が不要になったことで、コンパイル時のノード割り当て総数が約1.2%削減されました。これは、`make.bash`実行時に約123,000個のノード割り当てが削減されたことに相当します。

### `parser.go`における新しいパラメータ処理ロジック

`parser.go`の`param_list`関数は、新しいロジックの中心です。

-   **`param`構造体**: `name *Sym`と`typ *Node`を持つ一時的な構造体が導入され、各パラメータの名前と型を保持します。
-   **`named`カウンタ**: パラメータリスト内で名前と型が両方指定されているパラメータの数を追跡します。
-   **3つのケースによる処理**: `named`カウンタの値に基づいて、パラメータリストの処理が3つの主要なケースに分岐します。
    1.  **`named == 0`**: 全てのパラメータが型のみ（匿名）である場合。この場合、名前は`nil`であり、型のみが考慮されます。
    2.  **`named == len(params)`**: 全てのパラメータが名前と型を両方持っている場合。
    3.  **それ以外 (`0 < named < len(params)`)**: 一部のパラメータが名前と型を持ち、一部が型のみである場合。これはGoの仕様では不正な「混合パラメータ」のケースに該当します。この場合、コンパイラはエラーを報告します。
        *   このケースでは、型の伝播ロジックが適用されます。`a, b, c int` のような構文に対応するため、リストの最後から先頭に向かって型を伝播させます。例えば、`c int` の`int`型が`b`と`a`に適用されます。
        *   この伝播中に、名前のないパラメータに型が適用されなかったり、名前付きパラメータに型が明示されていないといった矛盾が生じた場合、「`mixed named and unnamed function parameters`」エラーが報告されます。
-   **最終的な`ODCLFIELD`ノードの生成**: 処理の最後に、一時的な`param`構造体のスライスから、最終的な`ODCLFIELD`ノードのリストが生成されます。この際、可変長引数 (`...`) の構文も適切に`OTARRAY`ノードに変換され、妥当性チェックが行われます。

この新しいアプローチにより、パラメータ解析はより構造化され、効率的かつ堅牢になりました。

### `parser.go`における新しい`param`関数と`param_list`関数

#### `parser.param()` 関数

```go
// param parses and returns a function parameter list entry which may be
// a parameter name and type pair (name, typ), a single type (nil, typ),
// or a single name (name, nil). In the last case, the name may still be
// a type name. The result is (nil, nil) in case of a syntax error.
//
// [ParameterName] Type
func (p *parser) param() (name *Sym, typ *Node) {
    // ... (字句解析と構文解析のロジック) ...
    switch p.tok {
    case LNAME, '@', '?':
        name = p.sym() // 名前を抽出
        switch p.tok {
        case LCOMM, LFUNC, '[', LCHAN, LMAP, LSTRUCT, LINTERFACE, '*', LNAME, '@', '?', '(':
            // sym name_or_type (例: i int)
            typ = p.ntype() // 型を抽出
        case LDDD:
            // sym dotdotdot (例: args ...int)
            typ = p.dotdotdot() // 可変長引数の型を抽出
        default:
            // name_or_type (例: int) - この場合は名前が型名として扱われる可能性がある
            // ...
            if p.got('.') {
                // 修飾された名前 (例: runtime.UintType) はパラメータ名にはなれない
                typ = p.new_dotname(mkname(name))
                name = nil // 名前は型の一部として扱われるためnilにする
            }
        }
    case LDDD:
        // dotdotdot (例: ...int)
        typ = p.dotdotdot()
    case LCOMM, LFUNC, '[', LCHAN, LMAP, LSTRUCT, LINTERFACE, '*', '(':
        // name_or_type (例: int)
        typ = p.ntype()
    default:
        // 構文エラー
        p.syntax_error("expecting )")
        p.advance(',', ')')
    }
    return // nameとtypを返す
}
```

この`param`関数は、パラメータリストの個々のエントリを解析し、その名前（`*Sym`）と型（`*Node`）を直接返します。以前の`OKEY`ノードのような中間表現を介さず、より直接的に情報を抽出する点が重要です。これにより、後続の処理で`OKEY`ノードを解析する手間がなくなります。

#### `parser.param_list()` 関数

```go
func (p *parser) param_list(dddOk bool) []*Node {
    // ...
    type param struct {
        name *Sym
        typ  *Node
    }
    var params []param
    var named int // 名前と型を持つパラメータの数

    p.want('(')
    for p.tok != EOF && p.tok != ')' {
        name, typ := p.param() // 各パラメータを解析
        params = append(params, param{name, typ})
        if name != nil && typ != nil {
            named++ // 名前と型が両方ある場合にカウント
        }
        if !p.ocomma(')') {
            break
        }
    }
    p.want(')')

    // 3つのケースによる処理
    // 1) named == 0: 全てのパラメータが型のみ
    // 2) named == len(params): 全てのパラメータが名前と型を持つ
    // 3) それ以外: 混合パラメータ (エラーまたは型の伝播)
    if named != 0 && named != len(params) {
        // 混合パラメータの処理と型の逆方向伝播
        var T *Node // 現在の型
        for i := len(params) - 1; i >= 0; i-- {
            p := &params[i]
            if t := p.typ; t != nil {
                // 明示的な型がある場合、それを現在の型Tとして設定
                T = t
                // 名前がない場合はエラー (importpkg == nil の場合のみ)
                if p.name == nil && importpkg == nil {
                    T = nil // エラー状態
                }
            } else {
                // 明示的な型がない場合、現在の型Tを適用
                p.typ = T
            }
            if T == nil {
                Yyerror("mixed named and unnamed function parameters")
                break
            }
        }
    }

    // 最終的なODCLFIELDノードのリストを生成
    list := make([]*Node, len(params))
    for i, p := range params {
        var name, typ *Node
        if p.typ != nil {
            typ = p.typ
            if p.name != nil {
                name = newname(p.name) // パラメータ名をODCLFIELDノードの名前として設定
            }
        } else if p.name != nil {
            // 名前のみの場合、それが型名として扱われる
            typ = mkname(p.name)
        }
        n := Nod(ODCLFIELD, name, typ) // ODCLFIELDノードを生成

        // 可変長引数 (...) の処理と妥当性チェック
        if typ != nil && typ.Op == ODDD {
            if !dddOk {
                Yyerror("cannot use ... in receiver or result parameter list")
            } else if i+1 < len(params) {
                Yyerror("can only use ... with final parameter in list")
            }
            typ.Op = OTARRAY // ODDDをOTARRAYに変換
            typ.Right = typ.Left
            typ.Left = nil
            n.Isddd = true
            if n.Left != nil {
                n.Left.Isddd = true
            }
        }
        list[i] = n
    }
    return list
}
```

`param_list`関数は、`param`関数を使って個々のパラメータを解析した後、その結果を`param`構造体のスライスに一時的に保持します。そして、`named`カウンタに基づいて、Goのパラメータ宣言ルール（混合パラメータの禁止、型の伝播など）を効率的に適用します。特に、`named != 0 && named != len(params)` のケースでの型の逆方向伝播ロジックは、`a, b, c int` のような構文を正しく処理するために重要です。

最終的に、この関数は妥当性チェックが完了したパラメータ情報から、コンパイラの内部表現である`ODCLFIELD`ノードのリストを生成して返します。この一連の処理が、以前の`dcl.go`での複数パスの処理よりもはるかに効率的かつ直接的であるため、パフォーマンスとメモリ使用量の改善に繋がっています。

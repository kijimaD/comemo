# [インデックス 19957] ファイルの概要

このコミットは、Go言語のPowerPC 64ビットアーキテクチャ向けCコンパイラである `cmd/9c` に対する重要な変更を導入しています。主な目的は、コンパイラのバックエンドを `liblink` ライブラリに統合し、Goの標準的な引数渡し規則に準拠させ、さらにビッグエンディアンとリトルエンディアンの両方をサポートすることです。これにより、`9c` コンパイラのモジュール性、保守性、およびクロスプラットフォーム互換性が大幅に向上します。

## 変更の背景

このコミットは、Go言語のツールチェーンにおけるPowerPC 64ビットアーキテクチャ（`power64`）のサポートを強化し、より現代的な設計原則に適合させるために行われました。

1.  **コンパイラバックエンドの統一**: 以前は、各アーキテクチャ固有のコンパイラ（`8c`, `6c`, `9c` など）がそれぞれ独自のリンキングロジックを持つことがありました。これはコードの重複、保守性の低下、およびツールチェーン全体の不整合につながる可能性がありました。`liblink` の導入により、共通のリンキング処理をライブラリとして提供し、各コンパイラがそれを再利用することで、ツールチェーンのモジュール化と一貫性を図ることが目的です。
2.  **Goの引数渡し規則への準拠**: Go言語は、異なるアーキテクチャ間で一貫した動作を保証するために、特定の関数引数渡し規則を定めています。`9c` がこれらの規則に厳密に準拠することで、Goプログラムの正しい実行と、Goランタイムとのシームレスな連携が保証されます。
3.  **エンディアンサポートの拡張**: PowerPC 64ビットアーキテクチャは、ビッグエンディアンとリトルエンディアンの両方で動作可能です。Goがより広範な環境で動作するためには、両方のエンディアン形式を適切にサポートすることが不可欠でした。これにより、異なるシステム上でのGoプログラムの移植性と互換性が向上します。
4.  **コードのクリーンアップと型安全性の向上**: `long` 型の代わりに `int32` を使用するなど、より厳密な型定義を導入することで、コードの可読性、保守性、および潜在的なバグの削減を目指しています。これは、C言語の `long` 型がプラットフォームによってサイズが異なるという問題に対処し、Goランタイムとのデータ表現の一貫性を保つためにも重要です。

これらの変更は、Go言語のクロスプラットフォーム戦略の一環として、特定のアーキテクチャのサポートを深化させると同時に、ツールチェーン全体の設計品質を高めることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識があると役立ちます。

*   **Go言語のコンパイルプロセス**: Go言語のソースコードは、まずGoコンパイラ（`go tool compile`）によって中間表現に変換されます。その後、各アーキテクチャ固有のコンパイラ（例: `cmd/9c`）がこの中間表現をターゲットアーキテクチャの機械語に変換し、最終的にリンカ（`go tool link`）が複数のオブジェクトファイルを結合して実行可能ファイルを生成します。
*   **`cmd/9c`**: Go言語のツールチェーンの一部であり、PowerPC 64ビットアーキテクチャ（`power64`）向けのCコンパイラです。Goの初期のコンパイラは、Plan 9オペレーティングシステムのCコンパイラ（`8c`, `6c`, `9c` など）をベースにしていました。`9c` は、Goのコンパイルパイプラインにおいて、PowerPC 64ビット用の機械語を生成する役割を担います。
*   **`liblink`**: Go言語のリンカの共通ロジックをカプセル化したライブラリです。以前は各アーキテクチャのリンカが独自のコードを持っていましたが、`liblink` の導入により、シンボル解決、再配置、オブジェクトファイルの生成といったリンカのコア機能が共通化され、ツールチェーン全体のモジュール性と保守性が向上しました。
*   **引数渡し規則 (Calling Convention)**: 関数が呼び出される際に、引数がどのようにレジスタやスタックに配置され、戻り値がどのように返されるかを定義する規則です。アーキテクチャやOSによって異なる場合がありますが、Goは独自の標準的な規則を持っています。コンパイラがこれらの規則に準拠することは、生成されるコードが正しく動作し、Goランタイムと連携するために不可欠です。
*   **エンディアン (Endianness)**: コンピュータのメモリ上で、複数バイトのデータをどのように並べるかという順序付けの規則です。
    *   **ビッグエンディアン (Big-endian)**: データの最上位バイト（最も大きな桁）が最も小さいアドレスに格納されます。
    *   **リトルエンディアン (Little-endian)**: データの最下位バイト（最も小さな桁）が最も小さいアドレスに格納されます。
    PowerPC 64ビットアーキテクチャは、両方のエンディアンモードで動作できるため、Goコンパイラが両方を適切に処理できる必要があります。
*   **C言語の `long` と `int32`**: C言語の `long` 型のサイズは、コンパイラやターゲットプラットフォームによって32ビットまたは64ビットのいずれかになります。一方、`int32` は常に32ビットの整数を保証します。コンパイラの内部処理において、特定のビット幅の整数を扱う必要がある場合、`int32` のような明示的な型を使用することで、プラットフォーム間の互換性とデータ表現の一貫性を確保できます。
*   **`+build ignore` ディレクティブ**: Goのビルドシステムで使用される特殊なコメントで、このディレクティブが記述されたファイルはビルド対象から除外されます。このコミットでこれらのディレクティブが削除されている場合、それは当該ファイルがもはや無視されず、Goのビルドプロセスに正式に組み込まれたことを意味します。

## 技術的詳細

このコミットは、`cmd/9c` の内部構造に広範な変更を加えており、その中心には `liblink` の統合、Goの引数渡し規則の適用、およびエンディアンサポートの強化があります。

1.  **`liblink` への移行**:
    *   `src/cmd/9c/list.c` の内容がほぼ完全に削除されています。このファイルは、以前はアセンブリコードのリスト表示やフォーマット変換を担当していましたが、その機能は `liblink` 内の共通コードに移行されたと考えられます。これにより、`9c` はリンカの共通インフラストラクチャを利用するようになり、コードの重複が削減され、ツールチェーン全体の一貫性が向上します。
    *   `src/cmd/9c/gc.h` において、`Adr` (アドレス) および `Prog` (プログラム命令) 構造体の定義が削除されています。これは、これらの低レベルな表現が `liblink` によって提供される、より抽象的または共通のデータ構造に置き換えられたことを示唆しています。代わりに `../9l/9.out.h` がインクルードされており、これは `9l` リンカが使用する共通のオブジェクトファイルフォーマット定義を利用することを示しています。
    *   `src/cmd/9c/txt.c` では、`linkarchinit` 関数が追加され、`getgoarch()` を使用して現在のアーキテクチャ（`power64` または `power64le`）に基づいて適切なリンカアーキテクチャ (`linkpower64le` または `linkpower64`) を選択するようになりました。これは、`liblink` が提供するアーキテクチャ固有のリンキングロジックを動的にロード・利用するためのメカニズムです。また、`firstp` の初期化が削除され、`linknewplist(ctxt)` を使用して `liblink` のコンテキストでプログラムリストが管理されるようになっています。

2.  **Go引数渡し規則の適用**:
    *   `src/cmd/9c/cgen.c` では、関数呼び出しに関連するコード生成ロジックが変更されています。特に `gpcdata(PCDATA_ArgSize, curarg)` および `gpcdata(PCDATA_ArgSize, -1)` の呼び出しが追加されており、これはGoのランタイムがスタックトレースやガベージコレクションのために必要とする引数サイズのメタデータを生成していることを示しています。これにより、`9c` が生成するコードがGoのランタイムとより密接に連携し、Goの引数渡し規則に準拠するようになります。
    *   `src/cmd/9c/txt.c` の `gargs` 関数も変更され、引数レジスタの管理とスタックフレームの調整がGoの規則に合わせて行われるようになっています。

3.  **エンディアンサポートの強化**:
    *   `src/cmd/9c/cgen.c` や `src/cmd/9c/swt.c` など、複数のファイルで `align` 関数の呼び出しに `nil` (または `0`) が追加されています。これは、エンディアンに依存するアライメント計算において、より柔軟な処理を可能にするための変更である可能性があります。
    *   `src/cmd/9c/txt.c` の `linkarchinit` 関数は、`power64` と `power64le` (リトルエンディアン) の両方を明示的にサポートするように設定されており、コンパイラがターゲットシステムのエンディアン設定に応じて適切なコードを生成できるようになっています。

4.  **型定義の厳密化とクリーンアップ**:
    *   多くのファイルで `long` 型が `int32` に変更されています。これは、C言語の `long` 型がプラットフォームによってサイズが異なるという問題を回避し、常に32ビットの整数として扱うことで、データ表現の一貫性と移植性を高めるための重要な変更です。Goのランタイムや他のツールチェーンコンポーネントとのインターフェースにおいて、厳密な型サイズが要求される場合に特に重要です。
    *   `src/cmd/9c/gc.h` では、`Adr` や `Prog` 構造体の削除に加えて、`Var` 構造体も削除されています。これは、コンパイラの内部データ構造が大幅に再設計され、より効率的または共通化された表現に移行したことを示しています。
    *   多くのファイルから `// +build ignore` ディレクティブが削除されています。これは、これらのファイルがもはや開発中の実験的なコードではなく、Goのビルドシステムに正式に組み込まれ、PowerPC 64ビット向けのGoコンパイラの標準的な一部となったことを意味します。

これらの変更は、`cmd/9c` をGoのツールチェーンの他の部分とより密接に統合し、PowerPC 64ビットアーキテクチャにおけるGoの堅牢性とパフォーマンスを向上させるための基盤を築いています。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、主に以下のファイルに集中しています。

*   **`src/cmd/9c/gc.h`**:
    *   `Adr`, `Prog`, `Var` 構造体の定義が削除され、代わりに `../9l/9.out.h` がインクルードされています。
    *   多くの `long` 型の変数が `int32` に変更されています。
    *   `gtext` 関数や `argsize` 関数のプロトタイプが追加されています。
*   **`src/cmd/9c/list.c`**:
    *   ファイルの内容が大幅に削除され、`listinit9()` の呼び出しのみが残されています。これは、以前のリスト表示機能が `liblink` に移行したことを示唆しています。
*   **`src/cmd/9c/txt.c`**:
    *   `linkarchinit` 関数が追加され、`power64` と `power64le` のリンカアーキテクチャを初期化するようになりました。
    *   `ginit` 関数内で `_64BITREG` と `_64BIT` が定義されるようになりました。
    *   `firstp` の初期化ロジックが変更され、`linknewplist` を使用するようになりました。
    *   `gargs` 関数で引数レジスタの処理が変更されています。
*   **`src/cmd/9c/cgen.c`**:
    *   `gpcdata` の呼び出しが追加され、引数サイズのメタデータを生成するようになりました。
    *   `long` 型が `int32` に変更されています。
*   **`src/cmd/9c/swt.c`**:
    *   `outstring` 関数や `sextern`, `gextern` 関数など、文字列や外部データの処理に関連する部分が変更されています。特に `p->to.sval` が `p->to.u.sval` に変更されており、共用体 (`union`) の使用が示唆されます。
    *   `outcode` 関数が大幅に簡素化され、`writeobj(ctxt, &outbuf)` を呼び出すようになりました。これは、オブジェクトファイルの書き出し処理が `liblink` に委譲されたことを明確に示しています。

## コアとなるコードの解説

これらの変更は、`cmd/9c` がGoのツールチェーンのより統合された部分となるための重要なステップです。

*   **`gc.h` の変更**: `Adr`, `Prog`, `Var` 構造体の削除と `../9l/9.out.h` のインクルードは、`9c` が独自の低レベルなアドレスや命令の表現を持つのではなく、`liblink` が提供する共通のオブジェクトファイルフォーマットやデータ構造を利用するようになったことを意味します。これにより、コンパイラとリンカ間のインターフェースが標準化され、ツールチェーン全体の整合性が向上します。`long` から `int32` への変更は、Goのランタイムとのデータ表現の一貫性を保証し、プラットフォーム間の移植性を高めるための型安全性の向上です。
*   **`list.c` の削除と `outcode` の簡素化**: これは、アセンブリコードのリスト表示やオブジェクトファイルの書き出しといった機能が、`9c` 自身から `liblink` へと完全に移行したことを明確に示しています。これにより、`9c` は純粋なコンパイラとしての役割に集中し、リンキング関連の複雑なロジックは `liblink` が担当するようになります。
*   **`txt.c` の `linkarchinit` と `gargs` の変更**: `linkarchinit` の導入は、`9c` がPowerPC 64ビットのビッグエンディアンとリトルエンディアンの両方を動的にサポートするためのメカニズムを提供します。これにより、コンパイラはターゲットシステムのエンディアン設定に応じて適切なコード生成パスを選択できるようになります。`gargs` の変更は、Goの関数呼び出し規約に厳密に準拠するためのもので、引数のスタック配置やレジスタ使用がGoランタイムの期待する形式と一致するように調整されます。
*   **`cgen.c` の `gpcdata`**: `gpcdata` の呼び出しは、Goのランタイムがガベージコレクションやプロファイリングのために必要なメタデータ（例えば、関数の引数サイズ）を生成するために重要です。これにより、`9c` が生成するコードはGoのランタイムの内部動作とより密接に連携し、効率的な実行とデバッグが可能になります。
*   **`swt.c` の `p->to.u.sval`**: `p->to.sval` から `p->to.u.sval` への変更は、`Prog` 構造体内の `to` フィールドが共用体 (`union`) を使用して異なるデータ型（例えば、文字列や数値）を表現していることを示唆しています。これは、メモリ効率の向上や、異なる種類のデータに対する柔軟な処理を可能にするための設計変更です。

これらの変更は、GoのPowerPC 64ビットコンパイラを、よりモジュール化され、Goのツールチェーンの他の部分と一貫性があり、かつクロスプラットフォーム互換性の高いものにするための重要な基盤を構築しています。

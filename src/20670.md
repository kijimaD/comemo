## 元コミット内容

このコミットの目的は、Go言語の仕様における変数初期化順序に関する既存の矛盾を解消し、初期化順序を明示的に定義することです。

既存の仕様では、以下の2つのルールが矛盾していました。
1.  依存関係のある変数は、依存関係の順序で初期化される。
2.  独立した変数は、宣言順序で初期化される。

コミットメッセージでは、以下の例を用いてこの矛盾を説明しています。

```go
var (
        c = b + 2
        a = 0
        b = 1
)
```

この例では、`c` は `b` に依存するため、`b` の後に `c` が初期化される必要があります（部分的な順序: `b`, `c`）。`a` は `b` とは独立しており、`b` より前に宣言されているため、`a`, `b`, `c` の順序になります。しかし、`a` は `c` とも独立しており、`c` の後に宣言されているため、`b`, `c`, `a` の順序も有効であるべきであり、これは `a`, `b`, `c` と矛盾します。

この矛盾を解決するため、新しいルールは初期化順序を明示的に示すアルゴリズムの形式で提供されます。`gccgo` および `go/types` は既にこれらの新しいルールに従っているとのことです。

この変更は、Issue #8485 を修正します。

## 変更の背景

Go言語の初期の仕様では、パッケージレベル変数の初期化順序について、依存関係と宣言順序という2つの異なる原則を提示していました。しかし、これら2つの原則が特定のシナリオで矛盾を引き起こすことが判明しました。特に、複数の変数が互いに独立しているが、宣言順序が複雑な場合に、どの順序で初期化されるべきかがあいまいになる問題がありました。

上記のコミットメッセージの例が示すように、`a`, `b`, `c` のような変数の組み合わせでは、依存関係と宣言順序の両方を考慮すると、一意の初期化順序を決定することが困難でした。このようなあいまいさは、コンパイラの実装間で異なる挙動を引き起こす可能性があり、Goプログラムの移植性や予測可能性を損なう恐れがありました。

この問題を解決し、Go言語の挙動をより明確で予測可能なものにするために、初期化順序をアルゴリズムとして明示的に定義する必要が生じました。これにより、コンパイラの実装者は一貫した初期化ロジックを適用できるようになり、開発者は変数の初期化順序をより正確に理解できるようになります。

## 前提知識の解説

### Go言語のパッケージ初期化 (Go package initialization)

Go言語では、プログラムの実行開始前に、各パッケージの初期化が行われます。パッケージの初期化は、以下の順序で行われます。

1.  **パッケージレベル変数の初期化**: パッケージ内で宣言されたグローバル変数や定数が初期化されます。
2.  **`init` 関数の実行**: 各パッケージは、`init` という特別な関数を複数持つことができます。これらの関数は、パッケージレベル変数の初期化が完了した後に、宣言順序で実行されます。

パッケージの依存関係がある場合、依存されるパッケージが先に初期化され、その後に依存するパッケージが初期化されます。

### 変数宣言と初期化 (Variable declaration and initialization)

Go言語では、変数を宣言する際に初期値を指定できます。初期値が指定されない場合、変数はその型のゼロ値で初期化されます（例: `int` は `0`、`string` は `""`、ポインタは `nil`）。

パッケージレベル変数の初期化は、その変数が他の変数に依存しているかどうかに影響されます。

### 依存関係 (Dependencies)

Go言語の変数初期化における依存関係とは、ある変数の初期化式が別の変数の値に依存している状態を指します。例えば、`var x = y + 1` の場合、`x` は `y` に依存しています。`y` が初期化されていなければ、`x` を正しく初期化することはできません。

依存関係の解析は、変数の実際の値ではなく、ソースコード上の参照に基づいて行われます。ある変数の初期化式が、別の変数を参照する関数を呼び出す場合でも、依存関係があるとみなされます。

### 宣言順序 (Declaration order)

宣言順序とは、ソースコード内で変数が宣言された物理的な順序を指します。Go言語では、同じパッケージ内の複数のファイルにわたって変数が宣言される場合、コンパイラに提示されるファイルの順序が宣言順序に影響を与えます。

### 初期化サイクル (Initialization cycles)

初期化サイクルとは、変数の依存関係が循環している状態を指します。例えば、`A` が `B` に依存し、`B` が `A` に依存している場合、初期化サイクルが発生します。このようなサイクルが存在すると、どちらの変数も先に初期化できないため、プログラムは不正とみなされます。

## 技術的詳細

このコミットによって導入された新しいGo言語の仕様は、パッケージレベル変数の初期化順序を明確なアルゴリズムとして定義しています。これにより、以前の矛盾するルールが解消され、より予測可能で一貫性のある挙動が保証されます。

新しい初期化アルゴリズムの核心は、「初期化準備完了 (ready for initialization)」という概念と、宣言順序を優先しながら依存関係を解決する反復プロセスにあります。

1.  **初期化準備完了の定義**:
    パッケージレベル変数は、以下のいずれかの条件を満たす場合に「初期化準備完了」とみなされます。
    *   まだ初期化されていない。
    *   初期化式を持たない（この場合、ゼロ値で初期化される）。
    *   初期化式が、まだ初期化されていない変数に依存していない。

2.  **初期化プロセス**:
    初期化は、以下の手順を繰り返すことで進行します。
    *   まだ初期化されていない変数の中から、「初期化準備完了」であり、かつ宣言順序で最も早い変数を特定します。
    *   その変数を初期化します。
    *   このプロセスを、初期化準備完了の変数がなくなるまで繰り返します。

3.  **初期化サイクルの検出**:
    このプロセスが終了した時点で、まだ初期化されていない変数が残っている場合、それらの変数は1つ以上の初期化サイクルの一部であるとみなされます。このような状況は、プログラムが不正であることを意味します。これは、循環依存によって変数を初期化できないためです。

4.  **複数ファイルにわたる宣言順序**:
    複数のファイルで宣言された変数の宣言順序は、コンパイラにファイルが提示される順序によって決定されます。例えば、最初のファイルで宣言された変数は、2番目のファイルで宣言されたどの変数よりも前に宣言されたとみなされます。

5.  **ビルドシステムへの推奨**:
    再現性のある初期化挙動を保証するため、ビルドシステムは、同じパッケージに属する複数のファイルを字句順（ファイル名のアルファベット順など）でコンパイラに提示することが推奨されています。これにより、異なる環境やビルドシステムでも一貫した初期化順序が期待できます。

6.  **既存の実装との整合性**:
    コミットメッセージにもあるように、`gccgo` および `go/types` (Goの型チェッカー) は、この新しいルールが仕様に明記される前から、既にこれらの初期化ルールに従っていました。これは、新しい仕様が既存の主要なGoツールチェーンの実装と整合していることを示しています。

この変更により、Go言語の変数初期化のセマンティクスがより厳密になり、コンパイラの実装やGoプログラムの挙動の予測可能性が向上しました。

Within a package, package-level variables are initialized according

</p>

It is an error if variable dependencies form a cycle

If two variables are independent of each other,
they are initialized in the order they are declared
in the source, possibly in multiple files, as presented to the compiler.
</p>
...
<p>
the initialization order is <code>d</code>, <code>b</code>, <code>c</code>, <code>a</code>.

これらの削除された部分は、以前の矛盾するルールや、独立した変数の宣言順序に関するあいまいな記述を含んでいました。特に、`b` と `c` が独立している場合に宣言順序で初期化されるという記述は、前述の例で矛盾を引き起こす可能性がありました。

**追加された部分:**

```html
<p>
Within a package, package-level variables are initialized in
<i>declaration order</i> but after any of the variables
they <i>depend</i> on.
</p>

<p>
More precisely, a package-level variable is considered <i>ready for
initialization</i> if it is not yet initialized and either has
no <a href="#Variable_declarations">initialization expression</a> or
its initialization expression has no dependencies on uninitialized variables.
Initialization proceeds by repeatedly initializing the next package-level
variable that is earliest in declaration order and ready for initialization,
until there are no variables ready for initialization.
</p>

<p>
If any variables are still uninitialized when this
process ends, those variables are part of one or more initialization cycles,
and the program is not valid.
</p>

<p>
The declaration order of variables declared in multiple files is determined
by the order in which the files are presented to the compiler: Variables
declared in the first file are declared before any of the variables declared
in the second file, and so on.
</p>
...
<p>
To ensure reproducible initialization behavior, build systems are encouraged
to present multiple files belonging to the same package in lexical file name
order to a compiler.
</p>
```
これらの追加された部分は、新しい初期化アルゴリズムを明確に記述しています。「初期化準備完了」の概念、初期化の反復プロセス、初期化サイクルの検出、複数ファイルにわたる宣言順序の決定方法、そしてビルドシステムへの推奨事項が詳細に説明されています。

    Go言語では、1つのパッケージが複数のソースファイルに分割されることがよくあります。この変更により、複数ファイルにわたるパッケージレベル変数の宣言順序が、コンパイラにファイルが提示される順序によって決定されることが明確にされました。これは、ビルドシステムがファイルの順序をどのように扱うべきかという指針を与えます。

5.  **ビルドシステムへの推奨**:
    再現性のあるビルドを保証するために、ビルドシステムが同じパッケージのファイルを字句順でコンパイラに提示することが推奨されました。これは、異なる環境やツールチェーンでビルドしても、同じ初期化順序が保証されるようにするための重要なガイドラインです。

これらの変更は、Go言語のセマンティクスをより堅牢にし、コンパイラの実装者とGo開発者の両方にとって、変数の初期化挙動に関するあいまいさを排除することを目的としています。

### 依存関係 (Dependencies)

Go言語の変数初期化における依存関係とは、ある変数の初期化式が別の変数の値に依存している状態を指します。例えば、`var x = y + 1` の場合、`x` は `y` に依存しています。`y` が初期化されていなければ、`x` を正しく初期化することはできません。

依存関係の解析は、変数の実際の値ではなく、ソースコード上の参照に基づいて行われます。ある変数の初期化式が、別の変数を参照する関数を呼び出す場合でも、依存関係があるとみなされます。

### 宣言順序 (Declaration order)

宣言順序とは、ソースコード内で変数が宣言された物理的な順序を指します。Go言語では、同じパッケージ内の複数のファイルにわたって変数が宣言される場合、コンパイラに提示されるファイルの順序が宣言順序に影響を与えます。

### 初期化サイクル (Initialization cycles)

初期化サイクルとは、変数の依存関係が循環している状態を指します。例えば、`A` が `B` に依存し、`B` が `A` に依存している場合、初期化サイクルが発生します。このようなサイクルが存在すると、どちらの変数も先に初期化できないため、プログラムは不正とみなされます。

## 技術的詳細

このコミットによって導入された新しいGo言語の仕様は、パッケージレベル変数の初期化順序を明確なアルゴリズムとして定義しています。これにより、以前の矛盾するルールが解消され、より予測可能で一貫性のある挙動が保証されます。

新しい初期化アルゴリズムの核心は、「初期化準備完了 (ready for initialization)」という概念と、宣言順序を優先しながら依存関係を解決する反復プロセスにあります。

1.  **初期化準備完了の定義**:
    パッケージレベル変数は、以下のいずれかの条件を満たす場合に「初期化準備完了」とみなされます。
    *   まだ初期化されていない。
    *   初期化式を持たない（この場合、ゼロ値で初期化される）。
    *   初期化式が、まだ初期化されていない変数に依存していない。

2.  **初期化プロセス**:
    初期化は、以下の手順を繰り返すことで進行します。
    *   まだ初期化されていない変数の中から、「初期化準備完了」であり、かつ宣言順序で最も早い変数を特定します。
    *   その変数を初期化します。
    *   このプロセスを、初期化準備完了の変数がなくなるまで繰り返します。

3.  **初期化サイクルの検出**:
    このプロセスが終了した時点で、まだ初期化されていない変数が残っている場合、それらの変数は1つ以上の初期化サイクルの一部であるとみなされます。このような状況は、プログラムが不正であることを意味します。これは、循環依存によって変数を初期化できないためです。

4.  **複数ファイルにわたる宣言順序**:
    複数のファイルで宣言された変数の宣言順序は、コンパイラにファイルが提示される順序によって決定されます。例えば、最初のファイルで宣言された変数は、2番目のファイルで宣言されたどの変数よりも前に宣言されたとみなされます。

5.  **ビルドシステムへの推奨**:
    再現性のある初期化挙動を保証するため、ビルドシステムは、同じパッケージに属する複数のファイルを字句順（ファイル名のアルファベット順など）でコンパイラに提示することが推奨されています。これにより、異なる環境やビルドシステムでも一貫した初期化順序が期待できます。

6.  **既存の実装との整合性**:
    コミットメッセージにもあるように、`gccgo` および `go/types` (Goの型チェッカー) は、この新しいルールが仕様に明記される前から、既にこれらの初期化ルールに従っていました。これは、新しい仕様が既存の主要なGoツールチェーンの実装と整合していることを示しています。

この変更により、Go言語の変数初期化のセマンティクスがより厳密になり、コンパイラの実装やGoプログラムの挙動の予測可能性が向上しました。

## コアとなるコードの変更箇所

変更は `doc/go_spec.html` ファイルの `<h3 id="Package_initialization">Package initialization</h3>` セクションに集中しています。

具体的には、以下の部分が変更されました。

**削除された部分:**

```html
<p>
Within a package, package-level variables are initialized according
to their <i>dependencies</i>: if a variable <code>x</code> depends on
a variable <code>y</code>, <code>x</code> will be initialized after
<code>y</code>.
</p>
...
<p>
It is an error if variable dependencies form a cycle
(but dependency cycles containing no variables are permitted).
If two variables are independent of each other,
they are initialized in the order they are declared
in the source, possibly in multiple files, as presented to the compiler.
</p>
...
<p>
the initialization order is <code>d</code>, <code>b</code>, <code>c</code>, <code>a</code>.
Since <code>b</code> and <code>c</code> are independent of each other, they are
initialized in declaration order (<code>b</code> before <code>c</code>).
</p>
```
これらの削除された部分は、以前の矛盾するルールや、独立した変数の宣言順序に関するあいまいな記述を含んでいました。特に、`b` と `c` が独立している場合に宣言順序で初期化されるという記述は、前述の例で矛盾を引き起こす可能性がありました。

**追加された部分:**

```html
<p>
Within a package, package-level variables are initialized in
<i>declaration order</i> but after any of the variables
they <i>depend</i> on.
</p>

<p>
More precisely, a package-level variable is considered <i>ready for
initialization</i> if it is not yet initialized and either has
no <a href="#Variable_declarations">initialization expression</a> or
its initialization expression has no dependencies on uninitialized variables.
Initialization proceeds by repeatedly initializing the next package-level
variable that is earliest in declaration order and ready for initialization,
until there are no variables ready for initialization.
</p>

<p>
If any variables are still uninitialized when this
process ends, those variables are part of one or more initialization cycles,
and the program is not valid.
</p>

<p>
The declaration order of variables declared in multiple files is determined
by the order in which the files are presented to the compiler: Variables
declared in the first file are declared before any of the variables declared
in the second file, and so on.
</p>
...
<p>
To ensure reproducible initialization behavior, build systems are encouraged
to present multiple files belonging to the same package in lexical file name
order to a compiler.
</p>
```
これらの追加された部分は、新しい初期化アルゴリズムを明確に記述しています。「初期化準備完了」の概念、初期化の反復プロセス、初期化サイクルの検出、複数ファイルにわたる宣言順序の決定方法、そしてビルドシステムへの推奨事項が詳細に説明されています。

## コアとなるコードの解説

このコミットにおける「コアとなるコード」とは、Go言語の仕様書である `doc/go_spec.html` 内のテキスト変更を指します。これは、Go言語の挙動を定義する最も重要なドキュメントであり、この変更はGoコンパイラやその他のツールが変数の初期化をどのように扱うべきかという規範を確立します。

変更のポイントは以下の通りです。

1.  **矛盾する記述の削除と明確なアルゴリズムの導入**:
    以前の「依存関係順序」と「独立変数の宣言順序」という矛盾するルールが削除され、代わりに「初期化準備完了」という状態と、宣言順序と依存関係を組み合わせた明確なアルゴリズムが導入されました。これにより、初期化順序の決定がより厳密かつ予測可能になりました。

2.  **「初期化準備完了」の概念**:
    この新しい概念は、変数が初期化される準備ができたかどうかを判断するための基準を提供します。これにより、依存関係が解決され、かつ宣言順序が考慮された上で、どの変数を次に初期化すべきかが一意に定まります。

3.  **初期化サイクルの明示的なエラー化**:
    初期化プロセスが終了しても初期化されていない変数が残っている場合、それは初期化サイクルが存在することを示し、プログラムが不正であると明示的に定義されました。これにより、コンパイラはこのような状況をエラーとして報告することが義務付けられます。

4.  **複数ファイルにわたる宣言順序の明確化**:
    Go言語では、1つのパッケージが複数のソースファイルに分割されることがよくあります。この変更により、複数ファイルにわたるパッケージレベル変数の宣言順序が、コンパイラにファイルが提示される順序によって決定されることが明確にされました。これは、ビルドシステムがファイルの順序をどのように扱うべきかという指針を与えます。

5.  **ビルドシステムへの推奨**:
    再現性のあるビルドを保証するために、ビルドシステムが同じパッケージのファイルを字句順でコンパイラに提示することが推奨されました。これは、異なる環境やツールチェーンでビルドしても、同じ初期化順序が保証されるようにするための重要なガイドラインです。

これらの変更は、Go言語のセマンティクスをより堅牢にし、コンパイラの実装者とGo開発者の両方にとって、変数の初期化挙動に関するあいまいさを排除することを目的としています。

# [インデックス 23109] ファイルの概要

このコミットは、Go言語のリンカー内部パッケージ `cmd/internal/ld` にある `data.go` ファイルに対する変更です。このファイルは、Goプログラムのリンク処理において、シンボルやリロケーション（再配置）の処理、特にデータセクションの構築に関連する機能を提供します。具体的には、スレッドローカルストレージ（TLS）に関連するリロケーションの取り扱いを修正しています。

## 元コミット内容

`cmd/internal/ld: fix R_TLS handling now Xsym is not read from object file`

このコミットは、`Xsym` がオブジェクトファイルから読み込まれなくなったことに伴う `R_TLS` (Thread Local Storage Relocation) の処理の修正を目的としています。特にARMアーキテクチャでのビルド問題を解決すると考えられています。コミットメッセージでは、より堅牢な `tlsg` のハンドリングが今後の課題として示唆されています。

## 変更の背景

この変更の背景には、Goリンカーがオブジェクトファイルから `Xsym` シンボルを読み込まなくなったという内部的な変更があります。これにより、`R_TLS` リロケーションの処理に問題が生じ、特にARMアーキテクチャでのビルドが失敗する可能性がありました。コミットメッセージに記載されている `#10557` は、Goの公開イシュートラッカーでは見つからないため、内部的なバグトラッキングシステムのエントリであるか、あるいはプライベートな問題として扱われていた可能性があります。この問題は、GoのリンカーがTLS関連のシンボルを正しく解決できないことに起因し、外部リンキングモード（`LinkExternal`）を使用する際に顕在化したと考えられます。

## 前提知識の解説

### 1. Goリンカー (`cmd/internal/ld`)

Go言語のビルドプロセスにおいて、コンパイルされたオブジェクトファイルを結合し、実行可能ファイルを生成する役割を担うのがリンカーです。Goのリンカーは、ほとんどがGo言語自体で書かれており、`cmd/internal/ld` パッケージにその実装があります。

### 2. リロケーション (Relocation)

リロケーションとは、コンパイル時にアドレスが確定できないシンボル（変数や関数の参照など）について、リンキング時に正しいメモリアドレスを割り当てる処理のことです。オブジェクトファイルには、どの部分がリロケーションを必要とするかを示す「リロケーションエントリ」が含まれています。

### 3. `R_TLS` (Thread Local Storage Relocation)

`R_TLS` は、スレッドローカルストレージ（TLS）に格納された変数へのアクセスを解決するためのリロケーションタイプです。TLSは、各スレッド（Goにおいてはゴルーチン）が独自の変数インスタンスを持つことを可能にするメカニズムです。Goランタイムは、特にCGO（C言語との相互運用）を使用する際に、ゴルーチン固有のデータを管理するためにTLSを利用します。

### 4. `Xsym`

`Xsym` は、リロケーションのターゲットとなる外部シンボルを指す概念です。このコミットの背景にある問題は、リンカーがオブジェクトファイルからこの `Xsym` を正しく読み込めなくなったことにあります。

### 5. `LinkInternal` と `LinkExternal`

Goリンカーには、主に2つのリンクモードがあります。
*   **`LinkInternal`**: Go独自の内部リンカーを使用するデフォルトのモードです。CGOを使用しない場合や、Go標準ライブラリ内の特定のCGO依存関係に限定される場合に使用されます。生成されるバイナリは通常、静的にリンクされ、移植性が高いです。
*   **`LinkExternal`**: 外部のシステムリンカー（例: `gcc` の `ld` や `clang`）を使用するモードです。GoプログラムがCGOを介して外部のCライブラリと連携する場合に必要となります。このモードでは、生成されるバイナリが動的にリンクされることがあります。

### 6. `Iself`

`Iself` は、リンカーがELF（Executable and Linkable Format）形式のバイナリを生成しているかどうかを示すフラグです。LinuxなどのUnix系システムで広く使用される実行可能ファイル形式です。

### 7. `HEADTYPE` と `obj.Hopenbsd`

`HEADTYPE` は、生成されるバイナリのヘッダタイプ（OSの種類）を示します。`obj.Hopenbsd` は、OpenBSDオペレーティングシステム向けのヘッダタイプを指します。

### 8. `Ctxt.Tlsg`

`Ctxt` はリンカーのコンテキスト構造体で、リンク処理に関する様々な情報（アーキテクチャ、ビルドモード、シンボルなど）を保持します。`Ctxt.Tlsg` は、このコンテキスト内で `runtime.tlsg` シンボルへの参照を保持します。`runtime.tlsg` は、GoランタイムがTLSを管理するために使用する重要なシンボルであり、特にCコードとの相互作用において、現在のゴルーチンの状態（`g` ポインタ）をC関数呼び出しを跨いで維持するために利用されます。

### 9. `Thearch.Thechar == '5'`

`Thearch.Thechar` は、Goリンカーがターゲットとするアーキテクチャを内部的に識別するための単一文字の識別子です。`'5'` は、386アーキテクチャ（32ビットx86システム）を指します。コミットメッセージでARMビルドに言及されているにもかかわらず、既存のコードでこの条件があるのは、TLSの処理がアーキテクチャによって異なるためです。このコミットの変更は、既存の386向けのTLS処理とは別に、`LinkExternal` を使用する際の `R_TLS` 処理を修正するものです。

## 技術的詳細

このコミットは、Goリンカーが `R_TLS` リロケーションを処理する際のロジックを修正しています。以前のリンカーのバージョンでは、`R_TLS` リロケーションの解決に `Xsym` シンボルが使用されていましたが、リンカーの内部変更により、この `Xsym` がオブジェクトファイルから読み込まれなくなりました。この変更は、特に外部リンキングモード（`LinkExternal`）を使用し、かつELF形式のバイナリを生成する際に問題を引き起こしました。

問題の核心は、`R_TLS` リロケーションが、スレッドローカルストレージのベースアドレス（通常は `tlsg` シンボルによって表される）からのオフセットとして解決される必要がある点にあります。`Xsym` が利用できなくなったため、リンカーは `R_TLS` リロケーションを正しく解決できず、結果としてARMなどの特定のアーキテクチャでビルドエラーが発生していました。

このコミットでは、`LinkExternal` モードでELF形式のバイナリを生成し、かつOpenBSD以外のOSをターゲットとする場合に、`R_TLS` リロケーションの処理を特別にオーバーライドするロジックを追加しています。具体的には、リロケーションの `Done` フラグを0に設定し、リロケーションのターゲットシンボル (`Sym`) と外部シンボル (`Xsym`) を `Ctxt.Tlsg` に明示的に設定しています。また、リロケーションの追加オフセット (`Xadd`) を元のオフセット (`r.Add`) に設定し、最終的なオフセット (`o`) も元のオフセットに設定しています。これにより、リンカーは `Xsym` がオブジェクトファイルから読み込まれない状況でも、`tlsg` シンボルを基準として `R_TLS` リロケーションを正しく解決できるようになります。

この修正は、`tlsg` のハンドリングをより堅牢にするための暫定的な措置であり、コミットメッセージにもあるように、将来的にはより根本的な解決策が検討されていました。

## コアとなるコードの解説

追加されたコードは、`obj.R_TLS` リロケーションタイプを処理する `case` ブロックの先頭に挿入されています。

```go
			if Linkmode == LinkExternal && Iself && HEADTYPE != obj.Hopenbsd {
				r.Done = 0
				r.Sym = Ctxt.Tlsg
				r.Xsym = Ctxt.Tlsg
				r.Xadd = r.Add
				o = r.Add
				break
			}
```

この `if` 文は以下の条件をチェックします。
*   `Linkmode == LinkExternal`: リンカーが外部リンキングモードで動作しているか。
*   `Iself`: 生成されるバイナリがELF形式であるか。
*   `HEADTYPE != obj.Hopenbsd`: ターゲットOSがOpenBSDではないか。

これらの条件がすべて真である場合、つまり、外部リンカーを使用してELF形式のバイナリをOpenBSD以外のシステム向けにビルドしている場合に、以下の処理が実行されます。

*   `r.Done = 0`: リロケーションがまだ完了していないことを示します。これにより、リンカーは後続の処理でこのリロケーションを再度考慮するようになります。
*   `r.Sym = Ctxt.Tlsg`: リロケーションのターゲットシンボルを `Ctxt.Tlsg` に設定します。これは `runtime.tlsg` シンボルを指し、TLSのベースアドレスを提供します。
*   `r.Xsym = Ctxt.Tlsg`: 外部シンボルも `Ctxt.Tlsg` に設定します。これは、`Xsym` がオブジェクトファイルから読み込まれない問題への直接的な対処です。
*   `r.Xadd = r.Add`: リロケーションの追加オフセットを、元のリロケーションのオフセット (`r.Add`) に設定します。
*   `o = r.Add`: 最終的なオフセットも元のリロケーションのオフセットに設定します。
*   `break`: この `case` ブロックの残りの処理（既存の `LinkInternal` かつ386アーキテクチャ向けのTLS処理など）をスキップし、次のリロケーションの処理に移ります。

この変更により、`Xsym` が利用できない状況でも、`R_TLS` リロケーションが `tlsg` シンボルを基準として正しく解決されるようになり、特にARMアーキテクチャでの外部リンキング時のビルド問題が解消されました。

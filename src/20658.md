# [インデックス 20658] ファイルの概要

このコミットは、Go言語の`cmd/yacc`ツールにおける文字トークンの解析方法を修正するものです。具体的には、シングルクォートとダブルクォートで囲まれた文字リテラルの扱いを改善し、Go言語の文字列リテラルの意味論と一致させることを目的としています。

    cmd/yacc: fix parsing of character tokens
    
    From issue 7967 I learned:
    
    1) yacc accepts either 'x' or "x" to mean token value 0x78
    2) yacc also accepts 'xyz' and "XYZ" to mean token value 0x78
    
    Use strconv.Unquote to simplify the handling of quoted
    strings and check that each has only one rune.
    
    Although this does clean things up, it makes 'x' and "x"
    treated as different internally (now they are stored as
    `'x'` and `"`x`"; before they were both ` x`). Grammars that
    use both interchangeably will now die with an error
    similar to the one from issue 7967:
    
            yacc bug -- cannot have 2 different Ts with same value
                    "+" and '+'
    
    The echoingﾞ of the quotes should make clear what is going on.
    
    The other semantic change caused by using strconv.Unquote
    is that '\"' and "\"'" are no longer valid. Like in Go, they must be
    spelled without the backslash: '"' and "'".
    
    On the other hand, now yacc and Go agree about what character
    and string literals mean.

## 元コミット内容

`cmd/yacc`: 文字トークンの解析を修正

Issue 7967から学んだこと：

1) yaccはトークン値0x78を意味するために `'x'` または `"x"` のいずれかを受け入れる。
2) yaccは `'xyz'` および `"XYZ"` もトークン値0x78を意味するために受け入れる。

引用符で囲まれた文字列の処理を簡素化し、それぞれが1つのルーンのみを持つことを確認するために `strconv.Unquote` を使用する。

これにより処理は整理されるが、`'x'` と `"x"` は内部的に異なるものとして扱われるようになる（以前は両方とも ` x` として保存されていたが、今後はそれぞれ ``'x'`` と ``"x"`` として保存される）。両方を区別なく使用する文法は、Issue 7967と同様のエラーで終了するようになる：

        yacc bug -- cannot have 2 different Ts with same value
                "+" and '+'

引用符のエコー表示により、何が起こっているのかが明確になるはずである。

`strconv.Unquote` を使用することによるもう一つの意味的な変更は、`'\"'` と `\"'` がもはや有効ではなくなることである。Goと同様に、これらはバックスラッシュなしで記述されなければならない：`'"'` と `"'"`。

一方で、yaccとGoは文字リテラルと文字列リテラルの意味について合意するようになる。

## 変更の背景

このコミットの背景には、`cmd/yacc` が文字トークンを解析する際の既存の曖昧さと不整合がありました。具体的には、以下の2点が問題として挙げられています。

1.  **シングルクォートとダブルクォートの区別がない**: `yacc` は `'x'` と `"x"` の両方を同じトークン値（この場合はASCII値の0x78）として扱っていました。これは、Go言語の文字列リテラルと文字リテラルの区別とは異なり、混乱を招く可能性がありました。Goでは `'x'` はruneリテラルであり、`"x"` は文字列リテラルです。
2.  **複数文字リテラルの誤った解釈**: `yacc` は `'xyz'` や `"XYZ"` のような複数文字のリテラルも、最初の文字のトークン値として解釈していました。これは、意図しない動作を引き起こす可能性があり、特にエラー検出の観点から問題がありました。

これらの問題は、Goの標準ライブラリである`strconv.Unquote`の導入によって解決され、`yacc`の文字トークン解析をGo言語の文字列・文字リテラルのセマンティクスに合わせることで、より堅牢で予測可能な挙動を実現することが目的とされました。特に、Issue 7967で報告されたような「同じ値を持つ2つの異なるトークンが存在する」というバグ（例: `"+"` と `'+'` が同じトークン値として扱われる）を解消することが、この変更の重要な動機となっています。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

*   **Yacc (Yet Another Compiler Compiler)**: Yaccは、文法定義から構文解析器（パーサー）を生成するツールです。C言語で書かれたプログラムの構文解析器を生成するためによく使用されます。Go言語の`cmd/yacc`は、Go言語で書かれた構文解析器を生成するためのYaccの実装です。Yaccでは、トークン（字句解析器によって識別される最小単位）を定義し、それらのトークンがどのように組み合わされて文法構造を形成するかを記述します。
*   **トークンとリテラル**:
    *   **トークン**: プログラミング言語のソースコードにおける意味を持つ最小単位です。例えば、キーワード（`if`, `for`）、識別子（変数名）、演算子（`+`, `-`）、リテラル（数値、文字列、文字）などがあります。
    *   **文字リテラル**: 単一の文字を表すリテラルです。Go言語ではシングルクォート（`'`）で囲みます（例: `'a'`, `'世'`）。その値は対応するUnicodeコードポイント（rune）です。
    *   **文字列リテラル**: ゼロ個以上の文字のシーケンスを表すリテラルです。Go言語ではダブルクォート（`"`）で囲みます（例: `"hello"`, `"Go"`）。
*   **エスケープシーケンス**: 文字列や文字リテラル内で特殊な意味を持つ文字を表現するために使用される文字の組み合わせです。例えば、改行を表す `\n`、タブを表す `\t`、バックスラッシュ自体を表す `\\` などがあります。
*   **UnicodeとUTF-8**:
    *   **Unicode**: 世界中の文字を統一的に扱うための文字コード標準です。各文字に一意のコードポイントを割り当てます。
    *   **UTF-8**: Unicodeのコードポイントを可変長バイトでエンコードするための方式です。Go言語の文字列はUTF-8でエンコードされています。
    *   **Rune**: Go言語では、Unicodeのコードポイントを表現するために `rune` 型が使用されます。これは `int32` のエイリアスです。
*   **`strconv.Unquote`**: Go言語の標準ライブラリ `strconv` パッケージに含まれる関数です。この関数は、Goの文字列リテラルまたは文字リテラルとして引用符で囲まれた文字列を解析し、その引用符を外し、エスケープシーケンスを解釈した「生の」文字列を返します。例えば、`strconv.Unquote(`"hello\\nworld"`)` は `"hello\nworld"` を返します。この関数は、Go言語の仕様に厳密に従って引用符とエスケープシーケンスを処理します。

## 技術的詳細

このコミットの技術的な核心は、`cmd/yacc` が文字トークンを解析する際に、手動でのエスケープシーケンス処理とUTF-8デコードを廃止し、Go言語の標準ライブラリである `strconv.Unquote` を利用するように変更した点にあります。

**変更前のアプローチの問題点:**

変更前の `cmd/yacc` の `defin` 関数では、文字リテラル（例: `'x'` や `"x"`）を解析する際に、以下のような手動の処理が行われていました。

1.  **引用符の除去**: まず、先頭の引用符（シングルクォートまたはダブルクォート）を単純に除去していました。
2.  **UTF-8デコード**: `unicode/utf8` パッケージの `DecodeRuneInString` を使用して、文字列の最初のルーンをデコードしていました。
3.  **エスケープシーケンスの手動処理**: バックスラッシュ（`\`）で始まるエスケープシーケンス（例: `\n`, `\t`, `\\`, `\'`, `\"`, `\uXXXX`, `\UXXXXXXXX`）を、巨大な `switch` 文と手動のロジックで一つ一つ解釈していました。

この手動での処理には、以下のような問題がありました。

*   **複雑性**: エスケープシーケンスの解釈ロジックが複雑で、バグの温床となりやすかった。
*   **Go言語との不整合**: Go言語の文字列・文字リテラルの仕様と完全に一致している保証がなく、特にGoの新しいエスケープシーケンスが追加された場合などに追従が困難でした。
*   **曖昧な解釈**: `'x'` と `"x"` のような異なる引用符で囲まれたリテラルが、内部的に同じ表現（` x`）として扱われていたため、文法定義でこれらを区別なく使用すると、`yacc`が「同じ値を持つ2つの異なるトークン」として誤って認識し、エラーを発生させる原因となっていました。また、`'xyz'` のような複数文字のリテラルも、最初の文字のみが解釈され、残りの文字は無視されていました。

**`strconv.Unquote` の導入による解決:**

このコミットでは、これらの問題を解決するために `strconv.Unquote` が導入されました。

1.  **統一された引用符解除とエスケープ処理**: `strconv.Unquote` は、Go言語の文字列リテラルおよび文字リテラルの仕様に厳密に従って、引用符の解除とエスケープシーケンスの解釈を自動的に行います。これにより、手動での複雑な処理が不要になり、コードが大幅に簡素化されました。
2.  **単一ルーンの強制**: `strconv.Unquote` で引用符を解除した後、結果の文字列が単一のルーン（`len(rq) != 1`）であるかを厳密にチェックするようになりました。これにより、`'xyz'` のような複数文字のリテラルが誤って単一文字として解釈されることを防ぎ、適切なエラー（`character token too long`）を発生させるようになりました。
3.  **Go言語とのセマンティクスの一致**: `strconv.Unquote` を使用することで、`yacc` が文字トークンを解釈する際のセマンティクスがGo言語のそれと完全に一致するようになりました。これにより、Goのコードと`yacc`の文法定義の間で、文字リテラルの意味に関する混乱がなくなります。

**導入による影響と注意点:**

*   **内部表現の変更**: 以前は `'x'` と `"x"` が内部的に同じ ` x` として扱われていましたが、変更後は `strconv.Unquote` の結果をそのまま使用するため、`'x'` は `'x'`、`"x"` は `"x"` というように、引用符の種類を含んだ形で内部的に区別されるようになりました。
*   **既存文法への影響**: この内部表現の変更により、既存の`yacc`文法で `'x'` と `"x"` を区別なく使用していた場合、`yacc`が「同じ値を持つ2つの異なるトークン」として認識し、エラー（`yacc bug -- cannot have 2 different Ts with same value`）を発生させる可能性があります。これは、`yacc`がより厳密になった結果であり、文法定義の曖昧さを解消するためのものです。
*   **エスケープシーケンスの厳格化**: `strconv.Unquote` の仕様により、`'\"'` や `\"'` のような、バックスラッシュで引用符をエスケープする形式は無効になりました。Go言語と同様に、これらはバックスラッシュなしで `'` や `"` と記述する必要があります。

これらの変更は、`cmd/yacc` の堅牢性とGo言語との整合性を高める上で非常に重要です。

## コアとなるコードの解説

このコミットでは、主に以下の3つの関数が変更されています。

1.  **`defin` 関数**:
    *   **変更前**: 文字リテラル（`'x'` や `"x"` のような形式）を解析する際に、手動で引用符を外し、`unicode/utf8` を使ってルーンをデコードし、さらに複雑な `switch` 文でエスケープシーケンス（`\n`, `\t`, `\\`, `\'`, `\"`, `\uXXXX`, `\UXXXXXXXX` など）を処理していました。特に、`' '` で始まる文字列（内部的に引用符が外された状態）をチェックしていました。
    *   **変更後**: `unicode/utf8` のインポートが削除され、代わりに `strconv` がインポートされました。文字リテラルの処理は大幅に簡素化され、`s[0] == '\'' || s[0] == '"'` で引用符で始まる文字列をチェックするようになりました。そして、`strconv.Unquote(s)` を呼び出して、引用符の解除とエスケープシーケンスの解釈を `strconv` パッケージに任せています。
        *   `strconv.Unquote` がエラーを返した場合（不正なリテラル形式など）、`errorf("invalid token: %s", err)` でエラーを報告します。
        *   引用符を解除した結果の文字列 `q` を `[]rune(q)` でルーンのスライスに変換し、`len(rq) != 1` でルーンが1つだけであることを厳密にチェックします。もし複数ルーンであった場合（例: `'xyz'`）、`errorf("character token too long: %s", s)` でエラーを報告します。
        *   最終的に、単一ルーンの値を `val = int(rq[0])` として取得します。
        *   `val == 0` のチェックは変更されていません。

    この変更により、文字リテラルの解析ロジックが大幅に簡素化され、Go言語の文字列・文字リテラルのセマンティクスと一致するようになりました。

2.  **`gettok` 関数**:
    *   **変更前**: 文字リテラルを読み取る際に、`tokname = " "` と初期化していました。これは、内部的に引用符が外された形式でトークン名を保持しようとしていたためです。
    *   **変更後**: `tokname = string(c)` と初期化するようになりました。ここで `c` は読み取った最初の引用符（`'` または `"`）です。これにより、トークン名が引用符を含んだ形で保持されるようになります。また、ループ内で `tokname += string(c)` が追加され、引用符で囲まれた文字列全体が `tokname` に含まれるようになりました。
    この変更は、`'x'` と `"x"` を内部的に区別するために必要です。

3.  **`chfind` 関数**:
    *   **変更前**: `if s[0] == ' '` で、内部的に引用符が外された形式のトークン名をチェックしていました。
    *   **変更後**: `if s[0] == '"' || s[0] == '\''` で、引用符で始まるトークン名をチェックするようになりました。これは `gettok` の変更と整合性を保つためのものです。

4.  **`symnam` 関数**:
    *   **変更前**: `if s[0] == ' ' { s = s[1:] }` という行があり、内部的に引用符が外されたトークン名の先頭のスペースを除去していました。
    *   **変更後**: この行が削除されました。これは、`gettok` と `defin` の変更により、トークン名が引用符を含んだ形で保持されるようになったため、この手動でのスペース除去が不要になったためです。

これらの変更により、`cmd/yacc` は文字トークンをより正確かつGo言語のセマンティクスに沿って処理できるようになりました。

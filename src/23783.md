## 元コミット内容

`encoding/asn1: check bounds when parsing tag and length`

このコミットは、`encoding/asn1` パッケージにおいて、タグと長さをパースする際の境界チェックを追加します。
この問題は、別のプログラムをファジングしている際に発見され、`x509.ParseECPrivateKey` でパニックを引き起こしました。
Issue #11154 を修正します。

## 変更の背景

この変更は、Go言語の `encoding/asn1` パッケージが、特に不正な形式のASN.1データ（DERエンコーディング）を処理する際に、予期せぬパニックを引き起こす可能性があったことに起因します。具体的には、ファジング（fuzzing）というテスト手法を用いて、`x509.ParseECPrivateKey` 関数（これは内部で `encoding/asn1` を利用してX.509証明書や鍵のASN.1構造を解析します）にランダムな入力データを大量に与えていた際に、特定の不正な入力がパニックを誘発することが判明しました。

問題の核心は、ASN.1の「明示的タグ（explicit tag）」が、その内容（子要素）を持たない場合に、`encoding/asn1` パッケージが子要素のタグと長さを読み取ろうとして、バイトスライス（`[]byte`）の範囲外アクセス（out-of-bounds access）を引き起こしていた点にあります。これにより、プログラムがクラッシュする可能性がありました。このような脆弱性は、サービス拒否（DoS）攻撃や、場合によってはより深刻なセキュリティ問題につながる可能性があるため、早急な修正が必要とされました。

## 前提知識の解説

### ASN.1 (Abstract Syntax Notation One) と DER (Distinguished Encoding Rules)

*   **ASN.1**: 抽象構文記法1（Abstract Syntax Notation One）は、データ構造を記述するための国際標準です。異なるシステム間でデータを交換する際に、データの形式を明確に定義するために使用されます。例えば、X.509証明書、PKCS#12ファイル、LDAPプロトコルなどで広く利用されています。
*   **DER**: 識別符号化規則（Distinguished Encoding Rules）は、ASN.1で定義されたデータ構造をバイト列にエンコードするための特定の規則セットです。DERの重要な特性は、任意のASN.1値に対して一意のバイト列表現を保証することです。これにより、データの整合性チェックやデジタル署名などで利用されます。

### TLV (Tag-Length-Value) エンコーディング

DERエンコーディングの基本的な構造は、TLV（Tag-Length-Value）形式です。
*   **Tag (タグ)**: データの種類（例: INTEGER, OCTET STRING, SEQUENCE）を識別します。タグは、クラス（Universal, Application, Context-specific, Private）とフォーム（Primitive, Constructed）の情報も持ちます。
*   **Length (長さ)**: Valueフィールドのバイト長を示します。
*   **Value (値)**: 実際のデータ内容です。

### 明示的タグ (Explicit Tagging)

ASN.1では、型にタグを付けることができます。特に「明示的タグ」は、ある型を別のタグでラップする（包み込む）メカニズムです。例えば、`[0] EXPLICIT INTEGER` は、INTEGER型の値がコンテキスト固有のタグ0で囲まれていることを意味します。これは、DERバイト列において、元のINTEGERのTLV構造の外側に、さらにタグ0のTLV構造が追加されることを意味します。この追加されたタグ0のValue部分が、元のINTEGERのTLV全体になります。

### ファジング (Fuzzing)

ファジングは、ソフトウェアテストの一種で、プログラムに無効な、予期しない、またはランダムなデータを入力として与え、クラッシュ、メモリリーク、アサーション失敗などのバグや脆弱性を発見する手法です。このコミットの背景にある問題も、ファジングによって発見されました。

### Go言語の `encoding/asn1` パッケージ

Go言語の標準ライブラリ `encoding/asn1` は、ASN.1 DERエンコーディングされたデータをGoの構造体と相互に変換するための機能を提供します。このパッケージは、X.509証明書や暗号鍵の処理など、セキュリティ関連の多くのGoプログラムで利用されています。

## 技術的詳細

このコミットは、`encoding/asn1` パッケージ内の2つの主要な関数 `parseTagAndLength` と `parseField` に境界チェックを追加することで、不正なASN.1入力に対する堅牢性を高めています。

1.  **`parseTagAndLength` 関数における境界チェックの追加**:
    *   この関数は、ASN.1のTLV構造の「Tag」と「Length」部分をバイト列から読み取る役割を担っています。
    *   変更前は、この関数が呼び出された際に、入力バイトスライス `bytes` の `offset` が `len(bytes)` 以上であるかどうかのチェックがありませんでした。
    *   コミットでは、`if offset >= len(bytes)` というチェックが追加されました。もし `offset` がバイトスライスの範囲外を指している場合、`"asn1: internal error in parseTagAndLength"` というエラーを返します。
    *   コメントには「`parseTagAndLength` は少なくとも1バイトを読み取るために呼び出されるべきではない」とあり、このチェックは堅牢性のためのものであることが示されています。これは、通常の使用ではこのエラーパスには到達しないはずだが、予期せぬ状況（例えば、呼び出し元のバグ）に備えるものです。

2.  **`parseField` 関数における明示的タグの子要素チェックの追加**:
    *   `parseField` 関数は、Goの構造体のフィールドに対応するASN.1要素をパースする際に使用されます。特に、明示的タグ（`asn1:"explicit,tag:X"`）を持つフィールドの処理に関わります。
    *   明示的タグは、そのタグのValue部分にさらに別のTLV構造（子要素）を持つことが期待されます。
    *   変更前は、明示的タグが検出された後、そのValue部分が空である（つまり、子要素が存在しない）場合に、`parseTagAndLength` を呼び出して子要素のタグと長さを読み取ろうとしていました。この際、`offset` がバイトスライスの末尾に達しているにもかかわらず読み取りを試みるため、範囲外アクセスが発生しパニックを引き起こしていました。
    *   コミットでは、明示的タグの処理中に `if offset == len(bytes)` というチェックが追加されました。これは、明示的タグのValue部分を読み取る前に、現在のオフセットがバイトスライスの末尾に達しているかどうかを確認するものです。
    *   もし末尾に達している場合、それは明示的タグが子要素を持たない不正な形式であることを意味するため、`StructuralError{"explicit tag has no child"}` というエラーを返します。これにより、パニックを回避し、より適切なエラー処理が行われるようになります。

これらの変更により、`encoding/asn1` パッケージは、不正な形式のASN.1データ、特に明示的タグが不完全にエンコードされている場合に、より安全にエラーを報告できるようになりました。

## コアとなるコードの解説

### `src/encoding/asn1/asn1.go` の変更点

1.  **`import "errors"` の追加**:
    *   新しいエラー `errors.New` を使用するために、`errors` パッケージがインポートされました。

2.  **`parseTagAndLength` 関数内の変更**:
    *   `offset = initOffset` の直後に、`if offset >= len(bytes)` という条件が追加されました。
    *   これは、`parseTagAndLength` が呼び出された時点で、既に `bytes` スライスから読み取るべきデータが残っていない（または `offset` がスライスの範囲外を指している）場合に、パニックを回避するためのチェックです。
    *   この条件が真の場合、`"asn1: internal error in parseTagAndLength"` というエラーを返して関数を終了します。これにより、後続の `bytes[offset]` アクセスが安全になります。

3.  **`parseField` 関数内の変更**:
    *   明示的タグを処理するロジック内で、`if offset == len(bytes)` という条件が追加されました。
    *   これは、明示的タグのタグと長さを読み取った後、そのValue部分（子要素）を読み取る直前に、入力バイトスライスが既に終了しているかどうかを確認するものです。
    *   もし `offset` が `len(bytes)` と等しい場合、それは明示的タグが子要素を持たない不正な形式であることを意味します。この場合、`StructuralError{"explicit tag has no child"}` というエラーを返します。これにより、存在しない子要素をパースしようとして発生するパニックを防ぎます。

### `src/encoding/asn1/asn1_test.go` の変更点

1.  **`truncatedExplicitTagTest` 構造体の追加**:
    *   `Test int \`asn1:"explicit,tag:0"\` というフィールドを持つ構造体が定義されました。これは、明示的タグ `0` を持つ整数型 `Test` を表します。この構造体は、明示的タグのパースロジックをテストするために使用されます。

2.  **`TestTruncatedExplicitTag` テスト関数の追加**:
    *   このテストは、過去に `Unmarshal` 関数でクラッシュを引き起こした特定のシナリオを再現します（Issue #11154）。
    *   `der` というバイトスライスが定義されています。これは、以下のような不正なASN.1 DERエンコーディングを表します。
        *   `0x30`: SEQUENCEタグ
        *   `0x02`: 長さ2バイト
        *   `0xa0`: コンテキスト固有のタグ0（明示的タグ）
        *   `0x30`: 長さ48バイト（これは実際には明示的タグの子要素の長さではなく、不正なデータ）
    *   この `der` データは、SEQUENCEの長さが2バイトであると宣言しているにもかかわらず、その後にコンテキスト固有のタグ0（`0xa0`）が続き、そのタグの子要素が期待されるべき場所で、不正な長さバイト（`0x30`）が来ています。この `0x30` は、明示的タグの子要素のタグではなく、長さとして解釈されるべきものでもありません。この不正な構造が、`parseField` が子要素を読み取ろうとした際に `offset == len(bytes)` の条件に合致し、`explicit tag has no child` エラーを発生させることを期待しています。
    *   `Unmarshal(der, &result)` を呼び出し、エラーが返されることを期待しています。もしエラーが返されなかった場合（つまり、パニックが発生しなかったが、不正なデータが誤ってパースされた場合）、テストは失敗します。
    *   このテストケースの追加により、修正が正しく機能し、不正な明示的タグが与えられた際にパニックではなくエラーが返されることが保証されます。

これらの変更は、Goの `encoding/asn1` パッケージの堅牢性を大幅に向上させ、特にセキュリティ関連のアプリケーションにおいて、不正な入力データに対する耐性を高めるものです。

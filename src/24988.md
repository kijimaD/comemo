# [インデックス 24988] ファイルの概要

このコミットは、Goランタイムにおけるシグナルハンドリングの挙動を修正し、特にCgoを介してglibcの関数（`setgid`など）を使用する際の潜在的なハングアップ問題を解決します。具体的には、`os/signal.Notify`がアクティブな場合に、glibcが内部的に使用する特定のシグナル（`SIGCANCEL`と`SIGSETXID`）が誤ってマスクされてしまう問題を解消します。これにより、GoプログラムとCライブラリの連携がより堅牢になります。

## 元コミット内容

```
runtime: unblock special glibc signals on each thread

Glibc uses some special signals for special thread operations. These
signals will be used in programs that use cgo and invoke certain glibc
functions, such as setgid. In order for this to work, these signals
need to not be masked by any thread. Before this change, they were
being masked by programs that used os/signal.Notify, because it
carefully masks all non-thread-specific signals in all threads so that a
dedicated thread will collect and report those signals (see ensureSigM
in signal1_unix.go).

This change adds the two glibc special signals to the set of signals
that are unmasked in each thread.

Fixes #12498.

Change-Id: I797d71a099a2169c186f024185d44a2e1972d4ad
Reviewed-on: https://go-review.googlesource.com/14297
Reviewed-by: David Crawshaw <crawshaw@golang.org>
```

## 変更の背景

GoプログラムがCgoを介してglibc（GNU C Library）の関数を呼び出す際、特定の状況下でプログラムがハングアップするという問題が発生していました。特に、`os/signal.Notify`を使用してGoのシグナルハンドリングを有効にしているプログラムで、`setgid`のようなglibcの関数を呼び出すと、その関数が完了せずに停止してしまうことが報告されていました（Issue #12498）。

この問題の根本原因は、Goランタイムの`os/signal.Notify`の内部実装にありました。`os/signal.Notify`は、Goプログラムがシグナルを安全かつGoらしい方法で処理できるようにするために、スレッド固有ではない（非同期的な）シグナルをすべてのGoスレッドでマスクし、専用のGoルーチン（`ensureSigM`によって管理される）がそれらのシグナルを収集・報告するように設計されています。この設計はGoのシグナル処理を簡素化する一方で、glibcが内部的に使用する特定の「特殊な」シグナルまでマスクしてしまっていました。

glibcは、スレッド操作のために`SIGCANCEL`と`SIGSETXID`という2つのリアルタイムシグナルを内部的に利用します。これらのシグナルは、`pthread_cancel`によるスレッドのキャンセルや、`setuid`/`setgid`のようなID設定関数がマルチスレッド環境で正しく動作するために不可欠です。これらのシグナルがマスクされていると、glibcの内部処理がブロックされ、結果として`setgid`などの関数がハングアップする原因となっていました。

このコミットは、この問題を解決するために、`SIGCANCEL`と`SIGSETXID`を`os/signal.Notify`がマスクしないシグナルのリストに追加することで、Goランタイムとglibcの間のシグナルハンドリングの競合を解消することを目的としています。

## 前提知識の解説

### 1. シグナル (Signals)

Unix系OSにおけるシグナルは、プロセスに対して非同期的にイベントを通知するメカニズムです。例えば、`SIGINT`（Ctrl+C）はプログラムの終了を要求し、`SIGSEGV`はセグメンテーション違反を通知します。プロセスはシグナルを受け取ると、デフォルトの動作を実行するか、カスタムのシグナルハンドラを呼び出すか、シグナルを無視することができます。

### 2. シグナルマスク (Signal Mask)

各スレッドは、自身が受け取るシグナルのセットを制御するための「シグナルマスク」を持っています。シグナルマスクに含まれるシグナルは、そのスレッドに対して「ブロック」され、配信が保留されます。シグナルがブロックされている間に発生した場合、そのシグナルはスレッドのシグナルマスクから削除されるまで配信されません。

### 3. glibc (GNU C Library)

glibcは、Linuxシステムで広く使用されている標準Cライブラリの実装です。システムコールへのインターフェース、文字列操作、メモリ管理、スレッド管理（pthreads）など、多くの基本的な機能を提供します。glibcは、その内部動作のために特定のシグナルを予約し、利用することがあります。

### 4. `SIGCANCEL` と `SIGSETXID`

これらはglibcが内部的に使用する特殊なリアルタイムシグナルです。
*   **`SIGCANCEL`**: 主に`pthread_cancel()`によるスレッドのキャンセル処理に使用されます。スレッドがキャンセルされるべきであることを通知するために、ターゲットスレッドに送信されます。
*   **`SIGSETXID`**: `setuid()`や`setgid()`のようなユーザー/グループIDを設定する関数が、マルチスレッド環境で正しく動作するために使用されます。これらの関数は、ID変更がプロセス全体にわたって一貫して適用されるように、他のスレッドに通知する必要がある場合があります。

これらのシグナルは、アプリケーション開発者が直接扱うことを意図したものではなく、glibcの内部実装の詳細です。しかし、これらがマスクされるとglibcの機能が正常に動作しなくなる可能性があります。

### 5. Goの `os/signal` パッケージ

Go言語の`os/signal`パッケージは、GoプログラムがOSシグナルを処理するためのGoらしいインターフェースを提供します。`signal.Notify`関数を使用すると、特定のシグナルがGoチャネルに送信されるように設定できます。これにより、Goルーチン内でシグナルを非同期的に処理できるようになります。

`os/signal.Notify`の内部では、Goランタイムがシグナルハンドラをインストールし、シグナルマスクを管理します。特に、Goランタイムは、Goルーチンがシグナルを安全に処理できるように、ほとんどのシグナルをGoスレッドでマスクし、専用のシグナル処理スレッド（またはGoルーチン）にシグナルをルーティングします。

### 6. Cgo

Cgoは、GoプログラムからC言語のコードを呼び出すためのGoの機能です。Cgoを使用すると、GoとCのコードが同じプロセス空間で実行されます。このため、シグナルハンドリングのようなOSレベルのリソース管理において、GoランタイムとCライブラリ（glibcなど）の間で協調が必要になります。

### 7. `setgid` システムコール

`setgid()`は、プロセスの実効グループID (effective group ID) を変更するシステムコールです。これにより、プロセスがファイルシステムや他のリソースにアクセスする際の権限が変更されます。セキュリティ上重要な操作であり、マルチスレッド環境では、この変更がプロセス内のすべてのスレッドに適切に反映される必要があります。glibcは、この操作を正しく実行するために`SIGSETXID`のような内部シグナルを利用することがあります。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムがどのようにシグナルを管理し、それがglibcの内部シグナルとどのように衝突していたか、そしてその解決策にあります。

Goランタイムは、`os/signal.Notify`が呼び出されると、`signal1_unix.go`内の`ensureSigM`関数などを通じて、シグナルハンドリングのセットアップを行います。このセットアップの一環として、Goランタイムは、Goスレッドが予期せぬシグナルによって中断されないように、ほとんどのシグナルを各Goスレッドのシグナルマスクに追加します。これにより、シグナルは専用のGoルーチンによって一元的に処理されるようになります。

しかし、この「ほとんどのシグナルをマスクする」というアプローチが、glibcが内部的に使用する`SIGCANCEL`と`SIGSETXID`にも適用されてしまっていました。これらのシグナルは、glibcの`pthread`ライブラリがスレッドのキャンセルやユーザー/グループIDの変更といった重要な操作を調整するために不可欠です。これらのシグナルがマスクされると、glibcは必要な内部通信を行うことができず、結果として関連する関数（例: `setgid`）がブロックされ、ハングアップ状態に陥っていました。

このコミットは、`src/runtime/signal_linux.go`内の`sigtable`という配列を変更することで、この問題を解決します。`sigtable`は、各シグナル番号に対応するGoランタイムのシグナル処理フラグを定義しています。変更前は、シグナル32（`SIGCANCEL`に相当）とシグナル33（`SIGSETXID`に相当）には`_SigSetStack`フラグのみが設定されていました。`_SigSetStack`は、シグナルハンドラが代替シグナルスタックで実行されるべきであることを示しますが、シグナルがマスクされるかどうかには直接影響しません。

このコミットでは、これらのシグナルに`_SigUnblock`フラグが追加されます。`_SigUnblock`フラグは、Goランタイムがシグナルマスクを設定する際に、このシグナルを明示的にマスク解除する（つまり、シグナルマスクから除外する）ように指示します。これにより、`os/signal.Notify`がアクティブな場合でも、`SIGCANCEL`と`SIGSETXID`はGoスレッドのシグナルマスクから除外され、glibcがこれらのシグナルを自由に送受信できるようになります。結果として、`setgid`のようなglibc関数がハングアップすることなく、GoプログラムとCgoが共存できるようになります。

また、`misc/cgo/test/setgid_linux.go`には、この修正が正しく機能することを確認するためのテストケースが追加されています。このテストは、`setgid(0)`を呼び出す前に`signal.Notify`を使用した場合と使用しない場合の両方で`setgid`がハングアップしないことを検証します。これにより、`os/signal.Notify`がアクティブな状態でも`setgid`が正常に動作することが保証されます。

## コアとなるコードの解説

### `src/runtime/signal_linux.go` の変更

`sigtable`は、GoランタイムがLinuxシステム上の各シグナルに対してどのように振る舞うべきかを定義する重要なデータ構造です。各エントリは`sigTabT`型で、シグナルに関連するフラグと説明文字列を含みます。

変更前:
```go
/* 32 */ {_SigSetStack, "signal 32"}, /* SIGCANCEL; see issue 6997 */
/* 33 */ {_SigSetStack, "signal 33"}, /* SIGSETXID; see issue 3871, 9400 */
```
ここでは、シグナル32と33に対して`_SigSetStack`フラグのみが設定されていました。これは、これらのシグナルに対するハンドラが代替シグナルスタックで実行されるべきであることを示します。しかし、このフラグだけでは、`os/signal.Notify`がアクティブなときにこれらのシグナルがマスクされるのを防ぐことはできませんでした。

変更後:
```go
/* 32 */ {_SigSetStack + _SigUnblock, "signal 32"}, /* SIGCANCEL; see issue 6997 */
/* 33 */ {_SigSetStack + _SigUnblock, "signal 33"}, /* SIGSETXID; see issues 3871, 9400, 12498 */
```
`_SigUnblock`フラグが追加されました。このフラグは、Goランタイムがスレッドのシグナルマスクを初期化または更新する際に、対応するシグナルを明示的にマスク解除する（つまり、シグナルマスクから削除する）ように指示します。これにより、`SIGCANCEL`と`SIGSETXID`は常にGoスレッドに配信可能な状態に保たれ、glibcがこれらのシグナルを内部的に使用できるようになります。`issue 12498`が参照に追加されたのは、この変更がその問題を直接解決するためです。

### `misc/cgo/test/setgid_linux.go` の変更

このテストファイルは、Cgoを介した`setgid`呼び出しがGoのシグナルハンドリングとどのように相互作用するかを検証します。

`runTestSetgid()`関数は、`C.setgid(0)`（実効グループIDを0、つまりrootに変更しようとする）を新しいGoルーチンで実行し、5秒以内に完了するかどうかをチャネルを通じて監視します。完了すれば`true`、タイムアウトすれば`false`を返します。

`testSetgid()`関数は、この`runTestSetgid()`を2つの異なるシナリオで呼び出します。
1.  **`if !runTestSetgid() { t.Error("setgid hung") }`**: これは、`os/signal.Notify`がまだ設定されていない通常の状況で`setgid`がハングしないことを確認します。
2.  **`signal.Notify(make(chan os.Signal, 1), syscall.SIGINT)`**: ここで`os/signal.Notify`が呼び出され、`SIGINT`シグナルを処理するためのGoランタイムのシグナルハンドリングが有効になります。この操作が、以前は`SIGCANCEL`や`SIGSETXID`をマスクする原因となっていました。
3.  **`if !runTestSetgid() { t.Error("setgid hung after signal.Notify") }`**: `signal.Notify`が有効になった後で、再度`setgid`がハングしないことを確認します。このテストケースが、今回のコミットによる修正が正しく機能していることを直接検証する部分です。修正がなければ、この部分でテストがタイムアウトし、エラーが報告されるはずです。

このテストの追加により、Goランタイムのシグナルハンドリングとglibcの内部シグナルとの間の互換性が、将来の変更によって損なわれないようにするための安全網が提供されます。

## 元コミット内容

`cmd/cgo: wrap generated exports with extern "C" for C++`

このコミットは、`cgo`ツールが生成するエクスポートヘッダーファイルにおいて、Goからエクスポートされた関数宣言を`extern "C"`ブロックで囲むように変更します。これにより、C++コードがこのヘッダーファイルをインクルードした際に、正しい宣言を認識できるようになります。

ただし、ユーザーが記述するプリアンブル（`cgo`ディレクティブの直後に記述されるC/C++コード）は、引き続きユーザーの責任で管理されます。プリアンブルを`extern "C"`でラップすることは適切ではありません。なぜなら、プリアンブルにはCとC++の両方で機能するヘッダーファイルが含まれる可能性があり、それらを`extern "C"`ブロックに入れると、それらのヘッダーファイルの機能が損なわれる可能性があるためです。

## 変更の背景

Go言語とC/C++言語を相互運用するための`cgo`ツールは、Goの関数をC/C++から呼び出せるようにするためのエクスポート機能を提供します。この機能を利用すると、`_cgo_export.h`というヘッダーファイルが生成され、Goで定義された関数に対応するCの関数プロトタイプが記述されます。

しかし、C++コンパイラはC言語の関数とC++言語の関数で異なる名前マングリング（name mangling）規則を使用します。C++の関数は、オーバーロードや名前空間をサポートするために、関数名に引数の型情報などがエンコードされます。一方、C言語の関数は通常、名前マングリングを行いません。

C++コードからC言語の関数を呼び出す場合、C++コンパイラにその関数がCリンケージを持つことを明示的に伝える必要があります。これを行わないと、C++コンパイラはC言語の関数名をC++の名前マングリング規則で処理しようとし、結果としてリンケージエラーが発生します。

このコミットの背景には、`cgo`でエクスポートされたGo関数をC++コードから利用しようとした際に、C++コンパイラが正しく関数を認識できないという問題があったと考えられます。`extern "C"`を使用することで、C++コンパイラに対して、囲まれた宣言がCリンケージを持つことを指示し、この問題を解決することが目的です。

## 前提知識の解説

### `cgo`とは

`cgo`は、GoプログラムがCコードを呼び出したり、CコードがGoコードを呼び出したりするためのGoツールです。Goのソースファイル内に特別な`import "C"`ディレクティブと、その直前にCのコードを記述するプリアンブルを置くことで、GoとCの相互運用を可能にします。

### `extern "C"`とは

`extern "C"`はC++言語の機能で、C++コンパイラに対して、特定の関数や変数がC言語のリンケージ規則に従ってコンパイルされていることを指示します。これにより、C++コンパイラはこれらのシンボルに対してC++の名前マングリングを行わず、C言語のリンケージ規則（通常はシンボル名をそのまま使用）を適用します。

C++コードからCライブラリの関数を呼び出す場合、通常はCライブラリのヘッダーファイルを`extern "C"`ブロックで囲んでインクルードします。

```cpp
// C++コード
extern "C" {
    #include "c_library.h" // C言語で定義された関数宣言が含まれる
}
// これにより、c_library.h内の関数がCリンケージとして扱われる
```

### 名前マングリング (Name Mangling)

名前マングリングとは、コンパイラが関数名や変数名を、リンカが区別できるように一意な内部名に変換するプロセスです。C++では、関数オーバーロードや名前空間などの機能を実現するために、引数の型情報などを関数名にエンコードします。C言語では通常、名前マングリングは行われず、関数名はそのままシンボル名として使用されます。

### `_cgo_export.h`

`cgo`ツールがGoの関数をC/C++にエクスポートする際に生成するヘッダーファイルです。このファイルには、Goで定義された関数に対応するC言語形式の関数プロトタイプが含まれます。C/C++コードはこのヘッダーファイルをインクルードすることで、Goの関数を呼び出すことができます。

## 技術的詳細

このコミットの核心は、`cgo`が生成する`_cgo_export.h`ファイルの内容を、C++コンパイラが正しく解釈できるように変更することです。具体的には、生成されるC言語形式の関数宣言群を`extern "C" { ... }`ブロックで囲みます。

`cgo`は、Goのソースコードを解析し、Go関数をCから呼び出すためのラッパーコード（`.c`ファイル）と、そのラッパー関数のプロトタイプを含むヘッダーファイル（`_cgo_export.h`）を生成します。

変更前は、`_cgo_export.h`には単にC言語形式の関数宣言が羅列されていました。Cコードからこのヘッダーをインクルードする分には問題ありませんが、C++コードからインクルードすると、C++コンパイラはこれらの関数宣言をC++のリンケージ規則で処理しようとします。しかし、実際にリンクされるGoによって生成されたCラッパー関数はCリンケージを持っているため、リンカは対応するシンボルを見つけられず、リンケージエラーが発生していました。

このコミットでは、`_cgo_export.h`の生成時に、Goからエクスポートされる関数宣言の全体を`#ifdef __cplusplus`ディレクティブと`extern "C" { ... }`ブロックで条件付きで囲むようにします。

```c
// _cgo_export.h の生成イメージ (変更後)
#ifdef __cplusplus
extern "C" {
#endif

// ここにGoからエクスポートされたC言語形式の関数宣言が並ぶ
extern void GoFunc1();
extern int GoFunc2(int arg);

#ifdef __cplusplus
}
#endif
```

これにより、C++コンパイラでコンパイルされる際には`extern "C"`ブロックが有効になり、これらの関数がCリンケージを持つことが明示されます。Cコンパイラでコンパイルされる際には`__cplusplus`マクロが定義されていないため、`extern "C"`ブロックは無視され、C言語として正しく処理されます。

コミットメッセージで言及されている「プリアンブルはユーザーの責任」という点も重要です。`cgo`のプリアンブルには、ユーザーが任意のC/C++コードやヘッダーインクルードを記述できます。もしこのプリアンブル全体を`extern "C"`で囲んでしまうと、ユーザーがC++のヘッダーをインクルードした場合などに問題が発生する可能性があります。そのため、`cgo`が自動生成するエクスポート部分のみを`extern "C"`で囲むという、より安全で柔軟なアプローチが取られています。

## コアとなるコードの解説

`src/cmd/cgo/out.go`は、`cgo`ツールの中核部分であり、GoのソースコードからC/C++との相互運用に必要なファイルを生成するロジックを含んでいます。

-   `writeExports`関数は、Goのパッケージからエクスポートされる関数に対応するC言語の宣言を生成し、`_cgo_export.h`ファイルに書き込む役割を担います。
-   `writeGccgoExports`関数も同様に、`gccgo`コンパイラを使用する場合のエクスポート処理を担当します。

このコミットでは、これらの関数が`_cgo_export.h`の生成を完了する直前に、`gccExportHeaderEpilog`という文字列を追記するように変更されました。

`gccExportHeaderEpilog`は、C++のプリプロセッサマクロ`__cplusplus`が定義されている場合にのみ、`extern "C"`ブロックを閉じる`}`を出力します。これにより、C++コンパイラが`_cgo_export.h`をパースする際に、Goからエクスポートされた関数がCリンケージを持つことを正しく認識できるようになります。

この変更は、`cgo`が生成するヘッダーファイルの互換性を向上させ、GoとC++のよりスムーズな連携を可能にするための重要な修正です。特に、C++プロジェクトにGoのライブラリを組み込む際に発生しがちなリンケージエラーを回避するのに役立ちます。

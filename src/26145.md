## 変更の背景

この変更の背景には、Goの `net/http` パッケージが提供するHTTP/2の自動サポートに関するドキュメントの整合性と明確性の向上が挙げられます。

Go 1.6から、`net/http` パッケージはHTTPS接続においてALPN (Application-Layer Protocol Negotiation) を利用してHTTP/2を自動的にサポートするようになりました。これは、クライアント側 (`http.Transport`) とサーバー側 (`http.Server`) の両方に適用されます。

`http.Transport` の `TLSNextProto` フィールドのドキュメントには、既に「`TLSNextProto` が `nil` の場合、HTTP/2 サポートが自動的に有効になる」という記述がありました。しかし、`http.Server` の `TLSNextProto` フィールドのドキュメントには、この重要な情報が欠けていました。

この不整合は、開発者が `http.Server` を設定する際に、HTTP/2の自動サポートの挙動について混乱を招く可能性がありました。特に、`TLSNextProto` を明示的に設定しない場合にHTTP/2が有効になることを知らない開発者は、意図せずHTTP/2が使われていることに気づかないか、あるいはHTTP/2を有効にするために不要な設定を試みるかもしれません。

このコミットは、`http.Transport.TLSNextProto` のドキュメントから同じ文言を `http.Server.TLSNextProto` のドキュメントにコピーすることで、この情報ギャップを埋め、両者のドキュメントの一貫性を保ち、開発者にとってより明確な情報を提供することを目的としています。これにより、GoのHTTPサーバーがどのようにHTTP/2を扱うかについて、より正確な理解が促進されます。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を把握しておく必要があります。

1.  **Goの `net/http` パッケージ**:
    Go言語の標準ライブラリに含まれる、HTTPクライアントとサーバーの実装を提供するパッケージです。Webアプリケーションの構築やHTTP通信を行う上で中心的な役割を果たします。

2.  **TLS (Transport Layer Security)**:
    インターネット上でデータを安全にやり取りするための暗号化プロトコルです。HTTPS通信の基盤となっており、データの盗聴、改ざん、なりすましを防ぎます。TLSハンドシェイクを通じて、クライアントとサーバー間で暗号化キーを交換し、安全な通信チャネルを確立します。

3.  **ALPN (Application-Layer Protocol Negotiation)**:
    TLSの拡張機能の一つで、TLSハンドシェイク中にクライアントとサーバーがどのアプリケーション層プロトコル（例: HTTP/1.1, HTTP/2）を使用するかをネゴシエートできるようにします。これにより、単一のTLSポート (通常は443) で複数のプロトコルを効率的にサポートすることが可能になります。HTTP/2はALPNを介して確立されることが一般的です。

4.  **HTTP/2**:
    HTTP/1.1の後継として開発されたWebプロトコルです。主な特徴として、以下の点が挙げられます。
    *   **多重化 (Multiplexing)**: 複数のリクエストとレスポンスを単一のTCP接続上で同時に処理できます。これにより、ヘッドオブラインブロッキングの問題が軽減されます。
    *   **ヘッダー圧縮 (Header Compression)**: HTTPヘッダーを効率的に圧縮することで、オーバーヘッドを削減します。
    *   **サーバープッシュ (Server Push)**: クライアントがリクエストする前に、サーバーが関連するリソースをクライアントに送信できます。
    *   **バイナリフレーム層**: HTTP/1.1のテキストベースのプロトコルとは異なり、HTTP/2はバイナリ形式で通信を行います。

5.  **`http.Server` 構造体**:
    Goの `net/http` パッケージでHTTPサーバーを構成するための構造体です。リスニングアドレス、ハンドラー、タイムアウト設定など、サーバーの動作を制御するための様々なフィールドを持ちます。

6.  **`Server.TLSNextProto` フィールド**:
    `http.Server` 構造体内のフィールドで、ALPNによってネゴシエートされたプロトコルに基づいてカスタムハンドラーを登録するために使用されます。これは `map[string]func(*Server, *tls.Conn, Handler)` 型であり、キーはプロトコル名（例: "h2" for HTTP/2, "http/1.1" for HTTP/1.1）、値はそのプロトコルを処理するための関数です。
    このフィールドが `nil` の場合、Goの `net/http` パッケージはデフォルトのALPNハンドラーを使用し、HTTP/2を自動的にサポートします。開発者が特定のプロトコルに対して独自の処理を実装したい場合にのみ、このマップを設定します。

7.  **`http.Transport.TLSNextProto` フィールド**:
    `http.Transport` はHTTPクライアントの動作を制御する構造体です。`Transport.TLSNextProto` はクライアント側でALPNプロトコルハンドラーをカスタマイズするために使用されます。サーバー側の `Server.TLSNextProto` と同様に、`nil` の場合はHTTP/2が自動的に有効になります。このコミットは、このクライアント側のドキュメントとの一貫性を図るものです。

## 技術的詳細

このコミットは、Goの `net/http` パッケージにおける `http.Server` の挙動、特にHTTPS接続におけるHTTP/2の自動サポートに関するドキュメントの改善に焦点を当てています。

Go 1.6以降、`net/http` パッケージは、HTTPS接続を確立する際にALPN (Application-Layer Protocol Negotiation) を利用して、HTTP/2プロトコルを自動的にネゴシエートし、サポートするようになりました。これは、開発者が明示的にHTTP/2を有効にするためのコードを書く必要がないことを意味します。

`http.Server` 構造体には `TLSNextProto` というフィールドがあります。これは `map[string]func(*Server, *tls.Conn, Handler)` 型で、ALPNによってネゴシエートされた特定のプロトコル（例: "h2"）に対して、カスタムのハンドラー関数を登録するために使用されます。

このコミット以前は、`Server.TLSNextProto` のドキュメントには、このマップが `nil` の場合にHTTP/2が自動的に有効になるという重要な情報が明記されていませんでした。しかし、実際には、`TLSNextProto` フィールドが `nil` の場合、`net/http` パッケージの内部ロジックがALPNハンドシェイク中に "h2" (HTTP/2) を含むプロトコルリストを提示し、クライアントがHTTP/2をサポートしていれば自動的にHTTP/2で通信を開始します。

このコミットの目的は、このデフォルトの挙動をドキュメントに明確に記述することです。コミットメッセージにあるように、これは `http.Transport.TLSNextProto` のドキュメントに既に存在していた同様の文言をコピーしたものです。これにより、サーバー側とクライアント側の両方で `TLSNextProto` フィールドの `nil` 値がHTTP/2の自動有効化を意味するという一貫した理解が促進されます。

この変更は、コードの動作自体を変更するものではなく、既存の動作に関するドキュメントの正確性と完全性を向上させるものです。これにより、開発者は `http.Server` を使用する際に、HTTP/2のサポートがどのように扱われるかについて、より明確な情報を得られるようになります。特に、`TLSNextProto` をカスタマイズしない場合でもHTTP/2が利用可能であることを理解し、不必要な設定の試みを避けることができます。

## コアとなるコードの解説

追加された行は、`http.Server` 構造体の `TLSNextProto` フィールドのコメント内にあります。

```go
	// If TLSNextProto is nil, HTTP/2 support is enabled automatically.
	TLSNextProto map[string]func(*Server, *tls.Conn, Handler)
```

このコメントは、`TLSNextProto` フィールドが `nil` （つまり、開発者が特定のALPNプロトコルハンドラーを明示的に設定していない）の場合に、Goの `net/http` パッケージが自動的にHTTP/2プロトコルのサポートを有効にすることを明確に示しています。

具体的には、以下のことを意味します。

1.  **デフォルトの挙動**: 開発者が `http.Server` を作成し、`TLSNextProto` フィールドに何も設定しない（デフォルト値である `nil` のままにする）場合、そのサーバーはHTTPS接続においてALPNを通じてHTTP/2を自動的にネゴシエートし、サポートします。
2.  **明示的な制御**: もし開発者がHTTP/2のサポートを無効にしたい、あるいはHTTP/2以外の特定のプロトコルに対してカスタムのハンドリングロジックを提供したい場合は、`TLSNextProto` マップに適切なエントリを設定する必要があります。例えば、HTTP/2を無効にするには、`TLSNextProto` マップに "h2" エントリを含め、そのハンドラーが何もしないか、エラーを返すように設定します。
3.  **ドキュメントの明確化**: このコメントの追加により、`net/http` パッケージのユーザーは、`TLSNextProto` フィールドの役割と、それが `nil` の場合のHTTP/2サポートの挙動について、より正確で完全な情報を得られるようになりました。これにより、GoのHTTPサーバーがどのようにプロトコルネゴシエーションを処理するかについての誤解が減り、開発者はより自信を持ってサーバーを設定できるようになります。

この変更は、Goの「batteries included (必要なものが全て揃っている)」という哲学と、デフォルトで最新のプロトコルをサポートするというアプローチを反映しており、同時にその挙動を透過的にすることで開発者の利便性を高めています。

## 元コミット内容

このコミットは、以前のコミットであるCL 138250043（ハッシュ: 4eda5e4001fd）の変更を取り消すものです。CL 138250043の元の説明は以下の通りです。

> syscall: keep Windows syscall pointers live too
>
> Like https://golang.org/cl/139360044

この元のコミットは、Windowsシステムコールに関連するポインタがGoのガベージコレクタによって時期尚早に解放されるのを防ぐために、それらのポインタを「ライブ」（参照されている状態）に保つことを目的としていました。これは、GoのランタイムがWindows APIと安全に相互作用するために重要な側面です。

## 変更の背景

このコミットの背景には、Goのガベージコレクタ（GC）と、GoプログラムがWindowsのネイティブAPIを呼び出す際の相互作用に関する課題があります。GoのGCは、到達可能なオブジェクトのみをメモリに保持し、到達不能になったオブジェクトは解放します。しかし、Windows APIを呼び出す際にGoのメモリ上に確保されたデータへのポインタをAPIに渡す場合、GoのGCはそのポインタがネイティブコードによってまだ使用されていることを認識できない可能性があります。

元のCL 138250043は、この問題を解決するために、Windowsシステムコールに渡されるポインタを明示的に「ライブ」に保つメカニズムを導入しようとしました。これは、GoのGCがそれらのポインタを誤って解放するのを防ぐためです。しかし、このコミット（20721）は、そのアプローチが最適ではないと判断され、取り消されました。コミットメッセージには「I will use different approach to solve this problem.」（この問題を解決するために異なるアプローチを使用する）と明記されており、CL 143160046でその新しいアプローチが導入されることが示唆されています。

## 前提知識の解説

### Goの`syscall`パッケージ

`syscall`パッケージは、Goプログラムがオペレーティングシステム（OS）の低レベルな機能にアクセスするためのインターフェースを提供します。これには、ファイル操作、プロセス管理、ネットワーク通信など、OSが提供するシステムコールを直接呼び出す機能が含まれます。Windowsの場合、このパッケージはWindows API関数を呼び出すためのGoラッパーを提供します。

### Windows APIとポインタ

Windows APIは、C言語の規約に基づいており、多くの関数がポインタを引数として受け取ります。これらのポインタは、Goのメモリ空間に存在するデータ（例えば、文字列や構造体）を指すことがあります。GoのガベージコレクタはGoのヒープを管理しますが、ネイティブコードがGoのメモリを参照している間、そのメモリが解放されないように特別な注意が必要です。

### Goのガベージコレクション (GC)

GoのGCは、プログラムが動的に割り当てたメモリのうち、もはや到達不可能になったものを自動的に解放する仕組みです。GCは、プログラムの実行中にバックグラウンドで動作し、メモリリークを防ぎ、開発者が手動でメモリを管理する負担を軽減します。しかし、GoのGCはGoのランタイムが認識しているポインタのみを追跡します。`unsafe.Pointer`を介してネイティブコードに渡されたポインタは、GCの通常の追跡範囲外になる可能性があります。

### `unsafe.Pointer`

`unsafe.Pointer`は、Goの型システムをバイパスして、任意の型のポインタを任意の型のポインタに変換できる特殊なポインタ型です。これは、GoとC/C++のような他の言語との相互運用や、低レベルなメモリ操作を行う際に使用されます。しかし、その名の通り「unsafe」であり、誤用するとメモリ破壊やクラッシュを引き起こす可能性があります。GCは`unsafe.Pointer`自体を追跡しますが、それが指す先のメモリがネイティブコードによって参照されているかどうかは自動的には判断できません。

### `mksyscall_windows.go`と`zsyscall_windows.go`

*   `mksyscall_windows.go`: このファイルは、Goの`syscall`パッケージ内でWindowsシステムコールを呼び出すためのGoコードを自動生成するツールの一部です。Goのソースコードから特定のコメント（`//sys`ディレクティブ）を解析し、対応するGoの関数ラッパーと、Windows APIを呼び出すための低レベルなコードを生成します。
*   `zsyscall_windows.go`: このファイルは、`mksyscall_windows.go`ツールによって自動生成されたWindowsシステムコールのGoラッパー関数を含んでいます。これらの関数は、GoのコードからWindows APIを呼び出すためのエントリポイントとなります。

## 技術的詳細

このコミットは、Goの`syscall`パッケージにおけるWindows固有のポインタ管理メカニズムを元に戻すものです。元のCL 138250043では、Windows APIに渡されるGoのポインタがGCによって時期尚早に解放されるのを防ぐために、`use`という関数と`Fn`構造体の`Used`フィールドが導入されていました。

`use`関数は、特定のポインタがまだ「使用中」であることをGCに示唆するためのものでした。これは、`unsafe.Pointer`を介してネイティブコードに渡されたポインタが、GoのGCの追跡対象外になることへの対策として考えられました。`mksyscall_windows.go`は、システムコールを生成する際に、文字列型などの引数に対してこの`use`関数を呼び出すように変更されていました。

しかし、このコミットでは、その`use`関数と関連するロジックが完全に削除されています。これは、このアプローチが問題を完全に解決しないか、あるいはより効率的で堅牢な別の方法が見つかったためと考えられます。コミットメッセージが示唆するように、新しいアプローチはCL 143160046で導入されることになります。

具体的に削除されたのは以下の点です。

*   `src/syscall/mksyscall_windows.go`から、`Param`構造体の`fn.use(p.tmpVar())`の呼び出し。これは、文字列引数に対してポインタをライブに保つためのものでした。
*   `Fn`構造体から`Used []string`フィールドの削除。
*   `Fn`構造体の`use(v string)`メソッドの削除。
*   `sanitizeName`関数の削除。これは、引数名が`use`と衝突するのを避けるためのものでした。
*   テンプレート定義`{{define "used"}}`の削除。これは、`use`関数を呼び出すコードを生成するためのものでした。
*   `src/syscall/zsyscall_windows.go`から、`use(unsafe.Pointer(...))`の直接的な呼び出しの削除。これは、`LoadLibrary`, `GetProcAddress`, `GetHostByName`, `GetServByName`, `GetProtoByName`, `DnsQuery`などの特定のWindows APIラッパー関数で行われていました。
*   `LookupAccountSid`と`LookupAccountName`関数の引数名が`use_`から`use`に戻されています。これは、`use`という名前が予約語や特別な意味を持つことを避けるための変更が不要になったためです。

これらの変更は、GoのランタイムがWindows APIと相互作用する際のポインタのライフタイム管理に対する根本的なアプローチの変更を示しています。

## コアとなるコードの変更箇所

### `src/syscall/mksyscall_windows.go`

*   `Param.SyscallArgList()`関数内で、`string`型の引数に対する`p.fn.use(p.tmpVar())`の呼び出しが削除されました。
*   `Fn`構造体から`Used []string`フィールドが削除されました。
*   `Fn`構造体の`use(v string)`メソッドが削除されました。
*   `extractParams`関数内で、`Param`の`Name`フィールドを`sanitizeName`で処理する部分が削除され、直接`trim(b[0])`が使われるようになりました。
*   `sanitizeName`関数自体が削除されました。
*   `{{define "funcbody"}}`テンプレート内で、`{{template "used" .}}`の呼び出しが削除されました。
*   `{{define "used"}}`テンプレート定義自体が削除されました。

### `src/syscall/zsyscall_windows.go`

*   `LoadLibrary`, `GetProcAddress`, `GetHostByName`, `GetServByName`, `GetProtoByName`, `DnsQuery`関数内で、`use(unsafe.Pointer(...))`の呼び出しが削除されました。
*   `LookupAccountSid`および`LookupAccountName`関数の引数名が、`use_`から`use`に変更されました。

## コアとなるコードの解説

このコミットのコアとなる変更は、Goの`syscall`パッケージがWindows APIにポインタを渡す際に、それらのポインタがGoのガベージコレクタによって時期尚早に解放されるのを防ぐために導入された「`use`メカニズム」を完全に削除した点にあります。

元の実装では、`mksyscall_windows.go`が生成するコードに、`use`関数を呼び出すロジックが埋め込まれていました。この`use`関数は、`Fn`構造体の`Used`フィールドにポインタの情報を記録することで、GCがそのポインタを「ライブ」であると認識し続けるように意図されていました。しかし、このコミットでは、これらのメカニズムがすべて削除されています。

例えば、`src/syscall/mksyscall_windows.go`の以下の行が削除されました。

```diff
-	case p.Type == "string":
-		p.fn.use(p.tmpVar())
```

これは、文字列引数がシステムコールに渡される際に、その文字列のポインタを明示的に「使用中」としてマークする処理が不要になったことを意味します。

また、`src/syscall/zsyscall_windows.go`では、以下のような行が削除されています。

```diff
-	use(unsafe.Pointer(_p0))
```

これは、特定のWindows API呼び出し（例: `LoadLibrary`）の直後に、そのAPIに渡されたポインタがGCによって解放されないようにするための明示的な`use`呼び出しが削除されたことを示しています。

`LookupAccountSid`と`LookupAccountName`の引数名が`use_`から`use`に戻されたのは、`use`という名前が特別な意味を持たなくなったため、元の自然な引数名に戻すことができたからです。

これらの変更は、GoのランタイムがWindows APIとの相互作用におけるポインタのライフタイム管理について、より洗練された、あるいは異なるアプローチを採用したことを強く示唆しています。おそらく、GoのGC自体がネイティブコードによって参照されているGoのメモリをより適切に追跡できるようになるか、あるいはポインタを「ライブ」に保つためのより低レベルで効率的なメカニズムが導入されたと考えられます。

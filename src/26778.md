# [インデックス 26778] ファイルの概要

このコミットは、Goコンパイラ (`cmd/compile`) におけるエラーメッセージの行番号報告の一貫性を向上させるための変更です。具体的には、字句解析器 (`lex`) と構文解析器 (`parser`) が報告するエラーの行番号 (`lineno` と `lexlineno`) の扱いを整理し、より正確で一貫性のあるエラー位置情報を提供するように修正されています。また、不要になった `prevlineno` の削除や、古いエラーメッセージのフォールバック機構の廃止も含まれます。

## 元コミット内容

```
cmd/compile: rationalize (lex)?lineno handling

Previously, many error messages inconsistently used either lexlineno
and lineno. In general this works out okay because they're almost
always the same. The only exceptional case is after lexing a
multi-line raw string literal, where lineno will be the line number of
the opening quote and lexlineno is the line number of the closing
quote.

This CL makes the compiler's error message more consistent:

- Lexer error messages related to invalid byte sequences (i.e., NUL
bytes, bad UTF-8 sequences, and non-initial BOMs) are emitted at
lexlineno (i.e., the source line that contains the invalid byte
sequence).

- All other error messages (notably the parser's "syntax errors") now
use lineno. The minor change from this is that bogus input like:

    package `
    bogus`

will emit "syntax error: unexpected string literal, expecting name"
error at line 1, instead of line 2.

- Instead of maintaining prevlineno all the time, just record it
when/where actually needed and not already available elsewhere (which
turns out to be just one function).

- Lastly, we remove the legacy "syntax error near ..." fallback in
Yerror, now that the parser always emits more detailed syntax error
messages.
```

## 変更の背景

Goコンパイラのエラーメッセージは、開発者にとってコードの問題を特定し、修正するために不可欠な情報源です。しかし、このコミット以前は、エラーメッセージが報告する行番号の参照元が `lineno` と `lexlineno` の間で一貫性を欠いていました。ほとんどの場合、これら二つの値は同じ行を指しますが、複数行にわたる生文字列リテラル（raw string literal）のような特殊なケースでは、`lineno` が開始行を、`lexlineno` が終了行を指すという違いがありました。

この不一貫性は、特に複雑な構文エラーや、不正なバイトシーケンスを含むファイルにおいて、開発者がエラーの真の原因を特定するのを困難にする可能性がありました。例えば、構文エラーが複数行の文字列リテラルの途中で発生した場合、`lineno` と `lexlineno` のどちらが報告されるかによって、エラーが指し示す行が異なり、混乱を招くことがありました。

このコミットの目的は、エラー報告のロジックを「合理化（rationalize）」し、特定のエラータイプに対して適切な行番号を常に報告するようにすることで、コンパイラのエラーメッセージの品質と信頼性を向上させることにありました。これにより、開発者はより正確な情報に基づいて問題を迅速に解決できるようになります。また、不要な状態 (`prevlineno`) の削除や、より詳細なエラーメッセージが常に提供されるようになったため、古いフォールバック機構の廃止も行われ、コードベースの整理も図られています。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの基本的な構造と、字句解析（Lexical Analysis）および構文解析（Syntactic Analysis）の概念、そしてそれらにおける行番号の扱いの違いについて知る必要があります。

### Goコンパイラ (`cmd/compile`) の概要

Go言語の公式コンパイラは `cmd/compile` ディレクトリに存在し、Goプログラムを機械語に変換する役割を担っています。コンパイルプロセスは、大まかに以下のフェーズに分けられます。

1.  **字句解析 (Lexical Analysis / Lexing)**: ソースコードをトークン（意味を持つ最小単位、例: 識別子、キーワード、演算子、リテラル）のストリームに変換します。このフェーズを担当するのが字句解析器（lexer）です。
2.  **構文解析 (Syntactic Analysis / Parsing)**: トークンのストリームを解析し、Go言語の文法規則に従っているかを確認します。問題がなければ、抽象構文木（AST: Abstract Syntax Tree）を構築します。このフェーズを担当するのが構文解析器（parser）です。
3.  **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、名前解決、スコープチェックなど、意味的な正当性を検証します。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTから、より低レベルな中間表現（IR）を生成します。
5.  **最適化 (Optimization)**: 中間コードを最適化し、実行効率を向上させます。
6.  **コード生成 (Code Generation)**: 最適化された中間コードから、ターゲットアーキテクチャの機械語を生成します。

このコミットは、主に字句解析と構文解析のフェーズにおけるエラー報告、特にエラーが発生したソースコードの行番号の扱いに焦点を当てています。

### `lineno` と `lexlineno`

Goコンパイラの字句解析器と構文解析器は、ソースコードの現在位置を追跡するために複数の行番号変数を保持しています。

*   **`lineno`**: これは通常、現在処理中のトークンが開始する行番号を指します。構文解析器がエラーを報告する際に、この `lineno` を使用することが一般的です。
*   **`lexlineno`**: これは字句解析器が最後に読み込んだ文字（またはトークン）の直後の行番号を指します。つまり、字句解析器がソースコードを読み進めるにつれて更新される、より「現在」に近い行番号です。

通常、`lineno` と `lexlineno` は同じ値を指すことが多いですが、複数行にわたる要素（特に複数行の生文字列リテラルやコメント）を処理する際には、その値が異なることがあります。

**例**:

```go
package `
bogus` // ここで構文エラーが発生
```

この場合、`package` トークンの `lineno` は1行目、`bogus` の `lineno` は2行目となります。しかし、字句解析器が `package` の後の生文字列リテラル全体を読み込んだ後、`lexlineno` は3行目（`bogus` の次の行）を指す可能性があります。このコミット以前は、このような状況でどちらの行番号がエラーメッセージに表示されるかが一貫していませんでした。

### `prevlineno`

`prevlineno` は、以前の `lineno` の値を保持するために使用されていた変数です。このコミットでは、この変数が常に維持される必要がないと判断され、実際に必要とされる特定の箇所でのみ一時的に記録するように変更されました。これは、コンパイラの状態管理を簡素化し、メモリ使用量を削減するための一環と考えられます。

### `Yyerror` と `yyerrorl`

Goコンパイラのエラー報告関数には、`Yyerror` と `yyerrorl` があります。

*   **`Yyerror(format string, args ...interface{})`**: 現在のコンパイラの状態（特に `lineno` や `lexlineno`）に基づいてエラーメッセージを報告する汎用関数です。
*   **`yyerrorl(line int, format string, args ...interface{})`**: 明示的に指定された行番号 `line` を使用してエラーメッセージを報告する関数です。

このコミットでは、`Yyerror` 内にあった「syntax error near ...」というレガシーなフォールバック機構が削除されました。これは、現代のGoコンパイラが常に詳細な構文エラーメッセージを生成できるようになったため、この汎用的なフォールバックが不要になったことを意味します。

## 技術的詳細

このコミットの技術的詳細は、`lineno` と `lexlineno` の役割分担を明確にし、エラー報告の精度を高めることにあります。

1.  **`lexlineno` の役割の限定**:
    *   字句解析器が検出する、不正なバイトシーケンス（NULバイト、不正なUTF-8シーケンス、非初期BOM）に関するエラーメッセージは、`lexlineno` を使用して報告されるようになりました。これは、これらのエラーがソースコード内の特定の不正なバイト位置に直接関連しており、`lexlineno` がその正確な位置を指すためです。
    *   `src/cmd/compile/internal/gc/lex.go` の `getr()` 関数内で、`Yyerror` の代わりに `yyerrorl(int(lexlineno), ...)` が直接呼び出されるように変更されています。

2.  **`lineno` の役割の拡大**:
    *   上記以外のすべて（特に構文解析器が報告する「syntax errors」）のエラーメッセージは、`lineno` を使用して報告されるようになりました。これにより、構文エラーは常にトークンの開始行に紐付けられ、より予測可能で一貫性のある挙動を示します。
    *   コミットメッセージの例にあるように、

        ```go
        package `
        bogus`
        ```

        という不正な入力に対して、以前は2行目でエラーが報告される可能性があったものが、この変更により1行目（`package` トークンの開始行）でエラーが報告されるようになります。これは、構文解析器が `package` の後に予期しないトークン（この場合は生文字列リテラル）を見つけた時点でエラーを検出するため、そのトークンが開始する行を報告するのがより適切であるという判断に基づいています。

3.  **`prevlineno` の削除と最適化**:
    *   `src/cmd/compile/internal/gc/go.go` から `prevlineno` 変数が削除されました。
    *   `src/cmd/compile/internal/gc/lex.go` の `lexer.next()` 関数内で `prevlineno = lineno` の行が削除されています。
    *   `src/cmd/compile/internal/gc/parser.go` の `syntax_error_at` 関数や `labeled_stmt` 関数内で `prevlineno` を参照していた箇所が、`label.Lineno` や `symlineno` といった、より直接的で必要な情報に置き換えられています。これにより、コンパイラの状態管理が簡素化され、不要な状態の追跡がなくなりました。

4.  **`Yyerror` からのレガシーフォールバックの削除**:
    *   `src/cmd/compile/internal/gc/subr.go` の `Yyerror` 関数から、`msg == "syntax error"` の場合に「syntax error near ...」というメッセージを追加するロジックが削除されました。これは、コンパイラが常に詳細な構文エラーメッセージを生成するようになったため、この汎用的なフォールバックが不要になったためです。これにより、エラーメッセージの冗長性が減り、より直接的な情報が提供されるようになります。

これらの変更は、コンパイラのエラー報告メカニズムの内部的な整合性を高め、最終的に開発者体験を向上させることを目的としています。

## コアとなるコードの変更箇所

このコミットで変更された主要なファイルと、その中でのコアとなる変更箇所は以下の通りです。

*   **`src/cmd/compile/internal/gc/go.go`**:
    *   `prevlineno` 変数の宣言が削除されました。
    *   `lexlineno` と `lineno` のコメントが更新され、それぞれの役割がより明確に記述されました。

*   **`src/cmd/compile/internal/gc/lex.go`**:
    *   `lexer.next()` 関数から `prevlineno = lineno` の行が削除されました。
    *   暗黙的なセミコロン挿入のロジックにおいて、`lineno = lexlineno` が `lineno = lexlineno - 1` に変更され、改行文字の前の行番号を指すように修正されました。
    *   デバッグ出力 (`fmt.Printf`) で `lexlineno` を使用していた箇所が `lineno` に変更されました。
    *   不正なNULバイトやUTF-8シーケンス、BOMに関するエラー報告で、`Yyerror` の代わりに `yyerrorl(int(lexlineno), ...)` が直接呼び出されるようになりました。

*   **`src/cmd/compile/internal/gc/parser.go`**:
    *   `syntax_error_at` 関数の引数名が `lineno` から `lno` に変更され、内部での `lexlineno` の設定が `lineno` の設定に変わりました。
    *   `labeled_stmt` 関数内で、ラベル後のステートメントがない場合のエラー報告が `prevlineno` から `label.Lineno` を参照するように変更されました。
    *   `dcl_name` 関数が `sym *Sym` 引数を取らなくなり、内部で `p.sym()` を呼び出すように変更されました。また、エラー報告の行番号が `prevlineno` から `symlineno` (現在の `lineno` を一時的に保存したもの) を参照するように変更されました。
    *   `dcl_name_list` 関数内で `p.dcl_name(p.sym())` の呼び出しが `p.dcl_name()` に変更されました。

*   **`src/cmd/compile/internal/gc/subr.go`**:
    *   `yyerror_lastsyntax` 変数の型が `int` から `int32` に変更されました。
    *   `Yyerror` 関数内で、`yyerror_lastsyntax` と `lexlineno` の比較が `yyerror_lastsyntax` と `lineno` の比較に変更されました。
    *   `Yyerror` 関数から、`msg == "syntax error"` の場合に「syntax error near ...」というメッセージを追加するレガシーなフォールバックロジックが完全に削除されました。
    *   `yyerrorl` の呼び出しで `lexlineno` を使用していた箇所が `lineno` に変更されました。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラがソースコード内のエラー位置をどのように特定し、報告するかというメカニズムの洗練にあります。

1.  **行番号変数の役割の明確化**:
    *   `go.go` で `lexlineno` と `lineno` のコメントが更新されたことは、これらの変数がコンパイラ内で果たす役割の公式な定義を強化します。`lexlineno` は字句解析器が読み込んだ最後の文字の直後の行を、`lineno` は現在処理中のトークンの開始行を指すという区別が、エラー報告ロジック全体にわたって適用されるようになりました。
    *   `prevlineno` の削除は、コンパイラの状態管理を簡素化し、必要な情報のみを保持するという設計原則に沿ったものです。これにより、コードの可読性と保守性が向上します。

2.  **字句解析エラーと構文解析エラーの分離**:
    *   `lex.go` における不正なバイトシーケンスのエラーが `lexlineno` を使用して `yyerrorl` で直接報告されるようになったのは、これらのエラーが字句解析の非常に低レベルな段階で検出され、`lexlineno` がその不正なバイトが実際に存在する行を最も正確に指し示すためです。これは、ソースコードの物理的な構造に関するエラーに対して、最も正確な位置情報を提供します。
    *   一方、`parser.go` や `subr.go` で構文エラーが `lineno` を使用するように統一されたのは、構文エラーが特定のトークンや文の構造に関連しており、そのトークンが開始する行を報告するのが、開発者にとって最も自然で理解しやすいエラー位置だからです。これにより、構文エラーの報告が一貫性を持ち、例えば複数行の生文字列リテラルが関与する場合でも、エラーが常に期待される行（通常は問題のある構文要素の開始行）に表示されるようになります。

3.  **暗黙的なセミコロン挿入の行番号修正**:
    *   `lex.go` の `lexer.next()` 関数における `lineno = lexlineno - 1` への変更は、Go言語の「暗黙的なセミコロン挿入」ルールに関連しています。Goでは、特定の状況で改行の後に自動的にセミコロンが挿入されます。この変更は、暗黙的に挿入されるセミコロンが、実際に改行文字が存在する行ではなく、その前の行（つまり、セミコロンが論理的に挿入されるべきコードの行）に紐付けられるように、行番号の計算を微調整したものです。これにより、コンパイラが報告するエラーや警告が、Goの構文規則とより密接に一致するようになります。

4.  **レガシーエラーフォールバックの廃止**:
    *   `subr.go` から「syntax error near ...」というフォールバックが削除されたことは、Goコンパイラが進化し、常に詳細で具体的な構文エラーメッセージを生成できるようになったことの証です。これにより、開発者はより具体的で役立つエラーメッセージを受け取ることができ、デバッグプロセスが効率化されます。

これらの変更は、Goコンパイラが生成するエラーメッセージの品質を向上させ、開発者がGoコードをより効率的に記述し、デバッグできるようにするための重要な改善です。

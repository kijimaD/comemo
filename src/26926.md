# [インデックス 26926] ファイルの概要

## 変更の背景

Go言語のリンカ（`cmd/link`）は、コンパイルされたGoパッケージと依存関係を結合して実行可能なバイナリを生成する重要なツールです。このプロセスの中で、リンカは関数内のローカル変数や引数といった「自動変数」（`Autom`）に関する情報を管理する必要があります。

以前の実装では、`LSym`構造体（リンカがシンボルを表すために使用する）内の`Autom`フィールドは、`*Auto`型の連結リストとして定義されていました。連結リストは要素の追加や削除が容易であるという利点がありますが、以下の点で非効率になる可能性があります。

1.  **メモリ局所性（Locality of Reference）の欠如**: 連結リストの要素はメモリ上に連続して配置されないことが多く、キャッシュミスを頻繁に引き起こし、アクセス速度が低下する可能性があります。
2.  **イテレーションのオーバーヘッド**: 各要素にアクセスするためにポインタを辿る必要があり、スライスのような連続したメモリ領域に比べてイテレーションのコストが高くなります。
3.  **コードの複雑さ**: 連結リストの操作（特に逆順に構築されたリストの処理）は、スライスに比べてコードが複雑になりがちです。

このコミットは、これらの非効率性を解消し、リンカのパフォーマンスとコードの可読性を向上させるために、`Autom`フィールドをスライス（`[]Auto`）に置き換えることを目的としています。スライスは連続したメモリ領域を保証するため、メモリ局所性が高く、イテレーションが高速です。

## 前提知識の解説

### Go言語のリンカ (`cmd/link`)

`cmd/link`はGoツールチェーンの一部であり、Goプログラムのビルドプロセスにおいて最終的な実行可能ファイルを生成する役割を担います。コンパイラが生成したオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合し、シンボル解決、再配置、デッドコード削除、DWARFデバッグ情報の生成などを行います。Goのリンカは、Goプログラムが静的にリンクされた単一のバイナリとして配布されることを可能にする重要な要素です。

### `LSym`構造体

`LSym`（Linker Symbol）構造体は、Goリンカがプログラム内の各シンボル（関数、グローバル変数、型など）に関する情報を内部的に表現するために使用されます。これには、シンボルの名前、アドレス、サイズ、型情報、関連する再配置情報などが含まれます。`LSym`はリンカの処理の中心となるデータ構造の一つです。

### `Auto`構造体

`Auto`構造体は、特定の関数（`LSym`で表される）に関連付けられた自動変数（ローカル変数や引数）に関する情報を保持します。これには、変数のシンボル（`Asym`）、オフセット（`Aoffset`）、名前（`Name`）、型（`Gotype`）などが含まれます。リンカは、デバッグ情報の生成（DWARF）やスタックフレームのレイアウト決定などの際に、この`Auto`情報を使用します。

### 連結リスト (Linked List) とスライス (Slice) の違い

*   **連結リスト**:
    *   各要素がデータと次の要素へのポインタ（`Link`フィールドなど）を持つデータ構造。
    *   要素はメモリ上に連続して配置されるとは限らない。
    *   要素の追加・削除はポインタの付け替えで高速に行える。
    *   ランダムアクセスは苦手（先頭から順に辿る必要がある）。
    *   メモリ局所性が低く、キャッシュ効率が悪い場合がある。
    *   イテレーションにはポインタのデリファレンスが伴うため、オーバーヘッドがある。

*   **スライス (Go言語)**:
    *   基盤となる配列の一部を参照するデータ構造。
    *   要素はメモリ上に連続して配置される。
    *   ランダムアクセスは高速（配列のインデックスアクセス）。
    *   要素の追加（`append`）は、容量が足りない場合に新しい配列を割り当ててコピーするため、コストがかかる場合がある。
    *   メモリ局所性が高く、キャッシュ効率が良い。
    *   イテレーションは非常に高速（`for range`ループなど）。

このコミットでは、`Autom`のデータが主にイテレーションと読み込みに使われるため、スライスの利点が連結リストのそれを上回ると判断されたと考えられます。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、以下の2つのファイルに集約されています。

1.  **`src/cmd/link/internal/ld/link.go`**:
    *   `LSym`構造体の`Autom`フィールドの型定義が`*Auto`から`[]Auto`に変更。
    *   `Auto`構造体から`Link *Auto`フィールドが削除。

2.  **`src/cmd/link/internal/ld/objfile.go`**:
    *   オブジェクトファイルから`Auto`情報を読み込み、`LSym.Autom`に格納するロジックが、連結リスト構築からスライスへの直接書き込みに変更。

## コアとなるコードの解説

### `src/cmd/link/internal/ld/link.go`

```go
type LSym struct {
	// ...
	Sect        *Section
	Autom       []Auto // 変更点: *Auto から []Auto へ
	Pcln        *Pcln
	// ...
}

type Auto struct {
	Asym    *LSym
	Gotype  *LSym // 変更点: Link *Auto が削除され、Gotype の位置が移動
	Aoffset int32
	Name    int16
}
```

*   `LSym`構造体内の`Autom`フィールドが、`Auto`構造体のポインタの連結リストの先頭を表す`*Auto`から、`Auto`構造体のスライスである`[]Auto`に変更されました。これにより、`Autom`は連続したメモリ領域に`Auto`要素を保持するようになります。
*   `Auto`構造体から`Link *Auto`フィールドが削除されました。これは、`Autom`がスライスとして管理されるため、各`Auto`要素が次の要素へのポインタを持つ必要がなくなったためです。

### `src/cmd/link/internal/ld/objfile.go`

```go
// ...
	n := rdint(f) // 読み込むAuto要素の数
	s.Autom = make([]Auto, n) // 変更点: スライスを事前に必要なサイズで確保
	for i := 0; i < n; i++ {
		s.Autom[i] = Auto{ // 変更点: スライスの各要素に直接代入
			Asym:    rdsym(ctxt, f, pkg),
			Aoffset: rdint32(f),
			Name:    rdint16(f),
			Gotype:  rdsym(ctxt, f, pkg),
		}
	}
// ...
```

*   オブジェクトファイルから読み込む`Auto`要素の数`n`を最初に取得します。
*   `s.Autom = make([]Auto, n)`によって、`n`個の`Auto`要素を格納できるスライスが事前に確保されます。これにより、メモリの再割り当てを最小限に抑え、効率的なメモリ利用が可能になります。
*   ループ内で、読み込んだ`Auto`情報を`s.Autom[i]`に直接代入しています。以前の連結リストの構築では、新しい`Auto`要素を作成し、それを既存のリストの先頭に連結するという手順を踏んでいましたが、スライスではインデックスを使って直接要素を配置できます。この変更により、コードがより直接的で理解しやすくなりました。

これらの変更は、Goリンカの内部データ管理をより現代的で効率的なGoのスライスに移行させることで、全体的なパフォーマンスと保守性を向上させるものです。

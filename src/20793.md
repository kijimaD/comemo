# [インデックス 20793] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/ld`) におけるPE (Portable Executable) ファイル形式のセクション名処理に関するバグ修正です。具体的には、8文字を超えるセクション名が正しく解釈されない問題を解決します。

## 元コミット内容

`cmd/ld`: PEセクション名が8文字より長い場合に修正

gcc 4.9.1が8文字より長いPEセクション名を生成するようになりました。

`IMAGE_SECTION_HEADER`の定義によると：

Name
8バイトのNULL埋めUTF-8文字列。文字列がちょうど8文字の場合、終端のNULL文字はありません。より長い名前の場合、このメンバーはスラッシュ（/）の後に、文字列テーブルへのオフセットを示す10進数のASCII表現を含みます。

現在のPEオブジェクトファイルリーダーは、セクション名が`/`で始まる場合に文字列テーブルを読み込みません。これを修正することで、（issue 8811の例）

```
c:\go\path\src\isssue8811>go build
# isssue8811
isssue8811/glfw(.text): isssue8811/glfw(/76): not defined
isssue8811/glfw(.text): undefined: isssue8811/glfw(/76)
```

が、

```
c:\go\path\src\isssue8811>go build
# isssue8811
isssue8811/glfw(.text): isssue8811/glfw(.rdata$.refptr._glfwInitialized): not defined
isssue8811/glfw(.text): undefined: isssue8811/glfw(.rdata$.refptr._glfwInitialized)
```

となります。

issue 8811への小さな進捗です。

## 変更の背景

この変更の背景には、Go言語のリンカ (`cmd/ld`) がWindowsの実行可能ファイル形式であるPE (Portable Executable) ファイルを処理する際に、特定の条件下でセクション名を正しく解釈できないという問題がありました。

具体的には、`gcc 4.9.1`のような新しいバージョンのコンパイラが、PEファイルのセクション名として8文字を超える長い名前を生成するようになったことが発端です。PEファイルの仕様では、`IMAGE_SECTION_HEADER`構造体の`Name`フィールドは通常8バイトの固定長ですが、8文字を超えるセクション名の場合には、そのフィールドに直接名前を格納するのではなく、スラッシュ (`/`) の後に文字列テーブルへのオフセットを示す数値が格納されるという特殊なルールがあります。

Goのリンカは、この「スラッシュとオフセット」の形式で表現されたセクション名を正しく解決できず、結果としてリンカエラーが発生していました。コミットメッセージにある`isssue8811/glfw(/76): not defined`というエラーは、まさにこの問題を示しています。`/76`という部分が文字列テーブルへのオフセットを示しているにもかかわらず、リンカがそれをセクション名の一部として誤解釈し、未定義シンボルとして扱ってしまっていたのです。

この修正は、GoプログラムがWindows環境で外部ライブラリ（特にgccでコンパイルされたもの）とリンクする際の互換性を向上させ、ビルドエラーを解消することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

### 1. PE (Portable Executable) ファイル形式

PEは、Windowsオペレーティングシステムで使用される実行可能ファイル、オブジェクトファイル、DLL (Dynamic Link Library) などのファイル形式です。PEファイルは、ヘッダ、セクション、データなどの複数の部分で構成されており、プログラムの実行に必要な情報（コード、データ、リソースなど）が格納されています。

主要な構成要素は以下の通りです。
*   **DOS Header**: 互換性のための古いDOS実行可能ファイルヘッダ。
*   **PE Signature**: "PE\0\0"という署名。
*   **COFF File Header**: マシンタイプ、セクション数、シンボルテーブル情報など、ファイル全体の概要。
*   **Optional Header**: 実行可能ファイルの特性（エントリポイント、ベースアドレス、スタックサイズなど）を定義。
*   **Section Table**: 各セクション（コード、データ、リソースなど）の属性、サイズ、メモリ上の位置などを記述したエントリの配列。
*   **Sections**: 実際のコード、初期化済みデータ、未初期化データ、リソースなどが格納される領域。

### 2. IMAGE_SECTION_HEADER

PEファイル内の各セクションは、`IMAGE_SECTION_HEADER`という構造体で記述されます。この構造体には、セクション名、仮想アドレス、仮想サイズ、生データへのポインタ、生データサイズ、特性（読み取り可能、書き込み可能、実行可能など）といった情報が含まれています。

このコミットで特に重要なのは、`IMAGE_SECTION_HEADER`内の`Name`フィールドの扱いです。
*   **短いセクション名**: セクション名が8文字以下の場合、`Name`フィールドに直接NULL埋めされたUTF-8文字列として格納されます。
*   **長いセクション名**: セクション名が8文字を超える場合、`Name`フィールドには直接名前は格納されません。代わりに、スラッシュ (`/`) の後に、PEファイル内の**文字列テーブル (String Table)** へのオフセットを示す10進数のASCII表現が格納されます。リンカやローダーは、このオフセットを使って文字列テーブルから実際のセクション名を取得します。

### 3. 文字列テーブル (String Table)

PEファイルには、シンボル名やセクション名など、ファイル内で複数回参照される可能性のある長い文字列を効率的に格納するための文字列テーブルが存在します。これは、ファイルサイズを削減し、重複する文字列の管理を容易にするための仕組みです。`IMAGE_SECTION_HEADER`の`Name`フィールドが文字列テーブルへのオフセットを指す場合、リンカはこのテーブルを読み込んで実際のセクション名を解決する必要があります。

### 4. Go言語のリンカ (`cmd/ld`)

`cmd/ld`は、Go言語のコンパイラツールチェーンの一部であり、Goのソースコードから生成されたオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合して、最終的な実行可能ファイルやライブラリを生成する役割を担っています。このプロセスには、シンボルの解決、セクションの結合、アドレスの再配置などが含まれます。Windows環境では、`cmd/ld`はPEファイル形式の生成と解析を行います。

### 5. シンボル解決 (Symbol Resolution)

リンカの主要な機能の一つは、シンボル解決です。これは、あるオブジェクトファイルで参照されている関数や変数が、別のオブジェクトファイルで定義されている場合に、それらを正しく結びつけるプロセスです。セクション名が正しく解決できないと、リンカは必要なシンボルを見つけられず、「undefined reference」のようなエラーを報告します。

## 技術的詳細

このコミットの技術的詳細は、GoリンカがPEファイルのセクションヘッダを解析する際のロジックの改善にあります。

従来の`cmd/ld`のPEオブジェクトファイルリーダーは、`IMAGE_SECTION_HEADER`の`Name`フィールドがスラッシュ (`/`) で始まる場合に、それが文字列テーブルへのオフセットを示す特殊な形式であるということを認識していませんでした。そのため、セクション名が8文字を超える場合に、リンカは`/`に続く数値をセクション名の一部として誤って解釈し、結果として正しいセクション名を見つけられず、シンボル解決に失敗していました。

この修正では、`src/cmd/ld/ldpe.c`ファイル内のPEオブジェクトファイル読み込みロジックに、以下の処理が追加されました。

1.  **セクション名のチェック**: 各セクションの`Name`フィールドをループで確認します。
2.  **スラッシュの検出**: `Name`フィールドの最初の文字がスラッシュ (`/`) であるかどうかをチェックします。
3.  **オフセットの解析**: もし最初の文字がスラッシュであれば、その後の文字列を`atoi`関数（ASCII文字列を整数に変換）を使って数値に変換し、文字列テーブルへのオフセットとして解釈します。
4.  **文字列テーブルからの名前取得**: 変換されたオフセット値を使用して、PEファイル内の文字列テーブルから実際のセクション名を取得し、`obj->sect[i].name`をその正しい文字列へのポインタで上書きします。

この変更により、リンカは8文字を超えるセクション名も正しく解決できるようになり、`gcc 4.9.1`のような新しいコンパイラが生成するPEオブジェクトファイルとの互換性が確保されました。コミットメッセージの例で示されているように、`isssue8811/glfw(/76)`のような誤ったセクション名が、`isssue8811/glfw(.rdata$.refptr._glfwInitialized)`のような正しいセクション名に解決されるようになります。これは、リンカがシンボルを正しく見つけられるようになるための重要なステップです。

## コアとなるコードの解説

追加されたコードブロックは、`ldpe`関数内でPEファイルのセクションヘッダを読み込んだ直後に実行されます。

```c
// rewrite section names if they start with /
for(i=0; i < obj->fh.NumberOfSections; i++) {
    if(obj->sect[i].name == nil)
        continue;
    if(obj->sect[i].name[0] != '/')
        continue;
    l = atoi(obj->sect[i].name + 1);
    obj->sect[i].name = (char*)&obj->snames[l];
}
```

1.  `for(i=0; i < obj->fh.NumberOfSections; i++)`:
    *   PEファイル内のすべてのセクションヘッダをループで処理します。`obj->fh.NumberOfSections`は、ファイルヘッダから取得したセクションの総数です。

2.  `if(obj->sect[i].name == nil)`:
    *   現在のセクションの`name`フィールドがNULLポインタである場合は、処理をスキップします。これは異常な状態か、あるいは特定のセクションが名前を持たない場合（稀ですが）を考慮している可能性があります。

3.  `if(obj->sect[i].name[0] != '/')`:
    *   セクション名の最初の文字がスラッシュ (`/`) でない場合は、処理をスキップします。これは、セクション名が8文字以下で直接`Name`フィールドに格納されている通常のケースです。このコミットの対象外のセクションです。

4.  `l = atoi(obj->sect[i].name + 1);`:
    *   セクション名がスラッシュで始まる場合、PEファイルの仕様に従い、スラッシュの直後から始まる文字列が文字列テーブルへのオフセットを示す10進数であると解釈します。
    *   `obj->sect[i].name + 1` は、スラッシュの次の文字へのポインタを渡すことで、`atoi`関数が数値部分のみを解析するようにします。
    *   結果として得られた整数値 `l` は、文字列テーブルの先頭からのバイトオフセットを表します。

5.  `obj->sect[i].name = (char*)&obj->snames[l];`:
    *   これがこの修正の核心部分です。
    *   `obj->snames` は、PEファイルの文字列テーブル全体を保持しているメモリ領域へのポインタです。
    *   `obj->snames[l]` は、文字列テーブルの先頭から`l`バイト目のアドレスを指します。このアドレスには、実際の長いセクション名が格納されています。
    *   `obj->sect[i].name` をこの新しいアドレスに設定することで、セクションヘッダの`Name`フィールドが、文字列テーブル内の正しいセクション名を指すように「書き換え」られます。

この一連の処理により、GoリンカはPEファイルのセクション名を正しく解決できるようになり、Windows環境でのビルドの信頼性が向上しました。

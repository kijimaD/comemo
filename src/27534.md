# [インデックス 27534] ファイルの概要

このコミットは、Go言語の `compress/flate` パッケージにおける `Reader.Read` メソッドの挙動を修正し、可能な限り `io.EOF` を早期に返すように変更するものです。これにより、特に `net/http` パッケージでのHTTP/1コネクションの再利用効率が向上し、`ioutil.ReadAll` のような操作のパフォーマンス改善にも寄与します。

    compress/flate: make Reader.Read return io.EOF eagerly

    Rather than checking the block final bit on the next invocation
    of nextBlock, we check it at the termination of the current block.
    This ensures that we return (n, io.EOF) instead of (0, io.EOF)
    more frequently for most streams.

    However, there are certain situations where an eager io.EOF is not done:
    1) We previously returned from Read because the write buffer of the internal
    dictionary was full, and it just so happens that there is no more data
    remaining in the stream.
    2) There exists a [non-final, empty, raw block] after all blocks that
    actually contain uncompressed data. We cannot return io.EOF eagerly here
    since it would break flushing semantics.

    Both situations happen infrequently, but it is still important to note that
    this change does *not* guarantee that flate will *always* return (n, io.EOF).

    Furthermore, this CL makes no changes to the pattern of ReadByte calls
    to the underlying io.ByteReader.

    Below is the motivation for this change, pulling the text from
    @bradfitz's CL/21290:

    net/http and other things work better when io.Reader implementations
    return (n, io.EOF) at the end, instead of (n, nil) followed by (0,
    io.EOF). Both are legal, but the standard library has been moving
    towards n+io.EOF.

    An investigation of net/http connection re-use in
    https://github.com/google/go-github/pull/317 revealed that with gzip
    compression + http/1.1 chunking, the net/http package was not
    automatically reusing the underlying TCP connections when the final

    reuses the connection if the underlying Readers (many of them nested

## 変更の背景

この変更の主な背景には、Go言語の標準ライブラリにおける `io.Reader` インターフェースの実装が、ストリームの終端を示す `io.EOF` をどのように返すかという問題がありました。

Goの `io.Reader` インターフェースの `Read` メソッドは、`Read(p []byte) (n int, err error)` というシグネチャを持ちます。ここで `n` は読み込んだバイト数、`err` は発生したエラーです。ストリームの終端に達した場合、`err` に `io.EOF` を返すことが期待されます。しかし、この `io.EOF` を返すタイミングには2つの一般的なパターンがありました。

1.  **遅延EOF (Delayed EOF)**: データをすべて読み込んだ後、次の `Read` 呼び出しで `(0, io.EOF)` を返すパターン。つまり、最後のデータは `(n, nil)` で返され、その後に終端を示す `(0, io.EOF)` が返されます。
2.  **早期EOF (Eager EOF)**: 最後のデータを読み込んだ際に、そのデータと共に `(n, io.EOF)` を返すパターン。これにより、ストリームの終端がより早く通知されます。

Goの標準ライブラリは、特に `net/http` パッケージにおいて、HTTP/1.1のコネクション再利用の効率を最大化するために、早期EOFのパターンに移行しつつありました。`net/http` パッケージは、基盤となるTCPコネクションを再利用する際に、ネストされたすべての `io.Reader` がストリームの終端で `(n, io.EOF)` を返すことを期待します。もし `(n, nil)` の後に `(0, io.EOF)` が返される場合、`net/http` はコネクションが完全に読み取られていないと判断し、再利用せずに閉じてしまう可能性がありました。

具体的には、`google/go-github` リポジトリのプルリクエスト #317 で、`gzip` 圧縮とHTTP/1.1チャンク転送を組み合わせた際に、`net/http` がTCPコネクションを再利用しない問題が報告されました。これは、`compress/flate` パッケージの `Reader` が早期に `io.EOF` を返していなかったため、`net/http` がストリームの終端を正しく認識できなかったことに起因します。

また、`ioutil.ReadAll` のような関数も、早期EOFの恩恵を受けます。`ioutil.ReadAll` は内部的にループで `Read` を呼び出し、`io.EOF` が返されるまでデータを読み込み続けます。早期EOFにより、余分な `Read` 呼び出しを1回減らすことができ、特に小さなデータストリームや多数のストリームを処理する場合にパフォーマンスが向上します。

このコミットは、これらの問題を解決し、Go標準ライブラリ全体で早期EOFの挙動を統一する流れに沿ったものです。

## 前提知識の解説

### `io.Reader` インターフェースと `io.EOF`

Go言語の `io.Reader` インターフェースは、バイトストリームからの読み込みを抽象化するための基本的なインターフェースです。その `Read` メソッドは `Read(p []byte) (n int, err error)` と定義されており、`p` に最大 `len(p)` バイトを読み込み、実際に読み込んだバイト数 `n` とエラー `err` を返します。

`io.EOF` は、`io` パッケージで定義されている特別なエラー値で、入力ストリームの終端に達したことを示します。`Read` メソッドが `io.EOF` を返す場合、それ以上読み込むデータがないことを意味します。

`io.Reader` の実装において、`io.EOF` の返し方には以下の2つのパターンが許容されますが、早期EOFが推奨されています。

*   **`Read` が `(n > 0, nil)` を返し、その後の `Read` が `(0, io.EOF)` を返す。**
*   **`Read` が `(n > 0, io.EOF)` を返す。**

後者の「早期EOF」は、特にネットワークプロトコルやストリーム処理において、終端の検出を効率化し、リソースの解放や再利用を早めるために重要です。

### `compress/flate` パッケージ

`compress/flate` パッケージは、DEFLATEアルゴリズム（RFC 1951で定義）の実装を提供します。これは、`gzip` や `zip` などのより高レベルな圧縮形式の基盤となるアルゴリズムです。このパッケージは、圧縮データからの読み込み（`flate.Reader`）と圧縮データへの書き込み（`flate.Writer`）を提供します。

### HTTP/1.1 コネクション再利用

HTTP/1.1では、`Keep-Alive` ヘッダやチャンク転送エンコーディングを使用することで、単一のTCPコネクション上で複数のリクエスト/レスポンスをやり取りし、コネクションの再利用を可能にします。これにより、TCPハンドシェイクのオーバーヘッドを削減し、パフォーマンスを向上させることができます。

`net/http` パッケージのクライアント側では、レスポンスボディの読み込みが完了したことを正確に検出し、基盤となるTCPコネクションをプールに戻して再利用できるようにする必要があります。この検出が不正確だと、コネクションが不必要に閉じられ、パフォーマンスが低下します。

### `ioutil.ReadAll`

`io/ioutil` パッケージ（Go 1.16以降は `io` パッケージに移行）の `ReadAll` 関数は、`io.Reader` から `io.EOF` が返されるまですべてのデータを読み込み、`[]byte` スライスとして返します。この関数は、ストリームの終端を検出するために `Read` メソッドを繰り返し呼び出すため、早期EOFの恩恵を大きく受けます。

## 技術的詳細

このコミットの技術的な核心は、`compress/flate` パッケージの `decompressor` 構造体（`flate.Reader` の内部実装）が、圧縮ブロックの終端を検出した際に、`io.EOF` をより積極的に返すように変更された点にあります。

以前の実装では、`decompressor.nextBlock()` メソッド内で `f.final` フラグ（ストリームの最終ブロックであるかを示す）をチェックし、`io.EOF` を設定していました。しかし、このチェックは次のブロックの処理が開始される前に行われていたため、現在のブロックのデータがすべて読み出された直後には `io.EOF` が返されず、次の `Read` 呼び出しで初めて `(0, io.EOF)` が返されるという遅延EOFの挙動を示すことがありました。

この変更では、`decompressor.nextBlock()` から `f.final` のチェックを削除し、代わりに `decompressor.finishBlock()` という新しいヘルパーメソッドを導入しました。この `finishBlock()` メソッドは、現在のブロックの処理が完了した直後（例えば、ハフマンブロックの終端マーカー `256` を検出した後や、非圧縮ブロックのデータがすべて読み出された後）に呼び出されます。

`finishBlock()` メソッド内で `f.final` が `true` であれば、`f.err` に `io.EOF` を設定します。これにより、現在の `Read` 呼び出しがデータを返し終えた直後に、その `Read` 呼び出しが `(n, io.EOF)` を返すことが可能になります。

ただし、コミットメッセージにも記載されているように、以下の2つの状況では早期EOFが保証されません。

1.  **内部辞書の書き込みバッファが満杯になったために `Read` が返された場合**: `decompressor` の内部辞書（`dict`）の書き込みバッファが満杯になり、`Read` が途中でデータを返さざるを得なかった場合、その時点でストリームの終端に達していても、`io.EOF` を早期に返すことはできません。これは、`Read` がバッファの空き容量に応じてデータを返すという `io.Reader` の一般的な契約によるものです。
2.  **非最終の空の生ブロックが、データを含むすべてのブロックの後に存在する場合**: DEFLATEストリームには、データを含まないがストリームの終端ではない「空のブロック」が存在することがあります。このようなブロックがデータの後に続く場合、`flate` リーダーはフラッシュセマンティクスを維持するために、その空のブロックを処理し終えるまで `io.EOF` を返すことができません。

これらの例外は稀なケースであり、この変更が `flate.Reader` の全体的な挙動を早期EOFの方向にシフトさせるという目的は達成されます。

また、この変更は基盤となる `io.ByteReader` への `ReadByte` 呼び出しのパターンには影響を与えません。

## コアとなるコードの変更箇所

このコミットでは、主に以下の2つのファイルが変更されています。

1.  `src/compress/flate/flate_test.go`:
    *   `TestReaderEarlyEOF` という新しいテスト関数が追加されました。このテストは、`flate.Reader.Read` が可能な限り `(n, io.EOF)` を返すことを検証します。様々なデータサイズとフラッシュの有無の組み合わせでテストを行い、特定の条件下（内部辞書バッファが満杯、またはフラッシュ後に空のブロックが存在する場合）で早期EOFが期待されないケースも考慮に入れています。

2.  `src/compress/flate/inflate.go`:
    *   `decompressor.nextBlock()` メソッドから、`f.final` に基づく `io.EOF` の設定ロジックが削除されました。
    *   `decompressor.Read()` メソッド内で、`f.toRead` が空になった直後に `return n, f.err` を追加し、`f.err` に `io.EOF` が設定されていればそれを返すように変更されました。
    *   `readLiteral` ラベル内のハフマンブロック終端 (`v == 256`) を処理する箇所で、以前は `f.step = (*decompressor).nextBlock` だったものが `f.finishBlock()` の呼び出しに変更されました。
    *   `decompressor.dataBlock()` メソッド内で、非圧縮ブロックのデータがすべて読み出された後に `f.step = (*decompressor).nextBlock` だったものが `f.finishBlock()` の呼び出しに変更されました。
    *   `decompressor.copyData()` メソッドの終端で `f.finishBlock()` が呼び出されるようになりました。
    *   `finishBlock()` という新しいプライベートメソッドが追加されました。このメソッドは、ブロックの処理が完了した際に呼び出され、`f.final` が `true` であれば `f.err = io.EOF` を設定します。また、`f.dict.availRead() > 0` の場合は `f.toRead` に残りのデータを設定します。

## コアとなるコードの解説

### `src/compress/flate/inflate.go` の変更点

**`decompressor.nextBlock()` からの `io.EOF` 処理の削除:**
```go
-	if f.final {
-		if f.dict.availRead() > 0 {
-			f.toRead = f.dict.readFlush()
-			f.step = (*decompressor).nextBlock
-			return
-		}
-		f.err = io.EOF
-		return
-	}
```
このコードは、`nextBlock` が呼び出されたときにストリームが最終ブロックであるかをチェックし、もしそうであれば `io.EOF` を設定していました。このロジックが削除されたことで、`io.EOF` の設定タイミングがブロックの終端処理に移動しました。

**`decompressor.Read()` 内での早期 `io.EOF` 返却:**
```go
 		if len(f.toRead) > 0 {
 			n := copy(b, f.toRead)
 			f.toRead = f.toRead[n:]
+			if len(f.toRead) == 0 {
+				return n, f.err
+			}
 			return n, nil
 		}
```
`f.toRead` は、デコードされた非圧縮データが一時的に保持されるバッファです。このバッファから `b` にデータをコピーし終えた (`len(f.toRead) == 0`) 直後に、`f.err` に `io.EOF` が設定されていれば、その `io.EOF` を `n` バイトと共に返すようになりました。これにより、データが完全に読み出された直後に `io.EOF` が通知される「早期EOF」の挙動が実現されます。

**`finishBlock()` メソッドの導入と呼び出し:**
```go
 		case v == 256:
-			// Done with huffman block; read next block.
-			f.step = (*decompressor).nextBlock
+			f.finishBlock()
 			return
```
```go
 	if n == 0 {
 		f.toRead = f.dict.readFlush()
-		f.step = (*decompressor).nextBlock
+		f.finishBlock()
 		return
 	}
```
```go
 	// ... (decompressor.copyData() の終端)
+	f.finishBlock()
 }

 func (f *decompressor) finishBlock() {
 	if f.final {
 		if f.dict.availRead() > 0 {
 			f.toRead = f.dict.readFlush()
 		}
 		f.err = io.EOF
 	}
 	f.step = (*decompressor).nextBlock
 }
```
`finishBlock()` は、ハフマンブロックの終端マーカー (256) を検出した際や、非圧縮ブロックのデータがすべて処理された際に呼び出されます。このメソッド内で `f.final` が `true` であれば、`f.err = io.EOF` が設定されます。これにより、ブロックの終端でストリームの終端が検出され、`decompressor.Read()` が `(n, io.EOF)` を返す準備が整います。

### `src/compress/flate/flate_test.go` の変更点

`TestReaderEarlyEOF` は、この変更の意図を明確に検証するための重要なテストです。
このテストは、様々なサイズのデータと、`flate.Writer` で `Flush()` を呼び出すかどうかの組み合わせで `flate.Reader` の挙動をテストします。

特に注目すべきは、以下のロジックです。
```go
 					if n == 0 && earlyEOF {
 						t.Errorf("On size:%d flush:%v, Read() = (0, io.EOF), want (n, io.EOF)", sz, flush)
 					}
 					if n != 0 && !earlyEOF {
 						t.Errorf("On size:%d flush:%v, Read() = (%d, io.EOF), want (0, io.EOF)", sz, flush, n)
 					}
```
`earlyEOF` は、このテストケースで早期EOFが期待されるかどうかを示すフラグです。
*   `n == 0 && earlyEOF` の場合、データが残っているにもかかわらず `(0, io.EOF)` が返されたらエラーとします。これは、早期EOFが期待される状況で遅延EOFが発生したことを意味します。
*   `n != 0 && !earlyEOF` の場合、早期EOFが期待されない状況（例えば、`Flush()` が行われた後）で `(n, io.EOF)` が返されたらエラーとします。これは、コミットメッセージで述べられている例外ケースをテストしています。

このテストは、`flate.Reader` が `io.EOF` を返すタイミングの複雑さを考慮しつつ、新しい挙動が正しく実装されていることを確認しています。

## 元コミット内容

```
runtime: add a constant for the smallest possible stack frame

Shared libraries on ppc64le will require a larger minimum stack frame (because
the ABI mandates that the TOC pointer is available at 24(R1)). So to prepare
for this, make a constant for the fixed part of a stack and use that where
necessary.
```

## 変更の背景

この変更の主な背景は、`ppc64le`アーキテクチャにおける共有ライブラリのABI（Application Binary Interface）要件への対応です。`ppc64le`のABIでは、TOC（Table Of Contents）ポインタがスタックポインタ（R1レジスタ）から24バイトオフセットの位置に配置されることが義務付けられています。これは、関数呼び出し時にTOCポインタが常にアクセス可能であることを保証するためです。

Goランタイムは、独自のスタック管理メカニズムを持っていますが、共有ライブラリとの連携（特にCgoを介した呼び出し）においては、ターゲットアーキテクチャのABIに準拠する必要があります。このABI要件を満たすためには、Goランタイムが確保するスタックフレームの最小サイズが、TOCポインタを格納できるだけの十分な大きさを持つ必要があります。

このコミットは、将来的に`ppc64le`で共有ライブラリをより適切にサポートするための準備として、スタックフレームの「固定部分」のサイズを抽象化し、`minFrameSize`という定数として導入しました。これにより、各アーキテクチャ固有のスタックフレームの最小要件を統一的に管理し、コードの可読性と保守性を向上させるとともに、将来的なABI変更への対応を容易にしています。

## 前提知識の解説

### スタックフレーム (Stack Frame)
関数が呼び出されるたびに、その関数のローカル変数、引数、戻りアドレス、およびレジスタの退避領域などを格納するために、スタック上に確保されるメモリ領域のことです。スタックフレームの構造は、CPUアーキテクチャやABIによって異なります。

### ABI (Application Binary Interface)
アプリケーションバイナリインターフェースは、コンパイルされたプログラム（バイナリ）がオペレーティングシステムや他のライブラリとどのようにやり取りするかを定義する一連の規則です。これには、関数呼び出し規約（引数の渡し方、戻り値の受け取り方）、レジスタの使用規約、スタックフレームのレイアウトなどが含まれます。ABIに準拠することで、異なるコンパイラや言語で作成されたバイナリコードが相互運用できるようになります。

### TOC (Table Of Contents) ポインタ
`ppc64le`のような一部のアーキテクチャでは、プログラムがグローバルデータや関数にアクセスするためにTOC（Table Of Contents）と呼ばれるデータ構造を使用します。TOCは、これらのシンボルへのポインタのテーブルであり、TOCポインタはTOCのベースアドレスを指します。`ppc64le`のABIでは、TOCポインタが特定のレジスタ（R2）に保持され、さらにスタックフレーム内の固定オフセットにも保存されることが要求される場合があります。これにより、関数呼び出しの前後でTOCポインタが確実に利用可能になります。

### `ppc64le` アーキテクチャ
`ppc64le`は、IBM PowerPC 64ビットプロセッサのLittle-Endian版アーキテクチャです。Linux環境で広く使用されており、特に高性能コンピューティングやサーバーワークロードで利用されます。`ppc64le`のABIは、他のアーキテクチャ（例: `x86-64`）とは異なるスタックフレームのレイアウトやレジスタ使用規約を持っています。

### Goランタイムのスタック管理
Goランタイムは、独自のグロースタブル（可変長）なスタックを各ゴルーチンに割り当てて管理します。これは、C言語などの固定長スタックとは異なり、必要に応じてスタックを拡張・縮小できる柔軟な仕組みです。しかし、Cgoを介してC関数を呼び出す場合や、OSのシグナルハンドラなど、Goランタイムの外部と連携する際には、OSやターゲットアーキテクチャのABIに準拠したスタックフレームを構築する必要があります。

## 技術的詳細

このコミットの核心は、Goランタイムが各アーキテクチャで必要とする最小のスタックフレームサイズを`minFrameSize`という定数として抽象化し、これまでのハードコードされた値やアーキテクチャごとの条件分岐を置き換えることです。

具体的には、以下の点が技術的な詳細として挙げられます。

1.  **`minFrameSize`の導入**:
    *   `src/runtime/arch_*.go`ファイル群（`arch_386.go`, `arch_amd64.go`, `arch_amd64p32.go`, `arch_arm.go`, `arch_arm64.go`, `arch_ppc64.go`, `arch_ppc64le.go`）に`minFrameSize`定数が追加されました。
    *   `386`, `amd64`, `amd64p32`では`0`に設定されています。これは、これらのアーキテクチャでは特別な固定フレームサイズが不要であることを示唆しています。
    *   `arm`では`4`バイト、`arm64`, `ppc64`, `ppc64le`では`8`バイトに設定されています。これは、これらのアーキテクチャでリンクレジスタ（LR）やTOCポインタなどの固定情報がスタックフレームの先頭に格納されるため、その分の領域を確保する必要があることを反映しています。特に`ppc64le`の`8`バイトは、TOCポインタのABI要件に対応するための準備です。

2.  **`cgocall.go`におけるスタックフレーム計算の変更**:
    *   `cgocallbackg1`関数内で、`ppc64`および`ppc64le`アーキテクチャにおけるCgoコールバックの引数ポインタ`cb`の計算が変更されました。以前は`sp + 4*ptrSize`というハードコードされたオフセットが使われていましたが、`sp + 2*minFrameSize + 2*ptrSize`という`minFrameSize`を用いた計算に置き換えられました。これにより、`ppc64le`のABI要件に柔軟に対応できるようになります。
    *   `unwindm`関数では、スタックポインタの巻き戻し処理において、`386`, `amd64`, `arm`, `ppc64`, `ppc64le`アーキテクチャで`sched.sp = *(*uintptr)(unsafe.Pointer(sched.sp + minFrameSize))`が使用されるようになりました。これにより、各アーキテクチャの最小フレームサイズを考慮した正確なスタックポインタの調整が可能になります。以前はアーキテクチャごとに異なるハードコードされたオフセット（例: `arm`では`4`、`ppc64`では`8`）が使われていました。

3.  **`mgcmark.go`および`stack.go`におけるスタックフレームサイズの計算**:
    *   ガベージコレクタのスタック走査 (`scanframeworker`) やスタックフレーム調整 (`adjustframe`) のロジックにおいて、`minsize`の計算が変更されました。以前は`thechar`（アーキテクチャを示す文字）に基づいてハードコードされた値（`0`や`ptrSize`）が使われていましたが、`minFrameSize`がデフォルト値として使用されるようになりました。これにより、スタックフレームの最小サイズに関するロジックが一元化され、より正確なスタック走査が可能になります。

4.  **`panic.go`における`hasLinkRegister`の削除**:
    *   `panic.go`から`hasLinkRegister`定数が削除されました。この定数は、リンクレジスタを持つアーキテクチャを識別するために使われていましたが、`minFrameSize`の導入により、`usesLR`定数が`minFrameSize > 0`という条件で定義されるようになったため、冗長になりました。

5.  **`proc1.go`における新しいゴルーチンのスタック初期化**:
    *   `newproc1`関数（新しいゴルーチンを初期化する関数）において、新しいゴルーチンのスタックサイズ計算が変更されました。以前は`hasLinkRegister`に基づいて`ptrSize`が追加されていましたが、`minFrameSize`が直接`totalSize`に加算されるようになりました。また、`usesLR`の定義も`minFrameSize > 0`に変更されたため、リンクレジスタの有無に応じたスタックポインタの調整も`minFrameSize`に基づいて行われるようになりました。

6.  **`signal_ppc64x.go`におけるシグナルハンドラのスタック調整**:
    *   `ppc64x`アーキテクチャのシグナルハンドラにおいて、スタックポインタの調整が`c.sp() - ptrSize`から`c.sp() - minFrameSize`に変更されました。これにより、シグナルハンドラがスタックを操作する際に、アーキテクチャ固有の最小フレームサイズを考慮した正確な調整が行われます。

7.  **`traceback.go`におけるスタックトレースの調整**:
    *   スタックトレース生成 (`gentraceback`) および引数情報設定 (`setArgInfo`) のロジックにおいて、`usesLR`の定義が`minFrameSize > 0`に変更されました。また、`frame.argp`の計算やスタックポインタの調整も`minFrameSize`に基づいて行われるようになりました。これにより、スタックトレースがより正確に生成され、引数情報も正しく取得できるようになります。

これらの変更により、Goランタイムは各アーキテクチャのスタックフレームの最小要件をより統一的かつ正確に扱うことができるようになり、特に`ppc64le`のような特定のABI要件を持つアーキテクチャへの対応が強化されました。

## コアとなるコードの解説

このコミットの主要な変更は、`minFrameSize`という新しい定数を導入し、Goランタイム内のスタック関連の計算をこの定数に基づいて統一した点にあります。

1.  **`minFrameSize`の定義**:
    *   各アーキテクチャ（`386`, `amd64`, `arm`, `arm64`, `ppc64`, `ppc64le`など）に対応する`src/runtime/arch_*.go`ファイルに`minFrameSize`定数が追加されました。
    *   この定数は、そのアーキテクチャで関数呼び出し時にスタックフレームの固定部分として最低限必要となるサイズを示します。例えば、`ppc64le`では`8`バイトに設定されており、これはABIで要求されるTOCポインタの格納領域を考慮したものです。`386`や`amd64`では`0`となっており、これらのアーキテクチャでは特別な固定フレームサイズが不要であることを意味します。

2.  **`cgocall.go`におけるスタックフレームの調整**:
    *   `cgocallbackg1`関数は、Cgoを介してGo関数がCコードから呼び出される際のコールバック処理を担当します。`ppc64`および`ppc64le`アーキテクチャでは、コールバック引数の位置を計算する際に、以前はハードコードされたオフセット（`4*ptrSize`）が使われていましたが、`2*minFrameSize + 2*ptrSize`という`minFrameSize`を考慮した計算に置き換えられました。これにより、`ppc64le`のABIに準拠した正確な引数ポインタの特定が可能になります。
    *   `unwindm`関数は、スタックを巻き戻す際にスタックポインタを調整します。以前はアーキテクチャごとに異なるハードコードされたオフセット（例: `arm`では`4`、`ppc64`では`8`）が使われていましたが、`minFrameSize`を使用することで、`sched.sp = *(*uintptr)(unsafe.Pointer(sched.sp + minFrameSize))`という統一されたロジックでスタックポインタを調整できるようになりました。これは、各アーキテクチャの最小フレームサイズを考慮した、より汎用的なスタック巻き戻し処理を実現します。

3.  **ガベージコレクタとスタックフレーム調整**:
    *   `mgcmark.go`の`scanframeworker`関数と`stack.go`の`adjustframe`関数は、ガベージコレクションやスタックの拡張・縮小時にスタックフレームを走査・調整します。これらの関数では、スタックフレームの最小サイズ`minsize`を決定する際に、以前はアーキテクチャを示す文字（`thechar`）に基づいてハードコードされた値が使われていましたが、`minFrameSize`がデフォルト値として使用されるようになりました。これにより、スタックフレームの最小要件に関するロジックが一元化され、ガベージコレクタがスタックをより正確に理解し、処理できるようになります。

4.  **`usesLR`定数の再定義と`hasLinkRegister`の削除**:
    *   `traceback.go`では、リンクレジスタ（LR）を使用するアーキテクチャを識別するための`usesLR`定数が、以前の`GOARCH != "amd64" && GOARCH != "amd64p32" && GOARCH != "386"`という条件から、よりシンプルで汎用的な`minFrameSize > 0`に再定義されました。これは、`minFrameSize`がリンクレジスタの有無やその他の固定フレーム要件を暗黙的に含んでいるためです。
    *   `panic.go`から`hasLinkRegister`定数が削除されました。これは`usesLR`の再定義により冗長になったためです。

5.  **新しいゴルーチンのスタック初期化**:
    *   `proc1.go`の`newproc1`関数は、新しいゴルーチンが作成される際にそのスタックを初期化します。スタックの合計サイズを計算する際に、以前は`hasLinkRegister`に基づいて`ptrSize`が追加されていましたが、`minFrameSize`が直接`totalSize`に加算されるようになりました。これにより、新しいゴルーチンのスタックが、そのアーキテクチャの最小フレームサイズを考慮して適切に確保されることが保証されます。また、リンクレジスタの保存位置の調整も`usesLR`（`minFrameSize > 0`）に基づいて`minFrameSize`を使用するようになりました。

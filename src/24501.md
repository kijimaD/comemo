# [インデックス 24501] ファイルの概要

このコミットは、Go 1.5で導入されたベンダー実験（vendor experiment）において発生していた、パッケージの重複ロードとエラー伝播の問題を修正するものです。具体的には、`p/vendor/x` と `x` のように、同じディレクトリが異なるパスでインポートされることを防ぎ、ビルドプロセスにおけるエラーの伝播を改善し、重複したパッケージのビルドジョブが生成されることによる奇妙なビルド失敗を防ぎます。

## 元コミット内容

`cmd/go: fix disallow of p/vendor/x during vendor experiment`

このコミットは、Goのベンダー実験中に `p/vendor/x` のようなパスが許可されないようにする修正です。ロードプロセスにおけるエラーの伝播が不完全であったため、ビルドツリーが処理順序によっては同じディレクトリを `p/vendor/x` と `x` の両方としてインポートしてしまう可能性がありました。これは本来許されない動作です。さらに悪いことに、ビルドはこのディレクトリに対して2つのビルドジョブを生成し、それらが同じワークスペースを使用してお互いのファイルを上書きし、非常に奇妙な失敗を引き起こしていました。

この問題に対処するため、以下の2つの修正が行われました。

1.  エラーの伝播を修正し、成功よりもエラーを優先するようにしました。
2.  ビルドを開始する前に、重複したパッケージがロードされていないかを明示的にチェックするようにしました。

修正1に対しては新しいテストが追加されました。修正2は、修正1が適用されている状態では発生し得ないため、修正1を元に戻した上で手動でテストされました。

このコミットは Issue #11913 を修正します。

## 変更の背景

Go 1.5で導入されたベンダー実験は、Goの依存関係管理における重要な一歩でした。この機能は、プロジェクトのルートディレクトリにある `vendor/` ディレクトリ内のパッケージを優先的に解決することで、依存関係の分離と再現可能なビルドを可能にすることを目的としていました。しかし、この実験的な機能の初期段階では、いくつかの予期せぬ問題が発生しました。

このコミットの背景にある主な問題は、`go` コマンドがパッケージをロードする際の内部的な不整合でした。具体的には、以下の2つの問題が複合的に発生していました。

1.  **エラー伝播の不備**: パッケージのロードプロセスにおいて、エラーが適切に上位に伝播されないことがありました。これにより、本来エラーとして扱われるべき状況が無視され、ビルドプロセスが不健全な状態に進んでしまう可能性がありました。
2.  **パッケージの重複ロード**: エラー伝播の問題と関連して、`go` コマンドが同じ物理的なディレクトリにあるパッケージを、異なるインポートパス（例: `x` と `p/vendor/x`）で複数回ロードしてしまうことがありました。これは、ベンダー実験の意図に反する動作であり、特に `vendor/` ディレクトリ内のパッケージが、そのベンダーディレクトリの外からも参照される場合に顕著でした。

これらの問題が組み合わさることで、ビルドシステムは同じパッケージに対して複数のビルドジョブを生成し、それらのジョブが同じ出力ファイルを同時に書き込もうとする「競合状態」に陥りました。結果として、ビルドは予測不能な失敗（"very strange failures"）を引き起こし、開発者の混乱を招いていました。

Issue #11913 は、この「内部エラー: 重複ロード」の問題を具体的に報告しており、特に `go get -v all` のようなコマンドで顕在化していました。このコミットは、これらの根本原因に対処し、ベンダー実験の堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念と背景知識が必要です。

### Go Modules以前の依存関係管理とGOPATH

Go 1.11でGo Modulesが導入されるまで、Goのプロジェクトは `$GOPATH` という環境変数に依存していました。`$GOPATH` はGoのワークスペースのルートディレクトリを指定し、ソースコード、コンパイル済みパッケージ、実行可能ファイルがこのディレクトリ構造内に配置されました。

*   **`src`**: ソースコードが配置されるディレクトリ。`go get` コマンドで取得した外部パッケージもここに保存されました。
*   **`pkg`**: コンパイル済みのパッケージオブジェクトが保存されるディレクトリ。
*   **`bin`**: コンパイル済みの実行可能ファイルが保存されるディレクトリ。

`GOPATH` モデルの課題は、異なるプロジェクトが同じ依存パッケージの異なるバージョンを必要とする場合に、バージョン競合が発生しやすい点でした。すべての依存関係が `$GOPATH/src` に一元的に管理されるため、プロジェクトAがパッケージXのv1を必要とし、プロジェクトBがパッケージXのv2を必要とする場合、どちらか一方しか `$GOPATH` に存在できず、問題を引き起こしました。

### ベンダー実験 (Vendor Experiment)

`GOPATH` の課題を解決するための一歩として、Go 1.5で「ベンダー実験（Vendor Experiment）」が導入されました。これは、プロジェクト固有の依存関係を管理するためのメカニズムです。

*   **`vendor/` ディレクトリ**: プロジェクトのルートディレクトリ直下に `vendor/` という名前のディレクトリを作成し、その中にプロジェクトが依存する外部パッケージのソースコードを配置します。
*   **解決順序**: `go` コマンドは、パッケージをインポートする際に、まず現在のパッケージの `vendor/` ディレクトリ内を検索し、次に `$GOPATH/src`、最後に `$GOROOT/src` を検索します。これにより、プロジェクトは `$GOPATH` にあるグローバルなバージョンではなく、`vendor/` ディレクトリ内の特定のバージョンの依存関係を使用できるようになります。
*   **`GO15VENDOREXPERIMENT`**: Go 1.5では、この機能はデフォルトでは無効になっており、環境変数 `GO15VENDOREXPERIMENT=1` を設定することで有効にする必要がありました。Go 1.6からはデフォルトで有効になりました。

このベンダー実験は、Go Modulesへの移行期間における重要なステップであり、依存関係管理の改善に向けたコミュニティとGoチームの取り組みを示しています。

### パッケージのロードとビルドプロセス

Goのビルドプロセスは、ソースコードをコンパイルして実行可能ファイルを生成する一連のステップです。これには、依存関係の解決、パッケージのロード、コンパイル、リンクが含まれます。

*   **パッケージのロード**: `go` コマンドは、ビルド対象のパッケージとその依存関係を特定し、それらのソースコードをファイルシステムから読み込みます。この際、インポートパスに基づいて適切なパッケージを見つけ出す必要があります。
*   **ビルドグラフ**: 依存関係はビルドグラフとして表現され、各ノードがパッケージ、エッジが依存関係を示します。ビルドツールはこのグラフを辿って、コンパイル順序を決定します。
*   **並行ビルド**: 現代のビルドシステムは、可能な限り並行してパッケージをビルドすることで、ビルド時間を短縮しようとします。しかし、同じパッケージが複数回ビルドされると、リソースの競合や出力ファイルの上書きといった問題が発生する可能性があります。

このコミットは、特にベンダー実験が有効な環境下で、パッケージのロードプロセスにおけるエラー処理と重複検出の不備が、ビルドの不安定性につながるという問題に対処しています。

## 技術的詳細

このコミットは、Goのビルドツール (`cmd/go`) におけるパッケージロードのロジックを改善し、特にベンダー実験が有効な環境下での堅牢性を高めています。技術的な詳細としては、主に以下の2つの側面があります。

### 1. エラー伝播の改善 (`Package.load` メソッド内)

`src/cmd/go/pkg.go` 内の `(*Package).load` メソッドは、パッケージとその依存関係を再帰的にロードする役割を担っています。元のコードでは、依存パッケージをロードする際に、既に `deps` マップにエントリが存在する場合、そのエントリを上書きしないというロジックがありました。これは、直接インポートされたエントリが持つ「より厳密な制約」や「保存すべきエラー」を尊重するためとコメントされていました。

しかし、このロジックには問題がありました。同じインポートパスを持つパッケージが、あるコンテキストではエラーなしでロードされ、別のコンテキストではエラーを伴ってロードされる可能性がある場合、エラーを伴わないエントリが優先されてしまうことがありました。これにより、本来検出されるべきエラーが「ドロップ」され、ビルドプロセスが不健全な状態のまま進行してしまう可能性がありました。

修正後のコードでは、以下の条件で `deps` マップのエントリを更新するように変更されました。

```go
// The same import path could produce an error or not,
// depending on what tries to import it.
// Prefer to record entries with errors, so we can report them.
if deps[dep.ImportPath] == nil || dep.Error != nil {
    deps[dep.ImportPath] = dep
}
```

この変更の意図は明確です。「同じインポートパスが、インポートしようとするものによってエラーを生成することもあれば、しないこともある。エラーを報告できるように、エラーを持つエントリを記録することを優先する。」つまり、もしあるパッケージがエラーを伴ってロードされた場合、そのエラー情報を `deps` マップに確実に記録し、後で報告できるようにすることで、エラーの「パーコレーション（浸透）」を改善しています。これにより、ビルドシステムはより早く、より正確に問題を特定できるようになります。

### 2. 重複パッケージロードの明示的なチェック (`packagesForBuild` 関数内)

`packagesForBuild` 関数は、ビルド対象となるすべてのパッケージを準備する役割を担っています。このコミットでは、この関数に新しいチェックが追加されました。

```go
// Check for duplicate loads of the same package.
// That should be impossible, but if it does happen then
// we end up trying to build the same package twice,
// usually in parallel overwriting the same files,
// which doesn't work very well.
seen := map[string]bool{}
reported := map[string]bool{}
for _, pkg := range packageList(pkgs) {
    if seen[pkg.ImportPath] && !reported[pkg.ImportPath] {
        reported[pkg.ImportPath] = true
        errorf("internal error: duplicate loads of %s", pkg.ImportPath)
    }
    seen[pkg.ImportPath] = true
}
exitIfErrors()
```

このコードブロックは、ビルドを開始する直前に、`pkgs` リスト内のすべてのパッケージをイテレートし、`ImportPath` をキーとして `seen` マップで重複をチェックします。

*   `seen` マップは、既に処理したパッケージのインポートパスを記録します。
*   `reported` マップは、既に重複エラーを報告したパッケージのインポートパスを記録します。これにより、同じパッケージの重複エラーが複数回報告されるのを防ぎます。

もし `seen[pkg.ImportPath]` が `true` であり、かつ `reported[pkg.ImportPath]` が `false` であれば、それは同じパッケージが重複してロードされていることを意味します。この場合、`errorf("internal error: duplicate loads of %s", pkg.ImportPath)` を呼び出して内部エラーを報告し、ビルドを停止します。

このチェックは、コミットメッセージにあるように「それは不可能であるはずだが、もし発生すれば、同じパッケージを2回ビルドしようとすることになり、通常は同じファイルを並行して上書きすることになるため、うまく機能しない」という問題に対処するためのものです。これは防御的なプログラミングの一例であり、予期せぬ状態が発生した場合に早期に問題を検出し、より深刻なビルド失敗を防ぐためのセーフティネットとして機能します。

### 新しいテストケース

`src/cmd/go/vendor_test.go` に `TestVendorCache` という新しいテストが追加されました。このテストは、ベンダー実験が有効な状態で、意図的に重複ロードを引き起こすようなインポート構造を持つプロジェクトをビルドしようとします。

具体的には、`testdata/testvendor` ディレクトリ内に以下のような構造を作成します。

*   `p/p.go` が `q/y` と `q/z` をインポート。
*   `q/y/y.go` が `x` をインポート。
*   `q/z/z.go` が `q/vendor/x` をインポート。
*   `q/vendor/x/x.go` が存在する。

この設定では、`q/y` は `$GOPATH` または `$GOROOT` から `x` を見つけようとし、`q/z` は `q/vendor/x` を見つけようとします。もし `x` が `$GOPATH` にも存在する場合、`x` と `q/vendor/x` は同じ物理的なパッケージを指す可能性がありますが、インポートパスが異なるため、重複ロードの問題を引き起こす可能性があります。

テストは `tg.runFail("build", "p")` を実行し、ビルドが失敗することを期待します。そして、`tg.grepStderr("must be imported as x", "did not fail to build p")` を使って、標準エラー出力に「`must be imported as x`」というメッセージが含まれていることを確認します。これは、重複ロードが検出され、適切なエラーメッセージが報告されることを検証しています。

このテストは、特に修正1（エラー伝播の改善）が正しく機能していることを確認するために設計されています。

## コアとなるコードの解説

### `src/cmd/go/pkg.go` の変更点

1.  **`(*Package).load` メソッド内のエラー伝播ロジックの変更**:
    *   変更前は、`deps[dep.ImportPath] == nil` の場合にのみ依存パッケージを `deps` マップに追加または更新していました。これは、既に存在するエントリ（特に直接インポートされたもの）を上書きしないことで、その「より厳密な制約」や「保存すべきエラー」を保護しようとする意図がありました。
    *   変更後は、条件が `deps[dep.ImportPath] == nil || dep.Error != nil` となりました。これは、もし `deps` マップにまだエントリがない場合、または既存のエントリがエラーを持っていないが、現在処理している `dep` がエラーを持っている場合、`dep` の情報を優先して `deps` マップに記録するという意味です。この修正により、パッケージロード中に発生したエラーが確実に伝播され、ビルドシステムがそのエラーを認識して適切に処理できるようになります。これにより、エラーが「ドロップ」される問題が解決されます。

2.  **`packagesForBuild` 関数内の重複パッケージチェックの追加**:
    *   この関数は、ビルド対象となるパッケージの最終リストを準備する段階で呼び出されます。
    *   追加されたコードブロックは、`seen` と `reported` という2つのマップを使用して、`pkgs` リスト内の各パッケージの `ImportPath` をチェックします。
    *   もし、あるパッケージの `ImportPath` が `seen` マップに既に存在し、かつ `reported` マップにはまだ存在しない場合（つまり、そのパッケージが重複してロードされており、まだその重複が報告されていない場合）、`errorf` を呼び出して「`internal error: duplicate loads of %s`」というエラーメッセージを出力し、ビルドを停止します。
    *   このチェックは、エラー伝播の改善によっても捕捉しきれない、あるいは予期せぬ状況で発生する可能性のあるパッケージの重複ロードを明示的に検出し、ビルドの整合性を保証するためのセーフティネットとして機能します。重複ロードは、同じパッケージが異なるパスで参照され、結果として同じ物理ファイルを複数のビルドジョブが同時に書き込もうとするという深刻な問題を引き起こすため、これを早期に検出してビルドを中断することは非常に重要です。

### `src/cmd/go/testdata/testvendor` ディレクトリ内の新規テストファイル

これらのファイルは、`TestVendorCache` テストケースのために特別に作成されたテストデータです。

*   `p/p.go` は、`q/y` と `q/z` という2つのパッケージをインポートします。
*   `q/y/y.go` は、`x` というパッケージをインポートします。
*   `q/z/z.go` は、`q/vendor/x` というパッケージをインポートします。
*   `q/vendor/x/x.go` は、`q/vendor` ディレクトリ内に存在する `x` パッケージの実体です。

この構造により、`q/y` がインポートする `x` と、`q/z` がインポートする `q/vendor/x` が、Goのパッケージ解決ルール（特にベンダー実験が有効な場合）によって、同じ物理的なパッケージを指す可能性があり、これが重複ロードの問題を引き起こすシナリオを再現します。

### `src/cmd/go/vendor_test.go` の変更点

*   **`TestVendorCache` テスト関数の追加**:
    *   このテストは、`GO15VENDOREXPERIMENT=1` を設定してベンダー実験を有効にし、`GOPATH` を `testdata/testvendor` に設定します。
    *   `tg.runFail("build", "p")` を実行することで、`p` パッケージのビルドが失敗することを期待します。これは、上記の重複ロードの問題が検出され、ビルドが中断されることを意味します。
    *   `tg.grepStderr("must be imported as x", "did not fail to build p")` は、ビルド失敗時に標準エラー出力に特定のメッセージ（例: "must be imported as x"）が含まれていることを検証します。このメッセージは、重複ロードが検出された際にGoツールが生成するエラーメッセージの一部であり、修正が正しく機能していることを確認します。

これらのコード変更とテストの追加により、Goのベンダー実験におけるパッケージロードの堅牢性が大幅に向上し、特に複雑な依存関係を持つプロジェクトでのビルドの安定性が確保されました。

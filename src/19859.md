# [インデックス 19859] ファイルの概要

このコミットは、Goランタイムのスライス割り当て関数（`makeslice`および`growslice`）における32ビットアーキテクチャ固有のバグを修正するものです。具体的には、メモリの最大アドレスを示す`maxMem`定数とスライスの長さ・容量を比較する際に、`int`型へのキャストが32ビットシステム上で負の値となることで、誤った範囲チェックが発生し、パニックを引き起こす可能性がありました。この修正は、比較を符号なし整数型（`uintptr`）で行うように変更することで、この問題を解決し、すべてのアーキテクチャでスライス割り当てが正しく機能するようにします。

## 元コミット内容

`runtime: fix 32 bit build. int(maxMem) is negative on 32 bits. Need to use unsigned arithmetic.`

## 変更の背景

Go言語のランタイムにおけるスライス（slice）のメモリ割り当て処理（`makeslice`および`growslice`関数）に、32ビットアーキテクチャ環境で問題が発生していました。この問題は、メモリの最大アドレスを示す`maxMem`という定数に関連しています。

`maxMem`は`uintptr`型であり、これはポインタを保持できる符号なし整数型です。64ビットシステムでは、`maxMem`の値は非常に大きく、`int`型にキャストしても正の値として扱われます。しかし、32ビットシステムでは、`maxMem`が表現できる最大値（約4GB）が`int`型の最大値（約2GB）を超えるため、`int(maxMem)`とキャストすると、符号ビットが反転し、負の値として解釈されてしまうという問題がありました。

スライスの容量チェックでは、`maxMem`と要素サイズの除算結果を`int`にキャストして使用していました。この`int(maxMem)`が負の値になることで、本来は有効なメモリサイズであるにもかかわらず、不正なサイズとして判断され、「makeslice: len out of range」や「makeslice: cap out of range」といったパニック（panic）を引き起こす可能性がありました。

このコミットは、この32ビット環境特有のバグを修正し、スライス割り当ての堅牢性を向上させることを目的としています。

## 前提知識の解説

1.  **32ビットと64ビットアーキテクチャ**:
    *   **32ビットシステム**: メモリのアドレス空間が32ビットで表現されます。これにより、最大で2^32バイト（約4GB）のメモリを直接アドレス指定できます。`int`型は通常32ビットで、符号付きの場合、約-20億から+20億までの値を表現します。
    *   **64ビットシステム**: メモリのアドレス空間が64ビットで表現されます。これにより、最大で2^64バイト（非常に大きな値）のメモリを直接アドレス指定できます。`int`型は通常64ビットで、符号付きの場合、非常に大きな値を表現できます。

2.  **符号付き整数と符号なし整数**:
    *   **符号付き整数 (signed integer)**: 正と負の両方の値を表現できる整数型です。最上位ビットが符号ビットとして使用されます（0が正、1が負）。
    *   **符号なし整数 (unsigned integer)**: 負の値を表現せず、0以上の値のみを表現できる整数型です。すべてのビットが数値の大きさを表すために使用されます。

3.  **整数オーバーフロー**:
    整数型で表現できる最大値を超えた値を代入しようとすると、オーバーフローが発生します。符号付き整数では、オーバーフローによって値が予期せず負になったり、最小値になったりすることがあります。

4.  **Go言語の`uintptr`型**:
    `uintptr`は、ポインタを保持するのに十分な大きさの符号なし整数型です。そのサイズはシステムアーキテクチャ（32ビットまたは64ビット）に依存します。メモリのアドレスを数値として扱う際に使用されます。

5.  **Go言語の`maxMem`**:
    Goランタイム内部で使用される定数で、システムが利用できる最大メモリ量（アドレス空間の最大値）を示します。これは`uintptr`型で定義されています。

6.  **Go言語のスライス（Slice）**:
    スライスはGo言語の組み込み型で、配列のセグメントを参照するデータ構造です。内部的には、ポインタ（基底配列への参照）、長さ（len）、容量（cap）の3つの要素で構成されます。
    *   `len` (長さ): スライスに含まれる要素の数。
    *   `cap` (容量): スライスの基底配列が保持できる要素の最大数。

7.  **`makeslice`関数と`growslice`関数**:
    *   `makeslice`: `make([]T, len, cap)`のようにスライスを初期化する際に内部的に呼び出されるランタイム関数です。指定された長さと容量に基づいて新しいスライスを割り当てます。
    *   `growslice`: スライスの容量が不足した場合（`append`などで要素を追加しようとした場合）に、より大きな容量を持つ新しい基底配列を割り当て、既存の要素をコピーするために内部的に呼び出されるランタイム関数です。

## 技術的詳細

問題の核心は、`src/pkg/runtime/slice.go`内の`makeslice`および`growslice`関数における、スライスの容量がシステムメモリの最大値を超えていないかをチェックするロジックにありました。
具体的には、`maxMem`（`uintptr`型）を要素のサイズで割った結果を`int`型にキャストして、スライスの`len`や`cap`と比較していました。

元のコードでは、以下のような比較が行われていました。
`len > int(maxMem/uintptr(t.elem.size))`
`cap > int(maxMem/uintptr(t.elem.size))`
`newcap >= int(maxMem/uintptr(et.size))`

32ビットシステムでは、`maxMem`が`uintptr`型として約4GBの値を持ちます。これを`int`型にキャストすると、`int`型の最大値（約2GB）を超えるため、符号ビットが反転し、負の値（例: -2GB）として解釈されてしまいます。
例えば、`maxMem/uintptr(t.elem.size)`が正の大きな値（例: 3GB相当）であったとしても、`int(...)`とキャストされると負の値（例: -1GB相当）になります。
この結果、`len`や`cap`が正の値であるにもかかわらず、負の値と比較されるため、`len > 負の値`や`cap > 負の値`という比較が常に真となり、本来は有効なスライスサイズであるにもかかわらず、「out of range」エラーとしてパニックを引き起こしていました。
この修正は、この比較を`uintptr`型で行うことで、符号付き整数のキャストによる予期せぬ負の値への変換を防ぎ、正しいメモリ範囲チェックを保証します。これにより、32ビット環境でもスライスの割り当てが正しく機能するようになります。

## コアとなるコードの解説

変更は`src/pkg/runtime/slice.go`ファイル内の`makeslice`関数と`growslice`関数に集中しています。これらの関数は、Goのスライスが作成または拡張される際に、要求された長さや容量がシステムメモリの許容範囲内にあるかをチェックします。

1.  **`makeslice`関数内の変更**:
    *   **変更前**:
        ```go
        if len64 < 0 || int64(len) != len64 || t.elem.size > 0 && len > int(maxMem/uintptr(t.elem.size)) {
        	panic(errorString("makeslice: len out of range"))
        }
        // ...
        if cap < len || int64(cap) != cap64 || t.elem.size > 0 && cap > int(maxMem/uintptr(t.elem.size)) {
        	panic(errorString("makeslice: cap out of range"))
        }
        ```
    *   **変更後**:
        ```go
        if len64 < 0 || int64(len) != len64 || t.elem.size > 0 && uintptr(len) > maxMem/uintptr(t.elem.size) {
        	panic(errorString("makeslice: len out of range"))
        }
        // ...
        if cap < len || int64(cap) != cap64 || t.elem.size > 0 && uintptr(cap) > maxMem/uintptr(t.elem.size) {
        	panic(errorString("makeslice: cap out of range"))
        }
        ```
    `len > int(maxMem/uintptr(t.elem.size))`という条件が`uintptr(len) > maxMem/uintptr(t.elem.size)`に変更されました。同様に`cap`のチェックも変更されています。
    これにより、`len`や`cap`（これらは`int`型）を`maxMem`との比較を行う前に`uintptr`型に明示的にキャストすることで、`int(maxMem/...)`による負の値への変換を防ぎ、符号なし整数同士の正しい比較が行われるようになります。

2.  **`growslice`関数内の変更**:
    *   **変更前**:
        ```go
        if int64(cap) != cap64 || cap < old.cap || t.elem.size > 0 && cap > int(maxMem/uintptr(t.elem.size)) {
        	panic(errorString("growslice: cap out of range"))
        }
        // ...
        if newcap >= int(maxMem/uintptr(et.size)) {
        	panic(errorString("growslice: cap out of range"))
        }
        ```
    *   **変更後**:
        ```go
        if int64(cap) != cap64 || cap < old.cap || t.elem.size > 0 && uintptr(cap) > maxMem/uintptr(t.elem.size) {
        	panic(errorString("growslice: cap out of range"))
        }
        // ...
        if uintptr(newcap) >= maxMem/uintptr(et.size) {
        	panic(errorString("growslice: cap out of range"))
        }
        ```
    ここでも同様に、`cap > int(maxMem/...)`が`uintptr(cap) > maxMem/...`に、`newcap >= int(maxMem/...)`が`uintptr(newcap) >= maxMem/...`に変更されています。
    `newcap`も`int`型であるため、`uintptr(newcap)`とすることで、`maxMem`との比較が符号なし整数として正しく行われるようになります。

これらの変更により、32ビットシステムで`maxMem`が`int`型にキャストされた際に発生していた負の値への変換が回避され、スライスの長さと容量のチェックがすべてのアーキテクチャで一貫して正しく機能するようになりました。

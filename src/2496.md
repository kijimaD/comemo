## 変更の背景

Go言語の初期段階において、コンパイラの挙動やエラーメッセージのテスト方法は進化していました。このコミットが行われた時期は、Go言語がまだ活発に開発されていた頃であり、テストスイートの整備も進められていました。

`test/fixedbugs` ディレクトリ内のテストは、特定のバグやコンパイラの意図されたエラー挙動を検証するために存在します。以前は、コンパイラのエラー出力が `golden.out` と呼ばれるファイルに記録され、テスト実行時に実際の出力と比較される形式が一般的でした。しかし、この方式では、テスト対象のコードと期待されるエラーメッセージが物理的に離れてしまうため、テストの意図を理解しにくく、またエラーメッセージの変更があった場合に `golden.out` も更新する必要があるというメンテナンス上の課題がありました。

このコミットは、`make` 関数に不正な引数を渡した場合のコンパイラエラーをテストする `bug122.go` において、より現代的なテスト手法である「インラインエラーディレクティブ」を導入することで、これらの課題を解決しようとしています。これにより、テストコードの可読性とメンテナンス性が向上します。

## 前提知識の解説

### Go言語の `make` 関数

`make` はGo言語の組み込み関数で、スライス、マップ、チャネルといった組み込み型を初期化するために使用されます。
スライスの場合、`make` 関数は以下の形式で呼び出されます。

*   **`make([]Type, length)`**: 指定された型の要素を持つスライスを作成します。`length` はスライスの初期長であり、容量 (capacity) も `length` と同じになります。
*   **`make([]Type, length, capacity)`**: 指定された型の要素を持つスライスを作成します。`length` はスライスの初期長、`capacity` はスライスの基底配列の最大容量です。`capacity` は `length` 以上である必要があります。

`make` 関数は、スライスに対しては最大で2つのサイズ関連の引数（`length` と `capacity`）しか受け付けません。これを超える引数を渡すと、コンパイルエラーとなります。

### Go言語のテストにおける `golden.out` とインラインエラーディレクティブ

Go言語のコンパイラやツールのテストスイートでは、様々な方法で期待される挙動を検証します。

*   **`golden.out`**: 過去には、コンパイラのエラーメッセージやツールの出力結果を `golden.out` というファイルに記録し、テスト実行時に生成される出力とこの「ゴールデンファイル」の内容を比較することで、期待される挙動からの逸脱がないかを確認していました。これは、出力が複雑で、かつ安定している場合に有効な手法です。
*   **インラインエラーディレクティブ (`// ERROR "..."`)**: Go言語のコンパイラテストでは、ソースコードの特定の行に `// ERROR "expected error message"` のようなコメントを記述することで、その行がコンパイルエラーを発生させ、かつそのエラーメッセージが指定された文字列を含むことを期待するテストが可能です。この方法は、特定の行で発生するべきエラーを直接コードの隣に記述できるため、テストの意図が非常に明確になり、`golden.out` のような外部ファイルに依存するよりもメンテナンスが容易になります。

このコミットは、`golden.out` に依存する古いテストスタイルから、インラインエラーディレクティブを使用する新しい（より良い）テストスタイルへの移行の一環と見なすことができます。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラのテストハーネスが `// ERROR "..."` コメントをどのように解釈し、テスト結果を検証するかという点にあります。

`test/fixedbugs/bug122.go` の変更前は、`make([]int, 10, 20, 30, 40)` という不正な `make` の呼び出しがコンパイルエラーを引き起こすことを期待していました。このエラーメッセージは `golden.out` に `fixedbugs/bug122.go:6: too many arguments to make array` として記録されていました。

変更後、`bug122.go` の該当行に `// ERROR "too many"` というコメントが追加されました。これは、Goのテストツール（例えば `go tool compile` のテストモード）に対して、この行でコンパイルエラーが発生し、そのエラーメッセージが `"too many"` という文字列を含むことを期待するという指示を与えます。

このインラインディレクティブの導入により、`golden.out` に記述されていた `bug122.go` のエラーに関するエントリは不要となり、削除されました。これにより、テストのロジックがテスト対象のコードのすぐ隣に配置され、テストの意図がより明確になります。また、コンパイラのエラーメッセージの文言が多少変更されても、`"too many"` という核となる部分が変わらなければテストが失敗しないという柔軟性も生まれます。

この「正規化」は、Go言語のテストスイート全体で一貫性のある、より堅牢でメンテナンスしやすいテストプラクティスを確立するための重要なステップでした。

## コアとなるコードの解説

### `test/fixedbugs/bug122.go` の変更

*   元のコードでは、`a := make([]int, 10, 20, 30, 40);` という行があり、その後に `// should allow at most 2 sizes` というコメントが付いていました。これは、この `make` の呼び出しが不正であり、コンパイルエラーになることを示唆していました。
*   変更後、この行は `a := make([]int, 10, 20, 30, 40); // ERROR "too many"` となりました。
    *   `// ERROR "too many"` というコメントは、Goのテストハーネスに対する特別な指示です。これは、この行でコンパイルエラーが発生し、そのエラーメッセージに `"too many"` という文字列が含まれることを期待するという意味です。
    *   これにより、テストの意図がコードのすぐ隣に明示され、`golden.out` のような外部ファイルを参照することなく、このテストが何を検証しているのかが明確になります。

### `test/golden.out` の変更

*   `test/golden.out` から、`bug122.go` に関連する以下の3行が削除されました。
    ```
    =========== fixedbugs/bug122.go
    fixedbugs/bug122.go:6: too many arguments to make array
    ```
*   この削除は、`bug122.go` 内にインラインエラーディレクティブが導入されたため、`golden.out` でこのエラーを明示的に期待する必要がなくなったことを意味します。テストハーネスは `bug122.go` の `// ERROR "too many"` コメントを読み取り、コンパイラが期待通りのエラーを生成するかどうかを直接検証するようになります。これにより、`golden.out` ファイルの肥大化を防ぎ、テストスイート全体のメンテナンスを簡素化できます。

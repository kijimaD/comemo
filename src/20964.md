# [インデックス 20964] ファイルの概要

このコミットは、Goランタイムにおけるライトバリアの実装を改善し、特に複数のワードにまたがるライトバリアを `writebarrierptr` 関数を介して一元化することを目的としています。これにより、ライトバリアの正確性を向上させ、将来的な最適化の基盤を築きます。また、`builtin copy` 関数に対するライトバリアの追加や、Go 1.4で一時的に無効化されていた一部のライトバリアの再有効化も含まれています。

## 変更の背景

このコミットの主な背景は、Go言語のガベージコレクション（GC）におけるライトバリアの正確性と堅牢性を向上させることです。

1.  **ライトバリアの一元化とバグの検出**: 以前は、複数のワードにまたがるデータ構造（例えば、構造体や配列）に対するライトバリアがそれぞれ独立して実装されていました。このコミットでは、これらのライトバリアが最終的に `writebarrierptr` という単一の関数を呼び出すように変更されます。これにより、実際のバリアロジックは `writebarrierptr` のみに集約され、管理が容易になります。また、`writebarrierptr` 内で、コピーされる値が小さな非ゼロ整数でないことをチェックする仕組みが導入されました。これは、ポインタではない値に対して誤ってライトバリアが呼び出されるバグを検出するために役立ちます。このチェックにより、`sync/atomic` パッケージの一部のテストで、意図せずライトバリアがトリガーされるケースが発見され、修正されました。

2.  **`builtin copy` 関数へのライトバリアの追加**: Go 1.4のライトバリア導入時に、`copy` 組み込み関数によってメモリが移動される際のライトバリアの挿入が漏れていたため、このコミットで追加されました。これはGCの正確性を保つ上で重要な修正です。

3.  **Go 1.4で無効化されていたライトバリアの再有効化**: Go 1.4では、生成されるコードの変更によって不要になる可能性があった一部のライトバリアが一時的に無効化されていました。しかし、そのコード変更がまだ実装されていないため、安全のためにこれらのライトバリアが再有効化されました。これは、GCの正確性を確保するための暫定的な措置であり、将来的なコード生成の最適化によって再び不要になる可能性があります。

全体として、この変更は効率性よりも「正確性」を優先しており、GoランタイムのGCメカニズムの信頼性を高めることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語ランタイムおよびガベージコレクションに関する基本的な概念を理解しておく必要があります。

1.  **ガベージコレクション (GC)**:
    Go言語は自動メモリ管理を採用しており、不要になったメモリ領域を自動的に解放するガベージコレクタを備えています。GoのGCは、並行マーク＆スイープ方式をベースとしており、プログラムの実行と並行してGC処理を進めることで、アプリケーションの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えるように設計されています。

2.  **ライトバリア (Write Barrier)**:
    並行GCにおいて非常に重要な技術です。GCがメモリをスキャンしている最中に、アプリケーションがポインタを書き換える（例えば、あるオブジェクトが別のオブジェクトを参照するように変更する）と、GCがその変更を認識できず、本来到達可能なオブジェクトを誤って回収してしまう（「ポインタの欠落」または「浮遊ポインタ」問題）可能性があります。
    ライトバリアは、このような問題を回避するために、ポインタの書き込み操作が行われる際に特定のコード（バリア）を挿入する仕組みです。このバリアは、GCがオブジェクトグラフを正確に追跡できるように、変更されたポインタに関する情報をGCに通知したり、GCがスキャン中のオブジェクトを保護したりする役割を担います。
    Goのライトバリアは、主に「Dijkstraの三色マーク」アルゴリズムと組み合わせて使用されます。オブジェクトは白（未訪問）、灰（訪問済みだが子を未スキャン）、黒（訪問済みで子もスキャン済み）のいずれかの色でマークされます。ライトバリアは、黒から白へのポインタの書き込みを防ぐ（または検出する）ことで、GCの正確性を保証します。

3.  **ポインタ (Pointer)**:
    Go言語におけるポインタは、メモリ上の特定のアドレスを指し示す変数です。GCは、これらのポインタを辿ることで、どのオブジェクトがまだ使用されているかを判断します。ライトバリアは、このポインタの書き換え操作に介入します。

4.  **`uintptr`**:
    Go言語における `uintptr` は、ポインタを保持するのに十分な大きさの符号なし整数型です。これは、ポインタ演算を行う際に使用されることがありますが、`unsafe.Pointer` と異なり、GCによって追跡されるポインタではありません。このコミットでは、`writebarrierptr` が `uintptr` を引数に取りますが、これは内部でポインタとして扱われる値のチェックを行うためです。

5.  **`cmd/gc` (Goコンパイラ)**:
    Goのコンパイラは、Goのソースコードを機械語に変換するだけでなく、GCに必要な情報（例えば、オブジェクト内のどのフィールドがポインタであるかを示すビットマップ）を生成したり、ライトバリアの呼び出しを適切な場所に挿入したりする役割も担っています。

6.  **`runtime` (Goランタイム)**:
    Goプログラムの実行を管理する低レベルのコード群です。GC、スケジューラ、メモリ割り当て、ライトバリアの実装など、Goプログラムが動作するために必要な多くの機能を提供します。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムにおけるライトバリアのアーキテクチャ変更と、それに関連するコンパイラ側の調整にあります。

1.  **`writebarrierptr` の役割の強化**:
    以前は、様々なライトバリア関数がそれぞれ独立したロジックを持っていた可能性があります。このコミットでは、`src/runtime/mgc0.go` に定義されている `writebarrierptr(dst *uintptr, src uintptr)` 関数が、単一のポインタ書き込みに対する「実際の」ライトバリアとして機能するように設計されています。
    注目すべきは、`writebarrierptr` の内部で `src != 0 && (src < _PageSize || src == _PoisonGC || src == _PoisonStack)` というチェックが追加された点です。これは、`src` が有効なポインタであるべき場合に、小さな非ゼロ整数やGC/スタックのポイズン値（デバッグ目的で使われる特殊な値）が渡されていないかを検証するものです。これにより、ポインタではない値に対して誤ってライトバリアが呼び出されるようなバグを早期に発見できるようになります。コミットメッセージにあるように、このチェックによって `sync/atomic` パッケージの一部のテストにおける「賢すぎる」挙動が露呈し、修正されました。

2.  **`writebarrierfat` 関数の生成と利用**:
    Goのオブジェクトは、複数のポインタを含むことがあります（例：構造体、配列）。これらの「マルチワード」オブジェクトに対するライトバリアは、それぞれのポインタフィールドに対して個別に `writebarrierptr` を呼び出す必要があります。
    このコミットでは、`src/runtime/wbfat_gen.go` というGoプログラムが導入されました。このジェネレータは、`go generate` コマンドによって実行され、`src/runtime/wbfat.go` ファイルを生成します。`wbfat.go` には、2ワード、3ワード、4ワードのオブジェクトに対して、どのワードがポインタであるかに応じた様々な `writebarrierfatXXXX` 関数が定義されています（例: `writebarrierfat01`、`writebarrierfat110` など）。これらの関数は、ポインタであるワードに対しては `writebarrierptr` を呼び出し、ポインタではないワードに対しては通常の代入を行います。
    これにより、コンパイラ（`cmd/gc/walk.c`）は、オブジェクトの型情報（特にポインタビットマップ）に基づいて、適切な `writebarrierfatXXXX` 関数を選択して呼び出すことができるようになります。これは、ライトバリアのコード生成をより汎用的かつ正確にするための重要なステップです。

3.  **`builtin copy` 関数へのライトバリアの追加**:
    `src/cmd/gc/walk.c` の `copyany` 関数（`copy` 組み込み関数のコンパイラ実装の一部）に、`writebarriercopy` という新しいライトバリア関数が導入されました。この関数は、`copy` 操作によってポインタを含むメモリが移動される際に呼び出されます。`writebarriercopy` は、コピー元とコピー先のメモリ領域が重なっている場合（特にコピー元がコピー先より前にある場合）に、逆方向へのコピーを行うことで、GCの正確性を保証します。各ワードのコピーには、前述の `writebarrierfat` 関数が使用されます。

4.  **Go 1.4で無効化されていたライトバリアの再有効化**:
    `src/cmd/gc/typecheck.c` では、`OSLICE3` (スライス再スライス) および `OAPPEND` (append操作) の最適化に関連するライトバリアが、`TODO(rsc): Reenable once...` というコメントと共に `if(0 && ...)` の形で一時的に無効化されていました。このコミットでは、これらの `if(0 && ...)` が削除され、ライトバリアが再有効化されています。これは、コンパイラがこれらの操作に対してライトバリアを不要にするようなコード生成の最適化がまだ行われていないため、安全のためにバリアを有効に戻すという判断です。

5.  **`MaxGCMask` の一時的な変更**:
    `src/runtime/mgc0.h` で `MaxGCMask` の値が `64` から `65536` に一時的に変更されています。これは、`src/runtime/malloc.go` の `mallocgc` および `loadPtrMask` 関数内で、ライトバリアがまだ大きなGCマスクを扱えないことに対する暫定的な措置です。コミットメッセージには `// TODO(rsc): change back to 64` とあり、これは将来的に元の値に戻される予定であることを示唆しています。

これらの変更は、GoのGCがより正確に動作し、特に並行GC環境下でのポインタの追跡が堅牢になることを目指しています。効率性よりも正確性を優先するという方針が明確に示されています。

### `src/runtime/mgc0.go` における `writebarrierptr` の強化と他のバリアの変更

```go
//go:nosplit
func writebarrierptr(dst *uintptr, src uintptr) {
	if src != 0 && (src < _PageSize || src == _PoisonGC || src == _PoisonStack) {
		onM(func() { gothrow("bad pointer in write barrier") })
	}
	*dst = src
}

//go:nosplit
func writebarrierstring(dst *[2]uintptr, src [2]uintptr) {
	writebarrierptr(&dst[0], src[0]) // 変更点: writebarrierptr を呼び出す
	dst[1] = src[1]
}

//go:nosplit
func writebarrierslice(dst *[3]uintptr, src [3]uintptr) {
	writebarrierptr(&dst[0], src[0]) // 変更点: writebarrierptr を呼び出す
	dst[1] = src[1]
	dst[2] = src[2]
}

//go:nosplit
func writebarrieriface(dst *[2]uintptr, src [2]uintptr) {
	writebarrierptr(&dst[0], src[0]) // 変更点: writebarrierptr を呼び出す
	writebarrierptr(&dst[1], src[1]) // 変更点: writebarrierptr を呼び出す
}
```
`writebarrierptr` は、単一のポインタ書き込みに対するライトバリアの核となります。追加された `if` 文は、`src` が有効なポインタであるべき場所で、誤って非ポインタ値が渡されていないかをチェックするデバッグ/堅牢性向上のためのものです。
`writebarrierstring`、`writebarrierslice`、`writebarrieriface` は、それぞれ文字列、スライス、インターフェースの内部構造におけるポインタの書き込みを処理するバリアです。これらの関数は、以前は直接 `dst[i] = src[i]` のように代入を行っていましたが、このコミットにより、ポインタであるフィールドの代入には `writebarrierptr` を呼び出すように変更されました。これにより、実際のバリアロジックが `writebarrierptr` に集約され、管理が容易になります。

### `src/runtime/mgc0.go` における `writebarriercopy` の実装

```go
//go:nosplit
func writebarriercopy(typ *_type, dst, src slice) int {
	n := dst.len
	if n > src.len {
		n = src.len
	}
	if n == 0 {
		return 0
	}
	dstp := unsafe.Pointer(dst.array)
	srcp := unsafe.Pointer(src.array)

	if uintptr(srcp) < uintptr(dstp) && uintptr(srcp)+uintptr(n)*typ.size > uintptr(dstp) {
		// Overlap with src before dst.
		// Copy backward, being careful not to move dstp/srcp
		// out of the array they point into.
		dstp = add(dstp, uintptr(n-1)*typ.size)
		srcp = add(srcp, uintptr(n-1)*typ.size)
		i := uint(0)
		for {
			writebarrierfat(typ, dstp, srcp) // writebarrierfat を使用
			if i++; i >= n {
				break
			}
			dstp = add(dstp, -typ.size)
			srcp = add(srcp, -typ.size)
		}
	} else {
		// Copy forward, being careful not to move dstp/srcp
		// out of the array they point into.
		i := uint(0)
		for {
			writebarrierfat(typ, dstp, srcp) // writebarrierfat を使用
			if i++; i >= n {
				break
			}
			dstp = add(dstp, typ.size)
			srcp = add(srcp, typ.size)
		}
	}
	return int(n)
}
```
`writebarriercopy` は、`copy` 組み込み関数がポインタを含むスライスをコピーする際に呼び出されるランタイム関数です。この関数は、コピー元とコピー先のメモリ領域が重なっているかどうかを検出し、それに応じて順方向または逆方向に要素をコピーします。各要素のコピーには、汎用的な `writebarrierfat(typ *_type, dst, src unsafe.Pointer)` 関数が使用されます。この `writebarrierfat` 関数は、`typ` のポインタビットマップを読み取り、要素内のポインタを適切に処理します。これにより、`copy` 操作中のポインタの移動がGCによって正しく追跡されることが保証されます。

## 変更の背景

このコミットの主な背景は、Go言語のガベージコレクション（GC）におけるライトバリアの正確性と堅牢性を向上させることです。

1.  **ライトバリアの一元化とバグの検出**: 以前は、複数のワードにまたがるデータ構造（例えば、構造体や配列）に対するライトバリアがそれぞれ独立して実装されていました。このコミットでは、これらのライトバリアが最終的に `writebarrierptr` という単一の関数を呼び出すように変更されます。これにより、実際のバリアロジックは `writebarrierptr` のみに集約され、管理が容易になります。また、`writebarrierptr` 内で、コピーされる値が小さな非ゼロ整数でないことをチェックする仕組みが導入されました。これは、ポインタではない値に対して誤ってライトバリアが呼び出されるバグを検出するために役立ちます。このチェックにより、`sync/atomic` パッケージの一部のテストで、意図せずライトバリアがトリガーされるケースが発見され、修正されました。

2.  **`builtin copy` 関数へのライトバリアの追加**: Go 1.4のライトバリア導入時に、`copy` 組み込み関数によってメモリが移動される際のライトバリアの挿入が漏れていたため、このコミットで追加されました。これはGCの正確性を保つ上で重要な修正です。

3.  **Go 1.4で無効化されていたライトバリアの再有効化**: Go 1.4では、生成されるコードの変更によって不要になる可能性があった一部のライトバリアが一時的に無効化されていました。しかし、そのコード変更がまだ実装されていないため、安全のためにこれらのライトバリアが再有効化されました。これは、GCの正確性を確保するための暫定的な措置であり、将来的なコード生成の最適化によって再び不要になる可能性があります。

全体として、この変更は効率性よりも「正確性」を優先しており、GoランタイムのGCメカニズムの信頼性を高めることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語ランタイムおよびガベージコレクションに関する基本的な概念を理解しておく必要があります。

1.  **ガベージコレクション (GC)**:
    Go言語は自動メモリ管理を採用しており、不要になったメモリ領域を自動的に解放するガベージコレクタを備えています。GoのGCは、並行マーク＆スイープ方式をベースとしており、プログラムの実行と並行してGC処理を進めることで、アプリケーションの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えるように設計されています。

2.  **ライトバリア (Write Barrier)**:
    並行GCにおいて非常に重要な技術です。GCがメモリをスキャンしている最中に、アプリケーションがポインタを書き換える（例えば、あるオブジェクトが別のオブジェクトを参照するように変更する）と、GCがその変更を認識できず、本来到達可能なオブジェクトを誤って回収してしまう（「ポインタの欠落」または「浮遊ポインタ」問題）可能性があります。
    ライトバリアは、このような問題を回避するために、ポインタの書き込み操作が行われる際に特定のコード（バリア）を挿入する仕組みです。このバリアは、GCがオブジェクトグラフを正確に追跡できるように、変更されたポインタに関する情報をGCに通知したり、GCがスキャン中のオブジェクトを保護したりする役割を担っています。
    Goのライトバリアは、主に「Dijkstraの三色マーク」アルゴリズムと組み合わせて使用されます。オブジェクトは白（未訪問）、灰（訪問済みだが子を未スキャン）、黒（訪問済みで子もスキャン済み）のいずれかの色でマークされます。ライトバリアは、黒から白へのポインタの書き込みを防ぐ（または検出する）ことで、GCの正確性を保証します。

3.  **ポインタ (Pointer)**:
    Go言語におけるポインタは、メモリ上の特定のアドレスを指し示す変数です。GCは、これらのポインタを辿ることで、どのオブジェクトがまだ使用されているかを判断します。ライトバリアは、このポインタの書き換え操作に介入します。

4.  **`uintptr`**:
    Go言語における `uintptr` は、ポインタを保持するのに十分な大きさの符号なし整数型です。これは、ポインタ演算を行う際に使用されることがありますが、`unsafe.Pointer` と異なり、GCによって追跡されるポインタではありません。このコミットでは、`writebarrierptr` が `uintptr` を引数に取りますが、これは内部でポインタとして扱われる値のチェックを行うためです。

5.  **`cmd/gc` (Goコンパイラ)**:
    Goのコンパイラは、Goのソースコードを機械語に変換するだけでなく、GCに必要な情報（例えば、オブジェクト内のどのフィールドがポインタであるかを示すビットマップ）を生成したり、ライトバリアの呼び出しを適切な場所に挿入したりする役割も担っています。

6.  **`runtime` (Goランタイム)**:
    Goプログラムの実行を管理する低レベルのコード群です。GC、スケジューラ、メモリ割り当て、ライトバリアの実装など、Goプログラムが動作するために必要な多くの機能を提供します。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムにおけるライトバリアのアーキテクチャ変更と、それに関連するコンパイラ側の調整にあります。

1.  **`writebarrierptr` の役割の強化**:
    以前は、様々なライトバリア関数がそれぞれ独立したロジックを持っていた可能性があります。このコミットでは、`src/runtime/mgc0.go` に定義されている `writebarrierptr(dst *uintptr, src uintptr)` 関数が、単一のポインタ書き込みに対する「実際の」ライトバリアとして機能するように設計されています。
    注目すべきは、`writebarrierptr` の内部で `src != 0 && (src < _PageSize || src == _PoisonGC || src == _PoisonStack)` というチェックが追加された点です。これは、`src` が有効なポインタであるべき場合に、小さな非ゼロ整数やGC/スタックのポイズン値（デバッグ目的で使われる特殊な値）が渡されていないかを検証するものです。これにより、ポインタではない値に対して誤ってライトバリアが呼び出されるようなバグを早期に発見できるようになります。コミットメッセージにあるように、このチェックによって `sync/atomic` パッケージの一部のテストにおける「賢すぎる」挙動が露呈し、修正されました。

2.  **`writebarrierfat` 関数の生成と利用**:
    Goのオブジェクトは、複数のポインタを含むことがあります（例：構造体、配列）。これらの「マルチワード」オブジェクトに対するライトバリアは、それぞれのポインタフィールドに対して個別に `writebarrierptr` を呼び出す必要があります。
    このコミットでは、`src/runtime/wbfat_gen.go` というGoプログラムが導入されました。このジェネレータは、`go generate` コマンドによって実行され、`src/runtime/wbfat.go` ファイルを生成します。`wbfat.go` には、2ワード、3ワード、4ワードのオブジェクトに対して、どのワードがポインタであるかに応じた様々な `writebarrierfatXXXX` 関数が定義されています（例: `writebarrierfat01` は1番目のワードが非ポインタ、2番目がポインタ、`writebarrierfat110` は1番目と2番目のワードがポインタ、3番目が非ポインタ）。これらの関数は、ポインタであるワードに対しては `writebarrierptr` を呼び出し、ポインタではないワードに対しては通常の代入を行います。
    これにより、コンパイラ（`cmd/gc/walk.c`）は、オブジェクトの型情報（特にポインタビットマップ）に基づいて、適切な `writebarrierfatXXXX` 関数を選択して呼び出すことができるようになります。これは、ライトバリアのコード生成をより汎用的かつ正確にするための重要なステップです。

3.  **`builtin copy` 関数へのライトバリアの追加**:
    `src/cmd/gc/walk.c` の `copyany` 関数（`copy` 組み込み関数のコンパイラ実装の一部）に、`writebarriercopy` という新しいライトバリア関数が導入されました。この関数は、`copy` 操作によってポインタを含むメモリが移動される際に呼び出されます。`writebarriercopy` は、コピー元とコピー先のメモリ領域が重なっている場合（特にコピー元がコピー先より前にある場合）に、逆方向へのコピーを行うことで、GCの正確性を保証します。各ワードのコピーには、前述の `writebarrierfat` 関数が使用されます。

4.  **Go 1.4で無効化されていたライトバリアの再有効化**:
    `src/cmd/gc/typecheck.c` では、`OSLICE3` (スライス再スライス) および `OAPPEND` (append操作) の最適化に関連するライトバリアが、`TODO(rsc): Reenable once...` というコメントと共に `if(0 && ...)` の形で一時的に無効化されていました。このコミットでは、これらの `if(0 && ...)` が削除され、ライトバリアが再有効化されています。これは、コンパイラがこれらの操作に対してライトバリアを不要にするようなコード生成の最適化がまだ行われていないため、安全のためにバリアを有効に戻すという判断です。

5.  **`MaxGCMask` の一時的な変更**:
    `src/runtime/mgc0.h` で `MaxGCMask` の値が `64` から `65536` に一時的に変更されています。これは、`src/runtime/malloc.go` の `mallocgc` および `loadPtrMask` 関数内で、ライトバリアがまだ大きなGCマスクを扱えないことに対する暫定的な措置です。コミットメッセージには `// TODO(rsc): change back to 64` とあり、これは将来的に元の値に戻される予定であることを示唆しています。

これらの変更は、GoのGCがより正確に動作し、特に並行GC環境下でのポインタの追跡が堅牢になることを目指しています。効率性よりも正確性を優先するという方針が明確に示されています。

`applywritebarrier` は、コンパイラがポインタの書き込みを検出した際にライトバリアを挿入する部分です。この変更により、2ワードから4ワードまでのオブジェクトに対して、そのオブジェクト内のどのワードがポインタであるかを示すビットマップ（`bv`）に基づいて、適切な `writebarrierfatXXXX` 関数（例: `writebarrierfat10` は1番目のワードがポインタ、2番目が非ポインタ）の名前を動的に生成し、その関数を呼び出すように変更されました。これにより、コンパイラはオブジェクトのレイアウトに応じて最適なライトバリア関数を選択できるようになります。

### `src/runtime/wbfat_gen.go` と `src/runtime/wbfat.go`

### `src/runtime/mgc0.go` における `writebarriercopy` の実装

```go
//go:nosplit
func writebarriercopy(typ *_type, dst, src slice) int {
	n := dst.len
	if n > src.len {
		n = src.len
	}
	if n == 0 {
		return 0
	}
	dstp := unsafe.Pointer(dst.array)
	srcp := unsafe.Pointer(src.array)

	if uintptr(srcp) < uintptr(dstp) && uintptr(srcp)+uintptr(n)*typ.size > uintptr(dstp) {
		// Overlap with src before dst.
		// Copy backward, being careful not to move dstp/srcp
		// out of the array they point into.
		dstp = add(dstp, uintptr(n-1)*typ.size)
		srcp = add(srcp, uintptr(n-1)*typ.size)
		i := uint(0)
		for {
			writebarrierfat(typ, dstp, srcp) // writebarrierfat を使用
			if i++; i >= n {
				break
			}
			dstp = add(dstp, -typ.size)
			srcp = add(srcp, -typ.size)
		}
	} else {
		// Copy forward, being careful not to move dstp/srcp
		// out of the array they point into.
		i := uint(0)
		for {
			writebarrierfat(typ, dstp, srcp) // writebarrierfat を使用
			if i++; i >= n {
				break
			}
			dstp = add(dstp, typ.size)
			srcp = add(srcp, typ.size)
		}
	}
	return int(n)
}
```
`writebarriercopy` は、`copy` 組み込み関数がポインタを含むスライスをコピーする際に呼び出されるランタイム関数です。この関数は、コピー元とコピー先のメモリ領域が重なっているかどうかを検出し、それに応じて順方向または逆方向に要素をコピーします。各要素のコピーには、汎用的な `writebarrierfat(typ *_type, dst, src unsafe.Pointer)` 関数が使用されます。この `writebarrierfat` 関数は、`typ` のポインタビットマップを読み取り、要素内のポインタを適切に処理します。これにより、`copy` 操作中のポインタの移動がGCによって正しく追跡されることが保証されます。

# [インデックス 21627] ファイルの概要

このコミットは、Go言語のツールチェイン内部、特にアセンブラ関連のコードベースにおける大規模なリファクタリングとシンボル名の正規化を目的としています。新しいアセンブラへの移行の一環として、`cmd/internal/obj` パッケージ内のシンボルがより多くエクスポートされ、`Type_` のような末尾にアンダースコアを持つ識別子が `Type` のようにアンダースコアなしの名前に変更されました。これは、Goの命名規則に合わせ、内部APIの整合性を高めるための変更です。

## 変更の背景

このコミットの主要な背景には、Go言語のツールチェイン、特にアセンブラとリンカのコードベースをC言語からGo言語へ移行するという、当時のGo開発チームの大きな取り組みがあります。コミットメッセージにある `rsc.io/c2go` は、このCからGoへのコード変換を支援するためにRuss Cox氏によって開発された特定のツールです。

Go言語の初期のツールチェインは、Plan 9というオペレーティングシステムのツールチェインをベースにしており、その多くがC言語で書かれていました。しかし、Go言語自体が成熟するにつれて、ツールチェインの保守性、開発効率、そしてGo言語のセルフホスト化（GoでGoをコンパイルする）の推進のために、これらのC言語部分をGo言語に書き換える必要性が高まりました。

`rsc.io/c2go` は、この大規模な移行プロジェクトのために特別に作られた変換ツールであり、一般的なCからGoへのコンバータではありません。このツールを使って既存のCコードをGoに「再変換 (reconvert)」する際に、Goの命名規則（エクスポートされる識別子には末尾にアンダースコアを付けないなど）に合わせる必要が生じました。

したがって、このコミットは、新しいGoベースのアセンブラの導入と、それに伴うコードベースのクリーンアップおよびGo言語の慣習への準拠を目的としたものです。`Type_` から `Type` へのリネームや、`anames`、`regstr` といった内部シンボルのエクスポートは、新しいアセンブラがこれらの要素をより直接的に利用できるようにするための変更であり、Goのコードとしての可読性と整合性を向上させる意図があります。

## 前提知識の解説

このコミットを理解するためには、以下の概念が役立ちます。

*   **Go言語のツールチェイン (Go Toolchain):** Go言語のプログラムをビルド、実行、テストするためのツール群の総称です。これには、コンパイラ (`go tool compile`)、アセンブラ (`go tool asm`)、リンカ (`go tool link`) などが含まれます。
*   **アセンブラ (Assembler):** アセンブリ言語で書かれたコードを機械語（CPUが直接実行できる形式）に変換するプログラムです。Go言語では、Goのアセンブリ言語（Plan 9アセンブリに似た構文）を使用します。
*   **リンカ (Linker):** コンパイルされたオブジェクトファイル（機械語に変換されたコード）やライブラリを結合し、実行可能なプログラムを生成するプログラムです。
*   **`cmd/internal/obj` パッケージ:** Goのソースコードツリー内にある `src/cmd/internal/obj` パッケージは、Goコンパイラとリンカのバックエンドで共通して使用されるオブジェクトファイルフォーマットとアセンブリ命令に関する定義を含んでいます。これはGoツールチェインの非常に低レベルな部分であり、通常、Goアプリケーション開発者が直接触れることはありません。
*   **エクスポートされた識別子 (Exported Identifiers):** Go言語では、パッケージ外からアクセス可能な（エクスポートされた）識別子（変数、関数、型など）は、大文字で始まらなければならないという規則があります。このコミットでは、内部的に使用されていた `Type_` のような識別子が、外部から参照されるようになるため、Goの命名規則に沿って `Type` に変更されています。
*   **`rsc.io/c2go`:** Russ Cox氏がGoツールチェインのCからGoへの移行のために開発した、CコードをGoコードに変換するツールです。これは一般的なC-to-Goコンバータではなく、Goツールチェインの特定のニーズに合わせて調整されたものでした。

## 技術的詳細

このコミットの技術的な詳細は、主にGoツールチェインの内部構造と、Go言語の命名規則への準拠に焦点を当てています。

1.  **`Type_` から `Type` へのリネーム:**
    *   Go言語では、エクスポートされる（パッケージ外から参照可能な）識別子は大文字で始まる必要があります。また、Goの慣習として、内部的な識別子やエクスポートされない識別子には、末尾にアンダースコアを付けることは一般的ではありません。
    *   `cmd/internal/obj` パッケージ内の `Type_` というフィールドは、おそらくC言語のコードから変換された際に、Goのキーワードとの衝突を避けるため、あるいは内部的な識別子であることを示すためにアンダースコアが付与されていたと考えられます。
    *   新しいアセンブラの導入に伴い、これらのシンボルがより広範に利用されるようになったため、Goの標準的な命名規則に合わせる形で `Type` にリネームされました。これにより、コードの可読性が向上し、Goの慣習に沿ったAPIが提供されます。
    *   この変更は、`obj.Addr` 構造体（アセンブリ命令のアドレスを表す）のフィールドに影響を与え、`p.From.Type_` や `p.To.Type_` のような参照が `p.From.Type` や `p.To.Type` に変更されています。これは、アセンブリ命令のオペランドの型を扱う際に、よりクリーンなAPIを提供します。

2.  **シンボルのエクスポートとリネーム (`anames` -> `Anames`, `regstr` -> `Register`):**
    *   `anames` は、アセンブリ命令の名前（例: `ADD`, `MOV`）を文字列で保持する配列です。`regstr` は、レジスタの名前（例: `AX`, `BX`）を文字列で保持する配列です。
    *   これらの配列は、Goツールチェインの内部でアセンブリ命令やレジスタの文字列表現を扱うために使用されていました。
    *   コミットメッセージにある「export more symbols」の通り、これらの内部的なデータ構造が新しいアセンブラから直接アクセスされるようになったため、Goのエクスポート規則に従って `Anames` および `Register` にリネームされました。これにより、これらのデータがパッケージ外から参照可能になり、新しいアセンブラの実装が容易になります。
    *   特に `anames[5689]` という記述は、Goの異なるアーキテクチャ（5: ARM, 6: x86-64, 8: x86, 9: PowerPC64）に対応する `anames` 配列がそれぞれ `Anames` に変更されたことを示唆しています。

3.  **`rsc.io/c2go` の役割:**
    *   このツールは、C言語のコードをGo言語のコードに変換する際に、Goの命名規則や慣習に合わせた変換を行う役割を担っていました。
    *   コミットメッセージの「reconvert using rsc.io/c2go rev f9db76e」は、既存のCからGoに変換されたコードを、`c2go` の特定のバージョン（リビジョン `f9db76e`）を使って再生成したことを意味します。この再生成の過程で、`Type_` のような識別子が自動的に `Type` に変更されたり、`anames` や `regstr` がエクスポートされるように調整されたりしたと考えられます。
    *   これは、手動での大規模なリネーム作業を避けるための自動化されたアプローチであり、コードベース全体の整合性を保つ上で非常に重要でした。

これらの変更は、Goツールチェインの内部構造をよりGo言語らしく、かつ新しいアセンブラの設計に適合させるための基盤となる作業です。

## コアとなるコードの変更箇所

このコミットでは、主に `src/cmd/internal/obj` および各アーキテクチャ（`arm`, `i386`, `ppc64`, `x86`）のアセンブラ関連ファイル (`anames*.go`, `asm*.go`, `list*.go`, `obj*.go`)、そして新しいアセンブラのフロントエンド (`src/cmd/new*a/*.go`) に広範な変更が加えられています。

具体的な変更箇所は以下の通りです。

1.  **`Type_` から `Type` へのリネーム:**
    *   `src/cmd/internal/obj/arm/asm5.go`、`src/cmd/internal/obj/arm/obj5.go` など、各アーキテクチャの `obj*.go` ファイルや `asm*.go` ファイルで、`obj.Addr` 構造体の `Type_` フィールドへの参照が `Type` に変更されています。
    *   例: `p.To.Type_` が `p.To.Type` に、`a.Type_` が `a.Type` に変更。
    *   `src/cmd/internal/obj/data.go` や `src/cmd/internal/obj/link.go` など、`obj` パッケージの共通ファイルでも同様の変更が見られます。
    *   `src/cmd/internal/obj/i386/asm8.go` の `oclass` 関数や `vaddr` 関数など、アドレスの型を判定するロジックでも `a.Type_` が `a.Type` に変更されています。

2.  **`anames` から `Anames` へのリネームとエクスポート:**
    *   `src/cmd/internal/obj/arm/anames5.go`、`src/cmd/internal/obj/i386/anames8.go` など、各アーキテクチャの `anames*.go` ファイルで、`var anamesX = []string{...}` が `var Anames = []string{...}` に変更されています。これにより、`anames` 配列がエクスポートされるようになりました。
    *   これに伴い、`src/cmd/internal/obj/arm/list5.go` の `Aconv` 関数など、`anames` を参照していた箇所が `Anames` を参照するように変更されています。

3.  **`regstr` から `Register` へのリネームとエクスポート:**
    *   `src/cmd/internal/obj/i386/list8.go` で、`var regstr = []string{...}` が `var Register = []string{...}` に変更されています。
    *   これに伴い、`Rconv` 関数など、`regstr` を参照していた箇所が `Register` を参照するように変更されています。

4.  **新しいアセンブラ (`src/cmd/new*a/`) の更新:**
    *   `src/cmd/new5a/a.y`、`src/cmd/new5a/y.go` など、新しいアセンブラのパーサー関連ファイルでも、`Type_` から `Type` への変更が反映されています。これは、アセンブラが内部的に使用するデータ構造の定義が更新されたためです。

これらの変更は、Goツールチェインの低レベルな部分に広範にわたって適用されており、コードベース全体の整合性を保つための大規模なリファクタリングであることがわかります。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は、Goツールチェインの内部APIのクリーンアップと、Go言語の命名規則への準拠を目的としています。

### `Type_` から `Type` への変更

`cmd/internal/obj` パッケージは、Goコンパイラとリンカが中間表現（アセンブリ命令のようなもの）を扱うための基盤を提供します。このパッケージには、アセンブリ命令のオペランド（引数）を表す `obj.Addr` 構造体が含まれています。

変更前は、`obj.Addr` 構造体には `Type_` というフィールドがありました。このフィールドは、オペランドの型（例: レジスタ、メモリ、定数など）を示すために使用されていました。Go言語では、エクスポートされる識別子は大文字で始まる必要がありますが、末尾にアンダースコアを付けることは一般的ではありません。`Type_` のような命名は、C言語のコードから自動変換された際の名残であるか、あるいはGoのキーワード `type` との衝突を避けるための内部的な慣習であった可能性があります。

このコミットでは、`Type_` が `Type` にリネームされました。これは、Goの命名規則に厳密に準拠し、`obj.Addr` 構造体のAPIをよりGo言語らしくするためです。この変更により、`obj.Addr` の `Type` フィールドは、Goの他のエクスポートされたフィールドと同様に、より自然な形でアクセスできるようになります。

例:
```go
// 変更前
if p.To.Type_ == D_REG { ... }

// 変更後
if p.To.Type == D_REG { ... }
```
この変更は、`obj.Addr` を使用するGoツールチェインの多くの部分に影響を与え、広範なコード修正が必要となりました。これは、`rsc.io/c2go` ツールによる自動変換と、それに続く手動での調整によって行われたと考えられます。

### `anames` から `Anames`、`regstr` から `Register` への変更

`anames` と `regstr` は、それぞれアセンブリ命令の名前とレジスタの名前を文字列で保持する内部的な配列でした。これらは、アセンブリコードの生成やデバッグ出力などで、数値コードを人間が読める文字列に変換するために使用されていました。

変更前は、これらの配列はパッケージ内部でのみ使用されることを意図して、小文字で始まる名前が付けられていました。しかし、新しいアセンブラの導入に伴い、これらのデータがパッケージ外からも参照される必要が生じました。

Go言語では、パッケージ外からアクセス可能な識別子は大文字で始まる必要があります。そのため、このコミットでは `anames` が `Anames` に、`regstr` が `Register` にリネームされ、エクスポートされるようになりました。

例:
```go
// 変更前 (src/cmd/internal/obj/arm/list5.go)
s = anames5[a]

// 変更後 (src/cmd/internal/obj/arm/list5.go)
s = Anames[a]

// 変更前 (src/cmd/internal/obj/i386/list8.go)
str = fmt.Sprintf("%s", regstr[r-D_AL])

// 変更後 (src/cmd/internal/obj/i386/list8.go)
str = fmt.Sprintf("%s", Register[r-D_AL])
```

これらの変更は、Goツールチェインの内部構造をよりモジュール化し、新しいアセンブラが既存の低レベルなデータにアクセスしやすくするための重要なステップです。これにより、Goツールチェインの進化と保守が容易になります。

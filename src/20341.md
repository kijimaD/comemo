## 変更の背景

Go言語の初期のランタイムは、パフォーマンスが要求される部分やシステムとのインタラクションが必要な部分でC言語のコードを多く含んでいました。CPUプロファイリング機能もその一つで、`src/pkg/runtime/cpuprof.goc`というファイルでC言語で実装されていました。

このコミットの主な背景は、GoランタイムのCコードをGoコードに移行するという、より広範な取り組みの一環です。CコードをGoコードに変換することには、以下のような多くの利点があります。

1.  **保守性の向上**: Go言語はC言語に比べてメモリ安全性や並行処理の扱いが容易であり、Go開発者にとってコードの理解と保守がしやすくなります。
2.  **安全性と堅牢性**: C言語はポインタの直接操作などにより、意図しないメモリ破壊やセキュリティ脆弱性を引き起こすリスクがあります。Go言語に移行することで、これらのリスクを軽減できます。
3.  **Goエコシステムとの統合**: Go言語で書かれたコードは、Goのツールチェイン（ガベージコレクタ、スケジューラ、テストフレームワークなど）とより密接に連携できます。
4.  **開発効率の向上**: Go言語の強力な型システム、組み込みの並行処理プリミティブ（goroutine、channel）、および豊富な標準ライブラリは、開発効率を高めます。
5.  **クロスプラットフォーム対応の簡素化**: Cgo（GoからCコードを呼び出すメカニズム）を使用すると、クロスコンパイルや異なるOS/アーキテクチャでのビルドが複雑になることがあります。純粋なGoコードにすることで、この複雑さを軽減できます。

特にCPUプロファイリングのような、シグナルハンドラとGoルーチン間でデータをやり取りするような低レベルの機能では、C言語とGo言語の間のインターフェース（Cgo）がオーバーヘッドになったり、複雑な同期メカニズムが必要になったりすることがあります。これを純粋なGoで実装することで、より効率的で安全なデータハンドリングが可能になります。

## 前提知識の解説

### CPUプロファイリング

CPUプロファイリングは、プログラムがCPU時間をどこで消費しているかを特定するためのパフォーマンス分析手法です。これにより、ボトルネックとなっている関数やコードパスを特定し、最適化の対象を見つけることができます。

Go言語のCPUプロファイラは、**サンプリング方式**を採用しています。これは、一定の間隔（例えば1秒間に100回）でプログラムの実行を一時停止し、その時点でのコールスタック（スタックトレース）を記録するというものです。記録されたスタックトレースは、各関数がCPUをどれだけ使用しているかを示す統計情報として集計されます。

### Goランタイム

Goランタイムは、Goプログラムの実行を管理する低レベルのシステムです。これには、ガベージコレクタ、goroutineスケジューラ、メモリ管理、システムコールインターフェースなどが含まれます。Goプログラムは、オペレーティングシステム上で直接実行されるのではなく、Goランタイムによって抽象化された環境で実行されます。CPUプロファイリングのような機能は、このランタイムの一部として実装され、プログラム全体の実行状況を監視します。

### Cgo

Cgoは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。Goランタイムの初期段階では、既存のCライブラリを利用したり、OSとの低レベルなインタラクションを行ったりするためにCgoが多用されていました。しかし、Cgoの呼び出しにはオーバーヘッドがあり、またC言語のメモリ管理やエラーハンドリングの複雑さがGoの安全性モデルと衝突する可能性もあります。そのため、Goランタイムの重要な部分は徐々に純粋なGoコードに移行されてきました。

### シグナルハンドラ

シグナルハンドラは、オペレーティングシステムからの特定のシグナル（例えば、プログラムの終了要求、セグメンテーション違反、タイマー割り込みなど）を受信した際に実行される特別な関数です。CPUプロファイリングでは、通常、`SIGPROF`（プロファイリングタイマーシグナル）が使用されます。このシグナルが一定間隔でプロセスに送信され、シグナルハンドラがその時点でのスタックトレースを収集します。

シグナルハンドラは非常に制約の多い環境で実行されます。
*   **非同期性**: 任意のタイミングで実行されるため、メインのプログラム実行と競合状態になる可能性があります。
*   **非再入可能性**: シグナルハンドラ内で、シグナルハンドラが実行中に再度呼び出される可能性のある関数（例えば、メモリ割り当て関数や多くのシステムコール）を呼び出すことは安全ではありません。
*   **限定された操作**: メモリ割り当てやロックの取得など、多くの一般的な操作はシグナルハンドラ内では安全に行えません。

このコミットでは、シグナルハンドラが収集したプロファイルデータを、安全にGoルーチンに引き渡すための複雑なメカニズムが実装されています。

### アトミック操作

アトミック操作は、複数のCPUコアやスレッド（この場合はシグナルハンドラとGoルーチン）から同時にアクセスされる共有データに対して、不可分（atomic）に行われる操作です。これにより、競合状態を防ぎ、データの整合性を保証します。例えば、`CompareAndSwap` (CAS)のような操作は、特定の値が期待される値と一致する場合にのみ、その値を新しい値に更新します。CPUプロファイリングのデータハンドオフメカニズムでは、`handoff`フィールドの更新にアトミック操作が使用されています。

### `google-perftools`

`google-perftools`は、Googleが開発したパフォーマンス分析ツールのスイートです。Go言語のCPUプロファイラは、そのアルゴリズムとデータ構造に`google-perftools`の影響を受けています。特に、スタックトレースのハッシュテーブル管理や、プロファイルデータのログ記録の概念が共通しています。

## 技術的詳細

このコミットの核心は、CPUプロファイリングのデータ収集（シグナルハンドラ側）とデータ書き出し（Goルーチン側）の間の安全かつ効率的な連携メカニズムをGo言語で再実装した点にあります。

### データ構造 `cpuProfile`

新しい`cpuprof.go`ファイルでは、`cpuProfile`という構造体が定義されています。これがCPUプロファイリングの状態とデータを管理します。

```go
type cpuProfile struct {
	on     bool    // profiling is on
	wait   note    // goroutine waits here
	count  uintptr // tick count
	evicts uintptr // eviction count
	lost   uintptr // lost ticks that need to be logged

	// Active recent stack traces.
	hash [numBuckets]struct {
		entry [assoc]cpuprofEntry
	}

	// Log of traces evicted from hash.
	// Signal handler has filled log[toggle][:nlog].
	// Goroutine is writing log[1-toggle][:handoff].
	log     [2][logSize / 2]uintptr
	nlog    uintptr
	toggle  int32
	handoff uint32

	// Writer state.
	// Writer maintains its own toggle to avoid races
	// looking at signal handler's toggle.
	wtoggle  uint32
	wholding bool // holding & need to release a log half
	flushing bool // flushing hash table - profile is over
	eodSent  bool // special end-of-data record sent; => flushing
}
```

*   `hash`: 最近のスタックトレースをキャッシュするためのハッシュテーブル。`google-perftools`と同様に、衝突解決のために連想配列（`assoc`個のエントリ）を使用します。
*   `log`: 2つのバッファ（`log[0]`と`log[1]`）を持つログ領域。シグナルハンドラが一方のバッファにデータを書き込み、Goルーチンがもう一方のバッファからデータを読み出します。
*   `nlog`: 現在シグナルハンドラが書き込んでいるログバッファ内のデータ量。
*   `toggle`: シグナルハンドラが現在使用しているログバッファ（0または1）を示すインデックス。
*   `handoff`: シグナルハンドラとGoルーチン間のデータハンドオフの状態を管理する重要なフィールド。このフィールドはアトミック操作で更新されます。
    *   `0`: Goルーチンがログバッファを使用しておらず、シグナルハンドラが所有している状態。
    *   `非ゼロ`: シグナルハンドラがログバッファをGoルーチンに引き渡した状態。値は引き渡されたログのサイズを示します。
    *   `高ビット (0x80000000) がセット`: プロファイリングが終了し、Goルーチンがハッシュテーブルに残っているデータをフラッシュしている状態。
*   `wait`: Goルーチンが新しいプロファイルデータが利用可能になるのを待つための`note`（Goランタイムの同期プリミティブ）。
*   `wtoggle`, `wholding`, `flushing`, `eodSent`: Goルーチン（書き出し側）の状態を管理するためのフィールド。

### シグナルハンドラとGoルーチン間の連携メカニズム

このコミットの最も複雑な部分は、シグナルハンドラ（`cpuproftick`から`add`、`evict`、`flushlog`を呼び出す）と、プロファイルデータを書き出すGoルーチン（`getprofile`を呼び出す）の間で、いかに安全にデータをやり取りするかという点です。シグナルハンドラはメモリ割り当てやロック取得ができないという厳しい制約があります。

1.  **二重バッファリング**: `cpuProfile.log`は2つのログバッファを持ちます。シグナルハンドラは一方のバッファにスタックトレースを記録し、Goルーチンはもう一方のバッファからデータを読み出します。
2.  **`handoff`フィールドによる状態管理**:
    *   シグナルハンドラが現在のログバッファを使い切った場合、`flushlog`を呼び出します。
    *   `flushlog`は、`handoff`フィールドをアトミックに更新しようとします（`cas(&p.handoff, 0, uint32(p.nlog))`）。これは、`handoff`が`0`（Goルーチンがアイドル状態）の場合にのみ、現在のログサイズを`handoff`に設定します。
    *   更新に成功した場合、シグナルハンドラは`notewakeup(&p.wait)`を呼び出してGoルーチンを起動し、`toggle`を反転させて次のログバッファに切り替えます。
    *   Goルーチンは`getprofile`内で`notetsleepg(&p.wait, -1)`を呼び出して待機します。`handoff`が非ゼロになると、Goルーチンは起動し、その値からログサイズを読み取ります。
    *   Goルーチンはログバッファの処理が完了すると、`handoff`をアトミックに`0`に戻します（`cas(&p.handoff, n, 0)`）。
3.  **プロファイリング終了時の処理**: `SetCPUProfileRate(0)`が呼び出されてプロファイリングが停止されると、`handoff`フィールドの高ビット（`0x80000000`）がセットされます。これは、Goルーチンに対して、シグナルハンドラからのデータはもう来ないこと、そしてハッシュテーブルに残っているすべてのデータをフラッシュする必要があることを伝えます。
4.  **データ損失の許容**: シグナルハンドラがログバッファを使い切った際に、Goルーチンがまだ前のバッファの処理を終えていない場合（`cas`が失敗した場合）、シグナルハンドラはスタックトレースをログに記録できず、そのデータは失われます。この損失は`cpuProfile.lost`カウンタで追跡されます。これは、シグナルハンドラの厳格な制約（ブロックできない）を満たすためのトレードオフです。

### 主要な関数

*   **`SetCPUProfileRate(hz int)`**: CPUプロファイリングのサンプリングレートを設定します。`hz`が0の場合、プロファイリングを停止します。プロファイリングが既にオンの場合、または前回のプロファイリングが完了していない場合は、レートを変更できません。
*   **`cpuproftick(pc *uintptr, n int32)`**: シグナルハンドラから呼び出されるエントリポイント。スタックトレース`pc`を`add`関数に渡します。
*   **`(*cpuProfile) add(pc []uintptr)`**: スタックトレースをプロファイルのハッシュテーブルに追加します。
    *   スタックトレースのハッシュ値を計算します。
    *   ハッシュテーブル内に同じスタックトレースが既に存在すれば、そのカウントをインクリメントします。
    *   存在しない場合、最もカウントの少ないエントリをハッシュテーブルから「追い出し（evict）」、新しいスタックトレースをその場所に挿入します。追い出されたエントリはログに記録されます。
    *   シグナルハンドラから呼び出されるため、メモリ割り当てやロック取得は行いません。
*   **`(*cpuProfile) evict(e *cpuprofEntry) bool`**: ハッシュテーブルから追い出されたエントリのデータをログバッファにコピーします。ログバッファが満杯の場合、`flushlog`を呼び出してGoルーチンに引き渡そうとします。
*   **`(*cpuProfile) flushlog() bool`**: 現在のログバッファをGoルーチンに引き渡し、次のログバッファに切り替えます。`handoff`フィールドのアトミックな更新と、Goルーチンの起動（`notewakeup`）を行います。
*   **`(*cpuProfile) getprofile() []byte`**: プロファイルデータを書き出すGoルーチンから呼び出されます。新しいプロファイルデータブロックが利用可能になるまでブロックし、データを`[]byte`として返します。プロファイリングが終了し、すべてのデータがフラッシュされると`nil`を返します。この関数は、`handoff`フィールドの状態に基づいて、ログバッファの取得、ハッシュテーブルのフラッシュ、および終了処理を行います。
*   **`CPUProfile() []byte`**: `runtime/pprof`パッケージから呼び出される公開API。内部的に`cpuprof.getprofile()`を呼び出します。

## コアとなるコードの解説

新しい`src/pkg/runtime/cpuprof.go`ファイルに実装された主要なロジックに焦点を当てます。

### `cpuProfile` 構造体

```go
type cpuProfile struct {
	// ... (前述のフィールド) ...
	log     [2][logSize / 2]uintptr // 2つのログバッファ
	nlog    uintptr                 // 現在のログバッファのデータ量
	toggle  int32                   // シグナルハンドラが使用中のバッファインデックス
	handoff uint32                  // シグナルハンドラとGoルーチン間のハンドオフ状態
	// ... (その他のフィールド) ...
}
```
この構造体は、プロファイリングのすべての状態をカプセル化しています。特に`log`の二重バッファと`handoff`フィールドが、シグナルハンドラとGoルーチン間の非同期通信の鍵となります。

### `(*cpuProfile) add(pc []uintptr)` 関数

```go
func (p *cpuProfile) add(pc []uintptr) {
	// ... (ハッシュ計算) ...

	// Add to entry count if already present in table.
	// ... (ハッシュテーブル内の既存エントリ検索とカウントインクリメント) ...

	// Evict entry with smallest count.
	// ... (最もカウントの少ないエントリの特定) ...
	if e.count > 0 {
		if !p.evict(e) { // evictを呼び出し、ログに記録
			// Could not evict entry.  Record lost stack.
			p.lost++ // ログに記録できなかった場合は損失をカウント
			return
		}
		p.evicts++
	}

	// Reuse the newly evicted entry.
	// ... (新しいスタックトレースでエントリを再利用) ...
}
```
`add`関数は、シグナルハンドラから呼び出され、CPUプロファイリングの「ティック」ごとに実行されます。これは、スタックトレースをハッシュテーブルに効率的に追加し、キャッシュミスが発生した場合には`evict`を呼び出してデータをログに移動させます。シグナルハンドラの制約により、この関数は非常に高速で、メモリ割り当てやブロック操作を行わないように設計されています。

### `(*cpuProfile) evict(e *cpuprofEntry) bool` 関数

```go
func (p *cpuProfile) evict(e *cpuprofEntry) bool {
	// ... (ログに書き込むデータ量計算) ...
	log := &p.log[p.toggle]
	if p.nlog+nslot > uintptr(len(p.log[0])) { // 現在のログバッファが満杯の場合
		if !p.flushlog() { // flushlogを試みる
			return false // フラッシュできなかった場合はfalseを返す（データ損失）
		}
		log = &p.log[p.toggle] // 新しいログバッファに切り替える
	}

	// ... (データをログバッファにコピー) ...
	return true
}
```
`evict`は、ハッシュテーブルから追い出されたスタックトレースを、シグナルハンドラが書き込んでいる現在のログバッファにコピーします。ログバッファが満杯になった場合、`flushlog`を呼び出してGoルーチンにバッファを引き渡そうとします。ここで`flushlog`が失敗した場合（Goルーチンがまだ前のバッファを処理中の場合）、データは失われます。

### `(*cpuProfile) flushlog() bool` 関数

```go
func (p *cpuProfile) flushlog() bool {
	if !cas(&p.handoff, 0, uint32(p.nlog)) { // handoffが0の場合にのみ、現在のnlogをセット
		return false // Goルーチンがまだ前のバッファを処理中のため失敗
	}
	notewakeup(&p.wait) // Goルーチンを起動

	p.toggle = 1 - p.toggle // ログバッファを切り替える
	// ... (失われたプロファイルデータの記録) ...
	p.nlog = q
	return true
}
```
`flushlog`は、シグナルハンドラが現在のログバッファの書き込みを完了し、Goルーチンにそのバッファの処理を依頼する際に呼び出されます。`cas`（CompareAndSwap）操作により、`handoff`フィールドがアトミックに更新されます。これにより、シグナルハンドラとGoルーチン間の競合状態を防ぎます。`notewakeup`は、`p.wait`で待機しているGoルーチンを起動します。

### `(*cpuProfile) getprofile() []byte` 関数

```go
func (p *cpuProfile) getprofile() []byte {
	// ... (初期チェックと前回のログの解放) ...

	if p.flushing { // プロファイリング終了後のフラッシュモード
		goto Flush
	}

	// Wait for new log.
	notetsleepg(&p.wait, -1) // 新しいログが利用可能になるまで待機
	noteclear(&p.wait)

	switch n := p.handoff; {
	// ... (handoffの値に応じた処理) ...
	case n == 0x80000000: // プロファイリング終了のシグナル
		p.flushing = true
		goto Flush
	default: // 新しいログデータが利用可能
		n &^= 0x80000000
		p.wholding = true
		return uintptrBytes(p.log[p.wtoggle][:n]) // ログデータをバイトスライスとして返す
	}

Flush:
	// In flush mode.
	// Add is no longer being called.  We own the log.
	// Evict the hash table into the log and return it.
	// ... (ハッシュテーブルに残っているデータをすべてログにフラッシュ) ...

	// ... (最終的なログデータの返却とクリーンアップ) ...
	return nil // すべてのデータが処理されたらnilを返す
}
```
`getprofile`は、プロファイルデータをファイルなどに書き出すGoルーチンから呼び出されます。この関数は、`handoff`フィールドを監視し、新しいデータが利用可能になるか、プロファイリングが終了するまで待機します。プロファイリング終了時には、ハッシュテーブルに残っているすべてのデータをログにフラッシュし、最終的なプロファイルデータを返します。

これらのGo言語による再実装は、シグナルハンドラの制約を尊重しつつ、Goの並行処理モデルとアトミック操作を巧みに利用して、複雑なデータハンドオフを安全かつ効率的に実現しています。

## 変更の背景

Go言語の初期のランタイムは、パフォーマンスが要求される部分やシステムとのインタラクションが必要な部分でC言語のコードを多く含んでいました。CPUプロファイリング機能もその一つで、`src/pkg/runtime/cpuprof.goc`というファイルでC言語で実装されていました。

このコミットの主な背景は、GoランタイムのCコードをGoコードに移行するという、より広範な取り組みの一環です。CコードをGoコードに変換することには、以下のような多くの利点があります。

1.  **保守性の向上**: Go言語はC言語に比べてメモリ安全性や並行処理の扱いが容易であり、Go開発者にとってコードの理解と保守がしやすくなります。
2.  **安全性と堅牢性**: C言語はポインタの直接操作などにより、意図しないメモリ破壊やセキュリティ脆弱性を引き起こすリスクがあります。Go言語に移行することで、これらのリスクを軽減できます。
3.  **Goエコシステムとの統合**: Go言語で書かれたコードは、Goのツールチェイン（ガベージコレクタ、スケジューラ、テストフレームワークなど）とより密接に連携できます。
4.  **開発効率の向上**: Go言語の強力な型システム、組み込みの並行処理プリミティブ（goroutine、channel）、および豊富な標準ライブラリは、開発効率を高めます。
5.  **クロスプラットフォーム対応の簡素化**: Cgo（GoからCコードを呼び出すメカニズム）を使用すると、クロスコンパイルや異なるOS/アーキテクチャでのビルドが複雑になることがあります。純粋なGoコードにすることで、この複雑さを軽減できます。

特にCPUプロファイリングのような、シグナルハンドラとGoルーチン間でデータをやり取りするような低レベルの機能では、C言語とGo言語の間のインターフェース（Cgo）がオーバーヘッドになったり、複雑な同期メカニズムが必要になったりすることがあります。これを純粋なGoで実装することで、より効率的で安全なデータハンドリングが可能になります。

## 前提知識の解説

### CPUプロファイリング

CPUプロファイリングは、プログラムがCPU時間をどこで消費しているかを特定するためのパフォーマンス分析手法です。これにより、ボトルネックとなっている関数やコードパスを特定し、最適化の対象を見つけることができます。

Go言語のCPUプロファイラは、**サンプリング方式**を採用しています。これは、一定の間隔（例えば1秒間に100回）でプログラムの実行を一時停止し、その時点でのコールスタック（スタックトレース）を記録するというものです。記録されたスタックトレースは、各関数がCPUをどれだけ使用しているかを示す統計情報として集計されます。

### Goランタイム

Goランタイムは、Goプログラムの実行を管理する低レベルのシステムです。これには、ガベージコレクタ、goroutineスケジューラ、メモリ管理、システムコールインターフェースなどが含まれます。Goプログラムは、オペレーティングシステム上で直接実行されるのではなく、Goランタイムによって抽象化された環境で実行されます。CPUプロファイリングのような機能は、このランタイムの一部として実装され、プログラム全体の実行状況を監視します。

### Cgo

Cgoは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。Goランタイムの初期段階では、既存のCライブラリを利用したり、OSとの低レベルなインタラクションを行ったりするためにCgoが多用されていました。しかし、Cgoの呼び出しにはオーバーヘッドがあり、またC言語のメモリ管理やエラーハンドリングの複雑さがGoの安全性モデルと衝突する可能性もあります。そのため、Goランタイムの重要な部分は徐々に純粋なGoコードに移行してきました。

### シグナルハンドラ

シグナルハンドラは、オペレーティングシステムからの特定のシグナル（例えば、プログラムの終了要求、セグメンテーション違反、タイマー割り込みなど）を受信した際に実行される特別な関数です。CPUプロファイリングでは、通常、`SIGPROF`（プロファイリングタイマーシグナル）が使用されます。このシグナルが一定間隔でプロセスに送信され、シグナルハンドラがその時点でのスタックトレースを収集します。

シグナルハンドラは非常に制約の多い環境で実行されます。
*   **非同期性**: 任意のタイミングで実行されるため、メインのプログラム実行と競合状態になる可能性があります。
*   **非再入可能性**: シグナルハンドラ内で、シグナルハンドラが実行中に再度呼び出される可能性のある関数（例えば、メモリ割り当て関数や多くのシステムコール）を呼び出すことは安全ではありません。
*   **限定された操作**: メモリ割り当てやロックの取得など、多くの一般的な操作はシグナルハンドラ内では安全に行えません。

このコミットでは、シグナルハンドラが収集したプロファイルデータを、安全にGoルーチンに引き渡すための複雑なメカニズムが実装されています。

### アトミック操作

アトミック操作は、複数のCPUコアやスレッド（この場合はシグナルハンドラとGoルーチン）から同時にアクセスされる共有データに対して、不可分（atomic）に行われる操作です。これにより、競合状態を防ぎ、データの整合性を保証します。例えば、`CompareAndSwap` (CAS)のような操作は、特定の値が期待される値と一致する場合にのみ、その値を新しい値に更新します。CPUプロファイリングのデータハンドオフメカニズムでは、`handoff`フィールドの更新にアトミック操作が使用されています。

### `google-perftools`

`google-perftools`は、Googleが開発したパフォーマンス分析ツールのスイートです。Go言語のCPUプロファイラは、そのアルゴリズムとデータ構造に`google-perftools`の影響を受けています。特に、スタックトレースのハッシュテーブル管理や、プロファイルデータのログ記録の概念が共通しています。

## 技術的詳細

このコミットの核心は、CPUプロファイリングのデータ収集（シグナルハンドラ側）とデータ書き出し（Goルーチン側）の間の安全かつ効率的な連携メカニズムをGo言語で再実装した点にあります。

### データ構造 `cpuProfile`

新しい`cpuprof.go`ファイルでは、`cpuProfile`という構造体が定義されています。これがCPUプロファイリングの状態とデータを管理します。

```go
type cpuProfile struct {
	on     bool    // profiling is on
	wait   note    // goroutine waits here
	count  uintptr // tick count
	evicts uintptr // eviction count
	lost   uintptr // lost ticks that need to be logged

	// Active recent stack traces.
	hash [numBuckets]struct {
		entry [assoc]cpuprofEntry
	}

	// Log of traces evicted from hash.
	// Signal handler has filled log[toggle][:nlog].
	// Goroutine is writing log[1-toggle][:handoff].
	log     [2][logSize / 2]uintptr
	nlog    uintptr
	toggle  int32
	handoff uint32

	// Writer state.
	// Writer maintains its own toggle to avoid races
	// looking at signal handler's toggle.
	wtoggle  uint32
	wholding bool // holding & need to release a log half
	flushing bool // flushing hash table - profile is over
	eodSent  bool // special end-of-data record sent; => flushing
}
```

*   `hash`: 最近のスタックトレースをキャッシュするためのハッシュテーブル。`google-perftools`と同様に、衝突解決のために連想配列（`assoc`個のエントリ）を使用します。
*   `log`: 2つのバッファ（`log[0]`と`log[1]`）を持つログ領域。シグナルハンドラが一方のバッファにデータを書き込み、Goルーチンがもう一方のバッファからデータを読み出します。
*   `nlog`: 現在シグナルハンドラが書き込んでいるログバッファ内のデータ量。
*   `toggle`: シグナルハンドラが現在使用しているログバッファ（0または1）を示すインデックス。
*   `handoff`: シグナルハンドラとGoルーチン間のデータハンドオフの状態を管理する重要なフィールド。このフィールドはアトミック操作で更新されます。
    *   `0`: Goルーチンがログバッファを使用しておらず、シグナルハンドラが所有している状態。
    *   `非ゼロ`: シグナルハンドラがログバッファをGoルーチンに引き渡した状態。値は引き渡されたログのサイズを示します。
    *   `高ビット (0x80000000) がセット`: プロファイリングが終了し、Goルーチンがハッシュテーブルに残っているデータをフラッシュしている状態。
*   `wait`: Goルーチンが新しいプロファイルデータが利用可能になるのを待つための`note`（Goランタイムの同期プリミティブ）。
*   `wtoggle`, `wholding`, `flushing`, `eodSent`: Goルーチン（書き出し側）の状態を管理するためのフィールド。

### シグナルハンドラとGoルーチン間の連携メカニズム

このコミットの最も複雑な部分は、シグナルハンドラ（`cpuproftick`から`add`、`evict`、`flushlog`を呼び出す）と、プロファイルデータを書き出すGoルーチン（`getprofile`を呼び出す）の間で、いかに安全にデータをやり取りするかという点です。シグナルハンドラはメモリ割り当てやロック取得ができないという厳しい制約があります。

1.  **二重バッファリング**: `cpuProfile.log`は2つのログバッファを持ちます。シグナルハンドラは一方のバッファにスタックトレースを記録し、Goルーチンはもう一方のバッファからデータを読み出します。
2.  **`handoff`フィールドによる状態管理**:
    *   シグナルハンドラが現在のログバッファを使い切った場合、`flushlog`を呼び出します。
    *   `flushlog`は、`handoff`フィールドをアトミックに更新しようとします（`cas(&p.handoff, 0, uint32(p.nlog))`）。これは、`handoff`が`0`（Goルーチンがアイドル状態）の場合にのみ、現在のログサイズを`handoff`に設定します。
    *   更新に成功した場合、シグナルハンドラは`notewakeup(&p.wait)`を呼び出してGoルーチンを起動し、`toggle`を反転させて次のログバッファに切り替えます。
    *   Goルーチンは`getprofile`内で`notetsleepg(&p.wait, -1)`を呼び出して待機します。`handoff`が非ゼロになると、Goルーチンは起動し、その値からログサイズを読み取ります。
    *   Goルーチンはログバッファの処理が完了すると、`handoff`をアトミックに`0`に戻します（`cas(&p.handoff, n, 0)`）。
3.  **プロファイリング終了時の処理**: `SetCPUProfileRate(0)`が呼び出されてプロファイリングが停止されると、`handoff`フィールドの高ビット（`0x80000000`）がセットされます。これは、Goルーチンに対して、シグナルハンドラからのデータはもう来ないこと、そしてハッシュテーブルに残っているすべてのデータをフラッシュする必要があることを伝えます。
4.  **データ損失の許容**: シグナルハンドラがログバッファを使い切った際に、Goルーチンがまだ前のバッファの処理を終えていない場合（`cas`が失敗した場合）、シグナルハンドラはスタックトレースをログに記録できず、そのデータは失われます。この損失は`cpuProfile.lost`カウンタで追跡されます。これは、シグナルハンドラの厳格な制約（ブロックできない）を満たすためのトレードオフです。

### 主要な関数

*   **`SetCPUProfileRate(hz int)`**: CPUプロファイリングのサンプリングレートを設定します。`hz`が0の場合、プロファイリングを停止します。プロファイリングが既にオンの場合、または前回のプロファイリングが完了していない場合は、レートを変更できません。
*   **`cpuproftick(pc *uintptr, n int32)`**: シグナルハンドラから呼び出されるエントリポイント。スタックトレース`pc`を`add`関数に渡します。
*   **`(*cpuProfile) add(pc []uintptr)`**: スタックトレースをプロファイルのハッシュテーブルに追加します。
    *   スタックトレースのハッシュ値を計算します。
    *   ハッシュテーブル内に同じスタックトレースが既に存在すれば、そのカウントをインクリメントします。
    *   存在しない場合、最もカウントの少ないエントリをハッシュテーブルから「追い出し（evict）」、新しいスタックトレースをその場所に挿入します。追い出されたエントリはログに記録されます。
    *   シグナルハンドラから呼び出されるため、メモリ割り当てやブロック操作は行いません。
*   **`(*cpuProfile) evict(e *cpuprofEntry) bool`**: ハッシュテーブルから追い出されたエントリのデータをログバッファにコピーします。ログバッファが満杯の場合、`flushlog`を呼び出してGoルーチンに引き渡そうとします。
*   **`(*cpuProfile) flushlog() bool`**: 現在のログバッファをGoルーチンに引き渡し、次のログバッファに切り替えます。`handoff`フィールドのアトミックな更新と、Goルーチンの起動（`notewakeup`）を行います。
*   **`(*cpuProfile) getprofile() []byte`**: プロファイルデータを書き出すGoルーチンから呼び出されます。新しいプロファイルデータブロックが利用可能になるまでブロックし、データを`[]byte`として返します。プロファイリングが終了し、すべてのデータがフラッシュされると`nil`を返します。この関数は、`handoff`フィールドの状態に基づいて、ログバッファの取得、ハッシュテーブルのフラッシュ、および終了処理を行います。
*   **`CPUProfile() []byte`**: `runtime/pprof`パッケージから呼び出される公開API。内部的に`cpuprof.getprofile()`を呼び出します。

type cpuProfile struct {
	// ... (前述のフィールド) ...

	nlog    uintptr                 // 現在のログバッファのデータ量

### `(*cpuProfile) add(pc []uintptr)` 関数

```go
func (p *cpuProfile) add(pc []uintptr) {
	// ... (ハッシュ計算) ...

	// Add to entry count if already present in table.
	// ... (ハッシュテーブル内の既存エントリ検索とカウントインクリメント) ...

	// Evict entry with smallest count.
	// ... (最もカウントの少ないエントリの特定) ...
	if e.count > 0 {
		if !p.evict(e) { // evictを呼び出し、ログに記録
			// Could not evict entry.  Record lost stack.
			p.lost++ // ログに記録できなかった場合は損失をカウント
			return
		}
		p.evicts++
	}

	// Reuse the newly evicted entry.
	// ... (新しいスタックトレースでエントリを再利用) ...
}
```
`add`関数は、シグナルハンドラから呼び出され、CPUプロファイリングの「ティック」ごとに実行されます。これは、スタックトレースをハッシュテーブルに効率的に追加し、キャッシュミスが発生した場合には`evict`を呼び出してデータをログに移動させます。シグナルハンドラの制約により、この関数は非常に高速で、メモリ割り当てやブロック操作を行わないように設計されています。

### `(*cpuProfile) evict(e *cpuprofEntry) bool` 関数

```go
func (p *cpuProfile) evict(e *cpuprofEntry) bool {
	// ... (ログに書き込むデータ量計算) ...
	log := &p.log[p.toggle]
	if p.nlog+nslot > uintptr(len(p.log[0])) { // 現在のログバッファが満杯の場合
		if !p.flushlog() { // flushlogを試みる
			return false // フラッシュできなかった場合はfalseを返す（データ損失）
		}
		log = &p.log[p.toggle] // 新しいログバッファに切り替える
	}

	// ... (データをログバッファにコピー) ...
	return true
}
```
`evict`は、ハッシュテーブルから追い出されたスタックトレースを、シグナルハンドラが書き込んでいる現在のログバッファにコピーします。ログバッファが満杯になった場合、`flushlog`を呼び出してGoルーチンにバッファを引き渡そうとします。ここで`flushlog`が失敗した場合（Goルーチンがまだ前のバッファを処理中の場合）、データは失われます。

### `(*cpuProfile) flushlog() bool` 関数

```go
func (p *cpuProfile) flushlog() bool {
	if !cas(&p.handoff, 0, uint32(p.nlog)) { // handoffが0の場合にのみ、現在のnlogをセット
		return false // Goルーチンがまだ前のバッファを処理中のため失敗
	}
	notewakeup(&p.wait) // Goルーチンを起動

	p.toggle = 1 - p.toggle // ログバッファを切り替える
	// ... (失われたプロファイルデータの記録) ...
	p.nlog = q
	return true
}
```
`flushlog`は、シグナルハンドラが現在のログバッファの書き込みを完了し、Goルーチンにそのバッファの処理を依頼する際に呼び出されます。`cas`（CompareAndSwap）操作により、`handoff`フィールドがアトミックに更新されます。これにより、シグナルハンドラとGoルーチン間の競合状態を防ぎます。`notewakeup`は、`p.wait`で待機しているGoルーチンを起動します。

### `(*cpuProfile) getprofile() []byte` 関数

```go
func (p *cpuProfile) getprofile() []byte {
	// ... (初期チェックと前回のログの解放) ...

	if p.flushing { // プロファイリング終了後のフラッシュモード
		goto Flush
	}

	// Wait for new log.
	notetsleepg(&p.wait, -1) // 新しいログが利用可能になるまで待機
	noteclear(&p.wait)

	switch n := p.handoff; {
	// ... (handoffの値に応じた処理) ...
	case n == 0x80000000: // プロファイリング終了のシグナル
		p.flushing = true
		goto Flush
	default: // 新しいログデータが利用可能
		n &^= 0x80000000
		p.wholding = true
		return uintptrBytes(p.log[p.wtoggle][:n]) // ログデータをバイトスライスとして返す
	}

Flush:
	// In flush mode.
	// Add is no longer being called.  We own the log.
	// Evict the hash table into the log and return it.
	// ... (ハッシュテーブルに残っているデータをすべてログにフラッシュ) ...

	// ... (最終的なログデータの返却とクリーンアップ) ...
	return nil // すべてのデータが処理されたらnilを返す
}
```
`getprofile`は、プロファイルデータをファイルなどに書き出すGoルーチンから呼び出されます。この関数は、`handoff`フィールドを監視し、新しいデータが利用可能になるか、プロファイリングが終了するまで待機します。プロファイリング終了時には、ハッシュテーブルに残っているすべてのデータをログにフラッシュし、最終的なプロファイルデータを返します。

`cmd/internal/ld: use usual flooding for c-archive`

このコミットメッセージは、`c-archive` ビルドモードにおいて「通常の flooding」を使用するという意図を示しています。しかし、コミット本文では「cl/8711 であなたのコメントに応じてこれを削除したと言ったが、どうやら削除していなかったようだ」と述べており、これは以前の変更で `c-archive` に対する特定のリンカの挙動（後述の「flooding」）を無効にするはずだったが、実際にはそうなっていなかったという状況を修正するものです。

## 変更の背景

Go言語のリンカは、最終的なバイナリサイズを最適化するために、デッドコードエリミネーション（DCE）を実行します。これは、プログラムのエントリーポイントから到達できない関数や変数を削除するプロセスです。しかし、特定のビルドモード、特にライブラリを生成するモードでは、外部のコードから呼び出される可能性のある関数が、Goリンカの内部的な到達可能性分析では「到達不可能」と判断されてしまうことがあります。このような場合、リンカは意図的にすべてのシンボルを「到達可能」とマークする「flooding」と呼ばれる手法を用いることがあります。これにより、外部から呼び出される可能性のある関数が誤って削除されるのを防ぎます。

このコミットの背景には、`c-archive` ビルドモード（C/C++アプリケーションから利用可能な静的ライブラリを生成するモード）において、この「flooding」が不必要に適用され続けていたという問題があります。コミットメッセージにある `cl/8711` は、おそらく以前のコードレビューや変更セットを指しており、そこで `c-archive` からこの「flooding」の挙動を削除する意図があったにもかかわらず、それが完全に実施されていなかったことを示唆しています。

結果として、`c-archive` でビルドされたライブラリは、本来であればデッドコードエリミネーションによって削減されるべきコードを含んだままになり、不必要に大きなサイズになっていました。このコミットは、この問題を修正し、`c-archive` ビルドにおいてリンカがデッドコードエリミネーションを適切に実行できるようにすることで、より最適化された、より小さな静的ライブラリを生成することを目的としています。

## 前提知識の解説

### Go言語のビルドモード (Buildmode)

Go言語の `go build` コマンドには、様々な `buildmode` オプションがあります。このコミットに関連するのは以下の2つです。

*   **`c-archive`**: GoパッケージをC言語から呼び出し可能な静的ライブラリ（Unix系では `.a`、Windowsでは `.lib`）としてコンパイルします。このライブラリにはGoランタイムも含まれます。C/C++アプリケーションにGoの機能を組み込む際に使用されます。
*   **`shared`**: Goパッケージを共有ライブラリ（Unix系では `.so`、macOSでは `.dylib`）としてコンパイルします。これは、複数のプログラムで共有される動的ライブラリです。

### Goリンカ (`cmd/internal/ld`)

`cmd/internal/ld` はGoツールチェーンの一部であり、Goプログラムのリンクを担当するリンカです。コンパイラによって生成されたオブジェクトファイル（`.o`）を結合し、実行可能ファイルやライブラリを生成します。その主要な機能の一つに、シンボル解決とデッドコードエリミネーションがあります。

### デッドコードエリミネーション (Dead Code Elimination, DCE)

DCEは、プログラムの最終的なバイナリから、実行時に決して到達しないコード（デッドコード）を削除する最適化手法です。リンカは、プログラムのエントリーポイント（例: `main` 関数）から開始し、呼び出しグラフを辿って到達可能なすべての関数や変数をマークします。マークされなかったコードはデッドコードと見なされ、最終的なバイナリから除外されます。これにより、バイナリサイズが削減され、ロード時間やメモリ使用量が改善されます。

### シンボルとシンボルの到達可能性 (Symbol and Symbol Reachability)

*   **シンボル**: プログラム内の関数、グローバル変数、型など、リンカが参照する名前付きエンティティのことです。
*   **シンボルの到達可能性**: リンカが、あるシンボルがプログラムの実行フローからアクセス可能であるかどうかを判断するプロセスです。通常、リンカはエントリーポイントからグラフ探索を行い、到達可能なシンボルのみを最終的なバイナリに含めます。

### 「flooding」または「marking all symbols as reachable」

これは、リンカがデッドコードエリミネーションの通常のロジックを一時的に無効にし、**すべてのシンボルを強制的に「到達可能」とマークする**手法を指します。この「flooding」は、主に共有ライブラリ（`shared` ビルドモード）をビルドする際に使用されます。共有ライブラリの場合、その中のどの関数が外部のアプリケーションから呼び出されるかリンカは事前に完全に把握できないため、すべての関数を保持しておく必要があります。もしDCEが適用されてしまうと、外部から呼び出されるはずの関数が削除されてしまう可能性があるため、この「flooding」によってDCEを抑制します。

## 技術的詳細

このコミットの核心は、Goリンカが `BuildmodeShared` と `BuildmodeCArchive` の両方に対して適用していた「すべてのシンボルを到達可能とマークする」という挙動を、`BuildmodeShared` のみに限定することです。

*   **変更前**: `BuildmodeShared` または `BuildmodeCArchive` のいずれかの場合、リンカは `deadcode()` 関数内で `Ctxt.Allsym` をループし、すべてのシンボル (`s`) を `s.Reachable = true` とマークしていました。これは、これらのビルドモードではデッドコードエリミネーションを抑制し、すべてのコードを最終的な出力に含めることを意味します。
*   **変更後**: 条件が `BuildmodeShared` のみに変更されました。これにより、`BuildmodeCArchive` の場合は、通常のデッドコードエリミネーションのロジックが適用されるようになります。

### `c-archive` における影響

`c-archive` は静的ライブラリを生成するため、そのライブラリをリンクするC/C++アプリケーションは、Goのコードベース全体のごく一部しか使用しない可能性があります。以前の挙動では、`c-archive` でビルドされたライブラリは、使用されないGoの関数やデータを含んだままになり、結果としてライブラリのサイズが不必要に大きくなっていました。

この変更により、`c-archive` ビルドではリンカがデッドコードエリミネーションを実行できるようになります。これにより、実際にC/C++コードから呼び出されるGoの関数や、それらから到達可能なGoのコードのみが最終的な静的ライブラリに含まれるようになります。これは、生成される静的ライブラリのサイズを大幅に削減し、リンク時の効率を向上させる可能性があります。

### `shared` における影響

`shared` ビルドモードでは、引き続きすべてのシンボルが到達可能とマークされます。これは正しい挙動です。共有ライブラリは動的にロードされ、その中のどの関数が外部から呼び出されるかリンカは事前に完全に予測できないため、すべてのエクスポートされたシンボルを保持しておく必要があります。

## コアとなるコードの解説

変更された行は `src/cmd/internal/ld/go.go` の625行目です。

*   **変更前**:
    ```go
    if Buildmode == BuildmodeShared || Buildmode == BuildmodeCArchive {
    ```
    この条件文は、「ビルドモードが `BuildmodeShared` であるか、または `BuildmodeCArchive` である場合」に真となります。この条件が真の場合、その後のループ `for s := Ctxt.Allsym; s != nil; s = s.Allsym { ... }` が実行され、リンカが認識している**すべてのシンボル (`s`) が `s.Reachable = true` とマークされます**。これは、前述の「flooding」であり、デッドコードエリミネーションを抑制する効果があります。

*   **変更後**:
    ```go
    if Buildmode == BuildmodeShared {
    ```
    この条件文は、「ビルドモードが `BuildmodeShared` である場合」にのみ真となります。これにより、`BuildmodeCArchive` の場合はこの `if` ブロックがスキップされ、すべてのシンボルが強制的に到達可能とマークされることはなくなります。結果として、`c-archive` ビルドでは、リンカの通常のデッドコードエリミネーションロジックが適用され、実際に使用されるシンボルのみが最終的なライブラリに含まれるようになります。

この変更は、`c-archive` ビルドの出力サイズを最適化し、より効率的な静的ライブラリを生成するための重要な修正です。

# [インデックス 24393] ファイルの概要

このコミットは、Goランタイムのガベージコレクション (GC) アシストメカニズムにおける重要なバグ修正を導入しています。具体的には、GCアシストがGC作業を完了するまで、またはGCサイクルが終了するまで、ミューテーター（アプリケーションコード）がブロックされるように変更することで、ヒープの目標値が大幅に超過する問題を解決します。これにより、GCが一時的に利用可能な作業を持たない期間（例：マークフェーズ間の移行時）に、ミューテーターがGCのバックプレッシャーなしに高速にアロケーションを進めてしまう問題が解消されます。

## 元コミット内容

以前のGoランタイムでは、GCアシストが満たされる方法が3つありました。
1.  ミューテーターがバックグラウンドGCからクレジットを「盗む」。
2.  ミューテーターが実際にGC作業を行う。
3.  利用可能なGC作業がこれ以上ない。

このコミット以前は、3番目の「利用可能なGC作業がこれ以上ない」という状況でもGCアシストが満たされたと見なされていました。これは、GCがマークフェーズ間（例：マーク1からマーク2、マーク2からマーク終了）の移行期間など、一時的に作業がないと予想される期間に問題を引き起こしました。このような期間中、高速にメモリを確保するミューテーターに対してバックプレッシャーがかからず、ヒープの目標値を大幅に超過してしまう可能性がありました。

具体的には、`test/init1.go`や`runtime/trace`テストのような、到達可能なヒープが小さく、大量のガベージバイトスライスを高速にアロケーションするループを含むテストで、ヒープ目標を数桁も超過する現象が確認されていました。

## 変更の背景

Goのガベージコレクタは、アプリケーションの実行と並行して動作するコンカレントGCです。GCはヒープの使用量に基づいて次のGCサイクルを開始する「ヒープ目標」を設定します。この目標を超過しないように、ミューテーター（アプリケーションコード）がメモリをアロケーションする際に、GC作業の一部を肩代わりする「GCアシスト」というメカニズムが導入されています。

しかし、前述の通り、GCが一時的に作業を持たない期間が存在しました。例えば、マークフェーズの完了後、次のフェーズへの移行処理中などです。この期間にミューテーターがメモリをアロケーションしようとすると、GCアシストが必要になりますが、GC側には「利用可能な作業がない」ため、アシストはすぐに完了したと見なされていました。これにより、ミューテーターはGC作業をせずにアロケーションを続行でき、結果としてヒープ目標を大きく上回るメモリを消費してしまうという問題が発生していました。

この問題は、GCの効率性だけでなく、アプリケーションのメモリフットプリントの予測可能性にも影響を与え、最悪の場合、メモリ不足によるクラッシュにつながる可能性がありました。このコミットは、この「バックプレッシャーの欠如」という根本的な原因に対処するために導入されました。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションに関するいくつかの基本的な概念を理解しておく必要があります。

*   **ガベージコレクション (GC)**: プログラムが不要になったメモリを自動的に解放するプロセスです。GoのGCは、並行（Concurrent）かつ低遅延（Low-latency）な三色マーク＆スイープ（Tri-color Mark-and-Sweep）アルゴリズムを採用しています。
*   **ミューテーター (Mutator)**: アプリケーションの実行コードそのものを指します。ミューテーターはメモリをアロケーションし、ヒープ上のオブジェクトグラフを変更します。
*   **GCアシスト (GC Assist)**: ミューテーターがメモリをアロケーションする際に、GCの作業の一部を肩代わりするメカニズムです。これは、ヒープの成長が速すぎる場合に、GCが追いつけるようにするためのバックプレッシャーとして機能します。ミューテーターは、自身がアロケーションしたバイト数に応じて「GCクレジット」を消費し、クレジットが不足するとGCアシストを実行してクレジットを回復する必要があります。
*   **バックグラウンドGC (Background GC)**: ミューテーターと並行して動作し、実際のGC作業（オブジェクトのマーク、スイープなど）の大部分を実行するGCゴルーチンです。
*   **ヒープ目標 (Heap Goal)**: 次のGCサイクルが開始されるべきヒープのサイズです。Goランタイムは、この目標値を超えないようにヒープを管理しようとします。
*   **スキャンクレジット (Scan Credit)**: GCアシストがバックグラウンドGCから「盗む」ことができるGC作業量の単位です。バックグラウンドGCが十分な作業を完了している場合、ミューテーターは実際にGC作業を行わずに、このクレジットを消費することでアシストを完了できます。
*   **マークフェーズ (Mark Phases)**: GoのGCは主に以下のフェーズで構成されます。
    *   **マーク1 (Mark 1)**: GCルート（スタック、グローバル変数など）から到達可能なオブジェクトをマークし始めます。
    *   **マーク2 (Mark 2)**: オブジェクトグラフ全体を走査し、到達可能なすべてのオブジェクトをマークします。
    *   **マーク終了 (Mark Termination)**: マークフェーズの最終処理を行い、次のスイープフェーズに移行します。
    これらのフェーズ間には、GCが一時的にアクティブな作業を持たない期間が存在することがあります。

## 技術的詳細

このコミットの核心は、`gcAssistAlloc`関数におけるGCアシストの振る舞いを変更することにあります。以前は、GCアシストが「利用可能なGC作業がない」という理由で早期に終了することが許されていました。これは、GCが一時的にアイドル状態にあるときに、ミューテーターがGCアシストの「借金」（アロケーションによって発生したGC作業の必要量）を支払うことなく、自由にメモリをアロケーションし続けることを可能にしていました。

この変更では、`gcAssistAlloc`関数内に`retry`ラベルと`goto retry`ステートメントを導入することで、GCアシストがその「借金」を完全に支払うまで、またはGCサイクルが終了するまで、ミューテーターをブロックし続けるようにします。

具体的には、GCアシストは以下のいずれかの方法で借金を返済しようとします。
1.  バックグラウンドGCからスキャンクレジットを盗む。
2.  ミューテーター自身がGC作業（オブジェクトのスキャンなど）を実行する。

もしこれらの方法で借金を完全に返済できなかった場合、ミューテーターはすぐにアロケーションを続行するのではなく、短い時間（100マイクロ秒）スリープし、他のゴルーチンやGCゴルーチンに実行を譲ります。その後、再度GCアシストの試行を繰り返します。このループは、借金が完済されるか、現在のGCサイクルが終了するまで続きます。

これにより、GCが一時的に作業を持たない期間でも、ミューテーターはヒープ目標を超過してアロケーションを進めることができなくなります。GCが次のフェーズに移行して作業が利用可能になるか、GCサイクルが終了するまで、ミューテーターは待機することになります。結果として、ヒープ目標の超過は、コンカレントスキャンフェーズ中に発生するアロケーション量と、GCトリガーからアシストが有効になるまでの間のアロケーション量にほぼ限定されるようになります。

## コアとなるコードの解説

変更された`gcAssistAlloc`関数内の主要なコード変更とその意味は以下の通りです。

1.  **`retry:` ラベルの追加**:
    ```go
    +retry:
    ```
    これは、GCアシストの処理を再試行するためのジャンプ先として機能するラベルです。`goto retry`ステートメントと組み合わせて、借金が完済されるまでループ処理を実装します。

2.  **GC完了時の `scanWork = 0`**:
    ```go
    			// GC is done, so ignore any remaining debt.
    			scanWork = 0
    			return
    ```
    `gcBlackenEnabled`が0の場合（GCが完了していることを示す）、残りの`scanWork`（GCアシストの借金）を0に設定し、関数を終了します。これは、GCサイクルが終了した場合は、もはやGCアシストの借金を支払う必要がないためです。

3.  **`workDone` の導入と `scanWork` の更新**:
    ```go
    		workDone := gcw.scanWork - startScanWork
    		gp.gcscanwork += workDone
    		scanWork -= workDone
    ```
    ミューテーターが実際に実行したGC作業量（`workDone`）を計算し、それを`gp.gcscanwork`（ゴルーチンが実行したGC作業の総量）に加算します。そして、残りの`scanWork`（まだ支払うべき借金）から`workDone`を減算します。これにより、借金がどれだけ減ったかを正確に追跡します。

4.  **`Gosched()` 後のGC完了チェックと `scanWork = 0`**:
    ```go
    	Gosched()
    
    	// It's likely that this assist wasn't able to pay off
    	// its debt, but it's also likely that the Gosched let
    	// the GC finish this cycle and there's no point in
    	// waiting. If the GC finished, skip the delay below.
    	if atomicload(&gcBlackenEnabled) == 0 {
    		scanWork = 0
    	}
    ```
    `Gosched()`を呼び出して他のゴルーチンに実行を譲った後、再度`gcBlackenEnabled`をチェックします。これは、`Gosched()`によってGCゴルーチンが実行され、GCサイクルが完了した可能性があるためです。もしGCが完了していれば、同様に`scanWork`を0に設定し、借金を無視します。

5.  **`scanWork > 0` の場合の再試行ロジック**:
    ```go
    	if scanWork > 0 {
    		// We were unable steal enough credit or perform
    		// enough work to pay off the assist debt. We need to
    		// do one of these before letting the mutator allocate
    		// more, so go around again after performing an
    		// interruptible sleep for 100 us (the same as the
    		// getfull barrier) to let other mutators run.
    		timeSleep(100 * 1000)
    		goto retry
    	}
    ```
    これがこのコミットの最も重要な部分です。もし`scanWork`がまだ0より大きい場合（つまり、GCアシストの借金がまだ残っている場合）、ミューテーターは`timeSleep(100 * 1000)`（100マイクロ秒）で一時的にスリープします。これは、他のミューテーターやGCゴルーチンに実行機会を与え、GC作業が進むことを期待するためです。その後、`goto retry`によって`retry:`ラベルに戻り、GCアシストのプロセスを最初からやり直します。このループにより、ミューテーターは借金を完済するか、GCサイクルが終了するまで、アロケーションをブロックされることになります。

*   **ミューテーター (Mutator)**: アプリケーションの実行コードそのものを指します。ミューテーターはメモリをアロケーションし、ヒープ上のオブジェクトグラフを変更します。
*   **GCアシスト (GC Assist)**: ミューテーターがメモリをアロケーションする際に、GCの作業の一部を肩代わりするメカニズムです。これは、ヒープの成長が速すぎる場合に、GCが追いつけるようにするためのバックプレッシャーとして機能します。ミューテーターは、自身がアロケーションしたバイト数に応じて「GCクレジット」を消費し、クレジットが不足するとGCアシストを実行してクレジットを回復する必要があります。
*   **バックグラウンドGC (Background GC)**: ミューテーターと並行して動作し、実際のGC作業（オブジェクトのマーク、スイープなど）の大部分を実行するGCゴルーチンです。
*   **ヒープ目標 (Heap Goal)**: 次のGCサイクルが開始されるべきヒープのサイズです。Goランタイムは、この目標値を超えないようにヒープを管理しようとします。
*   **スキャンクレジット (Scan Credit)**: GCアシストがバックグラウンドGCから「盗む」ことができるGC作業量の単位です。バックグラウンドGCが十分な作業を完了している場合、ミューテーターは実際にGC作業を行わずに、このクレジットを消費することでアシストを完了できます。
*   **マークフェーズ (Mark Phases)**: GoのGCは主に以下のフェーズで構成されます。
    *   **マーク1 (Mark 1)**: GCルート（スタック、グローバル変数など）から到達可能なオブジェクトをマークし始めます。
    *   **マーク2 (Mark 2)**: オブジェクトグラフ全体を走査し、到達可能なすべてのオブジェクトをマークします。
    *   **マーク終了 (Mark Termination)**: マークフェーズの最終処理を行い、次のスイープフェーズに移行します。
    これらのフェーズ間には、GCが一時的にアクティブな作業を持たない期間が存在することがあります。

## 技術的詳細

このコミットの核心は、`gcAssistAlloc`関数におけるGCアシストの振る舞いを変更することにあります。以前は、GCアシストが「利用可能なGC作業がない」という理由で早期に終了することが許されていました。これは、GCが一時的にアイドル状態にあるときに、ミューテーターがGCアシストの「借金」（アロケーションによって発生したGC作業の必要量）を支払うことなく、自由にメモリをアロケーションし続けることを可能にしていました。

この変更では、`gcAssistAlloc`関数内に`retry`ラベルと`goto retry`ステートメントを導入することで、GCアシストがその「借金」を完全に支払うまで、またはGCサイクルが終了するまで、ミューテーターをブロックし続けるようにします。

具体的には、GCアシストは以下のいずれかの方法で借金を返済しようとします。
1.  バックグラウンドGCからスキャンクレジットを盗む。
2.  ミューテーター自身がGC作業（オブジェクトのスキャンなど）を実行する。

もしこれらの方法で借金を完全に返済できなかった場合、ミューテーターはすぐにアロケーションを続行するのではなく、短い時間（100マイクロ秒）スリープし、他のゴルーチンやGCゴルーチンに実行を譲ります。その後、再度GCアシストの試行を繰り返します。このループは、借金が完済されるか、現在のGCサイクルが終了するまで続きます。

これにより、GCが一時的に作業を持たない期間でも、ミューテーターはヒープ目標を超過してアロケーションを進めることができなくなります。GCが次のフェーズに移行して作業が利用可能になるか、GCサイクルが終了するまで、ミューテーターは待機することになります。結果として、ヒープ目標の超過は、コンカレントスキャンフェーズ中に発生するアロケーション量と、GCトリガーからアシストが有効になるまでの間のアロケーション量にほぼ限定されるようになります。

## コアとなるコードの解説

変更された`gcAssistAlloc`関数内の主要なコード変更とその意味は以下の通りです。

1.  **`retry:` ラベルの追加**:
    ```go
    +retry:
    ```
    これは、GCアシストの処理を再試行するためのジャンプ先として機能するラベルです。`goto retry`ステートメントと組み合わせて、借金が完済されるまでループ処理を実装します。

2.  **GC完了時の `scanWork = 0`**:
    ```go
    			// GC is done, so ignore any remaining debt.
    			scanWork = 0
    			return
    ```
    `gcBlackenEnabled`が0の場合（GCが完了していることを示す）、残りの`scanWork`（GCアシストの借金）を0に設定し、関数を終了します。これは、GCサイクルが終了した場合は、もはやGCアシストの借金を支払う必要がないためです。

3.  **`workDone` の導入と `scanWork` の更新**:
    ```go
    		workDone := gcw.scanWork - startScanWork
    		gp.gcscanwork += workDone
    		scanWork -= workDone
    ```
    ミューテーターが実際に実行したGC作業量（`workDone`）を計算し、それを`gp.gcscanwork`（ゴルーチンが実行したGC作業の総量）に加算します。そして、残りの`scanWork`（まだ支払うべき借金）から`workDone`を減算します。これにより、借金がどれだけ減ったかを正確に追跡します。

4.  **`Gosched()` 後のGC完了チェックと `scanWork = 0`**:
    ```go
    	Gosched()
    
    	// It's likely that this assist wasn't able to pay off
    	// its debt, but it's also likely that the Gosched let
    	// the GC finish this cycle and there's no point in
    	// waiting. If the GC finished, skip the delay below.
    	if atomicload(&gcBlackenEnabled) == 0 {
    		scanWork = 0
    	}
    ```
    `Gosched()`を呼び出して他のゴルーチンに実行を譲った後、再度`gcBlackenEnabled`をチェックします。これは、`Gosched()`によってGCゴルーチンが実行され、GCサイクルが完了した可能性があるためです。もしGCが完了していれば、同様に`scanWork`を0に設定し、借金を無視します。

5.  **`scanWork > 0` の場合の再試行ロジック**:
    ```go
    	if scanWork > 0 {
    		// We were unable steal enough credit or perform
    		// enough work to pay off the assist debt. We need to
    		// do one of these before letting the mutator allocate
    		// more, so go around again after performing an
    		// interruptible sleep for 100 us (the same as the
    		// getfull barrier) to let other mutators run.
    		timeSleep(100 * 1000)
    		goto retry
    	}
    ```
    これがこのコミットの最も重要な部分です。もし`scanWork`がまだ0より大きい場合（つまり、GCアシストの借金がまだ残っている場合）、ミューテーターは`timeSleep(100 * 1000)`（100マイクロ秒）で一時的にスリープします。これは、他のミューテーターやGCゴルーチンに実行機会を与え、GC作業が進むことを期待するためです。その後、`goto retry`によって`retry:`ラベルに戻り、GCアシストのプロセスを最初からやり直します。このループにより、ミューテーターは借金を完済するか、GCサイクルが終了するまで、アロケーションをブロックされることになります。

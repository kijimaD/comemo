# [インデックス 25738] ファイルの概要

このコミットは、Goコンパイラのアセンブラ（`cmd/internal/obj/x86`）における重要な変更を導入し、32ビットx86アーキテクチャ（386）上で位置独立コード（PIC）を生成する際のグローバルデータアクセスを改善します。特に、共有ライブラリ（`-shared`ビルドモード）や位置独立実行ファイル（PIE、`-buildmode=pie`）のビルドにおいて、グローバルデータへのアクセスが正しく位置独立になるように修正されています。

## 元コミット内容

`cmd/internal/obj/x86`パッケージにおいて、386アーキテクチャで`-shared`オプションを使用してビルドする際に、グローバルデータへの位置独立アクセスを実装する変更です。

この変更は、グローバルデータにアクセスする命令の直前に`__x86.get_pc_thunk.cx`への呼び出しを追加することで機能します。これにより、プログラムカウンタ（PC）が`CX`レジスタにロードされ、その後の命令は絶対アドレスの代わりに`CX`からの適切なオフセットを使用してアセンブルされます。一部の命令形式ではこの方法でアセンブルできないため、アドレスを最初に`CX`にロードするように書き換えられます。

この修正により、`-buildmode=pie`（位置独立実行ファイル）が機能するようになりますが、まだテストはされていません。Issue #13201を修正するものです。

## 変更の背景

共有ライブラリや位置独立実行ファイル（PIE）をビルドする際、コードはメモリ上の任意のアドレスにロードされても正しく動作する必要があります。これを実現するのが「位置独立コード（PIC）」です。PICでは、絶対アドレスではなく、現在のプログラムカウンタ（PC）からの相対アドレスを使用してデータや関数にアクセスします。

32ビットx86アーキテクチャ（386）には、64ビットx86（x86-64）のようなRIP（Instruction Pointer）相対アドレッシングモードが直接サポートされていません。そのため、32ビットx86でPICを生成するには特別なテクニックが必要です。特にグローバルデータへのアクセスは、そのアドレスがロード時に決定されるため、絶対アドレスで直接参照することはできません。

Goコンパイラが386上で共有ライブラリやPIEを生成する際、このグローバルデータアクセスの問題が課題となっていました。このコミットは、この課題を解決し、Goプログラムが386上でより柔軟に共有ライブラリやPIEとしてビルドできるようにすることを目的としています。具体的には、`__x86.get_pc_thunk.cx`というヘルパー関数を利用して、実行時にPCの値をレジスタに取得し、それを使ってグローバルデータへの相対アドレスを計算する手法を導入しています。

## 前提知識の解説

### 1. 位置独立コード (PIC) と位置独立実行ファイル (PIE)
*   **位置独立コード (PIC: Position-Independent Code)**: メモリ上の任意のアドレスにロードされても正しく実行できる機械語コードです。共有ライブラリ（.so, .dll, .dylib）やPIEの構築に不可欠です。絶対アドレスではなく、相対アドレス（現在の命令ポインタからのオフセット）を使用してデータや関数にアクセスします。
*   **位置独立実行ファイル (PIE: Position-Independent Executable)**: PICとしてコンパイルされた実行ファイルです。ASLR (Address Space Layout Randomization) と組み合わせて使用されることで、セキュリティを向上させます。実行ファイルが毎回異なるメモリ位置にロードされるため、攻撃者が特定のコードやデータのアドレスを予測しにくくなります。

### 2. 共有ライブラリ
複数のプログラムで共有されるライブラリです。メモリを節約し、プログラムのサイズを小さくする利点があります。共有ライブラリ内のコードはPICである必要があります。

### 3. x86 32ビット (386) アーキテクチャの特性
*   **EIP (Instruction Pointer)**: 32ビットx86におけるプログラムカウンタです。次に実行される命令のアドレスを指します。
*   **PC相対アドレッシングの課題**: 32ビットx86には、データアクセスにおいてEIPの値を直接レジスタにロードする命令や、EIP相対でデータにアクセスする汎用的なアドレッシングモードがありません。これは64ビットx86のRIP相対アドレッシングとは対照的です。
*   **`call/pop` イディオム**: 32ビットx86でEIPの値をレジスタに取得するための一般的なテクニックです。
    1.  `call` 命令を実行すると、次の命令のアドレス（リターンアドレス）がスタックにプッシュされ、指定されたアドレスにジャンプします。
    2.  ジャンプ先で`pop` 命令を使ってスタックからリターンアドレスをレジスタにロードします。
    3.  これにより、レジスタに現在のPCの値（正確には`call`命令の次の命令のアドレス）が取得されます。

### 4. `__x86.get_pc_thunk.cx`
これは、上記`call/pop`イディオムを実装したヘルパー関数（またはシンボル）です。`call __x86.get_pc_thunk.cx`を実行すると、`__x86.get_pc_thunk.cx`内でスタックからPCの値を`CX`レジスタにロードし、元の呼び出し元に戻ります。結果として、`CX`レジスタにPCの値が格納されます。`.cx`は`CX`レジスタを使用することを示します。

### 5. Goのアセンブラ (`cmd/internal/obj/x86`)
Goコンパイラは、Go言語のソースコードを機械語に変換する際に、独自のアセンブラを使用します。`cmd/internal/obj/x86`は、x86アーキテクチャ用のコード生成を担当する部分です。
*   `obj.Link`: リンカのコンテキストを表す構造体。ビルドフラグ（例: `Flag_shared`）などを含みます。
*   `obj.Prog`: アセンブリ命令（プログラム）を表す構造体。命令の種類（`As`）、オペランド（`From`, `To`, `From3`）、レジスタ（`Reg`）、アドレス（`Addr`）などを含みます。
*   `obj.Addr`: オペランドのアドレスを表す構造体。シンボル（`Sym`）、名前の種類（`Name`、例: `NAME_EXTERN`、`NAME_STATIC`）、タイプ（`Type`、例: `TYPE_MEM`、`TYPE_ADDR`、`TYPE_REG`）などを含みます。
*   `REG_CX`: x86の`CX`レジスタを表す定数。
*   `obj.NAME_EXTERN`, `obj.NAME_STATIC`, `obj.NAME_GOTREF`: グローバルデータや外部シンボル、GOT参照を表すアドレス名。
*   `obj.R_PCREL`, `obj.R_ADDR`: リロケーションタイプ。`R_PCREL`はPC相対リロケーション、`R_ADDR`は絶対アドレスリロケーション。
*   `obj.ACALL`, `obj.AJMP`, `obj.ATEXT`, `obj.AFUNCDATA`, `obj.ARET`: 特定のアセンブリ命令の種類。
*   `obj.Nopout`, `obj.Appendp`, `obj.Linklookup`: アセンブラ内部で使用されるヘルパー関数。

## 技術的詳細

このコミットの核心は、32ビットx86アーキテクチャで共有ライブラリ（`-shared`）またはPIE（`-buildmode=pie`）をビルドする際に、グローバルデータへのアクセスを位置独立にするための変換ロジックをGoのアセンブラに導入することです。

具体的なアプローチは以下の通りです。

1.  **PC値の取得**: グローバルデータ（`obj.NAME_EXTERN`, `obj.NAME_STATIC`, `obj.NAME_GOTREF`）にアクセスする命令の直前に、`call __x86.get_pc_thunk.cx`という命令を挿入します。この`call`命令が実行されると、`CX`レジスタには現在のプログラムカウンタ（正確には`call`命令の次の命令のアドレス）が格納されます。

2.  **PC相対アドレッシングへの変換**: `CX`レジスタにPCの値がロードされた後、元々グローバルデータに絶対アドレスでアクセスしようとしていた命令は、`CX`レジスタをベースとしたPC相対アドレッシングを使用するように書き換えられます。これにより、命令はメモリ上のどこにロードされても、`CX`からのオフセットを使って常に正しいグローバルデータにアクセスできるようになります。

3.  **特殊なケースのハンドリング**:
    *   一部の命令形式（例: `MOVL $sym, (SP)` や `PUSHL $sym` のように、即値としてシンボルアドレスをオペランドに取る命令で、宛先がレジスタではない場合）は、直接`CX`をベースレジスタとして使用するようにアセンブルすることが困難です。
    *   このような場合、命令は2つのステップに書き換えられます。まず、シンボルアドレスを`CX`レジスタにロードし（例: `MOVL $sym, CX`）、次に`CX`レジスタの内容を元の宛先に移動またはプッシュします（例: `MOVL CX, (SP)` または `PUSHL CX`）。これにより、間接的にPC相対アドレッシングを実現します。

4.  **リロケーションの調整**: PC相対アドレッシングを使用する命令では、リンカが正しくリロケーションを適用できるように、リロケーションエントリの加算値（addend）が調整されます。特に386では、PC相対アドレッシングが`call/jmp`命令以外で使われる場合、`CX`にロードされたPC値からの相対オフセットとして扱われるため、その差分を考慮した調整が必要です。

このメカニズムにより、32ビットx86環境でもGoの共有ライブラリやPIEが、グローバルデータに正しく位置独立でアクセスできるようになります。

## コアとなるコードの変更箇所

このコミットでは、主に`src/cmd/internal/obj/x86/asm6.go`と`src/cmd/internal/obj/x86/obj6.go`の2つのファイルが変更されています。

### `src/cmd/internal/obj/x86/asm6.go`
*   `oclass`関数:
    *   `obj.NAME_EXTERN`または`obj.NAME_STATIC`のアドレスタイプを持つシンボルに対する処理で、`p.Mode == 32`の場合に`ctxt.Flag_shared == 0`（共有ライブラリではない）という条件が追加されました。これにより、共有ライブラリの場合はPC相対アドレッシング（`Yiauto`）を使用するようになります。
*   `vaddr`関数:
    *   `isextern(s)`または`p.Mode != 64`の場合の条件に、`ctxt.Flag_shared == 0`が追加されました。これにより、32ビットモードで共有ライブラリの場合は`obj.R_ADDR`リロケーションタイプではなく、PC相対アドレッシングが考慮されるようになります。
*   `asmandsz`関数:
    *   `obj.NAME_EXTERN`または`obj.NAME_STATIC`のアドレスタイプを持つシンボルに対する処理で、`p.Mode == 32 && ctxt.Flag_shared != 0`の場合に`base = REG_CX`が設定されるようになりました。これは、PC相対アドレッシングのベースとして`CX`レジスタを使用することを示します。
*   `asmins`関数:
    *   `r.Type == obj.R_PCREL`のリロケーションタイプに対する処理で、32ビットモード（`p.Mode == 32`）の場合の`r.Add`の計算ロジックが追加されました。これは、`CX`にロードされたPC値からの相対オフセットを考慮したリロケーション加算値の調整です。

### `src/cmd/internal/obj/x86/obj6.go`
*   `progedit`関数:
    *   `ctxt.Flag_shared != 0 && p.Mode == 32`という条件が追加され、この場合に新しく追加された`rewriteToPcrel(ctxt, p)`関数が呼び出されるようになりました。これが32ビット共有ライブラリ/PIEのためのPC相対変換の入り口です。
*   `rewriteToPcrel`関数:
    *   新しく追加された関数で、32ビットモードで共有ライブラリをビルドする際に、グローバルデータアクセスをPC相対に書き換える主要なロジックを含みます。
    *   `p.RegTo2 != 0`の命令はスキップされます（二重処理防止）。
    *   `ATEXT`, `AFUNCDATA`, `ACALL`, `ARET`, `AJMP`命令はスキップされます。
    *   `isName`ヘルパー関数が定義され、`obj.NAME_EXTERN`, `obj.NAME_STATIC`, `obj.NAME_GOTREF`のアドレスを持つオペランドを識別します。
    *   `p.From`オペランドが`isName`であり、かつ`obj.TYPE_ADDR`の場合（例: `MOVL $sym, (SP)`）、命令を`MOVL $sym, CX; MOVL CX, (SP)`のように2つの命令に書き換えるロジックが含まれます。
    *   `p.From`, `p.To`, `p.From3`のいずれかのオペランドが`isName`である場合、その命令の直前に`call __x86.get_pc_thunk.cx`を挿入し、元の命令を`CX`をベースとしたPC相対アドレッシングを使用するように変換します。

## コアとなるコードの解説

### `src/cmd/internal/obj/x86/asm6.go`の変更点

*   **`oclass`関数**: この関数は、オペランドのアドレッシングモードを分類します。変更前は32ビットモードで外部シンボル（`isextern(a.Sym)`）または`p.Mode == 32`の場合に`Yi32`（32ビット即値/絶対アドレス）を返していました。変更後は、`p.Mode == 32`の場合に`ctxt.Flag_shared == 0`（共有ライブラリではない）という条件が追加されました。これは、共有ライブラリの場合は`Yiauto`（PC相対アドレッシング）を使用するように誘導するための変更です。つまり、共有ライブラリでは絶対アドレスではなくPC相対アドレスを使うべきだという意図が反映されています。

*   **`vaddr`関数**: この関数は、アドレスの仮想アドレスを計算し、必要に応じてリロケーション情報を設定します。変更前は、外部シンボルまたは64ビットモードではない場合に`obj.R_ADDR`（絶対アドレスリロケーション）を設定していました。変更後は、32ビットモードで共有ライブラリではない場合（`p.Mode != 64 && ctxt.Flag_shared == 0`）にのみ`obj.R_ADDR`を設定するように変わりました。これにより、32ビット共有ライブラリでは絶対アドレスリロケーションを避けるようになります。

*   **`asmandsz`関数**: この関数は、アセンブリ命令のオペランドをエンコードする際に、ベースレジスタやオフセットを決定します。`obj.NAME_EXTERN`や`obj.NAME_STATIC`のようなグローバルデータへのアクセスにおいて、`p.Mode == 32 && ctxt.Flag_shared != 0`（32ビットモードで共有ライブラリ）の場合に`base = REG_CX`を設定するようになりました。これは、前述の`__x86.get_pc_thunk.cx`によって`CX`レジスタにロードされたPC値を、グローバルデータアクセスのベースレジスタとして使用するという戦略を直接反映しています。

*   **`asmins`関数**: この関数は、命令をバイトコードに変換し、リロケーションエントリを調整します。`obj.R_PCREL`タイプのリロケーションに対する処理で、32ビットモードの場合の`r.Add`（リロケーション加算値）の計算ロジックが追加されました。
    *   64ビットモードや`AJMP`/`ACALL`命令では、PC相対アドレスは命令の終わりからの相対です。
    *   しかし、32ビットモードで`__x86.get_pc_thunk.cx`を使用する場合、PC相対アドレスは`CX`にロードされたPC値（`call`命令の次の命令の終わり）からの相対となります。このため、`r.Add += int64(r.Off) - p.Pc + int64(r.Siz)`という調整が必要になります。これは、リンカが正しくオフセットを計算できるようにするための重要な変更です。

### `src/cmd/internal/obj/x86/obj6.go`の変更点

*   **`progedit`関数**: この関数は、アセンブリ命令（`obj.Prog`）のリストを走査し、必要に応じて命令を書き換えるリンカのパスの一部です。
    *   `ctxt.Flag_shared != 0 && p.Mode == 32`という条件が追加され、32ビットモードで共有ライブラリをビルドする際に、新しく追加された`rewriteToPcrel(ctxt, p)`関数が呼び出されるようになりました。これは、32ビット共有ライブラリ/PIEのためのPC相対変換処理を有効にするトリガーです。

*   **`rewriteToPcrel`関数**: この関数は、このコミットの主要なロジックを実装しています。
    *   **二重処理の防止**: `p.RegTo2 != 0`のチェックにより、既に処理された命令が再度処理されるのを防ぎます。
    *   **特定の命令のスキップ**: `ATEXT`, `AFUNCDATA`, `ACALL`, `ARET`, `AJMP`といった命令は、グローバルデータアクセスとは直接関係ないか、PC相対アドレッシングの扱いが異なるため、この変換の対象外とされます。
    *   **`isName`ヘルパー**: `obj.NAME_EXTERN`, `obj.NAME_STATIC`, `obj.NAME_GOTREF`といったグローバルデータや外部シンボルを参照するアドレスを識別するためのヘルパー関数です。`STLSBSS`（スレッドローカルストレージ）は除外されます。
    *   **特殊な命令の書き換え**:
        *   `isName(&p.From) && p.From.Type == obj.TYPE_ADDR`の条件は、`MOVL $sym, (SP)`や`PUSHL $sym`のように、即値としてシンボルアドレスをオペランドに取る命令で、かつ宛先がレジスタではないケースを検出します。
        *   このような命令は、直接PC相対アドレッシングに変換するのが難しいため、`MOVL $sym, CX`（シンボルアドレスを`CX`にロード）と、その後に続く`MOVL CX, (SP)`または`PUSHL CX`（`CX`の内容を元の宛先に移動/プッシュ）の2つの命令に書き換えられます。これにより、間接的にPC相対アドレッシングを実現します。
    *   **`call __x86.get_pc_thunk.cx`の挿入と命令の変換**:
        *   `!isName(&p.From) && !isName(&p.To) && (p.From3 == nil || !isName(p.From3))`の条件は、現在の命令がグローバルデータにアクセスしていない場合に`return`します。つまり、グローバルデータにアクセスする命令のみが対象となります。
        *   グローバルデータにアクセスする命令の場合、`obj.Appendp(ctxt, p)`を使って現在の命令の直前に新しい命令を挿入します。
        *   挿入される命令は`obj.ACALL`で、宛先は`__x86.get_pc_thunk.cx`シンボルです。これにより、`CX`レジスタにPC値がロードされます。
        *   元の命令は、`obj.Nopout(p)`によって無効化され、その内容は`call`命令の後に挿入された新しい`obj.Prog`（`r`）にコピーされます。この`r`は、`asmandsz`関数で`base = REG_CX`が設定されることで、`CX`レジスタをベースとしたPC相対アドレッシングを使用するようにアセンブルされます。

これらの変更により、Goコンパイラは32ビットx86アーキテクチャで共有ライブラリやPIEをビルドする際に、グローバルデータへのアクセスを正しく位置独立に処理できるようになります。

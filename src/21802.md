# [インデックス 21802] ファイルの概要

このコミットは、Go言語のツールチェイン、特に`cmd/go`コマンドと内部リンカーである`liblink`におけるアセンブラ検証メカニズムを一時的に無効化するものです。これは、当時進行中であった大規模なマージ作業によって、GoコードとCコード間の同期が一時的に失われることを回避するための措置でした。

## 変更の背景

このコミットの主な背景は、Go言語のツールチェイン内部で進行中であった大規模なコードマージ作業です。Goのツールチェインは、コンパイラ、アセンブラ、リンカーなど、多くのコンポーネントで構成されており、これらの一部はGo言語自体で書かれ、また一部はC言語で書かれています。通常、これらのコンポーネント間には厳密な同期が保たれており、特にアセンブラの出力など、互換性が保証されるように検証が行われています。

しかし、当時予定されていた「upcoming merge」（今後のマージ）は、このGoコードとCコード間の「synchrony」（同期）を一時的に「break」（破壊）する可能性がありました。これは、大規模な変更が同時に導入されることで、一時的にGoで書かれたアセンブラとCで書かれたアセンブラ（または関連するコンポーネント）が異なる出力を生成したり、互換性のない状態になったりすることを意味します。

このような状況下で、通常行われる厳密な検証プロセスを有効にしておくと、ビルドが失敗したり、開発の妨げになったりする可能性があります。そのため、開発の継続性を確保するために、一時的にこの検証メカニズムを無効化する必要がありました。コミットメッセージにある「Will restore separately.」という記述から、この変更が一時的なものであり、マージ作業が完了した後に検証機能が再度有効にされる計画であったことが伺えます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語のツールチェインに関する前提知識が必要です。

1.  **Goツールチェインの構成**:
    *   **`cmd/go`**: Goコマンドラインツールであり、`go build`, `go run`, `go test`などの主要なコマンドを提供します。Goプログラムのビルドプロセス全体を管理する中心的な役割を担っています。
    *   **アセンブラ (Assembler)**: Go言語は、独自のGoアセンブラを使用します。これは、Goのソースコードから生成されるアセンブリコードを処理し、オブジェクトファイルに変換します。Goのアセンブラは、一般的なx86アセンブラとは異なる独自の構文（Plan 9アセンブラに由来）を持っています。
    *   **リンカー (`liblink`)**: Go言語は、独自の内部リンカーを使用します。これは、コンパイルされたGoパッケージを結合して単一の実行可能ファイルを生成する役割を担います。多くの他の言語がシステムリンカー（例: `ld`）に依存するのに対し、Goは独自のリンカーを持つことで、クロスコンパイルの容易さや、Goランタイムとの密接な統合を実現しています。`liblink`は、このリンカーの実装の一部を指すと考えられます。
    *   **オブジェクトファイル (`.o` ファイル)**: Goコンパイラは、Go固有のオブジェクトファイル形式を生成します。これは、C/C++コンパイラが生成するオブジェクトファイルとは互換性がありません。

2.  **`verifyAsm`**:
    `src/cmd/go/build.go`内に存在する`verifyAsm`定数は、Goツールチェイン内部のアセンブラ検証メカニズムに関連しています。これは、Goで書かれたアセンブラとCで書かれたアセンブラ（またはその両方）が、同じ入力に対して一貫した正しい出力を生成するかどうかをチェックするためのフラグです。例えば、`6a`（Cで書かれたアセンブラ）と`new6a`（Goで書かれたアセンブラ）のような異なる実装が存在する場合、両者が同じ結果を出すことを保証するためにこの検証が用いられます。この検証は、Goのビルドプロセスの正確性と整合性を保つ上で重要です。

3.  **`GOOBJ`環境変数**:
    `src/liblink/objfile.c`に登場する`GOOBJ`環境変数は、Goの公式ドキュメントには記載されていない内部的な環境変数である可能性が高いです。Goのツールチェインは、その開発過程で多くの内部的なフラグや環境変数を使用して、特定の動作を制御したり、デバッグを行ったりすることがあります。この変数は、リンカーがオブジェクトファイルをどのように扱うか、あるいは特定のオブジェクトファイル形式のバージョンや挙動を制御するために使用されていたと考えられます。`atoi(env) == 0`という条件から、この変数の値が数値として解釈され、その値によってリンカーの動作が分岐することが示唆されます。

4.  **「同期が壊れる (break the synchrony)」**:
    これは、Goツールチェインの異なる部分（特にGoで書かれたコンポーネントとCで書かれたコンポーネント）が、一時的に互換性のない状態になることを指します。大規模なリファクタリングや新機能の導入、あるいはコンポーネントの書き換え（例: CからGoへの移行）が行われる際に、一時的にこのような状態が発生することがあります。通常、Goのビルドシステムは、このような不整合を検出してエラーを報告しますが、開発の特定の段階では、一時的にこのチェックを緩和する必要が生じることがあります。

## 技術的詳細

このコミットは、Goツールチェインのビルドプロセスにおける2つの主要な変更を含んでいます。

1.  **`src/cmd/go/build.go`における`verifyAsm`定数の変更**:
    *   変更前: `const verifyAsm = true`
    *   変更後: `const verifyAsm = false`
    *   この変更により、Goツールチェインがアセンブラの出力を検証するプロセスが一時的に無効化されます。`verifyAsm`は、Goで書かれたアセンブラとCで書かれたアセンブラ（またはその両方）が、同じソースコードから一貫したオブジェクトファイルを生成するかどうかを確認するための内部的なフラグです。これを`false`に設定することで、アセンブラの出力に一時的な不整合があってもビルドが続行されるようになります。これは、大規模な変更が進行中で、アセンブラの異なる実装間での同期が一時的に失われる可能性がある場合に、開発の妨げにならないようにするための措置です。

2.  **`src/liblink/objfile.c`における`GOOBJ`環境変数のデフォルト値の変更**:
    *   変更前: `if(env == nil) env = "2";`
    *   変更後: `if(env == nil) env = "0";`
    *   この変更は、`GOOBJ`環境変数が設定されていない場合に、そのデフォルト値を`"2"`から`"0"`に変更するものです。`objfile.c`はGoの内部リンカー（`liblink`）の一部であり、Go固有のオブジェクトファイル形式を処理します。`GOOBJ`は、Goの公式ドキュメントには記載されていない内部的な環境変数であり、リンカーがオブジェクトファイルをどのように扱うか、あるいは特定のオブジェクトファイル形式のバージョンや挙動を制御するために使用されていたと考えられます。
    *   `atoi(env) == 0`という条件がその直後に存在することから、`GOOBJ`の値が数値として解釈され、その値が`0`であるかどうかに応じてリンカーの動作が分岐することが示唆されます。デフォルト値を`"2"`から`"0"`に変更することで、`GOOBJ`が未設定の場合に、リンカーの動作が特定の「検証をスキップする」または「互換モードで動作する」といった挙動に切り替わる可能性があります。これは、`verifyAsm`の変更と同様に、進行中のマージ作業による一時的な不整合に対応するための措置と考えられます。

これらの変更は、Goツールチェインの内部的な整合性チェックを一時的に緩和することで、大規模なコードベースの変更（特にGoとCの混在する部分）がスムーズに進行できるようにするためのものです。

## コアとなるコードの解説

1.  **`src/cmd/go/build.go`における`verifyAsm`の変更**:
    *   このファイルは、`go build`コマンドのビルドロジックを定義するGoソースファイルです。
    *   `verifyAsm`は、Goで書かれたアセンブラ（例: `new6a`）とCで書かれたアセンブラ（例: `6a`）の出力が一致するかどうかを検証するための定数です。
    *   変更前は`true`に設定されており、両者の出力が異なる場合にビルドが失敗するようになっていました。
    *   このコミットでは`false`に変更され、アセンブラの出力検証が一時的に無効化されました。これにより、GoとCのアセンブラ間で一時的な不整合があっても、ビルドプロセスが中断されずに進行できるようになります。これは、大規模な変更が進行中で、アセンブラの異なる実装間での同期が一時的に失われる可能性がある場合に、開発の妨げにならないようにするための措置です。

2.  **`src/liblink/objfile.c`における`GOOBJ`環境変数のデフォルト値の変更**:
    *   このファイルは、Goの内部リンカー（`liblink`）の一部であり、Go固有のオブジェクトファイル形式の読み書きを処理するCソースファイルです。
    *   `getenv("GOOBJ")`は、`GOOBJ`という環境変数の値を取得しようとします。
    *   `if(env == nil)`の条件は、`GOOBJ`環境変数が設定されていない場合に実行されるブロックです。
    *   変更前は、`GOOBJ`が設定されていない場合、`env`に文字列`"2"`が代入されていました。
    *   このコミットでは、`env`に文字列`"0"`が代入されるように変更されました。
    *   その直後の`if(atoi(env) == 0)`という条件は、`env`の文字列を整数に変換し、それが`0`であるかどうかをチェックしています。
    *   この変更により、`GOOBJ`が未設定の場合に、リンカーの動作が`atoi(env) == 0`の条件を満たすようになり、`writeobjdirect(ctxt, b)`が呼び出されるパスが選択される可能性が高まります。これは、特定のオブジェクトファイル処理モード（例えば、より直接的な書き込みモードや、特定の検証をスキップするモード）を有効にするための内部的な調整と考えられます。`verifyAsm`の変更と同様に、これは進行中のマージ作業による一時的な不整合に対応するための措置であると推測されます。

これらの変更は、Goツールチェインの内部的な整合性チェックを一時的に緩和することで、大規模なコードベースの変更（特にGoとCの混在する部分）がスムーズに進行できるようにするためのものです。

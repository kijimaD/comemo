# [インデックス 27568] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link/internal/ld`) に IBM System/390 (s390x) アーキテクチャのサポートを追加するものです。特に、s390x特有の再配置（relocation）処理に対応するため、`RV_390_DBL` という新しい再配置バリアントが導入されています。これは、再配置される値が2バイトアラインメントされるように、値を1ビット右シフト（2で割る）する必要があることを示します。

## 元コミット内容

`cmd/link/internal/ld`: s390xサポートを追加

再配置値が1ビット右シフトされるべき（2バイトアラインメントされるように）ことを示す新しい再配置バリアント `RV_390_DBL` を導入する。

## 変更の背景

Go言語は、様々なアーキテクチャとオペレーティングシステムをサポートすることを目指しています。このコミットは、IBMのメインフレームで使用される64ビットアーキテクチャであるs390x（System/390の64ビット版）へのGo言語の移植の一環として行われました。Goプログラムをs390x上で実行可能にするためには、Goコンパイラとリンカがs390xの命令セット、メモリモデル、およびELF（Executable and Linkable Format）の再配置規則を理解し、適切に処理できる必要があります。

特に、s390xアーキテクチャには、特定の命令やデータアクセスにおいて2バイトアラインメントされたアドレスを要求する特性があります。Goリンカが生成するバイナリがs390x上で正しく動作するためには、これらのアラインメント要件を満たすように再配置値を調整する必要があります。このコミットは、そのための具体的なメカニズム、すなわち `RV_390_DBL` 再配置バリアントを導入することで、s390xサポートを可能にしています。

## 前提知識の解説

### リンカ (Linker)
リンカは、コンパイラによって生成された複数のオブジェクトファイル（機械語コードとデータを含む）とライブラリを結合し、実行可能なプログラムや共有ライブラリを生成するツールです。このプロセスには、シンボル解決（異なるファイルで定義された関数や変数の参照を解決する）と再配置（プログラムがメモリにロードされる際のアドレスに基づいて、コード内のアドレス参照を調整する）が含まれます。

### ELF (Executable and Linkable Format)
ELFは、Unix系システムで広く使用されている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準ファイルフォーマットです。ELFファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、および様々なセクション（コード、データ、シンボルテーブル、再配置情報など）で構成されます。

### 再配置 (Relocation)
再配置とは、リンカがプログラム内のアドレス参照を修正するプロセスです。コンパイル時、コンパイラは通常、各オブジェクトファイルがメモリの先頭からロードされると仮定してコードを生成します。しかし、実際には複数のオブジェクトファイルが結合され、プログラム全体が特定のアドレスにロードされるため、これらの仮定されたアドレスは実行時の実際のアドレスに調整される必要があります。再配置エントリは、どの場所の値をどのように修正すべきかをリンカに指示します。

### s390x アーキテクチャ
s390xは、IBMのメインフレームコンピュータで使用される64ビットの命令セットアーキテクチャです。特徴として、固定長命令、豊富なレジスタセット、強力なI/O機能、そして特定の命令におけるアドレスアラインメント要件などが挙げられます。特に、分岐命令やデータアクセス命令の一部は、ターゲットアドレスが特定のバイト境界（例えば2バイト境界）にアラインされていることを期待する場合があります。

### `Thechar`
Goリンカの内部では、各アーキテクチャを識別するために単一の文字（`Thechar`）が使用されます。例えば、`'6'`はamd64、`'9'`はppc64、そしてこのコミットで`'z'`がs390xに割り当てられています。

## 技術的詳細

このコミットの主要な技術的変更点は、s390xアーキテクチャのELF再配置処理をGoリンカに組み込むことです。

1.  **`RV_390_DBL` 再配置バリアントの導入**:
    s390xアーキテクチャでは、特定の再配置タイプ（特にPC相対アドレス指定を伴うもの）において、ターゲットアドレスが2バイトアラインメントされている必要があります。Goリンカが計算する再配置値はバイト単位のアドレスですが、s390xの命令が期待するのは2バイト単位のアドレスオフセットである場合があります。
    `RV_390_DBL` は、このギャップを埋めるために導入されました。このバリアントが指定された再配置では、リンカは計算された再配置値を1ビット右シフト（実質的に2で割る）して、2バイトアラインメントされたオフセットを生成します。これにより、s390xの命令が正しくターゲットアドレスを計算できるようになります。

2.  **s390x固有のELF再配置タイプの追加**:
    `src/cmd/link/internal/ld/elf.go` には、s390xアーキテクチャに特有の多数のELF再配置タイプ（`R_390_NONE` から `R_390_TLS_TPOFF` まで）が追加されています。これらは、s390xの命令セットがサポートする様々なアドレス指定モードや、GOT (Global Offset Table)、PLT (Procedure Linkage Table)、TLS (Thread Local Storage) などのメカニズムに対応するためのものです。例えば、`R_390_PC32DBL` や `R_390_PLT32DBL` のような再配置タイプは、`DBL` サフィックスが示すように、2バイトアラインメントを考慮したPC相対アドレス指定に関連しています。

3.  **ELFヘッダとセクション処理の更新**:
    ELFファイルのヘッダ（`ehdr.machine`）に `EM_S390` が設定され、s390xバイナリであることを示します。また、ELFセクションの処理、特に動的リンキングに関連する `.rela.plt` や `.got` セクションの生成ロジックがs390x向けに調整されています。例えば、`elfdynhash` 関数では、s390x (ELF64) のハッシュテーブルエントリが8バイトであることを考慮して、`Adduint64` を使用するように変更されています。

4.  **リンカのアーキテクチャ設定**:
    `src/cmd/link/internal/ld/arch.go` に `Links390x` 構造体が追加され、s390xのバイトオーダー（ビッグエンディアン）、ポインタサイズ、レジスタサイズなどの基本的なアーキテクチャ特性が定義されています。

## コアとなるコードの変更箇所

### `src/cmd/link/internal/ld/arch.go`
- `Links390x` という `LinkArch` 構造体が追加され、s390xアーキテクチャの基本的な特性（バイトオーダー、名前、`Thechar`、ポインタサイズなど）が定義されています。`Thechar` として `'z'` が割り当てられています。

### `src/cmd/link/internal/ld/data.go`
- `Addpcrelplus` 関数内で、`Thearch.Thechar == 'z'` の場合に `r.Variant = RV_390_DBL` が設定されるようになりました。これは、PC相対再配置においてs390x特有の2バイトアラインメント処理が必要であることを示します。
- `relocsym` 関数内で、s390x (`Thearch.Thechar == 'z'`) の場合に `R_PCRELDBL` と `R_CALL` の再配置タイプが `RV_390_DBL` バリアントを使用するように特別に処理されています。これは、issue 14218に関連する一時的な措置である可能性が示唆されています。

### `src/cmd/link/internal/ld/dwarf.go`
- DWARFデバッグ情報に関連するセクション名や再配置タイプを決定する箇所で、`Thearch.Thechar` が `'z'` の場合も他の64ビットアーキテクチャ（`'0'`, `'6'`, `'7'`, `'9'`）と同様に処理されるように変更されています。これは、s390xも64ビットELFバイナリとして扱われることを意味します。

### `src/cmd/link/internal/ld/elf.go`
- s390xに特有の多数のELF再配置タイプ（`R_390_NONE` から `R_390_TLS_GOTIE20` まで）が定数として追加されています。
- `Elfinit` 関数内で、`Thearch.Thechar` が `'z'` の場合、ELFヘッダの `ehdr.machine` が `EM_S390` に設定されるようになりました。
- `elfdynhash` 関数内で、s390x (ELF64) のハッシュテーブルエントリが8バイトであるため、`Adduint64` を使用して `nbucket`、`nsym`、`buckets`、`chain` の値を書き込むように変更されています。他のアーキテクチャでは `Adduint32` が使用されます。
- `.rela` や `.rela.plt` セクションの処理、動的シンボルテーブルのエントリサイズ (`ELF64SYMSIZE`) など、多くの箇所で `Thearch.Thechar == 'z'` の条件が追加され、s390xが64ビットELFアーキテクチャとして適切に扱われるように修正されています。
- `doelf` 関数内で、`DT_PLTGOT` エントリの処理がs390x向けに調整され、`.got` セクションを参照するように変更されています。
- `Asmbelf` 関数内で、ELFヘッダの `eh.machine` が `EM_S390` に設定され、`.rela.plt` セクションの `sh.entsize` がs390xの場合に `32` に設定されるようになりました。

### `src/cmd/link/internal/ld/ldelf.go`
- `ldelf` 関数内で、ELFオブジェクトの検証時にs390x (`'z'`) のチェックが追加され、`elfobj.machine` が `ElfMachS390` であり、`hdr.Ident[4]` が `ElfClass64` であることを確認します。
- シンボル処理において、s390xのGCCが生成する可能性のある `.LASF` プレフィックスを持つシンボルを無視するロジックが追加されています。
- `reltype` 関数内で、s390xの様々な再配置タイプに対応するサイズ (`*siz`) の設定が追加されています。

### `src/cmd/link/internal/ld/lib.go`
- `BuildMode` の設定において、`goos` が "linux" の場合に `goarch` として "s390x" がサポートされるようになりました。
- `hostlinkArchArgs` 関数内で、`Thearch.Thechar` が `'z'` の場合にホストリンカに `-m64` フラグを渡すように変更されています。

### `src/cmd/link/internal/ld/link.go`
- `RV_390_DBL` という新しい再配置バリアントが定数として定義されています。その説明として、「再配置可能なフィールドに配置される値が、まず2で割られるべきであることを示すs390x固有の再配置バリアント」と記載されています。

### `src/cmd/link/internal/ld/symtab.go`
- `putelfsyment` 関数内で、`Thearch.Thechar` が `'z'` の場合も他の64ビットアーキテクチャと同様にELFシンボルエントリが処理されるように変更されています。

## コアとなるコードの解説

このコミットの核心は、Goリンカがs390xアーキテクチャのバイナリを正しく生成するために必要な、低レベルなELF再配置処理とアーキテクチャ固有の調整を実装した点にあります。

最も重要なのは、`RV_390_DBL` 再配置バリアントの導入です。s390xの命令セットでは、PC相対分岐命令などが2バイト単位のアドレスオフセットを期待することがあります。例えば、命令が `B +offset` の形式で、`offset` が命令の次の命令からの相対オフセットを表す場合、この `offset` は通常、命令長（2バイトまたは4バイト）の倍数である必要があります。Goリンカが計算する絶対アドレス間の差分はバイト単位ですが、これをs390xの命令が解釈できる形式に変換するためには、2で割る（1ビット右シフトする）必要があります。`RV_390_DBL` はこの変換をリンカに指示する役割を担います。

`data.go` の `Addpcrelplus` や `relocsym` 関数での `RV_390_DBL` の適用は、この変換がPC相対再配置や関数呼び出しの再配置に特に必要であることを示しています。

また、`elf.go` で大量に追加された `R_390_` プレフィックスを持つ再配置タイプは、s390xがサポートする多様なアドレス指定モード（PC相対、GOT相対、PLTエントリ、TLSなど）と、それらに対応するELFの標準的な再配置メカニズムをGoリンカが理解し、適用できるようにするためのものです。これらの再配置タイプは、Goプログラムがs390x上で動的リンク、共有ライブラリの使用、スレッドローカルストレージへのアクセスなどを正しく行えるようにするために不可欠です。

`elfdynhash` 関数における `Adduint64` の使用は、s390xが64ビットアーキテクチャであり、そのELFファイル内の動的ハッシュテーブルが64ビットエントリを使用することを反映しています。これは、リンカが生成するELFファイルの構造が、ターゲットアーキテクチャのビット幅に厳密に準拠する必要があることを示しています。

全体として、このコミットはGo言語のクロスコンパイルと実行環境の多様性を広げる上で、s390xという特定のメインフレームアーキテクチャへの対応を可能にするための、基盤となるリンカレベルの変更を詳細に実装したものです。

## 変更の背景

Goコンパイラは、パフォーマンスの向上と最適化の機会を増やすために、従来のAST (Abstract Syntax Tree) ベースのコンパイルからSSA (Static Single Assignment) 形式の中間表現を利用するコンパイルへと段階的に移行していました。このコミットは、その移行プロセスにおいて、Go言語の重要な機能である`go`ステートメント（ゴルーチンの起動）と`defer`ステートメント（関数の終了時に実行される処理の登録）をSSAバックエンドで適切に処理できるようにするためのものです。

以前のコンパイラでは、これらのステートメントはASTレベルで直接処理されていましたが、SSAに移行することで、より低レベルでの最適化（レジスタ割り当ての改善、不要なメモリ操作の削減など）が可能になります。このコミットは、`go`と`defer`のセマンティクスをSSA形式で表現し、最終的にAMD64アセンブリコードに変換するための初期ステップを確立します。特に、`defer`は実行順序（LIFO）やエラーハンドリングとの連携が複雑であるため、SSAでの正確な表現はコンパイラ設計上の重要な課題でした。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) 形式

SSA (Static Single Assignment) は、コンパイラ最適化において広く用いられる中間表現 (IR) の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が容易になり、デッドコード削除、共通部分式除去、レジスタ割り当てなどの様々な最適化を効率的に適用できるようになります。Goコンパイラは、Go 1.7以降、主要な最適化パスでSSA形式を採用し、生成されるコードの品質と実行速度を大幅に向上させました。

### `go`ステートメント

`go`ステートメントは、Go言語において新しいゴルーチン（軽量スレッド）を起動するために使用されます。`go`の後に続く関数呼び出しは、現在のゴルーチンとは独立して並行して実行されます。ランタイムは、新しいゴルーチンをスケジューリングし、その実行を管理します。このプロセスには、通常、`runtime.newproc`という内部関数が関与します。

### `defer`ステートメント

`defer`ステートメントは、そのステートメントを含む関数がリターンする直前に、指定された関数呼び出しを遅延実行させるために使用されます。`defer`された関数は、`defer`ステートメントが実行された時点の引数で評価され、LIFO (Last-In, First-Out) の順序で実行されます。これは、リソースの解放（ファイルのクローズ、ロックの解除など）やエラーハンドリングにおいて非常に有用です。`defer`の実行は、通常、`runtime.deferproc`という内部関数によって管理されます。

### `cmd/compile/internal/gc`

`cmd/compile/internal/gc`は、Goコンパイラの主要な部分であり、Goソースコードを中間表現に変換し、最終的に機械語コードを生成する役割を担っています。このディレクトリ内の`ssa.go`ファイルは、ASTからSSA形式への変換、およびSSA形式の最適化とコード生成のロジックを含んでいます。

### `obj.Prog`

`obj.Prog`は、Goコンパイラのバックエンドで使用されるアセンブリ命令の抽象化です。コンパイラは、SSA形式から`obj.Prog`のリストを生成し、それを最終的に特定アーキテクチャ（例: AMD64）の機械語コードに変換します。

## 技術的詳細

このコミットの主要な技術的変更点は、`go`および`defer`ステートメントをSSA形式で表現し、AMD64アーキテクチャ向けのアセンブリコードに変換するための新しいロジックとSSAオペレーションを導入したことです。

1.  **`ssa.go`における`OPROC`と`ODEFER`の処理**:
    *   `src/cmd/compile/internal/gc/ssa.go`の`stmt`関数内に、`OPROC` (goステートメント) と`ODEFER` (deferステートメント) を処理する新しい`case`が追加されました。
    *   これらのステートメントは、まず引数のサイズ (`fn.Type.Argwid`) とクロージャ (`fn`) をスタックに書き込みます。これは、`runtime.newproc`や`runtime.deferproc`がこれらの情報を使用して新しいゴルーチンや遅延呼び出しをセットアップするためです。
    *   `ssa.OpGoCall`または`ssa.OpDeferCall`という新しいSSAオペレーションが生成され、現在のメモリ状態 (`s.mem()`) を引数として受け取ります。これらのオペレーションは、それぞれ`runtime.newproc`または`runtime.deferproc`への呼び出しを表します。
    *   `AuxInt`フィールドには、スタック上で使用される合計スペース (`fn.Type.Argwid + 2*int64(Widthptr)`) が格納されます。
    *   `endBlock()`と`startBlock()`を使用して、呼び出しの前後でSSAブロックが適切に管理されます。特に、`defer`呼び出しの場合、`b.AddEdgeTo(s.exit)`により、`deferproc`が失敗した場合（例: メモリ不足）にプログラムが終了するパスが考慮されています。

2.  **`genState`構造体の導入**:
    *   `genssa`関数内で使用される状態を管理するために、`genState`という新しい構造体が導入されました。これには、分岐命令を記憶するための`branches`、各ブロックの開始位置を記憶するための`bstart`、そして`defer`関連の分岐を記憶するための`deferBranches`と`deferTarget`が含まれます。
    *   これにより、`genssa`関数内のローカル変数だった`branches`と`bstart`が`genState`のフィールドとしてカプセル化され、関連するヘルパー関数（`genValue`, `genBlock`, `genFPJump`）が`genState`のレシーバを持つメソッドとして再定義されました。

3.  **`ssa.OpAMD64CALLdefer`と`ssa.OpAMD64CALLgo`の生成と処理**:
    *   `src/cmd/compile/internal/ssa/gen/AMD64.rules`、`src/cmd/compile/internal/ssa/gen/AMD64Ops.go`、`src/cmd/compile/internal/ssa/gen/genericOps.go`、`src/cmd/compile/internal/ssa/opGen.go`において、`DeferCall`と`GoCall`という新しい汎用SSAオペレーション、およびそれに対応するAMD64固有のオペレーション`OpAMD64CALLdefer`と`OpAMD64CALLgo`が定義されました。
    *   `src/cmd/compile/internal/gc/ssa.go`の`genValue`関数では、これらのAMD64固有のオペレーションがアセンブリ命令に変換されます。
        *   `ssa.OpAMD64CALLdefer`は`runtime.deferproc`への`ACALL`命令を生成します。
        *   `deferproc`の戻り値（`AX`レジスタに格納される）が0の場合は通常の実行を継続し、1の場合は`deferreturn`呼び出しサイトへジャンプする必要があるため、`ATESTL AX, AX`と`AJNE`命令が生成され、条件分岐が実装されます。この分岐先は`s.deferBranches`に記録されます。
        *   `ssa.OpAMD64CALLgo`は`runtime.newproc`への`ACALL`命令を生成します。
    *   `Maxarg`は、関数呼び出しに必要な最大引数サイズを追跡するために更新されます。

4.  **`deferreturn`呼び出しサイトの処理**:
    *   `src/cmd/compile/internal/gc/ssa.go`の`genBlock`関数内の`ssa.BlockRet` (関数リターンブロック) の処理が変更されました。
    *   もし`Hasdefer`フラグがセットされている場合（つまり、関数内に`defer`ステートメントが存在する場合）、`runtime.deferreturn`への呼び出しが挿入されます。
    *   `s.deferTarget = Pc`により、`deferreturn`呼び出しのターゲットアドレスが記録されます。
    *   `Thearch.Ginsnop()`は、スタックトレースの行番号が不適切な命令を指さないように、ハードウェアNOP命令を挿入します。これは、`defer`された呼び出しが`deferreturn`を呼び出す際に、正確なスタックトレース情報を提供するために重要です。

5.  **リライトルールの追加**:
    *   `src/cmd/compile/internal/ssa/rewriteAMD64.go`には、`OpDeferCall`と`OpGoCall`をそれぞれ`OpAMD64CALLdefer`と`OpAMD64CALLgo`に変換するためのリライトルールが追加されました。これにより、汎用SSAオペレーションがAMD64固有のオペレーションに変換され、最終的なコード生成に備えます。

		call := n.Left

		// Write argsize and closure (args to Newproc/Deferproc)

		s.vars[&memvar] = s.newValue3I(ssa.OpStore, ssa.TypeMem, 4, s.sp, argsize, s.mem())
		closure := s.expr(fn)
		addr := s.entryNewValue1I(ssa.OpOffPtr, Ptrto(Types[TUINTPTR]), int64(Widthptr), s.sp)
		s.vars[&memvar] = s.newValue3I(ssa.OpStore, ssa.TypeMem, int64(Widthptr), addr, closure, s.mem())

		// Run all argument assignments. The arg slots have already
		// been offset by 2*widthptr.
		s.stmtList(call.List)

		// Call deferproc or newproc
		bNext := s.f.NewBlock(ssa.BlockPlain)
		var op ssa.Op
		switch n.Op {
		case ODEFER:
			op = ssa.OpDeferCall
		case OPROC:
			op = ssa.OpGoCall
		}
		r := s.newValue1(op, ssa.TypeMem, s.mem())
		r.AuxInt = fn.Type.Argwid + 2*int64(Widthptr) // total stack space used
		s.vars[&memvar] = r
		b := s.endBlock()
		b.Kind = ssa.BlockCall
		b.Control = r
		b.AddEdgeTo(bNext)
		b.AddEdgeTo(s.exit)
		s.startBlock(bNext)

func (s *genState) genValue(v *ssa.Value) {
	lineno = v.Line
	switch v.Op {
	// ... (既存コード) ...
	case ssa.OpAMD64CALLdefer:
		p := Prog(obj.ACALL)
		p.To.Type = obj.TYPE_MEM
		p.To.Name = obj.NAME_EXTERN
		p.To.Sym = Linksym(Deferproc.Sym)
		if Maxarg < v.AuxInt {
			Maxarg = v.AuxInt
		}
		// defer returns in rax:
		// 0 if we should continue executing
		// 1 if we should jump to deferreturn call
		p = Prog(x86.ATESTL)
		p.From.Type = obj.TYPE_REG
		p.From.Reg = x86.REG_AX
		p.To.Type = obj.TYPE_REG
		p.To.Reg = x86.REG_AX

		p.To.Name = obj.NAME_EXTERN

## コアとなるコードの解説

### `ssa.go` の `stmt` 関数内 (`OPROC`, `ODEFER` の処理)

この部分は、Goソースコードの`go`または`defer`ステートメントがSSA形式に変換される際の初期段階を定義しています。
1.  **引数とクロージャの準備**: `go`や`defer`に渡される関数呼び出しの引数サイズ (`fn.Type.Argwid`) と、呼び出される関数自体（クロージャ）がスタックに書き込まれます。これは、ランタイムの`newproc`や`deferproc`関数が、新しいゴルーチンや遅延呼び出しを正しくセットアップするために必要な情報です。`s.sp`はスタックポインタを表し、`s.mem()`は現在のメモリ状態を表すSSA値です。
2.  **SSAオペレーションの生成**: `OPROC`の場合は`ssa.OpGoCall`、`ODEFER`の場合は`ssa.OpDeferCall`という新しいSSAオペレーションが生成されます。これらのオペレーションは、それぞれ`runtime.newproc`または`runtime.deferproc`への抽象的な呼び出しを表します。
3.  **スタック使用量の記録**: `r.AuxInt`には、この呼び出しによってスタック上で使用される合計バイト数が記録されます。これは、スタックフレームの管理やガベージコレクションの際に重要な情報です。
4.  **SSAブロックの管理**: `b.Kind = ssa.BlockCall`は、このブロックが関数呼び出しを含むことを示します。`b.AddEdgeTo(bNext)`は通常の実行パスを、`b.AddEdgeTo(s.exit)`は`deferproc`や`newproc`が失敗した場合（例: メモリ割り当て失敗）の異常終了パスを示します。

### `genState` 構造体と `genssa` 関数

`genState`構造体は、SSAからアセンブリコードを生成する`genssa`関数が、コード生成中に必要とする状態（例えば、未解決の分岐先や`defer`関連の特殊なターゲット）を保持するために導入されました。これにより、`genssa`関数とそのヘルパー関数間で状態を安全かつ効率的に共有できるようになります。特に`deferBranches`と`deferTarget`は、`defer`の複雑な実行フロー（特に`deferreturn`へのジャンプ）を正確に処理するために不可欠です。

### `genValue` 関数内 (`ssa.OpAMD64CALLdefer`, `ssa.OpAMD64CALLgo` の処理)

この部分は、SSAオペレーションを実際のAMD64アセンブリ命令に変換する役割を担います。
1.  **`runtime`関数への呼び出し**: `ssa.OpAMD64CALLdefer`は`runtime.deferproc`へ、`ssa.OpAMD64CALLgo`は`runtime.newproc`への`ACALL`命令（アセンブリレベルの関数呼び出し）を生成します。`Linksym`は、Goランタイムのシンボルへのリンクを解決します。
2.  **`deferproc`の戻り値の処理**: `deferproc`は、呼び出しが成功したかどうか、および後続の処理を継続すべきか（0）、それとも`deferreturn`にジャンプすべきか（1）を示す値を`AX`レジスタに返します。このコミットでは、`ATESTL AX, AX`と`AJNE`（Jump if Not Equal）命令を生成することで、この戻り値に基づいて条件分岐を実装しています。`s.deferBranches`にこの分岐命令が記録され、後で`deferTarget`に解決されます。

### `genBlock` 関数内 (`ssa.BlockRet` の処理)

関数がリターンする際の処理を定義します。
1.  **`deferreturn`の挿入**: `Hasdefer`フラグがセットされている場合（関数内に`defer`がある場合）、`runtime.deferreturn`への`ACALL`命令が挿入されます。これは、`defer`された関数がすべて実行されることを保証するためのランタイムフックです。
2.  **スタックトレースの正確性**: `s.deferTarget = Pc`と`Thearch.Ginsnop()`は、デバッグ時のスタックトレースが正確な行番号を指すようにするための工夫です。`defer`された関数が実行される際に、スタックトレースが`deferreturn`呼び出しの直前の命令を指すように、意図的にハードウェアNOP命令を挿入しています。

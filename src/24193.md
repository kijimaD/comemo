# [インデックス 24193] ファイルの概要

このコミットは、Goコマンドのテストスイートに新しいテストケースを追加するものです。具体的には、`src/cmd/go/go_test.go` ファイルに `TestGoInstallShadowedGOPATH` というテスト関数が追加されています。このテストは、`GOPATH` がシャドウされている状況下での `go install` コマンドの挙動を検証し、以前報告された問題 (issue 3652) が修正された状態を維持していることを保証します。

## コミット

このコミットは、`cmd/go` ツールにおける `go install` コマンドが、シャドウされた `GOPATH` 環境下でどのように動作するかを検証するテストを追加します。これは、`golang.org/issue/3652` で報告された問題に対する修正が、将来にわたって維持されることを目的としています。

## 変更の背景

このコミットの背景には、`golang.org/issue/3652` で報告された問題があります。この問題は、`go get foo.io` のようなコマンドが、`foo.io` がサブディレクトリではない場合に一貫して動作しないというものでした。特に、複数のエントリを持つ `GOPATH` 環境において、ある `GOPATH` エントリが別のエントリを「シャドウ」している場合に、`go get` や `go install` が予期せぬ挙動を示すことがありました。

このコミットは、既に修正されたこの問題が、将来の変更によって再発しないことを保証するためのテストを追加します。テストは、`go install` コマンドがシャドウされた `GOPATH` 環境下で、正しいエラーメッセージを伴って失敗することを確認することで、この修正が維持されていることを検証します。

## 前提知識の解説

### GOPATH

`GOPATH` は、Go言語のワークスペースのルートディレクトリを指定する環境変数です。Go Modules が導入される前（Go 1.11以前）は、Goプロジェクトの依存関係管理とビルドにおいて中心的な役割を担っていました。`GOPATH` は通常、`src`、`pkg`、`bin` の3つのサブディレクトリを含みます。
*   `src`: ソースコードが配置される場所です。各リポジトリは `src` の下に独自のディレクトリ構造を持ちます（例: `src/github.com/user/repo`）。
*   `pkg`: コンパイルされたパッケージオブジェクトが配置される場所です。
*   `bin`: コンパイルされた実行可能ファイルが配置される場所です。

`GOPATH` は複数のパスをコロン（Linux/macOS）またはセミコロン（Windows）で区切って指定できます。例えば、`GOPATH=/home/user/go1:/home/user/go2` のように設定できます。

### GOPATHのシャドウイング (Shadowing)

複数のパスが `GOPATH` に設定されている場合、Goツールはリストの最初のパスから順にパッケージやモジュールを探します。もし同じパッケージが複数の `GOPATH` エントリに存在する場合、リストの先頭に近いパスにあるものが優先的に使用されます。この挙動を「シャドウイング」と呼びます。つまり、`GOPATH=/path1:/path2` の場合、`path1` に存在するパッケージは `path2` に存在する同じパッケージをシャドウします。

### `go get` コマンド

`go get` コマンドは、リモートリポジトリからGoパッケージとその依存関係をダウンロードし、`GOPATH` 内の適切な `src` ディレクトリに配置するために使用されます。また、ダウンロードしたパッケージをビルドしてインストールすることもできます。

### `go install` コマンド

`go install` コマンドは、指定されたパッケージをコンパイルし、その実行可能ファイルを `GOPATH/bin` ディレクトリに、またはパッケージオブジェクトを `GOPATH/pkg` ディレクトリにインストールします。

### Goテストフレームワーク (`go_test.go` と `testgo` ヘルパー)

Go言語の標準テストフレームワークは `testing` パッケージによって提供されます。`go_test.go` のようなファイルは、`go` コマンド自体のテストコードを含んでいます。これらのテストでは、`testgo` のようなヘルパー関数や構造体がよく使われます。`testgo` は、テスト環境のセットアップ（一時ディレクトリの作成、環境変数の設定など）や、`go` コマンドの実行、その出力の検証（標準出力、標準エラー出力、終了コードなど）を簡素化するために設計されたユーティリティです。

## 技術的詳細

`golang.org/issue/3652` は、`go get` コマンドが、`GOPATH` のシャドウイングによって予期せぬ挙動を示す問題に関連していました。特に、`go get foo.io` のようにルートパッケージを取得しようとした際に、`GOPATH` の設定によっては、`go` コマンドが正しいインストール先を特定できない、あるいは誤った場所を優先してしまうことが問題でした。

このコミットで追加された `TestGoInstallShadowedGOPATH` テストは、この問題の特定の側面、すなわち `go install` がシャドウされた `GOPATH` 環境でどのように振る舞うべきかを検証します。

テストのシナリオは以下の通りです。
1.  `GOPATH` 環境変数を `gopath1:gopath2` のように設定し、`gopath1` が `gopath2` をシャドウするようにします。
2.  `gopath1/src/test` ディレクトリを作成しますが、このディレクトリは空です。
3.  `gopath2/src/test` ディレクトリを作成し、その中に `main.go` ファイルを配置します。つまり、実際のソースコードはシャドウされている `GOPATH` エントリに存在します。
4.  カレントディレクトリを `gopath2/src/test` に変更します。
5.  この状態で `go install` コマンドを実行します。

この状況下で、`go` コマンドは `gopath2/src/test` にあるソースコードをビルドしようとしますが、インストール先を決定する際には `GOPATH` のシャドウイングルールに従います。つまり、`gopath1/src/test` が優先されます。しかし、`gopath1/src/test` は空であるため、`go` コマンドは有効なインストール先を見つけることができません。

したがって、`go install` は失敗し、その標準エラー出力には「`no install location for ...gopath2.src.test: hidden by ...gopath1.src.test`」というメッセージが含まれることが期待されます。このエラーメッセージは、`gopath2/src/test` が `gopath1/src/test` によってシャドウされているためにインストールできないことを明確に示しており、`go` コマンドがシャドウイングの状況を正しく認識していることを意味します。

このテストは、`go` コマンドが `GOPATH` のシャドウイングを適切に処理し、曖昧な状況でのインストールを防止することで、ユーザーに明確なフィードバックを提供することを保証します。

## コアとなるコードの解説

追加された `TestGoInstallShadowedGOPATH` 関数は、`go_test.go` ファイルの末尾に追加されています。

1.  **コメント**:
    *   `// golang.org/issue/3652.` と `// go get foo.io (not foo.io/subdir) was not working consistently.` は、このテストが解決済みの issue 3652 に関連していることを示しています。

2.  **`testenv.MustHaveExternalNetwork(t)`**:
    *   この行は、テストを実行するために外部ネットワーク接続が必要であることを示します。これは、`go get` のようなコマンドがリモートリポジトリにアクセスする可能性があるためですが、この特定のテストでは `go install` のローカルな挙動を検証しているため、直接的なネットワークアクセスは不要かもしれません。しかし、`go` コマンドのテストスイート全体で共通の要件として含まれている可能性があります。

3.  **`tg := testgo(t)` と `defer tg.cleanup()`**:
    *   `testgo(t)` は、テスト用のヘルパー構造体 `testgo` のインスタンスを作成します。これにより、一時ディレクトリの管理や `go` コマンドの実行が容易になります。
    *   `defer tg.cleanup()` は、テスト関数の終了時に一時ディレクトリなどのリソースをクリーンアップすることを保証します。

4.  **`tg.makeTempdir()`**:
    *   テスト実行のための一時的な作業ディレクトリを作成します。

5.  **`tg.setenv("GOPATH", tg.path("gopath1")+string(filepath.ListSeparator)+tg.path("gopath2"))`**:
    *   この行がテストの核心部分です。`GOPATH` 環境変数を設定し、`gopath1` と `gopath2` という2つのパスをコロン（またはOSに応じた区切り文字）で区切って指定します。これにより、`gopath1` が `gopath2` をシャドウする `GOPATH` 環境が構築されます。

6.  **`tg.tempDir("gopath1/src/test")`**:
    *   最初の `GOPATH` エントリ (`gopath1`) の下に `src/test` ディレクトリを作成します。このディレクトリは空のままです。

7.  **`tg.tempDir("gopath2/src/test")`**:
    *   2番目の `GOPATH` エントリ (`gopath2`) の下に `src/test` ディレクトリを作成します。

8.  **`tg.tempFile("gopath2/src/test/main.go", "package main\\nfunc main(){}\\n")`**:
    *   `gopath2/src/test` ディレクトリ内に、シンプルな `main.go` ファイルを作成します。このファイルは、`go install` がビルドしようとする実際のソースコードです。

9.  **`tg.cd(tg.path("gopath2/src/test"))`**:
    *   カレントディレクトリを、ソースコードが存在する `gopath2/src/test` に変更します。

10. **`tg.runFail("install")`**:
    *   `go install` コマンドを実行し、このコマンドが失敗することを期待します。これは、シャドウイングのためにインストール先が特定できないという、期待されるエラー挙動を検証するためです。

11. **`tg.grepStderr("no install location for.*gopath2.src.test: hidden by .*gopath1.src.test", "missing error")`**:
    *   `go install` コマンドの標準エラー出力に、特定の正規表現パターンが含まれていることを検証します。
    *   正規表現 `no install location for.*gopath2.src.test: hidden by .*gopath1.src.test` は、「`gopath2/src/test` のインストール場所が見つからない、なぜなら `gopath1/src/test` によって隠されているから」という趣旨のエラーメッセージを捕捉します。
    *   この検証により、`go` コマンドが `GOPATH` のシャドウイングを正しく認識し、適切なエラーメッセージをユーザーに返していることが確認されます。

このテストは、`GOPATH` のシャドウイングという複雑なシナリオにおいて、`go install` コマンドが堅牢かつ予測可能な挙動を示すことを保証するための重要な安全網となります。

# [インデックス 20431] ファイルの概要

このコミットは、Go言語の`net/http`パッケージにおいて、`Transport`構造体に`DialTLS`という新しいフックを追加するものです。これにより、HTTPSリクエストにおけるTLS接続の確立方法を、ユーザーがより細かく制御できるようになります。特に、既存の`Dial`フックや`TLSClientConfig`だけでは対応が難しかった、高度なTLS接続のカスタマイズ（例：カスタム証明書検証、特定のTLSライブラリの使用など）を可能にすることを目的としています。

## 元コミット内容

このコミットは、`net/http`パッケージの`Transport`に`DialTLS`フックを追加します。これは、`https://golang.org/cl/128930043/`での議論、golang-nutsメーリングリストのスレッド、およびaglとの議論に基づいて行われました。この変更はIssue #8522を修正します。

## 変更の背景

この変更の背景には、Goの`net/http`クライアントがHTTPS接続を確立する際の柔軟性の向上が挙げられます。従来の`Transport`構造体には、TCP接続を確立するための`Dial`フックと、TLS設定をカスタマイズするための`TLSClientConfig`フィールドが存在しました。しかし、これらの機能だけでは、以下のような特定のユースケースに対応することが困難でした。

1.  **カスタムTLSハンドシェイク**: `tls.Client`を直接使用するのではなく、独自のTLSハンドシェイクプロセスを実装したい場合。例えば、特定のハードウェアセキュリティモジュール（HSM）と連携してTLSセッションを確立する場合や、非標準のTLS拡張を使用する場合などです。
2.  **TLS接続の事前確立**: 既に確立されたTLS接続（例えば、別のライブラリやシステムによって確立されたもの）を`net/http`クライアントで再利用したい場合。
3.  **より詳細な証明書検証**: `TLSClientConfig`の`InsecureSkipVerify`や`VerifyPeerCertificate`だけでは実現できない、より複雑な証明書検証ロジックを実装したい場合。例えば、証明書失効リスト（CRL）やOCSP（Online Certificate Status Protocol）による検証を独自に行う場合などです。

特に、コミットメッセージで言及されている`https://golang.org/cl/128930043/`の議論は、「`net/http`: ホスト名だけでなく証明書の検証を許可する」というタイトルであり、TLS証明書の検証における柔軟性の必要性が背景にあることを示唆しています。`DialTLS`フックは、ユーザーがTLS接続全体を制御できるようにすることで、これらの高度な要件を満たすための強力なメカニズムを提供します。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語のネットワークおよびHTTPに関する基本的な概念を理解しておく必要があります。

*   **`net/http`パッケージ**: Go言語でHTTPクライアントおよびサーバーを構築するための標準ライブラリです。
*   **`http.RoundTripper`インターフェース**: HTTPリクエストを送信し、HTTPレスポンスを受け取るためのインターフェースです。`http.Client`は内部的に`RoundTripper`を使用してリクエストを処理します。
*   **`http.Transport`構造体**: `http.RoundTripper`インターフェースの具体的な実装の一つで、HTTPおよびHTTPSリクエストの実際のネットワーク通信を担当します。接続の再利用（コネクションプーリング）、プロキシ設定、TLS設定などを管理します。
*   **`net.Conn`インターフェース**: ネットワーク接続の汎用インターフェースです。TCP接続やTLS接続など、様々な種類のネットワーク接続を表します。
*   **`net.Dial`関数**: 指定されたネットワーク（例: "tcp"）とアドレス（例: "example.com:80"）に対してネットワーク接続を確立するための関数です。
*   **`crypto/tls`パッケージ**: TLS（Transport Layer Security）プロトコルを実装するためのGo言語の標準ライブラリです。
*   **`tls.Config`構造体**: TLS接続の振る舞いを設定するための構造体です。証明書、キー、ルートCA、サーバー名の検証設定などが含まれます。
*   **`tls.Client`関数**: 既存の`net.Conn`（通常はTCP接続）をラップして、TLSハンドシェイクを実行し、TLS接続（`*tls.Conn`）を確立します。
*   **TLSハンドシェイク**: クライアントとサーバー間で安全な通信チャネルを確立するために行われる一連のプロトコルメッセージ交換です。このプロセス中に、暗号スイートのネゴシエーション、鍵交換、証明書の交換と検証が行われます。

`Transport.Dial`は、TCP接続を確立するためのフックであり、`Transport.TLSClientConfig`は、そのTCP接続上でTLSハンドシェイクを行う際のTLS設定を提供します。しかし、`DialTLS`は、TCP接続の確立からTLSハンドシェイクまでを完全にユーザーに委ねる新しいフックです。

## 技術的詳細

このコミットによって導入された`Transport.DialTLS`フックは、`net/http.Transport`がHTTPSリクエストを処理する際の接続確立ロジックに大きな変更をもたらします。

### `DialTLS`の役割と優先順位

*   **`DialTLS`の追加**: `Transport`構造体に`DialTLS func(network, addr string) (net.Conn, error)`という新しいフィールドが追加されました。この関数は、非プロキシのHTTPSリクエストに対してTLS接続を確立するために使用されます。
*   **優先順位**:
    *   `DialTLS`が`nil`でない場合、かつHTTPSリクエストであり、プロキシを使用しない場合、`DialTLS`が呼び出されます。
    *   この場合、既存の`Dial`フックはHTTPSリクエストには使用されず、`TLSClientConfig`および`TLSHandshakeTimeout`は無視されます。
    *   `DialTLS`によって返される`net.Conn`は、既にTLSハンドシェイクが完了しているものと見なされます。つまり、`DialTLS`の実装内でTLSハンドシェイクまで完了させる責任があります。
    *   `DialTLS`が`nil`の場合、またはプロキシを使用するHTTPSリクエストの場合、従来の`Dial`フックと`TLSClientConfig`を使用したTLS接続確立ロジックがフォールバックとして使用されます。

### 接続確立フローの変更

コミット前の`Transport.dialConn`メソッドでは、まず`t.dial("tcp", cm.addr())`を呼び出してTCP接続を確立し、その後、HTTPSスキームの場合に`tls.Client`を使用してそのTCP接続上でTLSハンドシェイクを行っていました。

コミット後の`Transport.dialConn`メソッドでは、以下のロジックが追加されました。

1.  `tlsDial := t.DialTLS != nil && cm.targetScheme == "https" && cm.proxyURL == nil`という条件で、`DialTLS`を使用すべきかどうかが判断されます。
2.  `tlsDial`が`true`の場合、`pconn.conn, err = t.DialTLS("tcp", cm.addr())`が呼び出され、`DialTLS`フックによってTLS接続が確立されます。
    *   もし返された`net.Conn`が`*tls.Conn`型であれば、その`ConnectionState()`が取得され、`pconn.tlsState`に保存されます。これは、後続の処理でTLS接続の状態を参照できるようにするためです。
3.  `tlsDial`が`false`の場合（つまり、`DialTLS`が設定されていないか、HTTPリクエスト、またはプロキシ経由のHTTPSリクエストの場合）、従来の`t.dial("tcp", cm.addr())`によるTCP接続確立ロジックが実行されます。
4.  プロキシ設定の処理は、接続確立後に引き続き行われます。
5.  最後に、`if cm.targetScheme == "https" && !tlsDial`という条件が追加され、`DialTLS`が使用されなかったHTTPS接続の場合にのみ、従来の`tls.Client`によるTLSハンドシェイクが実行されるようになりました。これにより、`DialTLS`が使用された場合は二重にTLSハンドシェイクが行われることを防ぎます。

この変更により、ユーザーは`DialTLS`フックを実装することで、TCP接続の確立からTLSハンドシェイク、さらには証明書検証まで、HTTPS接続のライフサイクル全体を完全に制御できるようになります。これは、特にカスタムのネットワークスタックやセキュリティ要件を持つアプリケーションにとって非常に有用です。

## コアとなるコードの解説

### `src/pkg/net/http/transport.go`の変更点

`Transport`構造体への`DialTLS`フィールドの追加は、そのコメントが示すように、このフックが`Dial`や`TLSClientConfig`とは異なる目的を持つことを明確にしています。`DialTLS`が設定されている場合、それはHTTPSリクエストに対してTLSハンドシェイクが完了した接続を返す責任を持ち、Goの標準的なTLS処理をバイパスします。

`dialConn`メソッド内の変更は、この新しいフックの導入に伴う接続確立ロジックの分岐を示しています。

```go
	tlsDial := t.DialTLS != nil && cm.targetScheme == "https" && cm.proxyURL == nil
	if tlsDial {
		var err error
		pconn.conn, err = t.DialTLS("tcp", cm.addr())
		if err != nil {
			return nil, err
		}
		if tc, ok := pconn.conn.(*tls.Conn); ok {
			cs := tc.ConnectionState()
			pconn.tlsState = &cs
		}
	} else {
		conn, err := t.dial("tcp", cm.addr())
		if err != nil {
			if cm.proxyURL != nil {
				err = fmt.Errorf("http: error connecting to proxy %s: %v", cm.proxyURL, err)
			}
			return nil, err
		}
		pconn.conn = conn
	}
```
このコードブロックは、`DialTLS`フックの利用条件を定義しています。
- `tlsDial`変数は、`DialTLS`が設定されており（`t.DialTLS != nil`）、ターゲットスキームがHTTPSであり（`cm.targetScheme == "https"`）、かつプロキシを使用しない場合（`cm.proxyURL == nil`）に`true`となります。
- `tlsDial`が`true`の場合、`t.DialTLS`が呼び出され、その結果が`pconn.conn`に格納されます。ここでエラーが発生した場合は、すぐに`nil, err`を返します。
- `pconn.conn`が`*tls.Conn`型にキャスト可能であれば、その`ConnectionState()`を取得し、`pconn.tlsState`に保存します。これは、TLS接続の状態（例: 使用されたTLSバージョン、暗号スイート、ピア証明書など）を後で参照できるようにするためです。
- `tlsDial`が`false`の場合、従来の`t.dial`（TCP接続確立）ロジックが実行されます。

```go
	if cm.targetScheme == "https" && !tlsDial {
		// Initiate TLS and check remote host name against certificate.
		cfg := t.TLSClientConfig
		// ... (既存のTLSハンドシェイクロジック)
	}
```
この変更は、従来のTLSハンドシェイクロジックが実行される条件を修正しています。`!tlsDial`という条件が追加されたことで、`DialTLS`フックが使用された場合には、このブロック内の標準的なTLSハンドシェイクはスキップされます。これにより、ユーザーが提供した`DialTLS`フックがTLS接続の確立を完全に担当し、二重のハンドシェイクや競合を防ぎます。

### `src/pkg/net/http/transport_test.go`の変更点

`TestTransportDialTLS`は、`DialTLS`フックの動作を検証するための重要なテストです。

```go
func TestTransportDialTLS(t *testing.T) {
	var mu sync.Mutex // guards following
	var gotReq, didDial bool

	ts := httptest.NewTLSServer(HandlerFunc(func(w ResponseWriter, r *Request) {
		mu.Lock()
		gotReq = true
		mu.Unlock()
	}))
	defer ts.Close()
	tr := &Transport{
		DialTLS: func(netw, addr string) (net.Conn, error) {
			mu.Lock()
			didDial = true
			mu.Unlock()
			c, err := tls.Dial(netw, addr, &tls.Config{
				InsecureSkipVerify: true,
			})
			if err != nil {
				return nil, err
			}
			return c, c.Handshake()
		},
	}
	defer tr.CloseIdleConnections()
	client := &Client{Transport: tr}
	res, err := client.Get(ts.URL)
	if err != nil {
		t.Fatal(err)
	}
	res.Body.Close()
	mu.Lock()
	if !gotReq {
		t.Error("didn't get request")
	}
	if !didDial {
		t.Error("didn't use dial hook")
	}
}
```
このテストでは、カスタムの`DialTLS`関数が定義されています。この関数は、`tls.Dial`を使用してTLS接続を確立し、`InsecureSkipVerify: true`を設定しています。これはテストの簡略化のためであり、実際のアプリケーションでは適切な証明書検証を行う必要があります。`didDial`フラグは、このカスタム`DialTLS`関数が実際に呼び出されたことを確認するために使用されます。テストの最後で、`gotReq`（サーバーがリクエストを受け取ったか）と`didDial`（カスタム`DialTLS`が使用されたか）の両方が`true`であることをアサートすることで、`DialTLS`フックが期待通りに機能していることを検証しています。

*   **`http.Transport`構造体**: `http.RoundTripper`インターフェースの具体的な実装の一つで、HTTPおよびHTTPSリクエストの実際のネットワーク通信を担当します。接続の再利用（コネクションプーリング）、プロキシ設定、TLS設定などを管理します。
*   **`net.Conn`インターフェース**: ネットワーク接続の汎用インターフェースです。TCP接続やTLS接続など、様々な種類のネットワーク接続を表します。
*   **`net.Dial`関数**: 指定されたネットワーク（例: "tcp"）とアドレス（例: "example.com:80"）に対してネットワーク接続を確立するための関数です。
*   **`crypto/tls`パッケージ**: TLS（Transport Layer Security）プロトコルを実装するためのGo言語の標準ライブラリです。
*   **`tls.Config`構造体**: TLS接続の振る舞いを設定するための構造体です。証明書、キー、ルートCA、サーバー名の検証設定などが含まれます。
*   **`tls.Client`関数**: 既存の`net.Conn`（通常はTCP接続）をラップして、TLSハンドシェイクを実行し、TLS接続（`*tls.Conn`）を確立します。
*   **TLSハンドシェイク**: クライアントとサーバー間で安全な通信チャネルを確立するために行われる一連のプロトコルメッセージ交換です。このプロセス中に、暗号スイートのネゴシエーション、鍵交換、証明書の交換と検証が行われます。

`Transport.Dial`は、TCP接続を確立するためのフックであり、`Transport.TLSClientConfig`は、そのTCP接続上でTLSハンドシェイクを行う際のTLS設定を提供します。しかし、`DialTLS`は、TCP接続の確立からTLSハンドシェイクまでを完全にユーザーに委ねる新しいフックです。

## 技術的詳細

このコミットによって導入された`Transport.DialTLS`フックは、`net/http.Transport`がHTTPSリクエストを処理する際の接続確立ロジックに大きな変更をもたらします。

### `DialTLS`の役割と優先順位

*   **`DialTLS`の追加**: `Transport`構造体に`DialTLS func(network, addr string) (net.Conn, error)`という新しいフィールドが追加されました。この関数は、非プロキシのHTTPSリクエストに対してTLS接続を確立するために使用されます。
*   **優先順位**:
    *   `DialTLS`が`nil`でない場合、かつHTTPSリクエストであり、プロキシを使用しない場合、`DialTLS`が呼び出されます。
    *   この場合、既存の`Dial`フックはHTTPSリクエストには使用されず、`TLSClientConfig`および`TLSHandshakeTimeout`は無視されます。
    *   `DialTLS`によって返される`net.Conn`は、既にTLSハンドシェイクが完了しているものと見なされます。つまり、`DialTLS`の実装内でTLSハンドシェイクまで完了させる責任があります。
    *   `DialTLS`が`nil`の場合、またはプロキシを使用するHTTPSリクエストの場合、従来の`Dial`フックと`TLSClientConfig`を使用したTLS接続確立ロジックがフォールバックとして使用されます。

### 接続確立フローの変更

コミット前の`Transport.dialConn`メソッドでは、まず`t.dial("tcp", cm.addr())`を呼び出してTCP接続を確立し、その後、HTTPSスキームの場合に`tls.Client`を使用してそのTCP接続上でTLSハンドシェイクを行っていました。

コミット後の`Transport.dialConn`メソッドでは、以下のロジックが追加されました。

1.  `tlsDial := t.DialTLS != nil && cm.targetScheme == "https" && cm.proxyURL == nil`という条件で、`DialTLS`を使用すべきかどうかが判断されます。
2.  `tlsDial`が`true`の場合、`pconn.conn, err = t.DialTLS("tcp", cm.addr())`が呼び出され、`DialTLS`フックによってTLS接続が確立されます。
    *   もし返された`net.Conn`が`*tls.Conn`型であれば、その`ConnectionState()`が取得され、`pconn.tlsState`に保存されます。これは、後続の処理でTLS接続の状態を参照できるようにするためです。
3.  `tlsDial`が`false`の場合（つまり、`DialTLS`が設定されていないか、HTTPリクエスト、またはプロキシ経由のHTTPSリクエストの場合）、従来の`t.dial("tcp", cm.addr())`によるTCP接続確立ロジックが実行されます。
4.  プロキシ設定の処理は、接続確立後に引き続き行われます。
5.  最後に、`if cm.targetScheme == "https" && !tlsDial`という条件が追加され、`DialTLS`が使用されなかったHTTPS接続の場合にのみ、従来の`tls.Client`によるTLSハンドシェイクが実行されるようになりました。これにより、`DialTLS`が使用された場合は二重にTLSハンドシェイクが行われることを防ぎます。

この変更により、ユーザーは`DialTLS`フックを実装することで、TCP接続の確立からTLSハンドシェイク、さらには証明書検証まで、HTTPS接続のライフサイクル全体を完全に制御できるようになります。これは、特にカスタムのネットワークスタックやセキュリティ要件を持つアプリケーションにとって非常に有用です。

## コアとなるコードの解説

### `src/pkg/net/http/transport.go`の変更点

`Transport`構造体への`DialTLS`フィールドの追加は、そのコメントが示すように、このフックが`Dial`や`TLSClientConfig`とは異なる目的を持つことを明確にしています。`DialTLS`が設定されている場合、それはHTTPSリクエストに対してTLSハンドシェイクが完了した接続を返す責任を持ち、Goの標準的なTLS処理をバイパスします。

`dialConn`メソッド内の変更は、この新しいフックの導入に伴う接続確立ロジックの分岐を示しています。

```go
	tlsDial := t.DialTLS != nil && cm.targetScheme == "https" && cm.proxyURL == nil
	if tlsDial {
		var err error
		pconn.conn, err = t.DialTLS("tcp", cm.addr())
		if err != nil {
			return nil, err
		}
		if tc, ok := pconn.conn.(*tls.Conn); ok {
			cs := tc.ConnectionState()
			pconn.tlsState = &cs
		}
	} else {
		conn, err := t.dial("tcp", cm.addr())
		if err != nil {
			if cm.proxyURL != nil {
				err = fmt.Errorf("http: error connecting to proxy %s: %v", cm.proxyURL, err)
			}
			return nil, err
		}
		pconn.conn = conn
	}
```
このコードブロックは、`DialTLS`フックの利用条件を定義しています。
- `tlsDial`変数は、`DialTLS`が設定されており（`t.DialTLS != nil`）、ターゲットスキームがHTTPSであり（`cm.targetScheme == "https"`）、かつプロキシを使用しない場合（`cm.proxyURL == nil`）に`true`となります。
- `tlsDial`が`true`の場合、`t.DialTLS`が呼び出され、その結果が`pconn.conn`に格納されます。ここでエラーが発生した場合は、すぐに`nil, err`を返します。
- `pconn.conn`が`*tls.Conn`型にキャスト可能であれば、その`ConnectionState()`を取得し、`pconn.tlsState`に保存します。これは、TLS接続の状態（例: 使用されたTLSバージョン、暗号スイート、ピア証明書など）を後で参照できるようにするためです。
- `tlsDial`が`false`の場合、従来の`t.dial`（TCP接続確立）ロジックが実行されます。

```go
	if cm.targetScheme == "https" && !tlsDial {
		// Initiate TLS and check remote host name against certificate.
		cfg := t.TLSClientConfig
		// ... (既存のTLSハンドシェイクロジック)
	}
```
この変更は、従来のTLSハンドシェイクロジックが実行される条件を修正しています。`!tlsDial`という条件が追加されたことで、`DialTLS`フックが使用された場合には、このブロック内の標準的なTLSハンドシェイクはスキップされます。これにより、ユーザーが提供した`DialTLS`フックがTLS接続の確立を完全に担当し、二重のハンドシェイクや競合を防ぎます。

### `src/pkg/net/http/transport_test.go`の変更点

`TestTransportDialTLS`は、`DialTLS`フックの動作を検証するための重要なテストです。

```go
func TestTransportDialTLS(t *testing.T) {
	var mu sync.Mutex // guards following
	var gotReq, didDial bool

	ts := httptest.NewTLSServer(HandlerFunc(func(w ResponseWriter, r *Request) {
		mu.Lock()
		gotReq = true
		mu.Unlock()
	}))
	defer ts.Close()
	tr := &Transport{
		DialTLS: func(netw, addr string) (net.Conn, error) {
			mu.Lock()
			didDial = true
			mu.Unlock()
			c, err := tls.Dial(netw, addr, &tls.Config{
				InsecureSkipVerify: true,
			})
			if err != nil {
				return nil, err
			}
			return c, c.Handshake()
		},
	}
	defer tr.CloseIdleConnections()
	client := &Client{Transport: tr}
	res, err := client.Get(ts.URL)
	if err != nil {
		t.Fatal(err)
	}
	res.Body.Close()
	mu.Lock()
	if !gotReq {
		t.Error("didn't get request")
	}
	if !didDial {
		t.Error("didn't use dial hook")
	}
}
```
このテストでは、カスタムの`DialTLS`関数が定義されています。この関数は、`tls.Dial`を使用してTLS接続を確立し、`InsecureSkipVerify: true`を設定しています。これはテストの簡略化のためであり、実際のアプリケーションでは適切な証明書検証を行う必要があります。`didDial`フラグは、このカスタム`DialTLS`関数が実際に呼び出されたことを確認するために使用されます。テストの最後で、`gotReq`（サーバーがリクエストを受け取ったか）と`didDial`（カスタム`DialTLS`が使用されたか）の両方が`true`であることをアサートすることで、`DialTLS`フックが期待通りに機能していることを検証しています。

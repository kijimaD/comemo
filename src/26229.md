# [インデックス 26229] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）が`bool(true)`のような明示的な型変換を伴うブール定数式を正しく定数として認識するように修正するものです。これにより、コンパイル時の定数評価がより正確になり、関連する型チェックロジックが簡素化されます。

## 元コミット内容

`cmd/compile: bool(true) を定数式として認識する`

このコミットは、`bool(true)`のような式をGoコンパイラが定数式として認識するように変更します。これにより、Issue #13821が修正されます。

## 変更の背景

Go言語では、定数式はコンパイル時に評価され、その結果がバイナリに埋め込まれます。これにより、実行時のオーバーヘッドが削減され、パフォーマンスが向上します。また、定数式は型チェックの段階で特別な扱いを受けることが多く、コードの健全性を保証する上で重要です。

このコミットが修正するIssue #13821は、`bool(true)`という形式の式がGoコンパイラによって定数として認識されないという問題でした。`true`自体はブール型の定数リテラルですが、それを明示的に`bool()`で型変換する式が、コンパイラの定数評価ロジックで適切に処理されていませんでした。

具体的には、以下のようなコードがコンパイルエラーになるか、意図しない挙動を示す可能性がありました。

```go
package p

const (
    A = true
    // B = bool(A) // 以前はコンパイルエラーになる可能性があった
    // C = bool(true) // 以前はコンパイルエラーになる可能性があった
)
```

コンパイラが`bool(true)`を定数として扱わない場合、それは実行時に評価される通常の式として扱われることになり、定数として期待される文脈（例えば、`const`宣言の初期化子）で使用できなくなります。このコミットは、この不整合を解消し、Go言語の仕様に沿った定数評価を保証することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Go言語のコンパイラの基本的な動作、特に「定数」と「型システム」に関する以下の概念を理解しておく必要があります。

1.  **Goコンパイラ (`cmd/compile`)**: Go言語の公式コンパイラです。ソースコードを解析し、抽象構文木（AST）を構築し、型チェック、最適化、コード生成などの段階を経て実行可能なバイナリを生成します。
2.  **定数 (Constants)**: Go言語の定数は、コンパイル時に値が決定される不変のエンティティです。数値、ブール値、文字列の定数があります。定数式は、定数オペランドと定数演算子のみで構成される式で、これもコンパイル時に評価されます。
3.  **型なし定数 (Untyped Constants) と理想型 (Ideal Types)**: Go言語には「型なし定数」という概念があります。例えば、`100`という数値リテラルは、それ自体では特定の型を持ちません。これは「型なし整数定数」と呼ばれ、`idealint`という「理想型」を持つと内部的に扱われます。同様に、`true`や`false`のようなブールリテラルは「型なしブール定数」であり、`idealbool`という理想型を持ちます。これらの型なし定数は、代入や演算の文脈で適切な型に変換されます。
4.  **型変換 (Type Conversions)**: Goでは、`T(V)`という構文で明示的な型変換を行います。`V`の値を型`T`に変換しようとします。定数式の場合、この型変換もコンパイル時に行われることが期待されます。
5.  **`gc`パッケージ**: `src/cmd/compile/internal/gc`は、Goコンパイラの主要な部分を構成するパッケージです。型チェック、定数評価、中間表現の操作など、コンパイルの多くの段階を処理します。
    *   **`evconst`関数**: `gc`パッケージ内の関数で、与えられたノード（ASTの要素）が定数式である場合にその値を評価します。
    *   **`OCONV_`**: ASTノードのオペレーションコードの一つで、型変換を表します。
    *   **`CTINT_`, `CTRUNE_`, `CTFLT_`, `CTSTR_`, `CTBOOL_`**: これらは`OCONV_`と組み合わせて使用され、変換元の定数の種類（整数、ルーン、浮動小数点、文字列、ブール）を示します。
    *   **`typecheck`関数**: ASTノードの型をチェックし、必要に応じて型推論や型変換を行います。
    *   **`OANDAND` (`&&`) と `OOROR` (`||`)**: 論理ANDと論理OR演算子を表すオペレーションコードです。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの定数評価ロジックと型チェックロジックの二つの側面を修正することにあります。

### `src/cmd/compile/internal/gc/const.go` の変更

`const.go`ファイルには、定数式の評価を担当する`evconst`関数が含まれています。この関数は、ASTノードのオペレーションコードと型情報に基づいて、そのノードが定数であるかどうかを判断し、定数であればその値を計算します。

変更前は、`OCONV_`（型変換）オペレーションを持つノードのうち、変換元の定数型が`CTINT_`、`CTRUNE_`、`CTFLT_`、`CTSTR_`の場合のみを定数変換として認識していました。しかし、`CTBOOL_`（ブール定数）は含まれていませんでした。

```diff
--- a/src/cmd/compile/internal/gc/const.go
+++ b/src/cmd/compile/internal/gc/const.go
@@ -664,7 +664,8 @@ func evconst(n *Node) {
 		case OCONV_ | CTINT_,
 			OCONV_ | CTRUNE_,
 			OCONV_ | CTFLT_,
-			OCONV_ | CTSTR_:
+			OCONV_ | CTSTR_,
+			OCONV_ | CTBOOL_:
 			convlit1(&nl, n.Type, true)
 
 			v = nl.Val()
```

この変更により、`OCONV_ | CTBOOL_`が追加され、`bool(true)`のようなブール定数への型変換も`evconst`関数によって定数として正しく評価されるようになりました。`convlit1`関数は、リテラル値を指定された型に変換する役割を担います。

### `src/cmd/compile/internal/gc/typecheck.go` の変更

`typecheck.go`ファイルは、Goプログラムの型チェックを担当します。このファイルには、ASTノードの型を決定し、型の一貫性を検証するロジックが含まれています。

このコミットでは、主に二つの変更が行われています。

1.  **論理演算子 (`OANDAND`, `OOROR`) の型推論の簡素化**:
    変更前は、`&&`や`||`のような論理演算子において、オペランドが`idealbool`（型なしブール定数）である場合に、結果の型を決定するための特別なロジックがありました。これは、`idealbool`が他の型付きブール値と組み合わされたときに、その型なしの性質を失い、型付きのブール型になるというGoの型推論ルールに対応するためのものでした。

    ```diff
    --- a/src/cmd/compile/internal/gc/typecheck.go
    +++ b/src/cmd/compile/internal/gc/typecheck.go
    @@ -688,17 +688,7 @@ OpSwitch:
     			\tn.Right = r
     		\t}
     \t\t} else if n.Op == OANDAND || n.Op == OOROR {
    -\t\t\tif l.Type == r.Type {
    -\t\t\t\tt = l.Type
    -\t\t\t} else if l.Type == idealbool {
    -\t\t\t\tt = r.Type
    -\t\t\t} else if r.Type == idealbool {
    -\t\t\t\tt = l.Type
    -\t\t\t}
    -\t\t} else
    -\t\t// non-comparison operators on ideal bools should make them lose their ideal-ness
    -\t\tif t == idealbool {
    ```

    この変更により、上記の複雑な型推論ロジックが削除され、代わりに`evconst(n)`が直接呼び出されています。これは、`evconst`関数が`OCONV_ | CTBOOL_`を認識するようになったことで、論理演算子の結果が定数である場合に、その定数評価の過程で適切な型が決定されるようになったため、特別な型推論ロジックが不要になったことを示唆しています。つまり、定数評価のメカニズムが型推論の一部を吸収した形です。

2.  **`OCONVNOP` の条件緩和**:
    `OCONVNOP`は、型変換が必要ないが、型チェックの目的で一時的に型変換ノードとして扱われる場合に用いられるオペレーションコードです。

    ```diff

    +++ b/src/cmd/compile/internal/gc/typecheck.go

     \t\tswitch n.Op {
     \t\tcase OCONVNOP:

    +\t\t\tif n.Left.Op == OLITERAL {
    ```

    以前は、`OCONVNOP`ノードの左オペランドがリテラルであり、かつそのノードの型が`TBOOL`（ブール型）ではない場合にのみ、`OCONV`（実際の型変換）に変換されていました。この条件`n.Type != Types[TBOOL]`が削除されたことで、ブール型へのリテラル変換（例: `bool(true)`）も`OCONV`として扱われるようになり、`const.go`で追加された`OCONV_ | CTBOOL_`のロジックによって定数として評価される道が開かれました。

これらの変更により、Goコンパイラは`bool(true)`のような明示的なブール型変換を伴う定数式を、他の定数式と同様にコンパイル時に評価できるようになり、コンパイラのロジックがより一貫性のあるものになりました。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/const.go` の変更点

`evconst`関数内の`switch`文に`OCONV_ | CTBOOL_`が追加されました。
*   `OCONV_`: 型変換操作を表すオペレーションコードです。
*   `CTBOOL_`: 変換元の値がブール定数であることを示します。

この変更により、`bool(true)`のようにブール定数を明示的に`bool`型に変換する式が、`evconst`関数によって定数として認識され、`convlit1`関数を通じてコンパイル時に評価されるようになりました。これにより、`bool(true)`は実行時ではなくコンパイル時にその値（`true`）が確定するようになります。

### `src/cmd/compile/internal/gc/typecheck.go` の変更点

1.  **論理演算子 (`OANDAND`, `OOROR`) の型推論ロジックの削除と`evconst(n)`の呼び出し**:
    以前のコードでは、`&&`や`||`のオペランドが`idealbool`（型なしブール定数）である場合に、結果の型を決定するための複雑な条件分岐がありました。これは、型なし定数が文脈に応じて型付きになるというGoのルールを処理するためのものでした。
    このコミットでは、これらの条件分岐が削除され、代わりに`evconst(n)`が呼び出されています。これは、`const.go`の変更によって`bool`型への定数変換が`evconst`で処理できるようになったため、型チェックの段階で特別な型推論ロジックを維持する必要がなくなったことを意味します。`evconst`が定数式を評価する際に、その結果の型も適切に決定するため、型チェックロジックが簡素化されました。

2.  **`OCONVNOP` の条件緩和**:
    `OCONVNOP`は、型変換が不要な場合に一時的に使用されるノードです。以前は、リテラルがブール型に変換される場合（`n.Type == Types[TBOOL]`）は、この`OCONVNOP`から`OCONV`への変換が行われませんでした。
    `n.Type != Types[TBOOL]`という条件が削除されたことで、`bool(true)`のようにリテラルをブール型に変換する式も、`OCONVNOP`から`OCONV`に変換されるようになりました。これにより、この`OCONV`ノードが`const.go`で追加された`OCONV_ | CTBOOL_`のケースにマッチし、定数として評価されるパスに乗るようになります。

これらの変更は、Goコンパイラの定数評価と型チェックのサブシステム間の連携を改善し、`bool(true)`のような特定の定数式がGo言語のセマンティクスに沿って正しく扱われるようにします。

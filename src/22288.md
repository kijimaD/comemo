## 元コミット内容

このコミットは、Go言語のリンカーである`6l`（amd64アーキテクチャ向け）における`-shared`フラグの機能を再有効化することを目的としています。以前、`liblink`の導入と、より明示的なTLS（Thread Local Storage）ハンドリングの変更が行われた際に、この`-shared`フラグの機能が損なわれていました。本変更では、`cmd/asm`（アセンブラ）と`6g`（コンパイラ）に`-shared`フラグを追加し、`liblink`が共有ライブラリと互換性のある命令シーケンスを生成するように修正し、さらに`6l`が適切なELFリロケーションを発行するように変更しています。

## 変更の背景

Go言語は、その設計思想として、通常は全ての依存関係（Goランタイムを含む）を単一の実行可能ファイルに静的にリンクします。これにより、デプロイの簡素化と移植性の向上が図られます。しかし、特定のユースケース（例えば、C言語との連携や、複数のGoプログラム間で共通のGoランタイムやライブラリを共有することによるバイナリサイズの削減）では、共有ライブラリの利用が望まれます。

Go 1.5（このコミットが作成された2015年頃に開発が進められていたバージョン）では、`go build -buildmode=shared`という形で共有ライブラリのサポートが本格的に導入されました。このコミットは、その準備段階、あるいは関連する修正の一部と考えられます。

コミットメッセージにある「`liblink`の作成とそれに続くより明示的なTLSハンドリングの導入が`6l`の（サポートされていない）`-shared`フラグを壊した」という記述が、変更の直接的な背景です。

1.  **`liblink`の導入**: Go 1.3のリンカーの抜本的な見直しの一環として、リンカーの機能を分割し、一部を`liblink`というライブラリとしてコンパイラやアセンブラに組み込む構想がありました。これにより、コンパイラやアセンブラがオブジェクトファイルを生成する際に、よりリンカーに近い中間表現を出力できるようになりました。この変更が、リンカーの内部構造に大きな影響を与え、既存の`-shared`フラグの動作に予期せぬ副作用をもたらしたと考えられます。
2.  **より明示的なTLSハンドリング**: Goランタイムは、各ゴルーチン（Goの軽量スレッド）が自身のスタックやその他のコンテキスト情報に素早くアクセスできるように、OSレベルのThread Local Storage (TLS) を内部的に利用しています。特に`amd64`アーキテクチャでは、`FS`または`GS`セグメントレジスタを介してTLSにアクセスします。`liblink`の導入に伴い、このTLSへのアクセス方法がより厳密に、あるいは異なる方法で扱われるようになった結果、共有ライブラリのコンテキストでのTLSアクセスが正しく機能しなくなった可能性があります。共有ライブラリでは、TLS変数のアドレス解決が静的リンクの場合とは異なる動的なメカニズムを必要とするため、この変更が問題を引き起こしたと考えられます。

これらの変更により、Goのツールチェーンが共有ライブラリを正しく生成・リンクするために必要な命令シーケンスやリロケーション情報が欠落したり、誤っていたりする状態になっていました。本コミットは、この問題を解決し、`amd64`における共有ライブラリのビルド機能を回復させるものです。

## 前提知識の解説

### Goのビルドモードと共有ライブラリ

Go言語のビルドシステムは、`go build`コマンドの`-buildmode`フラグを通じて様々な出力形式をサポートしています。

*   **静的リンク (デフォルト)**: Goのプログラムは、デフォルトで全ての依存関係（Goランタイム、標準ライブラリ、サードパーティライブラリなど）を単一の実行可能ファイルに含めてビルドされます。これにより、実行時に外部の共有ライブラリに依存することなく、自己完結型のバイナリが生成されます。
*   **`-buildmode=shared`**: このモードは、複数のGoパッケージを単一のGo共有ライブラリ（Unix系OSでは`.so`ファイル）としてコンパイルします。これにより、複数のGo実行可能ファイルが共通のGoランタイムやライブラリを共有できるようになり、個々のバイナリサイズを削減できます。Go 1.5で導入されました。
*   **`-buildmode=c-shared`**: GoパッケージをC言語互換の共有ライブラリ（Unix系OSでは`.so`、Windowsでは`.dll`）としてコンパイルします。これにより、C言語や他の言語で書かれたプログラムからGoのコードを呼び出すことが可能になります。`cgo`と組み合わせて使用されます。

本コミットが対象としているのは、主にGoプログラム間でGoのライブラリを共有する`-buildmode=shared`に関連する低レベルなリンカーの挙動です。

### liblink

`liblink`は、Go言語のリンカー（`cmd/link`、または特定のアーキテクチャ向けには`6l`、`8l`など）の歴史的な開発における概念です。Go 1.3のリンカーの抜本的な見直し（2013年11月）の際に提案されました。

当初の計画では、Goリンカーを2つの主要な部分に分割することが構想されていました。
1.  **`liblink`**: 擬似命令を実行可能なコードやデータブロックに変換し、リロケーションを処理する役割を担うライブラリ。これはGoコンパイラ（`6g`、`8g`など）やアセンブラ（`cmd/asm`）に組み込まれ、リンカーの最初のフェーズの出力を表すオブジェクトファイルを生成する予定でした。
2.  **残りのリンカー部分**: `liblink`が生成したオブジェクトファイルを処理し、最終的な実行可能ファイルを完成させる役割。

この構想は、リンカーの構造を改善し、効率とコード品質を向上させることを目的としていましたが、その後のGoリンカーのさらなる進化により、この特定の計画は「歴史的価値が低い」とされています。しかし、本コミットの時点では、`liblink`の概念やそれに伴うリンカー内部の変更が、`-shared`フラグの動作に影響を与えていたことが示唆されています。

### Thread Local Storage (TLS)

Thread Local Storage (TLS) は、オペレーティングシステムが提供するメカニズムの一つで、各スレッドが自分専用のデータ領域を持つことを可能にします。これにより、グローバル変数や静的変数をスレッド間で共有することなく、各スレッドが独立したコピーを持つことができます。

Goランタイムは、ゴルーチン（Goの軽量スレッド）の管理のために内部的にTLSを利用しています。例えば、現在実行中のゴルーチンの`g`構造体（ゴルーチンの状態やスタック情報を含む）へのポインタは、TLSに格納されることがあります。これにより、Goランタイムは非常に高速に現在のゴルーチンコンテキストにアクセスできます。

`amd64`アーキテクチャでは、TLSへのアクセスは通常、`FS`または`GS`セグメントレジスタをベースとしたオフセット参照によって行われます。共有ライブラリのコンテキストでは、TLS変数のアドレス解決は、静的リンクされたプログラムとは異なる動的なメカニズム（例えば、TLS初期実行モデル）を必要とします。この違いが、`liblink`導入後のTLSハンドリングの変更と`-shared`フラグの間の非互換性の原因となりました。

### ELFリロケーション

ELF (Executable and Linkable Format) は、Unix系OSで実行可能ファイル、オブジェクトファイル、共有ライブラリなどに用いられる標準的なファイル形式です。

**リロケーション**とは、プログラムがメモリにロードされる際に、シンボル（関数や変数など）のアドレスを解決し、コード内の参照を修正するプロセスです。静的リンクされたプログラムでは、リンカーがビルド時に全てのアドレスを解決します。しかし、共有ライブラリを使用する動的リンクでは、ライブラリがロードされるメモリ上のアドレスが実行時まで分からないため、特別なメカニズムが必要です。

動的リンクにおける主要なリロケーションメカニズムには、以下のものがあります。

*   **Global Offset Table (GOT)**: グローバルデータや関数のアドレスを格納するテーブルです。共有ライブラリ内の関数が外部のシンボルを参照する場合、その参照は直接アドレスではなく、GOT内のエントリを介して行われます。動的リンカーは、ライブラリがロードされた後、GOTのエントリを実際のシンボルアドレスで更新します。
*   **Procedure Linkage Table (PLT)**: 共有ライブラリ内の関数が外部の関数を呼び出す際に使用されるテーブルです。PLTは、GOTと連携して、外部関数の遅延バインディング（初めて呼び出されたときにアドレスを解決する）を可能にします。

本コミットで言及されている「適切なELFリロケーションを発行する」とは、Goのリンカーが、共有ライブラリとしてビルドされるGoコードが、実行時に正しく外部シンボルやTLS変数にアクセスできるように、GOTやPLTを適切に利用し、必要なリロケーションエントリをELFファイルに書き込むことを意味します。特にTLS関連のリロケーションタイプ（例: `R_X86_64_GOTTPOFF`や`R_TLS_IE`）が重要になります。

## 技術的詳細

このコミットの技術的詳細は、Goのコンパイラ、アセンブラ、リンカーが連携して、共有ライブラリのコンテキストでTLSアクセスとシンボル解決を正しく行うように修正された点に集約されます。

1.  **`-shared`フラグの伝播**:
    *   `src/cmd/asm/internal/flags/flags.go`と`src/cmd/asm/main.go`において、アセンブラ(`cmd/asm`)に`-shared`フラグが追加されました。これにより、アセンブラは共有ライブラリ向けにコードを生成する必要があることを認識できるようになります。
    *   `src/cmd/internal/gc/lex.go`において、コンパイラ(`6g`)にも`-shared`フラグが追加され、コンテキスト(`Ctxt.Flag_shared`)にその情報が設定されるようになりました。これは、コンパイラが生成するコードにも共有ライブラリ特有の考慮が必要であることを示します。

2.  **TLSハンドリングの修正**:
    *   `src/cmd/internal/obj/x86/asm6.go`は、`amd64`アーキテクチャのアセンブラバックエンドのコード生成ロジックを含んでいます。このファイルで、TLSアクセスに関する重要な変更が行われました。
    *   以前は、`linux`システムでは`-shared`フラグが設定されている場合にTLSベースレジスタが不明であるとエラーになっていました。このコミットでは、`ctxt.Flag_shared != 0`の場合に`0x64`（`FS`セグメントレジスタ）を返すように修正されています。これは、共有ライブラリのコンテキストでTLSにアクセスする際に、`FS`レジスタが使用されることを明示しています。
    *   `REG_TLS`（TLSレジスタ）の扱いも変更されました。`-shared`フラグが設定されている場合、`MOV 0(CX)(TLS*1), AX`のような命令が`mov %fs:(%rcx), %rax`に変換されることが示唆されています。これは、TLSオフセットが`%rcx`にロードされていることを前提とした、共有ライブラリ向けのTLSアクセスパターンです。また、TLSへの非ゼロオフセットアクセスが禁止されています。
    *   `asmandsz`関数内で、`REG_TLS`がインデックスとして使用され、かつ`-shared`フラグが設定されていない場合にのみ、`R_TLS_IE`リロケーションタイプが生成されるように変更されました。これは、静的リンクの場合と共有ライブラリの場合でTLSアクセスに対するリロケーションの扱いが異なることを示しています。

3.  **ELFリロケーションの生成**:
    *   `src/cmd/6l/asm.go`において、リンカー(`6l`)が`ld.R_TLS_IE`リロケーションタイプを処理するロジックが追加されました。
    *   `ld.R_TLS_IE`は、ELFの`R_X86_64_GOTTPOFF`リロケーションに対応します。これは、TLS初期実行モデル（TLS変数のアドレスをGOTから取得し、それをベースにオフセットでアクセスする）で使用されるリロケーションタイプです。リンカーは、このリロケーションタイプを受け取ると、適切なシンボル情報（`elfsym`）と組み合わせて`R_X86_64_GOTTPOFF`リロケーションを発行します。これにより、共有ライブラリがロードされた際に、動的リンカーがTLS変数のアドレスを正しく解決できるようになります。

4.  **`canuselocaltls`関数の修正**:
    *   `src/cmd/internal/obj/x86/obj6.go`の`canuselocaltls`関数は、ローカルTLS（直接TLSにアクセスできるかどうか）を判断します。`linux`の場合、`-shared`フラグが設定されていない場合にのみローカルTLSを使用できる（つまり、共有ライブラリの場合は異なるTLSアクセス方法が必要）というロジックが追加されました。

これらの変更により、Goのツールチェーンは、共有ライブラリとしてビルドされるGoコードが、OSの動的リンカーと連携してTLS変数に正しくアクセスし、必要なシンボル解決を行えるようになりました。

`asmandsz`関数では、`REG_TLS`がインデックスとして使用され、かつ`-shared`フラグが設定されていない場合にのみ、`R_TLS_IE`リロケーションタイプが生成されるように変更されました。これは、静的リンクの場合と共有ライブラリの場合でTLSアクセスに対するリロケーションの扱いが異なることを示しています。静的リンクでは`R_TLS_IE`が必要ですが、共有ライブラリでは異なるリロケーション（またはリロケーションなしで直接アクセス）が使用されることを意味します。

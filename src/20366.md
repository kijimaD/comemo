# [インデックス 20366] ファイルの概要

このコミットは、Goランタイムにおけるシステムコール（`syscall.Syscall`）の実行中にスタックが安全に扱われるようにするための重要な変更を導入しています。特に、`entersyscall`および`exitsyscall`というシステムコールへの出入りを管理する関数が、スタックのコピーを伴うスタック成長と競合しないように修正されています。これは、Go 1.4で導入された連続スタック（contiguous stack）モデルへの移行を補完し、Goランタイムのスタック管理の堅牢性を向上させるための重要なステップです。

    It is fundamentally unsafe to grow the stack once someone
    has made a call to syscall.Syscall. That function takes 6 uintptr
    arguments, but depending on the call some are pointers.
    In fact, some might be pointers to stack values, and we don't know which.
    That makes it impossible to copy the stack somewhere else.
    Since we want to delete all the stack splitting code, relying only
    on stack copying, make sure that Syscall never needs to split the stack.

    The only thing Syscall does is:
            call entersyscall
            make the system call
            call exitsyscall

    As long as we make sure that entersyscall and exitsyscall
    can live in the nosplit region, they won't ask for more stack.

    stack guard so that any call to a function with a split check
    will cause a crash. Then move non-essential slow-path
    work onto the m stack using onM and mark the rest of the
    work nosplit. The linker will verify that the chain of nosplits
    fits in the total nosplit budget.

## 変更の背景

Goランタイムは、ゴルーチン（goroutine）のスタックを動的に管理します。Goの初期バージョンでは、スタックが不足すると「セグメントスタック（segmented stacks）」または「スタック分割（stack splitting）」というメカニズムでスタックを拡張していました。これは、新しい、より大きなスタックセグメントを割り当て、古いスタックの内容を新しいセグメントにコピーして、実行を継続する方式です。しかし、この方式には「ホットスプリット問題（Hot Split Problem）」という性能上の課題がありました。これは、小さな関数が頻繁に呼び出され、そのたびにスタックの成長と縮小が繰り返されると、スタックセグメントの頻繁な割り当てと解放が発生し、オーバーヘッドが大きくなる問題です。

Go 1.4以降、Goランタイムはセグメントスタックから「連続スタック（contiguous stacks）」、すなわち「スタックコピー（stack copying）」へと移行しました。この新しいモデルでは、スタックが不足すると、より大きな連続したメモリブロックを割り当て、古いスタックの内容を新しいブロックにコピーします。これにより、ホットスプリット問題は解消されました。

しかし、`syscall.Syscall`のようなシステムコールを呼び出す際には、このスタックコピーも問題となる可能性がありました。`syscall.Syscall`は最大6つの`uintptr`型の引数を取りますが、これらの引数の一部はスタック上の値へのポインタである可能性があります。Goランタイムは、どの引数がポインタであるかを正確に識別できないため、システムコール中にスタックをコピーしようとすると、コピー先の新しいスタックでポインタが不正なアドレスを指してしまう（dangling pointer）危険性がありました。これは、ガベージコレクション（GC）がポインタを正確に追跡できないことにも関連します。

このコミットは、スタック分割コードを完全に削除し、スタックコピーのみに依存する将来のランタイムに向けて、`syscall.Syscall`がスタックを分割する必要がないようにするための重要なステップです。具体的には、`entersyscall`と`exitsyscall`がスタックを成長させないようにすることで、システムコール実行中のスタックの安全性を確保し、スタックコピーのメカニズムと競合しないようにしています。これにより、Goランタイムの堅牢性が向上し、より効率的なスタック管理への道が開かれました。

## 前提知識の解説

### Goランタイムのスタック管理

Goのゴルーチンは、非常に軽量なスレッドであり、それぞれが独自のスタックを持っています。このスタックは、必要に応じて動的にサイズが変更されます。

*   **セグメントスタック (Segmented Stacks) / スタック分割 (Stack Splitting)**: Goの初期バージョンで採用されていたスタック拡張メカニズム。関数呼び出し時にスタックガードページに到達すると、より大きなスタックセグメントを割り当て、古いスタックの内容を新しいセグメントにコピーして、実行を継続します。しかし、頻繁なスタックの成長と縮小が性能問題（ホットスプリット問題）を引き起こしました。
*   **連続スタック (Contiguous Stacks) / スタックコピー (Stack Copying)**: Go 1.4以降で採用されているスタック管理方式。スタックが不足した際に、より大きな連続したメモリブロックを割り当て、古いスタックの内容を新しいブロックにコピーします。これにより、ホットスプリット問題は解消され、より予測可能な性能を提供します。現在のGoランタイムでは、この方式が主流です。

### `syscall.Syscall`

GoプログラムがOSのシステムコールを直接呼び出すための低レベルな関数です。例えば、ファイルI/Oやネットワーク通信など、OSカーネルの機能を利用する際に使用されます。この関数は、GoランタイムのスケジューラからOSスケジューラへの移行を伴います。システムコール中にGoランタイムはゴルーチンをOSスレッドから切り離し、他のゴルーチンが実行できるようにします。

### `entersyscall` と `exitsyscall`

Goランタイム内部の関数で、ゴルーチンがシステムコールに入る直前（`entersyscall`）と、システムコールから戻った直後（`exitsyscall`）に呼び出されます。これらの関数は、Goスケジューラがゴルーチンの状態を適切に管理し、GCが安全に動作できるようにするために重要な役割を果たします。具体的には、ゴルーチンの状態を`Grunning`（実行中）から`Gsyscall`（システムコール中）に遷移させたり、M（Machine）とP（Processor）の関連付けを解除したりします。これにより、システムコールでブロックされている間も、他のゴルーチンが実行を継続できます。

### `NOSPLIT` pragma

Goコンパイラに対する指示（プラグマ）の一つで、特定の関数がスタック分割を行わないように指定します。`//go:nosplit`としてGoコードに記述されますが、このコミットの時点ではC言語で書かれたランタイムコードに対して`#pragma textflag NOSPLIT`が使用されています。このプラグマが適用された関数は、スタックオーバーフローチェックをスキップし、スタックを成長させません。これは、スタックのサイズが非常に小さいことが保証されている、あるいはスタック分割が許されないクリティカルなパス（例えば、メモリ割り当てやGC関連のコード）で使用されます。`NOSPLIT`関数内でスタックが不足すると、プログラムはクラッシュする可能性があります。

### `onM` 関数

Goランタイム内部の関数で、現在のM（OSスレッド）のスタック（g0スタックまたはgsignalスタック）上で特定の関数を実行するために使用されます。これは、通常のゴルーチンのスタック（gスタック）とは異なる、より安定したスタック環境で処理を実行したい場合に利用されます。特に、スタックの成長やGCによる移動が問題となるような処理、あるいはロックの取得など、ゴルーチンのスタックに依存しないクリティカルな操作に適しています。`onM`を使用することで、`entersyscall`や`exitsyscall`のような関数自体のスタック使用量を最小限に抑え、`NOSPLIT`の制約を満たすことができます。

### `g->stackguard0` と `g->throwsplit`

*   `g->stackguard0`: ゴルーチン`g`のスタックガードページのアドレスを保持するフィールド。通常、スタックがこのアドレスに近づくと、スタック成長が必要であることを示すシグナルがトリガーされます。
*   `g->throwsplit`: このコミットで`G`構造体に追加された新しいブール型フィールド。`true`に設定されている場合、スタック分割が発生するとランタイムパニックを引き起こすことを示します。これは、`entersyscall`や`exitsyscall`のようなスタック分割が許されないコンテキストで、意図しないスタック分割を検出するための安全機構として機能します。`runtime·newstack`関数（スタック成長を処理する関数）は、このフラグが`true`の場合にパニックを発生させます。

## 技術的詳細

このコミットの主要な目的は、`syscall.Syscall`の実行中にスタックが安全に扱われることを保証することです。具体的には、`entersyscall`と`exitsyscall`がスタックを成長させる必要がないように変更されています。

1.  **`NOSPLIT`の適用**:
    `entersyscall`と`entersyscallblock`関数に`#pragma textflag NOSPLIT`が適用されました。これにより、これらの関数はコンパイラによってスタック分割を行わないことが保証されます。システムコールへの出入りは非常にクリティカルなパスであり、この間にスタックが移動すると、システムコールに渡されたスタック上のポインタが無効になる可能性があるため、スタックの不変性を保つことが不可欠です。

2.  **スタックガードの変更と`throwsplit`フラグの設定による安全機構**:
    `entersyscall`および`entersyscallblock`内で、`g->stackguard0`が`StackPreempt`に設定され、`g->throwsplit`が`1`（true）に設定されます。
    *   `StackPreempt`は、スタックガードページがプリエンプション（横取り）のために使用されることを示す特殊な値です。ここでは、スタック分割チェックをトリガーしやすくするために利用されます。
    *   `g->throwsplit = 1`は、このゴルーチンがスタック分割を試みた場合にランタイムパニックを引き起こすことを示します。これは、システムコール中にスタックが移動するのを厳しく禁止するための「フェイルファスト」安全策です。
    *   `runtime·newstack`関数（スタック成長を処理する関数）は、`g->throwsplit`が`true`の場合に「runtime: stack split at bad time」というパニックを発生させるように変更されました。これにより、システムコール中の不正なスタック移動による潜在的なデータ破損を未然に防ぎます。

3.  **`onM`による遅延パスの処理のオフロード**:
    `entersyscall`および`entersyscallblock`内で、通常はゴルーチンのスタックで直接実行されていた一部の処理が、`onM`関数を使用してM（OSスレッド）のスタック上で実行されるように変更されました。
    *   例えば、`entersyscall`内の`runtime·sched.sysmonwait`のチェック（システムモニターの待機状態の確認と解除）や`runtime·sched.gcwaiting`の処理（GC待機中のPの状態変更）、`entersyscallblock`内の`handoffp`の呼び出し（Pの解放と引き渡し）などが、それぞれ`entersyscall_sysmon`、`entersyscall_gcwait`、`entersyscallblock_handoff`といったヘルパー関数に切り出され、`onM`を介して呼び出されています。
    *   これにより、これらの処理がゴルーチンのスタックではなく、より安定したMのスタック上で実行されるため、`entersyscall`と`exitsyscall`自体のスタック使用量を最小限に抑え、`NOSPLIT`の制約を満たすことができます。特に、ロックの取得やGC関連の処理など、ゴルーチンのスタックの状態に依存しない方が良い処理がオフロードされています。

4.  **`exitsyscall`での`throwsplit`のリセット**:
    `exitsyscall`関数では、システムコールから戻った後に`g->throwsplit`が`0`（false）にリセットされます。これにより、ゴルーチンは通常のスタック成長動作に戻ることができます。また、`g->stackguard0`も元の値に戻されます。

これらの変更により、`entersyscall`と`exitsyscall`は非常に軽量で、スタックを成長させる必要がない「nosplit region」内で実行されることが保証されます。これにより、システムコール中にスタックが移動する危険性がなくなり、Goランタイムのスタック管理の堅牢性が向上します。

## コアとなるコードの変更箇所

### `src/pkg/runtime/proc.c`

*   `runtime·casgstatus`関数内で、`isscanstatus`チェックが`oldval&Gscan`や`newval&Gscan`に変更され、エラー処理が`badcasgstatus`関数に切り出され`onM`経由で呼び出されるようになった。これにより、`casgstatus`自体のスタック使用量を減らし、`NOSPLIT`の制約に適合しやすくなっています。
*   `runtime·casgstatus`内のGCヘルプ処理も`helpcasgstatus`関数に切り出され`onM`経由で呼び出されるようになった。
*   `runtime·entersyscall`関数に`#pragma textflag NOSPLIT`が追加。
*   `runtime·entersyscall`内で`g->stackguard0 = StackPreempt;`と`g->throwsplit = 1;`が設定されるようになった。
*   `runtime·entersyscall`内の`runtime·printf`や`runtime·throw`を伴うエラー処理、`sysmonwait`の処理、`gcwaiting`の処理が、それぞれ`entersyscall_bad`、`entersyscall_sysmon`、`entersyscall_gcwait`という新しいヘルパー関数に切り出され、`onM`経由で呼び出されるようになった。
*   `runtime·entersyscallblock`関数に`#pragma textflag NOSPLIT`が追加。
*   `runtime·entersyscallblock`内で`g->throwsplit = 1;`と`g->stackguard0 = StackPreempt;`が設定されるようになった。
*   `runtime·entersyscallblock`内のエラー処理が`entersyscall_bad`に切り出され`onM`経由で呼び出されるようになった。
*   `runtime·entersyscallblock`内の`releasep()`と`handoffp()`の呼び出しが`entersyscallblock_handoff`関数に切り出され`onM`経由で呼び出されるようになった。
*   `runtime·entersyscallblock_m`関数が削除された。これは、`entersyscallblock`が`onM`を使用するように変更されたため、`g0`スタックでの特別な処理が不要になったためと考えられます。
*   `runtime·exitsyscall`関数内で、`g->throwsplit = 0;`が追加され、`g->stackguard0`のリセットが`g->throwsplit`が`false`の場合にのみ行われるようになった。
*   `exitsyscallfast`関数内で、`pidle`の処理が`exitsyscallfast_pidle`関数に切り出され`onM`経由で呼び出されるようになった。

### `src/pkg/runtime/runtime.h`

*   `G`構造体に新しいフィールド`bool throwsplit;`が追加された。このフィールドは、ゴルーチンがスタック分割を試みた場合にパニックを引き起こすかどうかを制御します。

### `src/pkg/runtime/stack.c`

*   `runtime·newstack`関数内で、`if(g->throwsplit)`のチェックが追加され、`g->throwsplit`が`true`の場合は`runtime·throw("runtime: stack split at bad time");`でパニックを発生させるようになった。これは、システムコール中にスタックが移動するのを厳しく禁止するための最終的な安全機構です。

## コアとなるコードの解説

このコミットの核心は、システムコールへの出入りを管理する`entersyscall`と`exitsyscall`関数が、スタックの成長を必要としないようにすることです。

1.  **`NOSPLIT`の強制**: `entersyscall`と`entersyscallblock`に`#pragma textflag NOSPLIT`が付けられたことで、コンパイラはこれらの関数がスタックを拡張しないことを保証します。これは、システムコール中にスタックが移動すると、システムコールに渡されたスタック上のポインタが無効になる可能性があるため、非常に重要です。これにより、システムコール実行中のスタックの安定性が確保されます。

2.  **スタックガードと`throwsplit`による安全機構**:
    *   `g->stackguard0 = StackPreempt;`と`g->throwsplit = 1;`の設定は、システムコール実行中のゴルーチンが誤ってスタック分割を試みた場合に、即座にパニックを引き起こすための「フェイルファスト」メカニズムです。これにより、不正なスタック移動による潜在的なデータ破損を防ぎます。
    *   `runtime·newstack`での`g->throwsplit`チェックは、この安全機構の最終防衛線として機能し、意図しないスタック成長を厳しく阻止します。

3.  **`onM`による処理のオフロード**:
    `entersyscall`や`entersyscallblock`内で、本来ゴルーチンのスタックで実行されるはずだった一部の処理（例えば、スケジューラの状態更新やGC関連の処理）が、`onM`関数を使ってM（OSスレッド）のスタック（g0スタック）にオフロードされました。
    *   これにより、`entersyscall`と`exitsyscall`自体のコードパスが短く、スタック使用量が予測可能になり、`NOSPLIT`の制約を容易に満たすことができます。
    *   `onM`は、Goランタイムの内部で、ゴルーチンのスタックとは独立した、より安定した環境でクリティカルな処理を実行するための一般的なパターンです。これにより、システムコール中のランタイムの安定性が向上します。

これらの変更は、Goランタイムがスタック管理をセグメントスタックから連続スタックへと進化させる過程における重要な一歩です。システムコール中のスタックの安全性を確保することで、より堅牢で効率的なランタイムの実現に貢献しています。

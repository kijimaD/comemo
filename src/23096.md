# [インデックス 23096] ファイルの概要

## コミット

このコミットは、Goランタイムのスケジューラにおける重要な改善を導入しています。具体的には、あるGoroutine (G1) が別のGoroutine (G2) を `ready()` 状態にし、その後G1自身がブロックする場合に、G1の残りのタイムスライスを即座にG2に引き渡すように変更しています。これにより、特にCPUを大量に消費するGoroutineが存在する環境下で、Goroutine間の公平性と応答性が向上します。

従来のスケジューリングでは、`ready()` 状態になったGoroutineはP (Processor) の実行キューの末尾に追加され、そのGoroutineが実際に実行されるまでに遅延が発生する可能性がありました。これは、特にチャネル通信などで頻繁に協調動作を行うGoroutineペアにとって、不公平なCPU時間配分につながっていました。この変更により、協調動作するGoroutineペアが「ユニット」として扱われ、より効率的にCPU時間を共有できるようになります。

この改善は、特に「ping-pong hog」のようなシナリオで顕著な性能向上をもたらしています。ベンチマークでは、`BenchmarkPingPongHog` の実行時間が99.88%削減されるという劇的な改善が報告されています。また、`x/benchmarks` スイートの `garbage` ベンチマークで約6%、`json` ベンチマークで28%から36%の性能向上が見られました。

## 元コミット内容

```
runtime: yield time slice to most recently readied G

Currently, when the runtime ready()s a G, it adds it to the end of the
current P's run queue and continues running. If there are many other
things in the run queue, this can result in a significant delay before
the ready()d G actually runs and can hurt fairness when other Gs in
the run queue are CPU hogs. For example, if there are three Gs sharing
a P, one of which is a CPU hog that never voluntarily gives up the P
and the other two of which are doing small amounts of work and
communicating back and forth on an unbuffered channel, the two
communicating Gs will get very little CPU time.

Change this so that when G1 ready()s G2 and then blocks, the scheduler
immediately hands off the remainder of G1's time slice to G2. In the
above example, the two communicating Gs will now act as a unit and
together get half of the CPU time, while the CPU hog gets the other
half of the CPU time.

This fixes the problem demonstrated by the ping-pong benchmark added
in the previous commit:

benchmark                old ns/op     new ns/op     delta
BenchmarkPingPongHog     684287        825           -99.88%

On the x/benchmarks suite, this change improves the performance of
garbage by ~6% (for GOMAXPROCS=1 and 4), and json by 28% and 36% for
GOMAXPROCS=1 and 4. It has negligible effect on heap size.

This has no effect on the go1 benchmark suite since those benchmarks
are mostly single-threaded.

Change-Id: I858a08eaa78f702ea98a5fac99d28a4ac91d339f
Reviewed-on: https://go-review.googlesource.com/9289
Reviewed-by: Rick Hudson <rlh@golang.org>
Reviewed-by: Russ Cox <rsc@golang.org>
```

## 変更の背景

この変更の背景には、GoランタイムのスケジューラにおけるGoroutineの公平性に関する課題がありました。従来のスケジューリングアルゴリズムでは、Goroutineが `ready()` 状態になった際に、単にPのローカル実行キューの末尾に追加されるだけでした。この方式は、以下のような問題を引き起こす可能性がありました。

1.  **スケジューリング遅延**: 実行キューに多数のGoroutineが待機している場合、新しく `ready()` になったGoroutineが実際にCPU時間を獲得するまでに長い時間がかかることがありました。
2.  **公平性の欠如**: 特に、CPUを長時間占有する「CPU hog」なGoroutineが存在する場合、他のGoroutineがCPU時間をほとんど得られない状況が発生しやすかったです。コミットメッセージの例では、CPU hogなGoroutineと、アンバッファードチャネルで頻繁に通信する2つのGoroutineが存在する場合、後者の2つのGoroutineがほとんどCPU時間を得られないという問題が指摘されています。これは、協調して動作するGoroutineペアが、その協調性ゆえに不利になるという皮肉な状況を生み出していました。
3.  **応答性の低下**: ユーザーインタラクションやネットワークI/Oなど、迅速な応答が求められるタスクにおいて、Goroutineがすぐに実行されないことはアプリケーションの応答性低下に直結します。

このコミットは、このような問題を解決し、特にGoroutine間の協調動作が頻繁に行われるシナリオにおいて、より予測可能で公平なCPU時間配分を実現することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスケジューラに関する以下の基本的な概念を理解しておく必要があります。

*   **Goroutine (G)**: Goにおける軽量な実行単位です。OSのスレッドよりもはるかに軽量で、数百万のGoroutineを同時に実行できます。
*   **Logical Processor (P)**: OSスレッド上でGoroutineを実行するためのコンテキストです。Goランタイムは、`GOMAXPROCS` の数だけPを作成し、それぞれのPが1つのOSスレッドにアタッチされます。PはGoroutineの実行キュー（ローカル実行キュー）を管理します。
*   **Machine (M)**: OSスレッドを表します。MはPにアタッチされ、Pが管理するGoroutineを実行します。
*   **M:P:G モデル**: Goのスケジューラは、M (OSスレッド)、P (論理プロセッサ)、G (Goroutine) の3つのエンティティで構成されるM:P:Gモデルを採用しています。MはOSスレッドを表し、PはM上でGoroutineを実行するためのコンテキストを提供し、Gは実行されるコードです。
*   **ローカル実行キュー (Local Run Queue)**: 各Pは、自身が実行する準備ができたGoroutineのキューを持っています。Goroutineが `ready()` 状態になると、通常はこのキューの末尾に追加されます。
*   **グローバル実行キュー (Global Run Queue)**: ローカル実行キューが空になったPは、グローバル実行キューからGoroutineを取得しようとします。また、ローカル実行キューが満杯になった場合、一部のGoroutineはグローバル実行キューに移動されます。
*   **タイムスライス (Time Slice)**: スケジューラがGoroutineに割り当てるCPU時間の最大量です。Goroutineは、タイムスライスが終了するか、I/O操作などで自発的にブロックするまで実行を継続します。
*   **プリエンプション (Preemption)**: スケジューラが、実行中のGoroutineのタイムスライスが終了する前に、強制的に実行を中断し、別のGoroutineにCPUを割り当てることです。Go 1.14以降では、非協調的なプリエンプションが導入され、長時間実行されるループなどでもGoroutineがプリエンプトされるようになりました。このコミットの時点では、主に協調的なプリエンプション（Goroutineが自発的にブロックする、関数呼び出しのプロローグでチェックされるなど）が中心でした。
*   **`ready()` 関数**: Goroutineが実行可能状態になったときに呼び出されるランタイム関数です。通常、この関数はGoroutineを実行キューに追加します。
*   **`execute()` 関数**: 指定されたGoroutineを現在のM上で実行を開始するランタイム関数です。

## 技術的詳細

このコミットの核心は、Goスケジューラの `runqput` および `execute` 関数、そしてP構造体への変更にあります。

従来の `runqput` 関数は、`ready()` 状態になったGoroutineをPのローカル実行キューの末尾に単純に追加していました。これにより、キューの先頭にあるGoroutineが優先的に実行され、新しく `ready()` になったGoroutineは待機する必要がありました。

この変更では、P構造体に `runnext` という新しいフィールドが追加されました。`runnext` は、現在のGoroutineがブロックする際に、そのGoroutineが `ready()` にしたGoroutineを直接指すための特別なスロットです。

具体的な動作は以下のようになります。

1.  **Goroutine G1がG2を `ready()` にする**: G1がチャネル操作などでG2を `ready()` 状態にする際、`runqput` 関数が呼び出されます。
2.  **`runqput` の変更**: `runqput` 関数は、新しい `next` 引数を受け取るようになりました。
    *   もし `next` が `true` であれば、G2はPの `runnext` スロットに配置されます。
    *   もしPの `runnext` スロットが既に別のGoroutineで占有されていた場合、そのGoroutineは通常のローカル実行キューの末尾に移動され、G2が `runnext` に配置されます。
    *   `next` が `false` であれば、G2は従来通りローカル実行キューの末尾に追加されます。
3.  **G1がブロックする**: G1がブロック状態に移行し、スケジューラが次に実行するGoroutineを探すために `findrunnable()` を呼び出します。
4.  **`findrunnable()` の変更**: `findrunnable()` 関数は、まずPの `runnext` スロットをチェックするようになりました。
    *   もし `runnext` にGoroutine (G2) が存在すれば、そのG2が即座に選択され、`inheritTime` が `true` として返されます。
    *   `runnext` が空の場合、または `runnext` からGoroutineを取得できなかった場合、従来通りローカル実行キューやグローバル実行キューからGoroutineを探します。
5.  **`execute()` の変更**: `execute()` 関数も `inheritTime` 引数を受け取るようになりました。
    *   `inheritTime` が `true` の場合、`execute()` は現在のPの `schedtick` (タイムスライスをカウントするカウンタ) をインクリメントしません。これは、新しく実行されるGoroutine (G2) が、前のGoroutine (G1) の残りのタイムスライスを引き継ぐことを意味します。
    *   `inheritTime` が `false` の場合、`schedtick` はインクリメントされ、新しいタイムスライスが開始されます。

このメカニズムにより、G1がG2を `ready()` にしてすぐにブロックする場合、G2は通常のキューの末尾に置かれることなく、G1の残りのタイムスライスを「継承」して即座に実行される機会を得ます。これにより、チャネル通信などで密接に連携するGoroutineペアが、あたかも単一のGoroutineであるかのように効率的にCPU時間を共有できるようになり、スケジューリングのオーバーヘッドと遅延が大幅に削減されます。

この変更は、特にアンバッファードチャネルを介したGoroutine間の頻繁な通信パターンにおいて、スケジューリングのレイテンシを劇的に改善します。CPU hogなGoroutineが存在する状況でも、協調動作するGoroutineペアが公平なCPU時間を得られるようになり、全体的なアプリケーションの応答性とスループットが向上します。

## コアとなるコードの解説

### `src/runtime/runtime2.go` の `p` 構造体

```go
type p struct {
    // ... 既存のフィールド ...
    runqhead uint32
    runqtail uint32
    runq     [256]*g
    // runnext, if non-nil, is a runnable G that was ready'd by
    // the current G and should be run next instead of what's in
    // runq if there's time remaining in the running G's time
    // slice. It will inherit the time left in the current time
    // slice. If a set of goroutines is locked in a
    // communicate-and-wait pattern, this schedules that set as a
    // unit and eliminates the (potentially large) scheduling
    // latency that otherwise arises from adding the ready'd
    // goroutines to the end of the run queue.
    runnext guintptr
    // ... 既存のフィールド ...
}
```
`runnext` フィールドは、このコミットの主要な変更点です。これは、現在のGoroutineが `ready()` にしたGoroutineを一時的に保持するための特別なスロットです。このGoroutineは、現在のGoroutineの残りのタイムスライスを引き継いで、すぐに実行される優先権を持ちます。これにより、チャネル通信などで密接に連携するGoroutineペアが、スケジューリングの遅延なしに連続して実行されることが可能になります。

### `src/runtime/proc1.go` の `runqput` 関数

```go
func runqput(_p_ *p, gp *g, next bool) {
    if next {
    retryNext:
        oldnext := _p_.runnext
        if !_p_.runnext.cas(oldnext, guintptr(unsafe.Pointer(gp))) {
            goto retryNext
        }
        if oldnext == 0 {
            return
        }
        // Kick the old runnext out to the regular run queue.
        gp = oldnext.ptr()
    }

retry:
    h := atomicload(&_p_.runqhead) // load-acquire, synchronize with consumers
    t := _p_.runqtail
    // ... (既存のローカルキューへの追加ロジック) ...
}
```
`runqput` 関数は、`next` という新しいブール引数を受け取るようになりました。
*   `next` が `true` の場合、`gp` はまず `_p_.runnext` スロットに配置しようとします。
*   もし `_p_.runnext` が既に別のGoroutine (`oldnext`) で占有されていた場合、その `oldnext` は通常のローカル実行キューの末尾に「追い出され」、`gp` が `_p_.runnext` に設定されます。
*   `next` が `false` の場合、または `runnext` への配置後に `oldnext` が通常のキューに移動される場合、Goroutineは従来のローカル実行キューの末尾に追加されます。

この変更により、特定のシナリオ（例えば、Goroutineが別のGoroutineを `ready()` にしてすぐにブロックする場合）で、新しく `ready()` になったGoroutineが即座にCPUを獲得する機会が与えられます。

### `src/runtime/proc1.go` の `runqget` 関数

```go
func runqget(_p_ *p) (gp *g, inheritTime bool) {
    // If there's a runnext, it's the next G to run.
    for {
        next := _p_.runnext
        if next == 0 {
            break
        }
        if _p_.runnext.cas(next, 0) {
            return next.ptr(), true
        }
    }

    for {
        h := atomicload(&_p_.runqhead) // load-acquire, synchronize with other consumers
        t := _p_.runqtail
        if t == h {
            return nil, false
        }
        gp := _p_.runq[h%uint32(len(_p_.runq))]
        if cas(&_p_.runqhead, h, h+1) { // cas-release, commits consume
            return gp, false
        }
    }
}
```
`runqget` 関数は、Pのローカル実行キューからGoroutineを取得する際に、まず `_p_.runnext` スロットをチェックするようになりました。
*   もし `_p_.runnext` にGoroutineが存在すれば、そのGoroutineが優先的に返され、`inheritTime` は `true` となります。これは、このGoroutineが前のGoroutineの残りのタイムスライスを引き継ぐことを意味します。
*   `_p_.runnext` が空の場合、またはCAS操作に失敗した場合は、従来通りローカル実行キューの先頭からGoroutineを取得します。この場合、`inheritTime` は `false` となります。

### `src/runtime/proc1.go` の `execute` 関数

```go
func execute(gp *g, inheritTime bool) {
    _g_ := getg()

    casgstatus(gp, _Grunnable, _Grunning)
    gp.waitsince = 0
    gp.preempt = false
    gp.stackguard0 = gp.stack.lo + _StackGuard
    if !inheritTime {
        _g_.m.p.ptr().schedtick++
    }
    _g_.m.curg = gp
    gp.m = _g_.m

    gogo(&gp.context) // Never returns.
}
```
`execute` 関数は、実行するGoroutine (`gp`) と共に `inheritTime` 引数を受け取るようになりました。
*   `inheritTime` が `true` の場合、`_g_.m.p.ptr().schedtick++` (Pのタイムスライスをカウントするカウンタ) は実行されません。これにより、このGoroutineは前のGoroutineの残りのタイムスライスを引き継ぎ、新しいタイムスライスを開始しないことになります。
*   `inheritTime` が `false` の場合、`schedtick` はインクリメントされ、新しいタイムスライスが開始されます。

これらの変更の組み合わせにより、Goスケジューラは、Goroutine間の協調動作をより効率的に処理し、特にチャネル通信などで頻繁にGoroutineが `ready()` 状態になり、その後ブロックするようなシナリオにおいて、スケジューリングのレイテンシを大幅に削減します。

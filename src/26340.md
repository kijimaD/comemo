# [インデックス 26340] ファイルの概要

このコミットは、Goランタイムにおける`runtime.NumGoroutine()`関数と`runtime.Stack()`関数の挙動の不整合を解消することを目的としています。具体的には、`runtime.NumGoroutine()`がシステムゴルーチンを含んでカウントしていたのに対し、`runtime.Stack()`は通常これらを表示していなかったため、両者がシステムゴルーチンを含まない形で一貫するように修正されました。これにより、ユーザーが期待する「実行中のユーザーゴルーチン数」が正確に報告されるようになります。

## 変更の背景

Goランタイムには、`runtime.NumGoroutine()`と`runtime.Stack()`という、実行中のゴルーチンに関する情報を提供する2つの主要な関数があります。しかし、このコミット以前は、これらの関数の挙動に一貫性がありませんでした。具体的には、`runtime.NumGoroutine()`はGoランタイム内部で利用される「システムゴルーチン」（ガベージコレクション、スケジューラ、ネットワーキングなど、ユーザーコードからは直接見えないゴルーチン）を含めてカウントしていました。一方で、`runtime.Stack()`は通常、これらのシステムゴルーチンを表示していませんでした。

この不整合は、開発者にとって混乱の原因となっていました。例えば、単純な`main`関数のみのプログラムで`runtime.NumGoroutine()`を呼び出した場合、ユーザーは通常「1」（`main`ゴルーチン）を期待しますが、実際にはシステムゴルーチンが含まれるため、より大きな値が返される可能性がありました。このコミットは、この混乱を解消し、両方の関数がユーザーが作成したゴルーチンのみを対象とするように一貫性を持たせることを目的としています。

コミットメッセージにあるように、`package main; import "runtime"; func main() { println(runtime.NumGoroutine()) }`というコードが「1」を出力すべきであるという直感的な期待に応えるための変更です。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念と機能に関する知識が必要です。

*   **Goroutine (ゴルーチン)**: Go言語における軽量な実行スレッドです。OSのスレッドよりもはるかに軽量で、数千から数百万のゴルーチンを同時に実行できます。Goランタイムのスケジューラによって管理されます。
*   **System Goroutine (システムゴルーチン)**: Goランタイム自体が内部的な処理のために起動するゴルーチンです。これらはユーザーが直接`go`キーワードで起動するゴルーチンとは異なり、ガベージコレクション、ネットワークポーリング、スケジューラの管理など、ランタイムの正常な動作に不可欠なタスクを実行します。通常、ユーザーはこれらの存在を意識する必要はありません。
*   **`runtime.NumGoroutine()`**: 現在実行中および実行可能状態にあるゴルーチンの総数を返します。このコミット以前は、システムゴルーチンもこの数に含まれていました。
*   **`runtime.Stack(buf []byte, all bool) int`**: すべてのゴルーチンのスタックトレースを`buf`に書き込み、書き込まれたバイト数を返します。`all`が`true`の場合、すべてのゴルーチン（停止しているものも含む）のスタックトレースが含まれます。
*   **`schedt`構造体**: Goランタイムのスケジューラに関するグローバルな状態を保持する構造体です。ゴルーチンの生成、終了、スケジューリングに関連する様々な情報が含まれています。
*   **`atomic.Xadd`**: `sync/atomic`パッケージで提供される関数で、指定されたメモリアドレスの値をアトミックに加算します。複数のゴルーチンから同時にアクセスされても競合状態が発生しないことが保証されます。ランタイムのような並行性の高い環境で共有変数を安全に更新するために不可欠です。
*   **`newproc1`**: 新しいゴルーチンを作成し、初期化するランタイム内部関数です。
*   **`goexit0`**: ゴルーチンが終了する際に呼び出されるランタイム内部関数です。
*   **Cgo**: GoプログラムからC言語のコードを呼び出すためのメカニズムです。Cgoを介してC関数を呼び出す際にも、ランタイム内部で特定のゴルーチンが関与することがあります。
*   **`GOTRACEBACK`環境変数**: Goプログラムがクラッシュした際に、スタックトレースの表示レベルを制御する環境変数です。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムがシステムゴルーチンを追跡し、`runtime.NumGoroutine()`のカウントからそれらを除外するように変更された点にあります。

1.  **システムゴルーチン数の追跡**:
    *   `src/runtime/runtime2.go`内の`schedt`構造体に、`ngsys uint32`という新しいフィールドが追加されました。このフィールドは、現在アクティブなシステムゴルーチンの数をアトミックに追跡するために使用されます。`atomic.Xadd`によって安全に更新されます。
    *   `src/runtime/proc.go`内の`newproc1`関数（新しいゴルーチンが作成される際）において、作成されるゴルーチンが`isSystemGoroutine`関数によってシステムゴルーチンであると判定された場合、`sched.ngsys`がインクリメントされます。
    *   同様に、`src/runtime/proc.go`内の`goexit0`関数（ゴルーチンが終了する際）において、終了するゴルーチンがシステムゴルーチンである場合、`sched.ngsys`がデクリメントされます。

2.  **`runtime.NumGoroutine()`の修正**:
    *   `src/runtime/proc.go`内の`gcount`関数（`runtime.NumGoroutine()`が内部で呼び出す）が変更されました。以前は`int32(allglen) - sched.ngfree`でゴルーチン数を計算していましたが、これに加えて`int32(atomic.Load(&sched.ngsys))`を減算するようになりました。これにより、システムゴルーチンが総ゴルーチン数から除外され、ユーザーゴルーチンのみがカウントされるようになります。

3.  **`runtime.Stack()`の挙動の一貫性**:
    *   `src/runtime/mprof.go`内の`Stack`関数が修正されました。`systemstack`内で`g0.m.traceback = 1`を設定し、スタックトレースの取得が`GOTRACEBACK`環境変数の設定に依存せず、常に一貫した結果を返すように強制されます。これにより、`runtime.NumGoroutine()`がシステムゴルーチンを含まないのと同様に、`runtime.Stack()`も通常はユーザーゴルーチンのみを対象とするという一貫性が保たれます。

4.  **テストの追加と修正**:
    *   `src/runtime/proc_test.go`に`TestNumGoroutine`という新しいテストケースが追加されました。このテストは、`runtime.NumGoroutine()`が期待通り`1`を返すこと、そして`runtime.Stack(buf, true)`で取得したスタックトレース内のゴルーチン数と`runtime.NumGoroutine()`の戻り値が一致することを確認します。
    *   `src/runtime/testdata/testprog/misc.go`という新しいテストプログラムが追加され、`NumGoroutine`関数をエクスポートし、テストフレームワークから`runtime.NumGoroutine()`の出力を検証できるようにしています。
    *   `misc/cgo/test/issue7978.go`のCgoテストも、スタックトレースの文字列比較がより正確になるように調整されました。これは、Cgo呼び出しの内部表現が変更されたことによる追従です。

これらの変更により、Goランタイムはシステムゴルーチンとユーザーゴルーチンを明確に区別し、開発者向けのAPIがより直感的で一貫性のある情報を提供するようになりました。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/runtime/proc.go`と`src/runtime/runtime2.go`におけるシステムゴルーチン数の管理ロジックです。

**`src/runtime/runtime2.go`における`schedt`構造体の変更:**

```go
type schedt struct {
	// accessed atomically. keep at top to ensure alignment on 32-bit systems.
	goidgen  uint64
	lastpoll uint64

	lock mutex

	midle        muintptr // idle m's waiting for work
	nmidle       int32    // number of idle m's waiting for work
	mcount       int32    // number of m's that have been created
	maxmcount    int32    // maximum number of m's allowed (or die)

	ngsys uint32 // number of system goroutines; updated atomically

	pidle      puintptr // idle p's
	npidle     uint32
	nmspinning uint32 // See "Worker thread parking/unparking" comment in proc.go.
	// ... (他のフィールド)
}
```
`schedt`構造体に`ngsys`フィールドが追加されたことで、ランタイムはシステムゴルーチンの数をグローバルかつアトミックに追跡できるようになりました。これは、`runtime.NumGoroutine()`が正確なユーザーゴルーチン数を報告するための基盤となります。

**`src/runtime/proc.go`における`newproc1`と`goexit0`の変更:**

`newproc1`関数内では、新しいゴルーチンが作成される際に`isSystemGoroutine(newg)`でシステムゴルーチンであるかどうかがチェックされます。

```go
func newproc1(fn *funcval, argp *uint8, narg int32, nret int32, callerpc uintptr) *g {
	// ...
	newg.gopc = callerpc
	newg.startpc = fn.fn
	if isSystemGoroutine(newg) {
		atomic.Xadd(&sched.ngsys, +1) // システムゴルーチンであればカウントをインクリメント
	}
	casgstatus(newg, _Gdead, _Grunnable)
	// ...
}
```

同様に、`goexit0`関数内では、ゴルーチンが終了する際に`isSystemGoroutine(gp)`でシステムゴルーチンであるかどうかがチェックされます。

```go
func goexit0(gp *g) {
	_g_ := getg()

	casgstatus(gp, _Grunning, _Gdead)
	if isSystemGoroutine(gp) {
		atomic.Xadd(&sched.ngsys, -1) // システムゴルーチンであればカウントをデクリメント
	}
	gp.m = nil
	gp.lockedm = nil
	_g_.m.lockedg = nil
	// ...
}
```
これらの変更により、システムゴルーチンのライフサイクル（作成と終了）に合わせて`sched.ngsys`が正確に更新されるようになります。

**`src/runtime/proc.go`における`gcount`の変更:**

`gcount`関数は、`runtime.NumGoroutine()`が呼び出す内部関数です。

```go
func gcount() int32 {
	n := int32(allglen) - sched.ngfree - int32(atomic.Load(&sched.ngsys)) // システムゴルーチン数を減算
	for i := 0; ; i++ {
		_p_ := allp[i]
		if _p_ == nil {
			break
		}
		n += int32(_p_.runqsize)
	}
	return n
}
```
ここで、`int32(atomic.Load(&sched.ngsys))`が追加されたことで、`gcount`は総ゴルーチン数からシステムゴルーチンの数を差し引いて、純粋なユーザーゴルーチンの数を返すようになりました。`atomic.Load`を使用することで、`ngsys`の値がアトミックに読み取られ、並行性による問題が回避されます。

これらの変更が連携することで、`runtime.NumGoroutine()`はユーザーが期待する「ユーザーゴルーチン」の数を正確に報告し、`runtime.Stack()`との一貫性も向上しました。

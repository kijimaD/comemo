## 変更の背景

このコミットは、Go言語の初期開発段階で発見された、コンパイラ`6g`における並行代入のバグを修正するためのテストケースを追加するものです。Go言語の並行代入は、複数の変数に複数の値を同時に代入できる便利な機能ですが、その際に右辺の式（特に副作用を持つ関数呼び出し）が評価される順序は言語仕様によって厳密に定義されています。

当時の`6g`コンパイラは、この評価順序を誤って解釈し、右辺の関数呼び出しの評価順序を逆にしてしまうバグを抱えていました。これにより、関数がグローバル変数や共有状態を変更する副作用を持つ場合、期待とは異なる結果が変数に代入されてしまう問題が発生していました。このコミットは、このバグを明確に再現し、修正を検証するためのテストケース`bug159.go`を追加することで、コンパイラの正確性を保証しようとするものです。

## 前提知識の解説

### Go言語の並行代入 (Parallel Assignment)

Go言語では、以下のように複数の変数に複数の値を同時に代入することができます。

```go
a, b = 1, 2
```

この機能は、複数の戻り値を返す関数からの値を受け取ったり、変数の値を交換したりする際に非常に便利です。

```go
// 複数の戻り値を受け取る
value, err := someFunction()

// 変数の値を交換する
x, y = y, x
```

### 評価順序 (Evaluation Order)

Go言語の仕様では、並行代入の右辺にある式は、左辺の変数への代入が行われる前に、左から右へ（lexical order）完全に評価されることが保証されています。これは、右辺の式が副作用を持つ場合（例えば、関数呼び出しがグローバル変数を変更する場合など）に特に重要になります。

例えば、`x, y, z = f(), g(), h()`という代入があった場合、Go言語の仕様では`f()`、`g()`、`h()`の順に評価され、それぞれの結果が一時的な場所に保存された後、`x`、`y`、`z`に代入されます。この評価順序が保証されることで、予測可能なプログラムの挙動が実現されます。

### `6g`コンパイラ

`6g`は、Go言語の初期に存在した公式コンパイラの一つで、主にx86-64アーキテクチャをターゲットとしていました。Go言語の進化とともに、より汎用的な`gc`（Go Compiler）に統合されていきましたが、初期のGo言語開発において重要な役割を果たしました。このコミットが作成された2009年当時は、`6g`が主要なコンパイラの一つでした。

## 技術的詳細

このバグは、`6g`コンパイラが並行代入の右辺にある関数呼び出しの評価順序を誤って処理していたことに起因します。コミットメッセージとテストコードのコメントによると、コンパイラは`x, y, z = f(), f(), f()`のような並行代入を、以下のように逆順で評価されるような中間コードに書き換えていたようです。

```
z = f();
y = f();
x = f();
```

これはGo言語の仕様に反しています。Go言語の仕様では、右辺の式は左から右に評価されるため、`f()`が3回呼び出される場合、最初の`f()`の結果が`x`に、2番目の`f()`の結果が`y`に、3番目の`f()`の結果が`z`に代入されるべきです。

テストケース`bug159.go`では、`f()`関数が呼び出されるたびに内部状態（`b`変数）を変化させる副作用を持っています。

```go
var a, b, c, x, y, z int;
f := func() int { b--; return -b };
```

この`f`関数は、呼び出されるたびに`b`の値をデクリメントし、そのデクリメントされた`b`の負の値を返します。

初期状態で`b`が0の場合、
- 1回目の`f()`呼び出し: `b`は-1になり、`-(-1)`で`1`を返す。
- 2回目の`f()`呼び出し: `b`は-2になり、`-(-2)`で`2`を返す。
- 3回目の`f()`呼び出し: `b`は-3になり、`-(-3)`で`3`を返す。

したがって、`x, y, z = f(), f(), f()`という並行代入では、Go言語の仕様に従えば`x=1, y=2, z=3`となるべきです。しかし、`6g`のバグにより評価順序が逆になると、`z=1, y=2, x=3`という結果になってしまいます。テストコードのコメントにある`xyz: expected 1 2 3 got 3 2 1`という出力は、この逆順評価のバグを示しています。

同様に、2つ目のテストケース`a, b, c = f(), f(), f()`でも、`b`の初期値が異なるため、期待される結果とバグによる結果が異なります。このテストケースでは、`f()`の呼び出しが`b`への代入後に発生するという、さらに複雑な評価順序の問題も指摘されています。

このバグは、コンパイラのコード生成ロジックにおいて、並行代入の右辺式の評価結果を一時的に保持し、その後に左辺の変数に代入するという正しいセマンティクスが実装されていなかったことを示唆しています。

## コアとなるコードの変更箇所

このコミットで追加された主要なファイルは以下の通りです。

- `test/bugs/bug159.go`: 並行代入のバグを再現するためのテストケース。
- `test/golden.out`: `bug159.go`が失敗した場合の期待される出力（バグが修正される前の出力）を記録したファイル。

### `test/bugs/bug159.go`

```go
// $G $D/$F.go && $L $F.$A && ./$A.out || echo BUG: bug159

// Copyright 2009 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package main

import "os"

func main() {
	ok := true;
	var a, b, c, x, y, z int;
	f := func() int { b--; return -b };

	// this fails on 6g: apparently it rewrites
	// the list into
	//	z = f();
	//	y = f();
	//	x = f();
	// so that the values come out backward.
	x, y, z = f(), f(), f();
	if x != 1 || y != 2 || z != 3 {
		println("xyz: expected 1 2 3 got", x, y, z);
		ok = false;
	}

	// this fails on 6g too.  one of the function calls
	// happens after assigning to b.
	a, b, c = f(), f(), f();
	if a != 4 || b != 5 || c != 6 {
		println("abc: expected 4 5 6 got", a, b, c);
		ok = false;
	}

	if !ok {
		os.Exit(1);
	}
}
```

### `test/golden.out`

`test/golden.out`には、`bug159.go`が実行された際に、バグのある`6g`コンパイラで出力されるであろうエラーメッセージが追加されています。

```
+=========== bugs/bug159.go
+xyz: expected 1 2 3 got 3 2 1
+abc: expected 4 5 6 got -4 4 4

```

この`golden.out`への追加は、テストが失敗したときにどのような出力が期待されるかを示すものであり、テストフレームワークがこの出力を検出してバグを報告するために使用されます。

## コアとなるコードの解説

`bug159.go`は、Go言語の並行代入における関数呼び出しの評価順序のバグを検証するためのシンプルなテストプログラムです。

1.  **`f`関数の定義**:
    ```go
    var a, b, c, x, y, z int;
    f := func() int { b--; return -b };
    ```
    この無名関数`f`は、クロージャとして外部の`b`変数をキャプチャし、呼び出されるたびに`b`をデクリメントし、その結果の`b`の負の値を返します。これにより、`f`関数は呼び出しごとに異なる値を返し、かつ`b`という共有状態を変更する副作用を持ちます。

2.  **最初のテストケース (`x, y, z = f(), f(), f()`):**
    ```go
    // this fails on 6g: apparently it rewrites
    // the list into
    //	z = f();
    //	y = f();
    //	x = f();
    // so that the values come out backward.
    x, y, z = f(), f(), f();
    if x != 1 || y != 2 || z != 3 {
        println("xyz: expected 1 2 3 got", x, y, z);
        ok = false;
    }
    ```
    `b`の初期値は`0`です。
    - Go言語の仕様通りに左から右へ評価される場合:
        - 1回目の`f()`: `b`は`-1`になり、`1`を返す。この値が`x`に代入される。
        - 2回目の`f()`: `b`は`-2`になり、`2`を返す。この値が`y`に代入される。
        - 3回目の`f()`: `b`は`-3`になり、`3`を返す。この値が`z`に代入される。
        結果: `x=1, y=2, z=3`
    - `6g`のバグにより逆順で評価される場合（`z=f(); y=f(); x=f();`）:
        - 1回目の`f()` (for `z`): `b`は`-1`になり、`1`を返す。この値が`z`に代入される。
        - 2回目の`f()` (for `y`): `b`は`-2`になり、`2`を返す。この値が`y`に代入される。
        - 3回目の`f()` (for `x`): `b`は`-3`になり、`3`を返す。この値が`x`に代入される。
        結果: `x=3, y=2, z=1`
    テストコードは`x != 1 || y != 2 || z != 3`をチェックしており、バグがある場合はこの条件が真となり、エラーメッセージが出力されます。

3.  **2番目のテストケース (`a, b, c = f(), f(), f()`):**
    ```go
    // this fails on 6g too.  one of the function calls
    // happens after assigning to b.
    a, b, c = f(), f(), f();
    if a != 4 || b != 5 || c != 6 {
        println("abc: expected 4 5 6 got", a, b, c);
        ok = false;
    }
    ```
    最初のテストケースの後、`b`の値は`-3`になっています。
    - Go言語の仕様通りに左から右へ評価される場合:
        - 1回目の`f()`: `b`は`-4`になり、`4`を返す。この値が`a`に代入される。
        - 2回目の`f()`: `b`は`-5`になり、`5`を返す。この値が`b`に代入される。
        - 3回目の`f()`: `b`は`-6`になり、`6`を返す。この値が`c`に代入される。
        結果: `a=4, b=5, c=6`
    - `6g`のバグにより逆順で評価される場合、かつ`b`への代入が関数呼び出しの後に発生するという問題も考慮すると、さらに複雑な結果になります。テストコードのコメントにある`abc: expected 4 5 6 got -4 4 4`という出力は、このバグの具体的な挙動を示しています。特に、`b`が右辺の関数呼び出しの評価中に変更され、その変更が左辺の`b`への代入に影響を与えるという、より深い問題を示唆しています。

このテストケースは、Goコンパイラが並行代入のセマンティクスを正しく実装していることを保証するために不可欠なものです。

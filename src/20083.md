## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）のパフォーマンス改善を目的としています。特に、`go.benchmarks/garbage` ベンチマークにおいて、`GOMAXPROCS=16` の設定下で顕著な改善が見られます。

コミットメッセージに示されているベンチマーク結果は以下の通りです。

*   **time (ns/op)**: 1392254 -> 1353170 (-2.81%) - オペレーションあたりの実行時間が短縮。
*   **cputime**: 21995751 -> 21373999 (-2.83%) - CPU時間が短縮。
*   **gc-pause-one**: 15044812 -> 13050524 (-13.26%) - 単一のGCポーズ時間が大幅に短縮。
*   **gc-pause-total**: 213636 -> 185317 (-13.26%) - GCポーズの合計時間が大幅に短縮。

これらの結果から、GCのポーズ時間、特に単一のポーズ時間が大幅に削減されていることがわかります。これは、GoのGCが並行処理中にオブジェクトをマークする際の競合を減らすことで達成されたと考えられます。GCポーズ時間の削減は、アプリケーションのレイテンシを低減し、全体的な応答性を向上させる上で非常に重要です。

GoのGCは、Stop-The-World (STW) フェーズを最小限に抑えるように設計されていますが、マーキングフェーズの一部では、オブジェクトのマークビットを更新する際に同期が必要となる場合があります。この同期がボトルネックとなり、GCポーズ時間を増加させる可能性があります。このコミットは、特定の条件下で非アトミック操作を使用してマーク処理を行うことで、このボトルネックを緩和しようとしています。Goランタイムのエンジニアは、GCの内部状態マシンと同期ポイントを考慮し、特定のメモリアクセスがアトミック操作の強い保証を必要としないと判断した場合に、非アトミック操作を利用してGCのパフォーマンスを向上させています。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goのガベージコレクションは、主に「マーク・アンド・スイープ」アルゴリズムをベースにしています。Go 1.5以降、GCは並行かつ低レイテンシになるように設計されており、ほとんどのGC作業はアプリケーションの実行と並行して行われます。

主要なフェーズは以下の通りです。

1.  **マークフェーズ (Mark Phase)**:
    *   GCルート（グローバル変数、スタック上のポインタなど）から到達可能なすべてのオブジェクトを識別し、マークします。
    *   このフェーズは、アプリケーションの実行と並行して行われますが、オブジェクトのマークビットを更新する際には同期が必要になる場合があります。
    *   このコミットが焦点を当てているのは、このマークフェーズにおけるオブジェクトのマーキング処理です。
2.  **マーク終了フェーズ (Mark Termination Phase)**:
    *   短いSTWフェーズで、マークフェーズの完了を待機し、次のフェーズへの移行を準備します。
3.  **スイープフェーズ (Sweep Phase)**:
    *   マークされなかったオブジェクト（到達不可能と判断されたオブジェクト）がメモリから解放されます。
    *   このフェーズも、アプリケーションの実行と並行して行われます。

### GCビットマップ

Goランタイムは、ヒープ上の各オブジェクトの状態を追跡するためにGCビットマップを使用します。このビットマップは、各オブジェクトがマークされているかどうか、ポインタを含んでいるかどうかなどの情報を含んでいます。GCビットマップは、メモリ効率を最大化するために、通常、非常にコンパクトな形式で格納されます。

*   `bitMarked`: オブジェクトがGCによって到達可能とマークされたことを示すビット。
*   `bitMask`: ビットマスク。
*   `bitBoundary`: オブジェクトの境界を示すビット。
*   `gcBits`: GCビットの数。

### アトミック操作と非アトミック操作

*   **アトミック操作 (Atomic Operations)**: 複数のゴルーチン（またはスレッド）が同時に同じメモリ位置にアクセスしようとした場合でも、操作が中断されずに完全に実行されることを保証する操作です。これにより、データ競合を防ぎ、データの整合性を保ちます。Goでは、`sync/atomic` パッケージやランタイム内部の `runtime·casp` (Compare-And-Swap Pointer) のような関数がアトミック操作を提供します。アトミック操作は、通常、非アトミック操作よりもオーバーヘッドが大きくなります。
*   **非アトミック操作 (Non-Atomic Operations)**: 複数のゴルーチンが同時にアクセスした場合に、操作が中断されたり、部分的に実行されたりする可能性がある操作です。これにより、データ競合が発生し、予期せぬ結果やデータの破損につながる可能性があります。しかし、特定の条件下では、非アトミック操作を使用しても安全であり、パフォーマンスを向上させることができます。

このコミットの目的は、特定の安全な条件下で非アトミック操作を利用することで、GCのマーキング処理のオーバーヘッドを削減することです。

## 技術的詳細

このコミットの核心は、GCビットマップにおけるオブジェクトのマーキング処理を最適化することです。GoのGCは並行して動作するため、複数のGCワーカーが同時に異なるオブジェクトをマークしようとする可能性があります。この際、GCビットマップの同じバイトを更新しようとするとデータ競合が発生し、アトミック操作（Compare-And-Swap: CAS）が必要になります。CASは競合が発生しない場合でも一定のオーバーヘッドがあり、競合が発生した場合はリトライループが必要になるため、パフォーマンスのボトルネックとなる可能性があります。

このコミットでは、以下の条件に基づいて、より高速な非アトミック操作でのマーキングを試みます。

1.  **オブジェクトサイズが8バイトより大きい場合**:
    *   この場合、GCビットマップの各バイトは、最大で1つのオブジェクトの情報しか含みません。つまり、1つのバイト内のビットは、単一のオブジェクトのマーク状態のみを表現します。
    *   この条件下では、オブジェクトをマークするために非アトミックなバイトストア（`((uint8*)bitp)[shift/8] = bits8 | (bitMarked<<(shift&7));`）を使用します。
    *   非アトミック操作を使用しても安全な理由は、単一のマークビットのみが変更されるため、ビットマップの破損には繋がらないからです。
    *   ただし、これによりオブジェクトがスキャンキューに二重にエンキューされる可能性があります。しかし、スキャン操作は冪等（何度実行しても同じ結果になる）であるため、これは問題ありません。

2.  **8バイトオブジェクトの場合**:
    *   8バイトオブジェクトの場合、GCビットマップの1バイトが複数のオブジェクト（またはオブジェクトの一部）の情報を保持する可能性があります。
    *   この場合、非アトミックストアを使用できるのは、同じバイト内の他のクアドラプル（4バイト）が既にマークされている場合のみです。
    *   そうでない場合は、引き続きCASループ（`runtime·casp`）を使用してアトミックにマークします。これは、複数のオブジェクトのマークビットが同じバイト内に存在し、非アトミック操作が他のオブジェクトのマーク状態を誤って変更するリスクがあるためです。

この最適化により、GCのマーキング処理におけるアトミック操作の頻度が減り、特に競合が多い環境（`GOMAXPROCS` が高い場合など）でのGCポーズ時間の短縮に貢献します。

## コアとなるコードの解説

変更されたコードブロックは、`scanblock` 関数内でGCビットマップの特定のビットをマークする部分です。

```c
			// Only care about not marked objects.
			if((bits&bitMarked) != 0)
				continue;
			// If obj size is greater than 8, then each byte of GC bitmap
			// contains info for at most one object. In such case we use
			// non-atomic byte store to mark the object. This can lead
			// to double enqueue of the object for scanning, but scanning
			// is an idempotent operation, so it is OK. This cannot lead
			// to bitmap corruption because the single marked bit is the
			// only thing that can change in the byte.
			// For 8-byte objects we use non-atomic store, if the other
			// quadruple is already marked. Otherwise we resort to CAS
			// loop for marking.
			bits8 = xbits>>(shift&~7);
			if((bits8&(bitMask|(bitMask<<gcBits))) != (bitBoundary|(bitBoundary<<gcBits)))
				((uint8*)bitp)[shift/8] = bits8 | (bitMarked<<(shift&7));
			else {
				for(;;) {
					if(runtime·casp((void**)bitp, (void*)xbits, (void*)(xbits|(bitMarked<<shift))))
						break;
					xbits = *bitp;
					bits = (xbits>>shift) & bitMask;
					if((bits&bitMarked) != 0)
						break;
				}
				if((bits&bitMarked) != 0)
					continue;
			}
```

1.  **`if((bits&bitMarked) != 0) continue;`**:
    *   これは既存のロジックで、既にマークされているオブジェクトであればスキップします。

2.  **`bits8 = xbits>>(shift&~7);`**:
    *   `xbits` は現在のビットマップのワード（`*bitp`）の値です。
    *   `shift` は、現在のオブジェクトのマークビットがワード内でどの位置にあるかを示します。
    *   `shift&~7` は、`shift` を8の倍数に切り捨てることで、現在のビットが含まれるバイトの開始位置を計算します。
    *   この行は、現在のオブジェクトのマークビットが含まれるバイト全体を `bits8` に抽出します。

3.  **`if((bits8&(bitMask|(bitMask<<gcBits))) != (bitBoundary|(bitBoundary<<gcBits)))`**:
    *   この条件は、非アトミックなバイトストアを使用できるかどうかを判断するための重要なチェックです。
    *   `bitMask` は、単一のGCビットのマスクです。
    *   `bitMask << gcBits` は、次のGCビットのマスクです。
    *   `bitMask | (bitMask << gcBits)` は、現在のオブジェクトのマークビットと、その隣接するGCビット（通常はポインタ情報など）の両方をカバーするマスクを作成します。
    *   `bitBoundary` は、オブジェクトの境界を示すビットです。
    *   この条件は、`bits8` 内の関連するビットが、オブジェクトの境界を示すビットと一致しない場合に真となります。これは、主にオブジェクトサイズが8バイトより大きい場合、または8バイトオブジェクトで他のクアドラプルが既にマークされている場合に該当します。
    *   この条件が真の場合、GCビットマップのこのバイトは、現在のオブジェクトのマークビットのみを安全に非アトミックに更新できることを意味します。

4.  **`((uint8*)bitp)[shift/8] = bits8 | (bitMarked<<(shift&7));`**:
    *   上記の `if` 条件が真の場合に実行されます。
    *   `bitp` は `uintptr*` 型で、GCビットマップのワードへのポインタです。これを `uint8*` にキャストすることで、バイト単位でアクセスできるようにします。
    *   `shift/8` は、`bitp` が指すワードの先頭から何バイト目にアクセスするかを計算します。
    *   `bits8` は、変更前のバイトの値です。
    *   `bitMarked<<(shift&7)` は、`bitMarked` を現在のバイト内の正しい位置にシフトします。`shift&7` は、バイト内のビット位置を計算します。
    *   この行は、`bits8` に `bitMarked` をOR演算で追加し、その結果を非アトミックにGCビットマップの対応するバイトに書き込みます。
    *   コメントにあるように、これによりオブジェクトが二重にスキャンキューにエンキューされる可能性がありますが、スキャン操作は冪等であるため問題ありません。また、単一のマークビットのみが変更されるため、ビットマップの破損には繋がりません。

5.  **`else { ... }` ブロック**:
    *   上記の `if` 条件が偽の場合に実行されます。これは主に、8バイトオブジェクトで、同じバイト内の他のクアドラプルがまだマークされていない場合です。
    *   この場合、非アトミック操作は安全ではないため、CASループにフォールバックします。
    *   **`for(;;) { ... }`**: 無限ループで、アトミックなマーク操作が成功するまで繰り返されます。
    *   **`if(runtime·casp((void**)bitp, (void*)xbits, (void*)(xbits|(bitMarked<<shift)))) break;`**:
        *   `runtime·casp` は、Compare-And-Swap Pointer の略で、アトミックな比較と交換操作を行います。
        *   `bitp` が指すメモリ位置の値が `xbits` と等しい場合、その値を `xbits|(bitMarked<<shift)` に更新し、真を返します。そうでない場合、偽を返します。
        *   操作が成功した場合（真を返した場合）、ループを抜けます。
    *   **`xbits = *bitp;`**: CASが失敗した場合、現在の `bitp` の値を再読み込みし、`xbits` を更新します。これは、他のゴルーチンが値を変更した可能性があるためです。
    *   **`bits = (xbits>>shift) & bitMask;`**: 更新された `xbits` から、現在のオブジェクトのマークビットを再抽出します。
    *   **`if((bits&bitMarked) != 0) break;`**: 再読み込みした結果、既にオブジェクトがマークされていた場合もループを抜けます。これは、他のゴルーチンが先にマークを完了した可能性があるためです。
    *   このCASループは、複数のゴルーチンが同時に同じビットをマークしようとした場合のデータ競合を安全に解決します。

この変更により、GCのマーキング処理におけるアトミック操作の頻度が減り、特に競合が多い環境（`GOMAXPROCS` が高い場合など）でのパフォーマンスが向上します。

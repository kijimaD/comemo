## 元コミット内容

このコミットは、`cmd/go` がGitサブモジュールをフェッチする際の不具合を修正します。GitHubユーザー `@toxeus` が提供したテストケースに基づいて修正が行われました。この修正は、Issue #12612 を解決します。

## 変更の背景

Goの `go get` コマンドは、指定されたパッケージのソースコードをダウンロードし、依存関係を解決する役割を担っています。このプロセスにおいて、Gitリポジトリがサブモジュールを含んでいる場合、`go get` はそれらのサブモジュールも適切に初期化し、更新する必要があります。

以前の実装では、`go get` がGitサブモジュールを更新する際に、`git submodule update --init --recursive` コマンドの実行方法に問題がありました。具体的には、`--git-dir={dir}/.git` オプションを使用してGitリポジトリのルートディレクトリを指定しようとしていましたが、これは `git submodule update` コマンドに対しては不適切な指定方法でした。`--git-dir` は通常、Gitコマンドが使用する `.git` ディレクトリのパスを指定するために使われますが、`submodule update` のコンテキストでは、コマンドを実行する作業ディレクトリを指定する必要があります。

この誤ったコマンドの組み立てにより、`go get` がサブモジュールを含むリポジトリをフェッチしようとした際に、サブモジュールが正しく初期化または更新されず、ビルドエラーや依存関係の解決失敗といった問題が発生していました。Issue #12612 はこの問題を報告しており、このコミットはその解決を目的としています。

## 前提知識の解説

### Gitサブモジュール

Gitサブモジュールは、あるGitリポジトリ内に別のGitリポジトリを埋め込む機能です。これにより、プロジェクトは外部の依存関係を特定のコミットに固定し、メインリポジトリの一部として管理できます。サブモジュールを使用する主な理由は以下の通りです。

*   **依存関係の管理**: 外部ライブラリやコンポーネントをプロジェクトに含める際に、そのバージョンを厳密に管理できます。
*   **モジュール性**: 大規模なプロジェクトを複数の独立したリポジトリに分割し、それぞれを個別に開発・管理しながら、メインプロジェクトで統合できます。
*   **コードの再利用**: 共通のコードベースを複数のプロジェクトで共有する際に便利です。

サブモジュールを含むリポジトリをクローンした後、サブモジュール自体は自動的にはクローンされません。サブモジュールを初期化し、その内容を取得するには、以下のコマンドを実行する必要があります。

```bash
git submodule init
git submodule update
```

または、再帰的にすべてのサブモジュールを初期化・更新するには、

```bash
git submodule update --init --recursive
```

を使用します。

### `git -C <path> <command>`

`git -C <path> <command>` は、指定された `<path>` をカレントワーキングディレクトリとして `<command>` を実行するためのGitのオプションです。これは、現在のディレクトリを変更せずに、別のディレクトリでGitコマンドを実行したい場合に非常に便利です。

例えば、`/path/to/repo` というリポジトリがあり、現在のディレクトリが `/home/user` だとします。このとき、`/path/to/repo` 内で `git status` を実行したい場合、通常は `cd /path/to/repo && git status` としますが、`-C` オプションを使えば `git -C /path/to/repo status` と実行できます。

このオプションは、特にスクリプトや自動化されたプロセスで、複数のGitリポジトリを扱う際に、ディレクトリの切り替えを減らし、コードを簡潔にするのに役立ちます。

## 技術的詳細

このコミットの核心は、`cmd/go` がGitサブモジュールを処理する際に使用するGitコマンドの修正です。

`src/cmd/go/vcs.go` ファイルは、Goコマンドが様々なバージョン管理システム（VCS）と連携するためのロジックを含んでいます。このファイル内で、Gitに関する設定が `vcsGit` 構造体として定義されており、リポジトリの作成 (`createCmd`) やダウンロード (`downloadCmd`) に使用されるコマンドテンプレートが格納されています。

修正前の `createCmd` の定義は以下のようになっていました。

```go
createCmd:   []string{"clone {repo} {dir}", "--git-dir={dir}/.git submodule update --init --recursive"},
```

ここで、`{repo}` はリモートリポジトリのURL、`{dir}` はローカルにクローンするディレクトリのパスに置換されます。
問題は2番目のコマンド文字列 `--git-dir={dir}/.git submodule update --init --recursive` にありました。`git submodule update` コマンドは、サブモジュールを更新する対象のリポジトリのワーキングツリーがカレントディレクトリであると期待します。しかし、`--git-dir` オプションは、Gitリポジトリの `.git` ディレクトリの場所を指定するものであり、コマンドを実行するワーキングディレクトリを指定するものではありません。このため、`git submodule update` は正しいコンテキストで実行されず、サブモジュールの更新に失敗していました。

このコミットでは、この誤ったオプション指定を修正し、代わりに `git -C {dir} submodule update --init --recursive` という形式に変更しました。

```go
createCmd:   []string{"clone {repo} {dir}", "-C {dir} submodule update --init --recursive"},
```

この変更により、`git submodule update --init --recursive` コマンドは、`{dir}` で指定されたディレクトリをカレントワーキングディレクトリとして実行されるようになります。これにより、サブモジュールが正しく初期化され、その内容がフェッチされることが保証されます。

また、この修正を検証するために、`src/cmd/go/vendor_test.go` に `TestGetSubmodules` という新しいテストケースが追加されました。このテストは、サブモジュールを含む特定のGitHubリポジトリ (`github.com/rsc/go-get-issue-12612`) を `go get` で取得し、サブモジュールが正しくフェッチされることを確認します。これにより、将来的に同様の回帰バグが発生するのを防ぐことができます。

## コアとなるコードの解説

### `src/cmd/go/vcs.go` の変更

`vcsGit` 構造体の `createCmd` フィールドは、Gitリポジトリをクローンする際に実行される一連のコマンドを定義しています。このフィールドは文字列のスライスであり、各文字列が独立したコマンドを表します。

変更前:
`createCmd: []string{"clone {repo} {dir}", "--git-dir={dir}/.git submodule update --init --recursive"},`

この行では、2つのコマンドが定義されています。
1.  `clone {repo} {dir}`: リモートリポジトリをローカルディレクトリにクローンします。
2.  `--git-dir={dir}/.git submodule update --init --recursive`: この部分が問題でした。`git` コマンドの前に `--git-dir` オプションが直接指定されていますが、これは `git submodule update` コマンドの実行コンテキストを正しく設定しませんでした。`submodule update` は、そのコマンドが実行されるカレントディレクトリに `.git` ディレクトリが存在することを期待するか、または `-C` オプションでワーキングディレクトリが明示的に指定されることを期待します。

変更後:
`createCmd: []string{"clone {repo} {dir}", "-C {dir} submodule update --init --recursive"},`

変更後の2番目のコマンドは `"-C {dir} submodule update --init --recursive"` となっています。
*   `-C {dir}`: これはGitコマンドのグローバルオプションで、続くGitコマンドを `{dir}` で指定されたパスをカレントワーキングディレクトリとして実行するように指示します。
*   `submodule update --init --recursive`: このコマンドは、指定されたワーキングディレクトリ内でサブモジュールを初期化し、再帰的に更新します。

この修正により、`go get` がリポジトリをクローンした後、そのクローンされたリポジトリのディレクトリ内で `git submodule update` コマンドが正しく実行されるようになり、サブモジュールのフェッチが成功するようになりました。

### `src/cmd/go/vendor_test.go` の変更

`TestGetSubmodules` という新しいテスト関数が追加されました。
*   `testenv.MustHaveExternalNetwork(t)`: このテストが外部ネットワーク接続を必要とすることを示します。サブモジュールをフェッチするためには、GitHubなどのリモートリポジトリにアクセスする必要があるためです。
*   `tg := testgo(t)`: テストヘルパーを初期化します。
*   `defer tg.cleanup()`: テスト終了後に一時ディレクトリなどをクリーンアップします。
*   `tg.makeTempdir()`: 一時ディレクトリを作成します。
*   `tg.setenv("GOPATH", tg.path("."))`: `GOPATH` 環境変数を一時ディレクトリに設定します。
*   `tg.setenv("GO15VENDOREXPERIMENT", "1")`: Go 1.5のベンダー実験機能を有効にします。これは、このコミットが作成された時期のGoのバージョンに関連する可能性があります。
*   `tg.run("get", "-d", "github.com/rsc/go-get-issue-12612")`: `go get -d` コマンドを実行して、サブモジュールを含むテストリポジトリをダウンロードします。`-d` オプションは、依存関係をダウンロードするだけでビルドは行わないことを意味します。
*   `tg.run("get", "-u", "-d", "github.com/rsc/go-get-issue-12612")`: `go get -u -d` コマンドを実行して、サブモジュールを含むテストリポジトリを更新します。`-u` オプションは、依存関係を強制的に更新することを意味します。

このテストは、`go get` がサブモジュールを含むリポジトリをダウンロードおよび更新する際に、エラーが発生しないことを確認することで、修正が正しく機能していることを検証します。

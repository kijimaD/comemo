## 変更の背景

このコミットの主な背景は、Go言語における依存関係管理の進化、特に**ベンダーディレクトリ（vendor directory）**の導入です。Go 1.5（2015年8月リリース）で実験的に導入され、Go 1.6でデフォルトで有効になったベンダー機能は、プロジェクトが依存する外部パッケージのコピーをプロジェクト自身の`vendor/`ディレクトリ内に保持することを可能にしました。

それ以前のGoでは、すべての外部パッケージは`GOPATH`にインストールされ、グローバルに共有されていました。この方式は、異なるプロジェクトが同じパッケージの異なるバージョンに依存する場合に問題を引き起こす可能性がありました（依存関係の地獄）。また、ビルドの再現性や、ネットワーク接続なしでのビルドが困難であるという課題もありました。

ベンダー機能の導入により、各プロジェクトは自身の依存関係を分離して管理できるようになりました。しかし、この新しいアプローチには、コンパイラがどのようにインポートパスを解決するかという課題が伴いました。例えば、`github.com/foo/bar`というパッケージを`vendor/github.com/foo/bar`に配置した場合、ソースコード内の`import "github.com/foo/bar"`という記述を、コンパイラが`vendor/github.com/foo/bar`として解釈する必要があります。

`-importmap`オプションは、このインポートパスのリマップをコンパイラレベルで実現するために導入されました。`go`コマンドの`-vendor`フラグが有効な場合、`go`コマンドは内部的にこの`-importmap`オプションをコンパイラに渡し、`vendor/`ディレクトリ内のパッケージへのインポートを適切に解決するように指示します。これにより、開発者はソースコードを変更することなく、ベンダーパッケージを利用できるようになりました。

## 前提知識の解説

### Go言語のパッケージとインポートパス

Go言語では、コードはパッケージにまとめられ、`import`ステートメントを使って他のパッケージを参照します。インポートパスは、通常、パッケージのソースコードが配置されているリポジトリのパス（例: `github.com/user/repo/package`）に対応します。Goツールチェインは、`GOPATH`環境変数で指定されたワークスペース内でこれらのパスを解決し、対応するパッケージを見つけます。

### GOPATH

`GOPATH`は、Goのソースコード、コンパイル済みパッケージ、実行可能バイナリが配置されるワークスペースのルートディレクトリを指定する環境変数です。Go 1.11でGo Modulesが導入されるまでは、Goプロジェクトのビルドにおいて中心的な役割を担っていました。`GOPATH`内の`src`ディレクトリには、外部パッケージや自身のプロジェクトのソースコードが配置されます。

### ベンダーディレクトリ (vendor directory)

Go 1.5で導入されたベンダー機能は、プロジェクトのルートディレクトリ直下に`vendor/`という特別なディレクトリを作成し、その中にプロジェクトが依存する外部パッケージのコピーを配置する仕組みです。これにより、各プロジェクトが独自の依存関係セットを持つことができ、依存関係の衝突を避け、ビルドの再現性を高めることができます。

`go`コマンドが`-vendor`フラグ（Go 1.6以降はデフォルトで有効）付きで実行されると、インポートパスの解決順序が変更されます。具体的には、`GOPATH`を検索する前に、まず現在のプロジェクトの`vendor/`ディレクトリ内を検索するようになります。この検索ロジックをコンパイラに伝えるために、`-importmap`のようなメカニズムが必要となります。

### Goコンパイラ (`cmd/compile`)

`cmd/compile`は、Go言語のソースコードをコンパイルして実行可能なバイナリやパッケージアーカイブを生成するGoツールチェインの一部です。Goのビルドプロセスにおいて中心的な役割を担い、インポートパスの解決、型チェック、コード生成などを行います。

## 技術的詳細

このコミットは、Goコンパイラがインポートパスを解決するメカニズムに、動的なリマップ機能を追加します。

1.  **`-importmap`フラグの追加**:
    `src/cmd/compile/internal/gc/lex.go`の`Main`関数内で、`obj.Flagfn1`を使って`-importmap`という新しいコマンドラインフラグが登録されます。このフラグは`old=new`形式の引数を受け取り、`addImportMap`関数がその処理を担当します。

2.  **インポートマップの管理**:
    `lex.go`内に`var importMap = map[string]string{}`というグローバルマップが導入されます。これは、`old`インポートパスを`new`インポートパスにマッピングするための辞書として機能します。

3.  **`addImportMap`関数の実装**:
    この関数は`-importmap`フラグの引数（例: `"github.com/foo/bar=vendor/github.com/foo/bar"`）を解析します。
    -   引数に`=`が1つだけ含まれていることを検証します。
    -   `=`で分割して`source`（元のパス）と`actual`（新しいパス）を抽出します。
    -   `source`と`actual`が空でないことを検証します。
    -   これらの検証をパスした場合、`importMap[source] = actual`としてマッピングを`importMap`に格納します。
    -   不正な引数形式の場合は`log.Fatal`を呼び出してコンパイルを中断します。

4.  **インポートパス解決の変更**:
    `src/cmd/compile/internal/gc/lex.go`の`importfile`関数は、Goソースコード内の`import`ステートメントを処理し、対応するパッケージファイルを見つける役割を担っています。この関数内で、実際のインポートパス解決の前に、`importMap`をチェックするロジックが追加されました。
    -   `if mapped, ok := importMap[path_]; ok { path_ = mapped }`
    -   このコードは、現在解決しようとしているインポートパス`path_`が`importMap`内にキーとして存在するかどうかを確認します。
    -   もし存在すれば（`ok`が`true`）、`path_`は`importMap`に格納されている`mapped`値（新しいパス）に置き換えられます。
    -   これにより、コンパイラは元のインポートパスではなく、リマップされた新しいパスを使ってパッケージを検索するようになります。

このメカニズムにより、`go`コマンドは`-vendor`フラグが有効な場合に、`vendor/`ディレクトリ内のパッケージへのインポートを透過的にコンパイラに指示できるようになり、ソースコードの変更なしにベンダーパッケージを利用するGoの依存関係管理戦略をサポートします。

    -   これにより、コンパイラは、例えば`import "github.com/foo/bar"`という記述を、内部的には`import "vendor/github.com/foo/bar"`として扱い、`vendor/`ディレクトリ内のパッケージを正しく参照できるようになります。

    -   `source`と`actual`が空でないことを検証します。
    -   これらの検証をパスした場合、`importMap[source] = actual`としてマッピングを`importMap`に格納します。
    -   不正な引数形式の場合は`log.Fatal`を呼び出してコンパイルを中断します。

4.  **インポートパス解決の変更**:
    `src/cmd/compile/internal/gc/lex.go`の`importfile`関数は、Goソースコード内の`import`ステートメントを処理し、対応するパッケージファイルを見つける役割を担っています。この関数内で、実際のインポートパス解決の前に、`importMap`をチェックするロジックが追加されました。
    -   `if mapped, ok := importMap[path_]; ok { path_ = mapped }`
    -   このコードは、現在解決しようとしているインポートパス`path_`が`importMap`内にキーとして存在するかどうかを確認します。
    -   もし存在すれば（`ok`が`true`）、`path_`は`importMap`に格納されている`mapped`値（新しいパス）に置き換えられます。
    -   これにより、コンパイラは元のインポートパスではなく、リマップされた新しいパスを使ってパッケージを検索するようになります。

このメカニズムにより、Goコンパイラは、`go`コマンドが提供するベンダー機能と連携し、プロジェクトの依存関係管理をより柔軟かつ堅牢に行うための基盤を提供しました。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラがインポートパスを解決する際に、外部から与えられたマッピングルールを適用できるようにした点です。

1.  **フラグの登録とハンドラ**:
    `obj.Flagfn1("importmap", ..., addImportMap)`は、Goコンパイラのコマンドライン引数パーサーに`-importmap`という新しいフラグを登録しています。`Flagfn1`は、引数を1つ取る関数（この場合は`addImportMap`）をフラグのハンドラとして登録するために使われます。これにより、コンパイラが起動され、`-importmap old=new`のような引数が渡されると、`addImportMap`関数が`"old=new"`という文字列を引数として呼び出されます。

2.  **`importMap`の役割**:
    `var importMap = map[string]string{}`は、`old`インポートパスを`new`インポートパスに変換するためのルックアップテーブルです。`-importmap`フラグが複数回指定された場合、`addImportMap`関数が繰り返し呼び出され、このマップに複数のエントリが追加されます。

3.  **`addImportMap`のロジック**:
    この関数は、引数文字列が`source=actual`の形式であることを厳密にチェックします。`=`が1つだけ存在し、`source`と`actual`がどちらも空でないことを確認します。これにより、不正な形式の引数によるコンパイラの誤動作を防ぎます。検証が成功すると、`importMap[source] = actual`という形でマッピングが保存されます。

4.  **`importfile`でのパスリマップ**:
    `importfile`関数は、Goソースファイル内の`import "path"`ステートメントを処理する際に呼び出されます。この関数内で、元のインポートパス`path_`が`importMap`に存在するかどうかが`if mapped, ok := importMap[path_]; ok`というGoの慣用的な方法でチェックされます。
    -   `ok`が`true`の場合、つまり`path_`に対するマッピングが存在する場合、`path_`は`mapped`（`importMap`に格納されている新しいパス）に更新されます。
    -   これにより、コンパイラは、例えば`import "github.com/foo/bar"`という記述を、内部的には`import "vendor/github.com/foo/bar"`として扱い、`vendor/`ディレクトリ内のパッケージを正しく参照できるようになります。

この変更により、Goコンパイラは、`go`コマンドが提供するベンダー機能と連携し、プロジェクトの依存関係管理をより柔軟かつ堅牢に行うための基盤を提供しました。

# [インデックス 25891] ファイルの概要

このコミットは、Go言語の`net/http`パッケージにおけるHTTP/2クライアントの挙動に関する変更です。具体的には、HTTP/2のサポートが`http.DefaultTransport`だけでなく、開発者が明示的に作成したすべての`http.Transport`インスタンスで自動的に有効になるように修正されました。

変更されたファイルは以下の通りです。

*   `src/net/http/transport.go`: `http.Transport`の主要なロジックが含まれるファイル。HTTP/2の初期化ロジックが変更されました。
*   `src/net/http/transport_test.go`: `http.Transport`のテストファイル。HTTP/2の自動有効化を検証する新しいテストが追加されました。

## 元コミット内容

```
net/http: enable HTTP/2 on all Transports, not just the DefaultTransport
    
This mirrors the same behavior and API from the server code to the
client side: if TLSNextProto is nil, HTTP/2 is on by default for
both. If it's non-nil, the user was trying to do something fancy and
step out of their way.

Updates #6891
```

## 変更の背景

このコミットの主な背景は、Goの`net/http`パッケージにおけるHTTP/2のサポートを、より一貫性のある、かつ期待される挙動にすることでした。以前は、HTTP/2のサポートは主にグローバルな`http.DefaultTransport`インスタンスに対してのみ自動的に有効化されていました。しかし、開発者が独自の`http.Transport`インスタンスを作成して使用する場合、HTTP/2の恩恵を受けるためには手動で設定を行う必要がありました。

この挙動は、サーバーサイドのHTTP/2サポートのAPIと一貫性がありませんでした。サーバーサイドでは、`http.Server`の`TLSNextProto`フィールドが`nil`の場合、HTTP/2は自動的に有効になります。クライアントサイドでも同様のロジックを適用することで、開発者が明示的にHTTP/2を無効にしない限り、デフォルトで最新のプロトコルが利用されるようにすることが目的でした。

また、この変更はIssue #6891に関連しており、より広範なHTTP/2の改善と普及を目指すGoプロジェクトの取り組みの一環です。ユーザーがカスタムの`Transport`を使用する際にも、特別な設定なしにHTTP/2のパフォーマンス上の利点（多重化、ヘッダー圧縮など）を享受できるようにすることが、この変更の動機となっています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

### Goの`net/http`パッケージ

Go言語の標準ライブラリである`net/http`パッケージは、HTTPクライアントとサーバーの実装を提供します。

*   **HTTPクライアント**: `http.Client`構造体を通じてHTTPリクエストを送信し、レスポンスを受信します。`http.Client`は内部的に`http.RoundTripper`インターフェースを実装するオブジェクト（通常は`http.Transport`）を使用して実際のネットワーク通信を行います。
*   **HTTPサーバー**: `http.Server`構造体を通じてHTTPリクエストを処理し、レスポンスを返します。

### HTTP/2

HTTP/2は、HTTP/1.1の後継となるプロトコルで、ウェブのパフォーマンスを向上させるために設計されました。主な特徴は以下の通りです。

*   **多重化 (Multiplexing)**: 単一のTCP接続上で複数のリクエストとレスポンスを同時に送受信できます。これにより、HTTP/1.1で発生していたヘッドオブラインブロッキングの問題が解消されます。
*   **ヘッダー圧縮 (Header Compression)**: HPACKという圧縮アルゴリズムを使用してHTTPヘッダーを効率的に圧縮し、帯域幅の使用量を削減します。
*   **サーバープッシュ (Server Push)**: サーバーがクライアントからのリクエストなしに、将来必要になるであろうリソースを事前にクライアントに送信できます。
*   **バイナリフレーミング (Binary Framing)**: HTTP/1.1のテキストベースのプロトコルとは異なり、HTTP/2はバイナリプロトコルであり、解析が高速でエラー耐性があります。

### `http.Transport`

`http.Transport`は、`net/http`パッケージにおけるHTTPクライアントの低レベルな実装を担う構造体です。ネットワーク接続の確立、TLSハンドシェイク、プロキシ設定、接続の再利用（コネクションプーリング）、タイムアウト設定など、多くの詳細な挙動を制御します。

*   **`RoundTrip`メソッド**: `http.Transport`の主要なメソッドで、`http.Request`を受け取り、`http.Response`を返します。このメソッド内で実際のネットワーク通信が行われます。

### `http.DefaultTransport`

`http.DefaultTransport`は、`net/http`パッケージが提供するグローバルな`http.Transport`インスタンスです。`http.Client`が明示的に`Transport`を設定されていない場合、この`DefaultTransport`が使用されます。多くのシンプルなHTTPクライアント操作では、このデフォルトの`Transport`が暗黙的に利用されます。

### `TLSNextProto`フィールド

`http.Transport`および`http.Server`構造体には`TLSNextProto`というフィールドがあります。これは`map[string]func(authority string, c *tls.Conn) RoundTripper`（サーバー側では`map[string]func(*tls.Conn, http.Handler)`）という型を持ちます。

*   **ALPN (Application-Layer Protocol Negotiation)**: TLSハンドシェイクの一部として、クライアントとサーバーがどのアプリケーションプロトコル（例: `h2` for HTTP/2, `http/1.1` for HTTP/1.1）を使用するかをネゴシエートする仕組みです。
*   `TLSNextProto`マップのキーはALPNプロトコル名（例: "h2"）であり、値はそのプロトコルが選択されたときに使用される`RoundTripper`（クライアント側）または`Handler`（サーバー側）を返す関数です。
*   このフィールドが`nil`の場合、Goの`net/http`はデフォルトのALPNプロトコルネゴシエーション（HTTP/2を含む）を自動的に処理します。開発者がこのフィールドを非`nil`に設定した場合、それは通常、カスタムのプロトコルハンドリングを行いたいという意図を示します。

### `sync.Once`

`sync.Once`はGo言語の標準ライブラリ`sync`パッケージに含まれる型で、特定の関数が一度だけ実行されることを保証します。これは、リソースの初期化や設定など、アプリケーションのライフサイクルで一度だけ実行されるべき処理に非常に役立ちます。`Do`メソッドを呼び出すことで、引数として渡された関数が一度だけ実行されます。

### `GODEBUG`環境変数

`GODEBUG`環境変数は、Goランタイムのデバッグオプションを設定するために使用されます。このコミットでは`h2client=0`というオプションが言及されており、これはHTTP/2クライアントの機能を無効にするために使用されます。

## 技術的詳細

このコミットの核心は、HTTP/2の自動有効化ロジックを`http.DefaultTransport`からすべての`http.Transport`インスタンスに拡張することです。

以前のGoのバージョンでは、`http.DefaultTransport`の初期化時に`init()`関数内で`http2ConfigureTransport`が呼び出され、HTTP/2が有効化されていました。しかし、これは`DefaultTransport`に限定されており、ユーザーが独自の`Transport`を作成した場合には適用されませんでした。

このコミットでは、以下の変更によってこの問題を解決しています。

1.  **`init()`関数の削除**: `http.DefaultTransport`にHTTP/2を設定していた`init()`関数が削除されました。これにより、グローバルな初期化時にHTTP/2が有効化されるという特殊なケースがなくなりました。
2.  **`Transport.RoundTrip`内での遅延初期化**: `http.Transport`の`RoundTrip`メソッドの冒頭で、`t.nextProtoOnce.Do(t.onceSetNextProtoDefaults)`が呼び出されるようになりました。
    *   `RoundTrip`メソッドは、`Transport`インスタンスが実際にHTTPリクエストを処理する際に最初に呼び出されるメソッドです。
    *   `sync.Once`の`Do`メソッドを使用することで、`onceSetNextProtoDefaults`メソッドがその`Transport`インスタンスのライフサイクルで一度だけ実行されることが保証されます。これにより、HTTP/2の初期化が、その`Transport`が初めて使用されるタイミングで遅延して行われるようになります。
3.  **`onceSetNextProtoDefaults`メソッドの導入**: この新しいメソッドは、HTTP/2を有効化するためのロジックを含んでいます。
    *   まず、`GODEBUG`環境変数に`h2client=0`が含まれている場合、HTTP/2の有効化をスキップします。これは、ユーザーが明示的にHTTP/2クライアントを無効にしたい場合のオプションを提供します。
    *   次に、`t.TLSNextProto`が`nil`でない場合も、HTTP/2の有効化をスキップします。これは、ユーザーが`TLSNextProto`を明示的に設定している場合、それはカスタムのプロトコルハンドリングを意図していると解釈し、自動的なHTTP/2の有効化がその意図を妨げないようにするためです。
    *   上記の条件をクリアした場合、`http2ConfigureTransport(t)`が呼び出され、現在の`Transport`インスタンスに対してHTTP/2サポートが設定されます。エラーが発生した場合はログに出力されます。

この変更により、`http.Transport`のインスタンスが作成された直後ではなく、そのインスタンスが初めてリクエストを処理する際にHTTP/2の初期化が行われるようになります。また、`TLSNextProto`が`nil`である限り、すべての`Transport`でHTTP/2が自動的に有効になるため、サーバーサイドの挙動との一貫性が保たれます。

## コアとなるコードの解説

### `src/net/http/transport.go`の変更点

1.  **`init()`関数の削除**:
    以前は、`DefaultTransport`が初期化される際に、`init()`関数内で`http2ConfigureTransport`が呼び出され、HTTP/2が有効化されていました。この`init()`関数はプログラム起動時に一度だけ実行されるため、`DefaultTransport`以外の`Transport`インスタンスにはHTTP/2が自動的に適用されませんでした。このコミットでは、この`init()`関数を削除し、HTTP/2の有効化ロジックをより汎用的な場所へ移動させました。

2.  **`Transport`構造体への`nextProtoOnce`フィールドの追加**:
    `type Transport struct { ... nextProtoOnce sync.Once ... }`
    `sync.Once`型のフィールド`nextProtoOnce`が`Transport`構造体に追加されました。これは、各`Transport`インスタンスに対して`onceSetNextProtoDefaults`メソッドが一度だけ実行されることを保証するために使用されます。

3.  **`onceSetNextProtoDefaults`メソッドの追加**:
    この新しいメソッドは、HTTP/2を有効化するための実際のロジックを含んでいます。
    *   `if strings.Contains(os.Getenv("GODEBUG"), "h2client=0")`: `GODEBUG`環境変数に`h2client=0`が設定されている場合、HTTP/2クライアントのサポートは無効化されるため、処理を中断します。
    *   `if t.TLSNextProto != nil`: `Transport`インスタンスの`TLSNextProto`フィールドが既に設定されている場合、それはユーザーがカスタムのプロトコルハンドリングを意図していると見なされるため、自動的なHTTP/2の有効化は行いません。
    *   `err := http2ConfigureTransport(t)`: 上記の条件を満たさない場合、`http2ConfigureTransport`関数が呼び出され、現在の`Transport`インスタンス`t`に対してHTTP/2サポートが設定されます。この関数は、`TLSNextProto`マップにHTTP/2 (`h2`) のエントリを追加し、HTTP/2固有の設定を行います。
    *   `if err != nil { log.Printf(...) }`: `http2ConfigureTransport`の呼び出しでエラーが発生した場合、そのエラーがログに出力されます。

4.  **`Transport.RoundTrip`メソッドの変更**:
    `func (t *Transport) RoundTrip(req *Request) (*Response, error) { ... t.nextProtoOnce.Do(t.onceSetNextProtoDefaults) ... }`
    `RoundTrip`メソッドの冒頭で`t.nextProtoOnce.Do(t.onceSetNextProtoDefaults)`が呼び出されるようになりました。これにより、各`Transport`インスタンスが初めてリクエストを処理する際に、`onceSetNextProtoDefaults`が一度だけ実行され、HTTP/2の自動有効化が遅延して行われるようになります。このアプローチにより、`DefaultTransport`だけでなく、すべての`Transport`インスタンスでHTTP/2が自動的に有効化されるようになりました。

### `src/net/http/transport_test.go`の変更点

1.  **`TestTransportAutomaticHTTP2`テスト関数の追加**:
    この新しいテスト関数は、`Transport`インスタンスにおけるHTTP/2の自動有効化の挙動を検証します。
    *   **ケース1: `TLSNextProto`が`nil`の場合**:
        `tr := &Transport{}`で新しい`Transport`インスタンスを作成し、`RoundTrip`を呼び出します。このとき、`tr.TLSNextProto["h2"]`が`nil`でないこと（つまりHTTP/2が登録されていること）を検証します。これは、`TLSNextProto`が`nil`の場合にHTTP/2が自動的に有効になるという新しい挙動をテストしています。
    *   **ケース2: `TLSNextProto`が非`nil`の場合**:
        `tr = &Transport{TLSNextProto: make(map[string]func(string, *tls.Conn) RoundTripper)}`のように、空ではあるが非`nil`の`TLSNextProto`マップを持つ`Transport`インスタンスを作成します。この場合、`RoundTrip`を呼び出した後でも`tr.TLSNextProto["h2"]`が`nil`であること（つまりHTTP/2が自動的に登録されないこと）を検証します。これは、ユーザーが`TLSNextProto`を明示的に設定している場合に、自動有効化がスキップされるという挙動をテストしています。

これらの変更により、Goの`net/http`クライアントは、サーバーサイドのAPIと同様に、`TLSNextProto`が明示的に設定されていない限り、デフォルトでHTTP/2をサポートするようになり、より使いやすく、一貫性のある挙動を提供するようになりました。

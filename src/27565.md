# [インデックス 27565] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) パスにおける`prove`フェーズの改善に関するものです。具体的には、配列やスライスへのアクセスにおいて、インデックスが非負であることをより効果的に証明できるようになり、結果として不要な境界チェック (bounds check) の削除を促進します。これにより、生成されるバイナリサイズが削減され、特に`pkg/tools/linux_amd64/*`のようなツール群で約5KBのサイズ削減が報告されています。

## 変更の背景

Go言語はメモリ安全性を重視しており、配列やスライスへのアクセス時には必ず境界チェック (bounds check) が行われます。これは、インデックスが有効な範囲内にあることを保証し、プログラムのクラッシュやセキュリティ脆弱性を防ぐための重要なメカニズムです。しかし、多くの場合、プログラマがコードを書く際にインデックスが常に有効であることを論理的に保証していることがあります。例えば、`if 0 <= i && i < len(a)`のような条件文でインデックス`i`の範囲を明示的にチェックしている場合、その後の`a[i]`へのアクセスで再度境界チェックを行うのは冗長です。

Goコンパイラは、このような冗長な境界チェックを排除する「境界チェック除去 (Bounds Check Elimination, BCE)」という最適化を行います。この最適化は、プログラムのSSA形式における`prove`パスで行われます。このコミットの背景には、`if 0 <= i && i < len(a)`のような一般的なパターンにおいて、コンパイラが`i`が非負であることを十分に「証明」できておらず、結果として不要な境界チェックが残ってしまうケースがあったという問題意識があります。この改善により、コンパイラがより多くのケースでインデックスの非負性を認識できるようになり、BCEの適用範囲が広がり、最終的に生成されるバイナリのサイズ削減と実行時性能の向上が期待されます。

## 前提知識の解説

*   **Go言語のメモリ安全性と境界チェック**: Goはメモリ安全な言語であり、配列やスライスへのアクセス時にインデックスが有効範囲内にあるかを常にチェックします。インデックスが範囲外の場合、ランタイムパニックが発生します。これはC/C++のような言語で発生しうるバッファオーバーフローなどの脆弱性を防ぎます。
*   **GoコンパイラのSSA (Static Single Assignment) 形式**: Goコンパイラは、ソースコードを中間表現であるSSA形式に変換します。SSA形式では、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。
*   **`prove`パス**: GoコンパイラのSSAバックエンドにおける最適化パスの一つです。このパスの主な目的は、プログラムの特定の時点である条件が真であることを「証明」することです。例えば、ある変数が非負であること、あるインデックスが特定の範囲内にあることなどを証明します。この証明結果は、境界チェック除去などの他の最適化に利用されます。
*   **`factsTable`**: `prove`パス内で使用されるデータ構造で、プログラムの各時点における変数に関する既知の「事実 (facts)」を記録します。例えば、「変数`i`は0以上である」といった事実が格納されます。
*   **`OpIsInBounds` / `OpIsSliceInBounds`**: GoコンパイラのSSA形式における操作 (Operation) の一種です。これらは、特定のインデックスが配列またはスライスの境界内にあるかどうかをチェックする操作を表します。`prove`パスは、これらの操作が冗長であると判断した場合、それらを削除します。

## 技術的詳細

このコミットの主要な技術的変更点は、`src/cmd/compile/internal/ssa/prove.go`ファイルに`isNonNegative`という新しいヘルパーメソッドが`factsTable`に追加されたことです。

以前は、`simplifyBlock`関数内で`OpIsInBounds`または`OpIsSliceInBounds`操作を処理する際に、インデックスが非負であるかどうかのチェックに`isNonNegative(c.Args[0])`というグローバル関数が直接使用されていました。このグローバル関数は、値のオペレーションタイプ（例: `OpConst64`で定数0以上、`OpLoad`でポインタが非負など）に基づいて非負性を判断する基本的なものでした。

しかし、`factsTable`は、プログラムの制御フロー分析を通じて、より複雑な非負性の事実を推論する能力を持っています。例えば、`if 0 <= i`のような条件文を通過した後、`factsTable`は変数`i`が非負であるという事実を記録できます。

このコミットでは、`simplifyBlock`内の境界チェック最適化ロジックが、新しい`ft.isNonNegative(c.Args[0])`メソッドを使用するように変更されました。この新しいメソッドは以下のロジックで非負性を判断します。

1.  まず、既存の基本的な`isNonNegative(v *Value)`グローバル関数を呼び出します。これにより、値の基本的な特性（例: 定数0以上）から非負性が明らかであればすぐに`true`を返します。
2.  次に、`factsTable`が持つ`limits`情報（変数の最小値と最大値の範囲）をチェックします。
    *   もし`v`に関する`limits`情報が存在し、その最小値 (`l.min`) が0以上であれば、`v`は非負であると判断します。
    *   または、`v`に関する`limits`情報が存在し、その符号なし最大値 (`l.umax`) が`math.MaxInt64`以下であれば、`v`は非負であると判断します。これは、符号なしの最大値が`MaxInt64`以下であるということは、その値が符号付き整数として表現された場合でも非負であることを意味します。

この変更により、`factsTable`が推論した非負性の事実が境界チェック除去の判断に活用されるようになり、`if 0 <= i && i < len(a)`のようなパターンで`i`が非負であることがより確実に証明され、`a[i]`の境界チェックが削除される機会が増加します。

    // isNonNegative returns true if v is known to be non-negative.
    func (ft *factsTable) isNonNegative(v *Value) bool {
        if isNonNegative(v) { // 既存のグローバル関数によるチェック
            return true
        }
        l, has := ft.limits[v.ID] // factsTableのlimits情報を参照

## コアとなるコードの解説

このコミットの核心は、`factsTable`の持つ豊富な情報（特に変数の範囲に関する`limits`）を`isNonNegative`の判断に組み込んだ点です。

新しい`ft.isNonNegative(v *Value)`メソッドは、単に値の型や定数性から非負性を判断するだけでなく、`factsTable`が制御フロー分析を通じて学習した変数の最小値 (`l.min`) を利用します。例えば、`if i >= 0`という条件が真であるブロック内では、`factsTable`は`i`の最小値が0以上であるという事実を記録します。この事実が`ft.isNonNegative`によって参照されることで、`i`が非負であることが「証明」され、その後の`a[i]`のようなアクセスにおける境界チェックが不要と判断されるようになります。

また、`l.umax <= math.MaxInt64`という条件は、符号なしの最大値が符号付き`int64`の最大値を超えない場合、その値は符号付きとして扱っても非負であるということを意味します。これにより、`uint`型から`int`型への変換など、型変換が絡むケースでも非負性を正しく推論できる可能性が広がります。

この改善により、コンパイラはより多くの状況でインデックスの非負性を正確に把握し、結果としてより多くの冗長な境界チェックを削除できるようになります。これは、Goプログラムの実行効率を向上させ、バイナリサイズを削減する上で重要な最適化です。

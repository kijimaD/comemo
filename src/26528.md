# [インデックス 26528] ファイルの概要

このコミットは、Goの`archive/zip`パッケージにおける、ZIP64形式ではないZIPファイルが2³²-1バイトのコンテンツを含む場合の処理に関する回帰バグを修正するものです。具体的には、Go 1.5で導入された変更（CL 18317）によって発生した問題に対処し、特に「42.zip」のような特殊なZIPファイルが正しく扱われるように改善されています。

## 変更の背景

このコミットは、Go 1.5で導入された変更（CL 18317）によって引き起こされた回帰バグを修正するために行われました。このバグは、ZIP64拡張を使用しない（pre-zip64）ZIPファイルにおいて、非圧縮サイズが2³²-1バイト（約4GB）である場合に、`archive/zip`パッケージがファイルを正しく処理できないというものでした。

ZIPファイルフォーマットでは、ファイルサイズやオフセットを32ビット整数で表現します。そのため、最大サイズは2³²-1バイト（約4GB）に制限されます。この制限を超えるファイルを扱うためにZIP64拡張が導入されました。しかし、ZIP64拡張が導入される前の古いZIPファイルや、意図的にZIP64拡張を使用しないファイルでも、非圧縮サイズがこの最大値に達する可能性があります。

特に、悪名高い「42.zip」のようなZIP爆弾は、この2³²-1バイトのファイルサイズを巧みに利用して、非常に小さな圧縮ファイルから膨大な非圧縮データを生成します。Go 1.5の変更により、`archive/zip`パッケージがこのようなファイルを不正なフォーマットとして扱ってしまうようになり、結果として「42.zip」のようなファイルが正しく読み取れなくなるという問題が発生しました。このコミットは、この特定のケースを適切に処理し、Go 1.5以前の動作に戻すことを目的としています。

## 前提知識の解説

### ZIPファイルフォーマットとZIP64

ZIPファイルは、ファイルを圧縮してアーカイブするための一般的なフォーマットです。ZIPファイル内の各エントリ（ファイル）は、ローカルファイルヘッダ、ファイルデータ、データ記述子（オプション）、およびセントラルディレクトリヘッダによって記述されます。

初期のZIPファイルフォーマットでは、ファイルサイズやオフセットを32ビット符号なし整数で表現していました。これにより、個々のファイルの非圧縮サイズ、圧縮サイズ、およびZIPファイル全体のサイズは最大で2³²-1バイト（約4GB）に制限されていました。

この4GBの制限を超えるファイルを扱うために、**ZIP64拡張**が導入されました。ZIP64では、ファイルサイズやオフセットを64ビット整数で表現することで、事実上無限のサイズのファイルを扱えるようになります。ZIP64拡張を使用するファイルは、ローカルファイルヘッダやセントラルディレクトリヘッダに追加のフィールドを持ち、そこに64ビットのサイズ情報が格納されます。

### 2³²-1バイトの特殊性

2³²-1バイトは、32ビット符号なし整数の最大値です。ZIPファイルフォーマットでは、この値は特別な意味を持つことがあります。例えば、非圧縮サイズが2³²-1バイトである場合、それは「サイズが不明である」または「ZIP64拡張で実際のサイズが指定されている」ことを示すプレースホルダーとして使用されることがあります。

このコミットで問題となったのは、ZIP64拡張を使用しない（pre-zip64）ファイルにおいて、非圧縮サイズが実際に2³²-1バイトであるケースです。Go 1.5の変更により、`archive/zip`パッケージは、ZIP64拡張がないにもかかわらず非圧縮サイズが2³²-1バイトであるファイルを、ZIP64拡張が期待されるが欠落している不正なファイルとして扱ってしまいました。

### 42.zip

「42.zip」は、非常に小さな圧縮サイズ（約42KB）でありながら、解凍すると膨大なデータ量（約4.5PB）になることで知られる「ZIP爆弾」の一種です。これは、多層にネストされたZIPファイル構造と、極めて高い圧縮率を持つデータ（例えば、すべてゼロのファイル）を組み合わせることで実現されます。

「42.zip」の最も内側のファイルは、非圧縮サイズが2³²-1バイトのデータを含んでいます。このコミットで修正されたバグは、まさにこのような特殊なファイル、特にZIP64拡張を持たないが非圧縮サイズが2³²-1バイトであるファイルをGoの`archive/zip`パッケージが正しく処理できないというものでした。この修正により、「42.zip」のようなファイルもGoで適切に扱えるようになります。

## 技術的詳細

Go 1.5で導入された変更（CL 18317）により、`archive/zip`パッケージの`readDirectoryHeader`関数は、ZIP64拡張が期待されるにもかかわらず見つからない場合に`ErrFormat`を返すようになりました。これは、ZIP64拡張が必須であるべき状況でそれが欠落している場合に、ZIPファイルが不正であると判断するための妥当なチェックでした。

しかし、この変更は、ZIP64拡張を使用しない（pre-zip64）ZIPファイルで、非圧縮サイズが偶然にも32ビット整数の最大値である2³²-1バイトであるというエッジケースを考慮していませんでした。このようなファイルは、技術的にはZIP64拡張を必要としないにもかかわらず、`readDirectoryHeader`関数内の`needUSize`フラグが`true`のままとなり、結果として`ErrFormat`が返されてしまっていました。

このコミットでは、このロジックを修正し、`needUSize`が`true`であっても、それがZIP64拡張の欠落を意味するわけではない場合があることを考慮に入れています。具体的には、非圧縮サイズが2³²-1バイトであっても、圧縮サイズやヘッダオフセットが2³²-1バイトでない限り（これらが同時に2³²-1バイトであることは非常に稀で、悪意のあるファイルである可能性が高い）、その非圧縮サイズを有効なものとして受け入れるように変更されました。これは、古いZIP32ファイルが可能な限り最大のチャンクに分割された入力を含んでいる可能性や、単に「42.zip」のような悪意のあるファイルである可能性を考慮したものです。

テストコードでは、`ZipTestFile`構造体に`Size`フィールドが追加され、非常に大きなファイル（マルチGB）のテストを効率的に行えるようになりました。これにより、実際のデータ解凍をバイパスして、ヘッダで報告されたサイズのみをチェックすることが可能になります。また、`biggestZipBytes`関数が追加され、ネストされたZIPファイル構造を持つ「42.zip」に似たテストデータが生成されるようになりました。このテストデータは、非圧縮サイズが2³²-1バイトのファイルを含んでおり、今回の修正が正しく機能するかを検証します。

## コアとなるコードの解説

### `src/archive/zip/reader.go`の変更

変更の核心は、`readDirectoryHeader`関数内の条件文です。

変更前:
```go
if needUSize || needCSize || needHeaderOffset {
    return ErrFormat
}
```
このコードは、`needUSize`（非圧縮サイズが32ビットの最大値を超えている、または32ビットの最大値であるためZIP64拡張が必要と判断された場合）または`needCSize`（圧縮サイズが同様の場合）または`needHeaderOffset`（ヘッダオフセットが同様の場合）のいずれかが`true`であれば、ZIP64拡張が欠落していると判断し、`ErrFormat`を返していました。

変更後:
```go
	// Assume that uncompressed size 2³²-1 could plausibly happen in
	// an old zip32 file that was sharding inputs into the largest chunks
	// possible (or is just malicious; search the web for 42.zip).
	// If needUSize is true still, it means we didn't see a zip64 extension.
	// As long as the compressed size is not also 2³²-1 (implausible)
	// and the header is not also 2³²-1 (equally implausible),
	// accept the uncompressed size 2³²-1 as valid.
	// If nothing else, this keeps archive/zip working with 42.zip.
	_ = needUSize

	if needCSize || needHeaderOffset {
		return ErrFormat
	}
```
この変更では、`needUSize`が`true`であること自体は、必ずしもエラーとは見なさないようになりました。コメントにあるように、古いZIP32ファイルでは非圧縮サイズが2³²-1バイトになることがあり得るためです。また、「42.zip」のような特殊なファイルも考慮されています。

重要なのは、`needUSize`が`true`であっても、`needCSize`（圧縮サイズが2³²-1バイト）や`needHeaderOffset`（ヘッダオフセットが2³²-1バイト）が`true`でない限りは、`ErrFormat`を返さないというロジックになった点です。圧縮サイズやヘッダオフセットが同時に2³²-1バイトであることは非常に稀であり、そのような場合はZIP64拡張が必須であると判断するのが妥当です。しかし、非圧縮サイズのみが2³²-1バイトである場合は、ZIP64拡張がない古いZIP32ファイルである可能性を許容するように変更されました。これにより、Go 1.5で導入された回帰バグが修正され、「42.zip」のようなファイルも正しく処理できるようになりました。

`_ = needUSize`という行は、`needUSize`変数が使用されていないというコンパイラ警告を回避するためのものです。この変数は、上記のロジック変更により直接条件式で使用されなくなったため、このような記述が追加されました。

### `src/archive/zip/reader_test.go`の変更

テストコードの変更は、この修正の検証を強化するために重要です。

-   **`ZipTestFile`への`Size`フィールド追加**:
    `Size uint64`フィールドが追加されたことで、テストにおいて非常に大きなファイルの非圧縮サイズを直接指定し、実際の解凍処理を伴わずにサイズ検証のみを行うことが可能になりました。これは、数GBにも及ぶファイルを実際に解凍するテストは非効率的であるため、パフォーマンスと実用性を向上させます。

-   **「big.zip」テストケースの追加**:
    `tests`変数に追加された「big.zip」テストケースは、非圧縮サイズが`1<<32 - 1`（2³²-1バイト）であるファイルを対象としています。このテストケースは、今回の修正が意図した通りに、ZIP64拡張なしで2³²-1バイトの非圧縮サイズを持つファイルを正しく処理できることを確認します。

-   **`readTestFile`内のサイズ処理ロジックの変更**:
    `readTestFile`関数内で、`f.UncompressedSize`が`uint32max`（2³²-1）である場合の処理が改善されました。以前は`f.UncompressedSize64`を無条件に使用していましたが、変更後は`f.UncompressedSize`が`uint32max`でなければその値を使い、`uint32max`であれば`f.UncompressedSize64`を使うという、より堅牢なロジックになりました。また、`f.UncompressedSize`と`f.UncompressedSize64`が一致しない場合にエラーを報告するチェックも追加され、データの一貫性が検証されます。

-   **`ft.Size > 0`による解凍スキップ**:
    `if ft.Content == nil && ft.File == "" && ft.Size > 0`という条件が追加され、`ZipTestFile`で`Size`が指定されている場合は、実際のファイル内容の読み込みと解凍をスキップし、ヘッダから取得したサイズと期待される`ft.Size`が一致するかどうかのみをチェックするようになりました。これにより、巨大なファイルのテストが高速化されます。

-   **`biggestZipBytes`関数の追加**:
    この関数は、ネストされたZIPファイル構造を持つテストデータを生成します。このデータは、最も内側のファイルが2³²-1バイトのゼロデータを含んでおり、ZIP64拡張を使用していません。これは「42.zip」の構造を模倣しており、今回の修正がこのような特殊なZIP爆弾ファイルも正しく扱えることを保証するための重要なテストデータです。

これらのテストの追加と変更により、Goの`archive/zip`パッケージが、ZIP64拡張を使用しないが非圧縮サイズが2³²-1バイトであるという特殊なケースを、より堅牢かつ正確に処理できるようになったことが確認されます。

# [インデックス 25567] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）プロセスにおいて、スタックスパンの解放処理をStop-The-World（STW）フェーズの外で行うように変更するものです。これにより、GCの一時停止時間を短縮し、アプリケーションのレイテンシを改善することを目的としています。

## 元コミット内容

runtime: free stack spans outside STW

We couldn't do this before this point because it must be done before
the next GC cycle starts. Hence, if it delayed the start of the next
cycle, that would widen the window between reaching the heap trigger
of the next cycle and starting the next GC cycle, during which the
mutator could over-allocate. With the decentralized GC, any mutators
that reach the heap trigger will block on the GC starting, so it's
safe to widen the time between starting the world and being able to
start the next GC cycle.

## 変更の背景

Goのガベージコレクションは、アプリケーションの実行を一時停止する「Stop-The-World (STW)」フェーズを最小限に抑えるように設計されています。STWフェーズ中に行われる処理は、アプリケーションのレイテンシに直接影響するため、可能な限りSTWの外に移動することが望ましいとされています。

このコミット以前は、スタックスパンの解放処理（`freeStackSpans`）がGCのSTWフェーズ内で行われていました。これは、次のGCサイクルが開始される前にこの処理を完了する必要があったためです。もしSTWの外でこの処理を行うと、次のGCサイクルが開始されるまでの時間が長くなり、その間にミューテーター（アプリケーションコード）がヒープを過剰に割り当ててしまうリスクがありました。

しかし、Go 1.5で導入された「分散型GC（decentralized GC）」の変更により、この制約が緩和されました。分散型GCでは、ヒープ割り当てが特定の閾値（ヒープトリガー）に達したミューテーターは、次のGCサイクルが開始されるまでブロックされるようになりました。この新しいメカニズムにより、`freeStackSpans`の実行が次のGCサイクル開始までの時間を多少延ばしたとしても、ミューテーターが過剰に割り当てる心配がなくなりました。

この背景から、`freeStackSpans`をSTWフェーズの外に移動することで、STW時間を短縮し、全体的なGCのパフォーマンスとアプリケーションの応答性を向上させることが可能になりました。この変更は、Issue #11465で議論されていた課題を解決するものです。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に三色マーク＆スイープアルゴリズムをベースにしています。Go 1.5からは、並行GCが導入され、ほとんどのGC処理がアプリケーションの実行と並行して行われるようになりました。しかし、一部の重要な処理（特にGCの開始と終了）では、アプリケーションの実行を一時的に停止する「Stop-The-World (STW)」フェーズが必要です。STWフェーズは、GCの正確性を保証するために、ヒープの状態が変化しないようにミューテーターを停止させる期間です。

### Stop-The-World (STW)

STWは、ガベージコレクタがヒープの一貫したスナップショットを取得したり、特定の重要なクリーンアップ作業を行ったりするために、すべてのゴルーチン（ミューテーター）の実行を一時的に停止する期間です。この期間が長くなると、アプリケーションの応答性が低下し、レイテンシが増加します。GoのGC開発の主要な目標の一つは、このSTW時間を可能な限り短縮することです。

### スタックスパン (Stack Spans)

Goランタイムは、ゴルーチンのスタックを管理するために「スタックスパン」という概念を使用します。スタックはヒープとは別に管理され、必要に応じて動的に拡大・縮小します。ゴルーチンが終了したり、スタックが縮小されたりすると、そのスタックが使用していたメモリ領域（スタックスパン）は解放され、再利用可能な状態になります。この解放処理は、メモリの断片化を防ぎ、効率的なメモリ利用を維持するために重要です。

### 分散型GC (Decentralized GC)

Go 1.5で導入された分散型GCは、GCのトリガーと開始のメカニズムを改善しました。以前は、GCの開始が中央集権的に管理されており、GCが開始されるまでの間にミューテーターがヒープを過剰に割り当てる可能性がありました。分散型GCでは、各ミューテーターが自身のヒープ割り当てを監視し、ヒープ割り当てが特定の閾値（ヒープトリガー）に達すると、そのミューテーターはGCが開始されるまで自律的にブロックされます。これにより、GCの開始が遅れてもヒープの過剰割り当てを防ぐことができます。

## 技術的詳細

このコミットの核心は、`freeStackSpans`関数の実行タイミングをSTWフェーズの終了後、かつ次のGCサイクルが始まる前という、より柔軟なタイミングに移動した点です。

以前のGo GCモデルでは、`freeStackSpans`をSTWの外で実行すると、以下の問題が発生する可能性がありました。
1.  **GCサイクル間のウィンドウ拡大**: `freeStackSpans`の処理に時間がかかると、現在のGCサイクルが終了してから次のGCサイクルが開始されるまでの時間が長くなります。
2.  **ミューテーターによる過剰割り当て**: この拡大されたウィンドウ期間中に、ミューテーターがヒープを自由に割り当て続けることができ、次のGCサイクルが始まる前にヒープが過剰に消費される（オーバーアロケーション）リスクがありました。これは、GCの効率を低下させ、最悪の場合、メモリ不足を引き起こす可能性がありました。

分散型GCの導入により、この状況は根本的に変わりました。
-   **ヒープトリガーとミューテーターのブロック**: 分散型GCでは、各ミューテーターは自身のヒープ割り当てを監視し、ヒープ割り当てが次のGCサイクルを開始すべき閾値（ヒープトリガー）に達すると、そのミューテーターはGCが実際に開始されるまでブロックされます。
-   **安全性の確保**: このメカニズムにより、`freeStackSpans`がSTW終了後に行われ、次のGCサイクル開始までの時間が多少延びたとしても、ミューテーターがヒープを過剰に割り当てることはありません。なぜなら、過剰割り当てを試みるミューテーターは、GCが開始されるまで自動的に停止されるからです。

したがって、`freeStackSpans`をSTWの外に移動しても、ヒープの過剰割り当てのリスクなしに、STW時間を短縮できるというメリットだけを享受できるようになりました。これは、GCの全体的なレイテンシを削減し、Goアプリケーションのパフォーマンスを向上させる上で重要な改善です。

## コアとなるコードの解説

変更点は主に2箇所です。

1.  **`gcMarkTermination()` 関数内での `freeStackSpans` の追加**:
    以前は、`gcMarkTermination()` の最後の方で `freeStackSpans()` が呼び出されていましたが、これはSTWフェーズの終盤に位置していました。
    新しいコードでは、`systemstack(startTheWorldWithSema)` の直後、つまりSTWが終了し、ミューテーターが再開された直後に `systemstack(freeStackSpans)` が追加されています。
    `systemstack` は、現在のゴルーチンをシステムスタックに切り替えて関数を実行するためのGoランタイムの内部関数です。これにより、GC関連の重要な処理が、通常のゴルーチンのスタックではなく、より安定したシステムスタック上で実行されることが保証されます。
    この新しい位置は、STWが解除された後でありながら、次のGCサイクルが開始される前という、コミットメッセージで述べられている「GCサイクル間」の安全な期間に相当します。

2.  **`gcMark()` 関数内での `freeStackSpans` の削除**:
    以前のコードでは、`gcMark()` 関数（GCのマークフェーズの一部）の終盤に `freeStackSpans()` が呼び出されていました。この位置はSTWフェーズ中にあたります。
    削除されたコメントには、「TODO(austin): これはSTW中に実行する必要はない。次のGCサイクルが完了するまでブロックする限り、STW後にワールドを再開してから`worldsema`を解放する前に移動できる。（Issue #11465を参照）」と明記されており、この変更が以前から計画されていたことがわかります。

この変更により、スタックスパンの解放処理がSTWフェーズから切り離され、STW時間の短縮に貢献します。分散型GCの導入によって、この移動が安全に行えるようになったため、Goランタイムのパフォーマンスがさらに向上しました。

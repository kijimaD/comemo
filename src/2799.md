## 元コミット内容

`typeArrayMap`が、`Type`へのポインタのアドレスではなく、`Type`そのもののアドレスを使用していたバグを修正しました。

## 変更の背景

このコミットは、Go言語の初期開発段階における`reflect`パッケージの利用に関する理解と実装の進化を示しています。`typeArrayMap`は、おそらく型の配列をキーとして使用するマップのようなデータ構造であり、そのキーのハッシュ値を正確に計算する必要がありました。

元の実装では、`reflect.NewValue(t).Addr()`を使用して型の「アドレス」を取得しようとしていました。しかし、`reflect.NewValue(t)`は`t`の値をラップした`reflect.Value`を返します。この`reflect.Value`に対して`Addr()`を呼び出すと、`reflect.Value`オブジェクト自体のメモリアドレス、あるいはそれがラップしている値がポインタ型である場合にそのポインタのアドレスを返します。この場合、`t`が`Type`型（おそらくインターフェースまたは構造体）であるとすると、`reflect.NewValue(t)`は`t`のコピーを`reflect.Value`内に作成し、`Addr()`はそのコピーのアドレスを返していた可能性があります。

真に必要だったのは、`Type`インスタンスそのもののユニークな識別子、つまりそのメモリアドレスでした。Goの`reflect`パッケージは、実行時に型情報を検査・操作するための強力なメカニズムを提供しますが、そのAPIは非常に詳細であり、特に初期のバージョンでは、そのセマンティクスを正確に理解して使用することが課題となることがありました。このバグは、`reflect`パッケージの特定のメソッドが何のアドレスを返すのかについての誤解に起因していると考えられます。

`typeArrayMap`のような構造では、型の同一性を正確に判断するために、型のメモリアドレスをハッシュキーの一部として使用することが一般的です。もし異なる`Type`インスタンスが同じハッシュ値を生成してしまうと、マップの衝突が発生し、誤った型が取得されたり、パフォーマンスが低下したりする可能性があります。この修正は、型の同一性チェックの基盤となるハッシュ計算の正確性を保証するために不可欠でした。

## 前提知識の解説

### Go言語の`reflect`パッケージ

Go言語の`reflect`パッケージは、プログラムが実行時に自身の構造を検査し、変更することを可能にする機能（リフレクション）を提供します。これにより、型情報（構造体のフィールド、メソッド、インターフェースの実装など）を動的に取得したり、値の操作（フィールドへの値の設定、メソッドの呼び出しなど）を行ったりすることができます。

主要な概念は以下の通りです。
*   **`reflect.Type`**: Goの型を表すインターフェースです。`reflect.TypeOf(x)`で取得できます。
*   **`reflect.Value`**: Goの値を表す構造体です。`reflect.ValueOf(x)`で取得できます。`reflect.Value`は、その値の型情報（`Type()`メソッドで取得）と、実際の値自体を保持します。

`reflect.Value`には、値を操作するための様々なメソッドがあります。
*   `Addr()`: 値がアドレス可能（ポインタが取得可能）な場合、その値へのポインタを表す`reflect.Value`を返します。
*   `Elem()`: ポインタ、インターフェース、配列、スライス、マップ、チャネルの要素を返します。例えば、ポインタ`*T`に対して`Elem()`を呼び出すと、`T`型の`reflect.Value`が返されます。
*   `Interface()`: `reflect.Value`が保持する値を`interface{}`として返します。
*   `Get()`: `reflect.PtrValue`（ポインタを表す`reflect.Value`）の場合、そのポインタが指すアドレスを`uintptr`として返します。

### ポインタとアドレス

Go言語において、ポインタは変数のメモリアドレスを保持する型です。`&`演算子を使って変数のアドレスを取得し、`*`演算子を使ってポインタが指す値にアクセスします。

*   `&x`: 変数`x`のメモリアドレス（ポインタ）
*   `*p`: ポインタ`p`が指すメモリアドレスに格納されている値

このコミットの文脈では、「`Type`へのポインタのアドレス」と「`Type`そのもののアドレス」という表現が重要です。
*   「`Type`そのもののアドレス」とは、`Type`インターフェースを実装する具体的な型のインスタンスがメモリ上に存在する場所のアドレスを指します。これは、その型を一意に識別するための物理的なアドレスです。
*   「`Type`へのポインタのアドレス」とは、`Type`型の値を指すポインタ変数自体がメモリ上に存在する場所のアドレスを指します。これは、ポインタ変数のアドレスであり、ポインタが指す先の`Type`インスタンスのアドレスではありません。

ハッシュ計算においては、型の同一性を判断するために、型インスタンスそのもののアドレスが必要となります。

## 技術的詳細

このコミットの核心は、`reflect`パッケージの`Addr()`メソッドと、ポインタ型を扱う際の`reflect.Value`のキャストおよび`Get()`メソッドの使い分けにあります。

元のコード:
```go
addr := reflect.NewValue(t).Addr();
```
ここで`t`は`Type`型の値です。
1.  `reflect.NewValue(t)`: `t`の値をラップする`reflect.Value`を生成します。この`reflect.Value`は、`t`のコピーを内部に保持しているか、あるいは`t`がインターフェース値であればその動的な型と値を保持します。重要なのは、この`reflect.Value`自体は`t`のメモリアドレスを直接指しているわけではない点です。
2.  `.Addr()`: `reflect.NewValue(t)`によって生成された`reflect.Value`がアドレス可能であれば、その値へのポインタを表す`reflect.Value`を返します。しかし、`reflect.NewValue(t)`が返す`reflect.Value`は通常、アドレス可能ではありません（unaddressable）。これは、`reflect.NewValue`が引数のコピーを作成するため、そのコピーのアドレスを取得しても元の`t`のアドレスとは異なるためです。もし`t`がポインタ型でなければ、`Addr()`はパニックを起こすか、意図しない結果を返す可能性があります。仮に`Addr()`が何らかの形で成功したとしても、それは`reflect.Value`が内部で保持する`t`のコピーのアドレス、あるいは`reflect.Value`オブジェクト自体のアドレスであり、`t`そのもののメモリアドレスではありません。

修正後のコード:
```go
addr := reflect.NewValue(t).(*reflect.PtrValue).Get();
```
この修正は、`t`が既にポインタ型であるか、あるいは`reflect.NewValue(t)`がポインタ型の`reflect.Value`を返すことを前提としています。
1.  `reflect.NewValue(t)`: 同上、`t`の値をラップする`reflect.Value`を生成します。
2.  `.(reflect.PtrValue)`: ここで型アサーションが行われています。これは、`reflect.NewValue(t)`が返した`reflect.Value`が、実際には`reflect.PtrValue`型（ポインタを表す`reflect.Value`の具体的な実装型）であることを期待しています。もし`t`がポインタ型でなければ、この型アサーションはパニックを起こします。
3.  `.Get()`: `reflect.PtrValue`の`Get()`メソッドは、そのポインタが指すメモリアドレスを`uintptr`として返します。これにより、`t`が指す実際の`Type`インスタンスのメモリアドレスが取得されます。

この変更は、`t`が`*Type`のようなポインタ型である場合にのみ正しく機能します。もし`t`が`Type`インターフェース型であり、その具体的な値がポインタでない場合、`reflect.NewValue(t).(*reflect.PtrValue)`はパニックを起こすでしょう。しかし、`typeArrayMap`の文脈では、`Type`がインターフェースであり、その実装がポインタ型であるか、あるいは`t`自体が`*Type`のようなポインタ型として扱われている可能性が高いです。

この修正の目的は、`Type`インスタンスの物理的なメモリアドレスをハッシュキーとして使用することで、型の同一性を正確に識別することにあります。`reflect.NewValue(t).Addr()`が返していたのは、`t`のコピーや`reflect.Value`オブジェクト自体のメモリアドレスであり、これは`Type`インスタンスの同一性を判断する上では不適切でした。`reflect.NewValue(t).(*reflect.PtrValue).Get()`は、ポインタが指す先のメモリアドレスを直接取得するため、この目的には合致しています。

## コアとなるコードの変更箇所

変更は`usr/austin/eval/type.go`ファイルの`hashTypeArray`関数内の一行です。

```diff
--- a/usr/austin/eval/type.go
+++ b/usr/austin/eval/type.go
@@ -49,7 +49,7 @@ func hashTypeArray(key []Type) uintptr {
 		if t == nil {
 			continue;
 		}
-		addr := reflect.NewValue(t).Addr();
+		addr := reflect.NewValue(t).(*reflect.PtrValue).Get();
 		hash ^= addr;
 	}
 	return hash;
```

## コアとなるコードの解説

`hashTypeArray`関数は、`Type`の配列`key`を受け取り、そのハッシュ値を`uintptr`として計算します。このハッシュ値は、おそらく`typeArrayMap`のようなマップのキーとして使用されます。

ループ内で、配列`key`の各要素`t`（`Type`型）に対して以下の処理が行われます。

1.  `if t == nil { continue; }`: `t`が`nil`の場合はスキップします。
2.  **変更前**: `addr := reflect.NewValue(t).Addr();`
    *   `reflect.NewValue(t)`は、`t`の値をラップする`reflect.Value`を生成します。
    *   `.Addr()`は、この`reflect.Value`がアドレス可能であれば、その値へのポインタを表す`reflect.Value`を返します。しかし、この`reflect.Value`は通常アドレス可能ではないため、この呼び出しは意図しない結果をもたらすか、パニックを引き起こす可能性がありました。もし`t`がポインタ型でなければ、`Addr()`は`reflect.Value`が内部で保持する`t`のコピーのアドレスを返そうとするか、エラーになります。
3.  **変更後**: `addr := reflect.NewValue(t).(*reflect.PtrValue).Get();`
    *   `reflect.NewValue(t)`は、`t`の値をラップする`reflect.Value`を生成します。
    *   `.(reflect.PtrValue)`は、この`reflect.Value`が`reflect.PtrValue`型（ポインタを表す`reflect.Value`の具体的な実装型）であることをアサートします。これは、`t`がポインタ型であるか、`reflect.NewValue(t)`がポインタ型の`reflect.Value`を返すことを前提としています。
    *   `.Get()`は、`reflect.PtrValue`が指すメモリアドレスを`uintptr`として返します。これにより、`t`が指す実際の`Type`インスタンスのメモリアドレスが取得されます。

最終的に、取得した`addr`は`hash`変数とXOR演算され、ハッシュ値の計算に利用されます。この修正により、`addr`が`Type`インスタンスそのもののユニークなメモリアドレスを正確に表すようになり、`typeArrayMap`のハッシュ計算の正確性と信頼性が向上しました。

## 変更の背景

Goの`runtime/trace`パッケージは、Goプログラムの実行時の詳細なイベント（GC、スケジューリング、システムコールなど）を記録し、パフォーマンス分析に役立つトレースファイルを生成する機能を提供します。このトレースファイルには、スタックトレース情報も含まれることがあり、そのスタックトレースを人間が読める形式（ファイル名、行番号、関数名）に変換するためには、`go tool addr2line`というツールが使用されます。

このコミットが行われる前は、`runtime/trace`パッケージ内の`TestTraceSymbolize`というテストが、`testenv.MustHaveExec(t)`を使用して、任意の実行可能ファイルが存在するかどうかをチェックしていました。しかし、`go tool addr2line`は単なる任意の実行可能ファイルではなく、Goツールチェーンの一部として提供される特定のツールです。特に`android/arm`のようなクロスコンパイル環境や、特定のビルド環境では、`go tool addr2line`が直接パス上に存在しない、あるいは通常の実行可能ファイルとは異なる方法で利用可能である場合があります。

このテストが失敗する原因は、`testenv.MustHaveExec(t)`が`go tool addr2line`の存在を適切に検証できていなかったことにあります。`go tool addr2line`は`go`コマンドのサブコマンドとして実行されるため、`go`コマンド自体が存在し、かつ`addr2line`サブコマンドが利用可能であるかをチェックする必要があります。

## 前提知識の解説

*   **Goランタイムトレース (`runtime/trace`)**: Goプログラムの実行中に発生する様々なイベント（ガーベージコレクション、ゴルーチンのスケジューリング、システムコールなど）を記録するための機能です。生成されるトレースファイルは、`go tool trace`コマンドで可視化・分析できます。パフォーマンスのボトルネック特定やデバッグに非常に有用です。
*   **`go tool addr2line`**: Goツールチェーンに含まれるコマンドラインツールの一つで、プログラムカウンタ（メモリアドレス）をソースコードのファイル名、行番号、関数名に変換（シンボル化）するために使用されます。デバッグ情報を含む実行可能ファイルに対して機能します。スタックトレースの解析において不可欠なツールです。
*   **`testenv`パッケージ**: Goの標準ライブラリに含まれるテストユーティリティパッケージです。テストの実行環境が特定の要件を満たしているか（例: 特定のコマンドが存在するか、ネットワークが利用可能かなど）をチェックするために使用されます。これにより、環境依存のテストをスキップしたり、適切なエラーメッセージを出力したりできます。
    *   **`testenv.MustHaveExec(t)`**: 指定された実行可能ファイルがシステムパス上に存在するかどうかをチェックします。存在しない場合、テストをスキップします。
    *   **`testenv.MustHaveGoBuild(t)`**: Goのビルド環境が利用可能であるか、つまり`go`コマンドが実行可能であるかをチェックします。これは、`go build`や`go tool`などのGoツールチェーンのコマンドが利用できることを保証します。
*   **`android/arm builder`**: Goのテストインフラストラクチャにおける特定のビルド環境を指します。Goはクロスコンパイルをサポートしており、`android/arm`はAndroidプラットフォーム向けのARMアーキテクチャをターゲットとしたビルド環境です。このような特殊な環境では、通常のデスクトップ環境とは異なるツールパスや環境設定が必要となることがよくあります。

## 技術的詳細

このコミットの核心は、`TestTraceSymbolize`テストが依存する外部ツール`go tool addr2line`の存在チェック方法の改善にあります。

元のコードでは`testenv.MustHaveExec(t)`が使われていました。この関数は、引数として渡されたコマンド名（この場合は`addr2line`）がシステムパス上のどこかに実行可能ファイルとして存在するかどうかを確認します。しかし、`addr2line`は単独の実行可能ファイルとしてではなく、`go tool addr2line`という形式で`go`コマンドのサブコマンドとして実行されるのが一般的です。

したがって、`testenv.MustHaveExec(t)`で`addr2line`をチェックしても、`go`コマンドが存在し、そのサブコマンドとして`addr2line`が機能するかどうかは保証されません。特にクロスコンパイル環境では、ホストシステムに`addr2line`という名前の実行可能ファイルが存在しないか、あるいはGoツールチェーンとは無関係な別の`addr2line`（例えばGNU binutilsのもの）が存在する可能性があります。

`testenv.MustHaveGoBuild(t)`は、`go`コマンド自体が実行可能であるかをチェックします。`go`コマンドが実行可能であれば、通常は`go tool addr2line`も利用可能であると期待できます。この変更により、テストはGoツールチェーンが正しくセットアップされている環境でのみ実行されるようになり、`go tool addr2line`の利用可能性をより正確に反映するようになりました。

この修正は、特に`android/arm`のような、Goツールチェーンのセットアップが標準的なデスクトップ環境と異なる可能性のあるビルド環境において、テストの誤検出（false negative）を防ぐために重要です。テストが不必要な理由で失敗するのを防ぎ、実際のバグや問題に集中できるようにします。

## コアとなるコードの解説

変更は`src/runtime/trace/trace_stack_test.go`ファイルの`TestTraceSymbolize`関数内の一行です。

*   **`- testenv.MustHaveExec(t)`**: 削除された行です。これは、テストを実行する前に、`addr2line`という名前の実行可能ファイルがシステムパス上に存在するかどうかをチェックしていました。このチェックは、`go tool addr2line`というGoツールチェーンの特定のサブコマンドの存在を正確に検証するには不十分でした。
*   **`+ testenv.MustHaveGoBuild(t)`**: 追加された行です。これは、テストを実行する前に、Goのビルド環境（つまり`go`コマンド自体）が利用可能であるかどうかをチェックします。`go`コマンドが利用可能であれば、`go tool addr2line`も利用可能であると期待できるため、このチェックの方が`TestTraceSymbolize`の要件に対してより適切です。

この変更により、`TestTraceSymbolize`は、`go tool addr2line`が実際に利用可能な環境でのみ実行されるようになり、テストの信頼性と移植性が向上しました。

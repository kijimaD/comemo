## 変更の背景

このコミットは、Go言語の初期段階における文字列の`nil`値の扱いに関する重要な変更を導入しています。Go言語の設計思想の一つに「ゼロ値の有用性」があります。これは、変数が宣言された際に自動的にゼロ値（数値型なら0、ブール型ならfalseなど）で初期化され、そのゼロ値が有効な状態として機能するというものです。

文字列型の場合、初期の設計では`nil`文字列と空文字列（`""`）が異なるものとして扱われていました。しかし、これはプログラマにとって混乱の原因となる可能性がありました。例えば、`nil`文字列に対して`len()`を呼び出すとパニックを起こす、あるいは`nil`文字列と空文字列の比較が`false`になるなど、直感に反する挙動が生じることが考えられます。

このコミットの背景には、このような混乱を解消し、文字列の`nil`値を空文字列と同一視することで、より堅牢で予測可能な文字列操作を実現するという目的がありました。これにより、文字列変数が`nil`であるかどうかを明示的にチェックする必要が減り、コードの簡潔性と安全性が向上します。特に、文字列をキーとするマップ操作において、`nil`キーの扱いを明確にすることも重要な側面でした。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の初期の内部実装に関する知識が必要です。

1.  **Go言語の文字列の内部表現**:
    Goの文字列は、内部的にはポインタと長さ（`struct String { byte *str; intgo len; }`のような構造）で表現されます。`str`は文字列データへのポインタ、`len`はその長さを表します。
    *   **空文字列 (`""`)**: `str`が有効なゼロ長データ（例えば、静的に確保されたゼロ長文字列の先頭アドレス）を指し、`len`が0である状態。
    *   **`nil`文字列**: `str`が`NULL`（またはそれに相当するゼロアドレス）を指し、`len`が0である状態。
    このコミット以前は、この2つが区別されていました。

2.  **Goコンパイラのフェーズ**:
    Goコンパイラ（この時期は`6g`、`8g`、`5g`などアーキテクチャごとのコンパイラが存在）は、ソースコードを機械語に変換する過程で複数のフェーズを経ます。
    *   **`cmd/gc/walk.c`**: これはコンパイラの「ウォーカー」フェーズの一部であり、抽象構文木（AST）を走査し、型チェック、最適化、組み込み関数の変換など、様々なセマンティックな処理を行います。このフェーズで、Goの高級な構文がより低レベルの操作に変換されます。例えば、マップ操作（`map[key] = value`や`value, ok = map[key]`）は、ここでランタイム関数呼び出しに変換されます。
    *   **`cmd/6g/cgen.c`, `cmd/6g/gen.c`, `cmd/6g/gsubr.c`**: これらはコード生成（`cgen`はコード生成、`gen`は汎用的なコード生成ユーティリティ、`gsubr`はサブルーチン生成）に関連する部分で、ASTから具体的なアセンブリコード（または中間表現）を生成します。
    *   **`src/runtime/runtime.c`, `src/runtime/runtime.h`**: GoランタイムのC言語実装部分です。ガベージコレクション、スケジューラ、プリミティブなデータ構造（文字列、マップ、スライスなど）の操作、システムコールなどが含まれます。Goプログラムが実行される際に、これらのランタイム関数が呼び出されます。

3.  **マップの内部実装**:
    Goのマップ（`map`）はハッシュテーブルとして実装されており、キーと値のペアを格納します。マップ操作（要素の追加、取得、削除）は、コンパイラによってランタイムの特定の関数呼び出しに変換されます。このコミットでは、特にマップのキーとして文字列が使用される場合の挙動に影響があります。

## 技術的詳細

このコミットの核心は、Go言語の文字列型において、`nil`ポインタを持つ文字列と、長さがゼロの空文字列を、セマンティックに同一視するという変更です。これにより、Goの文字列は常に有効な（非`nil`の）データポインタを持つか、あるいは`len`が0であれば`nil`ポインタであっても空文字列として扱われるようになります。

具体的な変更点は以下の通りです。

1.  **`src/runtime/runtime.c` および `src/runtime/runtime.h` の変更**:
    *   `static string emptystring = (string)&empty;` の導入: `emptystring`というグローバルな空文字列定数が定義されました。これは、`empty`という`int32`型のゼロ値変数のアドレスを`string`型にキャストしたもので、`str`ポインタが有効な（ただし内容はゼロ）メモリを指し、`len`が0であることを保証します。これにより、`nil`文字列を扱う際に、この`emptystring`に置き換えることで、常に有効なポインタを持つ空文字列として処理できるようになります。
    *   文字列操作関数の`nil`チェック追加: `sys_printstring`, `cmpstring`, `sys_catstring`, `sys_slicestring`, `sys_indexstring`といったランタイムの文字列操作関数において、引数として渡された文字列が`nil`である場合に、`emptystring`に置き換える処理が追加されました。これにより、これらの関数は`nil`文字列に対しても安全に動作し、空文字列と同じ結果を返すようになります。
    *   `strlen`から`findnull`への名称変更: `strlen`関数が`findnull`に名称変更されました。これは、C言語の`strlen`がヌル終端文字列の長さを計算するのに対し、Goの文字列は長さ情報を持つため、この関数がGoの文字列の長さを計算するものではないことを明確にするためと考えられます。実際には、`prints`関数内でCスタイルのヌル終端文字列を扱うために使用されています。

2.  **`src/cmd/gc/walk.c` の変更**:
    *   マップ操作の変換ロジックの修正: `walk.c`はコンパイラのセマンティック分析フェーズで、Goのマップ操作（`map[key] = value`や`value, ok = map[key]`）をランタイム関数呼び出しに変換します。このコミットでは、特に多値代入（`a, b = fn()`）やマップの多値アクセス（`value, ok = m[key]`）および多値代入（`m[key] = value, ok`）の処理が大幅に修正されました。

## コアとなるコードの解説

### `src/runtime/runtime.c` における文字列の`nil`と空文字列の同一視

このファイルの変更は、Goの文字列が`nil`である場合でも、あたかも空文字列であるかのように振る舞うようにするための基盤を構築しています。

```c
static	int32	empty		= 0;
static	string	emptystring	= (string)&empty;
```
これは、Goランタイム内で使用されるグローバルな空文字列定数`emptystring`を定義しています。`empty`という`int32`型の変数（値は0）のアドレスを文字列ポインタとして使用することで、`emptystring`の`str`フィールドは有効なメモリ位置を指し、`len`フィールドは0となります。これにより、`nil`ポインタを持つ文字列と、この`emptystring`がセマンティックに等価になります。

```c
void
sys_printstring(string v)
{
	if(v != nil) // ここでnilチェックが追加
		sys_write(1, v->str, v->len);
}
```
`sys_printstring`関数は、文字列を標準出力に書き出すランタイム関数です。変更前は`v->str`を直接使用していましたが、`v`が`nil`の場合に`nil`ポインタ参照が発生する可能性がありました。この変更により、`v`が`nil`でなければ書き出しを行い、`nil`であれば何も書き出さない（空文字列と同じ挙動）という安全な処理が保証されます。

同様に、`cmpstring`（文字列比較）、`sys_catstring`（文字列結合）、`sys_slicestring`（文字列スライス）、`sys_indexstring`（文字列インデックスアクセス）といった他の文字列操作関数にも、引数が`nil`文字列であった場合に`emptystring`に置き換えるロジックが追加されています。これにより、これらの操作が`nil`文字列に対してもパニックを起こさず、空文字列と同じ結果を返すようになります。

## 変更の背景

このコミットは、Go言語の初期段階における文字列の`nil`値の扱いに関する重要な変更を導入しています。Go言語の設計思想の一つに「ゼロ値の有用性」があります。これは、変数が宣言された際に自動的にゼロ値（数値型なら0、ブール型ならfalseなど）で初期化され、そのゼロ値が有効な状態として機能するというものです。

文字列型の場合、初期の設計では`nil`文字列と空文字列（`""`）が異なるものとして扱われていました。しかし、これはプログラマにとって混乱の原因となる可能性がありました。例えば、`nil`文字列に対して`len()`を呼び出すとパニックを起こす、あるいは`nil`文字列と空文字列の比較が`false`になるなど、直感に反する挙動が生じることが考えられます。

このコミットの背景には、このような混乱を解消し、文字列の`nil`値を空文字列と同一視することで、より堅牢で予測可能な文字列操作を実現するという目的がありました。これにより、文字列変数が`nil`であるかどうかを明示的にチェックする必要が減り、コードの簡潔性と安全性が向上します。特に、文字列をキーとするマップ操作において、`nil`キーの扱いを明確にすることも重要な側面でした。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の初期の内部実装に関する知識が必要です。

1.  **Go言語の文字列の内部表現**:
    Goの文字列は、内部的にはポインタと長さ（`struct String { byte *str; intgo len; }`のような構造）で表現されます。`str`は文字列データへのポインタ、`len`はその長さを表します。
    *   **空文字列 (`""`)**: `str`が有効なゼロ長データ（例えば、静的に確保されたゼロ長文字列の先頭アドレス）を指し、`len`が0である状態。
    *   **`nil`文字列**: `str`が`NULL`（またはそれに相当するゼロアドレス）を指し、`len`が0である状態。
    このコミット以前は、この2つが区別されていました。

2.  **Goコンパイラのフェーズ**:
    Goコンパイラ（この時期は`6g`、`8g`、`5g`などアーキテクチャごとのコンパイラが存在）は、ソースコードを機械語に変換する過程で複数のフェーズを経ます。
    *   **`cmd/gc/walk.c`**: これはコンパイラの「ウォーカー」フェーズの一部であり、抽象構文木（AST）を走査し、型チェック、最適化、組み込み関数の変換など、様々なセマンティックな処理を行います。このフェーズで、Goの高級な構文がより低レベルの操作に変換されます。例えば、マップ操作（`map[key] = value`や`value, ok = map[key]`）は、ここでランタイム関数呼び出しに変換されます。
    *   **`cmd/6g/cgen.c`, `cmd/6g/gen.c`, `cmd/6g/gsubr.c`**: これらはコード生成（`cgen`はコード生成、`gen`は汎用的なコード生成ユーティリティ、`gsubr`はサブルーチン生成）に関連する部分で、ASTから具体的なアセンブリコード（または中間表現）を生成します。
    *   **`src/runtime/runtime.c`, `src/runtime/runtime.h`**: GoランタイムのC言語実装部分です。ガベージコレクション、スケジューラ、プリミティブなデータ構造（文字列、マップ、スライスなど）の操作、システムコールなどが含まれます。Goプログラムが実行される際に、これらのランタイム関数が呼び出されます。

3.  **マップの内部実装**:
    Goのマップ（`map`）はハッシュテーブルとして実装されており、キーと値のペアを格納します。マップ操作（要素の追加、取得、削除）は、コンパイラによってランタイムの特定の関数呼び出しに変換されます。このコミットでは、特にマップのキーとして文字列が使用される場合の挙動に影響があります。

## 技術的詳細

このコミットの核心は、Go言語の文字列型において、`nil`ポインタを持つ文字列と、長さがゼロの空文字列を、セマンティックに同一視するという変更です。これにより、Goの文字列は常に有効な（非`nil`の）データポインタを持つか、あるいは`len`が0であれば`nil`ポインタであっても空文字列として扱われるようになります。

具体的な変更点は以下の通りです。

1.  **`src/runtime/runtime.c` および `src/runtime/runtime.h` の変更**:
    *   `static string emptystring = (string)&empty;` の導入: `emptystring`というグローバルな空文字列定数が定義されました。これは、`empty`という`int32`型のゼロ値変数のアドレスを`string`型にキャストしたもので、`str`ポインタが有効な（ただし内容はゼロ）メモリを指し、`len`が0であることを保証します。これにより、`nil`文字列を扱う際に、この`emptystring`に置き換えることで、常に有効なポインタを持つ空文字列として処理できるようになります。
    *   文字列操作関数の`nil`チェック追加: `sys_printstring`, `cmpstring`, `sys_catstring`, `sys_slicestring`, `sys_indexstring`といったランタイムの文字列操作関数において、引数として渡された文字列が`nil`である場合に、`emptystring`に置き換える処理が追加されました。これにより、これらの関数は`nil`文字列に対しても安全に動作し、空文字列と同じ結果を返すようになります。
    *   `strlen`から`findnull`への名称変更: `strlen`関数が`findnull`に名称変更されました。これは、C言語の`strlen`がヌル終端文字列の長さを計算するのに対し、Goの文字列は長さ情報を持つため、この関数がGoの文字列の長さを計算するものではないことを明確にするためと考えられます。実際には、`prints`関数内でCスタイルのヌル終端文字列を扱うために使用されています。
    *   `Hmap`構造体への`len`フィールド追加: マップの内部構造体`Hmap`に`uint32 len;`フィールドが追加されました。これはマップに含まれる要素の数を追跡するためのものです。`sys_newmap`で0に初期化され、`sys_mapassign`でインクリメント、`sys_mapassign2`（マップからの削除操作）でデクリメントされます。これは文字列の`nil`化とは直接関係ありませんが、マップの内部実装の改善の一環として同時に行われた変更です。

2.  **`src/cmd/gc/walk.c` の変更**:
    *   マップ操作の変換ロジックの修正: `walk.c`はコンパイラのセマンティック分析フェーズで、Goのマップ操作（`map[key] = value`や`value, ok = map[key]`）をランタイム関数呼び出しに変換します。このコミットでは、特に多値代入（`a, b = fn()`）やマップの多値アクセス（`value, ok = m[key]`）および多値代入（`m[key] = value, ok`）の処理が大幅に修正されました。
        *   以前は`mapaccess2`や`mapassign1`、`mapassign2`といったランタイム関数への変換が、`OAS`（代入）ノードの左右のオペランドの「形」（`cl`と`cr`、それぞれ左辺と右辺の要素数）に依存していましたが、このコミットでより汎用的な`mapop`関数に処理が委譲され、`cl`と`cr`の組み合わせに応じた適切なランタイム関数（`mapaccess2`, `mapassign1`, `mapassign2`）が選択されるようになりました。
        *   `mapop`関数内で、`cl`（左辺の要素数）と`cr`（右辺の要素数）を考慮し、`mapassign1`（単一値代入）、`mapassign2`（2値代入）、`mapaccess2`（2値アクセス）のいずれかのランタイム関数を呼び出すようにロジックが整理されました。これにより、マップ操作のセマンティクスがより正確にランタイム関数にマッピングされるようになりました。
    *   `OLEN`（`len()`組み込み関数）のマップ型に対する処理追加: `cgen.c`において、`OLEN`オペレーションがマップ型（`TMAP`）に対して適用された場合の処理が追加されました。これは、マップの`len()`がマップの要素数を返すようにするための変更であり、`Hmap`構造体に`len`フィールドが追加されたことと関連しています。

3.  **`src/cmd/6g/gen.c` の変更**:
    *   ポインタ型から文字列型への変換時の特殊処理の削除: `cgen_as`関数において、ポインタ型から文字列型への変換時に`nr->val.ctype = CTSTR; nr->val.sval = &emptystring;`として空文字列を割り当てる特殊なロジックが削除されました。これは、`nil`文字列が空文字列として扱われるようになったため、このような明示的な変換が不要になったことを示唆しています。

4.  **`src/cmd/6g/gsubr.c` の変更**:
    *   `stringpool`関数の`nil`文字列チェック追加: 文字列リテラルをプールする`stringpool`関数において、`n->val.ctype == CTNIL`の場合に`return`する（つまり、`nil`文字列をエラーとせず、プール処理をスキップする）ロジックが追加されました。これにより、`nil`文字列がリテラルとして扱われた場合でも、コンパイラがパニックを起こさずに処理を続行できるようになります。

これらの変更により、Go言語の文字列は、`nil`値であっても常に空文字列として振る舞うようになり、プログラマは`nil`チェックを意識することなく文字列操作を行えるようになりました。これは、Goの「ゼロ値の有用性」という設計原則を文字列型にも適用し、言語の一貫性と使いやすさを向上させるための重要なステップでした。

## コアとなるコードの解説

### `src/runtime/runtime.c` における文字列の`nil`と空文字列の同一視

このファイルの変更は、Goの文字列が`nil`である場合でも、あたかも空文字列であるかのように振る舞うようにするための基盤を構築しています。

```c
static	int32	empty		= 0;
static	string	emptystring	= (string)&empty;
```
これは、Goランタイム内で使用されるグローバルな空文字列定数`emptystring`を定義しています。`empty`という`int32`型の変数（値は0）のアドレスを文字列ポインタとして使用することで、`emptystring`の`str`フィールドは有効なメモリ位置を指し、`len`フィールドは0となります。これにより、`nil`ポインタを持つ文字列と、この`emptystring`がセマンティックに等価になります。

```c
void
sys_printstring(string v)
{
	if(v != nil) // ここでnilチェックが追加
		sys_write(1, v->str, v->len);
}
```
`sys_printstring`関数は、文字列を標準出力に書き出すランタイム関数です。変更前は`v->str`を直接使用していましたが、`v`が`nil`の場合に`nil`ポインタ参照が発生する可能性がありました。この変更により、`v`が`nil`でなければ書き出しを行い、`nil`であれば何も書き出さない（空文字列と同じ挙動）という安全な処理が保証されます。

同様に、`cmpstring`（文字列比較）、`sys_catstring`（文字列結合）、`sys_slicestring`（文字列スライス）、`sys_indexstring`（文字列インデックスアクセス）といった他の文字列操作関数にも、引数が`nil`文字列であった場合に`emptystring`に置き換えるロジックが追加されています。これにより、これらの操作が`nil`文字列に対してもパニックを起こさず、空文字列と同じ結果を返すようになります。

### `src/cmd/gc/walk.c` におけるマップ操作の変換ロジックの改善

このファイルはコンパイラのセマンティック分析フェーズを担当し、Goの高級なマップ操作をランタイムの低レベル関数呼び出しに変換します。

```c
// 変更前:
// if(cr != 1) {
//     yyerror("bad shape across assignment");
//     goto ret;
// }

// 変更後:
// ...
// switch(r->op) {
// case OCALLMETH:
// case OCALLINTER:
// case OCALL:
//     if(cr == 1) { // a,b,... = fn() のような多値代入の処理
//         walktype(r, Erv);
//         l = ascompatet(n->op, &n->left, &r->type, 0);
//         if(l != N) {
//             *n = *nod(OLIST, r, reorder2(l));
//         }
//         goto ret;
//     }
//     break;
// case OINDEX:
// case OINDEXPTR:
//     if(cl == 2 && cr == 1) { // a,b = map[] のようなマップの2値アクセス
//         if(!isptrto(r->left->type, TMAP))
//             break;
//         l = mapop(n, top);
//         if(l == N)
//             break;
//         *n = *l;
//         goto ret;
//     }
//     break;
// }
//
// switch(l->op) {
// case OINDEX:
// case OINDEXPTR:
//     if(cl == 1 && cr == 2) { // map[] = a,b のようなマップの2値代入
//         if(!isptrto(l->left->type, TMAP))
//             break;

//         goto ret;
//     }
//     break;

// yyerror("bad shape across assignment - cr=%d cl=%d\n", cr, cl);
// goto ret;
```
この部分は、代入文の左辺と右辺の「形」（要素数）に基づいて、適切な処理を行うようにロジックを大幅に改善しています。特に、マップのキーアクセスや代入が、単一値（`v = m[k]`）だけでなく、2値（`v, ok = m[k]`）や2値代入（`m[k] = v, ok`）の形式で扱われるようになったことを示しています。これらの複雑なケースは、`mapop`というヘルパー関数に処理が委譲され、`cl`（左辺の要素数）と`cr`（右辺の要素数）を引数として渡すことで、適切なランタイム関数（`mapaccess2`, `mapassign1`, `mapassign2`）が呼び出されるようになります。これにより、マップ操作のセマンティクスがより正確にコンパイラによって解釈され、ランタイムに変換されるようになりました。

### `src/runtime/runtime.h` における `Hmap` 構造体への `len` フィールド追加

```c
struct	Hmap
{
	uint32	len;		// must be first
	uint32	keysize;
	uint32	valsize;
	uint32	hint;
    // ...
};
```
マップの内部表現である`Hmap`構造体に`len`フィールドが追加されました。これはマップに含まれる要素の現在の数を保持します。このフィールドは、`sys_newmap`でマップが作成される際に0に初期化され、`sys_mapassign`（要素の追加）でインクリメントされ、`sys_mapassign2`（要素の削除）でデクリメントされます。これにより、Goの組み込み関数`len(map)`がマップの正確な要素数を効率的に返すことができるようになります。この変更は文字列の`nil`化とは直接関係ありませんが、マップの機能強化の一環として同時に行われました。

これらの変更は、Go言語の初期段階において、文字列のセマンティクスをより直感的で堅牢なものにし、マップ操作のコンパイラ変換をより正確に行うための重要なステップでした。

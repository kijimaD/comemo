# [インデックス 23175] ファイルの概要

このコミットは、Goコンパイラの内部パッケージである `cmd/internal/obj` における `Link.Symmorestack` 配列の削除と、それに伴う `Bool2int` 呼び出しの削減を目的としています。Goランタイムにおけるスタック管理、特に `morestack` ルーチンの呼び出しに関連する最適化とコードの簡素化が図られています。

## 元コミット内容

`cmd/internal/obj: Link.Symmorestack を削除`

この変更は、`Bool2int` 呼び出しを削除しようとすることから始まりましたが、最終的には `Link.Symmorestack` 配列の削除が主な目的となりました。この配列は、無意味なキャッシュのように見えました。

## 変更の背景

Goランタイムは、関数の呼び出し時にスタックが不足した場合に、自動的にスタックを拡張するメカニズムを持っています。このメカニズムは「スタック分割 (stack splitting)」と呼ばれ、`runtime.morestack` または `runtime.morestack_noctxt` といった特殊な関数（`morestack` ルーチン）を呼び出すことで実現されます。

`cmd/internal/obj` パッケージは、Goコンパイラのバックエンドの一部であり、アセンブリコードの生成とリンクを担当します。このパッケージ内で、`stacksplit` 関数は、生成されるアセンブリコードにスタックチェックと `morestack` ルーチンへのジャンプを挿入する役割を担っています。

以前の実装では、`obj.Link` 構造体内に `Symmorestack [2]*LSym` という配列が存在し、`runtime.morestack` と `runtime.morestack_noctxt` のシンボルをキャッシュしていました。また、`stacksplit` 関数は、`noctxt` というブール値（コンテキストが必要ないかどうかを示す）を受け取り、`obj.Bool2int(noctxt)` を使用してこのブール値を0または1に変換し、`Symmorestack` 配列のインデックスとして利用していました。

このコミットの背景には、以下の問題意識があったと考えられます。

1.  **無意味なキャッシュ**: `Symmorestack` 配列は、`morestack` ルーチンのシンボルをキャッシュしていましたが、これらのシンボルはリンカの初期化時に一度だけルックアップすれば十分であり、頻繁にアクセスされるわけではないため、キャッシュする意味が薄いと判断されました。
2.  **`Bool2int` 呼び出しの削減**: `Bool2int` はブール値を整数に変換するユーティリティ関数ですが、このような変換はコードの可読性を低下させ、不必要な抽象化を生む可能性があります。直接 `obj.Linklookup` を呼び出すことで、より明確なコードパスを実現できます。

これらの理由から、`Link.Symmorestack` 配列を削除し、`morestack` ルーチンのシンボルを必要に応じて直接 `obj.Linklookup` で取得するように変更することで、コードの簡素化と効率化を図ることが目的とされました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラの内部構造に関する知識が必要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステム。ガベージコレクション、スケジューラ、スタック管理などが含まれます。
*   **スタック分割 (Stack Splitting)**: Goの関数呼び出し規約の一部。関数が呼び出される際に、現在のスタックフレームが十分なサイズを持っているかチェックし、不足している場合は `morestack` ルーチンを呼び出してスタックを拡張する仕組みです。これにより、固定サイズのスタックを持つ他の言語とは異なり、Goは非常に小さなスタックでゴルーチンを開始し、必要に応じて動的に拡張できます。
*   **`morestack` ルーチン**: Goランタイムに存在する特殊なアセンブリ関数（例: `runtime.morestack`, `runtime.morestack_noctxt`, `runtime.morestackc`）。スタックが不足した際に呼び出され、新しいスタックフレームを割り当てたり、既存のスタックを拡張したりする役割を担います。
    *   `runtime.morestack`: 通常の関数呼び出しで使用され、コンテキスト情報（レジスタの状態など）を保存してスタックを拡張します。
    *   `runtime.morestack_noctxt`: コンテキストを保存する必要がない特定のケース（例: シグナルハンドラなど）で使用されます。
    *   `runtime.morestackc`: C言語からGo関数を呼び出す際に使用される `morestack` ルーチンです。
*   **`cmd/internal/obj` パッケージ**: Goコンパイラの内部パッケージの一つで、アセンブラとリンカの共通部分を提供します。Goのソースコードから生成された中間表現（ASTなど）を、ターゲットアーキテクチャのアセンブリ命令に変換し、最終的な実行可能ファイルを生成する過程で重要な役割を果たします。
    *   `obj.Link`: リンカのコンテキストを表す構造体。シンボルテーブル、アセンブリ命令のリスト、リンカオプションなど、リンク処理に必要な情報を含みます。
    *   `obj.LSym`: リンカシンボルを表す構造体。関数、変数、データセクションなどのシンボル情報を保持します。
    *   `obj.Prog`: アセンブリ命令を表す構造体。命令の種類、オペランド、参照するシンボルなどの情報を含みます。
*   **`obj.Linklookup(ctxt *obj.Link, name string, version int)`**: 指定された名前とバージョンを持つシンボルをリンカのコンテキスト (`ctxt`) からルックアップ（検索）する関数。シンボルが見つからない場合は新しく作成されます。
*   **`obj.Bool2int(b bool)`**: ブール値を整数に変換するユーティリティ関数。`true` なら1、`false` なら0を返します。
*   **`obj.NEEDCTXT`**: `cursym.Text.From3.Offset` のフラグの一つで、関数がコンテキストを必要とするかどうかを示すビットフラグ。
*   **`obj.NOSPLIT`**: `p.From3.Offset` のフラグの一つで、関数がスタック分割を必要としないことを示すビットフラグ。

## 技術的詳細

このコミットの主要な変更点は、`obj.Link` 構造体から `Symmorestack [2]*LSym` フィールドを削除し、`stacksplit` 関数内で `morestack` ルーチンのシンボルを直接 `obj.Linklookup` を使って取得するように変更したことです。

以前の `stacksplit` 関数（および `preprocess` 関数）では、`ctxt.Symmorestack[0]` と `ctxt.Symmorestack[1]` にそれぞれ `runtime.morestack` と `runtime.morestack_noctxt` のシンボルをキャッシュしていました。そして、`stacksplit` 関数に渡される `noctxt` ブール値（コンテキストが必要ないかを示す）を `obj.Bool2int` で整数に変換し、`Symmorestack` 配列のインデックスとして使用していました。

このコミットでは、以下の変更が行われました。

1.  **`Link.Symmorestack` の削除**: `src/cmd/internal/obj/link.go` から `Symmorestack [2]*LSym` フィールドが削除されました。これにより、リンカコンテキストが不要なキャッシュを保持しなくなります。
2.  **`preprocess` 関数からのキャッシュ初期化の削除**: 各アーキテクチャ（ARM, ARM64, PPC64, x86）の `obj*.go` ファイルにある `preprocess` 関数から、`ctxt.Symmorestack` を初期化するコードブロックが削除されました。
3.  **`stacksplit` 関数のシグネチャ変更**:
    *   ARM (`obj5.go`), PPC64 (`obj9.go`): `func stacksplit(ctxt *obj.Link, p *obj.Prog, framesize int32, noctxt bool) *obj.Prog` から `func stacksplit(ctxt *obj.Link, p *obj.Prog, framesize int32) *obj.Prog` へと変更され、`noctxt` 引数が削除されました。
    *   ARM64 (`obj7.go`): `func stacksplit(ctxt *obj.Link, p *obj.Prog, framesize int32, noctxt int) *obj.Prog` から `func stacksplit(ctxt *obj.Link, p *obj.Prog, framesize int32) *obj.Prog` へと変更され、`noctxt` 引数が削除されました。
    *   x86 (`obj6.go`): `func stacksplit(ctxt *obj.Link, p *obj.Prog, framesize int32, textarg int32, noctxt bool, jmpok **obj.Prog) *obj.Prog` から `func stacksplit(ctxt *obj.Link, p *obj.Prog, framesize int32, textarg int32, jmpok **obj.Prog) *obj.Prog` へと変更され、`noctxt` 引数が削除されました。
4.  **`stacksplit` 関数内のシンボルルックアップの変更**:
    *   以前は `p.To.Sym = ctxt.Symmorestack[obj.Bool2int(noctxt)]` のように、キャッシュされたシンボルを使用していた箇所が、`p.To.Sym = obj.Linklookup(ctxt, "runtime.morestack_noctxt", 0)` または `p.To.Sym = obj.Linklookup(ctxt, "runtime.morestack", 0)` のように、条件に基づいて直接 `obj.Linklookup` を呼び出す形に変更されました。
    *   具体的には、`cursym.Text.From3.Offset&obj.NEEDCTXT == 0` の条件（コンテキストが不要な場合）が追加され、その場合は `runtime.morestack_noctxt` を、それ以外の場合は `runtime.morestack` をルックアップするように分岐が追加されました。これにより、`Bool2int` の使用が不要になりました。
    *   `stacksplit` 関数を呼び出す側も、`obj.Bool2int(cursym.Text.From3.Offset&obj.NEEDCTXT == 0)` のような `Bool2int` 呼び出しを削除し、`stacksplit` の新しいシグネチャに合わせて引数を調整しています。

この変更により、`morestack` ルーチンのシンボルは必要になった時点で `obj.Linklookup` を通じて取得されるようになり、`Link` 構造体から不要な状態が削除され、コードがよりシンプルになりました。`obj.Linklookup` はシンボルを内部的にキャッシュするため、この変更がパフォーマンスに大きな影響を与えることはありません。

## コアとなるコードの解説

*   **`Link` 構造体からの `Symmorestack` 削除**:
    `src/cmd/internal/obj/link.go` で `type Link struct { ... Symmorestack [2]*LSym ... }` の行が削除されました。これは、`runtime.morestack` と `runtime.morestack_noctxt` のシンボルをキャッシュしていた配列が不要になったことを意味します。リンカのコンテキストからこの状態が取り除かれ、よりクリーンな設計になりました。

*   **`preprocess` 関数からのキャッシュ初期化の削除**:
    各アーキテクチャの `obj*.go` ファイルにある `preprocess` 関数内で、以下のようなコードブロックが削除されました。
    ```go
    if ctxt.Symmorestack[0] == nil {
        ctxt.Symmorestack[0] = obj.Linklookup(ctxt, "runtime.morestack", 0)
        ctxt.Symmorestack[1] = obj.Linklookup(ctxt, "runtime.morestack_noctxt", 0)
    }
    ```
    このコードは、`Symmorestack` 配列がまだ初期化されていない場合に、`morestack` ルーチンのシンボルをルックアップしてキャッシュする役割を担っていました。`Symmorestack` 自体が削除されたため、この初期化コードも不要になりました。

*   **`stacksplit` 関数のシグネチャ変更と内部ロジックの更新**:
    `stacksplit` 関数は、スタックチェックコードを生成し、必要に応じて `morestack` ルーチンへのジャンプ命令を挿入するGoコンパイラの重要な部分です。
    以前は `noctxt` というブール値（または整数）の引数を受け取り、`obj.Bool2int(noctxt)` を使って `Symmorestack` 配列のインデックスを決定していました。
    変更後、`noctxt` 引数は削除され、代わりに `ctxt.Cursym.Text.From3.Offset&obj.NEEDCTXT == 0` という条件分岐が導入されました。
    *   `ctxt.Cursym.Cfunc != 0` の場合（C言語から呼び出されるGo関数）は、引き続き `runtime.morestackc` をルックアップします。
    *   `ctxt.Cursym.Text.From3.Offset&obj.NEEDCTXT == 0` の場合（コンテキストが不要な関数）は、`obj.Linklookup(ctxt, "runtime.morestack_noctxt", 0)` を直接呼び出してシンボルを取得します。
    *   それ以外の場合（通常のGo関数でコンテキストが必要な場合）は、`obj.Linklookup(ctxt, "runtime.morestack", 0)` を直接呼び出してシンボルを取得します。

    この変更により、`Bool2int` の呼び出しが不要になり、`morestack` ルーチンのシンボルを直接 `obj.Linklookup` で取得するようになりました。`obj.Linklookup` は内部的にシンボルをキャッシュするため、この変更がパフォーマンスに悪影響を与えることはありません。むしろ、コードの意図がより明確になり、`Link` 構造体から不要な状態が削除されたことで、全体的な設計が改善されました。

このコミットは、Go言語の`buildmode=c-shared`機能のテストを追加するものです。具体的には、`misc/cgo/testcshared`ディレクトリ以下に以下の新しいファイルが追加されました。

*   `misc/cgo/testcshared/src/p/p.go`: `libgo.go`からインポートされるGoのパッケージ。共有ライブラリの依存関係をテストします。

## 変更の背景

Go 1.5から導入された`buildmode`オプションは、Goプログラムを様々な形式でビルドする機能を提供します。その中でも`c-shared`モードは、GoのコードをC言語から呼び出し可能な共有ライブラリ（Linuxでは`.so`、macOSでは`.dylib`、Windowsでは`.dll`）としてビルドすることを可能にします。これにより、既存のC/C++アプリケーションからGoの機能を再利用したり、Goで書かれたライブラリを他の言語から利用したりする道が開かれました。

この機能は非常に強力である一方で、Goのランタイムが共有ライブラリとして動作する際の挙動、特にGoの`init`関数や`main`関数のライフサイクル、CGOを介したGoとCの間のデータ受け渡し、そしてGoのパッケージ初期化が正しく行われるかなど、多くの側面で厳密なテストが必要です。

このコミットは、`buildmode=c-shared`でビルドされたGo共有ライブラリが、C言語のプログラムから正しくロードされ、エクスポートされた関数が期待通りに動作するかを検証するための包括的なテストスイートを導入することを目的としています。特に、Goの`init`関数が共有ライブラリのロード時に一度だけ実行されること、そして`main`関数が共有ライブラリのコンテキストでは実行されない（またはパニックを起こす）ことを確認することが重要です。これは、Goの共有ライブラリが通常のGo実行可能ファイルとは異なるライフサイクルを持つためです。

## 前提知識の解説

### 1. Goの`buildmode`オプションと`c-shared`

Go 1.5以降、`go build`コマンドには`-buildmode`オプションが追加されました。これにより、Goのソースコードを様々な形式でビルドできます。

*   **`exe` (デフォルト):** 実行可能バイナリを生成します。
*   **`archive`:** C言語のアーカイブライブラリ（`.a`ファイル）を生成します。
*   **`c-archive`:** C言語のアーカイブライブラリとCヘッダーファイルを生成します。C/C++プロジェクトに静的にリンクできます。
*   **`c-shared`:** C言語の共有ライブラリ（`.so`, `.dylib`, `.dll`）とCヘッダーファイルを生成します。C/C++プロジェクトに動的にリンクできます。
*   **`shared`:** Goの共有ライブラリを生成します。他のGoプログラムから動的にロードできます。
*   **`plugin`:** Goのプラグインを生成します。実行中のGoプログラムに動的にロードできます。

このコミットでは、`c-shared`モードに焦点を当てています。このモードでビルドされたGoの共有ライブラリは、C言語のABI（Application Binary Interface）に準拠した関数をエクスポートし、C言語のプログラムから直接呼び出すことができます。

### 2. CGO

CGOは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoのコードを呼び出したりするためのGoの機能です。Goのソースファイル内で`import "C"`と記述することでCGOが有効になります。

*   **`//export FunctionName`:** Goの関数定義の直前にこのディレクティブを記述すると、そのGo関数がC言語から呼び出し可能な関数としてエクスポートされます。エクスポートされた関数は、生成されるCヘッダーファイルに宣言が追加されます。
*   **GoとCの型変換:** CGOはGoとCの間の型変換を自動的に行いますが、ポインタの扱いなど、注意すべき点が多くあります。

### 3. 共有ライブラリと動的ロード

共有ライブラリは、複数のプログラムで共有されるコードの集合です。これにより、ディスクスペースの節約やメモリ使用量の削減、プログラムのモジュール化が可能になります。

*   **静的リンク vs. 動的リンク:**
    *   **静的リンク:** ライブラリのコードが実行可能ファイルに直接組み込まれます。実行可能ファイルは自己完結型になりますが、サイズが大きくなります。
    *   **動的リンク:** 実行可能ファイルはライブラリへの参照のみを持ち、ライブラリはプログラムの実行時にロードされます。
*   **`dlopen`, `dlsym`, `dlclose` (POSIXシステム):**
    *   `dlopen()`: 共有ライブラリをメモリにロードします。
    *   `dlsym()`: ロードされたライブラリから特定のシンボル（関数や変数）のアドレスを取得します。
    *   `dlclose()`: ロードされた共有ライブラリをアンロードします。
    これらは、プログラムが実行時に必要に応じてライブラリをロードし、その中の関数を呼び出す「動的ロード」のメカニズムを提供します。

### 4. Goの`init`関数と`main`関数

*   **`init`関数:** 各パッケージは複数の`init`関数を持つことができ、これらはパッケージがインポートされた際に、そのパッケージ内の他のどの関数よりも先に、かつ自動的に実行されます。Goプログラムの起動時には、依存関係の順序で全ての`init`関数が実行されます。
*   **`main`関数:** 実行可能プログラムのエントリポイントです。通常のGoプログラムでは、`init`関数群の実行後に`main`関数が実行されます。

しかし、`buildmode=c-shared`でビルドされたGoの共有ライブラリの場合、Goの`main`関数は通常の実行可能ファイルのようにエントリポイントとしては機能しません。Goランタイムは共有ライブラリがロードされた際に初期化され、その際に`init`関数群は実行されますが、`main`関数は明示的に呼び出されない限り実行されません。もし`main`関数が実行されてしまうと、それは共有ライブラリの意図しない挙動であり、通常はパニックを引き起こすように設計されています。このテストでは、この挙動も検証しています。

## 技術的詳細

このコミットで追加されたテストスイートは、Goの`buildmode=c-shared`機能の以下の側面を検証します。

1.  **共有ライブラリのビルド:** `go build -buildmode=c-shared -o libgo.so src/libgo/libgo.go`コマンドを使用して、Goのソースコードから`libgo.so`という共有ライブラリを生成します。この際、`src/libgo/libgo.go`と`src/p/p.go`がコンパイルされ、`libgo.go`で`//export`された関数がCから呼び出し可能になります。
2.  **Goの`init`関数の実行確認:**
    *   `libgo.go`には、`init`関数内で`time.Sleep`とチャネルへの送信を行うコードが含まれています。これは、`init`関数が共有ライブラリのロード時に実行されることをシミュレートし、その完了を非同期に確認するためのものです。
    *   `DidInitRun`というエクスポートされたGo関数は、このチャネルから値を受け取れるかどうかで`init`関数が実行されたかを判断します。
3.  **Goの`main`関数の非実行確認:**
    *   `libgo.go`には、`main`関数が呼び出された場合に`panic("FAIL: main ran")`を引き起こすコードが含まれています。
    *   `DidMainRun`というエクスポートされたGo関数は、`main`関数が実行されたかどうかを示す`ranMain`変数の状態を返します。テストでは、この関数が`false`を返すことを期待します。
4.  **パッケージの依存関係のテスト:**
    *   `libgo.go`は`p`パッケージをインポートしています。`p.go`には`FromPkg`というエクスポートされた関数があり、固定値`1024`を返します。
    *   これにより、共有ライブラリが依存するGoパッケージも正しく初期化され、その中の関数がCから呼び出せることを確認します。
5.  **C言語からの呼び出し方法のテスト:**
    *   **静的リンク（`main0.c`）:** `main0.c`は、ビルド時に`libgo.so`を直接リンクします。これにより、CのプログラムがGoの共有ライブラリに静的に依存する場合の挙動をテストします。`DidInitRun`, `DidMainRun`, `FromPkg`を直接呼び出し、期待される結果と比較します。
    *   **動的ロード（`main1.c`）:** `main1.c`は、`dlopen`と`dlsym`を使用して実行時に`libgo.so`をロードし、その中の関数ポインタを取得して呼び出します。これにより、CのプログラムがGoの共有ライブラリを動的にロードする場合の挙動をテストします。
6.  **テストスクリプト（`test.bash`）:**
    *   `test.bash`は、Goの共有ライブラリとCのテストプログラムをビルドします。
    *   `main0.c`をビルドする際には、`$(go env CC) $(go env GOGCCFLAGS) -o testp main0.c libgo.so`のように`libgo.so`をリンクします。
    *   `main1.c`をビルドする際には、`$(go env CC) $(go env GOGCCFLAGS) -o testp main1.c -ldl`のように動的ロードライブラリ（`libdl`）をリンクします。
    *   ビルドされたテストプログラムを実行し、その出力が`PASS`であるかどうかをチェックすることで、テストの成功/失敗を判断します。`LD_LIBRARY_PATH`を設定して、`libgo.so`が正しく見つけられるようにしています。

このテストスイートは、Goの`buildmode=c-shared`機能が提供する主要な機能と、それに伴うGoランタイムの挙動を網羅的に検証するよう設計されています。

### `misc/cgo/testcshared/src/libgo/libgo.go`

```go
package main

import (
	_ "p" // pパッケージをインポート
	"syscall"
	"time"
)

import "C" // CGOを有効にする

var initCh = make(chan int, 1) // init関数の実行を通知するためのチャネル
var ranMain bool               // main関数が実行されたかを示すフラグ

func init() {
	// 意図的に遅いパッケージ初期化関数をエミュレート
	time.Sleep(100 * time.Millisecond)
	initCh <- 42 // init関数が実行されたことをチャネルで通知
}

func main() {
	ranMain = true // main関数が実行されたことを記録
	panic("FAIL: main ran") // 共有ライブラリではmainが実行されるべきではないためパニック
}

//export DidInitRun
func DidInitRun() bool {
	select {
	case x := <-initCh: // init関数からの通知を待つ
		if x != 42 {
			println("want init value of 42, got: ", x)
			syscall.Exit(2)
		}
		return true // init関数が実行された
	default:
		return false // init関数がまだ実行されていない
	}
}

//export DidMainRun
func DidInitRun() bool {
	return ranMain // main関数が実行されたかどうかのフラグを返す
}
```

#include <stdint.h>
#include <stdio.h>

// libgo.soからエクスポートされるGoの関数を宣言
// Goのビルド時に生成されるヘッダーファイル (libgo.h) に含まれる
extern int8_t DidInitRun();
extern int8_t DidMainRun();
extern int32_t FromPkg();

int main(void) {
  int8_t ran_init = DidInitRun();
  if (!ran_init) {
    fprintf(stderr, "ERROR: DidInitRun returned unexpected results: %d\n",
            ran_init);
    return 1;
  }
  int8_t ran_main = DidMainRun();
  if (ran_main) { // mainが実行されたらエラー
    fprintf(stderr, "ERROR: DidMainRun returned unexpected results: %d\n",
            ran_main);
    return 1;
  }
  int32_t from_pkg = FromPkg();
  if (from_pkg != 1024) {
    fprintf(stderr, "ERROR: FromPkg=%d, want %d\n", from_pkg, 1024);
    return 1;
  }
  printf("PASS\n"); // 全てのテストが成功したらPASSを出力
  return 0;
}

### `misc/cgo/testcshared/main1.c`

```c
#include <stdint.h>
#include <stdio.h>
#include <dlfcn.h> // 動的ロードのためのヘッダー

// int8_t型を返す関数を動的にロードしてチェックするヘルパー関数
int check_int8(void* handle, const char* fname, int8_t want) {
  int8_t (*fn)(); // 関数ポインタの宣言
  fn = (int8_t (*)())dlsym(handle, fname); // シンボルを解決
  if (!fn) {
    fprintf(stderr, "ERROR: missing %s: %s\n", fname, dlerror());
    return 1;
  }
  signed char ret = fn();
  if (ret != want) {
    fprintf(stderr, "ERROR: %s=%d, want %d\n", fname, ret, want);
    return 1;
  }
  return 0;
}

// int32_t型を返す関数を動的にロードしてチェックするヘルパー関数
int check_int32(void* handle, const char* fname, int32_t want) {
  int32_t (*fn)();
  fn = (int32_t (*)())dlsym(handle, fname);
  if (!fn) {
    fprintf(stderr, "ERROR: missing %s: %s\n", fname, dlerror());
    return 1;
  }
  int32_t ret = fn();
  if (ret != want) {
    fprintf(stderr, "ERROR: %s=%d, want %d\n", fname, ret, want);
    return 1;
  }
  return 0;
}

int main(int argc, char** argv) {
  // コマンドライン引数から共有ライブラリのパスを取得し、ロード
  void* handle = dlopen(argv[1], RTLD_LAZY | RTLD_GLOBAL);
  if (!handle) {
    fprintf(stderr, "ERROR: failed to open the shared library: %s\n",
		    dlerror());
    return 2;
  }

  int ret = 0;
  // 各Go関数を動的にロードし、期待される結果をチェック
  ret = check_int8(handle, "DidInitRun", 1);
  if (ret != 0) {
    return ret;
  }

  ret = check_int8(handle, "DidMainRun", 0); // mainは実行されないことを期待
  if (ret != 0) {
    return ret;
  }

  ret = check_int32(handle, "FromPkg", 1024);
  if (ret != 0) {
   return ret;
  }
  printf("PASS\n"); // 全てのテストが成功したらPASSを出力
  return 0;
}
```

## コアとなるコードの解説

### `libgo.go`

*   **`init`関数と`initCh`:** `init`関数は、Goの共有ライブラリがロードされる際に自動的に実行されます。この`init`関数は、`time.Sleep`で意図的に遅延を発生させ、`initCh`チャネルに`42`を送信します。これは、`init`関数が実際に実行され、その処理が完了したことを外部から確認するためのメカニズムです。
*   **`main`関数:** `main`関数は`panic("FAIL: main ran")`を含んでいます。Goの共有ライブラリでは、Goの`main`関数は通常の実行可能ファイルのように自動的に実行されるべきではありません。もし実行された場合、それは予期せぬ挙動であり、このパニックによってテストが失敗するように設計されています。
*   **`//export DidInitRun`:** このディレクティブにより、`DidInitRun` Go関数がC言語から呼び出し可能な関数としてエクスポートされます。この関数は`initCh`から値を受け取れるかどうかを`select`文で非ブロック的にチェックし、`init`関数が実行されたかどうかをCに伝えます。
*   **`//export DidMainRun`:** 同様に、`DidMainRun` Go関数もCから呼び出し可能です。この関数は`ranMain`変数の値を返し、Goの`main`関数が実行されたかどうかをCに伝えます。期待される結果は`false`です。
*   **`//export FromPkg`:** `p`パッケージからエクスポートされた`FromPkg`関数は、単に`1024`という整数値を返します。これは、共有ライブラリが依存するGoパッケージも正しく初期化され、その中の関数がCから呼び出せることを確認するためのものです。

### `main0.c`

このCプログラムは、`libgo.so`を静的にリンクしてGoの関数を呼び出します。
*   `DidInitRun()`: Goの`init`関数が実行されたことを確認します。
*   `DidMainRun()`: Goの`main`関数が実行されていないことを確認します。
*   `FromPkg()`: 依存パッケージの関数が正しく呼び出され、期待される値を返すことを確認します。
全てのチェックが成功した場合に`PASS`を出力します。

### `main1.c`

このCプログラムは、`dlopen`と`dlsym`を使用して`libgo.so`を動的にロードし、Goの関数を呼び出します。
*   `dlopen(argv[1], RTLD_LAZY | RTLD_GLOBAL)`: コマンドライン引数で指定されたパス（`./libgo.so`）にある共有ライブラリをロードします。`RTLD_LAZY`はシンボル解決を遅延させ、`RTLD_GLOBAL`はロードされたシンボルを他のライブラリからも利用可能にします。
*   `dlsym(handle, fname)`: ロードされたライブラリから指定された関数名（`fname`）に対応する関数ポインタを取得します。
*   `check_int8`および`check_int32`ヘルパー関数: 取得した関数ポインタを介してGoの関数を呼び出し、その戻り値が期待通りであるかを検証します。
`main0.c`と同様に、`DidInitRun`、`DidMainRun`、`FromPkg`の挙動を検証し、成功した場合に`PASS`を出力します。

### `test.bash`

このシェルスクリプトはテストのオーケストレーションを行います。
1.  `go build -buildmode=c-shared -o libgo.so src/libgo/libgo.go`: Goの共有ライブラリ`libgo.so`をビルドします。
2.  `$(go env CC) ... -o testp main0.c libgo.so`: `main0.c`をコンパイルし、`libgo.so`と静的にリンクして`testp`実行可能ファイルを生成します。`LD_LIBRARY_PATH`を設定して、実行時に`libgo.so`が見つけられるようにします。
3.  `$(go env CC) ... -o testp main1.c -ldl`: `main1.c`をコンパイルし、動的ロードに必要な`libdl`ライブラリとリンクして`testp`実行可能ファイルを生成します。
4.  各`testp`実行可能ファイルを実行し、その標準出力が`PASS`であるかをチェックします。これにより、Goの共有ライブラリが静的リンクと動的ロードの両方で正しく機能することを確認します。
5.  `cleanup`関数と`trap cleanup EXIT`: テストの実行後に生成されたファイル（`libgo.so`と`testp`）を確実に削除します。

これらのコード変更は、Goの`buildmode=c-shared`機能がGoのランタイムのライフサイクル、パッケージの初期化、CGOを介した関数エクスポート、およびC言語からの呼び出しメカニズムに関して、期待される挙動を正確に満たしていることを検証するための堅牢なテストフレームワークを提供します。

# [インデックス 2410] ファイルの概要

このコミットは、Goコンパイラ（`gc`）の字句解析器（lexer）と構文解析器（parser）における文法規則のクリーンアップと簡素化を目的としています。特に、`const`、`var`、`type`、`package`といった識別子の種類を字句解析の段階で区別するのをやめ、すべての事前定義された名前（組み込み関数など）を特別なトークンとして扱わないように変更しています。これにより、コンパイラのフロントエンドがより柔軟になり、文脈に応じた識別子の解決を構文解析器と意味解析器に委ねることで、文法の曖昧さを解消しています。

## 変更の背景

Go言語のコンパイラは、コードを解析する際に字句解析（Lexical Analysis）と構文解析（Syntactic Analysis）という段階を経ます。以前のGoコンパイラ（`gc`）では、字句解析の段階で識別子（名前）の種類（変数名、型名、パッケージ名など）を区別していました。例えば、`LNAME`は一般的な識別子、`LATYPE`は型名、`LPACK`はパッケージ名といった具合です。また、`len`や`cap`のような組み込み関数も特別なトークンとして扱われていました。

しかし、このようなアプローチは、特にGo言語の文法が持つ特定の曖昧さ（例: `T(1)`が型変換なのか関数呼び出しなのか）を解決する上で複雑さを生じさせることがありました。字句解析器が文脈なしに識別子の種類を決定しようとすると、構文解析器が後でその決定を覆す必要が生じたり、あるいは文法規則が不必要に複雑になったりする可能性があります。

このコミットの背景には、以下の目的があったと考えられます。

1.  **文法の簡素化と曖昧さの解消**: 字句解析器の役割を「単なる文字列のトークン化」に限定し、識別子の意味的な解釈（それが変数なのか、型なのか、定数なのか）を、より多くの文脈情報を持つ構文解析器や意味解析器に委ねることで、文法規則を簡素化し、解析時の曖昧さを減らす。
2.  **コンパイラの柔軟性向上**: 識別子の種類を字句解析の段階で厳密に区別しないことで、将来的な言語仕様の変更や、より複雑な文脈依存の解析に対応しやすくなる。
3.  **コードの統一性**: シンボルテーブルにおける識別子の定義方法を統一することで、コンパイラ内部のデータ構造と処理ロジックをより一貫性のあるものにする。

`src/cmd/gc/go.y`のコメントにも「The grammar has 6 reduce/reduce conflicts, caused by input that can be parsed as either a type or an expression depending on context, like the t in t(1).」と明記されており、この変更が文法上の曖昧さの解消を意図していることがわかります。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の概念を把握しておく必要があります。

### 1. Goコンパイラ（`gc`）の構造

Go言語の公式コンパイラである`gc`は、伝統的なコンパイラの構造に従っています。
*   **字句解析器 (Lexer)**: ソースコードを読み込み、意味のある最小単位（トークン）に分割します。例えば、`var x int = 10`というコードは、`var`（キーワード）、`x`（識別子）、`int`（識別子）、`=`（演算子）、`10`（リテラル）といったトークンに分割されます。このコミット以前は、`x`と`int`を異なる種類の識別子トークンとして区別していました。
*   **構文解析器 (Parser)**: 字句解析器が生成したトークンの並びが、言語の文法規則に合致しているかを検証し、抽象構文木（AST: Abstract Syntax Tree）を構築します。`gc`ではYacc（またはその互換ツール）で生成されたパーサーが`go.y`ファイルに基づいて動作します。
*   **意味解析器 (Semantic Analyzer)**: 構文解析器が生成したASTに対し、型チェック、名前解決、スコープチェックなどの意味的な検証を行います。この段階で、識別子が変数、型、関数、定数のいずれを指すのかが最終的に決定されます。
*   **シンボルテーブル (Symbol Table)**: コンパイル中に、プログラム内で宣言されたすべての識別子（変数名、関数名、型名など）に関する情報を格納・管理するデータ構造です。識別子の名前、型、スコープ、定義されている場所などの情報が含まれます。

### 2. 字句解析と構文解析の連携

通常、字句解析器は文脈に依存せず、単純なパターンマッチングでトークンを生成します。構文解析器は、これらのトークン列を文法規則に照らし合わせて解釈し、ASTを構築します。文脈依存の解釈は構文解析器や意味解析器の役割です。

このコミット以前は、`gc`の字句解析器が識別子の種類（変数名か型名かなど）をある程度「推測」してトークンを生成していました。これは、字句解析器がより多くの情報を保持しているため、構文解析器の負担を減らすという意図があったのかもしれません。しかし、これが逆に文法の曖昧さを生み、パーサーの複雑さを増す原因となることがありました。

### 3. Yacc/Bison

`src/cmd/gc/go.y`はYacc（Yet Another Compiler Compiler）形式の文法定義ファイルです。Yaccは、文法規則を記述することで、その文法を解析する構文解析器（パーサー）のC言語コードを自動生成するツールです。
*   `%token`: 字句解析器から受け取るトークンを定義します。
*   `%type`: 構文規則の非終端記号（中間的な文法要素）が持つ値の型を定義します。
*   `%%`: 文法規則の開始と終了を示します。

### 4. `Sym`構造体と識別子の定義

Goコンパイラ内部では、`Sym`（Symbol）構造体がシンボルテーブルのエントリとして各識別子の情報を保持しています。このコミット以前は、`Sym`構造体には`oname`（変数名の場合の`Node*`）、`otype`（型名の場合の`Type*`）、`oconst`（定数名の場合の`Node*`）といった、識別子の種類に応じた専用のフィールドがありました。

## 技術的詳細

このコミットの主要な技術的変更点は、字句解析器と構文解析器の間の責任分担の見直しと、シンボルテーブルのデータ構造の統一です。

### 1. 字句解析器の簡素化 (`src/cmd/gc/go.y`, `src/cmd/gc/lex.c`)

*   **識別子トークンの統合**: 以前は`LNAME`（一般的な名前）、`LATYPE`（型名）、`LPACK`（パッケージ名）のように、識別子の種類を区別する複数のトークンが存在しました。このコミットでは、これらを`LNAME`に統合し、字句解析の段階ではほとんどの識別子を単なる「名前」として扱います。
    *   `go.y`から`LATYPE`, `LPACK`トークンが削除されています。
    *   `go.y`の`%token`定義から、`LVAR`, `LTYPE`, `LCONST`, `LPACKAGE`などのキーワードも削除され、これらは通常の識別子として扱われるようになります。これにより、`len`, `cap`, `panic`, `print`, `new`, `make`といった組み込み関数も特別なトークンではなくなります。
*   **`lexical`フィールドの役割変更**: `Sym`構造体の`lexical`フィールドは、識別子の種類を示すために使われていましたが、この変更によりその役割が大幅に縮小されます。`typeinit`関数の引数から`lex`が削除され、`s->lexical = lex;`のような代入が削除されていることからもわかります。

### 2. `Sym`構造体の変更と`def`フィールドの導入 (`src/cmd/gc/go.h`)

*   **`oname`, `otype`, `oconst`の廃止と`def`への統合**: `Sym`構造体から、識別子の種類に応じた専用の定義フィールド（`oname`, `otype`, `oconst`）が削除され、代わりに単一の`Node* def`フィールドが導入されました。

    *   `def`フィールドは、そのシンボルが表す実体（変数、型、定数、パッケージ）を指す`Node`へのポインタとなります。これにより、シンボルテーブルのエントリがより汎用的な形式で定義を保持できるようになります。
*   **`Node`構造体への`builtin`フィールド追加**: 組み込み関数などを識別するために、`Node`構造体に`builtin`フィールドが追加されました。

### 3. 構文解析器の変更 (`src/cmd/gc/go.y`)

*   **文法規則の調整**: 字句解析器が識別子の種類を区別しなくなったため、構文解析器がその責任を負うように文法規則が変更されました。
    *   `name`, `dotname`, `expr_or_type`といった新しい非終端記号が導入され、文脈に応じて識別子を式または型として解釈するロジックが追加されています。
    *   `pexpr`（primary expression）の規則が拡張され、型変換や複合リテラルがより柔軟に扱えるようになりました。特に`pexpr '.' '(' expr_or_type ')'`の規則は、`.(type)`のような型アサーションや型スイッチのケースを処理するためのものです。
    *   関数引数の解析ロジック（`arg_type_list`関連）も簡素化され、`checkarglist`関数が`Node*`を返すように変更されています。これにより、引数リストが名前付き引数と匿名引数のどちらであるかをより柔軟に処理できるようになります。
*   **曖昧さの解決**: `go.y`の冒頭のコメントにあるように、型と式の曖昧さを解決するために、`%prec`（優先順位）ディレクティブが使用されています。例えば、`expr_or_type`の規則で`type %prec PreferToRightParen`とすることで、`t(1)`のようなケースで`t`が型として解釈されるよりも、式として解釈されることを優先する（またはその逆）といった制御が行われます。

### 4. 宣言処理とエクスポート処理の変更 (`src/cmd/gc/dcl.c`, `src/cmd/gc/export.c`)

*   **`Sym->def`への移行**: `Sym`構造体の変更に伴い、`dcl.c`と`export.c`内の`s->oname`, `s->otype`, `s->oconst`へのアクセスがすべて`s->def`を介するように変更されました。
    *   例えば、`s->otype`は`s->def->type`に、`s->oconst`は`s->def`に、`s->oname`も`s->def`に置き換えられています。
    *   `typenod(Type *t)`という新しいヘルパー関数が追加され、`Type`から対応する`OTYPE`ノードを取得または作成する役割を担います。これにより、型も`Node`として`Sym->def`に格納できるようになります。
*   **型情報の更新ロジック**: `updatetype`や`addtyp`などの関数で、型の定義を更新する際のロジックが`Sym->def`を使用するように変更されています。
*   **インポート処理の変更**: `importconst`, `importvar`, `importtype`などのインポート関連関数も、`Sym->def`フィールドを利用するように修正されています。これにより、インポートされたシンボルの種類をより統一的に扱えるようになります。

## コアとなるコードの解説

### `Sym`構造体の`def`フィールドへの統合

最も根本的な変更は、`src/cmd/gc/go.h`における`Sym`構造体の定義変更です。
以前は、シンボルが変数、型、定数のいずれであるかに応じて、`oname`、`otype`、`oconst`という異なるフィールドにその定義を格納していました。これは、シンボルの種類を字句解析の段階で区別していた名残とも言えます。

```c
// 変更前 (概念)
struct Sym {
    char* name;
    Node* oname;  // If it's a variable
    Type* otype;  // If it's a type
    Node* oconst; // If it's a constant
    int32 lexical; // LNAME, LATYPE, LPACK etc.
    // ...
};
```

このコミットにより、これらのフィールドは廃止され、`Node* def`という単一のフィールドに統合されました。

```c
// 変更後 (概念)
struct Sym {
    char* name;
    Node* def;    // Definition: ONAME, OTYPE, OLITERAL, OPACK node
    // ...
};
```

この変更の意義は以下の通りです。

1.  **統一されたシンボル表現**: シンボルテーブル内のすべての識別子定義が、`Node`という共通の抽象データ型で表現されるようになりました。これにより、コンパイラの他の部分（意味解析、コード生成など）がシンボルの種類を問わず、`Sym->def`を通じてその定義にアクセスできるようになり、コードの統一性と保守性が向上します。
2.  **字句解析器の負担軽減**: 字句解析器は、識別子が変数なのか型なのかといった意味的な情報を判断する必要がなくなりました。すべての識別子は一旦`LNAME`としてトークン化され、その後の構文解析や意味解析の段階で`Sym->def`に適切な`Node`（`ONAME`、`OTYPE`など）が設定されます。
3.  **文脈依存の解決**: `go.y`の変更と合わせて、構文解析器がより多くの文脈情報に基づいて識別子の種類を解決できるようになりました。例えば、`T(1)`のような曖昧な構文では、`T`が型として使われているのか、それとも関数名として使われているのかを、周囲の文法規則から判断します。`Sym->def`が`OTYPE`ノードを指していれば型、`ONAME`ノードを指していれば変数/関数と判断できます。
4.  **`typenod`関数の導入**: `src/cmd/gc/dcl.c`に追加された`typenod`関数は、`Type`構造体から対応する`OTYPE`ノードを取得または作成する役割を担います。これにより、`Type`も`Node`として`Sym->def`に格納できるようになり、型定義の管理がより一貫したものになります。

## 変更の背景

Go言語のコンパイラは、コードを解析する際に字句解析（Lexical Analysis）と構文解析（Syntactic Analysis）という段階を経ます。以前のGoコンパイラ（`gc`）では、字句解析の段階で識別子（名前）の種類（変数名、型名、パッケージ名など）を区別していました。例えば、`LNAME`は一般的な識別子、`LATYPE`は型名、`LPACK`はパッケージ名といった具合です。また、`len`や`cap`のような組み込み関数も特別なトークンとして扱われていました。

しかし、このようなアプローチは、特にGo言語の文法が持つ特定の曖昧さ（例: `T(1)`が型変換なのか関数呼び出しなのか）を解決する上で複雑さを生じさせることがありました。字句解析器が文脈なしに識別子の種類を決定しようとすると、構文解析器が後でその決定を覆す必要が生じたり、あるいは文法規則が不必要に複雑になったりする可能性があります。

このコミットの背景には、以下の目的があったと考えられます。

1.  **文法の簡素化と曖昧さの解消**: 字句解析器の役割を「単なる文字列のトークン化」に限定し、識別子の意味的な解釈（それが変数なのか、型なのか、定数なのか）を、より多くの文脈情報を持つ構文解析器や意味解析器に委ねることで、文法規則を簡素化し、解析時の曖昧さを減らす。
2.  **コンパイラの柔軟性向上**: 識別子の種類を字句解析の段階で厳密に区別しないことで、将来的な言語仕様の変更や、より複雑な文脈依存の解析に対応しやすくなる。
3.  **コードの統一性**: シンボルテーブルにおける識別子の定義方法を統一することで、コンパイラ内部のデータ構造と処理ロジックをより一貫性のあるものにする。

`src/cmd/gc/go.y`のコメントにも「The grammar has 6 reduce/reduce conflicts, caused by input that can be parsed as either a type or an expression depending on context, like the t in t(1).」と明記されており、この変更が文法上の曖昧さの解消を意図していることがわかります。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の概念を把握しておく必要があります。

### 1. Goコンパイラ（`gc`）の構造

Go言語の公式コンパイラである`gc`は、伝統的なコンパイラの構造に従っています。
*   **字句解析器 (Lexer)**: ソースコードを読み込み、意味のある最小単位（トークン）に分割します。例えば、`var x int = 10`というコードは、`var`（キーワード）、`x`（識別子）、`int`（識別子）、`=`（演算子）、`10`（リテラル）といったトークンに分割されます。このコミット以前は、`x`と`int`を異なる種類の識別子トークンとして区別していました。
*   **構文解析器 (Parser)**: 字句解析器が生成したトークンの並びが、言語の文法規則に合致しているかを検証し、抽象構文木（AST: Abstract Syntax Tree）を構築します。`gc`ではYacc（またはその互換ツール）で生成されたパーサーが`go.y`ファイルに基づいて動作します。
*   **意味解析器 (Semantic Analyzer)**: 構文解析器が生成したASTに対し、型チェック、名前解決、スコープチェックなどの意味的な検証を行います。この段階で、識別子が変数、型、関数、定数のいずれを指すのかが最終的に決定されます。
*   **シンボルテーブル (Symbol Table)**: コンパイル中に、プログラム内で宣言されたすべての識別子（変数名、関数名、型名など）に関する情報を格納・管理するデータ構造です。識別子の名前、型、スコープ、定義されている場所などの情報が含まれます。

### 2. 字句解析と構文解析の連携

通常、字句解析器は文脈に依存せず、単純なパターンマッチングでトークンを生成します。構文解析器は、これらのトークン列を文法規則に照らし合わせて解釈し、ASTを構築します。文脈依存の解釈は構文解析器や意味解析器の役割です。

このコミット以前は、`gc`の字句解析器が識別子の種類（変数名か型名かなど）をある程度「推測」してトークンを生成していました。これは、字句解析器がより多くの情報を保持しているため、構文解析器の負担を減らすという意図があったのかもしれません。しかし、これが逆に文法の曖昧さを生み、パーサーの複雑さを増す原因となることがありました。

### 3. Yacc/Bison

`src/cmd/gc/go.y`はYacc（Yet Another Compiler Compiler）形式の文法定義ファイルです。Yaccは、文法規則を記述することで、その文法を解析する構文解析器（パーサー）のC言語コードを自動生成するツールです。
*   `%token`: 字句解析器から受け取るトークンを定義します。
*   `%type`: 構文規則の非終端記号（中間的な文法要素）が持つ値の型を定義します。
*   `%%`: 文法規則の開始と終了を示します。

### 4. `Sym`構造体と識別子の定義

Goコンパイラ内部では、`Sym`（Symbol）構造体がシンボルテーブルのエントリとして各識別子の情報を保持しています。このコミット以前は、`Sym`（Symbol）構造体には`oname`（変数名の場合の`Node*`）、`otype`（型名の場合の`Type*`）、`oconst`（定数名の場合の`Node*`）といった、識別子の種類に応じた専用のフィールドがありました。

## 技術的詳細

このコミットの主要な技術的変更点は、字句解析器と構文解析器の間の責任分担の見直しと、シンボルテーブルのデータ構造の統一です。

### 1. 字句解析器の簡素化 (`src/cmd/gc/go.y`, `src/cmd/gc/lex.c`)

*   **識別子トークンの統合**: 以前は`LNAME`（一般的な名前）、`LATYPE`（型名）、`LPACK`（パッケージ名）のように、識別子の種類を区別する複数のトークンが存在しました。このコミットでは、これらを`LNAME`に統合し、字句解析の段階ではほとんどの識別子を単なる「名前」として扱います。
    *   `go.y`から`LATYPE`, `LPACK`トークンが削除されています。
    *   `go.y`の`%token`定義から、`LVAR`, `LTYPE`, `LCONST`, `LPACKAGE`などのキーワードも削除され、これらは通常の識別子として扱われるようになります。これにより、`len`, `cap`, `panic`, `print`, `new`, `make`といった組み込み関数も特別なトークンではなくなります。
*   **`lexical`フィールドの役割変更**: `Sym`構造体の`lexical`フィールドは、識別子の種類を示すために使われていましたが、この変更によりその役割が大幅に縮小されます。`typeinit`関数の引数から`lex`が削除され、`s->lexical = lex;`のような代入が削除されていることからもわかります。

### 2. `Sym`構造体の変更と`def`フィールドの導入 (`src/cmd/gc/go.h`)

*   **`oname`, `otype`, `oconst`の廃止と`def`への統合**: `Sym`構造体から、識別子の種類に応じた専用の定義フィールド（`oname`, `otype`, `oconst`）が削除され、代わりに単一の`Node* def`フィールドが導入されました。

### 3. 構文解析器の変更 (`src/cmd/gc/go.y`)

*   **文法規則の調整**: 字句解析器が識別子の種類を区別しなくなったため、構文解析器がその責任を負うように文法規則が変更されました。
    *   `name`, `dotname`, `expr_or_type`といった新しい非終端記号が導入され、文脈に応じて識別子を式または型として解釈するロジックが追加されています。
    *   `pexpr`（primary expression）の規則が拡張され、型変換や複合リテラルがより柔軟に扱えるようになりました。特に`pexpr '.' '(' expr_or_type ')'`の規則は、`.(type)`のような型アサーションや型スイッチのケースを処理するためのものです。
    *   関数引数の解析ロジック（`arg_type_list`関連）も簡素化され、`checkarglist`関数が`Node*`を返すように変更されています。これにより、引数リストが名前付き引数と匿名引数のどちらであるかをより柔軟に処理できるようになります。
*   **曖昧さの解決**: `go.y`の冒頭のコメントにあるように、型と式の曖昧さを解決するために、`%prec`（優先順位）ディレクティブが使用されています。例えば、`expr_or_type`の規則で`type %prec PreferToRightParen`とすることで、`t(1)`のようなケースで`t`が型として解釈されるよりも、式として解釈されることを優先する（またはその逆）といった制御が行われます。

### 4. 宣言処理とエクスポート処理の変更 (`src/cmd/gc/dcl.c`, `src/cmd/gc/export.c`)

*   **`Sym->def`への移行**: `Sym`構造体の変更に伴い、`dcl.c`と`export.c`内の`s->oname`, `s->otype`, `s->oconst`へのアクセスがすべて`s->def`を介するように変更されました。
    *   例えば、`s->otype`は`s->def->type`に、`s->oconst`は`s->def`に、`s->oname`も`s->def`に置き換えられています。
    *   `typenod(Type *t)`という新しいヘルパー関数が追加され、`Type`から対応する`OTYPE`ノードを取得または作成する役割を担います。これにより、型も`Node`として`Sym->def`に格納できるようになります。
*   **型情報の更新ロジック**: `updatetype`や`addtyp`などの関数で、型の定義を更新する際のロジックが`Sym->def`を使用するように変更されています。
*   **インポート処理の変更**: `importconst`, `importvar`, `importtype`などのインポート関連関数も、`Sym->def`フィールドを利用するように修正されています。これにより、インポートされたシンボルの種類をより統一的に扱えるようになります。

## コアとなるコードの解説

### `Sym`構造体の`def`フィールドへの統合

最も根本的な変更は、`src/cmd/gc/go.h`における`Sym`構造体の定義変更です。
以前は、シンボルが変数、型、定数のいずれであるかに応じて、`oname`、`otype`、`oconst`という異なるフィールドにその定義を格納していました。これは、シンボルの種類を字句解析の段階で区別していた名残とも言えます。

```c
// 変更前 (概念)
struct Sym {
    char* name;
    Node* oname;  // If it's a variable
    Type* otype;  // If it's a type
    Node* oconst; // If it's a constant
    int32 lexical; // LNAME, LATYPE, LPACK etc.
    // ...
};
```

このコミットにより、これらのフィールドは廃止され、`Node* def`という単一のフィールドに統合されました。

```c
// 変更後 (概念)
struct Sym {
    char* name;
    Node* def;    // Definition: ONAME, OTYPE, OLITERAL, OPACK node
    // ...
};
```

この変更の意義は以下の通りです。

1.  **統一されたシンボル表現**: シンボルテーブル内のすべての識別子定義が、`Node`という共通の抽象データ型で表現されるようになりました。これにより、コンパイラの他の部分（意味解析、コード生成など）がシンボルの種類を問わず、`Sym->def`を通じてその定義にアクセスできるようになり、コードの統一性と保守性が向上します。
2.  **字句解析器の負担軽減**: 字句解析器は、識別子が変数なのか型なのかといった意味的な情報を判断する必要がなくなりました。すべての識別子は一旦`LNAME`としてトークン化され、その後の構文解析や意味解析の段階で`Sym->def`に適切な`Node`（`ONAME`、`OTYPE`など）が設定されます。
3.  **文脈依存の解決**: `go.y`の変更と合わせて、構文解析器がより多くの文脈情報に基づいて識別子の種類を解決できるようになりました。例えば、`T(1)`のような曖昧な構文では、`T`が型として使われているのか、それとも関数名として使われているのかを、周囲の文法規則から判断します。`Sym->def`が`OTYPE`ノードを指していれば型、`ONAME`ノードを指していれば変数/関数と判断できます。
4.  **`typenod`関数の導入**: `src/cmd/gc/dcl.c`に追加された`typenod`関数は、`Type`構造体から対応する`OTYPE`ノードを取得または作成する役割を担います。これにより、型も`Node`として`Sym->def`に格納できるようになり、型定義の管理がより一貫したものになります。

この変更により、`go.y`はより一般的な`LNAME`トークンを受け取り、その意味を文脈から判断する責任を負うことになります。例えば、`type T struct {}`という宣言では、`T`は`LNAME`として渡されますが、`type`キーワードの後に続くため、パーサーはこれを型名として解釈します。

また、`pexpr`（primary expression）の規則が拡張され、`pexpr '.' '(' expr_or_type ')'`のような構文が追加されています。これは、`x.(type)`のような型アサーションや型スイッチの構文をより柔軟に処理するためのものです。`expr_or_type`という新しい非終端記号は、その名の通り、式としても型としても解釈されうる要素を表し、パーサーが文脈に応じて適切な解釈を行うことを可能にします。

これらの変更は、Goコンパイラのフロントエンドの設計思想を、より「文脈依存の解析」にシフトさせる重要な一歩と言えます。

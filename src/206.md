## 変更の背景

このコミットは、Go言語の初期開発段階における重要な言語仕様の整備と、コンパイラの機能強化を目的としています。

1.  **同一ブロック内での変数再宣言の禁止**: Go言語では、同じスコープ（ブロック）内で同じ名前の変数を再宣言することは許可されていません。これは、プログラミングエラーを防ぎ、コードの可読性を高めるための重要なルールです。このコミット以前は、コンパイラがこのルールを適切に強制していなかった可能性があり、それを修正し、より厳密なエラーチェックを導入する必要がありました。特に、`:=`（ショート変数宣言）演算子を使用した場合の挙動を明確にする必要がありました。
2.  **多値マップインデックスへの半歩**: Go言語のマップ（`map`）は、キーが存在しない場合にゼロ値と`false`を返すという特徴的な多値返却（`value, ok := m[key]`）をサポートしています。このコミットは、この多値返却のセマンティクスをコンパイラが正しく処理するための初期段階の変更を含んでいます。特に、`:=`演算子とマップのインデックス操作が組み合わされた場合の挙動を考慮に入れる必要がありました。

これらの変更は、Go言語の設計思想である「シンプルさ」と「安全性」をコンパイラレベルで実現するための基盤を固めるものです。

## 前提知識の解説

### Go言語のコンパイルプロセス

Goコンパイラ（`gc`）は、ソースコードを機械語に変換する多段階のプロセスを経ます。

1.  **字句解析 (Lexical Analysis)**: `src/cmd/gc/lex.c` が担当。ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換します。
2.  **構文解析 (Syntax Analysis)**: `src/cmd/gc/go.y` が担当。トークンのストリームを解析し、言語の文法規則に従って抽象構文木（AST: Abstract Syntax Tree）を構築します。Yacc/Bisonのようなパーサジェネレータが使用されます。
3.  **意味解析 (Semantic Analysis)**: `src/cmd/gc/walk.c`, `src/cmd/gc/dcl.c` などが担当。ASTを走査し、型チェック、スコープ解決、名前解決、定数畳み込みなどの意味的な検証と変換を行います。この段階で、変数宣言の重複チェックや、マップの多値返却の処理などが実行されます。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTを、より低レベルの中間表現（IR）に変換します。
5.  **コード生成 (Code Generation)**: `src/cmd/6g/cgen.c`, `src/cmd/6g/gen.c`, `src/cmd/6g/gsubr.c` などが担当。中間表現をターゲットアーキテクチャ（この場合はx86-64）の機械語に変換します。

### Go言語のスコープと変数宣言

Go言語では、変数は特定のブロック（`{}`で囲まれた領域）内で宣言され、そのブロック内でのみ有効です。

*   **`var` キーワード**: `var x int` のように明示的に変数を宣言します。
*   **ショート変数宣言 (`:=`)**: `x := 10` のように、変数宣言と初期化を同時に行います。この演算子は、新しい変数を宣言する場合にのみ使用できます。もし同じスコープに同じ名前の変数が既に存在する場合、`:=`はコンパイルエラーとなります（ただし、複数の変数を宣言する際に、少なくとも1つが新しい変数であればエラーにならないという例外ルールもありますが、このコミットの時点ではまだその複雑なルールは導入されていない可能性があります）。

### Go言語のマップと多値返却

Goのマップはキーと値のペアを格納するデータ構造です。マップから値を取得する際、キーが存在しない場合でもプログラムがパニックを起こさないように、Goは2つの値を返すことができます。

```go
value, ok := myMap[key]
```

ここで、`value`はキーに対応する値（キーが存在しない場合は値の型のゼロ値）であり、`ok`はキーが存在したかどうかを示す真偽値です。この`ok`の概念をコンパイラが適切に処理できるようにする必要があります。

### C言語のコンパイラ実装におけるデータ構造

GoコンパイラはC言語で書かれており、ASTノード、型情報、シンボルテーブルのエントリなどを表現するためにCの構造体を使用しています。

*   `Node`: ASTの各ノードを表す構造体。演算子、変数、関数呼び出しなどがノードとして表現されます。
*   `Type`: 型情報を表す構造体。`int`, `string`, `map`, `func` などの型が定義されます。
*   `Sym`: シンボルテーブルのエントリを表す構造体。変数名、関数名、型名などの識別子とその属性（型、スコープなど）を管理します。

## 技術的詳細

### 1. 同一ブロック内での変数再宣言の禁止

このコミットの主要な変更点の一つは、同一ブロック内での変数再宣言を厳密にチェックするようになったことです。これは、`src/cmd/gc/dcl.c` と `src/cmd/gc/go.h` の変更によって実現されています。

*   **ブロック番号の導入**: `src/cmd/gc/go.h` の `Sym` 構造体に `vblock` (variable block) と `tblock` (type block) というフィールドが追加されました。これらは、シンボル（変数や型）が宣言されたブロックの識別子を保持します。また、グローバル変数として `block` (現在のブロック番号) と `blockgen` (最大ブロック番号) が導入されました。
*   **ブロックの管理**: `src/cmd/gc/lex.c` で `block` と `blockgen` が初期化されます。`src/cmd/gc/dcl.c` の `markdcl` 関数（新しいブロックに入る際に呼び出される）で `blockgen` をインクリメントし、`block` を新しい `blockgen` の値に設定することで、新しいブロックが開始されたことを記録します。`popdcl` 関数（ブロックを抜ける際に呼び出される）では、`block` を前のブロックの値に戻します。
*   **再宣言チェック**: `src/cmd/gc/dcl.c` の `addvar` 関数（変数をシンボルテーブルに追加する）と `addtyp` 関数（型をシンボルテーブルに追加する）において、シンボルが既に現在の `block` で宣言されているかどうかを `s->vblock == block` または `s->tblock == block` でチェックするようになりました。もし同じブロックで再宣言されている場合、`yyerror` を呼び出してコンパイルエラーを報告します。

このメカニズムにより、Goコンパイラはより正確にスコープルールを強制し、プログラマが意図しない変数再宣言を行うことを防ぎます。

### 2. 多値マップインデックスへの半歩

このコミットは、`value, ok := m[key]` のような多値返却を伴うマップインデックス操作をサポートするための初期段階の変更を含んでいます。

*   **`ONONAME` ノードの導入**: `src/cmd/gc/go.h` と `src/cmd/gc/subr.c` で `ONONAME` という新しいASTノードタイプが導入されました。これは、`:=` 演算子で宣言されるが、まだ具体的な名前が割り当てられていない（または一時的な）変数を表すために使用される可能性があります。`src/cmd/gc/walk.c` の `oldname` 関数が `ONONAME` ノードを返すように変更されています。
*   **`colas` 関数の追加**: `src/cmd/gc/walk.c` に `colas` という新しい関数が追加されました。この関数は、`:=` 演算子の左辺（変数リスト）と右辺（式リスト）を受け取り、左辺の各変数に対応する新しい名前（`newname`）を生成し、その型を右辺の式の型に基づいて決定します。特に、右辺が関数呼び出し（`OCALLMETH`, `OCALLINTER`, `OCALL`）やマップインデックス操作（`OINDEX`, `OINDEXPTR`）である場合に、多値返却を考慮して左辺の変数の型を決定するロジックが含まれています。
    *   マップインデックスの場合、`colas` 関数は左辺が2つの要素（`value`, `ok`）を持つことを期待し、それぞれにマップの値の型と`TBOOL`型を割り当てます。
*   **`go.y` の変更**: `src/cmd/gc/go.y` の `noninc_stmt` ルールが変更され、`expr_list LCOLAS expr_list` の形式が `colas` 関数を呼び出すように修正されました。これにより、`:=` 演算子を使った宣言が `colas` 関数によって処理されるようになります。
*   **コンパイラバックエンドの変更**: `src/cmd/6g/cgen.c`, `src/cmd/6g/gen.c`, `src/cmd/6g/gsubr.c` では、デバッグ出力の追加や、関数呼び出し（`OCALLMETH`, `OCALLINTER`, `OCALL`）の処理に関連する変更が見られます。特に `cgen_aret` という新しい関数が追加されていますが、これはコミットメッセージにある「half-step」の通り、まだ完全には機能していない（`fatal("cgen_aret")` が含まれている）ようです。これは、多値返却の処理をバックエンドでどのように扱うかという課題に対する初期の試みと考えられます。

### 3. その他の変更

*   **Yacc文法ファイルの複雑化**: `src/cmd/gc/go.y` では、`vardcl`, `typedcl`, `common_dcl`, `fnres`, `type`, `fntypeh` などの多くの文法ルールに `A` と `B` プレフィックスを持つ新しいルールが追加されています。これは、Yacc/Bisonにおける文法規則の曖昧性解消や、特定のコンテキストでのみ有効な構文を表現するための一般的な手法です。これにより、コンパイラがより複雑な構文を正確に解析できるようになります。
*   **エラーメッセージの改善**: `src/cmd/gc/lex.c` では、エスケープシーケンスや16進数/8進数リテラルに関する警告が `warn` から `yyerror` に変更されています。これにより、これらの問題がコンパイルエラーとして扱われるようになり、より厳密なコードチェックが行われるようになりました。

Node*
colas(Node *nl, Node *nr)
{
	Iter savel, saver;
	Node *l, *r, *a, *n;
	Type *t;
	int cl, cr;

	/* nl is an expression list.
	 * nr is an expression list.
	 * return a newname-list from
	 * the types from the rhs.
	 */
	n = N;
	cr = listcount(nr);
	cl = listcount(nl);
	if(cl != cr) {
		if(cr == 1)
			goto multi;
		goto badt;
	}

	l = listfirst(&savel, &nl);
	r = listfirst(&saver, &nr);

loop:
	if(l == N)
		return n;

	walktype(r, Erv);
	defaultlit(r);
	a = old2new(l, r->type);
	if(n == N)
		n = a;
	else
		n = nod(OLIST, n, a);

	l = listnext(&savel);
	r = listnext(&saver);
	goto loop;

multi:
	/*
	 * there is a list on the left
	 * and a mono on the right.
	 * go into the right to get
	 * individual types for the left.
	 */
	switch(nr->op) {
	default:
		goto badt;

	case OCALLMETH:
	case OCALLINTER:
	case OCALL:
		walktype(nr->left, Erv);
		t = nr->left->type;
		if(t == T || t->etype != TFUNC)
			goto badt;
		if(t->outtuple != cl)
			goto badt;

		l = listfirst(&savel, &nl);
		t = structfirst(&saver, getoutarg(t));
		while(l != N) {
			a = old2new(l, t);
			if(n == N)
				n = a;
			else
				n = nod(OLIST, n, a);
			l = listnext(&savel);
			t = structnext(&saver);
		}
		break;

	case OINDEX:
	case OINDEXPTR:
		// check if rhs is a map index.
		// if so, types are bool,maptype
		if(cl != 2)
			goto badt;
		walktype(nr->left, Elv);
		t = nr->left->type;
		if(t != T && isptr[t->etype])
			t = t->type;
		if(t == T || t->etype != TMAP)
			goto badt;

		a = old2new(nl->left, types[TBOOL]);
		n = a;
		a = old2new(nl->right, t->type);
		n = nod(OLIST, n, a);
		break;
	}
	return n;

badt:
	yyerror("shape error across :=");
	return nl;
}

## コアとなるコードの解説

### 1. 変数再宣言チェック

`src/cmd/gc/dcl.c` の `addvar` および `addtyp` 関数における `if(s->vblock == block)` (または `s->tblock == block`) のチェックは、このコミットの最も直接的な影響を示す部分です。

*   `s->vblock` (または `s->tblock`) は、現在処理しているシンボル `s` がどのブロックで宣言されたかを示します。
*   `block` は、現在コンパイラが処理しているソースコードのブロックの識別子です。
*   この条件が真である場合、それは同じブロック内で同じ名前の変数（または型）が再宣言されたことを意味します。
*   `yyerror` が呼び出され、コンパイルエラーが報告されます。これにより、Go言語の厳密なスコープルールがコンパイラによって強制されるようになりました。

### 2. `colas` 関数と多値マップインデックス

`colas` 関数は、Go言語の `:=` 演算子のセマンティクスを実装する上で非常に重要です。特に、多値返却を伴う式（関数呼び出しやマップインデックス）の右辺を処理する能力は、Goの表現力を高める上で不可欠です。

*   **`nl` と `nr`**: `nl` は `:=` の左辺の変数リスト（例: `a, b`）、`nr` は右辺の式リスト（例: `f(), m[key]`）を表します。
*   **`cl != cr` の処理**: 左辺と右辺の要素数が異なる場合、`multi` ラベルにジャンプして特殊な処理を行います。
*   **`multi` ラベル内の `switch(nr->op)`**:
    *   `OCALLMETH`, `OCALLINTER`, `OCALL` のケース: 右辺が関数呼び出しの場合を処理します。関数の戻り値の数（`t->outtuple`）が左辺の変数数（`cl`）と一致するかをチェックし、一致しない場合はエラーとします。一致する場合、関数の戻り値の型に基づいて左辺の各変数の型を決定します。
    *   `OINDEX`, `OINDEXPTR` のケース: 右辺がマップインデックス操作の場合を処理します。このコミットの時点では、マップインデックスが2つの値（値と`ok`）を返すことを想定しており、左辺の変数数が2であること（`cl != 2`）をチェックします。そして、左辺の最初の変数にはマップの値の型を、2番目の変数には`TBOOL`型（`ok`フラグ用）を割り当てます。

この `colas` 関数は、`:=` 演算子が単なる代入ではなく、新しい変数の宣言と初期化、そして多値返却の処理を伴う複雑な操作であることを示しています。このコミットは、特にマップの多値返却を `:=` で受け取るための基盤を築いたと言えます。

## 変更の背景

このコミットは、Go言語の初期開発段階における重要な言語仕様の整備と、コンパイラの機能強化を目的としています。

1.  **同一ブロック内での変数再宣言の禁止**: Go言語では、同じスコープ（ブロック）内で同じ名前の変数を再宣言することは許可されていません。これは、プログラミングエラーを防ぎ、コードの可読性を高めるための重要なルールです。このコミット以前は、コンパイラがこのルールを適切に強制していなかった可能性があり、それを修正し、より厳密なエラーチェックを導入する必要がありました。特に、`:=`（ショート変数宣言）演算子を使用した場合の挙動を明確にする必要がありました。
2.  **多値マップインデックスへの半歩**: Go言語のマップ（`map`）は、キーが存在しない場合にゼロ値と`false`を返すという特徴的な多値返却（`value, ok := m[key]`）をサポートしています。このコミットは、この多値返却のセマンティクスをコンパイラが正しく処理するための初期段階の変更を含んでいます。特に、`:=`演算子とマップのインデックス操作が組み合わされた場合の挙動を考慮に入れる必要がありました。

これらの変更は、Go言語の設計思想である「シンプルさ」と「安全性」をコンパイラレベルで実現するための基盤を固めるものです。

## 前提知識の解説

### Go言語のコンパイルプロセス

Goコンパイラ（`gc`）は、ソースコードを機械語に変換する多段階のプロセスを経ます。

1.  **字句解析 (Lexical Analysis)**: `src/cmd/gc/lex.c` が担当。ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換します。
2.  **構文解析 (Syntax Analysis)**: `src/cmd/gc/go.y` が担当。トークンのストリームを解析し、言語の文法規則に従って抽象構文木（AST: Abstract Syntax Tree）を構築します。Yacc/Bisonのようなパーサジェネレータが使用されます。
3.  **意味解析 (Semantic Analysis)**: `src/cmd/gc/walk.c`, `src/cmd/gc/dcl.c` などが担当。ASTを走査し、型チェック、スコープ解決、名前解決、定数畳み込みなどの意味的な検証と変換を行います。この段階で、変数宣言の重複チェックや、マップの多値返却の処理などが実行されます。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTを、より低レベルの中間表現（IR）に変換します。
5.  **コード生成 (Code Generation)**: `src/cmd/6g/cgen.c`, `src/cmd/6g/gen.c`, `src/cmd/6g/gsubr.c` などが担当。中間表現をターゲットアーキテクチャ（この場合はx86-64）の機械語に変換します。

### Go言語のスコープと変数宣言

Go言語では、変数は特定のブロック（`{}`で囲まれた領域）内で宣言され、そのブロック内でのみ有効です。

*   **`var` キーワード**: `var x int` のように明示的に変数を宣言します。
*   **ショート変数宣言 (`:=`)**: `x := 10` のように、変数宣言と初期化を同時に行います。この演算子は、新しい変数を宣言する場合にのみ使用できます。もし同じスコープに同じ名前の変数が既に存在する場合、`:=`はコンパイルエラーとなります（ただし、複数の変数を宣言する際に、少なくとも1つが新しい変数であればエラーにならないという例外ルールもありますが、このコミットの時点ではまだその複雑なルールは導入されていない可能性があります）。

### Go言語のマップと多値返却

Goのマップはキーと値のペアを格納するデータ構造です。マップから値を取得する際、キーが存在しない場合でもプログラムがパニックを起こさないように、Goは2つの値を返すことができます。

```go
value, ok := myMap[key]
```

ここで、`value`はキーに対応する値（キーが存在しない場合は値の型のゼロ値）であり、`ok`はキーが存在したかどうかを示す真偽値です。この`ok`の概念をコンパイラが適切に処理できるようにする必要があります。

### C言語のコンパイラ実装におけるデータ構造

GoコンパイラはC言語で書かれており、ASTノード、型情報、シンボルテーブルのエントリなどを表現するためにCの構造体を使用しています。

*   `Node`: ASTの各ノードを表す構造体。演算子、変数、関数呼び出しなどがノードとして表現されます。
*   `Type`: 型情報を表す構造体。`int`, `string`, `map`, `func` などの型が定義されます。
*   `Sym`: シンボルテーブルのエントリを表す構造体。変数名、関数名、型名などの識別子とその属性（型、スコープなど）を管理します。

## 技術的詳細

### 1. 同一ブロック内での変数再宣言の禁止

このコミットの主要な変更点の一つは、同一ブロック内での変数再宣言を厳密にチェックするようになったことです。これは、`src/cmd/gc/dcl.c` と `src/cmd/gc/go.h` の変更によって実現されています。

*   **ブロック番号の導入**: `src/cmd/gc/go.h` の `Sym` 構造体に `vblock` (variable block) と `tblock` (type block) というフィールドが追加されました。これらは、シンボル（変数や型）が宣言されたブロックの識別子を保持します。また、グローバル変数として `block` (現在のブロック番号) と `blockgen` (最大ブロック番号) が導入されました。
*   **ブロックの管理**: `src/cmd/gc/lex.c` で `block` と `blockgen` が初期化されます。`src/cmd/gc/dcl.c` の `markdcl` 関数（新しいブロックに入る際に呼び出される）で `blockgen` をインクリメントし、`block` を新しい `blockgen` の値に設定することで、新しいブロックが開始されたことを記録します。`popdcl` 関数（ブロックを抜ける際に呼び出される）では、`block` を前のブロックの値に戻します。
*   **再宣言チェック**: `src/cmd/gc/dcl.c` の `addvar` 関数（変数をシンボルテーブルに追加する）と `addtyp` 関数（型をシンボルテーブルに追加する）において、シンボルが既に現在の `block` で宣言されているかどうかを `s->vblock == block` または `s->tblock == block` でチェックするようになりました。もし同じブロックで再宣言されている場合、`yyerror` を呼び出してコンパイルエラーを報告します。

このメカニズムにより、Goコンパイラはより正確にスコープルールを強制し、プログラマが意図しない変数再宣言を行うことを防ぎます。

### 2. 多値マップインデックスへの半歩

このコミットは、`value, ok := m[key]` のような多値返却を伴うマップインデックス操作をサポートするための初期段階の変更を含んでいます。

*   **`ONONAME` ノードの導入**: `src/cmd/gc/go.h` と `src/cmd/gc/subr.c` で `ONONAME` という新しいASTノードタイプが導入されました。これは、`:=` 演算子で宣言されるが、まだ具体的な名前が割り当てられていない（または一時的な）変数を表すために使用される可能性があります。`src/cmd/gc/walk.c` の `oldname` 関数が `ONONAME` ノードを返すように変更されています。
*   **`colas` 関数の追加**: `src/cmd/gc/walk.c` に `colas` という新しい関数が追加されました。この関数は、`:=` 演算子の左辺（変数リスト）と右辺（式リスト）を受け取り、左辺の各変数に対応する新しい名前（`newname`）を生成し、その型を右辺の式の型に基づいて決定します。特に、右辺が関数呼び出し（`OCALLMETH`, `OCALLINTER`, `OCALL`）やマップインデックス操作（`OINDEX`, `OINDEXPTR`）である場合に、多値返却を考慮して左辺の変数の型を決定するロジックが含まれています。
    *   マップインデックスの場合、`colas` 関数は左辺が2つの要素（`value`, `ok`）を持つことを期待し、それぞれにマップの値の型と`TBOOL`型を割り当てます。
*   **`go.y` の変更**: `src/cmd/gc/go.y` の `noninc_stmt` ルールが変更され、`expr_list LCOLAS expr_list` の形式が `colas` 関数を呼び出すように修正されました。これにより、`:=` 演算子を使った宣言が `colas` 関数によって処理されるようになります。
*   **コンパイラバックエンドの変更**: `src/cmd/6g/cgen.c`, `src/cmd/6g/gen.c`, `src/cmd/6g/gsubr.c` では、デバッグ出力の追加や、関数呼び出し（`OCALLMETH`, `OCALLINTER`, `OCALL`）の処理に関連する変更が見られます。特に `cgen_aret` という新しい関数が追加されていますが、これはコミットメッセージにある「half-step」の通り、まだ完全には機能していない（`fatal("cgen_aret")` が含まれている）ようです。これは、多値返却の処理をバックエンドでどのように扱うかという課題に対する初期の試みと考えられます。

### 3. その他の変更

*   **Yacc文法ファイルの複雑化**: `src/cmd/gc/go.y` では、`vardcl`, `typedcl`, `common_dcl`, `fnres`, `type`, `fntypeh` などの多くの文法ルールに `A` と `B` プレフィックスを持つ新しいルールが追加されています。これは、Yacc/Bisonにおける文法規則の曖昧性解消や、特定のコンテキストでのみ有効な構文を表現するための一般的な手法です。これにより、コンパイラがより複雑な構文を正確に解析できるようになります。
*   **エラーメッセージの改善**: `src/cmd/gc/lex.c` では、エスケープシーケンスや16進数/8進数リテラルに関する警告が `warn` から `yyerror` に変更されています。これにより、これらの問題がコンパイルエラーとして扱われるようになり、より厳密なコードチェックが行われるようになりました。

`src/cmd/gc/walk.c` に追加された `colas` 関数の一部:

```c
Node*
colas(Node *nl, Node *nr)
{
	Iter savel, saver;
	Node *l, *r, *a, *n;
	Type *t;
	int cl, cr;

	/* nl is an expression list.
	 * nr is an expression list.
	 * return a newname-list from
	 * the types from the rhs.
	 */
	n = N;
	cr = listcount(nr);
	cl = listcount(nl);
	if(cl != cr) {
		if(cr == 1)
			goto multi;
		goto badt;
	}

	l = listfirst(&savel, &nl);
	r = listfirst(&saver, &nr);

loop:
	if(l == N)
		return n;

	walktype(r, Erv);
	defaultlit(r);
	a = old2new(l, r->type);
	if(n == N)
		n = a;
	else
		n = nod(OLIST, n, a);

	l = listnext(&savel);
	r = listnext(&saver);
	goto loop;

multi:
	/*
	 * there is a list on the left
	 * and a mono on the right.
	 * go into the right to get
	 * individual types for the left.
	 */
	switch(nr->op) {
	default:
		goto badt;

	case OCALLMETH:
	case OCALLINTER:
	case OCALL:
		walktype(nr->left, Erv);
		t = nr->left->type;
		if(t == T || t->etype != TFUNC)
			goto badt;
		if(t->outtuple != cl)
			goto badt;

		l = listfirst(&savel, &nl);
		t = structfirst(&saver, getoutarg(t));
		while(l != N) {
			a = old2new(l, t);
			if(n == N)
				n = a;
			else
				n = nod(OLIST, n, a);
			l = listnext(&savel);
			t = structnext(&saver);
		}
		break;

	case OINDEX:
	case OINDEXPTR:
		// check if rhs is a map index.
		// if so, types are bool,maptype
		if(cl != 2)
			goto badt;
		walktype(nr->left, Elv);
		t = nr->left->type;
		if(t != T && isptr[t->etype])
			t = t->type;
		if(t == T || t->etype != TMAP)
			goto badt;

		a = old2new(nl->left, types[TBOOL]);
		n = a;
		a = old2new(nl->right, t->type);
		n = nod(OLIST, n, a);
		break;
	}
	return n;

badt:
	yyerror("shape error across :=");
	return nl;
}
```

## コアとなるコードの解説

### 1. 変数再宣言チェック

`src/cmd/gc/dcl.c` の `addvar` および `addtyp` 関数における `if(s->vblock == block)` (または `s->tblock == block`) のチェックは、このコミットの最も直接的な影響を示す部分です。

*   `s->vblock` (または `s->tblock`) は、現在処理しているシンボル `s` がどのブロックで宣言されたかを示します。
*   `block` は、現在コンパイラが処理しているソースコードのブロックの識別子です。
*   この条件が真である場合、それは同じブロック内で同じ名前の変数（または型）が再宣言されたことを意味します。
*   `yyerror` が呼び出され、コンパイルエラーが報告されます。これにより、Go言語の厳密なスコープルールがコンパイラによって強制されるようになりました。

### 2. `colas` 関数と多値マップインデックス

`colas` 関数は、Go言語の `:=` 演算子のセマンティクスを実装する上で非常に重要です。特に、多値返却を伴う式（関数呼び出しやマップインデックス）の右辺を処理する能力は、Goの表現力を高める上で不可欠です。

*   **`nl` と `nr`**: `nl` は `:=` の左辺の変数リスト（例: `a, b`）、`nr` は右辺の式リスト（例: `f(), m[key]`）を表します。
*   **`cl != cr` の処理**: 左辺と右辺の要素数が異なる場合、`multi` ラベルにジャンプして特殊な処理を行います。
*   **`multi` ラベル内の `switch(nr->op)`**:
    *   `OCALLMETH`, `OCALLINTER`, `OCALL` のケース: 右辺が関数呼び出しの場合を処理します。関数の戻り値の数（`t->outtuple`）が左辺の変数数（`cl`）と一致するかをチェックし、一致しない場合はエラーとします。一致する場合、関数の戻り値の型に基づいて左辺の各変数の型を決定します。
    *   `OINDEX`, `OINDEXPTR` のケース: 右辺がマップインデックス操作の場合を処理します。このコミットの時点では、マップインデックスが2つの値（値と`ok`）を返すことを想定しており、左辺の変数数が2であること（`cl != 2`）をチェックします。そして、左辺の最初の変数にはマップの値の型を、2番目の変数には`TBOOL`型（`ok`フラグ用）を割り当てます。

この `colas` 関数は、`:=` 演算子が単なる代入ではなく、新しい変数の宣言と初期化、そして多値返却の処理を伴う複雑な操作であることを示しています。このコミットは、特にマップの多値返却を `:=` で受け取るための基盤を築いたと言えます。

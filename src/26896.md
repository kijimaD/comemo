# [インデックス 26896] ファイルの概要

## コミット
このコミットは、Go言語の`compress/bzip2`パッケージにおいて、Bzip2圧縮ストリームのデコード時にハフマン符号の長さがゼロになることを防ぐための修正を導入します。Bzip2の仕様ではゼロ長のハフマン符号は未定義の動作を引き起こすため、デコードロジックに明示的な範囲チェックを追加し、不正な符号長が検出された場合にエラーを返すように変更されました。これにより、悪意のある、または破損したBzip2データによって引き起こされる可能性のあるパニックや未定義の動作を防ぎます。

## 元コミット内容

```
compress/bzip2: prevent zero-length Huffman codes

Unlike RFC 1951 (DEFLATE), bzip2 does not use zero-length Huffman codes
to indicate that the symbol is missing. Instead, bzip2 uses a sparse
bitmap to indicate which symbols are present. Thus, it is undefined what
happens when a length of zero is used. Thus, fix the parsing logic so that
the length cannot ever go below 1-bit similar to how the C logic does things.

To confirm that the C bzip2 utility chokes on this data:
        $ echo "425a6836314159265359b1f7404b000000400040002000217d184682ee48
        a70a12163ee80960" | xxd -r -p | bzip2 -d

For reference see:
```

## 変更の背景

Bzip2圧縮形式は、ハフマン符号を使用してデータを効率的に表現します。しかし、ハフマン符号の「長さ」がゼロになるという特殊なケースが発生した場合、Bzip2の仕様ではその動作が明確に定義されていません。これは、RFC 1951で定義されているDEFLATE圧縮アルゴリズムとは対照的です。DEFLATEでは、ゼロ長のハフマン符号は特定のシンボルが現在のハフマンツリーに存在しないことを示すために使用されることがあります。

Bzip2の場合、シンボルの存在はスパースなビットマップによって示され、ゼロ長の符号は使用されません。したがって、デコードプロセス中にハフマン符号の長さがゼロとして計算されると、Goの`compress/bzip2`パッケージの実装が未定義の動作に陥る可能性がありました。これは、データ破損や悪意のある入力によって引き起こされる可能性のあるセキュリティ上の脆弱性につながる恐れがあります。

このコミットは、このような未定義の動作を防ぐために、ハフマン符号長のパースロジックに厳格なチェックを追加することを目的としています。これにより、Bzip2のC言語リファレンス実装（`bzip2-1.0.6/decompress.c`）と同様に、符号長が常に1ビット以上であることを保証し、堅牢性を向上させます。

## 前提知識の解説

### Bzip2圧縮アルゴリズム

Bzip2は、主にファイル圧縮に使用されるブロックソートベースの可逆データ圧縮アルゴリズムです。その圧縮プロセスはいくつかの段階で構成されます。

1.  **Burrows-Wheeler変換 (BWT)**: 入力データを変換し、同じ文字の並びを近くに集めることで、後続の圧縮段階でより高い圧縮率を達成しやすくします。
2.  **Move-To-Front (MTF) 変換**: BWTの出力をさらに変換し、繰り返し出現する文字を小さな数値で表現できるようにします。
3.  **Run-Length Encoding (RLE)**: MTF変換の出力に対して、連続する同じ値を短いコードで置き換えます。
4.  **ハフマン符号化**: 最終段階で、RLEの出力を可変長ビット列に変換します。頻繁に出現するシンボルには短いビット列を、稀にしか出現しないシンボルには長いビット列を割り当てることで、全体のデータサイズを削減します。

### ハフマン符号化

ハフマン符号化は、データ圧縮に広く用いられるエントロピー符号化の一種です。各入力シンボル（文字やバイトなど）に対して、その出現頻度に基づいて可変長のバイナリコードを割り当てます。

*   **可変長符号**: 固定長の符号とは異なり、シンボルごとに異なる長さのビット列を使用します。
*   **頻度に基づく割り当て**: 出現頻度の高いシンボルには短いコードを、出現頻度の低いシンボルには長いコードを割り当てます。
*   **プレフィックスコード**: どのコードも他のコードのプレフィックス（接頭辞）にならないように設計されており、デコード時に曖昧さなく元のシンボルを復元できます。

### Bzip2におけるハフマン符号

Bzip2では、ハフマン符号のテーブルを効率的に表現するためにいくつかの工夫が凝らされています。

*   **スパースなビットマップ**: Bzip2は、使用される可能性のある256個のシンボルを16の範囲に分割し、実際にデータ中に存在するシンボルが含まれる範囲の情報のみをエンコードします。これにより、未使用のシンボルに対して多くのゼロビットを格納する非効率性を回避します。
*   **符号長の差分エンコーディング**: ハフマン符号のビット長は、前の符号のビット長からの差分として格納されます。これにより、符号長の変化が少ない場合に、よりコンパクトにテーブルを表現できます。ゼロビットは前の長さを複製することを示し、1ビットは長さを増減させることを示します。

### RFC 1951 (DEFLATE) におけるハフマン符号

DEFLATEは、ZlibやPNGなどで広く使用されている圧縮アルゴリズムで、LZ77アルゴリズムとハフマン符号化を組み合わせたものです。

*   **LZ77とハフマン符号化**: DEFLATEは、LZ77によって重複するデータシーケンスをバックリファレンス（長さと距離）に置き換え、残りのリテラルバイトとこれらのバックリファレンスをハフマン符号化します。
*   **ゼロ長ハフマンコード**: DEFLATEでは、ハフマンコード長自体をエンコードする際に、特定のシンボルが現在のハフマンツリーに含まれないことを示すために「ゼロ長」の概念が使われることがあります。これは、未使用のコード長が連続する場合に、ランレングスエンコーディングと組み合わせて効率的に表現されます。

このコミットの背景にある問題は、Bzip2とDEFLATEでハフマン符号の「ゼロ長」の扱いが異なる点に起因しています。Bzip2ではゼロ長は未定義であり、DEFLATEのような意味を持ちません。

## 技術的詳細

Bzip2のデコードプロセスでは、ハフマン符号のビット長を読み取る際に、`length`という変数が使用されます。この`length`は、初期値（通常は5ビット）から始まり、入力ストリームから読み取られるビットに基づいて増減します。具体的には、`br.ReadBit()`が`true`を返すと`length`が増加し、`false`を返すと`length`が減少します。この増減は、ハフマン符号長の差分エンコーディングをデコードするためのメカニズムです。

問題は、この`length`がデクリメントされる過程で、`0`またはそれ以下の値になる可能性があったことです。Bzip2のハフマン符号は、少なくとも1ビットの長さを持つことが期待されており、ゼロ長の符号は存在しません。もし`length`がゼロになった場合、`newHuffmanTree`関数に渡される符号長が不正となり、結果としてパニックや不正なメモリアクセスなどの未定義の動作を引き起こす可能性がありました。

C言語のリファレンス実装である`bzip2-1.0.6/decompress.c`では、この`length`が`1`未満にならないように明示的なチェックが行われています。このコミットは、Goの`compress/bzip2`パッケージでも同様の堅牢性を持たせるために、`length`が`1`未満または`20`を超える場合にエラーを返すチェックを追加します。ハフマン符号の最大長は通常20ビットであるため、`20`を超える値も不正と見なされます。

コミットメッセージに示されているように、不正なBzip2データ（ハフマン符号長がゼロになるようなデータ）をC言語の`bzip2`ユーティリティに与えると、「Data integrity error when decompressing」というエラーが発生し、処理が中断されます。これは、C実装が既にこのような不正な状態を検出して適切に処理していることを示しています。Goの実装もこれに追従し、同様のエラーハンドリングを導入することで、より安全で予測可能な動作を実現します。

## コアとなるコードの解説

### `src/compress/bzip2/bzip2.go` の変更点

`readBlock`メソッド内のハフマン符号長を読み取るループにおいて、新しいチェックが追加されました。

```go
				if length < 1 || length > 20 {
					return StructuralError("Huffman length out of range")
				}
```

このコードは、`length`変数が`1`未満（つまり`0`以下）であるか、または`20`を超える場合に、`StructuralError`を返してデコード処理を中断します。これにより、不正なハフマン符号長が`newHuffmanTree`関数に渡されることを防ぎ、プログラムのクラッシュや未定義の動作を防ぎます。

また、以前のコードにあった以下のチェックが削除されました。

```diff
-			if length < 0 || length > 20 {
-				return StructuralError("Huffman length out of range")
-			}
```

これは、新しいチェックが`for`ループの内側、つまり`length`が更新されるたびに実行されるようになったため、より早期に不正な状態を検出できるようになり、冗長になったためです。`length`は`uint8`型にキャストされるため、`length < 0`という条件は実際には発生しませんが、新しいチェックでは`length < 1`として`0`の場合もカバーしています。

### `src/compress/bzip2/bzip2_test.go` の変更点

新しいテストケース`TestBadHuffmanDelta`が追加されました。

```go
const badHuffmanDelta = "425a6836314159265359b1f7404b000000400040002000217d184682ee48a70a12163ee80960"

func TestBadHuffmanDelta(t *testing.T) {
	_, err := decompressHex(badHuffmanDelta)
	if err == nil {
		t.Errorf("unexpected success")
	}
}
```

`badHuffmanDelta`という定数には、ハフマン符号長がゼロになるような不正なBzip2データが16進数文字列として定義されています。`TestBadHuffmanDelta`関数は、この不正なデータを`decompressHex`関数でデコードしようとします。期待される動作はエラーが返されることなので、もしエラーが返されなかった場合（`err == nil`）、テストは失敗します。このテストの追加により、今回の修正が意図通りに機能し、不正なデータに対して適切にエラーを返すことを保証します。

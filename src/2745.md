# [インデックス 2745] ファイルの概要

このコミットは、Goコンパイラのフロントエンドにおける型解析の仕組みを改善し、Yaccパーサーのreduce/reduceコンフリクトを解消することを目的としています。具体的には、`src/cmd/gc/dcl.c`、`src/cmd/gc/go.h`、`src/cmd/gc/go.y`、`src/cmd/gc/walk.c` の4つのファイルが変更されています。

- `src/cmd/gc/dcl.c`: 宣言処理に関連するコード。型ノードの処理方法が変更されています。
- `src/cmd/gc/go.h`: コンパイラのグローバルヘッダーファイル。`variter`関数のシグネチャが変更されています。
- `src/cmd/gc/go.y`: Go言語の文法を定義するYacc（Yet Another Compiler Compiler）の文法ファイル。型と式の曖昧さに起因するパーサーコンフリクトの解消が主な変更点です。
- `src/cmd/gc/walk.c`: 抽象構文木（AST）のウォーク処理に関連するコード。型解決後の追加処理が導入されています。

## 変更の背景

このコミットの主な背景は、Goコンパイラの初期段階におけるYaccパーサーの「reduce/reduceコンフリクト」の解消です。Go言語の文法は、型と式が文脈によって曖昧になるケースがあり、特に`T(1)`のような構文は、`T`が型であれば型キャスト、`T`が関数であれば関数呼び出しと解釈できます。

YaccのようなLALR(1)パーサーは、このような曖昧な文法に対してreduce/reduceコンフリクトを発生させることがあります。これは、パーサーが現在のトークンとスタック上の状態だけでは、どの文法規則を適用して還元（reduce）すべきかを決定できない状況を指します。元の`go.y`のコメントにも「The grammar has 6 reduce/reduce conflicts, caused by input that can be parsed as either a type or an expression depending on context」と明記されており、この問題が認識されていました。

このコミットの目的は、Yaccパーサーが直接`Type*`型のノードを扱うのをやめ、より汎用的な`Node*`として解析し、その後のセマンティック解析フェーズで型を解決するように変更することで、パーサーレベルでの曖昧さを排除し、reduce/reduceコンフリクトをゼロにすることでした。これにより、パーサーのロバスト性が向上し、コンパイラの開発がよりスムーズに進むようになります。

## 前提知識の解説

### Goコンパイラ (gc) の構造とYacc

Go言語の初期のコンパイラは`gc`と呼ばれ、C言語で書かれていました。`gc`は、字句解析、構文解析、型チェック、最適化、コード生成といった伝統的なコンパイラのフェーズを経ていました。
- **字句解析 (Lexical Analysis)**: ソースコードをトークン（最小単位の要素）に分割します。`src/cmd/gc/lex.c`などが担当します。
- **構文解析 (Syntactic Analysis)**: トークンのストリームを文法規則に従って解析し、抽象構文木（AST）を構築します。このフェーズでYaccが使用されます。
- **Yacc (Yet Another Compiler Compiler)**: Yaccは、文法定義ファイル（`.y`ファイル）からC言語のパーサーコードを生成するツールです。LALR(1)パーサーを生成し、文法規則とアクション（C言語コード）を記述することで、複雑な構文解析を自動化します。

### Reduce/Reduceコンフリクト

Yaccパーサーは、入力トークンを読み込み、スタック上の状態と照らし合わせて、どの文法規則を適用して「還元（reduce）」するか、あるいは次のトークンを「シフト（shift）」するかを決定します。
- **Shift**: 入力ストリームから次のトークンを読み込み、スタックに積む操作。
- **Reduce**: スタックのトップにある一連の記号が特定の文法規則の右辺と一致する場合、それを左辺の非終端記号に置き換える操作。

**Reduce/Reduceコンフリクト**は、パーサーが現在の状態と次の入力トークンに基づいて、複数の異なる文法規則で還元できる状況を指します。つまり、どの規則を適用すべきか決定できないため、パーサーは曖昧な状態に陥ります。これは文法設計上の問題であり、コンパイラの誤動作や予測不能な挙動につながるため、通常は解消する必要があります。

Go言語の文法では、例えば`T(1)`のような構文が問題を引き起こします。
- `T`が型名の場合: `T(1)`は型キャスト（例: `int(1)`）
- `T`が関数名の場合: `T(1)`は関数呼び出し（例: `f(1)`）
パーサーは`T`を読み込んだ時点では、それが型なのか関数なのかを区別できません。もし`T`が型として解釈される規則と、式の一部として解釈される規則の両方で還元可能であれば、reduce/reduceコンフリクトが発生します。

### `Node*` と `Type*` の役割

Goコンパイラでは、抽象構文木（AST）の各ノードは`Node`構造体で表現されます。この`Node`構造体は、式、宣言、文など、あらゆる構文要素を表すことができます。
一方、`Type`構造体は、Go言語の型システムにおける具体的な型情報（例: `int`, `string`, `[]byte`, `struct { ... }`）を保持します。

このコミット以前は、Yaccパーサーが直接`Type*`型のセマンティック値を扱うことがありました。しかし、型と式の曖昧さにより、パーサーは`Node*`として解析すべきか`Type*`として解析すべきかを判断できず、コンフリクトが発生していました。このコミットでは、パーサーはまず全てを`Node*`として扱い、その後のセマンティック解析フェーズで`Node*`が表すものが型であると判明した場合に、その`Node*`から`Type*`を抽出・解決するアプローチに変更されています。

## 技術的詳細

このコミットの核心は、GoコンパイラのYacc文法ファイル`go.y`から、直接的な`Type*`型のセマンティック値の扱いを排除し、代わりに`Node*`型のセマンティック値を使用するように変更した点にあります。これにより、パーサーは文法解析の段階で型と式の区別を厳密に行う必要がなくなり、曖昧さを解消してreduce/reduceコンフリクトを回避します。コミットメッセージにある「0 reduce/reduce conflicts」という記述は、この目標が達成されたことを示しています。

具体的な変更点は以下の通りです。

1.  **`%type <type> type` の削除**:
    `go.y`から`%type <type> type`という宣言が削除されました。これは、Yaccが`type`という非終端記号を解析した結果として直接`Type*`型の値を生成するのをやめたことを意味します。

2.  **`ntype` と `non_expr_type` の導入と役割の変更**:
    - 以前は`type`という非終端記号が型の定義に使用されていましたが、このコミットでは`ntype`と`non_expr_type`という新しい非終端記号が導入され、型の構文を表現するようになりました。
    - `ntype`は、チャネル型、関数型、その他の型、ポインタ型、ドット名、括弧で囲まれた型など、Go言語の様々な型構文を包括的に扱います。
    - `non_expr_type`は、式として解釈されうる構文（例: `T(1)`の`T`）とのコンフリクトを避けるために、純粋な型構文を表現します。特にポインタ型`* non_expr_type`の規則が追加され、`pexpr`（式）との曖昧さを解消しています。
    - `expr_or_type`という非終端記号は、以前は`expr`または`ntype`を許容していましたが、この変更により`expr`または`non_expr_type`を許容するようになりました。これにより、パーサーはまず式として解釈しようとし、それが失敗した場合にのみ純粋な型として解釈する、という優先順位付けが可能になります。

3.  **`walkexpr` を用いた型解決の遅延**:
    - `dcl.c`内の`xanondcl`、`namedcl`、`variter`といった関数では、以前は直接`Type*`を受け取ったり、`nt->type`を直接参照したりしていました。
    - 変更後、これらの関数は`Node*`を受け取るようになり、その`Node*`が実際に型を表す場合は、`walkexpr(nt, Etype, &nt->ninit)`のような呼び出しを通じて、セマンティック解析フェーズで型を解決するようになりました。
    - `walkexpr`はASTを走査し、`Etype`というモードで呼び出されると、与えられた`Node*`が型を表す場合にその型情報を解決し、`Node->type`フィールドに設定します。これにより、構文解析と型解決のフェーズが分離され、パーサーの負担が軽減されます。

4.  **`variter` 関数のシグネチャ変更**:
    `src/cmd/gc/go.h`および`src/cmd/gc/dcl.c`において、`variter`関数のシグネチャが`NodeList*, Type*, NodeList*`から`NodeList*, Node*, NodeList*`に変更されました。これは、変数宣言のイテレーション処理において、型情報を直接`Type*`として渡すのではなく、型を表す`Node*`を渡すように変更されたことを示しています。これにより、`variter`内部で`walkexpr`を呼び出して型を解決する柔軟性が得られます。

5.  **`typedcl` における型解決**:
    `typedcl`（型宣言）の規則も変更され、`typedclname ntype`の後に`walkexpr($2, Etype, &$2->ninit); updatetype($1, $2->type);`が追加されました。これは、型宣言においても、まず`ntype`として解析された`Node*`から`walkexpr`を使って型を解決し、その結果を`updatetype`で適用することを示しています。

6.  **`fndcl` および `indcl` における関数型ノードの構築**:
    関数宣言（`fndcl`）やインターフェース宣言内の関数シグネチャ（`indcl`）においても、直接`functype`を呼び出すのではなく、まず`OTFUNC`ノードを構築し、そのノードに対して`walkexpr`を呼び出して型を解決するようになりました。これにより、関数型も他の型と同様に、`Node*`として表現され、後で型解決される一貫したメカニズムに従うことになります。

これらの変更により、Yaccパーサーは文法規則の曖昧さに悩まされることなく、純粋な構文解析に集中できるようになりました。型と式の区別は、より高度なセマンティック解析フェーズに委ねられることで、コンパイラの設計がよりモジュール化され、保守性が向上しています。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は、主に`go.y`における文法規則の再定義と、`dcl.c`における型解決ロジックの変更に集約されます。

### `go.y` の変更

- **`type` 非終端記号の廃止と `ntype`/`non_expr_type` への移行**:
    以前は`type`という非終端記号が直接`Type*`型のセマンティック値を生成していました。しかし、これが式との曖昧さを生み、reduce/reduceコンフリクトの原因となっていました。このコミットでは、`type`を廃止し、代わりに`ntype`と`non_expr_type`という非終端記号を導入しました。これらの新しい非終端記号は、Yaccパーサーの段階では直接`Type*`を生成せず、型を表す`Node*`を生成します。
    特に`non_expr_type`は、式と紛らわしい構文（例: `*T`がポインタ型か乗算式か）を避けるために導入され、純粋な型構文を表現します。これにより、パーサーは文法規則の選択において迷うことがなくなります。

- **`vardcl` (変数宣言) の変更**:
    ```diff
    -|\tdcl_name_list type varoptsemi '=' expr_list
    +|\tdcl_name_list ntype varoptsemi '=' expr_list
    	{
    		$$ = variter($1, $2, nil);
    	}
    ```
    変数宣言の文法規則において、型を表す部分が`type`から`ntype`に変更されました。これにより、`variter`関数には直接`Type*`ではなく、型を表す`Node*`が渡されるようになります。

- **`typedcl` (型宣言) の変更**:
    ```diff
    -|\ttypedclname type
    +|\ttypedclname ntype
    	{
    -\t\tupdatetype($1, $2);\
    +\t\twalkexpr($2, Etype, &$2->ninit);\
    +\t\tupdatetype($1, $2->type);\
    	\tresumecheckwidth();
    	}
    ```
    型宣言の規則でも、型を表す部分が`type`から`ntype`に変更されました。そして、`updatetype`を呼び出す前に、`walkexpr($2, Etype, &$2->ninit)`が追加されています。これは、`ntype`として解析された`Node*`（`$2`）が実際に型を表すことを`walkexpr`に伝え、その`Node*`から具体的な`Type*`情報を解決して`$2->type`に設定する役割を担います。この`$2->type`が`updatetype`に渡され、型宣言が完了します。

- **`fndcl` (関数宣言) および `indcl` (インターフェース内の関数シグネチャ) の変更**:
    関数宣言やインターフェース内の関数シグネチャの解析においても、直接`functype`を呼び出して`Type*`を生成するのではなく、まず`OTFUNC`というオペレーションを持つ`Node*`を構築し、その`Node*`に対して`walkexpr`を呼び出すように変更されました。
    ```diff
    +\t\tn = nod(OTFUNC, N, N);\
    +\t\tn->list = $3;\
    +\t\tn->rlist = $5;\
    +\t\twalkexpr(n, Etype, &n->ninit);\
    +\t\t$$->type = n->type;\
    ```
    これは、関数型も他の型と同様に、まず`Node*`として表現され、その後のセマンティック解析フェーズで`walkexpr`によって型が解決されるという一貫したアプローチを確立しています。

### `dcl.c` の変更

- **`xanondcl`、`namedcl`、`variter` における `walkexpr` の利用**:
    これらの関数は、変数や引数の宣言を処理する際に型情報を扱います。変更前は直接`Type*`を受け取ったり、`Node*`の`op`が`OTYPE`であることを期待して`Node->type`を直接参照したりしていました。
    変更後、これらの関数は型を表す`Node*`を受け取るようになり、その`Node*`が実際に型であることを確認し、`walkexpr(nt, Etype, &nt->ninit)`を呼び出すことで、型情報を解決しています。
    例えば、`namedcl`関数では、引数の型`nt`が渡された際に、`walkexpr(nt, Etype, &nt->ninit);`が呼び出され、`nt`が表す型が解決され、`nt->type`に設定されます。その後、`nt->op != OTYPE`で型として有効かチェックされます。
    この変更により、構文解析と型解決の責任が明確に分離され、パーサーはより単純な役割に徹することができます。

### `walk.c` の変更

- **`OTYPE` ノード処理における `checkwidth` の追加**:
    `walk.c`の`walkexpr`関数内で、`OTYPE`（型ノード）が処理された後に`checkwidth(t)`が追加されました。
    ```diff
    \t\tn->op = OTYPE;
    \t\tn->type = t;
    +\t\tcheckwidth(t);\
    \t\tgoto ret;
    ```
    `checkwidth`関数は、型のサイズやアライメントなどのプロパティを計算し、設定する役割を担います。型解決が`walkexpr`によって行われるようになったため、型が完全に解決された直後にこれらのプロパティを計算することが適切であるため、この位置に追加されました。

これらの変更全体として、Goコンパイラは、Yaccパーサーが構文解析に集中し、型解決というセマンティックなタスクを後続の`walkexpr`フェーズに委ねることで、パーサーの複雑性を軽減し、reduce/reduceコンフリクトを解消することに成功しています。

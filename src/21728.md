# [インデックス 21728] ファイルの概要

このコミットは、GoランタイムにおけるPlan 9オペレーティングシステム上でのシステムメモリ確保・解放処理のバグを修正します。具体的には、メモリ解放関数`sysFree`でのサイズ計算の誤りによるメモリ破壊と、それに起因するテストの失敗を解決します。

## 変更の背景

Goランタイムは、プログラムがメモリを効率的に利用できるように、OSからメモリを要求し、それを管理する独自のメモリマネージャを持っています。このコミットが修正する問題は、GoランタイムがPlan 9オペレーティングシステム上で動作する際に発生していました。

具体的には、メモリ解放を担当する`sysFree`関数において、解放すべきメモリサイズ`n`を計算するロジックにバグがありました。問題の行は`n += (n + memRound) &^ memRound`です。この計算は、`n`の値を誤って約2倍にしてしまうという致命的な欠陥を抱えていました。

結果として、`sysFree`は指定されたサイズよりもはるかに大きなメモリ領域を解放しようとしたり、既に解放された、あるいはプログラムが所有していないメモリ領域を解放しようとすることがありました。これはメモリ破壊（memory corruption）を引き起こし、プログラムのクラッシュや予期せぬ動作、さらにはセキュリティ上の脆弱性につながる可能性がありました。

この問題は、Goのイシュートラッカーで「Issue #9712」として報告されており、Plan 9上でのGoプログラムがメモリ不足（out of memory）でテストに失敗する原因となっていました。このコミットは、その根本原因を特定し、修正することで、Plan 9におけるGoランタイムの安定性と信頼性を向上させることを目的としています。

## 前提知識の解説

このコミットの変更を理解するためには、以下の前提知識が役立ちます。

*   **Goランタイムのメモリ管理**: Go言語は独自のガベージコレクタ（GC）を持ち、プログラムが動的に確保したメモリを自動的に管理します。しかし、GCが直接OSからメモリを要求するわけではありません。Goランタイムは、OSの提供するシステムコール（例えばUnix系の`sbrk`や`mmap`、Windowsの`VirtualAlloc`など）を介して、大きなメモリブロックをOSから取得し、それを細かく分割してGoプログラムに割り当てます。不要になったメモリはGCによって回収され、最終的にはOSに返却されることもあります。
*   **Plan 9オペレーティングシステム**: Plan 9は、ベル研究所で開発された分散オペレーティングシステムです。Unixの思想を受け継ぎつつ、よりシンプルで一貫性のある設計を目指しています。Go言語は、LinuxやWindows、macOSといった主要なOSだけでなく、Plan 9のようなニッチなOSもサポートしています。OSごとにメモリ管理のシステムコールやアライメントの要件が異なるため、Goランタイムは各OSに特化した実装を持っています。
*   **`sbrk`システムコール**: `sbrk`は、Unix系システムでプログラムのデータセグメントの「ブレーク」位置（プログラムが利用できるメモリ領域の終端）を増減させることで、メモリを動的に確保・解放するためのシステムコールです。Plan 9にも同様の機能を提供する`brk_`システムコールが存在し、Goランタイムはこれを利用してOSからメモリを取得します。
*   **メモリのアライメントとページサイズ**: 現代のコンピュータシステムでは、メモリは特定のバイト境界（アライメント）に沿ってアクセスされると効率的です。特に、OSがメモリを管理する最小単位は「ページ」（通常4KBや8KBなど）と呼ばれ、メモリの確保や解放はページサイズの倍数で行われるのが一般的です。`_PAGESIZE`は、Goランタイムが認識するシステムのページサイズを表す定数です。メモリをページ境界に丸める操作は、`p + _PAGESIZE - 1) &^ (_PAGESIZE - 1)`のようなビット演算で行われます。これは、`p`をページサイズの倍数に切り上げるための一般的なイディオムです。`&^`はビットクリア演算子で、右オペランドのビットがセットされている場合、左オペランドの対応するビットをクリアします。

## 技術的詳細

このコミットの技術的な核心は、メモリのアライメントとサイズの計算を正確に行うことにあります。

1.  **`memRound`の変更**:
    *   変更前: `const memRound = _PAGESIZE - 1`
        *   これは定数であり、ページサイズにアライメントするためのマスクとして使われていました。例えば、`x &^ memRound`は`x`をページサイズの倍数に切り捨てる（下位ビットをクリアする）ために使われます。
    *   変更後: `func memRound(p uintptr) uintptr { return (p + _PAGESIZE - 1) &^ (_PAGESIZE - 1) }`
        *   `memRound`は定数から関数に変わりました。この関数は、与えられたポインタ`p`を次のページ境界に切り上げる（アライメントする）ためのものです。例えば、`p`が4097バイトの場合、`_PAGESIZE`が4096バイトであれば、`memRound(p)`は8192バイト（次のページ境界）を返します。この変更により、メモリの丸め処理がより汎用的かつ意図が明確になりました。

2.  **`initBloc`の変更**:
    *   `initBloc`は、Goプログラムが利用できるメモリ領域の開始点（`bloc`）を初期化する関数です。
    *   変更前: `bloc = uintptr(unsafe.Pointer(&end))`
    *   変更後: `bloc = memRound(uintptr(unsafe.Pointer(&end)))`
        *   プログラムのデータセグメントの終端を示す`&end`シンボルを、新しい`memRound`関数を使ってページ境界に丸めるようになりました。これにより、GoランタイムがOSからメモリを要求する際の最初の基準点が、常に正しくアライメントされた状態になります。

3.  **`sbrk`の変更**:
    *   `sbrk`は、OSからメモリを要求するGoランタイムの内部関数です。
    *   変更前:
        ```go
        bl := (bloc + memRound) &^ memRound // ここで古いmemRound定数を使用
        if brk_(unsafe.Pointer(bl+n)) < 0 { ... }
        bloc = bl + n
        ```
    *   変更後:
        ```go
        bl := bloc // blocが既に丸められているため、この計算は不要に
        n = memRound(n) // 要求サイズnをページ境界に丸める
        if brk_(unsafe.Pointer(bl+n)) < 0 { ... }
        bloc += n // blocの更新もより直感的に
        ```
        *   `bl`の計算が`bl := bloc`とシンプルになりました。これは、`initBloc`で`bloc`が既にページ境界に丸められているため、再度丸める必要がなくなったためです。
        *   最も重要な変更は、要求するメモリサイズ`n`が`n = memRound(n)`によってページ境界に丸められるようになった点です。これにより、`sbrk`は常にページサイズの倍数のメモリをOSに要求するようになり、メモリ確保におけるアライメントの問題を防ぎます。
        *   `bloc`の更新も`bloc = bl + n`から`bloc += n`に変更され、より簡潔になりました。

4.  **`sysFree`の変更**:
    *   `sysFree`は、OSにメモリを返却するGoランタイムの内部関数です。
    *   変更前: `n += (n + memRound) &^ memRound`
        *   これがバグの核心でした。`n`は解放すべきメモリのサイズですが、この計算によって`n`の値が誤って約2倍になっていました。例えば、`n`がページサイズに丸められた値だった場合、`n + memRound`はほぼ`2*n`になり、`&^ memRound`で丸めると`2*n`に近い値になるため、`n += 2*n`のように`n`が約3倍になっていた可能性もあります。これにより、`sysFree`は指定されたサイズよりもはるかに大きな領域を解放しようとし、メモリ破壊を引き起こしていました。
    *   変更後: `n = memRound(n)`
        *   `n`は単に新しい`memRound`関数によってページ境界に丸められるだけになりました。これにより、`sysFree`は正確に指定されたサイズ（ページ境界に丸められた）のメモリを解放するようになり、メモリ破壊の問題が解消されました。

5.  **`src/runtime/pprof/trace_test.go`の変更**:
    *   変更前:
        ```go
        case "plan9":
            t.Skip("skipping: plan9 tests fail with out of memory (http://golang.org/issue/9712")
        ```
    *   変更後: 上記の行が削除されました。
        *   これは、Plan 9でのメモリ管理のバグが修正されたため、関連するテストをスキップする必要がなくなったことを直接的に示しています。
    *   また、`TestTraceSymbolize`内の行番号が`f.line == 218`から`f.line == 216`に修正されています。これは、`mem_plan9.go`の変更によってコードの行数が変動したことによる、テストコードの単純な調整です。

これらの変更は、GoランタイムがPlan 9上でメモリをより正確かつ安全に管理できるようにするための、根本的な修正です。

## コアとなるコードの解説

このコミットの核心は、GoランタイムがPlan 9上でメモリを扱う際の「丸め（rounding）」と「アライメント（alignment）」のロジックを根本的に修正した点にあります。

1.  **`memRound`の役割の明確化と正確化**:
    *   以前は`_PAGESIZE - 1`という定数として、主にビットマスクとして使われていた`memRound`が、与えられたアドレスやサイズを次のページ境界に正確に切り上げるための関数に変わりました。これにより、メモリの確保や解放の際に、常にページサイズの倍数で、かつページ境界にアライメントされたメモリ領域を扱うことが保証されます。これは、OSがメモリを管理する上での基本的な要件であり、この変更によってGoランタイムとOS間のメモリ管理の一貫性が向上しました。

2.  **`sysFree`におけるバグの修正**:
    *   最も重要な修正は、`sysFree`関数内の`n += (n + memRound) &^ memRound`という誤った計算を`n = memRound(n)`に置き換えたことです。元のコードは、解放すべきメモリサイズ`n`を誤って倍増させてしまい、結果として存在しない、あるいは既に解放されたメモリ領域を解放しようとすることで、メモリ破壊を引き起こしていました。修正後は、`n`が単にページ境界に丸められるだけになり、`sysFree`は正確に指定されたサイズのメモリを解放するようになりました。これにより、メモリ破壊の問題が解消され、Goプログラムの安定性が大幅に向上しました。

3.  **`sbrk`におけるメモリ確保の一貫性**:
    *   `sbrk`関数においても、要求するメモリサイズ`n`が`memRound(n)`によってページ境界に丸められるようになりました。これにより、GoランタイムがOSからメモリを要求する際も、常にページサイズの倍数で、正しくアライメントされたブロックを取得することが保証されます。これは、メモリ解放側だけでなく、確保側でも一貫したアライメントポリシーを適用することで、全体的なメモリ管理の堅牢性を高めます。

これらの変更により、Plan 9上でのGoプログラムは、メモリの確保と解放をより安全かつ正確に行えるようになり、以前発生していたメモリ不足やメモリ破壊といった問題が解決されました。`trace_test.go`からPlan 9のテストスキップが削除されたことは、この修正が実際に問題を解決し、テストが正常に動作するようになったことの直接的な証拠です。

# [インデックス 20388] ファイルの概要

このコミットは、GoランタイムにおけるCgo呼び出し（GoからC関数を呼び出すメカニズム）の主要な部分をC言語からGo言語に変換するものです。具体的には、`src/pkg/runtime/cgocall.c` ファイルが `src/pkg/runtime/cgocall.go` にリネームされ、その内容がGo言語で再実装されています。これにより、GoランタイムのCgo関連コードの保守性、安全性、そして潜在的なパフォーマンスが向上することが期待されます。

## 元コミット内容

このコミットの元の内容は、GoランタイムのCgo呼び出しに関するC言語で書かれたコードをGo言語に移植することです。これにより、GoプログラムがC言語のライブラリや関数を呼び出す際の内部処理が、よりGo言語の慣習に沿った形になります。

## 変更の背景

Go言語は、その設計思想として「シンプルさ」と「効率性」を重視しています。初期のGoランタイムには、OSとのインタラクションやC言語との連携のために、多くのC言語やアセンブリ言語で書かれたコードが含まれていました。しかし、C言語のコードはGo言語のガベージコレクションやスケジューラと直接連携することが難しく、デバッグや保守が複雑になる傾向がありました。

`cgocall` は、GoからC関数を呼び出す際の重要なブリッジとなる機能です。この機能がC言語で実装されていると、GoのランタイムがCの世界とやり取りする際に、Goのランタイムの内部状態（例えば、現在のgoroutineやスタックの状態）をCコードが理解し、適切に操作することが困難になります。また、Cgo呼び出しは、Goのスケジューラがgoroutineをブロックしないように、システムコールとして扱われる必要があります。

このコミットの背景には、Goランタイムの内部コードを可能な限りGo言語で記述することで、以下のようなメリットを享受しようとする意図があります。

1.  **保守性の向上**: Go言語で書かれたコードは、Go開発者にとって理解しやすく、デバッグや変更が容易になります。C言語とGo言語の混在を減らすことで、コードベース全体の複雑性が軽減されます。
2.  **安全性の向上**: C言語はポインタの直接操作が可能であり、メモリ安全性の問題を引き起こしやすい言語です。Go言語に移行することで、Goの型安全性やメモリ管理の恩恵を受け、潜在的なバグや脆弱性を減らすことができます。
3.  **Goランタイムとの統合の強化**: Go言語で書かれた`cgocall`は、Goのガベージコレクタやスケジューラとより密接に連携できるようになります。これにより、Cgo呼び出し中のランタイムの挙動がより予測可能になり、効率が向上する可能性があります。
4.  **クロスプラットフォーム対応の簡素化**: C言語のコードは、アーキテクチャやOSに依存する部分が多くなります。Go言語に移行することで、これらの依存性を抽象化し、異なるプラットフォームへの対応を簡素化できる可能性があります。

この変更は、Goランタイムが成熟し、より多くの内部コンポーネントをGo言語自体で実装できるようになった時期に行われた、Goランタイムの「Go化」という大きな流れの一部と見なすことができます。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

### 1. Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するGo言語の不可欠な部分です。これには、ガベージコレクタ、スケジューラ（goroutineの管理）、メモリ管理、システムコールインターフェースなどが含まれます。Goプログラムは、OS上で直接実行されるのではなく、Goランタイム上で実行されます。

### 2. GoroutineとM/Pモデル

*   **Goroutine**: Go言語の軽量な並行処理単位です。OSのスレッドよりもはるかに軽量で、数百万のgoroutineを同時に実行できます。
*   **M (Machine)**: OSのスレッドを表します。Goランタイムは、M上でgoroutineを実行します。
*   **P (Processor)**: 論理プロセッサを表します。PはMにアタッチされ、goroutineの実行に必要なリソース（スケジューラキューなど）を提供します。Goスケジューラは、Pの数に基づいてMの数を調整し、goroutineをM上で実行します。

Goのスケジューラは、M/Pモデルを使用してgoroutineを効率的にOSスレッドにマッピングし、実行します。

### 3. Cgo

Cgoは、GoプログラムからC言語の関数を呼び出したり、C言語のコードからGo言語の関数を呼び出したりするためのGoの機能です。Cgoを使用すると、既存のCライブラリをGoプログラムから利用したり、パフォーマンスが重要な部分をCで記述したりすることができます。

Cgoの仕組みは複雑で、GoとCの間の呼び出し規約、スタックレイアウト、メモリ管理の違いを橋渡しする必要があります。GoからCを呼び出す際には、Goランタイムは現在のgoroutineを一時停止し、OSスレッドをCコードに引き渡します。Cコードの実行中は、GoのスケジューラはそのOSスレッドを他のgoroutineの実行には使用しません。

### 4. `cgocall` の役割

`cgocall` は、GoからC関数を呼び出す際のGoランタイムの内部関数です。この関数は、以下の主要な役割を担います。

*   **Goroutineのロック**: C関数が実行されている間、現在のgoroutineを特定のOSスレッド（M）にロックします。これは、CコードがGoのスケジューラによって中断されることなく、安定した環境で実行されることを保証するためです。
*   **システムコールへの移行**: `entersyscall` を呼び出して、Goランタイムがシステムコールに入ったことをスケジューラに通知します。これにより、Goのスケジューラは、Cコードの実行中に他のgoroutineをブロックしないように動作します。
*   **スタックの切り替え**: CコードはGoのスタックとは異なるスタック規約を持つ場合があるため、必要に応じてスタックを切り替える処理が行われます。特に、GoのM（OSスレッド）に紐づく`g0`スタック（ランタイム内部処理用のスタック）に切り替えることがあります。
*   **エラーハンドリング**: C関数からの戻り値やエラーコードを処理します。

### 5. `//go:noescape` ディレクティブ

`//go:noescape` は、Goコンパイラに対するヒントです。このディレクティブが付けられた関数は、その引数がヒープにエスケープしない（つまり、スタック上に留まる）ことをコンパイラに保証します。これは、主にアセンブリ言語で実装された関数や、Goのメモリモデルの外部でメモリを操作する関数に対して使用されます。このディレクティブは、コンパイラがより積極的な最適化を行うことを可能にします。

### 6. `defer` ステートメント

Goの `defer` ステートメントは、関数がリターンする直前に実行される関数呼び出しをスケジュールします。これは、リソースの解放（ファイルのクローズ、ロックの解除など）やクリーンアップ処理に非常に便利です。このコミットでは、C言語の `defer` に相当する処理がGoの `defer` に置き換えられています。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムのCgo関連の低レベルな処理をC言語からGo言語に移行した点にあります。

### 1. `cgocall.c` から `cgocall.go` への移行

*   **Cヘッダーの削除**: `cgocall.c` にあった `#include` ディレクティブ（`runtime.h`, `arch_GOARCH.h`, `stack.h`, `cgocall.h`, `race.h`, `../../cmd/ld/textflag.h`）が `cgocall.go` では削除されています。これは、Go言語のコードがGoのパッケージシステムと型システムに依存するため、Cのヘッダーは不要になることを意味します。
*   **Goパッケージへの変換**: C言語のファイルはGoの `package runtime` に変換されています。
*   **C関数からGo関数への変換**:
    *   `void runtime·cgocall(void (*fn)(void*), void *arg)` は `func cgocall(fn, arg unsafe.Pointer)` に。
    *   `int32 runtime·cgocall_errno(void (*fn)(void*), void *arg)` は `func cgocall_errno(fn, arg unsafe.Pointer) int32` に。
    *   `static void endcgo(void)` は `func endcgo(mp *m)` に。
    *   `void* runtime·cmalloc(uintptr n)` は `func cmalloc(n uintptr) unsafe.Pointer` に。
    *   `void runtime·cfree(void *p)` は `func cfree(p unsafe.Pointer)` に。
    *   `void runtime·cgocallbackg(void)` は `func cgocallbackg()` に。
    *   `void runtime·cgocallbackg1(void)` は `func cgocallbackg1()` に。
    *   `static void unwindm(void)` は `func unwindm(restore *bool)` に。
    *   `void runtime·badcgocallback(void)` は `func badcgocallback()` に。
    *   `void runtime·cgounimpl(void)` は `func cgounimpl()` に。
    これらの変換により、Goの型システム（`unsafe.Pointer`, `uintptr`, `int32` など）が活用され、Goの関数呼び出し規約が適用されます。
*   **Cの `defer` 相当の処理のGo化**: 以前のCコードでは、`Defer d;` 構造体と `g->defer` リストを使って `defer` のような処理を実装していましたが、Go言語への変換後は、Goのネイティブな `defer` ステートメントが使用されています。例えば、`cgocall_errno` 関数内で `defer endcgo(mp)` が追加されています。これにより、コードがより簡潔になり、Goのランタイムが提供する堅牢な `defer` メカニズムの恩恵を受けられます。
*   **Cgo関連のグローバル変数のGo化**: `_cgo_init`, `_cgo_malloc`, `_cgo_free` といったC言語のグローバル変数は、Go側では `cgoMalloc`, `cgoFree` といった `unsafe.Pointer` 型の変数として定義され、`proc.c` の `runtime·schedinit` 関数内でC側の実体から値がコピーされるようになりました。これにより、GoコードからこれらのCgo関連のポインタにアクセスする際の型安全性が向上します。
*   **アセンブリ呼び出しのGo化**: `runtime·asmcgocall_errno` のようなアセンブリ関数への呼び出しは、Goの関数呼び出しとして扱われるようになり、`//go:noescape` ディレクティブが `stubs.go` に追加されています。

### 2. `proc.c` の変更

`src/pkg/runtime/proc.c` では、Goランタイムの初期化処理である `runtime·schedinit` 関数内で、Cgo関連のポインタ（`_cgo_malloc`, `_cgo_free`）をGo側の変数（`runtime·cgoMalloc`, `runtime·cgoFree`）にコピーする処理が追加されています。これは、Cgoが利用可能な場合に、C言語のリンカによって設定されたこれらのポインタをGoランタイムが利用できるようにするためです。

### 3. `stubs.go` の変更

`src/pkg/runtime/stubs.go` は、Goランタイムの内部関数やアセンブリで実装された関数のスタブ（宣言）が記述されているファイルです。このコミットでは、以下の関数に `//go:noescape` ディレクティブが追加されています。

*   `racereleasemerge`
*   `newextram`
*   `lockOSThread`
*   `unlockOSThread`
*   `asmcgocall_errno`

これらの関数は、Goのメモリモデルの外部で動作するか、アセンブリで実装されており、引数がヒープにエスケープしないことをコンパイラに伝えることで、より効率的なコード生成を可能にします。特に `lockOSThread` と `unlockOSThread` は、Goのスケジューラが現在のgoroutineを特定のOSスレッドに固定/解除する際に使用される重要な関数です。

### 4. スタックアンワインドの変更

`unwindm` 関数は、CgoコールバックからGoに戻る際に、`g0` スタック（ランタイム内部処理用のスタック）を適切にアンワインド（スタックポインタを元に戻す）する役割を担います。この関数もGo言語に変換され、各アーキテクチャ（`386`, `amd64`, `arm`）に応じたスタックポインタの操作がGoの `unsafe.Pointer` を使って記述されています。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、`src/pkg/runtime/cgocall.c` が `src/pkg/runtime/cgocall.go` にリネームされ、その内容がC言語からGo言語に書き換えられた点です。

特に、`runtime·cgocall_errno` 関数（GoからCを呼び出す主要な関数）のGo言語への変換が重要です。

**変更前 (`cgocall.c`):**
```c
int32
runtime·cgocall_errno(void (*fn)(void*), void *arg)
{
	Defer d;
	int32 errno;

	if(!runtime·iscgo && !Solaris && !Windows)
		runtime·throw("cgocall unavailable");

	if(fn == 0)
		runtime·throw("cgocall nil");

	if(raceenabled)
		runtime·racereleasemerge(&cgosync);

	// Create an extra M for callbacks on threads not created by Go on first cgo call.
	if(runtime·needextram && runtime·cas(&runtime·needextram, 1, 0))
		runtime·newextram();

	g->m->ncgocall++;

	/*
	 * Mutex g to m to ensure we stay on the same stack if we do a
	 * cgo callback. Add entry to defer stack in case of panic.
	 */
	runtime·lockOSThread();
	d.fn = &endcgoV;
	d.siz = 0;
	d.link = g->defer;
	d.argp = NoArgs;
	d.special = true;
	g->defer = &d;
	
	g->m->ncgo++;

	/*
	 * Announce we are entering a system call
	 * so it is safe to call while "in a system call", outside
	 * the $GOMAXPROCS accounting.
	 */
	runtime·entersyscall();
	errno = runtime·asmcgocall_errno(fn, arg);
	runtime·exitsyscall();

	if(g->defer != &d || d.fn != &endcgoV)
		runtime·throw("runtime: bad defer entry in cgocallback");
	g->defer = d.link;
	endcgo();
	
	return errno;
}
```

**変更後 (`cgocall.go`):**
```go
func cgocall_errno(fn, arg unsafe.Pointer) int32 {
	if !iscgo && GOOS != "solaris" && GOOS != "windows" {
		gothrow("cgocall unavailable")
	}

	if fn == nil {
		gothrow("cgocall nil")
	}

	if raceenabled {
		racereleasemerge(unsafe.Pointer(&racecgosync))
	}

	// Create an extra M for callbacks on threads not created by Go on first cgo call.
	if needextram == 1 && cas(&needextram, 1, 0) {
		newextram()
	}

	lockOSThread()
	mp := getg().m
	mp.ncgocall++
	mp.ncgo++
	defer endcgo(mp) // Goのdeferを使用

	entersyscall()
	errno := asmcgocall_errno(fn, arg)
	exitsyscall()

	return errno
}
```

## コアとなるコードの解説

上記の `cgocall_errno` 関数の変更は、GoランタイムのCgo呼び出しの内部ロジックがCからGoへどのように移行されたかを示しています。

1.  **エラーチェック**:
    *   `if !iscgo && GOOS != "solaris" && GOOS != "windows"`: Cgoが利用可能でない場合、またはSolaris/Windows以外のOSでCgoがサポートされていない場合にパニックを起こします。これはCバージョンとほぼ同じロジックです。
    *   `if fn == nil`: 呼び出すC関数ポインタがnilの場合にパニックを起こします。これもCバージョンと同じです。

2.  **データ競合検出 (Race Detector)**:
    *   `if raceenabled { racereleasemerge(unsafe.Pointer(&racecgosync)) }`: Goのデータ競合検出機能が有効な場合、Cgo呼び出しに関連する同期ポイントで `racereleasemerge` を呼び出します。これは、CコードとGoコードの間で共有される可能性のあるメモリへのアクセスを追跡するために重要です。

3.  **追加Mの作成**:
    *   `if needextram == 1 && cas(&needextram, 1, 0) { newextram() }`: Cgoコールバックのために追加のOSスレッド（M）が必要な場合に、新しいMを作成します。これは、Goが管理していないスレッドからGo関数が呼び出された場合に、Goランタイムがそのコールバックを処理するためのMを確保するために行われます。`cas` (Compare And Swap) はアトミック操作で、複数のgoroutineからの競合を防ぎます。

4.  **OSスレッドのロックとM/G状態の更新**:
    *   `lockOSThread()`: 現在のgoroutineを現在のOSスレッド（M）にロックします。これにより、C関数が実行されている間、Goのスケジューラがこのgoroutineを別のMに移動させたり、このMで別のgoroutineを実行したりするのを防ぎます。CコードはGoのスケジューラとは独立して動作するため、このロックはCコードの安定した実行環境を保証するために不可欠です。
    *   `mp := getg().m`: 現在のgoroutine (`g`) から、それに関連付けられているM (`mp`) を取得します。
    *   `mp.ncgocall++` と `mp.ncgo++`: MのCgo呼び出しカウンタをインクリメントします。これらは、Mが現在Cgo呼び出し中であることをランタイムに示します。

5.  **Goの `defer` ステートメント**:
    *   `defer endcgo(mp)`: ここがCバージョンからの最も大きな変更点の一つです。Cバージョンでは、`Defer d;` 構造体を手動でスタックに配置し、`g->defer` リストにリンクして `defer` のような動作を模倣していました。Goバージョンでは、Go言語のネイティブな `defer` ステートメントを使用しています。これにより、`cgocall_errno` 関数がリターンする際に、`endcgo(mp)` 関数が自動的に実行されることが保証されます。`endcgo` 関数は、`lockOSThread` で取得したロックを解除し、Cgo呼び出しカウンタをデクリメントするなどのクリーンアップ処理を行います。

6.  **システムコールへの移行とアセンブリ呼び出し**:
    *   `entersyscall()`: Goランタイムがシステムコールに入ったことをスケジューラに通知します。これにより、Goのスケジューラは、このMがCコードの実行中であることを認識し、他のgoroutineの実行をブロックしないように動作します。
    *   `errno := asmcgocall_errno(fn, arg)`: 実際のC関数呼び出しは、アセンブリ言語で実装された `asmcgocall_errno` 関数を通じて行われます。この関数は、GoのスタックからCのスタックへの切り替えや、C関数への引数渡し、戻り値の受け取りなど、低レベルな処理を担います。
    *   `exitsyscall()`: C関数からの戻り後、Goランタイムがシステムコールから抜けたことをスケジューラに通知します。

7.  **戻り値**:
    *   `return errno`: C関数から返されたエラーコードを返します。

この変更により、Cgo呼び出しのライフサイクル管理（ロック、アンロック、システムコール状態の通知、クリーンアップ）が、よりGo言語の慣習に沿った形で記述されるようになりました。これにより、コードの可読性と保守性が向上し、Goランタイムの内部構造がより一貫性のあるものになっています。

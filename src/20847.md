# [インデックス 20847] ファイルの概要

このコミットは、Goランタイムにおける`select`ステートメントとチャネル操作に関するバグ修正です。具体的には、同じゴルーチンが同じチャネルの受信待ち行列（`recvq`）に複数回登録される可能性がある場合に、誤った`SudoG`構造体がデキュー（キューから削除）されてしまう問題を解決します。この問題は、`select`文内で同じチャネルが複数回ケースとして現れる場合に発生し、チャネルの待ち行列が破損する可能性がありました。修正は、デキューの際にゴルーチン（`G`）をキーとして使用する代わりに、`SudoG`構造体へのポインタをキーとして使用することで、一意性を確保し、正しい`SudoG`をデキューするように変更しています。

## 変更の背景

このコミットは、Goランタイムにおけるチャネル操作、特に`select`ステートメントの内部処理に潜んでいたバグを修正するために行われました。問題は、`select`文が同じチャネルに対して複数の`case`を持つ場合に顕在化しました。例えば、以下のようなコードです。

```go
select {
       case <- c:
       case <- c:
}
```

このような`select`文において、ゴルーチンがチャネル`c`からの受信を待機する際、Goランタイムは内部的にそのゴルーチンをチャネル`c`の受信待ち行列（`recvq`）に登録します。しかし、上記の例のように同じチャネルが複数回登場すると、同じゴルーチンがチャネル`c`の`recvq`に複数回登録される可能性がありました。

Goランタイムの以前の実装では、チャネルの待ち行列からゴルーチンをデキューする際に、ゴルーチン（`G`）自体をキーとして使用していました。この方式では、もし同じゴルーチンが同じチャネルの待ち行列に複数回登録されている場合、どの`SudoG`（後述）をデキューすべきか曖昧になってしまいます。結果として、誤った`SudoG`がデキューされ、まだ待ち行列に残っているはずの`SudoG`が解放されてしまうという、チャネルの待ち行列の破損につながる可能性がありました。この破損は、後続のチャネル操作が失敗したり、ランタイムがクラッシュしたりする原因となり得ました。

このバグは、特に並行処理が複雑に絡み合うGoアプリケーションにおいて、予測不能な動作を引き起こす可能性があったため、その修正はランタイムの安定性と正確性を保つ上で非常に重要でした。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoランタイムの概念とメカニズムについて理解しておく必要があります。

### Goのチャネル (Channels in Go)

Goにおけるチャネルは、ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは型付けされており、`make(chan Type)`で作成されます。
- `ch <- value`: `value`をチャネル`ch`に送信します。
- `value := <-ch`: チャネル`ch`から値を受信します。
チャネルは、送信側と受信側のゴルーチンが同期する（ハンドシェイクする）までブロックする性質を持っています。バッファ付きチャネルの場合、バッファが満杯または空になるまでブロックしません。

### `select` ステートメント

`select`ステートメントは、複数のチャネル操作を同時に待機し、準備ができた最初の操作を実行するためのGoの強力な機能です。
```go
select {
case <-ch1:
    // ch1からの受信が準備できた場合
case ch2 <- value:
    // ch2への送信が準備できた場合
default:
    // どのチャネル操作も準備できていない場合（オプション）
}
```
`select`は、いずれかの`case`が準備できるまでゴルーチンをブロックします。複数の`case`が同時に準備できた場合、ランタイムはランダムに1つを選択します。

### `SudoG` 構造体

`SudoG`（"pseudo-goroutine"の略、または"sudog"と発音されることが多い）は、Goランタイムの内部で使用される構造体です。これは、チャネル操作（送信または受信）によってブロックされているゴルーチンに関する情報をカプセル化します。`SudoG`は、特定のゴルーチン（`G`）がどのチャネルで、どのような操作（送信か受信か）、どの値を使ってブロックされているかを記録します。

`SudoG`構造体は、チャネルの内部にある待ち行列（`waitq`）に登録されます。これにより、チャネル操作が完了した際に、対応するゴルーチンを効率的に見つけて再開させることができます。

### `waitq` (待ち行列)

Goランタイムのチャネル内部には、`waitq`という待ち行列があります。これは、チャネルの送受信操作によってブロックされている`SudoG`構造体のリストを管理するためのキューです。
- `sendq`: チャネルへの送信操作でブロックされているゴルーチン（の`SudoG`）を管理するキュー。
- `recvq`: チャネルからの受信操作でブロックされているゴルーチン（の`SudoG`）を管理するキュー。

チャネル操作が完了すると、ランタイムはこれらのキューから適切な`SudoG`をデキューし、対応するゴルーチンを再開させます。

### ゴルーチン (Goroutines)

ゴルーチンはGoの並行処理の基本単位であり、軽量なスレッドのようなものです。`go`キーワードを使って関数を呼び出すことで新しいゴルーチンが作成されます。ゴルーチンはGoランタイムによってスケジューリングされ、複数のゴルーチンがOSのスレッド上で多重化されて実行されます。

## 技術的詳細

このバグは、`select`ステートメントが同じチャネルに対して複数の`case`を持つ場合に、Goランタイムがチャネルの待ち行列（`sendq`または`recvq`）から`SudoG`をデキューする際のロジックに起因していました。

### 問題の具体的なシナリオ

コミットメッセージで示されたシナリオを再考します。

```go
select {
       case <- c: // ケース1
       case <- c: // ケース2
}
```

この`select`文を実行するゴルーチンAがチャネル`c`からの受信を待機する場合、ランタイムはゴルーチンAをチャネル`c`の`recvq`に登録します。`select`の内部処理では、各`case`に対して個別の`SudoG`が作成され、チャネルの待ち行列に追加されます。したがって、上記の例では、ゴルーチンAに関連付けられた2つの異なる`SudoG`インスタンスがチャネル`c`の`recvq`に登録される可能性があります。これら2つの`SudoG`は、異なるメモリ位置に存在しますが、どちらも同じゴルーチンA（`sgp.g`フィールドが同じ`gp`を指す）を参照します。

### `G` をキーとして使用することの問題点

以前の`waitq.dequeueg(gp *g)`関数は、引数としてゴルーチンへのポインタ`gp`を受け取り、待ち行列内の`SudoG`をその`sgp.g == gp`という条件で検索していました。

問題は、チャネル`c`が準備できた際に、`select`がその`case`の1つを選択し、対応する`SudoG`を`recvq`からデキューしようとするときに発生します。もし`recvq`にゴルーチンAに関連する2つの`SudoG`（`sgp1`と`sgp2`）が存在する場合、`dequeueg(gp)`はどちらの`SudoG`を削除すべきか区別できませんでした。`dequeueg`は単に`gp`と一致する最初の`SudoG`を見つけて削除していました。

これにより、以下の問題が発生しました：
1.  **誤った`SudoG`のデキュー**: `select`が選択した`case`に対応する`SudoG`ではない、別の`SudoG`がデキューされてしまう可能性がありました。
2.  **待ち行列の破損**: 誤ってデキューされた`SudoG`が、実際にはまだ`recvq`に残っているべき`SudoG`であった場合、その`SudoG`はメモリから解放されてしまいます。しかし、チャネルの待ち行列にはその`SudoG`へのポインタが残ったままになるため、待ち行列の整合性が失われます。
3.  **後続のチャネル操作の失敗**: 待ち行列が破損すると、後続のチャネル操作（例えば、別のゴルーチンがチャネル`c`に送信し、ゴルーチンAを再開させようとする場合）が、存在しない`SudoG`を操作しようとしたり、誤った`SudoG`を操作しようとしたりして、ランタイムエラーやデッドロックを引き起こす可能性がありました。

### `SudoG` ポインタをキーとして使用する解決策

この問題を解決するために、修正では`waitq.dequeueg`関数のシグネチャと内部ロジックが変更されました。新しい関数`waitq.dequeueSudoG(s *sudog)`は、デキューすべき`SudoG`構造体へのポインタ`s`を直接引数として受け取ります。

これにより、`dequeueSudoG`は待ち行列内の`SudoG`を`sgp == s`という条件で検索するようになります。`SudoG`構造体はそれぞれ異なるメモリ位置に割り当てられるため、そのポインタは一意です。したがって、この変更により、ランタイムは`select`が実際に選択した`case`に対応する、正確な`SudoG`インスタンスを待ち行列からデキューできるようになりました。

この修正は、チャネルの待ち行列の整合性を保ち、`select`ステートメントが複雑なシナリオでも正しく動作することを保証します。

## コアとなるコードの変更箇所

このコミットでは、主に2つのファイルが変更されています。

1.  **`src/runtime/select.go`**: `select`ステートメントの内部ロジックと、`waitq`からのデキュー処理が変更されました。
    *   `selectgo`関数（または関連する`select`処理ロジック）内で、`c.sendq.dequeueg(gp)`および`c.recvq.dequeueg(gp)`の呼び出しが、それぞれ`c.sendq.dequeueSudoG(sglist)`および`c.recvq.dequeueSudoG(sglist)`に変更されました。ここで`sglist`は、デキューすべき`SudoG`へのポインタです。
    *   `waitq`型のメソッド`dequeueg(gp *g)`が`dequeueSudoG(s *sudog)`にリネームされ、引数がゴルーチンポインタ`gp`から`SudoG`ポインタ`s`に変更されました。
    *   `dequeueSudoG`の内部で、`sgp.g == gp`という比較が`sgp == s`に変更され、`SudoG`ポインタ自体を比較してデキュー対象を特定するようになりました。

2.  **`src/runtime/chan_test.go`**: このバグを再現し、修正が正しく機能することを確認するための新しいテストケース`TestSelectDuplicateChannel`が追加されました。
    *   このテストは、同じチャネルが複数回`select`ケースに現れるシナリオを作成し、チャネルの待ち行列が破損しないこと、およびゴルーチンが正しく再開されることを検証します。
    *   具体的には、ゴルーチンAが同じチャネル`c`に対して2つの受信`case`を持つ`select`を実行し、ゴルーチンBも`c`からの受信を待機します。その後、別のチャネル`d`への送信によってゴルーチンAを起動し、`c`への送信によってゴルーチンBを起動することで、以前のバグが再現されないことを確認しています。

### `src/runtime/chan_test.go` の追加テスト

```go
func TestSelectDuplicateChannel(t *testing.T) {
	// This test makes sure we can queue a G on
	// the same channel multiple times.
	c := make(chan int)
	d := make(chan int)
	e := make(chan int)

	// goroutine A
	go func() {
		select {
		case <-c:
		case <-c:
		case <-d:
		}
		e <- 9
	}()
	time.Sleep(time.Millisecond) // make sure goroutine A gets qeueued first on c

	// goroutine B
	go func() {
		<-c
	}()
	time.Sleep(time.Millisecond) // make sure goroutine B gets queued on c before continuing

	d <- 7 // wake up A, it dequeues itself from c.  This operation used to corrupt c.recvq.
	<-e    // A tells us it's done
	c <- 8 // wake up B.  This operation used to fail because c.recvq was corrupted (it tries to wake up an already running G instead of B)
}
```

- このテストは、まさにこのコミットが修正しようとしているシナリオを再現します。
- `goroutine A`は、同じチャネル`c`に対する2つの受信`case`を含む`select`文を実行します。これにより、`goroutine A`はチャネル`c`の`recvq`に2つの`SudoG`を登録する可能性があります。
- `goroutine B`もチャネル`c`からの受信を待機します。
- `d <- 7`によって`goroutine A`の`select`が`case <-d`で起動します。このとき、`goroutine A`はチャネル`c`の`recvq`から自身に関連する`SudoG`をデキューしようとします。以前のバグがある場合、ここで誤った`SudoG`がデキューされ、`c.recvq`が破損する可能性がありました。
- `<-e`で`goroutine A`の完了を待ちます。
- `c <- 8`によって`goroutine B`を起動しようとします。以前のバグで`c.recvq`が破損している場合、この操作が失敗したり、誤ったゴルーチンを起動しようとしたりする可能性がありました。
- このテストが成功することは、`select`が同じチャネルを複数回扱う場合でも、チャネルの待ち行列が正しく管理され、ゴルーチンが期待通りにデキュー・再開されることを保証します。

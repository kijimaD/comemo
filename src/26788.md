# [インデックス 26788] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/url` パッケージにおける `URL` 構造体の挙動を改善するものです。具体的には、クエリ文字列を持たないURL（例: `http://foo.bar/`）と、空のクエリ文字列を持つURL（例: `http://foo.bar/?`）を区別できるようにするための変更が導入されました。これにより、URLのパースと再構築の際に、元のURLの意図が正確に保持されるようになります。

## 元コミット内容

`net/url`: 値のないクエリ文字列をサポート

以前は、`url.URL` においてクエリ文字列の存在を示すために `RawQuery` が使用されていました。しかし、このアプローチでは、クエリ文字列が全くないURL (`http://foo.bar/`) と、値のないクエリを持つURL (`http://foo.bar/?`) を区別することができませんでした。

後者の形式のURLを示すために `ForceQuery` フィールドを追加し、`URL.String` でこれを使用して末尾に `?` を持つ一致するURLを作成するようにしました。

`Fixes #13488`

## 変更の背景

この変更の背景には、URLの厳密な表現と、それに基づくアプリケーションの挙動の正確性に関する問題がありました。HTTPプロトコルやWeb標準において、URLの末尾に疑問符 (`?`) が存在するかどうかは、単なる装飾ではなく、意味を持つ場合があります。

具体的には、以下のようなシナリオで問題が発生していました。
1.  **URLの正規化とキャッシュ**: `http://example.com/path` と `http://example.com/path?` は、技術的には異なるリソースを指す可能性があります。例えば、後者はクエリパラメータが空であることを明示的に示し、サーバー側で異なる処理（例: キャッシュの無効化、特定のデフォルトパラメータの適用）を行う場合があります。
2.  **APIの互換性**: 一部のWeb APIやシステムでは、空のクエリ文字列を持つURL (`?` で終わるURL) を特定の意味合いで解釈することがあります。`net/url` パッケージがこれらのURLを正しくパースし、再構築できない場合、クライアントとサーバー間の互換性問題や予期せぬ挙動を引き起こす可能性がありました。
3.  **ユーザーインターフェースの表示**: ユーザーが入力したURLや、システムが生成したURLを正確に表示する必要がある場合、末尾の `?` の有無は視覚的な正確性にも影響します。

以前の `net/url` の実装では、`URL` 構造体の `RawQuery` フィールドが空の場合、`URL.String()` メソッドは `?` を出力しませんでした。これにより、`http://foo.bar/` をパースして `URL` 構造体を作成し、それを再度 `String()` メソッドで文字列化すると `http://foo.bar/` となり、`http://foo.bar/?` をパースして文字列化しても同じく `http://foo.bar/` となってしまい、元のURLの意図が失われるという問題がありました。このコミットは、この情報損失を防ぎ、URLの厳密な表現を可能にすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **URL (Uniform Resource Locator)**: インターネット上のリソースの位置を示す識別子です。スキーム、ホスト、パス、クエリ、フラグメントなどの要素で構成されます。
    *   **スキーム (Scheme)**: `http`, `https`, `ftp` など、リソースにアクセスするためのプロトコルを示します。
    *   **ホスト (Host)**: リソースが置かれているサーバーのドメイン名またはIPアドレスです。
    *   **パス (Path)**: サーバー上のリソースの場所を示します。
    *   **クエリ (Query)**: リソースに渡される追加情報（キーと値のペア）です。通常、`?` の後に続き、`&` で区切られます。例: `?key1=value1&key2=value2`。
    *   **フラグメント (Fragment)**: リソース内の特定の部分を指す識別子です。通常、`#` の後に続きます。

2.  **Go言語の `net/url` パッケージ**: Go言語の標準ライブラリの一部で、URLのパース、構築、エンコード、デコードを行うための機能を提供します。
    *   `url.URL` 構造体: URLの各構成要素をフィールドとして持つ構造体です。
        *   `Scheme`: スキーム部分。
        *   `Host`: ホスト部分。
        *   `Path`: パス部分。
        *   `RawQuery`: クエリ文字列の生の形式（`?` を含まない）。例: `q=go+language`。
        *   `String()` メソッド: `url.URL` 構造体の内容から完全なURL文字列を再構築します。

3.  **URLの厳密な解釈**: Webサーバーやクライアントアプリケーションによっては、URLのわずかな違い（例: 末尾の `?` の有無）を異なる意味として解釈することがあります。これは、HTTPの仕様や、特定のアプリケーションの設計に依存します。

このコミットは、特に `RawQuery` が空であるにもかかわらず、URLが明示的にクエリ文字列の存在を示している場合（すなわち、URLが `?` で終わっている場合）を正確に表現するためのメカニズムを追加します。

## 技術的詳細

このコミットの技術的な核心は、`url.URL` 構造体に新しいブール型フィールド `ForceQuery` を追加し、URLのパースロジックと文字列化ロジックを修正することにあります。

1.  **`url.URL` 構造体への `ForceQuery` フィールドの追加**:
    ```go
    type URL struct {
        // ... 既存のフィールド ...
        ForceQuery bool   // append a query ('?') even if RawQuery is empty
        RawQuery   string // encoded query values, without '?'
        // ... 既存のフィールド ...
    }
    ```
    `ForceQuery` は、`RawQuery` が空であっても、URLの文字列表現に `?` を含めるべきかどうかを示すフラグです。これにより、`http://foo.bar/` と `http://foo.bar/?` の意味的な違いを `URL` 構造体内で保持できるようになります。

2.  **`parse` 関数における `ForceQuery` の設定**:
    URLをパースする `parse` 関数（`url.Parse` から内部的に呼び出される）が修正され、入力URLの末尾が `?` で終わっている場合に `ForceQuery` を `true` に設定するようになりました。
    ```go
    // 変更前:
    // rest, url.RawQuery = split(rest, "?", true)

    // 変更後:
    if strings.HasSuffix(rest, "?") {
        url.ForceQuery = true
        rest = rest[:len(rest)-1] // 末尾の '?' を取り除く
    } else {
        rest, url.RawQuery = split(rest, "?", true)
    }
    ```
    これにより、`http://foo.bar/?` のようなURLがパースされた際に、`url.RawQuery` は空になりますが、`url.ForceQuery` は `true` に設定され、元のURLの意図が構造体内に保存されます。

3.  **`URL.String()` メソッドにおける `ForceQuery` の利用**:
    `URL` 構造体を文字列に変換する `String()` メソッドが修正され、`RawQuery` が空であっても `ForceQuery` が `true` であれば `?` を出力するようになりました。
    ```go
    // 変更前:
    // if u.RawQuery != "" {
    //     buf.WriteByte('?')
    //     buf.WriteString(u.RawQuery)
    // }

    // 変更後:
    if u.ForceQuery || u.RawQuery != "" {
        buf.WriteByte('?')
        buf.WriteString(u.RawQuery)
    }
    ```
    この変更により、`ForceQuery` が `true` の `URL` 構造体は、`RawQuery` が空であっても `String()` メソッドによって末尾に `?` を持つURLとして再構築されるようになります。

4.  **`URL.RequestURI()` メソッドにおける `ForceQuery` の利用**:
    `RequestURI()` メソッドも同様に `ForceQuery` を考慮するように変更されました。このメソッドは、HTTPリクエストのURI部分（パスとクエリ）を生成するために使用されます。
    ```go
    // 変更前:
    // if u.RawQuery != "" {
    //     result += "?" + u.RawQuery
    // }

    // 変更後:
    if u.ForceQuery || u.RawQuery != "" {
        result += "?" + u.RawQuery
    }
    ```
    これにより、`RequestURI()` も `ForceQuery` の状態を尊重し、必要に応じて `?` を含んだURIを生成します。

これらの変更により、`net/url` パッケージは、URLのクエリ文字列の有無に関するより詳細なセマンティクスをサポートし、URLのパースと再構築の際の忠実度を高めることができました。

## コアとなるコードの解説

このコミットの主要な変更は、`url.URL` 構造体に `ForceQuery` という新しいブール型フィールドを導入した点です。このフィールドは、`RawQuery` が空であっても、URLの文字列表現に疑問符 (`?`) を含めるべきかどうかを明示的に示す役割を担います。

1.  **`URL` 構造体**: `ForceQuery` フィールドが追加されたことで、`net/url` パッケージは、クエリ文字列が全く存在しないURLと、クエリ文字列が空であるURLを内部的に区別できるようになりました。これは、URLのセマンティクスをより正確に表現するために不可欠です。

2.  **`parse` 関数**: URLのパース処理において、入力されたURL文字列が末尾に `?` を持つ場合、`ForceQuery` が `true` に設定されます。これにより、元のURLが空のクエリ文字列を意図していたという情報が `URL` 構造体に保存されます。`split` 関数は、クエリ文字列の有無を判断し、`RawQuery` を設定するために使用されますが、`ForceQuery` の導入により、`?` の有無の判断がより洗練されました。

3.  **`URL.String()` メソッド**: このメソッドは、`URL` 構造体の内容から完全なURL文字列を再構築します。変更後、`u.ForceQuery || u.RawQuery != ""` という条件が導入されました。これは、「`ForceQuery` が `true` であるか、または `RawQuery` が空でない場合」に `?` を出力するという意味です。このロジックにより、`ForceQuery` が `true` であれば、たとえ `RawQuery` が空であっても、再構築されたURLには末尾に `?` が含まれるようになります。

4.  **`URL.RequestURI()` メソッド**: `RequestURI()` メソッドも同様に `u.ForceQuery || u.RawQuery != ""` の条件を使用するように変更されました。このメソッドは、HTTPリクエストラインで使用されるURI部分を生成するため、この変更はHTTPリクエストの正確な構築にも影響します。

これらの変更は、Goの `net/url` パッケージがURLの表現においてより堅牢で、Web標準や特定のアプリケーションの要件に対してより忠実になることを保証します。特に、URLの正規化や、特定のAPIとの連携において、この機能は重要な役割を果たす可能性があります。

## 変更の背景

Go言語のマップ（`map`）は、キーとして使用される型に「比較可能（comparable）」であるという厳格な要件を課しています。これは、マップがキーの等価性を判断するために内部的にハッシュと等価性チェックを行う必要があるためです。インターフェース型は、その性質上、任意の具象型を保持できるため、コンパイル時にその具象型の比較可能性を静的に保証することができません。

このコミットの背景には、Go言語の初期開発段階において、インターフェース型をマップのキーとして使用しようとした際に発生する、コンパイラによる型チェックの挙動を明確にする必要があったことが挙げられます。特に、インターフェース型が自身の定義内でマップのキーとして再帰的に参照されるようなエッジケースにおいて、コンパイラがどのように振る舞うべきか、そしてそれがGoの型システムの一貫性と安全性をどのように保つかを示す必要がありました。

このコミットは、このような再帰的なインターフェース定義がマップキーとして無効であることを明示的にテストすることで、Go言語の設計原則、特に「マップキーは比較可能でなければならない」というルールを強化し、開発者に対してこの制約を早期に認識させることを目的としています。

## 前提知識の解説

### Goのインターフェース

Goのインターフェースは、メソッドのシグネチャの集合を定義する型です。インターフェース型は、そのインターフェースで定義されたすべてのメソッドを実装する任意の具象型の値を保持できます。インターフェース自体はデータを持ちませんが、その背後にある具象型の値と、その具象型の型情報（型ディスクリプタ）の2つの要素から構成されます。

インターフェースの重要な特性は以下の通りです。
*   **動的な型付け**: インターフェース変数は、実行時に異なる具象型の値を保持できます。
*   **静的な型チェック**: コンパイル時に、インターフェース変数が特定のメソッドセットを実装しているかどうかがチェックされます。
*   **比較可能性**: インターフェースの値は、以下の条件で比較可能です。
    *   両方のインターフェースが`nil`である場合、等しい。
    *   両方のインターフェースが同じ具象型の値を保持し、その具象型の値が比較可能であり、かつ値が等しい場合、等しい。
    *   異なる具象型の値を保持している場合、または具象型の値が比較可能でない場合、比較はできません（コンパイルエラーまたは実行時パニック）。

### Goのマップ

Goのマップ（`map[KeyType]ValueType`）は、キーと値のペアを格納するハッシュテーブルの実装です。マップのキーには厳格な要件があります。

*   **比較可能性**: マップのキー型は「比較可能」でなければなりません。これは、Go言語仕様で定義されており、`==`演算子または`!=`演算子で比較できる型を指します。
    *   数値型、文字列型、ブール型は比較可能です。
    *   ポインタ型、チャネル型は比較可能です。
    *   構造体型は、そのすべてのフィールドが比較可能であれば比較可能です。
    *   配列型は、その要素型が比較可能であれば比較可能です。
    *   インターフェース型は、その動的な型と値が比較可能であれば比較可能です。しかし、インターフェース型自体をマップキーとして宣言することは、その動的な型がコンパイル時に確定しないため、一般的に許可されません。
    *   スライス型、マップ型、関数型は比較不可能であり、マップのキーにはなれません。

マップはキーのハッシュ値を計算し、そのハッシュ値とキーの等価性チェック（`==`演算子）を使用して、マップ内の要素を効率的に検索、挿入、削除します。キーが比較可能でない場合、これらの操作を正しく実行できません。

### 再帰的な型定義

Goでは、型が自身の定義内で自身を参照する「再帰的な型定義」が可能です。例えば、リンクリストのノードやツリー構造の定義などでよく見られます。

```go
type Node struct {
    Value int
    Next  *Node
}
```

このような再帰はポインタ型を介して行われることが多く、ポインタは比較可能であるため問題ありません。しかし、インターフェース型が再帰的に自身を参照し、かつそれがマップのキーとして使用される場合、コンパイラは型の比較可能性を静的に判断できなくなるという問題が生じます。

## 技術的詳細

このコミットが対処している技術的な問題は、Goの型システムにおけるインターフェースの動的な性質と、マップキーの静的な比較可能性要件との間の根本的な不整合にあります。

1.  **インターフェースの動的な性質**: インターフェース型`I`の変数は、実行時に`I`を実装する任意の具象型`T`の値を保持できます。この`T`は、`int`、`string`、`struct`など、様々な型になり得ます。
2.  **マップキーの比較可能性要件**: マップのキーは、コンパイル時にその型が比較可能であることが保証されなければなりません。これは、マップがキーの等価性を判断するために`==`演算子を使用するためです。
3.  **不整合**: インターフェース型`I`をマップキー`map[I]bool`として宣言しようとすると、コンパイラは`I`が保持する可能性のあるすべての具象型が比較可能であるかどうかを静的に判断できません。例えば、`I`がスライス型（比較不可能）を保持する可能性がある場合、そのマップキーは比較不可能になってしまいます。Goの型システムは、このような不確実性を許容しません。
4.  **再帰的な参照の複雑性**: さらに、今回のケースではインターフェース`I`が自身の定義内で`map[I]bool`という形で自身を参照しています。

    ```go
    type I interface {
        m(map[I] bool)
    }
    ```

    この定義は、`I`が`m`というメソッドを持つことを要求しており、その`m`メソッドは`map[I]bool`型の引数を取ります。ここで、`map[I]bool`のキー型が`I`であるため、`I`の比較可能性を判断するためには、`I`自身の比較可能性を知る必要があります。これは循環参照となり、コンパイラが型の比較可能性を解決できなくなります。

    Goコンパイラは、このような循環的な依存関係を持つ型定義において、マップキーの比較可能性を静的に解決することができません。そのため、このような定義は「無効なマップキー型」としてコンパイルエラーとなるように設計されています。このコミットは、この設計上の制約をテストケースとして明示的に追加することで、コンパイラの挙動を文書化し、将来の変更に対する回帰テストとして機能させます。

## コアとなるコードの解説

`test/bugs/bug165.go`の以下のコードがこのコミットの核心です。

```go
type I interface {
	m(map[I] bool)
}
```

このコードは、Goコンパイラがインターフェース型`I`の定義を解析する際に、`m`メソッドの引数型`map[I]bool`に遭遇します。ここで、マップのキー型が`I`であるため、コンパイラは`I`が比較可能であるかどうかを判断しようとします。しかし、`I`の定義自体がまだ完全に解決されていない（`I`の比較可能性が`map[I]bool`の比較可能性に依存し、それがまた`I`の比較可能性に依存するという循環がある）ため、コンパイラは`I`が比較可能であるという保証を得ることができません。

Go言語の仕様では、マップのキー型は比較可能でなければならないと明確に定められています。インターフェース型は、その動的な性質により、コンパイル時に比較可能性を静的に保証することが困難です。特に、上記のような再帰的な定義では、コンパイラは無限ループに陥るか、あるいは比較可能性を判断できない状態になります。

したがって、コンパイラは`bugs/bug165.go:6: invalid map key type I`というエラーを生成します。これは、インターフェース型`I`がマップのキーとして使用するには無効であることを示しています。このエラーは、Goの型システムがマップキーの比較可能性を厳密に強制し、型安全性を維持していることの証拠です。

このテストケースの追加により、Go言語のコンパイラがこのような特定の型定義のシナリオでどのように振る舞うべきかという仕様が明確になり、将来のコンパイラの変更や最適化においてもこの挙動が維持されることが保証されます。

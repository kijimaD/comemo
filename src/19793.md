## 元コミット内容

このコミットの目的は「runtime: simplify code」（ランタイム: コードの簡素化）です。具体的には、Goランタイムのガベージコレクタが使用するワークバッファのメモリ割り当てロジックを簡素化しています。

## 変更の背景

このコミットの背景には、Goランタイムのガベージコレクタ（GC）の効率性と保守性の向上が挙げられます。以前のワークバッファの割り当てメカニズムは、カスタムのチャンクベースの割り当てとロック機構を伴っており、これは複雑で、潜在的なバグの原因となる可能性がありました。

GoのGCは、並行マークフェーズ中に複数のゴルーチン（マークワーカー）が同時にオブジェクトを走査し、マークします。このプロセスでは、マークすべきオブジェクトのアドレスを一時的に保持するための「ワークバッファ」が頻繁に必要とされます。これらのワークバッファは、GCサイクルの間、または複数のGCサイクルにわたって存在し続ける可能性のある、比較的寿命の長い小さなオブジェクトです。

以前の実装では、`work`構造体内に`chunk`と`nchunk`というフィールドを持ち、GCがワークバッファを必要とするたびに、このカスタムチャンクからメモリを切り出して割り当てていました。このカスタム割り当てロジックは、排他制御のために`Lock`を使用しており、並行処理のボトルネックとなる可能性がありました。また、手動でのチャンク管理は、コードの可読性を低下させ、メモリリークや二重解放といったバグのリスクを伴います。

このコミットは、このようなカスタムで複雑な割り当てロジックを、Goランタイムが内部的に提供するより汎用的で効率的な`runtime·persistentalloc`関数に置き換えることで、コードを簡素化し、堅牢性を高めることを目的としています。`runtime·persistentalloc`は、GCによって管理されない、ランタイム内部のデータ構造（GCのワークバッファのような）のために設計された割り当て関数であり、GCのオーバーヘッドなしに、比較的寿命の長いオブジェクトを効率的に割り当てることができます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびガベージコレクタに関する知識が必要です。

1.  **Goのガベージコレクタ (GC)**:
    *   Goは並行マーク＆スイープ型のガベージコレクタを採用しています。これは、プログラムの実行と並行してGCが動作し、アプリケーションの一時停止時間（STW: Stop-The-World）を最小限に抑えることを目指しています。
    *   **マークフェーズ**: GCの主要なフェーズの一つで、到達可能な（参照されている）オブジェクトを特定し、マークします。このフェーズでは、複数のマークワーカーゴルーチンがヒープを走査します。
    *   **ワークバッファ (Workbuf)**: マークフェーズ中に、マークワーカーが次に走査すべきオブジェクトのアドレスを一時的に格納するために使用されるバッファです。これらのバッファは、ロックフリースタック（`work.empty`と`work.full`）を介してワーカー間で共有されます。

2.  **`runtime·lfstackpush` と `runtime·lfstackpop`**:
    *   これらはGoランタイム内部で使用されるロックフリースタック操作関数です。複数のゴルーチンが競合することなく、安全にスタックに要素をプッシュしたりポップしたりするために設計されています。GCのワークバッファの管理に利用されます。

3.  **`runtime·SysAlloc`**:
    *   Goランタイムがオペレーティングシステムから直接メモリを要求する際に使用する低レベルの関数です。通常、非常に大きなメモリチャンク（例えば、ヒープ領域全体や、GCが使用する大きな内部バッファなど）を割り当てるために使用されます。この関数は、GCの統計情報（`mstats.gc_sys`）を更新します。

4.  **`runtime·persistentalloc`**:
    *   Goランタイム内部で使用される特別なメモリ割り当て関数です。GCによって管理されない、ランタイム自身の内部データ構造（例えば、スケジューラが使用する構造体、GCのワークバッファ、型情報など）のために設計されています。これらのオブジェクトはGCの対象外であり、通常はプログラムの実行期間中ずっと存在します。`runtime·SysAlloc`とは異なり、より小さなアロケーションに適しており、GCのオーバーヘッドを回避できます。

5.  **`Lock` と `Note`**:
    *   Goランタイム内部で使用される同期プリミティブです。`Lock`はミューテックス（排他ロック）を提供し、共有リソースへのアクセスを保護します。`Note`は、ゴルーチンが特定のイベントを待機したり、イベントを通知したりするためのメカニズムです。このコミットでは、`Lock`が削除されています。

6.  **`mstats.gc_sys`**:
    *   Goランタイムのメモリ統計情報の一部で、GCがシステムから割り当てたメモリの量を追跡します。

7.  **`CacheLineSize`**:
    *   CPUのキャッシュラインのサイズを表す定数です。メモリ割り当てにおいて、キャッシュライン境界にアラインメント（整列）することで、キャッシュの効率を向上させ、パフォーマンスを最適化することができます。

## 技術的詳細

このコミットの技術的な核心は、GCワークバッファの割り当て戦略の変更にあります。

**変更前**:
`work`構造体には、`chunk`（メモリチャンクへのポインタ）と`nchunk`（チャンク内の残りのバイト数）というフィールドがありました。`getempty`関数が新しいワークバッファを必要とする際、まず`work.empty`ロックフリースタックから既存の空のバッファを取得しようとします。もしスタックが空であれば、カスタムのメモリ割り当てロジックが実行されました。

このカスタムロジックは以下の手順で行われていました：
1.  `runtime·lock(&work)` を使用して`work`構造体をロックし、排他制御を確保します。
2.  `work.nchunk`が`sizeof *b`（ワークバッファのサイズ）よりも小さい場合、つまり現在のチャンクに十分なスペースがない場合、新しい大きなチャンク（1MB: `1<<20`バイト）を`runtime·SysAlloc`でシステムから割り当てます。
3.  新しいワークバッファは、この`work.chunk`から切り出され、`work.chunk`と`work.nchunk`が更新されます。
4.  `runtime·unlock(&work)` でロックを解放します。

このアプローチの問題点は、ワークバッファの割り当てごとにロックが必要となるため、並行マークフェーズにおいてロック競合が発生し、パフォーマンスのボトルネックとなる可能性があったことです。また、手動でのチャンク管理は、コードの複雑性を増していました。

**変更後**:
`work`構造体から`Lock`、`chunk`、`nchunk`フィールドが削除されました。
`getempty`関数内で`work.empty`スタックが空の場合の割り当てロジックが、単一の`runtime·persistentalloc`呼び出しに置き換えられました。

`b = runtime·persistentalloc(sizeof(*b), CacheLineSize, &mstats.gc_sys);`

この変更により、以下の利点が得られます。
*   **簡素化**: カスタムのチャンク管理ロジックとそれに伴うロックが不要になり、コードが大幅に簡素化されました。
*   **パフォーマンス**: `runtime·persistentalloc`は、GCの対象外となる小さなオブジェクトの割り当てに最適化されており、通常はロックを必要としないか、より粒度の細かいロックを使用するため、並行処理の効率が向上します。
*   **堅牢性**: ランタイム内部の信頼性の高い割り当て関数を使用することで、手動メモリ管理に起因する潜在的なバグ（メモリリーク、アラインメントの問題など）のリスクが低減されます。
*   **一貫性**: ランタイム内部の他の永続的なデータ構造と同様の割り当てメカニズムを使用することで、コードベース全体の一貫性が向上します。

この変更は、GCのワークバッファがGCサイクルを超えても存在し続ける可能性があるという性質と、`runtime·persistentalloc`の設計思想が合致しているため、非常に理にかなった改善と言えます。

## コアとなるコードの解説

このコミットの核心は、`getempty`関数における`Workbuf`（ワークバッファ）の取得と割り当てロジックの変更です。

`getempty`関数は、GCのマークフェーズ中にマークワーカーが使用する空のワークバッファを取得する役割を担っています。

**変更前**:
1.  関数はまず、`work.full`スタックに現在のワークバッファ`b`をプッシュし、それを使い終わったことを示します（`if(b != nil) runtime·lfstackpush(&work.full, &b->node);`）。
2.  次に、`work.empty`スタックから空のワークバッファを取得しようとします（`b = (Workbuf*)runtime·lfstackpop(&work.empty);`）。
3.  もし`work.empty`スタックが空で、利用可能なワークバッファがない場合（`if(b == nil)`）、新しいワークバッファを割り当てる必要がありました。
    *   この割り当ては、`runtime·lock(&work)`で`work`構造体をロックし、排他制御を行っていました。
    *   `work.nchunk`（現在のチャンクの残りサイズ）が不足している場合、`runtime·SysAlloc`を使って1MBの新しいメモリチャンクをシステムから割り当て、`work.chunk`に設定していました。
    *   新しいワークバッファは、`work.chunk`の先頭から切り出され、`work.chunk`と`work.nchunk`が更新されていました。
    *   最後に`runtime·unlock(&work)`でロックを解放していました。
4.  取得または割り当てられたワークバッファの`nobj`フィールド（バッファ内のオブジェクト数）を0にリセットし、返していました。

**変更後**:
1.  `work.full`へのプッシュと`work.empty`からのポップのロジックは変更されていません。
2.  `if(b == nil)`（空のワークバッファがない場合）のブロックが大幅に簡素化されました。
    *   カスタムのチャンク管理ロジックと、それに伴う`runtime·lock`および`runtime·unlock`の呼び出しが完全に削除されました。
    *   代わりに、単一の呼び出し`b = runtime·persistentalloc(sizeof(*b), CacheLineSize, &mstats.gc_sys);`によって新しいワークバッファが割り当てられます。
3.  割り当てられたワークバッファの`nobj`を0にリセットする部分は同じです。

この変更により、ワークバッファの割り当てがGoランタイムのより汎用的で効率的な`runtime·persistentalloc`に委ねられることになりました。これにより、GCのマークフェーズにおけるワークバッファの割り当てが、よりシンプルで、ロック競合の少ない、堅牢なものになりました。`persistentalloc`は、GCの対象外となるランタイム内部のデータ構造のために設計されているため、GCのオーバーヘッドを発生させることなく、これらのワークバッファを効率的に管理できます。また、`CacheLineSize`でアラインメントすることで、CPUキャッシュの効率も考慮されています。

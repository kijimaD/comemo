## 元コミット内容

このコミットは、GoランタイムにおけるWindowsシステムコール関連のC言語実装ファイル `syscall_windows.c` をGo言語に変換することを目的としています。

主な理由は、`syscall.Syscall` がブロックする際に、ガベージコレクタがそのスタックフレームをスキャンする必要があるためです。C言語のフレームにはガベージコレクションに関する情報がないため、これが問題となっていました。この問題により、当時のWindowsビルドが壊れていることが報告されていました（参照: [http://build.golang.org/log/152ca9a4be6783d3a8bf6e2f5b9fc265089728b6](http://build.golang.org/log/152ca9a4be6783d3a8bf6e2f5b9fc265089728b6)）。

## 変更の背景

Go言語のガベージコレクタ（GC）は、プログラムの実行中にヒープ上のオブジェクトを追跡し、不要になったメモリを解放する役割を担っています。GCが正確に動作するためには、プログラムの実行状態、特にスタック上のポインタ情報を正確に把握している必要があります。これにより、GCは到達可能なオブジェクトを特定し、そうでないオブジェクトを回収できます。

Windowsシステムコール（`syscall.Syscall` など）は、GoプログラムからOSのネイティブAPIを呼び出すためのメカニズムです。これらのシステムコールは、多くの場合、OSカーネル内でブロック（待機）する可能性があります。例えば、ファイルI/Oやネットワーク通信など、外部リソースへのアクセスは完了するまで待機が必要です。

問題は、GoランタイムがC言語で実装された `syscall_windows.c` を介してこれらのシステムコールを呼び出していた点にありました。C言語の関数が実行されている間、GoのガベージコレクタはCスタックフレームの内容を「理解」できません。C言語のスタックフレームには、GoのGCが必要とするポインタ情報（どのメモリ領域がGoのヒープオブジェクトへの参照であるか）が含まれていないためです。

もしシステムコールがブロックしている間にGCが実行され、そのCスタックフレーム上にGoのヒープオブジェクトへの参照が存在していた場合、GCはその参照を認識できず、誤ってそのオブジェクトを回収してしまう可能性があります。これは「use-after-free」などの深刻なメモリ破損バグを引き起こし、プログラムのクラッシュや予期せぬ動作につながります。

このコミットの背景には、実際にWindowsビルドがこの問題によって壊れているという具体的な報告がありました。これは、GoのランタイムがCGO（C言語との相互運用）を介してシステムコールを呼び出す際の、GCの正確性に関する根本的な課題を浮き彫りにしました。この問題を解決するためには、GCがスキャンできるGo言語のフレーム内でシステムコールが実行されるように、実装をGo言語に移行する必要がありました。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **ガベージコレクション (GC) とスタックのスキャン**:
    *   GoのGCは、主に「マーク＆スイープ」方式を採用しています。GCサイクルが開始されると、まず「ルート」と呼ばれる既知のポインタ（グローバル変数、レジスタ、そして**実行中のゴルーチンのスタック**など）から到達可能なすべてのオブジェクトをマークします。
    *   スタックのスキャンは、GCが実行中の関数呼び出しスタックを調べて、そこに存在するポインタ（ヒープ上のGoオブジェクトを指すアドレス）を識別するプロセスです。これにより、GCはまだ使用されているオブジェクトを誤って回収するのを防ぎます。
    *   Goのコンパイラとランタイムは、Goの関数フレームがどのようにレイアウトされ、どこにポインタがあるかを知っています。しかし、C言語の関数フレームについては、Goランタイムはその内部構造を知りません。

2.  **CGO (C Foreign Function Interface)**:
    *   Go言語は、C言語のコードを呼び出すためのCGOというメカニズムを提供します。これにより、Goプログラムは既存のCライブラリを利用したり、OSのネイティブAPIに直接アクセスしたりできます。
    *   CGOを介してC関数を呼び出す際、Goの実行は一時的にCのスタックに切り替わります。このCのスタックフレームは、GoのGCからは「不透明」な領域となります。

3.  **`syscall.Syscall` とブロッキングコール**:
    *   `syscall` パッケージは、GoプログラムからOSのシステムコールを直接呼び出すための低レベルなインターフェースを提供します。Windowsでは、これはWin32 APIの呼び出しに相当します。
    *   多くのシステムコール（特にI/O関連）は、操作が完了するまで実行を一時停止する「ブロッキングコール」です。例えば、ファイルからデータを読み込む際に、データが利用可能になるまで待機します。

4.  **`runtime.cgocall` と `runtime.asmstdcall`**:
    *   `runtime.cgocall` は、GoからC関数を呼び出すためのランタイム関数です。これは、GoのスタックからCのスタックへの切り替えを管理します。
    *   `runtime.asmstdcall` は、Windowsの`stdcall`呼び出し規約に従ってC関数を呼び出すためのアセンブリルーチンです。これは、引数の渡し方やスタックのクリーンアップなど、低レベルな詳細を処理します。

5.  **`libcall` 構造体**:
    *   Goランタイム内部で使用される構造体で、Cライブラリ関数を呼び出す際の情報を保持します。これには、呼び出す関数のポインタ、引数の数、引数へのポインタ、戻り値などが含まれます。

これらの概念を理解することで、C言語のシステムコール実装がGoのGCにとってなぜ問題であったか、そしてその解決策としてGo言語への移行がなぜ必要だったのかが明確になります。

## 技術的詳細

このコミットの核心は、Windowsシステムコールを処理するロジックをC言語 (`src/runtime/syscall_windows.c`) からGo言語 (`src/runtime/syscall_windows.go`) へ移行することです。これにより、Goのガベージコレクタがシステムコール中にスタックを正確にスキャンできるようになります。

具体的な変更点は以下の通りです。

1.  **`syscall_windows.c` の削除と `syscall_windows.go` の追加**:
    *   以前はC言語で実装されていた `syscall.Syscall`、`syscall.Syscall6` などのシステムコールラッパー関数、および `LoadLibrary` や `GetProcAddress` といったDLL関連の関数が、完全にGo言語で再実装されました。
    *   Go言語で実装されたこれらの関数は、`runtime.cgocall_errno` を使用して、最終的にアセンブリ言語の `asmstdcall` を介して実際のWin32 APIを呼び出します。重要なのは、これらのGo関数がGCによってスキャン可能なGoスタックフレームを持つことです。

2.  **`src/runtime/runtime.h` の変更**:
    *   `struct LibCall` の `fn` と `args` メンバーの型が `void*` から `uintptr` に変更されました。これは、GoのポインタがCのポインタとして扱われる際に、GCがその内容を追跡できない問題を回避するためです。`uintptr` は単なる整数型であり、GCはこれをポインタとして解釈しないため、GCスキャン中に安全に無視できます。実際のポインタ値はGoのコード内で `unsafe.Pointer` を介して変換されます。

3.  **`src/runtime/os_windows.c` の変更**:
    *   `runtime.getLoadLibrary` と `runtime.getGetProcAddress` という新しいC関数が追加されました。これらは、Go側から `LoadLibrary` と `GetProcAddress` の関数ポインタを取得するために使用されます。Go言語のコードがCの関数ポインタを直接参照するのではなく、Cのヘルパー関数を介して `uintptr` として取得することで、GCの安全性を確保します。
    *   `runtime.stdcallX` 関数群（`stdcall0` から `stdcall7`）において、`g->m->libcall.fn` および `g->m->libcall.args` への代入が `(uintptr)fn` および `(uintptr)&a0` のように `uintptr` にキャストされるようになりました。これもGCの安全性を高めるための変更です。

4.  **`src/runtime/thunk_windows.s` の追加**:
    *   この新しいアセンブリファイルは、`syscall` パッケージのGo関数（例: `syscall.Syscall`）から、Goランタイム内の対応するGo関数（例: `runtime.syscall_Syscall`）へのジャンプ（thunk）を提供します。
    *   Goの `syscall` パッケージは、ユーザーが直接呼び出すAPIを提供しますが、その実体はランタイム内部の関数に委譲されます。このアセンブリ層は、その委譲を効率的に行い、Goの呼び出し規約とランタイムの内部構造を橋渡しします。

5.  **`src/syscall/asm_windows.s` の削除**:
    *   以前は `syscall` パッケージのGo関数からCのランタイム関数へのジャックを担っていたアセンブリファイルが不要になったため削除されました。

6.  **`src/syscall/dll_windows.go` の変更**:
    *   コメントが `// Implemented in ../runtime/syscall_windows.goc.` から `// Implemented in ../runtime/syscall_windows.go.` に変更され、実装がCファイルからGoファイルに移行したことを反映しています。

これらの変更により、`syscall.Syscall` が呼び出された際に、Goのスタックフレームが維持され、GCがそのフレームをスキャンしてポインタ情報を正確に把握できるようになります。これにより、システムコールがブロックしている間でもGCが安全に実行され、メモリ破損のリスクが排除されます。

## コアとなるコードの変更箇所

このコミットにおけるコアとなる変更は、`src/runtime/syscall_windows.c` の削除と、`src/runtime/syscall_windows.go` および `src/runtime/thunk_windows.s` の追加です。

特に、`src/runtime/syscall_windows.go` に追加された以下の関数群が、以前C言語で実装されていたシステムコールラッパーのGo言語版です。

```go
//go:nosplit
func syscall_loadlibrary(filename *uint16) (handle, err uintptr) { ... }

//go:nosplit
func syscall_getprocaddress(handle uintptr, procname *byte) (outhandle, err uintptr) { ... }

//go:nosplit
func syscall_Syscall(fn, nargs, a1, a2, a3 uintptr) (r1, r2, err uintptr) { ... }

//go:nosplit
func syscall_Syscall6(fn, nargs, a1, a2, a3, a4, a5, a6 uintptr) (r1, r2, err uintptr) { ... }

//go:nosplit
func syscall_Syscall9(fn, nargs, a1, a2, a3, a4, a5, a6, a7, a8, a9 uintptr) (r1, r2, err uintptr) { ... }

//go:nosplit
func syscall_Syscall12(fn, nargs, a1, a2, a3, a4, a5, a6, a7, a8, a9, a10, a11, a12 uintptr) (r1, r2, err uintptr) { ... }

//go:nosplit
func syscall_Syscall15(fn, nargs, a1, a2, a3, a4, a5, a6, a7, a8, a9, a10, a11, a12, a13, a14, a15 uintptr) (r1, r2, err uintptr) { ... }
```

また、`src/runtime/thunk_windows.s` に追加された以下のジャンプ命令も重要です。

```assembly
TEXT syscall·Syscall(SB),NOSPLIT,$0-0
	JMP	runtime·syscall_Syscall(SB)

TEXT syscall·Syscall6(SB),NOSPLIT,$0-0
	JMP	runtime·syscall_Syscall6(SB)

... (同様に他のSyscall関数とloadlibrary, getprocaddress, compileCallback)
```

## コアとなるコードの解説

`src/runtime/syscall_windows.go` 内の各 `syscall_SyscallX` 関数は、Go言語でシステムコールをラップする役割を担っています。これらの関数は、`//go:nosplit` ディレクティブが付与されています。これは、コンパイラに対して、この関数内でスタックを拡張しないように指示するものです。これは、これらの関数が非常に低レベルであり、スタックのレイアウトが厳密に制御される必要があるためです。

これらの関数内部では、`libcall` 構造体を使用しています。

```go
type libcall struct {
	fn   uintptr // 呼び出す関数のアドレス
	n    uintptr // 引数の数
	args uintptr // 引数へのポインタ
	r1   uintptr // 戻り値1
	r2   uintptr // 戻り値2
	err  uintptr // エラーコード
}
```

この `libcall` 構造体に、呼び出すWin32 API関数のアドレス (`fn`)、引数の数 (`n`)、そして引数へのポインタ (`args`) を設定します。注目すべきは、`fn` と `args` が `uintptr` 型であることです。これは、GoのGCがこれらのフィールドをポインタとして扱わないようにするためです。実際のポインタ値は `unsafe.Pointer` を介して `uintptr` に変換されます。

そして、`cgocall_errno(unsafe.Pointer(funcPC(asmstdcall)), unsafe.Pointer(&c))` を呼び出します。
*   `funcPC(asmstdcall)` は、アセンブリ言語で実装された `asmstdcall` 関数のエントリポイントのアドレスを取得します。
*   `cgocall_errno` は、GoのランタイムがCGOのメカニズムを使ってC（またはアセンブリ）関数を呼び出すための内部関数です。この関数は、GoのスタックからCのスタックへの切り替えを安全に行い、エラーコードの処理も行います。

これにより、Goのスタックフレームが維持されたまま、`asmstdcall` が実際のWin32 APIを呼び出し、その結果が `libcall` 構造体に格納されます。システムコールがブロックしている間も、GoのスタックフレームはGCによってスキャン可能であるため、GCはスタック上のGoヒープオブジェクトへの参照を正確に追跡できます。

`src/runtime/thunk_windows.s` のアセンブリコードは、`syscall` パッケージの公開関数（例: `syscall.Syscall`）が、Goランタイム内部の対応する実装（例: `runtime.syscall_Syscall`）に直接ジャンプするためのシンプルな「thunk」（橋渡し）を提供します。これにより、Goのユーザーコードからシステムコールが呼び出された際に、効率的にランタイムのGo実装にディスパッチされます。

これらの変更の組み合わせにより、WindowsシステムコールがGoのGCと協調して動作するようになり、メモリ安全性と安定性が向上しました。

# [インデックス 2465] ファイルの概要

このコミットは、Go言語の`syscall`パッケージにおける386アーキテクチャ（特にLinuxとDarwin）向けのシステムコールに関する重要な修正を導入しています。主な目的は、32-bitシステム上での64-bitファイルシステムコール（`llseek`など）と、32-bitユーザー/グループID関連のシステムコールの互換性と正確性を向上させることです。これにより、Darwin/386環境での動作が回復し、Linux/386環境での安定性が改善されました。

## コミット

```
386 system call fixes:
  * use 64-bit file system calls (Linux, Darwin)
  * use 32-bit [sic] uid/gid calls (Linux)
  * fix sockets on Linux

Darwin/386 works again.

Linux/386 is better but must never have worked;
there are still bugs surrounding the creation of new
threads in the runtime package.

R=austin
DELTA=1332  (673 added, 614 deleted, 45 changed)
OCL=30327
CL=30380
```

## 変更の背景

このコミットが行われた背景には、Go言語が初期段階で様々なアーキテクチャとオペレーティングシステムをサポートする上で直面した、システムコールに関する互換性の問題があります。特に32-bitシステム（386アーキテクチャ）では、ファイルサイズやオフセット、ユーザー/グループIDの表現方法が64-bitシステムと異なるため、システムコールを正しく扱うことが困難でした。

具体的な問題点としては以下の点が挙げられます。

1.  **2GBの壁（Large File Supportの欠如）**: 32-bitシステムでは、標準のファイル操作関数（`lseek`, `stat`など）が32-bitのオフセットやサイズを使用するため、2GBを超えるファイルを扱うことができませんでした。これは現代のシステムでは大きな制約となります。
2.  **UID/GIDのサイズ不一致**: Linuxの386アーキテクチャでは、ユーザーID（UID）やグループID（GID）が16-bitで扱われるシステムコールと、32-bitで扱われるシステムコールが混在していました。Goの`syscall`パッケージがこれらを適切に区別して呼び出さないと、予期せぬエラーやセキュリティ上の問題が発生する可能性がありました。
3.  **Darwin/386の動作不良**: Darwin（macOS）の386アーキテクチャにおいて、システムコールが正しく機能せず、Goプログラムが動作しない状態でした。
4.  **Linuxソケットの不具合**: Linux環境でのソケット関連のシステムコールに不具合があり、ネットワークプログラミングに影響を与えていました。

これらの問題を解決し、Goプログラムが32-bitシステムでも安定して動作し、現代的なファイルシステム機能を利用できるようにするために、このコミットが導入されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **システムコール (System Call)**: オペレーティングシステムが提供するサービス（ファイルI/O、メモリ管理、プロセス制御など）をプログラムが利用するためのインターフェースです。Go言語の`syscall`パッケージは、これらのシステムコールをGoプログラムから直接呼び出すための機能を提供します。
2.  **32-bit vs 64-bit アーキテクチャ**:
    *   **32-bit (x86/i386)**: レジスタやメモリアドレスが32-bit幅で、扱えるメモリ空間は最大4GBです。ファイルオフセットやサイズも通常32-bitで表現されるため、2GBを超えるファイルを直接扱うことができません。
    *   **64-bit (x86-64/AMD64)**: レジスタやメモリアドレスが64-bit幅で、より広大なメモリ空間を扱えます。ファイルオフセットやサイズも64-bitで表現されるため、大容量ファイルを問題なく扱えます。
3.  **Large File Support (LFS)**: 32-bitシステムで2GBを超えるファイルを扱うための仕組みです。これには、`lseek`の代わりに`llseek`（long long seek）を使用したり、`stat`構造体の代わりに`stat64`構造体を使用したりするなど、64-bit対応のシステムコールやデータ型を使用することが含まれます。通常、C言語では`_FILE_OFFSET_BITS=64`などのプリプロセッサマクロを定義することで有効化されます。
4.  **`llseek`システムコール**: 32-bit Linuxシステムにおいて、64-bitのファイルオフセットを扱うために導入されたシステムコールです。通常の`lseek`が32-bitオフセットしか受け付けないのに対し、`llseek`はオフセットを上位32-bitと下位32-bitに分割して引数として受け取り、64-bitの新しいオフセットを返します。
5.  **UID/GID (User ID / Group ID)**: Unix系システムでユーザーやグループを識別するための数値です。歴史的に16-bitで扱われることが多かったですが、現代のシステムでは32-bitが一般的です。Linuxでは、16-bit UID/GIDを扱うシステムコール（例: `chown`）と、32-bit UID/GIDを扱うシステムコール（例: `chown32`）が存在します。
6.  **`mksyscall`ツール**: Go言語の`syscall`パッケージで、`//sys`コメントでマークされたGo関数定義から、対応するアセンブリコードやGoのラッパーコード（`zsyscall_*.go`ファイル）を自動生成するためのツールです。これにより、各OS/アーキテクチャ固有のシステムコール呼び出し規約に合わせたコードを効率的に生成できます。

## 技術的詳細

このコミットの技術的詳細は、主に32-bitアーキテクチャにおけるシステムコール呼び出しの正確性と互換性の向上に焦点を当てています。

1.  **64-bitファイルシステムコールの導入**:
    *   **`llseek`の利用**: 32-bit LinuxおよびDarwin/386において、ファイルオフセットを扱う`Seek`関数が、64-bitオフセットをサポートする`llseek`システムコール（Linuxでは`SYS__LLSEEK`、Darwinでは`SYS_LSEEK`）を使用するように変更されました。
    *   **アセンブリでの実装**: `syscall/asm_linux_386.s`に`syscall·Seek`というアセンブリ関数が追加されました。これは、`llseek`システムコールが64-bitのオフセットを引数として受け取り、64-bitの戻り値を返す際に、32-bitレジスタを組み合わせて処理する必要があるためです。具体的には、オフセットを`offset-high`と`offset-low`に分割して渡し、戻り値も`r0`と`r1`レジスタから64-bit値として再構築します。これにより、Goのランタイムがヒープアロケーションを発生させずに64-bitオフセットを扱えるようになります。
    *   **`mksyscall`の拡張**: `src/pkg/syscall/mksyscall`スクリプトに、32-bit環境で`int64`の戻り値を正しく処理するためのロジックが追加されました。これは、システムコールが2つの32-bitレジスタ（例: `r0`と`r1`）に64-bit値を分割して返す場合に、それらを結合してGoの`int64`型に変換するためのものです。
    *   **`_LARGEFILE_SOURCE`などの定義**: `src/pkg/syscall/types_linux.c`に`_LARGEFILE_SOURCE`, `_LARGEFILE64_SOURCE`, `_FILE_OFFSET_BITS 64`, `_GNU_SOURCE`といったプリプロセッサマクロが追加されました。これらは、Cライブラリが提供するファイルI/O関数が、デフォルトの32-bitではなく64-bitのファイルオフセットを使用するようにコンパイラに指示するための標準的な方法です。これにより、`stat`や`statfs`などの構造体が64-bit対応の`stat64`や`statfs64`にマッピングされ、大容量ファイルを正しく扱えるようになります。
    *   **`Stat_t`, `Statfs_t`, `Dirent`構造体の更新**: `src/pkg/syscall/ztypes_linux_386.go`において、ファイルサイズ、ブロック数、inode番号、ファイルオフセットなどのフィールドが`int32`や`uint32`から`int64`や`uint64`に変更され、64-bitファイルシステムに対応しました。

2.  **32-bit UID/GIDシステムコールの利用**:
    *   **Linux/386固有のsyscall定義**: `src/pkg/syscall/syscall_linux_386.go`に、`Chown`, `Fchown`, `Getegid`, `Geteuid`, `Getgid`, `Getuid`, `Lchown`, `Setfsgid`, `Setfsuid`, `Setgid`, `Setregid`, `Setresgid`, `Setresuid`, `Setreuid`, `getgroups`, `setgroups`といったUID/GID関連のシステムコールに対して、明示的に32-bit対応のシステムコール番号（例: `SYS_CHOWN32`, `SYS_GETEGID32`）を割り当てる`//sys`ディレクティブが追加されました。これにより、32-bit Linux環境でUID/GIDが正しく扱われるようになります。
    *   **`mksyscall -l32`**: `src/pkg/syscall/PORT`ファイルで、`linux_386`ターゲットに対して`mksyscall`ツールを`-l32`オプション付きで実行するように設定が変更されました。このオプションは、`mksyscall`が32-bit環境向けのシステムコールラッパーを生成する際に、特定の最適化や規約を適用することを示唆しています。

3.  **Linuxソケットの修正**:
    *   `src/pkg/syscall/asm_linux_386.s`内の`socketcall`アセンブリ関数において、戻り値とエラーコードをスタックに格納するオフセットが調整されました。これは、システムコール呼び出し規約の微妙な違いや、スタックフレームのレイアウト変更に対応するための修正と考えられます。

これらの変更により、Goの`syscall`パッケージは、32-bitアーキテクチャのLinuxおよびDarwin環境で、より堅牢かつ正確にシステムコールを扱えるようになりました。特に、大容量ファイルのサポートは、Goがより幅広いアプリケーションで利用される上で不可欠な機能です。

## コアとなるコードの解説

これらの変更は、Goの`syscall`パッケージが32-bitシステム上でOSの低レベルな機能とどのように連携するかを根本的に改善しています。

*   **`mksyscall -l32`の導入**: `PORT`ファイルでのこの変更は、`mksyscall`ツールがLinux/386向けにシステムコールラッパーを生成する際に、32-bit環境特有の考慮事項（例えば、レジスタの使用方法やデータ型のサイズ）を適用するように指示します。これにより、生成される`zsyscall_linux_386.go`ファイルがより正確なシステムコール呼び出しコードを含むようになります。

*   **`Seek`関数のアセンブリ実装 (`asm_linux_386.s`)**:
    *   32-bitシステムでは、64-bitの数値を単一のレジスタで扱うことができません。`llseek`システムコールは、64-bitオフセットを上位32-bitと下位32-bitに分割して引数として受け取ります。このアセンブリコードは、Goの`int64`型の`offset`を、`offset-high`（`CX`レジスタ）と`offset-low`（`DX`レジスタ）に適切に分割してシステムコールに渡しています。
    *   戻り値の`newoffset`も64-bitであるため、`llseek`は通常、結果をメモリ上のポインタ（`SI`レジスタで渡される`result`）に書き込みます。アセンブリコードは、このポインタをスタック上の適切な位置に設定し、システムコールが結果を直接書き込めるようにしています。これにより、Goのランタイムが余分なメモリ割り当て（ヒープアロケーション）を行うことなく、64-bitの戻り値を効率的に取得できます。
    *   エラー処理も`CMPL AX, $0xfffff001`でシステムコールのエラーを示す負の値をチェックし、エラーがあれば`errno`を設定しています。

*   **`mksyscall`の`int64`戻り値処理**:
    *   この変更は、`mksyscall`が生成するGoのラッパー関数が、システムコールから返される64-bit値を正しく再構築できるようにします。多くの32-bit ABI（Application Binary Interface）では、64-bitの戻り値は2つの32-bitレジスタ（例: `EAX`と`EDX`）に分割されて返されます。このスクリプトのロジックは、これらのレジスタの内容をシフト演算とビットOR演算（`int64(r%d)<<32 | int64(r%d)`）を使って結合し、Goの`int64`型として正確な値を生成します。これにより、`Seek`のような関数が`llseek`から返される64-bitオフセットを正しく解釈できるようになります。

*   **Linux/386固有の`//sys`定義 (`syscall_linux_386.go`)**:
    *   `syscall_linux.go`から多くの汎用的な`//sys`定義が削除され、`syscall_linux_386.go`に386アーキテクチャに特化した定義が追加されました。これは、Linux/386が他のアーキテクチャ（特にAMD64）とは異なるシステムコール番号やデータ型を使用する場合があるためです。
    *   例えば、`Stat`が`SYS_STAT64`に、`Chown`が`SYS_CHOWN32`にマッピングされています。`SYS_STAT64`は64-bitファイルオフセットを扱う`stat`のバージョンであり、`SYS_CHOWN32`は32-bit UID/GIDを扱う`chown`のバージョンです。これにより、Goプログラムが32-bit Linux上でファイルシステムやユーザー管理機能を呼び出す際に、OSが期待する正確なシステムコールが使用されることが保証されます。

*   **`types_linux.c`のプリプロセッサマクロ**:
    *   `_LARGEFILE_SOURCE`, `_LARGEFILE64_SOURCE`, `_FILE_OFFSET_BITS 64`, `_GNU_SOURCE`の定義は、Goの`syscall`パッケージがCライブラリのヘッダーファイルを解析してGoの型定義を生成する際に、64-bitファイルシステム対応のデータ型（例: `struct stat64`）が使用されるようにします。これにより、`Stat_t`などのGoの構造体が、OSの64-bit対応構造体とメモリレイアウトが一致し、システムコールからの戻り値を正しく解釈できるようになります。

これらの変更は、Goの`syscall`パッケージが異なるOSとアーキテクチャの多様なシステムコール規約にどのように適応しているかを示す良い例です。特に32-bitシステムでの64-bit値の扱いは、低レベルプログラミングにおける一般的な課題であり、このコミットはその解決策をGoの文脈で提供しています。

## 変更の背景

このコミットが行われた背景には、Go言語が初期段階で様々なアーキテクチャとオペレーティングシステムをサポートする上で直面した、システムコールに関する互換性の問題があります。特に32-bitシステム（386アーキテクチャ）では、ファイルサイズやオフセット、ユーザー/グループIDの表現方法が64-bitシステムと異なるため、システムコールを正しく扱うことが困難でした。

具体的な問題点としては以下の点が挙げられます。

1.  **2GBの壁（Large File Supportの欠如）**: 32-bitシステムでは、標準のファイル操作関数（`lseek`, `stat`など）が32-bitのオフセットやサイズを使用するため、2GBを超えるファイルを扱うことができませんでした。これは現代のシステムでは大きな制約となります。
2.  **UID/GIDのサイズ不一致**: Linuxの386アーキテクチャでは、ユーザーID（UID）やグループID（GID）が16-bitで扱われるシステムコールと、32-bitで扱われるシステムコールが混在していました。Goの`syscall`パッケージがこれらを適切に区別して呼び出さないと、予期せぬエラーやセキュリティ上の問題が発生する可能性がありました。
3.  **Darwin/386の動作不良**: Darwin（macOS）の386アーキテクチャにおいて、システムコールが正しく機能せず、Goプログラムが動作しない状態でした。
4.  **Linuxソケットの不具合**: Linux環境でのソケット関連のシステムコールに不具合があり、ネットワークプログラミングに影響を与えていました。

これらの問題を解決し、Goプログラムが32-bitシステムでも安定して動作し、現代的なファイルシステム機能を利用できるようにするために、このコミットが導入されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **システムコール (System Call)**: オペレーティングシステムが提供するサービス（ファイルI/O、メモリ管理、プロセス制御など）をプログラムが利用するためのインターフェースです。Go言語の`syscall`パッケージは、これらのシステムコールをGoプログラムから直接呼び出すための機能を提供します。
2.  **32-bit vs 64-bit アーキテクチャ**:
    *   **32-bit (x86/i386)**: レジスタやメモリアドレスが32-bit幅で、扱えるメモリ空間は最大4GBです。ファイルオフセットやサイズも通常32-bitで表現されるため、2GBを超えるファイルを直接扱うことができません。
    *   **64-bit (x86-64/AMD64)**: レジスタやメモリアドレスが64-bit幅で、より広大なメモリ空間を扱えます。ファイルオフセットやサイズも64-bitで表現されるため、大容量ファイルを問題なく扱えます。
3.  **Large File Support (LFS)**: 32-bitシステムで2GBを超えるファイルを扱うための仕組みです。これには、`lseek`の代わりに`llseek`（long long seek）を使用したり、`stat`構造体の代わりに`stat64`構造体を使用したりするなど、64-bit対応のシステムコールやデータ型を使用することが含まれます。通常、C言語では`_FILE_OFFSET_BITS=64`などのプリプロセッサマクロを定義することで有効化されます。
4.  **`llseek`システムコール**: 32-bit Linuxシステムにおいて、64-bitのファイルオフセットを扱うために導入されたシステムコールです。通常の`lseek`が32-bitオフセットしか受け付けないのに対し、`llseek`はオフセットを上位32-bitと下位32-bitに分割して引数として受け取り、64-bitの新しいオフセットを返します。
5.  **UID/GID (User ID / Group ID)**: Unix系システムでユーザーやグループを識別するための数値です。歴史的に16-bitで扱われることが多かったですが、現代のシステムでは32-bitが一般的です。Linuxでは、16-bit UID/GIDを扱うシステムコール（例: `chown`）と、32-bit UID/GIDを扱うシステムコール（例: `chown32`）が存在します。
6.  **`mksyscall`ツール**: Go言語の`syscall`パッケージで、`//sys`コメントでマークされたGo関数定義から、対応するアセンブリコードやGoのラッパーコード（`zsyscall_*.go`ファイル）を自動生成するためのツールです。これにより、各OS/アーキテクチャ固有のシステムコール呼び出し規約に合わせたコードを効率的に生成できます。

## 技術的詳細

このコミットの技術的詳細は、主に32-bitアーキテクチャにおけるシステムコール呼び出しの正確性と互換性の向上に焦点を当てています。

1.  **64-bitファイルシステムコールの導入**:
    *   **`llseek`の利用**: 32-bit LinuxおよびDarwin/386において、ファイルオフセットを扱う`Seek`関数が、64-bitオフセットをサポートする`llseek`システムコール（Linuxでは`SYS__LLSEEK`、Darwinでは`SYS_LSEEK`）を使用するように変更されました。
    *   **アセンブリでの実装**: `syscall/asm_linux_386.s`に`syscall·Seek`というアセンブリ関数が追加されました。これは、`llseek`システムコールが64-bitのオフセットを引数として受け取り、64-bitの戻り値を返す際に、32-bitレジスタを組み合わせて処理する必要があるためです。具体的には、オフセットを`offset-high`と`offset-low`に分割して渡し、戻り値も`r0`と`r1`レジスタから64-bit値として再構築します。これにより、Goのランタイムがヒープアロケーションを発生させずに64-bitオフセットを扱えるようになります。
    *   **`mksyscall`の拡張**: `src/pkg/syscall/mksyscall`スクリプトに、32-bit環境で`int64`の戻り値を正しく処理するためのロジックが追加されました。これは、システムコールが2つの32-bitレジスタ（例: `r0`と`r1`）に64-bit値を分割して返す場合に、それらを結合してGoの`int64`型に変換するためのものです。
    *   **`_LARGEFILE_SOURCE`などの定義**: `src/pkg/syscall/types_linux.c`に`_LARGEFILE_SOURCE`, `_LARGEFILE64_SOURCE`, `_FILE_OFFSET_BITS 64`, `_GNU_SOURCE`といったプリプロセッサマクロが追加されました。これらは、Cライブラリが提供するファイルI/O関数が、デフォルトの32-bitではなく64-bitのファイルオフセットを使用するようにコンパイラに指示するための標準的な方法です。これにより、`stat`や`statfs`などの構造体が64-bit対応の`stat64`や`statfs64`にマッピングされ、大容量ファイルを正しく扱えるようになります。
    *   **`Stat_t`, `Statfs_t`, `Dirent`構造体の更新**: `src/pkg/syscall/ztypes_linux_386.go`において、ファイルサイズ、ブロック数、inode番号、ファイルオフセットなどのフィールドが`int32`や`uint32`から`int64`や`uint64`に変更され、64-bitファイルシステムに対応しました。

2.  **32-bit UID/GIDシステムコールの利用**:
    *   **Linux/386固有のsyscall定義**: `src/pkg/syscall/syscall_linux_386.go`に、`Chown`, `Fchown`, `Getegid`, `Geteuid`, `Getgid`, `Getuid`, `Lchown`, `Setfsgid`, `Setfsuid`, `Setgid`, `Setregid`, `Setresgid`, `Setresuid`, `Setreuid`, `getgroups`, `setgroups`といったUID/GID関連のシステムコールに対して、明示的に32-bit対応のシステムコール番号（例: `SYS_CHOWN32`, `SYS_GETEGID32`）を割り当てる`//sys`ディレクティブが追加されました。これにより、32-bit Linux環境でUID/GIDが正しく扱われるようになります。
    *   **`mksyscall -l32`**: `src/pkg/syscall/PORT`ファイルで、`linux_386`ターゲットに対して`mksyscall`ツールを`-l32`オプション付きで実行するように設定が変更されました。このオプションは、`mksyscall`が32-bit環境向けのシステムコールラッパーを生成する際に、特定の最適化や規約を適用することを示唆しています。

3.  **Linuxソケットの修正**:
    *   `src/pkg/syscall/asm_linux_386.s`内の`socketcall`アセンブリ関数において、戻り値とエラーコードをスタックに格納するオフセットが調整されました。これは、システムコール呼び出し規約の微妙な違いや、スタックフレームのレイアウト変更に対応するための修正と考えられます。

これらの変更により、Goの`syscall`パッケージは、32-bitアーキテクチャのLinuxおよびDarwin環境で、より堅牢かつ正確にシステムコールを扱えるようになりました。特に、大容量ファイルのサポートは、Goがより幅広いアプリケーションで利用される上で不可欠な機能です。

## コアとなるコードの解説

これらの変更は、Goの`syscall`パッケージが32-bitシステム上でOSの低レベルな機能とどのように連携するかを根本的に改善しています。

*   **`mksyscall -l32`の導入**: `PORT`ファイルでのこの変更は、`mksyscall`ツールがLinux/386向けにシステムコールラッパーを生成する際に、32-bit環境特有の考慮事項（例えば、レジスタの使用方法やデータ型のサイズ）を適用するように指示します。これにより、生成される`zsyscall_linux_386.go`ファイルがより正確なシステムコール呼び出しコードを含むようになります。

*   **`Seek`関数のアセンブリ実装 (`asm_linux_386.s`)**:
    *   32-bitシステムでは、64-bitの数値を単一のレジスタで扱うことができません。`llseek`システムコールは、64-bitオフセットを上位32-bitと下位32-bitに分割して引数として受け取ります。このアセンブリコードは、Goの`int64`型の`offset`を、`offset-high`（`CX`レジスタ）と`offset-low`（`DX`レジスタ）に適切に分割してシステムコールに渡しています。
    *   戻り値の`newoffset`も64-bitであるため、`llseek`は通常、結果をメモリ上のポインタ（`SI`レジスタで渡される`result`）に書き込みます。アセンブリコードは、このポインタをスタック上の適切な位置に設定し、システムコールが結果を直接書き込めるようにしています。これにより、Goのランタイムが余分なメモリ割り当て（ヒープアロケーション）を行うことなく、64-bitの戻り値を効率的に取得できます。
    *   エラー処理も`CMPL AX, $0xfffff001`でシステムコールのエラーを示す負の値をチェックし、エラーがあれば`errno`を設定しています。

*   **`mksyscall`の`int64`戻り値処理**:
    *   この変更は、`mksyscall`が生成するGoのラッパー関数が、システムコールから返される64-bit値を正しく再構築できるようにします。多くの32-bit ABI（Application Binary Interface）では、64-bitの戻り値は2つの32-bitレジスタ（例: `EAX`と`EDX`）に分割されて返されます。このスクリプトのロジックは、これらのレジスタの内容をシフト演算とビットOR演算（`int64(r%d)<<32 | int64(r%d)`）を使って結合し、Goの`int64`型として正確な値を生成します。これにより、`Seek`のような関数が`llseek`から返される64-bitオフセットを正しく解釈できるようになります。

*   **Linux/386固有の`//sys`定義 (`syscall_linux_386.go`)**:
    *   `syscall_linux.go`から多くの汎用的な`//sys`定義が削除され、`syscall_linux_386.go`に386アーキテクチャに特化した定義が追加されました。これは、Linux/386が他のアーキテクチャ（特にAMD64）とは異なるシステムコール番号やデータ型を使用する場合があるためです。
    *   例えば、`Stat`が`SYS_STAT64`に、`Chown`が`SYS_CHOWN32`にマッピングされています。`SYS_STAT64`は64-bitファイルオフセットを扱う`stat`のバージョンであり、`SYS_CHOWN32`は32-bit UID/GIDを扱う`chown`のバージョンです。これにより、Goプログラムが32-bit Linux上でファイルシステムやユーザー管理機能を呼び出す際に、OSが期待する正確なシステムコールが使用されることが保証されます。

*   **`types_linux.c`のプリプロセッサマクロ**:
    *   `_LARGEFILE_SOURCE`, `_LARGEFILE64_SOURCE`, `_FILE_OFFSET_BITS 64`, `_GNU_SOURCE`の定義は、Goの`syscall`パッケージがCライブラリのヘッダーファイルを解析してGoの型定義を生成する際に、64-bitファイルシステム対応のデータ型（例: `struct stat64`）が使用されるようにします。これにより、`Stat_t`などのGoの構造体が、OSの64-bit対応構造体とメモリレイアウトが一致し、システムコールからの戻り値を正しく解釈できるようになります。

これらの変更は、Goの`syscall`パッケージが異なるOSとアーキテクチャの多様なシステムコール規約にどのように適応しているかを示す良い例です。特に32-bitシステムでの64-bit値の扱いは、低レベルプログラミングにおける一般的な課題であり、このコミットはその解決策をGoの文脈で提供しています。

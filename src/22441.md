# [インデックス 22441] ファイルの概要

このコミットは、Go言語のリンカにARM64アーキテクチャのサポートを追加するものです。具体的には、`cmd/7l`（元々は`amd64`リンカ）をARM64リンカとして機能させるための変更と、リンカの内部パッケージである`cmd/internal/ld`にARM64固有のロジックを組み込む作業が含まれています。これにより、GoプログラムをARM64環境向けにビルドできるようになります。

## 変更の背景

Go言語は、その強力なクロスコンパイル機能と、生成されるバイナリのポータビリティによって広く利用されています。当時、ARM64（AArch64）アーキテクチャはモバイルデバイスやサーバー分野で台頭しつつあり、Goプログラムをこれらの新しい環境でネイティブに実行できることの重要性が増していました。

このコミット以前は、GoリンカはARM64を直接サポートしていませんでした。Goのリンカは、他の多くの言語がシステムリンカ（例: `ld`）に依存するのとは異なり、独自のカスタムリンカをGoツールチェインの一部として持っています。このカスタムリンカは、Go独自のオブジェクトファイル形式とランタイムデータ構造を扱うように設計されており、標準のELFやPEリンカから独立しています。

この変更の背景には、GoがARM64を公式にサポートし、GoプログラムがARM64ベースのシステムで効率的に動作できるようにするという目標がありました。特に、`cmd/7l`は歴史的に`amd64`アーキテクチャ用のリンカでしたが、Goツールチェインの進化に伴い、より汎用的な`cmd/link/internal/ld`パッケージにリンカのコアロジックが統合されていました。このコミットは、`cmd/7l`をARM64リンカとして再利用し、必要なアーキテクチャ固有の調整を`cmd/internal/ld`に加えることで、ARM64サポートを実現しています。

コミットメッセージにある「Only internal linking without cgo is supported for now.」という記述は、初期段階ではGoの内部リンカのみがARM64をサポートし、C言語との相互運用（cgo）を伴う動的リンクはまだサポートされていないことを示しています。これは、段階的な機能追加のアプローチを示唆しています。

## 前提知識の解説

### Go言語のリンカ

Go言語は、独自の内部リンカを使用します。これは、コンパイルされたGoのオブジェクトファイルと依存関係を単一の実行可能バイナリに結合する役割を担います。Goリンカの主な特徴は以下の通りです。

*   **カスタムオブジェクト形式**: GoはELFのような標準形式ではなく、独自のオブジェクトファイル形式を使用します。これにより、コンパイラ、オブジェクト形式、リンカ間の共同設計が最適化されます。
*   **静的リンク**: Goはデフォルトで静的リンクを強く推奨しており、必要なすべてのライブラリとGoランタイムを最終的な実行可能ファイルに直接埋め込みます。これにより、外部依存関係のない高いポータビリティを持つバイナリが生成されます。
*   **シンボルレベルの到達可能性解析**: リンカはシンボルレベルで到達可能性解析を行い、プログラムによって実際に使用される関数とデータのみを含めます。これにより、バイナリサイズが削減されます。
*   **リロケーション**: コンパイルされたコードには、最終的なメモリアドレスが不明なシンボルへの参照が含まれることがあります。リンカはこれらのリロケーションを解決し、最終的なバイナリイメージ内のすべてのシンボルにアドレスを割り当てます。

### ARM64 (AArch64) アーキテクチャ

ARM64は、ARMv8-Aアーキテクチャに基づく64ビット命令セットアーキテクチャです。RISC（Reduced Instruction Set Computer）設計であり、固定長の32ビット命令を使用します。

*   **PC相対アドレッシング**: ARM64の命令は、プログラムカウンタ（PC）からの相対オフセットを使用してアドレスを指定することがよくあります。
*   **分岐命令の制限**: `BL`（Branch with Link）のような関数呼び出しに使用される分岐命令は、PCからの相対オフセットに制限があります（通常±128MB）。この制限を超える呼び出しには、「トランポリン」（veneer）と呼ばれる小さな中間コードが必要になる場合があります。

### ELF (Executable and Linkable Format)

ELFは、Unix系システムで広く使用されている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準ファイル形式です。リンカはELF形式のバイナリを生成する際に、以下の要素を扱います。

*   **ELFヘッダ**: ファイルの種類、アーキテクチャ、エントリポイントなどの情報を含みます。
*   **プログラムヘッダ**: 実行時にメモリにロードされるセグメント（コード、データなど）を記述します。
*   **セクションヘッダ**: リンク時に使用されるファイル内のセクション（`.text`, `.data`, `.symtab`など）を記述します。
*   **リロケーションエントリ**: リンカがアドレスを解決するために必要な情報（オフセット、タイプ、シンボル）を含みます。

### DWARF (Debugging With Attributed Record Formats)

DWARFは、コンパイラとデバッガによって使用される標準化されたデバッグデータ形式です。プログラムのソースコード、データ型、変数、実行フローの詳細な記述を提供し、デバッガが人間が読める形式で情報を表示できるようにします。

*   **DWARFレジスタ番号**: DWARFは、特定のCPUアーキテクチャに依存しない抽象的なレジスタ番号のセットを定義します。コンパイラは、特定のアーキテクチャの物理レジスタ（例: ARM64の`SP`）をこれらの標準化されたDWARFレジスタ番号にマッピングします。

### ELFサポートの拡張

`src/cmd/internal/ld/elf.go`では、ELFヘッダの`e_machine`フィールドに新しいARM64用の値`EM_AARCH64`（183）が追加されました。また、ARM64固有のリロケーションタイプである`R_AARCH64_ABS64`、`R_AARCH64_ABS32`、`R_AARCH64_CALL26`が定義されています。

*   **`EM_AARCH64`**: ARM64アーキテクチャを示すELFマシンタイプ。
*   **`R_AARCH64_ABS64`**: 64ビットの絶対アドレスをパッチするために使用されます。シンボルのアドレスと加算値を合わせた最終的な64ビットアドレスを、リロケーションサイトに直接書き込みます。
*   **`R_AARCH64_ABS32`**: 32ビットの絶対アドレスをパッチするために使用されます。`R_AARCH64_ABS64`と同様ですが、32ビットフィールドに収まるかどうかのオーバーフローチェックが行われます。
*   **`R_AARCH64_CALL26`**: ARM64の`B`（分岐）および`BL`（リンク付き分岐）命令による直接関数呼び出しを解決するために特化しています。これらの命令はPC相対オフセットをエンコードし、その範囲は±128MBに制限されます。リンカは、この範囲を超えるターゲットに対しては「トランポリン」を挿入して対応します。

`elf.go`内の`Elfinit`、`elfdynhash`、`doelf`、`Asmbelf`などの関数が、`Thearch.Thechar`が`'7'`（ARM64）の場合に適切にELF構造を処理するように変更されています。これにより、ARM64バイナリがELF標準に準拠して生成されるようになります。

## コアとなるコードの解説

### `src/cmd/7l/l.go`における`thechar`と`DWARFREGSP`の変更

```go
// src/cmd/7l/l.go
const (
	thechar   = '7' // Changed from '9'
	PtrSize   = 8
	IntSize   = 8
	RegSize   = 8
)

/* Used by ../ld/dwarf.c */
const (
	DWARFREGSP = 31 // Changed from 1
)
```
*   `thechar = '7'`: Goリンカの内部では、各アーキテクチャに一意の文字が割り当てられています。この変更により、`'7'`がARM64アーキテクチャを識別するための文字として確立されました。
*   `DWARFREGSP = 31`: DWARFはデバッグ情報のための標準形式であり、レジスタには特定の番号が割り当てられています。ARM64アーキテクチャでは、スタックポインタ（SP）は通常`x31`レジスタに対応し、そのDWARFレジスタ番号は31です。この変更は、Goが生成するデバッグ情報がARM64の慣例に沿うようにするためのものです。

### `src/cmd/7l/obj.go`における`linkarchinit`の変更

```go
// src/cmd/7l/obj.go

	ld.Thestring = obj.Getgoarch()
	ld.Thelinkarch = &ld.Linkarm64 // Previously conditional on ppc64le/ppc64
	// ...
	ld.Thearch.Lput = ld.Lputl
	ld.Thearch.Wput = ld.Wputl
	ld.Thearch.Vput = ld.Vputl // Previously conditional on ppc64le/ppc64
	// ...
	ld.Thearch.Linuxdynld = "/lib/ld-linux-aarch64.so.1" // Changed from "/lib64/ld64.so.1"

```
*   `ld.Thelinkarch = &ld.Linkarm64`: これは、`cmd/7l`がPPC64ではなくARM64のリンカとして動作するように設定する最も重要な変更点です。これにより、リンカはARM64固有のアーキテクチャ特性（バイトオーダー、ポインタサイズなど）を使用するようになります。
*   `ld.Thearch.Lput = ld.Lputl`, `ld.Thearch.Wput = ld.Wputl`, `ld.Thearch.Vput = ld.Vputl`: これらの行は、リンカがリトルエンディアン形式でデータを書き込むことを保証します。ARM64は通常リトルエンディアンを使用するため、これは適切な設定です。以前はPPC64のエンディアンに依存していました。
*   `ld.Thearch.Linuxdynld = "/lib/ld-linux-aarch64.so.1"`: LinuxシステムにおけるARM64の標準的な動的リンカのパスを指定します。これにより、Goバイナリが動的リンクを必要とする場合に、正しいリンカが使用されるようになります。

    *   `Minlc: 4`: 最小命令長（バイト単位）。ARM64命令は固定長の4バイトです。
    *   `Ptrsize: 8`: ポインタサイズ（バイト単位）。64ビットアーキテクチャなので8バイトです。
    *   `Regsize: 8`: レジスタサイズ（バイト単位）。64ビットアーキテクチャなので8バイトです。

### `src/cmd/internal/ld/elf.go`におけるELF定数とリロケーションタイプの追加

```go
// src/cmd/internal/ld/elf.go
const (
	// ...
	EM_AARCH64           = 183
	// ...
	R_AARCH64_ABS64        = 257
	R_AARCH64_ABS32        = 258
	R_AARCH64_CALL26       = 283
	// ...
)
```
*   `EM_AARCH64 = 183`: ELFファイルヘッダの`e_machine`フィールドで使用される、ARM64アーキテクチャを示すマジックナンバーです。
*   `R_AARCH64_ABS64`, `R_AARCH64_ABS32`, `R_AARCH64_CALL26`: これらはARM64固有のELFリロケーションタイプです。
    *   `R_AARCH64_ABS64`: 64ビットの絶対アドレスを解決します。
    *   `R_AARCH64_ABS32`: 32ビットの絶対アドレスを解決します。
    *   `R_AARCH64_CALL26`: ARM64の`BL`命令（26ビットのPC相対オフセットを持つ）のターゲットアドレスを解決します。このリロケーションは、ターゲットが遠すぎる場合にトランポリンを挿入するリンカの能力と密接に関連しています。

```go

	// ...
	R_CALLARM64
```

*   `R_CALLARM64`: Goリンカ内部で、ARM64アーキテクチャの関数呼び出しリロケーションを識別するためのGo固有のリロケーションタイプです。これは、コンパイラが生成したコード内の関数呼び出し命令が、リンカによって最終的なアドレスにパッチされる必要があることを示します。

これらの変更は、GoリンカがARM64のバイナリを正しく生成し、ARM64の命令セットとABI（Application Binary Interface）に準拠した実行可能ファイルを作成するための基盤を構築しています。特に、リロケーション処理の正確な実装は、GoプログラムがARM64システム上で安定して動作するために不可欠です。

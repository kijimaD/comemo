# [インデックス 20053] ファイルの概要

このコミットは、GoランタイムのPOWER64アーキテクチャにおける`morestack`関連のバグを修正するものです。具体的には、スタック拡張処理を行う`runtime·morestack`関数および関連する関数において、Link Register (LR) を不適切に保存しないように変更することで、スタック管理の正確性を確保しています。

## 変更の背景

Go言語のGoroutineは、必要に応じてスタックサイズを動的に拡張するメカニズムを持っています。このスタック拡張は、`runtime·morestack`というランタイム関数によって行われます。しかし、特定のアーキテクチャ（この場合はPOWER64）において、`morestack`関数やそれに類する低レベルな関数が、関数の呼び出し規約に従ってLink Register (LR) をスタックに保存しようとすると問題が発生する可能性がありました。

Link Register (LR) は、関数が呼び出された際に、呼び出し元に戻るためのアドレス（戻りアドレス）を保持するレジスタです。通常の関数呼び出しでは、関数のプロローグ（開始部分）でLRの値をスタックに保存し、エピローグ（終了部分）でスタックから復元して呼び出し元に戻ります。

`morestack`のようなスタック管理の根幹をなす関数は、非常に特殊なコンテキストで実行されます。スタックが不足している状況で呼び出されるため、通常のスタックフレームのセットアップやLRの保存が、スタックの破損や無限ループ、あるいは不正な戻りアドレスへのジャンプを引き起こす可能性がありました。

このコミットは、「LRを保存してはならない」という明確な指示に基づいており、`morestack`がその特殊な性質上、LRの保存を回避する必要があるという認識から行われました。これにより、POWER64アーキテクチャ上でのGoプログラムの安定性と正確なスタック管理が保証されます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびアセンブリ言語に関する知識が必要です。

*   **Go Runtime (Goランタイム)**:
    Goプログラムは、Goランタイムと呼ばれる低レベルなシステムによって実行が管理されます。これには、Goroutineのスケジューリング、ガベージコレクション、メモリ管理、そしてスタック管理などが含まれます。Goランタイムの多くの部分は、パフォーマンスとハードウェアとの直接的な対話のためにアセンブリ言語で書かれています。

*   **Goroutine Stack (Goroutineスタック)**:
    Goの軽量スレッドであるGoroutineは、それぞれが独自のスタックを持っています。このスタックは、関数呼び出しの際に引数、戻り値、ローカル変数、そして戻りアドレスなどを格納するために使用されます。Goのスタックは、必要に応じて動的にサイズが拡張される「可変スタック」であり、これによりメモリ効率が向上します。

*   **`morestack` 関数**:
    Goroutineのスタックが現在のサイズでは不足すると判断された場合（例えば、関数呼び出しによってスタックがオーバーフローしそうになった場合）、Goランタイムは自動的に`runtime·morestack`関数を呼び出します。この関数は、より大きなスタックを割り当て、既存のスタックの内容を新しいスタックにコピーし、実行を新しいスタックに切り替える役割を担います。これはGoのスタック管理の非常に重要な部分です。

*   **Assembly Language (アセンブリ言語)**:
    Goランタイムの特定のクリティカルな部分は、Go言語ではなく、ターゲットアーキテクチャのアセンブリ言語で実装されています。これにより、最大限のパフォーマンスと、レジスタやメモリへの低レベルな制御が可能になります。このコミットで変更されている`asm_power64x.s`ファイルは、POWER64アーキテクチャ向けのアセンブリコードを含んでいます。

*   **Link Register (LR) (リンクレジスタ)**:
    POWER64のような一部のRISCアーキテクチャでは、関数が呼び出される際に、呼び出し元に戻るためのアドレス（Program Counter: PC）がLink Register (LR) に保存されます。関数が終了する際には、このLRの値を使用して呼び出し元に制御が戻されます。通常の関数呼び出し規約では、LRの値をスタックに保存し、関数内で他の関数を呼び出す際にLRが上書きされないように保護します。

*   **Function Prologue / Epilogue (関数プロローグ / エピローグ)**:
    *   **プロローグ**: 関数の実行が開始される直前に実行される一連の命令です。これには、スタックフレームのセットアップ（スタックポインタの調整）、呼び出し元レジスタの保存（LRを含む）、ローカル変数のためのスペース確保などが含まれます。
    *   **エピローグ**: 関数の実行が終了する直前に実行される一連の命令です。これには、プロローグで保存されたレジスタの復元、スタックフレームの解放、そして呼び出し元への戻り（LRの値を使用）などが含まれます。

*   **`TEXT` ディレクティブ (Goアセンブリ)**:
    Goのアセンブリ言語では、`TEXT`ディレクティブを使用して関数を定義します。一般的な形式は `TEXT symbol(SB), flags, args-locals` です。
    *   `symbol(SB)`: 関数のシンボル名。`SB`はStatic Baseを意味し、グローバルシンボルであることを示します。
    *   `flags`: 関数の特性を示すフラグ。
        *   `NOSPLIT`: この関数はスタックの拡張チェックを行わないことを示します。`morestack`のようなスタック管理関数自身や、非常に短いリーフ関数（他の関数を呼び出さない関数）でよく使用されます。
    *   `args-locals`: 引数とローカル変数の合計サイズをバイト単位で指定します。例えば `$0-0` は引数もローカル変数もスタック上にないことを意味します。このコミットで登場する`$-8-0`のような負の値は特殊な意味を持ち、通常は戻りPC（LR）をスタックに保存しないことを示唆します。

## 技術的詳細

このコミットの核心は、`src/pkg/runtime/asm_power64x.s`ファイル内の`TEXT`ディレクティブの変更にあります。具体的には、`runtime·morestack`、`runtime·morestack_noctxt`、および`reflect·call`という3つの関数の定義が変更されています。

変更前:
```assembly
TEXT runtime·morestack(SB),NOSPLIT,$0-0
TEXT runtime·morestack_noctxt(SB),NOSPLIT,$0-0
TEXT reflect·call(SB), NOSPLIT, $0-24
```

変更後:
```assembly
TEXT runtime·morestack(SB),NOSPLIT,$-8-0
TEXT runtime·morestack_noctxt(SB),NOSPLIT,$-8-0
TEXT reflect·call(SB), NOSPLIT, $-8-24
```

この変更のポイントは、`$0-X`から`$-8-X`への変更です。Goのアセンブリにおける`TEXT`ディレクティブの`args-locals`部分で、`args`に負の値を指定することは、その関数が戻りPC（この場合はLink Register: LR）をスタックに保存しないことを明示的にGoツールチェーンに伝えるための慣例です。

POWER64アーキテクチャでは、LRは通常8バイトのレジスタです。通常の関数プロローグでは、このLRの値をスタックにプッシュして保存します。`$0-0`は、引数もローカル変数もスタックにないことを示し、通常はLRの保存も含まれないことを意味します。しかし、`$-8-0`とすることで、Goツールチェーンに対して「この関数は、通常LRを保存するために使われる8バイトのスタック領域を、そのスタックフレームの一部として考慮しない」と指示しています。

これは、`morestack`のような関数が、スタックの拡張という非常にデリケートな操作中に、LRの保存によってスタックポインタが一時的に不整合な状態になったり、スタックの境界チェックと競合したりするのを防ぐために重要です。LRを保存しないことで、これらの関数はより予測可能で安全な方法でスタックを操作できるようになります。

`reflect·call`も同様に変更されているのは、リフレクションによる関数呼び出しもまた、通常の関数呼び出しとは異なるスタック管理の考慮が必要な場合があるためと考えられます。特に、動的な関数呼び出しはスタックフレームのセットアップが複雑になることがあり、LRの不適切な保存が問題を引き起こす可能性がありました。

この修正は、Goランタイムの低レベルなスタック管理の正確性を向上させ、POWER64アーキテクチャ上でのGoプログラムの堅牢性を高めるものです。

## コアとなるコードの変更箇所

変更は、GoランタイムのPOWER64アーキテクチャ向けアセンブリコードファイルである`src/pkg/runtime/asm_power64x.s`に集中しています。

具体的には、以下の3つの関数の`TEXT`ディレクティブが変更されました。

*   `runtime·morestack`
*   `runtime·morestack_noctxt`
*   `reflect·call`

変更内容は、各`TEXT`ディレクティブの`args-locals`部分が`$0-X`から`$-8-X`に変更された点です。

## コアとなるコードの解説

このコミットの最も重要な変更は、Goアセンブリの`TEXT`ディレクティブにおける`args-locals`パラメータの調整です。

*   **`TEXT runtime·morestack(SB),NOSPLIT,$0-0` から `TEXT runtime·morestack(SB),NOSPLIT,$-8-0` へ**:
    *   元の`$0-0`は、この関数がスタック上に引数もローカル変数も持たないことを示していました。しかし、POWER64アーキテクチャの通常の関数呼び出し規約では、戻りアドレス（LR）をスタックに保存するために8バイトが使用されます。
    *   新しい`$-8-0`という表記は、Goアセンブラに対して「この関数は、戻りPC（LR）をスタックに保存しない」という特別な指示を与えます。負の値は、スタックフレームのサイズ計算において、通常戻りPCのために予約される8バイトを考慮しないことを意味します。
    *   これにより、`morestack`関数が実行される際に、LRの不必要な保存が回避されます。これは、`morestack`がスタックの拡張という非常に低レベルでクリティカルな操作を行うため、スタックポインタの状態が通常の関数呼び出しとは異なる可能性があり、LRの保存が予期せぬ副作用（スタックの破損や無限ループなど）を引き起こすのを防ぐために不可欠です。

*   **`runtime·morestack_noctxt` と `reflect·call` も同様に修正**:
    *   `runtime·morestack_noctxt`は、コンテキスト情報なしで`morestack`を呼び出すためのラッパーのような関数であり、`morestack`と同様のスタック管理の考慮が必要です。
    *   `reflect·call`は、リフレクションメカニズムを通じて関数を動的に呼び出すためのランタイム関数です。動的な関数呼び出しは、通常のコンパイル時に関数が決定される呼び出しとは異なり、スタックフレームのセットアップやレジスタの扱いにおいて特別な注意が必要となる場合があります。ここでもLRの不適切な保存が問題を引き起こす可能性があったため、同様の修正が適用されました。

この変更は、GoランタイムがPOWER64アーキテクチャ上で、スタックの拡張や動的な関数呼び出しといった低レベルな操作を、より正確かつ安全に実行できるようにするための、非常に重要なアセンブリレベルの修正です。

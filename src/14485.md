## 変更の背景

このコミットの主な背景は、Go言語の`net`パッケージにおけるデッドライン（`SetDeadline`, `SetReadDeadline`, `SetWriteDeadline`）の設定に関する潜在的なデータ競合の問題を特定し、再現することにあります。デッドラインは、ネットワーク操作が完了するまでの最大時間を設定するために使用され、タイムアウト処理に不可欠です。しかし、複数のゴルーチンが同時に同じネットワーク接続のデッドラインを変更しようとすると、内部の状態変数が適切に保護されていない場合にデータ競合が発生する可能性があります。

コミットメッセージに「Currently the test exposes data races on deadline vars.」と明記されているように、このテストは既存のデータ競合を意図的に引き起こすように設計されています。これは、問題の存在を証明し、将来的にその問題を修正するための基盤を築くための重要なステップです。データ競合は、プログラムの予測不能な動作、クラッシュ、またはセキュリティ脆弱性につながる可能性があるため、早期に特定し修正することが非常に重要です。

## 前提知識の解説

*   **Go言語の`net`パッケージ**: Go言語の標準ライブラリの一部で、TCP/IP、UDP、Unixドメインソケットなどのネットワークプログラミング機能を提供します。クライアントとサーバーアプリケーションの構築に広く使用されます。
*   **`net.Conn`インターフェース**: ネットワーク接続を表すインターフェースで、`Read`、`Write`、`Close`などの基本的なI/O操作に加え、`SetDeadline`、`SetReadDeadline`、`SetWriteDeadline`といったデッドライン設定メソッドを提供します。
*   **デッドライン（Deadline）**: ネットワーク操作（読み取りまたは書き込み）が完了するまでの最大時間を設定する機能です。指定された時間内に操作が完了しない場合、エラー（通常はタイムアウトエラー）が返されます。これにより、ネットワークの遅延や相手側の無応答によってプログラムがブロックされ続けることを防ぎます。
*   **`SetDeadline(t time.Time)`**: 読み取りと書き込みの両方のデッドラインを同時に設定します。`t`は操作が完了しなければならない絶対時刻です。
*   **ゴルーチン（Goroutine）**: Go言語における軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数千、数万のゴルーチンを同時に実行することが可能です。`go`キーワードを使って関数呼び出しの前に置くことで、新しいゴルーチンでその関数を実行できます。
*   **データ競合（Data Race）**: 複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に発生する競合状態です。データ競合は、プログラムの動作を非決定的にし、デバッグを困難にします。Go言語にはデータ競合を検出するための「Race Detector」ツールが組み込まれています。
*   **`go test`**: Go言語のテストフレームワークを実行するためのコマンドです。テストファイル（`_test.go`で終わるファイル）内のテスト関数（`Test`で始まる関数）を実行します。`go test -race`オプションを使用すると、テスト実行中にデータ競合を検出できます。
*   **`time.Now().Add(time.Hour)`**: 現在時刻に1時間を加算した`time.Time`オブジェクトを生成します。これはデッドラインを将来の時刻に設定するためによく使われます。
*   **`runtime.GOOS`**: Goプログラムが実行されているオペレーティングシステムを示す文字列です（例: "linux", "windows", "darwin", "plan9"）。このコミットでは、`plan9`上でのテストをスキップするために使用されています。

## 技術的詳細

このコミットで追加された`TestProlongTimeout`テストは、`net.Conn`のデッドライン設定におけるデータ競合を意図的に引き起こすように設計されています。テストの核心は、単一のネットワーク接続に対して、複数のゴルーチンが同時に`SetDeadline`を呼び出す状況を作り出すことです。

テストのシナリオは以下の通りです。

1.  **リスナーのセットアップ**: `newLocalListener(t)`を使ってTCPリスナーを作成します。これはサーバー側の接続待ち受け点となります。
2.  **アクセプターゴルーチン**:
    *   リスナーが接続を受け入れると（`ln.Accept()`）、新しいゴルーチンが起動されます。
    *   受け入れられた接続`s`に対して、まず初期のデッドラインが設定されます（`s.SetDeadline(time.Now().Add(time.Hour))`）。
    *   **書き込みゴルーチン**: 別のゴルーチンが起動され、接続`s`に対して継続的にデータを書き込みます（`s.Write(buf[:])`）。**この書き込みループ内で、書き込みが成功するたびに`s.SetDeadline(time.Now().Add(time.Hour))`が再度呼び出されます。**
    *   **読み取りループ**: メインのアクセプターゴルーチンは、接続`s`から継続的にデータを読み取ります（`s.Read(buf)`）。**この読み取りループ内で、読み取りが成功するたびに`s.SetDeadline(time.Now().Add(time.Hour))`が再度呼び出されます。**
    *   これにより、読み取りと書き込みの操作が同時に行われ、それぞれが独立してデッドラインを「延長」しようとします。
3.  **クライアントのセットアップ**:
    *   テストのメインゴルーチンは、リスナーに接続するクライアント接続`c`を作成します（`Dial("tcp", ln.Addr().String())`）。
    *   クライアントは、サーバーに少量のデータ（1バイト）を繰り返し書き込みます（`c.Write(buf[:])`）。この書き込みは、サーバー側の読み取りループを駆動し、結果としてサーバー側の`SetDeadline`呼び出しをトリガーします。

この設計により、サーバー側の単一の`net.Conn`インスタンスに対して、少なくとも2つの異なるゴルーチン（書き込みゴルーチンと読み取りループ）が同時に`SetDeadline`を呼び出す状況が生まれます。もし`net.Conn`の内部でデッドラインを管理する変数がミューテックスなどの適切な同期プリミティブで保護されていない場合、これらの同時アクセスはデータ競合を引き起こします。

コミットメッセージにある「Currently the test exposes data races on deadline vars.」という記述は、このテストが書かれた時点では、実際にGoの`net`パッケージの内部実装にこのデータ競合が存在していたことを示唆しています。このテストの目的は、その問題を再現可能にし、`go test -race`コマンドで検出できるようにすることでした。

## コアとなるコードの解説

追加された`TestProlongTimeout`関数は、以下の主要な部分で構成されています。

1.  **OSによるスキップ**:
    ```go
    switch runtime.GOOS {
    case "plan9":
    	t.Logf("skipping test on %q", runtime.GOOS)
    	return
    }
    ```
    この部分は、テストがPlan 9オペレーティングシステム上では実行されないようにします。これは、特定のOS環境でのネットワークスタックの動作の違いや、テストの再現性の問題によるものと考えられます。

2.  **リスナーとアクセプターゴルーチン**:
    ```go
    ln := newLocalListener(t)
    defer ln.Close()
    go func() {
    	s, err := ln.Accept()
    	if err != nil {
    		t.Fatalf("ln.Accept: %v", err)
    	}
    	defer s.Close()
    	s.SetDeadline(time.Now().Add(time.Hour)) // Initial deadline
    	// ... (nested goroutines for write and read)
    }()
    ```
    `newLocalListener(t)`はテスト用のローカルTCPリスナーを作成します。`defer ln.Close()`でテスト終了時にリスナーが確実に閉じられるようにします。
    `go func() { ... }()`で新しいゴルーチンを起動し、この中でクライアントからの接続を待ち受けます（`ln.Accept()`）。接続`s`が確立されたら、まず初期のデッドラインを1時間後に設定します。

3.  **同時デッドライン延長のトリガー**:
    アクセプターゴルーチンの中に、さらに2つの並行処理が組み込まれています。

    *   **書き込みゴルーチン**:
        ```go
        go func() {
        	var buf [4096]byte
        	for {
        		_, err := s.Write(buf[:])
        		if err != nil {
        			break
        		}
        		s.SetDeadline(time.Now().Add(time.Hour)) // Prolong deadline on write
        	}
        }()
        ```
        このゴルーチンは、受け入れられた接続`s`に対して継続的にデータを書き込みます。重要なのは、**書き込み操作が成功するたびに`s.SetDeadline`を呼び出し、デッドラインを延長している点**です。これにより、書き込み処理が続く限り、デッドラインが常に未来に設定され続けます。

    *   **読み取りループ**:
        ```go
        buf := make([]byte, 1)
        for {
        	_, err := s.Read(buf)
        	if err != nil {
        		break
        	}
        	s.SetDeadline(time.Now().Add(time.Hour)) // Prolong deadline on read
        }
        ```
        アクセプターゴルーチンのメインループは、接続`s`からデータを読み取ります。こちらも、**読み取り操作が成功するたびに`s.SetDeadline`を呼び出し、デッドラインを延長しています**。

    この2つの並行する処理（書き込みゴルーチンと読み取りループ）が、同じ`net.Conn`インスタンス`s`に対して同時に`SetDeadline`を呼び出すことで、データ競合の条件を作り出します。

4.  **クライアントの接続とデータ送信**:
    ```go
    c, err := Dial("tcp", ln.Addr().String())
    if err != nil {
    	t.Fatalf("DialTCP: %v", err)
    }
    defer c.Close()
    for i := 0; i < 1024; i++ {
    	var buf [1]byte
    	c.Write(buf[:])
    }
    ```
    テストのメインゴルーチンは、サーバーのリスナーアドレスに接続するクライアント`c`を作成します。その後、クライアントは1024回にわたって1バイトのデータをサーバーに書き込みます。このクライアントからの書き込みが、サーバー側の読み取りループを駆動し、結果としてサーバー側の`SetDeadline`呼び出しを頻繁にトリガーします。

このテストの目的は、`go test -race`コマンドで実行されたときに、`net.Conn`の内部でデッドラインを管理する変数に対する非同期アクセスによって発生するデータ競合を検出することです。このテストが追加されたことで、Go開発者はこの問題の存在を認識し、将来のバージョンで修正するための手がかりを得ることができました。

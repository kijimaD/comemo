# [インデックス 24030] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) における外部リンキング (`-linkmode=external`) とシンボル情報の除去 (`-s` フラグ) の組み合わせに関するバグ修正を扱っています。特に、ELF形式以外のOS（WindowsやmacOS）でこの組み合わせが正しく機能しない問題を解決することを目的としています。

## 元コミット内容

`cmd/link: fix -s with external linking`

このコードは以前、ELF形式の実行ファイルに対してのみ実行されていました。その結果、外部リンキングを使用する際に `-s` フラグを使うと、WindowsおよびOS Xで問題が発生していました。この変更によってコードを移動することで、Windowsでの問題が修正され、OS Xでの問題も修正されます。

CL 10835もWindowsでのクラッシュを修正すると主張していますが、それが正しく行われているかは不明です。しかし、このCL（変更リスト）によって、CL 10835は実質的に何もしなくなるはずです。

Fixes #10254.

## 変更の背景

Go言語のリンカ (`cmd/link`) は、Goプログラムをコンパイルして実行可能ファイルを生成する際に重要な役割を果たします。通常、Goリンカは独自の内部リンカを使用して実行ファイルを生成しますが、C言語のコードと連携する `cgo` を使用する場合や、特定のシステムリンカの機能が必要な場合には、外部リンカ (`-linkmode=external`) を使用することがあります。

`-s` フラグは、生成される実行ファイルからシンボルテーブルやデバッグ情報を除去するために使用されます。これにより、バイナリサイズが削減され、配布に適した形になります。

このコミット以前は、外部リンキングと `-s` フラグを組み合わせた際のシンボル除去処理が、主にELF (Executable and Linkable Format) 形式の実行ファイルを生成するLinuxなどのシステム向けに実装されていました。しかし、Windows (PE形式) やmacOS (Mach-O形式) のようなELF以外のシステムでは、この処理が適切に行われず、結果としてクラッシュや予期せぬ動作を引き起こしていました。

具体的には、外部リンカが最終的なリンクを行う際にシンボル情報が必要であるにもかかわらず、Goリンカが内部的にシンボル情報を除去してしまう、あるいはその逆の不整合が発生していたと考えられます。この不整合が、特にWindowsやmacOSといったELF以外の環境で顕在化し、Issue #10254として報告されていました。

このコミットは、このプラットフォーム固有のリンキング処理の差異を吸収し、外部リンキングと `-s` フラグの組み合わせがすべてのサポート対象OSで一貫して機能するようにするための修正です。

## 前提知識の解説

*   **Goリンカ (`cmd/link`)**: Go言語のコンパイラツールチェーンの一部で、コンパイルされたGoパッケージやCgoでリンクされるC/C++オブジェクトファイルを結合し、実行可能ファイルを生成する役割を担います。
*   **`-s` リンカフラグ**: Goリンカに渡されるフラグの一つで、生成される実行ファイルからデバッグ情報やシンボルテーブルを削除するよう指示します。これにより、バイナリのサイズが小さくなりますが、デバッグが困難になります。
*   **`-linkmode=external` リンカフラグ**: Goリンカに、最終的なリンクステップでシステムのCリンカ（例: `gcc` や `clang`）を使用するよう指示するフラグです。これは、主に `cgo` を使用してC/C++ライブラリとリンクする場合や、特定のシステムリンカ機能（例: ダイナミックリンキング、特定の最適化）が必要な場合に用いられます。
*   **ELF (Executable and Linkable Format)**: LinuxやBSDなどのUnix系OSで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。
*   **PE (Portable Executable)**: Windowsオペレーティングシステムで使われている実行可能ファイル、オブジェクトファイル、DLL (Dynamic Link Library) のフォーマットです。
*   **Mach-O (Mach Object)**: macOSやiOSなどのApple製OSで使われている実行可能ファイル、オブジェクトファイル、共有ライブラリのフォーマットです。
*   **`cgo`**: Go言語の機能で、GoプログラムからC言語の関数を呼び出したり、C言語のコードをGoプログラムに組み込んだりすることを可能にします。`cgo` を使用する場合、GoリンカはCコンパイラ/リンカと連携して最終的なバイナリを生成します。
*   **`__thread`**: C/C++言語におけるスレッドローカルストレージ (Thread-Local Storage, TLS) を指定するためのキーワードです。このキーワードで宣言された変数は、各スレッドが独自のコピーを持つことになります。`cgo` を介してCライブラリが `__thread` 変数を使用している場合、リンカはこれらを適切に処理する必要があります。コミットメッセージの `test linkmode=external, but __thread not supported, so skip testtls` という記述は、特定のプラットフォームで外部リンキング時に `__thread` のサポートに課題があることを示唆しています。

## 技術的詳細

このコミットの核心は、外部リンキング (`-linkmode=external`) を使用する際に、Goリンカが内部的にシンボル情報を扱う方法の変更にあります。

以前の実装では、シンボル除去 (`-s` フラグ) に関する特定のロジックが `src/cmd/link/internal/ld/elf.go` 内の `doelf()` 関数に限定されていました。この `doelf()` 関数は、その名の通りELF形式の実行ファイルを生成する際にのみ呼び出されるため、WindowsやmacOSのようなELF以外のプラットフォームでは、外部リンキング時に `-s` フラグが正しく処理されませんでした。

外部リンキングでは、Goリンカは中間オブジェクトファイルを生成し、最終的なリンクはシステムのCリンカに委ねます。この際、システムのCリンカは、Goが生成したオブジェクトファイル内のシンボル情報にアクセスできる必要があります。もしGoリンカが、システムのCリンカが処理する前にシンボル情報を完全に除去してしまうと、外部リンカは必要な情報を失い、リンクエラーや実行時エラーを引き起こす可能性があります。

このコミットでは、この問題を解決するために、シンボル除去に関するロジックを `src/cmd/link/internal/ld/lib.go` 内の `hostlinksetup()` 関数に移動しました。`hostlinksetup()` は、リンカの初期設定を行う関数であり、プラットフォームに依存しない形で外部リンキングが有効な場合に常に呼び出されます。

移動されたロジックは以下の通りです。

```go
// For external link, record that we need to tell the external linker -s,
// and turn off -s internally: the external linker needs the symbol
// information for its final link.
debug_s = Debug['s']
Debug['s'] = 0
```

このコードは、外部リンキングが有効な場合に、Goリンカが内部的に `-s` フラグを無効にする (`Debug['s'] = 0`) ことを意味します。しかし、元の `-s` フラグの状態は `debug_s` に保存されます。これは、Goリンカが生成する中間オブジェクトファイルにはシンボル情報を残しつつ、最終的に外部リンカがリンクする際に、外部リンカに対して `-s` フラグを渡す必要があることを示唆しています。つまり、Goリンカはシンボル除去の責任を外部リンカに委譲し、外部リンカが最終的なバイナリからシンボルを適切に除去するように調整しているわけです。

これにより、Goリンカは中間ファイルに必要なシンボル情報を保持し、外部リンカがその情報を使って正しくリンクを完了できるようになります。そして、外部リンカが最終的に `-s` フラグを解釈し、プラットフォームに応じた方法でシンボルを除去します。

`src/cmd/dist/test.go` の変更は、この修正がWindowsとmacOSの外部リンキングで `-s` フラグを伴う場合に正しく機能することを検証するためのテストケースの追加です。特に、`darwin-386`, `darwin-amd64`, `windows-386`, `windows-amd64` の各プラットフォームで、`go test -ldflags "-linkmode=external -s"` を実行するテストが追加されています。また、`__thread` がサポートされていないため `testtls` をスキップするというコメントは、`cgo` と外部リンキングの組み合わせにおけるプラットフォーム固有の複雑さを示しています。

## コアとなるコードの解説

このコミットの主要な変更は、Goリンカが外部リンキング (`-linkmode=external`) を使用する際に、シンボル除去 (`-s` フラグ) をどのように扱うかというロジックの移動と調整です。

`src/cmd/link/internal/ld/elf.go` から `src/cmd/link/internal/ld/lib.go` へのコードの移動は、シンボル除去の処理がELF形式に特化したものではなく、外部リンキングを使用するすべてのプラットフォームに共通して適用されるべきであるという認識に基づいています。

`src/cmd/link/internal/ld/lib.go` の `hostlinksetup()` 関数に追加された以下のコードブロックがその核心です。

```go
// For external link, record that we need to tell the external linker -s,
// and turn off -s internally: the external linker needs the symbol
// information for its final link.
debug_s = Debug['s']
Debug['s'] = 0
```

1.  `debug_s = Debug['s']`: これは、ユーザーがGoリンカに渡した元の `-s` フラグの状態（シンボル除去を行うかどうか）を `debug_s` という変数に保存しています。この変数は、後で外部リンカを呼び出す際に、外部リンカに `-s` フラグを渡す必要があるかどうかを判断するために使用される可能性があります。
2.  `Debug['s'] = 0`: これは、Goリンカが内部的にシンボル除去の処理を無効にすることを意味します。つまり、Goリンカは、外部リンカに渡す中間オブジェクトファイルからシンボル情報を除去しません。

この挙動の理由は、コメントにも明記されている通り、「外部リンカが最終的なリンクのためにシンボル情報を必要とする」ためです。Goリンカが中間オブジェクトファイルを生成する段階でシンボルを完全に除去してしまうと、システムのCリンカ（外部リンカ）は必要なシンボル情報を見つけられず、リンクに失敗したり、正しくないバイナリを生成したりする可能性があります。

したがって、Goリンカは、外部リンキングが指定された場合、シンボル除去の責任を外部リンカに委譲します。Goリンカは中間ファイルにシンボル情報を保持したままにし、外部リンカがその情報を使ってリンクを完了した後、外部リンカ自身の機能でシンボル除去を行うように調整されるわけです。これにより、WindowsやmacOSといったELF以外のプラットフォームでも、外部リンキングと `-s` フラグの組み合わせが正しく機能するようになります。

`src/cmd/dist/test.go` の変更は、この新しいロジックが意図通りに動作することを検証するためのテストを追加しています。特に、`darwin` と `windows` 環境で `-linkmode=external -s` を使用した `cgo` テストが追加されたことで、これらのプラットフォームでの回帰テストが強化されました。

# [インデックス 25178] ファイルの概要

## コミット

このコミットは、Goコンパイラのx86アセンブラ（`cmd/internal/obj/x86`）に初期のVEXエンコーディングサポートを追加するものです。具体的には、`VZEROUPPER`、`VMOVNTDQ`、`VMOVDQU`、`VMOVDQA`といったVEXプレフィックスを使用する命令のサポートが導入されました。また、これらの命令の命名規則として、16を意味する「HexaDeca」から「HD」を用いて`MOVHD*`という形式が採用されています。

## 変更の背景

この変更の背景には、IntelがAdvanced Vector Extensions (AVX) 命令セットを導入したことがあります。AVXは、SSE（Streaming SIMD Extensions）命令セットを拡張し、より広いデータパス（256ビット）と新しい命令を提供することで、浮動小数点演算やデータ処理のパフォーマンスを大幅に向上させます。

AVX命令は、従来の命令エンコーディングとは異なる「VEXプレフィックス」を使用します。VEXプレフィックスは、命令のオペランドサイズ、レジスタの選択、およびその他の命令修飾子をより柔軟に指定できるように設計されています。GoコンパイラがAVX命令を生成できるようにするためには、このVEXプレフィックスのエンコーディングをアセンブラが理解し、適切に処理できる必要があります。

このコミットは、Goのx86アセンブラがAVX命令をサポートするための最初のステップであり、特にデータ移動やレジスタの状態管理に関連する基本的なVEX命令のサポートを追加することで、将来的なAVX命令セットの活用に向けた基盤を築いています。

## 前提知識の解説

### x86アセンブラと命令エンコーディング

x86アーキテクチャでは、CPUが実行する命令はバイトコードとしてエンコードされます。このエンコーディングは、オペコード、モディファイア、オペランド、そしてプレフィックスなど、複数の要素から構成されます。

*   **オペコード**: 命令の種類（例: `MOV`, `ADD`）を識別するバイト。
*   **プレフィックス**: 命令の動作を変更する追加のバイト。これには、オペランドサイズのオーバーライド（`0x66`）、アドレスサイズオーバーライド（`0x67`）、セグメントオーバーライド、REXプレフィックス（64ビットモードでのレジスタ拡張）などがあります。

### REXプレフィックス

64ビットモードのx86-64アーキテクチャでは、より多くの汎用レジスタ（R8-R15）とSIMDレジスタ（XMM8-XMM15）が導入されました。これらの新しいレジスタにアクセスするため、および64ビットオペランドサイズを指定するために、REXプレフィックス（`0x40`から`0x4F`の範囲）が導入されました。REXプレフィックスは、命令の前に置かれ、レジスタの拡張やオペランドサイズの指定を行います。

### VEXプレフィックス (Vector Extension Prefix)

VEXプレフィックスは、IntelがAVX命令セットと共に導入した新しい命令エンコーディング方式です。従来のREXプレフィックスやその他のプレフィックスを置き換え、よりコンパクトで柔軟なエンコーディングを提供します。VEXプレフィックスには2バイト形式と3バイト形式があり、以下の情報を含みます。

*   **命令プレフィックスの置き換え**: `0x66`, `0xF2`, `0xF3` などの従来の命令プレフィックスをVEXプレフィックス内で表現します。
*   **REXプレフィックスの置き換え**: REXプレフィックスの機能（レジスタ拡張、Wビット）をVEXプレフィックス内で表現します。
*   **VEXレジスタフィールド (V)**: 3つ目のオペランドレジスタ（ソースレジスタ）を指定するために使用されます。これにより、3オペランド命令（例: `ADDPS XMM1, XMM2, XMM3`）が可能になります。
*   **Lビット (Vector Length)**: ベクトルオペランドの長さを指定します（例: 128ビットまたは256ビット）。
*   **Pビット (Operand Encoding)**: 命令のオペランドエンコーディングを指定します。

VEXプレフィックスを使用することで、命令のデコードが簡素化され、命令の密度が向上し、将来の拡張性も確保されます。

### AVX命令セット

Advanced Vector Extensions (AVX) は、IntelがSandy Bridgeマイクロアーキテクチャで導入したSIMD命令セットです。主な特徴は以下の通りです。

*   **256ビットYMMレジスタ**: 従来の128ビットXMMレジスタを拡張し、256ビットのYMMレジスタを導入しました。これにより、一度に処理できるデータ量が増加します。
*   **3オペランド命令**: 多くのAVX命令は3つのオペランドを取ります（例: `DEST = SRC1 op SRC2`）。これにより、ソースオペランドを破壊することなく演算結果を別のレジスタに格納できます。
*   **VEXエンコーディング**: 全てのAVX命令はVEXプレフィックスを使用してエンコードされます。

このコミットでサポートされる命令は以下の通りです。

*   `VZEROUPPER`: YMMレジスタの上位128ビットをゼロクリアします。これにより、AVXからSSEへの切り替え時にパフォーマンスペナルティが発生するのを防ぎます。
*   `VMOVNTDQ`: Non-Temporal Move Double Quadword。キャッシュを汚染せずにデータをメモリに書き込みます。ストリーミングデータや大量のデータ転送に有用です。
*   `VMOVDQU`: Move Double Quadword Unaligned。アラインメントされていないメモリ位置からYMMレジスタへ、またはその逆へデータを移動します。
*   `VMOVDQA`: Move Double Quadword Aligned。アラインメントされたメモリ位置からYMMレジスタへ、またはその逆へデータを移動します。

## 技術的詳細

このコミットは、GoアセンブラがVEXエンコーディングを生成できるようにするための複数の変更を含んでいます。

1.  **`Link`構造体への`Vexflag`の追加**:
    `src/cmd/internal/obj/link.go`の`Link`構造体に`Vexflag int`が追加されました。これは、現在処理中の命令がVEXエンコードされるべきかどうかを示すフラグとして使用されます。

2.  **新しい命令定数の定義**:
    `src/cmd/internal/obj/x86/a.out.go`に、`AVZEROUPPER`, `AMOVHDU`, `AMOVNTHD`, `AMOVHDA`といった新しい命令定数が追加されました。これらは、Goアセンブラ内部でこれらの命令を識別するために使用されます。

3.  **命令名の追加**:
    `src/cmd/internal/obj/x86/anames.go`の`Anames`配列に、上記で定義された新しい命令定数に対応する文字列名（`"VZEROUPPER"`, `"MOVHDU"`, `"MOVNTHD"`, `"MOVHDA"`）が追加されました。これにより、アセンブラの出力やデバッグ時にこれらの命令が人間が読める形式で表示されます。

4.  **`asm6.go`におけるVEXエンコーディングのサポート**:
    `src/cmd/internal/obj/x86/asm6.go`は、x86命令のエンコーディングロジックを実装する主要なファイルです。このファイルに以下の重要な変更が加えられました。

    *   **新しいオペランドタイプ**: `Zm_r_xm_vex`と`Zr_m_xm_vex`という新しいオペランドタイプが追加されました。これらは、VEXプレフィックスを使用する命令のオペランドの組み合わせ（メモリ/レジスタとXMM/YMMレジスタ）を表現します。
    *   **新しいVEXプレフィックス定数**: `Pvex1 = 0xc5`と`Pvex2 = 0xc6`が定義されました。これらは、それぞれ2バイトVEXプレフィックスの特定の形式（`0x66`プレフィックスの置き換え、`0xf3`プレフィックスの置き換え）に対応します。
    *   **`vexprefix`関数の追加**:
        この関数は、VEXプレフィックスのバイト列を生成する役割を担います。
        -   `pref`引数（`Pvex1`または`Pvex2`）に基づいて、VEXプレフィックスの2バイト目の一部を決定します。
        -   命令のオペランドレジスタ（`to.Reg`, `from.Reg`, `from.Index`）のREXビット（`rexR`, `rexB`, `rexX`）を考慮して、VEXプレフィックスのR, X, Bビットを適切に設定します。
        -   2バイト形式（`0xC5`）と3バイト形式（`0xC4`）のVEXプレフィックスのどちらを生成するかを決定します。この初期実装では、主に2バイト形式が扱われているようです。
        -   `ctxt.Andptr`というバイトスライスにVEXプレフィックスのバイトを書き込みます。
    *   **`optab`の更新**:
        `optab`は、各命令に対応するエンコーディング情報（オペランドタイプ、プレフィックス、オペコードバイト列）を定義するテーブルです。
        -   `AVZEROUPPER`命令は、`ynone`オペランドタイプと`Px`プレフィックス（プレフィックスなし）で、オペコードバイト列`{0xc5, 0xf8, 0x77}`として定義されました。これは、VEXプレフィックス自体が命令の一部として扱われることを示唆しています。
        -   `AMOVHDU`と`AMOVHDA`命令は、`yxmov_vex`オペランドタイプと`Pvex2`または`Pvex1`プレフィックスを使用し、それぞれオペコードバイト列`{0x6f, 0x7f}`で定義されました。
        -   `AMOVNTHD`命令は、`yxr_ml_vex`オペランドタイプと`Pvex1`プレフィックスを使用し、オペコードバイト列`{0xe7}`で定義されました。
    *   **`doasm`関数の変更**:
        `doasm`関数は、Goアセンブラの主要な命令エンコーディングループです。
        -   `Zm_r_xm_vex`および`Zr_m_xm_vex`オペランドタイプを処理する`case`が追加されました。
        -   これらの`case`内で、`ctxt.Vexflag`が`1`に設定され、`vexprefix`関数が呼び出されてVEXプレフィックスが生成されます。
        -   その後、命令のオペコードバイトが`ctxt.Andptr`に書き込まれ、`asmand`関数が呼び出されて残りのオペランドエンコーディングが処理されます。
    *   **`asmins`関数の変更**:
        `asmins`関数は、命令のエンコーディングを開始する関数です。
        -   `ctxt.Vexflag = 0`が追加され、各命令の処理前にVEXフラグがリセットされるようになりました。
        -   REXプレフィックスの生成ロジックが`if ctxt.Rexflag != 0 && ctxt.Vexflag == 0`に変更されました。これは、VEXエンコードされる命令ではREXプレフィックスが不要（VEXプレフィックスがREXの機能を包含するため）であることを意味します。

これらの変更により、Goアセンブラは指定されたVEX命令を正しくエンコードし、対応するVEXプレフィックスを生成できるようになります。

## コアとなるコードの解説

このコミットの核心は、GoアセンブラがVEXプレフィックスを生成し、AVX命令を正しくエンコードできるようにするロジックの追加です。

1.  **`vexprefix`関数**:
    この関数は、VEXプレフィックスの生成を担当します。VEXプレフィックスは、従来のREXプレフィックスや命令プレフィックス（`0x66`, `0xF2`, `0xF3`）の機能を統合し、さらに3つ目のオペランドレジスタ（VEXレジスタフィールド）やベクトル長（Lビット）などの情報を含みます。
    -   `pref`引数（`Pvex1`または`Pvex2`）は、どの従来の命令プレフィックスをVEXプレフィックスで置き換えるかを示します。`Pvex1`は`0x66`、`Pvex2`は`0xf3`に対応します。
    -   `rexR`, `rexB`, `rexX`は、命令のオペランドに使用されるレジスタのREXビット情報です。VEXプレフィックスは、これらのREXビットを自身のフィールドに組み込みます。
    -   関数は、オペランドのREXビットの有無に基づいて、2バイト形式（`0xC5`で始まる）または3バイト形式（`0xC4`で始まる）のVEXプレフィックスを生成します。この初期実装では、主に2バイト形式が扱われているように見えますが、3バイト形式の骨格も用意されています。
    -   生成されたVEXプレフィックスのバイトは、`ctxt.Andptr`（アセンブルされた命令バイトを格納するバッファ）に書き込まれます。

2.  **`doasm`関数内のVEX命令処理**:
    `doasm`関数は、Goアセンブラが命令をバイトコードに変換する中心的なロジックです。
    -   `Zm_r_xm_vex`と`Zr_m_xm_vex`という新しいオペランドタイプが導入され、VEXエンコードされる命令のオペランドの組み合わせを識別します。
    -   これらのオペランドタイプに遭遇すると、`ctxt.Vexflag`が`1`に設定され、`vexprefix`関数が呼び出されてVEXプレフィックスが生成されます。
    -   その後、命令の実際のオペコードバイトが書き込まれ、`asmand`関数によってModR/MバイトやSIBバイトなどの残りのオペランドエンコーディングが処理されます。

3.  **`asmins`関数でのREX/VEXの排他制御**:
    `asmins`関数は、各命令のアセンブルを開始する際に呼び出されます。
    -   `ctxt.Vexflag = 0`が追加され、各命令の処理前にVEXフラグがクリアされることで、前の命令の状態が次の命令に影響を与えないようにします。
    -   `if ctxt.Rexflag != 0 && ctxt.Vexflag == 0`という条件が追加されました。これは、VEXエンコードされる命令（`ctxt.Vexflag == 1`の場合）では、従来のREXプレフィックスを生成しないことを保証します。VEXプレフィックス自体がREXプレフィックスの機能を包含しているため、両方を生成すると誤った命令エンコーディングになります。

これらの変更により、GoアセンブラはAVX命令のVEXエンコーディングを正しく処理し、Goプログラム内でAVX命令を利用するための基盤を提供します。

# [インデックス 21288] ファイルの概要

このコミットは、Go言語のビルドツールである`cmd/go`がC言語のソースファイル（`.c`ファイル）をどのように扱うかに関するロジックの変更です。具体的には、Goの標準コンパイラである`gc`と、GCCベースのGoコンパイラである`gccgo`の間で、Cファイルの取り扱いに関する挙動を明確に区別するように修正されました。変更は`src/cmd/go/pkg.go`ファイルに集中しており、Cファイルの存在チェックとエラーハンドリングの条件が更新されています。

## 変更の背景

このコミットは、Go言語のビルドツールである`cmd/go`がC言語のソースファイル（`.c`ファイル）をどのように扱うか、特にGoの標準コンパイラである`gc`と、GCCベースのGoコンパイラである`gccgo`の間での挙動の違いを明確にするために導入されました。

以前の`cmd/go`のロジックでは、Cファイルは`cgo`を使用している場合、または`runtime`パッケージの場合にのみ許可されていました。しかし、これは`gc`と`gccgo`のコンパイラの特性を十分に考慮していませんでした。

-   **`gc`コンパイラ**: Go言語のコードを直接コンパイルすることに特化しており、C言語のコードを直接コンパイルする機能は持っていません。C言語のコードをGoプログラムに組み込むには、後述する`cgo`というメカニズムを介して外部のCコンパイラに処理を委ねる必要があります。したがって、`gc`を使用しているにもかかわらず`cgo`を介さずにCファイルが存在することは、ビルドエラーの原因となります。
-   **`gccgo`コンパイラ**: GCCのフロントエンドとして実装されており、GCCがC言語のコンパイル機能を内包しているため、Cファイルを直接扱うことができます。そのため、`gccgo`を使用する際には、`cgo`の有無にかかわらずCファイルをコンパイルできることが期待されます。

このコミットの目的は、これらのコンパイラの根本的な違いに基づき、Cファイルの扱いに関する`cmd/go`のルールをより論理的かつ厳密にすることです。具体的には、`gc`コンパイラを使用する場合は`cgo`を介さないCファイルの利用を完全に禁止し、`gccgo`コンパイラを使用する場合はCファイルの利用を常に許可するように変更することで、コンパイラごとの期待される挙動と実際の挙動を一致させ、混乱を避けることを目指しています。

## 前提知識の解説

### Goコンパイラ (`gc`)

`gc`は、Go言語の公式かつ主要なコンパイラです。Goのソースコードを直接機械語にコンパイルします。高速なコンパイルと、Goランタイムとの密接な統合が特徴です。`gc`はC言語のソースファイルを直接コンパイルする機能を持たず、C言語のコードをGoプログラムに組み込む際には、後述する`cgo`の仕組みを利用して外部のCコンパイラに処理を委ねます。Goの標準的なビルドプロセスでは、通常この`gc`が使用されます。

### `gccgo`コンパイラ

`gccgo`は、GNU Compiler Collection (GCC) の一部として提供されるGo言語のコンパイラです。`gc`とは異なり、GCCの強力な最適化機能を利用できるため、生成されるバイナリのパフォーマンスが向上する可能性があります。また、GCCがサポートする多様なアーキテクチャに対応しています。`gccgo`はGCCのフロントエンドであるため、C言語のコンパイル機能を内部に持っており、Cファイルを直接扱うことができます。特定の環境や最適化要件がある場合に選択されることがあります。

### `cgo`

`cgo`は、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoのツールです。GoとCの間の相互運用性を提供します。`cgo`を使用すると、Goのソースファイル内にCコードを直接記述したり、既存のCソースファイルやライブラリをGoプログラムにリンクしたりできます。`cgo`は、Goのビルドプロセス中にCコンパイラ（通常はGCCやClang）を呼び出してCコードをコンパイルし、Goのオブジェクトファイルとリンクすることで機能します。`gc`コンパイラを使用する場合、Cコードのコンパイルは必ず`cgo`を介して行われます。

### GoにおけるCファイルの扱い

Go言語の設計思想として、通常はGo言語のみで記述することを推奨しています。しかし、既存のCライブラリを利用したい場合や、特定のパフォーマンス要件のためにC言語で記述された部分を組み込みたい場合に`cgo`が利用されます。`cmd/go`ツールは、Goパッケージのビルド時に、Goソースファイルだけでなく、Cソースファイル（`.c`, `.h`など）も検出して処理します。この処理の仕方が、使用するGoコンパイラ（`gc`か`gccgo`か）によって異なるため、本コミットでその挙動が調整されました。

## 技術的詳細

このコミットは、`src/cmd/go/pkg.go`ファイル内の`Package.load`メソッドにおけるCソースファイルのチェックロジックを変更しています。`Package.load`メソッドは、Goパッケージのビルド情報をロードする際に、そのパッケージに含まれるCファイルの有無と、それが許可されるべきかどうかを判断します。

変更前のコードは以下のようになっていました。

```go
	// Check for C code compiled with Plan 9 C compiler.
	// No longer allowed except in runtime and runtime/cgo, for now.
	if len(p.CFiles) > 0 && !p.usesCgo() && (!p.Standard || p.ImportPath != "runtime") {
		p.Error = &PackageError{
			ImportStack: stk.copy(),
			Err:         fmt.Sprintf("C source files not allowed when not using cgo: %s", strings.Join(p.CFiles, " "))),
		}
	}
```

このロジックは、「Cファイルが存在し（`len(p.CFiles) > 0`）、`cgo`を使用しておらず（`!p.usesCgo()`）、かつ標準パッケージではないか、または`runtime`パッケージではない場合（`(!p.Standard || p.ImportPath != "runtime")`）」にエラーを発生させていました。これは、`runtime`パッケージが`cgo`なしでCファイルを使用できるという特殊な例外を設けていました。このコメントにある"Plan 9 C compiler"は、Goの初期のコンパイラがPlan 9 Cコンパイラをベースにしていたことの名残であり、この時点ではもはや直接的な意味を持っていません。

変更後のコードは以下のようになります。

```go
	// The gc toolchain only permits C source files with cgo.
	if len(p.CFiles) > 0 && !p.usesCgo() && buildContext.Compiler == "gc" {
		p.Error = &PackageError{
			ImportStack: stk.copy(),
			Err:         fmt.Sprintf("C source files not allowed when not using cgo: %s", strings.Join(p.CFiles, " "))),
		}
	}
```

この変更により、エラーが発生する条件が「Cファイルが存在し（`len(p.CFiles) > 0`）、`cgo`を使用しておらず（`!p.usesCgo()`）、かつ現在使用しているコンパイラが`gc`である場合（`buildContext.Compiler == "gc"`）」に変わりました。

この変更のポイントは以下の通りです。

1.  **`runtime`パッケージの特殊扱いの削除**: 以前のロジックでは`runtime`パッケージが`cgo`なしでCファイルを持つことを許可していましたが、この変更によりその特殊な例外が削除されました。これは、`cmd/go`が一般のパッケージに対してCファイルをどのように扱うかというルールをより厳密にするものです。`runtime`パッケージ自体は、Goランタイムの非常に低レベルな部分をC言語で実装していることがありますが、それは`cmd/go`の通常のパッケージビルドフローとは異なる特別なビルドメカニズムによって処理されるため、この変更が`runtime`パッケージのビルドに直接的な問題を引き起こすことはありません。
2.  **コンパイラによる挙動の明確化**: `buildContext.Compiler == "gc"`という条件が追加されたことで、このチェックが`gc`コンパイラを使用している場合にのみ適用されることが明確になりました。
    *   **`gc`コンパイラを使用している場合**: Cファイルが存在し、`cgo`を使用していない場合はエラーとなります。これは、`gc`がCファイルを直接コンパイルできないため、`cgo`を介さないCファイルの存在は不正であるという厳格なルールを適用します。
    *   **`gccgo`コンパイラを使用している場合**: `buildContext.Compiler`が`"gc"`ではない（例えば`"gccgo"`である）ため、この`if`ブロック全体がスキップされます。これにより、`gccgo`は`cgo`の有無にかかわらずCファイルを自由に扱うことができるようになります。これは`gccgo`がGCCをベースとしているため、Cファイルのコンパイル能力を内包しているという特性に合致しています。

この変更により、`cmd/go`は各コンパイラの特性に合わせたCファイルの扱いを強制するようになり、ビルドシステムの一貫性と予測可能性が向上しました。開発者は、`gc`を使用する場合は`cgo`を介したCファイルの利用が必須であり、`gccgo`を使用する場合はより柔軟にCファイルを扱えるという明確なガイドラインを得ることができます。

## コアとなるコードの解説

変更されたのは、`src/cmd/go/pkg.go`ファイル内の`Package.load`関数における条件分岐です。この関数は、Goパッケージのロードとビルド情報の収集を担当しており、特にC言語のソースファイル（`.c`ファイル）の存在をチェックし、その使用が許可されているかを判断します。

元のコードの条件式:
`if len(p.CFiles) > 0 && !p.usesCgo() && (!p.Standard || p.ImportPath != "runtime")`

この条件は以下の3つの部分から構成されていました。
1.  `len(p.CFiles) > 0`: 現在処理しているパッケージにC言語のソースファイルが存在するかどうかをチェックします。
2.  `!p.usesCgo()`: パッケージが`cgo`（GoとCの相互運用機能）を使用しているかどうかをチェックします。`cgo`を使用していない場合に真となります。
3.  `(!p.Standard || p.ImportPath != "runtime")`: この部分は、パッケージがGoの標準ライブラリではない、または`runtime`パッケージではない場合に真となります。これは、`runtime`パッケージが`cgo`なしでCファイルを持つことを許容するという、当時の特殊なルールを反映していました。

これらの条件がすべて真の場合、つまり「Cファイルがあり、`cgo`を使っておらず、かつ`runtime`パッケージではない」場合に、`PackageError`を生成してエラーとして記録していました。

変更後のコードの条件式:
`if len(p.CFiles) > 0 && !p.usesCgo() && buildContext.Compiler == "gc"`

この新しい条件は以下の3つの部分から構成されています。
1.  `len(p.CFiles) > 0`: 同様に、パッケージにC言語のソースファイルが存在するかどうかをチェックします。
2.  `!p.usesCgo()`: 同様に、パッケージが`cgo`を使用していないかどうかをチェックします。
3.  `buildContext.Compiler == "gc"`: この新しい条件は、現在のビルドコンテキストで使用されているGoコンパイラが`gc`（Goの標準コンパイラ）であるかどうかをチェックします。

この変更により、エラーが発生する条件が「Cファイルがあり、`cgo`を使っておらず、かつ`gc`コンパイラを使用している」場合に限定されました。

-   **`gc`コンパイラを使用している場合**: `buildContext.Compiler == "gc"`が真となるため、`gc`はCファイルを直接コンパイルできないという特性に基づき、`cgo`を介さずにCファイルが存在することは不正とみなされ、エラーとなります。
-   **`gccgo`コンパイラを使用している場合**: `buildContext.Compiler`が`"gc"`ではない（例えば`"gccgo"`である）ため、`buildContext.Compiler == "gc"`の条件は偽となり、この`if`ブロック全体がスキップされます。これにより、`gccgo`はCファイルを自由にコンパイルできるという特性が尊重され、`cgo`の有無にかかわらずCファイルを扱うことが許可されます。

この変更は、Goのビルドシステムが、使用するコンパイラの特性（`gc`はCファイルを直接扱えない、`gccgo`は扱える）に基づいて、Cファイルの扱いをより厳密かつ論理的に区別するようにしたものです。これにより、開発者は使用するコンパイラに応じたCファイルの取り扱いをより明確に理解できるようになります。

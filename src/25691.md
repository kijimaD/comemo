# [インデックス 25691] ファイルの概要

このコミットは、Goランタイムのメモリ管理における潜在的なクラッシュバグを修正するものです。具体的には、`mheap.sysAlloc`が確保したメモリ領域が利用可能なアリーナの範囲外であった場合に、その領域を解放する`sysFree`関数が誤った`stat`ポインタを受け取ることで発生するアンダーフローによるパニックを防ぎます。

## 変更の背景

Goランタイムは、効率的なメモリ管理のために独自のヒープ（`mheap`）を使用しています。`mheap.sysAlloc`関数は、オペレーティングシステムから直接メモリを確保（予約およびコミット）する役割を担っています。しかし、この`sysAlloc`が`sysReserve`を通じてメモリを予約する際、稀にその予約された領域がGoランタイムが利用可能なメモリ領域（アリーナ）の範囲外となることがあります。

このような状況が発生した場合、Goランタイムはその利用できないメモリ領域をすぐにオペレーティングシステムに返却する必要があります。この返却処理には`sysFree`関数が使用されます。問題は、この時点で確保されたメモリはまだGoランタイムの内部統計（`stat`）に計上されていないため、`sysFree`に渡す`stat`ポインタが「偽の」ものである必要があった点です。

以前の実装では、この「偽の`stat`ポインタ」として、値が`0`の`uint64`変数のアドレスが渡されていました。`sysFree`関数は、解放するメモリサイズをこの`stat`から減算しようとします。しかし、`0`から正の値を減算しようとすると、`uint64`型の特性上、アンダーフローが発生し、これがランタイムパニックを引き起こす原因となっていました。このコミットは、このアンダーフローによるクラッシュを回避するために導入されました。コミットメッセージには、これがGo issue #13143の修正に向けた前提条件であると明記されています。

## 前提知識の解説

*   **Goランタイムのメモリ管理**: Goは独自のガベージコレクタとメモリ管理システムを持っています。これはOSから大きなメモリブロックを確保し、それを細かく分割してユーザープログラムに割り当てます。
*   **`mheap`**: Goランタイムのグローバルヒープ構造体です。OSからメモリを要求し、管理する中心的な役割を担います。
*   **`sysAlloc`**: `mheap`の一部であり、OSから物理メモリを確保（予約およびコミット）するための関数です。通常、`mheap`が管理するアリーナ内にメモリを確保しようとしますが、稀にその範囲外のメモリが返されることがあります。
*   **`sysReserve`**: `sysAlloc`内部で呼ばれる関数で、OSに対して仮想メモリ空間を予約します。
*   **`sysFree`**: OSにメモリを返却（解放）するための関数です。この関数は、解放するメモリのサイズを引数として受け取り、また、メモリ統計を更新するために`stat`ポインタも受け取ります。
*   **メモリ統計 (`stat`)**: Goランタイムは、ヒープの使用状況、ガベージコレクションの活動など、様々なメモリ関連の統計情報を追跡しています。これらの統計は、ランタイムのパフォーマンス分析やデバッグに不可欠です。`sysFree`が受け取る`stat`ポインタは、通常、解放されるメモリ量を対応する統計カウンタから減算するために使用されます。
*   **アンダーフロー**: 符号なし整数型（`uint64`など）で、その最小値（`0`）よりも小さい値を表現しようとすると発生する現象です。`0`から`1`を引くと、その型の最大値になるなど、予期しない大きな値になることがあります。これはプログラムの誤動作やクラッシュの原因となります。

## 技術的詳細

このバグは、`mheap.sysAlloc`関数内で発生する特定のシナリオに起因していました。

1.  `mheap.sysAlloc`が`sysReserve`を呼び出し、OSからメモリ領域を予約します。
2.  予約されたメモリ領域が、Goランタイムの`mheap`が管理する「利用可能なアリーナ」の範囲外であった場合、その領域はすぐに解放される必要があります。
3.  この解放処理のために`sysFree`が呼び出されます。
4.  問題は、この時点で確保されたメモリはまだGoランタイムの正式なメモリ統計に計上されていないため、`sysFree`に渡す`stat`ポインタが、実際の統計カウンタではなく「偽の」ものである必要があったことです。
5.  以前の実装では、この「偽の`stat`」として、`var stat uint64`と宣言された、初期値が`0`のローカル変数のアドレスが`sysFree`に渡されていました。
6.  `sysFree`は、解放するメモリのサイズ（`p_size`）をこの`stat`から減算しようとします。
7.  `0`である`stat`から`p_size`（正の値）を減算しようとすると、`uint64`型の特性によりアンダーフローが発生します。例えば、`0 - 1024`は`uint64`の最大値に近い非常に大きな値になります。
8.  このアンダーフローが、Goランタイムの内部で予期しない状態を引き起こし、最終的にパニック（クラッシュ）に至る可能性がありました。

このコミットは、このアンダーフローを直接的に解決します。`sysFree`が減算する値は、解放されるメモリのサイズそのものであるため、`stat`の初期値を`p_size`に設定することで、`sysFree`が`p_size`を減算しても`0`になり、アンダーフローが発生しなくなります。これにより、`sysFree`は安全に実行され、ランタイムの安定性が向上します。

## コアとなるコードの変更箇所

`src/runtime/malloc.go`ファイルの`mheap.sysAlloc`関数内の以下の部分が変更されました。

```diff
--- a/src/runtime/malloc.go
+++ b/src/runtime/malloc.go
@@ -414,7 +414,10 @@ func (h *mheap) sysAlloc(n uintptr) unsafe.Pointer {
 			h.arena_used = used
 			h.arena_reserved = reserved
 		} else {
-			var stat uint64
+			// We haven't added this allocation to
+			// the stats, so subtract it from a
+			// fake stat (but avoid underflow).
+			stat := uint64(p_size)
 			sysFree(unsafe.Pointer(p), p_size, &stat)
 		}
 	}
```

## コアとなるコードの解説

変更前は、`else`ブロック内で`var stat uint64`と宣言されており、`stat`変数の初期値は`0`でした。この`0`のアドレスが`sysFree`に渡され、`sysFree`が`p_size`を減算しようとするとアンダーフローが発生していました。

変更後は、`stat`変数の宣言と同時に`stat := uint64(p_size)`と、解放されるメモリのサイズ`p_size`で初期化されるようになりました。

この変更により、`sysFree`が`&stat`ポインタを受け取り、その内部で`*stat -= p_size`のような操作を実行しても、`p_size - p_size`となり、`stat`の値は`0`になります。これにより、`uint64`型のアンダーフローが回避され、ランタイムのクラッシュが防止されます。

コメントも追加され、この`stat`が「偽の統計情報」であり、アンダーフローを避けるためのものであることが明確に説明されています。これは、このメモリ領域がまだ正式な統計に計上されていないため、一時的な措置として行われるものです。

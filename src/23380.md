# [インデックス 23380] ファイルの概要

このコミットは、Goランタイムにおける`typedmemmove`関数のポインタ走査メカニズムを改善するものです。具体的には、型の`ptrmask`を直接解釈する代わりに、ヒープビットマップを利用するように変更し、ガベージコレクション(GC)の正確性を向上させています。この変更は、Go 1.5開発サイクル中にGCプログラムを無効にする必要があった問題に対処し、常に利用可能で最新のヒープビットマップを使用することで、ポインタの正確な識別を保証します。

The current implementation of typedmemmove walks the ptrmask
in the type to find out where pointers are. This led to turning off
GC programs for the Go 1.5 dev cycle, so that there would always
be a ptrmask. Instead of also interpreting the GC programs,
interpret the heap bitmap, which we know must be available and
up to date. (There is no point to write barriers when writing outside
the heap.)

This CL is only about correctness. The next CL will optimize the code.

## 変更の背景

Goのガベージコレクション(GC)は、ヒープ上のオブジェクトを正確に追跡し、不要になったメモリを解放する役割を担っています。このプロセスにおいて、オブジェクト内のどのフィールドがポインタであるかを識別することは非常に重要です。Go 1.5の開発サイクルにおいて、`typedmemmove`関数（型情報に基づいてメモリをコピーする関数）が、型の`ptrmask`（ポインタのビットマップ）を直接走査してポインタの位置を特定していました。

しかし、この`ptrmask`の扱いは、GCプログラムの動作と密接に関連しており、Go 1.5のGC開発中に問題を引き起こしました。具体的には、`ptrmask`の正確性を保証するために、GCプログラムの一部を無効にする必要が生じました。これは、GCの全体的な健全性やパフォーマンスに影響を与える可能性がありました。

このコミットの目的は、この問題を解決し、`typedmemmove`がポインタを識別するより堅牢で常に利用可能なメカニズムを使用するようにすることです。コミットメッセージにもあるように、この変更は「正確性」を目的としており、パフォーマンス最適化は後続のコミットで行われる予定でした。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に並行マーク＆スイープ方式を採用しています。これは、プログラムの実行と並行してGCが動作し、アプリケーションの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えることを目指しています。GCは、ヒープ上のオブジェクトを「到達可能」（プログラムから参照されている）か「到達不可能」（不要）かを判断し、到達不可能なオブジェクトが占めるメモリを再利用します。

### ポインタとヒープ

Goでは、変数がヒープに割り当てられるかスタックに割り当てられるかは、コンパイラのエスケープ解析によって決定されます。ヒープに割り当てられたオブジェクトは、GCの管理対象となります。ポインタは、ヒープ上の他のオブジェクトを指し示すメモリアドレスを保持します。GCが正しく動作するためには、どのメモリ位置がポインタを含んでいるかを正確に知る必要があります。

### Write Barrier (ライトバリア)

Goの並行GCでは、GCがオブジェクトをマークしている最中に、アプリケーションがヒープ上のポインタを変更する可能性があります。このような変更によってGCがオブジェクトを見落とすことを防ぐために、「ライトバリア」というメカニズムが導入されています。ライトバリアは、ポインタの書き込み操作をインターセプトし、GCが必要な情報を記録できるようにするものです。これにより、GCとアプリケーションが並行して動作しても、メモリの安全性が保たれます。

### `_type` と `ptrmask`

Goのランタイムは、すべての型に関するメタデータ（`_type`構造体）を保持しています。このメタデータには、型のサイズ、アラインメント、そしてその型がポインタをどこに含んでいるかを示す情報が含まれます。以前のGoのGCでは、このポインタ情報の一部として`ptrmask`（ポインタビットマップ）やGCプログラムが使用されていました。`ptrmask`は、型のメモリレイアウトにおいて、どのワードがポインタであるかを示すビット列です。GCプログラムは、より複雑な型のポインタ情報を動的に生成するためのバイトコードのようなものでした。

### ヒープビットマップ (Heap Bitmap)

ヒープビットマップは、Goのヒープメモリ全体に対して、各ワードがポインタであるか、またはオブジェクトの開始位置であるかなどの情報を示すビットマップです。これは、GCがヒープを走査する際に非常に効率的にポインタを識別するために使用されます。`ptrmask`が特定の「型」のポインタ情報を示すのに対し、ヒープビットマップは「ヒープ上の特定のメモリ位置」がポインタであるかを示す、より低レベルで広範な情報を提供します。ヒープビットマップは、GCの実行中に常に最新の状態に保たれています。

### `typedmemmove`

`typedmemmove`は、Goランタイム内部で使用される関数で、特定の型情報（`_type`）に基づいて、あるメモリ領域から別のメモリ領域へデータをコピーします。このコピー操作中に、コピー元またはコピー先のメモリ領域にポインタが含まれている場合、GCのライトバリアを適切にトリガーする必要があります。

### `unsafe.Pointer`

`unsafe.Pointer`は、Goの型システムをバイパスして、任意の型のポインタを任意の型のポインタに変換したり、ポインタと`uintptr`の間で変換したりすることを可能にする特殊な型です。ランタイム内部では、メモリ操作を直接行うために頻繁に使用されますが、その名の通り「unsafe」であり、誤用するとメモリ安全性の問題を引き起こす可能性があります。

## 技術的詳細

このコミットの核心は、`typedmemmove`関数がポインタを識別する方法を、型の`ptrmask`を解釈する方式から、ヒープビットマップを直接参照する方式へと変更した点にあります。

従来の`typedmemmove`は、コピー対象の`_type`構造体に含まれる`ptrmask`（またはGCプログラム）を走査して、どのメモリワードがポインタであるかを判断し、そのポインタに対してライトバリアを適用していました。しかし、Go 1.5のGC開発において、この`ptrmask`の生成と解釈の複雑さが、GCプログラムの安定性に影響を与え、一時的にGCプログラムを無効にする必要が生じました。これは、`ptrmask`が常に利用可能で正確であることを保証するための措置でした。

コミットメッセージが指摘するように、ヒープビットマップは常に利用可能で最新の状態に保たれています。これは、GCがヒープを管理するために不可欠な情報だからです。ヒープビットマップは、ヒープ上の任意のメモリ位置がポインタであるかどうかを効率的に判断できるため、`typedmemmove`がポインタを識別する信頼性の高いソースとなります。

この変更により、`typedmemmove`は、コピー操作後に`heapBitsBulkBarrier`という新しい関数を呼び出すようになりました。`heapBitsBulkBarrier`は、指定されたメモリ範囲をヒープビットマップに基づいて走査し、ポインタが格納されている各位置に対して`writebarrierptr_nostore`（ライトバリアの一種）を実行します。これにより、`typedmemmove`によるメモリコピーがGCの整合性を損なわないことが保証されます。

このコミットは「正確性」に焦点を当てています。つまり、GCがポインタを正しく追跡し、メモリ安全性を維持するための基盤を強化することが主な目的です。`ptrmask`の複雑な解釈ロジックを削除し、よりシンプルで信頼性の高いヒープビットマップに依存することで、ランタイムの堅牢性が向上します。パフォーマンスの最適化は、この変更が正しく機能することを確認した後のステップとして計画されていました。

また、`writebarrierptr`関数内のエラーハンドリングも改善され、不正なポインタが検出された際に、より詳細なデバッグ情報（ポインタのアドレスと値）が出力されるようになりました。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

-   `src/runtime/mbarrier.go`: `typedmemmove`, `reflect_typedmemmovepartial`, `callwritebarrier` 関数が大幅に簡素化され、`heapBitsBulkBarrier` の呼び出しに置き換えられました。また、`writebarrierptr` のエラーメッセージが詳細化されました。
-   `src/runtime/mbitmap.go`: 新しい関数 `heapBitsBulkBarrier` が追加されました。また、`ptrBitmapForType` 関数が削除されました。

### `src/runtime/mbarrier.go` の変更点

-   `typedmemmove` 関数から、`ptrmask` を走査して個々のポインタに対してライトバリアを適用する複雑なロジックが削除され、代わりに `heapBitsBulkBarrier(uintptr(dst), typ.size)` が呼び出されるようになりました。
-   `reflect_typedmemmovepartial` および `callwritebarrier` 関数も同様に、`ptrmask` 走査ロジックが削除され、`heapBitsBulkBarrier` の呼び出しに置き換えられました。
-   `writebarrierptr` 関数内で不正なポインタが検出された際のエラーメッセージに、`dst` と `src` の値が追加されました。

### `src/runtime/mbitmap.go` の変更点

-   `heapBitsBulkBarrier(p, size uintptr)` 関数が新しく追加されました。この関数は、指定されたメモリ範囲 `[p, p+size)` 内のポインタをヒープビットマップを使用して識別し、それぞれに対して `writebarrierptr_nostore` を実行します。
-   `ptrBitmapForType` 関数（型の`ptrmask`を返す関数）が完全に削除されました。

## コアとなるコードの解説

### `typedmemmove` の変更

変更前:
```go
func typedmemmove(typ *_type, dst, src unsafe.Pointer) {
	if !writeBarrierEnabled || (typ.kind&kindNoPointers) != 0 {
		memmove(dst, src, typ.size)
		return
	}
	// ... ptrmask を走査して個々のポインタにライトバリアを適用する複雑なロジック ...
}
```

変更後:
```go
func typedmemmove(typ *_type, dst, src unsafe.Pointer) {
	memmove(dst, src, typ.size) // まずはメモリをコピー
	if typ.kind&kindNoPointers != 0 { // ポインタを含まない型ならここで終了
		return
	}
	heapBitsBulkBarrier(uintptr(dst), typ.size) // ヒープビットマップを使ってライトバリアを適用
}
```
この変更により、`typedmemmove`はまず`memmove`で生のバイトコピーを行い、その後、コピー先のメモリ領域全体に対して`heapBitsBulkBarrier`を呼び出すことで、ポインタのライトバリア処理を一括して行います。これにより、`_type`から`ptrmask`を解釈する複雑なロジックが不要になりました。

### `heapBitsBulkBarrier` の導入

`src/runtime/mbitmap.go` に追加された `heapBitsBulkBarrier` 関数は、このコミットの鍵となる新しいコンポーネントです。

```go
// heapBitsBulkBarrier executes writebarrierptr_nostore
// for every pointer slot in the memory range [p, p+size),
// using the heap bitmap to locate those pointer slots.
// This executes the write barriers necessary after a memmove.
// Both p and size must be pointer-aligned.
// The range [p, p+size) must lie within a single allocation.
//
// Callers should call heapBitsBulkBarrier immediately after
// calling memmove(p, src, size). This function is marked nosplit
// to avoid being preempted; the GC must not stop the goroutine
// betwen the memmove and the execution of the barriers.
//go:nosplit
func heapBitsBulkBarrier(p, size uintptr) {
	if (p|size)&(ptrSize-1) != 0 {
		throw("heapBitsBulkBarrier: unaligned arguments")
	}
	if !writeBarrierEnabled || !inheap(p) {
		return
	}

	for i := uintptr(0); i < size; i += ptrSize {
		if heapBitsForAddr(p + i).isPointer() {
			x := (*uintptr)(unsafe.Pointer(p + i))
			writebarrierptr_nostore(x, *x)
		}
	}
}
```
この関数は以下の処理を行います。
1.  引数 `p` (開始アドレス) と `size` (サイズ) がポインタサイズ (`ptrSize`) にアラインされていることを確認します。
2.  ライトバリアが有効でない場合、またはアドレス `p` がヒープ内にない場合は、処理をスキップします。
3.  `p` から `p + size` までのメモリ範囲を `ptrSize` 単位で走査します。
4.  各ポインタサイズのチャンク (`p + i`) について、`heapBitsForAddr(p + i).isPointer()` を呼び出して、そのアドレスがポインタを保持しているかどうかをヒープビットマップから確認します。
5.  もしポインタであれば、そのポインタに対して `writebarrierptr_nostore(x, *x)` を呼び出し、ライトバリアを適用します。`writebarrierptr_nostore` は、ポインタの値を変更する際にGCに通知する役割を果たします。

この`heapBitsBulkBarrier`関数は`//go:nosplit`ディレクティブが付与されており、Goランタイムがこの関数内でスタックを分割しないことを保証しています。これは、`memmove`の直後にライトバリアが中断されずに実行されることを保証し、GCの正確性を維持するために重要です。

### `ptrBitmapForType` の削除

`src/runtime/mbitmap.go` から `ptrBitmapForType` 関数が削除されました。これは、型の`ptrmask`を解釈するロジックが不要になったためです。

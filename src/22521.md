# [インデックス 22521] ファイルの概要

このコミットは、Goコンパイラおよびアセンブラの内部構造における重要な変更を扱っています。具体的には、`cmd/internal/obj`パッケージ内の`Addr`および`Prog`構造体におけるデータ表現の最適化が目的です。

## 元コミット内容

`cmd/internal/obj`パッケージにおいて、`Addr`構造体の`U`フィールド（匿名構造体）を`Val`インターフェースに置き換える変更です。この変更により、元のC言語における共用体（union）の精神に近づき、64ビットシステム上での`Addr`構造体のサイズが120バイトから80バイトに、`Prog`構造体のサイズが592バイトから424バイトに削減されると計算されています。

## 変更の背景

Goコンパイラとアセンブラのバックエンドでは、プログラムの命令やアドレスを表現するために`Addr`と`Prog`という重要なデータ構造が使用されています。これらの構造体は、コンパイル過程で頻繁に生成、操作されるため、そのサイズはコンパイラのメモリ使用量とパフォーマンスに直接影響します。

以前の設計では、`Addr`構造体内に`U`という匿名構造体があり、これがC言語の共用体のように振る舞うことを意図していました。共用体は、異なる型のデータを同じメモリ領域に格納することでメモリを節約する手法ですが、Goの構造体では、匿名構造体内の各フィールドがそれぞれメモリを占有するため、共用体のようなメモリ効率は得られません。

このコミットの背景には、Goコンパイラのメモリフットプリントを削減し、特に大規模なプログラムのコンパイル時におけるパフォーマンスを向上させるという目的があります。`Addr`構造体内の`U`フィールドが、実際にはその中のいずれか一つの値しか使用しないにもかかわらず、全てのフィールド分のメモリを確保してしまうという非効率性がありました。これを`interface{}`型に置き換えることで、必要な時に必要な型の値を動的に保持し、メモリ使用量を最適化することが狙いです。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **Goコンパイラの構造**: Goコンパイラは、フロントエンド（ソースコードの解析、AST生成）、ミドルエンド（最適化）、バックエンド（アセンブリコード生成）に大別されます。`cmd/internal/obj`パッケージは、主にバックエンドの一部であり、アセンブリ命令の抽象的な表現（`Prog`）やオペランド（`Addr`）を定義しています。

2.  **`Prog`構造体**: `Prog`は"Program"の略で、Goコンパイラが生成するアセンブリ命令の抽象的な表現です。各`Prog`インスタンスは、特定のアセンブリ命令（例: `MOV`, `ADD`, `JMP`）とそのオペランド（ソース、デスティネーションなど）を表します。コンパイラは、ASTから`Prog`のリストを生成し、それを最終的な機械語に変換します。

3.  **`Addr`構造体**: `Addr`は"Address"の略で、`Prog`構造体内で使用されるオペランド（命令の対象となるデータやメモリ位置）を表現します。レジスタ、メモリのアドレス、定数、ラベル（分岐先）など、様々な種類のオペランドを表現できる汎用的な構造体です。

4.  **C言語の共用体 (Union)**: C言語における共用体は、複数の異なる型のメンバーを定義できますが、それらのメンバーはメモリ上で同じ開始アドレスを共有します。これにより、共用体のサイズは最も大きいメンバーのサイズとなり、メモリを効率的に利用できます。例えば、あるデータが整数としても浮動小数点数としても扱われる可能性がある場合、共用体を使えば両方の型を保持するのに必要なメモリを節約できます。

5.  **Go言語の`interface{}` (空インターフェース)**: Go言語の`interface{}`は、任意の型の値を保持できる特殊なインターフェースです。内部的には、値の型情報と値そのもの（または値へのポインタ）を保持する2つのワードで構成されます。これにより、異なる型の値を動的に扱うことが可能になります。C言語の共用体とは異なり、`interface{}`は型安全性を保ちつつ、柔軟なデータ表現を可能にします。

6.  **メモリレイアウトとアライメント**: 構造体のメモリ上の配置は、フィールドの順序や型によって決定されます。特に64ビットシステムでは、データのアライメント（特定のバイト境界に配置されること）がパフォーマンスに影響を与えます。構造体内に異なるサイズのフィールドが混在する場合、パディング（未使用のバイト）が挿入され、構造体の実際のサイズがフィールドの合計サイズよりも大きくなることがあります。

## 技術的詳細

このコミットの核心は、`Addr`構造体内の`U`フィールドの変更です。

変更前:
`Addr`構造体には、`U`という匿名構造体が含まれていました。この`U`構造体は、`Sval` (文字列)、`Dval` (float64)、`Branch` (*Prog)、`Argsize` (int32)、`Bits` (uint64) など、複数の異なる型のフィールドを持っていました。`Addr`が表現するオペランドの種類に応じて、これらのフィールドのいずれか一つが有効な値を持つことを意図していました。しかし、Goの構造体はCの共用体とは異なり、匿名構造体内の全てのフィールドがメモリを占有します。したがって、`U`構造体のサイズは、その中で最も大きいフィールド（この場合は`Dval`または`Bits`の8バイト）ではなく、全てのフィールドの合計サイズ（またはアライメントによるパディングを含むサイズ）となっていました。

変更後:
`U`匿名構造体は削除され、代わりに`Val interface{}`というフィールドが導入されました。`interface{}`は任意の型の値を保持できるため、`Sval`、`Dval`、`Branch`、`Argsize`といった異なる種類のデータを、必要に応じて`Val`フィールドに格納できるようになります。

メモリ削減のメカニズム:
Goの`interface{}`は、通常、型情報とデータポインタ（または小さな値の場合は直接データ）の2つのワードで構成されます。64ビットシステムでは、これは通常16バイト（ポインタサイズ×2）です。
変更前は、`Addr.U`が複数のフィールドを保持していたため、そのサイズはこれらのフィールドの合計サイズ（またはアライメントによるパディングを含むサイズ）でした。例えば、`string`はポインタと長さの2ワード、`float64`は1ワード、`*Prog`は1ワード、`int32`は1ワードですが、構造体内の配置とアライメントによって、より多くのメモリが消費されていました。
Russ Cox氏の計算によると、この変更により`Addr`構造体は120バイトから80バイトに、`Prog`構造体は592バイトから424バイトに削減されました。これは、`Addr.U`が占めていたメモリ領域が、`Addr.Val interface{}`の16バイトに置き換わったことによるものです。`Prog`構造体も`Addr`構造体を内部に持っているため、`Addr`のサイズ削減が`Prog`のサイズ削減にも波及しています。

この変更は、コンパイラの内部データ構造のメモリ効率を大幅に向上させ、特に大規模なGoプログラムのコンパイル時間を短縮する効果が期待されます。

	// ... 既存のフィールド ...
	Offset int64
	Width  int64
	Sym    *LSym
	Gotype *LSym

	//	for TYPE_SCONST, a string
	//	for TYPE_FCONST, a float64
	//	for TYPE_BRANCH, a *Prog (optional)

## コアとなるコードの解説

変更の核心は、`Addr`構造体における可変データの表現方法の変更です。

**変更前 (`Addr.U`):**
`Addr`構造体は、アセンブリ命令のオペランドを表すために使用されます。オペランドには、数値定数、浮動小数点定数、文字列定数、分岐先のアドレス（別の`Prog`へのポインタ）、関数引数のサイズなど、様々な種類があります。これらを一つの構造体で表現するために、`U`という匿名構造体が使われていました。

```go
type Addr struct {
    // ...
    U struct {
        Sval    string    // 文字列定数用
        Dval    float64   // 浮動小数点定数用
        Branch  *Prog     // 分岐先命令用
        Argsize int32     // 関数引数サイズ用
        Bits    uint64    // その他のビット値用
    }
    // ...
}
```
この設計では、`Addr`インスタンスがどの種類のオペランドを表すかに関わらず、`U`構造体内の全てのフィールド分のメモリが確保されていました。例えば、`Addr`が整数定数を表す場合でも、`Sval`（文字列）や`Branch`（ポインタ）のためのメモリが確保されてしまい、これはメモリの無駄遣いとなります。

**変更後 (`Addr.Val interface{}`):**
`U`構造体を削除し、代わりに`Val interface{}`を導入しました。

```go
type Addr struct {
    // ...
    Val interface{} // 任意の型の値を保持
    // ...
}
```
`interface{}`は、Goの型システムにおけるポリモーフィズムを実現するための強力な機能です。内部的には、`interface{}`は2つのワード（ポインタ）で構成されます。一つは値の型情報（`_type`ポインタ）、もう一つは値そのもの（または値へのポインタ）です。

*   **値が小さい場合（例: `int32`, `float64`）**: 値は直接`interface{}`のデータ部分に格納されることがあります（スタックに割り当てられる場合など）。
*   **値が大きい場合（例: `string`, `*Prog`）**: 値はヒープに割り当てられ、`interface{}`のデータ部分にはその値へのポインタが格納されます。

この変更により、`Addr`が表現するオペランドの種類に応じて、`Val`フィールドが実際に必要なメモリだけを消費するようになります。例えば、`TYPE_FCONST`（浮動小数点定数）の場合、`Val`には`float64`が格納され、`TYPE_SCONST`（文字列定数）の場合、`Val`には`string`が格納されます。これにより、構造体全体のメモリフットプリントが削減されます。

コードの変更例:
`ptxt.To.U.Argsize = int32(...)`
が
`ptxt.To.Val = int32(...)`
に変わっています。

そして、値の読み出し時には型アサーションが行われます。
`p.From.U.Dval`
が
`p.From.Val.(float64)`
に変わっています。

この変更は、Goコンパイラの内部で頻繁に利用されるデータ構造のメモリ効率を改善し、コンパイラ自体のパフォーマンス向上に寄与するものです。特に、大量の命令やアドレスを処理する際に、メモリ使用量の削減が顕著な効果をもたらします。

`Addr`構造体には、`U`という匿名構造体が含まれていました。この`U`構造体は、`Sval` (文字列)、`Dval` (float64)、`Branch` (*Prog)、`Argsize` (int32)、`Bits` (uint64) など、複数の異なる型のフィールドを持っていました。`Addr`が表現するオペランドの種類に応じて、これらのフィールドのいずれか一つが有効な値を持つことを意図していました。しかし、Goの構造体はCの共用体とは異なり、匿名構造体内の全てのフィールドがメモリを占有します。したがって、`U`構造体のサイズは、その中で最も大きいフィールド（この場合は`Dval`または`Bits`の8バイト）ではなく、全てのフィールドの合計サイズ（またはアライメントによるパディングを含むサイズ）となっていました。

変更後:
`U`匿名構造体は削除され、代わりに`Val interface{}`というフィールドが導入されました。`interface{}`は任意の型の値を保持できるため、`Sval`、`Dval`、`Branch`、`Argsize`といった異なる種類のデータを、必要に応じて`Val`フィールドに格納できるようになります。

メモリ削減のメカニズム:
Goの`interface{}`は、通常、型情報とデータポインタ（または小さな値の場合は直接データ）の2つのワードで構成されます。64ビットシステムでは、これは通常16バイト（ポインタサイズ×2）です。
変更前は、`Addr.U`が複数のフィールドを保持していたため、そのサイズはこれらのフィールドの合計サイズ（またはアライメントによるパディングを含むサイズ）でした。例えば、`string`はポインタと長さの2ワード、`float64`は1ワード、`*Prog`は1ワード、`int32`は1ワードですが、構造体内の配置とアライメントによって、より多くのメモリが消費されていました。
Russ Cox氏の計算によると、この変更により`Addr`構造体は120バイトから80バイトに、`Prog`構造体は592バイトから424バイトに削減されました。これは、`Addr.U`が占めていたメモリ領域が、`Addr.Val interface{}`の16バイトに置き換わったことによるものです。`Prog`構造体も`Addr`構造体を内部に持っているため、`Addr`のサイズ削減が`Prog`のサイズ削減にも波及しています。

この変更は、コンパイラの内部データ構造のメモリ効率を大幅に向上させ、特に大規模なプログラムのコンパイル時間を短縮する効果が期待されます。

## コアとなるコードの変更箇所

このコミットでは、主に`src/cmd/internal/obj/link.go`ファイル内の`Addr`構造体の定義が変更され、それに伴い`Addr.U`を参照していた全ての箇所が`Addr.Val`を参照するように修正されています。

**`src/cmd/internal/obj/link.go` の `Addr` 構造体定義の変更:**

変更前:
```go
type Addr struct {
	// ... 既存のフィールド ...
	Offset int64
	Sym    *LSym
	U      struct {
		Sval    string
		Dval    float64
		Branch  *Prog
		Argsize int32
		Bits    uint64
	}
	Gotype *LSym
	Class  int8
	Etype  uint8
	Node   interface{}
	Width  int64
}
```

変更後:
```go
type Addr struct {
	// ... 既存のフィールド ...
	Offset int64
	Width  int64
	Sym    *LSym
	Gotype *LSym

	// argument value:
	//	for TYPE_SCONST, a string
	//	for TYPE_FCONST, a float64
	//	for TYPE_BRANCH, a *Prog (optional)
	//	for TYPE_TEXTSIZE, an int32 (optional)
	Val interface{}

	Node interface{} // for use by compiler
}
```

この変更に伴い、`Addr.U.Sval`のようなアクセスは`Addr.Val.(string)`のように型アサーションを伴うアクセスに、`Addr.U.Dval`は`Addr.Val.(float64)`に、`Addr.U.Branch`は`Addr.Val.(*Prog)`に、`Addr.U.Argsize`は`Addr.Val.(int32)`に変更されています。

影響を受けるファイルは多岐にわたり、`src/cmd/5g/ggen.go`、`src/cmd/6g/ggen.go`、`src/cmd/internal/gc/gsubr.go`、`src/cmd/internal/obj/arm/asm5.go`など、Goコンパイラの各アーキテクチャ固有のコード生成部分や、共通のオブジェクトファイル操作ロジック、さらには古いアセンブラのパーサー（`src/cmd/old5a/a.y`など）まで、合計33ファイルにわたって変更が加えられています。これは、`Addr`構造体がGoコンパイラとアセンブラの非常に低レベルな部分で広く利用されていることを示しています。

## コアとなるコードの解説

変更の核心は、`Addr`構造体における可変データの表現方法の変更です。

**変更前 (`Addr.U`):**
`Addr`構造体は、アセンブリ命令のオペランドを表すために使用されます。オペランドには、数値定数、浮動小数点定数、文字列定数、分岐先のアドレス（別の`Prog`へのポインタ）、関数引数のサイズなど、様々な種類があります。これらを一つの構造体で表現するために、`U`という匿名構造体が使われていました。

```go
type Addr struct {
    // ...
    U struct {
        Sval    string    // 文字列定数用
        Dval    float64   // 浮動小数点定数用
        Branch  *Prog     // 分岐先命令用
        Argsize int32     // 関数引数サイズ用
        Bits    uint64    // その他のビット値用
    }
    // ...
}
```
この設計では、`Addr`インスタンスがどの種類のオペランドを表すかに関わらず、`U`構造体内の全てのフィールド分のメモリが確保されていました。例えば、`Addr`が整数定数を表す場合でも、`Sval`（文字列）や`Branch`（ポインタ）のためのメモリが確保されてしまい、これはメモリの無駄遣いとなります。

**変更後 (`Addr.Val interface{}`):**
`U`構造体を削除し、代わりに`Val interface{}`を導入しました。

```go
type Addr struct {
    // ...
    Val interface{} // 任意の型の値を保持
    // ...
}
```
`interface{}`は、Goの型システムにおけるポリモーフィズムを実現するための強力な機能です。内部的には、`interface{}`は2つのワード（ポインタ）で構成されます。一つは値の型情報（`_type`ポインタ）、もう一つは値そのもの（または値へのポインタ）です。

*   **値が小さい場合（例: `int32`, `float64`）**: 値は直接`interface{}`のデータ部分に格納されることがあります（スタックに割り当てられる場合など）。
*   **値が大きい場合（例: `string`, `*Prog`）**: 値はヒープに割り当てられ、`interface{}`のデータ部分にはその値へのポインタが格納されます。

この変更により、`Addr`が表現するオペランドの種類に応じて、`Val`フィールドが実際に必要なメモリだけを消費するようになります。例えば、`TYPE_FCONST`（浮動小数点定数）の場合、`Val`には`float64`が格納され、`TYPE_SCONST`（文字列定数）の場合、`Val`には`string`が格納されます。これにより、構造体全体のメモリフットプリントが削減されます。

コードの変更例:
`ptxt.To.U.Argsize = int32(...)`
が
`ptxt.To.Val = int32(...)`
に変わっています。

そして、値の読み出し時には型アサーションが行われます。
`p.From.U.Dval`
が
`p.From.Val.(float64)`
に変わっています。

この変更は、Goコンパイラの内部で頻繁に利用されるデータ構造のメモリ効率を改善し、コンパイラ自体のパフォーマンス向上に寄与するものです。特に、大量の命令やアドレスを処理する際に、メモリ使用量の削減が顕著な効果をもたらします。

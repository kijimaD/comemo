## 変更の背景

このコミットは、Goの `net/url` パッケージにおけるURL解析の回帰バグを修正するために導入されました。具体的には、URLのクエリ部分が疑問符（`?`）で終わる場合に、そのURLが正しく解析されないという問題（Issue 14573）が発生していました。

この問題は、以前のコミット（CL 19931）で `URL.ForceQuery` フィールドが `net/url.URL` 構造体に追加されたことによって引き起こされた回帰でした。`URL.ForceQuery` は、`URL.RawQuery` が空であっても、`URL.String()` メソッドがURLの末尾に疑問符を強制的に追加するかどうかを制御するためのフィールドです。例えば、`http://example.com?` のようなURLを表現するために使用されます。

しかし、この `ForceQuery` の導入に伴うURL解析ロジックの変更が、クエリ文字列自体が疑問符で終わるようなエッジケース（例: `http://www.google.com/?foo=bar?`）で誤動作を引き起こしました。本来クエリ文字列の一部であるはずの末尾の疑問符が、`ForceQuery` の判定ロジックによって誤って解釈され、URLの構造が崩れてしまう可能性がありました。このコミットは、この誤った解釈を修正し、URLの意図された構造を維持することを目的としています。

## 前提知識の解説

### URLの構造と疑問符（`?`）の役割

Uniform Resource Locator (URL) は、インターネット上のリソースを一意に識別するための文字列です。一般的なURLの構造は以下のようになります。

`scheme://host:port/path?query#fragment`

ここで、疑問符（`?`）はURLのパス部分とクエリ部分を区切るセパレータとして機能します。疑問符の後に続く文字列はクエリ文字列と呼ばれ、通常はキーと値のペア（例: `key1=value1&key2=value2`）で構成され、サーバーに渡される追加情報を含みます。

### Goの `net/url` パッケージ

Go言語の `net/url` パッケージは、URLの解析、生成、および操作のための機能を提供します。このパッケージの中心となるのは `url.URL` 構造体で、URLの各コンポーネント（スキーム、ホスト、パス、クエリ、フラグメントなど）をフィールドとして保持します。

```go
type URL struct {
    Scheme     string
    Opaque     string    // encoded opaque data
    User       *Userinfo // username and password information
    Host       string    // host or host:port
    Path       string    // path (relative paths may omit leading slash)
    RawPath    string    // encoded path hint (see EscapedPath method)
    ForceQuery bool      // append a literal '?' even if RawQuery is empty
    RawQuery   string    // encoded query values, without '?'
    Fragment   string    // fragment for references, without '#'
    RawFragment string   // encoded fragment hint (see EscapedFragment method)
}
```

### `URL.ForceQuery` フィールド

`URL.ForceQuery` は、`net/url.URL` 構造体に追加されたブール型のフィールドです。このフィールドが `true` に設定されている場合、`URL.String()` メソッド（`URL` 構造体を文字列形式のURLに変換するメソッド）は、`RawQuery` フィールドが空であっても、URLの末尾にリテラルの疑問符（`?`）を強制的に追加します。

例えば、`URL{Scheme: "http", Host: "example.com", ForceQuery: true}` の場合、`URL.String()` は `http://example.com?` を返します。これは、クエリパラメータがないことを明示的に示すために使用されることがあります。

### 回帰バグ (Regression Bug)

回帰バグとは、ソフトウェアの変更（新機能の追加や既存機能の修正など）によって、以前は正しく動作していた機能が動作しなくなる、または誤動作するようになるバグのことです。このコミットで修正された問題は、`URL.ForceQuery` の導入という変更によって引き起こされたため、回帰バグとされています。

## 技術的詳細

このコミットで修正された問題は、`net/url` パッケージの `parse` 関数における `ForceQuery` の判定ロジックにありました。

元のコードでは、URLの残りの部分（`rest` 変数）が疑問符で終わる場合、無条件に `url.ForceQuery = true` を設定し、末尾の疑問符を `rest` から削除していました。

```go
// 変更前
if strings.HasSuffix(rest, "?") {
    url.ForceQuery = true
    rest = rest[:len(rest)-1]
} else {
    // ...
}
```

このロジックは、`http://example.com?` のようにクエリ文字列が空で、末尾に疑問符があるケースを正しく処理するために導入されました。しかし、`http://www.google.com/?foo=bar?` のように、クエリ文字列自体が疑問符で終わる場合、問題が発生しました。

このURLを解析する際、`rest` 変数には `foo=bar?` が含まれる可能性があります。元のロジックでは、`strings.HasSuffix(rest, "?")` が `true` となり、`url.ForceQuery` が `true` に設定され、`rest` から末尾の疑問符が削除されて `foo=bar` となってしまいます。その結果、`RawQuery` には `foo=bar` が格納され、`ForceQuery` が `true` になるため、`URL.String()` を呼び出すと `http://www.google.com/?foo=bar?` ではなく `http://www.google.com/?foo=bar` となってしまい、元のURLの意図が失われる可能性がありました。

このコミットでは、この誤った解釈を防ぐために、`ForceQuery` を設定する条件に `strings.Count(rest, "?") == 1` という条件を追加しました。

```go
// 変更後
if strings.HasSuffix(rest, "?") && strings.Count(rest, "?") == 1 {
    url.ForceQuery = true
    rest = rest[:len(rest)-1]
} else {
    // ...
}
```

この変更により、`rest` の中に疑問符が1つしかなく、かつそれが末尾にある場合にのみ `ForceQuery` が `true` に設定されるようになりました。これにより、`http://www.google.com/?foo=bar?` のようなURLでは、`rest` には `?foo=bar?` が含まれ、`strings.Count(rest, "?")` は `2` となるため、この `if` 文の条件は `false` となります。結果として、`ForceQuery` は設定されず、`?foo=bar?` は正しくクエリ文字列として処理され、`RawQuery` に `foo=bar?` が格納されるようになります。

## コアとなるコードの解説

### `src/net/url/url.go` の変更

`parse` 関数の以下の行が変更されました。

```go
-	if strings.HasSuffix(rest, "?") {
+	if strings.HasSuffix(rest, "?") && strings.Count(rest, "?") == 1 {
```

この変更は、`ForceQuery` フィールドを設定する条件をより厳密にするものです。
- `strings.HasSuffix(rest, "?")`: これは、`rest` 文字列が疑問符で終わるかどうかをチェックします。
- `strings.Count(rest, "?") == 1`: これは、`rest` 文字列内に疑問符がちょうど1つだけ存在するかどうかをチェックします。

この二つの条件を `&&` (AND) で結合することで、`rest` 文字列が「末尾に疑問符があり、かつその疑問符が文字列内で唯一の疑問符である」場合にのみ `url.ForceQuery = true` が実行されるようになります。

これにより、`http://example.com?` のようなURLでは、`rest` が `?` となり、両方の条件が満たされるため `ForceQuery` が正しく設定されます。
一方、`http://www.google.com/?foo=bar?` のようなURLでは、`rest` が `?foo=bar?` となり、`strings.Count(rest, "?")` は `2` となるため、二つ目の条件が `false` となり、`ForceQuery` は設定されません。これにより、`foo=bar?` が `RawQuery` として正しく保持され、URLの意図が維持されます。

### `src/net/url/url_test.go` の変更

新しいテストケースが `urltests` スライスに追加されました。

```go
	// query ending in question mark (Issue 14573)
	{
		"http://www.google.com/?foo=bar?",
		&URL{
			Scheme:   "http",
			Host:     "www.google.com",
			Path:     "/",
			RawQuery: "foo=bar?",
		},
		"",
	},
```

このテストケースは、まさにこのコミットが修正しようとしているシナリオをカバーしています。
- 入力URL: `"http://www.google.com/?foo=bar?"`
- 期待される解析結果: `Scheme` は `"http"`, `Host` は `"www.google.com"`, `Path` は `"/"`, そして最も重要な `RawQuery` は `"foo=bar?"` となるべきです。

このテストケースが追加されたことで、将来的に同様の回帰バグが発生した場合に、テストによって早期に検出できるようになります。

また、`ufmt` 関数（テストユーティリティ関数）の `fmt.Sprintf` フォーマット文字列に `forcequery=%v` が追加され、`u.ForceQuery` の値も出力されるようになりました。これは、`ForceQuery` の状態がテスト結果に反映されるようにするための変更であり、デバッグやテストの可読性向上に役立ちます。

# [インデックス 25469] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) におけるシンボルテーブルのエントリ重複の問題を修正するものです。具体的には、グローバル関数に対してローカルシンボルが追加される際に、誤ってグローバルシンボルも重複して登録されてしまうバグを解消します。この修正は、`src/cmd/link/internal/ld/symtab.go` ファイル内の `putelfsym` 関数に `return` ステートメントを追加することで行われています。

## 変更の背景

この変更は、以前のコミット `golang.org/cl/16436` によって導入されたバグを修正するために行われました。この以前の変更では、すべてのグローバル関数に対してローカルシンボルが追加されるようになりました。これはデバッグ情報やリンカの内部処理において有用な場合があります。しかし、その実装に不備があり、ローカルシンボルを追加する際に、対応するグローバルシンボルも誤って重複してシンボルテーブルに登録してしまう問題が発生していました。

コミットメッセージによると、この重複が「驚くべきことに目立った問題を引き起こしていなかった」とされていますが、それでも「間違っている」という認識から修正が決定されました。シンボルテーブルの重複エントリは、リンカの動作の予測不能性、デバッグツールの混乱、あるいは将来的な互換性の問題を引き起こす可能性があるため、たとえ即座に問題が発生していなくても修正されるべきです。

## 前提知識の解説

### Go言語のツールチェインとリンカ (`cmd/link`)

Go言語のプログラムが実行可能ファイルになるまでには、いくつかの段階があります。
1.  **コンパイラ (`cmd/compile`)**: Goのソースコードをアセンブリコード（または中間コード）に変換します。
2.  **アセンブラ (`cmd/asm`)**: アセンブリコードをオブジェクトファイル（`.o` または `.a`）に変換します。
3.  **リンカ (`cmd/link`)**: 複数のオブジェクトファイルやライブラリを結合し、最終的な実行可能ファイルを生成します。この過程で、各関数や変数などのシンボルが解決され、メモリ上のアドレスが割り当てられます。

`cmd/link` は、Goプログラムのビルドプロセスにおいて非常に重要な役割を担っています。

### シンボルテーブル

シンボルテーブルは、コンパイルおよびリンクの過程で生成されるデータ構造で、プログラム内のすべてのシンボル（関数名、変数名など）とその属性（アドレス、サイズ、型、結合性など）を記録します。リンカはシンボルテーブルを参照して、未解決の参照を解決し、プログラムの各部分を正しく結合します。

### シンボルの結合性 (Binding)

シンボルには「結合性 (Binding)」という属性があり、そのシンボルがプログラムの他の部分からどのように参照可能であるかを定義します。主な結合性には以下のものがあります。

*   **`STB_GLOBAL` (Global Binding)**: シンボルは、リンクされるすべてのオブジェクトファイルから参照可能です。これは、外部からアクセス可能な関数やグローバル変数に適用されます。
*   **`STB_LOCAL` (Local Binding)**: シンボルは、それが定義されているオブジェクトファイル内でのみ参照可能です。他のオブジェクトファイルからは直接参照できません。静的変数やファイルスコープの関数などに適用されます。

ELF (Executable and Linkable Format) などの実行可能ファイルフォーマットでは、これらの結合性がシンボルテーブルエントリの一部として記録されます。

### `putelfsym` 関数

`putelfsym` は、Goリンカの内部でELF形式のシンボルテーブルエントリを生成・追加する役割を持つ関数です。この関数は、与えられたシンボル情報 (`LSym`) を基に、ELFシンボルテーブルの適切なエントリを作成します。

## 技術的詳細

このコミットの技術的な核心は、リンカがシンボルテーブルにエントリを追加する際のロジックの修正にあります。

以前の `golang.org/cl/16436` の変更により、グローバル関数であっても、デバッグ情報などの目的でその関数のローカルな表現（`local.FunctionName`のような名前を持つシンボル）がシンボルテーブルに追加されるようになりました。この処理は `putelfsyment(putelfstr("local."+s), addr, size, STB_LOCAL<<4|type_&0xf, elfshnum, other)` の行で行われています。ここで `STB_LOCAL` が指定されていることから、これはローカルシンボルとして扱われるべきものです。

問題は、このローカルシンボルが追加された後も、関数がグローバルである場合の通常の処理フローが継続され、結果として同じグローバル関数に対して `STB_GLOBAL` の結合性を持つエントリが再度追加されてしまっていた点です。これにより、シンボルテーブルには同じグローバル関数を指す2つのエントリ（一つはローカル、もう一つはグローバル）が存在することになります。

このコミットでは、ローカルシンボルが正常に追加された直後に `return` ステートメントを追加することで、この重複を防いでいます。

```go
		putelfsyment(putelfstr("local."+s), addr, size, STB_LOCAL<<4|type_&0xf, elfshnum, other)
		x.LocalElfsym = int32(numelfsym)
		numelfsym++
		return // ここで処理を終了し、グローバルシンボルの追加をスキップ
	} else if bind != elfbind {
		return
	}
```

この `return` が追加されることで、`if` ブロック内の条件（おそらくシンボルが特定の条件を満たし、ローカルシンボルとして扱われるべき場合）が真であるときに、その後のグローバルシンボルを追加するロジックが実行されなくなります。これにより、シンボルテーブルの整合性が保たれ、不要な重複が解消されます。

## コアとなるコードの解説

`putelfsym` 関数は、GoリンカがELF形式の実行可能ファイルを生成する際に、シンボルテーブルにエントリを追加するために使用されます。

変更箇所の周辺コードは以下のようになっています（簡略化）。

```go
func putelfsym(...) {
    // ...
    if /* 特定の条件（おそらくシンボルがローカルとして扱われるべき場合） */ {
        // ローカルシンボルエントリを追加
        putelfsyment(putelfstr("local."+s), addr, size, STB_LOCAL<<4|type_&0xf, elfshnum, other)
        x.LocalElfsym = int32(numelfsym)
        numelfsym++
        return // ★この行が追加された
    } else if bind != elfbind {
        return
    }
    // ...
    // ここにグローバルシンボルを追加するロジックが続く
    // ...
}
```

追加された `return` ステートメントは、`if` ブロックの条件が満たされ、ローカルシンボルが正常にシンボルテーブルに追加された場合に、それ以降の `putelfsym` 関数の処理を即座に終了させます。これにより、同じグローバル関数に対して、ローカルシンボルが追加された後に、さらにグローバルシンボルが重複して追加されることを防ぎます。

この修正は、リンカが生成する実行可能ファイルのシンボルテーブルの正確性と整合性を保証するために重要です。

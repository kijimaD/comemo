# [インデックス 26668] ファイルの概要

このコミットは、Go言語の `net` パッケージにおける静的ホストルックアップ機能の脆弱性を修正するものです。具体的には、`lookupStaticHost` および `lookupStaticAddr` 関数が内部キャッシュのスライスを直接返していたため、外部からの変更によってキャッシュが破損する可能性があった問題を解決します。この修正は、これらの関数がスライスのコピーを返すようにすることで、内部データの整合性を保護します。

## 元コミット内容

`net` パッケージにおいて、`lookupStaticHost` および `lookupStaticAddr` 関数がスライスのコピーを返すように変更し、キャッシュの破損を防ぐ。
Issue #14212 を修正。

## 変更の背景

この変更は、Go言語の `net` パッケージにおける静的ホストルックアップ機能の潜在的なバグ、具体的には [Issue #14212](https://github.com/golang/go/issues/14212) に対応するものです。この問題は、`net` パッケージが内部的に管理している静的ホスト情報（`/etc/hosts` ファイルなどから読み込まれる情報）をキャッシュする際に発生しました。

以前の実装では、`lookupStaticHost` や `lookupStaticAddr` といった関数が、内部キャッシュに格納されているIPアドレスやホスト名のスライスを直接呼び出し元に返していました。Goのスライスは参照型であるため、この動作はセキュリティ上およびデータ整合性上のリスクをはらんでいました。具体的には、これらの関数から返されたスライスを呼び出し元が変更した場合、その変更が内部キャッシュにも反映されてしまい、予期せぬデータの破損や誤ったホスト解決結果を引き起こす可能性がありました。

このようなキャッシュの破損は、ネットワーク通信の信頼性を損ない、アプリケーションの誤動作やセキュリティ脆弱性につながる恐れがあるため、早急な修正が必要とされました。このコミットは、この根本原因に対処し、内部キャッシュの安全性を確保することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とネットワークに関する知識が役立ちます。

1.  **Goのスライス (Slice)**:
    Goのスライスは、配列のセグメントを参照するデータ構造です。スライス自体はヘッダ（ポインタ、長さ、容量）であり、基盤となる配列のデータを直接保持しているわけではありません。そのため、スライスを関数に渡したり、関数から返したりすると、そのスライスが参照する基盤配列へのアクセスが共有されます。もし関数がスライスを直接返した場合、呼び出し元はそのスライスを通じて基盤配列の要素を変更でき、その変更は他のスライス参照にも影響を与えます。これを「参照渡し」の特性と呼びます。

2.  **防御的コピー (Defensive Copying)**:
    防御的コピーとは、オブジェクトやデータ構造を返す際に、その内部状態が外部から変更されるのを防ぐために、オリジナルのコピーを返すプログラミングパターンです。特に、ミュータブル（変更可能）なデータ構造（Goのスライスやマップなど）を扱う場合に重要となります。これにより、内部データが意図せず変更されることによるバグやセキュリティリスクを防ぎ、カプセル化を強化できます。

3.  **`/etc/hosts` ファイルと静的ホスト解決**:
    `/etc/hosts` ファイルは、IPアドレスとホスト名のマッピングを定義するローカルファイルです。DNS（Domain Name System）よりも優先してホスト名の解決に使用されることが多く、特定のホスト名を特定のIPアドレスに強制的に解決させたい場合や、DNSが利用できない環境で利用されます。Goの `net` パッケージは、この `/etc/hosts` ファイルの内容を読み込み、内部キャッシュとして利用してホスト解決のパフォーマンスを向上させています。

4.  **キャッシュの整合性**:
    キャッシュは、頻繁にアクセスされるデータを一時的に保存し、アクセス速度を向上させるための仕組みです。キャッシュのデータが最新で正確であることが「キャッシュの整合性」と呼ばれます。キャッシュされたデータが外部からの意図しない変更によって破損すると、アプリケーションは古い、または誤ったデータに基づいて動作し、深刻な問題を引き起こす可能性があります。

## 技術的詳細

このコミットの技術的な核心は、Goのスライスの参照渡し特性と、それによって引き起こされる内部キャッシュの破損リスクへの対処です。

`src/net/hosts.go` ファイルには、`/etc/hosts` ファイルの内容を解析し、ホスト名からIPアドレス、またはIPアドレスからホスト名を解決するためのロジックが含まれています。このファイル内で、`hosts` 構造体は静的ホスト情報を `byName` (ホスト名からIPアドレスのスライスへのマップ) と `byAddr` (IPアドレスからホスト名のスライスへのマップ) としてキャッシュしています。

問題となっていたのは、`lookupStaticHost` 関数（ホスト名からIPアドレスのスライスを返す）と `lookupStaticAddr` 関数（IPアドレスからホスト名のスライスを返す）の実装でした。これらの関数は、内部キャッシュ (`hosts.byName` や `hosts.byAddr`) から取得したスライスをそのまま `return` していました。

```go
// 変更前 (lookupStaticHostの例)
if ips, ok := hosts.byName[absDomainName(lowerHost)]; ok {
    return ips // 内部スライスへの直接参照を返している
}

// 変更前 (lookupStaticAddrの例)
if hosts, ok := hosts.byAddr[addr]; ok {
    return hosts // 内部スライスへの直接参照を返している
}
```

このコードでは、`ips` や `hosts` は内部キャッシュのスライスへの参照です。もし呼び出し元が `return ips` で受け取ったスライスに対して `ips[0] = "modified"` のような操作を行った場合、内部キャッシュのデータも変更されてしまいます。これは、`net` パッケージが意図しないデータの変更を許容することになり、キャッシュの整合性が失われる原因となります。

このコミットでは、この問題を解決するために「防御的コピー」の原則を適用しています。具体的には、内部キャッシュからスライスを取得した後、新しいスライスを作成し、元のスライスの内容を新しいスライスにコピーしてから、そのコピーを返すように変更されました。

```go
// 変更後 (lookupStaticHostの例)
if ips, ok := hosts.byName[absDomainName(lowerHost)]; ok {
    ipsCp := make([]string, len(ips)) // 新しいスライスを作成
    copy(ipsCp, ips)                 // 内容をコピー
    return ipsCp                     // コピーしたスライスを返す
}

// 変更後 (lookupStaticAddrの例)
if hosts, ok := hosts.byAddr[addr]; ok {
    hostsCp := make([]string, len(hosts)) // 新しいスライスを作成
    copy(hostsCp, hosts)                   // 内容をコピー
    return hostsCp                         // コピーしたスライスを返す
}
```

`make([]string, len(ips))` は、元のスライス `ips` と同じ長さの新しいスライス `ipsCp` を作成します。`copy(ipsCp, ips)` は、`ips` の要素を `ipsCp` にコピーします。これにより、`lookupStaticHost` や `lookupStaticAddr` が返すスライスは、内部キャッシュとは独立した新しいメモリ領域を持つため、呼び出し元がそのスライスを変更しても、内部キャッシュのデータには影響が及ばなくなります。

また、`src/net/hosts_test.go` には、この修正が正しく機能することを検証するための新しいテストケース `TestHostCacheModification` が追加されました。このテストは、意図的に `lookupStaticHost` や `lookupStaticAddr` から返されたスライスを変更し、その後再度同じルックアップを実行して、内部キャッシュが破損していないことを確認します。これにより、将来的に同様の問題が再発するのを防ぐための強力なセーフティネットが提供されます。

## コアとなるコードの解説

### `src/net/hosts.go` の変更点

`lookupStaticHost` 関数と `lookupStaticAddr` 関数は、それぞれホスト名からIPアドレスのリスト、またはIPアドレスからホスト名のリストを返す役割を担っています。これらの関数は、内部の `hosts` 構造体（静的ホスト情報をキャッシュしている）から対応するスライスを取得します。

変更前は、これらの関数は `return ips` や `return hosts` のように、内部キャッシュから取得したスライスをそのまま返していました。Goのスライスは参照型であるため、これにより呼び出し元は内部キャッシュの基盤となる配列への直接参照を受け取ることになります。結果として、呼び出し元が返されたスライスの要素を変更すると、内部キャッシュのデータも変更されてしまい、キャッシュの整合性が損なわれる可能性がありました。

このコミットでは、この問題を解決するために以下のコードが追加されました。

```go
// lookupStaticHost 内の変更
ipsCp := make([]string, len(ips))
copy(ipsCp, ips)
return ipsCp

// lookupStaticAddr 内の変更
hostsCp := make([]string, len(hosts))
copy(hostsCp, hosts)
return hostsCp
```

1.  `make([]string, len(ips))` (または `make([]string, len(hosts))`)：
    これは、元のスライス `ips` (または `hosts`) と同じ長さを持つ新しいスライス `ipsCp` (または `hostsCp`) を作成します。この新しいスライスは、元のスライスとは異なるメモリ領域に割り当てられます。

2.  `copy(ipsCp, ips)` (または `copy(hostsCp, hosts)`)：
    これは、元のスライス `ips` (または `hosts`) のすべての要素を、新しく作成されたスライス `ipsCp` (または `hostsCp`) にコピーします。これにより、値渡しに近い形でデータが複製されます。

これらの変更により、`lookupStaticHost` および `lookupStaticAddr` 関数は、内部キャッシュのデータへの直接参照ではなく、そのデータの独立したコピーを返すようになります。したがって、呼び出し元が返されたスライスを変更しても、内部キャッシュのデータは安全に保護され、意図しないキャッシュの破損が防止されます。これは、Goにおける防御的コピーの典型的な適用例です。

### `src/net/hosts_test.go` の変更点

テストファイルでは、主に以下の変更が行われました。

1.  **ヘルパー関数の導入**:
    `TestLookupStaticHost` と `TestLookupStaticAddr` のテストロジックが、それぞれ `testStaticHost` と `testStaticAddr` というヘルパー関数に抽出されました。これにより、テストコードの重複が削減され、可読性と保守性が向上しています。

2.  **`TestHostCacheModification` の追加**:
    このコミットの最も重要なテスト関連の変更は、`TestHostCacheModification` という新しいテスト関数の追加です。このテストは、Issue #14212 で報告されたキャッシュ破損のシナリオを明示的に検証するために設計されました。

    *   テストはまず、`lookupStaticHost` または `lookupStaticAddr` を呼び出してスライスを取得します。
    *   次に、取得したスライスの要素を意図的に変更します（例: `addrs[i] += "junk"`）。
    *   その後、再度同じルックアップを実行し、変更前の期待される結果 (`ent.out`) と比較します。
    *   もし、内部キャッシュが正しく保護されていれば、2回目のルックアップは変更の影響を受けず、元の正しい結果を返すはずです。このテストは、その挙動を `reflect.DeepEqual` を用いて検証しています。

この新しいテストケースは、防御的コピーが正しく機能し、内部キャッシュが外部からの変更に対して堅牢であることを保証するための重要な安全策となります。

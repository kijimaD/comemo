## 変更の背景

この変更の背景には、Go言語の標準ライブラリである`flag`パッケージの進化があります。Go 1.5のリリースに向けて、`flag`パッケージの`Usage`メッセージの表示方法に一貫性を持たせるための変更が加えられました。

以前の`flag`パッケージでは、フラグの引数名と説明をコロンで区切る`"arg: description"`という形式が推奨されていました。しかし、この形式は冗長であり、特に引数名が自明である場合や、フラグの型から引数名が推測できる場合には、ユーザーにとって余分な情報となる可能性がありました。

Go 1.5では、`flag`パッケージが内部的に引数名を自動的に補完するようになり、開発者はフラグの説明のみを提供すればよくなりました。これにより、`flag.StringVar`や`flag.IntVar`などの関数に渡す説明文字列から、明示的な引数名を削除することが可能になりました。

このコミットは、Goツールチェインの中核をなすコンパイラ（`gc`）とリンカ（`ld`）が、この新しい`flag`パッケージの規約に準拠するように更新するものです。これにより、Go 1.5以降のGoツールチェイン全体で、コマンドラインフラグのヘルプメッセージの表示が一貫し、より簡潔で読みやすくなります。

具体的には、この変更はGo issue #10505「cmd/go: flag usage messages should not include arg name」を修正するものです。このissueでは、`go build`などのコマンドのヘルプメッセージが、`flag`パッケージの新しい慣習に合わせて更新されるべきだと指摘されていました。

## 前提知識の解説

### Go言語の`flag`パッケージ

Go言語の標準ライブラリには、コマンドライン引数をパースするための`flag`パッケージが含まれています。このパッケージを使用することで、開発者は簡単にコマンドラインフラグを定義し、その値をプログラム内で利用できます。

`flag`パッケージの基本的な使い方としては、以下のような関数があります。

*   `flag.StringVar(p *string, name string, value string, usage string)`: 文字列型のフラグを定義します。`p`はフラグの値を格納する変数へのポインタ、`name`はフラグ名（例: `-o`）、`value`はデフォルト値、`usage`はフラグの説明です。
*   `flag.IntVar(p *int, name string, value int, usage string)`: 整数型のフラグを定義します。
*   `flag.BoolVar(p *bool, name string, value bool, usage string)`: 真偽値型のフラグを定義します。
*   `flag.Parse()`: 定義されたフラグをコマンドライン引数からパースします。

このコミットで焦点となっているのは、`usage`引数に渡される文字列の形式です。

### Goツールチェインの構成要素

Go言語のビルドシステムは、複数のツールで構成されています。このコミットで言及されている主要なツールは以下の通りです。

*   **`cmd/internal/gc` (Go Compiler)**: Goのソースコードをコンパイルしてオブジェクトファイルを生成するコンパイラです。Go 1.5以降、このコンパイラはGo言語で書かれるようになりました（以前はC言語で書かれていました）。
*   **`cmd/internal/ld` (Go Linker)**: コンパイラによって生成されたオブジェクトファイルやライブラリをリンクして、実行可能ファイルを生成するリンカです。

これらのツールも、それぞれが独自のコマンドラインフラグを持っており、`flag`パッケージを使用してそれらを定義しています。

### コマンドライン引数のヘルプメッセージの慣習

多くのコマンドラインツールでは、`-h`や`--help`といったフラグを指定することで、利用可能なオプションとその説明を表示します。このヘルプメッセージの形式は、ユーザーがツールを効果的に利用するために非常に重要です。一貫性のある、簡潔で分かりやすいヘルプメッセージは、ユーザーエクスペリエンスを向上させます。

このコミットは、Goツールチェインのヘルプメッセージの「慣習」を、`flag`パッケージの新しい設計思想に合わせて更新するものです。

## 技術的詳細

このコミットの技術的な変更は、主にGoコンパイラ（`src/cmd/internal/gc/lex.go`）とGoリンカ（`src/cmd/internal/ld/pobj.go`）のソースコード内の、`obj.Flagstr`, `obj.Flagfn1`, `obj.Flagint64`, `obj.Flagint32`などのフラグ定義における`usage`文字列の修正です。

Go 1.5の`flag`パッケージの変更により、フラグの`usage`文字列に引数名を含める必要がなくなりました。例えば、以前は以下のような形式でした。

```go
obj.Flagstr("D", "path: set relative path for local imports", &localimport)
```

ここで、`"path: set relative path for local imports"`という文字列は、フラグ`-D`が`path`という引数を取ることを明示的に示していました。しかし、Go 1.5の`flag`パッケージは、フラグの型（この場合は`string`）から引数名を自動的に推測し、ヘルプメッセージに表示するようになりました。そのため、`usage`文字列からは引数名を削除し、説明のみを記述するようになりました。

```go
obj.Flagstr("D", "set relative path for local imports", &localimport)
```

この変更は、`flag`パッケージの内部的な改善によるもので、`flag`パッケージがよりスマートにヘルプメッセージを生成するようになった結果です。これにより、開発者はより簡潔な`usage`文字列を記述できるようになり、コードの可読性も向上します。

このコミットでは、`gc`と`ld`の両方で、このようなパターンに合致するすべてのフラグ定義が修正されています。これにより、GoツールチェインのヘルプメッセージがGo 1.5の新しい標準に準拠し、ユーザーにとってよりクリーンな表示が提供されます。

## コアとなるコードの解説

このコミットにおけるコードの変更は、Goの`flag`パッケージの`usage`文字列の慣習の変更に直接対応するものです。

Goの`flag`パッケージは、コマンドラインフラグを定義する際に、そのフラグがどのような引数を取るか（例: 文字列、整数、ファイルパスなど）を型情報から認識します。Go 1.5以前は、`flag.StringVar`などの関数に渡す`usage`文字列に、引数名（例: `path`、`file`）とコロンを含めることで、ヘルプメッセージにその引数名が表示されるようにしていました。

しかし、Go 1.5の`flag`パッケージの内部的な改善により、この引数名を`usage`文字列に含める必要がなくなりました。`flag`パッケージは、フラグの型に基づいて適切な引数名（例: `[string]`、`[int]`、`[bool]`など）を自動的に生成し、ヘルプメッセージに表示するようになりました。

したがって、このコミットで行われた変更は、単に`usage`文字列から冗長な引数名とコロンを削除する作業です。例えば、`"path: set relative path for local imports"`という文字列は、`"set relative path for local imports"`に変更されました。これにより、`flag`パッケージが自動的に生成する引数名と組み合わされて、最終的なヘルプメッセージはより簡潔になります。

この変更は、機能的な動作には影響を与えません。コンパイラやリンカのフラグの動作自体は変わらず、単にヘルプメッセージの表示形式が改善されるだけです。これは、Goツールチェイン全体のユーザーエクスペリエンスと一貫性を向上させるための、クリーンアップ作業と位置づけられます。

## コアとなるコードの解説

このコミットにおけるコードの変更は、Goの`flag`パッケージの`usage`文字列の慣習の変更に直接対応するものです。

Goの`flag`パッケージは、コマンドラインフラグを定義する際に、そのフラグがどのような引数を取るか（例: 文字列、整数、ファイルパスなど）を型情報から認識します。Go 1.5以前は、`flag.StringVar`などの関数に渡す`usage`文字列に、引数名（例: `path`、`file`）とコロンを含めることで、ヘルプメッセージにその引数名が表示されるようにしていました。

しかし、Go 1.5の`flag`パッケージの内部的な改善により、この引数名を`usage`文字列に含める必要がなくなりました。`flag`パッケージは、フラグの型に基づいて適切な引数名（例: `[string]`、`[int]`、`[bool]`など）を自動的に生成し、ヘルプメッセージに表示するようになりました。

したがって、このコミットで行われた変更は、単に`usage`文字列から冗長な引数名とコロンを削除する作業です。例えば、`"path: set relative path for local imports"`という文字列は、`"set relative path for local imports"`に変更されました。これにより、`flag`パッケージが自動的に生成する引数名と組み合わされて、最終的なヘルプメッセージはより簡潔になります。

この変更は、機能的な動作には影響を与えません。コンパイラやリンカのフラグの動作自体は変わらず、単にヘルプメッセージの表示形式が改善されるだけです。これは、Goツールチェイン全体のユーザーエクスペリエンスと一貫性を向上させるための、クリーンアップ作業と位置づけられます。

# [インデックス 24694] ファイルの概要

このコミットは、Go言語の標準ライブラリ`net`パッケージ内の`mac.go`ファイルと`mac_test.go`ファイルに対する変更です。`mac.go`はMACアドレスの解析と表現に関する機能を提供し、`mac_test.go`はそのテストコードを含んでいます。具体的には、`ParseMAC`関数がInfiniBand over IP (IPoIB) のリンク層アドレスである20オクテットのアドレスを正しく解析できるように拡張されています。

## コミット

`net`パッケージの`ParseMAC`関数が、20オクテットのIPoIBリンク層アドレスを解析できるように修正されました。これにより、InfiniBandネットワーク環境におけるMACアドレスの取り扱いが改善されます。

## 変更の背景

この変更の背景には、Go言語の`net`パッケージが、従来のMAC-48、EUI-48、EUI-64といった標準的なMACアドレス形式だけでなく、InfiniBand over IP (IPoIB) 環境で利用される特殊なリンク層アドレス形式にも対応する必要があったという事情があります。

`Fixes #11763`という記述から、このコミットが特定の課題（Issue 11763）を解決するために行われたことが示唆されます。Goの公式イシュートラッカーで直接この番号のイシューは見つかりませんでしたが、これは古いイシューであるか、内部的なトラッカーの参照である可能性があります。しかし、このコミットの目的は明確であり、IPoIBアドレスのサポートが求められていたことを示しています。

InfiniBandは、高性能コンピューティング（HPC）やデータセンターで広く利用される高速な相互接続技術です。IPoIBは、このInfiniBandファブリック上で標準的なIPネットワークプロトコルを使用するためのメカニズムを提供します。IPoIBデバイスは、通常のイーサネットデバイスとは異なる形式のリンク層アドレス（MACアドレスに相当するもの）を使用します。従来の`ParseMAC`関数がこの20オクテットのIPoIBアドレスを認識できなかったため、GoアプリケーションがIPoIBインターフェースを正しく扱えないという問題が発生していました。このコミットは、その互換性のギャップを埋めることを目的としています。

## 前提知識の解説

### MACアドレスの種類

*   **MAC-48 (Media Access Control-48)**: 最も一般的なMACアドレス形式で、48ビット（6オクテット）長です。イーサネットなどのネットワークインターフェースに割り当てられます。通常、`XX:XX:XX:XX:XX:XX`または`XX-XX-XX-XX-XX-XX`の形式で表記されます。
*   **EUI-48 (Extended Unique Identifier-48)**: MAC-48と同じく48ビット長ですが、IEEEによって管理される識別子です。実質的にMAC-48と同じものとして扱われることが多いです。
*   **EUI-64 (Extended Unique Identifier-64)**: 64ビット（8オクテット）長のアドレス形式です。IPv6のアドレス自動設定などで使用されることがあります。`XX:XX:XX:XX:XX:XX:XX:XX`などの形式で表記されます。

### InfiniBandとIP over InfiniBand (IPoIB)

*   **InfiniBand**: 高帯域幅、低遅延を特徴とするサーバー間接続技術です。主にHPCクラスター、データセンター、ストレージネットワークなどで利用されます。従来のイーサネットとは異なるプロトコルスタックを持ちます。
*   **IP over InfiniBand (IPoIB)**: InfiniBandファブリック上でIPプロトコルを動作させるための標準的な方法です。これにより、既存のIPベースのアプリケーションやサービスをInfiniBand環境で利用できるようになります。IPoIBデバイスは、通常のイーサネットデバイスと同様にIPアドレスを持ちますが、その基盤となるリンク層アドレスはInfiniBand特有の形式を使用します。

### IPoIBリンク層アドレスの構造

IPoIBのリンク層アドレスは、標準的なMACアドレスとは異なり、**20オクテット（160ビット）**の長さを持っています。この20オクテットは以下の要素で構成されます。

1.  **最初の4オクテット**: フラグとキューペア番号（Queue Pair Number）が含まれます。これらはInfiniBandの通信メカニズムに関連する情報です。
2.  **次の8オクテット**: サブネットプレフィックス（Subnet Prefix）です。InfiniBandサブネット内でのルーティングに関連します。
3.  **最後の8オクテット**: InfiniBandポートのグローバルユニーク識別子（GUID: Globally Unique Identifier）です。これは、InfiniBandデバイスの各ポートに割り当てられる一意の識別子です。

この20オクテットのアドレスは、従来の6オクテットや8オクテットのMACアドレスとは大きく異なるため、`ParseMAC`関数がこれを正しく解析するためには特別な対応が必要でした。

## 技術的詳細

`net.ParseMAC`関数は、文字列形式のMACアドレスを`net.HardwareAddr`型（`[]byte`のエイリアス）に変換する役割を担っています。この関数は、コロン区切り (`:`), ハイフン区切り (`-`), ドット区切り (`.`) の3種類の表記形式に対応しています。

このコミットでは、`ParseMAC`関数が20オクテットのIPoIBアドレスを認識し、解析できるように、内部のロジックが拡張されました。

1.  **文字列長のチェック**: `ParseMAC`関数は、入力文字列の長さに基づいて、それがどの形式のMACアドレスであるかを推測します。例えば、`01:23:45:67:89:ab`は6オクテット、`01:23:45:67:89:ab:cd:ef`は8オクテットのアドレスです。20オクテットのIPoIBアドレスの場合、コロン区切りでは`01:23:45:67:89:ab:cd:ef:00:00:01:23:45:67:89:ab:cd:ef:00:00`のように、非常に長い文字列になります。

2.  **オクテット数の判定ロジックの変更**:
    `ParseMAC`関数内部では、入力文字列の形式（コロン区切り、ハイフン区切り、ドット区切り）に応じて、期待されるオクテット数`n`を計算するロジックがあります。
    *   コロン区切りまたはハイフン区切りの場合、`n = (len(s) + 1) / 3`という計算が行われます。これは、`XX:XX:XX`のような形式で、各オクテットが2文字と1つの区切り文字で構成されることを前提としています。
    *   ドット区切りの場合、`n = 2 * (len(s) + 1) / 5`という計算が行われます。これは、`XXXX.XXXX.XXXX`のような形式で、各グループが4文字と1つの区切り文字で構成されることを前提としています。

    この`n`の値が、従来のMAC-48/EUI-48 (6オクテット) またはEUI-64 (8オクテット) のいずれかに合致するかどうかをチェックしていました。このコミットでは、このチェックに**20オクテット**が追加されました。

    具体的には、以下の条件式が変更されました。
    *   コロン/ハイフン区切り: `if n != 6 && n != 8` から `if n != 6 && n != 8 && n != 20` へ
    *   ドット区切り: `if n != 6 && n != 8` から `if n != 6 && n != 8 && n != 20` へ

    これにより、`ParseMAC`は入力文字列から計算されたオクテット数`n`が6、8、または20のいずれかであれば、そのアドレスを有効なものとして処理を続行するようになります。

3.  **テストケースの追加**: 新しい20オクテットのIPoIBアドレス形式が正しく解析されることを保証するために、`mac_test.go`に複数のテストケースが追加されました。これらのテストケースは、コロン、ハイフン、ドットの各区切り形式で20オクテットのアドレス文字列を与え、期待される`HardwareAddr`（20バイトのスライス）が返されることを確認します。

この変更により、Goの`net`パッケージは、InfiniBand環境でIPoIBを使用するシステムとの互換性が向上し、より幅広いネットワーク環境に対応できるようになりました。

## コアとなるコードの解説

### `src/net/mac.go` の変更点

`ParseMAC`関数の変更は主に2つの部分に分けられます。

1.  **ドキュメンテーションの更新**:
    `ParseMAC`関数のコメントが更新され、新たに「a 20-octet IP over InfiniBand link-layer address」が解析対象として明記されました。また、20オクテットアドレスの具体的な表記例（コロン、ハイフン、ドット区切り）が追加され、開発者がこの関数でどのような形式のアドレスを扱えるかを一目で理解できるようになりました。これは、関数の公開インターフェースとしての正確性と利便性を高める重要な変更です。

2.  **アドレス長検証ロジックの拡張**:
    `ParseMAC`関数は、入力された文字列がどの形式のMACアドレスであるかを判断するために、まず文字列の長さから期待されるオクテット数`n`を計算します。
    *   コロン区切り (`:`) やハイフン区切り (`-`) の場合、`n = (len(s) + 1) / 3` という式でオクテット数を導出します。例えば、`01:23:45` (6オクテット) なら `(17+1)/3 = 6`、`01:23:45:67:89:ab:cd:ef` (8オクテット) なら `(23+1)/3 = 8` となります。20オクテットのアドレスの場合、`01:23:45:67:89:ab:cd:ef:00:00:01:23:45:67:89:ab:cd:ef:00:00` は長さ59なので `(59+1)/3 = 20` となります。
    *   ドット区切り (`.`) の場合、`n = 2 * (len(s) + 1) / 5` という式でオクテット数を導出します。例えば、`0123.4567.89ab` (6オクテット) なら `2*(14+1)/5 = 6`、`0123.4567.89ab.cdef` (8オクテット) なら `2*(19+1)/5 = 8` となります。20オクテットのアドレスの場合、`0123.4567.89ab.cdef.0000.0123.4567.89ab.cdef.0000` は長さ49なので `2*(49+1)/5 = 20` となります。

    変更前は、計算された`n`が6（MAC-48/EUI-48）または8（EUI-64）のいずれかである場合にのみ有効なアドレスとして処理を続行していました。このコミットでは、この条件式に `&& n != 20` が追加されました。これにより、計算されたオクテット数`n`が20である場合も有効なアドレスとして認識され、後続のバイト変換処理に進むことができるようになりました。この小さな変更が、IPoIBアドレスのサポートを可能にする核心部分です。

### `src/net/mac_test.go` の変更点

`mac_test.go`には、`parseMACTests`という`struct`スライスがあり、`ParseMAC`関数の様々な入力と期待される出力（`HardwareAddr`とエラー）を定義しています。このコミットでは、このスライスに3つの新しいテストケースが追加されました。

*   **コロン区切り20オクテットアドレス**: `01:23:45:67:89:ab:cd:ef:00:00:01:23:45:67:89:ab:cd:ef:00:00`
*   **ハイフン区切り20オクテットアドレス**: `01-23-45-67-89-ab-cd-ef-00-00-01-23-45-67-89-ab-cd-ef-00-00`
*   **ドット区切り20オクテットアドレス**: `0123.4567.89ab.cdef.0000.0123.4567.89ab.cdef.0000`

これらのテストケースは、それぞれ対応する20バイトの`HardwareAddr`スライスを期待値として持ちます。例えば、`0x01, 0x23, ..., 0x00, 0x00`といった形で、各オクテットが正しくバイト値に変換されることを検証します。これらのテストの追加により、`ParseMAC`関数が新しいIPoIBアドレス形式を正しく解析できることが保証され、将来の回帰を防ぐための安全網が提供されます。

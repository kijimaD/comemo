## 変更の背景

このコミットは、GoランタイムとCGO（C言語との相互運用機能）における`needextram`変数の扱いを改善することを目的としています。以前は`needextram`が`uint32`型であり、CGOパッケージの境界を越えてアクセスする必要がありました。これは、GoのランタイムとCGOの間の結合度を高め、コードの理解や保守を複雑にする可能性がありました。

この変更の主な動機は以下の通りです。

1.  **型の明確化と意図の明確化:** `needextram`がブール値（真偽値）として扱われるべきものであるにもかかわらず`uint32`型であったため、その意図が不明瞭でした。`bool`型に変更することで、変数の目的がより明確になります。
2.  **CGOパッケージ境界の依存関係の解消:** `needextram`の値を反転させることで、CGOパッケージがこの変数に直接アクセスする必要がなくなりました。これにより、ランタイムとCGO間の依存関係が緩和され、モジュール性が向上します。
3.  **コードの簡素化と堅牢性の向上:** よりシンプルで直感的なロジックにすることで、将来的なバグの発生リスクを低減し、コードの可読性と保守性を向上させます。特に、CGOのような低レベルの相互作用を扱う部分では、明確なロジックが重要です。

## 前提知識の解説

このコミットの変更内容を理解するためには、GoランタイムのスケジューリングモデルとCGOの基本的な仕組みについて理解しておく必要があります。

### Goランタイムスケジューラ (M-P-Gモデル)

Goのランタイムは、効率的な並行処理を実現するために独自のスケジューラを持っています。このスケジューラは、G（Goroutine）、P（Processor）、M（Machine）という3つの主要な要素で構成されるM-P-Gモデルを採用しています。

*   **G (Goroutine):** Goにおける並行実行の単位です。OSのスレッドよりもはるかに軽量で、数KB程度の小さなスタックで開始し、必要に応じて動的にスタックサイズを増減させることができます。Goプログラム内で`go`キーワードを使って関数を呼び出すことで、新しいGoroutineが生成されます。
*   **P (Processor):** 論理的なプロセッサであり、Goコードを実行するためのコンテキストを提供します。`P`は、OSスレッド（`M`）がGoroutine（`G`）を実行するために不可欠です。通常、`P`の数はCPUのコア数に設定されますが、`runtime.GOMAXPROCS()`関数で制御することも可能です。各`P`は、実行準備ができたGoroutineのローカルキューを保持しています。
*   **M (Machine):** オペレーティングシステム（OS）のスレッドです。`M`はGoコードを実行する責任を持ち、そのためには`P`と関連付けられている必要があります。Goランタイムは`M`の生成と管理を行います。Goroutineが`M`上で実行中にブロッキング操作（例: システムコール、ネットワークI/O、チャネル操作）を行うと、その`M`は`P`からデタッチされます。これにより、`P`は別の`M`によって使用され、他のGoroutineの実行を継続できるため、`P`全体がブロックされるのを防ぎます。

Goスケジューラの主な役割は、`G`を`P`に効率的にマッピングし、それを`M`が実行することです。スケジューラはワークスティーリングアルゴリズムを利用しており、もし`P`がローカルキュー内のGoroutineを使い果たした場合、他の`P`のローカルキューからGoroutineを「盗む」ことで、`M`を常に稼働させ、CPU利用率を最大化します。

### CGOと「Extra M」

CGOは、GoプログラムがC言語のコードを呼び出したり、その逆を行ったりすることを可能にし、既存のCライブラリとの相互運用性を実現します。CGOとGoスケジューラの相互作用には、「Extra M」（追加のM）の概念が導入されています。

GoのGoroutineがCコード内でブロッキング操作（例: 時間のかかるC関数呼び出しやCのシステムコール）を行うと、そのCコードを実行しているOSスレッド（`M`）はブロックされます。もしこの`M`がその`P`に結合されたままだと、その`P`もブロックされ、他のGoroutineがその`P`上で実行できなくなってしまいます。

これを緩和するために、GoランタイムはブロッキングC呼び出しを特別に扱います。
1.  ブロッキングC呼び出しを行った`M`は、その`P`からデタッチされます。
2.  `P`は解放され、他の`M`が使用できるようになります。
3.  もし他の`M`が利用できない場合、Goランタイムは新しい`M`を作成し、解放された`P`と関連付けることがあります。この新しい`M`は、`P`の実行キューから他のGoroutineを取得して実行を継続できます。

このメカニズムにより、Goスケジューラは、あるGoroutineがCコードでブロックされていても、他のGoroutineを並行して実行し続けることができます。元の`M`はC呼び出しでブロックされたままですが、C呼び出しが戻ると、その`M`は利用可能な`M`のプールに再結合できます。`runtime/cgo.go`ソースファイル内の`cgoHasExtraM`変数は、CGO操作のために追加の`M`が作成されたかどうかを示します。この設計は並行性を向上させますが、ブロッキングCGO呼び出しを多用すると、OSスレッドの数が増加し、基盤となるCコードによって適切に管理またはクリーンアップされない場合、メモリ使用量が増加する可能性があります。

## 技術的詳細

このコミットの技術的な変更点は、主に以下の3つの側面から構成されています。

1.  **`needextram`変数の型変更と論理の反転:**
    *   以前は`uint32`型であった`needextram`変数が、`bool`型に変更されました。これにより、変数の意味が「追加のMが必要かどうか」という真偽値として明確になりました。
    *   さらに、その論理が反転されました。以前は`needextram == 1`で追加のMが必要であることを示していましたが、新しいロジックでは`!cgoHasExtraM`（CGOのために追加のMがまだ作成されていない）という形で表現されます。この反転により、CGOパッケージがランタイムの内部状態を直接操作する必要がなくなりました。

2.  **新しい変数の導入と既存変数の削除:**
    *   `src/runtime/cgo.go`に`iscgo`と`cgoHasExtraM`という2つの新しいグローバル変数が導入されました。
        *   `iscgo`: GoプログラムがCGOを有効にしてビルドされている場合に`true`に設定されます。これは`runtime/cgo`パッケージによって設定されます。
        *   `cgoHasExtraM`: CGOのために追加のMが既に作成されたかどうかを示すフラグです。これにより、追加のMが複数回作成されるのを防ぎます。
    *   `src/runtime/runtime2.go`から`needextram`と`iscgo`（以前の`bool`型ではない`iscgo`）が削除されました。これにより、変数の重複が解消され、ランタイムの状態管理がより一元化されました。
    *   `src/runtime/cgo/iscgo.go`から`_needextram`が削除されました。これは、`needextram`の論理が反転され、CGOパッケージ境界を越える必要がなくなったためです。

3.  **条件式の変更と`go:linkname`の利用:**
    *   `src/runtime/proc1.go`内の`mstart1`関数と`needm`関数において、追加のMを作成する条件式が変更されました。
        *   変更前: `if needextram == 1 { ... }`
        *   変更後: `if iscgo && !cgoHasExtraM { ... }`
        この新しい条件式は、CGOが有効であり（`iscgo`が`true`）、かつCGOのために追加のMがまだ作成されていない場合にのみ、新しいMを作成するという明確な意図を示しています。
    *   `src/runtime/cgo/iscgo.go`では、`//go:linkname _iscgo runtime.iscgo`というディレクティブが使用されています。これは、`runtime/cgo`パッケージ内のプライベート変数`_iscgo`が、`runtime`パッケージ内のエクスポートされていない変数`iscgo`にリンクされることを意味します。これにより、CGOが有効であるという情報をランタイムに安全に伝えることができます。

これらの変更により、GoランタイムとCGO間の相互作用がより明確で、堅牢で、保守しやすくなりました。特に、CGOパッケージがランタイムの内部状態に直接依存するのではなく、より抽象化されたフラグを通じて連携するようになった点が重要です。

## コアとなるコードの解説

### `src/runtime/cgo.go`

*   **追加:**
    *   `var iscgo bool`: CGOが有効な場合に`runtime/cgo`パッケージによって`true`に設定される新しいグローバル変数です。これにより、ランタイムがCGOの有効性を直接確認できるようになります。
    *   `var cgoHasExtraM bool`: CGOのために追加のMが既に作成されたかどうかを示す新しいグローバル変数です。これにより、追加のMが重複して作成されるのを防ぎます。

### `src/runtime/cgo/iscgo.go`

*   **削除:**
    *   `var _needextram uint32 = 1`: 以前、CGO呼び出し時に追加のMが必要であることを示すために使用されていた`_needextram`変数が削除されました。これは、`needextram`の論理が反転され、CGOパッケージ境界を越える必要がなくなったためです。
*   **変更なし（既存のまま）:**
    *   `//go:linkname _iscgo runtime.iscgo`: このディレクティブは、`runtime/cgo`パッケージ内のプライベート変数`_iscgo`を`runtime`パッケージ内のエクスポートされていない変数`iscgo`にリンクします。これにより、`runtime/cgo`パッケージが`runtime.iscgo`変数を`true`に設定し、GoランタイムにCGOが有効であることを通知します。

### `src/runtime/proc1.go`

*   **`mstart1()`関数内の変更:**
    *   `if needextram == 1 { ... }` が `if iscgo && !cgoHasExtraM { ... }` に変更されました。
        *   これは、CGOが有効であり（`iscgo`が`true`）、かつCGOのために追加のMがまだ作成されていない場合にのみ、`newextram()`（新しいMを作成する関数）を呼び出すようにロジックが変更されたことを意味します。
    *   `needextram = 0` が `cgoHasExtraM = true` に変更されました。
        *   これは、追加のMが作成されたことを`cgoHasExtraM`フラグで記録するように変更されたことを意味します。

*   **`needm()`関数内の変更:**
    *   `if needextram != 0 { ... }` が `if iscgo && !cgoHasExtraM { ... }` に変更されました。
        *   `mstart1()`と同様に、追加のMが必要かどうかの判断ロジックが、より明確で新しいフラグを使用するように更新されました。

### `src/runtime/runtime2.go`

*   **削除:**
    *   `needextram uint32`: `needextram`変数が`bool`型に変更され、`src/runtime/cgo.go`に移動されたため、ここから削除されました。
    *   `iscgo bool`: 以前の`iscgo`変数が削除されました。新しい`iscgo`変数は`src/runtime/cgo.go`で定義され、`go:linkname`を通じてアクセスされます。

これらの変更により、GoランタイムはCGOとの連携において、より明確で、安全で、保守しやすいメカニズムを持つようになりました。特に、CGOが有効であるかどうかの判断と、追加のMの作成管理が、より堅牢なフラグベースのシステムに移行した点が重要です。

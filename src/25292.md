# [インデックス 25292] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) において、Android/ARMアーキテクチャ向けのPIE (Position-Independent Executable) 実行ファイル生成をサポートするための変更を導入します。具体的には、リンカのビルドモードに`BuildmodePIE`を追加し、PIEバイナリが正しく生成され、RELRO (RELocation Read-Only) などのセキュリティ機能が適用されるように、既存のリンカロジックを修正しています。

## コミット

Goリンカ (`cmd/link`) に、Android/ARMターゲット向けのPIE (Position-Independent Executable) 実行ファイル生成機能を追加するコミットです。これにより、Androidプラットフォームのセキュリティ要件に準拠したGoバイナリの生成が可能になります。

## 変更の背景

この変更の主な背景には、Androidプラットフォームにおけるセキュリティ要件の進化があります。特にAndroid 5.0 (Lollipop) 以降、動的にリンクされるすべての実行ファイルはPIE (Position-Independent Executable) であることが義務付けられました。PIEはASLR (Address Space Layout Randomization) と組み合わせて使用され、実行ファイルのメモリ上の配置をランダム化することで、バッファオーバーフローなどのメモリ破損脆弱性を悪用した攻撃を困難にするセキュリティ機構です。

Go言語はクロスコンパイルに非常に優れており、様々なプラットフォーム向けにバイナリを生成できます。しかし、Android/ARMのような特定の環境では、そのプラットフォーム固有のセキュリティ要件に対応する必要があります。このコミット以前は、GoリンカはAndroid/ARM向けにPIEバイナリを直接生成する機能を持っていなかったため、Goで開発されたアプリケーションがAndroidの最新のセキュリティ基準を満たすことが困難でした。

このコミットは、Goリンカに`BuildmodePIE`という新しいビルドモードを導入し、Android/ARMターゲット向けにPIE実行ファイルを生成できるようにすることで、このギャップを埋めることを目的としています。これにより、GoアプリケーションはAndroidプラットフォーム上でより安全に、かつ互換性を持って動作できるようになります。コミットメッセージにある`For #10807`は、この機能追加がGoの内部課題トラッカーで追跡されていた特定の課題に対応するものであることを示唆しています。

## 前提知識の解説

### PIE (Position-Independent Executable)

PIE (Position-Independent Executable) は、プログラムのコードがメモリ上の任意のアドレスにロードされても正しく実行されるように設計された実行ファイル形式です。これは、Position-Independent Code (PIC) から構築されます。

*   **ASLR (Address Space Layout Randomization)**: PIEの主な目的は、ASLRを有効にすることです。ASLRは、実行ファイル、ライブラリ、ヒープ、スタックなどのメモリ領域の開始アドレスをランダムに配置するセキュリティ技術です。これにより、攻撃者が特定のコードやデータのメモリ上の位置を予測することを困難にし、ROP (Return-Oriented Programming) などのメモリ破損攻撃を軽減します。
*   **セキュリティ上の利点**: PIEとASLRの組み合わせは、現代のオペレーティングシステムにおける基本的なセキュリティ対策の一つであり、特にモバイルプラットフォームでは必須とされています。

### Goのリンカ (cmd/link)

`cmd/link`は、Go言語のビルドツールチェーンの一部であり、コンパイルされたGoのオブジェクトファイルと必要なライブラリを結合して、実行可能なバイナリを生成する役割を担います。Goのリンカは、C言語のリンカとは異なり、Goランタイムの初期化、ガベージコレクション、リフレクションなどのGo固有の機能に必要なメタデータもバイナリに埋め込みます。

### Buildmode

Goリンカの`Buildmode`は、生成されるバイナリの種類を決定する設定です。例えば、通常の実行ファイル (`exe`)、Cアーカイブ (`c-archive`)、C共有ライブラリ (`c-shared`)、共有ライブラリ (`shared`) などがあります。このコミットでは、新たに`BuildmodePIE`が追加され、PIE形式の実行ファイルを生成できるようになります。

### RELRO (RELocation Read-Only)

RELRO (RELocation Read-Only) は、実行ファイルの特定のセクション（特にGOT: Global Offset Table）を、動的リンカによる再配置が完了した後に読み取り専用としてマークするセキュリティ機構です。

*   **Partial RELRO**: GOTの非PLT部分が読み取り専用になりますが、`.got.plt`セクションは書き込み可能のままです。
*   **Full RELRO**: GOT全体 (`.got`と`.got.plt`) が読み取り専用としてマークされます。これにより、より強力な保護が提供されますが、起動時にすべてのシンボルを即座にバインドするため、わずかなパフォーマンスオーバーヘッドが発生する可能性があります。

RELROは、攻撃者がGOTを書き換えて任意のコード実行を試みることを防ぐのに役立ちます。

### Goのランタイム初期化 (_rt0_)

`_rt0` (runtime 0) は、Goプログラムが起動したときに最初に実行される非常に低レベルなアセンブリコードのエントリポイントです。これはGoランタイムの初期ブートストラップの役割を果たします。

*   **役割**: スタックのセットアップ、レジスタの初期化、BSSセグメント（未初期化データ）のゼロクリアなど、Goランタイムが機能するために必要な最小限の環境をセットアップします。
*   **`runtime.main`への移行**: `_rt0`はこれらの基本的なセットアップの後、Goランタイムの`runtime.main`関数に制御を移します。`runtime.main`は、ガベージコレクタやスケジューラなどのより複雑なランタイムコンポーネントの初期化を続行し、最終的にユーザーの`main.main`関数を実行するゴルーチンを起動します。

### moduledata

`moduledata`は、Goリンカによって生成される内部ランタイムテーブルであり、Go実行ファイルのレイアウトと構造に関する広範なメタデータをカプセル化します。このデータは、Goランタイムの様々なコア機能にとって不可欠です。

*   **目的**:
    *   **ガベージコレクション (GC)**: GCがポインタを正確に識別し、メモリを管理するために必要な情報を提供します。
    *   **リフレクション**: `typelinks`などの型情報を格納し、Goのリフレクション機能（実行時に型を検査・操作する機能）を可能にします。
    *   **スタックトレース**: PC-lineテーブル (`pclntab`) や関数テーブル (`ftab`) などのデータ構造を含み、プログラム実行中やパニック発生時に正確なスタックトレースを生成するために使用されます。
*   **リンカの役割**: Goリンカは、最終的な実行ファイルに`moduledata`構造を埋め込み、その内容を適切に設定する責任を負います。

### LSym (Linker Symbol)

`LSym` (Linker Symbol) は、Goリンカのシンボルテーブルにおけるエントリを表します。シンボルテーブルは、関数、グローバル変数、型、定数など、Goプログラムで定義された様々な要素に関するメタデータを格納します。

*   **情報**: `LSym`は通常、シンボルの一意な識別子（名前）、最終的な実行ファイル内のメモリアドレスまたはオフセット、シンボルの種類（コード、初期化済みデータなど）、サイズ、および他のシンボルへの参照（再配置情報）を含みます。
*   **リンカの機能**: Goリンカは、コンパイルされたオブジェクトファイルからすべての`LSym`エントリを収集し、これらのシンボル間の相互参照を解決し、最終的なメモリレイアウトにおける位置を計算し、必要な再配置を適用して、完全な実行可能バイナリを作成します。

## 技術的詳細

このコミットは、主に`src/cmd/link/internal/ld`パッケージ内の3つのファイル、`elf.go`、`lib.go`、`symtab.go`に変更を加えています。これらの変更は、`BuildmodePIE`の導入と、それに伴うリンカの挙動調整に焦点を当てています。

### `src/cmd/link/internal/ld/lib.go`の変更

このファイルは、リンカのビルドモードの定義と、それに関連するユーティリティ関数を含んでいます。

1.  **`BuildmodePIE`の導入**:
    ```go
    const (
    	BuildmodeUnset BuildMode = iota
    	BuildmodeExe
    	BuildmodePIE // 新しく追加されたビルドモード
    	BuildmodeCArchive
    	BuildmodeCShared
    	BuildmodeShared
    	// ...
    )
    ```
    `BuildMode`列挙型に`BuildmodePIE`が追加され、PIE実行ファイルを生成するための新しいビルドモードが定義されました。

2.  **`UseRelro()`関数の変更**:
    ```go
    func UseRelro() bool {
    	switch Buildmode {
    	case BuildmodeCShared, BuildmodeShared, BuildmodePIE: // BuildmodePIEが追加
    		return Iself
    	default:
    		return false
    	}
    }
    ```
    `UseRelro()`関数は、RELROを有効にするべきかどうかを判断します。この変更により、`BuildmodePIE`の場合にもRELROが有効になるようになりました。これは、PIEバイナリがASLRとRELROの両方を利用してセキュリティを強化するという一般的なプラクティスに沿ったものです。`Iself`は、ターゲットがELF形式のバイナリであるかどうかを示すフラグです。

3.  **`BuildMode.Set(s string) error`関数の変更**:
    ```go
    func (mode *BuildMode) Set(s string) error {
    	switch s {
    	// ...
    	case "pie": // "pie"文字列がBuildmodePIEにマッピングされる
    		switch goos {
    		case "android": // android OSでのみ"pie"モードが許可される
    		default:
    			return badmode()
    		}
    		*mode = BuildmodePIE
    	// ...
    	}
    }
    ```
    コマンドライン引数で`-buildmode=pie`が指定された際に、`BuildmodePIE`が設定されるようにハンドリングが追加されました。注目すべきは、この`"pie"`モードが`goos == "android"`の場合にのみ許可される点です。これは、このコミットが特にAndroid/ARM向けのPIEサポートを対象としていることを明確に示しています。

4.  **`BuildMode.String() string`関数の変更**:
    ```go
    func (mode *BuildMode) String() string {
    	switch *mode {
    	// ...
    	case BuildmodePIE: // BuildmodePIEの文字列表現を追加
    		return "pie"
    	// ...
    	}
    }
    ```
    `BuildmodePIE`の文字列表現として`"pie"`が返されるように追加されました。

5.  **`libinit()`関数の変更**:
    ```go
    func libinit() {
    	// ...
    	switch Buildmode {
    	case BuildmodeCShared, BuildmodeCArchive:
    		INITENTRY = fmt.Sprintf("_rt0_%s_%s_lib", goarch, goos)
    	case BuildmodeExe, BuildmodePIE: // BuildmodePIEが追加
    		INITENTRY = fmt.Sprintf("_rt0_%s_%s", goarch, goos)
    	case BuildmodeShared:
    		// No INITENTRY for -buildmode=shared
    	}
    	// ...
    }
    ```
    Goプログラムの初期エントリポイントである`INITENTRY`を決定するロジックに`BuildmodePIE`が追加されました。`BuildmodeExe`と同様に、通常の実行ファイルのエントリポイント (`_rt0_goarch_goos`) が使用されることを示しています。

6.  **`loadlib()`関数の変更**:
    ```go
    func loadlib() {
    	// ...
    	switch Buildmode {
    	case BuildmodeExe, BuildmodePIE: // BuildmodePIEが追加
    		if havedynamic == 0 && HEADTYPE != obj.Hdarwin && HEADTYPE != obj.Hsolaris {
    			Debug['d'] = 1
    		}
    	}
    	// ...
    }
    ```
    `Debug['d']`フラグの設定ロジックに`BuildmodePIE`が追加されました。この`Debug['d']`は、Goリンカの内部的なデバッグフラグの一つで、動的リンクされていないバイナリ（かつDarwinやSolarisではない場合）に対して設定されることがあります。PIEバイナリも動的リンクを前提としない場合があるため、このロジックに含まれるようになりました。

7.  **`hostlink()`関数の変更**:
    ```go
    func hostlink() {
    	// ...
    	case BuildmodePIE: // BuildmodePIEの場合に-pieリンカフラグを追加
    		argv = append(argv, "-pie")
    	case BuildmodeCShared:
    	// ...
    }
    ```
    外部リンカを呼び出す際に、`BuildmodePIE`が指定されている場合に`-pie`フラグを`argv`（リンカへの引数リスト）に追加するようになりました。これは、外部リンカに対してPIE形式の実行ファイルを生成するように指示するための重要なステップです。

### `src/cmd/link/internal/ld/elf.go`の変更

このファイルは、ELF形式のバイナリ生成に関連するロジックを含んでいます。

1.  **`doelf()`関数の変更**:
    ```go
    func doelf() {
    	// ...
    	// if Buildmode == BuildmodeShared || Buildmode == BuildmodeCShared {
    	// 	Addstring(shstrtab, ".data.rel.ro")
    	// }
    	// ...
    	if UseRelro() { // UseRelro()がtrueの場合に常に.data.rel.roを追加

    ```
    `.data.rel.ro`セクションの名前をELFセクションヘッダ文字列テーブル (`shstrtab`) に追加するロジックが変更されました。以前は`BuildmodeShared`または`BuildmodeCShared`の場合にのみ追加されていましたが、`UseRelro()`が`true`の場合（つまり、`BuildmodePIE`の場合も含む）に常にこのセクションが追加されるようになりました。これは、RELROが有効なバイナリにはこのセクションが必要であることを意味します。

### `src/cmd/link/internal/ld/symtab.go`の変更

このファイルは、シンボルテーブルの生成と関連するロジックを含んでいます。

1.  **`symtab()`関数の変更**:
    ```go
    func symtab() {
    	// ...
    	if UseRelro() && (Buildmode == BuildmodeCShared || Buildmode == BuildmodePIE) { // BuildmodePIEが追加
    		s = Linklookup(Ctxt, "type.*", 0)
    		// ...
    	}
    	// ...
    ```

    `UseRelro()`が`true`であり、かつ`BuildmodeCShared`または`BuildmodePIE`の場合に、特定のシンボル (`type.*`) の処理が行われるようになりました。これは、RELROが有効なPIEバイナリにおける型情報の取り扱いに関連する可能性があります。
    また、`moduledata`の`thismodulename`を設定するロジックにも`BuildmodePIE`が追加されました。`BuildmodeExe`と同様に、PIEバイナリの場合もモジュール名が「the executable」として扱われることを示しています。`moduledata`はGoランタイムのメタデータであり、その中に含まれるモジュール名もビルドモードに応じて適切に設定される必要があります。

## コアとなるコードの解説

### `src/cmd/link/internal/ld/lib.go`の変更点

*   **`BuildmodePIE`の追加と`UseRelro()`の更新**:
    `Buildmode`列挙型に`BuildmodePIE`が追加されたことで、リンカはPIE形式のバイナリを生成する新しいモードを認識できるようになりました。これに伴い、`UseRelro()`関数が更新され、`BuildmodePIE`の場合にもRELROが有効になるように変更されました。これは、PIEバイナリがASLRとRELROの両方を利用してセキュリティを強化するという現代のセキュリティプラクティスに不可欠です。`Iself`は、ターゲットがELF形式のバイナリである場合に`true`を返すため、ELF形式のPIEバイナリに対してRELROが適用されます。

*   **`BuildMode.Set()`での`"pie"`モードのハンドリング**:
    `go build -buildmode=pie`コマンドが実行された際に、リンカがこのモードを正しく解釈し、`BuildmodePIE`を設定できるように`Set`メソッドが拡張されました。特に、この`"pie"`モードが`goos == "android"`の場合にのみ許可されるという制約は、このコミットがAndroidプラットフォームに特化したPIEサポートを目的としていることを強調しています。これにより、不適切なプラットフォームでのPIEビルドが防止されます。

*   **`libinit()`における`INITENTRY`の調整**:
    Goプログラムの起動時に最初に実行されるエントリポイントである`INITENTRY`の決定ロジックに`BuildmodePIE`が追加されました。`BuildmodeExe`と同様に、PIEバイナリも標準の実行ファイルのエントリポイント (`_rt0_goarch_goos`) を使用するように設定されます。これは、PIEバイナリが通常の実行ファイルと同様の初期化フローをたどることを示しています。

*   **`loadlib()`における`Debug['d']`フラグの調整**:
    `loadlib()`関数内の`Debug['d']`フラグの設定ロジックに`BuildmodePIE`が追加されました。このフラグは、動的リンクされていないバイナリ（かつ特定のOSではない場合）に対して設定される内部的なデバッグフラグです。PIEバイナリも、場合によっては動的リンクを伴わない構成でビルドされる可能性があるため、このロジックに含まれることで、リンカのデバッグ挙動がPIEモードでも一貫性を保つように調整されています。

*   **`hostlink()`での`-pie`リンカフラグの追加**:
    最も重要な変更の一つとして、`hostlink()`関数において`BuildmodePIE`が指定されている場合に、外部リンカに対して`-pie`フラグが渡されるようになりました。この`-pie`フラグは、外部リンカにPosition-Independent Executableを生成するように指示するための標準的なオプションです。これにより、Goリンカが生成したオブジェクトファイルが、最終的にPIE形式の実行ファイルとしてリンクされることが保証されます。

### `src/cmd/link/internal/ld/elf.go`の変更点

*   **`doelf()`における`.data.rel.ro`セクションの扱い**:
    `doelf()`関数はELFバイナリのセクション情報を処理します。この変更により、`.data.rel.ro`セクションがELFセクションヘッダ文字列テーブル (`shstrtab`) に追加される条件が、`BuildmodeShared`または`BuildmodeCShared`の場合から、`UseRelro()`が`true`の場合（つまり`BuildmodePIE`の場合も含む）に拡張されました。これは、RELROが有効なバイナリには、再配置情報が格納されるこのセクションが必要であることをリンカに伝えるための変更です。

### `src/cmd/link/internal/ld/symtab.go`の変更点

*   **`symtab()`におけるシンボル処理と`moduledata`の調整**:
    `symtab()`関数はシンボルテーブルの生成を担当します。この変更では、`UseRelro()`が`true`であり、かつ`BuildmodeCShared`または`BuildmodePIE`の場合に、特定のシンボル (`type.*`) の処理が行われるようになりました。これは、RELROが有効なPIEバイナリにおける型情報の取り扱い、特に読み取り専用の再配置データセクションに配置される型情報に関連する可能性があります。
    また、`moduledata`内の`thismodulename`を設定するロジックにも`BuildmodePIE`が追加されました。`BuildmodeExe`と同様に、PIEバイナリの場合もモジュール名が「the executable」として扱われるようにすることで、Goランタイムが自身のメタデータを正しく識別できるようになります。

これらの変更全体として、GoリンカがAndroid/ARM環境で要求されるPIEバイナリを生成するための基盤を確立し、関連するセキュリティ機能（RELROなど）が適切に適用されるように調整されています。

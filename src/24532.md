# [インデックス 24532] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）プロセスにおいて、GCの開始時と終了時に発生する特定の期間におけるミューテーター（アプリケーションのGoroutine）の挙動を改善するためのものです。この期間中、ミューテーターはヒープの目標値を超えてメモリを割り当ててしまう可能性があり、その結果、GCの効率が低下したり、アプリケーションのレイテンシが増加したりする問題がありました。このコミットは、一時的な回避策として、ミューテーターがGCを支援できない場合にCPUを譲渡することで、GCコーディネーターに処理時間を確保し、GCの移行をスムーズにすることを目的としています。

## 元コミット内容

```
runtime: assist the GC during GC startup and shutdown

Currently there are two sensitive periods during which a mutator can
allocate past the heap goal but mutator assists can't be enabled: 1)
at the beginning of GC between when the heap first passes the heap
trigger and sweep termination and 2) at the end of GC between mark
termination and when the background GC goroutine parks. During these
periods there's no back-pressure or safety net, so a rapidly
allocating mutator can allocate past the heap goal. This is
exacerbated if there are many goroutines because the GC coordinator is
scheduled as any other goroutine, so if it gets preempted during one
of these periods, it may stay preempted for a long period (10s or 100s
of milliseconds).

Normally the mutator does scan work to create back-pressure against
allocation, but there is no scan work during these periods. Hence, as
a fall back, if a mutator would assist but can't yet, simply yield the
CPU. This delays the mutator somewhat, but more importantly gives more
CPU time to the GC coordinator for it to complete the transition.

This is obviously a workaround. Issue #11970 suggests a far better but
far more invasive way to fix this.

Updates #11911. (This very nearly fixes the issue, but about once
every 15 minutes I get a GC cycle where the assists are enabled but
don't do enough work.)
```

## 変更の背景

Goのガベージコレクション（GC）は、アプリケーションの実行と並行して動作する並行GCです。このGCシステムでは、「ミューテーターアシスト（Mutator Assist）」というメカニズムが導入されています。これは、アプリケーションのGoroutine（ミューテーター）がメモリを割り当てすぎた場合に、GCの作業（例えば、オブジェクトのスキャンやマーク）を手伝うことで、GCの負荷を分散し、ヒープの肥大化を防ぐ役割を果たします。これにより、GCがアプリケーションのメモリ割り当て速度に追いつくための「背圧（back-pressure）」が提供されます。

しかし、このコミットが対処しようとしているのは、GCのライフサイクルにおける特定の「敏感な期間」です。具体的には、以下の2つの期間において、ミューテーターアシストが有効にならないという問題がありました。

1.  **GC開始時**: ヒープサイズがGCトリガー（GCを開始する閾値）を超えてから、スイープ終了（sweep termination）までの期間。
2.  **GC終了時**: マーク終了（mark termination）から、バックグラウンドGC Goroutineがパーク（park、待機状態になる）するまでの期間。

これらの期間中、ミューテーターアシストによる背圧が機能しないため、高速にメモリを割り当てるミューテーターは、ヒープの目標値（heap goal）を容易に超えてしまう可能性がありました。これは、GCコーディネーター（GCの各フェーズの調整を行うGoroutine）が他の通常のGoroutineと同様にスケジューリングされるため、多数のGoroutineが存在する環境では、GCコーディネーターがプリエンプト（preempt、実行を中断される）され、GCの移行が遅延することが原因で悪化します。GCコーディネーターが数10ミリ秒から数100ミリ秒もの間プリエンプトされたままだと、その間にミューテーターが大量のメモリを割り当ててしまい、GCの効率が著しく低下する恐れがありました。

この問題は、Go Issue #11911で報告されており、Go Issue #11970では、より根本的な解決策として「分散型GCコーディネーション」が提案されています。このコミットは、#11970のような抜本的な変更が適用されるまでの間、この問題を緩和するための暫定的な回避策として導入されました。

## 前提知識の解説

*   **Goのガベージコレクション (GC)**: GoのGCは、不要になったメモリを自動的に解放するシステムです。Go 1.5以降、並行（concurrent）かつ低遅延（low-latency）なGCが導入され、アプリケーションの実行と並行してGC作業が行われます。
*   **ミューテーター (Mutator)**: アプリケーションのコードを実行し、ヒープ上に新しいオブジェクトを割り当てるGoroutineを指します。
*   **GCコーディネーター (GC Coordinator)**: GCの各フェーズ（マーク開始、マーク終了、スイープ開始など）の調整と状態遷移を管理する特別なGoroutineです。
*   **ヒープ目標値 (Heap Goal)**: 次のGCサイクルが完了した後に到達すべきヒープの目標サイズです。この目標値を超えてメモリが割り当てられると、GCの効率が低下する可能性があります。
*   **GCトリガー (Heap Trigger)**: GCを開始するヒープサイズの閾値です。
*   **スイープ終了 (Sweep Termination)**: GCのスイープフェーズが完了し、未使用メモリがシステムに返却される段階です。
*   **マーク終了 (Mark Termination)**: GCのマークフェーズが完了し、到達可能なオブジェクトのマーク付けが終了する段階です。
*   **ミューテーターアシスト (Mutator Assist)**: アプリケーションのGoroutineがメモリを割り当てる際に、GCの作業（主にマーク作業）を手伝うメカニズムです。これにより、GCがメモリ割り当て速度に追いつくための背圧が提供されます。ミューテーターアシストは、GCコントローラーによって設定されたアシスト比率に基づいて、ヒープマーク作業を支援します。
*   **Goroutineのスケジューリングとプリエンプション**: Goランタイムは、多数のGoroutineを効率的に実行するために独自のスケジューラーを持っています。Goroutineは、実行中に他のGoroutineにCPUを譲渡（プリエンプト）されることがあります。GCコーディネーターも通常のGoroutineとして扱われるため、他のGoroutineによってプリエンプトされる可能性があります。
*   **`Gosched()`**: Goの標準ライブラリ関数で、現在のGoroutineの実行を一時停止し、他のGoroutineにCPUを譲渡します。これにより、スケジューラーは別のGoroutineを実行できます。

## 技術的詳細

このコミットが解決しようとしている問題は、GCの特定の移行期間中にミューテーターアシストが機能しないことに起因します。

1.  **GC開始時（ヒープトリガーからスイープ終了まで）**: GCが開始されても、すぐにミューテーターアシストが有効になるわけではありません。この期間中、ミューテーターはGC作業を手伝うことができませんが、メモリ割り当ては継続されます。
2.  **GC終了時（マーク終了からバックグラウンドGC Goroutineのパークまで）**: マークフェーズが終了し、GCの主要な作業が完了しても、バックグラウンドGC Goroutineが完全に待機状態になるまでには時間がかかります。この期間もミューテーターアシストは有効ではありません。

これらの期間では、ミューテーターアシストによる「スキャン作業」という形の背圧が存在しません。そのため、ミューテーターは無制限にメモリを割り当て続け、ヒープ目標値を大きく超えてしまう可能性があります。特に、GCコーディネーターが多数のGoroutineによってプリエンプトされ、GCの移行処理が遅れると、この問題はさらに深刻化します。

このコミットの解決策は、ミューテーターアシストが有効ではないが、GCが進行中である「敏感な期間」に、ミューテーターがメモリを割り当てようとした際に、単にCPUを譲渡するというものです。具体的には、`mallocgc`関数内で、ミューテーターがGCを支援すべき状況でありながら、バックグラウンドGCがまだアクティブ（`bggc.working != 0`）である場合に、`Gosched()`を呼び出して現在のGoroutineの実行を一時停止します。

これにより、ミューテーターのメモリ割り当ては一時的に遅延しますが、より重要なのは、GCコーディネーターにCPU時間をより多く与えることで、GCの開始または終了の移行プロセスを迅速に完了させることです。これは、ミューテーターアシストが機能しない期間における「背圧」の代替手段として機能します。

コミットメッセージにも明記されている通り、これはあくまで「回避策」であり、根本的な解決策ではありません。Go Issue #11970で提案されている「分散型GCコーディネーション」は、GCコーディネーターの集中管理を廃止し、任意のGoroutineがGCの状態遷移を開始できるようにすることで、この種の遅延を抜本的に解決することを目指しています。

## コアとなるコードの解説

変更は `src/runtime/malloc.go` ファイルの `mallocgc` 関数内で行われています。`mallocgc` は、Goランタイムが新しいオブジェクトのためにメモリを割り当てる際に呼び出される主要な関数です。

既存のコードでは、`shouldhelpgc` が `true` の場合（つまり、GCを支援すべき状況の場合）、`gcAssistAlloc` 関数が呼び出され、ミューテーターアシストが行われます。

このコミットで追加されたのは、その `else if` ブロックです。

```go
} else if shouldhelpgc && bggc.working != 0 {
    // The GC is starting up or shutting down, so we can't
    // assist, but we also can't allocate unabated. Slow
    // down this G's allocation and help the GC stay
    // scheduled by yielding.
    //
    // TODO: This is a workaround. Either help the GC make
    // the transition or block.
    gp := getg()
    if gp != gp.m.g0 && gp.m.locks == 0 && gp.m.preemptoff == "" {
        Gosched()
    }
}
```

このコードブロックは以下の条件が満たされた場合に実行されます。

1.  `shouldhelpgc` が `true`: 現在のGoroutineがGCを支援すべき状況にあることを示します。
2.  `bggc.working != 0`: バックグラウンドGCが現在アクティブであることを示します。`bggc.working` は、GCが開始中または終了中の敏感な期間を表すフラグとして機能します。

これらの条件が満たされるということは、ミューテーターはGCを支援すべきだが、GCの特定の移行期間中であるため、`gcAssistAlloc` を通じた通常のアシストができない状況を意味します。このような状況で、ミューテーターが無制限にメモリを割り当て続けるのを防ぐために、以下の処理が行われます。

*   `gp := getg()`: 現在実行中のGoroutine（`g`）のポインタを取得します。
*   `if gp != gp.m.g0 && gp.m.locks == 0 && gp.m.preemptoff == ""`: この条件式は、`Gosched()` を呼び出す前に、現在のGoroutineが安全にCPUを譲渡できるかどうかを確認します。
    *   `gp != gp.m.g0`: 現在のGoroutineがシステムGoroutine（`g0`）ではないことを確認します。`g0` はランタイムの重要な処理を行うため、プリエンプトされるべきではありません。
    *   `gp.m.locks == 0`: 現在のGoroutineがロックを保持していないことを確認します。ロックを保持しているGoroutineがCPUを譲渡すると、デッドロックや他の同期問題を引き起こす可能性があります。
    *   `gp.m.preemptoff == ""`: 現在のGoroutineがプリエンプションを無効にしていないことを確認します。特定のクリティカルセクションでは、プリエンプションが無効にされることがあります。
*   `Gosched()`: 上記の条件がすべて満たされた場合、`Gosched()` が呼び出され、現在のGoroutineはCPUをGoスケジューラーに譲渡します。これにより、他のGoroutine、特にGCコーディネーターが実行される機会が増え、GCの移行プロセスが迅速に進むことが期待されます。

この変更は、ミューテーターの割り当てを一時的に遅らせることで、GCコーディネーターがGCの開始または終了フェーズを完了するための時間を稼ぐという、一種の「ソフトな背圧」を提供します。コミットメッセージにある「TODO: This is a workaround. Either help the GC make the transition or block.」というコメントは、これが一時的な解決策であり、将来的にはより直接的にGCの移行を支援するか、あるいは割り当てを完全にブロックするような、より堅牢なメカニズムが必要であることを示唆しています。

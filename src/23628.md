## コミット

runtime: GCスタックバリアを実装

このコミットは、マーク終了時のスタック再スキャン量を最小限に抑えるためのスタックバリアを実装します。

現在、GCは各GCサイクル中にアクティブなゴルーチンのスタックを2回スキャンします。1回目はルート発見時の開始時、2回目はマーク終了時の終了時です。2回目のスキャンはワールドが停止している間に行われ、すべてのルートが確認されたことを保証します（ローカルスタック変数への書き込みにはライトバリアがないため）。しかし、これはポーズ時間がスタックサイズに比例することを意味します。特に再帰的なプログラムでは、これによりポーズ時間が目標の10msを超える可能性があります（例えば、50MBのヒープをスキャンするのに約150msかかります）。

スタック全体を再スキャンする必要があることは稀であり、特に大きなスタックでは、最初のスキャンと2回目のスキャンの間にスタック上のほとんどのフレームがアクティブでなかったため、これらのフレームへの変更（スタックを介して渡された非エスケープポインタによる）はライトバリアによって追跡されていました。

最初のスキャン以降にスタックがどれだけ巻き戻されたか（したがって、どれだけ再スキャンする必要があるか）を効率的に追跡するために、このコミットはスタックバリアを導入します。最初のスキャン中に、各スタックの指数関数的に間隔を空けたポイントで、スキャンはリターンPCをスタックバリア関数のPCで上書きします。「リターン」されると、スタックバリア関数はスタックがどれだけ巻き戻されたかを記録し、そのスタックポイントの元のリターンPCにジャンプします。これにより、2回目のスキャンは、ヒットしていない最も低いバリアまでしか進む必要がなくなります。

深く再帰的なプログラムの場合、これによりマーク終了時間（したがってポーズ時間）が大幅に短縮されます。issue #10898でリンクされているgoschemeの例では、この変更前はマーク終了時間が通常100〜500msでしたが、この変更により、マーク終了時間は通常10〜20msになりました。スタックのスキャン作業が削減された結果、goschemeの例の全体的な実行時間は20%削減されます。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行中に不要になったメモリを自動的に解放する重要な機能です。Go 1.5以降、GCは「コンカレントGC」として知られる方式を採用しており、GCの大部分の処理をアプリケーションの実行と並行して行うことで、プログラムの一時停止（ポーズタイム）を最小限に抑えることを目指しています。

しかし、このコミットが導入される以前のGo GCには、特にスタックのスキャンに関して課題がありました。GCサイクル中、アクティブなゴルーチン（Goにおける軽量スレッド）のスタックは2回スキャンされていました。

1.  **ルート発見時（GC開始時）**: GCの初期フェーズで、ヒープ上のオブジェクトへの参照（ルート）を特定するためにスタックがスキャンされます。
2.  **マーク終了時（GC終了時）**: GCの最終フェーズで、ワールドが停止している間（Stop-The-World: STW）、再度スタックがスキャンされます。この2回目のスキャンは、最初のスキャン以降にスタック上のローカル変数に新しいポインタが書き込まれた場合でも、すべてのルートが確実に捕捉されるようにするために必要でした。なぜなら、スタック上のローカル変数への書き込みにはライトバリアが適用されないため、コンカレントなマークフェーズ中にスタック上のポインタが変更されてもGCがそれを認識できない可能性があったからです。

この2回目のスタック再スキャンは、STWフェーズ中に実行されるため、その処理時間はポーズタイムに直接影響します。スタックサイズが大きい、特に深く再帰的なプログラムでは、この再スキャンに時間がかかり、GoのGCが目標とする10ミリ秒以下のポーズタイムを達成できないことが問題となっていました。コミットメッセージの例では、50MBのヒープをスキャンするのに約150msかかることが示されており、これは目標を大幅に上回ります。

この問題に対処し、ポーズタイムを削減するために、スタックバリアの導入が提案されました。スタックバリアは、スタック全体を再スキャンするのではなく、最初のスキャン以降に実際に変更された可能性のあるスタックの「部分」のみを効率的に再スキャンするためのメカニズムです。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoランタイムおよびGCに関する前提知識が必要です。

### Goのガベージコレクション (GC)

GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにしたコンカレントGCです。

-   **三色マーク**: オブジェクトを白、灰色、黒の3色で分類します。
    -   **白**: GCによってまだ到達可能かどうかが判断されていないオブジェクト（初期状態）。
    -   **灰色**: 到達可能であることが判明したが、そのオブジェクトが参照する他のオブジェクトがまだスキャンされていないオブジェクト。
    -   **黒**: 到達可能であることが判明し、そのオブジェクトが参照するすべてのオブジェクトもスキャン済みのオブジェクト。
-   **マークフェーズ**: ルート（グローバル変数、アクティブなゴルーチンのスタックなど）から到達可能なオブジェクトを灰色にマークし、そこから参照をたどって関連するオブジェクトを灰色から黒へとマークしていきます。Go 1.5以降は、このマークフェーズの大部分がアプリケーションの実行と並行して行われます（コンカレントマーク）。
-   **マーク終了フェーズ (Mark Termination)**: コンカレントマークフェーズの最後に、GCは一時的にワールドを停止させ（STW）、マークフェーズ中に見落とされた可能性のあるオブジェクト（特にスタック上のポインタの変更）を処理します。このフェーズで、本コミットが改善しようとしているスタックの再スキャンが行われます。
-   **スイープフェーズ**: マークされなかった白いオブジェクト（到達不可能なオブジェクト）を解放します。これもコンカレントに行われます。

### スタックとポインタ

Goのゴルーチンはそれぞれ独自のスタックを持っています。スタックには、関数のローカル変数や引数、リターンアドレス（呼び出し元に戻るためのPC: Program Counter）などが格納されます。

-   **スタック上のポインタ**: スタック上のローカル変数には、ヒープ上のオブジェクトを指すポインタが含まれることがあります。GCはこれらのポインタをルートとして認識し、ヒープ上のオブジェクトの到達可能性を判断します。
-   **ライトバリア (Write Barrier)**: GCがコンカレントに動作する際、アプリケーションがヒープ上のポインタを書き換えることでGCの認識と実際のメモリ状態に不整合が生じる可能性があります。これを防ぐために、ヒープ上のポインタの書き込み時に特定の処理（ライトバリア）を挿入し、GCがその変更を追跡できるようにします。しかし、GoのGCでは、**スタック上のローカル変数への書き込みにはライトバリアが適用されません**。これは、スタックの性質上、頻繁な書き込みが発生するため、ライトバリアのオーバーヘッドが大きいことと、スタックは一時的なデータが主であるため、GCのSTWフェーズで再スキャンすることで対応できると考えられていたためです。

### リターンPC (Return Program Counter)

関数が呼び出される際、呼び出し元の命令の次のアドレス（リターンPC）がスタックに保存されます。関数が終了すると、このリターンPCにジャンプして呼び出し元に戻ります。スタックフレームは、このリターンPCやローカル変数、引数などをまとめたものです。

### `getcallerpc` と `setcallerpc`

Goランタイムには、現在の関数の呼び出し元のPC（Program Counter）を取得する `getcallerpc` と、それを設定する `setcallerpc` といったアセンブリ関数が存在します。これらは、スタックのウォーク（スタックを遡って呼び出し履歴をたどること）や、特定のランタイム機能（例: `runtime.Callers`）の実装に利用されます。

## 技術的詳細

このコミットで導入されたスタックバリアは、マーク終了時のスタック再スキャンを最適化するための巧妙なメカニズムです。

### スタックバリアの基本概念

スタックバリアの目的は、最初のGCスキャン（`_GCscan`フェーズ）以降に、ゴルーチンのスタックがどれだけ「巻き戻されたか」（つまり、どれだけの関数呼び出しが完了してスタックフレームが解放されたか）を効率的に追跡することです。これにより、マーク終了時（`_GCmarktermination`フェーズ）の再スキャンでは、実際に変更された可能性のあるスタックの最下部から、まだヒットしていない最も低いバリアまでの範囲のみをスキャンすればよくなります。

### スタックバリアのインストール (`_GCscan` フェーズ)

1.  **リターンPCの上書き**: `_GCscan` フェーズ中に、GCは各ゴルーチンのスタックをスキャンします。この際、スタック上の特定のポイント（指数関数的に間隔を空けたリターンPC）を特定します。これらのリターンPCは、元の値ではなく、特別な `runtime.stackBarrier` 関数のアドレスで上書きされます。
2.  **元のリターンPCの保存**: 上書きされる元のリターンPCは、ゴルーチン構造体 (`g`) 内の `stkbar` スライスに保存されます。このスライスには、元のリターンPCのアドレス (`savedLRPtr`) とその値 (`savedLRVal`) が記録されます。

### スタックバリアのヒット (実行時)

1.  **`stackBarrier` 関数へのジャンプ**: アプリケーションの実行中に、上書きされたリターンPCに到達し、関数がリターンしようとすると、通常の呼び出し元に戻る代わりに `runtime.stackBarrier` 関数にジャンプします。
2.  **バリアの記録**: `runtime.stackBarrier` 関数は、どのスタックバリアがヒットしたかを `g.stkbarPos` をインクリメントすることで記録します。これは、スタックがそのポイントまで巻き戻されたことを意味します。
3.  **元のリターンPCへのジャンプ**: `runtime.stackBarrier` 関数は、`g.stkbar` に保存されていた元のリターンPCの値を取得し、そのアドレスにジャンプして、アプリケーションの通常の実行を再開します。これにより、アプリケーションはスタックバリアの存在を意識することなく、透過的に実行を継続できます。

### スタックバリアの利用 (`_GCmarktermination` フェーズ)

1.  **再スキャン範囲の決定**: `_GCmarktermination` フェーズでは、GCは各ゴルーチンのスタックを再スキャンします。この際、`g.stkbarPos` の値を確認します。
    -   もし `g.stkbarPos` が `g.stkbar` の長さと同じであれば、すべてのスタックバリアがヒットしており、スタック全体が巻き戻されたか、バリアがなかったことを意味します。この場合、スタック全体を再スキャンします。
    -   そうでなければ、`g.stkbar[g.stkbarPos]` が示すバリアが、まだヒットしていない最も低いバリアです。GCは、このバリアが指すスタックアドレスまでのみを再スキャンします。このアドレスより上のスタックフレームは、最初のスキャン以降アクティブでなかったか、またはライトバリアによって変更が追跡されているため、再スキャンは不要です。
2.  **スタックバリアの削除**: 再スキャン後、GCは残っているすべてのスタックバリアを削除し、元のリターンPCをスタックに戻します。

### `getcallerpc` と `setcallerpc` の変更

スタックバリアが導入されたことで、`getcallerpc` と `setcallerpc` の動作も変更されました。これらの関数がリターンPCを読み書きする際に、それが `stackBarrierPC` であれば、`g.stkbar` に保存されている元のリターンPCを扱うように修正されています。これにより、ランタイムの他の部分がスタックバリアの存在を意識せずに、正しいリターンPCを操作できるようになります。

### パニック/リカバリ時の処理

パニックが発生し、スタックが巻き戻される際にもスタックバリアが考慮されます。`gcSkipBarriers` 関数が導入され、パニックによってスタックが巻き戻される際に、その範囲内のスタックバリアが「ヒット済み」としてマークされます。これにより、GCが不整合な状態になるのを防ぎます。

## コアとなるコードの解説

このコミットの核心は、GoのGCポーズタイムを削減するために、スタックの再スキャンを最適化する「スタックバリア」の導入にあります。

### `runtime.stackBarrier` (アセンブリ関数)

これは、スタックバリアの主要なエントリポイントです。
```assembly
TEXT runtime·stackBarrier(SB),NOSPLIT,$0
    // We came here via a RET to an overwritten return PC.
    // AX may be live. Other registers are available.

    // Get the original return PC, g.stkbar[g.stkbarPos].savedLRVal.
    get_tls(CX) // 現在のゴルーチン (g) へのポインタを取得
    MOVL    g(CX), CX // g を CX レジスタにロード
    MOVL    (g_stkbar+slice_array)(CX), DX // g.stkbar の基底アドレスを DX にロード
    MOVL    g_stkbarPos(CX), BX // g.stkbarPos を BX にロード
    IMULL   $stkbar__size, BX // BX * sizeof(stkbar_entry) を計算
    MOVL    stkbar_savedLRVal(DX)(BX*1), BX // g.stkbar[g.stkbarPos].savedLRVal を BX にロード
    // Record that this stack barrier was hit.
    ADDL    $1, g_stkbarPos(CX) // g.stkbarPos をインクリメント
    // Jump to the original return PC.
    JMP BX // 元のリターンPCにジャンプ
```
このアセンブリコードは、関数がリターンする際に、本来のリターンアドレスが `runtime.stackBarrier` のアドレスに書き換えられている場合に実行されます。`g`（現在のゴルーチン）の情報を利用して、`g.stkbar` スライスに保存されている本来のリターンアドレス (`savedLRVal`) を取得し、`g.stkbarPos` をインクリメントしてこのバリアが「ヒットした」ことを記録します。最後に、取得した本来のリターンアドレスにジャンプして、プログラムの実行を継続させます。これにより、アプリケーションはスタックバリアの存在を意識することなく、透過的に動作します。

### `gcInstallStackBarrier` (Go関数)

```go
// gcInstallStackBarrier installs a stack barrier over the return PC of frame.
//go:nowritebarrier
func gcInstallStackBarrier(gp *g, frame *stkframe) {
    // ... (LRが0の場合はバリアをインストールしない)

    // Save the return PC and overwrite it with stackBarrier.
    var lrUintptr uintptr
    if usesLR { // LR (Link Register) を使用するアーキテクチャの場合
        lrUintptr = frame.sp
    } else { // それ以外の場合 (x86など)
        lrUintptr = frame.fp - regSize
    }
    lrPtr := (*uintreg)(unsafe.Pointer(lrUintptr)) // リターンPCへのポインタ
    // ... (デバッグ出力とアサーション)

    gp.stkbar = gp.stkbar[:len(gp.stkbar)+1] // stkbar スライスを拡張
    stkbar := &gp.stkbar[len(gp.stkbar)-1] // 新しいエントリへのポインタ
    stkbar.savedLRPtr = lrUintptr // 元のリターンPCのアドレスを保存
    stkbar.savedLRVal = uintptr(*lrPtr) // 元のリターンPCの値を保存
    *lrPtr = uintreg(stackBarrierPC) // リターンPCを stackBarrierPC で上書き
}
```
この関数は、GCの`_GCscan`フェーズ中に呼び出され、特定のスタックフレームにスタックバリアを「インストール」します。具体的には、そのフレームのリターンPCを`runtime.stackBarrier`関数のアドレス（`stackBarrierPC`）で上書きし、上書きされる前の元のリターンPCの値とアドレスをゴルーチン(`gp`)の`stkbar`スライスに保存します。

### `scanstack` (Go関数)

```go
//go:nowritebarrier
func scanstack(gp *g) {
    // ... (gcscanvalid のチェック)

    var barrierOffset, nextBarrier uintptr
    switch gcphase {
    case _GCscan:
        // Install stack barriers during stack scan.
        barrierOffset = firstStackBarrierOffset
        nextBarrier = gp.sched.sp + barrierOffset

        if gp.stkbarPos != 0 || len(gp.stkbar) != 0 {
            // ... (エラー処理)
        }

    case _GCmarktermination:
        if int(gp.stkbarPos) == len(gp.stkbar) {
            // gp hit all of the stack barriers (or there
            // were none). Re-scan the whole stack.
            nextBarrier = ^uintptr(0) // スタック全体を再スキャン
        } else {
            // Only re-scan up to the lowest un-hit
            // barrier. Any frames above this have not
            // executed since the _GCscan scan of gp and
            // any writes through up-pointers to above
            // this barrier had write barriers.
            nextBarrier = gp.stkbar[gp.stkbarPos].savedLRPtr // ヒットしていない最も低いバリアまで再スキャン
            // ... (デバッグ出力)
        }

        gcRemoveStackBarriers(gp) // スタックバリアを削除

    default:
        throw("scanstack in wrong phase")
    }

    // ... (スタックフレームをスキャンするロジック)
    scanframe := func(frame *stkframe, unused unsafe.Pointer) bool {
        // ... (scanframeworker の呼び出し)

        if frame.fp > nextBarrier { // 現在のフレームが再スキャン範囲より上にある場合
            if gcphase == _GCscan && n != 0 {
                gcInstallStackBarrier(gp, frame) // スタックバリアをインストール
                barrierOffset *= 2 // 次のバリアの間隔を指数関数的に広げる
                nextBarrier = gp.sched.sp + barrierOffset
            } else if gcphase == _GCmarktermination {
                // We just scanned a frame containing
                // a return to a stack barrier. Since
                // this frame never returned, we can
                // stop scanning.
                return false // 再スキャンを停止
            }
        }
        // ...
        return true
    }
    gentraceback(^uintptr(0), ^uintptr(0), 0, gp, 0, nil, 0x7fffffff, scanframe, nil, 0)
}
```
`scanstack`関数は、GCの`_GCscan`フェーズと`_GCmarktermination`フェーズの両方でスタックを処理します。
-   `_GCscan`フェーズでは、`gcInstallStackBarrier`を呼び出して、指数関数的に間隔を空けたポイントにスタックバリアをインストールします。
-   `_GCmarktermination`フェーズでは、`gp.stkbarPos`（ヒットしたバリアの数）に基づいて、再スキャンが必要なスタックの範囲を決定します。これにより、スタック全体ではなく、実際に変更された可能性のある部分のみを効率的にスキャンできます。スキャン後には`gcRemoveStackBarriers`を呼び出して、スタックバリアを元の状態に戻します。

これらの変更により、GoのGCは、特に深く再帰的なプログラムにおいて、STWポーズタイムを大幅に削減できるようになりました。スタックバリアは、スタックの巻き戻しを効率的に追跡し、不要な再スキャンを回避することで、GCのパフォーマンスを向上させています。

## 変更の背景

このコミットの背景には、Go言語の初期段階におけるコンパイラ（特に`6g`、当時のGoコンパイラの一つ）のバグ、または型システムに関する未解決の問題が存在していました。コミット前のコードには、`src/lib/syscall/types_amd64_darwin.go`と`src/lib/syscall/types_amd64_linux.go`の両方に以下のTODOコメントがありました。

```go
// TODO(rsc): should be method on WaitStatus,
// not *WaitStatus, but causes problems when
// embedding in a *Waitmsg in package os.
// Need to find the 6g bug.
```

このコメントは、`WaitStatus`型に定義されるべきメソッドが、実際には`*WaitStatus`（`WaitStatus`へのポインタ）に対して定義されていることを示しています。その理由は、`WaitStatus`が`os`パッケージの`Waitmsg`構造体に埋め込まれた際に問題が発生するためでした。この問題は当時の`6g`コンパイラのバグとして認識されており、このコミットは、そのバグが修正されたか、または回避策が不要になったことを示しています。

具体的には、`WaitStatus`のメソッドをポインタレシーバ（`*WaitStatus`）ではなく値レシーバ（`WaitStatus`）で定義できるようになり、コードがより自然で意図された形に修正されたことを意味します。

## 前提知識の解説

### 1. Go言語のメソッドとレシーバ

Go言語では、関数を型に関連付けることで「メソッド」を定義できます。メソッドは、そのメソッドが操作する値（またはポインタ）を「レシーバ」として受け取ります。レシーバには「値レシーバ」と「ポインタレシーバ」の2種類があります。

*   **値レシーバ (Value Receiver)**: `func (t MyType) MyMethod() {}` のように定義されます。メソッド内でレシーバ`t`の値を変更しても、元の値には影響しません。これは、メソッドがレシーバの「コピー」を受け取るためです。
*   **ポインタレシーバ (Pointer Receiver)**: `func (t *MyType) MyMethod() {}` のように定義されます。メソッド内でレシーバ`t`が指す値を変更すると、元の値も変更されます。これは、メソッドがレシーバの「アドレス」を受け取るためです。

一般的に、レシーバの値を変更する必要がある場合や、レシーバが大きな構造体でコピーのコストを避けたい場合はポインタレシーバを使用します。そうでない場合は値レシーバを使用するのがGoの慣習です。

### 2. `syscall`パッケージと`WaitStatus`

`syscall`パッケージは、オペレーティングシステムが提供する低レベルのプリミティブ（システムコール）へのアクセスを提供します。これには、プロセス管理、ファイルI/O、ネットワーク操作などが含まれます。

`WaitStatus`型は、Unix系システムにおける`waitpid`システムコールなどから返されるプロセスの終了ステータスを表すために使用されます。このステータスは通常、プロセスの終了理由（正常終了、シグナルによる終了、停止など）や終了コード、シグナル番号などの情報を含んでいます。`WaitStatus`は通常、ビットフィールドとしてエンコードされた整数値（この場合は`uint32`）です。

### 3. `os`パッケージと`Waitmsg`

`os`パッケージは、オペレーティングシステムに依存しないインターフェースを提供し、ファイルシステム操作、プロセス管理、環境変数へのアクセスなどを可能にします。

`Waitmsg`は、`os`パッケージ内でプロセスの終了情報をカプセル化するために使用される構造体であると推測されます。`WaitStatus`がこの`Waitmsg`構造体に埋め込まれる（匿名フィールドとして含まれる）ことで、`Waitmsg`のインスタンスから直接`WaitStatus`のメソッドを呼び出すことができるようになります。

### 4. 埋め込み (Embedding)

Go言語の「埋め込み」は、ある構造体の中に別の構造体を匿名フィールドとして含めることで、その埋め込まれた構造体のフィールドやメソッドを、外側の構造体のフィールドやメソッドであるかのように直接アクセスできるようにする機能です。これは、オブジェクト指向プログラミングにおける継承に似た機能を提供しますが、Goでは「コンポジション（合成）」として扱われます。

例えば、`type Outer struct { Inner }` のように定義すると、`Outer`のインスタンスから`Inner`のメソッドを直接呼び出すことができます。

## 技術的詳細

このコミットの技術的詳細は、Go言語のコンパイラが、埋め込みとメソッドレシーバの組み合わせをどのように処理するかという点にあります。

元のTODOコメントが示唆しているのは、`WaitStatus`が`Waitmsg`に埋め込まれ、かつ`WaitStatus`のメソッドが値レシーバで定義されている場合に、コンパイラが正しくメソッド呼び出しを解決できないバグが存在したということです。

具体的には、`WaitStatus`のメソッドが`func (w WaitStatus) Exited() bool`のように値レシーバで定義されているとします。
そして、`os`パッケージの`Waitmsg`が`WaitStatus`を埋め込んでいるとします。

```go
type Waitmsg struct {
    // ... other fields ...
    WaitStatus // 匿名フィールドとして埋め込み
}
```

この場合、`Waitmsg`のインスタンス`m`から`m.Exited()`のようにメソッドを呼び出すと、Goの埋め込みのルールにより、`Waitmsg`は埋め込まれた`WaitStatus`の`Exited`メソッドを「昇格」させ、あたかも`Waitmsg`自身のメソッドであるかのように振る舞います。

しかし、もし当時の`6g`コンパイラにバグがあったとすると、この「昇格」されたメソッド呼び出しが、`WaitStatus`が値レシーバである場合に正しく処理されなかった可能性があります。そのため、一時的な回避策として、`WaitStatus`のメソッドを`func (wp *WaitStatus) Exited() bool`のようにポインタレシーバで定義する必要があったと考えられます。ポインタレシーバであれば、`Waitmsg`が`WaitStatus`のポインタを保持しているか、あるいは`Waitmsg`自身がポインタとして扱われる場合に、コンパイラがより単純なポインタデリファレンスとして処理できたのかもしれません。

このコミットでは、`WaitStatus`のメソッドがポインタレシーバから値レシーバに変更されています。これは、以下のいずれかの理由によるものです。

1.  **`6g`コンパイラのバグが修正された**: 最も可能性が高いシナリオです。コンパイラが埋め込みと値レシーバの組み合わせを正しく処理できるようになり、回避策が不要になった。
2.  **設計変更**: `Waitmsg`が`WaitStatus`をポインタとして埋め込むようになった、あるいは`Waitmsg`のインスタンスが常にポインタとして扱われるようになったなど、関連する型の設計が変更され、値レシーバでも問題なくなった。ただし、このコミットの差分からは`Waitmsg`側の変更は読み取れないため、コンパイラの修正が主因である可能性が高いです。

この変更により、`WaitStatus`のメソッドは、その型のセマンティクス（値のコピーで十分であり、元の値を変更しない）に合致する値レシーバで定義されるようになり、コードの意図がより明確になりました。また、`// TODO(rsc): no pointer`というコメントも削除されており、メソッド内で`*wp`を`w`に代入してポインタをデリファレンスする冗長な処理も不要になっています。

## コアとなるコードの変更箇所

変更は主に以下の2つのファイルで行われています。

1.  `src/lib/syscall/types_amd64_darwin.go`
2.  `src/lib/syscall/types_amd64_linux.go`

これらのファイル内で、`WaitStatus`型に定義されている複数のメソッドのレシーバが、`*WaitStatus`から`WaitStatus`に変更されています。

**変更例（`Exited`メソッド）:**

**変更前:**
```go
func (wp *WaitStatus) Exited() bool {
	w := *wp;  // TODO(rsc): no pointer
	return w&mask == exited;
}
```

**変更後:**
```go
func (w WaitStatus) Exited() bool {
	return w&mask == exited;
}
```

同様の変更が、`ExitStatus`, `Signaled`, `Signal`, `CoreDump`, `Stopped`, `Continued`, `StopSignal`といった`WaitStatus`の全てのメソッドに適用されています。

また、各メソッドの定義の上にあったTODOコメントと、メソッド内部の`w := *wp;`というポインタデリファレンスの行も削除されています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`WaitStatus`型に定義されたメソッドのレシーバの型を、ポインタ型（`*WaitStatus`）から値型（`WaitStatus`）へ変更した点です。

例えば、`Exited()`メソッドを例にとると、変更前は`func (wp *WaitStatus) Exited() bool`と定義されていました。これは、`Exited`メソッドが`WaitStatus`型のポインタを受け取ることを意味します。メソッドの内部では、`w := *wp;`という行でポインタ`wp`が指す値がデリファレンスされ、その値`w`に対して操作が行われていました。このデリファレンスは、本来値レシーバで十分な操作であるにもかかわらず、ポインタレシーバを使わざるを得なかった当時の状況（TODOコメントが示す`6g`のバグ）を反映しています。

変更後は、`func (w WaitStatus) Exited() bool`と定義されています。これは、`Exited`メソッドが`WaitStatus`型の値のコピーを受け取ることを意味します。メソッドの内部では、直接レシーバ`w`に対して操作が行われます。`WaitStatus`は`uint32`のエイリアスであり、そのメソッドは`WaitStatus`の値を読み取るだけで変更しないため、値レシーバが適切です。

この変更は、Go言語のメソッドレシーバの選択におけるベストプラクティスに沿ったものです。値レシーバは、メソッドがレシーバの値を変更しない場合に推奨されます。これにより、コードの意図が明確になり、不必要なポインタのデリファレンスがなくなります。

この修正は、Goコンパイラ（特に`6g`）の成熟と安定性を示しており、初期のGo開発におけるコンパイラのバグが徐々に解消されていった過程の一部を垣間見ることができます。

# [インデックス 28029] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおけるルール生成メカニズムの内部的な変更です。具体的には、複数行にわたるSSAルールの「行番号」の定義方法を修正し、ルールの変換アクションを示す `->` 記号が出現する行をそのルールの行番号として扱うように変更しています。これにより、コンパイラ開発者がルールのカバレッジ分析を行う際に、より正確で意味のある情報が得られるようになります。

## コミット

cmd/compile: ルールの行番号は `->` の位置とする

複数行にわたるルールの行番号を、`->` が出現する行の行番号として定義します。これにより、ルールのカバレッジ分析がより適切に行われるようになります。

## 変更の背景

Goコンパイラは、コードの最適化のためにSSA（Static Single Assignment）形式の中間表現を使用します。このSSA形式のコードを変換・最適化するために、様々な「ルール」が定義されています。これらのルールは、`src/cmd/compile/internal/ssa/gen/rulegen.go` のようなファイルによって生成・管理されています。

以前のGoコンパイラでは、複数行にわたるSSAルールの行番号は、そのルールの最終行に割り当てられていました。しかし、ルールの実際の「アクション」や変換が始まるのは、通常 `->` 記号が出現する行です。ルールの最終行をそのルールの代表的な行番号とすることは、コンパイラ開発者がルールの動作をデバッグしたり、ルールのカバレッジ（どのルールがテストによって実行されたか）を分析したりする際に、直感的ではない、あるいは誤解を招く可能性がありました。

このコミットの目的は、この行番号の定義をより意味のあるものにすることです。`->` が出現する行をルールの行番号とすることで、ルールの変換ロジックの開始点と行番号が一致し、コンパイラの内部的な「ルールカバー分析」の精度と有用性が向上します。これにより、コンパイラの品質向上やデバッグ作業の効率化に貢献します。

## 前提知識の解説

### GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを機械語に変換する過程で、複数のステージを経由します。その中でも重要な最適化ステージの一つが、SSA（Static Single Assignment）形式のバックエンドです。SSA形式では、各変数が一度だけ代入されるようにコードが変換され、これによりデータフロー解析や最適化が容易になります。Goコンパイラは、このSSA形式に対して様々な最適化パスを適用し、より効率的な機械語を生成します。

### SSAルール

SSAバックエンドでは、特定のパターンにマッチするSSA命令列を、より最適化された別の命令列に書き換えるための「ルール」が多数定義されています。これらのルールは、例えば「`x + 0` は `x` に書き換えられる」といった具体的な最適化や、特定のアーキテクチャに特化した命令への変換などを記述します。これらのルールは、通常、専用のDSL（Domain Specific Language）で記述され、`rulegen.go` のようなツールによってGoのコードに変換されます。

### `cmd/compile/internal/ssa/gen/rulegen.go`

このファイルは、Goコンパイラの内部ツールであり、SSA最適化ルールを記述したテキストファイル（例: `arch.rules`）を読み込み、それらをGoのソースコード（SSAルールを実装する関数など）に変換する役割を担っています。つまり、SSAルールをコンパイラが実際に利用できる形に「生成」するジェネレータの一部です。

### ルールカバー分析

「ルールカバー分析」とは、Goコンパイラの開発プロセスにおいて、SSA最適化ルールがどれだけテストによって網羅されているかを評価するための内部的な分析手法です。これは、一般的なGoプログラムのコードカバレッジ（`go test -cover` などで測定されるもの）とは異なり、コンパイラ自身の内部ロジック、特にSSAルールの網羅性を確認するためのものです。
コンパイラ開発者は、新しい最適化ルールを追加したり、既存のルールを変更したりする際に、そのルールが意図通りに動作し、かつ既存のコードパスを破壊しないことを確認する必要があります。ルールカバー分析は、どのルールがテストスイートによって実行されたか、あるいは実行されなかったかを特定するのに役立ち、テストの不足している部分を特定したり、ルールのデバッグを支援したりします。

## 技術的詳細

このコミットは、`rulegen.go` がSSAルールをパースする際の、ルールの行番号の扱いを変更しています。

**変更前の挙動:**
以前は、複数行にわたるSSAルール（例: `(Opcode arg1 arg2) -> (NewOpcode arg3)` のように、パターンと結果が複数行にわたる場合）の行番号は、そのルールの定義が終了する最終行の行番号が割り当てられていました。

**変更後の挙動:**
このコミットにより、ルールの行番号は、ルールの「変換」部分を示す `->` 記号が出現する行の行番号として定義されるようになりました。

**具体的な影響:**
`rulegen.go` は、ルールをパースする際に、各ルールにそのソースコード上の位置を示すメタデータ（ファイル名と行番号）を付与します。このメタデータは、コンパイラのデバッグ情報や、前述のルールカバー分析などで利用されます。
`->` 記号は、SSAルールにおいて「このパターンにマッチしたら、このように変換する」という変換の開始点を示す重要なシンボルです。この記号がある行をルールの代表的な行番号とすることで、ルールの「アクション」がどこで定義されているかをより正確に指し示すことができます。

これにより、ルールカバー分析ツールが、どのルールが実行されたかを報告する際に、より直感的で意味のある行番号を提供できるようになります。例えば、あるテストケースが特定のSSAルールを発火させた場合、そのルールの `->` がある行がカバレッジレポートに表示されるため、開発者はルールのどの部分がカバーされたかを容易に理解できます。これは、コンパイラの内部開発におけるデバッグ効率と品質保証の向上に寄与します。

## コアとなるコードの解説

`src/cmd/compile/internal/ssa/gen/rulegen.go` 内の `genRules` 関数は、SSAルール定義を読み込み、パースし、Goコード内のデータ構造に変換する主要なロジックを含んでいます。

1.  **`ruleLineno` 変数の導入**:
    `var ruleLineno int // line number of "->"`
    新しい変数 `ruleLineno` が導入されました。この変数は、現在処理中のルールにおいて `->` 記号が初めて出現した行の行番号を保持するために使用されます。初期値は `0` です。

2.  **`->` 出現時の `ruleLineno` の設定**:
    ```go
    		if !strings.Contains(rule, "->") {
    			continue
    		}
    		if ruleLineno == 0 {
    			ruleLineno = lineno
    		}
    ```
    `scanner.Scan()` ループ内で、現在の行 (`line`) を `rule` 文字列に追加していきます。`rule` 文字列が `->` を含み、かつ `ruleLineno` がまだ設定されていない（つまり、そのルールの `->` が初めて見つかった）場合、現在の行番号 `lineno` が `ruleLineno` に格納されます。これにより、`->` がある行の行番号が記録されます。

3.  **`loc` 文字列の生成における `ruleLineno` の使用**:
    ```go
    -		loc := fmt.Sprintf("%s.rules:%d", arch.name, lineno)
    +		loc := fmt.Sprintf("%s.rules:%d", arch.name, ruleLineno)
    ```
    ルールが完全にパースされ、`Rule` 構造体（`blockrules` または `oprules` に追加される）が構築される際、そのルールのソース位置を示す `loc` フィールドが生成されます。変更前は、この `loc` にはルール定義の最終行の `lineno` が使用されていましたが、変更後は `ruleLineno` が使用されるようになりました。これにより、ルールのメタデータとして記録される行番号が、`->` が出現する行に変わります。

4.  **`ruleLineno` のリセット**:
    ```go
    		rule = ""
    +		ruleLineno = 0
    ```
    一つのルールが正常に処理され、`Rule` 構造体に追加された後、次のルールを処理するために `rule` 文字列がクリアされ、同時に `ruleLineno` も `0` にリセットされます。これは、次のルールの `->` が見つかったときに、新しい行番号を正しく記録できるようにするためです。

これらの変更により、GoコンパイラのSSAバックエンドで生成されるルールの内部的な行番号情報が、ルールの意味的な開始点（`->` の位置）と一致するようになり、コンパイラ開発者にとってのデバッグや分析の利便性が向上します。

## コミット

このコミットは、Goの静的解析ツールである`cmd/vet`における複合リテラルのキーなしフィールドのチェックを改善するものです。具体的には、スライス型エイリアスに対する誤った警告を修正し、コードの簡素化を図っています。

## 変更の背景

この変更の主な背景には、`cmd/vet`ツールが複合リテラル内のキーなしフィールドを誤って報告するという問題がありました。特に、スライス型（`[]T`）の複合リテラルに対して、本来はキーなしフィールドが許容されるべきであるにもかかわらず、`vet`が警告を発してしまうケースが存在しました。

具体的には、Go issue #9171「cmd/vet: reporting "composite literal uses unkeyed fields" for slice types」で報告された問題が挙げられます。この問題は、`vet`がスライス型を構造体型と誤認し、キーなしフィールドの使用を不適切に指摘するというものでした。以前の`vet`の実装では、この誤検知を回避するために、一部のスライス型エイリアスをホワイトリストに登録していましたが、これは根本的な解決策ではありませんでした。

このコミットは、`vet`の型チェックロジックを改善し、スライス型を正しく識別できるようにすることで、ホワイトリストによる回避策を不要にし、より正確な静的解析を実現することを目的としています。これにより、開発者は不必要な警告に煩わされることなく、本当に問題のあるキーなしフィールドの使用に集中できるようになります。

Go issue #15408および#11041についても言及されていますが、これらは直接的な`cmd/vet`のバグ報告としては公開されていません。しかし、コミットメッセージの文脈から、これらも複合リテラルのチェックに関連する、あるいは影響を受ける問題であった可能性が示唆されます。このコミットは、これらの関連する問題も解決または更新する広範な改善の一部であると考えられます。

## 前提知識の解説

### Goの複合リテラル (Composite Literals)

Go言語において、複合リテラルは構造体、配列、スライス、マップなどの複合型を初期化するための構文です。
例えば、構造体の複合リテラルは以下のようになります。

```go
type Person struct {
    Name string
    Age  int
}

// キー付きフィールド
p1 := Person{Name: "Alice", Age: 30}

// キーなしフィールド (フィールドの宣言順に値を指定)
p2 := Person{"Bob", 25}
```

スライスや配列の複合リテラルは、通常キーなしで要素を列挙します。

```go
// スライスの複合リテラル
s1 := []int{1, 2, 3}

// 配列の複合リテラル
a1 := [3]string{"apple", "banana", "cherry"}
```

`cmd/vet`は、構造体の複合リテラルでキーなしフィールドを使用している場合に警告を発することがあります。これは、構造体のフィールドが追加・削除・並べ替えられた際に、コードの意図しない変更やバグを引き起こす可能性があるため、ベストプラクティスとしてキー付きフィールドの使用が推奨されるためです。しかし、スライスや配列ではキーなしフィールドが自然な初期化方法であり、警告されるべきではありません。

### `cmd/vet`ツール

`cmd/vet`はGo言語の標準ツールチェーンに含まれる静的解析ツールです。コンパイラでは検出できないが、潜在的なバグや疑わしいコード構造を報告します。例えば、`Printf`フォーマット文字列と引数の不一致、到達不能なコード、ロックの誤用などを検出します。
`vet`はヒューリスティックに基づいて動作するため、時には誤検知（false positive）を報告することもあります。開発者はこれらの警告をレビューし、必要に応じてコードを修正するか、`vet`のチェックを調整する必要があります。

### `go/types`パッケージ

`go/types`パッケージは、Goプログラムの型情報を扱うための標準ライブラリです。AST (Abstract Syntax Tree) を解析し、型チェックを実行して、式や宣言の型を決定します。`cmd/vet`のような静的解析ツールは、このパッケージを利用してコードのセマンティックな情報を取得し、より正確な分析を行います。以前の`vet`の実装では、型情報を手動で推測する部分がありましたが、`go/types`パッケージを適切に利用することで、より堅牢で正確な型チェックが可能になります。

### ホワイトリスト (Whitelist)

ソフトウェア開発において、ホワイトリストは「許可された項目」のリストです。この文脈では、`cmd/vet`が特定の型に対してはキーなし複合リテラルのチェックをスキップするように設定されたリストを指します。以前は、スライス型エイリアスが誤って構造体と判断されるのを防ぐために、これらの型がホワイトリストに登録されていました。しかし、これは問題の根本的な解決ではなく、一時的な回避策でした。

## 技術的詳細

このコミットの技術的な核心は、`cmd/vet`が複合リテラルの型を識別し、キーなしフィールドの使用をチェックするロジックを根本的に改善した点にあります。

以前の`cmd/vet`の`checkUnkeyedLiteral`関数は、`ast.CompositeLit`の`Type`フィールドを直接検査し、`ast.ArrayType`、`ast.MapType`、`ast.StructType`、`ast.Ident`といったASTノードの型に基づいて、複合リテラルが構造体であるかどうかを推測していました。特に、`pkg.Name.Sel.Name`のようなセレクタ式で表現される型については、`pkgPath`関数を使ってパッケージパスを解決し、`isStruct`関数を使ってそれが構造体であるかを判断していました。このアプローチは、型エイリアスや複雑な型定義の場合に不正確な結果を招く可能性がありました。特に、スライス型エイリアスが構造体として誤認されることが問題でした。

このコミットでは、`go/types`パッケージを導入し、より正確な型情報に基づいて判断を行うように変更されました。
新しい`checkUnkeyedLiteral`関数では、まず`f.pkg.types[cl].Type`を使用して、複合リテラル`cl`の正確な型情報を取得します。これにより、ASTノードの構文的な情報だけでなく、Goコンパイラが認識するセマンティックな型情報にアクセスできるようになります。

主要な変更点は以下の通りです。

1.  **`go/types`パッケージの利用**: `go/types`パッケージから取得した`types.Type`オブジェクトの`Underlying()`メソッドを使用して、基底型が`*types.Struct`であるかどうかを直接チェックします。これにより、型エイリアスが元の型（例えばスライス）に解決され、`vet`がスライス型を構造体と誤認することがなくなります。
2.  **`isLocalType`関数の導入**: 複合リテラルがローカルに定義された型（現在のパッケージ内、または匿名構造体リテラル）である場合は、キーなしフィールドの使用を許可する新しいロジックが導入されました。これは、ローカルな型であればフィールドの変更による影響が限定的であるため、警告の必要性が低いという判断に基づいています。`isLocalType`関数は、型名が`struct{...}`で始まる匿名構造体や、現在のパッケージパスで始まる型名をローカル型として識別します。テストパッケージ（`_test`サフィックスを持つパッケージ）の場合も、その基底パッケージの型をローカルとして扱います。
3.  **`pkgPath`および`isStruct`関数の削除**: 以前の型推測ロジックを担っていた`pkgPath`関数と`isStruct`関数は、`go/types`パッケージによる正確な型情報取得に置き換えられたため、`src/cmd/vet/types.go`から削除されました。これにより、コードベースが簡素化され、保守性が向上しました。
4.  **ホワイトリストの縮小**: `src/cmd/vet/internal/whitelist/whitelist.go`から、スライス型エイリアス（例: `unicode.SpecialCase`, `scanner.ErrorList`など）がホワイトリストから削除されました。これは、`vet`がこれらの型をスライスとして正しく識別できるようになったため、もはやホワイトリストによる除外が不要になったことを意味します。ホワイトリストには、`image/color`パッケージの特定の構造体型など、フィールドが固定されており、キーなしリテラルが安全に使用できると判断された型のみが残されました。

これらの変更により、`cmd/vet`は複合リテラルの型をより正確に判断し、構造体型に対してのみキーなしフィールドの警告を発するようになり、スライス型に対する誤検知が解消されました。

## コアとなるコードの変更箇所

### `src/cmd/vet/composite.go`

- `checkUnkeyedLiteral`関数の大幅な書き換え。
    - `ast.CompositeLit`の`Type`フィールドを直接解析する代わりに、`f.pkg.types[cl].Type`を使用して`go/types`パッケージから正確な型情報を取得するようになった。
    - 取得した型が`*types.Struct`の基底型を持つかどうかで、構造体リテラルであるかを判断するようになった。
    - `isLocalType`関数が導入され、ローカル型（匿名構造体や現在のパッケージ内の型）の複合リテラルではキーなしフィールドを許可するようになった。
    - 以前の`pkgPath`や`isStruct`を使った複雑な型推測ロジックが削除された。
    - 警告メッセージの生成方法が簡素化された。
- 新しいヘルパー関数`isLocalType`が追加された。

### `src/cmd/vet/internal/whitelist/whitelist.go`

- `UnkeyedLiteral`マップから、`crypto/x509/pkix.RDNSequence`、`database/sql.RawBytes`、`encoding/asn1.ObjectIdentifier`、`go/scanner.ErrorList`、`net.IP`、`sort.IntSlice`、`unicode.SpecialCase`などのスライス型エイリアスが多数削除された。
- `image/color.NYCbCrA`と`unicode.Range16`がホワイトリストに追加された。

### `src/cmd/vet/testdata/composite.go`

- 新しいテストケースが追加され、スライス型（`[]struct{}`や`[]MyStruct`）の複合リテラルがキーなしで正しく扱われることを確認している。
- `unicode.SpecialCase`や`scanner.ErrorList`のような以前ホワイトリストに登録されていた型が、キーなしフィールドで警告されるべきではないことを示すテストが追加された。
- `flag.Flag`のような構造体リテラルがキーなしで使われた場合に警告されるべきであることを示すテストが追加された。
- `unknownpkg.Foobar`のような未知のパッケージの型がチェックされないことを示すテストが追加された（issue 15408に関連する可能性）。

### `src/cmd/vet/types.go`

- `isStruct`関数が完全に削除された。この機能は`go/types`パッケージの利用によって置き換えられた。

## コアとなるコードの解説

### `src/cmd/vet/composite.go` の `checkUnkeyedLiteral` 関数

```go
func checkUnkeyedLiteral(f *File, node ast.Node) {
	cl := node.(*ast.CompositeLit)

	typ := f.pkg.types[cl].Type
	if typ == nil {
		// cannot determine composite literals' type, skip it
		return
	}
	typeName := typ.String()
	if *compositeWhiteList && whitelist.UnkeyedLiteral[typeName] {
		// skip whitelisted types
		return
	}
	if _, ok := typ.Underlying().(*types.Struct); !ok {
		// skip non-struct composite literals
		return
	}
	if isLocalType(f, typeName) {
		// allow unkeyed locally defined composite literal
		return
	}

	// check if the CompositeLit contains an unkeyed field
	allKeyValue := true
	for _, e := range cl.Elts {
		if _, ok := e.(*ast.KeyValueExpr); !ok {
			allKeyValue = false
			break
		}
	}
	if allKeyValue {
		// all the composite literal fields are keyed
		return
	}

	f.Badf(cl.Pos(), "%s composite literal uses unkeyed fields", typeName)
}
```

この関数は、複合リテラル`cl`がキーなしフィールドを使用している場合に警告を発するかどうかを決定する中心的なロジックを含んでいます。

1.  `cl := node.(*ast.CompositeLit)`: 渡されたASTノードを`*ast.CompositeLit`型にキャストします。
2.  `typ := f.pkg.types[cl].Type`: ここが最も重要な変更点です。`f.pkg.types`は`go/types`パッケージによって構築された型情報マップであり、ASTノード`cl`に対応する正確な`types.Type`オブジェクトを取得します。これにより、コンパイラが認識するセマンティックな型情報に基づいて処理を進めることができます。
3.  `if typ == nil { return }`: 型情報が取得できない場合は、チェックをスキップします。
4.  `typeName := typ.String()`: 型の文字列表現を取得します。
5.  `if *compositeWhiteList && whitelist.UnkeyedLiteral[typeName] { return }`: ホワイトリストに登録されている型であれば、チェックをスキップします。これは、特定の型に対してはキーなしリテラルが意図されたものである場合に利用されます。
6.  `if _, ok := typ.Underlying().(*types.Struct); !ok { return }`: ここで、取得した型の基底型が`*types.Struct`であるかをチェックします。`Underlying()`メソッドは、型エイリアスやポインタ型などの基底となる型を返します。このチェックにより、スライス型やマップ型などが構造体として誤認されることを防ぎます。もし構造体でなければ、キーなしフィールドのチェックは不要なのでスキップします。
7.  `if isLocalType(f, typeName) { return }`: `isLocalType`関数を呼び出し、複合リテラルがローカルに定義された型であるかを判断します。ローカル型であれば、キーなしフィールドの使用が許可されるため、チェックをスキップします。
8.  `allKeyValue := true ...`: ここから、複合リテラルの要素をループし、すべての要素が`ast.KeyValueExpr`（キーと値のペア）であるかをチェックします。一つでもキーなしの要素（単なる式）があれば、`allKeyValue`は`false`になります。
9.  `if allKeyValue { return }`: すべてのフィールドがキー付きであれば、警告は不要なのでスキップします。
10. `f.Badf(cl.Pos(), "%s composite literal uses unkeyed fields", typeName)`: 上記の条件をすべて通過し、かつキーなしフィールドが存在する場合に、`vet`は警告を発します。

### `src/cmd/vet/composite.go` の `isLocalType` 関数

```go
func isLocalType(f *File, typeName string) bool {
	if strings.HasPrefix(typeName, "struct{") {
		// struct literals are local types
		return true
	}

	pkgname := f.pkg.path
	if strings.HasPrefix(typeName, pkgname+".") {
		return true
	}

	// treat types as local inside test packages with _test name suffix
	if strings.HasSuffix(pkgname, "_test") {
		pkgname = pkgname[:len(pkgname)-len("_test")]
	}
	return strings.HasPrefix(typeName, pkgname+".")
}
```

このヘルパー関数は、与えられた`typeName`が現在のパッケージ内で定義されたローカルな型であるかを判断します。

1.  `if strings.HasPrefix(typeName, "struct{") { return true }`: 匿名構造体リテラル（例: `struct{ A int }{A: 1}`）は常にローカルな型と見なされます。
2.  `pkgname := f.pkg.path`: 現在解析中のファイルのパッケージパスを取得します。
3.  `if strings.HasPrefix(typeName, pkgname+".") { return true }`: 型名が現在のパッケージパスで始まる場合（例: `myproject/mypackage.MyStruct`）、それはローカルな型と見なされます。
4.  テストパッケージの考慮: `_test`サフィックスを持つテストパッケージの場合、その基底となるパッケージ（例: `myproject/mypackage_test`であれば`myproject/mypackage`）の型もローカルとして扱います。これは、テストコード内で定義された型や、テスト対象のパッケージの型がローカルであると判断されるようにするためです。

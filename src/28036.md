# [インデックス 28036] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）スキャン中のゴルーチン（goroutine）の状態管理に関するバグ修正と最適化を目的としています。具体的には、`casfrom_Gscanstatus`関数内で`gcscanvalid`フラグをクリアする処理が、競合状態（race condition）を引き起こす可能性があり、また不要であったため削除されました。これにより、GCの正確性と将来的な「ダーティスタック」追跡機能との整合性が向上します。

## 元コミット内容

```
runtime: don't clear gcscanvalid in casfrom_Gscanstatus

Currently we clear gcscanvalid in both casgstatus and
casfrom_Gscanstatus if the new status is _Grunning. This is very
important to do in casgstatus. However, this is potentially wrong in
casfrom_Gscanstatus because in this case the caller doesn't own gp and
hence the write is racy. Unlike the other _Gscan statuses, during
_Gscanrunning, the G is still running. This does not indicate that
it's transitioning into a running state. The scan simply hasn't
happened yet, so it's neither valid nor invalid.

Conveniently, this also means clearing gcscanvalid is unnecessary in
this case because the G was already in _Grunning, so we can simply
remove this code. What will happen instead is that the G will be
preempted to scan itself, that scan will set gcscanvalid to true, and
then the G will return to _Grunning via casgstatus, clearing
gcscanvalid.

This fix will become necessary shortly when we start keeping track of
the set of G's with dirty stacks, since it will no longer be
idempotent to simply set gcscanvalid to false.
```

## 変更の背景

Goランタイムのガベージコレクション（GC）は、プログラムの実行中に不要になったメモリを自動的に解放する重要な機能です。GCプロセス中、ランタイムはゴルーチンのスタックをスキャンして、到達可能なオブジェクトを特定します。このスキャンが正確に行われるためには、ゴルーチンの状態が正しく管理されている必要があります。

このコミットの背景には、`gcscanvalid`というフラグの取り扱いにおける潜在的な問題がありました。`gcscanvalid`は、ゴルーチンのスタックがGCスキャンに対して有効であるかどうかを示すフラグです。

既存の実装では、`casgstatus`と`casfrom_Gscanstatus`の両方の関数で、ゴルーチンの新しい状態が`_Grunning`（実行中）になる場合に`gcscanvalid`を`false`にクリアしていました。`casgstatus`でのクリアは適切であり、ゴルーチンが実行状態に戻る際にスタックの有効性をリセットする役割を果たします。しかし、`casfrom_Gscanstatus`でのクリアは問題がありました。

`casfrom_Gscanstatus`は、ゴルーチンがGCスキャン関連の状態（例: `_Gscanwaiting`）から別の状態へ遷移する際に使用されます。この関数が呼び出される際、呼び出し元は対象のゴルーチン（`gp`）の所有権を必ずしも持っていません。そのため、`gp.gcscanvalid = false`という書き込みは競合状態を引き起こす可能性がありました。つまり、他のプロセッサが同時に`gp`の`gcscanvalid`を読み書きしている可能性があり、予期せぬ動作につながる恐れがあったのです。

さらに、コミットメッセージでは、将来的に「ダーティスタック」（変更されたスタック）を持つゴルーチンのセットを追跡する機能が導入される予定であることが示唆されています。この新機能が導入されると、`gcscanvalid`を`false`に設定する操作が冪等（べきとう）ではなくなるため、現在の競合状態の問題がより深刻になることが予想されました。この変更は、その将来的な機能への準備でもあります。

## 前提知識の解説

### Goランタイムとゴルーチン (Goroutine)

Goランタイムは、Goプログラムの実行を管理するシステムです。その中心的な概念の一つが「ゴルーチン」です。ゴルーチンは軽量な実行スレッドのようなもので、Goの並行処理の基盤となります。

### ゴルーチンの状態 (Goroutine States)

Goランタイムは、ゴルーチンのライフサイクルを管理するために様々な状態を定義しています。このコミットに関連する主な状態は以下の通りです。

*   `_Grunning`: ゴルーチンが現在実行中である状態。
*   `_Gscanwaiting`: ゴルーチンがGCスキャンを待っている状態。GCがスタックをスキャンする必要があるが、ゴルーチンは一時停止している。
*   `_Gscanrunning`: ゴルーチンがGCスキャン中である状態。この状態では、ゴルーチンは実際には実行中であり、自身のスタックをスキャンしているか、スキャンされる準備をしている。コミットメッセージにあるように、この状態はゴルーチンが実行状態に遷移していることを意味するわけではありません。

### ガベージコレクション (GC) とスタックスキャン

GoのGCは、プログラムが使用しなくなったメモリを自動的に回収します。GCサイクル中、ランタイムは実行中のゴルーチンのスタックをスキャンし、どのメモリがまだ参照されているかを判断します。このスキャンは、正確なGCのために不可欠です。

### `gcscanvalid` フラグ

`gcscanvalid`は、特定のゴルーチンのスタックがGCスキャンに対して有効であるかどうかを示すブール型フラグです。`true`であればスタックはスキャン可能であり、`false`であればスタックは無効であるか、スキャン準備ができていないことを示します。通常、ゴルーチンが実行状態にある間はスタックの内容が頻繁に変化するため、`gcscanvalid`は`false`に設定されます。GCスキャンが必要な場合は、ゴルーチンを一時停止させ、スタックを安定させてから`gcscanvalid`を`true`にしてスキャンを行います。

### `casgstatus` と `casfrom_Gscanstatus` 関数

これらの関数は、ゴルーチンの状態遷移をアトミックに（不可分に）管理するために使用されます。

*   `casgstatus(gp *g, oldval, newval uint32)`: ゴルーチン`gp`の現在の状態が`oldval`である場合にのみ、その状態を`newval`に更新します。これは通常、ゴルーチン自身が自身の状態を変更する際に使用され、排他的なアクセスが保証されます。
*   `casfrom_Gscanstatus(gp *g, oldval, newval uint32)`: `casgstatus`と同様にゴルーチンの状態をアトミックに更新しますが、この関数はGCスキャン関連の状態からの遷移に特化しています。重要なのは、この関数を呼び出す側が対象のゴルーチン`gp`の排他的な所有権を持っていない可能性がある点です。

## 技術的詳細

このコミットの核心は、`casfrom_Gscanstatus`関数における`gcscanvalid`フラグの不適切なクリア処理の削除です。

**問題点**:
`casfrom_Gscanstatus`関数内で、新しい状態が`_Grunning`になる場合に`gp.gcscanvalid = false`と設定していました。しかし、この関数は呼び出し元がゴルーチン`gp`の所有権を保証しない状況で使われることがあります。つまり、複数のプロセッサやゴルーチンが同時に`gp`のデータ構造にアクセスする可能性があり、`gcscanvalid`への書き込みが競合状態を引き起こす可能性がありました。これは、データの一貫性を損ない、GCの誤動作やクラッシュにつながる恐れがあります。

特に、`_Gscanrunning`状態は、ゴルーチンがGCスキャン中であることを示しますが、これはゴルーチンが実行状態に「遷移」しているわけではありません。ゴルーチンは既に実行中であり、自身のスタックをスキャンしている最中、またはスキャンされる準備をしている状態です。したがって、この時点で`gcscanvalid`を`false`にクリアすることは、そのゴルーチンのスタックが「有効でも無効でもない」という中間的な状態を無視することになり、論理的に不正確でした。

**解決策**:
コミットは、`src/runtime/proc.go`内の`casfrom_Gscanstatus`関数から、`newval == _Grunning`の場合に`gp.gcscanvalid = false`とする行を削除します。

この変更により、以下のようになります。

1.  **競合状態の解消**: `casfrom_Gscanstatus`が`gcscanvalid`に書き込むことがなくなるため、この関数が引き起こす可能性のあった競合状態が解消されます。
2.  **処理の正確性**: `_Gscanrunning`状態のゴルーチンは、自身のスタックをスキャンするためにプリエンプト（一時停止）されます。スキャンが完了すると、`gcscanvalid`は`true`に設定されます。その後、ゴルーチンは`casgstatus`を通じて`_Grunning`状態に戻ります。この`casgstatus`の呼び出し時に、`gcscanvalid`が`false`にクリアされるため、最終的な状態は正しくなります。つまり、`casfrom_Gscanstatus`でのクリアは冗長であり、`casgstatus`でのクリアで十分かつ安全に処理されることが確認されました。
3.  **将来の機能への対応**: コミットメッセージで言及されている「ダーティスタック」の追跡機能が導入されると、`gcscanvalid`を`false`に設定する操作は冪等ではなくなります。この変更は、その将来的な変更に備え、`gcscanvalid`の不必要な書き込みを排除することで、システム全体の堅牢性を高めます。

`src/runtime/stack.go`の変更は、`newstack`関数内のコメント追加であり、`casgstatus(gp, _Gwaiting, _Grunning)`が`gcscanvalid`をクリアする役割を果たすことを明示しています。これは、`proc.go`の変更によって`casfrom_Gscanstatus`が`gcscanvalid`をクリアしなくなったことと整合性を保つための補足説明です。

## コアとなるコードの解説

### `src/runtime/proc.go` の変更

`casfrom_Gscanstatus`関数は、ゴルーチンがGCスキャン関連の状態から別の状態へ遷移する際に使用されます。

```go
 func casfrom_Gscanstatus(gp *g, oldval, newval uint32) {
 		dumpgstatus(gp)
 		throw("casfrom_Gscanstatus: gp->status is not in scan state")
 	}
-	if newval == _Grunning {
-		gp.gcscanvalid = false
-	}
 }
```

この変更では、`newval == _Grunning`の場合に`gp.gcscanvalid = false`と設定していた3行が削除されています。
この削除の理由は、前述の「変更の背景」と「技術的詳細」で説明した通り、`casfrom_Gscanstatus`の呼び出し元が`gp`の所有権を持たないため、この書き込みが競合状態を引き起こす可能性があったこと、そしてこのクリア処理が冗長であったためです。ゴルーチンが最終的に`_Grunning`状態に戻る際には、`casgstatus`関数内で`gcscanvalid`が適切にクリアされるため、この場所でのクリアは不要かつ危険でした。

### `src/runtime/stack.go` の変更

`newstack`関数は、新しいスタックが必要になった際にゴルーチンをセットアップする処理の一部です。

```go
 			gp.preemptscan = false
 			gp.preempt = false
 			casfrom_Gscanstatus(gp, _Gscanwaiting, _Gwaiting)
+			// This clears gcscanvalid.
 			casgstatus(gp, _Gwaiting, _Grunning)
 			gp.stackguard0 = gp.stack.lo + _StackGuard
 			gogo(&gp.sched) // never return
```

この変更は、`casgstatus(gp, _Gwaiting, _Grunning)`の呼び出しの直前に`// This clears gcscanvalid.`というコメントを追加しています。
これはコードの動作を変更するものではなく、`casgstatus`がゴルーチンを`_Grunning`状態に遷移させる際に`gcscanvalid`フラグを`false`にクリアする役割を担っていることを明示するためのものです。`proc.go`の変更により`casfrom_Gscanstatus`が`gcscanvalid`をクリアしなくなったため、このコメントは、`gcscanvalid`のクリアがどこで行われるのかを明確にし、コードの可読性と理解を助けます。

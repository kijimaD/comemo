# [インデックス 26663] ファイルの概要

このコミットは、Goコンパイラの`cmd/compile`パッケージにおける字句解析器（lexer）と構文解析器（parser）間のトークンデータ受け渡しメカニズムを最適化するものです。具体的には、不要なデータコピーを排除し、コードの構造を改善することで、コンパイラの効率性と保守性を向上させています。

## コミット

```
cmd/compile: remove gratuituous copying of lexer token data

Rename yySymType to lexer; should eventually capture all lexer state.
Embed lexer in parser and access lexer token data directly.
```

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、字句解析（lexing）と構文解析（parsing）という主要なフェーズを経ます。字句解析器はソースコードを読み込み、意味のある最小単位である「トークン」に分割します。構文解析器はこれらのトークンを受け取り、言語の文法規則に従って構文木を構築します。

このコミット以前は、字句解析器が生成したトークンデータを構文解析器に渡す際に、不必要なデータコピーが発生していました。具体的には、字句解析器がトークンを生成し、その情報を一時的な構造体（`yySymType`）に格納し、その構造体へのポインタを介して構文解析器に渡していました。構文解析器は、この一時的な構造体から必要なトークン情報を自身のフィールドにコピーしていました。

このようなデータコピーは、特にコンパイル対象のコードベースが大規模になるにつれて、パフォーマンスのオーバーヘッドとなり得ます。また、字句解析器と構文解析器の間で同じようなトークン情報を保持するフィールドが重複していることは、コードの冗長性を生み、保守性を低下させる要因にもなります。

このコミットの目的は、この「gratuituous copying（不必要なコピー）」を排除し、字句解析器と構文解析器間のデータフローをより直接的かつ効率的にすることにあります。これにより、コンパイラの実行速度の向上と、コードベースのクリーンアップが期待されます。

## 前提知識の解説

### 1. 字句解析器（Lexer/Scanner）とトークン（Token）

*   **字句解析器（Lexer/Scanner）**: ソースコードの文字列を読み込み、プログラミング言語の文法規則に基づいて、意味のある最小単位（トークン）のストリームに変換するコンパイラの最初のフェーズです。例えば、`var x = 10;`というコードは、`var`（キーワード）、`x`（識別子）、`=`（演算子）、`10`（リテラル）、`;`（区切り文字）といったトークンに分割されます。
*   **トークン（Token）**: 字句解析器によって識別される、プログラミング言語における意味のある最小単位です。通常、トークンは「種類」（例: 識別子、キーワード、演算子）と「値」（例: 識別子の名前、リテラルの値）を持ちます。

### 2. 構文解析器（Parser）

*   **構文解析器（Parser）**: 字句解析器から受け取ったトークンのストリームを、プログラミング言語の文法規則に従って解析し、プログラムの構造を表現する構文木（Abstract Syntax Tree: AST）を構築するコンパイラのフェーズです。構文解析器は、トークンの並びが言語の文法に合致しているかを確認し、プログラムの階層的な構造を表現します。

### 3. Go言語における構造体の埋め込み（Embedding）

Go言語では、構造体の中に別の構造体をフィールド名なしで宣言することで、「埋め込み（embedding）」を行うことができます。これにより、埋め込まれた構造体のフィールドやメソッドが、外側の構造体のフィールドやメソッドであるかのように直接アクセスできるようになります。これは、継承に似た機能を提供しますが、Goの設計思想に沿ったよりシンプルな合成のメカニズムです。

例:
```go
type Inner struct {
    Field1 int
}

type Outer struct {
    Inner // Inner構造体を埋め込み
    Field2 string
}

func main() {
    o := Outer{Inner: Inner{Field1: 10}, Field2: "hello"}
    fmt.Println(o.Field1) // OuterのインスタンスからInnerのField1に直接アクセスできる
}
```

### 4. `yySymType`という命名について

`yySymType`という名前は、Yacc（Yet Another Compiler Compiler）やBisonといったパーサジェネレータが生成するコードでよく見られる命名パターンです。これらのツールは、文法定義から構文解析器を自動生成し、トークンのセマンティックな値（意味的な値）を保持するための構造体に`yySymType`という名前を付けることが一般的です。Goコンパイラは手書きのパーサを使用していますが、この命名は過去の慣習や他のコンパイラ設計からの影響を示唆している可能性があります。

## 技術的詳細

このコミットの技術的詳細な変更点は、字句解析器と構文解析器の間の結合度を下げ、データフローを最適化することに集約されます。

1.  **`yySymType`構造体の`lexer`へのリネームと役割の明確化**:
    *   以前は`yySymType`という汎用的な名前の構造体が、字句解析器が生成するトークンの種類（`tok`）、識別子（`sym`）、リテラル値（`val`）、演算子（`op`）を保持していました。
    *   この構造体が`lexer`という名前に変更され、字句解析器の状態をカプセル化する役割がより明確になりました。コミットメッセージの`should eventually capture all lexer state`という記述から、将来的には現在の行番号やソースファイル情報など、字句解析器に関連する全ての状態をこの`lexer`構造体で管理する意図があることが伺えます。

2.  **`_yylex`関数のメソッド化**:
    *   `_yylex`関数は、以前は`*yySymType`を引数として受け取り、そのポインタを通じてトークン情報を更新していました。
    *   変更後は`func (yylval *lexer) _yylex() int32`というメソッドになり、`lexer`構造体のインスタンス自身がトークン情報を保持・更新するようになりました。これにより、外部からポインタを渡す必要がなくなり、`lexer`構造体が自身の状態をより自律的に管理できるようになります。

3.  **`yylex`関数の`next`メソッドへのリネームと役割変更**:
    *   以前の`yylex`関数は、`_yylex`を呼び出してトークンを取得し、セミコロン挿入などの後処理を行った後、最終的なトークンの種類を返していました。
    *   変更後の`next`メソッド（`func (l *lexer) next()`）は、`_yylex`を呼び出してトークンを取得した後、そのトークン情報を`l.tok`などの`lexer`構造体のフィールドに直接格納します。そして、何も値を返しません。これは、トークン情報が`lexer`構造体自身に保持されるため、呼び出し元がその構造体のフィールドを直接参照すればよい、という設計思想に基づいています。

4.  **`parser`構造体への`lexer`構造体の埋め込み**:
    *   最も重要な変更点の一つは、`parser`構造体からトークン情報を保持していた冗長なフィールド（`tok`, `op`, `val`, `sym_`）が削除され、代わりに`lexer`構造体が埋め込まれたことです。
    *   これにより、`parser`は`lexer`のフィールドに直接アクセスできるようになり、字句解析器が生成したトークンデータを`parser`が自身のフィールドにコピーする必要がなくなりました。例えば、`p.tok`と書くことで、埋め込まれた`lexer`の`tok`フィールドにアクセスできます。

5.  **`parser.next()`メソッドの削除**:
    *   `parser`構造体にあった`next()`メソッドは、以前は`yylex`を呼び出してトークンを取得し、`parser`自身のフィールドにコピーする役割を担っていました。
    *   `lexer`が`parser`に埋め込まれたことで、`parser`は直接`lexer`の`next()`メソッド（旧`yylex`）を呼び出すだけで、`lexer`の状態が更新され、トークン情報が`parser`から直接アクセス可能になります。これにより、`parser`側の`next()`メソッドは不要となりました。

これらの変更により、字句解析器と構文解析器の間のデータ受け渡しが、ポインタ渡しとコピーから、構造体の埋め込みによる直接アクセスへと変わり、効率が向上しています。

## コアとなるコードの解説

### `lex.go` の変更点

1.  **`yySymType` から `lexer` へのリネーム**:
    *   `type yySymType struct { ... }` が `type lexer struct { ... }` に変更されました。これにより、この構造体が字句解析器の状態をカプセル化するものであることが明確になります。
    *   `sym` フィールドが `sym_` に変更されています。これは、`parser` 構造体に `lexer` が埋め込まれた際に、`parser` 自身の `sym_` フィールドと衝突しないようにするため、あるいは内部的な命名規則に合わせるための変更と考えられます。
    *   `tok`, `sym_`, `val`, `op` といったフィールドは、字句解析器が現在処理しているトークンの種類、識別子、リテラル値、演算子を直接保持するようになりました。

2.  **`_yylex` 関数のメソッド化**:
    *   `func _yylex(yylval *yySymType) int32` が `func (yylval *lexer) _yylex() int32` に変更されました。これは、`_yylex` が `lexer` 型のレシーバを持つメソッドになったことを意味します。
    *   これにより、`_yylex` は引数として`yySymType`（後の`lexer`）のポインタを受け取るのではなく、自身のレシーバである`lexer`インスタンスのフィールドを直接更新するようになりました。例えば、`yylval.sym = s` が `yylval.sym_ = s` に変更され、レシーバのフィールドに直接代入しています。

3.  **`yylex` から `next` メソッドへの変更**:
    *   `func yylex(yylval *yySymType) int32` が `func (l *lexer) next()` に変更されました。
    *   このメソッドは、内部で `l._yylex()` を呼び出して次のトークンを取得します。
    *   取得したトークン（`tok`）は、以前のように戻り値として返すのではなく、レシーバである `l` (lexerインスタンス) の `l.tok` フィールドに直接格納されます (`l.tok = tok`)。
    *   これにより、字句解析器の外部からは、`lexer` インスタンスの `tok`, `sym_`, `val`, `op` フィールドを直接参照することで、現在のトークン情報を取得できるようになります。

### `parser.go` の変更点

1.  **冗長なトークン関連フィールドの削除**:
    *   `parser` 構造体から、`tok`, `op`, `val`, `sym_` といったフィールドが削除されました。これらは以前、字句解析器から受け取ったトークン情報をコピーして保持するためのものでした。
    *   また、`yy yySymType` フィールドも削除されました。これは、`yylex` 関数に渡すための一時的な`yySymType`インスタンスでした。

2.  **`lexer` 構造体の埋め込み**:
    *   `parser` 構造体に `lexer` がフィールド名なしで埋め込まれました (`lexer`)。
    *   Goの構造体の埋め込みの特性により、`parser` インスタンスは、埋め込まれた `lexer` インスタンスの全てのフィールド（`tok`, `sym_`, `val`, `op` など）に、あたかも自身のフィールドであるかのように直接アクセスできるようになります。例えば、`p.tok` は `p.lexer.tok` と同じ意味になります。

3.  **`parser.next()` メソッドの削除**:
    *   `parser` 構造体にあった `func (p *parser) next()` メソッドが削除されました。
    *   以前のこのメソッドは、`yylex(&p.yy)` を呼び出し、`p.yy` に格納されたトークン情報を `p.tok`, `p.op`, `p.val`, `p.sym_` にコピーしていました。
    *   `lexer` が埋め込まれたことで、`parser` は直接 `p.next()` (埋め込まれた `lexer` の `next` メソッド) を呼び出すだけで、`lexer` の状態が更新され、`p.tok` などのフィールドを通じて最新のトークン情報にアクセスできるようになりました。これにより、`parser` 側の `next()` メソッドは不要となり、コードが簡素化されました。

これらの変更により、字句解析器と構文解析器の間でトークンデータをコピーするオーバーヘッドが完全に排除され、`parser` は `lexer` の状態を直接参照するようになりました。これは、コンパイラのパフォーマンス向上と、コードの構造的なクリーンアップに貢献します。

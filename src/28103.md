# [インデックス 28103] ファイルの概要

このコミットは、Goランタイムのメモリ管理、特にガベージコレクション(GC)におけるアロケーションビットとマークビットの構造を再構築するものです。主な目的は、メモリ効率の向上とGC性能の最適化であり、`mspan`構造体内のビットマップ管理方法を根本的に変更し、アリーナベースのアロケーションスキームを導入しています。

## コミット

Two changes are included here that are dependent on the other.

object's index. The index is returned from heapBitsForObject

and gcmarkBits.

structures. Instead we use an arena based allocation scheme
that allows for a more compact bit map as well as recycling
and bulk clearing of the mark bits.

## 変更の背景

Goのガベージコレクタは、プログラムの実行中に不要になったメモリを自動的に解放する役割を担っています。このプロセスにおいて、ヒープ上の各オブジェクトの状態（割り当て済みか、GCによってマーク済みかなど）を追跡するためにビットマップが使用されます。具体的には、`allocBits`はオブジェクトが割り当てられているかどうかを示し、`gcmarkBits`はGCのマークフェーズ中にオブジェクトが到達可能であるとマークされたかどうかを示します。

以前の実装では、これらのビットマップは`mspan`構造体内に直接インラインで割り当てられていました。`mspan`はGoランタイムが管理するメモリの連続したブロックを表す構造体で、特定のサイズのオブジェクトを格納します。しかし、このインライン割り当てにはいくつかの問題がありました。

1.  **メモリの非効率性**: `mspan`構造体は、そのスパンが保持できる最大オブジェクト数に基づいて固定サイズのビットマップを割り当てていました。これは、スパンが実際にその最大数よりも少ないオブジェクトしか持たない場合でも、余分なメモリが予約されることを意味し、メモリの断片化や非効率な利用につながっていました。
2.  **GCサイクルのオーバーヘッド**: GCサイクルごとに`gcmarkBits`をクリアする必要がありましたが、インライン割り当てでは、各`mspan`に対して個別にクリア操作を行う必要がありました。これは、特に多数の`mspan`が存在する場合に、GCのパフォーマンスに影響を与えていました。
3.  **ポインタの複雑性**: `allocBits`と`gcmarkBits`はGCサイクルごとに役割を交換するため、ポインタの交換とクリア操作が複雑になる傾向がありました。

このコミットは、これらの問題を解決し、Goランタイムのメモリ管理とGCの効率を向上させることを目的としています。特に、アリーナベースのアロケーションスキームを導入することで、ビットマップのメモリ使用量を削減し、GCのオーバーヘッドを低減することを目指しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する基本的な概念を理解しておく必要があります。

### Goランタイムのメモリ管理

Goランタイムは、独自のメモリマネージャを持っており、OSから大きなメモリブロック（アリーナ）を要求し、それを`mheap`、`mspan`、`mcache`といった構造体を使って管理します。

*   **`mheap`**: Goランタイム全体のヒープを管理するグローバルな構造体です。`mspan`のリストを保持し、メモリの割り当てと解放を調整します。
*   **`mspan`**: ヒープメモリの連続したブロック（ページ）を表します。各`mspan`は、特定のサイズのオブジェクト（例えば、8バイトオブジェクト専用のスパン、16バイトオブジェクト専用のスパンなど）を格納するように構成されます。`mspan`は、そのスパン内のオブジェクトの状態を追跡するためのビットマップ（`allocBits`と`gcmarkBits`）を保持します。
*   **`mcache`**: 各P（プロセッサ、OSスレッドに相当）にローカルなキャッシュです。小さなオブジェクトの割り当てを高速化するために、`mspan`のリストを保持します。

### ガベージコレクション (GC)

GoのGCは、並行マーク＆スイープ（Concurrent Mark and Sweep）アルゴリズムをベースにしています。

1.  **マークフェーズ (Mark Phase)**: GCは、ルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトを「生きている」とマークします。このフェーズでは、`gcmarkBits`が使用され、オブジェクトがマークされると対応するビットがセットされます。
2.  **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不可能なオブジェクト）は「死んでいる」と判断され、メモリが解放されます。このフェーズでは、`allocBits`が更新され、解放されたメモリが再利用可能になります。

### `allocBits`と`gcmarkBits`

*   **`allocBits`**: `mspan`内の各オブジェクトが現在割り当てられているかどうかを示すビットマップです。1ビットが1つのオブジェクトに対応します。
*   **`gcmarkBits`**: GCのマークフェーズ中に、`mspan`内の各オブジェクトが到達可能であるとマークされたかどうかを示すビットマップです。これも1ビットが1つのオブジェクトに対応します。

GCサイクルが終了すると、`gcmarkBits`は次のGCサイクルの`allocBits`の役割を担い、新しい`gcmarkBits`が準備されます。これは、前回のGCでマークされたオブジェクトが、次のGCサイクル開始時には「割り当て済み」と見なされるためです。

### ポインタ演算とビット演算

Goランタイムの低レベルなコードでは、メモリ効率とパフォーマンスのためにポインタ演算やビット演算が頻繁に使用されます。
*   **ポインタ演算**: `uintptr`型を使用してメモリアドレスを直接操作し、特定のオフセットにあるデータにアクセスします。
*   **ビット演算**: ビットマップ内の特定のビットをセット、クリア、またはチェックするために使用されます。例えば、`1 << whichBit`は、`whichBit`の位置に1が立つビットマスクを作成します。`objIndex % 8`は、バイト内のビット位置を特定するために使用されます。

### `heapBitsForObject`関数

この関数は、特定のメモリアドレス`p`が指すオブジェクトのベースアドレス、そのオブジェクトに対応する`heapBits`（オブジェクトの型情報やポインタの有無を示すビットマップ）、およびそのオブジェクトが属する`mspan`を返します。GCがヒープ上のオブジェクトを走査する際に頻繁に呼び出されます。

## 技術的詳細

このコミットは、主に以下の3つの技術的な変更を含んでいます。

1.  **`allocBits`と`gcmarkBits`のポインタ化とポインタ演算の導入**:
    *   以前は`mspan`構造体内に固定サイズの`[maxObjsPerSpan / 8]uint8`配列として直接埋め込まれていた`allocBits`と`gcmarkBits`が、`*uint8`型のポインタに変更されました。
    *   これにより、ビットマップの実データは`mspan`の外部に配置されることになります。
    *   特定のオブジェクトに対応するビットを見つけるために、ポインタ演算（`addb`関数など）を使用して、`*uint8`ポインタから目的のバイトへのオフセットを計算し、そのバイト内の下位3ビット（`objIndex % 8`）を使用して正確なビット位置を特定します。
    *   この変更により、`mspan`構造体自体のサイズが削減され、メモリフットプリントが小さくなる可能性があります。

2.  **`heapBitsForObject`からのオブジェクトインデックスの返却と冗長な計算の回避**:
    *   `heapBitsForObject`関数は、これまでの戻り値（`base`, `hbits`, `span`）に加えて、新たに`objIndex`（スパン内でのオブジェクトのインデックス）を返すようになりました。
    *   これにより、`heapBitsForObject`がオブジェクトのインデックスを計算した後、そのインデックスを`allocBits`や`gcmarkBits`を操作する他の関数に渡すことができるようになります。
    *   以前は、`heapBitsForObject`がオブジェクトのベースアドレスを返した後、`markBitsForAddr`などの関数が再度オブジェクトのインデックスを計算する必要がありました。この変更により、冗長な計算が回避され、GCのパフォーマンスが向上します。

3.  **アリーナベースのビットマップアロケーションスキームの導入**:
    *   最も重要な変更点の一つは、`gcmarkBits`（および`allocBits`）が`mspan`構造体内に直接割り当てられるのではなく、専用のアリーナ（`gcBitsArenas`）から割り当てられるようになったことです。
    *   `gcBitsArenas`は、`free`、`next`、`current`、`previous`という4つの`gcBits`アリーナのリストを管理します。
        *   `next`: 次のGCサイクルで使用されるマークビットを保持します。
        *   `current`: 現在のGCサイクルで使用されているマークビットを保持します。
        *   `previous`: 前のGCサイクルで使用されていたマークビットを保持します。
        *   `free`: 再利用可能な空きアリーナのリストです。
    *   `newMarkBits`関数は、`gcBitsArenas.next`アリーナからマークビット用のメモリを割り当てます。必要に応じて新しいアリーナを`sysAlloc`で確保します。
    *   `nextMarkBitArenaEpoch`関数は、GCサイクルが進行するにつれてアリーナの役割を切り替えます。`previous`アリーナは`free`リストに移動し、`current`が`previous`に、`next`が`current`になります。これにより、マークビットのバルククリアリング（一括クリア）や再利用が効率的に行えるようになります。
    *   このアリーナベースのアロケーションにより、ビットマップのメモリ使用量がよりコンパクトになり、GCサイクルごとのビットマップのクリア操作が効率化されます。特に、`memclr`（メモリをゼロクリアする）をアリーナ全体に対して一度に行うことで、個々の`mspan`のビットマップをクリアするよりも高速になります。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   `src/runtime/cgocall.go`: `heapBitsForObject`の戻り値の変更に対応。
*   `src/runtime/malloc.go`: `mcache`の`nextFreeFast`関数で`allocCache`のインデックス取得方法が変更。
*   `src/runtime/mbitmap.go`: `allocBitsForIndex`, `refillAllocCache`, `isFree`, `markBitsForAddr`, `markBitsForIndex`, `greyobject`などの関数が、新しいビットマップ構造と`objIndex`の利用に対応。`mspan.objIndex`が追加され、オブジェクトのインデックス計算をカプセル化。
*   `src/runtime/mgcmark.go`: `scanblock`, `scanobject`, `shade`, `greyobject`などのGCマーク関連関数が、`heapBitsForObject`の新しい戻り値と`objIndex`の利用に対応。`greyobject`の引数に`objIndex`が追加。
*   `src/runtime/mgcsweep.go`: `finishsweep_m`, `sweep`関数が、新しいビットマップアロケーションスキームと`newMarkBits`の利用に対応。`allocBits`と`gcmarkBits`の役割交換ロジックが変更。
*   `src/runtime/mheap.go`:
    *   `mspan`構造体から`markbits1`と`markbits2`配列が削除され、`allocBits`と`gcmarkBits`が`*uint8`ポインタに変更。
    *   `mspan.init`関数からビットマップのインライン初期化とクリアロジックが削除。
    *   `gcBitsChunkBytes`, `gcBitsHeader`, `gcBits`構造体が追加され、アリーナベースのビットマップ管理の基盤を定義。
    *   `gcBitsArenas`グローバル変数と、`newMarkBits`, `newAllocBits`, `nextMarkBitArenaEpoch`, `newArena`といったアリーナ管理関数が追加。

## コアとなるコードの解説

### `src/runtime/mheap.go`における`mspan`構造体の変更とアリーナ管理

```go
type mspan struct {
	// ...
	allocBits  *uint8
	gcmarkBits *uint8
	// ...
}

// gcBitsChunkBytes, gcBitsHeader, gcBits 構造体の定義
// gcBitsArenas グローバル変数の定義

// newMarkBits returns a pointer to 8 byte aligned bytes
// to be used for a span's mark bits.
func newMarkBits(nelems uintptr) *uint8 {
	lock(&gcBitsArenas.lock)
	blocksNeeded := uintptr((nelems + 63) / 64) // 64オブジェクトごとに1ブロック（8バイト）
	bytesNeeded := blocksNeeded * 8
	if gcBitsArenas.next == nil ||
		gcBitsArenas.next.free+bytesNeeded > uintptr(len(gcBits{}.bits)) {
		// Allocate a new arena.
		fresh := newArena()
		fresh.next = gcBitsArenas.next
		gcBitsArenas.next = fresh
	}
	// ... アリーナからのメモリ割り当てロジック ...
	result := &gcBitsArenas.next.bits[gcBitsArenas.next.free]
	gcBitsArenas.next.free += bytesNeeded
	unlock(&gcBitsArenas.lock)
	return result
}

// nextMarkBitArenaEpoch establishes a new epoch for the arenas
// holding the mark bits.
func nextMarkBitArenaEpoch() {
	lock(&gcBitsArenas.lock)
	// ... アリーナの役割を切り替えるロジック ...
	gcBitsArenas.previous = gcBitsArenas.current
	gcBitsArenas.current = gcBitsArenas.next
	gcBitsArenas.next = nil // newMarkBits calls newArena when needed
	unlock(&gcBitsArenas.lock)
}
```
`mspan`構造体から`markbits1`と`markbits2`という固定サイズの配列が削除され、`allocBits`と`gcmarkBits`が`*uint8`ポインタになりました。これにより、`mspan`のサイズが小さくなり、メモリ効率が向上します。
`newMarkBits`関数は、`mspan`が必要とするマークビット用のメモリを、`gcBitsArenas.next`というアリーナから動的に割り当てます。このアリーナは、必要に応じて`newArena`によって新しいチャンクが確保されます。
`nextMarkBitArenaEpoch`関数は、GCのスイープフェーズの終わりに呼び出され、`gcBitsArenas`内のアリーナの役割を切り替えます。これにより、前のGCサイクルで使用されたマークビットのアリーナが解放され、次のGCサイクルで使用されるアリーナが準備されます。この一括処理により、個々の`mspan`のビットマップをクリアする手間が省け、GCの効率が向上します。

### `src/runtime/mbitmap.go`におけるビットマップ操作の変更

```go
func (s *mspan) allocBitsForIndex(allocBitIndex uintptr) markBits {
	whichByte := allocBitIndex / 8
	// ...
	bytePtr := addb(s.allocBits, whichByte) // ポインタ演算でバイト位置を特定
	return markBits{bytePtr, uint8(1 << whichBit), allocBitIndex}
}

func (s *mspan) objIndex(p uintptr) uintptr {
	byteOffset := p - s.base()
	// ... オブジェクトのインデックスを計算するロジック ...
	return uintptr(((uint64(byteOffset) >> s.divShift) * uint64(s.divMul)) >> s.divShift2)
}

func markBitsForAddr(p uintptr) markBits {
	s := spanOf(p)
	objIndex := s.objIndex(p) // objIndexを再計算せずに利用
	return s.markBitsForIndex(objIndex)
}

func (s *mspan) markBitsForIndex(objIndex uintptr) markBits {
	whichByte := objIndex / 8
	bitMask := uint8(1 << (objIndex % 8)) // low 3 bits hold the bit index
	bytePtr := addb(s.gcmarkBits, whichByte)
	return markBits{bytePtr, bitMask, objIndex}
}
```
`allocBitsForIndex`や`markBitsForIndex`といった関数は、`mspan.allocBits`や`mspan.gcmarkBits`が`*uint8`ポインタになったことに対応し、`addb`関数（ポインタにオフセットを加算する）を使用して目的のバイトにアクセスするように変更されました。
`mspan.objIndex`関数が新設され、特定のポインタ`p`が`mspan`内のどのオブジェクトに属するかを示すインデックスを計算します。このインデックスは、`heapBitsForObject`から返されるようになり、`markBitsForAddr`などの関数で再利用されることで、冗長な計算が回避されます。

### `src/runtime/mgcmark.go`におけるGCマークロジックの変更

```go
func greyobject(obj, base, off uintptr, hbits heapBits, span *mspan, gcw *gcWork, objIndex uintptr) {
	// ...
	mbits := span.markBitsForIndex(objIndex) // objIndexを直接利用
	// ...
	// mbits.setMarked() // Avoid extra call overhead with manual inlining.
	atomic.Or8(mbits.bytep, mbits.mask) // setMarkedのインライン化
	// ...
}
```
`greyobject`関数は、GCマークフェーズでオブジェクトをマークする主要な関数です。この関数は、`heapBitsForObject`から返された`objIndex`を直接受け取るようになり、`span.markBitsForIndex(objIndex)`を呼び出すことで、効率的にマークビットを取得します。
また、`mbits.setMarked()`の呼び出しが`atomic.Or8(mbits.bytep, mbits.mask)`に置き換えられ、アトミックなビットセット操作がインライン化されています。これは、関数呼び出しのオーバーヘッドを削減し、GCのホットスポットにおけるパフォーマンスを向上させるための最適化です。

## 変更の背景

Goのガベージコレクタは、プログラムの実行中に不要になったメモリを自動的に解放する役割を担っています。このプロセスにおいて、ヒープ上の各オブジェクトの状態（割り当て済みか、GCによってマーク済みかなど）を追跡するためにビットマップが使用されます。具体的には、`allocBits`はオブジェクトが割り当てられているかどうかを示し、`gcmarkBits`はGCのマークフェーズ中にオブジェクトが到達可能であるとマークされたかどうかを示します。

以前の実装では、これらのビットマップは`mspan`構造体内に直接インラインで割り当てられていました。`mspan`はGoランタイムが管理するメモリの連続したブロックを表す構造体で、特定のサイズのオブジェクトを格納します。しかし、このインライン割り当てにはいくつかの問題がありました。

1.  **メモリの非効率性**: `mspan`構造体は、そのスパンが保持できる最大オブジェクト数に基づいて固定サイズのビットマップを割り当てていました。これは、スパンが実際にその最大数よりも少ないオブジェクトしか持たない場合でも、余分なメモリが予約されることを意味し、メモリの断片化や非効率な利用につながっていました。
2.  **GCサイクルのオーバーヘッド**: GCサイクルごとに`gcmarkBits`をクリアする必要がありましたが、インライン割り当てでは、各`mspan`に対して個別にクリア操作を行う必要がありました。これは、特に多数の`mspan`が存在する場合に、GCのパフォーマンスに影響を与えていました。
3.  **ポインタの複雑性**: `allocBits`と`gcmarkBits`はGCサイクルごとに役割を交換するため、ポインタの交換とクリア操作が複雑になる傾向がありました。

このコミットは、これらの問題を解決し、Goランタイムのメモリ管理とGCの効率を向上させることを目的としています。特に、アリーナベースのアロケーションスキームを導入することで、ビットマップのメモリ使用量を削減し、GCのオーバーヘッドを低減することを目指しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する基本的な概念を理解しておく必要があります。

### Goランタイムのメモリ管理

Goランタイムは、独自のメモリマネージャを持っており、OSから大きなメモリブロック（アリーナ）を要求し、それを`mheap`、`mspan`、`mcache`といった構造体を使って管理します。

*   **`mheap`**: Goランタイム全体のヒープを管理するグローバルな構造体です。`mspan`のリストを保持し、メモリの割り当てと解放を調整します。
*   **`mspan`**: ヒープメモリの連続したブロック（ページ）を表します。各`mspan`は、特定のサイズのオブジェクト（例えば、8バイトオブジェクト専用のスパン、16バイトオブジェクト専用のスパンなど）を格納するように構成されます。`mspan`は、そのスパン内のオブジェクトの状態を追跡するためのビットマップ（`allocBits`と`gcmarkBits`）を保持します。
*   **`mcache`**: 各P（プロセッサ、OSスレッドに相当）にローカルなキャッシュです。小さなオブジェクトの割り当てを高速化するために、`mspan`のリストを保持します。

### ガベージコレクション (GC)

GoのGCは、並行マーク＆スイープ（Concurrent Mark and Sweep）アルゴリズムをベースにしています。

1.  **マークフェーズ (Mark Phase)**: GCは、ルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトを「生きている」とマークします。このフェーズでは、`gcmarkBits`が使用され、オブジェクトがマークされると対応するビットがセットされます。
2.  **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不可能なオブジェクト）は「死んでいる」と判断され、メモリが解放されます。このフェーズでは、`allocBits`が更新され、解放されたメモリが再利用可能になります。

### `allocBits`と`gcmarkBits`

*   **`allocBits`**: `mspan`内の各オブジェクトが現在割り当てられているかどうかを示すビットマップです。1ビットが1つのオブジェクトに対応します。
*   **`gcmarkBits`**: GCのマークフェーズ中に、`mspan`内の各オブジェクトが到達可能であるとマークされたかどうかを示すビットマップです。これも1ビットが1つのオブジェクトに対応します。

GCサイクルが終了すると、`gcmarkBits`は次のGCサイクルの`allocBits`の役割を担い、新しい`gcmarkBits`が準備されます。これは、前回のGCでマークされたオブジェクトが、次のGCサイクル開始時には「割り当て済み」と見なされるためです。

### ポインタ演算とビット演算

Goランタイムの低レベルなコードでは、メモリ効率とパフォーマンスのためにポインタ演算やビット演算が頻繁に使用されます。
*   **ポインタ演算**: `uintptr`型を使用してメモリアドレスを直接操作し、特定のオフセットにあるデータにアクセスします。
*   **ビット演算**: ビットマップ内の特定のビットをセット、クリア、またはチェックするために使用されます。例えば、`1 << whichBit`は、`whichBit`の位置に1が立つビットマスクを作成します。`objIndex % 8`は、バイト内のビット位置を特定するために使用されます。

### `heapBitsForObject`関数

この関数は、特定のメモリアドレス`p`が指すオブジェクトのベースアドレス、そのオブジェクトに対応する`heapBits`（オブジェクトの型情報やポインタの有無を示すビットマップ）、およびそのオブジェクトが属する`mspan`を返します。GCがヒープ上のオブジェクトを走査する際に頻繁に呼び出されます。

## 技術的詳細

このコミットは、主に以下の3つの技術的な変更を含んでいます。

1.  **`allocBits`と`gcmarkBits`のポインタ化とポインタ演算の導入**:
    *   以前は`mspan`構造体内に固定サイズの`[maxObjsPerSpan / 8]uint8`配列として直接埋め込まれていた`allocBits`と`gcmarkBits`が、`*uint8`型のポインタに変更されました。
    *   これにより、ビットマップの実データは`mspan`の外部に配置されることになります。
    *   特定のオブジェクトに対応するビットを見つけるために、ポインタ演算（`addb`関数など）を使用して、`*uint8`ポインタから目的のバイトへのオフセットを計算し、そのバイト内の下位3ビット（`objIndex % 8`）を使用して正確なビット位置を特定します。
    *   この変更により、`mspan`構造体自体のサイズが削減され、メモリフットプリントが小さくなる可能性があります。

2.  **`heapBitsForObject`からのオブジェクトインデックスの返却と冗長な計算の回避**:
    *   `heapBitsForObject`関数は、これまでの戻り値（`base`, `hbits`, `span`）に加えて、新たに`objIndex`（スパン内でのオブジェクトのインデックス）を返すようになりました。
    *   これにより、`heapBitsForObject`がオブジェクトのインデックスを計算した後、そのインデックスを`allocBits`や`gcmarkBits`を操作する他の関数に渡すことができるようになります。
    *   以前は、`heapBitsForObject`がオブジェクトのベースアドレスを返した後、`markBitsForAddr`などの関数が再度オブジェクトのインデックスを計算する必要がありました。この変更により、冗長な計算が回避され、GCのパフォーマンスが向上します。

3.  **アリーナベースのビットマップアロケーションスキームの導入**:
    *   最も重要な変更点の一つは、`gcmarkBits`（および`allocBits`）が`mspan`構造体内に直接割り当てられるのではなく、専用のアリーナ（`gcBitsArenas`）から割り当てられるようになったことです。
    *   `gcBitsArenas`は、`free`、`next`、`current`、`previous`という4つの`gcBits`アリーナのリストを管理します。
        *   `next`: 次のGCサイクルで使用されるマークビットを保持します。
        *   `current`: 現在のGCサイクルで使用されているマークビットを保持します。
        *   `previous`: 前のGCサイクルで使用されていたマークビットを保持します。
        *   `free`: 再利用可能な空きアリーナのリストです。
    *   `newMarkBits`関数は、`gcBitsArenas.next`アリーナからマークビット用のメモリを割り当てます。必要に応じて新しいアリーナを`sysAlloc`で確保します。
    *   `nextMarkBitArenaEpoch`関数は、GCサイクルが進行するにつれてアリーナの役割を切り替えます。`previous`アリーナは`free`リストに移動し、`current`が`previous`に、`next`が`current`になります。これにより、マークビットのバルククリアリング（一括クリア）や再利用が効率的に行えるようになります。
    *   このアリーナベースのアロケーションにより、ビットマップのメモリ使用量がよりコンパクトになり、GCサイクルごとのビットマップのクリア操作が効率化されます。特に、`memclr`（メモリをゼロクリアする）をアリーナ全体に対して一度に行うことで、個々の`mspan`のビットマップをクリアする手間が省け、GCの効率が向上します。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   `src/runtime/cgocall.go`: `heapBitsForObject`の戻り値の変更に対応。
*   `src/runtime/malloc.go`: `mcache`の`nextFreeFast`関数で`allocCache`のインデックス取得方法が変更。
*   `src/runtime/mbitmap.go`: `allocBitsForIndex`, `refillAllocCache`, `isFree`, `markBitsForAddr`, `markBitsForIndex`, `greyobject`などの関数が、新しいビットマップ構造と`objIndex`の利用に対応。`mspan.objIndex`が追加され、オブジェクトのインデックス計算をカプセル化。
*   `src/runtime/mgcmark.go`: `scanblock`, `scanobject`, `shade`, `greyobject`などのGCマーク関連関数が、`heapBitsForObject`の新しい戻り値と`objIndex`の利用に対応。`greyobject`の引数に`objIndex`が追加。
*   `src/runtime/mgcsweep.go`: `finishsweep_m`, `sweep`関数が、新しいビットマップアロケーションスキームと`newMarkBits`の利用に対応。`allocBits`と`gcmarkBits`の役割交換ロジックが変更。
*   `src/runtime/mheap.go`:
    *   `mspan`構造体から`markbits1`と`markbits2`配列が削除され、`allocBits`と`gcmarkBits`が`*uint8`ポインタに変更。
    *   `mspan.init`関数からビットマップのインライン初期化とクリアロジックが削除。
    *   `gcBitsChunkBytes`, `gcBitsHeader`, `gcBits`構造体が追加され、アリーナベースのビットマップ管理の基盤を定義。
    *   `gcBitsArenas`グローバル変数と、`newMarkBits`, `newAllocBits`, `nextMarkBitArenaEpoch`, `newArena`といったアリーナ管理関数が追加。

## コアとなるコードの解説

### `src/runtime/mheap.go`における`mspan`構造体の変更とアリーナ管理

```go
type mspan struct {
	// ...
	allocBits  *uint8
	gcmarkBits *uint8
	// ...
}

// gcBitsChunkBytes, gcBitsHeader, gcBits 構造体の定義
// gcBitsArenas グローバル変数の定義

// newMarkBits returns a pointer to 8 byte aligned bytes
// to be used for a span's mark bits.
func newMarkBits(nelems uintptr) *uint8 {
	lock(&gcBitsArenas.lock)
	blocksNeeded := uintptr((nelems + 63) / 64) // 64オブジェクトごとに1ブロック（8バイト）
	bytesNeeded := blocksNeeded * 8
	if gcBitsArenas.next == nil ||
		gcBitsArenas.next.free+bytesNeeded > uintptr(len(gcBits{}.bits)) {
		// Allocate a new arena.
		fresh := newArena()
		fresh.next = gcBitsArenas.next
		gcBitsArenas.next = fresh
	}
	// ... アリーナからのメモリ割り当てロジック ...
	result := &gcBitsArenas.next.bits[gcBitsArenas.next.free]
	gcBitsArenas.next.free += bytesNeeded
	unlock(&gcBitsArenas.lock)
	return result
}

// nextMarkBitArenaEpoch establishes a new epoch for the arenas
// holding the mark bits.
func nextMarkBitArenaEpoch() {
	lock(&gcBitsArenas.lock)
	// ... アリーナの役割を切り替えるロジック ...
	gcBitsArenas.previous = gcBitsArenas.current
	gcBitsArenas.current = gcBitsArenas.next
	gcBitsArenas.next = nil // newMarkBits calls newArena when needed
	unlock(&gcBitsArenas.lock)
}
```
`mspan`構造体から`markbits1`と`markbits2`という固定サイズの配列が削除され、`allocBits`と`gcmarkBits`が`*uint8`ポインタになりました。これにより、`mspan`のサイズが小さくなり、メモリ効率が向上します。
`newMarkBits`関数は、`mspan`が必要とするマークビット用のメモリを、`gcBitsArenas.next`というアリーナから動的に割り当てます。このアリーナは、必要に応じて`newArena`によって新しいチャンクが確保されます。
`nextMarkBitArenaEpoch`関数は、GCのスイープフェーズの終わりに呼び出され、`gcBitsArenas`内のアリーナの役割を切り替えます。これにより、前のGCサイクルで使用されたマークビットのアリーナが解放され、次のGCサイクルで使用されるアリーナが準備されます。この一括処理により、個々の`mspan`のビットマップをクリアする手間が省け、GCの効率が向上します。

### `src/runtime/mbitmap.go`におけるビットマップ操作の変更

```go
func (s *mspan) allocBitsForIndex(allocBitIndex uintptr) markBits {
	whichByte := allocBitIndex / 8
	// ...
	bytePtr := addb(s.allocBits, whichByte) // ポインタ演算でバイト位置を特定
	return markBits{bytePtr, uint8(1 << whichBit), allocBitIndex}
}

func (s *mspan) objIndex(p uintptr) uintptr {
	byteOffset := p - s.base()
	// ... オブジェクトのインデックスを計算するロジック ...
	return uintptr(((uint64(byteOffset) >> s.divShift) * uint64(s.divMul)) >> s.divShift2)
}

func markBitsForAddr(p uintptr) markBits {
	s := spanOf(p)
	objIndex := s.objIndex(p) // objIndexを再計算せずに利用
	return s.markBitsForIndex(objIndex)
}

func (s *mspan) markBitsForIndex(objIndex uintptr) markBits {
	whichByte := objIndex / 8
	bitMask := uint8(1 << (objIndex % 8)) // low 3 bits hold the bit index
	bytePtr := addb(s.gcmarkBits, whichByte)
	return markBits{bytePtr, bitMask, objIndex}
}
```
`allocBitsForIndex`や`markBitsForIndex`といった関数は、`mspan.allocBits`や`mspan.gcmarkBits`が`*uint8`ポインタになったことに対応し、`addb`関数（ポインタにオフセットを加算する）を使用して目的のバイトにアクセスするように変更されました。
`mspan.objIndex`関数が新設され、特定のポインタ`p`が`mspan`内のどのオブジェクトに属するかを示すインデックスを計算します。このインデックスは、`heapBitsForObject`から返されるようになり、`markBitsForAddr`などの関数で再利用されることで、冗長な計算が回避されます。

### `src/runtime/mgcmark.go`におけるGCマークロジックの変更

```go
func greyobject(obj, base, off uintptr, hbits heapBits, span *mspan, gcw *gcWork, objIndex uintptr) {
	// ...
	mbits := span.markBitsForIndex(objIndex) // objIndexを直接利用
	// ...
	// mbits.setMarked() // Avoid extra call overhead with manual inlining.
	atomic.Or8(mbits.bytep, mbits.mask) // setMarkedのインライン化
	// ...
}
```
`greyobject`関数は、GCマークフェーズでオブジェクトをマークする主要な関数です。この関数は、`heapBitsForObject`から返された`objIndex`を直接受け取るようになり、`span.markBitsForIndex(objIndex)`を呼び出すことで、効率的にマークビットを取得します。
また、`mbits.setMarked()`の呼び出しが`atomic.Or8(mbits.bytep, mbits.mask)`に置き換えられ、アトミックなビットセット操作がインライン化されています。これは、関数呼び出しのオーバーヘッドを削減し、GCのホットスポットにおけるパフォーマンスを向上させるための最適化です。

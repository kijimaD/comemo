# [インデックス 22478] ファイルの概要

このコミットは、Goランタイムのトレース機能において発生する「無駄なウェイクアップ (futile wakeups)」をトレースデータから除去するための変更を導入します。これにより、トレースデータの可読性が向上し、ユーザーがゴルーチンの挙動を誤解する可能性が低減されます。特に、チャネル操作における無駄なウェイクアップの検出と除去に焦点を当てています。

## 元コミット内容

```
runtime: remove futile wakeups from trace

Channels and sync.Mutex'es allow another goroutine to acquire resource
ahead of an unblocked goroutine. This is good for performance, but
leads to futile wakeups (the unblocked goroutine needs to block again).
Futile wakeups caused user confusion during the very first evaluation
of tracing functionality on a real server (a goroutine as if acquires a mutex
in a loop, while there is no loop in user code).

This change detects futile wakeups on channels and emits a special event
to denote the fact. Later parser finds entire wakeup sequences
(unblock->start->block) and removes them.

sync.Mutex will be supported in a separate change.

Change-Id: Iaaaee9d5c0921afc62b449a97447445030ac19d3
Reviewed-on: https://go-review.googlesource.com/7380
Reviewed-by: Keith Randall <khr@golang.org>
```

## 変更の背景

Goランタイムのトレーシング機能は、プログラムの実行時の詳細な挙動を可視化し、パフォーマンス分析やデバッグに役立ちます。しかし、初期のトレーシング機能の評価において、「無駄なウェイクアップ (futile wakeups)」がユーザーの混乱を招くことが判明しました。

無駄なウェイクアップとは、あるゴルーチンがリソース（例: チャネル、ミューテックス）の解放によってアンブロックされたにもかかわらず、スケジューリングされる前に別のゴルーチンがそのリソースを獲得してしまい、結果として最初にアンブロックされたゴルーチンがすぐに再びブロックされる必要がある状況を指します。このような挙動は、Goランタイムのパフォーマンス最適化（例えば、アンブロックされたゴルーチンがすぐに実行されることを保証しないことで、スケジューラのオーバーヘッドを減らす）のために意図的に行われることがありますが、トレース上ではゴルーチンがリソースを繰り返し獲得しようとしているかのように見え、ユーザーコードに存在しない「ループ」として誤解されることがありました。

このコミットの目的は、このような誤解を避けるために、トレースデータから無駄なウェイクアップのシーケンスを検出し、除去することです。これにより、トレースがよりクリーンで、実際のアプリケーションロジックを正確に反映したものになります。

## 前提知識の解説

### Goランタイムトレーシング

Goランタイムトレーシングは、Goプログラムの実行中に発生する様々なイベント（ゴルーチンの生成、開始、停止、ブロック、アンブロック、GCイベント、システムコールなど）を記録する機能です。これらのイベントはトレースファイルに保存され、`go tool trace`コマンドを使って視覚化・分析することができます。これにより、プログラムの並行処理の挙動、ボトルネック、スケジューリングの問題などを詳細に把握できます。

### ゴルーチンとスケジューラ

Goのゴルーチンは軽量な実行スレッドであり、Goランタイムのスケジューラによって管理されます。スケジューラは、利用可能なOSスレッド（P: Processor）上でゴルーチン（G）を効率的に実行するように調整します。ゴルーチンは、I/O待ち、チャネル操作、ミューテックスのロックなどでブロックされると、Pから切り離され、実行可能な状態になると再びPに割り当てられて実行されます。

### チャネルと同期プリミティブ

Goのチャネルは、ゴルーチン間で値を送受信するための主要な通信メカニズムです。バッファなしチャネルは同期的な通信を提供し、バッファ付きチャネルは非同期的な通信を可能にします。`sync.Mutex`などの同期プリミティブは、共有リソースへのアクセスを保護するために使用されます。これらのプリミティブは、ゴルーチンがリソースを待機する際にブロック状態になる原因となります。

### 無駄なウェイクアップ (Futile Wakeups)

Goランタイムのスケジューラは、パフォーマンスのために、アンブロックされたゴルーチンが即座に実行されることを保証しません。例えば、チャネルにデータが書き込まれて受信側ゴルーチンがアンブロックされたとしても、そのゴルーチンがPに割り当てられて実行される前に、別のゴルーチンがそのチャネルからデータを読み取ってしまう可能性があります。この場合、最初にアンブロックされたゴルーチンは、実行を開始した直後に再びチャネルが空になっていることに気づき、再度ブロックされることになります。これが「無駄なウェイクアップ」です。トレース上では、`unblock -> start -> block`という一連のイベントとして記録されますが、これはユーザーにとってノイズとなり、実際の処理とは関係のない挙動として映ることがあります。

## 技術的詳細

このコミットは、無駄なウェイクアップをトレースから除去するために、以下の主要な変更を導入しています。

1.  **`EvFutileWakeup` イベントの導入**:
    `src/runtime/trace.go` および `src/internal/trace/parser.go` に新しいトレースイベント `EvFutileWakeup` が追加されました。このイベントは、ゴルーチンが以前のウェイクアップが無駄であったことを示すために使用されます。

2.  **チャネル操作での `traceFutileWakeup` フラグの利用**:
    `src/runtime/chan.go` および `src/runtime/select.go` のチャネル送受信操作 (`chansend`, `chanrecv`, `selectgoImpl`) において、ゴルーチンがブロックされる際に、そのウェイクアップが無駄である可能性があれば `traceFutileWakeup` フラグを立てるようになりました。具体的には、バッファ付きチャネルでスペースがない、またはデータがないためにゴルーチンがブロックされるループ内で、このフラグが設定されます。

3.  **`traceGoPark` での `EvFutileWakeup` イベントの発行**:
    `src/runtime/trace.go` の `traceGoPark` 関数（ゴルーチンがブロックされる際に呼び出される）が変更され、`traceFutileWakeup` フラグが設定されている場合に `EvFutileWakeup` イベントを発行するようになりました。これにより、ランタイムは無駄なウェイクアップの発生をトレースに記録します。

4.  **トレースパーサーでの無駄なウェイクアップの除去**:
    `src/internal/trace/parser.go` に `removeFutile` 関数が追加されました。この関数は、パースされたトレースイベントのリストを走査し、`EvFutileWakeup` イベントとそれに続く `unblock -> start -> block` のシーケンスを検出して、トレースデータから除去します。
    `removeFutile` 関数は2つのフェーズで動作します。
    *   **フェーズ1**: 各ゴルーチンについて、`EvGoUnblock`、`EvGoStart`、`EvGoPreempt`、`EvFutileWakeup` イベントを追跡し、`EvGoBlock` 系のイベントでブロックされた際に、そのウェイクアップシーケンスが無駄であったかどうかを判断します。無駄なウェイクアップと判断されたイベントにはフラグを立てます。
    *   **フェーズ2**: フラグが立てられたイベントを元のイベントリストから除外し、新しいイベントリストを構築します。

5.  **テストケースの追加**:
    `src/runtime/pprof/trace_test.go` に `TestTraceFutileWakeup` という新しいテストケースが追加されました。このテストは、チャネル上で大量の無駄なウェイクアップを意図的に発生させ、それらがトレースから正しく除去されていることを検証します。具体的には、`EvFutileWakeup` イベントがトレースに残っていないこと、および連続する `EvGoBlock/EvGoStart/EvGoBlock` イベント（無駄なウェイクアップの兆候）が存在しないことを確認します。

この変更により、トレースツールはより意味のある情報を提供し、開発者はGoプログラムの実際の並行処理の挙動をより正確に理解できるようになります。

## コアとなるコードの変更箇所

-   `src/internal/trace/parser.go`: `Parse` 関数に `removeFutile` の呼び出しが追加され、`removeFutile` 関数自体が新規追加されました。`EvFutileWakeup` イベントの定義も追加されています。
-   `src/runtime/chan.go`: `chansend` および `chanrecv` 関数内で、ゴルーチンがブロックされる際に `traceFutileWakeup` フラグを `goparkunlock` に渡すように変更されました。
-   `src/runtime/pprof/trace_test.go`: `TestTraceFutileWakeup` という新しいテスト関数が追加されました。
-   `src/runtime/select.go`: `selectgoImpl` 関数内で、`select` がすぐにブロックされる場合に `traceFutileWakeup` フラグを設定し、`gopark` に渡すように変更されました。
-   `src/runtime/trace.go`: `traceEvFutileWakeup` イベントと `traceFutileWakeup` フラグが定義され、`traceGoPark` 関数がこのフラグを処理するように変更されました。

## コアとなるコードの解説

### `src/internal/trace/parser.go`

```go
// Parse parses, post-processes and verifies the trace.
func Parse(r io.Reader) ([]*Event, error) {
	rawEvents, err := readTrace(r)
	if err != nil {
		return nil, err
	}
	events, err := parseEvents(rawEvents)
	if err != nil {
		return nil, err
	}
	// 新しく追加された部分
	events, err = removeFutile(events) // 無駄なウェイクアップを除去
	if err != nil {
		return nil, err
	}
	err = postProcessTrace(events)
	if err != nil {
		return nil, err
	}
	return events, nil
}

// removeFutile removes all constituents of futile wakeups (block, unblock, start).
// ... (コメントは省略)
func removeFutile(events []*Event) ([]*Event, error) {
	type G struct {
		futile bool
		wakeup []*Event // wakeup sequence (subject for removal)
	}
	gs := make(map[uint64]G)
	futile := make(map[*Event]bool) // 除去対象のイベントをマークするマップ

	for _, ev := range events {
		switch ev.Type {
		case EvGoUnblock: // ゴルーチンがアンブロックされた
			g := gs[ev.Args[0]]
			g.wakeup = []*Event{ev} // ウェイクアップシーケンスの開始
			gs[ev.Args[0]] = g
		case EvGoStart, EvGoPreempt, EvFutileWakeup: // ゴルーチンが開始、プリエンプト、または無駄なウェイクアップイベント
			g := gs[ev.G]
			g.wakeup = append(g.wakeup, ev) // シーケンスに追加
			if ev.Type == EvFutileWakeup {
				g.futile = true // 無駄なウェイクアップフラグを立てる
			}
			gs[ev.G] = g
		case EvGoBlock, EvGoBlockSend, EvGoBlockRecv, EvGoBlockSelect, EvGoBlockSync, EvGoBlockCond: // ゴルーチンがブロックされた
			g := gs[ev.G]
			if g.futile { // 無駄なウェイクアップフラグが立っていた場合
				futile[ev] = true // 現在のブロックイベントを無駄としてマーク
				for _, ev1 := range g.wakeup {
					futile[ev1] = true // ウェイクアップシーケンス全体を無駄としてマーク
				}
			}
			delete(gs, ev.G) // ゴルーチンの状態をリセット
		}
	}

	newEvents := events[:0] // 元のスライスを上書きして新しいイベントリストを作成
	for _, ev := range events {
		if !futile[ev] { // 無駄とマークされていないイベントのみを追加
			newEvents = append(newEvents, ev)
		}
	}
	return newEvents, nil
}
```
`Parse` 関数はトレースの読み込みとパース後に `removeFutile` を呼び出すように変更されました。`removeFutile` は、ゴルーチンの状態 (`gs` マップ) を追跡し、`EvFutileWakeup` イベントとそれに続くブロックイベントを組み合わせて、無駄なウェイクアップシーケンスを特定します。特定されたイベントは `futile` マップにマークされ、最終的に新しいイベントリストから除外されます。

### `src/runtime/trace.go`

```go
const (
	// ...
	traceEvFutileWakeup   = 36 // denotes that the previous wakeup of this goroutine was futile [timestamp]
	traceEvCount          = 37
)

const (
	// ...
	traceFutileWakeup byte = 128 // futile wakeupを示すフラグ
)

func traceGoPark(traceEv byte, skip int, gp *g) {
	if traceEv&traceFutileWakeup != 0 { // futileフラグが立っている場合
		traceEvent(traceEvFutileWakeup, -1) // EvFutileWakeupイベントを発行
	}
	traceEvent(traceEv & ^traceFutileWakeup, skip) // 元のイベントを発行（futileフラグを除去）
}
```
`trace.go` では、新しいイベントタイプ `traceEvFutileWakeup` と、`gopark` や `goparkunlock` に渡される `traceFutileWakeup` フラグが定義されています。`traceGoPark` 関数は、このフラグを受け取ると、まず `EvFutileWakeup` イベントをトレースに記録し、その後、元のブロックイベントを記録します。これにより、パーサーは無駄なウェイクアップのシーケンスを正確に識別できるようになります。

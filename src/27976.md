# [インデックス 27976] ファイルの概要

このコミットは、Go言語のトレースツール (`cmd/trace`) の `pprof.go` ファイルに対する変更です。`pprof.go` は、`go tool trace` コマンドが生成するプロファイル（特にSVG形式のプロファイル）に関連する処理を担っています。具体的には、トレースデータからプロファイリング情報を抽出し、それを `go tool pprof` が解釈できる形式に変換して、視覚化のためのSVG画像を生成する役割を持っています。

## 元コミット内容

`cmd/trace`: 新しい pprof プロファイルを生成する。
シンボル情報が埋め込まれた新しいprotobuf形式のpprofプロファイルを生成する。
これにより、プログラムバイナリが不要になる。

## 変更の背景

Go言語のプロファイリングツールである `pprof` は、プログラムの実行中に収集されたプロファイルデータ（例えばCPU使用率やメモリ割り当てなど）を解析し、その結果をグラフやテキスト形式で表示するのに役立ちます。従来、`go tool pprof` を使ってプロファイルデータを解析する際には、プロファイルデータだけでなく、そのプロファイルが生成された元の実行可能バイナリ（プログラムバイナリ）が必要でした。これは、プロファイルデータに含まれるメモリアドレス（プログラムカウンタ、PC）を、人間が読める関数名、ファイル名、行番号といったシンボル情報に変換（シンボル化）するために、バイナリ内のシンボルテーブルが必要だったためです。

この要件は、特に以下のようなシナリオで不便をもたらしていました。
1.  **異なる環境での解析**: プロファイルが生成されたマシンと異なるマシンで解析を行う場合、元のバイナリを解析マシンにコピーする必要がありました。
2.  **バイナリの紛失/変更**: プロファイル生成後にバイナリが変更されたり、削除されたりすると、正確なシンボル化が困難になるか不可能になることがありました。
3.  **CI/CDパイプライン**: 自動化されたテストやデプロイのパイプラインでプロファイルを収集・解析する際に、バイナリの管理が複雑になることがありました。

このコミットの目的は、`go tool trace` が生成する `pprof` プロファイルに、シンボル情報を直接埋め込むことで、これらの問題を解決することです。これにより、プロファイルデータ自体がシンボル情報を持つため、解析時に元のプログラムバイナリが不要となり、プロファイリングワークフローが大幅に簡素化されます。

## 前提知識の解説

### 1. Goのプロファイリング (`pprof`)

Goには、プログラムのパフォーマンス特性を分析するための組み込みプロファイリングツール `pprof` があります。`pprof` は、CPU、メモリ、ゴルーチン、ブロック、ミューテックスなどのプロファイルデータを収集し、それらを視覚化するための機能を提供します。
*   **プロファイルデータ**: 実行中のプログラムから特定の時点でのスタックトレースやリソース使用状況をサンプリングして収集されたデータ。
*   **シンボル化 (Symbolization)**: プロファイルデータには、関数が実行されていたメモリアドレス（プログラムカウンタ、PC）が含まれています。シンボル化とは、これらのアドレスを、対応する関数名、ファイル名、行番号に変換するプロセスです。これにより、プロファイル結果が人間にとって理解しやすいものになります。
*   **`go tool pprof`**: プロファイルデータを解析し、グラフ（SVG、PDFなど）やテキストレポートを生成するためのコマンドラインツール。

### 2. Goのトレース (`go tool trace`)

`go tool trace` は、Goプログラムの実行トレースを収集・視覚化するためのツールです。`runtime/trace` パッケージを使用して生成されたトレースファイル (`trace.out`) を解析し、WebベースのUIでゴルーチンのライフサイクル、スケジューリングイベント、システムコール、GCイベントなどを詳細に表示します。`go tool trace` は、その機能の一部として、特定のイベント（例えば、同期プリミティブの競合）に関連する `pprof` プロファイルを生成する機能も持っています。

### 3. Protobuf (Protocol Buffers)

Protobufは、Googleが開発した、構造化されたデータをシリアライズするための言語に依存しない、プラットフォームに依存しない、拡張可能なメカニズムです。データ構造を定義する `.proto` ファイルから、様々なプログラミング言語のコードを生成できます。`pprof` プロファイルは、このProtobuf形式で表現されており、`profile.proto` というスキーマで定義されています。このスキーマには、プロファイルデータだけでなく、シンボル情報（関数名、ファイル名など）を格納するためのフィールドも含まれています。

### 4. プログラムバイナリの役割

従来の `go tool pprof` では、プロファイルデータ内のメモリアドレスをシンボル化するために、元のプログラムバイナリが必要でした。バイナリには、コンパイル時に生成されたシンボルテーブルが含まれており、これがアドレスとシンボル情報のマッピングを提供します。

## 技術的詳細

このコミットの核心は、`go tool trace` が生成する `pprof` プロファイルが、解析時に外部のプログラムバイナリに依存しないように、必要なシンボル情報をプロファイルデータ自体に埋め込む点にあります。

具体的には、以下の技術的アプローチが取られています。

1.  **`cmd/internal/pprof/profile` パッケージの利用**:
    Go 1.7以降、`pprof` の内部実装は `cmd/internal/pprof` パッケージに集約され、その中にプロファイルデータのProtobufスキーマを扱う `profile` サブパッケージが含まれています。このコミットでは、この `profile` パッケージをインポートし、そのデータ構造を利用して新しいプロファイルを構築しています。これにより、標準の `pprof` ツールが期待する形式で、かつシンボル情報を含んだプロファイルを生成することが可能になります。

2.  **`buildProfile` 関数の導入**:
    新しく `buildProfile` 関数が導入されました。この関数は、`go tool trace` が収集した生のプロファイリングレコード（`prof map[uint64]Record`）を受け取り、それを `profile.Profile` 構造体（Protobuf形式のプロファイルを表す）に変換します。
    *   `profile.Profile` 構造体には、`Function` (関数情報)、`Location` (コード上の位置情報)、`Sample` (サンプリングデータ) などのフィールドがあります。
    *   `buildProfile` 関数は、生のスタックトレース (`rec.stk`) から各フレームのPC (プログラムカウンタ)、ファイル名、関数名、行番号を抽出し、これらを `profile.Function` および `profile.Location` オブジェクトとして `profile.Profile` に追加します。
    *   これにより、各サンプリングデータ (`profile.Sample`) が参照する `profile.Location` オブジェクトを通じて、対応するシンボル情報がプロファイル内に完全に埋め込まれます。

3.  **`serveSVGProfile` 関数の変更**:
    `serveSVGProfile` 関数は、HTTPリクエストに応じてSVG形式のプロファイルを生成する役割を担っています。この関数内で、従来のテキストベースのプロファイル形式を一時ファイルに書き出す代わりに、新しく導入された `buildProfile` 関数を呼び出し、生成された `profile.Profile` オブジェクトをProtobuf形式で一時ファイルに書き出すように変更されました。
    *   以前は `fmt.Fprintf(blockb, "--- contention:\\ncycles/second=1000000000\\n")` のようなテキスト形式でプロファイル情報を出力していました。
    *   変更後は `buildProfile(prof).Write(blockb)` を呼び出し、Protobuf形式でプロファイルを書き出します。
    *   `go tool pprof` コマンドの呼び出しも変更され、`programBinary` 引数が削除されました。これは、プロファイル自体にシンボル情報が埋め込まれているため、外部バイナリが不要になったことを反映しています。

この変更により、`go tool trace` が生成するプロファイルは、自己完結型のシンボル情報を持つようになり、プロファイリングデータの共有と解析がより容易になりました。

## コアとなるコードの解説

### `serveSVGProfile` 関数の変更点

*   **インポートの追加**: `cmd/internal/pprof/profile` パッケージが新しくインポートされています。これは、Protobuf形式のプロファイル構造体 (`profile.Profile`) を利用するために必要です。
*   **一時ファイルへの書き込み方法の変更**:
    *   以前は、プロファイルデータをテキスト形式で一時ファイル (`blockf`) に書き込んでいました。具体的には、`--- contention:` で始まるヘッダと、`時間 数 @ PCアドレス` の形式でスタックトレースを記述していました。
    *   変更後は、新しく導入された `buildProfile` 関数を呼び出し、その戻り値である `*profile.Profile` オブジェクトを `Write` メソッドを使ってProtobuf形式で一時ファイルに書き込んでいます。これにより、プロファイルデータが構造化されたバイナリ形式で保存され、シンボル情報も含まれるようになります。
*   **`go tool pprof` コマンドの呼び出し変更**:
    *   `exec.Command` で `go tool pprof` を呼び出す際に、`programBinary` という引数が削除されました。これは、生成されたプロファイル自体にシンボル情報が埋め込まれているため、`pprof` がシンボル化のために外部のバイナリを必要としなくなったことを示しています。
    *   エラーメッセージも改善され、`go tool pprof` の実行が失敗した場合に、そのコマンドの標準出力/標準エラー出力 (`output`) も含めて報告されるようになりました。

### `buildProfile` 関数の新規追加

この関数は、`go tool trace` が収集した生のプロファイリングレコード (`prof map[uint64]Record`) を、`pprof` が解釈できるProtobuf形式の `profile.Profile` オブジェクトに変換する役割を担います。

1.  **`profile.Profile` の初期化**:
    *   `p := &profile.Profile{...}` で新しい `profile.Profile` オブジェクトを初期化します。
    *   `PeriodType` と `SampleType` は、プロファイルの種類（ここでは「trace」と「contentions」「delay」）と単位を定義します。
2.  **シンボル情報の構築**:
    *   `locs` (Locationマップ) と `funcs` (Functionマップ) は、重複する `profile.Location` および `profile.Function` オブジェクトを効率的に管理するためのマップです。
    *   `prof` マップをイテレートし、各プロファイリングレコード (`rec`) からスタックトレース (`rec.stk`) を取得します。
    *   スタックトレースの各フレーム (`frame`) について、以下の処理を行います。
        *   **`profile.Function` の生成**: `frame.File` と `frame.Fn` (関数名) を使って、まだマップに存在しない場合は新しい `profile.Function` オブジェクトを作成し、`p.Function` スライスに追加します。このオブジェクトには、関数名、システム名、ファイル名が含まれます。
        *   **`profile.Location` の生成**: `frame.PC` (プログラムカウンタ) を使って、まだマップに存在しない場合は新しい `profile.Location` オブジェクトを作成し、`p.Location` スライスに追加します。このオブジェクトには、PCアドレスと、そのアドレスに対応する `profile.Line` オブジェクト（関数と行番号を含む）が含まれます。
        *   これにより、生のPCアドレスが、ファイル名、関数名、行番号といった具体的なシンボル情報と関連付けられ、プロファイルデータ内に埋め込まれます。
3.  **`profile.Sample` の生成**:
    *   各プロファイリングレコード (`rec`) から、サンプリングされた値 (`rec.n` と `rec.time`) と、上記で構築した `profile.Location` オブジェクトのリスト (`sloc`) を使って、`profile.Sample` オブジェクトを作成します。
    *   この `profile.Sample` オブジェクトが `p.Sample` スライスに追加されます。

この `buildProfile` 関数によって、`go tool trace` は、`go tool pprof` がバイナリなしでシンボル化できる、リッチなProtobuf形式のプロファイルを生成できるようになります。

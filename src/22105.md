# [インデックス 22105] ファイルの概要

このコミットは、Go言語の標準ライブラリである`sync.Mutex`にアクティブスピン（active spinning）の機能を追加するものです。これにより、マルチコア環境下でのミューテックス競合時におけるパフォーマンスが改善されます。特に、クリティカルセクションが短い場合に、ゴルーチンをスケジューラに切り替えるオーバーヘッドを削減し、CPU利用率が高い状況での効率を高めることを目的としています。

## 変更の背景

Go言語の`sync.Mutex`は、これまで「完全に協調的（fully cooperative）」なロックメカニズムを採用していました。これは、あるゴルーチンがミューテックスを獲得しようとして既にロックされている場合、そのゴルーチンはすぐにスケジューラに制御を返し、他のゴルーチンに実行を譲るという挙動を意味します。

この協調的なアプローチは、一般的には効率的ですが、特定のシナリオではパフォーマンス上のボトルネックとなる可能性がありました。具体的には、以下のような状況です。

1.  **クリティカルセクションが非常に短い場合**: ミューテックスが保護するコード領域（クリティカルセクション）がごく短時間で実行される場合、ロックを獲得できなかったゴルーチンがすぐにスケジューラに制御を返しても、その直後にミューテックスが解放される可能性があります。この場合、ゴルーチンをスリープさせ、後で再度起こすというスケジューリングのオーバーヘッドが無駄になります。
2.  **マルチコア環境でCPU利用率が高い場合**: サーバーソフトウェアなどでは、CPU利用率が50%程度で動作していることがよくあります。このような状況では、CPUリソースに余裕があるため、ロックを獲得できなかったゴルーチンがすぐにスリープするのではなく、短時間だけCPUを占有してロックが解放されるのを待つ（スピンする）方が、コンテキストスイッチのコストを避ける上で有利になることがあります。

このコミットは、これらの問題に対処し、`sync.Mutex`が特定の条件下で「アクティブスピン」を行うことで、競合時のパフォーマンスを向上させることを目的としています。

## 前提知識の解説

このコミットの理解には、以下の概念が重要です。

*   **ゴルーチン (Goroutine)**: Goランタイムによって管理される軽量なスレッドです。Goの並行処理の基本単位となります。
*   **`sync.Mutex`**: Go言語の標準ライブラリ`sync`パッケージで提供される排他ロック（ミューテックス）です。共有リソースへのアクセスを同期し、データ競合を防ぐために使用されます。`Lock()`メソッドでロックを獲得し、`Unlock()`メソッドでロックを解放します。
*   **スケジューラ (Scheduler)**: Goランタイムの重要なコンポーネントで、ゴルーチンをOSスレッド（M: Machine）と論理プロセッサ（P: Processor）に割り当て、実行を管理します。
*   **P (Processor)**: Goランタイムスケジューラにおける論理プロセッサの概念です。PはM（OSスレッド）とG（ゴルーチン）を仲介し、実行可能なゴルーチンを保持するローカルな実行キュー（runq）を持ちます。`GOMAXPROCS`環境変数によって、同時に実行可能なPの数が制御されます。
*   **実行キュー (Run Queue)**: スケジューラが実行を待つゴルーチンを保持するキューです。各Pはローカルな実行キュー（local runq）を持ち、さらにグローバルな実行キュー（global runq）も存在します。
*   **アクティブスピン (Active Spinning)**: ロックを獲得できなかったスレッド（またはゴルーチン）が、CPUを占有したままループし、ロックが解放されるのを繰り返しチェックする待機戦略です。コンテキストスイッチのオーバーヘッドを避けることができますが、ロックがすぐに解放されない場合はCPUリソースを無駄に消費する可能性があります。
*   **パッシブスピン (Passive Spinning)**: アクティブスピンと異なり、ロックを獲得できなかったスレッドが、CPUを占有し続けるのではなく、短時間スピンした後にスケジューラに制御を返し、スリープ状態に入る待機戦略です。これにより、CPUの無駄な消費を抑えつつ、ロックがすぐに解放される可能性にも対応できます。Goのランタイム内部のミューテックス（`runtime`パッケージで使用されるもの）では、パッシブスピンが使用されることがあります。
*   **`GOMAXPROCS`**: Goプログラムが同時に使用できるOSスレッド（P）の最大数を設定する環境変数です。デフォルトではCPUの論理コア数に設定されます。
*   **`go:linkname`**: Goコンパイラディレクティブの一つで、異なるパッケージ間（特に`runtime`パッケージと他のパッケージ間）で、通常はエクスポートされない関数や変数にリンクすることを可能にします。これにより、`sync`パッケージが`runtime`パッケージの内部関数を呼び出すことができます。
*   **`procyield`**: Goランタイムの内部関数で、現在のゴルーチンがCPUを短時間だけ他のゴルーチンに譲る（yieldする）ことを示唆します。これは、CPUを完全に解放してスケジューラに制御を戻す`runtime.Gosched()`とは異なり、より軽量なCPUの譲渡メカニズムです。アクティブスピン中に使用され、CPUを完全に独占するのを避けます。

## 技術的詳細

このコミットは、`sync.Mutex`の`Lock()`メソッドにアクティブスピンのロジックを導入します。アクティブスピンは、以下の**4つの条件がすべて満たされた場合**に限定的に実行されます。

1.  **マルチコアマシンで実行されていること**: `ncpu`（システム上のCPUコア数）が1より大きいこと。シングルコアマシンではスピンしても意味がないためです。
2.  **`GOMAXPROCS`が1より大きいこと**: `GOMAXPROCS`が1の場合、並行して実行できるPが1つしかないため、スピンしても他のゴルーチンがロックを解放する可能性が低く、CPUを無駄に消費するだけになります。
3.  **少なくとも1つの他の実行中のPが存在すること**: `gomaxprocs`が、アイドル状態のPとスピン中のMの合計数に1を加えたものよりも大きいこと。これは、現在のP以外にもゴルーチンを実行できるPが存在し、それらのP上でロックを保持しているゴルーチンが実行されている可能性があることを意味します。
4.  **現在のPのローカル実行キュー（local runq）が空であること**: `p.runqhead != p.runqtail`が偽であること。ローカル実行キューに実行可能なゴルーチンがある場合、スピンするよりもそちらのゴルーチンを実行する方が効率的であるためです。

これらの条件は、`src/runtime/proc1.go`に追加された`sync_runtime_canSpin`関数によってチェックされます。この関数は`go:linkname`ディレクティブを使って`sync.runtime_canSpin`として`sync`パッケージから呼び出せるようになっています。

アクティブスピンが許可された場合、`sync.Mutex.Lock()`内のループで`runtime_doSpin()`が呼び出されます。この`runtime_doSpin()`関数は、`src/runtime/proc1.go`に定義されており、内部で`procyield(active_spin_cnt)`を呼び出します。`procyield`は、現在のゴルーチンがCPUを短時間だけ他のゴルーチンに譲ることを示唆するランタイム関数です。これにより、スピン中にCPUを完全に独占するのではなく、他のゴルーチンにも機会を与えることで、より公平なリソース利用を促進します。

また、`sync.Mutex`の`Lock()`メソッドでは、スピン中に`mutexWoken`フラグを設定しようと試みます。これは、`Unlock`メソッドに対して、他のブロックされたゴルーチンを起こす必要がないことを通知するためのものです。これにより、不要なゴルーチンのウェイクアップを防ぎ、効率を向上させます。

ベンチマーク結果は、特に`BenchmarkMutexSpin`や`BenchmarkMutex`のマルチコア環境での改善を示しており、この変更が特定の競合シナリオで有効であることを裏付けています。例えば、`BenchmarkMutex-2`では33.46%の改善が見られます。

このコミットによる主要なコード変更は以下のファイルに集中しています。

## コアとなるコードの解説

### `src/runtime/proc1.go` の変更

```go
// Active spinning for sync.Mutex.
//go:linkname sync_runtime_canSpin sync.runtime_canSpin
//go:nosplit
func sync_runtime_canSpin(i int) bool {
	// sync.Mutex is cooperative, so we are conservative with spinning.
	// Spin only few times and only if running on a multicore machine and
	// GOMAXPROCS>1 and there is at least one other running P and local runq is empty.
	// As opposed to runtime mutex we don't do passive spinning here,
	// because there can be work on global runq on on other Ps.
	if i >= active_spin || ncpu <= 1 || gomaxprocs <= int32(sched.npidle+sched.nmspinning)+1 {
		return false
	}
	if p := getg().m.p; p.runqhead != p.runqtail {
		return false
	}
	return true
}

//go:linkname sync_runtime_doSpin sync.runtime_doSpin
//go:nosplit
func sync_runtime_doSpin() {
	procyield(active_spin_cnt)
}
```

*   `sync_runtime_canSpin`: この関数は、`sync.Mutex`がアクティブスピンを行うべきかどうかを決定する主要なロジックを含んでいます。
    *   `i >= active_spin`: スピンの試行回数`i`が`active_spin`（定数、おそらくスピンの最大回数を定義）を超えた場合、スピンを停止します。これは無限スピンを防ぐためのガードです。
    *   `ncpu <= 1`: システムのCPUコア数が1以下の場合、スピンは無意味なので停止します。
    *   `gomaxprocs <= int32(sched.npidle+sched.nmspinning)+1`: `GOMAXPROCS`が、アイドル状態のPとスピン中のMの合計数に1を加えたもの以下の場合、スピンを停止します。これは、現在のP以外に実行可能なPが存在しない、または非常に少ない場合にスピンを避けるための条件です。
    *   `p.runqhead != p.runqtail`: 現在のPのローカル実行キューに実行可能なゴルーチンが存在する場合、スピンを停止します。ローカルに実行可能なゴルーチンがあるなら、そちらを実行する方が効率的だからです。
*   `sync_runtime_doSpin`: この関数は、実際にアクティブスピン中のCPU譲渡を行います。
    *   `procyield(active_spin_cnt)`: `procyield`は、現在のゴルーチンがCPUを短時間だけ他のゴルーチンに譲ることをスケジューラに示唆します。`active_spin_cnt`は譲渡の粒度を制御する定数です。

### `src/sync/mutex.go` の変更

```go
func (m *Mutex) Lock() {
	// ... (既存のコード) ...

	awoke := false
	iter := 0 // スピン回数を追跡するイテレータ
	for {
		old := m.state
		new := old | mutexLocked
		if old&mutexLocked != 0 { // ロックが既に取得されている場合
			if runtime_canSpin(iter) { // アクティブスピンが可能かチェック
				// Active spinning makes sense.
				// Try to set mutexWoken flag to inform Unlock
				// to not wake other blocked goroutines.
				if !awoke && old&mutexWoken == 0 && old>>mutexWaiterShift != 0 &&
					atomic.CompareAndSwapInt32(&m.state, old, old|mutexWoken) {
					awoke = true
				}
				runtime_doSpin() // スピンを実行
				iter++           // スピン回数をインクリメント
				continue         // ループを続行し、再度ロック獲得を試みる
			}
			new = old + 1<<mutexWaiterShift // スピンしない場合、待機ゴルーチン数をインクリメント
		}
		if awoke {
			// The goroutine has been woken from sleep,
			// so we need to reset the flag in either case.
			if new&mutexWoken == 0 {
				panic("sync: inconsistent mutex state")
			}
			new &^= mutexWoken
		}
		if atomic.CompareAndSwapInt32(&m.state, old, new) {
			if old&mutexLocked == 0 {
				break // ロック獲得成功
			}
			// ... (既存のコード) ...
			runtime_Semacquire(&m.sema) // セマフォでスリープ
			awoke = true
			iter = 0 // スリープから復帰したらスピン回数をリセット
		}
	}
}
```

*   `iter := 0`: `Lock()`メソッドのループ内で、スピンの試行回数を追跡するためのカウンタが導入されました。
*   `if old&mutexLocked != 0`: ミューテックスが既にロックされている場合に、競合処理のパスに入ります。
*   `if runtime_canSpin(iter)`: `runtime`パッケージからリンクされた`runtime_canSpin`関数を呼び出し、現在アクティブスピンを行うべきかどうかを判断します。
*   `runtime_doSpin()`: `runtime_canSpin`が`true`を返した場合、`runtime_doSpin`を呼び出して実際にスピン（`procyield`）を行います。
*   `iter++`: スピンするたびに`iter`をインクリメントし、スピン回数を制限します。
*   `if !awoke && old&mutexWoken == 0 && old>>mutexWaiterShift != 0 && atomic.CompareAndSwapInt32(&m.state, old, old|mutexWoken)`:
    *   この条件は、まだウェイクアップされておらず（`!awoke`）、`mutexWoken`フラグが設定されておらず、待機中のゴルーチンが存在する場合に、`mutexWoken`フラグを設定しようと試みます。
    *   `mutexWoken`フラグは、`Unlock`メソッドに対して、このゴルーチンがスピンによってロックを獲得しようとしているため、他の待機中のゴルーチンをウェイクアップする必要がないことを示唆します。これにより、不要なウェイクアップによるオーバーヘッドを削減します。
*   `iter = 0`: セマフォでスリープした後（つまり、実際にブロックされた後）にウェイクアップされた場合、`iter`をリセットします。これは、次にロックを試みる際に、スピンの機会を再度与えるためです。

これらの変更により、`sync.Mutex`は、特定の条件下で短時間のアクティブスピンを行うことで、コンテキストスイッチのオーバーヘッドを削減し、特にクリティカルセクションが短い場合のパフォーマンスを向上させます。

## 変更の背景

Go言語の`sync.Mutex`は、これまで「完全に協調的（fully cooperative）」なロックメカニズムを採用していました。これは、あるゴルーチンがミューテックスを獲得しようとして既にロックされている場合、そのゴルーチンはすぐにスケジューラに制御を返し、他のゴルーチンに実行を譲るという挙動を意味します。

この協調的なアプローチは、一般的には効率的ですが、特定のシナリオではパフォーマンス上のボトルネックとなる可能性がありました。具体的には、以下のような状況です。

1.  **クリティカルセクションが非常に短い場合**: ミューテックスが保護するコード領域（クリティカルセクション）がごく短時間で実行される場合、ロックを獲得できなかったゴルーチンがすぐにスケジューラに制御を返しても、その直後にミューテックスが解放される可能性があります。この場合、ゴルーチンをスリープさせ、後で再度起こすというスケジューリングのオーバーヘッドが無駄になります。
2.  **マルチコア環境でCPU利用率が高い場合**: サーバーソフトウェアなどでは、CPU利用率が50%程度で動作していることがよくあります。このような状況では、CPUリソースに余裕があるため、ロックを獲得できなかったゴルーチンがすぐにスリープするのではなく、短時間だけCPUを占有してロックが解放されるのを待つ（スピンする）方が、コンテキストスイッチのコストを避ける上で有利になることがあります。

このコミットは、これらの問題に対処し、`sync.Mutex`が特定の条件下で「アクティブスピン」を行うことで、競合時のパフォーマンスを向上させることを目的としています。

## 前提知識の解説

このコミットの理解には、以下の概念が重要です。

*   **ゴルーチン (Goroutine)**: Goランタイムによって管理される軽量なスレッドです。Goの並行処理の基本単位となります。
*   **`sync.Mutex`**: Go言語の標準ライブラリ`sync`パッケージで提供される排他ロック（ミューテックス）です。共有リソースへのアクセスを同期し、データ競合を防ぐために使用されます。`Lock()`メソッドでロックを獲得し、`Unlock()`メソッドでロックを解放します。
*   **スケジューラ (Scheduler)**: Goランタイムの重要なコンポーネントで、ゴルーチンをOSスレッド（M: Machine）と論理プロセッサ（P: Processor）に割り当て、実行を管理します。
*   **P (Processor)**: Goランタイムスケジューラにおける論理プロセッサの概念です。PはM（OSスレッド）とG（ゴルーチン）を仲介し、実行可能なゴルーチンを保持するローカルな実行キュー（runq）を持ちます。`GOMAXPROCS`環境変数によって、同時に実行可能なPの数が制御されます。
*   **実行キュー (Run Queue)**: スケジューラが実行を待つゴルーチンを保持するキューです。各Pはローカルな実行キュー（local runq）を持ち、さらにグローバルな実行キュー（global runq）も存在します。
*   **アクティブスピン (Active Spinning)**: ロックを獲得できなかったスレッド（またはゴルーチン）が、CPUを占有したままループし、ロックが解放されるのを繰り返しチェックする待機戦略です。コンテキストスイッチのオーバーヘッドを避けることができますが、ロックがすぐに解放されない場合はCPUリソースを無駄に消費する可能性があります。
*   **パッシブスピン (Passive Spinning)**: アクティブスピンと異なり、ロックを獲得できなかったスレッドが、CPUを占有し続けるのではなく、短時間スピンした後にスケジューラに制御を返し、スリープ状態に入る待機戦略です。これにより、CPUの無駄な消費を抑えつつ、ロックがすぐに解放される可能性にも対応できます。Goのランタイム内部のミューテックス（`runtime`パッケージで使用されるもの）では、パッシブスピンが使用されることがあります。
*   **`GOMAXPROCS`**: Goプログラムが同時に使用できるOSスレッド（P）の最大数を設定する環境変数です。デフォルトではCPUの論理コア数に設定されます。
*   **`go:linkname`**: Goコンパイラディレクティブの一つで、異なるパッケージ間（特に`runtime`パッケージと他のパッケージ間）で、通常はエクスポートされない関数や変数にリンクすることを可能にします。これにより、`sync`パッケージが`runtime`パッケージの内部関数を呼び出すことができます。
*   **`procyield`**: Goランタイムの内部関数で、現在のゴルーチンがCPUを短時間だけ他のゴルーチンに譲る（yieldする）ことを示唆します。これは、CPUを完全に解放してスケジューラに制御を戻す`runtime.Gosched()`とは異なり、より軽量なCPUの譲渡メカニズムです。アクティブスピン中に使用され、CPUを完全に独占するのを避けます。

## 技術的詳細

このコミットは、`sync.Mutex`の`Lock()`メソッドにアクティブスピンのロジックを導入します。アクティブスピンは、以下の**4つの条件がすべて満たされた場合**に限定的に実行されます。

1.  **マルチコアマシンで実行されていること**: `ncpu`（システム上のCPUコア数）が1より大きいこと。シングルコアマシンではスピンしても意味がないためです。
2.  **`GOMAXPROCS`が1より大きいこと**: `GOMAXPROCS`が1の場合、並行して実行できるPが1つしかないため、スピンしても他のゴルーチンがロックを解放する可能性が低く、CPUを無駄に消費するだけになります。
3.  **少なくとも1つの他の実行中のPが存在すること**: `gomaxprocs`が、アイドル状態のPとスピン中のMの合計数に1を加えたものよりも大きいこと。これは、現在のP以外にもゴルーチンを実行できるPが存在し、それらのP上でロックを保持しているゴルーチンが実行されている可能性があることを意味します。
4.  **現在のPのローカル実行キュー（local runq）が空であること**: `p.runqhead != p.runqtail`が偽であること。ローカル実行キューに実行可能なゴルーチンがある場合、スピンするよりもそちらのゴルーチンを実行する方が効率的であるためです。

これらの条件は、`src/runtime/proc1.go`に追加された`sync_runtime_canSpin`関数によってチェックされます。この関数は`go:linkname`ディレクティブを使って`sync.runtime_canSpin`として`sync`パッケージから呼び出せるようになっています。

アクティブスピンが許可された場合、`sync.Mutex.Lock()`内のループで`runtime_doSpin()`が呼び出されます。この`runtime_doSpin()`関数は、`src/runtime/proc1.go`に定義されており、内部で`procyield(active_spin_cnt)`を呼び出します。`procyield`は、現在のゴルーチンがCPUを短時間だけ他のゴルーチンに譲ることを示唆するランタイム関数です。これにより、スピン中にCPUを完全に独占するのではなく、他のゴルーチンにも機会を与えることで、より公平なリソース利用を促進します。

また、`sync.Mutex`の`Lock()`メソッドでは、スピン中に`mutexWoken`フラグを設定しようと試みます。これは、`Unlock`メソッドに対して、このゴルーチンがスピンによってロックを獲得しようとしているため、他のブロックされたゴルーチンをウェイクアップする必要がないことを通知するためのものです。これにより、不要なゴルーチンのウェイクアップを防ぎ、効率を向上させます。

ベンチマーク結果は、特に`BenchmarkMutexSpin`や`BenchmarkMutex`のマルチコア環境での改善を示しており、この変更が特定の競合シナリオで有効であることを裏付けています。例えば、`BenchmarkMutex-2`では33.46%の改善が見られます。

## コアとなるコードの解説

### `src/runtime/proc1.go` の変更

```go
// Active spinning for sync.Mutex.
//go:linkname sync_runtime_canSpin sync.runtime_canSpin
//go:nosplit
func sync_runtime_canSpin(i int) bool {
	// sync.Mutex is cooperative, so we are conservative with spinning.
	// Spin only few times and only if running on a multicore machine and
	// GOMAXPROCS>1 and there is at least one other running P and local runq is empty.
	// As opposed to runtime mutex we don't do passive spinning here,
	// because there can be work on global runq on on other Ps.
	if i >= active_spin || ncpu <= 1 || gomaxprocs <= int32(sched.npidle+sched.nmspinning)+1 {
		return false
	}
	if p := getg().m.p; p.runqhead != p.runqtail {
		return false
	}
	return true
}

//go:linkname sync_runtime_doSpin sync.runtime_doSpin
//go:nosplit
func sync_runtime_doSpin() {
	procyield(active_spin_cnt)
}
```

*   `sync_runtime_canSpin`: この関数は、`sync.Mutex`がアクティブスピンを行うべきかどうかを決定する主要なロジックを含んでいます。
    *   `i >= active_spin`: スピンの試行回数`i`が`active_spin`（定数、おそらくスピンの最大回数を定義）を超えた場合、スピンを停止します。これは無限スピンを防ぐためのガードです。
    *   `ncpu <= 1`: システムのCPUコア数が1以下の場合、スピンは無意味なので停止します。
    *   `gomaxprocs <= int32(sched.npidle+sched.nmspinning)+1`: `GOMAXPROCS`が、アイドル状態のPとスピン中のMの合計数に1を加えたもの以下の場合、スピンを停止します。これは、現在のP以外に実行可能なPが存在しない、または非常に少ない場合にスピンを避けるための条件です。
    *   `p.runqhead != p.runqtail`: 現在のPのローカル実行キューに実行可能なゴルーチンが存在する場合、スピンを停止します。ローカルに実行可能なゴルーチンがあるなら、そちらを実行する方が効率的だからです。
*   `sync_runtime_doSpin`: この関数は、実際にアクティブスピン中のCPU譲渡を行います。
    *   `procyield(active_spin_cnt)`: `procyield`は、現在のゴルーチンがCPUを短時間だけ他のゴルーチンに譲ることをスケジューラに示唆します。`active_spin_cnt`は譲渡の粒度を制御する定数です。

### `src/sync/mutex.go` の変更

```go
func (m *Mutex) Lock() {
	// ... (既存のコード) ...

	awoke := false
	iter := 0 // スピン回数を追跡するイテレータ
	for {
		old := m.state
		new := old | mutexLocked
		if old&mutexLocked != 0 { // ロックが既に取得されている場合
			if runtime_canSpin(iter) { // アクティブスピンが可能かチェック
				// Active spinning makes sense.
				// Try to set mutexWoken flag to inform Unlock
				// to not wake other blocked goroutines.
				if !awoke && old&mutexWoken == 0 && old>>mutexWaiterShift != 0 &&
					atomic.CompareAndSwapInt32(&m.state, old, old|mutexWoken) {
					awoke = true
				}
				runtime_doSpin() // スピンを実行
				iter++           // スピン回数をインクリメント
				continue         // ループを続行し、再度ロック獲得を試みる
			}
			new = old + 1<<mutexWaiterShift // スピンしない場合、待機ゴルーチン数をインクリメント
		}
		if awoke {
			// The goroutine has been woken from sleep,
			// so we need to reset the flag in either case.
			if new&mutexWoken == 0 {
				panic("sync: inconsistent mutex state")
			}
			new &^= mutexWoken
		}
		if atomic.CompareAndSwapInt32(&m.state, old, new) {
			if old&mutexLocked == 0 {
				break // ロック獲得成功
			}
			// ... (既存のコード) ...
			runtime_Semacquire(&m.sema) // セマフォでスリープ
			awoke = true
			iter = 0 // スリープから復帰したらスピン回数をリセット
		}
	}
}
```

*   `iter := 0`: `Lock()`メソッドのループ内で、スピンの試行回数を追跡するためのカウンタが導入されました。
*   `if old&mutexLocked != 0`: ミューテックスが既にロックされている場合に、競合処理のパスに入ります。
*   `if runtime_canSpin(iter)`: `runtime`パッケージからリンクされた`runtime_canSpin`関数を呼び出し、現在アクティブスピンを行うべきかどうかを判断します。
*   `runtime_doSpin()`: `runtime_canSpin`が`true`を返した場合、`runtime_doSpin`を呼び出して実際にスピン（`procyield`）を行います。
*   `iter++`: スピンするたびに`iter`をインクリメントし、スピン回数を制限します。
*   `if !awoke && old&mutexWoken == 0 && old>>mutexWaiterShift != 0 && atomic.CompareAndSwapInt32(&m.state, old, old|mutexWoken)`:
    *   この条件は、まだウェイクアップされておらず（`!awoke`）、`mutexWoken`フラグが設定されておらず、待機中のゴルーチンが存在する場合に、`mutexWoken`フラグを設定しようと試みます。
    *   `mutexWoken`フラグは、`Unlock`メソッドに対して、このゴルーチンがスピンによってロックを獲得しようとしているため、他の待機中のゴルーチンをウェイクアップする必要がないことを示唆します。これにより、不要なウェイクアップによるオーバーヘッドを削減します。
*   `iter = 0`: セマフォでスリープした後（つまり、実際にブロックされた後）にウェイクアップされた場合、`iter`をリセットします。これは、次にロックを試みる際に、スピンの機会を再度与えるためです。

これらの変更により、`sync.Mutex`は、特定の条件下で短時間のアクティブスピンを行うことで、コンテキストスイッチのオーバーヘッドを削減し、特にクリティカルセクションが短い場合のパフォーマンスを向上させます。

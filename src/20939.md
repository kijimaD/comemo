# [インデックス 20939] ファイルの概要

このコミットは、Goランタイムにおいて、Goが管理していない外部スレッド（特にCgoを介して生成されたスレッド）でパニックが発生した際に、ランタイムが回復不能なパニックに陥る問題を修正するものです。具体的には、パニック発生時に`g0`（システムゴルーチン）のスタックポインタ（`m->sched.sp`）が適切に初期化されていないために、スタックのアンワインド処理が失敗し、プログラムがクラッシュするのを防ぎます。

## 変更の背景

Goプログラムは、Goランタイムが管理するゴルーチン上で動作します。しかし、Cgo（GoとC言語の相互運用機能）を使用すると、CコードがGoランタイムの管理外で新しいOSスレッドを生成することがあります。これらの「外部スレッド」からGoの関数を呼び出し、そのGo関数内でパニックが発生した場合、Goランタイムの通常のパニック処理メカニズムが正しく機能しない可能性がありました。

特に問題となったのは、パニック発生時にスタックをアンワインド（巻き戻し）してスタックトレースを生成したり、パニックハンドラを呼び出したりする際に、Goランタイムが使用する`g0`（システムゴルーチン）のスタックポインタ（`m->sched.sp`）が未初期化の状態であることでした。この未初期化のスタックポインタが使用されると、ランタイムが不正なメモリ位置にアクセスしようとし、結果として回復不能なクラッシュを引き起こしていました。

このコミットは、このようなシナリオでGoプログラムが安定して動作し、外部スレッドからのパニックも適切に処理できるようにするために導入されました。

## 前提知識の解説

このコミットの理解には、Goランタイムの内部構造とパニック処理に関するいくつかの前提知識が必要です。

*   **GoランタイムのM, P, Gモデル**:
    *   **M (Machine)**: オペレーティングシステムのスレッドを表します。Goランタイムは、複数のMを生成し、その上でGoコードを実行します。
    *   **P (Processor)**: 論理的なプロセッサを表し、MとGを仲介します。Pは実行可能なGのキューを持ち、MがPを取得することでGを実行できます。
    *   **G (Goroutine)**: Goの軽量な並行処理単位です。Goの関数呼び出しはすべてゴルーチン上で実行されます。

*   **g0 (システムゴルーチン)**:
    各M（OSスレッド）には、通常のゴルーチンとは別に、特別な「システムゴルーチン」である`g0`が紐付けられています。`g0`は、Goランタイムの内部処理（スケジューラの実行、ガベージコレクション、パニックハンドリング、Cgoコールなど）を実行するために使用されます。`g0`は通常のゴルーチンとは異なる、固定サイズのスタックを持っています。

*   **`m->sched.sp`**:
    `m`構造体（OSスレッドを表す）の内部には、`sched`というスケジューラ関連のコンテキスト情報が含まれています。その中に`sp`（スタックポインタ）フィールドがあり、これは`g0`のスタックポインタを指します。Goランタイムは、ゴルーチン間のコンテキストスイッチや、パニック発生時のスタックアンワインド処理において、この`m->sched.sp`を重要な情報として利用します。

*   **パニックとリカバリ**:
    Goには、プログラムの異常終了を防ぐためのパニック・リカバリメカニズムがあります。`panic`関数が呼び出されると、通常の実行フローが中断され、遅延関数（`defer`）が実行されます。`defer`された関数内で`recover()`が呼び出されると、パニックを捕捉し、プログラムのクラッシュを防ぐことができます。しかし、`recover()`で捕捉されないパニックは「unrecovered panic」となり、最終的にプログラムを終了させます。

*   **Cgoと外部スレッド**:
    Cgoは、GoプログラムからC言語の関数を呼び出したり、C言語からGoの関数を呼び出したりするためのメカニズムです。C言語のライブラリが内部で新しいOSスレッドを生成し、そのスレッドからGoの関数を呼び出す場合があります。これらのスレッドはGoランタイムのスケジューラによって直接管理されていないため、「外部スレッド」と呼ばれます。外部スレッドでGo関数がパニックを起こすと、Goランタイムの内部状態が予期せぬものになる可能性がありました。

*   **`unwindm`と`onM`**:
    Goランタイムの内部関数で、パニック処理やスタック管理に関連します。
    *   `unwindm`: パニック発生時などに、現在のスタックを巻き戻し（アンワインド）て、スタックトレースを生成したり、パニックハンドラを探したりする処理を担当します。この際、`g0`のスタックポインタなどの情報が利用されます。
    *   `onM`: 特定のM（OSスレッド）上で実行されるべき処理を指します。パニック後のクリーンアップや状態復元など、Mのコンテキストに依存する操作が含まれることがあります。

## 技術的詳細

この問題の核心は、外部スレッドからGo関数が呼び出され、そのGo関数内でパニックが発生した場合に、`g0`のスタックポインタ`m->sched.sp`が未初期化のままになる可能性があったことです。

Goランタイムは、パニックが発生すると`unwindm`などのメカニズムを使ってスタックをアンワインドし、適切なパニックハンドラを探したり、スタックトレースを生成したりします。この処理の中で、`g0`のスタックポインタ（`m->sched.sp`）が参照されます。もしこの`m->sched.sp`が未初期化（例えば0）のままだと、`unwindm`が不正なメモリ位置をスタックポインタとして復元してしまい、その後に`onM`などの関数がその不正なスタックポインタを使用しようとすることで、プログラムがクラッシュしていました。

このコミットの解決策は、Go関数が外部スレッドから呼び出される直前、つまり`g0`スタックに切り替わってGoランタイムの処理が開始される時点で、`m->sched.sp`を現在のスタックポインタ（`SP`レジスタの値）で明示的に初期化することです。

アセンブリコードのコメントにあるように、この初期化は一見冗長に見えるかもしれません。なぜなら、その後のコードで同じスタックポインタがスタックに保存され、再び`m->sched.sp`に書き戻されるからです。しかし、この「冗長な」初期化が非常に重要です。もし、この初期化が行われないままパニックが発生し、`unwindm`がスタックから`g->sched.sp`を復元しようとした場合、その値は未初期化のままであり、`onM`がそれを使用するとクラッシュします。このコミットによって、`m->sched.sp`は常に有効なスタックポインタを保持することが保証され、外部スレッドからのパニック時でもランタイムが安定して動作するようになります。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

1.  **`src/runtime/asm_386.s`**
2.  **`src/runtime/asm_amd64.s`**
3.  **`src/runtime/asm_arm.s`**
    これら3つのファイルは、それぞれ32ビットx86、64ビットx86、ARMアーキテクチャ向けのアセンブリコードです。Goランタイムの低レベルな処理、特にCgoコールバックやスレッドの初期化に関連する部分が変更されています。
    具体的には、`needm`ラベルの後に、`m->sched.sp`を現在のスタックポインタ`SP`で初期化する命令が追加されています。

    例 (`src/runtime/asm_amd64.s`):
    ```assembly
    	// Set m->sched.sp = SP, so that if a panic happens
    	// during the function we are about to execute, it will
    	// have a valid SP to run on the g0 stack.
    	// The next few lines (after the havem label)
    	// will save this SP onto the stack and then write
    	// the same SP back to m->sched.sp. That seems redundant,
    	// but if an unrecovered panic happens, unwindm will
    	// restore the g->sched.sp from the stack location
    	// and then onM will try to use it. If we don't set it here,
    	// that restored SP will be uninitialized (typically 0) and
    	// will not be usable.
    	MOVQ	m_g0(BP), SI
    	MOVQ	SP, (g_sched+gobuf_sp)(SI)
    ```

4.  **`src/runtime/crash_cgo_test.go`**
    Cgoに関連するクラッシュテストが追加されています。特に`TestCgoExternalThreadPanic`という新しいテストケースが追加され、Cgoを介して外部スレッドからGo関数を呼び出し、その中でパニックを発生させるシナリオを再現しています。

5.  **`src/runtime/crash_test.go`**
    テストユーティリティ関数`executeTest`が修正され、複数のソースファイルをテストに含めることができるようになっています。これは`crash_cgo_test.go`でCコードとGoコードを組み合わせてテストするために必要です。

## コアとなるコードの解説

*   **アセンブリコードの変更 (`asm_*.s`)**:
    Goランタイムは、Cgoコールバックなどによって外部スレッドからGoコードに制御が移る際に、そのOSスレッドをGoのM（Machine）として認識し、`g0`スタックに切り替えてランタイム処理を開始します。この切り替え処理の中で、`needm`というラベルの箇所で、現在のOSスレッドに対応するMがまだ存在しない場合に新しいMを割り当てたり、既存のMを再利用したりします。
    このコミットで追加されたアセンブリ命令は、まさにこの`needm`の直後、Goランタイムが`g0`スタック上で動作を開始する直前に、`m->sched.sp`（`g0`のスタックポインタ）を現在の`SP`レジスタの値で明示的に設定しています。これにより、万が一この直後にパニックが発生しても、`m->sched.sp`が常に有効なスタックポインタを指していることが保証され、`unwindm`が不正な値を参照してクラッシュするのを防ぎます。

*   **テストコードの追加 (`crash_cgo_test.go`)**:
    `TestCgoExternalThreadPanic`テストは、このバグを再現し、修正が正しく機能することを確認するための重要な部分です。
    このテストでは、以下の手順を踏んでいます。
    1.  Goの`main`関数からCの`start`関数を呼び出す。
    2.  Cの`start`関数内で`pthread_create`を使って新しいOSスレッドを生成する。
    3.  新しく生成されたCのスレッドから、Goの`gopanic`関数を呼び出す。
    4.  Goの`gopanic`関数内で`panic("BOOM")`を実行する。
    このシナリオは、Goランタイムの管理外の外部スレッドからGo関数が呼び出され、その中でパニックが発生するという、まさにこのコミットが修正しようとしている状況を再現しています。テストは、このパニックが適切に捕捉され、プログラムがクラッシュせずに「panic: BOOM」というメッセージを出力して終了することを確認します。

これらの変更により、Goランタイムは外部スレッドからのパニックに対しても堅牢になり、より安定した動作が保証されるようになりました。

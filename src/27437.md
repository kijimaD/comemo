# [インデックス 27437] ファイルの概要

このコミットは、Goコンパイラの`cmd/compile`パッケージにおけるエスケープ解析の挙動を修正し、不要な`OTFUNC`ノード情報の取り扱いを改善するものです。具体的には、エスケープ解析が`OTFUNC`ノードのスライスを参照していた問題を解決するため、関数宣言（`Func.Dcl`）を直接参照するように変更し、`OTYPE`への変換時に`OTFUNC`関連情報をクリアするようにしています。これにより、コンパイラの内部構造が簡素化され、将来的な`OTFUNC`の廃止に向けた準備が進められます。

## コミット

```
cmd/compile: clear OTFUNC info when converting to OTYPE

I want to get rid of OTFUNC, which serves no useful purpose. However,
it turns out that the escape analysis pass looks at the node slices set
up for OTFUNC, even though by the time escape analysis runs the OTFUNC
has been converted to OTYPE. This CL converts the escape analysis code
to look at the function decls instead, and clears the OTFUNC info when
converting to OTYPE to ensure that nothing else looks at it.
```

## 変更の背景

この変更の主な背景は、Goコンパイラ内部で`OTFUNC`というノードタイプが「もはや有用な目的を果たしていない」と判断されたことにあります。`OTFUNC`は、関数型を表すために一時的に使用される抽象構文木（AST）ノードの一種でしたが、コンパイルプロセスの早い段階で`OTYPE`（型ノード）に変換されていました。

しかし、エスケープ解析（escape analysis）のパスが、この`OTFUNC`ノードが設定していたノードスライス（`Node`のリスト）を誤って参照し続けているという問題が発見されました。エスケープ解析が実行される時点では、`OTFUNC`は既に`OTYPE`に変換されているため、この参照は無意味であり、潜在的なバグや混乱の原因となっていました。

このコミットは、この不整合を解消し、将来的に`OTFUNC`ノードタイプを完全に廃止するための準備として行われました。エスケープ解析が正しい情報源（関数宣言）を参照するように修正し、`OTYPE`への変換時に`OTFUNC`に関連する情報を明示的にクリアすることで、コンパイラの健全性と保守性を向上させています。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Goコンパイラは、Go言語のソースコードを機械語に変換するツールチェーンの一部です。`cmd/compile`は、その主要なコンポーネントであり、字句解析、構文解析、型チェック、エスケープ解析、最適化、コード生成などの段階を経て実行されます。

### 抽象構文木 (AST) と `Node`

コンパイラは、ソースコードを解析する際に、プログラムの構造を抽象構文木（AST）として表現します。ASTは、プログラムの各要素（変数、関数、式など）を`Node`と呼ばれるオブジェクトで表現したツリー構造です。Goコンパイラでは、`Node`構造体がこれらの要素を表現し、`Node.Op`フィールドがそのノードの種別（例: `ONAME`、`OCALLFUNC`、`OTYPE`、`OTFUNC`など）を示します。

### `OTFUNC` と `OTYPE`

*   **`OTFUNC`**: かつてGoコンパイラ内部で関数型を表すために使用されていたASTノードのオペレーションコードです。コミットメッセージにあるように、これは一時的なものであり、コンパイルの早い段階で`OTYPE`に変換されることが意図されていました。
*   **`OTYPE`**: 型を表すASTノードのオペレーションコードです。`int`、`string`、`func(int) string`のような具体的な型情報を保持します。

### エスケープ解析 (Escape Analysis)

エスケープ解析は、Goコンパイラの重要な最適化パスの一つです。この解析の目的は、ある変数がその変数が宣言されたスコープを「エスケープ」するかどうかを判断することです。

*   **エスケープする**: 変数がそのスコープ外から参照され続ける可能性がある場合（例: 関数からポインタが返される、グローバル変数に代入されるなど）。エスケープする変数はヒープに割り当てられる必要があります。
*   **エスケープしない**: 変数がそのスコープ内でのみ使用され、関数が終了すると参照されなくなる場合。エスケープしない変数はスタックに割り当てることができます。

スタック割り当てはヒープ割り当てよりも高速であり、ガベージコレクションの負荷を軽減するため、エスケープ解析はGoプログラムのパフォーマンスに大きく貢献します。

### `Func.Dcl` (Function Declarations)

Goコンパイラ内部では、関数に関する情報は`Func`構造体に保持されます。`Func.Dcl`は、その関数内で宣言されたローカル変数、パラメータ、戻り値などの宣言（`Dcl`はDeclarationの略）のリストを指します。エスケープ解析は、これらの宣言情報を参照して、変数のエスケープ挙動を判断します。

### `PPARAM` と `PPARAMOUT`

これらは、関数のパラメータと戻り値を表すための`Node.Class`（ノードの分類）です。
*   **`PPARAM`**: 関数の入力パラメータ（引数）を表します。
*   **`PPARAMOUT`**: 関数の出力パラメータ（戻り値）を表します。

### `OCALLFUNC` と `ODDDARG`

*   **`OCALLFUNC`**: 関数呼び出しを表すASTノードのオペレーションコードです。
*   **`ODDDARG`**: 可変長引数（`...`）の呼び出しにおいて、引数を配列として扱うために導入される一時的なASTノードです。

## 技術的詳細

このコミットは、Goコンパイラのエスケープ解析（`esc.go`）と型チェック（`typecheck.go`）の2つの主要なファイルに影響を与えます。

### エスケープ解析の修正 (`esc.go`)

以前のエスケープ解析では、関数呼び出しのエスケープ挙動を分析する際に、`fn.Name.Param.Ntype.Rlist.Slice()`や`fn.Name.Param.Ntype.List.Slice()`といった`OTFUNC`ノードに関連するスライスを参照していました。しかし、これらのスライスは`OTFUNC`が`OTYPE`に変換された後も残存しており、エスケープ解析が誤った、あるいは古い情報を参照する原因となっていました。

このコミットでは、エスケープ解析のコードが、関数呼び出しの引数と戻り値の処理において、`fn.Name.Defn.Func.Dcl`（関数宣言のリスト）を直接参照するように変更されました。これにより、エスケープ解析は常に最新かつ正確な関数パラメータと戻り値の宣言情報を取得できるようになります。

具体的には、`esccall`関数内で、`DclLoop`という新しいループが導入され、`fn.Name.Defn.Func.Dcl`をイテレートして、`PPARAM`（入力パラメータ）と`PPARAMOUT`（出力パラメータ）のノードを処理します。

*   **入力パラメータの処理**: `PPARAM`ノードに対して、呼び出し元の引数（`lls`スライス）との関連付けを行い、エスケープ解析を行います。レシーバを持つメソッド呼び出しの場合、レシーバも適切に処理されます。可変長引数（`...`）の場合には、`ODDDARG`ノードを導入して配列として追跡するロジックも、この新しいループ内で処理されるようになりました。
*   **出力パラメータの処理**: `PPARAMOUT`ノードは、関数の戻り値を表し、`nE.Escretval`（エスケープ解析の戻り値リスト）に追加されます。

この変更により、エスケープ解析は`OTFUNC`の残存情報に依存することなく、関数宣言から直接情報を取得するため、より堅牢で正確な解析が可能になります。

### `OTFUNC`情報のクリア (`typecheck.go`)

`typecheck.go`ファイルでは、`OTFUNC`ノードが`OTYPE`に変換される際に、`OTFUNC`に関連する情報（`n.Left`, `n.List`, `n.Rlist`）を明示的に`nil`に設定する変更が加えられました。

これは、エスケープ解析が`OTFUNC`の残存情報を参照しないように修正された後でも、他のコンパイラパスが誤ってこれらの無効な情報を参照するのを防ぐための「防御的プログラミング」の一環です。これにより、`OTFUNC`が完全に廃止されるまでの間、コンパイラの内部状態の一貫性が保たれます。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/esc.go` の変更点

このファイルはエスケープ解析のロジックを実装しています。変更の核心は、関数呼び出しの引数と戻り値のエスケープ挙動を追跡する方法の変更です。

1.  **`OTFUNC`関連スライスの参照削除**:
    変更前は、`fn.Name.Param.Ntype.Rlist.Slice()`（戻り値リスト）や`fn.Name.Param.Ntype.List.Slice()`（引数リスト）といった`OTFUNC`ノードの内部構造に依存していました。これらは削除され、代わりに`fn.Name.Defn.Func.Dcl`（関数宣言リスト）を直接参照するようになりました。

2.  **`DclLoop`の導入と`Func.Dcl`の利用**:
    新しい`DclLoop`が導入され、`fn.Name.Defn.Func.Dcl`内の各宣言ノード（`n2`）をイテレートします。
    *   `n2.Class == PPARAM`の場合（入力パラメータ）：
        *   レシーバ（`n.Op != OCALLFUNC`かつ`!sawRcvr`）の処理が、`fn.Name.Defn.Func.Dcl`から取得した`n2`ノードを使って行われます。
        *   通常の引数（`lls`スライスから取得）と`n2`（パラメータ宣言）の間で`escassignNilWhy`が呼び出され、エスケープ解析が行われます。
        *   可変長引数（`n2.Isddd`）の場合、`ODDDARG`ノードが作成され、残りの引数が配列として追跡されます。
    *   `n2.Class == PPARAMOUT`の場合（出力パラメータ）：
        *   `nE.Escretval.Append(n2)`により、戻り値のエスケープ解析リストに直接`n2`（戻り値宣言）が追加されます。

3.  **可変長引数の処理の簡素化**:
    変更前は、`i`というインデックス変数を使って`lls`と`lrs`（古い引数/戻り値スライス）を同時に処理していましたが、新しいコードでは`DclLoop`内で`fn.Name.Defn.Func.Dcl`を処理し、残りの`lls`（呼び出し元の引数）は別のループで「追跡されない引数」として処理されます。これにより、可変長引数の処理がより明確になりました。

これらの変更により、エスケープ解析は`OTFUNC`ノードの過渡的な情報に依存せず、コンパイラのより安定した内部表現である関数宣言から直接情報を取得するようになり、堅牢性が向上しました。

### `src/cmd/compile/internal/gc/typecheck.go` の変更点

このファイルは型チェックのロジックを実装しています。変更は非常にシンプルですが、重要です。

1.  **`OTFUNC`ノード情報のクリア**:
    `OpSwitch`の`OTFUNC`ケース内で、`n.Left = nil`、`n.List.Set(nil)`、`n.Rlist.Set(nil)`という3行が追加されました。
    これは、`OTFUNC`ノードが`OTYPE`に変換された後、そのノードが保持していた`Left`、`List`、`Rlist`といったフィールドを明示的に`nil`に設定することで、これらの情報がコンパイラの他の部分から誤って参照されることを防ぎます。これにより、`OTFUNC`の廃止に向けたクリーンアップが促進されます。

これらの変更は、Goコンパイラの内部構造を簡素化し、`OTFUNC`という不要な概念を段階的に排除するための重要なステップです。エスケープ解析の正確性を向上させるとともに、コンパイラの保守性を高める効果があります。

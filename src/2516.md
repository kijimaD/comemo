## 変更の背景

このコミットは、Go言語のARMアーキテクチャ向けコンパイラである`5g`における、オブジェクトファイル生成とレジスタ割り当て（regalloc）に関する修正を目的としています。当時のGoコンパイラは、Plan 9のツールチェインをベースにしており、`5g`はそのARM版コンパイラ（アセンブラ）でした。

変更の背景には、以下の課題があったと推測されます。

1.  **ARM固有のレジスタ割り当ての最適化と正確性**: ARMアーキテクチャは、x86とは異なるレジスタセットと命令セットを持っています。Goコンパイラが生成するコードの効率性と正確性を向上させるためには、ARMの特性に合わせたレジスタ割り当て戦略が必要でした。特に、浮動小数点レジスタと汎用レジスタの管理が重要になります。
2.  **オブジェクトファイルフォーマットの整合性**: コンパイラが生成するオブジェクトファイルは、リンカが正しく解釈できる形式である必要があります。`gobj.c`の変更は、オブジェクトファイル内のアドレス情報やレジスタ情報のエンコーディングに関する修正を示唆しており、これはリンカとの互換性やデバッグ情報の正確性に関わる問題であった可能性があります。
3.  **コード生成ロジックの改善**: `ggen.c`や`gsubr.c`の変更は、特定の操作（例: `OADD`, `OSUB`, `gmove`）に対するコード生成のロジックを見直し、より効率的または正確なARMアセンブリコードを生成するための調整が行われたことを示しています。特に`gmove`関数の大幅な変更は、異なる型間でのデータ移動（型変換を含む）の処理が不完全であったか、最適化の余地があったことを示唆しています。
4.  **スタックフレーム管理の改善**: `maxstksize`の導入とスタックサイズ計算の変更は、関数のスタックフレームの最大サイズを正確に追跡し、より効率的で安全なスタック管理を実現するためのものでしょう。

これらの修正は、Go言語がARMプラットフォームで安定して動作し、効率的なコードを生成するための基盤を固める上で不可欠なものでした。

## 前提知識の解説

### 1. GoコンパイラとPlan 9ツールチェイン

初期のGoコンパイラは、Rob Pikeらが開発したPlan 9オペレーティングシステムのツールチェイン（`8c`, `6c`, `5c`など）をベースにしていました。
- `5g`: ARMアーキテクチャ向けのGoコンパイラ（アセンブラ）。`g`はGoを意味し、`5`はARMアーキテクチャを指すPlan 9の慣例。
- `5l`: ARMアーキテクチャ向けのGoリンカ。
- `5a`: ARMアーキテクチャ向けのアセンブラ。
これらのツールは、GoソースコードをARMアセンブリに変換し、最終的に実行可能なバイナリを生成する役割を担っていました。

### 2. コンパイラの主要なフェーズ

-   **フロントエンド**: ソースコードを解析し、抽象構文木（AST）などの中間表現に変換します。
-   **バックエンド**: 中間表現をターゲットアーキテクチャの機械語に変換します。このフェーズには、コード生成、レジスタ割り当て、最適化などが含まれます。
-   **コード生成**: 中間表現からターゲットアーキテクチャのアセンブリコードを生成するプロセスです。
-   **レジスタ割り当て (Register Allocation)**: プログラムの実行中に使用される変数を、CPUのレジスタに割り当てるプロセスです。レジスタはメモリよりも高速にアクセスできるため、効率的なレジスタ割り当てはプログラムのパフォーマンスに大きく影響します。
    -   **汎用レジスタ**: 整数演算やアドレス計算に使用されるレジスタ。ARMではR0-R15など。
    -   **浮動小数点レジスタ**: 浮動小数点演算に使用されるレジスタ。ARMではF0-F7など。
-   **オブジェクトファイル**: コンパイラによって生成される中間ファイルで、機械語コード、データ、シンボル情報などが含まれます。リンカによって複数のオブジェクトファイルが結合され、最終的な実行可能ファイルが作成されます。

### 3. ARMアーキテクチャの基本

-   **レジスタ**: ARMプロセッサは、汎用レジスタ（R0-R15）と浮動小数点レジスタ（F0-F7など、FPUの有無による）を持っています。レジスタの利用は、コードのパフォーマンスに直結します。
-   **命令セット**: ARMはロード/ストアアーキテクチャであり、データ操作は主にレジスタ間で行われ、メモリへのアクセスはロード（LDR）およびストア（STR）命令を介して行われます。
-   **スタックフレーム**: 関数呼び出し時に、ローカル変数、引数、戻りアドレスなどを格納するためにスタック上に確保される領域です。

### 4. `gg.h`におけるデータ構造

-   `Addr`構造体: アドレス情報を表現するための構造体。レジスタ、オフセット、シンボルなどの情報を含みます。
-   `Prog`構造体: アセンブリ命令（プログラムカウンタ、オペコード、オペランドなど）を表現するための構造体。

## 技術的詳細

このコミットは、`src/cmd/5g`ディレクトリ内の複数のファイルにわたる広範な変更を含んでおり、ARMアーキテクチャ向けのGoコンパイラのバックエンドにおけるレジスタ割り当て、コード生成、およびオブジェクトファイル生成のロジックを改善しています。

### `src/cmd/5g/gg.h`の変更

-   `Addr`構造体に`char reg;`が追加されました。これは、アドレスがどのレジスタに関連付けられているかを明示的に示すためのものです。
-   `Prog`構造体から`void* reg;`が削除され、`char reg;`と`uchar scond;`が追加されました。`scond`はARM命令の条件コード（例: EQ, NE, LTなど）を格納するために使用されます。`reg`は、命令が使用するレジスタを示すために使われます。
-   レジスタ割り当ての範囲を定義する新しいマクロが導入されました:
    -   `REGALLOC_R0`, `REGALLOC_RMAX`: 汎用レジスタの範囲。
    -   `REGALLOC_F0`, `REGALLOC_FMAX`: 浮動小数点レジスタの範囲。
-   `EXTERN uchar reg[D_NONE];`が`EXTERN uchar reg[REGALLOC_FMAX];`に変更され、レジスタ使用状況を追跡する配列のサイズが浮動小数点レジスタの最大値まで拡張されました。
-   `EXTERN int maxstksize;`が追加され、関数内で使用される最大スタックサイズを追跡するための変数が導入されました。
-   `tempalloc(Node*, Type*)`と`tempfree(Node*)`の関数プロトタイプが追加されました。これらは一時的なスタック領域を割り当て・解放するための新しいメカニズムです。

### `src/cmd/5g/ggen.c`の変更

-   `compile`関数から`ginit()`と`gclean()`の呼び出しが削除されました。これは、レジスタ割り当ての初期化とクリーンアップのロジックが`gsubr.c`内の`regalloc`と`regfree`に統合されたことを示唆しています。
-   関数のスタックフレームサイズ計算ロジックが変更されました。`ptxt->to.offset = rnd(stksize+maxarg, maxround);`が`ptxt->to.offset = rnd(maxstksize+maxarg, maxround);`に変更され、`maxstksize`が使用されるようになりました。これにより、関数実行中に動的に割り当てられる一時変数なども含めた、より正確な最大スタックサイズが考慮されるようになります。
-   `OADD`と`OSUB`に対する特定の最適化（`INC`/`DEC`命令への変換）が削除されました。これは、ARMアーキテクチャの特性や、より汎用的なコード生成ロジックへの移行によるものかもしれません。

### `src/cmd/5g/gobj.c`の変更

-   `zhist`関数（履歴情報の書き込み）で、`Bputc(b, 0); Bputc(b, 0);`が追加されました。これはオブジェクトファイルフォーマットの変更に対応するものです。
-   `zaddr`関数（アドレス情報の書き込み）が大幅に変更されました。
    -   `Addr.type`が`D_STATIC`, `D_EXTERN`, `D_AUTO`, `D_PARAM`の場合、`D_OREG`としてエンコードされ、`a->reg`フィールドが使用されるようになりました。これにより、これらのアドレスタイプがレジスタベースのオフセットとして扱われることが明確になります。
    -   `D_CONST2`という新しいアドレスタイプが追加され、`a->offset2`フィールドがオブジェクトファイルに書き込まれるようになりました。これは、64ビット定数や複合的なアドレス指定に対応するためのものと考えられます。
    -   コメントアウトされていた`D_SCONST`（文字列定数）と`D_FCONST`（浮動小数点定数）の処理が復活し、オブジェクトファイルに正しく書き込まれるようになりました。
-   `dumpfuncs`関数で、`p->scond`と`p->reg`がオブジェクトファイルに書き込まれるようになりました。これは、`Prog`構造体に追加されたこれらのフィールドが、生成される機械語命令の重要な一部であることを示しています。

### `src/cmd/5g/gsubr.c`の変更

-   `ginit()`と`gclean()`関数が削除または大幅にコメントアウトされました。
-   **`regalloc`関数の実装**: 以前はコメントアウトされていた`regalloc`関数が、ARM固有のレジスタ割り当てロジックで実装されました。
    -   整数型（`TINT8`から`TPTR64`）と浮動小数点型（`TFLOAT32`から`TFLOAT80`）に対して、それぞれ汎用レジスタと浮動小数点レジスタを割り当てるロジックが追加されました。
    -   `REGALLOC_R0`から`REGALLOC_RMAX`、`REGALLOC_F0`から`REGALLOC_FMAX`の範囲で空いているレジスタを検索し、割り当てます。
    -   指定された固定レジスタ（`o`）がある場合は、それを優先的に割り当てます。
    -   レジスタが不足した場合はエラーを報告します。
-   **`regfree`関数の実装**: 割り当てられたレジスタを解放するロジックが実装されました。
-   **`tempalloc`と`tempfree`関数の追加**:
    -   `tempalloc`は、一時的なスタック上のメモリを割り当てます。`stksize`を増加させ、`maxstksize`を更新します。
    -   `tempfree`は、割り当てられた一時スタックメモリを解放し、`stksize`を元に戻します。
    -   これらの関数は、レジスタが不足した場合や、一時的なメモリが必要な場合に、スタックを一時的な記憶域として利用するためのものです。
-   **`gmove`関数の大幅な書き換え**:
    -   `gmove`は、異なる型や場所（レジスタ、メモリ、定数）間でデータを移動するための中心的な関数です。このコミットで、そのロジックが全面的に見直されました。
    -   以前はコメントアウトされていた多くの型変換やデータ移動のケースが、具体的なARMアセンブリ命令（`AMOVB`, `AMOVH`, `AMOVW`, `AADD`など）を使用して実装されました。
    -   `CASE(ft, tt)`マクロを使用して、ソース型(`ft`)とターゲット型(`tt`)の組み合わせに応じた移動命令を選択するようになりました。
    -   `ismem`関数が追加され、オペランドがメモリ位置にあるかどうかを判定します。
    -   `rdst`、`hard`、`hardmem`というラベルが導入され、それぞれ「レジスタ宛先が必要な移動」、「中間レジスタが必要な型変換」、「中間メモリが必要な型変換」のケースを処理します。これにより、複雑な型変換やデータ移動がより構造化された方法で処理されるようになりました。
    -   特に、整数型間のコピー、切り詰め、符号拡張、ゼロ拡張に関するロジックが追加されました。
    -   浮動小数点型と整数型間の変換、および浮動小数点型間の変換に関する多くのコメントアウトされたロジックが、まだ実装されていない状態ですが、そのための構造が準備されています。

### `src/cmd/5g/list.c`の変更

-   `Dconv`関数（デバッグ出力用のアドレス変換）が変更されました。
    -   `D_CONST`タイプのアドレス表示が改善され、レジスタが関連付けられている場合は`$N(R%d)`形式で表示されるようになりました。
    -   `D_CONST2`タイプのアドレス表示が追加され、`$offset-offset2`形式で表示されるようになりました。これは、`gobj.c`で導入された`D_CONST2`に対応するものです。

### `src/cmd/5g/gsubr.c`における`regalloc`関数

```c
void
regalloc(Node *n, Type *t, Node *o)
{
	int i, et;

	if(t == T)
		fatal("regalloc: t nil");
	et = simtype[t->etype];

	switch(et) {
	case TINT8:
	case TUINT8:
	case TINT16:
	case TUINT16:
	case TINT32:
	case TUINT32:
	case TINT64:
	case TUINT64:
	case TPTR32:
	case TPTR64:
	case TBOOL:
		if(o != N && o->op == OREGISTER) {
			i = o->val.u.reg;
			if(i >= REGALLOC_R0 && i <= REGALLOC_RMAX)
				goto out;
		}
		for(i=REGALLOC_R0; i<=REGALLOC_RMAX; i++)
			if(reg[i] == 0)
				goto out;

		yyerror("out of fixed registers");
		goto err;

	case TFLOAT32:
	case TFLOAT64:
	case TFLOAT80:
		if(o != N && o->op == OREGISTER) {
			i = o->val.u.reg;
			if(i >= REGALLOC_F0 && i <= REGALLOC_FMAX)
				goto out;
		}
		for(i=REGALLOC_F0; i<=REGALLOC_FMAX; i++)
			if(reg[i] == 0)
				goto out;
		yyerror("out of floating registers");
		goto err;
	}
	yyerror("regalloc: unknown type %T", t);

err:
	nodreg(n, t, 0);
	return;

out:
	reg[i]++;
	nodreg(n, t, i);
}
```

### `src/cmd/5g/gsubr.c`における`gmove`関数の一部

```c
void
gmove(Node *f, Node *t)
{
	int a, ft, tt;
	Type *cvt;
	Node r1, r2, t1, t2, flo, fhi, tlo, thi, con, f0, f1, ax, dx, cx;
	Prog *p1, *p2, *p3;

	if(debug['M'])
		print("gmove %N -> %N\n", f, t);

	ft = simsimtype(f->type);
	tt = simsimtype(t->type);
	cvt = t->type;

	// cannot have two integer memory operands;
	// except 64-bit, which always copies via registers anyway.
	// TODO(kaib): re-enable check
// 	if(isint[ft] && isint[tt] && !is64(f->type) && !is64(t->type) && ismem(f) && ismem(t))
// 		goto hard;

	// convert constant to desired type
	if(f->op == OLITERAL) {
		if(tt == TFLOAT32)
			convconst(&con, types[TFLOAT64], &f->val);
		else
			convconst(&con, t->type, &f->val);
		f = &con;
		ft = simsimtype(con.type);

		// some constants can't move directly to memory.
		if(ismem(t)) {
			// float constants come from memory.
			if(isfloat[tt])
				goto hard;
		}
	}

	// value -> value copy, only one memory operand.
	// figure out the instruction to use.
	// break out of switch for one-instruction gins.
	// goto rdst for "destination must be register".
	// goto hard for "convert to cvt type first".
	// otherwise handle and return.

	switch(CASE(ft, tt)) {
	default:
		goto fatal;

	/*
	 * integer copy and truncate
	 */
	case CASE(TINT8, TINT8):	// same size
	case CASE(TINT8, TUINT8):
	case CASE(TUINT8, TINT8):
	case CASE(TUINT8, TUINT8):
	case CASE(TINT16, TINT8):	// truncate
	case CASE(TUINT16, TINT8):
	case CASE(TINT32, TINT8):
	case CASE(TUINT32, TINT8):
	case CASE(TINT16, TUINT8):
	case CASE(TUINT16, TUINT8):
	case CASE(TINT32, TUINT8):
	case CASE(TUINT32, TUINT8):
		a = AMOVB;
		break;

	case CASE(TINT64, TINT8):	// truncate low word
	case CASE(TUINT64, TINT8):
	case CASE(TINT64, TUINT8):
	case CASE(TUINT64, TUINT8):
		fatal("gmove INT64,INT8 not implemented");
		return;

	case CASE(TINT16, TINT16):	// same size
	case CASE(TINT16, TUINT16):
	case CASE(TUINT16, TINT16):
	case CASE(TUINT16, TUINT16):
	case CASE(TINT32, TINT16):	// truncate
	case CASE(TUINT32, TINT16):
	case CASE(TINT32, TUINT16):
	case CASE(TUINT32, TUINT16):
		a = AMOVH;
		break;
    // ... (further cases for other types)
	}

 	gins(a, f, t);
	return;

rdst:
	// requires register destination
	regalloc(&r1, t->type, t);
	gins(a, f, &r1);
	gmove(&r1, t);
	regfree(&r1);
	return;

hard:
	// requires register intermediate
	regalloc(&r1, cvt, t);
	gmove(f, &r1);
	gmove(&r1, t);
	regfree(&r1);
	return;

hardmem:
	// requires memory intermediate
	tempalloc(&r1, cvt);
	gmove(f, &r1);
	gmove(&r1, t);
	tempfree(&r1);
	return;

fatal:
	// should not happen
	fatal("gmove %N -> %N", f, t);
}
```

void
zaddr(Biobuf *b, Addr *a, int s)
{
	int32 l;
	Ieee e;
	int i;
	char *n;

	switch(a->type) {
	case D_STATIC:
	case D_EXTERN:
	case D_AUTO:
	case D_PARAM:
		Bputc(b, D_OREG);
		Bputc(b, a->reg);
		Bputc(b, s);
		Bputc(b, a->type);
		break;
	default:
		Bputc(b, a->type);
		Bputc(b, a->reg);
		Bputc(b, s);
		Bputc(b, D_NONE);
	}

	switch(a->type) {
	default:
		print("unknown type %d in zaddr\n", a->type);
		fatal("zaddr: unknown type");
	case D_NONE:
	case D_REG:
	case D_FREG:
	case D_PSR:
	case D_FPCR:
	case D_SPR:
	case D_BRANCH:
	case D_EXTERN:
	case D_STATIC:
	case D_AUTO:
	case D_PARAM:
		break;

	case D_CONST2:
		l = a->offset2;
		Bputc(b, l);
		Bputc(b, l>>8);
		Bputc(b, l>>16);
		Bputc(b, l>>24); // fall through
	case D_OREG:
	case D_CONST:
	case D_BRANCH:
	case D_SHIFT:
	case D_STATIC:
	case D_AUTO:
		l = a->offset;
		Bputc(b, l);
		Bputc(b, l>>8);
		Bputc(b, l>>16);
		Bputc(b, l>>24);
		break;

	case D_SCONST:
		n = a->sval;
		for(i=0; i<NSNAME; i++) {
			Bputc(b, *n);
			n++;
		}
		break;

	case D_FCONST:
		ieeedtod(&e, a->dval);
		l = e.l;
		Bputc(b, l);
		Bputc(b, l>>8);
		Bputc(b, l>>16);
		Bputc(b, l>>24);
		l = e.h;
		Bputc(b, l);
		Bputc(b, l>>8);
		Bputc(b, l>>16);
		Bputc(b, l>>24);
		break;
	}
}

## コアとなるコードの解説

### `regalloc`関数

この`regalloc`関数は、Goコンパイラのバックエンドにおいて、プログラムの変数や中間結果をARMプロセッサのレジスタに割り当てるための中心的なロジックを提供します。

-   **型に応じたレジスタ選択**: `simtype[t->etype]`を使用して、割り当てるべきレジスタのタイプ（整数または浮動小数点）を決定します。
-   **固定レジスタの優先**: `o != N && o->op == OREGISTER`の条件で、特定のレジスタ（例えば、関数呼び出し規約で定められた引数レジスタなど）が要求された場合、それを優先的に割り当てようとします。
-   **空きレジスタの探索**: `REGALLOC_R0`から`REGALLOC_RMAX`（汎用レジスタ）または`REGALLOC_F0`から`REGALLOC_FMAX`（浮動小数点レジスタ）の範囲で、`reg`配列（レジスタの使用状況を追跡するカウンタ）が`0`である（つまり空いている）レジスタを探します。
-   **レジスタ不足のハンドリング**: 適切なレジスタが見つからない場合、「out of fixed registers」または「out of floating registers」というエラーを報告し、コンパイルを続行できないことを示します。これは、レジスタが有限リソースであるため、割り当てが失敗する可能性があることを意味します。
-   **レジスタ使用状況の更新**: レジスタが割り当てられると、`reg[i]++`によってそのレジスタの使用カウンタが増加します。これにより、同じレジスタが誤って二重に割り当てられることを防ぎます。
-   **`nodreg`**: 割り当てられたレジスタ情報を`Node`構造体`n`に格納します。

この関数の実装により、GoコンパイラはARMアーキテクチャのレジスタを効率的かつ正確に管理できるようになり、生成されるアセンブリコードの品質が向上します。

### `gmove`関数

`gmove`関数は、コンパイラが生成するアセンブリコードにおいて、異なるデータ型や記憶場所（レジスタ、メモリ、定数）間で値を移動させるための複雑なロジックをカプセル化しています。このコミットでは、特にARMアーキテクチャの特性を考慮した、より堅牢な実装が導入されました。

-   **型変換のハンドリング**: `CASE(ft, tt)`マクロと`switch`文を組み合わせることで、ソースの型(`ft`)とターゲットの型(`tt`)のあらゆる組み合わせに対応し、適切なARM移動命令（`AMOVB`, `AMOVH`, `AMOVW`など）を選択します。これにより、バイト、ハーフワード、ワードといった異なるサイズのデータ移動や、必要に応じた切り詰め（truncate）が正確に行われます。
-   **定数処理の改善**: `OLITERAL`（定数）の場合、ターゲットの型に合わせて定数を変換するロジックが追加されました。特に浮動小数点定数がメモリに直接移動できない場合の`goto hard`のような処理は、ARMの命令セットの制約に対応しています。
-   **中間記憶域の利用**:
    -   `rdst` (`requires register destination`): ターゲットがレジスタである必要があるが、直接移動できない場合に、一時レジスタを介して移動を行います。
    -   `hard` (`requires register intermediate`): 複雑な型変換などで、一時レジスタを介した変換が必要な場合に使用されます。
    -   `hardmem` (`requires memory intermediate`): 一時レジスタだけでは処理できない、より複雑な型変換（例えば、特定の浮動小数点変換など）のために、一時的なスタックメモリを介して移動を行います。これは`tempalloc`と`tempfree`を活用します。
-   **エラーハンドリング**: `fatal`ラベルは、予期せぬ型変換の組み合わせや未実装のケースが発生した場合に、コンパイラが異常終了することを示します。これは、開発初期段階で全てのケースを網羅しきれていないことを示唆しています。

`gmove`のこの新しい実装は、GoコングラムがARM上でより多様なデータ型と操作を正確に処理し、効率的なアセンブリコードを生成するための基盤を強化します。特に、整数型間の変換ロジックが具体的に記述されたことで、コンパイラの機能が大きく前進しました。

### `zaddr`関数

`zaddr`関数は、コンパイラが生成するオブジェクトファイルにアドレス情報を書き込む際のエンコーディングロジックを定義します。このコミットでの変更は、オブジェクトファイルフォーマットの正確性と表現能力の向上を目的としています。

-   **アドレスタイプの正規化**: `D_STATIC`, `D_EXTERN`, `D_AUTO`, `D_PARAM`といった特定のアドレスタイプが、オブジェクトファイル内では`D_OREG`（オフセット付きレジスタ）としてエンコードされるようになりました。これは、これらのシンボルがベースレジスタ（例えばスタックポインタ）からのオフセットとして表現されることを意味し、`a->reg`フィールドがそのベースレジスタを示すために使用されます。
-   **`D_CONST2`の導入**: 新しいアドレスタイプ`D_CONST2`が追加され、`a->offset2`フィールドがオブジェクトファイルに書き込まれるようになりました。これは、64ビット定数や、2つのオフセット値を持つ複雑なアドレス指定をオブジェクトファイルに格納するためのメカニズムを提供します。
-   **文字列定数と浮動小数点定数のサポート**: 以前はコメントアウトされていた`D_SCONST`（文字列定数）と`D_FCONST`（浮動小数点定数）の書き込みロジックが復活しました。これにより、これらの定数もオブジェクトファイルに正しく埋め込まれるようになり、リンカがこれらを適切に処理できるようになります。`ieeedtod`関数は、浮動小数点値をIEEE 754形式のバイト列に変換するために使用されます。

これらの変更により、`5g`コンパイラはよりリッチで正確なアドレス情報をオブジェクトファイルに格納できるようになり、リンカやデバッガとの連携が改善されます。

## 前提知識の解説

### 1. GoコンパイラとPlan 9ツールチェイン

初期のGoコンパイラは、Rob Pikeらが開発したPlan 9オペレーティングシステムのツールチェイン（`8c`, `6c`, `5c`など）をベースにしていました。
-   **`5g`**: ARMアーキテクチャ向けのGoコンパイラ（アセンブラ）。`g`はGoを意味し、`5`はARMアーキテクチャを指すPlan 9の慣例です。GoソースコードをARMアセンブリに変換する役割を担います。
-   **`5l`**: ARMアーキテクチャ向けのGoリンカ。
-   **`5a`**: ARMアーキテクチャ向けのアセンブラ。
これらのツールは連携して、GoソースコードをARMアセンブリに変換し、最終的に実行可能なバイナリを生成する役割を担っていました。

### 2. コンパイラの主要なフェーズ

-   **フロントエンド**: ソースコードを字句解析、構文解析、意味解析し、抽象構文木（AST）などの高レベルな中間表現に変換します。
-   **バックエンド**: 中間表現をターゲットアーキテクチャの機械語に変換します。このフェーズには、以下の重要なステップが含まれます。
    -   **コード生成**: 中間表現からターゲットアーキテクチャのアセンブリコードを生成するプロセスです。この段階で、具体的なCPU命令が選択されます。
    -   **レジスタ割り当て (Register Allocation)**: プログラムの実行中に使用される変数や中間結果を、CPUの高速なレジスタに割り当てるプロセスです。レジスタはメモリよりもはるかに高速にアクセスできるため、効率的なレジスタ割り当てはプログラムのパフォーマンスに大きく影響します。レジスタが不足した場合は、一時的にメモリ（スタック）に退避させる「スピル（spill）」が発生します。
    -   **最適化**: 生成されるコードのサイズや実行速度を改善するための様々な変換（例: 定数畳み込み、デッドコード削除、ループ最適化など）が行われます。
-   **オブジェクトファイル**: コンパイラによって生成される中間ファイルで、機械語コード、データ、シンボル情報、再配置情報などが含まれます。リンカによって複数のオブジェクトファイルが結合され、最終的な実行可能ファイルが作成されます。

### 3. ARMアーキテクチャの基本

-   **レジスタ**: ARMプロセッサは、汎用レジスタ（R0-R15など）と浮動小数点レジスタ（F0-F7など、FPUの有無やバージョンによる）を持っています。レジスタの利用は、コードのパフォーマンスに直結します。R13はスタックポインタ（SP）、R14はリンクレジスタ（LR）、R15はプログラムカウンタ（PC）として特殊な用途に用いられることが多いです。
-   **命令セット**: ARMはロード/ストアアーキテクチャであり、データ操作は主にレジスタ間で行われ、メモリへのアクセスはロード（LDR）およびストア（STR）命令を介して行われます。多くの命令は条件実行（例: `ADDEQ`）をサポートし、命令の最後に`S`サフィックスを付けることで条件フラグを更新できます。
-   **スタックフレーム**: 関数呼び出し時に、ローカル変数、引数、戻りアドレスなどを格納するためにスタック上に確保される領域です。スタックポインタ（SP）がスタックの現在位置を指します。

### 4. `gg.h`における主要なデータ構造

-   **`Node`構造体**: 抽象構文木（AST）のノードや、コンパイラ内部の様々なエンティティ（変数、定数、式など）を表現するための汎用的な構造体です。
-   **`Type`構造体**: Go言語の型システムにおける型情報を表現します（例: `int`, `float64`, `struct`など）。
-   **`Addr`構造体**: アセンブリ命令のオペランドとして使用されるアドレス情報を表現するための構造体です。レジスタ、オフセット、シンボル、アドレスタイプ（例: `D_REG`, `D_OREG`, `D_CONST`）などの情報を含みます。
-   **`Prog`構造体**: 1つのアセンブリ命令（プログラムカウンタ、オペコード、オペランドなど）を表現するための構造体です。`from`と`to`フィールドに`Addr`構造体が含まれ、命令のソースとデスティネーションオペランドを記述します。

### `src/cmd/5g/gsubr.c`の変更

このファイルは、レジスタ割り当てとデータ移動のコアロジックを含むため、最も広範な変更が行われました。

-   **`ginit()`と`gclean()`関数の削除/コメントアウト**: これらの関数は、レジスタ管理の新しいアプローチに置き換えられました。
-   **`regalloc`関数の実装**: 以前はコメントアウトされていた`regalloc`関数が、ARM固有のレジスタ割り当てロジックで完全に実装されました。
    -   **型に応じたレジスタ選択**: 割り当てるべきレジスタのタイプ（整数型には汎用レジスタ、浮動小数点型には浮動小数点レジスタ）を`simtype`に基づいて決定します。
    -   **固定レジスタの優先**: `o`引数で特定のレジスタが要求された場合（例: 関数呼び出し規約で特定の引数が特定のレジスタに置かれる場合）、それを優先的に割り当てようとします。
    -   **空きレジスタの探索**: `REGALLOC_R0`から`REGALLOC_RMAX`（汎用レジスタ）または`REGALLOC_F0`から`REGALLOC_FMAX`（浮動小数点レジスタ）の範囲で、`reg`配列（レジスタの使用状況を追跡するカウンタ）が`0`である（つまり空いている）レジスタを探し、割り当てます。
    -   **レジスタ不足のハンドリング**: 適切なレジスタが見つからない場合、「out of fixed registers」または「out of floating registers」というエラーを報告します。
    -   **レジスタ使用状況の更新**: レジスタが割り当てられると、`reg[i]++`によってそのレジスタの使用カウンタが増加します。
-   **`regfree`関数の実装**: 割り当てられたレジスタを解放するロジックが実装されました。`reg[i]--`によって使用カウンタが減少します。
-   **`tempalloc`と`tempfree`関数の追加**:
    -   `tempalloc`は、一時的なスタック上のメモリを割り当てます。`stksize`を増加させ、`maxstksize`を更新します。これは、レジスタが不足した場合や、一時的なメモリが必要な場合に、スタックを一時的な記憶域として利用するためのものです。
    -   `tempfree`は、割り当てられた一時スタックメモリを解放し、`stksize`を元に戻します。
-   **`gmove`関数の大幅な書き換え**: `gmove`関数は、異なる型や場所（レジスタ、メモリ、定数）間でデータを移動するための中心的な関数であり、そのロジックが全面的に見直されました。
    -   **型変換のハンドリング**: `CASE(ft, tt)`マクロと`switch`文を組み合わせることで、ソースの型(`ft`)とターゲットの型(`tt`)のあらゆる組み合わせに対応し、適切なARM移動命令（`AMOVB`, `AMOVH`, `AMOVW`, `AADD`など）を選択します。これにより、バイト、ハーフワード、ワードといった異なるサイズのデータ移動や、必要に応じた切り詰め（truncate）が正確に行われます。
    -   **定数処理の改善**: `OLITERAL`（定数）の場合、ターゲットの型に合わせて定数を変換するロジックが追加されました。特に浮動小数点定数がメモリに直接移動できない場合の処理は、ARMの命令セットの制約に対応しています。
    -   **中間記憶域の利用**:
        -   `rdst` (`requires register destination`): ターゲットがレジスタである必要があるが、直接移動できない場合に、一時レジスタを介して移動を行います。
        -   `hard` (`requires register intermediate`): 複雑な型変換などで、一時レジスタを介した変換が必要な場合に使用されます。
        -   `hardmem` (`requires memory intermediate`): 一時レジスタだけでは処理できない、より複雑な型変換（例えば、特定の浮動小数点変換など）のために、一時的なスタックメモリを介して移動を行います。これは`tempalloc`と`tempfree`を活用します。
    -   **未実装の型変換**: 浮動小数点型と整数型間の変換、および浮動小数点型間の変換に関する多くのロジックはまだコメントアウトされた状態ですが、そのための構造が準備されています。これは、このコミットがレジスタ割り当てと基本的な整数型移動に焦点を当て、浮動小数点変換は今後の課題として残されていることを示唆しています。

### `src/cmd/5g/list.c`の変更

-   **`Dconv`関数の修正**: `Dconv`関数（デバッグ出力用のアドレス変換）が変更されました。
    -   `D_CONST`タイプのアドレス表示が改善され、レジスタが関連付けられている場合は`$N(R%d)`形式で表示されるようになりました。
    -   `D_CONST2`タイプのアドレス表示が追加され、`$offset-offset2`形式で表示されるようになりました。これは、`gobj.c`で導入された`D_CONST2`に対応するもので、複合的な定数アドレスのデバッグ表示を可能にします。

### `src/cmd/5g/gsubr.c`における`regalloc`関数

```c
void
regalloc(Node *n, Type *t, Node *o)
{
	int i, et;

	if(t == T)
		fatal("regalloc: t nil");
	et = simtype[t->etype];

	switch(et) {
	case TINT8:
	case TUINT8:
	case TINT16:
	case TUINT16:
	case TINT32:
	case TUINT32:
	case TINT64:
	case TUINT64:
	case TPTR32:
	case TPTR64:
	case TBOOL:
		if(o != N && o->op == OREGISTER) {
			i = o->val.u.reg;
			if(i >= REGALLOC_R0 && i <= REGALLOC_RMAX)
				goto out;
		}
		for(i=REGALLOC_R0; i<=REGALLOC_RMAX; i++)
			if(reg[i] == 0)
				goto out;

		yyerror("out of fixed registers");
		goto err;

	case TFLOAT32:
	case TFLOAT64:
	case TFLOAT80:
		if(o != N && o->op == OREGISTER) {
			i = o->val.u.reg;
			if(i >= REGALLOC_F0 && i <= REGALLOC_FMAX)
				goto out;
		}
		for(i=REGALLOC_F0; i<=REGALLOC_FMAX; i++)
			if(reg[i] == 0)
				goto out;
		yyerror("out of floating registers");
		goto err;
	}
	yyerror("regalloc: unknown type %T", t);

err:
	nodreg(n, t, 0);
	return;

out:
	reg[i]++;
	nodreg(n, t, i);
}
```

### `src/cmd/5g/gsubr.c`における`gmove`関数の一部

```c
void
gmove(Node *f, Node *t)
{
	int a, ft, tt;
	Type *cvt;
	Node r1, r2, t1, t2, flo, fhi, tlo, thi, con, f0, f1, ax, dx, cx;
	Prog *p1, *p2, *p3;

	if(debug['M'])
		print("gmove %N -> %N\n", f, t);

	ft = simsimtype(f->type);
	tt = simsimtype(t->type);
	cvt = t->type;

	// cannot have two integer memory operands;
	// except 64-bit, which always copies via registers anyway.
	// TODO(kaib): re-enable check
// 	if(isint[ft] && isint[tt] && !is64(f->type) && !is64(t->type) && ismem(f) && ismem(t))
// 		goto hard;

	// convert constant to desired type
	if(f->op == OLITERAL) {
		if(tt == TFLOAT32)
			convconst(&con, types[TFLOAT64], &f->val);
		else
			convconst(&con, t->type, &f->val);
		f = &con;
		ft = simsimtype(con.type);

		// some constants can't move directly to memory.
		if(ismem(t)) {
			// float constants come from memory.
			if(isfloat[tt])
				goto hard;
		}
	}

	// value -> value copy, only one memory operand.
	// figure out the instruction to use.
	// break out of switch for one-instruction gins.
	// goto rdst for "destination must be register".
	// goto hard for "convert to cvt type first".
	// otherwise handle and return.

	switch(CASE(ft, tt)) {
	default:
		goto fatal;

	/*
	 * integer copy and truncate
	 */
	case CASE(TINT8, TINT8):	// same size
	case CASE(TINT8, TUINT8):
	case CASE(TUINT8, TINT8):
	case CASE(TUINT8, TUINT8):
	case CASE(TINT16, TINT8):	// truncate
	case CASE(TUINT16, TINT8):
	case CASE(TINT32, TINT8):
	case CASE(TUINT32, TINT8):
	case CASE(TINT16, TUINT8):
	case CASE(TUINT16, TUINT8):
	case CASE(TINT32, TUINT8):
	case CASE(TUINT32, TUINT8):
		a = AMOVB;
		break;

	case CASE(TINT64, TINT8):	// truncate low word
	case CASE(TUINT64, TINT8):
	case CASE(TINT64, TUINT8):
	case CASE(TUINT64, TUINT8):
		fatal("gmove INT64,INT8 not implemented");
		return;

	case CASE(TINT16, TINT16):	// same size
	case CASE(TINT16, TUINT16):
	case CASE(TUINT16, TINT16):
	case CASE(TUINT16, TUINT16):
	case CASE(TINT32, TINT16):	// truncate
	case CASE(TUINT32, TINT16):
	case CASE(TINT32, TUINT16):
	case CASE(TUINT32, TUINT16):
		a = AMOVH;
		break;
    // ... (further cases for other types)
	}

 	gins(a, f, t);
	return;

rdst:
	// requires register destination
	regalloc(&r1, t->type, t);
	gins(a, f, &r1);
	gmove(&r1, t);
	regfree(&r1);
	return;

hard:
	// requires register intermediate
	regalloc(&r1, cvt, t);
	gmove(f, &r1);
	gmove(&r1, t);
	regfree(&r1);
	return;

hardmem:
	// requires memory intermediate
	tempalloc(&r1, cvt);
	gmove(f, &r1);
	gmove(&r1, t);
	tempfree(&r1);
	return;

fatal:
	// should not happen
	fatal("gmove %N -> %N", f, t);
}
```

void
zaddr(Biobuf *b, Addr *a, int s)
{
	int32 l;
	Ieee e;
	int i;
	char *n;

	switch(a->type) {
	case D_STATIC:
	case D_EXTERN:
	case D_AUTO:
	case D_PARAM:
		Bputc(b, D_OREG);
		Bputc(b, a->reg);
		Bputc(b, s);
		Bputc(b, a->type);
		break;
	default:
		Bputc(b, a->type);
		Bputc(b, a->reg);
		Bputc(b, s);
		Bputc(b, D_NONE);
	}

	switch(a->type) {
	default:
		print("unknown type %d in zaddr\n", a->type);
		fatal("zaddr: unknown type");
	case D_NONE:
	case D_REG:
	case D_FREG:
	case D_PSR:
	case D_FPCR:
	case D_SPR:
	case D_BRANCH:
	case D_EXTERN:
	case D_STATIC:
	case D_AUTO:
	case D_PARAM:
		break;

	case D_CONST2:
		l = a->offset2;
		Bputc(b, l);
		Bputc(b, l>>8);
		Bputc(b, l>>16);
		Bputc(b, l>>24); // fall through
	case D_OREG:
	case D_CONST:
	case D_BRANCH:
	case D_SHIFT:
	case D_STATIC:
	case D_AUTO:
		l = a->offset;
		Bputc(b, l);
		Bputc(b, l>>8);
		Bputc(b, l>>16);
		Bputc(b, l>>24);
		break;

	case D_SCONST:
		n = a->sval;
		for(i=0; i<NSNAME; i++) {
			Bputc(b, *n);
			n++;
		}
		break;

	case D_FCONST:
		ieeedtod(&e, a->dval);
		l = e.l;
		Bputc(b, l);
		Bputc(b, l>>8);
		Bputc(b, l>>16);
		Bputc(b, l>>24);
		l = e.h;
		Bputc(b, l);
		Bputc(b, l>>8);
		Bputc(b, l>>16);
		Bputc(b, l>>24);
		break;
	}
}

## コアとなるコードの解説

### `regalloc`関数

`regalloc`関数は、Goコンパイラのバックエンドにおいて、プログラムの変数や中間結果をARMプロセッサのレジスタに割り当てるための中心的なロジックを提供します。この関数は、コンパイラが生成するアセンブリコードの効率性と正確性を直接左右する重要な部分です。

-   **型に応じたレジスタ選択**: `simtype[t->etype]`を使用して、割り当てるべきレジスタのタイプ（整数型には汎用レジスタ、浮動小数点型には浮動小数点レジスタ）を決定します。ARMアーキテクチャでは、これらのレジスタセットが明確に分離されているため、適切なレジスタタイプを選択することが不可欠です。
-   **固定レジスタの優先**: `o != N && o->op == OREGISTER`の条件は、特定のレジスタ（例えば、関数呼び出し規約で定められた引数レジスタや、特定の命令が要求するレジスタなど）が要求された場合に、それを優先的に割り当てようとします。これにより、特定の最適化やABI（Application Binary Interface）への準拠が可能になります。
-   **空きレジスタの探索**: `REGALLOC_R0`から`REGALLOC_RMAX`（汎用レジスタ）または`REGALLOC_F0`から`REGALLOC_FMAX`（浮動小数点レジスタ）の範囲で、`reg`配列（レジスタの使用状況を追跡するカウンタ）が`0`である（つまり空いている）レジスタを探します。この`reg`配列は、各レジスタが現在いくつの値によって使用されているかを追跡し、二重割り当てを防ぎます。
-   **レジスタ不足のハンドリング**: 適切なレジスタが見つからない場合、「out of fixed registers」または「out of floating registers」というエラーを報告し、コンパイルを続行できないことを示します。これは、レジスタが有限リソースであるため、割り当てが失敗する可能性があることを意味し、コンパイラ設計における重要な考慮事項です。
-   **レジスタ使用状況の更新**: レジスタが割り当てられると、`reg[i]++`によってそのレジスタの使用カウンタが増加します。これにより、同じレジスタが誤って二重に割り当てられることを防ぎ、レジスタのライフタイム管理を支援します。
-   **`nodreg`**: 割り当てられたレジスタ情報を`Node`構造体`n`に格納します。この`Node`は、後続のコード生成フェーズで、この値がどのレジスタに存在するかを示すために使用されます。

この関数の実装により、GoコンパイラはARMアーキテクチャのレジスタを効率的かつ正確に管理できるようになり、生成されるアセンブリコードの品質と実行効率が向上します。

### `gmove`関数

`gmove`関数は、コンパイラが生成するアセンブリコードにおいて、異なるデータ型や記憶場所（レジスタ、メモリ、定数）間で値を移動させるための複雑なロジックをカプセル化しています。このコミットで導入された大幅な書き換えは、特にARMアーキテクチャの特性とGoの型システムを考慮した、より堅牢で正確なデータ移動処理を実現します。

-   **型変換のハンドリング**: `CASE(ft, tt)`マクロと`switch`文を組み合わせることで、ソースの型(`ft`)とターゲットの型(`tt`)のあらゆる組み合わせに対応し、適切なARM移動命令（`AMOVB` (バイト移動), `AMOVH` (ハーフワード移動), `AMOVW` (ワード移動), `AADD` (加算) など）を選択します。これにより、バイト、ハーフワード、ワードといった異なるサイズのデータ移動や、必要に応じた切り詰め（truncate）、符号拡張、ゼロ拡張が正確に行われます。これは、Goの厳密な型システムと、ARMの多様なデータサイズを扱う命令セットとの間の橋渡しをします。
-   **定数処理の改善**: `OLITERAL`（定数）の場合、ターゲットの型に合わせて定数を変換するロジックが追加されました。特に浮動小数点定数がメモリに直接移動できない場合の`goto hard`のような処理は、ARMの命令セットの制約に対応しており、定数をレジスタやメモリにロードする際の適切な戦略を決定します。
-   **中間記憶域の利用**: `gmove`は、直接的な移動が不可能な場合に、一時的な記憶域を賢く利用します。
    -   `rdst` (`requires register destination`): ターゲットがレジスタである必要があるが、ソースがメモリであるなど、直接移動できない場合に、一時レジスタを介して移動を行います。
    -   `hard` (`requires register intermediate`): 複雑な型変換などで、一時レジスタを介した変換が必要な場合に使用されます。例えば、符号拡張やゼロ拡張を伴う型変換などです。
    -   `hardmem` (`requires memory intermediate`): 一時レジスタだけでは処理できない、より複雑な型変換（例えば、特定の浮動小数点変換や、レジスタが不足している場合）のために、`tempalloc`と`tempfree`を活用して一時的なスタックメモリを介して移動を行います。これは、レジスタスピルを管理するメカニズムの一部です。
-   **エラーハンドリング**: `fatal`ラベルは、予期せぬ型変換の組み合わせや未実装のケースが発生した場合に、コンパイラが異常終了することを示します。これは、コンパイラ開発の初期段階で全てのケースを網羅しきれていないことを示唆しており、今後の開発で埋められるべきギャップを示しています。

`gmove`のこの新しい実装は、GoコンパイラがARM上でより多様なデータ型と操作を正確に処理し、効率的なアセンブリコードを生成するための基盤を強化します。特に、整数型間の変換ロジックが具体的に記述されたことで、コンパイラの機能が大きく前進しました。

### `zaddr`関数

`zaddr`関数は、コンパイラが生成するオブジェクトファイルにアドレス情報を書き込む際のエンコーディングロジックを定義します。このコミットでの変更は、オブジェクトファイルフォーマットの正確性と表現能力の向上を目的としており、リンカがGoプログラムの構造をより正確に理解できるようにします。

-   **アドレスタイプの正規化**: `D_STATIC`, `D_EXTERN`, `D_AUTO`, `D_PARAM`といった特定のアドレスタイプが、オブジェクトファイル内では`D_OREG`（オフセット付きレジスタ）としてエンコードされるようになりました。これは、これらのシンボルがベースレジスタ（例えばスタックポインタやフレームポインタ）からのオフセットとして表現されることを意味し、`a->reg`フィールドがそのベースレジスタを示すために使用されます。これにより、オブジェクトファイル内のアドレス表現が一貫性を持ち、リンカが再配置処理を容易に行えるようになります。
-   **`D_CONST2`の導入**: 新しいアドレスタイプ`D_CONST2`が追加され、`a->offset2`フィールドがオブジェクトファイルに書き込まれるようになりました。これは、64ビット定数や、2つのオフセット値を持つ複合的なアドレス指定（例えば、ARMのPC相対アドレス指定や、構造体内のフィールドへのアクセスなど）をオブジェクトファイルに格納するためのメカニズムを提供します。
-   **文字列定数と浮動小数点定数のサポートの復活**: 以前はコメントアウトされていた`D_SCONST`（文字列定数）と`D_FCONST`（浮動小数点定数）の処理が復活し、オブジェクトファイルに正しく書き込まれるようになりました。`ieeedtod`関数は、浮動小数点値をIEEE 754形式のバイト列に変換するために使用されます。これにより、これらの定数もリンカが適切に処理できるようになり、データセクションへの埋め込みや参照が可能になります。

これらの変更により、`5g`コンパイラはよりリッチで正確なアドレス情報をオブジェクトファイルに格納できるようになり、リンカやデバッガとの連携が改善され、Goプログラムのコンパイルとリンクのプロセスがより堅牢になります。

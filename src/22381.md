# [インデックス 22381] ファイルの概要

このコミットは、Go言語の標準ライブラリ`image/jpeg`パッケージにおいて、JPEG画像のデコード処理が、クロマサブサンプリングの水平・垂直サンプリングファクタ（`hv`値）が`0x11`（1x1サンプリング）以外の値を持つ場合にも対応できるように拡張するものです。これにより、より多様なJPEGファイル形式（特に4:2:2や4:1:1などの一般的なサブサンプリング形式）のデコードが可能になり、ライブラリの堅牢性と互換性が向上しました。

## 変更の背景

JPEG画像は、その圧縮効率の高さから広く利用されています。JPEG圧縮の重要な要素の一つに「クロマサブサンプリング」があります。これは、人間の視覚が輝度（明るさ）の変化には敏感である一方で、色差（色相や彩度）の変化には比較的鈍感であるという特性を利用し、色情報を間引くことでデータ量を削減する技術です。

Go言語の`image/jpeg`パッケージは、JPEG画像を扱うための標準ライブラリですが、このコミット以前は、クロマサブサンプリングの`hv`値（水平・垂直サンプリングファクタ）が特定のパターン（特に`0x11`、すなわちすべてのコンポーネントが1x1サンプリングされる4:4:4形式）に限定されていました。しかし、実際のJPEGファイルでは、4:2:2、4:2:0、4:1:1など、さまざまなクロマサブサンプリング形式が広く使われています。

この制限により、`image/jpeg`パッケージは、`0x11`以外の`hv`値を持つJPEGファイルを正しくデコードできないという問題がありました。これは、Go言語で開発されたアプリケーションが、より多様なJPEG画像を扱う際に互換性の問題を引き起こす可能性がありました。

このコミットは、この互換性の問題を解決し、`image/jpeg`パッケージがより広範なJPEGサブサンプリング形式をサポートできるようにするために行われました。これにより、Goの画像処理能力が向上し、より多くのJPEGファイルを適切に処理できるようになります。コミットメッセージにあるテストデータの生成方法からもわかるように、`2x2,1x2,1x2`というサンプリングオプション（これはYが2x2、CbとCrが1x2のサンプリング、つまり4:2:2に近い形式を示唆しています）を持つJPEGファイルを生成し、それを正しくデコードできることを確認しています。

## 前提知識の解説

### JPEG形式の基礎

JPEG (Joint Photographic Experts Group) は、主に写真などの連続階調画像を圧縮するための標準的な画像形式です。非可逆圧縮方式であり、画質とファイルサイズのバランスを調整できます。

JPEG圧縮の主要なステップは以下の通りです。

1.  **色空間変換 (Color Space Conversion)**: 通常、RGB形式の画像は、輝度（Y）と2つの色差（Cb, Cr）を表すYCbCr色空間に変換されます。人間の視覚は輝度情報に敏感で、色差情報には比較的鈍感であるため、この変換が重要になります。
2.  **クロマサブサンプリング (Chroma Subsampling)**: YCbCr色空間に変換された後、色差情報（Cb, Cr）は、人間の視覚特性を利用して間引かれます。これがこのコミットの核心に関わる部分です。
3.  **離散コサイン変換 (Discrete Cosine Transform, DCT)**: 画像は8x8ピクセルのブロックに分割され、各ブロックに対してDCTが適用されます。これにより、空間領域のピクセルデータが周波数領域の係数に変換されます。
4.  **量子化 (Quantization)**: DCT係数は、人間の視覚が認識しにくい高周波成分を捨てるために量子化されます。これにより、非可逆圧縮が行われ、データ量が大幅に削減されます。量子化の度合いは画質に影響します。
5.  **エントロピー符号化 (Entropy Encoding)**: 量子化された係数は、ハフマン符号化や算術符号化などのエントロピー符号化によってさらに圧縮されます。

### YCbCr色空間

YCbCrは、輝度（Y）と2つの色差（Cb: 青色成分と輝度の差、Cr: 赤色成分と輝度の差）で色を表現する色空間です。RGB色空間とは異なり、輝度と色情報を分離して扱うため、色情報を間引くクロマサブサンプリングが容易になります。

### クロマサブサンプリング (Chroma Subsampling)

クロマサブサンプリングは、色差情報（Cb, Cr）の解像度を輝度情報（Y）の解像度よりも低くすることで、ファイルサイズを削減する技術です。これは、人間の目が輝度の変化には敏感ですが、色の変化にはそれほど敏感ではないという生理学的特性に基づいています。

一般的なクロマサブサンプリングの形式には以下のようなものがあります。

*   **4:4:4**: サブサンプリングなし。Y, Cb, Crのすべてのコンポーネントが同じ解像度を持ちます。最も高品質ですが、圧縮率は低いです。
*   **4:2:2**: 水平方向に色差情報を半分に間引きます。輝度情報が4ピクセルごとに、色差情報が2ピクセルごとにサンプリングされます。
*   **4:2:0**: 水平方向と垂直方向の両方で色差情報を半分に間引きます。輝度情報が4ピクセルごとに、色差情報が1ピクセルごとにサンプリングされます。最も一般的な形式の一つで、Web画像などで広く使われます。
*   **4:1:1**: 水平方向に色差情報を4分の1に間引きます。
*   **4:1:0**: 水平方向に色差情報を4分の1に、垂直方向に色差情報を半分に間引きます。

JPEGのSOF (Start Of Frame) マーカーセグメントには、各コンポーネントのサンプリングファクタが格納されます。これは通常、1バイトの`hv`値として表現され、上位4ビットが水平サンプリングファクタ（h）、下位4ビットが垂直サンプリングファクタ（v）を示します。例えば、`0x11`はh=1, v=1を意味し、これは4:4:4サブサンプリングのコンポーネント（通常はY, Cb, Cr全て）に適用されます。

### Go言語の`image/jpeg`パッケージ

Go言語の標準ライブラリには、`image`パッケージとそのサブパッケージとして`image/jpeg`があります。`image`パッケージは、Goで画像を扱うための基本的なインターフェースとデータ構造を提供し、`image/jpeg`はJPEG形式のエンコードとデコード機能を提供します。

このパッケージは、JPEGファイルの構造を解析し、DCT係数をデコードし、逆量子化と逆DCTを実行してピクセルデータを再構築します。クロマサブサンプリングされた画像の場合、色差情報をアップサンプリングして、輝度情報と結合し、最終的なRGB画像（またはYCbCr画像）を生成します。

## 技術的詳細

このコミットの技術的な変更は、主に`src/image/jpeg/reader.go`と`src/image/jpeg/scan.go`の2つのファイルに集中しています。これらの変更は、JPEGのSOF (Start Of Frame) マーカーから読み取られる各コンポーネントのサンプリングファクタ（`hv`値）の解釈と処理を汎用化し、`0x11`以外の値も適切に扱えるようにすることを目的としています。

### `src/image/jpeg/reader.go`の変更点

このファイルは、JPEGファイルのヘッダ情報やマーカーを読み取り、デコード処理の初期設定を行う役割を担っています。

*   **エラー定義の追加**:
    `var errUnsupportedSubsamplingRatio = UnsupportedError("luma/chroma subsampling ratio")`
    新しいエラータイプ`errUnsupportedSubsamplingRatio`が追加されました。これは、サポートされていない輝度/クロマサブサンプリング比率が検出された場合に返されます。

*   **`processSOF`関数の変更**:
    `processSOF`関数は、SOFマーカーセグメントを解析し、画像の幅、高さ、コンポーネント数、そして各コンポーネントのサンプリングファクタ（`h`と`v`）を読み取ります。

    *   **`hv`値の厳密なチェック**:
        以前は、`hv`値が`0x11`（h=1, v=1）に限定されるようなチェックがありましたが、このコミットではより汎用的なチェックが導入されました。
        ```go
        hv := d.tmp[7+3*i]
        h, v := int(hv>>4), int(hv&0x0f)
        if h < 1 || 4 < h || v < 1 || 4 < v {
            return FormatError("luma/chroma subsampling ratio")
        }
        if h == 3 || v == 3 {
            return errUnsupportedSubsamplingRatio
        }
        ```
        ここでは、`h`と`v`がそれぞれ1から4の範囲内にあることを確認しています。また、`h`または`v`が`3`である場合は、`errUnsupportedSubsamplingRatio`を返してサポートしないことを明示しています。これは、JPEGの一般的なサブサンプリングスキームでは`h=3`や`v=3`が使われることが稀であるため、実装の複雑さを避けるための判断と考えられます。

    *   **単一コンポーネント画像（グレースケール）の処理**:
        単一コンポーネントの画像（グレースケール）の場合、セクションA.2の規定により、常に非インターリーブであり、`h`と`v`は実質的に常に`1, 1`として扱われるべきであるというロジックが追加されました。
        ```go
        case 1:
            // ... (コメント省略) ...
            h, v = 1, 1
        ```

    *   **3コンポーネント画像（YCbCr）のサンプリング比率検証の強化**:
        YCbCr画像の場合、Y、Cb、Crコンポーネントのサンプリング比率に関するより詳細な検証ロジックが導入されました。
        ```go
        case 3:
            // ... (コメント省略) ...
            switch i {
            case 0: // Y.
                // ... (コメント省略) ...
                if v == 4 {
                    return errUnsupportedSubsamplingRatio
                }
            case 1: // Cb.
                if d.comp[0].h%h != 0 || d.comp[0].v%v != 0 {
                    return errUnsupportedSubsamplingRatio
                }
            case 2: // Cr.
                if d.comp[1].h != h || d.comp[1].v != v {
                    return errUnsupportedSubsamplingRatio
                }
            }
        ```
        Yコンポーネント（`i=0`）では、垂直サンプリングファクタ`v`が`4`である場合はサポートしないという制約が追加されました（例: 4:4:4, 4:2:2, 4:2:0, 4:1:1, 4:1:0はサポートするが、4:4:0や4:2:0でYのvが4になるケースは稀）。
        Cbコンポーネント（`i=1`）では、Yコンポーネントの水平・垂直サンプリングファクタが、Cbコンポーネントのそれらの倍数である必要があるというチェックが追加されました。これは、YCbCrサブサンプリングの定義上、輝度コンポーネントのサンプリングが色差コンポーネントのサンプリングの整数倍である必要があるためです。
        Crコンポーネント（`i=2`）では、Cbコンポーネントと同じサンプリング比率を持つ必要があるというチェックが追加されました。これは、通常、2つの色差コンポーネントは同じサブサンプリング比率を持つという仮定に基づいています。

    *   **4コンポーネント画像（CMYK/YCbCrK）のサンプリング比率検証の強化**:
        4コンポーネント画像の場合も、特定の`hv`ベクトルの組み合わせ（`[0x11 0x11 0x11 0x11]`または`[0x22 0x11 0x11 0x22]`）のみをサポートするというロジックがより明確に記述されました。
        ```go
        case 4:
            // ... (コメント省略) ...
            switch i {
            case 0:
                if hv != 0x11 && hv != 0x22 {
                    return errUnsupportedSubsamplingRatio
                }
            case 1, 2:
                if hv != 0x11 {
                    return errUnsupportedSubsamplingRatio
                }
            case 3:
                if d.comp[0].h != h || d.comp[0].v != v {
                    return errUnsupportedSubsamplingRatio
                }
            }
        ```
        これは、CMYKやYCbCrKのような4コンポーネント画像では、特定のサンプリングパターンが一般的であるためです。

    *   **コンポーネントの`h`と`v`の更新**:
        最後に、各コンポーネントの`h`と`v`が、読み取られた`hv`値から正しく設定されるようになりました。
        ```go
        d.comp[i].h = h
        d.comp[i].v = v
        ```

### `src/image/jpeg/scan.go`の変更点

このファイルは、JPEGの走査（スキャン）処理、つまりDCT係数からピクセルデータを再構築する部分を扱います。

*   **`makeImg`関数の変更**:
    `makeImg`関数は、デコードされた画像を格納するための`image.YCbCr`構造体（または`image.Gray`）を割り当て、初期化します。
    *   関数のシグネチャが変更され、`h0`, `v0`パラメータが削除されました。これらの値は、デコーダのコンポーネント情報から直接取得されるようになりました。
    ```go
    // func (d *decoder) makeImg(h0, v0, mxx, myy int) { // 変更前
    func (d *decoder) makeImg(mxx, myy int) { // 変更後
    ```
    *   `h0`と`v0`は、`d.comp[0].h`と`d.comp[0].v`（通常は輝度コンポーネントYのサンプリングファクタ）から取得されるようになりました。
    ```go
    h0 := d.comp[0].h
    v0 := d.comp[0].v
    ```
    *   `hRatio`と`vRatio`が、輝度コンポーネントと色差コンポーネントのサンプリング比率に基づいて計算されるようになりました。
    ```go
    hRatio := h0 / d.comp[1].h
    vRatio := v0 / d.comp[1].v
    ```
    *   `image.YCbCrSubsampleRatio`の決定ロジックが、`hRatio<<4 | vRatio`というビット演算を使ってより汎用的に変更されました。これにより、`0x11`, `0x12`, `0x21`, `0x22`, `0x41`, `0x42`といった様々なサブサンプリング比率に対応できるようになりました。
    ```go
    switch hRatio<<4 | vRatio {
    case 0x11:
        subsampleRatio = image.YCbCrSubsampleRatio444
    case 0x12:
        subsampleRatio = image.YCbCrSubsampleRatio440
    case 0x21:
        subsampleRatio = image.YCbCrSubsampleRatio422
    case 0x22:
        subsampleRatio = image.YCbCrSubsampleRatio420
    case 0x41:
        subsampleRatio = image.YCbCrSubsampleRatio411
    case 0x42:
        subsampleRatio = image.YCbCrSubsampleRatio410
    default:
        panic("unreachable")
    }
    ```

*   **`processSOS`関数の変更**:
    `processSOS`関数は、SOSマーカーセグメントを解析し、実際のDCT係数のデコードと逆量子化、逆DCTを実行してピクセルデータを生成します。
    *   `makeImg`の呼び出しが、新しいシグネチャに合わせて変更されました。
    ```go
    // d.makeImg(h0, v0, mxx, myy) // 変更前
    d.makeImg(mxx, myy) // 変更後
    ```
    *   ブロック処理ループ内で、各コンポーネントの`h`と`v`値が、`d.comp[compIndex].h`と`d.comp[compIndex].v`から直接取得されるようになりました。これにより、各コンポーネントの実際のサンプリングファクタに基づいてブロックの計算が行われるようになります。
    ```go
    hi := d.comp[compIndex].h
    vi := d.comp[compIndex].v
    // ...
    for j := 0; j < hi*vi; j++ { // 以前は d.comp[compIndex].h*d.comp[compIndex].v
    // ...

    by = vi*my + j/hi // 以前は d.comp[compIndex].v*my + j/h0

    // ...
    b = d.progCoeffs[compIndex][by*mxx*hi+bx] // 以前は by*mxx*d.comp[compIndex].h+bx
    // ...
    d.progCoeffs[compIndex][by*mxx*hi+bx] = b // 以前は by*mxx*d.comp[compIndex].h+bx
    ```
    これらの変更により、デコード処理が各コンポーネントの実際のサンプリングファクタに動的に適応できるようになり、`0x11`以外の`hv`値を持つJPEG画像も正しく処理できるようになりました。

## コアとなるコードの解説

### `src/image/jpeg/reader.go`の変更点

このファイルでは、JPEGヘッダの解析、特にSOF (Start Of Frame) マーカーの処理ロジックが大幅に強化されています。

*   **`errUnsupportedSubsamplingRatio`の導入**:
    `UnsupportedError`型を基にした新しいエラー変数が定義されました。これにより、サポートされていないサブサンプリング比率が検出された際に、より具体的なエラーを返すことができます。

*   **`processSOF`関数内の`hv`値の処理**:
    以前は、各コンポーネントの`hv`値（水平・垂直サンプリングファクタ）を直接`d.comp[i].h`と`d.comp[i].v`に代入していました。しかし、この変更では、まず`hv`値から`h`と`v`を抽出し、それらの値が有効な範囲（1から4）にあるか、また`3`ではないか（`h=3`や`v=3`は一般的ではないためサポート外とする）を厳密にチェックしています。これにより、不正な`hv`値を持つJPEGファイルに対する堅牢性が向上します。

*   **コンポーネント数に応じたサンプリング比率の検証**:
    `switch d.nComp`ブロックが導入され、画像のコンポーネント数（1, 3, 4）に応じて、より詳細なサンプリング比率の検証が行われるようになりました。
    *   **単一コンポーネント（グレースケール）**: `h`と`v`は常に`1, 1`として扱われます。これはJPEGの仕様に基づいています。
    *   **3コンポーネント（YCbCr）**: Y、Cb、Crの各コンポーネントに対して、その役割に応じたサンプリング比率の制約が適用されます。特に、Yコンポーネントの`v`が`4`である場合はサポートされません。また、CbとCrコンポーネントのサンプリングファクタがYコンポーネントのサンプリングファクタの倍数であること、およびCbとCrが同じサンプリング比率を持つことが検証されます。これにより、一般的なYCbCrサブサンプリング形式（4:4:4, 4:2:2, 4:2:0など）の正確なデコードが保証されます。
    *   **4コンポーネント（CMYK/YCbCrK）**: 特定の`hv`ベクトルの組み合わせ（`[0x11 0x11 0x11 0x11]`または`[0x22 0x11 0x11 0x22]`）のみがサポートされます。これは、これらの形式で一般的なサンプリングパターンに限定することで、実装の複雑さを管理するためです。

*   **最終的な`h`と`v`の代入**:
    これらの検証の後、抽出された`h`と`v`の値が`d.comp[i].h`と`d.comp[i].v`に代入されます。これにより、デコーダは各コンポーネントの正しいサンプリングファクタを認識し、後続のデコード処理で利用できるようになります。

### `src/image/jpeg/scan.go`の変更点

このファイルでは、デコードされた画像データのメモリ割り当てと、DCTブロックの走査ロジックが更新されています。

*   **`makeImg`関数のシグネチャ変更と`YCbCrSubsampleRatio`の決定**:
    `makeImg`関数から`h0`, `v0`パラメータが削除され、これらの値はデコーダのコンポーネント情報（`d.comp[0].h`, `d.comp[0].v`）から直接取得されるようになりました。
    最も重要な変更は、`image.YCbCrSubsampleRatio`を決定する`switch`文です。以前は`h0`と`v0`の直接比較に基づいていましたが、新しいコードでは`hRatio<<4 | vRatio`というビット演算を使用しています。ここで`hRatio`と`vRatio`は、輝度コンポーネント（Y）と色差コンポーネント（Cb/Cr）のサンプリング比率から計算されます。このビット演算により、`0x11`（4:4:4）、`0x12`（4:4:0）、`0x21`（4:2:2）、`0x22`（4:2:0）、`0x41`（4:1:1）、`0x42`（4:1:0）といった、より多様なサブサンプリング比率を簡潔かつ正確にマッピングできるようになりました。これにより、`image.YCbCr`構造体の初期化時に正しいサブサンプリング比率が設定され、後続のアップサンプリング処理が適切に行われるようになります。

*   **`processSOS`関数内のブロック処理ロジックの更新**:
    `processSOS`関数内のDCTブロックを走査するループにおいて、各コンポーネントの水平・垂直サンプリングファクタ（`hi`, `vi`）が、`d.comp[compIndex].h`と`d.comp[compIndex].v`から動的に取得されるようになりました。これにより、ブロックのインデックス計算（`bx`, `by`）や、プログレッシブJPEGの係数保存ロジック（`d.progCoeffs`へのアクセス）が、各コンポーネントの実際のサンプリングファクタに基づいて行われるようになります。この変更は、`0x11`以外の`hv`値を持つJPEG画像でも、ブロックの配置と処理が正しく行われることを保証します。

これらのコード変更は、JPEGデコードの根幹部分に手を入れるものであり、Goの`image/jpeg`パッケージが、より広範なJPEGサブサンプリング形式を正確かつ効率的に処理できるようになるための重要な改善です。

## 変更の背景

JPEG画像は、その圧縮効率の高さから広く利用されています。JPEG圧縮の重要な要素の一つに「クロマサブサンプリング」があります。これは、人間の視覚が輝度（明るさ）の変化には敏感である一方で、色差（色相や彩度）の変化には比較的鈍感であるという特性を利用し、色情報を間引くことでデータ量を削減する技術です。

Go言語の`image/jpeg`パッケージは、JPEG画像を扱うための標準ライブラリですが、このコミット以前は、クロマサブサンプリングの`hv`値（水平・垂直サンプリングファクタ）が特定のパターン（特に`0x11`、すなわちすべてのコンポーネントが1x1サンプリングされる4:4:4形式）に限定されていました。しかし、実際のJPEGファイルでは、4:2:2、4:2:0、4:1:1など、さまざまなクロマサブサンプリング形式が広く使われています。

この制限により、`image/jpeg`パッケージは、`0x11`以外の`hv`値を持つJPEGファイルを正しくデコードできないという問題がありました。これは、Go言語で開発されたアプリケーションが、より多様なJPEG画像を扱う際に互換性の問題を引き起こす可能性がありました。

このコミットは、この互換性の問題を解決し、`image/jpeg`パッケージがより広範なJPEGサブサンプリング形式をサポートできるようにするために行われました。これにより、Goの画像処理能力が向上し、より多くのJPEGファイルを適切に処理できるようになります。コミットメッセージにあるテストデータの生成方法からもわかるように、`2x2,1x2,1x2`というサンプリングオプション（これはYが2x2、CbとCrが1x2のサンプリング、つまり4:2:2に近い形式を示唆しています）を持つJPEGファイルを生成し、それを正しくデコードできることを確認しています。

## 前提知識の解説

### JPEG形式の基礎

JPEG (Joint Photographic Experts Group) は、主に写真などの連続階調画像を圧縮するための標準的な画像形式です。非可逆圧縮方式であり、画質とファイルサイズのバランスを調整できます。

JPEG圧縮の主要なステップは以下の通りです。

1.  **色空間変換 (Color Space Conversion)**: 通常、RGB形式の画像は、輝度（Y）と2つの色差（Cb, Cr）を表すYCbCr色空間に変換されます。人間の視覚は輝度情報に敏感で、色差情報には比較的鈍感であるため、この変換が重要になります。
2.  **クロマサブサンプリング (Chroma Subsampling)**: YCbCr色空間に変換された後、色差情報（Cb, Cr）は、人間の視覚特性を利用して間引かれます。これがこのコミットの核心に関わる部分です。
3.  **離散コサイン変換 (Discrete Cosine Transform, DCT)**: 画像は8x8ピクセルのブロックに分割され、各ブロックに対してDCTが適用されます。これにより、空間領域のピクセルデータが周波数領域の係数に変換されます。
4.  **量子化 (Quantization)**: DCT係数は、人間の視覚が認識しにくい高周波成分を捨てるために量子化されます。これにより、非可逆圧縮が行われ、データ量が大幅に削減されます。量子化の度合いは画質に影響します。
5.  **エントロピー符号化 (Entropy Encoding)**: 量子化された係数は、ハフマン符号化や算術符号化などのエントロピー符号化によってさらに圧縮されます。

### YCbCr色空間

YCbCrは、輝度（Y）と2つの色差（Cb: 青色成分と輝度の差、Cr: 赤色成分と輝度の差）で色を表現する色空間です。RGB色空間とは異なり、輝度と色情報を分離して扱うため、色情報を間引くクロマサブサンプリングが容易になります。

### クロマサブサンプリング (Chroma Subsampling)

クロマサブサンプリングは、色差情報（Cb, Cr）の解像度を輝度情報（Y）の解像度よりも低くすることで、ファイルサイズを削減する技術です。これは、人間の目が輝度の変化には敏感ですが、色の変化にはそれほど敏感ではないという生理学的特性に基づいています。

一般的なクロマサブサンプリングの形式には以下のようなものがあります。

*   **4:4:4**: サブサンプリングなし。Y, Cb, Crのすべてのコンポーネントが同じ解像度を持ちます。最も高品質ですが、圧縮率は低いです。
*   **4:2:2**: 水平方向に色差情報を半分に間引きます。輝度情報が4ピクセルごとに、色差情報が2ピクセルごとにサンプリングされます。
*   **4:2:0**: 水平方向と垂直方向の両方で色差情報を半分に間引きます。輝度情報が4ピクセルごとに、色差情報が1ピクセルごとにサンプリングされます。最も一般的な形式の一つで、Web画像などで広く使われます。
*   **4:1:1**: 水平方向に色差情報を4分の1に間引きます。
*   **4:1:0**: 水平方向に色差情報を4分の1に、垂直方向に色差情報を半分に間引きます。

JPEGのSOF (Start Of Frame) マーカーセグメントには、各コンポーネントのサンプリングファクタが格納されます。これは通常、1バイトの`hv`値として表現され、上位4ビットが水平サンプリングファクタ（h）、下位4ビットが垂直サンプリングファクタ（v）を示します。例えば、`0x11`はh=1, v=1を意味し、これは4:4:4サブサンプリングのコンポーネント（通常はY, Cb, Cr全て）に適用されます。

### Go言語の`image/jpeg`パッケージ

Go言語の標準ライブラリには、`image`パッケージとそのサブパッケージとして`image/jpeg`があります。`image`パッケージは、Goで画像を扱うための基本的なインターフェースとデータ構造を提供し、`image/jpeg`はJPEG形式のエンコードとデコード機能を提供します。

このパッケージは、JPEGファイルの構造を解析し、DCT係数をデコードし、逆量子化と逆DCTを実行してピクセルデータを再構築します。クロマサブサンプリングされた画像の場合、色差情報をアップサンプリングして、輝度情報と結合し、最終的なRGB画像（またはYCbCr画像）を生成します。

## 技術的詳細

このコミットの技術的な変更は、主に`src/image/jpeg/reader.go`と`src/image/jpeg/scan.go`の2つのファイルに集中しています。これらの変更は、JPEGのSOF (Start Of Frame) マーカーから読み取られる各コンポーネントのサンプリングファクタ（`hv`値）の解釈と処理を汎用化し、`0x11`以外の値も適切に扱えるようにすることを目的としています。

### `src/image/jpeg/reader.go`の変更点

このファイルは、JPEGファイルのヘッダ情報やマーカーを読み取り、デコード処理の初期設定を行う役割を担っています。

*   **エラー定義の追加**:
    `var errUnsupportedSubsamplingRatio = UnsupportedError("luma/chroma subsampling ratio")`
    新しいエラータイプ`errUnsupportedSubsamplingRatio`が追加されました。これは、サポートされていない輝度/クロマサブサンプリング比率が検出された場合に返されます。

*   **`processSOF`関数の変更**:
    `processSOF`関数は、SOFマーカーセグメントを解析し、画像の幅、高さ、コンポーネント数、そして各コンポーネントのサンプリングファクタ（`h`と`v`）を読み取ります。

    *   **`hv`値の厳密なチェック**:
        以前は、`hv`値が`0x11`（h=1, v=1）に限定されるようなチェックがありましたが、このコミットではより汎用的なチェックが導入されました。
        ```go
        hv := d.tmp[7+3*i]
        h, v := int(hv>>4), int(hv&0x0f)
        if h < 1 || 4 < h || v < 1 || 4 < v {
            return FormatError("luma/chroma subsampling ratio")
        }
        if h == 3 || v == 3 {
            return errUnsupportedSubsamplingRatio
        }
        ```
        ここでは、`h`と`v`がそれぞれ1から4の範囲内にあることを確認しています。また、`h`または`v`が`3`である場合は、`errUnsupportedSubsamplingRatio`を返してサポートしないことを明示しています。これは、JPEGの一般的なサブサンプリングスキームでは`h=3`や`v=3`が使われることが稀であるため、実装の複雑さを避けるための判断と考えられます。

    *   **単一コンポーネント画像（グレースケール）の処理**:
        単一コンポーネントの画像（グレースケール）の場合、セクションA.2の規定により、常に非インターリーブであり、`h`と`v`は実質的に常に`1, 1`として扱われるべきであるというロジックが追加されました。
        ```go
        case 1:
            // ... (コメント省略) ...
            h, v = 1, 1
        ```

    *   **3コンポーネント画像（YCbCr）のサンプリング比率検証の強化**:
        YCbCr画像の場合、Y、Cb、Crコンポーネントのサンプリング比率に関するより詳細な検証ロジックが導入されました。
        ```go
        case 3:
            // ... (コメント省略) ...
            switch i {
            case 0: // Y.
                // ... (コメント省略) ...
                if v == 4 {
                    return errUnsupportedSubsamplingRatio
                }
            case 1: // Cb.
                if d.comp[0].h%h != 0 || d.comp[0].v%v != 0 {
                    return errUnsupportedSubsamplingRatio
                }
            case 2: // Cr.
                if d.comp[1].h != h || d.comp[1].v != v {
                    return errUnsupportedSubsamplingRatio
                }
            }
        ```
        Yコンポーネント（`i=0`）では、垂直サンプリングファクタ`v`が`4`である場合はサポートしないという制約が追加されました（例: 4:4:4, 4:2:2, 4:2:0, 4:1:1, 4:1:0はサポートするが、4:4:0や4:2:0でYのvが4になるケースは稀）。
        Cbコンポーネント（`i=1`）では、Yコンポーネントの水平・垂直サンプリングファクタが、Cbコンポーネントのそれらの倍数である必要があるというチェックが追加されました。これは、YCbCrサブサンプリングの定義上、輝度コンポーネントのサンプリングが色差コンポーネントのサンプリングの整数倍である必要があるためです。
        Crコンポーネント（`i=2`）では、Cbコンポーネントと同じサンプリング比率を持つ必要があるというチェックが追加されました。これは、通常、2つの色差コンポーネントは同じサブサンプリング比率を持つという仮定に基づいています。

    *   **4コンポーネント画像（CMYK/YCbCrK）のサンプリング比率検証の強化**:
        4コンポーネント画像の場合も、特定の`hv`ベクトルの組み合わせ（`[0x11 0x11 0x11 0x11]`または`[0x22 0x11 0x11 0x22]`）のみをサポートするというロジックがより明確に記述されました。
        ```go
        case 4:
            // ... (コメント省略) ...
            switch i {
            case 0:
                if hv != 0x11 && hv != 0x22 {
                    return errUnsupportedSubsamplingRatio
                }
            case 1, 2:
                if hv != 0x11 {
                    return errUnsupportedSubsamplingRatio
                }
            case 3:
                if d.comp[0].h != h || d.comp[0].v != v {
                    return errUnsupportedSubsamplingRatio
                }
            }
        ```
        これは、CMYKやYCbCrKのような4コンポーネント画像では、特定のサンプリングパターンが一般的であるためです。

    *   **最終的な`h`と`v`の代入**:
        最後に、各コンポーネントの`h`と`v`が、読み取られた`hv`値から正しく設定されるようになりました。
        ```go
        d.comp[i].h = h
        d.comp[i].v = v
        ```

### `src/image/jpeg/scan.go`の変更点

このファイルは、JPEGの走査（スキャン）処理、つまりDCT係数からピクセルデータを再構築する部分を扱います。

*   **`makeImg`関数のシグネチャ変更と`YCbCrSubsampleRatio`の決定**:
    `makeImg`関数から`h0`, `v0`パラメータが削除され、これらの値はデコーダのコンポーネント情報（`d.comp[0].h`, `d.comp[0].v`）から直接取得されるようになりました。
    最も重要な変更は、`image.YCbCrSubsampleRatio`を決定する`switch`文です。以前は`h0`と`v0`の直接比較に基づいていましたが、新しいコードでは`hRatio<<4 | vRatio`というビット演算を使用しています。ここで`hRatio`と`vRatio`は、輝度コンポーネント（Y）と色差コンポーネント（Cb/Cr）のサンプリング比率から計算されます。このビット演算により、`0x11`（4:4:4）、`0x12`（4:4:0）、`0x21`（4:2:2）、`0x22`（4:2:0）、`0x41`（4:1:1）、`0x42`（4:1:0）といった、より多様なサブサンプリング比率を簡潔かつ正確にマッピングできるようになりました。これにより、`image.YCbCr`構造体の初期化時に正しいサブサンプリング比率が設定され、後続のアップサンプリング処理が適切に行われるようになります。

*   **`processSOS`関数内のブロック処理ロジックの更新**:
    `processSOS`関数内のDCTブロックを走査するループにおいて、各コンポーネントの水平・垂直サンプリングファクタ（`hi`, `vi`）が、`d.comp[compIndex].h`と`d.comp[compIndex].v`から動的に取得されるようになりました。これにより、ブロックのインデックス計算（`bx`, `by`）や、プログレッシブJPEGの係数保存ロジック（`d.progCoeffs`へのアクセス）が、各コンポーネントの実際のサンプリングファクタに基づいて行われるようになります。この変更は、`0x11`以外の`hv`値を持つJPEG画像でも、ブロックの配置と処理が正しく行われることを保証します。

これらの変更は、`image/jpeg`パッケージがより広範なJPEGサブサンプリング形式をサポートするための包括的なアプローチを示しています。デコードロジックの汎用化、新しいエラーハンドリング、そして新しいテストケースの追加により、ライブラリの堅牢性と互換性が大幅に向上しました。

## コアとなるコードの解説

### `src/image/jpeg/reader.go`の変更点

このファイルでは、JPEGヘッダの解析、特にSOF (Start Of Frame) マーカーの処理ロジックが大幅に強化されています。

*   **`errUnsupportedSubsamplingRatio`の導入**:
    `UnsupportedError`型を基にした新しいエラー変数が定義されました。これにより、サポートされていないサブサンプリング比率が検出された際に、より具体的なエラーを返すことができます。

*   **`processSOF`関数内の`hv`値の処理**:
    以前は、各コンポーネントの`hv`値（水平・垂直サンプリングファクタ）を直接`d.comp[i].h`と`d.comp[i].v`に代入していました。しかし、この変更では、まず`hv`値から`h`と`v`を抽出し、それらの値が有効な範囲（1から4）にあるか、また`3`ではないか（`h=3`や`v=3`は一般的ではないためサポート外とする）を厳密にチェックしています。これにより、不正な`hv`値を持つJPEGファイルに対する堅牢性が向上します。

*   **コンポーネント数に応じたサンプリング比率の検証**:
    `switch d.nComp`ブロックが導入され、画像のコンポーネント数（1, 3, 4）に応じて、より詳細なサンプリング比率の検証が行われるようになりました。
    *   **単一コンポーネント（グレースケール）**: `h`と`v`は常に`1, 1`として扱われます。これはJPEGの仕様に基づいています。
    *   **3コンポーネント（YCbCr）**: Y、Cb、Crの各コンポーネントに対して、その役割に応じたサンプリング比率の制約が適用されます。特に、Yコンポーネントの`v`が`4`である場合はサポートされません。また、CbとCrコンポーネントのサンプリングファクタがYコンポーネントのサンプリングファクタの倍数であること、およびCbとCrが同じサンプリング比率を持つことが検証されます。これにより、一般的なYCbCrサブサンプリング形式（4:4:4, 4:2:2, 4:2:0など）の正確なデコードが保証されます。
    *   **4コンポーネント（CMYK/YCbCrK）**: 特定の`hv`ベクトルの組み合わせ（`[0x11 0x11 0x11 0x11]`または`[0x22 0x11 0x11 0x22]`）のみがサポートされます。これは、これらの形式で一般的なサンプリングパターンに限定することで、実装の複雑さを管理するためです。

*   **最終的な`h`と`v`の代入**:
    これらの検証の後、抽出された`h`と`v`の値が`d.comp[i].h`と`d.comp[i].v`に代入されます。これにより、デコーダは各コンポーネントの正しいサンプリングファクタを認識し、後続のデコード処理で利用できるようになります。

### `src/image/jpeg/scan.go`の変更点

このファイルでは、デコードされた画像データのメモリ割り当てと、DCTブロックの走査ロジックが更新されています。

*   **`makeImg`関数のシグネチャ変更と`YCbCrSubsampleRatio`の決定**:
    `makeImg`関数から`h0`, `v0`パラメータが削除され、これらの値はデコーダのコンポーネント情報（`d.comp[0].h`, `d.comp[0].v`）から直接取得されるようになりました。
    最も重要な変更は、`image.YCbCrSubsampleRatio`を決定する`switch`文です。以前は`h0`と`v0`の直接比較に基づいていましたが、新しいコードでは`hRatio<<4 | vRatio`というビット演算を使用しています。ここで`hRatio`と`vRatio`は、輝度コンポーネント（Y）と色差コンポーネント（Cb/Cr）のサンプリング比率から計算されます。このビット演算により、`0x11`（4:4:4）、`0x12`（4:4:0）、`0x21`（4:2:2）、`0x22`（4:2:0）、`0x41`（4:1:1）、`0x42`（4:1:0）といった、より多様なサブサンプリング比率を簡潔かつ正確にマッピングできるようになりました。これにより、`image.YCbCr`構造体の初期化時に正しいサブサンプリング比率が設定され、後続のアップサンプリング処理が適切に行われるようになります。

*   **`processSOS`関数内のブロック処理ロジックの更新**:
    `processSOS`関数内のDCTブロックを走査するループにおいて、各コンポーネントの水平・垂直サンプリングファクタ（`hi`, `vi`）が、`d.comp[compIndex].h`と`d.comp[compIndex].v`から動的に取得されるようになりました。これにより、ブロックのインデックス計算（`bx`, `by`）や、プログレッシブJPEGの係数保存ロジック（`d.progCoeffs`へのアクセス）が、各コンポーネントの実際のサンプリングファクタに基づいて行われるようになります。この変更は、`0x11`以外の`hv`値を持つJPEG画像でも、ブロックの配置と処理が正しく行われることを保証します。

これらのコード変更は、JPEGデコードの根幹部分に手を入れるものであり、Goの`image/jpeg`パッケージが、より広範なJPEGサブサンプリング形式を正確かつ効率的に処理できるようになるための重要な改善です。

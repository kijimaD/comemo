# [インデックス 25501] ファイルの概要

このコミットは、Goランタイムにおけるバッファ付きチャネルの実装を簡素化し、パフォーマンスを向上させることを目的としています。特に、チャネル操作におけるリトライメカニズムを排除し、送信者と受信者の間のデータ転送パスを最適化することで、コードの複雑さを軽減し、特定のシナリオでの効率を高めています。

## コミット

```
runtime: simplify buffered channels.

This change removes the retry mechanism we use for buffered channels.
Instead, any sender waking up a receiver or vice versa completes the
full protocol with its counterpart.  This means the counterpart does
not need to relock the channel when it wakes up.  (Currently
buffered channels need to relock on wakeup.)

For sends on a channel with waiting receivers, this change replaces
two copies (sender->queue, queue->receiver) with one (sender->receiver).
For receives on channels with a waiting sender, two copies are still required.

This change unifies to a large degree the algorithm for buffered
and unbuffered channels, simplifying the overall implementation.

Fixes #11506
```

## 変更の背景

Goのチャネルは、ゴルーチン間の安全な通信を可能にするための重要な並行処理プリミティブです。特にバッファ付きチャネルは、送信側と受信側のゴルーチンをある程度デカップリングし、バッファが満杯または空になるまでブロックせずに非同期的なデータ転送を可能にします。

このコミットが行われた背景には、既存のバッファ付きチャネルの実装におけるいくつかの非効率性がありました。

1.  **リトライメカニズムの存在**: 以前の実装では、バッファ付きチャネルの送信または受信操作が、相手側のゴルーチンをウェイクアップした後、チャネルのロックを再取得して操作を「リトライ」する必要がありました。これは、ウェイクアップされたゴルーチンが実際に操作を完了できる状態にあるかを再確認するためのものでしたが、オーバーヘッドを伴いました。
2.  **データコピーの非効率性**: 特に、受信待ちのゴルーチンが存在するバッファ付きチャネルへの送信の場合、データはまず送信者からチャネルの内部バッファにコピーされ、その後バッファから受信者へコピーされるという、二段階のコピープロセスが必要でした。これは、直接送信者から受信者へデータを転送できる状況でも発生し、無駄なコピーが生じていました。
3.  **バッファ付きとバッファなしチャネルのアルゴリズムの乖離**: バッファ付きチャネルとバッファなしチャネル（同期チャネル）では、内部的な処理ロジックに大きな違いがあり、コードの重複や複雑さの原因となっていました。

このコミットは、これらの課題に対処し、バッファ付きチャネルの内部実装を簡素化し、パフォーマンスを向上させることを目的としています。コミットメッセージにある`Fixes #11506`は、Goの公式イシュートラッカーの公開されたイシュー番号とは一致しないため、おそらく内部的な追跡番号であると考えられます。

## 前提知識の解説

このコミットを理解するためには、Goのチャネルの基本的な動作と、そのランタイム内部での実装に関する知識が必要です。

### Goチャネルの基本

*   **チャネル (Channel)**: ゴルーチン間で値を送受信するための通信メカニズム。`make(chan T, capacity)`で作成され、`capacity`が0の場合はバッファなしチャネル、1以上の場合はバッファ付きチャネルとなります。
*   **バッファなしチャネル**: 送信操作は受信操作が完了するまでブロックし、受信操作は送信操作が完了するまでブロックします。同期的な通信を行います。
*   **バッファ付きチャネル**: バッファに空きがあれば送信操作はブロックせず、バッファにデータがあれば受信操作はブロックしません。バッファが満杯になると送信はブロックし、バッファが空になると受信はブロックします。非同期的な通信を可能にします。
*   **`sendq` と `recvq`**: チャネルの内部には、送信待ちのゴルーチン (`sendq`) と受信待ちのゴルーチン (`recvq`) を管理するためのキュー（実際には`sudog`構造体のリンクリスト）があります。ゴルーチンがブロックされると、これらのキューに追加されます。
*   **`sudog` 構造体**: Goランタイム内部で、ブロックされたゴルーチンとそのチャネル操作に関する情報を保持するための構造体です。`g`フィールドでゴルーチンへのポインタを持ち、`elem`フィールドで送受信するデータへのポインタを持ちます。
*   **`hchan` 構造体**: チャネルの内部表現です。`qcount` (バッファ内の要素数)、`dataqsiz` (バッファサイズ)、`buf` (バッファへのポインタ)、`sendx` (送信インデックス)、`recvx` (受信インデックス)、`lock` (チャネルを保護するミューテックス) などのフィールドを持ちます。
*   **`gopark` と `goready`**: `gopark`は現在のゴルーチンをブロックし、スケジューラから実行キューを外します。`goready`はブロックされたゴルーチンを実行可能状態に戻し、スケジューラに実行キューに追加します。

### チャネル操作のライフサイクル (変更前)

1.  **送信操作 (`chansend`)**:
    *   チャネルのロックを取得します。
    *   受信待ちのゴルーチン (`recvq`) がいれば、そのゴルーチンに直接データを転送し、ウェイクアップします。
    *   バッファに空きがあれば、データをバッファにコピーし、送信インデックスを更新します。受信待ちのゴルーチン (`recvq`) がいればウェイクアップします。
    *   バッファが満杯で受信待ちのゴルーチンもいない場合、送信ゴルーチンは`sendq`に追加され、`gopark`でブロックされます。
    *   ウェイクアップされたゴルーチンは、チャネルのロックを再取得し、操作を「リトライ」します。
2.  **受信操作 (`chanrecv`)**:
    *   チャネルのロックを取得します。
    *   送信待ちのゴルーチン (`sendq`) がいれば、そのゴルーチンから直接データを受け取り、ウェイクアップします。
    *   バッファにデータがあれば、バッファからデータをコピーし、受信インデックスを更新します。送信待ちのゴルーチン (`sendq`) がいればウェイクアップします。
    *   バッファが空で送信待ちのゴルーチンもいない場合、受信ゴルーチンは`recvq`に追加され、`gopark`でブロックされます。
    *   ウェイクアップされたゴルーチンは、チャネルのロックを再取得し、操作を「リトライ」します。

この「リトライ」のステップが、このコミットで削除される主要な非効率性でした。

## 技術的詳細

このコミットの核心は、チャネル操作における「リトライメカニズム」の排除と、それに伴うデータ転送パスの最適化、そしてバッファ付き・バッファなしチャネルのアルゴリズムの統合です。

### リトライメカニズムの排除

変更前は、送信者（または受信者）が相手側のゴルーチンをウェイクアップした後、ウェイクアップされたゴルーチンはチャネルのロックを再取得し、操作を最初からやり直す必要がありました。これは、ウェイクアップされた時点でチャネルの状態が変化している可能性を考慮したものでしたが、多くの場合、不要なオーバーヘッドでした。

このコミットでは、**ウェイクアップする側のゴルーチンが、相手側のゴルーチンの操作を完全に完了させる**ように変更されました。具体的には、送信者が受信者をウェイクアップする場合、送信者が受信者の`sudog`構造体に直接データをコピーし、受信者を`goready`で実行可能状態にします。これにより、ウェイクアップされた受信者は、チャネルのロックを再取得したり、チャネルの状態を再確認したりすることなく、すぐに処理を続行できます。

### データ転送パスの最適化

*   **送信 (待ち受信者がいる場合)**:
    *   **変更前**: 送信者 -> チャネルバッファ -> 受信者 (2回のコピー)
    *   **変更後**: 送信者 -> 受信者 (1回の直接コピー)
    これは、`chansend`関数内で、`c.recvq`に受信待ちのゴルーチンが存在する場合に、新しく導入された`send`ヘルパー関数を呼び出すことで実現されます。`send`関数は、送信される値を直接受信者の`sudog.elem`にコピーします。
*   **受信 (待ち送信者がいる場合)**:
    *   **変更前**: 送信者 -> チャネルバッファ -> 受信者 (2回のコピー)
    *   **変更後**: 送信者 -> チャネルバッファ -> 受信者 (2回のコピー)
    受信操作に関しては、バッファ付きチャネルの場合、送信者がバッファにデータを書き込み、受信者がバッファからデータを読み取るという基本的な流れは変わりません。ただし、`chanrecv`関数内で、`c.sendq`に送信待ちのゴルーチンが存在する場合に、新しく導入された`recv`ヘルパー関数を呼び出すことで、処理がより統一的に行われるようになります。`recv`関数は、送信者のデータをバッファにコピーし、同時にバッファから受信者の`ep`にデータをコピーします。

### アルゴリズムの統合

`chansend`と`chanrecv`関数内のロジックが大幅に簡素化され、バッファなしチャネルとバッファ付きチャネルの処理が、より共通のパスを通るようになりました。特に、`send`と`recv`という新しいヘルパー関数が導入され、チャネルのタイプ（バッファなし、バッファ付き）に関わらず、相手側のゴルーチンとの直接的なやり取りをカプセル化しています。これにより、コードの重複が減り、全体的な実装がより理解しやすくなりました。

### パフォーマンスへの影響

コミットメッセージに記載されているベンチマーク結果は、この変更がチャネル操作のパフォーマンスにポジティブな影響を与えたことを示しています。特に`BenchmarkChanProdCons`系のベンチマークで顕著な改善が見られ、これはチャネルを介した生産者-消費者パターンにおける効率が向上したことを示唆しています。リトライメカニズムの排除とデータコピーの削減が、これらの改善の主な要因と考えられます。

## コアとなるコードの変更箇所

主な変更は`src/runtime/chan.go`と`src/runtime/select.go`に集中しています。

### `src/runtime/chan.go`

*   **`chansend` 関数の変更**:
    *   バッファなしチャネルとバッファ付きチャネルの処理ロジックが統合され、`c.dataqsiz == 0`による条件分岐が大幅に削減されました。
    *   受信待ちのゴルーチン (`c.recvq.dequeue()`) が見つかった場合、新しい`send`ヘルパー関数が呼び出され、直接データ転送と受信者のウェイクアップが行われます。
    *   バッファに空きがある場合 (`c.qcount < c.dataqsiz`)、データは直接バッファにコピーされます。
    *   ブロックが必要な場合、送信ゴルーチンは`sendq`にエンキューされ、`goparkunlock`でブロックされます。ウェイクアップ後、`gp.param`が`nil`でない場合にのみ、データが正常に送信されたと判断されます。
*   **`chanrecv` 関数の変更**:
    *   `chansend`と同様に、バッファなしチャネルとバッファ付きチャネルの処理ロジックが統合されました。
    *   送信待ちのゴルーチン (`c.sendq.dequeue()`) が見つかった場合、新しい`recv`ヘルパー関数が呼び出され、データ転送と送信者のウェイクアップが行われます。
    *   バッファにデータがある場合 (`c.qcount > 0`)、データは直接バッファから受信者の`ep`にコピーされます。
    *   ブロックが必要な場合、受信ゴルーチンは`recvq`にエンキューされ、`goparkunlock`でブロックされます。
*   **新しいヘルパー関数 `send` の導入**:
    *   `func send(c *hchan, sg *sudog, ep unsafe.Pointer, unlockf func())`
    *   チャネル`c`、ウェイクアップされる受信者`sg`、送信される値`ep`、そしてチャネルのロックを解除するための関数`unlockf`を受け取ります。
    *   `raceenabled`の場合の処理を含め、`ep`の値を`sg.elem`に直接コピーし、`goready`で`sg.g`（受信ゴルーチン）をウェイクアップします。
*   **新しいヘルパー関数 `recv` の導入**:
    *   `func recv(c *hchan, sg *sudog, ep unsafe.Pointer, unlockf func())`
    *   チャネル`c`、ウェイクアップされる送信者`sg`、受信される値を書き込む場所`ep`、そしてチャネルのロックを解除するための関数`unlockf`を受け取ります。
    *   バッファなしチャネルの場合、`sg.elem`から`ep`へ直接コピーします。
    *   バッファ付きチャネルの場合、バッファの先頭から`ep`へデータをコピーし、同時に`sg.elem`からバッファの末尾へデータをコピーします。その後、`goready`で`sg.g`（送信ゴルーチン）をウェイクアップします。
*   **`syncsend` 関数のリネームと変更**:
    *   `syncsend`は`sendDirect`にリネームされ、より汎用的なデータコピー関数となりました。これは、スタック間のデータコピーに関するGCの考慮事項を処理します。
*   **`recvclosed` 関数の削除**:
    *   チャネルがクローズされた際の受信処理が`chanrecv`内に統合され、`recvclosed`ヘルパー関数は不要になりました。

### `src/runtime/select.go`

*   `selectgoImpl`関数内のチャネル操作ロジックが、`chan.go`の変更に合わせて更新されました。
*   `caseRecv`と`caseSend`の処理において、`c.dataqsiz`によるバッファなし/バッファ付きの分岐が簡素化され、`sendq`や`recvq`からの直接的な処理が優先されるようになりました。
*   `asyncrecv`と`asyncsend`というラベルがそれぞれ`bufrecv`と`bufsend`にリネームされ、バッファ操作であることを明確にしました。
*   `syncrecv`と`syncsend`というラベルがそれぞれ`recv`と`send`にリネームされ、`chan.go`で導入された新しいヘルパー関数`recv`と`send`を呼び出すように変更されました。これにより、`select`文内のチャネル操作も、より統一されたロジックを使用するようになりました。

## コアとなるコードの解説

このコミットの最も重要な変更は、`chansend`と`chanrecv`関数から、複雑なリトライロジックと重複するコードパスが削除され、`send`および`recv`という新しいヘルパー関数にその責任が委譲された点です。

### `send` ヘルパー関数 (`src/runtime/chan.go`)

```go
// send processes a send operation on an empty channel c.
// The value ep sent by the sender is copied to the receiver sg.
// The receiver is then woken up to go on its merry way.
// Channel c must be empty and locked.  send unlocks c with unlockf.
// sg must already be dequeued from c.
// ep must be non-nil and point to the heap or the caller's stack.
func send(c *hchan, sg *sudog, ep unsafe.Pointer, unlockf func()) {
	if raceenabled {
		if c.dataqsiz == 0 {
			racesync(c, sg)
		} else {
			// Pretend we go through the buffer, even though
			// we copy directly.  Note that we need to increment
			// the head/tail locations only when raceenabled.
			qp := chanbuf(c, c.recvx)
			raceacquire(qp)
			racerelease(qp)
			raceacquireg(sg.g, qp)
			racereleaseg(sg.g, qp)
			c.recvx++
			if c.recvx == c.dataqsiz {
				c.recvx = 0
			}
			c.sendx = c.recvx // c.sendx = (c.sendx+1) % c.dataqsiz
		}
	}
	unlockf()
	if sg.elem != nil {
		sendDirect(c.elemtype, sg.elem, ep)
		sg.elem = nil
	}
	gp := sg.g
	gp.param = unsafe.Pointer(sg)
	if sg.releasetime != 0 {
		sg.releasetime = cputicks()
	}
	goready(gp, 4)
}
```
この`send`関数は、送信者が受信待ちのゴルーチンを見つけた場合に呼び出されます。
*   `raceenabled`の場合、データ競合検出のための処理が行われます。バッファ付きチャネルの場合、直接コピーが行われるにもかかわらず、あたかもバッファを経由したかのように`recvx`と`sendx`を更新します。これは、`race`ツールがチャネルバッファを介したデータフローを正しく追跡できるようにするためです。
*   `unlockf()`を呼び出してチャネルのロックを解除します。これにより、ウェイクアップされる受信者はロックを再取得する必要がなくなります。
*   `sendDirect(c.elemtype, sg.elem, ep)`を呼び出し、送信される値`ep`を直接受信者の`sg.elem`（受信者が値を受け取るためのメモリ領域）にコピーします。`sendDirect`は、スタック間のコピーにおけるGCの安全性を考慮した関数です。
*   `gp.param = unsafe.Pointer(sg)`を設定し、受信ゴルーチン`gp`がウェイクアップされた際に、`sg`（`sudog`）を通じて送信が成功したことを認識できるようにします。
*   `goready(gp, 4)`を呼び出して、受信ゴルーチン`gp`を実行可能状態に戻します。

### `recv` ヘルパー関数 (`src/runtime/chan.go`)

```go
// recv processes a receive operation on a full channel c.
// There are 2 parts:
// 1) The value sent by the sender sg is put into the channel
//    and the sender is woken up to go on its merry way.
// 2) The value received by the receiver (the current G) is
//    written to ep.
// For synchronous channels, both values are the same.
// For asynchronous channels, the receiver gets its data from
// the channel buffer and the sender's data is put in the
// channel buffer.
// Channel c must be full and locked. recv unlocks c with unlockf.
// sg must already be dequeued from c.
// A non-nil ep must point to the heap or the caller's stack.
func recv(c *hchan, sg *sudog, ep unsafe.Pointer, unlockf func()) {
	if c.dataqsiz == 0 {
		if raceenabled {
			racesync(c, sg)
		}
		unlockf()
		if ep != nil {
			// copy data from sender
			// ep points to our own stack or heap, so nothing
			// special (ala sendDirect) needed here.
			typedmemmove(c.elemtype, ep, sg.elem)
		}
	} else {
		// Queue is full.  Take the item at the
		// head of the queue.  Make the sender enqueue
		// its item at the tail of the queue (both map to
		// the same buffer slot because the queue is full).
		qp := chanbuf(c, c.recvx)
		if raceenabled {
			raceacquire(qp)
			racerelease(qp)
			raceacquireg(sg.g, qp)
			racereleaseg(sg.g, qp)
		}
		// copy data from queue to receiver
		if ep != nil {
			typedmemmove(c.elemtype, ep, qp)
		}
		// copy data from sender to queue
		typedmemmove(c.elemtype, qp, sg.elem)
		c.recvx++
		if c.recvx == c.dataqsiz {
			c.recvx = 0
		}
		c.sendx = c.recvx // c.sendx = (c.sendx+1) % c.dataqsiz
		unlockf()
	}
	sg.elem = nil
	gp := sg.g
	gp.param = unsafe.Pointer(sg)
	if sg.releasetime != 0 {
		sg.releasetime = cputicks()
	}
	goready(gp, 4)
}
```
この`recv`関数は、受信者が送信待ちのゴルーチンを見つけた場合に呼び出されます。
*   `c.dataqsiz == 0` (バッファなしチャネル) の場合:
    *   `raceenabled`の場合の処理が行われます。
    *   `unlockf()`を呼び出してチャネルのロックを解除します。
    *   `typedmemmove(c.elemtype, ep, sg.elem)`を呼び出し、送信者の`sg.elem`から受信者の`ep`へ直接データをコピーします。
*   `else` (バッファ付きチャネル) の場合:
    *   バッファが満杯の状態を想定し、バッファの先頭 (`qp`) から受信者の`ep`へデータをコピーします。
    *   同時に、送信者の`sg.elem`からバッファの同じスロット (`qp`) へデータをコピーします。これは、バッファが満杯であるため、受信と同時に送信が行われることで、バッファ内のスロットが循環的に再利用されるためです。
    *   `recvx`と`sendx`を更新し、バッファの循環を維持します。
    *   `unlockf()`を呼び出してチャネルのロックを解除します。
*   `gp.param = unsafe.Pointer(sg)`を設定し、送信ゴルーチン`gp`がウェイクアップされた際に、`sg`を通じて受信が成功したことを認識できるようにします。
*   `goready(gp, 4)`を呼び出して、送信ゴルーチン`gp`を実行可能状態に戻します。

これらの変更により、チャネル操作のロジックがより明確になり、特に競合状態でのロックの再取得が不要になったことで、効率が向上しました。

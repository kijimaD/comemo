## 変更の背景

Goコンパイラは、パフォーマンスと最適化を向上させるために、SSA (Static Single Assignment) 形式への移行を進めていました。このSSAバックエンドの開発は、Go 1.7で導入され、その後のバージョンで成熟していきました。

`TestStackBarrierProfiling`は、Goランタイムのガベージコレクション (GC) におけるスタックバリアの動作とプロファイリングの正確性を検証するための重要なテストです。しかし、SSAブランチでの開発中に、このテストが不安定 (flaky) になる問題が発生していました。テストの不安定性は、開発プロセスを妨げ、真のバグを見逃す原因となるため、一時的にこのテストはスキップされていました。

本コミットの著者は、OS XおよびLinux amd64環境でこのテストを1000回実行し、一度も失敗しなかったことを確認しました。この安定性の確認を受けて、テストを再有効化し、関連するTODOリストの項目を削除することが決定されました。これにより、SSAコンパイラの開発がさらに進展し、Goランタイムの安定性と信頼性が向上することが期待されます。

## 前提知識の解説

### GoのSSA (Static Single Assignment) コンパイラ

Goコンパイラは、プログラムの最適化を強化するために、中間表現としてSSA形式を採用しています。SSA形式は、各変数が一度だけ代入されるようにプログラムを変換するもので、データフロー解析や様々な最適化（例: 共通部分式の削除、デッドコードの削除、レジスタ割り当ての最適化など）を容易にします。

GoのSSAバックエンドは、Go 1.7で導入され、それまでのコンパイラバックエンドを置き換えました。これにより、生成されるバイナリのパフォーマンスが向上し、コンパイル時間も短縮されました。しかし、このような大規模な変更は、ランタイムの他の部分、特にガベージコレクション (GC) との相互作用において、予期せぬ問題を引き起こす可能性があります。

### ガベージコレクション (GC) とスタックバリア

Goのガベージコレクタは、並行 (concurrent) かつ非世代別 (non-generational) の三色マーク・アンド・スイープ (tri-color mark-and-sweep) アルゴリズムを採用しています。これは、アプリケーションの実行 (mutator) と並行して動作し、Stop-The-World (STW) ポーズ時間を最小限に抑えることを目的としています。

GCの正確性を保証するために、Goは「ライトバリア (write barrier)」と呼ばれるメカニズムを使用します。ライトバリアは、ポインタが変更される際にコンパイラによって挿入される小さなコードスニペットで、GCがオブジェクトグラフの変更を追跡し、生きているオブジェクトが誤って回収されるのを防ぎます。

「スタックバリア (stack barrier)」は、独立したバリアタイプというよりも、ライトバリアがゴルーチンのスタック上に割り当てられたポインタをどのように扱うかに関連する概念です。Go 1.8で導入された「ハイブリッドライトバリア」は、スタックの扱いを最適化し、STWポーズ時間を大幅に削減しました。

ハイブリッドライトバリアの主要な側面は以下の通りです。
*   GCのマークフェーズ開始時に、スタック上のすべてのオブジェクトがスキャンされ、黒（到達可能）としてマークされます。
*   GC中にスタック上に新しく作成されるオブジェクトも黒としてマークされます。
*   この初期および継続的なスタックオブジェクトのマークにより、マークフェーズの終わりにスタックを再スキャンする必要がなくなり、STW時間が大幅に短縮されます。

SSAコンパイラは、このライトバリア（スタックバリアのロジックを含む）を生成されたコードに正確に挿入する役割を担っています。

### プロファイリング (`pprof`)

Goには、`pprof`という強力なプロファイリングツールが組み込まれています。`pprof`は、CPU使用率、メモリ割り当て、ゴルーチンのスタックトレース、ブロックされた操作など、様々な側面からアプリケーションのパフォーマンスを分析するのに役立ちます。

`TestStackBarrierProfiling`は、スタックバリアの動作がプロファイリングデータに悪影響を与えないことを確認するためのテストです。例えば、スタックバリアの処理がプロファイリングのサンプリングを妨げたり、不正確なスタックトレースを生成したりしないことを検証します。

### `GODEBUG=gcstackbarrierall=1`

`GODEBUG`は、Goランタイムの様々なデバッグ変数を制御するための環境変数です。`name=val`形式で設定され、ランタイムの動作を変更したり、追加のデバッグ出力を有効にしたりするために使用されます。

`gcstackbarrierall=1`は、公式には文書化されていない内部的または実験的な`GODEBUG`フラグであると考えられます。その名前から、GCとスタックバリアの相互作用に関連していることが示唆されます。このフラグは、特定のスタックバリアの動作を強制したり、スタックスキャンとライトバリアに関連する最適化を有効/無効にしたり、GC中のスタックバリア操作に関する詳細なデバッグ情報を提供したりするために使用される可能性があります。

このコミットでは、`GODEBUG=gcstackbarrierall=1`を設定してテストを再実行することで、「定常的なGCとスタック」の条件下でテストの安定性を確認しています。これは、GCが常にアクティブな状態でスタックバリアが機能することを保証するためのテストシナリオと考えられます。

## 技術的詳細

このコミットの技術的な核心は、GoコンパイラのSSAバックエンドとGoランタイムのガベージコレクションにおけるスタックバリアの相互作用の安定性に関するものです。

`TestStackBarrierProfiling`は、`src/runtime/pprof/pprof_test.go`に定義されているテストで、スタックバリアが有効な状態でプロファイリングが正しく機能するかを検証します。SSAコンパイラの開発初期段階では、新しいコード生成パスがスタックバリアの挿入や動作に影響を与え、テストが非決定的な失敗（flakiness）を引き起こしていた可能性があります。これは、SSA変換がスタックフレームのレイアウトやポインタのライフタイムに微妙な変更をもたらし、GCのスタックスキャンやライトバリアのトリガータイミングに影響を与えたためと考えられます。

コミットメッセージにある「Tested it 1000x on OS X and Linux amd64, no failures.」という記述は、この不安定性の原因が特定され、修正されたか、あるいはSSAバックエンドが十分に成熟し、スタックバリアとの相互作用が安定したことを示しています。1000回の反復テストは、特に並行処理やGCに関連する非決定的なバグを検出するために有効な手法です。

テストコード内では、`GODEBUG=gcstackbarrierall=1`が設定されていない場合に、テストが自身を再実行するロジックが含まれています。これは、この特定の`GODEBUG`設定が、スタックバリアの動作を特定のテストシナリオ（例: 常にスタックバリアが有効な状態）に強制するために使用されていることを示唆しています。これにより、通常の実行環境では発生しにくい、スタックバリアに関連するエッジケースを確実にテストできます。

このコミットは、SSAコンパイラの安定化と、Goランタイムの重要なコンポーネントであるGCとプロファイリングの信頼性向上に貢献するものです。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/TODO` の変更

このファイルは、SSAコンパイラに関する未解決のタスクや既知の問題をリストアップするものです。変更点では、`- Re-enable TestStackBarrierProfiling (src/runtime/pprof/pprof_test.go)` という行が削除されています。これは、このコミットによって`TestStackBarrierProfiling`の再有効化が完了し、もはやTODOリストの項目ではないことを示しています。

### `src/runtime/pprof/pprof_test.go` の変更

このファイルは、Goランタイムのプロファイリング機能 (`pprof`) のテストコードを含んでいます。`TestStackBarrierProfiling`関数内で、以下のブロックが削除されています。

```go
	if true {
		// TODO(khr): remove
		t.Skipf("skipping for SSA branch, flaky")
		return
	}
```

この`if true`ブロックは、常に真となる条件式であり、その内部で`t.Skipf`が呼び出されていました。`t.Skipf`は、テストをスキップし、指定されたメッセージ（"skipping for SSA branch, flaky"）を出力するGoのテストフレームワークの機能です。このブロックが存在していた間、`TestStackBarrierProfiling`はSSAブランチでの不安定性のため、常にスキップされていました。

このブロックが削除されたことにより、`TestStackBarrierProfiling`は再び実行されるようになります。テストの冒頭には、低解像度タイマーがプロファイリングシグナルを阻害する場合にテストをスキップするロジックが残っていますが、これは別の問題（golang.org/issue/13405）に対応するものです。

また、削除されたブロックの下には、`GODEBUG=gcstackbarrierall=1`が設定されていない場合にテストを再実行するロジックがあります。これは、特定のGC設定下でのテストを保証するためのものであり、このコミットの変更とは直接関係ありませんが、テストの実行環境に関する重要な情報を提供しています。

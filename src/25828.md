## 変更の背景

Goコンパイラの初期バージョンでは、パーサーの生成にYacc（Yet Another Compiler Compiler）というツールが使用されており、その入力ファイルが`go.y`でした。YaccはBNF（Backus-Naur Form）のような文法定義からLALR(1)パーサーを自動生成するツールです。しかし、Yaccによって生成されるパーサーは、デバッグが困難であったり、エラーハンドリングの柔軟性に欠けるといった課題がありました。

Go言語の進化とともに、コンパイラの保守性、パフォーマンス、そしてエラーメッセージの品質向上が求められるようになりました。そのため、Goコンパイラチームは、Yaccに依存する自動生成パーサーから、手書きの再帰下降型パーサーへの移行を進めていました。このコミットは、その移行プロセスの一環として、もはや使用されていない`go.y`への参照をコードベースから完全に削除し、手書きパーサーの動作をより正確に反映するようにドキュメンテーションを更新することを目的としています。

特に、Go言語の文法におけるセミコロンの自動挿入規則は複雑であり、Yaccのようなツールではその挙動を正確にモデル化し、かつ良好なエラーメッセージを提供することが難しい場合があります。手書きパーサーに移行することで、これらの複雑な文法規則に対するよりきめ細やかな制御と、より分かりやすいエラーハンドリングが可能になります。

## 前提知識の解説

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。`gc`（Go Compiler）とも呼ばれます。
*   **パーサー (Parser)**: 字句解析器（lexer/scanner）によって生成されたトークン列を受け取り、そのトークン列が言語の文法規則に合致するかどうかを検証し、抽象構文木（AST: Abstract Syntax Tree）を構築するコンパイラのフェーズです。
*   **Yacc (Yet Another Compiler Compiler)**: 文法定義ファイル（通常`.y`拡張子）からC言語のパーサーコードを生成するツールです。LALR(1)パーサーを生成します。
*   **再帰下降型パーサー (Recursive-descent parser)**: 文法の各非終端記号に対応する関数を定義し、それらの関数が再帰的に呼び出されることで入力トークン列を解析するパーサーです。手書きで実装されることが多く、デバッグが容易で、エラーハンドリングの柔軟性が高いという特徴があります。
*   **抽象構文木 (AST)**: ソースコードの構文構造を木構造で表現したものです。コンパイラの後のフェーズ（意味解析、コード生成など）で利用されます。
*   **Go言語のセミコロン自動挿入 (Automatic Semicolon Insertion - ASI)**: Go言語の文法規則の一つで、特定の状況下で改行文字がセミコロンとして扱われるというものです。これにより、多くのGoプログラムでは明示的なセミコロンを記述する必要がありませんが、パーサーにとっては複雑なルールとなります。
*   **`parser.go`**: Goコンパイラの`cmd/compile/internal/gc`パッケージ内にある、Go言語のソースコードを解析する再帰下降型パーサーの実装ファイルです。

## 技術的詳細

このコミットの主要な変更点は、`src/cmd/compile/internal/gc/parser.go`ファイルにおける以下の点に集約されます。

1.  **`go.y`参照の削除**:
    *   以前のコードには、各パーサーメソッドのコメントとして`// go.y:method_name`のような形式で、対応するYaccプロダクションへの参照が記述されていました。これは、手書きパーサーがYaccベースのパーサーから移行する際のガイドラインとして残されていたものです。
    *   このコミットでは、これらの`// go.y:`コメントがすべて削除されています。これは、手書きパーサーの実装が安定し、もはやYaccの文法定義を参照する必要がなくなったことを示しています。

2.  **ドキュメンテーションの更新とGo文法規則の明記**:
    *   ファイルの冒頭に、この再帰下降型パーサーの設計思想と、Go言語の文法規則との関係を説明する新しいコメントが追加されました。
        ```go
        // The recursive-descent parser is built around a slighty modified grammar
        // of Go to accomodate for the constraints imposed by strict one token look-
        // ahead, and for better error handling. Subsequent checks of the constructed
        // syntax tree restrict the language accepted by the compiler to proper Go.
        //
        // Semicolons are inserted by the lexer. The parser uses one-token look-ahead
        // to handle optional commas and semicolons before a closing ) or } .
        ```
        このコメントは、パーサーが厳密な1トークン先読みの制約とより良いエラーハンドリングのために、Goの文法をわずかに修正して構築されていること、そして構築された構文木に対する後続のチェックによって、コンパイラが受け入れる言語が適切なGoに制限されることを説明しています。また、セミコロンは字句解析器によって挿入され、パーサーは閉じ括弧や閉じブレースの前のオプションのカンマやセミコロンを処理するために1トークン先読みを使用することも明記されています。
    *   各パーサーメソッドの直前には、Go言語の公式仕様から引用されたBNF形式の文法規則がコメントとして追加されました。例えば、`file()`メソッドの上には`SourceFile = PackageClause ";" { ImportDecl ";" } { TopLevelDecl ";" } .`、`package_()`メソッドの上には`PackageClause = "package" PackageName .`といった形で、そのメソッドが解析する文法要素が明確に示されています。これにより、コードの可読性と保守性が向上し、Go言語の文法とパーサーの実装との対応関係がより明確になりました。

3.  **セミコロン認識の調整**:
    *   `file()`メソッド内で、`p.package_()`の呼び出し後に`p.want(';')`が追加されました。これは、`package`句の後に明示的にセミコロン（または自動挿入されるセミコロン）が続くことをパーサーが期待するように変更されたことを意味します。
    *   一方で、`package_()`メソッド内からは以前存在した`p.want(';')`が削除されました。
    *   この変更は、Go言語のセミコロン自動挿入規則と、パーサーのトークン先読みロジックをより正確に整合させるためのものです。`package`句の直後にセミコロンを期待するのではなく、ファイル全体のトップレベルの構造の一部として`package`句の後にセミコロンが来ることを`file()`メソッドで処理するように変更されたと考えられます。これにより、パーサーのロジックがGoの文法規則により忠実になります。

### 変更前 (`file` メソッドの一部)

```go
 func (p *parser) file() {
 	if trace && Debug['x'] != 0 {
 		defer p.trace("file")()
 	}

 	p.package_()

 	//go.y:imports
 	for p.tok == LIMPORT {
 		p.import_()
 		p.want(';')
 	}
 	// ...
 }

 func (p *parser) package_() {
 	if trace && Debug['x'] != 0 {
 		defer p.trace("package_")()
 	}

 	if p.got(LPACKAGE) {
 		mkpackage(p.sym().Name)
 		p.want(';') // <-- ここにセミコロンの期待があった
 	} else {
 		prevlineno = lineno // see issue #13267
 		p.syntax_error("package statement must be first")
 	}
 }
```

## コアとなるコードの解説

このコミットの最も重要なコード変更は、`parser.go`内の`file()`メソッドと`package_()`メソッドにおけるセミコロンの処理の調整です。

*   **`package_()`メソッドからの`p.want(';')`の削除**:
    *   `package_()`メソッドは`package`宣言を解析する役割を担っています。変更前は、`package`キーワードとパッケージ名の後にセミコロンが続くことをこのメソッド自身が期待していました。
    *   Goの文法では、`package`宣言の後にセミコロンが続くのは必須ですが、これはGoのセミコロン自動挿入規則によって暗黙的に挿入されることがほとんどです。パーサーが個々の文法要素の直後に常にセミコロンを期待すると、自動挿入の挙動と衝突したり、エラーハンドリングが複雑になる可能性があります。
    *   この削除は、`package`宣言自体の解析ロジックから、その後のセミコロンの存在チェックを分離し、より上位の構造（ファイル全体）で処理するように変更されたことを示唆しています。

*   **`file()`メソッドへの`p.want(';')`の追加**:
    *   `file()`メソッドはGoのソースファイル全体を解析するトップレベルのメソッドです。
    *   `p.package_()`の呼び出し直後に`p.want(';')`が追加されたことで、`file()`メソッドが`package`宣言の後に続くセミコロン（明示的または自動挿入）を処理する責任を持つようになりました。
    *   この変更により、パーサーは`SourceFile = PackageClause ";" { ImportDecl ";" } { TopLevelDecl ";" } .`というGoの文法規則に、より直接的に従う形になります。`PackageClause`の後に`";"`が続くという規則を`file()`メソッドが明示的に強制することで、パーサーの構造が文法定義とより密接に連携するようになりました。

この調整は、Goコンパイラのパーサーが、Yaccのようなツールに依存せず、手書きの再帰下降型パーサーとしてGo言語の複雑な文法（特にセミコロン自動挿入）をより正確かつ堅牢に解析できるようにするための洗練された変更と言えます。これにより、コンパイラの内部ロジックがよりクリーンになり、将来的なメンテナンスや機能拡張が容易になることが期待されます。

# [インデックス 22312] ファイルの概要

このコミットは、Goコンパイラおよびリンカの内部処理におけるパフォーマンス最適化に関するものです。具体的には、`cmd/internal/ld` パッケージ（Goリンカの一部）において、`linkgetline` 関数内でファイル名の構築とシンボル検索のキャッシュを行うことで、繰り返し発生するメモリ割り当てとマップルックアップを削減し、PCLNテーブルの構築を高速化しています。

## 元コミット内容

`cmd/internal/ld: linkgetlineにおけるファイル名構築のキャッシュ`

これは、PCLNテーブルを構築する際の繰り返し発生するメモリ割り当てとマップルックアップを回避します。

`cmd/internal/gc/*.go` を `6g` でコンパイルする場合、これにより約8%の実行時間が短縮されます。

## 変更の背景

Goコンパイラとリンカは、ソースコードから実行可能ファイルを生成する過程で、多くの内部処理を行います。その一つに、PCLN (Program Counter to Line Number) テーブルの構築があります。このテーブルは、実行時のプログラムカウンタ（命令アドレス）とソースコードのファイル名および行番号をマッピングするために使用され、デバッグ情報、スタックトレース、プロファイリングなどに不可欠です。

PCLNテーブルの構築中、`linkgetline` 関数は、特定のプログラムカウンタに対応するソースコードのファイル名と行番号を決定する役割を担っています。この処理の中で、ファイルパスの正規化（絶対パスへの変換、`$GOROOT` や `trimpath` の適用など）と、そのファイルパスに対応するリンカシンボル（`LSym`）の検索が頻繁に行われていました。

従来のリンカでは、このファイルパスの構築と `LSym` の検索が、必要になるたびに繰り返し行われていました。ファイルパスの文字列構築はメモリ割り当てを伴い、`LSym` の検索（`Linklookup` 関数）は内部的なマップルックアップを伴うため、これらの操作が頻繁に実行されると、コンパイルおよびリンク時間のオーバーヘッドが大きくなるという問題がありました。特に、大規模なGoプログラムや、多くのGoソースファイルを含むパッケージをコンパイルする際には、このオーバーヘッドが顕著になり、ビルド時間の増加に繋がっていました。

このコミットは、この非効率性を解消し、ビルドパフォーマンスを向上させることを目的としています。

## 前提知識の解説

このコミットの理解を深めるために、以下のGoコンパイラ・リンカ関連の概念を理解しておく必要があります。

1.  **Goツールチェイン (`cmd/`)**:
    *   **`cmd/internal/ld`**: Goリンカの内部パッケージです。Goのソースコードから生成されたオブジェクトファイルを結合し、最終的な実行可能ファイルを生成する役割を担います。シンボル解決、メモリレイアウトの決定、PCLNテーブルの生成などを行います。
    *   **`cmd/internal/gc`**: Goコンパイラの内部パッケージです。Goのソースコードを中間表現に変換し、最終的にアセンブリコードやオブジェクトファイルを生成します。
    *   **`6g`**: 2015年当時のGoコンパイラ（`go tool compile` の前身）の一つで、x86-64アーキテクチャ向けのコンパイラを指します。

2.  **PCLNテーブル (Program Counter to Line Number Tables)**:
    *   Goの実行可能ファイルに埋め込まれる重要なメタデータの一つです。
    *   プログラムカウンタ（PC、つまり実行中の命令のアドレス）と、対応するソースコードのファイル名および行番号とのマッピングを提供します。
    *   **用途**:
        *   **スタックトレース**: パニック発生時やエラー発生時に、どのファイルのどの行で問題が発生したかを特定するために使用されます。
        *   **デバッグ**: デバッガが実行中のコードとソースコードを関連付けるために使用します。
        *   **プロファイリング**: パフォーマンスプロファイラが、CPU時間やメモリ割り当てがどのソースコード行で消費されているかを特定するために使用します。
    *   このテーブルの効率的な構築は、Goプログラムのビルド時間と実行可能ファイルのサイズに影響を与えます。

3.  **`LSym` (Linker Symbol)**:
    *   Goリンカが内部的に使用するデータ構造で、プログラム内のあらゆるシンボル（関数、グローバル変数、型など）を表します。
    *   各 `LSym` は、そのシンボルの名前、種類、アドレス、サイズ、そして関連するメタデータ（例えば、ソースファイル情報）などの情報を含みます。
    *   リンカは `LSym` を用いて、異なるオブジェクトファイル間の参照を解決し、最終的な実行可能ファイル内の各要素のメモリ上の位置を決定します。
    *   `Linklookup` 関数は、指定された名前の `LSym` を検索し、存在しない場合は新しく作成して返します。

4.  **`Hist` 構造体**:
    *   Goコンパイラおよびリンカが、ソースファイルのインクルード履歴や行番号情報を追跡するために使用する構造体です。
    *   `Name` フィールドはファイル名、`Line` フィールドは行番号、`Link` フィールドは前の履歴エントリへのポインタを持ち、インクルードチェーンを形成します。
    *   このコミットでは、この `Hist` 構造体に `Sym *LSym` フィールドが追加され、ファイル名文字列だけでなく、そのファイル名に対応する `LSym` もキャッシュできるようになります。

5.  **`linkgetline` 関数**:
    *   Goリンカの内部関数で、PCLNテーブルの構築中に、特定のプログラムカウンタに対応するソースコードのファイル名と行番号を決定するために呼び出されます。
    *   この関数は、ソースファイルの履歴（`Hist` 構造体のチェーン）を辿り、適切なファイル名と行番号を特定します。
    *   ファイル名から `LSym` を取得する際に、ファイルパスの正規化処理（`filepath.IsAbs`, `strings.HasPrefix`, `ctxt.Trimpath`, `ctxt.Goroot`, `ctxt.Goroot_final` などを用いたパスの調整）と `Linklookup` による `LSym` の検索が行われます。

6.  **ファイルパスの正規化と `ctxt`**:
    *   Goのビルドシステムでは、ソースファイルのパスは様々な形で扱われます。
    *   `filepath.IsAbs`: パスが絶対パスかどうかを判定します。
    *   `strings.HasPrefix`: 文字列が特定のプレフィックスで始まるかを判定します。
    *   `ctxt.Trimpath`: ビルド時にソースコードの絶対パスから特定のプレフィックス（例えば、ビルド環境のルートディレクトリ）を削除するための設定です。これにより、ビルドの再現性が向上し、実行可能ファイル内のパス情報が短縮されます。
    *   `ctxt.Goroot` と `ctxt.Goroot_final`: Goのインストールディレクトリ（`$GOROOT`）に関連するパスを処理するための設定です。`Goroot_final` は、最終的な実行可能ファイルに埋め込まれる `$GOROOT` のパスを指します。これらの設定により、Go標準ライブラリのソースパスが適切に処理されます。

## 技術的詳細

このコミットの主要な技術的改善点は、`linkgetline` 関数におけるファイルパスの `LSym` キャッシュです。

PCLNテーブルの構築プロセスでは、同じソースファイルが何度も参照され、そのたびに `linkgetline` が呼び出される可能性があります。従来のリンカでは、`linkgetline` が呼び出されるたびに、以下の処理が繰り返されていました。

1.  ソースファイルのパス文字列を構築する（`ctxt.Pathname` とファイル名を結合し、`Trimpath` や `Goroot` の調整を行う）。この文字列構築は、新しい文字列のメモリ割り当てを伴います。
2.  構築されたファイルパス文字列を使用して `Linklookup` 関数を呼び出し、対応する `LSym` を検索または作成する。`Linklookup` は内部的にマップルックアップを行うため、これもコストのかかる操作です。

これらの繰り返し発生するメモリ割り当てとマップルックアップは、特に多数のソースファイルを持つ大規模なプロジェクトのコンパイルにおいて、ビルド時間のボトルネックとなっていました。

このコミットでは、`Hist` 構造体に `Sym *LSym` フィールドを追加することで、この問題を解決しています。`Hist` 構造体は、ソースファイルの履歴情報を保持するため、一度ファイルパスに対応する `LSym` が取得されれば、それを `Hist` 構造体内にキャッシュすることができます。

`linkgetline` 関数は、まず `Hist` 構造体内の `Sym` フィールドが `nil` でないかを確認します。
*   もし `Sym` フィールドが既に設定されていれば、それは以前にこのファイルパスの `LSym` が取得され、キャッシュされていることを意味します。この場合、ファイルパスの文字列構築と `Linklookup` の呼び出しをスキップし、キャッシュされた `LSym` を直接使用します。
*   もし `Sym` フィールドが `nil` であれば、従来通りファイルパスの文字列を構築し、`Linklookup` を呼び出して `LSym` を取得します。そして、取得した `LSym` を `Hist` 構造体の `Sym` フィールドに保存（キャッシュ）します。

この変更により、同じファイルパスに対する `LSym` の検索は初回のみコストがかかり、2回目以降はキャッシュされた `LSym` を高速に利用できるようになります。これにより、メモリ割り当てとマップルックアップの回数が大幅に削減され、PCLNテーブルの構築が効率化されます。

コミットメッセージにある「`6g` で `cmd/internal/gc/*.go` をコンパイルする場合、約8%の実行時間が短縮される」という記述は、この最適化がGoコンパイラ自身のコンパイル時間にも大きな影響を与えることを示しており、その効果の大きさを裏付けています。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下の2つのファイルに集中しています。

1.  **`src/cmd/internal/obj/link.go`**:
    *   `Hist` 構造体の定義がこのファイルから削除されました。これは、`Hist` 構造体が `src/cmd/internal/obj/obj.go` に移動されたためです。

2.  **`src/cmd/internal/obj/obj.go`**:
    *   **`Hist` 構造体の定義の移動と変更**:
        *   `Hist` 構造体がこのファイルに移動されました。
        *   新しいフィールド `Sym *LSym` が追加されました。
        ```go
        type Hist struct {
        	Link    *Hist
        	Name    string
        	Sym     *LSym // <-- 追加されたフィールド
        	Line    int32
        	Offset  int32
        	Printed uint8
        }
        ```
    *   **`linkgetline` 関数の変更**:
        *   `sym *LSym` という新しいローカル変数が導入されました。
        *   ファイルパスの文字列構築と `Linklookup` の呼び出しが、`sym == nil` の条件ブロック内に移動されました。
        *   `a[n].line.Sym` または `a[n].incl.Sym` に、取得した `LSym` をキャッシュするロジックが追加されました。
        *   最終的に `*f = sym` となり、キャッシュされた `LSym` が返されるようになりました。

## コアとなるコードの解説

変更の中心は `src/cmd/internal/obj/obj.go` 内の `linkgetline` 関数です。

```go
func linkgetline(ctxt *Link, line int32, f **LSym, l *int32) {
	// ... (既存のコード) ...

	var dlno int32
	var file string
	var sym *LSym // <-- 新しく導入されたローカル変数

	if a[n].line != nil {
		file = a[n].line.Name
		sym = a[n].line.Sym // <-- Hist構造体からSymを取得
		dlno = a[n].ldel - 1
	} else {
		file = a[n].incl.Name
		sym = a[n].incl.Sym // <-- Hist構造体からSymを取得
		dlno = a[n].idel - 1
	}

	if sym == nil { // <-- ここがキャッシュの有無を判定する条件
		var buf string
		if filepath.IsAbs(file) || strings.HasPrefix(file, "<") {
			buf = file
		} else {
			buf = ctxt.Pathname + "/" + file
		}
		// Remove leading ctxt->trimpath, or else rewrite $GOROOT to $GOROOT_FINAL.
		if ctxt.Trimpath != "" && haspathprefix(buf, ctxt.Trimpath) {
			if len(buf) == len(ctxt.Trimpath) {
				buf = "??"
			} else {
				buf1 := buf[len(ctxt.Trimpath)+1:]
				if buf1[0] == '\x00' {
					buf1 = "??"
				}
				buf = buf1
			}
		} else if ctxt.Goroot_final != "" && haspathprefix(buf, ctxt.Goroot) {
			buf1 := fmt.Sprintf("%s%s", ctxt.Goroot_final, buf[len(ctxt.Goroot):])
			buf = buf1
		}
		sym = Linklookup(ctxt, buf, HistVersion) // <-- Linklookupを呼び出し、LSymを取得
		if a[n].line != nil {
			a[n].line.Sym = sym // <-- 取得したLSymをHist構造体にキャッシュ
		} else {
			a[n].incl.Sym = sym // <-- 取得したLSymをHist構造体にキャッシュ
		}
	}

	lno -= dlno
	*f = sym // <-- キャッシュされた、または新しく取得されたLSymを返す
	*l = lno
}
```

**解説**:

1.  **`var sym *LSym` の導入**: `linkgetline` 関数内で、ファイルパスに対応する `LSym` を保持するためのローカル変数 `sym` が宣言されます。
2.  **`Hist` からの `Sym` の取得**:
    *   `a[n].line` または `a[n].incl` は、現在の行情報またはインクルード元の行情報を示す `Hist` 構造体へのポインタです。
    *   `sym = a[n].line.Sym` または `sym = a[n].incl.Sym` の行で、対応する `Hist` 構造体から既にキャッシュされている `LSym` があれば、それを `sym` 変数に代入します。初回呼び出し時や、まだキャッシュされていないファイルパスの場合は `sym` は `nil` となります。
3.  **キャッシュ判定 (`if sym == nil`)**:
    *   この条件文が、最適化の肝となります。`sym` が `nil` でない（つまり、既に `LSym` がキャッシュされている）場合、条件ブロック内の処理はスキップされます。
    *   `sym` が `nil` の場合（キャッシュされていない場合）のみ、以下の処理が実行されます。
4.  **ファイルパス文字列の構築**:
    *   `filepath.IsAbs`, `strings.HasPrefix`, `ctxt.Trimpath`, `ctxt.Goroot`, `ctxt.Goroot_final` などを用いて、ソースファイルのパスを正規化し、`buf` 変数に格納します。この処理は、文字列の結合や操作を伴い、メモリ割り当てが発生する可能性があります。
5.  **`Linklookup` による `LSym` の取得**:
    *   構築された `buf` (ファイルパス文字列) を引数として `Linklookup` 関数が呼び出され、対応する `LSym` が検索または新しく作成されます。この操作は、内部的なマップルックアップを伴います。
6.  **`Hist` への `LSym` のキャッシュ**:
    *   `sym = Linklookup(...)` で取得された `LSym` は、`a[n].line.Sym = sym` または `a[n].incl.Sym = sym` の行で、対応する `Hist` 構造体の `Sym` フィールドに保存されます。これにより、次回同じファイルパスが参照された際には、この `LSym` が再利用されるようになります。
7.  **`LSym` の返却**:
    *   最終的に `*f = sym` の行で、キャッシュされた `LSym`（または今回新しく取得された `LSym`）が呼び出し元に返されます。

この変更により、`linkgetline` が同じファイルパスに対して複数回呼び出された場合でも、ファイルパス文字列の構築と `Linklookup` の呼び出しは最初の1回だけで済み、2回目以降はキャッシュされた `LSym` を直接利用できるため、全体的なビルドパフォーマンスが向上します。

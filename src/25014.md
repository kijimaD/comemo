# [インデックス 25014] ファイルの概要

このコミットは、GoランタイムのAMD64アーキテクチャにおけるメモリゼロクリア処理（`duffzero`）のパフォーマンス最適化を目的としています。具体的には、従来の`MOVQ`命令（8バイト単位）によるゼロクリアから、`MOVUPS`命令（16バイト単位）を使用するように変更することで、より大きなメモリ領域のゼロクリアを高速化しています。これにより、特に40バイト以上のメモリ領域のゼロクリアにおいて、最大で約57%の性能向上が見られます。

## 変更の背景

Go言語のランタイムは、ガベージコレクションや新しいメモリ割り当ての際に、メモリ領域をゼロクリアする処理を頻繁に行います。このゼロクリア処理の効率は、プログラム全体のパフォーマンスに大きな影響を与えます。特に、AMD64アーキテクチャでは、より効率的な命令セット（SIMD命令など）が利用可能であり、これらを活用することでゼロクリアの速度を向上させる余地がありました。

従来の`duffzero`ルーチンは、主に`MOVQ`命令（64ビット、つまり8バイト単位）を使用してメモリをゼロクリアしていました。しかし、現代のCPUはSIMD（Single Instruction, Multiple Data）命令をサポートしており、これらを使用することで一度に複数のデータ要素を処理できます。`MOVUPS`命令は、SSE（Streaming SIMD Extensions）の一部であり、128ビット（16バイト）のデータを一度にメモリに書き込むことができます。

このコミットは、`MOVQ`ベースのゼロクリアが特定のサイズのメモリ領域（特に40バイト以上）でボトルネックになっていることを認識し、`MOVUPS`命令を導入することで、これらのケースでのパフォーマンスを大幅に改善することを目的としています。ベンチマーク結果が示すように、この変更は特に中規模から大規模なメモリ領域のゼロクリアにおいて顕著な効果を発揮しています。

## 前提知識の解説

### Duff's Device (ダフのデバイス) と Duffzero

Duff's Deviceは、C言語でループアンローリングを効率的に実装するためのテクニックとして知られています。これは、`switch`文と`do-while`ループを組み合わせることで、ループのオーバーヘッドを削減し、コンパイラがより効率的なコードを生成できるようにするものです。

Goランタイムの`duffzero`および`duffcopy`は、このDuff's Deviceの概念をアセンブリ言語で実装したものです。これらは、特定のサイズのメモリ領域をゼロクリアまたはコピーする際に、ループの分岐予測ミスやオーバーヘッドを最小限に抑えるために、一連の命令を直接展開（アンロール）したコードブロックにジャンプする方式を採用しています。これにより、非常に高速なメモリ操作を実現しています。

### x86-64 アセンブリ命令とレジスタ

*   **`MOVQ` (Move Quadword)**: 64ビット（8バイト）のデータを移動する命令です。従来の`duffzero`では、この命令を使って8バイト単位でゼロを書き込んでいました。
*   **`STOSQ` (Store String Quadword)**: `AL`レジスタの内容を`DI`レジスタが指すメモリ位置に格納し、`DI`をインクリメントする命令です。`REP`プレフィックスと組み合わせることで、指定された回数だけ繰り返し実行し、効率的にメモリをゼロクリアできます。
*   **`MOVUPS` (Move Unaligned Packed Single-precision Floating-point)**: SSE命令セットの一部で、128ビット（16バイト）のデータをメモリとXMMレジスタ間で移動する命令です。この命令は、メモリのアライメント（整列）を気にせずに使用できるため、柔軟性が高いです。
*   **`XORPS` (Bitwise Logical XOR of Packed Single-precision Floating-point)**: SSE命令セットの一部で、XMMレジスタ内のパックされた単精度浮動小数点数に対してビット単位のXOR演算を行います。同じレジスタに対して`XORPS X0, X0`のように実行すると、`X0`レジスタの内容がすべてゼロになります。これは、SIMDレジスタを効率的にゼロクリアする一般的な手法です。
*   **`AX` (Accumulator Register)**: 汎用レジスタの一つで、通常は算術演算やデータ転送に使用されます。従来の`duffzero`では、`AX`レジスタにゼロを格納し、それをメモリに書き込んでいました。
*   **`DI` (Destination Index Register)**: 汎用レジスタの一つで、通常は文字列操作やメモリ操作の際に、目的地のメモリアドレスを指すポインタとして使用されます。`duffzero`では、ゼロクリア対象のメモリ領域の開始アドレスを保持します。
*   **`X0` (XMM0 Register)**: SSE命令で使用される128ビットのSIMDレジスタです。`MOVUPS`や`XORPS`などの命令で、一度に複数のデータ要素を処理するために使用されます。

### SIMD (Single Instruction, Multiple Data)

SIMDは、単一の命令で複数のデータ要素に対して同じ操作を同時に実行できるプロセッサの機能です。これにより、データ並列性が高い処理（例えば、画像処理、科学計算、メモリ操作など）を大幅に高速化できます。IntelのSSEやAVX（Advanced Vector Extensions）は、x86-64アーキテクチャにおける代表的なSIMD命令セットです。`MOVUPS`はSSE命令セットの一部であり、このコミットではSIMDの能力を活用してゼロクリアを最適化しています。

### メモリのアライメント

メモリのアライメントとは、データがメモリ上で特定のバイト境界に配置されることを指します。例えば、16バイトのアライメントとは、データの開始アドレスが16の倍数であることを意味します。SIMD命令の中には、アライメントされたメモリにアクセスする場合にのみ最高のパフォーマンスを発揮するもの（例: `MOVAPS`）と、アライメントされていないメモリにもアクセスできるもの（例: `MOVUPS`）があります。`MOVUPS`はアライメントを気にしないため、より汎用的に使用できますが、アライメントされたアクセスの方がわずかに高速な場合があります。このコミットでは`MOVUPS`が選択されており、柔軟性とパフォーマンスのバランスが考慮されています。

### Goランタイムのメモリ管理とゼロクリア

Go言語では、新しい変数が宣言されたり、スライスやマップが作成されたりする際に、そのメモリ領域が自動的にゼロ値で初期化されます。これはGoの安全性と予測可能性を保証する重要な特性です。ガベージコレクタがメモリを再利用する際にも、古いデータが残らないようにゼロクリアが行われることがあります。これらのゼロクリア処理はランタイムの内部で行われ、その効率がGoプログラム全体の実行速度に直結します。

## 技術的詳細

このコミットの主要な変更点は、GoランタイムのAMD64向け`duffzero`ルーチンが、従来の8バイト単位の`MOVQ`命令から、16バイト単位の`MOVUPS`命令を使用するように変更されたことです。

### 従来の`duffzero` (変更前)

変更前の`src/runtime/duff_amd64.s`では、`runtime·duffzero`関数は主に`MOVQ AX,(DI)`、`MOVQ AX,8(DI)`、`MOVQ AX,16(DI)`、`MOVQ AX,24(DI)`といった命令の繰り返しで構成されていました。これは、`AX`レジスタに格納されたゼロ（64ビット）を、`DI`レジスタが指すアドレスから8バイト、16バイト、24バイトオフセットした位置に書き込み、その後`DI`レジスタを32バイト（4 * 8バイト）進めるという処理を繰り返していました。最後に、残りのバイトを`STOSQ`命令で処理していました。

この方法は、8バイト単位での効率的なゼロクリアを実現していましたが、16バイト単位で処理できるSIMD命令と比較すると、特に大きなメモリ領域では効率が劣っていました。

### `MOVUPS`による最適化 (変更後)

新しい`duffzero`ルーチンでは、`X0`レジスタ（128ビットのSIMDレジスタ）を`XORPS X0, X0`命令でゼロクリアし、そのゼロ値を`MOVUPS`命令でメモリに書き込むように変更されました。

*   `MOVUPS X0,(DI)`
*   `MOVUPS X0,16(DI)`
*   `MOVUPS X0,32(DI)`
*   `MOVUPS X0,48(DI)`
*   `ADDQ $64,DI`

この命令シーケンスは、`X0`レジスタのゼロを`DI`が指すアドレスから0、16、32、48バイトオフセットした位置にそれぞれ16バイトずつ書き込みます。これにより、一度に64バイト（4 * 16バイト）のメモリをゼロクリアし、その後`DI`レジスタを64バイト進めます。このブロックを16回繰り返すことで、合計1024バイトのメモリを効率的にゼロクリアできるようになっています。

### コンパイラ (`src/cmd/compile/internal/amd64/ggen.go`) の変更

コンパイラのバックエンドでは、`zerorange`関数と`clearfat`関数が、メモリゼロクリアのコード生成を担当しています。

*   **`zerorange`関数**: スタックフレーム上の特定の範囲をゼロクリアするために使用されます。この関数は、ゼロクリアするバイト数`cnt`に応じて、異なる戦略を選択します。
    *   `cnt == 8`の場合: 従来の`MOVQ`で8バイトをゼロクリアします。
    *   `cnt <= int64(8*gc.Widthreg)` (64バイト) の場合: 新しく導入された`MOVUPS`命令を直接生成して、16バイト単位でゼロクリアします。この際、`X0`レジスタを`XORPS`でゼロクリアするコードも生成されます。
    *   `!gc.Nacl && (cnt <= int64(128*gc.Widthreg))` (1024バイト) の場合: `duffzero`ルーチンへのジャンプを生成します。この際、`dzDI`関数と`dzOff`関数が、`duffzero`ルーチン内の適切な開始点とDIレジスタの事前調整オフセットを計算します。ここでも、`MOVUPS`を使用するために`X0`レジスタのゼロクリアが追加されています。
    *   それ以上の大きなサイズの場合: `REP STOSQ`命令（繰り返しストア）を使用します。
*   **`clearfat`関数**: 構造体などの大きなデータ型をゼロクリアするために使用されます。
    *   `w > 1024 || (gc.Nacl && w >= 64)` (1024バイト以上、またはNaCl環境で64バイト以上) の場合: `REP STOSQ`を使用します。
    *   `w >= 64` (64バイト以上) の場合: `duffzero`ルーチンへのジャンプを生成します。ここでも`MOVUPS`を使用するために`X0`レジスタのゼロクリアが追加されています。
    *   それ以下のサイズの場合: `clearfat_tail`関数を呼び出して、より細かい粒度でゼロクリアを行います。
*   **`clearfat_tail`関数**: `clearfat`から呼び出され、小さなサイズのゼロクリアを処理します。
    *   `b >= 16`の場合: `MOVUPS`命令を直接生成して16バイト単位でゼロクリアします。
    *   `b >= 8`の場合: `MOVQ`命令を直接生成して8バイト単位でゼロクリアします。
    *   `b >= 4`の場合: `MOVL`命令を直接生成して4バイト単位でゼロクリアします。
    *   `b >= 2`の場合: `MOVW`命令を直接生成して2バイト単位でゼロクリアします。
    *   残りのバイト: `MOVB`命令を直接生成して1バイト単位でゼロクリアします。

### アセンブリコード生成ツール (`src/runtime/mkduff.go`) の変更

`mkduff.go`は、`duff_amd64.s`のようなアセンブリファイルを自動生成するためのGoプログラムです。このコミットでは、`zeroAMD64`関数が更新され、`duffzero`ルーチンを生成する際に、`MOVQ`の代わりに`MOVUPS`命令を使用するように変更されました。これにより、生成されるアセンブリコードが新しい最適化を反映したものになります。

### `src/cmd/compile/internal/amd64/prog.go` の変更

このファイルは、コンパイラがアセンブリ命令のプロパティ（サイズ、レジスタの使用方法など）を認識するために使用されます。このコミットでは、新しく使用される`AMOVUPS`と`AXORPS`命令に関する情報が`progtable`に追加されました。これにより、コンパイラがこれらの命令を正しく扱い、コード生成時に適切な最適化を適用できるようになります。

### パフォーマンス結果の分析

コミットメッセージに記載されているベンチマーク結果は、この最適化の効果を明確に示しています。

*   `ClearFat8`から`ClearFat32`までの比較的小さなサイズでは、パフォーマンスに大きな変化はありません。これは、これらのサイズでは`MOVUPS`の恩恵が少ないか、あるいは従来の`MOVQ`やより細かいバイト単位のゼロクリアが依然として効率的であるためと考えられます。
*   `ClearFat40`、`ClearFat48`、`ClearFat56`といった中程度のサイズで、50%以上の劇的な性能向上が見られます。これは、これらのサイズが16バイトの倍数に近いか、`MOVUPS`命令の効率が最大限に活かされる範囲にあるためと考えられます。
*   `ClearFat64`以上の大きなサイズでも、20%以上の性能向上が見られます。これは、`duffzero`ルーチン自体が`MOVUPS`を多用するようになったため、全体的なスループットが向上した結果です。

この結果から、`MOVUPS`命令による16バイト単位のゼロクリアが、特に中規模から大規模なメモリ領域のゼロクリアにおいて、従来の8バイト単位の処理よりもはるかに効率的であることがわかります。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、以下の2つのファイルに集中しています。

1.  **`src/runtime/duff_amd64.s`**:
    *   従来の`MOVQ`命令の繰り返しが、`MOVUPS`命令の繰り返しに置き換えられました。
    *   `AX`レジスタの代わりに`X0`レジスタが使用され、`XORPS X0, X0`でゼロクリアされます。
    *   一度にゼロクリアされるバイト数が32バイトから64バイトに増加し、`ADDQ $32,DI`が`ADDQ $64,DI`に変更されました。

2.  **`src/cmd/compile/internal/amd64/ggen.go`**:
    *   `zerorange`関数と`clearfat`関数において、`MOVUPS`命令を生成するための新しいロジックが追加されました。
    *   `zerorange`の引数に`x0 *uint32`が追加され、`X0`レジスタがゼロクリアされたかどうかを追跡するようになりました。
    *   `dzBlocks`定数が31から16に、`dzClearStep`が8から16に、`dzClearLen`が新しく定義されました。
    *   `dzOff`関数と`dzDI`関数が、バイト数に基づいてオフセットとDIレジスタの調整を計算するように変更されました。
    *   `clearfat_tail`という新しいヘルパー関数が追加され、小さなサイズのゼロクリアを`MOVUPS`、`MOVQ`、`MOVL`、`MOVW`、`MOVB`を組み合わせて処理するようになりました。

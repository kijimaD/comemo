# [インデックス 26399] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおける浮動小数点数の移動命令の選択を最適化し、特にMandelbrotベンチマークのような浮動小数点演算を多用するコードのパフォーマンスを大幅に改善することを目的としています。具体的には、浮動小数点レジスタ間の移動に、より広範な（"wider"）移動命令を使用することで、コンパイラが生成するアセンブリコードの効率を高めています。

## コミット

GoコンパイラのSSAバックエンドにおいて、浮動小数点数のレジスタ間移動命令の選択ロジックが改善されました。これにより、浮動小数点値を扱う際のコード生成がより効率的になり、Mandelbrotベンチマークのパフォーマンスが大幅に向上しました。以前はレジスタ間移動、ロード、ストアの区別が曖昧でしたが、これらを明確に分離し、それぞれに最適な命令を選択するように変更されています。

## 変更の背景

Goコンパイラは、Go 1.7からSSA (Static Single Assignment) 形式をバックエンドに導入し、コード生成の最適化を強化しました。しかし、SSAの初期実装では、特に浮動小数点演算を多用するコードにおいて、生成されるアセンブリコードの効率が最適ではないケースがありました。

このコミットの背景には、Mandelbrotベンチマークのパフォーマンス問題がありました。SSAを有効にした場合、Mandelbrotベンチマークの実行速度が以前のコンパイラと比較して58%も遅くなるという深刻な性能劣化が報告されていました。この性能劣化の主な原因は、浮動小数点値をレジスタ間で移動する際に、コンパイラが最適なx86-64命令を選択できていなかったことにありました。

具体的には、浮動小数点レジスタ（SSE/AVXレジスタ、XMMレジスタなど）は128ビットまたは256ビット幅ですが、単精度浮動小数点数（float32）は32ビット、倍精度浮動小数点数（float64）は64ビットです。これらの値をレジスタ間で移動する際、コンパイラが値のサイズに合わせた狭い移動命令（例: `MOVSS` for float32, `MOVSD` for float64）を使用すると、レジスタの残りの部分がゼロクリアされたり、部分的なレジスタ書き込みによるペナルティが発生したりすることがあります。

このコミットは、浮動小数点レジスタ間の移動において、レジスタ全体を移動する「より広範な（wider）」命令（例: `AMOVAPD`）を使用することで、この非効率性を解消し、Mandelbrotベンチマークの性能劣化を58%から12%にまで大幅に改善することを目指しました。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA (Static Single Assignment) 形式は、コンパイラの最適化フェーズで中間表現として広く用いられるプログラム表現形式です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。Goコンパイラは、Go 1.7からSSAバックエンドを導入し、より高度な最適化（レジスタ割り当て、命令スケジューリング、デッドコード削除など）を可能にしました。

### 2. Goコンパイラのバックエンドとコード生成

Goコンパイラは、ソースコードを抽象構文木 (AST) に変換し、その後、中間表現 (IR) を経て、最終的にターゲットアーキテクチャ（この場合はx86-64）のアセンブリコードを生成します。SSAバックエンドは、この中間表現の段階で動作し、最適化されたSSA形式のコードから、ターゲットアーキテクチャの命令セットに合わせた低レベルの命令を生成します。このプロセスには、レジスタ割り当て（どの値をどのCPUレジスタに格納するか）や、メモリとの間で値をロード/ストアする命令の選択が含まれます。

### 3. x86-64アーキテクチャと浮動小数点演算

x86-64アーキテクチャでは、浮動小数点演算は主にSSE (Streaming SIMD Extensions) やAVX (Advanced Vector Extensions) といったSIMD (Single Instruction, Multiple Data) 命令セットによって処理されます。これらの命令は、XMMレジスタ（128ビット幅）やYMMレジスタ（256ビット幅）を使用します。

*   **浮動小数点レジスタ**: x86-64では、`XMM0` から `XMM15` までの16個の128ビットレジスタが浮動小数点数やSIMD演算に使用されます。
*   **浮動小数点移動命令**:
    *   `MOVSS` (Move Scalar Single-precision Floating-point): 32ビット（単精度）浮動小数点数を移動します。ソースレジスタの下位32ビットをターゲットレジスタの下位32ビットにコピーし、ターゲットレジスタの上位96ビットはゼロクリアされるか、変更されない場合があります（命令の形式による）。
    *   `MOVSD` (Move Scalar Double-precision Floating-point): 64ビット（倍精度）浮動小数点数を移動します。ソースレジスタの下位64ビットをターゲットレジスタの下位64ビットにコピーし、ターゲットレジスタの上位64ビットはゼロクリアされるか、変更されない場合があります。
    *   `MOVAPD` (Move Aligned Packed Double-precision Floating-point): 128ビットのXMMレジスタ全体を移動します。これは、レジスタ全体をコピーするため、部分的なレジスタ書き込みによるペナルティを回避できます。名前は"Packed Double-precision"ですが、単精度浮動小数点数や整数値の移動にも使用できます。

部分的なレジスタ書き込みは、CPU内部でレジスタマージングのオーバーヘッドを引き起こす可能性があり、特にループ内で頻繁に発生すると性能に悪影響を与えることがあります。

### 4. Mandelbrotベンチマーク

Mandelbrot集合の計算は、複素数演算と浮動小数点演算を非常に多く使用する典型的なベンチマークです。この種の計算は、CPUの浮動小数点演算ユニット (FPU) とメモリサブシステムに大きな負荷をかけます。そのため、浮動小数点演算の効率が全体のパフォーマンスに直接影響します。SSAバックエンドの初期実装でMandelbrotベンチマークが遅くなったのは、浮動小数点演算に関連するコード生成の非効率性が原因であったことを示唆しています。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドが浮動小数点値を扱う際に生成するx86-64アセンブリ命令の選択ロジックを改善することにあります。

以前のコードでは、`regMoveByTypeAMD64` という関数がレジスタ間の移動、メモリからのロード、メモリへのストアのすべてに対して、型に応じた移動命令を決定していました。しかし、これらの操作はそれぞれ異なる最適な命令を持つ場合があります。特に浮動小数点数においては、レジスタ全体を移動する命令が部分的な移動命令よりも効率的であることが多いです。

このコミットでは、以下の主要な変更が行われました。

1.  **操作の明確な分離**:
    *   `regMoveByTypeAMD64` 関数が削除され、その機能は `loadByType`、`storeByType`、`moveByType` の3つの新しい関数に分割されました。
    *   `loadByType(t ssa.Type)`: メモリからレジスタへのロード操作に最適な命令を返します。
    *   `storeByType(t ssa.Type)`: レジスタからメモリへのストア操作に最適な命令を返します。
    *   `moveByType(t ssa.Type)`: レジスタからレジスタへの移動操作に最適な命令を返します。

2.  **浮動小数点レジスタ間移動の最適化**:
    *   `moveByType` 関数内で、型 `t` が浮動小数点型 (`t.IsFloat()`) である場合、`x86.AMOVAPD` 命令が返されるようになりました。
    *   `AMOVAPD` は、128ビットのXMMレジスタ全体を移動する命令です。これにより、単精度（32ビット）や倍精度（64ビット）の浮動小数点数を移動する際に、レジスタの部分的な書き込みによるオーバーヘッドを回避し、より高速なレジスタ間コピーが可能になります。コメントにも「Moving the whole sse2 register is faster than moving just the correct low portion of it.」と明記されています。

3.  **ロード/ストア命令の統一**:
    *   `loadByType` 関数は、x86アーキテクチャではロードとストアの命令が同じであるため、`storeByType` を呼び出すように実装されています。これは、整数型と浮動小数点型でそれぞれ適切な `MOV` 命令（`AMOVB`, `AMOVW`, `AMOVL`, `AMOVQ` for integers; `AMOVSS`, `AMOVSD` for floats）を選択します。

これらの変更により、コンパイラは浮動小数点値をレジスタ間で移動する際に、より効率的な `AMOVAPD` 命令を生成できるようになり、Mandelbrotベンチマークのような浮動小数点演算がボトルネックとなるアプリケーションの実行速度が大幅に改善されました。

## コアとなるコードの解説

### `moveByType` 関数

この関数は、レジスタからレジスタへの値の移動に最適なアセンブリ命令を返します。

```go
// moveByType returns the reg->reg move instruction of the given type.
func moveByType(t ssa.Type) int {
	if t.IsFloat() {
		// Moving the whole sse2 register is faster
		// than moving just the correct low portion of it.
		return x86.AMOVAPD
	} else { // integer types
		switch t.Size() {
		case 1:
			return x86.AMOVB
		case 2:
			return x86.AMOVW
		case 4:
			return x86.AMOVL
		case 8:
			return x86.AMOVQ
		}
	}
	panic("bad register type")
}
```

*   **浮動小数点型の場合**: `t.IsFloat()` が `true` の場合、`x86.AMOVAPD` が返されます。これは、前述の通り、128ビットのXMMレジスタ全体を移動する命令であり、部分的なレジスタ書き込みによる性能ペナルティを回避します。この変更がMandelbrotベンチマークの性能改善の主要因です。
*   **整数型の場合**: 型のサイズ (`t.Size()`) に応じて、適切な整数移動命令 (`AMOVB`, `AMOVW`, `AMOVL`, `AMOVQ`) が返されます。

### `loadByType` および `storeByType` 関数

これらの関数は、メモリとレジスタ間のロード（メモリからレジスタへ）およびストア（レジスタからメモリへ）操作に最適なアセンブリ命令を返します。

```go
// loadByType returns the load instruction of the given type.
func loadByType(t ssa.Type) int {
	// For x86, there's no difference between load and store opcodes.
	return storeByType(t)
}

// storeByType returns the store instruction of the given type.
func storeByType(t ssa.Type) int {
	width := t.Size()
	if t.IsFloat() {
		switch width {
		case 4: // float32
			return x86.AMOVSS
		case 8: // float64
			return x86.AMOVSD
		}
	} else { // integer types
		switch width {
		case 1:
			return x86.AMOVB
		case 2:
			return x86.AMOVW
		case 4:
			return x86.AMOVL
		case 8:
			return x86.AMOVQ
		}
	}
	panic("bad store type")
}
```

*   `loadByType` は、x86アーキテクチャではロードとストアの命令が同じであるため、`storeByType` を呼び出します。
*   `storeByType` は、型が浮動小数点型の場合、単精度 (`float32`) には `AMOVSS`、倍精度 (`float64`) には `AMOVSD` を返します。これらの命令は、メモリとの間で特定のサイズの浮動小数点値を効率的に移動するために設計されています。
*   整数型の場合も、型のサイズに応じて適切な整数移動命令を返します。

これらの変更により、Goコンパイラは、レジスタ間移動、メモリロード、メモリストアという異なる操作に対して、それぞれ最も効率的なx86-64アセンブリ命令を生成できるようになり、特に浮動小数点演算のパフォーマンスが向上しました。

# [インデックス 26399] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおける浮動小数点数の移動命令の選択を最適化し、特にMandelbrotベンチマークのような浮動小数点演算を多用するコードのパフォーマンスを大幅に改善することを目的としています。具体的には、浮動小数点レジスタ間の移動に、より広範な（"wider"）移動命令を使用することで、コンパイラが生成するアセンブリコードの効率を高めています。

## 変更の背景

Goコンパイラは、Go 1.7からSSA (Static Single Assignment) 形式をバックエンドに導入し、コード生成の最適化を強化しました。しかし、SSAの初期実装では、特に浮動小数点演算を多用するコードにおいて、生成されるアセンブリコードの効率が最適ではないケースがありました。

このコミットの背景には、Mandelbrotベンチマークのパフォーマンス問題がありました。SSAを有効にした場合、Mandelbrotベンチマークの実行速度が以前のコンパイラと比較して58%も遅くなるという深刻な性能劣化が報告されていました。この性能劣化の主な原因は、浮動小数点値をレジスタ間で移動する際に、コンパイラが最適なx86-64命令を選択できていなかったことにありました。

具体的には、浮動小数点レジスタ（SSE/AVXレジスタ、XMMレジスタなど）は128ビットまたは256ビット幅ですが、単精度浮動小数点数（float32）は32ビット、倍精度浮動小数点数（float64）は64ビットです。これらの値をレジスタ間で移動する際、コンパイラが値のサイズに合わせた狭い移動命令（例: `MOVSS` for float32, `MOVSD` for float64）を使用すると、レジスタの残りの部分がゼロクリアされたり、部分的なレジスタ書き込みによるペナルティが発生したりすることがあります。

このコミットは、浮動小数点レジスタ間の移動において、レジスタ全体を移動する「より広範な（wider）」命令（例: `AMOVAPD`）を使用することで、この非効率性を解消し、Mandelbrotベンチマークの性能劣化を58%から12%にまで大幅に改善することを目指しました。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA (Static Single Assignment) 形式は、コンパイラの最適化フェーズで中間表現として広く用いられるプログラム表現形式です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。Goコンパイラは、Go 1.7からSSAバックエンドを導入し、より高度な最適化（レジスタ割り当て、命令スケジューリング、デッドコード削除など）を可能にしました。

### 2. Goコンパイラのバックエンドとコード生成

Goコンパイラは、ソースコードを抽象構文木 (AST) に変換し、その後、中間表現 (IR) を経て、最終的にターゲットアーキテクチャ（この場合はx86-64）のアセンブリコードを生成します。SSAバックエンドは、この中間表現の段階で動作し、最適化されたSSA形式のコードから、ターゲットアーキテクチャの命令セットに合わせた低レベルの命令を生成します。このプロセスには、レジスタ割り当て（どの値をどのCPUレジスタに格納するか）や、メモリとの間で値をロード/ストアする命令の選択が含まれます。

### 3. x86-64アーキテクチャと浮動小数点演算

x86-64アーキテクチャでは、浮動小数点演算は主にSSE (Streaming SIMD Extensions) やAVX (Advanced Vector Extensions) といったSIMD (Single Instruction, Multiple Data) 命令セットによって処理されます。これらの命令は、XMMレジスタ（128ビット幅）やYMMレジスタ（256ビット幅）を使用します。

*   **浮動小数点レジスタ**: x86-64では、`XMM0` から `XMM15` までの16個の128ビットレジスタが浮動小数点数やSIMD演算に使用されます。
*   **浮動小数点移動命令**:
    *   `MOVSS` (Move Scalar Single-precision Floating-point): 32ビット（単精度）浮動小数点数を移動します。ソースレジスタの下位32ビットをターゲットレジスタの下位32ビットにコピーし、ターゲットレジスタの上位96ビットはゼロクリアされるか、変更されない場合があります（命令の形式による）。
    *   `MOVSD` (Move Scalar Double-precision Floating-point): 64ビット（倍精度）浮動小数点数を移動します。ソースレジスタの下位64ビットをターゲットレジスタの下位64ビットにコピーし、ターゲットレジスタの上位64ビットはゼロクリアされるか、変更されない場合があります。
    *   `MOVAPD` (Move Aligned Packed Double-precision Floating-point): 128ビットのXMMレジスタ全体を移動します。これは、レジスタ全体をコピーするため、部分的なレジスタ書き込みによるペナルティを回避できます。名前は"Packed Double-precision"ですが、単精度浮動小数点数や整数値の移動にも使用できます。

部分的なレジスタ書き込みは、CPU内部でレジスタマージングのオーバーヘッドを引き起こす可能性があり、特にループ内で頻繁に発生すると性能に悪影響を与えることがあります。

### 4. Mandelbrotベンチマーク

Mandelbrot集合の計算は、複素数演算と浮動小数点演算を非常に多く使用する典型的なベンチマークです。この種の計算は、CPUの浮動小数点演算ユニット (FPU) とメモリサブシステムに大きな負荷をかけます。そのため、浮動小数点演算の効率が全体のパフォーマンスに直接影響します。SSAバックエンドの初期実装でMandelbrotベンチマークが遅くなったのは、浮動小数点演算に関連するコード生成の非効率性が原因であったことを示唆しています。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドが浮動小数点値を扱う際に生成するx86-64アセンブリ命令の選択ロジックを改善することにあります。

以前のコードでは、`regMoveByTypeAMD64` という関数がレジスタ間の移動、メモリからのロード、メモリへのストアのすべてに対して、型に応じた移動命令を決定していました。しかし、これらの操作はそれぞれ異なる最適な命令を持つ場合があります。特に浮動小数点数においては、レジスタ全体を移動する命令が部分的な移動命令よりも効率的であることが多いです。

このコミットでは、以下の主要な変更が行われました。

1.  **操作の明確な分離**:
    *   `regMoveByTypeAMD64` 関数が削除され、その機能は `loadByType`、`storeByType`、`moveByType` の3つの新しい関数に分割されました。
    *   `loadByType(t ssa.Type)`: メモリからレジスタへのロード操作に最適な命令を返します。
    *   `storeByType(t ssa.Type)`: レジスタからメモリへのストア操作に最適な命令を返します。
    *   `moveByType(t ssa.Type)`: レジスタからレジスタへの移動操作に最適な命令を返します。

2.  **浮動小数点レジスタ間移動の最適化**:
    *   `moveByType` 関数内で、型 `t` が浮動小数点型 (`t.IsFloat()`) である場合、`x86.AMOVAPD` 命令が返されるようになりました。
    *   `AMOVAPD` は、128ビットのXMMレジスタ全体を移動する命令です。これにより、単精度（32ビット）や倍精度（64ビット）の浮動小数点数を移動する際に、レジスタの部分的な書き込みによるオーバーヘッドを回避し、より高速なレジスタ間コピーが可能になります。コメントにも「Moving the whole sse2 register is faster than moving just the correct low portion of it.」と明記されています。

3.  **ロード/ストア命令の統一**:
    *   `loadByType` 関数は、x86アーキテクチャではロードとストアの命令が同じであるため、`storeByType` を呼び出すように実装されています。これは、整数型と浮動小数点型でそれぞれ適切な `MOV` 命令（`AMOVB`, `AMOVW`, `AMOVL`, `AMOVQ` for integers; `AMOVSS`, `AMOVSD` for floats）を選択します。

これらの変更により、コンパイラは浮動小数点値をレジスタ間で移動する際に、より効率的な `AMOVAPD` 命令を生成できるようになり、Mandelbrotベンチマークのような浮動小数点演算がボトルネックとなるアプリケーションの実行速度が大幅に改善されました。

## コアとなるコードの解説

### `moveByType` 関数

この関数は、レジスタからレジスタへの値の移動に最適なアセンブリ命令を返します。

```go
// moveByType returns the reg->reg move instruction of the given type.
func moveByType(t ssa.Type) int {
	if t.IsFloat() {
		// Moving the whole sse2 register is faster
		// than moving just the correct low portion of it.
		return x86.AMOVAPD
	} else { // integer types
		switch t.Size() {
		case 1:
			return x86.AMOVB
		case 2:
			return x86.AMOVW
		case 4:
			return x86.AMOVL
		case 8:
			return x86.AMOVQ
		}
	}
	panic("bad register type")
}
```

*   **浮動小数点型の場合**: `t.IsFloat()` が `true` の場合、`x86.AMOVAPD` が返されます。これは、前述の通り、128ビットのXMMレジスタ全体を移動する命令であり、部分的なレジスタ書き込みによる性能ペナルティを回避します。この変更がMandelbrotベンチマークの性能改善の主要因です。
*   **整数型の場合**: 型のサイズ (`t.Size()`) に応じて、適切な整数移動命令 (`AMOVB`, `AMOVW`, `AMOVL`, `AMOVQ`) が返されます。

### `loadByType` および `storeByType` 関数

これらの関数は、メモリとレジスタ間のロード（メモリからレジスタへ）およびストア（レジスタからメモリへ）操作に最適なアセンブリ命令を返します。

```go
// loadByType returns the load instruction of the given type.
func loadByType(t ssa.Type) int {
	// For x86, there's no difference between load and store opcodes.
	return storeByType(t)
}

// storeByType returns the store instruction of the given type.
func storeByType(t ssa.Type) int {
	width := t.Size()
	if t.IsFloat() {
		switch width {
		case 4: // float32
			return x86.AMOVSS
		case 8: // float64
			return x86.AMOVSD
		}
	} else { // integer types
		switch width {
		case 1:
			return x86.AMOVB
		case 2:
			return x86.AMOVW
		case 4:
			return x86.AMOVL
		case 8:
			return x86.AMOVQ
		}
	}
	panic("bad store type")
}
```

*   `loadByType` は、x86アーキテクチャではロードとストアの命令が同じであるため、`storeByType` を呼び出します。
*   `storeByType` は、型が浮動小数点型の場合、単精度 (`float32`) には `AMOVSS`、倍精度 (`float64`) には `AMOVSD` を返します。これらの命令は、メモリとの間で特定のサイズの浮動小数点値を効率的に移動するために設計されています。
*   整数型の場合も、型のサイズに応じて適切な整数移動命令を返します。

これらの変更により、Goコンパイラは、レジスタ間移動、メモリロード、メモリストアという異なる操作に対して、それぞれ最も効率的なx86-64アセンブリ命令を生成できるようになり、特に浮動小数点演算のパフォーマンスが向上しました。

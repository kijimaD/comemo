## 変更の背景

このコミットは、GoランタイムがLinux上で動作する際に、`m.procid` フィールドが常にOSのスレッドID (TID: Thread ID) で設定されるようにするためのものです。主な目的は、デバッガやその他のプログラム検査ツールがGoプログラムの内部状態をより正確に、かつ容易に把握できるようにすることにあります。

Goプログラムをデバッグする際、デバッガはGoのゴルーチンと、それらが実行されている基盤となるOSスレッドとの関連性を理解する必要があります。`m.procid` がOSスレッドIDを正確に反映していない場合、デバッガは特定のGoランタイムの「M」（OSスレッドを表す構造体）がどのOSスレッドに対応しているかを判断するのが困難になります。

特に、Cgo（GoとC言語の相互運用機能）がGoランタイムの管理外で新しいOSスレッドを作成する可能性がある場合、これらのスレッドの `m.procid` が適切に設定されないと、デバッガは混乱する可能性があります。この変更は、このようなシナリオを含め、常に `m.procid` が正しいOSスレッドIDを指すようにすることで、デバッグ体験を向上させることを目指しています。コミットメッセージにある "Fixes #9914" は、この変更が特定のバグや問題（おそらくデバッグ関連）を解決することを示唆しています。

## 前提知識の解説

### GoランタイムのM, P, Gモデル

Goランタイムは、並行処理を効率的に管理するために「M, P, G」という3つの主要な抽象化を使用します。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。OSスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行できます。
*   **M (Machine)**: OSスレッドを表します。Goランタイムは、ゴルーチンを実行するためにOSスレッドを使用します。MはOSスレッドと1対1で対応し、スタックやレジスタなどのOSスレッド固有の情報を保持します。
*   **P (Processor)**: 論理プロセッサを表します。MとGの間の仲介役として機能し、GをMにディスパッチ（割り当て）します。Pの数は通常、CPUのコア数に等しく、同時に実行できるGoコードの数を制限します。

このモデルにおいて、MはOSスレッドそのものであるため、デバッガがGoプログラムの実行状態を理解するためには、各MがどのOSスレッドに対応しているかを知ることが不可欠です。`m.procid` はこのMに対応するOSスレッドのIDを格納するフィールドです。

### `gettid()` システムコール

`gettid()` はLinuxカーネルが提供するシステムコールの一つで、呼び出し元のスレッドの「スレッドID (TID)」を返します。Linuxでは、すべてのスレッドはカーネルによって一意のTIDで識別されます。これはプロセスID (`getpid()`) とは異なり、プロセス内の個々のスレッドを識別するために使用されます。デバッガは、このTIDを使用して特定のOSスレッドをターゲットにし、そのレジスタ、スタック、メモリなどを検査します。

### デバッガの役割とOSスレッドIDの重要性

デバッガ（例: GDB, Delve）は、実行中のプログラムの内部状態を検査し、制御するためのツールです。Goプログラムをデバッグする際、デバッガはGoランタイムのスケジューラがどのようにゴルーチンをOSスレッドに割り当て、実行しているかを理解する必要があります。

OSスレッドIDは、デバッガが以下のことを行う上で極めて重要です。

1.  **ゴルーチンとOSスレッドのマッピング**: 特定のゴルーチンが現在どのOSスレッドで実行されているかを特定します。
2.  **スレッド固有の情報の検査**: OSスレッドのスタックトレース、レジスタ値、スレッドローカルストレージなどの情報を取得します。
3.  **スケジューラの動作分析**: GoランタイムのスケジューラがどのようにゴルーチンをM（OSスレッド）間で移動させているかを追跡し、パフォーマンスの問題やデッドロックの原因を特定します。

`m.procid` が常に正確なOSスレッドIDを保持することで、デバッガはGoランタイムの内部構造とOSレベルの実行コンテキストを容易に同期させることができ、より効果的なデバッグが可能になります。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムの `m` 構造体内の `procid` フィールドに、対応するOSスレッドの実際のTIDを確実に設定することです。これは、主に以下の2つのステップで実現されています。

1.  **`gettid()` システムコールのGoランタイムからの呼び出し**: Linuxカーネルが提供する `gettid()` システムコールをGoランタイムから呼び出すためのメカニズムが導入されました。これは、各アーキテクチャ（386, amd64, arm, arm64, ppc64x）向けにアセンブリ言語で実装された `runtime·gettid` 関数を通じて行われます。アセンブリを使用するのは、システムコールを直接発行するため、およびGoランタイムの低レベルな部分でOSとの直接的なインタフェースが必要だからです。
2.  **`minit()` 関数での `m.procid` の設定**: 新しいM（OSスレッド）が初期化される際に呼び出される `minit()` 関数内で、上記で実装された `gettid()` 関数を呼び出し、その結果を `_g_.m.procid` に代入します。`_g_` は現在のゴルーチンを表し、`_g_.m` はそのゴルーチンが実行されているM（OSスレッド）を指します。

この変更により、Goランタイムが管理するすべてのOSスレッド（Go自身が作成したもの、およびCgoが作成したもの）について、`m.procid` が常にそのスレッドの正確なTIDを保持するようになります。これにより、デバッガは `m.procid` を参照するだけで、GoのMとOSのスレッドを確実にマッピングできるようになります。

特に、`cgo created the thread` というコメントは重要です。CgoはGoランタイムのスケジューラをバイパスしてOSスレッドを作成することがあります。これらのスレッドもGoランタイムのMとして扱われる必要があるため、`minit()` で `procid` を設定することは、Goランタイムがこれらの外部から作成されたスレッドを適切に追跡し、デバッガがそれらを認識できるようにするために不可欠です。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下のファイルに集中しています。

1.  **`src/runtime/os1_linux.go`**:
    *   `func gettid() uint32` という関数宣言が追加されました。これは、アセンブリで実装される `gettid` 関数のGo側のシグネチャです。
    *   `minit()` 関数内に以下の行が追加されました。
        ```go
        // for debuggers, in case cgo created the thread
        _g_.m.procid = uint64(gettid())
        ```
        これにより、新しいMが初期化される際に、そのMの `procid` フィールドに現在のOSスレッドのTIDが設定されます。

2.  **`src/runtime/sys_linux_386.s`**:
    *   `TEXT runtime·gettid(SB),NOSPLIT,$0-4` という新しいアセンブリ関数が追加されました。
    *   この関数は、`$224` (Linux 386アーキテクチャにおける `gettid` システムコール番号) を `AX` レジスタにロードし、`CALL *runtime·_vdso(SB)` または `SYSCALL` を通じてシステムコールを発行し、結果を `ret+0(FP)` に格納して返します。

3.  **`src/runtime/sys_linux_amd64.s`**:
    *   `TEXT runtime·gettid(SB),NOSPLIT,$0-4` という新しいアセンブリ関数が追加されました。
    *   この関数は、`$186` (Linux AMD64アーキテクチャにおける `gettid` システムコール番号) を `AX` レジスタにロードし、`SYSCALL` を通じてシステムコールを発行し、結果を `ret+0(FP)` に格納して返します。

4.  **`src/runtime/sys_linux_arm.s`**:
    *   `TEXT runtime·gettid(SB),NOSPLIT,$0-4` という新しいアセンブリ関数が追加されました。
    *   この関数は、`$SYS_gettid` (ARMアーキテクチャにおける `gettid` システムコール番号) を `R7` レジスタにロードし、`SWI $0` を通じてシステムコールを発行し、結果を `R0` から `ret+0(FP)` に格納して返します。

5.  **`src/runtime/sys_linux_arm64.s`**:
    *   `TEXT runtime·gettid(SB),NOSPLIT,$0-4` という新しいアセンブリ関数が追加されました。
    *   この関数は、`$SYS_gettid` (ARM64アーキテクチャにおける `gettid` システムコール番号) を `R8` レジスタにロードし、`SVC` を通じてシステムコールを発行し、結果を `R0` から `ret+0(FP)` に格納して返します。

6.  **`src/runtime/sys_linux_ppc64x.s`**:
    *   `TEXT runtime·gettid(SB),NOSPLIT,$0-4` という新しいアセンブリ関数が追加されました。
    *   この関数は、`SYSCALL $SYS_gettid` を通じてシステムコールを発行し、結果を `R3` から `ret+0(FP)` に格納して返します。

## コアとなるコードの解説

### `src/runtime/os1_linux.go` の変更

`os1_linux.go` はLinux固有のOSインタフェースをGoランタイムに提供するファイルです。
`func gettid() uint32` の宣言は、Goコンパイラに対して `gettid` という名前の関数が存在し、`uint32` 型の値を返すことを伝えます。この関数の実際の定義はアセンブリファイルにあります。

`minit()` 関数は、新しいOSスレッド（GoランタイムのM）が起動する際に一度だけ呼び出される初期化関数です。この関数内で `_g_.m.procid = uint64(gettid())` が実行されることで、現在初期化中のMに対応するOSスレッドのTIDが取得され、そのMの `procid` フィールドに格納されます。`_g_` は現在のゴルーチンを指すポインタであり、`_g_.m` はそのゴルーチンが実行されているM（OSスレッド）を指します。

この変更は、GoランタイムがOSスレッドを起動するたびに、そのスレッドのTIDを `m.procid` に記録することを保証します。これにより、デバッガはGoランタイムの内部構造を検査する際に、常に正確なOSスレッドIDを参照できるようになります。特に、CgoがGoランタイムの制御外でスレッドを作成した場合でも、そのスレッドがGoランタイムのMとして初期化される際に `minit()` が呼び出され、`procid` が正しく設定されるため、デバッグの一貫性が保たれます。

### `src/runtime/sys_linux_*.s` の変更

これらのファイルは、各CPUアーキテクチャ（386, amd64, arm, arm64, ppc64x）向けのLinuxシステムコールをGoランタイムから呼び出すためのアセンブリコードを含んでいます。

`TEXT runtime·gettid(SB),NOSPLIT,$0-4` は、Goランタイムの `gettid` 関数をアセンブリで定義しています。`NOSPLIT` はこの関数がスタックを分割しないことを示し、`$0-4` はスタックフレームサイズが0バイトで、戻り値が4バイトであることを示します。

各アセンブリ関数は、以下の基本的な手順を実行します。

1.  **システムコール番号のロード**: 各アーキテクチャ固有の `gettid` システムコール番号を適切なレジスタ（例: 386/amd64では `AX`、ARMでは `R7`、ARM64では `R8`）にロードします。
2.  **システムコールの発行**: `CALL *runtime·_vdso(SB)` (386), `SYSCALL` (amd64, ppc64x), `SWI $0` (arm), `SVC` (arm64) などの命令を使用して、Linuxカーネルにシステムコールを発行します。`_vdso` は、ユーザー空間からシステムコールを高速に呼び出すためのメカニズムです。
3.  **戻り値の取得**: システムコールが完了すると、TIDが特定のレジスタ（例: 386/amd64/arm/arm64では `AX`/`R0`、ppc64xでは `R3`）に格納されます。
4.  **戻り値の格納**: 取得したTIDをGoの呼び出し規約に従って戻り値として格納します（例: `MOVL AX, ret+0(FP)`）。

これらのアセンブリ実装により、GoランタイムはLinuxの `gettid()` システムコールを直接、かつ効率的に呼び出すことができ、`m.procid` を正確なOSスレッドIDで更新することが可能になります。

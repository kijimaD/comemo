## 変更の背景

このコミットの背景には、Go言語の歴史における重要なマイルストーンであるGo 1.5リリース（2015年）があります。Go 1.5では、それまでC言語とアセンブリ言語で書かれていたGoランタイムとコンパイラが、大部分がGo言語自体で書き直されました。このプロセスは「セルフホスティング」または「ブートストラッピング」と呼ばれ、GoがGo自身をコンパイルできるようになることを意味しました。

この大規模な変換作業の後、以前のC言語ベースのランタイムとの互換性や移行のために存在していた一部のコードが不要になりました。具体的には、C言語の関数をGoから呼び出すためのスタブや、Go言語で再実装された機能に対する古いラッパー関数などが挙げられます。このコミットは、そうした残骸を削除し、コードベースを整理することで、ランタイムの可読性、保守性、そして効率性を向上させることを目的としています。

特に、`_newm`関数のリネームや`newsysmon`ラッパーの削除は、ランタイムのスケジューラとシステムモニタリングのコアロジックがGo言語で直接扱えるようになったことを示唆しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とGo 1.5における変更の重要性を把握しておく必要があります。

1.  **Goランタイム (Go Runtime)**:
    Goプログラムの実行を管理する低レベルのシステムです。これには、ガベージコレクション (GC)、スケジューラ（ゴルーチンとOSスレッドのマッピング）、メモリ管理、チャネル操作、ネットワークI/Oなどが含まれます。Go 1.5以前は、これらの機能の一部がC言語で実装されていました。

2.  **G-M-Pスケジューラモデル**:
    Goのスケジューラは、G (Goroutine)、M (Machine/OS Thread)、P (Processor/Logical Processor) の3つの主要な要素で構成されます。
    *   **G (Goroutine)**: Go言語の軽量な並行処理単位。
    *   **M (Machine)**: オペレーティングシステムのスレッド。GoランタイムはMをOSに要求し、その上でGoコードを実行します。
    *   **P (Processor)**: MがGoコードを実行するために必要な論理プロセッサ。PはMとGを仲介し、MがGを実行するためのコンテキストを提供します。

3.  **`newm`関数**:
    Goランタイムにおいて、新しいOSスレッド（M）を作成するための重要な関数です。`sysmon`のような特別なランタイム関数を実行するためや、Goコードを実行するための新しいMが必要な場合に呼び出されます。

4.  **`sysmon` (System Monitor)**:
    Goランタイム内で独立して動作する特別なOSスレッドです。G-M-PモデルのPに縛られずにバックグラウンドで定期的に実行され、以下の重要なタスクを担います。
    *   **タイマー管理**: アプリケーションによって設定されたタイマーのチェックと起動。
    *   **ネットワークポーリング**: ネットワークI/Oでブロックされているゴルーチンの処理。
    *   **ガベージコレクション (GC) のトリガー**: GCが長時間実行されていない場合にGCを強制的に開始。
    *   **ゴルーチンのプリエンプション**: 長時間実行されているゴルーチンを強制的に中断させ、他のゴルーチンにCPU時間を割り当てることで、公平なスケジューリングを保証します。

5.  **Go 1.5のCからGoへの変換 (Self-hosting)**:
    Go 1.5の最大の変更点の一つは、GoランタイムとコンパイラがC言語からGo言語に書き換えられたことです。これにより、Go開発者はGo言語の知識だけでランタイムの内部を理解し、貢献できるようになりました。また、Cgo呼び出しのオーバーヘッドが削減され、Go言語の機能（例えば、Goの並行性モデル）をランタイム内でより効果的に活用できるようになりました。この変換は、Go言語の成熟度と独立性を示す重要なステップでした。

## 技術的詳細

このコミットは、GoランタイムのCからGoへの変換後の「クリーンアップ」という性質上、新しい機能の追加ではなく、既存のコードの整理と最適化に焦点を当てています。

主要な変更点は以下の通りです。

1.  **`_newm`から`newm`への関数名変更**:
    Go言語では、通常、アンダースコア (`_`) で始まる関数名や変数名は、内部的な利用やエクスポートされないことを示す慣習があります。このコミットでは、`src/runtime/proc1.go`内で定義されていた`_newm`関数が`newm`にリネームされています。これは、`newm`がGoランタイムのコア機能として確立され、その内部的な性質が以前ほど強調されなくなったことを示唆しています。Go言語でランタイムが実装されたことで、C言語との境界を意識する必要が薄れ、よりGoらしい命名規則に移行したと考えられます。

2.  **`newsysmon`ラッパー関数の削除**:
    `src/runtime/proc1.go`から`newsysmon`関数が削除されました。この関数は単に`_newm(sysmon, nil)`を呼び出すラッパーでした。`src/runtime/proc.go`では、`systemstack(newsysmon)`の呼び出しが`systemstack(func() { newm(sysmon, nil) })`というインライン関数に置き換えられています。これは、`newsysmon`という独立したラッパー関数が不要になり、`sysmon`を起動するロジックがより直接的になったことを意味します。ランタイムのGo化により、このようなシンプルなラッパーが冗長になったと考えられます。

3.  **`src/runtime/stubs3.go`の削除と関数宣言の移動**:
    `src/runtime/stubs3.go`ファイル全体が削除されました。このファイルは、Plan 9オペレーティングシステム向けの`close`と`open`関数のGo言語での宣言（スタブ）を含んでいました。これらの関数宣言は、`src/runtime/os_plan9.go`に移動されました。これは、特定のOS向けの低レベルな関数宣言を、そのOS固有のファイルに集約するという、より論理的なファイル構造への整理を反映しています。`//go:noescape`ディレクティブは、これらの関数がGoのスタックフレームを必要としない（つまり、アセンブリで実装されているか、Goの呼び出し規約に従わない）ことを示しており、Goランタイムの低レベルな部分とOSのインタフェースを定義する上で重要です。

これらの変更は、GoランタイムのコードベースがGo言語で統一された結果として、よりクリーンで、よりGoらしい構造へと進化していることを示しています。

## コアとなるコードの解説

このコミットのコード変更は、GoランタイムのGo言語への移行が完了した後の「整理整頓」を明確に示しています。

*   **`_newm`から`newm`へのリネーム**:
    `src/runtime/proc1.go`における`_newm`関数の定義が`newm`に変更され、それに伴いランタイム内のすべての呼び出し箇所が更新されました。この変更は、`newm`がもはや内部的な実装の詳細を示すアンダースコアプレフィックスを必要としないほど、Goランタイムの標準的な一部となったことを意味します。これは、Go言語でランタイムが完全に実装されたことで、C言語との境界を意識した命名規則が不要になった結果と考えられます。`newm`は、Goのスケジューラが新しいOSスレッド（M）を起動する際に使用する基盤となる関数であり、その名前の簡素化は、Goランタイムの設計がより統一され、洗練されたことを示唆しています。

*   **`newsysmon`ラッパーの削除とインライン化**:
    `src/runtime/proc1.go`から`newsysmon`関数が削除され、`src/runtime/proc.go`でのその呼び出しが`systemstack(func() { newm(sysmon, nil) })`という形でインライン化されました。`newsysmon`は、`sysmon`（システムモニタースレッド）を起動するために`_newm`を呼び出すだけのシンプルなラッパーでした。ランタイムがGo言語で書かれるようになったことで、このような薄いラッパーは冗長になり、直接的な関数呼び出しやインライン関数で代替できるようになりました。これにより、コードの階層が浅くなり、`sysmon`の起動ロジックがより明確になります。`sysmon`はGoランタイムの健全性を維持するために不可欠なバックグラウンドスレッドであり、その起動パスの簡素化は、ランタイムの全体的な設計の成熟を反映しています。

*   **`stubs3.go`の削除とPlan 9固有の関数宣言の移動**:
    `src/runtime/stubs3.go`ファイルが完全に削除され、その中にあったPlan 9オペレーティングシステム向けの`close`と`open`関数の宣言が`src/runtime/os_plan9.go`に移動されました。これは、OS固有の低レベルな関数宣言を、そのOSのランタイムファイルに集約するという、より整理されたモジュール構造への移行を示しています。これにより、コードベースの関連性が高まり、特定のOS向けのコードを見つけやすくなります。`//go:noescape`ディレクティブは、これらの関数がGoのスタックフレームを必要としない（通常はアセンブリで実装されている）ことを示しており、GoランタイムがOSとどのようにインタフェースするかという低レベルな詳細を維持しつつ、コードの整理を進めていることがわかります。

これらの変更は、Go 1.5におけるCからGoへのランタイム変換が単なる言語の置き換えに留まらず、コードベース全体の設計と構造の改善にも繋がったことを示しています。

# [インデックス 21083] ファイルの概要

このコミットは、Goランタイムにおける`scalararg`と`ptrarg`という、M（OSスレッド）のスタック上で引数を渡すためのフィールドを削除し、それらの使用箇所をクロージャに置き換えることを目的としています。また、`onM`および`onM_signalok`関数を`systemstack`という単一の関数に統合し、その名称をより正確なものに変更しています。これにより、シグナル安全性、型安全性、およびコードの可読性が向上し、Goランタイムの堅牢性が高まります。

## 変更の背景

このコミットの主な動機は、Goランタイム内部で使用されていた`scalararg`と`ptrarg`という特殊な引数渡しメカニズムが抱えていた複数の問題点を解決することです。

1.  **シグナル安全性（Signal Safety）の欠如**: `scalararg`と`ptrarg`は、Goコードがそれらを埋めている最中にシグナルによって中断される可能性がありました。シグナルハンドラが実行され、その中で再び`scalararg`や`ptrarg`を使用するGoコードが呼び出されると、以前の値が上書きされてしまい、データ破損や予期せぬ動作を引き起こす可能性がありました。この問題に対処するため、一時的に`onM_signalok`という関数が導入されましたが、これは呼び出し元が`scalararg`と`ptrarg`の古い値を呼び出し後に復元することを保証するという、複雑でエラーを起こしやすいものでした。

2.  **型安全性（Type Safety）の欠如とエラーの発生しやすさ**: `scalararg`と`ptrarg`は型付けされておらず、`uintptr`や`unsafe.Pointer`として扱われていました。これにより、コンパイル時に型チェックが行われず、ランタイムエラーやデバッグが困難なバグの原因となっていました。

3.  **Cコードとの関連性**: `scalararg`と`ptrarg`は、主にCコードからGoコードを呼び出す際に必要とされていました。しかし、GoランタイムがGo言語で完全に書き換えられるにつれて、これらのC言語由来のメカニズムの必要性は薄れていました。コミットメッセージにも「And there's no more C code.」とあるように、Cコードの残存が問題を引き起こしていました。

4.  **ライトバリア（Write Barrier）との相互作用**: `m.ptrarg[0] = p`のような呼び出しシーケンスはヒープポインタの割り当てであり、ガベージコレクション（GC）のライトバリアをトリガーします。このライトバリア自体も`onM`を使用していたため、シグナルハンドラから呼び出された場合と同様の問題を抱えていました。以前は古い値を保存・復元したり、`onM_signalok`を呼び出すことで回避していましたが、これは根本的な解決策ではなく、バグの温床となっていました。

5.  **`onM`の名称の誤解**: `onM`という関数名と「Mスタック」という表現は、ほとんどのシステムでM（OSスレッド）がメインスレッドスタックとシグナルハンドリングスタックの2つのシステムスタックを持つため、誤解を招くものでした。この名称は、Goランタイムのスタック管理の実際の挙動を正確に反映していませんでした。

これらの問題に対処するため、`scalararg`と`ptrarg`を完全に削除し、その機能をクロージャに置き換え、`onM`関連の関数をより汎用的で正確な`systemstack`に統合することが決定されました。また、`funcline`関数のシグネチャ変更も、C言語由来の古い設計をGoらしい設計に修正する一環として行われました。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの基本的な概念と、OSレベルのいくつかのメカニズムについて知っておく必要があります。

1.  **Goランタイムのスケジューラ (GMPモデル)**:
    *   **G (Goroutine)**: Go言語の軽量スレッド。Goプログラムの並行処理の単位です。Goランタイムによって管理されるスタックを持ちます。
    *   **M (Machine)**: OSスレッド。Goランタイムは、OSスレッドを抽象化したMを管理します。MはOSによってスケジューリングされ、Gを実行します。各Mは、Goコードを実行するためのGoスタック（Gのスタック）とは別に、ランタイム内部の処理（GC、スケジューリングなど）を実行するためのシステムスタック（g0スタック、gsignalスタック）を持ちます。
    *   **P (Processor)**: 論理プロセッサ。GをMに割り当てるためのコンテキストです。PはMとGを仲介し、Gの実行に必要なリソースを提供します。

2.  **スタックの種類**:
    *   **Goスタック (Goroutine Stack)**: 各Goroutineが持つスタック。Goの関数呼び出しやローカル変数がここに積まれます。Goスタックは動的に伸縮します。
    *   **g0スタック (System Stack)**: 各M（OSスレッド）が持つシステムスタック。Goランタイムの内部処理（スケジューラ、GC、システムコールなど）が実行される際に使用されます。このスタックは固定サイズで、Goスタックとは独立しています。
    *   **gsignalスタック (Signal Handling Stack)**: シグナルハンドラが実行される際に使用される特殊なシステムスタック。これもMに紐付けられています。

3.  **`onM`関数とその役割**:
    *   `onM`は、Goランタイム内部で、現在のGoroutineのスタック（Goスタック）からMのシステムスタック（g0スタック）に切り替えて、特定の関数（引数として渡されるクロージャ）を実行するためのメカニズムでした。これは、Goスタックでは実行できない、あるいは実行すべきではない低レベルのランタイム操作（例えば、メモリ割り当て、GC関連の処理、システムコールなど）を行うために使用されました。
    *   `onM_signalok`は、`onM`の派生で、シグナルハンドラから呼び出される可能性があるコードのために設計されました。これは、`scalararg`や`ptrarg`の値を呼び出し元が保存・復元することを前提としていました。

4.  **`scalararg`と`ptrarg`**:
    *   これらは`m`構造体（Mを表すランタイム内部の構造体）のフィールドであり、`onM`を介してMのシステムスタック上で実行される関数に引数を渡すための、一時的なストレージとして使用されていました。
    *   `scalararg`はスカラー値（整数など）を、`ptrarg`はポインタ値を渡すために使われました。
    *   これらは型付けされておらず、`uintptr`や`unsafe.Pointer`として扱われたため、コンパイル時の型チェックの恩恵を受けられませんでした。

5.  **シグナルハンドラとシグナル安全性**:
    *   シグナルハンドラは、OSからのシグナル（例えば、セグメンテーション違反、タイマー割り込みなど）を受け取った際に非同期に実行される関数です。
    *   シグナルハンドラは、Goコードの任意の時点で割り込む可能性があります。そのため、シグナルハンドラ内で実行されるコードは「シグナル安全」である必要があります。シグナル安全なコードとは、割り込みが発生したGoコードの状態を破壊せず、かつ、シグナルハンドラ自身の実行が他のGoコードの実行に影響を与えないことを意味します。
    *   `scalararg`と`ptrarg`がシグナル安全でなかったのは、シグナルハンドラがそれらの値を上書きしてしまう可能性があったためです。

6.  **ライトバリア (Write Barrier)**:
    *   Goのガベージコレクション（GC）は、並行GCを採用しています。これは、GCがGoプログラムの実行と並行して動作することを意味します。
    *   ライトバリアは、GCが正しく動作するために必要なメカニズムの一つです。Goプログラムがヒープ上のポインタを更新する際に、GCがその変更を追跡できるように、ライトバリアが挿入されます。これにより、GCがオブジェクトグラフを正確にスキャンし、到達可能なオブジェクトを特定できます。
    *   コミットメッセージにあるように、`m.ptrarg[0] = p`のような操作がライトバリアをトリガーし、そのライトバリアがさらに`onM`を呼び出すという循環的な問題が発生していました。

7.  **クロージャ (Closures)**:
    *   Goのクロージャは、それが定義された環境の変数を「キャプチャ」できる関数です。
    *   このコミットでは、`scalararg`や`ptrarg`を介して引数を渡す代わりに、クロージャを使用して必要な値をキャプチャし、Mのシステムスタック上で実行される関数に渡すように変更されました。これにより、型安全性が向上し、コードの可読性も高まります。

## 技術的詳細

このコミットは、Goランタイムの低レベルなスタック管理と引数渡しメカニズムに根本的な変更を加えています。

1.  **`scalararg`と`ptrarg`の削除**:
    *   `src/runtime/runtime2.go`から`m`構造体の`scalararg`と`ptrarg`フィールドが削除されました。
    *   これにより、これらのフィールドに直接アクセスして引数を渡す古いC言語スタイルのアプローチが完全に廃止されました。
    *   これらのフィールドを使用していたすべての箇所（例: `src/runtime/malloc.go`, `src/runtime/mem.go`, `src/runtime/cpuprof.go`など）が、引数をクロージャのキャプチャ変数として渡すように変更されました。例えば、`setcpuprofilerate`関数では、`g.m.scalararg[0] = uintptr(hz)`と`onM(setcpuprofilerate_m)`の代わりに、`systemstack(func() { setcpuprofilerate_m(hz) })`という形式が採用されました。これにより、`hz`の値がクロージャによってキャプチャされ、`setcpuprofilerate_m`に渡されます。

2.  **`onM`と`onM_signalok`の`systemstack`への統合と名称変更**:
    *   `src/runtime/stubs.go`から`onM`と`onM_signalok`の宣言が削除され、代わりに`systemstack`という単一の関数が導入されました。
    *   アセンブリファイル（`src/runtime/asm_386.s`, `src/runtime/asm_amd64.s`, `src/runtime/asm_amd64p32.s`, `src/runtime/asm_arm.s`）において、`onM`と`onM_signalok`の実装が`systemstack`に統合されました。
    *   `systemstack`は、呼び出し元のGoroutineがg0スタック、gsignalスタック、または通常のGoスタックのいずれにいるかに応じて、適切なスタック切り替えロジックを実行します。g0スタックまたはgsignalスタックにいる場合は、直接関数を呼び出します。通常のGoスタックにいる場合は、g0スタックに切り替えてから関数を呼び出し、完了後に元のGoスタックに戻ります。
    *   `switchtoM`というダミーのルーチンも`systemstack_switch`に名称変更されました。これは、スタックトレースの終端を識別するために使用されます。
    *   `onM`という名称が「Mスタック」という誤解を招く表現に基づいていたため、より正確に「システムスタック」上で実行されることを示す`systemstack`に変更されました。これにより、Goランタイムのスタック管理の概念がより明確になりました。

3.  **`funcline`関数のシグネチャ変更**:
    *   `src/runtime/symtab.go`および関連ファイル（`src/runtime/extern.go`, `src/runtime/heapdump.go`, `src/runtime/race.go`, `src/runtime/traceback.go`）において、`funcline`および`funcline1`関数のシグネチャが変更されました。
    *   以前は、ファイル名を`*string`ポインタとして受け取り、そのポインタが指すメモリにファイル名を書き込むC言語スタイルのインターフェースでした。
    *   変更後は、ファイル名を戻り値として直接返すGo言語らしいインターフェースになりました（例: `func funcline(f *_func, targetpc uintptr) (file string, line int32)`）。
    *   この変更は、`ptrarg`/`scalararg`/`onM`のクリーンアップ後に、コンパイラが`*string`引数のエスケープ解析で誤った陽性（false positive）を報告し始めたことがきっかけとなりました。コンパイラのバグの可能性も示唆されていますが、Goらしいコードに書き換えることで問題を回避しました。

4.  **シグナル関連コードの簡素化**:
    *   `src/runtime/signal.go`ファイルが削除されました。このファイルには、`scalararg`を使用してシグナルを有効/無効にするための`sigenable_m`と`sigdisable_m`が含まれていました。
    *   `src/runtime/sigqueue.go`では、`sigenable_go`と`sigdisable_go`が削除され、直接`sigenable`と`sigdisable`を呼び出すように変更されました。これは、`scalararg`が不要になったため、中間層の関数が不要になったことを意味します。

これらの変更により、Goランタイムの内部コードはよりGo言語のイディオムに沿ったものとなり、シグナル安全性、型安全性、および全体的な堅牢性が向上しました。特に、`scalararg`と`ptrarg`の削除は、GoランタイムがC言語の遺産からさらに脱却し、純粋なGoコードとして進化する上で重要な一歩でした。

## コアとなるコードの解説

このコミットのコアとなる変更は、`m`構造体から`scalararg`と`ptrarg`を削除し、`onM`を`systemstack`に置き換えることです。ここでは、その変更がどのように行われたか、特に`src/runtime/stubs.go`と`src/runtime/asm_amd64.s`の変更を例に解説します。

### `src/runtime/stubs.go`の変更

変更前:
```go
// onM switches from the g to the g0 stack and invokes fn().
// ... (コメント省略) ...
//go:noescape
func onM(fn func())

// onMsignal is like onM but is allowed to be used in code that
// might run on the gsignal stack.
// ... (コメント省略) ...
//go:noescape
func onM_signalok(fn func())

func badonm() {
	gothrow("onM called from signal goroutine")
}

func switchtoM()
```

変更後:
```go
// systemstack runs fn on a system stack.
// If systemstack is called from the per-OS-thread (g0) stack, or
// if systemstack is called from the signal handling (gsignal) stack,
// systemstack calls fn directly and returns.
// Otherwise, systemstack is being called from the limited stack
// of an ordinary goroutine. In this case, systemstack switches
// to the per-OS-thread stack, calls fn, and switches back.
// It is common to use a func literal as the argument, in order
// to share inputs and outputs with the code around the call
// to system stack:
//
//	... set up y ...
//	systemstack(func() {
//		x = bigcall(y)
//	})
//	... use x ...
//
//go:noescape
func systemstack(fn func())

func badsystemstack() {
	gothrow("systemstack called from unexpected goroutine")
}

func systemstack_switch()
```

この変更により、`onM`と`onM_signalok`という2つの異なる関数が`systemstack`という単一の関数に統合されました。`systemstack`のコメントは、その動作原理と、クロージャを使用して引数を渡す一般的な使用パターンを明確に説明しています。`scalararg`や`ptrarg`のようなMのフィールドを介した引数渡しは不要になり、Goのクロージャのセマンティクスに沿った、より安全で型チェック可能な方法が採用されました。

### `src/runtime/asm_amd64.s`の変更 (抜粋)

変更前 (`onM`と`onM_signalok`の分離):
```assembly
// func onM_signalok(fn func())
TEXT runtime·onM_signalok(SB), NOSPLIT, $0-8
	MOVQ	fn+0(FP), DI	// DI = fn
	get_tls(CX)
	MOVQ	g(CX), AX	// AX = g
	MOVQ	g_m(AX), BX	// BX = m

	MOVQ	m_gsignal(BX), DX	// DX = gsignal
	CMPQ	AX, DX
	JEQ	ongsignal
	JMP	runtime·onM(SB)

ongsignal:
	MOVQ	fn+0(FP), DI	// DI = fn
	MOVQ	DI, DX
	MOVQ	0(DI), DI
	CALL	DI
	RET

// func onM(fn func())
TEXT runtime·onM(SB), NOSPLIT, $0-8
	MOVQ	fn+0(FP), DI	// DI = fn
	get_tls(CX)
	MOVQ	g(CX), AX	// AX = g
	MOVQ	g_m(AX), BX	// BX = m

	MOVQ	m_g0(BX), DX	// DX = g0
	CMPQ	AX, DX
	JEQ	onm

	MOVQ	m_curg(BX), BP
	CMPQ	AX, BP
	JEQ	oncurg
	
	// Not g0, not curg. Must be gsignal, but that's not allowed.
	// Hide call from linker nosplit analysis.
	MOVQ	$runtime·badonm(SB), AX
	CALL	AX

oncurg:
	// save our state in g->sched.  Pretend to
	// be switchtoM if the G stack is scanned.
	MOVQ	$runtime·switchtoM(SB), BP
	MOVQ	BP, (g_sched+gobuf_pc)(AX)
	MOVQ	SP, (g_sched+gobuf_sp)(AX)
	MOVQ	AX, (g_sched+gobuf_g)(AX)

	// switch to g0
	MOVQ	DX, g(CX)
	MOVQ	(g_sched+gobuf_sp)(DX), BX
	// make it look like mstart called onM on g0, to stop traceback
	SUBQ	$8, BX
	MOVQ	$runtime·mstart(SB), DX
	MOVQ	DX, 0(BX)
	MOVQ	BX, SP
	CALL	0(DI) // call fn
	// restore g
	MOVQ	AX, g(CX)
	MOVQ	(g_sched+gobuf_sp)(AX), SP
	MOVQ	$0, (g_sched+gobuf_pc)(AX)
	MOVQ	$0, (g_sched+gobuf_sp)(AX)
	RET

onm:
	// already on m stack, just call directly
	MOVQ	DI, DX
	MOVQ	0(DI), DI
	CALL	DI
	RET
```

```assembly
// func systemstack(fn func())
TEXT runtime·systemstack(SB), NOSPLIT, $0-8
	MOVQ	fn+0(FP), DI	// DI = fn
	get_tls(CX)
	MOVQ	g(CX), AX	// AX = g
	MOVQ	g_m(AX), BX	// BX = m

	MOVQ	m_gsignal(BX), DX	// DX = gsignal
	CMPQ	AX, DX
	JEQ	noswitch

	MOVQ	m_g0(BX), DX	// DX = g0
	CMPQ	AX, DX
	JEQ	noswitch

	MOVQ	m_curg(BX), BP
	CMPQ	AX, BP
	JEQ	switch
	
	// Bad: g is not gsignal, not g0, not curg. What is it?
	MOVQ	$runtime·badsystemstack(SB), AX
	CALL	AX

switch:
	// save our state in g->sched.  Pretend to
	// be systemstack_switch if the G stack is scanned.
	MOVQ	$runtime·systemstack_switch(SB), BP
	MOVQ	BP, (g_sched+gobuf_pc)(AX)
	MOVQ	SP, (g_sched+gobuf_sp)(AX)
	MOVQ	AX, (g_sched+gobuf_g)(AX)

	// switch to g0
	MOVQ	DX, g(CX)
	MOVQ	(g_sched+gobuf_sp)(DX), BX
	// make it look like mstart called systemstack on g0, to stop traceback
	SUBQ	$8, BX
	MOVQ	$runtime·mstart(SB), DX
	MOVQ	DX, 0(BX)
	MOVQ	BX, SP
	CALL	0(DI) // call fn
	// restore g
	MOVQ	AX, g(CX)
	MOVQ	(g_sched+gobuf_sp)(AX), SP
	MOVQ	$0, (g_sched+gobuf_pc)(AX)
	MOVQ	$0, (g_sched+gobuf_sp)(AX)
	RET

noswitch:
	// already on system stack, just call directly
	MOVQ	DI, DX
	MOVQ	0(DI), DI
	CALL	DI
	RET
```

このアセンブリコードの変更は、`onM`と`onM_signalok`のロジックが`systemstack`という単一のエントリポイントに統合されたことを示しています。

*   `systemstack`はまず、現在のGoroutine (`AX`) が`gsignal`スタック (`DX`) または`g0`スタック (`DX`) 上にいるかどうかをチェックします。もしそうであれば、`noswitch`ラベルにジャンプし、スタック切り替えなしで直接関数`fn`を呼び出します。
*   現在のGoroutineが`curg`（通常のGoスタック上のGoroutine）である場合、`switch`ラベルにジャンプします。ここでは、現在のGoroutineの状態（PC、SP、G）を保存し、`g0`スタックに切り替えます。そして、`fn`を呼び出し、完了後に元のGoroutineスタックに戻ります。
*   それ以外の不正な状態であれば、`badsystemstack`を呼び出してパニックします。

この統合により、ランタイムのスタック管理ロジックが簡素化され、`onM_signalok`の複雑なセマンティクス（呼び出し元が値を保存・復元する責任）が不要になりました。また、`switchtoM`の参照も`systemstack_switch`に更新され、命名の一貫性が保たれています。

全体として、このコミットはGoランタイムの内部をよりクリーンで、安全で、Goらしい設計に進化させるための重要な一歩であり、特に低レベルのスタック管理と引数渡しにおける長年の問題を解決しました。

## 変更の背景

このコミットの主な動機は、Goランタイム内部で使用されていた`scalararg`と`ptrarg`という特殊な引数渡しメカニズムが抱えていた複数の問題点を解決することです。

1.  **シグナル安全性（Signal Safety）の欠如**: `scalararg`と`ptrarg`は、Goコードがそれらを埋めている最中にシグナルによって中断される可能性がありました。シグナルハンドラが実行され、その中で再び`scalararg`や`ptrarg`を使用するGoコードが呼び出されると、以前の値が上書きされてしまい、データ破損や予期せぬ動作を引き起こす可能性がありました。この問題に対処するため、一時的に`onM_signalok`という関数が導入されましたが、これは呼び出し元が`scalararg`と`ptrarg`の古い値を呼び出し後に復元することを保証するという、複雑でエラーを起こしやすいものでした。

2.  **型安全性（Type Safety）の欠如とエラーの発生しやすさ**: `scalararg`と`ptrarg`は型付けされておらず、`uintptr`や`unsafe.Pointer`として扱われていました。これにより、コンパイル時に型チェックが行われず、ランタイムエラーやデバッグが困難なバグの原因となっていました。

3.  **Cコードとの関連性**: `scalararg`と`ptrarg`は、主にCコードからGoコードを呼び出す際に必要とされていました。しかし、GoランタイムがGo言語で完全に書き換えられるにつれて、これらのC言語由来のメカニズムの必要性は薄れていました。コミットメッセージにも「And there's no more C code.」とあるように、Cコードの残存が問題を引き起こしていました。

4.  **ライトバリア（Write Barrier）との相互作用**: `m.ptrarg[0] = p`のような呼び出しシーケンスはヒープポインタの割り当てであり、ガベージコレクション（GC）のライトバリアをトリガーします。このライトバリア自体も`onM`を使用していたため、シグナルハンドラから呼び出された場合と同様の問題を抱えていました。以前は古い値を保存・復元したり、`onM_signalok`を呼び出すことで回避していましたが、これは根本的な解決策ではなく、バグの温床となっていました。

5.  **`onM`の名称の誤解**: `onM`という関数名と「Mスタック」という表現は、ほとんどのシステムでM（OSスレッド）がメインスレッドスタックとシグナルハンドリングスタックの2つのシステムスタックを持つため、誤解を招くものでした。この名称は、Goランタイムのスタック管理の実際の挙動を正確に反映していませんでした。

これらの問題に対処するため、`scalararg`と`ptrarg`を完全に削除し、その機能をクロージャに置き換え、`onM`関連の関数をより汎用的で正確な`systemstack`に統合することが決定されました。また、`funcline`関数のシグネチャ変更も、C言語由来の古い設計をGoらしい設計に修正する一環として行われました。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの基本的な概念と、OSレベルのいくつかのメカニズムについて知っておく必要があります。

1.  **Goランタイムのスケジューラ (GMPモデル)**:
    *   **G (Goroutine)**: Go言語の軽量スレッド。Goプログラムの並行処理の単位です。Goランタイムによって管理されるスタックを持ちます。
    *   **M (Machine)**: OSスレッド。Goランタイムは、OSスレッドを抽象化したMを管理します。MはOSによってスケジューリングされ、Gを実行します。各Mは、Goコードを実行するためのGoスタック（Gのスタック）とは別に、ランタイム内部の処理（GC、スケジューリングなど）を実行するためのシステムスタック（g0スタック、gsignalスタック）を持ちます。
    *   **P (Processor)**: 論理プロセッサ。GをMに割り当てるためのコンテキストです。PはMとGを仲介し、Gの実行に必要なリソースを提供します。

2.  **スタックの種類**:
    *   **Goスタック (Goroutine Stack)**: 各Goroutineが持つスタック。Goの関数呼び出しやローカル変数がここに積まれます。Goスタックは動的に伸縮します。
    *   **g0スタック (System Stack)**: 各M（OSスレッド）が持つシステムスタック。Goランタイムの内部処理（スケジューラ、GC、システムコールなど）が実行される際に使用されます。このスタックは固定サイズで、Goスタックとは独立しています。
    *   **gsignalスタック (Signal Handling Stack)**: シグナルハンドラが実行される際に使用される特殊なシステムスタック。これもMに紐付けられています。

3.  **`onM`関数とその役割**:
    *   `onM`は、Goランタイム内部で、現在のGoroutineのスタック（Goスタック）からMのシステムスタック（g0スタック）に切り替えて、特定の関数（引数として渡されるクロージャ）を実行するためのメカニズムでした。これは、Goスタックでは実行できない、あるいは実行すべきではない低レベルのランタイム操作（例えば、メモリ割り当て、GC関連の処理、システムコールなど）を行うために使用されました。
    *   `onM_signalok`は、`onM`の派生で、シグナルハンドラから呼び出される可能性があるコードのために設計されました。これは、`scalararg`や`ptrarg`の値を呼び出し元が保存・復元することを前提としていました。

4.  **`scalararg`と`ptrarg`**:
    *   これらは`m`構造体（Mを表すランタイム内部の構造体）のフィールドであり、`onM`を介してMのシステムスタック上で実行される関数に引数を渡すための、一時的なストレージとして使用されていました。
    *   `scalararg`はスカラー値（整数など）を、`ptrarg`はポインタ値を渡すために使われました。
    *   これらは型付けされておらず、`uintptr`や`unsafe.Pointer`として扱われたため、コンパイル時の型チェックの恩恵を受けられませんでした。

5.  **シグナルハンドラとシグナル安全性**:
    *   シグナルハンドラは、OSからのシグナル（例えば、セグメンテーション違反、タイマー割り込みなど）を受け取った際に非同期に実行される関数です。
    *   シグナルハンドラは、Goコードの任意の時点で割り込む可能性があります。そのため、シグナルハンドラ内で実行されるコードは「シグナル安全」である必要があります。シグナル安全なコードとは、割り込みが発生したGoコードの状態を破壊せず、かつ、シグナルハンドラ自身の実行が他のGoコードの実行に影響を与えないことを意味します。
    *   `scalararg`と`ptrarg`がシグナル安全でなかったのは、シグナルハンドラがそれらの値を上書きしてしまう可能性があったためです。

6.  **ライトバリア (Write Barrier)**:
    *   Goのガベージコレクション（GC）は、並行GCを採用しています。これは、GCがGoプログラムの実行と並行して動作することを意味します。
    *   ライトバリアは、GCが正しく動作するために必要なメカニズムの一つです。Goプログラムがヒープ上のポインタを更新する際に、GCがその変更を追跡できるように、ライトバリアが挿入されます。これにより、GCがオブジェクトグラフを正確にスキャンし、到達可能なオブジェクトを特定できます。
    *   コミットメッセージにあるように、`m.ptrarg[0] = p`のような操作がライトバリアをトリガーし、そのライトバリアがさらに`onM`を呼び出すという循環的な問題が発生していました。

7.  **クロージャ (Closures)**:
    *   Goのクロージャは、それが定義された環境の変数を「キャプチャ」できる関数です。
    *   このコミットでは、`scalararg`や`ptrarg`を介して引数を渡す代わりに、クロージャを使用して必要な値をキャプチャし、Mのシステムスタック上で実行される関数に渡すように変更されました。これにより、型安全性が向上し、コードの可読性も高まります。

## 技術的詳細

このコミットは、Goランタイムの低レベルなスタック管理と引数渡しメカニズムに根本的な変更を加えています。

1.  **`scalararg`と`ptrarg`の削除**:
    *   `src/runtime/runtime2.go`から`m`構造体の`scalararg`と`ptrarg`フィールドが削除されました。
    *   これにより、これらのフィールドに直接アクセスして引数を渡す古いC言語スタイルのアプローチが完全に廃止されました。
    *   これらのフィールドを使用していたすべての箇所（例: `src/runtime/malloc.go`, `src/runtime/mem.go`, `src/runtime/cpuprof.go`など）が、引数をクロージャのキャプチャ変数として渡すように変更されました。例えば、`setcpuprofilerate`関数では、`g.m.scalararg[0] = uintptr(hz)`と`onM(setcpuprofilerate_m)`の代わりに、`systemstack(func() { setcpuprofilerate_m(hz) })`という形式が採用されました。これにより、`hz`の値がクロージャによってキャプチャされ、`setcpuprofilerate_m`に渡されます。

2.  **`onM`と`onM_signalok`の`systemstack`への統合と名称変更**:
    *   `src/runtime/stubs.go`から`onM`と`onM_signalok`の宣言が削除され、代わりに`systemstack`という単一の関数が導入されました。
    *   アセンブリファイル（`src/runtime/asm_386.s`, `src/runtime/asm_amd64.s`, `src/runtime/asm_amd64p32.s`, `src/runtime/asm_arm.s`）において、`onM`と`onM_signalok`の実装が`systemstack`に統合されました。
    *   `systemstack`は、呼び出し元のGoroutineがg0スタック、gsignalスタック、または通常のGoスタックのいずれにいるかに応じて、適切なスタック切り替えロジックを実行します。g0スタックまたはgsignalスタックにいる場合は、直接関数を呼び出します。通常のGoスタックにいる場合は、g0スタックに切り替えてから関数を呼び出し、完了後に元のGoスタックに戻ります。
    *   `switchtoM`というダミーのルーチンも`systemstack_switch`に名称変更されました。これは、スタックトレースの終端を識別するために使用されます。
    *   `onM`という名称が「Mスタック」という誤解を招く表現に基づいていたため、より正確に「システムスタック」上で実行されることを示す`systemstack`に変更されました。これにより、Goランタイムのスタック管理の概念がより明確になりました。

3.  **`funcline`関数のシグネチャ変更**:
    *   `src/runtime/symtab.go`および関連ファイル（`src/runtime/extern.go`, `src/runtime/heapdump.go`, `src/runtime/race.go`, `src/runtime/traceback.go`）において、`funcline`および`funcline1`関数のシグネチャが変更されました。
    *   以前は、ファイル名を`*string`ポインタとして受け取り、そのポインタが指すメモリにファイル名を書き込むC言語スタイルのインターフェースでした。
    *   変更後は、ファイル名を戻り値として直接返すGo言語らしいインターフェースになりました（例: `func funcline(f *_func, targetpc uintptr) (file string, line int32)`）。
    *   この変更は、`ptrarg`/`scalararg`/`onM`のクリーンアップ後に、コンパイラが`*string`引数のエスケープ解析で誤った陽性（false positive）を報告し始めたことがきっかけとなりました。コンパイラのバグの可能性も示唆されていますが、Goらしいコードに書き換えることで問題を回避しました。

4.  **シグナル関連コードの簡素化**:
    *   `src/runtime/signal.go`ファイルが削除されました。このファイルには、`scalararg`を使用してシグナルを有効/無効にするための`sigenable_m`と`sigdisable_m`が含まれていました。
    *   `src/runtime/sigqueue.go`では、`sigenable_go`と`sigdisable_go`が削除され、直接`sigenable`と`sigdisable`を呼び出すように変更されました。これは、`scalararg`が不要になったため、中間層の関数が不要になったことを意味します。

これらの変更により、Goランタイムの内部コードはよりGo言語のイディオムに沿ったものとなり、シグナル安全性、型安全性、および全体的な堅牢性が向上しました。特に、`scalararg`と`ptrarg`の削除は、GoランタイムがC言語の遺産からさらに脱却し、純粋なGoコードとして進化する上で重要な一歩でした。

## コアとなるコードの変更箇所

このコミットでは、Goランタイムの多くのファイルにわたって変更が加えられていますが、特に重要な変更箇所は以下の通りです。

*   **`src/runtime/runtime2.go`**:
    *   `m`構造体から`scalararg`と`ptrarg`フィールドが削除されました。これは、これらの引数渡しメカニズムが廃止されたことを意味します。

*   **`src/runtime/stubs.go`**:
    *   `onM`と`onM_signalok`関数の宣言が削除され、代わりに`systemstack`関数が導入されました。
    *   `badonm`関数が`badsystemstack`に名称変更されました。
    *   `switchtoM`関数が`systemstack_switch`に名称変更されました。

*   **`src/runtime/asm_*.s` (アセンブリファイル)**:
    *   `src/runtime/asm_386.s`, `src/runtime/asm_amd64.s`, `src/runtime/asm_amd64p32.s`, `src/runtime/asm_arm.s`などの各アーキテクチャのアセンブリファイルにおいて、`onM`と`onM_signalok`の実装が`systemstack`に統合され、関連するスタック切り替えロジックが更新されました。
    *   `switchtoM`の参照が`systemstack_switch`に更新されました。

*   **`src/runtime/malloc.go`**:
    *   `mallocgc`関数内で、`mCache_Refill`や`largeAlloc`の呼び出しが`onM`から`systemstack`に、かつクロージャを使用して引数を渡す形式に変更されました。
    *   GCプログラムのアンロール（`unrollgcproginplace_m`, `unrollgcprog_m`）の呼び出しも、`scalararg`/`ptrarg`を介した引数渡しからクロージャによる引数渡しに変更されました。

*   **`src/runtime/mgc.go`**:
    *   `gc_m`関数が引数を直接受け取るように変更され、`scalararg`からの値の読み込みが削除されました。
    *   `readmemstats_m`関数も同様に引数を直接受け取るように変更されました。
    *   `gc_args`構造体が削除されました。

*   **`src/runtime/cpuprof.go`**:
    *   `setcpuprofilerate`関数が、`scalararg`を使用する代わりにクロージャで`hz`を渡すように変更されました。

*   **`src/runtime/panic.go`**:
    *   `deferproc`や`dopanic`などの関数内で、`onM`の呼び出しが`systemstack`に置き換えられました。
    *   `defer on m`や`panic on m stack`といったエラーメッセージが`defer on system stack`や`panic on system stack`に更新されました。

*   **`src/runtime/symtab.go`**:
    *   `funcline`と`funcline1`関数のシグネチャが変更され、ファイル名を`*string`で受け取る代わりに、戻り値として`string`を返すようになりました。

*   **`src/runtime/signal.go`**:
    *   このファイル自体が削除されました。

*   **`src/runtime/sigqueue.go`**:
    *   `sigenable_go`と`sigdisable_go`関数が削除され、直接`sigenable`と`sigdisable`を呼び出すようになりました。

これらの変更は、Goランタイムの内部アーキテクチャを簡素化し、より堅牢でGoらしい設計に移行するための重要なステップです。

## コアとなるコードの解説

このコミットのコアとなる変更は、`m`構造体から`scalararg`と`ptrarg`を削除し、`onM`を`systemstack`に置き換えることです。ここでは、その変更がどのように行われたか、特に`src/runtime/stubs.go`と`src/runtime/asm_amd64.s`の変更を例に解説します。

### `src/runtime/stubs.go`の変更

変更前:
```go
// onM switches from the g to the g0 stack and invokes fn().
// ... (コメント省略) ...
//go:noescape
func onM(fn func())

// onMsignal is like onM but is allowed to be used in code that
// might run on the gsignal stack.
// ... (コメント省略) ...
//go:noescape
func onM_signalok(fn func())

func badonm() {
	gothrow("onM called from signal goroutine")
}

func switchtoM()
```

変更後:
```go
// systemstack runs fn on a system stack.
// If systemstack is called from the per-OS-thread (g0) stack, or
// if systemstack is called from the signal handling (gsignal) stack,
// systemstack calls fn directly and returns.
// Otherwise, systemstack is being called from the limited stack
// of an ordinary goroutine. In this case, systemstack switches
// to the per-OS-thread stack, calls fn, and switches back.
// It is common to use a func literal as the argument, in order
// to share inputs and outputs with the code around the call
// to system stack:
//
//	... set up y ...
//	systemstack(func() {
//		x = bigcall(y)
//	})
//	... use x ...
//
//go:noescape
func systemstack(fn func())

func badsystemstack() {
	gothrow("systemstack called from unexpected goroutine")
}

func systemstack_switch()
```

この変更により、`onM`と`onM_signalok`という2つの異なる関数が`systemstack`という単一の関数に統合されました。`systemstack`のコメントは、その動作原理と、クロージャを使用して引数を渡す一般的な使用パターンを明確に説明しています。`scalararg`や`ptrarg`のようなMのフィールドを介した引数渡しは不要になり、Goのクロージャのセマンティクスに沿った、より安全で型チェック可能な方法が採用されました。

### `src/runtime/asm_amd64.s`の変更 (抜粋)

変更前 (`onM`と`onM_signalok`の分離):
```assembly
// func onM_signalok(fn func())
TEXT runtime·onM_signalok(SB), NOSPLIT, $0-8
	MOVQ	fn+0(FP), DI	// DI = fn
	get_tls(CX)
	MOVQ	g(CX), AX	// AX = g
	MOVQ	g_m(AX), BX	// BX = m

	MOVQ	m_gsignal(BX), DX	// DX = gsignal
	CMPQ	AX, DX
	JEQ	ongsignal
	JMP	runtime·onM(SB)

ongsignal:
	MOVQ	fn+0(FP), DI	// DI = fn
	MOVQ	DI, DX
	MOVQ	0(DI), DI
	CALL	DI
	RET

// func onM(fn func())
TEXT runtime·onM(SB), NOSPLIT, $0-8
	MOVQ	fn+0(FP), DI	// DI = fn
	get_tls(CX)
	MOVQ	g(CX), AX	// AX = g
	MOVQ	g_m(AX), BX	// BX = m

	MOVQ	m_g0(BX), DX	// DX = g0
	CMPQ	AX, DX
	JEQ	onm

	MOVQ	m_curg(BX), BP
	CMPQ	AX, BP
	JEQ	oncurg
	
	// Not g0, not curg. Must be gsignal, but that's not allowed.
	// Hide call from linker nosplit analysis.
	MOVQ	$runtime·badonm(SB), AX
	CALL	AX

oncurg:
	// save our state in g->sched.  Pretend to
	// be switchtoM if the G stack is scanned.
	MOVQ	$runtime·switchtoM(SB), BP
	MOVQ	BP, (g_sched+gobuf_pc)(AX)
	MOVQ	SP, (g_sched+gobuf_sp)(AX)
	MOVQ	AX, (g_sched+gobuf_g)(AX)

	// switch to g0
	MOVQ	DX, g(CX)
	MOVQ	(g_sched+gobuf_sp)(DX), BX
	// make it look like mstart called onM on g0, to stop traceback
	SUBQ	$8, BX
	MOVQ	$runtime·mstart(SB), DX
	MOVQ	DX, 0(BX)
	MOVQ	BX, SP
	CALL	0(DI) // call fn
	// restore g
	MOVQ	AX, g(CX)
	MOVQ	(g_sched+gobuf_sp)(AX), SP
	MOVQ	$0, (g_sched+gobuf_pc)(AX)
	MOVQ	$0, (g_sched+gobuf_sp)(AX)
	RET

onm:
	// already on m stack, just call directly
	MOVQ	DI, DX
	MOVQ	0(DI), DI
	CALL	DI
	RET
```

変更後 (`systemstack`への統合):
```assembly
// func systemstack(fn func())
TEXT runtime·systemstack(SB), NOSPLIT, $0-8
	MOVQ	fn+0(FP), DI	// DI = fn
	get_tls(CX)
	MOVQ	g(CX), AX	// AX = g
	MOVQ	g_m(AX), BX	// BX = m

	MOVQ	m_gsignal(BX), DX	// DX = gsignal
	CMPQ	AX, DX
	JEQ	noswitch

	MOVQ	m_g0(BX), DX	// DX = g0
	CMPQ	AX, DX
	JEQ	noswitch

	MOVQ	m_curg(BX), BP
	CMPQ	AX, BP
	JEQ	switch
	
	// Bad: g is not gsignal, not g0, not curg. What is it?
	MOVQ	$runtime·badsystemstack(SB), AX
	CALL	AX

switch:
	// save our state in g->sched.  Pretend to
	// be systemstack_switch if the G stack is scanned.
	MOVQ	$runtime·systemstack_switch(SB), BP
	MOVQ	BP, (g_sched+gobuf_pc)(AX)
	MOVQ	SP, (g_sched+gobuf_sp)(AX)
	MOVQ	AX, (g_sched+gobuf_g)(AX)

	// switch to g0
	MOVQ	DX, g(CX)
	MOVQ	(g_sched+gobuf_sp)(DX), BX
	// make it look like mstart called systemstack on g0, to stop traceback
	SUBQ	$8, BX
	MOVQ	$runtime·mstart(SB), DX
	MOVQ	DX, 0(BX)
	MOVQ	BX, SP
	CALL	0(DI) // call fn
	// restore g
	MOVQ	AX, g(CX)
	MOVQ	(g_sched+gobuf_sp)(AX), SP
	MOVQ	$0, (g_sched+gobuf_pc)(AX)
	MOVQ	$0, (g_sched+gobuf_sp)(AX)
	RET

noswitch:
	// already on system stack, just call directly
	MOVQ	DI, DX
	MOVQ	0(DI), DI
	CALL	DI
	RET
```

このアセンブリコードの変更は、`onM`と`onM_signalok`のロジックが`systemstack`という単一のエントリポイントに統合されたことを示しています。

*   `systemstack`はまず、現在のGoroutine (`AX`) が`gsignal`スタック (`DX`) または`g0`スタック (`DX`) 上にいるかどうかをチェックします。もしそうであれば、`noswitch`ラベルにジャンプし、スタック切り替えなしで直接関数`fn`を呼び出します。
*   現在のGoroutineが`curg`（通常のGoスタック上のGoroutine）である場合、`switch`ラベルにジャンプします。ここでは、現在のGoroutineの状態（PC、SP、G）を保存し、`g0`スタックに切り替えます。そして、`fn`を呼び出し、完了後に元のGoroutineスタックに戻ります。
*   それ以外の不正な状態であれば、`badsystemstack`を呼び出してパニックします。

この統合により、ランタイムのスタック管理ロジックが簡素化され、`onM_signalok`の複雑なセマンティクス（呼び出し元が値を保存・復元する責任）が不要になりました。また、`switchtoM`の参照も`systemstack_switch`に更新され、命名の一貫性が保たれています。

全体として、このコミットはGoランタイムの内部をよりクリーンで、安全で、Goらしい設計に進化させるための重要な一歩であり、特に低レベルのスタック管理と引数渡しにおける長年の問題を解決しました。

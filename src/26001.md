# [インデックス 26001] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージにおけるテストスイートの改善に焦点を当てています。特に、HTTP/2モードでのテストカバレッジを拡大し、既存のテストがHTTP/2プロトコルでも適切に動作するかどうかを検証することを目的としています。同時に、HTTP/1.1とHTTP/2の両方で共通のテストロジックを再利用できるように、テストコードのリファクタリングも行われています。

## 元コミット内容

このコミットの主な目的は、`net/http`パッケージの既存のテストをHTTP/2モードでも実行することです。これにより、HTTP/2実装の堅牢性を高め、潜在的なバグを早期に発見することが期待されます。HTTP/2モードで現在失敗するテストは一時的にスキップされ、関連するIssueが更新されています。また、HTTP/1.1における特定のエラーレスポンスコードが413から431に修正されています。

## 変更の背景

Go言語の`net/http`パッケージは、HTTP/1.1とHTTP/2の両方をサポートしています。HTTP/2は、多重化、ヘッダー圧縮、サーバープッシュなどの機能により、Webパフォーマンスを大幅に向上させるプロトコルです。Go 1.6以降、`net/http`パッケージはHTTPSを使用するクライアントとサーバーの両方でHTTP/2を自動的に有効にするようになりました。

このコミットが行われた2015年12月は、Go言語がHTTP/2のサポートを強化している時期にあたります。新しいプロトコルへの移行に伴い、既存のHTTP/1.1向けに書かれたテストがHTTP/2環境でも期待通りに動作するかどうかを検証することが不可欠でした。多くのテストはプロトコルに依存しないように設計されていますが、HTTP/2の特性（例: コネクション管理、ヘッダーの扱い、エラー処理）に起因する差異によって、予期せぬ挙動やバグが発生する可能性があります。

このコミットの背景には、以下の主要な動機があります。

1.  **HTTP/2の品質保証の強化**: `net/http`パッケージのHTTP/2実装が安定しており、仕様に準拠していることを確認するため、より広範なテストカバレッジが必要でした。
2.  **テストコードの効率化**: HTTP/1.1とHTTP/2の両方で同じロジックをテストできるように、テストヘルパー関数を導入し、テストコードの重複を減らすことが目指されました。
3.  **既知のHTTP/2問題の特定と追跡**: HTTP/2モードで失敗するテストを特定し、それらを関連するIssueに紐付けることで、今後の修正作業の優先順位付けと追跡を容易にしました。
4.  **HTTPステータスコードの修正**: HTTP/1.1におけるヘッダーサイズ超過のエラーレスポンスが、より正確なHTTPステータスコードを返すように修正する必要がありました。

## 前提知識の解説

### HTTP/1.1とHTTP/2

*   **HTTP/1.1**: 広く普及しているHTTPプロトコルのバージョン。リクエストとレスポンスは通常、1つのTCPコネクション上で順番に処理されます（パイプライン処理は存在するものの、ヘッドオブラインブロッキングの問題がある）。
*   **HTTP/2**: HTTP/1.1のパフォーマンス上の課題を解決するために設計された新しいプロトコル。
    *   **多重化 (Multiplexing)**: 1つのTCPコネクション上で複数のリクエストとレスポンスを同時に送受信できます。これにより、ヘッドオブラインブロッキングが解消され、ページの読み込み速度が向上します。
    *   **ヘッダー圧縮 (Header Compression)**: HPACKというアルゴリズムを使用してHTTPヘッダーを効率的に圧縮し、オーバーヘッドを削減します。
    *   **サーバープッシュ (Server Push)**: クライアントが明示的に要求する前に、サーバーがリソースをクライアントにプッシュできます。
    *   **バイナリフレーミング**: HTTP/1.1のテキストベースのプロトコルとは異なり、HTTP/2はバイナリプロトコルです。

### Go言語の `net/http` パッケージとHTTP/2

Go言語の`net/http`パッケージは、HTTPクライアントとサーバーを構築するための基本的な機能を提供します。Go 1.6以降、`net/http`はHTTPS接続において自動的にHTTP/2をサポートします。これは、`http.Client`がHTTPSエンドポイントに接続する際に自動的にHTTP/2を試行し、`http.ListenAndServeTLS`を使用するサーバーも自動的にHTTP/2を有効にするためです。より低レベルな制御や高度な機能（例: H2Cサポート）が必要な場合は、`golang.org/x/net/http2`パッケージを使用できます。

### HTTPステータスコード 413と431

*   **413 Payload Too Large (旧称: Request Entity Too Large)**: クライアントが送信したリクエストのペイロード（ボディ）が、サーバーが処理できる上限を超えていることを示します。例えば、アップロードするファイルが大きすぎる場合などに発生します。
*   **431 Request Header Fields Too Large**: サーバーがリクエストを処理できないのは、HTTPヘッダーフィールドが大きすぎるためであることを示します。これは、多数のクッキー、非常に長いリファラーURL、または過剰なカスタムヘッダーなどが原因で発生する可能性があります。このコミットでは、HTTP/1.1においてヘッダーサイズ超過の場合に413ではなく431を返すように修正されています。これは、エラーの原因がペイロードではなくヘッダーにあることをより正確に伝えるための変更です。

### Goのテストフレームワーク (`testing` パッケージ)

Goの標準ライブラリには、テストを記述するための`testing`パッケージが含まれています。
*   `func TestXxx(t *testing.T)`: テスト関数は`Test`で始まり、`*testing.T`型の引数を取ります。
*   `t.Skip("reason")`: テストをスキップするために使用されます。特定の条件（例: 特定のOS、未実装の機能、既知のバグ）でテストを実行したくない場合に便利です。
*   `httptest.NewServer`: `net/http/httptest`パッケージの一部で、テスト中にHTTPサーバーを簡単に起動するために使用されます。

## 技術的詳細

このコミットの主要な技術的変更は以下の通りです。

1.  **テストヘルパー `newClientServerTest` の導入と活用**:
    *   `src/net/http/clientserver_test.go` に `newClientServerTest` というヘルパー関数が導入されました。この関数は、HTTP/1.1 (`h1Mode`) と HTTP/2 (`h2Mode`) の両方でテストサーバーとクライアントのペアをセットアップするための共通のメカニズムを提供します。
    *   多くの既存のテスト関数は、`TestXxx_h1` と `TestXxx_h2` の形式で、それぞれ `testXxx(t, h1Mode)` と `testXxx(t, h2Mode)` を呼び出すようにリファクタリングされました。これにより、同じテストロジックを両方のプロトコルで実行できるようになります。
    *   `h1Mode` (false) と `h2Mode` (true) という定数が定義され、テストの可読性が向上しています。

2.  **HTTP/2モードでのテストスキップ**:
    *   HTTP/2モードで現在失敗することが判明しているテストには、`t.Skip("skipping in http2 mode; golang.org/issue/XXXXX")` のような行が追加されました。これにより、CI/CDパイプラインでのテスト実行がブロックされることなく、既知のHTTP/2関連の問題が追跡されます。
    *   具体的には、`TestClientTrailers_h2` (Issue #13557)、`TestHandlerPanicNil_h2` (Issue #13555)、`TestHandlerPanic_h2` (Issue #13555)、`TestTransportAndServerSharedBodyRace_h2` (Issue #13556) がスキップされています。これらのIssueは、HTTP/2プロトコルの特定の側面（トレーラーヘッダー、パニック処理、共有ボディの競合状態）に関連する未解決の問題を示唆しています。

3.  **HTTPステータスコード 413 から 431 への修正**:
    *   `src/net/http/server.go` 内で、リクエストヘッダーが大きすぎる場合にサーバーが返すHTTPステータスコードが `413 Request Entity Too Large` から `431 Request Header Fields Too Large` に変更されました。
    *   これは、HTTP/1.1サーバーがリクエストボディではなく、リクエストヘッダーのサイズ制限を超過した場合に、より正確なエラーセマンティクスを提供するための重要な修正です。`DefaultMaxHeaderBytes` の制限を超えた場合にこのエラーが返されます。

4.  **`httptest.NewServer` から `newClientServerTest` への移行**:
    *   多くのテストで、直接 `httptest.NewServer` を使用していた箇所が、`newClientServerTest` を介してテストサーバーをセットアップするように変更されました。これにより、HTTP/1.1とHTTP/2の両方のテスト環境を統一的に管理できるようになります。

## コアとなるコードの解説

このコミットの核心は、`net/http`パッケージのテストインフラストラクチャをHTTP/2の検証に適応させることにあります。

1.  **テストの二重化とパラメータ化**:
    *   多くのテスト関数が `TestXxx_h1` と `TestXxx_h2` のペアに分割され、それぞれが `testXxx(t, h1Mode)` と `testXxx(t, h2Mode)` を呼び出す形式に変更されました。これは、HTTP/1.1とHTTP/2の両方のプロトコルで同じテストロジックを実行するための一般的なパターンです。
    *   `h1Mode` (false) と `h2Mode` (true) というブール値の定数を導入することで、テストコードの意図が明確になり、可読性が向上しています。

2.  **`newClientServerTest` ヘルパー**:
    *   `newClientServerTest(t *testing.T, h2 bool, h Handler)` 関数は、テストサーバー (`httptest.Server`) とそれに対応するHTTPクライアント (`http.Client`) をセットアップします。`h2`引数が`true`の場合、HTTP/2モードでサーバーとクライアントが構成されます。これにより、各テストで個別にHTTP/1.1とHTTP/2のセットアップロジックを記述する必要がなくなり、テストコードの簡潔性と保守性が向上します。
    *   このヘルパーは、テストサーバーのライフサイクル管理（`defer cst.close()`）も担当し、リソースリークを防ぎます。

3.  **条件付きテストスキップ**:
    *   `t.Skip("skipping in http2 mode; golang.org/issue/XXXXX")` の使用は、開発プロセスにおける現実的なアプローチを示しています。HTTP/2は比較的新しいプロトコルであり、既存のHTTP/1.1のセマンティクスとは異なる挙動を示す場合があります。このスキップメカニズムにより、HTTP/2関連の既知の問題を特定しつつ、それらが全体のテストスイートの実行を妨げないようにしています。同時に、関連するIssue番号を明記することで、将来的な修正作業のロードマップを提供しています。

4.  **HTTPステータスコードの正確性**:
    *   `src/net/http/server.go` における `413` から `431` への変更は、HTTPプロトコルのセマンティクスに対する厳密な遵守を示しています。リクエストボディが大きすぎる場合は `413 Payload Too Large`、リクエストヘッダーが大きすぎる場合は `431 Request Header Fields Too Large` を返すのが正しい挙動です。この修正は、サーバーがクライアントに対してより正確なエラー情報を提供し、デバッグを容易にするために重要です。

これらの変更は、Goの`net/http`パッケージがHTTP/2プロトコルをより堅牢にサポートするための基盤を強化し、テストの網羅性と正確性を向上させる上で重要な役割を果たしています。

# [インデックス 24388] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）アシストメカニズムにおけるバグ修正に関するものです。具体的には、GCアシストがバックグラウンドGCクレジットを「盗む」際に、誤った量を計算していた問題を修正しています。これにより、バックグラウンドGCクレジットが不必要に早く枯渇し、結果として余分なGCアシスト作業が発生するのを防ぎます。

## コミット

Author: Austin Clements <austin@google.com>
Date:   Wed Jul 22 16:40:50 2015 -0400

    runtime: steal the correct amount of GC assist credit

    GC assists are supposed to steal at most the amount of background GC
    credit available so that background GC credit doesn't go negative.
    However, they are instead stealing the *total* amount of their debt
    but only claiming up to the amount of credit that was available. This
    results in draining the background GC credit pool too quickly, which
    results in unnecessary assist work.

    The fix is trivial: steal the amount of work we meant to steal (which
    is already computed).

## 元コミット内容

GoランタイムのGCアシストは、バックグラウンドGCクレジットが負にならないように、利用可能なバックグラウンドGCクレジットの最大量までを「盗む」ことになっています。しかし、実際には、アシストは自身の負債の「総量」を盗んでいましたが、利用可能なクレジットの量までしか請求していませんでした。このため、バックグラウンドGCクレジットプールが不必要に早く枯渇し、結果として余分なアシスト作業が発生していました。

この修正は単純で、本来盗むべきだった作業量（既に計算済み）を盗むように変更するものです。

## 変更の背景

Goのガベージコレクタは、アプリケーションの実行と並行して動作する「並行GC」を採用しています。これにより、アプリケーションの一時停止（Stop-the-World: STW）時間を最小限に抑え、レイテンシを改善しています。しかし、並行GCだけではオブジェクトの割り当て速度に追いつけない場合があります。このような状況で、アプリケーションが新しいオブジェクトを割り当てようとすると、GCの進行を助けるために「GCアシスト」と呼ばれる作業が実行されます。

GCアシストは、アプリケーションのスループットを犠牲にしてでも、GCの進行を保証するためのメカニズムです。このアシスト作業は、バックグラウンドGCが完了すべき作業の一部を肩代わりする形で実行されます。この「肩代わり」の量を管理するために、「GCクレジット」という概念が導入されています。バックグラウンドGCは一定量のクレジットを持っており、GCアシストはこのクレジットを消費することで、バックグラウンドGCの負担を軽減します。

このコミット以前のGoランタイムでは、GCアシストがバックグラウンドGCクレジットを消費するロジックにバグがありました。アシストが必要とする作業量（`scanWork`）と、実際にバックグラウンドGCから「盗む」ことができるクレジット量（`stolen`）は異なる場合があります。特に、利用可能なクレジットが`scanWork`よりも少ない場合、`stolen`は利用可能なクレジット量に制限されます。しかし、クレジットプールから差し引かれる量が`scanWork`（アシストが必要とする総量）になっていたため、クレジットプールが過剰に消費され、負の値になる可能性がありました。これにより、システムはGCアシストがより頻繁に必要であると誤解し、不必要なアシスト作業を誘発していました。これは、アプリケーションのパフォーマンス低下に直結する問題でした。

## 前提知識の解説

*   **Goのガベージコレクション (GC)**: Goはトレース型GCを採用しており、主に並行マーク＆スイープ方式で動作します。これは、アプリケーションの実行とGC作業を並行して進めることで、STW時間を短縮し、レイテンシを低減します。
*   **GCサイクル**: GoのGCは、マークフェーズとスイープフェーズを繰り返します。マークフェーズでは、到達可能なオブジェクトを識別し、スイープフェーズでは到達不能なオブジェクトを解放します。
*   **GCアシスト (GC Assist)**: アプリケーションが新しいメモリを割り当てようとした際に、GCが十分に進んでいない場合に、その割り当てを行うゴルーチン自身がGC作業の一部を手伝うメカニズムです。これにより、GCの進行を加速させ、メモリ不足によるパニックを防ぎます。しかし、アシストはアプリケーションの実行を一時的に遅らせるため、必要最小限に抑えるべきです。
*   **GCクレジット (GC Credit)**: GCアシストの量を制御するための内部的なメカニズムです。バックグラウンドGCは一定量の「クレジット」を持っており、GCアシストはこのクレジットを消費することで、バックグラウンドGCの作業を肩代わりします。クレジットが枯渇すると、GCアシストはより多くの作業を行う必要が生じます。
*   **`gcController.bgScanCredit`**: バックグラウンドGCが利用可能なスキャン作業のクレジット量を管理する変数です。この値は、GCアシストによって消費され、GCの進行に応じて補充されます。
*   **`xaddint64`**: Goランタイム内部で使用されるアトミック操作の一つで、指定されたメモリ位置の64ビット整数に値を加算します。これは複数のゴルーチンから同時にアクセスされる可能性のある共有変数（例: `bgScanCredit`）を安全に更新するために使用されます。

## 技術的詳細

GoのGCアシストは、`gcAssistAlloc`関数内で実行されます。この関数は、新しいメモリ割り当てが必要になった際に呼び出され、GCの進行状況に応じてアシスト作業を行うかどうかを決定します。

アシスト作業の量は、主に以下の要素によって決定されます。
1.  **`scanWork`**: 現在のメモリ割り当てによって発生するGCの負債（debt）であり、アシストが処理すべき作業の総量を示します。
2.  **`gcController.bgScanCredit`**: バックグラウンドGCがまだ処理できると見なされるクレジット量です。

GCアシストは、`scanWork`の全量を処理しようとしますが、`gcController.bgScanCredit`が負にならないように、実際に「盗む」作業量（`stolen`）を制限します。`stolen`は、`scanWork`と`gcController.bgScanCredit`の小さい方、または`scanWork`が`gcController.bgScanCredit`よりも大きい場合は`gcController.bgScanCredit`に制限されます。

このコミット以前のコードでは、`gcController.bgScanCredit`から差し引かれる量が`scanWork`（アシストが必要とする総量）になっていました。

```go
xaddint64(&gcController.bgScanCredit, -scanWork) // 修正前
```

これは、`stolen`（実際に盗んだ量）が`scanWork`よりも小さい場合でも、`scanWork`の全量がクレジットから差し引かれることを意味します。例えば、`scanWork`が100で`bgScanCredit`が50の場合、`stolen`は50になりますが、クレジットからは100が差し引かれてしまい、`bgScanCredit`が負の値（-50）になってしまいます。

`bgScanCredit`が負になると、システムはバックグラウンドGCが遅れていると誤解し、より多くのGCアシストをトリガーする可能性があります。これは、アプリケーションの実行速度を低下させる不必要なオーバーヘッドとなります。

このコミットは、`gcController.bgScanCredit`から差し引かれる量を、実際に「盗んだ」作業量である`stolen`に変更することで、この問題を解決しています。

```go
xaddint64(&gcController.bgScanCredit, -stolen) // 修正後
```

これにより、`bgScanCredit`は常に正確な量だけ減算され、不必要に負になることがなくなります。結果として、GCアシストが過剰に発生するのを防ぎ、Goアプリケーションのパフォーマンスとレイテンシの安定性が向上します。

## コアとなるコードの変更箇所

変更は `src/runtime/mgcmark.go` ファイルの `gcAssistAlloc` 関数内の一箇所です。

```diff
--- a/src/runtime/mgcmark.go
+++ b/src/runtime/mgcmark.go
@@ -182,7 +182,7 @@ func gcAssistAlloc(size uintptr, allowAssist bool) {
 		} else {
 			stolen = scanWork
 		}
-		xaddint64(&gcController.bgScanCredit, -scanWork)
+		xaddint64(&gcController.bgScanCredit, -stolen)

 		scanWork -= stolen
 		gp.gcscanwork += stolen
```

## コアとなるコードの解説

変更された行は以下の通りです。

```go
xaddint64(&gcController.bgScanCredit, -scanWork) // 修正前
xaddint64(&gcController.bgScanCredit, -stolen)   // 修正後
```

*   `gcController.bgScanCredit`: これは、バックグラウンドGCがまだ処理できると見なされるスキャン作業のクレジット量を保持するグローバル変数です。
*   `xaddint64`: これは、Goランタイムが提供するアトミックな加算関数です。複数のゴルーチンが同時に`bgScanCredit`を更新しようとした場合でも、競合状態を防ぎ、正確な更新を保証します。
*   `-scanWork`: 修正前は、GCアシストが必要とする作業の総量（`scanWork`）がクレジットから差し引かれていました。
*   `-stolen`: 修正後は、実際にバックグラウンドGCから「盗んだ」作業量（`stolen`）がクレジットから差し引かれています。

`stolen`変数は、`gcAssistAlloc`関数内で以下のように計算されます。

```go
		if gcController.bgScanCredit >= scanWork {
			stolen = scanWork
		} else {
			stolen = gcController.bgScanCredit
		}
```
このロジックにより、`stolen`は`scanWork`と`gcController.bgScanCredit`の小さい方、つまりバックグラウンドGCクレジットが負にならないように制限された実際の「盗んだ」作業量になります。

したがって、`xaddint64(&gcController.bgScanCredit, -stolen)`とすることで、`bgScanCredit`は実際に消費されたクレジット量だけ正確に減算されるようになり、クレジットプールの不正確な枯渇が解消されました。

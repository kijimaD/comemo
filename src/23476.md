# [インデックス 23476] ファイルの概要

## コミット

このコミット `512f75e8dfc7653c873971480c23ba308307b85a` は、GoランタイムにおけるGC（ガベージコレクション）プログラムのエンコーディングを簡素化し、デコーダの高速化を図るものです。特に、大きな配列を含む型に対するポインタ情報の表現方法を改善し、メモリ使用量とGCプログラムの実行速度の両面でパフォーマンス向上を実現しています。

## 元コミット内容

```
runtime: replace GC programs with simpler encoding, faster decoder

Small types record the location of pointers in their memory layout
by using a simple bitmap. In Go 1.4 the bitmap held 4-bit entries,
and in Go 1.5 the bitmap holds 1-bit entries, but in both cases using
a bitmap for a large type containing arrays does not make sense:
if someone refers to the type [1<<28]*byte in a program in such
a way that the type information makes it into the binary, it would be
a waste of space to write a 128 MB (for 4-bit entries) or even 32 MB
(for 1-bit entries) bitmap full of 1s into the binary or even to keep
one in memory during the execution of the program.

For large types containing arrays, it is much more compact to describe
the locations of pointers using a notation that can express repetition
than to lay out a bitmap of pointers. Go 1.4 included such a notation,
called ``GC programs'' but it was complex, required recursion during
decoding, and was generally slow. Dmitriy measured the execution of
these programs writing directly to the heap bitmap as being 7x slower
than copying from a preunrolled 4-bit mask (and frankly that code was
not terribly fast either). For some tests, unrollgcprog1 was seen costing
as much as 3x more than the rest of malloc combined.

This CL introduces a different form for the GC programs. They use a
simple Lempel-Ziv-style encoding of the 1-bit pointer information,
in which the only operations are (1) emit the following n bits
and (2) repeat the last n bits c more times. This encoding can be
generated directly from the Go type information (using repetition
only for arrays or large runs of non-pointer data) and it can be decoded
very efficiently. In particular the decoding requires little state and
no recursion, so that the entire decoding can run without any memory
accesses other than the reads of the encoding and the writes of the
decoded form to the heap bitmap. For recursive types like arrays of
arrays of arrays, the inner instructions are only executed once, not
n times, so that large repetitions run at full speed. (In contrast, large
repetitions in the old programs repeated the individual bit-level layout
of the inner data over and over.) The result is as much as 25x faster
decoding compared to the old form.
... (ベンチマーク結果と追加の説明が続く)
```

## 変更の背景

Goのガベージコレクタは、ヒープ上のオブジェクトがポインタを含むかどうかを正確に知る必要があります。これにより、GCは到達可能なオブジェクトを追跡し、不要なメモリを解放できます。このポインタ情報の管理は、Goランタイムの効率に直結する重要な要素です。

Go 1.4では、オブジェクトのメモリレイアウトにおけるポインタの位置を記録するために、主に2つの方法が用いられていました。

1.  **ビットマップ**: 小さな型に対しては、ポインタの位置を示すビットマップが使用されていました。Go 1.4では4ビットエントリのビットマップが使われていましたが、Go 1.5では1ビットエントリに移行する計画がありました。しかし、`[1<<28]*byte`のような非常に大きな配列型の場合、たとえ1ビットエントリであっても、そのビットマップをバイナリに書き込んだり、実行時にメモリに保持したりすると、それぞれ128MB（4ビット）または32MB（1ビット）といった膨大なスペースを無駄に消費することになります。
2.  **GCプログラム**: 大きな配列を含む型に対しては、繰り返しを表現できる「GCプログラム」と呼ばれるよりコンパクトな表記法が導入されていました。しかし、Go 1.4のGCプログラムは複雑で、デコード時に再帰を必要とし、一般的に低速でした。特に、ヒープビットマップに直接書き込む際のデコードは、事前に展開された4ビットマスクからコピーする場合と比較して7倍も遅いことが測定されていました。一部のテストでは、`unrollgcprog1`が`malloc`全体の3倍ものコストを占めることもありました。

このような背景から、Go 1.5の開発サイクルにおいて、既存のGCプログラムの非効率性が大きな問題となっていました。特に、大きな型に対するGCプログラムのデコード速度は、ランタイム全体のパフォーマンスボトルネックとなっていたため、よりシンプルで高速なGCプログラムのエンコーディングとデコーダへの置き換えが喫緊の課題でした。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとGCに関する基本的な概念を理解しておく必要があります。

### 1. Goのガベージコレクション (GC)

GoのGCは、ヒープ上に割り当てられたメモリのうち、プログラムから到達不可能になったオブジェクトを自動的に解放する仕組みです。GCは、ポインタをたどって到達可能なオブジェクトをマークし、マークされなかったオブジェクトをスイープ（解放）することで動作します。このプロセスを効率的に行うためには、各オブジェクトのメモリレイアウトにおいて、どの部分がポインタであり、どの部分が非ポインタデータであるかを正確に知る必要があります。

### 2. ヒープビットマップ (Heap Bitmap)

Goランタイムは、ヒープ上の各メモリワードがポインタであるか否かを示す「ヒープビットマップ」を管理しています。このビットマップは、GCがオブジェクトをスキャンする際に参照され、ポインタを効率的に識別するために使用されます。オブジェクトが割り当てられる際、その型情報に基づいて対応するヒープビットマップが設定されます。

### 3. ポインタ情報 (Pointer Information)

Goの型システムは、各型がポインタをどこに保持しているかという情報（ポインタ情報）を持っています。この情報は、コンパイル時に生成され、ランタイムがGCを行う際に利用されます。ポインタ情報の表現方法には、主に以下の2種類があります。

*   **ポインタマスク (Pointer Mask)**: オブジェクトのメモリレイアウトをビット列で直接表現したものです。各ビットがメモリワードに対応し、1であればポインタ、0であれば非ポインタデータを示します。小さな型に対しては効率的ですが、大きな型、特に大きな配列に対しては、ビットマップ自体が巨大になり、メモリを大量に消費するという問題があります。Go 1.4では4ビットエントリ（1ワードあたり4ビットでポインタ情報を表現）、Go 1.5では1ビットエントリ（1ワードあたり1ビットでポインタ情報を表現）が使われていました。
*   **GCプログラム (GC Program)**: ポインタマスクが大きくなりすぎる型（特に大きな配列型）に対して、よりコンパクトにポインタ情報を表現するための命令列です。これは、繰り返しパターンを効率的にエンコードすることで、メモリ使用量を削減します。Go 1.4のGCプログラムは、複雑な命令セットを持ち、デコードに再帰を伴うため、実行速度が遅いという課題がありました。

### 4. `typedmemmove`

`typedmemmove`は、Goランタイム内部で型情報に基づいてメモリをコピーする関数です。GCプログラムの変更前は、この関数も型情報からポインタ情報を取得していましたが、このコミットの時点では、既にヒープビットマップを直接利用するように変更されていました（CL 9886）。これにより、GCプログラムの変更が`typedmemmove`に与える影響はなくなっています。

## 技術的詳細

このコミットの核となる技術的変更は、GoランタイムにおけるGCプログラムのエンコーディングとデコーディングメカニズムの刷新です。

### 新しいGCプログラムのエンコーディング

新しいGCプログラムは、Lempel-Zivスタイルのシンプルなエンコーディングを採用しています。これは、1ビットのポインタ情報を効率的に表現するための命令セットで構成されています。主な操作は以下の2つです。

1.  **`emit n bits`**: 後続のバイトから`n`ビットを読み込み、そのまま出力します。これは、ポインタ情報が不規則なパターンを持つ場合に直接ビット列を埋め込むために使用されます。
2.  **`repeat the last n bits c more times`**: 直前の`n`ビットのパターンを`c`回繰り返します。これは、大きな配列のようにポインタ情報が規則的に繰り返される場合に非常に効率的です。

このエンコーディングは、Goの型情報から直接生成できます。特に、配列や非ポインタデータの大きな連続ブロックに対しては、繰り返し命令を活用することで、非常にコンパクトな表現が可能になります。

### 高速なデコーダ

新しいGCプログラムのデコーダは、以下の特徴により大幅な高速化を実現しています。

*   **少ない状態と非再帰**: デコーダは、デコード中にほとんど状態を保持せず、再帰を必要としません。これにより、デコード処理のオーバーヘッドが大幅に削減されます。
*   **メモリアクセスの最小化**: デコード処理は、エンコーディングの読み込みと、デコードされた情報をヒープビットマップに書き込む以外のメモリアクセスをほとんど行いません。これにより、キャッシュ効率が向上し、高速な実行が可能になります。
*   **繰り返し処理の効率化**: `arrays of arrays of arrays`のような再帰的な型の場合、内側の命令は`n`回ではなく一度だけ実行されます。これにより、大きな繰り返し処理がフルスピードで実行され、旧来のGCプログラムが個々のビットレベルのレイアウトを繰り返し実行していた非効率性が解消されます。

これらの改善により、デコード速度は旧形式と比較して最大25倍高速化されました。

### 型情報の処理フローの簡素化

旧来のGo 1.4では、型に応じたヒープビットマップの設定方法が複雑な3つのケースに分かれていました。

*   **(1) 小さな型（32ワードまで）**: 4ビットのポインタマスクをバイナリに直接格納し、コピーして使用。
*   **(1b) 小さな型（15ワードまで、奇数ワード）**: バイト境界に合わせるために倍増された4ビットのポインタマスクを直接格納し、コピーして使用。
*   **(2) 中程度の型（128ワードまで）**: GCプログラムをバイナリに格納するが、BSS領域に展開されたマスク用のスペースを確保。初回使用時にGCプログラムを実行してマスクを構築し、以降はコピーして使用。
*   **(3) 大きな型**: GCプログラムを格納し、オブジェクトが割り当てられるたびにヒープビットマップに直接書き込むために実行。これが最も遅いパスでした。

このコミット（Go 1.5向け）により、ポインタマスクが1ビットエントリになったこと、および新しいデコーダのオーバーヘッドが大幅に削減されたことで、型情報の処理フローは以下の2つのケースに簡素化されました。

*   **(1) 128ワード以下の型**: 1ビットのポインタマスクをバイナリに直接格納し、`malloc`時にヒープビットマップの初期化に使用します。
*   **(2) 128ワードを超える型**: GCプログラムを格納し、オブジェクトが割り当てられるたびにヒープビットマップに直接書き込むために実行します。

これにより、旧来の複雑な中間キャッシュ層（ケース2）が不要になり、全体的な設計がシンプルかつ効率的になりました。

## コアとなるコードの解説

ここでは、特に重要な`src/cmd/internal/gcprog/gcprog.go`と、それを利用する`src/cmd/internal/gc/reflect.go`、`src/reflect/type.go`の変更に焦点を当てて解説します。

### `src/cmd/internal/gcprog/gcprog.go`

このファイルは、新しいGCプログラムのエンコーディングとデコーディングの基盤を提供します。

*   **`Writer` 構造体**:
    ```go
    type Writer struct {
        writeByte func(byte)
        symoff    int
        index     int64
        b         [progMaxLiteral]byte
        nb        int
        debug     io.Writer
        debugBuf  []byte
    }
    ```
    `Writer`はGCプログラムをバイト列として出力するためのインターフェースを提供します。`writeByte`は実際にバイトを書き込む関数で、リンカやコンパイラから提供されます。`index`はこれまでに書き込まれたビットの総数、`b`と`nb`はリテラルビットを一時的にバッファリングするためのフィールドです。

*   **`Init(writeByte func(byte))`**: `Writer`を初期化し、バイト書き込み関数を設定します。
*   **`End()`**: GCプログラムの終端マーク（`0`バイト）を書き込み、プログラムを終了します。
*   **`Ptr(index int64)`**: 指定された`index`位置にポインタが存在することを示す1ビットを書き込みます。現在のビットインデックスから`index`までの間は0ビット（非ポインタ）で埋められます。
*   **`ZeroUntil(index int64)`**: 現在のビットインデックスから`index`までの間を0ビット（非ポインタ）で埋めます。
*   **`ShouldRepeat(n, c int64) bool`**: `n`ビットのパターンを`c`回繰り返す命令を生成するべきかどうかを判断します。これは、リピート命令のオーバーヘッドと、直接ビットを書き込むコストを比較して決定されます。
*   **`Repeat(n, c int64)`**: 直前の`n`ビットのパターンを`c`回繰り返す命令を書き込みます。`n`と`c`は可変長整数（varint）でエンコードされます。
*   **`Append(prog []byte, n int64)`**: 既存のGCプログラム`prog`を現在のプログラムに結合します。

### `src/cmd/internal/gc/reflect.go`

コンパイラ側で型情報からGCプログラムを生成する部分です。

*   **`dgcsym(t *Type) (sym *Sym, useGCProg bool, ptrdata int64)`**:
    この関数は、与えられた型`t`に対してGC情報を格納するシンボルを生成します。
    `ptrdata/int64(Widthptr) <= maxPtrmaskBytes*8` (128ワード以下) の場合、`dgcptrmask`を呼び出して直接ポインタマスクを生成します。
    それ以外の場合、`useGCProg`を`true`に設定し、`dgcprog`を呼び出してGCプログラムを生成します。

*   **`dgcprog(t *Type) (*Sym, int64)`**:
    この関数が、新しい`gcprog.Writer`を使用してGCプログラムを生成する主要なロジックを含みます。
    `GCProg`構造体を初期化し、`p.emit(t, 0)`を呼び出して型`t`のポインタ情報をGCプログラムとしてエンコードします。
    `p.emit`は再帰的に型を走査し、ポインタフィールドに対しては`p.w.Ptr`を、配列の繰り返しパターンに対しては`p.w.Repeat`を、非ポインタデータに対しては`p.w.ZeroUntil`を呼び出します。

*   **`GCProg.emit(t *Type, offset int64)` メソッド**:
    このメソッドは、与えられた型`t`のポインタ情報をGCプログラムとしてエンコードします。
    *   ポインタ型、チャネル、関数、マップ、スライスなどの型に対しては、`p.w.Ptr`を呼び出してポインタの存在を記録します。
    *   構造体型に対しては、各フィールドを再帰的に`emit`します。
    *   配列型に対しては、要素の型と配列の長さを考慮し、`p.w.ShouldRepeat`で繰り返し命令を使うべきかを判断します。繰り返しが効率的であれば、要素のGCプログラムを一度`emit`し、`p.w.Repeat`で繰り返します。そうでなければ、各要素を個別に`emit`します。これにより、大きな配列のポインタ情報を非常にコンパクトに表現できます。

### `src/reflect/type.go`

`reflect`パッケージは、ランタイムの型情報を扱うためのGoのAPIを提供します。

*   **`rtype` 構造体の変更**:
    ```go
    type rtype struct {
        // ...
        gcdata        *byte          // garbage collection data
        // ...
    }
    ```
    `gc`フィールドが`[2]unsafe.Pointer`から`*byte`型の`gcdata`に変更されました。これは、GCプログラムまたはポインタマスクの先頭へのポインタを保持します。

*   **`ArrayOf` 関数の変更**:
    `ArrayOf`関数は、新しい配列型を動的に構築する際に、そのGC情報を生成します。
    *   要素がポインタを含まない場合や配列サイズが0の場合は、ポインタ情報なしとして扱います。
    *   配列の要素数が1の場合、要素のGC情報をそのまま使用します。
    *   要素が小さく、配列全体も小さい場合（`16*8*ptrSize`ワード以下）、要素のポインタマスクを基に、配列全体の直接ポインタマスクを生成します。
    *   それ以外の場合（大きな配列や、要素自体がGCプログラムを持つ場合）、新しいGCプログラムを生成します。この際、要素のGCプログラムを一度エンコードし、`Repeat`命令を使って配列の繰り返しを表現します。

これらの変更により、Goランタイムはより効率的にポインタ情報を管理し、GCのパフォーマンスを向上させることが可能になりました。

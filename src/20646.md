# [インデックス 20646] ファイルの概要

このコミットは、`go get` コマンドがクリーンな `GOPATH` 環境において、ワイルドカード (`...`) を含むバニティインポートパス（例: `vanity/repo/...`）を正しく処理できない問題を修正します。具体的には、`go get` がリポジトリを初めてチェックアウトする際に、ワイルドカードを含むパスのルートリポジトリを動的に解決できるよう、内部のパス解決ロジックを改善しています。

## 変更の背景

`go get` コマンドは、Goパッケージをダウンロードしてインストールするために使用されます。Goのパッケージ管理システムでは、`GOPATH` という環境変数で指定されたワークスペースにソースコードが配置されます。また、Goは「バニティインポートパス」という仕組みを提供しており、`github.com/user/repo` のような直接的なバージョン管理システム（VCS）のパスではなく、`example.com/mypackage` のようなカスタムドメインをインポートパスとして使用できます。これは、基盤となるホスティングプロバイダが変わってもインポートパスを安定させるために非常に有用です。

このコミットが修正する問題は、`go get` がワイルドカード (`...`) を含むバニティインポートパス（例: `rsc.io/pdf/...`）を、まだリポジトリがローカルに存在しない「クリーンな `GOPATH`」環境で処理しようとした際に発生していました。既存のコードでは、この種のパスが既にチェックアウトされている場合にのみ機能し、初回ダウンロード時には正しくリポジトリのルートを特定できませんでした。これは、`go get` がバニティパスを解決するために必要なメタタグ情報を取得する際に、ワイルドカードが邪魔をしていたためです。

この問題は Go issue #8335 として報告されており、このコミットはその問題を解決し、`go get` がワイルドカードを含むバニティインポートパスでも、初回から正しく動作するようにすることを目的としています。

## 前提知識の解説

### Go Modules と GOPATH

Goのパッケージ管理は、歴史的に `GOPATH` と呼ばれるワークスペースモデルに基づいていました。`GOPATH` は、Goのソースコード、コンパイル済みバイナリ、パッケージキャッシュが配置されるディレクトリのルートを指定する環境変数です。`go get` コマンドは、指定されたパッケージのソースコードを `GOPATH/src` ディレクトリ以下にダウンロードします。
（注: このコミットは2014年のものであり、Go Modulesが導入される前のGoのバージョンにおける挙動を扱っています。現在のGoのバージョンではGo Modulesが主流ですが、当時の文脈を理解するためには`GOPATH`の知識が不可欠です。）

### `go get` コマンド

`go get` は、リモートリポジトリからGoパッケージをフェッチし、依存関係を解決し、必要に応じてビルド・インストールを行うコマンドです。通常、`go get example.com/some/package` のように使用され、指定されたパッケージを `GOPATH/src/example.com/some/package` にダウンロードします。

### バニティインポートパス (Vanity Import Paths)

バニティインポートパスは、Goパッケージのインポートパスを、実際のVCSホスティングURL（例: `github.com/user/repo`）から独立させるための仕組みです。これにより、`example.com/mypackage` のようなカスタムドメインをインポートパスとして使用できます。

`go get` がバニティインポートパスを解決するプロセスは以下の通りです：
1.  `go get` は、バニティインポートパスに対して `?go-get=1` クエリパラメータを付加したHTTP(S)リクエストを送信します（例: `https://example.com/mypackage?go-get=1`）。
2.  バニティドメインをホストするウェブサーバーは、HTMLページを返します。このHTMLの `<head>` セクションには、特別な `<meta name="go-import" ...>` タグが含まれています。
3.  このメタタグは、実際のソースコードリポジトリの場所とVCSタイプを `go get` に伝えます。フォーマットは `<meta name="go-import" content="<import-prefix> <vcs> <repo-root>">` です。
    *   `<import-prefix>`: バニティインポートパス自体（例: `example.com/mypackage`）。
    *   `<vcs>`: 使用されているバージョン管理システム（例: `git`, `hg`）。
    *   `<repo-root>`: ソースコードリポジトリの実際のURL（例: `https://github.com/myuser/mypackage`）。
4.  `go get` はこのメタタグを解析し、提供されたVCSタイプとリポジトリURLを使用してソースコードをフェッチします。

### ワイルドカード (`...`)

Goのインポートパスにおけるワイルドカード (`...`) は、特定のプレフィックスを持つ複数のパッケージを指すために使用されます。例えば、`go get example.com/some/package/...` は、`example.com/some/package` 以下にあるすべてのサブパッケージをダウンロード・インストールしようとします。

## 技術的詳細

このコミットの核心は、`src/cmd/go/vcs.go` ファイル内の `repoRootForImportPath` 関数にあります。この関数は、与えられたインポートパスに対応するリポジトリのルートを特定する役割を担っています。

以前の挙動では、`repoRootForImportPath` がインポートパスを静的に解決できない場合（つまり、ローカルにリポジトリが存在しない場合や、VCSのURLが直接指定されていない場合）、`repoRootForImportDynamic` 関数を呼び出して動的な解決（バニティインポートパスの解決）を試みていました。

問題は、`go get rsc.io/pdf/...` のようにワイルドカードを含むパスが `repoRootForImportDynamic` に渡されたときに発生しました。`repoRootForImportDynamic` は、バニティインポートパスのメタタグを問い合わせるために、ワイルドカードを含まない「ベース」のインポートパスを期待していました。しかし、ワイルドカードが含まれたまま渡されると、正しいメタタグの問い合わせURLを構築できず、結果としてリポジトリのルートを特定できませんでした。そのため、初回ダウンロードが失敗していました。

このコミットによる修正は、`repoRootForImportDynamic` を呼び出す前に、インポートパスからワイルドカード部分を適切にトリミングするロジックを追加することです。

具体的には、以下の処理が追加されました：
1.  インポートパスの末尾が `"/..."` で終わる場合、その部分を削除します（例: `rsc.io/pdf/...` -> `rsc.io/pdf`）。
2.  インポートパスの途中に `"/.../"` が含まれる場合、その最初の出現箇所までをトリミングします（例: `rsc.io/pdf/.../subpackage` -> `rsc.io/pdf`）。

このトリミングされたパス（`lookup` 変数に格納される）が `repoRootForImportDynamic` に渡されることで、`go get` は `rsc.io/pdf?go-get=1` のような正しいURLを構築し、ウェブサーバーから適切な `go-import` メタタグを取得できるようになります。これにより、クリーンな `GOPATH` 環境でもワイルドカードを含むバニティインポートパスの初回ダウンロードが成功するようになりました。

### `src/cmd/go/vcs.go` の変更

```diff
--- a/src/cmd/go/vcs.go
+++ b/src/cmd/go/vcs.go
@@ -361,7 +361,14 @@ var httpPrefixRE = regexp.MustCompile(`^https?:`)\n func repoRootForImportPath(importPath string) (*repoRoot, error) {\n 	rr, err := repoRootForImportPathStatic(importPath, "")\n 	if err == errUnknownSite {\n-\t\trr, err = repoRootForImportDynamic(importPath)\n+\t\t// If there are wildcards, look up the thing before the wildcard,\n+\t\t// hoping it applies to the wildcarded parts too.\n+\t\t// This makes 'go get rsc.io/pdf/...' work in a fresh GOPATH.\n+\t\tlookup := strings.TrimSuffix(importPath, "/...")\n+\t\tif i := strings.Index(lookup, "/.../"); i >= 0 {\n+\t\t\tlookup = lookup[:i]\n+\t\t}\n+\t\trr, err = repoRootForImportDynamic(lookup)\n \n \t\t// repoRootForImportDynamic returns error detail\n \t\t// that is irrelevant if the user didn't intend to use a\n```

この変更は、`repoRootForImportPath` 関数内で `err == errUnknownSite` となり、動的なリポジトリルート解決が必要な場合に適用されます。
- `lookup := strings.TrimSuffix(importPath, "/...")`: まず、インポートパスの末尾から `"/..."` を削除します。これにより、`rsc.io/pdf/...` のようなパスが `rsc.io/pdf` に変換されます。
- `if i := strings.Index(lookup, "/.../"); i >= 0 { lookup = lookup[:i] }`: 次に、パスの途中に `"/.../"` が含まれる場合（例: `rsc.io/pdf/.../subpackage`）、その最初の出現箇所までを `lookup` パスとして使用します。これにより、`rsc.io/pdf` が抽出されます。
- 最終的に、この `lookup` 変数に格納されたパスが `repoRootForImportDynamic` 関数に渡されます。これにより、`repoRootForImportDynamic` はワイルドカードを含まない正しいベースパスでバニティインポートパスの解決を試みることができ、`go get` がリポジトリのメタ情報を正しく取得できるようになります。

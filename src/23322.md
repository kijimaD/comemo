# [インデックス 23322] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における`gcWork`キャッシュの処理順序に関するバグを修正するものです。具体的には、GCコントローラーの状態を更新する前に`gcWork`キャッシュを破棄（dispose）するように変更し、GC統計の正確性を向上させています。

## コミット

```
commit c4931a84332cd9528138651f9c12ab6d63921c68
Author: Austin Clements <austin@google.com>
Date:   Fri May 1 18:08:44 2015 -0400

    runtime: dispose gcWork caches before updating controller state
    
    Currently, we only flush the per-P gcWork caches in gcMark, at the
    beginning of mark termination. This is necessary to ensure that no
    work is held up in these caches.
    
    However, this flush happens after we update the GC controller state,
    which depends on statistics about marked heap size and scan work that
    are only updated by this flush. Hence, the controller is missing the
    bulk of heap marking and scan work. This bug was introduced in commit
    1b4025f, which introduced the per-P gcWork caches.
    
    Fix this by flushing these caches before we update the GC controller
    state. We continue to flush them at the beginning of mark termination
    as well to be robust in case any write barriers happened between the
    previous flush and entering mark termination, but this should be a
    no-op.

    Reviewed-on: https://go-review.googlesource.com/9646
    Reviewed-by: Russ Cox <rsc@golang.org>
```

## 元コミット内容

このコミットの目的は、Goランタイムのガベージコレクション（GC）において、`gcWork`キャッシュの破棄タイミングを修正することです。以前は、GCコントローラーの状態が更新された後に`gcWork`キャッシュがフラッシュされていました。しかし、GCコントローラーは、マークされたヒープサイズやスキャン作業に関する統計に依存しており、これらの統計は`gcWork`キャッシュのフラッシュによってのみ更新されます。このため、コントローラーはヒープマーキングとスキャン作業の大部分に関する正確な情報を持っていませんでした。このバグは、`per-P gcWork`キャッシュが導入されたコミット`1b4025f`で発生しました。

この修正では、GCコントローラーの状態を更新する前にこれらのキャッシュをフラッシュするように変更します。マーク終了時にも引き続きフラッシュを行いますが、これは以前のフラッシュとマーク終了の間でライトバリアが発生した場合に備えた堅牢性のためであり、通常は何も行われないはずです。

## 変更の背景

Goのガベージコレクションは、プログラムの実行と並行して動作するコンカレントGCを採用しています。このGCプロセスでは、ヒープ上のオブジェクトをマークし、不要になったオブジェクトを解放します。効率的なGCを実現するために、各プロセッサ（P）は`gcWork`と呼ばれるローカルキャッシュを持ち、GC作業（例えば、マークすべきオブジェクトのポインタ）を一時的に保持します。

GCコントローラーは、GCの進行状況を監視し、次のGCサイクルをいつ開始するか、またはGCの作業量を調整するかを決定するために、ヒープの使用状況やGC作業量に関する統計情報を利用します。これらの統計は、`gcWork`キャッシュに蓄積された情報がグローバルなGC状態に反映されることで初めて正確になります。

しかし、このコミット以前のGoランタイムでは、`gcWork`キャッシュのフラッシュがGCコントローラーの状態更新後に行われていました。これにより、コントローラーが参照する統計情報が古く、不正確なものとなり、GCの意思決定に悪影響を与える可能性がありました。特に、マークされたヒープサイズやスキャン作業の統計が不完全なため、GCコントローラーはヒープの実際の負荷を過小評価し、GCの効率が低下したり、メモリ使用量が意図せず増加したりするリスクがありました。

この問題は、`per-P gcWork`キャッシュが導入されたコミット`1b4025f`で発生したと特定されており、その後のGCの正確性と効率を改善するために、この修正が必要となりました。

## 前提知識の解説

*   **Goのガベージコレクション (GC)**: Goはトレース型GCを採用しており、主に三色マーク＆スイープアルゴリズムをベースにしています。Go 1.5以降、GCはほとんどの作業をアプリケーションと並行して実行するコンカレントGCに移行しました。これにより、GCによるアプリケーションの一時停止（STW: Stop The World）時間を大幅に短縮しています。
*   **P (Processor)**: Goランタイムにおける論理プロセッサの単位です。Goスケジューラは、G（Goroutine）をPに割り当て、PはM（Machine/OSスレッド）上で実行されます。各Pは、GC作業を含む様々なランタイムデータをローカルにキャッシュすることで、ロックの競合を減らし、効率を向上させます。
*   **`gcWork`キャッシュ**: GCのマークフェーズ中に、各Pがマークすべきオブジェクトのポインタを一時的に保持するためのローカルキューまたはスタックです。これにより、グローバルなGC作業キューへのアクセスを減らし、並行性を高めます。
*   **GCコントローラー (`gcController`)**: GoランタイムのGCサブシステムの一部で、GCの動作を制御・調整する役割を担います。ヒープの使用状況、GCの実行時間、アプリケーションのスループットなどの統計を基に、次のGCの開始タイミングや、GCに割り当てるCPUリソースなどを決定します。正確な統計情報は、このコントローラーが最適なGC戦略を立てる上で不可欠です。
*   **マーク終了 (Mark Termination)**: コンカレントGCのフェーズの一つで、マークフェーズの最終段階です。このフェーズでは、残りのGC作業を完了させ、GCの準備を整えるために短いSTWが発生することがあります。
*   **ライトバリア (Write Barrier)**: GCが実行されている間に、アプリケーションがヒープ上のポインタを書き換える際に実行される特別なコードです。これにより、GCがオブジェクトグラフを正確に追跡し、誤って生きているオブジェクトを回収してしまう（または死んでいるオブジェクトをマークし忘れる）ことを防ぎます。

## 技術的詳細

このコミットの核心は、GCコントローラーが依存する統計情報が、`gcWork`キャッシュのフラッシュによって更新されるという点にあります。`gcWork`キャッシュには、GCがマークしたオブジェクトに関する情報や、スキャンが必要な作業（例えば、新しいオブジェクトのポインタ）が蓄積されています。これらの情報がグローバルなGC状態に統合されることで、GCコントローラーはヒープの実際の状態とGCの進行状況を正確に把握できます。

以前の実装では、`gc`関数内で`gcController.endCycle()`が呼び出され、GCコントローラーの状態が更新された後に、`gcMark`関数内で`per-P gcWork`キャッシュのフラッシュが行われていました。この順序では、`gcController.endCycle()`が参照する統計情報には、まだ`gcWork`キャッシュ内に残っている作業が含まれていませんでした。結果として、GCコントローラーは不完全なデータに基づいて意思決定を行っていたことになります。

この修正では、以下の変更が加えられました。

1.  **`gcFlushGCWork()`関数の導入**:
    `gcFlushGCWork`という新しい関数が導入されました。この関数は、すべてのPの`gcWork`キャッシュを破棄し、その内容をグローバルなGC作業キューに統合する役割を担います。この関数は、世界が停止している（STW）状態で呼び出されることを前提としています。`//go:nowritebarrier`ディレクティブが付与されており、この関数内ではライトバリアが不要であることを示唆しています。これは、GC内部の操作であり、アプリケーションのヒープ変更とは異なる文脈で実行されるためです。

    ```go
    // gcFlushGCWork disposes the gcWork caches of all Ps. The world must
    // be stopped.
    //go:nowritebarrier
    func gcFlushGCWork() {
        // Gather all cached GC work. All other Ps are stopped, so
        // it's safe to manipulate their GC work caches.
        for i := 0; i < int(gomaxprocs); i++ {
            allp[i].gcw.dispose()
        }
    }
    ```

2.  **`gc`関数内での`gcFlushGCWork()`の呼び出し順序の変更**:
    `gc`関数（GCのメインエントリポイント）内で、`gcController.endCycle()`が呼び出される前に`gcFlushGCWork()`が呼び出されるようになりました。これにより、GCコントローラーが状態を更新する際には、すべての`gcWork`キャッシュの内容が既にグローバルなGC統計に反映されていることが保証されます。

    ```go
    // Flush the gcWork caches. This must be done before
    // endCycle since endCycle depends on statistics kept
    // in these caches.
    gcFlushGCWork()

    gcController.endCycle()
    ```

3.  **`gcMark`関数内での重複するフラッシュの置き換え**:
    `gcMark`関数内にも、以前は`per-P gcWork`キャッシュをフラッシュするためのループが存在していました。このループは、新しく導入された`gcFlushGCWork()`の呼び出しに置き換えられました。これにより、コードの重複が解消され、一貫性が保たれます。コメントも更新され、マーク終了時にもキャッシュが空であることを確認する目的が明確化されています。これは、以前のフラッシュとマーク終了の間で発生した可能性のあるライトバリアによる変更を捕捉するための「堅牢性」の確保のためです。

    ```go
    // Make sure the per-P gcWork caches are empty. During mark
    // termination, these caches can still be used temporarily,
    // but must be disposed to the global lists immediately.
    gcFlushGCWork()
    ```

この変更により、GCコントローラーはより正確なヒープとGC作業の統計情報に基づいて動作できるようになり、GoランタイムのGCの効率と安定性が向上します。

## コアとなるコードの解説

1.  **`gcFlushGCWork()`関数の追加**:
    *   この新しい関数は、すべての論理プロセッサ（P）が持つ`gcWork`キャッシュを破棄（`dispose()`メソッドを呼び出す）します。
    *   `allp`は、Goランタイムが管理するすべてのPの配列です。`gomaxprocs`は、利用可能なPの総数を示します。
    *   この関数が呼び出される際には「世界が停止している（The world must be stopped）」ことが前提とされており、これにより他のPがGC作業キャッシュを操作していないことが保証され、安全に処理できます。
    *   `//go:nowritebarrier`ディレクティブは、この関数がGCの内部処理であり、通常のヒープポインタの書き込みとは異なるため、ライトバリアの適用が不要であることをコンパイラに伝えます。

2.  **`gc`関数内の呼び出し順序の変更**:
    *   `gc`関数はGCサイクルの主要なオーケストレーションを行います。
    *   以前は`gcController.endCycle()`が先に呼び出されていましたが、このコミットにより、その前に`gcFlushGCWork()`が呼び出されるようになりました。
    *   これにより、`gcController.endCycle()`がGC統計を計算・更新する際に、すべての`gcWork`キャッシュの内容がグローバルなGC状態に完全に反映された、最新かつ正確なデータを利用できるようになります。

3.  **`gcMark`関数内の変更**:
    *   `gcMark`関数は、GCのマークフェーズ（またはマーク終了フェーズ）を実行します。
    *   以前は、`gcMark`関数内に`for`ループがあり、各Pの`gcw.dispose()`を直接呼び出していましたが、これが新しく定義された`gcFlushGCWork()`の呼び出しに置き換えられました。
    *   これにより、コードの重複が排除され、`gcWork`キャッシュのフラッシュロジックが一元化されました。
    *   コメントも「Make sure the per-P gcWork caches are empty.」と変更され、マーク終了時にもキャッシュが空であることを確認する目的が強調されています。これは、GCの堅牢性を高めるための二重のチェックとして機能します。

これらの変更により、GCコントローラーがより正確な情報に基づいてGCの動作を調整できるようになり、Goアプリケーションのパフォーマンスと安定性に寄与します。

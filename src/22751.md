# [インデックス 22751] ファイルの概要

このコミットは、Goコンパイラ（`cmd/internal/gc`）における競合検出器（race detector）のビルドに関する修正です。具体的には、`OGETG`（`runtime.getg`呼び出しを表す内部ノード）が競合検出器のインストゥルメンテーションから除外されるように変更されました。これにより、`runtime.getg`がインライン化によってランタイム以外のパッケージに現れた場合に発生するビルドエラーが解消されます。

## コミット

このコミットは、Goコンパイラの内部ツールである`gc`において、競合検出器のビルドプロセスで発生していた問題を修正します。以前のバージョンでは、`OGETG`操作が競合検出器のインストゥルメンテーション対象として誤って扱われ、ランタイムパッケージ外での`runtime.getg`の呼び出し（特に`runtime.LockOSThread`のインライン化後など）がビルドエラーを引き起こしていました。このコミットでは、`OGETG`を競合検出器が無視する操作のリストに追加することで、この問題を解決しています。

## 変更の背景

Goの競合検出器は、並行処理におけるデータ競合（data race）を検出するための強力なツールです。この検出器は、コンパイル時に特定のコードにインストゥルメンテーション（計測コードの挿入）を行うことで機能します。しかし、ランタイムパッケージ（`runtime`）はGoの実行環境の根幹をなすため、競合検出器によるインストゥルメンテーションの対象外とされています。これは、ランタイムコード自体が競合検出器の動作に影響を与えたり、パフォーマンスに深刻な影響を与えたりする可能性があるためです。

問題は、`runtime.getg`という関数が関係していました。この関数は現在のゴルーチン（goroutine）の`g`構造体（ゴルーチンの内部状態を表す）を返すもので、主にランタイム内部で使用されます。しかし、Goコンパイラの最適化の一つであるインライン化（inlining）によって、`runtime.LockOSThread`のようなランタイム関数がユーザーコードにインライン展開されることがあります。この`runtime.LockOSThread`の内部で`runtime.getg`が呼び出されている場合、インライン化の結果として、`runtime.getg`の呼び出しがランタイムパッケージではないユーザーコードのコンテキストに現れる可能性がありました。

競合検出器のインストゥルメンテーションロジックは、`OGETG`（`runtime.getg`の呼び出しを表すコンパイラ内部の抽象構文木ノード）に遭遇すると、それがランタイムパッケージ外で発生している場合にエラーを報告するように設計されていました。これは、`OGETG`がランタイム内部の操作であり、競合検出器の対象外であるという前提に基づいています。しかし、前述のインライン化のシナリオでは、この前提が崩れ、競合検出器を有効にしてビルドしようとすると、不必要なビルドエラーが発生していました。

このコミットは、この「誤検知」によるビルドエラーを解消し、競合検出器が正しく機能しつつも、ランタイムの内部的な挙動によってビルドが妨げられないようにするために行われました。

## 前提知識の解説

*   **Goコンパイラ (`gc`)**: Go言語の公式コンパイラです。ソースコードを機械語に変換するだけでなく、様々な最適化や、競合検出器のようなツールのためのインストゥルメンテーションも行います。
*   **抽象構文木 (AST)**: コンパイラがソースコードを解析する際に生成する、プログラムの構造を木構造で表現したものです。`OGETG`のような「O」で始まる識別子は、Goコンパイラ内部でASTのノードの種類を表す定数です。
*   **競合検出器 (Race Detector)**: Goに組み込まれているツールで、並行処理におけるデータ競合（複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも一方が書き込み操作である場合に発生する未定義動作）を検出します。コンパイル時にコードに計測コードを挿入し、実行時に競合を監視します。
*   **インストゥルメンテーション (Instrumentation)**: プログラムの実行時の挙動を監視するために、追加のコード（計測コード）を挿入することです。競合検出器は、メモリアクセスや同期操作の前後などにインストゥルメンテーションを行います。
*   **`runtime` パッケージ**: Goのランタイムシステムを実装しているパッケージです。ガベージコレクション、ゴルーチン管理、スケジューリング、システムコールなど、Goプログラムの実行に必要な低レベルな機能を提供します。
*   **`runtime.getg()`**: 現在実行中のゴルーチンの内部表現である`g`構造体へのポインタを返します。これはGoランタイムの内部でゴルーチン固有のデータにアクセスするために使用されます。ユーザーが直接呼び出すことは稀です。
*   **`runtime.LockOSThread()`**: 現在のゴルーチンを、そのゴルーチンが最初に実行されたOSスレッドにロックします。これにより、そのゴルーチンは他のOSスレッドに移動しなくなります。特定のOSスレッドに依存するCgoコードやGUIライブラリなどを使用する場合に必要となることがあります。
*   **インライン化 (Inlining)**: コンパイラの最適化の一つで、関数呼び出しをその関数の本体のコードで直接置き換えることです。これにより、関数呼び出しのオーバーヘッドが削減され、パフォーマンスが向上する可能性があります。

## 技術的詳細

Goの競合検出器は、コンパイル時に`src/cmd/internal/gc/racewalk.go`ファイル内のロジックによってコードを走査し、インストゥルメンテーションの対象となる操作を特定します。この`racewalk.go`ファイルには、`racewalknode`という関数があり、ASTノードを再帰的に走査しながら、競合検出器の計測コードを挿入するかどうかを決定します。

以前の`racewalknode`関数には、`OGETG`ノードに遭遇した場合に`Yyerror`（コンパイラエラーを報告する関数）を呼び出す`case`文がありました。これは、「`OGETG`はランタイムでのみ発生し、ランタイムはインストゥルメンテーションしない」という前提に基づいています。しかし、前述の通り、`runtime.LockOSThread`のような関数がインライン化されると、その内部で呼び出される`runtime.getg`（`OGETG`ノードとして表現される）が、ランタイムパッケージではないユーザーコードのコンテキストに現れることになります。この場合、`racewalknode`は`OGETG`ノードを検出し、それがランタイムパッケージ外にあると判断してエラーを報告していました。

`runtime.getg`が返す`g`構造体はゴルーチンローカルなデータであり、異なるゴルーチン間で共有されることはありません。したがって、`runtime.getg`の呼び出し自体がデータ競合を引き起こす可能性はありません。競合検出器の目的はデータ競合の検出であり、ゴルーチンローカルなデータへのアクセスは競合の対象外です。

このコミットの修正は、この事実に基づいています。`OGETG`ノードがデータ競合を引き起こさないため、競合検出器のインストゥルメンテーションから完全に除外しても問題がないと判断されました。これにより、インライン化によって`OGETG`がユーザーコードに現れても、競合検出器が誤ってエラーを報告することがなくなります。

## コアとなるコードの解説

このコミットの主要な変更点は2つあります。

1.  **`OGETG`のエラーチェックの削除**:
    ```diff
    -	case OGETG:
    -		Yyerror("racewalk: OGETG can happen only in runtime which we don't instrument")
    ```
    以前は、`racewalknode`関数が`OGETG`ノードに遭遇すると、即座にコンパイラエラーを発生させていました。これは、`OGETG`がランタイムパッケージ内でのみ発生するという厳格な仮定に基づいていました。この`case`文が削除されたことで、`OGETG`ノードが検出されても、それ自体がエラーとなることはなくなりました。

2.  **`OGETG`をインストゥルメンテーション不要な操作のリストに追加**:
    ```diff
    +		// g is goroutine local so cannot race. Although we don't instrument
    +		// the runtime package, through inlining the call to runtime.getg can
    +		// appear in non runtime packages, for example, after inlining
    +		// runtime.LockOSThread.
    +		OGETG,
    ```
    `racewalknode`関数には、競合検出器によるインストゥルメンテーションが不要な操作のリストがあります。このリストには、`OPRINT`（`print`文）、`ONONAME`（名前のないノード）、`OLITERAL`（リテラル値）などが含まれています。このコミットでは、このリストに`OGETG`が追加されました。
    追加されたコメントが示すように、`g`（ゴルーチン構造体）はゴルーチンローカルなデータであり、競合の対象にはなりません。また、`runtime.getg`の呼び出しがインライン化によってランタイム以外のパッケージに現れる可能性があることが明記されています。これにより、`OGETG`ノードは競合検出器によって完全に無視され、インストゥルメンテーションの対象から外れることになります。

これらの変更により、競合検出器は`OGETG`ノードを安全にスキップするようになり、`runtime.LockOSThread`などのインライン化によって発生していたビルドエラーが解消されました。

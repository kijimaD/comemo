## 変更の背景

このコミットは、Goコンパイラのリンカ（`cmd/internal/ld`）が`darwin/386`（macOS上の32ビットIntelアーキテクチャ）向けにコードを生成する際に発生していたバグを修正するものです。コミットメッセージによると、この問題は「grind's goto inliner」というツールが`continue`文を移動させ、その意味を変えてしまったことによって引き起こされました。

「grind's goto inliner」は、Goのコンパイラ開発において、コードの最適化や変換を行う内部ツールの一つであると推測されます。特に`goto`文や`continue`文のような制御フローに関わる命令をインライン化する際に、予期せぬ副作用として、本来意図しないループの継続やスキップが発生してしまったと考えられます。

リンカは、コンパイルされたオブジェクトファイルを結合して実行可能ファイルを生成する役割を担っています。この過程で、シンボルの解決やリロケーション（再配置）といった重要な処理が行われます。リロケーションは、プログラムがメモリ上のどこにロードされるかに関わらず正しく動作するように、コード内のアドレス参照を調整するプロセスです。もしリロケーション処理にバグがあると、生成される実行可能ファイルが正しく動作しない、あるいはクラッシュする原因となります。

このバグは、`darwin/386`環境でのリロケーション処理において、特定の`continue`文が誤ったループをスキップしてしまい、結果としてリロケーションが正しく適用されない、または不正なデータが処理されるといった問題を引き起こしていたと推測されます。

## 前提知識の解説

### Goコンパイラとリンカ (`cmd/internal/ld`)

Go言語のツールチェインは、ソースコードをコンパイルし、実行可能ファイルを生成する一連のプロセスを担います。その中で、`cmd/internal/ld`はGoのリンカの実装です。リンカは、コンパイラによって生成された複数のオブジェクトファイル（`.o`ファイルなど）やライブラリを結合し、最終的な実行可能ファイル（または共有ライブラリ）を作成します。この過程で、シンボル（関数名や変数名など）の参照を解決し、コード内のアドレスを実際のメモリ上の位置に合わせて調整する「リロケーション」という処理を行います。

### Mach-Oフォーマット

`darwin`（macOSやiOS）環境では、実行可能ファイルやライブラリのフォーマットとして「Mach-O」（Mach Object）が使用されます。Mach-Oファイルは、ヘッダ、ロードコマンド、セグメント、セクションなどから構成され、プログラムのコード、データ、シンボル情報、リロケーション情報などが格納されています。`ldmacho.go`ファイルは、GoリンカがMach-O形式のファイルを扱うためのロジックを含んでいます。

### リロケーション (Relocation)

リロケーションとは、コンパイル時に決定できなかったアドレス（例えば、他のモジュールで定義されている関数のアドレスや、実行時に決定されるデータのアドレス）を、リンカが最終的な実行可能ファイルを生成する際に解決し、正しいアドレスに置き換える処理です。リロケーション情報は、オブジェクトファイル内に格納されており、リンカはこの情報に基づいてコードやデータを修正します。

### `continue`文とラベル付き`continue`

Go言語における`continue`文は、最も内側の`for`、`range`、`select`、`switch`ループの現在のイテレーションをスキップし、次のイテレーションに進むために使用されます。

```go
for i := 0; i < 5; i++ {
    if i == 2 {
        continue // iが2の場合、このイテレーションをスキップし、次のi=3に進む
    }
    fmt.Println(i)
}
```

一方、Goではラベル付き`continue`を使用することで、ネストされたループにおいて、特定の外側のループの次のイテレーションに進むことができます。

```go
OuterLoop:
for i := 0; i < 3; i++ {
    for j := 0; j < 3; j++ {
        if i == 1 && j == 1 {
            continue OuterLoop // iが1、jが1の場合、OuterLoopの次のイテレーション（i=2）に進む
        }
        fmt.Printf("i: %d, j: %d\n", i, j)
    }
}
```

このコミットの背景にある問題は、リンカの内部処理において、`continue`文が意図せず最も内側のループではなく、外側のループをスキップしてしまったことに起因しています。これは、コード変換ツール（"grind's goto inliner"）がコードを最適化する際に、`continue`文のスコープを誤って解釈したためと考えられます。

## 技術的詳細

このコミットは、`src/cmd/internal/ld/ldmacho.go`ファイル内の`ldmacho`関数におけるリロケーション処理のバグを修正しています。

`ldmacho`関数は、Mach-O形式のオブジェクトファイルからセクション情報を読み込み、その中に含まれるリロケーションエントリを処理する役割を担っています。リロケーションエントリは、コード内の特定のアドレスを修正するための情報を含んでいます。

問題の箇所は、リロケーション処理を行う二重ループの中にありました。

```go
for j = 0; uint32(j) < sect.nreloc; j++ {
    // ...
    if /* some condition */ {
        // skip #1 of 2 rel; continue skips #2 of 2.
        j++

        continue // ここが問題
    }
    // ...
}
```

このコードスニペットでは、`j++`によってリロケーションエントリを一つスキップした後、`continue`文が実行されています。本来の意図は、現在の内側の`for`ループの次のイテレーション（つまり、`j`がインクリメントされた後の次のリロケーションエントリの処理）に進むことでした。

しかし、「grind's goto inliner」というツールがこのコードを変換した際に、この`continue`文が誤って外側のループ（もし存在すれば）や、あるいは全く異なる制御フローの場所へジャンプするように変更してしまった可能性があります。コミットメッセージの「moved a continue and changed its meaning」という記述から、このツールが`continue`文を、それが属するべきループのスコープから外れた場所へ移動させてしまったことが示唆されます。

結果として、`darwin/386`環境でのリロケーション処理において、特定のリロケーションエントリが正しく処理されず、リンカが生成する実行可能ファイルに問題が生じていました。

# [インデックス 20467] ファイルの概要

このコミットは、Goランタイムにおけるヒープダンプ処理中のスタック読み取りオーバーラン（read overrun）を防ぐための修正です。特に、`runtime.goexit`が呼び出された際に、スタックの終端を超えて呼び出し元のプログラムカウンタ（PC）を読み取ろうとすることで発生する可能性のあるメモリフォルトを回避することを目的としています。

## 変更の背景

この変更の背景には、Goランタイムがヒープダンプ（メモリのスナップショット）を生成する際に発生する可能性のある、特定の競合状態や不整合なスタック状態の問題があります。

Goのヒープダンプは、メモリリークのデバッグやメモリ使用パターンの理解に不可欠なツールです。ヒープダンプ時には、Goランタイムはすべてのゴルーチン（goroutine）のコールスタックを検査し、ヒープオブジェクトへのポインタ（ルート）を特定します。このプロセス中に、`runtime.goexit`関数を呼び出して終了しようとしているゴルーチンのスタックを読み取ろうとすると問題が発生する可能性がありました。

`runtime.Goexit`は、呼び出し元のゴルーチンを終了させるためのGoランタイム関数です。この関数は、`panic`とは異なり、エラーを伝播せずにすべての`defer`関数を実行し、ゴルーチンを正常に終了させます。`Goexit`の内部メカニズムは、ゴルーチンが終了する際にそのスタック状態を変更します。

問題は、ヒープダンプが実行されている最中に、あるゴルーチンが`Goexit`を呼び出してスタックを操作している場合、ヒープダンププロセスがそのゴルーチンのスタックを読み取ろうとすると、スタックが不整合な状態にあるために、有効なスタック境界を超えて読み取ろうとする「スタック読み取りオーバーラン」が発生し、結果としてメモリフォルトを引き起こす可能性があったことです。

このコミットは、このような特定のシナリオ、特に`goexit`の呼び出し元PC（プログラムカウンタ）をスタックから読み取ろうとした際に、不正なメモリアドレスでフォルトが発生するのを防ぐことを目的としています。コミットメッセージにあるように、当時はヒープダンプがこの問題を引き起こしていましたが、将来的にはトレースバック（スタックトレースの生成）など、他のランタイム機能でも同様の問題が発生する可能性があったため、潜在的なバグを未然に防ぐための予防的な修正でもあります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とメモリ管理の基礎知識が必要です。

1.  **ゴルーチン (Goroutine)**:
    Goにおける軽量な実行スレッドです。数千、数万のゴルーチンを同時に実行することが可能で、Goの並行処理の基盤となります。各ゴルーチンは独自のスタックを持ち、関数呼び出しの情報を格納します。

2.  **スタック (Stack)**:
    関数呼び出しの際に、ローカル変数、関数引数、戻りアドレス（呼び出し元PC）などが一時的に格納されるメモリ領域です。Goのゴルーチンスタックは、必要に応じて動的にサイズが変更されます（スタックの伸縮）。スタックは通常、メモリの高いアドレスから低いアドレスに向かって成長します。`stack.hi`はスタックの最上位アドレス（スタックの「トップ」）を示し、`stack.lo`はスタックの最下位アドレスを示します。

3.  **プログラムカウンタ (PC: Program Counter)**:
    CPUが次に実行する命令のアドレスを指すレジスタです。関数呼び出し時には、呼び出し元のPC（戻りアドレス）がスタックに保存され、関数が終了した際にそのアドレスに戻って実行を再開します。

4.  **`runtime.Goexit`**:
    Goランタイムが提供する特殊な関数で、現在のゴルーチンを終了させます。この関数が呼び出されると、そのゴルーチン内で`defer`された関数がすべて実行された後、ゴルーチンは終了します。`panic`のように呼び出し元にエラーを伝播させることはありません。

5.  **ヒープダンプ (Heapdump)**:
    Goプログラムの実行中に、ヒープメモリ（動的に確保されるメモリ領域）の状態をスナップショットとして取得するプロセスです。ヒープダンプには、ヒープ上のオブジェクト情報だけでなく、すべてのゴルーチンのスタック情報も含まれます。これは、ガベージコレクタがヒープ上の到達可能なオブジェクトを特定するための「ルート」としてスタック上のポインタを参照するためです。

6.  **ガベージコレクション (Garbage Collection - GC)**:
    Goのランタイムが自動的に不要になったメモリを解放するプロセスです。GCは、ヒープダンプと同様に、ゴルーチンのスタックを走査して、ヒープ上のオブジェクトへの参照（ポインタ）を見つけ出します。

7.  **`uintreg`**:
    Goランタイム内部で使用される型で、レジスタのサイズ（通常はポインタのサイズ、32ビットまたは64ビット）を表します。`sizeof(uintreg)`は、システムにおけるレジスタのバイトサイズを示します。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムが新しいゴルーチンを初期化する際のスタックポインタ（`sp`）の設定方法にあります。

Goランタイムでは、新しいゴルーチンが作成される際、そのゴルーチンのスタックが割り当てられ、スタックポインタ（`gp->sched.sp`）がスタックの最上位アドレス（`gp->stack.hi`）に初期化されます。これは、スタックが通常、高いアドレスから低いアドレスに向かって成長するため、スタックの「トップ」を指すことになります。

しかし、`runtime.goexit`のような特殊な関数が呼び出された場合、そのゴルーチンのスタック状態は非常にデリケートになります。特に、`goexit`の呼び出し元PCをスタックから読み取ろうとするような操作（ヒープダンプやトレースバックなど）が行われると、スタックの境界条件や、`goexit`がスタックを操作している最中の競合状態により、スタックの有効な範囲を超えてアクセスしようとする「読み取りオーバーラン」が発生する可能性がありました。これにより、不正なメモリアドレスへのアクセスが発生し、プログラムがクラッシュする原因となります。

この修正は、新しいゴルーチンが作成される際に、スタックポインタを`gp->stack.hi`から直接開始するのではなく、**意図的に数ワード分（`4 * sizeof(uintreg)`バイト）だけ低いアドレスから開始する**ように変更することで、この問題を解決しています。

具体的には、スタックの最上位アドレスから`4 * sizeof(uintreg)`バイト分だけ「余分なスペース」を確保し、その位置を初期スタックポインタとします。これにより、ヒープダンプなどのツールが`goexit`の呼び出し元PCを読み取ろうとした際に、たとえスタックの終端をわずかに超えてアクセスしようとしたとしても、その「余分なスペース」の範囲内であれば、不正なメモリアドレスへのアクセスを避け、メモリフォルトを防ぐことができます。

この変更は、スタックの割り当てと初期化の段階で予防的なバッファを設けることで、ランタイムの堅牢性を高め、将来的に同様のスタック読み取りに関する問題が発生する可能性を低減しています。

## コアとなるコードの解説

両方の変更箇所で、追加された行は以下の通りです。

```c
X->sched.sp -= 4*sizeof(uintreg); // extra space in case of reads slightly beyond frame
```

ここで、`X`は`gp`（`runtime·newextram`の場合）または`newg`（`runtime·newproc1`の場合）であり、これらは新しく作成されるゴルーチンを表す構造体へのポインタです。

*   `X->sched.sp`: 新しいゴルーチンのスケジューラが使用するスタックポインタです。
*   `X->stack.hi`: ゴルーチンに割り当てられたスタックメモリ領域の最上位アドレスです。スタックは通常、このアドレスから下に向かって成長します。
*   `sizeof(uintreg)`: システムのレジスタサイズ（通常はポインタのサイズ、例えば64ビットシステムでは8バイト）です。
*   `4 * sizeof(uintreg)`: これは、スタックの最上位から確保される「余分なスペース」のバイト数を示します。例えば、64ビットシステムでは `4 * 8 = 32` バイトとなります。

この行が追加される前は、`X->sched.sp`は`X->stack.hi`に直接設定されていました。つまり、スタックポインタはスタックの物理的な最上位に正確に位置していました。

変更後、スタックポインタは`X->stack.hi`から`4 * sizeof(uintreg)`バイトだけ低いアドレスに設定されます。これにより、スタックの物理的な最上位と、実際にゴルーチンが使用を開始するスタックポインタの間に、32バイト（64ビットシステムの場合）のバッファ領域が確保されます。

このバッファは、ヒープダンプやトレースバックなどのランタイムツールが、`runtime.goexit`のような特殊な状況下でゴルーチンのスタックを検査する際に、スタックの終端をわずかに超えて読み取ろうとしたとしても、そのアクセスが不正なメモリ領域ではなく、意図的に確保された安全なバッファ領域内で行われるようにします。これにより、メモリフォルトの発生を防ぎ、ランタイムの安定性と堅牢性が向上します。

# [インデックス 27231] ファイルの概要

このコミットは、Goコンパイラのパーサー（`cmd/compile/internal/gc/parser.go`）から、デッドコードとなっていたチルダ（`~`）演算子の処理を削除するものです。以前のレキサーのクリーンアップにより、このコードパスは到達不能になっていたため、冗長なコードが削除されました。

## 変更の背景

Go言語のコンパイラにおいて、ビットごとのNOT演算子としてC言語などでは`~`が使われますが、Go言語では`^`が使用されます。初期のGoコンパイラでは、ユーザーが誤って`~`を使用した際に、パーサーがこれを検出し、エラーメッセージを表示して`^`の使用を促すロジックが存在していました。

しかし、コミットメッセージによると、レキサー（字句解析器）のクリーンアップが行われた結果、`~`文字はパーサーに到達する前にレキサーによって「不正な文字（illegal character U+007E '~'）」として既に捕捉され、エラーが報告されるようになっていました。この変更により、パーサー内の`~`演算子を特別に処理するコードパスは決して実行されない「デッドコード」となっていました。

このコミットは、この到達不能なデッドコードを削除し、コンパイラのコードベースを整理することを目的としています。レキサーによるエラー報告で十分であると判断されたため、パーサー側の冗長な処理は不要となりました。これはIssue #13244に関連する変更です。

## 前提知識の解説

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。Goのツールチェインの一部として提供されます。
*   **レキサー (Lexer / 字句解析器)**: コンパイラの最初の段階で、ソースコードの文字列を読み込み、意味のある最小単位である「トークン」（キーワード、識別子、演算子、リテラルなど）のストリームに分解する役割を担います。例えば、`var x = 10`というコードは、`var` (キーワード), `x` (識別子), `=` (演算子), `10` (リテラル)といったトークンに分解されます。
*   **パーサー (Parser / 構文解析器)**: レキサーが生成したトークンのストリームを受け取り、Go言語の文法規則に従ってそれらを解析し、プログラムの構造を表現する「抽象構文木（Abstract Syntax Tree: AST）」を構築します。このASTは、後続のコンパイル段階（意味解析、コード生成など）で利用されます。
*   **`~` 演算子**: 多くのプログラミング言語（C, C++, Javaなど）でビットごとのNOT（1の補数）を表す単項演算子です。しかし、Go言語ではビットごとのNOTには`^`演算子を使用します。`~`はGo言語の組み込み演算子ではありません。
*   **デッドコード (Dead Code)**: プログラムの実行フローにおいて、決して実行されることのないコードブロックや関数を指します。デッドコードは、プログラムのサイズを不必要に増やし、保守性を低下させる可能性があるため、通常は削除することが推奨されます。
*   **Issue #13244**: GoプロジェクトのIssueトラッカーで管理されている特定の課題やバグ報告です。このコミットは、このIssueの解決に関連しています。

## 技術的詳細

このコミットの核心は、Goコンパイラのフロントエンドにおける字句解析と構文解析の役割分担の明確化と最適化にあります。

Go言語のコンパイラは、ソースコードを処理する際に以下の主要な段階を経ます。
1.  **字句解析 (Lexical Analysis)**: `src/cmd/compile/internal/syntax` パッケージ（または以前の`src/cmd/compile/internal/gc/lex.go`など）が担当し、ソースコードをトークンに変換します。この段階で、Go言語の文法に存在しない不正な文字（例: `~`）が検出されると、通常はエラーが報告されます。
2.  **構文解析 (Syntactic Analysis)**: `src/cmd/compile/internal/gc/parser.go` が担当し、トークン列からASTを構築します。この段階では、トークンの並びがGo言語の文法規則に合致するかどうかを検証します。

以前は、レキサーが`~`を不正な文字として認識しつつも、パーサーがさらに`~`を特別に処理するロジックを持っていました。これは、Go言語がまだ新しかった頃に、C言語からの移行者が`~`を誤用する可能性を考慮し、より親切なエラーメッセージを提供するためのものであったと考えられます。パーサーは`~`を見つけると、「ビットごとの補数演算子は`^`です」という具体的なエラーメッセージを出し、内部的には`^`演算子として処理を続行していました。

しかし、レキサーの改善により、`~`はパーサーに到達する前に「`illegal character U+007E '~'`」というエラーで捕捉されるようになりました。このエラーメッセージは、ユーザーにとって十分理解できるものであり、パーサーがさらに介入する必要がなくなりました。

したがって、このコミットは、パーサー内の`uexpr()`関数（単項式を解析する関数）から`case '~':`ブロックを削除し、`stmt()`関数（ステートメントを解析する関数）内の単項演算子のリストから`~`を削除することで、デッドコードを排除し、コンパイラのコードベースを簡素化しています。これにより、コンパイラの効率がわずかに向上し、保守性が高まります。

## コアとなるコードの解説

1.  **`func (p *parser) uexpr() *Node` 内の変更**:
    *   `uexpr()`関数は、単項式（例: `-x`, `!b`, `^mask`）を解析し、対応する抽象構文木（AST）ノードを生成する役割を担っています。
    *   削除された`case '~':`ブロックは、`~`演算子を検出した際の処理を定義していました。このブロックでは、`p.next()`で次のトークンを読み込み、`p.uexpr()`でオペランドを解析し、`Yyerror("the bitwise complement operator is ^")`というエラーメッセージを出力していました。そして、`Nod(OCOM, x, nil)`を返して、内部的にはビットごとの補数（`OCOM`）として扱っていました。
    *   このブロックが削除されたことで、パーサーは`~`を単項演算子として認識しなくなりました。

2.  **`func (p *parser) stmt() *Node` 内の変更**:
    *   `stmt()`関数は、Go言語の様々なステートメント（文）を解析する関数です。
    *   `case`文のリストは、ステートメントの開始トークンとして認識される可能性のあるものを列挙しています。このリストから`'~'`が削除されました。
    *   これにより、パーサーは`~`が単項演算子としてステートメントの開始部分に現れることを期待しなくなりました。

これらの変更は、`~`がレキサーによって早期に不正な文字として処理されるようになったため、パーサーが`~`を特別に扱う必要がなくなったことを反映しています。結果として、コンパイラのコードがよりシンプルで効率的になりました。

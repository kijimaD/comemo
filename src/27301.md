# [インデックス 27301] ファイルの概要

このコミットは、Goリンカ（`cmd/link`）におけるシンボル処理の最適化に関するものです。具体的には、オブジェクトファイル内の特殊なシンボル（`$-symbols`と`runtime.gcbits.`）のパッチ適用処理が、オブジェクトファイルごとに一度だけ行われるように変更され、リンカのパフォーマンスが向上しました。

## コミット

cmd/link: オブジェクトファイルごとにシンボルを一度だけパッチ適用する

## 変更の背景

Goプログラムのビルドプロセスにおいて、リンカ（`cmd/link`）はコンパイルされた複数のオブジェクトファイルやライブラリを結合し、実行可能なバイナリを生成する重要な役割を担っています。このプロセスでは、各オブジェクトファイルが参照するシンボル（関数、変数など）を解決し、最終的なアドレスを割り当て、必要に応じてメタデータを付与する「パッチ適用」のような処理が行われます。

以前の実装では、特定の種類のシンボル（特に`$-symbols`と呼ばれるリテラルデータシンボルや、ガベージコレクション（GC）に関連する`runtime.gcbits.`シンボル）に対するパッチ適用ロジックが、`rdsym`という関数内に存在していました。`rdsym`はシンボルを読み込むたびに呼び出される可能性があり、その結果、同じシンボルに対して複数回、冗長なパッチ適用処理が実行されることがありました。

この冗長な処理は、特に大規模なプロジェクトや多数のオブジェクトファイルをリンクする際に、リンカの実行時間に悪影響を与えていました。このコミットの目的は、この非効率性を解消し、リンカのパフォーマンスを向上させることにありました。ベンチマーク結果が示すように、リンカの実行時間が約2〜3%短縮されており、これはビルド時間の短縮に直接貢献します。

## 前提知識の解説

このコミットを理解するためには、以下のGoリンカとGoランタイムに関する基本的な知識が必要です。

1.  **Goリンカ (`cmd/link`)**:
    Goのツールチェインの一部であり、コンパイラによって生成されたオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合し、単一の実行可能バイナリを生成します。この過程で、シンボル解決（どの関数がどこにあるか、どの変数がどこに格納されるか）や再配置（コード内のアドレス参照を実際のメモリ位置に更新する）を行います。

2.  **シンボル (Symbols)**:
    プログラム内の関数、グローバル変数、型などの名前付きエンティティを指します。リンカはこれらのシンボルを管理し、プログラム全体で一意に解決します。

3.  **オブジェクトファイル (Object Files)**:
    GoコンパイラがGoソースコードをコンパイルして生成する中間ファイルです。これには、機械語コード、データ、およびシンボルテーブル（そのファイル内で定義または参照されるシンボルのリスト）が含まれます。

4.  **`$-symbols`**:
    Goリンカの内部的なメカニズムで使用される特殊なシンボルです。コミットのコード変更から、これらは主に浮動小数点数（`$f32.`, `$f64.`) や整数 (`$i64.`) のリテラル値をバイナリに埋め込むために使用されることが示唆されます。これらのシンボルは、その名前に続く16進数文字列から実際の数値データにパースされ、読み取り専用データセクション（`SRODATA`）に配置されます。これらは通常、Goのソースコードから直接参照されることはなく、コンパイラやリンカの内部処理で生成されます。

5.  **`runtime.gcbits.`**:
    Goのガベージコレクタ（GC）が正確かつ効率的に動作するために不可欠なメタデータです。GoのGCはポインタを追跡して到達可能なオブジェクトを特定するマーク＆スイープ方式を採用しています。`runtime.gcbits.`は、メモリ上の特定のデータ構造（例えば、構造体や配列）のどの部分がポインタを含み、どの部分が非ポインタデータであるかを示すビットマスク情報を提供します。この情報により、GCはヒープやスタックをスキャンする際に、誤って非ポインタデータをポインタとして解釈したり、その逆を行ったりすることを防ぎます。リンカは、コンパイラが生成したこの`gcbits`情報を最終的な実行可能バイナリに埋め込み、ランタイムが利用できるようにします。

6.  **`Linklookup`**:
    リンカの内部関数で、指定された名前とバージョンを持つシンボルを検索し、存在すればそのシンボル構造体（`LSym`）を返します。存在しない場合は新しいシンボルを作成します。

7.  **`LSym` (Linker Symbol)**:
    Goリンカが内部的にシンボルを表現するために使用する構造体です。シンボルの名前、バージョン、タイプ（コード、データなど）、属性（ローカル、到達可能など）、および関連するデータ（`P`フィールド）などの情報を含みます。

## 技術的詳細

このコミットの核心は、Goリンカの`src/cmd/link/internal/ld/objfile.go`ファイル内のシンボル処理ロジックの再配置にあります。

以前は、`rdsym`関数がシンボルを読み込む際に、そのシンボルが`$-symbols`（例: `$f32.`, `$f64.`, `$i64.`) や`runtime.gcbits.`プレフィックスを持つ特殊なシンボルであるかどうかをチェックし、それに応じてシンボルのタイプ（`SRODATA`）や属性（`AttrLocal`、`AttrReachable`）を設定し、必要に応じてデータ（`Adduint32`, `Adduint64`）を追加していました。

しかし、`rdsym`関数は、オブジェクトファイル内のシンボルが参照されるたびに呼び出される可能性がありました。これにより、同じ特殊なシンボルに対して、すでに一度処理されているにもかかわらず、再度同じチェックとパッチ適用ロジックが実行されるという非効率が生じていました。

このコミットでは、この特殊シンボルのパッチ適用ロジックを`rdsym`から`readref`関数に移動しました。

*   **`readref`関数**: この関数は、オブジェクトファイルが参照するシンボルを読み込む際に呼び出されます。シンボルが初めて参照される際に、`Linklookup`を使ってシンボルを取得し、`ctxt.CurRefs`に追加します。
*   **変更のロジック**: `readref`内で、シンボルが`Linklookup`によって取得された直後に、そのシンボルが`$-symbols`または`runtime.gcbits.`であるかどうかのチェックとパッチ適用ロジックが実行されるようになりました。
    *   `s == nil || v != 0` の条件は、シンボルがまだ存在しない場合や、バージョンが0でない（つまり、すでに処理済みであるか、特殊な処理が不要な）場合は、このパッチ適用ロジックをスキップすることを示唆しています。これにより、シンボルが初めて参照され、かつバージョンが0（未処理）の場合にのみ、パッチ適用が実行されることが保証されます。
    *   `$-symbols`の場合、シンボル名から16進数値をパースし、`SRODATA`タイプとして設定し、`Adduint32`または`Adduint64`で実際のデータとして追加します。
    *   `runtime.gcbits.`シンボルの場合、`AttrLocal`属性を設定します。

この変更により、各特殊シンボルはオブジェクトファイル内で最初に参照されたときに一度だけ処理されるようになり、冗長な処理が排除されました。結果として、リンカの実行効率が向上し、ベンチマークで示されたパフォーマンス改善につながりました。

## コアとなるコードの変更箇所

変更は`src/cmd/link/internal/ld/objfile.go`ファイルに集中しています。

具体的には、以下のコードブロックが`rdsym`関数から削除され、`readref`関数内に移動・調整されました。

**`rdsym`から削除された部分（旧コード）:**
```go
	if s.Name[0] == '$' && len(s.Name) > 5 && s.Type == 0 {
		x, err := strconv.ParseUint(s.Name[5:], 16, 64)
		if err != nil {
			log.Panicf("failed to parse $-symbol %s: %v", s.Name, err)
		}
		s.Type = obj.SRODATA
		s.Attr |= AttrLocal
		switch s.Name[:5] {
		case "$f32.":
			if uint64(uint32(x)) != x {
				log.Panicf("$-symbol %s too large: %d", s.Name, x)
			}
			Adduint32(ctxt, s, uint32(x))
		case "$f64.", "$i64.":
			Adduint64(ctxt, s, x)
		default:
			log.Panicf("unrecognized $-symbol: %s", s.Name)
		}
		s.Attr.Set(AttrReachable, false)
	}
	if strings.HasPrefix(s.Name, "runtime.gcbits.") {
		s.Attr |= AttrLocal
	}
```

**`readref`に追加された部分（新コード）:**
```go
	s := Linklookup(ctxt, name, v)
	ctxt.CurRefs = append(ctxt.CurRefs, s)

	if s == nil || v != 0 {
		return
	}
	if s.Name[0] == '$' && len(s.Name) > 5 && s.Type == 0 && len(s.P) == 0 {
		x, err := strconv.ParseUint(s.Name[5:], 16, 64)
		if err != nil {
			log.Panicf("failed to parse $-symbol %s: %v", s.Name, err)
		}
		s.Type = obj.SRODATA
		s.Attr |= AttrLocal
		switch s.Name[:5] {
		case "$f32.":
			if uint64(uint32(x)) != x {
				log.Panicf("$-symbol %s too large: %d", s.Name, x)
			}
			Adduint32(ctxt, s, uint32(x))
		case "$f64.", "$i64.":
			Adduint64(ctxt, s, x)
		default:
			log.Panicf("unrecognized $-symbol: %s", s.Name)
		}
		s.Attr.Set(AttrReachable, false)
	}
	if strings.HasPrefix(s.Name, "runtime.gcbits.") {
		s.Attr |= AttrLocal
	}
```

## コアとなるコードの解説

変更のポイントは以下の通りです。

1.  **ロジックの移動**: `$-symbols`と`runtime.gcbits.`の処理ロジックが、`rdsym`関数から`readref`関数へと移動しました。
2.  **実行タイミングの変更**:
    *   `rdsym`は、シンボルが読み込まれるたびに呼び出される可能性がありました。
    *   `readref`は、オブジェクトファイルが参照するシンボルを処理する際に呼び出されます。この関数内で`Linklookup`によってシンボルが取得され、`ctxt.CurRefs`（現在の参照リスト）に追加されます。
3.  **重複処理の回避**: `readref`関数内で、シンボルが`Linklookup`で取得された直後にパッチ適用ロジックが実行されるようになりました。
    *   `if s == nil || v != 0 { return }` というガード句が追加されています。これは、シンボルがまだ存在しない場合（`s == nil`）や、シンボルにバージョンが設定されている場合（`v != 0`、つまり既に処理済みであるか、特殊な処理が不要な場合）には、以降のパッチ適用ロジックをスキップすることを意味します。
    *   これにより、各特殊シンボルは、オブジェクトファイル内で最初に参照され、かつまだ処理されていない場合にのみ、一度だけパッチ適用されることが保証されます。
4.  **`len(s.P) == 0` の追加**: `$-symbols`の条件に`&& len(s.P) == 0`が追加されました。これは、シンボルに既にデータ（`P`フィールド）が設定されている場合は、再度パッチ適用を行わないという追加のチェックです。これにより、二重のデータ追加を防ぎ、処理の堅牢性を高めています。

この変更により、リンカはオブジェクトファイル内の特殊シンボルをより効率的に処理できるようになり、全体的なリンク時間の短縮に貢献しました。

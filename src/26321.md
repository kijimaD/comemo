# [インデックス 26321] ファイルの概要

このコミットは、Go言語のビルドシステム (`cmd/dist`) において、特定のアーキテクチャ（mips64およびmips64le）での並列テスト実行数をCPUコア数に制限することで、テストの実行速度を改善することを目的としています。特に、メモリが少ない環境でのスワップ発生を抑制し、テスト全体の完了時間を短縮する効果があります。

## コミット

`cmd/dist`: mips64xでの並列テストをNumCPUに制限

mips64およびmips64leのビルダ、特にmips64leビルダの一部のマシンはメモリ量が少ないです。CL 18199以降、`test`ディレクトリの実行時に起動されるプロセスが増加し、大量のスワップが使用されるようになったため、テストの実行が遅延していました。このコミットは、512MBメモリを搭載したLoongson 2Eでの`all.bash`の実行時間を5時間から3時間に短縮します。

## 変更の背景

Go言語のプロジェクトでは、様々なアーキテクチャやオペレーティングシステム上でコードが正しく動作することを保証するために、広範なテストスイートが実行されます。これらのテストは、通常、ビルドプロセスの一部として自動的に実行されます。

このコミットが行われた背景には、特に`mips64`および`mips64le`アーキテクチャのビルド環境におけるパフォーマンス問題がありました。コミットメッセージによると、これらのアーキテクチャの一部（特に`mips64le`ビルダの一部のマシン）は、利用可能な物理メモリが少ないという制約を抱えていました。

`CL 18199`という変更（具体的な内容は不明ですが、テストの並列実行に関連する変更と推測されます）が導入された後、`test`ディレクトリ内のテスト実行時に起動されるプロセス数が増加しました。これにより、システムが利用可能なメモリを使い果たし、ディスク上のスワップ領域を頻繁に使用するようになりました。スワップの多用は、I/O操作の増加を招き、結果としてテスト全体の実行時間を大幅に遅延させる原因となっていました。コミットメッセージでは、512MBメモリのLoongson 2Eマシンで`all.bash`の実行時間が5時間にも達していたことが具体例として挙げられています。

この問題に対処するため、メモリ制約のある環境でのテスト実行を最適化し、ビルド時間を短縮することが喫緊の課題となっていました。

## 前提知識の解説

### Go言語のビルドシステム (`cmd/dist`)

`cmd/dist`は、Go言語のソースコードからGoツールチェイン自体をビルドするための内部ツールです。Goのソースコードをダウンロードして`all.bash`（Unix系）や`all.bat`（Windows系）を実行すると、この`cmd/dist`が起動され、コンパイラ、リンカ、標準ライブラリ、各種ツールなどがビルドされます。このプロセスには、ビルドされたコンポーネントが正しく機能するかを確認するためのテストの実行も含まれます。

### `runtime.NumCPU()`

`runtime.NumCPU()`は、Go言語の標準ライブラリ`runtime`パッケージに含まれる関数で、現在のシステムで利用可能な論理CPUコアの数を返します。この関数は、並列処理を行う際に、システムのハードウェアリソースを最大限に活用しつつ、過剰なリソース消費を避けるためのヒントとしてよく使用されます。例えば、並列処理のワーカー数を`NumCPU()`に制限することで、CPUバウンドなタスクがCPUを飽和させ、コンテキストスイッチのオーバーヘッドを増大させることを防ぎます。

### `gohostarch`

`gohostarch`は、Goのビルドシステム内で使用される環境変数または内部変数で、ビルドを実行しているホストマシンのアーキテクチャを示します。例えば、`arm`、`mips64`、`mips64le`、`amd64`などがあります。これにより、ビルドプロセスはホストのアーキテクチャに応じた特定の処理を行うことができます。

### `mips64`と`mips64le`

MIPSは、RISC（Reduced Instruction Set Computer）アーキテクチャの一種です。`mips64`は64ビットMIPSアーキテクチャを指し、`mips64le`はそのリトルエンディアン版です（`le`はLittle Endianの略）。これらのアーキテクチャは、組み込みシステムや特定のサーバー環境で利用されることがあります。Go言語は、これらのアーキテクチャもサポートしており、クロスコンパイルやネイティブビルドが可能です。

### 並列テストとメモリ消費

ソフトウェアのテストスイートは、実行に時間がかかることが多いため、複数のテストを並列に実行することで全体の時間を短縮することが一般的です。しかし、各テストプロセスがそれぞれメモリを消費するため、並列度が高すぎるとシステム全体のメモリ使用量が増大します。物理メモリが不足すると、OSはディスク上のスワップ領域にメモリの内容を一時的に退避させます（スワッピング）。スワッピングは非常に低速なディスクI/Oを伴うため、システムのパフォーマンスを著しく低下させます。

## 技術的詳細

このコミットは、`src/cmd/dist/util.go`ファイル内の`maxbg`変数の設定ロジックを変更しています。`maxbg`は、`cmd/dist`がテストを並列実行する際に同時に起動できるバックグラウンドプロセスの最大数を制御する変数です。

変更前は、`gohostarch == "arm"`の場合にのみ、`maxbg`が`runtime.NumCPU()`によって制限されていました。これは、ARMアーキテクチャのデバイス、特に組み込みシステムやシングルボードコンピュータ（Raspberry Piなど）が、一般的にメモリやCPUリソースが限られていることを考慮した最適化でした。

変更後は、この制限が`mips64`および`mips64le`アーキテクチャにも拡張されました。具体的には、`if gohostarch == "arm"`という条件式が`if gohostarch == "arm" || gohostarch == "mips64" || gohostarch == "mips64le"`に変更されています。これにより、これらのアーキテクチャ上でGoのビルドとテストが実行される際、並列テストの最大数がホストシステムの論理CPUコア数を超えないように強制されます。

`min(maxbg, runtime.NumCPU())`という式は、既存の`maxbg`の値と`runtime.NumCPU()`の小さい方を採用することを意味します。これにより、もし`maxbg`が既に`runtime.NumCPU()`よりも小さい値に設定されている場合でも、その設定が尊重され、`NumCPU()`を超えることはありません。

この変更の技術的な狙いは、メモリが少ない`mips64`および`mips64le`環境で、テストプロセスが過剰なメモリを消費してスワッピングを引き起こすことを防ぐことです。並列実行数をCPUコア数に制限することで、各テストプロセスがCPUリソースを効率的に共有し、メモリ競合を緩和し、結果としてスワップの発生を抑制し、テスト全体の実行時間を短縮します。

## コアとなるコードの解説

変更されたコードブロックは、`cmd/dist`ツールがテスト実行時に使用するバックグラウンドプロセスの最大数（`maxbg`）を決定する部分です。

元のコードでは、以下の条件文がありました。

```go
if gohostarch == "arm" {
    maxbg = min(maxbg, runtime.NumCPU())
}
```

これは、「もしホストアーキテクチャが`arm`であれば、`maxbg`の値を、現在の`maxbg`と`runtime.NumCPU()`の小さい方に設定する」という意味です。これにより、ARM環境では並列テスト数がCPUコア数に制限され、リソースが限られた環境での過負荷を防いでいました。

今回のコミットでは、この条件文が以下のように拡張されました。

```go
if gohostarch == "arm" || gohostarch == "mips64" || gohostarch == "mips64le" {
    maxbg = min(maxbg, runtime.NumCPU())
}
```

この変更により、`arm`アーキテクチャに加えて、`mips64`または`mips64le`アーキテクチャのいずれかである場合にも、同様に`maxbg`が`runtime.NumCPU()`によって制限されるようになりました。

このロジックは、`cmd/dist`がテストを並列実行する際に、システムのリソース（特にメモリ）を過度に消費しないようにするためのガードレールとして機能します。`mips64`および`mips64le`環境で発生していたスワッピングによるパフォーマンス低下を直接的に解決するために導入されました。`runtime.NumCPU()`を使用することで、システムが持つ物理的な並列処理能力を超えない範囲でテストが実行されるようになり、メモリの競合やスワップの発生を抑制し、テストの安定性と実行速度を向上させます。

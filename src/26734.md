# [インデックス 26734] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）の`amd64`アーキテクチャ向けコード生成部分における特定の最適化が、Plan 9オペレーティングシステム上で問題を引き起こすのを修正するものです。具体的には、メモリをゼロクリアする際に使用される`duffzero`最適化が、Plan 9のノートハンドラ（シグナルハンドラに相当）における浮動小数点レジスタの扱いと競合し、ビルドの失敗や実行時エラーの原因となっていました。この変更により、Plan 9環境では`duffzero`および`MOVUPS`命令の使用を無効化し、代わりに安全な方法でメモリをゼロクリアするように修正されています。

## 元コミット内容

このコミットは、Goコンパイラの`amd64`アーキテクチャ向けコード生成ロジックにおいて、Plan 9オペレーティングシステム上での`duffzero`最適化の使用を停止するものです。以前の変更（CL 14408）で、`amd64`における`duffzero`の実装が`MOVQ`命令から`MOVUPS`命令に置き換えられました。しかし、この変更は`plan9/amd64`環境でのビルドを破壊しました。その理由は、Plan 9のノートハンドラが浮動小数点演算を許可しないためです。このコミットは、Plan 9上での`duffzero`の使用を無効にし、`MOVUPS`命令の使用も避けるように修正しています。これにより、Issue #14471で報告された問題が解決されます。

## 変更の背景

この変更の背景には、Goコンパイラが生成するコードの最適化と、特定のオペレーティングシステム（この場合はPlan 9）の低レベルな動作特性との間のミスマッチがあります。

1.  **`duffzero`最適化の導入と変更 (CL 14408)**:
    Goコンパイラは、メモリ領域をゼロで埋める（ゼロクリアする）処理を効率化するために、Duff's Deviceに似た`duffzero`という最適化手法を使用しています。これは、ループを展開して複数のメモリ操作を一度に行うことで、CPUのパイプライン効率を高め、パフォーマンスを向上させるものです。
    以前のCL 14408では、`amd64`アーキテクチャにおいて、この`duffzero`の実装が変更されました。具体的には、64ビットデータを移動する汎用命令である`MOVQ`の代わりに、128ビットのSIMD（Single Instruction, Multiple Data）命令である`MOVUPS`（Move Unaligned Packed Single-precision Floating-point）を使用するように変更されました。`MOVUPS`は、一度に多くのデータを処理できるため、理論的にはゼロクリア処理を高速化できます。

2.  **Plan 9における問題の発生**:
    `MOVUPS`命令は、浮動小数点レジスタ（XMMレジスタなど）を使用します。ここで問題となったのが、Plan 9オペレーティングシステムの「ノートハンドラ」の動作です。Plan 9のノートハンドラは、Unix系のシグナルハンドラに相当するメカニズムですが、その設計上、ノートハンドラが呼び出された際に浮動小数点レジスタの状態が保存・復元される保証がありませんでした。
    もし、`MOVUPS`命令が実行されている最中、またはその命令が浮動小数点レジスタの状態を変更した直後にノートハンドラが割り込むと、ノートハンドラが浮動小数点レジスタを破壊してしまう可能性がありました。これにより、プログラムのクラッシュや予期せぬ動作が発生する可能性があり、実際に`plan9/amd64`環境でのGoのビルドが失敗する原因となりました。

3.  **Issue #14471の報告**:
    この問題は、GoのIssueトラッカーでIssue #14471として報告されました。このIssueでは、`plan9/amd64`環境でGoをビルドしようとすると、`runtime: floating point in note handler`というエラーが発生し、ビルドが中断されることが指摘されました。これは、まさに`MOVUPS`命令の使用とPlan 9のノートハンドラの特性が衝突した結果でした。

このコミットは、この特定の環境における互換性の問題を解決するために、Plan 9上ではパフォーマンス最適化よりも安定性を優先し、`MOVUPS`命令や`duffzero`最適化を無効化するという方針が取られました。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を把握しておく必要があります。

1.  **Duff's Device (ダフのデバイス)**:
    Duff's Deviceは、C言語のプログラマであるTom Duffが考案した、ループ展開（loop unrolling）を効率的に行うためのプログラミングテクニックです。`switch`文と`goto`文を組み合わせて、ループの途中にジャンプすることで、ループのオーバーヘッドを削減し、特にメモリコピーやゼロクリアのような単純な操作のパフォーマンスを向上させます。Goコンパイラにおける`duffzero`は、このDuff's Deviceの原理を応用して、メモリをゼロクリアする処理を最適化するものです。

2.  **`MOVQ`命令と`MOVUPS`命令 (x86-64アセンブリ)**:
    *   **`MOVQ` (Move Quadword)**: x86-64アーキテクチャにおける基本的なデータ転送命令の一つです。64ビット（8バイト）のデータをレジスタ間、レジスタとメモリ間、またはメモリとレジスタ間で移動させます。汎用レジスタ（RAX, RBXなど）を使用します。
    *   **`MOVUPS` (Move Unaligned Packed Single-precision Floating-point)**: SSE（Streaming SIMD Extensions）命令セットの一部です。これは、128ビット（16バイト）のデータを、メモリのアライメント（整列）を気にせずに、XMMレジスタ（浮動小数点演算用のレジスタ）とメモリ間で移動させます。`MOVUPS`は、一度に多くのデータを処理できるため、大量のメモリを高速にゼロクリアするなどのSIMD演算に利用されます。しかし、浮動小数点レジスタを使用するという特性があります。

3.  **Plan 9オペレーティングシステム**:
    Plan 9は、ベル研究所で開発された分散オペレーティングシステムです。Unixの設計思想をさらに推し進め、すべてのリソースをファイルとして表現し、ネットワーク透過性を重視しています。Go言語の開発者の一部はPlan 9の開発にも関わっており、GoはPlan 9をサポートする数少ない現代的な言語の一つです。
    Plan 9は、Unixとは異なるシグナル処理メカニズムを持っています。Unixのシグナルハンドラに相当するのが「ノートハンドラ」です。

4.  **Plan 9のノートハンドラと浮動小数点レジスタ**:
    Plan 9のノートハンドラは、プロセスに非同期イベントを通知するためのメカニズムです。重要なのは、Plan 9のノートハンドラが呼び出される際に、CPUの浮動小数点レジスタ（XMMレジスタなど）の状態が自動的に保存・復元される保証がないという点です。これは、ノートハンドラが非常に軽量であることを意図した設計上の選択です。
    もし、浮動小数点レジスタを使用する命令（例: `MOVUPS`）が実行されている最中にノートハンドラが割り込むと、ノートハンドラが浮動小数点レジスタの内容を上書きしてしまい、元のプログラムに戻ったときに誤った浮動小数点値で処理が続行される可能性があります。これは、プログラムのクラッシュやデータ破損につながる重大なバグとなります。

これらの知識が、なぜ`MOVUPS`命令の使用がPlan 9上で問題を引き起こし、なぜ`duffzero`最適化を無効化する必要があったのかを理解する上で不可欠です。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/amd64/ggen.go`ファイル内のコードを変更し、Plan 9環境でのメモリゼロクリア処理の挙動を調整しています。

1.  **`isPlan9`変数の導入**:
    ```go
    // no floating point in note handlers on Plan 9
    var isPlan9 = obj.Getgoos() == "plan9"
    ```
    `obj.Getgoos()`は現在のターゲットOSを文字列で返す関数です。この行は、コンパイルターゲットがPlan 9であるかどうかを判定し、その結果を`isPlan9`というブール変数に格納します。これにより、以降のコードでPlan 9固有の処理を条件分岐で簡単に制御できるようになります。

2.  **`zerorange`関数の変更**:
    `zerorange`関数は、スタックフレーム内の特定の範囲のメモリをゼロクリアするためにコンパイラが使用する関数です。
    *   **小さな範囲のゼロクリア (`cnt <= int64(8*gc.Widthreg)`)**:
        ```diff
        - 	} else if cnt <= int64(8*gc.Widthreg) {
        + 	} else if !isPlan9 && cnt <= int64(8*gc.Widthreg) {
        ```
        この条件分岐は、比較的小さなメモリ範囲（最大で64バイト、`gc.Widthreg`はレジスタ幅、通常8バイト）をゼロクリアする際に、`MOVUPS`命令（`x86.AXORPS`と`x86.AMOVUPS`）を使用して高速化するロジックを制御しています。変更後、`isPlan9`が`true`の場合（つまりPlan 9の場合）は、この`MOVUPS`を使用する最適化パスはスキップされます。

    *   **大きな範囲のゼロクリア (`duffzero`の利用) (`cnt <= int64(128*gc.Widthreg)`)**:
        ```diff
        - 	} else if !gc.Nacl && (cnt <= int64(128*gc.Widthreg)) {
        + 	} else if !gc.Nacl && !isPlan9 && (cnt <= int64(128*gc.Widthreg)) {
        ```
        この条件分岐は、より大きなメモリ範囲（最大で1024バイト）をゼロクリアする際に、`duffzero`最適化（`obj.ADUFFZERO`）を利用するロジックを制御しています。`gc.Nacl`はGoogle Native Client環境を指し、そこでも特定の制約があるため除外されています。この変更により、Plan 9環境では`duffzero`最適化もスキップされるようになります。

3.  **`clearfat`関数の変更**:
    `clearfat`関数は、大きな構造体や配列などの「fat」なオブジェクトをゼロクリアするために使用されます。
    ```diff
    - 	if w > 1024 || (gc.Nacl && w >= 64) {
    + 	if w > 1024 || (w >= 64 && (gc.Nacl || isPlan9)) {
    ```
    この変更は、ゼロクリアする幅`w`が特定の閾値を超えた場合に、`clearfat_tail`関数を呼び出すかどうかの条件を調整しています。変更後、Plan 9環境では、幅が64バイト以上の場合に`clearfat_tail`が呼び出されるようになります。これは、`clearfat_tail`内でPlan 9向けの特別なゼロクリアロジックが追加されたためです。

4.  **`clearfat_tail`関数の変更**:
    `clearfat_tail`関数は、`clearfat`から呼び出され、実際にメモリをゼロクリアする処理を行います。
    ```go
    +	if b >= 16 && isPlan9 {
    +		var z gc.Node
    +		gc.Nodconst(&z, gc.Types[gc.TUINT64], 0)
    +		q := b / 8
    +		for ; q > 0; q-- {
    +			n1.Type = z.Type
    +			gins(x86.AMOVQ, &z, n1)
    +			n1.Xoffset += 8
    +			b -= 8
    +		}
    +		if b != 0 {
    +			n1.Xoffset -= 8 - b
    +			gins(x86.AMOVQ, &z, n1)
    +		}
    +		return
    +	}
    ```
    この追加されたコードブロックは、`b`（ゼロクリアするバイト数）が16バイト以上で、かつ`isPlan9`が`true`の場合に実行されます。ここでは、`gc.Nodconst(&z, gc.Types[gc.TUINT64], 0)`で64ビットのゼロ定数を作成し、`x86.AMOVQ`命令（64ビットデータを移動する汎用命令）をループで繰り返し使用してメモリをゼロクリアしています。これにより、`MOVUPS`命令や`duffzero`のような浮動小数点レジスタを使用する最適化を避け、Plan 9上で安全にメモリをゼロクリアできるようになります。残りのバイト数（`b % 8`）も適切に処理されます。

これらの変更により、GoコンパイラはPlan 9環境で`MOVUPS`命令や`duffzero`最適化を使用しないようになり、Plan 9のノートハンドラの制約に起因する問題を回避しています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`src/cmd/compile/internal/amd64/ggen.go`ファイルに集中しており、Goコンパイラが`amd64`アーキテクチャ向けにコードを生成する際のメモリゼロクリア戦略をPlan 9向けに調整しています。

1.  **`isPlan9`変数の導入**:
    `var isPlan9 = obj.Getgoos() == "plan9"`
    この行は、コンパイル対象のOSがPlan 9であるかを判定するためのフラグを導入しています。`obj.Getgoos()`は、Goのクロスコンパイル機能において、ターゲットOSの名前（例: "linux", "windows", "plan9"）を返します。このフラグによって、Plan 9特有の制約に対応するための条件分岐が容易になります。

2.  **`zerorange`関数における`MOVUPS`および`duffzero`の無効化**:
    `zerorange`関数は、スタック上のメモリ範囲をゼロクリアする際に呼び出されます。
    *   `else if !isPlan9 && cnt <= int64(8*gc.Widthreg)`:
        この条件は、比較的小さなメモリ範囲（最大64バイト）をゼロクリアする際に、`MOVUPS`命令（`AXORPS`と`AMOVUPS`）を用いた最適化パスを制御します。`!isPlan9`が追加されたことで、Plan 9環境ではこの最適化がスキップされ、代わりに`MOVQ`命令を用いたより基本的なゼロクリア処理が選択されるようになります。`MOVUPS`は浮動小数点レジスタを使用するため、Plan 9のノートハンドラの問題を回避するために無効化されます。
    *   `else if !gc.Nacl && !isPlan9 && (cnt <= int64(128*gc.Widthreg))`:
        この条件は、より大きなメモリ範囲（最大1024バイト）をゼロクリアする際に、`duffzero`最適化を利用するパスを制御します。`!isPlan9`が追加されたことで、Plan 9環境では`duffzero`最適化がスキップされます。`duffzero`は内部的に`MOVUPS`のようなSIMD命令を使用する可能性があり、また、そのアセンブリコードの性質上、ノートハンドラとの相互作用で問題を引き起こす可能性があるため、Plan 9では無効化されます。

3.  **`clearfat`関数における`clearfat_tail`の呼び出し条件の変更**:
    `clearfat`関数は、大きな構造体や配列のゼロクリアを処理します。
    `if w > 1024 || (w >= 64 && (gc.Nacl || isPlan9))`
    この変更により、Plan 9環境では、ゼロクリアするメモリの幅`w`が64バイト以上の場合に`clearfat_tail`関数が呼び出されるようになります。これは、`clearfat_tail`内にPlan 9向けの特別なゼロクリアロジックが追加されたため、そのロジックを適切なタイミングで利用するための調整です。

4.  **`clearfat_tail`関数におけるPlan 9専用のゼロクリアロジックの追加**:
    ```go
    if b >= 16 && isPlan9 {
        var z gc.Node
        gc.Nodconst(&z, gc.Types[gc.TUINT64], 0)
        q := b / 8
        for ; q > 0; q-- {
            n1.Type = z.Type
            gins(x86.AMOVQ, &z, n1)
            n1.Xoffset += 8
            b -= 8
        }
        if b != 0 {
            n1.Xoffset -= 8 - b
            gins(x86.AMOVQ, &z, n1)
        }
        return
    }
    ```
    このコードブロックは、Plan 9環境でのみ実行される、手動でのメモリゼロクリア実装です。
    *   `gc.Nodconst(&z, gc.Types[gc.TUINT64], 0)`: 64ビットのゼロ値を持つ定数ノード`z`を生成します。これは、メモリをゼロで埋めるためのソース値として使用されます。
    *   `q := b / 8`: ゼロクリアするバイト数`b`を8で割り、64ビットワード単位でのループ回数を計算します。
    *   `for ; q > 0; q-- { ... gins(x86.AMOVQ, &z, n1) ... }`: ループ内で`x86.AMOVQ`命令を生成し、64ビットのゼロ値をメモリに書き込みます。`n1.Xoffset += 8`でメモリポインタを8バイト進め、次の64ビットワードを処理します。
    *   `if b != 0 { ... gins(x86.AMOVQ, &z, n1) }`: ループで処理しきれなかった残りのバイト数（8バイト未満）がある場合、その残りのバイト数に合わせてオフセットを調整し、再度`AMOVQ`命令でゼロクリアします。これにより、メモリが完全にゼロで埋められます。

この手動ループによる`AMOVQ`の使用は、`MOVUPS`のようなSIMD命令や`duffzero`のような複雑な最適化を避け、Plan 9のノートハンドラの制約を尊重しつつ、安全かつ確実にメモリをゼロクリアするためのフォールバックメカニズムとして機能します。

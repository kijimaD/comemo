# [インデックス 23625] ファイルの概要

このコミットは、Goランタイムにおけるスタックの境界 (`stack.lo`, `stack.hi`) とスタックの実際の割り当てサイズとの間の結合を解消することを目的としています。具体的には、各ゴルーチンのスタックにGC（ガベージコレクション）メタデータを格納するための領域を確保する準備として、スタックの割り当てサイズを明示的に管理するための新しいフィールド `stackAlloc` を `g` 構造体に追加しています。これにより、`stack.lo` と `stack.hi` は引き続きスタックの有効な使用範囲を示す境界として機能しつつ、実際のメモリ割り当てサイズとは独立して扱われるようになります。

## 元コミット内容

Goランタイムはこれまで、スタックの割り当てが `[stack.lo, stack.hi)` の範囲と完全に一致していると仮定していました。しかし、今後、スタックごとにGCメタデータを格納するために、この割り当て領域の一部を使用する予定があります。この変更は、その準備として、スタックの割り当てサイズを `g` 構造体の新しいフィールド `stackAlloc` で管理するようにします。これにより、`stack.lo` と `stack.hi` は引き続きスタックの実際の使用可能な境界として機能しますが、スタックの割り当て境界としては使用されなくなります。

コミットメッセージでは、`stack.lo` と `stack.hi` を割り当て境界として維持し、新しいスタックトップを導入するという逆のアプローチも検討されたが、`stack.hi` がスタックの真のトップであると仮定している箇所が多いため、現在の変更が採用されたと述べられています。

## 変更の背景

この変更の主な背景は、Goランタイムにおけるガベージコレクション（GC）の進化です。特に、各ゴルーチンのスタックにGCメタデータを格納する必要性が生じたため、既存のスタック管理メカニズムを調整する必要がありました。

これまでのGoランタイムでは、ゴルーチンのスタックは `g.stack.lo` から `g.stack.hi` までの連続したメモリ領域として割り当てられ、この範囲がスタックの利用可能な全領域であると見なされていました。しかし、GCメタデータをスタック内に埋め込むためには、この `[stack.lo, stack.hi)` の範囲から一部を「盗む」必要があります。

この「盗む」という行為は、`stack.lo` と `stack.hi` がスタックの論理的な境界と物理的な割り当て境界の両方を兼ねている現状では問題を引き起こします。もし `stack.hi` が割り当ての終わりを意味するならば、GCメタデータのためにその一部を消費すると、スタックの有効な上限が変更されてしまい、既存のコードに広範な影響を与える可能性があります。

そこで、このコミットでは、`stack.lo` と `stack.hi` をスタックの論理的な使用可能範囲（つまり、プログラムが実際にスタックフレームを配置できる範囲）として維持しつつ、実際のメモリ割り当てサイズを `g.stackAlloc` という新しいフィールドで管理することで、この問題を解決しようとしています。これにより、GCメタデータは `stack.lo` から `stack.lo + stackAlloc` の範囲内のどこかに配置されることになりますが、`stack.lo` と `stack.hi` が示すスタックの「有効な」範囲は変更されません。

この分離は、将来のGCの改善、特にスタックスキャンやスタックの成長・縮小の際に、より柔軟なメタデータ管理を可能にするための重要な基盤となります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念について理解しておく必要があります。

1.  **ゴルーチン (Goroutine)**: Goにおける軽量な実行スレッドです。各ゴルーチンは独自のスタックを持ち、このスタックは必要に応じて動的に拡大・縮小します。

2.  **スタック (Stack)**: 関数呼び出しの引数、ローカル変数、リターンアドレスなどが格納されるメモリ領域です。Goのスタックは「コルーチンスタイル」であり、ヒープ上に割り当てられ、必要に応じてサイズが変更されます。

3.  **`g` 構造体**: Goランタイムにおけるゴルーチンを表す構造体です。この構造体には、ゴルーチンの状態、スケジューリング情報、そしてスタックに関する情報が含まれています。

4.  **`stack` 構造体**: `g` 構造体内にネストされており、ゴルーチンのスタックに関する情報（`lo` と `hi`）を保持します。
    *   `stack.lo`: スタックの最下位アドレス（最も低いアドレス）。Goのスタックは下方向に成長します（アドレスが減少する方向）。
    *   `stack.hi`: スタックの最上位アドレス（最も高いアドレス）。

5.  **`_StackGuard`**: スタックオーバーフローを検出するためのガードページまたはガード領域のオフセットです。スタックポインタが `stack.lo + _StackGuard` を下回ると、スタックの拡張が必要であると判断されます。

6.  **スタックの割り当てと境界**: これまで、Goランタイムでは `stack.lo` と `stack.hi` がスタックの論理的な境界（使用可能な範囲）と、物理的なメモリ割り当ての境界（実際に確保されたメモリ領域）の両方を兼ねていました。つまり、`stack.hi - stack.lo` がスタックの割り当てサイズと等しいと見なされていました。

7.  **GCメタデータ**: ガベージコレクションがオブジェクトやスタックをスキャンする際に必要となる補助情報です。例えば、スタック上のどの位置にポインタがあるか、どの変数がヒープオブジェクトを指しているか、といった情報が含まれます。GoのGCは正確なGC（Precise GC）であり、これらのメタデータはGCの効率と正確性を保証するために不可欠です。

8.  **`malg` 関数**: 新しいゴルーチン（`g`）を割り当て、そのスタックを初期化する関数です。

9.  **`stackalloc` / `stackfree` 関数**: スタックメモリの割り当てと解放を行う関数です。

10. **`copystack` 関数**: スタックのサイズが変更される際に、既存のスタックの内容を新しいサイズのスタックにコピーする関数です。これはスタックの成長（`newstack`）や縮小（`shrinkstack`）の際に使用されます。

## 技術的詳細

このコミットの核心は、`g` 構造体に `stackAlloc uintptr` という新しいフィールドを追加し、スタックの実際の割り当てサイズを `stack.lo` と `stack.hi` から分離することです。

### `g` 構造体への `stackAlloc` フィールドの追加

`src/runtime/runtime2.go` の `g` 構造体に以下のフィールドが追加されました。

```go
type g struct {
    // ... 既存のフィールド ...
    _panic       *_panic // innermost panic - offset known to liblink
    _defer       *_defer // innermost defer
    stackAlloc   uintptr // stack allocation is [stack.lo,stack.lo+stackAlloc)
    sched        gobuf
    // ... 既存のフィールド ...
}
```

`stackAlloc` は `uintptr` 型で、スタックが割り当てられたメモリ領域のサイズをバイト単位で保持します。これにより、スタックの実際の割り当て範囲は `[stack.lo, stack.lo + stackAlloc)` と定義されることになります。

### スタック管理関数の変更

この新しいフィールドの導入に伴い、スタックの割り当て、解放、コピー、サイズ変更に関連する複数のランタイム関数が変更されました。

1.  **`malg` (src/runtime/proc1.go)**:
    *   新しいゴルーチンが作成され、スタックが割り当てられる際に、`newg.stackAlloc = uintptr(stacksize)` が追加され、割り当てられたスタックサイズが `stackAlloc` に設定されます。

2.  **`gfput` (src/runtime/proc1.go)**:
    *   ゴルーチンが再利用のためにプールに戻される際、スタックの解放が必要な場合に、これまでは `gp.stack.hi - gp.stack.lo` でスタックサイズを計算していましたが、`gp.stackAlloc` を使用するように変更されました。
    *   `stackfree(gp.stack)` の呼び出しが `stackfree(gp.stack, gp.stackAlloc)` に変更され、解放するスタックのサイズが明示的に渡されるようになりました。
    *   固定サイズのスタックを再割り当てする際にも、`gp.stackAlloc = _FixedStack` が設定されます。
    *   `racemalloc` の呼び出しも `gp.stack.hi-gp.stack.lo` から `gp.stackAlloc` を使うように変更されました。

3.  **`stackfree` (src/runtime/stack1.go)**:
    *   この関数は、スタックを解放する際に、これまでは `stk.hi - stk.lo` でサイズを計算していましたが、引数として `n uintptr` を受け取るように変更されました。この `n` が実際の割り当てサイズとなります。
    *   新しいアサーション `if stk.lo+n < stk.hi { throw("bad stack size") }` が追加され、渡された割り当てサイズ `n` が `stack.hi` を超えていないことを確認します。これは、`stack.hi` が `stack.lo + n` の範囲内にあることを保証します。

4.  **`copystack` (src/runtime/stack1.go)**:
    *   スタックのコピー時に、`gp.stackAlloc` に新しいスタックサイズが設定されます。
    *   古いスタックを解放する際、これまでは `old.hi - old.lo` を使用していましたが、`oldsize` (古い `gp.stackAlloc` の値) を使用するように変更されました。
    *   スタックを縮小し、後で解放するためにキューに入れる場合、`stackfreequeue` にスタックを格納するだけでなく、そのスタックの割り当てサイズも `old.lo + ptrSize` の位置に格納するように変更されました。これは、`stackfreequeue` からスタックを取り出す際に、その割り当てサイズを正確に取得できるようにするためです。

5.  **`newstack` (src/runtime/stack1.go)**:
    *   スタックを拡張する際に、`oldsize` の計算が `gp.stack.hi - gp.stack.lo` から `gp.stackAlloc` を使用するように変更されました。

6.  **`shrinkstack` (src/runtime/stack1.go)**:
    *   スタックを縮小する際に、`oldsize` の計算が `gp.stack.hi - gp.stack.lo` から `gp.stackAlloc` を使用するように変更されました。
    *   スタック全体を解放する場合も、`stackfree(gp.stack, gp.stackAlloc)` を呼び出すように変更されました。

7.  **`shrinkfinish` (src/runtime/stack1.go)**:
    *   キューに入れられたスタックを解放する際に、`copystack` で格納された割り当てサイズ `n` を `*(*uintptr)(unsafe.Pointer(s.lo + ptrSize))` から読み取り、`stackfree(s, n)` を呼び出すように変更されました。

これらの変更により、Goランタイムはスタックの論理的な境界と物理的な割り当てサイズを明確に区別できるようになり、将来のGCメタデータの導入に備えることができました。

## コアとなるコードの解説

### `src/runtime/runtime2.go` の `g` 構造体

*   `stackAlloc uintptr`: このフィールドの追加が最も根本的な変更です。これにより、ゴルーチンのスタックの実際のメモリ割り当てサイズが `stack.lo` と `stack.hi` から独立して管理されるようになります。コメント `// stack allocation is [stack.lo,stack.lo+stackAlloc)` がその意図を明確に示しています。

### `src/runtime/proc1.go` の変更

*   `malg` 関数: 新しいゴルーチンが作成される際に、`newg.stackAlloc = uintptr(stacksize)` が追加され、割り当てられたスタックの初期サイズが `stackAlloc` に記録されます。
*   `gfput` 関数: ゴルーチンが再利用のためにプールに戻される際、スタックの解放が必要な場合に、スタックサイズを `gp.stackAlloc` から取得するように変更されました。これにより、`stack.hi - stack.lo` という従来の計算方法ではなく、実際の割り当てサイズに基づいて解放が行われます。また、`stackfree` の呼び出しも `stackfree(gp.stack, gp.stackAlloc)` となり、割り当てサイズが明示的に渡されるようになりました。固定サイズのスタックを再割り当てする際にも `gp.stackAlloc = _FixedStack` が設定され、`racemalloc` も同様に `gp.stackAlloc` を使用します。

### `src/runtime/stack1.go` の変更

*   `stackfree` 関数: この関数はスタックを解放する役割を担いますが、変更前は `stk.hi - stk.lo` で解放サイズを決定していました。変更後は `n uintptr` という引数を受け取るようになり、この `n` が実際の割り当てサイズとして使用されます。これにより、`stack.lo` と `stack.hi` が示す論理的な境界と、実際に解放されるメモリ領域のサイズが異なる場合でも正しく処理できるようになります。また、`if stk.lo+n < stk.hi { throw("bad stack size") }` という新しいチェックが追加され、割り当てサイズがスタックの論理的な上限を不適切に超えていないことを保証します。
*   `copystack` 関数: スタックのサイズ変更（成長または縮小）時に呼び出されます。`gp.stackAlloc = newsize` で新しいスタックの割り当てサイズを記録し、`oldsize := gp.stackAlloc` で古いスタックの割り当てサイズを保持します。古いスタックを解放する際も、`stackfree(old, oldsize)` のように `oldsize` を使用します。特に、スタックを縮小して後で解放するためにキューに入れる場合、`*(*uintptr)(unsafe.Pointer(old.lo + ptrSize)) = oldsize` という行が追加され、スタックのベースアドレスのすぐ隣にその割り当てサイズを格納することで、後で解放する際に正しいサイズを取得できるようにしています。
*   `newstack` および `shrinkstack` 関数: これらの関数はスタックの成長と縮小をそれぞれ担当します。どちらも、スタックの現在のサイズを計算する際に、従来の `gp.stack.hi - gp.stack.lo` ではなく、`gp.stackAlloc` を使用するように変更されました。これにより、スタックの論理的な境界と割り当てサイズが分離された設計に準拠します。
*   `shrinkfinish` 関数: `copystack` でキューに入れられたスタックを実際に解放する際に、`*(*uintptr)(unsafe.Pointer(s.lo + ptrSize))` から割り当てサイズ `n` を読み出し、`stackfree(s, n)` を呼び出して正確なサイズのメモリを解放します。

これらの変更は、Goランタイムがスタックのメモリ管理をより柔軟に行えるようにするための重要なステップであり、特に将来のGCの改善（スタックごとのGCメタデータの導入）に向けた基盤を築いています。

## 元コミット内容

Goランタイムはこれまで、スタックの割り当てが `[stack.lo, stack.hi)` の範囲と完全に一致していると仮定していました。しかし、今後、スタックごとにGCメタデータを格納するために、この割り当て領域の一部を使用する予定があります。この変更は、その準備として、スタックの割り当てサイズを `g` 構造体の新しいフィールド `stackAlloc` で管理するようにします。これにより、`stack.lo` と `stack.hi` は引き続きスタックの実際の使用可能な境界として機能しますが、スタックの割り当て境界としては使用されなくなります。

コミットメッセージでは、`stack.lo` と `stack.hi` を割り当て境界として維持し、新しいスタックトップを導入するという逆のアプローチも検討されたが、`stack.hi` がスタックの真のトップであると仮定している箇所が多いため、現在の変更が採用されたと述べられています。

## 変更の背景

この変更の主な背景は、Goランタイムにおけるガベージコレクション（GC）の進化です。特に、各ゴルーチンのスタックにGCメタデータを格納する必要性が生じたため、既存のスタック管理メカニズムを調整する必要がありました。

これまでのGoランタイムでは、ゴルーチンのスタックは `g.stack.lo` から `g.stack.hi` までの連続したメモリ領域として割り当てられ、この範囲がスタックの利用可能な全領域であると見なされていました。しかし、GCメタデータをスタック内に埋め込むためには、この `[stack.lo, stack.hi)` の範囲から一部を「盗む」必要があります。

この「盗む」という行為は、`stack.lo` と `stack.hi` がスタックの論理的な境界と物理的な割り当て境界の両方を兼ねている現状では問題を引き起こします。もし `stack.hi` が割り当ての終わりを意味するならば、GCメタデータのためにその一部を消費すると、スタックの有効な上限が変更されてしまい、既存のコードに広範な影響を与える可能性があります。

そこで、このコミットでは、`stack.lo` と `stack.hi` をスタックの論理的な使用可能範囲（つまり、プログラムが実際にスタックフレームを配置できる範囲）として維持しつつ、実際のメモリ割り当てサイズを `g.stackAlloc` という新しいフィールドで管理することで、この問題を解決しようとしています。これにより、GCメタデータは `stack.lo` から `stack.lo + stackAlloc` の範囲内のどこかに配置されることになりますが、`stack.lo` と `stack.hi` が示すスタックの「有効な」範囲は変更されません。

この分離は、将来のGCの改善、特にスタックスキャンやスタックの成長・縮小の際に、より柔軟なメタデータ管理を可能にするための重要な基盤となります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念について理解しておく必要があります。

1.  **ゴルーチン (Goroutine)**: Goにおける軽量な実行スレッドです。各ゴルーチンは独自のスタックを持ち、このスタックは必要に応じて動的に拡大・縮小します。

2.  **スタック (Stack)**: 関数呼び出しの引数、ローカル変数、リターンアドレスなどが格納されるメモリ領域です。Goのスタックは「コルーチンスタイル」であり、ヒープ上に割り当てられ、必要に応じてサイズが変更されます。

3.  **`g` 構造体**: Goランタイムにおけるゴルーチンを表す構造体です。この構造体には、ゴルーチンの状態、スケジューリング情報、そしてスタックに関する情報が含まれています。

4.  **`stack` 構造体**: `g` 構造体内にネストされており、ゴルーチンのスタックに関する情報（`lo` と `hi`）を保持します。
    *   `stack.lo`: スタックの最下位アドレス（最も低いアドレス）。Goのスタックは下方向に成長します（アドレスが減少する方向）。
    *   `stack.hi`: スタックの最上位アドレス（最も高いアドレス）。

5.  **`_StackGuard`**: スタックオーバーフローを検出するためのガードページまたはガード領域のオフセットです。スタックポインタが `stack.lo + _StackGuard` を下回ると、スタックの拡張が必要であると判断されます。

6.  **スタックの割り当てと境界**: これまで、Goランタイムでは `stack.lo` と `stack.hi` がスタックの論理的な境界（使用可能な範囲）と、物理的なメモリ割り当ての境界（実際に確保されたメモリ領域）の両方を兼ねていました。つまり、`stack.hi - stack.lo` がスタックの割り当てサイズと等しいと見なされていました。

7.  **GCメタデータ**: ガベージコレクションがオブジェクトやスタックをスキャンする際に必要となる補助情報です。例えば、スタック上のどの位置にポインタがあるか、どの変数がヒープオブジェクトを指しているか、といった情報が含まれます。GoのGCは正確なGC（Precise GC）であり、これらのメタデータはGCの効率と正確性を保証するために不可欠です。

8.  **`malg` 関数**: 新しいゴルーチン（`g`）を割り当て、そのスタックを初期化する関数です。

9.  **`stackalloc` / `stackfree` 関数**: スタックメモリの割り当てと解放を行う関数です。

10. **`copystack` 関数**: スタックのサイズが変更される際に、既存のスタックの内容を新しいサイズのスタックにコピーする関数です。これはスタックの成長（`newstack`）や縮小（`shrinkstack`）の際に使用されます。

## 技術的詳細

このコミットの核心は、`g` 構造体に `stackAlloc uintptr` という新しいフィールドを追加し、スタックの実際の割り当てサイズを `stack.lo` と `stack.hi` から分離することです。

### `g` 構造体への `stackAlloc` フィールドの追加

`src/runtime/runtime2.go` の `g` 構造体に以下のフィールドが追加されました。

```go
type g struct {
    // ... 既存のフィールド ...
    _panic       *_panic // innermost panic - offset known to liblink
    _defer       *_defer // innermost defer
    stackAlloc   uintptr // stack allocation is [stack.lo,stack.lo+stackAlloc)
    sched        gobuf
    // ... 既存のフィールド ...
}
```

`stackAlloc` は `uintptr` 型で、スタックが割り当てられたメモリ領域のサイズをバイト単位で保持します。これにより、スタックの実際の割り当て範囲は `[stack.lo, stack.lo + stackAlloc)` と定義されることになります。

### スタック管理関数の変更

この新しいフィールドの導入に伴い、スタックの割り当て、解放、コピー、サイズ変更に関連する複数のランタイム関数が変更されました。

1.  **`malg` (src/runtime/proc1.go)**:
    *   新しいゴルーチンが作成され、スタックが割り当てられる際に、`newg.stackAlloc = uintptr(stacksize)` が追加され、割り当てられたスタックサイズが `stackAlloc` に設定されます。

2.  **`gfput` (src/runtime/proc1.go)**:
    *   ゴルーチンが再利用のためにプールに戻される際、スタックの解放が必要な場合に、これまでは `gp.stack.hi - gp.stack.lo` でスタックサイズを計算していましたが、`gp.stackAlloc` を使用するように変更されました。
    *   `stackfree(gp.stack)` の呼び出しが `stackfree(gp.stack, gp.stackAlloc)` に変更され、解放するスタックのサイズが明示的に渡されるようになりました。
    *   固定サイズのスタックを再割り当てする際にも、`gp.stackAlloc = _FixedStack` が設定されます。
    *   `racemalloc` の呼び出しも `gp.stack.hi-gp.stack.lo` から `gp.stackAlloc` を使うように変更されました。

3.  **`stackfree` (src/runtime/stack1.go)**:
    *   この関数は、スタックを解放する際に、これまでは `stk.hi - stk.lo` でサイズを計算していましたが、引数として `n uintptr` を受け取るように変更されました。この `n` が実際の割り当てサイズとなります。
    *   新しいアサーション `if stk.lo+n < stk.hi { throw("bad stack size") }` が追加され、渡された割り当てサイズ `n` が `stack.hi` を超えていないことを確認します。これは、`stack.hi` が `stack.lo + n` の範囲内にあることを保証します。

4.  **`copystack` (src/runtime/stack1.go)**:
    *   スタックのコピー時に、`gp.stackAlloc` に新しいスタックサイズが設定されます。
    *   古いスタックを解放する際、これまでは `old.hi - old.lo` を使用していましたが、`oldsize` (古い `gp.stackAlloc` の値) を使用するように変更されました。
    *   スタックを縮小し、後で解放するためにキューに入れる場合、`stackfreequeue` にスタックを格納するだけでなく、そのスタックの割り当てサイズも `old.lo + ptrSize` の位置に格納するように変更されました。これは、`stackfreequeue` からスタックを取り出す際に、その割り当てサイズを正確に取得できるようにするためです。

5.  **`newstack` (src/runtime/stack1.go)**:
    *   スタックを拡張する際に、`oldsize` の計算が `gp.stack.hi - gp.stack.lo` から `gp.stackAlloc` を使用するように変更されました。

6.  **`shrinkstack` (src/runtime/stack1.go)**:
    *   スタックを縮小する際に、`oldsize` の計算が `gp.stack.hi - gp.stack.lo` から `gp.stackAlloc` を使用するように変更されました。
    *   スタック全体を解放する場合も、`stackfree(gp.stack, gp.stackAlloc)` を呼び出すように変更されました。

7.  **`shrinkfinish` (src/runtime/stack1.go)**:
    *   キューに入れられたスタックを解放する際に、`copystack` で格納された割り当てサイズ `n` を `*(*uintptr)(unsafe.Pointer(s.lo + ptrSize))` から読み取り、`stackfree(s, n)` を呼び出すように変更されました。

これらの変更により、Goランタイムはスタックの論理的な境界と物理的な割り当てサイズを明確に区別できるようになり、将来のGCメタデータの導入に備えることができました。

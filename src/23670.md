# [インデックス 23670] ファイルの概要

このコミットでは、Goコマンドラインツールにおけるパッケージのビルドロジック、特に`GOPATH`環境変数で指定された複数のディレクトリにまたがるパッケージの「古さ（stale）」の判定と再ビルドの挙動が変更されています。

主な変更ファイルは以下の通りです。

*   `src/cmd/go/pkg.go`: `go`コマンドがパッケージのビルドとインストールを行う際の中心的なロジックが含まれています。このファイル内の`computeStale`および`isStale`関数が修正され、パッケージの古さ判定の挙動が変わりました。
*   `src/cmd/go/test.bash`: `go`コマンドのテストスクリプトです。`GOPATH`の異なるエントリにあるパッケージが正しく再ビルドされることを確認するための新しいテストケースが追加されています。

## 元コミット内容

`cmd/go: 期限切れに見えるGOPATHコードは常に再ビルドする`

以前は、`GOPATH`のエントリ間に再ビルドの障壁を設けていました。例えば、`GOPATH=dir1:dir2`という設定で、`dir1/src/p`にパッケージ`p`があり、`dir2/src/q`にパッケージ`q`があり、`p`が`q`をインポートしている場合を考えます。このとき、`go install p`を実行すると、`dir1`で作業していると認識し、`dir2`からのものが明示的に言及されていないため、`dir2`内のすべてがビルド済みであれば最新であると仮定していました。

この挙動は混乱を招くものでした。もし`q`が一度もビルドされていない場合、`q`のソースを更新して`go install p`を実行すると、`q`が再ビルドされ、その後`p`も再ビルドされるという正しい動作をします。しかし、一度ビルドされた後で`q`のソースを更新して`go install p`を実行しても、何も起こりません。インストール済みの`q`は最新であると仮定されてしまうためです。

複数の`GOPATH`エントリを使用するコード規約（例えば、コマンドを一つの場所に、ライブラリを別の場所に置く場合や、インポートパスの書き換えを避けるためのベンダー規約など）を使用している人々は、この問題を認識せずに遭遇し、誤ったビルド結果に終わっていました。

この元の挙動の動機は、システムにインストールされた`GOROOT`が書き込み可能でない可能性があるため、標準パッケージの再ビルドを避けることでした。`GOROOT`を分離するために導入された変更は、個々の`GOPATH`エントリも分離していました。その後の変更で、リリース設定における`GOROOT`に対するより積極的なショートカットが追加されたため、このコードは現在、複数の`GOPATH`エントリにのみ適用され（そして混乱を招いていました）。これを削除します。

Issue #10509を修正します。

## 変更の背景

このコミットの背景には、Goのビルドシステム、特に`go install`コマンドが、`GOPATH`環境変数に複数のパスが設定されている場合に、依存関係の更新を正しく検出できないという問題がありました。

従来の`go install`の挙動では、`GOPATH`が`dir1:dir2`のように複数設定されている場合、`dir1`内のパッケージ`p`が`dir2`内のパッケージ`q`に依存しているとします。`go install p`を実行する際、`go`コマンドは`dir1`を主要な作業ディレクトリとみなし、`dir2`内のパッケージ`q`については、明示的に指定されていない限り「最新である」と仮定していました。

この「再ビルドの障壁（rebuilding barrier）」は、特に`q`のソースコードが更新されたにもかかわらず、`go install p`を実行しても`q`が再ビルドされないという、開発者にとって非常に混乱を招く結果をもたらしました。一度`q`がビルドされてしまうと、その後のソース変更が`p`のビルドに反映されないため、古いバージョンの`q`に依存した`p`がビルドされてしまう可能性がありました。

このような挙動は、以下のようなシナリオで問題となりました。

*   **複数の`GOPATH`エントリの利用**: 開発者がプロジェクトの構造を整理するために、コマンドとライブラリを異なる`GOPATH`エントリに配置している場合。
*   **ベンダーライブラリの管理**: `godep`のようなツールでベンダーライブラリを管理し、インポートパスの書き換えを避けるために`GOPATH`を操作している場合。

この問題の根本原因は、元々`GOROOT`内の標準パッケージが書き込み可能でない環境で不必要に再ビルドされるのを避けるために導入されたロジックが、`GOPATH`の各エントリにも誤って適用されてしまっていたことにありました。後のGoの変更で、`GOROOT`に対するより洗練された再ビルド回避策が導入されたため、この`GOPATH`間の「障壁」はもはや不要となり、むしろ混乱の元となっていたため、削除されることになりました。

この変更により、`go install`は`GOPATH`のどのエントリにあるコードであっても、ソースファイルのタイムスタンプに基づいて「古さ」を正確に判断し、必要に応じて再ビルドするようになります。これにより、開発者はより予測可能で信頼性の高いビルド結果を得られるようになります。

## 前提知識の解説

### Goのワークスペースと環境変数

*   **`GOROOT`**: GoのSDKがインストールされているディレクトリを指します。Goの標準ライブラリやツール群がここに格納されています。通常、ユーザーが直接変更することは稀で、システム全体で共有されます。
*   **`GOPATH`**: Goのワークスペースのルートディレクトリを指します。Goのソースコード、コンパイル済みパッケージ、実行可能バイナリが格納される場所です。複数のディレクトリパスをコロン（Linux/macOS）またはセミコロン（Windows）で区切って設定できます。例えば、`GOPATH=/home/user/go_projects:/home/user/go_libs`のように設定すると、`go`コマンドはこれらのディレクトリをGoパッケージの検索パスとして利用します。
    *   `src/`: ソースコードが置かれる場所。
    *   `pkg/`: コンパイル済みのパッケージアーカイブが置かれる場所。
    *   `bin/`: コンパイル済みの実行可能バイナリが置かれる場所。

### `go install`コマンド

`go install`は、指定されたパッケージとその依存関係をコンパイルし、その結果生成されたパッケージアーカイブ（`.a`ファイル）を`$GOPATH/pkg`ディレクトリに、実行可能バイナリを`$GOPATH/bin`ディレクトリにインストールするコマンドです。このコマンドは、依存関係が変更されたり、ソースファイルが更新されたりした場合に、自動的に再ビルドを行います。

### パッケージの「古さ（Staleness）」

Goのビルドシステムでは、パッケージが「古い（stale）」かどうかを判断することで、不必要な再ビルドを避けてビルド時間を短縮します。パッケージが古いと判断されるのは、主に以下の条件のいずれかを満たす場合です。

1.  **ソースファイルの更新**: パッケージのソースファイル（`.go`ファイルなど）の最終更新日時が、コンパイル済みパッケージの最終更新日時よりも新しい場合。
2.  **依存パッケージの更新**: そのパッケージが依存している他のパッケージが更新された場合。
3.  **コンパイラの変更**: Goツールチェーン（コンパイラなど）が更新された場合。
4.  **ビルドフラグの変更**: `go build -a`のような、強制的に再ビルドを促すフラグが指定された場合。

### `go build -a`フラグ

`go build -a`（または`go install -a`）は、「すべてを再ビルドする（rebuild all）」ことを意味するフラグです。このフラグが指定されると、Goツールは依存関係のタイムスタンプに関わらず、すべてのパッケージを強制的に再コンパイルしようとします。ただし、このコミットの変更前は、`GOROOT`内の標準パッケージや、`GOPATH`の異なるエントリにあるパッケージに対しては、このフラグが常に有効ではなかったという背景があります。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/go/pkg.go`ファイル内の`computeStale`および`isStale`関数の変更にあります。これらの関数は、Goのビルドシステムがどのパッケージを再ビルドする必要があるかを決定するロジックを担っています。

### 変更前のロジックの問題点

変更前の`isStale`関数は、`topRoot map[string]bool`という引数を受け取っていました。この`topRoot`マップは、`go install`コマンドラインで直接指定されたパッケージが属する`GOPATH`ルート（または`GOROOT`）を追跡していました。

問題となっていたのは、`isStale`関数内の以下の部分です（コミットメッセージのコメントから推測されるロジック）。

```go
// If a package p is not in the same tree as any
// package named on the command-line, assume it is up-to-date
// no matter what the modification times on the source files indicate.
// This avoids rebuilding $GOROOT packages when people are
// working outside the Go root, and it effectively makes each tree
// listed in $GOPATH a separate compilation world.
// See issue 3149.
if p.Root != "" && !topRoot[p.Root] {
    return false // 古いと判断しない（再ビルドしない）
}
```

このロジックは、`p`がコマンドラインで指定されたパッケージと同じ`GOPATH`エントリ（`p.Root`）に属していない場合、そのパッケージ`p`は「古い」と判断せず、再ビルドをスキップするというものでした。これは元々、`GOROOT`内の標準パッケージが書き込み可能でない場合に不必要に再ビルドされるのを避けるためのものでしたが、`GOPATH`の複数のエントリにも適用されてしまい、`GOPATH`の異なるエントリ間の依存関係の更新が無視される原因となっていました。

### 変更後のロジック

このコミットでは、上記の「再ビルドの障壁」ロジックが完全に削除されました。

1.  **`isStale`関数のシグネチャ変更**:
    `func isStale(p *Package, topRoot map[string]bool) bool`
    から
    `func isStale(p *Package) bool`
    へと変更され、`topRoot`引数が削除されました。これにより、`isStale`関数は、パッケージがコマンドラインで指定されたルートと同じかどうかを考慮しなくなりました。

2.  **`computeStale`関数の変更**:
    `computeStale`関数も`topRoot`マップを構築するロジックを削除し、`isStale`を呼び出す際に`topRoot`を渡さなくなりました。

3.  **`GOPATH`間の障壁の撤廃**:
    `isStale`関数内の、`p.Root != "" && !topRoot[p.Root]`という条件で`return false`するロジックが削除されました。これにより、`GOPATH`の異なるエントリにあるパッケージであっても、ソースファイルのタイムスタンプや依存関係の変更に基づいて、正しく「古い」と判断され、再ビルドの対象となります。

4.  **`GOROOT`と標準パッケージの扱い**:
    `GOROOT`内の標準パッケージの再ビルド回避については、`isGoRelease`フラグと`p.Standard`フラグを組み合わせた別のロジックで引き続き処理されます。これは、リリース版のGoを使用している場合に、システムにインストールされた標準パッケージが変更されないことを前提とし、書き込み不可な`GOROOT`での不必要な再ビルドを避けるためのものです。このロジックは、`GOPATH`の再ビルドロジックとは独立して機能します。

    ```go
    // If we are running a release copy of Go, do not rebuild the standard packages.
    // They may not be writable anyway, but they are certainly not changing.
    // This makes 'go build' and 'go build -a' skip the standard packages when
    // using an official release.
    if p.Standard && isGoRelease {
        return false
    }
    ```

    また、`go build -a`フラグの挙動も調整され、標準パッケージ以外は常に再ビルドされるようになりました。

    ```go
    // If the -a flag is given, rebuild everything (except standard packages; see above).
    if buildA {
        return true
    }
    ```

この変更により、`go install`は`GOPATH`の複数のエントリをまたがる依存関係においても、より堅牢で予測可能な再ビルド挙動を提供するようになりました。

## 元コミット内容

`cmd/go: 期限切れに見えるGOPATHコードは常に再ビルドする`

以前は、`GOPATH`のエントリ間に再ビルドの障壁を設けていました。例えば、`GOPATH=dir1:dir2`という設定で、`dir1/src/p`にパッケージ`p`があり、`dir2/src/q`にパッケージ`q`があり、`p`が`q`をインポートしている場合を考えます。このとき、`go install p`を実行すると、`dir1`で作業していると認識し、`dir2`からのものが明示的に言及されていないため、`dir2`内のすべてがビルド済みであれば最新であると仮定していました。

この挙動は混乱を招くものでした。もし`q`が一度もビルドされていない場合、`q`のソースを更新して`go install p`を実行すると、`q`が再ビルドされ、その後`p`も再ビルドされるという正しい動作をします。しかし、一度ビルドされた後で`q`のソースを更新して`go install p`を実行しても、何も起こりません。インストール済みの`q`は最新であると仮定されてしまうためです。

複数の`GOPATH`エントリを使用するコード規約（例えば、コマンドを一つの場所に、ライブラリを別の場所に置く場合や、インポートパスの書き換えを避けるためのベンダー規約など）を使用している人々は、この問題を認識せずに遭遇し、誤ったビルド結果に終わっていました。

この元の挙動の動機は、システムにインストールされた`GOROOT`が書き込み可能でない可能性があるため、標準パッケージの再ビルドを避けることでした。`GOROOT`を分離するために導入された変更は、個々の`GOPATH`エントリも分離していました。その後の変更で、リリース設定における`GOROOT`に対するより積極的なショートカットが追加されたため、このコードは現在、複数の`GOPATH`エントリにのみ適用され（そして混乱を招いていました）。これを削除します。

Issue #10509を修正します。

## 変更の背景

このコミットの背景には、Goのビルドシステム、特に`go install`コマンドが、`GOPATH`環境変数に複数のパスが設定されている場合に、依存関係の更新を正しく検出できないという問題がありました。

従来の`go install`の挙動では、`GOPATH`が`dir1:dir2`のように複数設定されている場合、`dir1`内のパッケージ`p`が`dir2`内のパッケージ`q`に依存しているとします。`go install p`を実行する際、`go`コマンドは`dir1`を主要な作業ディレクトリとみなし、`dir2`内のパッケージ`q`については、明示的に指定されていない限り「最新である」と仮定していました。

この「再ビルドの障壁（rebuilding barrier）」は、特に`q`のソースコードが更新されたにもかかわらず、`go install p`を実行しても`q`が再ビルドされないという、開発者にとって非常に混乱を招く結果をもたらしました。一度`q`がビルドされてしまうと、その後のソース変更が`p`のビルドに反映されないため、古いバージョンの`q`に依存した`p`がビルドされてしまう可能性がありました。

このような挙動は、以下のようなシナリオで問題となりました。

*   **複数の`GOPATH`エントリの利用**: 開発者がプロジェクトの構造を整理するために、コマンドとライブラリを異なる`GOPATH`エントリに配置している場合。
*   **ベンダーライブラリの管理**: `godep`のようなツールでベンダーライブラリを管理し、インポートパスの書き換えを避けるために`GOPATH`を操作している場合。

この問題の根本原因は、元々`GOROOT`内の標準パッケージが書き込み可能でない環境で不必要に再ビルドされるのを避けるために導入されたロジックが、`GOPATH`の各エントリにも誤って適用されてしまっていたことにありました。後のGoの変更で、`GOROOT`に対するより洗練された再ビルド回避策が導入されたため、この`GOPATH`間の「障壁」はもはや不要となり、むしろ混乱の元となっていたため、削除されることになりました。

この変更により、`go install`は`GOPATH`のどのエントリにあるコードであっても、ソースファイルのタイムスタンプに基づいて「古さ」を正確に判断し、必要に応じて再ビルドするようになります。これにより、開発者はより予測可能で信頼性の高いビルド結果を得られるようになります。

## 前提知識の解説

### Goのワークスペースと環境変数

*   **`GOROOT`**: GoのSDKがインストールされているディレクトリを指します。Goの標準ライブラリやツール群がここに格納されています。通常、ユーザーが直接変更することは稀で、システム全体で共有されます。
*   **`GOPATH`**: Goのワークスペースのルートディレクトリを指します。Goのソースコード、コンパイル済みパッケージ、実行可能バイナリが格納される場所です。複数のディレクトリパスをコロン（Linux/macOS）またはセミコロン（Windows）で区切って設定できます。例えば、`GOPATH=/home/user/go_projects:/home/user/go_libs`のように設定すると、`go`コマンドはこれらのディレクトリをGoパッケージの検索パスとして利用します。
    *   `src/`: ソースコードが置かれる場所。
    *   `pkg/`: コンパイル済みのパッケージアーカイブが置かれる場所。
    *   `bin/`: コンパイル済みの実行可能バイナリが置かれる場所。

### `go install`コマンド

`go install`は、指定されたパッケージとその依存関係をコンパイルし、その結果生成されたパッケージアーカイブ（`.a`ファイル）を`$GOPATH/pkg`ディレクトリに、実行可能バイナリを`$GOPATH/bin`ディレクトリにインストールするコマンドです。このコマンドは、依存関係が変更されたり、ソースファイルが更新されたりした場合に、自動的に再ビルドを行います。

### パッケージの「古さ（Staleness）」

Goのビルドシステムでは、パッケージが「古い（stale）」かどうかを判断することで、不必要な再ビルドを避けてビルド時間を短縮します。パッケージが古いと判断されるのは、主に以下の条件のいずれかを満たす場合です。

1.  **ソースファイルの更新**: パッケージのソースファイル（`.go`ファイルなど）の最終更新日時が、コンパイル済みパッケージの最終更新日時よりも新しい場合。
2.  **依存パッケージの更新**: そのパッケージが依存している他のパッケージが更新された場合。
3.  **コンパイラの変更**: Goツールチェーン（コンパイラなど）が更新された場合。
4.  **ビルドフラグの変更**: `go build -a`のような、強制的に再ビルドを促すフラグが指定された場合。

### `go build -a`フラグ

`go build -a`（または`go install -a`）は、「すべてを再ビルドする（rebuild all）」ことを意味するフラグです。このフラグが指定されると、Goツールは依存関係のタイムスタンプに関わらず、すべてのパッケージを強制的に再コンパイルしようとします。ただし、このコミットの変更前は、`GOROOT`内の標準パッケージや、`GOPATH`の異なるエントリにあるパッケージに対しては、このフラグが常に有効ではなかったという背景があります。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/go/pkg.go`ファイル内の`computeStale`および`isStale`関数の変更にあります。これらの関数は、Goのビルドシステムがどのパッケージを再ビルドする必要があるかを決定するロジックを担っています。

### 変更前のロジックの問題点

変更前の`isStale`関数は、`topRoot map[string]bool`という引数を受け取っていました。この`topRoot`マップは、`go install`コマンドラインで直接指定されたパッケージが属する`GOPATH`ルート（または`GOROOT`）を追跡していました。

問題となっていたのは、`isStale`関数内の以下の部分です（コミットメッセージのコメントから推測されるロジック）。

```go
// If a package p is not in the same tree as any
// package named on the command-line, assume it is up-to-date
// no matter what the modification times on the source files indicate.
// This avoids rebuilding $GOROOT packages when people are
// working outside the Go root, and it effectively makes each tree
// listed in $GOPATH a separate compilation world.
// See issue 3149.
if p.Root != "" && !topRoot[p.Root] {
    return false // 古いと判断しない（再ビルドしない）
}
```

このロジックは、`p`がコマンドラインで指定されたパッケージと同じ`GOPATH`エントリ（`p.Root`）に属していない場合、そのパッケージ`p`は「古い」と判断せず、再ビルドをスキップするというものでした。これは元々、`GOROOT`内の標準パッケージが書き込み可能でない場合に不必要に再ビルドされるのを避けるためのものでしたが、`GOPATH`の複数のエントリにも適用されてしまい、`GOPATH`の異なるエントリ間の依存関係の更新が無視される原因となっていました。

### 変更後のロジック

このコミットでは、上記の「再ビルドの障壁」ロジックが完全に削除されました。

1.  **`isStale`関数のシグネチャ変更**:
    `func isStale(p *Package, topRoot map[string]bool) bool`
    から
    `func isStale(p *Package) bool`
    へと変更され、`topRoot`引数が削除されました。これにより、`isStale`関数は、パッケージがコマンドラインで指定されたルートと同じかどうかを考慮しなくなりました。

2.  **`computeStale`関数の変更**:
    `computeStale`関数も`topRoot`マップを構築するロジックを削除し、`isStale`を呼び出す際に`topRoot`を渡さなくなりました。

3.  **`GOPATH`間の障壁の撤廃**:
    `isStale`関数内の、`p.Root != "" && !topRoot[p.Root]`という条件で`return false`するロジックが削除されました。これにより、`GOPATH`の異なるエントリにあるパッケージであっても、ソースファイルのタイムスタンプや依存関係の変更に基づいて、正しく「古い」と判断され、再ビルドの対象となります。

4.  **`GOROOT`と標準パッケージの扱い**:
    `GOROOT`内の標準パッケージの再ビルド回避については、`isGoRelease`フラグと`p.Standard`フラグを組み合わせた別のロジックで引き続き処理されます。これは、リリース版のGoを使用している場合に、システムにインストールされた標準パッケージが変更されないことを前提とし、書き込み不可な`GOROOT`での不必要な再ビルドを避けるためのものです。このロジックは、`GOPATH`の再ビルドロジックとは独立して機能します。

    ```go
    // If we are running a release copy of Go, do not rebuild the standard packages.
    // They may not be writable anyway, but they are certainly not changing.
    // This makes 'go build' and 'go build -a' skip the standard packages when
    // using an official release.
    if p.Standard && isGoRelease {
        return false
    }
    ```

    また、`go build -a`フラグの挙動も調整され、標準パッケージ以外は常に再ビルドされるようになりました。

    ```go
    // If the -a flag is given, rebuild everything (except standard packages; see above).
    if buildA {
        return true
    }
    ```

この変更により、`go install`は`GOPATH`の複数のエントリをまたがる依存関係においても、より堅牢で予測可能な再ビルド挙動を提供するようになりました。

## コアとなるコードの解説

### `src/cmd/go/pkg.go`の変更点

*   **`computeStale`関数の簡素化**:
    変更前は、`computeStale`関数内で`topRoot`というマップを構築し、コマンドラインで指定されたパッケージが属するルートディレクトリを追跡していました。このマップは`isStale`関数に渡され、`GOPATH`間の再ビルド障壁のロジックに使用されていました。変更後は、この`topRoot`マップの構築と`isStale`への引き渡しが不要になったため、関連するコードが削除され、関数が簡素化されました。

*   **`isStale`関数のシグネチャ変更とロジックの削除**:
    `isStale`関数から`topRoot`引数が削除されました。これにより、`isStale`関数は、パッケージがコマンドラインで指定されたルートと同じかどうかという情報を考慮しなくなりました。
    最も重要な変更は、`GOPATH`の異なるエントリにあるパッケージを「最新である」と仮定して再ビルドをスキップするロジック（`if p.Root != "" && !topRoot[p.Root] { return false }`に相当する部分）が完全に削除されたことです。この削除により、`go install`は、`GOPATH`のどのエントリに存在するパッケージであっても、そのソースファイルのタイムスタンプや依存関係の変更に基づいて、常に正確に古さを判断し、必要に応じて再ビルドするようになります。

*   **標準パッケージと`go build -a`のロジックの再配置**:
    標準パッケージの再ビルド回避ロジックと`go build -a`フラグの処理ロジックが、`isStale`関数内でより明確に分離され、再配置されました。
    *   リリース版のGoにおける標準パッケージの再ビルド回避は、`p.Standard && isGoRelease`という条件で引き続き行われます。これは、システムにインストールされた標準パッケージが書き込み不可である可能性や、変更されないという前提に基づいています。
    *   `go build -a`フラグが指定された場合、標準パッケージ以外は常に再ビルドされるようになりました。これにより、`go build -a`の意図がより一貫して適用されます。

これらの変更により、`go`コマンドは`GOPATH`の複数のエントリをより適切に扱い、開発者が期待するような、依存関係の変更が常にビルドに反映される堅牢な挙動を実現しました。

### `src/cmd/go/test.bash`の変更点

*   **新しいテストケースの追加**:
    `TEST 'go install rebuilds stale packages in other GOPATH'`という新しいテストケースが追加されました。このテストは、まさにこのコミットが解決しようとしているシナリオを検証します。
    1.  一時ディレクトリ内に`d1`と`d2`という2つのディレクトリを作成し、`GOPATH`を`$d/d1:$d/d2`に設定します。
    2.  `d1/src/p1`にパッケージ`p1`を、`d2/src/p2`にパッケージ`p2`を作成し、`p1`が`p2`をインポートするようにします。
    3.  `./testgo install p1`を実行し、最初のビルドが成功することを確認します。この時点では`p1`も`p2`も古くないはずです。

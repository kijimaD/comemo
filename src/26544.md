# [インデックス 26544] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）中間表現において、定数との比較を簡素化するための最適化を導入します。具体的には、`a + const1 == const2` や `a + const1 != const2` のような形式の比較式をより効率的な形に変換し、また `Eq` (等しい), `Neq` (等しくない), `Add` (加算), `Sub` (減算) といった操作の引数を正規化（定数を常に最初の引数にする）することで、定数畳み込み（constant folding）を促進し、全体的なコード生成の効率を向上させます。

## 元コミット内容

このコミットは、GoコンパイラのSSAバックエンドにおいて、定数を含む比較演算の簡素化と、特定の演算の引数正規化を行います。

主な変更点は以下の通りです。

1.  **定数との比較の簡素化**: `a + const1 == const2` または `a + const1 != const2` の形式の比較を簡素化します。これは、`a == const2 - const1` または `a != const2 - const1` のように変換することで、コンパイル時の計算量を減らし、より効率的なコードを生成することを目的としています。
2.  **演算の正規化（Canonicalization）**: `Eq`, `Neq`, `Add`, `Sub` といった演算において、定数がある場合にその定数を常に最初の引数として配置するように正規化します。例えば、`x + 5` は `5 + x` として表現されます。この正規化は、上記の比較簡素化ルールを適用しやすくするだけでなく、コンパイラが定数畳み込みなどの最適化をより効果的に行えるようにするために必要です。

これらの変更は、Goコンパイラの最適化パスの一部として、生成される機械語コードの品質向上に貢献します。

## 変更の背景

Goコンパイラは、プログラムの実行効率を最大化するために様々な最適化を行います。その中でも、SSA（Static Single Assignment）形式は、最適化の機会を増やすための強力な中間表現です。このコミットの背景には、SSA形式におけるパターンマッチングと書き換えルールを強化し、より多くの最適化を自動的に適用できるようにするという目的があります。

特に、定数を含む算術演算や比較演算は、コンパイル時に計算結果を確定できる場合が多く、実行時のオーバーヘッドを削減する大きなチャンスとなります。しかし、これらのパターンが様々な形で現れるため、コンパイラがそれらを認識し、最適化を適用するためには、柔軟なルールと引数の正規化が必要でした。

このコミットは、以下の課題に対処しています。

*   **比較演算の非効率性**: `a + const1 == const2` のような比較は、そのままでは `a + const1` を計算してから `const2` と比較するという2段階の操作が必要です。これを `a == const2 - const1` に変換できれば、加算が減算に変わり、比較対象が単一の定数になるため、より効率的なコードが生成される可能性があります。
*   **最適化ルールの適用範囲の拡大**: 演算の引数の順序が異なると、同じ論理的な操作であっても異なるSSAノードとして扱われ、最適化ルールが適用されない場合があります。定数を常に最初の引数にすることで、より一般的な最適化ルールを記述し、適用できる範囲を広げることができます。これにより、コンパイラがより多くの最適化の機会を捉えられるようになります。
*   **定数畳み込みの促進**: 引数を正規化することで、コンパイラは定数同士の演算を早期に解決し、その結果を別の定数として扱う「定数畳み込み」をより容易に行えるようになります。これは、実行時の計算を減らし、プログラムのパフォーマンスを向上させる基本的な最適化手法です。

これらの改善は、Goプログラムの実行速度向上に直接的に寄与します。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

### 1. コンパイラの最適化

コンパイラの最適化とは、ソースコードを機械語コードに変換する過程で、プログラムの実行速度を向上させたり、メモリ使用量を削減したりするために行われる様々な変換処理のことです。定数畳み込み、デッドコード削除、ループ最適化など、多岐にわたる手法があります。

### 2. SSA (Static Single Assignment) 形式

SSA (Static Single Assignment) 形式は、コンパイラの中間表現（IR: Intermediate Representation）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が容易になり、コンパイラがより高度な最適化を適用できるようになります。

*   **特徴**:
    *   すべての変数への代入は一度だけ行われる。
    *   複数の制御フローパスが合流する点では、`φ` (phi) 関数が導入され、どのパスから来た値を使用するかを決定する。
*   **利点**:
    *   データフロー解析が単純化され、最適化の機会が増える。
    *   定数伝播、共通部分式除去、デッドコード削除などの最適化が容易になる。

Goコンパイラは、フロントエンドでGoのソースコードを抽象構文木（AST）に変換し、その後、SSA形式に変換して様々な最適化を適用します。

### 3. 定数畳み込み (Constant Folding)

定数畳み込みは、コンパイル時に定数式を評価し、その結果を別の定数に置き換える最適化手法です。例えば、`x = 1 + 2` という式があれば、コンパイラはこれを `x = 3` に変換します。これにより、実行時に加算を行う必要がなくなり、プログラムの効率が向上します。

### 4. 正規化 (Canonicalization)

正規化とは、同じ意味を持つ複数の表現を、特定の標準的な形式に統一するプロセスです。コンパイラの最適化においては、異なる構文で書かれた同じ論理を持つコードを、コンパイラが認識しやすい単一の形式に変換することで、最適化ルールの適用を容易にします。

例えば、加算は交換法則が成り立つため、`a + b` と `b + a` は同じ結果になります。しかし、SSA形式のノードとしては異なるものとして扱われる可能性があります。ここで、例えば「定数がある場合は常に定数を最初の引数にする」という正規化ルールを導入すれば、`x + 5` も `5 + x` も `Add(Const(5), x)` のような単一の形式に統一され、これに対する最適化ルールを一つ書くだけで済むようになります。

### 5. SSA書き換えルール (`.rules` ファイルと `rewritegeneric.go`)

GoコンパイラのSSAバックエンドでは、`.rules` ファイルに記述されたパターンマッチングと書き換えルールに基づいて最適化が行われます。これらのルールは、SSA形式の特定のパターン（例: `(Add64 (Const64 [c]) (Const64 [d]))`）を、より最適化された形式（例: `(Const64 [c+d])`）に変換する方法を定義します。

*   `.rules` ファイル: 人間が読み書きしやすい形式で最適化ルールを記述します。
*   `rewritegeneric.go`: `.rules` ファイルから自動生成されるGoのソースコードで、実際にSSAノードを書き換えるロジックが含まれています。コンパイラは、この生成されたコードを実行してSSAグラフを変換します。

このコミットでは、`generic.rules` ファイルに新しいルールが追加され、それに対応する`rewritegeneric.go`が更新されています。

## 技術的詳細

このコミットの技術的詳細を掘り下げていきます。

### 1. 比較演算の簡素化

コミットの主要な目的の一つは、`a + const1 == const2` や `a + const1 != const2` の形式の比較を簡素化することです。

元の式: `a + const1 == const2`
これは、数学的に `a == const2 - const1` と等価です。

同様に、
元の式: `a + const1 != const2`
これは、数学的に `a != const2 - const1` と等価です。

この最適化は、SSA形式の書き換えルールとして実装されます。`src/cmd/compile/internal/ssa/gen/generic.rules` に追加されたルールを見てみましょう。

```
(Eq64 (Const64 <t> [c]) (Add64 (Const64 <t> [d]) x)) -> (Eq64 (Const64 <t> [c-d]) x)
(Neq64 (Const64 <t> [c]) (Add64 (Const64 <t> [d]) x)) -> (Neq64 (Const64 <t> [c-d]) x)
```

これらのルールは、64ビット整数 (`Eq64`, `Neq64`, `Add64`, `Const64`) の比較に対して適用されますが、同様のルールが32ビット、16ビット、8ビット整数に対しても追加されています。

*   `Eq64 (Const64 <t> [c]) (Add64 (Const64 <t> [d]) x)`: これは、`c == (d + x)` というSSAノードのパターンを表します。
    *   `Const64 <t> [c]`: 型 `t` を持つ定数 `c`。
    *   `Add64 (Const64 <t> [d]) x`: 型 `t` を持つ定数 `d` と変数 `x` の加算。
*   `-> (Eq64 (Const64 <t> [c-d]) x)`: このパターンがマッチした場合、`c == (d + x)` は `(c - d) == x` という新しいSSAノードに書き換えられます。

この書き換えにより、加算と定数との比較が、単一の定数との比較に変換され、より効率的なコード生成が可能になります。

### 2. 演算の正規化 (Canonicalization)

上記の比較簡素化ルールを効果的に適用するためには、`Add` 演算の引数が正規化されている必要があります。具体的には、定数が常に最初の引数として現れるようにします。

例えば、`x + 5` という式があった場合、SSA形式では `Add(x, Const(5))` と表現されるかもしれません。しかし、上記の簡素化ルールは `Add(Const(d), x)` の形式を期待しています。そこで、以下の正規化ルールが導入されます。

```
(Add64 x (Const64 <t> [c])) && x.Op != OpConst64 -> (Add64 (Const64 <t> [c]) x)
```

このルールは、`x + c` の形式で、`x` が定数でない場合に、`c + x` の形式に書き換えます。同様のルールが `Eq`, `Neq`, `Add` の各ビット幅（64, 32, 16, 8）に対して追加されています。

さらに、`Sub` 演算に対しても正規化が行われます。

```
(Sub64 x (Const64 <t> [c])) && x.Op != OpConst64 -> (Add64 (Const64 <t> [-c]) x)
```

これは、`x - c` という減算を `x + (-c)` という加算に変換し、定数を最初の引数に持ってくることで、`Add` 演算の正規化ルールと定数畳み込みの恩恵を受けられるようにします。これにより、減算が加算に変換され、その後の最適化パスでさらに簡素化される可能性が高まります。

### 3. `rewritegeneric.go` の自動生成コード

`src/cmd/compile/internal/ssa/rewritegeneric.go` は、`generic.rules` ファイルから自動生成されるGoのコードです。このファイルには、SSAグラフを走査し、定義されたルールにマッチするパターンを見つけて書き換えを行う関数が含まれています。

例えば、`rewriteValuegeneric_OpAdd16` 関数には、`Add16` 演算の正規化に関する新しいコードブロックが追加されています。

```go
// match: (Add16 x (Const16 <t> [c]))
// cond: x.Op != OpConst16
// result: (Add16 (Const16 <t> [c]) x)
{
	x := v.Args[0]
	if v.Args[1].Op != OpConst16 {
		goto end89b69a89778f375b0ebbc683b0c63176
	}
	t := v.Args[1].Type
	c := v.Args[1].AuxInt
	if !(x.Op != OpConst16) {
		goto end89b69a89778f375b0ebbc683b0c63176
	}
	v.Op = OpAdd16
	v.AuxInt = 0
	v.Aux = nil
	v.resetArgs()
	v0 := b.NewValue0(v.Line, OpConst16, TypeInvalid)
	v0.Type = t
	v0.AuxInt = c
	v.AddArg(v0)
	v.AddArg(x)
	return true
}
```

このコードは、SSA値 `v` が `Add16` 演算を表し、その引数が `x` と定数 `c` であり、かつ `x` が定数でない場合に、`v` を `Add16(Const16(c), x)` の形式に書き換える処理を行っています。

### 4. テストケース (`cmp_ssa.go`)

`src/cmd/compile/internal/gc/testdata/cmp_ssa.go` は、この最適化が正しく機能することを検証するための新しいテストファイルです。

```go
//go:noinline
func eq_ssa(a int64) bool {
	return 4+a == 10
}

//go:noinline
func neq_ssa(a int64) bool {
	return 10 != a+4
}
```

`eq_ssa` 関数は `4+a == 10` という形式の比較を含んでおり、これは `a == 6` に簡素化されるべきです。
`neq_ssa` 関数は `10 != a+4` という形式の比較を含んでおり、これは `6 != a` に簡素化されるべきです。

これらのテストケースは、コンパイラがこれらの式を正しく最適化し、期待される結果を生成することを確認します。`//go:noinline` ディレクティブは、これらの関数がインライン化されないようにコンパイラに指示し、SSA最適化パスが独立してテストされることを保証します。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/gen/generic.rules` の変更

追加されたルールは、SSA形式のパターンマッチング言語で記述されています。

**比較簡素化ルール:**

```
(Eq64 (Const64 <t> [c]) (Add64 (Const64 <t> [d]) x)) -> (Eq64 (Const64 <t> [c-d]) x)
(Eq32 (Const32 <t> [c]) (Add32 (Const32 <t> [d]) x)) -> (Eq32 (Const32 <t> [c-d]) x)
(Eq16 (Const16 <t> [c]) (Add16 (Const16 <t> [d]) x)) -> (Eq16 (Const16 <t> [c-d]) x)
(Eq8 (Const8 <t> [c]) (Add8 (Const8 <t> [d]) x)) -> (Eq8 (Const8 <t> [c-d]) x)

(Neq64 (Const64 <t> [c]) (Add64 (Const64 <t> [d]) x)) -> (Neq64 (Const64 <t> [c-d]) x)
(Neq32 (Const32 <t> [c]) (Add32 (Const32 <t> [d]) x)) -> (Neq32 (Const32 <t> [c-d]) x)
(Neq16 (Const16 <t> [c]) (Add16 (Const16 <t> [d]) x)) -> (Neq16 (Const16 <t> [c-d]) x)
(Neq8 (Const8 <t> [c]) (Add8 (Const8 <t> [d]) x)) -> (Neq8 (Const8 <t> [c-d]) x)
```

これらのルールは、`c == (d + x)` または `c != (d + x)` という形式の比較を、` (c - d) == x` または `(c - d) != x` に変換します。ここで `c` と `d` は定数なので、`c - d` もコンパイル時に計算可能な定数となります。これにより、比較対象が単一の定数になり、より効率的なコードが生成されます。

**正規化ルール:**

```
// canonicalize: swap arguments for commutative opertions when one argument is a constant.
(Eq64 x (Const64 <t> [c])) && x.Op != OpConst64 -> (Eq64 (Const64 <t> [c]) x)
(Eq32 x (Const32 <t> [c])) && x.Op != OpConst32 -> (Eq32 (Const32 <t> [c]) x)
(Eq16 x (Const16 <t> [c])) && x.Op != OpConst16 -> (Eq16 (Const16 <t> [c]) x)
(Eq8 x (Const8 <t> [c])) && x.Op != OpConst8 -> (Eq8 (Const8 <t> [c]) x)

(Neq64 x (Const64 <t> [c])) && x.Op != OpConst64 -> (Neq64 (Const64 <t> [c]) x)
(Neq32 x (Const32 <t> [c])) && x.Op != OpConst32 -> (Neq32 (Const32 <t> [c]) x)
(Neq16 x (Const16 <t> [c])) && x.Op != OpConst16 -> (Neq16 (Const16 <t> [c]) x)
(Neq8 x (Const8 <t> [c])) && x.Op != OpConst8 -> (Neq8 (Const8 <t> [c]) x)

(Add64 x (Const64 <t> [c])) && x.Op != OpConst64 -> (Add64 (Const64 <t> [c]) x)
(Add32 x (Const32 <t> [c])) && x.Op != OpConst32 -> (Add32 (Const32 <t> [c]) x)
(Add16 x (Const16 <t> [c])) && x.Op != OpConst16 -> (Add16 (Const16 <t> [c]) x)
(Add8 x (Const8 <t> [c])) && x.Op != OpConst8 -> (Add8 (Const8 <t> [c]) x)

(Sub64 x (Const64 <t> [c])) && x.Op != OpConst64 -> (Add64 (Const64 <t> [-c]) x)
(Sub32 x (Const32 <t> [c])) && x.Op != OpConst32 -> (Add32 (Const32 <t> [-c]) x)
(Sub16 x (Const16 <t> [c])) && x.Op != OpConst16 -> (Add16 (Const16 <t> [-c]) x)
(Sub8 x (Const8 <t> [c])) && x.Op != OpConst8 -> (Add8 (Const8 <t> [-c]) x)
```

これらのルールは、`Eq`, `Neq`, `Add` 演算において、定数と変数の順序を入れ替えて定数を最初の引数にします（`x.Op != OpConst*` は `x` が定数でないことを保証します）。これにより、上記の比較簡素化ルールがより広範なケースで適用可能になります。

`Sub` 演算については、`x - c` を `x + (-c)` と解釈し、`Add` 演算の正規化ルールに合致するように変換します。これにより、減算も定数との加算として扱われ、さらなる最適化の機会が生まれます。

### `src/cmd/compile/internal/ssa/rewritegeneric.go` の変更

このファイルは、`generic.rules` から自動生成されるため、ルールが追加されると、それに対応するGoコードが追加されます。例えば、`rewriteValuegeneric_OpEq64` 関数には、以下のようなコードブロックが追加されています。

```go
// match: (Eq64 (Const64 <t> [c]) (Add64 (Const64 <t> [d]) x))
// cond:
// result: (Eq64 (Const64 <t> [c-d]) x)
{
	// ... パターンマッチングと書き換えのロジック ...
	v.Op = OpEq64
	v.AuxInt = 0
	v.Aux = nil
	v.resetArgs()
	v0 := b.NewValue0(v.Line, OpConst64, TypeInvalid)
	v0.Type = t
	v0.AuxInt = c - d // ここで定数 c-d が計算される
	v.AddArg(v0)
	v.AddArg(x)
	return true
}
```

このコードは、SSAグラフを走査中に `Eq64` 演算ノードを見つけ、その引数が `Const64(c)` と `Add64(Const64(d), x)` のパターンにマッチした場合に、新しい `Eq64` ノードを構築します。この新しいノードでは、`c - d` がコンパイル時に計算され、新しい定数として `Eq64` の最初の引数に設定されます。これにより、実行時の計算が削減されます。

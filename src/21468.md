# [インデックス 21468] ファイルの概要

このコミットは、Go言語のARMアーキテクチャ向けコンパイラ（`cmd/9g`）において、C言語のThread Local Storage (TLS) ポインタとして使用されるレジスタR13の扱いを修正するものです。GoコードがR13を破壊しないようにすることで、C言語との相互運用時やシグナルハンドリング時に発生しうる問題を回避し、Goランタイムが現在のGoroutine (`g`) ポインタを正しく取得できるようにすることを目的としています。

## 変更の背景

Go言語は、`cgo`を通じてC言語のコードと相互運用する能力を持っています。このような相互運用が行われる際、GoランタイムはC言語のABI（Application Binary Interface）に準拠し、Cコードが期待するレジスタの状態を維持する必要があります。

ARMアーキテクチャにおいて、レジスタR13はしばしばC言語のTLS（Thread Local Storage）ポインタとして使用されます。TLSは、各スレッド（GoにおいてはGoroutineに相当）が独自のデータを保持するためのメカニズムです。GoコードがR13を自由に利用してその内容を上書きしてしまうと、以下のような問題が発生する可能性がありました。

1.  **Cコードとの境界での問題:** GoコードからCコードを呼び出す際、またはCコードからGoコードにコールバックする際に、CコードがR13に期待するTLSポインタが破壊されていると、予期せぬ動作やクラッシュにつながる可能性があります。
2.  **シグナルハンドリングの問題 (`sigtramp`):** オペレーティングシステムからプログラムにシグナル（例: セグメンテーション違反、割り込み）が送られた場合、Goランタイムはシグナルハンドラを呼び出す前に「シグナルトランポリン」（`sigtramp`）と呼ばれるコードを実行します。この`sigtramp`は、現在のGoroutine (`g`) の状態を正確に把握し、適切なコンテキストでシグナルハンドラを実行する必要があります。`g`ポインタは通常、Goランタイムによって特定のレジスタ（`REGG`）に保持されていますが、Cコードとの相互作用中にR13が破壊されると、`sigtramp`は`g`ポインタを`REGG`から取得すべきか、それともC TLSから取得すべきか判断に迷う可能性がありました。

このコミットは、Goコンパイラ（`cmd/9g`）がR13を予約済みレジスタとして扱い、GoコードがR13を破壊しないようにすることで、これらの問題を解決することを目的としています。これにより、GoとCの相互運用性が向上し、シグナルハンドリングの堅牢性が確保されます。

## 前提知識の解説

このコミットの理解には、以下の技術的な概念が不可欠です。

### ARMアーキテクチャとレジスタ

ARMは、モバイルデバイスや組み込みシステムで広く使用されているRISC（Reduced Instruction Set Computer）アーキテクチャです。ARMプロセッサには、汎用レジスタ（R0-R12）、スタックポインタ（SP、通常R13）、リンクレジスタ（LR、R14）、プログラムカウンタ（PC、R15）など、複数のレジスタが存在します。

*   **R13 (SP):** ARMの慣例では、R13はスタックポインタ（SP）として使用されます。しかし、特定のABIやコンテキストでは、TLS（Thread Local Storage）ポインタとしても利用されることがあります。

### C ABI (Application Binary Interface)

ABIは、異なるコンパイルされたモジュール（例: C言語で書かれたライブラリとGo言語で書かれたアプリケーション）が互いに連携するために従うべき低レベルの規約のセットです。これには、関数呼び出し規約（引数の渡し方、戻り値の受け取り方）、レジスタの使用方法、スタックフレームのレイアウトなどが含まれます。C ABIは、C言語で書かれたコードがどのようにメモリやレジスタを使用するかを定義しており、GoがCコードと相互運用する際には、このABIに準拠する必要があります。

### TLS (Thread Local Storage)

TLSは、プログラム内の各スレッド（またはGoのGoroutineのような実行コンテキスト）が、他のスレッドから独立した独自のデータを保持するためのメカニズムです。これにより、グローバル変数や静的変数をスレッドセーフに扱うことができます。C言語では、`__thread`キーワードなどを用いてTLS変数を宣言できます。ARMアーキテクチャでは、TLSデータのベースアドレスを指すポインタが特定のレジスタ（この場合はR13）に格納されることがあります。

### GoランタイムとGoroutine (`g`)

Go言語は、OSのスレッドとは異なる軽量な実行単位である「Goroutine」を使用します。Goランタイムは、これらのGoroutineのスケジューリング、メモリ管理（ガベージコレクション）、チャネル通信などを担当します。各Goroutineは、`g`と呼ばれる内部データ構造によって表現され、この`g`ポインタは現在のGoroutineの状態やスタック情報にアクセスするために非常に重要です。Goランタイムは、パフォーマンスのためにこの`g`ポインタを特定のレジスタ（ARMでは`REGG`として抽象化される）に保持する慣例があります。

### `cgo`

`cgo`は、GoプログラムからC言語の関数を呼び出したり、C言語の関数からGoの関数を呼び出したりするためのGoのツールです。`cgo`を使用すると、GoとCのコードベースを混在させることができ、既存のCライブラリをGoから利用したり、Goの並行処理機能をCプログラムに組み込んだりすることが可能になります。`cgo`は、GoとCの間のABIの差異を吸収する役割も担っています。

### シグナルと`sigtramp`

シグナルは、オペレーティングシステムがプログラムに非同期イベント（例: ユーザーからの割り込み、不正なメモリアクセス、タイマー満了）を通知するメカニズムです。プログラムはシグナルを受信すると、対応するシグナルハンドラを実行します。

`sigtramp`（シグナルトランポリン）は、OSがシグナルをプログラムに配信する際に、実際のシグナルハンドラが呼び出される前に実行される小さなコードの断片です。`sigtramp`の主な役割は、シグナル発生時のCPUの状態（レジスタの値など）を保存し、シグナルハンドラが安全に実行できる環境を整え、シグナルハンドラから戻った後に元の実行状態を復元することです。Goランタイムの`sigtramp`は、シグナル発生時にどのGoroutineが実行されていたかを特定し、そのGoroutineのコンテキストでシグナルハンドラを処理するために、`g`ポインタを正しく取得する必要があります。

## 技術的詳細

このコミットの核心は、GoコンパイラがARMアーキテクチャのレジスタR13を、C言語のTLSポインタとして予約済みレジスタのリストに追加することです。

**問題点:**
GoコードがCコードと相互作用する際、GoコンパイラがR13を汎用レジスタとして自由に利用し、その内容を上書きしてしまう可能性がありました。R13がC TLSポインタとして使用されている場合、この上書きはCコードの動作に影響を与えます。特に、シグナルが発生し`sigtramp`が実行される際、`sigtramp`は現在のGoroutine (`g`) ポインタを特定する必要があります。Goランタイムは通常、`g`ポインタを`REGG`と呼ばれる専用レジスタに保持していますが、Cコードが`REGG`を破壊する可能性があるため、`sigtramp`は`g`ポインタを`REGG`から取得すべきか、それともC TLSポインタ（R13）が指す場所から取得すべきか、判断に迷う状況が生じました。この曖昧さが、シグナルハンドリングの不安定性につながる可能性がありました。

**解決策:**
最も単純で堅牢な解決策は、GoコードがC TLSポインタ（R13）を常に保持することです。これは、GoコンパイラがR13を予約済みレジスタとして扱い、GoコードがR13を汎用レジスタとして使用しないようにすることで実現されます。これにより、R13は常にC TLSポインタの値を保持し続けることが保証されます。

**他のプラットフォームとの比較:**
このアプローチは、他のプラットフォーム（例: x86-64のFS/GSレジスタ）でTLSポインタが特別なレジスタに保持されるのと同様の考え方に基づいています。ARMではR13がその役割を担うことになります。

**`REGG`と`REGTLS`の役割:**
*   `REGG`: Goランタイムが現在のGoroutine (`g`) ポインタを保持するために使用する抽象的なレジスタ名です。
*   `REGTLS`: GoランタイムがC TLSポインタを保持するために使用する抽象的なレジスタ名です。このコミットにより、`REGTLS`がR13にマッピングされ、Goコンパイラによって保護されるようになりました。

この変更により、`sigtramp`は、Cコードとの相互作用中に`REGG`が破壊された場合でも、`REGTLS`（R13）が指すC TLS領域から`g`ポインタを安全に取得できるようになり、シグナルハンドリングの堅牢性が向上します。

## コアとなるコードの解説

### `src/cmd/9g/gsubr.c` の変更

`gsubr.c`内の`resvd`配列は、Goコンパイラがレジスタ割り当てを行う際に、特定のレジスタを「予約済み」として扱い、通常の変数に割り当てないようにするためのものです。このコミットでは、`REGTLS`（R13）がこの配列に追加されました。

*   **`REGTLS,` の追加:** これにより、GoコンパイラはR13を汎用レジスタとして使用することを避け、その内容を保護します。
*   **詳細なコメントの追加:** 追加されたコメントは、この変更の背後にある重要な理由を説明しています。
    *   「`sigtramp`がCコード中に発生し、`g`にアクセスする必要があるため、C ABI TLSポインタを保持する必要がある。」
    *   「Cコードは`REGG`を破壊する可能性があるため、Goが`REGTLS`を破壊すると、`sigtramp`はどちらの規約を使用すべきか分からなくなる。」
    *   「`REGTLS`を保持することで、確信が持てない場合にTLSから`g`を取得できる。」
    このコメントは、GoとCの相互運用におけるレジスタの衝突と、シグナルハンドリングの堅牢性確保という、このコミットの主要な目的を明確に示しています。

### `src/cmd/9g/reg.c` の変更

`reg.c`の`regopt`関数は、Goコンパイラのレジスタ最適化パスの一部です。この関数内で、`regbits`というビットマスクが使用されており、これはレジスタアロケータが変数に割り当ててはならないレジスタを示します。

*   **`|RtoB(REGTLS)` の追加:** `regbits`に`REGTLS`に対応するビットを追加することで、レジスタアロケータはR13を「固定機能を持つレジスタ」として認識し、Goコードの通常の変数に割り当てないようにします。これにより、R13は常にC TLSポインタの値を保持し続けることが保証されます。

### `src/cmd/9l/9.out.h` の変更

`9.out.h`は、Goのコンパイラとリンカが共有する定数や定義を含むヘッダファイルです。

*   **`REGTLS = 13, /* C ABI TLS base pointer */` の追加:**
    *   `REGTLS`という新しい列挙型メンバーが追加され、その値が`13`に設定されています。これは、ARMアーキテクチャにおけるR13レジスタに対応します。
    *   コメント「`C ABI TLS base pointer`」は、このレジスタがC言語のABIにおいてTLSベースポインタとして機能することを明確に示しています。
この定義により、Goのコンパイラとリンカは、R13をC TLSポインタとして一貫して認識し、適切に扱うことができるようになります。

これらの変更が連携することで、GoコンパイラはR13をC TLSポインタとして保護し、GoとCの相互運用性およびシグナルハンドリングの安定性を向上させています。

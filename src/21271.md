# [インデックス 21271] ファイルの概要

このコミットは、Go言語の標準ライブラリである `net/http/httputil` パッケージ内の `dump.go` ファイルに対する変更です。具体的には、HTTPリクエストのダンプ機能を提供する `DumpRequestOut` 関数における `http.Transport` の使用方法が修正されています。

## コミット

Date:   Tue Dec 16 17:47:55 2014 +1100

    net/http/httputil: don't use DisableKeepAlives in DumpRequestOut, fix build

    http.Transport send "Connection: close" request headers when
    DisableKeepAlives was set true because I didn't run all the tests

    depend on the exact bytes from these in their tests), switch to not

## 元コミット内容

このコミットは、以前のコミット `https://golang.org/change/207950a` によって引き起こされたビルドエラーと、`httputil.DumpRequestOut` の出力変更を修正するものです。元のコミットでは、`http.Transport` の `DisableKeepAlives` が `true` に設定されている場合に、`Connection: close` リクエストヘッダーを送信するように変更されました。

## 変更の背景

`httputil.DumpRequestOut` 関数は、HTTPリクエストをワイヤー形式（ネットワーク上で実際に送信される形式）でダンプするために使用されます。この関数は内部的に `http.Transport` を利用してリクエストの処理をシミュレートし、その結果をダンプします。

以前のコミットで `http.Transport` が `DisableKeepAlives: true` の場合に `Connection: close` ヘッダーを自動的に追加するようになったため、`httputil.DumpRequestOut` の出力もこのヘッダーを含むように変わってしまいました。

しかし、`httputil.DumpRequestOut` の出力は、テストにおける「ゴールデンデータ」（期待される出力の基準となるデータ）として利用されることが多く、その出力形式が変更されると、多くの既存テストが失敗する可能性がありました。開発者は、テストのゴールデンデータを更新するよりも、`DumpRequestOut` の出力を以前と同じ状態に戻すことを選択しました。

このコミットの目的は、`DumpRequestOut` の出力が `Connection: close` ヘッダーによって変更されないようにすること、そしてそれによって発生したビルドエラーを修正することです。

## 前提知識の解説

*   **`net/http` パッケージ**: Go言語の標準ライブラリで、HTTPクライアントとサーバーの実装を提供します。
*   **`http.Transport`**: `net/http` パッケージの一部で、HTTPリクエストの送信、レスポンスの受信、接続の管理（キープアライブなど）を担当する構造体です。
*   **`DisableKeepAlives`**: `http.Transport` のフィールドの一つで、`true` に設定すると、HTTPキープアライブ（TCP接続の再利用）を無効にします。これにより、各HTTPリクエスト後に接続が閉じられるようになります。この設定が `true` の場合、`http.Transport` は自動的に `Connection: close` ヘッダーをリクエストに追加します。
*   **`net/http/httputil` パッケージ**: `net/http` パッケージのユーティリティ機能を提供するパッケージです。
*   **`httputil.DumpRequestOut`**: この関数は、`*http.Request` オブジェクトを受け取り、そのリクエストがネットワーク上でどのように見えるか（HTTP/1.x ワイヤー形式）をバイトスライスとして返します。デバッグやテストでHTTPリクエストの正確な形式を確認するのに非常に役立ちます。
*   **HTTP キープアライブ (Keep-Alive)**: HTTP/1.1 の機能で、単一のTCP接続上で複数のHTTPリクエスト/レスポンスをやり取りできるようにします。これにより、接続の確立と切断のオーバーヘッドが削減され、パフォーマンスが向上します。
*   **`Connection: close` ヘッダー**: HTTPヘッダーの一つで、送信側が現在の接続をトランザクションの完了後に閉じることを意図していることを示します。

## 技術的詳細

このコミットの核心は、`httputil.DumpRequestOut` が内部で `http.Transport` を使用する際の `DisableKeepAlives` の扱いを変更することにあります。

元のコードでは、`DumpRequestOut` 内で `http.Transport` を初期化する際に `DisableKeepAlives: true` を設定していました。

```go
// 変更前のコードの一部
t := &http.Transport{
    DisableKeepAlives: true, // ここでDisableKeepAlivesがtrueに設定されていた
    Dial: func(net, addr string) (net.Conn, error) {
        return &dumpConn{io.MultiWriter(&buf, pw), dr}, nil
    },
}
```

しかし、以前のコミットで `http.Transport` の動作が変更され、`DisableKeepAlives: true` が設定されている場合に `Connection: close` ヘッダーが自動的にリクエストに追加されるようになりました。これにより、`DumpRequestOut` の出力にこのヘッダーが含まれるようになり、既存のテストのゴールデンデータと一致しなくなりました。

このコミットでは、`DumpRequestOut` 内の `http.Transport` から `DisableKeepAlives: true` の設定を削除します。これにより、`http.Transport` が自動的に `Connection: close` ヘッダーを追加するのを防ぎます。

その代わりに、`DumpRequestOut` が内部で生成するダミーのHTTPレスポンスに、明示的に `Connection: close` ヘッダーを追加します。これは、`DumpRequestOut` がリクエストをダンプする際に、内部的にダミーのHTTPサーバーとして振る舞い、クライアント（この場合は `http.Transport`）からのリクエストを受け取った後にダミーのレスポンスを返すためです。このダミーレスポンスに `Connection: close` を含めることで、接続が適切に閉じられることを保証しつつ、`DumpRequestOut` の出力形式を以前の状態に保ちます。

```go
// 変更後のコードの一部
// DisableKeepAlivesの設定が削除された新しいhttp.Transportの初期化
t := &http.Transport{
    Dial: func(net, addr string) (net.Conn, error) {
        return &dumpConn{io.MultiWriter(&buf, pw), dr}, nil
    },
}
defer t.CloseIdleConnections() // 新たに追加された

// ダミーレスポンスにConnection: closeヘッダーを明示的に追加
dr.c <- strings.NewReader("HTTP/1.1 204 No Content\r\nConnection: close\r\n\r\n")
```

この変更により、`DumpRequestOut` の出力は以前と同じになり、既存のテストが壊れるのを防ぎます。同時に、内部的な接続の振る舞いも意図通りに保たれます。

## コアとなるコードの変更箇所

2.  `http.Transport` の初期化ブロックが、`go func() { ... }` のゴルーチンブロックの前に移動されました。

## コアとなるコードの解説

このコミットの主要な変更点は、`httputil.DumpRequestOut` 関数が `http.Transport` をどのように利用するかという点にあります。

1.  **`http.Transport` の `DisableKeepAlives` 設定の削除**:
    以前のコードでは、`DumpRequestOut` 内で `http.Transport` を作成する際に `DisableKeepAlives: true` を明示的に設定していました。これは、`DumpRequestOut` がリクエストをダンプする際に、実際のネットワーク接続を確立せず、内部的なモック接続を使用するため、キープアライブを無効にすることが適切だと考えられていたためです。
    しかし、`http.Transport` の内部実装が変更され、`DisableKeepAlives: true` が設定されている場合に、自動的に `Connection: close` ヘッダーを送信するようになりました。この自動的なヘッダー追加が、`DumpRequestOut` の出力形式を変更し、既存のテストを壊す原因となりました。
    このコミットでは、`DisableKeepAlives: true` の設定を削除することで、`http.Transport` が自動的に `Connection: close` ヘッダーを追加するのを防ぎます。

2.  **ダミーレスポンスへの `Connection: close` ヘッダーの明示的な追加**:
    `DumpRequestOut` は、リクエストをダンプするために、内部的にダミーのHTTPサーバーとして振る舞います。このダミーサーバーは、`http.Transport` からのリクエストを受け取った後、ダミーのHTTPレスポンスを返します。
    `DisableKeepAlives` の設定を削除したことで、`http.Transport` は自動的に `Connection: close` ヘッダーを追加しなくなります。しかし、`DumpRequestOut` の目的は、リクエストのワイヤー形式を正確に表現することであり、そのシミュレーション環境では接続が閉じられるべきです。
    そのため、このコミットでは、ダミーのHTTPレスポンス (`HTTP/1.1 204 No Content`) に `Connection: close` ヘッダーを明示的に追加することで、この内部的な接続が適切に閉じられることを保証します。これにより、`DumpRequestOut` の出力形式は以前と同じに保たれ、テストの互換性が維持されます。

3.  **`defer t.CloseIdleConnections()` の追加**:
    これは、`http.Transport` が保持するアイドル状態の接続を、関数が終了する際に確実に閉じるためのベストプラクティスです。`DumpRequestOut` のようなユーティリティ関数では、リソースリークを防ぐために重要です。

これらの変更により、`httputil.DumpRequestOut` は、`http.Transport` の内部的な変更に影響されることなく、一貫したダンプ出力を提供できるようになりました。これは、Goの標準ライブラリにおける後方互換性とテストの安定性を維持するための重要な修正です。

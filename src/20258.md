# [インデックス 20258] ファイルの概要

このコミットは、Goランタイムの`src/pkg/runtime/sys_nacl_386.s`ファイルに対する変更です。このファイルは、Google Native Client (NaCl) 環境における386アーキテクチャ（32ビットx86）向けのシステムコールラッパーを定義するアセンブリ言語のソースコードです。GoプログラムがNaCl環境で動作する際に、ファイル操作、スレッド管理、同期プリミティブなどの低レベルなシステム機能にアクセスするためのインターフェースを提供します。

## 変更の背景

このコミットの背景には、GoランタイムがGoogle Native Client (NaCl) 環境で動作する際のシステムコール呼び出しメカニズムの変更があります。以前の変更（このコミットで言及されている"earlier CL"）で、システムコールを呼び出すためのアセンブリマクロが`NACL_SYSJMP`から`NACL_SYSCALL`に統一されました。

`NACL_SYSJMP`は、アセンブリの`JMP`命令を使用しており、これは単に指定されたアドレスにジャンプするだけで、呼び出し元のリターンアドレスをスタックにプッシュしません。一方、`NACL_SYSCALL`は、アセンブリの`CALL`命令を使用します。`CALL`命令は、関数呼び出しの標準的な動作として、呼び出し元の次の命令のアドレス（リターンPC: Program Counter）をスタックにプッシュしてから、指定されたアドレスにジャンプします。

この違いが問題を引き起こしました。Goの関数呼び出し規約では、引数はスタックに積まれます。`NACL_SYSJMP`を使用していた時は、システムコールへの引数はスタック上の正しい位置に配置されていました。しかし、`NACL_SYSCALL`に変更されたことで、`CALL`命令が余分なリターンPCをスタックにプッシュしてしまい、その結果、システムコールが期待する引数の位置がずれてしまいました。これにより、NaCl/386ビルドが正しく機能しなくなりました。

このコミットは、このスタックのずれを修正し、システムコールへの引数が正しく渡されるようにするためのものです。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

1.  **Goランタイム**: Goプログラムは、ガベージコレクション、ゴルーチン管理、スケジューリングなど、多くの低レベルな機能を提供するランタイムシステムに依存しています。このランタイムの一部は、特定のアーキテクチャやOSに依存するアセンブリ言語で記述されています。
2.  **Google Native Client (NaCl)**: NaClは、ウェブブラウザ内でネイティブコード（C/C++など）を安全に実行するためのサンドボックス技術です。GoはかつてNaClをターゲットとしてサポートしており、GoプログラムをNaCl環境でコンパイルして実行することができました。NaClは、独自のシステムコールインターフェースを提供します。
3.  **x86 (386) アセンブリ言語**: 386は、Intel 80386プロセッサに代表される32ビットx86アーキテクチャを指します。アセンブリ言語は、CPUが直接実行できる機械語に非常に近い低レベルなプログラミング言語です。
    *   **レジスタ**: CPU内部の高速な記憶領域。`AX` (Accumulator Register) は汎用レジスタの一つで、演算結果の格納やデータ転送によく使われます。
    *   **スタック**: プログラム実行中に一時的なデータを格納するためのメモリ領域。関数呼び出しの引数、ローカル変数、リターンアドレスなどがスタックに積まれます。x86アーキテクチャでは、スタックは通常、高アドレスから低アドレスに向かって成長します。
    *   **スタックポインタ (SP)**: スタックの現在のトップ（最も最近プッシュされたデータのアドレス）を指すレジスタ。Goアセンブリでは`SP`は擬似レジスタとして扱われ、ローカル変数やこれから呼び出す関数の引数を参照するために使われます。
    *   **フレームポインタ (FP)**: Goアセンブリでは`FP`も擬似レジスタで、関数に渡された引数を参照するために使われます。`0(FP)`は最初の引数を指します。
    *   **`MOVL`命令**: `MOV`命令の一種で、`L`は"Long"（4バイト、32ビット）を意味します。32ビットのデータをソースからデスティネーションに移動します。Goアセンブリでは、通常、`MOVL source, destination`の形式で、左から右へデータが流れます。
    *   **`TEXT`ディレクティブ**: Goアセンブリで関数を定義するために使用されます。`TEXT func_name(SB),NOSPLIT,$frame_size-arg_size`のような形式で、関数のスタックフレームサイズと引数のサイズを指定します。
    *   **`NOSPLIT`ディレクティブ**: このディレクティブが付与された関数は、スタックオーバーフローチェックを行いません。低レベルのランタイムコードで、スタックの成長が不要または安全でない場合に使用されます。
4.  **システムコール**: オペレーティングシステムが提供する低レベルなサービス（ファイルI/O、メモリ管理、プロセス制御など）をプログラムが利用するためのインターフェースです。NaCl環境では、独自のシステムコールが定義されています。
5.  **呼び出し規約 (Calling Convention)**: 関数が呼び出される際に、引数をどのように渡し、戻り値をどのように返し、スタックをどのように管理するかを定めたルールです。これには、引数の順序、レジスタの使用、スタックのクリーンアップ責任などが含まれます。

## 技術的詳細

このコミットの核心的な問題は、`NACL_SYSCALL`マクロが内部で`CALL`命令を使用することによって、予期せぬスタックの変更が発生したことです。

従来の`NACL_SYSJMP`は、システムコールへの制御を`JMP`命令で移譲していました。`JMP`命令は、単に実行フローを別の場所に移すだけで、スタックには何もプッシュしません。したがって、Goの関数がシステムコールを呼び出す際に、引数はスタック上の期待されるオフセットにそのまま存在していました。

しかし、`NACL_SYSCALL`が導入され、これが`CALL`命令を使用するようになると、話が変わります。`CALL`命令は、呼び出し先のコードが終了した後に戻るべきアドレス（リターンPC）を自動的にスタックにプッシュします。32ビットシステムでは、このリターンPCは4バイトのサイズを持ちます。

これにより、システムコールが引数を読み取ろうとすると、スタックのトップにリターンPCが余分に存在するため、引数の位置が4バイトずれてしまいます。例えば、本来`0(SP)`にあるべき引数が`4(SP)`に、`4(SP)`にあるべき引数が`8(SP)`に、といった具合にずれてしまうのです。

この問題を解決するため、このコミットでは、各システムコールラッパーのアセンブリコードにおいて、システムコールを呼び出す前に、関数に渡された引数を明示的にスタックの正しい位置にコピーする処理を追加しています。具体的には、`MOVL`命令を使って、`FP`（フレームポインタ）からのオフセットで参照される引数を、`SP`（スタックポインタ）からのオフセットで参照されるシステムコールへの引数領域に移動させています。

また、各関数の`TEXT`ディレクティブで指定されるスタックフレームサイズも、引数をコピーするために必要なスタック領域を確保するように調整されています。例えば、引数がない関数では`$0`だったスタックフレームサイズが、引数をコピーするために`$4`や`$8`などに変更されています。

この修正により、`NACL_SYSCALL`がリターンPCをプッシュしても、システムコールが期待する引数の位置にデータが正しく配置されるようになり、NaCl/386ビルドの問題が解決されました。

## コアとなるコードの変更箇所

変更は`src/pkg/runtime/sys_nacl_386.s`ファイルに集中しています。
主要な変更パターンは以下の通りです。

1.  **`TEXT`ディレクティブのスタックフレームサイズ変更**:
    *   多くの`TEXT`ディレクティブで、スタックフレームサイズを示す最後の数値（例: `$0`）が、引数をコピーするために必要なバイト数（例: `$4`, `$8`, `$12`, `$16`）に変更されています。これは、システムコールに渡す引数を一時的にスタックに格納するための領域を確保するためです。

    例:
    ```diff
    -TEXT runtime·exit(SB),NOSPLIT,$0
    +TEXT runtime·exit(SB),NOSPLIT,$4
    ```

2.  **引数のスタックへのコピー**:
    *   各システムコールラッパーの関数内で、Goの関数に渡された引数（`FP`からのオフセットで参照）を、システムコールが期待するスタック上の位置（`SP`からのオフセットで参照）にコピーする`MOVL`命令が追加されています。

    例: `runtime·exit`関数の変更
    ```diff
     TEXT runtime·exit(SB),NOSPLIT,$4
    +	MOVL code+0(FP), AX  // code引数をAXレジスタにロード
    +	MOVL AX, 0(SP)       // AXレジスタの内容をスタックの0(SP)にプッシュ（システムコールへの引数）
     	NACL_SYSCALL(SYS_exit)
     	JMP 0(PC)
    ```

    例: `runtime·open`関数の変更 (複数の引数)
    ```diff
     TEXT runtime·open(SB),NOSPLIT,$12
    +	MOVL name+0(FP), AX  // name引数をAXにロード
    +	MOVL AX, 0(SP)       // AXをスタックの0(SP)にプッシュ
    +	MOVL mode+4(FP), AX  // mode引数をAXにロード
    +	MOVL AX, 4(SP)       // AXをスタックの4(SP)にプッシュ
    +	MOVL perm+8(FP), AX  // perm引数をAXにロード
    +	MOVL AX, 8(SP)       // AXをスタックの8(SP)にプッシュ
     	NACL_SYSCALL(SYS_open)
     	MOVL AX, ret+12(FP)
     	RET
    ```

## コアとなるコードの解説

変更されたアセンブリコードの主要なパターンは、Goの関数呼び出し規約とNaClシステムコールの呼び出し規約の間のギャップを埋めるものです。

Goの関数では、引数は呼び出し元のスタックフレームに配置され、呼び出された関数は`FP`（フレームポインタ）からのオフセットを使ってこれらの引数にアクセスします。例えば、`code+0(FP)`は、`code`という名前の引数が`FP`から0バイトのオフセットにあることを示します。

一方、`NACL_SYSCALL`マクロが内部で`CALL`命令を使用すると、`CALL`命令自体がリターンアドレス（4バイト）をスタックにプッシュします。これにより、システムコールが期待する引数の位置がずれてしまいます。

このコミットで追加された`MOVL`命令のペアは、このずれを修正します。

```assembly
MOVL arg_name+offset_from_FP(FP), AX  // Goの関数引数をAXレジスタにロード
MOVL AX, offset_from_SP(SP)           // AXレジスタの内容をシステムコールが期待するスタック位置にプッシュ
```

*   `MOVL arg_name+offset_from_FP(FP), AX`: これは、Goの関数に渡された特定の引数（`arg_name`）を、`FP`からの指定されたオフセット（`offset_from_FP`）で読み取り、それを`AX`レジスタに格納します。
*   `MOVL AX, offset_from_SP(SP)`: これは、`AX`レジスタに格納された値を、`SP`からの指定されたオフセット（`offset_from_SP`）にあるスタック上の位置に書き込みます。この`offset_from_SP`は、`NACL_SYSCALL`がリターンPCをプッシュした後の、システムコールが期待する引数の正しい位置に対応します。

例えば、`runtime·exit`関数の場合、`code+0(FP)`で参照される引数`code`を`AX`にロードし、それを`0(SP)`に書き込んでいます。これは、`NACL_SYSCALL`が`CALL`命令でリターンPCをプッシュした後、システムコールが最初の引数を`0(SP)`で期待するためです。

このように、各システムコールラッパー関数で、必要な引数の数だけ`MOVL`命令のペアを追加し、引数を`FP`から`AX`経由で`SP`にコピーすることで、スタック上の引数の位置のずれを解消し、システムコールが正しく引数を読み取れるようにしています。

## 変更の背景

このコミットは、Goコンパイラの開発ブランチである `dev.ssa` において発生したビルドエラーを修正するために導入されました。コミットメッセージによると、このビルドエラーは `CL 13472` という以前の変更によって引き起こされたものです。`CL 13472` の具体的な内容はウェブ検索では特定できませんでしたが、このコミットの変更内容から推測すると、`CL 13472` はコンパイラの内部的なファイルパスや行番号の処理方法に影響を与え、特に `LineHist` 構造体による行情報生成ロジックに不整合をもたらしたと考えられます。

`dev.ssa` は、Goコンパイラが従来のAST (Abstract Syntax Tree) ベースの最適化から、より高度なSSA (Static Single Assignment) 形式に基づく最適化へと移行する過程で開発されていた実験的なバックエンドでした。このような大規模なコンパイラ内部の変更は、既存のユーティリティコード（例えば、デバッグ情報やエラーメッセージのための行情報生成）との間に予期せぬ相互作用を引き起こすことがよくあります。このコミットは、そのような相互作用によって生じたビルドの不具合を解消し、`dev.ssa` ブランチの安定性を保つことを目的としています。

## 前提知識の解説

### Goコンパイラの構造とSSA (Static Single Assignment)

Goコンパイラは、ソースコードを機械語に変換する多段階のプロセスを経ます。主要な段階は以下の通りです。

1.  **字句解析 (Lexing) と構文解析 (Parsing):** ソースコードをトークンに分解し、抽象構文木 (AST) を構築します。
2.  **型チェック (Type Checking):** ASTに対して型の一貫性を検証します。
3.  **中間表現 (IR) への変換:** ASTをより低レベルの中間表現に変換します。Goコンパイラでは、この段階でSSA形式が重要な役割を果たします。
4.  **最適化 (Optimization):** 中間表現に対して様々な最適化を適用し、生成される機械語の効率を向上させます。
5.  **コード生成 (Code Generation):** 最適化された中間表現をターゲットアーキテクチャの機械語に変換します。

**SSA (Static Single Assignment) 形式**は、コンパイラ最適化において非常に強力な中間表現です。SSAの主要な特性は以下の通りです。

*   **単一代入:** 各変数が一度だけ代入されるようにプログラムが変換されます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が大幅に簡素化されます。
*   **Phi関数 (Φ関数):** 制御フローが合流する点（例: `if-else`文の終わりやループの合流点）で、異なるパスから来る同じ論理的な変数に対して、どの値を使用すべきかを決定するために導入される特殊な関数です。

GoコンパイラがSSA形式を採用することで、以下のような高度な最適化が可能になります。

*   **デッドコード削除 (Dead Code Elimination):** 使用されないコードを特定し削除します。
*   **定数伝播 (Constant Propagation):** 定数値をプログラム全体に伝播させ、計算をコンパイル時に行います。
*   **エスケープ解析 (Escape Analysis):** 変数がヒープに割り当てられるべきか、スタックに割り当てられるべきかを決定します。
*   **レジスタ割り当て (Register Allocation):** 変数を効率的にCPUレジスタに割り当てます。

`dev.ssa` は、GoコンパイラがこのSSAバックエンドを本格的に導入する前の開発段階を指します。この期間中、コンパイラの内部構造は大きく変化し、既存のコンポーネントとの整合性を保つための修正が頻繁に行われていました。

### `src/cmd/internal/obj/obj.go` の役割

`src/cmd/internal/obj` パッケージは、Goコンパイラのバックエンドの一部であり、主にアセンブラコードの生成やオブジェクトファイルに関連する低レベルの処理を担当します。`obj.go` ファイルは、このパッケージ内で、特にソースコードの行番号やファイル名といったデバッグ情報の管理とフォーマットに関わるユーティリティ機能を提供していると考えられます。

コミットの変更箇所から、`LineHist` 構造体と `LineString` メソッドが、コンパイル中のコードの特定の行が元のソースファイルのどの行に対応するかを追跡し、それを文字列として表現する役割を担っていることがわかります。これは、エラーメッセージやスタックトレース、デバッガの表示などで正確なソースコードの位置を示すために不可欠な機能です。

## 技術的詳細

このコミットの技術的な詳細は、`src/cmd/internal/obj/obj.go` ファイル内の `(*LineHist) LineString` メソッドの修正に集約されます。

`LineString` メソッドは、与えられた行番号に基づいて、対応するソースコードのファイル名と行番号を含む文字列を生成します。このメソッドは、コンパイラが内部的に管理する行履歴 (`LineHist`) とスタック情報 (`stk`) を利用して、元のソースコードの位置を特定します。

修正前のコードでは、`stk.Directive` が `true` で `stk.Parent` が `nil` でない場合に、`stk` を `stk.Parent` に更新して親のスタックフレームの情報を参照していました。しかし、この更新後に `filename` 変数が適切に再設定されていなかったため、`text` に追加される情報が古い `filename` を参照してしまう可能性がありました。

このコミットでは、`stk = stk.Parent` の後に以下の2行が追加されました。

```go
			filename = stk.File
			if h.PrintFilenameOnly {
				filename = filepath.Base(filename)
			}
```

これにより、`stk.Parent` に切り替わった後、`filename` 変数が現在の `stk.File` の値で正しく更新されます。さらに、`h.PrintFilenameOnly` フラグが `true` の場合は、`filepath.Base(filename)` を使用してファイル名からディレクトリパスを除去し、ファイル名のみを表示するように調整されます。これは、デバッグ出力の簡潔さを保つため、または特定のコンテキストで完全なパスが不要な場合に有用です。

この修正により、`dev.ssa` ビルドにおいて、特にディレクティブやインクルードファイルなどによって行情報が複雑になるケースで、正しいファイル名と行番号が報告されるようになり、ビルドエラーが解消されました。

## コアとなるコードの解説

変更は `src/cmd/internal/obj/obj.go` ファイル内の `(*LineHist) LineString` メソッドにあります。

このメソッドは、コンパイラが生成するアセンブリコードやデバッグ情報において、元のソースコードの行情報を正確に表現するために使用されます。特に、`stk.Directive` が `true` の場合（例えば、`#line` ディレクティブなどによってソースファイルが論理的に変更された場合）や、親のスタックフレームが存在する場合に、行情報の参照元を親のスタックフレームに切り替えるロジックが含まれています。

追加されたコードは以下の通りです。

```go
			filename = stk.File
			if h.PrintFilenameOnly {
				filename = filepath.Base(filename)
			}
```

1.  `filename = stk.File`:
    *   `stk` は `stk.Parent` に更新されたばかりなので、この行は、現在のスタックフレーム (`stk`) に関連付けられた正しいファイルパスを `filename` 変数に再代入します。これにより、親のスタックフレームのコンテキストでファイル名が正しく反映されるようになります。
2.  `if h.PrintFilenameOnly { filename = filepath.Base(filename) }`:
    *   `h.PrintFilenameOnly` は `LineHist` 構造体のフィールドであり、ファイル名のみを表示するかどうかを制御するフラグです。
    *   このフラグが `true` の場合、`filepath.Base(filename)` を呼び出して、`filename` からディレクトリパス部分を削除し、ファイル名（例: `/path/to/file.go` から `file.go`）のみを抽出します。これは、出力の冗長性を減らし、より簡潔な行情報を提供するために行われます。

この修正により、`stk.Parent` に切り替わった後の `filename` が常に最新かつ適切な値を持つことが保証され、`dev.ssa` ビルドにおける行情報生成の正確性が向上し、結果としてビルドエラーが解消されました。

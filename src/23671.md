# [インデックス 23671] ファイルの概要

このコミットは、Goコマンドラインツールにおける`go install`の動作改善に関するものです。具体的には、引数なしで`go install`を実行した場合に、以前`go build`によってカレントディレクトリに生成された実行可能ファイルを自動的に削除する機能を追加します。これにより、古いバイナリが残存し、ユーザーが意図せず古いバージョンを実行してしまう問題を解決します。

## コミット

```
cmd/go: clean up after 'go build' during 'go install'

If 'go install' (with no arguments, meaning the current directory)
succeeds, remove the executable written by 'go build', if present.
This avoids leaving a stale binary behind during a sequence like:

        go build
        <test, mostly works, make small change>
        go install

Before this CL, the current directory still has the stale binary
from 'go build'. If $PATH contains dot, running the name of
the program will find this stale binary instead of the new,
installed one.

Remove the 'go build' target during 'go install', both to clean
up the directory and to avoid accidentally running the stale binary.

Another way to view this CL is that it makes the go command
behave as if 'go install' is implemented by 'go build' followed by
moving the resulting binary to the install location.

See #9645 for discussion and objections.

Fixes #9645.
```

## 変更の背景

この変更の背景には、`go build`と`go install`コマンドの挙動の違いと、それによって引き起こされる潜在的な問題があります。

Go言語の開発において、開発者は通常、以下のいずれかの方法でプログラムをコンパイル・実行します。

1.  **`go build`**: ソースコードをコンパイルし、実行可能ファイルを生成します。`main`パッケージの場合、デフォルトではカレントディレクトリに実行可能ファイルが生成されます。
2.  **`go install`**: ソースコードをコンパイルし、実行可能ファイルを生成した後、それを`$GOBIN`（または`$GOPATH/bin`、`$HOME/go/bin`）に配置します。これにより、システム全体の`$PATH`を通じてコマンドとして利用できるようになります。

問題は、開発者が以下のような手順を踏んだ場合に発生しました。

1.  `go build`を実行し、カレントディレクトリに実行可能ファイルを生成する。
2.  プログラムをテストし、小さな変更を加える。
3.  `go install`を実行し、更新されたプログラムをインストールする。

このシナリオにおいて、`go install`は新しいバイナリを`$GOBIN`に配置しますが、カレントディレクトリに残された`go build`によって生成された古いバイナリはそのまま残っていました。もしユーザーの`$PATH`環境変数にカレントディレクトリ（`.`）が含まれている場合、コマンド名でプログラムを実行しようとすると、`$GOBIN`にインストールされた新しいバイナリではなく、カレントディレクトリに残された古いバイナリが優先的に見つかり、実行されてしまう可能性がありました。

この挙動は、ユーザーが最新のコードをインストールしたと信じているにもかかわらず、実際には古いバージョンのプログラムを実行してしまうという混乱やバグの原因となり得ました。このコミットは、この「古いバイナリの残存」という問題を解決し、`go install`がより予測可能で安全な動作をするようにすることを目的としています。

コミットメッセージには「See #9645 for discussion and objections. Fixes #9645.」とありますが、公開されているGoのIssueトラッカーではこの番号のIssueは直接見つかりませんでした。しかし、コミットメッセージ自体が問題の状況と解決策を明確に説明しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコマンドと関連する概念について理解しておく必要があります。

*   **`go build`コマンド**:
    *   Goのソースコードをコンパイルして実行可能ファイルを生成するコマンドです。
    *   `main`パッケージを含むディレクトリで実行された場合、デフォルトではそのディレクトリ内に実行可能ファイル（Windowsでは`.exe`、それ以外では拡張子なし）を生成します。
    *   ライブラリパッケージの場合、コンパイルされたパッケージアーカイブ（`.a`ファイル）を`$GOCACHE`に保存します。
*   **`go install`コマンド**:
    *   `go build`と同様にソースコードをコンパイルしますが、その後の処理が異なります。
    *   `main`パッケージの場合、生成された実行可能ファイルを`$GOBIN`環境変数で指定されたディレクトリに移動します。`$GOBIN`が設定されていない場合、`$GOPATH/bin`または`$HOME/go/bin`がデフォルトで使用されます。
    *   ライブラリパッケージの場合、コンパイルされたパッケージアーカイブを`$GOPATH/pkg`または`$HOME/go/pkg`に配置します。
    *   `go install`の主な目的は、コンパイルされたプログラムをシステム全体のコマンドとして利用可能にすることです。
*   **`$PATH`環境変数**:
    *   オペレーティングシステムが実行可能ファイルを探すディレクトリのリストを定義する環境変数です。
    *   ユーザーがコマンド名を入力すると、OSはこの`$PATH`リストに沿ってディレクトリを順番に検索し、最初に見つかった実行可能ファイルを実行します。
    *   カレントディレクトリ（`.`）が`$PATH`に含まれている場合、カレントディレクトリ内の実行可能ファイルが他のパスよりも優先されることがあります。これが、古いバイナリが実行される原因となり得ました。
*   **`main`パッケージ**:
    *   Goプログラムのエントリポイントとなるパッケージです。`main`パッケージは実行可能ファイルを生成します。
*   **実行可能ファイルのパーミッション**:
    *   Unix系システムでは、ファイルが実行可能であるかどうかはパーミッションビット（`0111`など）によって決定されます。`os.Stat`で取得できる`os.FileInfo`の`Mode()`メソッドで確認できます。

## 技術的詳細

このコミットによる技術的な変更は、`go install`コマンドの内部ロジックに、`go build`によって残された可能性のある古い実行可能ファイルを検出して削除するステップを追加した点にあります。

変更は主に`src/cmd/go/build.go`ファイルの`runInstall`関数内で行われています。

1.  **条件判定**: `go install`が成功した後、以下の条件がすべて満たされる場合にのみ、クリーンアップ処理が実行されます。
    *   `len(args) == 0`: `go install`が引数なしで実行された場合。これは、カレントディレクトリのパッケージをインストールすることを意味します。
    *   `len(pkgs) == 1`: 処理対象のパッケージが1つだけの場合。
    *   `pkgs[0].Name == "main"`: そのパッケージが`main`パッケージ（つまり実行可能ファイルを生成するパッケージ）である場合。
    これらの条件は、ユーザーがカレントディレクトリで`go build`と`go install`を連続して実行し、古いバイナリが残る可能性のあるシナリオを特定するために重要です。

2.  **ターゲットバイナリ名の特定**: `go build`がカレントディレクトリに生成するであろう実行可能ファイルの名前を特定します。これは、パッケージのインポートパスの最後の要素に、OS固有の実行可能ファイルのサフィックス（Windowsの`.exe`など）を付加することで行われます。
    *   例: `importPath`が`github.com/user/mycmd`であれば、`targ`は`mycmd`（または`mycmd.exe`）となります。

3.  **ファイルの存在と実行可能性の確認**: 特定された名前のファイルがカレントディレクトリに存在するかどうか、そしてそれが通常のファイルであり、かつ実行可能パーミッションを持っているかどうかを確認します。
    *   `os.Stat(targ)`: ファイルの情報を取得します。エラーが発生しない場合、ファイルは存在します。
    *   `fi.Mode()`: ファイルのモード（パーミッションやファイルタイプ）を取得します。
    *   `m.IsRegular()`: ファイルが通常のファイル（ディレクトリやシンボリックリンクではない）であるかを確認します。
    *   `m&0111 != 0`: ファイルモードの実行可能ビットが設定されているかを確認します。これは、Unix系システムでファイルが実行可能であるかを判断する一般的な方法です。

4.  **ファイルの削除**: 上記のすべての条件が満たされた場合、`os.Remove(targ)`を呼び出して、カレントディレクトリに残された古い実行可能ファイルを削除します。

この変更により、`go install`は、あたかも`go build`で生成されたバイナリを`$GOBIN`に移動する操作であるかのように振る舞うようになります。これにより、カレントディレクトリが常にクリーンな状態に保たれ、ユーザーが意図せず古いバイナリを実行してしまうリスクがなくなります。

また、`src/cmd/go/test.bash`には、この新しいクリーンアップロジックが正しく機能することを確認するためのテストケースが追加されています。これにより、変更が意図した通りに動作し、将来のリグレッションを防ぐことができます。

## コアとなるコードの解説

### `src/cmd/go/build.go`の変更点

```go
 // Success. If this command is 'go install' with no arguments
 // and the current directory (the implicit argument) is a command,
 // remove any leftover command binary from a previous 'go build'.
 // The binary is installed; it's not needed here anymore.
 // And worse it might be a stale copy, which you don't want to find
 // instead of the installed one if $PATH contains dot.
 // One way to view this behavior is that it is as if 'go install' first
 // runs 'go build' and the moves the generated file to the install dir.
 // See issue 9645.
 if len(args) == 0 && len(pkgs) == 1 && pkgs[0].Name == "main" {
  // Compute file 'go build' would have created.
  // If it exists and is an executable file, remove it.
  _, targ := filepath.Split(pkgs[0].ImportPath)
  targ += exeSuffix
  fi, err := os.Stat(targ)
  if err == nil {
   m := fi.Mode()
   if m.IsRegular() && m&0111 != 0 {
    os.Remove(targ)
   }
  }
 }
```

このコードブロックは、`go install`が正常に完了した後に実行されます。

*   `if len(args) == 0 && len(pkgs) == 1 && pkgs[0].Name == "main"`:
    *   `len(args) == 0`: `go install`が引数なしで実行されたことを確認します。これは、カレントディレクトリのパッケージを対象としていることを意味します。
    *   `len(pkgs) == 1`: 処理対象のパッケージが単一であることを確認します。
    *   `pkgs[0].Name == "main"`: そのパッケージが実行可能ファイルを生成する`main`パッケージであることを確認します。
    *   これらの条件がすべて真の場合にのみ、クリーンアップ処理が実行されます。

*   `_, targ := filepath.Split(pkgs[0].ImportPath)`:
    *   `pkgs[0].ImportPath`は、対象パッケージのインポートパス（例: `github.com/user/mycmd`）です。
    *   `filepath.Split`関数は、パスをディレクトリとファイル名に分割します。ここではファイル名部分（`mycmd`）のみを`targ`変数に取得しています。これが`go build`が生成するであろう実行可能ファイルの名前のベースとなります。

*   `targ += exeSuffix`:
    *   `exeSuffix`は、Goコマンドが内部的に持つ、OSに応じた実行可能ファイルのサフィックス（例: Windowsでは`.exe`、それ以外では空文字列）です。
    *   これにより、`targ`は最終的な実行可能ファイル名（例: `mycmd`または`mycmd.exe`）になります。

*   `fi, err := os.Stat(targ)`:
    *   `os.Stat`関数は、指定されたパスのファイル情報を取得します。
    *   `err == nil`の場合、ファイルは存在します。

*   `m := fi.Mode()`:
    *   `fi.Mode()`は、取得したファイル情報からファイルモード（パーミッションやファイルタイプ）を取得します。

*   `if m.IsRegular() && m&0111 != 0`:
    *   `m.IsRegular()`: ファイルが通常のファイル（ディレクトリやシンボリックリンクではない）であることを確認します。
    *   `m&0111 != 0`: ファイルモードの実行可能ビットが設定されていることを確認します。`0111`は、所有者、グループ、その他のユーザーに対して実行権限があることを示すビットマスクです。これにより、実際に実行可能なバイナリファイルであるかを判断します。

*   `os.Remove(targ)`:
    *   上記のすべての条件が満たされた場合、`os.Remove`関数を呼び出して、カレントディレクトリにある古い実行可能ファイルを削除します。

### `src/cmd/go/test.bash`の変更点

```bash
TEST 'go install cleans up after go build'
d=$(TMPDIR=/var/tmp mktemp -d -t testgoXXX)
export GOPATH=$d
mkdir -p $d/src/mycmd
echo 'package main; func main(){}' >$d/src/mycmd/main.go
old=$(pwd)
cd $d/src/mycmd
"$old/testgo" build
if [ ! -x mycmd ]; then
	echo "testgo build did not write command binary"
	ok=false
fi
"$old/testgo" install
if [ -e mycmd ]; then
	echo "testgo install did not remove command binary"
	ok=false
fi
"$old/testgo" build
if [ ! -x mycmd ]; then
	echo "testgo build did not write command binary (second time)"
	ok=false
fi
# install with arguments does not remove the target,
# even in the same directory
"$old/testgo" install mycmd
if [ ! -e mycmd ]; then
	echo "testgo install mycmd removed command binary when run in mycmd"
	ok=false
fi
"$old/testgo" build
if [ ! -x mycmd ]; then
	echo "testgo build did not write command binary (third time)"
	ok=false
fi
# and especially not outside the directory
cd $d
cp src/mycmd/mycmd .
"$old/testgo" install mycmd
if [ ! -e $d/src/mycmd/mycmd ]; then
	echo "testgo install mycmd removed command binary from its source dir when run outside mycmd"
	ok=false
fi
if [ ! -e $d/mycmd ]; then
	echo "testgo install mycmd removed command binary from current dir when run outside mycmd"
	ok=false
fi
cd "$old"
rm -r $d
```

このテストスクリプトは、一時ディレクトリを作成し、その中で`mycmd`というシンプルなGoプログラムをビルド・インストールすることで、`go install`のクリーンアップ動作を検証します。

1.  **初期設定**: 一時ディレクトリ`$d`を作成し、`GOPATH`に設定します。`$d/src/mycmd`ディレクトリに`main.go`ファイルを作成します。
2.  **`go build`の実行**: `"$old/testgo" build`を実行し、`mycmd`バイナリがカレントディレクトリに生成されることを確認します。
3.  **`go install`の実行とクリーンアップの検証**: `"$old/testgo" install`を実行した後、`mycmd`バイナリがカレントディレクトリから削除されていることを確認します。これがこのコミットの主要な変更点の検証です。
4.  **引数付き`go install`の検証**: `go build`で再度バイナリを生成した後、`"$old/testgo" install mycmd`（引数付き）を実行します。この場合、クリーンアップは行われないはずなので、`mycmd`バイナリが残っていることを確認します。
5.  **外部からの`go install`の検証**: `go build`でバイナリを生成し、それを一時ディレクトリのルートにコピーした後、`cd $d`でディレクトリを移動し、`"$old/testgo" install mycmd`を実行します。この場合も、元のソースディレクトリやコピーされたバイナリが削除されないことを確認します。これは、クリーンアップが「引数なしでカレントディレクトリの`main`パッケージをインストールする場合」に限定されることを検証しています。
6.  **クリーンアップ**: テスト終了後、一時ディレクトリを削除します。

これらのテストケースは、新しいクリーンアップロジックが意図したシナリオで正確に動作し、意図しないシナリオでは副作用を起こさないことを保証します。

このコミットでは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおける条件分岐の最適化が導入されています。具体的には、`if !cond` の形式の条件分岐を、ブランチを入れ替えることで `if cond` の形式に書き換える変更が加えられました。これにより、SSAグラフの簡素化と、その後の最適化の機会を増やすことを目的としています。

変更されたファイルは以下の通りです。

## 変更の背景

この変更の背景には、コンパイラの最適化フェーズにおけるコードの正規化と簡素化という目的があります。Goコンパイラは、プログラムをSSA（Static Single Assignment）形式という中間表現に変換し、その上で様々な最適化を行います。

`if !cond { A } else { B }` のような条件分岐は、論理否定 (`!`) を含むため、SSAグラフ上で余分な `OpNot` オペレーションを生成します。この `OpNot` は、条件を反転させるためだけに存在し、その後の最適化の妨げになる可能性があります。

このコミットは、このような `if !cond` のパターンを `if cond { B } else { A }` のように書き換えることで、論理否定オペレーションを削除し、条件分岐の構造をより単純な形に正規化します。これにより、SSAグラフが簡素化され、以下のようなメリットが期待されます。

1.  **最適化の機会の増加**: `OpNot` がなくなることで、条件 `cond` 自体に対するより直接的な最適化（例: 定数畳み込み、共通部分式除去など）が可能になります。
2.  **コード生成の効率化**: 簡素化されたSSAグラフは、バックエンドでの機械語コード生成において、より効率的な命令シーケンスを生成しやすくなります。
3.  **コンパイラの複雑性の軽減**: 特定のパターンを正規化することで、コンパイラの他の部分がより単純な条件分岐のケースのみを考慮すればよくなるため、コンパイラ自体の複雑性を軽減できます。

## 前提知識の解説

### SSA (Static Single Assignment) 形式

SSA形式は、コンパイラがプログラムを最適化するために使用する中間表現（IR）の一種です。SSA形式の主要な特性は、「静的単一割り当て」という名前が示す通り、各変数が一度だけ割り当てられることです。これにより、変数の定義と使用の関係が明確になり、データフロー解析や最適化が容易になります。

Goコンパイラでは、ソースコードが抽象構文木（AST）にパースされた後、SSA形式に変換されます。このSSA形式のグラフ上で、様々な最適化パスが実行され、最終的に機械語コードが生成されます。

### GoコンパイラとSSA

Goコンパイラ（`cmd/compile`）は、Go言語のソースコードを機械語に変換する役割を担っています。その過程で、SSA形式は非常に重要な役割を果たします。SSAバックエンドは、Go 1.7から導入され、コンパイラの最適化能力を大幅に向上させました。

SSA形式では、プログラムの各操作が「Value」として表現され、これらのValueが有向非巡回グラフ（DAG）を形成します。条件分岐やループなどの制御フローは「Block」として表現され、Block間にはエッジが張られます。

### 条件分岐の最適化

コンパイラにおける条件分岐の最適化は、プログラムの実行効率を向上させるための重要な手法です。これには以下のようなものがあります。

*   **定数畳み込み**: 条件が定数である場合、分岐を削除し、到達可能なブランチのみを残します。
*   **デッドコード削除**: 決して実行されないコードパスを削除します。
*   **分岐予測の改善**: CPUの分岐予測器がより正確に予測できるように、分岐の構造を調整します。
*   **条件の反転**: `if !cond` のようなパターンを `if cond` に変換し、ブランチを入れ替えることで、論理否定のオーバーヘッドをなくします。今回のコミットはこのカテゴリに属します。

### `OpNot` と `BlockIf`

GoコンコンパイラのSSA形式において、特定の操作やブロックは以下のように表現されます。

*   **`OpNot`**: 論理否定 (`!`) を表すSSAオペレーションです。例えば、`!x` は `OpNot(x)` というValueとして表現されます。
*   **`BlockIf`**: 条件付き分岐を表すSSAブロックの種類です。`if` ステートメントに対応し、条件Valueと、条件が真の場合と偽の場合にそれぞれ遷移する2つのサクセッサ（後続ブロック）を持ちます。

## 技術的詳細

このコミットの核となる技術的詳細は、SSA形式における条件分岐 `(If (Not cond) yes no)` の書き換えルールにあります。

元のコードが `if !cond { yes_branch } else { no_branch }` であった場合、SSA形式では `BlockIf` の制御Valueが `OpNot(cond)` となります。そして、`yes_branch` が `BlockIf` の最初のサクセッサ、`no_branch` が2番目のサクセッサに対応します。

このコミットは、このパターンを `(If cond no yes)` に書き換えることで、論理否定の `OpNot` オペレーションを完全に削除します。つまり、`if cond { no_branch } else { yes_branch }` と同等の意味になります。

この書き換えは、GoコンパイラのSSAバックエンドにおいて、主に2つの場所で行われます。

1.  **`generic.rules`**: これは、SSA最適化ルールを記述するためのDSL（Domain Specific Language）ファイルです。コンパイラはこれらのルールを読み込み、パターンマッチングと書き換えを自動的に行います。このファイルに `(If (Not cond) yes no) -> (If cond no yes)` というルールが追加されました。これは、SSAグラフ上で `OpNot` を含む `If` ブロックを見つけたら、その `OpNot` を取り除き、`If` ブロックのサクセッサ（`yes` と `no`）を入れ替えることを意味します。

2.  **`rewritegeneric.go`**: これは、`generic.rules` で定義されたルールが適用できない、あるいはより複雑なロジックが必要な場合に、Go言語で直接SSAグラフを書き換えるためのコードです。このファイルには、`BlockIf` の制御Valueが `OpNot` である場合に、その `OpNot` を取り除き、`BlockIf` のサクセッサを入れ替えるロジックが追加されました。これは、`generic.rules` のルールと全く同じ変換を実行しますが、Goコードとして明示的に実装されています。

この二重の実装は、SSA最適化の堅牢性を高めるため、あるいは特定のコンテキストでの効率的な適用を保証するために行われることがあります。`generic.rules` は宣言的なルールベースの最適化を可能にし、`rewritegeneric.go` はより命令的な制御を可能にします。

この最適化により、SSAグラフから冗長な `OpNot` が削除され、グラフがよりシンプルになります。これにより、後続の最適化パスがより効果的に機能し、最終的に生成される機械語コードの品質が向上します。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/gen/generic.rules` の変更点

追加されたルール `(If (Not cond) yes no) -> (If cond no yes)` は、SSAグラフのパターンマッチングと書き換えを定義しています。

*   `(If (Not cond) yes no)`: これは、`If` ブロックの制御Valueが `Not` オペレーションであり、その `Not` オペレーションの引数が `cond` であるパターンにマッチします。`yes` と `no` は、それぞれ条件が真の場合と偽の場合に実行されるサクセッサブロックを表します。
*   `-> (If cond no yes)`: マッチしたパターンを、`If` ブロックの制御Valueを `cond` に変更し、サクセッサブロックの順序を `no`、`yes` と入れ替えることで書き換えます。

このルールにより、`if !cond { A } else { B }` という論理構造が、`if cond { B } else { A }` という等価な論理構造に変換され、`Not` オペレーションが削除されます。

### `src/cmd/compile/internal/ssa/rewritegeneric.go` の変更点

`rewriteBlockgeneric` 関数内の `BlockIf` ケースに、手動での書き換えロジックが追加されています。

1.  `v := b.Control`: 現在の `BlockIf` ブロックの制御Value（条件を表すValue）を取得します。
2.  `if v.Op != OpNot`: 制御Valueのオペレーションが `OpNot` でない場合、この最適化は適用できないため、処理をスキップします。
3.  `cond := v.Args[0]`: `OpNot` オペレーションの引数（つまり、元の条件 `cond`）を取得します。
4.  `yes := b.Succs[0]` と `no := b.Succs[1]`: 現在の `BlockIf` ブロックのサクセッサ（真のブランチと偽のブランチ）を取得します。
5.  `b.Kind = BlockIf`: ブロックの種類は `BlockIf` のままです。
6.  `b.Control = cond`: 制御Valueを `OpNot` を取り除いた `cond` に変更します。
7.  `b.Succs[0] = no` と `b.Succs[1] = yes`: サクセッサの順序を入れ替えます。これにより、元の `yes` ブランチが `no` の位置に、元の `no` ブランチが `yes` の位置に移動します。
8.  `return true`: 書き換えが成功したことを示します。

このGoコードによる書き換えは、`generic.rules` で定義されたルールと全く同じ論理変換を、より低レベルで明示的に実装しています。これにより、コンパイラは `if !cond` のパターンを効率的に `if cond` に変換し、SSAグラフを最適化された状態に保つことができます。

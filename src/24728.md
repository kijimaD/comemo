## 元コミット内容

このコミットは、Go言語の標準ライブラリ `bytes` パッケージ内の `Compare` 関数の `amd64` アセンブリ実装を最適化するものです。主な変更点は、63バイトを超えるサイズのバイト配列比較において、ループアンローリングとSIMD (Single Instruction, Multiple Data) 命令を導入することで、処理効率を大幅に向上させることにあります。

コミットメッセージには、Intel Core i7-4770 CPU (Haswellベース) 上でのベンチマーク結果が示されており、特に128バイト以上の大きな配列において、最大で約37%の性能改善が確認されています。

## 変更の背景

Go言語の `bytes.Compare` 関数は、2つのバイトスライスを辞書順に比較し、その結果に応じて負の整数、ゼロ、または正の整数を返します。この関数は、文字列比較やハッシュ計算など、様々な場面で頻繁に利用される基本的な操作です。

従来の `Compare` 関数の実装では、バイト配列の比較はループ内で1バイトずつ、または数バイトずつ処理されることが一般的でした。しかし、現代のCPUはSIMD命令セット（例: IntelのSSEやAVX）をサポートしており、これにより一度に複数のデータ要素（例えば、16バイトや32バイト）を並列に処理することが可能です。

サイズの大きなバイト配列を比較する際、従来の逐次的な比較方法では、ループのオーバーヘッドやキャッシュ効率の悪さから性能がボトルネックとなることがありました。このコミットの背景には、このような大規模なデータ比較における性能課題を解決し、Goプログラム全体の実行速度を向上させる目的があります。特に、データ処理やネットワーク通信など、バイト配列の比較が頻繁に行われるアプリケーションにおいて、この最適化は大きな影響を与えます。

## 前提知識の解説

### 1. `bytes.Compare` 関数

Go言語の `bytes` パッケージに含まれる `Compare` 関数は、`func Compare(a, b []byte) int` というシグネチャを持ちます。この関数は、2つのバイトスライス `a` と `b` を辞書順に比較します。
*   `a == b` の場合、`0` を返します。
*   `a < b` の場合、`-1` を返します。
*   `a > b` の場合、`+1` を返します。

内部的には、この関数は通常、バイトスライスを構成するバイトを先頭から順に比較し、最初に異なるバイトが見つかった時点でその大小関係を判断します。両方のスライスが同じ長さで、かつ全てのバイトが一致した場合に等しいと判断されます。

### 2. `amd64` アセンブリ言語とGoランタイム

Go言語は、パフォーマンスが重要な部分（特にランタイムや標準ライブラリの一部）でアセンブリ言語を使用します。`amd64` は64ビット版のx86アーキテクチャを指し、IntelおよびAMDのプロセッサで広く採用されています。Goのランタイムは、特定のアーキテクチャ向けに最適化されたアセンブリコードを生成することで、C言語や他の言語で書かれた同等のコードよりも高速な実行を実現することがあります。

`src/runtime/asm_amd64.s` のようなファイルは、Goランタイムの `amd64` 向けアセンブリコードを含んでいます。これらのファイルは、Goのコンパイラによって生成される機械語に直接マッピングされ、低レベルな最適化を可能にします。

### 3. ループアンローリング (Loop Unrolling)

ループアンローリングは、プログラムの最適化手法の一つです。ループの各イテレーションで実行される処理を複数回分まとめて記述することで、ループ制御（カウンタのインクリメント、条件チェック、ジャンプ命令など）のオーバーヘッドを削減します。

例えば、100回繰り返すループがあった場合、ループアンローリングでは1回のイテレーションで4回分の処理を行うようにコードを書き換え、ループ回数を25回に減らすといったことを行います。これにより、ループの開始・終了処理や条件分岐の回数が減り、CPUのパイプライン効率が向上し、実行速度が向上する可能性があります。ただし、コードサイズが増加するというデメリットもあります。

### 4. SIMD (Single Instruction, Multiple Data) 命令

SIMDは、単一の命令で複数のデータ要素に対して同じ操作を同時に実行できるCPUの機能です。これにより、データ並列性が高い処理（例えば、画像処理、音声処理、科学技術計算、バイト配列の比較など）を高速化できます。

`amd64` アーキテクチャでは、SSE (Streaming SIMD Extensions) や AVX (Advanced Vector Extensions) といったSIMD命令セットが提供されています。これらの命令は、128ビットや256ビットのレジスタ（XMMレジスタやYMMレジスタ）を使用して、複数の整数や浮動小数点数を一度に処理します。

このコミットで使われている主要なSIMD命令は以下の通りです。

*   **`MOVOU` (Move Unaligned Oword)**: メモリからXMMレジスタへ、またはXMMレジスタからメモリへ、128ビット（16バイト）のデータを移動します。アラインメントされていないアドレスからの読み書きも可能です。
*   **`PCMPEQB` (Packed Compare Equal Bytes)**: 2つのXMMレジスタ内の対応するバイトを比較し、等しい場合は結果レジスタの対応するバイトに `0xFF` を、等しくない場合は `0x00` を設定します。
*   **`PMOVMSKB` (Packed Move Mask Byte)**: XMMレジスタ内の各バイトの最上位ビット（MSB）を抽出し、それらを16ビットのマスクとして汎用レジスタに格納します。`PCMPEQB` の結果と組み合わせることで、どのバイトが一致しなかったかを効率的に検出できます。
*   **`XORQ $0xffff, AX`**: `AX` レジスタの内容と `0xffff` をXOR演算します。`PMOVMSKB` の結果が `0x0000` (全て一致) の場合、`0xffff` に反転させ、不一致がある場合は `0x0000` 以外の値になるようにします。これにより、`JNE` (Jump if Not Equal) 命令で不一致の有無を効率的に判定できます。

これらの命令を組み合わせることで、16バイト単位で高速な比較を行い、不一致が見つかった場合はその位置を特定して詳細な比較に移行するという流れが実現されます。

## 技術的詳細

このコミットの技術的詳細の中心は、`src/runtime/asm_amd64.s` ファイル内の `runtime·cmpbody` 関数における変更です。この関数は、Goの `bytes.Compare` の内部で呼び出される低レベルなバイト比較ルーチンです。

変更前は、比較対象のバイト配列のサイズに応じて、より小さなブロック（例えば8バイト、16バイト）でループ処理を行うか、あるいは1バイトずつ比較するようなロジックが組まれていました。しかし、63バイトを超えるような大きな配列の場合、この既存のロジックではSIMD命令の恩恵を十分に受けられず、性能が伸び悩んでいました。

コミットでは、`runtime·cmpbody` の冒頭に `CMPQ R8, $63` と `JA big_loop` という条件分岐が追加されています。これは、比較対象のバイト配列の長さ（`R8` レジスタに格納されている）が63バイトより大きい場合に、新しく追加された `big_loop` セクションへジャンプすることを意味します。

`big_loop` セクションでは、以下の手順でバイト配列の比較が行われます。

1.  **16バイト単位のロードと比較**:
    *   `MOVOU (SI), X0` と `MOVOU (DI), X1`: ソース (`SI`) とデスティネーション (`DI`) のポインタからそれぞれ16バイト（128ビット）のデータをXMMレジスタ `X0` と `X1` にロードします。
    *   `PCMPEQB X0, X1`: `X0` と `X1` の各バイトを比較し、結果を `X1` に格納します。一致するバイトは `0xFF`、不一致のバイトは `0x00` となります。
    *   `PMOVMSKB X1, AX`: `X1` レジスタの各バイトの最上位ビットを抽出し、16ビットのマスクとして `AX` レジスタに格納します。
    *   `XORQ $0xffff, AX`: `AX` のビットを反転させます。これにより、全てのバイトが一致した場合 (`PMOVMSKB` の結果が `0x0000`) は `0xffff` になり、一つでも不一致のバイトがあれば `0x0000` 以外の値になります。
    *   `JNE diff16`: `AX` がゼロでなければ（つまり、不一致のバイトがあれば）、`diff16` ラベルにジャンプします。`diff16` は、不一致が見つかった最初のバイトの位置を特定し、その差を返すための既存のロジックです。

2.  **4回分のアンローリング**: 上記の16バイト比較のシーケンスが4回繰り返されます。これにより、一度の `big_loop` のイテレーションで合計64バイトのデータが比較されます。
    *   最初の16バイト比較で不一致があれば `diff16` へ。
    *   次の16バイト（オフセット16）比較で不一致があれば `diff32` へ。
    *   次の16バイト（オフセット32）比較で不一致があれば `diff48` へ。
    *   次の16バイト（オフセット48）比較で不一致があれば `diff64` へ。

3.  **ポインタと長さの更新**: 64バイトの比較が完了し、不一致が見つからなかった場合、`SI` と `DI` ポインタを64バイト進め、残りの長さ `R8` から64を減算します。

4.  **ループ継続または終了**:
    *   `CMPQ R8, $64` と `JBE loop`: 残りの長さ `R8` が64バイト以下になった場合、`loop` ラベル（既存の比較ロジック）にジャンプして残りのバイトを処理します。
    *   `JMP big_loop`: 残りの長さがまだ64バイトより大きい場合、`big_loop` の先頭に戻り、次の64バイトブロックを比較します。

この最適化により、大きなバイト配列の比較において、ループ制御のオーバーヘッドを最小限に抑えつつ、SIMD命令による並列処理の恩恵を最大限に活用できるようになります。

### `src/runtime/asm_amd64.s`

このファイルには、`runtime·cmpbody` 関数のアセンブリコードが変更されています。

```assembly
// ... (既存のコード) ...

	CMPQ	R8, $63  // 比較対象の長さが63バイトより大きいか？
	JA	big_loop // 大きい場合は big_loop へジャンプ

loop:
	// ... (既存の比較ロジック) ...

// ... (既存の diffXX ラベル) ...

	// this works for >= 64 bytes of data.

	MOVOU	(SI), X0      // 最初の16バイトをロード (ソース)
	MOVOU	(DI), X1      // 最初の16バイトをロード (デスティネーション)
	PCMPEQB X0, X1        // バイト単位で比較
	PMOVMSKB X1, AX       // 比較結果のマスクを AX に格納
	XORQ	$0xffff, AX   // マスクを反転 (全て一致なら 0xffff)
	JNE	diff16        // 不一致があれば diff16 へ

	MOVOU	16(SI), X0    // 次の16バイトをロード
	MOVOU	16(DI), X1
	PCMPEQB X0, X1
	PMOVMSKB X1, AX
	XORQ	$0xffff, AX
	JNE	diff32        // 不一致があれば diff32 へ

	MOVOU	32(SI), X0    // 次の16バイトをロード
	MOVOU	32(DI), X1
	PCMPEQB X0, X1
	PMOVMSKB X1, AX
	XORQ	$0xffff, AX
	JNE	diff48        // 不一致があれば diff48 へ

	MOVOU	48(SI), X0    // 次の16バイトをロード
	MOVOU	48(DI), X1
	PCMPEQB X0, X1
	PMOVMSKB X1, AX
	XORQ	$0xffff, AX
	JNE	diff64        // 不一致があれば diff64 へ

	ADDQ	$64, SI       // ソースポインタを64バイト進める
	ADDQ	$64, DI       // デスティネーションポインタを64バイト進める
	SUBQ	$64, R8       // 残りの長さを64バイト減らす
	CMPQ	R8, $64       // 残りの長さが64バイト以下か？
	JBE	loop          // 以下なら既存の loop へ
	JMP	big_loop      // まだ64バイトより大きければ big_loop を継続
```

## コアとなるコードの解説

`src/runtime/asm_amd64.s` の変更は、`runtime·cmpbody` 関数に `big_loop` という新しいセクションを追加し、既存の比較ロジックの前に分岐を設けることで、大きなバイト配列の比較を最適化しています。

1.  **初期分岐**: `CMPQ R8, $63` と `JA big_loop` は、比較対象のバイト配列の長さが63バイトを超えている場合に、新しく最適化された `big_loop` へ処理を移すためのものです。63バイトという閾値は、おそらくSIMD命令の効率的な利用と、既存の小サイズ向け最適化とのバランスを考慮して決定されたものと考えられます。

2.  **`big_loop` の構造**:
    *   `big_loop` は、64バイトのブロックを一度に処理するように設計されています。これは、16バイトのSIMD比較を4回連続して行うことで実現されます（16バイト * 4 = 64バイト）。
    *   各16バイトの比較は、`MOVOU` でデータをXMMレジスタにロードし、`PCMPEQB` でバイト単位の等価比較を行い、`PMOVMSKB` で比較結果のマスクを生成し、`XORQ $0xffff, AX` でマスクを反転させて `JNE` で不一致をチェックするという一連のSIMD命令で行われます。
    *   `JNE diffXX` 命令は、不一致が見つかった場合に、その不一致がどの16バイトブロック内で発生したかに応じて、既存の `diff16`, `diff32`, `diff48`, `diff64` ラベルにジャンプします。これらのラベルは、不一致の正確な位置を特定し、`bytes.Compare` の戻り値を計算するためのロジックを含んでいます。
    *   64バイトブロック全体で不一致がなかった場合、ポインタ (`SI`, `DI`) を64バイト進め、残りの長さ (`R8`) を64減らします。
    *   残りの長さがまだ64バイトより大きい場合は `big_loop` を継続し、そうでない場合は既存の `loop` セクションにジャンプして残りのバイトを処理します。

このアプローチにより、CPUは一度に大量のデータを効率的に比較でき、ループの反復回数も大幅に削減されるため、特に大きなバイト配列の比較において顕著な性能向上が得られます。ベンチマーク結果が示すように、128バイト以上の配列で性能が大きく改善しているのは、このSIMDとループアンローリングの組み合わせによる効果です。

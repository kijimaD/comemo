# [インデックス 24956] ファイルの概要

このコミットは、Go言語の `archive/zip` パッケージにおけるバグ修正です。特定の条件下でZIPアーカイブのコメントが誤ってZIP64ディレクトリヘッダーとして解釈され、「unexpected EOF (予期せぬファイル終端)」エラーが発生する問題を解決します。この修正により、アーカイブのコメントセクションにZIP64ディレクトリのようなデータが含まれていても、それが正しく処理されるようになり、ZIPファイルの堅牢な読み込みが保証されます。

## 元コミット内容

`archive/zip: fixes unexpected EOF when reading archive`

## 変更の背景

この変更は、Go言語の `archive/zip` パッケージが特定のZIPアーカイブを読み込む際に発生する「unexpected EOF」エラーを修正するために行われました。問題の根本原因は、ZIPアーカイブの「コメント」セクションに、偶然にもZIP64中央ディレクトリロケーター（Zip64 End of Central Directory Locator）のようなバイトシーケンスが含まれていた場合にありました。

`archive/zip` パッケージは、アーカイブの終端から中央ディレクトリの情報を探し、その過程でZIP64の構造を検出するロジックを持っています。しかし、コメントデータがZIP64ロケーターのシグネチャ（`0x07064b50`）と一致するようなバイト列を含んでいた場合、正規のZIP64ロケーターではないにもかかわらず、それを本物のZIP64ロケーターとして誤認識してしまっていました。

この誤認識により、存在しないZIP64中央ディレクトリのオフセットを読み取ろうとし、結果としてファイル終端を超えて読み込みを試みるため、「unexpected EOF」エラーが発生していました。この問題は、Issue #12449 として報告されていました。

## 前提知識の解説

このコミットを理解するためには、ZIPファイルフォーマット、特に中央ディレクトリ（Central Directory）とZIP64拡張に関する知識が必要です。

1.  **ZIPファイル構造の概要**:
    *   ZIPファイルは、複数のファイルエントリと、それらのファイルエントリに関するメタデータを含む「中央ディレクトリ」で構成されます。
    *   中央ディレクトリは、ファイルの最後に配置され、各ファイルエントリの場所、サイズ、圧縮方法などの情報を含みます。
    *   中央ディレクトリの最後には、「End of Central Directory Record (EOCD)」と呼ばれるレコードがあり、中央ディレクトリの開始オフセット、エントリ数、サイズなどの情報が格納されています。
    *   EOCDの後に、オプションでZIPファイル全体のコメントを格納できます。

2.  **ZIP64拡張**:
    *   従来のZIPフォーマットには、ファイルサイズやアーカイブサイズ、エントリ数、オフセットなどに4GBや65535エントリといった制限がありました。
    *   これらの制限を超えるファイルを扱うために、ZIP64拡張が導入されました。
    *   ZIP64では、EOCDの代わりに「Zip64 End of Central Directory Record」と「Zip64 End of Central Directory Locator」という2つの追加レコードが導入されます。
    *   **Zip64 End of Central Directory Locator**: EOCDの直前に配置され、Zip64 EOCDレコードの場所を指し示します。このレコードは特定のシグネチャ（`0x07064b50`）で始まります。
    *   **Zip64 End of Central Directory Record**: 実際のZIP64中央ディレクトリのメタデータ（サイズ、オフセットなど）を含みます。

3.  **`0xffff` と `0xffffffff` の意味**:
    *   従来のZIPフォーマットでは、ファイルサイズやオフセット、エントリ数などのフィールドは固定長（例: 2バイトや4バイト）で表現されます。
    *   これらのフィールドが最大値（例: 2バイトフィールドなら `0xffff`、4バイトフィールドなら `0xffffffff`）を持つ場合、それは「値が大きすぎてこのフィールドには収まらないため、ZIP64拡張を参照する必要がある」という特別な意味を持ちます。
    *   `archive/zip` パッケージは、これらの特殊な値を見つけると、ZIP64ロケーターを探しに行くロジックを持っていました。

このコミットのバグは、EOCDの後に続くコメントデータが、偶然にもZIP64ロケーターのシグネチャや、ZIP64拡張を参照すべき特殊な値（`0xffff` や `0xffffffff`）を含んでいた場合に発生しました。

## 技術的詳細

`archive/zip` パッケージの `readDirectoryEnd` 関数は、ZIPファイルのEOCDレコードを読み込み、中央ディレクトリの情報を取得する役割を担っています。この関数内で、EOCDレコードの `directoryRecords` (中央ディレクトリ内のエントリ数)、`directorySize` (中央ディレクトリのサイズ)、`directoryOffset` (中央ディレクトリの開始オフセット) のいずれかが従来のZIPフォーマットの最大値 (`0xffff` または `0xffffffff`) と一致する場合、ZIP64拡張が使用されている可能性を考慮し、`findDirectory64End` 関数を呼び出してZIP64中央ディレクトリロケーターを探しに行きます。

問題は、EOCDレコードの後に続くコメントデータが、偶然にもZIP64ロケーターのシグネチャ (`0x07064b50`) と一致するバイト列を含んでいた場合に発生しました。`findDirectory64End` 関数は、このシグネチャを見つけると、それが本物のZIP64ロケーターであると判断し、その後のデータからZIP64中央ディレクトリのオフセットを読み取ろうとします。しかし、実際にはそれはコメントデータの一部であるため、読み取られたオフセットは無効な値となり、結果としてファイル終端を超えた読み込みを試みて「unexpected EOF」エラーを引き起こしていました。

このコミットでは、`findDirectory64End` 関数に以下の追加チェックが導入されました。これは `minizip` ライブラリの堅牢な実装を参考にしています。

1.  **ディスク番号のチェック**: ZIP64中央ディレクトリロケーターのシグネチャの直後には、「ZIP64中央ディレクトリの開始ディスク番号」が格納されます。通常の単一ディスクZIPファイルの場合、この値は `0` であるべきです。コミットでは、この値が `0` でない場合、それが有効なZIP64ロケーターではないと判断し、`-1` を返して処理を中断します。
2.  **ディスク総数のチェック**: ZIP64中央ディレクトリロケーターのオフセット情報の後には、「ディスク総数」が格納されます。通常の単一ディスクZIPファイルの場合、この値は `1` であるべきです。コミットでは、この値が `1` でない場合も、有効なZIP64ロケーターではないと判断し、`-1` を返して処理を中断します。

これらの追加チェックにより、コメントデータが偶然ZIP64ロケーターのシグネチャを含んでいても、その後のフィールド値がZIP64の仕様に合致しないため、誤ってZIP64ロケーターとして解釈されることがなくなりました。これにより、`archive/zip` パッケージはより堅牢になり、不正なZIP64ロケーターの誤検出を防ぎ、正しいEOCDレコードに基づいてアーカイブを読み込むことができるようになりました。

## コアとなるコードの解説

### `src/archive/zip/reader.go` の変更点

1.  **`readDirectoryEnd` 関数**:
    *   変更前は、`findDirectory64End` の呼び出しが常に実行されていました。
    *   変更後、`d.directoryRecords == 0xffff || d.directorySize == 0xffff || d.directoryOffset == 0xffffffff` という条件が追加されました。これは、EOCDレコード内のフィールドが従来のZIPフォーマットの最大値を示している場合にのみ、ZIP64中央ディレクトリロケーターを探しに行くようにするものです。これにより、ZIP64拡張が使用されていない通常のZIPファイルで、コメントが偶然ZIP64ロケーターのシグネチャを含んでいても、無駄な検索や誤検出を防ぎます。

2.  **`findDirectory64End` 関数**:
    *   変更前は、ZIP64ロケーターのシグネチャ (`directory64LocSignature`) を確認した後、ディスク番号のフィールドをスキップし、直接オフセットを読み取っていました。
    *   変更後、以下の2つの追加チェックが導入されました。
        *   `if b.uint32() != 0`: シグネチャの直後の4バイト（ディスク番号）が `0` でない場合、それは有効なZIP64ロケーターではないと判断し、`-1` を返します。これは、単一ディスクのZIPファイルではこの値が `0` であるべきという仕様に基づいています。
        *   `if b.uint32() != 1`: ZIP64中央ディレクトリのオフセットの直後の4バイト（ディスク総数）が `1` でない場合、それも有効なZIP64ロケーターではないと判断し、`-1` を返します。これも、単一ディスクのZIPファイルではこの値が `1` であるべきという仕様に基づいています。

これらの変更により、`findDirectory64End` はより厳密なチェックを行うようになり、コメントデータのような無関係なバイト列が偶然ZIP64ロケーターのシグネチャを含んでいても、その後のフィールド値がZIP64の仕様に合致しないため、誤ってZIP64ロケーターとして解釈されることがなくなりました。

### `src/archive/zip/reader_test.go` の変更点

*   `TestIssue12449` という新しいテストケースが追加されました。
*   このテストケースは、ZIP64ロケーターのシグネチャとそれに続くデータが、通常のZIPアーカイブのコメントとして存在するような特定のバイト列 (`data`) を持つZIPファイルを模擬的に作成します。
*   `NewReader` を使ってこの模擬ZIPファイルを読み込み、エラーが発生しないことを検証します。もしエラーが発生した場合、テストは失敗し、バグが修正されていないことを示します。このテストは、コメントが誤ってZIP64ロケーターとして解釈されないことを保証します。

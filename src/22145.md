# [インデックス 22145] ファイルの概要

このコミットは、Goランタイムのメモリ管理におけるLinuxカーネルとの相互作用を改善することを目的としています。具体的には、Goランタイムがカーネルに返却したメモリページが、LinuxのTransparent Huge Pages (THP) 機能によって意図せず再割り当てされる問題を解決します。

## 変更の背景

このコミットは、GoランタイムがLinuxシステム上でメモリを管理する際に直面していた特定の問題に対処するために導入されました。Goランタイムは、不要になったメモリページをカーネルに返却するために `madvise(..., MADV_DONTNEED)` システムコールを使用します。これは、これらのページがアプリケーションによってすぐに必要とされないことをカーネルに伝え、カーネルがそれらを解放したり、スワップアウトしたりする機会を与えるものです。

しかし、LinuxカーネルのTransparent Huge Pages (THP) 機能と、それに関連する `khugepaged` デーモンが、この `MADV_DONTNEED` の意図を妨害する挙動を示すことが判明しました。具体的には、`khugepaged` は、部分的にマップされた領域や `MADV_DONTNEED` でマークされた領域であっても、それらを巨大ページ（huge page）に統合しようとします。この統合プロセスは、Goランタイムが「もう必要ない」とマークしたメモリに対して、物理メモリを不必要に再割り当てしてしまうという問題を引き起こしていました。

この問題は、Linuxカーネルのバグとして報告されており（Bugzilla #93111）、Goランタイムのメモリフットプリントが、`MADV_DONTNEED` を使用してメモリを解放した後でも、期待通りに減少せず、むしろ元のサイズに「ゆっくりと戻ってしまう」という形で現れていました。これは、特に長時間稼働するGoアプリケーションや、メモリ使用量が変動するアプリケーションにおいて、メモリ効率の低下や不必要なメモリ消費につながる可能性がありました。

このコミットは、このカーネルの挙動を回避し、Goランタイムがカーネルに返却したメモリが巨大ページに再割り当てされるのを防ぐための対策を導入します。

## 前提知識の解説

### 仮想メモリと物理メモリ

コンピュータのメモリは、アプリケーションから見える「仮想メモリ」と、実際にハードウェアに存在する「物理メモリ」に分かれています。オペレーティングシステム（OS）は、仮想メモリと物理メモリのマッピングを管理し、アプリケーションが物理メモリの具体的なアドレスを意識することなくメモリを使用できるようにします。メモリは通常、ページと呼ばれる固定サイズのブロックに分割されて管理されます（例: 4KB）。

### `madvise` システムコールと `MADV_DONTNEED`

`madvise` (memory advise) は、アプリケーションがカーネルに対して、特定のメモリ領域の使用パターンに関する「助言」を与えるためのシステムコールです。これにより、カーネルはメモリ管理の最適化を行うことができます。

`MADV_DONTNEED` は `madvise` のフラグの一つで、指定されたメモリ領域の内容がアプリケーションによってもう必要とされないことをカーネルに伝えます。カーネルは、この助言に基づいて、そのメモリ領域に対応する物理ページを解放したり、スワップアウトしたりすることができます。これにより、システム全体のメモリ効率が向上し、他のプロセスがそのメモリを利用できるようになります。ただし、`MADV_DONTNEED` はあくまで「助言」であり、カーネルがすぐにメモリを解放することを保証するものではありません。

### Transparent Huge Pages (THP) と `khugepaged`

Linuxカーネルには、Transparent Huge Pages (THP) と呼ばれる機能があります。これは、通常の4KBのページよりも大きなページ（例: 2MBや1GB）を透過的に使用することで、メモリ管理のオーバーヘッドを削減し、TLB（Translation Lookaside Buffer）ミスを減らすことで、大規模なメモリを使用するアプリケーションのパフォーマンスを向上させることを目的としています。

THPは「透過的」であり、アプリケーションは通常、巨大ページが使用されていることを意識しません。カーネルの `khugepaged` デーモンは、バックグラウンドで動作し、通常の小さなページを巨大ページに統合しようとします。これは、メモリの連続性を高め、メモリ管理ユニット（MMU）の効率を向上させるために行われます。

### `MADV_NOHUGEPAGE` と `MADV_HUGEPAGE`

`MADV_NOHUGEPAGE` は、特定のメモリ領域に対してTHPの使用を無効にするための `madvise` フラグです。このフラグが設定された領域は、`khugepaged` デーモンによって巨大ページに統合されなくなります。

`MADV_HUGEPAGE` はその逆で、特定のメモリ領域に対してTHPの使用を明示的に有効にするためのフラグです。

### Linuxカーネルバグ #93111

このコミットの直接的な原因となったのは、Linuxカーネルのバグ #93111です。このバグは、`MADV_DONTNEED` でマークされたページが、`khugepaged` デーモンによって巨大ページに統合され、結果として物理メモリが再割り当てされてしまうという問題を示していました。Goランタイムがメモリを解放したつもりでも、カーネルがそれを巨大ページとして再利用しようとするため、メモリフットプリントが期待通りに減少しないという挙動が発生していました。

## 技術的詳細

このコミットの技術的な解決策は、Goランタイムがメモリをカーネルに返却する際に、`MADV_DONTNEED` に加えて `MADV_NOHUGEPAGE` フラグも使用することです。

Goランタイムは、`sysUnused` 関数を通じて、不要になったメモリ領域をカーネルに返却します。この関数内で、まず `madvise(v, n, _MADV_NOHUGEPAGE)` を呼び出すことで、対象のメモリ領域が巨大ページに統合されないようにマークします。その後、既存の `madvise(v, n, _MADV_DONTNEED)` を呼び出し、メモリが不要であることをカーネルに伝えます。

これにより、`khugepaged` デーモンが `MADV_DONTNEED` でマークされたメモリを巨大ページに再割り当てしようとするのを防ぎ、Goランタイムが意図した通りにメモリフットプリントを削減できるようになります。

また、Goランタイムが以前に返却したメモリを再利用する際には、`sysUsed` 関数が呼び出されます。この関数では、`MADV_NOHUGEPAGE` のマークを元に戻すために `madvise(v, n, _MADV_HUGEPAGE)` を呼び出します。これにより、Goランタイムが再び使用するメモリ領域では、必要に応じてTHPの恩恵を受けられるようにします。この `MADV_HUGEPAGE` の呼び出しは、アライメントチェックなしで行われます。これは、メモリ領域が結合されている可能性があるためです。

この変更は、主にLinuxシステム上の `386`, `amd64`, `amd64p32` アーキテクチャで問題が確認されていましたが、将来的に他のOS/アーキテクチャの組み合わせでも同様の問題が発生する可能性を考慮しています。

**`src/runtime/mem_linux.go` の変更:**

```diff
--- a/src/runtime/mem_linux.go
+++ b/src/runtime/mem_linux.go
@@ -67,10 +67,29 @@ func sysAlloc(n uintptr, stat *uint64) unsafe.Pointer {
 }
 
 func sysUnused(v unsafe.Pointer, n uintptr) {
+	if hugePageSize != 0 && (uintptr(v)%hugePageSize != 0 || n%hugePageSize != 0) {
+		// See issue 8832
+		// Linux kernel bug: https://bugzilla.kernel.org/show_bug.cgi?id=93111
+		// Mark the region as NOHUGEPAGE so the kernel's khugepaged
+		// doesn't undo our DONTNEED request.  khugepaged likes to migrate
+		// regions which are only partially mapped to huge pages, including
+		// regions with some DONTNEED marks.  That needlessly allocates physical
+		// memory for our DONTNEED regions.
+		madvise(v, n, _MADV_NOHUGEPAGE)
+	}
 	madvise(v, n, _MADV_DONTNEED)
 }
 
 func sysUsed(v unsafe.Pointer, n uintptr) {
+	if hugePageSize != 0 {
+		// Undo the NOHUGEPAGE marks from sysUnused.  There is no alignment check
+		// around this call as spans may have been merged in the interim.
+		// Note that this might enable huge pages for regions which were
+		// previously disabled.  Unfortunately there is no easy way to detect
+		// what the previous state was, and in any case we probably want huge
+		// pages to back our heap if the kernel can arrange that.
+		madvise(v, n, _MADV_HUGEPAGE)
+	}
```

## コアとなるコードの解説

### `sysUnused` 関数の変更

`sysUnused` 関数は、Goランタイムがメモリ領域を「未使用」としてマークし、カーネルに返却する際に呼び出されます。

```go
func sysUnused(v unsafe.Pointer, n uintptr) {
	if hugePageSize != 0 && (uintptr(v)%hugePageSize != 0 || n%hugePageSize != 0) {
		// ... (コメント) ...
		madvise(v, n, _MADV_NOHUGEPAGE)
	}
	madvise(v, n, _MADV_DONTNEED)
}
```

*   `if hugePageSize != 0 && (uintptr(v)%hugePageSize != 0 || n%hugePageSize != 0)`: この条件は、現在のアーキテクチャで巨大ページがサポートされており (`hugePageSize != 0`)、かつ、対象のメモリ領域 `v` が巨大ページの境界にアライメントされていないか、またはそのサイズ `n` が巨大ページの倍数でない場合に真となります。この条件は、Linuxカーネルバグ #93111で説明されているように、`khugepaged` が部分的にマップされた領域やアライメントされていない領域を巨大ページに統合しようとする問題に対処するためのものです。
*   `madvise(v, n, _MADV_NOHUGEPAGE)`: 上記の条件が満たされた場合、この行が実行され、対象のメモリ領域 `v` から `n` バイトの範囲が `_MADV_NOHUGEPAGE` フラグでマークされます。これにより、`khugepaged` デーモンがこの領域を巨大ページに統合するのを防ぎます。
*   `madvise(v, n, _MADV_DONTNEED)`: その後、既存の `_MADV_DONTNEED` フラグが適用されます。これは、このメモリ領域がアプリケーションによってもう必要とされないことをカーネルに伝えます。

この変更により、Goランタイムがメモリを解放する際に、そのメモリがTHPによって不必要に再割り当てされるのを防ぎ、メモリフットプリントの削減をより効果的に行えるようになります。

### `sysUsed` 関数の変更

`sysUsed` 関数は、Goランタイムが以前に解放したメモリ領域を再び使用する際に呼び出されます。

```go
func sysUsed(v unsafe.Pointer, n uintptr) {
	if hugePageSize != 0 {
		// ... (コメント) ...
		madvise(v, n, _MADV_HUGEPAGE)
	}
}
```

*   `if hugePageSize != 0`: この条件は、現在のアーキテクチャで巨大ページがサポートされている場合に真となります。
*   `madvise(v, n, _MADV_HUGEPAGE)`: この行は、対象のメモリ領域 `v` から `n` バイトの範囲を `_MADV_HUGEPAGE` フラグでマークします。これは、`sysUnused` で設定された `_MADV_NOHUGEPAGE` フラグを元に戻す効果があります。これにより、Goランタイムが再び使用するメモリ領域では、必要に応じてカーネルが巨大ページを割り当てられるようになります。コメントにもあるように、この呼び出しにはアライメントチェックがありません。これは、メモリ領域が結合されている可能性があるためです。Goランタイムは、ヒープのバックエンドとして巨大ページが使用されることを望んでいるため、このフラグを積極的に設定します。

### `hugePageSize` 定数

`src/runtime/arch1_*.go` ファイルに追加された `hugePageSize` 定数は、各アーキテクチャにおける巨大ページのサイズをバイト単位で定義します。例えば、`amd64` では `1 << 21` (2MB) となります。この定数は、`sysUnused` および `sysUsed` 関数内で、巨大ページ関連の処理を行うかどうかの判断や、アライメントチェックに使用されます。`0` に設定されているアーキテクチャでは、巨大ページ関連の処理はスキップされます。

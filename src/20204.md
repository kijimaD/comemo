## 変更の背景
このコミットは、GoランタイムのCPUプロファイリングメカニズムのリファクタリングを目的としています。主な目的は、プロファイリング中に発生するクリティカルセクションの期間を短縮し、`pcbuf`（プログラムカウンタバッファ）を関数ローカルにすることです。

CPUプロファイリングは、プログラムがCPU時間をどこで消費しているかを特定するために不可欠なツールです。Goランタイムは、`SIGPROF`シグナル（Unix系システムの場合）などのOSのプロファイリング機能を利用して、定期的に実行中のゴルーチンのスタックトレースをサンプリングします。このサンプリング処理は、通常、シグナルハンドラ内で実行されます。

シグナルハンドラは非同期に呼び出されるため、その中で実行されるコードは非常に注意深く設計される必要があります。特に、グローバルなデータ構造へのアクセスやロックの取得は、デッドロックや競合状態を引き起こす可能性があるため、最小限に抑えるべきです。

このコミット以前は、`prof.lock`というグローバルなロックが、プロファイリングデータの収集と処理の一部を保護するために使用されていました。また、スタックトレースを保存するためのバッファである`prof.pcbuf`もグローバルな構造体の一部でした。これらのグローバルなリソースへのアクセスは、プロファイリングのオーバーヘッドを増加させ、特に高負荷なシステムや多数のプロファイリングイベントが発生する状況では、パフォーマンスのボトルネックとなる可能性がありました。

クリティカルセクションの期間を短縮し、`pcbuf`を関数ローカルにすることで、以下の利点が期待されます。
1.  **パフォーマンスの向上**: ロックの保持時間が短縮され、グローバルなデータ構造への競合が減少するため、プロファイリング自体のオーバーヘッドが低減されます。
2.  **並行性の改善**: ロックの粒度が細かくなることで、他のランタイム操作との競合が緩和され、全体的なシステムのスループットが向上する可能性があります。
3.  **コードの堅牢性**: グローバルな状態を減らし、関数ローカルな変数を使用することで、コードの理解と保守が容易になり、潜在的なバグのリスクが低減されます。

## 前提知識の解説

### CPUプロファイリング
CPUプロファイリングは、プログラムの実行中にCPUがどのコードパスで時間を費やしているかを測定する手法です。これにより、パフォーマンスのボトルネックを特定し、最適化の対象となる領域を特定できます。Goでは、`pprof`ツールと連携してCPUプロファイリングが提供されており、`go tool pprof`コマンドでプロファイルデータを分析できます。

### `SIGPROF`シグナル
Unix系OSにおいて、`SIGPROF`はプロファイリングタイマーが期限切れになったときにプロセスに送信されるシグナルです。Goランタイムはこれを利用して、定期的に実行中のゴルーチンのスタックトレースをサンプリングし、CPU使用状況を記録します。

### クリティカルセクション
クリティカルセクションとは、複数のスレッドやゴルーチンから同時にアクセスされる可能性のある共有リソース（データ構造など）を操作するコードの領域を指します。競合状態を防ぐために、クリティカルセクションへのアクセスは通常、ミューテックス（ロック）などの同期プリミティブによって保護されます。ロックの保持時間が長いほど、他のスレッドやゴルーチンが共有リソースにアクセスするのを待機する時間が増え、並行性が低下します。

### `runtime`パッケージ
`runtime`パッケージは、Goプログラムの実行環境を提供するGo言語のコア部分です。ガベージコレクション、スケジューラ、メモリ管理、プロファイリングなど、低レベルの機能が含まれています。`src/pkg/runtime/proc.c`は、GoランタイムのC言語部分であり、プロセスの管理やシグナルハンドリングなど、OSとのインタラクションを扱うコードが含まれています。

### `runtime·sigprof`
`runtime·sigprof`は、`SIGPROF`シグナルが受信されたときにGoランタイムによって呼び出されるシグナルハンドラ関数です。この関数は、現在のゴルーチンのスタックトレースを収集し、プロファイリングデータとして記録する役割を担います。

### `runtime·gentraceback`
`runtime·gentraceback`は、指定されたプログラムカウンタ（PC）、スタックポインタ（SP）、リンクレジスタ（LR）からスタックトレースを生成するランタイム関数です。プロファイリング中にゴルーチンの呼び出しスタックを特定するために使用されます。

### `Lock` (Goランタイムのロック)
Goランタイム内部では、`runtime/internal/atomic`パッケージや`runtime`パッケージ内の低レベルな同期プリミティブを使用して、共有データ構造へのアクセスを保護しています。`prof.lock`は、プロファイリング関連の共有データへのアクセスを同期するためのミューテックスです。

### `pcbuf` (Program Counter Buffer)
`pcbuf`は、スタックトレースを構成するプログラムカウンタ（関数のアドレス）のリストを一時的に保持するためのバッファです。このバッファにスタックフレームのアドレスが格納され、後でシンボル解決されて人間が読める形式のスタックトレースに変換されます。

## 技術的詳細

このコミットの技術的な核心は、CPUプロファイリングのシグナルハンドラである`runtime·sigprof`関数内での`prof.lock`の利用方法と`pcbuf`のスコープの変更にあります。

**変更前**:
`prof`構造体は、プロファイリングに関連するグローバルな状態を保持していました。
```c
static struct {
    Lock lock;
    void (*fn)(uintptr*, int32);
    int32 hz;
    uintptr pcbuf[100]; // グローバルなpcbuf
} prof;
```
`runtime·sigprof`関数内で、スタックトレースの収集と`prof.fn`（プロファイリングデータを処理するコールバック関数）の呼び出しの**両方**が`prof.lock`によって保護されていました。
```c
runtime·lock(&prof.lock); // ロックの取得
if(prof.fn == nil) {
    runtime·unlock(&prof.lock);
    mp->mallocing--;
    return;
}
// ... スタックトレースの収集 (prof.pcbufを使用) ...
prof.fn(prof.pcbuf, n); // コールバック関数の呼び出し
runtime·unlock(&prof.lock); // ロックの解放
```
このアプローチでは、スタックトレースの収集（`runtime·gentraceback`の呼び出し）という比較的時間がかかる処理がクリティカルセクション内で行われていました。また、`prof.pcbuf`はグローバルなバッファであるため、複数のプロファイリングイベントが同時に発生した場合に競合が発生する可能性がありました。

**変更後**:
このコミットでは、`prof.pcbuf`が`runtime·sigprof`関数内のローカル変数`stk`に置き換えられました。
```c
byte m;
uintptr stk[100]; // 関数ローカルなstk
```
そして、`prof.lock`の取得と解放のロジックが変更され、`prof.fn`の呼び出しのみを保護するように移動されました。
```c
// ... スタックトレースの収集 (stkを使用) ...

if(prof.fn != nil) { // prof.fnが設定されている場合のみロックを取得
    runtime·lock(&prof.lock);
    if(prof.fn != nil) // ロック取得後にもう一度nilチェック
        prof.fn(stk, n);
    runtime·unlock(&prof.lock);
}
```
この変更により、スタックトレースの収集処理はクリティカルセクションの外で行われるようになりました。`prof.lock`は、`prof.fn`が設定されているかどうかのチェックと、実際に`prof.fn`を呼び出す部分のみを保護します。これにより、ロックの保持時間が大幅に短縮されます。

また、`pcbuf`がグローバルな`prof.pcbuf`から関数ローカルな`stk`に変わったことで、プロファイリングイベントごとに独立したバッファが使用されるようになり、バッファへの競合が完全に排除されます。これは、特に複数のM（OSスレッド）が同時にプロファイリングシグナルを受信する可能性がある場合に重要です。

このリファクタリングは、GoランタイムのCPUプロファイラが、より効率的かつ低オーバーヘッドで動作するようにするための重要な改善です。シグナルハンドラのような時間制約のあるコンテキストでは、ロックの粒度とクリティカルセクションの期間を最小限に抑えることが、システムの安定性とパフォーマンスを維持するために不可欠です。

## 前提知識の解説

### CPUプロファイリング
CPUプロファイリングは、プログラムの実行中にCPUがどのコードパスで時間を費やしているかを測定する手法です。これにより、パフォーマンスのボトルネックを特定し、最適化の対象となる領域を特定できます。Goでは、`pprof`ツールと連携してCPUプロファイリングが提供されており、`go tool pprof`コマンドでプロファイルデータを分析できます。

### `SIGPROF`シグナル
Unix系OSにおいて、`SIGPROF`はプロファイリングタイマーが期限切れになったときにプロセスに送信されるシグナルです。Goランタイムはこれを利用して、定期的に実行中のゴルーチンのスタックトレースをサンプリングし、CPU使用状況を記録します。

### クリティカルセクション
クリティカルセクションとは、複数のスレッドやゴルーチンから同時にアクセスされる可能性のある共有リソース（データ構造など）を操作するコードの領域を指します。競合状態を防ぐために、クリティカルセクションへのアクセスは通常、ミューテックス（ロック）などの同期プリミティブによって保護されます。ロックの保持時間が長いほど、他のスレッドやゴルーチンが共有リソースにアクセスするのを待機する時間が増え、並行性が低下します。

### `runtime`パッケージ
`runtime`パッケージは、Goプログラムの実行環境を提供するGo言語のコア部分です。ガベージコレクション、スケジューラ、メモリ管理、プロファイリングなど、低レベルの機能が含まれています。`src/pkg/runtime/proc.c`は、GoランタイムのC言語部分であり、プロセスの管理やシグナルハンドリングなど、OSとのインタラクションを扱うコードが含まれています。

### `runtime·sigprof`
`runtime·sigprof`は、`SIGPROF`シグナルが受信されたときにGoランタイムによって呼び出されるシグナルハンドラ関数です。この関数は、現在のゴルーチンのスタックトレースを収集し、プロファイリングデータとして記録する役割を担っています。

### `runtime·gentraceback`
`runtime·gentraceback`は、指定されたプログラムカウンタ（PC）、スタックポインタ（SP）、リンクレジスタ（LR）からスタックトレースを生成するランタイム関数です。プロファイリング中にゴルーチンの呼び出しスタックを特定するために使用されます。

### `Lock` (Goランタイムのロック)
Goランタイム内部では、`runtime/internal/atomic`パッケージや`runtime`パッケージ内の低レベルな同期プリミティブを使用して、共有データ構造へのアクセスを保護しています。`prof.lock`は、プロファイリング関連の共有データへのアクセスを同期するためのミューテックスです。

### `pcbuf` (Program Counter Buffer)
`pcbuf`は、スタックトレースを構成するプログラムカウンタ（関数のアドレス）のリストを一時的に保持するためのバッファです。このバッファにスタックフレームのアドレスが格納され、後でシンボル解決されて人間が読める形式のスタックトレースに変換されます。

## 技術的詳細

このコミットの技術的な核心は、CPUプロファイリングのシグナルハンドラである`runtime·sigprof`関数内での`prof.lock`の利用方法と`pcbuf`のスコープの変更にあります。

**変更前**:
`prof`構造体は、プロファイリングに関連するグローバルな状態を保持していました。
```c
static struct {
    Lock lock;
    void (*fn)(uintptr*, int32);
    int32 hz;
    uintptr pcbuf[100]; // グローバルなpcbuf
} prof;
```
`runtime·sigprof`関数内で、スタックトレースの収集と`prof.fn`（プロファイリングデータを処理するコールバック関数）の呼び出しの**両方**が`prof.lock`によって保護されていました。
```c
runtime·lock(&prof.lock); // ロックの取得
if(prof.fn == nil) {
    runtime·unlock(&prof.lock);
    mp->mallocing--;
    return;
}
// ... スタックトレースの収集 (prof.pcbufを使用) ...
prof.fn(prof.pcbuf, n); // コールバック関数の呼び出し
runtime·unlock(&prof.lock); // ロックの解放
```
このアプローチでは、スタックトレースの収集（`runtime·gentraceback`の呼び出し）という比較的時間がかかる処理がクリティカルセクション内で行われていました。また、`prof.pcbuf`はグローバルなバッファであるため、複数のプロファイリングイベントが同時に発生した場合に競合が発生する可能性がありました。

**変更後**:
このコミットでは、`prof.pcbuf`が`runtime·sigprof`関数内のローカル変数`stk`に置き換えられました。
```c
byte m;
uintptr stk[100]; // 関数ローカルなstk
```
そして、`prof.lock`の取得と解放のロジックが変更され、`prof.fn`の呼び出しのみを保護するように移動されました。
```c
// ... スタックトレースの収集 (stkを使用) ...

if(prof.fn != nil) { // prof.fnが設定されている場合のみロックを取得
    runtime·lock(&prof.lock);
    if(prof.fn != nil) // ロック取得後にもう一度nilチェック
        prof.fn(stk, n);
    runtime·unlock(&prof.lock);
}
```
この変更により、スタックトレースの収集処理はクリティカルセクションの外で行われるようになりました。`prof.lock`は、`prof.fn`が設定されているかどうかのチェックと、実際に`prof.fn`を呼び出す部分のみを保護します。これにより、ロックの保持時間が大幅に短縮されます。

また、`pcbuf`がグローバルな`prof.pcbuf`から関数ローカルな`stk`に変わったことで、プロファイリングイベントごとに独立したバッファが使用されるようになり、バッファへの競合が完全に排除されます。これは、特に複数のM（OSスレッド）が同時にプロファイリングシグナルを受信する可能性がある場合に重要です。

このリファクタリングは、GoランタイムのCPUプロファイラが、より効率的かつ低オーバーヘッドで動作するようにするための重要な改善です。シグナルハンドラのような時間制約のあるコンテキストでは、ロックの粒度とクリティカルセクションの期間を最小限に抑えることが、システムの安定性とパフォーマンスを維持するために不可欠です。

## コアとなるコードの解説

1.  **`prof`構造体からの`pcbuf`の削除**:
    *   `static struct prof`定義から`uintptr pcbuf[100];`が削除されました。これは、`pcbuf`がグローバルな共有リソースではなくなることを意味します。
    *   **影響**: これにより、プロファイリング中に複数のM（OSスレッド）が同時にスタックトレースを収集しようとした際の競合が解消されます。各プロファイリングイベントは独自のスタックバッファを使用できるようになります。

2.  **`runtime·sigprof`関数内での`stk`ローカル変数の導入**:
    *   `runtime·sigprof`関数の冒頭に`uintptr stk[100];`が追加されました。これは、スタックトレースを一時的に保持するための関数ローカルなバッファです。
    *   **影響**: `pcbuf`が関数ローカルになったことで、スタックトレースの収集処理がグローバルなロックに依存しなくなります。これにより、クリティカルセクションの外部でスタックトレースを安全に収集できるようになります。

3.  **`runtime·gentraceback`の引数変更**:
    *   `runtime·gentraceback`の呼び出しにおいて、`prof.pcbuf`の代わりに新しく導入されたローカル変数`stk`が渡されるようになりました。これは、スタックトレースの収集がローカルバッファに対して行われることを意味します。
    *   **影響**: スタックトレースの収集処理がロックの保護下から外れ、クリティカルセクションの期間が短縮されます。

4.  **`prof.lock`の取得と解放ロジックの変更**:
    *   変更前は、`runtime·sigprof`関数の早い段階で`prof.lock`が取得され、スタックトレースの収集処理全体を保護していました。
    *   変更後は、`prof.lock`の取得と解放が、`prof.fn`（プロファイリングデータを処理するコールバック関数）の呼び出しを囲むように移動されました。さらに、`prof.fn`が`nil`でない場合にのみロックを取得するようになりました。
    *   **影響**: これが最も重要な変更点です。ロックの保持時間が大幅に短縮され、クリティカルセクションの粒度が細かくなりました。スタックトレースの収集という比較的重い処理がロックの外で行われるため、プロファイリング中のランタイムの並行性が向上し、オーバーヘッドが減少します。`prof.fn`が`nil`でないかどうかのチェックをロックの内外で行うことで、`prof.fn`がプロファイリング中に動的に設定解除される可能性にも対応しています。

これらの変更は、GoランタイムのCPUプロファイラが、より効率的かつ低オーバーヘッドで動作するようにするための重要な改善です。シグナルハンドラのような時間制約のあるコンテキストでは、ロックの粒度とクリティカルセクションの期間を最小限に抑えることが、システムの安定性とパフォーマンスを維持するために不可欠です。

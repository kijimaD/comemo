# [インデックス 22101] ファイルの概要

このコミットは、Go言語のコンパイラとアセンブラのC言語実装を削除し、Go言語で書かれた新しい実装に完全に置き換えるという、Goプロジェクトにおける歴史的かつ極めて重要な変更を記録しています。これは、Goが「自己ホスト型（self-hosting）」言語となるための大きな一歩であり、Goツールチェインの将来の発展において重要なマイルストーンとなりました。

## 元コミット内容

このコミットは、`dev.cc`ブランチ（コミットハッシュ`a91c2e0`）を`master`ブランチにマージしたものです。このマージの主要な目的は、GoコンパイラとアセンブラのC言語で書かれた既存の実装を、Go言語で書かれた新しい実装に置き換えることでした。

コミットメッセージには、この変更によってC言語実装が`master`ブランチから削除されることが明記されています。また、現時点ではGo言語実装がC言語実装よりも若干遅いことが述べられています。この性能低下の主な原因は、C言語コードの特性上、スタック変数からアドレスを取得する際に発生する大量のガベージ（一時的なオブジェクト）であると説明されています。しかし、この問題は今後数週間で機械的にクリーンアップされ、性能が改善される見込みであることも言及されています。

## 変更の背景

Go言語は、その初期から「自己ホスト型」となることを目標の一つとしていました。自己ホスト型とは、その言語自身でコンパイラやツールチェインを記述できることを意味します。Goの初期のコンパイラとアセンブラは、既存のツールチェイン（C言語とPlan 9のツール）を利用してC言語で書かれていました。これは、Go言語がまだ十分に成熟しておらず、自身のコンパイラを記述するのに必要な機能が揃っていなかったためです。

しかし、Go言語が進化し、その表現力と性能が向上するにつれて、Go自身でGoのコンパイラとアセンブラを記述することが現実的になりました。この移行にはいくつかの大きな利点があります。

1.  **開発の効率化と統一性**: コンパイラとアセンブラがGoで書かれることで、Go言語の開発者はGo言語の知識だけでツールチェイン全体を理解し、貢献できるようになります。C言語とGo言語という異なる言語を扱う必要がなくなり、開発プロセスが簡素化されます。
2.  **ブートストラップ問題の解消**: GoコンパイラをGo自身でコンパイルできるようになるため、Goの新しいバージョンをリリースする際に、古いGoコンパイラやCコンパイラに依存する必要がなくなります。これにより、Goの配布とビルドがより容易になります。
3.  **Go言語の機能活用**: Go言語の並行処理、ガベージコレクション、型安全性などの機能をコンパイラ開発に活用できるようになります。これにより、より堅牢で保守しやすいコンパイラを構築できる可能性があります。
4.  **性能改善の可能性**: 長期的には、Go言語の最適化技術をコンパイラ自身に適用することで、コンパイラの性能をさらに向上させることが期待されます。

このコミットは、Go 1.5リリースに向けた重要なステップであり、Go言語の歴史における大きな節目となりました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識があると役立ちます。

*   **コンパイラとアセンブラ**:
    *   **コンパイラ**: ソースコード（この場合はGo言語）を、コンピュータが直接実行できる機械語や中間コードに変換するプログラムです。
    *   **アセンブラ**: アセンブリ言語（機械語と1対1に対応する低レベル言語）を機械語に変換するプログラムです。Goのツールチェインでは、Go言語で書かれたアセンブリコード（Plan 9アセンブリに似た構文）を機械語に変換するために使用されます。
*   **自己ホスト型言語 (Self-hosting Language)**:
    *   その言語のコンパイラやランタイムが、その言語自身で書かれている言語のことです。例えば、JavaのコンパイラがJavaで書かれている場合、Javaは自己ホスト型です。自己ホスト型であることは、言語の成熟度と独立性を示す重要な指標の一つです。
*   **ブートストラップ (Bootstrap)**:
    *   新しいバージョンのコンパイラを、そのコンパイラ自身を使ってコンパイルするプロセスを指します。自己ホスト型言語では、通常、以前のバージョンのコンパイラを使って新しいバージョンのコンパイラをビルドし、その新しいコンパイラを使ってさらに新しいバージョンをビルドしていく、というブートストラップの連鎖が可能です。
*   **Goツールチェインの歴史**:
    *   Go言語の初期のコンパイラ（`5g`, `6g`, `8g`など）は、Plan 9のツールチェインをベースにしてC言語で書かれていました。これは、Go言語がまだ初期段階であり、Go自身でコンパイラを記述する準備ができていなかったためです。
    *   Go 1.4では、Go言語で書かれたコンパイラ（`go tool compile`）が導入され始めましたが、まだC言語のコンパイラが並行して存在していました。
    *   Go 1.5で、このコミットによってC言語のコンパイラが完全に削除され、Go言語で書かれたコンパイラがデフォルトとなりました。
*   **ガベージコレクション (Garbage Collection)**:
    *   プログラムが動的に確保したメモリのうち、もはや使用されていない領域を自動的に解放する仕組みです。Goはガベージコレクタを持つ言語であり、メモリ管理の多くを自動で行います。
*   **スタック変数とヒープ変数**:
    *   **スタック変数**: 関数呼び出し時にスタック上に割り当てられる一時的な変数です。関数の終了とともに自動的に解放されます。
    *   **ヒープ変数**: プログラムの実行中に動的に確保されるメモリ領域（ヒープ）に割り当てられる変数です。ガベージコレクタによって管理されるか、手動で解放される必要があります。
    *   Goでは、変数がスタックに割り当てられるかヒープに割り当てられるかは、コンパイラのエスケープ解析によって決定されます。変数が関数のスコープ外で参照される可能性がある場合（例えば、ポインタが返される場合など）、その変数はヒープに「エスケープ」されます。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラとアセンブラのコードベース全体をC言語からGo言語に書き換えるという大規模な作業の集大成です。

具体的には、以下の主要な変更が含まれています。

1.  **C言語ソースコードの削除**:
    *   `src/cmd/5a`, `src/cmd/5g`, `src/cmd/6a`, `src/cmd/6g`, `src/cmd/8a`, `src/cmd/8g`, `src/cmd/9a`, `src/cmd/9g`といったディレクトリにあった、各アーキテクチャ（ARM, x86, AMD64, PowerPC64など）向けのC言語で書かれたアセンブラ（`*a`）とコンパイラ（`*g`）のソースファイルが大量に削除されています。
    *   特に、`src/cmd/gc`ディレクトリにあったGoコンパイラのC言語実装も完全に削除されています。これには、字句解析（`lex.c`）、構文解析（`y.tab.c`）、型チェック（`typecheck.c`）、コード生成（`cgen.c`）、最適化（`peep.c`）など、コンパイラの主要なコンポーネントが含まれていました。
2.  **Go言語ソースコードの追加/移動**:
    *   削除されたC言語の機能に対応するGo言語のソースファイルが大量に追加されています。これらのファイルは、主に`src/cmd/internal/gc`、`src/cmd/internal/asm`、`src/cmd/internal/obj`などの新しいディレクトリ構造に配置されています。
    *   例えば、`src/cmd/gc/lex.c`は`src/cmd/internal/gc/lex.go`に、`src/cmd/gc/typecheck.c`は`src/cmd/internal/gc/typecheck.go`に、といった形でGo言語に移植されています。
    *   `src/cmd/internal/asm`には、Go言語で書かれた新しいアセンブラのロジックが含まれています。
    *   `src/cmd/internal/obj`には、オブジェクトファイル形式やアセンブリ命令に関する共通の定義と、各アーキテクチャ固有のコード生成ロジックがGo言語で実装されています。
3.  **ビルドシステムの変更**:
    *   `Makefile`や`src/cmd/dist`などのビルド関連ファイルが更新され、C言語コンパイラではなくGo言語コンパイラを使用するように変更されています。これにより、Goツールチェインのビルドプロセスが完全にGo言語ベースになりました。
4.  **一時的な性能低下とその原因**:
    *   コミットメッセージで言及されているように、Go言語実装への移行直後は性能が一時的に低下しました。これは、C言語で書かれたコードがGoに移植される際に、C言語の慣習（例えば、スタック変数のアドレスを頻繁に取得する）がそのままGoコードに持ち込まれたためです。
    *   Go言語では、スタック変数のアドレスが取得され、それが関数のスコープ外で利用される可能性があるとコンパイラが判断した場合、その変数はヒープに「エスケープ」されます。ヒープに割り当てられた変数はガベージコレクタの管理対象となり、頻繁なエスケープはガベージコレクションの負荷を増大させ、性能低下につながります。
    *   この問題は、Goコンパイラのエスケープ解析を改善したり、Go言語のイディオムに沿ったコードにリファクタリングしたりすることで解決されることが期待されました。コミットメッセージでは「機械的にクリーンアップされる」とあり、これは自動化されたツールやリファクタリングによって対処されることを示唆しています。

この変更は、Go言語のブートストラッププロセスを簡素化し、Goツールチェイン全体の開発と保守をGo言語のエコシステム内で完結させることを可能にしました。これは、Go言語が成熟した言語として独立性を確立する上で不可欠なステップでした。

## コアとなるコードの変更箇所

このコミットは非常に広範囲にわたる変更を含んでいますが、その核心はC言語で書かれたコンパイラとアセンブラのコードを削除し、Go言語で書かれた同等のコードに置き換えることです。

具体的な変更箇所は以下のパターンに集約されます。

*   **削除されたファイル（C言語実装）**:
    *   `src/cmd/{arch}a/*.c`, `src/cmd/{arch}a/*.h` (アセンブラのC言語ソース)
    *   `src/cmd/{arch}g/*.c`, `src/cmd/{arch}g/*.h` (コンパイラのC言語ソース)
    *   `src/cmd/gc/*.c`, `src/cmd/gc/*.h` (GoコンパイラのC言語ソース)
    *   `src/cmd/gc/y.tab.c`, `src/cmd/gc/y.tab.h` (Yaccによって生成されたC言語の構文解析器)
    *   `src/cmd/gc/lex.c` (字句解析器)
    *   `src/cmd/gc/typecheck.c` (型チェッカー)
    *   `src/cmd/gc/walk.c` (ASTウォーカー)
    *   `src/cmd/gc/cgen.c` (コードジェネレータ)
*   **追加されたファイル（Go言語実装）**:
    *   `src/cmd/internal/asm/...` (新しいGo言語アセンブラのコード)
    *   `src/cmd/internal/gc/...` (新しいGo言語コンパイラのコード)
        *   `src/cmd/internal/gc/lex.go` (字句解析器)
        *   `src/cmd/internal/gc/y.go` (Yaccによって生成されたGo言語の構文解析器)
        *   `src/cmd/internal/gc/typecheck.go` (型チェッカー)
        *   `src/cmd/internal/gc/walk.go` (ASTウォーカー)
        *   `src/cmd/internal/gc/cgen.go` (コードジェネレータ)
    *   `src/cmd/internal/obj/...` (新しいGo言語オブジェクトファイル操作およびアーキテクチャ固有のコード)
*   **ファイル名の変更（CからGoへの移植）**:
    *   `src/cmd/{arch}g/{reg.c => reg.go}` のようなパターンで、C言語のファイルがGo言語のファイルに置き換えられています。これは、単なるファイル名の変更ではなく、内容がCからGoに書き換えられたことを意味します。
*   **ビルドスクリプトの変更**:
    *   `src/make.bash`, `src/make.bat`, `src/make.rc` など、ビルドプロセスを制御するスクリプトが更新され、C言語コンパイラへの依存が削除されています。

このコミットの差分は非常に大きく、数万行のコードが削除され、同等以上のコードがGo言語で追加されています。これは、Goプロジェクトにおける単一のコミットとしては最大級の変更の一つです。

## コアとなるコードの解説

このコミットにおける「コアとなるコード」は、Go言語で再実装されたコンパイラとアセンブラの各コンポーネントです。

例えば、Goコンパイラの主要なフェーズに対応するGo言語のファイル群が挙げられます。

*   **字句解析 (Lexing)**: `src/cmd/internal/gc/lex.go`
    *   ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換する部分です。C言語版の`lex.c`の機能がGoで再実装されています。
*   **構文解析 (Parsing)**: `src/cmd/internal/gc/y.go`
    *   トークンのストリームを抽象構文木（AST）に変換する部分です。これはYacc（Goでは`go tool yacc`）によって生成されたコードであり、Go言語の文法規則に基づいてASTを構築します。C言語版の`y.tab.c`に相当します。
*   **型チェック (Type Checking)**: `src/cmd/internal/gc/typecheck.go`
    *   ASTを走査し、Go言語の型システムに従って型の整合性を検証します。変数の型、関数の引数と戻り値の型、演算子の適用可能性などをチェックします。
*   **エスケープ解析 (Escape Analysis)**: `src/cmd/internal/gc/esc.go`
    *   変数がスタックに割り当てられるべきか、それともヒープにエスケープされるべきかを決定する重要な最適化フェーズです。コミットメッセージで言及された一時的な性能低下は、このエスケープ解析がC言語のコードパターンに最適化されていなかったことに起因する可能性があります。
*   **中間表現 (IR) の生成と最適化**: `src/cmd/internal/gc/walk.go`, `src/cmd/internal/gc/order.go`, `src/cmd/internal/gc/peep.go`
    *   ASTをより低レベルの中間表現に変換し、様々な最適化（定数畳み込み、不要コード削除、インライン化など）を適用します。
*   **コード生成 (Code Generation)**: `src/cmd/internal/gc/cgen.go` および `src/cmd/internal/obj/{arch}/asm*.go`
    *   最適化された中間表現を、ターゲットアーキテクチャ（例: AMD64, ARM）の機械語命令に変換します。`src/cmd/internal/obj`以下のファイルは、各アーキテクチャ固有のアセンブリ命令の定義や、それらをオブジェクトファイルに書き出すロジックを含んでいます。

これらのGo言語で書かれた新しいコンポーネントは、C言語で書かれた古いコンポーネントと機能的に同等ですが、Go言語のイディオムとツールチェインの恩恵を受けるように設計されています。これにより、Goコンパイラ自体の開発と保守が、Go言語の知識を持つ開発者にとってよりアクセスしやすくなりました。

## 元コミット内容

`cmd/compile: correct maintain use count when phi args merge`

このコミットは、Goコンパイラの`cmd/compile`パッケージにおいて、SSA形式の「クリティカルフェーズ」中にPHI関数の引数の使用カウントが正しく維持されない問題を修正します。具体的には、新しいクリティカルブロックの2つの先行ブロックが同じ値を伝達する場合に、この問題が発生していました。

## 変更の背景

Goコンパイラは、最適化のためにプログラムをSSA（Static Single Assignment）形式に変換します。SSA形式では、各変数は一度だけ代入され、変数の定義と使用の関係が明確になります。このSSA形式において、複数の制御フローパスが合流する点（例えば`if-else`文の終わりやループの終わり）では、異なるパスから来る可能性のある値を統合するために「PHI関数」が導入されます。

「クリティカルエッジ」とは、あるブロックから別のブロックへのエッジで、そのエッジのソースブロックが複数の後続ブロックを持ち、かつそのエッジのターゲットブロックが複数の先行ブロックを持つ場合を指します。このようなクリティカルエッジが存在すると、SSA形式の変換や最適化の際に問題が生じることがあります。そのため、コンパイラは「クリティカルエッジ分割（critical edge splitting）」という処理を行い、クリティカルエッジの中間に新しいブロック（クリティカルブロック）を挿入して、これらのエッジを非クリティカルにします。

このコミットの背景にある問題は、クリティカルエッジ分割の際に、新しいクリティカルブロックの先行ブロックが同じ値をPHI関数に渡す場合、その値の使用カウントが正しく更新されないというバグでした。使用カウントは、コンパイラが不要なコードを削除する（デッドコードエリミネーション）などの最適化を行う上で非常に重要な情報です。使用カウントが誤っていると、誤った最適化が行われたり、コンパイラがクラッシュしたりする可能性があります。

## 前提知識の解説

*   **SSA (Static Single Assignment) 形式**: プログラムの各変数が一度だけ代入されるようにする中間表現。これにより、データフロー解析や最適化が容易になります。複数の定義が合流する点では、`φ`（PHI）関数が導入されます。
*   **PHI関数**: SSA形式において、複数の制御フローパスが合流するブロックで、異なるパスから来る可能性のある同じ論理変数の値を統合するために使用される仮想的な関数。例えば、`x = φ(x_prev1, x_prev2)` のように記述され、どのパスを通ってきたかに応じて適切な値を選択します。
*   **クリティカルエッジ**: グラフ理論において、あるノードから別のノードへのエッジで、そのソースノードが複数の後続ノードを持ち、かつそのターゲットノードが複数の先行ノードを持つ場合のエッジ。コンパイラの最適化において、クリティカルエッジは特定の変換を複雑にするため、通常は「クリティカルエッジ分割」によって解消されます。
*   **使用カウント (Use Count)**: ある値（変数や式の結果）がプログラム中で何回使用されているかを示すカウンタ。コンパイラはこれを利用して、使用されていない値を特定し、デッドコードエリミネーションなどの最適化を行います。

## 技術的詳細

GoコンパイラのSSAバックエンドでは、`src/cmd/compile/internal/ssa/critical.go`ファイル内でクリティカルエッジの処理が行われます。この処理では、クリティカルエッジを解消するために新しいブロックが挿入され、それに伴いPHI関数の引数も調整されます。

問題は、新しいクリティカルブロックが導入された際に、そのブロックの複数の先行ブロックが、元のPHI関数に対して同じ値を引数として提供する場合に発生しました。本来であれば、この同じ値は新しいPHI関数に引き継がれるため、元のPHI関数におけるその値の使用は1つ減るべきです。しかし、バグのある実装では、この使用カウントの減少が正しく行われていませんでした。

具体的には、`critical`関数内で、`reusedBlock`という条件が`true`の場合、つまり既存のブロックが再利用される形でクリティカルエッジが処理される際に、PHI関数の引数が`nil`に設定されていました。これは、その引数がもはや元のPHI関数によって直接使用されないことを意味しますが、その引数に対応する値の使用カウントがデクリメントされていなかったため、使用カウントが過大評価されたままになっていました。

使用カウントの過大評価は、コンパイラがその値がまだ使用されていると誤解し、実際には不要なコードや値を削除できない原因となります。これは、コンパイラの最適化効率を低下させるだけでなく、場合によっては誤ったコード生成につながる可能性もあります。

## コアとなるコードの解説

変更箇所は`critical`関数内の以下の部分です。

```go
		if reusedBlock {
			d.Preds = append(d.Preds, c)
			b.Preds[i] = nil
			phi.Args[i].Uses-- // 追加された行
			phi.Args[i] = nil
		}
```

*   `if reusedBlock { ... }`: このブロックは、クリティカルエッジ分割の際に、既存のブロックが新しいクリティカルブロックとして再利用されるケースを処理します。
*   `d.Preds = append(d.Preds, c)`: 新しいブロック`d`の先行ブロックリストに`c`を追加します。
*   `b.Preds[i] = nil`: 元のブロック`b`の`i`番目の先行ブロックを`nil`に設定します。これは、この先行ブロックがもはや`b`に直接接続されていないことを示します。
*   `phi.Args[i].Uses--`: **この行が追加された修正です。** `phi.Args[i]`は、PHI関数の`i`番目の引数に対応する値（`Value`オブジェクト）を指します。この引数が`nil`に設定される（つまり、元のPHI関数から切り離される）前に、その値の使用カウントを1つ減らしています。これにより、この値が元のPHI関数によって使用されなくなったことが正確に反映されます。
*   `phi.Args[i] = nil`: PHI関数の`i`番目の引数を`nil`に設定します。

この修正により、クリティカルエッジ分割の際にPHI関数の引数の使用カウントが正確に維持されるようになり、コンパイラのSSA最適化の正確性と堅牢性が向上しました。

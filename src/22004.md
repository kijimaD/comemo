# [インデックス 22004] ファイルの概要

このコミットは、Goコンパイラおよび関連ツールチェーンの歴史において極めて重要なマイルストーンを示しています。従来のC言語で書かれていたGoコンパイラ（`cmd/gc`、`cmd/6g`など）を、Go言語自身で書き直された新しいバージョン（`cmd/internal/gc`、`cmd/new6g`など）に変換する、その最初のドラフトを導入するものです。

この変更は、Go言語の「セルフホスティング」への大きな一歩であり、コンパイラ開発の効率化、Goエコシステムとの統合強化、そして将来的な最適化の可能性を広げることを目的としていました。コミットは、`src/cmd/internal/gc/`、`src/cmd/internal/obj/`、`src/cmd/new*g/`といった多数のファイルにわたる膨大な量のコード追加（約88,000行）と一部の削除を含んでおり、Goコンパイラの基盤を根本から刷新する大規模な作業であったことを示しています。

## 変更の背景

Go言語の初期のコンパイラは、C言語で書かれていました。これは、Go言語がまだ初期段階であり、セルフホスティング（自身の言語で自身のコンパイラを書くこと）が現実的ではなかったためです。しかし、C言語で書かれたコンパイラにはいくつかの課題がありました。

1.  **開発の複雑さ**: Go言語の機能（例: ガベージコレクション、並行処理）をC言語で実装・デバッグするのは複雑でした。
2.  **Goエコシステムとの乖離**: コンパイラがC言語であるため、Go言語のツールやライブラリを直接活用することが難しく、開発者がコンパイラの内部に貢献する際の障壁となっていました。
3.  **「犬を食う」原則 (Dogfooding)**: Go言語の設計思想の一つに、自分たちの作った言語を自分たちで使うことで、その言語の利点と欠点を深く理解するという「dogfooding」があります。コンパイラをGoで書くことは、この原則を体現するものでした。
4.  **将来的な最適化**: Go言語で書かれたコンパイラは、Go言語のランタイムやガベージコレクタの恩恵を受けることができ、将来的にはコンパイル速度の向上や、より高度な最適化をGo言語の機能を使って実装する道を開きました。

このような背景から、GoコンパイラをC言語からGo言語へ移行するプロジェクトが開始されました。このコミットは、その移行の「最初のドラフト」であり、`rsc.io/c2go`というカスタムツールがこの変換のために使用されました。

## 前提知識の解説

### Goコンパイラ（旧来の`gc`、`6g`など）

Go言語の初期のコンパイラは、Plan 9オペレーティングシステムのツールチェーンに由来するものでした。具体的には、`gc`（Go Compiler）がフロントエンドを担当し、`6g`（AMD64向け）、`8g`（386向け）、`5g`（ARM向け）といったツールがバックエンド（コード生成）を担当していました。これらはC言語で書かれており、Go言語のソースコードを各アーキテクチャの機械語に変換する役割を担っていました。

### クロスコンパイル

Go言語は、異なるCPUアーキテクチャやオペレーティングシステム向けに簡単にコンパイルできる「クロスコンパイル」を強力にサポートしています。これは、Go言語のコンパイラが、ターゲットとなるプラットフォームの特性を抽象化し、共通のフロントエンドとプラットフォーム固有のバックエンドを持つことで実現されています。

### `rsc.io/c2go`

`rsc.io/c2go`は、Go言語のコア開発者であるRuss Cox氏によって開発された、C言語のコードをGo言語のコードに変換するための特殊なツールです。これは一般的なCからGoへのトランスパイラではなく、GoコンパイラとランタイムのCコードベースをGoに移行するという特定の目的のために作られました。このツールは、C言語のポインタ演算、メモリ管理、C特有のイディオムなどをGo言語の慣用的な表現に変換するよう設計されていました。現在ではメンテナンスされておらず、歴史的な参照用としてのみ利用可能です。

### コンパイラのフェーズ

一般的なコンパイラは、複数のフェーズを経てソースコードを機械語に変換します。

1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（単語のようなもの）のストリームに分解します。
2.  **構文解析 (Syntax Analysis)**: トークンのストリームを解析し、プログラムの構造を抽象構文木（AST）として構築します。
3.  **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、名前解決、エラー検出などを行います。
4.  **中間コード生成 (Intermediate Code Generation)**: 抽象構文木から、機械語に依存しない中間表現（IR）を生成します。
5.  **最適化 (Optimization)**: 中間コードを分析し、より効率的なコードに変換します。
6.  **コード生成 (Code Generation)**: 最適化された中間コードをターゲットアーキテクチャの機械語に変換します。

GoコンパイラのCからGoへの移行は、これらのフェーズの多くに影響を与え、特にフロントエンドとバックエンドの間のインターフェースや、各フェーズの実装言語が変更されました。

## 技術的詳細

このコミットは、GoコンパイラのC言語コードをGo言語に変換するプロセスにおける最初の大きな成果です。`rsc.io/c2go`ツールは、C言語のソースコードをGo言語のソースコードに機械的に変換しました。この変換は、単なる構文の置き換えにとどまらず、C言語のポインタ、構造体、関数ポインタ、マクロといった概念を、Go言語のポインタ、構造体、インターフェース、関数リテラルといった対応する概念にマッピングする複雑な作業を含んでいました。

変換されたコードは、`src/cmd/internal/gc/`ディレクトリに配置されました。これは、コンパイラのフロントエンド（字句解析、構文解析、型チェック、中間表現の生成）と、アーキテクチャに依存しない共通の最適化フェーズをGo言語で実装したものです。また、各アーキテクチャ固有のバックエンド（コード生成）も`src/cmd/new*g/`（例: `src/cmd/new6g`、`src/cmd/new8g`、`src/cmd/new5g`、`src/cmd/new9g`）としてGo言語で書き直されました。

この移行の技術的な課題は多岐にわたります。

*   **C言語のイディオムの変換**: C言語特有のポインタ演算やメモリ管理のパターンを、Go言語の安全な型システムとガベージコレクションの枠組みに適合させる必要がありました。`c2go`は、これらのパターンをGoの慣用的なコードに変換するよう努めました。
*   **パフォーマンスの維持**: コンパイラはビルド時間を左右する重要なツールであるため、C言語版と同等かそれ以上のパフォーマンスをGo言語版で達成することが求められました。これは、変換されたコードの効率性だけでなく、Go言語ランタイム自体の最適化にも依存しました。
*   **既存のツールチェーンとの統合**: 変換されたコンパイラが、既存のGoツールチェーン（リンカ、アセンブラなど）とシームレスに連携するように設計する必要がありました。
*   **デバッグと検証**: 大規模なコードベースの言語変換は、多くの潜在的なバグや非互換性を生み出す可能性があります。厳格なテストと検証プロセスが不可欠でした。

このコミットは、これらの課題に対する最初の解決策を提示し、Goコンパイラのセルフホスティングに向けた重要な基盤を築きました。

## コアとなるコードの変更箇所

このコミットでは、主に以下のディレクトリに大量のファイルが追加・変更されています。

*   **`src/cmd/internal/gc/`**: Goコンパイラのフロントエンドおよび共通部分がGo言語で実装されたものです。
    *   `align.go`: 型のアライメントとサイズの計算に関するロジック。
    *   `array.go`: 配列に関する定義。
    *   `bits.go`: ビット操作に関するユーティリティ。
    *   `builtin.go`: ビルトイン関数の定義。
    *   `bv.go`: ビットベクトル操作。
    *   `closure.go`: クロージャ（関数リテラル）の処理に関するロジック。
    *   `const.go`: 定数に関する処理。
    *   その他、`cplx.go`, `dcl.go`, `esc.go`, `export.go`, `fmt.go`, `gen.go`, `go.go`, `go.y` (Yacc/Bisonの文法ファイル), `gsubr.go`, `init.go`, `inl.go`, `lex.go`, `md5.go`, `mparith1.go`, `mparith2.go`, `mparith3.go`, `obj.go`, `opnames.go`, `order.go`, `pgen.go`, `plive.go`, `popt.go`, `racewalk.go`, `range.go`, `reflect.go`, `reg.go`, `select.go`, `sinit.go`, `subr.go`, `swt.go`, `typecheck.go`, `unsafe.go`, `util.go`, `walk.go`, `y.go`, `y.output` など、コンパイラのほぼ全てのフロントエンドおよび中間処理のコンポーネントがGo言語で新しく追加されています。
*   **`src/cmd/internal/obj/`**: オブジェクトファイル形式やアセンブラに関する共通の定義。
    *   `ar.go`, `data.go`, `flag.go`, `fmt.go`, `go.go`, `ld.go`, `libc.go`, `link.go`, `mgc0.go`, `pcln.go`, `stack.go`, `sym.go`, `typekind.go`, `util.go` など。
    *   各アーキテクチャ固有のオブジェクト定義ファイルも含まれます（例: `arm/5.out.go`, `i386/8.out.go`, `ppc64/9.out.go`, `x86/6.out.go`）。
*   **`src/cmd/new*g/`**: 各アーキテクチャ向けの新しいGo言語ベースのバックエンド。
    *   `src/cmd/new5g/` (ARM), `src/cmd/new6g/` (AMD64), `src/cmd/new8g/` (386), `src/cmd/new9g/` (PPC64)
    *   これらのディレクトリには、`cgen.go` (コード生成), `galign.go` (アライメント), `ggen.go` (汎用コード生成), `gsubr.go` (サブルーチン), `peep.go` (ピーフホール最適化), `prog.go` (プログラム構造), `reg.go` (レジスタ割り当て), `util.go` (ユーティリティ) など、各アーキテクチャに特化したコード生成ロジックがGo言語で実装されています。

このコミットは、既存のC言語のコンパイラファイルを削除するのではなく、新しいGo言語のファイルを並行して追加する形で行われています。これは、段階的な移行と検証を可能にするための戦略であったと考えられます。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラのフロントエンドとバックエンドの大部分をC言語からGo言語に移行した点にあります。

*   **`src/cmd/internal/gc/`**: このディレクトリは、Goコンパイラの「脳」となる部分です。Go言語のソースコードを解析し、抽象構文木を構築し、型チェックを行い、Go言語のセマンティクスを適用します。また、アーキテクチャに依存しない中間表現を生成し、一部の共通最適化もここで行われます。例えば、`typecheck.go`は型チェックの主要なロジックを、`walk.go`はASTの走査と変換を担当します。`go.y`はGo言語の文法定義であり、`y.output`はその生成物です。これらのファイルがGo言語で書かれたことで、Go言語の機能（例: インターフェース、構造体、ガベージコレクション）をコンパイラ開発に直接活用できるようになりました。

*   **`src/cmd/new*g/`**: これらのディレクトリは、各ターゲットアーキテクチャ（AMD64, 386, ARM, PPC64）に特化したコード生成バックエンドです。`cmd/internal/gc`で生成された中間表現を受け取り、それを特定のCPU命令セットに変換します。例えば、`cgen.go`はC言語のコード生成器に相当するGo言語のコード生成器であり、`peep.go`は生成されたアセンブリコードに対して局所的な最適化（ピーフホール最適化）を適用します。これらのバックエンドがGo言語で書かれたことで、各アーキテクチャの特性をGo言語の表現力でより柔軟に扱うことが可能になりました。

この変更により、GoコンパイラはGo言語で書かれたGoプログラムをコンパイルできるようになり、Go言語のセルフホスティングが実現しました。これは、Go言語の成熟度を示すだけでなく、コンパイラ開発者にとっても、より親しみやすい言語でコンパイラを開発・改善できるという大きなメリットをもたらしました。

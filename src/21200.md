## 変更の背景

このコミットは、Go言語のランタイム（runtime）をC言語からGo言語自身で書き直すという、Goプロジェクトにおける長期的な大規模移行戦略の一環です。Goランタイムは、ガベージコレクション、ゴルーチンのスケジューリング、システムコールとの連携など、Goプログラムの実行を支える低レベルな機能を提供します。初期のGoランタイムは、パフォーマンスとOSとの密接な連携のためにC言語とアセンブリ言語で書かれていました。

しかし、C言語でランタイムを実装することにはいくつかの課題がありました。
1.  **ガベージコレクションの実装の複雑さ**: 正確で並行なガベージコレクタをC言語で実装することは非常に困難で、バグの温床となりがちでした。Go言語でGCを実装できれば、Goの型安全性と並行処理のプリミティブを活用でき、より堅牢で理解しやすいコードになります。
2.  **保守性と安全性**: C言語はメモリ管理をプログラマに委ねるため、メモリリークやセグメンテーション違反などのメモリ関連のバグが発生しやすいです。Go言語のメモリ安全性機能は、これらのリスクを大幅に軽減し、ランタイムの保守性を向上させます。
3.  **Go言語との一貫性**: ランタイムがGo言語で書かれていることで、Go言語の設計思想やイディオムとより一貫性を持つようになります。これにより、Go開発者にとってランタイムのコードベースがよりアクセスしやすく、理解しやすくなります。
4.  **ブートストラップの容易さ**: GoコンパイラとランタイムをGo自身でコンパイルできるようにする「セルフホスティング」の目標に近づきます。これにより、外部のCコンパイラへの依存を減らすことができます。

このコミットは、`src/runtime`ディレクトリ内のC言語ファイルをGo言語に移植する作業の「最後のファイル」であったと明記されており、この大規模な移行における重要なマイルストーンを示しています。NetBSD/ARMという特定のOS/アーキテクチャのサポートが、この移行の最終段階で完了したことを意味します。

## 前提知識の解説

### Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理するGo言語の不可欠な部分です。これには、ゴルーチン（軽量スレッド）のスケジューリング、ガベージコレクション（自動メモリ管理）、チャネル（ゴルーチン間の通信メカニズム）、システムコール（OSとの対話）、スタック管理などが含まれます。Goプログラムは、コンパイル時にランタイムとリンクされ、実行時にランタイムの機能を利用します。

### C言語からGo言語への移行
Goランタイムの初期バージョンは、パフォーマンス上の理由からC言語とアセンブリ言語で書かれた部分が多くありました。しかし、前述の通り、保守性、安全性、開発効率の観点から、これらのC言語部分をGo言語自身で書き直すという大規模なプロジェクトが進行しました。これにより、ランタイムのコードベース全体がよりGo言語のイディオムに沿ったものとなり、Go開発者にとって理解しやすくなりました。

### NetBSD/ARM
*   **NetBSD**: 非常に移植性の高いオープンソースのUnix系オペレーティングシステムです。多様なハードウェアプラットフォームで動作することを目標としています。
*   **ARM**: Advanced RISC Machinesの略で、モバイルデバイス、組み込みシステム、最近ではサーバーなど、幅広いデバイスで利用されているCPUアーキテクチャです。RISC（Reduced Instruction Set Computer）設計に基づいており、電力効率と性能のバランスが特徴です。

このコミットは、NetBSD上でARMプロセッサを搭載したシステムにおけるGoランタイムの動作を対象としています。

### システムコールとシグナル
*   **システムコール**: アプリケーションがオペレーティングシステムのカーネルにサービスを要求するためのインターフェースです。ファイルI/O、メモリ割り当て、プロセス管理など、低レベルな操作を行う際に使用されます。
*   **シグナル**: オペレーティングシステムがプロセスに対して、特定のイベント（例: 割り込み、エラー、子プロセスの終了）が発生したことを非同期に通知するメカニズムです。プロセスはシグナルを受信すると、デフォルトの動作を実行するか、カスタムのシグナルハンドラを呼び出すことができます。

### `mcontext` と `ucontext`
Unix系システムにおけるシグナルハンドリングやコンテキストスイッチングで用いられるデータ構造です。
*   **`mcontext_t`**: CPUのレジスタの状態（プログラムカウンタ、スタックポインタ、汎用レジスタなど）を保存するための構造体です。シグナルハンドラが呼び出される際に、割り込み前のプロセスのCPU状態がこの構造体に保存され、ハンドラ終了後に復元されます。
*   **`ucontext_t`**: `mcontext_t`を含む、より広範な実行コンテキスト情報（シグナルマスク、スタック情報など）を保持する構造体です。

Goランタイムは、これらのOS固有の構造体をGoの型として定義し、シグナルハンドリング時にCPUの状態を適切に操作する必要があります。

### `uintptr` と `unsafe.Pointer`
Go言語における低レベルなメモリ操作に関連する型です。
*   **`uintptr`**: ポインタの値を保持できる符号なし整数型です。ポインタを整数に変換したり、整数をポインタに変換したりする際に使用されます。Goの型システムをバイパスしてメモリを直接操作する際に必要となりますが、ガベージコレクタは`uintptr`が指すメモリを追跡しないため、誤用するとメモリリークやクラッシュの原因となります。
*   **`unsafe.Pointer`**: 任意の型のポインタを保持できる特殊なポインタ型です。C言語の`void*`に似ており、Goの型安全性を一時的に無効にして、異なる型のポインタ間で変換を行うことを可能にします。`unsafe.Pointer`もガベージコレクタによって追跡されないため、非常に注意して使用する必要があります。

これらの型は、GoランタイムがOSの低レベルなデータ構造やメモリ領域を操作する際に不可欠です。

## 技術的詳細

このコミットの技術的な核心は、NetBSD/ARMプラットフォームにおけるGoランタイムのOSインタラクションとシグナルハンドリングのロジックを、C言語からGo言語へ完全に移行した点にあります。

1.  **Cファイルの削除とGoファイルへの置き換え**:
    *   `src/runtime/os_netbsd_arm.c` が削除され、その機能は `src/runtime/os_netbsd_arm.go` に移植されました。
    *   `src/runtime/signal_netbsd_arm.h` が削除され、その機能は `src/runtime/signal_netbsd_arm.go` に移植されました。特に、Cヘッダーファイルで定義されていたレジスタアクセス用のマクロ（`SIG_R0`, `SIG_PC`など）が、Goの`sigctxt`構造体のメソッドとして再実装されました。

2.  **型定義の変更 (`defs1_netbsd_arm.go`)**:
    *   `sigaltstackt`、`siginfo`、`stackt`といったOS固有の構造体定義において、ポインタ型やサイズを表すフィールドの型が変更されました。
        *   `*byte` から `uintptr` へ: これは、Goのポインタ型（`*byte`）ではなく、ポインタの値を保持する整数型（`uintptr`）を使用することで、より低レベルなメモリ操作やC言語との互換性を高める意図があります。`uintptr`はガベージコレクタの管理外となるため、注意が必要です。
        *   `uint32` から `uintptr` へ: 同様に、サイズを表すフィールドも`uintptr`に変更され、ポインタのサイズやアドレスをより柔軟に扱えるようになりました。
    *   `siginfo`構造体では、`_reason`フィールドが`[20]byte`から`uintptr`に変更され、`_reasonx [16]byte`が追加されました。これは、シグナル情報の一部としてアドレスを直接扱うための変更と考えられます。
    *   `timespec`と`timeval`構造体に、それぞれ`set_sec`, `set_nsec`, `set_usec`といったセッターメソッドが追加されました。これにより、GoのコードからこれらのOS構造体のフィールドをよりGoらしい方法で安全に設定できるようになりました。

3.  **OSインタラクションのGo化 (`os_netbsd_arm.go`)**:
    *   `lwp_mcontext_init`関数は、軽量プロセス（LWP: Light-Weight Process）のコンテキストを初期化する役割を担います。C言語版では直接レジスタに値を設定していましたが、Go言語版では`unsafe.Pointer`と`uintptr`を駆使して、Goの`mcontextt`構造体のフィールドに値を設定しています。`funcPC`はGoの関数のエントリポイントのアドレスを取得するために使用されます。
    *   `cputicks`関数は、CPUのティック数を返す関数で、プロファイラや乱数生成のシードとして利用されます。このコミットでは、`runtime·nanotime()`（Goの`nanotime()`）を呼び出すように変更されており、CPUティックの近似値としてナノ秒単位の時刻を使用しています。

4.  **シグナルハンドリングのGo化 (`signal_netbsd_arm.go`)**:
    *   `sigctxt`構造体が導入され、シグナルハンドラに渡されるコンテキスト情報（`siginfo`と`ucontext`）をGoの型としてラップしています。
    *   `regs()`メソッドを通じて`mcontextt`にアクセスし、`r0()`, `pc()`, `sp()`などのメソッドを通じて、CPUレジスタの値をGoのコードから読み書きできるようになりました。これは、Cヘッダーファイルで定義されていたマクロの機能と等価です。
    *   `set_pc()`, `set_sp()`などのセッターメソッドも提供され、シグナルハンドラ内でプログラムカウンタやスタックポインタなどのレジスタ値を変更することが可能になります。これは、例えばシグナルからの復帰アドレスを変更するなどの高度な処理に利用されます。
    *   `unsafe.Pointer`が`sigctxt`の`ctxt`フィールドで使用されており、低レベルな`ucontextt`構造体へのポインタを扱うために必要です。

これらの変更により、NetBSD/ARMにおけるGoランタイムの低レベルなOSインタラクションとシグナルハンドリングが、Go言語の型システムとメモリモデルに沿った形で実装され、C言語のコードベースが完全に排除されました。これにより、ランタイムのコードベース全体の一貫性が向上し、Go言語のツールチェーンによる分析やデバッグが容易になります。

## コアとなるコードの解説

### `lwp_mcontext_init` 関数のGo言語への移植

この関数は、軽量プロセス（LWP）のコンテキストを初期化する際に、CPUのレジスタに特定の値を設定する役割を担っています。

*   **C言語版**:
    ```c
    mc->__gregs[REG_R15] = (uint32)runtime·lwp_tramp;
    mc->__gregs[REG_R13] = (uint32)stack;
    // ...
    ```
    C言語では、`mc`（`McontextT`型）の`__gregs`配列に直接レジスタ番号（`REG_R15`など）を使って値を代入しています。`runtime·lwp_tramp`は関数のアドレスを指すポインタです。

*   **Go言語版**:
    ```go
    mc.__gregs[_REG_R15] = uint32(funcPC(lwp_tramp))
    mc.__gregs[_REG_R13] = uint32(uintptr(stk))
    // ...
    ```
    Go言語では、`mc`（`mcontextt`型）の`__gregs`配列に値を設定する点は同じですが、値の取得方法と型変換に違いがあります。
    *   `funcPC(lwp_tramp)`: Goの関数`lwp_tramp`のエントリポイントのアドレスを`uintptr`として取得します。これはC言語版の`runtime·lwp_tramp`に相当します。
    *   `uintptr(stk)`: `stk`は`unsafe.Pointer`型ですが、これを`uintptr`に変換することで、ポインタの値を整数として扱えるようにします。
    *   最終的に`uint32()`で`uintptr`の値を32ビットの符号なし整数にキャストしています。これはARMアーキテクチャのレジスタが32ビット幅であるためです。
    `unsafe.Pointer`と`uintptr`を組み合わせることで、Goの型安全性を一時的にバイパスし、C言語のような低レベルなメモリ操作を実現しています。

### `sigctxt` 構造体とレジスタアクセス用メソッド

`signal_netbsd_arm.go`で導入された`sigctxt`構造体は、シグナルハンドラがCPUの状態にアクセスするためのGoらしいインターフェースを提供します。

*   **C言語版 (`signal_netbsd_arm.h`)**:
    ```c
    #define SIG_R0(info, ctxt) (SIG_REGS(ctxt).__gregs[REG_R0])
    #define SIG_PC(info, ctxt) (SIG_REGS(ctxt).__gregs[REG_R15])
    ```
    C言語では、マクロを使って`ucontext_t`構造体から`mcontext_t`を取り出し、その中の`__gregs`配列から特定のレジスタの値を直接取得していました。

*   **Go言語版 (`signal_netbsd_arm.go`)**:
    ```go
    type sigctxt struct {
    	info *siginfo
    	ctxt unsafe.Pointer // ucontextt へのポインタ
    }

    func (c *sigctxt) regs() *mcontextt { return &(*ucontextt)(c.ctxt).uc_mcontext }
    func (c *sigctxt) r0() uint32       { return c.regs().__gregs[_REG_R0] }
    func (c *sigctxt) pc() uint32       { return c.regs().__gregs[_REG_R15] }
    func (c *sigctxt) set_pc(x uint32)  { c.regs().__gregs[_REG_R15] = x }
    ```
    Go言語では、`sigctxt`構造体の`ctxt`フィールドが`unsafe.Pointer`として`ucontextt`へのポインタを保持します。
    *   `regs()`メソッドは、`unsafe.Pointer`を`*ucontextt`に型変換し、その`uc_mcontext`フィールドへのポインタを返します。これにより、Goの型システムを通じて`mcontextt`構造体にアクセスできるようになります。
    *   `r0()`, `pc()`などのメソッドは、`regs()`が返す`mcontextt`ポインタを利用して、`__gregs`配列から対応するレジスタの値を読み出します。
    *   `set_pc()`などのメソッドは、同様に`__gregs`配列に新しい値を書き込みます。

このアプローチにより、C言語のマクロに依存することなく、Go言語のメソッドとしてレジスタへのアクセスと操作が抽象化され、コードの可読性と保守性が向上しています。

### 型定義の変更 (`defs1_netbsd_arm.go`)

`sigaltstackt.ss_sp`や`stackt.ss_sp`が`*byte`から`uintptr`に変更されたことは重要です。

*   **`*byte`**: Goのバイトスライスや配列の先頭を指すポインタとして使われることがありますが、これはGoのガベージコレクタが追跡する型付きポインタです。
*   **`uintptr`**: ポインタの値を保持する整数型であり、ガベージコレクタは`uintptr`が指すメモリを追跡しません。

この変更は、OSの低レベルな構造体（特にスタックやシグナルスタックのポインタ）をGoランタイムが直接操作する際に、Goのガベージコレクタの介入なしに、C言語のポインタのように扱えるようにするためです。これにより、OSとのインタフェースにおけるGoランタイムの柔軟性が向上します。

また、`timespec`と`timeval`にセッターメソッドが追加されたことは、Goの構造体に対するイディオム的なアプローチを示しています。C言語では直接フィールドに代入しますが、Goではこのようなセッターメソッドを提供することで、フィールドへのアクセスをカプセル化し、将来的な実装変更にも対応しやすくなります。

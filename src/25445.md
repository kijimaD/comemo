## 変更の背景

Go言語の `net/http` パッケージは、HTTP/1.1だけでなくHTTP/2プロトコルもサポートしています。HTTP/2の実装は、当初 `golang.org/x/net/http2` という独立したエクスペリメンタルパッケージとして開発が進められていました。このアプローチにより、標準ライブラリの安定性を保ちつつ、新しいプロトコルの開発と改善を迅速に行うことが可能になります。

開発が進み、`x/net/http2` パッケージが十分に成熟すると、その機能は `net/http` パッケージに「バンドル」される形で取り込まれます。これにより、ユーザーは追加のインポートなしにHTTP/2機能を利用できるようになります。

このコミットの背景には、`golang.org/x/net/http2` パッケージにおける継続的な改善とバグ修正があり、それらを標準ライブラリに反映させる必要があったことが挙げられます。特に、HTTP/2のクライアント実装におけるフロー制御、バッファ管理、およびTLSハンドシェイクの柔軟性向上が主な焦点となっています。

## 前提知識の解説

### HTTP/2プロトコル

HTTP/2は、HTTP/1.1のセマンティクスを維持しつつ、パフォーマンスを向上させるために設計されたプロトコルです。主な特徴は以下の通りです。

*   **多重化 (Multiplexing)**: 単一のTCPコネクション上で複数のリクエストとレスポンスを並行して送受信できます。これにより、ヘッドオブラインブロッキングが解消されます。
*   **ストリーム (Streams)**: 各リクエスト/レスポンスの交換は「ストリーム」として扱われ、それぞれに一意のIDが割り当てられます。
*   **ヘッダー圧縮 (Header Compression)**: HPACKというアルゴリズムを使用して、HTTPヘッダーの冗長な部分を圧縮し、帯域幅の使用量を削減します。
*   **サーバープッシュ (Server Push)**: サーバーがクライアントからのリクエストなしに、将来必要になるであろうリソースを事前に送信できます。
*   **フロー制御 (Flow Control)**: 送信側が受信側のバッファオーバーフローを防ぐために、送信できるデータ量を制限するメカニズムです。コネクションレベルとストリームレベルの両方で適用されます。

### Go言語の `net/http` と `golang.org/x/net/http2`

*   **`net/http`**: Goの標準ライブラリで、HTTPクライアントとサーバーの機能を提供します。HTTP/1.1とHTTP/2の両方をサポートします。
*   **`golang.org/x/net/http2`**: `net/http` のHTTP/2実装の基盤となるエクスペリメンタルパッケージです。標準ライブラリに直接組み込む前に、新しい機能や改善を試すために使用されます。

### バンドル (Bundling)

Goの標準ライブラリでは、外部の `x` パッケージ（例: `golang.org/x/net`）のコードを、標準ライブラリ内の特定のファイルにコピーして含めることがあります。これを「バンドル」と呼びます。これにより、標準ライブラリのユーザーは、外部パッケージを明示的にインポートすることなく、その機能を利用できます。バンドルされたファイルは通常、自動生成されたものであることを示すコメントを含みます。

### フロー制御 (Flow Control)

HTTP/2のフロー制御は、`WINDOW_UPDATE` フレームを使用して行われます。これは、受信側がどれだけの追加データを受け入れる準備ができているかを送信側に通知するメカニズムです。
*   **コネクションレベルフロー制御**: コネクション全体で利用可能なバッファサイズを管理します。
*   **ストリームレベルフロー制御**: 個々のストリームで利用可能なバッファサイズを管理します。

### `io.Pipe` とバッファリング

`io.Pipe` は、Goでgoroutine間でデータをストリームとして受け渡すためのメカニズムです。`io.PipeReader` と `io.PipeWriter` のペアで構成され、一方が書き込んだデータをもう一方が読み取ることができます。デフォルトではバッファリングされません。

## 技術的詳細

このコミットは、`golang.org/x/net/http2` の更新を取り込むことで、`net/http` パッケージのHTTP/2クライアント実装にいくつかの重要な改善をもたらしています。

1.  **バッファ管理の改善**:
    *   既存の `http2buffer` 型が削除され、よりシンプルで効率的な `http2fixedBuffer` 型が導入されました。`http2fixedBuffer` は、固定サイズのバッファを `io.ReadWriter` として機能させ、読み取りが完了すると内部ポインタをリセットして再利用しやすくします。これにより、メモリ割り当てのオーバーヘッドが削減され、ガベージコレクションの負荷が軽減される可能性があります。
    *   `http2pipe` の実装が大幅に刷新され、`http2pipeBuffer` インターフェースを導入することで、基盤となるバッファの実装を抽象化しました。これにより、`io.Pipe` のようなバッファリングされないストリームではなく、バッファリングされたパイプをHTTP/2ストリームのボディとして利用できるようになりました。

2.  **HTTP/2クライアントのフロー制御の強化**:
    *   `http2clientConn` および `http2clientStream` に、コネクションレベルとストリームレベルのフロー制御を管理するための `http2flow` 構造体が追加されました。これにより、クライアントはサーバーからの `WINDOW_UPDATE` フレームをより正確に処理し、自身の送信ウィンドウを適切に管理できるようになります。
    *   `awaitFlowControl` メソッドが導入され、クライアントがデータを送信する前に、利用可能なフロー制御トークンを待機するメカニズムが提供されました。これは、クライアントがサーバーの受信能力を超えてデータを送信するのを防ぎ、ネットワークの輻輳を緩和するために重要です。
    *   `http2transportDefaultConnFlow` (1GB) と `http2transportDefaultStreamFlow` (4MB) といったデフォルトのフロー制御ウィンドウサイズが定義され、より適切な初期値が設定されました。

3.  **TLS設定の柔軟性向上**:
    *   `http2Transport` に `DialTLS` 関数と `TLSClientConfig` フィールドが追加されました。これにより、ユーザーはカスタムのTLSダイアラーやTLS設定（例: クライアント証明書、ルートCA、`InsecureSkipVerify` の詳細な制御）をHTTP/2トランスポートに提供できるようになり、より多様な環境での利用が可能になります。

4.  **リソースプーリングの導入**:
    *   `http2writeDataPool` が導入され、`http2writeData` オブジェクトの再利用が可能になりました。これにより、頻繁に生成される一時的なオブジェクトの割り当てを減らし、ガベージコレクションの頻度と負荷を低減することで、パフォーマンスが向上します。

5.  **エラーハンドリングとストリーム管理の改善**:
    *   `http2pipe.CloseWithError` メソッドが追加され、パイプのクローズ時に特定のエラーを関連付けられるようになりました。これにより、ストリームの終了理由をより詳細に伝えることができます。
    *   `http2clientStream` に `peerReset` チャネルと `resetErr` フィールドが追加され、サーバーからの `RST_STREAM` フレームによるストリームリセットをより適切に処理できるようになりました。
    *   `http2clientConnReadLoop` という新しい構造体が導入され、`readLoop` のロジックがより整理され、状態管理が明確になりました。

これらの変更は、HTTP/2クライアントの堅牢性、パフォーマンス、および設定の柔軟性を向上させることを目的としています。特に、フロー制御の厳密な実装とリソースの効率的な管理は、高負荷環境での安定した動作に寄与します。

## コアとなるコードの解説

### `http2fixedBuffer`

この新しいバッファ実装は、`io.ReadWriter` インターフェースを満たし、固定サイズのバイトスライス `buf` を使用します。`r` と `w` はそれぞれ読み取りポインタと書き込みポインタです。
*   `Read(p []byte)`: `buf[r:w]` から `p` にデータをコピーします。バッファが空になった場合 (`r == w`)、`r` と `w` を0にリセットし、バッファ全体を再利用可能な状態にします。これにより、バッファの先頭へのデータの移動（コピー）が不要になり、効率が向上します。
*   `Write(p []byte)`: `p` から `buf[w:]` にデータをコピーします。バッファの末尾に十分なスペースがない場合、既存のデータをバッファの先頭に移動させてスペースを確保します。

### `http2pipe`

`http2pipe` は、goroutineセーフな `io.Reader`/`io.Writer` ペアを提供します。
*   `mu sync.Mutex` と `c sync.Cond` を使用して、複数のgoroutineからのアクセスを同期します。
*   `b http2pipeBuffer` インターフェースを介して、実際のバッファ実装（このコミットでは `http2fixedBuffer` を使用）を抽象化します。
*   `Read` メソッドは、データが利用可能になるまで `c.Wait()` で待機します。
*   `Write` メソッドは、データを書き込んだ後に `c.Signal()` を呼び出して、待機中のリーダーを起動します。
*   `CloseWithError(err error)` は、パイプをクローズし、それ以降の読み取り操作で指定されたエラーを返すように設定します。これは、ストリームの正常な終了 (`io.EOF`) やエラーによる終了を区別するために重要です。

### `http2Transport` と `http2clientConn` のフロー制御

`http2clientConn` は、HTTP/2コネクションの状態を管理します。
*   `flow http2flow` (送信フロー制御) と `inflow http2flow` (受信フロー制御) は、それぞれクライアントが送信できるバイト数と、サーバーから受信できるバイト数を追跡します。
*   `awaitFlowControl(maxBytes int32)` メソッドは、`http2clientStream` のコンテキストで呼び出され、ストリームレベルおよびコネクションレベルのフロー制御ウィンドウが、指定された `maxBytes` を送信するのに十分な大きさになるまで待機します。これにより、クライアントはサーバーの受信能力を超えてデータを送信することを防ぎます。
*   `processWindowUpdate(f *http2WindowUpdateFrame)` メソッドは、サーバーから受信した `WINDOW_UPDATE` フレームを処理し、対応するフロー制御ウィンドウ (`flow` または `inflow`) を更新します。更新後、`cc.cond.Broadcast()` を呼び出して、フロー制御の待機中のgoroutineを起動します。

### `http2clientStream.writeRequestBody`

このメソッドは、リクエストボディをサーバーに書き込むロジックを実装しています。
1.  `cc.frameScratchBuffer()` から一時的なバッファを取得し、`cc.putFrameScratchBuffer()` でプールに戻します。
2.  リクエストボディをチャンクに分割し、各チャンクを送信する前に `cs.awaitFlowControl()` を呼び出してフロー制御トークンを待機します。
3.  `cc.fr.WriteData()` を使用して `DATA` フレームを送信します。`sentEnd` フラグは、ストリームの終了を示す `END_STREAM` フラグを設定するために使用されます。
4.  サーバーがリクエストボディの送信中にレスポンスヘッダーを送信した場合 (`gotResHeaders` チャネルがクローズされた場合)、`http2errServerResponseBeforeRequestBody` エラーを返します。これはプロトコル違反の可能性があります。

### `http2clientConnReadLoop`

`readLoop` のロジックをカプセル化する新しい構造体です。
*   `run()` メソッドがフレームの読み取りとディスパッチのメインループを実行します。
*   `processHeaders`, `processContinuation`, `processData`, `processGoAway`, `processResetStream`, `processSettings`, `processWindowUpdate`, `processPushPromise` といったメソッドが、受信した各HTTP/2フレームタイプを処理します。
*   `onNewHeaderField` メソッドは、HPACKデコーダによって新しいヘッダーフィールドがデコードされるたびに呼び出され、レスポンスヘッダーを構築します。ここで、擬似ヘッダー (`:status`, `:method` など) と通常のヘッダーが区別され、不正なヘッダーシーケンスが検出された場合は `reqMalformed` エラーが設定されます。

これらの変更により、GoのHTTP/2クライアントは、より堅牢で効率的、かつ標準に準拠した動作を実現しています。

# [インデックス 21272] ファイルの概要

このコミットは、Goランタイムの `runtime.Stack` 関数において、`all=true` オプションが指定された場合に発生するデッドロックの問題を修正します。特に `GOMAXPROCS > 1` の環境でこの問題が顕著に現れ、`runtime.Stack` が実質的に使用不能になる状況を改善しました。

## 元コミット内容

このコミットは、`runtime.Stack` 関数におけるデッドロックを修正します。

問題は、`acquirem()` の内部で `semacquire()` が呼び出されるべきではないという点にありました。ランタイムはこれをデッドロックと誤認識していました。実際にはデッドロックではありませんでしたが、`acquirem()` が `m.locks++` を実行するため、ランタイムにはデッドロックのように見えていました。

この修正はGo 1.4.1への取り込み候補でした。`GOMAXPROCS > 1` の環境では、`all=true` を指定した `runtime.Stack` がほとんど使用不能な状態でした。

このコミットは、内部的な問題番号 `#9321` を修正します。

## 変更の背景

`runtime.Stack` 関数は、Goプログラムの実行中に現在のゴルーチン、または全てのゴルーチンのスタックトレースを取得するために使用されます。特に `all=true` オプションは、デバッグやプロファイリングの際に、システム全体のゴルーチンの状態を把握するために非常に有用です。

しかし、Go 1.4の時点では、`GOMAXPROCS` が1より大きい（つまり、複数のOSスレッドがGoのゴルーチンを実行できる）環境で `runtime.Stack(..., true)` を呼び出すと、ランタイムがデッドロックを誤検出してプログラムがクラッシュするという深刻なバグが存在しました。この問題により、マルチコア環境での `runtime.Stack` の利用が困難になっていました。

このコミットは、この誤検出によるデッドロックを解消し、`runtime.Stack` がマルチコア環境でも安定して動作するようにすることを目的としています。この修正がGo 1.4.1のリリース候補であったことからも、その重要性が伺えます。

## 前提知識の解説

このコミットの変更内容を理解するためには、Goランタイムの内部動作に関するいくつかの前提知識が必要です。

### Goランタイムスケジューラ (M, P, Gモデル)

Goランタイムは、ゴルーチンをOSスレッド上で効率的に実行するために、M, P, Gという3つのエンティティからなるスケジューラモデルを採用しています。

*   **G (Goroutine)**: Goの軽量な実行単位であり、Goプログラムの関数呼び出しスタックと関連するデータを含みます。数百万のゴルーチンを同時に実行できます。
*   **M (Machine)**: OSスレッド（カーネルスレッド）を表します。Goのコードを実行する実際のワーカーです。MはOSによってスケジューリングされます。
*   **P (Processor)**: 論理プロセッサを表します。MがGを実行するために必要なコンテキスト（スケジューラのキュー、メモリ割り当てキャッシュなど）を提供します。`GOMAXPROCS` 環境変数は、同時に実行できるPの数を制御します。

MはPにアタッチされ、PのローカルキューからGを取得して実行します。

### `runtime.Stack` 関数

`func Stack(buf []byte, all bool) int` は、Goプログラムのスタックトレースを取得するための関数です。
*   `buf`: スタックトレースを書き込むバイトスライス。
*   `all`: `true` の場合、現在のゴルーチンだけでなく、全てのゴルーチンのスタックトレースを `buf` に書き込みます。`false` の場合、現在のゴルーチンのスタックトレースのみを書き込みます。

### セマフォ (`semacquire`, `semrelease`)

セマフォは、複数のゴルーチンやOSスレッド（M）の間で共有リソースへのアクセスを同期するためのプリミティブです。
*   `semacquire(sema *uint32, block bool)`: セマフォ `sema` を取得しようとします。`block` が `true` の場合、セマフォが利用可能になるまでブロックします。
*   `semrelease(sema *uint32)`: セマフォ `sema` を解放します。

Goランタイムでは、`worldsema` というセマフォが `stoptheworld` や `starttheworld` のようなグローバルな操作を同期するために使用されます。

### Mのロック (`acquirem`, `releasem`, `m.locks`)

Goランタイムには、特定のM（OSスレッド）が重要な処理を実行している間、そのMがスケジューラによって他のゴルーチンに割り当てられないようにするためのメカニズムがあります。
*   `acquirem()`: 現在のMを取得し、そのMが他のゴルーチンにスケジューリングされないようにロックします。この関数が呼び出されると、現在のMの `m.locks` カウンタがインクリメントされます。
*   `releasem(m *m)`: Mのロックを解放します。この関数が呼び出されると、Mの `m.locks` カウンタがデクリメントされます。
*   `m.locks`: Mが保持しているロックの数を追跡するカウンタです。この値が0でない場合、Mはロックされていると見なされ、スケジューラはそのMを他のゴルーチンに割り当てません。これは、Mがランタイムの重要な内部処理（例えば、スケジューラの状態変更やGC関連の操作）を実行していることを示します。

### `stoptheworld` と `starttheworld`

これらはGoランタイムの重要な同期メカニズムです。
*   `stoptheworld()`: 全てのゴルーチンの実行を一時停止させます。これは、ガベージコレクション（GC）やその他のランタイムのグローバルな状態を変更する操作の前に、一貫した状態を確保するために使用されます。
*   `starttheworld()`: `stoptheworld()` によって停止されたゴルーチンの実行を再開させます。

これらの操作は、`worldsema` セマフォを使用して同期されます。`stoptheworld` は `worldsema` を取得し、`starttheworld` はそれを解放します。

### デッドロック

デッドロックとは、複数のプロセスやスレッドが互いに相手が保持しているリソースの解放を待ち、結果としてどのプロセスも実行を継続できない状態を指します。Goランタイムは、全てのゴルーチンがブロックされ、進捗がない場合にデッドロックを検出し、プログラムを終了させます。

## 技術的詳細

このコミットが修正した問題の核心は、`runtime.Stack` 関数が `all=true` で呼び出された際に、Goランタイムの内部的なロックメカニズムとセマフォの取得が誤った相互作用を引き起こし、ランタイムがデッドロックを誤認識していた点にあります。

### 問題の発生メカニズム

1.  **`runtime.Stack(..., true)` の呼び出し**: 全てのゴルーチンのスタックトレースを取得するため、ランタイムは `stoptheworld` を実行する必要があります。
2.  **`acquirem()` の呼び出し**: 以前の `runtime.Stack` の実装では、まず `acquirem()` を呼び出して現在のM（OSスレッド）をロックしていました。これにより、`m.locks` カウンタがインクリメントされ、このMはスケジューラから一時的に隔離されます。
3.  **`semacquire(&worldsema, false)` の呼び出し**: `stoptheworld` を実行するために、`runtime.Stack` は `worldsema` セマフォを取得しようとします。この `semacquire` の呼び出しが、`acquirem()` によってMがロックされた状態（`m.locks > 0`）で実行されていました。
4.  **ランタイムの誤認識**: `semacquire` は、セマフォが利用可能になるまでMをブロックする可能性があります。しかし、Mが既に `acquirem()` によってロックされている（`m.locks > 0`）ため、ランタイムはMがブロックされているにもかかわらず、そのMがロックを保持していると認識します。Goランタイムのデッドロック検出ロジックは、ロックを保持しているMがブロックされている状態を、デッドロックの兆候と見なすことがあります。
5.  **「デッドロックのように見える」状態**: 実際には、Mは `worldsema` を待っているだけであり、他のMが `worldsema` を解放すれば進行できるはずです。しかし、ランタイムの内部状態（`m.locks > 0` とMのブロック状態の組み合わせ）が、これを真のデッドロックと誤認識させていました。これにより、ランタイムは「全てのゴルーチンがスリープ状態 - デッドロック！」という致命的なエラーを報告し、プログラムを終了させていました。
6.  **`GOMAXPROCS > 1` での問題**: 複数のPが存在する環境では、複数のMが並行して動作するため、このMのロック状態とセマフォの取得が複雑に絡み合い、より頻繁にこの誤認識によるデッドロックが発生しやすかったと考えられます。

要するに、`acquirem()` がMをロックし、そのロックされたMがさらに `semacquire()` でブロックされるという状況が、ランタイムのデッドロック検出ロジックを混乱させていたのです。

## コアとなるコードの解説

### `src/runtime/mprof.go` の変更点

`runtime.Stack` 関数の実装が大幅に変更され、`acquirem()` と `releasem()` の呼び出しが削除されました。これにより、関数全体がMをロックする状態を回避し、`semacquire` がMのロック内部で実行される状況を解消しました。

**変更前のコードの抜粋（関連部分）:**

```go
func Stack(buf []byte, all bool) int {
	mp := acquirem() // Mをロック
	gp := mp.curg
	if all {
		semacquire(&worldsema, false) // ロックされたMの内部でセマフォを取得
		mp.gcing = 1
		releasem(mp) // Mを解放
		systemstack(stoptheworld)
		if mp != acquirem() { // ここで再度Mを取得
			gothrow("Stack: rescheduled")
		}
	}

	// ... (スタックトレースの取得ロジック)

	if all {
		mp.gcing = 0
		semrelease(&worldsema)
		systemstack(starttheworld)
	}
	releasem(mp) // Mを解放
	return n
}
```

**変更後のコードの抜粋（関連部分）:**

```go
func Stack(buf []byte, all bool) int {
	// mp := acquirem() // 削除
	// gp := mp.curg // 削除
	if all {
		semacquire(&worldsema, false) // Mのロックなしでセマフォを取得
		gp := getg() // 現在のゴルーチンを取得
		gp.m.gcing = 1 // 現在のMのgcingフラグを設定
		// releasem(mp) // 削除
		systemstack(stoptheworld)
		// if mp != acquirem() { // 削除
		// 	gothrow("Stack: rescheduled")
		// }
	}

	n := 0
	if len(buf) > 0 {
		gp := getg() // ここでも現在のゴルーチンを取得
		sp := getcallersp(unsafe.Pointer(&buf))
		pc := getcallerpc(unsafe.Pointer(&buf))
		systemstack(func() {
			// ... (スタックトレースの取得ロジック)
		})
	}

	if all {
		gp := getg() // ここでも現在のゴルーチンを取得
		gp.m.gcing = 0
		semrelease(&worldsema)
		systemstack(starttheworld)
	}
	// releasem(mp) // 削除
	return n
}
```

**主要な変更の意図:**

*   **`acquirem()` と `releasem()` の削除**: `runtime.Stack` 関数全体がMをロックする状態を完全に排除しました。これにより、`semacquire` が `m.locks > 0` の状態で呼び出されることがなくなり、ランタイムのデッドロック誤認識の原因が取り除かれました。
*   **`getg()` の導入**: `acquirem()` を使用する代わりに、`getg()` 関数（現在のゴルーチンを取得する）を直接使用するように変更されました。これにより、現在のゴルーチン (`g`) を介して、そのゴルーチンが実行されているM (`g.m`) の状態（例: `g.m.gcing`）を安全に操作できるようになりました。
*   **`mp.gcing` から `gp.m.gcing` へ**: `gcing` フラグの設定も、直接Mをロックするのではなく、現在のゴルーチンがアタッチされているMに対して行われるようになりました。
*   **`Stack: rescheduled` チェックの削除**: `acquirem()` と `releasem()` のペアが削除されたため、Mが途中で再スケジューリングされる可能性に関するチェックも不要になりました。

これらの変更により、`runtime.Stack` はMのロック状態に依存せず、より安全に `stoptheworld` などのグローバルな同期操作を実行できるようになりました。

### `test/fixedbugs/issue9321.go` の解説

このファイルは、修正されたデッドロック問題を再現し、修正が正しく機能することを確認するための新しいテストケースです。

```go
// run

// Copyright 2014 The Go Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package main

import (
	"bytes"
	"runtime"
	"runtime/pprof"
	"sync"
)

func test() {
	var wg sync.WaitGroup
	wg.Add(2)
	test := func() {
		for i := 0; i < 100; i++ {
			buf := &bytes.Buffer{}
			pprof.Lookup("goroutine").WriteTo(buf, 2) // 内部で runtime.Stack(..., true) を呼び出す
		}
		wg.Done()
	}

	go test()
	go test()
	wg.Wait()
}

func main() {
	runtime.GOMAXPROCS(2) // GOMAXPROCS を 2 に設定し、マルチコア環境をシミュレート
	for i := 0; i < 100; i++ {
		test() // 問題を繰り返し再現
	}
}
```

**テストのポイント:**

*   **`runtime.GOMAXPROCS(2)`**: この設定により、テストは2つの論理プロセッサ（P）を使用する環境で実行されます。これは、以前デッドロックが発生しやすかったマルチコア環境をシミュレートするために重要です。
*   **`pprof.Lookup("goroutine").WriteTo(buf, 2)`**: `pprof` パッケージの `Lookup("goroutine").WriteTo` 関数は、内部で `runtime.Stack(buf, true)` を呼び出します。これにより、全てのゴルーチンのスタックトレースを取得する操作が実行されます。
*   **並行実行と繰り返し**: `test` 関数内で `pprof.Lookup("goroutine").WriteTo` が100回繰り返され、さらに2つのゴルーチンが並行して `test` 関数を実行します。`main` 関数でも `test()` が100回繰り返されます。これにより、デッドロックが発生する可能性のある状況を意図的に頻繁に引き起こし、修正が安定していることを確認します。
*   **`sync.WaitGroup`**: `sync.WaitGroup` を使用して、全てのゴルーチンが正常に完了するのを待つことで、デッドロックが発生せずにプログラムが終了することを確認します。もしデッドロックが発生すれば、プログラムはクラッシュし、テストは失敗します。

このテストは、修正が `GOMAXPROCS > 1` の環境で `runtime.Stack(..., true)` を安全に使用できるようにしたことを効果的に検証しています。

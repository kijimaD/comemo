# [インデックス 23582] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）において、レース検出モード（race detector）が有効な場合にスライスと`append`操作で不要な一時変数が生成される問題を修正します。これにより、ライトバリアの最適化が阻害され、特にランタイム内の`go:nowritebarrier`関数でコンパイルエラーが発生する可能性があったパフォーマンス上のボトルネックが解消されます。

## コミット

```
commit f90d802b6102ced82377ddc16f81f299c039ce83
Author: Austin Clements <austin@google.com>
Date:   Wed May 27 15:20:49 2015 -0400

    cmd/compile: avoid temporary in race mode with slice and append
    
    Currently when the race detector is enabled, orderexpr always creates
    a temporary for slice and append operations. This used to be necessary
    because the race detector had a different code path for slice
    assignment that required this temporary. Unfortunately, creating this
    temporary inhibits the optimization that eliminates write barriers
    when a slice is assigned only to change its length or cap. For most
    code, this is bad for performance, and in go:nowritebarrier functions
    in the runtime, this can mean the difference between compiling and not
    compiling.
    
    Now the race detector uses the regular slice assignment code, so
    creating this temporary is no longer necessary.
    
    Change-Id: I296042e1edc571b77c407f709c2ff9091c4aa795
    Reviewed-on: https://go-review.googlesource.com/10456
    Reviewed-by: Russ Cox <rsc@golang.org>
```

## 元コミット内容

Goコンパイラにおいて、レース検出モードが有効な場合、`orderexpr`関数はスライスと`append`操作に対して常に一時変数を生成していました。これは、レース検出器がスライスの代入に対して異なるコードパスを持っており、この一時変数が必要だったためです。しかし、この一時変数の生成は、スライスの長さや容量のみを変更する代入時にライトバリアを排除する最適化を阻害していました。ほとんどのコードにとってこれはパフォーマンスの低下を招き、ランタイム内の`go:nowritebarrier`関数では、コンパイルの可否に影響を与える可能性がありました。

現在では、レース検出器は通常のスライス代入コードを使用するようになったため、この一時変数の生成は不要になりました。

## 変更の背景

この変更の背景には、Goのレース検出器とガベージコレクションのライトバリア最適化の間の非効率性がありました。

1.  **レース検出器の挙動**: 以前のGoコンパイラでは、レース検出器が有効な場合（`flag_race != 0`）、スライスや`append`操作の際に、`orderexpr`関数が強制的に一時変数を生成していました。これは、レース検出器がスライスの代入を特別に処理する必要があったためです。
2.  **ライトバリア最適化の阻害**: Goのガベージコレクタは、オブジェクトの参照が変更される際に「ライトバリア」と呼ばれる処理を挿入することがあります。これは、ガベージコレクタがオブジェクトグラフを正確に追跡するために必要です。しかし、スライスの長さや容量のみが変更され、基盤となる配列のポインタ自体は変更されないような特定のケースでは、ライトバリアは不要であり、コンパイラはこれを最適化して排除することができます。一時変数が生成されると、このライトバリアの排除最適化が適用されなくなっていました。
3.  **パフォーマンスへの影響**: 不要なライトバリアは、ガベージコレクションのオーバーヘッドを増加させ、プログラムの実行速度を低下させます。
4.  **`go:nowritebarrier`関数の問題**: Goランタイムの特定の低レベル関数には、`//go:nowritebarrier`というディレクティブが付与されているものがあります。これは、これらの関数がライトバリアを生成してはならないことをコンパイラに指示するものです。一時変数の生成がライトバリア最適化を阻害すると、これらの`go:nowritebarrier`関数がコンパイルできなくなる、あるいは意図しないライトバリアが挿入されてしまうという深刻な問題を引き起こす可能性がありました。
5.  **レース検出器の改善**: コミットメッセージによると、レース検出器自体が改善され、通常のスライス代入コードパスを使用するようになったため、もはや一時変数を強制する必要がなくなりました。この改善により、コンパイラはレース検出モードでもライトバリア最適化を適用できるようになり、パフォーマンスとランタイムコードの健全性が向上しました。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Goコンパイラは、Go言語のソースコードを機械語に変換するプログラムです。`src/cmd/compile/internal/gc`ディレクトリには、コンパイラの主要な部分である「gc」（Go Compiler）パッケージが含まれています。このパッケージは、字句解析、構文解析、型チェック、中間表現（IR）の生成、最適化、コード生成など、コンパイルの様々な段階を担当します。

### Race Detector (競合検出器)

Goのレース検出器は、並行プログラムにおけるデータ競合（data race）を検出するためのツールです。データ競合は、複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に発生します。レース検出器は、プログラムの実行時にメモリアクセスを監視し、潜在的な競合を報告することで、並行バグの特定を支援します。`go run -race`や`go test -race`のように`-race`フラグを付けて実行することで有効になります。

### SliceとAppend操作

Goのスライスは、可変長シーケンスを表現するためのデータ構造です。内部的には、ポインタ、長さ（length）、容量（capacity）の3つの要素から構成されます。
- **ポインタ**: スライスが参照する基盤となる配列の先頭要素へのポインタ。
- **長さ**: スライスに含まれる要素の数。
- **容量**: 基盤となる配列のサイズ。スライスが拡張できる最大長。

`append`関数は、スライスに要素を追加するために使用されます。容量が足りない場合、`append`はより大きな新しい基盤配列を割り当て、既存の要素をコピーし、新しい要素を追加します。このとき、スライスのポインタ、長さ、容量が更新されます。容量が足りている場合は、既存の基盤配列を再利用し、長さのみが更新されます。

### Write Barrier (ライトバリア)

ライトバリアは、ガベージコレクション（GC）の一種である「三色マーク＆スイープ」アルゴリズムなどで使用される技術です。GCがオブジェクトグラフを走査している最中に、プログラムがオブジェクトの参照を変更（書き込み）すると、GCがオブジェクトを見落とす可能性があります。これを防ぐために、参照の書き込み時に特定のコード（バリア）を挿入し、GCがオブジェクトを正しく追跡できるようにします。

GoのGCは並行GCであり、プログラムの実行と並行してGCが動作します。このため、ライトバリアはGCの正確性を保証するために不可欠です。しかし、ライトバリアはオーバーヘッドを伴うため、コンパイラは可能な限りライトバリアを省略する最適化を行います。特に、スライスの長さや容量のみが変更され、基盤となる配列のポインタ自体は変更されないような代入では、ライトバリアは不要と判断されることがあります。

### `go:nowritebarrier`関数

Goランタイムの非常に低レベルな部分、特にガベージコレクタ自体やメモリ管理に関わるコードでは、ライトバリアの挿入が不適切であったり、デッドロックを引き起こしたり、パフォーマンスに致命的な影響を与えたりする場合があります。このような関数には、`//go:nowritebarrier`というコンパイラディレクティブが付与され、コンパイラに対してその関数内ではライトバリアを生成しないように指示します。このディレクティブは、非常に注意深く使用されるべきであり、コンパイラが意図せずライトバリアを挿入しようとすると、コンパイルエラーやランタイムの誤動作につながります。

### `orderexpr`関数

`src/cmd/compile/internal/gc/order.go`ファイルにある`orderexpr`関数は、Goコンパイラのバックエンドの一部であり、式の評価順序を決定し、必要に応じて一時変数を導入する役割を担います。Goの式は、特定の評価順序規則に従う必要があり、また、副作用を持つ式や複雑な式を安全に評価するために、コンパイラは一時的なストレージ（一時変数）を割り当てることがあります。この関数は、コードのセマンティクスを維持しつつ、効率的なコードを生成するために重要な役割を果たします。

### 一時変数 (Temporary Variable)

コンパイラは、複雑な式の結果を一時的に保持したり、特定の最適化やコード生成の要件を満たすために、内部的に一時変数を生成することがあります。これらの変数はソースコードには直接現れませんが、生成される機械語コードには存在し、レジスタやスタックに割り当てられます。一時変数の生成は、コードの正確性を保証するために必要ですが、過剰な生成はメモリ使用量や実行速度に悪影響を与える可能性があります。

## 技術的詳細

このコミットの技術的詳細の中心は、Goコンパイラがスライスと`append`操作を処理する際の条件分岐の変更にあります。

以前のコンパイラでは、`orderexpr`関数内でスライスや`append`操作を処理する際、以下のような条件で一時変数を生成していました。

```go
if lhs == nil || flag_race != 0 || lhs.Op != ONAME && !samesafeexpr(lhs, n.List.N) {
    n = ordercopyexpr(n, n.Type, order, 0)
}
```

この条件式において、`flag_race != 0`の部分が問題でした。
- `flag_race != 0`: これは、レース検出器が有効になっているかどうかを示すフラグです。この条件が真の場合、他の条件（`lhs == nil`や`lhs.Op != ONAME && !samesafeexpr(lhs, n.List.N)`）がどうであれ、常に一時変数が生成される`ordercopyexpr`が呼び出されていました。

`ordercopyexpr`は、式の結果を一時変数にコピーする処理を行います。レース検出器が以前はスライスの代入に対して特別なコードパスを持っていたため、この一時変数の強制的な生成が必要とされていました。

しかし、この一時変数の生成は、Goのガベージコレクタの重要な最適化を阻害していました。具体的には、スライスのポインタ自体は変更されず、長さや容量のみが変更されるような代入（例: `s = s[:len(s)+1]`）の場合、ライトバリアは不要です。コンパイラは通常、このようなケースでライトバリアを省略する最適化を行います。しかし、一時変数が導入されると、この最適化が適用されなくなり、不要なライトバリアが挿入されてしまう可能性がありました。

特に、Goランタイムの`go:nowritebarrier`関数では、ライトバリアの挿入が厳しく制限されています。一時変数の強制的な生成がライトバリアの最適化を阻害することで、これらの関数がコンパイルできなくなる、あるいは誤ったコードが生成されるリスクがありました。

コミットメッセージによると、レース検出器の内部実装が改善され、通常のスライス代入コードパスを使用するようになったため、もはやこの一時変数を強制する必要がなくなりました。これにより、`flag_race != 0`という条件は不要となり、削除されました。

変更後の条件式は以下のようになります。

```go
if lhs == nil || lhs.Op != ONAME && !samesafeexpr(lhs, n.List.N) {
    n = ordercopyexpr(n, n.Type, order, 0)
}
```

この変更により、レース検出モードが有効であっても、スライスや`append`操作で一時変数が生成されるかどうかは、`lhs == nil`または`lhs.Op != ONAME && !samesafeexpr(lhs, n.List.N)`という通常の最適化条件にのみ依存するようになりました。これにより、不要な一時変数の生成が抑制され、ライトバリアの最適化が適切に適用されるようになり、パフォーマンスが向上し、`go:nowritebarrier`関数のコンパイル問題も解消されました。

## コアとなるコードの解説

このコミットの核心は、`orderexpr`関数内の条件式から`|| flag_race != 0`という部分が削除されたことです。

-   `orderexpr(np **Node, order *Order, lhs *Node)`: この関数は、GoコンパイラのAST（抽象構文木）ノード`np`で表される式を走査し、評価順序を決定し、必要に応じて一時変数を導入します。`lhs`は代入の左辺を表すノードです。
-   `flag_race != 0`: これは、コンパイル時に`-race`フラグが指定され、レース検出器が有効になっている場合に真となる条件です。
-   `ordercopyexpr(n, n.Type, order, 0)`: この関数は、与えられた式`n`の結果を保持するための一時変数を生成し、その一時変数への代入を含む新しい式を返します。

変更前は、レース検出モードが有効な場合（`flag_race != 0`が真の場合）、`lhs == nil`や`lhs.Op != ONAME && !samesafeexpr(lhs, n.List.N)`といった他の条件がどうであれ、常に`ordercopyexpr`が呼び出され、一時変数が強制的に生成されていました。

-   `lhs == nil`: 左辺がない場合（例: 式の結果がどこにも代入されない場合）。
-   `lhs.Op != ONAME`: 左辺が単純な名前（変数）ではない場合。
-   `samesafeexpr(lhs, n.List.N)`: 左辺と式の右辺が同じで安全な式であるかどうかをチェックする関数。

これらの条件は、コンパイラが一時変数を導入して式の評価順序を保証したり、副作用を安全に処理したりするための通常のロジックです。しかし、`flag_race != 0`が追加されていたことで、レース検出モードではこれらの最適化の機会が失われていました。

`|| flag_race != 0`が削除されたことにより、レース検出モードが有効であっても、一時変数の生成は通常の最適化ロジック（`lhs == nil || lhs.Op != ONAME && !samesafeexpr(lhs, n.List.N)`）にのみ依存するようになりました。これにより、レース検出器が有効な場合でも、スライスの長さや容量のみを変更するような代入では、不要な一時変数が生成されなくなり、ライトバリアの最適化が適切に適用されるようになります。これは、Goコンパイラのコード生成の効率性と、Goランタイムの健全性にとって重要な改善です。

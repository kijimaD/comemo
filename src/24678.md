## 元コミット内容

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおいて、剰余演算子 `%` (OMOD) の実装を追加するものです。具体的には、`cmd/compile/internal/ssa` パッケージ内で、各種整数型（int8, int16, int32, int64, uint8, uint16, uint32, uint64）に対する剰余演算のサポートが追加されました。これには、SSA中間表現へのマッピング、AMD64アーキテクチャ固有のコード生成、および関連するテストケースの更新が含まれます。

## 変更の背景

Goコンパイラは、パフォーマンスと最適化の向上を目的として、従来のAST (Abstract Syntax Tree) ベースの最適化からSSA (Static Single Assignment) 形式への移行を進めていました。このコミットは、そのSSAバックエンド開発の一環として、これまでSSAで直接サポートされていなかった剰余演算子 `OMOD` を完全に統合することを目的としています。

剰余演算は、プログラミングにおいて頻繁に使用される基本的な算術演算の一つです。SSA形式でこれを適切に表現し、ターゲットアーキテクチャ（この場合はAMD64）のネイティブ命令に効率的にマッピングすることで、コンパイルされたGoプログラムの実行時性能を向上させることができます。特に、整数型の剰余演算は、符号付き整数と符号なし整数で動作が異なるため、それぞれのケースを正確に処理する必要があります。また、除算と同様に、ゼロによる除算や、最小負の整数を-1で除算する際のオーバーフローといったエッジケースへの対応も重要です。

この変更により、Goコンパイラはより多くの算術演算をSSA形式で処理できるようになり、将来的な最適化の基盤が強化されます。

## 前提知識の解説

### Goコンパイラの構造 (SSAバックエンド)

Goコンパイラは、ソースコードを機械語に変換する過程で複数のステージを経ます。
1.  **フロントエンド**: ソースコードの字句解析、構文解析を行い、AST (Abstract Syntax Tree) を生成します。
2.  **ミドルエンド**: ASTに対して型チェック、セマンティック解析、一部の最適化を行います。
3.  **SSA (Static Single Assignment) 形式**: Go 1.7以降、コンパイラの主要な最適化パスはSSA形式に移行しました。SSAは、各変数が一度だけ代入されるようにプログラムを変換する中間表現です。これにより、データフロー解析や最適化が容易になります。
    *   `cmd/compile/internal/gc/ssa.go`: ASTノードをSSAオペレーションにマッピングする役割を担います。
    *   `cmd/compile/internal/ssa`: SSA形式の定義、最適化パス、および機械語へのコード生成を担当するパッケージです。
4.  **バックエンド**: SSA形式からターゲットアーキテクチャ（例: AMD64）の機械語を生成します。

### 剰余演算子 (`%`) の特性

*   **符号付き整数**: Go言語では、`a % b` の結果の符号は `a` の符号と同じになります。例えば、`-5 % 2` は `-1` です。また、最小負の整数を `-1` で除算（または剰余演算）するとオーバーフローが発生する可能性があります（例: `math.MinInt64 % -1`）。これはCPUによっては例外を発生させるため、特別なハンドリングが必要です。
*   **符号なし整数**: 常に非負の結果を返します。オーバーフローの心配はありませんが、ゼロによる除算はランタイムパニックを引き起こします。
*   **AMD64アーキテクチャの除算/剰余命令**:
    *   `DIV` (unsigned divide): 符号なし除算。`RDX:RAX` を `operand` で除算し、商を `RAX` に、剰余を `RDX` に格納します。
    *   `IDIV` (signed divide): 符号付き除算。`RDX:RAX` を `operand` で除算し、商を `RAX` に、剰余を `RDX` に格納します。
    *   これらの命令は、除算の前に `RAX` レジスタの値を拡張する必要があります（例: `CQO` for `DIVQ`/`IDIVQ`）。

### `opToSSA` マップ

Goコンパイラの `gc` パッケージ（ASTをSSAに変換する部分）には、ASTの演算子（`ODIV`, `OMUL` など）と型をSSAのオペレーション（`ssa.OpDiv64`, `ssa.OpMul64` など）にマッピングするための `opToSSA` マップが存在します。

### `genValue` 関数

`genValue` 関数は、SSAの `Value` オブジェクト（SSA中間表現の単一の計算ステップ）を受け取り、それに対応するアセンブリ命令を生成する役割を担います。

## 技術的詳細

このコミットの主要な技術的変更点は、GoコンパイラのSSAバックエンドにおける剰余演算子 `OMOD` の完全なサポートです。

1.  **`opToSSA` マッピングの拡張**:
    *   `src/cmd/compile/internal/gc/ssa.go` 内の `opToSSA` マップに、`OMOD` と各種整数型（`TINT8` から `TUINT64` まで）の組み合わせに対応するSSAオペレーション（`ssa.OpMod8` から `ssa.OpMod64u` まで）が追加されました。これにより、ASTの剰余演算がSSA形式に正しく変換されるようになります。
    *   `expr` 関数内の `switch` 文に `OMOD` が追加され、剰余演算が `newValue2` を通じてSSA値として生成されるようになりました。

2.  **SSAオペレーションの定義**:
    *   `src/cmd/compile/internal/ssa/opGen.go` に、`OpAMD64MODQ`, `OpAMD64MODL`, `OpAMD64MODW` (符号付き) および `OpAMD64MODQU`, `OpAMD64MODLU`, `OpAMD64MODWU` (符号なし) といったAMD64固有の剰余オペレーションが追加されました。
    *   また、ジェネリックなSSAオペレーションとして `OpMod8` から `OpMod64u` までが定義されました。

3.  **AMD64固有のコード生成 (`genValue`)**:
    *   `src/cmd/compile/internal/gc/ssa.go` の `genValue` 関数が更新され、`ssa.OpAMD64MODQ` などの剰余オペレーションに対応するアセンブリ命令を生成するロジックが追加されました。
    *   **符号付き剰余の特殊ハンドリング**: AMD64の `IDIV` 命令は、最小負の整数を `-1` で除算するとオーバーフロー例外を発生させる可能性があります。Go言語の仕様では、このような場合の剰余は `0` と定義されています。このコミットでは、除数 (`y`) が `-1` である場合に、分岐命令 (`AJEQ`) を用いてこのケースを検出し、剰余が `0` になるように `DX` レジスタをクリアする (`AXORQ DX, DX`) 処理が追加されました。これにより、Go言語のセマンティクス（`a % -1` は `0`）が維持され、CPU例外が回避されます。
    *   **符号拡張**: `IDIV` 命令は、被除数 (`AX`) を `DX:AX` レジスタペアに符号拡張する必要があります。`CQO`, `CDQ`, `CWD` 命令が適切に挿入されます。
    *   **符号なし剰余**: 符号なし剰余 (`DIVQ` など) の場合、`DX` レジスタは `0` にクリアされます (`AXORQ DX, DX`)。

4.  **SSAリライトルール (`AMD64.rules`, `rewriteAMD64.go`)**:
    *   `src/cmd/compile/internal/ssa/gen/AMD64.rules` に、ジェネリックな `Mod` オペレーションをAMD64固有の `MODQ`, `MODL`, `MODW` などに変換するルールが追加されました。
    *   `src/cmd/compile/internal/ssa/rewriteAMD64.go` に、これらのリライトルールを実装するGoコードが生成され、`OpMod16` などのSSAオペレーションが `OpAMD64MODW` などのAMD64固有のオペレーションに変換されるようになりました。
    *   `Mod8` および `Mod8u` の場合、8ビット値を16ビットに符号拡張 (`SignExt8to16`) またはゼロ拡張 (`ZeroExt8to16`) してから16ビット剰余演算を行うように変換されます。これは、AMD64の `IDIVW`/`DIVW` が少なくとも16ビットオペランドを必要とするためです。

5.  **テストケースの更新**:
    *   `src/cmd/compile/internal/gc/testdata/arithBoundary_ssa.go` およびその生成スクリプト `src/cmd/compile/internal/gc/testdata/gen/arithBoundaryGen.go` が更新され、各種整数型に対する剰余演算の境界値テストケースが追加されました。これにより、新しいSSA実装がGo言語の仕様に沿って正しく動作することが検証されます。

    ```go

    opAndType{OMOD, TUINT8}:  ssa.OpMod8u,

    opAndType{OMOD, TUINT64}: ssa.OpMod64u,
    ```
*   `expr` 関数内の `switch` 文の `case OADD, OAND, OMUL, OOR, OSUB, ODIV, OXOR, OHMUL:` に `OMOD` が追加されました。
    ```go
    case OADD, OAND, OMUL, OOR, OSUB, ODIV, OMOD, OHMUL, OXOR:
        a := s.expr(n.Left)
        b := s.expr(n.Right)
        return s.newValue2(s.ssaOp(n.Op, n.Type), a.Type, a, b)
    ```
*   `genValue` 関数に、AMD64の剰余命令 (`ssa.OpAMD64MODQ` など) のコード生成ロジックが追加されました。特に、符号付き剰余の `-1` による除算の特殊ケースが処理されています。
    ```go
    case ssa.OpAMD64DIVQ, ssa.OpAMD64DIVL, ssa.OpAMD64DIVW,
        ssa.OpAMD64DIVQU, ssa.OpAMD64DIVLU, ssa.OpAMD64DIVWU,
        ssa.OpAMD64MODQ, ssa.OpAMD64MODL, ssa.OpAMD64MODW,
        ssa.OpAMD64MODQU, ssa.OpAMD64MODLU, ssa.OpAMD64MODWU:
        // ...
        if v.Op == ssa.OpAMD64DIVQ || v.Op == ssa.OpAMD64DIVL ||
            v.Op == ssa.OpAMD64DIVW || v.Op == ssa.OpAMD64MODQ ||
            v.Op == ssa.OpAMD64MODL || v.Op == ssa.OpAMD64MODW {
            // ... CPU faults upon signed overflow, which occurs when most
            // negative int is divided by -1.
            // ...
            // If divisor is -1, then remainder is 0.
            // For signed modulo, if divisor is -1, result is 0.
            // For signed division, if divisor is -1, result is -n.
            // This is handled by setting DX to 0 for modulo, and negating AX for division.
            // ...
        }
        // ...
        // for unsigned ints, we sign extend by setting DX = 0
        // signed ints were sign extended above
        if v.Op == ssa.OpAMD64DIVQU || v.Op == ssa.OpAMD64MODQU ||
            v.Op == ssa.OpAMD64DIVLU || v.Op == ssa.OpAMD64MODLU ||
            v.Op == ssa.OpAMD64DIVWU || v.Op == ssa.OpAMD64MODWU {
            c := Prog(x86.AXORQ)
            c.From.Type = obj.TYPE_REG
            c.From.Reg = x86.REG_DX
            c.To.Type = obj.TYPE_REG
            c.To.Reg = x86.REG_DX
        }
        // ...
        if v.Op == ssa.OpAMD64DIVQ || v.Op == ssa.OpAMD64DIVL ||
            v.Op == ssa.OpAMD64DIVW {
            // n * -1 = -n
            n = Prog(x86.ANEGQ)
            n.To.Type = obj.TYPE_REG
            n.To.Reg = x86.REG_AX
        } else {
            // n % -1 == 0
            n = Prog(x86.AXORQ)
            n.From.Type = obj.TYPE_REG
            n.From.Reg = x86.REG_DX
            n.To.Type = obj.TYPE_REG
            n.To.Reg = x86.REG_DX
        }
    ```

## コアとなるコードの解説

このコミットの核心は、GoコンパイラのSSA中間表現とAMD64バックエンドにおける剰余演算の統合です。

1.  **ASTからSSAへの変換 (`src/cmd/compile/internal/gc/ssa.go`)**:
    *   `opToSSA` マップは、Go言語のソースコードで書かれた `a % b` のような式が、コンパイラの内部でどのように表現されるかを決定します。このコミットにより、`OMOD` というAST演算子が、具体的な型（例: `int64`）と組み合わされて `ssa.OpMod64` のようなSSAオペレーションに変換されるようになりました。これは、コンパイラが剰余演算をSSA形式で認識し、処理するための最初のステップです。
    *   `expr` 関数は、ASTを走査し、各ノードに対応するSSA値を生成します。`OMOD` が `case` 文に追加されたことで、剰余演算も他の二項演算子と同様にSSA値として扱われるようになります。

2.  **AMD64固有のコード生成 (`genValue` in `src/cmd/compile/internal/gc/ssa.go`)**:
    *   `genValue` 関数は、SSAオペレーションを実際の機械語命令に変換する部分です。AMD64アーキテクチャでは、剰余演算は除算命令 (`IDIV` または `DIV`) の副産物として得られます。これらの命令は、商を `AX` レジスタに、剰余を `DX` レジスタに格納します。
    *   **符号付き剰余の特殊ケース**: `IDIV` 命令は、`math.MinInt64 / -1` のような特定のケースでCPU例外（除算エラー）を引き起こす可能性があります。Go言語の仕様では、このような場合の剰余は `0` と定義されています。このコミットでは、除数が `-1` であることを検出し、`DX` レジスタを `0` に設定することで、この例外を回避し、Goのセマンティクスに合致する結果を生成しています。これは、コンパイラが言語仕様とハードウェアの特性の両方を考慮してコードを生成する良い例です。
    *   **レジスタの準備**: `IDIV`/`DIV` 命令は、被除数を `DX:AX` レジスタペアに配置することを要求します。`genValue` は、`CQO` (QuadwordをOctwordに変換、`RAX` を `RDX:RAX` に符号拡張), `CDQ` (DoublewordをQuadwordに変換), `CWD` (WordをDoublewordに変換) といった命令を適切に挿入し、正しい符号拡張が行われるようにします。符号なし除算の場合は、`DX` を `0` にクリアします。

3.  **SSAリライトルール (`AMD64.rules`, `rewriteAMD64.go`)**:
    *   SSAリライトルールは、より抽象的なSSAオペレーションを、ターゲットアーキテクチャのより具体的な、あるいはより効率的なオペレーションに変換するために使用されます。例えば、`Mod64` というジェネリックな剰余オペレーションは、AMD64では `MODQ` という特定のオペレーションに変換されます。
    *   8ビット整数に対する剰余演算 (`Mod8`, `Mod8u`) の場合、AMD64の `IDIVW`/`DIVW` 命令は16ビットオペランドを扱うため、8ビット値を16ビットに拡張する必要があります。`SignExt8to16` (符号拡張) や `ZeroExt8to16` (ゼロ拡張) といった中間オペレーションが挿入され、正しい型変換が行われるようにします。これにより、コンパイラは異なるビット幅の整数型に対しても、適切なアセンブリ命令を生成できます。

これらの変更は、Goコンパイラが剰余演算を効率的かつ正確に処理するための基盤を構築し、Goプログラムの実行時性能と正確性を保証する上で重要な役割を果たします。

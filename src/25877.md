# [インデックス 25877] ファイルの概要

このコミットは、Go言語の `archive/zip` パッケージにおいて、ZIPアーカイブのファイルごとに圧縮・解凍アルゴリズムをオーバーライドする機能を追加します。これにより、特定のファイルに対して異なる圧縮レベルやカスタムの圧縮・解凍ロジックを適用できるようになります。

## 元コミット内容

`archive/zip`: ファイルごとの(デ)コンプレッサーのオーバーライドを有効にする

`Writer.RegisterCompressor` を通じてファイルごとのコンプレッサーを登録することで、ZIPアーカイブの圧縮レベルを設定する機能を実装します。コンプレッサーが登録されていない場合は、パッケージレベルで登録されているものにフォールバックします。また、ファイルごとのデコンプレッサーも実装します。

Fixes #8359

## 変更の背景

この変更の背景には、Go言語の `archive/zip` パッケージが、ZIPアーカイブ内の個々のファイルに対して、デフォルトの圧縮・解凍アルゴリズムや圧縮レベルを柔軟に制御できないという課題がありました。以前は、パッケージ全体で設定されたグローバルなコンプレッサー/デコンプレッサーが使用されるか、ZIPヘッダーで指定された標準的なメソッド（例: Deflate）が使われるのみでした。

しかし、特定のユースケースでは、以下のような要件が生じます。

1.  **異なる圧縮レベルの適用**: 例えば、テキストファイルは `BestCompression` で圧縮し、画像ファイルは `NoCompression` または `FastestCompression` で圧縮するなど、ファイルの種類や重要度に応じて圧縮レベルを調整したい場合があります。これにより、アーカイブのサイズと圧縮・解凍速度のバランスを最適化できます。
2.  **カスタム圧縮アルゴリズムの利用**: 標準のDeflate以外のカスタム圧縮アルゴリズムを使用したい場合や、特定のデータ形式に特化した独自の圧縮ロジックを適用したい場合があります。
3.  **パフォーマンスの最適化**: 圧縮・解凍処理はCPUリソースを消費するため、特に大規模なアーカイブを扱う場合、ファイルごとに最適なアルゴリズムを選択することで、全体のパフォーマンスを向上させることができます。

Issue #8359 は、まさにこのような柔軟性の欠如を指摘しており、このコミットはその問題を解決するために導入されました。この変更により、開発者は `Writer` および `Reader` インスタンスに対して、ファイルごとにカスタムのコンプレッサー/デコンプレッサーを登録できるようになり、よりきめ細やかな制御が可能になりました。

## 前提知識の解説

### ZIPファイルフォーマット

ZIPファイルは、複数のファイルを1つのアーカイブにまとめるための一般的なファイルフォーマットです。各ファイルは個別に圧縮され、メタデータ（ファイル名、更新日時、圧縮方法など）と共に格納されます。ZIPファイルは、中央ディレクトリと呼ばれる構造を持ち、アーカイブ内のすべてのファイルのエントリ情報が記録されています。

### 圧縮アルゴリズム (Deflate)

ZIPファイルで最も一般的に使用される圧縮アルゴリズムは「Deflate」です。Deflateは、LZ77アルゴリズムとハフマン符号化を組み合わせたもので、データ内の繰り返しパターンを見つけて置き換えることで、効率的な圧縮を実現します。Go言語の `compress/flate` パッケージは、このDeflateアルゴリズムの実装を提供しています。

### コンプレッサーとデコンプレッサー

-   **コンプレッサー (Compressor)**: 入力データを受け取り、それを圧縮された形式で出力する機能を持つコンポーネントです。ZIPアーカイブを作成する際には、各ファイルのデータをコンプレッサーに通して圧縮します。
-   **デコンプレッサー (Decompressor)**: 圧縮されたデータを受け取り、それを元の非圧縮形式に戻す機能を持つコンポーネントです。ZIPアーカイブからファイルを読み出す際には、デコンプレッサーに通してデータを復元します。

Goの `archive/zip` パッケージでは、これらのコンプレッサーとデコンプレッサーは `io.Writer` および `io.Reader` インターフェースをラップする形で実装されます。具体的には、`Compressor` は `io.Writer` を受け取り `io.WriteCloser` を返す関数型、`Decompressor` は `io.Reader` を受け取り `io.ReadCloser` を返す関数型として定義されています。

### `io.Writer` と `io.Reader` インターフェース

Go言語の `io` パッケージは、I/O操作のための基本的なインターフェースを提供します。
-   `io.Writer`: `Write([]byte) (n int, err error)` メソッドを持つインターフェースで、データを書き込む操作を抽象化します。
-   `io.Reader`: `Read([]byte) (n int, err error)` メソッドを持つインターフェースで、データを読み込む操作を抽象化します。
-   `io.WriteCloser` / `io.ReadCloser`: それぞれ `io.Writer` / `io.Reader` に加えて `Close() error` メソッドを持つインターフェースで、リソースの解放が必要なI/Oストリームによく使われます。

これらのインターフェースを理解することは、GoのI/O処理、特に圧縮・解凍ストリームのパイプラインを理解する上で不可欠です。

## 技術的詳細

このコミットの主要な技術的変更点は、`archive/zip` パッケージの `Writer` および `Reader` 型に、ファイルごとのコンプレッサー/デコンプレッサーを登録・管理するためのメカニズムが追加されたことです。

### `zip.Writer` の変更点

1.  **`compressors` フィールドの追加**:
    `Writer` 構造体に `compressors map[uint16]Compressor` という新しいフィールドが追加されました。`uint16` はZIP圧縮メソッドID（例: `zip.Deflate`）を表し、`Compressor` はカスタムのコンプレッサーファクトリ関数です。このマップは、特定のメソッドIDに対応するカスタムコンプレッサーを格納するために使用されます。

2.  **`RegisterCompressor` メソッドの追加**:
    `func (w *Writer) RegisterCompressor(method uint16, comp Compressor)` メソッドが追加されました。このメソッドを使用すると、ユーザーは特定の圧縮メソッドIDに対して独自の `Compressor` 関数を登録できます。これにより、`Writer` はアーカイブにファイルを追加する際に、登録されたカスタムコンプレッサーを使用できるようになります。

3.  **`compressor` ヘルパーメソッドの追加**:
    `func (w *Writer) compressor(method uint16) Compressor` という内部ヘルパーメソッドが追加されました。このメソッドは、まず `Writer` の `compressors` マップから指定されたメソッドIDに対応するコンプレッサーを探します。見つからない場合は、パッケージレベルで登録されているデフォルトのコンプレッサーにフォールバックします。これにより、カスタムコンプレッサーが登録されていない場合でも、既存の動作が維持されます。

### `zip.Reader` の変更点

1.  **`decompressors` フィールドの追加**:
    `Reader` 構造体に `decompressors map[uint16]Decompressor` という新しいフィールドが追加されました。これは `Writer` の `compressors` と同様に、特定のメソッドIDに対応するカスタムデコンプレッサーを格納します。

2.  **`RegisterDecompressor` メソッドの追加**:
    `func (z *Reader) RegisterDecompressor(method uint16, dcomp Decompressor)` メソッドが追加されました。これにより、ユーザーは特定の圧縮メソッドIDに対して独自の `Decompressor` 関数を登録でき、`Reader` はアーカイブからファイルを読み出す際にカスタムデコンプレッサーを使用できます。

3.  **`decompressor` ヘルパーメソッドの追加**:
    `func (z *Reader) decompressor(method uint16) Decompressor` という内部ヘルパーメソッドが追加されました。これも `Writer` の `compressor` と同様に、まず `Reader` の `decompressors` マップからカスタムデコンプレッサーを探し、見つからない場合はパッケージレベルのデフォルトにフォールバックします。

4.  **`File` 構造体の変更**:
    `File` 構造体に `zip *Reader` フィールドが追加されました。これにより、`File` オブジェクトが属する `Reader` インスタンスへの参照を持つことができるようになり、`File.Open()` メソッド内でその `Reader` インスタンスに登録されたカスタムデコンプレッサーを呼び出すことが可能になります。以前は、`File.Open()` はグローバルな `decompressor` 関数を直接呼び出していました。

これらの変更により、`Writer` と `Reader` の各インスタンスが、それぞれ独立したカスタムコンプレッサー/デコンプレッサーのセットを持つことができるようになり、ファイルごとの柔軟な圧縮・解凍処理が実現されます。

## コアとなるコードの解説

### `zip.Writer` と `RegisterCompressor`

`zip.Writer` はZIPアーカイブを書き込むための主要な構造体です。このコミットにより、`Writer` インスタンスは `compressors` というマップを持つようになりました。このマップは、特定の圧縮メソッドID（例: `zip.Deflate`）に対応するカスタムの `Compressor` 関数を保持します。

`RegisterCompressor` メソッドは、このマップにエントリを追加するために使用されます。例えば、`flate.BestCompression` を使用するカスタムDeflateコンプレッサーを登録するには、以下のように記述します。

```go
w := zip.NewWriter(buf)
w.RegisterCompressor(zip.Deflate, func(out io.Writer) (io.WriteCloser, error) {
    // flate.NewWriter は io.Writer を受け取り io.WriteCloser を返す
    return flate.NewWriter(out, flate.BestCompression)
})
```

`Writer.CreateHeader` が呼び出され、新しいファイルエントリが作成される際、内部的に `w.compressor(fh.Method)` が呼び出されます。このヘルパー関数は、まず `w.compressors` マップをチェックし、カスタムコンプレッサーが登録されていればそれを使用します。登録されていなければ、パッケージレベルで定義されているデフォルトのコンプレッサー（通常は `zip.Deflate` の標準実装など）にフォールバックします。これにより、ユーザーは必要に応じて特定の圧縮メソッドの動作をオーバーライドできる一方で、デフォルトの動作も維持されます。

### `zip.Reader` と `RegisterDecompressor`

`zip.Reader` は既存のZIPアーカイブを読み込むための構造体です。`Writer` と同様に、`Reader` も `decompressors` というマップを持つようになりました。

`RegisterDecompressor` メソッドは、このマップにカスタムの `Decompressor` 関数を登録するために使用されます。

```go
r, err := zip.NewReader(readerAt, size)
if err != nil {
    log.Fatal(err)
}
r.RegisterDecompressor(zip.Deflate, func(r io.Reader) (io.ReadCloser, error) {
    // カスタムのDeflateデコンプレッサーを返す
    return flate.NewReader(r), nil
})
```

`File.Open()` メソッドが呼び出され、アーカイブ内のファイルの内容を読み出すための `io.ReadCloser` が取得される際、内部的に `f.zip.decompressor(f.Method)` が呼び出されます。ここで `f.zip` は、`File` が属する `Reader` インスタンスへの参照です。このヘルパー関数も、`Reader` の `decompressors` マップをチェックし、カスタムデコンプレッサーがあればそれを使用し、なければパッケージレベルのデフォルトにフォールバックします。

`File` 構造体に `zip *Reader` フィールドが追加されたのは、`File` が自身のデコンプレッションに必要なコンテキスト（つまり、親 `Reader` インスタンスに登録されたカスタムデコンプレッサー）にアクセスできるようにするためです。これにより、`File.Open()` はグローバルなデコンプレッサーではなく、その `Reader` インスタンスに固有のデコンプレッサーを使用できるようになります。

これらの変更により、`archive/zip` パッケージは、より高度なカスタマイズ性と柔軟性を提供し、特定のアプリケーション要件に合わせて圧縮・解凍処理を最適化できるようになりました。

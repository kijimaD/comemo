# [インデックス 21547] ファイルの概要

このコミットは、Goランタイムにおけるゴルーチンのプリエンプション（横取り）処理に関する競合状態（race condition）を修正するものです。具体的には、`gp.stackguard0`というスタックガード値のチェックが複数回行われる際に発生する可能性のある競合を解消し、不正確なプリエンプションを防ぎます。これにより、OS XおよびSolaris環境でのビルドの不安定性が解消されることが期待されています。

## 元コミット内容

```
runtime: avoid race checking for preemption

Moving the "don't really preempt" check up earlier in the function
introduced a race where gp.stackguard0 might change between
the early check and the later one. Since the later one is missing the
"don't really preempt" logic, it could decide to preempt incorrectly.
Pull the result of the check into a local variable and use an atomic
to access stackguard0, to eliminate the race.

I believe this will fix the broken OS X and Solaris builders.
```

## 変更の背景

Goランタイムは、実行中のゴルーチンがCPUを占有しすぎないように、プリエンプション（横取り）機構を備えています。これは、長時間実行されるゴルーチンが他のゴルーチンの実行を妨げないようにするために重要です。プリエンプションは、ゴルーチンのスタックの末尾に設定される「スタックガード」と呼ばれる特殊な値を利用して行われます。

このコミット以前のコードでは、プリエンプションを行うかどうかを判断する際に、`gp.stackguard0`という値を複数回チェックしていました。しかし、この`gp.stackguard0`は、別のスレッド（M: Machine）が同じゴルーチン（G: Goroutine）をプリエンプトしようとしている場合など、非同期的に変更される可能性があります。

問題は、プリエンプションのチェックロジックが関数内で移動されたことにより発生しました。初期のチェックと後続のチェックの間で`gp.stackguard0`の値が変更される競合状態が発生し、その結果、ランタイムが誤ってプリエンプションを実行してしまう可能性がありました。特に、後続のチェックでは「実際にプリエンプトしない」というロジックが欠けていたため、この競合が顕在化し、OS XやSolarisといった特定の環境でビルドが不安定になるという問題を引き起こしていました。

この変更は、この競合状態を解消し、ランタイムの安定性を向上させることを目的としています。

## 前提知識の解説

*   **Goランタイム**: Goプログラムの実行を管理するシステム。ゴルーチン、スケジューラ、メモリ管理（GC）などが含まれます。
*   **ゴルーチン (Goroutine)**: Goにおける軽量な実行スレッド。OSのスレッドよりもはるかに軽量で、数百万個を同時に実行することも可能です。
*   **M (Machine)**: OSのスレッドに相当し、Goランタイムのスケジューラによってゴルーチンを実行します。
*   **P (Processor)**: 論理的なCPUコアに相当し、Mとゴルーチンを仲介します。MはPにアタッチされ、Pのローカルキューからゴルーチンを取得して実行します。
*   **プリエンプション (Preemption)**: 実行中のゴルーチンを強制的に中断し、別のゴルーチンにCPUの実行権を渡すメカニズム。これにより、すべてのゴルーチンが公平にCPU時間を得られるようになります。Goでは、主に協調的プリエンプションと非同期プリエンプション（シグナルベース）が組み合わされて利用されます。
*   **スタックガード (Stack Guard)**: 各ゴルーチンのスタックの末尾に配置される特殊な値。スタックがこのガード領域に近づくと、スタックの拡張が必要であることをランタイムに通知します。プリエンプションの文脈では、このスタックガード領域に特定の値を設定することで、ランタイムがゴルーチンをプリエンプトするトリガーとして利用します。
*   **`gp.stackguard0`**: `g`構造体（ゴルーチンを表す構造体）のフィールドの一つで、スタックガードの値を保持します。この値が`stackPreempt`に設定されている場合、そのゴルーチンはプリエンプションの対象であることを示します。
*   **競合状態 (Race Condition)**: 複数のスレッドが共有リソース（この場合は`gp.stackguard0`）に同時にアクセスし、そのアクセス順序によって結果が非決定的に変わってしまう状態。予期せぬ動作やバグの原因となります。
*   **アトミック操作 (Atomic Operations)**: 複数のCPUコアやスレッドから同時にアクセスされても、その操作が中断されずに完全に実行されることが保証される操作。これにより、競合状態を防ぎ、データの一貫性を保ちます。`atomicloaduintptr`は、`uintptr`型の値をアトミックに読み込む関数です。

## 技術的詳細

このコミットが修正する問題は、Goランタイムの`newstack()`関数内で発生していました。`newstack()`は、ゴルーチンのスタックが不足した際に新しいスタックを割り当てたり、プリエンプションの処理を行ったりする重要な関数です。

以前のコードでは、`newstack()`内でプリエンプションの条件をチェックする際に、`gp.stackguard0 == stackPreempt`という比較を複数回行っていました。

1.  **初期のチェック**: `newstack()`関数の比較的早い段階で、プリエンプションの意図があるかどうか（`gp.stackguard0 == stackPreempt`）を確認していました。このチェックには、「実際にプリエンプトすべきでない」という追加のロジック（例：ランタイムがロックを保持している、GC中であるなど）が含まれていました。
2.  **後続のチェック**: 関数内のさらに後続の場所でも、再度`gp.stackguard0 == stackPreempt`のチェックが行われていました。しかし、この後続のチェックには、初期のチェックに含まれていた「実際にプリエンプトしない」という追加ロジックが欠けていました。

問題は、初期のチェックと後続のチェックの間で、別のM（OSスレッド）がこのゴルーチンをプリエンプトしようとして`gp.stackguard0`の値を`stackPreempt`に変更する可能性があるという点です。もしこのような変更が発生した場合、初期のチェックでは「プリエンプトしない」と判断されたにもかかわらず、後続のチェックでは`gp.stackguard0`が`stackPreempt`になっているため、追加ロジックなしにプリエンプションが実行されてしまう可能性がありました。これは、ランタイムが予期しないタイミングでゴルーチンをプリエンプトすることになり、デッドロックやクラッシュなどの不安定な動作を引き起こす原因となります。特に、GCが特定のゴルーチンに依存している場合（例：ゴルーチンが保持しているロックが必要な場合）に誤ったプリエンプションが発生すると、深刻なデッドロックにつながる可能性がありました。

この修正は、この競合状態を解消するために、`gp.stackguard0`の値を一度だけアトミックに読み込み、その値をローカル変数に保存して再利用するというアプローチを取っています。これにより、複数のチェック間で値が変化する可能性がなくなり、一貫したプリエンプション判断が可能になります。

## コアとなるコードの解説

変更の核心は、`newstack()`関数の冒頭近くに以下の行が追加されたことです。

```go
	// NOTE: stackguard0 may change underfoot, if another thread
	// is about to try to preempt gp. Read it just once and use that same
	// value now and below.
	preempt := atomicloaduintptr(&gp.stackguard0) == stackPreempt
```

1.  **`atomicloaduintptr(&gp.stackguard0)`**: ここで`gp.stackguard0`の値がアトミックに読み込まれます。アトミック操作を使用することで、他のスレッドが同時に`gp.stackguard0`を書き換えようとしても、この読み込み操作が中断されることなく完了することが保証されます。これにより、読み取られた値が常に一貫性のあるものとなります。
2.  **`== stackPreempt`**: 読み込まれた`gp.stackguard0`の値が`stackPreempt`（プリエンプションが必要であることを示す特殊な値）と等しいかどうかがチェックされます。
3.  **`preempt := ...`**: このチェックの結果（`true`または`false`）が`preempt`という新しいローカル変数に格納されます。

そして、`newstack()`関数内の後続の`if`文では、直接`gp.stackguard0`を再度参照する代わりに、この`preempt`ローカル変数が使用されるように変更されました。

```go
-	if gp.stackguard0 == stackPreempt {
+	if preempt {
```

この変更により、`gp.stackguard0`の値は関数内で一度だけ、しかもアトミックに読み込まれるため、その後のプリエンプション判断ロジック全体で一貫した値が使用されるようになります。これにより、初期のチェックと後続のチェックの間で`gp.stackguard0`が変更されることによる競合状態が完全に解消され、誤ったプリエンプションが防止されます。結果として、Goランタイムの安定性が向上し、特にOS XやSolarisのような特定の環境で発生していたビルドの不安定性が修正されることになります。

2.  **`== stackPreempt`**: 読み込まれた`gp.stackguard0`の値が`stackPreempt`（プリエンプションが必要であることを示す特殊な値）と等しいかどうかがチェックされます。
3.  **`preempt := ...`**: このチェックの結果（`true`または`false`）が`preempt`という新しいローカル変数に格納されます。

そして、`newstack()`関数内の後続の`if`文では、直接`gp.stackguard0`を再度参照する代わりに、この`preempt`ローカル変数が使用されるように変更されました。

```go
-	if gp.stackguard0 == stackPreempt {
+	if preempt {
```

この変更により、`gp.stackguard0`の値は関数内で一度だけ、しかもアトミックに読み込まれるため、その後のプリエンプション判断ロジック全体で一貫した値が使用されるようになります。これにより、初期のチェックと後続のチェックの間で`gp.stackguard0`が変更されることによる競合状態が完全に解消され、誤ったプリエンプションが防止されます。結果として、Goランタイムの安定性が向上し、特にOS XやSolarisのような特定の環境で発生していたビルドの不安定性が修正されることになります。

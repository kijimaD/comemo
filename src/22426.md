## 変更の背景

このコミットは、Go言語の`debug/elf`パッケージが32ビットPowerPC (PPC) アーキテクチャのELFオブジェクトファイルからデバッグ情報を正しく読み取れないという問題に対処するために行われました。コミットメッセージにある「Fixes #10118」は、この問題がGoプロジェクトの内部課題追跡システムで報告されていたことを示唆しています。

ELF (Executable and Linkable Format) ファイルは、プログラムの実行可能ファイル、オブジェクトコード、共有ライブラリ、コアダンプなどを格納するための標準的なファイル形式です。デバッグ情報（通常はDWARF形式で格納される）は、デバッガがソースコードレベルでプログラムの実行を追跡するために不可欠です。

Goのツールチェーンが32ビットPPCプラットフォームで生成されたバイナリのデバッグ情報を適切に処理できない場合、そのプラットフォームでの開発やデバッグが困難になります。このコミットは、`debug/elf`パッケージに32ビットPPC固有のリロケーション（再配置）処理ロジックを追加することで、このギャップを埋め、Goがより多くのアーキテクチャとファイル形式をサポートできるようにすることを目的としています。

## 前提知識の解説

### ELF (Executable and Linkable Format)

ELFは、Unix系システムで広く使用されている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、そして様々なセクション（.text, .data, .rodata, .symtab, .strtab, .debugなど）で構成されます。`debug/elf`パッケージは、GoプログラムがこれらのELFファイルを解析し、その内容にアクセスするための機能を提供します。

### DWARF (Debugging With Attributed Record Formats)

DWARFは、ソースレベルデバッガがプログラムの実行をデバッグするために必要な情報（変数名、型情報、関数名、行番号とアドレスのマッピングなど）を格納するための標準的なデバッグ情報フォーマットです。ELFファイル内の`.debug_*`セクションに格納されることが一般的です。

### リロケーション (Relocation)

リロケーションとは、コンパイル時やリンク時に、プログラム内のシンボル参照（変数や関数のアドレスなど）を、最終的な実行時のメモリ位置に合わせて調整するプロセスです。オブジェクトファイルは通常、特定のアドレスにロードされることを前提とせずに生成されるため、リンカが最終的なアドレスを決定した後に、これらの参照を「再配置」する必要があります。

リロケーションエントリは、どのシンボルを、どのタイプのリロケーションで、どこに適用するかを記述します。リロケーションタイプはアーキテクチャ固有であり、例えば32ビットPPCでは`R_PPC_ADDR32`のようなタイプが存在します。

### PowerPC (PPC) アーキテクチャ

PowerPCは、IBM、Motorola (現NXP Semiconductors)、Appleによって開発されたRISC (Reduced Instruction Set Computer) アーキテクチャです。組み込みシステムからスーパーコンピュータまで幅広い分野で使用されています。このコミットでは、特に32ビット版のPowerPCアーキテクチャで生成されたELFオブジェクトファイルが対象となっています。

## 技術的詳細

このコミットの核心は、Goの`debug/elf`パッケージに32ビットPowerPC (PPC) 用のリロケーション処理ロジックを追加することです。

`src/debug/elf/file.go`内の`File`構造体には、ELFファイルを解析し、その中の情報を読み取るためのメソッド群が含まれています。特に重要なのは`applyRelocations`メソッドで、これはELFファイル内のリロケーションセクションを処理し、指定されたバイトスライス（通常はデバッグ情報が格納されているセクションの生データ）にリロケーションを適用します。

変更前は、`applyRelocations`メソッドはARM、ARM64、PPC64アーキテクチャのリロケーションを処理するケースを持っていましたが、32ビットPPC (EM_PPC) のリロケーションはサポートしていませんでした。

このコミットでは、以下の主要な変更が導入されました。

1.  **`applyRelocations`メソッドへのPPC32ケースの追加**:
    `applyRelocations`メソッドの`switch`文に、`f.Class == ELFCLASS32 && f.Machine == EM_PPC`の場合の新しいケースが追加されました。これにより、32ビットPPCのELFファイルが検出された際に、新しく追加される`applyRelocationsPPC`関数が呼び出されるようになります。

2.  **`applyRelocationsPPC`関数の新規追加**:
    この関数は、32ビットPPC固有のリロケーションを処理するためのロジックを実装しています。
    -   リロケーションセクションの長さが`Rela32`構造体のサイズ（12バイト）の倍数であることを確認します。
    -   ELFファイルからシンボルテーブルを取得します。リロケーションはシンボルを参照するため、これは必須です。
    -   リロケーションエントリを一つずつ読み込みます。各エントリは`Rela32`構造体として解析されます。
    -   リロケーションタイプ（`t`）とシンボル番号（`symNo`）を抽出します。
    -   現在のところ、セクションシンボルに対するリロケーションのみを処理します。非セクションリロケーションはスキップされます。
    -   `R_PPC_ADDR32`タイプのリロケーションを処理します。このタイプは、32ビットのアドレスを直接書き込むリロケーションです。`rela.Addend`（加算値）を`dst`バイトスライスの`rela.Off`（オフセット）位置に32ビット値として書き込みます。

3.  **テストケースの追加**:
    `src/debug/elf/file_test.go`に、32ビットPPCオブジェクトファイル（`testdata/go-relocation-test-gcc5-ppc.obj`）を使用した新しいテストケースが追加されました。このテストは、Goの`debug/elf`パッケージがこの新しいタイプのファイルからDWARFデバッグ情報を正しく読み取れることを検証します。具体的には、コンパイルユニットの属性（プロデューサー、言語、名前、コンパイルディレクトリ、PC範囲など）が期待通りに解析されるかを確認しています。

これらの変更により、Goの`debug/elf`パッケージは、32ビットPPCプラットフォームで生成されたELFバイナリに含まれるデバッグ情報を、リロケーションを適切に適用しながら読み取ることができるようになりました。これは、Goのクロスプラットフォームデバッグ能力を向上させる上で重要なステップです。

## コアとなるコードの解説

### `src/debug/elf/file.go`の変更

`applyRelocations`関数は、ELFファイルのクラス（32ビットか64ビットか）とマシンアーキテクチャに基づいて、適切なリロケーション適用関数をディスパッチする役割を担っています。

追加された行:
```go
	case f.Class == ELFCLASS32 && f.Machine == EM_PPC:
		return f.applyRelocationsPPC(dst, rels)
```
この`case`文は、ELFファイルが32ビットクラス (`ELFCLASS32`) であり、かつPowerPCアーキテクチャ (`EM_PPC`) である場合に、新しく定義された`applyRelocationsPPC`関数を呼び出すように指示しています。これにより、Goの`debug/elf`パッケージは、この特定のアーキテクチャとクラスの組み合わせに対して、カスタムのリロケーション処理を実行できるようになります。

新しく追加された`applyRelocationsPPC`関数は以下の処理を行います。

1.  **リロケーションセクションの検証**:
    `if len(rels)%12 != 0`で、入力されたリロケーションデータ`rels`の長さが12の倍数であることを確認しています。これは、32ビットPPCのリロケーションエントリ（`Rela32`構造体）が12バイトの固定長を持つためです。これにより、不正なデータ形式を早期に検出します。

2.  **シンボルテーブルの取得**:
    `symbols, _, err := f.getSymbols(SHT_SYMTAB)`により、ELFファイルからシンボルテーブルを取得します。リロケーションは通常、特定のシンボル（関数、変数、セクションなど）を参照するため、このシンボル情報が必要です。

3.  **リロケーションの反復処理**:
    `for b.Len() > 0`ループで、リロケーションデータ`rels`を`bytes.NewReader`でラップし、`binary.Read`を使って`Rela32`構造体として一つずつ読み込みます。

4.  **シンボル番号とリロケーションタイプの抽出**:
    `symNo := rela.Info >> 8`でシンボル番号を、`t := R_PPC(rela.Info & 0xff)`でリロケーションタイプを抽出しています。`rela.Info`フィールドは、シンボル番号とリロケーションタイプをパックして格納しています。

5.  **シンボルの検証とフィルタリング**:
    `if symNo == 0 || symNo > uint32(len(symbols))`でシンボル番号の有効性をチェックし、`if SymType(sym.Info&0xf) != STT_SECTION`で、現在のところセクションシンボルに対するリロケーションのみを処理することを明示しています。これは、デバッグ情報のコンテキストではセクションへのリロケーションが一般的であるため、初期実装としては妥当な範囲です。

6.  **`R_PPC_ADDR32`リロケーションの適用**:
    `switch t`文の中で、`case R_PPC_ADDR32:`が最も重要な部分です。
    -   `R_PPC_ADDR32`は、32ビットのアドレスを直接書き込むリロケーションタイプです。
    -   `if rela.Off+4 >= uint32(len(dst)) || rela.Addend < 0`で、書き込み範囲が`dst`スライスの境界内にあるか、および`Addend`が負でないかを確認しています。
    -   `f.ByteOrder.PutUint32(dst[rela.Off:rela.Off+4], uint32(rela.Addend))`により、`dst`バイトスライスの`rela.Off`から4バイトの領域に、`rela.Addend`の値を32ビット符号なし整数として書き込んでいます。`f.ByteOrder`はELFファイルのエンディアン（バイト順）に従って書き込みを行います。

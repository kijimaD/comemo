## 変更の背景

Go言語のランタイムは、ガベージコレクション（GC）によってメモリ管理を行いますが、GCの頻度や一時的なオブジェクトの生成は、アプリケーションのパフォーマンスに大きな影響を与えます。特に、ネットワーク通信や暗号化処理のような高頻度で実行されるコードパスでは、わずかなメモリ割り当ても積み重なると、GCの負荷を増大させ、レイテンシの増加やスループットの低下を招きます。

このコミットの背景には、`crypto/tls` パッケージにおけるTLSハンドシェイク後のデータ送受信（レコード層の暗号化・復号化）において、不要なヒープメモリ割り当てが発生しているという問題がありました。具体的には、AES-GCMモードの認証付き暗号化で使用される「追加認証データ (Additional Authenticated Data, AAD)」を構築するための一時的なバイトスライスが、各暗号化・復号化操作のたびにヒープに割り当てられていました。

このコミットは、これらのヒープ割り当てを排除し、スタック上でのデータ利用や構造体フィールドとしての再利用を促進することで、TLS通信のオーバーヘッドを削減し、全体的なパフォーマンスを向上させることを目的としています。ベンチマーク結果が示すように、1操作あたりのメモリ割り当てをゼロにすることで、処理速度が約7.39%向上し、スループットが1.08倍に改善されています。

## 前提知識の解説

### 1. Goのメモリ割り当てとエスケープ解析 (Escape Analysis)

Go言語では、変数がヒープに割り当てられるかスタックに割り当てられるかをコンパイラが自動的に判断します。このプロセスを「エスケープ解析」と呼びます。
*   **スタック割り当て:** 関数内で宣言され、その関数の実行が終了すると不要になる変数は、通常スタックに割り当てられます。スタック割り当ては高速で、GCの対象外です。
*   **ヒープ割り当て:** 変数が関数のスコープを超えて参照される可能性がある場合（例: ポインタが返される、グローバル変数に代入される、インターフェース型に変換されるなど）、その変数はヒープに割り当てられます。ヒープ割り当てはスタック割り当てよりも遅く、GCの対象となり、GCの負荷を増大させます。

エスケープ解析は非常に賢明ですが、時にはコンパイラが保守的に判断し、実際にはスタックで済むはずの変数をヒープに割り当ててしまうことがあります。特に、インターフェース型を介して関数に渡されるデータは、コンパイラがそのデータの寿命を正確に追跡できないため、ヒープにエスケープしやすい傾向があります。

### 2. `//go:noescape` ディレクティブ

`//go:noescape` は、Goコンパイラに対する特別な指示（プラグマ）です。このディレクティブが関数宣言の直前に記述されている場合、コンパイラはその関数の引数がヒープにエスケープしないと仮定します。これは、通常アセンブリ言語で実装された関数（例: `crypto/aes` のようなパフォーマンスが重要な部分）で使用され、コンパイラがGoコードからアセンブリ関数を呼び出す際に、引数をスタックに保持できることを保証するために利用されます。これにより、アセンブリ関数が内部でポインタを操作しても、Goのメモリモデルと整合性を保ちつつ、ヒープ割り当てを回避できます。

### 3. TLS (Transport Layer Security) プロトコル

TLSは、インターネット上で安全な通信を提供するための暗号化プロトコルです。TLSは複数の層に分かれており、このコミットが関連するのは主に「レコード層」です。レコード層は、アプリケーションデータを小さな断片（レコード）に分割し、暗号化、認証、圧縮などの処理を施して送信し、受信側でその逆の処理を行います。

### 4. AES-GCM (Advanced Encryption Standard - Galois/Counter Mode)

AES-GCMは、認証付き暗号化 (Authenticated Encryption with Associated Data, AEAD) モードの一種です。これは、データの機密性（暗号化）と完全性・認証性（改ざん検知と送信者の認証）の両方を提供します。
AES-GCMでは、暗号化される平文データに加えて、「追加認証データ (Additional Authenticated Data, AAD)」と呼ばれるデータも認証の対象とすることができます。AADは暗号化されませんが、メッセージの完全性保護に貢献します。TLSレコード層では、レコードヘッダの一部（シーケンス番号、タイプ、バージョン、長さなど）がAADとして使用され、メッセージのコンテキストが改ざんされていないことを保証します。

Goの `crypto/cipher.AEAD` インターフェースには `Seal` (暗号化) と `Open` (復号化) メソッドがあり、これらはAADを引数として受け取ります。

## 技術的詳細

このコミットの主要な技術的アプローチは、TLSレコード層の暗号化・復号化処理における一時的な `additionalData` バイトスライスのヒープ割り当てを排除することです。

### `src/crypto/tls/conn.go` の変更

`crypto/tls/conn.go` は、TLSコネクションの確立とデータ送受信のロジックを管理します。`halfConn` 構造体は、TLSコネクションの送受信の半分（送信または受信）の状態を保持します。

変更前は、`halfConn` の `decrypt` および `encrypt` メソッド内で、`additionalData` を構築するために `var additionalData [13]byte` というローカル変数が宣言されていました。この `additionalData` は、`cipher.AEAD` インターフェースの `Open` や `Seal` メソッドに引数として渡されます。Goのエスケープ解析は、インターフェース型を介して渡される変数の寿命を追跡するのが難しいため、このローカル変数がヒープにエスケープしてしまう可能性がありました。実際にベンチマーク結果は、この部分でヒープ割り当てが発生していたことを示しています。

このコミットでは、`halfConn` 構造体に `additionalData [13]byte` という固定サイズの配列フィールドを追加しました。
```go

    additionalData [13]byte // to avoid allocs; interface method args escape

```
そして、`decrypt` および `encrypt` メソッド内でローカル変数として `additionalData` を宣言する代わりに、`hc.additionalData` フィールドを直接使用するように変更しました。
```go

// ...
```

## コアとなるコードの解説

### `src/crypto/aes/aes_gcm.go` の変更点

このファイルでは、アセンブリ言語で実装されたAES-GCM関連の関数群（`aesEncBlock`, `gcmAesInit`, `gcmAesData`, `gcmAesEnc`, `gcmAesDec`, `gcmAesFinish`）の宣言に、`//go:noescape` ディレクティブが追加されました。

*   **`//go:noescape` の目的:** これらの関数は、Goのコードから呼び出されるアセンブリ関数です。通常、Goコンパイラは関数にポインタが渡されると、そのポインタがヒープにエスケープする可能性があると判断し、引数として渡されるデータをヒープに割り当てることがあります。しかし、アセンブリ関数が引数をスタック上で安全に処理し、呼び出し元のスコープを超えて参照しないことが保証されている場合、ヒープ割り当ては不要であり、オーバーヘッドとなります。`//go:noescape` はコンパイラに対し、これらの関数の引数はエスケープしないことを明示的に伝え、スタック割り当てを可能にすることで、メモリ割り当てを削減し、パフォーマンスを向上させます。

### `src/crypto/tls/conn.go` の変更点

このファイルでは、`halfConn` 構造体と、その `decrypt` および `encrypt` メソッドが変更されました。

1.  **`halfConn` 構造体への `additionalData` フィールドの追加:**
    *   `halfConn` 構造体に `additionalData [13]byte` という新しいフィールドが追加されました。これは、AES-GCMの認証付き暗号化で使用される追加認証データ (AAD) を格納するための固定サイズのバイト配列です。
    *   コメント `// to avoid allocs; interface method args escape` は、このフィールドがヒープ割り当てを避けるために導入されたことを明確に示しています。以前は、`cipher.AEAD` インターフェースのメソッドに渡されるローカル変数がエスケープ解析によってヒープに割り当てられていたため、このフィールドを構造体の一部として持つことで、各操作での再利用を可能にし、一時的なヒープ割り当てを排除しています。

2.  **`decrypt` および `encrypt` メソッドでの `additionalData` の使用方法の変更:**
    *   変更前は、`decrypt` および `encrypt` メソッド内で `var additionalData [13]byte` としてローカル変数が宣言され、AADが構築されていました。
    *   変更後は、このローカル変数の宣言が削除され、代わりに `hc.additionalData` (つまり、`halfConn` 構造体のフィールド) が使用されるようになりました。
    *   `copy(hc.additionalData[:], hc.seq[:])` や `hc.additionalData[11] = byte(n >> 8)` のように、構造体フィールドの `additionalData` を直接操作してAADを構築しています。
    *   最終的に `c.Open` や `c.Seal` メソッドに渡される際も、`hc.additionalData[:]` が使用されます。

これらの変更により、TLSレコードの暗号化・復号化のたびに発生していた `additionalData` のヒープ割り当てが完全に排除され、`halfConn` 構造体のライフサイクル内で一度だけ割り当てられたメモリが再利用されるようになりました。これにより、ガベージコレクションの負荷が軽減され、TLS通信のパフォーマンスが大幅に向上します。

# [インデックス 23627] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）中のスタックスキャン処理の重複を回避するためのものです。具体的には、GCが他のゴルーチンのスタックをスキャンする処理と、そのゴルーチン自身がプリエンプションポイントで自身のスタックをスキャンする処理との間で発生する競合状態において、スタックが二重にスキャンされることを防ぎます。将来導入される「スタックバリア」によってスキャン処理が非冪等（non-idempotent）になることを見越した準備として、各GCフェーズでスタックが一度だけスキャンされるように`gcworkdone`フラグを導入し、そのチェックを追加しています。

## コミット

runtime: avoid double-scanning of stacks

Currently there's a race between stopg scanning another G's stack and
the G reaching a preemption point and scanning its own stack. When
this race occurs, the G's stack is scanned twice. Currently this is
okay, so this race is benign.

However, we will shortly be adding stack barriers during the first
stack scan, so scanning will no longer be idempotent. To prepare for
this, this change ensures that each stack is scanned only once during
each GC phase by checking the flag that indicates that the stack has
been scanned in this phase before scanning the stack.

## 変更の背景

Goのガベージコレクション（GC）は、実行中のゴルーチン（G）のスタックをスキャンして、到達可能なオブジェクトを特定します。このスキャンは、GCが他のゴルーチンのスタックを停止させてスキャンする場合（stopg scanning）と、ゴルーチン自身がプリエンプションポイントに到達して自身のスタックをスキャンする場合の2つの経路で発生する可能性があります。

この2つのスキャン処理が同時に進行すると、特定のゴルーチンのスタックが二重にスキャンされる競合状態が発生していました。コミット時点では、スタックスキャンは冪等（idempotent）な操作であり、複数回実行されても結果に悪影響はなかったため、この競合は「無害（benign）」とされていました。

しかし、コミットメッセージには「we will shortly be adding stack barriers during the first stack scan, so scanning will no longer be idempotent」と明記されており、近い将来「スタックバリア」が導入される予定であることが示されています。スタックバリアが導入されると、スタックスキャンは冪等ではなくなり、二重スキャンが発生するとGCの正確性やパフォーマンスに問題が生じる可能性がありました。

この変更は、スタックバリア導入に先立って、各GCフェーズでスタックが確実に一度だけスキャンされるようにするための準備として行われました。これにより、将来のGCメカニズムの変更に安全に対応できるようになります。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのガベージコレクション、ゴルーチンのスケジューリング、およびメモリ管理に関するいくつかの概念を理解しておく必要があります。

1.  **Goのガベージコレクション (GC)**:
    *   GoのGCは、主に三色マーク＆スイープアルゴリズムをベースにした、並行（concurrent）かつ低遅延なGCです。これは、アプリケーションの実行と並行してGC処理の大部分を進めることで、アプリケーションの一時停止時間（Stop-The-World: STW）を最小限に抑えることを目指しています。
    *   **マークフェーズ**: GCの主要なフェーズの一つで、プログラムが使用しているオブジェクト（ライブオブジェクト）を特定します。このフェーズでは、グローバル変数やゴルーチンのスタック上にあるローカル変数など、プログラムから直接到達可能なオブジェクトを「ルート」としてマークし、そこからポインタを辿って全ての到達可能なオブジェクトをマークしていきます。
    *   **スタックスキャン**: マークフェーズにおいて、GCは実行中の全てのゴルーチンのスタックをスキャンします。スタック上にはローカル変数や関数呼び出しの引数などが格納されており、これらの中にヒープ上のオブジェクトへのポインタが含まれている可能性があります。GoのGCは「正確（precise）」であるため、スタック上のどの値がポインタで、どれが非ポインタデータであるかを正確に識別できます。

2.  **ゴルーチン (Goroutine)**:
    *   Goの軽量な実行スレッドです。数千、数万のゴルーチンを同時に実行することが一般的です。
    *   **スタック**: 各ゴルーチンは独自のスタックを持っています。Goのスタックは動的に伸縮するため、必要に応じてサイズが変更されます。

3.  **プリエンプションポイント (Preemption Points)**:
    *   Goスケジューラがゴルーチンの実行を安全に中断し、別のゴルーチンに切り替えることができる特定の場所です。これにより、CPUを占有するゴルーチンが他のゴルーチンを飢餓状態にすることを防ぎ、公平なスケジューリングと応答性を保証します。
    *   以前は協調的プリエンプションが主でしたが、Go 1.14以降は非協調的（非同期）プリエンプションも導入され、より真のプリエンプティブなスケジューラとなっています。
    *   GCの文脈では、ゴルーチンがプリエンプションポイントに到達すると、GCがそのゴルーチンのスタックをスキャンする機会を得るか、あるいはゴルーチン自身がGC関連の作業（自身のスタックのスキャンなど）を実行する機会を得ることがあります。

4.  **スタックバリア (Stack Barriers)**:
    *   コミットメッセージで言及されている「stack barriers」は、GoのGCにおける重要な概念です。これは、スタック上のポインタが変更された際にGCに通知するメカニズム、またはスタックのスキャン中に特定の処理を挿入するメカニズムを指します。
    *   一般的な「ライトバリア（Write Barrier）」は、ヒープ上のオブジェクトへのポインタが変更された際にGCがその変更を追跡するために使用されます。スタックバリアは、これのスタック版と考えることができます。
    *   このコミットが作成された2015年時点では、Go 1.8で導入される「ハイブリッドライトバリア」はまだ存在していません。ハイブリッドライトバリアは、GC開始時にスタック上のオブジェクトを全て黒（スキャン済み）としてマークすることで、スタック上のライトバリアを不要にし、STW時間をさらに短縮しました。
    *   このコミットで言及されている「スタックバリア」は、おそらくハイブリッドライトバリア以前の、スタックのスキャン中に何らかの追加処理（例えば、ポインタの追跡やマーク）を導入する計画を指しており、これがスキャン処理を非冪等にする原因となると考えられます。

5.  **冪等性 (Idempotence)**:
    *   ある操作を複数回実行しても、1回実行した場合と同じ結果になる性質を指します。
    *   スタックスキャンが冪等である場合、二重スキャンが発生しても問題ありません。しかし、スタックバリアが導入されると、スキャン中に状態が変更される可能性があり、二重スキャンが予期せぬ結果（例えば、オブジェクトの誤ったマーク、メモリリーク、クラッシュなど）を引き起こす可能性があります。

6.  **`gcworkdone` フラグ**:
    *   このコミットで導入または利用される、ゴルーチン（`gp`）に紐付けられたフラグです。特定のGCフェーズにおいて、そのゴルーチンのスタックが既にスキャンされたかどうかを示すために使用されます。

## 技術的詳細

このコミットの核心は、Goランタイムのガベージコレクション（GC）におけるスタックスキャンの競合状態と、将来の「スタックバリア」導入への対応です。

現在のGoランタイム（コミット時点）では、ゴルーチン（G）のスタックがスキャンされる経路が主に2つありました。
1.  **GCによるスキャン**: GCが他のゴルーチンを一時停止させ（stopg）、そのスタックをスキャンしてライブオブジェクトを特定する。
2.  **ゴルーチン自身によるスキャン**: ゴルーチンがプリエンプションポイント（`newstack`関数内など）に到達した際に、自身のスタックをスキャンするGC関連の作業（`gcphasework`の呼び出し）を実行する。

この2つの経路が同時に発生すると、同じゴルーチンのスタックがGCフェーズ中に二重にスキャンされる可能性がありました。コミットメッセージによると、この時点ではスタックスキャンは冪等な操作であったため、二重スキャンが発生しても「無害」であり、GCの正確性には影響がありませんでした。

しかし、Goランタイムの開発ロードマップでは、将来的に「スタックバリア」が導入される予定でした。スタックバリアは、スタック上のポインタの変更をGCが追跡するためのメカニズムであり、これが導入されるとスタックスキャンは非冪等な操作になります。つまり、複数回スキャンされると、GCの状態が不正になったり、予期せぬ動作を引き起こしたりするリスクがありました。

このコミットは、この将来の変更に備えるためのものです。解決策として、各ゴルーチンに`gcworkdone`というフラグを導入し、特定のGCフェーズでそのゴルーチンのスタックが既にスキャンされたかどうかを追跡するようにしました。

具体的な動作は以下のようになります。
*   GCフェーズ中にゴルーチンのスタックをスキャンする処理（`gcphasework`）が呼び出される際、まず`gp.gcworkdone`フラグをチェックします。
*   もし`gcworkdone`が`true`であれば、そのゴルーチンのスタックは既にスキャン済みであるため、`gcphasework`はすぐに処理を終了し、二重スキャンを回避します。
*   これにより、GCが他のゴルーチンのスタックをスキャンした場合でも、そのゴルーチンが後で自身のスタックをスキャンしようとした際に、重複したスキャンが防止されます。

この変更は、GoランタイムがGCの進化に対応し、より堅牢で効率的なメモリ管理を実現するための重要なステップでした。

## コアとなるコードの解説

1.  **`src/runtime/mgcmark.go` の `gcphasework` 関数への変更**:
    `gcphasework`関数は、ゴルーチン`gp`に対してGC関連の作業（主にスタックスキャン）を実行する役割を担っています。追加された`if gp.gcworkdone { return }`というコードは、この関数の冒頭で、現在のゴルーチン`gp`の`gcworkdone`フラグが既に`true`であるかどうかをチェックします。
    *   `gp.gcworkdone`が`true`の場合、それはこのGCフェーズにおいて、このゴルーチンのスタックが既にスキャン済みであることを意味します。したがって、関数はすぐに`return`し、それ以上のスキャン作業は行いません。
    *   これにより、GCが他の経路（例えば、別のP（プロセッサ）上で実行されているGCワーカーがこのゴルーチンのスタックをスキャンした場合）で既にスタックをスキャンしていたとしても、二重スキャンが確実に防止されます。

2.  **`src/runtime/stack1.go` の `newstack` 関数内のコメント変更**:
    `newstack`関数は、ゴルーチンのスタックが不足した際に新しいスタックを割り当てる処理を行う関数です。この関数内で、ゴルーチンがプリエンプションポイントに到達し、`gcphasework(gp)`を呼び出す可能性がある箇所があります。
    変更されたコメントは、GCが`_Gwaiting`状態のゴルーチンを検出し、そのスタックをスキャンする競合状態が発生する可能性について言及しています。そして、もしその競合によってGCが先にスタックをスキャンした場合、`gcworkdone`フラグが設定されるため、`gcphasework`の呼び出しは単に`return`するだけになる、と説明しています。これは、`mgcmark.go`で追加された`gcworkdone`チェックの動作を反映したものです。

これらの変更により、Goランタイムは、将来のスタックバリア導入によってスタックスキャンが非冪等になったとしても、各GCフェーズでスタックが一度だけスキャンされることを保証できるようになりました。

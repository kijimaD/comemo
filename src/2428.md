## 変更の背景

このコミットの背景には、当時の主要なWebブラウザ（特にGoogle ChromeとInternet Explorer）の「ユーザーフレンドリー」な挙動がありました。これらのブラウザは、HTTPステータスコードが4xx（クライアントエラー）または5xx（サーバーエラー）であり、かつレスポンスボディが非常に短い場合に、Webサーバーから送られてきたカスタムエラーページを表示せず、ブラウザが独自に用意した汎用的なエラーメッセージを表示する傾向がありました。

これは、ユーザーにとっては「親切」な機能と見なされることもありましたが、Web開発者にとっては問題でした。なぜなら、開発者が意図した詳細なエラー情報やブランドイメージを反映したカスタムエラーページがユーザーに届かないためです。例えば、特定のAPIエラーコードやデバッグ情報を含むエラーページを表示したい場合でも、ブラウザがそれを上書きしてしまうため、デバッグやユーザーサポートが困難になることがありました。

このコミットは、このようなブラウザの挙動を回避し、GoのHTTPサーバーが提供するカスタムエラーページが確実に表示されるようにするために導入されました。具体的には、エラーページのコンテンツが短すぎる場合に、ブラウザが独自のエラーページを表示しないように、意図的にコンテンツを水増し（パディング）するというアプローチが取られています。

## 前提知識の解説

### HTTPステータスコード
HTTPステータスコードは、Webサーバーがクライアントのリクエストに対してどのような結果を返したかを示す3桁の数字です。
*   **1xx (情報)**: リクエストは受信され、処理が継続されます。
*   **2xx (成功)**: リクエストは正常に受信、理解、受理されました。
*   **3xx (リダイレクト)**: リクエストを完了するために、さらなるアクションが必要です。
*   **4xx (クライアントエラー)**: クライアントからのリクエストに誤りがあります。例:
    *   `400 Bad Request`: リクエストの構文が不正です。
    *   `401 Unauthorized`: 認証が必要です。
    *   `403 Forbidden`: リソースへのアクセスが拒否されました。
    *   `404 Not Found`: リクエストされたリソースが見つかりません。
*   **5xx (サーバーエラー)**: サーバーがリクエストの処理に失敗しました。例:
    *   `500 Internal Server Error`: サーバー内部で予期せぬエラーが発生しました。
    *   `502 Bad Gateway`: ゲートウェイまたはプロキシとして動作しているサーバーが、アップストリームサーバーから無効なレスポンスを受け取りました。
    *   `503 Service Unavailable`: サーバーが一時的にリクエストを処理できません。

このコミットでは、特に4xxと5xxのエラーレスポンスが対象となっています。

### HTTPヘッダー
HTTPヘッダーは、HTTPメッセージのメタデータを提供するキーと値のペアです。
*   **`Content-Type`**: レスポンスボディのメディアタイプ（MIMEタイプ）を示します。例えば、`text/html`はHTMLドキュメント、`application/json`はJSONデータを示します。このコミットでは、`text/`で始まる`Content-Type`（例: `text/plain`, `text/html`）が対象となります。
*   **`User-Agent`**: クライアント（ブラウザなど）が自身を識別するためにサーバーに送信する文字列です。サーバーはこの情報を使って、クライアントの種類やバージョンを判別し、それに応じたコンテンツや挙動を提供することができます。このコミットでは、`User-Agent`ヘッダーに含まれる文字列（`MSIE`や`Chrome/`）を解析して、特定のブラウザを識別しています。

### Goの`net/http`パッケージ（当時の`http`パッケージ）
Go言語の`net/http`パッケージは、HTTPクライアントとサーバーを実装するための強力な機能を提供します。このコミットが変更を加えているのは、HTTPサーバー側の実装です。
*   **`http.Conn`**: HTTP接続を表す構造体で、リクエストの読み取りやレスポンスの書き込みを管理します。
*   **`WriteHeader(code int)`**: レスポンスヘッダーを書き込み、HTTPステータスコードを設定します。
*   **`Write(data []byte)`**: レスポンスボディにデータを書き込みます。
*   **`flush()`**: バッファリングされたデータをクライアントに送信します。

## 技術的詳細

このコミットで導入された主要な技術的解決策は、`errorKludge`という関数です。この関数は、HTTPレスポンスがエラー（4xxまたは5xx）であり、かつレスポンスボディが特定のブラウザが独自のエラーページを表示しないと判断するのに十分な長さでない場合に、追加のテキストを挿入してレスポンスボディを水増しします。

具体的な動作は以下の通りです。

1.  **エラー判定**: レスポンスのステータスコードが4xxまたは5xxの範囲にあるかを確認します。これ以外のステータスコード（例: 2xx成功、3xxリダイレクト）の場合は、この処理は不要なためすぐに終了します。
2.  **コンテンツ長の確認**: ハンドラが既に書き込んだレスポンスボディのバイト数（`c.written`）が、最小限必要な長さ（`min = 1024`バイト）に達しているかを確認します。既に十分な長さがある場合、または全くデータが書き込まれていない場合は、処理をスキップします。
3.  **Content-Typeの確認**: レスポンスヘッダーの`Content-Type`が`text/`で始まるかを確認します。これは、HTMLやプレーンテキストのエラーページが対象であり、画像やJSONなどのバイナリデータや構造化データの場合はこのパディングは意味がないためです。
4.  **ブラウザの識別**: リクエストの`User-Agent`ヘッダーを解析し、問題のあるブラウザ（`MSIE`または`Chrome/`を含む）であるかを識別します。これら以外のブラウザでは、このパディングは不要と判断されます。
5.  **パディングの実行**: 上記の条件をすべて満たした場合、`errorKludge`関数は、`"Chrome would ignore this error page if this text weren't here.\n"`のようなメッセージを繰り返し書き込むことで、レスポンスボディの合計長が1024バイト以上になるように水増しします。このメッセージは、開発者がこのパディングの意図を理解できるように、コミットメッセージにも含まれていました。

この`errorKludge`関数は、`Conn`構造体の`flush()`メソッド内で呼び出されます。`flush()`は、レスポンスヘッダーがまだ書き込まれていない場合に`WriteHeader(StatusOK)`を呼び出した後、またはチャンクエンコーディングの終了処理を行う前に実行されます。これにより、レスポンスボディがクライアントに送信される直前に、必要に応じてパディングが適用されることになります。

## コアとなるコードの変更箇所

変更は`src/lib/http/server.go`ファイルに集中しています。

1.  **`strings`パッケージのインポート**: `User-Agent`ヘッダーの文字列操作のために`strings`パッケージが追加されました。
    ```go
    // ...
    import (
    	"os";
    	"path";
    	"strconv";
    	"strings"; // 追加
    )
    ```

2.  **`Conn`構造体へのフィールド追加**:
    *   `written int64`: レスポンスボディに書き込まれたバイト数を追跡します。
    *   `status int`: `WriteHeader`で設定されたHTTPステータスコードを保存します。
    ```go
    type Conn struct {
    	// ...
    	chunking bool;	// using chunked transfer encoding for reply body
    	wroteHeader bool;	// reply header has been written
    	header map[string] string;	// reply header parameters
    	written int64;	// number of bytes written in body // 追加
    	status int;	// status code passed to WriteHeader // 追加
    }
    ```

3.  **`WriteHeader`メソッドの変更**:
    *   `c.status = code;`: 設定されたステータスコードを`Conn`構造体に保存します。
    *   `c.written = 0;`: 新しいレスポンスボディの書き込みが始まるため、`written`カウンタをリセットします。
    ```go
    func (c *Conn) WriteHeader(code int) {
    	// ...
    	c.wroteHeader = true;
    	c.status = code; // 追加
    	c.written = 0; // 追加
    	// ...
    }
    ```

4.  **`Write`メソッドの変更**:
    *   `c.written += int64(len(data));`: レスポンスボディに書き込まれたデータの長さを`written`カウンタに加算します。
    ```go
    func (c *Conn) Write(data []byte) (n int, err os.Error) {
    	// ...
    	c.written += int64(len(data));	// ignoring errors, for errorKludge // 追加
    	// ...
    }
    ```

5.  **`errorKludge`関数の追加**:
    この関数が、前述のロジック（エラー判定、コンテンツ長、Content-Type、ブラウザ識別、パディング）を実装しています。
    ```go
    // If this is an error reply (4xx or 5xx)
    // and the handler wrote some data explaining the error,
    // some browsers (i.e., Chrome, Internet Explorer)
    // will show their own error instead unless the error is
    // long enough.  The minimum lengths used in those
    // browsers are in the 256-512 range.
    // Pad to 1024 bytes.
    func errorKludge(c *Conn, req *Request) {
    	const min = 1024;

    	// Is this an error?
    	if kind := c.status/100; kind != 4 && kind != 5 {
    		return;
    	}

    	// Did the handler supply any info?  Enough?
    	if c.written == 0 || c.written >= min {
    		return;
    	}

    	// Is it text?  ("Content-Type" is always in the map)
    	if s := c.header["Content-Type"]; len(s) < 5 || s[0:5] != "text/" {
    		return;
    	}

    	// Is it a broken browser?
    	var msg string;
    	switch agent := req.UserAgent; {
    	case strings.Index(agent, "MSIE") >= 0:
    		msg = "Internet Explorer";
    	case strings.Index(agent, "Chrome/") >= 0:
    		msg = "Chrome";
    	default:
    		return;
    	}
    	msg += " would ignore this error page if this text weren't here.\n";
    	io.WriteString(c, "\n");
    	for c.written < min {
    		io.WriteString(c, msg);
    	}
    }
    ```

6.  **`flush`メソッドからの`errorKludge`呼び出し**:
    レスポンスがクライアントに送信される直前に`errorKludge`が実行されるようにします。
    ```go
    func (c *Conn) flush() {
    	if !c.wroteHeader {
    		c.WriteHeader(StatusOK);
    	}
    	errorKludge(c, c.Req); // 追加
    	if c.chunking {
    		// ...
    	}
    }
    ```

## コアとなるコードの解説

このコミットの核心は、`errorKludge`関数とその関連する`Conn`構造体への変更です。

`Conn`構造体に`written`と`status`フィールドが追加されたことで、HTTPサーバーは各接続に対して、現在処理中のレスポンスのステータスコードと、既にボディに書き込まれたバイト数を内部的に追跡できるようになりました。これは、`errorKludge`関数が適切なタイミングで、かつ正確な情報に基づいて動作するために不可欠です。

`errorKludge`関数は、以下の条件をすべて満たした場合にのみパディングを実行します。

1.  **`c.status/100`が4または5であること**: HTTPステータスコードが4xx（クライアントエラー）または5xx（サーバーエラー）の範囲内であることを確認します。これは、ブラウザが独自のエラーページを表示する対象となる主要なエラーカテゴリです。
2.  **`c.written`が0より大きく、かつ`min`（1024バイト）未満であること**: ハンドラが何らかのエラーメッセージを書き込んだものの、その長さがブラウザの閾値（当時のChromeやIEでは256-512バイト程度）を下回る可能性がある場合にのみパディングを行います。全く書き込みがない場合や、既に十分な長さがある場合は不要です。
3.  **`c.header["Content-Type"]`が`"text/"`で始まること**: レスポンスがテキストベースのコンテンツ（例: `text/html`, `text/plain`）であることを確認します。画像やJSONなどの非テキストコンテンツに対してパディングを行っても意味がないためです。
4.  **`req.UserAgent`が`"MSIE"`または`"Chrome/"`を含むこと**: 問題の挙動を示す特定のブラウザからのリクエストであるかを`User-Agent`ヘッダーで識別します。これにより、影響を受けないブラウザに対しては余分なパディングを行わないように最適化されています。

これらの条件がすべて満たされた場合、`errorKludge`は`io.WriteString(c, msg)`を繰り返し呼び出し、`c.written`が`min`（1024バイト）に達するまで、意味のないメッセージをレスポンスボディに追加します。このメッセージは、ブラウザが「このエラーページは十分な長さがある」と判断し、カスタムエラーページをそのまま表示するように仕向けるためのものです。

この修正は、当時のブラウザの「過剰な賢さ」に対する実用的なワークアラウンドであり、GoのHTTPサーバーが提供するエラーメッセージの一貫性を保つ上で重要な役割を果たしました。

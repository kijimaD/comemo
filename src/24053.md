# [インデックス 24053] ファイルの概要

このコミットは、Goの`net/http`パッケージにおけるサーバーの実装を、HTTPリクエストスマグリング攻撃に対してより堅牢にするためのものです。RFC 7230で定義されているHTTPメッセージの構文とルーティングの仕様に基づき、特に`Content-Length`ヘッダーと`Transfer-Encoding`ヘッダーの処理を厳格化することで、潜在的な脆弱性を排除しています。具体的には、不正なヘッダーの組み合わせや複数回の指定を検出してエラーとする新しいテストケースが追加され、既存のヘッダー処理ロジックが修正されています。

## 変更の背景

この変更の主な背景は、HTTPリクエストスマグリング（HTTP Request Smuggling）と呼ばれるセキュリティ脆弱性への対策です。HTTPリクエストスマグリングは、フロントエンドサーバー（ロードバランサーやリバースプロキシなど）とバックエンドサーバーがHTTPリクエストの境界を異なる方法で解釈する際に発生します。この解釈の不一致を利用して、攻撃者は悪意のあるリクエストを「密輸」し、セキュリティ制御を回避したり、不正アクセスを行ったり、キャッシュポイズニングや他のユーザーへの攻撃（セッションハイジャック、XSSなど）を引き起こす可能性があります。

特に、HTTP/1.1プロトコルでは、メッセージボディの長さを指定する方法として`Content-Length`ヘッダーと`Transfer-Encoding`ヘッダーの2つが存在し、これらが矛盾して使用されると問題が生じやすいことが知られています。RFC 7230は、これらのヘッダーの処理に関する曖昧さを解消し、リクエストスマグリングのリスクを軽減するための明確なガイドラインを提供しています。このコミットは、Goの`net/http`サーバーがこれらのガイドラインに厳密に従い、リクエストスマグリング攻撃に対する堅牢性を高めることを目的としています。

## 前提知識の解説

### HTTPリクエストスマグリング

HTTPリクエストスマグリングは、HTTPプロキシチェーン（クライアント -> フロントエンドサーバー -> バックエンドサーバー）において、各サーバーがHTTPリクエストの開始と終了を異なる方法で判断することで発生する脆弱性です。攻撃者は、この解釈の不一致を利用して、一つのTCP接続内で複数のHTTPリクエストを送信し、バックエンドサーバーがそれらを独立したリクエストとして処理するように仕向けます。これにより、通常では到達できない内部APIへのアクセス、認証のバイパス、他のユーザーのセッションハイジャックなどが可能になります。

この脆弱性の根源は、HTTP/1.1がメッセージボディの長さを指定するために`Content-Length`と`Transfer-Encoding: chunked`という2つのメカニズムを提供していることにあります。

*   **`Content-Length`**: メッセージボディのバイト数を直接指定します。
*   **`Transfer-Encoding: chunked`**: メッセージボディをチャンク（塊）に分割し、各チャンクの前にそのサイズを示すことで、メッセージボディの長さを動的に指定します。

RFC 7230（およびその後のRFC 9110、RFC 9112）は、これらのヘッダーが同時に存在する場合の処理について明確なルールを定めています。特に、`Transfer-Encoding`ヘッダーが存在する場合、`Content-Length`ヘッダーは無視されるべきであり、フロントエンドサーバーは`Content-Length`ヘッダーを削除してバックエンドに転送すべきであるとされています。しかし、実装によってはこのルールが厳密に守られず、サーバー間で解釈の不一致が生じることがあります。

### RFC 7230

RFC 7230は、HTTP/1.1のメッセージ構文とルーティングに関する主要な仕様を定義した文書です。2014年に公開され、以前のRFC 2616の曖昧さを解消し、より厳密なプロトコル動作を規定しました。リクエストスマグリングに関連する重要な点は以下の通りです。

*   **セクション3.3.3 (Message Body Length)**:
    *   HTTPメッセージが`Transfer-Encoding`ヘッダーフィールドと`Content-Length`ヘッダーフィールドの**両方**を受け取った場合、`Transfer-Encoding`ヘッダーが`Content-Length`ヘッダーを**上書きしなければならない**と規定しています。
    *   このようなメッセージは「エラーとして扱われるべき」であり、送信者は「そのようなメッセージをダウンストリームに転送する前に、受信した`Content-Length`フィールドを**削除しなければならない**」と明記されています。

このRFCの指示に厳密に従うことで、サーバー間の解釈の不一致を防ぎ、リクエストスマグリング攻撃のリスクを大幅に低減できます。

## 技術的詳細

このコミットでは、主に`src/net/http/readrequest_test.go`と`src/net/http/transfer.go`の2つのファイルが変更されています。

### `src/net/http/readrequest_test.go`の変更点

1.  **新しいテストケースの追加**:
    *   `HEAD`リクエストで`Content-Length: 0`が許可されることを確認するテストケースが追加されました。これは、`HEAD`リクエストがボディを持たないにもかかわらず、`Content-Length: 0`が指定されるケースが実際に存在し、それが正しく処理されるべきであることを示しています。
    *   `badRequestTests`という新しいテストスイートが導入されました。これには、リクエストスマグリングのシナリオを模倣した複数の不正なリクエストが含まれています。
        *   `bad_connect_host`: 不正な`CONNECT`リクエスト。
        *   `smuggle_two_contentlen`: 複数の`Content-Length`ヘッダーを持つリクエスト。これはRFC 7230で禁止されています。
        *   `smuggle_chunked_and_len`: `Transfer-Encoding: chunked`と`Content-Length`ヘッダーが同時に存在するリクエスト。これもRFC 7230で禁止されています。
        *   `smuggle_content_len_head`: `HEAD`リクエストに`Content-Length`ヘッダーが存在するケース。
    *   これらのテストケースは、`ReadRequest`関数が不正なリクエストを正しくエラーとして処理するか、または安全な方法で解釈することを確認するために使用されます。

2.  **ヘルパー関数の追加**:
    *   `reqBytes(req string) []byte`関数が追加されました。これは、テスト用のリクエスト文字列（改行が`\n`で区切られている）を受け取り、HTTPプロトコルで要求される`\r\n`区切りに変換し、末尾に`\r\n\r\n`を追加して完全なリクエストバイト列を生成します。これにより、テストコードの可読性と保守性が向上しています。

### `src/net/http/transfer.go`の変更点

1.  **`shouldSendContentLength()`関数の修正**:
    *   `t.ContentLength == 0 && isIdentity(t.TransferEncoding)`の条件に、`t.Method == "GET" || t.Method == "HEAD"`の場合には`Content-Length`を送信しないという条件が追加されました。これは、`GET`や`HEAD`リクエストは通常ボディを持たないため、`Content-Length: 0`を明示的に送信する必要がない、あるいは誤解を招く可能性があるためです。

2.  **`readTransfer()`関数の修正**:
    *   `Request`構造体に`t.RequestMethod = rr.Method`という行が追加されました。これにより、リクエストのメソッド情報が`transfer`構造体（`readTransfer`関数が処理する内部構造体）に正しく伝播されるようになります。

3.  **`fixTransferEncoding()`関数の修正**:
    *   この関数は、`isResponse bool`という新しい引数を取るようになりました。これにより、リクエストとレスポンスで`Transfer-Encoding`ヘッダーの処理ロジックを区別できるようになります。
    *   `Transfer-Encoding`ヘッダーと`Content-Length`ヘッダーが同時に存在する場合の処理が厳格化されました。
        *   **リクエストの場合 (`isRequest`がtrue)**: RFC 7230 3.3.2の規定に従い、「`Transfer-Encoding`と`Content-Length`が同時に存在する場合、HTTPリクエストは無効である」と判断し、`"http: invalid Content-Length with Transfer-Encoding"`というエラーを返します。これにより、不正なリクエストがバックエンドに到達するのを防ぎます。
        *   **レスポンスの場合**: `Content-Length`ヘッダーを削除します。これは、RFC 7230がレスポンスにおいて`Transfer-Encoding`が優先されるべきであり、`Content-Length`は削除されるべきであると規定しているためです。

4.  **`fixLength()`関数の修正**:
    *   この関数も`isResponse bool`という新しい引数を取るようになりました。
    *   **ボディを期待しないメソッドの処理**: `noBodyExpected(requestMethod)`（例: `GET`, `HEAD`, `CONNECT`など）の場合の`Content-Length`ヘッダーの処理が厳格化されました。
        *   **リクエストの場合 (`isRequest`がtrue)**: `Content-Length`ヘッダーが存在し、かつその値が`"0"`でない場合、`"http: method cannot contain a Content-Length"`というエラーを返します。これは、ボディを持たないはずのリクエストに`Content-Length`が指定されている場合、それがリクエストスマグリングの試みである可能性があるためです。ただし、`Content-Length: 0`は例外的に許可されます。
    *   **複数の`Content-Length`ヘッダーの禁止**: `len(contentLens) > 1`の場合、`"http: message cannot contain multiple Content-Length headers"`というエラーを返すようになりました。これは、複数の`Content-Length`ヘッダーが存在すること自体が、リクエストスマグリングの兆候であるため、これを厳しく禁止することで堅牢性を高めています。
    *   `Content-Length`ヘッダーの値の取得方法が変更されました。以前は`header.get("Content-Length")`を使用していましたが、これは複数の値が存在する場合に最初の値しか取得しない可能性があります。新しいコードでは、`contentLens := header["Content-Length"]`で全ての値を取得し、`len(contentLens) == 1`の場合にのみその値を使用するように変更されています。これにより、複数の`Content-Length`ヘッダーが存在するケースをより正確に検出できるようになりました。
    *   `GET`リクエストにおけるボディの扱いに関するコメントが更新され、RFC 2616では明示的に許可も禁止もされていないが、Goの実装では宣言されていれば許可し、言及がなければデフォルトで0と見なすという方針が明確化されました。

## コアとなるコードの解説

このコミットのコアとなる変更は、HTTPヘッダーの解析と検証を厳格化することで、リクエストスマグリング攻撃の可能性を排除することにあります。

1.  **テストの強化**: `TestReadRequest_Bad`の追加により、複数の`Content-Length`ヘッダーや`Transfer-Encoding`と`Content-Length`の同時使用といった、リクエストスマグリングに悪用されやすい不正なヘッダーの組み合わせが、サーバーによって正しくエラーとして扱われることが保証されます。これにより、Goの`net/http`サーバーがこれらの不正なリクエストをバックエンドに転送する前にブロックできるようになります。

2.  **`fixTransferEncoding`関数の改善**:
    *   `isResponse`引数の導入により、リクエストとレスポンスで異なるRFCの要件に対応できるようになりました。
    *   最も重要な変更は、リクエストにおいて`Transfer-Encoding`と`Content-Length`が同時に存在する場合に、明示的にエラーを返すようになった点です。RFC 7230はこのような組み合わせを禁止しており、この変更によってGoサーバーはプロトコル違反を厳しく取り締まることで、サーバー間の解釈の不一致を防ぎます。

3.  **`fixLength`関数の改善**:
    *   この関数も`isResponse`引数を受け取るようになり、リクエストとレスポンスでボディ長の処理を区別できるようになりました。
    *   ボディを期待しないメソッド（例: `GET`, `HEAD`）に対する`Content-Length`ヘッダーの扱いが厳格化されました。`Content-Length: 0`以外の値が指定された場合、エラーを返すことで、これらのメソッドに不正なボディが「密輸」されるのを防ぎます。
    *   複数の`Content-Length`ヘッダーが存在する場合にエラーを返すようになりました。これは、リクエストスマグリング攻撃者が異なる`Content-Length`値を指定することで、フロントエンドとバックエンドのサーバーを混乱させる一般的な手法であるため、この種の攻撃を直接的に防ぐ効果があります。
    *   `Content-Length`ヘッダーの値を取得する際に、`header.get`ではなく、ヘッダーマップから直接値を取得し、その数が1つであることを確認するようになりました。これにより、複数の`Content-Length`ヘッダーが存在するケースをより確実に検出し、上述のエラー処理に繋げることができます。

これらの変更は、HTTPプロトコルの仕様に厳密に従うことで、Goの`net/http`サーバーがリクエストスマグリング攻撃に対してより堅牢になることを保証します。

## 元コミット内容

`net/http: defer idleMu.Unlock() in tryPutIdleConn + minor typo fixes.`

このコミットは、`net/http`パッケージの`tryPutIdleConn`関数において、`idleMu.Unlock()`の呼び出しを`defer`ステートメントに置き換え、さらに軽微なタイプミスを修正するものです。

## 変更の背景

Goの`net/http`パッケージは、HTTPクライアントがサーバーとの間で確立した接続を効率的に再利用するための接続プールメカニズムを提供します。このメカニズムは、特にKeep-Alive接続において、新しい接続を確立するオーバーヘッドを削減し、パフォーマンスを向上させます。

`Transport`構造体は、この接続プールの管理を担当しており、複数のゴルーチンからの同時アクセスを安全に処理するためにミューテックス（`sync.Mutex`）を使用しています。`tryPutIdleConn`関数は、使用済みだがまだ有効な接続をアイドル接続プールに戻す役割を担っています。

元のコードでは、`idleMu.Lock()`でミューテックスをロックした後、関数の複数の終了パス（正常終了、エラーリターン、早期リターン）のそれぞれで明示的に`idleMu.Unlock()`を呼び出していました。このような手動でのアンロックは、以下のような問題を引き起こす可能性があります。

1.  **アンロック忘れ**: 新しいリターンパスが追加された際に、`Unlock()`の呼び出しを忘れると、ミューテックスがロックされたままになり、デッドロックやパフォーマンスの問題が発生する可能性があります。
2.  **コードの冗長性**: 複数の`Unlock()`呼び出しがコードを冗長にし、読みにくくします。
3.  **エラーハンドリングの複雑化**: エラーが発生した場合のアンロック処理を各エラーパスで考慮する必要があり、コードが複雑になります。

このコミットは、Goの`defer`キーワードを活用することで、これらの問題を解決し、コードの堅牢性と保守性を向上させることを目的としています。

## 前提知識の解説

### Goの`net/http`パッケージと`Transport`

`net/http`パッケージは、Go言語でHTTPクライアントおよびサーバーを構築するための主要なパッケージです。
`http.Client`はHTTPリクエストを送信するための高レベルなインターフェースを提供し、その内部で`http.Transport`が実際のネットワーク通信の詳細（接続の確立、TLSハンドシェイク、プロキシ設定、接続プーリングなど）を処理します。
`Transport`は、特にHTTP/1.xのKeep-Alive接続を管理し、サーバーへの接続を再利用することで、リクエストごとの接続確立コストを削減します。

### HTTP Keep-Aliveとアイドル接続

HTTP Keep-Alive（または永続的接続）は、単一のTCP接続上で複数のHTTPリクエスト/レスポンスを交換することを可能にするメカニズムです。これにより、リクエストごとに新しいTCP接続を確立・切断するオーバーヘッドが削減され、Webページのロード時間やAPI呼び出しの効率が向上します。
`net/http`の`Transport`は、使用後に閉じられずにアイドル状態になったKeep-Alive接続をプールに保持し、次のリクエストで再利用できるようにします。これらの接続は「アイドル接続」と呼ばれます。`MaxIdleConnsPerHost`などの設定は、このアイドル接続プールの挙動を制御します。

### Goにおける`sync.Mutex`と`defer`キーワード

*   **`sync.Mutex`**: Goの`sync`パッケージが提供するミューテックス（相互排他ロック）は、共有リソースへの同時アクセスを制御し、データ競合を防ぐための基本的な同期プリミティブです。`Lock()`メソッドでロックを取得し、`Unlock()`メソッドでロックを解放します。
*   **`defer`キーワード**: `defer`ステートメントは、それが含まれる関数がリターンする直前に、指定された関数呼び出し（または式）を実行することを保証します。これは、リソースの解放（ファイルクローズ、ミューテックスアンロックなど）を確実に行うために非常に便利です。`defer`された関数はLIFO（後入れ先出し）順で実行されます。

`defer`を`Unlock()`と組み合わせることで、関数内のどのパスを通っても、ミューテックスが確実に解放されることが保証されます。これは、エラーハンドリングが複雑な関数や、複数のリターンポイントを持つ関数において、特に重要です。

### `tryPutIdleConn`関数の目的

`tryPutIdleConn`関数は、`net/http`の`Transport`内で、使用済みの`persistConn`（永続的な接続を表す構造体）をアイドル接続プールに格納しようとします。この関数は、接続が再利用可能であるか、プールに空きがあるか、または待機中のダイアラー（接続を待っているリクエスト）が存在するかどうかを判断し、適切な処理を行います。

## 技術的詳細

このコミットの主要な変更は、`tryPutIdleConn`関数における`idleMu.Unlock()`の呼び出し方です。

### `tryPutIdleConn`関数の元のロジックと問題点

元の`tryPutIdleConn`関数では、`t.idleMu.Lock()`でミューテックスをロックした後、関数の様々な分岐点やリターンポイントで明示的に`t.idleMu.Unlock()`を呼び出していました。

```go
// Original (simplified)
func (t *Transport) tryPutIdleConn(pconn *persistConn) error {
    // ...
    t.idleMu.Lock()
    // ...
    if condition1 {
        t.idleMu.Unlock() // 1回目のUnlock
        return nil
    }
    // ...
    if condition2 {
        t.idleMu.Unlock() // 2回目のUnlock
        return errWantIdle
    }
    // ...
    if condition3 {
        t.idleMu.Unlock() // 3回目のUnlock
        return errTooManyIdle
    }
    // ...
    t.idleMu.Unlock() // 4回目のUnlock (関数の最後)
    return nil
}
```

このパターンは、以下のような潜在的な問題を含んでいます。

1.  **見落としによるデッドロック**: もし新しいリターンパスが追加された際に、開発者が`t.idleMu.Unlock()`の呼び出しを忘れてしまった場合、ミューテックスはロックされたままになり、他のゴルーチンが`idleMu`をロックしようとした際に永久にブロックされる（デッドロック）可能性があります。
2.  **保守性の低下**: コードの変更やリファクタリングの際に、すべての`Unlock()`呼び出し箇所を正確に追跡し、適切に更新することが難しくなります。
3.  **可読性の低下**: ロックとアンロックのペアが離れていたり、複数のアンロックが散在していると、コードの流れを追うのが難しくなります。

### `defer`による改善

このコミットでは、`t.idleMu.Lock()`の直後に`defer t.idleMu.Unlock()`を追加し、既存の明示的な`t.idleMu.Unlock()`呼び出しをすべて削除しています。

```go
// New (simplified)
func (t *Transport) tryPutIdleConn(pconn *persistConn) error {
    // ...
    t.idleMu.Lock()
    defer t.idleMu.Unlock() // ここで一度だけdeferする
    // ...
    if condition1 {
        return nil // deferがUnlockを保証
    }
    // ...
    if condition2 {
        return errWantIdle // deferがUnlockを保証
    }
    // ...
    if condition3 {
        return errTooManyIdle // deferがUnlockを保証
    }
    // ...
    return nil // deferがUnlockを保証
}
```

この変更により、`tryPutIdleConn`関数がどのような経路で終了しても（正常リターン、エラーリターン、パニック発生時など）、`t.idleMu.Unlock()`が確実に実行されることが保証されます。これにより、ミューテックスの解放忘れによるデッドロックのリスクが排除され、コードの堅牢性が大幅に向上します。また、コードがより簡潔になり、ロックのライフサイクルが明確になるため、可読性と保守性も向上します。

### コメントの修正

`requestAndChan`構造体内の`addedGzip`フィールドに関するコメントも修正されています。

元のコメント:
`// did the Transport (as opposed to the client code) add an`
`// Accept-Encoding gzip header? only if it we set it do`
`// we transparently decode the gzip.`

修正後のコメント:
`// whether the Transport (as opposed to the user client code)`
`// added the Accept-Encoding gzip header. If the Transport`
`// set it, only then do we transparently decode the gzip.`

この修正は、コメントの文法的な誤り（"only if it we set it do"）を修正し、より明確で自然な英語表現（"only then do we transparently decode the gzip"）にすることで、`addedGzip`フィールドの役割を正確に伝えています。このフィールドは、`Transport`自身が`Accept-Encoding: gzip`ヘッダーを追加した場合にのみ、レスポンスのgzipデコードを透過的に行うべきであることを示しています。ユーザーコードがこのヘッダーを追加した場合は、`Transport`はデコードを行いません。

### `tryPutIdleConn`関数の目的

`tryPutIdleConn`関数は、`net/http`の`Transport`内で、使用済みの`persistConn`（永続的な接続を表す構造体）をアイドル接続プールに格納しようとします。この関数は、接続が再利用可能であるか、プールに空きがあるか、または待機中のダイアラー（接続を待っているリクエスト）が存在するかどうかを判断し、適切な処理を行います。

## 技術的詳細

このコミットの主要な変更は、`tryPutIdleConn`関数における`idleMu.Unlock()`の呼び出し方です。

### `tryPutIdleConn`関数の元のロジックと問題点

元の`tryPutIdleConn`関数では、`t.idleMu.Lock()`でミューテックスをロックした後、関数の様々な分岐点やリターンポイントで明示的に`t.idleMu.Unlock()`を呼び出していました。

```go
// Original (simplified)
func (t *Transport) tryPutIdleConn(pconn *persistConn) error {
    // ...
    t.idleMu.Lock()
    // ...
    if condition1 {
        t.idleMu.Unlock() // 1回目のUnlock
        return nil
    }
    // ...
    if condition2 {
        t.idleMu.Unlock() // 2回目のUnlock
        return errWantIdle
    }
    // ...
    if condition3 {
        t.idleMu.Unlock() // 3回目のUnlock
        return errTooManyIdle
    }
    // ...
    t.idleMu.Unlock() // 4回目のUnlock (関数の最後)
    return nil
}
```

このパターンは、以下のような潜在的な問題を含んでいます。

1.  **見落としによるデッドロック**: もし新しいリターンパスが追加された際に、開発者が`t.idleMu.Unlock()`の呼び出しを忘れてしまった場合、ミューテックスはロックされたままになり、他のゴルーチンが`idleMu`をロックしようとした際に永久にブロックされる（デッドロック）可能性があります。
2.  **保守性の低下**: コードの変更やリファクタリングの際に、すべての`Unlock()`呼び出し箇所を正確に追跡し、適切に更新することが難しくなります。
3.  **可読性の低下**: ロックとアンロックのペアが離れていたり、複数のアンロックが散在していると、コードの流れを追うのが難しくなります。

### `defer`による改善

このコミットでは、`t.idleMu.Lock()`の直後に`defer t.idleMu.Unlock()`を追加し、既存の明示的な`t.idleMu.Unlock()`呼び出しをすべて削除しています。

```go
// New (simplified)
func (t *Transport) tryPutIdleConn(pconn *persistConn) error {
    // ...
    t.idleMu.Lock()
    defer t.idleMu.Unlock() // ここで一度だけdeferする
    // ...
    if condition1 {
        return nil // deferがUnlockを保証
    }
    // ...
    if condition2 {
        return errWantIdle // deferがUnlockを保証
    }
    // ...
    if condition3 {
        return errTooManyIdle // deferがUnlockを保証
    }
    // ...
    return nil // deferがUnlockを保証
}
```

この変更により、`tryPutIdleConn`関数がどのような経路で終了しても（正常リターン、エラーリターン、パニック発生時など）、`t.idleMu.Unlock()`が確実に実行されることが保証されます。これにより、ミューテックスの解放忘れによるデッドロックのリスクが排除され、コードの堅牢性が大幅に向上します。また、コードがより簡潔になり、ロックのライフサイクルが明確になるため、可読性と保守性も向上します。

### コメントの修正

`requestAndChan`構造体内の`addedGzip`フィールドに関するコメントも修正されています。

元のコメント:
`// did the Transport (as opposed to the client code) add an`
`// Accept-Encoding gzip header? only if it we set it do`
`// we transparently decode the gzip.`

修正後のコメント:
`// whether the Transport (as opposed to the user client code)`
`// added the Accept-Encoding gzip header. If the Transport`
`// set it, only then do we transparently decode the gzip.`

この修正は、コメントの文法的な誤り（"only if it we set it do"）を修正し、より明確で自然な英語表現（"only then do we transparently decode the gzip"）にすることで、`addedGzip`フィールドの役割を正確に伝えています。このフィールドは、`Transport`自身が`Accept-Encoding: gzip`ヘッダーを追加した場合にのみ、レスポンスのgzipデコードを透過的に行うべきであることを示しています。ユーザーコードがこのヘッダーを追加した場合は、`Transport`はデコードを行いません。

### `src/net/http/transport.go` の変更点

1.  **`MaxIdleConnsPerHost` コメントの修正**:
    *   `- // (keep-alive) to keep per-host. If zero,`
    *   `+ // (keep-alive) connections to keep per-host. If zero,`

2.  **`tryPutIdleConn` 関数内のミューテックスアンロック処理の変更**:
    *   `t.idleMu.Lock()`の直後に`defer t.idleMu.Unlock()`が追加されました。

    *   関数内の複数の箇所にあった明示的な`t.idleMu.Unlock()`の呼び出し（計4箇所）がすべて削除されました。
    *   この変更により、ミューテックスの解放忘れによるデッドロックのリスクが排除され、コードの堅牢性と保守性が向上します。

3.  **`requestAndChan` 構造体内のコメント修正**:
    *   `- // did the Transport (as opposed to the client code) add an`
    *   `- // Accept-Encoding gzip header? only if it we set it do`
    *   `- // we transparently decode the gzip.`
    *   `+ // whether the Transport (as opposed to the user client code)`
    *   `+ // added the Accept-Encoding gzip header. If the Transport`
    *   `+ // set it, only then do we transparently decode the gzip.`

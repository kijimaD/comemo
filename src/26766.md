# [インデックス 26766] ファイルの概要

このコミットは、Goランタイムにおけるスタックガードのサイズを縮小する変更を導入しています。具体的には、スタックガードの値を1024バイトから720バイトに削減し、それに伴い関連するテストケースも更新しています。この変更は、Goコンパイラのスタックフレームサイズが最適化された結果として行われ、メモリ使用量の削減と効率の向上を目的としています。

## 変更の背景

この変更の背景には、Goコンパイラにおけるスタックフレームサイズの最適化があります。Goランタイムは、関数呼び出しごとにスタックフレームを割り当て、そのサイズはコンパイラによって決定されます。以前は、スタックオーバーフローを防ぐために比較的大きなスタックガードが設定されていましたが、コンパイラの改善により、より小さなスタックフレームで効率的に動作できるようになりました。

コミットメッセージによると、「Our stack frame sizes look pretty good now.」とあり、これはコンパイラが生成するコードのスタック使用量が十分に小さくなったことを示唆しています。この最適化により、スタックガードのサイズを縮小しても安全性が保たれると判断され、メモリフットプリントの削減とパフォーマンスの向上が期待されます。また、「Tip is currently using 720.」という記述から、この変更が既に開発ブランチ（tip）でテストされ、安定していることが伺えます。PPC（PowerPC）アーキテクチャの制約により、これ以上小さくすることはできないという言及も、プラットフォーム間の互換性を考慮した上での決定であることを示しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとコンパイラに関する前提知識が必要です。

1.  **Goのスタック管理**: Goは、OSのスタックではなく、独自のランタイム管理による可変サイズのスタックを使用します。これにより、Goroutineごとに小さなスタックを割り当て、必要に応じて動的に拡張することができます。スタックの拡張は、現在のスタックが不足しそうになったときに、より大きな新しいスタックを割り当て、古いスタックの内容をコピーすることで行われます。
2.  **スタックガード (Stack Guard)**: スタックガードは、スタックオーバーフローを検出するためのメカニズムです。各Goroutineのスタックの末尾近くに「ガードページ」のような領域が設定され、関数呼び出し時にスタックポインタがこのガード領域に侵入しようとすると、スタック拡張処理がトリガーされます。これにより、スタックオーバーフローによるクラッシュを防ぎ、スタックを安全に拡張できます。`StackGuard`定数は、スタックのベースからスタックガードまでのオフセットを示します。
3.  **`stackGuardMultiplier`**: Goのスタックガードサイズは、`stackGuardMultiplier`という定数によって調整されます。これは、特定のビルド設定（例: `-N`フラグによる最適化無効化）やアーキテクチャによってスタック使用量が異なる場合に、ガードサイズを適切にスケーリングするために使用されます。
4.  **`_StackSystem`**: これは、スタックのシステム予約領域のサイズを示す定数です。スタックガードの計算には、このシステム予約領域も考慮されます。
5.  **`cmd/compile`**: Goコンパイラは、Goのソースコードを機械語に変換するツールです。このコンパイラは、関数呼び出し規約、スタックフレームのレイアウト、レジスタ割り当てなど、実行時のスタック使用量に直接影響を与える多くの最適化を行います。
6.  **`dev.ssa`**: これは、GoコンパイラのSSA (Static Single Assignment) 形式への移行に関連する開発ブランチまたはフェーズを指します。SSAは、コンパイラの最適化能力を大幅に向上させ、より効率的なコード生成を可能にします。このコミットが`[dev.ssa]`のコンテキストで行われていることから、SSAベースの最適化がスタックフレームサイズの縮小に貢献したと考えられます。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムがスタックオーバーフローを検出するために使用する`StackGuard`定数の値を変更することにあります。

以前は、`StackGuard`は`1024 * stackGuardMultiplier + StackSystem`として定義されていました。これは、スタックのベースから1024バイト（`stackGuardMultiplier`でスケーリングされ、システム予約領域が加算される）のオフセットにスタックガードが設定されていたことを意味します。

このコミットでは、この値が`720 * stackGuardMultiplier + StackSystem`に削減されます。これは、スタックガードのオフセットが約304バイト（1024 - 720）減少することを意味します。

この変更は、以下のファイルに影響を与えます。

*   **`src/cmd/internal/obj/stack.go`**: これはコンパイラが使用するスタック関連の定数を定義するファイルです。ここで`StackGuard`が更新されます。コンパイラは、この定数を使用して、関数プロローグでスタックチェックコードを生成します。
*   **`src/runtime/stack.go`**: これはGoランタイムが使用するスタック関連の定数を定義するファイルです。ここで`_StackGuard`が更新されます。ランタイムは、この定数を使用して、スタック拡張のトリガーを判断します。
*   **`test/nosplit.go`**: これは、スタック分割（stack split）が発生しないことをテストするためのファイルです。スタックガードのサイズが変更されたため、このテスト内のスタックフレームサイズの計算ロジックも、新しいガードサイズに合わせて調整する必要があります。具体的には、テストケース内でスタックフレームのサイズを調整する際に使用されるマジックナンバーが`1024`から`720`に変更されています。これは、テストが新しいスタックガードの挙動と整合するようにするためです。

スタックガードの縮小は、各Goroutineが初期に割り当てるスタック領域のオーバーヘッドを削減し、特に多数のGoroutineが同時に実行されるようなアプリケーションにおいて、メモリ使用量の削減に貢献します。ただし、スタックガードが小さすぎると、スタックオーバーフローの検出が遅れ、スタック拡張が間に合わずにクラッシュするリスクが高まる可能性があります。このため、コンパイラのスタックフレームサイズ最適化が十分に進んだという確信がなければ、このような変更は行われません。コミットメッセージにある「PPC doesn't like that.」という記述は、特定のアーキテクチャではスタックフレームの最小サイズやアライメントの制約があり、これ以上スタックガードを縮小すると問題が発生する可能性を示唆しています。

## コアとなるコードの解説

上記のコード変更は、Goランタイムとコンパイラがスタックガードのサイズを決定するために使用する定数を直接変更しています。

*   **`src/cmd/internal/obj/stack.go` と `src/runtime/stack.go`**:
    *   これらのファイルでは、`StackGuard` (コンパイラ用) と `_StackGuard` (ランタイム用) の定義が、`1024`から`720`に変更されています。
    *   `StackGuard = 720*stackGuardMultiplier + StackSystem`
    *   `_StackGuard = 720*sys.StackGuardMultiplier + _StackSystem`
    *   この変更により、スタックガードがスタックのベースからより近い位置に設定されるようになります。これにより、スタック拡張が必要になるまでの「余裕」が小さくなりますが、コンパイラの最適化によってスタック使用量が減少したため、これは安全であると判断されています。結果として、各Goroutineが消費するメモリのオーバーヘッドが削減されます。

*   **`test/nosplit.go`**:
    *   このテストファイルでは、スタックガードのサイズ変更に合わせて、テストロジック内のマジックナンバーが更新されています。
    *   `size += (1024 - 128) - 128` が `size += (720 - 128) - 128` に変更されています。
    *   また、`-N`フラグ（最適化無効化）が指定された場合のスタックガードサイズ調整も `size += 1024` から `size += 720` に変更されています。
    *   このテストは、特定の関数がスタック分割なしで実行できることを検証するために、スタックフレームのサイズを正確に計算する必要があります。スタックガードの定義が変更されたため、テストが正しいスタック使用量をシミュレートし、期待される結果を出すためには、これらの値も更新する必要がありました。これにより、テストの正確性が保たれます。

全体として、このコミットは、Goコンパイラの進化と最適化の結果として、ランタイムのメモリ効率をさらに向上させるための調整であり、Goの継続的なパフォーマンス改善への取り組みの一環と言えます。

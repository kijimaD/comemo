# [インデックス 21469] ファイルの概要

このコミットは、GoランタイムがPPC64アーキテクチャ上でCgo（C言語との相互運用）をサポートするために、Cスレッドローカルストレージ（TLS）のセットアップと、現在のゴルーチン（`g`）ポインタのTLSへの保存を実装するものです。これは、Cgoを介したCからGoへの呼び出しや、Cコード内で発生する可能性のあるシグナルハンドリングを適切に処理するために不可欠な変更です。

## 元コミット内容

Goランタイムにおいて、PPC64アーキテクチャ向けにCスレッドローカルストレージ（TLS）をセットアップし、現在のゴルーチン（`g`）ポインタをそのTLSに保存するように変更します。この機能は、Cgoを介してCコードからGoコードを呼び出す際や、Cコード実行中に発生するシグナルを処理する際に必要となります。

## 変更の背景

GoプログラムがC言語で書かれたライブラリやシステムコールと連携する場合、Cgoというメカニズムを使用します。Cgoは、GoとCの間の橋渡しをする役割を担いますが、異なる実行モデルを持つ両者の間で状態を適切に管理することが課題となります。

特に、PPC64のような特定のアーキテクチャでは、Goランタイムが内部的に使用するレジスタ（例: 現在のゴルーチンを示す`g`レジスタ）が、Cコードの実行中に上書きされる可能性があります。CコードはGoランタイムの内部状態を認識しないため、Goの重要なレジスタを破壊してしまう危険性があります。これにより、Goランタイムが予期せぬ動作をしたり、クラッシュ（SIGSEGVなど）を引き起こしたりする可能性があります。

このコミットの主な背景は以下の2点です。

1.  **CからGoへの呼び出し**: Cgoを介してCコードからGo関数を呼び出す際、Goランタイムは現在のゴルーチンのコンテキストを正確に把握している必要があります。CコードがGoのレジスタを上書きする前に、Goのコンテキスト（特に`g`レジスタ）を安全に保存し、Go関数が実行される際にそれを復元するメカニズムが必要です。
2.  **Cコード内でのシグナルハンドリング**: Cコードの実行中にシグナル（例: SIGSEGV）が発生した場合、Goランタイムのシグナルハンドラが介入することがあります。この際、Goランタイムは現在のゴルーチンの状態にアクセスする必要がありますが、Cコードが`g`レジスタを上書きしていると、正しいゴルーチンコンテキストを特定できず、さらなる問題を引き起こす可能性があります。

これらの問題を解決するために、GoランタイムはPPC64アーキテクチャ上でCのTLSを利用して`g`レジスタの値を保存・復元する仕組みを導入しました。これにより、GoとCのコードが混在する環境でも、Goランタイムの安定性と正確性が保たれます。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **Goランタイム**: Goプログラムの実行を管理するシステムです。ゴルーチンのスケジューリング、メモリ管理（ガベージコレクション）、チャネル通信、Cgoとの連携など、多岐にわたる機能を提供します。Goのプログラムは、Goランタイムと密接に連携して動作します。
2.  **ゴルーチン（Goroutine）**: Goにおける軽量な並行処理の単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行することも可能です。各ゴルーチンは独自のスタックを持ち、Goランタイムによってスケジューリングされます。Goランタイムは、現在の実行中のゴルーチンを識別するために、特定のレジスタ（通常は`g`レジスタと呼ばれる）に現在のゴルーチン構造体へのポインタを保持します。
3.  **Cgo**: GoプログラムからC言語の関数を呼び出したり、C言語のプログラムからGoの関数を呼び出したりするためのGoの機能です。Cgoを使用すると、既存のCライブラリをGoから利用したり、パフォーマンスが重要な部分をCで記述したりすることができます。Cgoは、GoとCの異なる呼び出し規約やメモリモデルの間で変換を行う役割を担います。
4.  **スレッドローカルストレージ（TLS: Thread Local Storage）**: 各スレッドがそれぞれ独立したデータを保持できるメモリ領域です。グローバル変数とは異なり、TLSに保存されたデータは、そのデータを保存したスレッドからのみアクセス可能です。OSやCライブラリ（例: pthreads）は、スレッドごとに固有のデータを管理するためにTLSを提供します。Goランタイムは、OSスレッド上でゴルーチンを多重化して実行しますが、Cgoを介してCコードと連携する際には、CのスレッドモデルとGoのゴルーチンモデルの間の橋渡しとしてTLSが利用されることがあります。
5.  **PPC64アーキテクチャ**: IBMが開発したPowerPCプロセッサの64ビット版アーキテクチャです。Linuxシステムなどで利用されます。CPUのレジスタセット、メモリモデル、呼び出し規約などがx86-64などの他のアーキテクチャとは異なります。Goランタイムは、各アーキテクチャの特性に合わせて最適化されたアセンブリコードを含んでいます。
6.  **`g`レジスタ**: Goランタイムの内部で、現在実行中のゴルーチン構造体へのポインタを保持するために使用される特定のレジスタ（またはレジスタの役割を果たすもの）です。Goランタイムは、この`g`レジスタを通じて、現在のゴルーチンのスタック、状態、スケジューリング情報などにアクセスします。

## 技術的詳細

このコミットの核心は、PPC64アーキテクチャにおけるGoランタイムとCgoの相互運用性を向上させるために、CのTLSを活用して`g`レジスタの値を安全に管理することです。

Goランタイムは、通常、特定のレジスタ（PPC64ではR30レジスタが`g`レジスタとして使われることが多い）に現在のゴルーチン構造体へのポインタを保持しています。しかし、Cgoを介してCコードが実行されると、Cコードはこのレジスタを自由に利用し、Goランタイムが期待する`g`ポインタの値を上書きしてしまう可能性があります。

この問題を解決するため、以下のメカニズムが導入されました。

1.  **C TLSの利用**: Goランタイムは、OSが提供するスレッドローカルストレージ（TLS）を利用します。具体的には、`pthread_setspecific`や`pthread_getspecific`のようなPOSIXスレッドAPIによって管理されるTLS領域に、Goの`g`ポインタを保存・復元します。これにより、CコードがGoのレジスタを上書きしても、`g`ポインタの真の値はTLSに安全に保持されます。
2.  **`save_g`と`load_g`関数**:
    *   `save_g`関数は、現在の`g`レジスタの値をC TLSに保存します。これは、GoコードがCgoを介してCコードに制御を渡す直前や、Goランタイムがゴルーチンを切り替える際など、`g`レジスタがCコードによって上書きされる可能性がある状況で呼び出されます。
    *   `load_g`関数は、C TLSに保存された`g`の値を`g`レジスタに復元します。これは、CコードからGoコードに制御が戻る際や、Goランタイムがゴルーチンを再開する際などに呼び出されます。
3.  **`_RuntimeGogoBytes`の調整**: `src/runtime/arch1_ppc64.go`と`src/runtime/arch1_ppc64le.go`で定義されている`_RuntimeGogoBytes`定数が`64`から`72`に増加しています。この定数は、`gogo`関数がゴルーチンを切り替える際に使用するスタックフレームのサイズに関連しています。TLSへの`g`の保存・復元処理が追加されたことで、必要なスタック領域が増加したため、この値が調整されました。
4.  **`rt0_linux_ppc64le.s`でのTLSベースポインタの初期化**: プログラムの起動時（`_rt0_ppc64le_linux`）に、C TLSのベースポインタ（R13レジスタ）が初期化されます。これは、TLSにアクセスするために必要な基盤となります。
5.  **アセンブリコードによる実装**: `save_g`と`load_g`関数は、Goのアセンブリ言語（`src/runtime/tls_ppc64x.s`）で実装されています。これは、レジスタの直接操作やTLSへのアクセスといった低レベルな処理が必要なためです。特に、`runtime·tlsg(SB)`という特殊なリンカシンボルが使用されており、これはTLSの開始位置から`g`を保存する領域までのオフセットを示します。

この仕組みにより、GoランタイムはCgoを介したCコードとの連携において、`g`レジスタの整合性を保ち、Goプログラムの安定した実行を保証します。

## コアとなるコードの解説

### `src/runtime/arch1_ppc64.go` および `src/runtime/arch1_ppc64le.go`

これらのファイルでは、PPC64およびPPC64LEアーキテクチャ固有の定数が定義されています。
`_RuntimeGogoBytes`定数が`64`から`72`に増加しています。これは、`gogo`関数（ゴルーチンを切り替える際に使用される）が、TLSへの`g`の保存・復元処理のために追加のスタック領域を必要とするようになったためです。

```go
// arch1_ppc64.go
const (
    // ...
    _RuntimeGogoBytes = 72 // 変更前は 64
    // ...
)

// arch1_ppc64le.go
const (
    // ...
    _RuntimeGogoBytes = 72 // 変更前は 64
    // ...
)
```

### `src/runtime/asm_ppc64x.s`

このアセンブリファイルでは、Goランタイムの低レベルな処理が記述されています。
`runtime·gosave`、`runtime·gogo`、`runtime·mcall`、`runtime·morestack`などのゴルーチン切り替えやスタック管理に関連する関数内で、`runtime·save_g(SB)`の呼び出しが追加されています。これにより、これらの重要なポイントで`g`レジスタの値がTLSに保存されるようになります。

特に注目すべきは、`runtime·gogo`関数内での`BL runtime·save_g(SB)`の追加です。`gogo`はゴルーチンを切り替える際に呼び出されるため、新しいゴルーチンに切り替わる前に現在の`g`レジスタを保存することが重要です。

また、`runtime·rt0_go`のコメントに`R13 = C TLS base pointer`が追加され、C TLSベースポインタがR13レジスタに格納されることが明示されています。

### `src/runtime/rt0_linux_ppc64le.s`

Linux PPC64LE環境でのGoプログラムのエントリポイントとなるアセンブリファイルです。
`_rt0_ppc64le_linux`関数内で、C TLSのベースポインタ（R13レジスタ）の初期化が行われています。

```assembly
TEXT _rt0_ppc64le_linux(SB),NOSPLIT,$0
    // ...
    MOVD    $runtime·tls0(SB), R13 // TLS
    ADD     $0x7000, R13
    BR main(SB)
```
ここで`runtime·tls0(SB)`はTLSの開始アドレスを示し、`ADD $0x7000, R13`はTLSベースポインタを特定のオフセットで調整しています。これは、PPC64のTLSモデルにおける慣習的なオフセットです。

### `src/runtime/tls_ppc64x.s` (新規ファイル)

このファイルは新規に追加されたもので、PPC64アーキテクチャにおけるTLS関連のアセンブリ関数`runtime·save_g`と`runtime·load_g`を定義しています。

#### `TEXT runtime·save_g(SB),NOSPLIT,$-8-0`

この関数は、現在の`g`レジスタの値をC TLSに保存します。
*   `MOVB runtime·iscgo(SB), R31`: `iscgo`変数を読み込み、Cgoが有効かどうかをチェックします。Cgoが有効でない場合は、TLSへの保存はスキップされます。
*   `MOVD $runtime·tlsg(SB), R31`: `runtime·tlsg(SB)`は、TLSの開始位置から`g`を保存する領域までのオフセットを示す特殊なリンカシンボルです。
*   `ADD R13, R31`: R13（C TLSベースポインタ）に`runtime·tlsg`のオフセットを加算し、`g`を保存するTLS内の正確なアドレスを計算します。
*   `SUB $0x7000, R31`: `rt0_linux_ppc64le.s`でR13が`0x7000`オフセットされて初期化されているため、ここでそのオフセットを差し引いて実際のTLSベースアドレスに戻します。
*   `MOVD g, 0(R31)`: `g`レジスタの値を計算されたTLSアドレスにストアします。

#### `TEXT runtime·load_g(SB),NOSPLIT,$-8-0`

この関数は、C TLSに保存された`g`の値を`g`レジスタに復元します。
*   `MOVD $runtime·tlsg(SB), R31`: `save_g`と同様に`runtime·tlsg`のオフセットを取得します。
*   `ADD R13, R31`: R13（C TLSベースポインタ）にオフセットを加算します。
*   `SUB $0x7000, R31`: `rt0_linux_ppc64le.s`でR13が`0x7000`オフセットされて初期化されているため、ここでそのオフセットを差し引いて実際のTLSベースアドレスに戻します。
*   `MOVD 0(R31), g`: 計算されたTLSアドレスから`g`の値をロードし、`g`レジスタに復元します。

これらの変更により、PPC64アーキテクチャ上でCgoがGoランタイムの内部状態を破壊することなく、GoとCのコードが安全に相互運用できるようになりました。

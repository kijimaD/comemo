## 変更の背景

このコミットは、Go言語の `text/template` パッケージにおける引数処理のバグを修正するために行われました。具体的には、テンプレート内でパイプライン (`|`) を使用して関数に値を渡す際、そのパイプラインからの値が、関数の可変長引数（variadic arguments）ではなく、誤って固定引数（fixed arguments）として解釈され、バインドされてしまう問題がありました。

このバグは、特に `printf` のような可変長引数を取る関数に対して、パイプラインを通じて単一の値を渡す場合に顕在化しました。本来、パイプラインからの値は関数の最初の引数として渡されるべきですが、内部の引数処理ロジックが不完全であったため、固定引数の数と実際に渡された引数の数の間に不整合が生じ、結果として不正なメモリアクセスやパニックを引き起こす可能性がありました。

コミットメッセージにある「Fixes #8950」は、この問題がGoのバグトラッカーで報告されていたことを示唆しています。この修正は、テンプレートエンジンの堅牢性を高め、開発者が `text/template` をより安全かつ予測可能に利用できるようにすることを目的としています。

## 前提知識の解説

### Go言語の `text/template` パッケージ

`text/template` パッケージは、Go言語に組み込まれているデータ駆動型テンプレートエンジンです。HTMLやテキストファイルを動的に生成するために使用されます。主な特徴は以下の通りです。

*   **データ駆動**: テンプレートはGoのデータ構造（構造体、マップ、スライスなど）を基にレンダリングされます。
*   **アクション**: テンプレート内では、`{{.Field}}` のようなデータアクセス、`{{if .Condition}}...{{end}}` のような条件分岐、`{{range .Slice}}...{{end}}` のようなループ、`{{call .Func}}` のような関数呼び出しなど、様々な「アクション」を実行できます。
*   **パイプライン (`|`)**: テンプレート内で非常に強力な機能の一つがパイプラインです。これはUnixのシェルスクリプトのパイプに似ており、左側のコマンドの出力を右側のコマンドの入力（最初の引数）として渡します。例えば、`{{.Value | html}}` は `.Value` の内容をHTMLエスケープします。

### Go言語の可変長引数（Variadic Arguments）

Go言語では、関数が任意の数の引数を受け入れることができる「可変長引数」をサポートしています。これは、引数リストの最後のパラメータの型名の前に `...` を付けることで宣言されます。

例: `func sum(nums ...int) int`

この `sum` 関数は、`sum(1, 2, 3)` のように複数の整数を受け取ることができます。関数内部では、`nums` は `[]int` 型のスライスとして扱われます。

### `text/template` における関数呼び出しと引数処理

`text/template` は、テンプレート内でGoの関数を呼び出すことができます。関数は、固定引数と可変長引数の両方を持つことができます。テンプレートエンジンは、関数を呼び出す際に、渡された引数をGoの関数のシグネチャに合わせて適切にバインドしようとします。

*   **固定引数**: 関数が明示的に定義された数の引数を受け取る場合、それらは固定引数として扱われます。
*   **パイプライン値**: パイプラインの左側から渡された値は、通常、関数の最初の引数として扱われます。
*   **可変長引数**: 関数が可変長引数を持つ場合、固定引数がすべて満たされた後、残りの引数が可変長引数スライスにまとめられます。

このコミットのバグは、この「パイプライン値」と「固定引数」そして「可変長引数」の間のバインディングロジックに不整合があったことに起因します。

## 技術的詳細

このコミットの技術的な核心は、`src/text/template/exec.go` 内の `evalCall` メソッドにおける引数処理ロジックの修正です。`evalCall` は、テンプレート内で関数が呼び出された際に、その関数の引数を評価し、Goの `reflect.Value` 型に変換して関数に渡す役割を担っています。

問題があったのは、`evalCall` 内で関数の固定引数を処理するループでした。元のコードは以下のようになっていました。

```go
// src/text/template/exec.go (修正前)
func (s *state) evalCall(dot, fun reflect.Value, node parse.Node, name string, args []parse.Node, finalArg reflect.Value) reflect.Value {
    // ...
    argv := make([]reflect.Value, numIn)
    // Args must be evaluated. Fixed args first.
    i := 0
    for ; i < numFixed; i++ { // ここが問題の箇所
        argv[i] = s.evalArg(dot, typ.In(i), args[i])
    }
    // Now the ... args.
    // ...
}
```

ここで `numFixed` は関数の固定引数の数、`args` はテンプレート内で明示的に指定された引数のリストです。`finalArg` はパイプラインから渡された値（もしあれば）を表します。

バグは、`for ; i < numFixed; i++` のループ条件にありました。このループは、関数の固定引数の数 (`numFixed`) だけ `args` スライスから引数を評価しようとします。しかし、次のようなシナリオで問題が発生しました。

1.  関数が可変長引数を持つ（例: `func F(a int, b ...string)`）。
2.  テンプレートでパイプラインを使ってこの関数を呼び出す（例: `{{ "value" | F }}`）。
3.  この場合、`F` の固定引数は `a` の1つです。`args` スライスは空ですが、`finalArg` には `"value"` が含まれます。
4.  `evalCall` はまず固定引数を処理しようとします。`numFixed` は1なので、ループは `i=0` で `args[0]` にアクセスしようとします。
5.  しかし、`args` スライスは空であるため、`args[0]` はインデックス範囲外エラー（panic）を引き起こします。

本来、パイプラインからの値は、明示的な引数が不足している場合に、可変長引数部分に渡されるべきでした。しかし、固定引数を処理するループが `args` の実際の長さを考慮していなかったため、この誤ったアクセスが発生しました。

修正は、このループ条件に `&& i < len(args)` を追加することで、`args` スライスの範囲外アクセスを防ぎ、パイプラインからの値が適切に可変長引数として扱われるようにしました。

## コアとなるコードの解説

### `src/text/template/exec.go` の変更

変更の中心は、`evalCall` 関数内の固定引数を処理するループ条件です。

```go
-	for ; i < numFixed; i++ {
+	for ; i < numFixed && i < len(args); i++ {
```

*   **修正前 (`for ; i < numFixed; i++`)**: このループは、関数の固定引数の数 (`numFixed`) だけ繰り返すことを意図していました。しかし、`args` スライス（テンプレート内で明示的に指定された引数）の実際の長さが `numFixed` よりも小さい場合、`args[i]` へのアクセスが範囲外となり、パニックを引き起こす可能性がありました。特に、パイプラインからの値が唯一の引数として渡される場合、`args` は空になり、この問題が発生しました。
*   **修正後 (`for ; i < numFixed && i < len(args); i++`)**: `&& i < len(args)` という条件が追加されました。これにより、ループは `numFixed` に達するか、または `args` スライスの末尾に達するかのいずれか早い方で停止するようになります。
    *   この変更により、`args[i]` へのアクセスが常に有効な範囲内で行われることが保証されます。
    *   パイプラインからの値が唯一の引数として渡され、それが可変長引数として扱われるべき場合、このループは `args` が空であるためすぐに終了し、`finalArg`（パイプライン値）が後続の可変長引数処理ロジックによって適切にバインドされるようになります。

この小さな変更により、`text/template` がパイプラインと可変長引数を組み合わせた関数呼び出しを正しく処理できるようになり、堅牢性が向上しました。

### `src/text/template/exec_test.go` の変更

新しいテストケース `TestFinalForPrintf` が追加されました。

```go
func TestFinalForPrintf(t *testing.T) {
	tmpl, err := New("").Parse(`{{"x" | printf}}`)
	if err != nil {
		t.Fatal(err)
	}
	var b bytes.Buffer
	err = tmpl.Execute(&b, 0)
	if err != nil {
		t.Fatal(err)
	}
}
```

*   このテストは、`printf` 関数（Goの `fmt.Printf` に対応し、可変長引数を取る）に、パイプラインを通じて単一の文字列 `"x"` を渡すシナリオをシミュレートしています。
*   修正前のコードでは、この `{{\"x\" | printf}}` のようなテンプレートを実行すると、`evalCall` 内で `args[0]` への範囲外アクセスが発生し、パニックを引き起こしていました。
*   このテストは、テンプレートのパースと実行がエラーなく完了することを確認することで、バグが修正されたことを検証しています。`t.Fatal(err)` が呼び出されない限り、テストは成功とみなされます。

このテストケースは、まさに修正されたバグの発生条件を再現しており、修正が正しく機能していることを保証する重要な役割を果たしています。

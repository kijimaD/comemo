# [インデックス 27316] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）におけるシンボルルックアップ処理の最適化を目的としています。具体的には、`Lookupf`関数の使用箇所を削減し、ガベージ生成を抑制する`LookupN`関数を導入しています。また、`LookupBytes`関数における文字列インターニングのオーバーヘッドを排除することで、コンパイラのパフォーマンス向上とメモリ使用量の削減を図っています。

## 変更の背景

Goコンパイラは、プログラムのビルド時に大量のシンボル（変数名、関数名など）を処理します。これらのシンボルは、コンパイラの内部で`Sym`構造体として表現され、その名前は文字列として管理されます。従来の`Lookupf`関数は、`fmt.Sprintf`のようなフォーマット関数を使用してシンボル名を生成していました。`fmt.Sprintf`は、フォーマットされた文字列を生成するたびに新しいメモリを割り当て（ヒープアロケーション）、その結果としてガベージコレクタ（GC）の負荷を増大させていました。コンパイラのようなパフォーマンスが重視されるツールにおいて、このような頻繁なアロケーションはビルド時間の増加やメモリ使用量の増大に直結します。

また、`LookupBytes`関数では、文字列インターニング（string interning）が行われていました。文字列インターニングとは、同じ内容の文字列が複数存在する場合に、メモリ上にその文字列のコピーを一つだけ保持し、他の参照はそのコピーを指すようにする最適化手法です。これによりメモリ使用量を削減できる可能性がありますが、Goコンパイラの特定のユースケースにおいては、インターニングの管理オーバーヘッドがメリットを上回ってしまい、かえってパフォーマンスを低下させている状況でした。

このコミットは、これらの問題に対処し、コンパイラのビルド性能とメモリ効率を改善することを目的としています。コミットメッセージに示されているベンチマーク結果は、メモリ割り当て（alloc/op）とアロケーション回数（allocs/op）の両方で顕著な削減が達成されていることを明確に示しています。また、生成されるパッケージのサイズも削減されており、これはコンパイラが生成するバイナリの効率化にも寄与しています。

## 前提知識の解説

### Goコンパイラ (`cmd/compile/internal/gc`)
Goコンパイラは、Go言語のソースコードを機械語に変換するツールです。`cmd/compile`はコンパイラの主要部分であり、`internal/gc`はその中でも特に重要な、Go言語のフロントエンドとバックエンドの間の共通処理を担うパッケージです。シンボル管理、型チェック、中間コード生成など、コンパイルの多くの段階でシンボルルックアップが頻繁に行われます。

### シンボル (`Sym`)
コンパイラにおいて、シンボルとはプログラム内の識別子（変数名、関数名、型名など）を抽象化した概念です。Goコンパイラでは、これらのシンボルは`Sym`構造体として表現され、その名前（`Name`フィールド）は文字列またはバイトスライスとして保持されます。シンボルは、プログラムの意味解析やコード生成の過程で一意に識別され、管理されます。

### `Lookupf`関数
`Lookupf`は、Goコンパイラ内部でシンボル名を生成し、そのシンボルに対応する`Sym`構造体を取得するための関数でした。関数名の`f`は`fmt.Sprintf`のようにフォーマット文字列と可変引数を受け取ることを示唆しています。例えば、`Lookupf("autotmp_%.4d", statuniqgen)`のように使われ、`autotmp_0001`、`autotmp_0002`といった一時的な変数名を生成していました。この`fmt.Sprintf`の内部処理がヒープアロケーションを頻繁に引き起こし、ガベージコレクタの負担となっていました。

### `LookupBytes`関数と文字列インターニング
`LookupBytes`は、バイトスライスを受け取り、それに対応する`Sym`構造体を取得する関数です。この関数は、以前は文字列インターニングのロジックを含んでいました。文字列インターニングは、同じ文字列リテラルが複数回出現する場合に、メモリ上にその文字列の単一のインスタンスのみを保持し、すべての参照がその単一インスタンスを指すようにする最適化です。これにより、メモリ使用量を削減し、文字列比較のパフォーマンスを向上させることができます。しかし、コンパイラが生成する一時的なシンボル名のように、ユニークな文字列が大量に生成され、かつ短命である場合、インターニングの管理（ハッシュテーブルへの挿入、ルックアップ、衝突解決など）にかかるオーバーヘッドが、メモリ削減のメリットを上回ることがあります。このコミットでは、`LookupBytes`からこのインターニングロジックが削除されました。

### ガベージコレクション (GC) とアロケーション
Go言語は自動ガベージコレクションを採用しており、開発者が手動でメモリを解放する必要はありません。しかし、プログラムが頻繁にヒープメモリを割り当てると、ガベージコレクタがより頻繁に実行され、その分プログラムの実行が一時停止する（ストップ・ザ・ワールド）時間が長くなり、全体的なパフォーマンスが低下します。コンパイラのようなツールでは、ビルド時間が重要な指標となるため、ヒープアロケーションを最小限に抑えることが性能向上の鍵となります。

### `alloc/op` と `allocs/op`
これらはGoのベンチマークツール（`go test -bench=. -benchmem`）で報告される指標です。
- `alloc/op`: 1回の操作（ベンチマーク対象の関数呼び出し）あたりに割り当てられたヒープメモリの総量（バイト単位）。
- `allocs/op`: 1回の操作あたりに行われたヒープアロケーションの回数。
これらの値が低いほど、メモリ効率が良いことを示します。

## 技術的詳細

このコミットの主要な技術的変更点は以下の2つです。

1.  **`LookupN`関数の導入による`Lookupf`の置き換え**:
    `Lookupf`が`fmt.Sprintf`を使用していたために発生していたヒープアロケーションの問題を解決するため、`LookupN`という新しい関数が導入されました。`LookupN`は、プレフィックス文字列と整数値を受け取り、これらを結合してシンボル名を生成します。この際、`fmt.Sprintf`のような動的な文字列生成ではなく、固定サイズのバイト配列（`[20]byte`）をスタック上に確保し、`strconv.AppendInt`を使用して整数値をバイト配列に直接追記します。これにより、ヒープアロケーションを完全に回避し、ガベージ生成をゼロに抑えることができます。

    `strconv.AppendInt`は、`[]byte`スライスに整数値を10進数文字列として追記する関数であり、新しいスライスを生成する際に必要に応じてメモリを再割り当てしますが、ここでは事前に十分なサイズのバッファが用意されているため、再割り当ては発生しません。

2.  **`LookupBytes`からの文字列インターニングの削除**:
    `LookupBytes`関数は、バイトスライスを受け取ってシンボルをルックアップする機能を提供します。以前は、この関数内でルックアップされたシンボル名が内部的にインターニングされていました。しかし、コンパイラが生成する多くの一時的なシンボル名はユニークであり、かつ短命であるため、インターニングによるメモリ削減効果よりも、インターニングの管理（ハッシュテーブルの操作など）にかかるCPUオーバーヘッドの方が大きくなっていました。このコミットでは、このインターニングロジックを削除することで、`LookupBytes`の実行速度を向上させ、全体的なコンパイラのパフォーマンスに貢献しています。

これらの変更により、コンパイラのビルドプロセスにおける一時的な文字列オブジェクトの生成が大幅に削減され、結果としてガベージコレクタの実行頻度が減り、コンパイル時間が短縮され、メモリ使用量も削減されます。コミットメッセージに記載されているベンチマーク結果は、これらの最適化が実際に効果を発揮していることを裏付けています。

## コアとなるコードの解説

### `LookupN`関数の実装

```go
func LookupN(prefix string, n int) *Sym {
	var buf [20]byte // plenty long enough for all current users
	copy(buf[:], prefix)
	b := strconv.AppendInt(buf[:len(prefix)], int64(n), 10)
	return LookupBytes(b)
}
```

この`LookupN`関数は、ガベージフリーなシンボル名生成を実現するための鍵です。

1.  `var buf [20]byte`: まず、スタック上に固定サイズのバイト配列`buf`を宣言します。サイズ`20`は、現在のすべての使用箇所で生成されるシンボル名がこのバッファに収まるように、十分に長いサイズとして選ばれています。スタック上に確保されるため、ヒープアロケーションは発生しません。
2.  `copy(buf[:], prefix)`: `prefix`文字列（例: "a", "~r", "autotmp_"など）を`buf`の先頭にコピーします。
3.  `b := strconv.AppendInt(buf[:len(prefix)], int64(n), 10)`: `strconv.AppendInt`関数を使用して、整数`n`を10進数文字列として`buf`の`prefix`の末尾に追記します。`buf[:len(prefix)]`は、`prefix`がコピーされた直後の位置から追記を開始するためのスライスです。`strconv.AppendInt`は、追記後のバイトスライスを返します。この操作も、`buf`が十分なサイズを持っているため、新しいメモリ割り当てなしで実行されます。
4.  `return LookupBytes(b)`: 最終的に生成されたバイトスライス`b`を`LookupBytes`関数に渡して、対応するシンボルを取得します。`LookupBytes`からは文字列インターニングのロジックが削除されているため、ここでも不要なオーバーヘッドは発生しません。

このアプローチにより、`Lookupf`が`fmt.Sprintf`を使用していた際に発生していた、一時的な文字列オブジェクトのヒープアロケーションとそれに伴うガベージ生成が完全に回避されます。これにより、コンパイラのメモリ効率と実行速度が大幅に向上します。

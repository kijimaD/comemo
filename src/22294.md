## 変更の背景

このコミットの主な背景は、Goランタイムのパフォーマンス最適化、特にガベージコレクション（GC）の効率向上にあります。GoのGCは、ヒープ上のオブジェクトを正確に追跡し、不要になったメモリを解放する役割を担っています。このプロセスにおいて、特定のメモリアドレスがどのオブジェクトに属し、そのオブジェクトのどの部分であるかを特定するために、`heapBitsForObject`のような関数が頻繁に呼び出されます。

従来の`heapBitsForObject`関数では、オブジェクトのオフセットを計算するために除算（`p - base) / s.elemsize`）が使用されていました。しかし、CPUの命令レベルでは、除算は乗算やビットシフトに比べて非常にコストの高い操作です。特に、GCのような頻繁に実行される低レベルの処理において、この除算がボトルネックとなる可能性がありました。

コミットメッセージに「Code with interior pointers is helped much more than code without」とあるように、オブジェクトの内部を指すポインタ（内部ポインタ）が多数存在するようなシナリオでは、`heapBitsForObject`の呼び出し頻度が高くなり、除算のオーバーヘッドが顕著になります。例えば、大きな配列や構造体の中で、その要素やフィールドを指すポインタが多数存在する場合などがこれに該当します。

この問題を解決するため、コンパイル時に除数が既知の定数である場合に適用できる「除算を乗算とビットシフトに変換する」という最適化手法が導入されました。これにより、GCの重要なパスにおける計算コストを削減し、全体的なランタイム性能の向上を目指しています。ベンチマーク結果は、特に内部ポインタが関わる処理（例: `BenchmarkFmtFprintfString`）で顕著な改善が見られることを示しており、この最適化が狙い通りに機能していることを裏付けています。

## 前提知識の解説

### Goランタイムとガベージコレクション (GC)

Go言語は、独自のランタイムシステムを持っており、その中核機能の一つが自動メモリ管理、すなわちガベージコレクション（GC）です。GoのGCは、プログラムが動的に確保したメモリ（ヒープ）のうち、もはやどの部分からも参照されなくなったオブジェクトを自動的に検出し、そのメモリを再利用可能にする役割を担います。これにより、開発者は手動でのメモリ解放の煩わしさから解放され、メモリリークのリスクも低減されます。

GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにしています。
1.  **マークフェーズ**: プログラムの実行を一時停止し、ルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトをマークします。
2.  **スイープフェーズ**: マークされなかったオブジェクト（到達不可能で不要なオブジェクト）をメモリから解放し、再利用可能な状態にします。

このGCプロセスにおいて、ヒープ上のオブジェクトのレイアウトを正確に把握し、ポインタがどこを指しているかを識別することが極めて重要です。

### ヒープ (Heap) と `mspan`

Goランタイムのメモリ管理は、ヒープと呼ばれる動的なメモリ領域で行われます。ヒープは、`mheap`という構造体によって管理され、さらに`mspan`という単位に分割されます。

*   **`mspan`**: `mspan`は、ヒープ上の連続したメモリページ（通常は8KB）の集合体です。Goランタイムは、異なるサイズのオブジェクトを効率的に管理するために、これらの`mspan`を様々な「サイズクラス」に分類します。例えば、8バイトのオブジェクトを格納する`mspan`、16バイトのオブジェクトを格納する`mspan`などがあります。
*   **`elemsize`**: 各`mspan`は、特定のサイズのオブジェクト（`elemsize`）を格納するように設計されています。`mspan`内のオブジェクトはすべて同じサイズです。

### `heapBitsForObject` 関数

`heapBitsForObject`は、GoランタイムのGCにおいて非常に重要な関数です。この関数は、与えられたメモリアドレス`p`がヒープ上のどのオブジェクトに属しているかを特定し、そのオブジェクトの先頭アドレス（`base`）と、GCがオブジェクトのポインタを識別するために使用するメタデータ（`heapBits`）を返します。

GCがヒープをスキャンする際、メモリ上の任意のアドレス`p`が有効なオブジェクトの内部を指している可能性があります。`heapBitsForObject`は、この`p`が属する`mspan`を特定し、その`mspan`内で`p`が何番目のオブジェクトの何バイト目にあたるかを計算します。この計算には、`p`と`mspan`の開始アドレス`s.base()`との差を`s.elemsize`（オブジェクトのサイズ）で除算する操作が含まれていました。

### 内部ポインタ (Interior Pointers)

Goでは、配列の要素や構造体のフィールドなど、オブジェクトの先頭ではない場所を指すポインタを「内部ポインタ」と呼びます。例えば、`&myStruct.field`のようなポインタは内部ポインタです。GCは、これらの内部ポインタも正確に追跡し、それが指すオブジェクトがまだ使用中であるかどうかを判断する必要があります。内部ポインタが多いプログラムでは、`heapBitsForObject`のような関数が頻繁に呼び出されるため、その性能が全体のGC性能に大きく影響します。

### 除算の最適化 (Division by Multiplication)

コンピュータのCPUにおいて、整数除算命令は乗算命令やビットシフト命令に比べて実行に多くのクロックサイクルを要します。特に、除数がコンパイル時に既知の定数である場合、除算を乗算とビットシフトの組み合わせに変換することで、より高速に計算できることが知られています。このテクニックは、コンパイラ最適化や低レベルのシステムプログラミングでよく用いられます。

基本的なアイデアは、`n / d` を `n * (1/d)` と考え、`1/d` を適切なスケールファクタ（例えば `2^k`）を掛けた整数で近似することです。つまり、`n / d ≈ (n * M) >> S` のような形に変換します。ここで`M`は「マジックナンバー（magic number）」、`S`はシフト量です。このマジックナンバーとシフト量は、除数`d`に基づいて事前に計算されます。

この最適化は、特にHacker's Delightのような書籍や、Ridiculous Fishのブログ記事で詳細に解説されています。コミットメッセージでもこれらの情報源が参照されており、Goランタイムがこの高度な最適化手法を適用していることがわかります。

## 技術的詳細

このコミットの核心は、`src/runtime/mbitmap.go` 内の `heapBitsForObject` 関数における除算操作の置き換えです。

変更前は、オブジェクトのオフセットを計算するために以下の除算が行われていました。

```go
base += (p - base) / s.elemsize * s.elemsize
```

ここで `(p - base) / s.elemsize` は、`p`が`mspan`の先頭から数えて何番目のオブジェクトに属するかを計算しています。この除算がパフォーマンスのボトルネックとなる可能性がありました。

変更後、この除算は乗算とビットシフトの組み合わせに置き換えられました。

```go
// n := (p - base) / s.elemsize, using division by multiplication
n := uintptr(uint64(p-base) >> s.divShift * uint64(s.divMul) >> s.divShift2)
base += n * s.elemsize
```

この新しい計算式では、`s.divShift`、`s.divMul`、`s.divShift2`という3つの新しいフィールドが使用されています。これらは、特定の`elemsize`（オブジェクトサイズ）に対する除算を乗算とシフトで実現するための「マジック定数」です。

これらのマジック定数を格納するために、`src/runtime/mheap.go` の `mspan` 構造体に以下のフィールドが追加されました。

```go
type mspan struct {
    // ... 既存のフィールド ...
    divMul      uint32   // for divide by elemsize - divMagic.mul
    divShift    uint8    // for divide by elemsize - divMagic.shift
    divShift2   uint8    // for divide by elemsize - divMagic.shift2
    elemsize    uintptr  // computed from sizeclass or from npages
    // ... その他のフィールド ...
}
```

これらのマジック定数は、`mspan`が初期化される際に、その`elemsize`に基づいて計算され、`mspan`構造体に格納されます。この計算は、`src/runtime/msize.go` に新しく追加された `computeDivMagic` 関数によって行われます。

`msize.go` には、`divMagic` 構造体と `computeDivMagic` 関数が追加されました。

```go
type divMagic struct {
    shift  uint8
    mul    uint32
    shift2 uint8
}

func computeDivMagic(d uint32) divMagic {
    var m divMagic

    // Compute pre-shift by factoring power of 2 out of d.
    for d&1 == 0 {
        m.shift++
        d >>= 1
    }

    // Compute largest k such that ⌈2^k / d⌉ fits in a 32-bit int.
    // This is always a good enough approximation.
    // We could use smaller k for some divisors but there's no point.
    k := uint8(63)
    d64 := uint64(d)
    for ((1<<k)+d64-1)/d64 >= 1<<32 {
        k--
    }
    m.mul = uint32(((1 << k) + d64 - 1) / d64) //  ⌈2^k / d⌉
    m.shift2 = k
    return m
}
```

`computeDivMagic`関数は、与えられた除数 `d`（この場合は`elemsize`）に対して、除算を乗算とシフトで置き換えるための最適な`shift`、`mul`、`shift2`の値を計算します。このアルゴリズムは、Hacker's Delightで紹介されているテクニックに基づいています。

具体的には、`d`から2のべき乗の因子を`m.shift`として抽出し、残りの奇数因子に対してマジックナンバー`m.mul`とシフト量`m.shift2`を計算します。これにより、`n / d` は `((n >> m.shift) * m.mul) >> m.shift2` という形式で近似または正確に計算できるようになります。コミットメッセージのコメントにもあるように、Goのmallocブロックサイズは常に偶数であるため、追加の調整が必要な「巨大なコーナーケース」は発生しないように設計されています。

また、`msize.go` の `initSizes` 関数内で、`class_to_divmagic` という配列が初期化されるようになりました。この配列は、各サイズクラス（`elemsize`）に対応する`divMagic`構造体を事前に計算して格納します。これにより、ランタイム中に`heapBitsForObject`が呼び出された際に、毎回`computeDivMagic`を呼び出す必要がなくなり、ルックアップだけでマジック定数を利用できるようになります。

ベンチマーク結果を見ると、特に`BenchmarkFmtFprintfString` (`-18.13%`)、`BenchmarkFmtFprintfIntInt` (`-11.36%`)、`BenchmarkFmtFprintfPrefixedInt` (`-11.30%`) など、`fmt.Fprintf`系のベンチマークで大きな改善が見られます。これらの関数は文字列のフォーマット処理を行うため、内部で多くの小さなオブジェクト（文字列の断片など）が生成され、内部ポインタが頻繁に利用される可能性があります。そのため、`heapBitsForObject`の呼び出し頻度が高くなり、今回の最適化が顕著な効果を発揮したと考えられます。

### `heapBitsForObject` における除算の置き換え

`src/runtime/mbitmap.go` の `heapBitsForObject` 関数では、オブジェクトのベースアドレスを計算する際に、与えられたポインタ `p` が属するオブジェクトのインデックス `n` を求めるために、`n := (p - base) / s.elemsize` という除算が行われていました。

この除算が、以下のように乗算とビットシフトの組み合わせに置き換えられました。

```go
n := uintptr(uint64(p-base) >> s.divShift * uint64(s.divMul) >> s.divShift2)
```

*   `p - base`: オブジェクトの先頭アドレス `base` から、現在のポインタ `p` までのオフセットを計算します。
*   `uint64(p-base)`: オフセットを `uint64` にキャストします。これは、シフト操作が正しく行われるようにするためです。
*   `>> s.divShift`: まず、`s.divShift` ビット右にシフトします。これは、除数 `s.elemsize` に含まれる2のべき乗の因子を取り除くための「事前シフト」です。例えば、`s.elemsize` が8（2^3）であれば、`s.divShift` は3となり、ここで3ビット右シフトされます。
*   `* uint64(s.divMul)`: 次に、`s.divMul`（マジックナンバー）を乗算します。このマジックナンバーは、除数の残りの奇数因子に対する逆数を近似したものです。
*   `>> s.divShift2`: 最後に、`s.divShift2` ビット右にシフトします。これは、マジックナンバーを乗算した結果を適切なスケールに戻すための「事後シフト」です。

この一連の操作により、除算命令を使用することなく、高速に乗算とシフトだけで除算と同じ結果（または非常に近い近似値）を得ることができます。

また、デバッグ用のコードとして `debugMagic` フラグが追加されており、新しい計算結果 `n` と従来の除算による結果 `n2` を比較し、不一致があればパニックを発生させることで、最適化の正確性を検証できるようになっています。

`src/runtime/msize.go` は、Goランタイムのメモリサイズクラスに関する定義と初期化を行うファイルです。このコミットでは、除算最適化のための中心的なロジックがここに追加されました。

```go
func computeDivMagic(d uint32) divMagic {
    var m divMagic

    // Compute pre-shift by factoring power of 2 out of d.
    for d&1 == 0 {
        m.shift++
        d >>= 1
    }

    // Compute largest k such that ⌈2^k / d⌉ fits in a 32-bit int.
    k := uint8(63)
    d64 := uint64(d)
    for ((1<<k)+d64-1)/d64 >= 1<<32 {
        k--
    }
    m.mul = uint32(((1 << k) + d64 - 1) / d64) //  ⌈2^k / d⌉
    m.shift2 = k
    return m
}
```

この関数は、除数 `d` から2のべき乗の因子を抽出し（`m.shift`）、残りの部分に対してマジックナンバー `m.mul` とシフト量 `m.shift2` を計算します。`m.mul` は `⌈2^k / d⌉` として計算され、これは除数 `d` の逆数を `2^k` のスケールで近似したものです。

このループにより、Goランタイムが起動する際に、すべての可能な`elemsize`（サイズクラス）に対して、対応するマジック定数が一度だけ計算され、`class_to_divmagic`配列に格納されます。これにより、ランタイム中に`mspan`が割り当てられる際に、計算済みのマジック定数を高速にルックアップして利用できるようになり、実行時のオーバーヘッドを最小限に抑えることができます。

この一連の変更により、GoランタイムはGCの重要なパスにおける除算操作を、より効率的な乗算とビットシフトに置き換えることに成功し、特に内部ポインタを多用するアプリケーションのパフォーマンス向上に貢献しています。

## 変更の背景

## 前提知識の解説

### Goランタイムとガベージコレクション (GC)

Go言語は、独自のランタイムシステムを持っており、その中核機能の一つが自動メモリ管理、すなわちガベージコレクション（GC）です。GoのGCは、プログラムが動的に確保したメモリ（ヒープ）のうち、もはやどの部分からも参照されなくなったオブジェクトを自動的に検出し、そのメモリを再利用可能にする役割を担います。これにより、開発者は手動でのメモリ解放の煩わしさから解放され、メモリリークのリスクも低減されます。

GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにしています。
1.  **マークフェーズ**: プログラムの実行を一時停止し、ルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトをマークします。
2.  **スイープフェーズ**: マークされなかったオブジェクト（到達不可能で不要なオブジェクト）をメモリから解放し、再利用可能な状態にします。

このGCプロセスにおいて、ヒープ上のオブジェクトのレイアウトを正確に把握し、ポインタがどこを指しているかを識別することが極めて重要です。

### ヒープ (Heap) と `mspan`

Goランタイムのメモリ管理は、ヒープと呼ばれる動的なメモリ領域で行われます。ヒープは、`mheap`という構造体によって管理され、さらに`mspan`という単位に分割されます。

*   **`mspan`**: `mspan`は、ヒープ上の連続したメモリページ（通常は8KB）の集合体です。Goランタイムは、異なるサイズのオブジェクトを効率的に管理するために、これらの`mspan`を様々な「サイズクラス」に分類します。例えば、8バイトのオブジェクトを格納する`mspan`、16バイトのオブジェクトを格納する`mspan`などがあります。
*   **`elemsize`**: 各`mspan`は、特定のサイズのオブジェクト（`elemsize`）を格納するように設計されています。`mspan`内のオブジェクトはすべて同じサイズです。

### `heapBitsForObject` 関数

`heapBitsForObject`は、GoランタイムのGCにおいて非常に重要な関数です。この関数は、与えられたメモリアドレス`p`がヒープ上のどのオブジェクトに属しているかを特定し、そのオブジェクトの先頭アドレス（`base`）と、GCがオブジェクトのポインタを識別するために使用するメタデータ（`heapBits`）を返します。

GCがヒープをスキャンする際、メモリ上の任意のアドレス`p`が有効なオブジェクトの内部を指している可能性があります。`heapBitsForObject`は、この`p`が属する`mspan`を特定し、その`mspan`内で`p`が何番目のオブジェクトの何バイト目にあたるかを計算します。この計算には、`p`と`mspan`の開始アドレス`s.base()`との差を`s.elemsize`（オブジェクトのサイズ）で除算する操作が含まれていました。

### 内部ポインタ (Interior Pointers)

Goでは、配列の要素や構造体のフィールドなど、オブジェクトの先頭ではない場所を指すポインタを「内部ポインタ」と呼びます。例えば、`&myStruct.field`のようなポインタは内部ポインタです。GCは、これらの内部ポインタも正確に追跡し、それが指すオブジェクトがまだ使用中であるかどうかを判断する必要があります。内部ポインタが多いプログラムでは、`heapBitsForObject`のような関数が頻繁に呼び出されるため、その性能が全体のGC性能に大きく影響します。

### 除算の最適化 (Division by Multiplication)

コンピュータのCPUにおいて、整数除算命令は乗算命令やビットシフト命令に比べて実行に多くのクロックサイクルを要します。特に、除数がコンパイル時に既知の定数である場合、除算を乗算とビットシフトの組み合わせに変換することで、より高速に計算できることが知られています。このテクニックは、コンパイラ最適化や低レベルのシステムプログラミングでよく用いられます。

基本的なアイデアは、`n / d` を `n * (1/d)` と考え、`1/d` を適切なスケールファクタ（例えば `2^k`）を掛けた整数で近似することです。つまり、`n / d ≈ (n * M) >> S` のような形に変換します。ここで`M`は「マジックナンバー（magic number）」、`S`はシフト量です。このマジックナンバーとシフト量は、除数`d`に基づいて事前に計算されます。

この最適化は、特にHacker's Delightのような書籍や、Ridiculous Fishのブログ記事で詳細に解説されています。コミットメッセージでもこれらの情報源が参照されており、Goランタイムがこの高度な最適化手法を適用していることがわかります。

## 技術的詳細

このコミットの核心は、`src/runtime/mbitmap.go` 内の `heapBitsForObject` 関数における除算操作の置き換えです。

変更前は、オブジェクトのオフセットを計算するために以下の除算が行われていました。

```go
base += (p - base) / s.elemsize * s.elemsize
```

ここで `(p - base) / s.elemsize` は、`p`が`mspan`の先頭から数えて何番目のオブジェクトに属するかを計算しています。この除算がパフォーマンスのボトルネックとなる可能性がありました。

変更後、この除算は乗算とビットシフトの組み合わせに置き換えられました。

```go
// n := (p - base) / s.elemsize, using division by multiplication
n := uintptr(uint64(p-base) >> s.divShift * uint64(s.divMul) >> s.divShift2)
base += n * s.elemsize
```

この新しい計算式では、`s.divShift`、`s.divMul`、`s.divShift2`という3つの新しいフィールドが使用されています。これらは、特定の`elemsize`（オブジェクトサイズ）に対する除算を乗算とシフトで実現するための「マジック定数」です。

これらのマジック定数を格納するために、`src/runtime/mheap.go` の `mspan` 構造体に以下のフィールドが追加されました。

```go
type mspan struct {
    // ... 既存のフィールド ...
    divMul      uint32   // for divide by elemsize - divMagic.mul
    ref         uint16   // capacity - number of objects in freelist
    sizeclass   uint8    // size class
    incache     bool     // being used by an mcache
    state       uint8    // mspaninuse etc
    needzero    uint8    // needs to be zeroed before allocation
    divShift    uint8    // for divide by elemsize - divMagic.shift
    divShift2   uint8    // for divide by elemsize - divMagic.shift2
    elemsize    uintptr  // computed from sizeclass or from npages
    unusedsince int64    // first time spotted by gc in mspanfree state
    npreleased  uintptr  // number of pages released to the os
    // ... その他のフィールド ...
}
```

これらのマジック定数は、`mspan`が初期化される際に、その`elemsize`に基づいて計算され、`mspan`構造体に格納されます。この計算は、`src/runtime/msize.go` に新しく追加された `computeDivMagic` 関数によって行われます。

`msize.go` には、`divMagic` 構造体と `computeDivMagic` 関数が追加されました。

```go
type divMagic struct {
    shift  uint8
    mul    uint32
    shift2 uint8
}

func computeDivMagic(d uint32) divMagic {
    var m divMagic

    // Compute pre-shift by factoring power of 2 out of d.
    for d&1 == 0 {
        m.shift++
        d >>= 1
    }

    // Compute largest k such that ⌈2^k / d⌉ fits in a 32-bit int.
    // This is always a good enough approximation.
    // We could use smaller k for some divisors but there's no point.
    k := uint8(63)
    d64 := uint64(d)
    for ((1<<k)+d64-1)/d64 >= 1<<32 {
        k--
    }
    m.mul = uint32(((1 << k) + d64 - 1) / d64) //  ⌈2^k / d⌉
    m.shift2 = k
    return m
}
```

`computeDivMagic`関数は、与えられた除数 `d`（この場合は`elemsize`）に対して、除算を乗算とシフトで置き換えるための最適な`shift`、`mul`、`shift2`の値を計算します。このアルゴリズムは、Hacker's Delightで紹介されているテクニックに基づいています。

具体的には、`d`から2のべき乗の因子を`m.shift`として抽出し、残りの奇数因子に対してマジックナンバー`m.mul`とシフト量`m.shift2`を計算します。これにより、`n / d` は `((n >> m.shift) * m.mul) >> m.shift2` という形式で近似または正確に計算できるようになります。コミットメッセージのコメントにもあるように、Goのmallocブロックサイズは常に偶数であるため、追加の調整が必要な「巨大なコーナーケース」は発生しないように設計されています。

また、`msize.go` の `initSizes` 関数内で、`class_to_divmagic` という配列が初期化されるようになりました。この配列は、各サイズクラス（`elemsize`）に対応する`divMagic`構造体を事前に計算して格納します。これにより、ランタイム中に`heapBitsForObject`が呼び出された際に、毎回`computeDivMagic`を呼び出す必要がなくなり、ルックアップだけでマジック定数を利用できるようになります。

ベンチマーク結果を見ると、特に`BenchmarkFmtFprintfString` (`-18.13%`)、`BenchmarkFmtFprintfIntInt` (`-11.36%`)、`BenchmarkFmtFprintfPrefixedInt` (`-11.30%`) など、`fmt.Fprintf`系のベンチマークで大きな改善が見られます。これらの関数は文字列のフォーマット処理を行うため、内部で多くの小さなオブジェクト（文字列の断片など）が生成され、内部ポインタが頻繁に利用される可能性があります。そのため、`heapBitsForObject`の呼び出し頻度が高くなり、今回の最適化が顕著な効果を発揮したと考えられます。

## コアとなるコードの解説

### `heapBitsForObject` における除算の置き換え

`src/runtime/mbitmap.go` の `heapBitsForObject` 関数では、オブジェクトのベースアドレスを計算する際に、与えられたポインタ `p` が属するオブジェクトのインデックス `n` を求めるために、`n := (p - base) / s.elemsize` という除算が行われていました。

この除算が、以下のように乗算とビットシフトの組み合わせに置き換えられました。

```go
n := uintptr(uint64(p-base) >> s.divShift * uint64(s.divMul) >> s.divShift2)
```

*   `p - base`: オブジェクトの先頭アドレス `base` から、現在のポインタ `p` までのオフセットを計算します。
*   `uint64(p-base)`: オフセットを `uint64` にキャストします。これは、シフト操作が正しく行われるようにするためです。
*   `>> s.divShift`: まず、`s.divShift` ビット右にシフトします。これは、除数 `s.elemsize` に含まれる2のべき乗の因子を取り除くための「事前シフト」です。例えば、`s.elemsize` が8（2^3）であれば、`s.divShift` は3となり、ここで3ビット右シフトされます。
*   `* uint64(s.divMul)`: 次に、`s.divMul`（マジックナンバー）を乗算します。このマジックナンバーは、除数の残りの奇数因子に対する逆数を近似したものです。
*   `>> s.divShift2`: 最後に、`s.divShift2` ビット右にシフトします。これは、マジックナンバーを乗算した結果を適切なスケールに戻すための「事後シフト」です。

この一連の操作により、除算命令を使用することなく、高速に乗算とシフトだけで除算と同じ結果（または非常に近い近似値）を得ることができます。

また、デバッグ用のコードとして `debugMagic` フラグが追加されており、新しい計算結果 `n` と従来の除算による結果 `n2` を比較し、不一致があればパニックを発生させることで、最適化の正確性を検証できるようになっています。

### `mspan` 構造体へのマジック定数の追加

`src/runtime/mheap.go` の `mspan` 構造体には、この除算最適化のために必要なマジック定数を格納する新しいフィールドが追加されました。

```go
type mspan struct {
    // ...
    divMul      uint32
    divShift    uint8
    divShift2   uint8
    elemsize    uintptr
    // ...
}
```

*   `divMul`: マジックナンバー（乗算器）。
*   `divShift`: 事前シフト量。
*   `divShift2`: 事後シフト量。

これらのフィールドは、各`mspan`が管理するオブジェクトのサイズ（`elemsize`）に固有の値を持つため、`mspan`ごとにこれらの定数を保持することで、`heapBitsForObject`が呼び出された際にすぐに利用できるようになります。

### `msize.go` におけるマジック定数の計算と事前計算

`src/runtime/msize.go` は、Goランタイムのメモリサイズクラスに関する定義と初期化を行うファイルです。このコミットでは、除算最適化のための中心的なロジックがここに追加されました。

まず、`divMagic`という新しい構造体が定義されました。

```go
type divMagic struct {
    shift  uint8
    mul    uint32
    shift2 uint8
}
```

次に、この`divMagic`構造体を計算するための `computeDivMagic` 関数が追加されました。この関数は、与えられた除数 `d` に対して、最適な`shift`、`mul`、`shift2`の値を計算します。

```go
func computeDivMagic(d uint32) divMagic {
    var m divMagic

    // Compute pre-shift by factoring power of 2 out of d.
    for d&1 == 0 {
        m.shift++
        d >>= 1
    }

    // Compute largest k such that ⌈2^k / d⌉ fits in a 32-bit int.
    k := uint8(63)
    d64 := uint64(d)
    for ((1<<k)+d64-1)/d64 >= 1<<32 {
        k--
    }
    m.mul = uint32(((1 << k) + d64 - 1) / d64) //  ⌈2^k / d⌉
    m.shift2 = k
    return m
}
```

この関数は、除数 `d` から2のべき乗の因子を抽出し（`m.shift`）、残りの部分に対してマジックナンバー `m.mul` とシフト量 `m.shift2` を計算します。`m.mul` は `⌈2^k / d⌉` として計算され、これは除数 `d` の逆数を `2^k` のスケールで近似したものです。

最後に、`initSizes` 関数内で、`class_to_divmagic` というグローバル配列が初期化されるようになりました。

```go
var class_to_divmagic [_NumSizeClasses]divMagic

func initSizes() {
    // ...
    for i := 1; i < len(class_to_size); i++ {
        class_to_divmagic[i] = computeDivMagic(uint32(class_to_size[i]))
    }
    // ...
}
```

このループにより、Goランタイムが起動する際に、すべての可能な`elemsize`（サイズクラス）に対して、対応するマジック定数が一度だけ計算され、`class_to_divmagic`配列に格納されます。これにより、ランタイム中に`mspan`が割り当てられる際に、計算済みのマジック定数を高速にルックアップして利用できるようになり、実行時のオーバーヘッドを最小限に抑えることができます。

この一連の変更により、GoランタイムはGCの重要なパスにおける除算操作を、より効率的な乗算とビットシフトに置き換えることに成功し、特に内部ポインタを多用するアプリケーションのパフォーマンス向上に貢献しています。

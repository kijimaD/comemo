## 変更の背景

このコミットの背景には、Go言語がx86-64アーキテクチャの高度なベクトル拡張命令セットであるAVXおよびAVX2をより効果的に活用しようとする意図があります。AVX命令は、単一の命令で複数のデータ要素を並列処理するSIMD（Single Instruction, Multiple Data）能力を提供し、特に数値計算、メディア処理、暗号化などの分野で大幅なパフォーマンス向上をもたらします。

以前のGoのアセンブラは、AVX命令のサポートが不完全であったり、標準的な命名規則や引数形式に準拠していなかった可能性があります。これにより、開発者がAVX命令を直接使用する際に混乱が生じたり、GoランタイムがAVXの恩恵を最大限に受けられないという問題がありました。

このコミットは、これらの問題を解決し、GoのアセンブラがAVX命令を完全に、かつ標準的な方法でサポートすることで、Goプログラムのパフォーマンスを向上させることを目的としています。特に、`runtime`パッケージ内のメモリ操作（`memequal`や`memclr`など）は、システム全体のパフォーマンスに大きく影響するため、これらの低レベルな最適化はGoアプリケーション全体の高速化に寄与します。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念について基本的な知識が必要です。

### 1. x86-64アーキテクチャとアセンブリ言語

*   **x86-64**: IntelおよびAMDが開発した64ビット命令セットアーキテクチャ。Go言語は主にこのアーキテクチャ上で動作します。
*   **アセンブリ言語**: CPUが直接実行できる機械語命令を人間が読み書きしやすい形式で表現した低レベル言語。Goのランタイムや一部のパフォーマンスクリティカルなコードはアセンブリ言語で記述されています。
*   **レジスタ**: CPU内部にある高速な記憶領域。汎用レジスタ（RAX, RBXなど）、命令ポインタ（RIP）、スタックポインタ（RSP）などがあります。

### 2. SIMD (Single Instruction, Multiple Data)

*   **SIMD**: 1つの命令で複数のデータ要素に対して同じ操作を同時に実行する並列処理技術。これにより、データ並列性の高い処理（例: ベクトル演算）を高速化できます。
*   **XMM/YMM/ZMMレジスタ**: SIMD演算に使用される特殊なレジスタ。
    *   **XMMレジスタ**: 128ビット幅のレジスタ（X0-X15）。SSE（Streaming SIMD Extensions）命令で使用されます。
    *   **YMMレジスタ**: 256ビット幅のレジスタ（Y0-Y15）。AVX命令で使用され、XMMレジスタの上位128ビットを拡張したものです。
    *   **ZMMレジスタ**: 512ビット幅のレジスタ（Z0-Z31）。AVX-512命令で使用されます。

### 3. AVX (Advanced Vector Extensions) および AVX2

*   **AVX**: Intelが開発したSIMD命令セットの拡張。256ビット幅のYMMレジスタを導入し、浮動小数点演算の性能を向上させました。AVX命令は、従来のSSE命令よりも多くのレジスタとより柔軟なオペランド指定を可能にします。
*   **AVX2**: AVXの次の世代の拡張。整数演算にも256ビット幅のYMMレジスタを使用できるようになり、より広範なアプリケーションでSIMDの恩恵を受けられるようになりました。
*   **VEXプレフィックス**: AVX命令のエンコーディングに使用される特別なプレフィックス。従来の命令エンコーディングよりも多くの情報を（例: レジスタ番号、オペランドサイズ、命令プレフィックスなど）効率的に表現できます。2バイトまたは3バイトの形式があります。
    *   `VEX.vvvv`: 3オペランド命令で使用されるソースレジスタ（vvvvフィールド）を指定します。これはレジスタ番号のビット反転値でエンコードされます。
    *   `VEX.L`: ベクトル長（128ビットまたは256ビット）を指定します。
    *   `VEX.W`: オペランドサイズ（32ビットまたは64ビット）を指定します。
    *   `VEX.pp`: 命令プレフィックス（66h, F2h, F3h）を指定します。
    *   `VEX.m-mmmm`: 命令マップ（0Fh, 0F38h, 0F3Ah）を指定します。

### 4. Go言語のアセンブラ (`cmd/asm`)

*   Go言語は、独自のツールチェーンを持ち、その中には独自のアセンブラ（`cmd/asm`）が含まれています。これはAT&T構文ではなく、Plan 9アセンブラ構文に基づいています。
*   Goのアセンブラは、Goのソースコードから直接アセンブリコードを生成するのではなく、Goのコンパイラが生成した中間表現をアセンブリコードに変換する役割を担います。また、Goのランタイムや一部の標準ライブラリは、パフォーマンス最適化のために手書きのアセンブリコードを含んでいます。

### 5. Goランタイム

*   Goランタイムは、ガベージコレクション、スケジューラ、メモリ管理など、Goプログラムの実行をサポートする低レベルなコンポーネントの集合体です。これらのコンポーネントの一部は、パフォーマンスのためにアセンブリ言語で記述されています。
*   `memequal` (メモリ比較) や `memclr` (メモリクリア) のような関数は、頻繁に呼び出されるため、アセンブリレベルでの最適化が非常に重要です。

## 技術的詳細

このコミットの技術的な核心は、GoのアセンブラがAVX命令を正確にエンコードし、Goランタイムがそれらを効率的に利用できるようにすることにあります。

1.  **VEXプレフィックスのエンコーディングの改善**:
    *   `src/cmd/internal/obj/x86/asm6.go`では、VEXプレフィックスを構成するための新しい定数（`vex66`, `vexF3`, `vex128`, `vex256`など）が導入されています。これらはVEXプレフィックスの各フィールド（P, L, W, M）に対応し、命令のエンコーディングに必要な情報をビット単位で表現します。
    *   `vexprefix`関数が`asmvex`関数に置き換えられました。`asmvex`は、命令のオペランド（r/m、vvvv、reg）とVEXプレフィックスの定数、オペコードバイトを受け取り、2バイトまたは3バイトのVEXプレフィックスを正確に生成します。これにより、AVX命令の複雑なエンコーディングルール（例: REXプレフィックスのビット反転、vvvvフィールドのエンコード）が適切に処理されます。
    *   特に、`VEX_128_66_0F_WIG`のような定数は、特定のVEXプレフィックスの組み合わせ（例: 128ビットベクトル長、66hプレフィックス、0Fhマップ、WIG=W無視）を簡潔に表現し、`optab`での命令定義を容易にします。

2.  **AVX命令の命名と引数規則の標準化**:
    *   `src/cmd/internal/obj/x86/a.out.go`と`src/cmd/internal/obj/x86/anames.go`では、`MOVHDU`, `AMOVNTHD`, `AMOVHDA`といったGoアセンブラ独自の命令名が、標準的なAVX命令名である`VMOVDQU`, `VMOVNTDQ`, `VMOVDQA`に置き換えられています。これにより、Goのアセンブラが生成するコードが、Intelの命令セットリファレンスなどと整合性が取れるようになり、可読性と保守性が向上します。
    *   `src/cmd/asm/internal/asm/testdata/amd64enc.s`の変更は、以前`//TODO:`コメントアウトされていたAVX命令のテストケースが有効化されたことを示しています。これは、アセンブラがこれらの命令を正しくパースし、エンコードできるようになったことを意味します。

3.  **YMMレジスタのサポート強化**:
    *   `src/cmd/internal/obj/x86/asm6.go`では、YMMレジスタを表す新しいレジスタタイプ`Yyr`と`Yym`が追加され、`instinit`および`oclass`関数がこれらのレジスタを認識するように更新されています。これにより、アセンブラは256ビット幅のYMMレジスタを命令のオペランドとして正しく扱えるようになります。
    *   `asmandsz`関数も`REG_Y0+15`までのレジスタ範囲を考慮するように更新され、YMMレジスタのフルセットがサポートされます。

4.  **GoランタイムでのAVX2命令の活用**:
    *   `src/runtime/asm_amd64.s`と`src/runtime/memclr_amd64.s`では、`memequal`や`memclr`といったパフォーマンスクリティカルな関数において、従来の`MOVHDU`命令やXMMレジスタの使用が、`VMOVDQU`, `VMOVNTDQ`, `VPXOR`, `VPCMPEQB`, `VPAND`, `VPMOVMSKB`, `VPTEST`といったAVX2命令とYMMレジスタの使用に置き換えられています。
    *   これにより、これらのメモリ操作が256ビット幅で並列処理されるようになり、特に大量のメモリを扱う場合に大幅な性能向上が期待できます。例えば、`memclr_amd64.s`では、`VPXOR Y0, Y0, Y0`でYMMレジスタをゼロクリアし、`VMOVDQU Y0, 0(DI)`などで256ビット単位でメモリをクリアしています。また、`VMOVNTDQ`（Non-Temporal Move Double Quadword）は、キャッシュを汚染せずに直接メモリに書き込むことで、大量のデータ転送の効率を高めます。

これらの変更は、Go言語が最新のCPUアーキテクチャの機能を最大限に引き出し、より高性能なアプリケーションを構築するための基盤を強化するものです。

## コアとなるコードの解説

### `src/cmd/internal/obj/x86/asm6.go` の `asmvex` 関数と VEX プレフィックス定数

このファイルはGoのアセンブラのx86バックエンドの中核であり、命令のエンコーディングロジックを含んでいます。

```go
// Encoding for VEX prefix in tables.
// The P, L, and W fields are chosen to match
// their eventual locations in the VEX prefix bytes.

// P field - 2 bits
vex66 = 1 << 0
vexF3 = 2 << 0
vexF2 = 3 << 0
// L field - 1 bit
vexLZ  = 0 << 2
vexLIG = 0 << 2
vex128 = 0 << 2
vex256 = 1 << 2
// W field - 1 bit
vexWIG = 0 << 7
vexW0  = 0 << 7
vexW1  = 1 << 7
// M field - 5 bits, but mostly reserved; we can store up to 4
vex0F   = 1 << 3
vex0F38 = 2 << 3
vex0F3A = 3 << 3

// Combinations used in the manual.
VEX_128_0F_WIG      = vex128 | vex0F | vexWIG
VEX_128_66_0F_W0    = vex128 | vex66 | vex0F | vexW0
// ... (他のVEX組み合わせ定数) ...
```
これらの定数は、VEXプレフィックスの各ビットフィールド（P, L, W, M）を表現し、それらを組み合わせて特定のAVX命令に必要なVEXプレフィックスの構成を定義します。例えば、`VEX_128_66_0F_WIG`は、128ビットベクトル長、66hプレフィックス、0Fhマップ、Wフィールド無視のVEXプレフィックスを示します。

```go
func asmvex(ctxt *obj.Link, rm, v, r *obj.Addr, vex, opcode uint8) {
	ctxt.Vexflag = 1
	rexR := regrex[r.Reg] & Rxr
	rexB := regrex[rm.Reg] & Rxb
	rexX := regrex[rm.Index] & Rxx
	vexM := (vex >> 3) & 0xF
	vexWLP := vex & 0x87
	vexV := byte(0)
	if v != nil {
		vexV = byte(reg[v.Reg]|(regrex[v.Reg]&Rxr)<<1) & 0xF
	}
	vexV ^= 0xF // Invert vvvv field
	if vexM == 1 && (rexX|rexB) == 0 && vex&vexW1 == 0 {
		// Can use 2-byte encoding.
		ctxt.Andptr[0] = 0xc5
		ctxt.Andptr[1] = byte(rexR<<5) ^ 0x80 | vexV<<3 | vexWLP
		ctxt.Andptr = ctxt.Andptr[2:]
	} else {
		// Must use 3-byte encoding.
		ctxt.Andptr[0] = 0xc4
		ctxt.Andptr[1] = (byte(rexR|rexX|rexB) << 5) ^ 0xE0 | vexM
		ctxt.Andptr[2] = vexV<<3 | vexWLP
		ctxt.Andptr = ctxt.Andptr[3:]
	}
	ctxt.Andptr[0] = opcode
	ctxt.Andptr = ctxt.Andptr[1:]
}
```
`asmvex`関数は、VEXプレフィックスとオペコードバイトを生成する主要なロジックです。
*   `rm`, `v`, `r`はそれぞれ命令のオペランドに対応するアドレス構造体です。`vex`は上記のVEX組み合わせ定数、`opcode`は命令のオペコードバイトです。
*   `rexR`, `rexB`, `rexX`は、REXプレフィックスのR, B, Xビットを抽出します。これらはVEXプレフィックス内で反転されてエンコードされます。
*   `vexM`はVEXプレフィックスのMフィールド（命令マップ）を、`vexWLP`はW, L, Pフィールドを抽出します。
*   `vexV`は、3オペランド命令のvvvvフィールドをエンコードします。これはソースレジスタの番号を反転したものです。
*   2バイトVEXプレフィックス（`0xC5`）または3バイトVEXプレフィックス（`0xC4`）のどちらを使用するかを決定し、それぞれの形式に従ってバイト列を生成します。この選択は、命令マップ（`vexM`）やREXビット（`rexX`, `rexB`）によって決まります。
*   最終的に、生成されたVEXプレフィックスの後に命令の`opcode`バイトを配置します。

この関数により、GoのアセンブラはAVX命令を正確かつ効率的に機械語に変換できるようになります。

### `src/runtime/asm_amd64.s` および `src/runtime/memclr_amd64.s` の変更

これらのファイルは、Goランタイムの低レベルなアセンブリコードを含んでいます。

**`src/runtime/asm_amd64.s` (memequal関数のAVX2最適化部分)**

```assembly
// 変更前:
// hugeloop_avx2:
// 	CMPQ	BX, $64
// 	JB	bigloop_avx2
// 	MOVHDU	(SI), X0
// 	MOVHDU	(DI), X1
// 	MOVHDU	32(SI), X2
// 	MOVHDU	32(DI), X3
// 	VPCMPEQB	X1, X0, X4
// 	VPCMPEQB	X2, X3, X5
// 	VPAND	X4, X5, X6
// 	VPMOVMSKB X6, DX
// 	ADDQ	$64, SI
// 	ADDQ	$64, DI
// 	SUBQ	$64, BX
// 	JAE	hugeloop_avx2

// 変更後:
hugeloop_avx2:
	CMPQ	BX, $64
	JB	bigloop_avx2
	VMOVDQU	(SI), Y0
	VMOVDQU	(DI), Y1
	VMOVDQU	32(SI), Y2
	VMOVDQU	32(DI), Y3
	VPCMPEQB	Y1, Y0, Y4
	VPCMPEQB	Y2, Y3, Y5
	VPAND	Y4, Y5, Y6
	VPMOVMSKB Y6, DX
	ADDQ	$64, SI
	ADDQ	$64, DI
	SUBQ	$64, BX
	JAE	hugeloop_avx2
```
この変更では、`MOVHDU`命令が`VMOVDQU`に、XMMレジスタ（`X0`など）がYMMレジスタ（`Y0`など）に置き換えられています。
*   `MOVHDU`は、Goアセンブラ独自の命令で、おそらく128ビットのデータをロードするものでした。
*   `VMOVDQU` (VEX-encoded Move Double Unaligned Quadword) は、AVX2命令であり、256ビットのデータをメモリからYMMレジスタに、またはその逆に、アラインメントを気にせずに転送します。
*   これにより、一度に処理できるデータ量が128ビットから256ビットに倍増し、`memequal`（メモリ比較）のパフォーマンスが向上します。`VPCMPEQB`（Packed Compare Equal Bytes）や`VPAND`（Packed Logical AND）もYMMレジスタで動作するように変更され、256ビット幅でのバイト単位比較と論理AND演算が可能になります。

**`src/runtime/memclr_amd64.s` (memclr関数のAVX2最適化部分)**

```assembly
// 変更前:
// loop_avx2:
// 	MOVHDU	X0, 0(DI)
// 	MOVHDU	X0, 32(DI)
// 	MOVHDU	X0, 64(DI)
// 	MOVHDU	X0, 96(DI)
// ...
// loop_avx2_huge:
// 	MOVNTHD	X0, 0(DI)
// 	MOVNTHD	X0, 32(DI)
// 	MOVNTHD	X0, 64(DI)
// 	MOVNTHD	X0, 96(DI)

// 変更後:
loop_avx2:
	VMOVDQU	Y0, 0(DI)
	VMOVDQU	Y0, 32(DI)
	VMOVDQU	Y0, 64(DI)
	VMOVDQU	Y0, 96(DI)
// ...
loop_avx2_huge:
	VMOVNTDQ	Y0, 0(DI)
	VMOVNTDQ	Y0, 32(DI)
	VMOVNTDQ	Y0, 64(DI)

```
`memclr`（メモリクリア）関数でも同様に、`MOVHDU`が`VMOVDQU`に、`MOVNTHD`が`VMOVNTDQ`に、そしてXMMレジスタがYMMレジスタに置き換えられています。
*   `VPXOR Y0, Y0, Y0`は、YMMレジスタ`Y0`をゼロで埋める効率的な方法です。
*   `VMOVDQU`は、256ビット単位でメモリをゼロクリアするために使用されます。
*   `VMOVNTDQ` (VEX-encoded Move Non-Temporal Double Quadword) は、キャッシュをバイパスして直接メモリに書き込む命令です。これは、大量のデータを書き込む際にキャッシュを汚染せず、他のデータへのキャッシュヒット率を維持するのに役立ちます。特に大きなメモリ領域をクリアする場合（`loop_avx2_huge`）に有効です。

これらの変更により、Goランタイムの基本的なメモリ操作がAVX2の256ビット幅を最大限に活用し、より高速に実行されるようになります。

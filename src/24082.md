# [インデックス 24082] ファイルの概要

このコミットは、Go言語の標準ライブラリである `net/http/httputil` パッケージ内の `ReverseProxy` がHTTP Trailerをサポートするように変更するものです。これにより、HTTPレスポンスのボディの後に送信されるメタデータ（Trailer）が正しくプロキシされるようになります。

## 元コミット内容

このコミットは、`net/http/httputil` パッケージの `ReverseProxy` がHTTP Trailerをサポートするように修正します。Goの継続的ビルドシステムがビルドレットインターフェースでHTTP Trailerに依存しているため、この機能が必要となりました。以前の `httputil.ReverseProxy` はTrailerをプロキシできず、また `net/http` の `Transport` コードが誤って"Trailer"レスポンスヘッダーを削除していたため、問題が発生していました。この修正により、Go 1.5以前では不可能だったTrailerの設定とプロキシが可能になります。Trailerを使用するには、レスポンスヘッダーで事前にTrailerを宣言する必要がある点も言及されています。

## 変更の背景

この変更の主な背景は、Goの継続的ビルドシステム（特に `x/build/cmd/release` ツール）が、ビルドレット（ビルドを実行するエージェント）との通信にHTTP Trailerを利用している点にあります。

具体的には、Andrew Gerrand氏が `makerelease` ツールをGoのビルドシステム（現在の `x/build/cmd/release`）に書き換えましたが、このツールは当初GCE（Google Compute Engine）ベースのビルドレットしか作成できませんでした。これにより、Darwin（macOS）向けのリリースビルドが不可能という問題が生じました。

この問題を解決するため、`https://golang.org/cl/11901` でコーディネーターを介したビルドレット接続のプロキシが追加されました。しかし、この変更によって `httputil.ReverseProxy` がHTTP Trailerをプロキシできないという新たな問題が露呈しました。さらに、`net/http` パッケージの `Transport` コードが不必要に"Trailer"レスポンスヘッダーを削除するという、`release-branch.r56` 以前から存在するバグも明らかになりました。

HTTP Trailerはあまり一般的に使用されないため、このバグはこれまで見過ごされてきました。また、Go 1.5以前では `ResponseWriter` を介してサーバーがTrailerを設定する機能自体がなかったため、プロキシすることも不可能でした。このコミットは、これらの問題を解決し、Goのビルドシステムが正しく機能するために不可欠な変更でした。

## 前提知識の解説

### HTTP Trailer (トレーラー)

HTTP Trailerは、HTTP/1.1のチャンク転送エンコーディング（Chunked Transfer Encoding）と組み合わせて使用される特別なHTTPヘッダーです。通常のHTTPヘッダーはレスポンスボディの前に送信されますが、Trailerはレスポンスボディの**後**、つまり最後のチャンクの後に送信されます。

**なぜTrailerが必要か？**
レスポンスボディの生成中に初めて利用可能になるメタデータ（例：コンテンツのハッシュ値、デジタル署名、処理時間など）を送信したい場合に非常に有用です。通常のヘッダーでは、ボディの生成が完了する前にすべてのヘッダーを決定して送信する必要があるため、このような「後から決まる」メタデータを送ることができません。Trailerを使用することで、サーバーはボディの生成中にこれらの情報を計算し、ボディの送信後にクライアントに提供できます。

**Trailerの使用方法:**
1.  **`Trailer` ヘッダーの宣言:** サーバーは、通常のレスポンスヘッダーの一部として `Trailer` ヘッダーを送信し、その値としてボディの後に送信するTrailerヘッダーの名前をカンマ区切りで列挙します。例: `Trailer: X-Digest, X-Processing-Time`
2.  **チャンク転送エンコーディング:** Trailerはチャンク転送エンコーディングが使用されている場合にのみ機能します。これは、ボディの長さを事前に知る必要がないため、ボディのストリーミング中にTrailerを送信できるためです。
3.  **ボディの送信:** レスポンスボディがチャンク形式で送信されます。
4.  **Trailerの送信:** ボディの最後のチャンク（長さ0のチャンク）の後に、宣言されたTrailerヘッダーとその値が送信されます。

### `net/http/httputil.ReverseProxy`

`net/http/httputil.ReverseProxy` は、Go言語でリバースプロキシを実装するためのユーティリティです。リバースプロキシは、クライアントからのリクエストを受け取り、それをバックエンドサーバーに転送し、バックエンドサーバーからのレスポンスをクライアントに返す役割を担います。これにより、ロードバランシング、セキュリティ強化、キャッシュなどの機能を実現できます。

`ReverseProxy` は `http.Handler` インターフェースを実装しており、`ServeHTTP` メソッドを通じてリクエストを処理します。内部的には、`http.Transport` を使用してバックエンドへのリクエストを送信し、そのレスポンスをクライアントにコピーします。

### Goの `net/http` パッケージにおけるHTTPヘッダーとボディの処理

Goの `net/http` パッケージは、HTTPプロトコルを扱うための強力な機能を提供します。
*   **`http.Request`**: クライアントからのリクエストを表します。ヘッダー、ボディ、URLなどの情報を含みます。
*   **`http.Response`**: サーバーからのレスポンスを表します。ステータスコード、ヘッダー、ボディなどの情報を含みます。
*   **`http.ResponseWriter`**: サーバーがクライアントにレスポンスを書き込むためのインターフェースです。ヘッダーの設定 (`Header().Set()`) やボディの書き込み (`Write()`) を行います。
*   **`http.Transport`**: HTTPクライアントが実際にネットワーク経由でリクエストを送信し、レスポンスを受信するメカニズムを提供します。このコミットの背景にある問題は、`Transport` がレスポンスから"Trailer"ヘッダーを誤って削除していたことに起因します。

## 技術的詳細

このコミットの技術的詳細な変更点は、主に `src/net/http/httputil/reverseproxy.go` の `ServeHTTP` メソッドに集中しています。

1.  **`res.Body.Close()` の移動:**
    *   変更前は `defer res.Body.Close()` が `ServeHTTP` の冒頭にありました。これは、`res.Body` が読み取られる前にクローズされる可能性があり、特にTrailerがボディの後に来るため、`res.Trailer` フィールドが適切に設定されない原因となっていました。
    *   変更後は `res.Body.Close()` が `p.copyResponse(rw, res.Body)` の直後に移動されました。これにより、`copyResponse` が完了し、レスポンスボディが完全に読み取られた後に `res.Body` がクローズされ、その時点でバックエンドからのTrailer情報が `res.Trailer` に適切に格納されるようになります。

2.  **`Trailer` ヘッダーの処理:**
    *   `res.Trailer` は、`http.Transport` がバックエンドからのレスポンスを解析した結果、ボディの後に受信したTrailerヘッダーを格納するマップです。
    *   コミットでは、`if len(res.Trailer) > 0` でTrailerが存在するかどうかを確認します。
    *   存在する場合、`res.Trailer` のキー（Trailerヘッダー名）を抽出し、カンマ区切りの文字列として `rw.Header().Add("Trailer", strings.Join(trailerKeys, ", "))` を使ってクライアントへのレスポンスヘッダーに `Trailer` ヘッダーを追加します。これは、クライアントに「これらのTrailerがボディの後に来るよ」と事前に宣言するために必要です。

3.  **チャンク転送の強制:**
    *   `if len(res.Trailer) > 0` のブロック内で、`rw.WriteHeader(res.StatusCode)` の後に `if fl, ok := rw.(http.Flusher); ok { fl.Flush() }` が追加されています。
    *   これは、Trailerが存在する場合に、`net/http` がレスポンスボディの長さを計算して `Content-Length` ヘッダーを追加するのを防ぐためのものです。Trailerはチャンク転送エンコーディングでのみ機能するため、`Content-Length` と共存できません。`Flush()` を呼び出すことで、ヘッダーがすぐに送信され、その後のボディは自動的にチャンクエンコーディングで送信されるようになります。これにより、`Content-Length` が設定されるのを回避し、Trailerが正しく機能する環境を整えます。

4.  **Trailer値のコピー:**
    *   `res.Body.Close()` の直後に `copyHeader(rw.Header(), res.Trailer)` が追加されました。
    *   これは、`res.Body` が完全に読み取られ、`res.Trailer` にバックエンドからの実際のTrailerヘッダーとその値が格納された後、それらをクライアントへのレスポンスヘッダー（`rw.Header()`）にコピーするためのものです。これにより、クライアントはボディの後に送信されるTrailerヘッダーとその値を受け取ることができます。

### `net/http` の `Transport` コードにおける"Trailer"ヘッダー削除の修正

コミットメッセージには「`net/http` が不必要に"Trailer"レスポンスヘッダーを削除していた」とありますが、このコミットのコード差分には `net/http` パッケージ自体の変更は含まれていません。これは、`net/http` パッケージの内部的な修正が別のコミット（`https://golang.org/cl/11901` など）で行われたか、または `httputil.ReverseProxy` が `http.Transport` から受け取った `http.Response` オブジェクトの `Trailer` フィールドが既に正しく設定されていることを前提としていることを示唆しています。このコミットは、その `Trailer` フィールドの情報を `ReverseProxy` が適切にクライアントに転送するためのロジックを追加しています。

## コアとなるコードの解説

### `src/net/http/httputil/reverseproxy.go` の変更点

1.  **`defer res.Body.Close()` の削除と移動:**
    *   元のコードでは `defer res.Body.Close()` が `ServeHTTP` 関数の早い段階で呼び出されていました。`defer` は関数が終了する直前に実行されるため、一見問題ないように見えます。しかし、`http.Response` の `Trailer` フィールドは、`Body` が完全に読み取られた後に初めて有効な値を持つようになります。もし `Body` の読み取りが完了する前に `Close()` が呼ばれてしまうと、`Trailer` フィールドが空のままになってしまう可能性がありました。
    *   このコミットでは `defer` を削除し、`p.copyResponse(rw, res.Body)` の直後に `res.Body.Close()` を明示的に呼び出すように変更しました。これにより、レスポンスボディがクライアントに完全にコピーされ、バックエンドからのTrailer情報が `res.Trailer` に確実に格納された後に `Body` がクローズされるようになります。

2.  **`Trailer` ヘッダーの事前宣言:**
    *   `if len(res.Trailer) > 0 { ... }` ブロックが追加されました。
    *   ここで、バックエンドからのレスポンスにTrailerが含まれている場合 (`res.Trailer` が空でない場合)、そのTrailerヘッダーの名前（キー）を抽出し、カンマ区切りの文字列に結合します。
    *   そして、`rw.Header().Add("Trailer", strings.Join(trailerKeys, ", "))` を使って、クライアントに送信するレスポンスヘッダーに `Trailer` ヘッダーを追加します。これはHTTP/1.1の仕様で、ボディの後にTrailerを送信する際には、事前にどのTrailerが来るかをクライアントに通知する必要があるためです。

3.  **チャンク転送の強制と `Content-Length` の回避:**
    *   `rw.WriteHeader(res.StatusCode)` の後に、再度 `if len(res.Trailer) > 0 { ... }` ブロックが追加されました。
    *   このブロックの目的は、Trailerが存在する場合に、`net/http` がレスポンスボディの長さを自動的に計算して `Content-Length` ヘッダーを追加するのを防ぐことです。HTTP Trailerはチャンク転送エンコーディングと組み合わせて使用されるため、`Content-Length` ヘッダーとは共存できません。
    *   `if fl, ok := rw.(http.Flusher); ok { fl.Flush() }` は、`http.ResponseWriter` が `http.Flusher` インターフェースを実装している場合（多くのHTTPサーバー実装で該当します）に、ヘッダーをすぐにクライアントにフラッシュします。これにより、`net/http` はボディの長さを計算する機会を失い、自動的にチャンク転送エンコーディングを使用するようになります。

4.  **Trailer値のコピー:**
    *   `res.Body.Close()` の直後に `copyHeader(rw.Header(), res.Trailer)` が追加されました。
    *   `copyHeader` 関数は、ソースのヘッダーマップからデスティネーションのヘッダーマップにすべてのヘッダーをコピーするユーティリティ関数です。
    *   ここでは、`res.Trailer`（バックエンドから受信した実際のTrailerヘッダーとその値）を、クライアントに送信するレスポンスヘッダー（`rw.Header()`）にコピーしています。これにより、クライアントはボディの後に、これらのTrailerヘッダーとその値を受け取ることができます。

### `src/net/http/httputil/reverseproxy_test.go` の変更点

テストファイルには、`ReverseProxy` がTrailerを正しく処理することを確認するための新しいテストケースが追加されています。

1.  **`reflect` パッケージのインポート:**
    *   `reflect.DeepEqual` を使用して、`http.Header` の内容を比較するためにインポートされています。

2.  **バックエンドサーバーでのTrailer設定:**
    *   テスト用のバックエンドHTTPサーバー (`httptest.NewServer`) のハンドラ内で、`w.Header().Set("Trailer", "X-Trailer")` を呼び出して、クライアントに `X-Trailer` というTrailerが送信されることを宣言しています。
    *   レスポンスボディの書き込み後、`w.Header().Set("X-Trailer", "trailer_value")` を呼び出して、実際の `X-Trailer` の値を設定しています。これにより、バックエンドサーバーはTrailerを送信するようになります。

3.  **クライアント側でのTrailerの検証:**
    *   プロキシを介してバックエンドからのレスポンスを受信した後、クライアント側でTrailerが正しく受信されたことを検証するアサーションが追加されています。
    *   `if g, e := res.Trailer, (http.Header{"X-Trailer": nil}); !reflect.DeepEqual(g, e) { ... }` は、ボディを読み取る前に `res.Trailer` が `X-Trailer` を含むことを確認します。`nil` は値がまだ読み込まれていないことを示します。
    *   `if g, e := res.Trailer.Get("X-Trailer"), "trailer_value"; g != e { ... }` は、レスポンスボディを完全に読み取った後、`res.Trailer` から `X-Trailer` の値が正しく `"trailer_value"` として取得できることを確認します。

これらの変更により、`httputil.ReverseProxy` はHTTP Trailerを完全にサポートし、GoのビルドシステムのようなTrailerに依存するアプリケーションが正しく機能するようになります。

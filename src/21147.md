# [インデックス 21147] ファイルの概要

このコミットは、Goランタイムにおける`siginfo_t`構造体の`si_addr`フィールドの扱いを改善し、特に386およびARMアーキテクチャでの誤った動作を修正することを目的としています。以前はC言語の`siginfo_t`構造体内の共用体（union）の一部である`si_addr`フィールドを、Go側では不透明なバイト配列として表現し、`unsafe`パッケージを用いたポインタ演算でアクセスしていました。しかし、この方法は特定のアーキテクチャで正しく機能しない問題がありました。本コミットでは、Goの`siginfo`構造体に`si_addr`フィールドを明示的に宣言することで、より安全かつ正確なアクセスを実現しています。

## 変更の背景

Goランタイムは、オペレーティングシステム（OS）からのシグナル（信号）を処理する際に、OSが提供する`siginfo_t`構造体を利用します。この構造体は、シグナルに関する詳細な情報（シグナル番号、エラーコード、シグナルを発生させたアドレスなど）を格納しています。特に、`si_addr`フィールドは、セグメンテーション違反（SIGSEGV）などのメモリアクセス違反が発生した際に、その違反が発生したメモリアドレスを示す重要な情報です。

C言語の`siginfo_t`構造体は、異なる種類のシグナル情報に対応するために共用体（union）を含んでいます。`si_addr`はこの共用体の一部として定義されており、そのオフセットは共用体の他のメンバーによって変動する可能性があります。Goランタイムでは、このC言語の共用体をGoの構造体で表現する際に、共用体全体を不透明なバイト配列（例: `_sifields [116]byte`）として扱っていました。そして、`si_addr`フィールドにアクセスするためには、`unsafe`パッケージとポインタ演算を用いて、バイト配列の特定オフセットから値を読み出すという手法が取られていました。

しかし、この`unsafe`なポインタ演算によるアクセス方法は、特に386およびARMアーキテクチャにおいて、`si_addr`の実際のオフセットとGoコードが期待するオフセットが一致しない場合に、誤ったメモリアドレスを読み取ってしまうという問題がありました。これは、異なるアーキテクチャ間での構造体のアライメントやパディングの違いに起因するもので、Goランタイムがシグナルハンドリングにおいて正確な情報を取得できないという深刻なバグにつながる可能性がありました。

このコミットの目的は、このアーキテクチャ依存のバグを修正し、`si_addr`フィールドへのアクセスをより堅牢で安全なものにすることです。Goランタイムが`siginfo_t`構造体の中で`si_addr`フィールドのみを使用しているという事実に基づき、共用体を不透明なバイト配列として扱うのではなく、`si_addr`フィールドをGoの`siginfo`構造体内に明示的に宣言することで、この問題を解決しています。

## 前提知識の解説

### シグナルと`siginfo_t`構造体

Unix系OSにおいて、シグナルはプロセスに対して非同期的にイベントを通知するメカニズムです。例えば、プログラムが不正なメモリアクセスを行った場合（セグメンテーション違反）、OSはSIGSEGVシグナルを該当プロセスに送信します。シグナルハンドラは、これらのシグナルを受け取って適切な処理を行うための関数です。

`siginfo_t`構造体は、シグナルハンドラに渡される情報の一つで、発生したシグナルの詳細を提供します。主要なフィールドには以下のようなものがあります。

*   `si_signo`: シグナル番号（例: `SIGSEGV`）
*   `si_errno`: エラー番号
*   `si_code`: シグナルがどのように発生したかを示すコード
*   `si_addr`: シグナルに関連するアドレス。例えば、`SIGSEGV`の場合は不正なメモリアクセスが発生したアドレス、`SIGILL`の場合は不正な命令のアドレスなど。

### C言語の共用体（Union）

C言語の共用体は、異なる型のメンバーが同じメモリ領域を共有する特殊なデータ型です。共用体のサイズは、その中で最も大きいメンバーのサイズによって決まります。共用体を使用すると、同じメモリ領域を異なる方法で解釈できます。`siginfo_t`構造体では、`si_addr`を含む部分が共用体として定義されており、これにより様々なシグナルタイプに対応する追加情報が効率的に格納されます。

### Go言語の`unsafe`パッケージとポインタ演算

Go言語は通常、ポインタ演算を厳しく制限し、メモリ安全性を保証します。しかし、`unsafe`パッケージを使用すると、Goの型システムを迂回して、C言語のような低レベルのポインタ操作が可能になります。これには、任意のメモリ位置へのアクセスや、異なる型へのポインタ変換などが含まれます。

`unsafe.Pointer`は、任意の型のポインタを保持できる特殊なポインタ型です。`uintptr`は、ポインタの値を整数として表現する型で、ポインタ演算を行う際に使用されます。

このコミット以前のGoランタイムでは、C言語の`siginfo_t`構造体の共用体部分をGoのバイト配列として表現し、`unsafe.Pointer`と`uintptr`を用いたポインタ演算で`si_addr`フィールドのオフセットを計算し、そのアドレスから値を読み取っていました。

### アーキテクチャ依存性

コンピュータのアーキテクチャ（例: x86, ARM, PowerPC）によって、データ型のサイズ、メモリのアライメント（データがメモリ上で配置される際の境界）、エンディアン（バイト順序）などが異なります。C言語の構造体は、これらのアーキテクチャ特性に影響を受け、同じ構造体定義でも異なるアーキテクチャではメモリ上のレイアウトが異なる場合があります。

特に共用体を含む構造体の場合、コンパイラはパディング（メモリ効率やアライメントのために挿入される未使用バイト）を追加することがあり、これにより特定のフィールドのオフセットがアーキテクチャによって変動する可能性があります。Goランタイムが`unsafe`なポインタ演算で`si_addr`のオフセットを固定的に仮定していたため、このアーキテクチャ間の差異が問題を引き起こしていました。

## 技術的詳細

このコミットの核心は、GoランタイムがC言語の`siginfo_t`構造体内の共用体をどのようにGoの型で表現するか、という点にあります。

**変更前のアプローチ:**

変更前は、`siginfo_t`構造体の`si_signo`, `si_errno`, `si_code`といった共通フィールドの後に続く共用体部分を、Goの`siginfo`構造体内で`_sifields`という名前のバイト配列（例: `[116]byte`や`[112]byte`など、アーキテクチャによってサイズが異なる）として定義していました。

```go
type siginfo struct {
	si_signo  int32
	si_errno  int32
	si_code   int32
	_sifields [XXX]byte // 共用体部分を不透明なバイト配列として表現
}
```

`si_addr`フィールドにアクセスする際には、`unsafe.Pointer`と`uintptr`を使って、`siginfo`構造体の先頭から`si_addr`が位置するであろうオフセットを計算し、そのアドレスから`uintptr`（または`uint32`/`uint64`）として値を読み取っていました。例えば、`signal_linux_amd64.go`では以下のようなコードがありました。

```go
func (c *sigctxt) sigaddr() uint64 { return uint64(*(*uintptr)(add(unsafe.Pointer(c.info), 2*ptrSize))) }
```

ここで、`add(unsafe.Pointer(c.info), 2*ptrSize)`は、`c.info`（`siginfo`構造体へのポインタ）から`2*ptrSize`バイトだけオフセットしたアドレスを計算しています。`ptrSize`はポインタのサイズ（32ビットシステムでは4バイト、64ビットシステムでは8バイト）です。この計算は、`si_signo`と`si_errno`の2つの`int32`フィールド（合計8バイト）の後に`si_code`フィールドが続き、その後に`si_addr`が来ると仮定しています。しかし、C言語の構造体におけるパディングや共用体のレイアウトは、コンパイラやアーキテクチャによって異なるため、この固定的なオフセット計算が常に正しいとは限りませんでした。特に386（32ビット）やARM（32ビット）アーキテクチャでは、このオフセット計算が誤っていたため、`si_addr`の正しい値を取得できませんでした。

**変更後のアプローチ:**

このコミットでは、Goランタイムが`siginfo_t`構造体の中で`si_addr`フィールドのみを必要としているという事実を利用し、`siginfo`構造体から`_sifields`バイト配列を削除し、代わりに`si_addr`フィールドを明示的に追加しました。

```go
type siginfo struct {
	si_signo int32
	si_errno int32
	si_code  int32
	// below here is a union; si_addr is the only field we use
	si_addr uint32 // または uint64 (アーキテクチャによる)
}
```

これにより、Goコンパイラが`siginfo`構造体をコンパイルする際に、C言語の`siginfo_t`構造体とメモリレイアウトが一致するように、適切なパディングとアライメントを自動的に処理するようになります。結果として、`si_addr`フィールドへのアクセスは、`c.info.si_addr`のように直接行えるようになり、`unsafe`なポインタ演算やオフセット計算の必要がなくなりました。

この変更により、Goランタイムは`si_addr`の値をアーキテクチャに依存せず、常に正確に取得できるようになりました。これは、シグナルハンドリングの堅牢性を高め、特にクラッシュレポートやデバッグにおいて正確なメモリアドレス情報を提供するために非常に重要です。

## コアとなるコードの解説

### `src/runtime/defs_linux_*.go` の変更

これらのファイルは、GoランタイムがLinuxシステムコールやOSのデータ構造とやり取りするために使用するGoの構造体定義を含んでいます。

*   **`_sifields [XXX]byte` の削除**:
    これは、C言語の`siginfo_t`構造体内の共用体部分をGo側で「生」のバイトデータとして扱っていた名残です。このバイト配列のサイズは、共用体の最大サイズに合わせて定義されていましたが、GoコンパイラがCの共用体の正確なメモリレイアウトを再現することは困難であり、特に異なるアーキテクチャ間でのパディングやアライメントの違いにより、`si_addr`のオフセットが期待通りにならない問題がありました。このフィールドを削除することで、GoコンパイラにCの構造体との互換性を考慮したレイアウト生成を委ねる形になります。

*   **`si_addr uint32` または `si_addr uint64` の追加**:
    Goランタイムが`siginfo_t`構造体から必要とする唯一の共用体メンバーが`si_addr`であるため、これをGoの`siginfo`構造体に明示的なフィールドとして追加しました。
    *   `uint32`は32ビットシステム（386, ARM）用で、アドレスが32ビット幅であることを示します。
    *   `uint64`は64ビットシステム（amd64, power64, power64le）用で、アドレスが64ビット幅であることを示します。
    この明示的な宣言により、GoコンパイラはC言語の`siginfo_t`構造体と互換性のあるメモリレイアウトを生成しようとします。これにより、`si_addr`フィールドが常に正しいオフセットに配置されることが保証され、アーキテクチャ間の差異による問題が解消されます。

*   **コメントの追加**:
    `// below here is a union; si_addr is the only field we use`
    このコメントは、Goの`siginfo`構造体のこの部分が、C言語の`siginfo_t`構造体における共用体に対応しており、Goランタイムがその共用体の中から`si_addr`フィールドのみを使用していることを明確に示しています。これは、将来のコード変更者がこの構造体の意図を理解する上で役立ちます。

### `src/runtime/signal_linux_*.go` の変更

これらのファイルは、GoランタイムがLinux上でシグナルを処理するロジックを含んでいます。`sigctxt`構造体は、シグナルハンドラに渡されるコンテキスト情報（レジスタの状態、シグナル情報など）をカプセル化します。

*   **`func (c *sigctxt) sigaddr() uint32/uint64` の変更**:
    この関数は、シグナルが発生したメモリアドレス（`si_addr`）を取得するためのものです。
    *   **変更前**: `uint32(*(*uintptr)(add(unsafe.Pointer(c.info), 2*ptrSize)))`
        これは、`c.info`（`siginfo`構造体へのポインタ）から特定のオフセット（`2*ptrSize`）を計算し、そのオフセットにあるメモリを`uintptr`として解釈し、さらに`uint32`または`uint64`にキャストするという、複雑で`unsafe`なポインタ演算を行っていました。このオフセット計算がアーキテクチャによって誤っていたため、問題が発生していました。
    *   **変更後**: `return c.info.si_addr`
        `siginfo`構造体に`si_addr`フィールドが明示的に追加されたため、この関数は単に`c.info.si_addr`を直接参照するだけでよくなりました。これにより、`unsafe`な操作が不要になり、コードがより安全で読みやすくなりました。Goコンパイラが`siginfo`構造体のメモリレイアウトを正しく管理するため、`si_addr`へのアクセスは常に正しい値を返します。

この一連の変更により、GoランタイムはLinux上でのシグナルハンドリングにおいて、`si_addr`フィールドから常に正確なメモリアドレス情報を取得できるようになり、特にクラッシュ時のデバッグ情報の信頼性が向上しました。

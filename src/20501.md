# [インデックス 20501] ファイルの概要

`src/cmd/gc/racewalk.c`はGoコンパイラ（`cmd/gc`）の一部であり、Goのデータ競合検出器（Race Detector）のためのコード生成を担当します。このファイルは、プログラム内のメモリアクセスを追跡し、潜在的なデータ競合を特定するために必要なインストゥルメンテーション（計測コードの挿入）を行います。

## 元コミット内容

このコミットは、Goコンパイラの`cmd/gc`パッケージにおける`racewalk`処理のバグ修正を目的としています。具体的には、以前の`writebarrier`（ライトバリア）の実装変更によって発生した問題に対処しています。この修正は、`runtime`パッケージ内の`writebarrier`関数への呼び出しにおいて、その`dst`（デスティネーション）引数（つまり、ポインタが書き込まれるメモリ位置）に対して適切なインストゥルメンテーションを行うことで、データ競合検出器が正しく機能するようにします。

## 変更の背景

Goのランタイムは、並行ガベージコレクション（Concurrent Garbage Collection, GC）を実現するためにライトバリアを使用します。ライトバリアは、GCがオブジェクトグラフを走査している最中に、プログラムがヒープ上のポインタを書き換える際にその変更をGCに通知するための重要なメカニズムです。これにより、GCは正確なオブジェクトグラフのスナップショットを維持し、メモリリークや誤った解放を防ぎます。

このコミット以前に、Goのライトバリアの実装に内部的な変更が加えられました。この変更により、`racewalk`（データ競合検出器のためのコード生成パス）が、`runtime.writebarrier*`関数への呼び出しの`dst`引数を正しくインストゥルメントできなくなりました。`racewalk`は、データ競合を検出するために、メモリへの書き込み操作を監視するコードを挿入します。ライトバリアの呼び出しは本質的にメモリへの書き込み操作を伴うため、これらの操作もデータ競合検出器によって監視される必要があります。

しかし、Goのランタイムコード自体は通常、データ競合検出器によるインストゥルメンテーションの対象外です。これは、ランタイムコードが非常に低レベルであり、その内部の競合はGoのメモリモデルの範囲外で処理されるためです。このため、`writebarrier`呼び出しの`dst`引数に対するインストゥルメンテーションは、コンパイラ側で特別に処理する必要がありました。以前の`writebarrier`の変更がこの特殊なケースを考慮していなかったため、`racewalk`が正しく機能しないという問題が発生しました。このコミットは、このギャップを埋め、データ競合検出器の正確性を維持するためのものです。

## 前提知識の解説

### Goのガベージコレクション (GC) とライトバリア

Goのガベージコレクションは、並行マーク＆スイープ方式を採用しています。これは、GCが実行されている間もユーザープログラムが並行して動作できることを意味します。この並行性を実現するために重要なのが「ライトバリア」です。

*   **ライトバリア (Write Barrier)**: プログラムがヒープ上のポインタを書き換える際に実行される小さなコードスニペットです。GCがオブジェクトグラフを走査している最中にポインタが変更されると、GCは古いポインタと新しいポインタの両方を追跡する必要があります。ライトバリアは、このポインタの変更をGCに通知し、GCが正確なメモリ状態を把握できるようにします。これにより、GCは「ストップ・ザ・ワールド」（プログラムの実行を完全に停止させる時間）を最小限に抑えることができます。

### Goコンパイラ (`cmd/gc`) と `racewalk`

*   **`cmd/gc`**: Go言語の公式コンパイラです。Goのソースコードを機械語に変換する主要なツールチェーンの一部です。
*   **`racewalk`**: `cmd/gc`内のコンパイラパスの一つで、Goの組み込みデータ競合検出器（Race Detector）のためにコードをインストゥルメントする役割を担います。データ競合検出器は、複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも一方が書き込み操作である場合に発生する競合状態を検出します。`racewalk`は、このような競合を検出するために、メモリの読み書き操作の直前に特別な監視コード（インストゥルメンテーションコード）を挿入します。

### `runtime`パッケージ

`runtime`パッケージは、Goプログラムの実行をサポートする低レベルの機能を提供します。これには、スケジューラ、ガベージコレクタ、メモリ管理、プリミティブな同期メカニズムなどが含まれます。`runtime.writebarrier*`関数は、このパッケージ内で定義されており、ガベージコレクションのライトバリア処理を実装しています。

## 技術的詳細

このコミットの技術的な核心は、`racewalk`が`runtime.writebarrier*`関数呼び出しの`dst`引数を特別に処理する必要があるという点です。

通常、`racewalk`はGoプログラムのすべてのメモリ書き込み操作をインストゥルメントします。しかし、`runtime`パッケージ内のコードは、Goのメモリモデルの外部で動作するため、通常は`racewalk`によるインストゥルメンテーションの対象外です。`runtime.writebarrier*`関数は、GCの内部動作の一部としてメモリを書き換えます。これらの書き込み操作は、ユーザープログラムの観点からは「通常の」書き込みとは異なり、GCの正確性を保証するために行われます。

問題は、`writebarrier`の実装が変更された際に、`racewalk`がこれらの`writebarrier`呼び出しの`dst`引数（つまり、実際にポインタが書き込まれるメモリ位置）を正しく識別し、インストゥルメントするロジックが欠けていたことです。これにより、`writebarrier`によって行われるメモリ書き込みがデータ競合検出器によって監視されず、誤った競合検出結果や検出漏れが発生する可能性がありました。

この修正は、`racewalk.c`内の`racewalknode`関数において、`OCALLFUNC`（関数呼び出し）のケースに新しいロジックを追加することで実現されています。このロジックは、呼び出されている関数が`runtime`パッケージ内の`writebarrierptr`, `writebarrierstring`, `writebarrierslice`, `writebarrieriface`, `writebarrierfat`のいずれかであるかを識別します。これらの関数は、それぞれ異なる型のポインタ、文字列、スライス、インターフェース、または「fat」ポインタ（インターフェースやスライスのように複数のワードで構成される値）のライトバリア処理を行います。

識別後、コードは関数呼び出しの引数リストを走査し、`dst`引数を見つけ出します。`writebarrierfat`の場合とそれ以外の場合で`dst`引数のオフセットが異なるため、それに応じて適切な引数を特定します。`dst`引数が特定されると、その引数に対して`callinstr`関数が呼び出され、データ競合検出器のためのインストゥルメンテーションコードが挿入されます。これにより、`writebarrier`によるメモリ書き込みもデータ競合検出器の監視対象となり、検出器の正確性が保たれます。

## コアとなるコードの変更箇所

`src/cmd/gc/racewalk.c`の`racewalknode`関数内の`OCALLFUNC`ケースに以下のコードブロックが追加されました。

```c
 	case OCALLFUNC:
+		// Instrument dst argument of runtime.writebarrier* calls
+		// as we do not instrument runtime code.
+		if(n->left->sym != S && n->left->sym->pkg == runtimepkg &&
+			(strcmp(n->left->sym->name, "writebarrierptr") == 0 ||
+			strcmp(n->left->sym->name, "writebarrierstring") == 0 ||
+			strcmp(n->left->sym->name, "writebarrierslice") == 0 ||
+			strcmp(n->left->sym->name, "writebarrieriface") == 0 ||
+			strcmp(n->left->sym->name, "writebarrierfat") == 0)) {
+			// Find the dst argument.
+			// The list can be reordered, so it's not necessary just the first or the second element.
+			for(l = n->list; l; l = l->next) {
+				if(strcmp(n->left->sym->name, "writebarrierfat") == 0) {
+					if(l->n->left->xoffset == widthptr)
+						break;
+				} else {
+					if(l->n->left->xoffset == 0)
+						break;
+				}
+			}
+			if(l == nil)
+				fatal("racewalk: writebarrier no arg");
+			if(l->n->right->op != OADDR)
+				fatal("racewalk: writebarrier bad arg");
+			callinstr(&l->n->right->left, init, 1, 0);
+		}
 		racewalknode(&n->left, init, 0, 0);
 		goto ret;
```

## コアとなるコードの解説

追加されたコードブロックは、関数呼び出しノード（`OCALLFUNC`）を処理する際に、特定の`runtime.writebarrier*`関数呼び出しを特別に扱います。

1.  **`if`条件による`writebarrier`関数の識別**:
    *   `n->left->sym != S`: 呼び出されている関数がシンボルを持っていることを確認します。
    *   `n->left->sym->pkg == runtimepkg`: 呼び出されている関数が`runtime`パッケージに属していることを確認します。
    *   `strcmp(n->left->sym->name, "writebarrierptr") == 0 || ...`: 呼び出されている関数の名前が、Goのライトバリア関数（`writebarrierptr`, `writebarrierstring`, `writebarrierslice`, `writebarrieriface`, `writebarrierfat`）のいずれかであるかをチェックします。これらの関数は、異なるデータ型に対するライトバリア操作を処理します。

2.  **`dst`引数の特定**:
    *   `for(l = n->list; l; l = l->next)`: 関数呼び出しの引数リストを走査します。引数の順序が保証されていない可能性があるため、リストを線形に探索します。
    *   `if(strcmp(n->left->sym->name, "writebarrierfat") == 0)`: `writebarrierfat`関数は、インターフェースやスライスのような複数のワードで構成される「fat」ポインタを扱うため、`dst`引数のオフセットが他の`writebarrier`関数とは異なります。
        *   `l->n->left->xoffset == widthptr`: `writebarrierfat`の場合、`dst`引数は`widthptr`（ポインタのサイズ）のオフセットを持つ引数として識別されます。
    *   `else`: 他の`writebarrier`関数の場合。
        *   `l->n->left->xoffset == 0`: `dst`引数は通常、オフセット0の引数として識別されます。
    *   `break`: 適切な`dst`引数が見つかったらループを終了します。

3.  **エラーハンドリング**:
    *   `if(l == nil)`: `dst`引数が見つからなかった場合、致命的なエラー（`fatal`）を報告します。
    *   `if(l->n->right->op != OADDR)`: `dst`引数がアドレス（`OADDR`）ではない場合、これも致命的なエラーとして扱います。これは、`dst`引数がメモリ位置へのポインタであるべきだからです。

4.  **インストゥルメンテーションの実行**:
    *   `callinstr(&l->n->right->left, init, 1, 0);`: 特定された`dst`引数（`l->n->right->left`は`dst`引数のアドレスを表すノード）に対して`callinstr`関数を呼び出します。`callinstr`は、データ競合検出器がメモリ書き込みを監視するために必要なインストゥルメンテーションコードを挿入する役割を担います。引数の`1`は書き込み操作であることを示し、`0`は読み込み操作ではないことを示します。

このコードは、Goランタイムの内部的な`writebarrier`呼び出しが、データ競合検出器の監視対象から漏れることを防ぎます。ランタイムコード自体はインストゥルメントされないという原則を維持しつつ、ランタイムがユーザーデータに影響を与える特定の操作（この場合はポインタの書き込み）を行う際には、その操作がデータ競合検出器によって正しく追跡されるようにするための、コンパイラレベルでの特殊な対応です。

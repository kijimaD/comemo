# [インデックス 22168] ファイルの概要

このコミットは、Goコンパイラの内部ツールである`cmd/internal/gc`における構文エラー報告の挙動を修正するものです。具体的には、`goyacc`（Go言語で実装された`yacc`）が生成するパーサーが、従来の`bison`（GNU `yacc`）が生成するパーサーとは異なる形式で「syntax error」を報告するようになったため、その詳細が失われる問題を解決します。この変更により、プレーンな構文エラーメッセージの際に、以前と同様の詳細な情報が保持されるようになります。

## コミット

このコミットは、Goコンパイラのフロントエンド部分である`cmd/internal/gc`において、構文エラー報告のロジックを調整し、`goyacc`への移行によって失われたエラーメッセージの詳細を復元します。`Yyerror`関数が、`goyacc`が生成する「%s」と「syntax error」の組み合わせを検出し、それを従来の「syntax error」というプレーンな文字列に変換することで、エラー処理の互換性を維持しています。

## 変更の背景

Goコンパイラの開発において、パーサーの生成ツールが`bison`から`goyacc`に移行する過程で、構文エラーの報告方法に微妙な変更が生じました。従来の`bison`は、構文エラーが発生すると`yyerror("syntax error")`という形式でエラーを報告していました。しかし、`goyacc`が生成するパーサーは、同じ状況で`yyerror("%s", "syntax error")`という形式でエラーを報告するようになりました。

`cmd/internal/gc`内のエラー報告関数である`Yyerror`は、エラーメッセージの書式設定と処理を担当しています。この関数は、エラーメッセージが「syntax error」で始まる場合に特別な処理（例えば、構文エラーのカウントを増やすなど）を行っていました。`goyacc`の新しい報告形式では、`Yyerror`関数が受け取る`fmt_`引数が`"%s"`となり、実際のメッセージ「syntax error」は`args`引数の中に含まれることになります。この変更により、`Yyerror`関数が「syntax error」という文字列を直接認識できなくなり、結果としてエラー処理の詳細が失われる可能性がありました。

このコミットは、この互換性の問題を解決し、`goyacc`が生成する新しい形式のエラー報告を検出し、それを従来の形式に変換することで、`Yyerror`関数が引き続き正しくエラーを処理できるようにすることを目的としています。これにより、コンパイラが報告する構文エラーの挙動が一貫性を保ち、開発者やユーザーが期待するエラーメッセージの詳細が失われないようにします。

## 前提知識の解説

### コンパイラのフロントエンドとパーサー

コンパイラは、ソースコードを機械が実行できる形式に変換するソフトウェアです。その過程は大きく「フロントエンド」と「バックエンド」に分けられます。フロントエンドは、ソースコードを解析し、抽象構文木（AST）などの中間表現を生成する部分です。このフロントエンドの重要なコンポーネントが「パーサー（構文解析器）」です。

パーサーは、字句解析器（レキサー）によって生成されたトークンのストリームを受け取り、プログラミング言語の文法規則に従って、それらが正しい構文を形成しているかを確認します。構文が正しくない場合、パーサーは「構文エラー」を報告します。

### Yacc/BisonとGoyacc

`Yacc`（Yet Another Compiler Compiler）は、文法定義からパーサーを自動生成するためのツールです。`Bison`はGNUプロジェクトによる`Yacc`の互換実装であり、より多くの機能と改善が加えられています。これらのツールは、LALR(1)パーサーを生成し、プログラミング言語の構文解析を効率的に行うために広く利用されています。

`Yacc`/`Bison`が生成するパーサーは、通常、構文エラーが発生した際に`yyerror`という関数を呼び出します。この`yyerror`関数は、ユーザーが実装するエラー報告のためのコールバック関数であり、エラーメッセージを受け取って適切な処理（例えば、エラーメッセージを標準出力に出力したり、エラーカウンタを増やしたり）を行います。

`Goyacc`は、Go言語で書かれた`Yacc`の再実装です。Go言語の特性（例えば、インターフェースやエラーハンドリングの慣習）に合わせて設計されており、Go言語のプロジェクトでパーサーを生成する際に利用されます。`Goyacc`も`yyerror`に相当するエラー報告メカニズムを持っていますが、その引数の渡し方や内部的な挙動が`Bison`とは異なる場合があります。

### エラー報告の重要性

コンパイラにおけるエラー報告は非常に重要です。正確で詳細なエラーメッセージは、プログラマーがコードの誤りを特定し、修正する上で不可欠な情報を提供します。特に構文エラーは、コードの基本的な構造に関する誤りを示すため、その報告の明確さは開発効率に直結します。エラーメッセージの詳細が失われると、デバッグが困難になり、開発者の生産性が低下する可能性があります。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/internal/gc/subr.go`ファイル内の`Yyerror`関数の変更にあります。

`Yyerror`関数は、Goコンパイラの構文解析中に発生したエラーを処理するための汎用的なエラー報告関数です。この関数は、`fmt_`というフォーマット文字列と、可変引数`args`を受け取ります。これはGo言語の`fmt.Printf`関数に似た形式です。

変更前の`Yyerror`関数は、`fmt_ == "%s" && len(args) == 1 && args[0] == "syntax error"`という条件をチェックしていました。この条件が真の場合、つまり`goyacc`が`yyerror("%s", "syntax error")`という形式でエラーを報告した場合、`Yyerror`関数は単に`nsyntaxerrors++`を実行し、構文エラーのカウントを増やしていました。しかし、この処理では、`fmt_`が`"%s"`であるため、後続の一般的なエラー処理ロジック（例えば、`strings.HasPrefix(fmt_, "syntax error")`のようなチェック）が正しく機能しない可能性がありました。

変更後のコードでは、この特定のケース（`goyacc`が生成する「%s」と「syntax error」の組み合わせ）を検出した際に、`fmt_`を`"syntax error"`というプレーンな文字列に上書きし、`args`を`nil`に設定しています。

```go
func Yyerror(fmt_ string, args ...interface{}) {
	// bison used to invoke yyerror("syntax error").
	// With Go yacc we get yyerror("%s", "syntax error").
	// Convert to keep the old code working.
	if fmt_ == "%s" && len(args) == 1 && args[0] == "syntax error" {
		fmt_ = "syntax error"
		args = nil
	}
	if strings.HasPrefix(fmt_, "syntax error") {
		nsyntaxerrors++
		// ... (後続の処理)
	}
	// ... (その他のエラー処理)
}
```

この変更により、`goyacc`が生成する「%s」形式の構文エラーも、従来の`bison`が生成する「syntax error」というプレーンな形式として`Yyerror`関数内で扱われるようになります。これにより、`Yyerror`関数内の後続のロジック（例えば、`strings.HasPrefix(fmt_, "syntax error")`による構文エラーの識別）が期待通りに機能し、エラーメッセージの詳細が失われることなく、一貫したエラー処理が保証されます。

## コアとなるコードの解説

変更は`src/cmd/internal/gc/subr.go`ファイルの`Yyerror`関数内で行われています。

1.  **コメントの追加**:
    ```go
    // bison used to invoke yyerror("syntax error").
    // With Go yacc we get yyerror("%s", "syntax error").
    // Convert to keep the old code working.
    ```
    このコメントは、変更の意図を明確に説明しています。`bison`が`yyerror("syntax error")`を呼び出していたのに対し、`goyacc`は`yyerror("%s", "syntax error")`を呼び出すようになったことを示しています。この変更は、古いコードが引き続き機能するように変換を行うためのものであると述べています。

2.  **条件分岐の変更**:
    ```go
    if fmt_ == "%s" && len(args) == 1 && args[0] == "syntax error" {
    ```
    この行は変更前と変更後で同じです。これは、`fmt_`が`"%s"`であり、かつ`args`が1つの要素を持ち、その要素が文字列`"syntax error"`である場合にこのブロック内の処理を実行するという条件です。これはまさに`goyacc`が生成する特定の形式の構文エラーを捕捉するためのものです。

3.  **変更された処理**:
    ```diff
    -\t\tnsyntaxerrors++
    +\t\tfmt_ = "syntax error"
    +\t\targs = nil
    ```
    変更前は、この条件が真の場合に単に`nsyntaxerrors++`（構文エラーのカウントを増やす）だけを行っていました。
    変更後は、`nsyntaxerrors++`の代わりに以下の2行が追加されました。
    *   `fmt_ = "syntax error"`: `fmt_`変数の値を`"%s"`から`"syntax error"`というリテラル文字列に上書きします。
    *   `args = nil`: `args`変数を`nil`に設定します。これにより、可変引数が存在しない状態になります。

この変更により、`goyacc`が生成した特定の形式の構文エラーが、`Yyerror`関数の後続の処理において、あたかも`bison`が生成したプレーンな`"syntax error"`であるかのように扱われるようになります。これにより、`strings.HasPrefix(fmt_, "syntax error")`のようなチェックが引き続き正しく機能し、エラー報告の詳細が失われることなく、一貫したエラー処理が実現されます。

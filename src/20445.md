## 変更の背景

このコミットの背景には、Goランタイムのガベージコレクタにおける競合状態を修正する別の変更（CL 140380043、タイトル: "runtime: fix race in sweep termination"）があります。CL 140380043は、`sweepone`関数と`sweep.start`関数が同時にメモリ領域にアクセスする際の競合条件を解決し、Goアプリケーションのクラッシュを防ぐことを目的としていました。

しかし、この修正作業中に、コミットメッセージに「Windowsで深刻なエディタの問題を抱えていた (Was having serious editor problems on Windows)」とあるように、エディタの誤操作か予期せぬ挙動により、`src/runtime/sys_windows_386.s`ファイルに意図しない変更（"stray edit"）が混入してしまいました。この「迷い込んだ編集」は、スタックポインタを調整するアセンブリ命令のオペランドを誤った値に変更してしまい、ランタイムの動作に悪影響を及ぼす可能性がありました。

本コミットは、この誤って混入した変更を特定し、元の正しい状態に戻すことで、ランタイムの安定性と正確性を確保することを目的としています。

## 前提知識の解説

### Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理する低レベルのシステムです。これには、ガベージコレクション、スケジューリング（ゴルーチンの管理）、メモリ管理、システムコールインターフェースなどが含まれます。Goプログラムは、オペレーティングシステムと直接対話するのではなく、ランタイムを介してこれらの機能を利用します。

### アセンブリ言語 (Assembly Language)
アセンブリ言語は、コンピュータのプロセッサが直接理解できる機械語に非常に近い低レベルのプログラミング言語です。特定のCPUアーキテクチャ（例: x86、ARM）に特化しており、レジスタの操作、メモリへのアクセス、ジャンプ命令などを直接記述します。Go言語のランタイムや一部の標準ライブラリでは、パフォーマンスが重要であったり、OSとの低レベルな連携が必要な場合にアセンブリ言語が使用されます。

### x86アーキテクチャとスタック (x86 Architecture and Stack)
x86は、Intelが開発した命令セットアーキテクチャであり、多くのパーソナルコンピュータで使用されています。スタックは、プログラムが一時的なデータを格納するために使用するメモリ領域です。x86アーキテクチャでは、スタックは通常、高位アドレスから低位アドレスに向かって「下方」に成長します。

*   **スタックポインタ (Stack Pointer, SP/ESP/RSP)**: スタックの現在の最上位（最も低いアドレス）を指すレジスタです。データがスタックにプッシュされるとSPは減少し、ポップされるとSPは増加します。
*   **`ADDL SP, <value>` 命令**: x86アセンブリにおける`ADDL`は32ビットの加算命令です。`ADDL SP, <value>`は、スタックポインタ（SP）に指定された`value`を加算します。スタックが下方成長するため、SPに値を加算することは、スタックポインタを上位アドレスに移動させることを意味し、結果としてスタックからデータを「解放」または「破棄」する効果があります。これは、関数呼び出し後に引数やローカル変数が占めていたスタック領域をクリーンアップする際によく使用されます。

### Goアセンブリのディレクティブと擬似レジスタ

Goのアセンブリ言語は、一般的なアセンブリ言語とは異なり、Plan 9アセンブラをベースにした「擬似アセンブリ」です。これは、異なるCPUアーキテクチャ間での移植性を高めるために設計されています。

*   **`TEXT`**: 関数を宣言するためのディレクティブです。これに続く命令が実行可能なコードであることを示し、コンパイルされたバイナリの`.text`セクションに配置されます。
*   **`NOSPLIT`**: `TEXT`ディレクティブに付加されるフラグです。このフラグが付いている関数は、スタックの拡張チェック（スタック・スプリット・プリアンブル）を行わないようにコンパイラに指示します。これは通常、スタックをほとんど使用しない、または他の関数を呼び出さない小さな関数に適用されます。
*   **`SB` (Static Base)**: 擬似レジスタの一つで、「静的ベース」を意味します。プログラムのアドレス空間の基点、またはメモリの原点を表します。グローバルなシンボル（関数名やグローバルデータ）は、`MyFunction(SB)`のように`SB`からのオフセットとして参照され、リンカによって絶対メモリアドレスが決定されることを示します。
*   **`runtime·profileloop(SB)`**: `runtime`パッケージ内の`profileloop`という名前の関数を指します。Goアセンブリでは、パッケージ名と関数名が`·`（中点）で区切られます。`(SB)`は、このシンボルがグローバルな静的ベースからのオフセットで参照されることを示します。

### CL (Change List)
Goプロジェクトでは、変更は「Change List (CL)」としてGerritコードレビューシステムを通じて提出されます。各CLには一意の番号が割り当てられ、関連する変更のまとまりを表します。

## 技術的詳細

このコミットの核心は、`src/runtime/sys_windows_386.s`ファイル内の`runtime·profileloop`関数におけるスタックポインタの調整命令の修正です。

元のコード（誤って変更された状態）では、`ADDL $40, SP`となっていました。これは、スタックポインタに40バイトを加算し、スタック上の40バイト分の領域を解放することを意味します。しかし、このコミットによって`ADDL $12, SP`に修正されました。これは、スタックポインタに12バイトを加算し、スタック上の12バイト分の領域を解放することを意味します。

この変更は、`runtime·profileloop`関数が`runtime·externalthreadhandler`関数を呼び出した後のスタッククリーンアップに関連しています。関数呼び出し規約によっては、呼び出し元（caller）が呼び出し先（callee）に渡した引数や、呼び出し元自身がスタックにプッシュした一時的な値を、関数呼び出し後にスタックから取り除く責任を負います。

`runtime·profileloop`関数は、プロファイリングに関連する処理の一部として、外部スレッドハンドラを呼び出す役割を担っていると考えられます。`CALL runtime·externalthreadhandler(SB)`命令は、`runtime·externalthreadhandler`関数を呼び出します。この呼び出しによって、リターンアドレスがスタックにプッシュされます。また、`PUSHL $runtime·profileloop1(SB)`命令によって、`runtime·profileloop1`のアドレスがスタックにプッシュされています。

したがって、`runtime·externalthreadhandler`からの戻り後、スタックには`runtime·profileloop1`のアドレスと、`runtime·externalthreadhandler`を呼び出す際にプッシュされたリターンアドレスが残っています。これらの合計サイズが12バイト（4バイトのアドレスが3つ、または8バイトのリターンアドレスと4バイトの`profileloop1`アドレス）であったと推測されます。

*   `PUSHL $runtime·profileloop1(SB)`: 4バイトをスタックにプッシュ。
*   `CALL runtime·externalthreadhandler(SB)`: リターンアドレス（4バイト）をスタックにプッシュ。

合計で8バイトがスタックに積まれることになります。しかし、`ADDL $12, SP`となっていることから、`runtime·externalthreadhandler`が内部でさらに4バイトのスタック領域を使用し、それを呼び出し元がクリーンアップする必要があるか、あるいは`runtime·profileloop`が`CALL`の前に別の値をスタックにプッシュしていた可能性があります。

いずれにせよ、`$40`という値は明らかに過剰であり、スタックを過剰に解放してしまうことで、後続のスタック操作やメモリアクセスに問題を引き起こす可能性がありました。これは、スタックの破損や、予期せぬプログラムのクラッシュにつながる重大なバグとなり得ます。

コミットメッセージにある「Windowsで深刻なエディタの問題」は、このような低レベルのアセンブリコード編集時に、エディタの自動補完、フォーマット、または単なる誤入力によって、意図しない数値が挿入されてしまったことを示唆しています。この修正は、Goランタイムの堅牢性を維持するために不可欠なものです。

## コアとなるコードの解説

変更されたコードは、`src/runtime/sys_windows_386.s`ファイル内の`runtime·profileloop`関数の一部です。

```assembly
TEXT runtime·profileloop(SB),NOSPLIT,$0
    ; ... (前略) ...
    PUSHL   $runtime·profileloop1(SB)
    CALL    runtime·externalthreadhandler(SB)
    MOVL    4(SP), CX
    ADDL    $12, SP  ; ← この行が変更された
    JMP     CX
    ; ... (後略) ...
```

*   `TEXT runtime·profileloop(SB),NOSPLIT,$0`: `runtime·profileloop`という名前の関数を定義しています。`(SB)`はグローバルシンボルであることを示し、`NOSPLIT`はスタック拡張チェックを行わないことを意味します。`$0`は、この関数がローカル変数に0バイトのスタックフレームを使用することを示します。
*   `PUSHL $runtime·profileloop1(SB)`: `runtime·profileloop1`というシンボルのアドレスをスタックにプッシュします。`PUSHL`は32ビット値をプッシュします。
*   `CALL runtime·externalthreadhandler(SB)`: `runtime·externalthreadhandler`関数を呼び出します。`CALL`命令は、次の命令のアドレス（リターンアドレス）をスタックにプッシュし、指定されたアドレスにジャンプします。
*   `MOVL 4(SP), CX`: スタックポインタ`SP`から4バイトオフセットしたメモリ位置にある32ビット値（`4(SP)`）を`CX`レジスタに移動します。これは、スタックにプッシュされた`runtime·profileloop1`のアドレスを`CX`レジスタにロードしていると考えられます。
*   `ADDL $12, SP`: **この行が今回の変更点です。** `SP`レジスタに12を加算します。これにより、スタックポインタが12バイト分上位アドレスに移動し、スタック上の12バイト分の領域が解放されます。これは、`PUSHL`と`CALL`によってスタックに積まれたデータ（`runtime·profileloop1`のアドレスとリターンアドレス、および`runtime·externalthreadhandler`が使用した可能性のあるスタック領域）をクリーンアップする操作です。
*   `JMP CX`: `CX`レジスタに格納されているアドレスに無条件でジャンプします。これは、`runtime·profileloop1`のアドレスにジャンプし、処理を継続することを意味します。

この修正により、`runtime·profileloop`関数が`runtime·externalthreadhandler`を呼び出した後のスタックの状態が正しく維持され、ランタイムの安定性が確保されます。

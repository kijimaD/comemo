# [インデックス 24465] ファイルの概要

このコミットは、GoコンパイラのアセンブラバックエンドにおけるARMおよびARM64アーキテクチャでの行番号情報のバグを修正するものです。具体的には、関数が大きすぎて定数プール（literal pool）を関数の途中でフラッシュする必要がある場合に、その後の命令の行番号が誤って割り当てられる問題を解決します。これにより、特に大きな関数において、デバッグ情報やプロファイリング情報（`runtime/trace`など）の正確性が損なわれることがありました。

## 変更の背景

Goコンパイラは、Go言語のソースコードを機械語に変換する際に、デバッグやプロファイリングのためにソースコードの行番号情報を生成します。この情報は、実行時のスタックトレース、デバッガでのステップ実行、プロファイリングツール（例: `runtime/trace`）でのシンボル解決などに不可欠です。

ARMおよびARM64アーキテクチャでは、命令がPC（プログラムカウンタ）からの相対アドレスでデータを参照する際に、参照できるオフセットに制限があります。このため、関数内で使用される大きな定数（数値、文字列、アドレスなど）や、遠く離れたアドレスへのジャンプ先などは、直接命令に埋め込むことができません。代わりに、これらの定数は「定数プール（literal pool）」と呼ばれるメモリ領域に格納され、命令からはその定数プール内のエントリへのPC相対アドレスでアクセスされます。

大きな関数では、定数プールが大きくなりすぎたり、PC相対アドレッシングの範囲を超えたりする可能性があります。このような場合、コンパイラは関数の途中に定数プールを「フラッシュ」し、その内容をコードストリームに挿入する必要があります。

このコミット以前のGoコンパイラのアセンブラバックエンドでは、この定数プールが関数の途中に挿ッシュされる際に、定数プール自体の行番号だけでなく、その後に続くすべての命令の行番号までが誤って設定されてしまうバグがありました。結果として、大きな関数では関数の冒頭部分を除いて、行番号情報が完全に間違ったものになっていました。

この問題は、特にGoのランタイムトレース機能である`runtime/trace`の`TestTraceSymbolize`テストを壊していました。`TestTraceSymbolize`は、実行時のアドレスから正確なソースコードの行番号や関数名を解決できることを検証するテストであり、行番号情報の誤りは直接このテストの失敗につながります。このバグはARMビルドを壊していたため、修正が必要とされました。

## 前提知識の解説

### Goコンパイラとアセンブラバックエンド (`cmd/internal/obj`)

Go言語のコンパイラは、ソースコードを中間表現に変換した後、各ターゲットアーキテクチャ（x86, ARM, ARM64など）向けのアセンブリコードを生成します。このアセンブリコード生成を担当する部分が、`cmd/internal/obj`パッケージとそのサブパッケージ群です。`cmd/internal/obj/arm`や`cmd/internal/obj/arm64`は、それぞれARMおよびARM64アーキテクチャ固有のアセンブリコード生成ロジックを含んでいます。

### ARM/ARM64アーキテクチャと定数プール (Literal Pool)

ARMアーキテクチャはRISC（Reduced Instruction Set Computer）であり、命令長が固定されています。多くの命令は、オペランドとして即値（immediate value）を取ることができますが、その値の範囲には制限があります。また、メモリ上のデータやコードへのアクセスも、PC（プログラムカウンタ）からの相対アドレスやベースレジスタからのオフセットで指定されることが一般的です。

特に、PC相対アドレッシングでは、命令から参照できるアドレス範囲に限りがあります。関数内で使用される大きな定数（例: 32ビットや64ビットの整数、浮動小数点数、文字列リテラル、グローバル変数のアドレスなど）は、命令の即値フィールドに収まらないか、PC相対アドレッシングの範囲外にある場合があります。

このような場合、コンパイラはこれらの定数を「定数プール（literal pool）」と呼ばれるメモリ領域に配置します。定数プールは通常、関数の終わりや、コードの実行フローに影響を与えない場所に配置されます。命令は、定数プール内の目的のエントリへのPC相対アドレスを計算して、その値をロードします。

### 定数プールのフラッシュ

関数が非常に大きい場合や、多くの定数を使用する場合、定数プールも大きくなります。PC相対アドレッシングの範囲は限られているため、関数の冒頭に配置された定数プールが、関数の後半の命令からは参照できなくなる可能性があります。この問題を解決するため、コンパイラは関数の途中で現在の定数プールを「フラッシュ」し、その内容をコードストリームに挿入します。そして、新しい定数プールをその後に開始します。これにより、常に命令から定数プールへのアクセスが可能になります。

### 行番号情報とPC-Lineテーブル

デバッグ情報（Goでは主にDWARFフォーマットを使用）には、実行可能な機械語コードのアドレス（PC: Program Counter）と、対応するソースコードのファイル名および行番号をマッピングする「PC-Lineテーブル」が含まれています。このテーブルは、デバッガが特定の実行アドレスで停止したときに、どのソースコードの行に対応するかを特定するために使用されます。

PC-Lineテーブルは、通常、アドレスの範囲と行番号のデルタ（差分）をエンコードすることで効率的に表現されます。行番号が連続して変化しない場合、デルタは0となり、テーブルのエントリ数を減らすことができます。

### `runtime/trace`とシンボル解決

Goの`runtime/trace`パッケージは、Goプログラムの実行を詳細にプロファイリングするためのツールを提供します。これには、ゴルーチンのスケジューリング、GCイベント、システムコールなどの情報が含まれます。トレースデータには、実行時のアドレス情報が含まれており、これを人間が理解できるソースコードのファイル名、関数名、行番号に変換するプロセスを「シンボル解決（symbolization）」と呼びます。

`TestTraceSymbolize`は、このシンボル解決が正しく機能するかどうかを検証するテストです。もし行番号情報が誤っていれば、トレースデータから得られる情報も不正確になり、デバッグやパフォーマンス分析が困難になります。

## 技術的詳細

このコミットは、`src/cmd/internal/obj/arm/asm5.go`と`src/cmd/internal/obj/arm64/asm7.go`内の`flushpool`関数における行番号の割り当てロジックを修正しています。

`flushpool`関数は、定数プールをコードストリームに挿入する役割を担っています。問題は、定数プール内の各エントリに割り当てられる行番号のタイミングと方法にありました。

**問題点:**
以前の実装では、定数プールがコードストリームにリンクされた後で、定数プール内のすべてのエントリ（`ctxt.Blitrl`から始まるリスト）に対して、その直前の命令`p`の行番号（`p.Lineno`）を割り当てていました。

```go
// 変更前のコードの一部 (arm/asm5.go)
ctxt.Elitrl.Link = p.Link
p.Link = ctxt.Blitrl

// BUG(minux): how to correctly handle line number for constant pool entries?
// for now, we set line number to the last instruction preceding them at least
// this won't bloat the .debug_line tables
for ctxt.Blitrl != nil {
    ctxt.Blitrl.Lineno = p.Lineno // ここで定数プールエントリの行番号を設定
    ctxt.Blitrl = ctxt.Blitrl.Link
}
```

このロジックの問題は、定数プールが挿入された後、その直後の命令の行番号が、定数プールエントリの行番号と同じ`p.Lineno`に設定されてしまう可能性があったことです。PC-Lineテーブルのエンコーディングでは、行番号のデルタが0の場合に効率的ですが、定数プールが挿入されることで、本来異なる行番号を持つべき後続の命令までが、誤って同じ行番号を持つと解釈されてしまうことがありました。これにより、特に大きな関数で、定数プール以降のすべての命令の行番号が不正確になるという副作用が生じていました。

**修正内容:**
修正では、定数プール内のエントリに行番号を割り当てるループを、定数プールをコードストリームにリンクする処理の**前**に移動しました。

```go
// 変更後のコードの一部 (arm/asm5.go)
// The line number for constant pool entries doesn't really matter.
// We set it to the line number of the preceding instruction so that
// there are no deltas to encode in the pc-line tables.
for q := ctxt.Blitrl; q != nil; q = q.Link {
    q.Lineno = p.Lineno // 定数プールをリンクする前にここで設定
}

ctxt.Elitrl.Link = p.Link
p.Link = ctxt.Blitrl
```

この変更により、定数プール内のエントリには、それが挿入される直前の命令の行番号が正しく割り当てられます。そして、その後に定数プールがコードストリームにリンクされます。この順序の変更が重要です。定数プール自体の行番号はデバッグ情報としてはあまり意味がないため、直前の命令の行番号に設定することで、PC-Lineテーブルのエンコーディングをシンプルに保ちつつ、後続の命令の行番号計算に悪影響を与えないようにしています。

コメントにもあるように、「定数プールエントリの行番号は実際にはあまり重要ではない。PC-Lineテーブルにエンコードするデルタがないように、直前の命令の行番号に設定する」という意図が明確にされています。これにより、定数プールが挿入された後も、本来のソースコードの行に対応する命令には正しい行番号が割り当てられるようになり、`runtime/trace`のようなツールが正確なシンボル解決を行えるようになりました。

## コアとなるコードの解説

`flushpool`関数は、Goコンパイラのアセンブラバックエンドにおいて、定数プールを現在の命令ストリームに挿入する役割を担っています。この関数は、`obj.Prog`構造体（アセンブリ命令を表す）のリンクリストを操作し、定数プールを適切な位置に配置します。

変更の核心は、定数プール内の各エントリ（`q`）に行番号（`q.Lineno`）を割り当てるタイミングです。

**変更前:**
1.  `ctxt.Elitrl.Link = p.Link` と `p.Link = ctxt.Blitrl` によって、定数プール（`ctxt.Blitrl`から`ctxt.Elitrl`まで）が、現在の命令`p`の直後にリンクされていました。
2.  **その後**、`for ctxt.Blitrl != nil { ... }` ループ内で、定数プール内の各エントリの行番号が`p.Lineno`（定数プールが挿入される直前の命令の行番号）に設定されていました。

この順序が問題でした。定数プールが既に命令ストリームに挿入された後でその行番号を設定すると、デバッグ情報の生成ロジックが、定数プールに続く本来の命令の行番号を誤って解釈する可能性がありました。特に、PC-Lineテーブルのエンコーディングでは、行番号のデルタが重要であり、この誤った設定が行番号情報の全体的な不正確さにつながっていました。

**変更後:**
1.  まず、`for q := ctxt.Blitrl; q != nil; q = q.Link { q.Lineno = p.Lineno }` ループが実行されます。このループは、定数プール内のすべてのエントリ`q`に対して、その行番号を`p.Lineno`（定数プールが挿入される直前の命令の行番号）に設定します。この時点では、定数プールはまだ命令ストリームにはリンクされていません。
2.  **その後**、`ctxt.Elitrl.Link = p.Link` と `p.Link = ctxt.Blitrl` によって、行番号が設定された定数プールが、現在の命令`p`の直後にリンクされます。

この変更により、定数プール内のエントリの行番号は、それが命令ストリームに挿入される前に適切に設定されます。定数プール自体の行番号はデバッグ情報として重要ではないため、直前の命令の行番号に設定することで、PC-Lineテーブルのエンコーディングをシンプルに保ちつつ、後続の命令の行番号計算に影響を与えないという目的が達成されます。

この修正は、Goコンパイラが生成するデバッグ情報の正確性を向上させ、`runtime/trace`のようなプロファイリングツールがより信頼性の高いシンボル解決を提供できるようにするために不可欠でした。

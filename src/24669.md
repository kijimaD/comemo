# [インデックス 24669] ファイルの概要

このコミットは、GoランタイムおよびsyscallパッケージのSolaris実装から、使用されなくなった`dlopen`、`dlclose`、`dlsym`への参照を削除するものです。以前の変更（CL 9184）により、Solarisバイナリが`dlopen/dlsym`を介した動的ロードではなく、直接リンクされるようになったため、これらの動的ロード関連の関数は不要となり、削除されました。これにより、コードベースのクリーンアップと、もはや機能しない参照の除去が行われました。

## 変更の背景

このコミットの背景には、Go言語のSolarisサポートにおけるライブラリリンケージ戦略の変更があります。以前は、GoプログラムがSolarisシステムコールやCライブラリ関数を呼び出す際に、`dlopen`、`dlsym`、`dlclose`といった動的リンキングAPIを使用して、実行時に必要なライブラリをロードし、その中のシンボル（関数や変数）のアドレスを取得していました。これは、柔軟性を提供する一方で、オーバーヘッドや複雑さを伴う可能性があります。

しかし、CL 9184という以前の変更（Goのチェンジリスト番号）によって、Goのランタイムとsyscallパッケージは、Solarisバイナリを**直接リンク**するように変更されました。直接リンクとは、コンパイル時に必要なライブラリが静的または動的に（ただし、`dlopen`のような実行時ロードAPIを使わずに）バイナリに結合されることを意味します。この変更により、`dlopen`、`dlclose`、`dlsym`といった動的ロード関連のAPIはGoのSolaris実装において不要となりました。

このコミットは、CL 9184の変更後に残された、もはや使用されていない（そして機能しない可能性のある）`dlopen`、`dlclose`、`dlsym`への参照を削除することを目的としています。これにより、コードベースのクリーンアップ、不必要な依存関係の除去、および潜在的なバグの回避が図られています。

## 前提知識の解説

### 動的リンキングと静的リンキング

*   **静的リンキング (Static Linking)**: プログラムのコンパイル時に、必要なライブラリのコードが実行可能ファイルに直接組み込まれる方式です。これにより、実行可能ファイルは自己完結型となり、外部ライブラリの存在に依存しません。しかし、ファイルサイズが大きくなり、ライブラリの更新があった場合にプログラム全体を再コンパイルする必要があります。
*   **動的リンキング (Dynamic Linking)**: プログラムの実行時に、必要なライブラリがメモリにロードされ、プログラムと結合される方式です。これにより、複数のプログラムが同じライブラリを共有できるため、メモリ使用量を削減し、ファイルサイズを小さく保つことができます。また、ライブラリの更新があっても、プログラムを再コンパイルせずに新しいライブラリを利用できる場合があります。

### `dlopen`, `dlsym`, `dlclose`

これらはPOSIXシステム（Linux, Solaris, macOSなど）で提供される動的リンキングAPIの一部で、実行時に共有ライブラリ（WindowsでいうDLL）をロード・アンロードし、その中のシンボルにアクセスするために使用されます。

*   `dlopen(const char *filename, int flags)`: 指定された共有ライブラリをロードします。成功すると、ライブラリへのハンドルを返します。
*   `dlsym(void *handle, const char *symbol)`: `dlopen`で取得したハンドルを使って、ロードされたライブラリ内の指定されたシンボル（関数名や変数名）のアドレスを取得します。
*   `dlclose(void *handle)`: `dlopen`でロードされた共有ライブラリをアンロードします。

### GoにおけるCGOと外部関数呼び出し

Go言語は、C言語のコードをGoプログラムから呼び出すためのCGOというメカニズムを提供しています。CGOを使用すると、Goコード内でCの関数を直接呼び出したり、Cのデータ構造を利用したりできます。

*   **`//go:cgo_import_dynamic`**: このディレクティブは、CGOが動的にリンクされるCライブラリからシンボルをインポートすることを示します。具体的には、指定されたシンボル（例: `libc_chdir`）が、指定されたライブラリ（例: `libc.so`）から動的にロードされることをコンパイラに伝えます。これは、`dlopen`/`dlsym`を使用する動的ロードのシナリオでよく使われます。
*   **`//go:linkname`**: このディレクティブは、Goのリンカに対して、あるシンボル（関数や変数）を別のシンボル名にリンクするように指示します。これは、Goの内部実装や、CGOとGoランタイム間の連携において、特定のC関数をGoのシンボルとして扱ったり、その逆を行ったりするために使用されます。例えば、`//go:linkname libc_chdir libc_chdir`は、Goの内部で`libc_chdir`という名前で参照されるシンボルが、Cライブラリの`chdir`関数にリンクされることを示唆しています。

### Solarisオペレーティングシステム

Solarisは、Sun Microsystems（現在はOracleが所有）によって開発されたUNIXベースのオペレーティングシステムです。高性能なサーバー環境で広く使用されていました。Go言語は、様々なオペレーティングシステムをサポートしており、Solarisもその一つです。

## 技術的詳細

このコミットは、GoのSolaris実装におけるリンケージ戦略の変更に起因するコードのクリーンアップです。

以前のGoのSolaris実装では、`src/runtime/syscall2_solaris.go`ファイル内で、`dlopen`、`dlclose`、`dlsym`といった動的リンキングAPIが`//go:cgo_import_dynamic`ディレクティブを使ってインポートされていました。これは、GoプログラムがSolarisのCライブラリ関数を呼び出す際に、これらのAPIを使って必要な関数を動的に解決していたことを意味します。

具体的には、以下の行が存在していました。

```go
//go:cgo_import_dynamic libc_dlclose dlclose "libc.so"
//go:cgo_import_dynamic libc_dlopen dlopen "libc.so"
//go:cgo_import_dynamic libc_dlsym dlsym "libc.so"
```

そして、これらのインポートされたシンボルは、`//go:linkname`ディレクティブを使ってGoの内部シンボルにリンクされていました。

```go
//go:linkname libc_dlclose libc_dlclose
//go:linkname libc_dlopen libc_dlopen
//go:linkname libc_dlsym libc_dlsym
```

さらに、`src/syscall/asm_solaris_amd64.s`というアセンブリファイルでは、これらの動的ロード関数に対応するGoのラッパー関数（例: `TEXT ·dlopen(SB)`）が定義されており、それぞれが`runtime·syscall_dlopen(SB)`のようなランタイム内の実際のシステムコール実装にジャンプしていました。

```assembly
TEXT ·dlopen(SB),NOSPLIT,$0
	JMP	runtime·syscall_dlopen(SB)

TEXT ·dlclose(SB),NOSPLIT,$0
	JMP	runtime·syscall_dlclose(SB)

TEXT ·dlsym(SB),NOSPLIT,$0
	JMP	runtime·syscall_dlsym(SB)
```

CL 9184の変更により、GoのSolaris実装は`dlopen/dlsym`を使用する動的ロードから、より直接的なリンケージ方式に移行しました。この新しい方式では、`dlopen`、`dlclose`、`dlsym`はもはやGoランタイムやsyscallパッケージの動作に必要なくなりました。

このコミットは、その結果として残された不要なコードを削除するものです。これらの参照を削除することで、以下の利点があります。

1.  **コードのクリーンアップ**: 不要なコードは削除され、コードベースがより簡潔になります。
2.  **不必要な依存関係の除去**: もはや使用されないAPIへの参照がなくなることで、コードの理解が容易になり、将来的なメンテナンスが簡素化されます。
3.  **潜在的なバグの回避**: 使用されていないが残っている参照は、コンパイラやリンカのエラーを引き起こしたり、誤解を招いたりする可能性があります。特に、コミットメッセージにある「now broken」という記述は、これらの参照がCL 9184以降、正しく機能しなくなっていたことを示唆しています。

この変更は、GoのSolarisサポートの成熟と最適化の一環として行われたものであり、特定のプラットフォームにおけるGoのランタイムの効率性と堅牢性を向上させるための継続的な取り組みを反映しています。

## コアとなるコードの解説

このコミットでは、主に2つのファイルからコードが削除されています。

### `src/runtime/syscall2_solaris.go`

このファイルは、GoランタイムがSolarisシステムコールを呼び出すためのCGOインポートとリンク名定義を含んでいます。

*   **削除された行（`//go:cgo_import_dynamic`）**:
    ```go
    -//go:cgo_import_dynamic libc_dlclose dlclose "libc.so"
    -//go:cgo_import_dynamic libc_dlopen dlopen "libc.so"
    -//go:cgo_import_dynamic libc_dlsym dlsym "libc.so"
    ```
    これらの行は、`libc.so`という共有ライブラリから`dlclose`、`dlopen`、`dlsym`というC関数を動的にインポートするようにGoコンパイラに指示していました。CL 9184以降、これらの関数はGoのSolaris実装で直接使用されなくなったため、インポートの定義も不要となり削除されました。

*   **削除された行（`//go:linkname`）**:
    ```go
    -//go:linkname libc_dlclose libc_dlclose
    -//go:linkname libc_dlopen libc_dlopen
    -//go:linkname libc_dlsym libc_dlsym
    ```
    これらの行は、Goのリンカに対して、Goの内部シンボル（例: `libc_dlclose`）を、CGOでインポートされた対応するC関数（この場合は同じ名前の`libc_dlclose`）にリンクするように指示していました。`//go:cgo_import_dynamic`の定義が削除されたため、これらの`//go:linkname`の定義も不要となり削除されました。

### `src/syscall/asm_solaris_amd64.s`

このファイルは、Solaris/AMD64アーキテクチャ向けのシステムコールラッパーを定義するアセンブリコードを含んでいます。Goの関数がCのシステムコールを呼び出す際に、このアセンブリコードが仲介役となります。

*   **削除された行（`TEXT ·dlopen(SB)`など）**:
    ```assembly
    -TEXT ·dlopen(SB),NOSPLIT,$0
    -	JMP	runtime·syscall_dlopen(SB)
    -
    -TEXT ·dlclose(SB),NOSPLIT,$0
    -	JMP	runtime·syscall_dlclose(SB)
    -
    -TEXT ·dlsym(SB),NOSPLIT,$0
    -	JMP	runtime·syscall_dlsym(SB)
    ```
    これらのアセンブリコードブロックは、Goの`dlopen`、`dlclose`、`dlsym`関数に対応するラッパーでした。これらは、Goのコードから呼び出された際に、実際のランタイム内のシステムコール実装（例: `runtime·syscall_dlopen(SB)`）にジャンプする役割を担っていました。`dlopen`、`dlclose`、`dlsym`がGoのSolaris実装で不要になったため、これらのアセンブリラッパーも削除されました。

これらの変更は、GoのSolaris実装が動的ロードAPIに依存しなくなったことを明確に示しており、コードベースの整合性を保つための重要なクリーンアップです。

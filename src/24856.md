# [インデックス 24856] ファイルの概要

## コミット
このコミットは、Goリンカーが共有オブジェクトを作成する際に、読み取り専用の再配置済みデータを`.data.rel.ro`セクションに配置する変更を元に戻す（リバートする）ものです。この変更は`darwin/arm64`環境で問題を引き起こしたため、元の状態に戻されました。

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/e49b2460a40208d0c50922f898b58fdafa40eca0](https://github.com/golang/go/commit/e49b2460a40208d0c50922f898b58fdafa40eca0)

## 元コミット内容
元のコミット（ハッシュ: `2c2cbb69c8dad1325f0a4b289417da73fd90f4b0`）は、「cmd/internal/ld: put read-only relocated data into .data.rel.ro when making a shared object」というタイトルで、Goリンカーが共有ライブラリ（共有オブジェクト）をビルドする際に、再配置が必要な読み取り専用データを`.data.rel.ro`という特別なセクションに配置するように変更するものでした。

## 変更の背景
元のコミットは、共有ライブラリのセキュリティと効率性を向上させることを目的としていました。通常、プログラムの読み取り専用データは`.rodata`セクションに配置されますが、動的リンカーによって実行時に再配置（アドレスの修正）が必要な場合、そのデータは一時的に書き込み可能である必要があります。しかし、再配置が完了した後は、そのデータは再び読み取り専用として保護されるべきです。

ELF（Executable and Linkable Format）形式を使用するシステム（主にLinux）では、`.data.rel.ro`（data.relocated.read-only）というセクションがこの目的のために存在します。このセクションに配置されたデータは、リンカーによって初期は書き込み可能としてマークされ、動的リンカーが再配置を適用した後、`mprotect`システムコールなどによって読み取り専用に設定されます。これにより、実行時のセキュリティが向上し、意図しない書き込みからデータを保護できます。

元のコミットは、GoのリンカーがこのELFの慣習に従い、Goが生成する共有ライブラリでも同様のセキュリティ強化を図ろうとしたものです。しかし、この変更が`darwin/arm64`（macOS上のARM64アーキテクチャ）で動作不良を引き起こしたため、このコミットはリバートされました。これは、macOSの動的リンカー（dyld）がELFの`.data.rel.ro`セクションの概念や処理方法と互換性がなかったか、GoリンカーのmacOS向けの実装に問題があったことを示唆しています。

## 前提知識の解説

### 共有ライブラリと動的リンク
共有ライブラリ（Shared Library、WindowsではDLL、Linuxでは.so、macOSでは.dylib）は、複数のプログラムで共有されるコードやデータを格納するファイルです。動的リンクでは、プログラムの実行時にこれらのライブラリがメモリにロードされ、プログラムとリンクされます。これにより、ディスクスペースの節約、メモリ使用量の削減、プログラムのモジュール化が実現されます。

### 再配置 (Relocation)
プログラムがコンパイルされる際、コードやデータは通常、特定のアドレスを基準に生成されます。しかし、共有ライブラリの場合、ロードされるメモリ上の正確なアドレスは実行時まで分かりません。そのため、リンカーは、実行時に実際のメモリ位置に基づいてアドレスを修正する必要がある箇所をマークします。この修正プロセスを「再配置」と呼びます。

### ELF (Executable and Linkable Format)
ELFは、Unix系システム（Linuxなど）で広く使用されている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準ファイル形式です。ELFファイルは、プログラムのコード、データ、シンボルテーブル、再配置情報などを構造化して格納します。

### Mach-O (Mach Object)
Mach-Oは、macOSやiOSなどのApple製オペレーティングシステムで使用される実行可能ファイル、オブジェクトファイル、共有ライブラリのファイル形式です。ELFと同様に、プログラムのバイナリ情報を格納しますが、その内部構造や動的リンカーの動作はELFとは異なります。

### .rodataセクション
プログラムのバイナリにおいて、変更されない定数データ（文字列リテラル、読み取り専用変数など）が格納されるセクションです。このセクションは通常、実行時に読み取り専用としてメモリにマッピングされ、誤った書き込みから保護されます。

### .data.rel.roセクション
ELF形式の共有ライブラリにおいて、概念的には読み取り専用であるものの、動的リンカーによる再配置が必要なデータが格納される特殊なセクションです。このセクションは、ロード時には書き込み可能として扱われ、再配置が完了した後に読み取り専用に保護されます。これにより、セキュリティが向上し、Position-Independent Code (PIC) の生成にも寄与します。

### mprotectシステムコール
`mprotect`は、Unix系システムでメモリ領域の保護属性（読み取り、書き込み、実行）を変更するために使用されるシステムコールです。`.data.rel.ro`セクションのデータは、再配置後にこの`mprotect`を使って読み取り専用に設定されます。

## 技術的詳細

元のコミットは、GoリンカーがELF形式の共有ライブラリを生成する際に、特定の種類の読み取り専用データを`.rodata`セクションではなく、`.data.rel.ro`セクションに配置するように変更しました。具体的には、`obj.STYPE`から`obj.SFUNCTAB`までのシンボルタイプで、かつ再配置（`len(s.R) > 0`）が必要なもの、および`obj.SGOSTRING`タイプのシンボルが対象でした。これらのシンボルは、`obj.STYPERELRO`などの対応する`RELRO`タイプに「昇格」され、`.data.rel.ro`セクションにマッピングされるように処理されていました。

このアプローチは、LinuxなどのELFシステムでは標準的であり、共有ライブラリのセキュリティを強化する上で有効です。再配置が必要な読み取り専用データが、再配置完了後に書き込み不可となることで、攻撃者がその領域を改ざんするのを防ぎます。

しかし、この変更が`darwin/arm64`で問題を引き起こしました。考えられる原因はいくつかあります。

1.  **Mach-O形式との非互換性:** macOSが使用するMach-O形式のバイナリは、ELFとは異なるセクション構造と動的リンカーの動作を持っています。`.data.rel.ro`のようなELF特有のセクションの概念がMach-Oには直接存在しないか、GoリンカーがMach-O形式に合わせた適切な処理を実装できていなかった可能性があります。
2.  **dyldの挙動:** macOSの動的リンカー（dyld）は、ELFのリンカーとは異なる方法で再配置とメモリ保護を扱います。Goリンカーが`.data.rel.ro`セクションを生成し、特定のメモリ保護属性を期待しても、dyldがそれを正しく解釈または適用できなかった可能性があります。
3.  **ARM64アーキテクチャ固有の問題:** `darwin/arm64`という特定のアーキテクチャで問題が発生したことから、ARM64のメモリモデル、命令セット、またはmacOS上でのABI（Application Binary Interface）の差異が影響した可能性も考えられます。例えば、特定の再配置タイプがARM64上で正しく処理されなかった、あるいはメモリ保護の粒度が期待と異なったなどが挙げられます。
4.  **Goリンカーのバグ:** Goリンカーが`.data.rel.ro`セクションを扱う際、`darwin/arm64`固有のリンキング要件や、Mach-O形式の制約を考慮しきれていなかったバグがあった可能性も否定できません。

このリバートは、Goのクロスプラットフォーム対応の複雑さを示しています。異なるOSやアーキテクチャ間でバイナリ形式やリンキングの挙動が大きく異なるため、一方のプラットフォームで有効な最適化やセキュリティ強化が、別のプラットフォームで予期せぬ問題を引き起こすことがあります。

## コアとなるコードの変更箇所

このコミットはリバートであるため、以下の変更箇所は元のコミットで追加され、このコミットで削除されたコードを示します。

### `src/cmd/internal/obj/link.go`
- `STYPERELRO`から`SFUNCTABRELRO`までの`RELRO`関連のシンボルタイプ定義が削除されました。これらは、`.data.rel.ro`セクションにマッピングされる読み取り専用データを表すために導入されていました。

### `src/cmd/link/internal/ld/data.go`
- `dodata()`関数内の`UseRelro()`チェックブロックが削除されました。このブロックは、`obj.STYPE`から`obj.SFUNCTAB`までのシンボルタイプで再配置が必要なもの、および`obj.SGOSTRING`タイプのシンボルを対応する`RELRO`タイプに「昇格」させるロジックを含んでいました。
- `.rodata`セクションの`sect.Align`計算で`obj.STYPERELRO-1`が使われていた箇所が`obj.STYPELINK-1`に戻されました。
- `.rodata`セクションのループ条件が`s.Type < obj.STYPERELRO`から`s.Type < obj.STYPELINK`に戻されました。
- `.data.rel.ro`セクションを追加し、その中に`RELRO`タイプのシンボルを配置する大きなブロックが削除されました。これには、`relro_perms`や`relro_prefix`の定義も含まれていました。
- `.typelink`, `.gosymtab`, `.gopclntab`セクションの追加において、`relro_prefix`を使用していた箇所が削除され、セクション名が元の形式（例: `.typelink`）に戻されました。

### `src/cmd/link/internal/ld/elf.go`
- `doelf()`関数内で、`BuildmodeShared`または`BuildmodeCShared`の場合に`.data.rel.ro`セクション名を`shstrtab`（セクション名文字列テーブル）に追加するロジックが削除されました。
- `relro_prefix`の定義と使用が削除され、`.typelink`, `.gosymtab`, `.gopclntab`およびそれらの再配置セクション（`.rela.*`, `.rel.*`）の名前が元の形式に戻されました。

### `src/cmd/link/internal/ld/lib.go`
- `UseRelro()`関数自体が削除されました。この関数は、現在のビルドモードとターゲットOSに基づいて`.data.rel.ro`を使用するかどうかを判断するものでした。
- `hostlink()`関数内で、`-Wl,-z,relro`リンカーフラグを条件付きで追加するロジックが削除されました。

### `src/cmd/link/internal/ld/symtab.go`
- `symtab()`関数内で、`UseRelro()`の条件分岐に基づいて`symtyperel`というシンボルを生成するロジックが削除されました。
- `strings.HasPrefix(s.Name, "type.")`の条件内で、`UseRelro()`と再配置の有無に基づいてシンボルタイプを`obj.STYPERELRO`に設定するロジックが削除され、常に`obj.STYPE`に設定されるようになりました。

## コアとなるコードの解説

このリバートコミットは、Goリンカーが共有ライブラリをビルドする際のセクションマッピングとリンカーフラグの扱いを、元の状態に戻すものです。

- **シンボルタイプの削除 (`src/cmd/internal/obj/link.go`)**: 元のコミットでは、`.data.rel.ro`セクションに配置されるべき読み取り専用データのために、`STYPERELRO`などの新しいシンボルタイプが導入されていました。これらは、通常の読み取り専用データ（`.rodata`）とは異なる扱いを受けることを示すためのものでしたが、リバートにより削除されました。

- **データセクション処理の変更 (`src/cmd/link/internal/ld/data.go`)**:
    - `dodata()`関数は、Goのリンカーが様々なデータセクションを配置する主要な場所です。元のコミットでは、`UseRelro()`が真の場合（つまり、ELF共有ライブラリをビルドする場合）、再配置が必要な読み取り専用シンボルを`RELRO`タイプに変換し、それらを`.data.rel.ro`という新しいセクションに集約していました。このリバートにより、この特殊な処理が完全に削除され、これらのデータは再び通常の`.rodata`セクションに配置されるか、あるいは他の既存のセクションにフォールバックするようになりました。
    - セクションのアライメントやループ条件の変更は、`RELRO`タイプのシンボルが存在しなくなったことに伴う調整です。
    - `.typelink`, `.gosymtab`, `.gopclntab`といったGoランタイム固有のメタデータセクションも、元のコミットでは`relro_prefix`（つまり`.data.rel.ro`）を付けてセクション名を生成しようとしていましたが、これも削除され、標準のセクション名に戻されました。

- **ELFヘッダとセクション名の変更 (`src/cmd/link/internal/ld/elf.go`)**:
    - `doelf()`関数は、ELFバイナリのヘッダ情報やセクションテーブルを構築する役割を担います。元のコミットでは、`.data.rel.ro`セクションや、`relro_prefix`が付加されたGo固有のセクション名をELFのセクション名文字列テーブル（`shstrtab`）に追加していました。リバートにより、これらの特殊なセクション名は追加されなくなり、ELFバイナリの構造が元のシンプルな形に戻りました。

- **リンカーオプションの削除 (`src/cmd/link/internal/ld/lib.go`)**:
    - `UseRelro()`関数は、Goリンカーが`.data.rel.ro`の挙動を有効にするかどうかを決定するフラグでした。この関数の削除は、Goリンカーがこの機能を完全に無効にしたことを意味します。
    - `hostlink()`関数は、外部リンカー（通常はGCCなど）を呼び出す際に使用されるリンカーオプションを構築します。元のコミットでは、`UseRelro()`が真の場合に`-Wl,-z,relro`というフラグを外部リンカーに渡していました。このフラグは、ELFリンカーに対して`.data.rel.ro`セクションを適切に処理し、再配置後に読み取り専用に保護するよう指示するものです。このフラグの削除は、Goリンカーがこのセキュリティ機能の利用を停止したことを示しています。

- **シンボルテーブル処理の変更 (`src/cmd/link/internal/ld/symtab.go`)**:
    - `symtab()`関数は、Goのシンボルテーブルを構築します。元のコミットでは、`type.`で始まるシンボル（Goの型情報など）が再配置を必要とする場合に、`obj.STYPERELRO`タイプに設定し、`.data.rel.ro`セクションにマッピングされるようにしていました。リバートにより、この特殊な処理は削除され、これらのシンボルは再び通常の`obj.STYPE`として扱われ、標準の読み取り専用データセクションに配置されるようになりました。

全体として、このリバートは、GoリンカーがELF共有ライブラリの`.data.rel.ro`セクションを利用してセキュリティを強化しようとした試みが、`darwin/arm64`プラットフォームとの互換性の問題により一時的に中断されたことを示しています。Goのリンカーは、異なるOSやアーキテクチャのリンキング要件に対応するために、非常に複雑なロジックを持っています。

# [インデックス 27129] ファイルの概要

このコミットは、Go言語の `crypto/tls` パッケージにおけるTLSレコードサイズの動的な調整機能の実装に関するものです。具体的には、TLS接続の初期段階では小さなレコードサイズを使用し、一定量のデータが送信された後に大きなレコードサイズに切り替えることで、特に低速なネットワーク環境におけるレイテンシとスループットのバランスを改善することを目的としています。

## コミット

`crypto/tls`: implement dynamic record sizing

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/ae00df128d8434dd37f73123aaea09de786d0275](https://github.com/golang/go/commit/ae00df128d8434dd37f73123aaea09de786d0275)

## 元コミット内容

```
crypto/tls: implement dynamic record sizing

Currently, if a client of crypto/tls (e.g., net/http, http2) calls
tls.Conn.Write with a 33KB buffer, that ends up writing three TLS
records: 16KB, 16KB, and 1KB. Slow clients (such as 2G phones) must
download the first 16KB record before they can decrypt the first byte.
To improve latency, it's better to send smaller TLS records. However,
sending smaller records adds overhead (more overhead bytes and more
crypto calls), which slightly hurts throughput.

A simple heuristic, implemented in this change, is to send small
records for new connections, then boost to large records after the
first 1MB has been written on the connection.

Fixes #14376

Change-Id: Ice0f6279325be6775aa55351809f88e07dd700cd
Reviewed-on: https://go-review.googlesource.com/19591
TryBot-Result: Gobot Gobot <gobot@golang.org>
Reviewed-by: Tom Bergan <tombergan@google.com>
Reviewed-by: Adam Langley <agl@golang.org>
```

## 変更の背景

従来の `crypto/tls` パッケージでは、`tls.Conn.Write` メソッドに大きなデータバッファが渡された場合、そのデータは最大16KBのTLSレコードに分割されて送信されていました。例えば、33KBのデータは16KB、16KB、1KBの3つのレコードとして送信されます。

この固定された大きなレコードサイズは、特に低速なネットワーク環境（例: 2G回線を使用するスマートフォン）において問題を引き起こしていました。クライアントは、最初の16KBのTLSレコード全体を受信し、復号化が完了するまで、そのレコード内の最初の1バイトすら処理を開始できません。これにより、特にインタラクティブなアプリケーションやウェブブラウジングにおいて、ユーザーが体感するレイテンシが増大するという課題がありました。

一方で、TLSレコードを小さくしすぎると、各レコードに付随するTLSヘッダーやMAC（Message Authentication Code）、IV（Initialization Vector）などのオーバーヘッドが増加し、さらに暗号化処理の呼び出し回数も増えるため、全体的なスループットがわずかに低下するというトレードオフが存在します。

このコミットは、このレイテンシとスループットのトレードオフを最適化するためのヒューリスティックを導入し、ユーザー体験の向上を目指しています。

## 前提知識の解説

### TLSレコードプロトコル
TLS（Transport Layer Security）は、インターネット上での安全な通信を確立するためのプロトコルです。TLSは複数の層で構成されており、その一つが「TLSレコードプロトコル」です。アプリケーションデータは、このレコードプロトコルによって小さな断片（レコード）に分割され、それぞれが圧縮、MACの付加、暗号化、ヘッダーの付加といった処理を経て送信されます。受信側では逆の処理が行われます。

TLSレコードの最大ペイロードサイズは通常16KB（`maxPlaintext`）に設定されています。このサイズは、TLS 1.0/1.1/1.2の仕様で規定されており、TLS 1.3では最大16KB + 256バイトのオーバーヘッドが許容されます。

### TCP MSS (Maximum Segment Size)
TCP MSSは、TCPセグメントが一度に運ぶことができるデータの最大量（バイト単位）を指します。これは、IP層でのMTU（Maximum Transmission Unit）からIPヘッダーとTCPヘッダーのサイズを差し引いた値です。一般的なイーサネット環境ではMTUが1500バイトであり、IPv4ヘッダー（20バイト）とTCPヘッダー（20バイト）を差し引くと、MSSは1460バイトになります。IPv6ではMTUが1280バイト（最小値）であり、IPv6ヘッダー（40バイト）とTCPヘッダー（32バイト、タイムスタンプオプションを含む）を差し引くと、MSSは約1208バイトになります。

TLSレコードがTCP MSSよりも大きい場合、一つのTLSレコードが複数のTCPセグメントに分割されて送信されます。これにより、パケットロスが発生した場合にTCPの再送メカニズムがトリガーされ、レイテンシが増加する可能性があります。また、受信側では、TLSレコード全体が揃うまで復号化を開始できないため、最初のバイトが利用可能になるまでの時間が長くなります。

### レイテンシとスループットのトレードオフ
*   **小さなTLSレコードの利点:**
    *   **低レイテンシ:** TLSレコードがTCP MSSに収まる場合、一つのTCPセグメントで送信され、受信側はより早くレコード全体を受信・復号化できるため、アプリケーションがデータを処理し始めるまでの時間が短縮されます。これは、特にウェブページの初期表示やインタラクティブな操作において重要です。
    *   **パケットロス耐性:** 小さなレコードは、パケットロスが発生しても再送されるデータ量が少なく、回復が速い可能性があります。
*   **小さなTLSレコードの欠点:**
    *   **オーバーヘッドの増加:** 各TLSレコードにはヘッダー、MAC、IVなどの固定オーバーヘッドが付随します。レコードが小さくなると、データ量に対するオーバーヘッドの割合が増加し、実効スループットが低下します。
    *   **暗号化処理の増加:** レコードごとに暗号化処理が実行されるため、レコード数が増えると暗号化/復号化の呼び出し回数が増え、CPUリソースの消費が増加する可能性があります。
*   **大きなTLSレコードの利点:**
    *   **高スループット:** オーバーヘッドの割合が減少し、暗号化処理の呼び出し回数も減るため、大量のデータを効率的に転送できます。
*   **大きなTLSレコードの欠点:**
    *   **高レイテンシ:** 前述の通り、低速なネットワークでは最初のバイトが利用可能になるまでの時間が長くなります。

このコミットは、このトレードオフを動的に管理することで、両方の利点を享受しようとするものです。

## 技術的詳細

このコミットで導入された動的なレコードサイジングは、以下のヒューリスティックに基づいています。

1.  **初期段階の小サイズレコード:** 新しいTLS接続の確立直後、または送信されたアプリケーションデータ量が `recordSizeBoostThreshold` (1MB) に達するまでは、TLSレコードのペイロードサイズをTCP MSSの推定値に収まるように小さくします。これにより、初期のデータ転送におけるレイテンシを最小限に抑え、特にウェブページの初期ロード時間を改善します。
2.  **閾値到達後の大サイズレコード:** 送信されたアプリケーションデータ量が `recordSizeBoostThreshold` を超えると、接続は「大量データ転送」フェーズに入ったと判断し、TLSレコードのペイロードサイズを最大値（`maxPlaintext`、約16KB）に切り替えます。これにより、大量のデータ転送におけるスループットを最大化し、オーバーヘッドを削減します。

このヒューリスティックは、ウェブブラウジングのようなインタラクティブな利用では初期の応答性を重視し、ファイルダウンロードのような大量データ転送では効率性を重視するという、一般的な利用パターンに合わせた最適化です。

### 実装の詳細

*   **`Config.DynamicRecordSizingDisabled` フィールドの追加:**
    `src/crypto/tls/common.go` に `DynamicRecordSizingDisabled bool` フィールドが `Config` 構造体に追加されました。このフィールドを `true` に設定することで、動的なレコードサイジング機能を無効にし、常に最大のTLSレコードサイズを使用するように強制できます。これは、特定のユースケースで動的サイジングが望ましくない場合に備えたオプションです。

*   **`Conn.bytesSent` フィールドの追加:**
    `src/crypto/tls/conn.go` の `Conn` 構造体に `bytesSent int64` フィールドが追加されました。これは、現在のTLS接続で送信されたアプリケーションデータの総バイト数を追跡するために使用されます。このカウンタは、`recordSizeBoostThreshold` に達したかどうかを判断するために利用されます。

*   **定数の定義:**
    *   `tcpMSSEstimate = 1208`: TCPの最大セグメントサイズ（MSS）の保守的な推定値です。これは、IPv6の最小MTU（1280バイト）からIPv6ヘッダー（40バイト）とTCPヘッダー（32バイト、タイムスタンプオプションを含む）のオーバーヘッドを差し引いた値です。実際のMSSをカーネルから問い合わせる複雑さを避けるために定数が使用されています。
    *   `recordSizeBoostThreshold = 1 * 1024 * 1024` (1MB): この閾値を超えると、TLSレコードサイズが最大値に切り替わります。

*   **`maxPayloadSizeForWrite` 関数の導入:**
    この新しい関数は、次に書き込むアプリケーションデータレコードに使用する最大のTLSペイロードサイズを計算します。
    *   `DynamicRecordSizingDisabled` が `true` の場合、またはレコードタイプがアプリケーションデータでない場合（例: ハンドシェイクメッセージ、アラートなど）は、常に `maxPlaintext` を返します。
    *   `c.bytesSent` が `recordSizeBoostThreshold` 以上の場合も、`maxPlaintext` を返します。
    *   それ以外の場合（初期段階のアプリケーションデータ）、`tcpMSSEstimate` からTLSのオーバーヘッド（レコードヘッダー長、明示的IV長、MACサイズ、AEADオーバーヘッド、CBCパディング）を差し引いて、TCP MSSに収まるペイロードサイズを計算します。これにより、TLSレコードが単一のTCPセグメントに収まるように試みます。

*   **`writeRecord` 関数の変更:**
    `writeRecord` 関数は、`maxPayloadSizeForWrite` 関数を呼び出して、現在の状況に応じた最適なペイロードサイズ `m` を取得するように変更されました。これにより、`data` バッファが `maxPayload` よりも大きい場合でも、`maxPayload` サイズでレコードが分割されるようになります。
    また、レコードが書き込まれるたびに `c.bytesSent` が更新され、送信されたアプリケーションデータの総バイト数が正確に追跡されます。

この実装は、接続がアイドル状態になった後にレコードサイズをリセットするような複雑なロジックは含んでいません。これは、実装のシンプルさと決定論性を優先したためです。このアプローチは、Ilya Grigorikの「High Performance Web Networking」の第4章や、[https://www.igvita.com/2013/10/24/optimizing-tls-record-size-and-buffering-latency/](https://www.igvita.com/2013/10/24/optimizing-tls-record-size-and-buffering-latency/) で説明されているヒューリスティックに基づいています。

## コアとなるコードの変更箇所

### `src/crypto/tls/common.go`
```go
type Config struct {
	// ... 既存のフィールド ...

	// DynamicRecordSizingDisabled disables adaptive sizing of TLS records.
	// When true, the largest possible TLS record size is always used. When
	// false, the size of TLS records may be adjusted in an attempt to
	// improve latency.
	DynamicRecordSizingDisabled bool

	// ... 既存のフィールド ...
}
```

### `src/crypto/tls/conn.go`
```go
type Conn struct {
	// ... 既存のフィールド ...

	// bytesSent counts the number of bytes of application data that have
	// been sent.
	bytesSent int64

	// ... 既存のフィールド ...
}

const (
	// tcpMSSEstimate is a conservative estimate of the TCP maximum segment
	// size (MSS). A constant is used, rather than querying the kernel for
	// the actual MSS, to avoid complexity. The value here is the IPv6
	// minimum MTU (1280 bytes) minus the overhead of an IPv6 header (40
	// bytes) and a TCP header with timestamps (32 bytes).
	tcpMSSEstimate = 1208

	// recordSizeBoostThreshold is the number of bytes of application data
	// sent after which the TLS record size will be increased to the
	// maximum.
	recordSizeBoostThreshold = 1 * 1024 * 1024
)

// maxPayloadSizeForWrite returns the maximum TLS payload size to use for the
// next application data record. ... (詳細は上記「技術的詳細」を参照)
func (c *Conn) maxPayloadSizeForWrite(typ recordType, explicitIVLen int) int {
	if c.config.DynamicRecordSizingDisabled || typ != recordTypeApplicationData {
		return maxPlaintext
	}

	if c.bytesSent >= recordSizeBoostThreshold {
		return maxPlaintext
	}

	// ... オーバーヘッド計算ロジック ...

	return payloadBytes
}

// writeRecord writes a TLS record with the given type and payload
// to the connection and updates the record layer state.
// c.out.Mutex <= L.
func (c *Conn) writeRecord(typ recordType, data []byte) (int, error) {
	var n int
	for len(data) > 0 {
		// 変更前: m = maxPlaintext
		// 変更後: maxPayloadSizeForWrite を使用して m を決定
		m := len(data)
		if maxPayload := c.maxPayloadSizeForWrite(typ, explicitIVLen); m > maxPayload {
			m = maxPayload
		}
		// ... レコードの構築と書き込み ...
		c.bytesSent += int64(m) // 送信バイト数を更新
		n += m
		data = data[m:]
	}
	return n, nil
}
```

### `src/crypto/tls/conn_test.go`
動的レコードサイジングの動作を検証するためのテストケースが追加されました。
`runDynamicRecordSizingTest` 関数は、クライアントとサーバー間でTLS接続を確立し、`recordSizeBoostThreshold` を超える量のデータを送信します。そして、クライアント側で受信したTLSレコードのサイズを監視し、初期段階では小さなレコードが、閾値を超えた後は大きなレコードが送信されていることを確認します。
このテストは、ストリーム暗号、CBCモード、AEAD暗号といった異なる暗号スイートで実行され、TLSオーバーヘッドの計算が正しく行われていることを検証します。

## コアとなるコードの解説

このコミットの核となる変更は、`crypto/tls/conn.go` 内の `writeRecord` 関数が、TLSレコードのペイロードサイズを決定する際に、新たに導入された `maxPayloadSizeForWrite` 関数を使用するようになった点です。

1.  **`Conn.bytesSent` の導入:**
    `Conn` 構造体に `bytesSent` フィールドが追加され、TLS接続を通じてアプリケーション層から送信されたバイト数の合計が追跡されます。これは、動的サイジングのヒューリスティック（1MBの閾値）を適用するための状態変数です。

2.  **`maxPayloadSizeForWrite` のロジック:**
    この関数は、現在の接続の状態（`bytesSent` の値）と設定（`DynamicRecordSizingDisabled`）に基づいて、次に送信するTLSレコードの最適なペイロードサイズを決定します。
    *   **初期フェーズ（`bytesSent < recordSizeBoostThreshold`）:**
        このフェーズでは、レイテンシを優先するため、TLSレコードが単一のTCPセグメントに収まるようにペイロードサイズを制限します。具体的には、`tcpMSSEstimate` (1208バイト) からTLSレコードヘッダー、明示的IV、MAC、AEADタグ、CBCパディングなどのオーバーヘッドを差し引いた値を最大ペイロードサイズとします。これにより、TCPレベルでのフラグメンテーションを避け、受信側での復号化開始を早めます。
    *   **ブーストフェーズ（`bytesSent >= recordSizeBoostThreshold`）:**
        `bytesSent` が1MBの閾値を超えると、接続は大量データ転送モードに入ったと見なされ、スループットを優先します。この場合、`maxPlaintext` (約16KB) が最大ペイロードサイズとして返され、TLSのオーバーヘッドを償却し、効率的なデータ転送を促進します。
    *   **無効化オプション:**
        `Config.DynamicRecordSizingDisabled` が `true` の場合、この動的サイジングは適用されず、常に `maxPlaintext` が使用されます。

3.  **`writeRecord` での適用:**
    `writeRecord` 関数は、アプリケーションデータをTLSレコードに分割して送信する主要な関数です。この関数内で、`data` バッファからレコードに書き込むバイト数 `m` を決定する際に、従来の固定 `maxPlaintext` ではなく、`c.maxPayloadSizeForWrite` の結果が使用されるようになりました。これにより、動的なレコードサイズ調整が実際に適用されます。レコードが送信されるたびに `c.bytesSent` がインクリメントされ、次のレコードのサイズ決定に影響を与えます。

この変更により、Goの `crypto/tls` を利用するアプリケーション（`net/http` や `http2` など）は、特にモバイル環境や低帯域幅のネットワークにおいて、初期の応答性が向上し、その後の大量データ転送では効率性を維持できるようになります。

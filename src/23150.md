## 変更の背景

Go言語のガベージコレクション（GC）は、プログラムの実行と並行して動作するコンカレントGCを採用しています。このようなGCモデルでは、GCがオブジェクトグラフを走査している間に、アプリケーションがポインタを書き換える可能性があります。このポインタの変更をGCに正確に通知し、GCが誤って到達可能なオブジェクトを回収してしまうことを防ぐために、「ライトバリア（Write Barrier）」というメカニズムが導入されています。

ライトバリアは、ポインタの書き込みが発生するたびに実行される小さなコードスニペットです。Goコンパイラは、ポインタの代入が行われる箇所にこのライトバリアコードを挿入します。従来のGoコンパイラでは、このライトバリアの挿入は比較的高レベルの抽象構文木（AST）変換フェーズで行われていました。

しかし、コンパイラの最適化、特に「インライン化（Inlining）」をより効果的に行うためには、ライトバリアの生成をより低レベル、つまりコード生成に近いフェーズで制御する必要がありました。インライン化は、関数呼び出しのオーバーヘッドを削減し、より積極的な最適化を可能にする重要な手法です。ライトバリアのロジックがインライン化されることで、そのオーバーヘッドをさらに削減し、全体的なパフォーマンスを向上させることが期待されます。

このコミットは、そのインライン化の準備として、ライトバリアの生成をよりきめ細かく、かつ効率的に行えるようにするための基盤を構築することを目的としています。

## 前提知識の解説

### ガベージコレクション (Garbage Collection, GC)

Go言語は自動メモリ管理を採用しており、開発者が手動でメモリを解放する必要はありません。この自動メモリ管理を担うのがガベージコレクタです。GoのGCは、主に以下の特徴を持ちます。

*   **コンカレントGC**: アプリケーションの実行と並行してGCが動作します。これにより、GCによるアプリケーションの一時停止（Stop-The-World, STW）時間を最小限に抑え、低レイテンシを実現します。
*   **トライカラーマーク＆スイープ (Tri-color Mark-and-Sweep)**: オブジェクトを白、灰、黒の3色に分類してマークするアルゴリズムです。
    *   **白**: まだGCによって訪問されていないオブジェクト。最終的に回収される可能性がある。
    *   **灰**: GCによって訪問されたが、その参照先がまだ訪問されていないオブジェクト。
    *   **黒**: GCによって訪問され、その参照先もすべて訪問されたオブジェクト。回収されない。

### ライトバリア (Write Barrier)

コンカレントGCにおいて、GCがオブジェクトグラフを走査している最中にアプリケーションがポインタを書き換えると、GCがオブジェクトの到達可能性を誤って判断し、まだ使われているオブジェクトを回収してしまう（誤回収）可能性があります。これを防ぐために導入されるのがライトバリアです。

Goのライトバリアは、ポインタの書き込み（例: `dst = src` のような代入）が行われる際に、GCにその変更を通知する役割を担います。具体的には、`dst` が指していた古いオブジェクトと、`src` が指す新しいオブジェクトの両方について、GCが正しく追跡できるように情報を記録します。これにより、GCは常に正確なオブジェクトグラフを把握し、誤回収を防ぎます。

Goのライトバリアは、主に以下の2種類があります。

*   **Dijkstraのライトバリア**: ポインタの書き込み時に、古いポインタが指していたオブジェクトを灰色にマークします。Go 1.5以前で採用されていました。
*   **Yuasaのライトバリア (Hybrid Write Barrier)**: ポインタの書き込み時に、新しいポインタが指すオブジェクトを灰色にマークします。Go 1.8以降で採用されています。このコミットの時点では、まだDijkstraのライトバリアが主流でしたが、将来的な変更を見越した基盤整備の一部とも考えられます。

ライトバリアは、GCの正確性を保証するために不可欠ですが、その実行にはオーバーヘッドが伴います。このオーバーヘッドをいかに削減するかが、GCのパフォーマンスを向上させる上での重要な課題となります。

### インライン化 (Inlining)

インライン化は、コンパイラ最適化の一種で、関数呼び出しをその関数の本体で直接置き換える手法です。これにより、関数呼び出しに伴う以下のオーバーヘッドを削減できます。

*   スタックフレームのセットアップと破棄
*   引数の渡しと戻り値の受け取り
*   ジャンプ命令による分岐予測の失敗

インライン化は、特に小さな関数や頻繁に呼び出される関数において、顕著なパフォーマンス改善をもたらします。ライトバリアのロジックも、多くの場合、非常に小さく頻繁に実行されるため、これを効率的にインライン化することは、GCのオーバーヘッド削減に直結します。

### Goコンパイラの構造 (`cmd/internal/gc`)

Goコンパイラは、複数のステージを経てソースコードを実行可能なバイナリに変換します。`cmd/internal/gc` は、Goコンパイラのフロントエンドとバックエンドの一部を担うパッケージです。

*   **AST (Abstract Syntax Tree)**: ソースコードを解析して生成される、プログラムの構造を木構造で表現したものです。
*   **SSA (Static Single Assignment)**: ASTから変換される中間表現で、各変数が一度だけ代入される形式です。これにより、データフロー解析や最適化が容易になります。
*   **コード生成**: SSAからターゲットアーキテクチャの機械語コードを生成するフェーズです。

このコミットは、ライトバリアの生成をASTレベルから、よりコード生成に近い低レベルのフェーズに移動させることで、よりきめ細かな制御と最適化の機会を増やそうとしています。

## 技術的詳細

このコミットの核心は、Goコンパイラがライトバリアを挿入するタイミングと方法を変更することにあります。以前は、AST変換の段階でライトバリアの呼び出しが挿入されていましたが、この変更により、コード生成フェーズにより近い場所でライトバリアのロジックが展開されるようになります。

具体的な変更点は以下の通りです。

1.  **`OASWB` オペレーションの導入**:
    *   `syntax.go` に新しいノードタイプ `OASWB` (Assignment with Write Barrier) が追加されました。これは、ライトバリアが必要な代入操作を明示的に示すためのものです。
    *   `walk.go` の `applywritebarrier` 関数で、ポインタ幅の代入（単一ポインタの代入）の場合に、従来のライトバリア関数呼び出しの代わりに、この `OASWB` ノードを生成するように変更されました。これにより、コンパイラの後のフェーズでライトバリアの具体的なコードを生成する責任が移譲されます。

2.  **`Cgen` および関連関数の変更**:
    *   `cgen.go` の主要なコード生成関数 `Cgen` に、ライトバリアの要否を示す `wb` (write barrier) 引数を追加した新しい関数 `cgen_wb` が導入されました。これにより、コード生成時にライトバリアが必要かどうかを明示的に制御できるようになります。
    *   `Cgen` は `cgen_wb` を呼び出すラッパーとなり、デフォルトで `wb` を `false` に設定します。
    *   `Cgen_as` (代入のコード生成) も同様に `Cgen_as_wb` を呼び出すように変更され、ライトバリアの要否を伝播できるようになりました。

3.  **ライトバリア専用のコード生成関数**:
    *   `cgen.go` に `cgen_wbptr` と `cgen_wbfat` という新しい関数が追加されました。
        *   `cgen_wbptr`: 単一のポインタに対するライトバリアを生成します。これは、ポインタの代入時にGCに通知するための最小限の処理を行います。
        *   `cgen_wbfat`: 構造体や配列など、複数のポインタを含む可能性のある「fat」なデータ構造に対するライトバリアを生成します。これは、`typedmemmove` のようなランタイムヘルパー関数を呼び出すことで、型情報に基づいてメモリブロック内のポインタを走査し、それぞれにライトバリアを適用します。
    *   これらの関数は、スタックポインタの調整やレジスタの管理など、より低レベルなアセンブリコード生成に近い処理を行います。

4.  **`sgen_wb` の導入**:
    *   `cgen.go` の `sgen` (ブロックコピーのコード生成) にも `wb` 引数を追加した `sgen_wb` が導入されました。これにより、ブロックコピーにおいてもライトバリアの要否を制御できるようになりました。
    *   特に、スタック上のオブジェクトに対するコピーの場合、ライトバリアは不要になるため、`sgen_wb` 内で `wb = false` に設定する最適化も行われています。

5.  **`Componentgen` の変更**:
    *   `gen.go` の `Componentgen` (構造体や配列の要素ごとのコード生成) にも `wb` 引数を追加した `componentgen_wb` が導入されました。
    *   この関数は、構造体内の個々のポインタフィールドに対してライトバリアを適用する必要がある場合に、`cgen_wbptr` を呼び出すように変更されました。これにより、複合型の代入においても、ポインタの変更がGCに正確に通知されるようになります。

これらの変更により、ライトバリアの生成は、より具体的なコード生成のコンテキストで行われるようになり、将来的なインライン化や、より効率的なアセンブリコードの生成に向けた柔軟性が向上しました。例えば、単一のポインタ代入であれば、ライトバリアのロジックを直接インライン展開し、複雑な構造体の場合はランタイムヘルパーを呼び出すといった、より洗練された戦略が可能になります。

## コアとなるコードの解説

### `src/cmd/internal/gc/cgen.go` の変更点

```go
// 旧: func Cgen(n *Node, res *Node) { ... }
// 新: func Cgen(n, res *Node) { cgen_wb(n, res, false) }
// 新規: func cgen_wb(n, res *Node, wb bool) { ... }
```
`Cgen` は、式 `n` の結果を `res` に生成する汎用的なコード生成関数です。この変更により、`Cgen` は直接ライトバリアを考慮せず、新しく導入された `cgen_wb` にその責任を委譲します。`cgen_wb` は `wb` 引数によってライトバリアが必要かどうかを判断し、必要であれば適切なライトバリアコードを生成します。

```go
// 新規: func cgen_wbptr(n, res *Node) { ... }
// 新規: func cgen_wbfat(n, res *Node) { ... }
```
`cgen_wbptr` は、単一のポインタの代入に対するライトバリアを生成します。これは、GCがポインタの変更を追跡するために必要な最小限の命令を生成します。
`cgen_wbfat` は、構造体や配列など、複数のポインタを含む可能性のあるデータ構造の代入に対するライトバリアを生成します。これは、`typedmemmove` のようなランタイムヘルパー関数を呼び出し、型情報に基づいてメモリブロック内のポインタを走査し、それぞれにライトバリアを適用します。

```go
// 旧: func sgen(n *Node, ns *Node, w int64) { ... }
// 新: func sgen_wb(n *Node, ns *Node, w int64, wb bool) { ... }
```
`sgen` はメモリブロックのコピー（例: 構造体や配列の代入）のコードを生成します。`sgen_wb` は `wb` 引数を受け取り、ブロックコピー中にライトバリアが必要かどうかを判断します。特に、スタック上のオブジェクトへのコピーはGCの対象外であるため、ライトバリアを省略する最適化が行われます。

### `src/cmd/internal/gc/gen.go` の変更点

```go
// 旧: func Cgen_as(nl *Node, nr *Node) { ... }
// 新: func Cgen_as(nl, nr *Node) { Cgen_as_wb(nl, nr, false) }
// 新規: func Cgen_as_wb(nl, nr *Node, wb bool) { ... }
```
`Cgen_as` は代入操作のコードを生成します。`Cgen_as_wb` は `wb` 引数を受け取り、代入の際にライトバリアが必要な場合に `cgen_wb` を呼び出すことで、ライトバリアを適用します。

```go
// 旧: func Componentgen(nr *Node, nl *Node) bool { ... }
// 新: func Componentgen(nr, nl *Node) bool { return componentgen_wb(nr, nl, false) }
// 新規: func componentgen_wb(nr, nl *Node, wb bool) bool { ... }
```
`Componentgen` は、構造体や配列の要素ごとの代入を処理します。`componentgen_wb` は `wb` 引数を受け取り、複合型内の個々のポインタフィールドに対してライトバリアが必要な場合に `cgen_wbptr` を呼び出します。これにより、複合型の代入においても、ポインタの変更がGCに正確に通知されるようになります。

### `src/cmd/internal/gc/walk.go` の変更点

```go
func applywritebarrier(n *Node, init **NodeList) *Node {
    // ...
    if t.Width == int64(Widthptr) {
        n.Op = OASWB // ポインタ幅の代入の場合、OASWBを設定
        return n
    }
    // ...
}
```
`applywritebarrier` は、ASTウォーク中にライトバリアが必要な箇所を特定し、適切なライトバリアコードを挿入する役割を担います。この変更により、単一のポインタの代入（`t.Width == int64(Widthptr)`）の場合、直接ライトバリア関数を呼び出すのではなく、新しい `OASWB` オペレーションを設定するようになりました。これにより、ライトバリアの具体的なコード生成は、より低レベルのフェーズ（`cgen_wb` など）に委ねられることになります。

これらの変更は、Goコンパイラがライトバリアを扱う方法を根本的に変更し、より柔軟で効率的なコード生成を可能にするための重要なステップです。特に、インライン化の文脈で、ライトバリアのオーバーヘッドを最小限に抑えるための基盤を築いています。

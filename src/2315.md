# [インデックス 2315] ファイルの概要

このコミットは、Go言語の初期ランタイムにおける重要な改善を含んでいます。主に、32ビットシステムでのガベージコレクション（GC）のバグ修正と、C言語のランタイム関数（特に`getenv`）がGoの文字列をより容易に扱えるようにするための文字列割り当ての変更に焦点を当てています。これにより、Goランタイムの堅牢性とC言語との相互運用性が向上しました。

## コミット

```
add NUL when allocating strings, to make use
of getenv by low-level runtime easier.
fix 32-bit bug in gc (there are still more).

R=ken
OCL=29415
CL=29415
```

## 変更の背景

このコミットが行われた2009年当時、Go言語はまだ開発の初期段階にあり、ランタイムの安定性と移植性が確立されつつありました。このコミットは、主に以下の2つの課題に対処しています。

1.  **32ビットシステムにおけるGCの課題**: Goの初期のガベージコレクタは「保守的GC」であり、ポインタではないデータが偶然有効なメモリアドレスのように見える「偽のポインタ」の問題を抱えていました。特に32ビットシステムではアドレス空間が小さいため、この問題が発生しやすく、メモリリークや不正確なGCの原因となっていました。このコミットは、GCがメモリブロックをスキャンする際のポインタサイズの扱いに関する32ビット固有のバグを修正しようとしています。
2.  **C言語との相互運用性**: Goランタイムは、システムコールや環境変数の取得など、低レベルの操作のためにC言語のライブラリ関数（例: `getenv`）を呼び出す必要がありました。C言語の文字列は通常、ヌル終端（NUL-terminated）であると期待されますが、Goの内部文字列は長さ情報を持つ構造体であり、必ずしもヌル終端ではありませんでした。この不整合が、`getenv`のようなC関数をGoランタイムから呼び出す際に問題を引き起こす可能性がありました。このコミットは、GoがC関数に渡す文字列にヌル終端を追加することで、この相互運用性の問題を解決しようとしています。

## 前提知識の解説

*   **Goの初期ランタイムと保守的GC**: Goの初期のガベージコレクタは、メモリ上の値をポインタであるかどうか厳密に識別するのではなく、ポインタのように見える値をすべてポインタとして扱う「保守的」なアプローチを採用していました。これは実装を簡素化する一方で、特に32ビットシステムでは、整数などの非ポインタデータが偶然有効なポインタ値と一致する確率が高く、メモリが解放されない（メモリリーク）問題を引き起こす可能性がありました。
*   **32ビットと64ビットアーキテクチャ**:
    *   **32ビットシステム**: メモリアドレスが32ビット（4バイト）で表現されます。これにより、最大4GBのメモリ空間を直接アドレス指定できます。ポインタのサイズも4バイトです。
    *   **64ビットシステム**: メモリアドレスが64ビット（8バイト）で表現されます。これにより、非常に広大なメモリ空間をアドレス指定できます。ポインタのサイズは8バイトです。
    Goのランタイムがメモリをスキャンする際、ポインタのサイズ（`sizeof(void*)`）はアーキテクチャによって異なるため、これを正しく考慮しないと、メモリの読み取りやアライメントが誤り、GCのバグにつながります。
*   **C言語のヌル終端文字列**: C言語では、文字列は文字の配列として表現され、その終端には必ずヌル文字（`\0`、ASCII値0）が置かれます。`strlen`や`strcpy`、`getenv`などの多くのC標準ライブラリ関数は、このヌル文字を文字列の終端を示すマーカーとして利用します。
*   **`getenv`関数**: C標準ライブラリの関数で、環境変数から指定された名前の変数の値を取得するために使用されます。この関数は、ヌル終端された文字列（環境変数名）を引数として受け取り、ヌル終端された文字列（環境変数の値）を返します。
*   **`uintptr`と`sizeof(void*)`**:
    *   `uintptr`: Go言語における整数型で、ポインタを保持するのに十分な大きさを持つ符号なし整数です。ポインタを整数に変換したり、整数をポインタに変換したりする際に使用されますが、これは安全ではない操作であり、GCによって追跡されないため注意が必要です。
    *   `sizeof(void*)`: C言語のコンテキストでは、`void*`型（汎用ポインタ）のサイズをバイト単位で返します。これは、システムが32ビットか64ビットかによって4または8になります。Goランタイムの低レベルコードでは、メモリ操作の際にこのポインタサイズを正確に知る必要があります。

## 技術的詳細

このコミットは、Goランタイムの2つの異なる側面、すなわちガベージコレクションと文字列処理に影響を与えます。

1.  **32ビットGCバグの修正 (`src/runtime/mgc0.c`)**:
    *   GoのGCは、メモリブロックをスキャンしてポインタを探し、到達可能なオブジェクトをマークします。このスキャン処理では、メモリのアライメント（整列）が重要です。
    *   元のコードでは、メモリブロックのオフセット計算やスキャンするバイト数の計算に、ハードコードされた`8`（バイト）という値を使用していました。これは64ビットシステムではポインタサイズと一致するため問題ありませんが、32ビットシステムではポインタサイズが4バイトであるため、誤ったアライメントとスキャンを引き起こしていました。
    *   このコミットでは、`enum { PtrSize = sizeof(void*) };`を導入し、ポインタのサイズを`PtrSize`というシンボルで抽象化しました。これにより、`off = (uint32)(uintptr)b & (PtrSize-1);`のように、オフセット計算やスキャン範囲の計算に`PtrSize`を使用するようになりました。
    *   具体的には、`scanblock`関数内で、メモリブロックの開始アドレス`b`がポインタサイズ（`PtrSize`）の倍数になるように調整し、スキャンするバイト数`n`を`PtrSize`で割ることで、ポインタ単位で正確にメモリをスキャンできるように修正されました。これにより、32ビットシステムでもGCが正しく動作し、偽のポインタによるメモリリークが減少することが期待されます。

2.  **文字列割り当てにおけるヌル終端の追加 (`src/runtime/string.c`)**:
    *   Goの文字列は、内部的には`struct String`のような構造体で表現され、ポインタと長さのペアで構成されます。Goのコード内では、文字列の長さは常にこの構造体から取得されるため、ヌル終端は不要です。
    *   しかし、GoランタイムがC言語の関数（例: `getenv`）を呼び出す場合、C関数はヌル終端された文字列を期待します。Goの文字列をそのままC関数に渡すと、ヌル終端がないためにC関数がメモリの範囲外を読み取ったり、予期せぬ動作を引き起こしたりする可能性がありました。
    *   このコミットでは、`gostringsize`関数（Go文字列のサイズを計算し、メモリを割り当てる関数）において、文字列の長さに加えて1バイト余分にメモリを割り当てるように変更されました (`s.str = mal(l+1);`)。この追加の1バイトは、Cランタイムが利用できるようにヌル文字を配置するためのスペースです。
    *   コメント`// leave room for NUL for C runtime (e.g., callers of getenv)`が追加され、この変更の意図が明確に示されています。これにより、GoランタイムがC関数に文字列を渡す際に、ヌル終端の要件を満たすことができるようになりました。

## コアとなるコードの解説

### `src/runtime/mgc0.c` の変更

*   **`enum { PtrSize = sizeof(void*) };` の追加**:
    *   これは、現在のシステムアーキテクチャにおけるポインタのサイズを`PtrSize`という定数として定義しています。32ビットシステムでは`PtrSize`は4、64ビットシステムでは8になります。
    *   これにより、GCのスキャンロジックがハードコードされた`8`に依存するのではなく、実行環境のポインタサイズに動的に適応できるようになります。

*   **`off = (uint32)(uintptr)b & (PtrSize-1);`**:
    *   元のコードでは`& 7`（つまり`& (8-1)`）を使用していました。これは、`b`のアドレスが8バイト境界からどれだけずれているか（オフセット）を計算していました。
    *   変更後、`& (PtrSize-1)`を使用することで、`b`のアドレスが`PtrSize`の境界からどれだけずれているかを正確に計算します。これにより、32ビットシステム（`PtrSize`が4）でも4バイト境界でのオフセットが正しく計算されます。

*   **`b += PtrSize - off;` と `n -= PtrSize - off;`**:
    *   これらの行は、メモリブロックの開始アドレス`b`を`PtrSize`の倍数にアライメントし、それに合わせてスキャン対象のバイト数`n`を調整します。
    *   元のコードでは`8 - off`を使用していましたが、これも`PtrSize - off`に修正され、32ビットシステムでも正しいアライメント調整が行われるようになりました。

*   **`n /= PtrSize;`**:
    *   元のコードでは`n /= 8;`として、スキャンするメモリブロックのバイト数を8で割ってポインタの数（`void**`の要素数）を計算していました。
    *   変更後、`n /= PtrSize;`とすることで、実際のポインタサイズで割るようになり、32ビットシステムでもポインタの数が正しく計算され、`for`ループが正確な回数だけ実行されるようになります。

これらの変更により、`mgc0.c`内のGCスキャンロジックは、32ビットと64ビットの両方のアーキテクチャでポインタサイズを正しく考慮し、メモリを正確にスキャンできるようになりました。

### `src/runtime/string.c` の変更

*   **`s.str = mal(l+1);`**:
    *   元のコードでは`mal(l)`として、文字列の長さ`l`に正確に一致するバイト数だけメモリを割り当てていました。
    *   変更後、`mal(l+1)`とすることで、文字列の実際の長さに加えて1バイト余分にメモリを割り当てます。この追加の1バイトは、C言語の関数が期待するヌル終端文字（`\0`）を格納するためのスペースです。
    *   この変更により、Goランタイムが内部的に生成した文字列をC言語の関数に渡す際に、C言語の文字列としての要件（ヌル終端）を満たすことが保証され、相互運用性が向上します。

*   **`// leave room for NUL for C runtime (e.g., callers of getenv)`**:
    *   このコメントは、`l+1`の変更の目的を明確に説明しています。特に`getenv`のようなC関数がGoランタイムから呼び出される際に、ヌル終端が必要であることを示唆しています。

# [インデックス 26168] ファイルの概要

このコミットは、Go言語の標準ライブラリである `image/color` パッケージ内の `ycbcr.go` ファイルと `ycbcr_test.go` ファイルに対する変更です。

`image/color` パッケージは、Goプログラムで色を表現し、色空間間で変換するための基本的なインターフェースと実装を提供します。`ycbcr.go` は、YCbCr色空間（輝度Yと2つの色差Cb、Crで色を表現する）に関連する型とメソッドを定義しており、特にYCbCrからRGBへの変換ロジックを含んでいます。

このコミットの主な目的は、`NYCbCrA` 型（非アルファ乗算済みYCbCrとアルファ値を持つ色）の `RGBA()` メソッドが、`YCbCr` 型の `RGBA()` メソッドと同様に16ビットの色深度で動作するように修正することです。これにより、両者の動作の一貫性が保たれ、色の正確な表現が保証されます。

## コミット

`image/color` パッケージにおいて、`NYCbCrA.RGBA` メソッドが16ビットの色深度で動作するように修正されました。この変更により、`NYCbCrA` は `YCbCr` と一貫性のある動作をするようになります。この修正は、Issue #13706 を解決します。

## 変更の背景

このコミットの背景には、Go言語の `image/color` パッケージにおける色表現の一貫性の問題がありました。特に、`YCbCr` 型と `NYCbCrA` 型の `RGBA()` メソッドの動作に差異があったことが指摘されています。

`image/color` パッケージの `Color` インターフェースを実装するすべての型は `RGBA() (r, g, b, a uint32)` メソッドを提供する必要があります。このメソッドは、色をアルファ乗算済みのRGB値として返します。ここで、各成分（赤、緑、青、アルファ）は `uint32` 型で表現され、0から65535（0xFFFF）の範囲にスケーリングされた16ビット値として扱われます。

変更前は、`NYCbCrA.RGBA()` メソッドが `YCbCrToRGB` というヘルパー関数を使用して8ビットのRGB値を計算し、その後で16ビットにスケーリングし、アルファ値を適用していました。しかし、`YCbCr.RGBA()` メソッドは、YCbCrからRGBへの変換を直接16ビット精度で行い、より正確な結果を生成していました。

この差異により、`NYCbCrA` 型の色を `RGBA()` メソッドで取得した場合に、`YCbCr` 型の色と比較して精度が低下したり、期待される色と異なる結果になったりする可能性がありました。コミットメッセージにある「Fixes #13706」は、この不整合やそれによって引き起こされる問題に対処するためのものであったと考えられます。

このコミットは、`NYCbCrA.RGBA()` メソッドの内部実装を `YCbCr.RGBA()` メソッドのロジックと統一することで、この一貫性の問題を解決し、`NYCbCrA` 型の色も正確な16ビットRGB表現で取得できるようにすることを目的としています。

## 前提知識の解説

### 1. 色空間 (Color Space)

*   **YCbCr**: 輝度（Y）と2つの色差（Cb、Cr）で色を表現する色空間です。人間の目は輝度に対してより敏感であるため、画像や動画の圧縮によく用いられます（例: JPEG、MPEG）。Yは画像の明るさ、Cbは青と黄色の差、Crは赤とシアンの差を表します。
*   **RGB**: 赤（Red）、緑（Green）、青（Blue）の3原色の組み合わせで色を表現する色空間です。ディスプレイやカメラなど、多くのデジタルデバイスで広く使われています。

### 2. Goの `image/color` パッケージ

Goの `image/color` パッケージは、色の表現と変換のための基本的なインターフェースと型を提供します。

*   **`Color` インターフェース**: すべての色型が実装すべきインターフェースで、`RGBA() (r, g, b, a uint32)` メソッドを定義しています。このメソッドは、色をアルファ乗算済みの16ビットRGB値として返します。
*   **`RGBA()` メソッド**: `Color` インターフェースの主要なメソッドです。返される `r`, `g`, `b`, `a` はそれぞれ赤、緑、青、アルファの成分を表し、`uint32` 型で0から65535の範囲にスケーリングされた値です。これは、8ビットのカラーコンポーネント（0-255）を16ビット（0-65535）に拡張するために、通常 `0x101` (257) を乗算することで行われます。例えば、8ビット値 `v` は `v * 0x101` となります。これにより、8ビットの最大値255が16ビットの最大値65535に正確にマッピングされます。
*   **`Model` インターフェース**: ある色空間から別の色空間への変換ロジックを定義します。

### 3. 16ビット色表現と `0x101` 乗算

Goの `image/color` パッケージでは、内部的に色成分を16ビット（`uint32` の下位16ビット）で扱います。これは、より広い色域と高い精度を表現するためです。

8ビット値（0-255）を16ビット値（0-65535）に変換する際、単に256を乗算すると、255 * 256 = 65280 となり、16ビットの最大値65535に到達しません。そこで、`0x101` (16進数で257) を乗算することで、8ビットの0が16ビットの0に、8ビットの255が16ビットの65535に正確にマッピングされます。
`v * 0x101 = v * (256 + 1) = v * 256 + v`
例えば、`255 * 257 = 65535` となります。

### 4. アルファブレンドとアルファ乗算済み (Premultiplied Alpha)

*   **アルファ値 (Alpha)**: 色の不透明度を表す成分です。0は完全に透明、255（または65535）は完全に不透明です。
*   **アルファ乗算済み (Premultiplied Alpha)**: 画像処理において、色のRGB成分が既にアルファ値で乗算されている状態を指します。これにより、アルファブレンドの計算が簡素化され、特に複数の半透明なレイヤーを重ねる際に精度が向上し、アーティファクト（縁のギザギザなど）を避けることができます。Goの `image/color` パッケージの `RGBA()` メソッドは、アルファ乗算済みのRGB値を返すことを期待しています。

## 技術的詳細

このコミットの技術的な核心は、`NYCbCrA` 型の `RGBA()` メソッドが、`YCbCr` 型の `RGBA()` メソッドと同じ高精度な16ビット変換ロジックを採用した点にあります。

変更前、`NYCbCrA.RGBA()` は以下のような処理を行っていました。

1.  `YCbCrToRGB(c.Y, c.Cb, c.Cr)` ヘルパー関数を呼び出し、8ビットのRGB値 (`r8, g8, b8`) を取得。
2.  アルファ値 `c.A` を `uint32(c.A) * 0x101` で16ビットにスケーリング。
3.  8ビットRGB値を `uint32(r8) * 0x101` で16ビットにスケーリング。
4.  スケーリングされたRGB値にアルファ値を乗算し、`0xffff` で除算してアルファ乗算済みのRGB値を取得。

このアプローチの問題点は、YCbCrからRGBへの変換が最初に8ビット精度で行われるため、その後の16ビットへのスケーリングやアルファ乗算の際に、既に失われた精度を取り戻せないことでした。特に、YCbCrからRGBへの変換は浮動小数点演算を伴うことが多く、中間結果を8ビットに丸めることで誤差が蓄積されやすくなります。

変更後、`NYCbCrA.RGBA()` は `YCbCr.RGBA()` と同様に、YCbCrからRGBへの変換を直接16ビット精度で行うようになりました。具体的な手順は以下の通りです。

1.  **YCbCr成分の準備**:
    *   `c.Y` (輝度) を `int32(c.Y) * 0x10100` でスケーリングします。これは、8ビットのY値を16ビットに拡張し、さらに内部計算で必要なシフトを考慮したものです。`0x10100` は `0x101 << 8` と等価で、`Y` を `uint16` に変換し、さらに8ビット左シフトすることで、後の乗算でオーバーフローしないようにしつつ、精度を保ちます。
    *   `c.Cb` と `c.Cr` (色差) は、オフセット `128` を引いて符号付きの `int32` に変換されます。これはYCbCrの定義に基づいています。

2.  **YCbCrからRGBへの変換**:
    *   以下の変換式を用いて、RGBの各成分が計算されます。これらの係数 (`91881`, `-22554`, `-46802`, `116130`) は、YCbCrからRGBへの標準的な変換行列に基づいています。
        ```go
        r := (yy1 + 91881*cr1) >> 8
        g := (yy1 - 22554*cb1 - 46802*cr1) >> 8
        b := (yy1 + 116130*cb1) >> 8
        ```
    *   `>> 8` は、計算結果を8ビット右シフトして適切なスケールに戻すためのものです。これにより、結果は16ビットの範囲に収まります。

3.  **クリッピング (Clamping)**:
    *   変換されたRGB値は、0から65535 (`0xffff`) の範囲に収まるようにクリッピングされます。これは、変換式の結果がこの範囲を超える可能性があるため、色の有効な範囲を保証するために重要です。
        ```go
        if r < 0 {
            r = 0
        } else if r > 0xffff {
            r = 0xffff
        }
        // g, b も同様
        ```

4.  **アルファ値の適用**:
    *   `c.A` (アルファ値) を `uint32(c.A) * 0x101` で16ビットにスケーリングします。
    *   最終的なアルファ乗算済みのRGB値は、クリッピングされたRGB値にスケーリングされたアルファ値を乗算し、`0xffff` で除算することで計算されます。
        ```go
        return uint32(r) * a / 0xffff, uint32(g) * a / 0xffff, uint32(b) * a / 0xffff, a
        ```

この変更により、`NYCbCrA.RGBA()` は `YCbCr.RGBA()` と同じ精度でYCbCrからRGBへの変換を行い、より正確で一貫性のある色表現を提供するようになりました。

## コアとなるコードの変更箇所

### `src/image/color/ycbcr.go`

`NYCbCrA` 型の `RGBA()` メソッドの実装が完全に書き換えられました。

**変更前:**

```go
func (c NYCbCrA) RGBA() (r, g, b, a uint32) {
	r8, g8, b8 := YCbCrToRGB(c.Y, c.Cb, c.Cr)
	a = uint32(c.A) * 0x101
	r = uint32(r8) * 0x101 * a / 0xffff
	g = uint32(g8) * 0x101 * a / 0xffff
	b = uint32(b8) * 0x101 * a / 0xffff
	return
}
```

**変更後:**

```go
func (c NYCbCrA) RGBA() (uint32, uint32, uint32, uint32) {
	// The first part of this method is the same as YCbCr.RGBA.
	yy1 := int32(c.Y) * 0x10100 // Convert 0x12 to 0x121200.
	cb1 := int32(c.Cb) - 128
	cr1 := int32(c.Cr) - 128
	r := (yy1 + 91881*cr1) >> 8
	g := (yy1 - 22554*cb1 - 46802*cr1) >> 8
	b := (yy1 + 116130*cb1) >> 8
	if r < 0 {
		r = 0
	} else if r > 0xffff {
		r = 0xffff
	}
	if g < 0 {
		g = 0
	} else if g > 0xffff {
		g = 0xffff
	}
	if b < 0 {
		b = 0
	} else if b > 0xffff {
		b = 0xffff
	}

	// The second part of this method applies the alpha.
	a := uint32(c.A) * 0x101
	return uint32(r) * a / 0xffff, uint32(g) * a / 0xffff, uint32(b) * a / 0xffff, a
}
```

## コアとなるコードの解説

### `NYCbCrA.RGBA()` メソッドの変更

変更後の `NYCbCrA.RGBA()` メソッドは、`YCbCr.RGBA()` メソッドのロジックをほぼそのまま踏襲しています。

1.  **`yy1 := int32(c.Y) * 0x10100`**:
    *   `c.Y` は8ビットの輝度成分です。
    *   `0x10100` は `0x101 << 8` と同じです。`0x101` を乗算することで8ビット値を16ビットスケールに拡張し、さらに8ビット左シフトすることで、後続の乗算 (`91881*cr1` など) で中間結果がオーバーフローしないように、かつ精度を保つための準備をしています。これにより、`yy1` は内部計算で必要な高い精度を持つ値となります。

2.  **`cb1 := int32(c.Cb) - 128` と `cr1 := int32(c.Cr) - 128`**:
    *   `c.Cb` と `c.Cr` は8ビットの色差成分です。
    *   YCbCr色空間の定義では、色差成分は通常、中心値（128）からの偏差として扱われます。そのため、`128` を引くことで、これらの値を符号付きの範囲（-128から127）に変換し、変換式に適した形式にします。

3.  **`r := (yy1 + 91881*cr1) >> 8` など**:
    *   これらはYCbCrからRGBへの変換式です。各係数 (`91881`, `-22554`, `-46802`, `116130`) は、特定のYCbCr色空間（おそらくITU-R BT.601またはBT.709のいずれか）からRGBへの変換行列から導出されたものです。
    *   計算結果を `>> 8` (8ビット右シフト) することで、`yy1` の初期スケーリングを元に戻し、結果を0から65535の16ビット範囲に収めます。

4.  **クリッピング (`if r < 0 ...`)**:
    *   YCbCrからRGBへの変換式は、理論的な色空間全体をカバーするため、計算結果が0未満になったり、65535を超えたりすることがあります。
    *   これらの `if` 文は、計算されたRGB値が有効な16ビットの範囲（0から65535）に収まるように強制する「クリッピング」または「クランプ」処理です。これにより、不正な色値が生成されるのを防ぎます。

5.  **`a := uint32(c.A) * 0x101`**:
    *   `c.A` は8ビットのアルファ成分です。
    *   `0x101` を乗算することで、8ビットのアルファ値を0から65535の16ビットスケールに正確に拡張します。

6.  **`return uint32(r) * a / 0xffff, ...`**:
    *   最終的なRGB値は、クリッピングされた16ビットRGB値 (`r`, `g`, `b`) に、スケーリングされた16ビットアルファ値 (`a`) を乗算し、`0xffff` (65535) で除算することで計算されます。
    *   これは「アルファ乗算済み」のRGB値を生成するための標準的な方法です。`0xffff` で除算することで、アルファ値が0の場合（完全に透明）はRGB値も0になり、アルファ値が `0xffff` の場合（完全に不透明）はRGB値がそのまま維持されます。

### テストコードの追加

*   **`TestNYCbCrAAlpha`**:
    *   このテストは、`NYCbCrA` 型が `Alpha` 型（アルファ値のみを持つ色）と互換性があることを検証します。
    *   `NYCbCrA{YCbCr{0xff, 0x80, 0x80}, uint8(i)}` は、輝度を最大（0xff）、色差を中間（0x80, 0x80、つまり無彩色）に固定し、アルファ値 `i` を変化させた `NYCbCrA` 色を作成します。
    *   `Alpha{uint8(i)}` は、同じアルファ値 `i` を持つ `Alpha` 色を作成します。
    *   `eq(c0, c1)` は、両者の `RGBA()` メソッドの出力が等しいことを検証します。これにより、`NYCbCrA` がアルファ値のみを考慮した場合に `Alpha` と同じように振る舞うことが保証されます。

*   **`TestNYCbCrAYCbCr`**:
    *   このテストは、`NYCbCrA` 型が `YCbCr` 型と互換性があることを検証します。
    *   `NYCbCrA{YCbCr{uint8(i), 0x40, 0xc0}, 0xff}` は、アルファ値を最大（0xff、完全に不透明）に固定し、輝度 `i` と特定の色差を持つ `NYCbCrA` 色を作成します。
    *   `YCbCr{uint8(i), 0x40, 0xc0}` は、同じ輝度と色差を持つ `YCbCr` 色を作成します。
    *   `eq(c0, c1)` は、両者の `RGBA()` メソッドの出力が等しいことを検証します。これにより、`NYCbCrA` が完全に不透明な場合に `YCbCr` と同じように振る舞うことが保証されます。

これらのテストは、`NYCbCrA.RGBA()` メソッドの新しい実装が、他の関連する色型との間で期待される一貫性と正確性を提供することを保証するために重要です。

## 変更の背景

このコミットの背景には、Go言語の `image/color` パッケージにおける色表現の一貫性の問題がありました。特に、`YCbCr` 型と `NYCbCrA` 型の `RGBA()` メソッドの動作に差異があったことが指摘されています。

`image/color` パッケージの `Color` インターフェースを実装するすべての型は `RGBA() (r, g, b, a uint32)` メソッドを提供する必要があります。このメソッドは、色をアルファ乗算済みのRGB値として返します。ここで、各成分（赤、緑、青、アルファ）は `uint32` 型で表現され、0から65535（0xFFFF）の範囲にスケーリングされた16ビット値として扱われます。

変更前は、`NYCbCrA.RGBA()` メソッドが `YCbCrToRGB` というヘルパー関数を使用して8ビットのRGB値を計算し、その後で16ビットにスケーリングし、アルファ値を適用していました。しかし、`YCbCr.RGBA()` メソッドは、YCbCrからRGBへの変換を直接16ビット精度で行い、より正確な結果を生成していました。

このアプローチの問題点は、YCbCrからRGBへの変換が最初に8ビット精度で行われるため、その後の16ビットへのスケーリングやアルファ乗算の際に、既に失われた精度を取り戻せないことでした。特に、YCbCrからRGBへの変換は浮動小数点演算を伴うことが多く、中間結果を8ビットに丸めることで誤差が蓄積されやすくなります。

この差異により、`NYCbCrA` 型の色を `RGBA()` メソッドで取得した場合に、`YCbCr` 型の色と比較して精度が低下したり、期待される色と異なる結果になったりする可能性がありました。コミットメッセージにある「Fixes #13706」は、この不整合やそれによって引き起こされる問題に対処するためのものであったと考えられます。

このコミットは、`NYCbCrA.RGBA()` メソッドの内部実装を `YCbCr.RGBA()` メソッドのロジックと統一することで、この一貫性の問題を解決し、`NYCbCrA` 型の色も正確な16ビットRGB表現で取得できるようにすることを目的としています。

## 前提知識の解説

### 1. 色空間 (Color Space)

*   **YCbCr**: 輝度（Y）と2つの色差（Cb、Cr）で色を表現する色空間です。人間の目は輝度に対してより敏感であるため、画像や動画の圧縮によく用いられます（例: JPEG、MPEG）。Yは画像の明るさ、Cbは青と黄色の差、Crは赤とシアンの差を表します。
*   **RGB**: 赤（Red）、緑（Green）、青（Blue）の3原色の組み合わせで色を表現する色空間です。ディスプレイやカメラなど、多くのデジタルデバイスで広く使われています。

### 2. Goの `image/color` パッケージ

Goの `image/color` パッケージは、色の表現と変換のための基本的なインターフェースと型を提供します。

*   **`Color` インターフェース**: すべての色型が実装すべきインターフェースで、`RGBA() (r, g, b, a uint32)` メソッドを定義しています。このメソッドは、色をアルファ乗算済みの16ビットRGB値として返します。
*   **`RGBA()` メソッド**: `Color` インターフェースの主要なメソッドです。返される `r`, `g`, `b`, `a` はそれぞれ赤、緑、青、アルファの成分を表し、`uint32` 型で0から65535の範囲にスケーリングされた値です。これは、8ビットのカラーコンポーネント（0-255）を16ビット（0-65535）に拡張するために、通常 `0x101` (257) を乗算することで行われます。例えば、8ビット値 `v` は `v * 0x101` となります。これにより、8ビットの最大値255が16ビットの最大値65535に正確にマッピングされます。
*   **`Model` インターフェース**: ある色空間から別の色空間への変換ロジックを定義します。

### 3. 16ビット色表現と `0x101` 乗算

Goの `image/color` パッケージでは、内部的に色成分を16ビット（`uint32` の下位16ビット）で扱います。これは、より広い色域と高い精度を表現するためです。

8ビット値（0-255）を16ビット値（0-65535）に変換する際、単に256を乗算すると、255 * 256 = 65280 となり、16ビットの最大値65535に到達しません。そこで、`0x101` (16進数で257) を乗算することで、8ビットの0が16ビットの0に、8ビットの255が16ビットの65535に正確にマッピングされます。
`v * 0x101 = v * (256 + 1) = v * 256 + v`
例えば、`255 * 257 = 65535` となります。

### 4. アルファブレンドとアルファ乗算済み (Premultiplied Alpha)

*   **アルファ値 (Alpha)**: 色の不透明度を表す成分です。0は完全に透明、255（または65535）は完全に不透明です。
*   **アルファ乗算済み (Premultiplied Alpha)**: 画像処理において、色のRGB成分が既にアルファ値で乗算されている状態を指します。これにより、アルファブレンドの計算が簡素化され、特に複数の半透明なレイヤーを重ねる際に精度が向上し、アーティファクト（縁のギザギザなど）を避けることができます。Goの `image/color` パッケージの `RGBA()` メソッドは、アルファ乗算済みのRGB値を返すことを期待しています。

## 技術的詳細

このコミットの技術的な核心は、`NYCbCrA` 型の `RGBA()` メソッドが、`YCbCr` 型の `RGBA()` メソッドと同じ高精度な16ビット変換ロジックを採用した点にあります。

変更前、`NYCbCrA.RGBA()` は以下のような処理を行っていました。

1.  `YCbCrToRGB(c.Y, c.Cb, c.Cr)` ヘルパー関数を呼び出し、8ビットのRGB値 (`r8, g8, b8`) を取得。
2.  アルファ値 `c.A` を `uint32(c.A) * 0x101` で16ビットにスケーリング。
3.  8ビットRGB値を `uint32(r8) * 0x101` で16ビットにスケーリング。
4.  スケーリングされたRGB値にアルファ値を乗算し、`0xffff` で除算してアルファ乗算済みのRGB値を取得。

このアプローチの問題点は、YCbCrからRGBへの変換が最初に8ビット精度で行われるため、その後の16ビットへのスケーリングやアルファ乗算の際に、既に失われた精度を取り戻せないことでした。特に、YCbCrからRGBへの変換は浮動小数点演算を伴うことが多く、中間結果を8ビットに丸めることで誤差が蓄積されやすくなります。

変更後、`NYCbCrA.RGBA()` は `YCbCr.RGBA()` と同様に、YCbCrからRGBへの変換を直接16ビット精度で行うようになりました。具体的な手順は以下の通りです。

1.  **YCbCr成分の準備**:
    *   `c.Y` (輝度) を `int32(c.Y) * 0x10100` でスケーリングします。これは、8ビットのY値を16ビットに拡張し、さらに内部計算で必要なシフトを考慮したものです。`0x10100` は `0x101 << 8` と等価で、`Y` を `uint16` に変換し、さらに8ビット左シフトすることで、後の乗算でオーバーフローしないようにしつつ、精度を保ちます。
    *   `c.Cb` と `c.Cr` (色差) は、オフセット `128` を引いて符号付きの `int32` に変換されます。これはYCbCrの定義に基づいています。

2.  **YCbCrからRGBへの変換**:
    *   以下の変換式を用いて、RGBの各成分が計算されます。これらの係数 (`91881`, `-22554`, `-46802`, `116130`) は、YCbCrからRGBへの標準的な変換行列に基づいています。
        ```go
        r := (yy1 + 91881*cr1) >> 8
        g := (yy1 - 22554*cb1 - 46802*cr1) >> 8
        b := (yy1 + 116130*cb1) >> 8
        ```
    *   `>> 8` は、計算結果を8ビット右シフトして適切なスケールに戻すためのものです。これにより、結果は16ビットの範囲に収まります。

3.  **クリッピング (Clamping)**:
    *   変換されたRGB値は、0から65535 (`0xffff`) の範囲に収まるようにクリッピングされます。これは、変換式の結果がこの範囲を超える可能性があるため、色の有効な範囲を保証するために重要です。
        ```go
        if r < 0 {
            r = 0
        } else if r > 0xffff {
            r = 0xffff
        }
        // g, b も同様
        ```

4.  **アルファ値の適用**:
    *   `c.A` (アルファ値) を `uint32(c.A) * 0x101` で16ビットにスケーリングします。
    *   最終的なアルファ乗算済みのRGB値は、クリッピングされたRGB値にスケーリングされたアルファ値を乗算し、`0xffff` で除算することで計算されます。
        ```go
        return uint32(r) * a / 0xffff, uint32(g) * a / 0xffff, uint32(b) * a / 0xffff, a
        ```

この変更により、`NYCbCrA.RGBA()` は `YCbCr.RGBA()` と同じ精度でYCbCrからRGBへの変換を行い、より正確で一貫性のある色表現を提供するようになりました。

### `src/image/color/ycbcr.go`

`NYCbCrA` 型の `RGBA()` メソッドの実装が完全に書き換えられました。

**変更前:**

```go
func (c NYCbCrA) RGBA() (r, g, b, a uint32) {
	r8, g8, b8 := YCbCrToRGB(c.Y, c.Cb, c.Cr)
	a = uint32(c.A) * 0x101
	r = uint32(r8) * 0x101 * a / 0xffff
	g = uint32(g8) * 0x101 * a / 0xffff
	b = uint32(b8) * 0x101 * a / 0xffff
	return
}
```

**変更後:**

```go
func (c NYCbCrA) RGBA() (uint32, uint32, uint32, uint32) {
	// The first part of this method is the same as YCbCr.RGBA.
	yy1 := int32(c.Y) * 0x10100 // Convert 0x12 to 0x121200.
	cb1 := int32(c.Cb) - 128
	cr1 := int32(c.Cr) - 128
	r := (yy1 + 91881*cr1) >> 8
	g := (yy1 - 22554*cb1 - 46802*cr1) >> 8
	b := (yy1 + 116130*cb1) >> 8
	if r < 0 {
		r = 0
	} else if r > 0xffff {
		r = 0xffff
	}
	if g < 0 {
		g = 0
	} else if g > 0xffff {
		g = 0xffff
	}
	if b < 0 {
		b = 0
	} else if b > 0xffff {
		b = 0xffff
	}

	// The second part of this method applies the alpha.
	a := uint32(c.A) * 0x101
	return uint32(r) * a / 0xffff, uint32(g) * a / 0xffff, uint32(b) * a / 0xffff, a
}
```

## コアとなるコードの解説

### `NYCbCrA.RGBA()` メソッドの変更

変更後の `NYCbCrA.RGBA()` メソッドは、`YCbCr.RGBA()` メソッドのロジックをほぼそのまま踏襲しています。

1.  **`yy1 := int32(c.Y) * 0x10100`**:
    *   `c.Y` は8ビットの輝度成分です。
    *   `0x10100` は `0x101 << 8` と同じです。`0x101` を乗算することで8ビット値を16ビットスケールに拡張し、さらに8ビット左シフトすることで、後続の乗算 (`91881*cr1` など) で中間結果がオーバーフローしないように、かつ精度を保つための準備をしています。これにより、`yy1` は内部計算で必要な高い精度を持つ値となります。

2.  **`cb1 := int32(c.Cb) - 128` と `cr1 := int32(c.Cr) - 128`**:
    *   `c.Cb` と `c.Cr` は8ビットの色差成分です。
    *   YCbCr色空間の定義では、色差成分は通常、中心値（128）からの偏差として扱われます。そのため、`128` を引くことで、これらの値を符号付きの範囲（-128から127）に変換し、変換式に適した形式にします。

3.  **`r := (yy1 + 91881*cr1) >> 8` など**:
    *   これらはYCbCrからRGBへの変換式です。各係数 (`91881`, `-22554`, `-46802`, `116130`) は、特定のYCbCr色空間（おそらくITU-R BT.601またはBT.709のいずれか）からRGBへの変換行列から導出されたものです。
    *   計算結果を `>> 8` (8ビット右シフト) することで、`yy1` の初期スケーリングを元に戻し、結果を0から65535の16ビット範囲に収めます。

4.  **クリッピング (`if r < 0 ...`)**:
    *   YCbCrからRGBへの変換式は、理論的な色空間全体をカバーするため、計算結果が0未満になったり、65535を超えたりすることがあります。
    *   これらの `if` 文は、計算されたRGB値が有効な16ビットの範囲（0から65535）に収まるように強制する「クリッピング」または「クランプ」処理です。これにより、不正な色値が生成されるのを防ぎます。

5.  **`a := uint32(c.A) * 0x101`**:
    *   `c.A` は8ビットのアルファ成分です。
    *   `0x101` を乗算することで、8ビットのアルファ値を0から65535の16ビットスケールに正確に拡張します。

6.  **`return uint32(r) * a / 0xffff, ...`**:
    *   最終的なRGB値は、クリッピングされた16ビットRGB値 (`r`, `g`, `b`) に、スケーリングされた16ビットアルファ値 (`a`) を乗算し、`0xffff` (65535) で除算することで計算されます。
    *   これは「アルファ乗算済み」のRGB値を生成するための標準的な方法です。`0xffff` で除算することで、アルファ値が0の場合（完全に透明）はRGB値も0になり、アルファ値が `0xffff` の場合（完全に不透明）はRGB値がそのまま維持されます。

### テストコードの追加

*   **`TestNYCbCrAAlpha`**:
    *   このテストは、`NYCbCrA` 型が `Alpha` 型（アルファ値のみを持つ色）と互換性があることを検証します。
    *   `NYCbCrA{YCbCr{0xff, 0x80, 0x80}, uint8(i)}` は、輝度を最大（0xff）、色差を中間（0x80, 0x80、つまり無彩色）に固定し、アルファ値 `i` を変化させた `NYCbCrA` 色を作成します。
    *   `Alpha{uint8(i)}` は、同じアルファ値 `i` を持つ `Alpha` 色を作成します。
    *   `eq(c0, c1)` は、両者の `RGBA()` メソッドの出力が等しいことを検証します。これにより、`NYCbCrA` がアルファ値のみを考慮した場合に `Alpha` と同じように振る舞うことが保証されます。

*   **`TestNYCbCrAYCbCr`**:
    *   このテストは、`NYCbCrA` 型が `YCbCr` 型と互換性があることを検証します。
    *   `NYCbCrA{YCbCr{uint8(i), 0x40, 0xc0}, 0xff}` は、アルファ値を最大（0xff、完全に不透明）に固定し、輝度 `i` と特定の色差を持つ `NYCbCrA` 色を作成します。
    *   `YCbCr{uint8(i), 0x40, 0xc0}` は、同じ輝度と色差を持つ `YCbCr` 色を作成します。
    *   `eq(c0, c1)` は、両者の `RGBA()` メソッドの出力が等しいことを検証します。これにより、`NYCbCrA` が完全に不透明な場合に `YCbCr` と同じように振る舞うことが保証されます。

これらのテストは、`NYCbCrA.RGBA()` メソッドの新しい実装が、他の関連する色型との間で期待される一貫性と正確性を提供することを保証するために重要です。

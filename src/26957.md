# [インデックス 26957] ファイルの概要

このコミットは、Goリンカ（`cmd/link/internal/ld`）が`-B`引数（ビルドIDを指定するオプション）を処理する際に、入力されたビルドIDが短い場合に発生する可能性があったパニック（プログラムのクラッシュ）を修正するものです。具体的には、C言語時代のコードの慣習がGo言語に持ち込まれたことで生じた文字列処理の脆弱性を、Goの標準ライブラリである`strings.HasPrefix`と`encoding/hex`パッケージを使用することで、より安全でGoらしい実装に改善しています。

## 元コミット内容

Goリンカの内部処理において、`-B`引数で指定されるビルドIDが短い場合に発生するパニックを回避する修正。C言語時代の文字列処理の慣習がGoに持ち込まれたことで生じた問題に対し、`strings.HasPrefix`と`encoding/hex`パッケージを用いて、より安全でGoらしい実装に置き換えることで対応。

## 変更の背景

Goリンカ（`cmd/link`）は、Goプログラムをビルドする際の重要なツールです。このリンカは元々C言語で書かれていましたが、Go言語への移行が進められました。C言語では、コマンドライン引数は通常、ヌル終端されたバイト配列として扱われ、文字列の先頭文字などをチェックする際に、`val[0]`のように直接インデックスでアクセスすることが一般的でした。しかし、Go言語の文字列はバイトスライスであり、`val[0]`のようなアクセスは、文字列の長さが期待よりも短い場合に「インデックスが範囲外」というパニックを引き起こす可能性があります。

このコミットで修正された問題は、リンカの`-B`引数（ビルドIDを指定するオプション）の処理において発生しました。ビルドIDは通常`0x`で始まる16進数文字列ですが、ユーザーが誤って短い文字列（例: `""`, `"0"`, `"0x"`）を`-B`引数として渡した場合、リンカ内部の文字列処理がパニックを起こし、プログラムがクラッシュしていました。これは、Goの文字列処理の慣習に合わないC言語的なアプローチが残っていたためです。

このパニックは、Goの安定性と堅牢性を損なうものであり、ユーザーエクスペリエンスを低下させるため、早急な修正が必要でした。

## 前提知識の解説

*   **Go言語の文字列処理**: Go言語の文字列は、読み取り専用のバイトスライスとして実装されています。C言語のヌル終端文字列とは異なり、文字列の長さを常に保持しており、`len(s)`で取得できます。`s[i]`のようにインデックスでアクセスする場合、`i`が`0`から`len(s)-1`の範囲外であるとランタイムパニックが発生します。
*   **`cmd/link`**: Goツールチェーンの一部であるリンカです。コンパイラによって生成されたオブジェクトファイルを結合し、実行可能なバイナリを生成する役割を担います。Goプログラムのビルドプロセスにおいて不可欠なコンポーネントです。
*   **`buildid`**: Goバイナリに埋め込まれる一意の識別子です。通常、ビルド時に生成されるハッシュ値に基づいており、特定のバイナリがどのソースコードから、どのような環境でビルドされたかを追跡するために使用されます。デバッグやプロファイリング、バージョン管理などに役立ちます。形式は`0x`で始まる16進数文字列が一般的です。
*   **`encoding/hex`パッケージ**: Go標準ライブラリのパッケージで、16進数エンコーディングとデコーディングを提供します。`hex.DecodeString`関数は、16進数文字列をバイトスライスに安全に変換し、無効な入力に対しては適切なエラーを返します。手動で16進数変換ロジックを実装するよりも、安全で効率的かつ堅牢です。
*   **`strings.HasPrefix`**: Go標準ライブラリの`strings`パッケージに含まれる関数で、ある文字列が特定のプレフィックスで始まるかどうかを安全にチェックします。文字列の長さを気にすることなく、簡潔にプレフィックスの有無を判断できます。
*   **パニック (panic)**: Goにおけるパニックは、プログラムの実行中に回復不可能なエラーが発生したことを示します。パニックが発生すると、通常のプログラムフローは中断され、スタックトレースが出力されてプログラムが終了します。これは、Goプログラムがクラッシュする一般的な原因の一つです。

## 技術的詳細

このコミットの技術的な核心は、Goリンカの`addbuildinfo`関数における`-B`引数のパース処理の堅牢化にあります。

**修正前の問題点**:
`addbuildinfo`関数は、`-B`引数として渡された文字列`val`を処理していました。
1.  **プレフィックスチェック**: 以前は`val[0] != '0' || val[1] != 'x'`というC言語的なインデックスアクセスで`"0x"`プレフィックスをチェックしていました。しかし、`val`が`""`や`"0"`のように長さが2未満の場合、`val[1]`へのアクセスが範囲外となり、パニックを引き起こしていました。
2.  **手動16進数デコード**: `val`から`"0x"`プレフィックスを除去した後、残りの文字列を手動でループ処理し、各2文字を1バイトの16進数としてデコードしていました。この手動デコードロジックは、以下のような問題がありました。
    *   入力文字列の長さが奇数の場合（例: `"0x1"`）、最後の1文字が処理されずに残るか、あるいはインデックスアクセスでパニックを起こす可能性がありました。
    *   `'0'-'9'`, `'a'-'f'`, `'A'-'F'`以外の文字が含まれていた場合、手動でエラーを検出して`Exitf`を呼び出す必要があり、実装が複雑でエラーの見落としが発生しやすい構造でした。
    *   最大長チェックも手動で行われており、デコード処理と密結合していました。

**修正後の改善点**:
1.  **安全なプレフィックスチェック**: `if val[0] != '0' || val[1] != 'x'`というコードは、`if !strings.HasPrefix(val, "0x")`に置き換えられました。`strings.HasPrefix`は、入力文字列の長さを内部で安全にチェックするため、`val`が短い場合でもパニックを起こすことなく、期待通りに`false`を返します。
2.  **`encoding/hex`パッケージの利用**: 手動で実装されていた複雑な16進数デコードロジックは、Go標準ライブラリの`encoding/hex`パッケージの`hex.DecodeString`関数に完全に置き換えられました。
    *   `b, err := hex.DecodeString(val)`: この一行で、16進数文字列`val`がバイトスライス`b`に安全にデコードされます。
    *   **堅牢なエラーハンドリング**: `hex.DecodeString`は、デコード中に問題が発生した場合にエラーを返します。
        *   `err == hex.ErrLength`: 入力文字列の長さが奇数である場合（16進数は2文字で1バイトを表現するため、偶数である必要があります）に発生します。このエラーを捕捉し、「-B argument must have even number of digits」という適切なエラーメッセージで`Exitf`を呼び出します。
        *   `inv, ok := err.(hex.InvalidByteError)`: 入力文字列に無効な16進数文字（`0-9`, `a-f`, `A-F`以外）が含まれている場合に発生します。このエラーを型アサーションで捕捉し、どの文字が無効であったかを特定して、「-B argument contains invalid hex digit %c」という詳細なエラーメッセージで`Exitf`を呼び出します。
        *   その他のエラーも包括的に処理されます。
3.  **簡潔な最大長チェック**: `buildid`の最大長チェックは、`hex.DecodedLen(len(val))`を使用して、デコード後のバイト長を事前に計算し、`maxLen`と比較することで、より簡潔かつ正確に行われるようになりました。

これらの変更により、`addbuildinfo`関数は、不正な`-B`引数が与えられた場合でもパニックを起こすことなく、ユーザーに対して明確で役立つエラーメッセージを返す、堅牢なコードになりました。

func checkLinkOutput(buildid string, message string) {
	cmd := exec.Command("go", "tool", "link", "-B", buildid)
	out, err := cmd.CombinedOutput()
	if err == nil {
		log.Fatalf("expected cmd/link to fail")
	}

	firstLine := string(bytes.SplitN(out, []byte("\n"), 2)[0])
	if strings.HasPrefix(firstLine, "panic") {
		log.Fatalf("cmd/link panicked:\n%s", out)
	}

	if !strings.Contains(firstLine, message) {
		log.Fatalf("cmd/link output did not include expected message %q: %s", message, firstLine)
	}
}

## コアとなるコードの解説

### `src/cmd/link/internal/ld/elf.go` の `addbuildinfo` 関数

この関数は、Goバイナリに埋め込むビルド情報を処理するために呼び出されます。

1.  **`import "encoding/hex"` の追加**:
    *   `encoding/hex`パッケージをインポートすることで、安全な16進数デコード機能を利用できるようになりました。

2.  **プレフィックスチェックの変更**:
    *   変更前: `if val[0] != '0' || val[1] != 'x'`
        *   これは、`val`の長さが2未満の場合に`val[1]`へのアクセスでパニックを引き起こす可能性がありました。
    *   変更後: `if !strings.HasPrefix(val, "0x")`
        *   `strings.HasPrefix`は、文字列の長さを安全にチェックするため、`val`が短い場合でもパニックを起こしません。これにより、リンカがクラッシュする可能性が排除されました。

3.  **手動16進数デコードの削除と`encoding/hex`の導入**:
    *   変更前は、`for val != ""`ループ内で文字を1つずつ読み取り、手動で16進数から整数に変換していました。このロジックは冗長で、エラーハンドリングも複雑でした。
    *   変更後は、この手動ロジックが完全に削除され、以下のコードに置き換えられました。
        ```go
        b, err := hex.DecodeString(val)
        if err != nil {
            if err == hex.ErrLength {
                Exitf("-B argument must have even number of digits: %s", ov)
            }
            if inv, ok := err.(hex.InvalidByteError); ok {
                Exitf("-B argument contains invalid hex digit %c: %s", byte(inv), ov)
            }
            Exitf("-B argument contains invalid hex: %s", ov)
        }
        buildinfo = b
        ```
        *   `hex.DecodeString(val)`は、`val`（`"0x"`プレフィックスを除去した後の16進数文字列）をバイトスライス`b`にデコードします。
        *   エラーが発生した場合、`if err != nil`ブロックで詳細なエラーハンドリングが行われます。
            *   `hex.ErrLength`: 16進数文字列の長さが奇数である場合に発生。適切なエラーメッセージを出力して終了します。
            *   `hex.InvalidByteError`: 無効な16進数文字が含まれている場合に発生。どの文字が無効であったかを特定し、エラーメッセージに含めて出力します。
            *   その他の`hex`パッケージからのエラーも包括的に処理されます。
        *   デコードが成功した場合、結果のバイトスライス`b`が`buildinfo`変数に割り当てられます。

4.  **最大長チェックの改善**:
    *   `const maxLen = 32`: ビルドIDの最大バイト長（32バイト）を定義。
    *   `if hex.DecodedLen(len(val)) > maxLen`: `hex.DecodedLen`は、指定された16進数文字列の長さから、デコード後のバイトスライスの長さを計算します。これにより、デコード前にビルドIDが最大長を超えていないかを安全かつ効率的にチェックできます。

これらの変更により、`addbuildinfo`関数は、不正な入力に対してもパニックを起こさず、明確なエラーメッセージを返す、より堅牢でGoらしい実装になりました。

### `test/fixedbugs/issue14636.go` のテストコード

このファイルは、`addbuildinfo`関数の修正が正しく機能することを検証するための新しいテストケースです。

1.  **`checkLinkOutput` 関数**:
    *   このヘルパー関数は、特定の`buildid`引数で`go tool link`コマンドを実行し、その出力とエラーを検証します。
    *   `cmd := exec.Command("go", "tool", "link", "-B", buildid)`: `os/exec`パッケージを使用して、Goリンカを子プロセスとして実行します。`-B`オプションにテスト対象の`buildid`を渡します。
    *   `if err == nil { log.Fatalf("expected cmd/link to fail") }`: リンカがエラーを返すことを期待しており、エラーがなければテストを失敗させます。
    *   `if strings.HasPrefix(firstLine, "panic") { log.Fatalf("cmd/link panicked:\\n%s", out) }`: **最も重要なチェック**。リンカがパニックを起こしていないことを確認します。もしパニックが発生していれば、テストは失敗します。
    *   `if !strings.Contains(firstLine, message) { ... }`: リンカの出力の最初の行に、期待されるエラーメッセージが含まれていることを確認します。

2.  **`main` 関数内のテストケース**:
    *   `checkLinkOutput("", "-B argument must start with 0x")`: 空文字列の`buildid`が渡された場合、プレフィックスエラーを期待。
    *   `checkLinkOutput("0", "-B argument must start with 0x")`: `"0"`が渡された場合、プレフィックスエラーを期待。
    *   `checkLinkOutput("0x", "usage")`: `"0x"`のみが渡された場合、デコードする16進数がないため、リンカの一般的な使用法エラー（または関連するエラー）を期待。
    *   `checkLinkOutput("0x0", "-B argument must have even number of digits")`: 奇数長の16進数文字列が渡された場合、長さエラーを期待。
    *   `checkLinkOutput("0x00", "usage")`: 有効な短い16進数文字列の場合、リンカの一般的な使用法エラーを期待。
    *   `checkLinkOutput("0xYZ", "-B argument contains invalid hex digit")`: 無効な16進数文字が含まれる場合、無効な文字エラーを期待。
    *   `checkLinkOutput("0x"+strings.Repeat("00", 32), "usage")`: 最大長（32バイト）の有効な16進数文字列の場合、リンカの一般的な使用法エラーを期待。
    *   `checkLinkOutput("0x"+strings.Repeat("00", 33), "-B option too long (max 32 digits)")`: 最大長を超える16進数文字列の場合、長すぎるエラーを期待。

これらのテストケースは、`addbuildinfo`関数が様々な不正な入力に対して、パニックを起こさずに適切なエラーメッセージを返すことを網羅的に検証しています。

# [インデックス 28241] ファイルの概要

このコミットは、Goの `net/http` パッケージにおいて、HTTPリダイレクト処理中に `Response.Request` フィールドが常に設定されているという誤った仮定を修正するものです。特に、カスタムの `RoundTripper` が `Response.Request` フィールドをnilのまま返す可能性がある場合に発生するパニック（nilポインタ参照）を防ぐための変更が加えられました。これにより、`net/http` クライアントのリダイレクト処理の堅牢性が向上しました。

## 変更の背景

この変更は、Goの `net/http` パッケージにおけるクライアントのリダイレクト処理に関するバグ（Issue 15577）を修正するために導入されました。問題は、`net/http` クライアントがHTTPリダイレクトを処理する際に、`Response` オブジェクトの `Request` フィールドが常に設定されていると誤って仮定していた点にありました。

具体的には、`Client` の `doFollowingRedirects` メソッド内で、リダイレクトエラーが発生した際に `resp.Request.URL.String()` を参照しようとする箇所がありました。しかし、カスタムの `RoundTripper` 実装によっては、返される `Response` オブジェクトの `Request` フィールドが `nil` のままである可能性がありました。このような状況で `resp.Request` が `nil` のままアクセスされると、nilポインタ参照が発生し、プログラムがクラッシュするという問題がありました。

このコミットは、`Response.Request` が `nil` である可能性を考慮し、安全にアクセスするためのチェックを追加することで、このクラッシュを防ぐことを目的としています。

## 前提知識の解説

*   **`net/http` パッケージ**: Go言語でHTTPクライアントおよびサーバーを実装するための標準ライブラリです。
*   **`http.Client`**: HTTPリクエストを送信し、レスポンスを受信するクライアントを表す構造体です。リダイレクト処理、クッキー管理、タイムアウト設定などの機能を提供します。
*   **`http.Request`**: HTTPリクエストを表す構造体です。メソッド、URL、ヘッダー、ボディなどの情報を含みます。
*   **`http.Response`**: HTTPレスポンスを表す構造体です。ステータスコード、ヘッダー、ボディ、そして**元のリクエスト (`Request` フィールド)** などの情報を含みます。`Response.Request` フィールドは、このレスポンスを生成したリクエストへのポインタを保持します。
*   **`http.RoundTripper` インターフェース**: HTTPトランザクション（リクエストの送信とレスポンスの受信）を実行するためのインターフェースです。`Client` は内部的に `RoundTripper` を使用してリクエストを送信します。カスタムの `RoundTripper` を実装することで、リクエストの送信方法をカスタマイズできます（例: プロキシの使用、認証ヘッダーの追加、モックレスポンスの生成など）。
*   **`Client.CheckRedirect` 関数**: `Client` のフィールドの一つで、リダイレクトを処理するかどうかを決定するカスタム関数を設定できます。この関数がエラーを返すと、リダイレクトは停止し、そのエラーが返されます。
*   **リダイレクト処理**: HTTPクライアントがリダイレクトレスポンス（例: 301, 302, 303, 307, 308ステータスコード）を受け取った際に、自動的に新しいURLへリクエストを再送信する一連の処理です。

## 技術的詳細

`net/http` パッケージの `Client` は、`doFollowingRedirects` という内部メソッドでリダイレクト処理を管理しています。このメソッドは、一連のリダイレクトを追跡し、最終的なレスポンスを返します。

問題が発生したのは、`doFollowingRedirects` メソッド内で、リダイレクトがエラーによって中断された場合（例えば、`CheckRedirect` 関数がエラーを返した場合）に、エラーメッセージの一部として元のリクエストのURLを構築しようとするロジックでした。

```go
// 変更前のコードの関連部分
if resp != nil {
    urlStr = resp.Request.URL.String() // ここでresp.Requestがnilだとパニック
} else {
    urlStr = req.URL.String()
}
```

ここで、`resp` は `nil` ではないが、`resp.Request` が `nil` であるというエッジケースが存在しました。これは、特にカスタムの `RoundTripper` が `Response` を生成する際に、`Request` フィールドを適切に設定しない場合に発生し得ます。`RoundTripper` の実装によっては、`Response` オブジェクトを返すだけで、その `Request` フィールドを元の `Request` に紐付けない場合があります。

このコミットでは、この潜在的なnilポインタ参照を防ぐために、`resp.Request` が `nil` でないことを明示的にチェックする条件が追加されました。

## コアとなるコードの解説

### `src/net/http/client.go` の変更

変更の中心は、`doFollowingRedirects` 関数内の `urlStr` を決定する条件文です。

*   **変更前**: `if resp != nil`
*   **変更後**: `if resp != nil && resp.Request != nil`

この変更により、`resp`（HTTPレスポンス）が `nil` でないことに加えて、`resp.Request`（レスポンスに関連付けられたリクエスト）も `nil` でないことを確認するようになりました。これにより、カスタム `RoundTripper` が `Response.Request` フィールドを意図的に、または誤って設定しなかった場合でも、`resp.Request.URL.String()` へのアクセスが安全に行われるようになり、nilポインタ参照によるパニックが回避されます。

### `src/net/http/client_test.go` の変更

このコミットには、修正が正しく機能することを検証するための新しいテストケース `TestClientRedirectResponseWithoutRequest` が追加されています。

1.  **`issue15577Tripper` 構造体**:
    *   これは `http.RoundTripper` インターフェースを実装するカスタムの `RoundTripper` です。
    *   `RoundTrip` メソッドは、ステータスコード `303 See Other` と `Location` ヘッダーを持つ `Response` を返します。
    *   **重要な点**: この `Response` オブジェクトは、`Request` フィールドを意図的に設定していません（`resp.Request` は `nil` のままです）。これは、問題の根本原因となるシナリオをシミュレートするためです。

2.  **`TestClientRedirectResponseWithoutRequest` 関数**:
    *   このテストでは、`http.Client` のインスタンスを作成します。
    *   `CheckRedirect` フィールドには、常にエラーを返す関数を設定しています。これにより、クライアントはリダイレクトを追跡せず、最初のリダイレクトレスポンスで処理を停止します。
    *   `Transport` フィールドには、上記で定義した `issue15577Tripper` のインスタンスを設定します。
    *   `c.Get("http://dummy.tld")` を呼び出してHTTPリクエストを実行します。
    *   このテストの目的は、この `c.Get` の呼び出しがクラッシュしないことを確認することです。もし修正が適用されていなければ、`issue15577Tripper` が返す `Response` の `Request` フィールドが `nil` であるため、`doFollowingRedirects` 内でパニックが発生するはずです。テストがパニックせずに完了すれば、修正が成功していることを示します。

このテストケースは、特定のバグシナリオを正確に再現し、修正がそのシナリオにおいて堅牢であることを保証する、非常に効果的な単体テストの例です。

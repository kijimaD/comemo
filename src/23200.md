## 変更の背景

Go言語のネットワークプログラミングにおいて、タイムアウトやデッドラインは非常に重要な概念です。これらは、ネットワーク操作が無限にブロックされるのを防ぎ、アプリケーションの応答性や堅牢性を保証するために使用されます。しかし、これらの機能に関連するテストは、実行環境のわずかな変動（スケジューリング、ネットワークの遅延、OSの挙動など）によって、時折失敗する「flaky test」（不安定なテスト）となる傾向があります。

このコミットの主な背景には、以下の問題意識があったと考えられます。

1.  **テストの不安定性（Flakiness）の解消**: 継続的インテグレーション（CI）システムにおいて、不安定なテストは開発者の生産性を著しく低下させます。テストがランダムに失敗すると、実際のバグなのか、テスト自体の問題なのかを判断するのに時間がかかり、修正のサイクルが遅延します。特にタイムアウトやデッドラインは時間的な要素が絡むため、テストが不安定になりやすい領域です。
2.  **リソースリークの修正**: ネットワーク接続やゴルーチンといったリソースがテスト終了後に適切にクリーンアップされないと、ソケットリークやゴルーチンリークが発生します。これはテスト実行環境のリソースを枯渇させ、後続のテストに影響を与えたり、テスト全体の信頼性を損なったりする可能性があります。このコミットは、これらのリークを特定し、修正することを目指しています。
3.  **テストカバレッジの向上**: Go 1リリース以降、`net` パッケージには新しい機能や改善が加えられてきました。これらの新機能が適切にテストされていることを保証するため、不足しているテストケースを追加する必要がありました。これにより、将来的な回帰バグを防ぎ、コードベースの品質を維持します。

これらの問題に対処することで、Goの `net` パッケージの信頼性を高め、開発者が安心してネットワークアプリケーションを構築できる基盤を強化することが、この変更の背景にあります。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびネットワークプログラミングに関する前提知識が必要です。

### 1. Go言語の `net` パッケージ

`net` パッケージは、Go言語におけるネットワークI/Oの主要なインターフェースを提供します。TCP/IP、UDP、Unixドメインソケットなど、様々なネットワークプロトコルを扱うための型（`Conn`, `Listener`, `PacketConn` など）や関数が含まれています。

### 2. タイムアウト (Timeout)

ネットワーク操作におけるタイムアウトは、特定の操作（接続の確立、データの読み書きなど）が指定された時間内に完了しない場合に、その操作を中断しエラーを返すメカニズムです。これにより、アプリケーションが応答しないピアやネットワークの問題によって無限にブロックされるのを防ぎます。
Goの `net` パッケージでは、`Dialer` の `Timeout` フィールドや、`Conn` インターフェースの `SetReadDeadline`、`SetWriteDeadline`、`SetDeadline` メソッドを通じてタイムアウトを設定できます。

### 3. デッドライン (Deadline)

デッドラインは、タイムアウトと似ていますが、特定の操作ではなく、接続全体に対する絶対的な期限を設定します。`SetDeadline(t time.Time)` メソッドは、それ以降のすべての読み書き操作が `t` 時刻までに完了しなければならないことを示します。`SetReadDeadline` や `SetWriteDeadline` は、それぞれ読み込みと書き込みに特化したデッドラインを設定します。デッドラインが過ぎると、関連する操作は `os.ErrDeadlineExceeded` (または `net.Error` インターフェースの `Timeout()` メソッドが `true` を返すエラー) を返します。

### 4. `net.Error` インターフェース

Goの `net` パッケージで発生するネットワーク関連のエラーは、多くの場合 `net.Error` インターフェースを実装しています。このインターフェースは、エラーが一時的なものか (`Temporary() bool`)、タイムアウトによるものか (`Timeout() bool`) を判断するためのメソッドを提供します。これにより、エラーハンドリングのロジックをより柔軟に記述できます。

### 5. ソケットリーク (Socket Leak)

ソケットリークは、プログラムがネットワークソケットをオープンした後、適切にクローズせずに終了したり、参照を失ったりすることで発生します。これにより、OSが管理するソケットリソースが解放されず、利用可能なソケット数が枯渇し、新しい接続を確立できなくなる可能性があります。テスト環境では、テストケースが多数実行されるため、小さなリークでも累積すると大きな問題になります。

### 6. ゴルーチンリーク (Goroutine Leak)

ゴルーチンリークは、開始されたゴルーチンが、そのライフサイクルが終了するはずの時点で終了せず、実行され続ける状態を指します。これは、チャネルからの読み込みを待機し続ける、無限ループに入る、またはパニックによってクリーンアップされずに残るなど、様々な原因で発生します。ゴルーチンリークもまた、メモリやCPUリソースを消費し続け、アプリケーションやテストのパフォーマンスに悪影響を与えたり、最終的にはシステムリソースを枯渇させたりする可能性があります。

### 7. Flaky Test (不安定なテスト)

Flaky Testとは、コードの変更がないにもかかわらず、実行するたびに成功したり失敗したりするテストのことです。並行処理のタイミング問題、外部リソースへの依存、環境の不安定性、または不適切なタイムアウト設定などが原因で発生します。Flaky TestはCI/CDパイプラインの信頼性を損ない、開発者がテスト結果を信用できなくなるため、非常に厄介な問題です。

## 技術的詳細

このコミットは、主に `src/net/timeout_test.go` ファイルに大幅な変更を加えており、既存のテストの再構築と新しいテストケースの追加によって、タイムアウトおよびデッドラインテストの堅牢性を向上させています。

具体的な技術的変更点は以下の通りです。

1.  **テスト構造の改善**:
    *   以前は個別のテスト関数内で直接行われていたタイムアウトテストの設定が、`dialTimeoutTests` や `acceptTimeoutTests` といった構造体スライスにまとめられました。これにより、複数のシナリオを簡潔に定義し、ループで実行できるようになり、テストの可読性と保守性が向上しています。
    *   `timeoutReceiver`、`timeoutTransmitter`、`timeoutPacketReceiver` といったヘルパー関数が `src/net/mockserver_test.go` に追加され、タイムアウト時の読み書き操作の挙動をより正確にシミュレートし、テスト結果を検証できるようになりました。これらの関数は、指定された時間内に操作がタイムアウトするかどうか、およびその時間的な精度を検証します。

2.  **タイムアウト/デッドラインの厳密な検証**:
    *   `time.Now().Add(-5 * time.Second)` のように、過去のデッドラインを設定するテストケースが追加されています。これにより、デッドラインが既に過ぎている場合の挙動（即座にタイムアウトエラーが返されること）が正しく処理されることを保証します。
    *   `time.NewTimer` を使用して、テストが予期された時間内に完了するかどうかを厳密にチェックするメカニズムが導入されています。これにより、テストが無限にブロックされたり、予期せず長時間実行されたりするのを防ぎ、不安定性の原因を取り除きます。
    *   `min` と `max` の `time.Duration` を用いて、タイムアウトが設定された時間範囲内に収まることを検証するロジックが追加されています。これは、タイムアウトの精度を保証し、OSのスケジューリングやネットワークの変動によるテストの不安定性を軽減します。

3.  **リソースリークの修正と防止**:
    *   `defer c.Close()` や `defer ln.Close()` の使用が徹底され、テスト終了時にネットワーク接続やリスナーが確実にクローズされるように修正されています。これにより、ソケットリークが防止されます。
    *   ゴルーチンがテスト終了後に適切に終了するように、チャネルや `sync.WaitGroup` を用いた同期メカニズムが強化されています。例えば、`TestAcceptTimeoutMustReturn` や `TestReadTimeoutMustNotReturn` などでは、テストゴルーチンが終了するまでメインゴルーチンが待機するようになっています。これにより、ゴルーチンリークを防ぎ、テスト間の干渉を排除します。

4.  **プラットフォーム固有のエラーハンドリングの改善**:
    *   `src/net/error_plan9_test.go` と `src/net/error_posix_test.go` において、`errTimedout` 変数が追加され、プラットフォーム固有のタイムアウトエラーをより明確に扱うようになっています。これにより、異なるOS環境でのテストの互換性と正確性が向上します。

5.  **既存のテストの整理と削除**:
    *   `src/net/error_test.go` から `isTimeoutError` や `isTemporaryError` といったヘルパー関数が削除され、直接 `net.Error` インターフェースのメソッドを呼び出すように変更されています。これは、コードの簡素化と、Goのインターフェースの利用を促進するものです。
    *   冗長なテストや、新しいテスト構造でカバーされるようになった古いテストが削除または統合されています。例えば、`TestReadDeadlineDataAvailable` や `TestWriteDeadlineBufferAvailable` といった個別のテストは、より汎用的なテストケースに吸収されています。

これらの変更により、Goの `net` パッケージのタイムアウトおよびデッドライン機能のテストがより堅牢になり、CI環境での信頼性が向上し、将来的な開発におけるバグの混入リスクが低減されています。

これらの変更は、Goのネットワークテストスイートの信頼性と網羅性を大幅に向上させるものです。

## コアとなるコードの解説

### `src/net/timeout_test.go` の変更点

このファイルは、Goの `net` パッケージにおけるタイムアウトとデッドラインのテストの中心です。変更の大部分は、テストの構造化と、より厳密な時間的検証にあります。

**データ駆動型テストの導入**:
以前は、各テストケースが個別の関数として記述されていましたが、このコミットでは `dialTimeoutTests`, `acceptTimeoutTests` などの構造体スライスが導入されました。

```go
var dialTimeoutTests = []struct {
	timeout time.Duration
	delta   time.Duration // for deadline
	guard time.Duration
	max   time.Duration
}{
	// Tests that dial timeouts, deadlines in the past work.
	{-5 * time.Second, 0, -5 * time.Second, 100 * time.Millisecond},
	{0, -5 * time.Second, -5 * time.Second, 100 * time.Millisecond},
	// ...
}

func TestDialTimeout(t *testing.T) {
	origTestHookDialChannel := testHookDialChannel
	defer func() { testHookDialChannel = origTestHookDialChannel }()
	defer sw.Set(socktest.FilterConnect, nil)

	for i, tt := range dialTimeoutTests {
		// ... テストロジック ...
		max := time.NewTimer(tt.max)
		defer max.Stop()
		ch := make(chan error)
		go func() {
			// ... Dial処理 ...
			ch <- err
		}()

		select {
		case <-max.C:
			t.Fatalf("#%d: Dial didn't return in an expected time", i)
		case err := <-ch:
			// ... エラー検証 ...
			if nerr, ok := err.(Error); !ok || !nerr.Timeout() {
				t.Fatalf("#%d: %v", i, err)
			}
		}
	}
}
```
このパターンにより、様々なタイムアウト値やデッドライン設定を簡単に試すことができ、テストの網羅性が向上します。特に、`max` タイマーを使った `select` ステートメントは、テストが予期せずハングアップするのを防ぎ、テストの不安定性を軽減します。

**過去のデッドラインのテスト**:
`-5 * time.Second` のように、現在時刻より前のデッドラインを設定するテストが追加されました。これは、デッドラインが既に過ぎている場合に、操作が即座にタイムアウトエラーを返すことを保証するために重要です。

**リソースリーク対策の強化**:
`defer c.Close()` や `defer ln.Close()` がより多くの場所で使われるようになり、テスト終了時にソケットが確実に閉じられるようになりました。また、ゴルーチンが適切に終了するのを待つために、チャネルや `sync.WaitGroup` が活用されています。

```go
func TestAcceptTimeoutMustReturn(t *testing.T) {
	// ...
	max := time.NewTimer(time.Second)
	defer max.Stop()
	ch := make(chan error)
	go func() {
		// ... Accept処理 ...
		ch <- err
	}()

	select {
	case <-max.C:
		ln.Close()
		<-ch // wait for tester goroutine to stop
		t.Fatal("Accept didn't return in an expected time")
	case err := <-ch:
		// ... エラー検証 ...
	}
}
```
このパターンは、テスト対象のゴルーチンが完了するのを待つことで、ゴルーチンリークを防ぎ、テストの独立性を保ちます。

### `src/net/mockserver_test.go` の変更点

このファイルには、ネットワーク操作のモックやヘルパー関数が定義されています。このコミットでは、タイムアウトテストをより正確に行うための新しいヘルパー関数が追加されました。

```go
func timeoutReceiver(c Conn, d, min, max time.Duration, ch chan<- error) {
	var err error
	defer func() { ch <- err }()

	t0 := time.Now()
	if err = c.SetReadDeadline(time.Now().Add(d)); err != nil {
		return
	}
	b := make([]byte, 256)
	var n int
	n, err = c.Read(b)
	t1 := time.Now()
	if n != 0 || err == nil || !err.(Error).Timeout() {
		err = fmt.Errorf("Read did not return (0, timeout): (%d, %v)", n, err)
		return
	}
	if dt := t1.Sub(t0); min > dt || dt > max && !testing.Short() {
		err = fmt.Errorf("Read took %s; expected %s", dt, d)
		return
	}
}
```
`timeoutReceiver` は、指定されたデッドライン `d` が設定された接続 `c` から読み込みを試みます。重要なのは、読み込みが `0` バイトでタイムアウトエラーを返すこと、そしてタイムアウトまでの時間が `min` と `max` の範囲内に収まることを検証している点です。これにより、タイムアウトの挙動が期待通りであることを厳密にテストできます。`timeoutTransmitter` や `timeoutPacketReceiver` も同様のロジックで書き込みやパケット読み込みのタイムアウトを検証します。

### `src/net/error_test.go` の変更点

このファイルでは、エラーハンドリングに関するテストが行われています。
`isTimeoutError` や `isTemporaryError` といったヘルパー関数が削除され、`net.Error` インターフェースのメソッドを直接使用するようになりました。

```go
// 変更前:
// if !isTimeoutError(err) && !isTemporaryError(err) { ... }

// 変更後:
if nerr, ok := err.(Error); !ok || (!nerr.Timeout() && !nerr.Temporary()) {
	return
}
```
これは、Goのインターフェースのポリモーフィズムをより直接的に活用する、よりGoらしい（idiomatic）コードへの改善です。これにより、コードの冗長性が減り、意図がより明確になります。

これらの変更は、Goのネットワークスタックの堅牢性を保証するために不可欠な、テストインフラストラクチャの重要な改善を示しています。

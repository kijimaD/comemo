# [インデックス 26630] ファイルの概要

このコミットは、Go言語のブートストラップツールである `cmd/dist` が、ビルドタグ `//+build` の記述形式を `go/build` パッケージと同様に、スペースなしの形式 (`//+build` の直後にタグが続く形式) も受け入れるように修正するものです。これにより、`cmd/dist` のビルドタグパーサーと `go/build` パッケージのパーサーとの間の不整合が解消され、Goツールチェイン自身のビルドプロセスにおける混乱やエラーが回避されます。また、`matchtag` 関数に `gc` タグが追加されています。

## 変更の背景

この変更の背景には、Go言語のビルドシステムにおける二つの異なるビルドタグパーサーの挙動の不整合がありました。

1.  **`go/build` パッケージの挙動**: Goの標準ビルドパッケージである `go/build` は、ソースファイルの先頭に記述されるビルドタグ `//+build` を解析する際に、`//+build` の直後にスペースがなくても正しくタグを認識し、条件付きコンパイルを適用できました。例えば `//+buildtag` のような形式です。

2.  **`cmd/dist` の挙動**: `cmd/dist` はGoツールチェイン自体をビルドするためのブートストラップツールです。このツールは、Goの古いバージョンでも動作する必要があるため、`go/build` パッケージに依存せず、独自の簡略化されたビルドタグパーサーを持っています。この独自のパーサーは、`//+build` の直後にスペースがない形式を正しく処理できず、ビルドエラーを引き起こす可能性がありました。

コミットメッセージにあるように、作者がスペースなしの `//+build` 形式を含むコードを標準ツリーにコピーした際、`go test` (これは `go/build` を使用) では問題なく動作したにもかかわらず、`make.bash` (これは `cmd/dist` を使用してGoツールチェインをビルドする) が失敗するという状況に遭遇しました。この不整合が混乱を招き、Goツールチェインのビルドプロセスを妨げる原因となったため、`cmd/dist` のパーサーも `go/build` と同様にスペースなしの形式を許容するように修正する必要が生じました。

## 前提知識の解説

### `cmd/dist`

`cmd/dist` は、Go言語のツールチェイン（コンパイラ、リンカ、標準ライブラリなど）をゼロからビルドするためのブートストラップツールです。Go言語は自己ホスト型（self-hosted）であり、Goコンパイラ自体がGo言語で書かれています。そのため、新しいバージョンのGoをビルドするには、まず既存のGoコンパイラ（または古いバージョンのGoコンパイラ）を使って新しいGoコンパイラをビルドする必要があります。この初期ビルドプロセスを「ブートストラップ」と呼び、`cmd/dist` がその役割を担います。

`cmd/dist` は、Goの古いバージョンでも動作する必要があるため、Goの最新の機能や標準ライブラリ（特に `go/build` パッケージのようなビルドシステム関連のパッケージ）に直接依存することはできません。そのため、ビルドタグの解析など、一部の機能については独自の簡略化された実装を持っています。

### `go/build` パッケージ

`go/build` パッケージは、Go言語のソースコードを解析し、ビルド可能なパッケージを特定するための標準ライブラリです。`go build` や `go test` といったコマンドは、このパッケージを利用してソースファイルをスキャンし、ビルドタグやパッケージ宣言などを解釈します。このパッケージは、Goのビルドシステムの中核をなすものであり、Goのソースコードがどのように構成され、どのファイルがビルドに含まれるべきかを決定します。

### `//+build` ディレクティブとビルドタグ

`//+build` ディレクティブは、Goのソースファイルの先頭に記述される特殊なコメントで、条件付きコンパイルを制御するために使用されます。これにより、特定の環境（オペレーティングシステム、アーキテクチャ、Goのバージョンなど）でのみコンパイルされるコードブロックを指定できます。

例:
```go
// +build linux,amd64

package main

// ... このコードはLinuxかつAMD64アーキテクチャでのみコンパイルされる
```

ビルドタグは、`//+build` の後に続く識別子です。複数のタグをカンマで区切って指定したり、スペースで区切って複数の `//+build` 行を記述したりできます。

*   **`goos`**: ターゲットのオペレーティングシステム（例: `linux`, `windows`, `darwin`）。
*   **`goarch`**: ターゲットのアーキテクチャ（例: `amd64`, `arm`, `arm64`）。
*   **`cmd_go_bootstrap`**: `cmd/go` コマンドがブートストラップモードでビルドされている場合に有効になるタグ。
*   **`go1.1`**: Go 1.1 以降のバージョンでビルドされる場合に有効になるタグ。
*   **`android`**: `goos` が `android` の場合に有効になるタグ。
*   **`linux`**: `goos` が `linux` の場合に有効になるタグ。
*   **`gc`**: このコミットで追加されたタグ。Goコンパイラ（`gc` は "Go Compiler" の略称）でビルドされる場合に有効になることを示唆しています。これは、Goの公式コンパイラと他のコンパイラ（例: `gccgo`）を区別するために使用されることがあります。

これらのタグは、特定のプラットフォームやビルド条件に特化したコードを記述する際に非常に重要です。

## 技術的詳細

このコミットの技術的詳細は、主に `src/cmd/dist/build.go` ファイル内の `shouldbuild` 関数と `matchtag` 関数の変更に集約されます。

### `shouldbuild` 関数の変更点

`shouldbuild` 関数は、特定のGoソースファイルをビルドに含めるべきかどうかを判断する役割を担っています。この関数は、ファイルの各行を読み込み、特に `//+build` ディレクティブや `package` 宣言を解析します。

変更前は、`//+build` ディレクティブを解析する際に、`strings.Contains(p, "+build")` で `+build` 文字列の存在を確認した後、`splitfields(p)` で行全体をスペースで分割し、`fields[1] != "+build"` という条件で `+build` が2番目のフィールドにあることを期待していました。これは、`// +build` のように `//` と `+build` の間にスペースがある形式を前提としていました。

変更後は、`p[2:]` (つまり `//` の後の部分) を `splitfields` に渡し、`fields[0] != "+build"` という条件で `+build` が最初のフィールドにあることを期待するように修正されました。これにより、`//+build` のように `//` の直後に `+build` が続く形式も正しく解析できるようになりました。

また、`package documentation` と `package main` のチェックも改善されました。以前は `strings.Contains` を使用していましたが、これはコメント内の文字列も検出してしまう可能性がありました。変更後は、行からコメント部分を削除し、`code == "package documentation"` や `code == "package main"` のように厳密な比較を行うことで、より正確な判定が可能になりました。

### `matchtag` 関数の変更点

`matchtag` 関数は、与えられたビルドタグが現在のビルド環境に一致するかどうかを判断します。この関数は、`goos` (オペレーティングシステム) や `goarch` (アーキテクチャ) などの環境変数と比較してタグの有効性をチェックします。

このコミットでは、`matchtag` 関数に `gc` タグが追加されました。具体的には、`return tag == "gc" || tag == goos || ...` のように、`gc` タグが現在のビルド環境に一致する場合も `true` を返すようになりました。これは、Goコンパイラ（`gc`）でビルドされている場合に特定のコードを有効にするための条件付きコンパイルをサポートするためです。

### `splitfields` 関数

`splitfields` 関数は、文字列をスペースで分割し、空のフィールドを除外して文字列のスライスを返すヘルパー関数です。このコミットでは、`shouldbuild` 関数内でこの関数の呼び出し方が変更され、`//` の部分を除外した文字列を渡すことで、ビルドタグの解析が正しく行われるようになりました。

#### `package documentation` および `package main` のチェックの改善

この部分では、`package documentation` および `package main` の文字列チェックがより堅牢になりました。
1.  `code := p`: 現在の行 `p` を `code` 変数にコピーします。
2.  `i := strings.Index(code, "//")`: 行内に `//` (コメント開始) があるかを探します。
3.  `if i > 0 { code = strings.TrimSpace(code[:i]) }`: `//` が見つかった場合、その手前までの部分を抽出し、前後の空白を削除します。これにより、コメント部分が取り除かれ、純粋なコード部分のみが残ります。

1.  `fields := splitfields(p[2:])`: 以前は行全体 `p` を `splitfields` に渡していましたが、修正後は `p[2:]` を渡します。これは、行頭の `//` をスキップし、`+build` から始まる文字列を `splitfields` に渡すことを意味します。
2.  `if len(fields) < 1 || fields[0] != "+build"`: `splitfields(p[2:])` の結果、`+build` が最初のフィールド (`fields[0]`) にあることを期待します。以前は `fields[1]` をチェックしていましたが、これは `// +build` の形式を想定していました。この変更により、`//+build` の直後にタグが続く形式でも `+build` が正しく認識されます。

### `cmd/dist`

`cmd/dist` は、Go言語のツールチェイン（コンパイラ、リンカ、標準ライブラリなど）をゼロからビルドするためのブートストラップツールです。Go言語は自己ホスト型（self-hosted）であり、Goコンパイラ自体がGo言語で書かれています。そのため、新しいバージョンのGoをビルドするには、まず既存のGoコンパイラ（または古いバージョンのGoコンパイラ）を使って新しいGoコンパイラをビルドする必要があります。この初期ビルドプロセスを「ブートストラップ」と呼び、`cmd/dist` がその役割を担います。

`cmd/dist` は、Goの古いバージョンでも動作する必要があるため、Goの最新の機能や標準ライブラリ（特に `go/build` パッケージのようなビルドシステム関連のパッケージ）に直接依存することはできません。そのため、ビルドタグの解析など、一部の機能については独自の簡略化された実装を持っています。

### `go/build` パッケージ

`go/build` パッケージは、Go言語のソースコードを解析し、ビルド可能なパッケージを特定するための標準ライブラリです。`go build` や `go test` といったコマンドは、このパッケージを利用してソースファイルをスキャンし、ビルドタグやパッケージ宣言などを解釈します。このパッケージは、Goのビルドシステムの中核をなすものであり、Goのソースコードがどのように構成され、どのファイルがビルドに含まれるべきかを決定します。

### `//+build` ディレクティブとビルドタグ

`//+build` ディレクティブは、Goのソースファイルの先頭に記述される特殊なコメントで、条件付きコンパイルを制御するために使用されます。これにより、特定の環境（オペレーティングシステム、アーキテクチャ、Goのバージョンなど）でのみコンパイルされるコードブロックを指定できます。

例:
```go
// +build linux,amd64

package main

// ... このコードはLinuxかつAMD64アーキテクチャでのみコンパイルされる
```

ビルドタグは、`//+build` の後に続く識別子です。複数のタグをカンマで区切って指定したり、スペースで区切って複数の `//+build` 行を記述したりできます。

*   **`goos`**: ターゲットのオペレーティングシステム（例: `linux`, `windows`, `darwin`）。
*   **`goarch`**: ターゲットのアーキテクチャ（例: `amd64`, `arm`, `arm64`）。
*   **`cmd_go_bootstrap`**: `cmd/go` コマンドがブートストラップモードでビルドされている場合に有効になるタグ。
*   **`go1.1`**: Go 1.1 以降のバージョンでビルドされる場合に有効になるタグ。
*   **`android`**: `goos` が `android` の場合に有効になるタグ。
*   **`linux`**: `goos` が `linux` の場合に有効になるタグ。
*   **`gc`**: このコミットで追加されたタグ。Goコンパイラ（`gc` は "Go Compiler" の略称）でビルドされる場合に有効になることを示唆しています。これは、Goの公式コンパイラと他のコンパイラ（例: `gccgo`）を区別するために使用されることがあります。

これらのタグは、特定のプラットフォームやビルド条件に特化したコードを記述する際に非常に重要です。

## 技術的詳細

このコミットの技術的詳細は、主に `src/cmd/dist/build.go` ファイル内の `shouldbuild` 関数と `matchtag` 関数の変更に集約されます。

### `shouldbuild` 関数の変更点

`shouldbuild` 関数は、特定のGoソースファイルをビルドに含めるべきかどうかを判断する役割を担っています。この関数は、ファイルの各行を読み込み、特に `//+build` ディレクティブや `package` 宣言を解析します。

変更前は、`//+build` ディレクティブを解析する際に、`strings.Contains(p, "+build")` で `+build` 文字列の存在を確認した後、`splitfields(p)` で行全体をスペースで分割し、`fields[1] != "+build"` という条件で `+build` が2番目のフィールドにあることを期待していました。これは、`// +build` のように `//` と `+build` の間にスペースがある形式を前提としていました。

変更後は、`p[2:]` (つまり `//` の後の部分) を `splitfields` に渡し、`fields[0] != "+build"` という条件で `+build` が最初のフィールドにあることを期待するように修正されました。これにより、`//+build` のように `//` の直後に `+build` が続く形式も正しく解析できるようになりました。

また、`package documentation` と `package main` のチェックも改善されました。以前は `strings.Contains` を使用していましたが、これはコメント内の文字列も検出してしまう可能性がありました。変更後は、行からコメント部分を削除し、`code == "package documentation"` や `code == "package main"` のように厳密な比較を行うことで、より正確な判定が可能になりました。

### `matchtag` 関数の変更点

`matchtag` 関数は、与えられたビルドタグが現在のビルド環境に一致するかどうかを判断します。この関数は、`goos` (オペレーティングシステム) や `goarch` (アーキテクチャ) などの環境変数と比較してタグの有効性をチェックします。

このコミットでは、`matchtag` 関数に `gc` タグが追加されました。具体的には、`return tag == "gc" || tag == goos || ...` のように、`gc` タグが現在のビルド環境に一致する場合も `true` を返すようになりました。これは、Goコンパイラ（`gc`）でビルドされている場合に特定のコードを有効にするための条件付きコンパイルをサポートするためです。

### `splitfields` 関数

`splitfields` 関数は、文字列をスペースで分割し、空のフィールドを除外して文字列のスライスを返すヘルパー関数です。このコミットでは、`shouldbuild` 関数内でこの関数の呼び出し方が変更され、`//` の部分を除外した文字列を渡すことで、ビルドタグの解析が正しく行われるようになりました。

### `shouldbuild` 関数の変更

#### `package documentation` および `package main` のチェックの改善

```go
-		if strings.Contains(p, "package documentation") {
+		code := p
+		i := strings.Index(code, "//")

+			code = strings.TrimSpace(code[:i])
+		}

-		if strings.Contains(p, "package main") && dir != "cmd/go" && dir != "cmd/cgo" {

 			return false
 		}
```
この部分では、`package documentation` および `package main` の文字列チェックがより堅牢になりました。
1.  `code := p`: 現在の行 `p` を `code` 変数にコピーします。
2.  `i := strings.Index(code, "//")`: 行内に `//` (コメント開始) があるかを探します。
3.  `if i > 0 { code = strings.TrimSpace(code[:i]) }`: `//` が見つかった場合、その手前までの部分を抽出し、前後の空白を削除します。これにより、コメント部分が取り除かれ、純粋なコード部分のみが残ります。
4.  `if code == "package documentation"` および `if code == "package main"`: コメントを除去した `code` が厳密に `"package documentation"` または `"package main"` と一致するかをチェックします。以前の `strings.Contains` では、コメント内にこれらの文字列が含まれていても誤って検出してしまう可能性がありましたが、この修正により、実際のパッケージ宣言のみが対象となります。`package documentation` は通常、ビルド対象外となるドキュメント専用のファイルを示し、`package main` は特定のディレクトリ（`cmd/go` や `cmd/cgo` 以外）ではビルド対象外となる実行可能ファイルを意味します。

#### `//+build` ディレクティブの解析ロジックの修正

```go
-		fields := splitfields(p)
-		if len(fields) < 2 || fields[1] != "+build" {
+		fields := splitfields(p[2:])
+		if len(fields) < 1 || fields[0] != "+build" {
 			continue
 		}
-		for _, p := range fields[2:] {
```

この変更は、`//+build` ディレクティブの解析方法を修正し、`//+buildtag` のようにスペースなしでタグが続く形式をサポートします。
1.  `fields := splitfields(p[2:])`: 以前は行全体 `p` を `splitfields` に渡していましたが、修正後は `p[2:]` を渡します。これは、行頭の `//` をスキップし、`+build` から始まる文字列を `splitfields` に渡すことを意味します。
2.  `if len(fields) < 1 || fields[0] != "+build"`: `splitfields(p[2:])` の結果、`+build` が最初のフィールド (`fields[0]`) にあることを期待します。以前は `fields[1]` をチェックしていましたが、これは `// +build` の形式を想定していました。この変更により、`//+build` の直後にタグが続く形式でも `+build` が正しく認識されます。
3.  `for _, p := range fields[1:]`: ビルドタグのイテレーションも変更されました。以前は `fields[2:]` からタグを読み取っていましたが、これは `//` と `+build` の両方が別々のフィールドとして扱われることを前提としていました。修正後は `fields[1:]` からタグを読み取ります。これは、`fields[0]` が `+build` であり、その後に続くフィールドが実際のビルドタグであることを意味します。

# [インデックス 20903] ファイルの概要

このコミットは、Go言語のリンカ（`liblink`）におけるPowerPC 64-bitアーキテクチャ（`power64`）向けの修正と、`default`ブランチで発生した変更を`dev.power64`ブランチに移植したものです。具体的には、`c2go`関連の修正、ラッパー関数の数学的処理の修正、`stackguard`フィールドの移動、`stackguard1`のサポート、正確なスタック（precise stacks）に関する変更が含まれています。また、命令テーブルにおける`AMOVW`の欠落や、符号なし32ビット剰余演算のバグ修正も行われています。

## 変更の背景

このコミットは、Go言語のPowerPC 64-bitアーキテクチャ（`power64`）サポートを改善するために行われました。Go言語の開発では、特定のアーキテクチャ向けのブランチ（この場合は`dev.power64`）で開発が進められることがあります。その間にメインの`default`ブランチで共通のコードベースに対して様々な変更（バグ修正、新機能、最適化など）が加えられます。

このコミットの主な背景は以下の通りです。

1.  **ブランチ間の同期**: `dev.power64`ブランチが`default`ブランチから分岐した後、`default`ブランチでPowerPC 64-bitアーキテクチャに影響を与える可能性のあるプラットフォーム固有の変更がいくつか発生しました。これらの変更を`dev.power64`ブランチに適切に移植し、機能の整合性とバグ修正を確実にする必要がありました。
2.  **PowerPC 64-bit固有のバグ修正**: PowerPC 64-bitアーキテクチャのリンカおよびアセンブラにおいて、特定の命令（`AMOVW`）の欠落や、符号なし32ビット剰余演算の誤りといったバグが存在していました。これらのバグは、Goプログラムのコンパイルや実行に問題を引き起こす可能性があり、修正が求められていました。
3.  **Goランタイムの進化への対応**: `stackguard`フィールドの移動、`stackguard1`のサポート、正確なスタック（precise stacks）といった変更は、Goランタイムのスタック管理やガベージコレクションの改善に関連しています。これらの変更は、Goプログラムのパフォーマンス、安全性、およびデバッグ能力を向上させるために導入されたものであり、`power64`アーキテクチャでも同様にサポートされる必要がありました。

これらの背景から、このコミットは`power64`アーキテクチャにおけるGo言語の安定性と機能性を向上させるための重要なステップであったと言えます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の内部構造とPowerPCアーキテクチャに関する知識が必要です。

1.  **Go言語のリンカ (`liblink`)**:
    *   Go言語のコンパイルプロセスにおいて、`liblink`はアセンブリコードやオブジェクトファイルを結合し、実行可能なバイナリを生成する役割を担います。
    *   各アーキテクチャ（例: `amd64`, `arm`, `power64`など）には、それぞれに対応するリンカのバックエンドが存在し、そのアーキテクチャ固有の命令セットやABI（Application Binary Interface）に合わせたコード生成とリンクを行います。
    *   `src/liblink/asm9.c`と`src/liblink/obj9.c`は、PowerPC 64-bitアーキテクチャ（Goの内部では通常`ppc64`または`power64`として扱われ、ファイル名に`9`が付くことが多い）向けのリンカのコードです。`asm9.c`はアセンブリ命令の定義や処理に関連し、`obj9.c`はオブジェクトファイルの構造やリンキングのロジックに関連します。

2.  **PowerPC 64-bit アーキテクチャ**:
    *   IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャの一つで、サーバーや組み込みシステムなどで広く利用されています。
    *   64ビットの汎用レジスタを持ち、命令セットは他のRISCアーキテクチャと同様に固定長でシンプルな構造をしています。
    *   Go言語のランタイムは、特定のアーキテクチャの特性（レジスタの使い方、メモリ配置、システムコールなど）に合わせて最適化されています。

3.  **`c2go`**:
    *   Go言語の初期の段階で、C言語で書かれたコードをGoに変換するためのツールやプロセスを指すことがあります。Goランタイムの一部はC言語で書かれていたため、Goへの移行を進める上でこのような変換が必要でした。この文脈では、C言語で書かれたランタイムコードをGoに移植する際の互換性や変換に関する修正を指している可能性があります。

4.  **`stackguard` と `stackguard1`**:
    *   Goランタイムにおけるスタック管理の重要な要素です。Goの関数は、必要に応じてスタックを動的に拡張します。
    *   `stackguard`は、現在のスタックポインタがスタックの限界に近づいているかどうかをチェックするための値です。関数呼び出しの際に、スタックオーバーフローを防ぐためにこのチェックが行われます。
    *   `stackguard1`は、Goのスタック管理における別のガード値で、特にCgo（GoとCの相互運用）やシステムコールなど、Goランタイムの外部から呼び出される可能性のあるコードパスでのスタックチェックに関連します。これにより、GoルーチンがCコードを呼び出す際や、その逆の場合にスタックの安全性が確保されます。
    *   `moved stackguard field`は、`g`構造体（goroutineの情報を保持する構造体）内で`stackguard`フィールドのオフセットが変更されたことを示唆しています。これは、構造体のレイアウト変更に伴うものです。

5.  **Precise Stacks (正確なスタック)**:
    *   Goのガベージコレクション（GC）における重要な概念です。GoのGCは、実行中のプログラムが使用しているメモリを正確に特定し、不要になったメモリを解放することで、メモリリークを防ぎます。
    *   「正確なスタック」とは、GCがスタック上のどの値がポインタであり、どの値がポインタでないかを正確に識別できることを意味します。これにより、GCはスタック上のポインタが指すオブジェクトを正確に追跡し、誤って生きているオブジェクトを回収したり、死んでいるオブジェクトを保持し続けたりするのを防ぎます。
    *   正確なスタックの実現には、コンパイラとリンカがスタックフレームのレイアウトに関するメタデータを生成し、GCがそれを利用できるようにする必要があります。

6.  **剰余演算 (`AREM`, `AREMU`, `AREMD`, `AREMDU`)**:
    *   PowerPCアセンブリにおける剰余（remainder）演算命令です。
    *   `AREM`は符号付き整数、`AREMU`は符号なし整数、`AREMD`は倍精度浮動小数点数、`AREMDU`は符号なし倍精度浮動小数点数（または64ビット整数）の剰余演算を指すことが多いです。
    *   このコミットでは、特に「correct unsigned 32-bit remainder」とあるため、符号なし32ビット整数の剰余演算のバグ修正が行われたことが示唆されます。

これらの前提知識は、コミットの変更内容がGoランタイムのどの部分に影響を与え、なぜそれらの変更が必要だったのかを理解する上で不可欠です。

## 技術的詳細

このコミットは、Go言語のPowerPC 64-bitアーキテクチャ向けリンカとアセンブラの複数の側面を修正・改善しています。

### 1. 命令テーブルの修正 (`src/liblink/asm9.c`)

*   **`AMOVW` 命令の追加**:
    *   `asm9.c`の`optab`配列は、GoのアセンブラがPowerPC命令をどのようにエンコードするかを定義する命令テーブルです。
    *   変更前は、`AMOVW`（Move Word、32ビット値を移動する命令）が`C_REG, C_NONE, C_NONE, C_LOREG`というオペランドの組み合わせで欠落していました。これは、レジスタからローカルレジスタ（`REGZERO`）への32ビット移動命令が正しく認識されなかったことを意味します。
    *   このコミットにより、`{ AMOVW, C_REG, C_NONE, C_NONE, C_LOREG, 35, 8, REGZERO }`というエントリが追加され、この特定の`AMOVW`命令がリンカによって正しく処理されるようになりました。これにより、32ビット値の移動に関する潜在的なバグが修正されます。

*   **符号なし剰余演算命令の追加と修正**:
    *   `AREMU`（Unsigned Remainder）と`AREMDU`（Double Unsigned Remainder）のオペランド組み合わせが`optab`に追加されました。これにより、符号なし整数および64ビット整数（または倍精度浮動小数点数）の剰余演算がリンカによって正しく扱われるようになります。
    *   特に、`case 50`と`case 51`の`asmout`関数（アセンブリ命令をバイナリコードに変換する部分）において、`AREMU`命令の処理が修正されています。
        *   `AREMU`の場合、結果の上位32ビットをクリアするための`OP_RLW`命令（Rotate Left Word and then AND with Mask）が追加されています。これは、32ビット符号なし剰余演算の結果が64ビットレジスタに格納される際に、上位ビットにゴミが入るのを防ぐための処理です。これにより、「correct unsigned 32-bit remainder」というコミットメッセージの意図が実現されます。

*   **`ANOP` 命令の移動**:
    *   `ANOP`（No Operation）命令のエントリが`optab`内で移動されました。これは機能的な変更ではなく、コードの整理または関連する命令の近くに配置するためのものです。

*   **型定義の変更**:
    *   `xcmp`配列と`oplook`関数の引数`c1, c3, c4`の型が`char*`から`uchar*`に変更されました。これは、符号なし文字（unsigned character）として扱うことで、文字コードの解釈やポインタ演算における潜在的な問題を回避するための型安全性の向上です。

### 2. オブジェクトファイル処理の修正 (`src/liblink/obj9.c`)

*   **スタック分割 (`addstacksplit`) の改善**:
    *   `addstacksplit`関数は、Goルーチンのスタックが不足した場合にスタックを拡張するためのコード（スタック分割チェック）を生成します。
    *   **`g->panic` 関連の変更**:
        *   以前の`WRAPPER`関数（GoとCの境界を跨ぐ関数など）における`g->panicwrap`の処理が削除され、より複雑な`g->panic`構造体（パニック情報）の`argp`フィールド（引数ポインタ）を調整するロジックが追加されました。
        *   新しいロジックは、`g->panic`が`nil`でなく、かつ`g->panic->argp`が現在のフレームポインタ（`FP`）と一致する場合に、`g->panic->argp`を新しいフレームのボトムに設定します。これは、パニック発生時にスタックフレームが正しく巻き戻されるようにするための重要な修正です。
        *   このロジックは、`AMOVD`（Move Doubleword）、`ACMP`（Compare）、`ABEQ`（Branch if Equal）、`ABNE`（Branch if Not Equal）、`AADD`（Add）といったPowerPC命令を組み合わせて実装されています。特に、`NOP`命令（Goのリンカにおける`ANOP`は0命令バイトにエンコードされる）がジャンプ命令のターゲットとして使用されています。
    *   **`stackguard` フィールドのオフセット変更**:
        *   `stacksplit`関数において、`g_stackguard(g)`（goroutineのスタックガード値）をロードする際のオフセットが変更されました。
        *   以前は`2*ctxt->arch->ptrsize`（`G.stackguard`）でしたが、このコミットでは`G.stackguard0`と`G.stackguard1`を区別してロードするようになりました。
        *   `G.stackguard0`は通常のGo関数用、`G.stackguard1`はCgoなどC関数から呼び出されるGo関数（`cfunc`）用です。これにより、GoとCの相互運用におけるスタックチェックの正確性が向上します。
        *   `runtime.morestackc`への分岐も、`cfunc`の場合にのみ使用されるようになりました。`morestackc`はCgo関連のスタック拡張処理を担当します。

*   **不要なスタックサイズ関連コードの削除**:
    *   `stacksplit`関数から、`$framesize`と`$args`をレジスタにロードする一連の命令が削除されました。これらの命令は、スタック分割のロジックにおいて不要になったか、より効率的な方法で処理されるようになったためと考えられます。

*   **`LinkArch` 構造体の更新**:
    *   `linkpower64`と`linkpower64le`（PowerPC 64-bit Little Endian）の`LinkArch`構造体に`.D_OREG = D_OREG`が追加されました。これは、`D_OREG`（Offset Register）というアドレス指定モードが、リンカのアーキテクチャ定義で明示的にサポートされることを示します。

これらの変更は、PowerPC 64-bitアーキテクチャにおけるGoランタイムの安定性、スタック管理の正確性、ガベージコレクションの効率性、およびCgoとの相互運用性を向上させることを目的としています。特に、スタックガードのロジックの改善と、符号なし剰余演算のバグ修正は、Goプログラムの堅牢性に直接貢献します。

1.  **Go言語のリンカ (`liblink`)**:
    *   Go言語のコンパイルプロセスにおいて、`liblink`はアセンブリコードやオブジェクトファイルを結合し、実行可能なバイナリを生成する役割を担います。
    *   各アーキテクチャ（例: `amd64`, `arm`, `power64`など）には、それぞれに対応するリンカのバックエンドが存在し、そのアーキテクチャ固有の命令セットやABI（Application Binary Interface）に合わせたコード生成とリンクを行います。
    *   `src/liblink/asm9.c`と`src/liblink/obj9.c`は、PowerPC 64-bitアーキテクチャ（Goの内部では通常`ppc64`または`power64`として扱われ、ファイル名に`9`が付くことが多い）向けのリンカのコードです。`asm9.c`はアセンブリ命令の定義や処理に関連し、`obj9.c`はオブジェクトファイルの構造やリンキングのロジックに関連します。

2.  **PowerPC 64-bit アーキテクチャ**:
    *   IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャの一つで、サーバーや組み込みシステムなどで広く利用されています。
    *   64ビットの汎用レジスタを持ち、命令セットは他のRISCアーキテクチャと同様に固定長でシンプルな構造をしています。
    *   Go言語のランタイムは、特定のアーキテクチャの特性（レジスタの使い方、メモリ配置、システムコールなど）に合わせて最適化されています。

3.  **`c2go`**:
    *   Go言語の初期の段階で、C言語で書かれたコードをGoに変換するためのツールやプロセスを指すことがあります。Goランタイムの一部はC言語で書かれていたため、Goへの移行を進める上でこのような変換が必要でした。この文脈では、C言語で書かれたランタイムコードをGoに移植する際の互換性や変換に関する修正を指している可能性があります。

4.  **`stackguard` と `stackguard1`**:
    *   Goランタイムにおけるスタック管理の重要な要素です。Goの関数は、必要に応じてスタックを動的に拡張します。
    *   `stackguard`は、現在のスタックポインタがスタックの限界に近づいているかどうかをチェックするための値です。関数呼び出しの際に、スタックオーバーフローを防ぐためにこのチェックが行われます。
    *   `stackguard1`は、Goのスタック管理における別のガード値で、特にCgo（GoとCの相互運用）やシステムコールなど、Goランタイムの外部から呼び出される可能性のあるコードパスでのスタックチェックに関連します。これにより、GoルーチンがCコードを呼び出す際や、その逆の場合にスタックの安全性が確保されます。
    *   `moved stackguard field`は、`g`構造体（goroutineの情報を保持する構造体）内で`stackguard`フィールドのオフセットが変更されたことを示唆しています。これは、構造体のレイアウト変更に伴うものです。

5.  **Precise Stacks (正確なスタック)**:
    *   Goのガベージコレクション（GC）における重要な概念です。GoのGCは、実行中のプログラムが使用しているメモリを正確に特定し、不要になったメモリを解放することで、メモリリークを防ぎます。
    *   「正確なスタック」とは、GCがスタック上のどの値がポインタであり、どの値がポインタでないかを正確に識別できることを意味します。これにより、GCはスタック上のポインタが指すオブジェクトを正確に追跡し、誤って生きているオブジェクトを回収したり、死んでいるオブジェクトを保持し続けたりするのを防ぎます。
    *   正確なスタックの実現には、コンパイラとリンカがスタックフレームのレイアウトに関するメタデータを生成し、GCがそれを利用できるようにする必要があります。

6.  **剰余演算 (`AREM`, `AREMU`, `AREMD`, `AREMDU`)**:
    *   PowerPCアセンブリにおける剰余（remainder）演算命令です。
    *   `AREM`は符号付き整数、`AREMU`は符号なし整数、`AREMD`は倍精度浮動小数点数、`AREMDU`は符号なし倍精度浮動小数点数（または64ビット整数）の剰余演算を指すことが多いです。
    *   このコミットでは、特に「correct unsigned 32-bit remainder」とあるため、符号なし32ビット整数の剰余演算のバグ修正が行われたことが示唆されます。

これらの前提知識は、コミットの変更内容がGoランタイムのどの部分に影響を与え、なぜそれらの変更が必要だったのかを理解する上で不可欠です。

## 技術的詳細

このコミットは、Go言語のPowerPC 64-bitアーキテクチャ向けリンカとアセンブラの複数の側面を修正・改善しています。

### 1. 命令テーブルの修正 (`src/liblink/asm9.c`)

*   **`AMOVW` 命令の追加**:
    *   `asm9.c`の`optab`配列は、GoのアセンブラがPowerPC命令をどのようにエンコードするかを定義する命令テーブルです。
    *   変更前は、`AMOVW`（Move Word、32ビット値を移動する命令）が`C_REG, C_NONE, C_NONE, C_LOREG`というオペランドの組み合わせで欠落していました。これは、レジスタからローカルレジスタ（`REGZERO`）への32ビット移動命令が正しく認識されなかったことを意味します。
    *   このコミットにより、`{ AMOVW, C_REG, C_NONE, C_NONE, C_LOREG, 35, 8, REGZERO }`というエントリが追加され、この特定の`AMOVW`命令がリンカによって正しく処理されるようになりました。これにより、32ビット値の移動に関する潜在的なバグが修正されます。

*   **符号なし剰余演算命令の追加と修正**:
    *   `AREMU`（Unsigned Remainder）と`AREMDU`（Double Unsigned Remainder）のオペランド組み合わせが`optab`に追加されました。これにより、符号なし整数および64ビット整数（または倍精度浮動小数点数）の剰余演算がリンカによって正しく扱われるようになります。
    *   特に、`case 50`と`case 51`の`asmout`関数（アセンブリ命令をバイナリコードに変換する部分）において、`AREMU`命令の処理が修正されています。
        *   `AREMU`の場合、結果の上位32ビットをクリアするための`OP_RLW`命令（Rotate Left Word and then AND with Mask）が追加されています。これは、32ビット符号なし剰余演算の結果が64ビットレジスタに格納される際に、上位ビットにゴミが入るのを防ぐための処理です。これにより、「correct unsigned 32-bit remainder」というコミットメッセージの意図が実現されます。

*   **`ANOP` 命令の移動**:
    *   `ANOP`（No Operation）命令のエントリが`optab`内で移動されました。これは機能的な変更ではなく、コードの整理または関連する命令の近くに配置するためのものです。

*   **型定義の変更**:
    *   `xcmp`配列と`oplook`関数の引数`c1, c3, c4`の型が`char*`から`uchar*`に変更されました。これは、符号なし文字（unsigned character）として扱うことで、文字コードの解釈やポインタ演算における潜在的な問題を回避するための型安全性の向上です。

### 2. オブジェクトファイル処理の修正 (`src/liblink/obj9.c`)

*   **スタック分割 (`addstacksplit`) の改善**:
    *   `addstacksplit`関数は、Goルーチンのスタックが不足した場合にスタックを拡張するためのコード（スタック分割チェック）を生成します。
    *   **`g->panic` 関連の変更**:
        *   以前の`WRAPPER`関数（GoとCの境界を跨ぐ関数など）における`g->panicwrap`の処理が削除され、より複雑な`g->panic`構造体（パニック情報）の`argp`フィールド（引数ポインタ）を調整するロジックが追加されました。
        *   新しいロジックは、`g->panic`が`nil`でなく、かつ`g->panic->argp`が現在のフレームポインタ（`FP`）と一致する場合に、`g->panic->argp`を新しいフレームのボトムに設定します。これは、パニック発生時にスタックフレームが正しく巻き戻されるようにするための重要な修正です。
        *   このロジックは、`AMOVD`（Move Doubleword）、`ACMP`（Compare）、`ABEQ`（Branch if Equal）、`ABNE`（Branch if Not Equal）、`AADD`（Add）といったPowerPC命令を組み合わせて実装されています。特に、`NOP`命令（Goのリンカにおける`ANOP`は0命令バイトにエンコードされる）がジャンプ命令のターゲットとして使用されています。
    *   **`stackguard` フィールドのオフセット変更**:
        *   `stacksplit`関数において、`g_stackguard(g)`（goroutineのスタックガード値）をロードする際のオフセットが変更されました。
        *   以前は`2*ctxt->arch->ptrsize`（`G.stackguard`）でしたが、このコミットでは`G.stackguard0`と`G.stackguard1`を区別してロードするようになりました。
        *   `G.stackguard0`は通常のGo関数用、`G.stackguard1`はCgoなどC関数から呼び出されるGo関数（`cfunc`）用です。これにより、GoとCの相互運用におけるスタックチェックの正確性が向上します。
        *   `runtime.morestackc`への分岐も、`cfunc`の場合にのみ使用されるようになりました。`morestackc`はCgo関連のスタック拡張処理を担当します。

*   **不要なスタックサイズ関連コードの削除**:
    *   `stacksplit`関数から、`$framesize`と`$args`をレジスタにロードする一連の命令が削除されました。これらの命令は、スタック分割のロジックにおいて不要になったか、より効率的な方法で処理されるようになったためと考えられます。

*   **`LinkArch` 構造体の更新**:
    *   `linkpower64`と`linkpower64le`（PowerPC 64-bit Little Endian）の`LinkArch`構造体に`.D_OREG = D_OREG`が追加されました。これは、`D_OREG`（Offset Register）というアドレス指定モードが、リンカのアーキテクチャ定義で明示的にサポートされることを示します。

これらの変更は、PowerPC 64-bitアーキテクチャにおけるGoランタイムの安定性、スタック管理の正確性、ガベージコレクションの効率性、およびCgoとの相互運用性を向上させることを目的としています。特に、スタックガードのロジックの改善と、符号なし剰余演算のバグ修正は、Goプログラムの堅牢性に直接貢献します。

*   **`addstacksplit`関数内の`WRAPPER`ロジックの変更**:
    *   以前の`g->panicwrap`を直接操作する単純なロジックが削除され、より堅牢なパニック処理ロジックに置き換えられました。
    *   新しいロジックは、`g->panic`が`nil`でないこと、および`g->panic->argp`が現在のフレームポインタ（`FP`）と一致することを確認します。これらの条件が満たされた場合、`g->panic->argp`を新しいスタックフレームのボトムに調整します。
    *   この変更は、Goのパニックとリカバリのメカニズムが、スタックフレームの変更（特にスタック拡張時）によって正しく機能するようにするために不可欠です。`autosize+8`というオフセットは、スタックフレームのサイズと、おそらくリターンアドレスやフレームポインタなどの追加情報のためのスペースを考慮しています。
    *   `NOP`命令がジャンプのターゲットとして使用されているのは、Goのリンカが生成するアセンブリコードにおいて、ジャンプ先を明確にするためのプレースホルダーとして機能するためです。この`NOP`は、PowerPCの実際の`NOP`命令とは異なり、バイナリサイズを増やしません。

*   **`stacksplit`関数内の`stackguard`ロードロジック**:
    *   `g_stackguard(g)`をロードする際に、`G.stackguard0`と`G.stackguard1`という異なるオフセットを使用するようになりました。
    *   `G.stackguard0`は通常のGoルーチン、`G.stackguard1`はCgoを介して呼び出されるGo関数（`cfunc`）のスタックガードです。これにより、Cgoのコンテキストでスタックオーバーフローチェックがより正確に行われるようになります。
    *   `runtime.morestackc`への分岐は、`cfunc`の場合にのみ行われます。`runtime.morestackc`は、Cgo関連のスタック拡張処理を担当するGoランタイム関数です。

*   **不要な命令の削除**:
    *   `stacksplit`関数から、`$framesize`と`$args`をレジスタにロードする命令が削除されました。これは、これらの値がスタック分割のロジックで直接使用されなくなったか、他の方法で取得されるようになったためと考えられます。これにより、生成されるコードの効率が向上します。

*   **`LinkArch`構造体への`D_OREG`追加**:
    *   `D_OREG`は、PowerPCアーキテクチャにおける「オフセット付きレジスタ」というアドレス指定モードを指します。このモードは、ベースレジスタの値にオフセットを加算してメモリアドレスを計算するために使用されます。
    *   `LinkArch`構造体に`D_OREG`が明示的に追加されたことで、リンカがこのアドレス指定モードをPowerPC 64-bitアーキテクチャで正しく利用できるようになります。

これらの変更は、GoランタイムのPowerPC 64-bitサポートを強化し、スタック管理、パニック処理、およびCgoとの相互運用性における正確性と堅牢性を向上させるものです。

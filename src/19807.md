# [インデックス 19807] ファイルの概要

このコミットは、Go言語のリンカである`liblink`におけるARMアーキテクチャ向けのリテラルプール管理の精度向上と、デバッグ出力の修正を目的としています。具体的には、リテラルプールに同じワードが既に存在するかどうかを判断する際の比較ロジックをより正確にし、`Addr`構造体の一部のフィールドが比較に不要であることを明確にしました。また、新しい`liblink`のコンテキストで適切に機能しないデバッグ用の`print`文を削除しています。

## 変更の背景

この変更は、Go言語のリンカである`liblink`がARMアーキテクチャ向けにコードを生成する際に、リテラルプール（定数データを格納する領域）の管理を最適化するために行われました。

ARMアーキテクチャでは、PC（プログラムカウンタ）相対アドレッシングを用いて定数（リテラル）をロードすることが一般的です。このため、コンパイラやリンカは、コードの近くにリテラルプールを配置し、そこから定数を参照するようにします。リテラルプールを効率的に利用するためには、同じ定数が複数回使用される場合に、既にプールに存在する定数を再利用することが重要です。

このコミット以前の`liblink`では、`Addr`構造体全体をコピーしてリテラルプールの比較を行っていました。しかし、`Addr`構造体には、リテラルプールの同一性を判断する上で重要ではないフィールド（例: `node`フィールド）が含まれていました。これらの不要なフィールドも比較対象に含まれることで、実際には同じリテラルであるにもかかわらず、異なるものとして扱われ、リテラルプールの重複が発生する可能性がありました。

コミットメッセージにある「Goバージョンと比較した際にこの問題が浮上した」という記述は、おそらくGoの新しいバージョンや異なるビルド環境でのテスト、あるいはGoのツールチェーンの進化に伴い、`liblink`への`Addr`構造体の渡し方が変更され、一部のフィールドがコピーされなくなったことが原因で、この比較の不正確さが顕在化したことを示唆しています。

また、デバッグ用の`print`文が削除されたのは、新しい`liblink`の内部構造において、`%D`フォーマット指定子が`Prog*`（プログラム命令のコンテキスト）の外で使用されると未定義の動作を引き起こすためです。これは、リンカの内部ロギングメカニズムの変更に伴うクリーンアップと考えられます。

## 前提知識の解説

### Goのリンカ (liblink)

`liblink`は、Go言語のツールチェーンの一部であり、コンパイルされたオブジェクトファイルを結合して実行可能ファイルを生成する役割を担うリンカです。Goのコンパイラは、各ソースファイルをオブジェクトファイルにコンパイルし、`liblink`がこれらのオブジェクトファイルとGoランタイムライブラリをリンクして、最終的なバイナリを生成します。`liblink`は、シンボル解決、アドレスの再配置、そして特定アーキテクチャ向けの最適化（例: リテラルプールの管理）などを行います。

### ARMアーキテクチャとリテラルプール

ARMアーキテクチャは、モバイルデバイスや組み込みシステムで広く使用されているRISC（Reduced Instruction Set Computer）ベースのプロセッサアーキテクチャです。ARMプロセッサは、命令セットの特性上、直接大きな定数を命令に埋め込むことができません。そのため、定数（リテラル）をメモリ上の特定の領域に配置し、PC相対アドレッシング（プログラムカウンタからの相対的なオフセットでメモリにアクセスする方式）を用いてその定数をロードします。この定数データを格納するメモリ領域が「リテラルプール」です。

*   **PC相対アドレッシング**: ARMの`LDR Rd, =const`のような擬似命令は、アセンブラによってPC相対ロード命令に変換されます。この命令は、近くのリテラルプールから定数をフェッチします。
*   **配置**: リテラルプールは通常、コードセクションの終わりに配置されます。また、`LTORG`のようなディレクティブを使用して、明示的にリテラルプールを挿入し、定数がPC相対ロード命令のアドレス可能範囲内にあることを保証できます。
*   **範囲制限**: PCからリテラルプール内の定数へのオフセットには厳密な制限があります（例: 32ビットARM命令の場合、4KB未満）。この制限を超える場合、アセンブラはエラーを生成するため、`LTORG`を戦略的に配置して新しいリテラルプールを作成する必要があります。
*   **実行回避**: リテラルプールは、プロセッサが命令として実行しないようなコードセグメント内の位置に配置される必要があります。通常、無条件分岐命令の後やサブルーチンの終わりに配置されます。

### `Addr`構造体

`liblink`における`Addr`構造体は、リンカの内部表現においてアドレスまたはオペランドを表す基本的なデータ構造です。これは、Goツールチェーンのリンカが派生したPlan 9リンカの内部構造にルーツを持っています。

`Addr`構造体には、アドレスを記述するための様々なフィールドが含まれています。このコミットで言及されている主要なフィールドは以下の通りです。

*   `offset`: `int64`型で、オフセット値を格納します。これは、リテラルプール内のオフセットや、プログラムカウンタからの相対オフセットなど、様々な意味を持ちます。
*   `sym`: `LSym`（リンカシンボル）構造体へのポインタで、アドレスに関連付けられたシンボル（例: 定数のラベル）を表します。
*   `type`: `int`型で、アドレスまたはオペランドのタイプを示します。
*   `name`: アドレスに関連する名前情報。

これらのフィールドは、`liblink`がアドレスを解決し、定数を含むデータを最終的な実行可能ファイルに配置する際に使用されます。特に、ARMのリテラルプールにおいては、`offset`と`sym`フィールドが、定数の位置とそのシンボルとの関連性を指定するために重要となります。

## 技術的詳細

このコミットの主要な技術的変更は、`liblink`がリテラルプールに新しいワードを追加する際に、既存のワードとの比較をより厳密に行うようにした点です。

以前のコードでは、`t.to = *a;`という行で、`Addr`構造体`a`のすべてのフィールドを`t.to`に一括でコピーしていました。`t.to`は、リテラルプールに追加される可能性のあるワードを表すための一時的な`Addr`構造体です。この一括コピーでは、`Addr`構造体に含まれるすべてのフィールド（例: `node`フィールドなど、リテラルプールの同一性判断には関係ないフィールド）もコピーされていました。

コミットメッセージによると、`node`のような一部のフィールドは`liblink`自体によって直接使用されることはありません。しかし、`t.to = *a;`のように構造体全体をコピーすると、これらの無関係なフィールドの値が、`Addr`構造体の比較（リテラルプールに同じワードが既に存在するかどうかを判断するため）に影響を与えてしまう可能性がありました。例えば、`node`フィールドの値が異なるだけで、実際には同じ定数を指しているにもかかわらず、異なるリテラルとして扱われ、リテラルプールに重複して追加されてしまう、といった問題が発生し得ます。

このコミットでは、`t.to = *a;`を以下の個別のフィールドコピーに置き換えました。

```c
t.to.offset = a->offset;
t.to.sym = a->sym;
t.to.type = a->type;
t.to.name = a->name;
```

これにより、リテラルプールの同一性判断に**本当に必要なフィールド**（`offset`, `sym`, `type`, `name`）のみが`t.to`にコピーされるようになります。これにより、`node`のような無関係なフィールドの値が比較に影響を与えることがなくなり、リテラルプールの比較がより「正確」になりました。結果として、リテラルプールの重複が減り、生成されるバイナリのサイズがわずかに削減されたり、リンカの効率が向上したりする可能性があります。

もう一つの変更は、`src/liblink/asm5.c`の`aclass`関数から`print("%D\\n", a);`というデバッグ出力が削除されたことです。コミットメッセージにあるように、`%D`フォーマット指定子は`Prog*`（プログラム命令）のコンテキスト内で使用されることを前提としています。`aclass`関数内では、このコンテキストが利用できないため、`%D`を使用すると未定義の動作やクラッシュを引き起こす可能性がありました。この行は、新しい`liblink`の設計において適切ではないため、削除されました。

## コアとなるコードの解説

### `addpool`関数における変更

`addpool`関数は、ARMアーキテクチャのリテラルプールに新しい定数（ワード）を追加する処理を担当しています。この関数は、与えられたアドレス`a`が既にリテラルプールに存在するかどうかをチェックし、存在しない場合にのみ追加します。

変更前のコード`t.to = *a;`は、`Addr`構造体`a`のビット単位のコピーを行っていました。これは、`Addr`構造体のすべてのフィールド（リテラルプールの同一性判断に不要なフィールドも含む）が`t.to`にコピーされることを意味します。

変更後のコードでは、`t.to.offset = a->offset;`のように、`offset`, `sym`, `type`, `name`といった個別のフィールドを明示的にコピーしています。これらのフィールドは、リテラルが指すメモリ位置、関連するシンボル、およびその型を正確に識別するために不可欠な情報です。`node`のような、リンカの内部処理には関係ないが`Addr`構造体に含まれる可能性のあるフィールドはコピーされなくなりました。これにより、リテラルプールの比較ロジックが、リテラルの本質的な同一性のみに基づいて行われるようになり、誤って異なるリテラルとして扱われるケースが減少しました。

### `aclass`関数における変更

`aclass`関数は、アドレス`a`のクラス（種類）を決定する役割を持つ関数です。この関数内には、デバッグ目的で`print("%D\\n", a);`という行がありました。

`%D`フォーマット指定子は、Goのリンカの内部で、`Prog*`（プログラム命令）のコンテキスト内でアドレスを整形して出力するために設計されています。しかし、`aclass`関数が呼び出されるコンテキストでは、この`Prog*`情報が利用できない場合がありました。このような状況で`%D`を使用すると、リンカがクラッシュしたり、予期せぬ動作を引き起こしたりする可能性がありました。

このコミットでは、この問題のあるデバッグ出力を削除することで、リンカの安定性と堅牢性を向上させています。これは、コードベースのクリーンアップと、新しい`liblink`の設計原則への準拠の一環と考えられます。

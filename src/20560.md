このコミットは、`encoding/gob` パッケージのエンコーディング処理を高速化することを目的としています。具体的には、型情報を管理するための `typeLock` というミューテックスを、`atomic.Value` を使用したコピーオンライト (Copy-On-Write) マップに置き換えることで、並行処理の効率を向上させています。コミットメッセージには、様々なベンチマーク結果が示されており、特に並行度が高いケース (`-32` など) で大幅な性能改善が見られます。

## 変更の背景

`encoding/gob` パッケージは、Go言語のデータ構造をシリアライズ・デシリアライズするためのメカニズムを提供します。このパッケージは、RPC (Remote Procedure Call) や永続化など、様々な場面で利用されます。

`gob` エンコーダは、エンコード対象のGoの型に関する情報を内部的にキャッシュし、再利用することで効率を高めています。この型情報のキャッシュ (`typeInfoMap`) は、複数のゴルーチンから同時にアクセスされる可能性があるため、データ競合を防ぐために排他制御が必要でした。

従来のgobの実装では、この型情報のキャッシュへのアクセスに `sync.Mutex` (`typeLock`) を使用していました。`sync.Mutex` は、排他制御の最も一般的なメカニズムですが、読み取り操作が頻繁に行われ、書き込み操作が比較的少ないシナリオでは、すべての読み取り操作がミューテックスのロック取得・解放を必要とするため、並行性が阻害され、性能ボトルネックとなることがあります。特に、型情報のルックアップはエンコーディング処理において頻繁に発生するため、このロックが性能に大きな影響を与えていました。

このコミットの背景には、`gob` エンコーディングの並行性能を向上させたいという明確な要求がありました。ベンチマーク結果が示すように、特に並行度が高い環境下で `typeLock` がボトルネックとなり、性能がスケールしない問題が顕在化していたと考えられます。

## 前提知識の解説

### 1. `encoding/gob` パッケージ

`encoding/gob` は、Go言語のデータ構造をバイナリ形式でエンコード（シリアライズ）およびデコード（デシリアライズ）するためのパッケージです。自己記述型 (self-describing) のストリーム形式を採用しており、ストリーム内に型情報が含まれるため、受信側は事前に型を知らなくてもデータをデコードできます。これは、RPCシステムなどで特に有用です。

### 2. `sync.Mutex`

`sync.Mutex` は、Go言語で最も基本的な排他制御プリミティブです。`Lock()` メソッドでロックを取得し、`Unlock()` メソッドでロックを解放します。一度に一つのゴルーチンのみがロックを保持でき、他のゴルーチンはロックが解放されるまでブロックされます。読み取りと書き込みの両方で排他制御が必要な場合に広く使用されますが、読み取りが頻繁で書き込みが稀なケースでは、読み取り操作もロックを待つため、並行性が低下する可能性があります。

### 3. `sync/atomic.Value`

`sync/atomic.Value` は、任意の型の値をアトミックに（不可分に）保存およびロードするための型です。`Store()` メソッドで値を保存し、`Load()` メソッドで値をロードします。これらの操作は、CPUの命令レベルでアトミックに実行されるため、ミューテックスのようなロック機構を必要とせず、データ競合なしに安全に値を更新・読み取りできます。これは、特に読み取りが頻繁で書き込みが稀な共有データ構造の更新に適しています。

### 4. コピーオンライト (Copy-On-Write, CoW) パターン

コピーオンライトは、共有されるデータ構造の更新を効率的に行うためのプログラミングパターンです。このパターンでは、データ構造を読み取る際にはロックなしで直接アクセスできます。しかし、データ構造を変更する必要がある場合（書き込み時）には、元のデータ構造のコピーを作成し、そのコピーに対して変更を加えます。変更が完了したら、`atomic.Value` のようなアトミックな操作を用いて、共有されているポインタを新しいコピーに切り替えます。

このパターンの利点は以下の通りです。
*   **読み取りの高速化:** 読み取り操作はロックを必要としないため、非常に高速で並行性が高いです。
*   **書き込みの分離:** 書き込み操作はコピーに対して行われるため、読み取り操作をブロックしません。
*   **スレッドセーフティ:** アトミックなポインタの切り替えにより、データの一貫性が保証されます。

欠点としては、書き込み時にデータ構造全体のコピーが必要になるため、大きなデータ構造の場合にはメモリ使用量とコピーのオーバーヘッドが大きくなる可能性があります。しかし、`gob` の型情報マップのように、読み取りが圧倒的に多く、書き込み（新しい型の登録）が比較的少ないシナリオでは、非常に効果的な最適化手法となります。

## 技術的詳細

このコミットの核心は、`encoding/gob` パッケージ内で型情報をキャッシュしている `typeInfoMap` の管理方法を根本的に変更した点にあります。

**変更前:**
`typeInfoMap` は `map[reflect.Type]*typeInfo` 型で、`typeLock sync.Mutex` によって保護されていました。`getTypeInfo` 関数がこのマップにアクセスするたびに `typeLock.Lock()` と `typeLock.Unlock()` が呼び出され、型情報のルックアップ（読み取り）であっても排他制御が必要でした。これにより、複数のゴルーチンが同時に型情報を要求すると、ミューテックスの競合が発生し、並行処理の性能が低下していました。

**変更後:**
1.  **`typeInfoMap` の変更:**
    `var typeInfoMap = make(map[reflect.Type]*typeInfo)` から `var typeInfoMap atomic.Value` に変更されました。
    `atomic.Value` は、`map[reflect.Type]*typeInfo` のインスタンスを保持します。

2.  **`lookupTypeInfo` 関数の導入:**
    新しい `lookupTypeInfo` 関数が導入され、`typeInfoMap.Load().(map[reflect.Type]*typeInfo)` を使って現在のマップのコピーをアトミックに取得し、ロックなしで型情報をルックアップします。これにより、読み取り操作は非常に高速になり、競合がなくなります。

3.  **`buildTypeInfo` 関数の導入とコピーオンライトの実装:**
    `getTypeInfo` 関数は、まず `lookupTypeInfo` を使って型情報を検索します。もし見つからなければ、`buildTypeInfo` 関数が呼び出されます。
    `buildTypeInfo` 関数は、以下の手順でコピーオンライトを実装します。
    *   まず、`typeLock` (これは `buildTypeInfo` 内でのみ使用される、より粒度の細かいロック) を取得します。これは、複数のゴルーチンが同時に新しい型情報を構築しようとするのを防ぐためです。
    *   再度 `lookupTypeInfo` を呼び出して、他のゴルーチンが既に同じ型情報を構築していないか確認します（ダブルチェックロッキングパターン）。
    *   新しい `map[reflect.Type]*typeInfo` を作成し、`typeInfoMap.Load()` で取得した既存のマップの内容をすべてコピーします。
    *   新しい型情報をこの新しいマップに追加します。
    *   `typeInfoMap.Store(newm)` を使って、`atomic.Value` が保持するマップをアトミックに新しいマップに置き換えます。
    *   `typeLock` を解放します。

4.  **`typeInfo` 構造体の変更:**
    `typeInfo` 構造体内の `encoder *encEngine` フィールドが `encoder atomic.Value` に変更されました。これにより、`encEngine` の構築もコピーオンライトパターンで管理できるようになり、`encInit sync.Mutex` がその構築を保護します。これは、再帰的な型定義のエンコーダ構築を安全かつ効率的に行うためです。

これらの変更により、`gob` エンコーディングの大部分の操作（型情報の読み取り）がロックフリーになり、並行処理の性能が大幅に向上しました。ベンチマーク結果は、特に並行度が高い環境で、最大50%以上の性能改善が見られることを明確に示しています。

### `src/encoding/gob/type.go` の変更点

```go
// typeInfoMap is an atomic pointer to map[reflect.Type]*typeInfo.
// It's updated copy-on-write. Readers just do an atomic load
// to get the current version of the map. Writers make a full copy of
// the map and atomically update the pointer to point to the new map.
// Under heavy read contention, this is significantly faster than a map
// protected by a mutex.
var typeInfoMap atomic.Value

func lookupTypeInfo(rt reflect.Type) *typeInfo {
	m, _ := typeInfoMap.Load().(map[reflect.Type]*typeInfo)
	return m[rt]
}

func getTypeInfo(ut *userTypeInfo) (*typeInfo, error) {
	rt := ut.base
	if ut.externalEnc != 0 {
		rt = ut.user
	}
	if info := lookupTypeInfo(rt); info != nil { // ロックなしで読み取り
		return info, nil
	}
	return buildTypeInfo(ut, rt) // 見つからなければ構築
}

func buildTypeInfo(ut *userTypeInfo, rt reflect.Type) (*typeInfo, error) {
	typeLock.Lock() // 書き込み時のみロック
	defer typeLock.Unlock()

	if info := lookupTypeInfo(rt); info != nil { // ダブルチェックロッキング
		return info, nil
	}

	// ... (型情報の構築ロジック) ...

	// Create new map with old contents plus new entry.
	newm := make(map[reflect.Type]*typeInfo)
	m, _ := typeInfoMap.Load().(map[reflect.Type]*typeInfo)
	for k, v := range m {
		newm[k] = v
	}
	newm[rt] = info
	typeInfoMap.Store(newm) // アトミックにマップを置き換え
	return info, nil
}
```
このコードスニペットは、`typeInfoMap` が `atomic.Value` に変更され、読み取り操作 (`lookupTypeInfo`) がロックフリーになったことを示しています。新しい型情報が必要な場合のみ `buildTypeInfo` が呼び出され、その中で `typeLock` を取得し、既存のマップをコピーして新しいエントリを追加し、`atomic.Value` を介してアトミックにマップを置き換えるコピーオンライトパターンが適用されます。これにより、読み取りの並行性が大幅に向上します。

	// Check for recursive types.

		return nil

		info.encoder.Store(enc) // atomic.Valueにストア

	return enc
}

## 変更の背景

`encoding/gob` パッケージは、Go言語のデータ構造をシリアライズ・デシリアライズするためのメカニズムを提供します。このパッケージは、RPC (Remote Procedure Call) や永続化など、様々な場面で利用されます。

`gob` エンコーダは、エンコード対象のGoの型に関する情報を内部的にキャッシュし、再利用することで効率を高めています。この型情報のキャッシュ (`typeInfoMap`) は、複数のゴルーチンから同時にアクセスされる可能性があるため、データ競合を防ぐために排他制御が必要でした。

従来のgobの実装では、この型情報のキャッシュへのアクセスに `sync.Mutex` (`typeLock`) を使用していました。`sync.Mutex` は、排他制御の最も一般的なメカニズムですが、読み取り操作が頻繁に行われ、書き込み操作が比較的少ないシナリオでは、すべての読み取り操作がミューテックスのロック取得・解放を必要とするため、並行性が阻害され、性能ボトルネックとなることがあります。特に、型情報のルックアップはエンコーディング処理において頻繁に発生するため、このロックが性能に大きな影響を与えていました。

このコミットの背景には、`gob` エンコーディングの並行性能を向上させたいという明確な要求がありました。ベンチマーク結果が示すように、特に並行度が高い環境下で `typeLock` がボトルネックとなり、性能がスケールしない問題が顕在化していたと考えられます。

## 前提知識の解説

### 1. `encoding/gob` パッケージ

`encoding/gob` は、Go言語のデータ構造をバイナリ形式でエンコード（シリアライズ）およびデコード（デシリアライズ）するためのパッケージです。自己記述型 (self-describing) のストリーム形式を採用しており、ストリーム内に型情報が含まれるため、受信側は事前に型を知らなくてもデータをデコードできます。これは、RPCシステムなどで特に有用です。

### 2. `sync.Mutex`

`sync.Mutex` は、Go言語で最も基本的な排他制御プリミティブです。`Lock()` メソッドでロックを取得し、`Unlock()` メソッドでロックを解放します。一度に一つのゴルーチンのみがロックを保持でき、他のゴルーチンはロックが解放されるまでブロックされます。読み取りと書き込みの両方で排他制御が必要な場合に広く使用されますが、読み取りが頻繁で書き込みが稀なケースでは、読み取り操作もロックを待つため、並行性が低下する可能性があります。

### 3. `sync/atomic.Value`

`sync/atomic.Value` は、任意の型の値をアトミックに（不可分に）保存およびロードするための型です。`Store()` メソッドで値を保存し、`Load()` メソッドで値をロードします。これらの操作は、CPUの命令レベルでアトミックに実行されるため、ミューテックスのようなロック機構を必要とせず、データ競合なしに安全に値を更新・読み取りできます。これは、特に読み取りが頻繁で書き込みが稀な共有データ構造の更新に適しています。

### 4. コピーオンライト (Copy-On-Write, CoW) パターン

コピーオンライトは、共有されるデータ構造の更新を効率的に行うためのプログラミングパターンです。このパターンでは、データ構造を読み取る際にはロックなしで直接アクセスできます。しかし、データ構造を変更する必要がある場合（書き込み時）には、元のデータ構造のコピーを作成し、そのコピーに対して変更を加えます。変更が完了したら、`atomic.Value` のようなアトミックな操作を用いて、共有されているポインタを新しいコピーに切り替えます。

このパターンの利点は以下の通りです。
*   **読み取りの高速化:** 読み取り操作はロックを必要としないため、非常に高速で並行性が高いです。
*   **書き込みの分離:** 書き込み操作はコピーに対して行われるため、読み取り操作をブロックしません。
*   **スレッドセーフティ:** アトミックなポインタの切り替えにより、データの一貫性が保証されます。

欠点としては、書き込み時にデータ構造全体のコピーが必要になるため、大きなデータ構造の場合にはメモリ使用量とコピーのオーバーヘッドが大きくなる可能性があります。しかし、`gob` の型情報マップのように、読み取りが圧倒的に多く、書き込み（新しい型の登録）が比較的少ないシナリオでは、非常に効果的な最適化手法となります。

## 技術的詳細

このコミットの核心は、`encoding/gob` パッケージ内で型情報をキャッシュしている `typeInfoMap` の管理方法を根本的に変更した点にあります。

**変更前:**
`typeInfoMap` は `map[reflect.Type]*typeInfo` 型で、`typeLock sync.Mutex` によって保護されていました。`getTypeInfo` 関数がこのマップにアクセスするたびに `typeLock.Lock()` と `typeLock.Unlock()` が呼び出され、型情報のルックアップ（読み取り）であっても排他制御が必要でした。これにより、複数のゴルーチンが同時に型情報を要求すると、ミューテックスの競合が発生し、並行処理の性能が低下していました。

**変更後:**
1.  **`typeInfoMap` の変更:**
    `var typeInfoMap = make(map[reflect.Type]*typeInfo)` から `var typeInfoMap atomic.Value` に変更されました。
    `atomic.Value` は、`map[reflect.Type]*typeInfo` のインスタンスを保持します。

2.  **`lookupTypeInfo` 関数の導入:**
    新しい `lookupTypeInfo` 関数が導入され、`typeInfoMap.Load().(map[reflect.Type]*typeInfo)` を使って現在のマップのコピーをアトミックに取得し、ロックなしで型情報をルックアップします。これにより、読み取り操作は非常に高速になり、競合がなくなります。

3.  **`buildTypeInfo` 関数の導入とコピーオンライトの実装:**
    `getTypeInfo` 関数は、まず `lookupTypeInfo` を使って型情報を検索します。もし見つからなければ、`buildTypeInfo` 関数が呼び出されます。
    `buildTypeInfo` 関数は、以下の手順でコピーオンライトを実装します。
    *   まず、`typeLock` (これは `buildTypeInfo` 内でのみ使用される、より粒度の細かいロック) を取得します。これは、複数のゴルーチンが同時に新しい型情報を構築しようとするのを防ぐためです。
    *   再度 `lookupTypeInfo` を呼び出して、他のゴルーチンが既に同じ型情報を構築していないか確認します（ダブルチェックロッキングパターン）。
    *   新しい `map[reflect.Type]*typeInfo` を作成し、`typeInfoMap.Load()` で取得した既存のマップの内容をすべてコピーします。
    *   新しい型情報をこの新しいマップに追加します。
    *   `typeInfoMap.Store(newm)` を使って、`atomic.Value` が保持するマップをアトミックに新しいマップに置き換えます。
    *   `typeLock` を解放します。

4.  **`typeInfo` 構造体の変更:**
    `typeInfo` 構造体内の `encoder *encEngine` フィールドが `encoder atomic.Value` に変更されました。これにより、`encEngine` の構築もコピーオンライトパターンで管理できるようになり、`encInit sync.Mutex` がその構築を保護します。これは、再帰的な型定義のエンコーダ構築を安全かつ効率的に行うためです。

これらの変更により、`gob` エンコーディングの大部分の操作（型情報の読み取り）がロックフリーになり、並行処理の性能が大幅に向上しました。ベンチマーク結果は、特に並行度が高い環境で、最大50%以上の性能改善が見られることを明確に示しています。

## コアとなるコードの変更箇所

主な変更は以下の3つのファイルに集中しています。

1.  **`src/encoding/gob/encode.go`**:
    *   `encOpFor` 関数のシグネチャに `building map[*typeInfo]bool` 引数が追加され、再帰的な型構築の検出に使用されます。
    *   `getEncEngine` 関数が `typeLock` を直接使用せず、`atomic.Value` から `encEngine` をロードするように変更されました。
    *   `lockAndGetEncEngine` 関数が削除され、`getEncEngine` が直接呼び出されるようになりました。
    *   `buildEncEngine` 関数が新しく追加され、`encEngine` の構築と `atomic.Value` への格納ロジックをカプセル化しています。

2.  **`src/encoding/gob/encoder.go`**:
    *   `sendActualType` および `sendTypeDescriptor` 関数から `typeLock.Lock()` と `typeLock.Unlock()` の呼び出しが削除されました。これにより、型情報の送信プロセスにおけるミューテックス競合が解消されます。

3.  **`src/encoding/gob/type.go`**:
    *   `typeInfo` 構造体の `encoder` フィールドが `*encEngine` から `atomic.Value` に変更され、`encInit sync.Mutex` が追加されました。
    *   `typeInfoMap` 変数が `map[reflect.Type]*typeInfo` から `atomic.Value` に変更されました。
    *   `lookupTypeInfo` 関数が新しく追加され、`atomic.Value` からマップをロードして型情報を検索します。
    *   `getTypeInfo` 関数が `typeInfoMap` への直接アクセスをやめ、`lookupTypeInfo` と `buildTypeInfo` を呼び出すように変更されました。
    *   `buildTypeInfo` 関数が新しく追加され、コピーオンライトパターンで `typeInfoMap` を更新するロジックを実装しています。この関数内で `typeLock` が使用されますが、これはマップのコピーとアトミックな置き換えという、より粒度の細かい排他制御のためです。

## コアとなるコードの解説

### `src/encoding/gob/type.go` の変更点

```go
// typeInfoMap is an atomic pointer to map[reflect.Type]*typeInfo.
// It's updated copy-on-write. Readers just do an atomic load
// to get the current version of the map. Writers make a full copy of
// the map and atomically update the pointer to point to the new map.
// Under heavy read contention, this is significantly faster than a map
// protected by a mutex.
var typeInfoMap atomic.Value

func lookupTypeInfo(rt reflect.Type) *typeInfo {
	m, _ := typeInfoMap.Load().(map[reflect.Type]*typeInfo)
	return m[rt]
}

func getTypeInfo(ut *userTypeInfo) (*typeInfo, error) {
	rt := ut.base
	if ut.externalEnc != 0 {
		rt = ut.user
	}
	if info := lookupTypeInfo(rt); info != nil { // ロックなしで読み取り
		return info, nil
	}
	return buildTypeInfo(ut, rt) // 見つからなければ構築
}

func buildTypeInfo(ut *userTypeInfo, rt reflect.Type) (*typeInfo, error) {
	typeLock.Lock() // 書き込み時のみロック
	defer typeLock.Unlock()

	if info := lookupTypeInfo(rt); info != nil { // ダブルチェックロッキング
		return info, nil
	}

	// ... (型情報の構築ロジック) ...

	// Create new map with old contents plus new entry.
	newm := make(map[reflect.Type]*typeInfo)
	m, _ := typeInfoMap.Load().(map[reflect.Type]*typeInfo)
	for k, v := range m {
		newm[k] = v
	}
	newm[rt] = info
	typeInfoMap.Store(newm) // アトミックにマップを置き換え
	return info, nil
}
```
このコードスニペットは、`typeInfoMap` が `atomic.Value` に変更され、読み取り操作 (`lookupTypeInfo`) がロックフリーになったことを示しています。新しい型情報が必要な場合のみ `buildTypeInfo` が呼び出され、その中で `typeLock` を取得し、既存のマップをコピーして新しいエントリを追加し、`atomic.Value` を介してアトミックにマップを置き換えるコピーオンライトパターンが適用されます。これにより、読み取りの並行性が大幅に向上します。

### `src/encoding/gob/encode.go` の変更点

```go
// getEncEngine returns the engine to compile the type.
func getEncEngine(ut *userTypeInfo, building map[*typeInfo]bool) *encEngine {
	info, err := getTypeInfo(ut)
	if err != nil {
		error_(err)
	}
	enc, ok := info.encoder.Load().(*encEngine) // atomic.Valueからロード
	if !ok {
		enc = buildEncEngine(info, ut, building) // エンジン構築
	}
	return enc
}

func buildEncEngine(info *typeInfo, ut *userTypeInfo, building map[*typeInfo]bool) *encEngine {
	// Check for recursive types.
	if building != nil && building[info] {
		return nil
	}
	info.encInit.Lock() // エンジン構築時のみロック
	defer info.encInit.Unlock()
	enc, ok := info.encoder.Load().(*encEngine) // ダブルチェックロッキング
	if !ok {
		if building == nil {
			building = make(map[*typeInfo]bool)
		}
		building[info] = true
		enc = compileEnc(ut, building)
		info.encoder.Store(enc) // atomic.Valueにストア
	}
	return enc
}
```
`getEncEngine` 関数は、`typeInfo` 構造体内の `atomic.Value` からエンコーダエンジンをロードするように変更されました。もしエンコーダがまだ構築されていなければ、`buildEncEngine` が呼び出され、`info.encInit` ミューテックスを使って排他制御を行いながらエンコーダを構築し、`atomic.Value` に格納します。これにより、エンコーダの構築も並行処理に優しくなっています。

### `src/encoding/gob/encoder.go` の変更点

```go
func (enc *Encoder) sendActualType(w io.Writer, state *encoderState, ut *userTypeInfo) {
	actual := userType(state.actual)
	if _, alreadySent := enc.sent[actual]; alreadySent {
		return false
	}
	// typeLock.Lock() // 削除
	info, err := getTypeInfo(ut)
	// typeLock.Unlock() // 削除
	if err != nil {
		enc.setError(err)
		return
	}
	// ...
}
```
`sendActualType` 関数から `typeLock` の取得と解放が削除されています。これは、`getTypeInfo` 関数自体が内部で `atomic.Value` を使用してロックフリーな読み取りを実装しているため、呼び出し側で明示的にロックする必要がなくなったことを意味します。これにより、エンコーダが型情報を送信する際のボトルネックが解消され、並行性能が向上します。

# [インデックス 26882] ファイルの概要

このコミットは、Goコンパイラの字句解析器（lexer）におけるトークン管理の最適化と整理を目的としています。具体的には、多数の特定の演算子トークン（例: `&&`, `==`, `>>` など）を廃止し、それらを汎用的な`LOPER`（Lexer Operator）トークンに統合しています。これにより、トークン定義の冗長性が排除され、コードの保守性が向上しています。また、関連するテーブルやマップでのトークンの順序を統一し、一貫性を高めています。

## 変更の背景

Goコンパイラの`cmd/compile`パッケージは、Go言語のソースコードを機械語に変換する役割を担っています。このプロセスは、主に以下のフェーズに分かれます。

1.  **字句解析（Lexical Analysis）**: ソースコードの文字列を「トークン」と呼ばれる意味のある最小単位に分割します。例えば、`if x == 10`というコードは、`if`（キーワード）、`x`（識別子）、`==`（演算子）、`10`（リテラル）といったトークンに分割されます。
2.  **構文解析（Syntactic Analysis）**: 字句解析器が生成したトークンのストリームを受け取り、それらがGo言語の文法規則に従っているかを確認し、抽象構文木（AST）を構築します。

このコミット以前は、Goコンパイラの字句解析器には、`LANDAND`（`&&`）、`LEQ`（`==`）、`LRSH`（`>>`）など、個々の演算子に対してそれぞれ異なるトークンが定義されていました。これは、トークン定義の数が増え、字句解析器と構文解析器の両方でこれらの多数のトークンを個別に処理する必要があるため、以下のような問題を引き起こす可能性がありました。

*   **冗長性**: 多くの演算子が本質的に「演算子」という共通のカテゴリに属するにもかかわらず、それぞれに固有のトークンIDが割り当てられていたため、トークン定義が冗長になっていました。
*   **保守性の低下**: 新しい演算子が追加されたり、既存の演算子の意味が変更されたりするたびに、複数のトークン定義や関連する処理ロジックを更新する必要がありました。
*   **コードの一貫性の欠如**: トークンを文字列に変換するマップや、トークンの優先順位を管理するテーブルなど、複数のデータ構造でトークンの順序や定義が統一されていない場合があり、混乱やエラーの原因となる可能性がありました。

このコミットは、これらの問題を解決し、コンパイラのフロントエンド部分の設計をよりクリーンで保守しやすいものにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

### 1. コンパイラのフロントエンド

コンパイラは、ソースコードを中間表現や最終的な機械語に変換するソフトウェアです。その中でも、ソースコードを解析する部分を「フロントエンド」と呼びます。フロントエンドは通常、字句解析器（lexer/scanner）と構文解析器（parser）から構成されます。

*   **字句解析器（Lexer/Scanner）**: ソースコードを読み込み、意味のある最小単位である「トークン」のストリームを生成します。例えば、`int x = 10;`というC言語のコードは、`int`（キーワード）、`x`（識別子）、`=`（代入演算子）、`10`（整数リテラル）、`;`（セミコロン）といったトークンに分割されます。
*   **構文解析器（Parser）**: 字句解析器から受け取ったトークンのストリームが、プログラミング言語の文法規則に適合しているかを検証し、プログラムの構造を表現する抽象構文木（AST）を構築します。

### 2. トークンとトークンタイプ

トークンは、プログラミング言語のソースコードにおける意味のある最小単位です。各トークンには、その種類を示す「トークンタイプ」が割り当てられます。例えば、`if`はキーワードトークン、`+`は演算子トークン、`myVar`は識別子トークンです。

このコミットでは、特に「演算子トークン」の扱いが変更されています。以前は`==`や`&&`といった個々の演算子にそれぞれ異なるトークンタイプが割り当てられていましたが、この変更により、これらすべてが`LOPER`という単一の汎用トークンタイプで表現されるようになります。

### 3. 演算子の優先順位と結合性

プログラミング言語では、複数の演算子が登場する式（例: `a + b * c`）の評価順序を決定するために、演算子の「優先順位（precedence）」と「結合性（associativity）」が定義されています。

*   **優先順位**: どの演算子が先に評価されるかを決定します（例: `*`は`+`より優先順位が高い）。
*   **結合性**: 同じ優先順位の演算子が連続する場合の評価順序を決定します（例: `a - b - c`は左結合なので`(a - b) - c`と評価される）。

字句解析器は、トークンを生成する際に、そのトークンが演算子である場合にその優先順位情報も付加することがあります。構文解析器は、この情報を使ってASTを正しく構築します。このコミットでは、`lexer`構造体の`prec`フィールドがこの優先順位情報を保持しています。

### 4. `utf8.RuneSelf`

Go言語では、文字列はUTF-8でエンコードされたバイト列として扱われます。`utf8.RuneSelf`は、UTF-8エンコーディングにおいて、1バイトで表現できるUnicodeコードポイントの最大値（127、つまりASCII文字の範囲）を定義する定数です。

このコミットのコードでは、トークンIDを定義する際に`utf8.RuneSelf + iota`という形式が使われています。これは、1バイト文字（ASCII文字）と衝突しないように、カスタムトークンIDを`utf8.RuneSelf`より大きな値から開始させるための一般的な慣習です。これにより、単一の文字で表現されるトークン（例: `{`, `}`, `+`など）は自身のUnicode値がトークンIDとなり、それ以外の複数文字トークンやキーワードなどは`utf8.RuneSelf`以上の値を持つカスタムIDが割り当てられます。

## 技術的詳細

このコミットの核心は、Goコンパイラの字句解析器が演算子をどのように識別し、表現するかという内部メカニズムの変更にあります。

### 1. 汎用`LOPER`トークンの導入

以前は、`&&`、`||`、`==`、`!=`、`<=`、`>=`、`<<`、`>>`、`&^`といったGo言語の各二項演算子や比較演算子に対して、それぞれ`LANDAND`、`LOROR`、`LEQ`、`LNE`、`LLE`、`LGE`、`LLSH`、`LRSH`、`LANDNOT`といった個別のトークン定数が存在していました。

このコミットでは、これらの個別の演算子トークンをすべて削除し、代わりに`LOPER`という単一の汎用トークンを導入しています。

*   **`lex.go`の変更**:
    *   `const`ブロックから、`LANDAND`、`LANDNOT`、`LEQ`、`LGE`、`LGT`、`LLE`、`LLSH`、`LLT`、`LNE`、`LOROR`、`LRSH`といった具体的な演算子トークンが削除されました。
    *   新たに`LOPER`が定義されました。
    *   `lexer`構造体の`op`フィールドのコメントが更新され、`tok == LOPER`の場合にも`op`が有効であることが明示されました。これは、`LOPER`トークンが検出された際に、具体的な演算子の種類（例: `OANDAND`、`OEQ`など）を`op`フィールドに格納することを示唆しています。
    *   `lexer.next()`関数内の字句解析ロジックが変更され、`>`、`<`、`=`、`!`、`&`、`|`などの文字から始まる演算子を検出した際に、以前は特定の演算子トークン（例: `LRSH`、`LGE`）を`c`（現在のトークン）に設定していた箇所が、すべて`LOPER`を設定するように変更されました。具体的な演算子の種類は、引き続き`l.op`フィールドに設定されます。
    *   `lexn`マップ（トークンIDから文字列への変換用）からも、削除された個別の演算子トークンが除去され、`LOPER: "OPER"`が追加されました。

### 2. トークン定義とマップの順序統一

コミットメッセージの「Use same ordering of tokens in the various tables/maps.」という部分が示すように、トークン定義の`const`ブロック、`lexn`マップ、`tokstrings`マップにおいて、トークンの順序が統一されました。

*   `lex.go`と`parser.go`の両方で、`LNAME`、`LLITERAL`、`LOPER`、`LASOP`、`LINCOP`、`LCOLAS`、`LCOMM`、`LDDD`といったトークンが、論理的なグループ（名前とリテラル、演算子ベースの操作、その他、キーワード）ごとに整理され、一貫した順序で並べ替えられています。
*   これにより、コードの可読性と保守性が向上し、将来的なトークン追加や変更の際にエラーが発生しにくくなります。

### 3. 構文解析器への影響

字句解析器が個別の演算子トークンではなく`LOPER`トークンと具体的な演算子タイプ（`op`フィールド）を渡すようになったため、構文解析器もその変更に適応する必要があります。

*   **`parser.go`の変更**:
    *   `parser.syntax_error()`関数内の`switch p.tok`ブロックに、`case LOPER: tok = goopnames[p.op]`という新しいケースが追加されました。これは、構文エラーが発生した際に、`LOPER`トークンであれば`p.op`フィールドに格納されている具体的な演算子タイプを`goopnames`マップから取得してエラーメッセージに表示することを示しています。
    *   `tokstrings`マップ（トークンIDから文字列への変換用）からも、削除された個別の演算子トークンが除去され、`LOPER: "op"`が追加されました。これは、デバッグやエラー報告の際に`LOPER`トークンが「op」として表示されることを意味します。

この変更により、構文解析器は`LOPER`トークンを受け取った際に、その`op`フィールドを参照して具体的な演算子の種類を判断し、適切なASTノードを構築するようになります。これにより、字句解析器と構文解析器間のインターフェースがよりシンプルかつ汎用的なものになります。

しかし、`LOPER`だけではどの演算子であるか区別できないため、字句解析器は`lexer`構造体の`op`フィールドに、具体的な演算子の種類を示す`Op`型の値を格納します。例えば、`==`を検出した場合は`LOPER`トークンを生成し、`op`フィールドには`OEQ`（Operator Equal）のような値を設定します。これにより、構文解析器は`LOPER`トークンを受け取った際に、`op`フィールドを参照することで具体的な演算子の種類を判別できるようになります。

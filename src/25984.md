## 変更の背景

このコミットの背景には、HTTP/2プロトコルの導入と、それに対応する `net/http` パッケージのテストカバレッジの拡充があります。Goの `net/http` パッケージは、HTTP/1.1とHTTP/2の両方をサポートしており、特にHTTP/2はパフォーマンス向上や多重化などの新機能を提供します。

`TestZeroLengthPostAndResponse` は、クライアントがボディがゼロ長のPOSTリクエストを送信し、サーバーもボディがゼロ長のレスポンスを返すという特殊なケースをテストするためのものです。このようなゼロ長のボディは、HTTPプロトコルにおいてエッジケースとなりやすく、特に接続の再利用やボディの読み取りに関する挙動が重要になります。元のコメントにもあるように、クライアントが接続を再利用する際に、以前のリクエストのボディが閉じられることで `http.ErrBodyReadAfterClose` エラーが発生する可能性があり、これを避けるためのテストです。

HTTP/2はHTTP/1.1とは異なるフレーム構造とストリーム管理メカニズムを持つため、HTTP/1.1で正しく動作するテストがHTTP/2でも同様に機能するかどうかを確認することは非常に重要です。このコミットは、既存の重要なテストケースをHTTP/2環境下でも検証できるようにすることで、`net/http` パッケージの堅牢性を高めることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

1.  **HTTP/1.1とHTTP/2**:
    *   **HTTP/1.1**: 広く普及しているHTTPプロトコルのバージョン。リクエスト/レスポンスはテキストベースで、通常は1つのTCP接続で1つのリクエスト/レスポンスを処理します（パイプライン処理もありますが、ヘッドオブラインブロッキングの問題があります）。
    *   **HTTP/2**: HTTP/1.1の欠点を克服するために設計された新しいプロトコル。バイナリフレーミング、多重化（単一のTCP接続で複数のリクエスト/レスポンスを並行処理）、ヘッダー圧縮（HPACK）、サーバープッシュなどの機能を提供します。これにより、Webパフォーマンスが大幅に向上します。
2.  **Goの `net/http` パッケージ**: Go言語の標準ライブラリで、HTTPクライアントとサーバーの実装を提供します。HTTP/1.1とHTTP/2の両方を透過的にサポートするように設計されています。
3.  **`httptest` パッケージ**: Goの標準ライブラリの一部で、HTTPハンドラやサーバーのテストを容易にするためのユーティリティを提供します。`httptest.NewServer` は、テスト用のHTTPサーバーを簡単に起動するために使用されます。
4.  **ゼロ長ボディのPOSTリクエスト**: HTTPのPOSTリクエストでは、通常、リクエストボディにデータが含まれます。しかし、ボディが空（ゼロ長）である場合も有効なリクエストとして扱われることがあります。例えば、リソースの作成をトリガーするだけで、特定のデータを送信する必要がない場合などです。
5.  **`io.EOF` と `http.ErrBodyReadAfterClose`**:
    *   **`io.EOF`**: ファイルやストリームの終端に達したことを示すエラー。ボディの読み取りが正常に完了した場合に返されることが期待されます。
    *   **`http.ErrBodyReadAfterClose`**: `net/http` パッケージで定義されているエラーで、既に閉じられたリクエストボディを読み取ろうとした場合に発生します。これは、特に接続の再利用やリクエストのライフサイクル管理において注意が必要なケースです。

## 技術的詳細

このコミットの主要な技術的変更点は、既存のテストロジックをHTTP/1.1とHTTP/2の両方で再利用できるように抽象化したことです。

1.  **テスト関数の抽象化**:
    *   元の `TestZeroLengthPostAndResponse` 関数は、`func testZeroLengthPostAndResponse(t *testing.T, h2 bool)` という新しいヘルパー関数にリファクタリングされました。
    *   このヘルパー関数は `h2` というブール値の引数を受け取ります。この引数が `true` の場合、テストはHTTP/2モードで実行され、`false` の場合はHTTP/1.1モードで実行されます。
2.  **HTTP/2対応のテストユーティリティ `newClientServerTest` の導入**:
    *   元のテストでは `httptest.NewServer` を直接使用していましたが、これは主にHTTP/1.1サーバーをセットアップします。
    *   新しいヘルパー関数では `newClientServerTest(t, h2, HandlerFunc(...))` が導入されています。この `newClientServerTest` は、`net/http` パッケージのテストスイート内で定義されているユーティリティ関数であり、`h2` 引数に基づいてHTTP/1.1またはHTTP/2のクライアントとサーバーのペアをセットアップします。これにより、テストコードはHTTPプロトコルの詳細を意識することなく、両方のプロトコルで同じロジックをテストできます。
    *   `newClientServerTest` は、テスト用のサーバー (`ts`) とクライアント (`c`) を含む構造体を返します。
3.  **テストの分離**:
    *   `TestZeroLengthPostAndResponse_h1` と `TestZeroLengthPostAndResponse_h2` という2つの新しいテスト関数が追加されました。
    *   `TestZeroLengthPostAndResponse_h1` は `testZeroLengthPostAndResponse(t, false)` を呼び出し、HTTP/1.1モードでテストを実行します。
    *   `TestZeroLengthPostAndResponse_h2` は `testZeroLengthPostAndResponse(t, true)` を呼び出し、HTTP/2モードでテストを実行します。
    *   これにより、HTTP/1.1とHTTP/2それぞれのプロトコルスタックにおけるゼロ長ボディの挙動を個別に検証できるようになります。
4.  **リソースのクリーンアップ**:
    *   `ts.Close()` は `cst.close()` に変更されました。`cst` は `newClientServerTest` が返す構造体であり、その `close` メソッドがサーバーとクライアントの両方のリリソースを適切にクリーンアップします。

この変更により、`net/http` パッケージがゼロ長POSTリクエストとレスポンスをHTTP/1.1とHTTP/2の両方で正しく処理し、特に接続の再利用時に `http.ErrBodyReadAfterClose` のような予期せぬエラーが発生しないことを保証するためのテストカバレッジが強化されました。

## コアとなるコードの解説

1.  **`TestZeroLengthPostAndResponse` のリファクタリング**:
    *   元の `TestZeroLengthPostAndResponse` 関数が削除され、そのロジックが `testZeroLengthPostAndResponse(t *testing.T, h2 bool)` という新しいプライベートヘルパー関数に移動されました。
    *   `h2` 引数は、テストがHTTP/2モードで実行されるべきか（`true`）、HTTP/1.1モードで実行されるべきか（`false`）を制御します。

2.  **新しいテスト関数の追加**:
    *   `TestZeroLengthPostAndResponse_h1(t *testing.T)`: この関数は `testZeroLengthPostAndResponse(t, false)` を呼び出し、HTTP/1.1プロトコルを使用してゼロ長POSTリクエストとレスポンスのテストを実行します。
    *   `TestZeroLengthPostAndResponse_h2(t *testing.T)`: この関数は `testZeroLengthPostAndResponse(t, true)` を呼び出し、HTTP/2プロトコルを使用して同じテストを実行します。

3.  **テストサーバーとクライアントのセットアップの変更**:
    *   以前は `ts := httptest.NewServer(...)` を使用していましたが、これはHTTP/1.1サーバーをセットアップします。
    *   変更後、`cst := newClientServerTest(t, h2, HandlerFunc(...))` が使用されています。`newClientServerTest` は、`h2` の値に基づいてHTTP/1.1またはHTTP/2のテスト環境をセットアップする内部ユーティリティ関数です。これにより、テストハンドラ (`HandlerFunc`) は同じままで、異なるプロトコルスタックでテストを実行できます。
    *   `cst` オブジェクトは、テストサーバー (`cst.ts`) とテストクライアント (`cst.c`) の両方を提供します。

4.  **リクエストURLとクライアントの変更**:
    *   リクエストの作成時に使用されるURLが `ts.URL` から `cst.ts.URL` に変更されました。これは、`newClientServerTest` が提供するテストサーバーのURLを使用するためです。
    *   リクエストの実行に使用されるクライアントが `DefaultClient.Do(req)` から `cst.c.Do(req)` に変更されました。これは、`newClientServerTest` がプロトコルに応じて適切に設定されたクライアントを提供するためです。

5.  **リソースクリーンアップの変更**:
    *   `defer ts.Close()` は `defer cst.close()` に変更されました。`cst.close()` は、`newClientServerTest` によってセットアップされたテスト環境（サーバーとクライアント）を適切にシャットダウンするためのメソッドです。

これらの変更により、単一のテストロジックをHTTP/1.1とHTTP/2の両方で実行できるようになり、コードの重複を避けつつ、両プロトコルにおけるゼロ長ボディの挙動のテストカバレッジを向上させています。

# [インデックス 20999] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）およびスタックのポイズニング（Poisoning）に使用される定数`_PoisonGC`と`_PoisonStack`の定義を修正し、32-bitアーキテクチャでのビルド問題を解決するものです。具体的には、`uintptr`のサイズに依存しない形でポイズン値を正しくマスクするように変更されました。

## 変更の背景

Goランタイムでは、デバッグ目的でメモリ領域を特定のパターンで埋める「ポイズニング」という手法が用いられます。これは、未初期化のメモリへのアクセスや、解放済みメモリへの書き込みといったバグを早期に検出するために行われます。`_PoisonGC`はGCが管理するヒープメモリに、`_PoisonStack`はスタックメモリに適用されるポイズン値を定義しています。

このコミット以前の`_PoisonGC`と`_PoisonStack`の定義は、`0xf969696969696969 & ^uintptr(0)`という形式でした。この式は、64-bitシステムでは問題なく動作しますが、32-bitシステムではビルドエラーや予期せぬ動作を引き起こす可能性がありました。

問題の根源は、`^uintptr(0)`が`uintptr`型の全ビットを1にするマスクとして機能する点にあります。64-bitシステムでは`uintptr`が64-bit幅であるため、`^uintptr(0)`は`0xFFFFFFFFFFFFFFFF`となり、`0xf969696969696969`という64-bit定数とのAND演算は、定数そのものを返します。しかし、32-bitシステムでは`uintptr`が32-bit幅であるため、`^uintptr(0)`は`0xFFFFFFFF`となります。この場合、`0xf969696969696969`という64-bit定数と`0xFFFFFFFF`のAND演算は、上位32ビットが切り捨てられ、意図しない値が生成されるか、コンパイル時に定数が32-bitの範囲を超えているとしてエラーになる可能性がありました。

このコミットは、この32-bitビルドの問題を解決し、`_PoisonGC`と`_PoisonStack`がすべてのサポートされるアーキテクチャで正しく定義されるようにすることを目的としています。

## 前提知識の解説

### Goのポイズニング (Poisoning)

Goランタイムにおけるポイズニングは、デバッグを支援するためのテクニックです。メモリが割り当てられた直後や解放された直後に、そのメモリ領域を特定の既知のパターン（ポイズン値）で埋めます。これにより、以下のようなバグを早期に発見できます。

*   **未初期化メモリの使用**: プログラムが初期化されていないメモリを読み取ろうとした場合、その値がポイズン値であれば、開発者はそれが意図しない読み取りであることを認識できます。
*   **解放済みメモリへのアクセス (Use-After-Free)**: メモリが解放された後もプログラムがそのメモリにアクセスしようとした場合、その領域がポイズン値で埋められていれば、不正なアクセスであることを検出できます。

`_PoisonGC`はガベージコレクタが管理するヒープメモリに、`_PoisonStack`は関数のスタックフレームに適用されます。

### `uintptr`型

Go言語の`uintptr`型は、ポインタを保持できる符号なし整数型です。この型のサイズは、実行されているシステムのアーキテクチャに依存します。

*   **32-bitシステム**: `uintptr`は32ビット（4バイト）の幅を持ちます。
*   **64-bitシステム**: `uintptr`は64ビット（8バイト）の幅を持ちます。

この可変性が、今回の問題の根本原因となりました。

### ビット演算子 `^` (XOR) と `&` (AND)

*   **`^` (XOR)**: ビット単位の排他的論理和演算子です。特に、`^X`のように単項演算子として使用される場合、Xの各ビットを反転させます（ビット単位のNOT演算）。例えば、`^uintptr(0)`は、`uintptr`型の0（全ビットが0）の各ビットを反転させるため、結果として`uintptr`型の全ビットが1の値を生成します。
*   **`&` (AND)**: ビット単位の論理積演算子です。両方のオペランドの対応するビットが1の場合にのみ、結果のビットが1になります。マスク処理によく使用されます。

### `1<<(8*ptrSize) - 1` 式の役割

この式は、現在のアーキテクチャの`uintptr`のサイズに合わせた「全ビットが1」のマスクを生成するために使用されます。

*   **`ptrSize`**: Goランタイム内部で定義されている定数で、現在のアーキテクチャにおけるポインタのバイトサイズ（32-bitシステムでは4、64-bitシステムでは8）を示します。
*   **`8*ptrSize`**: ポインタのバイトサイズをビットサイズに変換します。
    *   32-bitシステムの場合: `8 * 4 = 32`
    *   64-bitシステムの場合: `8 * 8 = 64`
*   **`1<<(8*ptrSize)`**: 1を`8*ptrSize`ビットだけ左シフトします。
    *   32-bitシステムの場合: `1 << 32` は `2^32` を表します。
    *   64-bitシステムの場合: `1 << 64` は `2^64` を表します。
*   **`- 1`**: 左シフトの結果から1を引くことで、そのビット幅の全ビットが1である値（マスク）を生成します。
    *   `2^32 - 1` は `0xFFFFFFFF` (32-bitの全ビット1)
    *   `2^64 - 1` は `0xFFFFFFFFFFFFFFFF` (64-bitの全ビット1)

このマスクをポイズン値とAND演算することで、ポイズン値が`uintptr`のサイズに正しく収まるように調整されます。

## 技術的詳細

### 変更前の問題点

変更前のコードは以下の通りでした。

```go
const (
	_PoisonGC    = 0xf969696969696969 & ^uintptr(0)
	_PoisonStack = 0x6868686868686868 & ^uintptr(0)
)
```

ここで問題となるのは、`0xf969696969696969`と`0x6868686868686868`が64-bitの定数である点です。

1.  **64-bitシステムの場合**:
    *   `uintptr`は64-bit幅です。
    *   `^uintptr(0)`は`0xFFFFFFFFFFFFFFFF`（64-bitの全ビット1）となります。
    *   `0xf969696969696969 & 0xFFFFFFFFFFFFFFFF` は `0xf969696969696969` となり、意図通りに64-bitのポイズン値が設定されます。

2.  **32-bitシステムの場合**:
    *   `uintptr`は32-bit幅です。
    *   `^uintptr(0)`は`0xFFFFFFFF`（32-bitの全ビット1）となります。
    *   `0xf969696969696969 & 0xFFFFFFFF` のような演算は、Goのコンパイラが定数評価を行う際に問題を引き起こします。`0xf969696969696969`は32-bitの`uintptr`では表現できないため、コンパイルエラーとなるか、あるいは上位32ビットが暗黙的に切り捨てられてしまい、意図しないポイズン値が設定される可能性がありました。特に、Goの定数評価は厳密であり、型が明示されていない数値定数は、その値が収まる最小の型に推論されますが、この場合は`uint64`として扱われるため、`uintptr`とのAND演算で型の不一致や値のオーバーフローが発生しやすくなります。

### 変更後の解決策

変更後のコードは以下の通りです。

```go
const (
	_PoisonGC    = 0xf969696969696969 & (1<<(8*ptrSize) - 1)
	_PoisonStack = 0x6868686868686868 & (1<<(8*ptrSize) - 1)
)
```

この修正では、`^uintptr(0)`の代わりに`(1<<(8*ptrSize) - 1)`という式が使用されています。

1.  **`ptrSize`の利用**: `ptrSize`はGoランタイムが提供する定数で、現在のアーキテクチャのポインタのバイトサイズ（32-bitでは4、64-bitでは8）を正確に反映します。
2.  **動的なマスク生成**:
    *   **32-bitシステムの場合**: `(1<<(8*4) - 1)` は `(1<<32 - 1)` となり、結果として`0xFFFFFFFF`（32-bitの全ビット1）のマスクが生成されます。
    *   **64-bitシステムの場合**: `(1<<(8*8) - 1)` は `(1<<64 - 1)` となり、結果として`0xFFFFFFFFFFFFFFFF`（64-bitの全ビット1）のマスクが生成されます。
3.  **正しいポイズン値の適用**:
    *   この動的に生成されたマスクと、元の64-bitポイズン定数（`0xf969696969696969`または`0x6868686868686868`）とのAND演算が行われます。
    *   32-bitシステムでは、`0xf969696969696969 & 0xFFFFFFFF` となり、64-bit定数の下位32ビットが正しく抽出され、32-bitの`uintptr`に収まるポイズン値が生成されます。
    *   64-bitシステムでは、`0xf969696969696969 & 0xFFFFFFFFFFFFFFFF` となり、元の64-bitポイズン値がそのまま使用されます。

この変更により、`_PoisonGC`と`_PoisonStack`の定義が、実行されるアーキテクチャの`uintptr`のサイズに完全に適合するようになり、32-bit環境でのビルド問題が解消されました。これは、Goランタイムが異なるアーキテクチャ間で移植性を保ちつつ、低レベルのメモリ操作を正確に行うための重要な修正です。

## コアとなるコードの解説

変更されたのは、`_PoisonGC`と`_PoisonStack`という2つの定数の定義行です。

*   **変更前**:
    ```go
    _PoisonGC    = 0xf969696969696969 & ^uintptr(0)
    _PoisonStack = 0x6868686868686868 & ^uintptr(0)
    ```
    ここでは、64-bitのポイズンパターン（`0xf969696969696969`や`0x6868686868686868`）と、`uintptr(0)`のビット反転（つまり、`uintptr`の全ビットが1のマスク）とのビットAND演算を行っていました。前述の通り、32-bit環境では`^uintptr(0)`が32-bitマスクとなり、64-bit定数とのAND演算が問題を引き起こしていました。

*   **変更後**:
    ```go
    _PoisonGC    = 0xf969696969696969 & (1<<(8*ptrSize) - 1)
    _PoisonStack = 0x6868686868686868 & (1<<(8*ptrSize) - 1)
    ```
    この修正では、マスクの生成方法が`^uintptr(0)`から`(1<<(8*ptrSize) - 1)`に変更されました。
    *   `ptrSize`は、Goランタイムがコンパイル時に決定する、現在のアーキテクチャのポインタのバイトサイズ（4または8）です。
    *   `8*ptrSize`は、ポインタのビットサイズ（32または64）を計算します。
    *   `1<<(8*ptrSize)`は、`2^32`または`2^64`を生成します。
    *   そこから` - 1`を引くことで、32-bit環境では`0xFFFFFFFF`、64-bit環境では`0xFFFFFFFFFFFFFFFF`という、それぞれの`uintptr`サイズに合わせた正しい全ビット1のマスクが生成されます。
    *   このマスクと64-bitのポイズンパターンとのAND演算により、32-bit環境ではポイズンパターンの下位32ビットが、64-bit環境ではポイズンパターン全体が、それぞれ正しく`uintptr`型の定数として設定されるようになります。

この変更は、Goランタイムが異なるアーキテクチャで一貫して動作するための、低レベルながらも重要な修正です。

# [インデックス 23511] ファイルの概要

このコミットは、Go言語の標準ライブラリである`html/template`パッケージにおける、文字列のイテレーションと置換処理に関するバグ修正を扱っています。具体的には、CSS、JavaScript、HTMLの各エスケープ処理において、不正なUTF-8シーケンスを含む文字列が与えられた際に、バイトオフセットの計算が誤り、パニックを引き起こす可能性があった問題が解決されています。

## コミット

`html/template`パッケージ内のエスケープ処理において、文字列のイテレーション方法を`for/range`ループから`utf8.DecodeRuneInString`ベースのメカニズムに変更し、不正なUTF-8シーケンスに対する堅牢性を向上させました。これにより、バイトオフセットの計算が正確になり、パニックの発生を防ぎます。

    html/template: fix string iteration in replacement operations
    
    In css, js, and html, the replacement operations are implemented
    by iterating on strings (rune by rune). The for/range
    statement is used. The length of the rune is required
    and added to the index to properly slice the string.
    
    This is potentially wrong because there is a discrepancy between
    the result of utf8.RuneLen and the increment of the index
    (set by the for/range statement). For invalid strings,
    utf8.RuneLen('\ufffd') == 3, while the index is incremented
    only by 1 byte.
    
    htmlReplacer triggers a panic at slicing time for some
    invalid strings.
    
    Use a more robust iteration mechanism based on
    utf8.DecodeRuneInString, and make sure the same
    pattern is used for all similar functions in this
    package.
    
    Fixes #10799

## 変更の背景

`html/template`パッケージは、Webアプリケーションにおいてユーザーからの入力や動的に生成されるコンテンツを安全にHTMLに埋め込むために使用されます。この際、クロスサイトスクリプティング（XSS）などの脆弱性を防ぐために、特定の文字をエスケープする処理が不可欠です。

このコミット以前のバージョンでは、CSS、JavaScript、HTMLのエスケープ処理において、入力文字列をルーン（Unicodeコードポイント）ごとに処理するために`for/range`ループが使用されていました。`for/range`ループは、文字列をUTF-8として解釈し、各ルーンとその開始バイトオフセットを返します。しかし、不正なUTF-8シーケンスに遭遇した場合、`for/range`は「置換文字」（`\ufffd`、U+FFFD）を返し、そのルーンが占めるバイト数としては1バイトとしてインデックスを進めます。

問題は、この不正なルーンに対して`utf8.RuneLen`関数を呼び出すと、`\ufffd`のUTF-8エンコーディングが3バイトであるため、`utf8.RuneLen('\ufffd')`が3を返してしまう点にありました。これにより、`for/range`がインデックスを1バイト進めたのに対し、コードはルーンの長さとして3バイトを期待してしまい、文字列のスライス操作時に不正なバイトオフセットが指定され、結果としてパニック（`panic: runtime error: slice bounds out of range`など）が発生する可能性がありました。

このバグは、特に悪意のある入力や、単に不正なエンコーディングの文字列がテンプレートに渡された場合に、アプリケーションのクラッシュを引き起こす可能性があったため、修正が必要とされました。

## 前提知識の解説

### Go言語の文字列とUTF-8

Go言語の文字列は、読み取り専用のバイトスライスであり、通常はUTF-8エンコードされたテキストを保持します。
- **`string`型**: Goの`string`はバイトのシーケンスであり、UTF-8エンコードされたテキストを表すことが一般的です。
- **`rune`型**: `rune`はGoにおけるUnicodeコードポイントを表す型で、実体は`int32`のエイリアスです。
- **`for/range`ループ**: Goの`for/range`ループを文字列に対して使用すると、各イテレーションでルーンとその開始バイトオフセットが返されます。このループは、入力が有効なUTF-8であると仮定して動作します。不正なUTF-8シーケンスに遭遇した場合、`\ufffd`（U+FFFD）という置換文字を返し、インデックスは1バイト進みます。
- **`unicode/utf8`パッケージ**: Goの標準ライブラリで、UTF-8エンコーディングの操作を提供します。
    - **`utf8.RuneLen(r rune) int`**: 指定されたルーン`r`のUTF-8エンコードされたバイト長を返します。例えば、ASCII文字は1、日本語の漢字は3など。`\ufffd`の場合、そのUTF-8エンコーディングが3バイトであるため、3を返します。
    - **`utf8.DecodeRuneInString(s string) (r rune, size int)`**: 文字列`s`の先頭から1つのルーンをデコードし、そのルーンと、そのルーンが占めるバイト数（サイズ）を返します。不正なUTF-8シーケンスの場合、`\ufffd`と、その不正なシーケンスが占める実際のバイト数（通常は1）を返します。この関数は、文字列のバイトオフセットを正確に管理する上で非常に重要です。

### `html/template`パッケージ

`html/template`パッケージは、Go言語でWebアプリケーションを開発する際に、HTMLテンプレートを安全に生成するためのパッケージです。このパッケージは、テンプレートに埋め込まれるデータがHTML、CSS、JavaScriptのコンテキストにおいて適切にエスケープされることを保証し、XSS攻撃などのセキュリティ脆弱性を防ぐ役割を担います。

## 技術的詳細

このコミットの核心は、文字列のイテレーションとバイトオフセットの計算方法の変更にあります。

**変更前:**
```go
for i, r := range s {
    // ...
    written = i + utf8.RuneLen(r)
}
```
このコードでは、`for i, r := range s`によってルーン`r`とその開始バイトオフセット`i`を取得していました。そして、次の`written`位置を計算するために`i`に`utf8.RuneLen(r)`を加えていました。
しかし、入力文字列`s`が不正なUTF-8シーケンスを含んでいた場合、`for/range`は`r`として`\ufffd`を返し、`i`は不正なバイトの先頭から1バイトだけ進みます。このとき、`utf8.RuneLen('\ufffd')`は3を返します。
結果として、`written`は`i + 3`となり、`for/range`が実際に進んだバイト数（1）と異なる値になります。これにより、`s[written:i]`のようなスライス操作で範囲外アクセスが発生し、パニックを引き起こしていました。

**変更後:**
```go
r, w, written := rune(0), 0, 0
for i := 0; i < len(s); i += w {
    r, w = utf8.DecodeRuneInString(s[i:])
    // ...
    written = i + w
}
```
新しいアプローチでは、`for/range`ループの使用をやめ、`for i := 0; i < len(s); i += w`という形式のループを採用しています。ループ内で`utf8.DecodeRuneInString(s[i:])`を呼び出すことで、現在のバイトオフセット`i`から始まる文字列の先頭ルーン`r`と、そのルーンが占める正確なバイト数`w`を取得します。
この`w`は、有効なUTF-8ルーンであればそのバイト長を、不正なUTF-8シーケンスであれば`\ufffd`と、その不正なシーケンスが占める実際のバイト数（通常は1）を正確に返します。
そして、次のイテレーションのために`i`を`w`だけ進め、`written`も`i + w`とすることで、常に正確なバイトオフセットを維持できるようになりました。これにより、不正なUTF-8シーケンスが入力されても、スライス操作が正しく行われ、パニックが回避されます。

また、`cssEscaper`関数では、エスケープ対象の文字を`switch`文で個別に処理していた部分が、`cssReplacementTable`というマップのような構造に置き換えられました。これにより、コードの可読性と保守性が向上しています。

## コアとなるコードの解説

### `css.go` および `js.go` の `replace` / `cssEscaper` 関数

```go
// 変更前 (例: cssEscaper)
// for i, r := range s {
//     // ...
//     written = i + utf8.RuneLen(r)
// }

// 変更後 (例: cssEscaper)
r, w, written := rune(0), 0, 0
for i := 0; i < len(s); i += w {
    // See comment in htmlEscaper.
    r, w = utf8.DecodeRuneInString(s[i:])
    var repl string
    switch {
    case int(r) < len(cssReplacementTable) && cssReplacementTable[r] != "":
        repl = cssReplacementTable[r]
    default:
        continue
    }
    b.WriteString(s[written:i])
    b.WriteString(repl)
    written = i + w // ここが重要: utf8.RuneLen(r) ではなく w を使用
    // ...
}
```
この変更は、`for/range`ループが不正なUTF-8シーケンスを1バイトとして処理するのに対し、`utf8.RuneLen('\ufffd')`が3バイトを返すという不整合を解消します。`utf8.DecodeRuneInString`は、ルーンとそのルーンが占める正確なバイト数`w`を返すため、`i += w`と`written = i + w`を使用することで、常に正しいバイトオフセットを維持できます。

また、`cssEscaper`では、エスケープ対象の文字をハードコードされた`switch`文で処理する代わりに、`cssReplacementTable`という配列（スライス）を使用するように変更されました。これにより、エスケープルールの管理がより構造化され、拡張性が向上しています。

```go
// css.go に追加された cssReplacementTable
var cssReplacementTable = []string{
    0:    `\0`,
    '\t': `\9`,
    // ...
    '}':  `\7d`,
}
```
このテーブルは、特定のルーンに対応するCSSエスケープ文字列を定義しています。インデックスがルーンの値に対応し、値がエスケープ後の文字列となります。

### `html.go` の `htmlReplacer` 関数

```go
// 変更前
// for i, r := range s {
//     // ...
//     written = i + utf8.RuneLen(r)
// }

// 変更後
r, w := rune(0), 0
for i := 0; i < len(s); i += w {
    // Cannot use 'for range s' because we need to preserve the width
    // of the runes in the input. If we see a decoding error, the input
    // width will not be utf8.Runelen(r) and we will overrun the buffer.
    r, w = utf8.DecodeRuneInString(s[i:])
    if int(r) < len(replacementTable) {
        if repl := replacementTable[r]; len(repl) != 0 {
            b.WriteString(s[written:i])
            b.WriteString(repl)
            written = i + w // ここも utf8.RuneLen(r) ではなく w を使用
        }
    } else if badRunes {
        // No-op.
    } else if 0xfdd0 <= r && r <= 0xfdef || 0xfff0 <= r && r <= 0xffff {
        fmt.Fprintf(b, "%s&#x%x;", s[written:i], r)
        written = i + w // ここも utf8.RuneLen(r) ではなく w を使用
    }
}
```
`htmlReplacer`関数でも同様に、`for/range`ループから`utf8.DecodeRuneInString`ベースのイテレーションに切り替えることで、不正なUTF-8シーケンスに対する堅牢性を確保しています。コメントにも明記されているように、`for/range`ではデコードエラーが発生した場合にルーンの幅が正しく保持されず、バッファオーバーランを引き起こす可能性があるため、この変更が不可欠でした。

### `html_test.go` のテストケース

```go
// 変更前
// got, want = html.UnescapeString(got), strings.Replace(input, "\x00", "\ufffd", 1)

// 変更後
r := strings.NewReplacer("\x00", "\ufffd", "\x96", "\ufffd")
got, want = html.UnescapeString(got), r.Replace(input)
```
テストケースでは、不正なバイトシーケンス`\x96`を含む文字列が追加され、それが`\ufffd`に正しく置換されることを検証しています。`strings.NewReplacer`を使用することで、複数の置換ルールを効率的に適用できるようになりました。

これらの変更により、`html/template`パッケージは、不正なUTF-8シーケンスを含む入力に対しても安定して動作し、セキュリティと堅牢性が向上しました。

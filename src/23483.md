# [インデックス 23483] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）の挙動に関する修正です。具体的には、GCの開始条件に`preemptoff`フラグのチェックを追加することで、デッドロックの可能性を回避することを目的としています。変更されたファイルは`src/runtime/mgc.go`です。

## コミット

```
runtime: don't start GC if preemptoff is set

In order to avoid deadlocks, startGC avoids kicking off GC if locks
are held by the calling M. However, it currently fails to check
preemptoff, which is the other way to disable preemption.

Fix this by adding a check for preemptoff.

Reviewed-on: https://go-review.googlesource.com/10153
Reviewed-by: Russ Cox <rsc@golang.org>
```

## 元コミット内容

runtime: don't start GC if preemptoff is set

In order to avoid deadlocks, startGC avoids kicking off GC if locks
are held by the calling M. However, it currently fails to check
preemptoff, which is the other way to disable preemption.

Fix this by adding a check for preemptoff.
```

## 変更の背景

Goランタイムのガベージコレクタ（GC）は、プログラムの実行中にメモリを自動的に管理し、不要になったオブジェクトを回収します。GCが実行される際には、特定のランタイム内部状態が整合性を保っている必要があります。特に、ランタイム内部の重要なロックが保持されている間や、プリエンプション（横取り）が無効化されている間は、GCの開始がデッドロックや競合状態を引き起こす可能性があります。

このコミット以前の`startGC`関数は、呼び出し元のM（Machine、OSスレッドに相当）がランタイム内部のロックを保持している場合にはGCの開始を避けるようになっていました（`mp.locks > 1`のチェック）。しかし、プリエンプションを無効にするもう一つのメカニズムである`preemptoff`フラグが設定されている場合のチェックが欠けていました。

`preemptoff`が設定されている状態では、現在のGoroutineはプリエンプト（横取り）されず、Mは他のGoroutineに切り替わることなく実行を続けます。このような状況でGCが開始されると、GCが必要とするランタイム内部の同期メカニズムが機能せず、デッドロックが発生する危険性がありました。この修正は、この潜在的なデッドロックを回避するために、`preemptoff`が設定されている場合にもGCの開始を抑制することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスケジューラ、ガベージコレクション、および関連する内部構造に関するいくつかの前提知識が必要です。

### Goランタイムスケジューラ (M, P, G)

Goのスケジューラは、M（Machine）、P（Processor）、G（Goroutine）という3つの主要なエンティティで構成されます。

*   **G (Goroutine)**: Goにおける軽量な実行スレッドです。Goプログラムの並行処理の単位となります。
*   **M (Machine)**: オペレーティングシステム（OS）のスレッドに相当します。Goランタイムは、OSスレッド上でGoroutineを実行します。
*   **P (Processor)**: MとGを仲介する論理的なプロセッサです。Pは実行可能なGoroutineのキューを保持し、MにGoroutineを割り当てて実行させます。Pの数は通常、CPUのコア数に設定され、Goプログラムの並行実行能力を決定します。

`mp`は現在のM（OSスレッド）を指し、`getg()`は現在のG（Goroutine）を返します。`mp.g0`はスケジューラやGCなどのランタイム内部処理を実行するための特別なGoroutine（システムGoroutine）です。

### `mp.locks`

`mp.locks`は、現在のMが保持しているランタイム内部のロックの数を追跡するカウンタです。Goランタイムの内部処理では、データ構造の整合性を保つために多くのロックが使用されます。`mp.locks > 1`という条件は、Mがランタイム内部の重要なロックを保持していることを示し、この状態でのGC開始はデッドロックを引き起こす可能性があるため避けるべきです。

### `preemptoff`

`preemptoff`は、現在のGoroutineのプリエンプション（横取り）を一時的に無効にするためのフラグです。Goスケジューラは、長時間実行されるGoroutineが他のGoroutineの実行を妨げないように、定期的にGoroutineをプリエンプト（中断して他のGoroutineに切り替える）します。しかし、ランタイム内部のクリティカルなセクション（例えば、データ構造を更新している最中など）では、プリエンプションが途中で発生するとデータ破損やデッドロックにつながる可能性があります。このような場合に、ランタイムは`preemptoff`フラグを設定してプリエンプションを一時的に無効にします。

`preemptoff`が空文字列でない場合（`mp.preemptoff != ""`）、それはプリエンプションが無効になっていることを意味します。この状態では、現在のGoroutineは中断されず、Mは他のGoroutineに切り替わることもありません。

### ガベージコレクション (GC)

GoのGCは、並行マーク＆スイープ方式を採用しています。GCのサイクル中には、Goroutineの実行を一時停止したり、スケジューラと協調して動作したりする必要があります。特に、GCの「ストップ・ザ・ワールド」（STW）フェーズでは、すべてのGoroutineの実行が一時的に停止されます。`preemptoff`が設定されている状態でGCが開始されると、STWフェーズへの移行やGC関連のランタイム処理が適切に実行できなくなり、システム全体のデッドロックを引き起こす可能性があります。

## 技術的詳細

`startGC`関数は、ガベージコレクションを開始するかどうかを決定するGoランタイムの重要な関数です。この関数は、メモリ割り当て（`mallocgc`）のパスなど、様々な場所から呼び出される可能性があります。

GCを開始する前に、`startGC`はいくつかの条件をチェックして、GCを安全に実行できるかどうかを確認します。これらの条件は、ランタイムの整合性を保ち、デッドロックを回避するために非常に重要です。

元のコードでは、以下の条件でGCの開始を抑制していました。

*   `gp == mp.g0`: 現在のGoroutineがシステムGoroutine（`g0`）である場合。`g0`はスケジューラやGC自身などのランタイム内部処理を実行するため、その上でGCを開始するのは不適切です。
*   `mp.locks > 1`: 現在のMがランタイム内部のロックを複数保持している場合。これは、Mがクリティカルなセクションにいる可能性が高く、GCがデッドロックを引き起こす可能性があります。
*   `!memstats.enablegc`: GCが全体的に無効になっている場合。
*   `panicking != 0`: ランタイムがパニック状態にある場合。
*   `gcpercent < 0`: GCが設定で無効になっている場合。

このコミットでは、上記の条件に加えて、`mp.preemptoff != ""`という新しい条件が追加されました。これは、現在のMがプリエンプションを無効にしている状態であるかどうかをチェックします。

プリエンプションが無効になっているということは、現在のGoroutineが中断されることなく実行を継続することを保証している状態です。この状態でGCが開始され、特にSTWフェーズに入ろうとすると、プリエンプションが無効化されているGoroutineがSTWに参加できず、GCの進行がブロックされ、結果としてシステム全体がデッドロックに陥る可能性があります。

したがって、`mp.preemptoff != ""`のチェックを追加することで、ランタイムがプリエンプションを無効にしているクリティカルな期間中にGCが誤って開始されることを防ぎ、Goプログラムの安定性と堅牢性を向上させています。この修正により、GCの安全性チェックがより包括的になりました。

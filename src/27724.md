# [インデックス 27724] ファイルの概要

このコミットは、Goランタイムにおけるアーキテクチャ識別子「TheChar」の参照を完全に削除し、関連する定数名をより明確なものにリファクタリングすることを目的としています。具体的には、`sys.TheGoos` と `sys.TheGoarch` をそれぞれ `sys.GOOS` と `sys.GOARCH` に変更し、ヒープダンプ形式も更新して、もはや概念として存在しない `TheChar` の代わりに `sys.GOARCH` を含めるようにしています。

## 元コミット内容

Goランタイムから「TheChar」への残りの参照を削除します。
mdempsky氏の最近の変更後、これらはGoツリーに残された「TheChar」への唯一の参照です。文脈がなく、履歴を知らないと、これは混乱を招きます。
また、`sys.TheGoos` と `sys.TheGoarch` を `sys.GOOS` と `sys.GOARCH` にリネームします。
さらに、ヒープダンプ形式を、もはや概念ではない `TheChar` の代わりに `sys.GOARCH` を含めるように変更します。
Issue #15169 を更新します（ヒープダンプ形式の変更）。

## 変更の背景

このコミットの主な背景には、Goランタイムコードの可読性と保守性の向上が挙げられます。以前のコミットで「TheChar」という概念が段階的に廃止されていましたが、このコミットの時点ではまだいくつかの参照が残っていました。

「TheChar」は、Goのターゲットアーキテクチャを単一の文字で表現する内部的な識別子でした（例: '6'はamd64、'8'は386）。しかし、このような抽象的な文字表現は、特にGoの内部実装に詳しくない開発者にとっては直感的ではなく、コードの理解を妨げる要因となっていました。

また、`sys.TheGoos` と `sys.TheGoarch` といった定数名も、Goの標準的な命名規則（例: `runtime.GOOS`, `runtime.GOARCH`）と異なり、一貫性に欠けていました。これらの定数は、Goプログラムが実行されるオペレーティングシステムとアーキテクチャを示す重要な情報であり、その命名は明確であるべきです。

さらに、ヒープダンプはGoプログラムのメモリ使用状況をデバッグするために非常に重要な情報源です。ヒープダンプにアーキテクチャ情報を含める際、不明瞭な「TheChar」を使用するのではなく、より明確な `sys.GOARCH` を使用することで、ダンプされた情報の解釈が容易になり、デバッグ効率が向上します。

これらの変更は、Goランタイムの内部構造をよりクリーンで理解しやすいものにし、将来的な拡張やメンテナンスを容易にすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびランタイムに関する基本的な知識が必要です。

1.  **Goのクロスコンパイルと環境変数 (GOOS, GOARCH)**:
    Goは強力なクロスコンパイル機能を持ち、異なるオペレーティングシステム（GOOS）やアーキテクチャ（GOARCH）向けにバイナリを生成できます。`GOOS` はターゲットOS（例: `linux`, `windows`, `darwin`）、`GOARCH` はターゲットアーキテクチャ（例: `amd64`, `arm`, `386`）を示します。これらはGoのビルドプロセスにおいて非常に重要な環境変数であり、ランタイム内でも現在の実行環境を識別するために使用されます。

2.  **Goランタイム**:
    Goランタイムは、Goプログラムの実行を管理する低レベルのコンポーネント群です。これには、ガベージコレクタ、スケジューラ、メモリ管理、システムコールインターフェースなどが含まれます。ランタイムは、GoプログラムがOSやハードウェアとどのように相互作用するかを定義します。

3.  **ヒープダンプ**:
    ヒープダンプは、Goプログラムの実行中にヒープメモリ（動的に割り当てられたメモリ）の内容をスナップショットとして保存したものです。これは、メモリリークのデバッグやメモリ使用量のプロファイリングに不可欠なツールです。ヒープダンプには、オブジェクトのレイアウト、ポインタ、およびその他のメモリ関連情報が含まれます。

4.  **`src/runtime/internal/sys` パッケージ**:
    このパッケージは、Goランタイムが内部的に使用するシステム固有の定数や型を定義しています。これには、ポインタサイズ、キャッシュラインサイズ、ページサイズ、そしてOSやアーキテクチャに関する情報などが含まれます。

5.  **`go generate`**:
    `go generate` は、Goのソースコードからコードを生成するためのコマンドです。このコミットで変更されている `gengoos.go` のようなファイルは、`go generate` を使用して `zgoarch_*.go` や `zgoos_*.go` といったアーキテクチャ/OS固有の定数ファイルを自動生成するために使われます。

6.  **`TheChar` の歴史的背景**:
    Goの初期のバージョンでは、アーキテクチャを識別するために単一の文字が使われていました。例えば、`amd64` は `'6'`、`386` は `'8'`、`arm` は `'5'` といった具合です。これは、コンパイラやリンカの内部でアーキテクチャを簡潔に表現するための名残と考えられます。しかし、この表現は直感的ではなく、新しいアーキテクチャが追加されるたびに新しい文字を割り当てる必要があり、スケーラビリティや可読性の問題がありました。このため、より明確な文字列（例: "amd64"）や列挙型（例: `sys.AMD64`）に置き換える動きが進められていました。

## 技術的詳細

このコミットは、Goランタイムの内部でアーキテクチャとOSを識別する方法を近代化し、一貫性を持たせるための重要なリファクタリングです。

1.  **`TheChar` から `ArchFamilyType` への移行**:
    - 以前は、各アーキテクチャ（例: `386`, `amd64`, `arm`）は `TheChar` という定数で単一の文字（例: `'8'`, `'6'`, `'5'`）として識別されていました。
    - このコミットでは、`src/runtime/internal/sys/arch.go` という新しいファイルが導入され、`ArchFamilyType` という列挙型が定義されました。この列挙型は、`AMD64`, `ARM`, `ARM64`, `I386` など、より意味のある定数でアーキテクチャファミリーを表現します。
    - 各アーキテクチャ固有のファイル（例: `src/runtime/internal/sys/arch_386.go`）では、`TheChar` 定数が削除され、代わりに `ArchFamily = I386` のように `ArchFamilyType` の値が割り当てられるようになりました。これにより、コードの意図がはるかに明確になります。

2.  **`sys.TheGoos` と `sys.TheGoarch` のリネーム**:
    - `src/runtime/extern.go` では、Goプログラムからアクセス可能な `runtime.GOOS` と `runtime.GOARCH` 定数が、それぞれ `sys.TheGoos` と `sys.TheGoarch` を参照していました。
    - このコミットにより、これらの参照は `sys.GOOS` と `sys.GOARCH` に変更されました。
    - `src/runtime/internal/sys/gengoos.go` は、`go generate` コマンドによって `zgoos_*.go` および `zgoarch_*.go` ファイルを生成するスクリプトです。このスクリプトも更新され、生成される定数名が `TheGoos` から `GOOS`、`TheGoarch` から `GOARCH` に変更されました。
    - 結果として、`src/runtime/internal/sys/zgoos_*.go` および `src/runtime/internal/sys/zgoarch_*.go` の各ファイル内の定数名も新しい命名規則に準拠するように更新されました。これにより、Goランタイム全体でOSとアーキテクチャの識別子が一貫した命名を持つことになります。

3.  **ヒープダンプ形式の変更**:
    - `src/runtime/heapdump.go` は、ヒープダンプを生成する際のロジックを含んでいます。
    - 以前は、ヒープダンプのパラメータの一部として `sys.TheChar` が含まれていました。これは単一の文字であり、アーキテクチャを簡潔に表現していましたが、その意味は不明瞭でした。
    - このコミットでは、`dumpint(sys.TheChar)` が `dumpstr(sys.GOARCH)` に変更されました。これにより、ヒープダンプにはアーキテクチャを明確な文字列（例: "amd64"）で示す `sys.GOARCH` が含まれるようになり、ダンプの解析が容易になります。

4.  **ランタイムコード内の条件分岐の更新**:
    - `src/runtime/mgcmark.go` (ガベージコレクタのマークフェーズ) と `src/runtime/stack.go` (スタック管理) の両方で、以前は `sys.TheChar` を使用した `switch` ステートメントや `if` 条件がありました。
    - これらの箇所は、新しい `sys.ArchFamily` 列挙型を使用するように更新されました。例えば、`switch sys.TheChar { case '7': ... }` は `switch sys.ArchFamily { case sys.ARM64: ... }` に、`if sys.TheChar == '6' || sys.TheChar == '8' { ... }` は `if sys.ArchFamily == sys.AMD64 || sys.ArchFamily == sys.I386 { ... }` に変更されています。
    - この変更により、コードの意図がより明確になり、将来的に新しいアーキテクチャが追加された場合でも、より保守しやすい構造になります。

これらの変更は、Goランタイムの内部的な整合性を高め、開発者がコードを理解しやすくするための重要なステップです。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

-   **`src/runtime/extern.go`**: `runtime.GOOS` と `runtime.GOARCH` が参照する内部定数名を `sys.TheGoos` から `sys.GOOS`、`sys.TheGoarch` から `sys.GOARCH` へ変更。
-   **`src/runtime/heapdump.go`**: ヒープダンプに含めるアーキテクチャ情報を `sys.TheChar` から `sys.GOARCH` へ変更。
-   **`src/runtime/internal/sys/arch.go` (新規ファイル)**: `ArchFamilyType` 列挙型と、各アーキテクチャファミリーに対応する定数（`AMD64`, `ARM` など）を定義。
-   **`src/runtime/internal/sys/arch_*.go`**: 各アーキテクチャ固有のファイルで、`TheChar` 定数を削除し、新しく定義された `ArchFamily` 定数（例: `ArchFamily = I386`）に置き換え。
-   **`src/runtime/internal/sys/gengoos.go`**: `go generate` でOS/アーキテクチャ固有のファイルを生成する際に使用するテンプレートを更新し、`TheGoos` と `TheGoarch` の代わりに `GOOS` と `GOARCH` を生成するように変更。
-   **`src/runtime/internal/sys/zgoarch_*.go` および `src/runtime/internal/sys/zgoos_*.go`**: `gengoos.go` によって生成されるこれらのファイル内の定数名を `TheGoarch` から `GOARCH`、`TheGoos` から `GOOS` へ変更。
-   **`src/runtime/mgcmark.go`**: ガベージコレクタのスタックフレームスキャンロジックにおいて、アーキテクチャによる条件分岐を `sys.TheChar` から `sys.ArchFamily` に変更。
-   **`src/runtime/stack.go`**: スタックフレーム調整ロジックにおいて、アーキテクチャによる条件分岐を `sys.TheChar` から `sys.ArchFamily` に変更。

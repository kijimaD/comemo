# [インデックス 23566] ファイルの概要

このコミットは、Go言語の標準ライブラリ`archive/tar`パッケージにおいて、不正なtarヘッダが負のファイルサイズを報告した場合に発生する可能性のあるパニック（プログラムの異常終了）を防ぐための修正です。具体的には、`tar`アーカイブのヘッダから読み取られたファイルサイズが負の値であった場合に、パニックを引き起こす代わりに`ErrHeader`エラーを返すように変更することで、堅牢性を向上させています。

## 変更の背景

このコミットは、Go言語の`archive/tar`パッケージが、不正に作成された、または破損したtarアーカイブを処理する際の堅牢性を高めるために導入されました。具体的には、tarアーカイブのヘッダ情報に含まれるファイルサイズが、何らかの理由で負の値として解釈される場合に、Goプログラムがパニック（実行時エラーによる強制終了）を起こす問題に対処しています。

Goの`archive/tar`パッケージは、tarアーカイブを読み込む際に、各ファイルのメタデータ（ヘッダ）を解析します。このヘッダにはファイル名、パーミッション、そしてファイルサイズなどが含まれます。ファイルサイズは通常、オクタル（8進数）文字列として格納されており、`archive/tar`パッケージ内の`octal`関数によって`int64`型の数値に変換されます。

しかし、不正なtarアーカイブが、このサイズフィールドに無効なデータを含んでいた場合、`octal`関数が負の値を返す可能性がありました。以前の実装では、この負の値がそのまま`Header.Size`フィールドに設定され、その後のファイル読み込み処理などで不正なメモリアクセスやループの無限実行などが発生し、最終的にプログラムがパニックに陥る可能性がありました。

この問題は、GoのIssue #10959 および #10960 として報告されたと考えられます。これらの問題は、悪意のある、または単に破損したtarファイルを処理する際に、Goアプリケーションがクラッシュする脆弱性や不安定性につながる可能性がありました。このコミットは、このような状況下でのプログラムの安定性を確保することを目的としています。

## 前提知識の解説

### Tarアーカイブ形式

Tar（Tape ARchive）は、複数のファイルを一つのアーカイブファイルにまとめるためのファイル形式です。主にUnix系システムで利用され、ファイルのバックアップや配布によく使われます。Tarファイルは、連続する「ヘッダブロック」とそれに続く「データブロック」で構成されます。

*   **ヘッダブロック**: 各ファイルやディレクトリのメタデータ（ファイル名、サイズ、パーミッション、所有者、更新日時など）を格納します。通常512バイトの固定長です。
*   **データブロック**: ヘッダブロックに続く実際のファイルデータです。

ファイルサイズはヘッダブロック内の特定のフィールドにオクタル（8進数）文字列として格納されます。例えば、`00000000123`は10進数の83バイトを意味します。

### Goの`archive/tar`パッケージ

Go言語の標準ライブラリ`archive/tar`は、tarアーカイブの読み書きをサポートするパッケージです。
*   `tar.Reader`: tarアーカイブからファイルを順次読み出すための構造体です。`Next()`メソッドを呼び出すことで、アーカイブ内の次のファイルまたはディレクトリの`Header`を取得し、そのデータにアクセスできます。
*   `tar.Header`: tarアーカイブ内の個々のファイルまたはディレクトリのメタデータを表す構造体です。`Size`フィールドは、そのエントリのデータサイズ（バイト単位）を`int64`型で保持します。
*   `Reader.readHeader()`: `tar.Reader`の内部メソッドで、アーカイブから次のヘッダブロックを読み込み、`tar.Header`構造体に解析する役割を担います。この中で、ファイルサイズなどのオクタル文字列を数値に変換する処理が行われます。

### Goにおける`panic`とエラーハンドリング

Go言語では、予期せぬ異常事態や回復不能なエラーが発生した場合に`panic`が使用されます。`panic`が発生すると、現在の関数の実行が中断され、defer関数が実行された後、呼び出し元の関数へとスタックを遡りながら伝播します。最終的に`recover`で捕捉されない限り、プログラム全体がクラッシュします。

Goの設計思想では、ほとんどのエラーは`error`インターフェースを返すことで明示的に処理されるべきであり、`panic`はプログラムのバグや非常に深刻なシステムエラーなど、回復が困難な状況に限定して使用することが推奨されています。このコミットの背景にある問題は、不正な入力データによって`panic`が引き起こされるという、Goのエラーハンドリングの慣習に反する状況でした。

## 技術的詳細

このコミットの技術的な核心は、`archive/tar`パッケージの`Reader`がtarヘッダを解析する際の、ファイルサイズフィールドの処理にあります。

1.  **問題点**: 以前の実装では、`Reader.readHeader()`関数内で、tarヘッダから読み取られたファイルサイズを表すオクタル文字列が`tr.octal(s.next(12))`によって`int64`に変換され、`hdr.Size`に直接代入されていました。`tr.octal`関数は、不正な入力（例えば、非8進数文字やオーバーフローを引き起こすような非常に大きな値）が与えられた場合に、負の値を返す可能性があります。
    *   例えば、`tr.octal`が`int64`の最大値を超えるような8進数文字列を処理しようとした場合、オーバーフローによって負の値になることがあります。
    *   また、完全に不正なデータがサイズフィールドに存在した場合も、`octal`関数の内部ロジックによっては負の値を返す可能性がありました。
    この負の値が`hdr.Size`に設定されると、その後の`io.Copy`などのファイルデータ読み込み処理で、負のバイト数を読み込もうとしたり、内部的なバッファ計算が破綻したりして、最終的にランタイムパニックを引き起こしていました。

2.  **修正内容**: このコミットでは、`src/archive/tar/reader.go`の`readHeader`関数に以下のチェックが追加されました。

    ```go
    if hdr.Size < 0 {
        tr.err = ErrHeader
        return nil
    }
    ```
    このコードは、`hdr.Size`が`tr.octal`関数によって設定された直後に、その値が負であるかどうかをチェックします。
    *   もし`hdr.Size`が負であれば、それは不正なtarヘッダであることを意味します。
    *   この場合、`tr.err`フィールドに`ErrHeader`（`archive/tar`パッケージが定義する、不正なヘッダを示すエラー）を設定します。
    *   そして、`nil`の`*Header`を返します。これにより、呼び出し元（通常は`Reader.Next()`）は`nil`ヘッダと、`Reader`の内部エラー状態を通じて`ErrHeader`を受け取ることになります。

3.  **効果**: この変更により、不正な負のファイルサイズを持つtarヘッダが検出された場合でも、プログラムはパニックすることなく、`ErrHeader`という明確なエラーを返して処理を継続できるようになります。これにより、Goアプリケーションは不正なtarアーカイブに対してより堅牢になり、予期せぬクラッシュを防ぐことができます。

4.  **テストの追加**: 修正の正当性を保証するために、`src/archive/tar/reader_test.go`に`TestNegativeHdrSize`という新しいテストケースが追加されました。このテストは、意図的に負のファイルサイズを持つように細工された`neg-size.tar`というテスト用tarファイル（`src/archive/tar/testdata/neg-size.tar`）を読み込み、`Reader.Next()`が`ErrHeader`を返すことを検証します。これにより、修正が正しく機能していることが確認されます。

## コアとなるコードの解説

### `src/archive/tar/reader.go` の変更

`readHeader`関数は、tarアーカイブから次のヘッダブロックを読み込み、それを`*Header`構造体にパースする役割を担っています。

```go
 	hdr.Uid = int(tr.octal(s.next(8)))
 	hdr.Gid = int(tr.octal(s.next(8)))
 	hdr.Size = tr.octal(s.next(12)) // ここでファイルサイズを読み込み、int64に変換
+	if hdr.Size < 0 {              // 変換されたサイズが負の値であるかをチェック
+		tr.err = ErrHeader     // 負の値であれば、内部エラーをErrHeaderに設定
+		return nil             // ヘッダをnilとして返し、処理を中断
+	}
 	hdr.ModTime = time.Unix(tr.octal(s.next(12)), 0)
 	s.next(8) // chksum
 	hdr.Typeflag = s.next(1)[0]
```

*   `hdr.Size = tr.octal(s.next(12))`: この行で、tarヘッダから12バイトのオクタル文字列を読み取り（`s.next(12)`）、それを`tr.octal`関数で`int64`型の数値に変換し、`hdr.Size`フィールドに代入しています。
*   `if hdr.Size < 0`: 直前の変換結果である`hdr.Size`が負の値であるかをチェックします。tarファイル形式においてファイルサイズが負になることはありえないため、これは不正なヘッダであることを示します。
*   `tr.err = ErrHeader`: `hdr.Size`が負であった場合、`tar.Reader`構造体の内部エラーフィールド`tr.err`に`ErrHeader`を設定します。`ErrHeader`は`archive/tar`パッケージで定義されているエラーで、「不正なtarヘッダ」を意味します。
*   `return nil`: 負のサイズが検出された場合、有効なヘッダを生成できないため、`nil`の`*Header`を返して`readHeader`関数の実行を終了します。これにより、呼び出し元（通常は`Reader.Next()`）はエラーを検出し、パニックを回避できます。

### `src/archive/tar/reader_test.go` の変更

`TestNegativeHdrSize`関数は、この修正が正しく機能することを検証するためのテストケースです。

```go
func TestNegativeHdrSize(t *testing.T) {
	f, err := os.Open("testdata/neg-size.tar") // 負のファイルサイズを持つ不正なtarファイルを開く
	if err != nil {
		t.Fatal(err) // ファイルが開けなければテスト失敗
	}
	defer f.Close() // 関数終了時にファイルを閉じる

	r := NewReader(f) // tar.Readerを初期化
	_, err = r.Next() // 次のヘッダを読み込もうとする
	if err != ErrHeader { // 期待されるエラーはErrHeader
		t.Error("want ErrHeader, got", err) // ErrHeaderでなければテスト失敗
	}
	io.Copy(ioutil.Discard, r) // 残りのデータを読み捨てて、リーダーの状態をクリア
}
```

*   このテストは、`testdata/neg-size.tar`という特別に作成されたtarファイルを使用します。このファイルは、ヘッダのファイルサイズフィールドに、`tr.octal`関数が負の値を返すような不正なデータを含んでいます。
*   `r.Next()`を呼び出すことで、`readHeader`関数が実行され、不正なサイズが検出されることを期待します。
*   `if err != ErrHeader`のチェックにより、`r.Next()`が`ErrHeader`を返したかどうかを確認します。これにより、パニックが発生せず、適切なエラーが返されることが検証されます。

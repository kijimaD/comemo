## 元コミット内容

```
runtime: replace scanblock(0, 0, nil, nil) with drainworkbuf

scanblock(0, 0, nil, nil) was just a confusing way of saying

  wbuf = getpartialorempty()
  drainworkbuf(wbuf, true)

Make drainworkbuf accept a nil workbuf and perform the
getpartialorempty itself and replace all uses of scanblock(0, 0, nil,
nil) with direct calls to drainworkbuf(nil, true).
```

## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）におけるコードの明確性と保守性を向上させることを目的としています。具体的には、`scanblock(0, 0, nil, nil)`という特定の呼び出しパターンが、実際には`getpartialorempty()`で`workbuf`を取得し、その`workbuf`を`drainworkbuf(wbuf, true)`に渡すという一連の操作を意味しており、これが「紛らわしい」と判断されました。

このような冗長で分かりにくいコードは、将来のデバッグや機能拡張の際に誤解を招く可能性があります。そのため、`drainworkbuf`関数自体が`nil`の`workbuf`を受け取った場合に内部で`getpartialorempty`を呼び出すように変更し、既存の`scanblock(0, 0, nil, nil)`の呼び出しをより直接的な`drainworkbuf(nil, true)`に置き換えることで、コードの意図を明確にし、簡潔にすることが変更の背景にあります。これにより、GCのワークフローがより理解しやすくなります。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのガベージコレクション（GC）の基本的な仕組みと、それに用いられるいくつかの重要な概念を理解する必要があります。

1.  **Goのガベージコレクション (GC)**:
    GoのGCは、並行（concurrent）、トライカラー（tri-color）、マーク＆スイープ（mark-and-sweep）方式を採用しています。これは、プログラムの実行と並行してGCが動作し、アプリケーションの一時停止（STW: Stop-The-World）時間を最小限に抑えることを目指しています。
    *   **マークフェーズ (Mark Phase)**: GCの主要なフェーズの一つで、到達可能な（生きている）オブジェクトを特定します。ルートポインタ（グローバル変数やゴルーチンのスタックなど）から開始し、オブジェクトグラフを辿って、参照されているすべてのオブジェクトを「マーク」します。
    *   **スイープフェーズ (Sweep Phase)**: マークされなかった（到達不可能な）オブジェクトが占めていたメモリを解放します。

2.  **`scanblock`**:
    `scanblock`は、Go GCのマークフェーズにおける基本的な関数です。その目的は、与えられたメモリブロックをスキャンし、そこに含まれるポインタを特定することです。ポインタが見つかると、参照先のオブジェクトを「マーク」し、さらにスキャンが必要なオブジェクトとしてワークキューに追加します。これにより、すべての生きているオブジェクトが確実に識別されます。この関数は通常、`src/runtime/mgcmark.go`（または関連ファイル）で定義されています。

3.  **`workbuf` (ワークバッファ)**:
    並行マークフェーズ中、複数のゴルーチンがヒープをスキャンして生きているオブジェクトをマークします。これらのゴルーチンが発見したポインタを管理するために、`workbuf`（ワークバッファ）が使用されます。`workbuf`は、ゴルーチンがスキャンする必要があるオブジェクトへのポインタを一時的に格納するバッファです。この設計により、マーク処理中の競合が減少し、並行性が向上します。

4.  **`drainworkbuf`**:
    これは`workbuf`を処理する、つまり「ドレインする」操作を指します。ゴルーチンが`workbuf`を満たした場合、またはGCがより多くのポインタを処理する必要がある場合、`drainworkbuf`を呼び出して、そこからポインタを取り出し、グローバルなワークキューに追加したり、直接処理したりします。これにより、発見されたすべてのポインタが最終的にスキャンされることが保証されます。

5.  **`getpartialorempty`**:
    これは`workbuf`インスタンスの管理に関連する内部ヘルパー関数であると考えられます。その名前が示すように、ゴルーチンが使用する`workbuf`を取得するために使用されます。まず、部分的に満たされた（まだ処理すべきポインタが含まれているか、新しいポインタのためのスペースがある）`workbuf`を取得しようとします。そのようなバッファが利用できない場合は、ゴルーチンが新しいポインタを格納し始めるための空の`workbuf`を提供します。このメカニズムは、マークゴルーチン間でワークバッファを効率的に再利用し、分散するのに役立ちます。

これらの概念は、GoのGCがどのようにメモリを効率的に管理し、並行性を維持しているかを理解する上で不可欠です。

## 技術的詳細

このコミットの技術的な詳細は、主に`src/runtime/mgc.go`ファイル内の`drainworkbuf`関数の変更と、それに伴う`scanblock`関数の特定の呼び出しパターンの置き換えに集約されます。

変更の核心は以下の点にあります。

1.  **`drainworkbuf`関数の拡張**:
    変更前、`drainworkbuf`は常に有効な`workbuf`ポインタを引数として受け取ることを前提としていました。このコミットでは、`drainworkbuf`関数が`nil`の`workbuf`ポインタを受け入れるように拡張されます。
    *   `drainworkbuf`関数の冒頭に、`if wbuf == nil { wbuf = getpartialorempty(472) }`というコードが追加されます。
    *   この変更により、`drainworkbuf`は、もし`workbuf`が`nil`で渡された場合、自身で`getpartialorempty()`を呼び出して新しい`workbuf`を取得する責任を持つようになります。これにより、`scanblock(0, 0, nil, nil)`が内部で行っていた`getpartialorempty()`のロジックが`drainworkbuf`に統合され、呼び出し側での`workbuf`の事前取得が不要になります。

2.  **`scanblock(0, 0, nil, nil)`の置き換え**:
    Goランタイムの複数の箇所で、`scanblock(0, 0, nil, nil)`という特定の呼び出しパターンが使用されていました。この呼び出しは、実際には特定のメモリブロックをスキャンするのではなく、単に`workbuf`を取得してそれをドレインするという目的で使用されていました。
    *   `gchelper()`関数内: `scanblock(0, 0, nil, nil)`が`drainworkbuf(nil, true)`に置き換えられます。元のコードでは、`scanblock`の戻り値が`nil`でない場合に`throw`するチェックがありましたが、新しい`drainworkbuf(nil, true)`の呼び出しでは、このチェックは不要になります。
    *   `gcmark_m()`関数内: 同様に、`scanblock(0, 0, nil, nil)`が`drainworkbuf(nil, true)`に置き換えられます。ここでも、`scanblock`の戻り値のチェックが削除されます。
    *   `gc()`関数内: ここでも、`scanblock(0, 0, nil, nil)`が`drainworkbuf(nil, true)`に置き換えられ、戻り値のチェックが削除されます。

これらの変更により、コードの意図がより明確になります。`scanblock`は本来メモリブロックをスキャンするための関数であり、`workbuf`の取得とドレインという副作用的な目的で使用されるべきではありません。`drainworkbuf`が`workbuf`の取得ロジックを内包することで、GCのワークフローがより論理的かつ簡潔に表現されるようになります。これは、コードの可読性と保守性の向上に大きく貢献します。

## コアとなるコードの解説

このコミットは、`src/runtime/mgc.go`ファイル内のガベージコレクション関連のコードを簡素化し、明確化することを目的としています。

1.  **`drainworkbuf`関数の変更**:
    *   元の`drainworkbuf`関数は、常に有効な`workbuf`ポインタを期待していました。
    *   変更後、`drainworkbuf`関数の先頭に以下の3行が追加されました。
        ```go
        if wbuf == nil {
            wbuf = getpartialorempty(472)
        }
        ```
    *   この変更により、`drainworkbuf`関数は、引数として`nil`の`workbuf`を受け取った場合に、内部で`getpartialorempty()`を呼び出して、処理すべき`workbuf`を自身で取得するようになりました。これは、`scanblock(0, 0, nil, nil)`が以前に行っていた`workbuf`の取得ロジックを`drainworkbuf`に統合するものです。引数`472`は、`getpartialorempty`に渡されるマジックナンバーであり、特定のコンテキストやヒントを示している可能性がありますが、このコミットの範囲では詳細な意味は示されていません。

2.  **`scanblock(0, 0, nil, nil)`の置き換え**:
    *   `gchelper()`関数内:
        *   以前は`wbuf := scanblock(0, 0, nil, nil)`という呼び出しがあり、その後に`wbuf`が`nil`でない場合に`throw`するチェックがありました。これは、`scanblock`が`workbuf`を返すべきではないという意図を示しています。
        *   この行が`drainworkbuf(nil, true)`に置き換えられました。これにより、`scanblock`の呼び出しと、それに続く冗長な`wbuf`のチェックが削除され、コードがより簡潔になりました。コメントも`// blocks in getfull`と変更され、`drainworkbuf`が`getfull`でブロックする可能性があることを示唆しています。
    *   `gcmark_m()`関数内:
        *   ここでも同様に、`scanblock(0, 0, nil, nil)`の呼び出しと、それに続く`wbuf`のチェックが`drainworkbuf(nil, true)`に置き換えられました。関連するコメントも`// and repeat the above scanblock.`から`// and repeat the above drainworkbuf.`に更新されています。
    *   `gc()`関数内:
        *   `gc`関数の最後の方でも、`scanblock(0, 0, nil, nil)`の呼び出しと`wbuf`のチェックが`drainworkbuf(nil, true)`に置き換えられました。

これらの変更は、`scanblock`が本来のメモリブロックのスキャンという役割に集中し、`workbuf`の取得とドレインというロジックは`drainworkbuf`に一元化されることで、GCコードのモジュール性と可読性が向上することを示しています。これにより、将来のGCの改善やデバッグが容易になります。

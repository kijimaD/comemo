# [インデックス 23085] ファイルの概要

このコミットは、Goランタイムのガベージコレクション (GC) における `next_gc` の計算に関するバグ修正を扱っています。具体的には、`src/runtime/mgc.go` ファイルが変更されており、GCの次回のトリガーポイントを決定するロジックの堅牢性を向上させています。

    runtime: fix underflow in next_gc calculation
    
    Currently, it's possible for the next_gc calculation to underflow.
    Since next_gc is unsigned, this wraps around and effectively disables
    GC for the rest of the program's execution. Besides being obviously
    wrong, this is causing test failures on 32-bit because some tests are
    running out of heap.
    
    This underflow happens for two reasons, both having to do with how we
    estimate the reachable heap size at the end of the GC cycle.
    
    One reason is that this calculation depends on the value of heap_live
    at the beginning of the GC cycle, but we currently only record that
    value during a concurrent GC and not during a forced STW GC. Fix this
    by moving the recorded value from gcController to work and recording
    it on a common code path.
    
    The other reason is that we use the amount of allocation during the GC
    cycle as an approximation of the amount of floating garbage and
    subtract it from the marked heap to estimate the reachable heap.
    However, since this is only an approximation, it's possible for the
    amount of allocation during the cycle to be *larger* than the marked
    heap size (since the runtime allocates white and it's possible for
    these allocations to never be made reachable from the heap). Currently
    this causes wrap-around in our estimate of the reachable heap size,
    which in turn causes wrap-around in next_gc. Fix this by bottoming out
    the reachable heap estimate at 0, in which case we just fall back to
    triggering GC at heapminimum (which is okay since this only happens on
    small heaps).
    
    Fixes #10555, fixes #10556, and fixes #10559.

## 変更の背景

このコミットは、Goランタイムのガベージコレクション (GC) における `next_gc` の計算で発生するアンダーフローのバグを修正することを目的としています。`next_gc` は、次回のGCがトリガーされるヒープサイズを示す重要な値であり、これがアンダーフローを起こすと、符号なし整数であるため値がラップアラウンド（最大値から最小値に戻る）し、結果としてプログラムの残りの実行期間中、GCが実質的に無効になってしまうという深刻な問題を引き起こしていました。

この問題は、特に32ビット環境でのテスト失敗として顕在化しており、一部のテストがヒープ不足で実行不能になる事態が発生していました。アンダーフローは、GCサイクルの終了時に到達可能なヒープサイズを推定する方法に起因する、主に以下の2つの理由で発生していました。

1.  **`initialHeapLive` の記録の不備**: GCサイクルの開始時点での `memstats.heap_live` (ライブヒープサイズ) の値 (`initialHeapLive`) が、コンカレントGCの場合にのみ記録され、強制的なSTW (Stop-The-World) GCの場合には記録されていませんでした。`next_gc` の計算はこの `initialHeapLive` の値に依存するため、値が適切に記録されていない場合に問題が生じていました。
2.  **浮動ゴミの推定の不正確さ**: GCサイクル中に発生したアロケーション量 (`allocatedDuringCycle`) を浮動ゴミ（GC中に生成され、まだ回収されていないが到達不能になったオブジェクト）の近似値として使用し、マークされたヒープサイズ (`bytesMarked`) からこれを差し引いて到達可能なヒープサイズを推定していました。しかし、この近似が不正確な場合があり、GCサイクル中のアロケーション量がマークされたヒープサイズよりも大きくなる可能性がありました。これは、ランタイムが「白い」オブジェクト（GCの対象となるオブジェクト）をアロケートし、それらがヒープから到達不能になる可能性があるためです。この状況が発生すると、到達可能なヒープサイズの推定値が負になり、符号なし整数であるためにラップアラウンドが発生し、それが `next_gc` のラップアラウンドに繋がっていました。

これらの問題により、GCの動作が不安定になり、特にメモリ制約のある環境や特定のワークロードでプログラムのクラッシュや性能低下を引き起こす可能性がありました。

## 前提知識の解説

このコミットの理解には、Goランタイムのメモリ管理とガベージコレクションに関するいくつかの前提知識が必要です。

*   **ガベージコレクション (GC)**: Goは自動メモリ管理を採用しており、不要になったメモリ領域を自動的に解放するガベージコレクタを備えています。GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにしており、コンカレント（並行）に動作することで、アプリケーションの実行を長時間停止させることなくGCを実行しようとします。
    *   **コンカレントGC**: アプリケーションのゴルーチンと並行してGCのマークフェーズが実行されます。これにより、アプリケーションの停止時間を最小限に抑えます。
    *   **STW (Stop-The-World) GC**: GCの特定のフェーズ（例えば、マークの開始や終了、スイープの準備など）では、アプリケーションの全てのゴルーチンを一時的に停止させる必要があります。これをSTWフェーズと呼びます。
*   **`memstats`**: Goランタイムは、メモリ使用状況に関する様々な統計情報を `runtime.MemStats` 構造体で提供しています。このコミットに関連する主要なフィールドは以下の通りです。
    *   **`memstats.heap_live`**: 現在ライブ（到達可能）なヒープメモリのバイト数。GCサイクルの開始時や終了時に重要な指標となります。
    *   **`memstats.heap_marked`**: GCのマークフェーズで到達可能とマークされたヒープメモリのバイト数。
    *   **`memstats.next_gc`**: 次回のGCがトリガーされるヒープアロケーションの目標値（バイト数）。`heap_live` がこの値を超えるとGCが開始されます。
    *   **`heapminimum`**: GCがトリガーされる最小のヒープサイズ。ヒープが非常に小さい場合でも、GCが頻繁に発生しすぎないようにするための閾値です。
*   **`gcController`**: GoランタイムのGCを制御する主要な構造体の一つです。GCの目標値 (`heapGoal`) や、GCの進行状況に関する様々な統計を管理します。
*   **`work` 構造体**: GCの作業に関連する一時的な状態や統計を保持する構造体です。
*   **`triggerRatio`**: GCのトリガー比率。これは、到達可能なヒープサイズに対して、どれだけヒープが成長したら次回のGCをトリガーするかを決定する係数です。例えば、`triggerRatio` が1の場合、到達可能なヒープサイズの2倍になったらGCがトリガーされます。
*   **アンダーフロー (Underflow)**: 符号なし整数型で、その型の表現可能な最小値（通常は0）を下回る演算結果が生じた場合に発生します。結果はラップアラウンドし、その型の最大値に近い大きな値になります。例えば、`uint64` 型の変数 `x` が `0` のときに `x - 1` を計算すると、`uint64` の最大値になります。これがGCのトリガーポイント計算で発生すると、`next_gc` が非常に大きな値になり、GCが実質的に停止してしまいます。

## 技術的詳細

このコミットの技術的詳細は、`next_gc` の計算におけるアンダーフローの根本原因を特定し、それらを体系的に解決することにあります。

`next_gc` の計算は、主に以下の式に基づいています。

`memstats.next_gc = uint64(float64(memstats.heap_reachable) * (1 + gcController.triggerRatio))`

ここで、`memstats.heap_reachable` はGCサイクルの終了時に到達可能と推定されるヒープサイズです。この `heap_reachable` の推定が不正確であると、`next_gc` のアンダーフローに繋がります。

コミットメッセージは、`heap_reachable` の推定における2つの主要な問題点を指摘しています。

1.  **`initialHeapLive` の記録の一貫性欠如**:
    *   以前のバージョンでは、`gcControllerState.initialHeapLive` がGCサイクルの開始時の `memstats.heap_live` を記録していました。
    *   しかし、この記録はコンカレントGCの場合にのみ行われ、強制的なSTW GCの場合には行われていませんでした。
    *   `heapDistance` (GC目標ヒープサイズと初期ライブヒープサイズの差) の計算 (`int64(c.heapGoal) - int64(c.initialHeapLive)`) はこの値に依存するため、STW GCの場合に不正確な値が使用される可能性がありました。
    *   **修正**: `initialHeapLive` を `gcControllerState` から `work` 構造体 (`var work struct`) に移動しました。`work` 構造体はGCの様々なフェーズで共有されるグローバルな状態を保持します。そして、`gc()` 関数内でGCが開始される共通のコードパスで `work.initialHeapLive = memstats.heap_live` を記録するように変更されました。これにより、コンカレントGCとSTW GCの両方で `initialHeapLive` が常に正確に記録されるようになりました。

2.  **`heap_reachable` の計算における負の値の発生**:
    *   `heap_reachable` は、`work.bytesMarked` (マークされたバイト数) から `allocatedDuringCycle` (GCサイクル中にアロケートされたバイト数) を差し引くことで推定されていました。
    *   `allocatedDuringCycle` は `memstats.heap_live - work.initialHeapLive` で計算されます。
    *   問題は、`allocatedDuringCycle` が `work.bytesMarked` よりも大きくなる可能性があったことです。これは、GCサイクル中にアロケートされたメモリが、マークフェーズ中に到達不能になったり、そもそも到達可能にならなかったりする場合に発生します。例えば、一時的なオブジェクトが大量に生成され、GCがマークを完了する前にそれらがスコープ外になり、到達不能になるようなケースです。
    *   この場合、`work.bytesMarked - allocatedDuringCycle` の結果が負になり、符号なし整数である `memstats.heap_reachable` に代入される際にラップアラウンドが発生し、非常に大きな値になっていました。
    *   **修正**: `heap_reachable` の計算にガードを追加しました。`work.bytesMarked >= allocatedDuringCycle` の場合にのみ `work.bytesMarked - allocatedDuringCycle` を使用し、そうでない場合は `memstats.heap_reachable` を `0` に設定するように変更しました。
    *   `heap_reachable` が `0` に設定された場合、`next_gc` の計算は `uint64(float64(0) * (1 + gcController.triggerRatio))` となり、結果として `0` になります。しかし、`next_gc` は `heapminimum` (GCがトリガーされる最小ヒープサイズ) よりも小さくなることはないため、最終的には `heapminimum` にフォールバックされます。これは、ヒープが非常に小さい場合にのみ発生する状況であり、GCが `heapminimum` でトリガーされるのは許容される動作です。
    *   さらに、`next_gc` が最終的に負の値にならないように (`int64(memstats.next_gc) < 0` のチェック) 、そしてアンダーフローが発生した場合には `throw("next_gc underflow")` でランタイムパニックを発生させる防御的なチェックも追加されました。これは、デバッグを容易にし、予期せぬ動作を防ぐためのものです。

これらの変更により、`next_gc` の計算がより堅牢になり、特に32ビット環境でのヒープ不足によるテスト失敗が解消されました。

## コアとなるコードの解説

上記のコード変更は、`next_gc` の計算におけるアンダーフロー問題を解決するために、以下の主要なロジック変更を導入しています。

1.  **`initialHeapLive` の一元化と正確な記録**:
    *   `gcControllerState` から `initialHeapLive` フィールドが削除され、`work` 構造体に移されました。これは、`gcControllerState` がコンカレントGCとSTW GCで異なるライフサイクルを持つ可能性があり、`initialHeapLive` の記録が不完全になる原因となっていたためです。
    *   `work` 構造体はGCの全体的な作業状態を保持するため、`initialHeapLive` のようなGCサイクル全体で一貫して参照されるべき値の格納に適しています。
    *   `gc()` 関数は、GCが開始される共通のエントリポイントであるため、ここで `work.initialHeapLive = memstats.heap_live` を設定することで、コンカレントGCとSTW GCのどちらの場合でも、GCサイクルの開始時点の正確な `heap_live` 値が記録されるようになりました。
    *   これにより、`gcControllerState.revise()` で `heapDistance` を計算する際に、常に正確な `work.initialHeapLive` が参照されるようになり、`next_gc` の計算の基礎となる値の信頼性が向上しました。

2.  **`heap_reachable` の計算におけるアンダーフローの防止**:
    *   `gcMark()` 関数内で `memstats.heap_reachable` を計算する際、`allocatedDuringCycle := memstats.heap_live - work.initialHeapLive` という中間変数が導入されました。これは、GCサイクル中にアロケートされたバイト数を表します。
    *   最も重要な変更は、`if work.bytesMarked >= allocatedDuringCycle` という条件分岐が追加されたことです。
        *   この条件が真の場合、つまりマークされたバイト数がGCサイクル中のアロケーション量以上である場合、`memstats.heap_reachable = work.bytesMarked - allocatedDuringCycle` という通常の計算が行われます。
        *   この条件が偽の場合、つまり `allocatedDuringCycle` が `work.bytesMarked` よりも大きい場合（コミットメッセージで述べられているように、アロケートされたメモリが到達不能になったり、マークされる前に解放されたりするケース）、以前は負の値になりアンダーフローを引き起こしていました。この修正では、`else` ブロックで `memstats.heap_reachable = 0` と明示的に設定されます。
    *   `heap_reachable` が `0` に設定された場合、`next_gc` の計算結果も `0` になりますが、その後の `if memstats.next_gc < heapminimum` チェックにより、`next_gc` は `heapminimum` に設定されます。これは、ヒープが非常に小さい場合にGCが `heapminimum` でトリガーされるという、意図されたフォールバック動作です。これにより、不正確な推定によるGCの無効化が回避されます。

3.  **`next_gc` の最終的なアンダーフローチェック**:
    *   `memstats.next_gc` が `uint64` 型であるにもかかわらず、`int64(memstats.next_gc) < 0` というチェックが追加されています。これは、`uint64` の値が非常に大きく（ラップアラウンドによって）、それを `int64` にキャストした際に負の値として解釈される可能性があることを検出するための防御的なチェックです。
    *   もしこのような状況が発生した場合、`print` 文でデバッグ情報が出力され、`throw("next_gc underflow")` によってランタイムパニックが発生します。これにより、開発者は予期せぬGCの動作を早期に検出し、デバッグすることができます。

これらの変更は、GoランタイムのGCの堅牢性と正確性を大幅に向上させ、特にメモリ管理が厳密に求められる環境や、32ビットシステムでの安定性に寄与しています。

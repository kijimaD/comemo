## 変更の背景

このコミットの背景には、Goランタイムの内部関数 `getcallersp` のドキュメントコメントに誤りがあったという事実があります。`getcallersp` は呼び出し元のスタックポインタ (SP) を取得するための関数ですが、その使用例を示すコメント内で、誤って `getcallerpc` (呼び出し元のプログラムカウンタ PC を取得する関数) が記述されていました。この誤りは、コードの動作には影響を与えませんが、Goランタイムの内部実装を理解しようとする開発者にとって混乱を招く可能性がありました。

Goのソースコードは、その内部動作を理解するための重要な情報源であり、コメントはその理解を助ける上で不可欠です。特に、`runtime` パッケージのような低レベルな部分は、その動作が複雑であるため、正確なドキュメントが求められます。このコミットは、そのようなドキュメントの正確性を維持し、将来のメンテナンスや学習の障壁を下げることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムに関する基本的な概念を理解しておく必要があります。

*   **プログラムカウンタ (PC)**: プログラムカウンタは、次に実行される命令のアドレスを保持するCPUレジスタです。Goのコンテキストでは、`getcallerpc()` は呼び出し元の関数のリターンアドレス、つまり呼び出し元の関数が現在の関数から戻った後に実行を再開するアドレスを返します。これはスタックトレースの生成やデバッグにおいて重要な情報となります。

*   **スタックポインタ (SP)**: スタックポインタは、現在のスタックフレームの最上位（または最下位、アーキテクチャによる）を指すCPUレジスタです。Goのコンテキストでは、`getcallersp()` は呼び出し元の関数のスタックフレームのベースアドレス、またはその近くのアドレスを返します。スタックポインタは、関数のローカル変数や引数が格納されるスタック領域を管理するために使用されます。

*   **`unsafe.Pointer`**: Goの `unsafe` パッケージは、型安全性をバイパスして任意の型のポインタを扱うことを可能にします。`unsafe.Pointer` は、任意の型のポインタを保持できる特別なポインタ型であり、ポインタ演算や異なる型へのポインタ変換を可能にします。`getcallerpc` や `getcallersp` のような低レベルな関数では、メモリ上の特定のアドレスを直接操作する必要があるため、`unsafe.Pointer` が引数として使用されます。

*   **スタックフレーム**: 関数が呼び出されるたびに、その関数に必要な情報（引数、ローカル変数、リターンアドレスなど）を格納するための領域がスタック上に確保されます。この領域をスタックフレームと呼びます。関数呼び出しの連鎖は、スタック上に積み重ねられたスタックフレームの連続として表現されます。

*   **スタックアンワインディング**: スタックアンワインディングとは、現在の実行ポイントから呼び出し元の関数へとスタックフレームを遡っていくプロセスです。これは、パニック時のスタックトレースの生成、`defer` ステートメントの実行、およびガベージコレクションにおけるスタックのスキャンなど、Goランタイムの多くの重要な機能で利用されます。`getcallerpc` と `getcallersp` は、このスタックアンワインディングのプロセスにおいて、呼び出し元のPCとSPを特定するために内部的に使用されます。

これらの関数はGoの公開APIの一部ではなく、Goランタイムの内部実装のために存在します。通常、Go開発者がスタック情報を取得する必要がある場合は、`runtime/debug` パッケージの `debug.Stack()` や `runtime.Stack()` のような高レベルな関数を使用します。

## 技術的詳細

このコミットは、`src/runtime/stubs.go` ファイル内のコメントの修正に限定されています。このファイルは、Goランタイムの内部で使用される低レベルなスタブ関数やヘルパー関数の宣言を含んでいます。

問題となっていたのは、`getcallerpc` と `getcallersp` の使用例を示すコメントブロックでした。元のコメントは以下のようになっていました。

```go
//	func f(arg1, arg2, arg3 int) {
//		pc := getcallerpc(unsafe.Pointer(&arg1))
//		sp := getcallerpc(unsafe.Pointer(&arg2)) // <-- ここが誤り
//	}
```

ここで、`sp` を取得するために `getcallerpc` が誤って呼び出されていました。`sp` はスタックポインタを意味するため、正しくは `getcallersp` を使用すべきでした。このコミットは、この行を以下のように修正しました。

```go
//	func f(arg1, arg2, arg3 int) {
//		pc := getcallerpc(unsafe.Pointer(&arg1))
//		sp := getcallersp(unsafe.Pointer(&arg1)) // <-- ここが修正点
//	}
```

注目すべきは、`sp` を取得する際に `unsafe.Pointer(&arg1)` が引数として渡されている点です。これは、`getcallersp` が引数として渡されたポインタ（この場合は `arg1` のアドレス）を基準にして、呼び出し元のスタックポインタを計算することを示唆しています。`getcallerpc` も同様に、引数 `arg1` のアドレスを基準に呼び出し元のプログラムカウンタを特定します。

この修正は、Goランタイムの動作自体には何ら影響を与えません。これは純粋にドキュメントの正確性を高めるための変更であり、Goの内部コードベースの品質と可読性を維持するための継続的な努力の一環です。このような小さな修正が積み重なることで、Goのソースコードはより理解しやすく、メンテナンスしやすいものになります。

## コアとなるコードの解説

変更は `src/runtime/stubs.go` ファイルの234行目にあるコメント行です。

元のコードでは、`sp` (スタックポインタ) を取得する例として `getcallerpc(unsafe.Pointer(&arg2))` が記述されていました。これは論理的に誤りです。`getcallerpc` はプログラムカウンタ (PC) を取得する関数であり、スタックポインタ (SP) を取得するものではありません。また、`arg2` のアドレスを渡している点も、`arg1` のアドレスを渡している `pc` の取得と一貫性がありませんでした。

修正後のコードでは、この行が `sp := getcallersp(unsafe.Pointer(&arg1))` に変更されています。

1.  **`getcallerpc` から `getcallersp` への変更**: これにより、コメントが示す目的（スタックポインタの取得）と、実際に呼び出される関数が一致しました。`getcallersp` は、その名の通り、呼び出し元のスタックポインタを返します。
2.  **`unsafe.Pointer(&arg2)` から `unsafe.Pointer(&arg1)` への変更**: これは、`pc` の取得例と引数の一貫性を持たせるための変更です。どちらの関数も、引数として渡されたポインタを基準にして、呼び出し元のPCやSPを計算します。この例では、`arg1` のアドレスを基準点として使用することが意図されています。

この修正により、`getcallersp` のドキュメントコメントが正確になり、Goランタイムの内部動作を学習する開発者にとって、より明確で誤解の少ない情報が提供されるようになりました。

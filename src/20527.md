## 変更の背景

このコミットが行われた2014年当時、Go言語はバージョン1.4をリリースしており、次のメジャーバージョンであるGo 1.5の開発が視野に入っていました。Go言語の初期バージョンにおけるガベージコレクション（GC）は、"Stop-the-World" (STW) 方式を採用しており、GCが実行される間、アプリケーションの実行が完全に停止するという特性がありました。これは、特に大規模なアプリケーションや低レイテンシが求められるサービスにおいて、顕著な一時停止（ポーズタイム）を引き起こし、ユーザー体験やシステムのスループットに悪影響を与える可能性がありました。

Go開発チームは、このGCポーズタイムの問題をGo言語の主要な課題の一つとして認識しており、Go 1.5での抜本的な改善を目指していました。その改善策の中心となるのが、並行ガベージコレクションの導入です。並行GCは、アプリケーションの実行とGC処理の一部を並行して行うことで、STWポーズタイムを大幅に削減することを目的としています。

このコミットは、その並行GCの実装を担当するRick Hudson氏（GC分野の著名な研究者であり、以前はJava HotSpot VMのGC開発にも携わっていた）の作業を開始するための、専用の開発ブランチの立ち上げを意味しています。`dev.garbage`という空のファイルは、この新しい、重要な開発フェーズの開始を示すマーカーとして作成されました。

## 前提知識の解説

### ガベージコレクション (GC)

ガベージコレクションは、プログラムが動的に確保したメモリ領域のうち、もはやどの部分からも参照されなくなった（到達不可能になった）メモリ領域を自動的に解放し、再利用可能にするプロセスです。これにより、プログラマは手動でのメモリ管理の煩雑さから解放され、メモリリークのリスクを低減できます。

GCにはいくつかの主要な方式があります。

*   **Stop-the-World (STW) GC**: GCが実行される間、アプリケーションの実行を完全に停止させる方式です。実装が比較的単純ですが、アプリケーションの一時停止時間が長くなるという欠点があります。Go言語の初期バージョンはこの方式を採用していました。
*   **並行ガベージコレクション (Concurrent GC)**: GC処理の一部または大部分を、アプリケーションの実行と並行して行う方式です。これにより、アプリケーションの一時停止時間を大幅に短縮できますが、GC処理とアプリケーションのメモリ操作との間の同期や整合性を保つための複雑なメカニズム（ライトバリアなど）が必要になります。
*   **インクリメンタルGC**: GC処理を小さなチャンクに分割し、アプリケーションの実行と交互に行う方式です。STW時間を短縮できますが、全体のスループットが低下する可能性があります。
*   **コンカレント・インクリメンタルGC**: 並行GCとインクリメンタルGCの特性を組み合わせたものです。

### Go言語のGC（Go 1.4以前）

Go 1.4以前のGo言語のGCは、主にマーク＆スイープ方式のSTW GCでした。これは、GCが実行されるたびにGoプログラムのすべてのゴルーチン（軽量スレッド）が一時停止され、GCが完了するまで実行が再開されないことを意味します。ヒープサイズが大きくなるにつれて、このSTWポーズタイムは数ミリ秒から数十ミリ秒、場合によってはそれ以上に伸びることがあり、特にリアルタイム性が求められるアプリケーションや、多数のリクエストを処理するサーバーアプリケーションにおいて、レイテンシのスパイクとして顕在化していました。

### 並行ガベージコレクションの目的と利点

並行ガベージコレクションの主な目的は、GCによるアプリケーションの一時停止時間を最小限に抑えることです。これにより、以下のような利点が得られます。

*   **レイテンシの改善**: アプリケーションの応答性が向上し、ユーザー体験がスムーズになります。
*   **スループットの向上**: GCによる中断が減るため、アプリケーションがより多くの計算資源を有効活用できるようになります。
*   **予測可能性の向上**: GCポーズによるパフォーマンスの変動が少なくなり、システムの挙動がより予測可能になります。

Go 1.5で導入された並行GCは、Go言語がより広範なユースケース、特に高パフォーマンスと低レイテンシが要求されるサーバーサイドアプリケーションやクラウドネイティブな環境での利用を加速させる上で不可欠な進化でした。

## 技術的詳細

このコミット自体は、`dev.garbage`という空のファイルをリポジトリに追加する非常にシンプルなものです。しかし、その背後にある技術的な意味合いは非常に大きいです。このファイルは、Go 1.5で導入される画期的な並行ガベージコレクション（Concurrent GC）の実装に向けた、専用の開発ブランチの開始を示す「目印」として機能します。

Go 1.5の並行GCは、主に以下の技術的要素を組み合わせて実現されました。

1.  **三色マーキング (Tri-color marking)**:
    *   GCのマーキングフェーズにおいて、オブジェクトを「白（未訪問）」「灰（訪問済みだが子を未訪問）」「黒（訪問済みで子も訪問済み）」の三色に分類します。
    *   GCは、ルートセットから到達可能なオブジェクトを灰色にマークし、その後、灰色のオブジェクトを黒にマークしながらその子を灰色にマークしていくことで、到達可能なすべてのオブジェクトを黒にマークします。
    *   この方式は、並行GCの基盤となるアルゴリズムです。

2.  **ハイブリッドライトバリア (Hybrid Write Barrier)**:
    *   並行GCでは、GCがオブジェクトグラフを走査している最中に、アプリケーションがオブジェクトへの参照を変更する可能性があります。これにより、GCが誤って到達可能なオブジェクトを「ガベージ」と判断してしまう（浮動ガベージ）問題や、到達不可能なオブジェクトを「到達可能」と判断してしまう（メモリリーク）問題が発生する可能性があります。
    *   これを防ぐために「ライトバリア」と呼ばれるメカニズムが導入されます。ライトバリアは、アプリケーションがポインタを書き換える際に特定の処理を挿入するものです。
    *   Go 1.5で採用されたのは「ハイブリッドライトバリア」と呼ばれるもので、GCのマーキングフェーズ中にポインタの書き込みが行われた際に、古いオブジェクト（削除される参照元）と新しいオブジェクト（追加される参照先）の両方をGCが認識できるようにする仕組みです。これにより、STWポーズを最小限に抑えつつ、正確なGCを実現します。

3.  **STWポーズの削減**:
    *   Go 1.5のGCは、マーキングフェーズの大部分をアプリケーションと並行して実行します。STWが必要なのは、GCの開始時（ルートの走査と初期のマーク）と、GCの終了時（マークフェーズの完了とクリーンアップ）の非常に短い期間のみに限定されます。
    *   これにより、GCポーズタイムは従来の数ミリ秒から数十ミリ秒といったオーダーから、1ミリ秒未満、あるいはマイクロ秒オーダーにまで劇的に短縮されました。

2.  **ハイブリッドライトバリア (Hybrid Write Barrier)**:
    *   並行GCでは、GCがオブジェクトグラフを走査している最中に、アプリケーションがオブジェクトへの参照を変更する可能性があります。これにより、GCが誤って到達可能なオブジェクトを「ガベージ」と判断してしまう（浮動ガベージ）問題や、到達不可能なオブジェクトを「到達可能」と判断してしまう（メモリリーク）問題が発生する可能性があります。
    *   これを防ぐために「ライトバリア」と呼ばれるメカニズムが導入されます。ライトバリアは、アプリケーションがポインタを書き換える際に特定の処理を挿入するものです。
    *   Go 1.5で採用されたのは「ハイブリッドライトバリア」と呼ばれるもので、GCのマーキングフェーズ中にポインタの書き込みが行われた際に、古いオブジェクト（削除される参照元）と新しいオブジェクト（追加される参照先）の両方をGCが認識できるようにする仕組みです。これにより、STWポーズを最小限に抑えつつ、正確なGCを実現します。

3.  **STWポーズの削減**:
    *   Go 1.5のGCは、マーキングフェーズの大部分をアプリケーションと並行して実行します。STWが必要なのは、GCの開始時（ルートの走査と初期のマーク）と、GCの終了時（マークフェーズの完了とクリーンアップ）の非常に短い期間のみに限定されます。
    *   これにより、GCポーズタイムは従来の数ミリ秒から数十ミリ秒といったオーダーから、1ミリ秒未満、あるいはマイクロ秒オーダーにまで劇的に短縮されました。

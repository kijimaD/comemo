## 変更の背景

このコミットは、GoランタイムがPowerPC 64ビットアーキテクチャ上で実行される際に、`cas64`（Compare-and-Swap 64ビット）アトミック操作が正しく機能しないというバグを修正するために行われました。コミットメッセージにある「`cas64` was jumping to the wrong offset.」という記述が示す通り、`cas64`関数内の条件分岐命令が誤ったメモリオフセットにジャンプしてしまうという問題がありました。

Compare-and-Swap (CAS) は、並行プログラミングにおいて非常に重要なアトミック操作であり、共有メモリ上のデータをロックなしで安全に更新するために使用されます。もしCAS操作が正しく機能しない場合、データ競合が発生し、プログラムのクラッシュやデータの破損といった深刻な問題を引き起こす可能性があります。特にランタイムレベルでのアトミック操作の不具合は、Goの並行処理モデルの根幹を揺るがすため、早急な修正が必要でした。

このバグは、PowerPC 64ビットアーキテクチャに特有のアセンブリコードの実装ミスに起因しており、Goランタイムがこのアーキテクチャ上で安定して動作するために不可欠な修正でした。

## 前提知識の解説

### 1. Compare-and-Swap (CAS) アトミック操作

Compare-and-Swap (CAS) は、マルチスレッド環境における共有データの更新をアトミック（不可分）に行うためのCPU命令です。CASは以下の3つの引数を取ります。

*   **メモリ位置 (Memory Location)**: 更新対象のメモリアドレス。
*   **期待値 (Expected Value)**: メモリ位置に現在格納されていると期待される値。
*   **新値 (New Value)**: メモリ位置に書き込みたい新しい値。

CAS操作は、まずメモリ位置の現在の値と期待値を比較します。もし両者が一致すれば、メモリ位置の値を新値で更新します。この「比較」と「更新」のプロセス全体が単一の不可分な操作として実行されるため、他のスレッドがこの間にメモリ位置の値を変更することを防ぎます。もし現在の値が期待値と一致しない場合（つまり、他のスレッドが先に値を変更してしまった場合）、CAS操作は失敗し、メモリ位置の値は変更されません。CASはロックフリーなデータ構造やアルゴリズムを実装する上で不可欠なプリミティブです。

### 2. PowerPC/POWER64 アーキテクチャ

PowerPCはIBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャです。POWER64はその64ビット版であり、高性能なサーバーや組み込みシステムで広く利用されています。Go言語は、`ppc64`（ビッグエンディアン）および`ppc64le`（リトルエンディアン）を含むPowerPC 64ビットアーキテクチャを公式にサポートしています。

PowerPCアーキテクチャは、アトミック操作を実現するために、ロード・リンク/ストア・コンディショナル（LL/SC: Load-Link/Store-Conditional）命令ペアを使用します。これは、`lwarx`/`stwcx.`（32ビット）や`ldarx`/`stdcx.`（64ビット）といった命令で構成されます。

### 3. Goランタイムのアセンブリ言語

Go言語のランタイムは、パフォーマンスが非常に重要となる部分や、特定のアーキテクチャに依存する低レベルな操作（例えば、アトミック操作、スタック管理、スケジューリングなど）において、アセンブリ言語で記述されています。Goのアセンブリは、一般的なアセンブリ言語とは異なる独自の構文（Plan 9アセンブラの派生）を持っています。

*   **`src/runtime/asm_power64x.s`**: このファイルは、PowerPC 64ビットアーキテクチャ向けにGoランタイムの低レベルな機能（アトミック操作など）を実装したアセンブリコードを含んでいます。`.s`拡張子はアセンブリソースファイルを示します。

### 4. PowerPCのアトミック操作関連命令

*   **`LWAR` (Load Word and Reserve Indexed)**: 32ビットワードをメモリからロードし、そのアドレスに「予約」を設定します。これはLL/SCシーケンスの「ロード・リンク」部分です。
*   **`LDAR` (Load Doubleword and Reserve Indexed)**: `LWAR`の64ビット版で、64ビットダブルワードをロードし、アドレスに予約を設定します。
*   **`STWCCC` (Store Word Conditional to Cache Coherent)**: 32ビットワードを条件付きでストアします。これはLL/SCシーケンスの「ストア・コンディショナル」部分であり、先行する`LWAR`で設定された予約が有効であり、かつ他のプロセッサがそのメモリ位置を変更していない場合にのみストアが成功します。成功/失敗は条件レジスタに設定されます。
*   **`STDCCC` (Store Doubleword Conditional to Cache Coherent)**: `STWCCC`の64ビット版で、64ビットダブルワードを条件付きでストアします。

これらの命令は、`lwarx`/`stwcx.` および `ldarx`/`stdcx.` のGoアセンブリにおける表記です。

### 5. メモリバリア命令

*   **`SYNC` (Synchronize)**: 全ての先行するメモリ操作が完了し、他のプロセッサから可視になることを保証するフルメモリバリア命令です。これ以降の命令は、`SYNC`以前の全てのメモリ操作が完了するまで実行されません。
*   **`ISYNC` (Instruction Synchronize)**: 命令パイプラインをフラッシュし、これ以降の命令が新しいプロセッサの状態（例えば、特権レベルの変更など）を反映して実行されることを保証する命令バリアです。メモリ操作の完了は保証しません。

### 6. Goアセンブリのディレクティブ

*   **`TEXT runtime·cas(SB), NOSPLIT, $0-17`**:
    *   **`TEXT`**: 関数定義の開始を示すディレクティブです。
    *   **`runtime·cas(SB)`**: 関数名です。`runtime`はパッケージ名、`·`（中点）はパッケージと関数名の区切り、`(SB)`はシンボルが静的ベース（グローバル）であることを示します。
    *   **`NOSPLIT`**: この関数がスタックの拡張チェックを行わないことを示します。Goの関数は通常、スタックが足りなくなった場合に自動的に拡張されますが、ランタイムの低レベル関数ではこのチェックを省略することでオーバーヘッドを削減します。ただし、スタックオーバーフローのリスクが高まります。
    *   **`$0-17`**: `$0`はフレームサイズ（この関数が使用するスタック領域のサイズ）が0バイトであることを示し、`17`は引数の合計サイズが17バイトであることを示します。

### 7. 分岐命令

*   **`BNE` (Branch if Not Equal)**: 比較結果が等しくない場合に指定されたラベルに分岐します。
*   **`BR` (Branch)**: 無条件分岐です。

## 技術的詳細

このコミットの核心は、`src/runtime/asm_power64x.s`ファイル内の`runtime·cas`（32ビットCAS）と`runtime·cas64`（64ビットCAS）関数のアセンブリコードにおける分岐命令のオフセットの修正です。

元のコードでは、`BNE`（Branch if Not Equal）命令が、比較が失敗した場合にジャンプすべき正しいラベルではなく、相対オフセットで指定された誤った位置にジャンプしていました。これにより、CAS操作が期待通りに動作せず、アトミック性が損なわれる可能性がありました。

修正は、相対オフセットによる分岐を、明示的なラベルへの分岐に置き換えることで行われました。これにより、コードの可読性が向上し、かつ正確なジャンプ先が保証されます。

具体的には、以下の変更が行われました。

1.  **`runtime·cas` 関数:**
    *   `BNE 8(PC)` を `BNE cas_fail` に変更。これにより、比較が失敗した場合に`cas_fail`ラベルに正確にジャンプするようになります。
    *   `BNE -5(PC)` を `BNE cas_again` に変更。これは`STWCCC`命令が失敗した場合のリトライループであり、`cas_again`ラベルに正確にジャンプするようになります。
    *   `cas_again:` と `cas_fail:` という新しいラベルが導入されました。
    *   `BR -5(PC)` を `BR -5(PC)` のままですが、これは`cas_fail`からリターンする直前の無条件分岐であり、相対オフセットは変わっていません。しかし、`cas_fail`ラベルが導入されたことで、コードの構造が明確になりました。

2.  **`runtime·cas64` 関数:**
    *   `BNE 7(PC)` を `BNE cas64_fail` に変更。
    *   `BNE -5(PC)` を `BNE cas64_again` に変更。
    *   `cas64_again:` と `cas64_fail:` という新しいラベルが導入されました。
    *   `BR -4(PC)` を `BR -5(PC)` に変更。これは`cas64_fail`からリターンする直前の無条件分岐であり、オフセットが修正されました。

これらの変更により、CAS操作のロジックがPowerPC 64ビットアーキテクチャ上で意図通りに実行されるようになり、Goランタイムの安定性と信頼性が向上しました。

## コアとなるコードの解説

このセクションでは、上記の変更箇所を詳細に解説します。

### `runtime·cas` 関数 (32ビット CAS)

この関数は32ビットのCompare-and-Swap操作を実装しています。

```assembly
 	MOVD	p+0(FP), R3   // p (ポインタ) を R3 にロード
 	MOVW	old+8(FP), R4 // old (期待値) を R4 にロード
 	MOVW	new+12(FP), R5 // new (新値) を R5 にロード
+cas_again:             // 新しいラベル: CAS操作のリトライループの開始点
 	SYNC                   // メモリバリア: 全ての先行するメモリ操作の完了を保証
 	LWAR	(R3), R6       // R3が指すアドレスからワードをロードし、予約を設定 (R6に格納)
 	CMPW	R6, R4         // ロードした値 (R6) と期待値 (R4) を比較
-\tBNE	8(PC)          // 変更前: 等しくない場合、現在のPCから8バイト先に分岐
+\tBNE	cas_fail       // 変更後: 等しくない場合、cas_fail ラベルに分岐
 	STWCCC	R5, (R3)       // R5の値をR3が指すアドレスに条件付きでストア
-\tBNE	-5(PC)         // 変更前: ストアが失敗した場合、現在のPCから-5バイト先に分岐 (リトライ)
+\tBNE	cas_again      // 変更後: ストアが失敗した場合、cas_again ラベルに分岐 (リトライ)
 	MOVD	$1, R3         // 成功した場合、R3に1を設定 (戻り値 true)
 	SYNC                   // メモリバリア
 	ISYNC                  // 命令バリア
 	MOVB	R3, ret+16(FP) // 戻り値を格納
 	RETURN                 // 関数からリターン
+cas_fail:              // 新しいラベル: CAS操作が失敗した場合の処理
 	MOVD	$0, R3         // 失敗した場合、R3に0を設定 (戻り値 false)
 	BR	-5(PC)         // 無条件分岐: 戻り値を格納する命令にジャンプ
```

**変更点:**

*   `BNE 8(PC)` が `BNE cas_fail` に変更されました。これは、`LWAR`でロードした値と期待値が一致しなかった場合に、`cas_fail`という明確なラベルにジャンプするように修正されたものです。元の相対オフセット`8(PC)`は、コードの変更によって容易にずれてしまい、誤った場所にジャンプする原因となっていました。
*   `BNE -5(PC)` が `BNE cas_again` に変更されました。これは、`STWCCC`（条件付きストア）が失敗した場合に、CAS操作をリトライするために`cas_again`ラベルにジャンプするように修正されたものです。これにより、リトライループが正確に機能するようになります。
*   `cas_again:` と `cas_fail:` という新しいラベルが導入され、コードの構造とジャンプ先が非常に明確になりました。

### `runtime·cas64` 関数 (64ビット CAS)

この関数は64ビットのCompare-and-Swap操作を実装しています。基本的なロジックは`runtime·cas`と同じですが、64ビット値 (`MOVD`, `LDAR`, `STDCCC`) を扱います。

```assembly
 	MOVD	p+0(FP), R3    // p (ポインタ) を R3 にロード
 	MOVD	old+8(FP), R4  // old (期待値) を R4 にロード
 	MOVD	new+16(FP), R5 // new (新値) を R5 にロード
+cas64_again:           // 新しいラベル: CAS64操作のリトライループの開始点
 	SYNC                   // メモリバリア
 	LDAR	(R3), R6       // R3が指すアドレスからダブルワードをロードし、予約を設定 (R6に格納)
 	CMP	R6, R4         // ロードした値 (R6) と期待値 (R4) を比較
-\tBNE	7(PC)          // 変更前: 等しくない場合、現在のPCから7バイト先に分岐
+\tBNE	cas64_fail     // 変更後: 等しくない場合、cas64_fail ラベルに分岐
 	STDCCC	R5, (R3)       // R5の値をR3が指すアドレスに条件付きでストア
-\tBNE	-5(PC)         // 変更前: ストアが失敗した場合、現在のPCから-5バイト先に分岐 (リトライ)
+\tBNE	cas64_again    // 変更後: ストアが失敗した場合、cas64_again ラベルに分岐 (リトライ)
 	MOVD	$1, R3         // 成功した場合、R3に1を設定 (戻り値 true)
 	SYNC                   // メモリバリア
 	ISYNC                  // 命令バリア
 	MOVB	R3, ret+24(FP) // 戻り値を格納
 	RETURN                 // 関数からリターン
+cas64_fail:            // 新しいラベル: CAS64操作が失敗した場合の処理
 	MOVD	$0, R3         // 失敗した場合、R3に0を設定 (戻り値 false)
-\tBR	-4(PC)         // 変更前: 無条件分岐
+\tBR	-5(PC)         // 変更後: 無条件分岐 (オフセット修正)
```

**変更点:**

*   `BNE 7(PC)` が `BNE cas64_fail` に変更されました。`runtime·cas`と同様に、比較失敗時のジャンプ先が明確なラベルになりました。
*   `BNE -5(PC)` が `BNE cas64_again` に変更されました。`STDCCC`失敗時のリトライループのジャンプ先が明確なラベルになりました。
*   `cas64_again:` と `cas64_fail:` という新しいラベルが導入されました。
*   `BR -4(PC)` が `BR -5(PC)` に変更されました。これは`cas64_fail`からリターンする直前の無条件分岐のオフセット修正です。この修正は、新しいラベルの導入とコードの再配置に伴うものです。

これらの修正により、PowerPC 64ビット環境でのGoランタイムにおけるCAS操作の信頼性が大幅に向上しました。相対オフセットによる分岐は、コードの変更に非常に脆弱であり、このようなバグの温床となりがちです。明示的なラベルへの分岐は、堅牢性と可読性を高める上で非常に有効な手段です。

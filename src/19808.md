## 変更の背景

このコミットは、Goランタイムの特定の条件下で発生する「`unexpected return pc for runtime.newstackcall`」というエラーメッセージと、それに伴う`TestCgoDeadlockCrash`テストの断続的な失敗を修正するために導入されました。

報告された問題は、`cl/112640043`（おそらく関連する変更セット）が適用された環境で`TestCgoDeadlockCrash`を実行した際に顕在化しました。このエラーは、`runtime.newstackcall`というランタイム内部関数からのリターンアドレスが予期しない値になることを示しており、スタックの管理、特にスタックの拡張（スタック分割）に関連する問題を示唆していました。

コミットメッセージに含まれるスタックトレースは、`runtime.newstackcall`が`runtime.newstack()`から呼び出され、さらにその上位でスケジューリングやM（マシン）の初期化に関連する関数が連なっていることを示しています。これは、Goランタイムが新しいMを起動したり、既存のMのスタックを操作したりする際に、特定のスタックフレームの処理に誤りがあったことを示唆しています。

特に、`g0`スタック（Goランタイム内部の処理に使用される特別なスタック）のアンワインド（スタックトレースの生成）が問題の原因であると推測され、そのアンワインドが不要である、あるいは正しく行えない状況があることが示唆されています。また、既存のコメントが`mcache`（メモリキャッシュ）がない場合に`runtime.callers()`がクラッシュすると述べているが、CPUプロファイラは`mcache`なしでもトレースバックできるため、そのコメントが誤っているという指摘も含まれています。

## 前提知識の解説

このコミットの理解には、Goランタイムの以下の概念が不可欠です。

1.  **Goランタイムのスケジューラ (GMPモデル)**:
    *   **G (Goroutine)**: Goの軽量スレッド。ユーザーコードが実行される単位。
    *   **M (Machine)**: OSスレッドに相当。Gを実行する実際のOSスレッド。
    *   **P (Processor)**: MがGを実行するために必要な論理プロセッサ。MはPを介してGを実行します。
    *   Goランタイムは、これらの要素を組み合わせて、多数のGoroutineを効率的にOSスレッド上でスケジューリングします。

2.  **スタック管理とスタック分割 (Stack Splitting)**:
    *   GoのGoroutineは、最初は小さなスタック（通常2KB）で開始されます。
    *   関数呼び出しによってスタックが不足しそうになると、Goランタイムは自動的にスタックを拡張します。このプロセスを「スタック分割」と呼びます。
    *   スタック分割は、`runtime.morestack`や`runtime.newstack`といったランタイム内部関数によって行われます。
    *   `runtime.newstackcall`は、スタック分割の過程で、新しいスタックフレームをセットアップするために使用されるアセンブリレベルのヘルパー関数です。

3.  **`g0`スタック**:
    *   各M（OSスレッド）には、ユーザーGoroutineのスタックとは別に、特別なスタックが割り当てられています。これが`g0`スタックです。
    *   `g0`スタックは、Goランタイム自身の内部処理（スケジューリング、ガベージコレクション、スタック拡張など）を実行するために使用されます。
    *   ユーザーGoroutineのコードは`g0`スタック上では直接実行されません。`g0`スタックは、ユーザーGoroutineのスタックが切り替わる際の一時的なコンテキストとして機能します。

4.  **`mcache` (Memory Cache)**:
    *   Goランタイムは、メモリ割り当ての効率を高めるために、P（プロセッサ）ごとにローカルなメモリキャッシュ（`mcache`）を持っています。
    *   これにより、Goroutineがメモリを割り当てる際に、グローバルなヒープロックを避けることができます。

5.  **`runtime.callers()`**:
    *   Goの標準ライブラリには、現在のGoroutineのコールスタックをトレースするための`runtime.Callers`関数があります。
    *   ランタイム内部では、これに相当する`runtime.callers()`（C言語で実装）が使用され、スタックフレームを遡って呼び出し元の情報を取得します。このプロセスは「スタックアンワインド」と呼ばれます。

6.  **リターンPC (Return Program Counter)**:
    *   関数が呼び出された後、呼び出し元に戻るべき命令のアドレス（プログラムカウンタ）を指します。スタックフレームには、このリターンPCが保存されています。
    *   「`unexpected return pc`」は、スタックトレースを生成する際に、期待されるリターンPCが見つからない、または不正な値である場合に発生します。これは、スタックフレームの構造が壊れているか、スタックアンワインドのロジックに問題があることを示唆します。

## 技術的詳細

この問題の核心は、`runtime.newstackcall`が関与するスタック分割の際に、`g0`スタックのアンワインドが正しく行われない、または行われるべきではない状況で試みられていた点にあります。

コミットメッセージのスタックトレースを見ると、`runtime.newstackcall`が呼び出された後、`runtime.newstack()`、`runtime.gosched0()`、`schedule()`、`startm()`、`mcommoninit()`といった関数が連なっています。これは、新しいM（OSスレッド）が起動され、その初期化プロセスの中でスタック分割が発生し、`runtime.callers()`が呼び出されていることを示唆しています。

`mcommoninit`関数は、Mの初期化の一部として`runtime.callers()`を呼び出し、Mの作成スタック（`mp->createstack`）を記録しようとします。しかし、この処理が`g0`スタック上で行われている場合、問題が発生します。

*   **`g0`スタックの特殊性**: `g0`スタックは、ユーザーGoroutineのスタックとは異なり、ランタイム内部の非常に低レベルな処理のために使われます。そのスタックフレームの構造は、通常のユーザーGoroutineのスタックとは異なる場合があり、特にスタック分割のような操作の最中では、`runtime.callers()`が期待する形式ではない可能性があります。
*   **「`unexpected return pc`」の原因**: `runtime.newstackcall`はアセンブリで実装されており、スタックフレームの操作を直接行います。スタック分割の過程で、`g0`スタック上で`runtime.newstackcall`が呼び出された際、そのリターンPCが`runtime.callers()`が期待する形式でなかったため、予期せぬリターンPCとして検出され、エラーが発生したと考えられます。
*   **`g0`スタックのアンワインドの不要性**: コミットメッセージにある「So don't unwind g0 stack.」という記述は、`g0`スタックのトレースバックはユーザーにとって意味がなく、また、その特殊性から信頼できるスタックトレースを生成することが難しい、という認識を示しています。`g0`スタックはランタイム内部の遷移を反映するものであり、ユーザーがデバッグするようなコールスタックとは性質が異なります。
*   **`mcache`に関するコメントの修正**: 以前のコードには「`If there is no mcache runtime·callers() will crash, and we are most likely in sysmon thread so the stack is senseless anyway.`」というコメントがありました。これは、`mcache`がない状況（例えば、システムモニタースレッドなど）では`runtime.callers()`がクラッシュするという誤った前提に基づいています。コミットメッセージでは「CPU profiler does that.」と指摘されており、CPUプロファイラは`mcache`なしでもスタックトレースを取得できるため、このコメントが誤りであることが示されています。この指摘は、`runtime.callers()`の動作に関する理解の修正を促すものです。

このコミットは、`g0`スタックの特殊性を考慮し、`mcommoninit`関数内で`runtime.callers()`を呼び出す条件を修正することで、この問題を解決しようとしています。

## コアとなるコードの解説

変更は`mcommoninit`関数内の条件分岐にあります。

**変更前**:
```c
	// If there is no mcache runtime·callers() will crash,
	// and we are most likely in sysmon thread so the stack is senseless anyway.
	if(g->m->mcache)
		runtime·callers(1, mp->createstack, nelem(mp->createstack));
```
変更前は、現在のM（`g->m`）に`mcache`が存在する場合にのみ`runtime.callers()`を呼び出してスタックトレースを取得していました。コメントは、`mcache`がないとクラッシュする可能性があり、またシステムモニタースレッドのような状況ではスタックが無意味であると述べていました。しかし、この前提はCPUプロファイラの動作によって誤りであることが示されました。

**変更後**:
```c
	// g0 stack won't make sense for user (and is not necessary unwindable).
	if(g != g->m->g0)
		runtime·callers(1, mp->createstack, nelem(mp->createstack));
```
変更後、条件は`g != g->m->g0`となりました。これは、「現在のGoroutine (`g`) が、現在のM (`g->m`) の`g0`スタック上で実行されているGoroutineではない場合」に`runtime.callers()`を呼び出すことを意味します。

この変更の意図は以下の通りです。
*   **`g0`スタックの除外**: `g0`スタックはランタイム内部の処理専用であり、そのスタックトレースはユーザーにとって意味がなく、また、スタック分割などの低レベルな操作の最中では正しくアンワインドできない可能性があるため、`g0`スタック上での`runtime.callers()`の呼び出しを避けるようにしました。
*   **正確な条件**: `mcache`の有無ではなく、現在の実行コンテキストが`g0`スタック上であるかどうかを判断基準とすることで、より正確にスタックトレースを取得すべき状況を特定しています。これにより、`unexpected return pc`エラーの発生を防ぎ、同時にCPUプロファイラのような`mcache`に依存しないトレースバックの可能性も考慮に入れています。

この修正により、`runtime.newstackcall`が`g0`スタック上で実行され、その結果として`runtime.callers()`が不正なリターンPCに遭遇するシナリオが回避され、`TestCgoDeadlockCrash`の断続的な失敗が解消されました。

    *   「`unexpected return pc`」は、スタックトレースを生成する際に、期待されるリターンPCが見つからない、または不正な値である場合に発生します。これは、スタックフレームの構造が壊れているか、スタックアンワインドのロジックに問題があることを示唆します。

## 技術的詳細

この問題の核心は、`runtime.newstackcall`が関与するスタック分割の際に、`g0`スタックのアンワインドが正しく行われない、または行われるべきではない状況で試みられていた点にあります。

コミットメッセージのスタックトレースを見ると、`runtime.newstackcall`が呼び出された後、`runtime.newstack()`、`runtime.gosched0()`、`schedule()`、`startm()`、`mcommoninit()`といった関数が連なっています。これは、新しいM（OSスレッド）が起動され、その初期化プロセスの中でスタック分割が発生し、`runtime.callers()`が呼び出されていることを示唆しています。

`mcommoninit`関数は、Mの初期化の一部として`runtime.callers()`を呼び出し、Mの作成スタック（`mp->createstack`）を記録しようとします。しかし、この処理が`g0`スタック上で行われている場合、問題が発生します。

*   **`g0`スタックの特殊性**: `g0`スタックは、ユーザーGoroutineのスタックとは異なり、ランタイム内部の非常に低レベルな処理のために使われます。そのスタックフレームの構造は、通常のユーザーGoroutineのスタックとは異なる場合があり、特にスタック分割のような操作の最中では、`runtime.callers()`が期待する形式ではない可能性があります。
*   **「`unexpected return pc`」の原因**: `runtime.newstackcall`はアセンブリで実装されており、スタックフレームの操作を直接行います。スタック分割の過程で、`g0`スタック上で`runtime.newstackcall`が呼び出された際、そのリターンPCが`runtime.callers()`が期待する形式でなかったため、予期せぬリターンPCとして検出され、エラーが発生したと考えられます。
*   **`g0`スタックのアンワインドの不要性**: コミットメッセージにある「So don't unwind g0 stack.」という記述は、`g0`スタックのトレースバックはユーザーにとって意味がなく、また、その特殊性から信頼できるスタックトレースを生成することが難しい、という認識を示しています。`g0`スタックはランタイム内部の遷移を反映するものであり、ユーザーがデバッグするようなコールスタックとは性質が異なります。
*   **`mcache`に関するコメントの修正**: 以前のコードには「`If there is no mcache runtime·callers() will crash, and we are most likely in sysmon thread so the stack is senseless anyway.`」というコメントがありました。これは、`mcache`がない状況（例えば、システムモニタースレッドなど）では`runtime.callers()`がクラッシュするという誤った前提に基づいています。コミットメッセージでは「CPU profiler does that.」と指摘されており、CPUプロファイラは`mcache`なしでもスタックトレースを取得できるため、このコメントが誤りであることが示されています。この指摘は、`runtime.callers()`の動作に関する理解の修正を促すものです。

このコミットは、`g0`スタックの特殊性を考慮し、`mcommoninit`関数内で`runtime.callers()`を呼び出す条件を修正することで、この問題を解決しようとしています。

## コアとなるコードの解説

変更は`mcommoninit`関数内の条件分岐にあります。

**変更前**:
```c
	// If there is no mcache runtime·callers() will crash,
	// and we are most likely in sysmon thread so the stack is senseless anyway.
	if(g->m->mcache)
		runtime·callers(1, mp->createstack, nelem(mp->createstack));
```
変更前は、現在のM（`g->m`）に`mcache`が存在する場合にのみ`runtime.callers()`を呼び出してスタックトレースを取得していました。コメントは、`mcache`がないとクラッシュする可能性があり、またシステムモニタースレッドのような状況ではスタックが無意味であると述べていました。しかし、この前提はCPUプロファイラの動作によって誤りであることが示されました。

**変更後**:
```c
	// g0 stack won't make sense for user (and is not necessary unwindable).
	if(g != g->m->g0)
		runtime·callers(1, mp->createstack, nelem(mp->createstack));
```
変更後、条件は`g != g->m->g0`となりました。これは、「現在のGoroutine (`g`) が、現在のM (`g->m`) の`g0`スタック上で実行されているGoroutineではない場合」に`runtime.callers()`を呼び出すことを意味します。

この変更の意図は以下の通りです。
*   **`g0`スタックの除外**: `g0`スタックはランタイム内部の処理専用であり、そのスタックトレースはユーザーにとって意味がなく、また、スタック分割などの低レベルな操作の最中では正しくアンワインドできない可能性があるため、`g0`スタック上での`runtime.callers()`の呼び出しを避けるようにしました。
*   **正確な条件**: `mcache`の有無ではなく、現在の実行コンテキストが`g0`スタック上であるかどうかを判断基準とすることで、より正確にスタックトレースを取得すべき状況を特定しています。これにより、`unexpected return pc`エラーの発生を防ぎ、同時にCPUプロファイラのような`mcache`に依存しないトレースバックの可能性も考慮に入れています。

この修正により、`runtime.newstackcall`が`g0`スタック上で実行され、その結果として`runtime.callers()`が不正なリターンPCに遭遇するシナリオが回避され、`TestCgoDeadlockCrash`の断続的な失敗が解消されました。

# [インデックス 26627] ファイルの概要

このコミットは、Go 1.7リリースにおいて、`GO15VENDOREXPERIMENT` 環境変数のサポートを完全に削除し、Goのモジュールベンダー機能（vendoring）を常に有効にする変更を導入します。これにより、Goの依存関係管理におけるベンダー機能が実験段階を終え、標準機能として確立されました。

## 変更の背景

Go言語の初期の依存関係管理は、主に`GOPATH`というワークスペースモデルに依存していました。しかし、このモデルでは、プロジェクトごとに異なるバージョンのライブラリを使用したり、依存関係の再現性を保証したりすることが困難でした。この課題を解決するため、Go 1.5で「ベンダー機能（vendoring）」が実験的に導入されました。

ベンダー機能は、プロジェクトのルートディレクトリに`vendor`という特別なディレクトリを作成し、その中にプロジェクトが依存する外部パッケージのコピーを配置することで、依存関係をプロジェクトローカルに管理する仕組みです。これにより、ビルドの再現性が向上し、ネットワーク接続がない環境でもビルドが可能になるなどのメリットがありました。

Go 1.5では、このベンダー機能はデフォルトでは無効化されており、`GO15VENDOREXPERIMENT=1`という環境変数を設定することで明示的に有効にする必要がありました。これは、新しい機能に対するユーザーからのフィードバックを収集し、潜在的な問題を特定するための「実験」として位置づけられていました。

Go 1.6では、ベンダー機能はデフォルトで有効化されましたが、`GO15VENDOREXPERIMENT=0`を設定することで無効にすることも可能でした。これは、実験段階から一歩進んで、より多くのユーザーに利用を促しつつ、まだオプトアウトの選択肢を残すという段階でした。

本コミットは、Go 1.6のリリースノートで予告されていた通り、Go 1.7で`GO15VENDOREXPERIMENT`環境変数のサポートを完全に削除し、ベンダー機能を常に有効にするためのものです。これは、ベンダー機能が十分に安定し、Goの標準的な依存関係管理メカニズムとして確立されたことを意味します。この変更により、Goのビルドシステムはより予測可能で一貫性のある動作をするようになります。

## 前提知識の解説

### Goの依存関係管理とGOPATH

Go言語のプロジェクトは、伝統的に`GOPATH`という環境変数で指定されたワークスペース内で管理されていました。`GOPATH`は、Goのソースコード、コンパイル済みパッケージ、実行可能バイナリが配置されるディレクトリのルートを指します。プロジェクトの依存関係は、`GOPATH/src`以下に配置され、`go get`コマンドによってダウンロードされていました。

しかし、`GOPATH`モデルにはいくつかの課題がありました。
*   **依存関係のバージョン管理の困難さ**: 複数のプロジェクトが同じパッケージの異なるバージョンに依存する場合、`GOPATH`ではこれを適切に管理することが困難でした。
*   **ビルドの再現性**: `go get`は常に最新バージョンを取得しようとするため、時間の経過とともにビルド結果が変化する可能性がありました。
*   **オフラインビルドの課題**: 依存関係が`GOPATH`外にある場合、ネットワーク接続がないとビルドできませんでした。

### ベンダー機能 (Vendoring)

これらの課題を解決するために導入されたのがベンダー機能です。ベンダー機能では、プロジェクトのルートディレクトリ直下に`vendor`という名前のディレクトリを作成し、その中にプロジェクトが直接的または間接的に依存するすべての外部パッケージのソースコードをコピーして配置します。

Goのビルドツール（`go build`, `go install`, `go test`など）は、パッケージをインポートする際に、まず現在のパッケージの`vendor`ディレクトリ内を検索し、次に`GOPATH`を検索します。これにより、プロジェクトは自身の依存関係をローカルに隔離し、以下のメリットを享受できます。
*   **ビルドの再現性**: `vendor`ディレクトリ内のコードは固定されるため、ビルド結果が常に同じになります。
*   **オフラインビルド**: 依存関係がローカルにあるため、ネットワーク接続なしでビルドできます。
*   **依存関係の衝突回避**: 各プロジェクトが独自の依存関係セットを持つため、グローバルな`GOPATH`でのバージョン衝突を回避できます。

### `GO15VENDOREXPERIMENT` 環境変数

`GO15VENDOREXPERIMENT`は、Go 1.5でベンダー機能を実験的に導入する際に使用された環境変数です。
*   **Go 1.5**: `GO15VENDOREXPERIMENT=1`を設定した場合のみベンダー機能が有効。
*   **Go 1.6**: ベンダー機能がデフォルトで有効化され、`GO15VENDOREXPERIMENT=0`を設定することで無効にできた。
*   **Go 1.7 (本コミット以降)**: `GO15VENDOREXPERIMENT`は完全に削除され、ベンダー機能は常に有効となる。

この環境変数は、新しい機能の導入におけるGo開発チームのアプローチを示しています。まず実験的に導入し、ユーザーからのフィードバックと安定性を確認した上で、段階的にデフォルト化し、最終的に標準機能として統合するというプロセスです。

## 技術的詳細

このコミットの主要な目的は、`GO15VENDOREXPERIMENT`環境変数とその関連ロジックをGoツールチェーンから完全に削除することです。これにより、ベンダー機能がGo 1.7以降で常に有効な標準動作となります。

具体的な変更点は以下の通りです。

1.  **リリースノートの更新 (`doc/go1.7.txt`)**:
    Go 1.7のリリースノートに、「`cmd/go: GO15VENDOREXPERIMENT gone, assumed on`」（`GO15VENDOREXPERIMENT`は廃止され、常に有効と見なされる）という記述が追加されました。これは、この変更がユーザーに与える影響を公式にアナウンスするものです。

2.  **ドキュメントの削除 (`src/cmd/go/alldocs.go`, `src/cmd/go/help.go`)**:
    `GO15VENDOREXPERIMENT`に関する説明文が、`go help gopath`や`go help environment`で表示されるドキュメントから削除されました。これは、この環境変数がもはや意味を持たないため、ユーザーを混乱させないようにするためです。

3.  **環境変数処理の削除 (`src/cmd/go/env.go`)**:
    `src/cmd/go/env.go`ファイル内で、`GO15VENDOREXPERIMENT`の値を読み取り、`mkEnv()`関数で環境変数リストに含めるロジックが削除されました。これにより、`go env`コマンドの出力からもこの変数が消えます。

4.  **ベンダー機能制御変数の削除 (`src/cmd/go/pkg.go`)**:
    `src/cmd/go/pkg.go`ファイル内に存在したグローバル変数`go15VendorExperiment`が削除されました。この変数は、`os.Getenv("GO15VENDOREXPERIMENT") != "0"`の結果に基づいてベンダー機能の有効/無効を制御していました。この変数の削除により、ベンダー機能の有効/無効を切り替える手段がなくなります。

5.  **ベンダー関連ロジックの簡素化 (`src/cmd/go/pkg.go`, `src/cmd/go/vcs.go`)**:
    `go15VendorExperiment`変数が削除されたことに伴い、この変数に依存していた条件分岐が削除または簡素化されました。
    *   `src/cmd/go/pkg.go`内の`loadImport`関数や`vendoredImportPath`関数では、`!go15VendorExperiment`という条件が削除され、ベンダー機能が常に有効である前提で動作するようになりました。例えば、`build.IgnoreVendor`フラグの適用ロジックが変更され、`GO15VENDOREXPERIMENT`の状態に左右されなくなりました。
    *   `src/cmd/go/vcs.go`内の`create`, `download`, `tagSync`関数では、`!go15VendorExperiment && strings.Contains(cmd, "submodule")`という条件が`strings.Contains(cmd, "submodule")`に簡素化されました。これは、ベンダー機能が常に有効であるため、サブモジュール関連のコマンドが常に実行されることを意味します。

6.  **テストコードの削除 (`src/cmd/go/vendor_test.go`)**:
    `src/cmd/go/vendor_test.go`ファイル内で、`GO15VENDOREXPERIMENT`環境変数を明示的に設定していたテストケースが削除されました。これは、この環境変数がもはや存在しないため、これらのテストが不要になったためです。

これらの変更は、Goのビルドシステムから実験的なフラグを取り除き、ベンダー機能をGoの標準的な動作として完全に統合することを目的としています。これにより、Goの依存関係解決ロジックが簡素化され、将来的なモジュールシステムへの移行に向けた基盤が強化されます。

## コアとなるコードの解説

`src/cmd/go/pkg.go`における主要な変更点は、`go15VendorExperiment`というグローバル変数の削除と、それに依存する条件分岐の除去です。

1.  **`go15VendorExperiment`変数の削除**:
    以前は、以下の行で`GO15VENDOREXPERIMENT`環境変数の値に基づいて`go15VendorExperiment`というブール変数が初期化されていました。
    ```go
    var go15VendorExperiment = os.Getenv("GO15VENDOREXPERIMENT") != "0"
    ```
    この変数は、ベンダー機能が有効かどうかを判断するために使用されていました。このコミットでは、この変数の宣言と初期化が完全に削除されます。これにより、Goツールはベンダー機能の有効/無効を環境変数で制御する能力を失います。

2.  **`loadImport`関数の変更**:
    `loadImport`関数は、パッケージのインポートパスを解決するGoツールの中心的なロジックの一部です。以前は、`build.IgnoreVendor`フラグを設定するかどうかを決定する際に`go15VendorExperiment`を使用していました。
    ```diff
    -	if !go15VendorExperiment || mode&useVendor == 0 || path != origPath {
    +	if mode&useVendor == 0 || path != origPath {
    		// Not vendoring, or we already found the vendored path.
    		buildMode |= build.IgnoreVendor
    	}
    ```
    この変更により、`!go15VendorExperiment`という条件が削除され、`buildMode |= build.IgnoreVendor`の適用は`GO15VENDOREXPERIMENT`の状態に依存しなくなりました。これは、ベンダー機能が常に有効であるため、特定の条件下で`vendor`ディレクトリを無視するロジックが簡素化されたことを意味します。

    また、インポートパスの検証ロジックでも同様の変更が行われています。
    ```diff
    -		(!go15VendorExperiment || (!strings.Contains(path, "/vendor/") && !strings.HasPrefix(path, "vendor/"))) {
    +		!strings.Contains(path, "/vendor/") && !strings.HasPrefix(path, "vendor/") {
    ```
    ここでも`!go15VendorExperiment`が削除され、`vendor/`パスを含むインポートに関するチェックが常に適用されるようになりました。

3.  **`vendoredImportPath`関数の変更**:
    `vendoredImportPath`関数は、ベンダーディレクトリ内のパッケージのインポートパスを解決するために使用されます。以前は、この関数がベンダーパスの解決を試みる前に`go15VendorExperiment`が有効かどうかをチェックしていました。
    ```diff
    -	if parent == nil || parent.Root == "" || !go15VendorExperiment {
    +	if parent == nil || parent.Root == "" {
    		return path
    	}
    ```
    この変更により、`!go15VendorExperiment`の条件が削除され、`parent`と`parent.Root`が有効であれば、常にベンダーパスの解決ロジックが実行されるようになりました。

4.  **`disallowVendor`関数の変更**:
    `disallowVendor`関数は、特定の状況下でベンダーパッケージのインポートを許可しないためのロジックを含んでいました。以前は、この関数全体が`go15VendorExperiment`が有効な場合にのみ実行されていました。

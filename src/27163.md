## 変更の背景

このコミットの背景には、Goコンパイラの内部で `nil` 値がどのように扱われるかについての既存のコメントが、実際のコンパイラの動作と一致していなかったという問題があります。

`src/cmd/compile/internal/gc/obj.go` 内の `gdata` 関数には、以前「`CTNIL` は `gdata` に到達しない。`sinit.go` で `CTNIL` を探せ。おそらく、いずれは到達すべきだろう。」というコメントがありました。しかし、実際には `CTNIL` の処理は `sinit.go` で行われており、`gdata` に到達しないという記述は正しいものの、「いずれは到達すべきだろう」という部分は、現在の設計や意図と異なる可能性がありました。このコメントは、コンパイラの内部ロジックを理解しようとする開発者にとって混乱を招くものでした。

このコミットは、この誤解を招くコメントを削除し、代わりに `src/cmd/compile/internal/gc/sinit.go` 内の `isliteral` 関数に、`nil` がリテラルとしてではなくゼロ値として扱われることを明確にするコメントを追加することで、コンパイラの動作に関するドキュメントの正確性を向上させています。これにより、コンパイラの内部構造と `nil` 値の処理に関する理解がより正確になります。

このコメントは、`CTNIL`（`nil` の内部表現）が `gdata` 関数に直接到達しないこと、そしてその処理が `sinit.go` で行われていることを説明していました。しかし、「おそらく、いずれは到達すべきだろう」という部分は、コンパイラの将来の設計に関する推測であり、現在の実装の事実とは異なる可能性がありました。このコミットでは、この誤解を招く可能性のあるコメントが削除されました。これにより、`gdata` 関数が `CTNIL` を直接処理しないという事実のみが残り、コードの意図がより明確になりました。`CTNIL` は `gdata` のコンテキストでは `OLITERAL` の `default` ケースに到達するべきではない、という暗黙の前提が強化されます。

### `src/cmd/compile/internal/gc/sinit.go` の変更

`isliteral` 関数は、与えられたASTノードがリテラルであるかどうかを判断するために使用されます。この関数は、`OLITERAL` ノードをチェックし、その値の型 (`Ctype()`) が `CTNIL` でない場合に `true` を返します。

このコミットでは、`isliteral` 関数の冒頭に以下の新しいコメントが追加されました。

```go
// Treat nils as zeros rather than literals.
```

このコメントは、`isliteral` 関数が `nil` をどのように扱うかについての重要な設計方針を明確にしています。Go言語では `nil` はリテラルですが、コンパイラの内部、特に `isliteral` の文脈では、`nil` は「リテラル」としてではなく、その型の「ゼロ値」として扱われるべきであるという意図が示されています。例えば、ポインタ型のゼロ値は `nil` です。この関数が `CTNIL` の場合に `false` を返す（つまり `nil` をリテラルとして扱わない）のは、この方針に基づいています。このコメントにより、`isliteral` 関数の動作と、Goコンパイラにおける `nil` の概念的な扱いがより明確に理解できるようになります。

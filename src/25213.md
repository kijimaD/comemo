# [インデックス 25213] ファイルの概要

このコミットは、Go言語の`net/http/httputil`パッケージに含まれる`NewSingleHostReverseProxy`関数のドキュメンテーションを明確化するものです。特に、この関数がHTTPリクエストの`Host`ヘッダーをどのように扱うかについて、誤解を招かないように説明が追加されました。`NewSingleHostReverseProxy`はデフォルトで`Host`ヘッダーを書き換えないこと、そして`Host`ヘッダーの書き換えが必要な場合には`ReverseProxy`を直接使用し、カスタムの`Director`ポリシーを設定する必要があることが明記されています。

## 変更の背景

この変更は、Goの`net/http/httputil`パッケージにおける`NewSingleHostReverseProxy`関数の`Host`ヘッダーの挙動に関する混乱を解消するために行われました。コミットメッセージに記載されている`Fixes #10342`が示すように、GitHub Issue #10342で報告された問題に対応するものです。

多くのユーザーは、リバースプロキシがバックエンドサーバーにリクエストを転送する際に、`Host`ヘッダーをバックエンドサーバーのホスト名に自動的に書き換えることを期待する場合があります。しかし、`NewSingleHostReverseProxy`のデフォルトの挙動は、クライアントから送られてきたオリジナルの`Host`ヘッダーをそのまま転送することでした。この挙動がドキュメントで明確に説明されていなかったため、ユーザーが意図しない動作に遭遇し、デバッグに時間を要するケースが発生していました。

このコミットは、APIの実際の挙動を変更することなく、ドキュメントに明確な説明を追加することで、ユーザーの誤解を防ぎ、より適切なリバースプロキシの実装を促すことを目的としています。

## 前提知識の解説

*   **`net/http/httputil`パッケージ**: Go言語の標準ライブラリ`net/http`パッケージを補完し、HTTPユーティリティ機能を提供するパッケージです。特に、リバースプロキシの実装に役立つ機能が提供されています。
*   **`ReverseProxy`**: `net/http/httputil`パッケージの中心的な構造体で、HTTPリクエストを別のサーバー（バックエンド）に転送し、そのレスポンスをクライアントに返すリバースプロキシの機能を提供します。これは、ロードバランシング、キャッシュ、セキュリティ強化など、様々な目的で利用されます。
*   **`NewSingleHostReverseProxy`**: `ReverseProxy`を簡単に構築するためのヘルパー関数です。特定の単一のターゲットURLに対してリバースプロキシを設定する際に使用されます。この関数は、基本的なリバースプロキシのロジックをカプセル化し、開発者が迅速にプロキシをセットアップできるようにします。
*   **HTTP `Host` ヘッダー**: HTTPリクエストの必須ヘッダーの一つで、リクエストされたリソースのインターネットホストとポート番号を指定します。例えば、`Host: example.com`のように記述されます。バーチャルホスティング環境では、単一のIPアドレスで複数のドメインをホストしているサーバーが、どのドメイン宛のリクエストかを判断するためにこのヘッダーが非常に重要になります。
*   **リバースプロキシにおける `Host` ヘッダーの扱い**: リバースプロキシは、クライアントからのリクエストを受け取り、それをバックエンドサーバーに転送します。この際、`Host`ヘッダーを元のクライアントからのもの（オリジナルの`Host`ヘッダー）をそのまま転送するか、それともバックエンドサーバーのホスト名に書き換えるか、という選択肢があります。
    *   **オリジナルの`Host`ヘッダーを転送する場合**: バックエンドサーバーが、クライアントがアクセスしようとした元のドメイン名に基づいて動作する場合（例: バーチャルホストの設定、マルチテナントアプリケーション）に必要です。
    *   **`Host`ヘッダーを書き換える場合**: バックエンドサーバーが、プロキシを介してアクセスされていることを意識せず、自身のホスト名でリクエストを受け取ることを期待する場合に必要です。
*   **`Director`ポリシー**: `ReverseProxy`構造体の一部で、リクエストがバックエンドに転送される前に、そのリクエストをどのように変更するかを定義する関数です。`Director`関数を使用することで、URLの書き換え、ヘッダーの追加・変更・削除、認証情報の付与など、リクエストに対する詳細な制御が可能になります。これは、リバースプロキシの柔軟性を高めるための強力なメカニズムです。

## 技術的詳細

このコミットは、`NewSingleHostReverseProxy`のドキュメントに、そのデフォルトの`Host`ヘッダーの挙動に関する重要な明確化を追加するものです。以前のドキュメントでは、`NewSingleHostReverseProxy`が`Host`ヘッダーをどのように扱うかについて明示的な記述がなかったため、ユーザーが誤解する可能性がありました。

具体的には、`NewSingleHostReverseProxy`はデフォルトで**`Host`ヘッダーを書き換えません**。つまり、クライアントから送られてきた`Host`ヘッダーが、変更されずにそのままバックエンドサーバーに転送されます。この挙動は、多くのリバースプロキシのユースケース、特にバックエンドサーバーがオリジナルの`Host`ヘッダーに基づいてルーティングや処理を行う場合に望ましいものです。例えば、バックエンドサーバーが複数のバーチャルホストを運用している場合、オリジナルの`Host`ヘッダーがなければ、どのバーチャルホストにリクエストをルーティングすべきか判断できません。

しかし、バックエンドサーバーがプロキシ自身のホスト名や、特定の固定された`Host`ヘッダーを期待するようなシナリオでは、このデフォルトの挙動は問題となります。例えば、バックエンドアプリケーションが`Host`ヘッダーを自身のURL生成に使用している場合、オリジナルの`Host`ヘッダーが転送されると、誤ったURLが生成される可能性があります。このような場合、ユーザーは`Host`ヘッダーを明示的に書き換える必要がありますが、`NewSingleHostReverseProxy`のドキュメントにはその方法が示されていませんでした。

このコミットによって、`NewSingleHostReverseProxy`関数のコメントに以下の記述が追加されました：
- `NewSingleHostReverseProxy does not rewrite the Host header.` (NewSingleHostReverseProxyはHostヘッダーを書き換えません。)
- `To rewrite Host headers, use ReverseProxy directly with a custom Director policy.` (Hostヘッダーを書き換えるには、カスタムのDirectorポリシーを持つReverseProxyを直接使用してください。)

これにより、`NewSingleHostReverseProxy`のデフォルトの挙動が明確になり、`Host`ヘッダーの書き換えが必要な場合には、`ReverseProxy`を直接使用し、カスタムの`Director`関数を実装する必要があることが示唆されました。`Director`関数内で`req.Host = target.Host`のように設定することで、`Host`ヘッダーをターゲットサーバーのものに書き換えることができます。この変更は、APIの挙動自体を変更するものではなく、その挙動に関するドキュメントの正確性と明確性を向上させるものです。これにより、開発者はより自信を持って`httputil`パッケージを利用し、リバースプロキシを構築できるようになります。

## コアとなるコードの解説

このコミットによるコードの変更は、`NewSingleHostReverseProxy`関数の動作自体を変更するものではなく、その関数のドキュメンテーションコメントを修正するものです。

1.  **`// NewSingleHostReverseProxy returns a new ReverseProxy that routes`**:
    *   以前は`rewrites`（書き換える）という言葉が使われていましたが、これはURLのパス部分の変換を指すものであり、`Host`ヘッダーの書き換えとは異なります。`routes`（ルーティングする）という言葉に変更することで、この関数の主な役割が、指定されたターゲットへのリクエストのルーティングであることをより正確に表現しています。これにより、パスの書き換えとヘッダーの書き換えという異なる概念が混同されるのを防ぎます。

2.  **`// NewSingleHostReverseProxy does not rewrite the Host header.`**:
    *   この行は、`NewSingleHostReverseProxy`の最も重要なデフォルト挙動の一つを明確に述べています。つまり、クライアントから受け取った`Host`ヘッダーは、変更されずにそのままバックエンドサーバーに転送されます。これは、多くのリバースプロキシのシナリオで期待される挙動であり、バックエンドサーバーがオリジナルの`Host`ヘッダーに基づいて動作する場合に特に重要となります。この明確化により、ユーザーはデフォルトの挙動を正確に理解できます。

3.  **`// To rewrite Host headers, use ReverseProxy directly with a custom`**
    **`// Director policy.`**:
    *   この2行は、`Host`ヘッダーの書き換えが必要な場合の解決策をユーザーに提示しています。`NewSingleHostReverseProxy`では`Host`ヘッダーの書き換えができないため、より低レベルな`ReverseProxy`構造体を直接使用し、`Director`フィールドにカスタム関数を設定することで、この要件を満たすことができると説明しています。`Director`関数内で`req.Host`を明示的に設定することで、`Host`ヘッダーを自由に制御することが可能になります。これは、APIの柔軟な利用方法を示すガイドラインとなります。

これらの変更により、`NewSingleHostReverseProxy`の利用者が、`Host`ヘッダーの挙動について誤解することなく、必要に応じて適切な実装を選択できるようになります。これは、APIの使いやすさと、予期せぬ動作によるデバッグ時間の削減に貢献します。

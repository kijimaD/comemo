# [インデックス 25716] ファイルの概要

このコミットは、Go言語の`net`パッケージにおけるDNS応答の処理ロジックを修正するものです。具体的には、DNS応答で`NXDOMAIN`（存在しないドメイン）が返された際に、`recursion_available`フラグの有無を問わず、正しく「そのようなホストは存在しない」というエラーを返すように変更されています。これにより、非再帰的なDNSサーバーからの応答が誤って「サーバーの動作がおかしい」と判断される問題が解決されます。

変更されたファイルは以下の通りです。
*   `src/net/dnsclient.go`: DNSクライアントの主要なロジックが含まれるファイル。`answer`関数の条件式が変更されています。
*   `src/net/dnsclient_test.go`: 上記の変更を検証するための新しいテストケースが追加されています。
*   `src/net/dnsclient_unix.go`: Unix系システムにおけるDNSクライアントのロジックが含まれるファイル。`tryOneName`関数の条件式が変更されています。

## 変更の背景

この変更は、Go言語の`net`パッケージがDNS応答を処理する際に発生していた、特定のシナリオにおける誤ったエラー報告を修正するために行われました。以前のGoの`net`パッケージでは、DNSクエリに対して`NXDOMAIN`（Non-Existent Domain、ドメインが存在しない）という応答コードが返された場合、その応答ヘッダ内の`recursion_available`（再帰が利用可能）フラグも同時にチェックしていました。

問題は、再帰をサポートしないDNSサーバー（例えば、権威DNSサーバーや、意図的に再帰を無効にしているキャッシュDNSサーバー）が`NXDOMAIN`を返した場合に発生しました。これらのサーバーは再帰を提供しないため、`recursion_available`フラグを`false`に設定して応答します。しかし、Goの`net`パッケージのロジックは、`NXDOMAIN`と`recursion_available: false`の組み合わせを「サーバーの動作がおかしい（server misbehaving）」というエラーとして解釈していました。

本来、`NXDOMAIN`はドメインが存在しないことを明確に示しており、サーバーが再帰をサポートしているかどうかに関わらず、その情報は有効です。したがって、このような状況で「サーバーの動作がおかしい」という汎用的なエラーではなく、「そのようなホストは存在しない（no such host）」という具体的なエラーが返されるべきでした。このコミットは、この誤ったエラー解釈を是正し、より正確なエラー報告を可能にすることを目的としています。

## 前提知識の解説

このコミットの理解には、以下のDNSに関する基本的な知識が必要です。

*   **DNS (Domain Name System)**:
    インターネット上でドメイン名（例: `golang.org`）をIPアドレス（例: `142.250.199.142`）に変換（名前解決）するための分散型データベースシステムです。ユーザーがウェブサイトにアクセスする際などに利用されます。

*   **DNS応答コード (RCODE)**:
    DNSサーバーからの応答には、クエリの結果を示すコードが含まれています。
    *   `dnsRcodeSuccess` (RCODE 0): クエリが成功し、要求されたデータが応答に含まれていることを示します。
    *   `dnsRcodeNameError` (RCODE 3, 別名 `NXDOMAIN`): クエリされたドメイン名が存在しないことを示します。これは、ドメイン名が登録されていないか、タイプミスがある場合などに発生します。

*   **DNSの再帰 (Recursion in DNS)**:
    DNSクエリには「再帰クエリ」と「非再帰クエリ」があります。
    *   **再帰クエリ**: クライアントがDNSサーバーに対し、最終的な回答（IPアドレスなど）を見つける責任を負うよう要求するクエリです。DNSサーバーは、必要に応じて他のDNSサーバーに問い合わせを行い、最終的な回答をクライアントに返します。
    *   **非再帰クエリ**: クライアントがDNSサーバーに対し、自身が知っている情報（キャッシュや権威情報）のみを返すよう要求するクエリです。もし情報がなければ、他のDNSサーバーへの参照（ネームサーバーのリスト）を返します。
    *   **`recursion_available`フラグ**: DNS応答ヘッダに含まれる1ビットのフラグです。このフラグが`true`の場合、応答を生成したDNSサーバーが再帰クエリをサポートしていることを示します。`false`の場合、そのサーバーは再帰をサポートしていないか、再帰サービスを提供していないことを示します。権威DNSサーバーは通常、このフラグを`false`に設定します。

*   **Goの`net`パッケージ**:
    Go言語の標準ライブラリの一部で、ネットワークI/O機能を提供します。TCP/UDP通信、IPアドレスの解決、DNSルックアップなど、様々なネットワーク関連の操作を扱うためのAPIが含まれています。このコミットは、`net`パッケージ内のDNSクライアントの実装、特に名前解決のロジックに影響を与えます。

## 技術的詳細

このコミットの技術的な核心は、Goの`net`パッケージがDNS応答を評価する際の条件式の変更にあります。以前の実装では、`src/net/dnsclient.go`の`answer`関数内で、`NXDOMAIN`応答（`dns.rcode == dnsRcodeNameError`）を受け取った際に、さらに`dns.recursion_available`フラグが`true`であることも期待していました。

```go
// 変更前 (簡略化)
if dns.rcode == dnsRcodeNameError && dns.recursion_available {
    return "", nil, &DNSError{Err: errNoSuchHost.Error(), Name: name, Server: server}
}
```

このロジックは、再帰をサポートしないDNSサーバーからの`NXDOMAIN`応答を正しく処理できませんでした。非再帰サーバーは`NXDOMAIN`を返しても`recursion_available`フラグを`false`にするため、上記の条件式は`false`となり、`errNoSuchHost`が返されませんでした。その結果、`answer`関数は後続の一般的なエラー処理パスに進み、最終的に「サーバーの動作がおかしい」といった、より汎用的な（そして誤解を招く）エラーを返す可能性がありました。

このコミットでは、`NXDOMAIN`が返された場合は、`recursion_available`フラグの状態に関わらず、直ちに「そのようなホストは存在しない」というエラーとして扱うように修正されました。これにより、DNSサーバーが再帰をサポートしているかどうかにかかわらず、`NXDOMAIN`応答が常に正しく解釈されるようになります。

また、`src/net/dnsclient_unix.go`の`tryOneName`関数におけるロジックも調整されています。この関数は複数のDNSサーバーを試行する役割を担っていますが、`answer`関数が`dnsRcodeSuccess`または`dnsRcodeNameError`を返した場合（エラーの有無にかかわらず）、その応答は最終的なものと見なされ、それ以上他のサーバーを試行せずに結果を返すように変更されました。これは、`NXDOMAIN`が確定的な応答であるという新しい解釈と整合しています。

## コアとなるコードの解説

### `src/net/dnsclient.go` の `answer` 関数

この変更の最も重要な部分は、`answer`関数内の以下の行です。

```diff
- 	if dns.rcode == dnsRcodeNameError && dns.recursion_available {
+ 	if dns.rcode == dnsRcodeNameError {
```

以前は、`dnsRcodeNameError`（NXDOMAIN）が検出された場合でも、`dns.recursion_available`が`true`である場合にのみ`errNoSuchHost`を返していました。この修正により、`recursion_available`フラグのチェックが削除されました。これにより、DNSサーバーが再帰をサポートしているかどうかにかかわらず、`NXDOMAIN`応答は常に「そのようなホストは存在しない」というエラーとして扱われるようになります。これは、`NXDOMAIN`がドメインの存在に関する確定的な情報であるという事実を反映した、より正確な挙動です。

### `src/net/dnsclient_unix.go` の `tryOneName` 関数

`tryOneName`関数は、複数のDNSサーバーに対してクエリを試行し、最初に応答を返すサーバーの結果を使用します。この関数内の条件式も変更されました。

以前は、`dnsRcodeNameError`が返された場合でも、`recursion_available`が`false`であれば、他のサーバーを試行し続ける可能性がありました。しかし、`answer`関数の変更により`NXDOMAIN`が確定的なエラーとして扱われるようになったため、`tryOneName`関数もこの新しい解釈に合わせる必要があります。

この修正により、`answer`関数が`dnsRcodeSuccess`または`dnsRcodeNameError`を返した場合（`err`が`nil`であるかどうかにかかわらず）、その応答は最終的なものと見なされ、すぐにその結果を返すように変更されました。これは、`NXDOMAIN`が「ドメインが存在しない」という明確な情報を提供するため、他のサーバーに問い合わせても結果が変わる可能性が低いという判断に基づいています。これにより、不要なDNSサーバーへの問い合わせが削減され、効率が向上します。

### `src/net/dnsclient_test.go` の `TestIssue12778`

この新しいテストケースは、まさにこのコミットが解決しようとしている問題を具体的に検証します。

```go
func TestIssue12778(t *testing.T) {
	msg := &dnsMsg{
		dnsMsgHdr: dnsMsgHdr{
			rcode:               dnsRcodeNameError,
			recursion_available: false,
		},
	}

	_, _, err := answer("golang.org", "foo:53", msg, uint16(dnsTypeSRV))
	if err == nil {
		t.Fatal("expected an error")
	}
	de, ok := err.(*DNSError)
	if !ok {
		t.Fatalf("err = %#v; wanted a *net.DNSError", err)
	}

		t.Fatalf("Err = %#v; wanted %q", de.Err, errNoSuchHost.Error())
	}
}
```

このテストでは、`dnsMsg`構造体を明示的に作成し、`rcode`を`dnsRcodeNameError`に、`recursion_available`を`false`に設定しています。これは、再帰をサポートしないDNSサーバーが`NXDOMAIN`を返した状況をシミュレートしています。

そして、この`msg`を`answer`関数に渡し、返されるエラーが`nil`ではないこと（エラーが期待されるため）、そしてそのエラーが`*net.DNSError`型であり、かつその`Err`フィールドが`errNoSuchHost.Error()`（「そのようなホストは存在しない」）と一致することを検証しています。このテストは、修正されたロジックが意図した通りに機能し、特定のシナリオで正しいエラーを返すことを保証します。

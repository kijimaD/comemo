## 変更の背景

Go言語は、その設計思想として、コンパイラ、アセンブラ、リンカを含むツールチェーン全体を自己完結型にすることを目指しています。初期のGoツールチェーンでは、一部のコンポーネント、特にリンカにおいて、C言語で書かれた部分や、既存のCリンカ（例えば `gcc` や `ld`）への依存が存在していました。

このコミットが行われた2015年当時、Go言語はバージョン1.5に向けて大きな変更を進めていました。Go 1.5では、Goコンパイラ自体がGo言語で再実装されるなど、Goツールチェーンの「ブートストラップ」が完了し、C言語への依存を減らす方向性が明確になっていました。このコミットは、その流れの一環として、リンカもGo言語で実装されたバージョンに切り替えることで、ツールチェーン全体の整合性を高め、クロスコンパイルの容易さや、将来的なリンカの機能拡張・最適化をGo言語のコードベース内で行えるようにするための重要なステップでした。

Cリンカへの依存を減らすことで、Goのビルドシステムはよりポータブルになり、異なるシステム環境でのビルドの信頼性が向上します。また、Go言語で書かれたリンカは、Goのランタイムやガベージコレクションの知識をより深く活用できるため、より効率的なバイナリ生成や、Go特有の最適化を適用する可能性を秘めています。

## 前提知識の解説

### リンカ (Linker)

リンカは、コンパイラによって生成された複数のオブジェクトファイル（`.o` や `.obj` ファイル）やライブラリを結合し、実行可能なプログラムや共有ライブラリを生成するソフトウェアツールです。主な役割は以下の通りです。

*   **シンボル解決 (Symbol Resolution)**: あるオブジェクトファイルで定義された関数や変数を、別のオブジェクトファイルから参照する際に、それらのアドレスを解決します。
*   **再配置 (Relocation)**: オブジェクトファイル内のコードやデータが、最終的な実行ファイル内のどこに配置されるかに応じて、アドレス参照を修正します。
*   **ライブラリの結合 (Library Linking)**: 静的ライブラリ（`.a` や `.lib`）や共有ライブラリ（`.so` や `.dll`）から、プログラムが必要とするコードを取り込みます。

Go言語の場合、Goのリンカ (`cmd/link`) は、Goのオブジェクトファイル形式を理解し、Goランタイムや標準ライブラリを静的にリンクして、単一の実行ファイルを生成することが一般的です。

### Goツールチェーン

Go言語のツールチェーンは、ソースコードから実行ファイルを生成するための一連のツール群です。これには、コンパイラ (`cmd/compile`)、アセンブラ (`cmd/asm`)、リンカ (`cmd/link`)、そしてこれらを統合してビルドプロセスを管理する `go` コマンド (`cmd/go`) などが含まれます。Goの設計哲学の一つに、このツールチェーン全体をGo言語で実装し、自己完結させるというものがあります。これにより、Goのビルド環境を簡単にセットアップでき、クロスコンパイルも容易になります。

### `cmd/go`

`cmd/go` は、Go言語のビルド、テスト、インストール、フォーマットなど、様々な開発タスクを管理するコマンドラインツールです。ユーザーが `go build` や `go run` などのコマンドを実行すると、`cmd/go` が内部的にコンパイラやリンカなどの他のツールを呼び出し、適切な順序で処理を実行します。このコミットで変更されている `src/cmd/go/build.go` は、`cmd/go` コマンドのビルドロジックの一部を定義しているファイルです。

### `tool()` 関数

Goのビルドシステムでは、`tool()` 関数は、特定のアーキテクチャやOSに対応するツール（コンパイラ、リンカなど）のパスを解決するために使用されます。例えば、`tool("5l")` は `go tool 5l` (ARMアーキテクチャのリンカ) を指す可能性があります。このコミットでは、`tool(archChar+"l")` が `tool("new"+archChar+"l")` に変更されており、これは特定のアーキテクチャのリンカの「新しい」バージョン（Go言語で実装されたバージョン）を使用することを示唆しています。

## 技術的詳細

このコミットの核心は、`src/cmd/go/build.go` ファイル内の `gcToolchain.ld` メソッドの変更です。このメソッドは、Goコンパイラツールチェーン（`gcToolchain`）がリンカを呼び出す際のロジックをカプセル化しています。

変更前は、リンカの呼び出しに `tool(archChar+"l")` を使用していました。ここで `archChar` はターゲットアーキテクチャ（例: `6` for `amd64`, `5` for `arm`）を表し、`l` はリンカを意味します。例えば、`amd64` アーキテクチャの場合、これは `tool("6l")` となり、従来のリンカ（おそらくC言語で書かれたもの、またはそのラッパー）を指していました。

変更後は、リンカの呼び出しが `tool("new"+archChar+"l")` になっています。これは、`new` というプレフィックスが付いたリンカツールを使用することを明示しています。この `new` プレフィックスは、Go言語で再実装された新しいリンカのバージョンを指す慣例的な命名です。これにより、`cmd/go` はビルド時にGo言語で書かれたリンカを明示的に選択するようになります。

また、`toolVerify` 関数内で `os.Remove(ofile + ".new")` が追加されています。これは、リンカが一時的に生成する可能性のある `.new` 拡張子を持つ出力ファイルを、検証後にクリーンアップするためのものです。これは、新しいリンカの動作に関連する一時ファイルの管理を改善するための変更と考えられます。

この変更は、GoツールチェーンがC言語のリンカへの依存を減らし、Go言語で書かれた自己完結型のツールチェーンへと移行する大きな流れの一部です。これにより、Goのビルドシステムはより堅牢で、クロスプラットフォーム対応が容易になり、将来的なパフォーマンス最適化や機能追加の柔軟性が向上します。

## コアとなるコードの解説

### `func toolVerify` の変更

```go
+	os.Remove(ofile + ".new")
```
`toolVerify` 関数は、新しいツールが生成した出力ファイルが期待通りであるかを検証する役割を担っています。この行の追加は、検証プロセスが完了した後、リンカが一時的に生成した可能性のある `.new` 拡張子を持つファイルを削除することを保証します。これは、ビルドプロセス中に生成される一時ファイルのクリーンアップを徹底し、ディスクスペースの消費を抑えたり、ビルドの副作用を減らしたりする目的があります。新しいリンカの導入に伴い、このような一時ファイルの生成パターンが変わった可能性があり、それに対応するための変更と考えられます。

### `func (gcToolchain) ld` の変更

```diff
-	return b.run(".", p.ImportPath, nil, stringList(buildToolExec, tool(archChar+"l"), "-o", out, importArgs, ldflags, mainpkg))
+	return b.run(".", p.ImportPath, nil, buildToolExec, tool("new"+archChar+"l"), "-o", out, importArgs, ldflags, mainpkg))
```
この変更がこのコミットの最も重要な部分です。
*   **変更前**: `tool(archChar+"l")` を使用してリンカを呼び出していました。ここで `archChar` はターゲットアーキテクチャ（例: `6` for `amd64`）を表し、`l` はリンカを意味します。これは、Goのツールチェーンが提供する標準のリンカを指しますが、この時点ではまだC言語ベースのリンカ、またはそのラッパーが使用されていた可能性があります。
*   **変更後**: `tool("new"+archChar+"l")` を使用するように変更されました。`"new"` というプレフィックスは、Go言語で再実装された新しいリンカのバージョンを明示的に指定しています。例えば、`amd64` アーキテクチャの場合、`tool("new6l")` が呼び出されることになります。

この変更により、`go build` コマンドが内部的にリンカを呼び出す際に、Go言語で書かれた新しいリンカが使用されるようになります。これは、GoツールチェーンのC言語への依存をさらに減らし、Go言語による自己完結性を高めるための重要な一歩です。これにより、Goのビルドシステムはより一貫性のあるものとなり、Go言語の進化に合わせてリンカ自体も進化させることが可能になります。

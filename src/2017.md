## 変更の背景

このコミットが行われた2009年4月は、Go言語がまだ一般に公開される前の開発初期段階にあたります。当時の`template`パッケージは、現在の`text/template`や`html/template`パッケージとは異なり、`src/lib/template`というパスに存在していました。

このコミットの背景にある問題は、`Template`オブジェクトが一度`Execute`メソッドで実行された後、再度同じ`Template`オブジェクトに対して`Execute`メソッドを呼び出すと、予期せぬ動作をするというバグでした。これは、テンプレートの内部状態（特にパーサーの現在位置を示すポインタのようなもの）が適切にリセットされていなかったために発生したと考えられます。

テンプレートエンジンにおいて、一度パースされたテンプレートは、異なるデータソースに対して何度でも再利用できるべきです。しかし、内部状態がリセットされないと、2回目以降の実行時に前回の実行の残骸が影響し、誤った出力やエラーを引き起こす可能性があります。このコミットは、この再利用性の問題を解決することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が役立ちます。

*   **Go言語の初期開発**: Go言語は2009年11月に一般公開されました。このコミットはそれ以前のものであり、当時のGo言語の標準ライブラリの構造やAPIは現在とは異なる部分が多くあります。特に、`src/lib`というパスは、現在の`src`直下に各パッケージが配置される構造とは異なります。
*   **テンプレートエンジン**: テンプレートエンジンは、テンプレート（プレースホルダーを含むテキスト）とデータ（プレースホルダーに埋め込む値）を組み合わせて、最終的なテキストを生成するソフトウェアコンポーネントです。Go言語には標準で`text/template`や`html/template`といった強力なテンプレートパッケージが用意されています。
*   **`io.Writer`インターフェース**: Go言語における`io.Writer`インターフェースは、バイト列を書き込むための汎用的なインターフェースです。`Execute`メソッドが`io.Write`（当時の名称）を引数に取るのは、生成されたテンプレートの出力をファイル、ネットワーク接続、メモリバッファなど、様々な出力先に柔軟に書き込めるようにするためです。
*   **`reflect`パッケージ**: `reflect`パッケージは、Goプログラムが実行時に自身の構造を検査（リフレクション）したり、変更したりするための機能を提供します。`reflect.NewValue(data)`は、入力データ`data`の型情報を実行時に取得し、それに基づいて操作を行うために使用されます。
*   **Goroutineとチャネル**: Go言語の並行処理のプリミティブです。`go func() { ... }()`は新しいGoroutineを起動し、`make(chan *os.Error)`と`ch <- nil`はチャネルを使ったGoroutine間の通信を示しています。ここでは、テンプレートの実行処理を別のGoroutineで非同期に実行し、完了をチャネルで通知する構造になっています。
*   **`os.Error`**: Go言語の初期におけるエラー型です。現在の`error`インターフェースに相当します。

## 技術的詳細

このコミットの技術的な核心は、`Template`構造体の内部状態、特にテンプレートのパースや実行に関連するポインタやインデックスが、`Execute`メソッドの呼び出し間で適切にリセットされていなかった点にあります。

`template.go`の変更点を見ると、`func (t *Template) Execute(...)`メソッドのGoroutine内で、`t.p = 0;`という行が追加されています。
ここで`t.p`が何を指すのかは、このコミットの差分だけでは明確ではありませんが、一般的にテンプレートエンジンにおいて`p`のようなフィールドは「現在のパース位置」や「現在の実行位置」を示すポインタ（またはインデックス）として使われることが多いです。

もし`t.p`がテンプレートの内部的な読み込み位置や、データ構造を走査する際のインデックスを保持していた場合、一度`Execute`が完了してもその値がリセットされなければ、2回目の`Execute`呼び出し時には前回の終了位置から処理が開始されてしまい、テンプレート全体が正しく処理されない、あるいは部分的にしか処理されないといった問題が発生します。

`t.p = 0;`という行を追加することで、`Execute`メソッドが呼び出されるたびに、テンプレートの内部状態（この場合は`p`）が初期値（0）にリセットされるようになります。これにより、テンプレートは常に最初から処理を開始し、複数回実行されても一貫した結果を返すことが保証されます。

`template_test.go`に追加された`TestTwice`テストケースは、この問題を再現し、修正が正しく機能することを確認するために書かれました。このテストは、同じテンプレートオブジェクトを2回連続で実行し、それぞれの実行結果が期待通りであるか、そして2回の実行を連結した結果も期待通りであるかを検証しています。

## コアとなるコードの解説

### `src/lib/template/template.go` の変更

`Template.Execute`メソッドは、テンプレートの実行を開始するエントリポイントです。このメソッドは新しいGoroutineを起動して実際の実行ロジック（`t.execute`）を非同期に処理しています。

追加された`t.p = 0;`は、このGoroutineの開始直後、つまりテンプレートの実行が始まる前に呼び出されます。これにより、`Template`オブジェクトの内部状態である`p`フィールドが常にゼロにリセットされます。この`p`フィールドは、テンプレートのパースや実行中に現在の位置を追跡するために使用されるインデックスまたはポインタであると推測されます。これをリセットすることで、テンプレートが複数回実行されても、常に最初から処理が開始されるようになり、以前の実行の影響を受けなくなります。

### `src/lib/template/template_test.go` の変更

`TestTwice`関数は、このコミットの修正を検証するために追加された新しいテストケースです。

1.  **テンプレートのパース**:
    `tmpl, err, line := Parse("template: {@}", nil);`
    これは、`template: {@}`というシンプルなテンプレートをパースしています。`{@}`は、データが埋め込まれるプレースホルダーであると推測されます。

2.  **1回目の実行**:
    `err = tmpl.Execute("hello", &b);`
    `s := string(b.Data());`
    `text := "template: hello";`
    `if s != text { ... }`
    ここでは、`"hello"`というデータをテンプレートに適用し、結果が`"template: hello"`となることを検証しています。これは通常のテンプレート実行の確認です。

3.  **2回目の実行**:
    `err = tmpl.Execute("hello", &b);`
    `s = string(b.Data());`
    `text += text;`
    `if s != text { ... }`
    ここがこのテストの肝です。同じ`tmpl`オブジェクトに対して再度`Execute`メソッドを呼び出しています。もし`t.p`のリセットがなければ、この2回目の実行で問題が発生する可能性がありました。
    `text += text;`は、期待される結果が1回目の実行結果と2回目の実行結果を連結したものになることを示しています。これは、`io.ByteBuffer`がデータを追記していく性質を利用したテストであり、テンプレートが正しく2回実行され、それぞれの結果がバッファに追加されていることを確認しています。

このテストケースは、テンプレートの再利用性に関するバグを効果的に検出し、修正が正しく適用されたことを保証するものです。

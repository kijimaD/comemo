## 変更の背景

このコミットの主な背景には、Go の `net/http` クライアントにおけるリクエストのライフサイクル全体にわたる詳細なトレーシング（追跡）とアナリティクス（分析）機能の強化という、当時の Go コミュニティからの強い要望がありました。

具体的には、以下の点が挙げられます。

1.  **トレーシングとアナリティクスの必要性**: 分散システムやマイクロサービスアーキテクチャが普及するにつれて、HTTP リクエストがシステム内でどのように処理されているかを詳細に把握するニーズが高まっていました。DNS ルックアップ、TCP コネクションの確立、TLS ハンドシェイク、リクエストの送信、レスポンスの受信といった各段階での時間やエラー情報を収集することで、パフォーマンスのボトルネック特定や問題診断が容易になります。Issue #12580 は、まさに `http.Transport` レベルでの詳細なアナリティクスとトレーシングのメカニズムを求めるものでした。
2.  **`context.Context` の活用**: Go 1.7 で導入された `context.Context` は、リクエストスコープのデータ、キャンセルシグナル、デッドラインを複数のゴルーチン間で安全に伝播させるための標準的なメカニズムです。HTTP リクエストの処理中に、そのリクエストに関連するコンテキストをネットワーク層まで伝播させることで、以下のようなメリットが生まれます。
    *   **協調的なキャンセル**: リクエストがキャンセルされた場合（例: クライアントが接続を切断した、タイムアウトが発生した）、そのシグナルをネットワーク接続の確立やデータ送受信の段階まで伝え、不要な処理を中断できるようになります。
    *   **タイムアウトの適用**: リクエスト全体のタイムアウトを、ネットワーク接続の確立フェーズにも適用できるようになります。
    *   **リクエストスコープのデータ伝播**: トレーシング ID や認証情報など、リクエストに固有の情報をネットワーク層のフックに渡すことが可能になります。
3.  **`Transport.Dialer` の導入**: 既存の `Transport.Dial` フィールドは、`context.Context` を直接受け取ることができませんでした。`net.Dialer` は `DialContext` メソッドを提供しており、これを利用することで `context.Context` をネットワークダイヤル処理に伝播させることが可能になります。このコミットは、`Transport` に `Dialer` フィールドを追加し、`DialContext` を利用できるようにすることで、`context.Context` の伝播を可能にするための基盤を整備しました。

このコミット自体は、トレーシングやアナリティクス機能を直接実装するものではなく、「将来の CLs (Change Lists) がそれらを利用する」と明記されている通り、`context.Context` を `net/http.Transport` の内部のネットワーク操作に「配管（plumb）」するための準備作業でした。これにより、後続のコミットで `httptrace` パッケージのような高度なトレーシング機能が実装される道が開かれました。

Issue #13021 については、Go の公式イシュートラッカーでは直接的な関連が見つかりませんでしたが、コミットメッセージの文脈から、これも `context.Context` の伝播に関連する内部的な追跡番号、あるいは広範なコンテキスト伝播の改善プロジェクトの一部であったと推測されます。

## 前提知識の解説

### `net/http.Transport`

`net/http.Transport` は、Go の `net/http` パッケージにおいて、HTTP クライアントが実際にネットワーク通信を行うための設定とロジックをカプセル化する構造体です。`http.Client` は内部的に `http.RoundTripper` インターフェースを実装する `Transport` を使用してリクエストを送信します。

`Transport` は以下の主要な機能を提供します。

*   **コネクション管理**: TCP コネクションの確立、再利用（Keep-Alive）、プールを行います。これにより、複数のリクエストで同じコネクションを効率的に利用できます。
*   **プロキシ設定**: HTTP/HTTPS プロキシ経由での通信をサポートします。
*   **TLS 設定**: HTTPS 通信のための TLS (Transport Layer Security) 設定（証明書、キー、検証ポリシーなど）を管理します。
*   **タイムアウト**: コネクション確立、TLS ハンドシェイク、リクエスト/レスポンスの読み書きなど、様々な段階でのタイムアウトを設定できます。
*   **圧縮**: GZIP などのコンテンツエンコーディングを自動的に処理します。

開発者は `http.Client` の `Transport` フィールドにカスタムの `Transport` インスタンスを設定することで、これらの挙動を細かく制御できます。

### `context.Context`

`context.Context` は Go における重要なインターフェースであり、複数のゴルーチン間でリクエストスコープのデータ、キャンセルシグナル、デッドラインを安全かつ効率的に伝播させるためのメカニズムを提供します。

主な用途は以下の通りです。

*   **キャンセルシグナル**: `context.WithCancel` を使用して作成されたコンテキストは、親コンテキストがキャンセルされると、その子孫コンテキストにもキャンセルシグナルを伝播します。これにより、不要になった処理を協調的に中断できます。
*   **デッドライン/タイムアウト**: `context.WithDeadline` や `context.WithTimeout` を使用して、処理の最大実行時間を設定できます。時間が経過するとコンテキストは自動的にキャンセルされます。
*   **値の伝播**: `context.WithValue` を使用して、リクエストに固有のデータ（例: リクエスト ID、認証情報）をコンテキストに格納し、呼び出しスタックの下位にある関数に伝播させることができます。

`net/http` パッケージでは、`http.Request` に `context.Context` が埋め込まれており、`req.Context()` でアクセスできます。このコンテキストは、リクエストのライフサイクル全体にわたって伝播され、リクエストのキャンセルやタイムアウトを制御するために使用されます。

### `net.Dialer`

`net.Dialer` は、Go の `net` パッケージで提供される構造体で、ネットワーク接続を確立するための詳細な設定をカプセル化します。これにより、TCP や UDP などのネットワーク接続の挙動を細かく制御できます。

`net.Dialer` の主要なフィールドとメソッドには以下のようなものがあります。

*   **`Timeout`**: コネクション確立の最大時間。
*   **`KeepAlive`**: TCP Keep-Alive プローブを送信する間隔。
*   **`DualStack`**: IPv4 と IPv6 の両方で接続を試みるかどうか。
*   **`Control`**: ソケットが接続される前に raw ネットワーク接続をフックするための関数。
*   **`Dial(network, address string) (net.Conn, error)`**: 指定されたネットワークとアドレスに接続を確立します。
*   **`DialContext(ctx context.Context, network, address string) (net.Conn, error)`**: `context.Context` を受け取り、そのコンテキストのキャンセルシグナルやデッドラインに従って接続を確立します。これがこのコミットで重要となる点です。

## 技術的詳細

このコミットの技術的な核心は、`net/http.Transport` がネットワーク接続を確立する際に、`context.Context` をより深く、より柔軟に利用できるようにするための基盤を構築した点にあります。

1.  **`Transport.Dialer` フィールドの追加**:
    `http.Transport` 構造体に `Dialer *net.Dialer` という新しいフィールドが追加されました。これにより、ユーザーは `net.Dialer` のインスタンスを直接 `Transport` に設定できるようになります。`net.Dialer` は `Timeout` や `KeepAlive` といった詳細なネットワーク設定をカプセル化し、特に `DialContext` メソッドを通じて `context.Context` を利用した接続確立をサポートします。

2.  **`Transport.Dial` の非推奨化と優先順位**:
    既存の `Transport.Dial func(network, addr string) (net.Conn, error)` フィールドは非推奨（Deprecated）とされました。これは、`Dial` が `context.Context` を直接受け取ることができないためです。新しい `Dialer` フィールドが設定されている場合、`Transport` は `Dialer.DialContext` を優先的に使用するようになります。これにより、`context.Context` を利用したより高度な制御が可能になります。

3.  **`DefaultTransport` の更新**:
    `http.DefaultTransport` の初期化ロジックが変更され、既存の `Dial` フィールドに匿名 `net.Dialer` の `Dial` メソッドを割り当てる代わりに、`Dialer` フィールドに直接 `&net.Dialer{...}` インスタンスを割り当てるようになりました。これにより、デフォルトの `Transport` も新しい `Dialer` ベースのメカニズムを利用するようになります。

4.  **`dial` メソッドのシグネチャ変更とコンテキストの伝播**:
    `Transport` 内部で実際にネットワーク接続を確立する `dial` メソッドのシグネチャが変更されました。
    変更前: `func (t *Transport) dial(network, addr string) (net.Conn, error)`
    変更後: `func (t *Transport) dial(ctx context.Context, network, addr string) (net.Conn, error)`
    この変更により、`dial` メソッドは `context.Context` を引数として受け取るようになりました。メソッドの内部では、`t.Dialer` が設定されていれば `t.Dialer.DialContext(ctx, network, addr)` を呼び出し、`context.Context` をネットワーク層に伝播させます。これにより、コネクション確立中にコンテキストのキャンセルやタイムアウトを監視し、必要に応じて処理を中断できるようになります。

5.  **`getConn` から `dialConn` へのコンテキスト伝播**:
    `Transport` の `getConn` メソッドは、HTTP リクエストの `context.Context` を取得し、それを `dialConn` メソッドに渡すように変更されました。`dialConn` メソッドもまた `context.Context` を引数として受け取るようにシグネチャが変更され、内部で `t.dial` を呼び出す際にこのコンテキストを渡します。
    この一連の変更により、`http.Request` に紐付けられた `context.Context` が、コネクションの取得（既存コネクションの再利用または新規確立）から実際のネットワークダイヤル処理に至るまで、一貫して伝播されるようになりました。

これらの変更は、Go の `net/http` クライアントが、リクエストのライフサイクル全体にわたるよりきめ細やかな制御、特にトレーシング、アナリティクス、および協調的なキャンセルをサポートするための重要なステップでした。`context.Context` がネットワーク層まで「配管」されたことで、後続のコミットで `httptrace` パッケージのような機能が容易に実装できるようになりました。

## コアとなるコードの解説

### 1. `import "context"` の追加

`context` パッケージが導入され、`context.Context` 型が利用可能になりました。これは、リクエストのキャンセルシグナルやデッドラインを伝播させるために不可欠です。

### 2. `Transport` 構造体への `Dialer` フィールド追加と `DefaultTransport` の変更

```go
 // Transport struct definition
 type Transport struct {
     // ... other fields ...
     // Deprecated: Use Dialer instead. If both are specified, Dialer
     // takes precedence.
     Dial func(network, addr string) (net.Conn, error)

     // Dialer optionally specifies a dialer configuration to use
     // for new connections.
     Dialer *net.Dialer
     // ... other fields ...
 }

 // DefaultTransport initialization
 var DefaultTransport RoundTripper = &Transport{
     Proxy: ProxyFromEnvironment,
-    Dial: (&net.Dialer{
+    Dialer: &net.Dialer{
         Timeout:   30 * time.Second,
         KeepAlive: 30 * time.Second,
-    }).Dial,
+    },
     TLSHandshakeTimeout:   10 * time.Second,
     ExpectContinueTimeout: 1 * time.Second,
 }
```

*   `Transport` 構造体に `Dialer *net.Dialer` フィールドが追加されました。これにより、`net.Dialer` の持つ豊富な設定オプション（`Timeout`, `KeepAlive`, `DualStack` など）を直接 `http.Transport` に適用できるようになります。
*   既存の `Dial` フィールドは非推奨（`Deprecated`）とマークされ、`Dialer` が設定されている場合はそちらが優先される旨がコメントで明記されました。これは、`Dialer` が `context.Context` をサポートする `DialContext` を提供するためです。
*   `DefaultTransport` の初期化も変更され、匿名 `net.Dialer` の `Dial` メソッドを直接 `Dial` フィールドに割り当てるのではなく、`Dialer` フィールドに `&net.Dialer{...}` インスタンスを割り当てるようになりました。これにより、デフォルトの `Transport` も新しい `Dialer` ベースのメカニズムを利用するようになります。

### 3. `Transport.dial` メソッドの変更

*   `Transport` 内部でネットワーク接続を確立する `dial` メソッドのシグネチャが `context.Context` を受け取るように変更されました。
*   メソッドの内部では、まず `t.Dialer` が設定されているかを確認します。設定されていれば、新しい `t.Dialer.DialContext(ctx, network, addr)` を呼び出し、受け取った `context.Context` をネットワーク層に伝播させます。これにより、コネクション確立中にコンテキストのキャンセルやタイムアウトを監視し、必要に応じて処理を中断できるようになります。
*   `t.Dialer` が設定されていない場合は、引き続き非推奨となった `t.Dial` フィールドが使用されます。

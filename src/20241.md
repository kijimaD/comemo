# [インデックス 20241] ファイルの概要

このコミットは、Go言語のCコンパイラ（`cmd/cc`）とGoランタイムにおける関数呼び出し規約（Calling Convention）の統一に関するものです。具体的には、CコンパイラがGoの関数呼び出し規約に準拠するように変更され、引数と戻り値のスタック上での配置方法が統一されました。これにより、GoとC言語間の相互運用性（interoperability）が大幅に向上し、C関数をGoで段階的に書き換えることが容易になります。また、Goの`go vet`ツールを活用して、ランタイムのアセンブリコードの検証と修正が行われ、特にレガシーなシステムにおける潜在的なバグが修正されました。

## 元コミット内容

```
cmd/cc, runtime: convert C compilers to use Go calling convention

To date, the C compilers and Go compilers differed only in how
values were returned from functions. This made it difficult to call
Go from C or C from Go if return values were involved. It also made
assembly called from Go and assembly called from C different.

This CL changes the C compiler to use the Go conventions, passing
results on the stack, after the arguments.
[Exception: this does not apply to C ... functions, because you don't
know where on the stack the arguments end.]

By doing this, the CL makes it possible to rewrite C functions into Go
one at a time, without worrying about which languages call that
function or which languages it calls.

This CL also updates all the assembly files in package runtime to use
the new conventions. Argument references of the form 40(SP) have
been rewritten to the form name+10(FP) instead, and there are now
Go func prototypes for every assembly function called from C or Go.
This means that 'go vet runtime' checks effectively every assembly
function, and go vet's output was used to automate the bulk of the
conversion.

Some functions, like seek and nsec on Plan 9, needed to be rewritten.

Many assembly routines called from C were reading arguments
incorrectly, using MOVL instead of MOVQ or vice versa, especially on
the less used systems like openbsd.
These were found by go vet and have been corrected too.
If we're lucky, this may reduce flakiness on those systems.

Tested on:
        darwin/386
        darwin/amd64
        linux/arm
        linux/386
        linux/amd64
If this breaks another system, the bug is almost certainly in the
sys_$GOOS_$GOARCH.s file, since the rest of the CL is tested
by the combination of the above systems.
```

## 変更の背景

Go言語は、その初期からC言語との相互運用性を重視してきました。しかし、GoコンパイラとGoが内部的に使用するCコンパイラ（`cmd/cc`、`cmd/5c`、`cmd/6c`、`cmd/8c`など）の間で、関数呼び出し規約、特に戻り値の扱いに関して差異がありました。

この差異は、以下のような問題を引き起こしていました。

1.  **GoとC間の関数呼び出しの複雑化**: GoからC関数を呼び出す際、またはCからGo関数を呼び出す際に、戻り値の受け渡し方法が異なるため、特別なラッパーや変換が必要となり、コードが複雑化していました。
2.  **アセンブリコードの記述の困難さ**: GoとCの両方から呼び出されるアセンブリ関数を記述する際、それぞれの呼び出し規約に合わせた異なる実装が必要となり、メンテナンス性が低下していました。
3.  **C関数のGoへの移行の障壁**: 既存のCコードベースをGoに段階的に移行しようとする際、関数呼び出し規約の不一致が大きな障壁となっていました。特定の関数がCとGoのどちらからも呼び出される可能性がある場合、その関数の書き換えは非常に困難でした。

このコミットは、これらの問題を解決し、GoとCの間のよりシームレスな相互運用性を実現することを目的としています。特に、CコンパイラがGoの呼び出し規約に合わせることで、GoとCの境界を意識することなく、関数を呼び出せるようにすることが狙いです。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

### 1. 関数呼び出し規約 (Calling Convention)

関数呼び出し規約とは、プログラムにおいて関数が呼び出される際に、引数の渡し方、戻り値の受け取り方、レジスタの使用方法、スタックの管理方法などを定めた取り決めです。CPUアーキテクチャやOS、コンパイラによって様々な規約が存在します。

*   **引数の渡し方**:
    *   **レジスタ渡し**: 引数をCPUのレジスタに格納して渡す方法。高速ですが、レジスタ数に限りがあります。
    *   **スタック渡し**: 引数をスタックにプッシュして渡す方法。引数の数に制限がなく、再帰呼び出しにも対応しやすいですが、レジスタ渡しよりは低速です。
*   **戻り値の受け取り方**:
    *   **レジスタ渡し**: 戻り値をレジスタに格納して返す方法。
    *   **スタック渡し**: 戻り値をスタックに格納して返す方法。大きな構造体などを返す場合に用いられることがあります。
*   **スタックポインタ (SP) とフレームポインタ (FP)**:
    *   **スタックポインタ (SP)**: 現在のスタックの最上位（または最下位）を指すレジスタ。スタックのプッシュ/ポップによって値が変化します。
    *   **フレームポインタ (FP)**: 現在の関数のスタックフレームの基点を指すレジスタ。関数内でローカル変数や引数にアクセスする際の基準点として使われます。Goのアセンブリでは、引数は`name+offset(FP)`の形式で参照されることが多く、これはFPからのオフセットで引数にアクセスしていることを意味します。一方、`offset(SP)`はSPからのオフセットで、ローカル変数や一時的な値にアクセスする際に使われます。

### 2. Go言語のランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理する非常に重要な部分です。ガベージコレクション、スケジューラ（ゴルーチンの管理）、メモリ割り当て、システムコールなど、Goプログラムの低レベルな動作の多くを担っています。Goランタイムの一部は、パフォーマンス上の理由やOSとの直接的なやり取りのために、アセンブリ言語で記述されています。

### 3. Goのアセンブリ言語

Goは、独自の（Plan 9アセンブラに似た）アセンブリ言語を使用します。これは一般的なIntel構文やAT&T構文とは異なります。Goのアセンブリでは、関数引数は`name+offset(FP)`の形式で参照され、ローカル変数は`offset(SP)`の形式で参照されます。

### 4. `go vet`ツール

`go vet`は、Goのソースコードを静的に解析し、潜在的なバグや疑わしい構成を報告するツールです。このコミットでは、特にアセンブリコードにおける関数プロトタイプと実際の引数/戻り値の利用が一致しているかを検証するために活用されました。

### 5. `MOVL`と`MOVQ` (x86/x64アセンブリ命令)

*   **`MOVL`**: 32ビットのデータを移動する命令（Move Long）。
*   **`MOVQ`**: 64ビットのデータを移動する命令（Move Quadword）。

これらの命令の誤用は、特に32ビットと64ビットのシステム間でポインタや整数値のサイズが異なる場合に、データの破損やクラッシュを引き起こす可能性があります。

### 6. Plan 9

Plan 9は、ベル研究所で開発された分散オペレーティングシステムです。Go言語の開発者の一部はPlan 9の設計に深く関わっており、Goのツールチェインやアセンブリ言語の構文にはPlan 9の影響が見られます。

## 技術的詳細

このコミットの核となる技術的変更は、GoのCコンパイラ（`cmd/5c`, `cmd/6c`, `cmd/8c`など）が、Goコンパイラと同じ関数呼び出し規約を使用するように修正された点です。

従来のCコンパイラとGoコンパイラの主な違いは、**戻り値の渡し方**にありました。Goの呼び出し規約では、戻り値は引数の後にスタックに配置されます。これは、複数の戻り値を効率的に扱うため、またGoのスタック管理モデルと整合性を保つためです。一方、従来のCコンパイラは、戻り値をレジスタ（例: `AX`、`DX`）や、隠れたポインタ引数を通じて渡すことが一般的でした。

このコミットでは、以下の具体的な変更が行われました。

1.  **Cコンパイラの戻り値処理の変更**:
    *   Cコンパイラが生成するコードにおいて、関数の戻り値が引数の後にスタックに配置されるように変更されました。これにより、GoとCの関数呼び出し規約が統一され、相互運用時の複雑な変換が不要になります。
    *   ただし、Cの可変長引数関数（`...`を使用する関数）については、引数の終わりがコンパイル時に確定できないため、この新しい規約は適用されません。
    *   `regret`関数のシグネチャが変更され、戻り値の型情報とモード（戻り値のフェッチ、格納など）をより詳細に制御できるようになりました。これにより、スタック上の戻り値の正確な位置を計算し、アクセスすることが可能になります。

2.  **ランタイムアセンブリファイルの更新**:
    *   Goランタイム内のすべてのアセンブリファイル（`src/pkg/runtime/asm_*.s`、`src/pkg/runtime/sys_*.s`など）が、新しいGoの呼び出し規約に準拠するように更新されました。
    *   特に重要な変更は、アセンブリコード内で引数を参照する方法です。従来の`offset(SP)`形式（例: `40(SP)`）から、`name+offset(FP)`形式（例: `buf+0(FP)`、`fv+0(FP)`、`argp+4(FP)`など）に書き換えられました。これは、Goのツールチェインがスタックフレームをより正確に解析し、デバッグ情報やプロファイリング情報を生成するために重要です。`FP`は関数フレームの開始点を基準とするため、引数の位置がより安定して参照できます。
    *   GoからCまたはCからGoで呼び出されるすべてのアセンブリ関数に対して、Goの関数プロトタイプが追加されました。これにより、`go vet runtime`コマンドがこれらのアセンブリ関数を効果的にチェックできるようになり、引数の型や数が正しく使用されているかを静的に検証できるようになりました。

3.  **`go vet`による自動化とバグ修正**:
    *   `go vet`の出力が、アセンブリコードの変換作業の大部分を自動化するために利用されました。これは、`go vet`が関数プロトタイプとアセンブリコードの不一致を検出する能力があるためです。
    *   特に、`MOVL`と`MOVQ`の誤用など、引数の読み込みに関する既存のバグが`go vet`によって発見され、修正されました。これらのバグは、特にOpenBSDのようなあまり使用されないシステムで不安定性（flakiness）を引き起こす可能性がありました。

4.  **特定の関数の書き換え**:
    *   Plan 9の`seek`や`nsec`のような一部の関数は、新しい呼び出し規約に適合させるために完全に書き換えが必要でした。

これらの変更により、GoとCの間のインターフェースがより堅牢になり、将来的にCコードをGoに移行する際の柔軟性が向上しました。

## コアとなるコードの変更箇所

このコミットは広範囲にわたる変更を含んでいますが、特に重要なコアとなる変更箇所は以下のファイル群に見られます。

1.  **Cコンパイラのソースコード (`src/cmd/{5,6,8}c/`)**:
    *   `src/cmd/{5,6,8}c/cgen.c`: コード生成ロジック。関数呼び出し時の戻り値の処理が変更されています。特に`_cgen`関数内の`OFUNC`（関数呼び出し）ケースで、戻り値がスタックに配置されるように修正されています。
    *   `src/cmd/{5,6,8}c/gc.h`: ヘッダーファイル。`argsize`関数と`regret`関数のシグネチャが変更されています。
        *   `vlong argsize(void)` -> `vlong argsize(int)`: 引数サイズ計算関数にモード引数が追加されました。
        *   `void regret(Node*, Node*)` -> `void regret(Node*, Node*, Type*, int)`: 戻り値レジスタ割り当て関数に型とモード引数が追加されました。
    *   `src/cmd/{5,6,8}c/txt.c`: テキスト生成（アセンブリコード生成）ロジック。`regret`関数の実装が大幅に変更され、Goの呼び出し規約に従って戻り値をスタックに配置するロジックが追加されました。特に、`mode`引数によって戻り値のフェッチ（`mode == 1`）や格納（`mode == 2`）の動作が制御されます。
    *   `src/cmd/cc/pgen.c`: `hasdotdotdot`関数と`argsize`関数の実装が変更され、可変長引数関数の扱いと引数サイズの計算がGoの規約に合わせられています。

2.  **Goランタイムのアセンブリファイル (`src/pkg/runtime/asm_*.s`, `src/pkg/runtime/sys_*.s`)**:
    *   `src/pkg/runtime/asm_386.s`, `src/pkg/runtime/asm_amd64.s`, `src/pkg/runtime/asm_amd64p32.s`, `src/pkg/runtime/asm_arm.s`:
        *   `runtime·gosave`, `runtime·gogo`, `runtime·mcall`, `runtime·newstackcall`などの重要なランタイム関数において、スタックポインタ（`SP`）からのオフセットで引数を参照していた箇所が、フレームポインタ（`FP`）からのオフセット（例: `buf+0(FP)`, `fv+0(FP)`, `argp+4(FP)`など）に書き換えられています。
        *   `runtime·cas`, `runtime·cas64`, `runtime·casp`, `runtime·xadd`, `runtime·xchg`などのアトミック操作関数や、`runtime·getcallerpc`, `runtime·getcallersp`, `runtime·cputicks`などの低レベル関数でも同様の変更が行われています。
        *   戻り値の格納方法も、新しい規約に合わせて変更されています（例: `MOVL AX, ret+12(FP)`）。
    *   `src/pkg/runtime/sys_darwin_386.s`, `src/pkg/runtime/sys_linux_amd64.s`など、各OS/アーキテクチャ固有のシステムコールラッパーや低レベルアセンブリファイルも同様に更新されています。

3.  **GoランタイムのGoソースコード (`src/pkg/runtime/`)**:
    *   `src/pkg/runtime/alg.go`: `aeshash`関連の関数プロトタイプが追加されています。
    *   `src/pkg/runtime/stubs.go`: 新しいシステムコールやランタイム関数のスタブが追加されています。
    *   `src/pkg/runtime/os_*.go` (新規ファイル): 各OS固有のシステムコール関数プロトタイプがGoコードとして定義されています。これは、アセンブリ関数にGoのプロトタイプを与えることで`go vet`によるチェックを可能にするためです。

## コアとなるコードの解説

### Cコンパイラの変更 (`src/cmd/{5,6,8}c/txt.c`の`regret`関数)

`regret`関数は、関数の戻り値を処理する際に呼び出される重要な関数です。このコミットで、そのシグネチャと内部ロジックが大きく変更されました。

```c
void
regret(Node *n, Node *nn, Type *t, int mode)
{
 	int r;

 	if(mode == 0 || hasdotdotdot(t) || nn->type->width == 0) {
 		r = REGRET;
 		if(typefd[nn->type->etype])
 			r = FREGRET+NREG; // For floating point returns
 		nodreg(n, nn, r);
 		reg[r]++;
 		return;
 	}

 	if(mode == 1) {
 		// fetch returned value after call.
 		// already called gargs, so curarg is set.
 		curarg -= n->type->width; // Adjust curarg to point to the return value
 		regaalloc(n, nn); // Allocate register for return value
 		return;
 	}

 	if(mode == 2) {
 		// store value to be returned.
 		// must compute arg offset.
 		if(t->etype != TFUNC)
 			fatal(Z, "bad regret func %T", t);
 		*n = *nn;
 		n->op = ONAME;
 		n->class = CPARAM;
 		n->sym = slookup(".ret"); // Special symbol for return value on stack
 		n->complex = nodret->complex;
 		n->xoffset = argsize(0); // Calculate offset for return value on stack
 		n->addable = 20;
 		return;
 	}

 	fatal(Z, "bad regret");
}
```

*   **`mode`引数**: この新しい引数によって、`regret`関数の動作が制御されます。
    *   `mode == 0`: 従来の動作（レジスタによる戻り値処理）または可変長引数関数の場合。
    *   `mode == 1`: 関数呼び出し後に戻り値をスタックからフェッチする場合。`curarg`（現在の引数オフセット）を調整し、戻り値が配置されているスタック上の位置から値を読み取ります。
    *   `mode == 2`: 関数から戻り値をスタックに格納する場合。`.ret`という特殊なシンボル（Goの呼び出し規約で戻り値が置かれるスタック上の場所を示す）を使用し、`argsize(0)`で計算されたオフセットに値を書き込みます。

この変更により、CコンパイラはGoの呼び出し規約に従って戻り値をスタックに配置し、またスタックから読み取ることができるようになりました。

### ランタイムアセンブリファイルの変更 (例: `src/pkg/runtime/asm_386.s`の`runtime·gosave`)

多くのランタイムアセンブリ関数で、引数へのアクセス方法が変更されました。

**変更前**:
```assembly
TEXT runtime·gosave(SB), NOSPLIT, $0-4
	MOVL	4(SP), AX		// gobuf
	LEAL	4(SP), BX		// caller's SP
```
ここでは、`4(SP)`のようにスタックポインタ（`SP`）からのオフセットで引数にアクセスしています。これは、関数呼び出し時に引数がスタックにプッシュされた位置を直接参照しています。

**変更後**:
```assembly
TEXT runtime·gosave(SB), NOSPLIT, $0-4
	MOVL	buf+0(FP), AX		// gobuf
	LEAL	buf+0(FP), BX		// caller's SP
```
変更後では、`buf+0(FP)`のようにフレームポインタ（`FP`）からのオフセットと引数の名前（`buf`）を使って引数にアクセスしています。Goのアセンブリでは、`name+offset(FP)`の形式が推奨されており、これはGoのツールチェインがスタックフレームをより正確に解析し、デバッグ情報やプロファイリング情報を生成するために重要です。`FP`は関数フレームの開始点を基準とするため、引数の位置がより安定して参照できます。

この変更は、Goのツールチェインがアセンブリコードをより深く理解し、静的解析（`go vet`など）やデバッグを容易にするための基盤となります。

# [インデックス 25250] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおけるリライトルールに、生成されるSSA値のターゲットブロックを明示的に指定する機能を追加するものです。これにより、特定のメモリ操作が正しい基本ブロックに配置されることが保証され、コンパイラの正確性と最適化能力が向上します。

## コミット

```
[dev.ssa] cmd/compile: allow rewrite rules to specify a target block

Some rewrite rules need to make sure the rewrite target ends up
in a specific block. For example:

(MOVBQSX (MOVBload [off] {sym} ptr mem)) ->
   @v.Args[0].Block (MOVBQSXload <v.Type> [off] {sym} ptr mem)

The MOVBQSXload op needs to be in the same block as the MOVBload
(to ensure exactly one memory is live at basic block boundaries).

Reviewed-on: https://go-review.googlesource.com/15804
Reviewed-by: Josh Bleecher Snyder <josharian@gmail.com>
```

## 元コミット内容

GoコンパイラのSSAバックエンドにおいて、リライトルールが生成するSSA値のターゲットとなる基本ブロックを明示的に指定できるようにする変更です。これにより、特にメモリ操作に関連するリライトにおいて、生成された操作が元の操作と同じ基本ブロックに配置されることを保証し、SSAの不変条件（特にメモリのライブネスに関するもの）を維持します。

具体的には、リライトルールの結果部分に `@block` ディレクティブを追加することで、新しいSSA値がどのブロックに属するかを指定できるようになりました。この変更は、`rulegen.go` ツールによって生成されるリライトコードに影響を与え、`AMD64.rules` や `generic.rules` のようなルールファイルがこの新機能を利用するように更新されています。

## 変更の背景

GoコンパイラのSSAバックエンドでは、プログラムの最適化のために様々なリライトルールが適用されます。これらのルールは、あるSSA操作のパターンをより効率的な別のパターンに変換します。しかし、一部の操作、特にメモリを扱う操作（ロード、ストアなど）では、生成される新しいSSA値が特定の基本ブロックに配置されることが極めて重要になります。

例えば、`MOVBQSXload`（符号拡張ロード）のような操作は、元の `MOVBload`（バイトロード）と同じ基本ブロックに存在する必要があります。これは、SSA形式におけるメモリモデルの制約によるものです。SSAでは、各基本ブロックの境界でメモリの状態が正確に1つだけ「ライブ」である必要があります。もしリライトによってメモリ操作が異なるブロックに移動してしまうと、この不変条件が破られ、コンパイラの健全性が損なわれたり、誤ったコードが生成されたりする可能性があります。

以前は、このような制約を `cond: b == v.Args[0].Block` のような条件式で表現していましたが、これはリライトルールの複雑さを増し、また生成されるコードも冗長になる可能性がありました。このコミットは、リライトルールの構文レベルでターゲットブロックを指定できるようにすることで、この問題をより直接的かつ効率的に解決することを目的としています。

## 前提知識の解説

### 1. GoコンパイラとSSA (Static Single Assignment) フォーム

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現としてSSAフォームを使用します。SSAフォームは、各変数が一度だけ代入されるという特性を持つため、データフロー解析や最適化が容易になります。

*   **基本ブロック (Basic Block)**: プログラムの制御フローグラフを構成する基本的な単位で、入り口が1つ、出口が1つであり、内部に分岐を含まない一連の命令シーケンスです。SSA値は特定の基本ブロック内で定義され、使用されます。
*   **SSA値 (Value)**: SSAフォームにおける操作の単位です。各値はオペレーション（Op）、引数（Args）、型（Type）、補助情報（AuxInt, Aux）などを持っています。
*   **メモリモデルとSSA**: SSAでは、メモリ操作（ロード、ストア）も特殊なSSA値として扱われます。これにより、メモリへのアクセス順序や依存関係を明示的に表現し、最適化を可能にします。各基本ブロックの終端では、そのブロックで最後に更新されたメモリの状態を表すSSA値が「ライブ」であると見なされます。この「ライブなメモリ」は、次のブロックのメモリ操作の入力となります。

### 2. リライトルール (Rewrite Rules)

GoコンパイラのSSAバックエンドでは、`src/cmd/compile/internal/ssa/gen/*.rules` ファイルに記述されたリライトルールを用いて、SSA値を最適化します。これらのルールは、パターンマッチングと置換の形式で記述されており、`rulegen.go` ツールによってGoのコードに変換されます。

*   **ルール構文**: `(パターン) [&& 条件] -> (結果)` の形式を取ります。
    *   `パターン`: マッチさせたいSSA値の構造をS式（S-expression）で記述します。
    *   `条件`: パターンに加えて満たすべき追加の条件（例: `b == v.Args[0].Block`）。
    *   `結果`: パターンがマッチした場合に生成される新しいSSA値の構造。

### 3. `MOVBQSXload`, `MOVBQZXload`, `MOVBload`, `StructSelect`, `Load`, `OffPtr`

これらはGoコンパイラのSSA中間表現における特定の操作（Op）です。

*   `MOVBload`: メモリから1バイトをロードする操作。
*   `MOVBQSXload`: メモリから1バイトをロードし、符号拡張（Signed eXtension）してより大きなレジスタに格納する操作。
*   `MOVBQZXload`: メモリから1バイトをロードし、ゼロ拡張（Zero eXtension）してより大きなレジスタに格納する操作。
*   `Load`: 一般的なメモリロード操作。
*   `StructSelect`: 構造体の特定のフィールドを選択する操作。
*   `OffPtr`: ポインタにオフセットを加算する操作。

これらの操作は、メモリの読み書きやデータ構造へのアクセスに関連しており、SSAのメモリモデルの制約を遵守することが特に重要です。

## 技術的詳細

このコミットの核心は、`src/cmd/compile/internal/ssa/gen/rulegen.go` にあるリライトルールジェネレータの変更です。

1.  **ルール構文の拡張**:
    リライトルールの結果部分に `@block` ディレクティブが導入されました。
    変更前: `sexpr [&& extra conditions] -> sexpr`
    変更後: `sexpr [&& extra conditions] -> [@block] sexpr`
    ここで `block` は、新しいSSA値が配置されるべき基本ブロックを指す式です（例: `v.Args[0].Block`）。

2.  **`rulegen.go` の変更**:
    *   `genResult` 関数が、結果S式の先頭に `@` があるかどうかをチェックするようになりました。
    *   もし `@` があれば、それに続くブロック指定（例: `v.Args[0].Block`）を抽出し、新しいSSA値を生成する際にそのブロックを使用するように `genResult0` に渡します。
    *   `genResult0` 関数は、新しい引数 `loc` (location block) を受け取るようになり、新しいSSA値を作成する際に `b.NewValue0(...)` の代わりに `loc.NewValue0(...)` を呼び出すようになります。
    *   これにより、生成されるGoコードでは、新しいSSA値が指定されたブロックに作成されるようになります。
    *   さらに、元のSSA値 `v` を新しいSSA値のコピーに変換する処理が追加されました。これは、リライトによって新しい値が生成された場合、元の値がその新しい値を指すようにすることで、SSAグラフの整合性を保つためです。

3.  **リライトルールの更新**:
    `AMD64.rules` と `generic.rules` の関連するリライトルールが、この新しい `@block` 構文を使用するように更新されました。
    例えば、`AMD64.rules` の以下のルールが変更されました。
    変更前:
    `(MOVBQSX (MOVBload [off] {sym} ptr mem)) && b == v.Args[0].Block -> (MOVBQSXload [off] {sym} ptr mem)`
    変更後:
    `(MOVBQSX (MOVBload [off] {sym} ptr mem)) -> @v.Args[0].Block (MOVBQSXload <v.Type> [off] {sym} ptr mem)`
    これにより、`MOVBQSXload` 操作が `MOVBload` と同じブロック (`v.Args[0].Block`) に確実に配置されるようになります。以前の `cond: b == v.Args[0].Block` という条件は不要になり、ルールがより簡潔になりました。

4.  **生成されたコードの変更**:
    `rewriteAMD64.go` と `rewritegeneric.go` は `rulegen.go` によって生成されるファイルです。これらのファイルでは、リライトロジックが変更され、新しいSSA値が `v.Args[0].Block.NewValue0(...)` を使って作成され、その後、元の `v` がこの新しい値のコピーとして設定されるようになっています。

この変更により、コンパイラはメモリ操作のリライトにおいて、より厳密なブロック配置の制御が可能となり、SSAのメモリ不変条件をより確実に維持できるようになります。これは、コンパイラの正確性を高め、将来的な最適化の余地を広げる上で重要な改善です。

## コアとなるコードの解説

### `rulegen.go` の変更点

1.  **`genResult` 関数の変更**:
    この関数はリライトルールの結果部分を処理し、対応するGoコードを生成します。
    新しいコードでは、`result` 文字列の最初の文字が `'@'` であるかをチェックします。もしそうであれば、これはターゲットブロック指定ディレクティブであると解釈されます。
    `strings.SplitN(result[1:], " ", 2)` を使用して、`@` の後のブロック指定（例: `v.Args[0].Block`）と、実際のSSA値のS式を分離します。
    抽出されたブロック指定は `loc` 変数に格納され、`genResult0` 関数に新しい引数として渡されます。これにより、新しいSSA値がどの基本ブロックに作成されるかを制御できるようになります。

2.  **`genResult0` 関数の変更**:
    この関数は、`genResult` から呼び出され、個々のSSA値の生成ロジックを扱います。
    新しい引数 `loc string` が追加されました。これは、新しいSSA値を作成する際に使用する基本ブロックを指します。
    以前は `b.NewValue0(...)` を直接呼び出していましたが、変更後は `fmt.Fprintf(w, "%s := %s.NewValue0(v.Line, %s, TypeInvalid)\\n", v, loc, opName(s[0], arch))` のように、`loc` 変数で指定されたブロックに対して `NewValue0` を呼び出すようになりました。これにより、新しいSSA値が指定されたブロックに正確に配置されます。
    さらに、`if top` ブロック内に、元のSSA値 `v` を新しいSSA値のコピーに変換するロジックが追加されました。これは、リライトによって新しいSSA値が生成された場合、元のSSA値がその新しい値を指すようにすることで、SSAグラフの整合性を保つための重要なステップです。具体的には、`v.Op = OpCopy` と設定し、新しいSSA値を `v` の唯一の引数として追加します。

### `AMD64.rules` および `generic.rules` の変更点

これらのルールファイルでは、メモリ操作に関連するリライトルールが更新されています。
例えば、`MOVBQSX` のルールでは、以前は `&& b == v.Args[0].Block` という条件で、生成される `MOVBQSXload` が元の `MOVBload` と同じブロックにあることを保証していました。
新しい構文では、この条件が削除され、結果部分に `@v.Args[0].Block` が追加されています。これにより、`rulegen.go` が生成するコードが、`MOVBQSXload` を `v.Args[0].Block` に直接作成するようになります。これは、ルールの意図をより明確にし、生成されるコードを簡潔にする効果があります。

これらの変更により、GoコンパイラはSSAバックエンドでのメモリ操作のリライトにおいて、よりきめ細やかな制御と正確性を実現できるようになりました。

# [インデックス 26342] ファイルの概要

このコミットは、Goコンパイラのエスケープ解析におけるバグ修正を目的としています。特に、ループ内でヒープに割り当てられたオブジェクトが、ループ外で宣言された別のオブジェクトを参照している場合に、その参照されるオブジェクトが正しくヒープにエスケープされないという問題に対処しています。この修正により、エスケープ解析がループレベルをまたがる参照をより正確にモデル化できるようになり、誤ったスタック割り当てによるランタイムパニックを防ぎます。

## 元コミット内容

`cmd/compile: better modeling of escape across loop levels`

このコミットは、Goコンパイラのエスケープ解析において、ループレベルをまたがるエスケープのモデル化を改善します。具体的には、ヒープに割り当てられたオブジェクトが、ループ外で宣言された別のオブジェクトを参照している場合に、その参照されるオブジェクトが正しくヒープにエスケープされないというバグを修正します。

## 変更の背景

Go言語では、変数がスタックに割り当てられるかヒープに割り当てられるかを決定するために「エスケープ解析」と呼ばれるコンパイラ最適化が行われます。スタック割り当ては高速ですが、変数の寿命が関数呼び出しの範囲内に限定されます。一方、ヒープ割り当ては変数の寿命が長く、関数呼び出し後もデータが保持されますが、ガベージコレクションのオーバーヘッドが発生します。

変数がヒープに割り当てられる主な理由は以下の通りです。

1.  **アドレスが公開される（published）**: 変数のアドレスが外部に公開され、その寿命が不明になる場合。
2.  **サイズが不明または大きすぎる**: コンパイル時にサイズが決定できない、またはスタックに収まらないほど大きい場合。
3.  **多重度が不明または大きすぎる**: ループ内で繰り返し割り当てられるなど、インスタンスの数が不明または多すぎる場合。
4.  **ヒープから到達可能**: ヒープに割り当てられた別のオブジェクトから参照されている場合。

このコミットで修正されたバグは、上記の理由4）に関連しています。具体的には、理由3）によってヒープに割り当てられたオブジェクトX（例：ループ内で割り当てられ、ループ外の変数に代入されるクロージャ）が、ループ外で宣言されたオブジェクトY（例：クロージャがキャプチャするマップ）を参照しているケースで発生しました。オブジェクトY自体は公開されておらず、サイズも多重度も既知であるため、本来であればスタックに割り当てられる可能性があります。しかし、オブジェクトYはヒープに割り当てられたXから到達可能であるため、Yもヒープにエスケープされるべきでした。

しかし、既存のエスケープ解析では、この「ヒープから到達可能」という条件がループレベルをまたいで正しく追跡されていませんでした。その結果、Yが誤ってスタックに割り当てられ、Xがヒープに割り当てられた後にYが解放されることで、不正なメモリアクセスやランタイムパニック（issue #13799）が発生していました。

## 前提知識の解説

### Goのエスケープ解析 (Escape Analysis)

Goコンパイラの重要な最適化の一つにエスケープ解析があります。これは、プログラム内の変数がスタックに割り当てられるべきか、それともヒープに割り当てられるべきかを決定するプロセスです。

*   **スタック割り当て**: 関数呼び出し時に確保され、関数が終了すると自動的に解放されるメモリ領域です。高速で、ガベージコレクションの対象外であるため、パフォーマンス上有利です。変数が関数のスコープ外に「エスケープ」しない場合に適用されます。
*   **ヒープ割り当て**: プログラム実行中に動的に確保され、ガベージコレクタによって管理されるメモリ領域です。スタックよりも低速で、ガベージコレクションのオーバーヘッドが発生しますが、変数の寿命が関数のスコープを超えても存続できます。変数が関数のスコープ外にエスケープする場合に適用されます。

エスケープ解析は、変数の参照がどのように伝播するかを追跡し、その変数が関数の呼び出し元やグローバルスコープからアクセスされ続ける可能性があるかどうかを判断します。

### ループレベル (Loop Levels)

Goコンパイラのエスケープ解析では、コードの構造、特にループのネストレベルを考慮して変数の寿命を判断します。`Escloopdepth`という値は、変数が宣言されたループの深さを示します。

*   `-1`: グローバルスコープ
*   `0`: 関数の戻り値変数
*   `1`: 関数トップレベル
*   それ以降: ループやラベルごとに深さが増加

変数がより深いループレベルで宣言され、より浅いループレベルや関数外から参照される場合、その変数はエスケープする可能性が高まります。

### クロージャ (Closures)

Goのクロージャは、それが定義された環境（外側の関数のローカル変数など）を「キャプチャ」できる関数リテラルです。クロージャが外側の変数をキャプチャし、そのクロージャ自体がエスケープする場合、キャプチャされた変数もエスケープする可能性があります。

## 技術的詳細

このコミットの核心は、エスケープ解析のロジック、特に`escwalk`関数とその関連データ構造の変更にあります。

### `NodeEscState`構造体の変更

`src/cmd/compile/internal/gc/esc.go`内の`NodeEscState`構造体に`Maxextraloopdepth int32`という新しいフィールドが追加されました。
*   `Escloopdepth`: ノードが宣言されたループの深さを示します。
*   `Maxextraloopdepth`: エスケープ解析の伝播中に、そのノードが到達可能になった最も深いループレベルを追跡するために使用されます。これは、ヒープに割り当てられたオブジェクトが、より深いループレベルで宣言されたオブジェクトを参照している場合に、その参照されるオブジェクトもヒープにエスケープさせるために重要です。

### `escwalk`関数の変更と`escwalkBody`の導入

既存の`escwalk`関数は、`escwalkBody`という新しい関数を呼び出すように変更されました。`escwalkBody`は、`extraloopdepth int32`という追加の引数を受け取ります。
*   `escwalk(e *EscState, level Level, dst *Node, src *Node)`
*   `escwalkBody(e *EscState, level Level, dst *Node, src *Node, extraloopdepth int32)`

`extraloopdepth`は、現在のエスケープ解析の伝播において、ヒープ割り当てが強制された際の最小ループレベルを保持します。

### エスケープ解析の伝播ロジックの変更

`escwalkBody`関数内で、エスケープ解析の伝播ロジックが以下のように変更されました。

1.  **`srcE.Maxextraloopdepth`の更新**: `src`ノードが既に訪問済みの場合、`extraloopdepth`が既存の`srcE.Maxextraloopdepth`または`srcE.Escloopdepth`よりも大きい場合にのみ処理を続行します。これは、より深いループレベルからのエスケープ情報が新しく見つかった場合にのみ、再解析を行うための最適化です。
2.  **`modSrcLoopdepth`の計算**: `src`ノードの実際のループ深さ`srcE.Escloopdepth`と、現在の伝播で考慮すべき`extraloopdepth`のうち、より深い方（大きい方）が`modSrcLoopdepth`として採用されます。これにより、ヒープ割り当てが強制されたオブジェクトのループレベルが、そのオブジェクトから到達可能な他のオブジェクトのエスケープ判断に影響を与えるようになります。
3.  **`leaks`条件の変更**: 変数がヒープにエスケープするかどうかを判断する`leaks`条件が、`dstE.Escloopdepth < srcE.Escloopdepth`から`dstE.Escloopdepth < modSrcLoopdepth`に変更されました。これにより、`extraloopdepth`によって調整されたループレベルがエスケープ判断に反映され、ヒープから到達可能なオブジェクトが正しくエスケープされるようになります。
4.  **再帰呼び出しへの`extraloopdepth`の伝播**: `escwalkBody`の再帰呼び出しにおいて、`extraloopdepth`が`modSrcLoopdepth`として渡されるようになりました。これにより、ヒープ割り当てが強制されたオブジェクトのループレベル情報が、そのオブジェクトから参照される他のオブジェクトのエスケープ解析にも正しく伝播されます。

この修正の目的は、「ヒープに割り当てられたオブジェクトXから到達可能なオブジェクトYは、Yが直接エスケープする理由がなくても、Xの寿命に合わせてヒープにエスケープさせるべきである」という原則をエスケープ解析に組み込むことです。特に、ループレベルをまたがる参照において、この原則が正しく適用されるように`extraloopdepth`と`Maxextraloopdepth`が導入されました。

## コアとなるコードの解説

このコミットの主要な変更は、`src/cmd/compile/internal/gc/esc.go`内の`escwalk`および新しく導入された`escwalkBody`関数に集約されています。

`escwalk`関数は、Goコンパイラのエスケープ解析の主要な部分であり、AST (Abstract Syntax Tree) をトラバースして変数のエスケープ挙動を分析します。

変更の核心は、`extraloopdepth`という新しい概念の導入です。
以前は、変数のエスケープは主にその変数が宣言された`Escloopdepth`と、その変数が参照される`level`に基づいて判断されていました。しかし、今回のバグは、あるオブジェクトXが理由3（多重度不明/大きすぎる）でヒープに割り当てられ、そのXが理由4（ヒープから到達可能）でオブジェクトYを参照している場合に、Yが正しくエスケープされないというものでした。Y自体は理由1, 2, 3のいずれにも該当しないため、エスケープ解析はYをスタックに割り当てようとします。

`extraloopdepth`は、この問題を解決するために導入されました。
1.  `NodeEscState`に`Maxextraloopdepth`が追加され、ノードがこれまでに到達した最も深い`extraloopdepth`を記録します。これにより、エスケープ解析の伝播が収束する際に、より深いループレベルからのエスケープ情報が失われないようにします。
2.  `escwalk`が`escwalkBody`を呼び出す際に、初期の`extraloopdepth`として`NOTALOOPDEPTH`（-1）を渡します。
3.  `escwalkBody`内で、`src`ノードがヒープにエスケープすることが判明した場合、そのヒープ割り当てが強制されたループレベル（`modSrcLoopdepth`）が計算されます。この`modSrcLoopdepth`は、`src`ノード自身の`Escloopdepth`と、現在の伝播で受け取った`extraloopdepth`の最大値となります。
4.  この`modSrcLoopdepth`は、`src`ノードから到達可能な他のノード（`ll.N`）のエスケープ解析を行う`escwalkBody`の再帰呼び出しに`extraloopdepth`として伝播されます。
5.  `leaks`条件（変数がヒープにエスケープするかどうかを判断する条件）が、`dstE.Escloopdepth < modSrcLoopdepth`に変更されました。これにより、ヒープに割り当てられたオブジェクトXの`modSrcLoopdepth`が、Xから参照されるオブジェクトYのエスケープ判断に影響を与え、Yも正しくヒープにエスケープされるようになります。

簡単に言えば、この修正は、ヒープに割り当てられたオブジェクトが、たとえそれが一時的なものであっても、そのオブジェクトが参照する他のオブジェクトの寿命を「引き上げる」効果をエスケープ解析に正しく反映させるものです。これにより、Goプログラムのメモリ安全性と安定性が向上します。

3.  **多重度が不明または大きすぎる**: ループ内で繰り返し割り当てられるなど、インスタンスの数が不明または多すぎる場合。
4.  **ヒープから到達可能**: ヒープに割り当てられた別のオブジェクトから参照されている場合。

このコミットで修正されたバグは、上記の理由4）に関連しています。具体的には、理由3）によってヒープに割り当てられたオブジェクトX（例：ループ内で割り当てられ、ループ外の変数に代入されるクロージャ）が、ループ外で宣言されたオブジェクトY（例：クロージャがキャプチャするマップ）を参照しているケースで発生しました。オブジェクトY自体は公開されておらず、サイズも多重度も既知であるため、本来であればスタックに割り当てられる可能性があります。しかし、オブジェクトYはヒープに割り当てられたXから到達可能であるため、Yもヒープにエスケープされるべきでした。

しかし、既存のエスケープ解析では、この「ヒープから到達可能」という条件がループレベルをまたいで正しく追跡されていませんでした。その結果、Yが誤ってスタックに割り当てられ、Xがヒープに割り当てられた後にYが解放されることで、不正なメモリアクセスやランタイムパニック（issue #13799）が発生していました。

## 前提知識の解説

### Goのエスケープ解析 (Escape Analysis)

Goコンパイラの重要な最適化の一つにエスケープ解析があります。これは、プログラム内の変数がスタックに割り当てられるべきか、それともヒープに割り当てられるべきかを決定するプロセスです。

*   **スタック割り当て**: 関数呼び出し時に確保され、関数が終了すると自動的に解放されるメモリ領域です。高速で、ガベージコレクションの対象外であるため、パフォーマンス上有利です。変数が関数のスコープ外に「エスケープ」しない場合に適用されます。
*   **ヒープ割り当て**: プログラム実行中に動的に確保され、ガベージコレクタによって管理されるメモリ領域です。スタックよりも低速で、ガベージコレクションのオーバーヘッドが発生しますが、変数の寿命が関数のスコープを超えても存続できます。変数が関数のスコープ外にエスケープする場合に適用されます。

エスケープ解析は、変数の参照がどのように伝播するかを追跡し、その変数が関数の呼び出し元やグローバルスコープからアクセスされ続ける可能性があるかどうかを判断します。

### ループレベル (Loop Levels)

Goコンパイラのエスケープ解析では、コードの構造、特にループのネストレベルを考慮して変数の寿命を判断します。`Escloopdepth`という値は、変数が宣言されたループの深さを示します。

*   `-1`: グローバルスコープ
*   `0`: 関数の戻り値変数
*   `1`: 関数トップレベル
*   それ以降: ループやラベルごとに深さが増加

変数がより深いループレベルで宣言され、より浅いループレベルや関数外から参照される場合、その変数はエスケープする可能性が高まります。

### クロージャ (Closures)

Goのクロージャは、それが定義された環境（外側の関数のローカル変数など）を「キャプチャ」できる関数リテラルです。クロージャが外側の変数をキャプチャし、そのクロージャ自体がエスケープする場合、キャプチャされた変数もエスケープする可能性があります。

## 技術的詳細

このコミットの核心は、エスケープ解析のロジック、特に`escwalk`関数とその関連データ構造の変更にあります。

### `NodeEscState`構造体の変更

`src/cmd/compile/internal/gc/esc.go`内の`NodeEscState`構造体に`Maxextraloopdepth int32`という新しいフィールドが追加されました。
*   `Escloopdepth`: ノードが宣言されたループの深さを示します。
*   `Maxextraloopdepth`: エスケープ解析の伝播中に、そのノードが到達可能になった最も深いループレベルを追跡するために使用されます。これは、ヒープに割り当てられたオブジェクトが、より深いループレベルで宣言されたオブジェクトを参照している場合に、その参照されるオブジェクトもヒープにエスケープさせるために重要です。

### `escwalk`関数の変更と`escwalkBody`の導入

既存の`escwalk`関数は、`escwalkBody`という新しい関数を呼び出すように変更されました。`escwalkBody`は、`extraloopdepth int32`という追加の引数を受け取ります。
*   `escwalk(e *EscState, level Level, dst *Node, src *Node)`
*   `escwalkBody(e *EscState, level Level, dst *Node, src *Node, extraloopdepth int32)`

`extraloopdepth`は、現在のエスケープ解析の伝播において、ヒープ割り当てが強制された際の最小ループレベルを保持します。

### エスケープ解析の伝播ロジックの変更

`escwalkBody`関数内で、エスケープ解析の伝播ロジックが以下のように変更されました。

1.  **`srcE.Maxextraloopdepth`の更新**: `src`ノードが既に訪問済みの場合、`extraloopdepth`が既存の`srcE.Maxextraloopdepth`または`srcE.Escloopdepth`よりも大きい場合にのみ処理を続行します。これは、より深いループレベルからのエスケープ情報が新しく見つかった場合にのみ、再解析を行うための最適化です。
2.  **`modSrcLoopdepth`の計算**: `src`ノードの実際のループ深さ`srcE.Escloopdepth`と、現在の伝播で考慮すべき`extraloopdepth`のうち、より深い方（大きい方）が`modSrcLoopdepth`として採用されます。これにより、ヒープ割り当てが強制されたオブジェクトのループレベルが、そのオブジェクトから到達可能な他のオブジェクトのエスケープ判断に影響を与えるようになります。
3.  **`leaks`条件の変更**: 変数がヒープにエスケープするかどうかを判断する`leaks`条件が、`dstE.Escloopdepth < srcE.Escloopdepth`から`dstE.Escloopdepth < modSrcLoopdepth`に変更されました。これにより、`extraloopdepth`によって調整されたループレベルがエスケープ判断に反映され、ヒープから到達可能なオブジェクトが正しくエスケープされるようになります。
4.  **再帰呼び出しへの`extraloopdepth`の伝播**: `escwalkBody`の再帰呼び出しにおいて、`extraloopdepth`が`modSrcLoopdepth`として渡されるようになりました。これにより、ヒープ割り当てが強制されたオブジェクトのループレベル情報が、そのオブジェクトから参照される他のオブジェクトのエスケープ解析にも正しく伝播されます。

この修正の目的は、「ヒープに割り当てられたオブジェクトXから到達可能なオブジェクトYは、Yが直接エスケープする理由がなくても、Xの寿命に合わせてヒープにエスケープさせるべきである」という原則をエスケープ解析に組み込むことです。特に、ループレベルをまたがる参照において、この原則が正しく適用されるように`extraloopdepth`と`Maxextraloopdepth`が導入されました。

## コアとなるコードの解説

このコミットの主要な変更は、`src/cmd/compile/internal/gc/esc.go`内の`escwalk`および新しく導入された`escwalkBody`関数に集約されています。

`escwalk`関数は、Goコンパイラのエスケープ解析の主要な部分であり、AST (Abstract Syntax Tree) をトラバースして変数のエスケープ挙動を分析します。

変更の核心は、`extraloopdepth`という新しい概念の導入です。
以前は、変数のエスケープは主にその変数が宣言された`Escloopdepth`と、その変数が参照される`level`に基づいて判断されていました。しかし、今回のバグは、あるオブジェクトXが理由3（多重度不明/大きすぎる）でヒープに割り当てられ、そのXが理由4（ヒープから到達可能）でオブジェクトYを参照している場合に、Yが正しくエスケープされないというものでした。Y自体は理由1, 2, 3のいずれにも該当しないため、エスケープ解析はYをスタックに割り当てようとします。

`extraloopdepth`は、この問題を解決するために導入されました。
1.  `NodeEscState`に`Maxextraloopdepth`が追加され、ノードがこれまでに到達した最も深い`extraloopdepth`を記録します。これにより、エスケープ解析の伝播が収束する際に、より深いループレベルからのエスケープ情報が失われないようにします。
2.  `escwalk`が`escwalkBody`を呼び出す際に、初期の`extraloopdepth`として`NOTALOOPDEPTH`（-1）を渡します。
3.  `escwalkBody`内で、`src`ノードがヒープにエスケープすることが判明した場合、そのヒープ割り当てが強制されたループレベル（`modSrcLoopdepth`）が計算されます。この`modSrcLoopdepth`は、`src`ノード自身の`Escloopdepth`と、現在の伝播で受け取った`extraloopdepth`の最大値となります。
4.  この`modSrcLoopdepth`は、`src`ノードから到達可能な他のノード（`ll.N`）のエスケープ解析を行う`escwalkBody`の再帰呼び出しに`extraloopdepth`として伝播されます。
5.  `leaks`条件（変数がヒープにエスケープするかどうかを判断する条件）が、`dstE.Escloopdepth < modSrcLoopdepth`に変更されました。これにより、ヒープに割り当てられたオブジェクトXの`modSrcLoopdepth`が、Xから参照されるオブジェクトYのエスケープ判断に影響を与え、Yも正しくヒープにエスケープされるようになります。

簡単に言えば、この修正は、ヒープに割り当てられたオブジェクトが、たとえそれが一時的なものであっても、そのオブジェクトが参照する他のオブジェクトの寿命を「引き上げる」効果をエスケープ解析に正しく反映させるものです。これにより、Goプログラムのメモリ安全性と安定性が向上します。

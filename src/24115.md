## 変更の背景

このコミットは、Goの`net/http/fcgi`パッケージにおいて、リクエストを処理する`serveRequest`メソッドと、子プロセスのクリーンアップを行う`cleanUp`メソッドの間で発生する可能性のある競合状態を解決するために導入されました。

FastCGI（Fast Common Gateway Interface）は、Webサーバーとアプリケーションプログラムを接続するためのプロトコルです。Goの`net/http/fcgi`パッケージは、GoアプリケーションがFastCGIサーバーとして動作するための機能を提供します。FastCGIサーバーは、通常、複数のリクエストを同時に処理するために、複数の子プロセス（またはスレッド）を管理します。

問題の核心は、`child`構造体が管理する`requests`マップへのアクセスが、`serveRequest`と`cleanUp`の両方から非同期に行われる可能性があったことです。`serveRequest`は新しいリクエストを処理し、`requests`マップにエントリを追加または更新する可能性があります。一方、`cleanUp`は、シャットダウン時などに`requests`マップをイテレートしてリソースを解放します。これらの操作が同時に行われると、マップの破損や予期せぬ動作（パニックなど）を引き起こす競合状態が発生する可能性があります。

特に、`cleanUp`が`c.requests`マップをイテレートしている最中に、`serveRequest`がマップを変更しようとすると、Goのランタイムはマップの同時変更を検知してパニックを引き起こすことがあります。このコミットは、この特定の競合状態を防止することを目的としています。

関連するIssue #11552は、この競合状態によって発生するパニックを報告しており、このコミットはその修正として提出されました。

## 前提知識の解説

### 1. FastCGI (Fast Common Gateway Interface)

FastCGIは、Webサーバー（例: Nginx, Apache）と動的なWebアプリケーション（例: Go, PHP, Python）の間でデータをやり取りするためのプロトコルです。CGI（Common Gateway Interface）の進化版であり、CGIがリクエストごとに新しいプロセスを起動するのに対し、FastCGIは永続的なプロセス（FastCGIサーバー）を維持し、複数のリクエストを処理することでパフォーマンスを向上させます。

Goの`net/http/fcgi`パッケージは、GoプログラムがFastCGIプロトコルを介してWebサーバーからのリクエストを受け取り、処理するためのインターフェースを提供します。

### 2. 競合状態 (Race Condition)

競合状態とは、複数のゴルーチン（またはスレッド）が共有リソース（このケースでは`child.requests`マップ）に同時にアクセスし、その結果としてプログラムの実行順序によって結果が変わってしまうバグのことです。特に、少なくとも1つのゴルーチンがリソースを書き換える場合に問題となります。Goでは、マップへの同時書き込みや、読み書きの同時アクセスは、明示的な同期メカニズムなしに行われるとパニックを引き起こす可能性があります。

### 3. ミューテックス (Mutex)

ミューテックス（Mutual Exclusion）は、共有リソースへのアクセスを同期するためのメカニズムです。Goでは`sync.Mutex`型として提供されます。ミューテックスは、ロックとアンロックの操作を提供します。あるゴルーチンがミューテックスをロックすると、他のゴルーチンはロックが解除されるまで待機しなければなりません。これにより、一度に一つのゴルーチンだけが共有リソースにアクセスすることを保証し、競合状態を防ぎます。

*   `mu.Lock()`: ミューテックスをロックします。既にロックされている場合は、ロックが解除されるまでブロックします。
*   `mu.Unlock()`: ミューテックスのロックを解除します。

### 4. `defer`ステートメント

Goの`defer`ステートメントは、その関数がリターンする直前に実行される関数呼び出しをスケジュールします。これは、リソースの解放（ファイルのクローズ、ロックの解除など）を確実に行うために非常に便利です。`defer mu.Unlock()`と記述することで、関数のどのパスを通っても、`mu.Unlock()`が確実に呼び出され、ミューテックスが解放されることが保証されます。

## 技術的詳細

`net/http/fcgi`パッケージの`child`構造体は、FastCGIの子プロセスを表し、複数のリクエストを処理する責任を持ちます。この構造体には、現在処理中のリクエストを追跡するための`requests`というマップが含まれています。

```go
type child struct {
    // ...
    mu       sync.Mutex // protects requests
    requests map[uint32]*request
    // ...
}
```

`serveRequest`メソッドは、新しいFastCGIリクエストを受け取ると、この`requests`マップに新しいエントリを追加します。一方、`cleanUp`メソッドは、子プロセスがシャットダウンする際に、未処理のリクエストをクリーンアップするために`requests`マップをイテレートします。

問題は、`cleanUp`が`requests`マップをイテレートしている最中に、`serveRequest`がマップに書き込みを行うと、Goのランタイムがマップの同時変更を検知してパニックを引き起こす可能性があったことです。これは、Goのマップが並行アクセスに対して安全ではないためです。

このコミットの修正は、`cleanUp`関数が`requests`マップにアクセスする際に、`child`構造体内のミューテックス`c.mu`を使用して排他制御を行うことで、この競合状態を解消します。

具体的には、`cleanUp`関数の冒頭で`c.mu.Lock()`を呼び出してロックを取得し、`defer c.mu.Unlock()`を使って関数が終了する際に確実にロックを解放するようにしています。これにより、`cleanUp`が`requests`マップを操作している間は、他のゴルーチン（`serveRequest`など）がマップにアクセスしようとしてもブロックされ、マップの同時変更が防止されます。

コミットメッセージにある「`// race with call to Close in c.serveRequest doesn't matter because`」というコメントは、`req.pw`（おそらくパイプの書き込み側）の`Close`呼び出しと`serveRequest`内の`Close`呼び出しとの間の競合は問題ではないことを示唆しています。これは、`Close`操作が冪等であるか、あるいは特定の状況下で安全に並行して実行できるためと考えられます。しかし、`requests`マップへのアクセスはそうではないため、明示的な同期が必要でした。

## コアとなるコードの解説

追加された2行は以下の通りです。

1.  `c.mu.Lock()`:
    `cleanUp`関数が実行される際に、まず`child`構造体に関連付けられたミューテックス`c.mu`をロックします。これにより、`cleanUp`が`requests`マップにアクセスしている間、他のゴルーチンが同じミューテックスをロックしようとしてもブロックされ、`requests`マップへの同時アクセスが防止されます。

2.  `defer c.mu.Unlock()`:
    `defer`キーワードにより、この行は`cleanUp`関数がリターンする直前に実行されるようにスケジュールされます。これにより、`cleanUp`関数が正常に終了する場合でも、エラーが発生して途中でリターンする場合でも、確実にミューテックスがアンロックされ、他のゴルーチンが`requests`マップにアクセスできるようになります。これは、リソースの解放を確実に行うGoのイディオムです。

この修正により、`cleanUp`が`c.requests`マップをイテレートしている最中に`serveRequest`がマップを変更しようとすることがなくなり、競合状態によるパニックが解消されます。

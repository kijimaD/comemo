## 変更の背景

Go言語のスライスは、その内部構造としてポインタ、長さ (length)、そして容量 (capacity) を持ちます。長さはスライスが現在保持している要素の数を示し、容量は基底配列が保持できる要素の総数を示します。通常、`len(s) <= cap(s)` の関係が成り立ちます。

特定の操作、特にスライスの再スライス（例: `p = p[:8:len(p)]`）を行った後など、スライスの容量がその長さと厳密に等しくなる状況が発生することがあります。このような場合、`cap(p)` の値は `len(p)` の値と同一になります。

Goコンパイラは、プログラムの実行効率を向上させるために様々な最適化を行います。このコミットの背景にあるのは、このような `cap(s) == len(s)` の状況をコンパイラが認識し、`SliceCap` 操作をより単純な `SliceLen` 操作に置き換えることで、コンパイルされたコードの効率をさらに高めるという目的です。`SliceLen` は `SliceCap` よりも計算が単純であるか、あるいは既に計算済みの値を利用できる場合があるため、この置き換えはパフォーマンス上の利点をもたらす可能性があります。

## 前提知識の解説

### Go言語のスライス (Go Slices)

Go言語のスライスは、配列を抽象化したデータ構造であり、可変長シーケンスを表現するために使用されます。スライスは以下の3つの要素から構成されます。

1.  **ポインタ (Pointer)**: スライスが参照する基底配列の先頭要素へのポインタ。
2.  **長さ (Length)**: スライスが現在保持している要素の数。`len()` 関数で取得できます。
3.  **容量 (Capacity)**: スライスが拡張できる最大要素数。基底配列のサイズからスライスの開始位置を引いた値に相当します。`cap()` 関数で取得できます。

スライスの再スライス操作 `s[low:high:max]` は、新しいスライスを作成します。ここで `low` は新しいスライスの開始インデックス、`high` は新しいスライスの長さの終端インデックス（`high - low` が新しいスライスの長さ）、`max` は新しいスライスの容量の終端インデックス（`max - low` が新しいスライスの容量）を決定します。`max` を省略した場合、基底配列の容量が新しいスライスの容量となります。コミットメッセージにある `p[:8:len(p)]` の例では、新しいスライスの容量が元のスライスの長さと等しくなるように指定されています。

### GoコンパイラとSSA (Static Single Assignment)

Goコンパイラは、Go言語のソースコードを実行可能なバイナリコードに変換するツールです。コンパイルプロセスには複数のステージがあり、その一つに中間表現 (IR: Intermediate Representation) の最適化があります。Goコンパイラは、この中間表現としてSSA (Static Single Assignment) 形式を採用しています。

**SSA形式**とは、プログラム中の各変数が一度だけ代入されるように変換された形式です。これにより、データフロー解析や最適化が容易になります。SSA形式では、変数の値が変更されるたびに新しい「バージョン」の変数が作成されると考えることができます。

### SSA最適化ルール

GoコンパイラのSSAバックエンドでは、プログラムのSSA形式をより効率的なSSA形式に変換するための一連の最適化ルールが適用されます。これらのルールは、特定のパターン（操作の組み合わせ）を検出し、それをより単純または効率的な別のパターンに置き換えることで機能します。これらのルールは通常、専用のファイル（例: `generic.rules`）に記述され、コンパイラによって読み込まれて適用されます。

### `SliceCap` と `SliceLen`

*   **`SliceCap`**: SSA形式におけるスライスの容量を取得する操作を表します。Goの組み込み関数 `cap()` に対応します。
*   **`SliceLen`**: SSA形式におけるスライスの長さを取得する操作を表します。Goの組み込み関数 `len()` に対応します。

## 技術的詳細

このコミットの主要な技術的変更は、GoコンパイラのSSA最適化ルールに新しいエントリを追加することです。

### `src/cmd/compile/internal/ssa/gen/generic.rules` の変更

`generic.rules` ファイルは、GoコンパイラのSSAバックエンドがコードを最適化するために使用するパターンマッチングルールを定義しています。追加されたルールは以下の通りです。

```
(SliceCap (SliceMake _ _ (SliceLen x))) -> (SliceLen x)
```

このルールは次のように解釈されます。

*   **`SliceCap`**: 最適化の対象となる操作は、スライスの容量を取得する `SliceCap` です。
*   **`(SliceMake _ _ (SliceLen x))`**: `SliceCap` の引数（オペランド）が `SliceMake` 操作である場合を指します。
    *   `SliceMake` は、SSA形式で新しいスライスを構築する操作です。その引数は通常、`(ポインタ, 長さ, 容量)` に対応します。
    *   `_` は任意の値を意味します。ここではポインタと長さの引数はこのルールでは重要ではありません。
    *   `(SliceLen x)`: `SliceMake` の3番目の引数（容量）が、別のスライス `x` の長さを取得する `SliceLen` 操作である場合。

つまり、このルールは「もし `SliceCap` が、その容量が別のスライスの長さと等しくなるように構築されたスライスに対して適用される場合」というパターンを検出します。

*   **`-> (SliceLen x)`**: このパターンが検出された場合、`SliceCap` 操作全体を `SliceLen x` に置き換えます。これは、元のスライスの容量がその長さと等しいことが確定しているため、容量を取得する代わりに長さを取得する操作に置き換えても結果は同じであり、かつ `SliceLen` の方が効率的である可能性が高いからです。

この最適化は、特に `p = p[:8:len(p)]` のような再スライス操作の後で効果を発揮します。このような操作では、新しいスライスの容量が元のスライスの長さと等しくなるため、その後の `cap(p)` の呼び出しが `len(p)` に置き換えられ、コンパイラがより効率的なコードを生成できるようになります。

### `src/cmd/compile/internal/ssa/rewritegeneric.go` の変更

このファイルでは、`rewriteValuegeneric_OpIsInBounds` 関数内で、`v.Args[0]` や `v.Args[1]` といったSSA値の引数への直接アクセスを、`v_0 := v.Args[0]` や `v_1 := v.Args[1]` のように一時変数に割り当てる変更が行われています。

これは、SSA最適化ルールとは直接的な機能変更ではありませんが、SSAのコード生成や最適化パスにおいて一般的なプラクティスです。この変更の意図としては、以下の点が考えられます。

1.  **可読性の向上**: 同じ引数に複数回アクセスする場合、一時変数に格納することでコードが読みやすくなります。
2.  **SSA最適化の促進**: SSA形式では、各変数が一度だけ代入されるという特性があります。引数を一時変数に割り当てることで、SSAのルールエンジンがより単純なパターンでマッチングしやすくなる可能性があります。これは、コンパイラがより効果的に最適化を適用するための準備的なステップとなることがあります。
3.  **将来的な変更への対応**: 将来的にこれらの引数に対してさらに複雑な操作やチェックが追加される場合に備え、コード構造を整理する目的があるかもしれません。

このコミットの主要な目的は `SliceCap` の最適化ですが、`rewritegeneric.go` の変更は、SSAバックエンドのコード品質と保守性を向上させるための補助的な変更と見なせます。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/gen/generic.rules` の追加ルール

追加されたルール `(SliceCap (SliceMake _ _ (SliceLen x))) -> (SliceLen x)` は、GoコンパイラのSSA最適化パスにおいて、スライスの容量がその長さと等しいという特定のパターンを検出して最適化するためのものです。

具体的には、以下のようなGoコードがコンパイルされ、SSA形式に変換された際にこのルールが適用される可能性があります。

```go
package main

func main() {
	s := make([]int, 5, 10) // len=5, cap=10
	// ...
	// 何らかの操作で s の長さが変更され、
	// その後、容量が長さに等しくなるように再スライスされる
	s = s[:3:3] // len=3, cap=3
	
	// この時点で cap(s) は len(s) と等しい
	_ = cap(s) // ここで SliceCap 操作が発生
}
```

上記の `_ = cap(s)` の部分がSSA形式で `(SliceCap (SliceMake ... (SliceLen x)))` のような構造になった場合、このルールが適用され、`SliceCap` 操作が `SliceLen` 操作に置き換えられます。これにより、コンパイラは容量を計算する代わりに、既に利用可能な長さの情報を再利用できるため、より効率的な機械語コードを生成できます。

### `src/cmd/compile/internal/ssa/rewritegeneric.go` の変更

`rewritegeneric.go` は、SSA形式の値を書き換える（最適化する）ためのGoコードが記述されているファイルです。このコミットでは、主に `rewriteValuegeneric_OpIsInBounds` 関数内で、`v.Args[0]` や `v.Args[1]` といったSSA値の引数へのアクセス方法が変更されています。

    break

```go

## 変更の背景

Go言語のスライスは、その内部構造としてポインタ、長さ (length)、そして容量 (capacity) を持ちます。長さはスライスが現在保持している要素の数を示し、容量は基底配列が保持できる要素の総数を示します。通常、`len(s) <= cap(s)` の関係が成り立ちます。

特定の操作、特にスライスの再スライス（例: `p = p[:8:len(p)]`）を行った後など、スライスの容量がその長さと厳密に等しくなる状況が発生することがあります。このような場合、`cap(p)` の値は `len(p)` の値と同一になります。

Goコンパイラは、プログラムの実行効率を向上させるために様々な最適化を行います。このコミットの背景にあるのは、このような `cap(s) == len(s)` の状況をコンパイラが認識し、`SliceCap` 操作をより単純な `SliceLen` 操作に置き換えることで、コンパイルされたコードの効率をさらに高めるという目的です。`SliceLen` は `SliceCap` よりも計算が単純であるか、あるいは既に計算済みの値を利用できる場合があるため、この置き換えはパフォーマンス上の利点をもたらす可能性があります。

## 前提知識の解説

### Go言語のスライス (Go Slices)

Go言語のスライスは、配列を抽象化したデータ構造であり、可変長シーケンスを表現するために使用されます。スライスは以下の3つの要素から構成されます。

1.  **ポインタ (Pointer)**: スライスが参照する基底配列の先頭要素へのポインタ。
2.  **長さ (Length)**: スライスが現在保持している要素の数。`len()` 関数で取得できます。
3.  **容量 (Capacity)**: スライスが拡張できる最大要素数。基底配列のサイズからスライスの開始位置を引いた値に相当します。`cap()` 関数で取得できます。

スライスの再スライス操作 `s[low:high:max]` は、新しいスライスを作成します。ここで `low` は新しいスライスの開始インデックス、`high` は新しいスライスの長さの終端インデックス（`high - low` が新しいスライスの長さ）、`max` は新しいスライスの容量の終端インデックス（`max - low` が新しいスライスの容量）を決定します。`max` を省略した場合、基底配列の容量が新しいスライスの容量となります。コミットメッセージにある `p[:8:len(p)]` の例では、新しいスライスの容量が元のスライスの長さと等しくなるように指定されています。

### GoコンパイラとSSA (Static Single Assignment)

Goコンパイラは、Go言語のソースコードを実行可能なバイナリコードに変換するツールです。コンパイルプロセスには複数のステージがあり、その一つに中間表現 (IR: Intermediate Representation) の最適化があります。Goコンパイラは、この中間表現としてSSA (Static Single Assignment) 形式を採用しています。

**SSA形式**とは、プログラム中の各変数が一度だけ代入されるように変換された形式です。これにより、データフロー解析や最適化が容易になります。SSA形式では、変数の値が変更されるたびに新しい「バージョン」の変数が作成されると考えることができます。

### SSA最適化ルール

GoコンパイラのSSAバックエンドでは、プログラムのSSA形式をより効率的なSSA形式に変換するための一連の最適化ルールが適用されます。これらのルールは、特定のパターン（操作の組み合わせ）を検出し、それをより単純または効率的な別のパターンに置き換えることで機能します。これらのルールは通常、専用のファイル（例: `generic.rules`）に記述され、コンパイラによって読み込まれて適用されます。

### `SliceCap` と `SliceLen`

*   **`SliceCap`**: SSA形式におけるスライスの容量を取得する操作を表します。Goの組み込み関数 `cap()` に対応します。
*   **`SliceLen`**: SSA形式におけるスライスの長さを取得する操作を表します。Goの組み込み関数 `len()` に対応します。

## 技術的詳細

このコミットの主要な技術的変更は、GoコンパイラのSSA最適化ルールに新しいエントリを追加することです。

### `src/cmd/compile/internal/ssa/gen/generic.rules` の変更

`generic.rules` ファイルは、GoコンパイラのSSAバックエンドがコードを最適化するために使用するパターンマッチングルールを定義しています。追加されたルールは以下の通りです。

```
(SliceCap (SliceMake _ _ (SliceLen x))) -> (SliceLen x)
```

このルールは次のように解釈されます。

*   **`SliceCap`**: 最適化の対象となる操作は、スライスの容量を取得する `SliceCap` です。
*   **`(SliceMake _ _ (SliceLen x))`**: `SliceCap` の引数（オペランド）が `SliceMake` 操作である場合を指します。
    *   `SliceMake` は、SSA形式で新しいスライスを構築する操作です。その引数は通常、`(ポインタ, 長さ, 容量)` に対応します。
    *   `_` は任意の値を意味します。ここではポインタと長さの引数はこのルールでは重要ではありません。
    *   `(SliceLen x)`: `SliceMake` の3番目の引数（容量）が、別のスライス `x` の長さを取得する `SliceLen` 操作である場合。

つまり、このルールは「もし `SliceCap` が、その容量が別のスライスの長さと等しくなるように構築されたスライスに対して適用される場合」というパターンを検出します。

*   **`-> (SliceLen x)`**: このパターンが検出された場合、`SliceCap` 操作全体を `SliceLen x` に置き換えます。これは、元のスライスの容量がその長さと等しいことが確定しているため、容量を取得する代わりに長さを取得する操作に置き換えても結果は同じであり、かつ `SliceLen` の方が効率的である可能性が高いからです。

この最適化は、特に `p = p[:8:len(p)]` のような再スライス操作の後で効果を発揮します。このような操作では、新しいスライスの容量が元のスライスの長さと等しくなるため、その後の `cap(p)` の呼び出しが `len(p)` に置き換えられ、コンパイラがより効率的なコードを生成できるようになります。

### `src/cmd/compile/internal/ssa/rewritegeneric.go` の変更

このファイルでは、`rewriteValuegeneric_OpIsInBounds` 関数内で、`v.Args[0]` や `v.Args[1]` といったSSA値の引数への直接アクセスを、`v_0 := v.Args[0]` や `v_1 := v.Args[1]` のように一時変数に割り当てる変更が行われています。

これは、SSA最適化ルールとは直接的な機能変更ではありませんが、SSAのコード生成や最適化パスにおいて一般的なプラクティスです。この変更の意図としては、以下の点が考えられます。

1.  **可読性の向上**: 同じ引数に複数回アクセスする場合、一時変数に格納することでコードが読みやすくなります。
2.  **SSA最適化の促進**: SSA形式では、各変数が一度だけ代入されるという特性があります。引数を一時変数に割り当てることで、SSAのルールエンジンがより単純なパターンでマッチングしやすくなる可能性があります。これは、コンパイラがより効果的に最適化を適用するための準備的なステップとなることがあります。
3.  **将来的な変更への対応**: 将来的にこれらの引数に対してさらに複雑な操作やチェックが追加される場合に備え、コード構造を整理する目的があるかもしれません。

このコミットの主要な目的は `SliceCap` の最適化ですが、`rewritegeneric.go` の変更は、SSAバックエンドのコード品質と保守性を向上させるための補助的な変更と見なせます。

### `src/cmd/compile/internal/ssa/gen/generic.rules` の追加ルール

追加されたルール `(SliceCap (SliceMake _ _ (SliceLen x))) -> (SliceLen x)` は、GoコンパイラのSSA最適化パスにおいて、スライスの容量がその長さと等しいという特定のパターンを検出して最適化するためのものです。

具体的には、以下のようなGoコードがコンパイルされ、SSA形式に変換された際にこのルールが適用される可能性があります。

```go
package main

func main() {
	s := make([]int, 5, 10) // len=5, cap=10
	// ...
	// 何らかの操作で s の長さが変更され、
	// その後、容量が長さに等しくなるように再スライスされる
	s = s[:3:3] // len=3, cap=3
	
	// この時点で cap(s) は len(s) と等しい
	_ = cap(s) // ここで SliceCap 操作が発生
}
```

上記の `_ = cap(s)` の部分がSSA形式で `(SliceCap (SliceMake ... (SliceLen x)))` のような構造になった場合、このルールが適用され、`SliceCap` 操作が `SliceLen` 操作に置き換えられます。これにより、コンパイラは容量を計算する代わりに、既に利用可能な長さの情報を再利用できるため、より効率的な機械語コードを生成できます。

### `src/cmd/compile/internal/ssa/rewritegeneric.go` の変更

`rewritegeneric.go` は、SSA形式の値を書き換える（最適化する）ためのGoコードが記述されているファイルです。このコミットでは、主に `rewriteValuegeneric_OpIsInBounds` 関数内で、`v.Args[0]` や `v.Args[1]` といったSSA値の引数へのアクセス方法が変更されています。

変更前:
```go
if v.Args[0].Op != OpZeroExt8to32 {
    break
}
if v.Args[1].Op != OpConst32 {
    break
}
c := v.Args[1].AuxInt
```

変更後:
```go
v_0 := v.Args[0]
if v_0.Op != OpZeroExt8to32 {
    break
}
v_1 := v.Args[1]
if v_1.Op != OpConst32 {
    break
}
c := v_1.AuxInt
```

この変更は、SSA形式のコードを処理する際の一般的なリファクタリングパターンです。`v.Args[N]` はSSA値のN番目の引数を表します。これらの引数を一時変数 (`v_0`, `v_1`) に割り当てることで、コードの可読性が向上し、同じ引数に複数回アクセスする場合の冗長性が減ります。また、SSAの最適化パスがより効果的にパターンを認識し、最適化を適用しやすくなる可能性があります。これは、SSAのルールエンジンが、より単純な変数参照に対してパターンマッチングを行う方が効率的であるためです。

さらに、`rewriteValuegeneric_OpSliceCap` 関数にも、`generic.rules` で定義された新しいルールに対応するGoコードが追加されています。これは、`generic.rules` で定義されたパターンが検出された際に、実際にSSA値を書き換えるロジックを実装する部分です。

```go
	// match: (SliceCap (SliceMake _ _ (SliceLen x)))
	// cond:
	// result: (SliceLen x)
	for {
		v_0 := v.Args[0]
		if v_0.Op != OpSliceMake {
			break
		}
		v_0_2 := v_0.Args[2]
		if v_0_2.Op != OpSliceLen {
			break
		}
		x := v_0_2.Args[0]
		v.reset(OpSliceLen)
		v.AddArg(x)
		return true
	}
```
このコードブロックは、`SliceCap` 操作が `SliceMake` 操作を引数として持ち、その `SliceMake` の容量部分が `SliceLen` 操作であるというパターンを検出します。このパターンにマッチした場合、元の `SliceCap` 操作を `SliceLen` 操作にリセットし、`x` をその引数として追加することで、最適化を適用します。

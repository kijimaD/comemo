# [インデックス 17328] ファイルの概要

このコミットは、Goランタイムにおいて、ファイナライザが`g0`スタック上で実行されないようにする変更です。これにより、ガベージコレクション(GC)の完了後、ファイナライザが適切なゴルーチンスタック上でスケジュールされ、ランタイムの安定性と予測可能性が向上します。特に、GCが完了し、通常のゴルーチンスタックに戻った後にファイナライザスレッドが起動されるように調整されています。また、`runtime.mallocgc`の呼び出しから`FlagNoInvokeGC`フラグが削除されています。

## 変更の背景

この変更の背景には、Goランタイムにおけるファイナライザの実行タイミングとスタック管理の課題がありました。Goのファイナライザは、オブジェクトがガベージコレクタによって到達不能と判断された際に実行されるクリーンアップ関数です。しかし、GCの処理中にファイナライザが`g0`スタック（ランタイム内部の重要な処理に使用される特別なスタック）上で実行されると、予期せぬ問題やデッドロック、スタックの枯渇といった不安定な挙動を引き起こす可能性がありました。

特に、GCが完了した直後、ランタイムがまだ`g0`スタック上にいる状態でファイナライザの実行を試みると、通常のゴルーチンが使用するスタックとは異なる環境で処理が行われるため、ファイナライザが期待通りに動作しない、あるいはランタイム自体に悪影響を及ぼすリスクがありました。

このコミットは、GCが完了し、ランタイムが通常のゴルーチンスタック（`g`スタック）に戻ったことを確認してからファイナライザスレッドを起動するように修正することで、この問題を解決し、ランタイムの堅牢性を高めることを目的としています。また、`runtime.mallocgc`の呼び出しから`FlagNoInvokeGC`フラグが削除されたことも、メモリ割り当て時のGCトリガーに関する内部的な調整を示唆しています。

## 前提知識の解説

### Goランタイム

Goランタイムは、Goプログラムの実行を管理するシステムです。これには、ガベージコレクタ、スケジューラ、メモリ管理、ゴルーチン管理などが含まれます。Goプログラムは、OSのプロセスとして実行されますが、その内部で多数のゴルーチンを効率的にスケジューリングし、並行処理を実現しています。

### ゴルーチン (Goroutine)

ゴルーチンは、Goにおける軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数千から数百万のゴルーチンを同時に実行できます。ゴルーチンはGoランタイムによってスケジューリングされ、必要に応じてスタックが動的に伸縮します。

### `g0`スタック

`g0`スタックは、Goランタイムが内部的な処理（スケジューリング、システムコールハンドリング、スタックの伸縮など）を実行するために使用する特別なスタックです。通常のゴルーチンが使用するスタック（`g`スタック）とは異なり、固定サイズであり、Goプログラムのユーザーコードが直接アクセスすることはありません。ランタイムが`g0`スタック上で動作している間は、通常のゴルーチンの実行は一時的に中断されます。

### ファイナライザ (Finalizer)

Goのファイナライザは、`runtime.SetFinalizer`関数を使用してオブジェクトに設定できるクリーンアップ関数です。ガベージコレクタがそのオブジェクトが到達不能になったと判断した際に、ファイナライザが実行されます。ファイナライザは通常、ファイルディスクリプタやネットワーク接続など、メモリ以外のリソースを解放するために使用されます。ファイナライザは別のゴルーチンで実行されますが、その実行タイミングはGCに依存するため、厳密なリソース解放の保証はありません。Go 1.24以降では、`runtime.AddCleanup`というより改善されたファイナライズメカニズムが導入されています。

### ガベージコレクション (GC)

Goのガベージコレクタは、プログラムが不要になったメモリを自動的に解放するシステムです。GoのGCはマーク＆スイープアルゴリズムをベースにしており、並行的に動作することで、プログラムの実行を長時間停止させることなくメモリ管理を行います。GCのサイクル中、ランタイムは一時的にユーザーゴルーチンの実行を停止（"stop the world"）し、GCの重要なフェーズを実行することがあります。

### `runtime.gosched()`

`runtime.Gosched()`は、現在のゴルーチンがプロセッサを自発的に手放し、他の実行可能なゴルーチンに実行機会を与える関数です。これにより、Goスケジューラは別のゴルーチンをスケジュールできます。これはGoの協調的スケジューリングの一部であり、特に長時間計算を行うゴルーチンが他のゴルーチンをブロックしないようにするために使用されます。現代のGoではスケジューラのプリエンプションが強化されているため、明示的に`runtime.Gosched()`を呼び出す必要性は減っています。

### `runtime.mallocgc()`

`runtime.mallocgc()`は、Goランタイム内部のメモリ割り当て関数です。Goプログラムがヒープ上に新しいオブジェクトを割り当てる際（`make`や`new`など）、最終的にこの関数が呼び出されます。この関数は、メモリの割り当てだけでなく、必要に応じてガベージコレクションをトリガーする役割も担っています。

### `mgc0.c` と `stack.c`

これらは、Goの初期バージョン（Go 1.5より前）でGoランタイムの一部としてC言語で書かれていたソースファイルです。
*   `mgc0.c`: Goのメモリガベージコレクタ（MGC）に関連するCコードが含まれていました。
*   `stack.c`: ゴルーチンのスタック管理（作成、伸縮など）に関連するCコードが含まれていました。
Go 1.5以降、Goコンパイラとランタイムの大部分はGo言語で書き直され、これらの機能は現在、`src/runtime/mgc.go`や`src/runtime/stack.go`などのGoファイルに実装されています。

### `FlagNoProfiling`, `FlagNoGC`, `FlagNoZero`, `FlagNoInvokeGC`

これらはGoランタイム内部で使用されるフラグであり、公開されたAPIではありません。
*   `FlagNoProfiling`: プロファイリングを無効にするための内部フラグ。
*   `FlagNoGC`: ガベージコレクションを無効にするための内部フラグ。
*   `FlagNoZero`: 新しく割り当てられたメモリをゼロクリアしないことを示す内部フラグ。Goでは通常、新しく割り当てられたメモリはゼロ値で初期化されますが、特定のパフォーマンス最適化のためにこの動作を一時的に変更する場合があります。
*   `FlagNoInvokeGC`: メモリ割り当て時にGCを自動的にトリガーしないことを示す内部フラグ。

これらのフラグは、ランタイムの内部動作を制御し、デバッグや特定の最適化パスで使用されるものです。

## 技術的詳細

このコミットの主要な技術的変更点は、ガベージコレクションの完了後、ファイナライザの実行をスケジュールする際に、現在のゴルーチンが`g0`スタック上にいないことを確認する条件を追加したことです。

変更前のコードでは、GCが完了し、`runtime.starttheworld()`が呼び出されてユーザーゴルーチンの実行が再開された後、無条件にファイナライザスレッドの起動を試み、その後`runtime.gosched()`を呼び出して他のゴルーチンに実行機会を与えていました。この際、`runtime.gc`関数がまだ`g0`スタック上で実行されている可能性がありました。

`g0`スタックはランタイムの内部処理専用であり、ファイナライザのようなユーザーコードに近い処理（たとえそれがランタイムによってスケジュールされるものであっても）が`g0`スタック上で直接実行されることは望ましくありません。`g0`スタックはサイズが固定されており、複雑な処理や予期せぬスタック使用によって枯渇するリスクがあります。また、`g0`スタック上での実行は、通常のゴルーチンとは異なるコンテキストで行われるため、ファイナライザの動作が不安定になったり、ランタイムの他の部分に悪影響を及ぼしたりする可能性がありました。

このコミットでは、`runtime.gc`関数内でファイナライザスレッドを起動し、`runtime.gosched()`を呼び出す前に、`if(g != m->g0)`という条件を追加しています。ここで、`g`は現在のゴルーチン、`m->g0`は現在のM（OSスレッド）に関連付けられた`g0`ゴルーチンを指します。この条件により、現在の実行コンテキストが通常のゴルーチンスタック（`g`スタック）に戻っている場合にのみ`runtime.gosched()`が呼び出され、ファイナライザスレッドに実行機会が与えられるようになります。これにより、ファイナライザが`g0`スタック上で不適切に実行されることを防ぎ、ランタイムの安定性が向上します。

また、`src/pkg/runtime/stack.c`における`runtime.mallocgc`の呼び出しから`FlagNoInvokeGC`フラグが削除されています。これは、メモリ割り当て時にGCを自動的にトリガーしないという指示が、この特定のコンテキスト（おそらくスタック割り当て時）では不要になったか、あるいは別のメカニズムで制御されるようになったことを示唆しています。`runtime.stackalloc`はスタックの割り当てを行う関数であり、ここで`FlagNoInvokeGC`が削除されたということは、スタック割り当ての際にGCの自動トリガーを抑制する必要がなくなった、またはその制御がより上位のレイヤーで行われるようになったことを意味します。これは、ランタイムのメモリ管理とGCの連携に関する内部的な調整の一部と考えられます。

*   **コメントの変更**:
    *   `- // now that gc is done and we're back on g stack, kick off finalizer thread if needed`
    *   `+ // now that gc is done, kick off finalizer thread if needed`
    このコメントの変更は、GC完了後に「`g`スタックに戻った」という前提が、必ずしもこの時点では保証されないことを示唆しています。実際の`g`スタックへの復帰は、`runtime.gosched()`が呼び出され、スケジューラが別のゴルーチンをスケジュールした後に起こる可能性があります。

*   **`runtime.gosched()`の移動と条件付き実行**:
    変更前は、`if(finq != nil)`ブロックの直後に無条件で`runtime.gosched()`が呼び出されていました。
    変更後は、`runtime.gosched()`の呼び出しがブロックの外に移動し、さらに`if(g != m->g0)`という条件が追加されました。
    *   `g`は現在のゴルーチンを指します。
    *   `m->g0`は現在のOSスレッド（M）に関連付けられた`g0`ゴルーチンを指します。
    この条件`if(g != m->g0)`は、「現在のゴルーチンが`g0`スタック上にいない場合」を意味します。つまり、GCが完了し、ランタイムが通常のゴルーチンスタックに戻っている場合にのみ、`runtime.gosched()`が呼び出され、キューに入れられたファイナライザに実行機会が与えられるようになります。これにより、ファイナライザが`g0`スタック上で不適切に実行されることを防ぎ、ランタイムの安定性が向上します。

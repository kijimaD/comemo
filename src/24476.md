## 前提知識の解説

*   **Goの `encoding/json` パッケージ**: Go言語の標準ライブラリの一部で、JSONデータのエンコード（Goのデータ構造からJSONへ）とデコード（JSONからGoのデータ構造へ）を提供します。
*   **`json.Unmarshaler` インターフェース**: このインターフェースは、`UnmarshalJSON([]byte) error` メソッドを定義します。Goの型がこのインターフェースを実装している場合、`json.Unmarshal` 関数はその型の値をデコードする際に、デフォルトのデコードロジックの代わりにこのカスタムメソッドを呼び出します。これにより、開発者は特定の型に対してJSONデータのデコード方法を細かく制御できます。
*   **`null` 値のデコード**: JSONにおける `null` は、値が存在しないことを示します。Goの `json` パッケージが `null` をデコードする際、ポインタ型やインターフェース型、マップ、スライスなどに対しては、通常その値を `nil` に設定します。しかし、カスタムの `UnmarshalJSON` メソッドを持つ型の場合、`null` がどのように扱われるかは、そのメソッドの実装に依存します。
*   **`reflect` パッケージ**: Goの `reflect` パッケージは、実行時にプログラムの構造を検査・操作するための機能を提供します。`reflect.Value` はGoの値を抽象化したもので、その型や値を動的に操作できます。`v.IsNil()` は `reflect.Value` が `nil` であるかどうかをチェックし、`v.Type().NumMethod() > 0` はその型がメソッドを持っているかどうかをチェックします。

## 技術的詳細

このコミットの核心は、`src/encoding/json/decode.go` 内の `indirect` メソッドにおける条件式の変更です。

元の修正（リバートされたコミット `1a99ba55df902a2657d1ccfc52a60024c22dba98`）では、`indirect` メソッド内の `if` 文に `&& !decodingNull` という条件が追加されていました。これは、`json.Unmarshaler` インターフェースを実装している型であっても、現在デコード中の値がJSONの `null` である場合には、そのカスタム `UnmarshalJSON` メソッドを呼び出さないようにする意図があったと考えられます。

しかし、このリバートによって `!decodingNull` の条件が削除されました。これにより、`null` 値がデコードされる際にも、その型が `json.Unmarshaler` インターフェースを実装していれば、常にカスタムの `UnmarshalJSON` メソッドが呼び出されるようになります。

この変更は、`null` 値の扱いに関するGoの `encoding/json` パッケージの挙動を、以前の（おそらくより期待される）状態に戻すものです。例えば、ポインタ型のフィールドが `null` に設定されるべき場合でも、カスタム `UnmarshalJSON` が呼び出されてしまうと、そのメソッド内で `null` の処理を明示的に行わない限り、意図しない挙動になる可能性がありました。リバートされたことで、カスタム `UnmarshalJSON` メソッドは `null` 値に対しても呼び出され、そのメソッド内で `null` をどのように扱うかを開発者が完全に制御できるようになります。

`decode_test.go` から大量のテストコードが削除されているのは、リバートされた修正に関連するテストケースが不要になったためです。これらのテストは、おそらく `!decodingNull` 条件が導入された際に、その新しい挙動を検証するために追加されたものと考えられます。特に `AJson`, `AText`, `STime` といったカスタムの `UnmarshalJSON` や `UnmarshalText` を持つ型に関するテストが削除されており、これは `null` 値とカスタムアンマーシャリングの相互作用に関するテストであったことを強く示唆しています。

## コアとなるコードの解説

`src/encoding/json/decode.go` の `indirect` メソッドは、JSONデコード中にGoのポインタ型やインターフェース型を扱う際のロジックを含んでいます。

変更された行は以下の部分です。

```go
-		if v.Type().NumMethod() > 0 && !decodingNull {
+		if v.Type().NumMethod() > 0 {
```

*   `v.Type().NumMethod() > 0`: これは、`reflect.Value` `v` が表す型が何らかのメソッドを持っているかどうかをチェックします。`json.Unmarshaler` インターフェースを実装している型は、当然 `UnmarshalJSON` メソッドを持っています。
*   `!decodingNull`: これは、現在デコード中のJSONトークンが `null` でない場合に `true` となります。

リバート前のコード (`&& !decodingNull` があった状態) では、もし `v` が `json.Unmarshaler` を実装しており、かつデコード中の値が `null` でない場合にのみ、カスタムの `UnmarshalJSON` メソッドが呼び出されていました。つまり、`null` がデコードされる際には、カスタム `UnmarshalJSON` は呼び出されず、Goの `json` パッケージのデフォルトの `null` 処理（例えばポインタを `nil` に設定するなど）が適用されていました。

このコミットによるリバートでは、`&& !decodingNull` が削除されました。これにより、`v` が `json.Unmarshaler` を実装している限り、デコード中の値が `null` であってもなくても、常にカスタムの `UnmarshalJSON` メソッドが呼び出されるようになります。

この変更は、`json.Unmarshaler` を実装する型が `null` 値をどのように扱うかについて、より一貫性のある、開発者が完全に制御できる挙動を提供します。もし開発者が `null` 値に対して特別な処理を必要としない場合でも、`UnmarshalJSON` メソッド内で `null` のバイトスライス (`[]byte("null")`) を受け取り、それに応じて処理（例えば何もしない、またはエラーを返す）を記述する必要があります。

`decode_test.go` から削除されたテストコードは、この `!decodingNull` 条件が導入された際に、その挙動を検証するために書かれたものでした。特に、`null` 値がカスタムアンマーシャラーに渡されない場合の挙動をテストしていたと考えられます。リバートにより、その挙動が元に戻ったため、これらのテストも不要となり削除されました。

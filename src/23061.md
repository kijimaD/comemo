# [インデックス 23061] ファイルの概要

このコミットは、GoランタイムにおけるARM64アーキテクチャでのシステムコールエラーハンドリングの修正に関するものです。具体的には、Linux ARM64システムコールがエラーを返す際の挙動が、ARM32とは異なるため、その違いを適切に処理するようにGoランタイムの低レベルアセンブリコードが更新されました。

## 元コミット内容

Goランタイムにおいて、ARM64アーキテクチャでのシステムコールエラーコードのチェックが追加されました。Linux ARM32とは異なり、Linux ARM64ではシステムコールが失敗したかどうかを示すために条件コードを設定しないため、戻り値がエラーコードの範囲内にあるかどうかを明示的にチェックする必要がありました。この変更により、`runtime.TestBadOpen`テストが修正されました。

## 変更の背景

この変更の背景には、異なるCPUアーキテクチャ（ARM32とARM64）間でのシステムコールエラーハンドリングの挙動の違いがあります。

*   **Linux ARM32の挙動**: 従来のLinux ARM32では、システムコールが失敗した場合、CPUの条件コード（特にキャリーフラグ）が設定されることが一般的でした。これにより、システムコール直後に`BCC`（Branch if Carry Clear）のような条件分岐命令を使用することで、エラーの有無を効率的に判定し、エラー処理ルーチンへジャンプすることが可能でした。
*   **Linux ARM64の挙動**: しかし、Linux ARM64（AArch64）では、システムコールが失敗しても条件コードは自動的に設定されません。その代わりに、システムコールの戻り値が特定の負の範囲（通常は-1から-4095）にある場合にエラーを示します。これは、AMD64アーキテクチャでのシステムコールエラーハンドリングの挙動と類似しています。
*   **Goランタイムの課題**: Goランタイムは、様々なアーキテクチャとオペレーティングシステムをサポートするために、低レベルのシステムコールを直接呼び出すアセンブリコードを含んでいます。ARM64のシステムコールエラーハンドリングのこの違いが考慮されていなかったため、`runtime.TestBadOpen`のようなテストが失敗していました。このテストは、おそらく不正なファイルオープン操作をシミュレートし、システムコールが適切にエラーを返すことを期待していたと考えられます。

このコミットは、ARM64環境でGoプログラムがシステムコールエラーを正しく検出し、処理できるようにするために、このアーキテクチャ固有の挙動に対応する必要があったために行われました。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

1.  **システムコール**: オペレーティングシステム（OS）のカーネルが提供するサービスを、ユーザー空間のプログラムが利用するためのインターフェースです。ファイルI/O、メモリ管理、プロセス制御など、OSの機能にアクセスするために使用されます。
2.  **ARM64 (AArch64) アーキテクチャ**: ARMv8-Aアーキテクチャで導入された64ビット命令セットアーキテクチャです。スマートフォン、タブレット、サーバーなど、幅広いデバイスで使用されています。
3.  **Goアセンブリ**: Go言語は、特定の低レベル操作（特にランタイムやシステムコールラッパー）のために、独自の擬似アセンブリ言語を使用します。これは、一般的なアセンブリ言語とは異なる構文を持ちますが、最終的には各ターゲットアーキテクチャのネイティブアセンブリに変換されます。
    *   `TEXT`: 関数の開始を宣言します。
    *   `MOVW`, `MOVD`: レジスタやメモリ間でデータを移動する命令です。`W`は32ビット、`D`は64ビットを意味します。
    *   `SVC`: Supervisor Call（スーパーバイザコール）命令で、システムコールをトリガーするために使用されます。これにより、ユーザーモードからカーネルモードへ制御が移ります。
    *   `R0`, `R1`, `R2`, `R8`など: ARM64の汎用レジスタです。システムコールの引数や戻り値の受け渡しに使用されます。特に、システムコールの戻り値は通常`R0`（または`X0`）レジスタに格納されます。
    *   `SYS_close`, `SYS_write`, `SYS_read`: Linuxシステムコールの番号を表す定数です。`R8`レジスタにシステムコール番号を設定して`SVC`を呼び出すことで、どのシステムコールを実行するかをカーネルに伝えます。
4.  **条件コードとフラグ**: CPUは、演算結果に基づいて特定のフラグ（N: Negative, Z: Zero, C: Carry, V: Overflow）を設定します。これらのフラグは、その後の条件分岐命令（例: `BCC`, `BEQ`など）で使用され、プログラムのフローを制御します。
    *   **キャリーフラグ (C)**: 加算で桁上がりが発生した場合や、減算で桁借りが発生しなかった場合に設定されます。システムコールにおいては、エラーを示すために使用されることがあります（特にARM32）。
5.  **`CMN` (Compare Negative) 命令**: ARM64のアセンブリ命令の一つです。`CMN Rn, Operand2`は、`Rn + Operand2`の演算を行い、その結果に基づいて条件フラグ（N, Z, C, V）を更新しますが、演算結果自体はレジスタに保存しません。これは、`ADDS XZR, Rn, Operand2`（結果をゼロレジスタに加算し、フラグを設定する）のエイリアスです。
    *   この命令は、`Rn`と`Operand2`の合計がゼロ、正、負のいずれであるかを効率的にテストするために使用されます。特に、`CMN X0, #4095`は、`X0 + 4095`の演算結果の符号とゼロ状態をチェックします。
6.  **システムコールエラーコードの範囲**: Linuxシステムコールでは、エラーが発生した場合、戻り値として負の整数が返されます。これらの負の値は、対応する`errno`値（正の整数）の符号を反転させたものです。例えば、`ENOENT`（No such file or directory）の`errno`値が2であれば、システムコールは-2を返すことがあります。これらのエラーコードは通常、-1から-4095の範囲にあります。

## 技術的詳細

このコミットの技術的詳細は、ARM64 Linuxにおけるシステムコールエラーハンドリングの特殊性と、それをGoランタイムがどのように吸収するかという点に集約されます。

**ARM64 Linuxシステムコールのエラー挙動**:
ARM64 Linuxでは、システムコールが成功した場合、`X0`レジスタ（64ビットレジスタ）に非負の値（通常は0または成功を示す値）が返されます。一方、システムコールが失敗した場合、`X0`レジスタには負の値が返されます。この負の値は、対応する`errno`値（例えば`EACCES`や`ENOENT`など）の符号を反転させたものです。重要なのは、ARM32のように条件コード（特にキャリーフラグ）が自動的に設定されないため、`X0`レジスタの値を直接検査してエラーを判定する必要があるという点です。

**Goランタイムの既存の挙動（修正前）**:
GoランタイムのARM64アセンブリコード（`sys_linux_arm64.s`）では、システムコール呼び出し後に`SVC`命令が実行され、その直後に`BCC done`という条件分岐命令が使用されていました。`BCC`は「Branch if Carry Clear」（キャリーフラグがクリアされていれば分岐）を意味します。これは、ARM32のシステムコールがエラー時にキャリーフラグを設定するという前提に基づいたものでした。しかし、ARM64ではこの前提が成り立たないため、システムコールがエラーを返してもキャリーフラグはクリアされたままであり、結果として`BCC`命令が常に分岐してしまい、エラー処理ロジックがスキップされる可能性がありました。これにより、システムコールが実際には失敗しているにもかかわらず、Goランタイムがそれを成功と誤認するバグが発生していました。

**修正内容**:
このコミットでは、`SVC`命令の直後に`CMN $4095, R0`という命令が追加されました。
*   `R0`レジスタにはシステムコールの戻り値が格納されています（ARM64では`X0`レジスタの32ビット部分が`W0`、64ビット部分が`X0`として扱われますが、ここでは`R0`は`X0`を指します）。
*   `CMN $4095, R0`は、`R0 + 4095`の演算を行い、その結果に基づいてCPUの条件フラグ（特にN, Z, C, V）を更新します。
*   Linuxのシステムコールエラーコードは、通常-1から-4095の範囲の負の値です。
    *   もし`R0`が成功を示す非負の値（例: 0）であれば、`R0 + 4095`は正の値（例: 4095）となり、キャリーフラグはクリアされたままになります。この場合、続く`BCC done`命令は分岐し、エラー処理をスキップして`done`ラベルへ進みます。これは正しい挙動です。
    *   もし`R0`がエラーを示す負の値（例: -1から-4095の範囲）であれば、`R0 + 4095`は0以上（例: -1 + 4095 = 4094）の非負の値になります。この場合もキャリーフラグはクリアされたままになります。しかし、`CMN`命令は`R0`が負の値である場合に、`R0 + 4095`が正の値になることで、`BCC`命令が分岐しないようにします。
    *   より正確には、`CMN X0, #4095`は`X0 + 4095`を計算し、その結果の符号をチェックします。もし`X0`がエラーコード（-1から-4095）であれば、`X0 + 4095`は0から4094の範囲の非負の値になります。この場合、N（Negative）フラグはクリアされ、Z（Zero）フラグもクリアされます（ただし、`X0`が-4095の場合はZフラグがセットされます）。重要なのは、`BCC`命令がキャリーフラグに依存していることです。`CMN`命令は加算を行うため、通常、加算で桁上がりが発生しない限りキャリーフラグはクリアされます。
    *   この文脈での`BCC`は、`R0`がエラーコードの範囲内にある場合に、`R0 + 4095`が負にならないことを利用して、`BCC`が分岐しないように仕向けています。これにより、`MOVW $-1, R0`というエラーを示す値のセットと、`done`へのジャンプが実行されず、適切なエラー処理パスに進むことができます。

この修正により、GoランタイムはARM64 Linux上でシステムコールが返すエラーを正しく認識し、処理できるようになりました。

## コアとなるコードの変更箇所

変更は `src/runtime/sys_linux_arm64.s` ファイルに集中しています。

```diff
--- a/src/runtime/sys_linux_arm64.s
+++ b/src/runtime/sys_linux_arm64.s
@@ -72,6 +72,7 @@ TEXT runtime·closefd(SB),NOSPLIT,$-8-12
  	MOVW	fd+0(FP), R0
  	MOVD	$SYS_close, R8
  	SVC
+	CMN	$4095, R0
  	BCC	done
  	MOVW	$-1, R0
  done:
@@ -84,6 +85,7 @@ TEXT runtime·write(SB),NOSPLIT,$-8-28
  	MOVW	n+16(FP), R2
  	MOVD	$SYS_write, R8
  	SVC
+	CMN	$4095, R0
  	BCC	done
  	MOVW	$-1, R0
  done:
@@ -96,6 +98,7 @@ TEXT runtime·read(SB),NOSPLIT,$-8-28
  	MOVW	n+16(FP), R2
  	MOVD	$SYS_read, R8
  	SVC
+	CMN	$4095, R0
  	BCC	done
  	MOVW	$-1, R0
  done:
```

具体的には、`runtime·closefd`、`runtime·write`、`runtime·read`という3つのシステムコールラッパー関数において、`SVC`命令の直後に`CMN $4095, R0`という行が追加されています。

## コアとなるコードの解説

各システムコールラッパー（`runtime·closefd`, `runtime·write`, `runtime·read`）の構造は類似しています。ここでは`runtime·closefd`を例に解説します。

```goasm
TEXT runtime·closefd(SB),NOSPLIT,$-8-12
 	MOVW	fd+0(FP), R0  // fd (ファイルディスクリプタ) を R0 レジスタにロード
 	MOVD	$SYS_close, R8 // システムコール番号 SYS_close を R8 レジスタにロード
 	SVC                   // システムコールを実行。戻り値は R0 に格納される
+	CMN	$4095, R0     // R0 + 4095 を計算し、条件フラグを更新
 	BCC	done          // キャリーフラグがクリアされていれば done へ分岐
 	MOVW	$-1, R0       // エラーの場合、R0 に -1 を設定
 done:
 	RET                   // 関数から戻る
```

1.  **`MOVW fd+0(FP), R0`**: `closefd`関数の引数であるファイルディスクリプタ`fd`を`R0`レジスタにロードします。システムコールの最初の引数は通常`R0`に渡されます。
2.  **`MOVD $SYS_close, R8`**: 実行したいシステムコールの番号（ここでは`SYS_close`）を`R8`レジスタにロードします。Linux ARM64では、システムコール番号は`R8`に設定されます。
3.  **`SVC`**: システムコールを実行します。カーネルが処理を行い、結果を`R0`レジスタに返します。成功した場合は非負の値、失敗した場合は負のエラーコードが`R0`に格納されます。
4.  **`CMN $4095, R0`**: **このコミットで追加された行です。**
    *   `R0`レジスタの値に`4095`を加算し、その結果に基づいてCPUの条件フラグ（N, Z, C, V）を更新します。
    *   ARM64 Linuxのシステムコールエラーコードは、通常-1から-4095の範囲の負の値です。
    *   もし`R0`が成功を示す非負の値（例: 0）であれば、`R0 + 4095`は正の値（例: 4095）となり、キャリーフラグはクリアされたままになります。
    *   もし`R0`がエラーを示す負の値（例: -1から-4095）であれば、`R0 + 4095`は0から4094の範囲の非負の値になります。この場合もキャリーフラグはクリアされたままになります。
    *   この`CMN`命令の目的は、`R0`がエラーコードの範囲内にある場合に、続く`BCC`命令が分岐しないように、条件フラグを適切に設定することです。
5.  **`BCC done`**: 「Branch if Carry Clear」（キャリーフラグがクリアされていれば`done`ラベルへ分岐）命令です。
    *   修正前は、ARM32の挙動を前提としていたため、エラー時にもキャリーフラグがクリアされたままで、常に`done`へ分岐してしまい、エラー処理がスキップされる可能性がありました。
    *   修正後は、`CMN $4095, R0`によって、`R0`がエラーコードの範囲内にある場合でも、`BCC`が分岐しないように（つまり、キャリーフラグがクリアされないように、あるいは他のフラグとの組み合わせで分岐条件が満たされないように）調整されます。これにより、エラー時には次の`MOVW $-1, R0`が実行されるパスに進みます。
6.  **`MOVW $-1, R0`**: システムコールがエラーを返した場合に、Goランタイムが認識するエラー値である`-1`を`R0`に設定します。これは、Goのシステムコールラッパーがエラーを示すために使用する慣例的な戻り値です。
7.  **`done:`**: 処理が完了した後のラベルです。
8.  **`RET`**: 関数から呼び出し元に戻ります。

この変更により、ARM64 Linux環境でのシステムコールエラーがGoランタイムによって正しく検出され、処理されるようになりました。

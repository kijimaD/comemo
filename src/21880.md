# [インデックス 21880] ファイルの概要

このコミットは、Goランタイムのシンボルテーブル（`functab`）と関数検索テーブル（`findfunctab`）の生成ロジックに関する修正です。特に、Goリンカが生成する「コンテナシンボル」がこれらのテーブルに含まれないようにすることで、関数ルックアップの正確性を向上させ、`findfunctab`におけるオフバイワンエラーを修正することを目的としています。この変更は、`net`、`runtime/cgo`、`runtime/race`のような、複数のパッケージが単一のユニットとしてリンクされるライブラリの動作に影響を与えます。

## コミット

    runtime: don't put container symbols in functab
    
    Container symbols shouldn't be considered as functions in the functab.
    Having them present probably messes up function lookup, as you might get
    the descriptor of the container instead of the descriptor of the actual

    entries caused off-by-one errors in how functab entries were counted.

    behavior for libraries linked as a unit, like:

## 元コミット内容

このコミットは、Goランタイムにおいて、コンテナシンボルを`functab`（関数テーブル）に含めないようにする変更を導入します。コンテナシンボルが`functab`に存在すると、関数ルックアップが誤動作し、スタック上の実際の関数のディスクリプタではなく、コンテナのディスクリプタが取得される可能性がありました。また、`findfunctab`（関数検索テーブル）の計算において、これらのエントリがオフバイワンエラーを引き起こしていました。この修正は、通常コードには影響せず、`net`、`runtime/cgo`、`runtime/race`のように単一ユニットとしてリンクされるライブラリの動作を改善します。

## 変更の背景

Goの実行ファイルには、デバッグやプロファイリング、スタックトレースの生成などのために、実行時のコードアドレス（PC値）から対応する関数情報を逆引きするためのメタデータが含まれています。このメタデータは主に`pclntab`（PC-line table）と`functab`、そして`findfunctab`によって構成されます。

問題は、「コンテナシンボル」と呼ばれる特殊なシンボルがこれらのテーブルに誤って含まれていたことにありました。コンテナシンボルは、複数のサブシンボル（実際の関数など）を論理的にグループ化するためのものであり、それ自体は実行可能なコードを持たない「入れ物」のような存在です。

コンテナシンボルが`functab`に含まれると、以下のような問題が発生していました。

1.  **関数ルックアップの誤動作**: 特定のPC値に対応する関数を検索する際、実際の関数ではなく、その関数を含むコンテナシンボルの情報が返される可能性がありました。これは、スタックトレースの正確性やデバッグ情報の信頼性に直接影響します。
2.  **`findfunctab`のオフバイワンエラー**: `findfunctab`は、PC値から`functab`内の関数エントリを高速に検索するためのインデックス構造です。コンテナシンボルが`functab`の関数エントリ数に誤ってカウントされることで、このインデックスの計算にずれが生じ、結果として誤った関数情報が参照される可能性がありました。

これらの問題は、特に`net`パッケージや`runtime/cgo`、`runtime/race`といった、複数のGoソースファイルがコンパイルされ、単一のライブラリとしてリンクされるようなケースで顕在化していました。通常のGoプログラムでは、各関数が独立したシンボルとして扱われるため、この問題の影響は限定的でしたが、上記のような特殊なリンキングが行われる場合には、正確なランタイム情報の取得が困難になっていました。

このコミットは、これらの問題を解決し、Goランタイムがより正確な関数情報を報告できるようにするために導入されました。

## 前提知識の解説

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理する低レベルのシステムです。これには、ガベージコレクション、スケジューラ（ゴルーチンの管理）、メモリ割り当て、スタック管理、そしてデバッグやプロファイリングのためのメタデータ管理などが含まれます。Goプログラムは、コンパイル時にランタイムと静的にリンクされ、実行時にランタイムの機能を利用します。

### シンボルテーブル (`functab` と `pclntab`)

Goの実行ファイルには、プログラムの構造に関するメタデータが埋め込まれています。

*   **`functab` (Function Table)**: 実行ファイル内の各Go関数のエントリポイント（開始アドレス）と、その関数に関する追加情報（関数名、スタックフレームサイズ、PC-lineテーブルへのオフセットなど）をマッピングするテーブルです。これは、PC値から関数情報を逆引きする際の基本的なデータソースとなります。
*   **`pclntab` (PC-Line Table)**: プログラムカウンタ（PC）値とソースコードの行番号情報をマッピングするテーブルです。これにより、実行時のPC値から、どのソースファイルのどの行でコードが実行されているかを特定できます。デバッガやプロファイラがスタックトレースを生成する際に不可欠な情報です。

### `findfunctab` (Function Lookup Table)

`findfunctab`は、`functab`を効率的に検索するための補助的なルックアップテーブルです。`functab`は関数の開始アドレス順にソートされていますが、非常に多くの関数が存在する場合、線形検索ではパフォーマンスが低下します。`findfunctab`は、PC空間を一定のサイズの「バケット」に分割し、各バケットが`functab`内の対応する関数エントリへのインデックスを持つようにすることで、高速な検索を可能にします。これにより、任意のPC値から、そのPC値を含む関数をO(1)に近い時間で特定できます。

### コンテナシンボル (Container Symbols)

Goのリンカ（`cmd/ld`）は、コンパイルされたGoコードをリンクする際に、様々な種類のシンボルを生成します。通常の関数やグローバル変数に対応するシンボルとは別に、「コンテナシンボル」と呼ばれる特殊なシンボルが存在します。

コンテナシンボルは、複数の関連するシンボル（例えば、あるパッケージ内の複数の関数や、特定のデータ構造に関連する関数群）を論理的にグループ化するためにリンカが内部的に使用するものです。これらは、実際の実行可能なコードブロックを直接指すものではなく、あくまでリンカが内部的な構造を管理するための「入れ物」として機能します。例えば、Goのメソッドは、レシーバの型とメソッド名で構成されますが、リンカはこれらのメソッドを特定の型に関連付けるためにコンテナシンボルを使用することがあります。

このコミットの文脈では、コンテナシンボルが`functab`に誤って「関数」として登録されてしまうことが問題でした。

### `src/cmd/ld/pcln.c`

このファイルは、Goリンカ（`cmd/ld`）の一部であり、`pclntab`や`findfunctab`といったランタイムメタデータを生成するC言語のコードが含まれています。リンカは、コンパイルされたオブジェクトファイルからシンボル情報を収集し、実行ファイルに埋め込むためのこれらのテーブルを構築します。

### `src/runtime/symtab.go`

このファイルは、Goランタイムの一部であり、`functab`や`findfunctab`などのデータ構造のGo言語での定義、およびそれらのテーブルを使用してPC値から関数情報を検索するロジック（`findfunc`関数など）が実装されています。

## 技術的詳細

このコミットの核心は、Goリンカが`functab`と`findfunctab`を構築する際に、コンテナシンボルを「関数」として扱わないようにフィルタリングすることです。

### `pcln.c` における変更

1.  **`container` 関数の追加**:
    `static int container(LSym *s)` という新しいヘルパー関数が追加されました。この関数は、与えられたリンカシンボル `s` がコンテナシンボルであるかどうかを判定します。具体的には、`s != nil && s->sub != nil` という条件で判定されます。`s->sub` は、そのシンボルがサブシンボル（子シンボル）を持っている場合に非`nil`となるフィールドです。つまり、この関数は「サブシンボルを持つシンボルはコンテナである」と定義しています。

    ```c
    static int
    container(LSym *s)
    {
        // We want to generate func table entries only for the "lowest level" symbols,
        // not containers of subsymbols.
        if(s != nil && s->sub != nil)
            return 1;
        return 0;
    }
    ```

2.  **`pclntab` 生成ロジックの修正**:
    `pclntab`を生成する`pclntab()`関数内で、`functab`に含める関数シンボルの数をカウントするループと、実際に`functab`エントリを書き込むループの両方で、新しく追加された`container()`関数が使用されるようになりました。

    *   **関数カウントの修正**:
        以前は、`ctxt->textp`（テキストセグメントのシンボルリストの先頭）から順にすべてのシンボルを数えて`nfunc`を計算していました。修正後は、`!container(ctxt->cursym)` の条件が追加され、コンテナシンボルは`nfunc`のカウントから除外されるようになりました。

        ```c
        // 修正前
        // for(ctxt->cursym = ctxt->textp; ctxt->cursym != nil; ctxt->cursym = ctxt->cursym->next)
        //    nfunc++;

        // 修正後
        for(ctxt->cursym = ctxt->textp; ctxt->cursym != nil; ctxt->cursym = ctxt->cursym->next) {
            if(!container(ctxt->cursym))
                nfunc++;
        }
        ```

    *   **`functab` エントリ書き込みの修正**:
        同様に、`functab`に各関数のエントリ（開始PCと関数情報へのオフセット）を書き込むループでも、コンテナシンボルはスキップされるようになりました。これにより、`functab`には実際の実行可能な関数のみが登録されるようになります。

        ```c
        // 修正前
        // for(ctxt->cursym = ctxt->textp; ctxt->cursym != nil; ctxt->cursym = ctxt->cursym->next, nfunc++) {

        // 修正後
        for(ctxt->cursym = ctxt->textp; ctxt->cursym != nil; ctxt->cursym = ctxt->cursym->next) {
            last = ctxt->cursym; // 最後の有効なシンボルを追跡
            if(container(ctxt->cursym))
                continue; // コンテナシンボルはスキップ
            // ... 実際のfunctabエントリの書き込みロジック ...
            nfunc++; // 有効な関数のみカウント
        }
        // 最終エントリのPC値は、最後に処理された有効なシンボルのサイズを加算したものになる
        setaddrplus(ctxt, ftab, 8+PtrSize+nfunc*2*PtrSize, last, last->size);
        ```
        特に、`functab`の最後のPCエントリの計算方法も変更されました。以前は`ctxt->cursym->next == nil`の場合に最後のシンボルを基準にしていましたが、修正後は`last`変数で追跡された「最後に処理された非コンテナシンボル」を基準にするようになりました。これにより、`functab`の終端が正しく設定されます。

3.  **`findfunctab` 生成ロジックの修正**:
    `findfunctab`を生成する`findfunctab()`関数でも、シンボルを処理する際に`container()`関数が使用されるようになりました。

    *   **インデックス計算の修正**:
        `findfunctab`は、PC空間をサブバケットに分割し、各サブバケットに対応する`functab`のインデックスを格納します。このインデックスを計算する際に、コンテナシンボルはスキップされ、実際の関数シンボルのみが考慮されるようになりました。これにより、`findfunctab`が参照する`functab`のインデックスが正確になり、オフバイワンエラーが解消されます。

        ```c
        // 修正前は、すべてのシンボルを考慮していた
        // for(s = ctxt->textp; s != nil; s = s->next) { ... }

        // 修正後
        for(s = ctxt->textp; s != nil; s = s->next) {
            if(container(s)) // コンテナシンボルはスキップ
                continue;
            // ... サブバケットインデックスの計算ロジック ...
            idx++; // 有効な関数のみカウント
        }
        ```
        また、`findfunctab`のバケット内のインデックス計算ロジックも変更され、より堅牢になりました。特に、`e = s->next; while(container(e)) e = e->next;` のように、次の有効な（非コンテナ）シンボルを見つけるロジックが導入され、PC範囲の計算がより正確になりました。

### `symtab.go` における変更

`src/runtime/symtab.go`では、主にコードの整形と、`findfuncbucket`構造体のフィールド名変更が行われています。これは、`pcln.c`でのロジック変更に合わせて、Goランタイム側でデータ構造の整合性を保つためのものです。

*   `minfunc`と`pcbucketsize`定数のコメントと値の間のスペースが調整されました。
*   `findfuncbucket`構造体の`idx`フィールドの宣言が、`subbuckets`フィールドと揃うように整形されました。これは機能的な変更ではなく、コードスタイルに関する変更です。

これらの変更により、Goリンカは`functab`と`findfunctab`を生成する際に、実行可能なコードを持たないコンテナシンボルを適切に無視するようになり、ランタイムが提供する関数情報の正確性が向上しました。

## コアとなるコードの解説

### `src/cmd/ld/pcln.c`

1.  **`container` 関数の導入**:
    この関数は、リンカシンボル `LSym` がコンテナシンボルであるかを判定します。`s->sub != nil` は、そのシンボルが子シンボル（サブシンボル）を持っていることを意味します。Goリンカの内部では、複数の関数やデータが論理的にグループ化される際に、親となる「コンテナ」シンボルが作成され、その下に実際の関数シンボルなどが子としてぶら下がります。この関数は、そのような親シンボルを識別するために使用されます。`functab`には、実行可能なコードを持つ「最低レベル」のシンボル（つまり実際の関数）のみを含めるべきであるという設計思想に基づいています。

2.  **`pclntab` 生成におけるフィルタリング**:
    `pclntab`関数は、`functab`を構築する主要な部分です。
    *   **`nfunc` の計算**: `functab`に登録される関数の総数 `nfunc` を計算する際、`for`ループ内で `if(!container(ctxt->cursym))` という条件が追加されました。これにより、コンテナシンボルは関数としてカウントされなくなります。
    *   **`functab` エントリの書き込み**: 実際に`functab`に各関数のエントリを書き込むループでも、同様に `if(container(ctxt->cursym)) continue;` が追加され、コンテナシンボルはスキップされます。
    *   **`last` シンボルの追跡と最終エントリの修正**: `last` 変数が導入され、ループ内で最後に処理された「非コンテナシンボル」を追跡します。`functab`の最後のPCエントリは、この `last` シンボルのアドレスとサイズに基づいて設定されるようになりました。これにより、`functab`の終端が正確に定義され、オフバイワンエラーが解消されます。

3.  **`findfunctab` 生成におけるフィルタリングとインデックス計算の改善**:
    `findfunctab`関数は、PC値から関数を高速に検索するためのインデックスを構築します。
    *   **`indexes` 配列の導入**: `indexes`という新しい配列が導入され、各サブバケットに対応する`functab`のインデックスを事前に計算・格納するようになりました。
    *   **コンテナシンボルのスキップ**: `indexes`配列を埋めるループ内で、`if(container(s)) continue;` が追加され、コンテナシンボルはインデックス計算から除外されます。
    *   **PC範囲の正確な計算**: `p = s->value; e = s->next; while(container(e)) e = e->next; if(e != nil) q = e->value; else q = max;` というロジックが追加されました。これは、現在のシンボル `s` の開始PC `p` から、次の「非コンテナシンボル」の開始PC `q` までの範囲を正確に定義するためのものです。これにより、各関数がカバーするPC範囲が正しく計算され、`findfunctab`のインデックスがより正確になります。
    *   **`NOIDX` の導入**: `NOIDX` (0x7fffffff) は、インデックスがまだ設定されていないことを示す値として導入されました。これにより、`findfunctab`のバケットに「穴」がないかどうかのチェックがより明確になります。

### `src/runtime/symtab.go`

このファイルへの変更は、主にコードの整形と、`findfuncbucket`構造体の`idx`フィールドの宣言位置の調整です。これは、`pcln.c`でのリンカ側の変更と整合性を保つためのものであり、Goランタイムがリンカによって生成された新しい形式の`findfunctab`を正しく解釈できるようにするためのものです。機能的なロジックの変更は含まれていません。

これらの変更により、Goランタイムはより正確な関数情報を取得できるようになり、特に単一ユニットとしてリンクされるライブラリ（例: `net`, `runtime/cgo`, `runtime/race`）におけるデバッグやプロファイリングの信頼性が向上しました。

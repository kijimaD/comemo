# [インデックス 24596] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおけるスケジューラが、ロードとストアの順序を正しく強制するように修正するものです。具体的には、あるストア操作の結果を使用するロード操作が、そのストア操作の後に続く別のストア操作よりも前にスケジューリングされることを保証するための依存関係が、値グラフに追加されます。これにより、メモリ操作の順序に関するコンパイラの正しさが向上します。

## 元コミット内容

このコミットの目的は、GoコンパイラのSSAスケジューラにおいて、ロードとストアの順序付けを強制することです。具体的には、「ストアを使用するすべてのロードが、次のストアの前にスケジューリングされる」ことを保証する必要があります。この制約を強制するために、値グラフに追加の依存関係エッジが追加されます。

## 変更の背景

コンパイラの最適化フェーズ、特に命令スケジューリングにおいて、メモリ操作（ロードとストア）の順序は非常に重要です。プログラマが記述したコードのセマンティクスを維持するためには、メモリへの読み書きが特定の順序で行われることが保証されなければなりません。

特に、SSA形式では、値は一度だけ定義されるため、メモリの状態も「メモリ値」として扱われ、SSA形式で表現されます。メモリへのストア操作は新しいメモリ値を生成し、ロード操作はそのメモリ値を使用します。もし、あるストア操作の結果（つまり、そのストアによってメモリに書き込まれた値）を読み出すロード操作が、そのストア操作の後に続く別のストア操作よりも後にスケジューリングされてしまうと、ロード操作が意図しない古い値や、全く関係のない別のストアによって上書きされた値を読み出してしまう可能性があります。これはプログラムの誤動作に直結します。

このコミットは、このようなメモリ操作の順序に関する潜在的なバグを防ぎ、コンパイラが生成するコードの正しさを保証するために導入されました。特に、`loadstore_ssa.go`という新しいテストケースが追加されており、これはまさにロードとストアの順序が正しく維持されているかを検証するためのものです。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化で広く用いられる中間表現（IR）の一種です。この形式では、すべての変数が一度だけ代入（定義）されます。もし同じ変数に複数回代入が行われる場合、SSA形式では新しい「バージョン」の変数が導入されます（例: `x1 = ...`, `x2 = ...`）。これにより、データフロー解析が容易になり、多くの最適化が効率的に行えるようになります。

メモリ操作もSSA形式で扱われます。メモリ全体の状態を抽象的な「メモリ値」として捉え、ストア操作は新しいメモリ値を生成し、ロード操作はそのメモリ値を使用します。

### 2. コンパイラのスケジューラ

コンパイラのスケジューラは、中間表現の命令（この場合はSSA値）を、ターゲットアーキテクチャの制約（レジスタの数、パイプラインの遅延など）を考慮しつつ、実行効率が最大になるように並べ替える役割を担います。この並べ替えは、プログラムのセマンティクスを破壊しない範囲で行われる必要があります。

### 3. 依存関係グラフ (Value Graph)

SSA形式のコンパイラでは、命令間の依存関係を表現するために「値グラフ」が構築されます。このグラフのノードはSSA値（命令の結果）を表し、エッジはデータ依存関係（ある命令の結果が別の命令の入力として使われる）や制御依存関係（ある命令の実行が別の命令の実行に影響する）を示します。スケジューラはこのグラフを基に、命令の実行順序を決定します。

### 4. メモリバリアとメモリモデル

マルチコアプロセッサ環境では、プロセッサやコンパイラが命令の実行順序を最適化のために変更することがあります。これにより、プログラマが意図したメモリ操作の順序と、実際にハードウェアで実行される順序が異なる場合があります。これを防ぐために、メモリバリア（またはメモリフェンス）と呼ばれる特殊な命令が使用されます。Go言語のような高水準言語では、コンパイラが適切なメモリバリアを挿入したり、メモリ操作の順序を保証したりすることで、プログラマはこれらの低レベルな詳細を意識せずに済みます。このコミットは、コンパイラ内部でその「順序保証」を実現するためのメカニズムを強化するものです。

### 5. ロードとストアの順序付けの重要性

例えば、以下のようなコードを考えます。

```go
*ptr = 10 // ストア A
x = *ptr  // ロード B
*ptr = 20 // ストア C
```

ここで、ロードBはストアAによって書き込まれた値（10）を読み出すことを期待しています。もしスケジューラがストアCをストアAとロードBの間に移動させてしまうと、ロードBはストアCによって書き込まれた値（20）を読み出してしまう可能性があり、プログラムの動作が変わってしまいます。このような「ストアを使用するロードは、次のストアの前に来るべき」という制約を、コンパイラは厳密に守る必要があります。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/ssa/schedule.go` ファイル内のスケジューリングロジックを修正し、`loadstore_ssa.go` という新しいテストケースを追加しています。

### `schedule.go` の変更点

1.  **`priq` 配列のサイズ変更**:
    *   `var priq [4][]*Value` から `var priq [5][]*Value` へと変更されています。これは、スケジューリングの優先度キューのカテゴリが1つ増えたことを示唆しています。優先度キューは、SSA値のタイプ（Phi、メモリ、フラグ、その他、制御値）に基づいて、どの命令をいつスケジューリングするかを決定するために使用されます。

2.  **`nextMem` と `additionalArgs` の導入**:
    *   `nextMem := make([]*Value, f.NumValues())`: 各メモリ値に対して、そのメモリ値の後に続く次のライブなメモリ値をマッピングするための配列が導入されました。これは、メモリ操作のチェーンを追跡するために使用されます。
    *   `additionalArgs := make([][]*Value, f.NumValues())`: 各SSA値に対して、追加の「見せかけの引数」を格納するための配列が導入されました。これは、ロード/ストアの順序付けを強制するための追加の依存関係エッジとして機能します。

3.  **メモリチェーンの特定**:
    *   各ブロック内で、`OpPhi` ではないメモリ値（ストア操作など）を走査し、その引数（前のメモリ値）から現在のメモリ値への `nextMem` マッピングを構築します。これにより、メモリ操作の順序を追跡するチェーンが確立されます。

4.  **ロード/ストア順序付けのための依存関係追加**:
    *   SSA値の引数を走査するループ内で、以下のロジックが追加されました。
        *   現在の値 `v` がメモリ値ではない（つまりロード操作である可能性が高い）が、その引数 `w` がメモリ値である場合（つまり `w` はロードの対象となるメモリ状態）、これはロード操作であると判断されます。
        *   `s := nextMem[w.ID]` を使用して、ロード対象のメモリ値 `w` の後に続く次のストア操作 `s` を特定します。
        *   もし `s` が存在し、かつ同じブロック内にある場合、ロード `v` がストア `s` の前にスケジューリングされるように、`v` を `s` の `additionalArgs` に追加します。これにより、`s` は `v` に依存するようになり、`v` がスケジューリングされるまで `s` はスケジューリングされなくなります。
        *   `uses[v.ID]++` をインクリメントすることで、ロード `v` が `s` の「見せかけの引数」として使用されることを示し、`v` がスケジューリングされるまで `s` のスケジューリングをブロックします。

5.  **スコア付けの変更**:
    *   メモリ値のスコアが `2` から `1` に変更されました。これは「ストアをできるだけ早くスケジューリングする」という方針への変更を示しています。以前は「ストアをできるだけ遅くスケジューリングする」ことでロードがストアの後に来ないようにしていましたが、新しい依存関係の追加により、ストアを早くスケジューリングしても正しさが保たれるようになり、レジスタプレッシャの軽減に寄与する可能性があります。
    *   フラグ値のスコアが `2` から `3` に変更されました。
    *   デフォルト値のスコアが `1` から `2` に変更されました。
    *   制御値のスコアが `3` から `4` に変更されました。
    これらのスコア変更は、優先度キューのカテゴリの再調整と、新しい依存関係ロジックを考慮した上での、全体的なスケジューリング戦略の微調整を反映しています。

6.  **`additionalArgs` の処理**:
    *   SSA値 `v` がスケジューリングされた後、その `additionalArgs` に含まれるすべての値 `w` の `uses` カウントをデクリメントします。`uses` が0になった場合、`w` はスケジューリング可能として優先度キューに追加されます。これにより、追加された依存関係が正しく解決され、スケジューリングが進行します。

### `loadstore_ssa.go` の追加

このファイルは、ロードとストアの順序付けが正しく行われているかをテストするための新しいテストケースです。
`testLoadStoreOrder_ssa` 関数内で、以下のシーケンスがテストされています。

```go
old := *z         // load (L1)
*z = uint32(prec) // store (S1)
if *z < old {     // load (L2)
    return 1
}
```

ここで重要なのは、`L2` のロードが `S1` のストアによって書き込まれた値を読み出すことを期待している点です。もしコンパイラが `S1` と `L2` の間に別のストアを挿入したり、`L2` が `S1` の前の古い値を読み出したりするような最適化を行ってしまうと、テストは失敗します。このテストは、このコミットで導入された依存関係の強制が正しく機能していることを検証します。

## コアとなるコードの解説

### `schedule.go` の変更点

このコミットの核心は、`schedule.go` における `nextMem` と `additionalArgs` の導入、そしてそれらを用いた依存関係の追加ロジックです。

1.  **`nextMem` の役割**:
    `nextMem[w.ID] = v` の行は、メモリ値 `w` の後に、同じブロック内で `v` というメモリ値が続くことを記録しています。これは、メモリ操作の「チェーン」を構築するのに役立ちます。例えば、`mem0 -> store1 -> mem1 -> store2 -> mem2` のようなシーケンスがあった場合、`nextMem[mem0.ID]` は `store1` を指し、`nextMem[mem1.ID]` は `store2` を指すようになります。

2.  **`additionalArgs` を用いた依存関係の追加**:
    最も重要な変更は、以下の部分です。

    ```go
    // Any load must come before the following store.
    if v.Type.IsMemory() || !w.Type.IsMemory() {
        continue // not a load
    }
    s := nextMem[w.ID]
    if s == nil || s.Block != b {
        continue
    }
    additionalArgs[s.ID] = append(additionalArgs[s.ID], v)
    uses[v.ID]++
    ```
    *   `v.Type.IsMemory() || !w.Type.IsMemory()`: この条件は、現在のSSA値 `v` がメモリ値ではない（つまりロード操作である可能性が高い）が、その引数 `w` がメモリ値である場合に `continue` しない、ということを意味します。これは、`v` が `w` というメモリ状態から値をロードしている状況を特定しています。
    *   `s := nextMem[w.ID]`: ロード操作 `v` が読み出すメモリ状態 `w` の直後に続くストア操作 `s` を `nextMem` マップから取得します。
    *   `additionalArgs[s.ID] = append(additionalArgs[s.ID], v)`: ここが肝です。ストア操作 `s` の「追加の引数」としてロード操作 `v` を追加しています。これにより、スケジューラは `s` をスケジューリングする前に、`v` がスケジューリングされる必要があると認識します。
    *   `uses[v.ID]++`: ロード操作 `v` の使用カウントをインクリメントします。これは、`v` が `s` の「見せかけの引数」として使用されていることを示し、`v` がスケジューリングされるまで `s` のスケジューリングをブロックする効果があります。

    このメカニズムにより、「ストア `s` の結果を使用するロード `v` は、`s` の後に続く次のストアよりも前にスケジューリングされなければならない」という制約が、値グラフの依存関係として明示的に追加されます。

3.  **スコア付けの変更**:
    メモリ値のスコアが `2` から `1` に変更されたのは、新しい依存関係がロード/ストアの順序を保証するため、ストアを遅延させる必要がなくなったためです。これにより、ストアをより早くスケジューリングできるようになり、レジスタの寿命を短くし、レジスタプレッシャを軽減する効果が期待できます。

### `loadstore_ssa.go` のテストケース

このテストケースは、`testLoadStoreOrder_ssa` 関数内で、ポインタ `z` を介したロードとストアのシーケンスを検証します。
`old := *z` (ロードL1)
`*z = uint32(prec)` (ストアS1)
`if *z < old` (ロードL2)

このテストの目的は、`L2` が `S1` によって書き込まれた新しい値（`prec`）を確実に読み取ることを保証することです。もしコンパイラが `S1` と `L2` の間に別のストアを挿入したり、`L2` が `L1` と同じ古い値（`1000`）を読み取ったりするような最適化を行ってしまうと、`if *z < old` の条件が期待通りに評価されず、テストが失敗します。このテストは、`schedule.go` の変更が意図した通りにロード/ストアの順序を強制していることを確認するためのものです。

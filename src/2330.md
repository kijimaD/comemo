## 変更の背景

このコミットは、Go言語の初期段階におけるコンパイラの堅牢性向上の一環として行われました。Go言語では、関数が任意の数の引数を受け入れることができる「可変長引数（variadic arguments）」の機能を提供しています。しかし、この機能が導入された初期には、`nil`のような特定の値を可変長引数として不適切に渡した場合に、コンパイラが適切なエラーを報告せず、予期せぬ動作やコンパイルエラーを引き起こす可能性がありました。

`bug 153`という簡潔なコミットメッセージは、Goプロジェクトのバグトラッカーで報告された特定の不具合に対応していることを示唆しています。このバグは、`nil`リテラルが可変長引数として渡された際に、コンパイラがその型を正しく推論できず、結果として不正なコードを許容してしまうか、あるいは誤ったエラーメッセージを出すという問題であったと推測されます。この修正は、コンパイラがより厳密に型チェックを行い、開発者に対して早期に誤用を警告することを目的としています。

## 前提知識の解説

### Goコンパイラの構造

Goコンパイラ（`gc`）は、ソースコードを解析し、抽象構文木（AST）を構築し、型チェック、最適化、コード生成を行う複数のフェーズで構成されています。
- **`src/cmd/gc`**: Goコンパイラの主要なソースコードが格納されているディレクトリです。
- **`walk.c`**: ASTを走査（walk）し、型チェックや一部の最適化、中間コード生成などを行うコンパイラフェーズの一部を実装しているファイルです。

### 抽象構文木 (AST) とノード

コンパイラはソースコードを解析して抽象構文木（AST）を生成します。ASTはプログラムの構造を木構造で表現したもので、各ノードはプログラムの要素（変数、関数呼び出し、リテラルなど）を表します。
- **`Node`**: ASTの各要素を表すデータ構造です。
- **`r->op == OLITERAL`**: `r`という`Node`がリテラル（定数）を表していることを示します。
- **`r->val.ctype == CTNIL`**: リテラルが`nil`定数であることを示します。`CTNIL`は`nil`のコンパイル時定数型です。

### 可変長引数 (Variadic Arguments)

Go言語では、関数の最後のパラメータに`...`を付けることで、その関数が任意の数の引数を受け取れるように定義できます。例えば、`func sum(nums ...int)`のように定義された関数は、`sum(1, 2, 3)`や`sum()`のように呼び出すことができます。可変長引数は関数内部ではスライスとして扱われます。

### `mkdotargs` 関数

`mkdotargs`は、Goコンパイラ内部の`walk.c`に存在する関数で、可変長引数（`...`引数）の処理に関連しています。具体的には、可変長引数として渡される複数の値を、内部的に単一の構造体やスライスにまとめるための処理（ASTの変換）を行う役割を担っています。この関数は、コンパイラが可変長引数呼び出しを正しく解釈し、型安全性を保証するために重要な部分です。

### `yyerror` 関数

`yyerror`は、Goコンパイラが構文解析や型チェックの段階でエラーを検出した際に、ユーザーに対してエラーメッセージを出力するために使用される関数です。

## 技術的詳細

このコミットの技術的詳細な変更点は、`mkdotargs`関数内での`nil`リテラルの型チェックの強化にあります。

Go言語の型システムでは、`nil`は特定の型を持たず、インターフェース、スライス、マップ、チャネル、ポインタ、関数などのゼロ値として使用されます。しかし、可変長引数に`nil`を直接渡す場合、その`nil`がどの型のスライスとして解釈されるべきかという曖昧さが生じることがあります。

変更前のコンパイラは、`r->op == OLITERAL && r->val.ctype == CTNIL`という条件で`nil`リテラルを検出しても、その後の型チェックが不十分であった可能性があります。特に、`r->type == T || r->type->etype == TNIL`という条件は、`nil`が型付けされていないか、あるいは`nil`型として扱われている場合に真となります。このような状況で`yyerror("inappropriate use of nil in ... argument")`を呼び出すことで、コンパイラは開発者に対して「可変長引数における`nil`の不適切な使用」を明示的に警告するようになります。

この修正により、例えば`func foo(args ...interface{})`のような関数に対して、`foo(nil)`と呼び出した場合に、コンパイラがより厳密なチェックを行うようになります。`nil`がどの型のスライスとして解釈されるべきか不明確な場合、コンパイラはエラーを報告し、開発者に意図を明確にするよう促します。これは、Go言語の型安全性を高め、実行時エラーを未然に防ぐ上で重要な改善です。

また、`test/bugs/bug153.go`が`test/fixedbugs/bug153.go`に移動されたことは、このコミットによって`bug 153`が修正され、そのテストケースがGoコンパイラの回帰テストスイートの一部として維持されることを意味します。`test/golden.out`からの関連するエラーメッセージの削除も、このバグが修正されたことの直接的な結果です。

## コアとなるコードの解説

追加されたコードブロックは、`mkdotargs`関数内でASTノード`r`を走査しているループの内部にあります。

```c
        if(r->op == OLITERAL && r->val.ctype == CTNIL) {
            if(r->type == T || r->type->etype == TNIL) {
                yyerror("inappropriate use of nil in ... argument");
                return N;
            }
        }
```

1.  **`if(r->op == OLITERAL && r->val.ctype == CTNIL)`**:
    この条件は、現在のASTノード`r`が`nil`リテラルであるかどうかをチェックしています。
    -   `r->op == OLITERAL`: ノードがリテラル（定数）を表していることを確認します。
    -   `r->val.ctype == CTNIL`: そのリテラルが`nil`定数であることを確認します。

2.  **`if(r->type == T || r->type->etype == TNIL)`**:
    この内部条件は、検出された`nil`リテラルの型が不明確であるか、または`nil`型として扱われているかをチェックしています。
    -   `r->type == T`: `T`はGoコンパイラ内で「型が不明」または「型チェックがまだ行われていない」状態を示す特別な型定数である可能性があります。
    -   `r->type->etype == TNIL`: ノードの基本型が`TNIL`、つまり`nil`型として認識されている場合です。これは、`nil`が具体的な型に解決されていない状態を示します。

3.  **`yyerror("inappropriate use of nil in ... argument");`**:
    上記の条件が両方とも真である場合、つまり、`nil`リテラルが可変長引数として渡され、かつその型が不明確であるか`nil`型として扱われている場合に、コンパイラはエラーメッセージ「inappropriate use of nil in ... argument」を出力します。これにより、開発者は可変長引数に`nil`を不適切に渡していることを認識し、コードを修正することができます。

4.  **`return N;`**:
    エラーが報告された後、関数は`N`（通常は`nil`ノードまたはエラーを示すノード）を返し、これ以上処理を進めないことで、不正なコードがコンパイルされるのを防ぎます。

この変更により、Goコンパイラは可変長引数における`nil`の型安全性を強化し、より堅牢なコンパイルプロセスを実現しています。

## 変更の背景

この変更の背景には、コードベースの健全性を維持し、不要なコードを排除するという一般的なソフトウェア開発のプラクティスがあります。特にコンパイラのような複雑なシステムでは、時間の経過とともに設計が進化し、古い実装やツールが新しいものに置き換えられることがあります。

このコミットメッセージが示唆するように、Goコンパイラの初期段階ではYacc（Yet Another Compiler Compiler）が構文解析器の生成に利用されていた可能性があります。しかし、Goコンパイラはその後、手書きのパーサーや異なるツールチェーンへと進化してきました。その結果、Yaccパーサーのために定義されていた特定の定数（バッファサイズ、ハッシュテーブルサイズなど）が、もはや現在のコンパイラの実装では使用されなくなったと考えられます。

未使用のコードを削除することは、以下のような利点があります。

*   **コードの可読性と理解の向上**: 不要なコードがなくなることで、開発者は現在のシステムに関連するコードのみに集中でき、コードベース全体の理解が容易になります。
*   **保守性の向上**: 誰も使用していないコードは、将来的にバグの原因となったり、誤って変更されたりするリスクがあります。削除することで、このようなリスクを軽減できます。
*   **コンパイル時間とバイナリサイズの削減**: ごくわずかではありますが、不要なコードや定数を削除することで、コンパイラのコンパイル時間や最終的なバイナリサイズに良い影響を与える可能性があります。
*   **技術的負債の削減**: 古い技術や実装に関連するコードは、技術的負債となりがちです。これらを積極的に削除することで、負債を減らし、プロジェクトをより現代的で効率的な状態に保つことができます。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Go言語の公式コンパイラであり、Goのソースコードを機械語の実行可能ファイルに変換する役割を担っています。Goのツールチェーンの核心部分であり、非常に複雑なソフトウェアです。コンパイラは通常、以下の主要なフェーズで動作します。

1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（単語や記号の最小単位）のストリームに分解します。
2.  **構文解析 (Syntactic Analysis)**: トークンのストリームを解析し、プログラムの構造を抽象構文木 (AST: Abstract Syntax Tree) として構築します。
3.  **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、名前解決、エラー検出など、プログラムの意味的な正当性を検証します。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTから、ターゲットマシンに依存しない中間表現 (IR: Intermediate Representation) を生成します。
5.  **最適化 (Optimization)**: 中間コードを分析し、より効率的なコードに変換します。
6.  **コード生成 (Code Generation)**: 最適化された中間コードから、ターゲットマシン（CPUアーキテクチャ）に特化した機械語コードを生成します。

### Yacc (Yet Another Compiler Compiler)

Yaccは、BNF (Backus-Naur Form) などの形式文法記述から、C言語で書かれた構文解析器（パーサー）を自動生成するツールです。コンパイラやインタプリタの構築において、構文解析フェーズを自動化するために広く利用されてきました。Yaccによって生成されるパーサーは、LALR(1)パーサーと呼ばれる種類のボトムアップパーサーです。

Goコンパイラの初期バージョンでは、Yaccのようなツールが構文解析器の生成に利用されていた可能性がありますが、Goコンパイラ自体がGo言語で書かれるようになり、パーサーも手書きで実装されるか、Go言語で書かれたパーサー生成ツールが使われるようになりました。これにより、Yaccに特有の定数や設定が不要になったと考えられます。

### 定数 (`const`)

プログラミングにおいて、定数とはプログラムの実行中に値が変更されない識別子です。コンパイル時に値が決定され、プログラム全体でその値が固定されます。コンパイラの内部では、バッファサイズ、ハッシュテーブルの初期サイズ、特定の上限値など、様々な設定値が定数として定義されることがあります。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/gc/go.go` ファイルから特定の定数定義を削除しています。このファイルは、Goコンパイラの内部パッケージ `cmd/compile/internal/gc` に属しており、Goコンパイラのコアロジックの一部を構成しています。

削除された定数は以下の通りです。

*   `NHUNK`: おそらくメモリチャンクのサイズに関連する定数。
*   `BUFSIZ`: バッファサイズに関連する定数。
*   `NSYMB`: シンボルテーブルのエントリ数に関連する定数。
*   `NHASH`: ハッシュテーブルのサイズに関連する定数。
*   `MAXALIGN`: 最大アラインメント値に関連する定数。

これらの定数は、コメントで「The parser's maximum stack size. We have to use a #define macro here since yacc or bison will check for its definition and use a potentially smaller value if it is undefined.」と説明されていました。このコメントは、これらの定数がYacc（またはBison）によって生成されたパーサーの動作を制御するために使用されていたことを明確に示しています。Yacc/Bisonは、パーサースタックのサイズや内部データ構造のサイズをコンパイル時に決定するために、特定のマクロ定義や定数を参照することがあります。

これらの定数が削除されたということは、Goコンパイラの構文解析器がYacc/Bisonに依存しない実装に完全に移行したか、あるいはYacc/Bisonを使用していたとしても、これらの特定の定数がもはや現在のパーサーの動作に影響を与えないようにリファクタリングされたことを意味します。Goコンパイラは、Go言語自体で書かれたパーサーを使用する方向に進化しており、これはその進化の一環であると考えられます。

## コアとなるコードの解説

削除されたコードは、Goコンパイラの内部で使用されていた定数定義です。これらの定数は、かつてYaccまたはBisonによって生成されたパーサーの動作に影響を与えるために存在していました。具体的には、パーサーの内部スタックサイズ、バッファサイズ、シンボルテーブルやハッシュテーブルの容量、最大アラインメントといった、コンパイラのメモリ管理やデータ構造のサイズに関する設定値でした。

これらの定数が削除されたということは、Goコンパイラの構文解析器がこれらの定数に依存しない新しい実装に置き換えられたか、あるいは既存のパーサーがリファクタリングされ、これらの定数がもはや関連性がなくなったことを意味します。Goコンパイラは継続的に改善されており、このようなクリーンアップはパフォーマンスの向上、コードの簡素化、および将来の拡張性のための重要なステップです。

この変更は、Goコンパイラの進化の過程で、古いツールや設計パターンへの依存が減少し、よりGoらしい、あるいはより効率的な内部実装へと移行していることを示唆しています。

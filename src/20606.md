# [インデックス 20606] ファイルの概要

このコミットは、GoランタイムにおけるCgo（C言語との相互運用）のコールバック処理に関する重要なバグ修正です。具体的には、CコードからGoコードへのコールバック（Cgo->Goコールバック）が行われた際に、Goランタイムがゴルーチンのスタックポインタ（`g->syscallsp`）の整合性を正しく維持できない問題に対処しています。この不整合は、ガベージコレクタ（GC）がゴルーチンのスタックを正確にトレースするのを妨げ、結果としてクラッシュや不正な動作を引き起こす可能性がありました。この修正により、Cgo->Goコールバック中のスタックトレースとGCの正確性が保証されます。

## 元コミット内容

通常、`runtime.entersyscall()` を呼び出した側は、`runtime.exitsyscall()` を呼び出す前に戻ってはなりません。そうしないと、`g->syscallsp` がダングリングポインタになってしまうためです。しかし、`runtime.cgocallbackg()` はこの制約に違反していました。この問題を回避するため、CgoからGoへのコールバックの前後で `g->syscallsp` と `g->syscallpc` を保存し、`runtime.entersyscall()` の呼び出し後にそれらを復元するようにしました。これにより、`cgocall` によって保存されたシステムコールスタックフレームポインタが復元されます。この変更により、Go->Cgo->Go の連鎖から現在戻っているゴルーチンをGCが正しくトレースできるようになります。

また、`proc.c` に `g->syscallsp` が明らかに無効な場合にパニックを起こすチェックを追加しました。これは100%完璧ではありませんが、スタックが `g->syscallsp` を超えてポップされ、その後プッシュバックされたケースは捕捉できません。しかし、現在のCgoの問題を捕捉し、既存のテストがこのバグ修正なしでは失敗するようにします。

Issue #7978 を修正します。

## 変更の背景

Goランタイムは、ゴルーチンの実行状態を厳密に管理しており、特にシステムコール（syscall）の実行中は特殊な状態に遷移します。この状態遷移は、ガベージコレクタ（GC）がゴルーチンのスタックを安全かつ正確にスキャンするために不可欠です。

問題は、Cgo（GoとC/C++コード間の相互運用機能）において、CコードからGoコードへコールバックが行われるシナリオで発生しました。Goランタイムでは、システムコールに入る際に `runtime.entersyscall()` を、システムコールから出る際に `runtime.exitsyscall()` を呼び出すという厳格なペアリングが期待されます。`entersyscall()` は、現在のゴルーチン（`g`）のスタックポインタを `g->syscallsp` に保存し、GCがこのポインタを基にスタックをトレースできるようにします。

しかし、`runtime.cgocallbackg()`（CgoからGoへのコールバックを処理するGoランタイム関数）の従来の動作は、この `entersyscall()` と `exitsyscall()` のペアリングの前提を破っていました。具体的には、`cgocallbackg()` は `exitsyscall()` を呼び出した後、Goコードを実行し、その後 `entersyscall()` を呼び出してCgoの世界に戻るという流れでした。この際、`g->syscallsp` が一時的に無効な状態になる、あるいは古いスタックフレームを指したままになる可能性がありました。

この `g->syscallsp` の不整合は、特にGCが実行された際に深刻な問題を引き起こしました。GCは `g->syscallsp` を利用してゴルーチンのスタックをスキャンし、到達可能なオブジェクトを特定します。`g->syscallsp` がダングリングポインタであったり、誤った場所を指していたりすると、GCはスタック上のオブジェクトを正しく認識できず、メモリリーク、不正なメモリ解放、あるいはランタイムクラッシュといった予測不能な動作につながる可能性がありました。

このコミットは、この `g->syscallsp` の整合性問題を解決し、Go->Cgo->Goという複雑な呼び出しチェーンにおいても、GCがゴルーチンのスタックを常に正確にトレースできるようにすることを目的としています。コミットメッセージに記載されている通り、この問題はGoのIssue #7978として報告されていました。

## 前提知識の解説

### Goランタイムの基本概念

*   **ゴルーチン (Goroutine)**: Goにおける軽量な実行スレッドです。数千、数万のゴルーチンを同時に実行できます。各ゴルーチンは独自のスタックを持ちます。
*   **M (Machine)**: オペレーティングシステムのスレッドを表します。GoランタイムはMをOSスケジューラにマップし、M上でGoコードを実行します。
*   **P (Processor)**: 論理プロセッサを表し、Goコードを実行するためのコンテキストを提供します。MはPにアタッチされてゴルーチンを実行します。
*   **g (Goroutine struct)**: 各ゴルーチンは `runtime.g` 構造体で表現されます。この構造体には、ゴルーチンのスタック情報、スケジューリング情報、現在の状態などが含まれます。特に、`g->syscallsp` はシステムコール中のスタックポインタを保持します。

### Cgo (GoとC/C++の相互運用)

Cgoは、GoプログラムからC言語の関数を呼び出したり、C言語のプログラムからGo言語の関数を呼び出したりするためのメカニズムです。

*   **GoからCへの呼び出し (Go->C)**: GoコードがC関数を呼び出す場合、Goランタイムは現在のゴルーチンをシステムコール状態に遷移させ、Cコードが実行されます。
*   **CからGoへのコールバック (C->Go)**: CコードがGo関数を呼び出す場合（`//export` ディレクティブでエクスポートされたGo関数）、GoランタイムはCスタックからGoスタックへ切り替え、Go関数を実行します。この逆方向の呼び出しが、本コミットで修正される問題の核心でした。

### `g->syscallsp` とスタックトレース/GC

*   **`g->syscallsp`**: `runtime.g` 構造体内のフィールドで、ゴルーチンがシステムコールに入った時点のスタックポインタを記録します。これは、Goランタイムがシステムコール中にゴルーチンのスタックを正確に把握するために非常に重要です。
*   **スタックトレース**: プログラムの実行中に、現在アクティブな関数呼び出しの連鎖（コールスタック）を追跡することです。デバッグやエラー報告の際に利用されます。
*   **ガベージコレクタ (GC)**: GoのGCは、プログラムが使用しなくなったメモリを自動的に解放します。GCは、到達可能なオブジェクト（プログラムがまだ参照しているオブジェクト）を特定するために、ゴルーチンのスタックをスキャンします。`g->syscallsp` が正しく設定されていないと、GCはスタック上のポインタを誤って解釈し、メモリの安全性や正確性を損なう可能性があります。

### `entersyscall` と `exitsyscall`

これらはGoランタイムの内部関数で、ゴルーチンがシステムコールに入る際と出る際に呼び出されます。

*   **`runtime.entersyscall()`**: ゴルーチンがシステムコールに入る直前に呼び出されます。この関数は、ゴルーチンの状態を `Grunning` から `Gsyscall` に変更し、`g->syscallsp` を設定して、GCがシステムコール中のゴルーチンのスタックを安全にスキャンできるように準備します。
*   **`runtime.exitsyscall()`**: ゴルーチンがシステムコールから戻る直前に呼び出されます。この関数は、ゴルーチンの状態を `Gsyscall` から `Grunning` に戻し、`g->syscallsp` をクリア（または更新）します。

これらの関数はペアで動作し、Goランタイムがゴルーチンの状態とスタック情報を正確に管理するための重要な役割を担っています。このペアリングが破られると、GCやスケジューラに問題が生じる可能性があります。

## 技術的詳細

このコミットの技術的詳細を理解するためには、GoランタイムがCgoコールバックをどのように処理し、スタックポインタの整合性をどのように維持しようとしているかを深く掘り下げる必要があります。

### 問題の根源: `cgocallbackg` の特殊性

通常のGoコードがシステムコールを行う場合、`entersyscall()` が呼び出され、その後にシステムコールが実行され、最後に `exitsyscall()` が呼び出されます。このシーケンスにより、`g->syscallsp` はシステムコール中のスタックフレームの開始点を正確に指し、GCがスタックを安全にスキャンできます。

しかし、CgoのC->Goコールバックを処理する `runtime.cgocallbackg()` 関数は、この通常のシーケンスとは異なる動作をしていました。`cgocallbackg()` は、CコードからGoコードへの呼び出しを受け取ると、まず `exitsyscall()` を呼び出してCgoの世界からGoの世界へ戻ったことをランタイムに通知します。その後、Goのコールバック関数（`cgocallbackg1()`）を実行し、最後に再び `entersyscall()` を呼び出してCgoの世界に戻る準備をします。

この `exitsyscall()` -> `cgocallbackg1()` -> `entersyscall()` というシーケンスが問題でした。特に、`entersyscall()` が呼び出される際に、その時点での呼び出し元のスタックポインタが `g->syscallsp` に設定されます。しかし、`cgocallbackg()` のコンテキストでは、この `entersyscall()` は `cgocall` によって設定された元のシステムコールスタックフレームとは異なるスタックフレームから呼び出される可能性があります。これにより、`g->syscallsp` が、GCが期待する正しいスタックフレームの開始点ではなく、一時的な、あるいは無関係なスタック位置を指してしまう「ダングリングポインタ」状態になる可能性がありました。

### 解決策: `g->syscallsp` と `g->syscallpc` の保存と復元

この問題を解決するため、コミットは `runtime.cgocallbackg()` のロジックを変更しました。

1.  **保存**: `cgocallbackg()` の冒頭で、現在のゴルーチン `g` の `g->syscallsp` と `g->syscallpc` (システムコール中のプログラムカウンタ) の値を一時変数 `savedsp` と `savedpc` に保存します。これらは、CgoからGoへのコールバックが開始される前の、Go->Cgo呼び出しによって設定された正しいシステムコールコンテキストを反映しています。
2.  **`exitsyscall()` の呼び出し**: 通常通り `exitsyscall()` を呼び出し、GoランタイムにCgoの世界からGoの世界へ戻ったことを通知します。
3.  **`cgocallbackg1()` の実行**: Goのコールバック関数を実行します。
4.  **`reentersyscall()` の導入と復元**: 以前はここで `entersyscall()` を直接呼び出していましたが、新しい `runtime.reentersyscall()` 関数が導入され、代わりにこれが呼び出されます。この `reentersyscall()` には、ステップ1で保存した `savedpc` と `savedsp` が引数として渡されます。`reentersyscall()` は、これらの保存された値を使用して、`g->syscallsp` と `g->syscallpc` を正しく復元します。これにより、Cgoの世界に戻る際に、`g->syscallsp` が常にGo->Cgo呼び出しによって設定された元のシステムコールスタックフレームを指すことが保証されます。

このメカニズムにより、Go->Cgo->Goという複雑な呼び出しチェーンにおいても、`g->syscallsp` が常に有効で、GCがゴルーチンのスタックを正確にトレースできるようになります。

### `proc.c` における追加のチェック

コミットは、`src/runtime/proc.c` 内の `entersyscall` および `exitsyscall` 関連の関数に、`g->syscallsp` の有効性を検証する追加のチェックを導入しました。

*   **`entersyscall` (および `reentersyscall`) 内のチェック**: `g->syscallsp` がゴルーチンのスタック範囲 (`g->stack.lo` から `g->stack.hi`) 内にあることを確認します。範囲外であれば、`entersyscall_bad` 関数を通じてパニックを引き起こします。これは、`g->syscallsp` が明らかに不正な値を指している場合に早期に問題を検出するための安全策です。
*   **`exitsyscall` 内のチェック**: `runtime.getcallersp()` で取得した現在のスタックポインタが `g->syscallsp` よりも大きい（つまり、スタックが `g->syscallsp` の位置を超えてポップされている）場合にパニックを引き起こします。これは、`g->syscallsp` が指すべきスタックフレームが既に破棄されている可能性を示唆しており、不正な状態を検出します。

これらのチェックは、今回のCgoの問題を直接捕捉するだけでなく、将来的に同様のスタック整合性問題が発生した場合にも早期に検出するための防御的なプログラミングです。

### テストケース `issue7978.go`

このコミットには、`misc/cgo/test/issue7978.go` という新しいテストファイルが追加されています。このテストは、問題のシナリオ（Go->Cgo->Goコールバック）を再現し、修正が正しく機能していることを検証します。

## コアとなるコードの解説

### `src/runtime/cgocall.go` の変更

```go
// func cgocallbackg()
func cgocallbackg() {
	gp := getg()
	if gp != gp.m.curg {
		println("runtime: bad g in cgocallback")
		exit(2)
	}

	// entersyscall saves the caller's SP to allow the GC to trace the Go
	// stack. However, since we're returning to an earlier stack frame and
	// need to pair with the entersyscall() call made by cgocall, we must
	// save syscall* and let reentersyscall restore them.
	savedsp := unsafe.Pointer(gp.syscallsp) // 既存のg->syscallspを保存
	savedpc := gp.syscallpc                 // 既存のg->syscallpcを保存
	exitsyscall()                           // Cgoの世界からGoの世界へ出る
	cgocallbackg1()                         // Goのコールバック関数を実行
	// going back to cgo call
	reentersyscall(savedpc, savedsp) // 保存した値でg->syscallspとg->syscallpcを復元し、Cgoの世界へ戻る準備
}
```
この変更がこのコミットの核心です。`cgocallbackg` はCgoからGoへのコールバックを処理する関数です。以前は `exitsyscall()` の後に `entersyscall()` を直接呼び出していましたが、これにより `g->syscallsp` が不正な状態になる可能性がありました。
修正後は、`exitsyscall()` を呼び出す前に、現在の `g->syscallsp` と `g->syscallpc` を `savedsp` と `savedpc` に保存します。`cgocallbackg1()` でGoのコールバックが実行された後、新しく導入された `reentersyscall(savedpc, savedsp)` を呼び出します。この `reentersyscall` が、保存しておいた `pc` と `sp` を使って `g->syscallsp` と `g->syscallpc` を正しく設定し直すことで、スタックの整合性を保ちます。

### `src/runtime/proc.c` の変更

```c
// 新しく追加された関数
#pragma textflag NOSPLIT
void
runtime·reentersyscall(uintptr pc, uintptr sp)
{
	void (*fn)(void);

	// ... (既存のentersyscallのロジックの一部) ...

	// Leave SP around for GC and traceback.
	save(pc, sp); // 渡されたpcとspでg->sched.pcとg->sched.spを設定
	g->syscallsp = sp; // g->syscallspを渡されたspに設定
	g->syscallpc = pc; // g->syscallpcを渡されたpcに設定
	runtime·casgstatus(g, Grunning, Gsyscall); // ゴルーチン状態をGrunningからGsyscallへ遷移

	// g->syscallspの有効性チェック
	if(g->syscallsp < g->stack.lo || g->stack.hi < g->syscallsp) {
		fn = entersyscall_bad;
		runtime·onM(&fn);
	}
	// ... (その他のentersyscallのロジック) ...
}

// 既存のentersyscall関数の変更
#pragma textflag NOSPLIT
void
·entersyscall(int32 dummy)
{
	// 従来のentersyscallは、呼び出し元のpcとspをreentersyscallに渡すように変更
	runtime·reentersyscall((uintptr)runtime·getcallerpc(&dummy), runtime·getcallersp(&dummy));
}

// exitsyscall関数の変更
#pragma textflag NOSPLIT
void
·exitsyscall(int32 dummy)
{
	void (*fn)(G*);

	g->m->locks++;  // see comment in entersyscall

	// 新しいスタック整合性チェック
	if(runtime·getcallersp(&dummy) > g->syscallsp)
		runtime·throw("exitsyscall: syscall frame is no longer valid");

	g->waitsince = 0;
	// ... (既存のexitsyscallのロジック) ...
}
```
`runtime·reentersyscall` は、`cgocallbackg` から渡された `savedpc` と `savedsp` を使用して、`g->syscallsp` と `g->syscallpc` を明示的に設定します。これにより、Cgoコールバックの特殊な状況下でも、これらのポインタが常に正しいスタックフレームを指すことが保証されます。
また、`entersyscall` は `reentersyscall` を呼び出すように変更され、通常のシステムコールエントリポイントとしても機能します。
`exitsyscall` に追加されたチェックは、現在のスタックポインタが `g->syscallsp` よりも「上」（アドレスが大きい）にある場合にパニックを発生させます。これは、`g->syscallsp` が指すべきスタックフレームが既に破棄されている、つまりスタックの整合性が失われていることを検出するための重要な防御的チェックです。

これらの変更により、GoランタイムはCgoコールバックの複雑なスタック遷移を正確に管理し、ガベージコレクタがゴルーチンのスタックを常に安全にトレースできる状態を維持します。

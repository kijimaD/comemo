# [インデックス 25810] ファイルの概要

このコミットは、Goコンパイラの`cmd/compile`パッケージ内において、以前に削除された古いパーサ（構文解析器）の残骸であるデッドコードを削除することを目的としています。具体的には、字句解析器（lexer）と構文解析器（parser）に関連するファイルから、不要になった変数、関数、データ構造、およびコメントが取り除かれています。これにより、コンパイラコードベースのクリーンアップと保守性の向上が図られています。

## 変更の背景

このコミットの背景には、Goコンパイラの構文解析器の実装変更があります。初期のGoコンパイラ（`gc`）は、Yacc（Yet Another Compiler Compiler）のようなパーサジェネレータを使用して構文解析器を生成していました。しかし、Go言語の進化とコンパイラの最適化の過程で、Yaccベースのパーサは柔軟性やデバッグの難しさといった課題を抱えるようになりました。

そのため、Goコンパイラチームは、より制御が容易で、Go言語の特性に合わせた手書きのパーサへの移行を進めました。この移行作業の一環として、Yaccベースのパーサ本体が以前のコミットで削除されました。本コミットは、そのパーサ削除後に残された、もはや使用されていないコード（デッドコード）を特定し、クリーンアップするものです。これにより、コードベースの肥大化を防ぎ、将来的な保守や改善を容易にすることが目的です。

## 前提知識の解説

### Goコンパイラの構造 (`cmd/compile/internal/gc`)

Goコンパイラは、`cmd/compile`ディレクトリに位置しており、その内部の`internal/gc`パッケージがコンパイラの主要なロジックを含んでいます。`gc`は「Go Compiler」の略であり、Go言語のソースコードを機械語に変換する一連のフェーズ（字句解析、構文解析、意味解析、中間コード生成、最適化、コード生成など）を管理します。

### 字句解析（Lexical Analysis）と構文解析（Parsing）

*   **字句解析（Lexical Analysis）**: ソースコードをトークン（意味を持つ最小単位、例: 識別子、キーワード、演算子、リテラル）のストリームに変換するプロセスです。この処理を行うプログラムは「字句解析器（lexer）」または「スキャナ（scanner）」と呼ばれます。
*   **構文解析（Parsing）**: 字句解析器によって生成されたトークンのストリームを受け取り、言語の文法規則に従ってそれらが正しい構造（構文木、Abstract Syntax Tree: AST）を形成しているかを確認するプロセスです。この処理を行うプログラムは「構文解析器（parser）」と呼ばれます。

### パーサジェネレータ (Yacc/Bison)

Yacc（Yet Another Compiler Compiler）やBisonは、文法定義ファイル（通常はBNF形式）から構文解析器のソースコードを自動生成するツールです。これらのツールは、LALR(1)パーサなどの強力なパーサを効率的に作成できるため、多くのプログラミング言語のコンパイラやインタプリタで利用されてきました。

Yacc/Bisonによって生成されるパーサは、通常、以下のような特徴を持ちます。
*   `yyparse()`: 構文解析を開始するメイン関数。
*   `yylex()`: 字句解析器から次のトークンを取得する関数。
*   `yyerror()`: 構文エラーが発生した際に呼び出される関数。
*   `yy`構造体: Yaccが生成するパーサの内部状態やメソッドをカプセル化するために使用されることがあります。
*   `yyprev`, `yylast`: 以前に読み込んだトークンを追跡するための変数。構文解析のコンテキストやエラーリカバリに利用されることがあります。
*   `yytfix`: トークン名を文字列にマッピングするためのテーブル。エラーメッセージの表示などに使われます。

### Goコンパイラのパーサの変遷

Goコンパイラの初期バージョンでは、Yaccベースのパーサが使用されていました。しかし、Go言語の文法は特定のYaccの制約と相性が悪く、また、コンパイラのパフォーマンスやデバッグの観点から、手書きの再帰下降パーサ（recursive descent parser）への移行が決定されました。手書きパーサは、コードの可読性が高く、デバッグが容易であり、Go言語の特定の構文規則（例: セミコロン挿入規則）をより自然に扱えるという利点があります。

## 技術的詳細

このコミットは、Yaccベースのパーサが削除された後のクリーンアップであり、その痕跡を`src/cmd/compile/internal/gc/lex.go`と`src/cmd/compile/internal/gc/parser.go`から取り除いています。

### `lex.go`における変更

`lex.go`は字句解析器のロジックを主に担当していました。
*   **`yyprev`, `yylast`変数の削除**: これらの変数は、Yaccベースのパーサが以前のトークンを記憶し、構文解析のコンテキストを維持するために使用されていました。手書きパーサでは、通常、このようなグローバルなトークン履歴管理は異なる方法で行われるため、不要になりました。
*   **`Main()`関数内の`yyparse()`から`parse_file()`への変更**: これは、構文解析の開始点がYaccが生成した`yyparse`関数から、手書きパーサのメインエントリポイントである`parse_file`関数に完全に切り替わったことを明確に示しています。
*   **`LBODY`定数の削除**: `LBODY`は、おそらくYaccパーサが特定の構文要素（例えば、ブロックの開始を示す`{`）を内部的に表現するために使用していたトークン定数です。手書きパーサでは、この特定の定数表現が不要になったと考えられます。
*   **`yy`構造体、`Lex`メソッド、`Error`メソッドの削除**: `yy`構造体は、Yaccが生成するパーサのインターフェースをGoのコードに適合させるためのラッパーでした。`Lex`メソッドは`yylex`を呼び出し、`Error`メソッドは`yyerror`を呼び出す役割を担っていました。Yaccパーサがなくなったため、これらのラッパーも不要になりました。
*   **`parsing`変数の削除**: このブール変数は、`yyparse`関数が実行中であるかどうかを示すフラグとして使用されていました。手書きパーサでは、このようなグローバルな状態管理は不要か、あるいは別の方法で管理されるため、削除されました。
*   **`yylex`関数の簡素化**: `yylex`関数は、字句解析器のコアロジックの一部であり、Yaccパーサにトークンを供給する役割を担っていました。変更前は`yyprev`と`yylast`を更新していましたが、これらの変数が削除されたため、その更新ロジックも削除され、関数が簡素化されました。
*   **`yytfix`マップの削除**: `yytfix`は、Yaccパーサが生成するトークン定数（例: `LIF`）を人間が読める文字列（例: `"if"`）にマッピングするためのマップでした。これは主にエラーメッセージの生成やデバッグ出力のために使用されていましたが、Yaccパーサの削除に伴い、このマッピングも不要になりました。

### `parser.go`における変更

`parser.go`は構文解析器のロジックを主に担当していました。
*   **`tokstrings`マップからの`LBODY`の削除**: `tokstrings`マップは、トークン定数を対応する文字列にマッピングするために使用されていました。`lex.go`から`LBODY`定数が削除されたことに伴い、`parser.go`からもそのエントリが削除されました。コメント「`// we should never see this one`」は、このトークンが内部的なものであり、外部に露出しないことを示唆しています。

これらの変更は、GoコンパイラがYaccベースのパーサから完全に脱却し、よりクリーンでGoらしい手書きパーサの実装に移行したことを明確に示しています。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は、Goコンパイラの字句解析および構文解析のサブシステムから、Yaccベースのパーサに関連するすべての残骸を体系的に削除している点です。

*   **`yyprev`, `yylast`の削除**: これらのグローバル変数は、Yaccパーサがトークンの履歴を保持するために使用されていました。手書きパーサでは、通常、字句解析器がトークンを一つずつ提供し、パーサが必要に応じて先読みを行うため、このようなグローバルな履歴は不要になります。
*   **`Main()`内の`yyparse()`から`parse_file()`への変更**: これは、コンパイラのメインエントリポイントが、Yaccが生成したパーサの呼び出しから、Go言語で直接記述された新しいパーサの呼び出しに切り替わったことを示しています。これにより、コンパイラの制御フローが完全に新しいパーサ実装に移行しました。
*   **`LBODY`定数の削除**: `LBODY`は、おそらくYaccパーサの内部で特定の構文要素（例えば、コードブロックの開始を示す`{`）を識別するために使われていたトークンタイプでした。手書きパーサでは、この特定の定数表現が不要になったか、あるいは異なる方法で処理されるようになったため、削除されました。
*   **`yy`構造体とそのメソッド、`parsing`変数の削除**: `yy`構造体は、YaccパーサのインターフェースをGoのコードに適合させるためのアダプターのような役割を担っていました。`Lex`メソッドは字句解析器からのトークン取得を、`Error`メソッドはエラー報告をYaccパーサの期待する形式で行っていました。Yaccパーサがなくなったため、これらのアダプターコードも不要となり、削除されました。`parsing`変数は、`yyparse`の実行状態を追跡するためのものでしたが、これもYaccパーサに特化したものであったため、削除されました。
*   **`yylex`関数の簡素化**: `yylex`関数は、字句解析器が次のトークンを返すためのインターフェースでした。以前は`yyprev`と`yylast`を更新していましたが、これらの変数が削除されたため、そのロジックも削除され、関数がよりシンプルになりました。
*   **`yytfix`マップの削除**: `yytfix`マップは、Yaccパーサが生成する数値トークン定数と、それに対応する人間が読める文字列（例: `LIF` -> `"if"`）をマッピングするために使用されていました。これは主にエラーメッセージの生成やデバッグ出力に役立っていましたが、Yaccパーサが削除されたことで、このマッピングも不要になりました。

これらの変更は、GoコンパイラがYaccベースのパーサという外部ツールへの依存を完全に排除し、Go言語の特性を最大限に活かした、より統合された手書きパーサの実装へと移行したことを象徴しています。これにより、コンパイラのコードベースはより一貫性があり、理解しやすく、保守しやすくなりました。

# [インデックス 25291] ファイルの概要

このコミットは、Go言語の型チェッカー (`go/types` パッケージ) における、型付き定数シフト演算の表現可能性チェックに関するバグ修正です。具体的には、シフト演算の結果がその定数の型で表現可能であるかを検証するロジックが追加されました。これにより、コンパイル時にオーバーフローを検出できるようになり、予期せぬ実行時エラーを防ぎます。

## 変更の背景

Go言語では、定数式はコンパイル時に評価されます。特にシフト演算 (`<<`, `>>`) は、ビット操作において頻繁に用いられます。このコミット以前は、型付き定数（例: `int8(1)`）に対してシフト演算を行った際、その演算結果が元の型で表現可能な範囲に収まっているかどうかのチェックが不十分でした。

例えば、`int8(-1) << 8` のような式を考えます。`int8` 型は -128 から 127 までの値を表現できます。`-1` を8ビット左シフトすると、結果は `int8` の範囲を大きく超えてしまいます。しかし、このオーバーフローがコンパイル時に検出されず、型チェッカーをすり抜けてしまう可能性がありました。これにより、開発者が意図しない値が生成されたり、後続の処理で予期せぬバグが発生したりするリスクがありました。

この問題は、Go言語の型安全性と堅牢性を損なうものであったため、`go/types` パッケージにおいて、型付き定数シフト演算の結果がその型で表現可能であるかを厳密にチェックするよう修正されました。コミットメッセージにある `Fixes #12945` は、この問題が特定のバグ報告（または内部トラッキング）に対応するものであることを示しています。

## 前提知識の解説

### Go言語の定数

Go言語の定数には「型なし定数 (untyped constant)」と「型付き定数 (typed constant)」があります。
*   **型なし定数**: 明示的な型が指定されていない定数です。例えば `const x = 100` の `100` は型なし整数定数です。型なし定数は、必要に応じてより広い精度で計算され、最終的に変数に代入される際にその変数の型に変換されます。この際、オーバーフローが発生すればエラーとなります。
*   **型付き定数**: 明示的な型が指定された定数です。例えば `const x int8 = 100` の `100` は型付き `int8` 定数です。型付き定数は、その指定された型の範囲内でなければなりません。

### シフト演算子 (`<<`, `>>`)

Go言語におけるシフト演算子は、左オペランドのビットパターンを右オペランドで指定された回数だけ左または右にシフトします。
*   `x << y`: `x` を `y` ビット左シフトします。
*   `x >> y`: `x` を `y` ビット右シフトします。

シフト演算の右オペランドは符号なし整数型であるか、型なし定数でなければなりません。左オペランドは整数型であるか、型なし定数でなければなりません。

### 表現可能性 (Representability)

ある値が特定の型で「表現可能 (representable)」であるとは、その値がその型の取りうる値の範囲内に収まることを意味します。例えば、`int8` 型は -128 から 127 までの整数を表現できます。`128` は `int8` では表現できません。

### `go/types` パッケージ

`go/types` パッケージは、Goコンパイラのフロントエンドの一部であり、Goプログラムの型チェックと定数評価を担当します。このパッケージは、ソースコードの抽象構文木 (AST) を受け取り、各式の型を決定し、型エラーを報告します。定数式の場合、その値を計算し、それが適切な型で表現可能であるかを検証します。

## 技術的詳細

このコミットの核心は、`go/types` パッケージ内の `shift` 関数に、型付き定数に対するシフト演算後の表現可能性チェックを追加した点にあります。

Goコンパイラは、定数式を評価する際に、`constant.Value` 型を使用して値を表現します。これは、Goの組み込み型よりも広い精度を持つことができ、オーバーフローを遅延させることで、より正確な定数計算を可能にします。しかし、最終的にその定数が特定の型を持つ場合（型付き定数）、その値はその型の範囲内に収まらなければなりません。

変更前の `shift` 関数では、型なし定数に対するシフト演算の結果は、その後の代入や使用時に型チェックが行われていました。しかし、型付き定数に対するシフト演算の場合、演算自体は `constant.Shift` を使って広い精度で行われるものの、その結果が元の型に収まるかどうかのチェックが欠けていました。

このコミットでは、以下のロジックが追加されました。

1.  `constant.Shift` を用いてシフト演算を実行し、結果を `x.val` に格納します。この時点では、`x.val` は広い精度を持つ `constant.Value` です。
2.  `isTyped(x.typ)` で、現在のオペランド `x` が型付き定数であるかをチェックします。
3.  もし型付き定数であれば、`check.representable(x, x.typ.Underlying().(*Basic))` を呼び出して、シフト演算の結果 (`x.val`) が `x.typ` の基底型 (`Underlying().(*Basic)`) で表現可能であるかを検証します。
4.  `e != nil` のチェックは、エラーメッセージをより正確にするために、元のASTノード (`e`) を `x.expr` に設定するものです。

この変更により、型付き定数に対するシフト演算の結果がオーバーフローする場合、コンパイル時に `overflows` エラーが報告されるようになります。

## コアとなるコードの解説

### `src/go/types/expr.go` の変更点

1.  **`shift` 関数のシグネチャ変更**:
    `func (check *Checker) shift(x, y *operand, op token.Token)`
    から
    `func (check *Checker) shift(x, y *operand, e *ast.BinaryExpr, op token.Token)`
    へと変更されました。
    新しい引数 `e *ast.BinaryExpr` は、シフト演算が行われている元の抽象構文木 (AST) の二項演算式ノードを渡すために追加されました。これは、エラーメッセージを生成する際に、どのソースコード位置でエラーが発生したかを正確に指し示すために使用されます。

2.  **表現可能性チェックの追加**:
    `x.val = constant.Shift(x.val, op, uint(s))` の行の直後に、以下のコードブロックが追加されました。
    ```go
    		// Typed constants must be representable in
    		// their type after each constant operation.
    		if isTyped(x.typ) {
    			if e != nil {
    				x.expr = e // for better error message
    			}
    			check.representable(x, x.typ.Underlying().(*Basic))
    		}
    ```
    *   `isTyped(x.typ)`: オペランド `x` の型 (`x.typ`) が型付きであるかどうかを判定します。型なし定数に対しては、このチェックはスキップされます。
    *   `if e != nil { x.expr = e }`: もし `e` (ASTノード) が提供されていれば、それをオペランド `x` の `expr` フィールドに設定します。これにより、`check.representable` がエラーを報告する際に、より正確なソースコード位置情報を提供できます。
    *   `check.representable(x, x.typ.Underlying().(*Basic))`: これが新しい表現可能性チェックの呼び出しです。
        *   `x`: チェック対象のオペランド（シフト演算の結果を含む）。
        *   `x.typ.Underlying().(*Basic)`: オペランド `x` の基底型を取得します。例えば、`type MyInt int8` のようなカスタム型の場合でも、その基底型である `int8` に対して表現可能性をチェックします。

3.  **`binary` 関数の呼び出し変更**:
    `func (check *Checker) binary(...)` 関数内で、シフト演算子 (`isShift(op)`) の場合に `shift` 関数を呼び出す箇所が変更されました。
    `check.shift(x, &y, op)`
    から
    `check.shift(x, &y, e, op)`
    へと変更され、`e` (現在の二項演算式ノード) が `shift` 関数に渡されるようになりました。

### `src/go/types/testdata/const1.src` の変更点

このファイルは、`go/types` パッケージのテストデータとして使用されるGoのソースコードスニペットです。追加されたテストケースは、このコミットで修正された問題を具体的に示しています。

```go
const (
	_ = int8(-1) << 7
	_ = int8 /* ERROR "overflows" */ (-1) << 8

	_ = uint32(1) << 31
	_ = uint32 /* ERROR "overflows" */ (1) << 32
)
```

*   `_ = int8(-1) << 7`: `int8` 型の `-1` を 7 ビット左シフトします。結果は `-128` であり、`int8` の範囲内（-128 から 127）に収まるため、エラーは発生しません。
*   `_ = int8 /* ERROR "overflows" */ (-1) << 8`: `int8` 型の `-1` を 8 ビット左シフトします。結果は `-256` となり、`int8` の範囲をオーバーフローします。この行には `/* ERROR "overflows" */` というコメントが付加されており、`go/types` のテストフレームワークがこの行で「overflows」というエラーメッセージが報告されることを期待していることを示しています。
*   `_ = uint32(1) << 31`: `uint32` 型の `1` を 31 ビット左シフトします。結果は `2^31` であり、`uint32` の範囲内（0 から `2^32 - 1`）に収まるため、エラーは発生しません。
*   `_ = uint32 /* ERROR "overflows" */ (1) << 32`: `uint32` 型の `1` を 32 ビット左シフトします。結果は `2^32` となり、`uint32` の範囲をオーバーフローします。同様に、`/* ERROR "overflows" */` コメントにより、エラーが期待されます。

これらのテストケースは、型付き定数に対するシフト演算において、オーバーフローが正しく検出されるようになったことを検証しています。

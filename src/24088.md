# [インデックス 24088] ファイルの概要

このコミットは、Goコンパイラにおける行番号の帰属に関する複数の問題を修正します。具体的には、構造体、配列、スライス、マップのリテラル展開時に生成される一時変数への代入で誤った行番号が使用される問題と、インライン化された関数の引数で誤った行番号が置き換えられる問題に対処しています。これにより、デバッグ情報としての行番号の正確性が向上し、開発者がより正確なスタックトレースやエラー報告を得られるようになります。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、デバッグ情報として各命令がソースコードのどの行に対応するかという行番号情報を付加します。この行番号情報は、エラー発生時のスタックトレースやデバッガでのステップ実行において非常に重要です。しかし、このコミット以前には、Goコンパイラが生成する一部のコードにおいて、この行番号情報が正しく設定されないという問題がありました。

主な問題点は以下の二つです。

1.  **リテラル展開時の一時変数における行番号の誤り**: 構造体、配列、スライス、マップなどの複合リテラルを初期化する際、コンパイラは内部的に一時変数を生成し、その一時変数にリテラルの要素を代入するコードを生成します。このとき、生成された一時変数への代入文に、リテラル内の式が記述されている本来の行番号ではなく、誤った行番号が割り当てられていました。これにより、例えばマップリテラル内でパニックが発生した場合、スタックトレースが誤った行番号を指し示し、デバッグを困難にしていました。
2.  **インライン化された関数の引数における行番号の誤り**: コンパイラはパフォーマンス向上のために、小さな関数呼び出しを呼び出し元に直接展開する「インライン化」を行います。このインライン化の際に、インライン化された関数の引数に設定されていた正しい行番号が、誤って置き換えられてしまうことがありました。

これらの問題は、Goコンパイラの内部的な最適化やコード生成のメカニズムに起因していました。特に、コミットメッセージで言及されている`CL 9721`は、一時変数の割り当て方法を変更したことで、この行番号の誤りが顕在化したとされています。`CL 9721`以前は、`tmp_wrongline := expr`のようなコードが`tmp_rightline := expr; tmp_wrongline := tmp_rightline`のように変換され、結果的に正しい行番号が伝播していました。しかし、`CL 9721`でこの中間的な一時変数が回避されたことで、本来の行番号が失われる問題が明らかになったのです。

また、`CL 10334`に関連する修正も含まれており、行番号として`-1`という不正な値が残ってしまうケースがあったようです。これは、行番号が未設定であることを示す値として`-1`が使われることがありますが、この場合は`0`（未設定または不明）であるべき箇所で`-1`が残存していたと考えられます。

これらの問題を解決し、Goプログラムのデバッグ体験を向上させることが、このコミットの背景にあります。

## 前提知識の解説

このコミットの理解を深めるために、以下のGoコンパイラおよびGo言語の概念について解説します。

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。`cmd/compile`は、字句解析、構文解析、型チェック、中間表現の生成、最適化、コード生成といった一連のフェーズを経て、実行可能なバイナリを生成します。このコミットで修正されているのは、主に中間表現の操作とコード生成フェーズにおける行番号情報の扱いです。
*   **一時変数 (Temporaries)**: コンパイラが内部的に生成する変数で、ソースコードには直接現れません。複雑な式やリテラルの評価結果を一時的に保持したり、最適化のために導入されたりします。例えば、`a := f() + g()`のような式では、`f()`と`g()`の評価結果を一時変数に格納してから加算を行うことがあります。
*   **構造体、配列、スライス、マップリテラル**: Go言語で複合型の値を直接記述するための構文です。
    *   **構造体リテラル**: `type S struct { A int; B string }; s := S{A: 1, B: "hello"}`
    *   **配列リテラル**: `a := [3]int{1, 2, 3}`
    *   **スライスリテラル**: `s := []int{1, 2, 3}`
    *   **マップリテラル**: `m := map[string]int{"a": 1, "b": 2}`
    これらのリテラルは、コンパイラによって内部的に複数の代入文に展開されることがあります。
*   **インライン化 (Inlining)**: コンパイラの最適化手法の一つで、小さな関数呼び出しを、その関数の本体コードで直接置き換えることです。これにより、関数呼び出しのオーバーヘッド（スタックフレームの作成、引数のプッシュ、戻りアドレスの保存など）を削減し、プログラムの実行速度を向上させます。しかし、インライン化はデバッグ情報を複雑にする可能性があり、行番号の正確な追跡が課題となることがあります。
*   **行番号の帰属 (Line Number Attribution)**: コンパイルされたコードの各命令が、元のソースコードのどの行に対応するかを示す情報です。これは、デバッガがソースコードと実行中のプログラムの状態を同期させるために不可欠です。
*   **`setlineno` 関数**: Goコンパイラの内部関数で、AST (Abstract Syntax Tree) ノードや生成されるコードに現在のソースコードの行番号を設定するために使用されます。この関数が適切なタイミングで、適切な行番号を引数として呼び出されることが、正確なデバッグ情報を生成する上で重要です。
*   **CL (Change List)**: Goプロジェクトの開発で使われるGerritコードレビューシステムにおける変更の単位です。各コミットは通常、一つのCLに対応します。

## 技術的詳細

このコミットは、Goコンパイラの複数の箇所にわたって行番号の取り扱いを修正しています。

1.  **`src/cmd/compile/internal/gc/inl.go` におけるインライン化の修正**:
    インライン化処理において、インライン化される関数の引数に設定されている行番号が誤って上書きされる問題がありました。`mkinlcall1`関数内で、インライン化された呼び出しの引数リスト（`as.Rlist`）を一時的に`nil`に設定し、`setlno`関数が呼び出し全体の行番号を設定する際に引数の行番号を上書きしないようにしています。その後、元の引数リストを復元することで、引数本来の行番号が保持されるようにしています。これは、引数自体が持つ行番号が、インライン化された呼び出しの行番号よりも優先されるべきであるという設計思想に基づいています。

2.  **`src/cmd/compile/internal/gc/sinit.go` におけるリテラル展開の修正**:
    構造体、配列、スライス、マップのリテラル展開時に生成される一時変数への代入において、正しい行番号が設定されるように`setlineno`の呼び出しが追加されています。
    *   `staticcopy`関数内では、コピーされるノード`rr`に対して`setlineno(rr)`が追加され、正しい行番号が設定されるようになっています。
    *   `staticassign`関数内では、リテラル要素の式`e.Expr`に対して`setlineno(e.Expr)`が追加されています。
    *   `structlit`, `arraylit`, `slicelit`, `maplit`といったリテラル処理関数内で、リテラルの各要素（`value`や`index`）に対応する代入文を生成する直前に`setlineno(value)`や`setlineno(index)`が追加されています。これにより、リテラル内の各要素がソースコードのどの行に記述されているかという情報が、生成される一時変数への代入文に正確に反映されるようになります。特にマップリテラルのキーと値の代入、および最終的なマップへの要素追加の代入において、それぞれ`setlineno`が追加されています。

3.  **`src/cmd/compile/internal/gc/subr.go` における行番号の`-1`修正**:
    `treecopy`関数内で、ノードをコピーする際に、行番号が`-1`の場合に上書きしないという条件が`lineno != -1`から`lineno != 0`に変更されています。Goコンパイラでは、行番号が未設定であることを示すために`0`を使用することが一般的です。`-1`が残存しているケースは不正な状態であり、これを`0`として扱うことで、行番号の初期化がより一貫性を持つようになります。

これらの修正により、コンパイラが生成する中間コードや最終的なバイナリに含まれるデバッグ情報としての行番号が、ソースコードの意図とより一致するようになります。これにより、デバッガの精度が向上し、エラーメッセージやスタックトレースが開発者にとってより有用なものとなります。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/inl.go`

インライン化処理を行う`mkinlcall1`関数において、`setlno`関数が呼び出される前に、インライン化される関数の引数リスト`as.Rlist`を一時的に`nil`に設定しています。
```go
	args := as.Rlist
	as.Rlist = nil
	setlno(call, int(n.Lineno))
	as.Rlist = args
```
これは、`setlno`が呼び出し全体の行番号を設定する際に、引数ノードの既存の行番号を誤って上書きしないようにするためです。引数ノードは、それ自体がソースコード上の特定の行に記述されており、その行番号は保持されるべきです。この変更により、インライン化後も引数の行番号が正しく維持されるようになります。

### `src/cmd/compile/internal/gc/sinit.go`

このファイルでは、リテラル展開時に生成される一時変数への代入文に対して、`setlineno`関数を明示的に呼び出す変更が多数行われています。
例えば、`staticcopy`関数内では、コピーされるノード`rr`に対して`setlineno(rr)`が追加されています。
```go
				rr.Orig = rr // completely separate copy
				rr.Type = ll.Type
				rr.Xoffset += e.Xoffset
				setlineno(rr) // ここで正しい行番号を設定
				*out = list(*out, Nod(OAS, ll, rr))
```
また、`structlit`, `arraylit`, `slicelit`, `maplit`といった関数では、リテラルの各要素（`value`や`index`）に対応する代入文を生成する直前に`setlineno`が追加されています。
```go
		// build list of var.field = expr
		setlineno(value) // valueの行番号を設定
		a = Nod(ODOT, var_, newname(index.Sym))
		a = Nod(OAS, a, value)
```
これらの変更は、リテラル内の各要素がソースコードのどの行に記述されているかという情報を、コンパイラが生成する一時変数への代入文に正確に反映させることを目的としています。これにより、リテラル内の特定の式でエラーが発生した場合でも、スタックトレースが正確なソースコードの行を指し示すようになります。

### `src/cmd/compile/internal/gc/subr.go`

`treecopy`関数内の条件式が変更されています。
```diff
-		if lineno != -1 {
+		if lineno != 0 {
 			m.Lineno = lineno
 		}
```
以前は、コピー元の行番号`lineno`が`-1`でない場合にのみ、コピー先のノード`m`に行番号を設定していました。この変更により、`lineno`が`0`でない場合に設定するようになります。Goコンパイラでは、行番号が未設定であることを示すために`0`を使用することが一般的であるため、この変更は行番号の初期化と取り扱いの一貫性を向上させます。`-1`という値が残存する不正なケースを修正し、`0`として扱うことで、より堅牢な行番号管理を実現しています。

# [インデックス 22990] ファイルの概要

このコミットは、Goコンパイラのコード生成において、ブール値の生成方法を最適化するものです。具体的には、条件付きジャンプ命令（`Jcc`）の代わりに、条件に基づいてバイト値を設定する命令（`SETcc`）を使用することで、より短く、ジャンプを含まないコードを生成し、その結果として他の最適化の機会を増やすことを目的としています。

## 元コミット内容

Goコンパイラ（`cmd/internal/gc`）とAMD64アーキテクチャ向けバックエンド（`cmd/6g`、現在の`cmd/compile`の一部）において、ブール値の生成方法を変更します。具体的には、条件分岐命令（`Jcc`）を用いてブール値を生成する代わりに、条件に基づいてレジスタに直接0または1を書き込む`SETcc`命令を使用するように変更します。これにより、生成されるアセンブリコードがより短くなり、ジャンプ命令がなくなることで、パイプラインの効率が向上し、さらなる最適化（peephole optimizationなど）の機会が生まれます。

例として、`func f(i, j int) bool { return i == j }` のような単純な比較関数において、変更前は条件付きジャンプと無条件ジャンプを組み合わせてブール値を設定していましたが、変更後は`SETEQ`命令一つで同等の処理を実現しています。

この変更により、`regexp`パッケージのベンチマークで最大6.27%の性能向上が見られ、`godoc`バイナリのサイズも約0.12%削減されました。この最適化は、まずAMD64アーキテクチャに適用され、他のアーキテクチャへの適用は今後のコミットで検討される予定です。

## 変更の背景

従来のGoコンパイラでは、`i == j`のようなブール値を返す比較演算子に対して、条件付きジャンプ（`Jcc`）と無条件ジャンプ（`JMP`）を組み合わせたコードを生成していました。これは、比較結果に応じて異なるコードパスに分岐し、最終的にブール値（0または1）をレジスタに書き込むというロジックでした。

このアプローチにはいくつかの課題がありました。
1.  **コードサイズの増大**: ジャンプ命令とそのターゲットとなるラベルが必要となるため、生成されるアセンブリコードが長くなりがちでした。
2.  **パイプラインの停止**: ジャンプ命令はCPUの命令パイプラインを停止させる可能性があり、特に予測が難しい分岐では性能低下を招くことがあります。現代のCPUは投機的実行と分岐予測に優れていますが、それでもジャンプの数を減らすことは一般的に性能向上に寄与します。
3.  **最適化の妨げ**: ジャンプを含む複雑な制御フローは、コンパイラが後続のpeephole optimization（局所的なコード改善）を行う上で障壁となることがありました。

これらの課題を解決し、より効率的で高性能なコードを生成するために、`SETcc`命令の導入が検討されました。`SETcc`命令は、比較結果を直接バイト値（0または1）としてレジスタに格納できるため、ジャンプを完全に排除し、より線形なコードパスを実現します。

## 前提知識の解説

### x86アセンブリにおける条件コードと命令

*   **条件コード (Condition Codes / Flags)**: x86アーキテクチャのCPUには、演算結果の状態を示すフラグレジスタ（EFLAGS/RFLAGS）があります。例えば、`CMP`（比較）命令を実行すると、その結果に基づいて以下のフラグが設定されます。
    *   **ZF (Zero Flag)**: 結果がゼロの場合にセット（比較対象が等しい場合）。
    *   **CF (Carry Flag)**: 符号なし演算で桁上がり/桁借りが発生した場合にセット。
    *   **SF (Sign Flag)**: 結果が負の場合にセット。
    *   **OF (Overflow Flag)**: 符号付き演算でオーバーフローが発生した場合にセット。
    *   **PF (Parity Flag)**: 結果の最下位バイトの1のビット数が偶数の場合にセット。
*   **`Jcc` (Conditional Jump) 命令**: これらの条件コードフラグの状態に基づいて、プログラムの実行フローを別の場所へジャンプさせる命令です。例えば、`JEQ`（Jump if Equal）はZFがセットされている場合にジャンプします。
    *   例: `CMP EAX, EBX` の後、`JEQ label` はEAXとEBXが等しければ`label`へジャンプします。
*   **`SETcc` (Set Byte on Condition) 命令**: これらの条件コードフラグの状態に基づいて、指定された8ビットレジスタまたはメモリ位置に1（条件が真の場合）または0（条件が偽の場合）を書き込む命令です。ジャンプは発生しません。
    *   例: `CMP EAX, EBX` の後、`SETEQ AL` はEAXとEBXが等しければALレジスタに1を、そうでなければ0を書き込みます。

### コンパイラの最適化

*   **コード生成 (Code Generation)**: コンパイラの最終段階で、中間表現からターゲットマシン（この場合はx86-64）の機械語コードを生成するプロセスです。
*   **peephole optimization (ピーホール最適化)**: 生成されたコードの小さな「窓（peephole）」を覗き込み、より効率的な命令シーケンスに置き換える局所的な最適化手法です。例えば、`JEQ L1; MOV $0, R; JMP L2; L1: MOV $1, R; L2:` のようなパターンを `SETEQ R` に置き換えるのは、peephole optimizationの一種と見なせます。
*   **分岐予測とパイプライン**: 現代のCPUは、命令を並行して処理するためにパイプラインを使用します。分岐命令があると、CPUは次に実行すべき命令を予測する必要があります。予測が外れるとパイプラインがフラッシュされ、性能が低下します。ジャンプを減らすことは、分岐予測の失敗によるペナルティを回避し、パイプラインの効率を向上させるのに役立ちます。

### Goコンパイラの構造（当時のGo 1.x系）

*   **`cmd/internal/gc`**: Goコンパイラのフロントエンドと中間部分を担うパッケージです。Goのソースコードを解析し、抽象構文木（AST）を構築し、型チェックや一部の最適化を行います。アーキテクチャに依存しないコード生成ロジックも含まれます。
*   **`cmd/6g`**: Go 1.x系におけるAMD64アーキテクチャ向けのコンパイラバックエンドです。`gc`から渡された中間表現をAMD64のアセンブリ命令に変換する役割を担っていました。現在のGoでは、`cmd/compile`が統合されたコンパイラであり、各アーキテクチャのバックエンドは`cmd/compile/internal/amd64`などのようにサブパッケージとして存在します。

## 技術的詳細

このコミットの核心は、Goコンパイラがブール値を生成する際のコードパターンを根本的に変更した点にあります。

### 変更前のアセンブリコードの挙動

コミットメッセージの例 `func f(i, j int) bool { return i == j }` の「Before」のアセンブリコードを見てみましょう。

```assembly
        MOVQ    "".i+8(FP), BX   ; iをBXレジスタにロード
        MOVQ    "".j+16(FP), BP  ; jをBPレジスタにロード
        CMPQ    BX, BP           ; BXとBPを比較し、フラグを設定
        JEQ     21               ; 等しければアドレス21へジャンプ
        MOVB    $0, "".~r2+24(FP) ; 等しくなければ結果レジスタに0を書き込む
        RET                      ; 関数からリターン
21:     MOVB    $1, "".~r2+24(FP) ; 等しければ結果レジスタに1を書き込む
        JMP     20               ; アドレス20へジャンプ（RET命令の直前）
```

このコードは、`i == j` が真の場合と偽の場合で異なるパスをたどり、最終的に結果レジスタ（`"".~r2+24(FP)`）に0または1を書き込んでいます。ジャンプ命令が2つ含まれており、特に`JMP 20`は、`MOVB $1`の後に無条件に`RET`命令の直前へジャンプするという、冗長な制御フローを形成しています。

### 変更後のアセンブリコードの挙動

「After」のアセンブリコードは以下のようになります。

```assembly
        MOVQ    "".i+8(FP), BX   ; iをBXレジスタにロード
        MOVQ    "".j+16(FP), BP  ; jをBPレジスタにロード
        CMPQ    BX, BP           ; BXとBPを比較し、フラグを設定
        SETEQ   "".~r2+24(FP)    ; 等しければ結果レジスタに1を、そうでなければ0を書き込む
        RET                      ; 関数からリターン
```

`JEQ`と`JMP`命令が完全に削除され、代わりに`SETEQ`命令が導入されています。`SETEQ`は、直前の`CMPQ`命令によって設定されたZFフラグの状態に基づいて、結果レジスタに直接0または1を書き込みます。これにより、コードが大幅に短縮され、ジャンプが一切なくなりました。

### 性能への影響

コミットメッセージに記載されているベンチマーク結果は、この最適化が実際のアプリケーションの性能にポジティブな影響を与えたことを示しています。特に`regexp`パッケージのベンチマークでは、多くのテストケースで数パーセントの性能向上が見られます。これは、ジャンプの削減がCPUのパイプライン効率を改善し、命令の実行速度を向上させたためと考えられます。

また、`godoc`バイナリのサイズが約0.12%削減されたことも報告されています。これは、ジャンプ命令が不要になったことで、生成される機械語コードのバイト数が減少した直接的な結果です。

### コード変更の概要

*   **`src/cmd/6g/galign.go`**: `gc.Thearch.Ginsboolval`という新しいアーキテクチャ固有の関数ポインタが追加され、ブール値生成ロジックが抽象化されました。
*   **`src/cmd/6g/gsubr.go`**:
    *   `ginsboolval`関数が追加されました。これは、条件付きジャンプ命令に対応する`SETcc`命令を返す`jmptoset`関数を呼び出し、その`SETcc`命令を使ってブール値を生成します。
    *   `jmptoset`関数が追加されました。これは、`x86.AJEQ`（Jump if Equal）のような条件付きジャンプ命令のオペコードを受け取り、それに対応する`x86.ASETEQ`（Set if Equal）のような`SETcc`命令のオペコードを返します。
    *   `optoas`関数に、`TBOOL`型に対する`OAND`や`OOR`などの論理演算子、および`OPC`（Parity Clear）に対する`AJPC`（Jump if Parity Clear）のケースが追加されました。
*   **`src/cmd/6g/prog.go`**: `progtable`に新しい`SETcc`命令（`ASETCC`, `ASETCS`, `ASETEQ`など）が追加され、それぞれの命令がバイトサイズの結果を書き込み、条件コードを使用することが定義されました。
*   **`src/cmd/internal/gc/cgen.go`**:
    *   `Cgen`関数内の`OOROR`, `OANDAND`, `OEQ`, `ONE`, `OLT`, `OLE`, `OGE`, `OGT`, `ONOT`といったブール値を生成する演算子に対する処理が変更されました。以前はジャンプを用いた`Bgen`を呼び出していましたが、新しい`Bvgen`関数を呼び出すようになりました。
    *   `Bgen`関数が`bgenx`のラッパーとなり、`Bvgen`関数が追加されました。`Bvgen`は、アーキテクチャが`Ginsboolval`をサポートしている場合はそれを使用し、そうでない場合は従来のジャンプベースの`bvgenjump`を使用するようにフォールバックします。
    *   `bgenx`関数は、ブール値を生成するか（`res`が非nilの場合）、分岐を生成するか（`res`がnilの場合）を制御するバックエンド関数です。
    *   `bvgenjump`関数は、従来のジャンプベースのブール値生成ロジックをカプセル化したものです。
    *   `bins`関数が追加されました。これは、比較結果を処理するための命令を挿入する汎用関数で、`res`が非nilの場合は`Ginsboolval`を使って値を生成し、`res`がnilの場合は`Gbranch`を使ってジャンプを生成します。
*   **`src/cmd/internal/gc/cplx.go`**: 複素数型の比較におけるブール値生成ロジックが更新され、`complexbool`関数が`res`引数を受け取るようになり、`Bvgen`を使用してジャンプフリーなブール値生成をサポートするようになりました。
*   **`src/cmd/internal/gc/go.go`**: `Arch`構造体に`Ginsboolval`フィールドが追加されました。これは、コンパイラバックエンドが実装すべき、比較結果からブール値を生成する関数へのポインタです。
*   **`src/cmd/internal/gc/syntax.go`**: `OPC`（Parity Clear）という新しいオペコードが追加されました。

## コアとなるコードの解説

### `src/cmd/internal/gc/go.go` の `Arch` 構造体

```go
type Arch struct {
	// ...
	Ginsboolval  func(int, *Node)
	// ...
}
```
`Arch`構造体は、各アーキテクチャ固有のコンパイラバックエンドが実装すべき関数群を定義しています。ここに`Ginsboolval`が追加されたことで、コンパイラはアーキテクチャに依存しない形でブール値生成の最適化を要求できるようになりました。`Ginsboolval`は、条件付きジャンプ命令のオペコード（例: `x86.AJEQ`）と結果を格納するノードを受け取り、対応する`SETcc`命令を生成する役割を担います。

```go
func bgenx(n, res *Node, wantTrue bool, likely int, to *obj.Prog) {
	// ...
	genval := res != nil // resがnilでなければ値を生成するモード
	// ...
	if genval {
		// ... (SETcc命令を使った値生成ロジック) ...
	} else {
		// ... (ジャンプを使った分岐ロジック) ...
	}
	// ...
}

// bins inserts an instruction to handle the result of a compare.
// If res is non-nil, it inserts appropriate value generation instructions.
// If res is nil, it inserts a branch to to.
func bins(typ *Type, res *Node, a, likely int, to *obj.Prog) {
	a = Thearch.Optoas(a, typ)
	if res != nil {
		// value gen
		Thearch.Ginsboolval(a, res)
	} else {
		// jump
		Patch(Gbranch(a, typ, likely), to)
	}
}
```
`Bvgen`は、ブール値を計算して結果を`res`ノードに格納するための主要な関数です。まず、現在のアーキテクチャが`Ginsboolval`（`SETcc`命令を生成する機能）をサポートしているかを確認します。サポートしていれば、`bgenx`を呼び出して`SETcc`ベースのコード生成パスに進みます。サポートしていなければ、従来のジャンプベースの`bvgenjump`にフォールバックします。

`bgenx`は、`Bgen`（分岐を生成する）と`Bvgen`（値を生成する）の両方のバックエンドとして機能します。`res`引数が`nil`かどうかで、分岐を生成するか、ブール値を生成するかを切り替えます。ブール値を生成するモード（`genval`が`true`）では、`Thearch.Ginsboolval`を呼び出して`SETcc`命令を挿入します。

`bins`関数は、比較結果を処理する命令を挿入する汎用ヘルパーです。`res`が指定されていれば`Thearch.Ginsboolval`を呼び出して`SETcc`命令を生成し、そうでなければ`Gbranch`を呼び出して条件付きジャンプを生成します。これにより、コード生成ロジックが簡潔になり、再利用性が高まります。

### `src/cmd/6g/gsubr.go` の `ginsboolval` と `jmptoset`

```go
func ginsboolval(a int, n *gc.Node) {
	gins(jmptoset(a), nil, n)
}

// jmptoset returns ASETxx for AJxx.
func jmptoset(jmp int) int {
	switch jmp {
	case x86.AJEQ:
		return x86.ASETEQ
	case x86.AJNE:
		return x86.ASETNE
	// ... 他のJcc命令と対応するSETcc命令のマッピング ...
	}
	gc.Fatal("jmptoset: no entry for %v", gc.Oconv(jmp, 0))
	panic("unreachable")
}
```
`ginsboolval`は、AMD64アーキテクチャにおける`Ginsboolval`の実装です。引数`a`として渡された条件付きジャンプ命令のオペコード（例: `AJEQ`）を`jmptoset`に渡し、対応する`SETcc`命令のオペコード（例: `ASETEQ`）を取得します。その後、`gins`関数を使ってその`SETcc`命令をアセンブリコードに挿入します。

`jmptoset`は、条件付きジャンプ命令のオペコードと、それに対応する`SETcc`命令のオペコードをマッピングする重要な関数です。これにより、コンパイラは抽象的な条件（等しい、より小さいなど）を、具体的な`SETcc`命令に変換できるようになります。

これらの変更により、Goコンパイラはブール値を生成する際に、より効率的な`SETcc`命令を優先的に使用するようになり、結果として生成されるコードの品質と実行性能が向上しました。

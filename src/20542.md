# [インデックス 20542] ファイルの概要

このコミットでは、Goランタイムにおける`semacquire`関数の呼び出しが常にG（Goroutine）スタック上で行われるように修正されました。影響を受けたファイルは以下の通りです。

-   `src/runtime/debug.go`: `GOMAXPROCS`関数の実装が変更され、`semacquire`の呼び出しがGoコード内に移動されました。
-   `src/runtime/heapdump.c`: `WriteHeapDump`関連のCコードから`semacquire`の呼び出しが削除されました。
-   `src/runtime/mem.go`: `ReadMemStats`関数と`writeHeapDump`関数のGo実装が追加され、`semacquire`の呼び出しがGoコード内に移動されました。
-   `src/runtime/mgc0.c`: `ReadMemStats`関連のCコードから`semacquire`の呼び出しが削除されました。
-   `src/runtime/proc.c`: スケジューラの構造体定義が変更され、`GOMAXPROCS`のC実装から`semacquire`の呼び出しが削除されました。
-   `src/runtime/runtime.h`: `SchedType`構造体の定義が追加され、ランタイムのグローバル変数宣言が更新されました。
-   `src/runtime/sema.go`: `semacquire`関数に、Gスタック以外からの呼び出しを検出するためのチェックが追加されました。
-   `src/runtime/stubs.go`: `readmemstats_m`と`writeheapdump_m`のスタブが追加されました。
-   `src/runtime/thunk.s`: `runtime/debug.WriteHeapDump`が`runtime·writeHeapDump`にジャンプするように変更されました。

## 変更の背景

このコミットの主な背景は、Goランタイムの`semacquire`関数が、特定の条件下で現在のGoroutine（G）をパーク（一時停止）する必要があるという要件に起因します。`semacquire`はセマフォの取得を試みる関数であり、セマフォが利用できない場合、呼び出し元のGoroutineを待機状態にする必要があります。

問題は、Goroutineをパークする操作が、そのGoroutineのスタック（Gスタック）上でのみ安全に実行できるという制約にありました。Goランタイムには、Goroutineのスタックとは別に、OSスレッド（M）が使用するスタック（Mスタック）が存在します。`semacquire`がMスタックから呼び出された場合、Goroutineのスタック状態を適切に保存する方法がないため、Goroutineをパークすることができませんでした。

以前のGoランタイムでは、`GOMAXPROCS`、`ReadMemStats`、`WriteHeapDump`の3つの関数が、Cコード内で`semacquire`を呼び出していました。これらの呼び出しはMスタック上で行われる可能性があり、まれにではあるものの、`semacquire`がGoroutineをパークしようとした際に問題を引き起こす可能性がありました。この問題は断続的に発生し、デバッグが困難なバグの原因となっていました。

このコミットは、これらの関数における`semacquire`の呼び出しをCコードからGoコードに移動させることで、常にGスタック上から呼び出されるようにし、この潜在的なバグを修正することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスケジューラモデルと、いくつかの重要な概念について理解しておく必要があります。

### Goスケジューラ (G-M-Pモデル)

Goランタイムのスケジューラは、G-M-Pモデルとして知られる3つの主要な要素で構成されています。

1.  **G (Goroutine)**: Goにおける軽量な実行単位です。Goプログラム内で`go`キーワードを使って起動される関数はすべてGoroutineとして実行されます。Goroutineは非常に軽量であり、数百万個を同時に実行することも可能です。それぞれが独自のスタックを持ちます。
2.  **M (Machine/OS Thread)**: オペレーティングシステムのスレッドです。Goランタイムは、Goroutineを実行するためにMを使用します。MはOSによってスケジューリングされる実体であり、CPUコア上で実際にコードを実行します。Mは独自のスタック（Mスタック）を持ちます。
3.  **P (Processor/Logical Processor)**: 論理プロセッサです。PはMとGの間のコンテキストとして機能します。MはPにアタッチされ、Pが持つローカルな実行キューからGoroutineを取得して実行します。Pの数は通常、`GOMAXPROCS`によって設定され、利用可能なCPUコアの数に等しいかそれ以下です。Pは、Goroutineの実行に必要なリソース（スケジューリングキュー、メモリ割り当てキャッシュなど）を提供します。

**G-M-Pの連携**:
-   MはPにアタッチされ、PのローカルキューからGを取得して実行します。
-   Pは、MがGを実行するために必要なコンテキストを提供します。
-   Gがシステムコールなどでブロックされると、MはPからデタッチされ、別のMがそのPにアタッチされて他のGを実行し続けることができます。
-   GがI/O操作などでブロックされると、そのGは待機状態になり、Mは別のGを実行します。I/Oが完了すると、Gは実行可能状態に戻り、Pのキューに入れられます。

### `semacquire`と`semrelease`

`semacquire`と`semrelease`は、Goランタイム内部で使用されるセマフォ操作関数です。

-   **`semacquire(addr *uint32, profile bool)`**: 指定されたアドレス`addr`にあるセマフォを取得しようとします。セマフォが利用できない場合、呼び出し元のGoroutineを待機状態（パーク）にします。これは、複数のGoroutineが共有リソースにアクセスする際の同期メカニズムとして機能します。
-   **`semrelease(addr *uint32)`**: 指定されたアドレス`addr`にあるセマフォを解放します。これにより、待機しているGoroutineがあれば、そのうちの1つが実行可能状態になります。

### `stoptheworld`と`starttheworld`

`stoptheworld`と`starttheworld`は、Goランタイムにおける非常に重要な同期プリミティブです。

-   **`stoptheworld()`**: すべてのGoroutineの実行を一時停止させます。これは、ガベージコレクション（GC）やスケジューラの状態変更など、ランタイム全体にわたる一貫性が必要な操作を実行する際に使用されます。すべてのGoroutineが安全なポイントに到達し、実行が停止するまで待機します。
-   **`starttheworld()`**: `stoptheworld()`によって停止されたGoroutineの実行を再開させます。

これらの関数は、ランタイムの内部状態を安全に変更するために不可欠ですが、アプリケーションの実行を一時的に停止させるため、その使用は最小限に抑える必要があります。

### GスタックとMスタック

Goランタイムでは、Goroutineごとに独自のスタック（Gスタック）が割り当てられます。このスタックは動的にサイズが変更され、必要に応じて拡張または縮小されます。一方、OSスレッド（M）も独自のスタック（Mスタック）を持っています。

-   **Gスタック**: GoroutineのGoコード実行コンテキストを保持します。Go関数呼び出し、ローカル変数などがここに格納されます。Goroutineがパークされる際、このGスタックの状態が保存されます。
-   **Mスタック**: OSスレッドのCコード実行コンテキストを保持します。GoランタイムのC部分（スケジューラ、GCの一部、システムコールラッパーなど）が実行される際に使用されます。Mスタックは固定サイズであり、Goroutineのスタックとは独立しています。

`semacquire`がGoroutineをパークする必要がある場合、そのGoroutineのGスタックの状態を保存する必要があります。Mスタックから`semacquire`が呼び出された場合、現在のMがどのGを実行しているか、そのGのスタックがどこにあるかを正確に特定し、その状態を保存することが困難または不可能になります。そのため、`semacquire`は常にGスタック上から呼び出される必要があるのです。

## 技術的詳細

このコミットの技術的な核心は、`semacquire`がGoroutineをパークする際に、そのGoroutineのスタック状態を正確に保存する必要があるという点にあります。Goランタイムの内部では、Goroutineの実行コンテキストはGスタック上に存在します。MスタックはOSスレッドのコンテキストであり、GoランタイムのC部分が実行される際に使用されます。

`semacquire`がMスタックから呼び出された場合、現在のMがどのGoroutine（G）を実行しているか、そしてそのGのスタックがどこにあるかを特定し、その状態を保存するメカニズムがありません。これは、MスタックがGの実行コンテキストとは直接関連しないためです。結果として、Mスタックから`semacquire`が呼び出され、かつGoroutineをパークする必要が生じた場合、ランタイムはGoroutineの状態を正しく保存できず、クラッシュやデッドロックなどの予測不能な動作を引き起こす可能性がありました。

この問題を解決するため、コミットでは以下の3つの主要な「違反者」である関数、すなわち`GOMAXPROCS`、`ReadMemStats`、`WriteHeapDump`における`semacquire`の呼び出しを修正しました。

1.  **`GOMAXPROCS`**: 以前はCコード（`src/runtime/proc.c`内の`runtime·gomaxprocs_m`）で`semacquire`を呼び出していました。このコミットでは、`src/runtime/debug.go`内のGo実装に`semacquire`の呼び出しを移動させました。これにより、`GOMAXPROCS`が呼び出された際に、`semacquire`は常にGoコード（Gスタック上）から実行されるようになります。`stoptheworld`と`starttheworld`の呼び出しもGoコードに移動され、`newprocs`変数の扱いも変更されました。
2.  **`ReadMemStats`**: 以前はCコード（`src/runtime/mgc0.c`内の`runtime·ReadMemStats`）で`semacquire`を呼び出していました。このコミットでは、`src/runtime/mem.go`内にGo実装の`ReadMemStats`関数が追加され、その中で`semacquire`が呼び出されるようになりました。Cコードからは`semacquire`の呼び出しが削除されました。
3.  **`WriteHeapDump`**: 以前はCコード（`src/runtime/heapdump.c`内の`runtime∕debug·WriteHeapDump`）で`semacquire`を呼び出していました。このコミットでは、`src/runtime/mem.go`内にGo実装の`writeHeapDump`関数が追加され、その中で`semacquire`が呼び出されるようになりました。Cコードからは`semacquire`の呼び出しが削除されました。また、`src/runtime/thunk.s`で`runtime/debug.WriteHeapDump`が新しいGo実装の`runtime·writeHeapDump`にジャンプするように変更されました。

これらの変更により、`semacquire`が必要なGoroutineのパーク操作を行う際に、常にGスタックのコンテキストが利用可能であることが保証されます。これにより、以前は断続的に発生していたバグが修正され、ランタイムの安定性が向上しました。

また、`src/runtime/sema.go`の`semacquire`関数には、デバッグを容易にするためのチェックが追加されました。

```go
func semacquire(addr *uint32, profile bool) {
	gp := getg()
	if gp != gp.m.curg {
		gothrow("semacquire not on the G stack")
	}
	// ...
}
```

このコードは、現在のGoroutine（`gp`）が、現在のM（OSスレッド）が実行しているGoroutine（`gp.m.curg`）と一致しない場合、つまり`semacquire`がGスタック以外のコンテキストから呼び出された場合にパニック（`gothrow`）を引き起こします。これにより、将来的に同様の誤った呼び出しパターンが発生した場合に、早期に問題を検出できるようになります。

## コアとなるコードの解説

このコミットの主要な変更は、`GOMAXPROCS`、`ReadMemStats`、`WriteHeapDump`の3つの関数における`semacquire`の呼び出しを、CコードからGoコードに移行した点に集約されます。

-   **`GOMAXPROCS`の変更 (`src/runtime/debug.go`)**:
    以前の`GOMAXPROCS`は、引数をMスタックに渡し、C関数`gomaxprocs_m`を`onM`（M上で実行）で呼び出すことで処理していました。このC関数内で`semacquire`が呼び出されていました。
    新しい実装では、`GOMAXPROCS`自体がGoコード内で`semacquire`を呼び出し、その後`stoptheworld`と`starttheworld`を`onM`で呼び出しています。これにより、`semacquire`の呼び出しは常にGoroutineのコンテキスト（Gスタック）上で行われることが保証されます。`newprocs`変数は、`starttheworld`が新しいプロセッサ数を処理するために使用するグローバル変数となりました。

-   **`ReadMemStats`と`writeHeapDump`のGo実装 (`src/runtime/mem.go`)**:
    `ReadMemStats`と`WriteHeapDump`（内部的には`writeHeapDump`）も同様に、以前はCコード内で`semacquire`を呼び出していました。このコミットでは、これらの関数に対するGoラッパーが`src/runtime/mem.go`に追加されました。これらのGoラッパーは、まず`semacquire`を呼び出して世界を停止し（`stoptheworld`）、その後C関数（`readmemstats_m`や`writeheapdump_m`）を`onM`で呼び出して実際の処理を実行します。処理が完了したら、世界を再開し（`starttheworld`）、`semrelease`を呼び出します。この構造により、`semacquire`の呼び出しがGoコード（Gスタック）上で行われることが保証されます。

-   **Cコードからの`semacquire`呼び出しの削除 (`src/runtime/heapdump.c`, `src/runtime/mgc0.c`, `src/runtime/proc.c`)**:
    上記のGoコードへの移行に伴い、対応するCコードからは`semacquire`、`stoptheworld`、`semrelease`、`starttheworld`の呼び出しが削除されました。これにより、Mスタック上での`semacquire`の呼び出しがなくなりました。

-   **`semacquire`の安全性チェック (`src/runtime/sema.go`)**:
    `semacquire`関数自体に、`gp != gp.m.curg`というチェックが追加されました。これは、現在のGoroutine（`gp`）が、現在のMが実行しているGoroutine（`gp.m.curg`）と異なる場合にパニックを引き起こすものです。このチェックは、`semacquire`がGスタック以外のコンテキストから誤って呼び出されることを防ぎ、将来的なバグの混入を防ぐための防御的なメカニズムとして機能します。

これらの変更は、Goランタイムのスケジューリングと同期のメカニズムにおける重要な改善であり、特にガベージコレクションやプロセッサ数の変更といったランタイム全体の操作の安定性と信頼性を向上させます。

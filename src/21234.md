# [インデックス 21234] ファイルの概要

このコミットは、Goランタイムにおけるハッシュ関数のパフォーマンス改善を目的としています。具体的には、AES-NI命令セットの`aesenc`命令のレイテンシが高いという特性を考慮し、大きなデータオブジェクトのハッシュ計算において複数のデータストリームを並列に処理することで、ハッシュ処理を高速化しています。

変更された主なファイルは以下の通りです。

-   `src/cmd/8a/lex.c`: アセンブラの字句解析器に関連する変更。新しい命令の追加に対応。
-   `src/cmd/8l/8.out.h`: リンカの出力ヘッダに関連する変更。新しい命令の定義を追加。
-   `src/liblink/asm8.c`: リンカのアセンブリコード生成に関連する変更。新しい命令のサポートを追加。
-   `src/runtime/alg.go`: ランタイムのアルゴリズム定義ファイル。ハッシュ関連の定数に変更。
-   `src/runtime/asm_386.s`: 32ビット(x86)アーキテクチャ向けのアセンブリコード。`aeshashbody`関数の実装が大幅に修正され、並列処理が導入されています。
-   `src/runtime/asm_amd64.s`: 64ビット(x86-64)アーキテクチャ向けのアセンブリコード。`aeshashbody`関数の実装が大幅に修正され、並列処理が導入されています。

## 変更の背景

Go言語のランタイムにおけるハッシュ関数は、マップ（`map`）の実装やその他のデータ構造で広く利用されており、その性能はGoプログラム全体のパフォーマンスに直結します。このコミット以前の`aeshash`の実装では、IntelのAES-NI（Advanced Encryption Standard New Instructions）命令セットに含まれる`AESENC`命令を使用していました。`AESENC`命令は、AES暗号化のラウンド処理をハードウェアレベルで高速化するための命令ですが、その特性として「高いレイテンシ（latency）」を持つことが知られています。

レイテンシとは、ある命令が実行を開始してから結果が利用可能になるまでの時間のことです。`AESENC`命令の場合、このレイテンシが比較的高いため、連続して`AESENC`命令を実行すると、CPUの実行ユニットが結果を待つ間にアイドル状態になり、スループットが低下する可能性があります。特に、大きなデータブロックをハッシュする際には、多数の`AESENC`命令が連続して実行されるため、このレイテンシがボトルネックとなり、ハッシュ計算の全体的な速度が制限されていました。

この問題に対処するため、コミットの作者は、`AESENC`命令のレイテンシを隠蔽し、CPUの実行ユニットをより効率的に利用する方法として、「複数のデータストリームを並列にハッシュする」というアプローチを採用しました。これにより、あるストリームの`AESENC`命令が実行されている間に、別のストリームの処理を進めることができ、全体としてハッシュ計算のスループットを向上させることが可能になります。ベンチマーク結果が示すように、特に大きなデータサイズ（1024バイト以上）のハッシュにおいて、劇的な性能改善が達成されています。

## 前提知識の解説

### Go言語におけるハッシュ関数と`aeshash`

Go言語では、`map`型などの内部実装でハッシュ関数が利用されます。ハッシュ関数は、任意のサイズの入力データ（キー）を受け取り、固定サイズのハッシュ値を出力する関数です。良いハッシュ関数は、異なる入力に対して異なるハッシュ値を生成し、ハッシュ値の衝突（異なる入力が同じハッシュ値になること）を最小限に抑える必要があります。

Goのランタイムでは、特定のアーキテクチャ（Intel/AMDのx86/x86-64など）で利用可能なハードウェア支援命令を活用してハッシュ計算を高速化しています。このコミットで言及されている`aeshash`は、AES-NI命令セットを利用したハッシュアルゴリズムの実装を指します。

### AES-NI (Advanced Encryption Standard New Instructions)

AES-NIは、IntelおよびAMDのプロセッサに搭載されている命令セット拡張で、AES暗号化アルゴリズムの処理をハードウェアレベルで高速化します。これにより、ソフトウェアのみでAESを実装するよりもはるかに高速に暗号化・復号化を行うことができます。AES-NIには、以下のような命令が含まれます。

-   `AESENC`: AES暗号化の1ラウンドを実行します。
-   `AESENCLAST`: AES暗号化の最終ラウンドを実行します。
-   `AESDEC`: AES復号化の1ラウンドを実行します。
-   `AESDECLAST`: AES復号化の最終ラウンドを実行します。
-   `AESIMC`: AESのMixColumns操作の逆を実行します。
-   `AESKEYGENASSIST`: AESラウンドキー生成を支援します。

これらの命令は、128ビットのXMMレジスタ（SSE/AVX命令で使用されるレジスタ）を操作し、データの並列処理を可能にします。

### 命令のレイテンシとスループット

CPUの命令には、それぞれ「レイテンシ」と「スループット」という特性があります。

-   **レイテンシ (Latency)**: 命令が実行を開始してから結果が利用可能になるまでのクロックサイクル数です。レイテンシが高い命令は、結果が出るまでに時間がかかります。
-   **スループット (Throughput)**: ある命令を連続して実行できる頻度です。例えば、スループットが1サイクル/命令であれば、毎サイクル新しい命令を開始できます。スループットが低い（例えば4サイクル/命令）場合、新しい命令を開始するまでに4サイクル待つ必要があります。

`AESENC`命令は、一般的にレイテンシが高い（例えば、Intel Haswellアーキテクチャでは7サイクル）一方で、スループットは比較的高い（例えば、1サイクル/命令）とされています。これは、CPUが`AESENC`命令の実行結果を待っている間に、他の独立した命令を実行できることを意味します。しかし、ハッシュ計算のように`AESENC`命令が連続して依存関係を持つ場合（前の`AESENC`の結果が次の`AESENC`の入力になる場合）、レイテンシがボトルネックとなり、CPUの実行ユニットが十分に活用されない「ストール」が発生しやすくなります。

### SIMD (Single Instruction, Multiple Data)

SIMDは、単一の命令で複数のデータ要素に対して同じ操作を同時に実行する並列処理の形式です。x86アーキテクチャでは、SSE（Streaming SIMD Extensions）やAVX（Advanced Vector Extensions）などの命令セットがSIMDをサポートしており、XMMレジスタ（128ビット）やYMMレジスタ（256ビット）を使用して複数の整数や浮動小数点数を一度に処理できます。

このコミットでは、`AESENC`命令が128ビットのXMMレジスタを操作する特性と、SIMDの概念を組み合わせて、複数のハッシュストリームを並列に処理することで、`AESENC`のレイテンシを隠蔽し、全体のスループットを向上させています。

## 技術的詳細

このコミットの核心は、`AESENC`命令の高いレイテンシを克服するために、複数のハッシュ計算を並列で実行する「パイプライン処理」を導入した点にあります。従来の`aeshashbody`関数は、データを16バイト（128ビット）ずつ処理し、各ブロックのハッシュ計算が前のブロックの結果に依存する形で逐次的に行われていました。この逐次処理では、`AESENC`命令のレイテンシが直接性能に影響を与えていました。

新しい実装では、特に大きなデータサイズ（64バイト以上、AMD64では128バイト以上）のハッシュにおいて、複数のXMMレジスタ（`X0`, `X1`, `X2`, `X3`など）を使用して、同時に複数のデータブロックのハッシュ計算を進めます。これにより、ある`AESENC`命令が実行されている間に、別の`AESENC`命令の入力準備や、別のデータブロックに対する`AESENC`命令の実行を開始することができます。これは、CPUのパイプラインをより深く埋め、実行ユニットのアイドル時間を減らすことで、全体のスループットを向上させる効果があります。

具体的な変更点としては、以下の点が挙げられます。

1.  **並列ストリーム処理**:
    -   32バイト、64バイト、128バイト、そしてそれ以上のサイズのデータに対して、それぞれ異なる並列処理のパスが追加されました。
    -   例えば、64バイト以上のデータの場合、4つのXMMレジスタ（`X0`から`X3`）をハッシュ状態として使用し、それぞれが異なるデータブロックのハッシュ計算を担当します。
    -   ループ内で、新しいデータブロックを読み込み（`MOVOU`）、既存のハッシュ状態とXORし（`PXOR`）、`AESENC`命令を適用します。この際、複数の`AESENC`命令が同時に発行されることで、レイテンシが隠蔽されます。

2.  **データサイズに応じた分岐**:
    -   入力データのサイズ（`CX`レジスタで渡される）に応じて、処理を分岐させるための新しいジャンプ命令（`JB`, `JE`, `JBE`, `JMP`）が追加されました。
    -   `aes0to15`, `aes16`, `aes17to32`, `aes33to64`, `aes65plus` (386) / `aes65to128`, `aes129plus` (amd64) といったラベルが追加され、それぞれのデータサイズに最適化された処理パスが実行されます。

3.  **アセンブリ命令の追加**:
    -   `src/cmd/8a/lex.c`, `src/cmd/8l/8.out.h`, `src/liblink/asm8.c`において、新しいSIMD命令である`PSHUFHW`, `PSHUFL`, `PSHUFLW`のサポートが追加されています。これらの命令は、データのシャッフルや並べ替えに使用され、特に部分的なブロックの処理や、並列処理のためのデータ準備に利用される可能性があります。

4.  **`hashRandomBytes`定数の変更**:
    -   `src/runtime/alg.go`で、`hashRandomBytes`定数が`32`から`ptrSize / 4 * 64`に変更されました。これは、ハッシュキー生成に使用されるランダムバイトのサイズを、ポインタサイズ（32ビットまたは64ビット）に基づいて動的に調整し、より多くのキーを生成できるようにするための変更です。これにより、並列ハッシュ処理で複数のハッシュ状態を初期化するための十分なキーが提供されます。

ベンチマーク結果は、この変更が特に大きなデータサイズ（1024バイト、65536バイト）のハッシュにおいて、70%から80%以上の劇的な性能改善をもたらしたことを明確に示しています。これは、`AESENC`命令のレイテンシを効果的に隠蔽し、CPUの並列処理能力を最大限に引き出した結果と言えます。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、`src/runtime/asm_386.s`と`src/runtime/asm_amd64.s`ファイル内の`runtime·aeshashbody`関数の実装です。特に、データサイズに応じた分岐と、複数のXMMレジスタを使用した並列ハッシュ処理のロジックが追加されています。

	PINSRD	$2, CX, X6	// size to high 64 bits of xmm6

	JE	aes16

	MOVOU	-16(AX)(CX*1), X1

	MOVOU	-64(AX)(CX*1), X0
	MOVOU	-48(AX)(CX*1), X1
	MOVOU	-32(AX)(CX*1), X2
	MOVOU	-16(AX)(CX*1), X3

	AESENC	X6, X0

	AESENC	runtime·aeskeysched+32(SB), X2
	AESENC	runtime·aeskeysched+48(SB), X3

	SHRL	$6, CX

	MOVOU	(AX), X4
	MOVOU	16(AX), X5

	AESENC	X5, X1
	MOVOU	32(AX), X4
	MOVOU	48(AX), X5
	AESENC	X4, X2
	AESENC	X5, X3

	AESENC	X7, X0
	AESENC	X7, X1
	AESENC	X7, X2
	AESENC	X7, X3

	DECL	CX
	JNE	aesloop

	// 2 more scrambles to finish
	AESENC	X7, X0
	AESENC	X7, X1
	AESENC	X7, X2
	AESENC	X7, X3
	AESENC	X7, X0
	AESENC	X7, X1
	AESENC	X7, X2
	AESENC	X7, X3

	PXOR	X3, X1
	PXOR	X1, X0

## コアとなるコードの解説

`runtime·aeshashbody`関数は、Goのハッシュ関数が内部的に呼び出すアセンブリルーチンで、実際のハッシュ計算を行います。この関数は、入力データへのポインタ（`AX`レジスタ）とデータの長さ（`CX`レジスタ）、そしてハッシュのシード値を受け取ります。

変更後のコードは、入力データの長さに基づいて異なる処理パスに分岐します。これは、短いデータと長いデータで最適なハッシュ戦略が異なるためです。

1.  **初期設定と分岐**:
    -   `h+8(FP)` (386) / `h+16(FP)` (amd64) からシード値を`X6`レジスタにロードします。
    -   データの長さ`CX`を`X6`レジスタの別の部分に挿入し、`PSHUFHW`命令でシャッフルして、ハッシュ計算の初期状態の一部として利用します。
    -   `runtime·aeskeysched`（AESキーのスケジュール）を`X7`レジスタにロードします。これは、`AESENC`命令のラウンドキーとして使用されます。
    -   `CMPL`/`CMPQ`命令で`CX`（データの長さ）を様々な定数（16, 32, 64, 128）と比較し、適切な処理パスにジャンプします。

2.  **小サイズデータ（0-15バイト、16バイト）の処理**:
    -   これらのケースでは、並列処理の恩恵が少ないため、比較的単純な逐次処理が行われます。
    -   `MOVOU`でデータをXMMレジスタにロードし、`PAND`や`PSHUFB`で部分的なブロックを適切に処理した後、数回の`AESENC`命令でハッシュを計算します。
    -   `aes0`は、データ長が0の場合にシード値をそのまま返す最適化パスです。

3.  **中サイズデータ（17-32バイト、33-64バイト）の処理**:
    -   これらのサイズでは、2つまたは4つのXMMレジスタ（`X0`, `X1`、または`X0`から`X3`）を使用して、データを並列にロードし、それぞれに対して`AESENC`命令を適用します。
    -   例えば`aes17to32`では、2つの16バイトブロックを`X0`と`X1`にロードし、それぞれを独立してスクランブル（`AESENC`）した後、`PXOR`で結果を結合します。これにより、`AESENC`のレイテンシを部分的に隠蔽します。
    -   `aes33to64`では、4つの16バイトブロックを`X0`から`X3`にロードし、同様に並列処理を行います。

4.  **大サイズデータ（65バイト以上、AMD64では129バイト以上）の処理**:
    -   この部分が最も重要な変更点であり、高い性能改善をもたらしています。
    -   **初期スクランブル**: まず、データの最後の部分（例えば、386では最後の64バイト、AMD64では最後の128バイト）を複数のXMMレジスタにロードし、一度スクランブルします。これは、ループに入る前の初期状態を設定するためです。
    -   **ループ処理 (`aesloop`)**:
        -   ループ内で、データの先頭から64バイト（386）または128バイト（AMD64）のブロックを読み込みます。
        -   これらのブロックを、既存のハッシュ状態を保持するXMMレジスタ（`X0`から`X3`、または`X0`から`X5`, `X8`, `X9`）にXORで結合し、さらに`AESENC`命令を適用します。
        -   この際、複数の`MOVOU`と`AESENC`命令が連続して実行されますが、これらは異なるXMMレジスタを操作するため、CPUはこれらの命令を並列に実行できます。これにより、`AESENC`のレイテンシが効果的に隠蔽され、CPUの実行ユニットが常に忙しい状態を保ちます。
        -   `ADDL`/`ADDQ`でデータポインタ`AX`を進め、`DECL`/`DECQ`で残りのブロック数`CX`を減らし、`JNE`でループを継続します。
    -   **最終スクランブルと結合**: ループが終了した後、残りのハッシュ状態を数回スクランブルし、最終的に`PXOR`命令で全てのハッシュ状態を結合して最終的なハッシュ値を生成します。

この並列処理のアプローチにより、`AESENC`命令のレイテンシがボトルネックとなることなく、CPUのSIMDユニットを最大限に活用して、大規模なデータのハッシュ計算を劇的に高速化することに成功しています。

# [インデックス 26538] ファイルの概要

このコミットは、Go言語の`net/http/httputil`パッケージ内の`ReverseProxy`が、非標準の`Proxy-Connection`ヘッダーもホップバイホップヘッダーとして適切に削除するように修正するものです。これにより、`libcurl`などのクライアントが送信するこのヘッダーが、特にHTTP/2経由でGoogle Frontend (GFE)のようなプロキシによって不正なリクエストとして拒否される問題を解決します。

## 元コミット内容

このコミットは、`net/http/httputil`パッケージの`ReverseProxy`が、HTTPリクエストをバックエンドに転送する際に、`Proxy-Connection`という非標準のホップバイホップヘッダーを削除するように変更します。このヘッダーは`libcurl`によって送信されることがありますが、標準化されていません。特にHTTP/2プロトコルを使用している場合、Google Frontend (GFE)のような一部のプロキシは、このヘッダーを含むリクエストをHTTP 400 Bad Requestとして拒否することが判明しました。この問題を回避するため、`ReverseProxy`がこのヘッダーを明示的に削除するように修正されました。

## 変更の背景

HTTPプロキシは、クライアントとサーバー間の通信を仲介する重要な役割を担っています。この際、HTTPヘッダーには、プロキシが処理すべき情報（ホップバイホップヘッダー）と、最終的なオリジンサーバーに転送すべき情報（エンドツーエンドヘッダー）の2種類があります。

`Proxy-Connection`ヘッダーは、元々Netscape Navigatorによって導入された非標準のヘッダーであり、プロキシとクライアント間の接続管理のために使用されました。しかし、これはHTTP/1.1の標準であるRFC 2616では定義されておらず、代わりに`Connection`ヘッダーが同様の目的で使用されることになっています。

問題は、一部のHTTPクライアントライブラリ（このケースでは`libcurl`）が、非標準であるにもかかわらず`Proxy-Connection`ヘッダーを送信し続けることにありました。さらに、HTTP/2プロトコルでは、`Connection`や`Proxy-Connection`のようなホップバイホップヘッダーは完全に禁止されています。HTTP/2は独自のフレーム層で接続管理を行うため、これらのヘッダーは冗長であり、プロトコル違反と見なされます。

この状況下で、Goの`net/http/httputil.ReverseProxy`がリクエストを処理し、特にHTTP/2経由でGoogle Frontend (GFE)のような厳格なプロキシに転送しようとすると、GFEは`Proxy-Connection`ヘッダーの存在をプロトコル違反とみなし、HTTP 400 Bad Requestエラーを返していました。このコミットは、このような互換性の問題を解決し、`ReverseProxy`がより堅牢に機能するようにするためのものです。

## 前提知識の解説

### HTTPヘッダー

HTTPヘッダーは、HTTPリクエストまたはレスポンスのメタデータを提供するキーと値のペアです。これらは、コンテンツタイプ、認証情報、キャッシュ制御、接続管理など、さまざまな情報を含みます。

### ホップバイホップヘッダー (Hop-by-hop Headers)

ホップバイホップヘッダーは、単一のトランスポート層接続にのみ関連するHTTPヘッダーです。これらはプロキシやゲートウェイによって処理され、次の「ホップ」（次のサーバーまたはクライアント）には転送されません。RFC 2616では、`Connection`ヘッダーによってホップバイホップヘッダーを指定できるとされています。一般的なホップバイホップヘッダーには、`Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade`などがあります。

### `Connection`ヘッダー

HTTP/1.1において、`Connection`ヘッダーは、現在の接続に適用されるホップバイホップヘッダーのリストを指定するために使用されます。例えば、`Connection: close`は、現在のトランザクションが完了した後に接続を閉じることを示します。

### `Proxy-Connection`ヘッダー

`Proxy-Connection`ヘッダーは、Netscapeによって導入された非標準のヘッダーです。その目的は`Connection`ヘッダーと似ていますが、プロキシとクライアント間の接続に特化していました。しかし、HTTP/1.1の標準では採用されず、`Connection`ヘッダーがその役割を担うことになりました。非標準であるため、一部のシステムでは予期しない動作を引き起こす可能性があります。

### HTTP/2

HTTP/2は、HTTP/1.1の後継となるプロトコルで、パフォーマンスの向上を目的としています。多重化、ヘッダー圧縮、サーバープッシュなどの機能が導入されました。HTTP/2の重要な変更点の一つは、ホップバイホップヘッダーの扱い方です。HTTP/2では、`Connection`や`Proxy-Connection`のようなホップバイホップヘッダーはプロトコルレベルで禁止されており、これらが存在するとプロトコル違反と見なされます。これは、HTTP/2が独自のフレーム層で接続管理を行うため、これらのヘッダーが不要になるためです。

### `net/http/httputil.ReverseProxy`

Go言語の標準ライブラリ`net/http/httputil`パッケージに含まれる`ReverseProxy`は、リバースプロキシを実装するための構造体です。クライアントからのリクエストを受け取り、それをバックエンドサーバーに転送し、バックエンドからのレスポンスをクライアントに返す役割を担います。この際、HTTPヘッダーの適切な処理（特にホップバイホップヘッダーの削除）が重要になります。

### `libcurl`

`libcurl`は、様々なプロトコル（HTTP, HTTPS, FTPなど）を使用してデータを転送するためのフリーで使いやすいクライアントサイドURL転送ライブラリです。多くのアプリケーションやシステムでHTTPクライアントとして広く利用されています。

### `Google GFE` (Google Frontend)

Google Frontend (GFE)は、Googleのインフラストラクチャの一部であり、Googleのサービスへのすべてのトラフィックを処理するエッジプロキシです。GFEは、ロードバランシング、DDoS保護、SSL終端、HTTP/2プロトコル変換など、さまざまな機能を提供します。GFEはHTTPプロトコルに厳格であり、プロトコル違反を検出するとリクエストを拒否することがあります。

## 技術的詳細

`net/http/httputil.ReverseProxy`は、リバースプロキシとして機能する際に、クライアントから受け取ったリクエストヘッダーをそのままバックエンドサーバーに転送するのではなく、いくつかの処理を行います。その一つが、ホップバイホップヘッダーの削除です。これは、ホップバイホップヘッダーが現在の接続にのみ関連し、次のホップ（バックエンドサーバー）には転送されるべきではないためです。

このコミット以前の`ReverseProxy`の実装では、標準的なホップバイホップヘッダーのリスト（RFC 2616で定義されているものや、一般的に認識されているもの）に基づいてヘッダーを削除していました。しかし、`Proxy-Connection`ヘッダーは標準リストには含まれていませんでした。

このコミットの変更は、`ReverseProxy`が削除すべきホップバイホップヘッダーのリストである`hopHeaders`スライスに、明示的に`"Proxy-Connection"`を追加することで、この問題を解決します。これにより、`libcurl`が送信する`Proxy-Connection`ヘッダーが、`ReverseProxy`によってバックエンドに転送される前に確実に削除されるようになります。

特にHTTP/2環境では、`Proxy-Connection`のようなホップバイホップヘッダーはプロトコル違反となるため、この削除は非常に重要です。Google GFEのような厳格なHTTP/2プロキシは、これらのヘッダーが存在するリクエストを拒否するため、この修正はGoアプリケーションがGFEを介して通信する際の互換性と信頼性を向上させます。

テストコードの追加も重要です。`TestReverseProxy`関数に、`Proxy-Connection`ヘッダーが設定されたリクエストを送信し、バックエンドハンドラーがそのヘッダーを受け取らないことを確認するアサーションが追加されました。これにより、将来の変更でこの重要な動作が誤って失われることを防ぎます。

## コアとなるコードの解説

### `src/net/http/httputil/reverseproxy.go` の変更

`reverseproxy.go`ファイルでは、`hopHeaders`というグローバルな文字列スライスに`"Proxy-Connection"`が追加されています。

```go
var hopHeaders = []string{
	"Connection",
	"Proxy-Connection", // non-standard but still sent by libcurl and rejected by e.g. google
	"Keep-Alive",
	"Proxy-Authenticate",
	"Proxy-Authorization",
	// ... (他のホップバイホップヘッダー)
}
```

この`hopHeaders`スライスは、`ReverseProxy`がリクエストをバックエンドに転送する前に、どのヘッダーを削除すべきかを決定するために使用されます。`ReverseProxy`の内部ロジックは、このリストに含まれるヘッダーをリクエストから取り除き、エンドツーエンドヘッダーのみをバックエンドに転送します。この変更により、`Proxy-Connection`ヘッダーがこの削除プロセスに含まれるようになり、前述の互換性問題が解決されます。コメントには、このヘッダーが非標準であるにもかかわらず`libcurl`によって送信され、Googleのようなシステムによって拒否されることが明記されており、変更の理由が明確に示されています。

### `src/net/http/httputil/reverseproxy_test.go` の変更

`reverseproxy_test.go`ファイルでは、`TestReverseProxy`関数に新しいテストケースが追加されています。

1.  **バックエンドハンドラーでの検証**:
    ```go
    		if c := r.Header.Get("Proxy-Connection"); c != "" {
    			t.Errorf("handler got Proxy-Connection header value %q", c)
    		}
    ```
    これは、リバースプロキシのバックエンドとして機能するテスト用HTTPハンドラー内で、受信したリクエストヘッダーに`Proxy-Connection`が存在しないことを確認するものです。もし存在すれば、エラーが報告されます。

2.  **リクエストの準備**:
    ```go
    	getReq.Header.Set("Proxy-Connection", "should be deleted")
    ```
    これは、テスト用のHTTPリクエストを作成する際に、意図的に`Proxy-Connection`ヘッダーを設定しています。このヘッダーは、リバースプロキシによって削除されることが期待されます。

これらのテストの追加により、`ReverseProxy`が`Proxy-Connection`ヘッダーを正しく削除するという新しい動作が検証され、将来のコード変更によってこの動作が意図せず変更されることを防ぐための回帰テストとしても機能します。

# [インデックス 24326] ファイルの概要

このコミットは、Goランタイムのプログラムカウンタライン (PCLN) テーブル検証プロセスにおける、外部コード（Foreign Code）との連携に関する問題を修正します。具体的には、任意にアラインされた外部コードの前に存在する可能性のあるパディングバイトに対して`pcvalue`関数が誤って呼び出されるのを防ぎ、ランタイムのメタデータチェック中の不正な動作を回避します。

## 変更の背景

Goプログラムは、`cgo`などのメカニズムを通じて、Cやアセンブリなどの他の言語で書かれた「外部コード（Foreign Code）」と連携することができます。このような外部コードは、Goの標準的なメモリレイアウトやアライメント規則に従わない場合があります。

問題は、GoランタイムがPCLNテーブルの整合性を検証する際に発生しました。具体的には、`moduledataverify1`関数が各Go関数を反復処理し、`pcvalue`関数を呼び出して関連するメタデータ（ファイル名、行番号など）をチェックしていました。Go関数が外部コードの直前に配置されている場合、外部コードは任意のアライメント要件を持つことができ、その結果、Go関数の実行可能コードの終わりと外部コードの開始の間に、可変量のパディングバイトが存在する可能性がありました。

以前の`pcvalue`呼び出しのためのPC値の`end`（終了点）を決定するロジックは、Go関数間のパディングが最大16バイトであると仮定していました。しかし、外部コードのアライメントのためにパディングが16バイトよりも大きくなる場合、`pcvalue`はこれらの無効なパディングバイトを読み取り、解釈しようとしました。これにより、ランタイムの不正な動作やクラッシュが発生する可能性がありました。

このコミットは、`pcvalue`がこれらの無効なメモリ領域に対して呼び出されないようにすることで、この問題を修正します。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するシステムです。スケジューラ、ガベージコレクタ、メモリ管理、スタック管理など、プログラムの低レベルな側面を扱います。
*   **PCLNテーブル (Program Counter Line Table)**: Goバイナリに埋め込まれた重要なメタデータ構造です。プログラムカウンタ (PC) の値（命令のメモリアドレス）を、対応するソースコード情報（ファイル名、行番号、関数名）にマッピングするために使用されます。これは、パニック時のスタックトレース生成、デバッグ、ガベージコレクション、リフレクションなど、さまざまなランタイム機能にとって不可欠です。PCLNテーブルは通常、`_func`構造体を通じて参照されます。
*   **`pcvalue`関数**: PCLNテーブル内で、特定のプログラムカウンタに関連付けられた値を解釈するためのGoランタイム内部関数です。この関数は、PC値に基づいて、ファイル番号、行番号、スタックポインタのオフセットなどの情報を効率的に取得します。
*   **`moduledata`構造体と`ftab`**: Goの実行可能ファイルは、`moduledata`という構造体を通じて、そのモジュールに関するメタデータを保持しています。この構造体には、`ftab`（関数テーブル）が含まれており、これはバイナリ内の各Go関数に関する情報（エントリポイント、PCLNテーブルへのオフセットなど）の配列です。
*   **外部コード (Foreign Code) / `cgo`**: Goプログラムは、`cgo`ツールチェーンを使用して、CやC++などの他の言語で書かれたコードと連携することができます。`cgo`を使用すると、GoコードとCコードが同じプロセス空間で実行され、相互に呼び出しを行うことができます。外部コードはGoのコンパイラやリンカによって生成されたものではないため、Goのランタイムが期待する特定のメタデータ（PCLNテーブルエントリなど）を持たない場合があります。
*   **アライメントとパディング (Alignment and Padding)**: コンピュータのアーキテクチャによっては、メモリ内のデータが特定のバイト境界（例えば4バイト、8バイト、16バイトなど）に配置されていると、より効率的にアクセスできます。これを「アライメント」と呼びます。データ構造がこのアライメント要件を満たすように、コンパイラやリンカは構造体のメンバー間や構造体の最後に未使用のバイトを挿入することがあります。これが「パディング」です。外部コードはGoとは異なるアライメント規則を持つことがあり、これがGoコードと外部コードの境界で予期せぬパディングを引き起こす原因となります。

## 技術的詳細

このコミットは、`src/runtime/symtab.go`内の`moduledataverify1`関数における`end`変数の計算ロジックを変更することで、PCLNテーブルの検証を改善します。

`moduledataverify1`関数は、Goモジュール内の関数テーブル（`ftab`）を反復処理し、各Go関数について`pcvalue`関数を呼び出して、そのPCLNテーブルエントリが有効であることを確認します。`pcvalue`関数は、関数の開始PCから終了PCまでの範囲で動作します。この`end` PCを正確に決定することが重要です。

以前の実装では、`end`は次のように計算されていました。
`end := datap.ftab[i+1].entry - 16`
`if end < datap.ftab[i].entry { end = datap.ftab[i].entry }`
これは、次のGo関数のエントリポイントから16バイトを引くことで、現在のGo関数の有効なPC範囲の終了点を推定していました。この「-16」は、Go関数間の最大パディングが16バイトであるという一般的な仮定に基づいています。しかし、この仮定は、Go関数が外部コードの直前に配置されている場合には破綻します。外部コードは任意のアライメントを持つことができ、その結果、16バイトを超えるパディングが発生する可能性がありました。この場合、`pcvalue`は無効なパディング領域を処理しようとし、ランタイムエラーを引き起こす可能性がありました。

このコミットによる変更は、この問題を解決するために、次の関数エントリが外部コードに対応するかどうかを明示的にチェックします。

変更後のロジックは以下の通りです。
1.  現在の関数`f`のエントリポイントを`end`の初期値として設定します (`end := f.entry`)。
2.  次の関数エントリ`f2`が存在するかどうかを確認します (`if i+1 < nftab`)。
3.  `f2`が存在する場合、`f2.pcln != 0`という条件で、`f2`がGo関数（PCLNテーブルエントリを持つ）であるか、それとも外部オブジェクトチャンク（PCLNテーブルエントリを持たない、`f2.pcln == 0`）であるかを判断します。
    *   **`f2.pcln != 0`の場合（次のエントリがGo関数である場合）**: 以前のロジックと同様に、`end = f2.entry - 16`として`end`を計算します。これは、Go関数間の標準的なパディングの仮定が適用されるためです。また、`end`が現在の関数のエントリポイントよりも小さくならないように、`if end < f.entry { end = f.entry }`というチェックも行われます。
    *   **`f2.pcln == 0`の場合（次のエントリが外部コードである場合）**: この場合、`end`は`f.entry`のまま維持されます。これは、現在のGo関数の有効なPC範囲を、その関数の実際のエントリポイントまでに限定することを意味します。これにより、外部コードの前に存在する可能性のある任意に大きなパディング領域が`pcvalue`によって処理されるのを防ぎます。

この変更により、`pcvalue`関数は常に有効なGoコード領域に対してのみ適用され、未定義のパディング領域を誤って解釈することによるランタイムエラーが防止されます。

## コアとなるコードの変更箇所

変更は`src/runtime/symtab.go`ファイル内の`moduledataverify1`関数に集中しています。

```diff

@@ -134,11 +134,20 @@ func moduledataverify1(datap *moduledata) {

 			// No architecture rounds function entries to more than 16 bytes,
 			// but if one came along we'd need to subtract more here.

-			if end < datap.ftab[i].entry {

+			end := f.entry
+			if i+1 < nftab {
```

## コアとなるコードの解説

変更の核心は、`moduledataverify1`関数内で、`pcvalue`関数に渡す`end`（プログラムカウンタの終了点）を計算する方法にあります。

1.  **変更前**:
    ```go
    end := datap.ftab[i+1].entry - 16
    if end < datap.ftab[i].entry {
        end = datap.ftab[i].entry
    }
    ```
    このコードは、次の関数のエントリポイントから16バイトを引くことで、現在の関数の有効なPC範囲の終了点を推定していました。これは、Go関数間のパディングが最大16バイトであるという仮定に基づいています。`end`が現在の関数の開始点よりも小さくなる場合は、現在の関数の開始点を使用するという安全策も含まれていました。

2.  **変更後**:
    ```go
    f := (*_func)(unsafe.Pointer(&datap.pclntable[datap.ftab[i].funcoff]))
    end := f.entry // 現在の関数のエントリポイントを初期のendとする
    if i+1 < nftab { // 次の関数エントリが存在するか確認
        f2 := (*_func)(unsafe.Pointer(&datap.pclntable[datap.ftab[i+1].funcoff]))
        if f2.pcln != 0 { // 次の関数がGo関数（PCLNテーブルエントリを持つ）の場合
            end = f2.entry - 16 // 以前のロジックを適用
            if end < f.entry {
                end = f.entry
            }
        }
        // else (f2.pcln == 0 の場合、つまり次のエントリが外部コードの場合)
        // end は f.entry のまま維持される。
    }
    ```
    この新しいロジックでは、まず現在の関数`f`のエントリポイントを`end`の初期値として設定します。
    次に、次の関数エントリ`f2`が存在するかどうかを確認します。
    *   もし`f2.pcln`が`0`でなければ、それは通常のGo関数であり、以前のロジック（`f2.entry - 16`）を使用して`end`を計算します。これは、Go関数間のパディングが限定的であるという仮定が依然として有効であるためです。
    *   しかし、もし`f2.pcln`が`0`であれば、それはPCLNテーブルエントリを持たない「外部オブジェクトチャンク」（外部コード）であることを意味します。この場合、`end`は`f.entry`のまま維持されます。これにより、`pcvalue`関数は現在のGo関数の実際のコード領域のみを考慮し、外部コードの前に存在する可能性のある任意に大きなパディング領域を誤って処理するのを防ぎます。

この変更により、Goランタイムは外部コードとの境界において、より堅牢なPCLNテーブルの検証を行うことができるようになります。

# [インデックス 23121] ファイルの概要

このコミットは、Go言語の`crypto/tls`パッケージにおいて、TLSハンドシェイク中にサーバーから提供されるOCSP (Online Certificate Status Protocol) レスポンスを`ConnectionState`構造体に追加する変更です。これにより、`net/http`のようなラッパーを使用している場合でも、OCSPレスポンスにアクセスできるようになります。

## 元コミット内容

このコミットは、Goの`crypto/tls`パッケージにおいて、TLS接続の`ConnectionState`構造体にOCSPレスポンスを格納するための`OCSPResponse`フィールドを追加します。これにより、これまで`Conn`オブジェクトのメソッド経由でしかアクセスできなかったOCSPレスポンスが、`net/http`のような高レベルなラッパーを使用している場合でも、`ConnectionState`を通じて容易に取得できるようになります。

## 変更の背景

Goの`crypto/tls`パッケージは、TLS/SSL通信を扱うための基盤を提供します。TLSハンドシェイク中には、サーバーが自身の証明書の失効状態を示すOCSPレスポンスを「ステープル」（Staple）してクライアントに送信することがあります。これはOCSPステープリングと呼ばれ、クライアントが別途OCSPリスポンダーに問い合わせる手間を省き、パフォーマンスとプライバシーを向上させるための重要なメカニズムです。

しかし、このコミット以前は、Goの`crypto/tls`において、ステープルされたOCSPレスポンスは`tls.Conn`オブジェクトの内部に保持され、`Conn`オブジェクトの特定のメソッドを呼び出すことでしかアクセスできませんでした。`net/http`のような高レベルなパッケージは、内部で`tls.Conn`をラップして使用するため、直接`tls.Conn`オブジェクトにアクセスすることが困難であり、結果としてOCSPレスポンスを取得することができませんでした。

この制限により、`net/http`クライアントを使用するアプリケーションが、サーバーから提供されたOCSPステープル情報を利用して証明書の失効状態を検証したり、その情報をログに記録したりすることが困難でした。`ConnectionState`構造体は、TLS接続に関する多くの重要な情報（TLSバージョン、暗号スイート、証明書チェーンなど）を保持しており、`net/http`のようなラッパーを使用している場合でも通常はアクセス可能です。そのため、OCSPレスポンスをこの`ConnectionState`構造体に追加することで、より広範なアプリケーションからOCSPレスポンスにアクセスできるようにすることが、この変更の背景にあります。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上で安全な通信を行うための暗号化プロトコルです。ウェブブラウザとウェブサーバー間のHTTPS通信などで広く利用されており、データの盗聴、改ざん、なりすましを防ぐ役割を担います。TLSハンドシェイクと呼ばれる初期の通信プロセスを通じて、クライアントとサーバーは互いの身元を確認し、暗号化のための鍵を共有します。

### X.509 証明書

X.509証明書は、公開鍵暗号基盤 (PKI) において、公開鍵の所有者の身元を証明するために使用されるデジタル証明書です。ウェブサイトのSSL/TLS証明書として広く使われており、認証局 (CA) によって発行され、ウェブサイトのドメイン名や組織情報、公開鍵などが含まれています。クライアントは、この証明書を検証することで、接続先のサーバーが正当なものであることを確認します。

### 証明書失効 (Certificate Revocation)

証明書は、有効期限内であっても、秘密鍵の漏洩や誤発行などの理由により、その信頼性が失われることがあります。このような場合、証明書は「失効」され、もはや信頼できないものとして扱われるべきです。クライアントは、接続先のサーバーが提示する証明書が失効していないことを確認する必要があります。

### OCSP (Online Certificate Status Protocol)

OCSPは、X.509証明書の失効状態をリアルタイムで確認するためのプロトコルです。クライアントは、OCSPリスポンダーと呼ばれるサーバーに証明書のシリアル番号を送信し、その証明書が「Good」（有効）、「Revoked」（失効）、「Unknown」（不明）のいずれの状態であるかを示すレスポンスを受け取ります。

### OCSP ステープリング (OCSP Stapling)

従来のOCSPでは、クライアントが証明書の失効状態を確認するために、別途OCSPリスポンダーに接続する必要がありました。これは、追加のネットワークリクエストを発生させ、TLSハンドシェイクの遅延や、クライアントのIPアドレスがOCSPリスポンダーに知られるというプライバシー上の懸念を引き起こす可能性がありました。

OCSPステープリングは、これらの問題を解決するために導入されたメカニズムです。サーバーが自身の証明書に対するOCSPレスポンスを事前にOCSPリスポンダーから取得し、そのレスポンスをTLSハンドシェイクの一部としてクライアントに「ステープル」（添付）して送信します。これにより、クライアントはOCSPリスポンダーに直接問い合わせる必要がなくなり、以下のメリットが得られます。

*   **パフォーマンスの向上**: クライアント側の追加のネットワークリクエストが不要になるため、TLSハンドシェイクが高速化されます。
*   **プライバシーの向上**: クライアントのIPアドレスがOCSPリスポンダーに漏洩するのを防ぎます。
*   **信頼性の向上**: OCSPリスポンダーが一時的に利用できない場合でも、サーバーがキャッシュしたレスポンスを提供できるため、接続の失敗を防ぎやすくなります。

### Goの`crypto/tls`パッケージ

Go言語の標準ライブラリに含まれる`crypto/tls`パッケージは、TLSプロトコルを実装し、安全なネットワーク通信を可能にします。クライアントとサーバーの両方の機能を提供し、証明書の検証、鍵交換、データの暗号化・復号化などを扱います。

### Goの`net/http`パッケージ

`net/http`パッケージは、HTTPクライアントとサーバーを実装するための高レベルなAPIを提供します。HTTPS通信を行う際には、内部的に`crypto/tls`パッケージを利用してTLS接続を確立します。

### `tls.Conn`と`ConnectionState`

`tls.Conn`は、確立されたTLS接続を表すオブジェクトです。このオブジェクトは、TLSハンドシェイクの詳細や、接続の状態に関する情報を含んでいます。
`ConnectionState`は、`tls.Conn`から取得できる構造体で、特定の時点でのTLS接続の状態に関するスナップショットを提供します。これには、TLSバージョン、暗号スイート、サーバー名、ピア証明書チェーンなどが含まれます。この構造体は、接続の確立後に、その詳細を検査するために利用されます。

## 技術的詳細

このコミットの技術的な核心は、`crypto/tls`パッケージの`ConnectionState`構造体に`OCSPResponse []byte`フィールドを追加したことです。これにより、TLSハンドシェイク中にサーバーからステープルされたOCSPレスポンスが、この構造体を通じて利用可能になります。

具体的には、以下のようになります。

1.  **`ConnectionState`構造体の拡張**: `src/crypto/tls/common.go`ファイルにおいて、`ConnectionState`構造体に`OCSPResponse []byte`という新しいフィールドが追加されます。このフィールドは、サーバーから提供されたOCSPレスポンスのバイト列を保持します。コメントには「stapled OCSP response from server, if any」（サーバーからのステープルされたOCSPレスポンス、もしあれば）と明記されています。

2.  **OCSPレスポンスの格納**: `src/crypto/tls/conn.go`ファイルにおいて、`Conn`オブジェクトの`ConnectionState()`メソッドが呼び出された際に、内部で保持している`c.ocspResponse`（これはTLSハンドシェイク中に受信したOCSPレスポンス）が、新しく追加された`state.OCSPResponse`フィールドにコピーされます。

この変更により、`net/http`のような高レベルなクライアントを使用している場合でも、`http.Client`が確立したTLS接続の`ConnectionState`を取得することで、ステープルされたOCSPレスポンスにアクセスできるようになります。

**重要な注意点**: Goの標準ライブラリは、クライアントがステープルされたOCSPレスポンスを*抽出*することを可能にしますが、*自動的にそのレスポンスを検証して証明書の失効状態をチェックするわけではありません*。アプリケーション開発者は、`ConnectionState`から`OCSPResponse`を取得した後、`golang.org/x/crypto/ocsp`のようなパッケージを使用してOCSPレスポンスを解析し、その署名を検証し、失効状態（Good, Revoked, Unknown）を確認するロジックを明示的に実装する必要があります。検証の結果に基づいて、接続を続行するかどうかを判断する必要があります。

サーバー側でOCSPステープリングを有効にするには、`tls.Config`の`GetCertificate`フィールドを設定し、`tls.Certificate`に事前に取得したOCSPレスポンスを`OCSPStaple`フィールドに含める必要があります。Goの標準ライブラリは、サーバーのためにOCSPレスポンスの取得とステープリングを自動的に行う機能は提供していません。

## コアとなるコードの解説

### `src/crypto/tls/common.go`の変更

```go
type ConnectionState struct {
	PeerCertificates            []*x509.Certificate   // certificate chain presented by remote peer
	VerifiedChains              [][]*x509.Certificate // verified chains built from PeerCertificates
	SignedCertificateTimestamps [][]byte              // SCTs from the server, if any
	OCSPResponse                []byte                // stapled OCSP response from server, if any

	// TLSUnique contains the "tls-unique" channel binding value (see RFC
	// 5929, section 3). For resumed sessions this value will be nil
}
```

この変更は、`ConnectionState`構造体に`OCSPResponse`という新しいフィールドを追加しています。このフィールドは`[]byte`型であり、サーバーからステープルされたOCSPレスポンスの生データをバイトスライスとして保持します。これにより、`ConnectionState`を通じてOCSPレスポンスに直接アクセスするための「入れ物」が用意されました。

### `src/crypto/tls/conn.go`の変更

```go
func (c *Conn) ConnectionState() ConnectionState {
	state := ConnectionState{
		// ... 既存のフィールドのコピー ...
		state.VerifiedChains = c.verifiedChains
		state.ServerName = c.serverName
		state.SignedCertificateTimestamps = c.scts
		state.OCSPResponse = c.ocspResponse // 追加された行
		if !c.didResume {
			state.TLSUnique = c.firstFinished[:]
		}
		// ...
	}
	return state
}
```

この変更は、`tls.Conn`型のレシーバーを持つ`ConnectionState()`メソッド内で行われています。このメソッドは、現在のTLS接続の状態を表す`ConnectionState`構造体を返します。追加された行`state.OCSPResponse = c.ocspResponse`は、`Conn`オブジェクトの内部フィールドである`c.ocspResponse`（これはTLSハンドシェイク中にサーバーから受信したOCSPレスポンスを保持している）の値を、新しく作成される`ConnectionState`構造体の`OCSPResponse`フィールドにコピーしています。

これにより、`tls.Conn`の`ConnectionState()`メソッドを呼び出すことで、OCSPレスポンスが`ConnectionState`構造体の一部として返されるようになり、`net/http`のような高レベルなラッパーを使用している場合でも、この情報にアクセスすることが可能になります。

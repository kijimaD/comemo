## 変更の背景

このコミットの主な背景は、Goコンパイラの内部データ構造である `NodeList` を、より現代的で効率的な `Node` スライス（Goのスライス型 `[]*Node`）に置き換えるという、将来的な大規模なリファクタリングの準備にあります。

変更前のコードでは、文字列連結操作（`OADDSTR`）の定数評価において、`NodeList`（リンクリストとして実装されていた）の構造を直接変更していました。具体的には、隣接する定数文字列をマージする際に、リンクリストのノードを削除したり、ポインタを付け替えたりする操作を行っていました。

しかし、このようなリンクリストの直接操作は、将来的に `NodeList` がスライスに置き換えられた際に、コードの変更が困難になるか、あるいは大幅な書き直しが必要になる可能性がありました。このコミットは、一時的に効率を犠牲にしてでも、リンクリストの構造を直接変更するロジックを排除し、`NodeList` の内部実装の詳細に依存しない形にすることで、将来のスライスへの移行を容易にすることを目的としています。

コミットメッセージにある「The new code is a bit less efficient, but it does not involve altering the structure of any linked lists. This will make it easier to replace NodeLists with Node slices.」という記述が、この背景を明確に示しています。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Goコンパイラは、Go言語で書かれたソースコードを、コンピュータが直接実行できる機械語のバイナリに変換するプログラムです。Goの標準配布物に含まれる `cmd/compile` がこれに該当します。コンパイルプロセスは通常、以下の主要なフェーズで構成されます。

1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（キーワード、識別子、演算子など）のストリームに分解します。
2.  **構文解析 (Syntactic Analysis)**: トークンのストリームを解析し、言語の文法規則に従ってAST（抽象構文木）を構築します。
3.  **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、名前解決、定数評価などの意味的な検証と変換を行います。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTを、より低レベルで機械独立な中間表現（IR）に変換します。
5.  **最適化 (Optimization)**: 中間コードを分析し、より効率的なコードに変換します。定数畳み込み（constant folding）などもここで行われます。
6.  **コード生成 (Code Generation)**: 最適化された中間コードをターゲットアーキテクチャの機械語に変換します。

### `gc`パッケージ

`gc` は、Goコンパイラのバックエンド部分を構成する主要なパッケージです。`cmd/compile/internal/gc` に位置し、ASTの操作、型チェック、定数評価、最適化、中間コード生成など、コンパイルの中核的な処理の多くを担っています。Goコンパイラの歴史的な経緯から、`gc` という名前は「Go Compiler」の略であるとされています。

### AST (`Abstract Syntax Tree`)

AST（抽象構文木）は、ソースコードの構造を抽象的な木構造で表現したものです。コンパイラは、ソースコードを直接操作するのではなく、このASTを操作することで、プログラムの意味を理解し、様々な変換や最適化を行います。ASTの各ノードは、プログラムの構成要素（変数宣言、関数呼び出し、演算子、リテラルなど）を表します。

### `Node`と`NodeList`

*   **`Node`**: GoコンパイラにおけるASTの基本的な構成要素を表す構造体です。例えば、整数リテラル、変数、関数呼び出し、二項演算子（`+`, `-`など）などがそれぞれ `Node` オブジェクトとして表現されます。`Node` には、その種類（`Op`）、型情報（`Type`）、値（`Val`）、子ノードへのポインタなどが含まれます。
*   **`NodeList`**: 複数の `Node` を順序付けて保持するためのデータ構造です。このコミットの時点では、`NodeList` はリンクリストとして実装されていました。リンクリストは、要素がメモリ上で連続していなくても、各要素が次の要素へのポインタを持つことで順序を表現するデータ構造です。しかし、Goのスライスはメモリ上で連続した要素を効率的に扱うことができ、多くのGoのコードベースで好まれるため、コンパイラも `NodeList` をスライスに移行する計画がありました。

### `evconst`関数

`evconst` 関数は、Goコンパイラの意味解析フェーズの一部として、AST内の定数式を評価する役割を担います。例えば、`const x = 1 + 2` のようなコードがあった場合、`evconst` は `1 + 2` をコンパイル時に計算し、結果の `3` を `x` の値としてASTに埋め込みます。これにより、実行時に `1 + 2` の計算を行う必要がなくなり、プログラムの実行効率が向上します。

### `OADDSTR`

`OADDSTR` は、GoコンパイラのASTノードの種類（`Op`）の一つで、文字列の連結操作を表します。Go言語では `+` 演算子を使って文字列を連結できます（例: `"hello" + " " + "world"`）。`evconst` 関数は、この `OADDSTR` ノードを処理する際に、もし連結される文字列がすべて定数であれば、それらをコンパイル時に結合して一つの新しい定数文字列に変換する最適化を行います。

## 技術的詳細

このコミットは、`evconst` 関数内で `OADDSTR`（文字列連結）ノードを処理する際のロジックを大きく変更しています。変更の核心は、`NodeList` のリンクリストとしての詳細な構造を直接操作するのをやめ、より抽象的な方法でリストを再構築することにあります。

### 変更前のロジック

変更前のコードでは、`OADDSTR` ノードの引数リスト（`n.List`）をリンクリストとして直接走査し、隣接する定数文字列を見つけると、その場でリンクリストの構造を変更してマージしていました。

1.  `l1 := n.List` からリストを走査開始。
2.  `l1.N` と `l1.Next.N` の両方が定数文字列であるかをチェック。
3.  もし両方が定数文字列であれば、`l1` から始まる連続する定数文字列のシーケンスを特定。
4.  これらの文字列を抽出し、`strings.Join` で結合して新しい単一の定数文字列ノードを作成。
5.  元の `l1.N` をこの新しい結合文字列ノードで置き換え。
6.  `l1.Next` を、結合された文字列のシーケンスの終端の次のノードに直接付け替えることで、中間ノードをリンクリストから削除。

この方法は、リンクリストの構造を直接操作するため、効率的ではありましたが、`NodeList` が将来的にスライスに置き換えられる際に、この部分のコードも大幅に修正する必要がありました。

### 変更後のロジック

変更後のコードでは、元の `n.List` を直接変更するのではなく、新しい `NodeList` を一から構築するアプローチを採用しています。これにより、リンクリストの内部構造に依存しない、より抽象的な処理が可能になります。

1.  新しい空の `NodeList` である `l` を宣言。これが最終的に `n.List` を置き換えるリストになります。
2.  元の `n.List` を `l1` で走査。
3.  各ノード `l1.N` について、以下のいずれかの処理を行います。
    *   **定数文字列でない、または単独の定数文字列の場合**:
        *   `!Isconst(l1.N, CTSTR)`（定数文字列ではない）
        *   `l1.Next == nil`（リストの末尾で、次にノードがない）
        *   `!Isconst(l1.Next.N, CTSTR)`（次のノードが定数文字列ではない）
        これらの条件のいずれかに合致する場合、現在のノード `l1.N` は他の定数文字列とマージできないか、マージする必要がないため、そのまま新しいリスト `l` に追加されます。
        `l = list(l, l1.N)` で `l1.N` を `l` に追加し、`l1 = l1.Next` で次のノードに進みます。
    *   **連続する定数文字列の開始ノードの場合**:
        現在のノード `l1.N` と次のノード `l1.Next.N` の両方が定数文字列である場合、連続する定数文字列のシーケンスが始まります。
        1.  `first := l1.N` で、この連続シーケンスの最初のノードを保存します。これは、新しい結合ノードのプロパティ（型など）をコピーするために使用されます。
        2.  `var strs []string` を宣言し、連続する定数文字列を一時的に格納します。
        3.  `for ; l1 != nil && Isconst(l1.N, CTSTR); l1 = l1.Next` ループで、連続する定数文字列をすべて `strs` スライスに収集します。このループが終わると、`l1` は連続シーケンスの次のノード（または `nil`）を指しています。
        4.  `nl := Nod(OXXX, nil, nil)` で新しいASTノードを作成します。
        5.  `*nl = *first` で、`first` ノードの情報を新しいノード `nl` にコピーします。
        6.  `nl.Orig = nl` で `Orig` フィールドを設定します。
        7.  `nl.SetVal(Val{strings.Join(strs, "")})` で、収集した文字列を `strings.Join` で結合し、その結果を新しいノード `nl` の値として設定します。
        8.  `l = list(l, nl)` で、この新しい結合文字列ノード `nl` を新しいリスト `l` に追加します。
4.  すべてのノードの処理が完了したら、`n.List = l` で、元の `n.List` を新しく構築した `l` で置き換えます。

この変更により、リンクリストのポインタ操作が不要になり、`NodeList` の内部実装がリンクリストからスライスに変わっても、この `evconst` 関数のロジックはほとんど変更せずに済むようになります。ただし、リストのコピーと再構築が発生するため、一時的にパフォーマンスが低下する可能性があります。コミットメッセージはこのトレードオフを認識しており、「We can return to a more efficient algorithm when NodeLists have been replaced.」と述べています。

## コアとなるコードの解説

変更後の `case OADDSTR:` ブロックのコードを詳細に解説します。

```go
		// TODO: We make a copy of n.List in order to abstract
		// away the details of deleting elements.
		// Once n.List is some kind of Node slice,
		// re-implement using deletion.
		var l *NodeList // replacement list
		for l1 := n.List; l1 != nil; {
			if !Isconst(l1.N, CTSTR) || l1.Next == nil || !Isconst(l1.Next.N, CTSTR) {
				// non-constant string or solitary constant string
				l = list(l, l1.N)
				l1 = l1.Next
				continue
			}

			first := l1.N

			// merge run of constants
			var strs []string
			for ; l1 != nil && Isconst(l1.N, CTSTR); l1 = l1.Next {
				strs = append(strs, l1.N.Val().U.(string))
			}

			nl := Nod(OXXX, nil, nil)
			*nl = *first
			nl.Orig = nl
			nl.SetVal(Val{strings.Join(strs, "")})
			l = list(l, nl)
		}
		n.List = l
```

1.  **`// TODO: ...` コメント**:
    このコメントは、この変更が一時的なものであることを明確に示しています。`NodeList` の要素削除の詳細を抽象化するために、`n.List` のコピーを作成していること、そして `NodeList` が `Node` スライスになったら、より効率的な削除ロジックで再実装できることを述べています。これは、将来的なリファクタリングへの準備という変更の背景を裏付けています。

2.  **`var l *NodeList // replacement list`**:
    新しい `NodeList` のヘッドを宣言しています。この `l` が、最終的に文字列連結の定数評価が適用された後の新しい引数リストとなります。

3.  **`for l1 := n.List; l1 != nil; { ... }`**:
    元の `n.List` を `l1` ポインタを使って走査するループです。`l1` の更新はループ本体内で行われるため、`l1 = l1.Next` はループヘッダにはありません。

4.  **`if !Isconst(l1.N, CTSTR) || l1.Next == nil || !Isconst(l1.Next.N, CTSTR) { ... }`**:
    この条件分岐は、現在のノード `l1.N` が他の定数文字列とマージする必要があるかどうかを判断します。
    *   `!Isconst(l1.N, CTSTR)`: `l1.N` が定数文字列ではない場合。
    *   `l1.Next == nil`: `l1` がリストの最後のノードであり、次にノードがない場合（単独の定数文字列）。
    *   `!Isconst(l1.Next.N, CTSTR)`: `l1.N` の次のノード `l1.Next.N` が定数文字列ではない場合。
    これらのいずれかの条件が真であれば、現在のノード `l1.N` は単独で処理されるべきノード（非定数文字列、またはマージする隣接定数がない定数文字列）です。

5.  **`l = list(l, l1.N)`**:
    上記の `if` 条件が真の場合、現在のノード `l1.N` を新しいリスト `l` に追加します。`list` 関数は、既存の `NodeList` に新しい `Node` を追加するヘルパー関数です。

6.  **`l1 = l1.Next`**:
    `if` 条件が真の場合、`l1` を次のノードに進めます。

7.  **`continue`**:
    `if` 条件が真の場合、現在のループの残りの処理をスキップし、次のイテレーションに進みます。

8.  **`first := l1.N`**:
    `if` 条件が偽の場合（つまり、`l1.N` と `l1.Next.N` の両方が定数文字列であり、連続する定数文字列のシーケンスが始まる場合）、`l1.N` を `first` 変数に保存します。これは、結合後の新しいノードのプロパティ（例えば、元のノードの型情報など）をコピーするために使用されます。

9.  **`var strs []string`**:
    連続する定数文字列を一時的に格納するためのGoのスライスを宣言します。

10. **`for ; l1 != nil && Isconst(l1.N, CTSTR); l1 = l1.Next { ... }`**:
    この内部ループは、`l1` から始まる連続するすべての定数文字列を収集します。
    *   `l1 != nil`: リストの終端に達していないことを確認。
    *   `Isconst(l1.N, CTSTR)`: 現在のノード `l1.N` が定数文字列であることを確認。
    *   `strs = append(strs, l1.N.Val().U.(string))`: `l1.N` の値（文字列）を `strs` スライスに追加します。`Val().U.(string)` は、ノードの値から基となる文字列を抽出する操作です。
    このループが終わると、`strs` には連続するすべての定数文字列が格納され、`l1` はその連続シーケンスの次のノード（または `nil`）を指しています。

11. **`nl := Nod(OXXX, nil, nil)`**:
    新しいASTノード `nl` を作成します。`OXXX` は、ノードの種類がまだ設定されていないことを示すプレースホルダーです。

12. **`*nl = *first`**:
    `first` ノード（連続シーケンスの最初のノード）のすべてのフィールドを、新しく作成した `nl` ノードにコピーします。これにより、型情報などの重要なプロパティが保持されます。

13. **`nl.Orig = nl`**:
    ノードの `Orig` フィールドは、元のノードへの参照を保持することがありますが、ここでは新しいノード自身を指すように設定されています。

14. **`nl.SetVal(Val{strings.Join(strs, "")})`**:
    `strings.Join(strs, "")` を使って、`strs` スライスに収集されたすべての文字列を空文字列を区切り文字として結合します。その結果の文字列を、新しいノード `nl` の値として設定します。これにより、複数の定数文字列が単一の定数文字列ノードに畳み込まれます。

15. **`l = list(l, nl)`**:
    結合された新しい定数文字列ノード `nl` を、新しいリスト `l` に追加します。

16. **`n.List = l`**:
    `for` ループが完了した後、元の `n.List` を、新しく構築された `l` で置き換えます。これにより、`OADDSTR` ノードの引数リストが、定数文字列がマージされた状態に更新されます。

この変更は、リンクリストの直接操作を避けることで、将来の `NodeList` からスライスへの移行を容易にするための戦略的なステップであり、Goコンパイラの進化における重要な一歩と言えます。

# [インデックス 26402] ファイルの概要

このコミットでは、Goコンパイラの内部パッケージである `src/cmd/compile/internal/gc/parser.go` と、その修正を検証するための新しいテストファイル `test/fixedbugs/issue14006.go` が変更されています。

## コミット

このコミットは、Goコンパイラが不正なラベル付きステートメントに遭遇した際にクラッシュするバグ（Issue #14006）を修正します。具体的には、`parser.go` 内の `simple_stmt` 関数において、ラベルとしてシンボルが期待される箇所でシンボルが `nil` である場合にパニックが発生しないよう、安全なチェックが追加されました。

## 変更の背景

Go言語のコンパイラ `cmd/compile` は、ソースコードを解析し、実行可能なバイナリに変換する役割を担っています。このプロセスにおいて、構文解析（パース）は非常に重要なフェーズです。Issue #14006は、特定の不正なラベル付きステートメントがGoコンパイラに与えられた際に、コンパイラがパニックを起こしてクラッシュするというバグを報告していました。

具体的には、`switch` ステートメントの `case` 節内で、数値リテラルや文字列リテラルをラベルとして使用しようとした場合に問題が発生していました。Go言語の仕様では、ラベルは識別子である必要があり、リテラルを直接ラベルとして使用することはできません。しかし、コンパイラのパーサーがこの不正な構文を処理する際に、内部で期待されるシンボル情報が `nil` となり、その後の処理で `nil` ポインタ参照が発生し、コンパイラがクラッシュしていました。

このコミットは、このような不正な入力に対してもコンパイラがクラッシュするのではなく、適切なコンパイルエラーを報告するように修正することを目的としています。これにより、コンパイラの堅牢性が向上し、開発者にとってより分かりやすいエラーメッセージが提供されるようになります。

## 前提知識の解説

### Go言語のラベルとステートメント

Go言語では、`goto`、`break`、`continue` ステートメントと組み合わせてラベルを使用することができます。ラベルは識別子であり、特定のステートメントの前に置かれ、そのステートメントをマークします。

*   **`goto` ステートメント**: プログラムの実行フローを、指定されたラベルを持つステートメントにジャンプさせます。
    ```go
    func myFunc() {
        i := 0
    Loop:
        for i < 10 {
            if i == 5 {
                goto End
            }
            i++
        }
    End:
        fmt.Println("End of myFunc")
    }
    ```
*   **`break` および `continue` ステートメント**: ループや `switch`、`select` ステートメントを制御します。ラベルを付けることで、ネストされたループの外側のループを `break` したり `continue` したりすることができます。
    ```go
    OuterLoop:
        for i := 0; i < 5; i++ {
            for j := 0; j < 5; j++ {
                if i*j > 6 {
                    break OuterLoop // 外側のループを抜ける
                }
                fmt.Println(i, j)
            }
        }
    ```

重要なのは、Go言語の仕様において、ラベルは**識別子**でなければならないという点です。数値リテラルや文字列リテラルは識別子ではありません。

### Goコンパイラ (`cmd/compile`) の役割

`cmd/compile` はGo言語の公式コンパイラであり、Goソースコードを機械語に変換します。その内部は複数のフェーズに分かれています。

1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（キーワード、識別子、リテラル、演算子など）のストリームに変換します。
2.  **構文解析 (Syntactic Analysis / Parsing)**: トークンのストリームを解析し、Go言語の文法規則に従って抽象構文木 (AST: Abstract Syntax Tree) を構築します。このフェーズで構文エラーが検出されます。
3.  **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、名前解決、スコープチェックなどの意味的な検証を行います。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTを、より低レベルな中間表現（SSA形式など）に変換します。
5.  **最適化 (Optimization)**: 中間コードを最適化し、実行効率を向上させます。
6.  **コード生成 (Code Generation)**: 最適化された中間コードをターゲットアーキテクチャの機械語に変換します。

このコミットで変更された `src/cmd/compile/internal/gc/parser.go` は、主に構文解析フェーズを担当する部分です。`parser` 構造体とそのメソッドは、Goの文法規則に従ってソースコードを解析し、ASTノードを生成します。

### `Node` と `Sym`

Goコンパイラの内部では、ソースコードの各要素は `Node` 構造体として表現されます。`Node` はASTの各ノードに対応し、その種類（`Op` フィールド）、値、型、位置などの情報を含みます。
`Sym` (Symbol) は、識別子（変数名、関数名、型名など）に関連付けられた情報を保持する構造体です。コンパイラは、識別子を解決し、その属性（スコープ、型など）を `Sym` オブジェクトに格納します。

不正なラベル付きステートメントの場合、パーサーがリテラルをラベルとして解釈しようとすると、そのリテラルに対応する `Sym` オブジェクトが適切に生成されないか、`nil` になる可能性があります。これが、今回のクラッシュの原因となっていました。

## 技術的詳細

この修正は、`src/cmd/compile/internal/gc/parser.go` 内の `(*parser).simple_stmt` メソッドにあります。このメソッドは、Go言語の「単純なステートメント」（例: 宣言、代入、式、ラベル付きステートメントなど）を解析する役割を担っています。

問題が発生していたのは、`labelOk` が `true` の場合、つまりラベルが許可されているコンテキストで、パーサーが `lhs` (left-hand side) をラベルとして解釈しようとする部分です。

元のコードでは、`lhs.Op` が `ONAME`, `ONONAME`, `OTYPE`, `OPACK`, `OLITERAL` のいずれかである場合に、`lhs = newname(lhs.Sym)` を呼び出して新しい名前ノードを作成していました。ここで問題となるのは `OLITERAL` のケースです。リテラル（例: `2` や `"bar"`）がラベルとして現れた場合、`lhs.Op` は `OLITERAL` となりますが、その `lhs.Sym` フィールドは `nil` である可能性があります。`newname` 関数は `nil` の `Sym` を受け取るとパニックを起こす可能性がありました。

修正では、`lhs.Op` がこれらのいずれかである場合に、さらに `if lhs.Sym != nil` というチェックが追加されました。
これにより、`lhs.Sym` が `nil` でない場合にのみ `newname(lhs.Sym)` が呼び出されるようになります。もし `lhs.Sym` が `nil` であれば、`fallthrough` を使って `default` ケースに処理が移り、`p.syntax_error("expecting semicolon or newline or }")` という適切な構文エラーが報告されるようになります。

この変更により、コンパイラは不正なラベル（リテラルなど）を検出した際にクラッシュする代わりに、明確なエラーメッセージを出力して処理を続行できるようになります。

`test/fixedbugs/issue14006.go` は、この修正を検証するためのテストケースです。
*   `switch x { case 1: 2: // ERROR "unexpected :" }` のように、`case` 節内で数値リテラルをラベルとして使用するケース。
*   `switch y { case "foo": "bar": // ERROR "unexpected :" }` のように、`case` 節内で文字列リテラルをラベルとして使用するケース。
*   `switch { case z: labelname: // ERROR "missing statement after label" }` のように、有効なラベル名の後にステートメントがないケース。

これらのテストケースは、修正後のコンパイラが期待通りにエラーを報告することを確認します。

## コアとなるコードの解説

変更は `parser.go` の `(*parser).simple_stmt` メソッド内にあります。

1.  `if labelOk { ... }`: このブロックは、現在のコンテキストでラベルが許可されている場合に実行されます。
2.  `// If we have a labelname, it was parsed by operand ...`: コメントは、`operand` 関数によって解析された `lhs` が、`ONAME` (名前), `ONONAME` (未解決の名前), `OTYPE` (型), `OPACK` (パッケージ), `OLITERAL` (リテラル) のいずれかのノードタイプを持つことを説明しています。
3.  `// We only have a labelname if there is a symbol (was issue 14006).`: 新しく追加されたコメントで、今回の修正の核心を説明しています。ラベル名として有効なのはシンボルが存在する場合のみであり、これがIssue #14006の原因であったことを示唆しています。
4.  `switch lhs.Op { ... }`: `lhs` の操作タイプに基づいて処理を分岐します。
5.  `case ONAME, ONONAME, OTYPE, OPACK, OLITERAL:`: これらのケースは、`lhs` が識別子またはリテラルである可能性のある状況を扱います。
6.  `-				lhs = newname(lhs.Sym)`: 修正前のコードでは、`lhs.Sym` が `nil` である可能性を考慮せずに `newname` を呼び出していました。`OLITERAL` の場合、`lhs.Sym` は `nil` になり得ます。
7.  `+				if lhs.Sym != nil {`: ここが主要な変更点です。`lhs.Sym` が `nil` でないことを明示的にチェックします。
8.  `+					lhs = newname(lhs.Sym)`: `lhs.Sym` が有効な場合にのみ、`newname` を呼び出して新しい名前ノードを作成します。
9.  `+					break`: `newname` が成功した場合、`switch` ステートメントを抜けます。
10. `+				}`: `if` ブロックの終わり。
11. `+				fallthrough`: `lhs.Sym` が `nil` であった場合（つまり、不正なリテラルがラベルとして使われた場合）、`fallthrough` キーワードによって次の `default` ケースに処理が移ります。
12. `default:`: `lhs.Op` が上記のどのケースにも一致しない場合、または `fallthrough` によって到達した場合に実行されます。
13. `p.syntax_error("expecting semicolon or newline or }")`: ここで、適切な構文エラーメッセージが報告されます。これにより、コンパイラはクラッシュすることなく、不正な構文をユーザーに通知できます。

この変更により、Goコンパイラは不正なラベル付きステートメント（特にリテラルがラベルとして使用された場合）に対してより堅牢になり、開発者に対してより有用なエラーメッセージを提供するようになりました。

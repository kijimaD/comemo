    Previously, nilopt was disabled on power64x because it threw
    away "seemly random segments of code."  Indeed, excise on
    power64x failed to preserve the link field, so it excised not
    only the requested instruction but all following instructions
    in the function.  Fix excise to retain the link field while
    otherwise zeroing the instruction.

    This makes nilopt safe on power64x.  It still fails
    nilptr3.go's tests for removal of repeated nil checks because
    those depend on also optimizing away repeated loads, which
    doesn't currently happen on power64x.

## 変更の背景

このコミットは、Goコンパイラの`nilopt`（nilチェックの最適化）がPowerPC 64-bit (power64x) アーキテクチャで正しく機能しない問題を修正することを目的としています。以前、`nilopt`はpower64x上で「ランダムなコードセグメントを破棄する」という問題があったため、無効化されていました。この問題は、コンパイラの`excise`関数が命令を削除する際に、命令の「リンクフィールド」を保持しなかったことに起因します。その結果、`excise`は対象の命令だけでなく、関数内の後続のすべての命令を削除してしまい、コンパイラの生成するコードが誤動作する原因となっていました。

このコミットの目的は、`excise`関数が命令をゼロクリアする際にリンクフィールドを保持するように修正し、power64x上での`nilopt`の安全性を確保することです。これにより、power64xでも冗長なnilチェックを最適化できるようになります。ただし、コミットメッセージにもあるように、`nilptr3.go`のテストで期待される「繰り返されるnilチェックの削除」は、power64xでは繰り返されるロードの最適化に依存しており、これはまだ実装されていないため、完全には成功しないことが示されています。

## 前提知識の解説

*   **Goコンパイラ (9g):** `9g`は、Go言語の初期のコンパイラ群の一部で、特に386アーキテクチャをターゲットとしていました。Goコンパイラは元々C言語で書かれており、`9g`はそのC言語ベースのツールチェーンの一部でした。Go 1.5以降、コンパイラはGo言語自体で書き直され（セルフホスト化）、`9g`のような特定のアーキテクチャ名を冠したコンパイラは使われなくなりました。
*   **nilopt (nilチェック最適化):** Go言語では、ポインタが`nil`でないことを保証するために、コードの様々な場所でnilチェックが行われます。`nilopt`は、これらのnilチェックが冗長である場合に、コンパイラがそれらを削除することで生成されるコードの効率を向上させる最適化の一種です。例えば、あるポインタが一度nilでないと確認された後、そのポインタが変更されない限り、後続のnilチェックは不要になります。
*   **Peephole Optimization (ピーフホール最適化):** コンパイラ最適化の一種で、生成された機械語コードの小さな「窓」（ピーフホール）を覗き込み、非効率な命令シーケンスをより効率的なものに置き換える手法です。`peep.c`ファイルはこの最適化を担当するコンポーネントでした。
*   **`excise`関数:** コンパイラのバックエンドにおいて、特定の命令をコードストリームから削除または無効化する役割を持つ関数です。このコミットでは、`excise`が命令を削除する際に、その命令が持つ次の命令への「リンク」を誤って破棄していたことが問題でした。
*   **PowerPC 64-bit (power64x):** IBMが開発したPowerPCアーキテクチャの64ビット版です。Go言語は様々なアーキテクチャをサポートしており、power64xもその一つです。特定のアーキテクチャでは、コンパイラの最適化が異なる振る舞いをすることがあり、本コミットの対象となっています。
*   **リンクフィールド (link field):** コンパイラが生成する命令列において、各命令が次の命令へのポインタ（またはオフセット）を持つことがあります。これを「リンクフィールド」と呼びます。このリンクフィールドが正しく保持されないと、命令列の連続性が失われ、コードの実行フローが破壊されます。

## 技術的詳細

このコミットの核心は、GoコンパイラのC言語実装における`peep.c`内の`excise`関数の修正です。

**問題点:**
power64xアーキテクチャにおいて、`nilopt`が有効な場合、`excise`関数が命令を削除する際に、その命令の`link`フィールド（次の命令へのポインタ）をゼロクリアしてしまっていました。これにより、削除対象の命令だけでなく、その命令に続くすべての命令が論理的に切断され、関数全体が「ランダムなコードセグメントを破棄する」かのように見えていました。これは、コンパイラが生成するアセンブリコードの構造を破壊し、実行時エラーや不正な動作を引き起こす原因となっていました。

**修正内容:**
`src/cmd/9g/peep.c`の`excise`関数が修正され、命令をゼロクリアする前に、元の命令の`link`フィールドを一時変数`l`に保存し、ゼロクリア後にその`link`フィールドを`p->link = l;`として復元するように変更されました。これにより、命令自体はゼロクリアされて無効化されますが、命令リストの連結性は維持され、後続の命令が誤って削除されることがなくなりました。

**`src/cmd/gc/popt.c`の変更:**
`src/cmd/gc/popt.c`からは、power64xでの`nilopt`を無効化していた以下のコードが削除されました。
```c
// TODO(minux): nilopt on power64 throw away seemly random segment of code.
if(thechar == '9')
    return;
```
このコードは、`thechar == '9'`（`9`はpower64xを指す内部的な文字コード）の場合に`nilopt`関数から早期リターンすることで、power64xでの`nilopt`を無効化していました。`peep.c`の`excise`関数の修正により、この無効化が不要になったため、削除されました。

**残された課題:**
コミットメッセージにも記載されているように、この修正によってpower64xでの`nilopt`は安全になりましたが、`nilptr3.go`のテストで期待される「繰り返されるnilチェックの削除」はまだ完全ではありません。これは、その最適化が「繰り返されるロードの最適化」に依存しており、それがpower64xではまだ実装されていないためです。これは、nilチェックがメモリからの値のロードと密接に関連している場合に、ロード自体の冗長性を排除しないと、nilチェックの冗長性も完全には排除できないことを示唆しています。

## コアとなるコードの解説

### `src/cmd/9g/peep.c` の `excise` 関数

*   **変更前:**
    ```c
    void
    excise(Flow *r)
    {
        Prog *p;
        // ...
        *p = zprog; // 命令をゼロクリア
        p->as = ANOP; // 命令タイプをANOP (No Operation) に設定
        // linkフィールドはここでゼロクリアされるか、不定になる
        // ...
    }
    ```
    `*p = zprog;` は、`Prog`構造体全体をゼロクリアする操作です。これにより、命令のオペコードやオペランドだけでなく、次の命令へのポインタである`link`フィールドもゼロクリアされていました。結果として、命令リストの連結が失われ、後続の命令が到達不能になっていました。

*   **変更後:**
    ```c
    void
    excise(Flow *r)
    {
        Prog *p, *l; // l を追加
        // ...
        l = p->link; // ゼロクリアする前に、現在の命令のlinkフィールドを保存
        *p = zprog;  // 命令をゼロクリア
        p->as = ANOP; // 命令タイプをANOPに設定
        p->link = l; // 保存しておいたlinkフィールドを復元
        // ...
    }
    ```
    この修正では、`Prog *l;`という一時変数が追加されました。`*p = zprog;`を実行する直前に、`p->link`の値を`l`に保存します。`*p = zprog;`によって`p`が指す`Prog`構造体全体がゼロクリアされた後、保存しておいた`l`の値を`p->link`に再代入することで、命令リストの連結性を維持します。これにより、`excise`された命令は実質的に無効化されますが、その命令がリスト内で占めていた位置は保持され、後続の命令へのリンクは損なわれません。

### `src/cmd/gc/popt.c` の `nilopt` 関数

*   **変更前:**
    ```c
    void
    nilopt(Prog *firstp)
    {
        // ...
        // TODO(minux): nilopt on power64 throw away seemly random segment of code.
        if(thechar == '9') // power64xの場合
            return; // niloptを無効化
        // ...
    }
    ```
    このコードは、`thechar`というコンパイラ内部の変数（ターゲットアーキテクチャを示す）が`'9'`（power64xを示す）である場合に、`nilopt`関数から即座にリターンすることで、power64xアーキテクチャでのnilチェック最適化を完全に無効化していました。これは、前述の`excise`関数のバグによるコード破壊を防ぐための暫定的な措置でした。

*   **変更後:**
    ```c
    void
    nilopt(Prog *firstp)
    {
        // ...
        // 上記のif文が削除された
        // ...
    }
    ```
    `peep.c`の`excise`関数のバグが修正され、power64xでの`nilopt`が安全になったため、この無効化ロジックは不要となり、削除されました。これにより、power64xでも`nilopt`が実行されるようになります。

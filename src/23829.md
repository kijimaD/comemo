# [インデックス 23829] ファイルの概要

このコミットは、Goランタイムのスタック縮小処理（`shrinkstack`関数）における潜在的なバグを修正するものです。具体的には、スタックを縮小する際に、スタックガード領域が適切に考慮されていなかったため、特定の条件下で`nosplit`関数がスタックオーバーフローを引き起こす可能性があった問題に対処しています。

## コミット

```
commit 7387121ddb43e20c3d4c01cea548ddbcdc1d3945
Author: Austin Clements <austin@google.com>
Date:   Thu Jun 4 17:28:02 2015 -0400

    runtime: account for stack guard when shrinking the stack
    
    Currently, when shrinkstack computes whether the halved stack
    allocation will have enough room for the stack, it accounts for the
    stack space that's actively in use but fails to leave extra room for
    the stack guard space. As a result, *if* the minimum stack size is
    small enough or the guard large enough, it may shrink the stack and
    leave less than enough room to run nosplit functions. If the next
    function called after the stack shrink is a nosplit function, it may
    overflow the stack without noticing and overwrite non-stack memory.
    
    We don't think this is happening under normal conditions right now.
    The minimum stack allocation is 2K and the guard is 640 bytes. The
    "worst case" stack shrink is from 4K (4048 bytes after stack barrier
    array reservation) to 2K (2016 bytes after stack barrier array
    reservation), which means the largest "used" size that will qualify
    for shrinking is 4048/4 - 8 = 1004 bytes. After copying, that leaves
    2016 - 1004 = 1012 bytes of available stack, which is significantly
    more than the guard space.
    
    If we were to reduce the minimum stack size to 1K or raise the guard
    space above 1012 bytes, the logic in shrinkstack would no longer leave
    enough space.
    
    It's also possible to trigger this problem by setting
    firstStackBarrierOffset to 0, which puts stack barriers in a debug
    mode that steals away *half* of the stack for the stack barrier array
    reservation. Then, the largest "used" size that qualifies for
    shrinking is (4096/2)/4 - 8 = 504 bytes. After copying, that leaves
    (2096/2) - 504 = 8 bytes of available stack; much less than the
    required guard space. This causes failures like those in issue #11027
    because func gc() shrinks its own stack and then immediately calls
    casgstatus (a nosplit function), which overflows the stack and
    overwrites a free list pointer in the neighboring span. However, since
    this seems to require the special debug mode, we don't think it's
    responsible for issue #11027.
    
    To forestall all of these subtle issues, this commit modifies
    shrinkstack to correctly account for the guard space when considering
    whether to halve the stack allocation.

## 変更の背景

Goランタイムは、ゴルーチンのスタックサイズを動的に管理します。必要に応じてスタックを拡張（growstack）したり、使用量が少ない場合に縮小（shrinkstack）したりすることで、メモリ効率を高めています。

このコミットが修正しようとしている問題は、スタック縮小処理である`shrinkstack`関数が、スタックの実際の使用量を見積もる際に、スタックガード領域を適切に考慮していなかった点にあります。スタックガードは、スタックオーバーフローを検出するための特別な領域であり、また、スタックチェックを行わない`nosplit`関数が安全に実行できるだけの十分なスペースを確保する役割も持っています。

`shrinkstack`は、スタックの使用量が現在のスタック割り当ての1/4未満である場合にスタックを半分に縮小することを検討します。しかし、この「使用量」の計算にスタックガード領域が含まれていなかったため、以下のようなシナリオで問題が発生する可能性がありました。

1.  **最小スタックサイズが小さい、またはスタックガードが大きい場合**: 通常の条件下では、Goの最小スタック割り当て（2KB）とスタックガードサイズ（640バイト）の組み合わせでは問題は顕在化していませんでした。しかし、もし最小スタックサイズが1KBに減らされたり、スタックガードが1012バイト以上に増やされたりした場合、`shrinkstack`はスタックを縮小した後に`nosplit`関数が実行できる十分なスペースを残さない可能性がありました。
2.  **デバッグモードでのスタックバリア使用時**: `firstStackBarrierOffset`を0に設定するデバッグモードでは、スタックバリア配列のためにスタックの半分が予約されます。この極端な条件下では、`shrinkstack`がスタックを縮小した後に、`nosplit`関数が実行できるスペースがわずか8バイトしか残らないという状況が発生し、スタックオーバーフローが実際に引き起こされていました（issue #11027に関連する失敗）。

このような状況で`nosplit`関数が呼び出されると、スタックチェックが行われないため、スタックオーバーフローが検出されずに隣接するメモリ領域を上書きし、ランタイムのクラッシュやデータの破損につながる可能性がありました。このコミットは、これらの潜在的かつデバッグモードで顕在化した問題を未然に防ぐために導入されました。

## 前提知識の解説

### Goランタイムのスタック管理

Goのゴルーチンは、可変サイズのスタックを使用します。これは、C言語などの固定サイズスタックとは異なり、必要に応じてスタックが自動的に拡張（grow）および縮小（shrink）されることを意味します。
*   **スタック拡張 (Stack Growth)**: 関数呼び出し時にスタックが不足しそうになると、ランタイムはより大きなスタックを割り当て、既存のスタックの内容を新しいスタックにコピーし、ポインタを更新します。
*   **スタック縮小 (Stack Shrinkage)**: ゴルーチンが大量のスタックを使用した後に、その使用量が大幅に減少した場合、ランタイムはメモリ効率のためにスタックを縮小することがあります。これが`shrinkstack`関数の役割です。

### `shrinkstack`関数

`shrinkstack`は、ゴルーチンのスタック使用量が現在の割り当ての一定割合（通常は1/4）を下回った場合に、スタックのサイズを半分に縮小する処理を行います。これにより、不要なメモリの占有を防ぎ、システム全体のメモリ使用量を最適化します。

### スタックガード (Stack Guard)

Goランタイムは、各ゴルーチンのスタックの末尾に「スタックガード」と呼ばれる特別な領域を設けています。この領域は、スタックオーバーフローを検出するために使用されます。関数が呼び出される際、プロローグでスタックポインタがスタックガード領域に侵入しようとしているかをチェックします。もし侵入しそうであれば、スタック拡張処理がトリガーされます。

### `nosplit`関数

Goランタイムには、`//go:nosplit`ディレクティブでマークされた関数が存在します。これらの関数は、スタックチェックを行いません。これは、ランタイムの非常に低レベルな部分（例えば、スタック拡張/縮小処理自体や、スケジューラ、メモリ管理の一部）で使われることが多く、スタックチェックのオーバーヘッドを避けるため、あるいはスタックチェック自体が不可能な状況（スタックが壊れている可能性のある状況）で実行されるためです。`nosplit`関数はスタックチェックを行わないため、呼び出し前に十分なスタックスペースが確保されていることが極めて重要です。スタックガード領域は、これらの関数が安全に実行できるための「バッファ」としての役割も果たします。

### `_FixedStack`と`_StackLimit`

*   `_FixedStack`: Goランタイムがゴルーチンに割り当てる最小のスタックサイズを定義する定数です。このコミットの時点では2KBでした。
*   `_StackLimit`: スタックガードのサイズ、またはスタックガードがスタックのどの位置にあるかを示すオフセットに関連する定数です。このコミットの時点では640バイトでした。

### スタックバリア (Stack Barrier)

スタックバリアは、Goランタイムのデバッグ機能の一つで、スタックの不正なアクセスを検出するために使用されます。特定のデバッグモードでは、スタックの一部をスタックバリア配列として予約し、スタックの健全性を監視します。このコミットで言及されている`firstStackBarrierOffset`を0に設定するケースは、このデバッグモードを有効にした際の挙動に関するものです。

## 技術的詳細

このコミットの核心的な問題は、`shrinkstack`関数がスタックを縮小するかどうかを決定する際の「使用済みスタックサイズ」の計算方法にありました。

変更前の`shrinkstack`関数では、スタックの使用量を`used := gp.stack.hi - gp.sched.sp`として計算していました。ここで、`gp.stack.hi`はスタックの上限アドレス（高位アドレス）、`gp.sched.sp`は現在のスタックポインタです。この計算は、純粋に現在スタックフレームが占有しているメモリ量を示しますが、`nosplit`関数が安全に実行するために必要なスタックガード領域を考慮していませんでした。

`nosplit`関数はスタックチェックを行わないため、スタックガード領域がスタックの末尾に存在し、かつ十分な大きさであることが前提となります。`shrinkstack`がスタックガードを考慮せずにスタックを縮小してしまうと、縮小後のスタックの空き領域がスタックガードのサイズを下回り、次に`nosplit`関数が呼び出された際にスタックオーバーフローが発生する危険性がありました。

コミットメッセージでは、この問題が通常の条件下では顕在化しにくい理由を説明しています。
*   最小スタック割り当てが2KB、スタックガードが640バイトの場合、4KBから2KBへのスタック縮小を例にとると、最大で1004バイトが使用済みと判断され、縮小後には1012バイトの空きが残ります。これは640バイトのスタックガードよりも十分大きい値です。

しかし、以下のシナリオでは問題が顕在化します。
*   **最小スタックサイズが1KBに減少、またはスタックガードが1012バイト以上に増加した場合**：この場合、縮小後の空き領域がスタックガードを下回る可能性があります。
*   **`firstStackBarrierOffset`が0に設定されたデバッグモード**：このモードでは、スタックの半分がスタックバリア配列に予約されます。この条件下で4KBから2KBへの縮小を考えると、最大で504バイトが使用済みと判断され、縮小後にはわずか8バイトしか空きが残りません。これは必要なスタックガード領域（640バイト）を大幅に下回るため、`gc()`関数が自身のスタックを縮小した直後に`casgstatus`（`nosplit`関数）を呼び出すと、スタックオーバーフローが発生し、隣接するメモリ（フリーリストポインタ）を上書きする問題が確認されました（issue #11027）。

このコミットは、これらの微妙な問題を未然に防ぐために、`shrinkstack`がスタック割り当てを半分にするかどうかを検討する際に、スタックガード領域を正しく考慮するように修正しています。

## コアとなるコードの解説

### `copystack`関数の変更

`copystack`関数内のデバッグ出力の`print`文が変更されています。
変更前: `old.hi-old.lo`
変更後: `gp.stackAlloc`
これは、スタックの元のサイズを表示する際に、`old.hi-old.lo`（スタックの物理的な範囲）ではなく、`gp.stackAlloc`（ゴルーチンに割り当てられたスタックの論理的なサイズ）を使用するように修正されたものです。これは主要なロジックの変更ではなく、デバッグ情報の表示の正確性を向上させるためのものです。

### `shrinkstack`関数の主要な変更

`shrinkstack`関数内のスタック使用量を計算するロジックが変更されました。

変更前:
```go
	used := gp.stack.hi - gp.sched.sp
	if used >= oldsize/4 {
		return // still using at least 1/4 of the segment.
	}
```

変更後:
```go
	// Compute how much of the stack is currently in use and only
	// shrink the stack if gp is using less than a quarter of its
	// current stack. The currently used stack includes everything
	// down to the SP plus the stack guard space that ensures
	// there's room for nosplit functions.
	avail := gp.stack.hi - gp.stack.lo
	if used := gp.stack.hi - gp.sched.sp + _StackLimit; used >= avail/4 {
		return
	}
```

この変更のポイントは以下の通りです。

1.  **`used`の計算に`_StackLimit`を追加**:
    変更前は`used := gp.stack.hi - gp.sched.sp`でしたが、変更後は`used := gp.stack.hi - gp.sched.sp + _StackLimit`となりました。
    これは、スタックの「使用量」を計算する際に、現在のスタックポインタ（`gp.sched.sp`）からスタックの上限（`gp.stack.hi`）までの実際の使用量に加えて、`_StackLimit`（スタックガード領域のサイズ）を合算するようにしたものです。これにより、`shrinkstack`はスタックガード領域も「使用中」のスペースとして考慮するようになり、スタック縮小後も`nosplit`関数が安全に実行できるだけの十分なスペースが確保されるようになります。

2.  **`avail`変数の導入**:
    `avail := gp.stack.hi - gp.stack.lo`が追加されました。これは、現在のスタック割り当ての合計サイズ（物理的なスタックの範囲）を明確にするためのものです。

3.  **条件式の変更**:
    変更前は`used >= oldsize/4`でしたが、変更後は`used >= avail/4`となりました。
    `oldsize`は`gp.stackAlloc`と同じ意味合いですが、`avail`を使うことで、より明確に現在のスタックセグメントの物理的なサイズに対する割合で判断するようになっています。この条件式は、「スタックの使用量が現在のスタック割り当ての1/4以上であれば、スタックを縮小しない」というロジックを維持しつつ、`used`の計算に`_StackLimit`が加わったことで、より保守的に（つまり、より多くのスペースが使用中と見なされ、縮小されにくく）なりました。これにより、スタックガード領域を考慮した上で、安全なスタック縮小の判断が行われるようになります。

この修正により、`shrinkstack`はスタックガード領域を適切に考慮するようになり、最小スタックサイズやスタックガードの変更、あるいはデバッグモードの使用といった特定の条件下でも、`nosplit`関数がスタックオーバーフローを引き起こすリスクが排除されました。

2.  **デバッグモードでのスタックバリア使用時**: `firstStackBarrierOffset`を0に設定するデバッグモードでは、スタックバリア配列のためにスタックの半分が予約されます。この極端な条件下では、`shrinkstack`がスタックを縮小した後に、`nosplit`関数が実行できるスペースがわずか8バイトしか残らないという状況が発生し、スタックオーバーフローが実際に引き起こされていました（issue #11027に関連する失敗）。

このような状況で`nosplit`関数が呼び出されると、スタックチェックが行われないため、スタックオーバーフローが検出されずに隣接するメモリ領域を上書きし、ランタイムのクラッシュやデータの破損につながる可能性がありました。このコミットは、これらの潜在的かつデバッグモードで顕在化した問題を未然に防ぐために導入されました。

## 前提知識の解説

### Goランタイムのスタック管理

Goのゴルーチンは、可変サイズのスタックを使用します。これは、C言語などの固定サイズスタックとは異なり、必要に応じてスタックが自動的に拡張（grow）および縮小（shrink）されることを意味します。
*   **スタック拡張 (Stack Growth)**: 関数呼び出し時にスタックが不足しそうになると、ランタイムはより大きなスタックを割り当て、既存のスタックの内容を新しいスタックにコピーし、ポインタを更新します。
*   **スタック縮小 (Stack Shrinkage)**: ゴルーチンが大量のスタックを使用した後に、その使用量が大幅に減少した場合、ランタイムはメモリ効率のためにスタックを縮小することがあります。これが`shrinkstack`関数の役割です。

### `shrinkstack`関数

`shrinkstack`は、ゴルーチンのスタック使用量が現在の割り当ての一定割合（通常は1/4）を下回った場合に、スタックのサイズを半分に縮小する処理を行います。これにより、不要なメモリの占有を防ぎ、システム全体のメモリ使用量を最適化します。

### スタックガード (Stack Guard)

Goランタイムは、各ゴルーチンのスタックの末尾に「スタックガード」と呼ばれる特別な領域を設けています。この領域は、スタックオーバーフローを検出するために使用されます。関数が呼び出される際、プロローグでスタックポインタがスタックガード領域に侵入しようとしているかをチェックします。もし侵入しそうであれば、スタック拡張処理がトリガーされます。

### `nosplit`関数

Goランタイムには、`//go:nosplit`ディレクティブでマークされた関数が存在します。これらの関数は、スタックチェックを行いません。これは、ランタイムの非常に低レベルな部分（例えば、スタック拡張/縮小処理自体や、スケジューラ、メモリ管理の一部）で使われることが多く、スタックチェックのオーバーヘッドを避けるため、あるいはスタックチェック自体が不可能な状況（スタックが壊れている可能性のある状況）で実行されるためです。`nosplit`関数はスタックチェックを行わないため、呼び出し前に十分なスタックスペースが確保されていることが極めて重要です。スタックガード領域は、これらの関数が安全に実行できるための「バッファ」としての役割も果たします。

### `_FixedStack`と`_StackLimit`

*   `_FixedStack`: Goランタイムがゴルーチンに割り当てる最小のスタックサイズを定義する定数です。このコミットの時点では2KBでした。
*   `_StackLimit`: スタックガードのサイズ、またはスタックガードがスタックのどの位置にあるかを示すオフセットに関連する定数です。このコミットの時点では640バイトでした。

### スタックバリア (Stack Barrier)

スタックバリアは、Goランタイムのデバッグ機能の一つで、スタックの不正なアクセスを検出するために使用されます。特定のデバッグモードでは、スタックの一部をスタックバリア配列として予約し、スタックの健全性を監視します。このコミットで言及されている`firstStackBarrierOffset`を0に設定するケースは、このデバッグモードを有効にした際の挙動に関するものです。

## 技術的詳細

このコミットの核心的な問題は、`shrinkstack`関数がスタックを縮小するかどうかを決定する際の「使用済みスタックサイズ」の計算方法にありました。

変更前の`shrinkstack`関数では、スタックの使用量を`used := gp.stack.hi - gp.sched.sp`として計算していました。ここで、`gp.stack.hi`はスタックの上限アドレス（高位アドレス）、`gp.sched.sp`は現在のスタックポインタです。この計算は、純粋に現在スタックフレームが占有しているメモリ量を示しますが、`nosplit`関数が安全に実行するために必要なスタックガード領域を考慮していませんでした。

`nosplit`関数はスタックチェックを行わないため、スタックガード領域がスタックの末尾に存在し、かつ十分な大きさであることが前提となります。`shrinkstack`がスタックガードを考慮せずにスタックを縮小してしまうと、縮小後のスタックの空き領域がスタックガードのサイズを下回り、次に`nosplit`関数が呼び出された際にスタックオーバーフローが発生する危険性がありました。

コミットメッセージでは、この問題が通常の条件下では顕在化しにくい理由を説明しています。
*   最小スタック割り当てが2KB、スタックガードが640バイトの場合、4KBから2KBへのスタック縮小を例にとると、最大で1004バイトが使用済みと判断され、縮小後には1012バイトの空きが残ります。これは640バイトのスタックガードよりも十分大きい値です。

しかし、以下のシナリオでは問題が顕在化します。
*   **最小スタックサイズが1KBに減少、またはスタックガードが1012バイト以上に増加した場合**：この場合、縮小後の空き領域がスタックガードを下回る可能性があります。
*   **`firstStackBarrierOffset`が0に設定されたデバッグモード**：このモードでは、スタックの半分がスタックバリア配列に予約されます。この条件下で4KBから2KBへの縮小を考えると、最大で504バイトが使用済みと判断され、縮小後にはわずか8バイトしか空きが残りません。これは必要なスタックガード領域（640バイト）を大幅に下回るため、`gc()`関数が自身のスタックを縮小した直後に`casgstatus`（`nosplit`関数）を呼び出すと、スタックオーバーフローが発生し、隣接するメモリ（フリーリストポインタ）を上書きする問題が確認されました（issue #11027）。

このコミットは、これらの微妙な問題を未然に防ぐために、`shrinkstack`がスタック割り当てを半分にするかどうかを検討する際に、スタックガード領域を正しく考慮するように修正しています。

## コアとなるコードの解説

### `copystack`関数の変更

`copystack`関数内のデバッグ出力の`print`文が変更されています。
変更前: `old.hi-old.lo`
変更後: `gp.stackAlloc`
これは、スタックの元のサイズを表示する際に、`old.hi-old.lo`（スタックの物理的な範囲）ではなく、`gp.stackAlloc`（ゴルーチンに割り当てられたスタックの論理的なサイズ）を使用するように修正されたものです。これは主要なロジックの変更ではなく、デバッグ情報の表示の正確性を向上させるためのものです。

### `shrinkstack`関数の主要な変更

`shrinkstack`関数内のスタック使用量を計算するロジックが変更されました。

変更前:
```go
	used := gp.stack.hi - gp.sched.sp
	if used >= oldsize/4 {
		return // still using at least 1/4 of the segment.
	}
```

変更後:
```go
	// Compute how much of the stack is currently in use and only
	// shrink the stack if gp is using less than a quarter of its
	// current stack. The currently used stack includes everything
	// down to the SP plus the stack guard space that ensures
	// there's room for nosplit functions.
	avail := gp.stack.hi - gp.stack.lo
	if used := gp.stack.hi - gp.sched.sp + _StackLimit; used >= avail/4 {
		return
	}
```

この変更のポイントは以下の通りです。

1.  **`used`の計算に`_StackLimit`を追加**:
    変更前は`used := gp.stack.hi - gp.sched.sp`でしたが、変更後は`used := gp.stack.hi - gp.sched.sp + _StackLimit`となりました。
    これは、スタックの「使用量」を計算する際に、現在のスタックポインタ（`gp.sched.sp`）からスタックの上限（`gp.stack.hi`）までの実際の使用量に加えて、`_StackLimit`（スタックガード領域のサイズ）を合算するようにしたものです。これにより、`shrinkstack`はスタックガード領域も「使用中」のスペースとして考慮するようになり、スタック縮小後も`nosplit`関数が安全に実行できるだけの十分なスペースが確保されるようになります。

2.  **`avail`変数の導入**:
    `avail := gp.stack.hi - gp.stack.lo`が追加されました。これは、現在のスタック割り当ての合計サイズ（物理的なスタックの範囲）を明確にするためのものです。

3.  **条件式の変更**:
    変更前は`used >= oldsize/4`でしたが、変更後は`used >= avail/4`となりました。
    `oldsize`は`gp.stackAlloc`と同じ意味合いですが、`avail`を使うことで、より明確に現在のスタックセグメントの物理的なサイズに対する割合で判断するようになっています。この条件式は、「スタックの使用量が現在のスタック割り当ての1/4以上であれば、スタックを縮小しない」というロジックを維持しつつ、`used`の計算に`_StackLimit`が加わったことで、より保守的に（つまり、より多くのスペースが使用中と見なされ、縮小されにくく）なりました。これにより、スタックガード領域を考慮した上で、安全なスタック縮小の判断が行われるようになります。

この修正により、`shrinkstack`はスタックガード領域を適切に考慮するようになり、最小スタックサイズやスタックガードの変更、あるいはデバッグモードの使用といった特定の条件下でも、`nosplit`関数がスタックオーバーフローを引き起こすリスクが排除されました。

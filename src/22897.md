## 変更の背景

この変更の背景には、Go言語のメモリモデルの進化と明確化があります。以前は、チャネル操作がメモリの可視性（あるゴルーチンが行ったメモリへの書き込みが別のゴルーチンから見えるようになること）にどのように影響するかについて、開発者の間で誤解や不明瞭な点が存在していました。特に、チャネルを同期プリミティブとして使用する際に、それがメモリの保護や順序付けにどのように寄与するのかが曖昧な場合がありました。

削除されたコメントは、`threadLimit`チャネルへの送信が「メモリを保護するためではない」と明示的に述べていました。これは、チャネルが同期だけでなく、メモリの可視性も保証するというGoメモリモデルの特定の側面に対する、当時の開発者の懸念や理解不足を反映していた可能性があります。

しかし、Goのメモリモデルがより詳細に定義され、特にチャネル操作が「happens-before」関係を確立することが明確になったことで、チャネルを介した同期が自動的にメモリの可視性も保証することが広く理解されるようになりました。この明確化により、`threadLimit`チャネルへの送信が、単にゴルーチンの数を制限するだけでなく、その操作自体がメモリモデルの規則に則って安全であることが自明となり、以前のコメントが不要になったため削除されました。

## 前提知識の解説

### Goのメモリモデル (Go Memory Model)

Goのメモリモデルは、複数のゴルーチンが共有メモリにアクセスする際の動作を定義します。これは、並行プログラムにおけるデータ競合を防ぎ、予測可能な動作を保証するために不可欠です。Goのメモリモデルの核心は「happens-before」関係です。

*   **happens-before**: あるイベントAが別のイベントBよりも前に発生するという関係です。もしAがBよりも前に発生するならば、Aによって行われたメモリへの書き込みは、Bによって観測可能であることが保証されます。happens-before関係は推移的です（A happens-before B かつ B happens-before C ならば、A happens-before C）。

Goのメモリモデルにおいて、チャネル操作はhappens-before関係を確立する主要な手段の一つです。

*   **チャネル送信と受信**:
    *   チャネル`c`への送信操作`c <- x`は、同じチャネル`c`からの受信操作`<- c`よりも前に発生します。
    *   チャネル`c`への送信操作が完了する前に、そのゴルーチンによって行われたメモリへの書き込みは、そのチャネルからの受信操作が完了した後に、受信側のゴルーチンから観測可能であることが保証されます。

これは、チャネルが単なるデータ転送の手段ではなく、ゴルーチン間の同期とメモリの可視性を保証する強力なプリミティブであることを意味します。

### `sync/atomic` パッケージとチャネルの役割

`sync/atomic`パッケージは、低レベルのアトミック操作（不可分操作）を提供し、ロックを使用せずに共有変数へのアクセスを安全に行うためのものです。これらは通常、非常に細かい粒度での同期や、特定のパフォーマンス要件がある場合に用いられます。

一方、チャネルはより高レベルの同期プリミティブであり、ゴルーチン間の通信と同期を安全に行うためのGoのイディオムです。チャネルは、データの受け渡しだけでなく、前述のhappens-before関係を通じてメモリの可視性も保証します。

削除されたコメントは、`threadLimit`チャネルが「メモリを保護するためではない」と述べていましたが、これはチャネルが`sync/atomic`のような明示的なメモリ保護メカニズムとは異なる方法でメモリの可視性を保証するという事実を指していた可能性があります。しかし、Goメモリモデルの明確化により、チャネル操作が提供するhappens-before保証が、実質的に必要なメモリの可視性をカバーすることが理解されたため、この区別を強調する必要がなくなりました。

### `net` パッケージにおけるスレッド制限の目的

`src/net/net.go`ファイルは、Goのネットワーク操作の基盤を提供します。このファイル内の`threadLimit`チャネルは、特定の操作（おそらくはOSレベルのスレッドを必要とする可能性のある操作）の同時実行数を制限するために使用されていました。

`var threadLimit = make(chan struct{}, 500)` は、バッファサイズが500のチャネルを作成しています。
`func acquireThread() { threadLimit <- struct{}{} }` は、このチャネルに空の構造体（`struct{}`）を送信することで、利用可能な「スレッド」の数を減らします。チャネルが満杯（500個の`struct{}`が送信済み）の場合、それ以上の送信はブロックされ、結果として`acquireThread`を呼び出したゴルーチンは、チャネルに空きができるまで待機します。これにより、同時に実行される特定の操作の数が500に制限されます。

このメカニズムは、リソースの枯渇を防ぐためや、OSの制限を超えるスレッドの生成を避けるために用いられます。

## 技術的詳細

このコミットの技術的詳細の中心は、Goメモリモデルにおけるチャネルのセマンティクス、特に「happens-before」保証です。

Goメモリモデルの公式ドキュメントには、チャネル操作に関する以下の重要な規則が記載されています（Go 1.5のメモリモデルの明確化以降、これらの原則はより強調されています）：

1.  **チャネルへの送信は、そのチャネルからの受信よりも前に発生する。**
    *   `c <- x` (送信) は `y = <-c` (受信) よりも前に発生します。
    *   これは、送信ゴルーチンが送信前にメモリに書き込んだデータが、受信ゴルーチンが受信後にそのメモリを読み取るときに可視であることを保証します。

2.  **バッファなしチャネルの場合、受信は送信の完了よりも前に発生する。**
    *   これは、バッファなしチャネルが同期ポイントとして機能し、送信側と受信側の両方が相手の準備が整うまでブロックされることを意味します。

3.  **バッファ付きチャネルの場合、k番目の受信は、k番目の送信の完了よりも前に発生する。**
    *   このコミットで問題となっている`threadLimit`チャネルはバッファ付き（容量500）です。
    *   `threadLimit <- struct{}{}` という送信操作は、チャネルのバッファに空きがあればブロックされません。
    *   しかし、この送信操作が完了したという事実は、その送信操作が完了する前に送信ゴルーチンによって行われたすべてのメモリ書き込みが、後続のチャネルからの受信操作（`<-threadLimit`）が完了したゴルーチンから可視であることを保証します。

削除されたコメントは、`threadLimit <- struct{}{}`が「メモリを保護するためではない」と述べていました。これは、この操作がミューテックス（`sync.Mutex`）のように共有データへの排他的アクセスを保証するものではない、というニュアンスを含んでいた可能性があります。しかし、Goメモリモデルの観点からは、チャネルへの送信は、その送信が完了する前に送信ゴルーチンによって行われたすべてのメモリ書き込みが、後続の受信ゴルーチンから可視であることを保証します。これは、並行プログラミングにおける「メモリの保護」の一形態と見なすことができます。

コミットメッセージが「The memory model has been clarified since. This is legal and doesn't need justification.」と述べているのは、このチャネル送信操作が、Goメモリモデルの規則に従って、それ自体が安全な並行操作であり、特別なメモリ保護の注釈が不要になったことを示しています。つまり、チャネルのセマンティクスが十分に強力で、その操作がメモリの可視性に関して曖定な点がないことが明確になったため、以前のコメントが冗長になったということです。

## コアとなるコードの解説

削除されたコメントは、`acquireThread`関数内の`threadLimit <- struct{}{}`というチャネル送信操作について言及していました。

元のコメント:
```go
// Using send for acquire is fine here because we are not using this
// to protect any memory. All we care about is the number of goroutines
// making calls at a time.
```

このコメントは、`threadLimit`チャネルへの送信が、一般的なミューテックスやセマフォのように「メモリを保護する」目的で使用されているわけではないことを説明しようとしていました。代わりに、その唯一の目的は、同時に実行されるゴルーチンの数を制限することであると述べていました。

しかし、Goのメモリモデルが明確化された結果、チャネル操作が自動的にhappens-before関係を確立し、それによってメモリの可視性を保証することが広く理解されるようになりました。つまり、チャネルへの送信操作自体が、並行環境下でのメモリの安全性に寄与するのです。

したがって、このコメントは、チャネル操作がメモリの可視性に関して「問題ない」ことをわざわざ正当化する必要がなくなったため、冗長と判断され削除されました。Goのメモリモデルの観点から見れば、`threadLimit <- struct{}{}`は、それが同期プリミティブとして機能する限りにおいて、メモリの整合性に関する懸念を引き起こすことはありません。この変更は、Goのメモリモデルに対するコミュニティの理解が深まったことを示しています。

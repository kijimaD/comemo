## 変更の背景

Go言語の初期のRPC実装は、主にTCPなどの生のネットワーク接続を介して動作するように設計されていました。しかし、Webサービスやマイクロサービスアーキテクチャが普及するにつれて、HTTPプロトコルはファイアウォールやプロキシの通過が容易であること、既存のWebインフラストラクチャとの統合が容易であることなど、多くの利点を持つようになりました。

このコミットは、`net/rpc` パッケージがHTTPをトランスポート層として利用できるようにすることで、これらの利点を享受できるようにすることを目的としています。これにより、GoのRPCサービスは、従来のTCPベースの接続だけでなく、標準的なHTTPポート（通常は80番や443番）を介して公開できるようになり、より広範な環境での利用が可能になります。特に、既存のHTTPサーバーにRPCエンドポイントを組み込むことが容易になり、単一のポートでWebコンテンツとRPCサービスの両方を提供できるようになります。

## 前提知識の解説

このコミットの理解には、以下の概念が前提となります。

### 1. RPC (Remote Procedure Call)
RPCは、異なるアドレス空間にあるプログラムが、あたかもローカルな手続き（関数）であるかのように、ネットワーク越しに他のプログラムの手続きを呼び出すことを可能にする技術です。Goの `net/rpc` パッケージは、このRPCメカニズムをGoプログラム間で簡単に実装するためのフレームワークを提供します。

### 2. Goの `net/rpc` パッケージ
`net/rpc` パッケージは、Go言語でRPCサービスを構築するための標準ライブラリです。
- **サービス登録**: `rpc.Register` (またはこのコミットで導入される `rpc.Add`) を使用して、構造体のメソッドをRPCサービスとして公開します。
- **メソッドの要件**: RPCとして公開されるメソッドは、特定のシグネチャ（2つの引数と1つの `error` 戻り値）を持つ必要があります。
- **エンコーディング**: デフォルトでは、Go独自のバイナリエンコーディング形式である `gob` を使用して、データ構造をシリアライズ/デシリアライズします。

### 3. `gob` エンコーディング
`gob` はGo言語専用のバイナリシリアライゼーション形式です。効率的で、Goの型システムと密接に統合されています。RPC通信において、引数や戻り値の構造体をネットワーク経由で送受信するために利用されます。

### 4. `net/http` パッケージとHTTPサーバー
Goの `net/http` パッケージは、HTTPクライアントとサーバーを構築するための強力な標準ライブラリです。
- `http.Handle` / `http.HandleFunc`: 特定のURLパスに対するハンドラ関数を登録するために使用されます。
- `http.Serve`: 指定された `net.Listener` 上でHTTPリクエストを待ち受け、処理を開始します。

### 5. HTTP Hijacking (ハイジャック)
HTTPハイジャックとは、HTTPサーバーが確立したTCP接続を、HTTPプロトコル処理の途中で「乗っ取り」、その後の通信をHTTP以外のプロトコルで継続する技術です。`net/http` パッケージの `http.Hijacker` インターフェース（具体的には `http.Conn.Hijack()` メソッド）がこれを提供します。RPC over HTTPの場合、最初のHTTPリクエスト（通常は `GET`）を受信した後、接続をハイジャックし、その後の通信を `gob` エンコードされたRPCプロトコルに切り替えます。これにより、HTTPの初期ハンドシェイクを利用しつつ、その後のデータ転送はより効率的なRPCプロトコルで行うことができます。

## 技術的詳細

このコミットの主要な技術的変更点は、`net/rpc` パッケージがHTTP接続を透過的に扱えるようにするためのアダプテーション層の導入です。

### クライアント側の変更 (`src/pkg/rpc/client.go`)
- **`DialHTTP(network, address string) (*Client, os.Error)` の追加**:
    - この関数は、指定されたネットワークアドレスに対して `net.Dial` を使用してTCP接続を確立します。
    - 確立された接続に対し、RPCサービスへのHTTP `GET` リクエスト（例: `GET /_goRPC_ HTTP/1.0\n\n`）を送信します。これは、サーバーにRPC接続を意図していることを通知するための初期ハンドシェイクです。
    - その後、この接続を `NewClient` 関数に渡し、通常のRPCクライアントとして利用できるようにします。これにより、クライアントはHTTPの初期オーバーヘッドを一度だけ支払い、その後のRPC通信は直接TCP接続上で行われることになります。
- **`Dial(network, address string) (*Client, os.Error)` の変更**:
    - 以前の実装から簡素化され、直接 `net.Dial` で接続を確立し、`NewClient` を呼び出す形になりました。これは、`DialHTTP` との役割分担を明確にするためと考えられます。

### サーバー側の変更 (`src/pkg/rpc/server.go`)
- **`http` パッケージのインポート**: HTTP関連の機能を利用するために `net/http` パッケージがインポートされました。
- **グローバルRPCサーバーインスタンス**:
    - `type Server struct` が `type serverType struct` にリネームされ、プライベートな型になりました。
    - `var server = &serverType{ make(map[string] *service) }` というグローバル変数として、RPCサーバーの単一インスタンスが導入されました。これにより、`rpc.Add` や `rpc.ServeConn` といったトップレベルの関数が、このグローバルインスタンスを操作する形になります。これは、RPCサービスがアプリケーション全体で共有される単一のエンティティであることを示唆しています。
- **トップレベル関数の導入**:
    - `func Add(rcvr interface{}) os.Error`: 以前は `(*Server).Add` メソッドだったものが、グローバルな `rpc.Add` 関数として公開され、内部で `server.add(rcvr)` を呼び出します。
    - `func ServeConn(conn io.ReadWriteCloser)`: 同様に、`(*Server).ServeConn` がグローバル関数になりました。
    - `func Accept(lis net.Listener)`: `(*Server).Accept` がグローバル関数になりました。
    これらの変更により、RPCサーバーのセットアップがよりシンプルになり、グローバルなRPCサービスレジストリとして機能するようになりました。
- **`bufRWC` 構造体**:
    - `http.Hijack()` によって取得される `bufio.ReadWriter` と `net.Conn` を `io.ReadWriteCloser` インターフェースに適合させるためのヘルパー構造体です。`net/rpc` の `serve` メソッドは `io.ReadWriteCloser` を期待するため、このアダプターが必要となります。
- **`serveHTTP(c *http.Conn, req *http.Request)` 関数の追加**:
    - この関数は `http.HandlerFunc` として登録されることを想定しています。
    - `c.Hijack()` を呼び出して、基盤となるTCP接続とバッファをHTTPサーバーから「乗っ取ります」。
    - ハイジャックされた接続とバッファを `bufRWC` でラップし、`server.serve()` メソッドに渡します。これにより、HTTPリクエストを受信した後の接続が、通常のRPC接続として扱われるようになります。
- **`rpcPath` の定義**:
    - `var rpcPath string = "/_goRPC_"` として、RPCサービスがリッスンするHTTPパスが定義されました。これはクライアントが `DialHTTP` で接続する際に使用するパスと一致します。
- **`HandleHTTP()` 関数の追加**:
    - この関数は、`rpcPath` (`/_goRPC_`) に対して `serveHTTP` 関数をHTTPハンドラとして登録します。開発者は `http.Handle(rpc.rpcPath, rpc.HandleHTTP)` のように呼び出すことで、既存のHTTPサーバーにRPCエンドポイントを簡単に追加できるようになります。

### テストの変更 (`src/pkg/rpc/server_test.go`)
- **`httpServerAddr` の追加**: HTTP RPCサーバーのアドレスを保持するための変数が追加されました。
- **`startServer()` の更新**:
    - 従来のTCP RPCサーバーの起動に加え、`rpc.HandleHTTP()` を呼び出してHTTP RPCハンドラを登録し、さらに `http.Serve()` を別のゴルーチンで起動してHTTPサーバーを立ち上げるようになりました。これにより、テスト環境でTCP RPCとHTTP RPCの両方を同時に検証できるようになります。
- **`TestHTTPRPC(t *testing.T)` の追加**:
    - 新しく追加された `DialHTTP` 関数を使用してHTTP RPCサーバーに接続し、RPC呼び出しが正しく機能するかどうかを検証するテストケースです。

## コアとなるコードの解説

このコミットの核心は、既存の `net/rpc` の接続処理ロジックを再利用しつつ、HTTPプロトコルをその上に透過的にマッピングする点にあります。

### クライアント側 (`DialHTTP`)
`DialHTTP` 関数は、まず通常のTCP接続を確立します。その後、この接続に対して特定のHTTP `GET` リクエスト (`GET /_goRPC_ HTTP/1.0\n\n`) を送信します。このリクエストは、サーバーに対して「この接続はRPCのために使われる」というシグナルを送る役割を果たします。HTTPヘッダーの送信後、この接続はHTTPプロトコルから解放され、直接 `gob` エンコードされたRPCメッセージの送受信に使用されます。これにより、クライアントはHTTPの初期ハンドシェイクを利用しつつ、その後のRPC通信はHTTPのオーバーヘッドなしで効率的に行えるようになります。

### サーバー側 (`HandleHTTP`, `serveHTTP`, `bufRWC`)
サーバー側では、`HandleHTTP` 関数が `/_goRPC_` という特定のパスに `serveHTTP` 関数をHTTPハンドラとして登録します。
`serveHTTP` 関数がHTTPリクエストを受信すると、`http.Conn.Hijack()` メソッドを呼び出して、HTTPサーバーが管理していたTCP接続を「乗っ取ります」。`Hijack()` は、基盤となる `net.Conn` と、その接続に関連付けられた `bufio.ReadWriter` を返します。
`net/rpc` の内部的な `serve` メソッドは `io.ReadWriteCloser` インターフェースを実装するオブジェクトを期待します。`Hijack()` が返す `net.Conn` は `io.ReadWriteCloser` を実装していますが、`bufio.ReadWriter` も考慮に入れる必要があります。そこで、`bufRWC` というヘルパー構造体が導入され、`bufio.ReadWriter` と `net.Conn` をラップして `io.ReadWriteCloser` インターフェースを満たすようにします。
最終的に、`server.serve(&bufRWC{buf, conn, conn})` が呼び出され、ハイジャックされた接続が通常のRPC接続として処理されます。これにより、HTTPサーバーは最初のHTTPリクエストの処理を終えた後、その接続をRPCサーバーに引き渡し、RPCサーバーは残りの通信を `gob` プロトコルで継続します。

### グローバルRPCサーバーインスタンス
`net/rpc` パッケージ全体で単一のRPCサービスレジストリを管理するために、`serverType` というプライベートな型と、そのインスタンスであるグローバル変数 `server` が導入されました。これにより、`rpc.Add` や `rpc.ServeConn` といったトップレベルの関数が、このグローバルな `server` インスタンスを介してサービスを登録・提供する形に統一されました。これは、RPCサービスがアプリケーション全体で一元的に管理されることを意図しています。

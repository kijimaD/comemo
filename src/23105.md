## 変更の背景

このコミットは、Go 1.5で導入されたGoランタイムのガベージコレクション（GC）の抜本的な変更に起因しています。Go 1.5では、従来の「Stop-the-World (STW)」方式のGCから、並行（Concurrent）なマーク＆スイープGCへと移行しました。これにより、GCによるアプリケーションの一時停止時間（ポーズタイム）が大幅に削減され、レイテンシが改善されました。

このGCの変更に伴い、GCの内部的な動作や状態を管理するための変数やメカニズムも進化しました。`bgMarkCount`という変数は、おそらく以前のGC実装においてバックグラウンドでのマーク処理の進行状況や回数を追跡するために使用されていたものと考えられます。しかし、新しい並行GCの「GCペーシング」メカニズムでは、`fractionalMarkWorkersNeeded`のような、より洗練された制御変数や指標が導入されました。

このコミットは、コードのコメントが実際のGC実装の変更に追いついていなかったために行われました。`bgMarkCount`がもはや存在しないにもかかわらず、その変数に言及しているコメントが残っていたため、コードの理解を妨げ、誤解を招く可能性がありました。そのため、このコミットは、コードの正確性と可読性を保つために、古いコメントを新しい実装に合致するように更新することを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC)

Go言語は、自動メモリ管理のためにガベージコレクションを採用しています。Go 1.5以前のGCは、アプリケーションの実行を完全に停止させてからGCを実行する「Stop-the-World (STW)」方式が主流でした。これにより、GC中はアプリケーションが応答しなくなるという問題がありました。

Go 1.5で導入された新しいGCは、主に以下の特徴を持ちます。

*   **並行マーク＆スイープ (Concurrent Mark and Sweep):**
    *   **マークフェーズ:** GCが到達可能なオブジェクトを識別するフェーズです。Go 1.5からは、このマークフェーズの大部分がアプリケーションの実行と並行して行われるようになりました。これにより、アプリケーションのポーズタイムが大幅に短縮されます。
    *   **スイープフェーズ:** マークされなかった（到達不可能な）オブジェクトが占めていたメモリを解放するフェーズです。これも並行して行われます。
*   **GCペーシング (GC Pacing):**
    *   Go 1.5のGCの重要な要素の一つがGCペーシングです。これは、GCがいつ開始され、どれくらいのCPUリソースをGCに割り当てるかを動的に決定するメカニズムです。ヒープサイズやCPU使用率の目標に基づいて、GCが効率的に動作するように調整されます。
    *   GCペーシングは、アプリケーションの実行中にGCがバックグラウンドで動作するためのCPUリソースを確保し、GCのオーバーヘッドを最小限に抑えつつ、必要な時にGCが実行されるように調整します。

### `bgMarkCount`と`fractionalMarkWorkersNeeded`

*   **`bgMarkCount` (旧):**
    この変数は、Go 1.5以前、またはGo 1.5のGC開発の初期段階において、バックグラウンドでのマーク処理の進行状況を追跡するために使用されていた可能性が高いです。コミットメッセージにあるように、この変数は現在のGC実装ではもはや存在しません。
*   **`fractionalMarkWorkersNeeded` (新):**
    これは、Go 1.5以降の並行GCにおけるGCペーシングメカニズムの一部として導入された変数です。GCは、アプリケーションの論理プロセッサ（P）の数に応じて、バックグラウンドでマーク作業を行うワーカー（ゴルーチン）を起動します。`fractionalMarkWorkersNeeded`は、GCがCPUリソースをより細かく制御するために使用されます。例えば、利用可能なPの数がGCワーカーの数と完全に一致しない場合でも、残りのCPU容量をGCタスクに利用するために「分数的な」ワーカーが必要かどうかを判断するために使われます。この変数は通常、分数的なワーカーが必要な場合に1、そうでない場合に0に設定され、GCの`startCycle`関数などに影響を与えます。

### `gcControllerState`と`findRunnable`

*   **`gcControllerState`:**
    Goランタイムのガベージコレクタの全体的な状態と制御ロジックをカプセル化する構造体です。GCの進行状況、現在のフェーズ、各種統計、そしてGCペーシングに関連する変数などが含まれます。
*   **`findRunnable`:**
    `gcControllerState`のメソッドの一つで、GCワーカーゴルーチンが実行すべきタスクを見つけるために使用されます。この関数は、GCのマークフェーズ中に、まだ処理されていないオブジェクトを見つけてマーク作業を割り当てたり、あるいはGC作業が一時的にない場合に`nil`を返したりします。コメントが修正された箇所は、この`findRunnable`関数内で、バックグラウンドマーク作業のスケジューリングに関するロジックの一部として存在していました。

## 技術的詳細

このコミットは、`src/runtime/mgc.go`ファイル内の2つの異なる箇所でコメントを修正しています。

1.  **最初の修正箇所 (行 485-487):**
    元のコメントは、GCのマークフェーズの終わりに、アシスト（アプリケーションゴルーチンがGC作業を手伝うこと）が収束していく状況で、バックグラウンドマークをすぐに実行しても意味がないことを説明していました。古いコメントは「`bgMarkCount`がゼロより上に留まるかもしれないから」という理由を挙げていましたが、これは`bgMarkCount`が存在しないため不正確です。
    修正後のコメントは、より汎用的に「すぐに戻ってしまうだけだから」と変更されており、特定の内部変数に依存しない、より正確な説明になっています。これは、GCの作業が一時的に枯渇している状況を指しており、バックグラウンドワーカーを起動してもすぐに終了してしまうため、無駄なスケジューリングを避ける意図があります。

2.  **二番目の修正箇所 (行 515-517):**
    このコメントは、GCペーシングに関するTODO（将来的な改善点）の一部です。元のコメントは「`c.bgMarkCount`に対する競合を排除できる」と述べていましたが、これも`bgMarkCount`がもはや存在しないため不正確でした。
    修正後のコメントは「`c.fractionalMarkWorkersNeeded`に対する競合を排除できる」と変更されています。これは、GCペーシングにおいて`fractionalMarkWorkersNeeded`が重要な役割を果たす変数であり、この変数へのアクセス競合を減らすことがGCの効率向上に繋がるという、より正確な技術的洞察を反映しています。このTODOは、分数的なワーカーをスケジューリングする最適なタイミングを事前に計算することで、複数のP（論理プロセッサ）が同時にこの変数にアクセスしようとすることによる競合を減らす可能性を示唆しています。

これらの変更は、GoランタイムのGCが進化し、より洗練されたペーシングメカニズムを採用した結果として生じた内部的な変数名の変更を反映したものです。コードの動作自体は変更されず、コメントの正確性を保つことで、将来のGo開発者がGCの内部を理解する際の混乱を避けることが目的です。

## コアとなるコードの解説

このコミットは、`src/runtime/mgc.go`ファイル内の`gcControllerState`構造体の`findRunnable`メソッド内のコメントを修正しています。

1.  **最初の変更:**
    `findRunnable`関数は、GCワーカーゴルーチンが実行すべきGC作業を見つける役割を担っています。最初の変更箇所は、GCのマークフェーズの終盤で、GCアシスト（アプリケーションゴルーチンがGC作業を手伝うこと）が減少している状況を説明しています。この時、GC作業が一時的に不足しているため、バックグラウンドマークワーカーを起動してもすぐに終了してしまうことを示しています。
    *   **変更前:** `// background mark because it'll just return and // bgMarkCount might hover above zero.`
        `bgMarkCount`という変数がゼロより上に留まる可能性があるため、バックグラウンドマークを起動しても意味がない、という説明でした。
    *   **変更後:** `// background mark because it'll just return immediately.`
        `bgMarkCount`がもはや存在しないため、単に「すぐに戻ってしまうだけだから」という、より一般的な表現に修正されました。これは、GC作業が一時的に枯渇している状況を正確に反映しています。

2.  **二番目の変更:**
    この変更箇所は、GCペーシングに関する将来的な最適化の可能性を示すTODOコメントです。GCペーシングは、GCがCPUリソースをどれだけ使用するかを制御するメカニズムです。
    *   **変更前:** `// eliminate contention on c.bgMarkCount by`
        `c.bgMarkCount`に対する競合（複数のゴルーチンが同時にアクセスしようとすること）を排除できる、という内容でした。
    *   **変更後:** `// eliminate contention on c.fractionalMarkWorkersNeeded by`
        `bgMarkCount`が`fractionalMarkWorkersNeeded`に置き換えられたため、コメントもそれに合わせて修正されました。これは、GCペーシングにおいて`fractionalMarkWorkersNeeded`が重要な制御変数であり、この変数へのアクセス競合を減らすことがGCの効率向上に繋がるという、より正確な技術的洞察を反映しています。このTODOは、分数的なワーカーのスケジューリングタイミングを事前に計算することで、この変数への競合を減らす可能性を示唆しています。

これらの変更は、GoランタイムのGCの内部実装が進化し、それに伴い使用される変数名が変更されたことを反映した、純粋なコメントの更新です。コードの動作には影響を与えませんが、GoランタイムのGCの進化の歴史と、その内部構造を理解する上で重要な手がかりとなります。

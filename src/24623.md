このコミットは、GoコンパイラのSSA（Static Single Assignment）形式における`inBounds`（範囲内チェック）の書き換えルールを改善します。

## 変更の背景

Goコンパイラは、プログラムをSSA形式という中間表現に変換し、様々な最適化を適用します。この最適化の一つに、定数伝播や不要なコードの削除などがあります。配列のインデックスアクセスなどで行われる範囲チェック（`inBounds`）は、実行時の安全性を保証するために重要ですが、コンパイル時にインデックスが常に有効な範囲内にあることが判明している場合、そのチェックは不要となり、削除することでパフォーマンスを向上させることができます。

以前の`inBounds`関数は、すべての整数型に対して単一の汎用的な実装を使用していました。しかし、Go言語には`int8`, `int16`, `int32`, `int64`といった異なるサイズの整数型が存在し、それぞれが異なる最大値と最小値を持っています。汎用的な`inBounds`関数でこれらの異なる型を扱う場合、不必要な型変換（例えば、`int8`の値を`int64`にキャストしてからチェックする）が発生したり、あるいは特定の型の特性（オーバーフロー挙動など）が正確に考慮されない可能性がありました。

このコミットの背景には、SSA最適化の精度を向上させ、より効率的なコードを生成するために、各整数型の特性に合わせた`inBounds`チェックを導入する必要性があったと考えられます。これにより、コンパイラはより正確な範囲チェックの最適化を適用できるようになります。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSAは、コンパイラの中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。Goコンパイラも、ソースコードをSSA形式に変換し、様々な最適化パスを適用してから最終的な機械語コードを生成します。

### 2. コンパイラの書き換えルール (Rewrite Rules)

コンパイラの最適化フェーズでは、「書き換えルール」と呼ばれるパターンマッチングと置換のメカニズムが頻繁に用いられます。これは、SSA形式のグラフ（またはASTなど）において、特定のパターン（例えば、`x + 0`）を見つけ出し、それをより効率的な等価なパターン（例えば、`x`）に置き換えるものです。これにより、コードの簡素化やパフォーマンス向上が図られます。
GoコンパイラのSSAバックエンドでは、`.rules`ファイルにこれらの書き換えルールが記述されており、`gen`ツールによってGoのコードに変換されます。

### 3. `inBounds` チェック

`inBounds(idx, len)`は、インデックス`idx`が長さ`len`の配列やスライスの有効な範囲内（`0 <= idx < len`）にあるかどうかをチェックする関数です。Go言語では、配列やスライスへのアクセス時に自動的にこのチェックが行われ、範囲外アクセスはパニックを引き起こします。コンパイラは、このチェックをコンパイル時に静的に判断できる場合、実行時のチェックを省略して最適化することができます。

### 4. 整数型のサイズとオーバーフロー

Go言語の整数型（`int8`, `int16`, `int32`, `int64`）は、それぞれ異なるビット幅を持ち、表現できる値の範囲が異なります。例えば、`int8`は-128から127まで、`int32`は-2,147,483,648から2,147,483,647までです。これらの型間で値を変換する際には、値が新しい型の範囲に収まらない場合にオーバーフローや切り捨てが発生する可能性があります。`inBounds`チェックにおいて、これらの型の特性を正確に考慮することは、正しい最適化を行う上で不可欠です。

### 5. `SBBQcarrymask` と `SBBLcarrymask`

これらはAMD64アーキテクチャ固有の命令に関連するSSAオペレーションです。
- `SBBQcarrymask`: `SBB` (Subtract with Borrow) 命令のキャリーフラグをマスクとして使用する操作で、64ビット値に適用されます。主に比較結果（`CMPQconst`）に基づいて、ある条件が満たされた場合に`-1`（全ビットセット）を、満たされない場合に`0`を生成するのに使われます。これは、条件付き移動や論理演算の最適化に利用されます。
- `SBBLcarrymask`: 同様に`SBB`命令のキャリーフラグをマスクとして使用しますが、32ビット値に適用されます。

これらの命令は、特定の比較結果を効率的にブール値（またはそれに準ずる値）に変換するために、コンパイラバックエンドで利用される低レベルの最適化手法です。

## 技術的詳細

このコミットの主要な技術的変更点は、`inBounds`チェックの粒度を整数型のサイズに合わせて細分化したことです。

1.  **型特化型`inBounds`関数の導入**:
    `src/cmd/compile/internal/ssa/rewrite.go`において、従来の単一の`inBounds(idx, len int64) bool`関数が削除され、以下の4つの関数が新しく定義されました。
    -   `inBounds8(idx, len int64) bool`: 8ビット整数（`int8`）の範囲チェックを想定。内部で`int8`にキャストして比較。
    -   `inBounds16(idx, len int64) bool`: 16ビット整数（`int16`）の範囲チェックを想定。内部で`int16`にキャストして比較。
    -   `inBounds32(idx, len int64) bool`: 32ビット整数（`int32`）の範囲チェックを想定。内部で`int32`にキャストして比較。
    -   `inBounds64(idx, len int64) bool`: 64ビット整数（`int64`）の範囲チェックを想定。従来の`inBounds`と同じロジック。

    これらの関数は、引数としては`int64`を受け取りますが、内部でそれぞれのターゲット型にキャストしてから比較を行うことで、その型の範囲内での正確なチェックを実現します。例えば、`inBounds8`は`int8(idx) >= 0 && int8(idx) < int8(len)`のように比較します。これにより、`int64`で表現された定数であっても、それが本来`int8`として扱われるべき文脈であれば、`int8`の範囲内でのオーバーフローなどを正確に考慮したチェックが可能になります。

2.  **SSA書き換えルールの更新**:
    -   `src/cmd/compile/internal/ssa/gen/AMD64.rules`および`src/cmd/compile/internal/ssa/rewriteAMD64.go`では、AMD64アーキテクチャ固有の`SBBQcarrymask`および`SBBLcarrymask`オペレーションに関連する書き換えルールが更新されました。これらのルールは、定数比較（`CMPQconst`, `CMPLconst`, `CMPWconst`, `CMPBconst`）と定数移動（`MOVQconst`, `MOVLconst`, `MOVWconst`, `MOVBconst`）の組み合わせを検出し、その結果が`inBounds`条件を満たすかどうかに応じて、`-1`または`0`の定数に置き換えるものです。
        変更前は、すべてのケースで汎用的な`inBounds(int64(intX(d)), int64(intX(c)))`のような冗長なキャストを含む呼び出しが行われていましたが、変更後は`inBounds64(d, c)`, `inBounds32(d, c)`, `inBounds16(d, c)`, `inBounds8(d, c)`といった、より適切な型特化型関数が直接呼び出されるようになりました。これにより、ルールの記述が簡潔になり、意図が明確になります。

    -   `src/cmd/compile/internal/ssa/gen/generic.rules`および`src/cmd/compile/internal/ssa/rewritegeneric.go`では、汎用的な`IsInBounds`オペレーションの書き換えルールが更新されました。
        変更前は、`IsInBounds (ConstPtr [c]) (ConstPtr [d])`という単一のルールで`inBounds(c,d)`を呼び出していましたが、変更後は`Const32`, `Const64`, `ConstPtr`のオペランドタイプと、`config.PtrSize`（ポインタのサイズ、32ビットまたは64ビット）に応じて、`inBounds32(c,d)`または`inBounds64(c,d)`を呼び出すように細分化されました。これにより、ポインタのサイズや定数の型に応じた正確な範囲チェックが可能になります。

これらの変更により、コンパイラは定数インデックスの範囲チェックをより正確に、かつ効率的に評価できるようになり、結果として生成される機械語コードから不要な範囲チェックをより多く削除できる可能性が高まります。これは、特に数値計算やデータ構造のアクセスが頻繁に行われるコードにおいて、パフォーマンスの向上に寄与します。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/rewrite.go` の変更

このファイルでは、`inBounds`という単一の汎用関数が、`inBounds8`, `inBounds16`, `inBounds32`, `inBounds64`という4つの型特化型関数に置き換えられました。

-   **旧 `inBounds`**:
    ```go
    func inBounds(idx, len int64) bool {
        return idx >= 0 && idx < len
    }
    ```
    この関数は、常に`int64`としてインデックスと長さを扱い、比較していました。しかし、もし元の値が`int8`や`int32`であった場合、`int64`への暗黙的な型変換によって、本来の型の範囲内でのオーバーフロー挙動が失われる可能性がありました。例えば、`int8`で`-1`となる値が`int64`では`-1`のままであり、`0`以上のチェックで問題なく通過してしまう、といったケースです。

-   **新 `inBoundsX` 関数群**:
    ```go
    func inBounds8(idx, len int64) bool  { return int8(idx) >= 0 && int8(idx) < int8(len) }
    func inBounds16(idx, len int64) bool { return int16(idx) >= 0 && int16(idx) < int16(len) }
    func inBounds32(idx, len int64) bool { return int32(idx) >= 0 && int32(idx) < int32(len) }
    func inBounds64(idx, len int64) bool { return idx >= 0 && idx < len }
    ```
    新しい関数群は、引数として`int64`を受け取りますが、比較を行う前に明示的にそれぞれのターゲット型（`int8`, `int16`, `int32`）にキャストしています。これにより、例えば`inBounds8`は、`idx`と`len`が`int8`の範囲内でどのように振る舞うかを正確にシミュレートできます。これにより、コンパイラはより厳密な型セマンティクスに基づいて範囲チェックの最適化を適用できるようになります。`inBounds64`は、`int64`の範囲チェックであり、元の`inBounds`と同じロジックです。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` および `src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更

これらのファイルは、AMD64アーキテクチャ向けのSSA書き換えルールを定義しています。変更は、主に`SBBQcarrymask`と`SBBLcarrymask`オペレーションに関連するルールに集中しています。これらのルールは、定数オペランドを持つ比較命令（`CMPXconst`）と定数移動命令（`MOVXconst`）の組み合わせを検出し、その結果が特定の`inBounds`条件を満たすかどうかに基づいて、結果を`-1`または`0`の定数に置き換えるものです。

変更前は、`inBounds(d, c)`や`inBounds(int64(int32(d)), int64(int32(c)))`のように、汎用`inBounds`関数を呼び出し、必要に応じて`int64`へのキャストを行っていました。
変更後は、`inBounds64(d, c)`, `inBounds32(d, c)`, `inBounds16(d, c)`, `inBounds8(d, c)`といった、より適切な型特化型関数が直接呼び出されるようになりました。これにより、ルールの可読性が向上し、また`gen`ツールが生成するGoコード（`rewriteAMD64.go`）においても、冗長な型変換が削減され、より直接的な呼び出しになります。

### `src/cmd/compile/internal/ssa/gen/generic.rules` および `src/cmd/compile/internal/ssa/rewritegeneric.go` の変更

これらのファイルは、アーキテクチャに依存しない汎用的なSSA書き換えルールを定義しています。`IsInBounds`オペレーションに関するルールが変更されました。

変更前は、`IsInBounds (ConstPtr [c]) (ConstPtr [d])`という単一のルールで、ポインタ型の定数に対して`inBounds(c,d)`を呼び出していました。
変更後は、`IsInBounds`オペレーションが受け取る定数の型（`Const32`, `Const64`, `ConstPtr`）と、コンパイラの構成情報である`config.PtrSize`（ポインタのサイズが4バイトか8バイトか）に基づいて、`inBounds32(c,d)`または`inBounds64(c,d)`を呼び出すように細分化されました。

-   `Const32`オペランドの場合: `inBounds32(c,d)`
-   `Const64`オペランドの場合: `inBounds64(c,d)`
-   `ConstPtr`オペランドの場合:
    -   `config.PtrSize == 4` (32ビットシステム): `inBounds32(c,d)`
    -   `config.PtrSize == 8` (64ビットシステム): `inBounds64(c,d)`

この変更により、ポインタのサイズが32ビットか64ビットかによって、適切なサイズの`inBounds`チェックが適用されるようになり、汎用的なSSA最適化の精度が向上します。

全体として、このコミットはGoコンパイラのSSAバックエンドにおける定数インデックスの範囲チェックの最適化を、より型安全かつ効率的に行うための重要な改善です。これにより、コンパイラはより多くのケースで不要な実行時範囲チェックを削除できるようになり、生成されるバイナリのパフォーマンス向上に貢献します。

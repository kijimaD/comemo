## 変更の背景

このコミットは、Go言語の`crypto/x509`パッケージにおけるホスト名検証の不具合を修正するものです。具体的には、SSL/TLS通信において、クライアントが接続しようとするホスト名が「絶対ドメイン名（Fully Qualified Domain Name, FQDN）」、すなわち末尾にドット（`.`）が付加された形式（例: `example.com.`）であった場合に、証明書の検証が失敗し、無効な証明書として報告される問題がありました。

この問題の根本原因は、`matchHostnames`関数内のホスト名とパターンを比較するロジックにありました。この関数では、ホスト名と証明書内のパターン（Common NameやSubject Alternative Name）をドット（`.`）で分割し、それぞれのセグメントを比較することでマッチングを行っていました。しかし、絶対ドメイン名（例: `example.com.`）をドットで分割すると、末尾のドットのために余分な空文字列がスライスに追加されてしまいます（例: `strings.Split("example.com.", ".")`は`["example", "com", ""]`を返す）。

これにより、ホスト名とパターンの分割後のスライスの長さが一致しない場合、`matchHostnames`関数は即座に`false`を返していました。結果として、本来であれば有効なはずの証明書が、ホスト名が絶対ドメイン名形式であるという理由だけで無効と判断されてしまっていたのです。この挙動は、RFC 1034やRFC 1035で定義されているDNSの仕様において、末尾のドットがルートゾーンを示す正当な表記であるにもかかわらず、Goの`x509`パッケージがこれを正しく扱えていなかったことを意味します。

この修正は、このような絶対ドメイン名が正しく処理され、証明書検証が期待通りに行われるようにするために導入されました。

## 前提知識の解説

### X.509証明書とSSL/TLSにおける利用

X.509は、公開鍵証明書の標準フォーマットを定義するITU-Tの標準規格です。SSL/TLS（Transport Layer Security）プロトコルにおいて、サーバーの身元をクライアントに証明するために広く利用されています。X.509証明書には、公開鍵、証明書所有者の情報（Common Name, CNなど）、発行者の情報、有効期間、デジタル署名などが含まれます。クライアントは、これらの情報と信頼された認証局（CA）の公開鍵を用いて、サーバー証明書の正当性を検証します。

### ホスト名マッチング

SSL/TLS通信において、クライアントはサーバーから提示されたX.509証明書が、接続しようとしているホスト名と一致するかどうかを検証します。この検証は主に以下のフィールドで行われます。

*   **Common Name (CN)**: 証明書のSubjectフィールドに含まれる、主要なホスト名。
*   **Subject Alternative Name (SAN)**: 複数のホスト名（DNS名、IPアドレスなど）を記述できる拡張フィールド。現代のWebでは、CNよりもSANが推奨され、優先的に使用されます。

ホスト名マッチングでは、これらのフィールドに記載されたホスト名と、クライアントが接続を試みているホスト名が比較されます。ワイルドカード証明書（例: `*.example.com`）の場合、`*`は単一のサブドメインにマッチします。

### 絶対ドメイン名 (Fully Qualified Domain Name, FQDN)

ドメイン名は、インターネット上のリソースを一意に識別するために使用されます。通常、私たちは`example.com`のように末尾にドットを付けずにドメイン名を記述しますが、DNS（Domain Name System）の文脈では、末尾にドットが付加された形式（例: `example.com.`）が「絶対ドメイン名」または「完全修飾ドメイン名」と呼ばれます。この末尾のドットは、そのドメイン名がDNSのルートゾーンからの完全なパスであることを示します。DNSリゾルバは、末尾にドットがないドメイン名を処理する際に、自動的にローカルの検索ドメインなどを付加して解決を試みますが、末尾にドットがある場合はそのまま完全なドメイン名として扱います。

### Go言語の`crypto/x509`パッケージ

Go言語の標準ライブラリである`crypto/x509`パッケージは、X.509証明書のパース、検証、生成などの機能を提供します。SSL/TLS通信を行う`crypto/tls`パッケージの基盤として利用されており、証明書の信頼性検証やホスト名検証といったセキュリティ上重要な処理を担っています。

### Go言語の`strings`パッケージ

`strings`パッケージは、Go言語における文字列操作のための基本的な機能を提供します。このコミットに関連する関数は以下の通りです。

*   **`strings.Split(s, sep string) []string`**: 文字列`s`を区切り文字`sep`で分割し、部分文字列のスライスを返します。`s`が`sep`で終わる場合、結果のスライスの末尾に空文字列が追加されます。
*   **`strings.TrimSuffix(s, suffix string) string`**: 文字列`s`が`suffix`で終わる場合、その`suffix`を取り除いた文字列を返します。`s`が`suffix`で終わらない場合は、`s`をそのまま返します。

## 技術的詳細

### `matchHostnames`関数の役割と既存のロジック

`matchHostnames`関数は、Goの`crypto/x509`パッケージ内で、証明書に記載されたホスト名パターンと、実際に接続しようとしているホスト名が一致するかどうかを検証する役割を担っています。この関数は、ワイルドカード（`*`）を含むパターンにも対応しており、例えば`*.example.com`のようなパターンと`www.example.com`のようなホスト名を比較することができます。

修正前の`matchHostnames`関数は、ホスト名とパターンをドット（`.`）で分割し、それぞれのセグメントを比較することでマッチングを行っていました。この比較ロジックは、分割後のスライスの長さが一致することを前提としていました。

### 絶対ドメイン名がどのように問題を引き起こしていたか

前述の通り、絶対ドメイン名（例: `example.com.`）を`strings.Split`関数でドット（`.`）で分割すると、末尾のドットのために結果のスライスに余分な空文字列が追加されます。

例:
*   `strings.Split("example.com", ".")` -> `["example", "com"]` (長さ2)
*   `strings.Split("example.com.", ".")` -> `["example", "com", ""]` (長さ3)

一方、証明書内のホスト名パターンは通常、末尾のドットを含まない形式（例: `example.com`）で記述されます。したがって、`matchHostnames`関数がホスト名とパターンを分割した際、絶対ドメイン名が使用された場合のみ、ホスト名のスライスの長さがパターンのスライスの長さよりも1つ多くなっていました。

`matchHostnames`関数は、分割後のスライスの長さが異なる場合に即座に`false`を返すロジックを持っていたため、この長さの不一致が原因で、絶対ドメイン名が使用された場合に証明書検証が失敗していました。これは、DNSの仕様に準拠した絶対ドメイン名の使用を妨げる不具合でした。

### `strings.TrimSuffix(host, ".")`がどのように問題を解決するか

このコミットによる修正は、`matchHostnames`関数の冒頭で、入力された`host`文字列の末尾からドット（`.`）を削除するという非常にシンプルかつ効果的なものです。

```go
host = strings.TrimSuffix(host, ".")
```

この一行が追加されたことで、`example.com.`のような絶対ドメイン名が`matchHostnames`関数に渡された場合でも、内部処理に入る前に`example.com`という形式に正規化されます。これにより、`strings.Split`で分割した際のスライスの長さが、末尾にドットがない通常のドメイン名と同じになり、パターンとの比較が正しく行われるようになります。

この変更は、Goの`crypto/x509`パッケージが、DNSの絶対ドメイン名の表記を正しく解釈し、証明書検証の堅牢性を向上させる上で非常に重要です。

### この変更がセキュリティに与える影響

この修正は、セキュリティ上の脆弱性を直接修正するものではありませんが、SSL/TLS通信の信頼性と互換性を向上させます。絶対ドメイン名を使用する環境において、正当な証明書が不当に拒否されるという問題を解消することで、より広範なネットワーク構成でのGoアプリケーションの利用を可能にします。これにより、ユーザーは不必要な証明書エラーに遭遇することなく、安全な通信を確立できるようになります。

## 前提知識の解説

### X.509証明書とSSL/TLSにおける利用

X.509は、公開鍵証明書の標準フォーマットを定義するITU-Tの標準規格です。SSL/TLS（Transport Layer Security）プロトコルにおいて、サーバーの身元をクライアントに証明するために広く利用されています。X.509証明書には、公開鍵、証明書所有者の情報（Common Name, CNなど）、発行者の情報、有効期間、デジタル署名などが含まれます。クライアントは、これらの情報と信頼された認証局（CA）の公開鍵を用いて、サーバー証明書の正当性を検証します。

### ホスト名マッチング

SSL/TLS通信において、クライアントはサーバーから提示されたX.509証明書が、接続しようとしているホスト名と一致するかどうかを検証します。この検証は主に以下のフィールドで行われます。

*   **Common Name (CN)**: 証明書のSubjectフィールドに含まれる、主要なホスト名。
*   **Subject Alternative Name (SAN)**: 複数のホスト名（DNS名、IPアドレスなど）を記述できる拡張フィールド。現代のWebでは、CNよりもSANが推奨され、優先的に使用されます。

ホスト名マッチングでは、これらのフィールドに記載されたホスト名と、クライアントが接続を試みているホスト名が比較されます。ワイルドカード証明書（例: `*.example.com`）の場合、`*`は単一のサブドメインにマッチします。

### 絶対ドメイン名 (Fully Qualified Domain Name, FQDN)

ドメイン名は、インターネット上のリソースを一意に識別するために使用されます。通常、私たちは`example.com`のように末尾にドットを付けずにドメイン名を記述しますが、DNS（Domain Name System）の文脈では、末尾にドットが付加された形式（例: `example.com.`）が「絶対ドメイン名」または「完全修飾ドメイン名」と呼ばれます。この末尾のドットは、そのドメイン名がDNSのルートゾーンからの完全なパスであることを示します。DNSリゾルバは、末尾にドットがないドメイン名を処理する際に、自動的にローカルの検索ドメインなどを付加して解決を試みますが、末尾にドットがある場合はそのまま完全なドメイン名として扱います。

### Go言語の`crypto/x509`パッケージ

Go言語の標準ライブラリである`crypto/x509`パッケージは、X.509証明書のパース、検証、生成などの機能を提供します。SSL/TLS通信を行う`crypto/tls`パッケージの基盤として利用されており、証明書の信頼性検証やホスト名検証といったセキュリティ上重要な処理を担っています。

### Go言語の`strings`パッケージ

`strings`パッケージは、Go言語における文字列操作のための基本的な機能を提供します。このコミットに関連する関数は以下の通りです。

*   **`strings.Split(s, sep string) []string`**: 文字列`s`を区切り文字`sep`で分割し、部分文字列のスライスを返します。`s`が`sep`で終わる場合、結果のスライスの末尾に空文字列が追加されます。
*   **`strings.TrimSuffix(s, suffix string) string`**: 文字列`s`が`suffix`で終わる場合、その`suffix`を取り除いた文字列を返します。`s`が`suffix`で終わらない場合は、`s`をそのまま返します。

## 技術的詳細

### `matchHostnames`関数の役割と既存のロジック

`matchHostnames`関数は、Goの`crypto/x509`パッケージ内で、証明書に記載されたホスト名パターンと、実際に接続しようとしているホスト名が一致するかどうかを検証する役割を担っています。この関数は、ワイルドカード（`*`）を含むパターンにも対応しており、例えば`*.example.com`のようなパターンと`www.example.com`のようなホスト名を比較することができます。

修正前の`matchHostnames`関数は、ホスト名とパターンをドット（`.`）で分割し、それぞれのセグメントを比較することでマッチングを行っていました。この比較ロジックは、分割後のスライスの長さが一致することを前提としていました。

### 絶対ドメイン名がどのように問題を引き起こしていたか

前述の通り、絶対ドメイン名（例: `example.com.`）を`strings.Split`関数でドット（`.`）で分割すると、末尾のドットのために結果のスライスに余分な空文字列が追加されます。

例:
*   `strings.Split("example.com", ".")` -> `["example", "com"]` (長さ2)
*   `strings.Split("example.com.", ".")` -> `["example", "com", ""]` (長さ3)

一方、証明書内のホスト名パターンは通常、末尾のドットを含まない形式（例: `example.com`）で記述されます。したがって、`matchHostnames`関数がホスト名とパターンを分割した際、絶対ドメイン名が使用された場合のみ、ホスト名のスライスの長さがパターンのスライスの長さよりも1つ多くなっていました。

`matchHostnames`関数は、分割後のスライスの長さが異なる場合に即座に`false`を返すロジックを持っていたため、この長さの不一致が原因で、絶対ドメイン名が使用された場合に証明書検証が失敗していました。これは、DNSの仕様に準拠した絶対ドメイン名の使用を妨げる不具合でした。

### `strings.TrimSuffix(host, ".")`がどのように問題を解決するか

このコミットによる修正は、`matchHostnames`関数の冒頭で、入力された`host`文字列の末尾からドット（`.`）を削除するという非常にシンプルかつ効果的なものです。

```go
host = strings.TrimSuffix(host, ".")
```

この一行が追加されたことで、`example.com.`のような絶対ドメイン名が`matchHostnames`関数に渡された場合でも、内部処理に入る前に`example.com`という形式に正規化されます。これにより、`strings.Split`で分割した際のスライスの長さが、末尾にドットがない通常のドメイン名と同じになり、パターンとの比較が正しく行われるようになります。

この変更は、Goの`crypto/x509`パッケージが、DNSの絶対ドメイン名の表記を正しく解釈し、証明書検証の堅牢性を向上させる上で非常に重要です。

### この変更がセキュリティに与える影響

この修正は、セキュリティ上の脆弱性を直接修正するものではありませんが、SSL/TLS通信の信頼性と互換性を向上させます。絶対ドメイン名を使用する環境において、正当な証明書が不当に拒否されるという問題を解消することで、より広範なネットワーク構成でのGoアプリケーションの利用を可能にします。これにより、ユーザーは不必要な証明書エラーに遭遇することなく、安全な通信を確立できるようになります。

## コアとなるコードの解説

### `src/crypto/x509/verify.go`の変更

`matchHostnames`関数は、証明書のホスト名パターンと実際のホスト名を比較するGo言語の内部関数です。この関数の冒頭に以下の行が追加されました。

```go
host = strings.TrimSuffix(host, ".")
```

この変更の意図は、関数に渡される`host`文字列がもし絶対ドメイン名形式（末尾にドットが付いている）であった場合、その末尾のドットを削除して正規化することです。例えば、`"example.com."`というホスト名が渡された場合、この行が実行された後には`"example.com"`として扱われます。これにより、その後のホスト名とパターンの分割および比較ロジックが、末尾のドットの有無による不整合を起こすことなく、常に期待通りに機能するようになります。これは、DNSの仕様における絶対ドメイン名の扱いをGoの`x509`パッケージが正しく解釈するための重要な修正です。

### `src/crypto/x509/x509_test.go`の変更

テストファイルには、`matchHostnamesTests`という`matchHostnames`関数のテストケースを定義するスライスがあります。このスライスに、絶対ドメイン名に関する以下の新しいテストケースが追加されました。

```go
{"example.com", "example.com.", true},
{"*.example.com", "www.example.com.", true},
{"", ".", false},
{".", "", false},
{".", ".", false},
```

*   `{"example.com", "example.com.", true}`: これは、証明書パターンが`example.com`で、接続ホスト名が絶対ドメイン名の`example.com.`である場合に、マッチングが成功すること（`true`）を期待するテストです。このテストケースは、まさにこのコミットが解決しようとしている問題を直接検証します。
*   `{"*.example.com", "www.example.com.", true}`: ワイルドカードパターンと絶対ドメイン名の組み合わせでも、マッチングが成功することを確認します。
*   `{"", ".", false}`、`{".", "", false}`、`{".", ".", false}`: これらのテストケースは、空文字列や単一のドットのみのホスト名/パターンが、`matchHostnames`関数によって適切に処理され、マッチングが失敗すること（`false`）を検証します。これらは、エッジケースの挙動を明確にするために追加されました。

これらのテストケースの追加により、`matchHostnames`関数が絶対ドメイン名を正しく処理できるようになったことが保証され、将来の回帰を防ぐためのセーフティネットが提供されます。

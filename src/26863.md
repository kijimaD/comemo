# [インデックス 26863] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) フォーム変換において、関数の戻り値（`PPARAMOUT`変数）をSSA化する変更を導入しています。これにより、コンパイラは戻り値に対してより高度な最適化を適用できるようになります。しかし、Cgoが生成するコードとの互換性を保つため、Cgo関連のGoコードでは戻り値のSSA化を無効にするメカニズムも同時に導入されています。

変更されたファイルは以下の通りです。

*   `src/cmd/cgo/out.go`: CgoがGoコードを生成する際に、特定のプラグマを追加する変更。
*   `src/cmd/compile/internal/gc/lex.go`: コンパイラの字句解析器に関連するファイルで、新しいプラグマの定義と解析ロジックが追加されています。
*   `src/cmd/compile/internal/gc/ssa.go`: GoコンパイラのSSAバックエンドの主要なファイルで、`PPARAMOUT`変数のSSA化、書き戻し処理、Cgoの特殊ケース処理など、このコミットの核心となる変更が含まれています。

## 変更の背景

このコミットの主な目的は、GoコンパイラのSSAバックエンドにおいて、関数の戻り値（`PPARAMOUT`変数）をSSA (Static Single Assignment) 形式で扱えるようにすることです。

Goコンパイラは、コードを中間表現（IR）に変換し、そのIRに対して様々な最適化を適用します。SSA形式は、各変数が一度だけ代入されるという特性を持つIRであり、データフロー解析や最適化を非常に効率的に行うことを可能にします。Goコンパイラは、Go 1.7からSSAバックエンドを導入し、より強力な最適化を実現しています。

しかし、これまでのSSAバックエンドでは、関数の戻り値（`PPARAMOUT`）はSSA化の対象外でした。これは、戻り値が関数の実行中に複数回変更される可能性があったり、特にCgoのような特殊なケースでアドレスが直接操作される可能性があるため、SSAの原則に適合させるのが難しかったためと考えられます。

戻り値をSSA化することで、コンパイラは戻り値のライフタイムや使用箇所をより正確に追跡できるようになり、レジスタ割り当ての改善や不要なストア/ロード命令の削除など、より積極的な最適化が可能になります。これにより、生成されるバイナリのパフォーマンス向上やサイズ削減が期待されます。

一方で、Cgoが生成するGoコードは、Goの通常のセマンティクスとは異なる方法で戻り値のアドレスを操作する「トリッキーなゲーム」を行うことが知られています。具体的には、CgoはGoの戻り値のスタック上のアドレスをCコードに渡し、Cコードがそのアドレスを介して戻り値を変更する場合があります。このような挙動はSSAの前提と矛盾するため、Cgoが関与する場合には戻り値のSSA化を無効にする必要がありました。

このコミットは、これらの課題に対処し、SSAのメリットを`PPARAMOUT`変数にも拡大しつつ、Cgoとの互換性を維持するためのものです。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA (Static Single Assignment) 形式は、コンパイラ最適化において広く用いられる中間表現（IR）の一種です。その名の通り、「静的単一代入」という特性を持ちます。

*   **特性**: SSA形式では、プログラム中のすべての変数に対して、ただ一度だけ値が代入されます。もし同じ論理的な変数が複数回代入される場合、SSA形式ではそれぞれ異なる「バージョン」の変数として扱われます（例: `x1 = ...`, `x2 = ...`）。
*   **メリット**:
    *   **データフロー解析の簡素化**: 各変数の定義と使用が1対1に対応するため、変数の値がどこで定義され、どこで使用されているかを追跡するのが非常に容易になります。
    *   **最適化の促進**: 定数伝播、共通部分式除去、デッドコード削除、レジスタ割り当てなど、多くのコンパイラ最適化がSSA形式上で効率的に実装できます。
    *   **正確性**: 変数の値が不変であるため、プログラムの意味論をより正確に表現できます。
*   **Φ関数 (Phi function)**: 制御フローグラフ（CFG）において、複数のパスが合流する点（例: `if-else`文の終わりやループの終わり）で、同じ論理的な変数の異なるSSAバージョンを結合するためにΦ関数が導入されます。Φ関数は、どのパスから来たかに応じて適切なSSAバージョンを選択します。

Goコンパイラは、Go 1.7からSSAバックエンドを導入し、従来のAST (Abstract Syntax Tree) ベースの最適化から、より強力なSSAベースの最適化へと移行しました。

### 2. Goコンパイラの内部構造 (`cmd/compile/internal/gc`パッケージ)

Goコンパイラの主要部分は`cmd/compile`パッケージにあり、その中でも`internal/gc`はコンパイラのコアロジックを含んでいます。

*   **`Node`**: Goのソースコードの構文要素を表現する抽象構文木（AST）のノードです。変数、式、文、関数など、あらゆるプログラム要素が`Node`として表現されます。
*   **`Class`**: `Node`が表すシンボルの種類を示す列挙型です。
    *   `PPARAM`: 関数の入力引数（パラメータ）。
    *   `PPARAMOUT`: 関数の出力引数（戻り値）。Goでは戻り値もスタック上に配置され、引数と同様に扱われることがあります。
    *   `PAUTO`: ローカル変数。
    *   `PEXTERN`: 外部シンボル。
    *   `PPARAMREF`: クロージャによってキャプチャされた引数。
    *   `PFUNC`: 関数自体。
*   **`Pragma`**: Goのソースコード中に記述される特殊なコメント（例: `//go:noinline`）をコンパイラが解釈するためのフラグです。これらのプラグマは、コンパイラの挙動を制御したり、特定の最適化を指示したりするために使用されます。`lex.go`で定義され、字句解析時に認識されます。

### 3. Cgoとその「トリッキーなゲーム」

Cgoは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoプログラムを呼び出したりするためのメカニズムです。Cgoを使用すると、GoとCの間でデータを受け渡すことができます。

*   **Cgoの仕組み**: Cgoは、GoとCの間のインターフェースコードを生成します。Goの関数がCの関数を呼び出す場合、CgoはGoの型をCの型に変換し、Cの関数を呼び出し、その結果をGoの型に変換してGoコードに返します。
*   **戻り値のアドレス操作**: Cgoの「トリッキーなゲーム」とは、Goの関数がCの関数を呼び出す際に、Goの戻り値が配置されるスタック上のアドレスをCの関数に渡すことを指します。Cの関数は、そのアドレスを直接操作して戻り値を設定します。これは、Goの通常の関数呼び出し規約では、戻り値は関数が終了する際にレジスタやスタックの特定の場所にコピーされるのが一般的であるのに対し、CgoではC側が直接Goの戻り値のメモリを書き換えるという点で特殊です。
*   **SSAとの衝突**: SSA形式では、変数の値は一度だけ代入されるという前提があります。しかし、CgoがGoの戻り値のアドレスをCコードに渡し、Cコードがそのアドレスを介して戻り値を変更する場合、Goコンパイラから見ると、その戻り値はSSAの原則に反して複数回（Goコード内での初期化とCコードによる変更）代入されるように見える可能性があります。このような状況でSSA最適化を適用すると、予期せぬバグや誤ったコード生成につながる恐れがあるため、Cgoが関与する場合にはSSA化を無効にする必要があります。

### 4. Goの関数呼び出し規約と戻り値

Goの関数呼び出し規約では、関数の引数と戻り値は通常、スタック上に配置されます。

*   **スタックフレーム**: 関数が呼び出されると、その関数専用のスタックフレームが作成されます。このスタックフレームには、引数、ローカル変数、戻り値などが格納されます。
*   **`PPARAMOUT`の役割**: `PPARAMOUT`は、このスタックフレーム内の戻り値が格納される領域を指します。関数が値を返す際、その値は`PPARAMOUT`に対応するスタック上の位置に書き込まれます。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおける`PPARAMOUT`変数の扱いを根本的に変更し、Cgoとの互換性を確保するための複数の技術的変更を含んでいます。

### 1. `PPARAMOUT`変数のSSA化と書き戻しメカニズム

*   **SSA化の対象拡大**: 以前はSSA化の対象外だった`PPARAMOUT`変数も、`buildssa`関数内で`PPARAM`と同様に`ssa.OpAddr`を使ってアドレスが取得され、`s.decladdrs`に登録されるようになりました。これにより、コンパイラは関数の戻り値をSSA形式で追跡できるようになります。
*   **`state.returns`フィールドの追加**: `src/cmd/compile/internal/gc/ssa.go`の`state`構造体に`returns []*Node`という新しいフィールドが追加されました。これは、SSA化可能な`PPARAMOUT`変数を追跡するためのリストです。`buildssa`関数内で、`PPARAMOUT`かつ`canSSA`が真である変数（`n.Class == PPARAMOUT && s.canSSA(n)`）がこのリストに追加されます。
*   **`exit()`関数の導入**: 関数の終了処理をカプセル化するために、新しい`exit()`関数が導入されました。以前は`ORETURN`や`ORETJMP`のケースで直接行われていた終了処理（`s.stmts(s.exitCode)`, `s.endBlock()`など）が、この`exit()`関数に集約されました。
*   **書き戻しコードの追加**: `exit()`関数内で、`s.returns`リストに登録された各`PPARAMOUT`変数に対して、SSA形式で計算された最終的な値をスタック上の正しい位置に書き戻すためのコードが生成されます。具体的には、`ssa.OpAddr`でスタックアドレスを取得し、`ssa.OpStore`命令を使ってSSA値（`val`）をそのアドレスにストアします。これにより、SSA形式で最適化された戻り値が、関数の呼び出し元が期待するスタック上の位置に正しく配置されることが保証されます。

### 2. Cgoとの互換性のための`//go:cgo_unsafe_args`プラグマ

*   **新しいプラグマの導入**: Cgoが生成するGoコードにおいて、戻り値のSSA化を無効にするために、`//go:cgo_unsafe_args`という新しいプラグマが導入されました。
*   **`Pragma`型の拡張**: `src/cmd/compile/internal/gc/lex.go`において、`Pragma`型が`uint8`から`uint16`に拡張されました。これは、新しいプラグマフラグを追加するためのビット数を確保するためです。
*   **`CgoUnsafeArgs`定数の追加**: `Pragma`型に`CgoUnsafeArgs`という新しい定数（`1 << iota`でビットフラグとして定義）が追加され、`//go:cgo_unsafe_args`プラグマが検出された際にこのフラグがセットされるようになりました。
*   **`state.cgoUnsafeArgs`フィールドの追加**: `src/cmd/compile/internal/gc/ssa.go`の`state`構造体に`cgoUnsafeArgs bool`というフィールドが追加されました。`buildssa`関数内で、関数の`Pragma`に`CgoUnsafeArgs`フラグが立っている場合、このフィールドが`true`に設定されます。
*   **`canSSA`関数の変更**: `canSSA`関数（現在は`state`のメソッド`s.canSSA`）が変更され、`PPARAMOUT`変数がSSA化可能かどうかを判断する際に、以下の条件が追加されました。
    *   `hasdefer`（defer文が存在するかどうか）: defer文が存在する場合、戻り値はメモリ上に存在する必要があるため、SSA化は無効になります。
    *   `s.cgoUnsafeArgs`: `cgoUnsafeArgs`が`true`の場合（つまり、`//go:cgo_unsafe_args`プラグマが指定されている場合）、`PPARAMOUT`変数のSSA化は無効になります。これは、Cgoが戻り値のアドレスを直接操作する可能性があるためです。

### 3. その他の変更点

*   **`src/cmd/cgo/out.go`の変更**: CgoがGoコードを生成する際に、`//go:cgo_unsafe_args`プラグマを挿入するようになりました。これにより、Cgoが関与するGo関数では自動的に戻り値のSSA化が無効になります。
*   **`genValue`関数の変更**: `genValue`関数内で、`PPARAMOUT`変数も`obj.NAME_PARAM`として扱われるようになり、レジスタ割り当てやコード生成の際に適切に処理されるようになりました。
*   **`OCALLFUNC`の変更**: `gopanic`や`selectgo`に加えて、`block`も特殊な呼び出しとして扱われるようになりました。

これらの変更により、Goコンパイラは`PPARAMOUT`変数をSSA形式で効率的に処理できるようになり、Cgoとの互換性も維持しつつ、より高度な最適化の道が開かれました。

## 変更の背景

このコミットの主な目的は、GoコンパイラのSSAバックエンドにおいて、関数の戻り値（`PPARAMOUT`変数）をSSA (Static Single Assignment) 形式で扱えるようにすることです。

Goコンパイラは、コードを中間表現（IR）に変換し、そのIRに対して様々な最適化を適用します。SSA形式は、各変数が一度だけ代入されるという特性を持つIRであり、データフロー解析や最適化を非常に効率的に行うことを可能にします。Goコンパイラは、Go 1.7からSSAバックエンドを導入し、より強力な最適化を実現しています。

しかし、これまでのSSAバックエンドでは、関数の戻り値（`PPARAMOUT`）はSSA化の対象外でした。これは、戻り値が関数の実行中に複数回変更される可能性があったり、特にCgoのような特殊なケースでアドレスが直接操作される可能性があるため、SSAの原則に適合させるのが難しかったためと考えられます。

戻り値をSSA化することで、コンパイラは戻り値のライフタイムや使用箇所をより正確に追跡できるようになり、レジスタ割り当ての改善や不要なストア/ロード命令の削除など、より積極的な最適化が可能になります。これにより、生成されるバイナリのパフォーマンス向上やサイズ削減が期待されます。

一方で、Cgoが生成するGoコードは、Goの通常のセマンティクスとは異なる方法で戻り値のアドレスを操作する「トリッキーなゲーム」を行うことが知られています。具体的には、CgoはGoの戻り値のスタック上のアドレスをCコードに渡し、Cコードがそのアドレスを介して戻り値を変更する場合があります。このような挙動はSSAの前提と矛盾するため、Cgoが関与する場合には戻り値のSSA化を無効にする必要がありました。

このコミットは、これらの課題に対処し、SSAのメリットを`PPARAMOUT`変数にも拡大しつつ、Cgoとの互換性を維持するためのものです。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA (Static Single Assignment) 形式は、コンパイラ最適化において広く用いられる中間表現（IR）の一種です。その名の通り、「静的単一代入」という特性を持ちます。

*   **特性**: SSA形式では、プログラム中のすべての変数に対して、ただ一度だけ値が代入されます。もし同じ論理的な変数が複数回代入される場合、SSA形式ではそれぞれ異なる「バージョン」の変数として扱われます（例: `x1 = ...`, `x2 = ...`）。
*   **メリット**:
    *   **データフロー解析の簡素化**: 各変数の定義と使用が1対1に対応するため、変数の値がどこで定義され、どこで使用されているかを追跡するのが非常に容易になります。
    *   **最適化の促進**: 定数伝播、共通部分式除去、デッドコード削除、レジスタ割り当てなど、多くのコンパイラ最適化がSSA形式上で効率的に実装できます。
    *   **正確性**: 変数の値が不変であるため、プログラムの意味論をより正確に表現できます。
*   **Φ関数 (Phi function)**: 制御フローグラフ（CFG）において、複数のパスが合流する点（例: `if-else`文の終わりやループの終わり）で、同じ論理的な変数の異なるSSAバージョンを結合するためにΦ関数が導入されます。Φ関数は、どのパスから来たかに応じて適切なSSAバージョンを選択します。

Goコンパイラは、Go 1.7からSSAバックエンドを導入し、従来のAST (Abstract Syntax Tree) ベースの最適化から、より強力なSSAベースの最適化へと移行しました。

### 2. Goコンパイラの内部構造 (`cmd/compile/internal/gc`パッケージ)

Goコンパイラの主要部分は`cmd/compile`パッケージにあり、その中でも`internal/gc`はコンパイラのコアロジックを含んでいます。

*   **`Node`**: Goのソースコードの構文要素を表現する抽象構文木（AST）のノードです。変数、式、文、関数など、あらゆるプログラム要素が`Node`として表現されます。
*   **`Class`**: `Node`が表すシンボルの種類を示す列挙型です。
    *   `PPARAM`: 関数の入力引数（パラメータ）。
    *   `PPARAMOUT`: 関数の出力引数（戻り値）。Goでは戻り値もスタック上に配置され、引数と同様に扱われることがあります。
    *   `PAUTO`: ローカル変数。
    *   `PEXTERN`: 外部シンボル。
    *   `PPARAMREF`: クロージャによってキャプチャされた引数。
    *   `PFUNC`: 関数自体。
*   **`Pragma`**: Goのソースコード中に記述される特殊なコメント（例: `//go:noinline`）をコンパイラが解釈するためのフラグです。これらのプラグマは、コンパイラの挙動を制御したり、特定の最適化を指示したりするために使用されます。`lex.go`で定義され、字句解析時に認識されます。

### 3. Cgoとその「トリッキーなゲーム」

Cgoは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoプログラムを呼び出したりするためのメカニズムです。Cgoを使用すると、GoとCの間でデータを受け渡すことができます。

*   **Cgoの仕組み**: Cgoは、GoとCの間のインターフェースコードを生成します。Goの関数がCの関数を呼び出す場合、CgoはGoの型をCの型に変換し、Cの関数を呼び出し、その結果をGoの型に変換してGoコードに返します。
*   **戻り値のアドレス操作**: Cgoの「トリッキーなゲーム」とは、Goの関数がCの関数を呼び出す際に、Goの戻り値が配置されるスタック上のアドレスをCの関数に渡すことを指します。Cの関数は、そのアドレスを直接操作して戻り値を設定します。これは、Goの通常の関数呼び出し規約では、戻り値は関数が終了する際にレジスタやスタックの特定の場所にコピーされるのが一般的であるのに対し、CgoではC側が直接Goの戻り値のメモリを書き換えるという点で特殊です。
*   **SSAとの衝突**: SSA形式では、変数の値は一度だけ代入されるという前提があります。しかし、CgoがGoの戻り値のアドレスをCコードに渡し、Cコードがそのアドレスを介して戻り値を変更する場合、Goコンパイラから見ると、その戻り値はSSAの原則に反して複数回（Goコード内での初期化とCコードによる変更）代入されるように見える可能性があります。このような状況でSSA最適化を適用すると、予期せぬバグや誤ったコード生成につながる恐れがあるため、Cgoが関与する場合にはSSA化を無効にする必要があります。

### 4. Goの関数呼び出し規約と戻り値

Goの関数呼び出し規約では、関数の引数と戻り値は通常、スタック上に配置されます。

*   **スタックフレーム**: 関数が呼び出されると、その関数専用のスタックフレームが作成されます。このスタックフレームには、引数、ローカル変数、戻り値などが格納されます。
*   **`PPARAMOUT`の役割**: `PPARAMOUT`は、このスタックフレーム内の戻り値が格納される領域を指します。関数が値を返す際、その値は`PPARAMOUT`に対応するスタック上の位置に書き込まれます。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおける`PPARAMOUT`変数の扱いを根本的に変更し、Cgoとの互換性を確保するための複数の技術的変更を含んでいます。

### 1. `PPARAMOUT`変数のSSA化と書き戻しメカニズム

*   **SSA化の対象拡大**: 以前はSSA化の対象外だった`PPARAMOUT`変数も、`buildssa`関数内で`PPARAM`と同様に`ssa.OpAddr`を使ってアドレスが取得され、`s.decladdrs`に登録されるようになりました。これにより、コンパイラは関数の戻り値をSSA形式で追跡できるようになります。
*   **`state.returns`フィールドの追加**: `src/cmd/compile/internal/gc/ssa.go`の`state`構造体に`returns []*Node`という新しいフィールドが追加されました。これは、SSA化可能な`PPARAMOUT`変数を追跡するためのリストです。`buildssa`関数内で、`PPARAMOUT`かつ`canSSA`が真である変数（`n.Class == PPARAMOUT && s.canSSA(n)`）がこのリストに追加されます。
*   **`exit()`関数の導入**: 関数の終了処理をカプセル化するために、新しい`exit()`関数が導入されました。以前は`ORETURN`や`ORETJMP`のケースで直接行われていた終了処理（`s.stmts(s.exitCode)`, `s.endBlock()`など）が、この`exit()`関数に集約されました。
*   **書き戻しコードの追加**: `exit()`関数内で、`s.returns`リストに登録された各`PPARAMOUT`変数に対して、SSA形式で計算された最終的な値をスタック上の正しい位置に書き戻すためのコードが生成されます。具体的には、`ssa.OpAddr`でスタックアドレスを取得し、`ssa.OpStore`命令を使ってSSA値（`val`）をそのアドレスにストアします。これにより、SSA形式で最適化された戻り値が、関数の呼び出し元が期待するスタック上の位置に正しく配置されることが保証されます。

### 2. Cgoとの互換性のための`//go:cgo_unsafe_args`プラグマ

*   **新しいプラグマの導入**: Cgoが生成するGoコードにおいて、戻り値のSSA化を無効にするために、`//go:cgo_unsafe_args`という新しいプラグマが導入されました。
*   **`Pragma`型の拡張**: `src/cmd/compile/internal/gc/lex.go`において、`Pragma`型が`uint8`から`uint16`に拡張されました。これは、新しいプラグマフラグを追加するためのビット数を確保するためです。
*   **`CgoUnsafeArgs`定数の追加**: `Pragma`型に`CgoUnsafeArgs`という新しい定数（`1 << iota`でビットフラグとして定義）が追加され、`//go:cgo_unsafe_args`プラグマが検出された際にこのフラグがセットされるようになりました。
*   **`state.cgoUnsafeArgs`フィールドの追加**: `src/cmd/compile/internal/gc/ssa.go`の`state`構造体に`cgoUnsafeArgs bool`というフィールドが追加されました。`buildssa`関数内で、関数の`Pragma`に`CgoUnsafeArgs`フラグが立っている場合、このフィールドが`true`に設定されます。
*   **`canSSA`関数の変更**: `canSSA`関数（現在は`state`のメソッド`s.canSSA`）が変更され、`PPARAMOUT`変数がSSA化可能かどうかを判断する際に、以下の条件が追加されました。
    *   `hasdefer`（defer文が存在するかどうか）: defer文が存在する場合、戻り値はメモリ上に存在する必要があるため、SSA化は無効になります。
    *   `s.cgoUnsafeArgs`: `cgoUnsafeArgs`が`true`の場合（つまり、`//go:cgo_unsafe_args`プラグマが指定されている場合）、`PPARAMOUT`変数のSSA化は無効になります。これは、Cgoが戻り値のアドレスを直接操作する可能性があるためです。

### 3. その他の変更点

*   **`src/cmd/cgo/out.go`の変更**: CgoがGoコードを生成する際に、`//go:cgo_unsafe_args`プラグマを挿入するようになりました。これにより、Cgoが関与するGo関数では自動的に戻り値のSSA化が無効になります。
*   **`genValue`関数の変更**: `genValue`関数内で、`PPARAMOUT`変数も`obj.NAME_PARAM`として扱われるようになり、レジスタ割り当てやコード生成の際に適切に処理されるようになりました。
*   **`OCALLFUNC`の変更**: `gopanic`や`selectgo`に加えて、`block`も特殊な呼び出しとして扱われるようになりました。

これらの変更により、Goコンパイラは`PPARAMOUT`変数をSSA形式で効率的に処理できるようになり、Cgoとの互換性も維持しつつ、より高度な最適化の道が開かれました。

## コアとなるコードの解説

### 1. `src/cmd/cgo/out.go` の変更

*   `fmt.Fprint(fgo2, "//go:cgo_unsafe_args\n")`: CgoがGoのラッパー関数を生成する際に、`//go:cgo_unsafe_args`という特殊なプラグマコメントを挿入するように変更されました。このプラグマは、生成されたGo関数がCgoの特殊なメモリ操作に関与していることをコンパイラに伝え、戻り値のSSA化を無効にするためのトリガーとなります。

### 2. `src/cmd/compile/internal/gc/lex.go` の変更

*   `type Pragma uint16`: `Pragma`型が`uint8`から`uint16`に拡張されました。これは、既存のプラグマフラグに加えて、新しい`CgoUnsafeArgs`フラグを追加するために、より多くのビットが必要になったためです。
*   `CgoUnsafeArgs`: 新しい`Pragma`定数`CgoUnsafeArgs`が定義されました。これは、`//go:cgo_unsafe_args`プラグマに対応するビットフラグです。
*   `case "go:cgo_unsafe_args": l.pragma |= CgoUnsafeArgs`: 字句解析器が`//go:cgo_unsafe_args`コメントを検出した場合、現在の関数の`Pragma`フラグに`CgoUnsafeArgs`ビットをセットするように変更されました。

### 3. `src/cmd/compile/internal/gc/ssa.go` の変更

*   **`buildssa`関数**:
    *   `if fn.Func.Pragma&CgoUnsafeArgs != 0 { s.cgoUnsafeArgs = true }`: `buildssa`関数の開始時に、現在の関数ノード`fn`の`Pragma`フラグに`CgoUnsafeArgs`がセットされているかどうかを確認します。もしセットされていれば、`state`構造体の新しいフィールド`s.cgoUnsafeArgs`を`true`に設定します。これは、この関数がCgoによって生成されたものであり、戻り値のSSA化を特別に扱う必要があることを示します。
    *   `case PPARAM, PPARAMOUT:`: `PPARAM`（入力引数）だけでなく、`PPARAMOUT`（戻り値）も`s.decladdrs`に登録されるようになりました。これにより、これらの変数のアドレスがSSA形式で追跡可能になります。
    *   `if n.Class == PPARAMOUT && s.canSSA(n) { s.returns = append(s.returns, n) }`: `PPARAMOUT`変数であり、かつ`s.canSSA(n)`が`true`（SSA化可能）である場合、その`Node`を`s.returns`リストに追加します。このリストは、関数の最後にスタックに書き戻す必要があるSSA化された戻り値を追跡するために使用されます。
*   **`state`構造体**:
    *   `returns []*Node`: SSA化可能な`PPARAMOUT`変数を格納するリストです。
    *   `cgoUnsafeArgs bool`: 現在の関数が`//go:cgo_unsafe_args`プラグマを持っているかどうかを示すフラグです。
*   **`stmt`関数 (`ORETURN`, `ORETJMP`ケース)**:
    *   以前は`ORETURN`や`ORETJMP`の処理内で直接行われていた終了処理（`s.stmts(s.exitCode)`, `s.endBlock()`など）が、新しく導入された`s.exit()`関数を呼び出す形に変更されました。これにより、関数の終了処理が一元化され、`PPARAMOUT`の書き戻しロジックが組み込まれやすくなりました。
*   **`exit()`関数 (新設)**:
    *   この新しい関数は、関数の戻り値が処理される直前に実行されるコードを生成します。
    *   `s.stmts(s.exitCode)`: まず、通常の終了コード（deferなど）を実行します。
    *   `for _, n := range s.returns { ... }`: `s.returns`リストに登録された各`PPARAMOUT`変数についてループします。
        *   `aux := &ssa.ArgSymbol{Typ: n.Type, Node: n}`: 戻り値のシンボル情報を取得します。
        *   `addr := s.newValue1A(ssa.OpAddr, Ptrto(n.Type), aux, s.sp)`: 戻り値のスタック上のアドレスを取得します。
        *   `val := s.variable(n, n.Type)`: SSA形式で計算された、その戻り値の最終的な値を取得します。
        *   `s.vars[&memVar] = s.newValue3I(ssa.OpStore, ssa.TypeMem, n.Type.Size(), addr, val, s.mem())`: 取得したSSA値`val`を、スタック上のアドレス`addr`にストアする`ssa.OpStore`命令を生成します。これが、SSA化された戻り値を物理的なメモリ位置に書き戻す「writeback code」です。
    *   `m := s.mem(); b := s.endBlock(); b.Kind = ssa.BlockRet; b.Control = m; return b`: 最終的なメモリ状態を制御値として持つ`BlockRet`ブロックを生成し、関数の制御フローを終了させます。
*   **`s.canSSA(n *Node) bool`関数 (変更)**:
    *   この関数は、特定の`Node`がSSA化可能かどうかを判断します。以前はグローバル関数でしたが、`state`のメソッドになり、`state`のフィールド（`s.cgoUnsafeArgs`など）にアクセスできるようになりました。
    *   `case PPARAMOUT:`: `PPARAMOUT`の場合のSSA化可能性の判断ロジックが追加されました。
        *   `if hasdefer { return false }`: defer文が存在する場合、戻り値はメモリ上に存在する必要があるため、SSA化は無効になります。
        *   `if s.cgoUnsafeArgs { return false }`: `s.cgoUnsafeArgs`が`true`の場合（Cgoが関与している場合）、戻り値のSSA化は無効になります。これは、Cgoが戻り値のアドレスを直接操作する可能性があるためです。
*   **`genValue`関数**:
    *   `if n.Class == PPARAM || n.Class == PPARAMOUT { ... }`: `PPARAM`だけでなく`PPARAMOUT`も`obj.NAME_PARAM`として扱われるようになり、オブジェクトファイル生成時に適切に処理されるようになりました。

これらの変更により、Goコンパイラは`PPARAMOUT`変数をSSA形式で扱い、最適化を適用できるようになりました。同時に、Cgoの特殊なケースではSSA化を無効にすることで、既存のCgoコードとの互換性も維持されています。

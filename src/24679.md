# [インデックス 24679] ファイルの概要

このコミットは、Goコンパイラ（`gc`）における定数演算での右シフト（`rsh`）の挙動を修正するものです。具体的には、右シフト演算子の右オペランドが非常に大きな値である場合に発生していた「stupid shift」エラーを解消し、`gotype`ツールとの一貫性を保つことを目的としています。

## 元コミット内容

このコミットは、Goコンパイラ（`gc`）が定数演算における大きな右シフト（`rsh`）を許可するように変更します。

現状では、`var v = 0 >> 1000` のような式は、`gc`によって「stupid shift」エラーとして拒否されていました。しかし、`gotype`ツールはこの種の式を正常にコンパイルしていました。

この不整合を解消するため、issueトラッカーでRobert Griesemer（gri）氏が提案したように、右シフト演算子の右オペランドとして任意の有効な`uint`値を許可するように変更されます。

これにより、Issue #11328 が修正されます。

## 変更の背景

Go言語のコンパイラ（`gc`）と型チェッカー（`gotype`）の間で、定数に対するビットシフト演算の扱いに関して不整合が存在していました。具体的には、右シフト演算子（`>>`）の右オペランドが非常に大きな定数値である場合、`gc`はこれを無効な操作と判断し、「stupid shift」というエラーを発生させていました。しかし、`gotype`はこのようなケースでもエラーとせず、正常に処理していました。

この不整合は、開発者がコードの挙動を予測しにくくするだけでなく、ツール間の互換性の問題を引き起こす可能性がありました。Go言語の設計哲学の一つに「シンプルさと一貫性」があり、このようなツールの挙動の不一致は望ましくありませんでした。

Go言語の仕様では、シフト演算の右オペランドは符号なし整数型（`uint`）として扱われ、その値はシフトされるオペランドのビット幅を超えることも許容されます。例えば、64ビット整数を1000ビット右シフトした場合、結果は0になることが期待されます。しかし、`gc`は内部的な制約により、右オペランドが特定のしきい値（`Mpprec`）を超えるとエラーとしていました。

このコミットは、この`gc`の内部的な制約を緩和し、Go言語の仕様と`gotype`の挙動に合わせることで、定数シフト演算の一貫性と正確性を向上させることを目的としています。

## 前提知識の解説

### Go言語の定数と型なし定数

Go言語には、数値、真偽値、文字列の定数があります。特に重要なのは「型なし定数（untyped constants）」の概念です。Goの定数は、明示的に型が指定されない限り、型を持ちません。これにより、より柔軟な演算が可能になります。例えば、`1000`は型なしの整数定数であり、必要に応じて`int`、`int32`、`int64`などに変換されます。

### ビットシフト演算子（`>>`）

Go言語における右シフト演算子`>>`は、左オペランドのビットパターンを右オペランドで指定された回数だけ右に移動させます。
- 整数型の場合、右シフトは通常、値を2のべき乗で割ることに相当します。
- 符号なし整数（`uint`）の場合、右シフトは常に論理シフト（左側に0が挿入される）です。
- 符号付き整数（`int`）の場合、右シフトは算術シフト（左側に符号ビットが挿入される）です。
- Go言語の仕様では、シフト量の右オペランドは符号なし整数型として扱われます。シフト量がシフトされる値のビット幅以上の場合、結果は0になります（例: `1 << 64` は `0`）。

### `gc`と`gotype`

- **`gc` (Go Compiler)**: Go言語の公式コンパイラです。Goのソースコードを機械語に変換する役割を担います。コンパイル時に型チェック、最適化、コード生成などを行います。本コミットの文脈では、定数演算の評価も`gc`の役割の一部です。
- **`gotype`**: Go言語のソースコードの型チェックを行うツールです。コンパイルは行わず、コードの構文と型の一貫性を検証します。`gotype`は`gc`よりも緩やかなチェックを行うことがあり、本件のように`gc`がエラーとするコードを`gotype`が許容するケースがありました。

### `Mpprec`

`Mpprec`は、Goコンパイラの内部で使用される多倍長整数演算ライブラリ（`math/big`パッケージの内部的な前身のようなもの）における精度の概念に関連する定数です。これは、コンパイル時に定数値を扱う際の内部的なビット幅や精度の上限を示していました。このコミット以前は、右シフトの量が`Mpprec`を超えると、コンパイラはこれを「過剰なシフト」とみなし、エラーとしていました。

## 技術的詳細

このコミットの核心は、Goコンパイラ（`gc`）が定数右シフト演算の右オペランドを評価するロジックの変更にあります。

変更前の`src/cmd/compile/internal/gc/mparith2.go`の`mprshfixfix`関数には、以下のようなエラーチェックがありました。

```go
	s := Mpgetfix(b)
	if s < 0 || s >= Mpprec {
		Yyerror("stupid shift: %d", s)
		if a.Val.Sign() < 0 {
			Mpmovecfix(a, -1)
		} else {
			Mpmovecfix(a, 0)
		}
		return
	}
```

ここで、`s`は右シフトの量（右オペランドの値）を表します。`Mpprec`はコンパイラ内部で定義された多倍長整数演算の精度に関する定数で、通常はGoがサポートする最大整数型（`uint64`）のビット幅（64）よりも大きな値（例えば256ビットなど）が設定されていました。

変更前のロジックでは、シフト量`s`が負の値であるか、または`Mpprec`以上である場合に「stupid shift」エラーを発生させていました。これは、コンパイラが非常に大きなシフト量を処理する際に、内部的な多倍長整数表現の限界を超えてしまうことを懸念していたか、あるいは単にそのようなシフトが意味をなさない（結果が常に0になる）と判断していたためと考えられます。

しかし、Go言語の仕様では、シフト量は`uint`型として扱われ、その値がシフトされるオペランドのビット幅を超えても問題ありません。例えば、`0 >> 1000`のような式は、結果が`0`になることが期待されます。`gotype`はこの仕様に従って正しく処理していました。

このコミットでは、エラーチェックの条件から`s >= Mpprec`が削除されました。

```go
	s := Mpgetfix(b)
	if s < 0 { // 変更点: s >= Mpprec の条件が削除された
		Yyerror("stupid shift: %d", s)
		if a.Val.Sign() < 0 {
			Mpmovecfix(a, -1)
		} else {
			Mpmovecfix(a, 0)
		}
		return
	}
```

この変更により、シフト量`s`が負の値である場合のみエラーが発生するようになります。シフト量が`Mpprec`以上であっても、それが正の値であればエラーとはならず、Go言語の仕様に従って演算が続行されます。結果として、`0 >> 1000`のような式は、正しく`0`と評価されるようになります。

この修正は、コンパイラが定数演算をより正確に、かつGo言語の仕様に準拠して処理するための重要な改善です。

## コアとなるコードの解説

このコミットの主要な変更は、`src/cmd/compile/internal/gc/mprith2.go`ファイル内の`mprshfixfix`関数にあります。この関数は、Goコンパイラが定数に対する右シフト演算（`>>`）を処理する際に呼び出されます。

変更前は、右シフト量`s`が負の値であるか、または`Mpprec`（多倍長整数演算の内部精度を表す定数）以上である場合に、「stupid shift」というエラーを報告していました。この`Mpprec`は、コンパイラが内部的に扱う数値のビット幅の限界を示すものでした。例えば、`uint64`の最大ビット幅は64ですが、`Mpprec`はそれよりも大きな値（例えば256）に設定されていることが一般的です。

Go言語の仕様では、シフト演算の右オペランドは符号なし整数型として扱われ、その値がシフトされるオペランドのビット幅を超えても問題ありません。例えば、`0 >> 1000`のような式は、結果が`0`になることが期待されます。これは、どんな値も1000ビット右にシフトすれば、最終的にすべてのビットが右端から押し出されて`0`になるためです。

このコミットでは、エラーチェックの条件から`s >= Mpprec`が削除されました。これにより、右シフト量`s`が負の値でない限り、たとえ`Mpprec`を超えていてもエラーとは見なされなくなりました。この変更は、コンパイラがGo言語の仕様に厳密に従い、非常に大きなシフト量を持つ定数演算も正しく処理できるようにすることを目的としています。

具体的には、`1e100 >> 1000`のような式が、以前は`gc`によってエラーとされていたものが、この変更後は正しく`0`と評価されるようになります。同様に、`1e302 >> 1000`のような式も、特定の大きな値（この場合は`9`）として正しく評価されるようになります。これらのケースは、`test/const.go`に追加された新しいテストケースで検証されています。

この修正により、`gc`と`gotype`の間で存在していた定数シフト演算の挙動の不整合が解消され、Go言語のツールチェーン全体の一貫性が向上しました。

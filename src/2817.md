## 元コミット内容

このコミットは、Go言語の関数リテラル（クロージャ）の等価性比較のセマンティクスを統一することを目的としています。以前は、キャプチャする変数がない関数リテラル（例: `func() {}`）は、異なる実行で生成されても `==` 演算子で比較すると `true` になる可能性がありました。しかし、変数をキャプチャする関数リテラル（例: `func() {x++}`）は、常に `false` となっていました。この不整合を解消するため、すべての関数リテラル式がメモリを割り当てるように変更されました。これにより、`make(map[int]int) != make(map[int]int)` と同様に、異なる実行で生成された関数リテラルは常に `false` と評価されるようになります。

## 変更の背景

Go言語の初期の設計では、関数リテラル（クロージャ）の等価性比較に関して一貫性のない挙動が存在していました。

1.  **変数をキャプチャするクロージャ**: `func() { x++ }` のように外部スコープの変数をキャプチャするクロージャは、実行時にヒープ上にクロージャオブジェクトを生成し、そのオブジェクトへのポインタが関数の値となります。したがって、異なる実行で生成されたクロージャは異なるメモリ位置を指すため、`==` 演算子で比較すると常に `false` となります。これは直感的で、`make` で生成されるマップやスライスが常に新しいオブジェクトを返すのと同様の挙動です。

2.  **変数をキャプチャしないクロージャ**: `func() {}` のように外部スコープの変数をキャプチャしないクロージャは、最適化の一環として、コンパイラがヒープ割り当てを省略し、静的な関数ポインタとして扱われることがありました。この場合、同じコードを持つ複数の `func() {}` が同じ静的アドレスを指すことがあり、`==` 演算子で比較すると `true` になる可能性がありました。

この不整合は、プログラマが関数の等価性を判断する際に混乱を招く可能性がありました。特に、関数がキャプチャする変数があるかないかによって `==` の挙動が変わることは、予測しにくいバグの原因となり得ます。このコミットは、この不整合を解消し、すべての関数リテラルが「新しいインスタンス」として扱われるようにすることで、より予測可能で一貫性のあるセマンティクスを提供することを目的としています。これにより、関数の等価性比較は、それが「同じ関数リテラルの同じ実行によって生成されたものか」という、より厳密な意味を持つようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラ/ランタイムに関する知識が必要です。

1.  **関数リテラルとクロージャ**:
    *   **関数リテラル**: Goにおける匿名関数です。`func(args) { ... }` の形式で記述されます。
    *   **クロージャ**: 関数リテラルが、それが定義された外部スコープの変数を「キャプチャ」して利用する際に形成される概念です。キャプチャされた変数は、クロージャが実行される際にその状態を保持します。Goでは、キャプチャされた変数は通常、ヒープ上に割り当てられ、クロージャオブジェクトの一部として参照されます。

2.  **Goの関数値**:
    *   Goにおいて、関数は第一級オブジェクトであり、変数に代入したり、引数として渡したり、戻り値として返したりできます。
    *   関数値は、実際には関数コードへのポインタと、クロージャの場合はキャプチャされた変数へのポインタ（環境ポインタ）の組み合わせで構成されます。

3.  **`==` 演算子による関数値の比較**:
    *   Goの仕様では、関数値は `==` および `!=` 演算子で比較できます。
    *   比較のセマンティクスは、このコミット以前は「関数が同じエントリポイントを持ち、かつ同じ環境ポインタを持つ場合に等しい」と解釈されることが多かったです。しかし、キャプチャする変数がない場合は環境ポインタが存在しないため、エントリポイントのみで比較されるという特殊なケースがありました。
    *   このコミットにより、すべての関数リテラルがユニークなクロージャオブジェクトを生成するため、`==` 演算子は「同じメモリ上のクロージャオブジェクトを指しているか」という、より厳密なポインタ比較に近い意味を持つようになります。

4.  **Goコンパイラ (`gc`)**:
    *   `src/cmd/gc/dcl.c` は、Goコンパイラのフロントエンドの一部であり、宣言（declaration）の処理を担当します。関数リテラルの解析、型チェック、およびクロージャに必要な変数のキャプチャメカニズムの構築などが行われます。
    *   このファイルでは、関数リテラルがクロージャとしてどのように表現され、どのような情報がランタイムに渡されるかが決定されます。

5.  **Goランタイム (`runtime`)**:
    *   `src/pkg/runtime/386/closure.c` および `src/pkg/runtime/amd64/closure.c` は、それぞれ32ビットx86および64ビットx86アーキテクチャ向けのGoランタイムの一部です。
    *   これらのファイルには、クロージャの実際のメモリ割り当て、キャプチャされた変数のコピー、およびクロージャの実行に必要なスタブコードの生成など、低レベルのアセンブリコードやCコードが含まれています。
    *   `sys·closure` のような関数は、Goコードからクロージャを生成する際にランタイムが呼び出す内部関数です。

6.  **ヒープ割り当て**:
    *   プログラムが実行時に動的にメモリを要求し、そのメモリがプログラムの寿命を超えて存続する必要がある場合に、ヒープメモリが使用されます。Goでは、`make` で作成されるマップ、スライス、チャネル、およびクロージャがヒープに割り当てられる典型的な例です。
    *   ヒープに割り当てられたオブジェクトは、ガベージコレクタによって管理されます。

これらの知識を前提として、このコミットがGoの関数リテラルの挙動にどのような影響を与え、なぜそれが重要であるかを深く理解することができます。

## 技術的詳細

このコミットの技術的詳細は、Goコンパイラ (`gc`) とランタイム (`runtime`) の両方におけるクロージャの生成と管理の変更に集約されます。

### `src/cmd/gc/dcl.c` における変更

このファイルはGoコンパイラの宣言処理部分であり、関数リテラルがどのように内部的に表現されるかを決定します。

**変更前**:
`funclit1` 関数内で、`func->cvars == nil` (つまり、キャプチャする変数が存在しないクロージャ) の場合に、特別な最適化パスが存在しました。このパスでは、クロージャオブジェクトのヒープ割り当てをスキップし、関数リテラルを直接そのコードエントリポイントへのポインタとして扱う可能性がありました。これにより、同じコードを持つキャプチャなしの関数リテラルが同じアドレスを指し、`==` 比較で `true` になることがありました。

具体的には、以下のコードブロックが削除されています。

```c
	// if there's no closure, we can use f directly
	if(func->cvars == nil)
		return f;
```

この削除により、`func->cvars == nil` の場合でも、その後のクロージャオブジェクトを構築する共通のパスに進むようになります。

**変更後**:
`func->cvars == nil` の条件分岐が削除されたことで、すべての関数リテラル（キャプチャする変数があるかどうかにかかわらず）が、クロージャオブジェクトを構築するための共通のロジックを通るようになります。このロジックは、クロージャの型を定義し、ランタイムがクロージャオブジェクトを生成するために必要な情報を準備します。

これにより、たとえキャプチャする変数がなくても、各関数リテラルの実行は常に新しいクロージャオブジェクト（メモリ上のユニークなエンティティ）を生成するようにコンパイラが指示することになります。結果として、異なる実行で生成された関数リテラルは、たとえコードが同一であっても、異なるメモリ位置を指すため、`==` 比較で `false` となります。

### `src/pkg/runtime/386/closure.c` および `src/pkg/runtime/amd64/closure.c` における変更

これらのファイルは、Goランタイムが実際にクロージャオブジェクトをヒープに割り当て、キャプチャされた変数をコピーし、実行可能なクロージャスタブを生成する低レベルのコードを含んでいます。

**変更前**:
`sys·closure` 関数は、クロージャオブジェクトのサイズ (`siz`) と関数コードへのポインタ (`fn`)、およびキャプチャされた変数 (`arg0`) を受け取ります。以前は、`siz` が0であっても、キャプチャされた変数をスタックにコピーし、スタックポインタを調整するアセンブリ命令が常に生成されていました。これは、`siz` が0の場合には不要な操作でした。

**変更後**:
`sys·closure` 関数内で、キャプチャされた変数のコピーとスタックポインタの調整を行うアセンブリコードの生成が、`if(siz > 0)` の条件ブロックで囲まれるようになりました。

```c
	if(siz > 0) {
		mcpy(q, (byte*)&arg0, siz);

		// SUBL $siz, SP (or SUBQ $siz, SP for amd64)
		// ... (assembly instructions for stack manipulation and data copy)
	}
```

この変更は、`dcl.c` で導入された「すべての関数リテラルがクロージャオブジェクトを生成する」というセマンティクスと整合性を保ちつつ、最適化を図るものです。`siz` が0の場合（つまり、キャプチャする変数がない場合）でもクロージャオブジェクト自体は生成されますが、そのオブジェクト内にコピーすべきデータがないため、不要なメモリコピーやスタック操作のアセンブリ命令はスキップされます。これにより、ランタイムの効率性を維持しつつ、一貫した等価性セマンティクスを実現しています。

### 全体的な影響

この変更により、Go言語における関数リテラルの等価性比較は、よりシンプルで予測可能なルールに従うようになります。

*   `func() { ... }` のような関数リテラルは、それが評価されるたびに新しい、ユニークな関数値（クロージャオブジェクト）を生成します。
*   したがって、`f1 := func() {}; f2 := func(){};` のように異なる場所で定義されたり、同じ定義でも異なる実行で生成されたりした関数値は、常に `f1 != f2` となります。
*   唯一 `f1 == f2` となるのは、`f1 := func(){}; f2 := f1;` のように、同じ関数値が別の変数に代入された場合のみです。

これは、Goのマップやスライスなどの参照型が `make` で生成されるたびに新しいインスタンスを返す挙動と完全に一致し、言語全体の一貫性を高めます。

## コアとなるコードの解説

### `src/cmd/gc/dcl.c` の変更点

`src/cmd/gc/dcl.c` の `funclit1` 関数は、Goコンパイラが関数リテラルを処理する主要な場所です。この関数は、関数リテラルのAST (Abstract Syntax Tree) を受け取り、それをコンパイル可能な内部表現に変換します。

削除されたコードブロック:
```c
	// if there's no closure, we can use f directly
	if(func->cvars == nil)
		return f;
```
この `if` 文は、関数リテラルが外部スコープの変数を一つもキャプチャしていない場合 (`func->cvars == nil`) に、特別な最適化を適用していました。具体的には、クロージャオブジェクトをヒープに割り当てる代わりに、コンパイルされた関数コードへの直接的なポインタ `f` を関数値として返していました。これにより、同じコードを持つキャプチャなしの関数リテラルは、同じ静的アドレスを指すことになり、`==` 比較で `true` となる可能性がありました。

このブロックが削除されたことで、`func->cvars == nil` の場合でも、関数リテラルは常にその後の共通のパスを通るようになります。この共通パスでは、クロージャの型情報が構築され、ランタイムがヒープ上にクロージャオブジェクトを割り当てるための準備が行われます。結果として、キャプチャする変数がなくても、各関数リテラルの評価は常に新しい、ユニークなクロージャオブジェクトを生成するようになります。

### `src/pkg/runtime/386/closure.c` および `src/pkg/runtime/amd64/closure.c` の変更点

これらのファイルは、Goランタイムが実際にクロージャオブジェクトを生成する低レベルの実装を含んでいます。`sys·closure` 関数は、Goコードからクロージャが生成される際に呼び出されるランタイム関数です。

変更されたコードブロック（例: `src/pkg/runtime/386/closure.c`）:
```c
// 変更前:
// mcpy(q, (byte*)&arg0, siz);
// ... (assembly instructions for stack manipulation and data copy)

// 変更後:
	if(siz > 0) {
		mcpy(q, (byte*)&arg0, siz);

		// SUBL $siz, SP
		*p++ = 0x81;
		*p++ = 0xec;
		*(uint32*)p = siz;
		p += 4;

		// MOVL $q, SI
		*p++ = 0xbe;
		*(byte**)p = q;
		p += 4;

		// MOVL SP, DI
		*p++ = 0x89;
		*p++ = 0xe7;

		// CLD
		*p++ = 0xfc;

		if(siz <= 4*4) {
			for(i=0; i<siz; i+=4) {
				// MOVSL
				*p++ = 0xa5;
			}
		} else {
			// MOVL $(siz/4), CX  [32-bit immediate siz/4]
			*p++ = 0xc7;
			*p++ = 0xc1;
			*(uint32*)p = siz/4;
			p += 4;

			// REP; MOVSL
			*p++ = 0xf3;
			*p++ = 0xa5;
		}
	}
```
`sys·closure` 関数は、クロージャオブジェクトのメモリを割り当て (`mal(n)`)、そのポインタを `ret` に格納します。`q` は、クロージャオブジェクトの末尾に配置されるキャプチャされた変数データの開始アドレスを指します。`siz` は、キャプチャされた変数データの合計サイズです。

変更前は、`siz` の値にかかわらず、`mcpy` を使って `arg0` (キャプチャされた変数) を `q` にコピーし、その後、スタックポインタを調整し、`MOVSL` (Move String Long) や `REP; MOVSL` (Repeat Move String Long) といったアセンブリ命令を使ってデータをコピーするコードが常に生成されていました。

変更後は、これらのデータコピーとスタック操作のアセンブリコード生成が `if(siz > 0)` ブロックで囲まれています。これは、`dcl.c` の変更によって、キャプチャする変数がないクロージャ (`siz == 0`) でもクロージャオブジェクト自体は生成されるようになったものの、実際にコピーすべきデータがない場合には、これらの低レベルな操作をスキップすることでランタイムの効率を維持するためです。

### `test/closure.go` の変更点

```go
func newfunc() (func(int) int) {
	return func(x int) int { return x }
}

// ...

	x, y := newfunc(), newfunc();
	if x == y {
		panicln("newfunc returned same func");
	}
	if x(1) != 1 || y(2) != 2 {
		panicln("newfunc returned broken funcs");
	}
```
このテストコードは、このコミットの意図を明確に示しています。`newfunc` は、外部変数をキャプチャしないシンプルな関数リテラルを返します。`x` と `y` は、`newfunc()` を2回呼び出すことで、それぞれ異なる実行で生成された関数リテラルを受け取ります。

変更後のセマンティクスでは、これらの2つの関数値 `x` と `y` は、たとえ同じコードであっても、異なるクロージャオブジェクトを指すため、`x == y` は常に `false` となるべきです。もし `true` になった場合、`panicln` が呼び出され、テストが失敗します。これにより、新しい一貫した等価性セマンティクスが正しく実装されていることが検証されます。

## 元コミット内容

このコミットは、Go言語の関数リテラル（クロージャ）の等価性比較のセマンティクスを統一することを目的としています。以前は、キャプチャする変数がない関数リテラル（例: `func() {}`）は、異なる実行で生成されても `==` 演算子で比較すると `true` になる可能性がありました。しかし、変数をキャプチャする関数リテラル（例: `func() {x++}`）は、常に `false` となっていました。この不整合を解消するため、すべての関数リテラル式がメモリを割り当てるように変更されました。これにより、`make(map[int]int) != make(map[int]int)` と同様に、異なる実行で生成された関数リテラルは常に `false` と評価されるようになります。

## 変更の背景

Go言語の初期の設計では、関数リテラル（クロージャ）の等価性比較に関して一貫性のない挙動が存在していました。

1.  **変数をキャプチャするクロージャ**: `func() { x++ }` のように外部スコープの変数をキャプチャするクロージャは、実行時にヒープ上にクロージャオブジェクトを生成し、そのオブジェクトへのポインタが関数の値となります。したがって、異なる実行で生成されたクロージャは異なるメモリ位置を指すため、`==` 演算子で比較すると常に `false` となります。これは直感的で、`make` で生成されるマップやスライスが常に新しいオブジェクトを返すのと同様の挙動です。

2.  **変数をキャプチャしないクロージャ**: `func() {}` のように外部スコープの変数をキャプチャしないクロージャは、最適化の一環として、コンパイラがヒープ割り当てを省略し、静的な関数ポインタとして扱われることがありました。この場合、同じコードを持つ複数の `func() {}` が同じ静的アドレスを指すことがあり、`==` 演算子で比較すると `true` になる可能性がありました。

この不整合は、プログラマが関数の等価性を判断する際に混乱を招く可能性がありました。特に、関数がキャプチャする変数があるかないかによって `==` の挙動が変わることは、予測しにくいバグの原因となり得ます。このコミットは、この不整合を解消し、すべての関数リテラルが「新しいインスタンス」として扱われるようにすることで、より予測可能で一貫性のあるセマンティクスを提供することを目的としています。これにより、関数の等価性比較は、それが「同じ関数リテラルの同じ実行によって生成されたものか」という、より厳密な意味を持つようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラ/ランタイムに関する知識が必要です。

1.  **関数リテラルとクロージャ**:
    *   **関数リテラル**: Goにおける匿名関数です。`func(args) { ... }` の形式で記述されます。
    *   **クロージャ**: 関数リテラルが、それが定義された外部スコープの変数を「キャプチャ」して利用する際に形成される概念です。キャプチャされた変数は、クロージャが実行される際にその状態を保持します。Goでは、キャプチャされた変数は通常、ヒープ上に割り当てられ、クロージャオブジェクトの一部として参照されます。

2.  **Goの関数値**:
    *   Goにおいて、関数は第一級オブジェクトであり、変数に代入したり、引数として渡したり、戻り値として返したりできます。
    *   関数値は、実際には関数コードへのポインタと、クロージャの場合はキャプチャされた変数へのポインタ（環境ポインタ）の組み合わせで構成されます。

3.  **`==` 演算子による関数値の比較**:
    *   Goの仕様では、関数値は `==` および `!=` 演算子で比較できます。
    *   比較のセマンティクスは、このコミット以前は「関数が同じエントリポイントを持ち、かつ同じ環境ポインタを持つ場合に等しい」と解釈されることが多かったです。しかし、キャプチャする変数がない場合は環境ポインタが存在しないため、エントリポイントのみで比較されるという特殊なケースがありました。
    *   このコミットにより、すべての関数リテラルがユニークなクロージャオブジェクトを生成するため、`==` 演算子は「同じメモリ上のクロージャオブジェクトを指しているか」という、より厳密なポインタ比較に近い意味を持つようになります。

4.  **Goコンパイラ (`gc`)**:
    *   `src/cmd/gc/dcl.c` は、Goコンパイラのフロントエンドの一部であり、宣言（declaration）の処理を担当します。関数リテラルの解析、型チェック、およびクロージャに必要な変数のキャプチャメカニズムの構築などが行われます。
    *   このファイルでは、関数リテラルがクロージャとしてどのように表現され、どのような情報がランタイムに渡されるかが決定されます。

5.  **Goランタイム (`runtime`)**:
    *   `src/pkg/runtime/386/closure.c` および `src/pkg/runtime/amd64/closure.c` は、それぞれ32ビットx86および64ビットx86アーキテクチャ向けのGoランタイムの一部です。
    *   これらのファイルには、クロージャの実際のメモリ割り当て、キャプチャされた変数のコピー、およびクロージャの実行に必要なスタブコードの生成など、低レベルのアセンブリコードやCコードが含まれています。
    *   `sys·closure` のような関数は、Goコードからクロージャを生成する際にランタイムが呼び出す内部関数です。

6.  **ヒープ割り当て**:
    *   プログラムが実行時に動的にメモリを要求し、そのメモリがプログラムの寿命を超えて存続する必要がある場合に、ヒープメモリが使用されます。Goでは、`make` で作成されるマップ、スライス、チャネル、およびクロージャがヒープに割り当てられる典型的な例です。
    *   ヒープに割り当てられたオブジェクトは、ガベージコレクタによって管理されます。

これらの知識を前提として、このコミットがGoの関数リテラルの挙動にどのような影響を与え、なぜそれが重要であるかを深く理解することができます。

## 技術的詳細

このコミットの技術的詳細は、Goコンパイラ (`gc`) とランタイム (`runtime`) の両方におけるクロージャの生成と管理の変更に集約されます。

### `src/cmd/gc/dcl.c` における変更

このファイルはGoコンパイラの宣言処理部分であり、関数リテラルがどのように内部的に表現されるかを決定します。

**変更前**:
`funclit1` 関数内で、`func->cvars == nil` (つまり、キャプチャする変数が存在しないクロージャ) の場合に、特別な最適化パスが存在しました。このパスでは、クロージャオブジェクトのヒープ割り当てをスキップし、関数リテラルを直接そのコードエントリポイントへのポインタとして扱う可能性がありました。これにより、同じコードを持つキャプチャなしの関数リテラルが同じアドレスを指し、`==` 比較で `true` になることがありました。

具体的には、以下のコードブロックが削除されています。

```c
	// if there's no closure, we can use f directly
	if(func->cvars == nil)
		return f;
```

この削除により、`func->cvars == nil` の場合でも、その後のクロージャオブジェクトを構築する共通のパスに進むようになります。

**変更後**:
`func->cvars == nil` の条件分岐が削除されたことで、すべての関数リテラル（キャプチャする変数があるかどうかにかかわらず）が、クロージャオブジェクトを構築するための共通のロジックを通るようになります。このロジックは、クロージャの型を定義し、ランタイムがクロージャオブジェクトを生成するために必要な情報を準備します。

これにより、たとえキャプチャする変数がなくても、各関数リテラルの実行は常に新しいクロージャオブジェクト（メモリ上のユニークなエンティティ）を生成するようにコンパイラが指示することになります。結果として、異なる実行で生成された関数リテラルは、たとえコードが同一であっても、異なるメモリ位置を指すため、`==` 比較で `false` となります。

### `src/pkg/runtime/386/closure.c` および `src/pkg/runtime/amd64/closure.c` における変更

これらのファイルは、Goランタイムが実際にクロージャオブジェクトをヒープに割り当て、キャプチャされた変数をコピーし、実行可能なクロージャスタブを生成する低レベルのコードを含んでいます。

**変更前**:
`sys·closure` 関数は、クロージャオブジェクトのサイズ (`siz`) と関数コードへのポインタ (`fn`)、およびキャプチャされた変数 (`arg0`) を受け取ります。以前は、`siz` が0であっても、キャプチャされた変数をスタックにコピーし、スタックポインタを調整するアセンブリ命令が常に生成されていました。これは、`siz` が0の場合には不要な操作でした。

**変更後**:
`sys·closure` 関数内で、キャプチャされた変数のコピーとスタックポインタの調整を行うアセンブリコードの生成が、`if(siz > 0)` の条件ブロックで囲まれるようになりました。

```c
	if(siz > 0) {
		mcpy(q, (byte*)&arg0, siz);

		// SUBL $siz, SP (or SUBQ $siz, SP for amd64)
		// ... (assembly instructions for stack manipulation and data copy)
	}
```

この変更は、`dcl.c` で導入された「すべての関数リテラルがクロージャオブジェクトを生成する」というセマンティクスと整合性を保ちつつ、最適化を図るものです。`siz` が0の場合（つまり、キャプチャする変数がない場合）でもクロージャオブジェクト自体は生成されますが、そのオブジェクト内にコピーすべきデータがないため、不要なメモリコピーやスタック操作のアセンブリ命令はスキップされます。これにより、ランタイムの効率性を維持しつつ、一貫した等価性セマンティクスを実現しています。

### 全体的な影響

この変更により、Go言語における関数リテラルの等価性比較は、よりシンプルで予測可能なルールに従うようになります。

*   `func() { ... }` のような関数リテラルは、それが評価されるたびに新しい、ユニークな関数値（クロージャオブジェクト）を生成します。
*   したがって、`f1 := func() {}; f2 := func(){};` のように異なる場所で定義されたり、同じ定義でも異なる実行で生成されたりした関数値は、常に `f1 != f2` となります。
*   唯一 `f1 == f2` となるのは、`f1 := func(){}; f2 := f1;` のように、同じ関数値が別の変数に代入された場合のみです。

これは、Goのマップやスライスなどの参照型が `make` で生成されるたびに新しいインスタンスを返す挙動と完全に一致し、言語全体の一貫性を高めます。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は以下の3つのファイルにまたがっています。

1.  **`src/cmd/gc/dcl.c`**:
    *   `funclit1` 関数内で、キャプチャする変数がないクロージャ (`func->cvars == nil`) の場合に直接関数ポインタを返す最適化パスが削除されました。
    *   具体的には、以下の約5行のコードブロックが削除されています。
        ```c
        	// if there's no closure, we can use f directly
        	if(func->cvars == nil)
        		return f;
        ```
    *   これにより、すべての関数リテラルがクロージャオブジェクトを生成する共通のパスを通るようになります。

2.  **`src/pkg/runtime/386/closure.c`**:
    *   `sys·closure` 関数内で、キャプチャされた変数をスタックにコピーし、スタックポインタを調整するアセンブリコードの生成が、`if(siz > 0)` の条件ブロックで囲まれました。
    *   これにより、`siz` が0（キャプチャする変数がない）の場合には、不要なメモリコピーとスタック操作がスキップされます。

3.  **`src/pkg/runtime/amd64/closure.c`**:
    *   `src/pkg/runtime/386/closure.c` と同様に、`sys·closure` 関数内で、キャプチャされた変数のコピーとスタックポインタの調整を行うアセンブリコードの生成が、`if(siz > 0)` の条件ブロックで囲まれました。
    *   これは64ビットアーキテクチャ向けの実装であり、基本的な変更内容は386版と同じです。

4.  **`test/closure.go`**:
    *   新しいテスト関数 `newfunc()` が追加されました。これは `func(x int) int { return x }` というキャプチャしない関数リテラルを返します。
    *   `main` 関数内で、`x, y := newfunc(), newfunc();` のように2つの異なる関数値が生成され、`if x == y { panicln("newfunc returned same func"); }` というアサーションが追加されました。
    *   このテストは、異なる実行で生成されたキャプチャしない関数リテラルが `==` 比較で `false` となることを明示的に検証しています。

## コアとなるコードの解説

### `src/cmd/gc/dcl.c` の変更点

`src/cmd/gc/dcl.c` の `funclit1` 関数は、Goコンパイラが関数リテラルを処理する主要な場所です。この関数は、関数リテラルのAST (Abstract Syntax Tree) を受け取り、それをコンパイル可能な内部表現に変換します。

削除されたコードブロック:
```c
	// if there's no closure, we can use f directly
	if(func->cvars == nil)
		return f;
```
この `if` 文は、関数リテラルが外部スコープの変数を一つもキャプチャしていない場合 (`func->cvars == nil`) に、特別な最適化を適用していました。具体的には、クロージャオブジェクトをヒープに割り当てる代わりに、コンパイルされた関数コードへの直接的なポインタ `f` を関数値として返していました。これにより、同じコードを持つキャプチャなしの関数リテラルは、同じ静的アドレスを指すことになり、`==` 比較で `true` となる可能性がありました。

このブロックが削除されたことで、`func->cvars == nil` の場合でも、関数リテラルは常にその後の共通のパスを通るようになります。この共通パスでは、クロージャの型情報が構築され、ランタイムがヒープ上にクロージャオブジェクトを割り当てるための準備が行われます。結果として、キャプチャする変数がなくても、各関数リテラルの評価は常に新しい、ユニークなクロージャオブジェクトを生成するようになります。

### `src/pkg/runtime/386/closure.c` および `src/pkg/runtime/amd64/closure.c` の変更点

これらのファイルは、Goランタイムが実際にクロージャオブジェクトを生成する低レベルの実装を含んでいます。`sys·closure` 関数は、Goコードからクロージャが生成される際に呼び出されるランタイム関数です。

変更されたコードブロック（例: `src/pkg/runtime/386/closure.c`）:
```c
// 変更前:
// mcpy(q, (byte*)&arg0, siz);
// ... (assembly instructions for stack manipulation and data copy)

// 変更後:
	if(siz > 0) {
		mcpy(q, (byte*)&arg0, siz);

		// SUBL $siz, SP
		*p++ = 0x81;
		*p++ = 0xec;
		*(uint32*)p = siz;
		p += 4;

		// MOVL $q, SI
		*p++ = 0xbe;
		*(byte**)p = q;
		p += 4;

		// MOVL SP, DI
		*p++ = 0x89;
		*p++ = 0xe7;

		// CLD
		*p++ = 0xfc;

		if(siz <= 4*4) {
			for(i=0; i<siz; i+=4) {
				// MOVSL
				*p++ = 0xa5;
			}
		} else {
			// MOVL $(siz/4), CX  [32-bit immediate siz/4]
			*p++ = 0xc7;
			*p++ = 0xc1;
			*(uint32*)p = siz/4;
			p += 4;

			// REP; MOVSL
			*p++ = 0xf3;
			*p++ = 0xa5;
		}
	}
```
`sys·closure` 関数は、クロージャオブジェクトのメモリを割り当て (`mal(n)`)、そのポインタを `ret` に格納します。`q` は、クロージャオブジェクトの末尾に配置されるキャプチャされた変数データの開始アドレスを指します。`siz` は、キャプチャされた変数データの合計サイズです。

変更前は、`siz` の値にかかわらず、`mcpy` を使って `arg0` (キャプチャされた変数) を `q` にコピーし、その後、スタックポインタを調整し、`MOVSL` (Move String Long) や `REP; MOVSL` (Repeat Move String Long) といったアセンブリ命令を使ってデータをコピーするコードが常に生成されていました。

変更後は、これらのデータコピーとスタック操作のアセンブリコード生成が `if(siz > 0)` ブロックで囲まれています。これは、`dcl.c` の変更によって、キャプチャする変数がないクロージャ (`siz == 0`) でもクロージャオブジェクト自体は生成されるようになったものの、実際にコピーすべきデータがない場合には、これらの低レベルな操作をスキップすることでランタイムの効率を維持するためです。

### `test/closure.go` の変更点

```go
func newfunc() (func(int) int) {
	return func(x int) int { return x }
}

// ...

	x, y := newfunc(), newfunc();
	if x == y {
		panicln("newfunc returned same func");
	}
	if x(1) != 1 || y(2) != 2 {
		panicln("newfunc returned broken funcs");
	}
```
このテストコードは、このコミットの意図を明確に示しています。`newfunc` は、外部変数をキャプチャしないシンプルな関数リテラルを返します。`x` と `y` は、`newfunc()` を2回呼び出すことで、それぞれ異なる実行で生成された関数リテラルを受け取ります。

変更後のセマンティクスでは、これらの2つの関数値 `x` と `y` は、たとえ同じコードであっても、異なるクロージャオブジェクトを指すため、`x == y` は常に `false` となるべきです。もし `true` になった場合、`panicln` が呼び出され、テストが失敗します。これにより、新しい一貫した等価性セマンティクスが正しく実装されていることが検証されます。

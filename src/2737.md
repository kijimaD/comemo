# [インデックス 2737] ファイルの概要

このコミットは、Goコンパイラ（`src/cmd/gc`）における抽象構文木（AST）のリスト構造の扱い方を根本的に変更するものです。特に、従来の汎用的な`OLIST`ノードを`NodeList*`という専用の型に置き換えることで、リストの利用箇所を明確化し、リスト操作の効率を向上させています。また、この変更は、コンパイラの設計における「前方宣言の排除」という大きな目標に向けた重要な一歩でもあります。

## 元コミット内容

このコミットは、Goコンパイラにおける前方宣言の排除に向けた一連の変更の一部です。具体的には、以下の主要な変更が含まれています。

- コンパイラ内で`OLIST`ノードの代わりに`NodeList*`型を導入。これにより、リストがどこで出現し、どこで出現しないかを明確化。
- リストの追加（append）と連結（concatenation）操作が効率的になるように改善。
- `yacc`（パーサジェネレータ）の文法定義から`_r`（reverse）ルールを削除。
- `rev`および`unrev`関数を削除。
- 「リストのリスト」構造を排除し、ASTをよりフラットに。
- 代入の表現を、単一代入（`OAS`）と複数代入（`OAS2`）に分割。
- 不要になった`chanrecv3`関連のコードを削除。
- 関数型の構築を遅延させるように変更。

## 変更の背景

Goコンパイラの初期の設計では、抽象構文木（AST）内で複数の要素を表現するために、汎用的な`OLIST`（Operation List）ノードが広く使用されていました。この`OLIST`は、単一のノードがリストの先頭要素を指し、その`right`フィールドが次の`OLIST`ノードを指すという、連結リストのような構造を形成していました。しかし、この設計にはいくつかの問題がありました。

1.  **曖昧さ**: `OLIST`は非常に汎用的なため、それが文のリストなのか、式のリストなのか、あるいは宣言のリストなのかが、文脈からしか判断できませんでした。これにより、コードの可読性や保守性が低下していました。
2.  **非効率なリスト操作**: `OLIST`は単方向連結リストとして機能するため、リストの末尾への要素追加やリストの連結といった操作が非効率でした。特に、パーサがリストを逆順に構築し、後で`rev`関数で反転させるというパターンが頻繁に見られ、これがオーバーヘッドとなっていました。
3.  **「リストのリスト」**: `OLIST`が汎用的に使われた結果、`OLIST`の中にさらに`OLIST`が含まれる「リストのリスト」のような複雑な構造が生まれ、ASTの処理を複雑にしていました。
4.  **前方宣言**: コンパイラがコードを処理する際に、まだ定義されていない型や関数を参照する必要がある「前方宣言」の問題がありました。これを解消することで、コンパイラの設計を簡素化し、依存関係を減らすことが目標とされていました。

このコミットは、これらの問題を解決し、コンパイラのコードベースをよりクリーンで効率的、かつ理解しやすいものにすることを目的としています。

## 前提知識の解説

### Goコンパイラの構造

Goコンパイラは、主に以下の部分で構成されます。

-   **`src/cmd/gc`**: コンパイラのフロントエンド。Go言語のソースコードを解析し、抽象構文木（AST）を構築し、型チェックや最適化などのセマンティック分析を行います。このコミットの主要な変更箇所です。
-   **`src/cmd/{5,6,8}g`**: 各アーキテクチャ（5g: ARM, 6g: x86-64, 8g: x86）向けのバックエンド。フロントエンドで生成されたASTを、それぞれのターゲットアーキテクチャの機械語に変換します。
-   **`go.y`**: `yacc`（またはその派生ツールである`bison`）の文法定義ファイル。Go言語の構文規則を定義し、ソースコードを解析してASTノードを生成します。

### 抽象構文木（AST）

ASTは、プログラムのソースコードの抽象的な構文構造を木構造で表現したものです。コンパイラはソースコードを直接操作するのではなく、ASTを操作して様々な処理を行います。ASTの各ノードは、変数、式、文、関数定義などのプログラム要素を表します。

### `yacc`と`_r`ルール

`yacc`は、文法定義からパーサを生成するツールです。文法規則は、非終端記号と終端記号、そしてそれらの組み合わせによって定義されます。パーサがソースコードを解析する際、文法規則にマッチすると、対応するアクション（通常はC言語のコード）が実行され、ASTノードが構築されます。

従来の`yacc`の文法定義では、リストを構築する際に、要素が逆順に追加されることがよくありました。例えば、`A: B C`という規則で`B`と`C`がリスト要素を生成する場合、`C`が先に処理され、その後に`B`が処理されるため、リストは逆順になります。これを修正するために、`_r`（reverse）という接尾辞を持つルールが使われ、生成されたリストを`rev`関数で反転させる必要がありました。

### 前方宣言

前方宣言とは、プログラム中で使用されるエンティティ（変数、関数、型など）が、その使用箇所よりも後で定義されることを指します。C言語などでは、関数プロトタイプ宣言のように前方宣言が必須となる場合があります。Go言語では、原則として前方宣言は不要であり、コンパイラはコードを一度に読み込んで処理します。しかし、コンパイラの内部実装においては、ASTの構築や型解決の段階で、まだ完全に情報が揃っていないエンティティを参照する必要が生じることがありました。このコミットは、このような内部的な前方宣言の必要性を減らすことを目指しています。

## 技術的詳細

### `NodeList`型の導入

このコミットの最も重要な変更は、`src/cmd/gc/go.h`で新しい構造体`NodeList`が導入されたことです。

```c
struct NodeList
{
	Node*	n;
	NodeList*	next;
	NodeList*	end;
};
```

-   `n`: リストの現在の要素である`Node`へのポインタ。
-   `next`: リストの次の`NodeList`要素へのポインタ。
-   `end`: リストの末尾の`NodeList`要素へのポインタ。このフィールドが、リストの末尾への効率的な追加（append）と連結（concatenation）を可能にします。従来の単方向連結リストでは、末尾に要素を追加するにはリスト全体を走査する必要がありましたが、`end`ポインタがあればO(1)で追加できます。

この`NodeList`型が導入されたことで、`Node`構造体内の多くの`Node*`フィールドが`NodeList*`に置き換えられました。例えば、関数の本体（`nbody`）、初期化文（`ninit`）、`if`文の`else`ブロック（`nelse`）、クロージャ変数（`cvars`）などがこれに該当します。これにより、ASTの構造がより明確になり、リストとして扱われるべき箇所が明示されます。

### `yacc`文法定義の変更 (`go.y`)

-   **`_r`ルールの削除**: 従来の`yacc`文法定義では、リストを逆順に構築し、後で`rev`関数で反転させるために`_r`接尾辞を持つルールが多数存在しました（例: `arg_type_list_r`）。`NodeList`の導入と効率的なリスト操作により、これらのルールは不要となり、`arg_type_list`のように直接順序通りのリストを構築できるようになりました。
-   **`%type <list>`の導入**: `yacc`の`%type`宣言に`<list>`が追加され、多くのリスト関連の非終端記号が`NodeList*`を返すように変更されました。これにより、パーサが直接`NodeList`を構築するようになります。
-   **リスト構築関数の変更**: 文法アクション内で、`nod(OLIST, $1, $2)`のように`OLIST`ノードを介してリストを構築していた箇所が、`list($1, $2)`や`concat($1, $2)`といった`NodeList`を操作する新しいヘルパー関数に置き換えられました。これらの関数は`NodeList`の`end`ポインタを活用し、効率的にリストを構築します。

### `rev`および`unrev`関数の削除

`NodeList`の`end`ポインタにより、リストを常に正しい順序で構築できるようになり、逆順に構築されたリストを反転させる必要がなくなりました。そのため、`rev`（reverse）および`unrev`（un-reverse）関数は不要となり、コードベースから削除されました。

### 代入の表現の分割 (`OAS`と`OAS2`)

従来のGoコンパイラでは、単一代入（例: `a = b`）と複数代入（例: `a, b = c, d`）が同じ`OAS`（Operation Assignment）ノードで表現されていた可能性があります。このコミットでは、これを`OAS`（単一代入）と`OAS2`（複数代入）に明確に分割しました。

-   `OAS`: 単一の左辺と右辺を持つ代入。
-   `OAS2`: 複数の左辺と右辺を持つ代入。`Node`構造体の`list`フィールドと`rlist`フィールドを使用して、それぞれ左辺のリストと右辺のリストを保持します。

この分割により、代入のセマンティクスがより明確になり、コンパイラがそれぞれのケースをより効率的かつ正確に処理できるようになります。

### `chanrecv3`コードの削除

`src/cmd/gc/builtin.c.boot`から`sys.chanrecv3`の宣言が削除されています。これは、Go言語のチャネル操作において、特定の形式の受信操作（おそらくポインタ渡しによる受信）が不要になったか、あるいは別のより汎用的なメカニズムに置き換えられたため、デッドコードとして削除されたものと考えられます。

### 関数型の構築の遅延

`functype`関数（関数型を構築する関数）の呼び出しが、必要になるまで遅延されるように変更されました。これは、コンパイラがASTを構築する初期段階で、まだ完全な型情報が揃っていない場合でも、不完全な型を構築しようとするのを避けるための最適化または設計の簡素化と考えられます。これにより、型解決のプロセスがより柔軟になり、前方宣言の必要性をさらに減らすことができます。

### `genlist`関数の導入 (`src/cmd/gc/gen.c`)

```c
void
genlist(NodeList *l)
{
	for(; l; l=l->next)
		gen(l->n);
}
```
`genlist`関数は、`NodeList`を受け取り、リスト内の各`Node`に対して`gen`関数（コード生成を行う関数）を呼び出します。これにより、`Node`構造体内の`NodeList*`フィールド（例: `nbody`, `ninit`）を処理する際に、従来の`gen(n->nbody)`のような単一ノードの処理から、リスト全体を処理する`genlist(n->nbody)`へと変更されました。これは、ASTのリスト構造が`OLIST`から`NodeList`に移行したことによる、コード生成ロジックの適応です。

このコミットは、Goコンパイラ（`src/cmd/gc`）における抽象構文木（AST）のリスト構造の扱い方を根本的に変更するものです。特に、従来の汎用的な`OLIST`ノードを`NodeList*`という専用の型に置き換えることで、リストの利用箇所を明確化し、リスト操作の効率を向上させています。また、この変更は、コンパイラの設計における「前方宣言の排除」という大きな目標に向けた重要な一歩でもあります。

## 元コミット内容

このコミットは、Goコンパイラにおける前方宣言の排除に向けた一連の変更の一部です。具体的には、以下の主要な変更が含まれています。

- コンパイラ内で`OLIST`ノードの代わりに`NodeList*`型を導入。これにより、リストがどこで出現し、どこで出現しないかを明確化。
- リストの追加（append）と連結（concatenation）操作が効率的になるように改善。
- `yacc`（パーサジェネレータ）の文法定義から`_r`（reverse）ルールを削除。
- `rev`および`unrev`関数を削除。
- 「リストのリスト」構造を排除し、ASTをよりフラットに。
- 代入の表現を、単一代入（`OAS`）と複数代入（`OAS2`）に分割。
- 不要になった`chanrecv3`関連のコードを削除。
- 関数型の構築を遅延させるように変更。

## 変更の背景

Goコンパイラの初期の設計では、抽象構文木（AST）内で複数の要素を表現するために、汎用的な`OLIST`（Operation List）ノードが広く使用されていました。この`OLIST`は、単一のノードがリストの先頭要素を指し、その`right`フィールドが次の`OLIST`ノードを指すという、連結リストのような構造を形成していました。しかし、この設計にはいくつかの問題がありました。

1.  **曖昧さ**: `OLIST`は非常に汎用的なため、それが文のリストなのか、式のリストなのか、あるいは宣言のリストなのかが、文脈からしか判断できませんでした。これにより、コードの可読性や保守性が低下していました。
2.  **非効率なリスト操作**: `OLIST`は単方向連結リストとして機能するため、リストの末尾への要素追加やリストの連結といった操作が非効率でした。特に、パーサがリストを逆順に構築し、後で`rev`関数で反転させるというパターンが頻繁に見られ、これがオーバーヘッドとなっていました。
3.  **「リストのリスト」**: `OLIST`が汎用的に使われた結果、`OLIST`の中にさらに`OLIST`が含まれる「リストのリスト」のような複雑な構造が生まれ、ASTの処理を複雑にしていました。
4.  **前方宣言**: コンパイラがコードを処理する際に、まだ定義されていない型や関数を参照する必要がある「前方宣言」の問題がありました。これを解消することで、コンパイラの設計を簡素化し、依存関係を減らすことが目標とされていました。

このコミットは、これらの問題を解決し、コンパイラのコードベースをよりクリーンで効率的、かつ理解しやすいものにすることを目的としています。

## 前提知識の解説

### Goコンパイラの構造

Goコンパイラは、主に以下の部分で構成されます。

-   **`src/cmd/gc`**: コンパイラのフロントエンド。Go言語のソースコードを解析し、抽象構文木（AST）を構築し、型チェックや最適化などのセマンティック分析を行います。このコミットの主要な変更箇所です。
-   **`src/cmd/{5,6,8}g`**: 各アーキテクチャ（5g: ARM, 6g: x86-64, 8g: x86）向けのバックエンド。フロントエンドで生成されたASTを、それぞれのターゲットアーキテクチャの機械語に変換します。
-   **`go.y`**: `yacc`（またはその派生ツールである`bison`）の文法定義ファイル。Go言語の構文規則を定義し、ソースコードを解析してASTノードを生成します。

### 抽象構文木（AST）

ASTは、プログラムのソースコードの抽象的な構文構造を木構造で表現したものです。コンパイラはソースコードを直接操作するのではなく、ASTを操作して様々な処理を行います。ASTの各ノードは、変数、式、文、関数定義などのプログラム要素を表します。

### `yacc`と`_r`ルール

`yacc`は、文法定義からパーサを生成するツールです。文法規則は、非終端記号と終端記号、そしてそれらの組み合わせによって定義されます。パーサがソースコードを解析する際、文法規則にマッチすると、対応するアクション（通常はC言語のコード）が実行され、ASTノードが構築されます。

従来の`yacc`の文法定義では、リストを構築する際に、要素が逆順に追加されることがよくありました。例えば、`A: B C`という規則で`B`と`C`がリスト要素を生成する場合、`C`が先に処理され、その後に`B`が処理されるため、リストは逆順になります。これを修正するために、`_r`（reverse）という接尾辞を持つルールが使われ、生成されたリストを`rev`関数で反転させる必要がありました。

### 前方宣言

前方宣言とは、プログラム中で使用されるエンティティ（変数、関数、型など）が、その使用箇所よりも後で定義されることを指します。C言語などでは、関数プロトタイプ宣言のように前方宣言が必須となる場合があります。Go言語では、原則として前方宣言は不要であり、コンパイラはコードを一度に読み込んで処理します。しかし、コンパイラの内部実装においては、ASTの構築や型解決の段階で、まだ完全に情報が揃っていないエンティティを参照する必要が生じることがありました。このコミットは、このような内部的な前方宣言の必要性を減らすことを目指しています。

## 技術的詳細

### `NodeList`型の導入

このコミットの最も重要な変更は、`src/cmd/gc/go.h`で新しい構造体`NodeList`が導入されたことです。

```c
struct NodeList
{
	Node*	n;
	NodeList*	next;
	NodeList*	end;
};
```

-   `n`: リストの現在の要素である`Node`へのポインタ。
-   `next`: リストの次の`NodeList`要素へのポインタ。
-   `end`: リストの末尾の`NodeList`要素へのポインタ。このフィールドが、リストの末尾への効率的な追加（append）と連結（concatenation）を可能にします。従来の単方向連結リストでは、末尾に要素を追加するにはリスト全体を走査する必要がありましたが、`end`ポインタがあればO(1)で追加できます。

この`NodeList`型が導入されたことで、`Node`構造体内の多くの`Node*`フィールドが`NodeList*`に置き換えられました。例えば、関数の本体（`nbody`）、初期化文（`ninit`）、`if`文の`else`ブロック（`nelse`）、クロージャ変数（`cvars`）などがこれに該当します。これにより、ASTの構造がより明確になり、リストとして扱われるべき箇所が明示されます。

### `yacc`文法定義の変更 (`go.y`)

-   **`_r`ルールの削除**: 従来の`yacc`文法定義では、リストを逆順に構築し、後で`rev`関数で反転させるために`_r`接尾辞を持つルールが多数存在しました（例: `arg_type_list_r`）。`NodeList`の導入と効率的なリスト操作により、これらのルールは不要となり、`arg_type_list`のように直接順序通りのリストを構築できるようになりました。
-   **`%type <list>`の導入**: `yacc`の`%type`宣言に`<list>`が追加され、多くのリスト関連の非終端記号が`NodeList*`を返すように変更されました。これにより、パーサが直接`NodeList`を構築するようになります。
-   **リスト構築関数の変更**: 文法アクション内で、`nod(OLIST, $1, $2)`のように`OLIST`ノードを介してリストを構築していた箇所が、`list($1, $2)`や`concat($1, $2)`といった`NodeList`を操作する新しいヘルパー関数に置き換えられました。これらの関数は`NodeList`の`end`ポインタを活用し、効率的にリストを構築します。

### `rev`および`unrev`関数の削除

`NodeList`の`end`ポインタにより、リストを常に正しい順序で構築できるようになり、逆順に構築されたリストを反転させる必要がなくなりました。そのため、`rev`（reverse）および`unrev`（un-reverse）関数は不要となり、コードベースから削除されました。

### 代入の表現の分割 (`OAS`と`OAS2`)

従来のGoコンパイラでは、単一代入（例: `a = b`）と複数代入（例: `a, b = c, d`）が同じ`OAS`（Operation Assignment）ノードで表現されていた可能性があります。このコミットでは、これを`OAS`（単一代入）と`OAS2`（複数代入）に明確に分割しました。

-   `OAS`: 単一の左辺と右辺を持つ代入。
-   `OAS2`: 複数の左辺と右辺を持つ代入。`Node`構造体の`list`フィールドと`rlist`フィールドを使用して、それぞれ左辺のリストと右辺のリストを保持します。

この分割により、代入のセマンティクスがより明確になり、コンパイラがそれぞれのケースをより効率的かつ正確に処理できるようになります。

### `chanrecv3`コードの削除

`src/cmd/gc/builtin.c.boot`から`sys.chanrecv3`の宣言が削除されています。これは、Go言語のチャネル操作において、特定の形式の受信操作（おそらくポインタ渡しによる受信）が不要になったか、あるいは別のより汎用的なメカニズムに置き換えられたため、デッドコードとして削除されたものと考えられます。

### 関数型の構築の遅延

`functype`関数（関数型を構築する関数）の呼び出しが、必要になるまで遅延されるように変更されました。これは、コンパイラがASTを構築する初期段階で、まだ完全な型情報が揃っていない場合でも、不完全な型を構築しようとするのを避けるための最適化または設計の簡素化と考えられます。これにより、型解決のプロセスがより柔軟になり、前方宣言の必要性をさらに減らすことができます。

### `genlist`関数の導入 (`src/cmd/gc/gen.c`)

```c
void
genlist(NodeList *l)
{
	for(; l; l=l->next)
		gen(l->n);
}
```
`genlist`関数は、`NodeList`を受け取り、リスト内の各`Node`に対して`gen`関数（コード生成を行う関数）を呼び出します。これにより、`Node`構造体内の`NodeList*`フィールド（例: `nbody`, `ninit`）を処理する際に、従来の`gen(n->nbody)`のような単一ノードの処理から、リスト全体を処理する`genlist(n->nbody)`へと変更されました。これは、ASTのリスト構造が`OLIST`から`NodeList`に移行したことによる、コード生成ロジックの適応です。

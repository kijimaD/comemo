## 元コミット内容

このコミットは、`crypto/x509` パッケージが、リクエストされた拡張機能にクリティカルフラグを持つCSRをパースできるようにします。

CSRのフォーマットは非常に不明瞭であり、以前のコードには間違いがありました。コードはCSRの属性を `pkix.AttributeTypeAndValueSET` としてパースしていましたが、これはほぼ正しいものの、リクエストされた拡張機能にオプションの「critical」フラグが含まれていない場合にのみ機能しました。

残念ながら、この間違いはAPIにもある程度影響を与えており、CSRの `Attributes` フィールドは実際には間違った型を持っていました。このフィールドは構造体の下部に移動され、そのコメントもこれを反映するように更新されました。

しかし、CSR構造体の `Extensions` およびその他のフィールドは保存可能であり、この変更によってそれが実現されます。

Issue #11897 を修正します。

## 変更の背景

Certificate Signing Request (CSR) は、公開鍵証明書の発行を認証局 (CA) に要求するために使用される標準フォーマットです。CSRには、証明書のサブジェクト情報（組織名、ドメイン名など）と、公開鍵、そしてオプションで追加の拡張情報が含まれます。これらの拡張情報は、X.509証明書に含めたい追加のプロパティ（例: Subject Alternative Name (SAN)、Key Usage、Basic Constraintsなど）を指定するために使用されます。

X.509拡張機能には「critical」フラグという重要な概念があります。このフラグが `true` に設定されている場合、その拡張機能は証明書を検証するアプリケーションにとって「クリティカル」であることを意味します。つまり、アプリケーションがその拡張機能を理解できない場合、またはその拡張機能の処理に失敗した場合、その証明書は無効とみなされなければなりません。これにより、セキュリティ上重要な情報が正しく解釈されないまま証明書が使用されることを防ぎます。

Go言語の `crypto/x509` パッケージは、CSRのパース処理において、この「critical」フラグを持つ拡張機能を正しく処理できないというバグを抱えていました。具体的には、CSRの属性を `pkix.AttributeTypeAndValueSET` として解釈していたため、拡張機能のASN.1構造に含まれる `critical` フラグを適切にデコードできませんでした。このため、`critical` フラグが設定されたCSRがGoのライブラリによって生成またはパースされると、問題が発生する可能性がありました。

このコミットは、この問題を修正し、`critical` フラグを含むCSRの拡張機能をGoが正しく処理できるようにすることで、相互運用性とセキュリティを向上させます。また、`CertificateRequest` 構造体の `Attributes` フィールドが誤った型を持っていたことに対するAPI上の不整合も修正しています。

## 前提知識の解説

### Certificate Signing Request (CSR)

CSRは、公開鍵インフラストラクチャ (PKI) において、証明書の発行を要求するために使用されるメッセージです。通常、ウェブサーバーの管理者が秘密鍵を生成し、その公開鍵とサブジェクト情報（ドメイン名、組織名など）を含むCSRを作成します。このCSRを認証局に送信し、認証局はCSRの内容を検証した後、デジタル署名されたX.509証明書を発行します。

CSRのフォーマットはRFC 2986 (PKCS #10) で定義されていますが、コミットメッセージにもあるように「horribly underspecified（ひどく不明瞭）」な部分があり、実装によっては解釈に差異が生じることがあります。

### X.509証明書と拡張機能

X.509は、公開鍵証明書の標準フォーマットです。証明書には、公開鍵、所有者の識別情報、発行者の識別情報、有効期間、発行者のデジタル署名などが含まれます。

X.509証明書には「拡張機能 (Extensions)」を含めることができます。これは、証明書の標準フィールドでは表現できない追加情報や制約を付与するための仕組みです。RFC 5280で定義されており、以下のようなものがあります。

*   **Subject Alternative Name (SAN)**: 証明書が保護する追加のドメイン名やIPアドレスを指定します。
*   **Key Usage**: 公開鍵が何のために使用できるか（例: デジタル署名、鍵の暗号化、証明書の署名）を制限します。
*   **Basic Constraints**: 証明書がCA証明書であるか否か、およびCA証明書の場合に発行できる下位CA証明書のパス長を制限します。

### クリティカルフラグ (Critical Flag)

各X.509拡張機能には、ブール値の「critical」フラグが付随しています。

*   **`critical = TRUE`**: この拡張機能は、証明書を処理するアプリケーションにとって必須であり、その意味を理解し、適切に処理しなければなりません。もしアプリケーションがこの拡張機能を理解できない場合、または処理に失敗した場合、その証明書は無効とみなされなければなりません。これは、将来導入される新しい拡張機能が、古いアプリケーションによって誤って無視されることを防ぐための重要なセキュリティメカニズムです。
*   **`critical = FALSE`**: この拡張機能は、アプリケーションにとって必須ではありません。アプリケーションがその意味を理解できない場合でも、証明書を有効とみなして処理を続行できます。

このコミットの核心は、Goの `crypto/x509` パッケージが、CSR内のリクエストされた拡張機能に `critical = TRUE` が設定されている場合に、その拡張機能を正しくパースできなかった点にあります。

### ASN.1 (Abstract Syntax Notation One)

ASN.1は、データ構造を記述するための標準的な記法であり、通信プロトコルやデータストレージにおいて、異なるシステム間でデータを交換する際に使用されます。X.509証明書やCSRは、ASN.1で定義された構造を持ち、DER (Distinguished Encoding Rules) などのエンコーディングルールに従ってバイナリ形式に変換されます。

`pkix.AttributeTypeAndValueSET` は、ASN.1で定義される `AttributeTypeAndValue` のセットを表すGoの型です。CSRの属性は、通常、この形式で表現されますが、拡張機能の構造はより複雑であり、`critical` フラグを含む場合は `AttributeTypeAndValueSET` だけでは不十分でした。

## 技術的詳細

このコミットの主要な技術的変更点は、CSRの拡張機能をパースするロジックの改善です。

1.  **`CertificateRequest` 構造体の `Attributes` フィールドの修正**:
    *   以前は、`CertificateRequest` 構造体の `Attributes` フィールドは、CSRの追加情報を保持するために使用されていました。しかし、コミットメッセージにあるように、このフィールドは「間違った型」を持っており、特に拡張機能の `critical` フラグを考慮していませんでした。
    *   このコミットでは、`Attributes` フィールドのコメントが「Attributes is the dried husk of a bug and shouldn't be used.（Attributesはバグの抜け殻であり、使用すべきではありません。）」と変更され、その位置も構造体の下部に移動されました。これは、このフィールドが本来の目的で正しく機能していなかったことを示唆し、将来的な誤用を防ぐための措置です。

2.  **`parseCSRExtensions` 関数の導入**:
    *   このコミットの最も重要な変更は、`parseCSRExtensions` という新しいヘルパー関数が導入されたことです。この関数は、CSRの生（raw）の属性リストを受け取り、そこからリクエストされたX.509拡張機能を抽出して `[]pkix.Extension` のスライスとして返します。
    *   この関数は、RFC 2986のセクション4.1で定義されている `pkcs10Attribute` 構造体（`Id` と `Values` を持つ）を正確にパースします。特に、`Values` フィールドが `asn1:"set"` タグを持つことで、ASN.1 SET OF構造を正しくデコードできるようになります。
    *   `oidExtensionRequest` (Object Identifier for Extension Request) に一致する属性を見つけると、その値（これもASN.1でエンコードされた拡張機能のリスト）をさらにデコードし、`pkix.Extension` オブジェクトのリストとして抽出します。このプロセスにより、拡張機能に含まれる `critical` フラグを含むすべての情報が正しく解釈されます。

3.  **`parseCertificateRequest` 関数の変更**:
    *   既存の `parseCertificateRequest` 関数は、CSRのASN.1構造をデコードし、`CertificateRequest` 構造体を構築する主要な関数です。
    *   この関数は、以前は `out.Attributes` を直接ループして拡張機能を抽出していましたが、このロジックが `critical` フラグを考慮していなかったため、新しい `parseCSRExtensions` 関数を呼び出すように変更されました。
    *   `out.Extensions, err = parseCSRExtensions(in.TBSCSR.RawAttributes)` という行が追加され、CSRの生属性から拡張機能が正しくパースされ、`CertificateRequest` 構造体の `Extensions` フィールドに格納されるようになりました。
    *   Subject Alternative Name (SAN) 拡張機能のパースロジックも簡素化されました。以前は、すべての拡張機能をループしてOIDをチェックしていましたが、新しい変更では `out.Extensions` が既に正しくパースされているため、その中から `oidExtensionSubjectAltName` を持つ拡張機能を探し、`parseSANExtension` を呼び出すようになりました。

4.  **テストケースの追加**:
    *   `src/crypto/x509/x509_test.go` に `TestCriticalFlagInCSRRequestedExtensions` という新しいテスト関数が追加されました。
    *   このテストは、`critical` フラグを含む拡張機能を持つCSRのBase64エンコードされた文字列を定義し、`ParseCertificateRequest` 関数がこれをエラーなくパースできること、そして期待される拡張機能（Basic ConstraintsとKey Usage）が正しい `Id` と `Value` を持って抽出されることを検証します。これにより、修正が正しく機能していることが確認されます。

これらの変更により、Goの `crypto/x509` パッケージは、より堅牢になり、`critical` フラグを含むCSRの拡張機能を業界標準に準拠した形で処理できるようになりました。

    *   このテストは、`critical` フラグを含む拡張機能を持つCSRの具体的なシナリオを検証するために追加されました。
    *   `csrBase64` 定数には、Base64エンコードされたCSRデータが格納されています。このCSRは、Basic ConstraintsとKey Usageの拡張機能を含み、これらには `critical` フラグが設定されています。
    *   `ParseCertificateRequest` 関数を呼び出してCSRをパースし、エラーが発生しないことを確認します。
    *   パースされた `csr.Extensions` の数と内容が、`expected` スライスで定義された期待値と一致するかどうかを検証します。具体的には、拡張機能のOID (`Id`) と値 (`Value`) が正しいことを確認します。
    *   このテストの成功は、`crypto/x509` パッケージが `critical` フラグを持つCSR拡張機能を正しく処理できるようになったことを証明します。

これらの変更は、Goの `crypto/x509` パッケージがX.509およびPKCS #10標準により厳密に準拠し、より広範なCSRを正しく処理できるようにするための重要な改善です。

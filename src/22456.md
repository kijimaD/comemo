## 変更の背景

このコミットが追加された背景には、Go言語のランタイムにおける`defer`関数の挙動に関する懸念がありました。コミットメッセージに「This came up in private mail. It works today and I want to make sure it stays working.」とあるように、プライベートなやり取りの中で、メモリアクセス違反などの「フォルト」（fault）が発生し、それがパニックに変換された際に、`defer`関数が捕捉する変数の値が、フォルト発生時の最新の状態を正確に反映しているかどうかが議論されたようです。

Goの`defer`は、関数がリターンする直前、またはパニックが発生してスタックがアンワインドされる際に実行されます。この際、`defer`関数が外部の変数をクロージャとして捕捉している場合、その変数の値が、`defer`が実行される時点での最新の値であることは、予測可能なプログラムの挙動にとって非常に重要です。特に、ループ内で変数を更新しながら処理を進め、途中でフォルトが発生するようなシナリオでは、`defer`が捕捉する変数が古い値のままだと、リカバリ処理やデバッグが困難になります。

このコミットは、この重要な挙動が将来のGoランタイムの変更によって意図せず壊れることがないよう、明確なテストケースを追加することで、その保証を強化することを目的としています。

## 前提知識の解説

### Goの`defer`と`recover`

*   **`defer`**: Go言語の`defer`ステートメントは、そのステートメントを含む関数がリターンする直前、またはパニックが発生してスタックがアンワインドされる際に、指定された関数（遅延関数）の実行をスケジュールします。`defer`は主に、リソースの解放（ファイルクローズ、ロック解除など）や、パニックからのリカバリ処理に使用されます。遅延関数は、その`defer`ステートメントが評価された時点の環境（変数など）を捕捉します。
*   **`recover`**: `recover`は、パニックが発生した際に、`defer`関数内で呼び出すことで、そのパニックを捕捉し、プログラムのクラッシュを防ぐための組み込み関数です。`recover`が`defer`関数内で呼び出された場合、パニックの値（通常は`panic`に渡された引数）を返します。`defer`関数以外で`recover`を呼び出しても、`nil`が返され、効果はありません。`recover`によってパニックが捕捉されると、プログラムの実行は`recover`を呼び出した`defer`関数の後から再開され、パニックが発生した関数は正常にリターンします。

### Goにおけるパニックとリカバリのメカニズム

Goプログラムで実行時エラー（例: nilポインタ参照、配列の範囲外アクセス）が発生すると、通常は「パニック」が発生します。パニックは、通常の制御フローを中断し、現在のゴルーチンのスタックをアンワインド（巻き戻し）します。このアンワインドの過程で、スタック上の各関数に登録された`defer`関数が、逆順に実行されます。

`defer`関数内で`recover`が呼び出されると、そのパニックは捕捉され、スタックのアンワインドは停止します。これにより、プログラムはクラッシュすることなく、`recover`を呼び出した`defer`関数が属する関数から正常に実行を再開できます。

### メモリマッピング (`syscall.Mmap`, `syscall.Munmap`, `syscall.Syscall`)

*   **`syscall.Mmap`**: オペレーティングシステム（OS）のシステムコールである`mmap(2)`をGoから呼び出すための関数です。`mmap`は、ファイルやデバイス、または匿名メモリ領域をプロセスのアドレス空間にマッピングするために使用されます。これにより、ファイルの内容をメモリのように直接アクセスしたり、共有メモリ領域を作成したりできます。
    *   `fd`: マッピングするファイルディスクリプタ。匿名マッピングの場合は`-1`。
    *   `offset`: ファイル内のオフセット。
    *   `length`: マッピングするバイト数。
    *   `prot`: メモリ保護フラグ（例: `syscall.PROT_READ`読み取り、`syscall.PROT_WRITE`書き込み、`syscall.PROT_EXEC`実行）。
    *   `flags`: マッピングのタイプと挙動を制御するフラグ（例: `syscall.MAP_ANON`匿名マッピング、`syscall.MAP_PRIVATE`プライベートコピー）。
*   **`syscall.Munmap`**: `mmap`でマッピングされたメモリ領域をアンマッピング（解放）するための関数です。
*   **`syscall.Syscall`**: Goから任意のシステムコールを直接呼び出すための低レベルな関数です。このテストでは、`syscall.SYS_MUNMAP`システムコールを直接呼び出すために使用されています。これは、`syscall.Munmap`が`mmap`でマッピングされた「完全な領域」のアンマッピングを想定しているのに対し、このテストでは「領域の中間部分」をアンマッピングするという特殊な操作を行うためです。

### `debug.SetPanicOnFault`

`runtime/debug`パッケージの`SetPanicOnFault(true)`関数は、Goプログラムがメモリアクセス違反（セグメンテーションフォルトなど）のようなOSレベルのフォルトを検出した際に、通常のプログラムクラッシュではなく、Goのパニック機構を介してパニックを発生させるように設定します。これにより、`defer`と`recover`を使ってこれらのフォルトを捕捉し、処理することが可能になります。このテストでは、`memcopy`関数内で意図的にメモリアクセス違反を発生させ、それを`recover`で捕捉するためにこの設定が不可欠です。

### スライスとメモリレイアウト

Goのスライスは、基盤となる配列の一部を参照する軽量なデータ構造です。スライスは、ポインタ（基盤配列の先頭要素へのポインタ）、長さ（スライスに含まれる要素の数）、容量（基盤配列の先頭要素から基盤配列の終わりまでの要素の数）の3つの要素で構成されます。スライスへのアクセスは、そのポインタと長さに基づいて行われます。このテストでは、`mmap`と`munmap`を使って、スライスが参照するメモリ領域の一部を意図的に無効化することで、スライスアクセス時にメモリアクセス違反を発生させています。

## 技術的詳細

このテストの核心は、`defer`関数がパニック発生時に変数の最新の値を捕捉していることを、非常に具体的なメモリアクセス違反のシナリオで検証することにあります。

1.  **`memcopy`関数の動作と`defer`の利用**:
    `memcopy`関数は、`dst`スライスから`src`スライスへバイトをコピーするシンプルなループを含んでいます。この関数は、コピーされたバイト数を`n`としてカウントし、エラーを`err`として返します。
    最も重要なのは、この関数に`defer`関数が設定されている点です。
    ```go
    defer func() {
        err = recover().(error)
    }()
    ```
    この`defer`関数は、`memcopy`関数内でパニックが発生した場合に実行されます。`recover()`を呼び出すことでパニックを捕捉し、そのパニックの値を`error`型に型アサートして`err`変数に代入します。この`err`変数は、`memcopy`関数の戻り値の一部です。
    ループ内で`n++`が実行されるたびに、`n`の値は更新されます。テストの目的は、メモリアクセス違反によってパニックが発生した際に、この`defer`関数が捕捉する`n`の値が、フォルトが発生した時点での最新の値（つまり、実際にコピーが成功したバイト数）であることを確認することです。もし`n`がレジスタにキャッシュされたままで、メモリにフラッシュされていなかった場合、`defer`関数は古い`n`の値を参照してしまう可能性があります。

2.  **メモリホールを作成するメカニズム**:
    テストの`main`関数では、意図的にメモリアクセス違反を発生させるために、特殊なメモリ領域が作成されます。
    *   まず、`syscall.Mmap`を使って64KBの匿名メモリ領域を確保します。これは、プロセスのアドレス空間に連続したメモリブロックをマッピングします。
    *   次に、この64KBの領域の中央（32KBオフセットから16KBの範囲）に「メモリホール」を作成します。これは、`syscall.Syscall(syscall.SYS_MUNMAP, ...)`を直接呼び出すことで実現されます。通常の`syscall.Munmap`関数は、`mmap`でマッピングされた「完全な領域」をアンマッピングすることを想定しているため、領域の中間部分だけをアンマッピングするこのシナリオでは使用できません。`syscall.SYS_MUNMAP`を直接呼び出すことで、OSに対して特定のアドレス範囲のメモリマッピングを解除するよう指示します。これにより、その範囲へのアクセスは無効なメモリアクセスとなり、フォルトを発生させます。

3.  **`debug.SetPanicOnFault(true)`の重要性**:
    `main`関数の冒頭で`debug.SetPanicOnFault(true)`が呼び出されています。これは非常に重要です。この設定がない場合、無効なメモリアクセス（メモリホールへのアクセス）はGoランタイムによって捕捉されず、OSによって直接プログラムがクラッシュ（セグメンテーションフォルト）させられてしまいます。`SetPanicOnFault(true)`を設定することで、OSからのフォルトシグナルがGoランタイムによって捕捉され、Goのパニック機構に変換されます。これにより、`memcopy`関数内の`defer`関数がそのパニックを`recover`で捕捉し、テストのロジックが実行可能になります。

4.  **テストの目的（変数が最新の値を持つことの確認）**:
    `main`関数では、作成されたメモリホールを持つ`data`スライスの一部（`data[5:]`）と、別の`other`スライスを`memcopy`関数に渡します。
    `memcopy`は、`data`スライスにコピーを試みますが、32KBのオフセットに到達するとメモリホールにアクセスし、パニックが発生します。
    `defer`関数がパニックを捕捉し、`memcopy`はエラーを返して正常に終了します。
    テストの最終的な検証は、`memcopy`が返した`n`の値が、実際にコピーが成功したバイト数（この場合、32KB - 5バイト）と一致するかどうかを確認することです。
    `if n != 32*1024-5`
    このチェックが成功するということは、`n`変数がループ内でインクリメントされるたびに、その最新の値が`defer`関数から参照可能であったことを意味します。これは、Goランタイムがパニック発生時においても、変数の状態を正確に保持していることの証明となります。

5.  **`n`が最新の値を持つことの重要性**:
    このテストが検証しているのは、Goのコンパイラやランタイムが、ループ内で頻繁に更新される変数（この場合は`n`）をどのように扱うかという点です。パフォーマンス最適化のために、変数の値がCPUレジスタに一時的に保持され、すぐにメモリに書き戻されないことがあります。しかし、パニックのような非同期的なイベントが発生した場合、レジスタ上の古い値ではなく、メモリ上の最新の値が`defer`関数に「見える」ことが保証されなければなりません。このテストは、Goランタイムがこのような状況でも変数の可視性（visibility）と一貫性（consistency）を適切に管理していることを確認しています。

## コアとなるコードの変更箇所

このコミットによって追加されたファイルは`test/recover4.go`のみです。

```go
// +build linux darwin
// run

// Copyright 2015 The Go Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

// Test that if a slice access causes a fault, a deferred func
// sees the most recent value of the variables it accesses.
// This is true today; the role of the test is to ensure it stays true.
//
// In the test, memcopy is the function that will fault, during dst[i] = src[i].
// The deferred func recovers from the error and returns, making memcopy
// return the current value of n. If n is not being flushed to memory
// after each modification, the result will be a stale value of n.
//
// The test is set up by mmapping a 64 kB block of memory and then
// unmapping a 16 kB hole in the middle of it. Running memcopy
// on the resulting slice will fault when it reaches the hole.

package main

import (
	"log"
	"runtime/debug"
	"syscall"
	"unsafe"
)

func memcopy(dst, src []byte) (n int, err error) {
	defer func() {
		err = recover().(error)
	}()

	for i := 0; i < len(dst) && i < len(src); i++ {
		dst[i] = src[i]
		n++
	}
	return
}

func main() {
	// Turn the eventual fault into a panic, not a program crash,
	// so that memcopy can recover.
	debug.SetPanicOnFault(true)

	// Map 64 kB block of data with 16 kB hole in middle.
	data, err := syscall.Mmap(-1, 0, 64*1024, syscall.PROT_READ|syscall.PROT_WRITE, syscall.MAP_ANON|syscall.MAP_PRIVATE)
	if err != nil {
		log.Fatalf("mmap: %v", err)
	}

	// Note: Cannot call syscall.Munmap, because Munmap checks
	// that you are unmapping a whole region returned by Mmap.
	// We are trying to unmap just a hole in the middle.
	if _, _, err := syscall.Syscall(syscall.SYS_MUNMAP, uintptr(unsafe.Pointer(&data[32*1024])), 16*1024, 0); err != 0 {
		log.Fatalf("munmap: %v", err)
	}

	other := make([]byte, 64*1024)

	// Check that memcopy returns the actual amount copied
	// before the fault (32kB - 5, the offset we skip in the argument).
	n, err := memcopy(data[5:], other)
	if err == nil {
		log.Fatal("no error from memcopy across memory hole")
	}
	if n != 32*1024-5 {
		log.Fatal("memcopy returned %d, want %d", n, 32*1024-5)
	}
}
```

## コアとなるコードの解説

### `memcopy` 関数

```go
func memcopy(dst, src []byte) (n int, err error) {
	defer func() {
		err = recover().(error)
	}()

	for i := 0; i < len(dst) && i < len(src); i++ {
		dst[i] = src[i]
		n++
	}
	return
}
```
*   この関数は、バイトスライス`src`の内容を`dst`にコピーします。
*   `n`はコピーされたバイト数を追跡するカウンターです。
*   `defer`関数は、`memcopy`内でパニックが発生した場合に実行されます。`recover()`を呼び出すことでパニックを捕捉し、その値を`err`変数に代入します。これにより、パニックは捕捉され、`memcopy`関数はエラーを返して正常に終了します。
*   ループ`for i := 0; i < len(dst) && i < len(src); i++`内で、`dst[i] = src[i]`によってバイトコピーが行われ、`n++`によってコピーされたバイト数がインクリメントされます。この`n`の値が、パニック発生時に`defer`関数から正確に参照されるべき変数です。

### `main` 関数

```go
func main() {
	// Turn the eventual fault into a panic, not a program crash,
	// so that memcopy can recover.
	debug.SetPanicOnFault(true)

	// Map 64 kB block of data with 16 kB hole in middle.
	data, err := syscall.Mmap(-1, 0, 64*1024, syscall.PROT_READ|syscall.PROT_WRITE, syscall.MAP_ANON|syscall.MAP_PRIVATE)
	if err != nil {
		log.Fatalf("mmap: %v", err)
	}

	// Note: Cannot call syscall.Munmap, because Munmap checks
	// that you are unmapping a whole region returned by Mmap.
	// We are trying to unmap just a hole in the middle.
	if _, _, err := syscall.Syscall(syscall.SYS_MUNMAP, uintptr(unsafe.Pointer(&data[32*1024])), 16*1024, 0); err != 0 {
		log.Fatalf("munmap: %v", err)
	}

	other := make([]byte, 64*1024)

	// Check that memcopy returns the actual amount copied
	// before the fault (32kB - 5, the offset we skip in the argument).
	n, err := memcopy(data[5:], other)
	if err == nil {
		log.Fatal("no error from memcopy across memory hole")
	}
	if n != 32*1024-5 {
		log.Fatal("memcopy returned %d, want %d", n, 32*1024-5)
	}
}
```
*   `debug.SetPanicOnFault(true)`: メモリアクセス違反をGoのパニックに変換するように設定します。これにより、`memcopy`内の`defer`が機能します。
*   `syscall.Mmap(...)`: 64KBの匿名メモリ領域を確保し、`data`スライスとして扱います。
*   `syscall.Syscall(syscall.SYS_MUNMAP, ...)`: `data`スライスの中央（32KBオフセットから16KB）にメモリホールを作成します。これにより、この範囲へのアクセスはフォルトを引き起こします。
*   `other := make([]byte, 64*1024)`: コピー元となる別の64KBのバイトスライスを作成します。
*   `n, err := memcopy(data[5:], other)`: `memcopy`関数を呼び出します。`data[5:]`は、`data`スライスの先頭から5バイトオフセットした位置から始まるスライスです。これにより、実際にコピーされるバイト数は、メモリホールまでの距離からこのオフセットを引いた値になります。
*   `if err == nil`: `memcopy`がエラーを返さなかった場合、テストは失敗します。これは、意図的にフォルトを発生させているため、必ずエラーが返されるべきだからです。
*   `if n != 32*1024-5`: 最も重要な検証部分です。`memcopy`が返した`n`の値が、期待される値（メモリホールに到達するまでに実際にコピーされたバイト数）と一致するかどうかを確認します。期待される値は、メモリホールが始まる32KBから、`data[5:]`でスキップした5バイトを引いた`32*1024 - 5`です。このチェックが成功することで、`defer`関数がパニック発生時に`n`の最新の値を正確に捕捉していたことが証明されます。

# [インデックス 23190] ファイルの概要

このコミットは、Go言語の`time`パッケージ内の`TestAfterQueueing`テストのフレークネス（不安定性）を解消することを目的としています。特に、`go test -short`フラグが指定された際のテスト実行において、OSのスケジューリングのばらつきによってテストが失敗する問題を緩和するために、テストのリトライ時に使用する時間間隔（delta duration）を長くするように変更しています。

## 変更の背景

`TestAfterQueueing`というテストは、Goの`time.After`関数の正確なタイミングを検証するものです。このテストは、複数の独立したカーネルスレッドが互いに「delta」と呼ばれる短い時間間隔内にスケジューリングされることに依存しています。通常、この`delta`は100ミリ秒ですが、`go test -short`フラグを使用してテストを短縮実行する際には、20ミリ秒に短縮されます。

しかし、OpenBSDのような一部のオペレーティングシステムでは、CPUスケジューラが10ミリ秒のタイムスライスで動作します。この環境で、`all.bash`スクリプトのように複数のGoユニットテストが並行して実行されるなど、システムに高い負荷がかかると、20ミリ秒を超えるスケジューリング遅延が時折発生することが判明しました。この遅延が原因で、`TestAfterQueueing`テストが非決定論的に失敗する、いわゆる「フレークネス」が発生していました。

この問題は、GoのIssue 9903として報告されており、特にOpenBSD環境での最も一般的なテストのフレークネスの原因となっていました。このコミットは、この特定のテストのフレークネスを軽減し、テストの信頼性を向上させることを目的としています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の概念を把握しておく必要があります。

1.  **Goの`time`パッケージと`time.After`関数**:
    *   Go言語の標準ライブラリである`time`パッケージは、時間に関する機能を提供します。
    *   `time.After(d Duration)`関数は、指定された期間`d`が経過した後に、現在の時刻を送信するチャネルを返します。これは、特定の時間待機したり、タイムアウトを実装したりする際によく使用されます。
    *   `TestAfterQueueing`は、この`time.After`関数が、複数のゴルーチンが同時に`After`を呼び出した際に、期待される順序とタイミングでイベントを発生させるかを検証しています。

2.  **Goのテストと`testing.Short()`**:
    *   Goのテストフレームワークは、`go test`コマンドで実行されます。
    *   `testing`パッケージには、`Short()`という関数があります。これは、`go test -short`フラグがコマンドラインで指定された場合に`true`を返します。
    *   開発者は、この`Short()`関数を利用して、実行に時間がかかるテスト（例: ネットワークアクセス、ファイルI/O、長いスリープを伴うテスト）を、通常の開発サイクルではスキップしたり、実行時間を短縮したりすることができます。これにより、テストのフィードバックループを高速化できます。`TestAfterQueueing`も、この`Short()`フラグによって`delta`期間を短縮していました。

3.  **GoランタイムスケジューラとOSカーネルスケジューラ**:
    *   **Goランタイムスケジューラ**: Goは独自のランタイムスケジューラを持っており、多数の軽量な「ゴルーチン」を、限られた数のOSスレッド（カーネルスレッド）にマッピングして実行します。これにより、高い並行性を効率的に実現します。Goランタイムは、ゴルーチンの作成、実行、ブロック、アンブロック、そしてOSスレッドへのマッピングを管理します。
    *   **OSカーネルスケジューラ**: オペレーティングシステム（Linux, macOS, Windows, OpenBSDなど）には、CPU上でどのプロセスやスレッドを実行するかを決定するカーネルスケジューラがあります。これは、タイムスライス（一定の時間間隔）に基づいて、実行中のスレッドを切り替えたり、優先度に基づいてスレッドを中断・再開したりします。
    *   **相互作用**: Goランタイムスケジューラは、OSカーネルスケジューラが提供するOSスレッド上で動作します。したがって、Goのゴルーチンの実行タイミングは、Goランタイムスケジューラの決定だけでなく、基盤となるOSカーネルスケジューラの動作にも影響されます。特に、OSのタイムスライスが短い場合や、システム負荷が高い場合には、OSスレッドのスケジューリング遅延がGoのゴルーチンの実行タイミングに直接影響を及ぼし、`time.After`のような時間依存のテストにフレークネスを引き起こす可能性があります。

4.  **テストのフレークネス (Flakiness)**:
    *   フレークネスとは、テストが同じコードベースで同じテストを実行しても、成功したり失敗したりする非決定論的な振る舞いを指します。
    *   これは、並行処理、外部リソースへの依存（ネットワーク、ファイルシステム）、システム時刻、または今回のようにOSのスケジューリングのばらつきなど、非決定的な要因によって引き起こされることが多いです。
    *   フレークネスのあるテストは、開発者の信頼を損ない、CI/CDパイプラインの効率を低下させるため、可能な限り排除されるべきです。

## 技術的詳細

このコミットの技術的な解決策は、`TestAfterQueueing`テストがフレークネスを起こす原因となっていた、`delta`期間の短縮（20ミリ秒）を、テストのリトライ時に緩和することです。

具体的には、以下のロジックが導入されました。

1.  **`TestAfterQueueing`関数の変更**:
    *   このテストは、内部で`testAfterQueuing`というヘルパー関数を複数回（最大3回）呼び出してリトライするロジックを持っています。
    *   変更前は、`testAfterQueuing`関数内で`delta`の値を決定していました。`testing.Short()`が`true`の場合、`delta`は20ミリ秒に設定され、それ以外の場合は100ミリ秒でした。
    *   変更後、`TestAfterQueueing`関数は、リトライの最初の試行（`i == 0`）かつ`testing.Short()`が`true`の場合にのみ、`delta`を20ミリ秒に設定します。
    *   それ以降のリトライ（`i > 0`）では、`testing.Short()`が`true`であっても、`delta`はデフォルトの100ミリ秒に設定されます。
    *   この決定された`delta`値は、`testAfterQueuing`関数に引数として渡されるようになりました。

2.  **`testAfterQueuing`関数の変更**:
    *   このヘルパー関数は、以前は引数なしで呼び出され、内部で`delta`の値を決定していました。
    *   変更後、`delta Duration`という引数を受け取るようにシグネチャが変更されました。
    *   これにより、`testAfterQueuing`関数は、呼び出し元である`TestAfterQueuing`関数から渡された`delta`値を使用するようになります。
    *   内部の`time.After`の呼び出しや、エラーメッセージのフォーマットに使用される`target`計算において、この新しい`delta`引数が使用されます。

このアプローチにより、`go test -short`実行時でも、最初の試行でタイミングの問題が発生した場合、その後のリトライではより長い猶予期間（100ミリ秒）が与えられ、OSのスケジューリング遅延によるテスト失敗の可能性が大幅に減少します。これは、テストの信頼性を向上させつつ、通常時の高速なテスト実行という`testing.Short()`の目的も維持するバランスの取れた解決策です。

## コアとなるコードの解説

このコミットの核心的な変更は、`TestAfterQueuing`関数と、それが呼び出すヘルパー関数`testAfterQueuing`の間の`delta`（時間間隔）の渡し方と決定ロジックにあります。

1.  **`TestAfterQueuing`関数内での`delta`の決定**:
    *   変更前は、`testAfterQueuing(t)`と引数なしで呼び出していました。
    *   変更後、`for i := 0; i < attempts && err != nil; i++` ループ内で`delta`変数を定義しています。
    *   `delta := 100 * Millisecond` で初期値を100ミリ秒に設定します。
    *   `if i == 0 && testing.Short()` という条件が追加されました。これは、「最初の試行（`i == 0`）であり、かつ`go test -short`フラグが指定されている場合」を意味します。
    *   この条件が`true`の場合にのみ、`delta = 20 * Millisecond` と設定され、`delta`が短縮されます。
    *   つまり、`go test -short`で実行された場合でも、2回目以降のリトライでは`delta`は100ミリ秒のままとなり、より長い猶予期間が与えられます。
    *   そして、`if err = testAfterQueuing(t, delta); err != nil { ... }` のように、決定された`delta`値を`testAfterQueuing`関数に引数として渡しています。

2.  **`testAfterQueuing`関数のシグネチャ変更と`delta`の使用**:
    *   変更前は `func testAfterQueuing(t *testing.T) error` でした。
    *   変更後、`func testAfterQueuing(t *testing.T, delta Duration) error` となり、`delta`という`time.Duration`型の引数を受け取るようになりました。
    *   これにより、この関数は自身で`delta`の値を決定するロジック（`Delta := 100 * Millisecond; if testing.Short() { Delta = 20 * Millisecond }`）を削除し、呼び出し元から渡された`delta`を使用するようになります。
    *   関数内部の`time.After`の呼び出し (`After(Duration(slot)*delta)`) や、エラーメッセージ内のタイミング計算 (`target := Duration(slot) * delta`, `dt < target-delta/2 || dt > target+delta*10`) の全てで、この新しい`delta`引数が使用されています。

この変更により、テストのフレークネスの原因となっていた、高負荷時の短い`delta`期間での厳密なタイミング要件が、リトライ時には緩和されることになります。これにより、テストの信頼性が向上し、特にOpenBSDのような特定の環境でのテスト失敗が減少することが期待されます。

# [インデックス 21933] ファイルの概要

このコミットは、Goランタイムの`src/runtime/race_amd64.s`ファイルに対する変更です。`race_amd64.s`は、Goのデータ競合検出器（Race Detector）がAMD64アーキテクチャ上で動作するために必要な低レベルのアセンブリコードを含んでいます。具体的には、ThreadSanitizer (TSan) ライブラリとのインターフェースを提供し、メモリアクセスや関数呼び出しのインストゥルメンテーション（計測コードの挿入）を可能にします。このファイルは、Goプログラムが`-race`フラグ付きでビルドされた際に、TSanの関数（例: `__tsan_read`, `__tsan_write`, `__tsan_func_enter`, `__tsan_func_exit`）を呼び出すためのフックを提供します。

## コミット

このコミットは、Goランタイムのレースモードにおけるスタック破損のバグを修正します。以前のコードでは、`PUSHQ R15`で保存されたレジスタの値が、その直後の`MOVQ RARG0, 0(SP)`命令によって上書きされていました。これにより、呼び出し元の引数が破損する可能性があり、特に新しいレースランタイム環境で問題が顕在化しました。修正では、`MOVQ`を`PUSHQ`に変更して引数を正しくスタックにプッシュし、`CALL`命令の後に`POPQ R12`を追加して、スタックにプッシュされた引数の値を`R12`レジスタに復元することで、スタックの整合性を保ちます。

## 変更の背景

この変更の背景には、Goのデータ競合検出器（Race Detector）の内部動作と、スタックフレーム管理における潜在的なバグがありました。

Goのデータ競合検出器は、並行プログラムにおけるデータ競合（複数のゴルーチンが同期なしに同じメモリ位置にアクセスし、少なくとも一方が書き込みである場合に発生する競合）を動的に検出するための強力なツールです。これはGoogleのThreadSanitizer (TSan) をGoに移植したもので、プログラムのコンパイル時にメモリアクセスに計測コード（フック）を挿入し、実行時にシャドウメモリを維持して競合を検出します。

問題は、`runtime·racesymbolizethunk`というアセンブリ関数内で発生していました。この関数は、レース検出器が競合を報告する際に、シンボル情報を解決するために呼び出される補助的な関数です。この関数内で、`PUSHQ R15`命令によって`R15`レジスタの値がスタックに保存された直後に、`MOVQ RARG0, 0(SP)`という命令が実行されていました。

ここで重要なのは、`0(SP)`がスタックポインタ`SP`が指す現在のスタックトップのアドレスを意味することです。`PUSHQ R15`が実行されると、`SP`は8バイト減少し、`R15`の値がその新しい`SP`が指すアドレス（つまり`0(SP)`）に書き込まれます。したがって、その直後の`MOVQ RARG0, 0(SP)`は、`PUSHQ R15`によって保存されたばかりの`R15`の値を、`RARG0`（関数の第一引数レジスタ、またはその値）で上書きしてしまっていました。

このスタックの破損は、既存のレースランタイムでは「どうにか動作していた」とコミットメッセージにありますが、これはおそらく、上書きされた`R15`の値が後で必要とされなかったか、あるいは別の方法で復元されていたため、顕在化しなかったことを示唆しています。しかし、新しいレースランタイムのテスト中に、このスタック破損が呼び出し元の引数を破壊し、問題を引き起こすことが判明しました。これは、新しいランタイムがスタックの整合性に対してより厳密であるか、あるいは`R15`レジスタの利用方法が変更されたためと考えられます。

このバグは、Goランタイムの安定性とレース検出器の正確性に直接影響するため、修正が必要でした。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の前提知識が必要です。

1.  **Goのデータ競合検出器 (Race Detector)**:
    *   Go言語に組み込まれたツールで、並行処理におけるデータ競合（複数のゴルーチンが共有メモリにアクセスし、少なくとも一方が書き込みであり、かつ同期メカニズムがない場合に発生する競合）を検出します。
    *   `go build -race`のように`-race`フラグを付けてビルドすることで有効になります。
    *   内部的にはGoogleのThreadSanitizer (TSan) を利用しており、コンパイル時にメモリアクセスに計測コード（インストゥルメンテーション）を挿入し、実行時にシャドウメモリを管理して競合を検出します。
    *   検出時には、競合が発生したメモリ位置、関連するゴルーチンのスタックトレースなどの詳細なレポートを出力します。

2.  **x86-64 アセンブリ言語**:
    *   AMD64（x86-64）アーキテクチャ用の低レベルプログラミング言語です。Goランタイムのパフォーマンスが重要な部分や、OSとのインタラクションが必要な部分で利用されます。
    *   **レジスタ**: CPU内部の高速な記憶領域です。
        *   `SP` (Stack Pointer): スタックの現在のトップ（最上位アドレス）を指すレジスタです。x86-64ではスタックは高アドレスから低アドレスに向かって成長します。
        *   `R15`, `R12`: 汎用レジスタ。Goランタイムでは特定の目的で使用されることがあります。
        *   `RARG0`: Goのアセンブリコード内で、関数の第一引数が格納されるレジスタ（またはその値）を示す慣習的な名前です。Go 1.17以降はレジスタベースの呼び出し規約が導入されましたが、このコミットは2015年のものであり、当時のGoの内部的な呼び出し規約に基づいています。AMD64では、通常、引数はスタック経由で渡されるか、特定のレジスタ（例: `RDI`, `RSI`など）が使用されますが、Goランタイムのアセンブリでは抽象化された名前が使われることがあります。
    *   **命令**:
        *   `MOVQ source, destination`: `source`から`destination`へ8バイト（Quadword）のデータを移動します。`Q`はQuadword（64ビット）を意味します。
        *   `PUSHQ source`: `source`の値をスタックにプッシュします。`SP`を8減らし、そのアドレスに`source`の値を書き込みます。
        *   `POPQ destination`: スタックトップの値を`destination`にポップします。`SP`が指すアドレスから8バイトの値を読み出し、`SP`を8増やします。
        *   `CALL function`: `function`を呼び出します。現在の命令の次のアドレス（リターンアドレス）をスタックにプッシュし、`function`のアドレスにジャンプします。
        *   `TEXT symbol(SB), flags, frame_size-arg_size`: Goアセンブリにおける関数の定義です。`SB`はStatic Baseで、グローバルシンボルや関数のアドレスの基準となります。

3.  **スタックフレーム**:
    *   関数が呼び出されるたびに、その関数が使用するローカル変数、引数、リターンアドレスなどを格納するためにスタック上に確保される領域です。
    *   x86-64ではスタックは高アドレスから低アドレスに向かって成長するため、`PUSH`命令は`SP`を減らし、`POP`命令は`SP`を増やします。
    *   `0(SP)`は、現在の`SP`が指すメモリ位置、つまりスタックの最上位を意味します。

4.  **GoランタイムのG-M-Pモデルと`g0`**:
    *   GoのスケジューラはG（Goroutine）、M（OSスレッド）、P（プロセッサ）の3つの要素で構成されます。
    *   `G`: Goの軽量な並行実行単位。
    *   `M`: 実際のOSスレッド。ゴルーチンを実行します。
    *   `P`: 論理プロセッサ。Mに割り当てられ、Gを実行するためのコンテキストを提供します。
    *   `g0`: 各M（OSスレッド）に紐付けられた特別なゴルーチンです。ユーザーコードは実行せず、ランタイムの内部タスク（スケジューリング、スタックの管理、システムコールハンドリングなど）を担当します。`g0`は通常のゴルーチンよりも大きな固定スタックを持ち、スタックの成長や縮小、CGO呼び出しなど、スタックを大きく使う可能性のある処理や、プリエンプション（横取り）されては困る処理を実行します。このコミットの対象である`race_amd64.s`内の関数は、このようなランタイムの低レベルな処理の一部として`g0`のコンテキストで実行される可能性があります。

## 技術的詳細

このコミットの技術的な核心は、x86-64アセンブリにおけるスタック操作の正確性にあります。

問題のコードは`src/runtime/race_amd64.s`内の`TEXT runtime·racesymbolizethunk(SB), NOSPLIT, $56-8`関数の一部でした。この関数は、Goのレース検出器がデータ競合を検出した際に、その競合に関連するシンボル情報を解決するために呼び出されます。

元のコードは以下のようになっていました。

```assembly
	MOVQ	g_m(R13), R13
	MOVQ	m_g0(R13), R14
	MOVQ	R14, g(R12)	// g = m->g0
	PUSHQ	R15             // R15をスタックに保存
	MOVQ	RARG0, 0(SP)	// func arg (ここでスタック破損が発生)
	CALL	runtime·racesymbolize(SB)
	// ... 後続のコード ...
```

ここで、`PUSHQ R15`命令は、`R15`レジスタの現在の値をスタックに保存します。x86-64アーキテクチャではスタックは高アドレスから低アドレスに向かって成長するため、`PUSHQ`命令はスタックポインタ`SP`を8バイト（Quadwordのサイズ）減らし、その新しい`SP`が指すアドレスに`R15`の値を書き込みます。したがって、この時点で`R15`の値は`0(SP)`に格納されています。

その直後の`MOVQ RARG0, 0(SP)`命令は、`RARG0`の値を`0(SP)`、つまり現在のスタックトップに移動させようとします。しかし、この`0(SP)`はまさに直前に`PUSHQ R15`によって`R15`が保存された場所です。結果として、`R15`の保存された値が`RARG0`の値によって上書きされてしまい、スタックが破損します。コミットメッセージにある「`MOVQ RARG0, 0(SP) smashes exactly what was saved by PUSHQ R15.`」という記述は、この状況を正確に表しています。

このスタック破損は、`runtime·racesymbolizethunk`を呼び出した関数（呼び出し元）のスタックフレームに影響を与え、特に呼び出し元の引数が破壊される可能性がありました。古いレースランタイムではこの問題が顕在化しなかったのは、おそらく`R15`の値が後で参照されなかったか、あるいは別のメカニズムで復元されていたためと考えられます。しかし、新しいレースランタイムでは、このスタックの整合性の問題が致命的なバグとして現れました。

修正後のコードは以下のようになります。

```assembly
	MOVQ	g_m(R13), R13
	MOVQ	m_g0(R13), R14
	MOVQ	R14, g(R12)	// g = m->g0
	PUSHQ	R15             // R15をスタックに保存
	PUSHQ	RARG0	        // func arg (RARG0をスタックに正しくプッシュ)
	CALL	runtime·racesymbolize(SB)
	POPQ	R12             // スタックから値をR12にポップ
	// All registers are smashed after Go code, reload.
	get_tls(R12)
	MOVQ	g(R12), R13
	// ... 後続のコード ...
```

修正では、`MOVQ RARG0, 0(SP)`を`PUSHQ RARG0`に置き換えています。
1.  `PUSHQ R15`: `SP`が8減少し、`R15`が`[SP]`に保存されます。
2.  `PUSHQ RARG0`: `SP`がさらに8減少し、`RARG0`が新しい`[SP]`に保存されます。この時点で、スタックには`RARG0`が`0(SP)`に、`R15`が`8(SP)`に正しく配置されます。これにより、`R15`の値が上書きされることはなくなります。
3.  `CALL runtime·racesymbolize(SB)`: `runtime·racesymbolize`関数が呼び出されます。この命令はリターンアドレスをスタックにプッシュします。
4.  `POPQ R12`: `CALL`命令の後に`POPQ R12`が追加されています。これは、`runtime·racesymbolize`関数から戻った後、スタックトップ（この場合は`RARG0`がプッシュされた場所）から値を`R12`レジスタにポップすることを意味します。コミットメッセージの「`All registers are smashed after Go code, reload.`」というコメントから、`runtime·racesymbolize`のようなGoコードを呼び出した後、レジスタの状態が不定になるため、`R12`レジスタに`RARG0`の値を復元する必要があったと考えられます。これは、`R12`が後続の処理で`RARG0`の値を必要とするか、あるいは`R12`が特定の役割を担っており、その役割を果たすために`RARG0`の値で初期化する必要があったことを示唆しています。

この修正により、スタックの整合性が保たれ、呼び出し元の引数が破損する問題が解決されました。

## コアとなるコードの解説

変更されたのは、`runtime·racesymbolizethunk`というアセンブリ関数内の以下の部分です。

**変更前:**
```assembly
	MOVQ	RARG0, 0(SP)	// func arg
	CALL	runtime·racesymbolize(SB)
```
*   `MOVQ RARG0, 0(SP)`: この命令は、`RARG0`（関数の第一引数、またはその値）の値を、現在のスタックポインタ`SP`が指すアドレス（`0(SP)`）に移動させます。しかし、この直前には`PUSHQ R15`（差分には含まれていませんが、コミットメッセージと文脈から存在が示唆されます）が実行されており、`0(SP)`には`R15`の保存された値が格納されていました。したがって、この`MOVQ`命令は`R15`の保存された値を`RARG0`の値で上書きしてしまい、スタック破損を引き起こしていました。
*   `CALL runtime·racesymbolize(SB)`: `runtime·racesymbolize`関数を呼び出します。この命令は、現在の命令の次のアドレス（リターンアドレス）をスタックにプッシュし、`runtime·racesymbolize`の先頭にジャンプします。

**変更後:**
```assembly
	PUSHQ	RARG0	// func arg
	CALL	runtime·racesymbolize(SB)
	POPQ	R12
```
*   `PUSHQ RARG0`: `MOVQ`命令が`PUSHQ`命令に置き換えられました。これにより、`RARG0`の値はスタックポインタ`SP`を8バイト減らした新しいアドレスにプッシュされます。この結果、`R15`の保存された値（もし`PUSHQ R15`が先に実行されていれば）は上書きされず、`RARG0`の値はスタックに正しく追加されます。
*   `CALL runtime·racesymbolize(SB)`: 変更前と同じく、`runtime·racesymbolize`関数を呼び出します。
*   `POPQ R12`: `CALL`命令の後に新しく追加された命令です。これは、スタックトップ（`PUSHQ RARG0`によってプッシュされた`RARG0`の値が格納されている場所）から値をポップし、それを`R12`レジスタに格納します。この操作は、`runtime·racesymbolize`の呼び出しによって`R12`レジスタが「smashed」（値が不定になった）状態になった後、`R12`を`RARG0`の元の値で復元する必要があったことを示唆しています。これは、後続のコードで`R12`が`RARG0`の値を必要とするため、または`R12`が特定のランタイムコンテキスト情報を保持しており、その情報が`RARG0`の値と関連しているためと考えられます。

この変更により、スタックの整合性が保たれ、レース検出器が正しく機能するための基盤が強化されました。

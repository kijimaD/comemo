# [インデックス 21486] ファイルの概要

このコミットは、Go言語の`math/big`パッケージにおける`amd64`アーキテクチャ向けアセンブリカーネルのパフォーマンス最適化に関するものです。具体的には、多倍長整数（big.Int）の加算・減算処理（`AddVx`および`SubVx`）において、キャリーフラグ（Carry Flag, CF）の保存と復元に使用されていた回転命令（`RCRQ`, `RCLQ`）を、より効率的な算術命令（`ADDQ`, `SBBQ`）に置き換えることで、処理速度の向上を図っています。この変更は、著名な多倍長整数ライブラリであるGMPの作者、Torbjörn Granlund氏の提案に基づいています。

## 変更の背景

この変更の主な背景は、Go言語の`math/big`パッケージが提供する多倍長整数演算のパフォーマンス改善です。特に、`amd64`アーキテクチャにおける低レベルのアセンブリコードの最適化が目的でした。

従来の`AddVx`および`SubVx`アセンブリカーネルでは、多倍長整数演算において重要な役割を果たすキャリーフラグ（Carry Flag, CF）の保存と復元に、`RCRQ`（Rotate Carry Right Quadword）や`RCLQ`（Rotate Carry Left Quadword）といった回転命令が使用されていました。しかし、現代のCPUアーキテクチャでは、これらの回転命令はパイプラインのストールを引き起こしやすく、`ADDQ`や`SBBQ`のようなより単純な算術命令に比べて実行速度が遅くなる傾向があることが知られています。

この問題に対し、任意精度演算ライブラリのデファクトスタンダードであるGMP（GNU Multiple Precision Arithmetic Library）の主要開発者であるTorbjörn Granlund氏から、`ADDQ`/`SBBQ`命令を用いたより効率的なキャリーフラグ操作のテクニックが提案されました。この提案を受け、Goチームは`math/big`パッケージのアセンブリコードを修正し、ベンチマーク結果が示すように、特に大きな数値を扱う場合に顕著な性能向上が実現されました。

## 前提知識の解説

### `math/big`パッケージ

Go言語の標準ライブラリの一部であり、任意精度の数値型（`Int`, `Rat`, `Float`）を提供します。Goの組み込み型である`int`や`int64`では表現できない、非常に大きな整数や、高い精度が要求される浮動小数点数、有理数を扱う際に使用されます。暗号学、科学計算、金融アプリケーションなど、正確な数値計算が不可欠な分野で利用されます。

### 多倍長整数演算 (Big Integer Arithmetic)

コンピュータのCPUが一度に処理できるワードサイズ（例: 64ビット）を超える数値を扱うための演算手法です。多倍長整数は、複数のワード（通常は`uint`や`uint64`のような符号なし整数型）の配列として表現されます。加算、減算、乗算、除算などの演算は、これらのワードを一つずつ処理し、各ワード間のキャリー（繰り上がり）やボロー（繰り下がり）を適切に伝播させることで実現されます。このキャリー/ボローの伝播が、多倍長整数演算の性能を左右する重要な要素となります。

### `AddVx` / `SubVx`

`math/big`パッケージ内部で使用される、多倍長整数演算の基盤となるアセンブリ関数です。`AddVx`は2つの多倍長整数ベクトル（ワードの配列）の加算を行い、`SubVx`は減算を行います。これらの関数は、Goのソースコードからは直接呼び出されず、`math/big`パッケージのより高レベルな関数（例: `Int.Add`, `Int.Sub`）から利用されます。アセンブリ言語で実装されているのは、CPUのレジスタやフラグを直接操作することで、最大限のパフォーマンスを引き出すためです。

### キャリーフラグ (Carry Flag, CF)

CPUのフラグレジスタ（x86-64では`RFLAGS`レジスタ）内の単一のビットです。算術演算の結果、符号なし数のオーバーフロー（加算で最上位ビットからの繰り上がり）や、減算でボロー（借り入れ）が発生したことを示します。多倍長整数演算では、あるワードの演算で発生したキャリー/ボローを、次の上位ワードの演算に引き継ぐためにこのキャリーフラグが利用されます。

### `RCRQ` (Rotate Carry Right Quadword) / `RCLQ` (Rotate Carry Left Quadword)

x86-64アーキテクチャのアセンブリ命令です。
*   `RCRQ`: 指定されたレジスタの内容を、キャリーフラグを含めて右にビット回転させます。最下位ビットがキャリーフラグに移動し、キャリーフラグの以前の値が最上位ビットに移動します。
*   `RCLQ`: 指定されたレジスタの内容を、キャリーフラグを含めて左にビット回転させます。最上位ビットがキャリーフラグに移動し、キャリーフラグの以前の値が最下位ビットに移動します。

これらの命令は、キャリーフラグをデータの一部として扱うことができるため、多倍長整数演算におけるキャリーの伝播に利用されることがあります。しかし、現代のCPUでは、これらの命令は複雑なマイクロコードに変換されることが多く、パイプラインの効率を低下させる可能性があります。

### `ADDQ` (Add Quadword) / `SBBQ` (Subtract with Borrow Quadword)

x86-64アーキテクチャの基本的な算術命令です。
*   `ADDQ`: 2つのオペランドを加算します。結果がレジスタの最大値を超えた場合、キャリーフラグがセットされます。
*   `SBBQ`: 2つのオペランドを減算し、さらにキャリーフラグ（ボローとして扱われる）の値を減算します。結果が負になった場合（ボローが必要な場合）、キャリーフラグがセットされます。

これらの命令は、CPUにとって非常に基本的な操作であり、通常は非常に高速に実行されます。特に、`SBBQ Rx, Rx` や `ADDQ Rx, Rx` のように同じレジスタに対して演算を行うことで、キャリーフラグの状態をレジスタに保存したり、レジスタの値からキャリーフラグを復元したりするテクニックが存在します。

### GMP (GNU Multiple Precision Arithmetic Library)

任意精度演算のためのフリーソフトウェアライブラリであり、C言語で書かれています。非常に高速で最適化されており、多くのプログラミング言語や数学ソフトウェアのバックエンドとして利用されています。Torbjörn Granlund氏は、このライブラリの主要な貢献者の一人であり、多倍長整数演算の分野における世界的な権威です。

## 技術的詳細

このコミットの技術的な核心は、`amd64`アセンブリコードにおけるキャリーフラグの操作方法の変更です。

### 従来のキャリーフラグ操作（`RCRQ`/`RCLQ`を使用）

多倍長整数演算のループ内では、各ワードの加算/減算の前に前回の演算で発生したキャリーフラグをCPUのCFに復元し、演算後に現在のワードで発生したキャリーフラグをレジスタに保存する必要があります。

*   **キャリーフラグの復元 (`CF = c`)**: `RCRQ $1, CX`
    *   `CX`レジスタに保存されているキャリーの状態（例えば、前のワードの演算結果のキャリー）をCPUのCFに復元するために使用されていました。`CX`の最下位ビットがCFに移動し、CFの以前の値が`CX`の最上位ビットに移動します。
*   **キャリーフラグの保存 (`c = CF`)**: `RCLQ $1, CX`
    *   CPUのCFの状態を`CX`レジスタに保存するために使用されていました。CFの以前の値が`CX`の最下位ビットに移動し、`CX`の最上位ビットがCFに移動します。

これらの回転命令は、キャリーフラグを直接操作できるという点で便利ですが、現代のCPUのパイプライン処理においては、その複雑さから性能ボトルネックとなることがありました。特に、CFへの依存関係が長く続く場合、CPUの命令並列実行能力が十分に活用されない可能性があります。

### 新しいキャリーフラグ操作（`ADDQ`/`SBBQ`を使用）

Torbjörn Granlund氏の提案に基づき、より高速な`ADDQ`/`SBBQ`命令の組み合わせが採用されました。

*   **キャリーフラグの保存 (`c = CF`)**: `SBBQ CX, CX`
    *   この命令は `CX = CX - CX - CF` を計算します。
    *   もしCPUのCFがセットされていれば（CF=1）、`CX - CX - 1` となり、結果は`-1`（64ビット全てが1）になります。
    *   もしCPUのCFがクリアされていれば（CF=0）、`CX - CX - 0` となり、結果は`0`になります。
    *   これにより、CPUのCFの状態が`CX`レジスタに効率的に保存されます。
    *   その後、Goの`Word`型（`uint64`）がキャリーを`0`または`1`として扱うため、`NEGQ CX`命令が追加されることがあります。`NEGQ`は2の補数を計算する命令で、`-1`を`1`に、`0`を`0`に変換します。

*   **キャリーフラグの復元 (`CF = c`)**: `ADDQ CX, CX`
    *   この命令は `CX = CX + CX` を計算します。
    *   もし`CX`レジスタに保存されているキャリーの状態が`-1`（すべてのビットが1、つまり元のCFが1だった場合）であれば、`ADDQ`によってオーバーフローが発生し、CPUのCFがセットされます。
    *   もし`CX`レジスタに保存されているキャリーの状態が`0`であれば、`ADDQ`はオーバーフローせず、CPUのCFはクリアされます。
    *   これにより、`CX`レジスタに保存されたキャリーの状態がCPUのCFに効率的に復元されます。

この新しいアプローチは、CPUにとってより単純で予測しやすい算術命令を使用するため、パイプラインの効率が向上し、命令の実行スループットが高まります。特に、多倍長整数演算のように、キャリーフラグの操作がループ内で頻繁に行われる処理においては、この最適化が全体的な性能に大きく寄与します。

コミットメッセージに含まれるベンチマーク結果は、この最適化の効果を明確に示しています。特に、`BenchmarkAddVV_1e3`や`BenchmarkAddVV_1e4`のように、より大きな多倍長整数を扱うベンチマークでは、最大で約20%近い性能向上が見られます。これは、多倍長整数演算の基盤となるアセンブリルーチンの効率が、アプリケーション全体の性能にどれほど影響を与えるかを示しています。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は、`src/math/big/arith_amd64.s`ファイルに集中しています。

*   **`src/math/big/arith_amd64.s`**:
    *   `addVV` (vector-vector加算), `subVV` (vector-vector減算), `addVW` (vector-word加算), `subVW` (vector-word減算) の各アセンブリ関数において、キャリーフラグの保存と復元ロジックが変更されました。
    *   具体的には、以下の命令の置き換えが行われました:
        *   `RCRQ $1, CX` が `ADDQ CX, CX` に変更。
        *   `RCLQ $1, CX` が `SBBQ CX, CX` に変更。
    *   一部の箇所で、`SBBQ CX, CX` の後に `NEGQ CX` が追加されています。これは、`SBBQ CX, CX` の結果（`-1`または`0`）をGoの`Word`型が期待するキャリーの値（`1`または`0`）に変換するためです。
    *   不要になった`ZERO_CX`マクロが削除されました。
*   **`src/math/big/arith_386.s`**:
    *   このファイル自体には直接的なコード変更はありませんが、コメントとして`// TODO(gri) Replace uses of RCRL/RCLL with ADDL/SBBL respectively.`が追加されており、将来的に32ビット版のアセンブリコードでも同様の最適化を行う意図が示されています。

## コアとなるコードの解説

`src/math/big/arith_amd64.s`内の`addVV`や`subVV`といった関数は、多倍長整数を構成する各ワード（64ビット）に対して、アセンブリレベルで加算や減算を行うループを含んでいます。これらのループの各イテレーションで、前回のワード演算からのキャリー（またはボロー）を考慮し、現在のワード演算の結果発生したキャリーを次のイテレーションに渡す必要があります。

変更前は、このキャリーの伝播に`RCRQ`と`RCLQ`が使われていました。例えば、`addVV`のループ内では:

```assembly
U1: // n >= 0
    // regular loop body unrolled 4x
    RCRQ $1, CX         // CF = c (CXに保存されたキャリーをCFに復元)
    MOVQ 0(R8)(SI*8), R11
    ADCQ 0(R9)(SI*8), R11 // R11 = R11 + 0(R9) + CF (キャリーを考慮した加算)
    ...
    RCLQ $1, CX         // c = CF (現在のCFをCXに保存)
```

変更後は、これが以下のように置き換えられました:

```assembly
U1: // n >= 0
    // regular loop body unrolled 4x
    ADDQ CX, CX         // restore CF (CXに保存されたキャリーをCFに復元)
    MOVQ 0(R8)(SI*8), R11
    ADCQ 0(R9)(SI*8), R11 // R11 = R11 + 0(R9) + CF (キャリーを考慮した加算)
    ...
    SBBQ CX, CX         // save CF (現在のCFをCXに保存)
    // NEGQ CX           // (一部の箇所で追加される)
```

この変更により、CPUはより効率的な命令パスを実行できるようになり、特に多倍長整数演算のように多数のワードを連続して処理するシナリオで、顕著な性能向上が見られました。`NEGQ CX`の追加は、`SBBQ CX, CX`がキャリーフラグの状態を`-1`または`0`として`CX`に保存するため、Goの`uint64`型でキャリーを`1`または`0`として扱うための変換です。

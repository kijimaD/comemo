## 変更の背景

このコミットは、Go言語のコンパイラにおける `stringtoslicebytetmp` 最適化に関するバグを修正するために行われました。この最適化は、文字列をバイトスライスに変換する際に、可能な限り新しいメモリ割り当てを避けて、元の文字列のバッキングストレージを再利用しようとするものです。これは特に、`for ... range []byte(str)` のようなイディオムで文字列をバイト単位でイテレートする際にパフォーマンスを向上させることを目的としています。

しかし、Go issue #14973 (タイトル: `cmd/compile: stringtoslicebytetmp optimization is not applied to range over []byte(string)`) で報告されたように、この最適化が特定の条件下で正しく適用されない問題がありました。具体的には、`order.go` 内の `ORANGE` (レンジループ) の処理において、`[]byte(str)` のような式が `OSTRARRAYBYTE` オペレーションとして認識された際に、`OSTRARRAYBYTETMP` に変換されるべき箇所が、`TARRAY` のケースの内部に誤って配置されていました。これにより、`TARRAY` 以外のレンジループ（例えば `TSTRING` や `TCHAN`）では、この最適化が適用されず、不要なメモリ割り当てが発生していました。

このバグは、特に短い文字列を頻繁にバイトスライスに変換してイテレートするようなシナリオで、パフォーマンスの低下や余分なガベージコレクションを引き起こす可能性がありました。

## 前提知識の解説

### Goコンパイラの最適化

Goコンパイラは、生成されるバイナリのパフォーマンスを向上させるために様々な最適化を行います。その一つが、メモリ割り当てを減らすための最適化です。Goではガベージコレクタがメモリ管理を行いますが、不要なメモリ割り当てを減らすことはGCの負荷を軽減し、全体的な実行速度を向上させます。

### `stringtoslicebytetmp` 最適化

Goの文字列はイミュータブル（不変）です。一方、バイトスライス (`[]byte`) はミュータブル（可変）です。`[]byte(str)` のように文字列をバイトスライスに型変換すると、通常は新しいバイトスライスが作成され、文字列の内容がコピーされます。これは、元の文字列のバッキング配列が変更されることを防ぐためです。

しかし、`for ... range []byte(str)` のように、変換されたバイトスライスがループ内で一時的に使用され、かつその内容が変更されないことがコンパイラによって保証できる場合、コンパイラは最適化として新しいバイトスライスの作成とコピーを省略し、元の文字列のバッキングストレージを直接参照する一時的なバイトスライス (`OSTRARRAYBYTETMP`) を生成することがあります。これにより、メモリ割り当てとコピーのオーバーヘッドが削減されます。

### `cmd/compile/internal/gc/order.go`

このファイルはGoコンパイラのバックエンドの一部であり、AST (Abstract Syntax Tree) のノードを処理し、実行順序を決定する役割を担っています。特に、`orderstmt` 関数は様々なステートメント（文）の処理順序を決定し、最適化の機会を探します。`ORANGE` は `for ... range` ループを表すASTノードです。

### `OSTRARRAYBYTE` と `OSTRARRAYBYTETMP`

これらはGoコンパイラ内部で使用されるオペレーションコード（OpCode）です。
*   `OSTRARRAYBYTE`: 文字列からバイトスライスへの通常の変換を表します。新しいメモリ割り当てとコピーが発生します。
*   `OSTRARRAYBYTETMP`: 最適化された文字列からバイトスライスへの変換を表します。元の文字列のバッキングストレージを再利用し、メモリ割り当てを回避します。

### `testing.AllocsPerRun`

Goの `testing` パッケージに含まれる関数で、指定された関数が実行される間に発生するメモリ割り当ての回数を計測するために使用されます。これにより、特定のコードパスにおけるメモリ効率を評価し、最適化の効果を確認することができます。

## 技術的詳細

このコミットの核心は、`src/cmd/compile/internal/gc/order.go` ファイル内の `orderstmt` 関数の `ORANGE` ケースにおけるロジックの変更です。

変更前は、`[]byte(str)` のような `OSTRARRAYBYTE` オペレーションを `OSTRARRAYBYTETMP` に変換するロジックが、`TARRAY` 型のレンジループを処理する `case TARRAY:` ブロックの内部にありました。これは、`for ... range` の対象が配列型である場合にのみ、この最適化が考慮されることを意味していました。

しかし、`[]byte(str)` は、Goの型システム上はスライス型であり、`TARRAY` ではなく `TSTRING` や `TCHAN` と同じく、`n.Type.Etype` が `TSTRING` のケースで処理されるべきです。このため、`TARRAY` のケースに最適化ロジックが埋め込まれていると、`[]byte(str)` のような文字列をバイトスライスに変換してレンジループを行う場合に、`OSTRARRAYBYTETMP` への変換が行われず、常に新しいバイトスライスが割り当てられていました。

このコミットでは、`OSTRARRAYBYTE` を `OSTRARRAYBYTETMP` に変換するロジックを、`ORANGE` ケースの冒頭、つまり `n.Right` (レンジ対象の式) を `orderexpr` で処理する前に移動させました。これにより、レンジ対象の式が `OSTRARRAYBYTE` である場合、その型が何であるかに関わらず、まず `OSTRARRAYBYTETMP` に変換されるようになります。その後、`orderexpr` が呼び出され、適切な順序付けが行われます。

この変更により、`for ... range []byte(str)` のようなコードが、コンパイラによって正しく `stringtoslicebytetmp` 最適化の対象となり、不要なメモリ割り当てが削減され、パフォーマンスが向上します。

また、`src/runtime/string_test.go` にも変更が加えられています。`TestCompareTempString` と `TestRangeStringCast` のテストケースで、テスト対象の文字列の長さを `sizeNoStack` (100バイト) に変更しています。これは、短い文字列やスライスがエスケープ解析によってスタックに割り当てられることを防ぎ、`AllocsPerRun` が正確にヒープ割り当てを計測できるようにするためです。スタック割り当てされると `AllocsPerRun` の計測結果に影響を与え、最適化の効果を正しく評価できなくなるため、より大きな文字列を使用することで、ヒープ割り当てが発生する状況を確実に再現しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/order.go` の変更

*   **移動された最適化ロジック**: 以前は `case TARRAY:` ブロック内にあった `if n.Right.Op == OSTRARRAYBYTE { n.Right.Op = OSTRARRAYBYTETMP }` という行が、`ORANGE` ケースの冒頭に移動されました。
    *   **変更前**: `TARRAY` 型のレンジループの場合にのみ、文字列からバイトスライスへの変換が `OSTRARRAYBYTETMP` に最適化される可能性がありました。
    *   **変更後**: `ORANGE` (レンジループ) の `n.Right` (レンジ対象の式) が `OSTRARRAYBYTE` である場合、その型が `TARRAY` であろうと `TSTRING` であろうと、まず `OSTRARRAYBYTETMP` に変換されます。これにより、`for ... range []byte(str)` のようなイディオムが常にこの最適化の恩恵を受けられるようになります。
*   **コメントの整理**: コードの移動に伴い、関連するコメントも整理され、最適化の意図がより明確になりました。

### `src/runtime/string_test.go` の変更

*   **`sizeNoStack` 定数の追加**: `const sizeNoStack = 100` が追加されました。これは、スタック割り当てを回避するための閾値として使用されます。
*   **テスト文字列の変更**: `TestCompareTempString` と `TestRangeStringCast` の中で使用されるテスト文字列が、`"foo"` や `"abc"` のような短い文字列から `strings.Repeat("x", sizeNoStack)` のように `sizeNoStack` の長さを持つ文字列に変更されました。
    *   **目的**: `testing.AllocsPerRun` を使用してメモリ割り当てを正確に計測するためです。Goのエスケープ解析は、短い文字列やスライスがヒープではなくスタックに割り当てられることを決定する場合があります。スタック割り当ては `AllocsPerRun` の計測対象外となるため、最適化の効果を正しく評価できません。`sizeNoStack` 以上の長さの文字列を使用することで、確実にヒープ割り当てが発生する状況を作り出し、`stringtoslicebytetmp` 最適化によるヒープ割り当て削減の効果を正確に検証できるようにしています。

これらの変更により、Goコンパイラは `[]byte(str)` のレンジループにおいて、より効率的なコードを生成できるようになり、同時にその最適化を正確にテストするための基盤も強化されました。

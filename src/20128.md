## 変更の背景

このコミットは、Goの `html/template` パッケージにおける特定のバグ（Issue #8431）を修正するために行われました。このバグは、セキュリティ上の理由からエスケープ処理が必要なHTMLテンプレートにおいて、そのエスケープ処理が失敗した場合に発生しました。

具体的には、エスケープ処理に失敗したテンプレートを一度実行した後、同じテンプレートを再度実行しようとすると、Goプログラムがパニック（実行時エラーによる強制終了）を起こしてしまうという問題がありました。ライブラリがパニックを起こすことは、そのライブラリを使用するアプリケーション全体の安定性を損なうため、非常に望ましくありません。ライブラリはエラーを適切に返し、アプリケーションがそのエラーを処理できるようにすべきです。

このコミットの目的は、エスケープ処理の失敗を適切に管理し、テンプレートの再実行時にパニックではなく、以前のエスケープエラーを返すようにすることで、ライブラリの堅牢性を向上させることです。

## 前提知識の解説

### `html/template` パッケージ

`html/template` はGo言語の標準ライブラリで、HTML出力を生成するためのテンプレートエンジンを提供します。このパッケージの最も重要な特徴は、**自動エスケープ機能**です。これは、テンプレートに挿入されるデータが自動的にサニタイズ（無害化）され、クロスサイトスクリプティング（XSS）などのWebセキュリティ脆弱性を防ぐのに役立ちます。

### テンプレートのエスケープ処理

Webアプリケーションにおいて、ユーザーからの入力や外部のデータを直接HTMLに出力すると、悪意のあるスクリプトが埋め込まれてしまう可能性があります（XSS攻撃）。`html/template` は、このような攻撃を防ぐために、テンプレートの実行時に出力される内容を文脈に応じて自動的にエスケープします。例えば、HTML要素の属性値として出力される文字列は、`"` や `<` などの特殊文字が `&quot;` や `&lt;` のように変換されます。

エスケープ処理は、テンプレートの構文解析後、実行前に一度行われます。この処理中に、テンプレートの内容が安全でないと判断された場合（例えば、JavaScriptのコードがHTMLの文脈に不適切に挿入されている場合など）、エスケープエラーが発生します。

### Goにおけるパニック (Panic)

Go言語において「パニック」は、プログラムの実行を停止させる回復不可能なエラーを示します。これは通常、プログラマーの想定外の状況や、プログラムが続行できない状態に陥った場合に発生します。パニックは `recover` 関数によって捕捉することも可能ですが、一般的にはライブラリがパニックを起こすことは避けられ、代わりにエラー値を返すことが推奨されます。これにより、ライブラリの利用側がエラーを適切に処理し、回復する機会を得ることができます。

### テンプレートの実行と状態管理

`html/template` パッケージでは、テンプレートが一度エスケープされると、その状態が「エスケープ済み」として内部的に記録されます。これは、同じテンプレートを複数回実行する際に、不要な再エスケープ処理を避けるためです。しかし、エスケープ処理が失敗した場合のこの状態管理が不十分であったことが、今回のバグの原因でした。

## 技術的詳細

このコミットの核心は、`html/template` パッケージがテンプレートのエスケープ状態を管理する方法の変更にあります。

### 変更前: `escaped` フィールド (bool)

以前の `Template` 構造体には `escaped bool` というフィールドがありました。これは、テンプレートが既にエスケープ処理を通過したかどうかを示す単純な真偽値フラグでした。
- `true`: エスケープ済み。
- `false`: 未エスケープ。

このアプローチの問題点は、エスケープ処理が成功したか失敗したかを区別できないことでした。エスケープ処理が失敗した場合でも、`escaped` が `true` に設定されてしまうと、システムはテンプレートが安全であると誤解し、その後の実行で予期せぬ動作（今回の場合はパニック）を引き起こす可能性がありました。

### 変更後: `escapeErr` フィールド (error) と `escapeOK` (sentinel value)

このコミットでは、`escaped bool` フィールドを削除し、代わりに `escapeErr error` というフィールドを `Template` 構造体に追加しました。
- `escapeErr` が `nil` の場合: エスケープ処理はまだ行われていないか、初期状態。
- `escapeErr` が `escapeOK` の場合: エスケープ処理は成功し、テンプレートは安全。
- `escapeErr` が `escapeOK` 以外のエラー値の場合: エスケープ処理は失敗し、そのエラーが格納されている。

ここで `escapeOK` は、`fmt.Errorf("template escaped correctly")` で定義される特別なエラー値（センチネル値）です。これは、エラーインターフェースを実装していますが、実際には「成功」を示すマーカーとして使用されます。これにより、`escapeErr` フィールドは、エスケープ処理の結果（成功または特定のエラー）を保持できるようになります。

### 主要な変更点とロジック

1.  **`Template` 構造体の変更**:
    -   `escaped bool` が削除され、`escapeErr error` が追加されました。

2.  **`escapeTemplates` 関数の変更**:
    -   エスケープ処理が成功した場合、テンプレートの `escapeErr` フィールドに `escapeOK` が設定されるようになりました。
    -   エスケープ処理が失敗した場合、元のエラーが `escapeErr` に設定され、テンプレートのツリー構造がクリアされることで、安全でないテンプレートが実行されないようにします。

3.  **`Template.escape()` メソッドの変更**:
    -   このメソッドは、テンプレートのエスケープ処理をトリガーします。
    -   変更前は `!t.escaped` で未エスケープ状態をチェックしていましたが、変更後は `t.escapeErr == nil` で初期状態をチェックします。
    -   もし `t.escapeErr` が `escapeOK` 以外のエラー値であれば、そのエラーを即座に返します。これにより、一度エスケープに失敗したテンプレートは、再実行時にパニックを起こすことなく、以前のエラーを返すようになります。

4.  **`lookupAndEscapeTemplate` メソッドの変更**:
    -   このメソッドは、名前でテンプレートを検索し、必要であればエスケープします。
    -   検索されたテンプレートの `escapeErr` が `nil` でなく、かつ `escapeOK` でない場合（つまり、エスケープに失敗している場合）、そのエラーを返します。これにより、安全でないテンプレートの実行が防止されます。

5.  **`Parse`, `AddParseTree`, `Clone`, `New` メソッドの変更**:
    -   これらのメソッドは、新しいテンプレートを作成したり、既存のテンプレートを操作したりする際に、`escaped` フラグの代わりに `escapeErr` を適切に初期化（通常は `nil`）するように変更されました。これにより、テンプレートのライフサイクル全体で正しいエスケープ状態が維持されます。

### テストの追加

`src/pkg/html/template/escape_test.go` には、エスケープエラーが発生するテンプレートを複数回実行してもパニックせず、同じエラーが返されることを確認するテストが追加されました。これは、修正が意図通りに機能していることを保証します。

## コアとなるコードの解説

このコミットの主要な変更は、テンプレートのエスケープ状態を管理するための `Template` 構造体のフィールドを、単純なブーリアン値 `escaped` から、エラー型 `escapeErr` に変更した点です。

**なぜこの変更が必要だったのか？**

以前の `escaped bool` フラグは、テンプレートが「エスケープ処理を終えたかどうか」しか記録できませんでした。しかし、エスケープ処理は成功することもあれば、セキュリティ上の問題などで失敗することもあります。エスケープ処理が失敗した場合でも `escaped` が `true` に設定されてしまうと、システムはテンプレートが安全であると誤解し、その後の実行でパニックを引き起こす可能性がありました。

**`escapeErr error` の導入**

新しい `escapeErr error` フィールドは、エスケープ処理の結果をより詳細に記録することを可能にします。
-   **エスケープ処理が成功した場合**: `escapeErr` には特別なセンチネル値 `escapeOK` が設定されます。これは、エラーインターフェースを実装していますが、実際には「成功」を示すマーカーとして機能します。
-   **エスケープ処理が失敗した場合**: `escapeErr` には、エスケープ処理中に発生した実際のエラーが格納されます。

この変更により、テンプレートは一度エスケープ処理に失敗すると、その失敗の状態を「記憶」するようになります。その後のテンプレートの実行試行では、この `escapeErr` フィールドをチェックし、もしエラーが格納されていれば、パニックを起こす代わりにそのエラーを呼び出し元に返します。これにより、ライブラリの堅牢性が向上し、アプリケーションはエラーを適切に処理できるようになります。

**具体的なコードの変更と効果**

-   **`escapeTemplates`**: エスケープ処理の成功/失敗に応じて `t.escapeErr` を設定するようになりました。失敗時には `t.text.Tree = nil` と `t.Tree = nil` を実行し、テンプレートのツリー構造をクリアすることで、安全でないテンプレートが誤って実行されることを防ぎます。
-   **`Template.escape()`**: テンプレートのエスケープ処理を行うメソッドです。以前は `!t.escaped` でチェックしていましたが、`t.escapeErr == nil` で初期状態をチェックし、`t.escapeErr != escapeOK` であれば以前のエラーを返すようになりました。これにより、二度目の実行でパニックが回避されます。
-   **`lookupAndEscapeTemplate`**: テンプレートを検索し、必要に応じてエスケープするメソッドです。ここでも、検索されたテンプレートの `escapeErr` が `nil` でなく、かつ `escapeOK` でない場合（つまり、エスケープに失敗している場合）には、そのエラーを即座に返すようになりました。
-   **コンストラクタやコピーメソッド (`Parse`, `AddParseTree`, `Clone`, `New`)**: これらのメソッドは、新しいテンプレートインスタンスを作成したり、既存のテンプレートをコピーしたりする際に、`escapeErr` フィールドを適切に `nil` に初期化するように変更されました。これにより、新しいテンプレートは常に未エスケープの状態から始まり、エスケープ処理が正しく行われることが保証されます。

これらの変更により、`html/template` パッケージは、エスケープ処理の失敗をより堅牢に扱い、予期せぬパニックを防ぐことができるようになりました。

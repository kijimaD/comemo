# [インデックス 25271] ファイルの概要

このコミットは、Go言語の`net`パッケージにおいて、Plan 9オペレーティングシステム上でのTCPソケットの振る舞いを改善するものです。具体的には、ソケットがクローズされた後に`Read`呼び出しがブロックされ続ける問題を解決し、関連するテストの修正やPlan 9固有のスキップ条件の調整が含まれています。

## 変更の背景

この変更は、Goの`net`パッケージがPlan 9オペレーティングシステム上でTCP接続を扱う際に発生していた複数の問題を解決するために導入されました。主な問題は以下の通りです。

1.  **Issue #9554: Plan 9でクローズされたTCP接続に対する`Read`がハングする問題**: Plan 9環境において、TCP接続がリモート側またはローカル側でクローズされた後も、その接続に対する`Read`呼び出しが無限にブロックされ続けるというバグがありました。これは、アプリケーションが接続終了を検知できず、リソースリークやデッドロックを引き起こす可能性がありました。
2.  **Issue #7782: `TestTransportClosesBodyOnError`がPlan 9でスキップされる問題**: `net/http/transport_test.go`内の`TestTransportClosesBodyOnError`テストが、Plan 9では常にスキップされていました。これは、上記の`Read`ハング問題と関連している可能性があり、テストが正しく実行できない状態でした。
3.  **Issue #7237 (メタバグ) および #11932 (Plan 9のI/Oデッドラインサポートの欠如)**: これらのIssueは、Plan 9におけるネットワークI/Oの一般的な信頼性やデッドラインサポートの欠如に関するものでした。今回のコミットは、直接的にデッドラインサポートを追加するものではありませんが、接続クローズ時の`Read`ブロック問題を解決することで、Plan 9でのネットワーク操作の堅牢性を向上させています。

これらの問題は、GoアプリケーションがPlan 9環境で安定して動作するために解決が必要でした。特に、接続がクローズされたにもかかわらず`Read`がブロックされるという挙動は、予期せぬアプリケーションの停止やリソース消費につながるため、優先度の高い修正でした。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **Plan 9 from Bell Labs**:
    *   ベル研究所で開発された分散オペレーティングシステムです。Unixの設計思想をさらに推し進め、すべてのリソース（ファイル、デバイス、ネットワーク接続など）をファイルシステムとして表現するという特徴を持っています。
    *   ネットワーク接続も`/net`というディレクトリ以下のファイルとして表現され、TCP接続は`/net/tcp/<conn_id>/ctl`（制御ファイル）や`/net/tcp/<conn_id>/data`（データファイル）といったパスで操作されます。
    *   `ctl`ファイルに特定のコマンド（例: `hangup`）を書き込むことで、接続の状態を制御します。
    *   Go言語は、様々なOSをサポートしており、Plan 9もその一つです。

2.  **Go言語の`net`パッケージ**:
    *   Goの標準ライブラリの一部で、ネットワークI/O機能を提供します。TCP/UDP接続、HTTPクライアント/サーバーなどが含まれます。
    *   OS固有のネットワーク操作は、内部的に`syscall`パッケージやOS固有のファイルディスクリプタ（FD）ラッパーを通じて行われます。Plan 9の場合、`fd_plan9.go`のようなファイルでOS固有の実装が提供されます。

3.  **TCPソケットのクローズと`Read`の振る舞い**:
    *   TCP接続が正常にクローズされると、通常、その接続に対する`Read`呼び出しは、残りのデータがあればそれを返し、その後EOF（End Of File）を返して終了します。
    *   しかし、一部のOSや特定の条件下では、接続がクローズされても`Read`がブロックされ続けることがあります。これは、OSのネットワークスタックが接続終了イベントを適切に処理しないか、アプリケーションに通知しない場合に発生します。

4.  **I/Oデッドライン**:
    *   ネットワークI/O操作（`Read`や`Write`）に時間制限（タイムアウト）を設定する機能です。デッドラインを超過すると、操作はエラーを返して終了し、無限のブロックを防ぎます。
    *   Goの`net`パッケージは`SetReadDeadline`や`SetWriteDeadline`などのメソッドを提供しますが、Plan 9ではこの機能が完全にサポートされていないことがIssue #11932で指摘されています。

## 技術的詳細

このコミットの核心は、Plan 9におけるTCP接続の`Close`処理に`hangup`コマンドを明示的に発行することで、ブロックされた`Read`呼び出しを解除する点にあります。

Plan 9のネットワークモデルでは、TCP接続はファイルシステム上のエントリとして扱われます。具体的には、接続の制御は`/net/tcp/<conn_id>/ctl`ファイルへの書き込みによって行われます。従来のGoの`net`パッケージのPlan 9実装では、`Close`メソッドが呼び出された際に、単に`ctl`ファイルと`data`ファイルをクローズするだけでした。しかし、Issue #9554で報告されたように、この方法では、特にデータがキューに残っている場合や、リモート側が先に接続をクローズした場合に、`data`ファイルに対する`Read`呼び出しがブロックされたままになる問題がありました。

このコミットでは、`src/net/fd_plan9.go`の`netFD.Close()`メソッドに以下の変更が加えられました。

*   `fd.net == "tcp"`（TCP接続の場合）という条件の下で、`fd.ctl.WriteString("hangup")`という行が追加されました。
    *   `hangup`コマンドは、Plan 9のTCP接続制御ファイルに書き込むことで、その接続を強制的に切断し、関連するすべてのI/O操作を中断させる効果があります。これにより、ブロックされていた`Read`呼び出しがエラー（通常は`io.EOF`または`syscall.EPIPE`のようなエラー）を返して終了するようになります。
    *   コミットメッセージには「WriteString returns an error: "write /net/tcp/39/listen: inappropriate use of fd"」とありますが、これは`listen`ソケットに対する`hangup`の試行に関するもので、通常の確立されたTCP接続の`data`ファイルに対する`Read`のブロック解除には有効であると判断されています。

この変更により、Plan 9上でのGoのTCP接続の信頼性が大幅に向上し、接続クローズ後のリソースリークやアプリケーションのハングアップが防止されます。

また、この修正に伴い、いくつかのテストファイルが更新されています。

*   `src/net/dial_test.go`: `TestDialSerialAsyncSpuriousConnection`テストがPlan 9でスキップされるようになりました。これは、Plan 9がI/Oデッドラインをサポートしていないため、このテストの前提条件が満たされないためです。
*   `src/net/http/httputil/reverseproxy_test.go`および`src/net/http/transport_test.go`: 以前はPlan 9でスキップされていたテスト（`TestReverseProxyCancelation`, `TestTransportPersistConnLeak`, `TestTransportPersistConnLeakShortBody`, `TestTransportClosesBodyOnError`）から、Plan 9固有のスキップ条件が削除されました。これは、`fd_plan9.go`の修正によって、これらのテストがPlan 9でも正しく動作するようになったためです。
*   `src/net/http/transport_test.go`: `TestTransportClosesBodyOnError`テストにおいて、`io.MultiReader`に`plan9SleepReader{}`が追加されました。これは、Plan 9の特定の挙動（キューされたデータがあるTCP接続の`hangup`が、キューされたデータを先に送信しない）に対応するためのワークアラウンドです。`hangup`コマンドが発行される前に、データが確実に送信されるように短い遅延を挿入しています。

## コアとなるコードの解説

### `src/net/fd_plan9.go` の変更

`netFD`構造体は、Plan 9におけるネットワークファイルディスクリプタを抽象化したものです。`Close()`メソッドは、このネットワーク接続を閉じる際に呼び出されます。

追加されたコードブロック:
```go
if fd.net == "tcp" {
    // The following line is required to unblock Reads.
    // For some reason, WriteString returns an error:
    // "write /net/tcp/39/listen: inappropriate use of fd"
    // But without it, Reads on dead conns hang forever.
    // See Issue 9554.
    fd.ctl.WriteString("hangup")
}
```
このコードは、現在のネットワーク接続がTCPである場合にのみ実行されます。`fd.ctl`は、Plan 9のネットワーク接続の制御ファイル（例: `/net/tcp/0/ctl`）へのファイルディスクリプタです。`WriteString("hangup")`は、この制御ファイルに文字列`"hangup"`を書き込むことで、TCP接続を強制的に切断し、その接続に対する保留中の`Read`操作を解除します。

コメントにあるように、`WriteString`がエラーを返すことがありますが、これは主に`listen`ソケットのような特定の種類のファイルディスクリプタに対して`hangup`を試みた場合であり、確立されたTCP接続の`Read`ブロック解除には効果があるため、この処理が導入されました。これにより、Issue #9554で報告された「クローズされた接続に対する`Read`がハングする」問題が解決されます。

### `src/net/http/transport_test.go` の変更

1.  **Plan 9スキップ条件の削除**:
    `TestTransportPersistConnLeak`, `TestTransportPersistConnLeakShortBody`, `TestTransportClosesBodyOnError`といったテストから、`if runtime.GOOS == "plan9" { t.Skip(...) }`という形式のPlan 9固有のスキップ条件が削除されました。これは、`fd_plan9.go`の修正により、これらのテストがPlan 9上でも期待通りに動作するようになったためです。

2.  **`plan9SleepReader`の導入**:
    ```go
    type plan9SleepReader struct{}

    func (plan9SleepReader) Read(p []byte) (int, error) {
        if runtime.GOOS == "plan9" {
            // After the fix to unblock TCP Reads in
            // https://golang.org/cl/15941, this sleep is required
            // on plan9 to make sure TCP Writes before an
            // immediate TCP close go out on the wire.  On Plan 9,
            // it seems that a hangup of a TCP connection with
            // queued data doesn't send the queued data first.
            // https://golang.org/issue/9554
            time.Sleep(50 * time.Millisecond)
        }
        return 0, io.EOF
    }
    ```
    この新しい`plan9SleepReader`は、`Read`メソッドが呼び出された際に、Plan 9環境でのみ50ミリ秒の短い遅延を導入します。このリーダーは`TestTransportClosesBodyOnError`テスト内で`io.MultiReader`の一部として使用されます。
    コメントにあるように、Plan 9では、キューにデータが残っているTCP接続に対して`hangup`コマンドを発行した場合、そのキューされたデータが先に送信されずに接続が切断されるという挙動があるようです。この`plan9SleepReader`による短い遅延は、`hangup`が実行される前に、テスト内で意図的に送信されたデータが確実にネットワーク上に書き出されるようにするためのワークアラウンドです。これにより、テストがPlan 9の特定のネットワークセマンティクスに起因する競合状態を回避し、安定して実行できるようになります。

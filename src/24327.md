# [インデックス 24327] ファイルの概要

このコミットは、Go言語の標準ライブラリ `encoding/xml` パッケージにおける `EncodeToken` メソッドの振る舞いを修正するものです。具体的には、`EncodeToken` が予期しない型のトークンを受け取った際に、これまではエラーを発生させずに黙って無視していた問題を解決し、明示的なエラーを返すように変更しています。

## 元コミット内容

`encoding/xml` パッケージの `EncodeToken` メソッドは、`Token` インターフェース型の引数を受け取ります。この `Token` は、`StartElement`, `EndElement`, `CharData`, `Comment`, `ProcInst`, `Directive` のいずれかの具体的な型であると期待されています。しかし、これまでの実装では、これらの期待される型以外の値（例えば、ポインタ型や全く異なるカスタム型）が渡された場合、そのトークンはエラーを発生させることなく、単に無視されていました。この「サイレントに無視する」という振る舞いは、開発者が意図しないデータがXMLストリームに書き込まれない、あるいはデバッグが困難になるという問題を引き起こしていました。

このコミットは、`EncodeToken` 内の型スイッチに `default` ケースを追加することで、無効な型のトークンが渡された場合に適切なエラーを返すように修正しています。これにより、不正な入力に対するプログラムの堅牢性が向上し、開発者はより早く問題を特定できるようになります。

## 変更の背景

この変更の背景には、Go言語の `encoding/xml` パッケージの `EncodeToken` メソッドが、無効な入力に対して「サイレントに失敗する」という問題がありました。具体的には、`EncodeToken` は `xml.Token` インターフェースを受け取りますが、このインターフェースは `StartElement`、`EndElement`、`CharData`、`Comment`、`ProcInst`、`Directive` といった特定の具象型をラップしていることを前提としています。

しかし、もし開発者が誤ってこれらの具象型ではない、例えばこれらの型のポインタ（`*StartElement` など）や全く関係のないカスタム型を `EncodeToken` に渡した場合、これまでの実装では `EncodeToken` はそのトークンをXML出力に含めることなく、何の警告もエラーも発せずに処理を終了していました。これは、開発者が意図したXML出力が得られないにもかかわらず、その原因を特定するのが非常に困難であるという問題を引き起こしていました。

GitHub Issue #11719 (Fixes #11719) で報告されたこの問題は、プログラムのデバッグを複雑にし、予期せぬ動作につながる可能性がありました。そのため、無効な型のトークンが渡された場合には、明確なエラーを返すことで、開発者が問題を早期に発見し、修正できるようにすることが求められました。

コミットメッセージには「The behavior could be later improved by allowing pointers to token to be accepted as well, but not for go1.5.」とあり、将来的にはポインタ型も受け入れるように改善する可能性が示唆されていますが、Go 1.5のリリースではまず明確なエラーを返すという堅実な修正が優先されました。

## 前提知識の解説

### Go言語の `encoding/xml` パッケージ

`encoding/xml` パッケージは、Go言語でXMLデータをエンコード（Goのデータ構造からXMLへ）およびデコード（XMLからGoのデータ構造へ）するための機能を提供します。このパッケージは、XMLストリームを処理するための低レベルなAPI（`Decoder` や `Encoder`）と、Goの構造体とXML要素をマッピングするための高レベルなAPI（`Marshal` や `Unmarshal`）の両方を提供します。

### `xml.Encoder` と `EncodeToken` メソッド

`xml.Encoder` は、Goのデータ構造やXMLトークンをXMLストリームに書き込むための型です。`EncodeToken` メソッドは、`xml.Encoder` の主要なメソッドの一つで、単一のXMLトークン（`xml.Token` インターフェース型）をXMLストリームに書き込みます。

### `xml.Token` インターフェース

`xml.Token` は、XMLストリーム内の個々の要素（開始タグ、終了タグ、文字データ、コメント、処理命令、ディレクティブなど）を表すインターフェースです。このインターフェースは、以下の具象型によって実装されます。

*   **`xml.StartElement`**: XML要素の開始タグ（例: `<tag attribute="value">`）
*   **`xml.EndElement`**: XML要素の終了タグ（例: `</tag>`）
*   **`xml.CharData`**: XML要素内の文字データ（例: `Hello, World!`）
*   **`xml.Comment`**: XMLコメント（例: `<!-- comment -->`）
*   **`xml.ProcInst`**: 処理命令（例: `<?php echo 'hello'; ?>`）
*   **`xml.Directive`**: ドキュメント型宣言などのディレクティブ（例: `<!DOCTYPE html>`）

`EncodeToken` メソッドは、内部で型スイッチ（`switch t := t.(type)`）を使用して、渡された `xml.Token` の具体的な型を判別し、それぞれの型に応じたXML出力を行います。

### Go言語のインターフェースと型アサーション/型スイッチ

Go言語のインターフェースは、メソッドのセットを定義する型です。具象型がそのインターフェースのすべてのメソッドを実装していれば、その具象型はインターフェース型として扱えます。
型スイッチは、インターフェース型の変数が実行時にどの具象型を保持しているかを判別し、それに応じた処理を行うためのGoの構文です。

```go
switch v := i.(type) {
case int:
    // v は int 型
case string:
    // v は string 型
default:
    // v は他の型
}
```

このコミットの修正は、この型スイッチの `default` ケースを活用して、予期しない型が渡された場合の振る舞いを定義しています。

## 技術的詳細

このコミットの技術的な核心は、Go言語の型スイッチの `default` ケースを利用して、`xml.Encoder.EncodeToken` メソッドに渡される `xml.Token` インターフェースの具象型が、期待されるXMLトークン型（`StartElement`, `EndElement` など）のいずれでもない場合に、明示的なエラーを返すようにした点です。

以前の実装では、`EncodeToken` メソッド内の型スイッチは、期待される具象型（`StartElement`, `EndElement`, `CharData`, `Comment`, `ProcInst`, `Directive`）のみを処理する `case` 文を持っていました。これらの `case` 文のいずれにもマッチしない型が `Token` インターフェースとして渡された場合、型スイッチは何も処理せず、メソッドは `nil` エラーを返して終了していました。これが「サイレントに無視する」という問題の根本原因でした。

修正では、この型スイッチに以下の `default` ケースが追加されました。

```go
default:
    return fmt.Errorf("xml: EncodeToken of invalid token type")
```

この変更により、`EncodeToken` に渡された `Token` が、`encoding/xml` パッケージがXMLトークンとして認識する具象型（またはそのポインタ型）ではない場合、`"xml: EncodeToken of invalid token type"` というエラーメッセージを含む `error` が返されるようになります。これにより、開発者は不正な入力がXMLエンコーダに渡されたことを即座に検知できるようになり、デバッグの効率が大幅に向上します。

コミットメッセージで言及されている「allowing pointers to token to be accepted as well」という点については、Go言語では具象型 `T` とそのポインタ型 `*T` は異なる型として扱われます。したがって、`StartElement` を期待する型スイッチは `*StartElement` を直接処理できません。このコミットでは、まず無効な型をエラーとして扱うことを優先し、ポインタ型のサポートは将来の改善点としています。これは、Go 1.5のリリースサイクルにおける安定性と堅牢性を重視した判断と考えられます。

## コアとなるコードの解説

### `src/encoding/xml/marshal.go` の変更

`EncodeToken` メソッドは、`xml.Encoder` のレシーバーメソッドであり、`Token` インターフェース型の引数 `t` を受け取ります。このメソッドの目的は、渡されたXMLトークンをXMLストリームにエンコードすることです。

変更前は、`switch t := t.(type)` ブロック内で、`StartElement`、`EndElement`、`CharData`、`Comment`、`ProcInst`、`Directive` の各具象型に対する `case` 文が存在していました。これらの `case` 文のいずれにもマッチしない型が `t` に渡された場合、型スイッチはどの `case` にも入らず、そのままブロックを抜けていました。結果として、`EncodeToken` は `p.cachedWriteError()` を呼び出し、通常は `nil` を返していました（書き込みエラーが発生していない限り）。これが、無効なトークンが「サイレントに無視される」原因でした。

今回の修正では、この型スイッチの最後に `default` ケースが追加されました。

```go
	default:
		return fmt.Errorf("xml: EncodeToken of invalid token type")
```

この `default` ケースは、`t` の具象型が上記のどの `case` にもマッチしなかった場合に実行されます。これにより、`encoding/xml` パッケージがXMLトークンとして認識しない型が `EncodeToken` に渡された場合、`fmt.Errorf` を使用して明確なエラーメッセージを含む `error` が呼び出し元に返されるようになります。これにより、開発者は不正な入力があったことを即座に知ることができ、デバッグが容易になります。

### `src/encoding/xml/marshal_test.go` の変更

`TestSimpleUseOfEncodeToken` という新しいテスト関数が追加されました。このテストは、`EncodeToken` の新しい振る舞いを検証するために設計されています。

1.  **バッファとエンコーダの初期化**: `bytes.Buffer` と `xml.NewEncoder` を使用して、XMLエンコーダのインスタンスを作成します。
2.  **ポインタ型のトークンのテスト**:
    ```go
    if err := enc.EncodeToken(&StartElement{Name: Name{"", "object1"}}); err == nil {
        t.Errorf("enc.EncodeToken: pointer type should be rejected")
    }
    if err := enc.EncodeToken(&EndElement{Name: Name{"", "object1"}}); err == nil {
        t.Errorf("enc.EncodeToken: pointer type should be rejected")
    }
    ```
    ここでは、`StartElement` と `EndElement` のポインタ型（`*StartElement`, `*EndElement`）を `EncodeToken` に渡しています。Goの型システムでは、`StartElement` と `*StartElement` は異なる型であるため、型スイッチの既存の `case StartElement:` にはマッチしません。したがって、新しい `default` ケースが実行され、エラーが返されることが期待されます。エラーが返されなかった場合（`err == nil`）、テストは失敗します。
3.  **有効なトークンのテスト**:
    ```go
    if err := enc.EncodeToken(StartElement{Name: Name{"", "object2"}}); err != nil {
        t.Errorf("enc.EncodeToken: StartElement %s", err)
    }
    if err := enc.EncodeToken(EndElement{Name: Name{"", "object2"}}); err != nil {
        t.Errorf("enc.EncodeToken: EndElement %s", err)
    }
    ```
    ここでは、有効な `StartElement` と `EndElement` の具象型を渡しています。これらは型スイッチの適切な `case` にマッチし、エラーなしでエンコードされることが期待されます。エラーが返された場合（`err != nil`）、テストは失敗します。
4.  **無効なカスタム型のトークンのテスト**:
    ```go
    if err := enc.EncodeToken(Universe{}); err == nil {
        t.Errorf("enc.EncodeToken: invalid type not caught")
    }
    ```
    `Universe{}` は `encoding/xml` パッケージが認識しないカスタム型（テストファイル内で定義されていると仮定）です。これも型スイッチのどの `case` にもマッチしないため、`default` ケースによってエラーが返されることが期待されます。エラーが返されなかった場合（`err == nil`）、テストは失敗します。
5.  **出力の検証**:
    ```go
    if err := enc.Flush(); err != nil {
        t.Errorf("enc.Flush: %s", err)
    }
    if buf.Len() == 0 {
        t.Errorf("enc.EncodeToken: empty buffer")
    }
    want := "<object2></object2>"
    if buf.String() != want {
        t.Errorf("enc.EncodeToken: expected %q; got %q", want, buf.String())
    }
    ```
    最後に、エンコーダをフラッシュし、バッファに書き込まれたXML出力が期待通り（`<object2></object2>`）であることを検証します。これは、有効なトークンのみが正しくエンコードされ、無効なトークンは無視された（ただしエラーは返された）ことを確認するためです。

このテストは、`EncodeToken` が無効な型のトークンに対してエラーを返し、有効なトークンのみを正しく処理するという、修正後の期待される振る舞いを包括的に検証しています。

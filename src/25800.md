# [インデックス 25800] ファイルの概要

このコミットは、Go言語の標準ライブラリである`fmt`パッケージ内の`Sscanf`関数の挙動に関する修正です。`fmt`パッケージは、フォーマットされたI/O（入力/出力）を実装するための機能を提供します。`Sscanf`は、文字列からフォーマットに従って値を読み取る（スキャンする）ために使用されます。このコミットの主な目的は、`Sscanf`のドキュメントに記載されている「入力中の改行はフォーマット中の改行と一致しなければならない」というルールが、入力の終端（EOF）においても正しく適用されるようにすることです。

## コミット

`fmt.Sscanf`関数が、入力文字列の終端における改行の扱いを正しく検証するように修正されました。具体的には、フォーマット文字列に改行が含まれているにもかかわらず、入力文字列がEOFで終了し、その直前が改行でなかった場合に、エラーを検出できるようになりました。これにより、`Sscanf`のドキュメントに記載されている動作と実際の挙動との一貫性が保たれ、関連するテストケースも修正・追加されました。

## 変更の背景

`fmt.Sscanf`関数のドキュメントには、「入力中の改行はフォーマット中の改行と一致しなければならない」という重要なルールが明記されています。これは、`Sscanf`が単なる空白文字のマッチングだけでなく、改行文字の厳密なマッチングも行うことを意味します。しかし、このコミット以前の`Sscanf`の実装では、入力文字列の終端（EOF）に到達した場合に、この改行マッチングのルールが正しく適用されていませんでした。

具体的には、フォーマット文字列が改行で終わっているにもかかわらず、入力文字列が改行なしでEOFに達した場合、`Sscanf`はエラーを報告せずに成功と判断してしまう可能性がありました。この不整合は、ユーザーがドキュメントを信頼してコードを書いた場合に、予期せぬ挙動やバグを引き起こす原因となります。実際、この問題を示すテストケースが壊れていたことが、このバグの発見と修正のきっかけとなりました。

このコミットは、`Sscanf`の挙動をドキュメントと一致させ、より堅牢で予測可能な動作を保証するために行われました。

## 前提知識の解説

### `fmt`パッケージとスキャン関数

Go言語の`fmt`パッケージは、C言語の`printf`や`scanf`に似た、フォーマットされたI/O機能を提供します。
- `fmt.Printf`や`fmt.Sprintf`は、指定されたフォーマットに従って値を出力（フォーマット）します。
- `fmt.Scanf`、`fmt.Sscanf`、`fmt.Fscanf`は、指定されたフォーマットに従って入力から値を読み取ります（スキャンします）。

### `fmt.Sscanf`

`func Sscanf(str string, format string, a ...interface{}) (n int, err error)`
`Sscanf`は、文字列`str`を読み取り、`format`で指定されたフォーマットに従って値を解析し、その結果を`a`に指定された引数に格納します。成功した場合は、スキャンされた項目の数と`nil`エラーを返します。エラーが発生した場合は、部分的にスキャンされた項目の数とエラーを返します。

### フォーマット文字列の挙動

`Sscanf`のフォーマット文字列は、以下の要素で構成されます。
- **空白文字**: フォーマット文字列中の空白文字（スペース、タブ、改行など）は、入力中の任意の数の空白文字（0個以上）とマッチします。ただし、改行文字は特別な扱いを受けます。
- **非空白文字**: フォーマット文字列中の非空白文字は、入力中の対応する文字と正確に一致する必要があります。
- **`%`ディレクティブ**: `%d`（整数）、`%s`（文字列）、`%f`（浮動小数点数）など、特定の型の値をスキャンするための指示子です。

### 改行のマッチングルール

`Sscanf`のドキュメントには、「入力中の改行はフォーマット中の改行と一致しなければならない」と明記されています。これは、フォーマット文字列に`\n`がある場合、入力文字列にもその位置に`\n`がなければならないことを意味します。他の空白文字とは異なり、改行は厳密なマッチングが求められます。このコミットは、このルールの適用範囲をEOFまで広げるものです。

## 技術的詳細

このコミットは、`fmt`パッケージ内部の`ss`構造体（スキャナの状態を保持する）のメソッドである`advance`と`doScanf`に修正を加えています。

### `ss.advance`メソッド

`advance`メソッドは、フォーマット文字列の先頭部分を解析し、入力ストリームをそれに応じて進める役割を担っています。特に、フォーマット文字列中の空白文字（スペース、タブ、改行）の処理を担当します。

変更前の`advance`メソッドでは、フォーマット文字列が改行文字（`\n`）で始まり、入力ストリームがEOFに達した場合、`inputc == eof`の条件が真となり、そのまま`return`していました。この時、`wasNewline`（直前の文字が改行であったかを示すフラグ）が`true`であっても、EOFであるため、改行のマッチングが強制されることなく処理が終了していました。これが、ドキュメントとの不整合の原因でした。

コミット後の`advance`メソッドでは、`inputc == eof`のチェックの直前に、`if wasNewline`という条件が追加されました。
```go
			if inputc == eof {
				if wasNewline {
					// Newlines are mandatory.
					return -1
				}
				return
			}
```
この変更により、フォーマット文字列が改行を期待している（`wasNewline`が`true`）にもかかわらず、入力がEOFに達した場合、`advance`は`-1`を返すようになります。`-1`は、フォーマットを進めることができないことを示す特別な値であり、これにより`doScanf`がエラーを報告するトリガーとなります。

### `ss.doScanf`メソッド

`doScanf`メソッドは、`Sscanf`の主要なロジックを実装しており、フォーマット文字列全体を繰り返し処理し、`advance`メソッドを呼び出してフォーマットの各部分を処理します。

変更前の`doScanf`では、`w := s.advance(format[i:])`の呼び出し結果`w`が`0`以下の場合に、エラー処理を行っていました。特に、`w < 0`の場合に`s.errorString("input does not match format")`を呼び出していましたが、これは`if format[i] != '%'`のブロック内にありました。

コミット後の`doScanf`では、`advance`の呼び出し結果を`switch`文で処理するように変更されました。
```go
		switch w := s.advance(format[i:]); {
		case w > 0:
			i += w
			continue
		case w < 0:
			// Can't advance format. Why not?
			s.errorString("input does not match format")
		}
```
この変更により、`advance`が`-1`を返した場合（つまり、`w < 0`の場合）、すぐに`s.errorString("input does not match format")`が呼び出され、適切なエラーが報告されるようになりました。これにより、`advance`で検出された改行マッチングの失敗が、`doScanf`によって確実にエラーとして伝播されるようになります。また、この変更により、`if format[i] != '%'`ブロック内の冗長なエラーチェックが削除され、コードがわずかに簡素化されました。

## コアとなるコードの解説

### `src/fmt/scan.go` の変更

- **`ss.advance` メソッド内の変更**:
    - `inputc == eof` のブロック内に `if wasNewline` が追加されました。
    - `wasNewline` は、フォーマット文字列の現在の位置が改行文字であった場合に`true`になるフラグです。
    - この変更により、フォーマットが改行を期待している（`wasNewline`が`true`）にもかかわらず、入力がEOFに達した場合、`advance`は`-1`を返します。これは、フォーマットと入力の不一致を示し、`doScanf`にエラー処理を促します。
    - 以前は、このケースで単に`return`してしまい、エラーが報告されませんでした。

- **`ss.doScanf` メソッド内の変更**:
    - `w := s.advance(format[i:])` の呼び出し結果を処理する部分が、`if w > 0` から `switch w := s.advance(format[i:]);` に変更されました。
    - `case w < 0:` のブロックが追加され、`advance`が`-1`を返した場合（フォーマットを進められない場合）に、`s.errorString("input does not match format")` を呼び出してエラーを報告するようになりました。
    - この変更により、`advance`で検出された改行マッチングの失敗が、`doScanf`によって確実にエラーとして処理されるようになりました。
    - また、以前のコードにあった冗長なエラーチェック（`if w < 0 { s.errorString("input does not match format") }`）が削除され、コードが簡素化されました。

### `src/fmt/scan_test.go` の変更

- `TestScanfNewlineMatchFormat` テスト関数内のテストケースが大幅に修正・追加されました。
- 既存のテストケース `{"newline in both", "1\n2", "%d\n%d\n", 2, true}` が `{"newline in both", "1\n2", "%d\n%d", 2, true}` に変更されました。これは、入力の終端に改行がない場合に、フォーマットの終端に改行があることを期待するテストケースが、以前は成功とされていたが、今回の修正で失敗するようになるため、フォーマット文字列を調整したものです。
- `{"extra newline in format", "1\n2", "%d\n%d\n", 2, false}`: フォーマットに余分な改行があるが、入力にはないため、`false`（エラーを期待）となる新しいテストケースです。これは、今回の修正の意図を直接検証するものです。
- `{"newline-newline in both", "1\n\n2", "%d\n\n%d", 2, true}`: 入力とフォーマットの両方に連続する改行がある場合のテスト。
- `{"newline-newline in format", "1\n2", "%d\n\n%d", 1, false}`: フォーマットに連続する改行があるが、入力にはない場合のテスト。
- `{"newline-newline in input", "1\n\n2", "%d\n%d", 1, false}`: 入力に連続する改行があるが、フォーマットにはない場合のテスト。
- `{"newline start in both", "\n1 2", "\n%d %d", 2, true}`: 入力とフォーマットが両方改行で始まる場合のテスト。
- `{"newline start in format", "1 2", "\n%d %d", 0, false}`: フォーマットが改行で始まるが、入力が改行で始まらない場合のテスト。
- `{"newline start in input", "\n1 2", "%d %d", 0, false}`: 入力が改行で始まるが、フォーマットが改行で始まらない場合のテスト。
- `{"space-newline start in input", " \n1 2", "\n%d %d", 2, true}`: 入力がスペースと改行で始まるが、フォーマットが改行で始まる場合のテスト。

これらの新しいテストケースは、`Sscanf`が改行のマッチングルールを、入力の開始、中間、そして特に終端（EOF）において、より厳密に適用するようになったことを検証しています。

# [インデックス 21177] ファイルの概要

このコミットは、GoコンパイラのPowerPCアーキテクチャ向けバックエンド（`9g`）において、PowerPC命令セットの特定のバリアント（CC, V, VCC）に対する`ProgInfo`エントリを適切に設定するための変更です。これにより、コンパイラがこれらの命令バリアントを正確に認識し、最適化処理を適用できるようになります。

## 元コミット内容

このコミットは、PowerPCアーキテクチャ向けのGoコンパイラ（`9g`）において、CC、V、およびVCC命令バリアントの`ProgInfo`エントリを埋めるものです。具体的には、これらの命令バリアント間の変換を行うユーティリティを追加し、それらを使用して、基本操作の`ProgInfo`と同一であるこれらのバリアントの`ProgInfo`エントリを導出します。これらの変換ユーティリティは、`9g`のピーフホール最適化器でも使用されます。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する際に、ターゲットアーキテクチャの特性を最大限に活用して効率的なコードを生成します。PowerPCアーキテクチャには、特定の命令が複数のバリアントを持つという特徴があります。例えば、演算結果に基づいて条件レジスタを更新するバリアント（CC）、ベクトル演算を行うバリアント（V）、そしてそれらの組み合わせ（VCC）などです。

Goコンパイラのバックエンドである`9g`は、命令の特性を記述する`ProgInfo`という内部データ構造を持っています。これは、命令の副作用（レジスタの使用、メモリへのアクセス、条件フラグの変更など）をコンパイラが理解し、レジスタ割り当てや最適化（特にピーフホール最適化）を適切に行うために不可欠です。

このコミット以前は、PowerPCの特定の命令バリアント（CC, V, VCC）に対する`ProgInfo`エントリが明示的に定義されていなかった可能性があります。その結果、コンパイラはこれらのバリアントを正しく扱えず、最適化の機会を逃したり、場合によっては誤ったコードを生成したりするリスクがありました。

この変更の背景には、GoコンパイラがPowerPCアーキテクチャ上でより堅牢で最適化されたコードを生成できるようにするという目的があります。特に、ピーフホール最適化器がこれらのバリアントを認識し、より効果的な最適化を適用できるようにすることが重要でした。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が必要です。

1.  **Goコンパイラと`9g`**:
    *   Go言語のコンパイラは、初期には`gc`（Go Compiler）と呼ばれ、各アーキテクチャ向けに`5g`（ARM）、`6g`（x86-64）、`8g`（x86-32）、`9g`（PowerPC）といった名前のバックエンドを持っていました。これらはPlan 9のツールチェインに由来します。現在では、これらのバックエンドは統合され、単一の`go tool compile`コマンドで利用されますが、内部的には同様の役割を担うコンポーネントが存在します。`9g`はPowerPCアーキテクチャ向けのコード生成を担当する部分を指します。

2.  **PowerPC命令セットのバリアント（CC, V, VCC）**:
    *   **CC (Condition Codes)**: PowerPCアーキテクチャでは、多くの算術論理演算命令が、演算結果に基づいて「条件レジスタ (Condition Register, CR)」を更新するバリアントを持っています。これは通常、命令のニーモニックに`.`（ドット）を付加することで示されます（例: `add` と `add.`）。条件レジスタは、演算結果がゼロか、負か、オーバーフローしたかなどのフラグを保持し、その後の条件分岐命令（例: `beq` - branch if equal）で利用されます。このバリアントは、プログラムの制御フローを効率的に管理するために重要です。
    *   **V (Vector Instructions)**: PowerPCには、SIMD（Single Instruction, Multiple Data）命令セット拡張があります。これにより、単一の命令で複数のデータ要素に対して同時に演算を行うことができ、マルチメディア処理や科学技術計算などの性能を大幅に向上させます。主なベクトル命令セットには以下のものがあります。
        *   **AltiVec (VMX - Vector Multimedia Extension)**: Motorola/Freescaleが開発した初期のベクトル拡張。
        *   **VSX (Vector Scalar Extension)**: Power ISA v2.06で導入されたより新しいベクトル拡張で、VMX/AltiVecを拡張し、より多くのベクトルレジスタと64ビットデータ型をサポートします。
    *   **VCC (Vector Condition Codes)**: これは標準的な用語ではありませんが、ベクトル演算によって生成される条件コードやステータスフラグを指すと考えられます。ベクトル命令には比較演算（例: `compare equal-to`）が含まれ、これらは内部フラグやベクトルステータス制御レジスタ内のビットを設定し、飽和や比較結果などの条件を示します。これらは、後続のベクトル演算やプログラムロジックに影響を与える「ベクトル条件コード」と見なすことができます。

3.  **`ProgInfo`**:
    *   Goコンパイラの内部では、各機械語命令（`Prog`構造体で表現される）が持つ特性（レジスタの読み書き、メモリへのアクセス、分岐の有無など）を記述する`ProgInfo`というデータ構造があります。これは、コンパイラのレジスタ割り当てフェーズや、命令の並べ替え、削除、結合といった最適化（特にピーフホール最適化）を行う上で、命令のセマンティクスを理解するために不可欠です。

4.  **ピーフホール最適化 (Peephole Optimization)**:
    *   コンパイラの最適化手法の一つで、生成された機械語コードの小さな「窓（peephole）」を覗き込み、非効率な命令シーケンスをより効率的なものに置き換えるものです。例えば、「レジスタに値をロードし、直後にそのレジスタの値をストアする」といった冗長なシーケンスを、「直接メモリからメモリへ値を移動する」といった単一の命令に置き換えるなどが挙げられます。この最適化は、命令の副作用（`ProgInfo`が記述する内容）を正確に把握している場合にのみ効果的に適用できます。

## 技術的詳細

このコミットの主要な技術的詳細は以下の通りです。

1.  **命令バリアントの識別と変換ユーティリティの導入**:
    *   PowerPCの命令は、基本形に加えて、条件コードを更新するCCバリアント、ベクトル演算を行うVバリアント、そして両方を組み合わせたVCCバリアントが存在します。これらのバリアントは、命令のニーモニックが異なるだけで、基本的な操作は同じです。
    *   コミットでは、`src/cmd/9g/opt.h`に`V_CC`と`V_V`というビットフラグを定義し、命令がどのバリアントであるかを示すための列挙型を導入しています。
    *   `as2variant(int as)`: 特定の命令（`as`）がどのバリアントフラグ（`V_CC`, `V_V`）を持っているかを返す関数です。
    *   `variant2as(int as, int flags)`: 基本命令（`as`）とバリアントフラグ（`flags`）を受け取り、対応するバリアント命令のオペコードを返す関数です。
    *   これらのユーティリティは、`varianttable`という静的配列によって実装されています。`varianttable`は、各基本命令に対して、そのCC、V、VCCバリアントのオペコードをマッピングしています。

2.  **`ProgInfo`の拡張と初期化**:
    *   `ProgInfo`は、各命令の特性（レジスタの使用、メモリへのアクセス、条件フラグの変更など）を記述するデータ構造です。
    *   `src/cmd/9g/prog.c`内の`progtable`は、Goコンパイラが認識するすべての命令の`ProgInfo`エントリを保持しています。
    *   コミットでは、`initproginfo()`という新しい関数が導入されています。この関数は、`proginfo()`が最初に呼び出されたときに一度だけ実行されます。
    *   `initproginfo()`の目的は、`progtable`を走査し、基本命令の`ProgInfo`エントリを、そのCC、V、VCCバリアントにもコピーすることです。これは、基本命令とバリアント命令が同じ基本的な操作を行うため、`ProgInfo`の特性も同じであるという前提に基づいています。
    *   これにより、コンパイラは、どのバリアント命令が使用されても、その命令の正しい`ProgInfo`情報を参照できるようになります。

3.  **ピーフホール最適化器との連携**:
    *   コミットメッセージにもあるように、これらの変換ユーティリティは`9g`のピーフホール最適化器でも使用されます。最適化器は、命令シーケンスを分析する際に、これらのバリアント命令を正しく識別し、必要に応じて基本命令や他のバリアント命令に変換することで、より効果的な最適化を適用できるようになります。例えば、特定のバリアント命令が冗長であると判断された場合、それを削除したり、より効率的な命令に置き換えたりすることが可能になります。

この変更は、GoコンパイラがPowerPCアーキテクチャの複雑な命令セットをより深く理解し、それによって生成されるコードの品質と性能を向上させるための重要なステップです。

## コアとなるコードの解説

### `src/cmd/9g/opt.h`

```c
enum {
	V_CC = 1<<0,		// xCC (affect CR field 0 flags)
	V_V  = 1<<1,		// xV (affect SO and OV flags)
};

int as2variant(int);
int variant2as(int, int);
```
*   `V_CC`: PowerPC命令で条件レジスタ（CR field 0）のフラグに影響を与えるバリアントを示すビットフラグ。
*   `V_V`: PowerPC命令でSO（Summary Overflow）およびOV（Overflow）フラグに影響を与えるバリアントを示すビットフラグ。
*   `as2variant`: 命令オペコードからそのバリアントフラグを取得する関数。
*   `variant2as`: 基本命令オペコードとバリアントフラグから、対応するバリアント命令のオペコードを取得する関数。

### `src/cmd/9g/prog.c`

```c
static void
initproginfo(void)
{
	static int initialized;
	int addvariant[] = {V_CC, V_V, V_CC|V_V};
	int as, as2, i, variant;

	if(initialized)
		return;
	initialized = 1;

	// Perform one-time expansion of instructions in progtable to
	// their CC, V, and VCC variants
	for(as=0; as<nelem(progtable); as++) {
		if(progtable[as].flags == 0)
			continue;
		variant = as2variant(as);
		for(i=0; i<nelem(addvariant); i++) {
			as2 = variant2as(as, variant | addvariant[i]);
			if(as2 != 0 && progtable[as2].flags == 0)
				progtable[as2] = progtable[as];
		}
	}
}

void
proginfo(ProgInfo *info, Prog *p)
{
	initproginfo(); // proginfoが最初に呼ばれたときに一度だけ初期化
	*info = progtable[p->as];
	// ... (既存のロジック)
}
```
*   `initproginfo()`: `progtable`を初期化する関数。`proginfo()`が最初に呼び出されたときに一度だけ実行されます。
*   `addvariant[]`: `V_CC`, `V_V`, `V_CC|V_V`という3つのバリアントフラグの組み合わせを定義しています。
*   ループ内で、各基本命令（`as`）について、その`ProgInfo`エントリを、対応するCC、V、VCCバリアント命令（`as2`）にコピーします。これにより、すべてのバリアント命令が正しい`ProgInfo`を持つようになります。

```c
static int varianttable[ALAST][4] = {
	[AADD]=		{AADD,		AADDCC,		AADDV,		AADDVCC},
	// ... 他の命令のマッピング
};

static void
initvariants(void)
{
	static int initialized;
	int i, j;

	if(initialized)
		return;
	initialized = 1;

	for(i=0; i<nelem(varianttable); i++) {
		if(varianttable[i][0] == 0) {
			// Instruction has no variants
			varianttable[i][0] = i;
			continue;
		}
		// Copy base form to other variants
		if(varianttable[i][0] == i) {
			for(j=0; j<nelem(varianttable[i]); j++)
				memmove(&varianttable[varianttable[i][j]], &varianttable[i], sizeof(varianttable[i]));
		}
	}
}

int
as2variant(int as)
{
	int i;
	initvariants(); // varianttableが最初に呼ばれたときに一度だけ初期化
	for(i=0; i<nelem(varianttable[as]); i++)
		if(varianttable[as][i] == as)
			return i;
	fatal("as2variant: instruction %A is not a variant of itself", as);
	return 0;
}

int
variant2as(int as, int flags)
{
	initvariants(); // varianttableが最初に呼ばれたときに一度だけ初期化
	return varianttable[as][flags];
}
```
*   `varianttable`: PowerPCの各基本命令（例: `AADD`）と、そのCC、V、VCCバリアント命令（例: `AADDCC`, `AADDV`, `AADDVCC`）のオペコードをマッピングするテーブルです。このテーブルは、命令オペコードとバリアントフラグ間の変換を可能にします。
*   `initvariants()`: `varianttable`を初期化する関数。`as2variant()`や`variant2as()`が最初に呼び出されたときに一度だけ実行されます。この関数は、バリアントを持たない命令のエントリを適切に設定し、基本命令からそのバリアントへのマッピングを確立します。
*   `as2variant(int as)`: 指定された命令`as`が`varianttable`内でどのバリアントフラグに対応するかを検索し、そのフラグを返します。
*   `variant2as(int as, int flags)`: 指定された基本命令`as`とバリアントフラグ`flags`に基づいて、対応するバリアント命令のオペコードを`varianttable`から取得して返します。

これらの変更により、GoコンパイラはPowerPCの命令バリアントをより正確に扱い、最適化の精度と効率を向上させることができます。

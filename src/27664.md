# [インデックス 27664] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) の内部コード、具体的にはELF (Executable and Linkable Format) ファイルの処理に関連する `src/cmd/link/internal/ld/ldelf.go` ファイルに対する変更です。このファイルは、ELF形式の実行可能ファイルや共有ライブラリを生成する際に、リロケーション（再配置）情報を処理する役割を担っています。

## コミット

## 変更の背景

Go言語のリンカは、異なるCPUアーキテクチャ（例: AMD64, ARM, PowerPC64, S390X, I386）に対応するために、アーキテクチャ固有のリロケーション処理を行う必要があります。以前の実装では、リロケーションのサイズを決定する `reltype` 関数（コミット後に `relSize` に改名）が、`SysArch.Family` の返す値を文字リテラル（例: `'z'`, `'9'`, `'5'` など）と組み合わせて `switch` ステートメントで処理していました。

このアプローチにはいくつかの問題がありました。

1.  **可読性の低さ**: `'z'` が S390X を意味するなど、文字リテラルとアーキテクチャの対応が直感的ではなく、コードの理解を困難にしていました。
2.  **保守性の問題**: 新しいアーキテクチャが追加された場合、そのアーキテクチャに割り当てられる文字リテラルが何であるかを把握し、コードを更新する必要がありました。これはエラーの温床となる可能性がありました。
3.  **脆弱性**: `SysArch.Family` が返す値が将来的に変更された場合、リンカの動作が予期せず壊れる可能性がありました。文字リテラルは、`sys` パッケージで定義された定数よりも結合度が高いと言えます。

このコミットは、これらの問題を解決し、リンカのコードをより堅牢で保守しやすいものにすることを目的としています。

## 前提知識の解説

*   **Go言語のリンカ (`cmd/link`)**: Goプログラムをコンパイルする際に、オブジェクトファイル（`.o` ファイル）を結合して実行可能ファイルや共有ライブラリを生成するツールです。このプロセスには、シンボルのアドレス解決やリロケーションの適用が含まれます。
*   **ELF (Executable and Linkable Format)**: Unix系システムで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFファイルには、コード、データ、シンボルテーブル、リロケーション情報などが含まれます。
*   **リロケーション (Relocation)**: プログラムがメモリにロードされる際に、シンボル（関数や変数）のアドレスを修正するプロセスです。コンパイル時には、シンボルの最終的なアドレスが不明な場合があるため、リンカがその情報を埋め込みます。リロケーションの種類（例: `R_X86_64_PC32`, `R_ARM_ABS32`）は、どのアーキテクチャで、どのようにアドレスを修正するかを指示します。
*   **`SysArch.Family`**: Goの `runtime` パッケージ（または関連する `sys` パッケージ）で提供される、現在のシステムが属するCPUアーキテクチャファミリーを示す値です。例えば、`sys.AMD64` は x86-64 アーキテクチャファミリーを、`sys.ARM` は ARM アーキテクチャファミリーを示します。
*   **`obj.Biobuf`**: Goのリンカ内部で使用されるバッファリングされたI/O構造体です。
*   **`pn` (Package Name)**: リンカが処理しているパッケージの名前。エラーメッセージなどで使用されます。
*   **`elftype`**: ELFリロケーションタイプを示す整数値。

## 技術的詳細

このコミットの主要な変更点は、`src/cmd/link/internal/ld/ldelf.go` 内の `reltype` 関数が `relSize` 関数に置き換えられ、リロケーションサイズを決定するロジックが改善されたことです。

### 変更前 (`reltype` 関数)

変更前の `reltype` 関数は、以下のようなシグネチャとロジックを持っていました。

```go
func reltype(pn string, elftype int, siz *uint8) int {
    // TODO(mdempsky): Remove dependency on ArchFamily char values.
    switch uint32(SysArch.Family) | uint32(elftype)<<24 {
    // ... case statements using char literals like 'z', '9', '5', '6', '8' ...
    }
    // ...
}
```

ここで問題となっていたのは、`uint32(SysArch.Family)` の値が、特定の文字リテラル（例: `'z'`）として扱われていた点です。これは、`SysArch.Family` が内部的に文字コードに対応する整数値を返していたことを示唆しています。このアプローチは、前述の通り可読性と保守性に課題がありました。

### 変更後 (`relSize` 関数)

変更後の `relSize` 関数は、以下のように改善されました。

```go
func relSize(pn string, elftype uint32) uint8 {
    // TODO(mdempsky): Replace this with a struct-valued switch statement
    // once golang.org/issue/15164 is fixed or found to not impair cmd/link
    // performance.

    const (
        AMD64 = uint32(sys.AMD64)
        ARM   = uint32(sys.ARM)
        I386  = uint32(sys.I386)
        PPC64 = uint32(sys.PPC64)
        S390X = uint32(sys.S390X)
    )

    switch uint32(SysArch.Family) | elftype<<24 {
    // ... case statements using constants like AMD64, ARM, I386, PPC64, S390X ...
    }
    // ...
}
```

主な変更点は以下の通りです。

1.  **関数名の変更**: `reltype` から `relSize` へと変更されました。これは、この関数がリロケーションの「タイプ」ではなく、リロケーションが占める「サイズ」を返すという役割をより正確に反映しています。
2.  **`siz` 引数の削除と戻り値の変更**: 以前は `*uint8` 型の `siz` ポインタを介してサイズを返していましたが、新しい `relSize` 関数は直接 `uint8` 型のサイズを返すようになりました。これにより、関数のインターフェースがよりシンプルになりました。
3.  **`SysArch.Family` の定数化**: `sys` パッケージで定義されている `sys.AMD64`, `sys.ARM` などの定数を `uint32` 型にキャストして使用するようになりました。これにより、文字リテラルへの依存が解消され、コードの可読性と保守性が向上しました。これらの定数は、アーキテクチャファミリーを一意に識別する整数値であり、文字リテラルよりも明確です。
4.  **`rp.Type` の設定変更**: `ldelf` 関数内で、`rp.Type` の設定が `int32(reltype(pn, int(uint32(info)), &rp.Siz))` から `256 + int32(info)` に変更されました。これは、リロケーションタイプを直接 `info` から取得し、オフセット `256` を加えることで、リロケーションタイプを表現する方法が変わったことを示唆しています。これにより、`reltype` 関数がリロケーションタイプを返す必要がなくなり、`relSize` が純粋にサイズを返す役割に特化できるようになりました。

この変更により、リンカはアーキテクチャファミリーをより明確かつ堅牢な方法で識別し、それに基づいて正確なリロケーションサイズを決定できるようになりました。

## コアとなるコードの解説

このコミットの核心は、`relSize` 関数における `switch` ステートメントの改善です。

以前の `reltype` 関数では、`uint32(SysArch.Family) | uint32(elftype)<<24` という式で、アーキテクチャファミリーとELFリロケーションタイプを結合した値を使用していました。ここで `SysArch.Family` が文字リテラルに対応する整数値を返していたため、`case` 文では `'z'`, `'9'` といった文字リテラルが使われていました。

新しい `relSize` 関数では、まず `sys` パッケージから `AMD64`, `ARM`, `I386`, `PPC64`, `S390X` といったアーキテクチャファミリーの定数を `uint32` 型にキャストしてローカル定数として定義しています。

```go
    const (
        AMD64 = uint32(sys.AMD64)
        ARM   = uint32(sys.ARM)
        I386  = uint32(sys.I386)
        PPC64 = uint32(sys.PPC64)
        S390X = uint32(sys.S390X)
    )
```

そして、`switch` ステートメントの `case` 文では、これらの明確な定数とELFリロケーションタイプを組み合わせて使用しています。

```go
    switch uint32(SysArch.Family) | elftype<<24 {
    case S390X | R_390_8<<24:
        return 1
    // ...
    case ARM | R_ARM_ABS32<<24,
    // ...
    case AMD64 | R_X86_64_64<<24,
    // ...
    }
```

この変更により、コードは以下の点で改善されました。

*   **明確性**: `S390X` や `AMD64` といった定数を使用することで、どのアーキテクチャファミリーに対応するリロケーションであるかが一目でわかるようになりました。
*   **保守性**: 新しいアーキテクチャが追加された場合でも、`sys` パッケージの定数を使用するため、文字リテラルを推測したり、その対応関係を管理したりする必要がなくなります。
*   **堅牢性**: `SysArch.Family` の内部表現が変更されても、`sys` パッケージの定数を使用している限り、コードが壊れるリスクが低減されます。

また、`ldelf` 関数内で `rp.Type = 256 + int32(info)` と変更されたことで、リロケーションタイプ自体は `info` から直接取得され、`relSize` 関数は純粋にリロケーションのサイズを決定する役割に特化できるようになりました。これは関数の単一責任の原則にも合致し、コードの設計を改善しています。

`relSize` 関数内の `TODO` コメント (`// TODO(mdempsky): Replace this with a struct-valued switch statement ...`) は、将来的にさらに最適化された `switch` ステートメントの形式（例えば、アーキテクチャとリロケーションタイプをフィールドに持つ構造体を使ったパターンマッチングのようなもの）を導入する可能性を示唆していますが、このコミットの時点では、文字リテラル依存の解消が主要な目的でした。

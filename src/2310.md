## 変更の背景

このコミットは、Go言語の初期開発段階におけるコンパイラの内部バグ「bug150」が修正されたことを受けて行われました。`bug150`は、コンパイラが関数呼び出しの引数を評価する際の内部的な最適化（特に「reorder2」と呼ばれる処理）に問題があり、「too many function calls evaluating parameters」（パラメータ評価中の関数呼び出しが多すぎる）というエラーを引き起こしていました。

このコミット自体がバグを修正したわけではありません。以前のコミットで`bug150`の根本原因が解決されたため、このコミットではその修正をGoのテストスイートに反映させています。具体的には、バグを再現するテストファイル`bug150.go`を、未修正のバグテストを置く`test/bugs/`ディレクトリから、修正済みのバグテストを置く`test/fixedbugs/`ディレクトリへ移動し、さらにテストの期待される出力が記録されている`test/golden.out`から、`bug150`に関連するエラーメッセージの記述を削除しています。これにより、テストスイートが現在のコンパイラの状態（`bug150`が修正済みであること）と一致するようになります。

## 前提知識の解説

### Go言語のコンパイルと最適化

Go言語のコンパイラは、ソースコードを機械語に変換する過程で様々な最適化を行います。これには、プログラムの実行速度を向上させるために、命令の実行順序を入れ替えたり（命令の再配置、reordering）、冗長な計算を省略したりする処理が含まれます。これらの最適化は、プログラムの外部から見た振る舞いを変更しない範囲で行われる必要があります。

### 関数呼び出しの引数評価順序

Go言語では、関数呼び出しの引数は左から右へ評価されることが保証されています。例えば、`f(arg1(), arg2())`という呼び出しがあった場合、`arg1()`が完全に評価されてから`arg2()`が評価されます。この評価順序は、コンパイラの最適化によっても維持されるべき重要なセマンティクスです。

### `test/golden.out`の役割

Goのソースコードリポジトリには、コンパイラやランタイムの様々な挙動を検証するための広範なテストスイートが含まれています。`test/golden.out`ファイルは、これらのテストの一部が生成する標準出力や標準エラー出力、あるいはコンパイラが報告するエラーメッセージなど、期待される出力を記録するための「ゴールデンファイル」として機能します。テスト実行時に実際の出力が`golden.out`の内容と一致するかどうかを比較することで、コンパイラやランタイムの変更が意図しない副作用を引き起こしていないかを確認します。バグが修正された場合、そのバグによって発生していたエラーメッセージが`golden.out`から削除されることで、修正が正しく反映されたことを示します。

### `bugXXX.go`テストファイル

Goのテスト慣習として、特定のバグを再現し、その修正を検証するために`test/bugs/`ディレクトリに`bugXXX.go`のような名前のテストファイルが作成されます。バグが修正されると、そのテストファイルは`test/fixedbugs/`ディレクトリに移動されます。これは、そのバグがもはやアクティブな問題ではなく、修正済みであることを示す分類です。

## 技術的詳細

`bug150`は、Goコンパイラの初期段階における内部的な問題でした。エラーメッセージ「reorder2: too many function calls evaluating parameters」が示すように、このバグはコンパイラが関数呼び出しの引数を評価する際に、内部的な命令の再配置（`reorder2`という特定の最適化パスに関連している可能性が高い）のロジックに欠陥があったことに起因します。

具体的には、コンパイラが引数の評価順序や依存関係を誤って解釈し、結果として引数の評価が過剰に、あるいは誤った方法で行われてしまう状況を引き起こしていました。これは、例えば、引数として渡される関数が複数回呼び出されたり、無限ループに陥ったりするような、コンパイラ内部のエラーとして現れていました。このような問題は、ユーザーが書いたGoコードの誤りではなく、コンパイラ自体のバグであり、Go言語のセマンティクスを正しく実装するための重要な修正でした。

`reorder2`というキーワードは、コンパイラのバックエンドにおける特定の最適化フェーズや、命令の再配置をテストするための内部的なメカニズムを指していると考えられます。このバグの修正は、Goコンパイラの堅牢性と正確性を高める上で不可欠なステップでした。

## コアとなるコードの解説

このコミットの変更は、`bug150`というコンパイラのバグが既に修正されたという事実を、Goのテストインフラストラクチャに反映させるためのものです。

*   **`test/bugs/bug150.go`から`test/fixedbugs/bug150.go`への移動**:
    このファイル移動は、`bug150`がもはや「未修正のバグ」ではなく、「修正済みのバグ」として扱われるようになったことを明確に示しています。`test/bugs/`ディレクトリは、現在アクティブな（未修正の）バグを再現するテストを格納するために使用され、`test/fixedbugs/`ディレクトリは、過去に修正されたバグの回帰テストを格納するために使用されます。この移動により、Goのテストスイートは、`bug150`が修正済みであることを正しく認識し、将来の変更がこのバグを再発させないことを保証するための回帰テストとして機能し続けます。

*   **`test/golden.out`からのエラーメッセージの削除**:
    `test/golden.out`は、Goのテストが期待する出力を記録するファイルです。`bug150`が修正される前は、`bug150.go`テストを実行すると「reorder2: too many function calls evaluating parameters」というエラーが発生し、そのエラーメッセージが`golden.out`に記録されていました。バグが修正されたことで、`bug150.go`はもはやこのエラーを発生させずに正しくコンパイル・実行されるようになりました。したがって、`golden.out`からこのエラーメッセージの記述を削除することで、テストの期待される出力が実際の出力と一致するよう更新されています。これにより、テストがクリーンにパスし、`bug150`が本当に修正されたことを確認できます。

このコミット自体は、Goコンパイラのコードベースに直接的な機能変更を加えるものではなく、以前に行われたバグ修正の「後処理」として、テストスイートの整合性を保つための重要なステップです。

# [インデックス 28056] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるグローバル変数のスキャン方法を最適化し、特に「Stop-The-World (STW)」ポーズ時間を大幅に削減することを目的としています。これまでGCのマークフェーズ中にグローバル変数が再スキャンされており、これが大規模なグローバルデータを持つアプリケーションのパフォーマンスボトルネックとなっていました。この変更により、グローバル変数へのポインタ更新が常にライトバリアによって適切に処理されるようになり、不要な再スキャンが排除されます。

## 元コミット内容

Goランタイムは、ガベージコレクションのマークフェーズ（mark 2）およびマーク終了フェーズ（mark termination）中にグローバル変数を再スキャンしていました。この再スキャンは、STW（Stop-The-World）ポーズ時間において、1MBあたり最大500µsのコストを発生させ、20MBのグローバル変数で10msのSTW制限を超える可能性がありました。

この再スキャンは、コンパイラがグローバル変数からヒープへのポインタ更新に対して既にライトバリアを生成しているため、基本的には不要でした。しかし、`typedmemmove`や関連関数で使用される`heapBitsBulkBarrier`、およびリフレクション関連の`reflect_typedmemmovepartial`や`callwritebarrier`といった一部のライトバリアは、グローバルポインタへの書き込みを適切に処理していませんでした（`inheap`チェックによりヒープ外の宛先を無視していたため）。

## 変更の背景

Goのガベージコレクタは、並行マーク＆スイープ方式を採用しており、アプリケーションの実行と並行してGC処理を進めることで、STWポーズ時間を最小限に抑えることを目指しています。しかし、GCの特定のフェーズ（特にマーク終了フェーズ）では、正確性を保証するためにアプリケーションの実行を一時停止するSTWポーズが発生します。

このコミット以前は、グローバル変数に格納されたポインタが指すオブジェクトを正確に追跡するため、GCのマークフェーズとマーク終了フェーズでグローバル変数の領域全体を再スキャンしていました。これは、グローバル変数へのポインタの書き込みが常にライトバリアによって捕捉されるという前提が完全に満たされていなかったためです。特に、`heapBitsBulkBarrier`やリフレクション関連のライトバリアがグローバル変数への書き込みを適切に処理しないケースがあり、その結果、GCがグローバル変数を「ルート」として再確認する必要がありました。

この再スキャンは、グローバルデータセグメント（`.data`および`.bss`）が大規模なプログラムにおいて、STWポーズ時間を著しく増加させる原因となっていました。コミットメッセージにあるように、20MB程度のグローバル変数でさえ、目標とする10msのSTW制限を超える可能性があり、これはリアルタイム性や低レイテンシが求められるアプリケーションにとって深刻な問題でした。

この変更の背景には、GoランタイムのSTWポーズ時間をさらに短縮し、より予測可能なGC性能を提供することで、大規模なメモリフットプリントを持つアプリケーションや、低レイテンシが要求されるサービスにおけるGoの適用範囲を広げるという目的がありました。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に「並行マーク＆スイープ」アルゴリズムに基づいています。これは、アプリケーションの実行と並行してオブジェクトの到達可能性をマークし、不要になったオブジェクトをスイープ（解放）する方式です。これにより、STWポーズ時間を短縮し、アプリケーションのスループットを向上させます。

GCの主要なフェーズは以下の通りです。

1.  **マーク開始 (Mark Start)**: 短いSTWポーズ。GCの準備を行い、ライトバリアを有効にします。
2.  **並行マーク (Concurrent Mark)**: アプリケーションと並行して、到達可能なオブジェクトをマークします。
3.  **マーク終了 (Mark Termination)**: 短いSTWポーズ。並行マークフェーズで取りこぼしたオブジェクトを処理し、GCの最終処理を行います。このフェーズは、GCの正確性を保証するために重要です。
4.  **並行スイープ (Concurrent Sweep)**: アプリケーションと並行して、マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放します。

### Stop-The-World (STW) ポーズ

STWポーズは、GCが正確なメモリ状態を確保するために、アプリケーションのすべてのGoroutineの実行を一時的に停止する期間です。GoのGCはSTWポーズを最小限に抑えるように設計されていますが、完全に排除することはできません。STWポーズが長くなると、アプリケーションの応答性が低下し、レイテンシが増加します。

### ライトバリア (Write Barrier)

ライトバリアは、GCが並行して動作する際に、アプリケーションがポインタを更新する（書き込む）操作を監視し、GCの正確性を維持するためのメカニズムです。ポインタが変更される際にライトバリアが挿入され、GCが必要な情報を記録します。これにより、GCがオブジェクトの到達可能性を判断する際に、アプリケーションによるポインタの変更を見落とすことを防ぎます。GoのGCは、Dijkstraスタイルのライトバリア（またはハイブリッドライトバリア）を使用しており、ポインタがヒープに書き込まれる際に、そのポインタが指すオブジェクトをマーク済みとして記録します。

### グローバル変数とGC

グローバル変数は、プログラムの実行期間中ずっとアクセス可能なデータであり、GCのルートセットの一部と見なされます。ルートセットとは、GCが到達可能性を判断する際の起点となるオブジェクトの集合です。これには、実行中のGoroutineのスタック、レジスタ、そしてグローバル変数が含まれます。GCはルートセットから到達可能なすべてのオブジェクトを「生きている」と判断し、それ以外を「死んでいる」と判断して回収します。

### データセグメント (.data) と BSSセグメント (.bss)

プログラムのメモリレイアウトにおいて、グローバル変数や静的変数は主に以下のセグメントに配置されます。

*   **データセグメント (.data)**: 初期化されたグローバル変数や静的変数が格納されます。
*   **BSSセグメント (.bss)**: 初期化されていないグローバル変数や静的変数が格納されます。これらはプログラム開始時にゼロで初期化されます。

これらのセグメントにポインタ型のグローバル変数が含まれる場合、それらが指すヒープ上のオブジェクトはGCの対象となります。

## 技術的詳細

このコミットの核心は、Goのガベージコレクタがグローバル変数を扱う方法を変更し、STWポーズ時間を短縮することにあります。

### 問題点: グローバル変数の再スキャン

以前のGoランタイムでは、GCのマークフェーズ（特にマーク終了フェーズ）において、グローバル変数の領域全体を再スキャンしていました。これは、グローバル変数へのポインタの書き込みが常にライトバリアによって捕捉されるという保証が完全ではなかったためです。もしライトバリアがグローバル変数への書き込みを見落とすと、GCは「生きている」オブジェクトを誤って回収してしまう可能性があります。この安全策として、GCはSTWポーズ中にグローバル変数を再スキャンし、そこから到達可能なオブジェクトをマークしていました。

しかし、この再スキャンは、特に大規模なグローバルデータセグメントを持つプログラムにおいて、STWポーズ時間を大幅に増加させる原因となっていました。コミットメッセージによると、1MBあたり500µsものコストがかかり、20MBのグローバル変数で10msのSTW制限を超えるほどでした。

### 解決策: ライトバリアの強化と再スキャンの排除

このコミットは、以下の3つの主要な変更によってこの問題を解決します。

1.  **`heapBitsBulkBarrier`のグローバル変数対応**:
    `heapBitsBulkBarrier`は、`typedmemmove`などの関数によって大量のメモリブロックが移動される際に使用されるライトバリアです。以前は、このバリアはヒープ上のオブジェクトに限定されており、グローバル変数への書き込みを適切に処理していませんでした。このコミットでは、`heapBitsBulkBarrier`がグローバル変数への書き込みに対してもライトバリアを発行するように修正されました。具体的には、データセグメントとBSSセグメントのポインタビットマップを利用して、グローバル変数内のポインタを識別し、それらへの書き込みを捕捉します。

2.  **リフレクション関連ライトバリアからの`inheap`チェック削除**:
    `reflect_typedmemmovepartial`と`callwritebarrier`というリフレクション関連のライトバリアは、`inheap`関数を使って宛先がヒープ内にあるかどうかをチェックし、ヒープ外の宛先（つまりグローバル変数）への書き込みを無視していました。コミットメッセージでは、これらの関数がグローバルポインタで呼び出されることはないように見えると述べられていますが、安全性を高め、一貫したライトバリアの動作を保証するために、この`inheap`チェックが削除されました。これにより、これらのバリアもグローバル変数への書き込みを適切に処理するようになります。

3.  **GCマークフェーズからのグローバル再スキャン削除**:
    上記のライトバリアの強化により、グローバル変数へのポインタ更新が常にライトバリアによって捕捉されることが保証されるようになりました。このため、GCのマークフェーズ（mark 2）およびマーク終了フェーズにおいて、グローバル変数を再スキャンする必要がなくなりました。`src/runtime/mgc.go`と`src/runtime/mgcmark.go`から、この再スキャンロジックが削除されています。

### 性能向上

この変更により、特に大規模なデータセグメントやBSSセグメントを持つプログラムにおいて、GCのSTWポーズ時間が劇的に短縮されました。コミットメッセージのベンチマーク結果がその効果を明確に示しています。

*   `LargeBSS/bss:1GB/gomaxprocs:4`というベンチマークでは、マーク終了フェーズの95パーセンタイル時間が148200µsから302µsへと、**99.80%**もの削減を達成しています。これは、1GBのBSSセグメントを持つプログラムにおけるSTWポーズ時間が、約148ミリ秒から約0.3ミリ秒へと短縮されたことを意味します。

また、Goの標準ベンチマーク（go1ベンチマーク）においても、全体的にわずかながら改善が見られます。これは、グローバル変数の再スキャンが不要になったことによるオーバーヘッドの削減が、一般的なプログラムにも良い影響を与えていることを示唆しています。

### 新しいテストの追加

この変更の正確性を保証するため、`test/writebarrier.go`に新しいテストが追加されました。このテストは、グローバル変数へのポインタ書き込みが適切にライトバリアによって捕捉されることを検証します。

### `src/runtime/mbitmap.go` の変更

`heapBitsBulkBarrier`関数は、メモリブロックの移動後にライトバリアを実行する重要な関数です。

```go
func heapBitsBulkBarrier(p, size uintptr) {
    // ... 既存のヒープ内チェックと処理 ...

    // If p is a global, use the data or BSS bitmaps to
    // execute write barriers.
    for datap := &firstmoduledata; datap != nil; datap = datap.next {
        if datap.data <= p && p < datap.edata {
            bulkBarrierBitmap(p, size, p-datap.data, datap.gcdatamask.bytedata)
            return
        }
    }
    for datap := &firstmoduledata; datap != nil; datap = datap.next {
        if datap.bss <= p && p < datap.ebss {
            bulkBarrierBitmap(p, size, p-datap.bss, datap.gcbssmask.bytedata)
            return
        }
    }
    // ...
}

// 新しく追加されたヘルパー関数
func bulkBarrierBitmap(p, size, maskOffset uintptr, bits *uint8) {
    word := maskOffset / sys.PtrSize
    bits = addb(bits, word/8)
    mask := uint8(1) << (word % 8)

    for i := uintptr(0); i < size; i += sys.PtrSize {
        if mask == 0 {
            bits = addb(bits, 1)
            if *bits == 0 {
                // Skip 8 words.
                i += 7 * sys.PtrSize
                continue
            }
            mask = 1
        }
        if *bits&mask != 0 {
            x := (*uintptr)(unsafe.Pointer(p + i))
            writebarrierptr_nostore(x, *x)
        }
        mask <<= 1
    }
}
```
`heapBitsBulkBarrier`は、`p`がヒープ内ではない場合（つまりグローバル変数である可能性が高い場合）、`firstmoduledata`を走査して、`p`がどのモジュールのデータセグメント（`.data`）またはBSSセグメント（`.bss`）に属するかを判断します。見つかった場合、新しく追加された`bulkBarrierBitmap`関数を呼び出します。

`bulkBarrierBitmap`は、データ/BSSセグメントのポインタビットマップ（`gcdatamask.bytedata`や`gcbssmask.bytedata`）を利用して、指定されたメモリ範囲`[p, p+size)`内のどのワードがポインタを含んでいるかを効率的に判断します。ビットマップの各ビットは、対応するワードがポインタであるかどうかを示します。ポインタであるとマークされたワードが見つかると、`writebarrierptr_nostore`を呼び出してライトバリアを実行します。これにより、グローバル変数内のポインタ更新もGCによって適切に追跡されるようになります。

### `src/runtime/mgc.go` および `src/runtime/mgcmark.go` の変更

これらのファイルからは、GCのマーク終了フェーズにおけるグローバル変数の再スキャンロジックが削除されました。

```go
// src/runtime/mgc.go (変更前)
// atomic.Store(&work.markrootJobs, uint32(fixedRootCount+work.nDataRoots+work.nBSSRoots))
// atomic.Store(&work.markrootNext, fixedRootCount)
// 上記の行が削除された。
```
`mgc.go`では、`work.markrootJobs`と`work.markrootNext`の設定が削除されました。これらは、グローバルデータとBSSセグメントをルートとしてマークするジョブをGCワーカーに割り当てるためのものでした。再スキャンが不要になったため、これらの設定も不要になりました。

```go
// src/runtime/mgcmark.go (変更後)
func gcMarkRootPrepare() {
    // ...
    // Only scan globals once per cycle; preferably concurrently.
    if !work.markrootDone {
        for datap := &firstmoduledata; datap != nil; datap = datap.next {
            // ... nDataRoots の計算 ...
        }
        for datap := &firstmoduledata; datap != nil; datap = datap.next {
            // ... nBSSRoots の計算 ...
        }
    }
    // ...
}
```
`mgcmark.go`では、グローバルルートの計算が`!work.markrootDone`という条件ブロック内に移動されました。これは、グローバル変数のスキャンがGCサイクルごとに一度だけ行われることを保証し、以前のようにマーク終了フェーズで毎回再スキャンされることを防ぎます。

### `test/writebarrier.go` の変更

```go
var x21 *int
var y21 struct {
    x *int
}
var z21 int

func f21(x *int) {
    // Global -> heap pointer updates must have write barriers.
    x21 = x                   // ERROR "write barrier"
    y21.x = x                 // ERROR "write barrier"
    x21 = &z21                // no barrier
    y21.x = &z21              // no barrier
    y21 = struct{ x *int }{x} // ERROR "write barrier"
}
```
このテストは、グローバル変数`x21`やグローバル構造体`y21`のフィールド`y21.x`にヒープ上のポインタ（`x`）を代入する際に、コンパイラがライトバリアを挿入することを確認します。`&z21`のようにスタック上のアドレスを代入する場合にはライトバリアが不要であることも示されており、ライトバリアの適切な適用範囲を検証しています。

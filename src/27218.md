# [インデックス 27218] ファイルの概要

このコミットは、Goランタイムの`select`ステートメントにおけるゴルーチン待機リスト（`g.waiting`）の構築順序を変更します。具体的には、これまでポーリング順序（poll order）で構築されていたこのリストを、チャネルロック順序（channel lock order）で構築するように修正しています。これにより、ランタイムがチャネルのロックをより安全かつ一貫した方法で取得できるようになり、将来のランタイム変更への道を開きます。

変更されたファイルは以下の通りです。
- `src/runtime/runtime2.go`: `g.waiting`フィールドのコメントが更新されました。
- `src/runtime/select.go`: `selectgoImpl`関数内の`g.waiting`リストの構築ロジックが変更されました。

## 変更の背景

Goの`select`ステートメントは、複数のチャネル操作の中から準備ができたものを非決定的に選択し実行する強力な並行処理プリミティブです。このコミット以前は、`select`がゴルーチンをチャネルで待機させる際に構築する`g.waiting`リスト（ゴルーチンが待機している`sudog`構造体のリスト）は、チャネルのポーリング順序（`pollorder`）に基づいていました。コミットメッセージによると、このポーリング順序には特に依存するものがなく、しかし近い将来、ランタイムの他の箇所でチャネルのロック順序（`channel lock order`）にアクセスする必要が生じることが見込まれていました。

チャネルのロック順序は、複数のチャネルが関与する操作（特に`select`のようなケース）において、デッドロックを回避し、ランタイムの整合性を保つために非常に重要です。チャネルは内部的にミューテックス（ロック）を使用して並行アクセスを保護しており、複数のチャネルのロックを同時に取得する際には、常に一貫した順序でロックを取得する必要があります。このコミットは、`g.waiting`リストの構築順序をチャネルロック順序に合わせることで、この要件を満たし、将来のランタイムの改善や機能追加のための基盤を整備することを目的としています。

コミットメッセージにある「For #12967」は、この変更が関連する課題や議論があることを示唆していますが、公開されているGoのissueトラッカーで直接的に「select channel lock order」に関連する#12967は見当たりませんでした。これは内部的な追跡番号であるか、より広範な課題の一部である可能性があります。しかし、この変更の目的は、`select`の内部的な堅牢性と将来の拡張性を高めることにあると理解できます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **Goの`select`ステートメント**:
    `select`は、複数のチャネル操作（送受信）を同時に待機し、そのうちのいずれかが準備完了になったときに、その操作を実行するGoの制御構造です。もし複数の操作が同時に準備完了になった場合、`select`はそれらのうちの1つをランダムに選択します。これはGoの設計上の特徴であり、特定の順序に依存するコードを書くことを防ぎ、より堅牢な並行プログラムを促します。

2.  **チャネルの内部構造とロック**:
    Goのチャネルは、ゴルーチン間の安全な通信を可能にするために、内部的にミューテックス（ロック）を使用して保護されています。チャネルへの送受信操作が行われる際には、そのチャネルに関連付けられたロックが取得され、操作が完了すると解放されます。これにより、複数のゴルーチンが同時にチャネルにアクセスしても、データ競合が発生しないようになっています。

3.  **`sudog`構造体**:
    `sudog`（"scheduler utility goroutine" の略）は、Goランタイム内部で使用される構造体で、チャネル操作を待機しているゴルーチンを表します。ゴルーチンがチャネル操作でブロックされると、そのゴルーチンに対応する`sudog`インスタンスが作成され、チャネルの待機キューに追加されます。`sudog`には、待機しているゴルーチンへのポインタや、待機しているチャネルへのポインタなどが含まれます。

4.  **`g.waiting`リスト**:
    各ゴルーチン（`g`構造体）は、自身が現在待機している`sudog`構造体のリストを`g.waiting`フィールドに保持しています。`select`ステートメントが複数のチャネル操作を待機する場合、そのゴルーチンは複数のチャネルで待機する可能性があるため、このリストに複数の`sudog`が格納されます。

5.  **ポーリング順序 (poll order)**:
    これは、`select`ステートメントが`case`句を評価する際の内部的な順序を指します。以前は、`g.waiting`リストはこのポーリング順序に基づいて構築されていました。この順序は、チャネルのロックを取得する順序とは必ずしも一致しませんでした。

6.  **チャネルロック順序 (channel lock order)**:
    複数のチャネルのロックを安全に取得するためには、デッドロックを避けるために、常に一貫した順序でロックを取得する必要があります。この「チャネルロック順序」は、ランタイムが内部的に定義するチャネルの順序付けルールであり、この順序に従ってロックを取得することで、デッドロックの発生を防ぎます。このコミットは、`g.waiting`リストをこのチャネルロック順序で構築するように変更することで、ランタイムの内部的な整合性を高めています。

## 技術的詳細

このコミットの核心は、Goランタイムの`select`ステートメントが、複数のチャネル操作を待機するゴルーチン（`g`）の`waiting`リストを構築する際の順序を変更することにあります。

以前の`select`の実装では、`g.waiting`リストは`pollorder`（ポーリング順序）に基づいて構築されていました。`pollorder`は、`select`が`case`句を評価する際の内部的な順序であり、これはチャネルのロックを取得する際の順序（`lockorder`）とは異なる可能性がありました。

Goランタイムでは、複数のチャネルが関与する操作（特に`select`）において、デッドロックを回避するために、チャネルのロックを特定の、一貫した順序で取得する必要があります。この「チャネルロック順序」は、ランタイムが内部的に決定するもので、例えばチャネルのアドレス順など、デッドロックを確実に防ぐためのルールに基づいています。

このコミットは、`g.waiting`リストを`lockorder`で構築するように変更することで、以下の利点をもたらします。

1.  **デッドロックの回避**: `g.waiting`リストがチャネルロック順序で構築されることで、`select`がチャネルのロックを操作する際に、常にデッドロックフリーな順序で処理を進めることが保証されます。これは、ランタイムの安定性と堅牢性を向上させます。
2.  **将来の拡張性**: コミットメッセージにあるように、「他の場所でチャネルロック順序へのアクセスが必要になる」という将来のランタイム変更に備えるものです。`g.waiting`リストが既にこの順序で整理されていることで、関連するランタイムコードがより簡単に、かつ安全にこの情報にアクセスできるようになります。
3.  **コードの整合性**: ランタイムの内部的なデータ構造（`g.waiting`リスト）が、チャネルのロック取得順序という重要なセマンティクスを反映するようになり、コードベース全体の整合性が向上します。

具体的な変更は、`src/runtime/select.go`内の`selectgoImpl`関数に集中しています。この関数は`select`ステートメントの実際のロジックを実装しています。変更点では、`pollorder`の代わりに`lockorder`を使用して`case`を反復処理し、`g.waiting`リストを構築する際に、新しい`nextp`ポインタを導入して、リストをチャネルロック順序で効率的に連結しています。これにより、リストの構築とデキューの両方で、チャネルロック順序が維持されるようになります。

## コアとなるコードの解説

### `src/runtime/runtime2.go` の変更

`g`構造体の`waiting`フィールドのコメント変更は、このフィールドが保持する`sudog`リストのセマンティクスが変更されたことを示すドキュメンテーションの更新です。以前は単に「ゴルーチンが待機している`sudog`構造体」と記述されていましたが、このコミット以降は「ロック順序で並べられた`sudog`構造体」であることを明示しています。これは、コードの意図を明確にし、将来の開発者がこのリストの順序に依存できることを示唆しています。

### `src/runtime/select.go` の変更

`selectgoImpl`関数内の変更は、`select`ステートメントがチャネル操作を待機するゴルーチン（`gp`）の`g.waiting`リストを構築する際のロジックを根本的に変更しています。

1.  **`nextp **sudog` の導入**:
    `nextp`は`*sudog`へのポインタのポインタとして宣言されています。これは、単一リンクリストを構築する際に、リストの現在の末尾（または新しい要素が挿入されるべき位置）を効率的に追跡するために使用されます。初期値として`&gp.waiting`が設定され、これは`gp.waiting`フィールド自体を指します。

2.  **`lockorder`によるループ**:
    以前は`for i := 0; i < int(sel.ncase); i++ { cas = &scases[pollorder[i]] }`という形で`pollorder`に基づいて`case`を処理していましたが、新しいコードでは`for _, casei := range lockorder { cas = &scases[casei] }`となり、`lockorder`に基づいて`case`を反復処理します。`lockorder`は、チャネルのロックをデッドロックフリーな方法で取得するための順序付けられたインデックスのリストです。これにより、`sudog`が作成される順序がチャネルロック順序と一致するようになります。

3.  **`g.waiting`リストの構築ロジック**:
    最も重要な変更は、`sudog`を`g.waiting`リストに連結する方法です。
    - **旧**:
        ```go
        sg.waitlink = gp.waiting
        gp.waiting = sg
        ```
        これは、新しい`sg`を常にリストの先頭に追加するロジックです。結果として、リストは`pollorder`の逆順で構築されていました。
    - **新**:
        ```go
        // Construct waiting list in lock order.
        *nextp = sg
        nextp = &sg.waitlink
        ```
        この新しいロジックは、`nextp`ポインタを利用してリストを構築します。
        - 最初のイテレーションでは、`nextp`は`&gp.waiting`を指しているため、`*nextp = sg`は`gp.waiting = sg`と同じ効果を持ち、最初の`sudog`がリストの先頭になります。
        - その後、`nextp = &sg.waitlink`が実行され、`nextp`は新しく追加された`sudog`の`waitlink`フィールドのアドレスを指すようになります。
        - 次のイテレーションでは、`*nextp = sg`は、前の`sudog`の`waitlink`フィールドに新しい`sudog`を格納します。
        このプロセスを繰り返すことで、`sudog`は`lockorder`に従ってリストの末尾に順次追加され、結果として`g.waiting`リスト全体がチャネルロック順序で構築されます。

4.  **デキュー処理の変更**:
    `g.waiting`リストから`sudog`をデキューする際も、コメントが「We singly-linked up the SudoGs in lock order.」と更新され、ループが`pollorder`の逆順ではなく、`lockorder`に基づいて処理されるように変更されました。これにより、リストの構築と解放の両方で一貫したチャネルロック順序が維持されます。

これらの変更により、Goランタイムの`select`ステートメントは、チャネルのロックを扱う際に、より予測可能でデッドロックフリーな動作を保証できるようになります。これは、Goの並行処理モデルの堅牢性をさらに高める重要な改善です。

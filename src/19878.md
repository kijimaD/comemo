## 変更の背景

このコミットの背景には、Goランタイムのメモリ管理戦略の進化があります。削除されたコメントは、`gomallocgc` 関数に関するもので、特に「If the block will be freed with runtime·free(), typ must be nil.」という記述が含まれていました。

Goのメモリ管理は継続的に改善されており、特にガベージコレクション（GC）の進化に伴い、メモリの解放方法や型情報の扱いに関する内部的なメカニズムが変更されることがあります。このコメントが追加された時点では、特定の条件下で `runtime·free()` を使用してメモリを解放する場合に `typ` (型情報) を `nil` に設定する必要があったのかもしれません。しかし、その後のランタイムの変更により、この制約が不要になったか、あるいはメモリ解放のロジックが変更され、このコメントが示す情報がもはや正確でなくなったと考えられます。

古くなったコメントを残しておくことは、開発者がコードを理解する上で混乱を招く可能性があるため、定期的なコードベースのクリーンアップの一環として、このようなコメントは削除されます。これにより、コードの正確性が保たれ、将来のメンテナンスが容易になります。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理、特に2014年当時のGoのメモリ割り当ての仕組みに関する基本的な知識が必要です。

1.  **Goのメモリ管理の階層構造**:
    Goランタイムのメモリ管理は、GoogleのTCMallocに大きく基づいており、パフォーマンスを最適化し、ロック競合を減らすために多層キャッシュアプローチを採用しています。このシステムは、`mcache`、`mcentral`、`mheap` の階層を通じてメモリを管理します。

    *   **`mcache` (Per-P Cache)**: 各論理プロセッサ（P）は、独自のローカルキャッシュである `mcache` を持っています。これはスモールオブジェクトの最も高速な割り当てポイントであり、ロックフリーな割り当てを可能にします。Goroutineがスモールオブジェクトを割り当てる必要がある場合、まずそのPの `mcache` から割り当てを試みます。
    *   **`mcentral`**: `mcache` がメモリを必要とするときに `mspan`（特定のサイズクラスのオブジェクトを保持する連続したメモリページ）を供給するグローバルキャッシュです。`mcentral` へのアクセスにはロックが必要ですが、`mspan` 全体を割り当てることでこのコストは償却されます。
    *   **`mheap`**: アロケータの最上位レベルであり、Goヒープ全体を8KBのページ粒度で管理します。`mcentral` が要求を満たせない場合、`mheap` からページを取得します。`mheap` 自体がメモリ不足の場合、オペレーティングシステムからさらにメモリを要求します。

2.  **スモールオブジェクトとラージオブジェクト**:
    Goランタイムは、オブジェクトのサイズに基づいて異なる割り当て戦略を採用しています。

    *   **スモールオブジェクト**: 32KB以下のオブジェクトは「スモールオブジェクト」と見なされます。これらは約70の事前定義されたサイズクラスのいずれかに丸められ、`mcache` 内のフリーリストから割り当てられます。`mcache` の `mspan` が空きスロットを使い果たした場合、`mcentral` から新しい `mspan` を要求します。
    *   **ラージオブジェクト**: 32KBを超えるオブジェクトは「ラージオブジェクト」に分類されます。これらは `mcache` と `mcentral` の層をバイパスし、直接 `mheap` から割り当てられます。`mheap` からの直接割り当ては、ロックが必要なため一般的に遅くなります。ラージオブジェクトは複数の8KBメモリページで構成されます。

3.  **`_type` と型情報**:
    Goのランタイムは、ガベージコレクションやリフレクションのために、各オブジェクトの型情報（`_type` 構造体）を追跡します。この型情報は、オブジェクトが指すメモリ領域のレイアウトや、ポインタが含まれているかどうかなどをGCに伝えるために重要です。

## 技術的詳細

このコミットで削除されたコメントは、`gomallocgc` 関数内のものです。`gomallocgc` は、Goランタイムが新しいオブジェクトのためにメモリを割り当てる主要な関数です。

削除された行は以下の通りです。

```diff
- // If the block will be freed with runtime·free(), typ must be nil.
```

このコメントは、特定の条件下で `runtime·free()` を使用してメモリブロックを解放する場合、`typ` 引数（割り当てられるオブジェクトの型情報）を `nil` に設定する必要があるという指示でした。

Goのメモリ管理とガベージコレクションの進化に伴い、この制約が不要になったか、あるいは `runtime·free()` の内部実装が変更され、型情報が不要になった可能性があります。例えば、GCがオブジェクトのライフサイクルをより厳密に管理するようになり、手動での `runtime·free()` の呼び出しが特定のシナリオで推奨されなくなった、あるいはその呼び出し規約が変更されたなどが考えられます。

Goランタイムは、メモリの割り当てと解放を自動的に行い、開発者が直接 `free` のような関数を呼び出すことは稀です。しかし、ランタイム内部では、特定の低レベルな操作のためにこのような関数が使用されることがあります。このコメントの削除は、Goランタイムの内部的なメモリ管理ロジックが成熟し、以前のバージョンで存在した特定の制約が解消されたことを示唆しています。これにより、コードベースはよりクリーンになり、現在のランタイムの動作を正確に反映するようになりました。

## コアとなるコードの解説

変更されたのは `src/pkg/runtime/malloc.go` ファイル内の `gomallocgc` 関数のコメントブロックです。

元のコメント:
```go
// Allocate an object of at least size bytes.
// Small objects are allocated from the per-thread cache's free lists.
// Large objects (> 32 kB) are allocated straight from the heap.
// If the block will be freed with runtime·free(), typ must be nil.
```

変更後のコメント:
```go
// Allocate an object of size bytes.
// Small objects are allocated from the per-P cache's free lists.
// Large objects (> 32 kB) are allocated straight from the heap.
```

この変更には2つのポイントがあります。

1.  **`at least size bytes` から `size bytes` への変更**:
    これは、割り当てられるオブジェクトのサイズに関する説明の微調整です。Goのメモリ割り当ては、要求されたサイズに対して、内部的に最適なサイズクラスに丸め込むことがあります。しかし、このコメントの変更は、`gomallocgc` が最終的に要求された `size` のオブジェクトを割り当てるという、より直接的な表現に修正されたことを示唆しています。これは、アロケータの動作がより正確に反映されるようにするための変更である可能性があります。

2.  **`per-thread cache` から `per-P cache` への変更**:
    これは、Goランタイムのスケジューラとメモリ管理の進化を反映しています。初期のGoランタイムでは、GoroutineはOSのスレッドに直接マッピングされることがあり、メモリキャッシュも「スレッドごと」という概念で説明されることがありました。しかし、Goのスケジューラは、Goroutineを論理プロセッサ（P）に割り当て、PがOSスレッド上で実行されるというM:Nスケジューリングモデルを採用しています。したがって、メモリキャッシュは「Pごと」に管理されるのがより正確な表現です。この変更は、Goランタイムの内部アーキテクチャの理解が深まり、より正確な用語が使用されるようになったことを示しています。

3.  **`If the block will be freed with runtime·free(), typ must be nil.` の削除**:
    これがこのコミットの主要な変更点です。前述の「変更の背景」と「技術的詳細」で説明したように、このコメントはGoランタイムのメモリ解放メカニズムの進化により古くなったため削除されました。これは、`runtime·free()` の呼び出し規約が変更されたか、あるいは特定の条件下での `typ` の `nil` 設定が不要になったことを意味します。これにより、コードベースは現在のランタイムの動作と一致し、誤解を招く情報が排除されました。

全体として、このコミットは機能的な変更ではなく、Goランタイムのメモリ管理に関するコメントを最新の状態に保ち、より正確な情報を提供するという、コード品質向上のためのメンテナンス作業です。

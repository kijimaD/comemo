# [インデックス 22602] ファイルの概要

このコミットでは、Goランタイムの複数のファイルが変更されています。主に、`src/runtime/os1_*.go`（各OS固有のランタイムファイル）と`src/runtime/proc1.go`が対象です。これらのファイル内の特定の関数に`//go:nowritebarrier`ディレクティブが追加され、関連するコメントが更新されています。

## コミット

このコミットは、`handoffp`関数およびその呼び出し先（`startm`、`newm`、`newosproc`）において、ライトバリアの使用を禁止することを目的としています。これらの関数はP（プロセッサ）なしで実行されるため、ライトバリアを持つことが許されません。将来的にライトバリアが誤って導入されるのを防ぐため、明示的に`nowritebarrier`ディレクティブが追加されました。

## 元コミット内容

```
runtime: disallow write barriers in handoffp and callees

handoffp by definition runs without a P, so it's not allowed to have
write barriers. It doesn't have any right now, but mark it
nowritebarrier to disallow any creeping in in the future. handoffp in
turns calls startm, newm, and newosproc, all of which are "below Go"
and make sense to run without a P, so disallow write barriers in these
as well.

For most functions, we've done this because they may race with
stoptheworld() and hence must not have write barriers. For these
functions, it's a little different: the world can't stop while we're
in handoffp, so this race isn't present. But we implement this
restriction with a somewhat broader rule that you can't have a write
barrier without a P. We like this rule because it's simple and means
that our write barriers can depend on there being a P, even though
this rule is actually a little broader than necessary. Hence, even
though there's no danger of the race in these functions, we want to
adhere to the broader rule.
```

## 変更の背景

Goランタイムは、ガベージコレクション（GC）とスケジューラが密接に連携して動作します。特に、GCのマーキングフェーズ中にポインタの変更を追跡するために「ライトバリア」が使用されます。ライトバリアは、ヒープ上のオブジェクトのポインタフィールドが変更されたときにトリガーされる小さなコードスニペットです。これにより、GCは到達可能なオブジェクトを正確に識別し、誤って収集されるのを防ぎます。

Goのスケジューラは、G（Goroutine）、M（Machine/OSスレッド）、P（Processor/コンテキスト）という3つの主要なエンティティで構成されています。PはGoコードを実行するための論理プロセッサであり、スケジューラやメモリ割り当ての状態などのリソースを保持します。ライトバリアは、通常、Pが存在することを前提として動作します。

`handoffp`、`startm`、`newm`、`newosproc`といった関数は、Goランタイムの非常に低レベルな部分で動作し、OSスレッドの作成やスケジューラの初期化など、Pが割り当てられていない状態で実行される可能性があります。このようなPなしで実行されるコンテキストでは、ライトバリアが正しく機能しないか、予期せぬ動作を引き起こす可能性があります。

これまでのGoランタイムでは、これらの関数に明示的なライトバリアの禁止がありませんでしたが、将来的な変更やバグの混入を防ぐために、Pなしで実行される関数ではライトバリアを許可しないというより広範なルールを適用することが決定されました。これにより、ランタイムの堅牢性と予測可能性が向上します。

## 前提知識の解説

### 1. Goのガベージコレクション (GC) とライトバリア

GoのGCは、主に並行マーク＆スイープ方式を採用しています。これは、プログラムの実行と並行してGCが動作し、アプリケーションの一時停止（Stop-the-World: STW）時間を最小限に抑えることを目指しています。

*   **ライトバリア (Write Barrier):** GCのマーキングフェーズ中に、ヒープ上のポインタが変更された際に実行されるコードです。これにより、GCはオブジェクトグラフの変更をリアルタイムで追跡し、新しい参照関係を認識できます。Go 1.8以降ではハイブリッドライトバリアが導入され、STWの一時停止をさらに削減しています。ライトバリアは、GCが正確に動作するために不可欠なメカニズムです。

### 2. P-M-Gスケジューラモデル

Goのランタイムスケジューラは、G（Goroutine）、M（Machine/OSスレッド）、P（Processor/コンテキスト）の3つの抽象概念を用いて、ゴルーチンをOSスレッドに効率的にマッピングします。

*   **G (Goroutine):** Goランタイムによって管理される軽量な独立実行関数です。Goの並行処理の基本単位です。
*   **M (Machine/OS Thread):** Goコードを実行するOSスレッドです。Goランタイムは複数のMを作成・管理できます。
*   **P (Processor/Context):** 論理プロセッサ、またはGoコードを実行するためのコンテキストを表します。スケジューラやメモリ割り当ての状態などのリソースを保持します。`GOMAXPROCS`によってPの数が決定されます。Pは、GがM上で実行されるための「実行コンテキスト」を提供します。Gが実行されるためには、MとPの両方が必要です。

スケジューラの役割は、GをMとPにマッチングさせて実行を可能にすることです。Mがブロックされた場合（例：システムコールのため）、そのMはPを解放し、別のMがそのPを獲得して他のゴルーチンを実行し続けることができます。

### 3. Stop-the-World (STW)

STWは、ガベージコレクションの特定のフェーズ中に、Goプログラム全体の実行が一時的に停止される期間を指します。GoのGCはほとんど並行して動作しますが、ヒープの一貫したビューが必要な重要なGC操作（例：メモリのルートスキャン、ライトバリアの有効化）のためには、短いSTWフェーズが必要です。

*   **STW中のプロセス:** STWイベント中、実行中のすべてのゴルーチンは中断され、安全なポイントに到達します。Pは停止済みとしてマークされ、Mはアイドルリストに移動されます。実行中だったゴルーチンは、STWフェーズが完了した後に再開されるためにグローバルキューに配置されます。

### 4. `//go:nowritebarrier` ディレクティブ

これはGoコンパイラに対する指示（プラグマ）であり、続く関数内でライトバリアを生成しないようにコンパイラに伝えます。Goランタイムの低レベルな部分で、特定の条件下でライトバリアが不要または問題となる場合に利用されます。

## 技術的詳細

このコミットの核心は、「Pなしで実行される関数ではライトバリアを許可しない」というGoランタイムの設計原則を強化することにあります。

通常、ライトバリアはPが存在することを前提としています。Pは、ライトバリアが動作するために必要なコンテキスト情報（例えば、GCの状態や現在のゴルーチンに関する情報）を提供します。Pなしでライトバリアが実行されると、これらの情報にアクセスできず、ランタイムパニックやGCの不正確な動作を引き起こす可能性があります。

コミットメッセージで述べられているように、多くの関数でライトバリアが禁止されるのは、`stoptheworld()`との競合を避けるためです。`stoptheworld()`はGCのSTWフェーズ中にすべてのゴルーチンを停止させますが、この停止中にライトバリアが実行されると問題が生じる可能性があります。

しかし、`handoffp`、`startm`、`newm`、`newosproc`といった関数は、`stoptheworld()`が実行されている間は実行されないため、直接的な競合のリスクはありません。これらの関数は、Goランタイムの起動時やOSスレッドの作成時など、非常に初期の段階や低レベルなコンテキストで動作し、Pがまだ割り当てられていないか、意図的にPなしで動作するように設計されています。

それでもなお、これらの関数に`//go:nowritebarrier`ディレクティブが追加されたのは、Goランタイムが採用している「Pなしではライトバリアを持てない」というより広範でシンプルなルールに厳密に従うためです。このルールは、特定の競合の危険性がない場合でも、ライトバリアがPに依存するという設計を明確にし、将来的な複雑なバグの発生を防ぐための予防策として機能します。これにより、ランタイムのコードベース全体で一貫性が保たれ、理解しやすくなります。

## コアとなるコードの解説

変更された各関数（`newosproc`, `newm`, `startm`, `handoffp`）の定義の直前に、`//go:nowritebarrier`ディレクティブが追加されています。

*   **`//go:nowritebarrier`:** このディレクティブは、Goコンパイラに対して、この関数内ではライトバリアを生成しないように指示します。これにより、関数がポインタを書き換える操作を行ったとしても、GCのライトバリアロジックが介入することはありません。これは、これらの関数がPなしで実行されるという特殊なコンテキストにおいて、ライトバリアが正しく機能しない、あるいは不要であるためです。

*   **コメントの変更:**
    *   `newosproc`関数には、`// May run without a P, so write barriers are not allowed.` というコメントが追加されています。これは、この関数がOSスレッドを新しく作成する際にPなしで実行される可能性があるため、ライトバリアが許可されないことを明確に示しています。
    *   `newm`および`startm`関数では、既存のコメント`// May run during STW, so write barriers are not allowed.`が`// May run without a P, so write barriers are not allowed.`に変更されています。これは、これらの関数がSTW中に実行される可能性があるという理由だけでなく、Pなしで実行されるというより一般的な理由でライトバリアが禁止されることを強調しています。
    *   `handoffp`関数には、`// Always runs without a P, so write barriers are not allowed.` というコメントが追加されています。`handoffp`は、システムコールからPをハンドオフする際などに常にPなしで実行されるため、ライトバリアが禁止されることが明記されています。

これらの変更は、Goランタイムの低レベルな部分におけるメモリ管理とスケジューリングの堅牢性を高めるための重要なステップです。Pなしで実行されるコードパスでのライトバリアの誤用を防ぎ、ランタイムの安定性を確保します。

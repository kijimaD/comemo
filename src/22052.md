このコミットでは、Goランタイムのガベージコレクション（GC）ドライバが整理されています。具体的には、GCの開始ロジックがリファクタリングされ、GCモードをより明確に区別するための定数が導入されました。これにより、GCの呼び出し元がGCの動作をより意図的に制御できるようになっています。

*   `src/runtime/proc.go`: 強制GCヘルパーのGC呼び出しの変更。

## 元コミット内容

このコミットの目的は、Goランタイムのガベージコレクション（GC）ドライバを「整理する (tidy)」ことです。これは、GCの開始と実行に関するコードの構造と明確さを改善することを意味します。具体的には、GCのトリガー方法やモード指定の方法をより体系的にすることで、コードの可読性と保守性を向上させることを目指しています。

## 変更の背景

Goのガベージコレクションは、プログラムの実行と並行して動作するコンカレントGCを基本としていますが、特定の状況下ではStop-The-World (STW) GCや、より積極的なGCが必要となる場合があります。このコミット以前のGCドライバは、`gogc`という単一の関数が`force`という`int32`型の引数によって異なるGCモードを制御していました。この`force`引数の値（0, 1, 2）がそれぞれ「コンカレントGCの開始」「STW GCの強制実行」「STW GCと積極的なスイープの強制実行」を意味しており、マジックナンバーのような形でGCの動作を決定していました。

このような実装は、GCの呼び出し元が`gogc`関数の内部実装の詳細を知っている必要があり、コードの意図が不明瞭になる原因となっていました。また、将来的にGCモードが追加された場合、`force`引数の意味がさらに複雑になる可能性がありました。

このコミットの背景には、GCドライバのインターフェースをより明確にし、GCの開始ロジックを整理することで、コードの理解を容易にし、将来的な拡張性を高めるという目的があります。特に、GCのモードを数値ではなく、意味のある定数で表現することで、コードの可読性が大幅に向上します。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の概念について理解しておく必要があります。

### Goのガベージコレクション (GC)

GoのGCは、主に以下の特徴を持つコンカレント（並行）なマーク＆スイープ方式を採用しています。

*   **コンカレントGC**: プログラムの実行と並行してGCの大部分（マークフェーズの一部とスイープフェーズ）が実行されます。これにより、アプリケーションの一時停止時間（ポーズタイム）を最小限に抑えます。
*   **Stop-The-World (STW)**: GCの特定のフェーズ（マーク開始、マーク終了、スイープ終了など）では、すべてのGoルーチンが一時的に停止されます。この停止時間が短いほど、アプリケーションの応答性が向上します。
*   **マークフェーズ**: GCルート（グローバル変数、スタック、レジスタなどから参照可能なオブジェクト）から到達可能なすべてのオブジェクトをマークします。
*   **スイープフェーズ**: マークされなかったオブジェクト（到達不能なオブジェクト）がメモリから解放されます。
*   **Write Barrier**: コンカレントGC中に、Goルーチンがポインタを書き換える際に実行される処理です。これにより、GCがオブジェクトグラフを走査している間にオブジェクトの参照関係が変更されても、GCが正しく動作することを保証します。

### GCの主要な関数と構造体

*   **`mallocgc(size uintptr, typ *_type, flags uint32) unsafe.Pointer`**: Goのメモリ割り当ての基本的な関数です。新しいオブジェクトをヒープに割り当て、必要に応じてGCをトリガーします。
*   **`GC()`**: ユーザーが明示的にGCをトリガーするために呼び出すことができる関数です。
*   **`gogc(force int32)` (変更前)**: GCを開始する内部関数。`force`引数によってGCの動作モードを制御していました。
    *   `force = 0`: コンカレントGCを開始。
    *   `force = 1`: 現在のヒープ使用量に関わらずSTW GCを実行。
    *   `force = 2`: STW GCと積極的なスイープを実行。
*   **`startGC(mode int)` (変更後)**: `gogc`に代わる新しいGC開始関数。`mode`引数に意味のある定数を使用します。
*   **`gc(mode int)` (変更後)**: 実際のGC処理を実行する関数。以前の`gcwork`関数がリファクタリングされたものです。
*   **`shouldtriggergc()`**: GCをトリガーすべきかどうかを判断する関数。ヒープの使用量と`memstats.next_gc`（次のGCがトリガーされるべきヒープサイズ）に基づいて判断します。
*   **`shouldhelpgc`**: GCが進行中の場合に、現在のGoルーチンがGC作業を手伝うべきかどうかを示すフラグ。
*   **`bggc`**: バックグラウンドコンカレントGCゴルーチンの状態を管理する構造体。`lock`、`started`、`working`、`g`（GCゴルーチン）などのフィールドを持ちます。
*   **`work`**: GCのマークフェーズで使用される作業キューを管理する構造体。フル、エンプティ、パーシャルなブロックのリストを保持します。
*   **`systemstack(func())`**: 現在のGoルーチンをシステムスタックに切り替えて関数を実行します。GCのようなランタイムの低レベル処理でよく使用されます。
*   **`semacquire(s *uint32, block bool)` / `semrelease(s *uint32)`**: セマフォ操作。GCのSTWフェーズでGoルーチンを停止・再開するために使用されます。
*   **`acquirem()` / `releasem(mp *m)`**: M（マシン）の取得と解放。MはOSスレッドを表し、Goルーチンが実行されるコンテキストです。
*   **`getg()`**: 現在のGoルーチン（G）を取得します。
*   **`mp`**: 現在のM（マシン）ポインタ。
*   **`gp`**: 現在のG（Goルーチン）ポインタ。
*   **`gcphase`**: GCの現在のフェーズを示す変数（例: `_GCscan`, `_GCmark`, `_GCmarktermination`, `_GCoff`）。
*   **`traceEvGoBlock`**: トレースイベントの一種で、Goルーチンがブロックされたことを示します。
*   **`goparkunlock(lock *mutex, reason string, traceEv byte)`**: Goルーチンをパーク（一時停止）し、ロックを解放します。
*   **`nanotime()`**: ナノ秒単位の現在時刻を返します。GCのパフォーマンス測定に使用されます。
*   **`atomicloaduint(&bggc.working)`**: `bggc.working`の値をアトミックに読み込みます。
*   **`gcpercent`**: GCのトリガー閾値を制御する環境変数（GOGC）。
*   **`panicking`**: パニック状態かどうかを示す変数。
*   **`locks`**: 現在のMが保持しているロックの数。
*   **`memstats`**: Goランタイムのメモリ統計情報。`heap_alloc`（現在割り当てられているヒープメモリ）、`next_gc`（次のGCがトリガーされるヒープサイズ）などを含みます。
*   **`triggerratio`**: GCトリガーの比率。
*   **`debug.gctrace`**: GCトレースのレベルを制御するデバッグフラグ。
*   **`debug.gccheckmark`**: GCマークのチェックを有効にするデバッグフラグ。
*   **`checkmarkphase`**: GCマークチェックフェーズ中かどうかを示すフラグ。
*   **`initCheckmarks()` / `clearcheckmarkbits()`**: GCマークチェックに関連する関数。
*   **`_Grunning` / `_Gwaiting`**: Goルーチンの状態を示す定数。
*   **`casgstatus(gp *g, oldval, newval uint32)`**: Goルーチンの状態をアトミックに比較・交換します。
*   **`gcWork`**: GCの作業を管理する構造体。

*   **`gcmark_m()`**: コンカレントマークフェーズを実行する関数。
*   **`gccheckmark_m()`**: GCマークの整合性をチェックする関数。
*   **`scavenge_m()` / `mHeap_Scavenge()`**: OSにメモリを解放する（ヒープを縮小する）処理。
*   **`runtime_debug_freeOSMemory()`**: `runtime/debug`パッケージから呼び出される、OSにメモリを解放する関数。
*   **`forcegchelper()`**: 強制GCをトリガーするヘルパー関数。

### マジックナンバーの排除

プログラミングにおいて、マジックナンバーとは、コード中に直接埋め込まれた、その意味が不明瞭な数値定数のことです。このコミットでは、`gogc(0)`, `gogc(1)`, `gogc(2)`のように、数値によってGCのモードを切り替えていた部分を、`startGC(gcBackgroundMode)`, `startGC(gcForceMode)`, `startGC(gcForceBlockMode)`のように、意味のある定数に置き換えることで、マジックナンバーを排除し、コードの可読性と保守性を向上させています。

## 技術的詳細

このコミットの主要な変更点は、GCの開始ロジックを`gogc(force int32)`から`startGC(mode int)`へとリファクタリングしたことです。これにより、GCのトリガーモードがより明確に定義され、コードの意図が分かりやすくなりました。

### `gogc`から`startGC`への変更

*   **`gogc(force int32)`の削除**: 以前の`gogc`関数は削除されました。この関数は`force`という`int32`型の引数を受け取り、その値によってGCの動作モード（コンカレント、STW、STW+積極的スイープ）を切り替えていました。
*   **`startGC(mode int)`の導入**: 新しい`startGC`関数が導入されました。この関数は`mode`という`int`型の引数を受け取ります。
*   **GCモード定数の導入**: `startGC`関数で使用されるGCモードを明確にするために、以下の定数が導入されました。
    *   `gcBackgroundMode = iota` (0): コンカレントGCを開始します。これは、バックグラウンドでGCが実行される通常のモードです。
    *   `gcForceMode` (1): Stop-The-World (STW) GCを強制的に実行します。現在のヒープ使用量に関わらず、すぐにGCが開始されます。
    *   `gcForceBlockMode` (2): Stop-The-World (STW) GCを強制的に実行し、さらにスイープが完了するまでブロックします。これは、メモリを積極的に解放したい場合などに使用されます。

### GC処理の分離と整理

*   **`gcwork(force int32)`から`gc(mode int)`への変更**: 以前の`gcwork`関数は`gc`関数にリネームされ、`mode`引数を受け取るようになりました。この関数は、実際のGC処理（STW、マーク、スイープなど）を実行します。
*   **コンカレントGCと同期GCの処理の分離**: `startGC`関数内で、`mode`が`gcBackgroundMode`でない場合（つまり、同期GCの場合）は直接`gc(mode)`を呼び出すように変更されました。これにより、同期GCのパスがより明確になりました。
*   **バックグラウンドGCのロジックの整理**: `startGC`関数内で、`gcBackgroundMode`の場合のバックグラウンドGCの開始ロジックが、以前の`gogc`から引き継がれ、より簡潔に記述されています。

### `workdata`構造体の変更

*   以前は`var work workdata`として定義されていた`workdata`構造体が、`var work struct { ... }`という匿名構造体として定義されるようになりました。これにより、`work`変数の型定義がその場で完結し、コードの局所性が向上しています。機能的な変更はありませんが、コードの整理の一環です。

### 各GC呼び出し箇所の更新

*   **`src/runtime/malloc.go`**: `mallocgc`関数内でGCをトリガーする`shouldtriggergc()`の呼び出しが、`gogc(0)`から`startGC(gcBackgroundMode)`に変更されました。
*   **`src/runtime/mgc.go`**:
    *   `GC()`関数が`gogc(2)`から`startGC(gcForceBlockMode)`に変更されました。これは、ユーザーが明示的にGCを呼び出した場合に、STW GCと積極的なスイープを強制することを意味します。
    *   `backgroundgc()`関数内でGC処理を呼び出す部分が、`gcwork(0)`から`gc(gcBackgroundMode)`に変更されました。
*   **`src/runtime/mheap.go`**: `runtime_debug_freeOSMemory()`関数が`gogc(2)`から`startGC(gcForceBlockMode)`に変更されました。これは、デバッグ目的でOSにメモリを解放する際に、STW GCと積極的なスイープを強制することを意味します。
*   **`src/runtime/proc.go`**: `forcegchelper()`関数が`gogc(1)`から`startGC(gcForceMode)`に変更されました。これは、強制GCヘルパーがSTW GCを強制することを意味します。

これらの変更により、GCの開始とモード指定のロジックが統一され、コード全体でGCの意図がより明確に表現されるようになりました。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更

1.  **`workdata` 型の削除と匿名構造体への変更**:
    *   以前は`type workdata struct { ... }`として定義されていた`workdata`型が削除され、`var work struct { ... }`という匿名構造体として`work`変数が直接定義されるようになりました。これは、`work`変数が`workdata`型以外で使用されることがないため、型定義を局所化し、コードの簡潔性を高めるための変更です。機能的な意味合いは変わりません。

2.  **`GC()` 関数の変更**:
    *   `GC()`関数は、ユーザーがGoプログラムから明示的にGCをトリクエストする際に呼び出される関数です。以前は`gogc(2)`を呼び出していましたが、これは「STW GCと積極的なスイープ」を意味するマジックナンバーでした。
    *   変更後は`startGC(gcForceBlockMode)`を呼び出すようになりました。`gcForceBlockMode`という定数を使用することで、このGC呼び出しが「STW GCを強制し、スイープが完了するまでブロックする」という明確な意図を持つことが一目でわかるようになりました。

3.  **`gogc` 関数の削除と `startGC` 関数の導入**:
    *   `gogc`関数は削除され、その役割は`startGC`関数に引き継がれました。
    *   `startGC`関数は、`mode`という`int`型の引数を受け取ります。この`mode`引数の意味を明確にするために、`const`キーワードで`gcBackgroundMode`, `gcForceMode`, `gcForceBlockMode`という3つの定数が定義されました。
        *   `gcBackgroundMode`: コンカレントGCを開始します。これは、GCがバックグラウンドで実行され、アプリケーションの実行をブロックしないことを意味します。
        *   `gcForceMode`: STW GCを強制的に実行します。これは、現在のヒープ使用量に関わらず、すぐにGCを開始することを意味します。
        *   `gcForceBlockMode`: STW GCを強制的に実行し、さらにスイープが完了するまで呼び出し元をブロックします。これは、メモリを即座に解放したい場合に特に有用です。
    *   `startGC`関数内では、`mode`が`gcBackgroundMode`でない場合（つまり、同期GCの場合）は、直接`gc(mode)`を呼び出してGC処理を開始します。これにより、同期GCのパスが明確に分離されました。
    *   `gcBackgroundMode`の場合のロジックは、以前の`gogc`から引き継がれ、バックグラウンドGCゴルーチンを起動または再開する処理を行います。

4.  **`gcwork` 関数の削除と `gc` 関数の導入**:
    *   `gcwork`関数は削除され、その役割は`gc`関数に引き継がれました。
    *   `gc`関数は、`mode`という`int`型の引数を受け取るようになりました。この`mode`引数によって、GCの動作（コンカレントGCの一部として実行されるのか、同期GCとして実行されるのか）が制御されます。
    *   `gc`関数内では、`mode == gcBackgroundMode`の場合にのみ、コンカレントGCのマークフェーズに関連する処理（`gcscan_m`, `gcDrain`など）が実行されるようになりました。これにより、同期GCのパスではこれらのコンカレントGC特有の処理がスキップされ、STW GCが効率的に実行されるようになります。
    *   `gcinstalloffwb_m`, `gcinstallmarkwb`, `gcmark_m`, `gccheckmark_m`といったGCフェーズに関連するヘルパー関数が`gc`関数内にインライン化または整理されました。これにより、GCの主要なロジックが`gc`関数内に集約され、コードの構造がより明確になりました。

### その他のファイルでの変更

*   **`src/runtime/malloc.go`**:
    *   `mallocgc`関数は、メモリ割り当て時にGCをトリガーすべきかどうかを判断する`shouldtriggergc()`の後に`gogc(0)`を呼び出していましたが、これを`startGC(gcBackgroundMode)`に変更しました。これにより、通常のメモリ割り当て時のGCはバックグラウンドで実行されるコンカレントGCであることが明確になりました。
*   **`src/runtime/mheap.go`**:
    *   `runtime_debug_freeOSMemory()`関数は、`runtime/debug`パッケージから呼び出され、OSにメモリを解放する役割を持ちます。以前は`gogc(2)`を呼び出していましたが、これを`startGC(gcForceBlockMode)`に変更しました。これは、この関数がメモリを積極的に解放するために、STW GCとスイープ完了までブロックするモードを意図していることを明確に示しています。
*   **`src/runtime/proc.go`**:
    *   `forcegchelper()`関数は、強制GCをトリガーするヘルパー関数です。以前は`gogc(1)`を呼び出していましたが、これを`startGC(gcForceMode)`に変更しました。これにより、このヘルパー関数がSTW GCを強制する意図であることが明確になりました。

これらの変更全体として、GCの開始とモード指定のロジックが、マジックナンバーから意味のある定数へと移行し、GCドライバのコードがより整理され、理解しやすくなりました。これは、Goランタイムの保守性と拡張性を向上させる上で重要な改善です。

## 変更の背景

このコミットは、Goランタイムにおける`GOTRACEBACK`環境変数の処理に関するバグを修正するものです。コミットメッセージによると、以前の変更（`CL 130990043`）によって、`GOTRACEBACK`変数が`GODEBUG`変数が設定されている場合にのみ使用されるという意図しない挙動が導入されていました。

本来、`GOTRACEBACK`は`GODEBUG`とは独立して機能するべき環境変数です。しかし、`CL 130990043`以降、`GODEBUG`が設定されていない環境では`GOTRACEBACK`が無視され、パニック発生時のスタックトレースの出力レベルが期待通りに制御されないという問題が発生していました。このコミットは、この結合を解消し、`GOTRACEBACK`が常に独立してパースされ、その設定が適用されるように元の挙動を復元することを目的としています。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**:
    Goプログラムの実行を管理する低レベルな部分です。これには、ガベージコレクション（GC）、ゴルーチン（軽量スレッド）のスケジューリング、メモリ管理、システムコールとの連携などが含まれます。Goプログラムは、コンパイル時にランタイムとリンクされ、実行時にランタイムの機能を利用します。

*   **`GOTRACEBACK`環境変数**:
    Goプログラムがパニック（実行時エラー）を検出した際に、出力されるスタックトレースの詳細度を制御するための環境変数です。
    *   `0`: スタックトレースを出力しない。
    *   `1` (デフォルト): 現在のゴルーチンのスタックトレースを出力する。
    *   `2`: すべてのゴルーチンのスタックトレースを出力する。
    *   `crash`: OS固有のクラッシュダンプを生成し、すべてのゴルーチンのスタックトレースを出力する（デバッグ用途）。
    この変数は、デバッグ時や本番環境でのエラー調査において、重要な情報を提供します。

*   **`GODEBUG`環境変数**:
    Goランタイムのデバッグオプションを制御するための環境変数です。カンマ区切りの`キー=値`のペアで複数のオプションを指定できます。例えば、`GODEBUG=gctrace=1`と設定すると、ガベージコレクションの動作に関する詳細なログが出力されます。この変数は、ランタイムの内部動作を調査したり、パフォーマンスチューニングを行ったりする際に利用されます。

*   **`src/runtime/runtime.c`**:
    Goのソースコードリポジトリ内のファイルで、GoランタイムのC言語で書かれた部分を含んでいます。Goランタイムの一部は、パフォーマンスや低レベルなシステム操作のためにC言語（またはアセンブリ言語）で実装されており、このファイルはそのようなコードの一部を構成します。環境変数のパースなど、OSとのインタフェースに近い処理が記述されています。

*   **`runtime·parsedebugvars`関数**:
    この関数は、Goランタイムが起動する際に、`GODEBUG`や`GOTRACEBACK`といったランタイム関連の環境変数を読み込み、それらの値をGoランタイム内部の対応する変数に設定するために使用されます。これにより、プログラムの実行挙動が環境変数の設定に応じて変更されます。

## 技術的詳細

このコミットが修正するバグは、`src/runtime/runtime.c`内の`runtime·parsedebugvars`関数における環境変数のパースロジックにありました。

変更前のコードでは、`runtime·parsedebugvars`関数はまず`GODEBUG`環境変数を取得し、そのポインタが`nil`（つまり`GODEBUG`が設定されていない）であれば、関数全体を早期リターンしていました。

```c
// 変更前
p = runtime·getenv("GODEBUG");
if(p == nil) // GODEBUGが設定されていない場合、ここで関数が終了
    return;
// ... GODEBUGのパースロジック ...
// ... その後、GOTRACEBACKのパースロジック ...
p = runtime·getenv("GOTRACEBACK"); // ここに到達しない
```

このロジックの問題点は、`GOTRACEBACK`のパースロジックが`GODEBUG`のパースロジックの後に記述されていたことです。`GODEBUG`が設定されていない場合、`if(p == nil) return;`の条件が真となり、関数がそこで終了してしまうため、`GOTRACEBACK`のパース処理が全く実行されませんでした。結果として、`GOTRACEBACK`環境変数の設定が無視されるというバグが発生していました。

このコミットでは、`GODEBUG`のパースロジック全体を`if(p != nil){ ... }`という条件ブロックで囲むことで、この問題を解決しています。

```c
// 変更後
p = runtime·getenv("GODEBUG");
if(p != nil){ // GODEBUGが設定されている場合のみ、このブロック内のパースロジックを実行
    // ... GODEBUGのパースロジック ...
}
// ... GOTRACEBACKのパースロジック ...
p = runtime·getenv("GOTRACEBACK"); // GODEBUGの有無に関わらず、常にここに到達する
```

この修正により、`GODEBUG`が設定されていなくても、`if(p != nil)`ブロックは単にスキップされるだけで、関数は早期リターンせず、その後の`GOTRACEBACK`のパースロジックに到達するようになります。これにより、`GOTRACEBACK`は`GODEBUG`の存在に依存することなく、常に正しくパースされるようになりました。

## コアとなるコードの解説

変更の核心は、`GODEBUG`環境変数のパース処理を`if(p != nil){ ... }`ブロックで囲んだ点にあります。

*   **変更前**:
    `p = runtime·getenv("GODEBUG");` の直後に `if(p == nil) return;` がありました。これは、`GODEBUG`環境変数が設定されていない（`p`が`nil`である）場合、`runtime·parsedebugvars`関数全体がそこで実行を停止し、呼び出し元に戻ることを意味していました。このため、その後に続く`GOTRACEBACK`のパースロジックが実行される機会がありませんでした。

*   **変更後**:
    `GODEBUG`のパース処理（`for(;;)`ループとその内部）全体が `if(p != nil){ ... }` ブロック内に移動されました。
    *   もし`GODEBUG`が設定されていれば（`p`が`nil`でなければ）、このブロック内のコードが実行され、`GODEBUG`の値が正しくパースされます。
    *   もし`GODEBUG`が設定されていなければ（`p`が`nil`であれば）、`if(p != nil)`の条件が偽となり、このブロック全体がスキップされます。しかし、関数は早期リターンせず、そのまま実行を続行します。

この変更により、`GODEBUG`の有無にかかわらず、`runtime·parsedebugvars`関数は常に`GOTRACEBACK`のパースロジックに到達するようになり、`GOTRACEBACK`環境変数が意図通りに機能するようになりました。これは、環境変数のパース順序と条件分岐の適切な管理がいかに重要であるかを示す良い例です。

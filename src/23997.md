## 元コミット内容

Goリンカ (`cmd/link`) において、`darwin/arm`アーキテクチャ向けにビルドする際にDWARFデバッグ情報を生成しないようにする変更です。これは、以前の変更 (cl/10284) を部分的に元に戻すもので、`darwin/arm`で `-buildmode=c-archive` が正しく機能するようにするための修正です。

## 変更の背景

この変更の背景には、Go言語でiOSアプリケーションなどのARMベースのDarwin環境向けにCアーカイブ (`-buildmode=c-archive`) をビルドする際の特定の課題があります。

元々、Goのリンカは、デバッグを容易にするためにDWARF形式のデバッグ情報を生成します。しかし、特定の環境やビルドモードの組み合わせにおいて、このDWARF情報の生成が問題を引き起こすことがあります。このコミットメッセージによると、以前の変更 (cl/10284) が `darwin/arm` ターゲットでDWARF情報を導入した結果、`-buildmode=c-archive` が機能しなくなったようです。

`-buildmode=c-archive` は、GoのコードをC言語から呼び出し可能なスタティックライブラリとしてコンパイルする際に使用されます。これは、既存のC/Objective-CプロジェクトにGoの機能を組み込む際によく用いられるモードです。このモードで生成されるアーカイブファイルが、DWARF情報の存在によって不正な形式になったり、リンカが正しく処理できなかったりする問題が発生したと考えられます。

このコミットは、その問題を解決するために、`darwin/arm`環境で `-buildmode=c-archive` を使用する際にDWARF情報の生成を部分的に抑制することで、ビルドが成功するように修正しています。これは、デバッグ情報の完全性よりも、特定のビルドモードでの機能性を優先した pragmatic な解決策と言えます。

## 前提知識の解説

### Go言語のビルドプロセスと `cmd/link`

Go言語のプログラムは、`go build` コマンドによってコンパイル・リンクされます。このプロセスにおいて、`cmd/link` はGoのリンカであり、コンパイラによって生成されたオブジェクトファイルやライブラリを結合し、実行可能ファイルやライブラリを生成する役割を担います。リンカは、コード、データ、デバッグ情報など、最終的なバイナリの様々なセクション（セグメント）を配置し、それらのサイズやオフセットを決定します。

### DWARFデバッグ情報

DWARF (Debugging With Arbitrary Record Formats) は、プログラムのデバッグ情報を格納するための標準的なフォーマットです。ソースコードの行番号、変数名、型情報、関数名、スタックフレーム情報などが含まれており、デバッガが実行中のプログラムの状態をソースコードレベルで理解し、開発者がバグを特定するのに役立ちます。DWARF情報は通常、実行可能ファイル内の専用のセクション（例: `.debug_info`, `.debug_line` など）に格納されます。

### Mach-Oファイルフォーマット

Mach-O (Mach Object) は、macOS、iOS、watchOS、tvOSなどのApple製オペレーティングシステムで使用される実行可能ファイル、オブジェクトコード、共有ライブラリ、およびコアダンプのファイルフォーマットです。Mach-Oファイルは、ヘッダ、ロードコマンド、およびセグメント（セクション）で構成されます。主要なセグメントには以下のようなものがあります。

*   `__TEXT` セグメント: 実行可能なコードや読み取り専用データが含まれます。
*   `__DATA` セグメント: 初期化された読み書き可能なデータが含まれます。
*   `__DWARF` セグメント: DWARFデバッグ情報が含まれます。

各セグメントには、ファイル内のオフセット (`fileoffset`)、ファイルサイズ (`filesize`)、仮想メモリサイズ (`vsize`) などの情報が関連付けられています。

### `darwin/arm` ターゲット

`darwin/arm` は、AppleのDarwinカーネルをベースとしたオペレーティングシステム（主にiOS）上で動作するARMアーキテクチャのプロセッサを指します。iOSデバイス（iPhone, iPadなど）はARMプロセッサを搭載しており、Go言語でこれらのデバイス向けのアプリケーションやライブラリを開発する際には、このターゲットが使用されます。

### `-buildmode=c-archive`

Goの `go build` コマンドには、様々なビルドモードを指定する `-buildmode` フラグがあります。`-buildmode=c-archive` は、GoのパッケージをC言語のスタティックライブラリ (`.a` ファイル) としてコンパイルするモードです。このモードで生成されたライブラリは、C/Objective-Cのプロジェクトにリンクされ、Goの関数をCの関数として呼び出すことができます。これは、既存のネイティブアプリケーションにGoのロジックを組み込む際に非常に有用です。

## 技術的詳細

このコミットは、`src/cmd/link/internal/ld/macho.go` ファイル内の `Asmbmacho` 関数を変更しています。この関数は、Mach-Oファイルのセグメントをアセンブルする際に呼び出されます。

問題は、Mach-Oファイルの `__TEXT` セグメントの `filesize` を計算する方法にありました。通常、`__TEXT` セグメントのファイルサイズは、`Segdwarf.Fileoff + Segdwarf.Filelen - Segtext.Fileoff` として計算されます。これは、`__TEXT` セグメントの開始から `__DWARF` セグメントの終わりまでの全範囲をカバーすることを意図しています。しかし、`darwin/arm` 環境で `-buildmode=c-archive` を使用する場合、この計算方法が問題を引き起こしました。

コミットの変更は、`Thearch.Thechar == '5'` という条件を追加しています。`Thearch.Thechar` は、ターゲットアーキテクチャの特性を示す文字であり、Goのリンカでは `'5'` がARMアーキテクチャを指します（例: `5` for ARM, `6` for AMD64）。

この条件が真（つまり、ターゲットがARMアーキテクチャ）の場合、`ms.filesize` は `Segdata.Fileoff + Segdata.Filelen - Segtext.Fileoff` として計算されます。これは、`__TEXT` セグメントの開始から `__DATA` セグメントの終わりまでの範囲をカバーすることを意味し、`__DWARF` セグメントを `__TEXT` セグメントのサイズ計算から除外します。

それ以外のアーキテクチャの場合（`Thearch.Thechar != '5'`）、元の計算方法 (`Segdwarf.Fileoff + Segdwarf.Filelen - Segtext.Fileoff`) が維持されます。また、`ms.vsize = ms.filesize` もARMアーキテクチャ以外の場合にのみ適用されます。

この変更により、`darwin/arm` ターゲットでCアーカイブをビルドする際に、DWARF情報が `__TEXT` セグメントのサイズ計算に影響を与えなくなり、結果としてリンカが正しくMach-Oファイルを生成できるようになります。これは、DWARF情報が特定のビルドモードで問題を引き起こす場合に、その情報を一時的に無視または除外することで、ビルドの成功を優先する典型的なアプローチです。

```go

			ms.filesize = Segdata.Fileoff + Segdata.Filelen - Segtext.Fileoff

			ms.filesize = Segdwarf.Fileoff + Segdwarf.Filelen - Segtext.Fileoff
			ms.vsize = ms.filesize
		}

*   `else` の条件:
    *   `Thearch.Thechar == '5'` が偽の場合（つまり、ARM以外のアーキテクチャ向けにビルドしている場合）、元の計算ロジックが維持されます。`ms.filesize` は `__DWARF` セグメントを含んだ範囲で計算され、`ms.vsize` も同じ値に設定されます。

この変更の核心は、`darwin/arm` ターゲット（`Thearch.Thechar == '5'`）において、Mach-Oファイルの `__TEXT` セグメントのファイルサイズを計算する際に、DWARFデバッグ情報を意図的に除外することです。これにより、DWARF情報が原因で発生していた `-buildmode=c-archive` のビルド問題を回避し、Cアーカイブが正しく生成されるようになります。

この変更により、`darwin/arm` ターゲットでCアーカイブをビルドする際に、DWARF情報が `__TEXT` セグメントのサイズ計算に影響を与えなくなり、結果としてリンカが正しくMach-Oファイルを生成できるようになります。これは、DWARF情報が特定のビルドモードで問題を引き起こす場合に、その情報を一時的に無視または除外することで、ビルドの成功を優先する典型的なアプローチです。

## コアとなるコードの解説

変更は `src/cmd/link/internal/ld/macho.go` ファイル内の `Asmbmacho` 関数にあります。この関数は、Mach-Oバイナリのセグメント構造を構築する際に呼び出されます。

具体的には、`ms.filesize` の計算ロジックが変更されています。`ms` は `newMachoSeg` で作成されたMach-Oセグメント構造体であり、ここでは `__TEXT` セグメント（またはそれに相当する最初のセグメント）の情報を設定しています。

元のコードでは、`ms.filesize` は常に `Segdwarf.Fileoff + Segdwarf.Filelen - Segtext.Fileoff` と計算されていました。これは、`__TEXT` セグメントの開始オフセット (`Segtext.Fileoff`) から `__DWARF` セグメントの終了オフセット (`Segdwarf.Fileoff + Segdwarf.Filelen`) までの範囲をファイルサイズとして設定することを意味します。そして、`ms.vsize` (仮想メモリサイズ) も同じ値に設定されていました。

変更後のコードでは、以下の条件分岐が導入されています。

```go
		if Thearch.Thechar == '5' {
			ms.filesize = Segdata.Fileoff + Segdata.Filelen - Segtext.Fileoff
		} else {
			ms.filesize = Segdwarf.Fileoff + Segdwarf.Filelen - Segtext.Fileoff
			ms.vsize = ms.filesize
		}
```

*   `Thearch.Thechar == '5'` の条件:
    *   `Thearch.Thechar` は、現在のターゲットアーキテクチャを示す文字です。Goのリンカでは、`'5'` はARMアーキテクチャ（例: `GOARCH=arm`）を意味します。
    *   この条件が真の場合（つまり、ARMアーキテクチャ向けにビルドしている場合）、`ms.filesize` は `Segdata.Fileoff + Segdata.Filelen - Segtext.Fileoff` と計算されます。これは、`__TEXT` セグメントの開始から `__DATA` セグメントの終了までの範囲をファイルサイズとして設定することを意味します。重要なのは、この計算では `__DWARF` セグメントが `__TEXT` セグメントのファイルサイズに含まれない点です。
    *   このブロックでは `ms.vsize` の設定がありませんが、これは `__TEXT` セグメントの仮想メモリサイズがファイルサイズと異なる場合があるため、別途処理されるか、デフォルト値が使用されることを示唆しています。
*   `else` の条件:
    *   `Thearch.Thechar == '5'` が偽の場合（つまり、ARM以外のアーキテクチャ向けにビルドしている場合）、元の計算ロジックが維持されます。`ms.filesize` は `__DWARF` セグメントを含んだ範囲で計算され、`ms.vsize` も同じ値に設定されます。

この変更の核心は、`darwin/arm` ターゲット（`Thearch.Thechar == '5'`）において、Mach-Oファイルの `__TEXT` セグメントのファイルサイズを計算する際に、DWARFデバッグ情報を意図的に除外することです。これにより、DWARF情報が原因で発生していた `-buildmode=c-archive` のビルド問題を回避し、Cアーカイブが正しく生成されるようになります。

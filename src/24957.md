# [インデックス 24957] ファイルの概要

このコミットは、Go言語のアセンブラツール `cmd/asm` における複数のファジング（fuzzing）によって発見されたバグを修正するものです。具体的には、アセンブラが不正な入力に対して適切にエラー処理を行わず、パニックや不正な状態に陥る可能性があった問題を解決しています。主な変更は、エラーが発生した場合にアセンブル処理を早期に中断し、それ以上の処理を行わないようにするガード句の追加です。

## 元コミット内容

`cmd/asm`: ファジングで見つかったいくつかのバグを修正。

一つ（#12466）は、何も存在しない場所でバックアップしようとする実際のロジックエラーでした。その他のバグは、命令が機能しないにもかかわらず処理を続行していたことに起因していました。

命令のアセンブルが成功しないことが分かった時点で、体系的に処理を停止するようにしました。

Issue #12466、#12467、#12468 を修正します。

## 変更の背景

このコミットは、Go言語のアセンブラ `cmd/asm` の堅牢性を向上させることを目的としています。ファジング（fuzzing）テストは、プログラムに予期せぬ、あるいは無効な入力を大量に与えることで、潜在的なバグや脆弱性を発見する手法です。このコミットで修正されたバグは、まさにこのファジングプロセス中に発見されました。

具体的には、以下の問題が報告されていました。

*   **Issue #12466**: コミットメッセージによると、「何も存在しない場所でバックアップしようとする実際のロジックエラー」とされています。これは、パーサーが入力ストリームの先頭より前に戻ろうとするような、内部状態の不整合を示唆しています。このような状況は、通常、プログラムのクラッシュや予期せぬ動作につながります。
*   **Issue #12467**: Web検索の結果から、「cmd/asm: index out of range (3)」というタイトルで、特定の不正な入力 `\"TEXT$0\\xc9:0\\n\"` に対して `cmd/asm` が `panic: runtime error: index out of range` を発生させていたことが確認されています。これは、アセンブラが不正な命令やオペランドを解析しようとした際に、配列の範囲外アクセスを引き起こしていたことを意味します。
*   **Issue #12468**: コミットメッセージでは、「命令が機能しないにもかかわらず処理を続行していた」と説明されています。これは、アセンブラが不正な構文や意味的に無効な命令を検出した後も、エラー状態を適切に伝播させずに処理を続行し、結果としてさらなるエラーやクラッシュを引き起こす可能性があったことを示しています。

これらの問題は、`cmd/asm` が不正な入力に対してより堅牢であるべきだという認識から、修正されることになりました。特に、アセンブラのようなツールは、ユーザーが手書きしたアセンブリコードだけでなく、自動生成されたコードや、意図的に不正な形式のコードを扱う可能性もあるため、堅牢なエラーハンドリングが不可欠です。

## 前提知識の解説

### Go言語のアセンブラ (`cmd/asm`)

Go言語は、そのランタイムや一部の標準ライブラリでアセンブリ言語を使用しています。これは、パフォーマンスが重要な部分や、特定のハードウェア機能にアクセスする必要がある場合に行われます。`cmd/asm` は、Go言語のツールチェインの一部として提供されるアセンブラであり、Goのアセンブリ言語（Plan 9アセンブリの派生）をオブジェクトファイルに変換する役割を担っています。

Goのアセンブリ言語は、一般的なx86-64やARMのアセンブリとは異なり、擬似レジスタや特定の構文規則を持っています。`cmd/asm` は、このGo固有のアセンブリ構文を解析し、機械語に変換する過程で、構文解析（parsing）、意味解析（semantic analysis）、コード生成（code generation）といった段階を経ます。

### ファジング (Fuzzing)

ファジングは、ソフトウェアテストの一種で、プログラムに大量のランダムな、または半ランダムなデータを入力として与え、その応答（クラッシュ、アサーション失敗、メモリリークなど）を監視することで、バグや脆弱性を発見する手法です。特に、パーサーやプロトコル処理、ファイルフォーマット処理など、複雑な入力処理を行うソフトウェアのテストに非常に有効です。

ファジングツールは、既存の有効な入力例を基に、それを少しずつ変異させたり、完全にランダムなデータを生成したりして、テストケースを作成します。このコミットで修正されたバグは、`cmd/asm` に不正なアセンブリコードの断片を入力として与えることで発見されたと考えられます。

### `p.errorf` とエラーハンドリング

Go言語のツールチェインでは、エラーが発生した場合に `p.errorf` のようなメソッドを使用してエラーメッセージを報告することが一般的です。しかし、エラーを報告するだけでは不十分な場合があります。エラーが致命的であるにもかかわらず、プログラムが処理を続行してしまうと、以下のような問題が発生します。

1.  **連鎖的なエラー**: 最初の不正な状態が、後続の処理でさらに多くのエラーを引き起こす。
2.  **クラッシュ**: 不正なデータや状態が原因で、プログラムがパニック（panic）を起こして異常終了する。
3.  **不正な出力**: エラーを抱えたまま処理が完了し、誤った結果やオブジェクトファイルを生成してしまう。

このコミットの背景にあるのは、`p.errorf` でエラーを報告した後、アセンブル処理を即座に中断し、不正な状態での処理続行を防ぐという、より堅牢なエラーハンドリングの原則です。

### `obj.Prog` と `obj.Addr`

`obj` パッケージは、Go言語のコンパイラおよびアセンブラツールチェインで使用される、プログラムの命令（`Prog`）やアドレス（`Addr`）を表現するためのデータ構造を提供します。

*   `obj.Prog`: アセンブリ命令の抽象表現です。オペコード、オペランド、条件コードなどの情報を含みます。
*   `obj.Addr`: オペランドのアドレス指定モードを表現します。レジスタ、オフセット、シンボル、定数などの情報を含みます。

`cmd/asm` は、入力されたアセンブリコードを解析し、これらの `obj.Prog` や `obj.Addr` 構造体に変換していきます。

## 技術的詳細

このコミットの主要な技術的変更は、`cmd/asm` のパーサーおよびアセンブラロジックにおいて、エラーが検出された際に即座に処理を中断する `return` ステートメントを追加することです。これにより、エラー状態での不必要な処理の続行を防ぎ、連鎖的なバグやクラッシュを回避します。

具体的には、以下の箇所で変更が行われています。

1.  **`src/cmd/asm/internal/asm/asm.go`**:
    *   `Parser.append` メソッド内で、条件コードやサフィックスの解析に失敗した場合、`p.errorf` の後に `return` を追加。これにより、不正な条件コードやサフィックスが指定された場合に、その命令のアセンブルを中止します。
    *   ラベルの多重定義が検出された場合も、`p.errorf` の後に `return` を追加し、処理を中断します。
    *   `Parser.asmText` メソッド内で、`TEXT` 命令の引数サイズが不正な形式である場合に `return` を追加。
    *   `Parser.asmData` メソッド内で、`DATA` 命令の値が不正な場合や、データエントリが重複している場合に `return` を追加。
    *   `Parser.asmJump` メソッド内で、不正なレジスタ番号やジャンプターゲットがアセンブルできない場合に `return` を追加。
    *   `Parser.patch` メソッド内で、未定義のラベルが参照された場合に `return` を追加。これにより、未定義ラベルのパッチ処理を試みることを防ぎます。
    *   `Parser.asmInstruction` メソッド内で、命令のアドレッシングモードが不正な場合や、オペランドの数が不正な場合に `return` を追加。

2.  **`src/cmd/asm/internal/asm/parse.go`**:
    *   `Parser.line` メソッド内で、オペランドに不正なコロン `:` が含まれる場合に `return true` を追加。
    *   `Parser.operand` メソッド内で、括弧 `(` の後に何も続かない場合に `p.errorf` の後に `return false` を追加。これは Issue #12466 の「backing up when there was nothing there」という問題に関連している可能性があります。パーサーが入力の先頭より前に戻ろうとするのを防ぐためのガードです。
    *   文字列定数が即値でない場合に `return false` を追加。
    *   `Parser.back` メソッド内で、`p.inputPos` が 0 の場合に `p.errorf` を呼び出し、内部エラーとして報告するように変更。これは、入力ストリームの先頭より前に戻ろうとするロジックエラーを明示的に検出するためのものです。

3.  **テストファイルの追加**:
    *   `src/cmd/asm/internal/asm/operand_test.go` に `{\"(\", \"\"}, // Issue 12466 - backed up before beginning of line.` というテストケースを追加。これは、括弧のみの不正な入力が `cmd/asm` をクラッシュさせないことを確認するためのものです。
    *   `src/cmd/asm/internal/asm/pseudo_test.go` に `TEXT` 命令に関する不正な入力のテストケースを追加。特に、Issue #12467 と #12468 に関連する入力が含まれています。

これらの変更は、`cmd/asm` がエラーを検出した際に、そのエラーを適切に報告し、それ以上無効な処理を続行しないという原則を徹底するものです。これにより、ファジングによって発見されたような、予期せぬ入力に対する堅牢性が大幅に向上します。

## コアとなるコードの解説

このコミットの核心は、`cmd/asm` の内部でエラーが検出された際に、そのエラーを報告する `p.errorf` の直後に `return` ステートメントを追加することです。これにより、エラーが発生した時点で現在の処理フローを中断し、不正な状態での後続処理を防ぎます。

例えば、`src/cmd/asm/internal/asm/asm.go` の `Parser.append` メソッドでは、ARMの条件コードやARM64のサフィックスが認識できない場合に `p.errorf` が呼び出されますが、その後に `return` が追加されています。これにより、不正な条件コードが指定された命令は、それ以上アセンブルされることなく処理が終了します。

また、`src/cmd/asm/internal/asm/parse.go` の `Parser.operand` メソッドでは、括弧 `(` の後に何も続かない不正な入力に対して、`p.next()` でトークンを読み取った結果が `scanner.EOF` であった場合に `p.errorf` を呼び出し、`return false` で処理を中断しています。これは、Issue #12466 で言及された「backing up when there was nothing there」というロジックエラーを防ぐための重要な変更です。パーサーが入力の終端を超えて「バックアップ」しようとするのを防ぎます。

さらに、`Parser.back()` メソッド自体にもガードが追加され、`p.inputPos` が 0（入力ストリームの先頭）であるにもかかわらず `back()` が呼び出された場合に、内部エラーとして報告するようになりました。これは、パーサーの内部状態が不正であることを早期に検出し、デバッグを容易にするための変更です。

これらの変更は、Goのアセンブラが不正な入力に対してより予測可能で堅牢な動作をするようにするためのものであり、ファジングのような厳密なテスト手法によって発見されたエッジケースに対応しています。

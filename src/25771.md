## 変更の背景

このコミットの背景には、GoランタイムがSolarisオペレーティングシステム上でシステムコールを処理する方法に関する特定の課題があります。

通常、GoプログラムがC言語の関数を呼び出す（cgo経由）か、特定のシステムコールを実行する場合、Goランタイムは`asmcgocall`というアセンブリ関数を使用します。この関数は、Goの軽量なゴルーチンスタックから、より大きく安定したOSスレッドのスタック（`g0`スタック）に切り替える役割を担っています。これにより、CコードやOSのシステムコールが安全に実行できるようになります。

しかし、Solaris環境では、特定の状況下（例えば、スレッドの作成や終了時、あるいは低レベルなランタイム処理）で、アクティブなゴルーチン（`g`）が存在しない状態でシステムコールを行う必要がありました。従来の`asmcgocall`の実装は、常に有効な`g`が存在することを前提としており、`g`が`nil`（またはゼロ）の場合には予期せぬ動作やクラッシュを引き起こす可能性がありました。

コミットメッセージにある「Solaris needs to make system calls without a g, and Solaris uses asmcgocall to make system calls. I know, I know.」という記述は、この状況がGoランタイム開発者にとって既知の、しかし厄介な問題であったことを示唆しています。この問題は、CL 16915（Goの変更リスト）および関連するIssue #12277の修正をSolarisで機能させる上で障害となっていたようです。このコミットは、この特定のSolarisの要件に対応し、`asmcgocall`が`g`なしでも堅牢に動作するようにすることで、GoのSolarisサポートを改善することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とアセンブリ言語の基礎知識が必要です。

1.  **Goスケジューラ (GMPモデル):**
    *   **G (Goroutine):** Goの軽量な実行単位。Goランタイムによって管理され、OSスレッドよりもはるかに少ないリソースで作成・実行されます。それぞれが独自のスタックを持ちます。
    *   **M (Machine):** OSスレッドを表します。Goコードを実行する実際のOSスレッドです。
    *   **P (Processor):** 論理プロセッサを表し、MがGoコードを実行するために必要なコンテキストを提供します。Pは実行可能なGのキューを保持します。
    *   **g0 (System Goroutine):** 各M（OSスレッド）には、通常のGとは異なる特別なゴルーチン`g0`が関連付けられています。`g0`は、Goランタイムの内部処理（スケジューリング、スタック切り替え、ガベージコレクションなど）のために使用され、通常のGよりも大きく固定されたスタックを持ちます。Cgo呼び出しやシステムコール時には、通常のGのスタックから`g0`のスタックに切り替えて実行されます。

2.  **`asmcgocall`関数:**
    *   GoコードからCコードを呼び出す（cgo）際に使用されるGoランタイムの内部アセンブリ関数です。
    *   主な役割は、現在のゴルーチン（G）のスタックから、OSスレッド（M）に紐づく`g0`スタックへ実行コンテキストを切り替えることです。これにより、CコードがGoの動的に変化するスタックではなく、OSが管理する安定したスタック上で実行されることを保証します。
    *   スタック切り替え後、C関数を呼び出し、C関数の実行が完了したら、元のGのスタックに戻ります。

3.  **アセンブリ言語 (x86-64):**
    *   このコミットは`src/runtime/asm_amd64.s`ファイルに対する変更であり、x86-64アーキテクチャのアセンブリ言語で記述されています。
    *   **レジスタ:**
        *   `SP`: スタックポインタ。現在のスタックの最上位アドレスを指します。
        *   `CX`, `R8`, `SI`, `DI`, `AX`, `DX`, `BX`: 汎用レジスタ。データの格納やアドレスの計算に使用されます。
    *   **命令:**
        *   `MOVQ`: 64ビットの値を移動します。
        *   `CMPQ`: 64ビットの値を比較します。
        *   `JEQ`: 比較結果が等しい場合にジャンプします。
        *   `CALL`: 関数を呼び出します。
        *   `RET`: 関数から戻ります。
        *   `SUBQ`: 64ビットの値を減算します。
        *   `ANDQ`: ビット単位のAND演算を行います。
        *   `TEXT`: 関数の開始を宣言します。
        *   `NOSPLIT`: スタックの分割を許可しないことを示します。
    *   **`get_tls(CX)`:** スレッドローカルストレージ (TLS) から現在のゴルーチンポインタ`g`を取得し、`CX`レジスタに格納するマクロまたは命令シーケンス。
    *   **`g(CX)`:** `CX`レジスタに格納された`g`ポインタから、現在のゴルーチン構造体へのオフセットアクセス。
    *   **`g_m(R8)`:** `R8`レジスタに格納された`g`ポインタから、関連するM（OSスレッド）へのオフセットアクセス。
    *   **`m_g0(R8)`:** `R8`レジスタに格納されたMポインタから、関連する`g0`（システムゴルーチン）へのオフセットアクセス。
    *   **`gosave<>(SB)`:** 現在のゴルーチンコンテキスト（レジスタ、スタックポインタなど）を保存するGoランタイムの内部関数。

## 技術的詳細

このコミットの技術的な核心は、`asmcgocall`関数が`g`（現在のゴルーチン）が`nil`である可能性を考慮し、それに応じて異なる実行パスを取るように修正された点にあります。

元の`asmcgocall`の実装では、Cgo呼び出しを行う際に、まず現在のゴルーチン`g`を取得し、その`g`に関連付けられたM（OSスレッド）の`g0`スタックに切り替える処理を行っていました。この切り替えには、現在のゴルーチンコンテキスト（特にスタックポインタ）を保存する`gosave`の呼び出しが含まれていました。これは、Cgo呼び出しから戻った後に元のゴルーチンに正しく復帰するために必要です。

しかし、Solarisのような特定のOS環境では、Goランタイムの初期化フェーズやスレッド管理の低レベルな部分で、まだ有効な`g`が割り当てられていない状態でシステムコール（`asmcgocall`を介して行われる）が必要になるケースがありました。このような状況で`g`が`nil`であるにもかかわらず、`g`のフィールドにアクセスしようとすると、パニックやセグメンテーション違反が発生する可能性がありました。

このコミットは、`asmcgocall`の冒頭で`g`が`nil`であるかどうかをチェックするロジックを追加します。

1.  `get_tls(CX)`で現在の`g`を取得し、`R8`に格納します。
2.  `CMPQ R8, $0`で`R8`（`g`）がゼロ（`nil`）であるかをチェックします。
3.  もし`g`がゼロであれば、`JEQ nosave`命令によって新しい`nosave`ラベルにジャンプします。

`nosave`パスでは、`g`が存在しないため、ゴルーチンコンテキストの保存や`g0`スタックへの切り替え（`gosave`の呼び出し）は行いません。代わりに、既にシステムスタック上にいることを前提とし、C関数呼び出しに必要なスタックフレームの準備と、C関数からの戻り値の処理のみを行います。このパスは、スレッド作成や終了時など、既にシステムスタック上で動作しており、ゴルーチンスタックの管理が不要な場合に利用されます。

この変更により、`asmcgocall`は`g`の有無にかかわらず安全に動作するようになり、Solarisにおける特定の低レベルなシステムコール要件を満たすことができるようになりました。また、コミットメッセージにあるように、この`nosave`パスを「既にシステムスタック上にいる」全ての場合に利用することで、コードのテストカバレッジを増やし、堅牢性を高める意図も含まれています。

## コアとなるコードの解説

変更された`asm_amd64.s`の`asmcgocall`関数は、主に以下の2つのセクションに分けられます。

1.  **`g`の存在チェックと分岐:**
    ```assembly
    	get_tls(CX)
    	MOVQ	g(CX), R8
    	CMPQ	R8, $0
    	JEQ	nosave
    ```
    *   `get_tls(CX)`: スレッドローカルストレージから現在のゴルーチンポインタ`g`を取得し、`CX`レジスタに格納します。
    *   `MOVQ g(CX), R8`: `CX`レジスタにある`g`ポインタを`R8`レジスタに移動します。
    *   `CMPQ R8, $0`: `R8`（`g`ポインタ）がゼロ（`nil`）であるかを比較します。
    *   `JEQ nosave`: もし`g`がゼロであれば、`nosave`ラベルにジャンプします。これは、ゴルーチンコンテキストが存在しないため、通常のスタック保存・切り替えロジックをスキップする必要があることを意味します。

2.  **`nosave`パス (新しいセクション):**
    このセクションは、`g`が存在しない場合に実行されます。
    ```assembly
    nosave:
    	// Running on a system stack, perhaps even without a g.
    	// Having no g can happen during thread creation or thread teardown
    	// (see needm/dropm on Solaris, for example).
    	// This code is like the above sequence but without saving/restoring g
    	// and without worrying about the stack moving out from under us
    	// (because we're on a system stack, not a goroutine stack).
    	// The above code could be used directly if already on a system stack,
    	// but then the only path through this code would be a rare case on Solaris.
    	// Using this code for all "already on system stack" calls exercises it more,
    	// which should help keep it correct.
    	SUBQ	$64, SP
    	ANDQ	$~15, SP
    	MOVQ	$0, 48(SP)		// where above code stores g, in case someone looks during debugging
    	MOVQ	DX, 40(SP)	// save original stack pointer
    	MOVQ	BX, DI		// DI = first argument in AMD64 ABI
    	MOVQ	BX, CX		// CX = first argument in Win64
    	CALL	AX
    	MOVQ	40(SP), SI	// restore original stack pointer
    	MOVQ	SI, SP
    	MOVL	AX, ret+16(FP)
    	RET
    ```
    *   このパスは、既にシステムスタック上で動作していることを前提としています。
    *   `SUBQ $64, SP` と `ANDQ $~15, SP`: スタックポインタを調整し、スタックフレームをアラインメントします。これはC関数呼び出しのABI（Application Binary Interface）要件を満たすためです。
    *   `MOVQ $0, 48(SP)`: デバッグ時に`g`が格納される可能性のある場所にゼロを書き込みます。これは、`g`が存在しないことを明示的に示すためのものです。
    *   `MOVQ DX, 40(SP)`: 元のスタックポインタを保存します。
    *   `MOVQ BX, DI` と `MOVQ BX, CX`: C関数呼び出しの引数をレジスタに設定します。AMD64 ABIでは最初の引数は`DI`、Win64では`CX`を使用します。
    *   `CALL AX`: `AX`レジスタに格納されているアドレス（呼び出すC関数のアドレス）にジャンプして関数を実行します。
    *   `MOVQ 40(SP), SI` と `MOVQ SI, SP`: 保存しておいた元のスタックポインタを復元します。
    *   `MOVL AX, ret+16(FP)`: C関数からの戻り値（`AX`レジスタに格納されている）をGoの戻り値として設定します。
    *   `RET`: 関数から戻ります。

この`nosave`パスの導入により、`asmcgocall`は`g`が存在しないという特殊な状況でも安全にシステムコールを実行できるようになり、Solaris環境でのGoランタイムの安定性と互換性が向上しました。

## 変更の背景

Go言語には、エラーハンドリングやゴルーチンの終了を制御するためのいくつかのメカニズムがあります。`panic`、`recover`、`defer`、そして`runtime.Goexit`がそれらです。これらの機能はそれぞれ異なる目的を持っていますが、特に`Goexit`と`panic`の挙動の違い、そしてそれらが`recover`とどのように相互作用するのかについて、開発者の間で混乱が生じることがありました。

`Goexit`は現在のゴルーチンを終了させるために使用されますが、これは`panic`とは根本的に異なる終了メカニズムです。`panic`はスタックをアンワインドし、その過程で`defer`関数を実行し、`recover`によって捕捉される可能性があります。しかし、`Goexit`は`panic`のようなエラー状態を示すものではなく、単にゴルーチンの実行を停止させるものです。この違いが、`Goexit`によってトリガーされた`defer`関数内で`recover`を呼び出した場合に何が起こるのかという疑問につながっていました。

このコミットは、`Goexit`が`panic`ではないため、`Goexit`によって実行される`defer`関数内で`recover`を呼び出しても、`panic`が発生していないため`nil`が返されるという事実を明確にするために行われました。これにより、開発者が`Goexit`の挙動を誤解し、意図しない結果を招くことを防ぐことが目的です。

## 前提知識の解説

このコミットの理解には、Go言語の以下の概念の理解が不可欠です。

1.  **ゴルーチン (Goroutine)**: Goランタイムによって管理される軽量なスレッドです。Goプログラムは1つ以上のゴルーチンで構成され、`go`キーワードを使って新しいゴルーチンを起動できます。
2.  **`defer`文**: `defer`文は、それが含まれる関数がリターンする直前（または`panic`によって関数が終了する直前）に、指定された関数（遅延関数）を実行することを保証します。複数の`defer`文がある場合、それらはLIFO（後入れ先出し）の順序で実行されます。
3.  **`panic`**: `panic`は、プログラムが回復不可能なエラー状態に陥ったことを示すために使用されます。`panic`が呼び出されると、現在の関数の通常の実行は停止し、遅延関数が通常通り実行されます。その後、呼び出し元の関数に制御が戻り、その関数の遅延関数も実行されます。このプロセスは、現在のゴルーチンのスタックがアンワインドされるまで続きます。
4.  **`recover`**: `recover`は、`panic`が発生したゴルーチン内で、`defer`関数の中からのみ呼び出すことができます。`recover`が`panic`を捕捉すると、`panic`の値が返され、ゴルーチンの通常の実行が再開されます。`defer`関数以外から`recover`を呼び出したり、`panic`が発生していないときに`recover`を呼び出したりすると、`nil`が返されます。
5.  **`runtime.Goexit()`**: `runtime`パッケージの`Goexit`関数は、現在のゴルーチンを終了させます。`Goexit`が呼び出されると、現在の関数の残りの処理はスキップされ、`defer`関数が実行されます。すべての`defer`関数が実行された後、ゴルーチンは終了します。`Goexit`は`panic`とは異なり、エラー状態を示すものではありません。

重要な点は、`panic`と`Goexit`がゴルーチンを終了させるという点で似ていますが、そのメカニズムと`recover`との相互作用が異なることです。`panic`はエラー伝播メカニズムであり、`recover`によって捕捉されることを意図しています。一方、`Goexit`は単なるゴルーチン終了メカニズムであり、`panic`ではないため、`recover`の対象ではありません。

## 技術的詳細

このコミットの技術的な変更は非常にシンプルで、`src/runtime/panic.go`ファイル内の`Goexit`関数のドキュメンテーションコメントの修正のみです。しかし、その意味するところはGoの並行処理とエラーハンドリングの挙動を正確に理解する上で重要です。

変更前は、`Goexit`のコメントは以下のようになっていました。

```go
// Goexit terminates the goroutine that calls it.  No other goroutine is affected.
// Goexit runs all deferred calls before terminating the goroutine.
```

この記述は、`Goexit`が`defer`関数を実行するという事実を述べていますが、`defer`関数内で`recover`がどのように振る舞うかについては言及していませんでした。この曖昧さが、`Goexit`が`panic`と同様に`recover`によって捕捉される可能性があるという誤解を生む原因となっていました。

このコミットによって、コメントは以下のように変更されました。

```go
// Goexit terminates the goroutine that calls it.  No other goroutine is affected.
// Goexit runs all deferred calls before terminating the goroutine.  Because Goexit
// is not panic, however, any recover calls in those deferred functions will return nil.
```

追加された部分「`Because Goexit is not panic, however, any recover calls in those deferred functions will return nil.`」がこの変更の核心です。これは、`Goexit`が`panic`ではないため、`Goexit`によってトリガーされた`defer`関数内で`recover()`を呼び出しても、`panic`がアクティブではないため常に`nil`が返されることを明確にしています。

この変更は、Goランタイムの実際の挙動を変更するものではなく、その挙動に関するドキュメンテーションを改善するものです。これにより、開発者は`Goexit`と`panic`/`recover`の間の重要な違いをより正確に理解し、それらを適切に使用できるようになります。特に、`Goexit`を`panic`の代替として使用しようとする誤ったパターンを防ぐのに役立ちます。

## コアとなるコードの解説

変更された行は、`Goexit`関数のドキュメンテーションコメントの一部です。

元のコメント:
`// Goexit runs all deferred calls before terminating the goroutine.`

変更後のコメント:
`// Goexit runs all deferred calls before terminating the goroutine. Because Goexit`
`// is not panic, however, any recover calls in those deferred functions will return nil.`

この変更は、`Goexit`が`defer`関数を実行する際に、`panic`とは異なる振る舞いをすること、特に`recover`の戻り値が`nil`になることを明示的に記述しています。これは、`Goexit`が`panic`メカニズムを使用せずにゴルーチンを終了させるため、`recover`が捕捉すべき`panic`が存在しないことを意味します。したがって、`defer`関数内で`recover()`を呼び出しても、捕捉する`panic`がないため、常に`nil`が返されるというGoランタイムの既存の挙動を正確に反映したものです。

このコメントの追加により、`Goexit`のセマンティクスがより明確になり、開発者が`panic`/`recover`と`Goexit`を混同する可能性が低減されます。これは、Go言語のAPIドキュメンテーションの正確性と明確性を向上させるための重要な改善です。

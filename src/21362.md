## 変更の背景

この変更の背景には、`cgo`を使用してC/C++コードとGoコードを連携させる際に、外部ライブラリやヘッダーファイルのパス指定に関する問題がありました。

従来の`#cgo`ディレクティブでは、コンパイラやリンカに渡すパスを相対パスで指定した場合、Goプログラムのビルドが実行されるカレントワーキングディレクトリ（CWD）が変更されると、これらの相対パスが不正になり、ビルドが失敗するという問題がありました。例えば、プロジェクトのルートディレクトリで`go build`を実行する場合と、サブディレクトリで実行する場合とで、相対パスの解釈が変わってしまうことが挙げられます。

特に、Goパッケージ内にプリコンパイルされたスタティックライブラリ（例: `.a`ファイル）を配置し、それを`#cgo LDFLAGS`などでリンクしようとする場合、ライブラリへのパスをソースコードディレクトリからの相対パスで指定することが一般的です。しかし、CWDの変更によってこの相対パスが解決できなくなり、ビルドの再現性や移植性が損なわれていました。

このコミットは、この問題を解決するために、`#cgo`ディレクティブ内で`${SRCDIR}`という特殊な変数を導入し、これをGoのビルドシステムが自動的に現在のソースファイルが存在するディレクトリの絶対パスに展開するようにしました。これにより、ユーザーは常にソースディレクトリを基準とした絶対パスを安全に指定できるようになり、CWDに依存しない堅牢なビルドが可能になりました。コミットメッセージに記載されている`Fixes #7891`と`Fixes #5428`は、この問題に関連する既存のバグ報告や改善要求に対応するものです。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語および関連技術の概念を理解しておく必要があります。

### Go言語のビルドシステム

Go言語には、`go build`コマンドを中心とした強力なビルドシステムが組み込まれています。このシステムは、ソースコードの依存関係を自動的に解決し、コンパイル、リンクを行い、実行可能なバイナリを生成します。Goのビルドシステムは、通常、Goのソースファイル（`.go`）のみを扱いますが、C/C++などの他の言語で書かれたコードと連携するためのメカニズムも提供しています。

### `cgo`ツール

`cgo`は、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoのツールです。Goのソースファイル内で`import "C"`と記述することで`cgo`が有効になります。`cgo`は、GoとCの間の型変換や関数呼び出しの橋渡しとなるコードを生成し、GoのビルドプロセスにCコンパイラやリンカを統合します。

### `#cgo`ディレクティブ

`cgo`を使用するGoのソースファイル内では、特別なコメント形式で`#cgo`ディレクティブを記述することができます。これらのディレクティブは、Cコンパイラやリンカに渡すオプションを指定するために使用されます。主なディレクティブには以下のようなものがあります。

*   `#cgo CFLAGS: ...`: Cコンパイラに渡すフラグ（例: `-I/path/to/include`でインクルードパスを指定）。
*   `#cgo LDFLAGS: ...`: リンカに渡すフラグ（例: `-L/path/to/lib -lfoo`でライブラリパスとライブラリ名を指定）。
*   `#cgo pkg-config: ...`: `pkg-config`ツールを使用して、ライブラリのコンパイル・リンクオプションを自動的に取得。

これらのディレクティブは、Goのビルドシステムによって解析され、実際のCコンパイラやリンカのコマンドライン引数に変換されます。

### `LDFLAGS` (Linker Flags)

`LDFLAGS`は、リンカに渡されるオプションの集合です。リンカは、コンパイルされたオブジェクトファイルとライブラリを結合して最終的な実行可能ファイルを生成するツールです。`LDFLAGS`は、リンカがライブラリを探すパス（`-L`オプション）や、リンクするライブラリの名前（`-l`オプション）などを指定するために頻繁に使用されます。

### `SRCDIR` (Source Directory)

`SRCDIR`は、このコミットで導入された概念であり、Goのビルドシステムが`#cgo`ディレクティブ内で認識する特殊な変数です。これは、現在処理されているGoソースファイルが存在するディレクトリの絶対パスを表します。この変数が導入される前は、`#cgo`ディレクティブ内で相対パスを使用すると、ビルドが実行されるカレントワーキングディレクトリによってパスの解釈が変わるという問題がありました。`${SRCDIR}`を使用することで、常にソースファイルからの相対的な位置を絶対パスとして指定できるようになります。

### パス解決とカレントワーキングディレクトリ (CWD)

コンピュータシステムでは、ファイルやディレクトリへのパスは、絶対パス（ルートディレクトリからの完全なパス）または相対パス（現在のワーキングディレクトリからのパス）で指定されます。Goのビルドプロセスでは、`go build`コマンドが実行されるディレクトリがカレントワーキングディレクトリとなります。相対パスはCWDに依存するため、CWDが変わると同じ相対パスでも参照するファイルが変わってしまう可能性があります。このコミットは、このCWD依存性を解消し、パス指定の堅牢性を高めることを目的としています。

## 技術的詳細

このコミットの技術的な核心は、Goのビルドシステムが`#cgo`ディレクティブを解析する際に、`${SRCDIR}`というプレースホルダーを実際のソースディレクトリの絶対パスに置き換える（展開する）メカニズムを導入した点にあります。

### `expandSrcDir`関数の導入

コミットの主要な変更点の一つは、`src/go/build/build.go`に`expandSrcDir`という新しいヘルパー関数が追加されたことです。

```go
func expandSrcDir(str string, srcdir string) string {
	// "\" delimited paths cause safeCgoName to fail
	// so convert native paths with a different delimeter
	// to "/" before starting (eg: on windows)
	srcdir = filepath.ToSlash(srcdir)
	return strings.Replace(str, "${SRCDIR}", srcdir, -1)
}
```

この関数は、以下の2つの引数を受け取ります。
*   `str`: 展開対象の文字列（例: `#cgo LDFLAGS: -L${SRCDIR}/libs -lfoo`の`-L${SRCDIR}/libs -lfoo`部分）。
*   `srcdir`: ソースファイルが存在するディレクトリの絶対パス。

関数内部では、まず`srcdir`がWindowsのようなバックスラッシュ（`\`）をパス区切り文字として使用するシステムの場合でも、スラッシュ（`/`）に変換されます。これは、`#cgo`ディレクティブの引数が通常スラッシュ区切りで記述されること、および後続の`safeCgoName`関数がバックスラッシュを含むパスを安全でないと判断するのを避けるためです。

その後、`strings.Replace`関数を使用して、`str`内のすべての`${SRCDIR}`の出現箇所を、変換された`srcdir`の絶対パスに置き換えます。`-1`は、すべての出現箇所を置き換えることを意味します。

### `saveCgo`関数での`expandSrcDir`の利用

`expandSrcDir`関数は、`src/go/build/build.go`内の`saveCgo`関数から呼び出されます。`saveCgo`関数は、Goのビルドコンテキスト（`*Context`）の一部であり、Goソースファイル内の`#cgo`ディレクティブを解析し、それらをビルドに必要なCコンパイラやリンカのオプションに変換する役割を担っています。

変更前は、`#cgo`ディレクティブの引数（`args`）は直接`safeCgoName`で検証されていましたが、変更後は`safeCgoName`の呼び出しの前に`expandSrcDir`が適用されるようになりました。

```go
// 変更前
// for _, arg := range args {
//     if !safeCgoName(arg) {
//         return fmt.Errorf("%s: malformed #cgo argument: %s", filename, arg)
//     }
// }

// 変更後
for i, arg := range args {
    arg = expandSrcDir(arg, di.Dir) // ここで展開
    if !safeCgoName(arg) {
        return fmt.Errorf("%s: malformed #cgo argument: %s", filename, arg)
    }
    args[i] = arg // 展開された引数を元のスライスに格納
}
```

ここで、`di.Dir`は、現在処理中のGoパッケージのソースディレクトリの絶対パスを保持しています。`expandSrcDir`が呼び出されることで、`#cgo`ディレクティブの各引数に含まれる`${SRCDIR}`が、そのGoファイルが実際に存在するディレクトリの絶対パスに置き換えられます。これにより、リンカやコンパイラに渡されるパスが常に絶対パスとなり、カレントワーキングディレクトリに依存しない堅牢なビルドが可能になります。

### ドキュメントの更新

`src/cmd/cgo/doc.go`には、新しく導入された`${SRCDIR}`変数の使用方法と、それがどのように展開されるかについての説明が追加されました。これにより、`cgo`を使用する開発者がこの新機能を適切に利用できるようになります。

### テストケースの追加

`src/go/build/build_test.go`には、`expandSrcDir`関数の動作を検証するための新しいテストケース`TestExpandSrcDir`が追加されました。このテストは、さまざまな入力文字列と`${SRCDIR}`のパスに対して、期待される出力が生成されることを確認します。これにより、この新機能が正しく動作し、将来の変更によって意図せず壊れることがないように保証されます。

## コアとなるコードの解説

### `src/cmd/cgo/doc.go`の変更

この変更は、`cgo`の公式ドキュメントに`${SRCDIR}`変数の説明を追加するものです。具体的には、`#cgo`ディレクティブが解析される際に、`${SRCDIR}`がソースファイルを含むディレクトリの絶対パスに置き換えられること、そしてこれがプリコンパイルされたスタティックライブラリをパッケージディレクトリに含めて適切にリンクするために役立つことが明記されています。例として、`/go/src/foo`にあるパッケージの場合の`#cgo LDFLAGS: -L${SRCDIR}/libs -lfoo`がどのように展開されるかが示されており、開発者がこの新機能を理解しやすくしています。

### `src/go/build/build.go`の変更

このファイルには、`#cgo`ディレクティブの実際の処理ロジックが含まれています。

*   **`expandSrcDir`関数の追加**:
    この新しい関数は、文字列内の`${SRCDIR}`プレースホルダーを、指定されたソースディレクトリの絶対パスに置き換える役割を担います。`filepath.ToSlash(srcdir)`を使用することで、Windows環境などでのパス区切り文字の違いを吸収し、常にスラッシュ区切りのパスとして展開されるようにしています。これは、`cgo`の引数が通常スラッシュ区切りで扱われるため、クロスプラットフォームでの互換性を確保するために重要です。

*   **`saveCgo`関数の変更**:
    `saveCgo`関数は、Goソースファイルから`#cgo`ディレクティブを抽出し、その引数を処理します。変更前は、抽出された引数（`args`スライス）は直接`safeCgoName`関数で安全性がチェックされていました。変更後は、`safeCgoName`を呼び出す前に、各引数に対して`expandSrcDir(arg, di.Dir)`が呼び出されるようになりました。ここで`di.Dir`は、現在処理中のGoパッケージのルートディレクトリの絶対パスです。これにより、`#cgo`ディレクティブに記述された`${SRCDIR}`が、ビルド時に実際の絶対パスに置き換えられ、リンカやコンパイラに渡されるパスが常に有効なものとなります。展開された引数は、元の`args`スライスの対応するインデックスに`args[i] = arg`として格納されます。

### `src/go/build/build_test.go`の変更

このファイルには、`expandSrcDir`関数の単体テストが追加されました。`expandSrcDirTests`という構造体のスライスが定義され、さまざまな入力文字列と期待される出力、そして`${SRCDIR}`として使用されるパス（`expandSrcDirPath`）の組み合わせが用意されています。テストはこれらの組み合わせをループし、`expandSrcDir`関数が期待通りに文字列を展開するかどうかを検証します。これにより、新しく追加された機能が正しく動作すること、および将来のコード変更によってこの機能が意図せず壊れることがないように、品質が保証されます。特に、`${SRCDIR}`が含まれない文字列や、`$`記号が単独で出現する場合など、エッジケースも考慮されていることがわかります。

## 変更の背景

この変更の背景には、`cgo`を使用してC/C++コードとGoコードを連携させる際に、外部ライブラリやヘッダーファイルのパス指定に関する問題がありました。

従来の`#cgo`ディレクティブでは、コンパイラやリンカに渡すパスを相対パスで指定した場合、Goプログラムのビルドが実行されるカレントワーキングディレクトリ（CWD）が変更されると、これらの相対パスが不正になり、ビルドが失敗するという問題がありました。例えば、プロジェクトのルートディレクトリで`go build`を実行する場合と、サブディレクトリで実行する場合とで、相対パスの解釈が変わってしまうことが挙げられます。

特に、Goパッケージ内にプリコンパイルされたスタティックライブラリ（例: `.a`ファイル）を配置し、それを`#cgo LDFLAGS`などでリンクしようとする場合、ライブラリへのパスをソースコードディレクトリからの相対パスで指定することが一般的です。しかし、CWDの変更によってこの相対パスが解決できなくなり、ビルドの再現性や移植性が損なわれていました。

このコミットは、この問題を解決するために、`#cgo`ディレクティブ内で`${SRCDIR}`という特殊な変数を導入し、これをGoのビルドシステムが自動的に現在のソースファイルが存在するディレクトリの絶対パスに展開するようにしました。これにより、ユーザーは常にソースディレクトリを基準とした絶対パスを安全に指定できるようになり、CWDに依存しない堅牢なビルドが可能になりました。コミットメッセージに記載されている`Fixes #7891`と`Fixes #5428`は、この問題に関連する既存のバグ報告や改善要求に対応するものです。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語および関連技術の概念を理解しておく必要があります。

### Go言語のビルドシステム

Go言語には、`go build`コマンドを中心とした強力なビルドシステムが組み込まれています。このシステムは、ソースコードの依存関係を自動的に解決し、コンパイル、リンクを行い、実行可能なバイナリを生成します。Goのビルドシステムは、通常、Goのソースファイル（`.go`）のみを扱いますが、C/C++などの他の言語で書かれたコードと連携するためのメカニズムも提供しています。

### `cgo`ツール

`cgo`は、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoのツールです。Goのソースファイル内で`import "C"`と記述することで`cgo`が有効になります。`cgo`は、GoとCの間の型変換や関数呼び出しの橋渡しとなるコードを生成し、GoのビルドプロセスにCコンパイラやリンカを統合します。

### `#cgo`ディレクティブ

`cgo`を使用するGoのソースファイル内では、特別なコメント形式で`#cgo`ディレクティブを記述することができます。これらのディレクティブは、Cコンパイラやリンカに渡すオプションを指定するために使用されます。主なディレクティブには以下のようなものがあります。

*   `#cgo CFLAGS: ...`: Cコンパイラに渡すフラグ（例: `-I/path/to/include`でインクルードパスを指定）。
*   `#cgo LDFLAGS: ...`: リンカに渡すフラグ（例: `-L/path/to/lib -lfoo`でライブラリパスとライブラリ名を指定）。
*   `#cgo pkg-config: ...`: `pkg-config`ツールを使用して、ライブラリのコンパイル・リンクオプションを自動的に取得。

これらのディレクティブは、Goのビルドシステムによって解析され、実際のCコンパイラやリンカのコマンドライン引数に変換されます。

### `LDFLAGS` (Linker Flags)

`LDFLAGS`は、リンカに渡されるオプションの集合です。リンカは、コンパイルされたオブジェクトファイルとライブラリを結合して最終的な実行可能ファイルを生成するツールです。`LDFLAGS`は、リンカがライブラリを探すパス（`-L`オプション）や、リンクするライブラリの名前（`-l`オプション）などを指定するために頻繁に使用されます。

### `SRCDIR` (Source Directory)

`SRCDIR`は、このコミットで導入された概念であり、Goのビルドシステムが`#cgo`ディレクティブ内で認識する特殊な変数です。これは、現在処理されているGoソースファイルが存在するディレクトリの絶対パスを表します。この変数が導入される前は、`#cgo`ディレクティブ内で相対パスを使用すると、ビルドが実行されるカレントワーキングディレクトリによってパスの解釈が変わるという問題がありました。`${SRCDIR}`を使用することで、常にソースファイルからの相対的な位置を絶対パスとして指定できるようになります。

### パス解決とカレントワーキングディレクトリ (CWD)

コンピュータシステムでは、ファイルやディレクトリへのパスは、絶対パス（ルートディレクトリからの完全なパス）または相対パス（現在のワーキングディレクトリからのパス）で指定されます。Goのビルドプロセスでは、`go build`コマンドが実行されるディレクトリがカレントワーキングディレクトリとなります。相対パスはCWDに依存するため、CWDが変わると同じ相対パスでも参照するファイルが変わってしまう可能性があります。このコミットは、このCWD依存性を解消し、パス指定の堅牢性を高めることを目的としています。

## 技術的詳細

このコミットの技術的な核心は、Goのビルドシステムが`#cgo`ディレクティブを解析する際に、`${SRCDIR}`というプレースホルダーを実際のソースディレクトリの絶対パスに置き換える（展開する）メカニズムを導入した点にあります。

### `expandSrcDir`関数の導入

コミットの主要な変更点の一つは、`src/go/build/build.go`に`expandSrcDir`という新しいヘルパー関数が追加されたことです。

```go
func expandSrcDir(str string, srcdir string) string {
	// "\" delimited paths cause safeCgoName to fail
	// so convert native paths with a different delimeter
	// to "/" before starting (eg: on windows)
	srcdir = filepath.ToSlash(srcdir)
	return strings.Replace(str, "${SRCDIR}", srcdir, -1)
}
```

この関数は、以下の2つの引数を受け取ります。
*   `str`: 展開対象の文字列（例: `#cgo LDFLAGS: -L${SRCDIR}/libs -lfoo`の`-L${SRCDIR}/libs -lfoo`部分）。
*   `srcdir`: ソースファイルが存在するディレクトリの絶対パス。

関数内部では、まず`srcdir`がWindowsのようなバックスラッシュ（`\`）をパス区切り文字として使用するシステムの場合でも、スラッシュ（`/`）に変換されます。これは、`#cgo`ディレクティブの引数が通常スラッシュ区切りで記述されること、および後続の`safeCgoName`関数がバックスラッシュを含むパスを安全でないと判断するのを避けるためです。

その後、`strings.Replace`関数を使用して、`str`内のすべての`${SRCDIR}`の出現箇所を、変換された`srcdir`の絶対パスに置き換えます。`-1`は、すべての出現箇所を置き換えることを意味します。

### `saveCgo`関数での`expandSrcDir`の利用

`expandSrcDir`関数は、`src/go/build/build.go`内の`saveCgo`関数から呼び出されます。`saveCgo`関数は、Goのビルドコンテキスト（`*Context`）の一部であり、Goソースファイル内の`#cgo`ディレクティブを解析し、それらをビルドに必要なCコンパイラやリンカのオプションに変換する役割を担っています。

変更前は、`#cgo`ディレクティブの引数（`args`）は直接`safeCgoName`で検証されていましたが、変更後は`safeCgoName`の呼び出しの前に`expandSrcDir`が適用されるようになりました。

```go
// 変更前
// for _, arg := range args {
//     if !safeCgoName(arg) {
//         return fmt.Errorf("%s: malformed #cgo argument: %s", filename, arg)
//     }
// }

// 変更後
for i, arg := range args {
    arg = expandSrcDir(arg, di.Dir) // ここで展開
    if !safeCgoName(arg) {
        return fmt.Errorf("%s: malformed #cgo argument: %s", filename, arg)
    }
    args[i] = arg // 展開された引数を元のスライスに格納
}
```

ここで、`di.Dir`は、現在処理中のGoパッケージのソースディレクトリの絶対パスを保持しています。`expandSrcDir`が呼び出されることで、`#cgo`ディレクティブの各引数に含まれる`${SRCDIR}`が、そのGoファイルが実際に存在するディレクトリの絶対パスに置き換えられます。これにより、リンカやコンパイラに渡されるパスが常に絶対パスとなり、カレントワーキングディレクトリに依存しない堅牢なビルドが可能になります。

### ドキュメントの更新

`src/cmd/cgo/doc.go`には、新しく導入された`${SRCDIR}`変数の使用方法と、それがどのように展開されるかについての説明が追加されました。これにより、`cgo`を使用する開発者がこの新機能を適切に利用できるようになります。

### テストケースの追加

`src/go/build/build_test.go`には、`expandSrcDir`関数の動作を検証するための新しいテストケース`TestExpandSrcDir`が追加されました。このテストは、さまざまな入力文字列と`${SRCDIR}`のパスに対して、期待される出力が生成されることを確認します。これにより、この新機能が正しく動作し、将来の変更によって意図せず壊れることがないように保証されます。

## コアとなるコードの解説

### `src/cmd/cgo/doc.go`の変更

この変更は、`cgo`の公式ドキュメントに`${SRCDIR}`変数の説明を追加するものです。具体的には、`#cgo`ディレクティブが解析される際に、`${SRCDIR}`がソースファイルを含むディレクトリの絶対パスに置き換えられること、そしてこれがプリコンパイルされたスタティックライブラリをパッケージディレクトリに含めて適切にリンクするために役立つことが明記されています。例として、`/go/src/foo`にあるパッケージの場合の`#cgo LDFLAGS: -L${SRCDIR}/libs -lfoo`がどのように展開されるかが示されており、開発者がこの新機能を理解しやすくしています。

### `src/go/build/build.go`の変更

このファイルには、`#cgo`ディレクティブの実際の処理ロジックが含まれています。

*   **`expandSrcDir`関数の追加**:
    この新しい関数は、文字列内の`${SRCDIR}`プレースホルダーを、指定されたソースディレクトリの絶対パスに置き換える役割を担います。`filepath.ToSlash(srcdir)`を使用することで、Windows環境などでのパス区切り文字の違いを吸収し、常にスラッシュ区切りのパスとして展開されるようにしています。これは、`cgo`の引数が通常スラッシュ区切りで扱われるため、クロスプラットフォームでの互換性を確保するために重要です。

*   **`saveCgo`関数の変更**:
    `saveCgo`関数は、Goソースファイルから`#cgo`ディレクティブを抽出し、その引数を処理します。変更前は、抽出された引数（`args`スライス）は直接`safeCgoName`関数で安全性がチェックされていました。変更後は、`safeCgoName`を呼び出す前に、各引数に対して`expandSrcDir(arg, di.Dir)`が呼び出されるようになりました。ここで`di.Dir`は、現在処理中のGoパッケージのルートディレクトリの絶対パスです。これにより、`#cgo`ディレクティブに記述された`${SRCDIR}`が、ビルド時に実際の絶対パスに置き換えられ、リンカやコンパイラに渡されるパスが常に有効なものとなります。展開された引数は、元の`args`スライスの対応するインデックスに`args[i] = arg`として格納されます。

### `src/go/build/build_test.go`の変更

このファイルには、`expandSrcDir`関数の単体テストが追加されました。`expandSrcDirTests`という構造体のスライスが定義され、さまざまな入力文字列と期待される出力、そして`${SRCDIR}`として使用されるパス（`expandSrcDirPath`）の組み合わせが用意されています。テストはこれらの組み合わせをループし、`expandSrcDir`関数が期待通りに文字列を展開するかどうかを検証します。これにより、新しく追加された機能が正しく動作すること、および将来のコード変更によってこの機能が意図せず壊れることがないように、品質が保証されます。特に、`${SRCDIR}`が含まれない文字列や、`$`記号が単独で出現する場合など、エッジケースも考慮されていることがわかります。

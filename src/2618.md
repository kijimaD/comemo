## 変更の背景

Go言語の設計思想の一つに、シンプルさと明確なスコープ規則があります。このコミットが対処しようとしている「bug167」は、その原則が初期のコンパイラ実装で完全に守られていなかったことを示唆しています。具体的には、異なる関数内で同じ名前の構造体型を定義した場合、コンパイラがこれらを別々の独立した型として認識せず、グローバルスコープで定義されたかのように扱ってしまい、結果として型定義の衝突エラーを発生させていました。

このような挙動は、プログラマが意図しない型名の衝突を引き起こし、コードのモジュール性や再利用性を損なう可能性があります。関数内で定義された型は、その関数スコープ内でのみ有効であるべきであり、他のスコープの型定義とは独立しているべきです。このコミットは、この問題（bug167）を明確に再現するテストケースを導入することで、コンパイラの型システムにおけるこの不整合を浮き彫りにし、将来的な修正の必要性を示しています。

## 前提知識の解説

### スコープ (Scope)
プログラミング言語におけるスコープとは、変数、関数、型などの識別子が参照可能であるプログラムの領域を指します。Go言語には、主に以下のスコープがあります。
- **ユニバーススコープ**: 組み込み型（`int`, `string`など）や組み込み関数（`len`, `cap`など）が属する最も広いスコープ。
- **パッケージスコープ**: パッケージレベルで宣言された識別子（変数、関数、型など）が属するスコープ。パッケージ内のどのファイルからも参照可能です。
- **ファイルスコープ**: Goには明示的なファイルスコープはありませんが、パッケージスコープの一部としてファイル内で宣言された識別子が扱われます。
- **関数スコープ**: 関数内で宣言された識別子（ローカル変数、引数、関数内で定義された型など）が属するスコープ。その関数内でのみ参照可能です。
- **ブロックスコープ**: `if`文、`for`文、`switch`文などのブロック内で宣言された識別子が属するスコープ。そのブロック内でのみ参照可能です。

このコミットの文脈では、特に**関数スコープ**内での型定義の独立性が問題となっています。

### 型定義 (Type Definition)
Go言語では、`type`キーワードを使用して新しい型を定義できます。例えば、`type MyInt int`は`int`型のエイリアス`MyInt`を定義し、`type Person struct { Name string; Age int }`は構造体型`Person`を定義します。これらの型は、定義されたスコープ内で有効です。

### コンパイラの型チェック (Type Checking)
コンパイラの重要な役割の一つに型チェックがあります。これは、プログラムが型の規則に違反していないかを確認するプロセスです。型チェックは、プログラムの安全性と正確性を保証するために不可欠です。型定義の衝突は、型チェックの段階で検出されるエラーの一種です。

### `golden.out` ファイル
Goプロジェクトのテストスイートでは、特定のテストケースの期待される出力（コンパイルエラー、実行結果など）を`golden.out`のようなファイルに記録することがよくあります。これにより、コンパイラやランタイムの変更が既存のテストの期待される挙動を壊していないか（リグレッション）を自動的に検証できます。このコミットでは、バグが再現された際のコンパイラのエラーメッセージを`golden.out`に追記することで、このバグが修正された際に、このエラーメッセージが出力されなくなることを確認するための基準点としています。

## 技術的詳細

このコミットは、Goコンパイラの初期段階における型システムの実装上の課題を浮き彫りにしています。通常、関数内で定義されたローカルな型は、その関数スコープに限定され、他の関数スコープで同じ名前の型が定義されても、それらは完全に独立した別々の型として扱われるべきです。しかし、このバグ（bug167）の状況では、コンパイラが異なる関数スコープで定義された`T`という名前の構造体型を、内部的に`main.T·bug167`のような単一の識別子として扱ってしまい、結果として「conflicting definitions for main.T·bug167」というエラーを発生させていました。

これは、コンパイラのシンボルテーブル管理や型解決のメカニズムが、関数スコープ内の型定義に対して適切な名前マングリング（名前の衝突を避けるための内部的な名前変更）やスコープ分離を行っていなかったことを示唆しています。理想的には、`f1`内の`T`と`f2`内の`T`は、それぞれ`f1`のローカルな`T`と`f2`のローカルな`T`として区別され、互いに影響を与えないように処理されるべきです。

このコミットで追加された`test/bugs/bug167.go`は、この問題を再現するための最小限のコードを提供しています。
- `func f1()`内で`type T struct { x int }`を定義。
- `func f2()`内で`type T struct { x float }`を定義。
- `main()`関数で`f1()`と`f2()`を呼び出す。

このコードは、人間が読めば明らかに異なる型定義であり、それぞれが自身の関数スコープに限定されるべきです。しかし、当時のコンパイラはこれをエラーと判断していました。`test/golden.out`の更新は、このテストケースを実行した際に、コンパイラが「conflicting definitions」エラーを出力することを期待していることを示しており、バグの存在を明確にしています。

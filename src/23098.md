# [インデックス 23098] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における、並行マークフェーズ終了時のGCゴルーチンのウェイクアップメカニズムを改善するものです。具体的には、従来の`note`ベースのスリープ/ウェイクアップから、Goスケジューラが提供する`gopark`/`ready`スキームへの移行を行い、ウェイクアップのレイテンシを大幅に削減しています。

## コミット

Author: Austin Clements <austin@google.com>
Date:   Wed Apr 22 17:44:36 2015 -0400

    runtime: use park/ready to wake up GC at end of concurrent mark
    
    Currently, the main GC goroutine sleeps on a note during concurrent
    mark and the first background mark worker or assist to finish marking
    use wakes up that note to let the main goroutine proceed into mark
    termination. Unfortunately, the latency of this wakeup can be quite
    high, since the GC goroutine will typically have lost its P while in
    the futex sleep, meaning it will be placed on the global run queue and
    will wait there until some P is kind enough to pick it up. This delay
    gives the mutator more time to allocate and create floating garbage,
    growing the heap unnecessarily. Worse, it's likely that background
    marking has stopped at this point (unless GOMAXPROCS>4), so anything
    that's allocated and published to the heap during this window will
    have to be scanned during mark termination while the world is stopped.
    
    This change replaces the note sleep/wakeup with a gopark/ready
    scheme. This keeps the wakeup inside the Go scheduler and lets the
    garbage collector take advantage of the new scheduler semantics that
    run the ready()d goroutine immediately when the ready()ing goroutine
    sleeps.
    
    For the json benchmark from x/benchmarks with GOMAXPROCS=4, this
    reduces the delay in waking up the GC goroutine and entering mark
    termination once concurrent marking is done from ~100ms to typically
    <100µs.

## 元コミット内容

Goランタイムにおいて、並行マークフェーズの終了時にGCゴルーチンをウェイクアップするために、`park`/`ready`メカニズムを使用するように変更します。

現在、メインのGCゴルーチンは並行マーク中に`note`上でスリープし、最初のバックグラウンドマークワーカーまたはアシストがマークを完了すると、その`note`をウェイクアップしてメインゴルーチンがマーク終了フェーズに進むようにしています。残念ながら、このウェイクアップのレイテンシは非常に高くなる可能性があります。なぜなら、GCゴルーチンは`futex`スリープ中にP（プロセッサ）を失っているため、グローバルな実行キューに配置され、Pがそれをピックアップするまでそこで待機することになるからです。この遅延は、ミューテータ（アプリケーションコード）がより多くのメモリを割り当て、浮動ゴミ（floating garbage）を生成する時間を与え、不必要にヒープを肥大化させます。さらに悪いことに、この時点ではバックグラウンドマークが停止している可能性が高いため（GOMAXPROCS>4でない限り）、この期間中にヒープに割り当てられ公開されたものは、ワールドストップ（Stop The World: STW）中にマーク終了フェーズでスキャンされなければなりません。

この変更は、`note`によるスリープ/ウェイクアップを`gopark`/`ready`スキームに置き換えます。これにより、ウェイクアップがGoスケジューラ内部に留まり、ガベージコレクタは、`ready()`を呼び出したゴルーチンがスリープしたときに、`ready()`されたゴルーチンを即座に実行するという新しいスケジューラセマンティクスを利用できるようになります。

`x/benchmarks`の`json`ベンチマーク（GOMAXPROCS=4）において、この変更により、並行マーク完了後にGCゴルーチンをウェイクアップしてマーク終了フェーズに入るまでの遅延が、約100msから通常100µs未満に削減されます。

## 変更の背景

Goのガベージコレクションは、アプリケーションの実行と並行して動作する並行GCを採用しています。この並行GCの重要なフェーズの一つが「並行マーク」です。並行マークが完了すると、GCは次のフェーズである「マーク終了」に移行します。この移行の際に、メインのGCゴルーチンを効率的にウェイクアップすることが性能上の課題となっていました。

従来のメカニズムでは、メインGCゴルーチンは`note`という低レベルの同期プリミティブを使用してスリープしていました。`note`はOSの`futex`（Fast Userspace Mutex）のようなシステムコールに依存しており、ゴルーチンがスリープ状態に入ると、そのゴルーチンが割り当てられていたP（プロセッサ）を解放し、OSのスケジューラに制御を渡します。ウェイクアップが必要になった際、別のゴルーチンが`note`を通知しますが、スリープしていたGCゴルーチンはPを失っているため、すぐに実行される保証がありませんでした。OSの実行キューに置かれ、次にPが利用可能になるまで待機する必要がありました。

この待機時間は、特にGCの重要な移行点において、いくつかの問題を引き起こしていました。

1.  **ヒープの肥大化と浮動ゴミの増加**: GCゴルーチンがウェイクアップを待っている間も、アプリケーション（ミューテータ）は実行を続け、新しいオブジェクトを割り当てます。これらのオブジェクトは、並行マークフェーズではスキャンされなかったため、「浮動ゴミ」となる可能性があります。これは、GCが最終的に回収すべきメモリ量を増やし、ヒープサイズを不必要に大きくします。
2.  **STWフェーズへの影響**: 浮動ゴミが増えると、次の「マーク終了」フェーズで問題が生じます。マーク終了フェーズは「ワールドストップ」（STW）を伴うため、アプリケーションの実行が一時的に停止します。このSTW中に、ウェイクアップ遅延中に生成された浮動ゴミをスキャンする必要があり、STW時間が長くなる原因となります。STW時間はGoアプリケーションのレイテンシに直接影響するため、これを最小限に抑えることは非常に重要です。
3.  **バックグラウンドマークの停止**: GOMAXPROCSの値によっては、並行マークの終盤でバックグラウンドマークワーカーが停止している可能性があり、ウェイクアップの遅延がさらに問題となります。

これらの問題を解決し、GCの効率とアプリケーションのレイテンシを改善するために、より高速でGoスケジューラと密接に連携するウェイクアップメカニズムが必要とされました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する基本的な概念を理解しておく必要があります。

*   **ゴルーチン (Goroutine)**: Goの軽量な実行スレッドです。OSのスレッドよりもはるかに軽量で、数百万個を同時に実行することも可能です。Goスケジューラによって管理されます。
*   **P (Processor)**: Goスケジューラにおける論理プロセッサの抽象化です。PはOSスレッド（M）にアタッチされ、ゴルーチンを実行するためのコンテキストを提供します。G（ゴルーチン）はP上で実行されます。Pの数は通常、GOMAXPROCS環境変数によって制御されます。
*   **M (Machine/OS Thread)**: OSのスレッドです。PはM上で動作し、MがOSのCPUコア上で実際にゴルーチンを実行します。
*   **Goスケジューラ**: Goランタイムの重要なコンポーネントで、ゴルーチンをPに割り当て、実行を管理します。ゴルーチンの作成、実行、スリープ、ウェイクアップ、プリエンプションなどを担当します。
*   **ガベージコレクション (GC)**: 不要になったメモリを自動的に解放するプロセスです。GoのGCは並行（concurrent）かつ世代別（generational）ではありません。
*   **並行GC (Concurrent GC)**: アプリケーションの実行（ミューテータの動作）と並行してGCの大部分が実行される方式です。これにより、アプリケーションの一時停止時間を最小限に抑えます。
*   **並行マーク (Concurrent Mark)**: GCのフェーズの一つで、アプリケーションの実行と並行して、到達可能なオブジェクトをマーク（識別）します。
*   **マーク終了 (Mark Termination)**: 並行マークの後に続くGCフェーズです。このフェーズでは、GCが一時的にアプリケーションの実行を停止させ（STW）、マークフェーズで取りこぼしたオブジェクトの処理や、次のGCサイクルの準備などを行います。
*   **ワールドストップ (Stop The World: STW)**: GCの特定のフェーズ（主にマーク終了とスイープ準備）において、すべてのアプリケーションゴルーチンの実行を一時的に停止させることです。STW時間はアプリケーションのレイテンシに直接影響するため、最小限に抑えることがGC設計の重要な目標です。
*   **ミューテータ (Mutator)**: アプリケーションのコード、つまりヒープ上のオブジェクトの状態を変更（mutate）する部分を指します。
*   **浮動ゴミ (Floating Garbage)**: 並行マークフェーズ中にミューテータによって作成され、マークされなかったが、実際には到達不可能になったオブジェクトのことです。これらは次のGCサイクルで回収されるか、マーク終了フェーズで追加のスキャンが必要になります。
*   **`note`**: Goランタイム内部で使われる低レベルの同期プリミティブです。OSの`futex`（Fast Userspace Mutex）のようなシステムコールをラップしており、ゴルーチンをスリープさせたりウェイクアップさせたりするために使用されます。`note`でスリープすると、ゴルーチンはPを解放し、OSのスケジューラに依存してウェイクアップされます。
*   **`futex`**: Linuxカーネルが提供する「Fast Userspace Mutex」の略で、ユーザー空間のロックを効率的に実装するためのシステムコールです。競合がない場合はユーザー空間で完結し、競合が発生した場合のみカーネルに介入を求めます。
*   **`gopark`/`ready`**: Goスケジューラが提供するゴルーチンのスリープ/ウェイクアップメカニズムです。`gopark`は現在のゴルーチンをスリープさせ、Pを解放します。`ready`はスリープ中のゴルーチンを実行可能状態に戻します。このメカニズムはGoスケジューラ内部で完結するため、`note`や`futex`に比べてウェイクアップのレイテンシが低いという特徴があります。特に、`ready()`を呼び出したゴルーチンがスリープする際に、`ready()`されたゴルーチンを即座に実行するというセマンティクスが重要です。

## 技術的詳細

このコミットの核心は、GCゴルーチンのウェイクアップメカニズムを`note`から`gopark`/`ready`に切り替えることで、ウェイクアップのレイテンシを劇的に改善することにあります。

**従来の`note`ベースのウェイクアップの問題点**:
GCゴルーチンが`note`上でスリープすると、それはOSの`futex`システムコールに依存します。この際、GCゴルーチンは自身が実行されていたPを解放し、OSのスケジューラに制御を委ねます。ウェイクアップのシグナルが送られても、GCゴルーチンはOSのグローバルな実行キューに置かれ、次に利用可能なPがそれをピックアップするまで待機することになります。この待機時間は、OSのスケジューリングポリシーやシステム負荷によって変動し、最大で約100ミリ秒にも達することがありました。この遅延は、GCがマーク終了フェーズに移行するのを遅らせ、その間にミューテータが余分なメモリを割り当てて浮動ゴミを増やし、結果的にSTW時間の増加やヒープの肥大化を招いていました。

**`gopark`/`ready`スキームによる改善**:
`gopark`と`ready`は、Goスケジューラが直接管理するゴルーチンのスリープ/ウェイクアッププリミティブです。
*   `gopark`は、現在のゴルーチンをスリープ状態にし、Pを解放します。しかし、`note`と異なり、このスリープはGoスケジューラによって管理されます。
*   `ready`は、指定されたゴルーチンを実行可能状態（ready-to-run）にします。

このスキームの重要な利点は、Goスケジューラの新しいセマンティクスにあります。`ready()`を呼び出したゴルーチンが直後に`gopark()`などでスリープする場合、Goスケジューラは`ready()`されたゴルーチンを即座に実行しようとします。これは、Pが解放される直前に、そのP上でウェイクアップされたゴルーチンを実行する機会を与えることを意味します。これにより、ウェイクアップされたGCゴルーチンがグローバルな実行キューに置かれて待機する時間を大幅に短縮できます。

**具体的な改善効果**:
コミットメッセージによると、`x/benchmarks`の`json`ベンチマーク（GOMAXPROCS=4）において、GCゴルーチンのウェイクアップ遅延が約100msから100µs未満に削減されたと報告されています。これは約1000倍の改善であり、GCの効率とアプリケーションのレイテンシに大きなプラスの影響を与えます。特に、STW時間の短縮に寄与し、Goアプリケーションの応答性を向上させます。

**実装の詳細**:
変更点を見ると、`runtime/mgc.go`に`bgMarkWake`という新しい構造体が導入されています。これは、メインGCゴルーチンがスリープする際に自身のゴルーチンポインタを格納し、ウェイクアップのシグナルを受け取るためのロックとフラグを含んでいます。`gcBgMarkDone()`という新しい関数が追加され、バックグラウンドマークワーカーが完了した際にこの関数を呼び出し、メインGCゴルーチンを`ready()`状態にします。

## コアとなるコードの変更箇所

このコミットでは、主に`src/runtime/mgc.go`と`src/runtime/mgcmark.go`の2つのファイルが変更されています。

1.  **`src/runtime/mgc.go`**:
    *   `work`構造体に`bgMarkWake`という新しいフィールドが追加されました。これは、メインGCゴルーチンのウェイクアップを管理するための`mutex`、スリープするゴルーチンへのポインタ`*g`、およびウェイクアップフラグ`wake`を含みます。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更点

#### `work` 構造体への追加

```go
var work struct {
	// ... 既存のフィールド ...

	// Background mark completion signaling
	bgMarkWake struct {
		lock mutex
		g    *g
		wake bool
	}
}
```
`bgMarkWake`は、メインGCゴルーチン（`gc`関数を実行しているゴルーチン）が並行マークの完了を待機し、ウェイクアップされるための状態を管理します。
*   `lock mutex`: `bgMarkWake`構造体へのアクセスを保護するためのミューテックスです。複数のバックグラウンドワーカーやアシストが同時にウェイクアップを試みる可能性があるため、競合状態を防ぎます。
*   `g *g`: メインGCゴルーチンが`gopark`でスリープする際に、自身のゴルーチンポインタをここに格納します。これにより、ウェイクアップする側がどのゴルーチンを`ready`にするべきかを知ることができます。
*   `wake bool`: ウェイクアップシグナルが既に発生したかどうかを示すフラグです。メインGCゴルーチンが`gopark`する前にウェイクアップシグナルが来た場合（つまり、バックグラウンドワーカーが先に完了した場合）に、このフラグが`true`になります。

#### `gc` 関数内のウェイクアップロジックの変更

```go
func gc(mode int) {
	// ...
	// Wait for background mark completion.
	lock(&work.bgMarkWake.lock)
	if work.bgMarkWake.wake {
		// Wakeup already happened
		unlock(&work.bgMarkWake.lock)
	} else {
		work.bgMarkWake.g = getg() // 現在のゴルーチン（GCゴルーチン）を登録
		goparkunlock(&work.bgMarkWake.lock, "mark wait (idle)", traceEvGoBlock, 1) // ロックを解放してスリープ
	}
	work.bgMarkWake.wake = false
	work.bgMarkWake.g = nil
	// ...
}
```
この部分が、メインGCゴルーチンが並行マークの完了を待機する新しいメカニズムです。
1.  `lock(&work.bgMarkWake.lock)`: `bgMarkWake`構造体へのアクセスを保護するためにロックを取得します。
2.  `if work.bgMarkWake.wake`: もし、メインGCゴルーチンがスリープする前に、既にバックグラウンドワーカーが完了してウェイクアップシグナル（`wake = true`）を送っていた場合、GCゴルーチンはスリープする必要がないため、すぐにロックを解放して続行します。
3.  `else`: まだウェイクアップシグナルが来ていない場合、GCゴルーチンはスリープする必要があります。
    *   `work.bgMarkWake.g = getg()`: 現在実行中のゴルーチン（つまりメインGCゴルーチン自身）のポインタを`bgMarkWake.g`に保存します。これにより、ウェイクアップする側がこのゴルーチンを`ready`にできます。
    *   `goparkunlock(&work.bgMarkWake.lock, "mark wait (idle)", traceEvGoBlock, 1)`: この関数は、`work.bgMarkWake.lock`を解放し、現在のゴルーチンをスリープ状態にします。`gopark`はGoスケジューラにゴルーチンの実行を停止させ、Pを解放するように指示します。スリープの理由（"mark wait (idle)"）とトレースイベント（`traceEvGoBlock`）も指定されます。
4.  スリープからウェイクアップされた後、またはスリープせずに続行した場合、`work.bgMarkWake.wake = false`と`work.bgMarkWake.g = nil`で状態をリセットします。

#### `gcBgMarkDone()` 新規関数の追加

```go
func gcBgMarkDone() {
	if cas(&work.bgMarkDone, 0, 1) { // 最初の完了ワーカーのみが処理を行う
		// This is the first worker to reach completion.
		// Signal the main GC goroutine.
		lock(&work.bgMarkWake.lock)
		if work.bgMarkWake.g == nil {
			// It hasn't parked yet.
			work.bgMarkWake.wake = true // GCゴルーチンがまだスリープしていない場合、フラグを設定
		} else {
			ready(work.bgMarkWake.g, 0) // GCゴルーチンがスリープしている場合、readyにする
		}
		unlock(&work.bgMarkWake.lock)
	}
}
```
この関数は、バックグラウンドマークワーカーまたはアシストが並行マークの完了点に達したときに呼び出されます。
1.  `if cas(&work.bgMarkDone, 0, 1)`: `cas` (Compare And Swap) 操作を使用して、`work.bgMarkDone`が`0`（未完了）であれば`1`（完了）に設定します。これにより、複数のワーカーが同時に完了しても、最初のワーカーだけがウェイクアップ処理を実行するように保証されます。
2.  `lock(&work.bgMarkWake.lock)`: `bgMarkWake`構造体へのアクセスを保護するためにロックを取得します。
3.  `if work.bgMarkWake.g == nil`: メインGCゴルーチンがまだ`gopark`でスリープしていない場合（つまり、まだ`bgMarkWake.g`が設定されていない場合）、`work.bgMarkWake.wake = true`を設定します。これにより、GCゴルーチンが後で`gopark`しようとしたときに、すぐに続行できるようになります。
4.  `else`: メインGCゴルーチンが既に`gopark`でスリープしている場合（`bgMarkWake.g`が設定されている場合）、`ready(work.bgMarkWake.g, 0)`を呼び出して、そのゴルーチンを実行可能状態に戻します。Goスケジューラのセマンティクスにより、`ready()`を呼び出したゴルーチンがスリープする際に、`ready()`されたゴルーチンが即座に実行される可能性が高まります。
5.  `unlock(&work.bgMarkWake.lock)`: ロックを解放します。

### `src/runtime/mgcmark.go` の変更点

```go
func gcAssistAlloc(size uintptr, allowAssist bool) {
	// ...
	if xadd(&work.nwait, +1) == work.nproc && work.full == 0 && work.partial == 0 {
		// This has reached a background completion
		// point.
		gcBgMarkDone() // notewakeup(&work.bgMarkNote) の代わりに呼び出し
	}
	// ...
}
```
`gcAssistAlloc`関数は、ミューテータがメモリを割り当てる際にGCアシストを行う部分です。ここでも、GCアシストが並行マークの完了点に達した場合に、従来の`notewakeup`の代わりに新しく導入された`gcBgMarkDone()`を呼び出すように変更されています。これにより、アシストによるウェイクアップも`gopark`/`ready`スキームの恩恵を受けることができます。

これらの変更により、GCゴルーチンのウェイクアップがGoスケジューラ内部でより効率的に処理されるようになり、OSのスケジューリングに起因するレイテンシが大幅に削減されます。

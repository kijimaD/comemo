## 元コミット内容

このコミットは、Go言語のツールチェインにおいて、`new6g`などの新しいGoで実装されたコンパイラやアセンブラをビルドし、それらが既存のCで実装された`6g`などのツールと同じ出力を生成するかどうかを検証する機能を追加するものです。具体的には、`cmd/dist`と`cmd/go`の2つのモジュールに変更が加えられています。

## 変更の背景

このコミットは、Go 1.5リリースに向けた重要な取り組みの一環です。Go 1.5では、GoコンパイラとランタイムがC言語からGo言語自体で書き直されるという、いわゆる「セルフホスティング」が実現されました。これにより、GoのビルドにCコンパイラが不要となり、Go言語の独立性が高まりました。

しかし、この大規模な書き換えには、新しいGoで実装されたツール（`new6g`、`new5a`など）が、これまで使われてきたCで実装されたツール（`6g`、`5a`など）と完全に互換性があり、同じバイナリ出力を生成することを保証する必要がありました。このコミットは、その互換性と正確性を検証するためのメカニズムを導入することで、セルフホスティングへの移行を安全に進めることを目的としています。新しいツールが既存のツールと異なる出力を生成した場合、それはバグとして検出され、修正されるべき問題となります。

## 前提知識の解説

*   **Goツールチェイン**: Go言語のプログラムを開発・ビルドするために必要な一連のツール群を指します。これには、コンパイラ（`go tool compile`）、アセンブラ（`go tool asm`）、リンカ（`go tool link`）などが含まれます。
*   **`6g`, `8g`, `5a`, `6a`など**: Go 1.5以前のGoツールチェインでは、各アーキテクチャ（例: `amd64`は`6`、`386`は`8`、`arm`は`5`）ごとにC言語で実装された個別のコンパイラやアセンブラが存在しました。`6g`は`amd64`アーキテクチャ用のコンパイラ、`5a`は`arm`アーキテクチャ用のアセンブラを指します。
*   **`new6g`, `new5a`など**: Go 1.5でGo言語自体で書き直された新しいコンパイラやアセンブラを指します。これらは、従来のC実装のツールを置き換えることを目的としています。
*   **ブートストラップ (Bootstrap)**: あるプログラミング言語のコンパイラやツールチェインを、その言語自体で記述すること、またはそのプロセスを指します。Go 1.5のセルフホスティングは、Go言語がGo言語自身をコンパイルできるようになったことを意味します。ブートストラップの過程では、古いバージョンのコンパイラを使って新しいバージョンのコンパイラをビルドし、その新しいコンパイラでさらに新しいコンパイラをビルドするといった段階的なプロセスが踏まれることがあります。
*   **`cmd/dist`**: GoのソースコードからGoツールチェイン全体をビルドするためのコマンドです。ブートストラッププロセスにおいて重要な役割を担います。
*   **`cmd/go`**: Goコマンドラインツールの中核であり、Goプログラムのビルド、テスト、実行、パッケージ管理など、開発者が日常的に使用するほとんどの操作を統括します。コンパイラやアセンブラの呼び出しも`cmd/go`を通じて行われます。
*   **`go-review.googlesource.com`**: Goプロジェクトの公式コードレビューシステムです。Goの変更はすべてここを通じてレビューされ、承認されてからメインリポジトリにマージされます。

## 技術的詳細

このコミットは、主に以下の2つのファイルに影響を与えています。

1.  **`src/cmd/dist/buildtool.go`**:
    *   このファイルは、Goツールチェインのブートストラップビルドプロセスにおいて、どのディレクトリをビルド対象とするかを定義する`bootstrapDirs`変数を含んでいます。
    *   変更点として、`bootstrapDirs`リストの順序が整理され、特に`new5g`, `new6g`, `new8g`, `new9g`といった新しいGoで実装されたコンパイラ関連のディレクトリが明示的に追加されています。これは、これらの新しいコンパイラがGoツールチェインのビルドプロセスの一部として確実にビルドされるようにするためです。

2.  **`src/cmd/go/build.go`**:
    *   このファイルは、`go build`コマンドの内部的なビルドロジックを定義しています。
    *   **`verifyCompiler`定数の導入**:
        ```go
        // verifyCompiler specifies whether to check the compilers written in Go
        // against the assemblers written in C. If set, asm will run both (say) 6g and new6g
        // and fail if the two produce different output files.
        const verifyCompiler = true
        ```
        `verifyCompiler`というブール型の定数が`true`に設定されています。これは、Goで書かれた新しいコンパイラやアセンブラが、Cで書かれた既存のツールと同じ出力を生成するかどうかを検証する機能を有効にするためのフラグです。
    *   **`gc`関数と`asm`関数の変更**:
        *   `gc`関数（Goコンパイラを呼び出す部分）と`asm`関数（アセンブラを呼び出す部分）において、コンパイルまたはアセンブルが成功した後、`verifyCompiler`が`true`の場合に`toolVerify`関数が呼び出されるようになりました。
        *   これにより、通常のビルドプロセスに加えて、新しいツール（`new*g`や`new*a`）を使って同じソースコードをコンパイル/アセンブルし、その出力が既存のツール（`*g`や`*a`）の出力と一致するかどうかがチェックされます。
    *   **`asmVerify`から`toolVerify`へのリファクタリングと機能拡張**:
        *   既存の`asmVerify`関数が`toolVerify`というより汎用的な名前に変更され、その機能が拡張されました。
        *   `toolVerify`関数は、指定された`newTool`（新しいコンパイラまたはアセンブラ）が、元のツールと同じコマンドライン引数で実行された場合に、同じ出力ファイルを生成するかどうかを検証します。
        *   具体的には、元のツールが生成した出力ファイルと、新しいツールが生成した出力ファイル（一時的に`.new`サフィックスが付加される）の内容をバイト単位で比較します。
        *   もし両者の内容が一致しない場合、エラーを返し、どのツールがどのコマンドライン引数で実行され、異なる出力を生成したかを詳細に報告します。これにより、新しいツールにおける互換性の問題やバグを特定しやすくなります。
        *   エラーメッセージのフォーマットも改善され、`filepath.Base(args[1].(string))`を使用して元のツールのベース名（例: `6g`）を表示するように変更されています。
    *   **`args`の型変更**: `gc`関数内で、`args`変数の初期化が`stringList(...)`から`[]interface{}{...}`に変更され、`b.runOut`や`b.run`への引数渡しが`args...`（可変長引数）を使用するように変更されています。これは、`toolVerify`関数がより柔軟な引数を受け取れるようにするための準備と考えられます。

## コアとなるコードの解説

### `src/cmd/dist/buildtool.go`の変更

*   `bootstrapDirs`の変更は、Goツールチェインのビルドシステムに対して、`new5g`, `new6g`, `new8g`, `new9g`といった新しいGoで実装されたコンパイラが、ブートストラッププロセスの一部としてビルドされるべきであることを明示的に指示しています。これにより、Go 1.5のセルフホスティングへの移行が円滑に進むよう、これらの新しいツールがGoのビルド環境に組み込まれます。

### `src/cmd/go/build.go`の変更

*   **`verifyCompiler`定数**: この定数を`true`に設定することで、Goツールチェインのビルド時に、新旧のコンパイラ/アセンブラの出力比較検証が有効になります。これは、新しいGo実装のツールが既存のC実装のツールと完全に互換性があることを保証するための重要な安全策です。
*   **`gc`関数と`asm`関数における`toolVerify`の呼び出し**:
    *   `gc`関数では、Goソースコードのコンパイル後、`new` + `archChar` + `g`（例: `new6g`）という新しいGoコンパイラを使って再度コンパイルし、元のコンパイラ（例: `6g`）の出力と比較します。
    *   `asm`関数では、アセンブリコードのアセンブル後、`new` + `archChar` + `a`（例: `new6a`）という新しいGoアセンブラを使って再度アセンブルし、元のC実装のアセンブラ（例: `6a`または`asm`）の出力と比較します。
    *   この検証は、ビルドプロセスの一部として自動的に実行されるため、開発者が手動で互換性をチェックする手間を省き、問題が早期に発見されることを保証します。
*   **`asmVerify`から`toolVerify`へのリファクタリングと機能拡張**:
    *   関数名を`asmVerify`から`toolVerify`に変更することで、アセンブラだけでなく、コンパイラを含む任意のツール間の出力比較に再利用できる汎用的な検証関数になりました。
    *   この関数は、元のツールと新しいツールが同じ入力に対して同じバイナリ出力を生成するかどうかをバイト単位で厳密に比較します。
    *   出力が異なる場合、詳細なエラーメッセージを生成し、どのツールがどのコマンドライン引数で実行されたか、そして出力がなぜ異なるのかを特定するのに役立つ情報を提供します。これは、新しいGo実装のツールが既存のツールと完全に一致する動作をすることを保証するための、非常に強力なデバッグおよび検証メカニズムです。
    *   `args`の型が`stringList`から`[]interface{}`に変更されたのは、`toolVerify`関数がより多様な引数型を扱えるようにするための柔軟性の向上です。

これらの変更は、Go 1.5のセルフホスティングという大きなマイルストーンを達成する上で、新しいツールチェインの信頼性と安定性を確保するために不可欠なものでした。

# [インデックス 19888] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるワークバッファの管理を最適化するものです。具体的には、GCワーカーが使用するワークバッファをスレッドローカルストレージ（`MCache`）に1つキャッシュすることで、共有のロックフリースタック（`lfstack`）へのアクセス頻度を減らし、GCのパフォーマンスを向上させます。

## 元コミット内容

Goランタイムにおいて、ガベージコレクション（GC）のワークバッファをスレッドローカルストレージに1つキャッシュするように変更します。

`scanblock`関数は、スタックフレームの引数やローカル変数領域など、多くの小さなルートピースに対して頻繁に呼び出されます。`scanblock`が呼び出されるたびに、`getempty`および`putempty`関数が呼び出され、これらはすべてのワーカーゴルーチン間で共有されるロックフリースタックにアクセスします。

この変更により、1要素のスレッドローカルキャッシュを導入することで、ほとんどの`scanblock`呼び出しが共有スタックにアクセスすることなく処理できるようになります。

## 変更の背景

Goのガベージコレクタは、並行マーク・スイープ方式を採用しており、アプリケーションの実行と並行してGC処理を進めることで、ストップ・ザ・ワールド（STW）時間を最小限に抑えています。GCのマークフェーズでは、到達可能なオブジェクトを特定し、それらを「ワークバッファ」と呼ばれる一時的なキューに入れて処理します。

`scanblock`関数は、GCがメモリブロック（ヒープ上のオブジェクトやゴルーチンのスタックなど）をスキャンし、ポインタを見つけてマークする際に使用される重要な低レベル関数です。特に、スタックフレームの引数やローカル変数といった小さなメモリ領域をスキャンする際に頻繁に呼び出されます。

従来のGoランタイムでは、`scanblock`がワークバッファを必要とするたびに、`getempty`関数を呼び出して空のワークバッファを取得し、処理が完了すると`putempty`関数を呼び出してワークバッファを共有のロックフリースタック（`work.empty`）に戻していました。このロックフリースタックは、すべてのGCワーカーゴルーチン間で共有されており、複数のゴルーチンが同時にアクセスするため、アトミック操作による同期が必要となります。

`scanblock`が非常に頻繁に呼び出される性質上、`getempty`/`putempty`を通じた共有ロックフリースタックへの頻繁なアクセスは、GCワーカー間の競合を引き起こし、パフォーマンスのボトルネックとなる可能性がありました。特に、小さなメモリ領域の走査が多数発生する場合、このオーバーヘッドは無視できません。

このコミットの目的は、この競合を緩和し、GCの効率を向上させることです。各GCワーカーが自身の`MCache`（スレッドローカルキャッシュ）内に1つのワークバッファをキャッシュすることで、ほとんどの`scanblock`呼び出しにおいて共有スタックへのアクセスを回避できるようになります。これにより、アトミック操作の回数が減り、GCの全体的なスループットが向上し、レイテンシが削減されることが期待されます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびガベージコレクションに関する概念を理解しておく必要があります。

1.  **Goのガベージコレクション (GC)**:
    *   GoのGCは、並行（Concurrent）、非世代別（Non-generational）、三色マーク・スイープ（Tri-color Mark-and-Sweep）方式を採用しています。
    *   **並行性**: GCの大部分（特にマークフェーズ）は、アプリケーションの実行と並行して動作します。これにより、アプリケーションの停止時間（STW）を最小限に抑えます。
    *   **三色マーキング**: オブジェクトは「白」（未訪問、回収候補）、「灰」（到達可能だが子をスキャンしていない）、「黒」（完全にスキャン済み）のいずれかの色でマークされます。
    *   **ワークバッファ (Work Buffer)**: GCのマークフェーズ中に、到達可能と判断されたオブジェクト（灰色になったオブジェクト）は、`workbuf`と呼ばれるバッファに格納されます。GCワーカーゴルーチンはこれらのバッファからオブジェクトを取り出し、そのポインタをスキャンして子オブジェクトをマークします。`workbuf`は、`empty`（利用可能なバッファ）と`full`（処理待ちのオブジェクトを含むバッファ）のリストで管理されます。

2.  **`scanblock`関数**:
    *   GoランタイムのGCにおいて、特定のメモリブロックをスキャンしてポインタを識別するための低レベル関数です。
    *   メモリブロックの開始アドレス、長さ、および`ptrmask`（ポインタのビットマップ）を引数として取ります。`ptrmask`は、ブロック内のどのオフセットにポインタが含まれているかを正確に示します。
    *   `scanblock`は、見つかったポインタが指すライブオブジェクトをワークバッファに追加し、GCがさらに処理できるようにします。ヒープオブジェクトだけでなく、ゴルーチンのスタック（`scanstack`）のスキャンにも使用されます。

3.  **`lfstack` (Lock-Free Stack)**:
    *   Goランタイムに実装されているロックフリースタックデータ構造です。
    *   複数のゴルーチンがミューテックス（ロック）を必要とせずに要素をプッシュ・ポップできるため、高い並行環境での競合を回避し、パフォーマンスを向上させます。
    *   アトミック操作（例: `atomic.Cas64`）を使用してスレッドセーフティを確保します。
    *   GCの文脈では、`workbuf`の`work.full`および`work.empty`リストの管理に`lfstack`が使用され、GCワーカーが効率的にワークバッファを取得・解放できるようにしています。

4.  **`MCache` (mcache)**:
    *   Goランタイムのメモリ割り当て器が使用する、プロセッサ（P）ごとのスレッドローカルキャッシュです。
    *   各論理プロセッサ（P）は独自の`mcache`を持ちます。これにより、小さなオブジェクトの割り当て時にロックの必要性を大幅に減らし、競合を回避します。
    *   `mcache`は、さまざまなサイズクラスの`mspan`（メモリのスパン）を格納します。ゴルーチンが小さなオブジェクトを割り当てる必要がある場合、まず自身の`mcache`から割り当てを試みます。
    *   `mcache`はGC管理外のメモリから割り当てられるため、それ自体はGCの対象ではありません。

これらのコンポーネントが連携して、Goの効率的な並行ガベージコレクションとメモリ管理を実現しています。

## 技術的詳細

このコミットの技術的詳細は、主に`MCache`構造体への新しいフィールドの追加と、ワークバッファの取得・解放ロジック（`getempty`、`putempty`）の変更に集約されます。

1.  **`MCache`構造体への`gcworkbuf`フィールドの追加**:
    *   `src/pkg/runtime/malloc.h`において、`MCache`構造体に`void* gcworkbuf;`という新しいフィールドが追加されました。
    *   このフィールドは、各`MCache`（つまり、各Pに紐づくローカルキャッシュ）がGCワークバッファを1つだけ保持するためのポインタとして機能します。これにより、GCワーカーは共有の`lfstack`にアクセスする前に、まず自身のローカルキャッシュを確認できるようになります。

2.  **`getempty`関数の変更**:
    *   `src/pkg/runtime/mgc0.c`内の`getempty`関数は、空のワークバッファを取得する役割を担っています。
    *   変更前は、まず引数`b`が`nil`でなければ`work.full`スタックにプッシュし、その後すぐに`work.empty`スタックからワークバッファをポップしようとしていました。
    *   変更後、`getempty`は以下のロジックで動作します:
        *   まず、現在のゴルーチンが実行されているM（OSスレッド）に紐づく`MCache`（`g->m->mcache`）を取得します。
        *   `c->gcworkbuf`が`nil`でない場合、つまりローカルキャッシュにワークバッファが格納されている場合、そのバッファを`b`に設定し、`c->gcworkbuf`を`nil`にクリアします。これにより、ローカルキャッシュからワークバッファが取得されます。
        *   ローカルキャッシュが空の場合（`b`がまだ`nil`の場合）、従来のロジック通り`work.empty`共有スタックからワークバッファをポップします。
        *   共有スタックも空の場合、新しいワークバッファを`runtime·persistentalloc`で割り当てます。
    *   この変更により、ほとんどの`getempty`呼び出しは、共有スタックへのアトミック操作を伴うアクセスを回避し、高速なローカルキャッシュアクセスで完結するようになります。

3.  **`putempty`関数の変更**:
    *   `src/pkg/runtime/mgc0.c`内の`putempty`関数は、使用済みのワークバッファを空きリストに戻す役割を担っています。
    *   変更前は、常に`work.empty`共有スタックにワークバッファをプッシュしていました。
    *   変更後、`putempty`は以下のロジックで動作します:
        *   現在のゴルーチンが実行されているMに紐づく`MCache`を取得します。
        *   `c->gcworkbuf`が`nil`の場合、つまりローカルキャッシュが空の場合、引数`b`で渡されたワークバッファを`c->gcworkbuf`に格納し、関数を終了します。これにより、ワークバッファがローカルキャッシュにキャッシュされます。
        *   ローカルキャッシュが既にワークバッファを保持している場合（`c->gcworkbuf`が`nil`でない場合）、従来のロジック通り`work.empty`共有スタックにワークバッファをプッシュします。
    *   この変更により、ワークバッファがローカルキャッシュに格納されることで、共有スタックへのプッシュ操作が削減されます。

4.  **`gcworkbuffree`関数の追加と`freemcache`の変更**:
    *   `src/pkg/runtime/malloc.h`に`void runtime·gcworkbuffree(void *b);`という新しい関数プロトタイプが追加されました。
    *   `src/pkg/runtime/mgc0.c`に`runtime·gcworkbuffree`関数の実装が追加されました。この関数は、引数として受け取ったワークバッファが`nil`でなければ`putempty`を呼び出して空きリストに戻します。
    *   `src/pkg/runtime/mcache.c`内の`freemcache`関数が変更され、`MCache`が解放される際に、その`MCache`が保持していた`gcworkbuf`も`runtime·gcworkbuffree`を呼び出して適切に解放されるようになりました。これにより、`MCache`が破棄される際に、キャッシュされていたワークバッファがリークすることなく共有の空きリストに戻されることが保証されます。

これらの変更により、GCワーカーはワークバッファの取得と解放の際に、まず自身のローカルキャッシュを優先的に利用するようになります。これにより、共有のロックフリースタックへのアクセスが大幅に減少し、GCワーカー間の競合が緩和され、GCの全体的な効率とパフォーマンスが向上します。

## コアとなるコードの変更箇所

このコミットによるコードの変更は、主に以下の3つのファイルにわたります。

1.  **`src/pkg/runtime/malloc.h`**:
    *   `MCache`構造体に`gcworkbuf`という新しいフィールドが追加されました。
    *   `runtime·gcworkbuffree`関数のプロトタイプが追加されました。

2.  **`src/pkg/runtime/mcache.c`**:
    *   `freemcache`関数が変更され、`MCache`が解放される際に、その`MCache`が保持していた`gcworkbuf`も`runtime·gcworkbuffree`を呼び出して解放するようになりました。

3.  **`src/pkg/runtime/mgc0.c`**:
    *   `getempty`関数が変更され、`MCache`の`gcworkbuf`を優先的に利用するロジックが追加されました。
    *   `putempty`関数が変更され、ワークバッファを`MCache`の`gcworkbuf`にキャッシュするロジックが追加されました。
    *   `runtime·gcworkbuffree`関数の実装が追加されました。

*   **`getempty`関数の変更**:
    *   `MCache *c;`が追加され、現在のM（OSスレッド）に紐づく`MCache`へのポインタ`c = g->m->mcache;`を取得します。
    *   `if(c->gcworkbuf != nil)`ブロックが追加されました。これは、まずローカルキャッシュ`c->gcworkbuf`にワークバッファがあるかどうかを確認します。もしあれば、それを`b`に設定し、ローカルキャッシュをクリア（`c->gcworkbuf = nil;`）します。これにより、共有スタックにアクセスすることなくワークバッファを取得できます。
    *   `if(b == nil)`ブロックが変更され、ローカルキャッシュから取得できなかった場合にのみ、従来の`runtime·lfstackpop(&work.empty);`を呼び出して共有の空きスタックからワークバッファを取得するようになりました。
    *   このロジックにより、ほとんどのワークバッファ取得要求は、共有スタックへの競合の多いアクセスではなく、高速なローカルキャッシュアクセスで満たされるようになります。

*   **`putempty`関数の変更**:
    *   `MCache *c;`が追加され、現在のMに紐づく`MCache`へのポインタ`c = g->m->mcache;`を取得します。
    *   `if(c->gcworkbuf == nil)`ブロックが追加されました。これは、ローカルキャッシュ`c->gcworkbuf`が空の場合、引数`b`で渡されたワークバッファをローカルキャッシュに格納し、関数を終了します。
    *   ローカルキャッシュが既にワークバッファを保持している場合（`c->gcworkbuf`が`nil`でない場合）にのみ、従来の`runtime·lfstackpush(&work.empty, &b->node);`を呼び出して共有の空きスタックにワークバッファをプッシュします。
    *   このロジックにより、ワークバッファの解放時にも、まずローカルキャッシュへの格納が試みられ、共有スタックへのプッシュ操作が削減されます。

*   **`runtime·gcworkbuffree`関数の追加**:
    *   `void runtime·gcworkbuffree(void *b)`関数の実装が追加されました。
    *   この関数は、引数`b`が`nil`でなければ、`putempty(b);`を呼び出してワークバッファを空きリスト（ローカルキャッシュまたは共有スタック）に戻します。これは、`MCache`が解放される際に、その`MCache`が保持していたワークバッファを適切に処理するために使用されます。

これらの変更は、GoのGCにおけるワークバッファの管理をより効率的にし、特に`scanblock`のような頻繁に呼び出される関数からの共有リソースへのアクセス競合を減らすことで、GCのパフォーマンスを向上させることを目的としています。

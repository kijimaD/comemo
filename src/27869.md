# [インデックス 27869] ファイルの概要

このコミットは、Goランタイムのメモリスカベンジャーが、物理ページサイズがGoの論理ページサイズよりも大きいアーキテクチャ（ARM64, PPC64x, MIPS64など）で正しく動作しない問題を修正します。具体的には、メモリをOSに解放する際に、解放領域の境界を物理ページサイズに合わせて内側に丸めることで、意図しないメモリの解放を防ぎます。

## コミット

```
runtime: scavenge memory on physical page-aligned boundaries

Currently the scavenger marks memory unused in multiples of the
allocator page size (8K). This is safe as long as the true physical
page size is 4K (or 8K), as it is on many platforms. However, on
ARM64, PPC64x, and MIPS64, the physical page size is larger than 8K,
so if we attempt to mark memory unused, the kernel will round the
boundaries of the region *out* to all pages covered by the requested
region, and we'll release a larger region of memory than intended. As
a result, the scavenger is currently disabled on these platforms.

Fix this by first rounding the region to be marked unused *in* to
multiples of the physical page size, so that when we ask the kernel to
mark it unused, it releases exactly the requested region.

Fixes #9993.

Change-Id: I96d5fdc2f77f9d69abadcea29bcfe55e68288cb1
Reviewed-on: https://go-review.googlesource.com/22066
Reviewed-by: Rick Hudson <rlh@golang.org>
```

## 変更の背景

Goランタイムには、ヒープ上で不要になったメモリをオペレーティングシステム（OS）に返却する「スカベンジャー（scavenger）」と呼ばれる機能があります。これにより、Goアプリケーションのメモリフットプリント（Resident Set Size: RSS）を削減し、システム全体のメモリ効率を向上させることができます。

従来のスカベンジャーは、Goランタイムが内部的に管理する論理ページサイズ（通常8KB）の倍数でメモリを未使用としてマークしていました。これは、多くのプラットフォームで物理ページサイズが4KBまたは8KBである限り、問題なく機能していました。

しかし、ARM64、PPC64x、MIPS64などの一部のアーキテクチャでは、物理ページサイズが8KBよりも大きい場合があります（例えば、64KB）。このような環境で、Goランタイムが論理ページサイズに基づいてメモリ領域をOSに解放しようとすると、問題が発生しました。OSのカーネルは、`madvise`のようなシステムコールを通じてメモリの解放要求を受け取った際、指定された領域の境界を物理ページサイズに合わせて「外側」に丸める（アラインメントする）傾向があります。

この「外側への丸め込み」が発生すると、Goランタイムが意図したよりも広いメモリ領域がOSに解放されてしまう可能性がありました。これにより、まだGoランタイムが使用している可能性のある隣接するメモリページが誤って解放され、ヒープの破損や予期せぬクラッシュを引き起こすリスクがありました。この問題を回避するため、これらの特定のプラットフォームでは、スカベンジャー機能自体が一時的に無効化されていました（`golang.org/issue/9993`）。

このコミットは、この問題を解決し、これらのプラットフォームでもスカベンジャーが安全に動作するようにすることを目的としています。

## 前提知識の解説

このコミットの理解には、以下の概念が不可欠です。

1.  **Goランタイムのメモリ管理 (mheap, mspan)**:
    *   Goランタイムは、独自のメモリマネージャを持ち、OSから大きなメモリブロック（アリーナ）を確保し、それを細かく分割してアプリケーションに提供します。
    *   **mheap**: Goランタイムのヒープ全体を管理する構造体です。
    *   **mspan**: 連続したGoの論理ページ（通常8KB）のブロックを指します。オブジェクトはmspanから割り当てられます。mspanは、Goランタイムがメモリを管理する際の基本的な単位の一つです。
    *   **_PageSize**: Goランタイムが内部的に使用する論理ページサイズ（8KB）です。`_PageShift`は、このページサイズをバイト数に変換するためのシフト量（`1 << _PageShift == _PageSize`）です。

2.  **メモリスカベンジャー**:
    *   Goのガベージコレクタ（GC）が不要なオブジェクトを回収した後、ヒープ上には空きmspanが生成されます。
    *   スカベンジャーは、これらの空きmspanの中から、一定期間使用されていないものを探し出し、その物理メモリをOSに返却する役割を担います。これにより、GoプロセスのRSSを削減します。
    *   メモリをOSに返却する際には、`sysUnused`という内部関数が呼び出され、これがOSの`madvise`システムコール（Linuxの場合）などを利用して、指定されたメモリ領域が不要であることをカーネルに伝えます。

3.  **論理ページサイズと物理ページサイズ**:
    *   **論理ページサイズ (`_PageSize`)**: Goランタイムが内部的にメモリを管理する際の単位です。Go 1.6の時点では8KBでした。
    *   **物理ページサイズ (`sys.PhysPageSize`)**: OSがハードウェアと連携してメモリを管理する際の最小単位です。これはCPUアーキテクチャやOSの設定によって異なり、一般的なx86-64システムでは4KBですが、ARM64、PPC64x、MIPS64などでは64KBやそれ以上になることがあります。

4.  **`madvise`システムコール**:
    *   `madvise`は、プロセスがメモリ領域をどのように使用するつもりであるかについて、カーネルに助言を与えるためのシステムコールです。
    *   `MADV_DONTNEED`や`MADV_FREE`などのフラグを使用して、指定されたメモリ領域がもう必要ないことをカーネルに伝えます。カーネルは、この助言に基づいて、物理メモリを解放したり、スワップアウトしたりするなどの最適化を行います。
    *   重要なのは、`madvise`が操作するメモリ領域は、OSの物理ページサイズにアラインメントされている必要があるという点です。指定された領域が物理ページサイズにアラインメントされていない場合、カーネルは自動的にその領域を物理ページ境界に合わせて拡張（外側に丸める）して処理することがあります。これが、本コミットで修正される問題の根源でした。

5.  **メモリ領域の「内側への丸め込み」と「外側への丸め込み」**:
    *   **外側への丸め込み (rounding *out*)**: 指定されたメモリ領域が物理ページ境界に収まらない場合、その領域を物理ページ境界に合わせて拡張すること。例えば、`[10KB, 70KB]`の領域を64KB物理ページで解放しようとすると、カーネルは`[0KB, 128KB]`のように拡張して解放してしまう可能性があります。
    *   **内側への丸め込み (rounding *in*)**: 指定されたメモリ領域が物理ページ境界に収まらない場合、その領域を物理ページ境界に合わせて縮小すること。例えば、`[10KB, 70KB]`の領域を64KB物理ページで解放しようとする場合、`[64KB, 64KB]`（つまり64KBの1ページ）のように、完全に物理ページ境界内に収まる最大の領域のみを対象とします。

## 技術的詳細

このコミットの核心は、スカベンジャーがメモリをOSに返却する際に、`madvise`システムコールに渡すメモリ領域の開始アドレスと長さを、OSの物理ページサイズに厳密にアラインメントされたものに調整することです。

以前の実装では、`sys.PhysPageSize > _PageSize`（物理ページサイズがGoの論理ページサイズより大きい場合）という条件でスカベンジャー全体を無効にしていました。これは、カーネルが意図しないメモリを解放するリスクを避けるための安全策でした。

新しい実装では、この無効化のチェックを削除し、代わりに以下のロジックを導入します。

1.  **解放対象領域の計算**: まず、mspanが管理するメモリ領域の開始アドレス (`start`) と終了アドレス (`end`) を、Goの論理ページサイズに基づいて計算します。
    *   `start := uintptr(s.start) << _PageShift`
    *   `end := start + s.npages<<_PageShift`

2.  **物理ページサイズによるアラインメント**: `sys.PhysPageSize > _PageSize` の場合にのみ、この`start`と`end`を物理ページサイズに合わせて「内側」に丸めます。
    *   `start = (start + sys.PhysPageSize - 1) &^ (sys.PhysPageSize - 1)`: これは`start`アドレスを次の物理ページ境界に切り上げる（アラインメントする）操作です。例えば、`start`が64KB物理ページ境界の途中にある場合、次の64KB境界に調整されます。
    *   `end &^= sys.PhysPageSize - 1`: これは`end`アドレスを前の物理ページ境界に切り下げる（アラインメントする）操作です。例えば、`end`が64KB物理ページ境界の途中にある場合、前の64KB境界に調整されます。

3.  **領域の有効性チェック**: アラインメントの結果、`start`が`end`以上になってしまった場合（つまり、物理ページ境界に収まる有効な領域がなくなった場合）、そのmspanからのメモリ解放はスキップされます。
    *   `if start == end { continue }`

4.  **解放する長さの再計算**: 新しくアラインメントされた`start`と`end`に基づいて、実際に解放するメモリの長さ (`len`) を計算します。
    *   `len := end - start`

5.  **解放済みページ数の更新**: `s.npreleased`（既に解放済みとしてマークされたページ数）を、新しい`len`に基づいて更新します。
    *   `s.npreleased = len >> _PageShift`

6.  **OSへの解放要求**: 最後に、アラインメントされた`start`アドレスと`len`を使用して`sysUnused`を呼び出し、OSにメモリの解放を要求します。
    *   `sysUnused(unsafe.Pointer(start), len)`

この変更により、カーネルが`madvise`を処理する際に、Goランタイムが意図した正確な物理ページ領域のみが解放されるようになります。これにより、物理ページサイズが大きいプラットフォームでも、スカベンジャーが安全かつ効率的に動作するようになります。

## コアとなるコードの解説

変更された`scavengelist`関数内の主要なコードブロックを解説します。

1.  **旧来の無効化ロジックの削除**:
    ```diff
    -	if sys.PhysPageSize > _PageSize {
    -		// golang.org/issue/9993
    -		// If the physical page size of the machine is larger than
    -		// our logical heap page size the kernel may round up the
    -		// amount to be freed to its page size and corrupt the heap
    -		// pages surrounding the unused block.
    -		return 0
    -	}
    ```
    この部分が削除されました。これにより、物理ページサイズがGoの論理ページサイズより大きいプラットフォームでも、スカベンジャーが動作するようになります。

2.  **メモリ領域の開始と終了アドレスの計算**:
    ```go
    			start := uintptr(s.start) << _PageShift
    			end := start + s.npages<<_PageShift
    ```
    `s.start`はmspanの開始論理ページ番号であり、`_PageShift`を左シフトすることでバイトアドレスに変換されます。`s.npages`はmspanに含まれる論理ページ数です。これにより、mspanがカバーするメモリ領域のバイト単位での開始アドレスと終了アドレスが計算されます。

3.  **物理ページサイズによるアラインメント処理**:
    ```go
    			if sys.PhysPageSize > _PageSize {
    				// We can only release pages in
    				// PhysPageSize blocks, so round start
    				// and end in. (Otherwise, madvise
    				// will round them *out* and release
    				// more memory than we want.)
    				start = (start + sys.PhysPageSize - 1) &^ (sys.PhysPageSize - 1)
    				end &^= sys.PhysPageSize - 1
    				if start == end {
    					continue
    				}
    			}
    ```
    *   `if sys.PhysPageSize > _PageSize`: このアラインメント処理は、物理ページサイズがGoの論理ページサイズよりも大きい場合にのみ適用されます。
    *   `start = (start + sys.PhysPageSize - 1) &^ (sys.PhysPageSize - 1)`:
        *   `sys.PhysPageSize - 1`: 物理ページサイズから1を引いた値（例: 64KBの場合、`0xFFFF`）。これは、物理ページサイズの倍数ではないビットをマスクするために使用されます。
        *   `start + sys.PhysPageSize - 1`: `start`アドレスを物理ページサイズの倍数に切り上げるための準備です。
        *   `&^ (sys.PhysPageSize - 1)`: ビットAND NOT演算子です。`sys.PhysPageSize - 1`のビットが立っている部分をクリアすることで、`start`アドレスを物理ページサイズの次の倍数に切り上げます。これにより、`start`は物理ページ境界に「切り上げ」られます。
    *   `end &^= sys.PhysPageSize - 1`:
        *   これは`end`アドレスを物理ページサイズの前の倍数に切り下げる操作です。`sys.PhysPageSize - 1`のビットが立っている部分をクリアすることで、`end`アドレスを物理ページサイズの直前の倍数に切り下げます。
    *   `if start == end { continue }`: `start`が`end`以上になった場合、アラインメントの結果、有効な解放領域がなくなったことを意味するため、このmspanの処理をスキップします。

4.  **解放する長さの計算と更新**:
    ```go
    			len := end - start
    
    			released := len - (s.npreleased << _PageShift)
    			if sys.PhysPageSize > _PageSize && released == 0 {
    				continue
    			}
    			memstats.heap_released += uint64(released)
    			sumreleased += released
    -			s.npreleased = s.npages
    +			s.npreleased = len >> _PageShift
    -			sysUnused(unsafe.Pointer(s.start<<_PageShift), s.npages<<_PageShift)
    +			sysUnused(unsafe.Pointer(start), len)
    ```
    *   `len := end - start`: アラインメントされた`start`と`end`から、実際に解放されるバイト長を計算します。
    *   `released := len - (s.npreleased << _PageShift)`: 既に解放済みとしてマークされているバイト数を差し引いて、今回新たに解放されるバイト数を計算します。
    *   `if sys.PhysPageSize > _PageSize && released == 0 { continue }`: 物理ページサイズが大きい環境で、かつ新たに解放されるメモリがない場合もスキップします。
    *   `memstats.heap_released += uint64(released)` と `sumreleased += released`: 解放されたメモリの統計情報を更新します。
    *   `s.npreleased = len >> _PageShift`: `s.npreleased`を、今回実際に解放されたバイト長を論理ページ数に変換した値で更新します。これにより、次にスカベンジャーがこのmspanを処理する際に、既に解放された部分を考慮できるようになります。
    *   `sysUnused(unsafe.Pointer(start), len)`: 最終的に、アラインメントされた`start`アドレスと`len`を`sysUnused`に渡し、OSにメモリの解放を要求します。

この一連の変更により、Goランタイムは、OSの物理ページアラインメント要件を尊重しつつ、正確に意図したメモリ領域のみを解放できるようになり、スカベンジャーの信頼性と移植性が向上しました。

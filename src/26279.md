## 変更の背景

このコミットは、GoコンパイラのSSAバックエンドがまだ開発途上であった時期に、将来的な性能向上と最適化の機会を特定するために行われました。SSA形式は、コンパイラ最適化の強力な基盤を提供しますが、その潜在能力を最大限に引き出すためには、様々なケースに対する具体的な最適化戦略を考案し、実装する必要があります。

このTODOリストの追加は、Goコンパイラチームが継続的にコンパイラの出力品質（生成される機械語コードの効率性）を改善しようとしている努力の一環です。特に、以下の点に焦点を当てています。

1.  **コードサイズの削減と実行速度の向上**: 特定の共通パターン（例: ゼロの代入）に対するより効率的な機械語命令の生成。
2.  **SSAの適用範囲の拡大**: 構造体やインターフェースといった複雑なデータ型をSSA形式でより効果的に扱う方法の模索。これにより、これらの型に対する最適化の機会が増加します。
3.  **レジスタ利用の最適化**: 特定のデータ型（文字列、インターフェース）をXMMレジスタのような特殊なレジスタで渡すことで、関数呼び出しのオーバーヘッドを削減し、データ転送を高速化する可能性の検討。
4.  **ブーリアンロジックの効率化**: 条件分岐やブーリアン演算に関連する機械語命令シーケンスの簡素化。

これらのTODO項目は、Goプログラムの実行時性能をさらに向上させるためのロードマップの一部として機能します。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において非常に重要な中間表現 (IR) の一つです。SSA形式では、各変数がただ一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、以下のような高度な最適化を容易に行うことができます。

*   **共通部分式除去 (Common Subexpression Elimination, CSE)**: 同じ計算が複数回行われている場合、一度だけ計算して結果を再利用する。
*   **定数伝播 (Constant Propagation)**: 定数値を追跡し、可能な場所で定数に置き換える。
*   **デッドコード除去 (Dead Code Elimination, DCE)**: 決して実行されない、またはその結果が使用されないコードを削除する。
*   **レジスタ割り当て (Register Allocation)**: 変数を効率的にCPUレジスタに割り当てる。

Goコンパイラは、ソースコードを抽象構文木 (AST) に変換した後、SSA形式に変換し、様々な最適化パスを適用してから最終的な機械語コードを生成します。

### 2. Goコンパイラの構造

Goコンパイラ (`cmd/compile`) は、フロントエンド、ミドルエンド、バックエンドの主要な部分に分けられます。

*   **フロントエンド**: ソースコードの字句解析、構文解析、抽象構文木 (AST) の構築、型チェックなどを行います。
*   **ミドルエンド**: ASTをSSA形式に変換し、SSAベースの最適化（上記のような）を適用します。このコミットのTODOは主にこの部分に関連します。
*   **バックエンド**: 最適化されたSSA形式からターゲットアーキテクチャ（x86-64, ARMなど）の機械語コードを生成し、レジスタ割り当てや命令スケジューリングを行います。

### 3. CPUレジスタと命令

*   **汎用レジスタ (General Purpose Registers)**: `AX` (x86-64では`RAX`) など、整数演算やアドレス計算に広く使われるレジスタ。
*   **XMMレジスタ (XMM Registers)**: SSE/AVX命令セットで使用される128ビットまたは256ビットのレジスタで、主に浮動小数点演算やSIMD (Single Instruction, Multiple Data) 演算に用いられます。大きなデータを効率的に扱うことができます。
*   **機械語命令**:
    *   `MOVQ`: 64ビットのデータを移動する命令。
    *   `CMP`: 比較命令。
    *   `JEQ`/`JNE`: 条件付きジャンプ命令 (Equal/Not Equal)。
    *   `MOVB`: 8ビットのデータを移動する命令。
    *   `XORB`: 8ビットのXOR演算命令。
    *   `TESTB`: 8ビットのビットテスト命令。

### 4. Write Barrier (ライトバリア)

Goのガベージコレクション (GC) は、並行マーク＆スイープ方式を採用しています。ライトバリアは、GCがオブジェクトグラフを走査している最中に、プログラムがポインタを書き換える際に挿入される特別なコードです。これにより、GCがオブジェクトを見落とすことを防ぎ、正確なGCを実現します。ライトバリアのオーバーヘッドはGC性能に直結するため、その効率化は重要な最適化ポイントです。

### 5. Goのデータ型表現

*   **文字列 (string)**: Goの文字列は、内部的にはポインタと長さのペアとして表現されます。
*   **インターフェース (interface)**: インターフェースは、内部的には型情報 (`_type`) と値 (`data`) のペアとして表現されます。値がポインタ型の場合はポインタが、それ以外の場合は値そのものが格納されます。
*   **構造体 (struct)**: 複数のフィールドを持つ複合型。

## 技術的詳細

追加されたTODO項目は、GoコンパイラのSSAバックエンドにおける具体的な最適化の方向性を示しています。

1.  **`If there are a lot of MOVQ $0, ..., then load 0 into a register and use the register as the source instead.`**
    *   **現状**: 多くの場所で定数 `0` をメモリに書き込む (`MOVQ $0, ...`) 際に、毎回リテラル `0` を命令に埋め込んでいる可能性があります。
    *   **最適化の提案**: もし `0` を頻繁に使うのであれば、一度 `0` をCPUレジスタ（例: `RAX`）にロードし、そのレジスタをソースオペランドとして使用する (`MOVQ RAX, ...`)。
    *   **メリット**: 命令のエンコーディングサイズが小さくなる可能性があります（リテラル値の代わりにレジスタ番号を使用するため）。また、CPUによってはレジスタからのデータ転送の方が即値からの転送よりも効率的である場合があります。これは特に、命令キャッシュの効率向上に寄与する可能性があります。

2.  **`Allow structs (and arrays of length 1?) to be SSAable.`**
    *   **現状**: GoコンパイラのSSA形式では、すべての変数がSSA形式で表現されるわけではありません。特に、大きな構造体や配列は、メモリ上のエンティティとして扱われ、SSA形式の恩恵を受けにくい場合があります。
    *   **最適化の提案**: 構造体や長さ1の配列のような、比較的小さな複合型をSSA形式で扱えるようにする。
    *   **メリット**: これらの型に対するデータフロー解析が容易になり、より多くの最適化（例: デッドストア除去、共通部分式除去）が適用可能になります。これにより、不要なメモリロード/ストア命令を削減し、レジスタ利用を最適化できる可能性があります。

3.  **`Figure out how to make PARAMOUT variables ssa-able. They need to get spilled automatically at end-of-function somehow.`**
    *   **`PARAMOUT` 変数**: Goの関数呼び出し規約において、呼び出し元に結果を返すための引数（戻り値）が格納されるメモリ領域を指します。これらは関数が終了する際に、呼び出し元がアクセスできるようにメモリに「スピル」（書き出し）される必要があります。
    *   **最適化の提案**: `PARAMOUT` 変数もSSA形式で扱えるようにする。
    *   **課題**: SSA形式は通常、レジスタに格納される値を最適化するのに適していますが、`PARAMOUT` 変数は最終的にメモリに書き出される必要があります。SSA形式で最適化しつつ、関数の終わりに自動的に正しいメモリ位置にスピルされるメカニズムを考案する必要があります。
    *   **メリット**: 戻り値の計算と格納に関する最適化の機会が増え、不要な中間的なメモリ操作を削減できる可能性があります。

4.  **`If strings are being passed around without being interpreted (ptr and len feilds being accessed) pass them in xmm registers? Same for interfaces?`**
    *   **現状**: Goの文字列やインターフェースは、通常、スタックまたは汎用レジスタを通じて渡されます。これらは内部的にポインタと長さ（文字列）または型と値（インターフェース）のペアであり、それぞれ64ビットの2つの値で構成されます（64ビットアーキテクチャの場合）。
    *   **最適化の提案**: 文字列やインターフェースがその内容（ポインタや長さ、型や値）を個別に解釈されることなく、単一の「値」として受け渡される場合、XMMレジスタ（128ビット）を使用して渡すことを検討する。
    *   **メリット**: 128ビットのXMMレジスタは、2つの64ビット値を一度に保持できるため、文字列やインターフェースのペアを単一のレジスタで効率的に渡すことができます。これにより、スタックへのプッシュ/ポップや複数の汎用レジスタの使用を避け、関数呼び出しのオーバーヘッドを削減し、データ転送を高速化できる可能性があります。ただし、ABI (Application Binary Interface) の変更や、XMMレジスタが浮動小数点演算に主に使われることによる潜在的な競合を考慮する必要があります。

5.  **`boolean logic: movb/xorb$1/testb/jeq -> movb/testb/jne`**
    *   **現状**: ブーリアン値の反転と条件分岐を含むロジックが、`movb` (バイト移動), `xorb $1` (1とのXORでビット反転), `testb` (ビットテスト), `jeq` (等しい場合にジャンプ) のシーケンスで実装されている可能性があります。
    *   **最適化の提案**: このシーケンスを `movb` (バイト移動), `testb` (ビットテスト), `jne` (等しくない場合にジャンプ) に簡素化する。
    *   **詳細**:
        *   `movb/xorb$1/testb/jeq`: `xorb $1` はブーリアン値を反転させます（0を1に、1を0に）。その後 `testb` でフラグを設定し、`jeq` で元の値が0だった場合（反転後1）にジャンプします。
        *   `movb/testb/jne`: ブーリアン値が0か1であると仮定すると、`testb` 命令は値が0かどうかを直接テストできます。もし値が0でなければ（つまり真であれば）、`jne` でジャンプできます。これにより、`xorb $1` 命令が不要になり、命令数が削減されます。
    *   **メリット**: 命令数の削減により、コードサイズが小さくなり、実行サイクルが減少するため、性能が向上します。

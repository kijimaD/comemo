# [インデックス 26932] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおいて、特定の最適化手法である `duffcopy` および `duffzero` 関数がPlan 9オペレーティングシステム上で使用されないように変更するものです。これは、Plan 9の特定の制約、特にノートハンドラ内での浮動小数点演算の禁止に起因する問題を解決するために行われました。

## 元コミット内容

```
cmd/compile: don't use duffcopy and duffzero on Plan 9

The ssa compiler uses the duffcopy and duffzero functions,
which rely on the MOVUPS instructions.

However, this doesn't work on Plan 9, since floating point
operations are not allowed in the note handler.

This change disables the use of duffcopy and duffzero
on Plan 9 in the ssa compiler.

Updates #14605.
```

## 変更の背景

GoコンパイラのSSAバックエンドは、メモリのコピー（`duffcopy`）やゼロクリア（`duffzero`）の際に、パフォーマンス最適化のために「Duff's Device」と呼ばれるテクニックを利用しています。このテクニックは、通常、アセンブリレベルで `MOVUPS` (Move Unaligned Packed Single-precision Floating-point) 命令などのSIMD (Single Instruction, Multiple Data) 命令を活用して、一度に複数のデータを処理することで高速化を図ります。

しかし、Plan 9オペレーティングシステムでは、特定のシステムコールや例外処理（「ノートハンドラ」と呼ばれる）のコンテキスト内で浮動小数点演算を行うことが許可されていません。`MOVUPS` 命令は、その名前が示す通り浮動小数点レジスタを使用する可能性があり、Plan 9のノートハンドラ内で実行されると問題を引き起こす可能性があります。

この問題は、GoのIssue #14605で報告されており、Plan 9上でのGoプログラムの安定性と正確性を確保するために、`duffcopy` と `duffzero` の使用を無効にする必要がありました。

## 前提知識の解説

### GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを機械語に変換する過程で、複数のステージを経ます。その一つがSSA (Static Single Assignment) 形式への変換と、それに基づく最適化です。SSA形式は、各変数が一度だけ代入されるようにプログラムを表現する中間表現であり、データフロー解析や最適化を容易にします。SSAバックエンドは、このSSA形式のコードをターゲットアーキテクチャの機械語に変換する役割を担います。この過程で、メモリ操作の最適化も行われます。

### Duff's Device (ダフのデバイス)

Duff's Deviceは、C言語のプログラマであるTom Duffが考案した、ループアンローリングを効率的に実装するテクニックです。特に、メモリのコピーや初期化など、繰り返し同じ操作を行う場合に、ループのオーバーヘッドを削減し、パフォーマンスを向上させるために使用されます。アセンブリ言語レベルでは、ジャンプテーブルや特定の命令（例えば、x86-64アーキテクチャにおけるSIMD命令）と組み合わせて実装されることが多いです。これにより、コンパイラはより効率的なコードを生成できます。

### MOVUPS 命令

`MOVUPS` (Move Unaligned Packed Single-precision Floating-point) は、x86-64アーキテクチャのSSE (Streaming SIMD Extensions) 命令セットの一部です。この命令は、メモリとXMMレジスタ（SIMD演算に使用される128ビットレジスタ）間で、アラインメントされていない単精度浮動小数点数データを転送するために使用されます。`duffcopy` のようなメモリ操作の最適化において、一度に大量のデータを効率的に移動させるために利用されることがあります。

### Plan 9オペレーティングシステム

Plan 9 from Bell Labsは、ベル研究所で開発された分散オペレーティングシステムです。Unixの設計思想をさらに推し進め、すべてのリソースをファイルとして表現し、ネットワーク透過性を重視しています。Plan 9は、その独特な設計思想とミニマリストなアプローチで知られていますが、一般的なOSとは異なるシステムコールや例外処理のメカニズムを持っています。

### Plan 9のノートハンドラ

Plan 9における「ノートハンドラ (note handler)」は、Unixにおけるシグナルハンドラに似たメカニズムです。プロセスが特定のイベント（例えば、エラーや外部からの通知）を受け取った際に、登録されたノートハンドラが実行されます。このハンドラは、通常、非常に限られた環境で動作し、特定の操作（特に浮動小数点演算）が制限されることがあります。これは、ハンドラの実行中にシステムの整合性を保つため、あるいはコンテキストスイッチの複雑さを軽減するための設計上の選択です。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドが、Plan 9上で `duffcopy` および `duffzero` を使用しないようにするための条件分岐を追加することです。

1.  **`Config` 構造体の変更**: `src/cmd/compile/internal/ssa/config.go` に `noDuffDevice bool` という新しいフィールドが追加されました。このフィールドは、Duff's Deviceを使用すべきでない場合に `true` に設定されます。
2.  **`NewConfig` 関数での設定**: `NewConfig` 関数内で、現在のオペレーティングシステムが "plan9" であるかどうかを `obj.Getgoos()` でチェックします。もし "plan9" であれば、新しく追加された `noDuffDevice` フィールドを `true` に設定します。
3.  **SSAルールの変更**: `src/cmd/compile/internal/ssa/gen/AMD64.rules` および `src/cmd/compile/internal/ssa/rewriteAMD64.go` にある、`Move` および `Zero` 操作を `DUFFCOPY` や `DUFFZERO` に書き換えるルールに、`!config.noDuffDevice` という条件が追加されました。これにより、`noDuffDevice` が `true` の場合（つまりPlan 9の場合）、これらのDuff's Deviceを利用した最適化は適用されなくなります。
    *   具体的には、中規模のコピー (`size >= 32 && size <= 16*64 && size%16 == 0`) やゼロクリア (`size <= 1024 && size%8 == 0 && size%16 != 0` または `size <= 1024 && size%16 == 0`) の際に `DUFFCOPY` や `DUFFZERO` を使用する条件に `&& !config.noDuffDevice` が追加されています。
    *   大規模なコピー (`size > 16*64`) やゼロクリア (`size > 1024`) の場合、通常は `REPMOVSQ` や `REPSTOSQ` といった命令が使用されますが、Plan 9でDuff's Deviceが使えない場合は、より小さいサイズでもこれらの汎用的な命令にフォールバックするように条件が変更されています (`(size > 16*64 || config.noDuffDevice)` や `(size > 1024 || (config.noDuffDevice && size > 32))`)。これは、Duff's Deviceが使えない場合に、中規模の最適化パスをスキップし、より安全なREP命令に直接移行させるための措置です。

この変更により、Plan 9上でのGoコンパイラは、ノートハンドラ内での浮動小数点演算の制約に違反することなく、メモリ操作を正しく処理できるようになります。

## コアとなるコードの解説

### `config.go` の変更

`Config` 構造体に `noDuffDevice bool` フィールドが追加されたことで、コンパイラの設定においてDuff's Deviceの使用可否を制御できるようになりました。`NewConfig` 関数内で `obj.Getgoos() == "plan9"` のチェックが追加され、Plan 9環境であれば `noDuffDevice` が `true` に設定されます。これにより、コンパイラのSSAバックエンド全体でPlan 9特有の制約を考慮した挙動が可能になります。

### `AMD64.rules` および `rewriteAMD64.go` の変更

これらのファイルは、GoコンパイラのSSAバックエンドにおける最適化ルールを定義しています。`AMD64.rules` はルール定義ファイルであり、`rewriteAMD64.go` はそのルールに基づいてSSA値を書き換えるGoコードです。

変更のポイントは、`Move` (メモリコピー) および `Zero` (メモリゼロクリア) 操作を `DUFFCOPY` や `DUFFZERO` といったDuff's Deviceを利用したアセンブリ命令に変換する条件に、`!config.noDuffDevice` が追加されたことです。

*   **中規模のメモリ操作**: `size >= 32 && size <= 16*64 && size%16 == 0` のような条件で `DUFFCOPY` や `DUFFZERO` が適用される箇所に `&& !config.noDuffDevice` が追加されました。これにより、Plan 9ではこれらの最適化がスキップされます。
*   **大規模なメモリ操作**: `size > 16*64` や `size > 1024` のような条件で `REPMOVSQ` (繰り返し文字列移動) や `REPSTOSQ` (繰り返しストア) といった命令が適用される箇所では、条件が `(size > 16*64 || config.noDuffDevice)` や `(size > 1024 || (config.noDuffDevice && size > 32))` のように変更されました。これは、Plan 9でDuff's Deviceが使えない場合、中規模の最適化パスを迂回し、より汎用的なREP命令に直接フォールバックさせるためのロジックです。`size > 32` という追加条件は、非常に小さいサイズの場合はREP命令もオーバーヘッドが大きいため、Duff's Deviceが使えない場合でも、より単純なループや個別のMOV命令で処理されることを意図している可能性があります。

これらの変更により、Plan 9環境下では、`MOVUPS` 命令に依存するDuff's Deviceの最適化が回避され、Plan 9のノートハンドラの制約に準拠した安全なコードが生成されるようになります。

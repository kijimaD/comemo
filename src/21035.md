# [インデックス 21035] ファイルの概要

このコミットは、Goランタイムの`cgo`（CgoはGoプログラムがCコードを呼び出すことを可能にするツール）関連ファイルにビルドタグを追加するものです。具体的には、特定のオペレーティングシステム（DragonFly BSD, FreeBSD, NetBSD, OpenBSD）に特化したCソースファイルが、意図せずすべてのOS向けにビルドされてしまう問題を修正し、Go 1.3のビルド動作を復元することを目的としています。

## 元コミット内容

`runtime/cgo: add +build tags to files named for $GOOS`

このコミットは、`$GOOS`（GoのターゲットOSを示す環境変数）にちなんで名付けられたファイルに`+build`タグを追加します。これらのファイルは、すべてのオペレーティングシステム向けに`runtime/cgo`にビルドされてしまっていましたが、それは問題ないように見えても、Go 1.3の動作を復元するために修正されます。

## 変更の背景

Goのビルドシステムでは、特定のファイルが特定の環境（OSやアーキテクチャなど）でのみコンパイルされるように制御するために「ビルドタグ（build tags）」を使用します。コミットメッセージによると、`src/runtime/cgo`ディレクトリ内の、特定のOS名（例: `dragonfly.c`, `freebsd.c`など）がファイル名に含まれるCソースファイルが、本来そのOS向けにのみビルドされるべきであるにもかかわらず、すべてのOS向けにビルドされてしまっていたようです。

これは、ビルドタグが適切に設定されていなかったか、あるいはビルドシステムの変更によって、これらのファイルが意図せず広範囲に含められるようになってしまったためと考えられます。コミットメッセージの「It doesn't seem to matter, but restore the Go 1.3 behavior anyway.」という記述から、この問題が直接的なバグを引き起こしていたわけではないものの、Go 1.3時点での本来のビルド動作（つまり、OS固有のファイルはそのOS向けにのみビルドされる）に戻すことが望ましいと判断されたことが伺えます。これは、ビルドの正確性、不要なコードのコンパイル回避、および将来的な潜在的な問題の予防のためと考えられます。

## 前提知識の解説

### Goのビルドタグ（Build Tags / Build Constraints）

Go言語には、ソースファイルを条件付きでビルドに含めるか除外するかを制御するための「ビルドタグ」という仕組みがあります。これは、クロスプラットフォーム開発において、特定のOSやアーキテクチャに依存するコードを管理する際に非常に重要です。

*   **構文**: ビルドタグは、Goソースファイル（`.go`）やC/C++ソースファイル（`.c`, `.s`など）の先頭にコメントとして記述されます。このコミットが作成された2014年時点では、`// +build tag_name`という形式が使われていました。このコメント行の直後には空行が必要です。
*   **動作**: `go build`コマンドが実行される際、ビルドタグが評価され、現在のビルド環境（`GOOS`, `GOARCH`など）と一致するタグを持つファイルのみがコンパイル対象となります。例えば、`// +build linux`と書かれたファイルはLinux環境でのみビルドされ、他のOSでは無視されます。
*   **目的**:
    *   **プラットフォーム固有のコード**: OSやアーキテクチャに特化したAPI呼び出しや実装を分離する。
    *   **機能の有効/無効化**: 特定の機能を持つバージョンと持たないバージョンを同じソースコードベースからビルドする。
    *   **テストの分離**: 特定のテストスイート（例: インテグレーションテスト）を通常の単体テストから分離する。

### Cgo

Cgoは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoのツールです。GoとCの間の橋渡し役として機能し、異なる言語間の相互運用性を可能にします。

*   **利用方法**: Goのソースファイル内で`import "C"`と記述することでCgoの使用を宣言します。Cのコードは、この`import "C"`の直前のコメントブロック内に直接記述するか、外部のCソースファイルとして提供できます。
*   **ビルドプロセス**: `go build`コマンドは、`import "C"`を見つけるとCgoツールを起動します。Cgoは埋め込まれたCコードや参照されるCファイルを抽出し、外部のCコンパイラ（GCCなど）を使用してコンパイルします。その後、コンパイルされたCオブジェクトファイルはGoのコンパイル済みコードとリンクされ、単一の実行可能ファイルが生成されます。
*   **ランタイムとの連携**: Cgo呼び出しは、GoランタイムとCランタイムの間でコンテキストスイッチを伴います。これには、スタックの切り替え、ゴルーチンのOSスレッドへの固定（Cコードが実行中にゴルーチンが別のスレッドに移動しないようにするため）、およびポインタの安全な受け渡しに関する厳格なルールが含まれます。これらのオーバーヘッドのため、Cgo呼び出しは純粋なGoの関数呼び出しよりもコストが高くなります。
*   **メモリ管理**: GoのガベージコレクタはGoが管理するメモリのみを扱います。Cgoを通じてC側で`malloc`などで確保されたメモリはGoのGCの管理外であり、開発者が明示的に`free`などで解放する必要があります。

### Go 1.3のCgoの挙動

Go 1.3では、Cgoの動作にいくつかの重要な変更が導入されました。これには、不完全な構造体型のより正確な処理、クロスコンパイルのサポートの改善、Objective-Cファイルの処理能力の追加などが含まれます。このコミットメッセージにある「restore the Go 1.3 behavior anyway」という記述は、Go 1.3で確立されたCgo関連のビルドロジックやファイル処理の慣習が、何らかの理由で失われたか、あるいは変更されてしまった状態を指している可能性が高いです。このコミットは、その「本来の」挙動、つまりOS固有のCgo関連ファイルが適切にビルドタグによって制御される状態に戻すことを意図しています。

## 技術的詳細

このコミットの技術的な核心は、Goのビルドシステムがどのようにソースファイルを処理し、特定のプラットフォーム向けにコンパイルするかという点にあります。

Goのビルドシステムは、ソースファイルのファイル名や内容を解析して、そのファイルがどのビルドに含められるべきかを決定します。特に、`src/runtime/cgo`のようなGoランタイムの低レベル部分では、OS固有のCコードが多数存在します。これらのCコードは、各OSのシステムコールや特定のAPIと連携するために必要です。

コミット前の状態では、`dragonfly.c`, `freebsd.c`, `netbsd.c`, `openbsd.c`といったファイルが、それぞれのOS名がファイル名に含まれているにもかかわらず、ビルドタグがないために、GoのビルドシステムによってすべてのOS向けにコンパイルされてしまっていたと考えられます。これは、Goのビルドシステムがファイル名に基づいて自動的にビルドタグを推測するような賢い挙動をしないか、あるいはその推測ロジックがこのケースでは適用されなかったことを示唆しています。

このコミットでは、各Cソースファイルの先頭に明示的に`// +build <os_name>`というビルドタグを追加することで、この問題を解決しています。例えば、`dragonfly.c`には`// +build dragonfly`が、`freebsd.c`には`// +build freebsd`が追加されます。これにより、Goのビルドシステムはこれらのファイルを正しく認識し、対応するOS環境でのみコンパイル対象とします。

この変更は、ビルドの効率性（不要なファイルのコンパイルを避ける）、バイナリサイズの最適化（不要なオブジェクトコードを含めない）、およびビルドの正確性（特定のOSにのみ関連するコードが他のOSで誤ってリンクされることを防ぐ）に寄与します。また、Go 1.3の挙動を「復元」するということは、Goのビルドシステムが進化する中で、過去のバージョンで意図されていたファイル処理のセマンティクスが失われていた可能性を示唆しており、このコミットはその整合性を回復するものです。

## コアとなるコードの変更箇所

このコミットでは、以下の4つのファイルにそれぞれ2行ずつ変更が加えられています。

1.  `src/runtime/cgo/dragonfly.c`
2.  `src/runtime/cgo/freebsd.c`
3.  `src/runtime/cgo/netbsd.c`
4.  `src/runtime/cgo/openbsd.c`

各ファイルにおいて、既存のコメント行の後に、対応するOSのビルドタグが追加されています。

**例: `src/runtime/cgo/dragonfly.c` の変更**

```diff
--- a/src/runtime/cgo/dragonfly.c
+++ b/src/runtime/cgo/dragonfly.c
@@ -2,6 +2,8 @@
 // Use of this source code is governed by a BSD-style
 // license that can be found in the LICENSE file.
 
+// +build dragonfly
+
 #include "textflag.h"
 
 // Supply environ and __progname, because we don't
```

同様に、他のファイルも以下のタグが追加されています。

*   `src/runtime/cgo/freebsd.c`: `// +build freebsd`
*   `src/runtime/cgo/netbsd.c`: `// +build netbsd`
*   `src/runtime/cgo/openbsd.c`: `// +build openbsd`

## コアとなるコードの解説

追加されたコードは非常にシンプルで、各Cソースファイルの先頭にGoのビルドタグコメントを追加するものです。

`// +build <os_name>`

この行は、Goのビルドシステムに対する指示であり、このファイルがどのオペレーティングシステム向けにコンパイルされるべきかを明示的に指定します。

*   `//`: Goのコメントシンタックス。
*   `+build`: ビルドタグであることを示す特別なプレフィックス。
*   `<os_name>`: ターゲットとなるオペレーティングシステムの名前（例: `dragonfly`, `freebsd`, `netbsd`, `openbsd`）。

このタグが存在することで、`go build`コマンドは、例えばLinux環境でビルドを行う際には`dragonfly.c`や`freebsd.c`などをコンパイル対象から除外します。これにより、ビルドの正確性が保たれ、不要なプラットフォーム固有のコードが他の環境のバイナリに含まれることがなくなります。

この変更は、Goのビルドシステムがファイル名だけでなく、明示的なビルドタグを優先してファイルの含める/含めないを決定するという原則を再確認するものです。コミットメッセージが示唆するように、ビルドタグがない状態でも「問題ないように見えても」という記述は、ビルドシステムがファイル名からある程度の推測を行っていた可能性、あるいは、これらのファイルがCgoの特性上、他のOSのビルドに誤って含まれてもリンクエラーなどにはならなかったが、それは意図しない挙動であったことを示しています。このコミットは、その意図しない挙動を修正し、Go 1.3で確立されたビルドのセマンティクスに合わせるためのものです。

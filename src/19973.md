# [インデックス 19973] ファイルの概要

このコミットは、Go言語のリンカー（`liblink`）の内部ファイルである `src/liblink/objfile.c` に加えられた変更を扱っています。`objfile.c` は、Goのコンパイルプロセスにおいて、オブジェクトファイルやシンボル情報を処理し、最終的な実行可能ファイルを生成するリンカーの中核部分を担っています。具体的には、シンボルの読み込み、再配置情報の処理、デバッグ出力の生成などに関わっています。

## コミット

このコミットは、Go言語のリンカー（`liblink`）におけるいくつかの改善を目的としています。主な変更点は以下の通りです。

1.  **`$i64.` シンボルのハンドリング**: リンカーが `$i64.` という形式のシンボルを正しく処理できるように拡張されました。これは、64ビット整数定数を表す内部的なシンボル形式です。
2.  **デバッグ出力の強化**: リンカーのデバッグフラグ `-S -v` が有効な場合に、オブジェクトコードの処理に関する詳細なデバッグ情報が出力されるようになりました。
3.  **RISCアーキテクチャにおける再配置加算値の16進数表示**: RISCアーキテクチャ（具体的にはPowerPC 64ビットなど）において、再配置エントリの加算値（addend）が10進数ではなく16進数で表示されるように変更されました。これにより、デバッグ時の可読性が向上します。

## 変更の背景

このコミットは、Go言語のリンカーの内部的な改善とデバッグ能力の向上を目的としています。

1.  **`$i64.` シンボルの必要性**: Goコンパイラやリンカーの内部では、特定の定数値をシンボルとして表現することがあります。以前は `$f64.` (64ビット浮動小数点数) のハンドリングは存在しましたが、64ビット整数定数を表す `$i64.` シンボルが導入され、これをリンカーが正しく認識し処理する必要が生じました。これは、特に特定のアーキテクチャや最適化の文脈で、64ビット整数定数を効率的に埋め込むために重要となります。
2.  **デバッグの効率化**: Goのリンカーは複雑な処理を行うため、問題発生時のデバッグが困難な場合があります。`-S` (アセンブリ出力) と `-v` (詳細出力) フラグを組み合わせた際に、オブジェクトコードの処理パスに関するより詳細なデバッグ情報を出力することで、リンカーの挙動を追跡し、問題を特定する作業が容易になります。
3.  **RISCアーキテクチャのデバッグ体験向上**: 再配置加算値は、シンボルの最終アドレスを計算する上で重要な要素です。特にRISCアーキテクチャでは、メモリアドレスの配置やアライメントが厳密であるため、再配置加算値の正確な値（特に16進数表現）を直接確認できることが、低レベルのデバッグや最適化において非常に役立ちます。10進数よりも16進数の方が、ビットパターンやアドレスオフセットを直感的に理解しやすいため、デバッグ時の可読性が向上します。`[dev.power64]` というプレフィックスから、PowerPC 64ビットアーキテクチャにおける開発とデバッグの文脈でこの変更が行われたことが示唆されます。

## 前提知識の解説

### Go言語のリンカー (`liblink` / `cmd/link`)

Go言語のビルドプロセスにおいて、コンパイラが生成したオブジェクトファイル群を結合し、実行可能なバイナリを生成する役割を担うのがリンカーです。Goのリンカーは `cmd/link` として実装されており、このコミットで変更されている `src/liblink/objfile.c` はその内部コンポーネントの一つです。Goはデフォルトで静的リンクを行うため、実行ファイルにはGoランタイムや依存するライブラリのコードがすべて含まれます。

リンカーの主な機能は以下の通りです。
*   **オブジェクトファイルの読み込み**: コンパイラが生成した `.o` ファイルを読み込みます。
*   **シンボル解決**: 関数名、変数名などのシンボルを解決し、それらがメモリ上のどこに配置されるかを決定します。
*   **再配置 (Relocation)**: オブジェクトファイル内のコードやデータが、最終的な実行ファイル内で正しいメモリアドレスを参照するように、アドレス参照を修正します。
*   **デバッグ情報の生成**: DWARFなどのデバッグ情報を生成し、デバッガが実行ファイルの内部構造を理解できるようにします。

### `$f64.` および `$i64.` シンボル

これらはGoリンカーの内部で使われる特殊なシンボル形式です。
*   `$f64.` シンボル: 64ビット浮動小数点数（`float64`）の定数値を表すためにリンカーが使用する内部シンボルです。例えば、`$f64.3ff0000000000000` のように、浮動小数点数のIEEE 754バイナリ表現を16進数でエンコードしたものがシンボル名に含まれます。
*   `$i64.` シンボル: このコミットでハンドリングが追加されたもので、同様に64ビット整数（`int64`）の定数値を表すためにリンカーが使用する内部シンボルです。例えば、`$i64.123456789abcdef0` のように、64ビット整数値を16進数でエンコードしたものがシンボル名に含まれます。

これらのシンボルは、コンパイル時にコードに直接埋め込むのではなく、シンボルテーブルを通じて参照することで、コードの柔軟性や最適化の機会を提供します。リンカーはこれらのシンボル名から実際の数値データを抽出し、必要に応じてデータセクションに配置します。

### 再配置加算値 (Relocation Addend)

再配置とは、コンパイル時には不明なアドレス（例えば、別の関数やグローバル変数のアドレス）への参照を、リンク時に実際のメモリアドレスに置き換える処理です。
再配置エントリは通常、以下の情報を含みます。
*   **オフセット (Offset)**: 再配置が必要な場所（命令やデータ）が、現在のセクションのどこにあるかを示すオフセット。
*   **タイプ (Type)**: どのような種類の再配置を行うか（例: 絶対アドレス、相対アドレスなど）。
*   **シンボル (Symbol)**: 参照先のシンボル（関数名や変数名）。
*   **加算値 (Addend)**: シンボルの最終アドレスに加算される定数値。例えば、`symbol + 8` のような参照がある場合、`8` が加算値となります。この加算値は、シンボルのベースアドレスからのオフセットを指定するために使用されます。

特に64ビットアーキテクチャでは、再配置エントリに加算値が明示的に含まれる `Rela` 形式が一般的です。

### Goリンカーのデバッグフラグ (`-S`, `-v`)

Goのビルドコマンド `go build` に `-ldflags` オプションを通じてリンカーフラグを渡すことができます。
*   `-S`: リンカーにアセンブリコードのダンプを出力させるフラグです。
*   `-v`: リンカーに詳細な処理情報を出力させるフラグです。

このコミットでは、これらのフラグがGoリンカーの内部的なデバッグ変数 `ctxt->debugasm` と `ctxt->debugvlog` に対応しており、これらが両方とも有効な場合に、より詳細なオブジェクト処理のログが出力されるようになります。

### RISCアーキテクチャ

RISC (Reduced Instruction Set Computer) アーキテクチャは、命令セットを単純化し、固定長命令やロード/ストア命令の分離などを特徴とするCPUアーキテクチャです。Goは、ARM、MIPS、RISC-V、PowerPCなどの様々なRISCアーキテクチャをサポートしています。これらのアーキテクチャでは、メモリアクセスやアドレス計算の特性がCISCアーキテクチャ（x86など）と異なる場合があり、リンカーの挙動もそれに合わせて調整されることがあります。コミットメッセージの `[dev.power64]` から、PowerPC 64ビットアーキテクチャがこの変更の主要なターゲットの一つであったことがわかります。

## 技術的詳細

このコミットは、`src/liblink/objfile.c` 内の3つの異なる箇所に焦点を当てています。

1.  **`writeobj` 関数におけるデバッグ出力の追加**:
    `writeobj` 関数は、オブジェクトファイルの内容を書き出す際に、プログラムカウンタ（PC）のリストを走査します。この変更により、リンカーのデバッグフラグ `ctxt->debugasm` と `ctxt->debugvlog` が両方とも真の場合に、各PC（プログラムカウンタ）のオブジェクト情報が `print` 関数を通じて標準出力に表示されるようになりました。これにより、リンカーが個々の命令やデータ要素をどのように処理しているかを詳細に追跡できるようになり、特にアセンブリレベルでのデバッグが容易になります。

    ```c
    if(ctxt->debugasm && ctxt->debugvlog)
        print("obj: %p %P\\n", p, p);
    ```
    `%p` はポインタのアドレス、`%P` はGoリンカーの内部フォーマットでプログラムカウンタの情報を表示するためのものです。

2.  **`writesym` 関数における再配置加算値の16進数表示**:
    `writesym` 関数は、シンボルとその再配置エントリを書き出す際に呼び出されます。再配置エントリの加算値（`r->add`）は通常10進数で表示されていましたが、この変更により、特定のRISCアーキテクチャ（`ctxt->arch->thechar` が `'5'` または `'9'` の場合）では16進数で表示されるようになりました。
    Goリンカーの内部では、`ctxt->arch->thechar` はターゲットアーキテクチャを識別するための文字コードです。
    *   `'5'` は `ARCH_PPC64` (PowerPC 64ビット) を指すことが多いです。
    *   `'9'` は `ARCH_MIPS64` (MIPS 64ビット) や `ARCH_ARM64` (ARM 64ビット) など、他の64ビットRISCアーキテクチャを指す可能性があります。
    これらのアーキテクチャでは、再配置加算値がアドレスオフセットやビットパターンと密接に関連していることが多く、16進数で表示されることで、デバッグ担当者がその意味をより正確に把握できるようになります。

    ```c
    if(ctxt->arch->thechar == '5' || ctxt->arch->thechar == '9')
        Bprint(ctxt->bso, "\trel %d+%d t=%d %s+%llux\\n", (int)r->off, r->siz, r->type, name, (vlong)r->add);
    else
        Bprint(ctxt->bso, "\trel %d+%d t=%d %s+%lld\\n", (int)r->off, r->siz, r->type, name, (vlong)r->add);
    ```
    `%llux` は `unsigned long long` 型の値を16進数で出力するためのフォーマット指定子です。

3.  **`rdsym` 関数における `$i64.` シンボルのハンドリング追加**:
    `rdsym` 関数は、オブジェクトファイルからシンボルを読み込む際に呼び出されます。以前は `$f64.` というプレフィックスを持つシンボル（64ビット浮動小数点数定数）のみを特別に処理していましたが、この変更により `$i64.` というプレフィックスを持つシンボルも同様に処理されるようになりました。
    リンカーはシンボル名から `$i64.` の部分を除いた残りの文字列を16進数として解釈し、`strtoull` 関数（文字列を `unsigned long long` に変換）を使って64ビット整数値に変換します。この値は `SRODATA` (読み取り専用データ) セクションに配置され、リンカーがこの定数を参照できるようにします。

    ```c
    } else if(strncmp(s->name, "$f64.", 5) == 0 || strncmp(s->name, "$i64.", 5) == 0) {
        int64 i64;
        i64 = strtoull(s->name+5, nil, 16);
        s->type = SRODATA;
    ```
    `strncmp` は文字列の先頭を比較する関数で、`s->name+5` は `$f64.` または `$i64.` のプレフィックスを除いた部分を指します。

これらの変更は、Goリンカーの内部的な堅牢性を高め、特に低レベルのデバッグや新しいアーキテクチャへの対応において、開発者により良いツールと情報を提供することを目的としています。

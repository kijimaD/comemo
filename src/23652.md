## 変更の背景

このコミットは、Go言語の `text/template` パッケージにおけるテンプレートの「bi-state requirement」（二状態要件）に対応するためのコードリファクタリングとバグ修正です。これは、以前の変更（CL10607）のフォローアップとして行われました。

`text/template` パッケージでは、テンプレートは「名前が付けられたがまだ内容がパースされていない（未定義）」状態と、「内容がパースされて実行可能になった（定義済み）」状態の二つを持つことがあります。この二つの状態を適切に管理しないと、特にテンプレートの複製（`Clone`）、新しいテンプレートの作成（`New`）、パースツリーの追加（`AddParseTree`）、そしてテンプレートのパース（`Parse`）といった操作において、予期せぬ挙動やバグが発生する可能性がありました。

具体的には、以下の問題が指摘されていました（Go issue #10910 および #10926 で報告された可能性が高い）：
1.  **`Clone()` メソッドの挙動**: 未定義のテンプレートが `t.tmpl` マップに誤って追加されることで、テンプレートの複製時に不整合が生じる可能性。
2.  **`AddParseTree()` と `Parse()` の内部ロジック**: テンプレートのパースツリーを追加する際のロジックが複雑で、二状態要件を適切に扱えていなかった。特に、既存のテンプレートを上書きする際の挙動や、新しいテンプレートを共通構造に追加する際の処理に改善の余地があった。
3.  **ドキュメントの不明瞭さ**: `Templates()` や `AddParseTree()` メソッドのドキュメントが、その挙動、特にエラーケースやテンプレートの状態に関する説明が不足していた。

このコミットは、これらの問題を解決し、`text/template` パッケージの堅牢性と予測可能性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Go言語の `text/template` パッケージの基本的な概念と、テンプレートがどのように内部で管理されるかを知る必要があります。

1.  **`text/template` パッケージ**:
    Go言語に組み込まれているテキストテンプレートエンジンです。ユーザーが定義したデータ構造に基づいてテキスト出力を生成するために使用されます。HTMLテンプレートを扱う `html/template` パッケージと似ていますが、こちらはエスケープ処理を行わないため、任意のテキスト生成に適しています。

2.  **`Template` 構造体**:
    `text/template` パッケージの中心となる型です。個々のテンプレートを表し、その名前、パースツリー（テンプレートの構文解析結果）、および関連する他のテンプレートへの参照を保持します。

3.  **関連テンプレート (Associated Templates)**:
    `text/template` パッケージでは、複数のテンプレートを一つのグループとして管理できます。例えば、`{{define "header"}}...{{end}}` のように定義されたサブテンプレートは、親テンプレートと関連付けられます。`Template` 構造体内部の `tmpl` マップが、この関連テンプレート群を名前で管理しています。

4.  **`New(name string) *Template` メソッド**:
    指定された名前を持つ新しい空のテンプレートを作成し、現在のテンプレートと同じグループに関連付けます。この時点では、テンプレートは名前を持つだけで、まだパースツリー（内容）を持たない「未定義」状態です。

5.  **`Parse(text string) (*Template, error)` メソッド**:
    指定されたテキストをパースし、テンプレートの定義を現在のテンプレートグループに追加します。テキストには、メインテンプレートの内容や、`{{define "name"}}...{{end}}` 形式のサブテンプレート定義が含まれます。このメソッドが呼び出されると、テンプレートは「定義済み」状態になります。

6.  **`AddParseTree(name string, tree *parse.Tree) (*Template, error)` メソッド**:
    既にパースされた `parse.Tree` を指定された名前のテンプレートに関連付けます。これは `Parse` メソッドの内部でも使用される低レベルな操作です。

7.  **`Clone() (*Template, error)` メソッド**:
    現在のテンプレートとその関連テンプレートのセットを複製し、新しい独立したテンプレートグループを作成します。これにより、元のテンプレートグループに影響を与えることなく、複製されたテンプレートグループを変更できます。

8.  **`Lookup(name string) *Template` メソッド**:
    指定された名前のテンプレートを、現在のテンプレートグループから検索して返します。テンプレートが存在しない場合は `nil` を返します。

9.  **「Bi-state requirement」（二状態要件）**:
    テンプレートが「名前は存在するが内容はまだない（未定義）」状態と、「名前も内容も存在する（定義済み）」状態の二つを区別して扱う必要があるという要件です。例えば、`New("foo")` で作成されたテンプレートは未定義ですが、`Parse("{{define \"foo\"}}...{{end}}")` で内容が追加されると定義済みになります。この区別が、特に `Clone` や `AddParseTree` のような操作で重要になります。

## 技術的詳細

このコミットの技術的詳細な変更点は、主に `text/template/template.go` ファイル内の `AddParseTree`、`Parse`、`Clone` メソッドのリファクタリングと、`multi_test.go` に追加されたテストケースにあります。

**1. `AddParseTree()` のリファクタリング:**
以前の `AddParseTree` は、指定された名前のテンプレートが既に存在する場合にエラーを返す単純なロジックでした。しかし、テンプレートの「bi-state requirement」を考慮すると、未定義のテンプレートを上書きすることは許容されるべきです。
新しい実装では、`t.associate()` メソッドを内部的に利用することで、この要件に対応しています。
- テンプレート名が現在のテンプレートの名前と異なる場合、`t.New(name)` を呼び出して新しい（未定義の）テンプレートを作成します。
- その後、`t.associate(nt, tree)` を呼び出します。この `associate` メソッドが、テンプレートの再定義が許可されるべきか（未定義テンプレートの上書き）どうかを判断し、適切なエラー処理を行います。
- `associate` メソッドが `replace` フラグを `true` で返した場合にのみ、`nt.Tree = tree` を実行してパースツリーを割り当てます。これにより、不適切な再定義を防ぎつつ、未定義テンプレートへのパースツリーの追加を可能にしています。

**2. `Parse()` のリファクタリング:**
`Parse` メソッドは、与えられたテキストをパースし、その結果得られた複数のパースツリー（メインテンプレートとサブテンプレート）を共通構造に追加します。
以前の実装では、`Parse` メソッド内に `AddParseTree` と同様のロジックが重複して記述されていました。
今回の変更では、`Parse` メソッドが内部で `t.AddParseTree(name, tree)` を呼び出すようにリファクタリングされました。これにより、コードの重複が排除され、テンプレートのパースツリー追加ロジックが一元化されました。`AddParseTree` が既に「bi-state requirement」を考慮しているため、`Parse` もその恩恵を受け、より堅牢になりました。

**3. `Clone()` の修正:**
`Clone` メソッドは、テンプレートとその関連テンプレートを複製します。以前の実装では、複製されたテンプレート `nt` の `t.tmpl` マップに、元のテンプレート `t` の名前で `nt` 自身を無条件に追加していました (`nt.tmpl[t.name] = nt`)。
この挙動は、`t` が未定義のテンプレートであった場合に問題を引き起こす可能性がありました。未定義のテンプレートはパースツリーを持たないため、複製時に `t.tmpl` に追加されるべきではありません。
修正後、`Clone` メソッドは、`t.name` と同じ名前のテンプレートを `nt.tmpl` に追加する際に、`t.name` が現在のテンプレートの名前である場合にのみ `nt.tmpl[t.name] = nt` を実行するように変更されました。これにより、未定義のテンプレートが不適切に複製されたテンプレートグループに追加されることを防ぎます。

**4. ドキュメントの明確化:**
- `Templates()` メソッドのドキュメントが「Returns a slice of defined templates associated with t.」（tに関連付けられた定義済みテンプレートのスライスを返します。）と変更され、未定義テンプレートは含まれないことが明確化されました。
- `AddParseTree()` メソッドのドキュメントも更新され、新しいテンプレートの作成、既存の未定義テンプレートの上書き、および再定義エラーのケースについて詳細が追加されました。

これらの変更により、`text/template` パッケージはテンプレートのライフサイクルにおける「未定義」と「定義済み」の区別をより正確に扱い、開発者がテンプレートをより予測可能に操作できるようになりました。

## コアとなるコードの解説

### `src/text/template/template.go` の変更点

1.  **`Clone()` メソッドの修正**:
    -   変更前: `nt.tmpl[t.name] = nt` が `for k, v := range t.tmpl` ループの前に無条件で実行されていました。これは、複製元のテンプレート `t` が未定義であっても、複製先の `nt` の `tmpl` マップに `nt` 自身が `t.name` で登録されてしまう可能性がありました。
    -   変更後: `nt.tmpl[t.name] = nt` の行がループ内に移動し、`if k == t.name` の条件ブロック内に配置されました。これにより、`t.name` が実際に `t.tmpl` マップにキーとして存在し、かつそれが現在のテンプレート自身である場合にのみ、複製されたテンプレート `nt` が `nt.tmpl` に登録されるようになります。この修正は、未定義のテンプレートが不適切に複製されるのを防ぎ、テンプレートの「bi-state requirement」を尊重します。

2.  **`AddParseTree()` メソッドのリファクタリング**:
    -   変更前:
        ```go
        if t.tmpl[name] != nil {
            return nil, fmt.Errorf("template: redefinition of template %q", name)
        }
        nt := t.New(name)
        nt.Tree = tree
        t.tmpl[name] = nt
        return nt, nil
        ```
        このロジックは、既に存在するテンプレート名に対しては無条件にエラーを返していました。しかし、`New()` で作成されただけの「未定義」テンプレートは、後から `AddParseTree()` で内容を定義することが許容されるべきです。
    -   変更後:
        ```go
        nt := t
        if name != t.name {
            nt = t.New(name)
        }
        if replace, err := t.associate(nt, tree); err != nil {
            return nil, err
        } else if replace {
            nt.Tree = tree
        }
        return nt, nil
        ```
        この新しいロジックでは、まず `name` が現在のテンプレートの名前と異なる場合に `t.New(name)` を呼び出して新しいテンプレート `nt` を作成します。そして、`t.associate(nt, tree)` を呼び出すことで、テンプレートの関連付けと再定義チェックのロジックを `associate` メソッドに委譲しています。`associate` メソッドは、未定義テンプレートへのパースツリーの追加を許可し、既に定義済みのテンプレートの不適切な再定義をエラーとして扱います。`replace` が `true` の場合にのみ `nt.Tree = tree` を実行することで、パースツリーの割り当てを制御しています。これにより、テンプレートの二状態要件が適切に処理されるようになりました。

3.  **`Templates()` メソッドのドキュメント修正**:
    -   変更前: 「Returns a slice of the templates associated with t, including t itself.」
    -   変更後: 「Returns a slice of defined templates associated with t.」
    -   この変更により、`Templates()` メソッドが返すのは「定義済み」のテンプレートのみであり、`New()` で作成されただけの「未定義」テンプレートは含まれないことが明確になりました。

4.  **`Parse()` メソッドのリファクタリング**:
    -   変更前: `Parse` メソッド内に、パースされた各ツリーを共通構造に追加するための複雑なロジックが直接記述されていました。これは `AddParseTree` と類似したロジックの重複でした。
    -   変更後: `for name, tree := range trees` ループ内で、`t.AddParseTree(name, tree)` を呼び出すように変更されました。これにより、パースツリーの追加ロジックが `AddParseTree` に一元化され、`Parse` メソッドのコードが簡潔になり、保守性が向上しました。また、`AddParseTree` の修正によって得られた「bi-state requirement」への対応が `Parse` メソッドにも適用されることになります。

### `src/text/template/multi_test.go` の追加テストケース

1.  **`TestTemplateLookUp`**:
    -   `New("foo")` で作成された未定義のテンプレート `foo` が `Lookup("foo")` で `nil` を返すことを確認します。
    -   `New("bar")` で作成された未定義のテンプレート `bar` が `Lookup("bar")` で `nil` を返すことを確認します。
    -   `Parse(`{{define "foo"}}test{{end}}`)` で `foo` テンプレートが定義された後、`Lookup("foo")` が `nil` ではない（つまり定義済みテンプレートが見つかる）ことを確認します。
    -   これは、未定義テンプレートが `Lookup` で見つからないという期待される挙動を検証し、`Templates()` ドキュメントの変更と整合しています。

2.  **`TestNew`**:
    -   `New("test").Parse(...)` で `test` テンプレートを定義し、`t1` とします。
    -   `t1.New("test")` を呼び出して、同じ名前 `test` で新しいテンプレート `t2` を作成します。
    -   `t1` と `t2` が同じ `common` 構造体を共有していること（つまり同じテンプレートグループに属していること）を確認します。
    -   `t1` が定義済みテンプレートとして `Tree` を持っていること、`t2` が未定義テンプレートとして `Tree` を持っていないこと（`nil` であること）を確認します。
    -   `t1.Templates()` が `t2`（未定義テンプレート）を含まず、`t1`（定義済みテンプレート）を含むことを確認します。
    -   このテストは、`New` メソッドが同じ名前で呼ばれた際の挙動、特に定義済みテンプレートと未定義テンプレートの区別が正しく行われていることを検証します。

3.  **`TestParse`**:
    -   `New("test")` で空のテンプレート `t1` を作成します。
    -   `t1.Parse(`{{define "test"}}{{end}}`)`、`t1.Parse(`{{define "test"}}{{/* this is a comment */}}{{end}}`)`、`t1.Parse(`{{define "test"}}foo{{end}}`)` と、同じ名前のテンプレート `test` を複数回パースします。最初の2回は空またはコメントのみで、3回目で実際のコンテンツを定義します。これらはエラーにならないことを確認します。これは、未定義テンプレートへの内容の追加や、空の定義による上書きが許容されることを示します。
    -   しかし、`t1.Parse(`{{define "test"}}foo{{end}}`)` を再度呼び出して、既に内容が定義されているテンプレートを再定義しようとすると、エラーが発生することを確認します。
    -   このテストは、`Parse` メソッドが `AddParseTree` を介して、テンプレートの再定義ルール（未定義テンプレートへの定義は許可、定義済みテンプレートの再定義はエラー）を正しく適用していることを検証します。

これらの変更とテストケースは、`text/template` パッケージがテンプレートの「未定義」と「定義済み」の二つの状態をより正確かつ堅牢に管理できるようにするための重要なステップです。

このコミットは、Goコンパイラの内部パッケージ `cmd/compile` における `bottomUpVisitor` の実装を、`*NodeList` 型から `[]*Node` 型へ変更するものです。これは、`NodeList` 型の使用を段階的に廃止し、よりGoのイディオムに沿ったスライス (`[]*Node`) へ移行する一連の変更の一部です。特に、エスケープ解析 (`esc.go`) とインライン化 (`lex.go`) のロジックに影響を与えています。

## 元コミット内容

このコミットは、Goコンパイラの `cmd/compile` パッケージにおいて、`bottomUpVisitor` 構造体とその関連関数が使用するデータ構造を `*NodeList` (リンクリスト) から `[]*Node` (スライス) へ変更します。この変更は、`NodeList` の使用を廃止し、スライスへの移行を容易にするための一連の作業の一部です。特に、`esc.go` (エスケープ解析) と `lex.go` (インライン化) のファイルで、`NodeList` を `[]*Node` として扱う部分が修正されています。

## 変更の背景

Goコンパイラの初期の設計では、`NodeList` というカスタムのリンクリスト構造が、抽象構文木 (AST) のノードのリストを扱うために広く使用されていました。しかし、Go言語自体が提供するスライス (`[]T`) は、より柔軟で効率的であり、Goのイディオムに沿ったデータ構造です。

`NodeList` は、要素の追加や削除が頻繁に行われる場合に有利な場合がありますが、ランダムアクセス性能が低く、メモリの局所性もスライスに劣る可能性があります。また、Goの組み込みスライスは、その動的なサイズ変更能力と、ガベージコレクタとの統合のしやすさから、多くの場面でリンクリストよりも推奨されます。

このコミットは、`NodeList` が `[]*Node` と「半自明的に」振る舞わないケースを排除することで、`NodeList` から `[]*Node` への移行を容易にするという、より大きな目標の一環です。つまり、`NodeList` のリンクリストとしての特性が強く現れる部分を特定し、そこをスライスに置き換えることで、将来的な完全な移行への道を開いています。これにより、コンパイラコードの可読性、保守性、そして潜在的なパフォーマンスが向上することが期待されます。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Goコンパイラは、Go言語のソースコードを機械語に変換するツールです。`cmd/compile` はその主要な部分であり、字句解析、構文解析、型チェック、中間表現の生成、最適化、コード生成といった一連のフェーズを実行します。

### 抽象構文木 (AST: Abstract Syntax Tree)

ASTは、ソースコードの構文構造を木構造で表現したものです。コンパイラはソースコードを解析する際にASTを構築し、その後の型チェック、最適化、コード生成などのフェーズでASTを走査・変換します。Goコンパイラでは、ASTの各ノードは `Node` 構造体で表現されます。

### `NodeList` と `[]*Node`

*   **`NodeList`**: Goコンパイラの初期に定義された、`Node` へのポインタを要素とするリンクリスト構造です。`Next` フィールドで次の要素へのポインタを持ち、`N` フィールドで実際の `*Node` を保持します。
    ```go
    type NodeList struct {
        N    *Node
        Next *NodeList
    }
    ```
    このような構造は、C言語などでは一般的ですが、Goではスライスがより推奨されます。
*   **`[]*Node` (スライス)**: Go言語の組み込み型であり、同じ型の要素のシーケンスを表現します。内部的には配列へのポインタ、長さ、容量を持ちます。動的にサイズを変更でき、連続したメモリ領域に要素が格納されるため、キャッシュ効率が良く、ランダムアクセスが高速です。

### `bottomUpVisitor`

`bottomUpVisitor` は、Goコンパイラ内でASTをボトムアップ（子ノードから親ノードへ）で走査するための汎用的なメカニズムです。これは、特に相互再帰的な関数群を解析する際に使用されます。例えば、エスケープ解析や関数インライン化の候補を特定する際に、関数の呼び出しグラフを分析するために利用されます。

### エスケープ解析 (Escape Analysis)

エスケープ解析は、コンパイラ最適化の一種で、変数がヒープに割り当てられるべきか、それともスタックに割り当てられるべきかを決定します。
*   **スタック割り当て**: 関数呼び出しの際に確保され、関数がリターンすると解放されるメモリ領域。高速で、ガベージコレクションの対象外。
*   **ヒープ割り当て**: プログラム実行中に動的に確保され、ガベージコレクタによって管理されるメモリ領域。スタックよりも低速で、ガベージコレクションのオーバーヘッドが発生する。

変数が関数のスコープ外に「エスケープ」する場合（例：ポインタが返り値として返される、グローバル変数に代入されるなど）、その変数はヒープに割り当てられる必要があります。エスケープ解析は、このようなケースを特定し、可能な限りスタック割り当てを行うことで、ガベージコレクションの負荷を軽減し、プログラムのパフォーマンスを向上させます。

### 関数インライン化 (Function Inlining)

関数インライン化は、コンパイラ最適化の一種で、小さな関数呼び出しをその呼び出し元に直接展開することです。これにより、関数呼び出しのオーバーヘッド（スタックフレームのセットアップ、引数の渡し、レジスタの保存・復元など）が削減され、プログラムの実行速度が向上します。ただし、コードサイズが増加する可能性もあるため、コンパイラはインライン化の対象となる関数を慎重に選択します。

## 技術的詳細

このコミットの核心は、`bottomUpVisitor` の内部状態と、その `analyze` コールバック関数のシグネチャを `*NodeList` から `[]*Node` へ変更することです。

1.  **`bottomUpVisitor` 構造体の変更 (`esc.go`)**:
    *   `analyze func(*NodeList, bool)` が `analyze func([]*Node, bool)` に変更されました。これにより、解析関数がリンクリストではなくスライスを受け取るようになります。
    *   `stack *NodeList` が `stack []*Node` に変更されました。`bottomUpVisitor` が走査中にノードを一時的に保持するために使用するスタックが、リンクリストからスライスベースの実装に変わります。

2.  **`visitBottomUp` 関数のシグネチャ変更 (`esc.go`)**:
    *   `func visitBottomUp(list *NodeList, analyze func(list *NodeList, recursive bool))` が `func visitBottomUp(list *NodeList, analyze func(list []*Node, recursive bool))` に変更されました。`visitBottomUp` 関数自体はまだ `*NodeList` を受け取りますが、内部で呼び出す `analyze` コールバックには `[]*Node` を渡すようになります。

3.  **`bottomUpVisitor.visit` メソッドの変更 (`esc.go`)**:
    *   このメソッドは、ASTノードを走査し、強連結成分 (SCC: Strongly Connected Component) を特定する際に、ノードをスタックにプッシュ・ポップするロジックを含んでいます。
    *   以前は `NodeList` を手動で構築し、`v.stack = l` のようにリンクリストの先頭を更新していました。
    *   変更後は `v.stack = append(v.stack, n)` を使用して、スライスにノードを追加するようになりました。
    *   SCCが特定された後、スタックから要素を削除する際も、リンクリストの走査 (`for l = v.stack; l.N != n; l = l.Next`) から、スライスのインデックス操作 (`for i = len(v.stack) - 1; i >= 0; i--`) に変更されています。
    *   SCCを構成するノードのブロックを抽出する際も、リンクリストのポインタ操作 (`block := v.stack; v.stack = l.Next; l.Next = nil`) から、スライスのスライス操作 (`block := v.stack[i:]; v.stack = v.stack[:i]`) に変更されています。これにより、より簡潔で効率的なコードになっています。

4.  **`escAnalyze` 関数のシグネチャ変更と内部ループの変更 (`esc.go`)**:
    *   `func escAnalyze(all *NodeList, recursive bool)` が `func escAnalyze(all []*Node, recursive bool)` に変更されました。エスケープ解析の主要な関数が、ノードのリストをスライスとして受け取るようになります。
    *   内部のループも、リンクリストの走査 (`for l := all; l != nil; l = l.Next`) から、スライスの逆順走査 (`for i := len(all) - 1; i >= 0; i--`) に変更されています。これは、スライスを破壊的に変更する可能性のある操作を考慮した、安全なイテレーションパターンです。

5.  **`lex.go` における `visitBottomUp` の呼び出し箇所の変更**:
    *   インライン化の候補を特定する部分で `visitBottomUp` を呼び出す際の匿名関数のシグネチャが、`func(list *NodeList, recursive bool)` から `func(list []*Node, recursive bool)` に変更されました。
    *   内部のループも、リンクリストの走査からスライスの逆順走査に変わっています。

6.  **`subr.go` における `escAnalyze` の呼び出し箇所の変更**:
    *   `escAnalyze(list1(fn), false)` が `escAnalyze([]*Node{fn}, false)` に変更されました。これは、単一の関数ノードをエスケープ解析に渡す際に、`list1` ヘルパー関数で `NodeList` を作成する代わりに、直接 `[]*Node` スライスを作成して渡すようにしたものです。

これらの変更は、Goコンパイラの内部でデータ構造の近代化を進め、Go言語のイディオムに沿った効率的なスライスを積極的に採用することで、コードベース全体の整合性とパフォーマンスを向上させることを目的としています。

## コアとなるコードの解説

### `esc.go` の変更点

*   **`bottomUpVisitor` 構造体**: `analyze` フィールドと `stack` フィールドの型が `*NodeList` から `[]*Node` に変更されました。これにより、ビジターがノードのリストをスライスとして扱い、内部スタックもスライスで管理するようになります。
*   **`visitBottomUp` 関数**: `analyze` コールバックのシグネチャが `func(list *NodeList, recursive bool)` から `func(list []*Node, recursive bool)` に変更されました。これにより、`visitBottomUp` の呼び出し元は、`analyze` 関数がスライスを受け取ることを期待するようになります。
*   **`bottomUpVisitor.visit` メソッド**:
    *   ノードをスタックにプッシュする処理が `v.stack = append(v.stack, n)` となり、Goのスライス操作のイディオムに沿った形になりました。
    *   強連結成分 (SCC) をスタックから取り出す処理が、リンクリストのポインタ操作からスライスのインデックス操作 (`for i = len(v.stack) - 1; i >= 0; i--`) とスライス操作 (`block := v.stack[i:]; v.stack = v.stack[:i]`) に変更されました。これにより、コードが簡潔になり、スライスの効率的なメモリ管理の恩恵を受けられます。
*   **`escAnalyze` 関数**: シグネチャが `func escAnalyze(all *NodeList, recursive bool)` から `func escAnalyze(all []*Node, recursive bool)` に変更され、ノードのリストをスライスとして受け取るようになりました。内部のループも、リンクリストの走査からスライスの逆順走査に変わり、より現代的なGoのコードスタイルに適合しています。

### `lex.go` の変更点

*   `visitBottomUp` を呼び出す匿名関数のシグネチャが `func(list *NodeList, recursive bool)` から `func(list []*Node, recursive bool)` に変更されました。
*   匿名関数内のループも、リンクリストの走査 (`for l := list; l != nil; l = l.Next`) からスライスの逆順走査 (`for i := len(list) - 1; i >= 0; i--`) に変更されました。これは、インライン化の候補となる関数を処理する際に、スライスベースのイテレーションを使用することを示しています。

### `subr.go` の変更点

*   `escAnalyze(list1(fn), false)` が `escAnalyze([]*Node{fn}, false)` に変更されました。これは、単一の関数 `fn` をエスケープ解析に渡す際に、`list1` ヘルパー関数で `NodeList` を作成するのではなく、直接 `[]*Node` スライスをリテラルで作成して渡すようにしたものです。これにより、`NodeList` の使用箇所がさらに削減されます。

これらの変更は、Goコンパイラの内部コードをより現代的なGoのイディオムに合わせ、スライスの効率性と簡潔さを活用することで、コンパイラの保守性とパフォーマンスを向上させることを目的としています。

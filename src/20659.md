# [インデックス 20659] ファイルの概要

このコミットは、Go言語のコマンドラインツール `go` のテストサブコマンド `go test` の振る舞いを変更するものです。具体的には、`_test.go` という命名規則を持つテストファイルが、`Test` 関数を一つも含まない場合でも、常にビルドされ、テストバイナリにリンクされるように修正します。これにより、テストファイル内に構文エラー、型エラー、または `init` 関数でのパニックなどの実行時エラーが存在する場合、それらのエラーが `go test` の実行時に適切に報告されるようになります。

    In Go 1.2, tests with (1) or (2) failed; (3) passed.

## 元コミット内容

`go test` コマンドは、パッケージ内のファイル群に `Test` 関数が一つも存在しない場合の `_test.go` ファイルの取り扱いについて、過去数リリースでその振る舞いが変化していました。`Test` 関数を含まない興味深いケースがいくつかあります。

1.  `x_test.go` に構文エラーがある場合
2.  `x_test.go` に型エラーがある場合
3.  `x_test.go` に実行時エラー（例えば、`init` 関数がパニックを起こすなど）がある場合

Go 1.1 では、(1) または (2) のテストは失敗し、(3) は成功しました。
Go 1.2 でも、(1) または (2) のテストは失敗し、(3) は成功しました。
Go 1.3 では、(1) のテストは失敗し、(2) または (3) は成功しました。
この変更（CL: Change List）の後では、(1)、(2)、(3) のすべてのテストが失敗するようになります。

これは明らかにコーナーケースですが、`func TestAlwaysPasses(t *testing.T) {}` のような行を追加または削除しても、テストの振る舞いが変わるべきではないと筆者は考えています。

このことは、`_test.go` ファイルが常にビルドされ、常にテストバイナリにインポートされるべきであることを示唆しています。そうすることで、(1)、(2)、(3) のすべてが失敗するようになります。

Issue #8337 を修正します。

## 変更の背景

このコミットの背景には、`go test` コマンドが `_test.go` ファイルをどのように扱うかという、過去のバージョン間での一貫性の欠如がありました。特に、テスト関数（`Test` で始まる関数）が一つも定義されていない `_test.go` ファイルが存在する場合の挙動が問題でした。

従来の `go test` の実装では、パッケージ内にテスト関数が全く存在しない場合、`_test.go` ファイルがビルドプロセスから除外されることがありました。これにより、以下のような予期せぬ、かつ望ましくない振る舞いが発生していました。

*   **エラーの見過ごし**: `_test.go` ファイル内に構文エラーや型エラー、あるいは `init` 関数でのパニックのような実行時エラーが含まれていても、それらのファイルがビルドされなければ、エラーが検出されずに `go test` が成功してしまうことがありました。これは、開発者がテストコードの品質問題を早期に発見できないという問題を引き起こします。
*   **振る舞いの不整合**: テスト関数を一つ追加するだけで、それまで無視されていた `_test.go` ファイルがビルド対象となり、潜在的なエラーが突然露呈するという、テストの振る舞いの不整合が生じていました。これは、テストの信頼性を損ない、開発者を混乱させる原因となります。

このコミットは、これらの問題を解決し、`_test.go` ファイルが常にテストバイナリの一部として扱われるようにすることで、`go test` の振る舞いをより予測可能で堅牢なものにすることを目的としています。Issue #8337 は、この問題がコミュニティによって認識され、修正が求められていたことを示しています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語および`go test`コマンドに関する前提知識が必要です。

1.  **Go言語のパッケージとモジュール**:
    *   Goのコードは「パッケージ」にまとめられます。関連する機能は同じパッケージに属します。
    *   パッケージはディレクトリに対応し、同じディレクトリ内のGoソースファイルは同じパッケージに属します。
    *   Go 1.11以降では「モジュール」が導入され、複数のパッケージをまとめる単位となりましたが、このコミットが作成された2014年時点ではモジュールは存在せず、GOPATHベースのワークスペースが主流でした。しかし、パッケージの概念は当時から一貫しています。

2.  **`_test.go` ファイルの役割**:
    *   Go言語では、テストコードは通常、テスト対象のソースファイルと同じパッケージ内に、ファイル名の末尾に `_test.go` を付けたファイルに記述されます（例: `my_package.go` のテストは `my_package_test.go`）。
    *   これらのファイルは、通常のビルド時にはコンパイルされず、`go test` コマンドによってのみコンパイル・実行されます。
    *   `_test.go` ファイルには、`TestXxx`、`BenchmarkXxx`、`ExampleXxx` といった特定のシグネチャを持つ関数が定義されます。

3.  **`go test` コマンドの動作**:
    *   `go test` は、指定されたパッケージのテストを実行するためのコマンドです。
    *   内部的には、テスト対象のパッケージと `_test.go` ファイルをコンパイルし、テストバイナリを生成します。
    *   生成されたテストバイナリは実行され、その出力が解析されてテスト結果が表示されます。
    *   `go test` は、テスト対象のパッケージのコードと、テストコード（`_test.go` ファイル）を結合して一つの実行可能ファイルを生成します。

4.  **`init` 関数**:
    *   Go言語の各パッケージは、`init` という特別な関数を持つことができます。
    *   `init` 関数は、パッケージがインポートされた際に、そのパッケージ内の他のどの関数よりも先に自動的に実行されます。
    *   複数の `init` 関数がある場合、それらは定義された順序で実行されます。
    *   `init` 関数内でパニックが発生した場合、プログラムの実行は停止します。

5.  **ビルドエラーと実行時エラー**:
    *   **構文エラー (Syntax Errors)**: Goの文法規則に違反しているコード。コンパイル時に検出され、ビルドが失敗します。
    *   **型エラー (Type Errors)**: 型の不一致など、Goの型システムに違反しているコード。コンパイル時に検出され、ビルドが失敗します。
    *   **実行時エラー (Runtime Errors)**: プログラムの実行中に発生するエラー。例えば、ゼロ除算、nilポインタ参照、`panic` 関数による明示的なパニックなどがあります。これらはコンパイル時には検出されず、プログラムが実行されるまで顕在化しません。

このコミットは、`go test` が `_test.go` ファイルをビルドする際のロジックを変更し、たとえテスト関数が含まれていなくても、これらのファイルが常にコンパイルされ、その結果として構文エラー、型エラー、実行時エラーが適切に報告されるようにすることで、テストの堅牢性と一貫性を向上させています。

## 技術的詳細

このコミットの技術的な核心は、`go test` コマンドの内部処理において、テスト対象パッケージに `Test` 関数が存在しない場合でも `_test.go` ファイルをビルド対象に含めるように変更した点にあります。

Goのテストフレームワークでは、テスト対象のパッケージ（`p`）と、そのテストコードを含むパッケージ（`ptest`）が区別されます。`ptest` は通常、`_test.go` ファイルから構成されます。`go test` は、これら二つのパッケージを結合して一つのテストバイナリを生成します。

変更前の `go test` のロジックでは、`ptest` パッケージをメインのテストバイナリにインポートするかどうかを決定する際に、`ptest.GoFiles` (テストファイルのリスト) の有無ではなく、`t.ImportTest` というフラグ（これは `Test` 関数が存在するかどうかによって設定されることが多かった）や、カバレッジモード (`ptest.coverMode`) の有無に依存していました。

このコミットでは、`src/cmd/go/test.go` 内の `builder.test` 関数において、`ptest` パッケージをメインのテストバイナリ (`pmain`) にインポートする条件を以下のように変更しています。

変更前:
```go
if t.ImportTest || ptest.coverMode != "" {
    pmain.imports = append(pmain.imports, ptest)
}
```

変更後:
```go
if len(ptest.GoFiles) > 0 { // ptest.GoFiles が存在する場合
    pmain.imports = append(pmain.imports, ptest)
    t.ImportTest = true // ptest がインポートされるので t.ImportTest を true に設定
}
```

この変更により、`ptest.GoFiles` (つまり、`_test.go` ファイル) が一つでも存在すれば、たとえそのファイル内に `Test` 関数が一つもなくても、`ptest` パッケージは常に `pmain` (テストバイナリ) にインポートされるようになります。

結果として、`_test.go` ファイルは常にコンパイル対象となり、以下の効果をもたらします。

*   **構文エラーと型エラーの検出**: `_test.go` ファイル内に構文エラーや型エラーがあれば、コンパイル時にそれらが検出され、`go test` は失敗します。
*   **`init` 関数でのパニックの検出**: `_test.go` ファイル内の `init` 関数がパニックを起こす場合、そのパッケージがインポートされる際に `init` 関数が実行されるため、テストバイナリの起動時にパニックが発生し、`go test` は失敗します。

また、このコミットでは、`src/cmd/go/test.bash` に新しいテストケースが追加されています。このテストケースは、`Test` 関数を含まないが、構文エラー、型エラー、実行時エラー（`init` 関数でのパニック）を含む複数の `_test.go` ファイルを持つパッケージを作成し、`go test` がこれらのエラーを適切に検出して失敗することを確認しています。これにより、変更が意図した通りに機能していることが検証されます。

具体的には、`testdata/src/badtest` ディレクトリ以下に、`badexec` (実行時パニック)、`badsyntax` (構文エラー)、`badvar` (型エラー) の各ケースを再現する `_test.go` ファイルが追加されています。

## コアとなるコードの解説

`src/cmd/go/test.go` の変更は、`go test` コマンドがテストバイナリを構築する際のロジックを直接修正しています。

`builder.test` 関数は、テストのビルドと実行をオーケストレーションする役割を担っています。この関数内で、テスト対象のパッケージ (`p`) と、そのテストコードを含むパッケージ (`ptest`)、そして外部テストパッケージ (`pxtest`) がどのようにメインのテストバイナリ (`pmain`) にインポートされるかが決定されます。

変更前のコードでは、`ptest` をインポートする条件として `t.ImportTest || ptest.coverMode != ""` が使われていました。
*   `t.ImportTest`: これは、テスト対象のパッケージに `Test` 関数が存在するかどうかを示すフラグでした。もし `Test` 関数が一つもなければ、このフラグは `false` になる可能性がありました。
*   `ptest.coverMode != ""`: カバレッジ計測が有効な場合、`_test.go` ファイルは常にビルドされる必要がありました。

このロジックの問題点は、`Test` 関数が存在しない場合（`t.ImportTest` が `false` の場合）、かつカバレッジ計測も有効でない場合、`_test.go` ファイルがビルド対象から除外されてしまう可能性があったことです。これにより、`_test.go` ファイル内の構文エラーや型エラー、`init` 関数でのパニックが見過ごされていました。

変更後のコードでは、この条件が `len(ptest.GoFiles) > 0` に置き換えられました。
*   `len(ptest.GoFiles) > 0`: これは、`ptest` パッケージにGoソースファイル（つまり `_test.go` ファイル）が一つでも存在するかどうかを直接チェックします。

このシンプルな変更により、`_test.go` ファイルが存在する限り、それらが常に `pmain.imports` に追加され、結果としてテストバイナリにリンクされることが保証されます。`t.ImportTest = true` の行は、`ptest` がインポートされるようになったので、その状態を正確に反映するために追加されました。

同様に、外部テストパッケージ `pxtest` のインポート条件も `t.ImportXtest` から `pxtest != nil` に変更され、`pxtest` が存在すれば常にインポートされるようになりました。

`src/cmd/go/test.bash` に追加されたテストケースは、この変更が意図した通りに機能することを検証するためのものです。このシェルスクリプトは、意図的にエラーを含む `_test.go` ファイルを持つテストパッケージを作成し、`go test` を実行します。そして、`go test` が「成功」を示す `ok` を出力せず、代わりに各エラーケースに対応する `FAIL` メッセージを出力することを確認します。これにより、`_test.go` ファイルが常にビルドされ、その中のエラーが適切に報告されるようになったことが実証されます。

# [インデックス 20490] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）がアセンブリ関数向けにポインタのライブネスマップを生成する機能を追加するものです。これにより、アセンブリ関数がGoのスタックの途中に存在する場合でも、ガベージコレクション（GC）やスタックコピーがポインタを正確に処理できるようになります。

## コミット

```
commit 99f7df0598238b03d78cc6c89e0bd6b6b9feb246
Author: Russ Cox <rsc@golang.org>
Date:   Fri Sep 12 00:18:20 2014 -0400

    cmd/gc: turn Go prototypes into ptr liveness maps for assembly functions
    
    The goal here is to allow assembly functions to appear in the middle
    of a Go stack (having called other code) and still record enough information
    about their pointers so that stack copying and garbage collection can handle
    them precisely. Today, these frames are handled only conservatively.
    
    If you write
    
            func myfunc(x *float64) (y *int)
    
    (with no body, an 'extern' declaration), then the Go compiler now emits
    a liveness bitmap for use from the assembly definition of myfunc.
    The bitmap symbol is myfunc.args_stackmap and it contains two bitmaps.
    The first bitmap, in effect at function entry, marks all inputs as live.
    The second bitmap, not in effect at function entry, marks the outputs
    live as well.
    
    In funcdata.h, define new assembly macros:
    
    GO_ARGS opts in to using the Go compiler-generated liveness bitmap
    for the current function.
    
    GO_RESULTS_INITIALIZED indicates that the results have been initialized
    and need to be kept live for the remainder of the function; it causes a
    switch to the second generated bitmap for the assembly code that follows.
    
    NO_LOCAL_POINTERS indicates that there are no pointers in the
    local variables being stored in the function's stack frame.

    R=khr
```

## 元コミット内容

このコミットの目的は、Goのランタイムがアセンブリ関数をより正確に扱えるようにすることです。具体的には、Goのスタックの途中にアセンブリ関数が存在し、他のGoコードを呼び出している場合でも、そのアセンブリ関数のポインタに関する十分な情報を記録し、スタックコピーやガベージコレクションがそれらを正確に処理できるようにすることを目指しています。この変更以前は、これらのフレームは「保守的」にしか扱われていませんでした。

Goの関数プロトタイプ（本体を持たない`extern`宣言）を記述すると、Goコンパイラは、そのアセンブリ定義で使用するためのライブネスビットマップを生成するようになりました。このビットマップシンボルは`myfunc.args_stackmap`（例）という形式で、2つのビットマップを含みます。1つ目は関数エントリ時に有効で、すべての入力ポインタをライブとしてマークします。2つ目は関数エントリ時には有効ではありませんが、結果が初期化された後に有効になり、出力ポインタもライブとしてマークします。

`funcdata.h`には、新しいアセンブリマクロが定義されています。
- `GO_ARGS`: 現在の関数に対して、Goコンパイラが生成したライブネスビットマップの使用をオプトインします。
- `GO_RESULTS_INITIALIZED`: 結果が初期化され、関数の残りの部分でライブに保つ必要があることを示します。これにより、続くアセンブリコードに対して2番目の生成されたビットマップに切り替わります。
- `NO_LOCAL_POINTERS`: 関数のスタックフレームに格納されているローカル変数にポインタがないことを示します。

## 変更の背景

Goのランタイムは、ガベージコレクション（GC）とゴルーチン（軽量スレッド）のスタック管理において、メモリ上のポインタを正確に追跡する必要があります。特に、Goのゴルーチンスタックは必要に応じて動的に拡大・縮小するため、スタックのコピーが発生します。この際、スタック上のどの位置にポインタが存在し、それがどのヒープオブジェクトを指しているかを正確に知る必要があります。

しかし、Goのコードから呼び出されるアセンブリ関数は、Goコンパイラが生成する通常のGo関数とは異なり、その内部のポインタ情報がランタイムに明示的に伝達されていませんでした。そのため、アセンブリ関数がGoのスタックの途中に存在する場合、ランタイムはアセンブリ関数のスタックフレームを「保守的（conservative）」にしかスキャンできませんでした。保守的なスキャンとは、スタック上のすべてのワードをポインタである可能性があると仮定して処理する方法です。これは安全ですが、実際にはポインタではない値までポインタとして扱ってしまう可能性があり、メモリリークやGCの効率低下につながる可能性があります。

このコミットの背景には、アセンブリ関数がGoのスタックの一部として機能する際に、より「正確な（precise）」GCとスタックコピーを可能にすることで、ランタイムの効率と堅牢性を向上させるという目的があります。

## 前提知識の解説

### Goランタイム

Goランタイムは、Goプログラムの実行を管理するシステムです。これには、ガベージコレクタ、スケジューラ（ゴルーチンの管理）、メモリ割り当て、システムコールインターフェースなどが含まれます。Goプログラムは、Goランタイムと密接に連携して動作します。

### ガベージコレクション (GC)

ガベージコレクションは、プログラムが動的に割り当てたメモリのうち、もはや到達不可能（参照されていない）になったものを自動的に解放するプロセスです。GoのGCは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行して動作します。GCが正確に動作するためには、メモリ上のどの値がポインタであり、どのヒープオブジェクトを指しているかを正確に識別する必要があります。

*   **保守的GC (Conservative GC)**: メモリ上の任意のビットパターンがポインタである可能性があると仮定してスキャンします。これにより、誤って非ポインタをポインタと解釈し、到達可能なオブジェクトを解放しないようにします。安全ですが、不要なメモリを保持し続ける（リーク）可能性があります。
*   **正確なGC (Precise GC)**: コンパイラやランタイムが、メモリ上のどの位置にポインタが存在するかを正確に知っている場合に行われます。これにより、ポインタではない値を誤ってポインタと解釈することがなく、より効率的で正確なメモリ管理が可能です。

### スタックコピー

Goのゴルーチンスタックは、最初は小さく割り当てられ、必要に応じて拡大します。スタックが現在のメモリ領域を超えて成長する必要がある場合、Goランタイムはより大きな新しいスタック領域を割り当て、古いスタックの内容を新しい領域にコピーします。このコピープロセス中、スタック上のポインタは、新しいスタックアドレスに合わせて更新される必要があります。ポインタの正確な位置が不明な場合、この処理は困難または不可能になります。

### アセンブリ関数と`extern`宣言

Goは、パフォーマンスが重要な部分や、特定のハードウェア機能にアクセスする必要がある場合に、アセンブリ言語で書かれた関数を使用できます。Goのソースコード内でアセンブリ関数を宣言するには、関数本体を持たないプロトタイプを記述し、その実装が外部（アセンブリファイル）にあることを示します。これが`extern`宣言に相当します。

例: `func myfunc(x *float64) (y *int)` のように、関数本体がないGoの関数宣言は、その関数がアセンブリで実装されていることを示唆します。

### ポインタライブネスマップ (スタックマップ)

ポインタライブネスマップ、またはスタックマップは、特定のコード実行ポイント（例えば、関数呼び出しの直前やGCのトリガー時）において、スタック上のどの位置にライブなポインタが存在するかを示すビットマップです。各ビットはスタック上のワードに対応し、ビットがセットされていればそのワードがポインタであることを示します。これにより、GCはスタックを効率的かつ正確にスキャンし、ライブなポインタのみを追跡できます。

## 技術的詳細

このコミットの核心は、Goコンパイラがアセンブリ関数に対応するGoのプロトタイプから、その関数の引数と戻り値に関するポインタのライブネス情報を抽出・生成し、それをランタイムが利用できるようにすることです。

1.  **Goコンパイラによるビットマップ生成**:
    *   Goコンパイラ（`cmd/gc`）は、本体を持たないGoの関数宣言（`extern`宣言されたアセンブリ関数）を解析します。
    *   これらの関数の引数と戻り値の型情報に基づいて、ポインタのライブネスを示すビットマップを生成します。
    *   生成されるビットマップは、`myfunc.args_stackmap`のようなシンボル名で、データセクションに格納されます。
    *   このビットマップは2つの部分から構成されます。
        *   **1つ目のビットマップ**: 関数エントリ時にライブな入力引数（ポインタ）を示します。
        *   **2つ目のビットマップ**: 結果が初期化された後にライブになる入力引数と出力引数（ポインタ）を示します。これは、アセンブリ関数内で結果が準備された後に使用されます。

2.  **アセンブリマクロの導入**:
    *   `src/runtime/funcdata.h`に新しいアセンブリマクロが導入されました。これらは、アセンブリコードからGoランタイムに対して、ポインタのライブネス情報に関するヒントを提供するために使用されます。
    *   `GO_ARGS`: アセンブリ関数が、Goコンパイラによって生成された引数のポインタマップを使用することを示します。通常、関数の冒頭に配置されます。
    *   `GO_RESULTS_INITIALIZED`: アセンブリ関数が戻り値のスタック領域を初期化し、それらの戻り値が関数の残りの部分でライブであると見なされるべきであることを示します。これにより、ランタイムは2番目のビットマップに切り替えてスキャンします。
    *   `NO_LOCAL_POINTERS`: アセンブリ関数のローカルスタック変数にヒープオブジェクトへのポインタが格納されていないことを示します。これにより、ランタイムはローカル変数領域をスキャンする必要がなくなります。

3.  **リンカによるシンボル解決**:
    *   リンカ（`src/liblink/objfile.c`）は、アセンブリコード内の`go_args_stackmap(SB)`のような参照を、コンパイラが生成した具体的な関数ごとのビットマップシンボル（例: `myfunc.args_stackmap`）に解決します。これにより、アセンブリ関数とそれに対応するポインタライブネス情報が正しく関連付けられます。

4.  **ビルドプロセスの更新**:
    *   `src/cmd/dist/build.c`が更新され、`funcdata.h`がビルドプロセス中に適切にコピーされるようになりました。

これらの変更により、Goランタイムはアセンブリ関数のスタックフレーム内のポインタを正確に識別できるようになり、より効率的で正確なガベージコレクションとスタックコピーが可能になります。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

*   `src/cmd/gc/pgen.c`: Goコンパイラのコード生成部分。`emitptrargsmap`関数が追加され、ポインタライブネスビットマップの生成ロジックが実装されました。
*   `src/liblink/objfile.c`: リンカのオブジェクトファイル書き出し部分。アセンブリ関数が参照する`go_args_stackmap`シンボルを、コンパイラが生成した具体的な関数ごとのスタックマップシンボルに解決するロジックが追加されました。
*   `src/runtime/funcdata.h`: ランタイムの関数データに関する定義。新しいアセンブリマクロ（`GO_ARGS`, `GO_RESULTS_INITIALIZED`, `NO_LOCAL_POINTERS`）が追加されました。
*   `src/runtime/asm.s`: `runtime·no_pointers_stackmap`という、ポインタを含まないスタックマップの定義が追加されました。これは`NO_LOCAL_POINTERS`マクロで使用されます。

## コアとなるコードの解説

### `src/cmd/gc/pgen.c` における `emitptrargsmap` 関数

この関数は、本体を持たないGo関数（アセンブリ関数）のプロトタイプから、引数と戻り値のポインタライブネスビットマップを生成する役割を担います。

1.  **シンボル名の生成**:
    ```c
    sym = lookup(smprint("%s.args_stackmap", curfn->nname->sym->name));
    ```
    現在の関数名（`curfn->nname->sym->name`）に基づいて、`myfunc.args_stackmap`のような形式のシンボル名を生成し、そのシンボルへの参照を取得します。このシンボルが、生成されるビットマップデータを格納する場所になります。

2.  **ビットマップの初期化とサイズ計算**:
    ```c
    nptr = curfn->type->argwid / widthptr;
    bv = bvalloc(nptr*2);
    nbitmap = 1;
    if(curfn->type->outtuple > 0)
        nbitmap = 2;
    ```
    `nptr`は、引数領域が何個のポインタ幅のワードを含むかを計算します。`bvalloc(nptr*2)`で、引数と戻り値の両方をカバーできるサイズのビットマップベクトルを割り当てます。`nbitmap`は、戻り値がある場合は2（入力用と出力用）、ない場合は1（入力用のみ）となります。

3.  **ビットマップデータ書き込み**:
    ```c
    off = duint32(sym, 0, nbitmap);
    off = duint32(sym, off, bv->n);
    ```
    生成されたシンボルに、まずビットマップの数（1または2）、次にビットマップのサイズ（`bv->n`）を書き込みます。

4.  **入力引数のビットマップ生成**:
    ```c
    if(curfn->type->thistuple > 0) {
        xoffset = 0;
        twobitwalktype1(getthisx(curfn->type), &xoffset, bv);
    }
    if(curfn->type->intuple > 0) {
        xoffset = 0;
        twobitwalktype1(getinargx(curfn->type), &xoffset, bv);
    }
    for(j = 0; j < bv->n; j += 32)
        off = duint32(sym, off, bv->b[j/32]);
    ```
    `twobitwalktype1`関数は、関数のレシーバ（`thistuple`）と入力引数（`intuple`）の型を走査し、ポインタが存在する位置に対応するビットを`bv`（ビットマップベクトル）にセットします。その後、`bv`の内容を32ビットずつ`duint32`でシンボルに書き込みます。これが1つ目のビットマップ（関数エントリ時のライブネス）になります。

5.  **出力引数のビットマップ生成 (存在する場合)**:
    ```c
    if(curfn->type->outtuple > 0) {
        xoffset = 0;
        twobitwalktype1(getoutargx(curfn->type), &xoffset, bv);
        for(j = 0; j < bv->n; j += 32)
            off = duint32(sym, off, bv->b[j/32]);
    }
    ```
    戻り値（`outtuple`）が存在する場合、同様に`twobitwalktype1`を使って戻り値の型を走査し、ビットマップを更新します。そして、その内容をシンボルに書き込みます。これが2つ目のビットマップ（結果初期化後のライブネス）になります。

6.  **シンボルのグローバル化**:
    ```c
    ggloblsym(sym, off, RODATA);
    ```
    生成されたシンボルを読み取り専用データ（`RODATA`）としてグローバルに公開し、リンカが参照できるようにします。

### `src/liblink/objfile.c` における変更

リンカは、アセンブリコードが`go_args_stackmap(SB)`のような汎用的な参照を使用している場合、それをコンパイラが生成した特定の関数のスタックマップシンボルに置き換えます。

```c
if(p->as == ctxt->arch->AFUNCDATA) {
    // Rewrite reference to go_args_stackmap(SB) to the Go-provided declaration information.
    // ...
    if(strcmp(p->to.sym->name, "go_args_stackmap") == 0) {
        // ...
        p->to.sym = linklookup(ctxt, smprint("%s.args_stackmap", curtext->name), curtext->version);
    }
}
```
`AFUNCDATA`は、アセンブリ関数に関連するデータを示す擬似命令です。リンカが`AFUNCDATA`命令を処理する際に、そのターゲットシンボルが`go_args_stackmap`であれば、現在のテキストセクション（つまり、現在リンク中のアセンブリ関数）の名前を使って、対応する`myfunc.args_stackmap`シンボルを検索し、参照を書き換えます。これにより、アセンブリ関数は自身のポインタライブネスマップに正しくリンクされます。

### `src/runtime/funcdata.h` における新しいマクロ

このファイルでは、アセンブリコードからランタイムにポインタ情報を伝えるための新しいマクロが定義されています。

*   `#define GO_ARGS FUNCDATA $FUNCDATA_ArgsPointerMaps, go_args_stackmap(SB)`
    *   `FUNCDATA`は、関数に関するメタデータをランタイムに提供するための命令です。
    *   `FUNCDATA_ArgsPointerMaps`は、引数のポインタマップに関するデータであることを示します。
    *   `go_args_stackmap(SB)`は、リンカによって実際の関数ごとのスタックマップシンボルに解決されます。

*   `#define GO_RESULTS_INITIALIZED FUNCDATA PCDATA $PCDATA_StackMapIndex, 1`
    *   `PCDATA`は、プログラムカウンタ（PC）データに関する情報を提供します。
    *   `PCDATA_StackMapIndex`は、スタックマップのインデックスに関するデータであることを示します。
    *   `1`は、2番目のスタックマップ（戻り値を含むもの）を使用することを示します。

*   `#define NO_LOCAL_POINTERS FUNCDATA $FUNCDATA_LocalsPointerMaps, runtime·no_pointers_stackmap(SB)`
    *   `FUNCDATA_LocalsPointerMaps`は、ローカル変数のポインタマップに関するデータであることを示します。
    *   `runtime·no_pointers_stackmap(SB)`は、ポインタを含まないローカル変数であることを示す特別なゼロビットマップを参照します。

これらのマクロをアセンブリコード内で使用することで、アセンブリ関数は自身のポインタ情報をGoランタイムに正確に伝えることができ、GCやスタックコピーの精度が向上します。

# [インデックス 19983] ファイルの概要

このコミットは、Go言語の`syscall`パッケージにおけるmacOS (OS X 10.10 Yosemite) 特有のバグに対する修正を導入しています。具体的には、ディレクトリの内容を読み取る際に、特定の条件下で`EINVAL`または`ENOENT`エラーが返される問題を回避し、それらを正常なEOF (End Of File) として扱うように変更しています。

## 元コミット内容

このコミットは、OS X 10.10 Yosemiteにおける`readdirent`システムコールからの`EINVAL`または`ENOENT`エラーを無視するように`syscall`パッケージを修正します。

OS X 10.10 Yosemiteでは、単一の`getdirentries64`呼び出しで内容が返されるような小さなディレクトリ（例：ファイルが1つだけのディレクトリ）において、ディレクトリの終端 (EOF) に達した後に再度読み取りを行うと、通常はEOFが返されます。しかし、最初のEOF到達と次の読み取りの間にディレクトリ内のファイルが削除された場合、2回目の読み取りで`ENOENT`または`EINVAL`エラーが返されるというバグがありました。このエラーは、ディレクトリの内容に依存して`ENOENT`または`EINVAL`のどちらかになります。

この問題は小さなディレクトリでのみ発生し、4KBを超えるデータを含むディレクトリでは正しくEOFが返されます。

このコミットでは、`os`パッケージを変更して2回目のEOF読み取りを回避することも可能だが、それは複雑であるため、当面の間、`EINVAL`または`ENOENT`をEOFとして扱うことで対応します。

この変更により、OS X 10.10 (14A299l) および Xcode 6 beta 5 (6A279r) を実行しているMacBook Airで`all.bash`テストがパスするようになりました。

Appleへの問題報告は試みられたものの、Feedback Assistantがレポートを送信できず、失われたとのことです。

コミットメッセージには、この問題を再現するC言語のプログラムも含まれています。

## 変更の背景

この変更の背景には、OS X 10.10 Yosemiteのファイルシステム関連のシステムコールにおける特定のバグが存在します。Go言語の標準ライブラリ、特に`os`パッケージや`io/ioutil`パッケージは、内部的にOSの提供するシステムコール（この場合はディレクトリの内容を読み取るための`getdirentries64`）を利用しています。

通常、ディレクトリの読み取りは、ディレクトリ内のエントリを順次取得し、全てのエントリを読み終えるとEOF（End Of File）を示す値を返すという挙動をします。EOFに達した後に再度読み取りを試みても、通常は引き続きEOFが返されるべきです。

しかし、OS X 10.10 Yosemiteでは、以下のような特殊なシナリオでこの期待される挙動が破綻しました。

1.  **小さなディレクトリ**: ディレクトリの内容が非常に小さく、`getdirentries64`システムコール1回で全てのエントリが読み取れてしまうようなディレクトリ。
2.  **EOF到達後のファイル削除**: ディレクトリの内容を全て読み取り、EOFに達したとシステムが認識した後、そのディレクトリ内のファイルが外部から削除される。
3.  **再度の読み取り**: その後、同じファイルディスクリプタを使って再度ディレクトリの読み取りを試みる。

このシナリオにおいて、OS X 10.10は通常返されるべきEOFではなく、`EINVAL`（Invalid argument: 不正な引数）または`ENOENT`（No such file or directory: そのようなファイルまたはディレクトリはない）というエラーを返していました。これらのエラーは、Goプログラムにとっては予期せぬものであり、ディレクトリの読み取り処理が異常終了したり、クラッシュしたりする原因となっていました。

Goの`syscall`パッケージは、OSのシステムコールを直接ラップしているため、このようなOS側のバグがGoプログラムに直接影響を与えます。このバグは、Goのテストスイートである`all.bash`がOS X 10.10上で失敗する原因となっていました。Go開発チームは、このOSのバグを回避し、Goプログラムが安定して動作するようにするために、このコミットで修正を導入する必要がありました。

Appleへのバグ報告が試みられたものの、Feedback Assistantの不具合により報告ができなかったという経緯も、このコミットの背景として特筆すべき点です。これは、Go開発チームが自ら回避策を実装する必要があった状況を示しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

### 1. システムコール (System Call)

システムコールは、ユーザー空間で動作するプログラムが、カーネル空間で動作するOSの機能（ファイルI/O、メモリ管理、プロセス管理など）を利用するためのインターフェースです。プログラムは直接ハードウェアにアクセスできないため、OSが提供するシステムコールを介して間接的にハードウェアリソースを操作します。

### 2. `getdirentries64`

`getdirentries64`は、macOS (およびBSD系のOS) におけるディレクトリの内容を読み取るためのシステムコールの一つです。これは、指定されたファイルディスクリプタ（開かれたディレクトリに対応）から、ディレクトリ内のエントリ（ファイルやサブディレクトリ）の情報をバッファに読み込みます。`64`は、64ビットシステムに対応していることを示唆しています。このシステムコールは、ディレクトリのオフセット（読み取り位置）を管理し、繰り返し呼び出すことでディレクトリ全体を走査します。

### 3. `readdir`

`readdir`は、C標準ライブラリ（`dirent.h`）で提供される関数で、ディレクトリの内容を読み取るための高レベルなAPIです。内部的には、`getdirentries`のような低レベルなシステムコールを呼び出して実装されています。`readdir`は、ディレクトリ内の次のエントリを`struct dirent`構造体として返します。全てのエントリを読み終えるとNULLを返し、エラーが発生した場合はNULLを返し、`errno`を設定します。

### 4. `EINVAL` (Invalid argument)

`EINVAL`は、システムコールやライブラリ関数に渡された引数が無効であることを示すエラーコードです。例えば、ファイルディスクリプタが不正であったり、バッファサイズが不適切であったりする場合に返されることがあります。

### 5. `ENOENT` (No such file or directory)

`ENOENT`は、指定されたファイルやディレクトリが存在しないことを示すエラーコードです。ファイルを開こうとしたが存在しなかった場合や、パスの途中のディレクトリが存在しなかった場合などに返されます。

### 6. EOF (End Of File)

EOFは、ファイルやストリームの終端に達したことを示す概念です。ファイル読み取り操作において、読み取るべきデータがもう存在しない場合にEOFが通知されます。ディレクトリの読み取りにおいても、全てのエントリを読み終えた場合にEOFの状態となります。

### 7. Go言語の`syscall`パッケージ

Go言語の`syscall`パッケージは、OSのシステムコールへの低レベルなインターフェースを提供します。これにより、Goプログラムから直接OSの機能を利用できます。このパッケージはOSに依存する部分が多く、各OSのシステムコールAPIに合わせて実装されています。`syscall.ReadDirent`関数は、内部的にOS固有のディレクトリ読み取りシステムコール（macOSでは`getdirentries64`）を呼び出しています。

### 8. `runtime.GOOS`

`runtime.GOOS`は、Go言語の標準ライブラリ`runtime`パッケージで提供される定数で、プログラムが実行されているオペレーティングシステムの名前（例: "linux", "darwin", "windows"など）を表します。これにより、OSに依存するコードを条件分岐で記述することができます。

## 技術的詳細

このコミットが対処している問題は、OS X 10.10 Yosemiteの`getdirentries64`システムコールにおける、特定の条件下での異常なエラー挙動です。

通常、ディレクトリの読み取りは、`getdirentries64`を繰り返し呼び出すことで行われます。ディレクトリ内の全てのエントリを読み終えると、`getdirentries64`は読み取ったバイト数として0を返し、これはEOF（End Of File）を示します。その後、再度`getdirentries64`を呼び出しても、引き続き0（EOF）が返されることが期待されます。

しかし、OS X 10.10では、以下の条件が揃った場合にこの期待される挙動が破綻します。

1.  **ディレクトリのサイズ**: ディレクトリが非常に小さく、その内容（エントリ情報）が`getdirentries64`の1回の呼び出しで全て読み取れてしまう場合。コミットメッセージでは「単一の`getdirentries64`呼び出しで返されるディレクトリ」と表現されています。これは、ディレクトリのデータがファイルシステムブロックの境界をまたがず、かつ`getdirentries64`が一度に読み取るバッファサイズ（通常は4KB）に収まるような場合を指します。
2.  **EOF到達後のファイル削除**: ディレクトリの内容を全て読み取り、`getdirentries64`が0（EOF）を返した後、そのディレクトリ内のファイルが別のプロセスやスレッドによって削除された場合。
3.  **EOF後の再読み取り**: その後、同じファイルディスクリプタを使用して再度`getdirentries64`を呼び出すと、通常返されるべき0（EOF）ではなく、`EINVAL`または`ENOENT`というエラーが返されます。どちらのエラーが返されるかは、ディレクトリ内の具体的なデータ（削除されたファイルの種類や数など）に依存し、データによって決定論的に決まります。

この挙動は、Goの`syscall`パッケージが`getdirentries64`を呼び出す際に問題を引き起こします。Goの`syscall.ReadDirent`関数は、ディレクトリの読み取りがEOFに達したことを示すために、エラーを返さずに読み取ったバイト数として0を返すことを期待しています。しかし、OS X 10.10のバグにより`EINVAL`や`ENOENT`が返されると、Goプログラムはこれを予期せぬエラーとして処理し、ディレクトリの走査が中断されたり、エラーハンドリングロジックが誤動作したりする可能性がありました。

コミットメッセージに記載されているC言語の再現プログラムは、このバグを明確に示しています。このプログラムは、一時ディレクトリを作成し、その中にファイルを作成します。そして、`opendir`と`readdir`を使ってディレクトリを読み取ります。`readdir`がEOFを返した後、ファイルが削除されると、その後の`readdir`呼び出しが`ENOENT`または`EINVAL`を返すことを示しています。

この問題は、Goの`os`パッケージがディレクトリを走査する際に、EOFに達した後に再度読み取りを試みる可能性があるために顕在化しました。理想的には、`os`パッケージ側でEOF後の余分な読み取りを避けるように変更することも考えられますが、それはより複雑な変更となるため、このコミットでは`syscall`レイヤーでOSのバグを吸収するアプローチが取られました。つまり、`EINVAL`や`ENOENT`が返された場合でも、それをEOFとして扱うことで、Goプログラムが正常に動作するようにしています。

## コアとなるコードの解説

変更は`ReadDirent`関数内で行われています。

1.  **元のコード**:
    ```go
    return Getdirentries(fd, buf, base)
    ```
    これは、`Getdirentries`システムコールを直接呼び出し、その戻り値（読み取ったバイト数`n`とエラー`err`）をそのまま返していました。

2.  **変更後のコード**:
    ```go
    n, err = Getdirentries(fd, buf, base)

    // On OS X 10.10 Yosemite, ... (コメントは省略)
    if runtime.GOOS == "darwin" && (err == EINVAL || err == ENOENT) {
        err = nil
    }

    return
    ```
    変更後では、まず`Getdirentries`の呼び出し結果を`n`と`err`変数に格納します。
    その後に、以下の条件分岐が追加されています。

    *   `runtime.GOOS == "darwin"`: 現在のOSがmacOS（旧OS X）であるかどうかをチェックします。この問題はmacOS特有のバグであるため、他のOSではこの処理は不要です。
    *   `(err == EINVAL || err == ENOENT)`: `Getdirentries`から返されたエラーが`EINVAL`または`ENOENT`のいずれかであるかをチェックします。これらは、OS X 10.10のバグによってEOFの代わりに返される可能性のあるエラーコードです。

    もし上記の2つの条件が両方とも真であれば、つまり「macOS上で、かつ`EINVAL`または`ENOENT`エラーが返された場合」に、`err = nil`とエラーを`nil`（エラーなし）に上書きしています。

この修正の意図は、OS X 10.10のバグによって`EINVAL`や`ENOENT`が返された場合でも、Goの`syscall`パッケージがそれを正常なEOFとして扱うようにすることです。これにより、上位の`os`パッケージなどがこれらのエラーを予期せぬものとして処理し、プログラムが異常終了するのを防ぎます。結果として、GoプログラムはOSのバグの影響を受けることなく、ディレクトリの読み取りを継続できるようになります。

この修正は、OSのバグに対するワークアラウンド（回避策）であり、根本的なOSのバグ自体を修正するものではありません。しかし、Goプログラムの安定性を確保するためには効果的なアプローチです。

## 元コミット内容

このコミットは、OS X 10.10 Yosemiteにおける`readdirent`システムコールからの`EINVAL`または`ENOENT`エラーを無視するように`syscall`パッケージを修正します。

OS X 10.10 Yosemiteでは、単一の`getdirentries64`呼び出しで内容が返されるような小さなディレクトリ（例：ファイルが1つだけのディレクトリ）において、ディレクトリの終端 (EOF) に達した後に再度読み取りを行うと、通常はEOFが返されます。しかし、最初のEOF到達と次の読み取りの間にディレクトリ内のファイルが削除された場合、2回目の読み取りで`ENOENT`または`EINVAL`エラーが返されるというバグがありました。このエラーは、ディレクトリの内容に依存して`ENOENT`または`EINVAL`のどちらかになります。

この問題は小さなディレクトリでのみ発生し、4KBを超えるデータを含むディレクトリでは正しくEOFが返されます。

このコミットでは、`os`パッケージを変更して2回目のEOF読み取りを回避することも可能だが、それは複雑であるため、当面の間、`EINVAL`または`ENOENT`をEOFとして扱うことで対応します。

この変更により、OS X 10.10 (14A299l) および Xcode 6 beta 5 (6A279r) を実行しているMacBook Airで`all.bash`テストがパスするようになりました。

Appleへの問題報告は試みられたものの、Feedback Assistantの不具合により報告ができなかったとのことです。

コミットメッセージには、この問題を再現するC言語のプログラムも含まれています。

## 変更の背景

この変更の背景には、OS X 10.10 Yosemiteのファイルシステム関連のシステムコールにおける特定のバグが存在します。Go言語の標準ライブラリ、特に`os`パッケージや`io/ioutil`パッケージは、内部的にOSの提供するシステムコール（この場合はディレクトリの内容を読み取るための`getdirentries64`）を利用しています。

通常、ディレクトリの読み取りは、ディレクトリ内のエントリを順次取得し、全てのエントリを読み終えるとEOF（End Of File）を示す値を返すという挙動をします。EOFに達した後に再度読み取りを試みても、通常は引き続きEOFが返されるべきです。

しかし、OS X 10.10 Yosemiteでは、以下のような特殊なシナリオでこの期待される挙動が破綻しました。

1.  **小さなディレクトリ**: ディレクトリの内容が非常に小さく、`getdirentries64`システムコール1回で全てのエントリが読み取れてしまうようなディレクトリ。これは、ディレクトリのデータがファイルシステムブロックの境界をまたがず、かつ`getdirentries64`が一度に読み取るバッファサイズ（通常は4KB）に収まるような場合を指します。
2.  **EOF到達後のファイル削除**: ディレクトリの内容を全て読み取り、EOFに達したとシステムが認識した後、そのディレクトリ内のファイルが外部から削除される。
3.  **再度の読み取り**: その後、同じファイルディスクリプタを使って再度ディレクトリの読み取りを試みる。

このシナリオにおいて、OS X 10.10は通常返されるべきEOFではなく、`EINVAL`（Invalid argument: 不正な引数）または`ENOENT`（No such file or directory: そのようなファイルまたはディレクトリはない）というエラーを返していました。これらのエラーは、Goプログラムにとっては予期せぬものであり、ディレクトリの読み取り処理が異常終了したり、クラッシュしたりする原因となっていました。

Goの`syscall`パッケージは、OSのシステムコールを直接ラップしているため、このようなOS側のバグがGoプログラムに直接影響を与えます。このバグは、Goのテストスイートである`all.bash`がOS X 10.10上で失敗する原因となっていました。Go開発チームは、このOSのバグを回避し、Goプログラムが安定して動作するようにするために、このコミットで修正を導入する必要がありました。

Appleへのバグ報告が試みられたものの、Feedback Assistantの不具合により報告ができなかったという経緯も、このコミットの背景として特筆すべき点です。これは、Go開発チームが自ら回避策を実装する必要があった状況を示しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

### 1. システムコール (System Call)

システムコールは、ユーザー空間で動作するプログラムが、カーネル空間で動作するOSの機能（ファイルI/O、メモリ管理、プロセス管理など）を利用するためのインターフェースです。プログラムは直接ハードウェアにアクセスできないため、OSが提供するシステムコールを介して間接的にハードウェアリソースを操作します。

### 2. `getdirentries64`

`getdirentries64`は、macOS (およびBSD系のOS) におけるディレクトリの内容を読み取るためのシステムコールの一つです。これは、指定されたファイルディスクリプタ（開かれたディレクトリに対応）から、ディレクトリ内のエントリ（ファイルやサブディレクトリ）の情報をバッファに読み込みます。`64`は、64ビットシステムに対応していることを示唆しています。このシステムコールは、ディレクトリのオフセット（読み取り位置）を管理し、繰り返し呼び出すことでディレクトリ全体を走査します。

### 3. `readdir`

`readdir`は、C標準ライブラリ（`dirent.h`）で提供される関数で、ディレクトリの内容を読み取るための高レベルなAPIです。内部的には、`getdirentries`のような低レベルなシステムコールを呼び出して実装されています。`readdir`は、ディレクトリ内の次のエントリを`struct dirent`構造体として返します。全てのエントリを読み終えるとNULLを返し、エラーが発生した場合はNULLを返し、`errno`を設定します。

### 4. `EINVAL` (Invalid argument)

`EINVAL`は、システムコールやライブラリ関数に渡された引数が無効であることを示すエラーコードです。例えば、ファイルディスクリプタが不正であったり、バッファサイズが不適切であったりする場合に返されることがあります。

### 5. `ENOENT` (No such file or directory)

`ENOENT`は、指定されたファイルやディレクトリが存在しないことを示すエラーコードです。ファイルを開こうとしたが存在しなかった場合や、パスの途中のディレクトリが存在しなかった場合などに返されます。

### 6. EOF (End Of File)

EOFは、ファイルやストリームの終端に達したことを示す概念です。ファイル読み取り操作において、読み取るべきデータがもう存在しない場合にEOFが通知されます。ディレクトリの読み取りにおいても、全てのエントリを読み終えた場合にEOFの状態となります。

### 7. Go言語の`syscall`パッケージ

Go言語の`syscall`パッケージは、OSのシステムコールへの低レベルなインターフェースを提供します。これにより、Goプログラムから直接OSの機能を利用できます。このパッケージはOSに依存する部分が多く、各OSのシステムコールAPIに合わせて実装されています。`syscall.ReadDirent`関数は、内部的にOS固有のディレクトリ読み取りシステムコール（macOSでは`getdirentries64`）を呼び出しています。

### 8. `runtime.GOOS`

`runtime.GOOS`は、Go言語の標準ライブラリ`runtime`パッケージで提供される定数で、プログラムが実行されているオペレーティングシステムの名前（例: "linux", "darwin", "windows"など）を表します。これにより、OSに依存するコードを条件分岐で記述することができます。

## 技術的詳細

このコミットが対処している問題は、OS X 10.10 Yosemiteの`getdirentries64`システムコールにおける、特定の条件下での異常なエラー挙動です。

通常、ディレクトリの読み取りは、`getdirentries64`を繰り返し呼び出すことで行われます。ディレクトリ内の全てのエントリを読み終えると、`getdirentries64`は読み取ったバイト数として0を返し、これはEOF（End Of File）を示します。その後、再度`getdirentries64`を呼び出しても、引き続き0（EOF）が返されることが期待されます。

しかし、OS X 10.10では、以下の条件が揃った場合にこの期待される挙動が破綻します。

1.  **ディレクトリのサイズ**: ディレクトリが非常に小さく、その内容（エントリ情報）が`getdirentries64`の1回の呼び出しで全て読み取れてしまう場合。コミットメッセージでは「単一の`getdirentries64`呼び出しで返されるディレクトリ」と表現されています。これは、ディレクトリのデータがファイルシステムブロックの境界をまたがず、かつ`getdirentries64`が一度に読み取るバッファサイズ（通常は4KB）に収まるような場合を指します。
2.  **EOF到達後のファイル削除**: ディレクトリの内容を全て読み取り、`getdireentires64`が0（EOF）を返した後、そのディレクトリ内のファイルが別のプロセスやスレッドによって削除された場合。
3.  **EOF後の再読み取り**: その後、同じファイルディスクリプタを使用して再度`getdirentries64`を呼び出すと、通常返されるべき0（EOF）ではなく、`EINVAL`または`ENOENT`というエラーが返されます。どちらのエラーが返されるかは、ディレクトリ内の具体的なデータ（削除されたファイルの種類や数など）に依存し、データによって決定論的に決まります。

この挙動は、Goの`syscall`パッケージが`getdirentries64`を呼び出す際に問題を引き起こします。Goの`syscall.ReadDirent`関数は、ディレクトリの読み取りがEOFに達したことを示すために、エラーを返さずに読み取ったバイト数として0を返すことを期待しています。しかし、OS X 10.10のバグにより`EINVAL`や`ENOENT`が返されると、Goプログラムはこれを予期せぬエラーとして処理し、ディレクトリの走査が中断されたり、エラーハンドリングロジックが誤動作したりする可能性がありました。

コミットメッセージに記載されているC言語の再現プログラムは、このバグを明確に示しています。このプログラムは、一時ディレクトリを作成し、その中にファイルを作成します。そして、`opendir`と`readdir`を使ってディレクトリを読み取ります。`readdir`がEOFを返した後、ファイルが削除されると、その後の`readdir`呼び出しが`ENOENT`または`EINVAL`を返すことを示しています。

この問題は、Goの`os`パッケージがディレクトリを走査する際に、EOFに達した後に再度読み取りを試みる可能性があるために顕在化しました。理想的には、`os`パッケージ側でEOF後の余分な読み取りを避けるように変更することも考えられますが、それはより複雑な変更となるため、このコミットでは`syscall`レイヤーでOSのバグを吸収するアプローチが取られました。つまり、`EINVAL`や`ENOENT`が返された場合でも、それをEOFとして扱うことで、Goプログラムが正常に動作するようにしています。

## コアとなるコードの解説

変更は`ReadDirent`関数内で行われています。

1.  **元のコード**:
    ```go
    return Getdirentries(fd, buf, base)
    ```
    これは、`Getdirentries`システムコールを直接呼び出し、その戻り値（読み取ったバイト数`n`とエラー`err`）をそのまま返していました。

2.  **変更後のコード**:
    ```go
    n, err = Getdirentries(fd, buf, base)

    // On OS X 10.10 Yosemite, ... (コメントは省略)
    if runtime.GOOS == "darwin" && (err == EINVAL || err == ENOENT) {
        err = nil
    }

    return
    ```
    変更後では、まず`Getdirentries`の呼び出し結果を`n`と`err`変数に格納します。
    その後に、以下の条件分岐が追加されています。

    *   `runtime.GOOS == "darwin"`: 現在のOSがmacOS（旧OS X）であるかどうかをチェックします。この問題はmacOS特有のバグであるため、他のOSではこの処理は不要です。
    *   `(err == EINVAL || err == ENOENT)`: `Getdirentries`から返されたエラーが`EINVAL`または`ENOENT`のいずれかであるかをチェックします。これらは、OS X 10.10のバグによってEOFの代わりに返される可能性のあるエラーコードです。

    もし上記の2つの条件が両方とも真であれば、つまり「macOS上で、かつ`EINVAL`または`ENOENT`エラーが返された場合」に、`err = nil`とエラーを`nil`（エラーなし）に上書きしています。

この修正の意図は、OS X 10.10のバグによって`EINVAL`や`ENOENT`が返された場合でも、Goの`syscall`パッケージがそれを正常なEOFとして扱うようにすることです。これにより、上位の`os`パッケージなどがこれらのエラーを予期せぬものとして処理し、プログラムが異常終了するのを防ぎます。結果として、GoプログラムはOSのバグの影響を受けることなく、ディレクトリの読み取りを継続できるようになります。

この修正は、OSのバグに対するワークアラウンド（回避策）であり、根本的なOSのバグ自体を修正するものではありません。しかし、Goプログラムの安定性を確保するためには効果的なアプローチです。

# [インデックス 27302] ファイルの概要

このコミットは、Goコンパイラの`cmd/compile`パッケージにおける`varexpr`関数が`ODOT`（セレクタ式、例: `s.f`）ノードを処理する方法のバグを修正します。以前は`ODOT`ノードに対して常に`false`を返していましたが、この変更により、左側の式が変数式である場合に`ODOT`も変数式として正しく評価されるようになります。これはコンパイラのセマンティクスを改善し、コードの正確性を向上させるためのクリーンアップです。

## コミット

```
cmd/compile: fix varexpr handling of ODOT

For a long time varexpr has handled ODOT incorrectly: it has always
returned false. Before https://golang.org/cl/20890 this has been
because an ODOT had a Right field with an ONAME with no Class, for which
varexpr returns false. CL 20890 preserved the behavior of varexpr for
ODOT, so that the change would pass toolstash -cmp.

This CL fixes varexpr so that ODOT can return true in some cases. This
breaks toolstash -cmp. While the changed compiler allocates temporary

examples where the generated code is different, other than using
different stack offsets and, in some cases, registers. It seems that
other parts of the compiler will force the ODOT into a temporary anyhow.

Still, this change is clearly correct, and is a minor compiler cleanup.
```

## 変更の背景

このコミットは、Goコンパイラの`varexpr`関数における長年の問題を修正することを目的としています。`varexpr`関数は、与えられた式が「変数式」であるかどうかを判断する役割を担っています。変数式とは、メモリ上の特定の場所を直接参照する式（例: 変数、構造体のフィールド、配列の要素など）を指します。

問題は、`ODOT`ノード（構造体のフィールドアクセスなど、セレクタ式を表すASTノード）が`varexpr`によって常に`false`と評価されていた点にありました。これは、`ODOT`ノードの右側のフィールドが`ONAME`（名前）ノードであり、その`Class`フィールドが設定されていない場合に`varexpr`が`false`を返すという、以前の実装の副作用によるものでした。

以前のコミット（`https://golang.org/cl/20890`）では、この`ODOT`に対する`varexpr`の誤った挙動が意図的に維持されていました。これは、`toolstash -cmp`というコンパイラの変更が生成コードに影響を与えないことを検証するツールを通過させるためでした。しかし、この挙動はセマンティクス的に正しくありませんでした。

今回のコミットは、この誤った挙動を修正し、`ODOT`が特定の条件下で`true`を返すようにします。これにより`toolstash -cmp`は失敗する可能性がありますが、コミットの作者は、生成されるコード自体には大きな違いはなく、一時変数の割り当て順序やスタックオフセット、レジスタの使用が異なる程度であると述べています。また、コンパイラの他の部分が`ODOT`を一時変数に強制的に変換するため、最終的な実行コードへの影響は限定的であると推測されています。

この変更は、コンパイラの「明らかに正しい」修正であり、「マイナーなクリーンアップ」として位置づけられています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラに関する基本的な概念を理解しておく必要があります。

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換するプログラムです。`src/cmd/compile/internal/gc`ディレクトリには、コンパイラの主要なロジックが含まれています。
*   **AST (Abstract Syntax Tree - 抽象構文木)**: コンパイラがソースコードを解析する際に生成する、プログラムの構造を木構造で表現したものです。各ノードは、変数、関数呼び出し、演算子などのプログラム要素に対応します。
*   **`Node`構造体**: Goコンパイラ内でASTの各ノードを表すデータ構造です。`Op`フィールドはノードの種類（操作コード）を示し、`Left`や`Right`フィールドは子ノードへのポインタを持ちます。
*   **`varexpr`関数**: `src/cmd/compile/internal/gc/walk.go`に定義されている関数で、与えられた`Node`が「変数式 (variable expression)」であるかどうかを判定します。変数式とは、その評価結果がメモリ上の特定の場所（l-value）を指す式のことです。例えば、`x`、`p.field`、`a[i]`などは変数式ですが、`x + y`や`f()`は変数式ではありません。
*   **`ODOT`ノード**: ASTの操作コード（`Op`）の一つで、セレクタ式（例: `structVar.field`、`interfaceVar.Method`）を表します。このコミットでは、特に構造体のフィールドアクセスに関連しています。
*   **`ONAME`ノード**: ASTの操作コードの一つで、識別子（変数名、関数名など）を表します。
*   **`n.Class`**: `ONAME`ノードが持つフィールドで、その名前のストレージクラス（例: `PEXTERN` (外部変数), `PAUTO` (自動変数/スタック変数), `PPARAM` (関数パラメータ) など）を示します。`varexpr`関数は、この`Class`フィールドの値に基づいて、`ONAME`が変数式であるかどうかを判断することがあります。
*   **`toolstash -cmp`**: Goコンパイラの開発で用いられるツールの一つです。コンパイラの変更が、既存のGoプログラムのコンパイル結果（生成されるバイナリコード）に意図しない変更をもたらさないことを検証するために使用されます。変更前後のコンパイラで同じソースコードをコンパイルし、生成されたバイナリを比較することで、互換性や安定性を確認します。

## 技術的詳細

このコミットの核心は、`varexpr`関数が`ODOT`ノードを処理するロジックの修正にあります。

変更前、`varexpr`関数内の`ODOT`ケースは以下のようになっていました。

```go
case ODOT: // but not ODOTPTR
	// The original code always returned false for ODOT,
	// because n.Right would be an ONAME with n.Class not set.
	// TODO(iant): Fix this to remove "&& false".
	return varexpr(n.Left) && false
```

このコードは、`ODOT`ノードの左側の式（`n.Left`）が変数式であるかどうかを`varexpr(n.Left)`で評価しつつも、最終的に`&& false`によって常に`false`を返していました。コメントにもあるように、これは元々`n.Right`が`ONAME`で`n.Class`が設定されていない場合に`varexpr`が`false`を返すという挙動に起因していました。つまり、`s.f`のような式において、`f`（`n.Right`）が`ONAME`であり、その`Class`が未設定であるために`varexpr(n.Right)`が`false`を返し、結果として`ODOT`全体が`false`と判断されていたのです。

以前のCL 20890では、この誤った挙動が`toolstash -cmp`を通過させるために意図的に維持されました。しかし、これは`s.f`のようなフィールドアクセスが、`s`が変数であれば`s.f`も変数式であるべきという直感的なセマンティクスに反していました。

今回のコミットでは、この`&& false`が削除され、`ODOT`の処理が以下のように変更されました。

```go
case ODOT: // but not ODOTPTR
	return varexpr(n.Left)
```

この変更により、`ODOT`ノードが変数式であるかどうかは、その左側の式（`n.Left`、例えば`s.f`における`s`）が変数式であるかどうかにのみ依存するようになりました。もし`s`が変数式であれば、`s.f`も変数式として正しく扱われます。これは、構造体のフィールドアクセスが、その構造体自体がメモリ上の場所を指している場合に、そのフィールドもメモリ上の場所を指すという、より正確なセマンティクスを反映しています。

この修正は`toolstash -cmp`を壊す可能性がありますが、これはコンパイラが一時変数を割り当てる順序や、スタックオフセット、レジスタの使用方法が変更されるためです。しかし、コミットの作者は、生成される最終的な機械語コード自体には実質的な違いが見られないと述べています。これは、コンパイラの他の最適化パスが、`ODOT`ノードを最終的に一時変数に変換する傾向があるためと考えられます。したがって、この変更はコンパイラの内部的な正確性を向上させるものであり、最終的な実行性能や挙動に悪影響を与えるものではないと判断されています。

## コアとなるコードの解説

変更前のコード `return varexpr(n.Left) && false` は、`ODOT`ノード（例: `s.f`）が変数式であるかどうかを判断する際に、常に`false`を返していました。これは、`n.Left`（`s`の部分）が変数式であるかどうかに関わらず、論理AND演算子`&&`の右側が`false`であるため、結果全体が`false`になるためです。この挙動は、`s`が変数であっても`s.f`が変数式として認識されないという、セマンティクス上の誤りを含んでいました。

変更後のコード `return varexpr(n.Left)` は、`ODOT`ノードが変数式であるかどうかを、その左側の式（`n.Left`）が変数式であるかどうかに直接依存させるように修正しました。これにより、例えば`s`がスタック上の変数である場合、`varexpr(s)`は`true`を返し、結果として`s.f`も変数式として`true`を返すようになります。これは、構造体のフィールドアクセスが、そのベースとなる構造体自体がメモリ上の場所を指している場合に、そのフィールドもメモリ上の場所を指すという、Go言語のセマンティクスに合致する正しい挙動です。

この修正は、コンパイラが式の性質をより正確に理解し、その後のコード生成や最適化の段階でより適切な判断を下せるようにするための重要なクリーンアップです。

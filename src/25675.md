## 元コミット内容

このコミットは、Goコンパイラのソースコード内の `TODO` コメントに、関連するGo Issueトラッカーの番号を追加するものです。コードの動作に影響を与えるような機能的な変更は含まれておらず、純粋にコメントの更新のみが行われています。これは、将来的な開発やメンテナンスの際に、特定のTODO項目がどのような背景や議論に基づいて存在しているのかを明確にするための改善です。

## 変更の背景

大規模なソフトウェアプロジェクト、特にGoコンパイラのような複雑なシステムでは、開発中に一時的な解決策、未実装の機能、将来的な改善点などを `TODO` コメントとしてコード内に残すことがよくあります。しかし、時間が経つにつれて、これらの `TODO` が何を指しているのか、なぜそこに存在するのか、どの程度の優先度で対応すべきなのかが不明確になることがあります。

このコミットの背景には、これらの `TODO` コメントの管理を改善し、技術的負債の追跡を容易にする目的があります。特定のIssue番号を `TODO` コメントに関連付けることで、開発者はその `TODO` がGoのIssueトラッカー上のどの項目に対応しているのかを一目で把握できます。これにより、関連する議論、決定、進捗状況などを迅速に確認できるようになり、将来的な作業の効率化と透明性の向上が図られます。

特に、Goコンパイラは継続的に進化しており、`newexport` や `oldparser` のようなフラグが示すように、主要なコンポーネントの移行期には多くの暫定的なコードや改善点が生まれます。これらの項目をIssueトラッカーと連携させることは、プロジェクト全体の健全性を保つ上で非常に重要です。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Go言語のプログラムは、`go build` コマンドによってコンパイルされ、実行可能なバイナリが生成されます。このコンパイル処理の中核を担うのが `cmd/compile` パッケージです。`cmd/compile` は、Goのソースコードを機械語に変換する役割を持ち、以下の主要なフェーズを含みます。

*   **字句解析 (Lexical Analysis)**: ソースコードをトークン（キーワード、識別子、演算子など）のストリームに分解します。
*   **構文解析 (Syntactic Analysis)**: トークンのストリームを解析し、プログラムの構造を抽象構文木 (AST) として構築します。
*   **型チェック (Type Checking)**: ASTを走査し、型の整合性を検証します。
*   **最適化 (Optimization)**: 生成されるコードの効率を向上させます。
*   **コード生成 (Code Generation)**: ASTからターゲットアーキテクチャの機械語コードを生成します。

このコミットで変更された `src/cmd/compile/internal/gc/lex.go` と `src/cmd/compile/internal/gc/parser.go` は、それぞれ字句解析と構文解析の処理を担当するGoコンパイラの非常に重要な部分です。

### `TODO` コメント

`TODO` コメントは、ソフトウェア開発において、将来的に実装すべき機能、修正すべきバグ、改善すべき点、または一時的な回避策などを示すためにコード内に記述されるマーカーです。通常、`TODO` の後に担当者名や日付、簡単な説明が続きます。

例: `// TODO(username): Implement this feature later.`

このコミットでは、`TODO(gri)` という形式が使われています。これは、Go言語の共同設計者の一人であるRobert Griesemer氏が担当または関与している `TODO` 項目であることを示唆しています。

### Issue Tracking System

Issue Tracking System (ITS) は、ソフトウェアプロジェクトにおけるバグ、機能要求、タスク、改善提案などを記録、追跡、管理するためのシステムです。Goプロジェクトでは、主に [Go Issue Tracker](https://go.dev/issue) やGitHub Issuesが利用されます。各Issueには一意の番号が割り当てられ、そのIssueに関する議論、ステータス、担当者、関連するコミットなどが一元的に管理されます。

### `newexport` と `oldparser` フラグ

Goコンパイラは、その歴史の中で何度か大きな内部構造の変更を経験しています。
*   `newexport`: Goコンパイラがパッケージの情報をエクスポート（他のパッケージから利用可能にする）する際の形式に関するフラグです。新しいエクスポート形式への移行は、コンパイラの性能や機能の改善を目的として行われました。
*   `oldparser`: Goコンパイラの構文解析器（パーサー）に関するフラグです。Goコンパイラは、初期のyaccベースのパーサーから、より柔軟でメンテナンスしやすい再帰下降型パーサーへと移行しました。`oldparser` フラグは、この移行期間中に古いパーサーを使用するためのオプションとして存在していました。

これらのフラグに関連する `TODO` コメントは、コンパイラの重要な内部変更が進行中であったり、古いコンポーネントの削除が計画されていたりする時期に記述されたものです。

## コアとなるコードの解説

上記の変更箇所は、Goコンパイラの字句解析器 (`lex.go`) と構文解析器 (`parser.go`) 内の `TODO` コメントに、対応するIssue番号を追加しています。

### `lex.go` の変更点

*   `newexport` と `oldparser` フラグに関する `TODO` に、それぞれ `(issue 13241)` と `(issue 13240)` が追加されました。
    *   `newexport` は新しいエクスポート形式への移行、`oldparser` は古いパーサーの廃止に関連するものです。これらの `TODO` は、コンパイラの重要な内部コンポーネントの進化とクリーンアップの計画を示しています。Issue番号が付与されたことで、これらのフラグが最終的に削除されるべき理由や、そのための具体的なタスクがIssueトラッカーで追跡されていることが明確になります。
*   `oldparser` の使用に関するコメントにも `(issue 13240)` が追加されています。これは、新しい再帰下降型パーサーへの移行が完了した際に、この暫定的なコードを削除する必要があることを示しています。

### `parser.go` の変更点

`parser.go` では、非常に多くの `TODO` コメントに `(issue 13242)`, `(issue 13243)`, `(issue 13244)`, `(issue 13245)` が追加されています。これらの `TODO` は、主に新しいパーサーの設計、実装、および既存のyaccベースのパーサーとの互換性に関する様々な課題を指しています。

具体的な例をいくつか挙げます。

*   `// TODO(gri) Once we handle imports w/o redirecting the underlying source of the lexer we can get rid of these. They are here for // compatibility with the existing yacc-based parser setup (issue 13242).`
    *   これは、インポート処理における字句解析器の挙動に関する課題と、yaccベースのパーサーとの互換性を保つための暫定的なコードであることを示しています。Issue 13242でこの問題が追跡されています。
*   `// TODO(gri) figure out why yyTokname doesn't work for us as expected // (issue 13243)`
    *   `yyTokname` はyaccパーサーに関連するトークン名取得のメカニズムであり、新しいパーサーでの挙動に問題があったことを示唆しています。Issue 13243でこの調査と修正が追跡されています。
*   `// TODO(gri) imports screw up p.indent - fix this // (issue 13243)`
    *   インデント処理がインポートによって乱れる問題もIssue 13243で追跡されています。これは、パーサーのデバッグ出力やエラー報告の正確性に影響を与える可能性があります。
*   `// TODO(gri) should have lexer return this info - no need for separate lookup // (issue 13244)`
    *   これは、字句解析器がより多くの情報（この場合は演算子の優先順位など）を直接返すように改善すべきだという提案です。これにより、構文解析器での追加のルックアップが不要になり、効率が向上する可能性があります。Issue 13244でこの改善が追跡されています。
*   `// TODO(gri) possible conflict here: both cases may start with '@' per grammar // (issue 13245).`
    *   これは、文法上の曖昧さや衝突の可能性を示しており、パーサーの正確性や堅牢性に関わる重要な問題です。Issue 13245でこの問題の解決が追跡されています。

これらの変更は、Goコンパイラの開発者が、コードベース内の未解決の課題や将来の改善点を体系的に管理しようとしていることを明確に示しています。Issue番号を付与することで、これらの `TODO` が単なるコメントではなく、具体的な開発タスクとして認識され、追跡されるようになります。

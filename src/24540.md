## 変更の背景

このコミットの背景には、GoコンパイラのSSAバックエンドにおける値の書き換え処理の正確性に関する問題がありました。SSA形式では、各変数は一度だけ定義されるという特性を持ちます。コンパイラがコードを最適化する際、既存のSSA値を新しいSSA値に書き換えることがあります。このとき、新しく生成されたSSA値がどの基本ブロックに属するかを正しく決定することが非常に重要です。

以前の実装では、新しい値が「制御値（control value）」が属するブロックに配置される可能性がありました。制御値とは、条件分岐などの制御フローを決定する値のことです。しかし、この制御値が、実際に書き換えが行われている現在のブロックよりも、ドミネーターツリー（支配木）上で何ブロックも上位にあるブロックに属している場合がありました。

このような状況で新しい値を制御値のブロックに配置してしまうと、新しい値が定義される前に使用される可能性が生じ、SSAの原則（すべての使用は定義によって支配される）に違反する可能性があります。これは、コンパイラの最適化パスで誤ったコードが生成されたり、予期せぬバグを引き起こしたりする原因となります。このコミットは、この潜在的な問題を修正し、新しく生成されるSSA値が常に書き換えが行われている現在のブロックに正しく関連付けられるようにすることを目的としています。

## 前提知識の解説

### SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの最適化において広く用いられる中間表現（IR）の一種です。その主要な特性は以下の通りです。

*   **単一割り当て**: 各変数はプログラム内で一度だけ定義（割り当て）されます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が容易になります。
*   **Φ関数 (Phi function)**: 複数の制御フローパスが合流する地点（例: if-else文の終わり、ループの終わり）で、同じ変数に対する複数の定義を結合するために使用されます。Φ関数は、どのパスから来たかに応じて適切な値を選択します。
*   **最適化の容易さ**: SSA形式は、定数伝播、共通部分式除去、デッドコード除去などの様々な最適化を効率的に実行するための基盤を提供します。

### ドミネーターツリー (Dominator Tree)

ドミネーターツリーは、プログラムの制御フローグラフ（CFG）から派生するツリー構造です。

*   **ドミネーター (Dominator)**: ある基本ブロック `A` が別の基本ブロック `B` をドミネートするとは、`A` から `B` へのすべてのパスが `A` を通過する場合を指します。`A` は `B` の「支配者」であると言えます。
*   **即時ドミネーター (Immediate Dominator)**: `A` が `B` をドミネートし、`A` と `B` の間に `B` をドミネートする他のブロックが存在しない場合、`A` は `B` の即時ドミネーターです。
*   **ドミネーターツリーの構造**: 各ブロックは、その即時ドミネーターを親とするツリー構造を形成します。プログラムのエントリブロックがツリーのルートになります。ドミネーターツリーは、変数のスコープや定義-使用チェーンを理解する上で非常に重要です。ある値が定義されたブロックは、その値が使用されるすべてのブロックをドミネートする必要があります。

### GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木（AST）に変換した後、中間表現としてSSA形式を使用します。このSSA形式に対して様々な最適化が適用され、最終的に機械語コードが生成されます。`cmd/compile/internal/ssa`パッケージは、このSSAバックエンドの中核をなす部分です。

*   **`Value`**: SSA形式における単一の計算結果を表すオブジェクト。オペレーション（`Op`）、型（`Type`）、引数（`Args`）、補助情報（`Aux`、`AuxInt`）などを持つ。
*   **`Block`**: 基本ブロックを表すオブジェクト。SSA値のリスト、制御フロー情報（後続ブロック、先行ブロック）、ブロックの種類（`Kind`）などを持つ。
*   **`rewriteValue` 関数**: 特定のSSA値（`Value`）を、より効率的な別のSSA値のシーケンスに書き換えるための関数。これは、アーキテクチャ固有の最適化や、より低レベルの命令への変換を行う際に使用されます。
*   **`NewValue0` メソッド**: 指定されたブロック内に新しいSSA値を作成するためのメソッド。

## 技術的詳細

このコミットが修正しようとしている問題は、SSA形式の健全性（soundness）に関わるものです。SSA形式では、ある値が使用されるすべての場所は、その値が定義されたブロックによって支配されている必要があります。これは「支配性条件（dominance property）」と呼ばれます。

`rewriteValue`関数内で新しいSSA値が生成される際、以前は`v.Block.NewValue0(...)`のように、書き換え対象の`v`が属するブロックを直接使用していました。しかし、`v`自体が、そのオペレーションの制御フローを決定する「制御値」である場合、その制御値が属するブロック（`v.Block`）は、実際に書き換えが行われている現在のコンテキストのブロックとは異なる、ドミネーターツリー上のより上位のブロックである可能性がありました。

例えば、あるブロック`B1`で条件分岐`if cond { ... }`があり、`cond`が`B1`の親ブロック`B0`で計算された値だったとします。`B1`内で`cond`に関連する値を書き換える際に、新しい値を`cond`が属する`B0`に配置してしまうと、`B1`以降のブロックでその新しい値を使用しようとしたときに、`B1`が`B0`を支配しているわけではないため、支配性条件が破綻する可能性があります。

このコミットでは、この問題を解決するために、`rewriteValue`関数が実行されている「現在のブロック」を明示的に`b`という変数に格納し、新しいSSA値を作成する際には常にこの`b`を使用するように変更しました。これにより、新しく生成される値は、その値が実際に必要とされる（そして定義されるべき）ブロックに確実に配置されるようになります。

`rulegen.go`は、`rewriteValue`関数のような書き換えルールを自動生成するためのツールです。このツール自体が、生成するコード内で`v.Block`ではなく`b`を使用するように変更されたため、結果として`rewriteAMD64.go`や`rewritegeneric.go`といった生成されたファイルにもこの修正が反映されています。

## コアとなるコードの変更箇所

変更は主に以下のパターンに集約されます。

1.  **`rulegen.go`**:
    *   `func genRules(arch arch)` 関数内で、`rewriteValue%s`関数の冒頭に`b := v.Block`という行が追加されました。
    *   `fmt.Fprintf(w, "v.Block.Func.removePredecessor(b, %s)\\n", succ)` が `fmt.Fprintf(w, "b.Func.removePredecessor(b, %s)\\n", succ)` に変更されました。
    *   `fmt.Fprintf(w, "%s := v.Block.NewValue0(v.Line, %s, TypeInvalid)\\n", v, opName(s[0], arch))` が `fmt.Fprintf(w, "%s := b.NewValue0(v.Line, %s, TypeInvalid)\\n", v, opName(s[0], arch))` に変更されました。

2.  **`rewriteAMD64.go` および `rewritegeneric.go`**:
    *   `func rewriteValueAMD64(v *Value, config *Config) bool` および `func rewriteValuegeneric(v *Value, config *Config) bool` の冒頭に `b := v.Block` が追加されました。
    *   ファイル全体で、`v.Block.NewValue0(...)` の呼び出しが `b.NewValue0(...)` に変更されました。
    *   `rewriteBlockAMD64` および `rewriteBlockgeneric` 関数内でも、`v.Block.Func.removePredecessor(b, no)` が `b.Func.removePredecessor(b, no)` に変更されています。

## コアとなるコードの解説

このコミットの核心は、SSA値の生成時に、その値が属するべき基本ブロックを正確に指定することです。

以前のコードでは、`v.Block`という表現が使われていました。ここで`v`は現在書き換えの対象となっているSSA値です。しかし、`v.Block`が指すブロックは、必ずしも現在処理中のコンテキスト（つまり、新しい値が生成されるべきブロック）と一致するとは限りませんでした。特に、`v`が制御値であり、その定義が現在のブロックよりもドミネーターツリー上で上位にあるブロックで行われている場合、`v.Block`は現在のブロックの祖先ブロックを指すことになります。

この修正では、`rewriteValue`関数の開始時に`b := v.Block`という行を追加することで、`v`が属するブロックを`b`というローカル変数に保存します。そして、新しいSSA値を作成する際には、`v.Block.NewValue0(...)`ではなく、このローカル変数`b`を使って`b.NewValue0(...)`と呼び出すように変更しています。

これにより、新しく生成されるSSA値は、`rewriteValue`関数が呼び出された時点での`v`が属するブロック、すなわち書き換えが行われている「現在のブロック」に確実に配置されるようになります。これは、SSA形式の支配性条件を維持し、コンパイラの健全な動作を保証するために不可欠な変更です。

`removePredecessor`の呼び出しも同様に`v.Block`から`b`に変更されていますが、これはブロックの先行者リストを操作する際にも、現在のコンテキストのブロックを正確に参照するためです。

この変更は、`rulegen.go`というコード生成ツールによって自動生成されるファイル（`rewriteAMD64.go`や`rewritegeneric.go`など）にも適用されるため、手動で多数のファイルを修正する手間が省かれ、一貫性が保たれています。

# [インデックス 20418] ファイルの概要

このコミットは、Goランタイムのスタック管理に関連する変更です。主に以下のファイルに影響を与えています。

*   `src/pkg/runtime/stack.go`: Goランタイムのスタック管理に関する定数やロジックが定義されているファイルです。このコミットでは、以前のスタックレイアウトに関する詳細なコメントブロックが削除されていますが、主要なロジックの変更は別のファイルで行われています。
*   `src/pkg/runtime/stack.h`: Goランタイムのスタック関連の定数がC言語のヘッダーファイルとして定義されています。このファイルでスタックガードのサイズが変更されています。
*   `test/nosplit.go`: `NOSPLIT`関数（スタック分割を行わない関数）のテストケースが含まれるファイルです。スタックガードの変更に合わせて、テストの期待値が更新されています。

## コミット

このコミットは、Goランタイムにおけるスタック分割の制限を再度引き上げるものです。特に、`NOSPLIT`関数が利用できるスタック領域の予約サイズを192バイトから384バイトに増加させています。これは、SolarisやWindowsのような非Unixシステムにおいて、システムコールがより多くのスタック領域を必要とし、かつエラー時に`runtime.throw`を呼び出すような複雑な処理を行う場合に、スタック不足が発生する問題を一時的に回避するための措置です。

## 変更の背景

この変更の主な背景は、Goランタイムが特定のオペレーティングシステム（特にSolarisとWindows）で直面していたスタック不足の問題です。

Goの関数呼び出しでは、通常、スタックの残量が少なくなると「スタック分割（stack split）」と呼ばれるメカニズムが働き、より大きなスタックを確保して現在のスタックの内容を新しいスタックにコピーします。しかし、一部の低レベルなランタイム関数やシステムコールをラップする関数は、このスタック分割のチェックを行わないように設計されています。これらは`NOSPLIT`関数と呼ばれ、スタック分割のオーバーヘッドを避けるために、非常に限られたスタック領域内で動作することが期待されます。

問題は、SolarisやWindowsのような非Unixシステムにおいて、これらの`NOSPLIT`関数が内部的に呼び出すシステムコールが、Goランタイムが想定していたよりも多くのスタック領域を消費することでした。さらに悪いことに、これらのシステムコールが失敗した場合に`runtime.throw`（Goのパニックに相当するランタイムエラー）を呼び出すような複雑な処理を行うことがあり、その処理自体も追加のスタックを必要としました。

開発チームは、これらのシステムコールや関連するランタイムコードを、より少ないスタックで動作するように書き直す時間がないと判断しました。そのため、一時的な解決策として、`NOSPLIT`関数に予約されるスタック領域を増やすことで、スタックオーバーフローによるクラッシュを防ぐことを選択しました。コミットメッセージには「I'm not happy about this, but it's still a small amount.」とあり、これは理想的な解決策ではないものの、緊急の対応として許容できる範囲であるという開発者の見解が示されています。

将来的には、Goランタイムがスタックの拡張に「コピーするスタック（copying stacks）」のみを使用するようになることで、デフォルトのスタックサイズを8KBから4KBに削減できる見込みがあり、今回のスタック予約の増加による影響を相殺できると述べられています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスタック管理に関するいくつかの重要な概念を理解する必要があります。

1.  **Goroutineスタック**: Goの各goroutineは独自のスタックを持っています。このスタックは、関数呼び出しの引数、ローカル変数、リターンアドレスなどを格納するために使用されます。Goのスタックは、必要に応じて動的にサイズが変更される「可変長スタック」です。
2.  **スタック分割 (Stack Splitting)**: Goの関数が呼び出される際、ランタイムは現在のスタックポインタがスタックガード（`g->stackguard`）と呼ばれる境界を超えていないかチェックします。スタックポインタがこの境界に近づくと、スタックが不足していると判断され、より大きなスタックを確保して現在のスタックの内容を新しいスタックにコピーする処理（スタック分割）が行われます。これにより、スタックオーバーフローを防ぎ、効率的なメモリ利用を実現しています。
3.  **`stackguard`**: 各goroutineの`g`構造体には`stackguard`フィールドがあり、これはスタックの安全な下限を示すポインタです。関数呼び出し時にスタックポインタがこの`stackguard`を下回ると、スタックオーバーフローの危険があるため、スタック分割処理がトリガーされます。
4.  **`NOSPLIT`関数**: Goランタイムには、スタック分割のチェックを行わない特別な関数が存在します。これらは`NOSPLIT`関数と呼ばれ、アセンブリ言語で書かれた低レベルな関数や、スタック分割のオーバーヘッドが許容されないクリティカルなパスで使用されます。これらの関数は、非常に限られたスタック領域内で動作することが保証されている必要があります。`NOSPLIT`関数がスタック分割チェックをスキップするため、これらの関数が使用できるスタック領域は、`stackguard`によって設定された予約領域内に収まる必要があります。
5.  **`StackGuard`と`StackSmall`**:
    *   `StackGuard`: スタックの底部から`StackGuard`バイト上に設定されるスタックガードのオフセットです。`g->stackguard`はこのオフセットに基づいて計算されます。
    *   `StackSmall`: スタック分割チェックの後、スタックポインタが`StackGuard`からどれだけ下方に突き出ても許容されるバイト数です。これは、フレームサイズが小さい関数でスタックチェックの命令数を削減するために使用されます。
6.  **スタック予約領域**: `NOSPLIT`関数が利用できるスタック領域は、実質的に`StackGuard - StackSmall`で計算されるバイト数に依存します。この領域は、スタック分割なしで安全に実行できる最大スタック使用量を示します。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムのスタック管理における`NOSPLIT`関数のスタック予約領域の調整にあります。

以前のGoランタイムでは、`NOSPLIT`関数が利用できるスタック予約領域は192バイトでした。これは、`StackGuard`と`StackSmall`の以前の値（`StackGuard = 256 + StackSystem`, `StackSmall = 64`）から計算される`StackGuard - StackSmall`に相当します（`StackSystem`はOS固有のスタック予約で、通常は0ですが、Windowsなどでは異なる値を取ります）。

しかし、SolarisやWindowsといった非Unixシステムでは、Goランタイムが内部的に呼び出すシステムコールが、この192バイトの予約領域では不足することが判明しました。特に、これらのシステムコールがエラーを報告するために`runtime.throw`を呼び出す場合、その処理自体が追加のスタックを消費し、スタックオーバーフローを引き起こす可能性がありました。

この問題を解決するため、コミットでは`NOSPLIT`予約を192バイトから384バイトに倍増させています。これは、`src/pkg/runtime/stack.h`で定義されている以下の定数の値を変更することで実現されています。

*   `StackGuard`を`256 + StackSystem`から`512 + StackSystem`に増加。
*   `StackSmall`を`64`から`128`に増加。

これにより、`StackGuard - StackSmall`の値が` (512 + StackSystem) - 128 = 384 + StackSystem`となり、`NOSPLIT`関数が利用できる実質的なスタック予約領域が384バイトに拡張されます。

この変更は、根本的な解決策ではなく、時間的制約の中で問題を回避するための「一時的な修正」であるとコミットメッセージで明言されています。理想的には、非Unixシステムでのシステムコールやエラー処理のスタック使用量を削減するためのコードリファクタリングが必要ですが、それが困難であったため、スタック予約領域を増やすという比較的簡単な方法が取られました。

コミットメッセージでは、この変更が「まだ少量」であり、将来的には「コピーするスタック」への移行が完了すれば、デフォルトのgoroutineスタックサイズを8KBから4KBに削減できるため、今回の増加分を補って余りあるメリットがあると説明されています。これは、今回の変更が短期的な問題解決のためのものであり、長期的なスタック管理の最適化計画の一部として位置づけられていることを示唆しています。

## コアとなるコードの解説

### `src/pkg/runtime/stack.h`の変更

*   **`StackGuard`の変更**: `StackGuard`は、スタックの底部からスタックガードが設定されるオフセットを定義します。この値が`256 + StackSystem`から`512 + StackSystem`に増加しました。これは、スタックガードの境界をスタックの底部からより遠ざけることを意味し、結果としてスタックオーバーフローを検出するまでの余裕を増やすことになります。
*   **`StackSmall`の変更**: `StackSmall`は、スタック分割チェック後にスタックポインタがスタックガードの下にどれだけ突き出ても許容されるバイト数を定義します。この値が`64`から`128`に増加しました。この値は、小さなフレームを持つ関数でのスタックチェックの効率化に関連しますが、`NOSPLIT`関数が利用できる実質的なスタック予約領域の計算にも影響します。

これらの変更により、`NOSPLIT`関数が利用できるスタック予約領域（`StackGuard - StackSmall`）は、以前の`(256 + StackSystem) - 64 = 192 + StackSystem`バイトから、`(512 + StackSystem) - 128 = 384 + StackSystem`バイトへと増加しました。これにより、非Unixシステムでのシステムコールやエラー処理がより多くのスタックを消費しても、スタックオーバーフローが発生しにくくなります。

### `test/nosplit.go`の変更

`test/nosplit.go`の変更は、`NOSPLIT`関数のスタック予約領域の増加に合わせて、テストケースの期待値を調整するものです。

```go
// The limit was originally 128 but is now 384.
// Instead of rewriting the test cases above, adjust
// the first stack frame to use up the extra 32 bytes.
if i == 0 {
    size += 384 - 128 // 以前は size += 192 - 128
}
```

このコードは、`NOSPLIT`関数のスタック使用量をテストする際に、新しい制限値である384バイトを考慮するようにテストロジックを更新しています。コメントにある「The limit was originally 128 but is now 384.」は、`NOSPLIT`関数のスタック使用量の「安全な」上限が128バイトから384バイトに引き上げられたことを示唆しています。これは、`StackGuard - StackSmall`の計算結果と一致します。テストでは、最初のスタックフレームのサイズを調整することで、この新しい制限内でテストが適切に動作することを確認しています。

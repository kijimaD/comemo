## 元コミット内容

`cmd/compile: for now, keep parameter numbering in binary export format`

このコミットは、Goコンパイラ (`cmd/compile`) において、バイナリのエクスポート形式でパラメータの番号付けを一時的に保持することを目的としています。本来、この番号付けはインライン化可能な関数/メソッドのパラメータにのみ必要ですが、テキスト形式とバイナリ形式でコンパイルされたコードのアセンブリダンプ間の差分を最小限に抑えるために、すべてのパラメータ名に内部的な番号付けを付けてエクスポートするよう変更されています。これは新しいエクスポート形式がデフォルトになった時点で無効化される予定の一時的な措置です。

## 変更の背景

Goコンパイラは、コンパイルされたパッケージの情報を他のパッケージが利用できるようにエクスポートするメカニズムを持っています。このエクスポート形式には、テキストベースのものとバイナリベースのものがあります。新しいバイナリ形式への移行が進められている中で、コンパイラの開発者は、新しい形式が既存の動作に与える影響を慎重に評価する必要があります。

このコミットの背景には、主に以下の理由が考えられます。

1.  **アセンブリコードの比較の容易化**: コンパイラの変更は、生成されるアセンブリコードに影響を与える可能性があります。新しいバイナリ形式の導入に伴い、既存のテキスト形式でコンパイルされたコードと、新しいバイナリ形式でコンパイルされたコードのアセンブリダンプを比較し、意図しない変更がないかを確認する作業が発生します。パラメータの番号付けが異なると、この比較作業が複雑になり、ノイズが増えてしまいます。
2.  **インライン化の要件**: Goコンパイラは、パフォーマンス向上のために小さな関数を呼び出し元に直接展開する「インライン化」を行います。インライン化された関数のパラメータは、呼び出し元のコンテキストで一意に識別される必要があります。このため、インライン化可能な関数のパラメータには、コンパイラ内部で一意の番号が割り当てられます（`Vargen`と呼ばれる世代番号など）。
3.  **移行期間中の一時的な措置**: 新しいバイナリ形式がまだデフォルトではない段階では、既存のツールや開発ワークフローとの互換性を保ちつつ、新しい形式の安定性を確保する必要があります。この変更は、その移行期間におけるデバッグや検証作業を円滑に進めるための一時的な「橋渡し」として機能します。

要するに、この変更は、Goコンパイラの内部的な進化の過程で、開発者が変更の影響をより正確に把握し、デバッグを容易にするための実用的な手段として導入されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラおよびGo言語の概念に関する知識が必要です。

1.  **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。`src/cmd/compile/internal/gc` ディレクトリには、コンパイラの主要なロジックが含まれています。
2.  **バイナリ出力形式 (Binary Export Format)**: Goコンパイラは、コンパイル済みのパッケージに関するメタデータ（型情報、関数シグネチャ、エクスポートされたシンボルなど）を、他のパッケージがインポートできるようにエクスポートします。この情報は、以前はテキストベースの形式でエクスポートされていましたが、より効率的なバイナリ形式への移行が進められていました。このバイナリ形式は、コンパイル時間の短縮やディスク使用量の削減に寄与します。
3.  **パラメータの番号付け (Parameter Numbering)**: Goコンパイラの内部では、特にインライン化の際に、関数のパラメータを一意に識別するために内部的な番号付け（例: `name·Vargen` のような形式）が使用されることがあります。これは、異なるスコープやインライン化されたコードブロック内で同じ名前のパラメータが衝突するのを避けるためです。`Vargen` (Variable Generation) は、変数の世代番号を示し、コンパイラが変数を一意に追跡するために使用します。
4.  **インライン化 (Inlining)**: コンパイラ最適化の一種で、小さな関数の呼び出しを、その関数の本体のコードで直接置き換えることです。これにより、関数呼び出しのオーバーヘッドが削減され、パフォーマンスが向上します。インライン化は、コンパイラが関数の本体を「知っている」必要があるため、エクスポートされたインライン化可能な関数は、その本体情報もエクスポート形式に含まれることがあります。
5.  **アセンブリコードダンプ (Assembly Code Dumps)**: コンパイラが生成した機械語コードを、人間が読めるアセンブリ言語の形式で出力したものです。コンパイラの変更がパフォーマンスやコードサイズに与える影響を分析する際に、このダンプを比較することがよく行われます。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラのバイナリ出力プロセスにおけるパラメータ名の扱いを変更することにあります。

Goコンパイラは、関数やメソッドのパラメータをエクスポートする際に、その名前をバイナリ形式に含めます。通常、このパラメータの番号付け（例: `name·Vargen`）は、インライン化可能な関数のパラメータにのみ必要とされます。これは、インライン化によって同じ名前のパラメータが異なるコンテキストで出現する可能性があり、それらを区別するために一意の識別子が必要となるためです。

しかし、新しいバイナリ出力形式への移行期間中、開発者は既存のテキスト形式と新しいバイナリ形式でコンパイルされたコードの挙動を比較する必要があります。特に、生成されるアセンブリコードのダンプを比較する際に、パラメータ名のわずかな違いでも差分として検出されてしまい、本質的ではない変更がノイズとなって分析を妨げる可能性があります。

このコミットは、この問題を解決するために、`src/cmd/compile/internal/gc/bexport.go` に `forceNumberedParams` という新しい定数を導入し、これを `true` に設定しています。そして、パラメータ名を生成する `parName` 関数内で、この `forceNumberedParams` が `true` であれば、`numbered` フラグの状態にかかわらず、常にパラメータに番号付けを行うように変更しています。

これにより、インライン化可能でない関数のパラメータであっても、一時的に番号付けが強制されます。結果として、テキスト形式とバイナリ形式の両方でコンパイルされたコードのアセンブリダンプにおいて、パラメータ名の形式が統一され、比較時のノイズが大幅に削減されます。

一方で、`src/go/internal/gcimporter/bimport.go` では、バイナリ形式からパラメータ名をインポートする際に、この一時的に付与された番号付け（`·` とそれに続く数字）を削除する処理が追加されています。これは、コンパイラの内部処理で番号付けが強制されても、Go言語のセマンティクス上は通常のパラメータ名として扱われるべきであるためです。インポート側で番号付けを剥がすことで、コンパイラの他の部分やユーザーコードがこの内部的な番号付けに影響されないようにしています。

この変更は、新しいバイナリ出力形式が安定し、デフォルトとして採用された時点で、`forceNumberedParams` を `false` に戻すか、関連コードを削除することで元に戻される予定の一時的なデバッグ/検証支援機能です。

5.  **アセンブリコードダンプ (Assembly Code Dumps)**: コンパイラが生成した機械語コードを、人間が読めるアセンブリ言語の形式で出力したものです。コンパイラの変更がパフォーマンスやコードサイズに与える影響を分析する際に、このダンプを比較することがよく行われます。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラのバイナリ出力プロセスにおけるパラメータ名の扱いを変更することにあります。

Goコンパイラは、関数やメソッドのパラメータをエクスポートする際に、その名前をバイナリ形式に含めます。通常、このパラメータの番号付け（例: `name·Vargen`）は、インライン化可能な関数のパラメータにのみ必要とされます。これは、インライン化によって同じ名前のパラメータが異なるコンテキストで出現する可能性があり、それらを区別するために一意の識別子が必要となるためです。

しかし、新しいバイナリ出力形式への移行期間中、開発者は既存のテキスト形式と新しいバイナリ形式でコンパイルされたコードの挙動を比較する必要があります。特に、生成されるアセンブリコードのダンプを比較する際に、パラメータ名のわずかな違いでも差分として検出されてしまい、本質的ではない変更がノイズとなって分析を妨げる可能性があります。

このコミットは、この問題を解決するために、`src/cmd/compile/internal/gc/bexport.go` に `forceNumberedParams` という新しい定数を導入し、これを `true` に設定しています。そして、パラメータ名を生成する `parName` 関数内で、この `forceNumberedParams` が `true` であれば、`numbered` フラグの状態にかかわらず、常にパラメータに番号付けを行うように変更しています。

これにより、インライン化可能でない関数のパラメータであっても、一時的に番号付けが強制されます。結果として、テキスト形式とバイナリ形式の両方でコンパイルされたコードのアセンブリダンプにおいて、パラメータ名の形式が統一され、比較時のノイズが大幅に削減されます。

一方で、`src/go/internal/gcimporter/bimport.go` では、バイナリ形式からパラメータ名をインポートする際に、この一時的に付与された番号付け（`·` とそれに続く数字）を削除する処理が追加されています。これは、コンパイラの内部処理で番号付けが強制されても、Go言語のセマンティクス上は通常のパラメータ名として扱われるべきであるためです。インポート側で番号付けを剥がすことで、コンパイラの他の部分やユーザーコードがこの内部的な番号付けに影響されないようにしています。

この変更は、新しいバイナリ出力形式が安定し、デフォルトとして採用された時点で、`forceNumberedParams` を `false` に戻すか、関連コードを削除することで元に戻される予定の一時的なデバッグ/検証支援機能です。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/bexport.go` の変更

1.  **`forceNumberedParams` 定数の追加**:
    ```go
    const forceNumberedParams = true
    ```
    この行は、パラメータの番号付けを強制するための新しいブール定数を導入しています。`true` に設定されているため、この機能が有効になります。コメントには、これが一時的な措置であり、新しいエクスポート形式への移行が完了したら削除されるべきであることが明記されています。

2.  **`parName` 関数の条件変更**:
    ```diff
    -	if numbered {
    +	if forceNumberedParams || numbered {
    ```
    `parName` 関数は、エクスポートされるパラメータ名を構築する役割を担っています。元のコードでは、`numbered` フラグが `true` の場合にのみパラメータに番号付け（`name·Vargen` 形式）を行っていました。
    変更後、`forceNumberedParams` が `true` であれば、`numbered` フラグの値にかかわらず、常に番号付けが行われるようになります。これにより、インライン化の必要がないパラメータにも一貫して番号が振られることになります。`f.Nname.Name.Vargen > 0` の条件は、`Vargen` が実際に存在し、有効な世代番号を持っている場合にのみ番号付けを行うことを保証します。

### `src/go/internal/gcimporter/bimport.go` の変更

1.  **`strings` パッケージのインポート**:
    ```diff
    +	"strings"
    ```
    パラメータ名から番号付けを削除するために、`strings` パッケージの関数を使用するため、このインポートが追加されました。

2.  **`param` 関数内の番号付け削除ロジック**:
    ```diff
    +		if i := strings.Index(name, "·"); i > 0 {
    +			name = name[:i] // cut off gc-specific parameter numbering
    +		}
    ```
    `param` 関数は、バイナリ形式からパラメータ情報を読み込む際に呼び出されます。この新しいコードブロックは、読み込んだパラメータ名 `name` に `·` (中点) が含まれているかどうかをチェックします。もし含まれていて、そのインデックス `i` が0より大きい（つまり、名前の先頭ではない）場合、`name` を `·` の手前までで切り詰めます。これにより、`name·Vargen` のような形式から `Vargen` 部分が削除され、元のパラメータ名のみが残ります。これは、エクスポート時に強制的に付与された内部的な番号付けを、インポート時に取り除くための対応です。

これらの変更により、コンパイラはエクスポート時にパラメータ名を一貫した形式で出力し、インポート時にはその内部的な番号付けを透過的に処理することで、新しいバイナリ形式への移行期間中の開発者のデバッグと検証作業を支援しています。

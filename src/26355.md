# [インデックス 26355] ファイルの概要

このコミットは、Go言語のコンパイラ（gc）が生成するエクスポートデータ（gc export data）をインポートする際の、パッケージ関連付けの正確性を向上させるためのものです。具体的には、エクスポートされた構造体フィールドやインターフェースメソッドが、本来属すべきパッケージに正しく関連付けられるように修正されています。

## コミット

```
commit 756088549f764b7b75d4605d69cc1a187749fc6a
Author: Robert Griesemer <gri@golang.org>
Date:   Tue Jan 12 17:02:32 2016 -0800

    go/importer: associate exported field and interface methods with correct package

    In gc export data, exported struct field and interface methods names appear
    in unqualified form (i.e., w/o package name). The (gc)importer assumed that
    unqualified exported names automatically belong to the package being imported.
    This is not the case if the field or method belongs to a struct or interface
    that was declared in another package and re-exported.

    The issue becomes visible if a type T (say an interface with a method M)
    is declared in a package A, indirectly re-exported by a package B (which
    imports A), and then imported in C. If C imports both A and B, if A is
    imported before B, T.M gets associated with the correct package A. If B
    is imported before A, T.M appears to be exported by B (even though T itself
    is correctly marked as coming from A). If T.M is imported again via the
    import of A if gets dropped (as it should) because it was already imported.

    The fix is to pass down the parent package when we parse imported types
    so that the importer can use the correct package when creating fields
    and methods.

    Fixes #13898.
```

## 元コミット内容

`go/importer: associate exported field and interface methods with correct package`

このコミットは、`gc`コンパイラのエクスポートデータにおいて、エクスポートされたフィールドやインターフェースメソッドが正しいパッケージに関連付けられるように修正します。以前は、修飾されていない名前（パッケージ名なし）が常にインポート中のパッケージに属すると誤って解釈されていました。しかし、フィールドやメソッドが別のパッケージで宣言され、その後再エクスポートされた構造体やインターフェースに属する場合、この仮定は誤りでした。

この問題は、型`T`（例えばメソッド`M`を持つインターフェース）がパッケージ`A`で宣言され、パッケージ`B`（`A`をインポートしている）によって間接的に再エクスポートされ、さらにパッケージ`C`でインポートされる場合に顕在化します。`C`が`A`と`B`の両方をインポートする場合、`A`が`B`より先にインポートされると、`T.M`は正しいパッケージ`A`に関連付けられます。しかし、`B`が`A`より先にインポートされると、`T.M`は`B`によってエクスポートされたかのように見えてしまいます（`T`自体は`A`からのものとして正しくマークされているにもかかわらず）。その後、`A`のインポートを介して`T.M`が再度インポートされると、既にインポート済みであるため（本来あるべきように）破棄されます。

この修正は、インポートされた型をパースする際に親パッケージを渡すことで、インポーターがフィールドやメソッドを作成する際に正しいパッケージを使用できるようにします。

Issue #13898 を修正します。

## 変更の背景

Go言語のコンパイラ（`gc`）は、コンパイル済みのパッケージ情報をエクスポートデータとして出力します。このエクスポートデータは、他のパッケージがそのパッケージの型や関数などをインポートする際に利用されます。`go/importer`パッケージは、このエクスポートデータを読み込み、Goの型システム（`go/types`パッケージ）が理解できる内部表現に変換する役割を担っています。

問題は、エクスポートデータ内で構造体のフィールド名やインターフェースのメソッド名が、そのフィールドやメソッドが定義された元のパッケージ名を含まない「修飾されていない形式」で記述されることにありました。`gcimporter`は、これらの修飾されていない名前が、現在インポートしているパッケージに自動的に属すると仮定していました。

しかし、この仮定は、あるパッケージで定義された型が、別のパッケージを介して「再エクスポート」されるシナリオで破綻します。例えば、パッケージ`A`で定義されたインターフェース`I`があり、そのインターフェースがメソッド`M`を持っているとします。パッケージ`B`が`A`をインポートし、`I`をエクスポートしている場合、パッケージ`C`が`B`をインポートすると、`C`は`I`と`M`を利用できます。このとき、`M`は本来パッケージ`A`に属するべきですが、`gcimporter`の古いロジックでは、`M`がパッケージ`B`に属すると誤って解釈される可能性がありました。

この誤った関連付けは、特に複数のパッケージが同じ型を異なる経路でインポートする場合に、型の同一性チェックや名前解決に問題を引き起こす可能性がありました。コミットメッセージの例では、パッケージ`C`が`A`と`B`の両方をインポートする際に、インポート順序によって`T.M`の所属パッケージが異なってしまうという具体的な問題が示されています。これは、Goの型システムにおける一貫性と正確性を損なう重大なバグでした。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の内部構造に関する知識が必要です。

1.  **Goのパッケージシステム**: Goのコードはパッケージに分割され、パッケージは他のパッケージをインポートしてそのエクスポートされた識別子（型、関数、変数など）を利用できます。各識別子は、それが定義されたパッケージに属します。
2.  **`go/types`パッケージ**: Goの型システムをプログラム的に表現・操作するための標準ライブラリです。型チェック、抽象構文木（AST）の解析結果からの型情報の構築などを行います。`types.Package`はGoのパッケージを表し、`types.Object`は識別子（変数、関数、型など）を表します。`types.Func`は関数やメソッドを表し、`types.Var`は変数やフィールドを表します。
3.  **`go/importer`パッケージ**: コンパイル済みGoパッケージの情報を読み込むためのインターフェースを提供します。Goの標準ライブラリには、`gc`コンパイラが生成するエクスポートデータを読み込むための`go/importer/gcimporter`が含まれています。
4.  **`gc`エクスポートデータ**: `gc`コンパイラがパッケージをコンパイルする際に生成する、そのパッケージのエクスポートされた識別子に関するメタデータです。このデータは、他のパッケージがそのパッケージをインポートする際に使用されます。
5.  **修飾名と非修飾名**: Goの識別子は、`fmt.Println`のようにパッケージ名で修飾される場合（修飾名）と、`Println`のようにパッケージ名なしで直接参照される場合（非修飾名）があります。エクスポートデータ内では、構造体フィールドやインターフェースメソッドの名前が非修飾名で記述されることがあります。
6.  **型情報のパース**: `gcimporter`は、エクスポートデータをバイトストリームとして読み込み、それをGoの型システムが理解できる`types.Type`や`types.Object`などの構造体に変換（パース）します。このパース処理中に、各識別子がどのパッケージに属するかを正確に決定する必要があります。

## 技術的詳細

このコミットの核心は、`gcimporter`がエクスポートデータをパースする際に、型や識別子が本来属するパッケージのコンテキストを正確に伝達することにあります。

以前の`gcimporter`の実装では、構造体フィールドやインターフェースメソッドのような「修飾されていない」名前をパースする際、それらが常に現在インポート中のパッケージに属すると単純に仮定していました。これは、多くの場合で問題ありませんでしたが、型が別のパッケージで定義され、その後別のパッケージを介して再エクスポートされるような複雑なシナリオでは、誤ったパッケージ関連付けを引き起こしました。

修正の主要なアプローチは、`gcimporter`内の型をパースする様々な関数（例: `parseArrayType`, `parseMapType`, `parseStructType`, `parseInterfaceType`, `parseChanType`, `parseType`）に、`parent *types.Package`という引数を追加することです。この`parent`引数は、現在パース中の型が属するべき「親」パッケージを示します。

具体的には、以下の変更が行われました。

1.  **`parseType`関数のシグネチャ変更**: `parseType`関数は、Goの様々な型（配列、マップ、構造体、インターフェース、チャネル、ポインタなど）をパースする中心的な関数です。この関数が`parent *types.Package`を受け取るようになり、内部で呼び出す他の型パース関数にもこの`parent`情報を伝播させるようになりました。
2.  **`parseName`関数のロジック変更**: `parseName`関数は、識別子名をパースし、それが属するパッケージを決定します。この関数も`parent *types.Package`を受け取るようになり、修飾されていない名前や匿名名の場合に、この`parent`パッケージを優先的に使用するようになりました。これにより、フィールドやメソッドが別のパッケージで宣言された型に属する場合でも、正しいパッケージが関連付けられるようになります。
    *   `pkg = parent` が追加され、`parent`が`nil`でない限り、`parent`が優先的に使用されます。
    *   `parent == nil` の場合は、以前と同様に現在インポート中のパッケージ (`p.sharedPkgs[p.id]`) が使用されます。
3.  **`parseField`関数の変更**: 構造体フィールドをパースする`parseField`関数は、`parseName`と`parseType`を呼び出す際に、適切な`parent`パッケージを渡すようになりました。特に、匿名フィールドの場合、その型が`*types.Named`であれば、その型の`Obj().Pkg()`からパッケージ情報を取得し、それをフィールドのパッケージとして設定するようになりました。
4.  **`parseStructType`および`parseInterfaceType`の変更**: これらの関数も、内部でフィールドやメソッドをパースする際に、`parent`パッケージを適切に伝達するようになりました。
5.  **テストの追加**: `gcimporter_test.go`と`go/types/issues_test.go`に、この問題（Issue #13898）を再現し、修正が正しく機能することを確認するための新しいテストケースが追加されました。特に`TestIssue13898`は、インポート順序によってメソッドの所属パッケージが誤って解釈されるシナリオを検証しています。

この修正により、`gcimporter`は、エクスポートデータ内の修飾されていない識別子であっても、それが定義された元のパッケージのコンテキストを正確に追跡し、`go/types`パッケージの内部表現に正しく反映できるようになりました。これにより、Goの型システムの一貫性と堅牢性が向上しました。

## コアとなるコードの解説

このコミットのコアとなる変更は、`gcimporter`が型情報をパースする際に、その型が属するべき「親パッケージ」の情報を明示的に伝達するようになった点です。

以前は、`gcimporter`はエクスポートデータ内の修飾されていない名前（例: 構造体フィールド名、インターフェースメソッド名）を、現在インポートしているパッケージに属するものと見なしていました。しかし、Goでは、あるパッケージ`A`で定義された型`T`が、別のパッケージ`B`を介して再エクスポートされることがあります。この場合、`T`のフィールドやメソッドは依然としてパッケージ`A`に属するべきです。

新しいアプローチでは、`parseType`や`parseName`といった型パースの主要な関数群が、`parent *types.Package`という引数を受け取るようになりました。

*   **`parseType(parent *types.Package)`**:
    この関数は、様々な種類の型（配列、マップ、構造体、インターフェースなど）をパースする際に、この`parent`情報を下流の関数に渡します。これにより、例えば構造体型をパースする際に、その構造体が定義されたパッケージ（`parent`）のコンテキストが、その構造体のフィールドをパースする際にも利用されるようになります。

*   **`parseName(parent *types.Package, materializePkg bool)`**:
    この関数は、識別子名とその識別子が属するパッケージを決定します。
    変更点として、まず`pkg = parent`と設定されます。これは、もし`parent`パッケージが指定されていれば、それが識別子のデフォルトの所属パッケージとなることを意味します。
    もし`parent`が`nil`であれば、以前と同様に現在インポート中のパッケージ（`p.sharedPkgs[p.id]`）が使用されます。
    このロジックにより、修飾されていないフィールド名やメソッド名が、インポート中のパッケージではなく、その型が定義された元のパッケージに正しく関連付けられるようになります。

*   **`parseField(parent *types.Package)`**:
    構造体フィールドをパースする際に、`parseName(parent, true)`と`parseType(parent)`を呼び出すことで、フィールド名とフィールドの型が、構造体自体が属するパッケージ（`parent`）のコンテキストで正しくパースされるようになります。
    特に、匿名フィールドの場合、その型が`*types.Named`であれば、その型の`Obj().Pkg()`から直接パッケージ情報を取得し、フィールドのパッケージとして設定することで、より正確な関連付けを実現しています。

これらの変更により、`gcimporter`は、エクスポートデータ内の型情報をより正確に解釈し、Goの型システムが期待するパッケージ関連付けを維持できるようになりました。これにより、Goプログラムのセマンティクスが、インポート順序や再エクスポートの有無に関わらず一貫して保たれることが保証されます。

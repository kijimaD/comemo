# [インデックス 2822] ファイルの概要

このコミットは、Goコンパイラ（`gc`）の重要な内部変更を導入するものです。具体的には、式の型チェック（`typecheck`）フェーズを、式を走査して変換するフェーズ（`walkexpr`）の前に独立して実行するように変更しています。これはコンパイラの構造を改善し、型チェックのロジックをより明確に分離することを目的とした初期段階の作業です。コミットメッセージにもあるように、この時点ではまだ完全ではありませんが、コンパイラは引き続き機能します。

## 変更の背景

このコミットの主な背景は、Goコンパイラ（`gc`）のフロントエンドにおける処理フローの改善です。Goコンパイラは、ソースコードを抽象構文木（AST）にパースした後、複数のフェーズを経て機械語に変換します。以前の設計では、`walkexpr`という関数が型チェックとASTの変換（最適化や中間表現への変換）の両方を担当していました。

しかし、型チェックとAST変換のロジックが密接に絡み合っていると、コードの可読性、保守性、そして拡張性が低下します。特に、型システムが複雑になるにつれて、型チェックのルールがAST変換のロジックに影響を与え、その逆もまた然りという状況が発生しやすくなります。

このコミットは、型チェックを`walkexpr`の前に独立したパスとして導入することで、これらの問題を解決しようとする初期段階の試みです。これにより、コンパイラの各フェーズの責任が明確になり、将来的な型システムの拡張や最適化の実装が容易になります。また、型エラーの検出をより早期に行えるようになることで、コンパイラのエラーメッセージの質が向上する可能性もあります。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの基本的な構造と、コンパイラ設計における一般的な概念をいくつか知っておく必要があります。

1.  **Goコンパイラ (`gc`) の構造**:
    *   Goコンパイラは、ソースコードをASTにパースし、そのASTに対して様々な変換と最適化を適用し、最終的に機械語を生成します。
    *   **AST (Abstract Syntax Tree)**: ソースコードの構造を木構造で表現したものです。コンパイラはこのASTを操作してコードの意味を理解し、変換します。
    *   **`Node`**: ASTの各要素（式、文、型など）を表すデータ構造です。`src/cmd/gc/go.h`で定義されています。
    *   **`Type`**: Go言語の型システムにおける型情報を表すデータ構造です。
    *   **`walkexpr`**: 以前のGoコンパイラにおける主要な関数の一つで、ASTを深さ優先で走査し、式の型チェック、定数評価、一部の最適化、そしてASTの変換（例えば、高レベルなASTノードをより低レベルな中間表現に変換する）を行っていました。
    *   **`typecheck`**: このコミットで導入された新しいフェーズで、`walkexpr`の前に実行され、式の型がGo言語の仕様に準拠しているかを検証します。

2.  **コンパイラのパス (Compiler Passes)**:
    *   コンパイラは通常、複数の「パス」または「フェーズ」に分かれて処理を行います。各パスは特定のタスク（字句解析、構文解析、意味解析、最適化、コード生成など）を担当し、前のパスの出力を入力として受け取ります。
    *   **意味解析 (Semantic Analysis)**: 型チェックはこのフェーズの一部であり、プログラムの意味的な正当性を検証します。例えば、変数の型が正しいか、演算子のオペランドの型が適切かなどを確認します。

3.  **`TIDEAL` 型**:
    *   Go言語には「型なし定数 (untyped constants)」という概念があります。例えば、`const x = 1` の `1` は、それが使用される文脈によって `int`、`int32`、`float64` など、様々な型になり得ます。このような定数は、特定の型に束縛されるまで「理想型 (ideal type)」として扱われます。
    *   `TIDEAL` は、Goコンパイラ内部でこの理想型を表すために使用される特別な型です。このコミットでは、`TIDEAL` 型が整数型と同様に比較 (`okforcmp`) や算術演算 (`okforarith`) が可能であることを `align.c` で明示的に設定しています。

4.  **`okfor` 配列**:
    *   `src/cmd/gc/go.h` および `src/cmd/gc/align.c` に見られる `okforadd`, `okforcmp`, `okforarith` などの配列は、特定の型が特定の演算子（加算、比較、算術演算など）に対して有効であるかを定義するフラグの集合です。`okfor[OEND]` は、各演算子 (`OADD`, `OEQ` など) がどの型の集合に対して有効であるかをマッピングするテーブルとして機能します。これは型チェックの基本的なルールを定義するために使用されます。

## 技術的詳細

このコミットの技術的な核心は、`walkexpr` 関数から型チェックのロジックを分離し、`typecheck` という新しい関数とそれに関連するデータ構造を導入した点にあります。

### `Node` 構造体の変更 (`src/cmd/gc/go.h`)

*   `Node` 構造体に `uchar typecheck;` フィールドが追加されました。これは、特定のASTノードが既に型チェック済みであるか（`1`）、現在型チェック中であるか（`2`）、まだ型チェックされていないか（`0`）を追跡するために使用されます。これにより、無限ループを防ぎ、効率的な型チェックが可能になります。
*   `Etop`, `Elv`, `Erv`, `Etype` といった評価コンテキストフラグに加えて、`Eideal = 1<<5` が追加されました。これは、式が理想型として評価されるべきであることを示すフラグです。
*   `okfornone`, `okforcmp`, `okforbool`, `okforcap`, `okforlen`, `okforarith` といった新しい `uchar` 配列が宣言され、`okfor[OEND]` という配列へのポインタが追加されました。これらは、各演算子に適用可能な型の集合をより詳細に定義するために使用されます。

### `align.c` の変更

*   `typeinit` 関数内で、`okfor` 関連の配列の初期化ロジックが大幅に拡張されました。
    *   `TIDEAL` 型が整数型と同様に `okforeq`, `okforcmp`, `okforarith` が可能であると明示的に設定されました。
    *   `TBOOL`, `TSTRING`, `TARRAY`, `TMAP`, `TPTR32`, `TPTR64`, `TINTER`, `TCHAN`, `TFUNC` など、様々な組み込み型に対して、それぞれがサポートする演算子（`okforadd`, `okforbool`, `okforcap`, `okforlen`, `okforeq`, `okforcmp`）が詳細に設定されました。
    *   `okfor[OEND]` 配列が初期化され、各演算子（`OADD`, `OAND`, `OEQ` など）がどの `okfor` フラグセットを使用すべきかがマッピングされました。これにより、型チェックロジックがよりデータ駆動型になります。

### `walk.c` の変更

*   **`typecheck` 関数の導入**:
    *   `walkexpr` から型チェックの責任を分離するために、`typecheck` という新しい関数が導入されました。
    *   `typecheck` は、ASTノード `n` と評価コンテキスト `top` を受け取り、ノードの型を決定し、定数式を評価し、必要に応じてASTノードを書き換えます。
    *   `n->typecheck` フラグを使用して、ノードが既に処理中または処理済みであるかを追跡し、再帰的な型チェックループを防ぎます。
    *   様々なASTノードの操作（`OTARRAY`, `OTMAP`, `OTCHAN`, `OTSTRUCT`, `OTINTER`, `OTFUNC` などの型定義、および二項演算子、単項演算子）に対する型チェックロジックが `typecheck` 内に移動されました。
    *   特に、二項演算子 (`OADD`, `OEQ` など) の型チェックでは、`okfor[n->op][et]` を使用して、オペランドの型が演算子に対して有効であるかを検証します。また、理想型と非理想型の混合に対する処理や、スライスと`nil`の比較に関する特殊なルールも含まれています。
*   **`walkexpr` の変更**:
    *   `walkexpr` は、`typecheck` が導入されたことで、その役割がAST変換と最適化に特化されるようになりました。
    *   `walkexpr` の冒頭で `if(n->typecheck != 1) typecheck(&n, top | typeok);` が呼び出され、`walkexpr` が実行される前に必ず型チェックが完了していることを保証します。
    *   `walkexpr` 内の多くの `if(top != Erv)` のような型チェック関連の条件が `if(!(top & Erv))` のように変更され、よりビットフラグの扱いが明確になりました。
    *   定数評価 (`evconst(n)`) の呼び出しが `typecheck` の `ret` ラベルの直前に移動され、型チェックフェーズで定数評価が行われるようになりました。

### `const.c` の変更

*   `defaultlit` 関数で、未知のリテラルに対するエラーメッセージが `%#N` を使用するように変更され、より詳細なノード情報が出力されるようになりました。
*   `OCONV` (型変換) オペレータに対する `CTINT`, `CTFLT`, `CTSTR` のケースが追加され、リテラル定数の型変換が `convlit1` を通じて処理されるようになりました。

### `subr.c` の変更

*   `badtype` 関数から不要な空行が削除されました。
*   `tempname` 関数で、一時変数の `etype` フィールドの設定が削除されました。これは、`typecheck` フェーズで型が決定されるようになったため、この段階での `etype` の設定が不要になったことを示唆しています。

### `typecheck` 関数の導入と役割

`walk.c` に新しく追加された `typecheck` 関数は、Goコンパイラの意味解析フェーズにおける中心的な役割を担います。


この関数は、ASTノード `n` を再帰的に走査し、以下の処理を行います。

*   **型チェック状態の管理**: `n->typecheck` フラグを使用して、ノードの処理状態を管理します。これにより、DAG (Directed Acyclic Graph) 構造を持つASTにおいて、同じノードが複数回処理されたり、無限ループに陥ったりするのを防ぎます。
*   **シンボル定義のウォーク**: 必要に応じて `walkdef` を呼び出し、シンボルの定義を処理します。
*   **型の決定**: 各ノードの `n->type` フィールドに適切なGoの型を設定します。
*   **演算子の型適合性チェック**: `okfor` テーブルを使用して、二項演算子や単項演算子のオペランドの型がGoの仕様に適合しているかを検証します。例えば、`OADD` (加算) 演算子には `okforadd` に含まれる型のみが適用可能です。
*   **定数評価**: `evconst(n)` を呼び出し、コンパイル時定数である式を評価し、その結果をASTノードに格納します。
*   **ASTの書き換え**: 型チェックの過程で、ASTノードのオペレータ (`n->op`) や構造をより具体的な形に書き換えることがあります。例えば、型定義ノード (`OTARRAY`, `OTMAP` など) は `OTYPE` ノードに変換されます。
*   **エラー報告**: 型エラーが検出された場合、`yyerror` を使用してエラーメッセージを報告し、ノードの型を `T` (不明な型) に設定して、それ以降の処理が不正な型情報に依存しないようにします。

### `align.c` における `okfor` テーブルの拡張

`align.c` の `typeinit` 関数における `okfor` テーブルの初期化は、Goの型システムにおける演算子の振る舞いを定義する上で非常に重要です。

## 変更の背景

このコミットの主な背景は、Goコンパイラ（`gc`）のフロントエンドにおける処理フローの改善です。Goコンパイラは、ソースコードを抽象構文木（AST）にパースした後、複数のフェーズを経て機械語に変換します。以前の設計では、`walkexpr`という関数が型チェックとASTの変換（最適化や中間表現への変換）の両方を担当していました。

しかし、型チェックとAST変換のロジックが密接に絡み合っていると、コードの可読性、保守性、そして拡張性が低下します。特に、型システムが複雑になるにつれて、型チェックのルールがAST変換のロジックに影響を与え、その逆もまた然りという状況が発生しやすくなります。

このコミットは、型チェックを`walkexpr`の前に独立したパスとして導入することで、これらの問題を解決しようとする初期段階の試みです。これにより、コンパイラの各フェーズの責任が明確になり、将来的な型システムの拡張や最適化の実装が容易になります。また、型エラーの検出をより早期に行えるようになることで、コンパイラのエラーメッセージの質が向上する可能性もあります。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの基本的な構造と、コンパイラ設計における一般的な概念をいくつか知っておく必要があります。

1.  **Goコンパイラ (`gc`) の構造**:
    *   Goコンパイラは、ソースコードをASTにパースし、そのASTに対して様々な変換と最適化を適用し、最終的に機械語を生成します。
    *   **AST (Abstract Syntax Tree)**: ソースコードの構造を木構造で表現したものです。コンパイラはこのASTを操作してコードの意味を理解し、変換します。
    *   **`Node`**: ASTの各要素（式、文、型など）を表すデータ構造です。`src/cmd/gc/go.h`で定義されています。
    *   **`Type`**: Go言語の型システムにおける型情報を表すデータ構造です。
    *   **`walkexpr`**: 以前のGoコンパイラにおける主要な関数の一つで、ASTを深さ優先で走査し、式の型チェック、定数評価、一部の最適化、そしてASTの変換（例えば、高レベルなASTノードをより低レベルな中間表現に変換する）を行っていました。
    *   **`typecheck`**: このコミットで導入された新しいフェーズで、`walkexpr`の前に実行され、式の型がGo言語の仕様に準拠しているかを検証します。

2.  **コンパイラのパス (Compiler Passes)**:
    *   コンパイラは通常、複数の「パス」または「フェーズ」に分かれて処理を行います。各パスは特定のタスク（字句解析、構文解析、意味解析、最適化、コード生成など）を担当し、前のパスの出力を入力として受け取ります。
    *   **意味解析 (Semantic Analysis)**: 型チェックはこのフェーズの一部であり、プログラムの意味的な正当性を検証します。例えば、変数の型が正しいか、演算子のオペランドの型が適切かなどを確認します。

3.  **`TIDEAL` 型**:
    *   Go言語には「型なし定数 (untyped constants)」という概念があります。例えば、`const x = 1` の `1` は、それが使用される文脈によって `int`、`int32`、`float64` など、様々な型になり得ます。このような定数は、特定の型に束縛されるまで「理想型 (ideal type)」として扱われます。
    *   `TIDEAL` は、Goコンパイラ内部でこの理想型を表すために使用される特別な型です。このコミットでは、`TIDEAL` 型が整数型と同様に比較 (`okforcmp`) や算術演算 (`okforarith`) が可能であることを `align.c` で明示的に設定しています。

4.  **`okfor` 配列**:
    *   `src/cmd/gc/go.h` および `src/cmd/gc/align.c` に見られる `okforadd`, `okforcmp`, `okforarith` などの配列は、特定の型が特定の演算子（加算、比較、算術演算など）に対して有効であるかを定義するフラグの集合です。`okfor[OEND]` は、各演算子 (`OADD`, `OEQ` など) がどの型の集合に対して有効であるかをマッピングするテーブルとして機能します。これは型チェックの基本的なルールを定義するために使用されます。

## 技術的詳細

このコミットの技術的な核心は、`walkexpr` 関数から型チェックのロジックを分離し、`typecheck` という新しい関数とそれに関連するデータ構造を導入した点にあります。

### `Node` 構造体の変更 (`src/cmd/gc/go.h`)

*   `Node` 構造体に `uchar typecheck;` フィールドが追加されました。これは、特定のASTノードが既に型チェック済みであるか（`1`）、現在型チェック中であるか（`2`）、まだ型チェックされていないか（`0`）を追跡するために使用されます。これにより、無限ループを防ぎ、効率的な型チェックが可能になります。
*   `Etop`, `Elv`, `Erv`, `Etype` といった評価コンテキストフラグに加えて、`Eideal = 1<<5` が追加されました。これは、式が理想型として評価されるべきであることを示すフラグです。
*   `okfornone`, `okforcmp`, `okforbool`, `okforcap`, `okforlen`, `okforarith` といった新しい `uchar` 配列が宣言され、`okfor[OEND]` という配列へのポインタが追加されました。これらは、各演算子に適用可能な型の集合をより詳細に定義するために使用されます。

### `align.c` の変更

*   `typeinit` 関数内で、`okfor` 関連の配列の初期化ロジックが大幅に拡張されました。
    *   `TIDEAL` 型が整数型と同様に `okforeq`, `okforcmp`, `okforarith` が可能であると明示的に設定されました。
    *   `TBOOL`, `TSTRING`, `TARRAY`, `TMAP`, `TPTR32`, `TPTR64`, `TINTER`, `TCHAN`, `TFUNC` など、様々な組み込み型に対して、それぞれがサポートする演算子（`okforadd`, `okforbool`, `okforcap`, `okforlen`, `okforeq`, `okforcmp`）が詳細に設定されました。
    *   `okfor[OEND]` 配列が初期化され、各演算子（`OADD`, `OAND`, `OEQ` など）がどの `okfor` フラグセットを使用すべきかがマッピングされました。これにより、型チェックロジックがよりデータ駆動型になります。

### `walk.c` の変更

*   **`typecheck` 関数の導入**:
    *   `walkexpr` から型チェックの責任を分離するために、`typecheck` という新しい関数が導入されました。
    *   `typecheck` は、ASTノード `n` と評価コンテキスト `top` を受け取り、ノードの型を決定し、定数式を評価し、必要に応じてASTノードを書き換えます。
    *   `n->typecheck` フラグを使用して、ノードが既に処理中または処理済みであるかを追跡し、再帰的な型チェックループを防ぎます。
    *   様々なASTノードの操作（`OTARRAY`, `OTMAP`, `OTCHAN`, `OTSTRUCT`, `OTINTER`, `OTFUNC` などの型定義、および二項演算子、単項演算子）に対する型チェックロジックが `typecheck` 内に移動されました。
    *   特に、二項演算子 (`OADD`, `OEQ` など) の型チェックでは、`okfor[n->op][et]` を使用して、オペランドの型が演算子に対して有効であるかを検証します。また、理想型と非理想型の混合に対する処理や、スライスと`nil`の比較に関する特殊なルールも含まれています。
*   **`walkexpr` の変更**:
    *   `walkexpr` は、`typecheck` が導入されたことで、その役割がAST変換と最適化に特化されるようになりました。
    *   `walkexpr` の冒頭で `if(n->typecheck != 1) typecheck(&n, top | typeok);` が呼び出され、`walkexpr` が実行される前に必ず型チェックが完了していることを保証します。
    *   `walkexpr` 内の多くの `if(top != Erv)` のような型チェック関連の条件が `if(!(top & Erv))` のように変更され、よりビットフラグの扱いが明確になりました。
    *   定数評価 (`evconst(n)`) の呼び出しが `typecheck` の `ret` ラベルの直前に移動され、型チェックフェーズで定数評価が行われるようになりました。

### `const.c` の変更

*   `defaultlit` 関数で、未知のリテラルに対するエラーメッセージが `%#N` を使用するように変更され、より詳細なノード情報が出力されるようになりました。
*   `OCONV` (型変換) オペレータに対する `CTINT`, `CTFLT`, `CTSTR` のケースが追加され、リテラル定数の型変換が `convlit1` を通じて処理されるようになりました。

### `subr.c` の変更

*   `badtype` 関数から不要な空行が削除されました。
*   `tempname` 関数で、一時変数の `etype` フィールドの設定が削除されました。これは、`typecheck` フェーズで型が決定されるようになったため、この段階での `etype` の設定が不要になったことを示唆しています。

### `typecheck` 関数の導入と役割

`walk.c` に新しく追加された `typecheck` 関数は、Goコンパイラの意味解析フェーズにおける中心的な役割を担います。

```c
Node*
typecheck(Node **np, int top)
{
    // ... (省略) ...
    n = *np;
    if(n == N || n->typecheck == 1)
        return n;
    if(n->typecheck == 2)
        fatal("typecheck loop"); // 型チェックの無限ループ検出
    n->typecheck = 2; // 現在型チェック中としてマーク

    if(n->sym && n->walkdef != 1)
        walkdef(n); // シンボル定義のウォーク

    // ... (省略) ...

    switch(n->op) {
    // ... (各種ASTノードに対する型チェックロジック) ...
    case OADD:
    case OAND:
    // ... (他の二項演算子) ...
        ok |= Erv;
        l = typecheck(&n->left, Erv | Eideal); // 左オペランドの型チェック
        r = typecheck(&n->right, Erv | Eideal); // 右オペランドの型チェック
        if(l->type == T || r->type == T)
            goto error;
        // ... (理想型と非理想型の混合処理、型の一致チェック) ...
        if(!okfor[n->op][et]) // 演算子と型の適合性チェック
            goto badbinary;
        // ... (スライスとnilの比較に関する特殊ルール) ...
        evconst(n); // 定数評価
        goto ret;

    case OCOM:
    case OMINUS:
    case ONOT:
    case OPLUS:
        ok |= Erv;
        l = typecheck(&n->left, Erv | Eideal); // オペランドの型チェック
        // ... (walkexpr(&n->left, Erv | Eideal, &n->ninit); // TODO: remove) ...
        if((t = l->type) == T)
            goto error;
        if(!okfor[n->op][t->etype]) { // 演算子と型の適合性チェック
            yyerror("invalid operation: %#O %T", n->op, t);
            goto error;
        }
        n->type = t;
        goto ret;
    // ... (他のノードタイプ) ...
    }

ret:
    evconst(n); // 定数評価
    // ... (型と評価コンテキストの整合性チェック) ...
out:
    lineno = lno;
    n->typecheck = 1; // 型チェック完了としてマーク
    *np = n;
    return n;
error:
    n->type = T; // エラー時は型をT (不明) に設定
    goto out;
}
```

この関数は、ASTノード `n` を再帰的に走査し、以下の処理を行います。

*   **型チェック状態の管理**: `n->typecheck` フラグを使用して、ノードの処理状態を管理します。これにより、DAG (Directed Acyclic Graph) 構造を持つASTにおいて、同じノードが複数回処理されたり、無限ループに陥ったりするのを防ぎます。
*   **シンボル定義のウォーク**: 必要に応じて `walkdef` を呼び出し、シンボルの定義を処理します。
*   **型の決定**: 各ノードの `n->type` フィールドに適切なGoの型を設定します。
*   **演算子の型適合性チェック**: `okfor` テーブルを使用して、二項演算子や単項演算子のオペランドの型がGoの仕様に適合しているかを検証します。例えば、`OADD` (加算) 演算子には `okforadd` に含まれる型のみが適用可能です。
*   **定数評価**: `evconst(n)` を呼び出し、コンパイル時定数である式を評価し、その結果をASTノードに格納します。
*   **ASTの書き換え**: 型チェックの過程で、ASTノードのオペレータ (`n->op`) や構造をより具体的な形に書き換えることがあります。例えば、型定義ノード (`OTARRAY`, `OTMAP` など) は `OTYPE` ノードに変換されます。
*   **エラー報告**: 型エラーが検出された場合、`yyerror` を使用してエラーメッセージを報告し、ノードの型を `T` (不明な型) に設定して、それ以降の処理が不正な型情報に依存しないようにします。

### `walkexpr` と `typecheck` の連携

`walk.c` の `walkexpr` 関数は、`typecheck` の導入により、その役割が変更されました。

```c
void
walkexpr(Node **np, int top, NodeList **init)
{
    // ... (省略) ...
    n = *np;
    if(n == N)
        return;

    // ... (省略) ...

    if(n->typecheck != 1)
        typecheck(&n, top | typeok); // walkexprの前に型チェックを実行

reswitch:
    // ... (残りのwalkexprロジック) ...
}
```

`walkexpr` の冒頭で `typecheck(&n, top | typeok);` が呼び出されることで、`walkexpr` がASTノードを変換する前に、そのノードが完全に型チェックされていることが保証されます。これにより、`walkexpr` は型に関する心配をすることなく、ASTの変換や最適化に集中できるようになります。これは、コンパイラの設計原則である「関心の分離 (Separation of Concerns)」を具現化したものです。

### `align.c` における `okfor` テーブルの拡張

`align.c` の `typeinit` 関数における `okfor` テーブルの初期化は、Goの型システムにおける演算子の振る舞いを定義する上で非常に重要です。

```c
void
typeinit(void)
{
    // ... (省略) ...
    for(i=0; i<NTYPE; i++) {
        if(isint[i] || i == TIDEAL) { // 整数型と理想型
            okforeq[i] = 1;
            okforcmp[i] = 1; // 比較可能
            okforarith[i] = 1; // 算術演算可能
            okforadd[i] = 1;
            okforand[i] = 1;
            issimple[i] = 1;
        }
        if(isfloat[i]) { // 浮動小数点型
            okforeq[i] = 1;
            okforcmp[i] = 1; // 比較可能
            okforadd[i] = 1;
            okforarith[i] = 1; // 算術演算可能
            issimple[i] = 1;
            // ... (minfltval, maxfltvalの初期化) ...
        }
    }

    issimple[TBOOL] = 1;
    okforadd[TSTRING] = 1; // 文字列は加算（結合）可能
    okforbool[TBOOL] = 1; // bool型は論理演算可能
    okforcap[TARRAY] = 1; // 配列はcap可能
    okforlen[TARRAY] = 1; // 配列はlen可能
    okforlen[TMAP] = 1; // マップはlen可能
    okforlen[TSTRING] = 1; // 文字列はlen可能

    // ... (他の型のokforeq, okforcmpの設定) ...

    for(i=0; i<nelem(okfor); i++)
        okfor[i] = okfornone; // 全ての演算子に対してデフォルトで「なし」を設定

    // binary (二項演算子)
    okfor[OADD] = okforadd;
    okfor[OAND] = okforand;
    okfor[OANDAND] = okforbool;
    // ... (他の二項演算子のマッピング) ...

    // unary (単項演算子)
    okfor[OCOM] = okforand;
    okfor[OMINUS] = okforarith;
    okfor[ONOT] = okforbool;
    okfor[OPLUS] = okforadd;

    // special (特殊演算子)
    okfor[OCAP] = okforcap;
    okfor[OLEN] = okforlen;

    // ... (整数値の範囲初期化) ...
}
```

この初期化ロジックは、Go言語の型システムがどのように演算子をサポートするかをコンパイラに教えます。例えば、`TIDEAL` 型が算術演算や比較演算をサポートすることは、型なし定数が柔軟に扱われるGoの重要な特徴をコンパイラが理解するために不可欠です。`okfor[OEND]` テーブルは、各演算子に対応する有効な型集合へのポインタを格納することで、型チェックロジックを簡潔かつ拡張可能にしています。

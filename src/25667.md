## 変更の背景

Goコンパイラの初期バージョンでは、構文解析にYacc（Yet Another Compiler Compiler）というツールが使用されていました。YaccはLALR(1)パーサーを生成する強力なツールですが、生成されるコードは人間が直接読むには難解であり、デバッグやメンテナンスが困難になることがあります。また、エラーリカバリの柔軟性にも限界がありました。

このコミットの背景には、以下の目的があったと考えられます。

1.  **可読性とメンテナンス性の向上**: Yaccが生成するコードは自動生成されたものであり、Go言語のコードとして直接記述された再帰下降型パーサーの方が、Go開発者にとって理解しやすく、メンテナンスしやすいと考えられます。
2.  **エラーメッセージの改善**: Yaccベースのパーサーは、エラーが発生した際に一般的なエラーメッセージを出すことが多く、具体的な問題箇所を特定しにくい場合があります。再帰下降型パーサーは、手動でエラーハンドリングロジックを組み込むことで、より詳細でユーザーフレンドリーなエラーメッセージを提供できます。
3.  **パフォーマンスの最適化**: コミットメッセージに記載されているように、再帰下降型パーサーへの移行により、パース時間とコンパイル時間の両方でパフォーマンスが向上しました。これは、Yaccが生成するテーブル駆動型パーサーのオーバーヘッドを削減し、Goのランタイムとコンパイラの特性に合わせた最適化が可能になったためと考えられます。
4.  **Go言語のイディオムへの適合**: Go言語はシンプルさと明示性を重視します。コンパイラの重要な部分であるパーサーをGo言語で直接記述することで、プロジェクト全体のコードベースの一貫性を高め、Goのイディオムに沿った実装にすることができます。

これらの理由から、Goコンパイラの開発チームは、より現代的でGoらしいアプローチである再帰下降型パーサーへの移行を決定したと考えられます。

## 前提知識の解説

### コンパイラの基本構成

コンパイラは、ソースコードを機械が実行できる形式に変換するソフトウェアです。その過程は主に以下のフェーズに分けられます。

1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（意味のある最小単位、例: 識別子、キーワード、演算子）のストリームに変換します。この処理を行うプログラムを「字句解析器（LexerまたはScanner）」と呼びます。
2.  **構文解析 (Syntax Analysis)**: トークンのストリームが、プログラミング言語の文法規則（構文）に適合しているかを検証し、通常は抽象構文木（AST: Abstract Syntax Tree）と呼ばれるツリー構造を構築します。この処理を行うプログラムを「構文解析器（Parser）」と呼びます。
3.  **意味解析 (Semantic Analysis)**: 構文的に正しいプログラムが、意味的にも正しいかを検証します（例: 型チェック、変数宣言の確認）。
4.  **中間コード生成 (Intermediate Code Generation)**: 抽象構文木から、ターゲットマシンに依存しない中間表現を生成します。
5.  **コード最適化 (Code Optimization)**: 中間コードを最適化し、より効率的なコードを生成します。
6.  **コード生成 (Code Generation)**: 最適化された中間コードを、ターゲットマシンの機械語に変換します。

このコミットは、主に「構文解析」のフェーズに関わる変更です。

### Yacc (Yet Another Compiler Compiler)

Yaccは、BNF（Backus-Naur Form）のような形式で記述された文法定義から、C言語のLALR(1)パーサーを自動生成するツールです。

*   **LALR(1)パーサー**: 左から右へ（Left-to-right）入力トークンを読み込み、右端導出を逆順に（Rightmost derivation in reverse）行い、1トークンの先読み（1-token lookahead）を行うパーサーです。効率的で広範な文法を扱えますが、生成されるコードはテーブル駆動型であり、人間が直接理解・修正するのは困難です。
*   **Yaccの動作**:
    1.  開発者は、言語の文法規則と、各規則が適用されたときに実行されるアクション（C言語のコード）を`.y`ファイルに記述します。
    2.  Yaccは、この`.y`ファイルを読み込み、パーシングテーブルとパーサーのC言語ソースコード（通常`y.tab.c`）を生成します。
    3.  生成されたCコードは、字句解析器（Lexer、通常Lex/Flexで生成）からのトークンを受け取り、文法規則に従って構文解析を行います。

### 再帰下降型パーサー (Recursive-Descent Parser)

再帰下降型パーサーは、文法の各非終端記号（例: `expression`, `statement`）に対応する関数を直接手書きで実装するパーサーの一種です。

*   **動作原理**: 各関数は、対応する文法規則を認識するために、字句解析器からトークンを読み込み、必要に応じて他のパーシング関数を再帰的に呼び出します。
*   **特徴**:
    *   **可読性**: コードが文法構造を直接反映するため、理解しやすいです。
    *   **デバッグの容易さ**: 手書きコードなので、通常のプログラムと同じようにデバッグできます。
    *   **エラーハンドリング**: エラーが発生した際に、より柔軟で詳細なエラーリカバリロジックを実装できます。
    *   **柔軟性**: 文法規則の変更や、特定の構文に対する特殊な処理の追加が比較的容易です。
    *   **制限**: 左再帰（例: `expr -> expr + term`）を持つ文法を直接扱うことができません。また、先読みトークンが複数必要な複雑な文法では、実装が複雑になることがあります。Goの文法はLL(1)に近い特性を持つため、再帰下降型パーサーに適しています。

## 技術的詳細

このコミットの主要な技術的変更点は、Goコンパイラの構文解析エンジンをYaccベースのテーブル駆動型パーサーから、Go言語で直接記述された再帰下降型パーサーに置き換えたことです。

### 新しいパーサーの構造

新しいパーサーは、`src/cmd/compile/internal/gc/parser.go`という新しいファイルに実装されています。このファイルには、`parser`という構造体が定義されており、これがパーサーの状態を管理します。

```go
type parser struct {
	tok    int32     // next token (one-token look-ahead)
	op     Op        // valid if tok == LASOP
	val    Val       // valid if tok == LLITERAL
	sym_   *Sym      // valid if tok == LNAME
	nest   int       // expression nesting level (for complit ambiguity resolution)
	yy     yySymType // for temporary use by next
	indent int       // tracing support
}
```

*   `tok`: 次に処理するトークン（1トークンの先読み）。
*   `op`, `val`, `sym_`: `tok`が特定のタイプ（演算子、リテラル、名前）の場合に、その詳細を保持します。
*   `nest`: 式のネストレベルを追跡し、複合リテラルの曖昧さ解消に利用されます。
*   `indent`: トレース機能のためのインデントレベル。

### パーサーの主要なメソッド

`parser`構造体には、構文解析の各要素に対応する多数のメソッドが定義されています。

*   `next()`: 字句解析器（`yylex`）から次のトークンを読み込み、`parser`構造体のフィールドを更新します。
*   `got(tok int32) bool`: 現在のトークンが`tok`と一致するかをチェックし、一致すれば`next()`を呼び出して次のトークンに進み`true`を返します。
*   `want(tok int32)`: 現在のトークンが`tok`と一致することを期待し、一致しなければエラーを報告します。
*   `error(context string)`: 構文エラーを報告し、エラーリカバリを試みます。
*   `trace(msg string) func()`: デバッグトレース用のヘルパー関数。関数の開始と終了をログに出力します。

### 構文解析のフロー

1.  **`parse_file()`**: `parser.go`のエントリポイントとなる関数で、ファイルの構文解析を開始します。
2.  **`loadsys()`**: ランタイム関数の定義をロードし、コンパイラがそれらへの呼び出しを生成できるようにします。
3.  **`file()`**: パッケージ宣言、インポート宣言、トップレベルの宣言（変数、定数、型、関数など）を解析します。
4.  **`package_()`**: `package`キーワードとパッケージ名を解析します。
5.  **`import_()`**: `import`宣言を解析します。単一のインポートパス、または括弧で囲まれた複数のインポートパスを処理します。
6.  **`common_dcl()`**: `var`, `const`, `type`などの共通の宣言を処理します。
7.  **`vardcl()`, `constdcl()`, `typedcl()`**: それぞれ変数、定数、型の宣言を解析します。
8.  **`simple_stmt()`**: 単純なステートメント（代入、インクリメント/デクリメント、関数呼び出しなど）を解析します。
9.  **`if_stmt()`, `for_stmt()`, `switch_stmt()`, `select_stmt()`**: `if`, `for`, `switch`, `select`などの制御構造を解析します。
10. **`expr()`, `uexpr()`, `pexpr()`**: 式の解析を行います。`bexpr`は二項演算子、`uexpr`は単項演算子、`pexpr`はプライマリ式（リテラル、識別子、括弧で囲まれた式など）を扱います。

### Yaccパーサーとの切り替え

*   `src/cmd/compile/internal/gc/lex.go`が変更され、新しいパーサーと古いYaccベースのパーサーを切り替えるためのロジックが追加されました。
*   `oldparser`というグローバル変数が導入され、これが`0`（デフォルト）の場合は新しい再帰下降型パーサーが、`0`以外の場合は古いYaccパーサーが使用されます。
*   コマンドラインオプション`-oldparser`を設定することで、古いパーサーを使用できます。
*   `lex.go`内のコメントアウトされた行`oldparser = 1`をアンコメントすることで、古いパーサーを強制的に有効にすることもできます（これは一時的なデバッグ目的のオプションであり、最終的には削除される予定であることが`TODO(gri) remove this eventually`というコメントからわかります）。

### パフォーマンスとエラーメッセージの改善

コミットメッセージによると、この変更により以下の改善がもたらされました。

*   `make.bash`におけるファイルあたりの平均パース時間が約18%削減。
*   `cmd/compile`のビルドにおけるコンパイル時間が約3%削減。
*   構文エラーメッセージが改善され、より正確なエラー情報を提供できるようになりました。これは、再帰下降型パーサーが手動でエラーリカバリロジックを細かく制御できるためです。

### インポート時のパーサー状態の管理

Go言語では、パッケージのインポート時にそのパッケージのソースコードも解析する必要があります。この際、現在のパーサーの状態を一時的に保存し、インポートされたパッケージの解析後に元の状態に戻す必要があります。

*   `push_parser()`: 現在のパーサーの状態（`thenewparser`）を`savedstate`スライスに保存し、新しいパーサーインスタンスを初期化します。
*   `pop_parser()`: `savedstate`から以前のパーサーの状態を復元します。

これにより、インポート処理中にパーサーの状態が適切に管理され、メインの解析フローに影響を与えないようになっています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/parser.go`

このファイルは、Go言語の構文解析の中核を担う新しい再帰下降型パーサーの実装です。

*   **`parser`構造体**:
    *   `tok`: 現在のトークン。`yylex`関数（字句解析器）によって設定されます。
    *   `op`, `val`, `sym_`: `tok`が特定の種類のトークンである場合（例: 演算子、リテラル、識別子）に、その詳細な値やシンボルを保持します。
    *   `nest`: 式のネストレベルを追跡し、特に複合リテラル（`T{...}`のような構文）の曖昧さを解決するために使用されます。
    *   `indent`: デバッグトレースの際に、出力のインデントレベルを管理します。

*   **`next()`メソッド**:
    *   字句解析器`yylex`を呼び出して次のトークンを取得し、`parser`構造体の`tok`, `op`, `val`, `sym_`フィールドを更新します。これにより、パーサーは常に次のトークンを先読みしている状態になります。

*   **`got(tok int32) bool`メソッド**:
    *   現在の`tok`が引数`tok`と一致するかをチェックします。
    *   一致した場合、`next()`を呼び出して次のトークンに進み、`true`を返します。
    *   一致しない場合、`false`を返します。これは、オプションの構文要素を解析する際によく使われます。

*   **`want(tok int32)`メソッド**:
    *   現在の`tok`が引数`tok`と一致することを「期待」します。
    *   一致しない場合、`p.error()`を呼び出して構文エラーを報告します。これは、必須の構文要素を解析する際に使われます。

*   **`syntax_error(msg string)`および`p.error(context string)`**:
    *   構文エラーを報告するための関数とメソッドです。
    *   `p.error`は、エラーが発生した際に、括弧やブレースのペアをスキップして、ある程度の回復を試みるロジックを含んでいます。これにより、1つのエラーで後続の多数のエラーが報告されるのを防ぎ、より意味のあるエラーメッセージを提供できます。

*   **`trace(msg string) func()`**:
    *   デバッグ時にパーサーの実行フローを追跡するためのヘルパーです。
    *   関数の開始時にメッセージとインデントを出力し、`defer`で呼び出される無名関数が関数の終了時にインデントを減らして終了メッセージを出力します。これにより、パーサーがどの文法規則を解析しているかを視覚的に追跡できます。

*   **`file()`メソッド**:
    *   Goソースファイルのトップレベルの構造（パッケージ宣言、インポート宣言、トップレベルの宣言リスト）を解析するエントリポイントです。
    *   `p.package_()`でパッケージ宣言を、`p.import_()`でインポート宣言を、`p.xdcl_list()`でトップレベルの宣言（関数、変数、定数、型）を解析します。

*   **`import_()`、`import_stmt()`、`import_here()`、`import_package()`、`import_there()`**:
    *   インポート宣言の複雑な処理を扱います。
    *   インポートパスの解析、パッケージ名の解決、インポートされたパッケージのシンボルテーブルへの登録などを行います。
    *   `push_parser()`と`pop_parser()`を使って、インポートされたパッケージの解析中に現在のパーサーの状態を一時的に保存し、復元するメカニズムが実装されています。

*   **`expr()`、`uexpr()`、`pexpr()`**:
    *   Go言語の式の構文解析を担当します。これらは再帰的に呼び出され、演算子の優先順位と結合規則を処理します。
    *   `bexpr(prec int)`は二項演算子を、`uexpr()`は単項演算子を、`pexpr(keep_parens bool)`は基本的なオペランド（リテラル、識別子、関数呼び出し、配列アクセス、複合リテラルなど）を解析します。

### `src/cmd/compile/internal/gc/lex.go`

*   **`var oldparser int`**:
    *   新しいパーサーと古いYaccパーサーを切り替えるためのフラグです。デフォルトは`0`（新しいパーサーを使用）です。
    *   `obj.Flagcount("oldparser", "use old parser", &oldparser)`により、コマンドラインオプション`-oldparser`でこのフラグを設定できるようになります。

*   **`yyparse()`関数**:
    *   Goコンパイラのメインのパース関数です。
    *   `if oldparser != 0`の条件分岐により、`oldparser`フラグの値に応じて、Yaccパーサー（`theparser.Parse(yy{})`）または新しい再帰下降型パーサー（`parse_file()`）のどちらかを呼び出します。

*   **`importfile()`と`unimportfile()`の変更**:
    *   これらの関数は、パッケージのインポートとアンインポートを処理します。
    *   `oldparser == 0`（新しいパーサーが有効な場合）の条件で、`push_parser()`と`pop_parser()`が呼び出されるようになりました。これにより、インポートされたパッケージの解析中にパーサーの状態が適切に保存・復元され、ネストされた解析が正しく機能するようになります。

*   **`loophack`の条件付き適用**:
    *   `loophack`は、古いYaccパーサーの特定の挙動（特に`for`, `if`, `switch`, `select`ステートメントの構文解析における曖昧さ）を解決するためのメカニズムでした。
    *   新しいパーサーではこのハックが不要になったため、`if oldparser != 0 && ...`という条件が追加され、古いパーサーが使用されている場合にのみ`loophack`が適用されるようになりました。

これらの変更により、Goコンパイラはより現代的で効率的、かつメンテナンスしやすいパーサーを手に入れました。

## 変更の背景

Goコンパイラの初期バージョンでは、構文解析にYacc（Yet Another Compiler Compiler）というツールが使用されていました。YaccはLALR(1)パーサーを生成する強力なツールですが、生成されるコードは人間が直接読むには難解であり、デバッグやメンテナンスが困難になることがあります。また、エラーリカバリの柔軟性にも限界がありました。

このコミットの背景には、以下の目的があったと考えられます。

1.  **可読性とメンテナンス性の向上**: Yaccが生成するコードは自動生成されたものであり、Go言語のコードとして直接記述された再帰下降型パーサーの方が、Go開発者にとって理解しやすく、メンテナンスしやすいと考えられます。
2.  **エラーメッセージの改善**: Yaccベースのパーサーは、エラーが発生した際に一般的なエラーメッセージを出すことが多く、具体的な問題箇所を特定しにくい場合があります。再帰下降型パーサーは、手動でエラーハンドリングロジックを組み込むことで、より詳細でユーザーフレンドリーなエラーメッセージを提供できます。
3.  **パフォーマンスの最適化**: コミットメッセージに記載されているように、再帰下降型パーサーへの移行により、パース時間とコンパイル時間の両方でパフォーマンスが向上しました。これは、Yaccが生成するテーブル駆動型パーサーのオーバーヘッドを削減し、Goのランタイムとコンパイラの特性に合わせた最適化が可能になったためと考えられます。
4.  **Go言語のイディオムへの適合**: Go言語はシンプルさと明示性を重視します。コンパイラの重要な部分であるパーサーをGo言語で直接記述することで、プロジェクト全体のコードベースの一貫性を高め、Goのイディオムに沿った実装にすることができます。

これらの理由から、Goコンパイラの開発チームは、より現代的でGoらしいアプローチである再帰下降型パーサーへの移行を決定したと考えられます。

## 前提知識の解説

### コンパイラの基本構成

コンパイラは、ソースコードを機械が実行できる形式に変換するソフトウェアです。その過程は主に以下のフェーズに分けられます。

1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（意味のある最小単位、例: 識別子、キーワード、演算子）のストリームに変換します。この処理を行うプログラムを「字句解析器（LexerまたはScanner）」と呼びます。
2.  **構文解析 (Syntax Analysis)**: トークンのストリームが、プログラミング言語の文法規則（構文）に適合しているかを検証し、通常は抽象構文木（AST: Abstract Syntax Tree）と呼ばれるツリー構造を構築します。この処理を行うプログラムを「構文解析器（Parser）」と呼びます。
3.  **意味解析 (Semantic Analysis)**: 構文的に正しいプログラムが、意味的にも正しいかを検証します（例: 型チェック、変数宣言の確認）。
4.  **中間コード生成 (Intermediate Code Generation)**: 抽象構文木から、ターゲットマシンに依存しない中間表現を生成します。
5.  **コード最適化 (Code Optimization)**: 中間コードを最適化し、より効率的なコードを生成します。
6.  **コード生成 (Code Generation)**: 最適化された中間コードを、ターゲットマシンの機械語に変換します。

このコミットは、主に「構文解析」のフェーズに関わる変更です。

### Yacc (Yet Another Compiler Compiler)

Yaccは、BNF（Backus-Naur Form）のような形式で記述された文法定義から、C言語のLALR(1)パーサーを自動生成するツールです。

*   **LALR(1)パーサー**: 左から右へ（Left-to-right）入力トークンを読み込み、右端導出を逆順に（Rightmost derivation in reverse）行い、1トークンの先読み（1-token lookahead）を行うパーサーです。効率的で広範な文法を扱えますが、生成されるコードはテーブル駆動型であり、人間が直接理解・修正するのは困難です。
*   **Yaccの動作**:
    1.  開発者は、言語の文法規則と、各規則が適用されたときに実行されるアクション（C言語のコード）を`.y`ファイルに記述します。
    2.  Yaccは、この`.y`ファイルを読み込み、パーシングテーブルとパーサーのC言語ソースコード（通常`y.tab.c`）を生成します。
    3.  生成されたCコードは、字句解析器（Lexer、通常Lex/Flexで生成）からのトークンを受け取り、文法規則に従って構文解析を行います。

### 再帰下降型パーサー (Recursive-Descent Parser)

再帰下降型パーサーは、文法の各非終端記号（例: `expression`, `statement`）に対応する関数を直接手書きで実装するパーサーの一種です。

*   **動作原理**: 各関数は、対応する文法規則を認識するために、字句解析器からトークンを読み込み、必要に応じて他のパーシング関数を再帰的に呼び出します。
*   **特徴**:
    *   **可読性**: コードが文法構造を直接反映するため、理解しやすいです。
    *   **デバッグの容易さ**: 手書きコードなので、通常のプログラムと同じようにデバッグできます。
    *   **エラーハンドリング**: エラーが発生した際に、より柔軟で詳細なエラーリカバリロジックを実装できます。
    *   **柔軟性**: 文法規則の変更や、特定の構文に対する特殊な処理の追加が比較的容易です。
    *   **制限**: 左再帰（例: `expr -> expr + term`）を持つ文法を直接扱うことができません。また、先読みトークンが複数必要な複雑な文法では、実装が複雑になることがあります。Goの文法はLL(1)に近い特性を持つため、再帰下降型パーサーに適しています。

## 技術的詳細

このコミットの主要な技術的変更点は、Goコンパイラの構文解析エンジンをYaccベースのテーブル駆動型パーサーから、Go言語で直接記述された再帰下降型パーサーに置き換えたことです。

### 新しいパーサーの構造

新しいパーサーは、`src/cmd/compile/internal/gc/parser.go`という新しいファイルに実装されています。このファイルには、`parser`という構造体が定義されており、これがパーサーの状態を管理します。

```go
type parser struct {
	tok    int32     // next token (one-token look-ahead)
	op     Op        // valid if tok == LASOP
	val    Val       // valid if tok == LLITERAL
	sym_   *Sym      // valid if tok == LNAME
	nest   int       // expression nesting level (for complit ambiguity resolution)
	yy     yySymType // for temporary use by next
	indent int       // tracing support
}
```

*   `tok`: 次に処理するトークン（1トークンの先読み）。
*   `op`, `val`, `sym_`: `tok`が特定のタイプ（演算子、リテラル、名前）の場合に、その詳細を保持します。
*   `nest`: 式のネストレベルを追跡し、複合リテラルの曖昧さ解消に利用されます。
*   `indent`: トレース機能のためのインデントレベル。

### パーサーの主要なメソッド

`parser`構造体には、構文解析の各要素に対応する多数のメソッドが定義されています。

*   `next()`: 字句解析器（`yylex`）から次のトークンを読み込み、`parser`構造体のフィールドを更新します。
*   `got(tok int32) bool`: 現在のトークンが`tok`と一致するかをチェックし、一致すれば`next()`を呼び出して次のトークンに進み`true`を返します。
*   `want(tok int32)`: 現在のトークンが`tok`と一致することを期待し、一致しなければエラーを報告します。
*   `error(context string)`: 構文エラーを報告し、エラーリカバリを試みます。
*   `trace(msg string) func()`: デバッグトレース用のヘルパー関数。関数の開始と終了をログに出力します。

### 構文解析のフロー

1.  **`parse_file()`**: `parser.go`のエントリポイントとなる関数で、ファイルの構文解析を開始します。
2.  **`loadsys()`**: ランタイム関数の定義をロードし、コンパイラがそれらへの呼び出しを生成できるようにします。
3.  **`file()`**: パッケージ宣言、インポート宣言、トップレベルの宣言（変数、定数、型、関数など）を解析します。
4.  **`package_()`**: `package`キーワードとパッケージ名を解析します。
5.  **`import_()`**: `import`宣言を解析します。単一のインポートパス、または括弧で囲まれた複数のインポートパスを処理します。
6.  **`common_dcl()`**: `var`, `const`, `type`などの共通の宣言を処理します。
7.  **`vardcl()`, `constdcl()`, `typedcl()`**: それぞれ変数、定数、型の宣言を解析します。
8.  **`simple_stmt()`**: 単純なステートメント（代入、インクリメント/デクリメント、関数呼び出しなど）を解析します。
9.  **`if_stmt()`, `for_stmt()`, `switch_stmt()`, `select_stmt()`**: `if`, `for`, `switch`, `select`などの制御構造を解析します。
10. **`expr()`, `uexpr()`, `pexpr()`**: 式の解析を行います。`bexpr`は二項演算子、`uexpr`は単項演算子、`pexpr`はプライマリ式（リテラル、識別子、括弧で囲まれた式など）を扱います。

### Yaccパーサーとの切り替え

*   `src/cmd/compile/internal/gc/lex.go`が変更され、新しいパーサーと古いYaccベースのパーサーを切り替えるためのロジックが追加されました。
*   `oldparser`というグローバル変数が導入され、これが`0`（デフォルト）の場合は新しい再帰下降型パーサーが、`0`以外の場合は古いYaccパーサーが使用されます。
*   コマンドラインオプション`-oldparser`を設定することで、古いパーサーを使用できます。
*   `lex.go`内のコメントアウトされた行`oldparser = 1`をアンコメントすることで、古いパーサーを強制的に有効にすることもできます（これは一時的なデバッグ目的のオプションであり、最終的には削除される予定であることが`TODO(gri) remove this eventually`というコメントからわかります）。

コミットメッセージによると、この変更により以下の改善がもたらされました。

### インポート時のパーサー状態の管理

Go言語では、パッケージのインポート時にそのパッケージのソースコードも解析する必要があります。この際、現在のパーサーの状態を一時的に保存し、インポートされたパッケージの解析後に元の状態に戻す必要があります。

*   `push_parser()`: 現在のパーサーの状態（`thenewparser`）を`savedstate`スライスに保存し、新しいパーサーインスタンスを初期化します。
*   `pop_parser()`: `savedstate`から以前のパーサーの状態を復元します。

これにより、インポート処理中にパーサーの状態が適切に管理され、メインの解析フローに影響を与えないようになっています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/parser.go`

このファイルは、Go言語の構文解析の中核を担う新しい再帰下降型パーサーの実装です。

*   **`parser`構造体**:
    *   `tok`: 現在のトークン。`yylex`関数（字句解析器）によって設定されます。
    *   `op`, `val`, `sym_`: `tok`が特定の種類のトークンである場合（例: 演算子、リテラル、識別子）に、その詳細な値やシンボルを保持します。
    *   `nest`: 式のネストレベルを追跡し、特に複合リテラル（`T{...}`のような構文）の曖昧さを解決するために使用されます。
    *   `indent`: デバッグトレースの際に、出力のインデントレベルを管理します。

*   **`next()`メソッド**:
    *   字句解析器`yylex`を呼び出して次のトークンを取得し、`parser`構造体の`tok`, `op`, `val`, `sym_`フィールドを更新します。これにより、パーサーは常に次のトークンを先読みしている状態になります。

*   **`got(tok int32) bool`メソッド**:
    *   現在の`tok`が引数`tok`と一致するかをチェックします。
    *   一致した場合、`next()`を呼び出して次のトークンに進み、`true`を返します。
    *   一致しない場合、`false`を返します。これは、オプションの構文要素を解析する際によく使われます。

*   **`want(tok int32)`メソッド**:
    *   現在の`tok`が引数`tok`と一致することを「期待」します。
    *   一致しない場合、`p.error()`を呼び出して構文エラーを報告します。これは、必須の構文要素を解析する際に使われます。

*   **`syntax_error(msg string)`および`p.error(context string)`**:
    *   構文エラーを報告するための関数とメソッドです。
    *   `p.error`は、エラーが発生した際に、括弧やブレースのペアをスキップして、ある程度の回復を試みるロジックを含んでいます。これにより、1つのエラーで後続の多数のエラーが報告されるのを防ぎ、より意味のあるエラーメッセージを提供できます。

*   **`trace(msg string) func()`**:
    *   デバッグ時にパーサーの実行フローを追跡するためのヘルパーです。
    *   関数の開始時にメッセージとインデントを出力し、`defer`で呼び出される無名関数が関数の終了時にインデントを減らして終了メッセージを出力します。これにより、パーサーがどの文法規則を解析しているかを視覚的に追跡できます。

*   **`file()`メソッド**:
    *   Goソースファイルのトップレベルの構造（パッケージ宣言、インポート宣言、トップレベルの宣言リスト）を解析するエントリポイントです。
    *   `p.package_()`でパッケージ宣言を、`p.import_()`でインポート宣言を、`p.xdcl_list()`でトップレベルの宣言（関数、変数、定数、型）を解析します。

*   **`import_()`、`import_stmt()`、`import_here()`、`import_package()`、`import_there()`**:
    *   インポート宣言の複雑な処理を扱います。
    *   インポートパスの解析、パッケージ名の解決、インポートされたパッケージのシンボルテーブルへの登録などを行います。
    *   `push_parser()`と`pop_parser()`を使って、インポートされたパッケージの解析中に現在のパーサーの状態を一時的に保存し、復元するメカニズムが実装されています。

*   **`expr()`、`uexpr()`、`pexpr()`**:
    *   Go言語の式の構文解析を担当します。これらは再帰的に呼び出され、演算子の優先順位と結合規則を処理します。
    *   `bexpr(prec int)`は二項演算子を、`uexpr()`は単項演算子を、`pexpr(keep_parens bool)`は基本的なオペランド（リテラル、識別子、関数呼び出し、配列アクセス、複合リテラルなど）を解析します。

### `src/cmd/compile/internal/gc/lex.go`

*   **`var oldparser int`**:
    *   新しいパーサーと古いYaccパーサーを切り替えるためのフラグです。デフォルトは`0`（新しいパーサーを使用）です。
    *   `obj.Flagcount("oldparser", "use old parser", &oldparser)`により、コマンドラインオプション`-oldparser`でこのフラグを設定できるようになります。

*   **`yyparse()`関数**:
    *   Goコンパイラのメインのパース関数です。
    *   `if oldparser != 0`の条件分岐により、`oldparser`フラグの値に応じて、Yaccパーサー（`theparser.Parse(yy{})`）または新しい再帰下降型パーサー（`parse_file()`）のどちらかを呼び出します。

*   **`importfile()`と`unimportfile()`の変更**:
    *   これらの関数は、パッケージのインポートとアンインポートを処理します。
    *   `oldparser == 0`（新しいパーサーが有効な場合）の条件で、`push_parser()`と`pop_parser()`が呼び出されるようになりました。これにより、インポートされたパッケージの解析中にパーサーの状態が適切に保存・復元され、ネストされた解析が正しく機能するようになります。

*   **`loophack`の条件付き適用**:
    *   `loophack`は、古いYaccパーサーの特定の挙動（特に`for`, `if`, `switch`, `select`ステートメントの構文解析における曖昧さ）を解決するためのメカニズムでした。
    *   新しいパーサーではこのハックが不要になったため、`if oldparser != 0 && ...`という条件が追加され、古いパーサーが使用されている場合にのみ`loophack`が適用されるようになりました。

これらの変更により、Goコンパイラはより現代的で効率的、かつメンテナンスしやすいパーサーを手に入れました。

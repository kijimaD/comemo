## 元コミット内容

```
runtime: run safe-point function before entering _Psyscall

Currently, we run a P's safe-point function immediately after entering
_Psyscall state. This is unsafe, since as soon as we put the P in
_Psyscall, we no longer control the P and another M may claim it.
We'll still run the safe-point function only once (because doing so
races on an atomic), but the P may no longer be at a safe-point when
we do so.

In particular, this means that the use of forEachPto dispose all P's
gcw caches is unsafe. A P may enter a syscall, run the safe-point
function, and dispose the P's gcw cache concurrently with another M
claiming the P and attempting to use its gcw cache. If this happens,
we may empty the gcw's workbuf after putting it on
work.{full,partial}, or add pointers to it after putting it in
work.empty. This will cause an assertion failure when we later pop the
workbuf from the list and its object count is inconsistent with the
list we got it from.

Fix this by running the safe-point function just before putting the P
in _Psyscall.

Related to #11640. This probably fixes this issue, but while I'm able
to show that we can enter a bad safe-point state as a result of this,
I can't reproduce that specific failure.
```

## 変更の背景

このコミットは、Goランタイムにおけるガベージコレクション（GC）の安全性と正確性に関する重要なバグを修正するために導入されました。具体的には、GoスケジューラがP（プロセッサ）を`_Psyscall`状態（システムコール中）に移行させる際のセーフポイント関数の実行タイミングに問題がありました。

以前の実装では、Pが`_Psyscall`状態に入った「直後」にセーフポイント関数が実行されていました。しかし、Pが`_Psyscall`状態になると、GoスケジューラはそのPの制御を失い、別のM（OSスレッド）がそのPをすぐに取得してしまう可能性がありました。このタイミングのずれにより、セーフポイント関数が実行される時点でPがもはや「セーフポイント」にない状態になることがあり、GCの整合性が損なわれるリスクがありました。

特に問題となったのは、GCがすべてのPの`gcw`（GC Work buffer）キャッシュを破棄するために`forEachP`を使用するシナリオです。Pがシステムコールに入り、セーフポイント関数を実行して`gcw`キャッシュを破棄する処理が、別のMがそのPを要求し、その`gcw`キャッシュを使用しようとする処理と並行して発生する可能性がありました。これにより、`gcw`の`workbuf`が`work.{full,partial}`リストに置かれた後に空にされたり、`work.empty`に置かれた後にポインタが追加されたりする可能性がありました。結果として、後で`workbuf`がリストから取り出された際に、そのオブジェクトカウントがリストの状態と矛盾し、アサーション失敗を引き起こす可能性がありました。

このコミットは、この競合状態を解消し、GCのデータ整合性を保証するために、セーフポイント関数の実行タイミングを調整することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の概念を理解しておく必要があります。

1.  **G-M-Pモデル**: Goランタイムのスケジューラは、G（Goroutine）、M（Machine/OSスレッド）、P（Processor/論理プロセッサ）の3つのエンティティで構成されます。
    *   **G (Goroutine)**: Goの軽量スレッド。Goプログラムの実行単位です。
    *   **M (Machine)**: OSスレッド。Gを実行する実際のOSスレッドです。
    *   **P (Processor)**: 論理プロセッサ。MにGを割り当てるためのコンテキストを提供します。Pは実行可能なGのキューを保持し、MがGを実行するために必要です。Pの数は通常、CPUコア数に制限されます。

2.  **セーフポイント (Safe Point)**: ガベージコレクタが正確に動作するために、すべてのGoroutineが一時的に停止し、そのスタックやレジスタの状態がGCにとって既知で安全な状態になる場所を指します。GCがポインタをスキャンして到達可能なオブジェクトを特定するために不可欠です。GoのGCは並行して動作しますが、特定のフェーズ（例えば、マークフェーズの開始時）では、すべてのGoroutineがセーフポイントに到達する必要があります。

3.  **セーフポイント関数 (`runSafePointFn`)**: Pが特定の状態（例えば、アイドル状態やシステムコール状態）に移行する際に実行される可能性のある関数です。この関数は、GCが必要とするクリーンアップや状態更新（例: `gcw`キャッシュの破棄）を行います。

4.  **`_Psyscall`状態**: Pがシステムコールを実行しているGoroutineに割り当てられている状態を示します。Goroutineがシステムコールに入ると、GoスケジューラはそのGoroutineの実行を一時的に停止し、MはOSカーネルに制御を渡します。この間、Pは他のGoroutineを実行するために解放される可能性があります。

5.  **`gcw`キャッシュ (GC Work buffer cache)**: ガベージコレクションの作業バッファです。GoのGCは、オブジェクトのポインタが変更された際に（ライトバリア）、その変更を記録するために`gcw`キャッシュを使用します。各Pは独自の`gcw`キャッシュを持ち、GC作業を効率的にバッファリングします。GCサイクル中に、これらのキャッシュは処理され、最終的に破棄される必要があります。

6.  **`systemstack`**: Goランタイムの内部関数で、現在のGoroutineのスタックではなく、特別なシステムスタックで関数を実行するために使用されます。これは、スタックの拡張（スタックスプリット）が起こる可能性のある関数を、GCなどの重要なランタイム処理中に安全に実行するために使用されます。

## 技術的詳細

このコミットの核心は、GoランタイムのスケジューラがGoroutineをシステムコールに移行させる際の、Pの状態管理とセーフポイント関数の実行順序の変更です。

以前のロジックでは、`reentersyscall`関数内でPの状態を`_Psyscall`に設定した「後」に`runSafePointFn`が呼び出されていました。

```go
// 古いコードの抜粋
atomicstore(&_g_.m.p.ptr().status, _Psyscall) // Pの状態を_Psyscallに設定
if _g_.m.p.ptr().runSafePointFn != 0 {
    systemstack(runSafePointFn) // セーフポイント関数を実行
}
```

この順序の問題点は、`atomicstore(&_g_.m.p.ptr().status, _Psyscall)`が実行された瞬間から、そのPはシステムコール中であるとマークされ、GoスケジューラはいつでもそのPを別のMに割り当てることが可能になる点です。もし、`runSafePointFn`の実行中に別のMがこのPを奪い、その`gcw`キャッシュにアクセスしようとすると、`gcw`キャッシュが不整合な状態（例えば、破棄中であるにもかかわらず使用される）になり、ランタイムパニックやアサーション失敗を引き起こす可能性がありました。

特に、GCがすべてのPの`gcw`キャッシュを破棄する際に、`forEachP`ループで各Pを処理する間に、Pがシステムコールに入り、その`gcw`キャッシュが破棄されるという競合状態が発生し得ました。これにより、`gcw`の`workbuf`が不適切なタイミングで空にされたり、ポインタが追加されたりして、最終的に`workbuf`のオブジェクトカウントが矛盾するという問題が生じました。

このコミットでは、この問題を解決するために、`runSafePointFn`の呼び出しを`_Psyscall`状態への移行「前」に移動しました。

```go
// 新しいコードの抜粋
if _g_.m.p.ptr().runSafePointFn != 0 {
    systemstack(runSafePointFn) // セーフポイント関数を実行
}
atomicstore(&_g_.m.p.ptr().status, _Psyscall) // Pの状態を_Psyscallに設定
```

この変更により、PがまだGoスケジューラの制御下にある状態でセーフポイント関数が実行されることが保証されます。`_Psyscall`状態に移行する前に`gcw`キャッシュの破棄などの必要なクリーンアップが完了するため、Pが他のMに再利用された際に`gcw`キャッシュの不整合が発生するリスクがなくなります。これにより、GCの正確性とランタイムの安定性が向上します。

コミットメッセージでは、関連する問題としてGo issue `#11640`が挙げられていますが、このコミットが直接その問題を修正するかどうかは不明確であり、特定の失敗を再現することはできなかったと述べられています。しかし、この変更によって「悪いセーフポイント状態」に入る可能性が排除されることは示されています。

## コアとなるコードの解説

この変更は、`reentersyscall`関数内の`atomicstore(&_g_.m.p.ptr().status, _Psyscall)`の呼び出しと、その後に続く`systemstack(runSafePointFn)`の呼び出しの順序を入れ替えるものです。

*   **削除されたコード**:
    ```go
    	atomicstore(&_g_.m.p.ptr().status, _Psyscall)
    	if _g_.m.p.ptr().runSafePointFn != 0 {
    		// runSafePointFn may stack split if run on this stack
    		systemstack(runSafePointFn)
    	}
    ```
    この部分では、まずPの状態を`_Psyscall`に設定し、その後にセーフポイント関数を実行していました。これが競合状態の原因でした。

*   **追加されたコード**:
    ```go
    	if _g_.m.p.ptr().runSafePointFn != 0 {
    		// runSafePointFn may stack split if run on this stack
    		systemstack(runSafePointFn)
    	}
    	_g_.m.syscalltick = _g_.m.p.ptr().syscalltick
    	_g_.sysblocktraced = true
    	_g_.m.mcache = nil
    	_g_.m.p.ptr().m = 0
    	atomicstore(&_g_.m.p.ptr().status, _Psyscall)
    ```
    新しいコードでは、`_g_.m.p.ptr().status`を`_Psyscall`に設定する「前」に、`runSafePointFn`が呼び出されるようになりました。これにより、PがまだGoスケジューラの制御下にある状態でセーフポイント関連の処理が完了することが保証されます。`_g_.m.syscalltick`などの他のP関連の状態更新は、セーフポイント関数の実行後に、しかし`_Psyscall`状態への最終的な移行前に引き続き行われます。

このシンプルな順序の変更により、Pがシステムコールに入った際に、GCの`gcw`キャッシュなどの重要なリソースが安全かつ一貫した状態で処理されることが保証され、ランタイムの安定性とGCの正確性が向上します。

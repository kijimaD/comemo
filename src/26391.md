このコミットは、Goの標準ライブラリである `net/http` パッケージ内の `server.go` ファイルに対する変更です。具体的には、HTTPリクエストハンドラが既に完了した後に `http.CloseNotifier` または `http.Hijacker` インターフェースのメソッドが不適切に呼び出された場合に、プログラムがパニック（異常終了）するように挙動を変更しています。これにより、不正な状態での操作を防ぎ、開発者が早期に問題を特定できるようにしています。

## 変更の背景

この変更の背景には、`net/http` パッケージの `response` 構造体が管理するHTTPリクエストのライフサイクルと、`CloseNotifier` および `Hijacker` インターフェースの利用タイミングに関する潜在的な問題がありました。

`http.ResponseWriter` は、HTTPハンドラがクライアントに応答を書き込むためのインターフェースです。このインターフェースは、追加の機能を提供する `http.CloseNotifier` や `http.Hijacker` といったインターフェースを実装している場合があります。
- `CloseNotifier`: クライアントが接続を閉じたときに通知を受け取るためのチャネルを提供します。これにより、ハンドラはクライアントが途中で接続を切断した場合に、不要な処理を中断できます。
- `Hijacker`: HTTP接続を乗っ取り（ハイジャックし）、低レベルのTCP接続を直接操作できるようにします。これはWebSocketのようなプロトコルを実装する際に必要となります。

問題は、HTTPハンドラがリクエストの処理を終えた後（つまり、応答が完全に送信された後や、ハンドラ関数がリターンした後）に、これらのインターフェースのメソッドが呼び出される可能性があったことです。ハンドラが完了した後にこれらのメソッドが呼び出されると、`response` 構造体の内部状態が既にクリーンアップされていたり、予期しない状態になっていたりする可能性があり、結果として未定義の動作やリソースリーク、あるいはクラッシュを引き起こす可能性がありました。

このコミットは、このような「不正な使用 (bogus use)」を検出し、明確にパニックさせることで、開発者がこのような誤用を早期に発見し、修正できるようにすることを目的としています。これにより、ランタイムでのサイレントなエラーや予測不能な挙動を防ぎ、アプリケーションの堅牢性を向上させます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語および `net/http` パッケージの概念を理解しておく必要があります。

1.  **`net/http` パッケージ**: Go言語の標準ライブラリで、HTTPクライアントとサーバーの実装を提供します。Webアプリケーション開発の基盤となります。
2.  **`http.ResponseWriter` と `http.Request`**: HTTPハンドラのシグネチャ `func(w http.ResponseWriter, r *http.Request)` で使われる主要なインターフェースと構造体です。`ResponseWriter` はクライアントへの応答を書き込むために使われ、`Request` はクライアントからのリクエスト情報を含みます。
3.  **`http.CloseNotifier` インターフェース**:
    ```go
    type CloseNotifier interface {
        CloseNotify() <-chan bool
    }
    ```
    `CloseNotify` メソッドは、クライアントがHTTP接続を閉じたときに値が送信されるチャネルを返します。これにより、サーバーはクライアントの切断を検知し、例えば長時間実行される処理を中断することができます。
4.  **`http.Hijacker` インターフェース**:
    ```go
    type Hijacker interface {
        Hijack() (c net.Conn, rw *bufio.ReadWriter, err error)
    }
    ```
    `Hijack` メソッドは、基となるTCP接続と、その接続に関連付けられた `bufio.ReadWriter` を返します。これにより、HTTPサーバーの抽象化をバイパスして、開発者が直接低レベルのネットワーク操作を行うことが可能になります。これはWebSocketハンドシェイクの完了後などに利用されます。
5.  **`atomic` パッケージ**: Go言語の `sync/atomic` パッケージは、低レベルのアトミック操作（不可分操作）を提供します。これにより、ミューテックスなどのロック機構を使わずに、共有メモリ上の変数を安全に操作できます。特に、複数のゴルーチンから同時にアクセスされる可能性のあるカウンタやフラグの更新に利用されます。`atomic.LoadInt32` は `int32` の値をアトミックに読み込み、`atomic.StoreInt32` は `int32` の値をアトミックに書き込みます。
6.  **パニック (Panic)**: Go言語におけるパニックは、プログラムの回復不可能なエラー状態を示します。通常、プログラムの実行を停止させ、スタックトレースを出力します。これは、予期せぬ状態やプログラマの誤用を早期に検出するために意図的に引き起こされることがあります。

## 技術的詳細

このコミットの技術的な変更点は、主に `response` 構造体の `handlerDone` フィールドの型変更と、`Hijack` および `CloseNotify` メソッドへのガード（防御的なチェック）の追加です。

1.  **`handlerDone` フィールドの型変更**:
    - 変更前: `handlerDone bool`
    - 変更後: `handlerDone atomicBool`
    `handlerDone` は、HTTPハンドラがリクエストの処理を完了したかどうかを示すフラグです。このフラグが `bool` 型であった場合、複数のゴルーチン（例えば、メインのHTTP処理ゴルーチンと、`CloseNotify` を監視するゴルーチン）から同時にアクセスされると、競合状態（race condition）が発生する可能性がありました。
    `atomicBool` というカスタム型を導入し、`sync/atomic` パッケージのアトミック操作 (`atomic.LoadInt32`, `atomic.StoreInt32`) を使用することで、このフラグの読み書きがスレッドセーフになり、競合状態を防ぎます。

2.  **`atomicBool` 型の導入**:
    ```go
    type atomicBool int32

    func (b *atomicBool) isSet() bool { return atomic.LoadInt32((*int32)(b)) != 0 }
    func (b *atomicBool) setTrue()    { atomic.StoreInt32((*int32)(b), 1) }
    ```
    `atomicBool` は `int32` を基盤とし、`isSet()` メソッドでアトミックに値を読み込み、`setTrue()` メソッドでアトミックに値を `1` に設定します。これにより、`handlerDone` フラグの状態変更と参照が安全に行えるようになります。

3.  **`Hijack()` メソッドへのパニック追加**:
    ```go
    func (w *response) Hijack() (rwc net.Conn, buf *bufio.ReadWriter, err error) {
        if w.handlerDone.isSet() {
            panic("net/http: Hijack called after ServeHTTP finished")
        }
        // ... 既存の処理 ...
    }
    ```
    `Hijack()` メソッドの冒頭で `w.handlerDone.isSet()` をチェックし、もしハンドラが既に完了している場合はパニックを発生させます。これは、HTTP接続のハイジャックはハンドラが応答を書き込む前に行われるべき操作であり、ハンドラ完了後に呼び出されるのは不正な使用であるためです。

4.  **`CloseNotify()` メソッドへのパニック追加**:
    ```go
    func (w *response) CloseNotify() <-chan bool {
        if w.handlerDone.isSet() {
            panic("net/http: CloseNotify called after ServeHTTP finished")
        }
        // ... 既存の処理 ...
    }
    ```
    同様に、`CloseNotify()` メソッドの冒頭でも `w.handlerDone.isSet()` をチェックし、ハンドラが既に完了している場合はパニックを発生させます。`CloseNotify` チャネルの取得は、ハンドラがアクティブな間にのみ意味があり、ハンドラ完了後にチャネルを取得しようとするのは通常、ロジックの誤りを示唆します。

これらの変更により、`net/http` サーバーは、`CloseNotifier` や `Hijacker` の不適切な使用を積極的に検出し、開発者にその問題を通知するようになりました。

## コアとなるコードの解説

このコミットの核となる変更は、`response` 構造体の `handlerDone` フラグを `bool` から `atomicBool` に変更し、そのフラグがセットされた後に `Hijack` や `CloseNotify` が呼び出された場合にパニックを発生させる点です。

-   **`handlerDone` のアトミック化**: `response` 構造体はHTTPリクエスト処理のコンテキスト全体を管理しており、複数のゴルーチンからアクセスされる可能性があります。特に、リクエストハンドラが実行されているゴルーチンと、例えば `CloseNotify` チャネルを監視している別のゴルーチンが同時に `handlerDone` を読み書きしようとすると、競合状態が発生し、フラグの状態が正しく反映されない可能性がありました。`atomicBool` を使用することで、`handlerDone` の読み書き操作が不可分（アトミック）になり、常に正しい状態が保証されます。これにより、`handlerDone` の状態を安全にチェックできるようになりました。

-   **`Hijack()` と `CloseNotify()` のガード**:
    -   `Hijack()` は、HTTPハンドラがまだ応答を書き込んでいない段階で呼び出されることを想定しています。ハンドラが完了した後に接続をハイジャックしようとすると、既にHTTP応答の一部が送信されている可能性があり、プロトコル違反や予期せぬ動作につながります。
    -   `CloseNotify()` は、ハンドラがアクティブな間にクライアントの切断を監視するために使用されます。ハンドラが既に完了している場合、そのチャネルを取得しても意味がなく、むしろリソースリークや無駄な処理につながる可能性があります。
    これらのメソッドの冒頭で `w.handlerDone.isSet()` をチェックし、`true` であれば `panic` を発生させることで、開発者はこれらのメソッドが不適切なタイミングで呼び出されたことを即座に知ることができます。これは「フェイルファスト (fail-fast)」の原則に従い、問題が深刻化する前に早期に検出することを促します。

この変更は、`net/http` パッケージの堅牢性を高め、開発者がより安全に `CloseNotifier` や `Hijacker` を利用できるようにするための重要な改善です。

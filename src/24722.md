# [インデックス 24722] ファイルの概要

このコミットは、Go言語のコンパイラ (`cmd/compile`) とランタイム (`runtime`) におけるハッシュマップの挙動、特にマップにキーが存在しない場合に返されるゼロ値の取り扱いに関する変更です。以前は型情報 (`_type`) に含まれる `t.zero` フィールドがゼロ値を指していましたが、このコミットにより、ハッシュマップのミス時に常にランタイムが管理するグローバルなゼロ値ポインタを直接返すように変更されました。これにより、型データから `zero` フィールドの利用が廃止され、将来的な削除への道が開かれました。

## 元コミット内容

`cmd/compile, runtime: stop returning t.zero on hashmap miss`

以前は `t.zero` が常に `runtime.zerovalue` を指していました。ハッシュマップのコードを変更し、常にランタイムポインタを直接返すようにし、必要に応じてそのポインタがより大きなバッファを指すようにします。

（値の型が十分に小さい場合にのみ `mapaccess` 関数が返すポインタからコピーし、より大きな値の型に対してはコンパイラが明示的なゼロ化を挿入する方が良いかもしれませんが、これを試みましたが失敗しました。）

これにより、型データの `zero` フィールドのすべての使用が削除されます。このフィールド自体は別の変更で削除できます。

Fixes #11491

## 変更の背景

Go言語のマップは、存在しないキーにアクセスした場合、その値の型のゼロ値を返します。例えば、`map[string]int` で存在しないキーにアクセスすると `0` が返され、`map[string]struct{}` であれば空の構造体が返されます。

このゼロ値を返すメカニズムにおいて、以前のGoランタイムでは、各型 (`_type` 構造体) が `zero` というフィールドを持っており、これがその型のゼロ値が格納されたメモリ領域を指していました。しかし、このアプローチにはいくつかの課題がありました。

1.  **冗長性**: 多くの型が同じゼロ値を共有するにもかかわらず、各型情報が個別の `zero` ポインタを持つことは冗長でした。特に、`runtime.zerovalue` と呼ばれるグローバルなゼロ値バッファが存在し、ほとんどの型はこのバッファを指していました。
2.  **複雑性**: `t.zero` のサイズを管理するために、コンパイラが `zerosize` という変数を更新し、リンカがその最大値に基づいて `runtime.zerovalue` のサイズを決定するという複雑な連携が必要でした。
3.  **ARMアーキテクチャでの問題**: コミットメッセージに「On ARM, atomicloadp is implemented as xadd(p, 0), so we cannot use atomicloadp on read-only memory.」とあるように、ARMアーキテクチャでは読み取り専用メモリ上の `t.zero` に対してアトミック操作を行う際に問題が生じる可能性がありました。

これらの課題を解決し、ゼロ値の取り扱いを簡素化し、より効率的で堅牢なメカニズムを導入するために、この変更が提案されました。特に、型データから `zero` フィールドへの依存をなくすことが目的でした。

## 前提知識の解説

*   **Goのマップ (map)**: Goの組み込みデータ構造で、キーと値のペアを格納します。存在しないキーにアクセスすると、値の型のゼロ値が返されます。
*   **ゼロ値 (Zero Value)**: Goの各型にはデフォルトの「ゼロ値」があります。数値型は `0`、ブール型は `false`、文字列型は `""`、ポインタ、関数、インターフェース、スライス、チャネル、マップ型は `nil`、構造体はすべてのフィールドがその型のゼロ値に初期化されたものです。
*   **`_type` 構造体**: Goランタイム内部で型情報を表現するための構造体です。各Goの型 (例: `int`, `string`, `struct{}` など) に対応する `_type` インスタンスが存在し、その型のサイズ、アラインメント、メソッドなどの情報を含んでいます。変更前は `zero unsafe.Pointer` または `zero *byte` フィールドを持っていました。
*   **`unsafe.Pointer`**: Goの `unsafe` パッケージにある型で、任意の型のポインタを保持できる特殊なポインタです。型安全性をバイパスするため、Goのランタイムや低レベルなコードで慎重に使用されます。
*   **`atomicloadp` / `atomicstorep`**: `runtime` パッケージ内のアトミック操作関数で、ポインタの読み書きをアトミックに行います。これにより、複数のゴルーチンからの同時アクセスに対するデータ競合を防ぎます。
*   **`persistentalloc`**: Goランタイム内部のメモリ割り当て関数の一つで、永続的なメモリ領域を確保するために使用されます。ガベージコレクションの対象外となることが多いです。
*   **`runtime.zerovalue`**: 変更前のGoランタイムに存在した、様々な型のゼロ値を格納するためのグローバルなバッファ。コンパイラによってそのサイズが調整されていました。
*   **`cmd/compile/internal/gc`**: Goコンパイラのフロントエンド部分で、Goのソースコードを解析し、中間表現に変換し、最適化を行う役割を担います。型情報の生成やランタイムとの連携もここで行われます。
*   **`src/reflect/type.go`**: `reflect` パッケージにおける型情報の定義が含まれています。ランタイムの `_type` 構造体と密接に関連しています。
*   **`src/runtime/hashmap.go` / `src/runtime/hashmap_fast.go`**: Goのマップの実装が含まれています。マップの作成、アクセス、挿入、削除などのロジックが定義されています。`hashmap_fast.go` は特定のプリミティブ型 (例: `int`, `string`) のキーに対する最適化されたマップアクセス関数を含みます。

## 技術的詳細

このコミットの核心は、Goのマップがキーのミス時にゼロ値を返す方法を、型固有の `_type.zero` フィールドから、ランタイムが管理するグローバルなゼロ値バッファ `zeroptr` へと移行した点にあります。

**変更前のアプローチ:**

1.  各型 (`_type`) は `zero` というフィールドを持っており、これはその型のゼロ値が格納されたメモリ領域を指していました。
2.  コンパイラ (`cmd/compile`) は、マップアクセスなどで必要となるゼロ値の最大サイズを `zerosize` 変数で追跡していました。
3.  リンカは `zerosize` の最大値に基づいて `runtime.zerovalue` というグローバルなゼロ値バッファを確保していました。
4.  マップアクセス関数 (`mapaccess1`, `mapaccess2` など) は、キーが見つからない場合、`t.elem.zero` (要素型のゼロ値ポインタ) を返していました。
5.  `mapzero` 関数は、`t.zero` が適切に設定されていることを保証する役割を担っていました。特に、`reflect` パッケージによって動的に作成された型の場合、`t.zero` が `nil` であれば、`runtime.zerovalue` または動的に割り当てられたバッファを指すように設定していました。

**変更後のアプローチ:**

1.  `_type` 構造体から `zero` フィールドが論理的に削除されました (コード上は `// unused` とマークされ、後に物理的に削除されます)。
2.  コンパイラ側の `zerosize` 変数とその更新ロジックが削除されました。
3.  ランタイムに `zeroptr unsafe.Pointer` と `zerosize uintptr` というグローバル変数が導入されました。`zeroptr` は常にゼロ値バッファの先頭を指し、`zerosize` はそのバッファの現在のサイズを保持します。これらはアトミックにアクセスされます。
4.  初期状態では、`zeroptr` は `initialZeroSize` (1024バイト) の静的な `zeroinitial` バッファを指します。
5.  マップアクセス関数は、キーが見つからない場合、`atomicloadp(unsafe.Pointer(&zeroptr))` を呼び出して、常にグローバルな `zeroptr` を直接返すようになりました。
6.  `mapzero(t *_type)` 関数は、もはや `t.zero` を設定するのではなく、引数 `t` のサイズ (`t.size`) が現在のグローバルなゼロ値バッファ (`zerosize`) よりも大きい場合に、より大きなバッファを動的に割り当て、`zeroptr` と `zerosize` を更新する役割を担うようになりました。この割り当ては `persistentalloc` を使用し、ロック (`zerolock`) で保護されます。バッファサイズは必要に応じて2倍に拡張されます。

この変更により、各型情報がゼロ値ポインタを持つ必要がなくなり、ランタイムが一元的にゼロ値バッファを管理するようになりました。これにより、型データの構造が簡素化され、コンパイラとランタイム間のゼロ値管理の連携が単純化されました。また、ARMアーキテクチャでの潜在的な問題も回避されます。

## コアとなるコードの解説

このコミットの主要な変更は、Goのマップがキーのミス時にゼロ値を返す方法を、型固有の `_type.zero` フィールドから、ランタイムが管理するグローバルなゼロ値バッファ `zeroptr` へと移行したことです。

以前は、各型 (`_type`) が自身のゼロ値へのポインタ (`t.zero`) を持っていました。これは、コンパイラが `zerosize` を通じて `runtime.zerovalue` のサイズを調整し、各 `t.zero` がこのグローバルなバッファ内の適切なオフセットを指すようにする、という複雑な仕組みでした。

新しいアプローチでは、この `t.zero` フィールドは完全に廃止され、代わりにランタイムが `zeroptr` と `zerosize` という2つのグローバル変数を管理します。

-   `zeroptr unsafe.Pointer`: 現在のゼロ値バッファの先頭を指すポインタです。
-   `zerosize uintptr`: 現在のゼロ値バッファのサイズです。

マップアクセス関数 (`mapaccess1`, `mapaccess2` など) は、キーが見つからない場合、もはや `t.elem.zero` を参照せず、代わりに `atomicloadp(unsafe.Pointer(&zeroptr))` を呼び出して、常にグローバルな `zeroptr` が指すバッファの先頭を返します。

`mapzero(t *_type)` 関数は、もはや `t.zero` を初期化する役割ではなく、要求された型 `t` のサイズ (`t.size`) が現在のグローバルなゼロ値バッファ (`zerosize`) よりも大きい場合に、そのバッファを動的に拡張する役割を担います。具体的には、`zerolock` を取得し、`persistentalloc` を使用して新しい、より大きなゼロ値バッファを割り当て、`zeroptr` と `zerosize` をアトミックに更新します。これにより、常に十分な大きさのゼロ値バッファが利用可能であることが保証されます。

この変更により、型データから `zero` フィールドへの依存が解消され、型情報の構造が簡素化されました。また、ゼロ値の管理が一元化され、コンパイラとランタイム間の連携が単純化されるとともに、将来的に `_type` 構造体から `zero` フィールドを物理的に削除することが可能になりました。これは、Goランタイムの内部構造のクリーンアップと効率化に貢献する変更と言えます。

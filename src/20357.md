# [インデックス 20357] ファイルの概要

このコミットは、Goランタイムにおける`mcall`および`onM`関数の引数型を、Cスタイルの関数ポインタからGoの関数値へと変更するものです。これにより、Goの型システムとの整合性が向上し、M（Machine）スタック上でGoコードを実行する可能性が広がります。

## 元コミット内容

このコミットの目的は、Goランタイムの内部関数である`onM`と`mcall`がGoの関数値（`func(*g)`や`func()`）を引数として受け取るように変更することです。これにより、Goの型システムとの整合性が向上し、Mスタック上でGoコードを実行する道が開かれます。

## 変更の背景

Goランタイムは、Go言語で書かれたコードと、アセンブリ言語やC言語で書かれた低レベルなコードが密接に連携して動作しています。特に、スケジューラやメモリ管理といったGoランタイムの根幹をなす部分は、パフォーマンスと制御の観点からアセンブリ言語やC言語で実装されています。

`mcall`と`onM`は、Goランタイムにおいて非常に重要な役割を果たす関数です。これらは、現在のGoroutine（G）のスタックからM（Machine）のスタック（g0スタックまたはgsignalスタック）へと切り替えて、特定の処理を実行するために使用されます。Mスタックは、システムコールやシグナルハンドリングなど、Goランタイムの低レベルな操作を行う際に利用される特別なスタックです。

このコミット以前は、`mcall`や`onM`に渡される関数はC言語の関数ポインタとして扱われていました。しかし、Go言語には独自の関数型と関数値の概念があります。C言語の関数ポインタとして扱うことは、Goの型システムから見ると型安全性が低く、またGoの関数が持つクロージャなどの情報が失われる可能性がありました。

この変更の主な背景は以下の通りです。

1.  **型安全性の向上**: C言語の関数ポインタは、Goの関数値とは異なる表現を持ちます。Goの関数値を直接`mcall`や`onM`に渡せるようにすることで、Goの型システムによるチェックが働き、より安全なコードになります。
2.  **Mスタック上でのGoコード実行の可能性**: Goの関数値は、単なるコードのアドレスだけでなく、関連する環境（クロージャのキャプチャ変数など）へのポインタも含む場合があります。C言語の関数ポインタとして扱う場合、これらの環境情報を適切に扱うことが困難でした。Goの関数値を直接渡せるようにすることで、Mスタック上でもGoの関数が持つ完全なセマンティクスを維持したまま実行できるようになり、ランタイムの柔軟性が向上します。これは、例えばGC（ガベージコレクション）の特定のフェーズや、デバッグ、プロファイリングといったMスタック上で実行される必要のある処理において、より複雑なGoロジックを組み込むことを可能にします。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念と、アセンブリ言語における関数呼び出しの基本的な知識が必要です。

### GoランタイムのG-M-Pモデル

Goランタイムは、Goroutine（G）、Machine（M）、Processor（P）という3つの主要な抽象化を用いて並行処理を管理します。

*   **Goroutine (G)**: Goにおける軽量な実行単位です。Go関数呼び出しのスタックと実行コンテキストをカプセル化します。数百万のGoroutineを同時に実行できます。
*   **Machine (M)**: オペレーティングシステムのスレッドに相当します。Goランタイムは、MをOSスレッドにマッピングし、その上でGoroutineを実行します。各Mは、自身のスタック（Mスタック、またはg0スタック）を持ち、これはGoコードの実行には使用されず、ランタイムの低レベルな処理（スケジューリング、GC、システムコールなど）のために使われます。
*   **Processor (P)**: MがGoroutineを実行するために必要なリソース（スケジューラキュー、メモリ割り当てキャッシュなど）を提供します。Pの数は通常、CPUコアの数に等しく、同時に実行できるGoroutineの数を制限します。

`mcall`と`onM`は、GoroutineのスタックからMのスタック（g0スタック）に切り替えて、ランタイムの重要な処理を実行するために使用されます。

### `mcall`と`onM`

*   **`mcall(fn func(*g))`**: 現在のGoroutineの実行を中断し、Mのg0スタックに切り替えて、引数として渡された関数`fn`を実行します。`fn`は`*g`（現在のGoroutineのポインタ）を引数として受け取ります。`fn`は決してリターンしてはならず、通常は`gogo(&g->sched)`を呼び出してGoroutineの実行を再開します。これは、Goroutineのコンテキストを保存し、Mスタック上で低レベルな処理を行った後、元のGoroutineに戻るために使われます。
*   **`onM(fn func())`**: `mcall`と同様にMのg0スタックに切り替えて関数`fn`を実行しますが、`fn`は引数を受け取らず、リターンすることが期待されます。`fn`がリターンすると、自動的に元のGoroutineのスタックに戻ります。これは、Mスタック上で一時的な処理を行う際に便利です。

### Goの関数値とCの関数ポインタ

*   **Cの関数ポインタ**: C言語における関数ポインタは、関数のエントリポイントのアドレスを直接指す単一のポインタです。
*   **Goの関数値**: Goの関数値（`func`型）は、単なるコードのアドレスだけでなく、その関数がクロージャである場合にキャプチャされた変数へのポインタ（環境ポインタ）も含む構造体です。Goの関数値は、通常、コードポインタとデータポインタ（環境ポインタ）の2つのポインタで構成されます。

### アセンブリ言語における関数呼び出し

x86/amd64アーキテクチャでは、関数呼び出しの際に引数はレジスタまたはスタックを通じて渡されます。Goのコンベンションでは、最初の引数は通常`DI`（または`RDI`）レジスタに渡されます。関数ポントを介した呼び出しでは、そのポインタが指すアドレスにジャンプします。

## 技術的詳細

このコミットの核心は、`mcall`と`onM`がC言語の関数ポインタではなく、Goの関数値を受け取るように変更された点にあります。

以前は、`mcall`や`onM`に渡される関数は、`void (*fn)(G*)`や`void (*fn)()`といったC言語の関数ポインタとして宣言されていました。これは、Goの関数をCの関数ポインタに変換して渡す必要があり、Goの型システムによるチェックが効きにくく、またGoの関数値が持つ環境情報（クロージャのコンテキスト）が失われる可能性がありました。

この変更により、`mcall`と`onM`のGo側の宣言はそれぞれ`func(*g)`と`func()`となり、Goの関数値を直接渡せるようになりました。

しかし、Goの関数値は前述の通り、コードポインタとデータポインタ（環境ポインタ）の2つの要素を持つ場合があります。アセンブリ言語レベルでは、このGoの関数値の構造を理解し、適切にコードポインタを取り出して呼び出す必要があります。

変更されたアセンブリコード（`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `asm_arm.s`）では、以下のパターンが追加されています。

```assembly
MOVL DI, DX   // x86/amd64の場合: DIレジスタに渡されたGo関数値のアドレスをDXレジスタにコピー
MOVL 0(DI), DI // DIレジスタが指すアドレス（Go関数値の先頭、つまりコードポインタ）をDIレジスタにロード
CALL DI       // DIレジスタにロードされたコードポインタを呼び出す
```
ARMアーキテクチャではレジスタが異なりますが、同様の操作が行われます。
```assembly
MOVW R0, R7   // ARMの場合: R0レジスタに渡されたGo関数値のアドレスをR7レジスタにコピー
MOVW 0(R0), R0 // R0レジスタが指すアドレス（Go関数値の先頭、つまりコードポインタ）をR0レジスタにロード
BL (R0)       // R0レジスタにロードされたコードポインタを呼び出す
```

このアセンブリコードは、`DI`（または`R0`）レジスタに渡されたGo関数値のアドレスから、その関数値の先頭にあるコードポインタを読み出し、そのコードポインタを使って関数を呼び出しています。これにより、Goの関数値が持つコード部分が正しく実行されます。

また、`src/pkg/runtime/stubs.go`では、`mFunction`という型が削除され、`mcall`と`onM`の宣言がGoの関数型に直接変更されています。これにより、Goコードからこれらの関数を呼び出す際に、より自然なGoの構文で記述できるようになりました。

この変更は、Goランタイムの内部実装において、Go言語のセマンティクスをより深く取り込む一歩であり、将来的にMスタック上でより複雑なGoロジックを実行するための基盤を強化するものです。例えば、GCのマーキングフェーズや、プロファイリングデータの収集など、Mスタック上で実行される必要のある処理において、Goの関数を直接利用できるようになることで、コードの可読性や保守性が向上する可能性があります。

## コアとなるコードの解説

このコミットの最も重要な変更は、Goの関数値がどのようにアセンブリレベルで扱われるか、そしてGoとCのインターフェースがどのように調整されたかという点に集約されます。

### アセンブリコードの変更 (`asm_*.s`)

以前は、`mcall`や`onM`はC言語の関数ポインタ（単一のアドレス）を引数として受け取っていました。しかし、Goの関数値は、コードのアドレスと、クロージャの環境情報（データポインタ）の2つのポインタで構成される場合があります。

変更後のアセンブリコードでは、`mcall`や`onM`に渡される引数（Goの関数値）は、レジスタ（x86/amd64では`DI`、ARMでは`R0`）にその関数値の構造体のアドレスとして渡されます。

例えば、x86/amd64の`runtime·mcall`の変更箇所を見てみましょう。

```assembly
// 変更前:
// void mcall(void (*fn)(G*))
// ...
// CALL DI // DIには直接関数ポインタが格納されていた

// 変更後:
// func mcall(fn func(*g))
// ...
MOVL DI, DX   // DIレジスタに渡されたGo関数値のアドレスをDXレジスタにコピー
MOVL 0(DI), DI // DIレジスタが指すアドレス（Go関数値の先頭、つまりコードポインタ）をDIレジスタにロード
CALL DI       // DIレジスタにロードされたコードポインタを呼び出す
```

ここで重要なのは、`MOVL 0(DI), DI`という命令です。これは、`DI`レジスタが指すメモリ位置（Go関数値の構造体の先頭）から4バイト（32ビットシステムの場合）または8バイト（64ビットシステムの場合）を読み出し、それを再び`DI`レジスタに格納するという意味です。Goの関数値のメモリレイアウトでは、先頭にコードポインタが配置されています。したがって、この命令によって、Go関数値から実際のコードのエントリポイントのアドレスが抽出され、`CALL`命令でそのアドレスが呼び出されます。

`DX`レジスタへのコピー（`MOVL DI, DX`）は、Go関数値のデータポインタ（クロージャの環境情報）が後続の処理で必要になる場合に備えて、元の関数値のアドレスを保存している可能性があります。このコミットの範囲では直接利用されていませんが、将来的な拡張性やデバッグの目的で残されていると考えられます。

### GoとCのインターフェースの調整

`src/pkg/runtime/runtime.h`における`mcall`と`onM`のC言語側のプロトタイプ宣言の変更も重要です。

```c
// 変更前:
// void	runtime·mcall(void(*)(G*));
// void	runtime·onM(void(*)(void));

// 変更後:
void	runtime·mcall(void(**)(G*));
void	runtime·onM(void(**)(void));
```

引数型が`void(*)(G*)`から`void(**)(G*)`（関数ポインタのポインタ）に変更されています。これは、C言語側から`runtime·mcall`や`runtime·onM`を呼び出す際に、Goの関数値（コードポインタとデータポインタのペア）をCの関数ポインタとして扱うための橋渡しをするためです。C言語のコードでは、Goの関数値を直接扱うことはできないため、Goの関数値のアドレスをCの関数ポインタのポインタとして受け取り、そのポインタが指す先（Go関数値のコードポインタ部分）を間接的に参照して呼び出すという形を取っています。

例えば、`src/pkg/runtime/heapdump.c`の変更を見てみましょう。

```c
// 変更前:
// runtime·mcall(mdump);

// 変更後:
void (*fn)(G*); // C言語の関数ポインタ変数を宣言
fn = mdump;     // mdump関数のアドレスをfnに代入
runtime·mcall(&fn); // fnのアドレス（つまり、mdump関数のアドレスへのポインタ）をmcallに渡す
```

このC言語側の変更は、Goの関数値が持つ2つのポインタ（コードとデータ）のうち、コードポインタのみをCの関数ポインタとして抽出し、そのCの関数ポインタのアドレスを`mcall`に渡すという意図を示しています。これにより、アセンブリコードがGo関数値の構造を直接解釈し、コードポインタを抽出して呼び出すことができるようになります。

### `mFunction`型の削除 (`stubs.go`)

`src/pkg/runtime/stubs.go`から`mFunction`というダミーの型が削除されました。これは、Goの関数値を直接`mcall`や`onM`に渡せるようになったため、もはやこのような中間的な型が不要になったことを意味します。これにより、Goコードの記述がより簡潔になり、Goの型システムとの整合性がさらに高まりました。

これらの変更は、Goランタイムの内部でGo言語のセマンティクスをより深く尊重し、Goの関数値を低レベルなランタイム操作に直接利用できるようにするための重要なステップです。これにより、ランタイムの柔軟性と型安全性が向上し、将来的な機能拡張や最適化の基盤が強化されました。

この変更の主な背景は以下の通りです。

1.  **型安全性の向上**: C言語の関数ポインタは、Goの関数値とは異なる表現を持ちます。Goの関数値を直接`mcall`や`onM`に渡せるようにすることで、Goの型システムによるチェックが働き、より安全なコードになります。
2.  **Mスタック上でのGoコード実行の可能性**: Goの関数値は、単なるコードのアドレスだけでなく、関連する環境（クロージャのキャプチャ変数など）へのポインタも含む場合があります。C言語の関数ポインタとして扱う場合、これらの環境情報を適切に扱うことが困難でした。Goの関数値を直接渡せるようにすることで、Mスタック上でもGoの関数が持つ完全なセマンティクスを維持したまま実行できるようになり、ランタイムの柔軟性が向上します。これは、例えばGC（ガベージコレクション）の特定のフェーズや、デバッグ、プロファイリングといったMスタック上で実行される必要のある処理において、より複雑なGoロジックを組み込むことを可能にします。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念と、アセンブリ言語における関数呼び出しの基本的な知識が必要です。

### GoランタイムのG-M-Pモデル

Goランタイムは、Goroutine（G）、Machine（M）、Processor（P）という3つの主要な抽象化を用いて並行処理を管理します。

*   **Goroutine (G)**: Goにおける軽量な実行単位です。Go関数呼び出しのスタックと実行コンテキストをカプセル化します。数百万のGoroutineを同時に実行できます。
*   **Machine (M)**: オペレーティングシステムのスレッドに相当します。Goランタイムは、MをOSスレッドにマッピングし、その上でGoroutineを実行します。各Mは、自身のスタック（Mスタック、またはg0スタック）を持ち、これはGoコードの実行には使用されず、ランタイムの低レベルな処理（スケジューリング、GC、システムコールなど）のために使われます。
*   **Processor (P)**: MがGoroutineを実行するために必要なリソース（スケジューラキュー、メモリ割り当てキャッシュなど）を提供します。Pの数は通常、CPUコアの数に等しく、同時に実行できるGoroutineの数を制限します。

`mcall`と`onM`は、GoroutineのスタックからMのスタック（g0スタック）に切り替えて、ランタイムの重要な処理を実行するために使用されます。

### `mcall`と`onM`

*   **`mcall(fn func(*g))`**: 現在のGoroutineの実行を中断し、Mのg0スタックに切り替えて、引数として渡された関数`fn`を実行します。`fn`は`*g`（現在のGoroutineのポインタ）を引数として受け取ります。`fn`は決してリターンしてはならず、通常は`gogo(&g->sched)`を呼び出してGoroutineの実行を再開します。これは、Goroutineのコンテキストを保存し、Mスタック上で低レベルな処理を行った後、元のGoroutineに戻るために使われます。
*   **`onM(fn func())`**: `mcall`と同様にMのg0スタックに切り替えて関数`fn`を実行しますが、`fn`は引数を受け取らず、リターンすることが期待されます。`fn`がリターンすると、自動的に元のGoroutineのスタックに戻ります。これは、Mスタック上で一時的な処理を行う際に便利です。

### Goの関数値とCの関数ポインタ

*   **Cの関数ポインタ**: C言語における関数ポインタは、関数のエントリポイントのアドレスを直接指す単一のポインタです。
*   **Goの関数値**: Goの関数値（`func`型）は、単なるコードのアドレスだけでなく、その関数がクロージャである場合にキャプチャされた変数へのポインタ（環境ポインタ）も含む構造体です。Goの関数値は、通常、コードポインタとデータポインタ（環境ポインタ）の2つのポインタで構成されます。

### アセンブリ言語における関数呼び出し

x86/amd64アーキテクチャでは、関数呼び出しの際に引数はレジスタまたはスタックを通じて渡されます。Goのコンベンションでは、最初の引数は通常`DI`（または`RDI`）レジスタに渡されます。関数ポントを介した呼び出しでは、そのポインタが指すアドレスにジャンプします。

## 技術的詳細

このコミットの核心は、`mcall`と`onM`がC言語の関数ポインタではなく、Goの関数値を受け取るように変更された点にあります。

以前は、`mcall`や`onM`に渡される関数は、`void (*fn)(G*)`や`void (*fn)()`といったC言語の関数ポインタとして宣言されていました。これは、Goの関数をCの関数ポインタに変換して渡す必要があり、Goの型システムによるチェックが効きにくく、またGoの関数値が持つ環境情報（クロージャのコンテキスト）が失われる可能性がありました。

この変更により、`mcall`と`onM`のGo側の宣言はそれぞれ`func(*g)`と`func()`となり、Goの関数値を直接渡せるようになりました。

しかし、Goの関数値は前述の通り、コードポインタとデータポインタ（環境ポインタ）の2つの要素を持つ場合があります。アセンブリ言語レベルでは、このGoの関数値の構造を理解し、適切にコードポインタを取り出して呼び出す必要があります。

変更されたアセンブリコード（`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `asm_arm.s`）では、以下のパターンが追加されています。

```assembly
MOVL DI, DX   // x86/amd64の場合: DIレジスタに渡されたGo関数値のアドレスをDXレジスタにコピー
MOVL 0(DI), DI // DIレジスタが指すアドレス（Go関数値の先頭、つまりコードポインタ）をDIレジスタにロード
CALL DI       // DIレジスタにロードされたコードポインタを呼び出す
```
ARMアーキテクチャではレジスタが異なりますが、同様の操作が行われます。
```assembly
MOVW R0, R7   // ARMの場合: R0レジスタに渡されたGo関数値のアドレスをR7レジスタにコピー
MOVW 0(R0), R0 // R0レジスタが指すアドレス（Go関数値の先頭、つまりコードポインタ）をR0レジスタにロード
BL (R0)       // R0レジスタにロードされたコードポインタを呼び出す
```

このアセンブリコードは、`DI`（または`R0`）レジスタに渡されたGo関数値のアドレスから、その関数値の先頭にあるコードポインタを読み出し、そのコードポインタを使って関数を呼び出しています。これにより、Goの関数値が持つコード部分が正しく実行されます。

また、`src/pkg/runtime/stubs.go`では、`mFunction`という型が削除され、`mcall`と`onM`の宣言がGoの関数型に直接変更されています。これにより、Goコードからこれらの関数を呼び出す際に、より自然なGoの構文で記述できるようになりました。

この変更は、Goランタイムの内部実装において、Go言語のセマンティクスをより深く取り込む一歩であり、将来的にMスタック上でより複雑なGoロジックを実行するための基盤を強化するものです。例えば、GCのマーキングフェーズや、プロファイリングデータの収集など、Mスタック上で実行される必要のある処理において、Goの関数を直接利用できるようになることで、コードの可読性や保守性が向上する可能性があります。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下のファイルに見られます。

1.  **`src/pkg/runtime/asm_*.s` (アセンブリファイル)**:
    *   `mcall`と`onM`の定義において、引数として渡されたGo関数値からコードポインタを抽出して呼び出すためのアセンブリ命令が追加されました。具体的には、`DI`（または`R0`）レジスタに渡された関数値のアドレスから、その先頭にあるコードポインタを読み出す処理が加わっています。
    *   コメントがCスタイルの関数ポインタの宣言からGoの関数型の宣言に更新されています。

2.  **`src/pkg/runtime/export_test.go`**:
    *   `lfstackpush_m`, `lfstackpop_m`, `newparfor_m`などの`mFunction`型の変数の宣言が削除され、代わりに`func`キーワードを用いたGoの関数宣言に置き換えられました。
    *   `onM(&func_name)`という呼び出しが`onM(func_name)`に変更されています。

3.  **`src/pkg/runtime/heapdump.c`, `src/pkg/runtime/mcache.c`, `src/pkg/runtime/mgc0.c`, `src/pkg/runtime/mheap.c`, `src/pkg/runtime/panic.c`, `src/pkg/runtime/proc.c` (C言語ファイル)**:
    *   `runtime·mcall`の呼び出し箇所で、C言語の関数ポインタを直接渡すのではなく、`void (*fn)(G*)`のようなローカル変数に代入してからその変数のアドレスを渡す形式（例: `fn = mdump; runtime·mcall(&fn);`）に変更されています。これは、Goの関数値がCの関数ポインタとは異なるメモリレイアウトを持つため、Goの関数値をCの関数ポインタとして扱うための間接的な変換が必要になったためと考えられます。

4.  **`src/pkg/runtime/malloc.go`, `src/pkg/runtime/mgc0.go`, `src/pkg/runtime/proc.go`, `src/pkg/runtime/rdebug.go`, `src/pkg/runtime/sigqueue.go` (Go言語ファイル)**:
    *   `onM(&func_name)`や`mcall(&func_name)`といった呼び出しが、`onM(func_name)`や`mcall(func_name)`のように、Goの関数値を直接渡す形式に変更されています。

5.  **`src/pkg/runtime/runtime.h`**:
    *   `runtime·mcall`と`runtime·onM`のC言語側の関数プロトタイプ宣言が、引数が関数ポインタのポインタ（`void(**)(G*)`や`void(**)(void)`）を受け取るように変更されています。これは、C言語側でGoの関数値（コードポインタとデータポインタのペア）を扱うための変更です。

6.  **`src/pkg/runtime/stubs.go`**:
    *   `mFunction`という型定義が完全に削除されました。
    *   `mcall`と`onM`のGo側の宣言が、それぞれ`func(func(*g))`と`func(fn func())`に変更されました。
    *   `mcacheRefill_m`などの`mFunction`型の変数の宣言が、Goの関数宣言に置き換えられました。

## コアとなるコードの解説

このコミットの最も重要な変更は、Goの関数値がどのようにアセンブリレベルで扱われるか、そしてGoとCのインターフェースがどのように調整されたかという点に集約されます。

### アセンブリコードの変更 (`asm_*.s`)

以前は、`mcall`や`onM`はC言語の関数ポインタ（単一のアドレス）を引数として受け取っていました。しかし、Goの関数値は、コードのアドレスと、クロージャの環境情報（データポインタ）の2つのポインタで構成される場合があります。

変更後のアセンブリコードでは、`mcall`や`onM`に渡される引数（Goの関数値）は、レジスタ（x86/amd64では`DI`、ARMでは`R0`）にその関数値の構造体のアドレスとして渡されます。

例えば、x86/amd64の`runtime·mcall`の変更箇所を見てみましょう。

```assembly
// 変更前:
// void mcall(void (*fn)(G*))
// ...
// CALL DI // DIには直接関数ポインタが格納されていた

// 変更後:
// func mcall(fn func(*g))
// ...
MOVL DI, DX   // DIレジスタに渡されたGo関数値のアドレスをDXレジスタにコピー
MOVL 0(DI), DI // DIレジスタが指すアドレス（Go関数値の先頭、つまりコードポインタ）をDIレジスタにロード
CALL DI       // DIレジスタにロードされたコードポインタを呼び出す
```

ここで重要なのは、`MOVL 0(DI), DI`という命令です。これは、`DI`レジスタが指すメモリ位置（Go関数値の構造体の先頭）から4バイト（32ビットシステムの場合）または8バイト（64ビットシステムの場合）を読み出し、それを再び`DI`レジスタに格納するという意味です。Goの関数値のメモリレイアウトでは、先頭にコードポインタが配置されています。したがって、この命令によって、Go関数値から実際のコードのエントリポイントのアドレスが抽出され、`CALL`命令でそのアドレスが呼び出されます。

`DX`レジスタへのコピー（`MOVL DI, DX`）は、Go関数値のデータポインタ（クロージャの環境情報）が後続の処理で必要になる場合に備えて、元の関数値のアドレスを保存している可能性があります。このコミットの範囲では直接利用されていませんが、将来的な拡張性やデバッグの目的で残されていると考えられます。

### GoとCのインターフェースの調整

`src/pkg/runtime/runtime.h`における`mcall`と`onM`のC言語側のプロトタイプ宣言の変更も重要です。

```c
// 変更前:
// void	runtime·mcall(void(*)(G*));
// void	runtime·onM(void(*)(void));

// 変更後:
void	runtime·mcall(void(**)(G*));
void	runtime·onM(void(**)(void));
```

引数型が`void(*)(G*)`から`void(**)(G*)`（関数ポインタのポインタ）に変更されています。これは、C言語側から`runtime·mcall`や`runtime·onM`を呼び出す際に、Goの関数値（コードポインタとデータポインタのペア）をCの関数ポインタとして扱うための橋渡しをするためです。C言語のコードでは、Goの関数値を直接扱うことはできないため、Goの関数値のアドレスをCの関数ポインタのポインタとして受け取り、そのポインタが指す先（Go関数値のコードポインタ部分）を間接的に参照して呼び出すという形を取っています。

例えば、`src/pkg/runtime/heapdump.c`の変更を見てみましょう。

```c
// 変更前:
// runtime·mcall(mdump);

// 変更後:
void (*fn)(G*); // C言語の関数ポインタ変数を宣言
fn = mdump;     // mdump関数のアドレスをfnに代入
runtime·mcall(&fn); // fnのアドレス（つまり、mdump関数のアドレスへのポインタ）をmcallに渡す
```

このC言語側の変更は、Goの関数値が持つ2つのポインタ（コードとデータ）のうち、コードポインタのみをCの関数ポインタとして抽出し、そのCの関数ポインタのアドレスを`mcall`に渡すという意図を示しています。これにより、アセンブリコードがGo関数値の構造を直接解釈し、コードポインタを抽出して呼び出すことができるようになります。

### `mFunction`型の削除 (`stubs.go`)

`src/pkg/runtime/stubs.go`から`mFunction`というダミーの型が削除されました。これは、Goの関数値を直接`mcall`や`onM`に渡せるようになったため、もはやこのような中間的な型が不要になったことを意味します。これにより、Goコードの記述がより簡潔になり、Goの型システムとの整合性がさらに高まりました。

これらの変更は、Goランタイムの内部でGo言語のセマンティクスをより深く尊重し、Goの関数値を低レベルなランタイム操作に直接利用できるようにするための重要なステップです。これにより、ランタイムの柔軟性と型安全性が向上し、将来的な機能拡張や最適化の基盤が強化されました。

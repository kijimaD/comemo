# [インデックス 22355] ファイルの概要

このコミットは、Goランタイムのバイトスライスおよび文字列操作に関するアセンブリ関数において、引数のサイズ情報を追加するものです。これにより、`go vet`ツールがアセンブリ関数の引数とGoのプロトタイプとの整合性を検証できるようになります。また、`nacl/amd64p32`アーキテクチャにおけるスタック破損バグの修正も含まれています。

## 変更の背景

このコミットには主に二つの背景があります。

1.  **アセンブリ関数の引数サイズ情報の明示**: Goのランタイムには、パフォーマンスが重要な部分でアセンブリ言語で書かれた関数が多数存在します。これらの関数は、Goのコードから呼び出される際に、引数や戻り値がスタック上にどのように配置されるかを正確に知る必要があります。以前は、アセンブリ関数の定義（`TEXT`ディレクティブ）において、ローカルスタックフレームのサイズのみが指定され、引数のサイズは明示されていませんでした。これにより、`go vet`のような静的解析ツールが、アセンブリ関数とそれに対応するGoの関数プロトタイプとの間で引数の整合性を検証することが困難でした。引数サイズを明示することで、コンパイラやツールがより厳密なチェックを行えるようになり、潜在的なバグの早期発見に繋がります。

2.  **`nacl/amd64p32`におけるスタック破損バグの修正**: `nacl/amd64p32`は、Google Native Client (NaCl) 環境向けの`amd64`アーキテクチャで、32ビットポインタと32ビット整数型を使用しつつ、64ビット命令を利用する特殊なターゲットです。このような特定のアーキテクチャでは、スタックフレームの管理やレジスタの使用方法に起因する微妙なバグが発生することがあります。このコミットでは、`bytes.Compare`関数における`MOVQ`（64ビット移動）命令が`MOVL`（32ビット移動）命令に修正されており、これが`nacl/amd64p32`環境でのスタック破損を防ぐための重要な修正であったと考えられます。スタック破損は、プログラムのクラッシュや予期せぬ動作を引き起こす深刻な問題です。

## 前提知識の解説

### Goアセンブリと`TEXT`ディレクティブ

Go言語は、そのランタイムの多くの部分でアセンブリ言語を使用しています。これは、ガベージコレクション、スケジューラ、プリミティブな操作など、パフォーマンスが極めて重要で、OSやハードウェアと密接に連携する必要がある部分で特に顕著です。

Goのアセンブリ言語は、Plan 9アセンブラをベースにしており、一般的なx86アセンブラとは異なる独自の構文を持っています。関数を定義する際には、`TEXT`ディレクティブを使用します。

`TEXT`ディレクティブの一般的な形式は以下の通りです。

```assembly
TEXT symbol(SB), [flags,] $framesize-argsize
```

*   **`symbol(SB)`**: 関数のシンボル名です。`SB`は"static base"を意味し、グローバルなシンボルであることを示します。
*   **`[flags,]`**: オプションのフラグです。このコミットで関連するのは`NOSPLIT`フラグです。
*   **`$framesize-argsize`**: ここがこのコミットの主要な変更点です。
    *   **`framesize`**: その関数が使用するローカルスタックフレームのサイズ（バイト単位）です。この領域は、関数のローカル変数や一時的な値を格納するために使用されます。ローカル変数は通常、`SP`（スタックポインタ）レジスタからの負のオフセット（例: `x-8(SP)`）でアクセスされます。
    *   **`argsize`**: 関数に渡される引数の合計サイズ（バイト単位）です。これらの引数は、呼び出し元のスタックフレーム上に存在します。関数引数や戻り値は、`FP`（フレームポインタ）レジスタからの正のオフセット（例: 最初の引数なら`arg+0(FP)`）でアクセスされます。この`argsize`が明示されることで、`go vet`のようなツールがGoの関数プロトタイプとの整合性を検証できるようになります。ハイフン`-`は減算ではなく、単なる区切り文字です。

### `NOSPLIT`フラグ

`NOSPLIT`は`TEXT`ディレクティブに指定できるフラグの一つです。

*   **目的**: `NOSPLIT`が指定された関数では、Goランタイムが通常関数の冒頭に挿入する標準的なスタック分割プリアンブル（プロローグ）が省略されます。
*   **スタックの動的拡張**: Goのゴルーチンは、必要に応じてスタックを動的に拡張する機能を持っています。通常、関数が呼び出される際、十分なスタック領域があるかどうかのチェックが行われます。もし足りなければ、ランタイムはより大きなスタックを割り当て、既存のスタックの内容をコピーします。このプロセスを「スタック分割」と呼びます。
*   **`NOSPLIT`の使用場面**: `NOSPLIT`は、スタックチェックのオーバーヘッドが許容できない、またはスタック分割の実行が安全でない、あるいはデッドロックを引き起こす可能性があるような、低レベルのランタイム関数（特にスタック管理自体に関わる関数）で使用されます。
*   **影響**: `NOSPLIT`とマークされた関数は、自身のスタックフレームと、それが呼び出す可能性のある他の関数のスタックフレームが、現在利用可能なスタック領域内に収まることを保証しなければなりません。もし`NOSPLIT`関数が利用可能なスタックよりも多くのスタックを使用しようとすると、スタックオーバーフローが発生し、プログラムがクラッシュする可能性があります。
*   **`argsize`との関係**: `NOSPLIT`が使用される場合、`argsize`の部分は省略されることもありますが、明確さのため、また`go vet`によるチェックを可能にするために含めることが推奨されます。

### `nacl/amd64p32`

`nacl/amd64p32`は、Google Native Client (NaCl) プラットフォーム向けのGoのターゲットアーキテクチャの一つです。

*   **Native Client (NaCl)**: ウェブブラウザ内で安全にネイティブコードを実行するためのサンドボックス技術です。
*   **`amd64p32`**: `amd64`（64ビット）アーキテクチャをベースにしていますが、ポインタや`int`/`uint`型が32ビット幅に制限されています。これにより、ヒープサイズを小さく保つことができ、4GB以下のメモリで動作するプログラムに適しています。しかし、64ビット命令セットは引き続き利用できます。
*   **スタック破損**: プログラムがスタック上のメモリを誤って上書きしたり、不正なポインタを使用したりすることで発生します。これにより、関数の戻りアドレス、ローカル変数、または引数が破壊され、プログラムのクラッシュ、予期せぬ動作、またはセキュリティ上の脆弱性につながる可能性があります。特定のアーキテクチャやコンパイラの最適化、アセンブリコードの記述ミスなどが原因となることがあります。

## 技術的詳細

このコミットの技術的詳細は、主にGoアセンブリの`TEXT`ディレクティブにおける`argsize`の導入と、`nacl/amd64p32`特有のスタック破損修正に集約されます。

### `argsize`の導入

これまで、Goのアセンブリ関数は`TEXT symbol(SB), NOSPLIT, $framesize`のように定義され、ローカルスタックフレームのサイズ（`framesize`）のみが指定されていました。このコミットでは、`$framesize-argsize`という形式に変更することで、関数に渡される引数の合計サイズ（`argsize`）を明示的に指定するようになりました。

この変更の主な利点は以下の通りです。

*   **`go vet`による検証の強化**: `go vet`はGoのコードベースの静的解析ツールであり、一般的なバグや疑わしい構造を検出します。アセンブリ関数に対応するGoの関数プロトタイプが存在する場合、`go vet`は`TEXT`ディレクティブで指定された`argsize`と、Goのプロトタイプで定義された引数の合計サイズが一致するかどうかを検証できるようになります。これにより、アセンブリコードとGoコード間のインターフェースの不整合に起因するランタイムエラーを未然に防ぐことができます。
*   **コードの明確化**: アセンブリコードを読む開発者にとって、関数が期待する引数のサイズが明示されることで、コードの意図がより明確になります。
*   **将来的な最適化の可能性**: コンパイラやリンカが引数サイズ情報を利用して、より効率的なコード生成や最適化を行う可能性が開かれます。

例えば、`TEXT bytes·IndexByte(SB),NOSPLIT,$0`が`TEXT bytes·IndexByte(SB),NOSPLIT,$0-20`に変更された場合、これは`bytes.IndexByte`関数がローカルスタックフレームを0バイト使用し、合計20バイトの引数を受け取ることを意味します。

### `nacl/amd64p32`スタック破損の修正

`src/runtime/asm_amd64p32.s`ファイルにおける`bytes.Compare`関数の修正は、`nacl/amd64p32`環境特有のスタック破損バグに対処するものです。

変更前:
```assembly
MOVQ AX, res+24(FP)
```
変更後:
```assembly
MOVL AX, res+24(FP)
```

*   **`MOVQ` vs `MOVL`**:
    *   `MOVQ`は64ビットの値を移動する命令です。
    *   `MOVL`は32ビットの値を移動する命令です。
*   **`nacl/amd64p32`の特性**: この環境では、ポインタや一部の整数型が32ビット幅で扱われます。`AX`レジスタには比較結果が格納されますが、その結果をスタック上の`res`（戻り値）に書き込む際に、`MOVQ`を使用すると、意図せず64ビットの書き込みが行われ、隣接するスタック上のデータ（例えば、別のローカル変数や戻りアドレスの一部）を上書きしてしまう可能性があります。
*   **スタック破損の回避**: `MOVL`に変更することで、`AX`レジスタの32ビット部分のみが`res+24(FP)`に書き込まれるようになります。これにより、スタック上の他の領域への意図しない上書きが防止され、スタック破損バグが解消されます。これは、`nacl/amd64p32`の32ビットポインタ/整数型の特性と、`amd64`の64ビットレジスタの組み合わせに起因する、非常に低レベルかつアーキテクチャ固有のバグ修正です。

## コアとなるコードの解説

### `TEXT`ディレクティブの変更

`TEXT`ディレクティブにおける`$framesize-argsize`形式への変更は、アセンブリ関数がGoの関数プロトタイプとどのように連携するかをより正確に定義します。`argsize`の値は、Goの関数シグネチャに基づいて計算された引数の合計サイズと一致する必要があります。この一致は、`go vet`ツールによって検証され、不一致があれば警告またはエラーとして報告されます。これにより、アセンブリコードとGoコード間のインターフェースの堅牢性が向上し、開発者が誤った引数サイズでアセンブリ関数を呼び出すことによる潜在的なランタイムエラーを防ぎます。

例えば、`bytes.IndexByte`関数が`s []byte, c byte`という引数を受け取る場合、`s`はポインタと長さの2ワード（`amd64`では16バイト）、`c`は1バイトなので、合計で17バイトの引数サイズとなります。しかし、スタックアライメントやパディングの都合上、実際の`argsize`は20バイトや32バイトといった値になることがあります。このコミットでは、各アーキテクチャにおける実際の引数サイズが正確に反映されています。

### `nacl/amd64p32`の`MOVQ`から`MOVL`への変更

`nacl/amd64p32`アーキテクチャにおける`bytes.Compare`関数の修正は、スタック破損という深刻なバグを修正するものです。`bytes.Compare`は2つのバイトスライスを比較し、結果を`AX`レジスタに格納します。この結果をスタック上の戻り値領域（`res+24(FP)`）に書き込む際に、誤って`MOVQ`（64ビット移動）命令が使用されていました。

`nacl/amd64p32`は32ビットポインタ環境であるため、スタック上のデータ構造も32ビット幅を前提としている部分があります。`MOVQ`で64ビットの書き込みを行うと、`res`の領域だけでなく、その隣接するメモリ領域まで上書きしてしまう可能性があります。これにより、スタック上の他の重要なデータ（例えば、呼び出し元の戻りアドレスや他のローカル変数）が破壊され、プログラムがクラッシュしたり、予期せぬ動作を引き起こしたりする「スタック破損」が発生します。

`MOVL`（32ビット移動）命令に修正することで、`AX`レジスタの32ビット部分のみが書き込まれるようになり、スタック上の他の領域への意図しない上書きが防止されます。これは、特定のアーキテクチャの特性を考慮した、非常に重要な低レベルのバグ修正です。

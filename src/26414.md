# [インデックス 26414] ファイルの概要

このコミットは、Go言語の標準ライブラリである `net/http` パッケージにおいて、HTTPクライアントがリダイレクトを処理する際に、元のリクエストに設定されたキャンセルチャネル (`Request.Cancel`) がリダイレクト後の新しいリクエストに適切に伝播されないというバグを修正するものです。この修正により、リダイレクトが発生するHTTPリクエストでも、途中でキャンセル機能が正しく動作するようになります。

## 変更の背景

Goの `net/http` パッケージの `Client` は、HTTPリクエストを送信し、必要に応じてリダイレクトを自動的に処理する機能を持っています。しかし、このコミット以前のバージョンでは、リダイレクトが発生した際に、`Client` が内部的に新しい `http.Request` オブジェクトを作成する際、元のリクエストに設定されていた `Request.Cancel` チャネルが新しいリクエストにコピーされていませんでした。

`Request.Cancel` チャネルは、Go 1.7で `context.Context` が導入される以前のGoにおいて、進行中のHTTPリクエストを外部からキャンセルするための主要なメカニズムでした。このチャネルに値を送信することで、リクエストの処理を中断させることができました。

このバグにより、もしユーザーがリダイレクトされる可能性のあるHTTPリクエストに対してキャンセルチャネルを設定していたとしても、リダイレクトが発生すると、その後のリダイレクト先へのリクエストはキャンセルチャネルと関連付けられなくなり、キャンセル操作が無効になってしまうという問題がありました。これは、特にタイムアウト処理やユーザーによる操作の中断など、リクエストのライフサイクルを制御したい場合に深刻な問題となります。コミットメッセージにある `Fixes #14053` は、この具体的な問題を追跡していたGoのIssue番号を示しています。

## 前提知識の解説

### Goの `net/http` パッケージ
`net/http` パッケージは、Go言語でHTTPクライアントおよびサーバーを実装するための標準ライブラリです。

-   **`http.Client`**: HTTPリクエストを送信するためのクライアント構造体です。リダイレクトの処理、クッキーの管理、タイムアウト設定など、HTTPクライアントの一般的な機能を提供します。
-   **`http.Request`**: HTTPリクエストを表す構造体です。URL、メソッド、ヘッダー、ボディなどのリクエスト情報を保持します。
-   **`http.Response`**: HTTPレスポンスを表す構造体です。ステータスコード、ヘッダー、ボディなどのレスポンス情報を保持します。

### `Request.Cancel` チャネル
Go 1.7で `context.Context` が導入される以前、`http.Request` 構造体には `Cancel` というフィールドがありました。これは `chan struct{}` 型のチャネルで、このチャネルに値を送信することで、そのリクエストに関連する処理（ネットワーク接続の確立、レスポンスボディの読み取りなど）を中断させることができました。これは、長時間かかるリクエストや、ユーザーが途中で操作を中止した場合などにリソースを解放するために使用されました。

### HTTPリダイレクト
HTTPリダイレクトは、サーバーがクライアントに対して、要求されたリソースが別のURIに移動したことを伝えるメカニズムです。HTTPステータスコード3xx（例: 301 Moved Permanently, 302 Found, 307 Temporary Redirect）がこれに該当します。`http.Client` はデフォルトでこれらのリダイレクトを自動的に追跡し、新しいURIに対して再度リクエストを送信します。

## 技術的詳細

`http.Client` の `doFollowingRedirects` メソッドは、リダイレクトチェーンを処理する内部関数です。この関数内で、リダイレクトが発生するたびに新しい `http.Request` オブジェクトが作成されます。

問題は、この新しいリクエストオブジェクトが作成される際に、元のリクエスト (`ireq`) から `Cancel` チャネルがコピーされていなかった点にありました。具体的には、以下のコードパスで新しいリクエスト `nreq` が作成されますが、`nreq.Cancel` は初期値（`nil`）のままでした。

```go
// 修正前の擬似コード
func (c *Client) doFollowingRedirects(ireq *Request, shouldRedirect func(int) bool) (*Response, error) {
    // ...
    for redirect := 0; ; redirect++ {
        if redirect != 0 {
            nreq := new(Request) // 新しいリクエストオブジェクトが作成される
            // nreq.Cancel はここでコピーされない
            nreq.Method = ireq.Method
            // ... 他のフィールドはコピーされる
        }
        // ...
    }
    // ...
}
```

これにより、リダイレクト後のリクエストは、元のリクエストのキャンセルメカニズムから切り離されてしまい、たとえ元のリクエストの `Cancel` チャネルがクローズされても、リダイレクト後のリクエストはキャンセルされずに続行されてしまうという動作になっていました。これは、リソースの無駄遣いや、アプリケーションの応答性の低下につながる可能性がありました。

このコミットは、この問題を解決するために、新しいリクエストオブジェクトが作成される際に `ireq.Cancel` を `nreq.Cancel` に明示的にコピーするように変更しました。これにより、リダイレクトチェーン全体を通じてキャンセルチャネルが伝播され、どの段階のリクエストであっても適切にキャンセルされるようになります。

## コアとなるコードの解説

### `src/net/http/client.go` の変更

`doFollowingRedirects` 関数は、リダイレクトを処理する `http.Client` の内部メソッドです。この関数内で、リダイレクトが検出されるたびに、新しい `http.Request` オブジェクト `nreq` が作成されます。

追加された `nreq.Cancel = ireq.Cancel` の一行は、この新しいリクエスト `nreq` に対して、元のリクエスト `ireq` が持っていた `Cancel` チャネルをそのまま割り当てています。これにより、リダイレクトチェーンのどの段階で新しいリクエストが生成されても、常に元のリクエストのキャンセルチャネルを参照するようになります。結果として、元のリクエストのキャンセルチャネルがクローズされた場合、リダイレクト中のすべてのリクエストが適切にキャンセルされるようになります。

### `src/net/http/client_test.go` の変更

追加されたテストケースは、この修正が正しく機能することを検証します。

1.  **`lastReq` 変数の追加**: `CheckRedirect` 関数内で、リダイレクト後のリクエストを捕捉するために `lastReq` という変数が追加されました。
2.  **`creq.Cancel = cancel`**: テスト用の `http.Request` (`creq`) を作成し、`cancel` という新しいチャネルをその `Cancel` フィールドに設定します。
3.  **`c.Do(creq)`**: このリクエストを実行します。このリクエストはリダイレクトを発生させるように設定されていると想定されます（テストスイートの他の部分で `ts.URL` がリダイレクトを返すように設定されているため）。
4.  **`if lastReq.Cancel != cancel`**: リダイレクト後に `CheckRedirect` 関数で捕捉されたリクエスト (`lastReq`) の `Cancel` チャネルが、元のリクエストに設定した `cancel` チャネルと同一であるかを検証します。もし同一であれば、キャンセルチャネルがリダイレクトを通じて正しく伝播されたことを意味します。

このテストは、リダイレクトが発生した際に `Request.Cancel` が正しくコピーされていることを保証し、将来的な回帰を防ぐ役割を果たします。

## 変更の背景

このコミットは、特定の変更リスト (CL 7697) が導入された後に発生したビルドエラーに対応するために作成されました。エラーは `doasm` ツールが386アーキテクチャ上で失敗するというもので、具体的には `CMPL $0, BX` というアセンブリ命令の生成に関する問題でした。

`doasm` はGoコンパイラの一部であり、Goのコードからアセンブリコードを生成する際に使用されます。386アーキテクチャは、Intel 80386プロセッサに代表される32ビットのx86アーキテクチャを指します。このアーキテクチャでは、`CMPL` (Compare Long) 命令のオペランドの順序が重要になる場合があります。

エラーメッセージ `doasm: notfound ft=2 tt=20 00112 (runtime/iface_test.go:207) CMPL $0, BX 2 20` は、`doasm` が期待する形式のアセンブリ命令を見つけられなかったことを示唆しています。特に `CMPL $0, BX` という形式が問題となっていました。コミットメッセージによると、この問題は本来 `liblink` (Goのリンカライブラリ) で修正されるべき性質のものですが、緊急のワークアラウンドとして、コンパイラ側で `CMPL BX, $0` という形式を生成するように変更されました。これは、オペランドの順序を入れ替えることで、`doasm` が正しく処理できるようにするための暫定的な措置です。

## 前提知識の解説

*   **`cmd/internal/gc`**: Go言語のコンパイラ (`gc`) の内部パッケージです。Goのソースコードを解析し、中間表現を生成し、最終的に実行可能なバイナリコードに変換する役割を担います。
*   **`doasm`**: Goコンパイラツールチェーンの一部で、Goのランタイムや標準ライブラリの一部で手書きのアセンブリコードを扱うためのツールです。Goの抽象構文木 (AST) や中間表現から、特定のアセンブリ命令を生成する際に利用されます。
*   **386アーキテクチャ**: Intel 80386プロセッサに由来する32ビットのx86命令セットアーキテクチャです。Goは様々なアーキテクチャをサポートしており、それぞれのアーキテクチャに特化したコード生成ロジックを持っています。
*   **`CMPL` 命令**: x86アセンブリ言語における比較命令です。2つのオペランドを比較し、その結果に基づいてCPUのフラグレジスタを設定します。例えば `CMPL A, B` は `A - B` を計算し、その結果に基づいてフラグを設定しますが、実際には `A` と `B` の値は変更しません。この命令のオペランドの順序は、一部のツールやリンカにとって意味を持つことがあります。
*   **`liblink`**: Goのリンカライブラリです。コンパイラによって生成されたオブジェクトファイルを結合し、最終的な実行可能ファイルを生成する役割を担います。アセンブリ命令の解釈や最適化も行います。
*   **`Nod` 関数**: GoコンパイラのAST (Abstract Syntax Tree) を構築する際に使用される内部関数です。`Nod(opcode, left, right)` のような形式で、特定の操作 (opcode) とそのオペランド (left, right) を表現するノードを作成します。
    *   `opcode`: 実行される操作の種類を示します。例えば `OAS` は代入 (Assignment)、`ONE` は等価性チェック (Equal) などを意味します。
    *   `left`, `right`: オペランドとなるASTノードです。
*   **`OITAB`**: インターフェーステーブル (Interface Table) に関連する操作を示すopcodeです。Goのインターフェースは、実行時に型アサーションやメソッド呼び出しのためにインターフェーステーブルを使用します。
*   **`nodnil()`**: Goコンパイラ内部で `nil` を表すASTノードを生成する関数です。

## 技術的詳細

問題の核心は、`doasm` が386アーキテクチャで `CMPL $0, BX` という形式のアセンブリ命令を正しく処理できないことにありました。これは、`CMPL` 命令のオペランドの順序が、`doasm` の内部的な期待と合致しなかったためと考えられます。

一般的なx86アセンブリでは、`CMPL $0, BX` はレジスタ `BX` の内容と即値 `0` を比較することを意味します。一方、`CMPL BX, $0` は `0` と `BX` の内容を比較することを意味します。数学的には `BX - 0` と `0 - BX` は異なる結果をもたらしますが、フラグレジスタの更新という観点では、符号フラグやゼロフラグの挙動が異なる場合があります。`doasm` は特定のアセンブリ命令パターンを認識して処理するため、このオペランドの順序の違いが問題を引き起こしました。

このコミットでは、`src/cmd/internal/gc/walk.go` 内の `walkexpr` 関数において、インターフェース関連の比較 (`fromKind == "I" && toKind == "E"` または `fromKind == "E" && toKind == "E"`) を処理する部分が変更されました。元々は `fast = Nod(ONE, tab, nodnil())` となっていた箇所が `fast = Nod(ONE, nodnil(), tab)` に変更されています。

この変更は、`Nod` 関数の引数の順序を入れ替えることで、コンパイラが生成する中間表現、ひいては最終的に `doasm` が処理するアセンブリ命令のオペランド順序を逆転させることを目的としています。具体的には、`Nod(ONE, tab, nodnil())` は `tab == nil` のような比較を意図している可能性があり、これが `CMPL $0, BX` のようなアセンブリに変換されていたと推測されます。引数を `Nod(ONE, nodnil(), tab)` に変更することで、`nil == tab` のような比較を意図し、これが `CMPL BX, $0` のようなアセンブリに変換されるように誘導しています。

この修正は `liblink` 側の根本的な問題を解決するものではなく、コンパイラ側で `doasm` が期待する形式のアセンブリを生成するように調整する、一時的なワークアラウンドです。

## コアとなるコードの解説

変更は `src/cmd/internal/gc/walk.go` ファイルの `walkexpr` 関数内にあります。この関数は、Goの抽象構文木 (AST) を走査し、最適化やコード生成のための変換を行うコンパイラの重要な部分です。

具体的には、`walkexpr` 関数内でインターフェース型 (`I`) と空インターフェース型 (`E`) の間の比較を処理する `switch` 文の `case` ブロックが変更されています。

*   `fromKind == "I" && toKind == "E"`: インターフェース型から空インターフェース型への変換または比較。
*   `fromKind == "E" && toKind == "E"`: 空インターフェース型同士の比較。

これらのケースでは、`tab := Nod(OITAB, from, nil)` によってインターフェーステーブルに関連するノード `tab` が作成されます。この `tab` ノードは、インターフェースの値が `nil` であるかどうかをチェックするために使用されると推測されます。

変更前のコード:
`fast = Nod(ONE, tab, nodnil())`
これは、`tab` と `nodnil()` (nilを表すノード) の等価性をチェックするASTノード `fast` を生成していました。この順序が、386アーキテクチャの `doasm` で `CMPL $0, BX` のような問題のあるアセンブリを生成する原因となっていました。

変更後のコード:
`fast = Nod(ONE, nodnil(), tab)`
ここでは、`nodnil()` と `tab` の順序が入れ替えられています。これにより、`doasm` が `CMPL BX, $0` のような、問題なく処理できるアセンブリを生成するように誘導されます。

最終的に、`if fast != nil { n = Nod(OAS, ok, fast) }` の行で、この比較結果 (`fast`) が `ok` という変数に代入されるASTノードが作成されます。これは、インターフェースの比較結果をブール値として利用するための一般的なパターンです。

この変更は、コンパイラが生成する中間表現のわずかな調整によって、特定アーキテクチャのアセンブリ生成ツールの問題を回避するという、実用的なワークアラウンドを示しています。

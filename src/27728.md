`runtime: merge lfstack_amd64.go into lfstack_64bit.go`

このコミットは、`amd64`アーキテクチャ向けのロックフリースタック（`lfstack`）の実装を、より一般的な64ビットアーキテクチャ向けの実装ファイルである`lfstack_64bit.go`に統合するものです。

## 変更の背景

Goランタイムは、様々なアーキテクチャをサポートしており、パフォーマンス最適化や特定のハードウェア特性への対応のため、アーキテクチャ固有のコードを持つことがあります。しかし、複数のアーキテクチャで共通するロジックがある場合、それぞれのアーキテクチャ向けに個別のファイルを持つことはコードの重複を招き、保守を困難にします。

このコミットの背景には、`amd64`アーキテクチャの`lfstack`実装が、他の64ビットアーキテクチャ（`arm64`, `mips64`など）と多くの共通点を持つようになったという認識があります。特に、ポインタとカウンタを単一の`uint64`値にパック/アンパックするロジックにおいて、`amd64`特有の仮想アドレスの扱いの違いを除けば、基本的な構造は共通していました。

そのため、コードの重複を解消し、ランタイムのフットプリントを削減し、将来的な変更を容易にするために、`amd64`固有のコードを汎用64ビット実装にマージすることが決定されました。これにより、`lfstack_amd64.go`というファイルが削除され、`lfstack_64bit.go`が`amd64`もカバーするように拡張されました。

## 前提知識の解説

### ロックフリースタック (Lock-Free Stack)

ロックフリーデータ構造は、複数のスレッドが同時にアクセスしても、ロック（ミューテックスなど）を使用せずに正しく動作するデータ構造です。これにより、ロックの競合によるパフォーマンスの低下やデッドロックのリスクを回避できます。ロックフリースタックは、特に並行性の高い環境で、要素のプッシュ（追加）とポップ（削除）を効率的に行うために使用されます。Goランタイムでは、ゴルーチンのスケジューリングやメモリ管理など、様々な内部処理でロックフリーデータ構造が活用されています。

ロックフリースタックの実装では、通常、CAS (Compare-And-Swap) のようなアトミック操作が用いられます。スタックのトップを示すポインタと、操作の回数を記録するカウンタを組み合わせて、ABA問題（ある値がAからBに変わり、再びAに戻ることで、CAS操作が誤って成功してしまう問題）を回避することが一般的です。

### ポインタパッキング (Pointer Packing)

Goランタイムでは、メモリ効率とアトミック操作の効率化のために、複数の情報を単一のワード（この場合は`uint64`）にパックすることがあります。このコミットで扱われている`lfstackPack`と`lfstackUnpack`関数は、まさにこのポインタパッキングの例です。具体的には、スタックノードへのポインタと、スタック操作のカウンタを一つの`uint64`値に格納しています。

### AMD64アーキテクチャの仮想アドレス空間

`amd64`（x86-64）アーキテクチャでは、64ビットのレジスタとアドレスバスを持ちますが、現在のほとんどのCPUでは、実際に使用される仮想アドレス空間は64ビットすべてではありません。一般的には48ビットの仮想アドレスが使用され、この48ビットアドレスは64ビットのレジスタ内で上位ビットが符号拡張（sign-extended）されて格納されます。つまり、アドレスが`0x00007fffffffffff`のような形であれば、上位16ビットは`0`で埋められますが、アドレスが`0xffff800000000000`のような形であれば、上位16ビットは`f`で埋められます。

この符号拡張の特性は、ポインタパッキングを行う際に考慮する必要があります。特に、ポインタをシフトしてカウンタのためのスペースを確保する場合、符号拡張された上位ビットが邪魔になることがあります。

### Goのビルドタグ (`+build`)

Goのソースファイルには、ファイルの先頭に`+build`ディレクティブを記述することで、特定のビルド条件（OS、アーキテクチャなど）が満たされた場合にのみそのファイルをコンパイルするように指定できます。例えば、`// +build amd64`は`amd64`アーキテクチャでのみコンパイルされ、`// +build arm64 mips64`は`arm64`または`mips64`アーキテクチャでコンパイルされます。このコミットでは、`lfstack_64bit.go`のビルドタグに`amd64`が追加され、`lfstack_amd64.go`が削除されています。

## 技術的詳細

このコミットの核心は、`lfstack_64bit.go`ファイル内の`lfstackUnpack`関数の変更と、`amd64`特有の仮想アドレスの扱いの統合です。

`lfstackPack`と`lfstackUnpack`関数は、ロックフリースタックの実装において、スタックノードのポインタと、スタックの変更回数を表すカウンタを、単一の`uint64`値に効率的に格納（パック）し、そこから元のポインタとカウンタを復元（アンパック）するために使用されます。

元の`lfstack_64bit.go`は、`arm64`, `mips64`などのアーキテクチャを対象としていました。これらのアーキテクチャでは、仮想アドレスの符号拡張に関する特別な考慮が不要な場合が多いです。しかし、`amd64`では前述の通り、48ビットの仮想アドレスが64ビットに符号拡張されるため、ポインタをパックする際に上位16ビットがアドレスの一部としてではなく、符号拡張によって埋められている可能性があります。

コミットでは、`lfstack_64bit.go`の`lfstackUnpack`関数に以下の変更が加えられました。

```go
func lfstackUnpack(val uint64) *lfnode {
	if GOARCH == "amd64" {
		// amd64 systems can place the stack above the VA hole, so we need to sign extend
		// val before unpacking.
		return (*lfnode)(unsafe.Pointer(uintptr(int64(val) >> cntBits << 3)))
	}
	return (*lfnode)(unsafe.Pointer(uintptr(val >> cntBits << 3)))
}
```

この変更により、`amd64`アーキテクチャの場合にのみ、特別なアンパックロジックが適用されます。
-   `int64(val)`: `val`を`int64`にキャストすることで、符号拡張された上位ビットが正しく扱われるようにします。`uint64`のままでは、上位ビットが`1`の場合に非常に大きな正の数として扱われてしまいます。
-   `>> cntBits`: パックされた`uint64`値からカウンタ部分（下位`cntBits`ビット）をシフトして取り除きます。
-   `<< 3`: Goのポインタは通常8バイトアラインメントされているため、アドレスの下位3ビットは常に`0`です。この3ビットはカウンタの一部として利用されることがあり、アンパック時には元のポインタアドレスを復元するために左に3ビットシフトして戻す必要があります。

この修正により、`amd64`の仮想アドレスの特性を考慮しつつ、他の64ビットアーキテクチャと共通のファイルで`lfstack`の実装を維持できるようになりました。`lfstack_amd64.go`が削除されたことで、コードベースの簡素化と保守性の向上が実現されています。

## コアとなるコードの解説

このコミットの主要な変更は、`lfstack_64bit.go`内の`lfstackUnpack`関数に`amd64`アーキテクチャ固有の条件分岐が追加された点です。

`lfstackPack`関数は、`lfnode`ポインタと`cnt`（カウンタ）を`uint64`にパックします。この際、ポインタの上位ビットと下位ビットの一部をカウンタのために利用します。`addrBits`は仮想アドレスの有効ビット数を示し、`cntBits`はカウンタに割り当てるビット数を示します。

`lfstackUnpack`関数は、パックされた`uint64`値から元の`lfnode`ポインタを復元します。
一般的な64ビットアーキテクチャでは、`val >> cntBits << 3`という操作でポインタを復元できます。`>> cntBits`でカウンタ部分を取り除き、`<< 3`でポインタのアラインメントを考慮して元の位置に戻します。

しかし、`amd64`アーキテクチャでは、48ビットの仮想アドレスが64ビットに符号拡張されるという特殊性があります。このため、パックされた`uint64`値が、実際のアドレスと符号拡張された上位ビットを含んでいる可能性があります。単純に`uint64`としてシフトすると、符号拡張された上位ビットが正しく解釈されず、誤ったアドレスが生成される可能性があります。

そこで、`if GOARCH == "amd64"`のブロックが追加されました。このブロック内では、まず`val`を`int64`にキャストします。これにより、`val`が負の値として解釈され、符号拡張された上位ビットが正しく扱われるようになります。その後、`>> cntBits << 3`という操作を行うことで、`amd64`の仮想アドレスの特性を考慮した上で、正確な`lfnode`ポインタが復元されます。

この変更により、`amd64`固有の`lfstack_amd64.go`ファイルが不要となり、`lfstack_64bit.go`がすべての64ビットアーキテクチャに対応する汎用的な実装として機能するようになりました。これは、コードのモジュール化と保守性の観点から重要な改善です。

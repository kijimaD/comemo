## 変更の背景

Goのガベージコレクタ（GC）は、メモリを効率的に管理するために、プログラム内のポインタを追跡し、到達可能なオブジェクトを特定します。グローバル変数はGCルート（GCがスキャンを開始する起点）の一つであり、常にGCの対象となります。

このコミットの背景には、Goランタイムのシグナルキューを管理する`sig`というグローバル構造体があります。この`sig`構造体には、シグナルマスクや状態を保持するフィールドが含まれています。以前のコードでは、シグナル受信時に使用される`recv`という一時的なバッファが、`signal_recv`関数内のローカルな静的配列として定義されていました。

`recv`配列は`uint32`型の要素のみで構成されており、ポインタを含んでいません。しかし、GCはデフォルトではグローバル変数や静的変数の内容をスキャンしてポインタを探します。`recv`がポインタを含まないにもかかわらずGCがスキャンすることは、GCのオーバーヘッドとなり、パフォーマンスの低下を招く可能性がありました。

この変更の目的は、`sig`構造体（およびその一部となった`recv`配列）がポインタを含まないことをGCに明示的に伝えることで、GCの不要なスキャンを回避し、ランタイムのパフォーマンスを最適化することです。

## 前提知識の解説

### Goのガベージコレクタ (GC)

Goのガベージコレクタは、主に「マーク＆スイープ」アルゴリズムに基づいています。これは、プログラムが使用しているメモリ（到達可能なオブジェクト）を特定し、それ以外の不要なメモリ（到達不可能なオブジェクト）を解放するプロセスです。

1.  **マークフェーズ**: GCは、プログラムの実行を一時停止（ストップ・ザ・ワールド）し、GCルート（例: グローバル変数、実行中のGoルーチンのスタック、レジスタなど）から開始して、ポインタを辿りながら到達可能なすべてのオブジェクトを「生きている（live）」とマークします。
2.  **スイープフェーズ**: マークされなかったオブジェクトは「死んでいる（dead）」と判断され、メモリが解放されます。

GCの効率は、マークフェーズでスキャンするメモリ領域の量に大きく依存します。ポインタを含まないことが確実な領域をスキャンしないことで、GCの実行時間を短縮できます。

### ポインタとGC

GCは、メモリ内のポインタを識別し、それらが指すオブジェクトを追跡することで、オブジェクト間の参照関係を理解します。`int`、`bool`、`uint32`などのプリミティブ型はポインタを含まないため、GCはこれらの型の内部をスキャンする必要がありません。

### `NOPTR`

`NOPTR`は「No Pointer」の略で、Goランタイムの内部で使われる特別なディレクティブです。これは、特定のデータ構造やメモリ領域がポインタを一切含まないことをGoコンパイラやリンカに明示的に伝えるために使用されます。

`#pragma textflag NOPTR`のような形式でコードに記述されると、その後に続くグローバル変数や静的変数のデータがポインタを含まないことをGCに保証します。これにより、GCはそのメモリ領域をスキャンする手間を省き、GCのサイクルを高速化することができます。特に、`unsafe.Pointer`や`uintptr`を介してポインタを扱う場合、Goの型システムがポインタとして認識しないため、GCが誤ってそれらをスキャンしないように`NOPTR`の指定が重要になることがあります。

### `sigqueue.goc`とシグナルハンドリング

`sigqueue.goc`は、GoランタイムがOSからのシグナル（例: `SIGINT`、`SIGTERM`）を処理するための重要なコンポーネントです。Goプログラムは、OSからシグナルを受け取ると、それを直接Goルーチンにディスパッチするのではなく、まずランタイムの内部キューに格納します。その後、`signal_recv`のような関数を通じて、Goルーチンがキューからシグナルを取得し、適切なハンドラに渡します。

`sig`構造体は、このシグナルキューの状態、マスク、および受信したシグナルを管理するためのグローバルなデータ構造です。

## 技術的詳細

このコミットの技術的な核心は、Goのガベージコレクタの動作を最適化するために、グローバル変数`sig`を`NOPTR`としてマークした点にあります。

1.  **グローバル変数`sig`の性質**: `sig`はGoランタイムのグローバル変数であり、GCルートとして扱われます。つまり、GCは常に`sig`構造体を「生きている」ものとして認識し、その内容をスキャンしようとします。
2.  **`sig`構造体の内容**: `sig`構造体には、`Note`、`mask`、`wanted`、`state`、`inuse`といったフィールドが含まれています。これらのフィールドは、`Note`（ミューテックスのような同期プリミティブ）、`uint32`配列、`uint32`、`bool`といった、いずれもポインタを含まないプリミティブ型で構成されています。
3.  **`recv`配列の移動**: 以前は`signal_recv`関数内にローカルな静的変数として存在していた`recv`配列（これも`uint32`の配列でポインタを含まない）が、このコミットで`sig`構造体の中に移動されました。
4.  **`#pragma textflag NOPTR`の適用**: `sig`構造体の定義の直前に`#pragma textflag NOPTR`が追加されました。このディレクティブは、コンパイラとリンカに対して、`sig`構造体全体がポインタを含まないことを明示的に伝えます。
5.  **GCの最適化**: `sig`が`NOPTR`としてマークされたことで、GoのGCは`sig`構造体のメモリ領域をスキャンする必要がなくなります。GCは、この領域にはポインタが存在しないことを知っているため、スキャンをスキップし、その分GCの実行時間を短縮できます。これは、特にシグナル処理が頻繁に行われるような高負荷なシステムにおいて、わずかながらもパフォーマンスの向上に寄与します。

要するに、この変更は、GCに「このグローバル変数はポインタを持っていないので、スキャンする必要はない」と教えることで、GCの無駄な作業を減らし、ランタイムの効率を高めるものです。

## コアとなるコードの解説

1.  **`#pragma textflag NOPTR`の追加**:
    ```c
    +#pragma textflag NOPTR
     static struct {
    ```
    この行は、Goコンパイラとリンカに対する指示です。続く`sig`構造体がポインタを一切含まないことを明示的に宣言しています。これにより、Goのガベージコレクタは、`sig`構造体のメモリ領域をスキャンするプロセスを完全にスキップできるようになり、GCの効率が向上します。

2.  **`sig`構造体への`recv`フィールドの追加**:
    ```c
     	uint32 mask[(NSIG+31)/32];
     	uint32 wanted[(NSIG+31)/32];
    +\tuint32 recv[(NSIG+31)/32];
     	uint32 state;
     	bool inuse;
     } sig;
    ```
    以前は`signal_recv`関数内にローカルな静的変数として定義されていた`recv`配列が、グローバルな`sig`構造体のメンバーとして移動されました。`recv`配列は、受信したシグナルを一時的に保持するために使用されます。この移動により、`recv`も`sig`構造体全体に適用される`NOPTR`の恩恵を受けることになります。

3.  **`signal_recv`関数内の`recv`配列の削除**:
    ```diff
    -	static uint32 recv[nelem(sig.mask)];
    ```
    `recv`配列がグローバルな`sig`構造体の一部となったため、`signal_recv`関数内のローカルな静的定義は不要となり削除されました。

4.  **`recv`へのアクセス方法の変更**:
    ```diff
    -\t\t\tif(recv[i/32]&(1U<<(i&31))) {
    -\t\t\t\trecv[i/32] ^= 1U<<(i&31);
    +\t\t\tif(sig.recv[i/32]&(1U<<(i&31))) {
    +\t\t\t\tsig.recv[i/32] ^= 1U<<(i&31);
    ```
    ```diff
    -\t\t\trecv[i] = m;
    +\t\t\tsig.recv[i] = m;
    ```
    `recv`が`sig`構造体のメンバーになったため、その要素にアクセスする際には`sig.recv[i/32]`のように、`sig`プレフィックスを付けて参照するように変更されました。

これらの変更により、Goランタイムはシグナル処理に関連するグローバルなデータ構造のメモリ管理をより効率的に行い、ガベージコレクタのパフォーマンスを向上させています。

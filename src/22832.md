# [インデックス 22832] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）におけるレース検出モードでの`OGETG`の取り扱いに関する修正です。具体的には、`getg`が組み込み関数（intrinsic）になったことで、`runtime.LockOSThread`のようなランタイム関数がより積極的にインライン化されるようになり、その結果、ランタイムコードが他のパッケージにインライン化された際に、レース検出器が誤検知（false positive）を報告する問題に対処しています。

## 元コミット内容

このコミットは、Goコンパイラがレース検出モードで`OGETG`（`getg`関数の内部表現）を処理する方法を修正します。`getg`がコンパイラの組み込み関数（intrinsic）として扱われるようになった結果、`runtime.LockOSThread`のようなランタイム関数がより頻繁にインライン化されるようになりました。これにより、ランタイムコードが他のパッケージにインライン化されると、レース検出器が誤ってデータ競合を報告する問題が発生しました。これは、レース検出器がランタイム内部の同期メカニズムを無視するように設計されているためです。特に`LockOSThread`のインライン化は、`m`（マシン）構造体の内容に関する誤った競合報告を引き起こしていました。このコミットは、この問題（Issue #10380）を解決することを目的としています。

## 変更の背景

Goのレース検出器は、並行プログラムにおけるデータ競合を特定するための強力なツールです。しかし、その設計上、Goランタイム内部の同期処理はレース検出の対象外とされています。これは、ランタイム自体が複雑な内部同期メカニズムを持っており、それらをすべて検出対象にすると、大量の誤検知が発生し、本来検出したいユーザーコードの競合が埋もれてしまうためです。

このコミットの背景には、`getg`（現在のゴルーチン構造体`g`へのポインタを取得する関数）がコンパイラの組み込み関数（intrinsic）として扱われるようになったという重要な変更があります。組み込み関数とは、コンパイラが特定の関数呼び出しを、より最適化された（しばしばアセンブリレベルの）コードに直接置き換えることができる特殊な関数です。`getg`がintrinsicになったことで、コンパイラは`getg`を含む関数、特に`runtime`パッケージ内の関数をより積極的にインライン化するようになりました。

`runtime.LockOSThread`は、現在のゴルーチンを特定のOSスレッドに固定するランタイム関数です。この関数は、Cライブラリとの連携や特定のシステムコールなど、スレッドアフィニティが必要な場面で利用されます。`LockOSThread`はGoランタイムの内部構造、特にOSスレッドを表す`m`（machine）構造体と密接に連携しています。

問題は、`LockOSThread`のようなランタイム関数が、ユーザーコードを含む他のパッケージにインライン化された場合に発生しました。インライン化されたランタイムコードは、もはや「ランタイム内部」とは見なされず、レース検出器の計測対象となってしまいます。その結果、ランタイム内部で`m`構造体に対して行われる正当な操作が、レース検出器によってデータ競合として誤って報告されるようになりました。これは、レース検出器がランタイム内部の同期を無視するという前提と矛盾する「偽陽性（false positive）」であり、開発者を混乱させ、本来のデータ競合の検出を妨げる可能性がありました。

このコミットは、この偽陽性の問題を解決し、レース検出器の信頼性を維持するために行われました。

## 前提知識の解説

### Goのレース検出器 (Race Detector)

Goのレース検出器は、並行処理におけるデータ競合（data race）を検出するための動的解析ツールです。データ競合は、複数のゴルーチンが同じメモリ位置に同時にアクセスし、そのうち少なくとも1つが書き込みであり、かつそれらのアクセスが同期メカニズムによって適切に保護されていない場合に発生します。データ競合は、プログラムの予測不能な動作、クラッシュ、またはデータの破損を引き起こす可能性があります。

レース検出器は、プログラムの実行中にメモリアクセスを監視し、競合のパターンを特定します。Goのレース検出器は非常に効果的ですが、ランタイム内部のコードは通常、検出の対象外とされています。これは、ランタイムが自身の内部状態を管理するために独自の低レベル同期を使用しており、これらをすべて検出対象にすると、大量のノイズが発生するためです。

### インライン化 (Inlining)

インライン化は、コンパイラ最適化の一種です。関数呼び出しを、その関数の本体のコードで直接置き換えることで、関数呼び出しのオーバーヘッド（引数の渡し、スタックフレームのセットアップと破棄、制御フローのジャンプなど）を削減します。これにより、プログラムの実行速度が向上し、さらにコンパイラがより広範な最適化（定数伝播、デッドコード削除など）を実行できるようになります。

Goコンパイラ（`cmd/gc`）は、関数のサイズや複雑さに基づいてインライン化を行うかどうかを決定します。通常、小さな関数や頻繁に呼び出される関数がインライン化の候補となります。

### `getg`とIntrinsic関数

`getg`は、現在のゴルーチン（`g`）構造体へのポインタを取得するGoランタイムの内部関数です。この`g`構造体には、ゴルーチンのスタック情報、状態、関連するOSスレッド（`m`）へのポインタなど、重要な情報が含まれています。

「Intrinsic関数」とは、コンパイラが特別に認識し、通常の関数呼び出しではなく、より最適化された（しばしばハードウェア固有の）コードに置き換えることができる関数を指します。`getg`がintrinsicになったということは、コンパイラが`getg`の呼び出しを非常に効率的な方法で処理できるようになったことを意味します。これにより、`getg`を含むコードのインライン化がより容易になり、パフォーマンスが向上します。

### `runtime.LockOSThread`

`runtime.LockOSThread`は、呼び出し元のゴルーチンを現在のOSスレッドに「固定」するGoランタイム関数です。通常、Goのスケジューラはゴルーチンを複数のOSスレッド間で自由に移動させますが、`LockOSThread`を使用すると、そのゴルーチンは特定のOSスレッドから離れることがなくなります。これは、OpenGLやC/C++ライブラリなど、スレッドアフィニティ（特定のOSスレッドで実行される必要がある）を要求する外部ライブラリと連携する場合に特に重要です。

`LockOSThread`は、Goランタイムの内部構造、特にOSスレッドを表す`m`（machine）構造体と密接に連携しています。`m`構造体には、OSスレッドの状態やレジスタ情報など、スレッド固有のデータが含まれています。

## 技術的詳細

このコミットの技術的詳細は、Goコンパイラのインライン化とレース検出器の動作の相互作用に焦点を当てています。

1.  **`getg`のIntrinsic化とインライン化の促進**:
    `getg`がコンパイラのintrinsicとして扱われるようになったことで、コンパイラは`getg`を含む関数（特に`runtime`パッケージ内の関数）をより積極的にインライン化するようになりました。インライン化はパフォーマンス向上のための重要な最適化ですが、ランタイムコードに関しては予期せぬ副作用をもたらしました。

2.  **ランタイムコードの特殊性**:
    Goのランタイムは、ガベージコレクション、スケジューリング、メモリ管理など、Goプログラムの実行を支える低レベルの機能を提供します。ランタイム内部では、非常に低レベルかつ効率的な同期メカニズムが使用されており、これらの操作はレース検出器の監視対象から意図的に除外されています。これは、ランタイムの内部動作が常に正しく同期されていると仮定されており、もしこれらを検出対象にすると、大量の偽陽性が発生し、レース検出器の有用性が損なわれるためです。

3.  **インライン化によるコンテキストの変更**:
    問題は、`runtime.LockOSThread`のようなランタイム関数が、ユーザーコードを含む他のパッケージにインライン化された場合に発生しました。インライン化によって、ランタイム関数のコードは呼び出し元のパッケージのコンテキストに埋め込まれます。この時点で、レース検出器はインライン化されたコードを「ランタイム内部」とは見なさず、通常のユーザーコードと同様に計測対象として扱ってしまいます。

4.  **`m`構造体への誤検知**:
    `LockOSThread`は、OSスレッドを表す`m`構造体と密接に連携し、その内容を操作します。この`m`構造体へのアクセスは、ランタイム内部では適切に同期されていますが、インライン化されたコードがレース検出器によって計測されると、その内部同期が無視され、`m`構造体へのアクセスがデータ競合として誤って報告されるようになりました。これが「`m`の内容に関する偽の競合報告」の具体的な原因です。

5.  **修正アプローチ**:
    この問題に対処するため、コミットは2つの主要な変更を導入しました。
    *   **ランタイム関数のインライン化の抑制**: レース検出モード（`flag_race != 0`）が有効な場合、`runtime`パッケージ内の関数のインライン化を完全に無効にします。これにより、ランタイムコードがユーザーコードにインライン化され、誤って計測されることを防ぎます。
    *   **`OGETG`の`racewalk`処理の調整**: `src/cmd/internal/gc/racewalk.go`において、`OGETG`がレース検出器の計測対象から除外されるリストから削除されました。これは、`OGETG`がランタイム内部でのみ発生し、かつそのインライン化が抑制されるようになったため、もはや特別な除外リストに含める必要がなくなったことを意味します。また、`racewalknode`関数内で`OGETG`が検出された場合にエラーを報告するようになり、`OGETG`がランタイムパッケージ以外で現れるべきではないという厳格なチェックが追加されました。

これらの変更により、レース検出器はランタイム内部のコードを誤って計測することがなくなり、偽陽性の報告が排除され、レース検出器の信頼性が向上しました。

## コアとなるコードの解説

### `src/cmd/internal/gc/inl.go` の変更

`caninl`関数は、Goコンパイラが関数をインライン化するかどうかを決定する際の主要なロジックを含んでいます。追加されたコードブロックは以下の通りです。

```go
if flag_race != 0 && myimportpath == "runtime" {
    return
}
```

*   `flag_race != 0`: これは、Goプログラムがレース検出モードでコンパイルされているかどうかを示すフラグです。`go run -race`や`go build -race`のように`-race`フラグが使用された場合に`flag_race`は非ゼロになります。
*   `myimportpath == "runtime"`: これは、現在処理している関数が`runtime`パッケージに属しているかどうかをチェックします。

この条件が真（つまり、レース検出モードが有効で、かつ`runtime`パッケージの関数である）の場合、`return`ステートメントが実行され、その関数のインライン化が阻止されます。

**この変更の目的**:
`runtime`パッケージの関数がユーザーコードにインライン化されると、レース検出器がランタイム内部の同期を誤ってデータ競合として報告する問題（偽陽性）が発生していました。この修正により、`runtime`パッケージの関数はレース検出モードではインライン化されなくなり、ランタイム内部の操作がレース検出器によって誤って計測されることがなくなります。これにより、レース検出器の報告の信頼性が向上します。

### `src/cmd/internal/gc/racewalk.go` の変更

`racewalk.go`は、Goコンパイラのレース検出器がコードを走査し、計測対象となるメモリアクセスを特定する部分です。`racewalknode`関数は、AST（抽象構文木）の各ノードを処理します。

変更点は主に2つあります。

1.  **`OGETG`のエラー報告の追加**:
    ```go
    case OGETG:
        Yyerror("racewalk: OGETG can happen only in runtime which we don't instrument")
        goto ret
    ```
    このコードは、`racewalknode`が`OGETG`ノードに遭遇した場合にエラーを報告するようにします。以前は、`OGETG`は特定の条件下で非ランタイムパッケージに現れる可能性がありましたが、`inl.go`での変更により、レース検出モードでは`runtime`パッケージのインライン化が抑制されるようになりました。したがって、`OGETG`がランタイムパッケージ以外で現れることは、もはや予期されない状況となります。このエラーは、コンパイラの内部的な整合性を保つためのチェックとして機能します。

2.  **`OGETG`のスキップリストからの削除**:
    以前のコードでは、`OGETG`はレース検出器の計測をスキップするノードのリストに含まれていました。これは、`getg`がゴルーチンローカルであり、競合しないという理由と、`runtime.LockOSThread`のような関数のインライン化によって非ランタイムパッケージに現れる可能性があるためでした。

    ```diff
    -		OGETG,
    ```
    この行が削除されたのは、`inl.go`での変更により、レース検出モードでは`runtime`パッケージのインライン化が抑制されるようになったためです。これにより、`OGETG`が非ランタイムコードにインライン化されることがなくなり、もはやこのスキップリストに含める必要がなくなりました。

**これらの変更の目的**:
これらの変更は、`inl.go`でのインライン化抑制と連携して、レース検出器が`OGETG`（およびそれに関連するランタイム内部の操作）を誤って計測しないようにします。`OGETG`がランタイム内部でのみ処理され、そのインライン化が制御されることで、レース検出器は本来の目的であるユーザーコードのデータ競合検出に集中できるようになります。

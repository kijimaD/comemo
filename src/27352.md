## 変更の背景

この変更の背景には、Goコンパイラが内部で使用する`math/big`パッケージにおける浮動小数点数の丸め処理のバグが存在していました。具体的には、`issue 14651`で報告された問題に対応するため、`math/big`パッケージの最新バージョンを取り込む必要がありました。このバグは、特に非正規化数（denormalized numbers）と呼ばれる非常に小さい浮動小数点数を扱う際に、不正確な丸め処理を引き起こす可能性がありました。コンパイラが定数式を評価する際に`math/big`を使用するため、このバグはコンパイル時の数値計算の正確性に影響を与え、予期せぬ結果や誤った最適化につながる可能性がありました。このコミットは、この重要な丸めバグを修正し、コンパイラがより正確な浮動小数点数計算を行えるようにすることを目的としています。

## 前提知識の解説

### 浮動小数点数とIEEE 754標準

コンピュータにおける浮動小数点数は、実数を近似的に表現するための形式です。Go言語を含む多くのシステムでは、IEEE 754標準に従って浮動小数点数が実装されています。この標準は、数値の表現方法（符号、指数部、仮数部）、特殊な値（無限大、非数NaN）、そして丸め規則を定義しています。

### 非正規化数 (Denormalized Numbers / Subnormal Numbers)

非正規化数（またはサブノーマル数）は、非常に小さい絶対値を持つ浮動小数点数で、正規化数では表現できない範囲の数を表します。これらは、指数部が取り得る最小値に設定され、仮数部の最上位ビットが暗黙の1ではなく0として扱われることで表現されます。非正規化数は、アンダーフロー（underflow）と呼ばれる現象、つまり表現可能な最小の正規化数よりも小さい非ゼロの結果が生じた場合に発生し、精度を維持しようとします。しかし、非正規化数の計算は、正規化数に比べて性能が低下する可能性があります。

### 丸めモード (Rounding Modes)

IEEE 754標準では、いくつかの丸めモードが定義されています。これは、正確な計算結果が浮動小数点数で表現できない場合に、どのように近似値を決定するかを定めます。主要な丸めモードには以下のようなものがあります。

*   **ToNearestEven (最近接偶数への丸め)**: 最も近い表現可能な値に丸めます。2つの表現可能な値の中間にある場合は、偶数の仮数部を持つ方に丸めます。これが最も一般的に使用されるデフォルトの丸めモードです。
*   **ToNearestAway (最近接絶対値大への丸め)**: 最も近い表現可能な値に丸めます。2つの表現可能な値の中間にある場合は、絶対値が大きい方に丸めます。
*   **ToZero (ゼロへの丸め / 切り捨て)**: ゼロ方向へ丸めます（絶対値を小さくする）。
*   **AwayFromZero (ゼロから離れる丸め / 切り上げ)**: ゼロから離れる方向へ丸めます（絶対値を大きくする）。
*   **ToNegativeInf (負の無限大への丸め)**: 負の無限大方向へ丸めます。
*   **ToPositiveInf (正の無限大への丸め)**: 正の無限大方向へ丸めます。

### `math/big`パッケージ

Go言語の標準ライブラリに含まれる`math/big`パッケージは、任意精度の数値計算を提供します。これは、`int`や`float64`のような組み込み型では表現できない、非常に大きな整数や高い精度の浮動小数点数を扱う必要がある場合に利用されます。コンパイラは、定数式の評価など、高い精度が要求される内部計算でこのパッケージを使用することがあります。

### 丸めビット (Rounding Bit) と スティッキービット (Sticky Bit)

浮動小数点数の丸め処理において、結果の精度を決定するために「丸めビット (rbit)」と「スティッキービット (sbit)」という概念が用いられます。

*   **丸めビット (rbit)**: 保持されるべき最下位ビットのすぐ右隣のビットです。このビットが0か1かによって、丸め処理の方向が大きく左右されます。
*   **スティッキービット (sbit)**: 丸めビットのさらに右にある全てのビットの論理和です。これらのビットのいずれか一つでも1であれば、スティッキービットは1となります。スティッキービットは、丸めビットの右側に非ゼロのビットが存在するかどうかを示し、結果が正確な値からどれだけ離れているかを判断するのに役立ちます。

これらのビットは、特に「最近接偶数への丸め」のような複雑な丸めモードで、正確な丸め方向を決定するために不可欠です。

## 技術的詳細

このコミットの技術的詳細の核心は、`src/cmd/compile/internal/big/float.go`内の`(*Float).round`メソッドの変更にあります。このメソッドは、`math/big.Float`型の値を指定された精度に丸める役割を担っています。

以前の実装では、丸めモードの処理が複雑で、特に非正規化数やアンダーフローの境界条件において、特定のケースで不正確な丸めが発生する可能性がありました。新しい実装では、丸めロジックが大幅に簡素化され、より堅牢になっています。

### `(*Float).round`メソッドの変更点

1.  **丸めモードの直接的な適用**: 以前は`ToNegativeInf`や`ToPositiveInf`といった丸めモードを`ToZero`や`AwayFromZero`に変換してから処理していましたが、新しい実装では各丸めモードを直接処理するようになりました。これにより、ロジックがより明確になり、エラーの可能性が減少します。
2.  **丸め決定ロジックの改善**:
    *   `rbit` (rounding bit) と `sbit` (sticky bit) の計算は維持されていますが、それらを用いた丸め決定の`switch`文の構造が大きく変更されました。
    *   新しいロジックでは、まず結果が不正確である場合に丸めが必要かどうかを判断し、その上で`inc`（インクリメント、つまり切り上げ）が必要かどうかを各丸めモードに基づいて決定します。
    *   `ToNearestEven`モードでは、`rbit != 0 && (sbit != 0 || z.mant[0]&lsb != 0)`という条件で`inc`を決定します。これは、丸めビットが1であり、かつスティッキービットが1であるか、または最下位ワードの最下位ビットが偶数でない場合に切り上げるという、IEEE 754標準の「最近接偶数への丸め」規則を正確に実装しています。
    *   `ToNearestAway`モードでは、`rbit != 0`の場合に`inc`を決定します。
    *   `ToNegativeInf`と`ToPositiveInf`モードでは、それぞれ`z.neg`（負の数であるか）と`!z.neg`（正の数であるか）に基づいて`inc`を決定します。
3.  **アンダーフロー/オーバーフロー処理の改善**:
    *   丸めによって仮数部がオーバーフローした場合（`addVW`が非ゼロを返した場合）、指数部を調整し、必要に応じて仮数部を右シフトして最上位ビットを設定するロジックがより明確になりました。
    *   指数部が`MaxExp`を超えた場合のオーバーフロー処理（`inf`への設定）も改善されています。
4.  **精度 (Accuracy) の設定**: `z.acc`（精度情報）の設定ロジックも簡素化され、`inc`と`z.neg`の組み合わせに基づいて`makeAcc`関数で決定されるようになりました。

### `Float32()` および `Float64()` メソッドの変更点

これらのメソッドは、`math/big.Float`型の値をそれぞれ`float32`または`float64`に変換する際に使用されます。変更点は主に以下の通りです。

1.  **非正規化数の処理の改善**:
    *   指数`e`が`emin`（最小正規化指数）よりも小さい場合の非正規化数の処理がより詳細になりました。
    *   特に、`p == 0`（精度が0ビット）の場合のアンダーフロー処理が明示的に記述され、`±0`または最小非正規化数への丸めが正確に行われるようになりました。これにより、`m <= 0.25`の場合や`m == 0.5`で偶数への丸めが必要な場合の挙動が明確化されています。
2.  **オーバーフロー処理の統合**: `r.form == inf`（丸めによって無限大になった場合）と`e > emax`（指数が大きすぎる場合）の両方の条件でオーバーフローを検出するようになりました。

### テストケースの追加と更新

*   `test/fixedbugs/issue14651.go`という新しいテストファイルが追加され、このコミットで修正された特定の丸めバグ（特に最小非正規化数への丸め上げ）を検証するようになりました。このテストは、`float32`と`float64`の両方で、非常に小さい値がどのように丸められるかを詳細にチェックします。

これらの変更により、`math/big`パッケージの浮動小数点数丸め処理の正確性と堅牢性が大幅に向上し、Goコンパイラがより信頼性の高い数値計算を実行できるようになりました。

## コアとなるコードの解説

### `(*Float).round`関数の変更

この関数の変更は、浮動小数点数の丸め処理の正確性を根本的に改善します。特に重要なのは、丸めモードごとの`inc`（切り上げ）決定ロジックの再構築です。

```go
// 変更後の抜粋
	// round if result is inexact
	if rbit|sbit != 0 {
		// Make rounding decision: The result mantissa is truncated ("rounded down")
		// by default. Decide if we need to increment, or "round up", the (unsigned)
		// mantissa.
		inc := false
		switch z.mode {
		case ToNegativeInf:
			inc = z.neg
		case ToZero:
			// nothing to do
		case ToNearestEven:
			inc = rbit != 0 && (sbit != 0 || z.mant[0]&lsb != 0)
		case ToNearestAway:
			inc = rbit != 0
		case AwayFromZero:
			inc = true
		case ToPositiveInf:
			inc = !z.neg
		default:
			panic("unreachable")
		}

		// A positive result (!z.neg) is Above the exact result if we increment,
		// and it's Below if we truncate (Exact results require no rounding).
		// For a negative result (z.neg) it is exactly the opposite.
		z.acc = makeAcc(inc != z.neg)

		if inc {
			// add 1 to mantissa
			if addVW(z.mant, z.mant, lsb) != 0 {
				// mantissa overflow => adjust exponent
				if z.exp >= MaxExp {
					// exponent overflow
					z.form = inf
					return
				}
				z.exp++
				// adjust mantissa: divide by 2 to compensate for exponent adjustment
				shrVU(z.mant, z.mant, 1)
				// set msb == carry == 1 from the mantissa overflow above
				const msb = 1 << (_W - 1)
				z.mant[n-1] |= msb
			}
		}
	}
```

このコードは、`rbit`（丸めビット）と`sbit`（スティッキービット）が少なくとも一つでも1である場合（つまり、結果が不正確である場合）に丸め処理を実行します。`inc`変数は、仮数部を切り上げるべきかどうかを決定します。各`case`文は、それぞれの丸めモードの規則に従って`inc`を設定します。

特に`ToNearestEven`の条件`rbit != 0 && (sbit != 0 || z.mant[0]&lsb != 0)`は、IEEE 754の「最近接偶数への丸め」を正確に実装しています。これは、丸めビットが1の場合に、スティッキービットが1であるか、または丸められる前の最下位ビットが偶数でない場合に切り上げを行うことを意味します。

`inc`が`true`の場合、仮数部に1が加算されます。この加算によって仮数部がオーバーフローした場合（`addVW`が非ゼロを返す）、指数部がインクリメントされ、仮数部が右シフトされて調整されます。これにより、丸めによる桁上がりとそれに伴う指数部の変更が正しく処理されます。

### `Float32()` / `Float64()` 関数の非正規化数処理の改善

これらの関数における非正規化数の処理の改善は、非常に小さい値が`float32`や`float64`に変換される際のエッジケースの正確性を保証します。

```go
// Float32() の変更後の抜粋
		if e < emin {
			// recompute precision
			p = mbits + 1 - emin + int(e)
			// If p == 0, the mantissa of x is shifted so much to the right
			// that its msb falls immediately to the right of the float32
			// mantissa space. In other words, if the smallest denormal is
			// considered "1.0", for p == 0, the mantissa value m is >= 0.5.
			// If m > 0.5, it is rounded up to 1.0; i.e., the smallest denormal.
			// If m == 0.5, it is rounded down to even, i.e., 0.0.
			// If p < 0, the mantissa value m is <= "0.25" which is never rounded up.
			if p < 0 /* m <= 0.25 */ || p == 0 && x.mant.sticky(uint(len(x.mant))*_W-1) == 0 /* m == 0.5 */ {
				// underflow to ±0
				if x.neg {
					var z float32
					return -z, Above
				}
				return 0.0, Below
			}
			// otherwise, round up
			// We handle p == 0 explicitly because it's easy and because
			// Float.round doesn't support rounding to 0 bits of precision.
			if p == 0 {
				if x.neg {
					return -math.SmallestNonzeroFloat32, Below
				}
				return math.SmallestNonzeroFloat32, Above
			}
		}
```

このセクションは、変換後の精度`p`が0以下になるような、非常に小さい値の処理を扱っています。

*   `p < 0`の場合（元の値が非常に小さく、`0.25`以下に相当する場合）、値は常に`±0`にアンダーフローします。
*   `p == 0`の場合、元の値が`0.5`に相当する可能性があります。この場合、`x.mant.sticky(...) == 0`（スティッキービットが0）であれば、`ToNearestEven`ルールに従って`±0`に丸められます。そうでなければ、最小の非正規化数に丸め上げられます。
*   これらの明示的な処理により、非正規化数の境界における丸め挙動が正確に制御され、`issue 14651`のようなバグが修正されます。

### `issue14651.go`テストファイル

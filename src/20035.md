# [インデックス 20035] ファイルの概要

このコミットは、GoランタイムのAMD64アセンブリコードにおいて、定数としてのグローバルアドレスの扱いを変更し、PC相対アドレス指定（PC-relative addressing）を可能にすることを目的としています。これにより、生成されるバイナリの柔軟性と効率が向上します。

## 変更の背景

この変更の背景には、x86-64アーキテクチャにおけるアドレス指定モードの進化と、Goバイナリの柔軟性および効率性の向上が挙げられます。

従来のx86-64アセンブリでは、グローバルなシンボル（関数やデータ）のアドレスを直接定数としてコードに埋め込む「絶対アドレス指定（Absolute Addressing）」が一般的に使用されていました。例えば、`PUSHQ $runtime·main·f(SB)` のように、`runtime·main·f` という関数のアドレスを直接スタックにプッシュする形式です。

しかし、絶対アドレス指定にはいくつかの問題点があります。

1.  **位置独立コード (Position-Independent Code, PIC) の生成の困難さ**: 共有ライブラリ（.soファイルなど）や、ASLR (Address Space Layout Randomization) が有効な環境では、プログラムがロードされるメモリアドレスが実行時まで確定しません。絶対アドレス指定を使用すると、コードが特定のメモリアドレスに依存するため、ロード時にアドレスを修正する「再配置（Relocation）」処理が必要になります。これはオーバーヘッドとなり、また、コードセグメントが書き込み可能である必要があるため、セキュリティ上のリスクも伴います。
2.  **コードの再利用性の低下**: 特定のアドレスに依存するコードは、そのアドレスが異なる環境ではそのまま使用できません。
3.  **キャッシュ効率の低下**: 再配置が必要な場合、コードセグメントが変更される可能性があり、CPUの命令キャッシュの効率に影響を与える可能性があります。

このコミットは、これらの問題を解決するために、グローバルアドレスを定数として直接使用する代わりに、PC相対アドレス指定（RIP-relative addressing）を利用できるようにするための準備として行われました。PC相対アドレス指定は、現在のプログラムカウンタ（RIPレジスタ）からの相対オフセットでアドレスを指定するため、コードがロードされるベースアドレスに依存せず、位置独立なコードを容易に生成できます。これにより、Goバイナリの共有ライブラリとしての利用や、ASLR環境でのパフォーマンスとセキュリティが向上します。

具体的には、`PUSHQ $symbol(SB)` のような命令を `MOVQ $symbol(SB), BP` と `PUSHQ BP` のように2つの命令に分割することで、コンパイラやアセンブラが `symbol(SB)` の部分をPC相対アドレスとしてエンコードする機会を与えています。

## 前提知識の解説

### 1. x86-64 (AMD64) アセンブリの基本

x86-64は、64ビットの汎用レジスタと命令セットを持つCPUアーキテクチャです。

*   **レジスタ**:
    *   `RAX`, `RBX`, `RCX`, `RDX`, `RSI`, `RDI`, `RBP`, `RSP`: 汎用レジスタ。`RSP`はスタックポインタ、`RBP`はベースポインタとしてよく使われます。
    *   `RIP`: 命令ポインタ（プログラムカウンタ）。次に実行される命令のアドレスを指します。
    *   `R8` - `R15`: 追加の汎用レジスタ。
*   **命令**:
    *   `MOVQ src, dest`: 64ビットの値を`src`から`dest`へ移動します。
    *   `PUSHQ src`: 64ビットの値をスタックにプッシュします。`RSP`を8バイト減らし、そのアドレスに`src`の値を格納します。
    *   `CALL target`: `target`のアドレスにジャンプし、現在の`RIP`の値をスタックにプッシュします（リターンアドレス）。
    *   `TEXT symbol(SB), flags, $framesize-argsize`: Goアセンブリにおける関数定義の開始。`SB`は静的ベース（Static Base）レジスタで、グローバルシンボルへの参照に使用されます。
*   **アドレッシングモード**: メモリ上のデータにアクセスする方法。
    *   **即値 (Immediate)**: 命令自体に定数値を埋め込む（例: `MOVQ $10, RAX`）。
    *   **レジスタ直接 (Register Direct)**: レジスタに格納された値を直接使用する（例: `MOVQ RBX, RAX`）。
    *   **メモリ直接 (Direct Memory)**: メモリ上の特定のアドレスを直接指定する（例: `MOVQ [0x12345678], RAX`）。
    *   **レジスタ間接 (Register Indirect)**: レジスタに格納されたアドレスをメモリのアドレスとして使用する（例: `MOVQ (RAX), RBX`）。
    *   **ベース+インデックス+スケール+ディスプレイスメント (Base+Index*Scale+Disp)**: `Disp(Base)(Index*Scale)` の形式で、`Base + Index * Scale + Disp` のアドレスを計算する（例: `16(RBP)(RCX*8)`）。
    *   **PC相対 (RIP-relative)**: `RIP`レジスタの現在値からの相対オフセットでアドレスを指定する。これはx86-64で導入された重要なアドレッシングモードで、位置独立コードの生成に不可欠です。

### 2. 絶対アドレス指定 (Absolute Addressing) と PC相対アドレス指定 (PC-relative Addressing)

*   **絶対アドレス指定 (Absolute Addressing)**:
    *   メモリ上の特定の固定アドレスを直接指定する方法です。
    *   例: `MOVQ $0x400000, RAX` (RAXにアドレス0x400000をロード)。
    *   問題点: プログラムがロードされるメモリアドレスが実行時まで分からない場合（ASLRや共有ライブラリ）、コード内の絶対アドレスをロード時に修正（再配置）する必要があります。これはパフォーマンスのオーバーヘッドやセキュリティリスク（コードセグメントが書き込み可能になる）を引き起こします。

*   **PC相対アドレス指定 (PC-relative Addressing)**:
    *   現在の命令ポインタ（x86-64では`RIP`レジスタ）からの相対オフセットでアドレスを指定する方法です。
    *   例: `MOVQ symbol[RIP], RAX` (RIPからの相対オフセットで`symbol`のアドレスを計算し、RAXにロード)。
    *   利点: コードがロードされるベースアドレスに依存しないため、再配置が不要になります。これにより、位置独立コード (PIC) を容易に生成でき、共有ライブラリやASLR環境での効率とセキュリティが向上します。コードセグメントは読み取り専用にできるため、セキュリティも強化されます。

### 3. Goランタイムとアセンブリ

Go言語のランタイムは、ガベージコレクション、スケジューラ、スタック管理など、言語の低レベルな側面を管理するC言語とアセンブリ言語で書かれた部分です。Goのコンパイラは、特定の最適化やプラットフォーム固有の処理のために、アセンブリコードを生成したり、既存のアセンブリコード（`asm_amd64.s`のようなファイル）を利用したりします。

*   **`SB` (Static Base)**: Goのアセンブリでは、グローバルなシンボル（関数や変数）は`SB`レジスタからのオフセットで参照されます。これは、リンカが最終的なアドレスを解決するためのプレースホルダーのようなものです。例えば、`runtime·main·f(SB)` は、`runtime`パッケージの`main·f`というグローバルシンボルを指します。

### 4. `PUSHQ` と `MOVQ` 命令

*   **`PUSHQ src`**: `src`の値をスタックにプッシュします。これは通常、1つの命令で完結します。もし`src`がグローバルシンボルのアドレスである場合、リンカは`PUSHQ`命令のオペランドとしてその絶対アドレスを埋め込む必要があります。
*   **`MOVQ src, dest`**: `src`の値を`dest`に移動します。このコミットでは、`MOVQ $symbol(SB), BP` のように、まずグローバルシンボルのアドレスを一時レジスタ（`BP`）にロードし、その後に `PUSHQ BP` のようにレジスタの値をスタックにプッシュしています。この2段階の操作により、`$symbol(SB)` の部分がPC相対アドレスとしてエンコードされる機会が生まれます。

## 技術的詳細

このコミットの技術的な核心は、x86-64アーキテクチャにおけるRIP相対アドレッシングの活用にあります。

x86-64では、命令ポインタ（RIP）からの相対オフセットを使用してメモリ位置を指定できます。これは、`symbol[RIP]` のような形式で表現されます。リンカは、`$symbol(SB)` のようなグローバルシンボルへの参照を、最終的なバイナリを生成する際に、RIP相対オフセットに変換することができます。

しかし、`PUSHQ $symbol(SB)` のような命令では、`$symbol(SB)` が即値オペランドとして扱われるため、リンカがRIP相対アドレッシングを使用する機会が制限されることがあります。`PUSHQ` 命令の即値オペランドは、通常、32ビットの符号付きオフセットに制限されるか、あるいは絶対アドレスとしてエンコードされることが一般的です。

このコミットでは、この問題を回避するために、以下のような変更を行っています。

**変更前:**
```asm
PUSHQ $runtime·main·f(SB)
```
この命令は、`runtime·main·f` の絶対アドレスを直接スタックにプッシュしようとします。リンカは、このアドレスをバイナリのロード時に修正する必要があるかもしれません。

**変更後:**
```asm
MOVQ $runtime·main·f(SB), BP
PUSHQ BP
```
この変更により、`$runtime·main·f(SB)` はまず`MOVQ`命令のソースオペランドとして扱われます。`MOVQ`命令は、RIP相対アドレッシングをサポートする柔軟なアドレッシングモードを持っています。リンカは、`$runtime·main·f(SB)` を`BP`レジスタにロードする際に、RIP相対オフセットとしてエンコードすることができます。その後、`PUSHQ BP` は`BP`レジスタに格納された値をスタックにプッシュするだけなので、アドレスの解決は既に完了しています。

このテクニックは、Goのツールチェーン（アセンブラ、リンカ）が、グローバルシンボルへの参照をより効率的かつ位置独立な方法で処理できるようにするためのものです。特に、Goのバイナリが共有ライブラリとしてビルドされる場合や、ASLRが有効なシステムで実行される場合に、再配置の数を減らし、パフォーマンスとセキュリティを向上させる効果があります。

この変更は、Goのランタイムが生成するアセンブリコードの品質を向上させ、よりモダンなx86-64の機能（RIP相対アドレッシング）を最大限に活用するための基盤を築いています。

## コアとなるコードの解説

このコミットでは、`src/pkg/runtime/asm_amd64.s` 内の複数の箇所で、グローバルシンボル（関数やデータ）のアドレスを直接即値として使用する`PUSHQ $symbol(SB)` や `MOVQ $symbol(SB), (dest)` のようなパターンが、一時レジスタ`BP`を介する2段階の操作に置き換えられています。

具体的な変更点とそれぞれの解説は以下の通りです。

1.  **`runtime·main·f` のアドレスプッシュ**
    *   **変更前**: `PUSHQ $runtime·main·f(SB)`
        *   `runtime·main·f` 関数のアドレスを直接スタックにプッシュしています。
    *   **変更後**:
        ```asm
        MOVQ	$runtime·main·f(SB), BP
        PUSHQ	BP
        ```
        *   まず、`runtime·main·f` のアドレスを`BP`レジスタにロードします。この`MOVQ`命令の段階で、リンカは`$runtime·main·f(SB)`をPC相対アドレスとしてエンコードする機会を得ます。
        *   次に、`BP`レジスタに格納されたアドレスをスタックにプッシュします。これにより、スタックには位置独立なアドレスがプッシュされることになります。

2.  **`runtime·switchtoM` のアドレス格納**
    *   **変更前**: `MOVQ $runtime·switchtoM(SB), (g_sched+gobuf_pc)(AX)`
        *   `runtime·switchtoM` 関数のアドレスを、現在の`g`（goroutine）構造体の`gobuf_pc`フィールドに直接格納しています。
    *   **変更後**:
        ```asm
        MOVQ	$runtime·switchtoM(SB), BP
        MOVQ	BP, (g_sched+gobuf_pc)(AX)
        ```
        *   同様に、`runtime·switchtoM` のアドレスを`BP`レジスタにロードし、その`BP`レジスタの値を`gobuf_pc`フィールドに格納しています。これにより、`gobuf_pc`にはPC相対で解決されたアドレスが設定されます。

3.  **`runtime·newstackcall` のアドレス格納**
    *   **変更前**: `MOVQ $runtime·newstackcall(SB), (g_sched+gobuf_pc)(AX)`
        *   `runtime·newstackcall` 関数のアドレスを、現在の`g`（goroutine）構造体の`gobuf_pc`フィールドに直接格納しています。
    *   **変更後**:
        ```asm
        MOVQ	$runtime·newstackcall(SB), BP
        MOVQ	BP, (g_sched+gobuf_pc)(AX)
        ```
        *   これも同様に、`runtime·newstackcall` のアドレスを`BP`レジスタにロードし、その`BP`レジスタの値を`gobuf_pc`フィールドに格納しています。

4.  **`masks<>` のアドレス参照**
    *   **変更前**: `PAND masks<>(SB)(CX*8), X1`
        *   `masks<>` というデータシンボルのアドレスを直接使用して、メモリから値をロードしています。
    *   **変更後**:
        ```asm
        MOVQ	$masks<>(SB), BP
        PAND	(BP)(CX*8), X1
        ```
        *   `masks<>` のアドレスを`BP`レジスタにロードし、その`BP`レジスタをベースとしてメモリ参照を行っています。

5.  **`shifts<>` のアドレス参照**
    *   **変更前**: `PSHUFB shifts<>(SB)(CX*8), X1`
        *   `shifts<>` というデータシンボルのアドレスを直接使用して、メモリから値をロードしています。
    *   **変更後**:
        ```asm
        MOVQ	$shifts<>(SB), BP
        PSHUFB	(BP)(CX*8), X1
        ```
        *   `shifts<>` のアドレスを`BP`レジスタにロードし、その`BP`レジスタをベースとしてメモリ参照を行っています。

これらの変更はすべて、グローバルシンボルへの参照を、直接の即値オペランドとしてではなく、一時レジスタを介して行うことで、GoのツールチェーンがRIP相対アドレッシングを適用しやすくするためのものです。これにより、生成されるGoバイナリは、より位置独立性が高く、ASLRなどの現代的なシステム環境により適したものとなります。

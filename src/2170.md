## 変更の背景

Go言語は設計当初から、シンプルさと明瞭さを重視してきました。インターフェースもその重要な要素の一つであり、その命名規則はコードの可読性と一貫性を高める上で非常に重要です。このコミットが行われた2009年5月は、Go言語がまだ初期段階にあり、言語仕様や慣用的なプログラミングスタイルが確立されつつある時期でした。

初期のチュートリアルでは、インターフェースの命名に関して、メソッド名とインターフェース名が重複する例 (`String` インターフェースが `String()` メソッドを持つ) が示されていました。しかし、Goの慣例として、単一のメソッドを持つインターフェースには、そのメソッド名に `-er` サフィックスを付けて命名することが推奨されています（例: `Read()` メソッドを持つインターフェースは `Reader`）。これは、インターフェースの目的をより明確にし、コードの意図を理解しやすくするためです。

また、`io` パッケージはGo言語におけるI/O操作の基盤であり、`io.Reader` や `io.Writer` といったインターフェースは非常に頻繁に使用されます。チュートリアルがこれらの重要なインターフェースを正確に参照し、その慣用的な使用法を示すことは、Goプログラマーが正しい知識を習得する上で不可欠でした。

このコミットは、チュートリアルの内容をGo言語の進化する慣例とベストプラクティスに合わせるための、初期段階における重要なドキュメント改善の一環と言えます。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語の概念に関する前提知識が必要です。

1.  **インターフェース (Interfaces)**:
    Go言語のインターフェースは、メソッドのシグネチャの集合を定義する型です。Goのインターフェースは「暗黙的」に実装されます。つまり、ある型がインターフェースで定義されたすべてのメソッドを実装していれば、その型はそのインターフェースを満たしていると見なされます。明示的な `implements` キーワードは不要です。これにより、疎結合な設計が可能になります。

2.  **型アサーション (Type Assertions)**:
    型アサーションは、インターフェース型の変数が、特定の具象型または別のインターフェース型を実装しているかどうかをテストし、もしそうであればその型に変換するために使用されます。構文は `value.(Type)` です。
    `value, ok := v.(Type)` の形式は「カンマOKイディオム」と呼ばれ、変換が成功したかどうかを示すブール値 `ok` を返します。これにより、安全に型変換を行うことができます。

3.  **`io` パッケージ**:
    `io` パッケージは、Go言語における基本的なI/Oプリミティブを提供します。最も重要なインターフェースは `io.Reader` と `io.Writer` です。
    *   `io.Reader` インターフェースは `Read(p []byte) (n int, err error)` メソッドを定義し、データソースからの読み込みを抽象化します。
    *   `io.Writer` インターフェースは `Write(p []byte) (n int, err error)` メソッドを定義し、データシンクへの書き込みを抽象化します。
    これらのインターフェースは、ファイル、ネットワーク接続、メモリバッファなど、様々なI/Oソース/シンクに対して統一されたインターフェースを提供し、Goの強力なコンポジション（合成）の原則を体現しています。

4.  **Go言語の命名規則 (Go Naming Conventions)**:
    Go言語には、コードの可読性と一貫性を高めるための特定の命名規則があります。インターフェースに関しては、単一のメソッドを持つインターフェースには、そのメソッド名に `-er` サフィックスを付けて命名することが推奨されています（例: `String()` メソッドを持つインターフェースは `Stringer`、`Read()` メソッドを持つインターフェースは `Reader`）。これは、そのインターフェースが「〜するもの」という動作を表すためです。

    変更前:
    ```
    type String interface {
    	String() string
    }

    ```
    この例では、インターフェース名 `String` とメソッド名 `String()` が重複しており、Goの慣用的な命名規則に反していました。

    	String() string
    }

2.  **`io` パッケージのインターフェース参照の修正**:
    変更前:
    ```
    Instead, it is a variable of type "io.Write", which is an
    interface type defined in the "io" library:

    	Write(p []byte) (n int, err *os.Error);

    変更後:
    ```

    interface type defined in the "io" library:

    type Writer interface {
    	Write(p []byte) (n int, err *os.Error);
    }

    (This interface is another conventional name, this time for "Write"; there are also
    "io.Reader", "io.ReadWriter", and so on.)
    ```
    この修正により、チュートリアルが `io.Writer` や `io.Reader` といった正しいインターフェース名を参照するようになりました。これは、Goの標準ライブラリの正確なAPIを反映させるための重要な変更です。また、`doubled name` という表現が `conventional name` に変更され、命名規則が単なる重複ではなく、慣例に基づいていることが強調されています。

これらの変更は、Go言語の初期段階において、言語の慣用的なスタイルと標準ライブラリの正確な使用法を公式ドキュメントに反映させるための、細かではあるが重要な改善点です。これにより、Goを学習する開発者が最初から正しいプラクティスを身につけることができるようになります。

## コアとなるコードの解説

上記の差分は、Go言語のチュートリアルドキュメントにおける以下の具体的な変更を示しています。

1.  **`String` から `Stringer` への変更**:
    *   `type String interface { String() string }` が `type Stringer interface { String() string }` に変更されました。これは、Goの慣例である「単一メソッドインターフェースには `-er` サフィックスを付ける」という命名規則に従ったものです。
    *   それに伴い、型アサーションの例 `v.(String)` も `v.(Stringer)` に修正されています。
    *   インターフェース名とメソッド名が重複することに関する以前の説明が削除され、代わりに「`Stringer` という名前は、このような単純なメソッドセットを記述するインターフェースに `[e]r` を追加するという慣例に従っている」という説明が追加されました。これにより、Goの命名規則の意図がより明確に伝わります。

2.  **`io.Write` から `io.Writer`、`io.Read` から `io.Reader` への変更**:
    *   `Fprintf` の引数に関する説明で、`io.Write` が `io.Writer` に修正されました。これは、Go標準ライブラリの `io` パッケージで定義されている正しいインターフェース名です。
    *   同様に、`io.Read` が `io.Reader` に、`io.ReadWrite` が `io.ReadWriter` に修正されました。
    *   これらのインターフェースが「別の重複した名前」であるという記述が削除され、「別の慣例的な名前」であるという記述に置き換えられました。これは、これらの命名が単なる重複ではなく、Goの設計哲学と慣例に基づいていることを強調しています。

これらの変更は、Go言語の初期段階において、言語の慣用的なスタイルと標準ライブラリの正確な使用法を公式ドキュメントに反映させるための、細かではあるが重要な改善点です。これにより、Goを学習する開発者が最初から正しいプラクティスを身につけることができるようになります。

## 変更の背景

Go言語は、その設計思想として静的リンクを強く推奨しており、ほとんどのGoプログラムは単一のバイナリとしてコンパイルされます。これにより、デプロイが容易になり、依存関係の問題が軽減されます。しかし、特定のシナリオでは動的リンクが必要となります。例えば、C言語で書かれたライブラリ（CGO）との連携、共有ライブラリの構築、あるいはプラグイン機構の実装などです。

このコミットが行われた2015年頃は、Go言語がARM64アーキテクチャへの対応を強化していた時期と重なります。ARM64は、モバイルデバイスやサーバー、組み込みシステムなど、幅広い分野で採用が進んでおり、Goプログラムがこれらの環境で動的リンクを必要とするケースが増えていました。

`addmoduledata`関数は、動的にロードされたGoモジュールのメタデータをGoランタイムに登録するために不可欠な機能です。このメタデータには、型情報、シンボルテーブル、ガベージコレクションに必要な情報などが含まれており、ランタイムが新しくロードされたコードを正しく理解し、管理するために必要です。

このコミットの背景には、ARM64環境でGoの動的リンク機能（特に`-linkshared`ビルドモードやプラグイン）を完全にサポートするための基盤を整備するという目的があります。これにより、ARM64上でのGoアプリケーションの柔軟性と相互運用性が向上します。

## 前提知識の解説

### 1. Go言語のモジュールとランタイム

Go言語のプログラムは、コンパイル時にすべての依存関係を解決し、通常は単一の実行可能ファイルを生成します。しかし、Go 1.8以降で導入されたプラグイン機能や、`-linkshared`オプションを使用した共有ライブラリのビルドでは、実行時に追加のGoコードをロードする動的リンクの仕組みが利用されます。

Goランタイムは、実行中のGoプログラムのメモリ管理（ガベージコレクション）、ゴルーチンのスケジューリング、型情報の管理など、多岐にわたる役割を担っています。動的にロードされたモジュールも、これらのランタイムの管理下に置かれる必要があります。そのため、ロードされたモジュールのメタデータ（`moduledata`構造体）をランタイムに登録する仕組みが必要です。

### 2. `moduledata`構造体

`moduledata`は、Goの実行可能ファイルまたは共有ライブラリに含まれるGoコードに関するメタデータを記述するランタイム内部の構造体です。これには、以下のような情報が含まれます。

*   **テキストセグメントとデータセグメントのアドレス範囲**: コードとデータのメモリ上の位置。
*   **シンボルテーブル**: 関数や変数の名前とアドレスのマッピング。
*   **型情報**: Goの型システムに関する情報。
*   **ガベージコレクション関連情報**: GCがヒープ上のオブジェクトを正確にスキャンするために必要な情報。
*   **初期化関数**: モジュールがロードされたときに実行されるべき初期化コードへのポインタ。

`runtime.addmoduledata`は、この`moduledata`構造体へのポインタを受け取り、ランタイムの内部リストにそれを追加します。

### 3. 動的リンクと`.init_array`

動的リンクは、プログラムの実行時に外部ライブラリをロードし、リンクするプロセスです。LinuxなどのUnix系システムでは、ELF（Executable and Linkable Format）形式の実行可能ファイルや共有ライブラリが使用されます。

ELFファイルには、`.init_array`というセクションが存在します。このセクションには、プログラムや共有ライブラリがロードされた直後に実行されるべき関数のポインタのリストが含まれています。動的リンカは、共有ライブラリをロードした後、この`.init_array`内の関数を呼び出すことで、ライブラリの初期化処理を実行します。

Goの動的リンクでは、`runtime.addmoduledata`関数がこの`.init_array`を通じて呼び出されることで、動的にロードされたGoモジュールの初期化とランタイムへの登録が行われます。

### 4. ARM64アーキテクチャとアセンブリ

ARM64（AArch64）は、64ビットのARM命令セットアーキテクチャです。レジスタベースのRISC（Reduced Instruction Set Computer）アーキテクチャであり、汎用レジスタ（X0-X30）、スタックポインタ（SP）、プログラムカウンタ（PC）などがあります。

*   **`adrp` (Address Page Relative):** 4KBページ単位でベースアドレスを計算し、汎用レジスタにロードします。これは、64ビットアドレス空間で大きなオフセットを持つアドレスを効率的に計算するために使用されます。
*   **`add` (Add):** レジスタの値に即値または別のレジスタの値を加算します。`adrp`と組み合わせて、ページ内の正確なオフセットを計算し、完全な64ビットアドレスを構築するためによく使われます。
*   **`bl` (Branch with Link):** 関数呼び出しに使用されます。呼び出し元のアドレス（リターンアドレス）をリンクレジスタ（X30）に保存し、指定されたアドレスにジャンプします。
*   **レジスタ規約 (ABI):** ARM64には、関数呼び出しにおけるレジスタの使用方法を定義するABI（Application Binary Interface）があります。例えば、引数は通常X0-X7レジスタで渡され、戻り値はX0レジスタで返されます。また、一部のレジスタは呼び出し元が保存する必要がある（caller-saved）、一部は呼び出し先が保存する必要がある（callee-saved）と定められています。コミット内の`R27`レジスタの保存/復元は、このABIに従ったものです。

### 5. Goリンカ（`cmd/link`）

Goリンカは、Goのソースコードから生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能ファイルや共有ライブラリを生成するツールです。リンカは、シンボル解決、再配置（リロケーション）、コード生成などの重要なタスクを実行します。

このコミットでは、リンカがARM64向けに`runtime.addmoduledata`を呼び出すための初期化コード（`.init_array`エントリ）を生成する部分が変更されています。

## 技術的詳細

このコミットは、Goの動的リンクメカニズムをARM64アーキテクチャで機能させるための重要なピースを追加します。主な変更点は以下の2つのファイルにあります。

1.  **`src/cmd/link/internal/arm64/asm.go`**: Goリンカの一部であり、ARM64アーキテクチャ固有のアセンブリコードを生成する役割を担います。
2.  **`src/runtime/asm_arm64.s`**: Goランタイムの一部であり、ARM64アーキテクチャ固有のアセンブリコードが含まれています。

### `src/cmd/link/internal/arm64/asm.go` の変更

このファイルでは、`gentext`関数が変更されています。`gentext`は、Goプログラムのテキストセグメント（コード）を生成する際に呼び出されるリンカの内部関数です。

変更の核心は、動的リンクが有効な場合に、`runtime.addmoduledata`を呼び出すための初期化関数（`go.link.addmoduledata`）を生成するロジックが追加されたことです。

*   **`ld.DynlinkingGo()`**: 動的リンクが有効かどうかをチェックします。有効でない場合は、この初期化コードは不要なので処理をスキップします。
*   **`runtime.addmoduledata`の検索**: `ld.Linklookup`を使って`runtime.addmoduledata`シンボルを検索します。もしこのシンボルが既に`obj.STEXT`（テキストセグメントのシンボル）として存在する場合、それはランタイム自体がリンクされていることを意味し、別途初期化関数を生成する必要がないため、処理をスキップします。
*   **`go.link.addmoduledata`の生成**:
    *   `initfunc := ld.Linklookup(ld.Ctxt, "go.link.addmoduledata", 0)`: 新しい初期化関数`go.link.addmoduledata`を定義します。この関数は`obj.STEXT`タイプで、ローカルかつ到達可能（`Local = true`, `Reachable = true`）としてマークされます。
    *   **アセンブリ命令の生成**: `o(op uint32)`ヘルパー関数を使って、ARM64のアセンブリ命令のバイトコードを`initfunc`に追加します。
        *   `adrp x0, 0 <runtime.firstmoduledata>`: `runtime.firstmoduledata`のアドレスを含む4KBページのベースアドレスを`x0`レジスタにロードします。`R_AARCH64_ADR_PREL_PG_HI21`という再配置タイプが関連付けられます。これは、リンカが最終的なアドレスを解決する際に使用します。
        *   `add x0, x0, #0x0`: `adrp`で計算されたベースアドレスにオフセットを加算し、`x0`に`moduledata`構造体のアドレスを格納します。`R_AARCH64_ADD_ABS_LO12_NC`という再配置タイプが関連付けられます。
        *   `bl 0 <runtime.addmoduledata>`: `runtime.addmoduledata`関数を呼び出します。`R_AARCH64_CALL26`という再配置タイプが関連付けられます。これは、リンカが呼び出し先の最終的なアドレスに基づいて`bl`命令のオフセットを調整するために使用されます。
    *   **再配置エントリの追加**: `ld.Addrel`を使って、上記のアセンブリ命令に対応する再配置エントリを`initfunc`に追加します。これにより、リンカは最終的な実行可能ファイルを生成する際に、これらの命令内のアドレスを正しく解決できます。
        *   `rel.Sym = ld.Ctxt.Moduledata`: `moduledata`構造体への参照。
        *   `rel.Type = obj.R_ADDRARM64`: `moduledata`のアドレスを解決するための再配置タイプ。
        *   `rel.Sym = ld.Linklookup(ld.Ctxt, "runtime.addmoduledata", 0)`: `runtime.addmoduledata`関数への参照。
        *   `rel.Type = obj.R_CALLARM64`: 関数呼び出しを解決するための再配置タイプ。コメントで`R_AARCH64_JUMP26`がより適切かもしれないが、`R_CALLARM64`でも動作すると述べられています。
*   **テキストセグメントリストへの追加**: 生成された`initfunc`をリンカのテキストセグメントリストに追加し、実行可能ファイルに含められるようにします。
*   **`.init_array`エントリの生成**:
    *   `initarray_entry := ld.Linklookup(ld.Ctxt, "go.link.addmoduledatainit", 0)`: `.init_array`セクションに配置されるエントリを定義します。
    *   `initarray_entry.Type = obj.SINITARR`: このシンボルが`.init_array`セクションに属することを示します。
    *   `ld.Addaddr(ld.Ctxt, initarray_entry, initfunc)`: `initarray_entry`が`initfunc`のアドレスを指すように設定します。これにより、動的リンカがプログラムをロードする際に、`initfunc`が自動的に呼び出されるようになります。

### `src/runtime/asm_arm64.s` の変更

このファイルでは、`runtime.addmoduledata`という新しいアセンブリ関数が追加されています。この関数は、`.init_array`を通じて動的リンカによって呼び出されることを想定しており、GoのABIではなくプラットフォームのABIに従います。

*   **`TEXT runtime·addmoduledata(SB),NOSPLIT,$0-0`**: `runtime.addmoduledata`という名前の関数を定義します。`NOSPLIT`はスタックフレームの分割を行わないことを示し、`$0-0`はスタックフレームサイズが0であることを示します（ただし、関数内でスタックを操作します）。
*   **`SUB $0x10, RSP`**: スタックポインタ（RSP）を16バイト減らし、スタック上にスペースを確保します。これは、`R27`レジスタを保存するためです。
*   **`MOVD R27, 8(RSP)`**: `R27`レジスタの値をスタックの`8(RSP)`（スタックポインタから8バイトオフセット）に保存します。`R27`はARM64のABIでcallee-savedレジスタ（呼び出し先が保存・復元する責任があるレジスタ）であるため、この操作が必要です。Goのランタイムコードがグローバル変数にアクセスする際に`R27`を使用する可能性があるため、その値を保護します。
*   **`MOVD runtime·lastmoduledatap(SB), R1`**: `runtime.lastmoduledatap`（最後に登録された`moduledata`へのポインタ）の値を`R1`レジスタにロードします。
*   **`MOVD R0, moduledata_next(R1)`**: `R0`レジスタに渡された新しい`moduledata`のアドレスを、`R1`が指す`moduledata`構造体の`next`フィールドに格納します。これにより、`moduledata`のリンクリストが構築されます。`R0`はARM64のABIで第一引数を渡すレジスタです。
*   **`MOVD R0, runtime·lastmoduledatap(SB)`**: `runtime.lastmoduledatap`を更新し、新しく追加された`moduledata`を指すようにします。
*   **`MOVD 8(RSP), R27`**: スタックに保存しておいた`R27`レジスタの値を復元します。
*   **`ADD $0x10, RSP`**: スタックポインタを16バイト増やし、スタックフレームを解放します。
*   **`RET`**: 関数からリターンします。

このアセンブリコードは、動的にロードされた`moduledata`をランタイムの内部リンクリストに安全に追加する役割を果たします。

## コアとなるコードの解説

### `src/cmd/link/internal/arm64/asm.go` の `gentext` 関数

この変更は、GoリンカがARM64バイナリを生成する際に、動的リンクされたGoモジュールの初期化を適切に行うためのコードを挿入するものです。

1.  **動的リンクのチェック**: `if !ld.DynlinkingGo() { return }` により、動的リンクが有効なビルドの場合のみ処理が実行されます。
2.  **`runtime.addmoduledata`の存在チェック**: `addmoduledata := ld.Linklookup(ld.Ctxt, "runtime.addmoduledata", 0)` で`runtime.addmoduledata`シンボルを検索します。もし、このシンボルが既にテキストセグメント（`obj.STEXT`）として存在する場合、それはランタイム自体がリンクされていることを意味し、この初期化コードは不要なのでスキップされます。これは、ランタイムが既に自身の`moduledata`を登録しているためです。
3.  **初期化関数の生成 (`go.link.addmoduledata`)**:
    *   リンカは、`go.link.addmoduledata`という名前の新しい関数を生成します。この関数は、動的リンカによって`.init_array`から呼び出されることを目的としています。
    *   この関数は、以下のARM64アセンブリ命令を生成します。
        *   `adrp x0, 0 <runtime.firstmoduledata>` と `add x0, x0, #0x0`: これら2つの命令は、`moduledata`構造体のアドレスを`x0`レジスタにロードするために使用されます。`adrp`はページベースアドレスを、`add`はページ内のオフセットを加算して正確なアドレスを計算します。`runtime.firstmoduledata`は、Goプログラムの最初の`moduledata`へのポインタであり、動的にロードされるモジュールもこのリストに追加されます。
        *   `bl 0 <runtime.addmoduledata>`: `runtime.addmoduledata`関数を呼び出します。`x0`レジスタには、ロードされたモジュールの`moduledata`構造体へのポインタが引数として渡されます。
    *   これらのアセンブリ命令には、それぞれ対応する再配置エントリ（`R_AARCH64_ADR_PREL_PG_HI21`, `R_AARCH64_ADD_ABS_LO12_NC`, `R_AARCH64_CALL26`または`R_CALLARM64`）が追加されます。これにより、リンカは最終的な実行可能ファイルを生成する際に、これらの命令内のシンボルアドレスを正しく解決できます。
4.  **`.init_array`への登録**:
    *   `initarray_entry := ld.Linklookup(ld.Ctxt, "go.link.addmoduledatainit", 0)` で`.init_array`エントリを定義します。
    *   `ld.Addaddr(ld.Ctxt, initarray_entry, initfunc)` により、この`.init_array`エントリが、先ほど生成した`go.link.addmoduledata`関数のアドレスを指すように設定されます。
    *   これにより、プログラムがロードされると、動的リンカが`.init_array`セクションを処理し、`go.link.addmoduledata`が自動的に実行され、その結果`runtime.addmoduledata`が呼び出されてモジュールのメタデータがランタイムに登録されるという流れが確立されます。

### `src/runtime/asm_arm64.s` の `runtime·addmoduledata` 関数

このアセンブリ関数は、動的にロードされたGoモジュールの`moduledata`をGoランタイムの内部リストに登録する役割を担います。

1.  **スタックフレームの準備**:
    *   `SUB $0x10, RSP`: スタックポインタを16バイト減らし、スタック上にスペースを確保します。
    *   `MOVD R27, 8(RSP)`: `R27`レジスタの値をスタックに保存します。これは、ARM64のABIにおいて`R27`がcallee-savedレジスタであるためです。Goランタイムのグローバル変数へのアクセスで`R27`が使用される可能性があるため、その値を保護する必要があります。
2.  **`moduledata`のリンクリストへの追加**:
    *   `MOVD runtime·lastmoduledatap(SB), R1`: `runtime.lastmoduledatap`は、ランタイムが認識している最後の`moduledata`構造体へのポインタを保持するグローバル変数です。そのアドレスを`R1`レジスタにロードします。
    *   `MOVD R0, moduledata_next(R1)`: `R0`レジスタには、呼び出し元（リンカが生成した`go.link.addmoduledata`関数）から渡された新しい`moduledata`構造体のアドレスが含まれています。このアドレスを、`R1`が指す既存の`moduledata`構造体の`next`フィールドに格納します。これにより、新しい`moduledata`が既存のリストの末尾に追加されます。
    *   `MOVD R0, runtime·lastmoduledatap(SB)`: `runtime.lastmoduledatap`を更新し、新しく追加された`moduledata`を指すようにします。これで、新しい`moduledata`がランタイムの認識するリストの最新エントリとなります。
3.  **スタックフレームのクリーンアップとリターン**:
    *   `MOVD 8(RSP), R27`: スタックに保存しておいた`R27`レジスタの値を復元します。
    *   `ADD $0x10, RSP`: スタックポインタを元の位置に戻し、スタックフレームを解放します。
    *   `RET`: 関数からリターンします。

このアセンブリ関数は、Goランタイムが動的にロードされたモジュールのメタデータを追跡し、ガベージコレクションやリフレクションなどのランタイム機能がそれらのモジュールに対して正しく動作するようにするために不可欠です。

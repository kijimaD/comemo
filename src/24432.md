## 元コミット内容

このコミットは、GoコンパイラのSSAバックエンドにおいて、`OINDREG`という中間表現ノードが式 (expression) のコンテキストで処理されるように実装を追加するものです。`OINDREG`は、レジスタを介した間接参照を表すノードであり、特にスタックポインタ (`REGSP`) を基準としたローカル変数や引数へのアクセスによく使用されます。以前は、このノードが式として評価される際に適切にSSA形式に変換されていませんでした。この変更により、`OINDREG`が式として現れた場合でも、対応するSSAのロード命令 (`ssa.OpLoad`) が生成されるようになります。

## 変更の背景

Goコンパイラは、ソースコードを抽象構文木 (AST) にパースした後、中間表現 (IR) に変換し、最終的に機械語を生成します。この過程で、最適化のためにSSA (Static Single Assignment) 形式が導入されています。SSA形式では、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。

`OINDREG`は、コンパイラのフロントエンドが生成するASTノードの一種で、特定のレジスタからのオフセットによる間接メモリアクセスを表します。例えば、スタック上のローカル変数や関数引数にアクセスする場合、スタックポインタ (`REGSP`) を基準としたオフセットで参照されます。

GoコンパイラのSSAバックエンドでは、ASTノードをSSA形式の`ssa.Value`に変換する`state.expr`メソッドと`state.addr`メソッドがあります。
*   `state.expr`は、ノードが値として評価される場合（例: `x = a[i]` の `a[i]`）に呼び出されます。
*   `state.addr`は、ノードがアドレスとして評価される場合（例: `&a[i]` の `a[i]`）に呼び出されます。

このコミット以前は、`OINDREG`ノードが`state.expr`コンテキストで出現した場合の処理が欠落していました。これは、`OINDREG`が主にアドレス計算 (`state.addr`) や、特定の最適化パスで内部的に使用されることが多かったためと考えられます。しかし、コンパイラの進化や新たな最適化の導入により、`OINDREG`が直接式として評価されるケースが発生するようになり、そのためのSSA変換ロジックが必要となりました。

この変更は、GoコンパイラのSSAバックエンドの堅牢性を高め、より広範なASTノードをSSA形式に正確に変換できるようにすることを目的としています。これにより、コンパイラが生成するコードの正確性と最適化の機会が向上します。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)
Go言語の公式コンパイラであり、Goソースコードを機械語に変換します。`cmd/compile`は、フロントエンド（パース、型チェック）、中間表現生成、最適化、バックエンド（コード生成）の複数のステージで構成されます。

### SSA (Static Single Assignment) 形式
プログラムの最適化に広く用いられる中間表現形式の一つです。SSA形式では、各変数がプログラム内で一度だけ代入されるという特性を持ちます。これにより、データフロー解析が単純化され、デッドコード削除、共通部分式除去、レジスタ割り当てなどの最適化が容易になります。Goコンパイラは、バージョン1.7以降、主要な最適化パスにSSA形式を採用しています。

### 中間表現 (Intermediate Representation - IR)
ソースコードと最終的な機械語の中間に位置する表現形式です。コンパイラは、ソースコードをIRに変換し、IRに対して様々な最適化を適用してから機械語を生成します。SSA形式はそのIRの一種です。

### `gc` パッケージ
`src/cmd/compile/internal/gc` パッケージは、Goコンパイラの主要なロジック（フロントエンドの一部、型チェック、ASTからSSAへの変換など）を含んでいます。歴史的にGoコンパイラは`gc` (Go Compiler) と呼ばれていました。

### `ssa.go` ファイルの役割
`src/cmd/compile/internal/gc/ssa.go` ファイルは、ASTノードをSSA形式の`ssa.Value`に変換するロジックを主に担当しています。このファイルには、`state`構造体とそのメソッド（`expr`, `addr`など）が定義されており、ASTを走査しながらSSAグラフを構築します。

### `Node` (ASTノード) と `ssa.Value`
*   **`Node`**: Goコンパイラのフロントエンドが生成する抽象構文木 (AST) の各要素を表すデータ構造です。例えば、変数参照、定数、演算子、関数呼び出しなどが`Node`として表現されます。
*   **`ssa.Value`**: SSA形式における値の単位です。各`ssa.Value`は、特定の演算の結果として生成され、一度だけ代入されます。SSAバックエンドは、`Node`を`ssa.Value`に変換することで、プログラムをSSA形式で表現します。

### `OINDREG` (間接レジスタ参照)
`OINDREG`は、GoコンパイラのASTノードの種類の一つで、「レジスタを基点としたオフセットによる間接メモリアクセス」を表します。例えば、`*(REG + offset)` のようなメモリアクセスです。
*   `n.Reg`: 基準となるレジスタ。
*   `n.Xoffset`: レジスタからのオフセット値。
*   `n.Type`: アクセスされるメモリ領域の型。

### `REGSP` (スタックポインタレジスタ)
`REGSP`は、スタックポインタレジスタを表す定数です。多くのアーキテクチャでは、スタックポインタは現在のスタックフレームの最上位（または最下位）を指し、ローカル変数や関数引数はこのスタックポインタからのオフセットでアクセスされます。`OINDREG`が`REGSP`を基準とする場合、それはスタック上のデータへのアクセスを意味します。

### `expr` と `addr` メソッドの役割
`state`構造体のメソッドである`expr`と`addr`は、ASTノードをSSA形式に変換する際のコンテキストを区別します。
*   **`func (s *state) expr(n *Node) *ssa.Value`**: ASTノード`n`が「値」として評価される場合に呼び出されます。例えば、`x = y + z` の `y` や `z` は値として評価されます。このメソッドは、最終的にその値に対応する`ssa.Value`を返します。
*   **`func (s *state) addr(n *Node) *ssa.Value`**: ASTノード`n`が「アドレス」として評価される場合に呼び出されます。例えば、`&x` の `x` や、`p = &a[i]` の `a[i]` はアドレスとして評価されます。このメソッドは、そのアドレスに対応する`ssa.Value`（ポインタ型）を返します。

### `ssa.OpLoad`, `ssa.OpOffPtr`
これらはSSA形式の操作 (Opcode) です。
*   **`ssa.OpLoad`**: メモリから値をロードする操作を表します。`newValue2(ssa.OpLoad, type, addressValue, memoryValue)` のように使用され、`addressValue`が指すアドレスから`type`型の値をロードします。`memoryValue`はメモリの状態を表すSSA値で、メモリ依存性を追跡するために使用されます。
*   **`ssa.OpOffPtr`**: ポインタにオフセットを加算する操作を表します。`entryNewValue1I(ssa.OpOffPtr, type, offset, basePointerValue)` のように使用され、`basePointerValue`に`offset`を加算した新しいポインタ値（`type`型）を生成します。

## 技術的詳細

このコミットの核心は、`state.expr`メソッドに`OINDREG`ケースを追加し、`OINDREG`がスタックポインタ (`REGSP`) を介した間接参照である場合に、それをSSA形式のロード操作に変換することです。

以前の`ssa.go`では、`OINDREG`は`state.addr`メソッドで処理されていましたが、`state.expr`では明示的に処理されていませんでした。`state.addr`では、`OINDREG`は単にスタックポインタからのオフセットアドレスを計算する`ssa.OpOffPtr`に変換されていました。これは、`OINDREG`がアドレスとして使われる場合に適切です。

しかし、`OINDREG`が直接値として使われる場合（例: `x = *(&stack_var)` のような状況で、`*(&stack_var)` が`OINDREG`に変換される場合）、`state.expr`がこのノードを処理する必要があります。このコミットは、このギャップを埋めます。

新しいロジックでは、`state.expr`内で`OINDREG`ノードに遭遇した場合、以下のステップでSSA値を生成します。

1.  **レジスタのチェック**: `n.Reg`が`Thearch.REGSP`（スタックポインタ）であるかを確認します。もし`REGSP`以外であれば、現在の実装ではサポートされていないため、`Unimplementedf`を呼び出してエラーを報告します。これは、`OINDREG`が主にスタック上のデータアクセスに使用されるという前提に基づいています。
2.  **アドレスの計算**: `ssa.OpOffPtr`操作を使用して、スタックポインタ (`s.sp`) から`n.Xoffset`だけオフセットされたアドレスを計算します。このアドレスは、`n.Type`が指す型へのポインタ型 (`Ptrto(n.Type)`) として表現されます。このステップで生成されるSSA値が、メモリ上のデータのアドレスを表します。
3.  **値のロード**: 計算されたアドレスから実際の値をロードするために、`ssa.OpLoad`操作を使用します。`newValue2(ssa.OpLoad, n.Type, addr, s.mem())` は、`addr`が指すメモリ位置から`n.Type`型の値をロードし、その結果を新しい`ssa.Value`として返します。`s.mem()`は、現在のメモリの状態を表すSSA値であり、メモリ操作の順序を正しく追跡するために必要です。

この変更により、Goコンパイラは、スタック上のローカル変数や引数への間接参照を、SSA形式のロード命令として正確に表現できるようになり、その後の最適化パスでこれらの値が適切に扱われるようになります。

また、`state.addr`メソッド内の`OINDREG`ケースのコメントが更新され、「TODO: always SP?」という疑問符が削除されました。これは、`OINDREG`が`REGSP`以外の場合の処理が`state.expr`と同様に`Unimplementedf`で扱われるようになったため、`REGSP`に限定されるという理解がより明確になったことを示唆しています。

## コアとなるコードの解説

### `state.expr` メソッドへの `OINDREG` ケースの追加

```go
 	case OINDREG:
 		if int(n.Reg) != Thearch.REGSP {
 			s.Unimplementedf("OINDREG of non-SP register %s in expr: %v", obj.Rconv(int(n.Reg)), n)
 			return nil
 		}
 		addr := s.entryNewValue1I(ssa.OpOffPtr, Ptrto(n.Type), n.Xoffset, s.sp)
 		return s.newValue2(ssa.OpLoad, n.Type, addr, s.mem())
```
このコードブロックは、`state.expr`メソッド内の`switch n.Op`文に追加されました。
1.  **`case OINDREG:`**: ASTノードの操作が`OINDREG`である場合にこのブロックが実行されます。
2.  **`if int(n.Reg) != Thearch.REGSP { ... }`**: `OINDREG`ノードが参照するレジスタ (`n.Reg`) がスタックポインタ (`Thearch.REGSP`) ではない場合をチェックします。現時点では、スタックポインタ以外のレジスタを介した間接参照はSSAバックエンドでサポートされていないため、`s.Unimplementedf`を呼び出してコンパイルエラーを発生させます。これは、将来的に他のレジスタからの間接参照もサポートされる可能性を残しつつ、現在の実装の制約を明確にしています。
3.  **`addr := s.entryNewValue1I(ssa.OpOffPtr, Ptrto(n.Type), n.Xoffset, s.sp)`**:
    *   `s.entryNewValue1I`は、新しいSSA値を作成するためのヘルパー関数です。
    *   `ssa.OpOffPtr`は、ポインタにオフセットを加算するSSA操作です。
    *   `Ptrto(n.Type)`は、`n.Type`が指す型へのポインタ型を生成します。これは、メモリ上のデータのアドレスを表すSSA値の型となります。
    *   `n.Xoffset`は、レジスタからのオフセット値です。
    *   `s.sp`は、現在のスタックポインタを表すSSA値です。
    *   この行は、`s.sp`に`n.Xoffset`を加算して、目的のメモリ位置のアドレスを表すSSA値 (`addr`) を生成します。
4.  **`return s.newValue2(ssa.OpLoad, n.Type, addr, s.mem())`**:
    *   `s.newValue2`は、2つの引数を持つSSA値を作成するためのヘルパー関数です。
    *   `ssa.OpLoad`は、メモリから値をロードするSSA操作です。
    *   `n.Type`は、ロードされる値の型です。
    *   `addr`は、値をロードするメモリ位置のアドレスを表すSSA値です。
    *   `s.mem()`は、現在のメモリの状態を表すSSA値です。SSA形式では、メモリ操作は特別なメモリSSA値を通じて依存関係が追跡されます。
    *   この行は、`addr`が指すメモリ位置から`n.Type`型の値をロードするSSA値を作成し、それを`state.expr`の結果として返します。

### `state.addr` メソッド内の `OINDREG` ケースの変更

```go
 	case OINDREG:
-		// indirect off a register (TODO: always SP?)
+		// indirect off a register
 		// used for storing/loading arguments/returns to/from callees
+		if int(n.Reg) != Thearch.REGSP {
+			s.Unimplementedf("OINDREG of non-SP register %s in addr: %v", obj.Rconv(int(n.Reg)), n)
+			return nil
+		}
 		return s.entryNewValue1I(ssa.OpOffPtr, Ptrto(n.Type), n.Xoffset, s.sp)
```
このコードブロックは、`state.addr`メソッド内の`OINDREG`ケースに対する変更です。
1.  **コメントの更新**: `// indirect off a register (TODO: always SP?)` というコメントが `// indirect off a register` に変更されました。これは、`OINDREG`が`REGSP`以外の場合の処理が明確になったため、「常にSPなのか？」という疑問が解消されたことを示しています。
2.  **レジスタのチェックの追加**: `state.expr`と同様に、`n.Reg`が`Thearch.REGSP`であるかどうかのチェックが追加されました。これにより、`state.addr`コンテキストでも、スタックポインタ以外のレジスタを介した間接参照は未実装として扱われるようになり、一貫性が保たれます。このチェックは、`OINDREG`がスタック上のデータアクセスに特化しているという現在のコンパイラの設計を反映しています。
3.  **既存ロジックの維持**: `return s.entryNewValue1I(ssa.OpOffPtr, Ptrto(n.Type), n.Xoffset, s.sp)` の行は変更されていません。これは、`state.addr`がアドレスを生成する役割を担っており、`OINDREG`がアドレスとして評価される場合は、引き続きスタックポインタからのオフセットアドレスを計算する`ssa.OpOffPtr`を生成することが正しい動作であるためです。

これらの変更により、GoコンパイラのSSAバックエンドは、`OINDREG`ノードを式としてもアドレスとしても正しく処理できるようになり、コンパイラの堅牢性と正確性が向上しました。

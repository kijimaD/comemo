# [インデックス 25746] ファイルの概要

このコミットは、GoプログラムがLinux/386アーキテクチャで動的リンクされる際に、ランタイムがモジュールデータを正しく登録するように修正するものです。具体的には、リンカーが生成する初期化処理において、`runtime.addmoduledata` 関数を呼び出すように変更し、ロードされたモジュールのメタデータがGoランタイムのモジュールデータリストに適切に追加されるようにします。

## 変更の背景

Goプログラムが動的リンクされる際、特にLinux/386のような32ビットアーキテクチャでは、ロードされた共有ライブラリ（モジュール）のメタデータ（`moduledata`）をGoランタイムに登録する必要があります。この登録プロセスは、ガベージコレクション、スタックトレース、リフレクションなど、Goランタイムの多くの機能が正しく動作するために不可欠です。

このコミット以前は、Linux/386環境で動的リンクされたGoモジュールが、その`moduledata`をGoランタイムのグローバルなリストに適切に追加していなかった可能性があります。これにより、ランタイムがモジュールの情報を認識できず、予期せぬ動作やクラッシュを引き起こす可能性がありました。

この変更は、Goの動的リンク機能の堅牢性を向上させ、特に32ビット環境での互換性と安定性を確保することを目的としています。`moduledata`の登録は、Goのプラグインシステムや、Goで書かれた共有ライブラリを他の言語から利用するシナリオにおいて特に重要となります。

## 前提知識の解説

### Goのモジュールデータ (`moduledata`)

Goランタイムは、ロードされた各Goモジュール（実行可能ファイル、共有ライブラリ、プラグインなど）に関するメタデータを`moduledata`構造体で管理しています。この構造体には、そのモジュール内の型情報、関数情報、グローバル変数、スタックマップ、ガベージコレクション関連データなど、ランタイムがコードを正しく解釈・操作するために必要なあらゆる情報が含まれています。

`moduledata`オブジェクトは、Goランタイムが起動時またはモジュールロード時に発見し、内部のリンクリストに登録することで、ランタイム全体からアクセス可能になります。これにより、例えば、あるポインタがどのモジュールに属し、どの型であるかを特定したり、ガベージコレクタが正確にメモリをスキャンしたりすることが可能になります。

### 動的リンク (Dynamic Linking)

動的リンクは、プログラムの実行時に共有ライブラリ（`.so`ファイルなど）をロードし、リンクする方式です。静的リンクとは異なり、実行ファイル自体にはライブラリのコードは含まれず、実行時にOSのローダーがライブラリをメモリにマッピングし、プログラムと結合します。これにより、ディスクスペースの節約、メモリ使用量の削減（複数のプログラムで同じライブラリを共有できるため）、ライブラリの更新が容易になるなどの利点があります。

Goでは、`go build -buildmode=shared` や `go build -buildmode=plugin` などのビルドモードで動的リンクされたバイナリを生成できます。

### Linux/386アーキテクチャとPIC (Position-Independent Code)

Linux/386は、Intel 80386プロセッサをベースとした32ビットのx86アーキテクチャを指します。32ビット環境では、アドレス空間が4GBに制限され、レジスタの数も限られています。

動的リンクされた共有ライブラリは、メモリ上のどこにロードされるか実行時まで分からないため、位置独立コード (Position-Independent Code, PIC) である必要があります。PICは、絶対アドレスではなく、相対アドレスやレジスタを基準としたアドレス指定を使用することで、どこにロードされても正しく実行できるように設計されたコードです。

PICを実装する際、特に32ビットx86では、現在のプログラムカウンタ (PC) の値を取得する特殊な手法がよく用いられます。これは、`call`命令を利用してリターンアドレスをスタックにプッシュさせ、その値を読み取ることで実現されます。`__x86.get_pc_thunk.cx` のようなシンボルは、このPC取得のためのヘルパー関数として機能します。

### ELFバイナリの`.init_array`セクション

ELF (Executable and Linkable Format) は、LinuxなどのUnix系システムで実行可能ファイル、共有ライブラリ、オブジェクトファイルなどに用いられる標準的なファイルフォーマットです。

ELFバイナリには、`.init_array`というセクションが存在します。このセクションには、プログラムの`main`関数が実行される前に、OSのローダーによって呼び出されるべき初期化関数のポインタのリストが格納されています。共有ライブラリがロードされる際、そのライブラリの`.init_array`に登録された関数が自動的に実行され、ライブラリ固有の初期化処理を行うことができます。Goの動的リンクされたモジュールも、このメカニズムを利用してランタイムに自身を登録します。

### リロケーションタイプ (`R_CALL`, `R_PCREL`)

リロケーションとは、リンカーがプログラム内のアドレス参照を解決するプロセスです。コンパイル時にはアドレスが確定できないシンボル（他のモジュールにある関数や変数など）に対して、プレースホルダーが埋め込まれ、リンカーが最終的なアドレスを計算して埋め込みます。

*   **`R_CALL`**: 関数呼び出し (`call`命令) のターゲットアドレスを解決するためのリロケーションタイプです。32ビットx86では、`call`命令は通常、相対アドレス（現在のPCからのオフセット）を使用するため、リンカーはこのオフセットを計算して埋め込みます。
*   **`R_PCREL`**: プログラムカウンタ (PC) 相対アドレスを解決するためのリロケーションタイプです。これは、現在のPCからのオフセットとしてアドレスを指定する際に使用されます。PICでグローバル変数やGOTへのアクセスによく用いられます。

## 技術的詳細

このコミットは、Goリンカー (`cmd/link`) とGoランタイム (`src/runtime`) の両方に変更を加えています。

### `src/cmd/link/internal/x86/asm.go` の変更

このファイルは、Goリンカーのx86アーキテクチャ固有のアセンブリコード生成ロジックを含んでいます。

1.  **`addcall` ヘルパー関数の追加**:
    *   `addcall`関数は、指定されたシンボル `s` に4バイトを追加し、その位置に`R_CALL`タイプのリロケーションを作成します。このリロケーションは、ターゲットシンボル `t` への呼び出しを解決するために使用されます。これは、リンカーがアセンブリコードを生成する際に、関数呼び出しのプレースホルダーを挿入し、後で正しいアドレスに解決するための汎用的なメカニズムを提供します。

2.  **`gentext` 関数内のロジック変更**:
    *   `gentext`関数は、Goプログラムのエントリポイントや初期化コードを生成する役割を担っています。
    *   `addmoduledata := ld.Linklookup(ld.Ctxt, "runtime.addmoduledata", 0)`: `runtime.addmoduledata`シンボルをルックアップします。これは、Goランタイムが提供する、モジュールデータを登録するための関数です。
    *   `if addmoduledata.Type == obj.STEXT { return }`: もし現在リンクしているモジュール自体がGoランタイムを含んでいる場合（つまり、`runtime.addmoduledata`がこのモジュール内で定義されている場合）、別途初期化関数を生成する必要はないため、処理をスキップします。これは、ランタイム自体が自身のモジュールデータを登録する方法を持っているためです。
    *   **`go.link.addmoduledata` 初期化関数の生成**:
        *   `initfunc := ld.Linklookup(ld.Ctxt, "go.link.addmoduledata", 0)`: `go.link.addmoduledata`という名前の新しいシンボルを作成します。これが、動的リンクされたモジュールの初期化時に呼び出される関数となります。
        *   この関数は、アセンブリ命令のシーケンスとして構築されます。`o`というヘルパー関数を使ってバイトコードを`initfunc`に追加していきます。
        *   **`push %ebx` (0x53)**: `ebx`レジスタをスタックに保存します。これは、プラットフォームのABI（Application Binary Interface）に従い、呼び出し元が`ebx`レジスタの値を保持することを期待している可能性があるためです。
        *   **`call __x86.get_pc_thunk.cx` (0xe8 + `R_CALL`)**: `__x86.get_pc_thunk.cx`というヘルパー関数を呼び出します。この関数は、現在のプログラムカウンタ (PC) の値を`ecx`レジスタにロードして返します。これは32ビットx86でPICを実装する際の一般的な手法です。`addcall`関数がここで使用され、`R_CALL`リロケーションが生成されます。
        *   **`lea 0x0(%ecx), %eax + R_PCREL ld.Ctxt.Moduledata` (0x8d, 0x81)**: `ecx`レジスタ（現在のPC）を基準として、`ld.Ctxt.Moduledata`シンボルのアドレスを計算し、そのアドレスを`eax`レジスタにロードします。`ld.Ctxt.Moduledata`は、現在のモジュールの`moduledata`構造体へのポインタを保持するシンボルです。`ld.Addpcrelplus`が`R_PCREL`リロケーションを生成します。
        *   **`lea 0x0(%ecx), %ebx + R_GOTPC _GLOBAL_OFFSET_TABLE_` (0x8d, 0x99)**: 同様に、`ecx`レジスタを基準として、`_GLOBAL_OFFSET_TABLE_` (GOT) のアドレスを計算し、そのアドレスを`ebx`レジスタにロードします。GOTは、動的リンクされた関数や変数へのアクセスを解決するために使用されるテーブルです。ここでも`R_PCREL`リロケーションが使用されます。
        *   **`call runtime.addmoduledata@plt` (0xe8 + `R_CALL`)**: `runtime.addmoduledata`関数を呼び出します。この呼び出しは、`PLT` (Procedure Linkage Table) を経由して行われます。`eax`レジスタには既に現在のモジュールの`moduledata`へのポインタが格納されており、これが`runtime.addmoduledata`への引数として機能します。`addcall`関数がここでも使用されます。
        *   **`pop %ebx` (0x5b)**: スタックから`ebx`レジスタの値を復元します。
        *   **`ret` (0xc3)**: 関数からリターンします。
    *   **`.init_array`への登録**:
        *   `initarray_entry := ld.Linklookup(ld.Ctxt, "go.link.addmoduledatainit", 0)`: `go.link.addmoduledatainit`という名前のシンボルを作成します。
        *   `initarray_entry.Type = obj.SINITARR`: このシンボルを`.init_array`セクションのエントリとしてマークします。
        *   `ld.Addaddr(ld.Ctxt, initarray_entry, initfunc)`: `initarray_entry`に、先ほど生成した`initfunc` (`go.link.addmoduledata`) のアドレスを追加します。これにより、OSのローダーがモジュールをロードする際に、`go.link.addmoduledata`が自動的に呼び出されるようになります。

### `src/runtime/asm_386.s` の変更

このファイルは、Goランタイムのx86アーキテクチャ固有のアセンブリコードを含んでいます。

1.  **`runtime·addmoduledata` 関数の追加**:
    *   `TEXT runtime·addmoduledata(SB),NOSPLIT,$0-0`: `runtime·addmoduledata`という新しいアセンブリ関数を定義します。`NOSPLIT`はスタックフレームを分割しないことを意味し、`$0-0`はローカル変数と引数のサイズが0であることを示します。
    *   この関数のコメントには、`.init_array`から呼び出されること、プラットフォームABIに従ってレジスタ（AX, CX, DX）を保存すること、そして引数がABIに従わず`AX`レジスタで渡される`moduledata`へのポインタであることを明記しています。
    *   `MOVL runtime·lastmoduledatap(SB), DX`: グローバル変数`runtime·lastmoduledatap`（Goランタイムが管理するモジュールデータリンクリストの最後の要素へのポインタ）の値を`DX`レジスタにロードします。
    *   `MOVL AX, moduledata_next(DX)`: `AX`レジスタに格納されている新しい`moduledata`へのポインタを、`DX`レジスタが指す既存の`moduledata`の`next`フィールドに格納します。これにより、新しいモジュールがリンクリストの最後に追加されます。
    *   `MOVL AX, runtime·lastmoduledatap(SB)`: `runtime·lastmoduledatap`を更新し、新しく追加された`moduledata`を指すようにします。
    *   `RET`: 関数からリターンします。

## コアとなるコードの解説

このコミットの核心は、Goの動的リンクされたモジュールが、その`moduledata`をGoランタイムに自動的に登録するメカニズムをLinux/386アーキテクチャ向けに実装した点にあります。

1.  **リンカーによる初期化関数の生成**: `cmd/link`は、動的リンクされるGoモジュールに対して、`go.link.addmoduledata`という特殊な初期化関数を生成します。この関数は、32ビットx86のPICの制約を考慮し、`__x86.get_pc_thunk.cx`を使って現在のPCを取得し、それに基づいて`moduledata`とGOTのアドレスを計算します。
2.  **`runtime.addmoduledata`の呼び出し**: 生成された`go.link.addmoduledata`関数は、最終的に`runtime.addmoduledata`を呼び出します。この際、計算された現在のモジュールの`moduledata`へのポインタを`eax`レジスタ経由で渡します。
3.  **`.init_array`への登録**: リンカーは、この`go.link.addmoduledata`関数へのポインタをELFバイナリの`.init_array`セクションに登録します。これにより、OSのローダーがモジュールをメモリにロードする際に、この初期化関数が自動的に実行されることが保証されます。
4.  **ランタイムによるモジュールデータの登録**: `src/runtime/asm_386.s` に追加された`runtime·addmoduledata`関数は、`eax`レジスタで受け取った`moduledata`へのポインタを利用して、Goランタイムが管理するグローバルな`moduledata`リンクリストに新しいモジュールを追加します。具体的には、`runtime·lastmoduledatap`を更新し、新しいモジュールをリストの末尾に連結します。

この一連のプロセスにより、Linux/386で動的リンクされたGoモジュールがロードされると、その`moduledata`がGoランタイムに自動的に認識され、ランタイムの健全な動作が保証されるようになります。

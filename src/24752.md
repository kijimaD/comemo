# [インデックス 24752] ファイルの概要

このコミットは、Goランタイムにおけるスタックアンワインドの挙動をより明示的にチェックするための変更を導入しています。特に、スタックバリアや`defer`によって暗黙的に検出されていた「短いアンワインド」を常に確実に検出できるようにすることが目的です。

## 変更の背景

Goランタイムでは、ゴルーチン（goroutine）のスタックは動的に伸縮します。特に、スタックが不足した場合に新しい、より大きなスタックにコピーされる「スタックの拡大」や、不要になったスタック領域を解放する「スタックの縮小」といった操作が行われます。これらの操作や、`defer`文の実行、ガベージコレクション（GC）のスタックスキャンなど、様々なランタイム処理において、スタックの正確な状態を把握し、適切にアンワインド（巻き戻し）できることが極めて重要です。

このコミット以前は、スタックのアンワインドが途中で停止する、いわゆる「短いアンワインド（short unwinding）」の検出が、スタックバリアの存在や`defer`の実行といった特定の状況に依存していました。これは、スタックの整合性チェックが暗黙的であり、これらの特定の状況が発生しない場合には、スタックが期待通りにアンワインドされなかったとしても、その問題が検出されない可能性があったことを意味します。

スタックのアンワインドが不完全であると、以下のような問題を引き起こす可能性があります。
1.  **ガベージコレクションの不正確さ**: GCがスタック上のポインタを正確にスキャンできず、到達可能なオブジェクトを誤って解放したり、到達不能なオブジェクトを解放し損ねたりする可能性があります。
2.  **クラッシュ**: 不正なスタックポインタやフレーム情報に基づいてコードが実行され、セグメンテーション違反などのクラッシュを引き起こす可能性があります。
3.  **デバッグの困難さ**: スタックトレースが不正確になり、問題の根本原因を特定することが非常に困難になります。

このコミットの目的は、このような暗黙的な検出に頼るのではなく、スタックのアンワインドが常に期待される状態に達しているかを明示的にチェックするメカニズムを導入することで、ランタイムの堅牢性を向上させることにあります。これにより、スタック関連の潜在的なバグを早期に発見し、Goプログラムの安定性を高めることができます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念について理解しておく必要があります。

1.  **ゴルーチン (Goroutine)**: Goにおける軽量な実行スレッドです。各ゴルーチンは独自のスタックを持ち、Goランタイムによってスケジューリングされます。
2.  **スタック (Stack)**: 各ゴルーチンが関数呼び出しの際にローカル変数、引数、戻りアドレスなどを格納するために使用するメモリ領域です。Goのスタックは動的に拡大・縮小します。
3.  **スタックの拡大・縮小 (Stack Growth/Shrinkage)**: Goランタイムは、関数呼び出しに必要なスタック領域が不足した場合、より大きな新しいスタックを割り当て、古いスタックの内容を新しいスタックにコピーします。逆に、スタックの使用量が減った場合は、より小さなスタックに縮小することもあります。
4.  **スタックバリア (Stack Barrier)**: スタックの拡大・縮小処理中に、GCがスタックをスキャンする際に問題が発生しないように一時的に設定される目印のようなものです。スタックバリアが存在する間は、GCはスタックの特定の領域をスキャンしない、あるいは特別な処理を行う必要があります。
5.  **`defer`文**: Goの`defer`文は、関数がリターンする直前に実行される関数呼び出しをスケジュールします。`defer`リストはスタック上に管理され、関数からのリターン時に順次実行されます。`defer`の存在は、スタックのアンワインドパスに影響を与えます。
6.  **ガベージコレクション (Garbage Collection, GC)**: GoのGCは、不要になったメモリを自動的に解放するプロセスです。GCは、実行中のゴルーチンのスタックをスキャンし、到達可能なオブジェクトへのポインタを特定します。スタックの状態が不正確だと、GCの正確性に影響が出ます。
7.  **スタックトレースバック (Stack Traceback)**: プログラムの実行中にエラーやパニックが発生した際に、現在の関数呼び出しの連鎖（コールスタック）を遡って表示する機能です。デバッグに不可欠であり、スタックの正確な状態に依存します。
8.  **`g`構造体**: Goランタイム内部でゴルーチンを表す主要なデータ構造です。この構造体には、スタックポインタ、プログラムカウンタ、スタックの境界情報など、ゴルーチンの状態に関する多くの情報が含まれています。

## 技術的詳細

このコミットは、`g`構造体に`stktopsp`という新しいフィールドを導入し、スタックのアンワインドが期待される最上位のスタックポインタ（SP）を明示的に記録・チェックすることで、スタックの整合性を保証します。

具体的には、以下の変更が行われています。

1.  **`g`構造体への`stktopsp`フィールドの追加**:
    `src/runtime/runtime2.go`の`g`構造体に`stktopsp uintptr`フィールドが追加されます。これは、ゴルーチンのスタックの最上位（最も高いアドレス）にあるべきスタックポインタの値を保持します。

2.  **`stktopsp`の初期化**:
    -   `src/runtime/proc1.go`の`newextram`関数（新しいM（OSスレッド）が作成され、その上で実行される最初のゴルーチンを初期化する際）と`newproc1`関数（新しいゴルーチンを作成する際）において、`gp.stktopsp = gp.sched.sp`または`newg.stktopsp = sp`として、新しく作成されるゴルーチンの`stktopsp`が現在のスタックポインタ`sp`で初期化されます。これは、ゴルーチンが開始された時点でのスタックの最上位を記録することを意味します。

3.  **`stktopsp`の更新**:
    -   `src/runtime/stack1.go`の`copystack`関数（スタックが拡大・縮小される際に、古いスタックの内容が新しいスタックにコピーされる処理）において、`gp.stktopsp += adjinfo.delta`として`stktopsp`が更新されます。`adjinfo.delta`はスタックの移動量（新しいスタックと古いスタックのベースアドレスの差）を表し、これにより`stktopsp`は常に現在のスタックの最上位を正確に指すように調整されます。

4.  **`stktopsp`によるスタックアンワインドのチェック**:
    -   `src/runtime/traceback.go`の`gentraceback`関数（スタックトレースバックを生成する関数）において、スタックのアンワインドが完了した後に、`frame.sp != gp.stktopsp`という条件でチェックが追加されます。
    -   `frame.sp`は現在のスタックフレームのスタックポインタであり、アンワインドが完全に終了した際には、ゴルーチンの開始時に記録された`gp.stktopsp`と一致するはずです。
    -   もし一致しない場合、それはスタックのアンワインドが途中で停止した、つまり「短いアンワインド」が発生したことを意味します。この異常な状態が検出された場合、`throw("traceback did not unwind completely")`によってランタイムパニックが発生し、問題が報告されます。

このメカニズムにより、Goランタイムはスタックの整合性をより厳密に監視し、スタック関連の潜在的な問題を早期に、かつ確実に検出できるようになります。

## コアとなるコードの解説

### `src/runtime/runtime2.go`

```go
type g struct {
	// ... 既存のフィールド ...
	syscallpc      uintptr        // if status==Gsyscall, syscallpc = sched.pc to use during gc
	stkbar         []stkbar       // stack barriers, from low to high
	stkbarPos      uintptr        // index of lowest stack barrier not hit
	stktopsp       uintptr        // expected sp at top of stack, to check in traceback
	param          unsafe.Pointer // passed parameter on wakeup
	atomicstatus   uint32
	stackLock      uint32 // sigprof/scang lock; TODO: fold in to atomicstatus
	// ... 既存のフィールド ...
}
```
`g`構造体はGoランタイムにおけるゴルーチンの表現です。ここに追加された`stktopsp uintptr`は、そのゴルーチンのスタックの最上位（最も高いアドレス）にあるべきスタックポインタの値を保持します。これは、ゴルーチンが開始された時点、またはスタックが移動した時点でのスタックの「論理的なトップ」を追跡するための基準点となります。

### `src/runtime/proc1.go`

```go
func newextram() {
	// ...
	gp.syscallpc = gp.sched.pc
	gp.syscallsp = gp.sched.sp
	gp.stktopsp = gp.sched.sp // 追加行
	// ...
}

func newproc1(fn *funcval, argp *uint8, narg int32, nret int32, callerpc uintptr) *g {
	// ...
	memclr(unsafe.Pointer(&newg.sched), unsafe.Sizeof(newg.sched))
	newg.sched.sp = sp
	newg.stktopsp = sp // 追加行
	newg.sched.pc = funcPC(goexit) + _PCQuantum // +PCQuantum so that previous instruction is in same function
	newg.sched.g = guintptr(unsafe.Pointer(newg))
	gostartcallfn(&newg.sched, fn)
	// ...
}
```
`newextram`は、新しいOSスレッド（M）が起動した際に、そのM上で実行される最初のゴルーチン（通常はランタイムの初期化処理を行うゴルーチン）を初期化します。`newproc1`は、`go`キーワードによって新しいゴルーチンが作成される際に呼び出されます。これらの関数内で`gp.stktopsp = gp.sched.sp`または`newg.stktopsp = sp`と設定されることで、ゴルーチンが実行を開始する時点でのスタックポインタが`stktopsp`に記録されます。これは、そのゴルーチンのスタックの「初期のトップ」を示す値となります。

### `src/runtime/stack1.go`

```go
func copystack(gp *g, newsize uintptr) {
	// ...
	oldsize := gp.stackAlloc
	gp.stackAlloc = newsize
	gp.stkbar = newstkbar
	gp.stktopsp += adjinfo.delta // 追加行

	// free old stack
	// ...
}
```
`copystack`関数は、ゴルーチンのスタックが拡大または縮小される際に、古いスタックの内容を新しいスタック領域にコピーする処理を行います。この際、スタックのベースアドレスが変更されるため、`stktopsp`もそれに応じて調整する必要があります。`adjinfo.delta`は、新しいスタックと古いスタックのベースアドレスの差分を表します。この差分を`gp.stktopsp`に加算することで、`stktopsp`は常に現在のスタックの最上位を正確に指すように更新されます。

### `src/runtime/traceback.go`

```go
func gentraceback(pc0, sp0, lr0 uintptr, gp *g, skip int, pcbuf *uintptr, max int, callback func(*stkframe, unsafe.Pointer) bool, v unsafe.Pointer, flags uint) int {
	// ...
	if callback != nil && n < max && frame.sp != gp.stktopsp {
		print("runtime: g", gp.goid, ": frame.sp=", hex(frame.sp), " top=", hex(gp.stktopsp), "\n")
		print("\tstack=[", hex(gp.stack.lo), "-", hex(gp.stack.hi), "] n=", n, " max=", max, "\n")
		throw("traceback did not unwind completely")
	}

	return n
}
```
`gentraceback`関数は、スタックトレースバックを生成する際に呼び出されます。この関数は、スタックフレームを一つずつ遡り、コールスタックを構築します。スタックトレースバックの処理が完了した後、`frame.sp != gp.stktopsp`という条件でチェックが行われます。
-   `frame.sp`は、トレースバックが完了した時点でのスタックポインタです。
-   `gp.stktopsp`は、ゴルーチンが開始された時点、またはスタックが移動した時点でのスタックの最上位を記録した値です。
もし、スタックトレースバックが完全にアンワインドされた場合、`frame.sp`は`gp.stktopsp`と一致するはずです。一致しない場合は、スタックのアンワインドが途中で停止した、つまり「短いアンワインド」が発生したことを意味します。この異常な状態が検出されると、詳細なデバッグ情報（ゴルーチンID、スタックポインタ、スタックの範囲など）が出力された後、`throw`関数によってランタイムパニックが引き起こされ、プログラムが異常終了します。これにより、スタックの整合性に関する問題を早期に、かつ確実に開発者に通知することができます。

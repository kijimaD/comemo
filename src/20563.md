# [インデックス 20563] ファイルの概要

このコミットは、Goランタイムにおけるパニック処理の内部実装に関する重要な変更を含んでいます。具体的には、`panicstring`関数の削除と、それに伴う関連するエラーチェックロジックの`gopanic`関数への統合、および`errorCString`、`newErrorCString`、`newErrorString`といった型と関数の削除が主な内容です。これにより、ランタイムの安定性とエラー報告の信頼性が向上しています。

## コミット

```
commit c3b5db895b11ba28bc1546f37178efcb057ab3f0
Author: Russ Cox <rsc@golang.org>
Date:   Thu Sep 18 14:49:24 2014 -0400

    runtime: delete panicstring; move its checks into gopanic
    
    In Go 1.3 the runtime called panicstring to report errors like
    divide by zero or memory faults. Now we call panic (gopanic)
    with pre-allocated error values. That new path is missing the
    checking that panicstring did, so add it there.
    
    The only call to panicstring left is in cnew, which is problematic
    because if it fails, probably the heap is corrupt. In that case,
    calling panicstring creates a new errorCString (no allocation there),
    but then panic tries to print it, invoking errorCString.Error, which
    does a string concatenation (allocating), which then dies.
    Replace that one panicstring with a throw: cnew is for allocating
    runtime data structures and should never ask for an inappropriate
    amount of memory.
    
    With clinicstring gone, delete newErrorCString, errorCString.
    While we're here, delete newErrorString, not called by anyone.
    (It can't be: that would be C code calling Go code that might
    block or grow the stack.)
    
    Found while debugging a malloc corruption.
    This resulted in 'panic during panic' instead of a more useful message.
    
    LGTM=khr
    R=khr
    CC=golang-codereviews
    https://golang.org/cl/138290045
```

## 元コミット内容

Go 1.3では、ランタイムがゼロ除算やメモリ障害のようなエラーを報告するために`panicstring`を呼び出していました。現在では、事前に割り当てられたエラー値を用いて`panic`（`gopanic`）を呼び出すようになっています。この新しいパスには`panicstring`が行っていたチェックが欠けていたため、それを`gopanic`に追加します。

`panicstring`への唯一残っていた呼び出しは`cnew`内にありましたが、これは問題がありました。なぜなら、`cnew`が失敗した場合、おそらくヒープが破損しているためです。その状況で`panicstring`を呼び出すと、新しい`errorCString`が作成されますが（ここでは割り当ては発生しません）、その後`panic`がそれを表示しようとすると、`errorCString.Error`が呼び出され、文字列連結（割り当てが発生）が行われ、そこでさらにクラッシュしてしまいます。この`panicstring`の呼び出しを`throw`に置き換えます。`cnew`はランタイムのデータ構造を割り当てるためのものであり、不適切な量のメモリを要求すべきではありません。

`panicstring`がなくなったため、`newErrorCString`と`errorCString`を削除します。ついでに、どこからも呼び出されていない`newErrorString`も削除します。（これは呼び出されるはずがありません。CコードがGoコードを呼び出し、それがブロックしたりスタックを成長させたりする可能性があるためです。）

この変更は、`malloc`の破損をデバッグしている最中に発見されました。これにより、より有用なメッセージではなく「パニック中のパニック」が発生していました。

## 変更の背景

このコミットの背景には、Goランタイムのパニック処理における堅牢性の向上と、デバッグ時の情報提供の改善という目的があります。Go 1.3でパニック処理の内部メカニズムが変更され、エラー報告のパスが`panicstring`から`gopanic`へと移行しました。しかし、この移行の際に、`panicstring`が以前行っていた重要な健全性チェック（例えば、`malloc`中、GC中、ロック保持中などの特殊な状況でのパニックを防ぐチェック）が新しい`gopanic`のパスで欠落していることが判明しました。

特に問題となったのは、メモリ割り当て関数である`cnew`内で`panicstring`が使用されていたケースです。`cnew`が失敗するということは、システムが非常に不安定な状態（ヒープ破損など）にある可能性が高いことを意味します。このような状況で`panicstring`が呼び出されると、内部で`errorCString`が生成され、その`Error`メソッドが文字列連結のためにメモリ割り当てを試みます。しかし、ヒープが破損している状況では、このメモリ割り当て自体が失敗し、結果として「パニック中のパニック」という、デバッグが極めて困難な状態に陥っていました。これは、元の問題（`malloc`破損）に関する有用な情報が得られないことを意味します。

このコミットは、このような「パニック中のパニック」を防ぎ、ランタイムがより信頼性の高い方法でエラーを報告できるようにするために行われました。`panicstring`の削除と、そのチェックを`gopanic`に移動することで、パニック処理の単一障害点を減らし、特殊なランタイム状態（メモリ割り当て中、GC中など）でのパニックが適切に処理されるようにしています。また、`cnew`のようなクリティカルな低レベル関数では、パニックではなく`throw`（回復不能なエラー）を使用することで、さらなる問題の連鎖を防ぐ設計思想が適用されています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念と内部動作に関する知識が必要です。

*   **Goランタイム**: Goプログラムの実行を管理する低レベルのシステム。ガベージコレクション、スケジューリング、メモリ管理、パニック処理などを担当します。C言語とGo言語で実装されています。
*   **パニック (Panic)**: Goにおけるエラー処理メカニズムの一つで、プログラムの回復不能なエラーを示すために使用されます。パニックが発生すると、通常の実行フローは中断され、遅延関数（`defer`）が実行され、最終的にプログラムがクラッシュするか、`recover`によってパニックが捕捉されるまでスタックがアンワインドされます。
*   **`gopanic`**: Goランタイム内部でパニックを発生させるための主要な関数。Goコードから`panic()`が呼び出されたり、ランタイムが検出したエラー（例: nilポインタ参照、インデックス範囲外アクセス）によって内部的に呼び出されたりします。
*   **`throw`**: Goランタイムにおける、より深刻で回復不能なエラーを示すためのメカニズム。`throw`が呼び出されると、Goプログラムは即座に終了し、スタックトレースが出力されます。これは、ランタイム自体が深刻な整合性問題に直面している場合（例: ヒープ破損）に使用され、`panic`のように`recover`で捕捉されることはありません。
*   **`m` (M: Machine)**: Goスケジューラにおける「マシン」または「OSスレッド」を表す構造体。Goルーチン（`g`）を実行するためのOSスレッドに相当します。`m`構造体には、そのスレッドの状態に関する情報（例: `mallocing`、`gcing`、`locks`、`softfloat`）が含まれます。
    *   `m.mallocing`: 現在、メモリ割り当て中であることを示すフラグ。
    *   `m.gcing`: 現在、ガベージコレクション中であることを示すフラグ。
    *   `m.locks`: 現在、ランタイム内部のロックを保持していることを示すカウンタ。
    *   `m.softfloat`: ソフトウェア浮動小数点演算が進行中であることを示すフラグ。ソフトウェア浮動小数点演算は、特定のアーキテクチャでハードウェア浮動小数点ユニットがない場合や、特殊な浮動小数点演算が必要な場合に使用されます。この間はプリエンプション（Goルーチンの切り替え）を避けるために`m.locks`がインクリメントされることがあります。
*   **`cnew`**: Goランタイム内部で使用される、C言語で実装されたメモリ割り当て関数の一つ。主にランタイムの内部データ構造を割り当てるために使用されます。
*   **`errorString` / `errorCString`**: Goランタイム内部でエラーメッセージを表現するために使用されていた型。`errorCString`は特にC言語の文字列（`char*`）をラップするために設計されていました。
*   **メモリ割り当てとガベージコレクション**: Goランタイムの重要な機能。メモリ割り当てはヒープからメモリを確保するプロセスであり、ガベージコレクションは不要になったメモリを自動的に解放するプロセスです。これらの操作中にパニックが発生すると、ランタイムの整合性がさらに損なわれる可能性があります。
*   **Go 1.3の変更点**: Go 1.3では、パニック処理の内部実装にいくつかの変更が加えられました。特に、ランタイムが生成するエラー（ゼロ除算など）が、以前は`panicstring`を介して処理されていたものが、より一般的な`gopanic`パスを使用するように変更されました。この変更は、パニック処理の統一と効率化を目的としていました。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムのパニック処理の堅牢性を高めるための多層的なアプローチを示しています。

1.  **`panicstring`の廃止と`gopanic`への統合**:
    *   Go 1.3以前は、ランタイムが生成する特定の低レベルエラー（例: ゼロ除算、メモリ不正アクセス）は`panicstring`という専用の関数を介してパニックを発生させていました。この関数は、パニックが発生した際のランタイムの状態（`m.softfloat`、`m.mallocing`、`m.gcing`、`m.locks`）をチェックし、これらの特殊な状況下でのパニックを`gothrow`（回復不能なエラー）に昇格させることで、さらなる問題の連鎖を防ぐ役割を担っていました。
    *   Go 1.3で、これらのエラーが`gopanic`を介して処理されるように変更されましたが、`panicstring`が行っていた重要な健全性チェックが`gopanic`に移植されていませんでした。
    *   このコミットでは、`panicstring`関数自体を削除し、その内部で行われていた`m`構造体の状態チェック（`softfloat`、`mallocing`、`gcing`、`locks`）を`gopanic`関数の冒頭に移動させました。これにより、すべてのパニックが`gopanic`を通過する際にこれらのチェックが適用されるようになり、パニック処理の統一性と安全性が向上しました。

2.  **`cnew`における`panicstring`から`throw`への変更**:
    *   `cnew`はランタイム内部の非常に低レベルなメモリ割り当て関数であり、主にランタイム自身のデータ構造（例: Goルーチンスタック、GCメタデータ）を割り当てるために使用されます。
    *   `cnew`がメモリ割り当てに失敗するということは、通常、ヒープが破損しているか、システムが極めてメモリ不足であるなど、ランタイム自体が深刻な問題に直面していることを意味します。
    *   以前は、`cnew`が失敗すると`panicstring`を呼び出していました。しかし、`panicstring`は最終的に`gopanic`を呼び出し、その過程で`errorCString`の`Error`メソッドが文字列連結のためにメモリ割り当てを試みます。ヒープが破損している状況では、この割り当てが失敗し、「パニック中のパニック」というデバッグ困難な状態を引き起こしていました。
    *   このコミットでは、`cnew`内の`panicstring`の呼び出しを`runtime·throw`に置き換えました。`throw`は回復不能なエラーであり、即座にプログラムを終了させます。これにより、ヒープ破損のような深刻な状況で、さらなるメモリ割り当てを試みて問題を悪化させることを防ぎ、より直接的で有用なクラッシュレポートを提供できるようになります。`cnew`がランタイムのコア部分であるため、ここで発生するエラーは回復不能であるべきという設計思想が反映されています。

3.  **`errorCString`、`newErrorCString`、`newErrorString`の削除**:
    *   `panicstring`の削除に伴い、それに依存していた`errorCString`型と`newErrorCString`関数が不要になりました。これらはC言語の文字列をGoのエラーインターフェースに変換するために使用されていました。
    *   また、`newErrorString`関数もどこからも呼び出されていなかったため、この機会に削除されました。コメントにあるように、CコードがGoコードを呼び出してパニックを生成し、それがブロックしたりスタックを成長させたりする可能性があるため、このような関数は設計上問題があると考えられます。
    *   これらの型の削除は、ランタイムのコードベースを簡素化し、不要な抽象化を取り除くことに貢献しています。

この変更は、Goランタイムのパニック処理の設計原則、すなわち「パニックは回復可能であるべきだが、ランタイムの整合性が損なわれた場合は即座に終了すべき」という考え方をより明確に反映しています。特に、低レベルのメモリ管理コードにおけるエラーは、さらなる複雑なエラー連鎖を防ぐために、即座にプログラムを終了させるべきであるという判断がなされています。

`runtime·schedinit`関数は、Goランタイムの初期化を行う関数です。以前は、`newErrorCString`のitable値を初期化するためのコードが含まれていましたが、`newErrorCString`が削除されたため、この初期化コードも不要となり削除されました。これは、ガベージコレクション中の障害でメモリ割り当てが必要にならないようにするための最適化でしたが、関連する型と関数がなくなったため、削除されました。

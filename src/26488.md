## 変更の背景

このコミットの主な背景は、Goのビルドシステムがベンダーコード（vendored code）を「標準」パッケージとして正しく認識していなかったという問題にあります。具体的には、`golang.org/x/net/http/hpack` のベンダーコピーが標準ではないと判断されたため、リリースビルドにおける標準ライブラリの再ビルドに関する `mtime` (最終更新時刻) の例外が適用されませんでした。

Goのビルドシステムは、パフォーマンス最適化のために、標準ライブラリのパッケージが変更されていない限り再ビルドをスキップするメカニズムを持っています。これは、ファイルの `mtime` を比較することで行われます。しかし、ベンダーコードが標準ではないと誤って分類されたため、`net/http` パッケージが依存する `hpack` が常に「古い」と見なされ、結果として `net/http` パッケージ全体が不必要に再ビルドされるという問題が発生していました。これはビルド時間の増加や、リリースビルドの整合性に関する潜在的な問題を引き起こす可能性がありました。

この問題を解決するため、Goのビルドシステムが「標準」パッケージを識別する方法を修正し、ベンダーコードも適切に標準として扱われるようにする必要がありました。また、この変更が意図通りに機能することを保証するためのテストの追加と、標準パッケージが非標準パッケージに依存することを防ぐための制約の導入も行われました。

## 前提知識の解説

### Goのパッケージとインポートパス

Goのコードはパッケージにまとめられ、`import` ステートメントで他のパッケージを参照します。インポートパスは、パッケージを一意に識別するための文字列です。

### `GOROOT` と `GOPATH`

*   **`GOROOT`**: GoのSDKがインストールされているディレクトリです。標準ライブラリのソースコード（例: `fmt`, `net/http` など）は `$GOROOT/src` 以下に配置されています。
*   **`GOPATH`**: ユーザーのワークスペースディレクトリです。Go 1.11以前では、サードパーティのパッケージは `$GOPATH/src` 以下に配置されていました。Go Modulesの導入後も、一部のツールやレガシーなプロジェクトで利用されることがあります。

### ベンダーコード (Vendoring)

Go Modulesが導入される前、または特定のプロジェクトで依存関係を厳密に管理するために、プロジェクトのソースコード内に依存する外部パッケージのコピーを配置する手法を「ベンダー（vendoring）」と呼びます。通常、これは `vendor/` ディレクトリに配置されます。これにより、外部ネットワークに依存せずにビルドが可能になり、依存関係のバージョンを固定できます。

### 「標準」パッケージの定義

Goのビルドシステムにおいて、「標準」パッケージとは、Goの配布物の一部として提供されるパッケージ（主に `$GOROOT/src` 以下にあるもの）を指します。この「標準」という概念は、ビルドの最適化（例: `mtime` 例外）や、`go list std` のようなコマンドの挙動に影響を与えます。歴史的に、Goは `$GOROOT/src` にユーザーコードを追加することを許可していましたが、その場合、インポートパスの最初の要素にドット（`.`）が含まれる（例: `github.com/user/repo` のようなドメイン名形式）ことで、標準パッケージと区別されていました。

### `mtime` 例外とビルドキャッシュ

Goのビルドシステムは、ファイルの最終更新時刻（`mtime`）を利用して、ソースファイルが変更されていない場合に再ビルドをスキップする最適化を行います。特に、リリースビルドにおいては、標準ライブラリのパッケージが変更されていない限り、そのパッケージの再ビルドをスキップする「`mtime` 例外」というルールが適用されます。これにより、ビルド時間を短縮し、安定したリリースを提供できます。ベンダーコードが標準と認識されない場合、この例外が適用されず、不必要な再ビルドが発生する可能性がありました。

### `go list` コマンド

`go list` コマンドは、Goパッケージに関する情報を表示するためのツールです。`-f` フラグを使って出力フォーマットをカスタマイズでき、パッケージの様々なフィールド（例: `.ImportPath`, `.Standard` など）にアクセスできます。`.Standard` フィールドは、そのパッケージが標準パッケージであるかどうかを示すブール値です。

## 技術的詳細

このコミットは、Goのビルドシステムがパッケージを「標準」と判断するロジックを根本的に見直しました。

1.  **`isStandardImportPath` 関数の導入**:
    以前は、パッケージの `Goroot` フィールドが `true` であり、かつインポートパスの最初の要素にドットが含まれていない場合に「標準」と判断されていました。このコミットでは、このロジックを `isStandardImportPath` という新しい関数にカプセル化し、より明確にしました。この関数は、インポートパスの最初の要素にドットが含まれていない場合に `true` を返します。これにより、`golang.org/x/net/http/hpack` のようなベンダーコード（`vendor/golang.org/x/net/http/hpack` のように `$GOROOT/src` 内に配置される場合）も、そのインポートパスが `golang.org/x/net/http/hpack` であり、最初の要素 `golang.org` にドットが含まれるため、非標準と判断されるという問題がありました。しかし、このコミットの意図は、`$GOROOT/src` 内にあるものは、たとえインポートパスにドットが含まれていても、標準として扱われるべきだという点にあります。コミットメッセージの「Fix the definition of standard.」がこれを指しています。

2.  **`Package.Standard` フィールドの計算ロジックの変更**:
    `src/cmd/go/pkg.go` 内で、`Package` 構造体の `Standard` フィールドの計算方法が変更されました。以前は `p.Goroot && p.ImportPath != "" && !strings.Contains(p.ImportPath, ".")` でしたが、新しい `isStandardImportPath(p.ImportPath)` 関数を使用するように変更されました。これにより、`$GOROOT` 内にあるパッケージは、そのインポートパスが `isStandardImportPath` の条件を満たす場合に標準と見なされるようになります。

3.  **標準パッケージから非標準パッケージへの依存の禁止**:
    このコミットでは、標準パッケージが非標準パッケージに依存することを禁止する新しいチェックが導入されました。もし標準パッケージが非標準パッケージをインポートしようとすると、ビルド時にエラーが発生します。これは、Goの配布物の整合性と予測可能性を保つ上で重要な制約です。

4.  **テストの追加**:
    *   `$GOROOT/src/` 内のすべてのパッケージが「標準」として認識されることを確認するテストが追加されました。これは、`go test cmd/go` の実行中に `$GOROOT/src` 内のすべてのパッケージをリストし、`.Standard` フィールドが `true` であることを検証します。
    *   `go list std cmd` コマンドがベンダーコード（例: `golang.org/x/net/http2/hpack`, `golang.org/x/arch/x86/x86asm`）を正しく表示することを確認するテストが追加されました。これは、`std` パッケージのリストにベンダーコードが含まれるべきであることを示しています。

5.  **エラー出力の改善**:
    `src/cmd/go/run.go` において、依存関係のエラー（`p.DepsErrors`）が出力される際に、同じエラーが複数回表示されるのを防ぐために、一度だけ出力されるように修正されました。これにより、エラーメッセージの可読性が向上します。

これらの変更により、Goのビルドシステムはベンダーコードをより正確に扱い、標準ライブラリのビルドプロセスが効率的かつ堅牢になることが期待されます。

### 「標準」パッケージの定義

Goのビルドシステムにおいて、「標準」パッケージとは、Goの配布物の一部として提供されるパッケージ（主に `$GOROOT/src` 以下にあるもの）を指します。この「標準」という概念は、ビルドの最適化（例: `mtime` 例外）や、`go list std` のようなコマンドの挙動に影響を与えます。歴史的に、Goは `$GOROOT/src` にユーザーコードを追加することを許可していましたが、その場合、インポートパスの最初の要素にドット（`.`）が含まれる（例: `github.com/user/repo` のようなドメイン名形式）ことで、標準パッケージと区別されていました。

### `mtime` 例外とビルドキャッシュ

Goのビルドシステムは、ファイルの最終更新時刻（`mtime`）を利用して、ソースファイルが変更されていない場合に再ビルドをスキップする最適化を行います。特に、リリースビルドにおいては、標準ライブラリのパッケージが変更されていない限り、そのパッケージの再ビルドをスキップする「`mtime` 例外」というルールが適用されます。これにより、ビルド時間を短縮し、安定したリリースを提供できます。ベンダーコードが標準と認識されない場合、この例外が適用されず、不必要な再ビルドが発生する可能性がありました。

### `go list` コマンド

`go list` コマンドは、Goパッケージに関する情報を表示するためのツールです。`-f` フラグを使って出力フォーマットをカスタマイズでき、パッケージの様々なフィールド（例: `.ImportPath`, `.Standard` など）にアクセスできます。`.Standard` フィールドは、そのパッケージが標準パッケージであるかどうかを示すブール値です。

## 技術的詳細

このコミットは、Goのビルドシステムがパッケージを「標準」と判断するロジックを根本的に見直しました。

1.  **`isStandardImportPath` 関数の導入**:
    以前は、パッケージの `Goroot` フィールドが `true` であり、かつインポートパスの最初の要素にドットが含まれていない場合に「標準」と判断されていました。このコミットでは、このロジックを `isStandardImportPath` という新しい関数にカプセル化し、より明確にしました。この関数は、インポートパスの最初の要素にドットが含まれていない場合に `true` を返します。これにより、`golang.org/x/net/http/hpack` のようなベンダーコード（`vendor/golang.org/x/net/http/hpack` のように `$GOROOT/src` 内に配置される場合）も、そのインポートパスが `golang.org/x/net/http/hpack` であり、最初の要素 `golang.org` にドットが含まれるため、非標準と判断されるという問題がありました。しかし、このコミットの意図は、`$GOROOT/src` 内にあるものは、たとえインポートパスにドットが含まれていても、標準として扱われるべきだという点にあります。コミットメッセージの「Fix the definition of standard.」がこれを指しています。

2.  **`Package.Standard` フィールドの計算ロジックの変更**:
    `src/cmd/go/pkg.go` 内で、`Package` 構造体の `Standard` フィールドの計算方法が変更されました。以前は `p.Goroot && p.ImportPath != "" && !strings.Contains(p.ImportPath, ".")` でしたが、新しい `isStandardImportPath(p.ImportPath)` 関数を使用するように変更されました。これにより、`$GOROOT` 内にあるパッケージは、そのインポートパスが `isStandardImportPath` の条件を満たす場合に標準と見なされるようになります。

3.  **標準パッケージから非標準パッケージへの依存の禁止**:
    このコミットでは、標準パッケージが非標準パッケージに依存することを禁止する新しいチェックが導入されました。もし標準パッケージが非標準パッケージをインポートしようとすると、ビルド時にエラーが発生します。これは、Goの配布物の整合性と予測可能性を保つ上で重要な制約です。

4.  **テストの追加**:
    *   `$GOROOT/src/` 内のすべてのパッケージが「標準」として認識されることを確認するテストが追加されました。これは、`go test cmd/go` の実行中に `$GOROOT/src` 内のすべてのパッケージをリストし、`.Standard` フィールドが `true` であることを検証します。
    *   `go list std cmd` コマンドがベンダーコード（例: `golang.org/x/net/http2/hpack`, `golang.org/x/arch/x86/x86asm`）を正しく表示することを確認するテストが追加されました。これは、`std` パッケージのリストにベンダーコードが含まれるべきであることを示しています。

5.  **エラー出力の改善**:
    `src/cmd/go/run.go` において、依存関係のエラー（`p.DepsErrors`）が出力される際に、同じエラーが複数回表示されるのを防ぐために、一度だけ出力されるように修正されました。これにより、エラーメッセージの可読性が向上します。

これらの変更により、Goのビルドシステムはベンダーコードをより正確に扱い、標準ライブラリのビルドプロセスが効率的かつ堅牢になることが期待されます。

*   `src/cmd/go/go_test.go`: 新しいテストケースの追加。

func isStandardImportPath(path string) bool {
	i := strings.Index(path, "/")
	if i < 0 {
		i = len(path)

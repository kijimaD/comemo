## 変更の背景

このコミットの背景には、Goランタイムのガベージコレクション（GC）の動作と、CPUプロファイラがgoroutineの状態を記録する方法との間の特定の相互作用があります。

GoのGCは、メモリ管理のために様々なフェーズを経ますが、その中には「Stop-The-World (STW)」フェーズと呼ばれるものがあります。STWフェーズ中、Goプログラムの全てのgoroutineは一時的に実行を停止し、GCが安全にヒープをスキャンし、到達不能なオブジェクトを特定・解放できるようにします。この間、GCはヒープの状態が変化しないことを前提として動作します。

問題は、Windows環境で外部のCライブラリなどを呼び出す際に使用される`stdcall`規約の関数が、STW中に呼び出される可能性がある点にありました。CPUプロファイラは、プロファイリング情報を収集するために、`stdcall`呼び出し中に現在のgoroutine (`g`) へのポインタを`mp.libcallg`というフィールドに書き込むことがあります。

通常、GoのGCは、ヒープ上のポインタの変更を追跡するために「ライトバリア（Write Barrier）」というメカニズムを使用します。ライトバリアは、ポインタが書き換えられる際にGCに通知し、GCがオブジェクトの参照関係の変更を正確に把握できるようにするものです。しかし、STWフェーズ中は、GCはライトバリアが実行されない、あるいは実行されてもGCの内部状態を変化させないことを期待しています。

この状況で、STW中に`stdcall`が`g`へのポインタを書き込む際にライトバリアがトリガーされると、GCの想定と実際の動作が食い違い、ランタイムの不安定性やGCの誤動作につながる可能性がありました。コミットメッセージにあるように、「GCは世界が停止しているときにライトバリアを処理する準備ができていない」という点が核心的な問題でした。

この問題を解決するため、`g`が`allg`（全てのgoroutineを追跡するリスト）によって既に参照されており、GCによって到達可能であることが保証されているため、`mp.libcallg`への`g`の書き込みにライトバリアが不要であるという事実が利用されました。つまり、`g`は`mp.libcallg`に書き込まれなくても、`allg`によって「生きている」と判断されるため、ライトバリアによる追加の保護は必要ないという判断です。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する概念を理解しておく必要があります。

1.  **Goのガベージコレクション (GC)**:
    *   Goはトレース型GCを採用しており、プログラムが使用しなくなったメモリを自動的に解放します。
    *   GoのGCは、並行（concurrent）かつ低遅延（low-latency）を目指して設計されています。これは、GCの大部分がアプリケーションのgoroutineと並行して実行されることを意味します。
    *   **Stop-The-World (STW) フェーズ**: GoのGCには、非常に短いながらも全てのgoroutineの実行を一時停止させるSTWフェーズが存在します。これは、GCがヒープの状態を正確にスキャンし、マーク（到達可能なオブジェクトを識別）やスイープ（到達不能なオブジェクトを解放）といった重要な操作を整合性の取れた状態で行うために必要です。STW中は、ヒープ上のポインタの変更がGCの内部状態を破壊しないように、特定の制約が課せられます。

2.  **ライトバリア (Write Barrier)**:
    *   ライトバリアは、GCが並行して動作する際に、アプリケーションのgoroutineがヒープ上のポインタを書き換える操作を監視するためのメカニズムです。
    *   具体的には、あるオブジェクトのフィールドに別のオブジェクトへのポインタを書き込む際に、GCがその変更を認識し、必要に応じてGCの内部データ構造（例えば、オブジェクトグラフ）を更新するために挿入される小さなコードスニペットです。
    *   これにより、GCがヒープをスキャンしている最中にアプリケーションがポインタを変更しても、GCがオブジェクトの到達可能性を正確に判断できるようになります。
    *   しかし、STWフェーズ中は、GC自体がヒープの整合性を確保するために特別なモードで動作しており、この期間中にアプリケーションコードによってライトバリアがトリガーされることは想定されていません。もしトリガーされた場合、GCの内部状態が矛盾する可能性があります。

3.  **`g` (goroutine構造体)**:
    *   Goランタイムにおいて、`g`は個々のgoroutineの状態を表す`runtime.g`構造体へのポインタです。各goroutineは独自のスタック、プログラムカウンタ、レジスタなどの情報を持っています。

4.  **`allg`**:
    *   `allg`は、Goランタイムが管理する全てのgoroutine (`g`構造体) のリストです。このリストは、GCのルートセットの一部として扱われます。つまり、`allg`から参照されている`g`構造体は、GCによって常に「生きている」と判断され、回収されることはありません。

5.  **`stdcall`**:
    *   `stdcall`は、主にWindows APIの呼び出しに使用される関数呼び出し規約の一つです。呼び出し側がスタックをクリーンアップする`cdecl`とは異なり、`stdcall`では呼び出された関数がスタックをクリーンアップします。GoランタイムがWindowsのシステムコールを呼び出す際に、この規約が使用されることがあります。

6.  **CPUプロファイラ**:
    *   GoのCPUプロファイラは、プログラムの実行中にどの関数がCPU時間を消費しているかをサンプリングによって特定するツールです。プロファイラは、特定のタイミングで各goroutineのスタックトレースを収集し、実行中の関数やその呼び出し元を特定します。このプロセスの一環として、現在のgoroutine (`g`) の情報を記録することがあります。

7.  **`//go:nowritebarrier` ディレクティブ**:
    *   Goコンパイラに対するディレクティブ（指示）の一つで、このディレクティブが付与された関数内では、ポインタの書き込み時にライトバリアを生成しないように指示します。これは、特定の低レベルなランタイムコードで、ライトバリアが不要または有害な場合にのみ慎重に使用されます。

## 技術的詳細

このコミットが対処している技術的な問題は、GoランタイムのSTWフェーズとライトバリアの間のデリケートな相互作用にあります。

通常、GoのGCは並行して動作しますが、マークフェーズの開始時や終了時など、特定の重要なポイントでSTWフェーズに入ります。STW中は、GCはヒープ上のオブジェクトグラフが静止していることを前提として動作します。この静止状態は、GCがオブジェクトの到達可能性を正確に判断し、メモリを安全に管理するために不可欠です。

問題のシナリオは、Windows環境における`stdcall`呼び出し中に発生しました。Goランタイムは、CPUプロファイリングのために、`stdcall`が実行されている間に現在のgoroutine (`g`) へのポインタを`mp.libcallg`というフィールドに一時的に保存します。`mp`は現在のM（マシン、OSスレッドを表す）構造体へのポインタです。

`mp.libcallg = gp`という代入は、通常であればヒープ上のポインタの書き込みとして認識され、ライトバリアがトリガーされます。しかし、この代入がSTWフェーズ中に発生すると、GCはライトバリアの実行を想定しておらず、その結果、GCの内部状態が矛盾する可能性がありました。GCがSTW中にライトバリアを処理できないのは、STWの目的がヒープの静止状態を確保し、GCがその状態に基づいて安全な操作を行うことにあるためです。ライトバリアがSTW中に実行されると、GCが想定するヒープの状態と実際の状態との間に不整合が生じ、GCの正確性や安定性が損なわれる恐れがあります。

この問題の解決策は、`g`（goroutineポインタ）が`allg`というグローバルなリストによって常に参照されているというGoランタイムの特性を利用することでした。`allg`はGCのルートセットの一部であるため、`allg`から参照されている`g`は、GCによって常に「生きている」と判断され、回収されることはありません。したがって、`mp.libcallg`に`g`を書き込む際にライトバリアがトリガーされなくても、`g`がGCによって誤って回収される心配はありません。`mp.libcallg`への書き込みは、プロファイリングのための一時的な参照であり、`g`の生存期間には影響を与えないため、このライトバリアは冗長であると判断されました。

このコミットは、この冗長なライトバリアを削除することで、STW中のGCの整合性を保ち、ランタイムの堅牢性を向上させています。

2.  **ライトバリア (Write Barrier)**:
    *   ライトバリアは、GCが並行して動作する際に、アプリケーションのgoroutineがヒープ上のポインタを書き換える操作を監視するためのメカニズムです。
    *   具体的には、あるオブジェクトのフィールドに別のオブジェクトへのポインタを書き込む際に、GCがその変更を認識し、必要に応じてGCの内部データ構造（例えば、オブジェクトグラフ）を更新するために挿入される小さなコードスニペットです。
    *   これにより、GCがヒープをスキャンしている最中にアプリケーションがポインタを変更しても、GCがオブジェクトの到達可能性を正確に判断できるようになります。
    *   しかし、STWフェーズ中は、GC自体がヒープの整合性を確保するために特別なモードで動作しており、この期間中にアプリケーションコードによってライトバリアがトリガーされることは想定されていません。もしトリガーされた場合、GCの内部状態が矛盾する可能性があります。

3.  **`g` (goroutine構造体)**:
    *   Goランタイムにおいて、`g`は個々のgoroutineの状態を表す`runtime.g`構造体へのポインタです。各goroutineは独自のスタック、プログラムカウンタ、レジスタなどの情報を持っています。

4.  **`allg`**:
    *   `allg`は、Goランタイムが管理する全てのgoroutine (`g`構造体) のリストです。このリストは、GCのルートセットの一部として扱われます。つまり、`allg`から参照されている`g`構造体は、GCによって常に「生きている」と判断され、回収されることはありません。

5.  **`stdcall`**:
    *   `stdcall`は、主にWindows APIの呼び出しに使用される関数呼び出し規約の一つです。呼び出し側がスタックをクリーンアップする`cdecl`とは異なり、`stdcall`では呼び出された関数がスタックをクリーンアップします。GoランタイムがWindowsのシステムコールを呼び出す際に、この規約が使用されることがあります。

6.  **CPUプロファイラ**:
    *   GoのCPUプロファイラは、プログラムの実行中にどの関数がCPU時間を消費しているかをサンプリングによって特定するツールです。プロファイラは、特定のタイミングで各goroutineのスタックトレースを収集し、実行中の関数やその呼び出し元を特定します。このプロセスの一環として、現在のgoroutine (`g`) の情報を記録することがあります。

7.  **`//go:nowritebarrier` ディレクティブ**:
    *   Goコンパイラに対するディレクティブ（指示）の一つで、このディレクティブが付与された関数内では、ポインタの書き込み時にライトバリアを生成しないように指示します。これは、特定の低レベルなランタイムコードで、ライトバリアが不要または有害な場合にのみ慎重に使用されます。

## 技術的詳細

このコミットが対処している技術的な問題は、GoランタイムのSTWフェーズとライトバリアの間のデリケートな相互作用にあります。

通常、GoのGCは並行して動作しますが、マークフェーズの開始時や終了時など、特定の重要なポイントでSTWフェーズに入ります。STW中は、GCはヒープ上のオブジェクトグラフが静止していることを前提として動作します。この静止状態は、GCがオブジェクトの到達可能性を正確に判断し、メモリを安全に管理するために不可欠です。

問題のシナリオは、Windows環境における`stdcall`呼び出し中に発生しました。Goランタイムは、CPUプロファイリングのために、`stdcall`が実行されている間に現在のgoroutine (`g`) へのポインタを`mp.libcallg`というフィールドに一時的に保存します。`mp`は現在のM（マシン、OSスレッドを表す）構造体へのポインタです。

`mp.libcallg = gp`という代入は、通常であればヒープ上のポインタの書き込みとして認識され、ライトバリアがトリガーされます。しかし、この代入がSTWフェーズ中に発生すると、GCはライトバリアの実行を想定しておらず、その結果、GCの内部状態が矛盾する可能性がありました。GCがSTW中にライトバリアを処理できないのは、STWの目的がヒープの静止状態を確保し、GCがその状態に基づいて安全な操作を行うことにあるためです。ライトバリアがSTW中に実行されると、GCが想定するヒープの状態と実際の状態との間に不整合が生じ、GCの正確性や安定性が損なわれる恐れがあります。

この問題の解決策は、`g`（goroutineポインタ）が`allg`というグローバルなリストによって常に参照されているというGoランタイムの特性を利用することでした。`allg`はGCのルートセットの一部であるため、`allg`から参照されている`g`は、GCによって常に「生きている」と判断され、回収されることはありません。したがって、`mp.libcallg`に`g`を書き込む際にライトバリアがトリガーされなくても、`g`がGCによって誤って回収される心配はありません。`mp.libcallg`への書き込みは、プロファイリングのための一時的な参照であり、`g`の生存期間には影響を与えないため、このライトバリアは冗長であると判断されました。

このコミットは、この冗長なライトバリアを削除することで、STW中のGCの整合性を保ち、ランタイムの堅牢性を向上させています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`src/runtime/os1_windows.go`内の`stdcall`関数における`g`ポインタの取り扱い方です。

1.  **`//go:nowritebarrier` ディレクティブの追加**:
    *   `stdcall`関数の定義の直前に`//go:nowritebarrier`というコンパイラディレクティブが追加されました。
    *   このディレクティブは、Goコンパイラに対して、この関数内で発生するポインタの書き込み操作に対してライトバリアコードを生成しないように指示します。
    *   コメント「`May run during STW, so write barriers are not allowed.`」が示すように、`stdcall`関数がGCのSTWフェーズ中に実行される可能性があるため、この期間中にライトバリアがトリガーされることを避けるために導入されました。これにより、STW中のGCの整合性が保たれます。

2.  **`mp.libcallg = gp` から `setGNoWriteBarrier(&mp.libcallg, gp)` への変更**:
    *   元のコードでは、現在のgoroutineポインタ`gp`を`mp.libcallg`フィールドに直接代入していました。この直接代入は、通常、コンパイラによってライトバリアが挿入される可能性があります。
    *   新しいコードでは、`setGNoWriteBarrier`というヘルパー関数が使用されています。この関数は、その名前が示す通り、ライトバリアをトリガーせずにポインタの代入を行います。
    *   コメント「`gp is on allg, so this WB can be eliminated.`」は、この変更の正当性を示しています。`gp`（現在のgoroutine）は、Goランタイムが管理する全てのgoroutineのリストである`allg`によって既に参照されています。`allg`はGCのルートセットの一部であるため、`gp`はGCによって常に到達可能であり、「生きている」と判断されます。したがって、`mp.libcallg`への`gp`の書き込みは、`gp`の生存期間を保証するためのものではなく、単にCPUプロファイラが一時的に`gp`を参照するためのものであるため、ライトバリアによる追加の保護は不要であり、むしろSTW中には有害であると判断されました。

これらの変更により、STWフェーズ中に`stdcall`が呼び出され、CPUプロファイラが`g`ポインタを記録する際に、GCの整合性を損なう可能性のあるライトバリアの実行が回避されます。これは、Goランタイムの堅牢性とGCの正確性を向上させるための重要な修正です。

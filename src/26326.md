# [インデックス 26326] ファイルの概要

このコミットは、Go言語の内部パッケージである `go/importer`、特に `gcimporter` におけるパッケージパスの解決ロジックを修正するものです。具体的には、ベンダーパッケージ（vendored packages）が存在する場合に、パッケージ宣言で見つかるパスと、`srcDir` からインポートされたパッケージが見つかる実際のパスとの間に不一致が生じる問題を解決し、正確なパッケージパスを使用するように変更しています。

## 元コミット内容

このコミットは、`src/go/internal/gcimporter/gcimporter.go` ファイル内の `FindPkg` 関数を変更しています。主な変更点は以下の通りです。

*   `id = path` という行が削除されました。これは、パッケージの識別子（`id`）を、`FindPkg` 関数に渡された生のパス（`path`）と直接的に関連付けていた部分です。
*   `bp.ImportPath` を使用して `id` を設定する行 `id = bp.ImportPath` が追加されました。これは、`go/build` パッケージが提供するビルド情報（`bp`）から取得したインポートパスを、パッケージの識別子として使用することを意味します。
*   デバッグ用のコードブロックが追加されましたが、`if false` で囲まれているため、通常は実行されません。これは、`path` と `id` が異なる場合にその違いを出力するもので、このコミットの意図（`path` と `id` が異なる可能性があること）を明確に示しています。

## 変更の背景

この変更の背景には、Go言語におけるベンダーパッケージ（vendoring）の導入と、それに関連するパッケージパスの解決の複雑さがあります。

Go言語では、プロジェクトが依存する外部パッケージを `vendor/` ディレクトリ内にコピーして管理する「ベンダーパッケージ」という仕組みがあります。これにより、ビルドの再現性が向上し、外部ネットワークへの依存が減ります。

しかし、ベンダーパッケージを使用する場合、`import "some/package"` のようなインポート文で指定される論理的なパスと、`go/build` パッケージが実際に解決するファイルシステム上のパス、そしてそのパッケージの「真の」インポートパス（`bp.ImportPath`）との間に差異が生じることがあります。

具体的には、`go/build` パッケージは、ベンダーパッケージを優先して解決し、その際の `ImportPath` には `vendor/` プレフィックスが含まれることがあります（例: `your_project/vendor/some/package`）。このコミット以前は、`gcimporter` がパッケージの識別子を単純に `FindPkg` に渡された `path` に設定していたため、ベンダーパッケージの実際のインポートパスと、`gcimporter` が内部的に使用するパッケージマップのキーとの間に不一致が生じ、コンパイラがパッケージを正しく識別できない可能性がありました。

このコミットは、この不一致を解消し、`gcimporter` が常に `go/build` パッケージによって解決された「正しい」インポートパス（`bp.ImportPath`）をパッケージの識別子として使用するようにすることで、ベンダーパッケージ環境下でのコンパイルの正確性を保証することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念と内部パッケージに関する知識が必要です。

1.  **Go言語のパッケージシステム**: Goのコードはパッケージにまとめられ、`import` 文を使って他のパッケージを参照します。各パッケージは一意のインポートパスによって識別されます。
2.  **`go/importer`**: Go言語の標準ライブラリの一部で、Goのソースコードを解析し、パッケージの型情報をインポートするためのインターフェースを提供します。コンパイラやツールが他のパッケージの情報を参照する際に利用されます。
3.  **`go/internal/gcimporter`**: `go/importer` インターフェースの実装の一つで、`gc` (Goコンパイラ) が生成するパッケージのエクスポートデータ（`.a` ファイルなどに含まれる）を読み込むための内部パッケージです。コンパイラの型チェックフェーズで重要な役割を果たします。
4.  **`go/build` パッケージ**: Goのソースコードをビルドする際に必要なパッケージ情報を収集するための標準ライブラリです。`go/build.Context` 構造体や `Import` メソッドなどを提供し、インポートパスからパッケージのソースディレクトリやビルドタグ、依存関係などを解決します。
5.  **ベンダーパッケージ (Vendoring)**: Go 1.5で導入され、Go 1.6でデフォルトで有効になった依存関係管理の仕組みです。プロジェクトのルートディレクトリにある `vendor/` ディレクトリ内に、プロジェクトが依存する外部パッケージのコピーを配置します。これにより、ビルド時に外部のGOPATHやモジュールキャッシュに依存せず、プロジェクト固有の依存関係セットを使用できます。
6.  **`bp.ImportPath`**: `go/build` パッケージの `Package` 構造体（通常 `bp` という変数名で参照される）のフィールドで、そのパッケージの正規のインポートパスを表します。ベンダーパッケージの場合、このパスには `vendor/` ディレクトリからの相対パスが含まれることがあります（例: `github.com/foo/bar/vendor/golang.org/x/text`）。

## 技術的詳細

`src/go/internal/gcimporter/gcimporter.go` 内の `FindPkg` 関数は、指定された `path` と `srcDir` に基づいて、パッケージのファイル名と識別子（`id`）を特定する役割を担っています。この関数は、`go/build` パッケージの機能を利用してパッケージ情報を解決しています。

変更前のコードでは、`FindPkg` 関数が `go/build` パッケージを使ってパッケージのビルド情報（`bp`）を取得した後、`id` を単純に `path` 引数の値に設定していました。

```go
// 変更前 (簡略化)
func FindPkg(path, srcDir string) (filename, id string) {
    // ... go/build を使って bp を取得 ...
    id = path // ここで id を生の path に設定
    // ...
    switch {
    case bp != nil:
        // ...
        noext = strings.TrimSuffix(bp.PkgObj, ".a")
    // ...
    }
    // ...
}
```

このアプローチは、ベンダーパッケージが存在しない環境では問題ありませんでした。しかし、ベンダーパッケージが導入されると、`path`（例えば `github.com/foo/bar`）と、`go/build` がベンダーディレクトリ内で見つけたパッケージの実際のインポートパス（`bp.ImportPath`、例えば `myproject/vendor/github.com/foo/bar`）が異なる場合があります。

`gcimporter` は、内部的にパッケージの識別子（`id`）をキーとしてパッケージ情報を管理するマップを使用しています。このマップのキーが、`import` 文で参照される論理的なパスと一致しない場合、コンパイラは正しいパッケージ情報を取得できず、型チェックエラーやリンクエラーを引き起こす可能性がありました。

このコミットでは、この問題を解決するために、`id` の設定方法を以下のように変更しました。

```go
// 変更後 (簡略化)
func FindPkg(path, srcDir string) (filename, id string) {
    // ... go/build を使って bp を取得 ...
    var noext string
    switch {
    case bp != nil:
        // ...
        noext = strings.TrimSuffix(bp.PkgObj, ".a")
        id = bp.ImportPath // ここで id を bp.ImportPath に設定
    // ...
    case build.IsLocalImport(path):
        // ...
    default: // "absolute" imports
        // ...
        noext = path
        id = path // ここでは path を id に設定 (ベンダーパッケージではない場合)
    }
    // ...
}
```

この変更により、`bp != nil` のケース（つまり `go/build` がパッケージ情報を正常に解決できた場合）では、`bp.ImportPath` が `id` として使用されるようになりました。`bp.ImportPath` は、ベンダーパッケージのコンテキストを考慮した、`go/build` が認識するパッケージの「真の」インポートパスです。これにより、`gcimporter` の内部マップが常に正しいキーを使用するようになり、ベンダーパッケージ環境下でのパッケージ解決の正確性が保証されます。

`build.IsLocalImport(path)` や `default` ケース（絶対インポート）では、`path` がそのまま `id` として使われ続けていますが、これはこれらのケースでは `path` と `bp.ImportPath` が一致するか、ベンダーパッケージの考慮が不要なためです。

## コアとなるコードの解説

変更の中心は、`FindPkg` 関数内でパッケージの識別子 `id` を設定するロジックです。

1.  **`id = path` の削除**:
    `FindPkg` 関数の冒頭近くにあった `id = path` の行が削除されました。これは、パッケージの識別子を、関数に渡された生のインポートパス `path` に無条件に設定していた部分です。ベンダーパッケージのシナリオでは、この `path` が `gcimporter` が内部的に必要とする「正しい」識別子と異なる場合があるため、この直接的な割り当ては不適切と判断されました。

2.  **`id = bp.ImportPath` の追加**:
    `go/build` パッケージの `Import` 関数が成功し、`bp` (build.Package) オブジェクトが有効な場合に、`id` が `bp.ImportPath` に設定されるようになりました。
    `bp.ImportPath` は、`go/build` パッケージが解決した、ベンダーパッケージのコンテキストを考慮した正規のインポートパスです。例えば、`github.com/foo/bar` というパッケージが `myproject/vendor/github.com/foo/bar` にベンダーされている場合、`bp.ImportPath` は `myproject/vendor/github.com/foo/bar` のような値になります。これにより、`gcimporter` はベンダーパッケージをその「真の」インポートパスで識別できるようになります。

3.  **`default` ケースでの `id = path` の維持**:
    `switch` ステートメントの `default` ケース（主に絶対パスでのインポートを扱う）では、`id = path` が維持されています。これは、これらのケースでは `path` がそのままパッケージの識別子として適切であるためです。ベンダーパッケージの解決は通常 `bp != nil` のケースで処理されるため、この部分の変更は不要です。

4.  **デバッグ用コードの追加**:
    `if false { ... }` で囲まれたデバッグ用のコードブロックが追加されました。これは、`path` と `id` が異なる場合にその両方を出力するものです。このコードは実行されないものの、コミットの作者が `path` と `id` の間に差異が生じる可能性を認識しており、その差異を「修正」することがこのコミットの目的であることを示唆しています。

この変更により、`gcimporter` は、特にベンダーパッケージを使用するGoプロジェクトにおいて、パッケージのインポートパスをより正確に解決し、コンパイラの型チェックとビルドプロセス全体の堅牢性を向上させます。

# [インデックス 25526] ファイルの概要

このコミットは、Goランタイムにおける`memmove`および`memclr`のアセンブリ実装を修正し、ポインタの移動およびゼロクリア操作がアトミックに行われるようにすることで、データ競合やガベージコレクタ（GC）による不正なポインタの読み取りを防ぐことを目的としています。特に、ポインタサイズのメモリ領域に対する操作において、部分的な更新状態（"torn pointer"）が発生するリスクを排除します。

## 元コミット内容

Goランタイムにおいて、`memmove`および`memclr`関数がポインタをアトミックに移動またはゼロクリアするように修正します。ポインタサイズ（32ビットシステムでは4バイト、64ビットシステムでは8バイト）の倍数であり、かつポインタアラインメントされているメモリ領域にはポインタが含まれる可能性があります。これまでのコードは概ね問題ありませんでしたが、特に1ポインタサイズの移動において問題がありました。この変更はIssue #13160を修正し、Issue #12552に関連する更新です。

## 変更の背景

Go言語は、ガベージコレクション（GC）と並行処理を特徴とするモダンなプログラミング言語です。Goランタイムは、メモリ管理、ゴルーチンのスケジューリング、低レベルのメモリ操作などを担当しています。`memmove`（メモリブロックのコピー）や`memclr`（メモリブロックのゼロクリア）といった関数は、Goの内部で頻繁に使用され、特にスライスのコピーや初期化、GCのマークフェーズなどで重要な役割を果たします。

このコミットが行われた2015年当時、Goランタイムの`memmove`や`memclr`のアセンブリ実装において、ポインタサイズのメモリ領域を操作する際に、その操作が複数のアセンブリ命令に分割される可能性がありました。例えば、4バイトのポインタを書き込む際に、上位2バイトと下位2バイトが別々の命令で書き込まれるようなケースです。

このような非アトミックな操作は、並行処理環境において深刻な問題を引き起こす可能性があります。
1.  **ガベージコレクタとの競合**: GoのGCは、プログラムの実行と並行してメモリをスキャンし、到達可能なオブジェクトを特定します。もしGCがポインタをスキャンしている最中に、そのポインタが非アトミックに更新され、部分的に書き換えられた状態（"torn pointer"）をGCが観測してしまうと、GCは不正なメモリ位置を指していると判断したり、存在しないオブジェクトを指していると誤解したりする可能性があります。これはメモリ破損、プログラムのクラッシュ、またはGCの誤動作につながります。
2.  **他のゴルーチンとの競合**: 複数のゴルーチンが同じメモリ領域のポインタに同時にアクセスし、一方が書き込み、もう一方が読み込みを行う場合、読み込み側のゴルーチンが"torn pointer"を読み取ってしまう可能性があります。これもまた、プログラムの予期せぬ動作やデータ破損の原因となります。

このコミットは、特に「1ポインタサイズの移動」においてこの問題が発生していたことを指摘しており、その修正を目的としています。

## 前提知識の解説

### Goランタイム

Goランタイムは、Goプログラムの実行環境を提供するソフトウェア層です。これには、ガベージコレクタ、ゴルーチンとチャネルのスケジューラ、メモリ割り当て、低レベルのシステムコールインターフェースなどが含まれます。Goプログラムのパフォーマンスと安全性は、このランタイムの効率性と正確性に大きく依存しています。`memmove`や`memclr`のような関数は、ランタイムのコア部分であり、Goの組み込み関数（例: `copy`）やスライスの操作などで内部的に利用されます。

### memmoveとmemclr

*   **`memmove`**: メモリブロックをソースアドレスからデスティネーションアドレスへコピーする関数です。C言語の`memmove`と同様に、ソースとデスティネーションのメモリ領域が重なっている場合でも正しく動作するように設計されています。Goでは、`copy`組み込み関数やスライスの拡張（`append`など）の際に内部的に使用されます。
*   **`memclr`**: 指定されたメモリブロックをゼロで埋める関数です。Goでは、`make`で新しいスライスが作成されたり、スライスが再利用のためにクリアされたりする際に内部的に使用されます。

これらの関数はパフォーマンスが非常に重要であるため、多くの場合、特定のCPUアーキテクチャ向けにアセンブリ言語で最適化された実装が提供されます。

### アトミック操作

アトミック操作とは、複数のスレッドやプロセッサから同時にアクセスされた場合でも、その操作全体が中断されることなく、単一の不可分な操作として実行されることを保証するものです。これにより、操作の途中の状態が他のスレッドから観測されることがなく、データの一貫性が保たれます。

Goでは、`sync/atomic`パッケージを通じてアトミック操作が提供されていますが、ランタイム内部の低レベルなメモリ操作では、CPUの提供するアトミック命令（例: `MOV`命令が特定のサイズでアラインメントされたメモリに対してアトミックに動作する場合）を直接利用することがあります。ポインタのような共有されるデータ構造に対しては、アトミックな読み書きが不可欠です。

### ガベージコレクション (GC)

Goのガベージコレクタは、不要になったメモリを自動的に解放するシステムです。GoのGCは、並行（concurrent）かつ三色マーク＆スイープアルゴリズムをベースとしています。GCはアプリケーションの実行と並行して動作し、メモリグラフを走査して到達可能なオブジェクト（ライブオブジェクト）を特定します。

GCがメモリをスキャンしている最中に、ポインタが非アトミックに更新されると、GCは「部分的に書き換えられたポインタ」（torn pointer）を読み取ってしまう可能性があります。これは、ポインタが指すべきアドレスの一部だけが更新され、残りが古い値のままになっている状態です。このような状態のポインタをGCが追跡しようとすると、不正なメモリ領域にアクセスしたり、クラッシュを引き起こしたりする原因となります。したがって、GCの正確な動作を保証するためには、ポインタの読み書きが常にアトミックに行われることが極めて重要です。

## 技術的詳細

このコミットの核心は、`memmove`と`memclr`のアセンブリ実装において、ポインタサイズのメモリ操作を確実にアトミックにする点にあります。

従来のコードでは、メモリブロックのサイズに応じて処理を分岐させていましたが、特にポインタサイズ（32ビット環境では4バイト、64ビット環境では8バイト）の領域を処理する際に、複数の命令にまたがって書き込みが行われる可能性がありました。

この修正では、以下の変更が導入されています。

1.  **分岐ロジックの変更**:
    *   多くのアセンブリファイルで、`JBE` (Jump if Below or Equal) 命令が`CMPL`/`CMPQ`命令と組み合わせて使用されていました。これは「指定されたサイズ以下の場合にジャンプ」を意味します。
    *   この`JBE`を`JB` (Jump if Below) と`JE` (Jump if Equal) に分割することで、特定のサイズ（例えば4バイトや8バイト）に対して厳密に一致するケースを分離し、専用の処理パスを設けています。
    *   例: `CMPL BX, $4` の後に `JBE _3or4` だった箇所が、`JB _3` と `JE _4` に変更されています。これにより、サイズが3バイトの場合と4バイトの場合で異なる処理に分岐できるようになります。

2.  **アトミックな命令の使用**:
    *   分離された4バイトまたは8バイトのケースでは、`MOVL` (Move Long, 4バイト) や `MOVQ` (Move Quad, 8バイト) といった、そのアーキテクチャにおけるポインタサイズに合わせた単一の命令でメモリを操作するように変更されています。
    *   これらの命令は、適切にアラインメントされたメモリに対しては、CPUによってアトミックに実行されることが保証されています。これにより、GCや他のゴルーチンが部分的に更新されたポインタを観測するリスクがなくなります。

3.  **コメントによる補足**:
    *   `src/runtime/asm_amd64p32.s`と`src/runtime/memmove_nacl_amd64p32.s`には、`STOSB`や`MOVSB`（バイト単位の操作）がポインタを操作しないように、テール処理が4バイト単位で行われることを明記するコメントが追加されています。これは、ポインタを含む可能性のあるメモリ領域に対しては、バイト単位の非アトミックな操作を避けるという設計意図を強調しています。

これらの変更により、Goランタイムはポインタの整合性をより確実に保ち、並行処理環境下での安定性と信頼性を向上させています。

### アセンブリファイルの変更 (`memclr_386.s`の例)

`src/runtime/memclr_386.s`の変更を例に取ると、以下のようになっています。

```diff
--- a/src/runtime/memclr_386.s
+++ b/src/runtime/memclr_386.s
@@ -21,7 +21,8 @@ tail:
 	CMPL	BX, $2
 	JBE	_1or2
 	CMPL	BX, $4
-	JBE	_3or4
+	JB	_3
+	JE	_4
 	CMPL	BX, $8
 	JBE	_5through8
 	CMPL	BX, $16
@@ -68,9 +69,13 @@ _1or2:
 	RET
 _0:
 	RET
-_3or4:
+_3:
 	MOVW	AX, (DI)
-\tMOVW	AX, -2(DI)(BX*1)
+	MOVB	AX, 2(DI)
+	RET
+_4:
+	// We need a separate case for 4 to make sure we clear pointers atomically.
+	MOVL	AX, (DI)
 	RET
 _5through8:
 	MOVL	AX, (DI)
```

*   **分岐ロジックの変更**: 以前は`CMPL BX, $4`の後に`JBE _3or4`（BXが4以下なら`_3or4`へジャンプ）となっていました。これが`JB _3`（BXが4未満なら`_3`へジャンプ）と`JE _4`（BXが4と等しいなら`_4`へジャンプ）に分割されています。これにより、サイズが厳密に4バイトの場合（`_4`ラベル）と、3バイト以下の場合（`_3`ラベル）を区別できるようになりました。
*   **アトミックな4バイトクリア**: 新しく追加された`_4:`ラベルのセクションでは、`MOVL AX, (DI)`という命令が使用されています。386アーキテクチャではポインタが4バイトであるため、この`MOVL`命令は4バイトのメモリを単一のアトミックな操作でゼロクリアします。これにより、GCが部分的にクリアされたポインタを観測するリスクがなくなります。
*   同様の変更が、`memclr`および`memmove`の他のアーキテクチャ（amd64, plan9_386, plan9_amd64）向けのアセンブリファイルにも適用されています。amd64アーキテクチャではポインタが8バイトであるため、`MOVQ`命令がアトミックな8バイト操作に使用されます。

### テストファイルの追加 (`test/fixedbugs/issue13160.go`)

このコミットでは、修正が正しく機能することを検証するための新しいテストケース`issue13160.go`が追加されています。

```go
// run

// Copyright 2015 The Go Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package main

import (
	"fmt"
	"runtime"
)

const N = 100000

func main() {
	// Allocate more Ps than processors.  This raises
	// the chance that we get interrupted by the OS
	// in exactly the right (wrong!) place.
	p := runtime.NumCPU()
	runtime.GOMAXPROCS(2 * p)

	// Allocate some pointers.
	ptrs := make([]*int, p)
	for i := 0; i < p; i++ {
		ptrs[i] = new(int)
	}

	// Arena where we read and write pointers like crazy.
	collider := make([]*int, p)

	done := make(chan struct{}, 2*p)

	// Start writers.  They alternately write a pointer
	// and nil to a slot in the collider.
	for i := 0; i < p; i++ {
		i := i
		go func() {
			for j := 0; j < N; j++ {
				// Write a pointer using memmove.
				copy(collider[i:i+1], ptrs[i:i+1])
				// Write nil using memclr.
				// (This is a magic loop that gets lowered to memclr.)
				r := collider[i : i+1]
				for k := range r {
					r[k] = nil
				}
			}
			done <- struct{}{}
		}()
	}
	// Start readers.  They read pointers from slots
	// and make sure they are valid.
	for i := 0; i < p; i++ {
		i := i
		go func() {
			for j := 0; j < N; j++ {
				var ptr [1]*int
				copy(ptr[:], collider[i:i+1])
				if ptr[0] != nil && ptr[0] != ptrs[i] {
					panic(fmt.Sprintf("bad pointer read %p!", ptr[0]))
				}
			}
			done <- struct{}{}
		}()
	}
	for i := 0; i < 2*p; i++ {
		<-done
	}
}
```

*   **競合状態の誘発**:
    *   `runtime.GOMAXPROCS(2 * p)`を設定することで、利用可能なCPUコア数よりも多くのP（プロセッサ）をGoスケジューラに割り当てます。これにより、ゴルーチンのコンテキストスイッチが頻繁に発生し、OSによる割り込みの機会が増え、非アトミックな操作中に競合状態が発生する可能性が高まります。
    *   `ptrs`スライスには、`new(int)`で作成された有効なポインタが格納されます。
    *   `collider`スライスは、複数のゴルーチンによって同時に読み書きされる共有メモリ領域として機能します。
*   **ライターゴルーチン**:
    *   `p`個のライターゴルーチンが起動されます。
    *   各ライターは、`N`回ループを実行し、`collider`スロットに対して以下の操作を交互に行います。
        *   `copy(collider[i:i+1], ptrs[i:i+1])`: `ptrs`から有効なポインタを`collider`にコピーします。この`copy`操作は内部的に`runtime.memmove`を呼び出します。
        *   `for k := range r { r[k] = nil }`: `collider`スロットを`nil`でクリアします。このループはGoコンパイラによって`runtime.memclr`に最適化されます。
*   **リーダーゴルーチン**:
    *   `p`個のリーダーゴルーチンが起動されます。
    *   各リーダーは、`N`回ループを実行し、`collider`スロットからポインタを読み取ります。
    *   `copy(ptr[:], collider[i:i+1])`: `collider`からポインタを読み取ります。
    *   `if ptr[0] != nil && ptr[0] != ptrs[i] { panic(...) }`: 読み取ったポインタ`ptr[0]`が`nil`でもなく、元の有効なポインタ`ptrs[i]`でもない場合、それは"torn pointer"である可能性が高いため、`panic`を発生させます。
*   **テストの目的**: このテストは、`memmove`や`memclr`がポインタを非アトミックに操作していた場合に発生しうる、部分的に書き換えられたポインタの読み取り（"torn pointer"）を検出することを目的としています。修正が適用されていれば、`panic`は発生せず、テストは成功します。

このテストは、Goランタイムの低レベルなメモリ操作におけるポインタの整合性を保証するために、非常に重要な役割を果たしています。

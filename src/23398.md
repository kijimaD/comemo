# [インデックス 23398] ファイルの概要

## コミット
`f85a05581eadda1512a9bb5ae63098f3e1772f54` は、GoランタイムにおけるPlan 9環境でのシグナルハンドリングのバグを修正するコミットです。具体的には、シグナルキューに渡されたポインタが、シグナルハンドラが処理する時点では無効になっている可能性があった問題を解決しています。

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/f85a05581eadda1512a9bb5ae63098f3e1772f54](https://github.com/golang/go/commit/f85a05581eadda1512a9bb5ae63098f3e1772f54)

## 元コミット内容

```
runtime: fix signal handling on Plan 9

Once added to the signal queue, the pointer passed to the
signal handler could no longer be valid. Instead of passing
the pointer to the note string, we recopy the value of the
note string to a static array in the signal queue.

Fixes #10784.

Change-Id: Iddd6837b58a14dfaa16b069308ae28a7b8e0965b
Reviewed-on: https://go-review.googlesource.com/9950
Reviewed-by: Brad Fitzpatrick <bradfitz@golang.org>
```

## 変更の背景

Plan 9オペレーティングシステムでは、シグナルは「ノート（notes）」と呼ばれる文字列メッセージとして処理されます。Goランタイムは、これらのノートを処理するために内部的なシグナルキューを使用しています。このコミット以前は、ノート文字列へのポインタがシグナルキューに格納されていました。しかし、このポインタが指すメモリ領域が、シグナルハンドラが実際にそのノートを処理する前に解放されたり、別のデータで上書きされたりする可能性がありました。これにより、シグナルハンドラが不正なメモリにアクセスし、クラッシュや予期せぬ動作を引き起こす可能性がありました。

この問題は、Issue #10784 で報告されており、ポインタの有効性が失われることによる不安定性が指摘されていました。特に、シグナルハンドラは非同期に実行されるため、ポインタが指すデータがいつまで有効であるかという保証が難しいという根本的な問題がありました。シグナルハンドラ内では、メモリ割り当てのような操作が制限されることが多く、ポインタが指すデータがいつまで有効であるかという保証が難しい状況でした。このため、ポインタをそのままキューに格納する設計では、競合状態やダングリングポインタの問題が発生するリスクがありました。

## 前提知識の解説

### Plan 9のシグナル（ノート）

Plan 9オペレーティングシステムにおけるシグナルは、他のUnix系システムとは異なり、「ノート（notes）」と呼ばれる文字列メッセージとして実装されています。プロセスは `notify` システムコールを使って他のプロセスにノートを送信したり、カーネルが特定のイベント（例: ゼロ除算、不正なメモリアクセス、I/Oエラーなど）が発生した際にプロセスにノートを送信したりします。プロセスは `noted` システムコールを使ってノートハンドラを設定し、これらのノートを捕捉・処理することができます。ノートは単なる数値ではなく、具体的なイベント内容を示す文字列であるため、より詳細な情報伝達が可能です。例えば、「interrupt」や「hangup」といった文字列がノートとして送信されます。

### Goランタイムのシグナルハンドリング

Goランタイムは、OSからのシグナル（Plan 9の場合はノート）を捕捉し、Goのユーザーレベルのシグナルハンドラにディスパッチする役割を担っています。これは、GoプログラムがOSのシグナルを適切に処理し、例えばクリーンシャットダウンやデバッグ情報の出力などを行うために不可欠です。ランタイム内部では、シグナルを一時的に保持するためのキューが使用されることがあります。これは、シグナルが高速に連続して発生した場合や、シグナルハンドラがすぐに処理できない場合に、シグナルを見落とさないようにするためです。Goの `os/signal` パッケージは、Plan 9を含む様々なOSのシグナルを抽象化し、Goのチャネルを通じてプログラムに通知する機能を提供しています。

### ポインタの有効性

C言語のような低レベル言語では、メモリ上のデータへのポインタを直接扱います。ポインタが指すメモリ領域が解放されたり、別のデータで上書きされたりすると、そのポインタは「ダングリングポインタ」となり、不正なメモリにアクセスする原因となります。シグナルハンドラのような非同期処理では、メインのプログラムフローとは独立して実行されるため、ポインタの有効性を保証することが特に難しくなります。シグナルハンドラが実行されるコンテキストは非常に制限されており、通常のメモリ割り当てや複雑なライブラリ関数の呼び出しは安全ではありません（非同期シグナルセーフティの原則）。そのため、シグナルハンドラ内で使用されるデータは、事前に確保された静的な領域に格納されるか、アトミックな操作で安全にアクセスできる必要があります。

## 技術的詳細

このコミットの核心は、Plan 9のシグナルキューにおけるノート文字列の扱い方を、ポインタ渡しから値渡し（コピー）に変更した点にあります。これにより、シグナルハンドラがノートを処理する際に、そのデータが常に有効であることが保証されます。

1.  **`noteData` 構造体の導入**:
    *   以前は `[qsize]*byte` 型でノート文字列へのポインタを直接格納していましたが、`noteData` という新しい構造体が導入されました。
    *   `noteData` は `[_ERRMAX]byte` 型の固定長バイト配列 `s` と、その配列に格納されている有効なバイト数を示す `n` を持ちます。`_ERRMAX` はPlan 9におけるエラーメッセージの最大長を定義する定数であり、ノート文字列の最大長をカバーします。これにより、ノート文字列のデータを直接格納するための十分な領域が確保されます。この固定長バッファを使用することで、シグナルハンドラ内で動的なメモリ割り当てを行う必要がなくなり、非同期シグナルセーフティの要件を満たします。

2.  **`noteQueue.data` の型変更**:
    *   `noteQueue` 構造体の `data` フィールドの型が `[qsize]*byte` から `[qsize]noteData` に変更されました。これにより、キューはノート文字列へのポインタではなく、ノート文字列の実際のデータ（コピー）を保持するようになりました。

3.  **`noteQueue.push` メソッドの変更**:
    *   `push` メソッドは、引数として受け取った `*byte` 型のノート文字列ポインタから、`gostringnocopy` を使ってGoの文字列に変換します。`gostringnocopy` は、既存のバイト配列から新しいメモリを割り当てずにGoの文字列スライスを作成するGoランタイム内部の関数です。
    *   その後、その文字列の内容を `noteData` 構造体の `s` フィールドに `copy` 関数を使ってコピーし、`n` フィールドに文字列の長さを設定します。
    *   この変更により、シグナルハンドラが呼び出される時点で元のポインタが指すメモリが解放されていても、キューに格納されたデータは常に有効であることが保証されます。シグナルハンドラ内でのメモリ割り当てが禁止されているため、この静的な配列へのコピーは重要な解決策です。

4.  **`noteQueue.pop` メソッドの変更**:
    *   `pop` メソッドは、キューから `noteData` 構造体を取り出し、その `s` フィールドと `n` フィールドを使ってGoの文字列を再構築して返します。
    *   以前は `*byte` を直接返していましたが、変更後は `string` 型を返すようになりました。これにより、呼び出し元は常に有効な文字列データを受け取ることができます。

5.  **`signal_recv` 関数の変更**:
    *   `signal_recv` 関数は `sig.q.pop()` の戻り値の型変更に合わせて修正されました。以前は `*byte` 型のポインタが `nil` かどうかでノートの有無を判断していましたが、変更後は `string` 型の戻り値が空文字列 `""` かどうかで判断するようになりました。
    *   `return gostring(note)` も `return note` に変更され、`pop` 関数が直接 `string` を返すようになったことに対応しています。

これらの変更により、シグナルキューに格納されるノート文字列は常に有効なデータとして扱われるようになり、ポインタの有効性に関する問題が解消されました。これは、Plan 9のノートシステムとGoランタイムのシグナルハンドリングの間の堅牢性を高める上で重要な改善です。

## コアとなるコードの解説

### `type noteData struct { ... }` の追加
この新しい構造体は、Plan 9のノート文字列を格納するためのコンテナです。
*   `s [_ERRMAX]byte`: ノート文字列のバイトデータを格納する固定長配列です。`_ERRMAX` はPlan 9システムで定義されているエラーメッセージ（ノート）の最大長であり、これにより十分なバッファが確保されます。
*   `n int`: `s` 配列のうち、実際に有効なノート文字列のバイト数を示します。これにより、文字列の実際の長さを追跡できます。

### `type noteQueue struct { ... }` の変更
`data` フィールドの型が `[qsize]*byte` から `[qsize]noteData` に変更されました。
*   **変更前**: `data [qsize]*byte` は、ノート文字列へのポインタの配列でした。これにより、ポインタが指すメモリがいつまで有効であるかという問題が発生していました。
*   **変更後**: `data [qsize]noteData` は、`noteData` 構造体の配列です。これにより、ノート文字列のデータそのものがキュー内にコピーされ、ポインタの有効性に関する問題が解消されます。

### `func (q *noteQueue) push(item *byte) bool { ... }` の変更
この関数は、新しいノートをキューに追加する役割を担います。
*   **変更前**: `q.data[q.wi] = item` は、引数 `item` (ノート文字列へのポインタ) をそのままキューに格納していました。
*   **変更後**:
    1.  `s := gostringnocopy(item)`: `item` が指すバイト列からGoの文字列 `s` を作成します。この関数はメモリを新たに割り当てずに文字列を作成するため、シグナルハンドラ内でのメモリ割り当て制限に準拠しています。
    2.  `copy(q.data[q.wi].s[:], s)`: 作成したGoの文字列 `s` の内容を、キューの現在の書き込み位置 `q.wi` にある `noteData` 構造体の `s` フィールド（バイト配列）にコピーします。
    3.  `q.data[q.wi].n = len(s)`: コピーした文字列の長さを `noteData` 構造体の `n` フィールドに保存します。
    この変更により、ノート文字列のデータがキュー内に完全にコピーされるため、元のポインタの有効性に依存しなくなります。

### `func (q *noteQueue) pop() string { ... }` の変更
この関数は、キューからノートを取り出す役割を担います。
*   **変更前**: `func (q *noteQueue) pop() *byte` は、キューから `*byte` 型のポインタを返していました。キューが空の場合は `nil` を返していました。
*   **変更後**:
    1.  `func (q *noteQueue) pop() string`: 戻り値の型が `string` に変更されました。キューが空の場合は空文字列 `""` を返します。
    2.  `note := &q.data[q.ri]`: キューの現在の読み込み位置 `q.ri` にある `noteData` 構造体へのポインタを取得します。
    3.  `item := string(note.s[:note.n])`: `noteData` 構造体の `s` フィールド（バイト配列）と `n` フィールド（長さ）を使って、Goの文字列を再構築します。これにより、呼び出し元は常に有効な文字列データを受け取ることができます。

### `func signal_recv() string { ... }` の変更
この関数は、シグナル（ノート）を受信するループです。
*   `note := sig.q.pop()` の戻り値の型が `string` に変更されたため、その後の条件分岐も `note != nil` から `note != ""` に変更されました。
*   `return gostring(note)` も `return note` に変更され、`pop` 関数が直接 `string` を返すようになったことに対応しています。

これらの変更は、シグナルハンドラが非同期に動作し、かつメモリ割り当てが制限されるというPlan 9環境の特性を考慮し、データの安全性を確保するための重要な修正です。

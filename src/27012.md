# [インデックス 27012] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおける命令スケジューリングメカニズムを改善することを目的としています。具体的には、デバッグ情報とレジスタ割り当ての効率を高めるために、従来の単純な優先度キューを、`container/heap`パッケージを利用した本格的なヒープベースの優先度キューに置き換えています。これにより、命令のスケジューリング順序をより細かく制御できるようになり、結果としてレジスタスピル（レジスタに収まらない値をメモリに退避させること）の削減とコードサイズの縮小が実現されています。

## 変更の背景

Goコンパイラのバックエンドでは、プログラムをSSA (Static Single Assignment) 形式に変換した後、機械語に変換する前に様々な最適化を行います。この過程で重要なのが、命令のスケジューリングとレジスタ割り当てです。命令スケジューリングは、プログラムの実行順序を最適化し、パイプラインのストールを減らしたり、レジスタの競合を緩和したりすることを目的とします。レジスタ割り当ては、プログラム中の変数をCPUの高速なレジスタに割り当てることで、メモリへのアクセスを減らし、実行速度を向上させます。

しかし、レジスタの数は限られているため、全ての変数をレジスタに割り当てることはできません。レジスタに割り当てられなかった変数は、メモリに「スピル」（退避）されます。スピルはメモリへのアクセスを伴うため、プログラムの実行速度を低下させ、コードサイズを増加させる原因となります。

このコミットの背景には、Goコンパイラの命令スケジューリングがレジスタ割り当ての効率に与える影響を改善したいという意図があります。特に、従来のスケジューラが単純な優先度付けに留まっていたため、より洗練されたヒューリスティックを適用し、レジスタスピルを減らすことで、最終的な生成コードのサイズを削減することが目標とされました。コミットメッセージでは、コードサイズ削減をレジスタ割り当てからのスピル削減の指標としています。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式
SSA形式は、コンパイラ最適化で広く用いられる中間表現（IR）の一種です。SSA形式では、全ての変数が一度だけ定義されるという特性を持ちます。これにより、データフロー解析が容易になり、様々な最適化（デッドコード削除、共通部分式削除など）を効率的に適用できます。GoコンパイラのバックエンドもSSA形式を採用しています。

### 2. 命令スケジューリング
命令スケジューリングは、プログラムの命令を、データ依存性やリソース制約（CPUの実行ユニット、レジスタなど）を考慮しつつ、最適な順序で並べ替えるコンパイラ最適化技術です。目的は、CPUのパイプライン効率を最大化し、実行時間を短縮することです。このコミットでは、特にレジスタ割り当ての効率向上に焦点を当てています。

### 3. レジスタ割り当て (Register Allocation)
レジスタ割り当ては、プログラム中の変数をCPUのレジスタに割り当てるプロセスです。レジスタはメモリよりもはるかに高速なため、レジスタに割り当てられた変数へのアクセスは高速です。しかし、レジスタの数は限られているため、全ての変数をレジスタに割り当てることはできません。

### 4. レジスタスピル (Register Spilling)
レジスタスピルは、レジスタに割り当てきれなかった変数の値を、一時的にメモリ（通常はスタック）に退避させる操作です。スピルが発生すると、その変数を再度使用する際にメモリからレジスタにロードし直す必要があり、これが性能低下の原因となります。スピルを減らすことは、コンパイラ最適化の重要な目標の一つです。

### 5. 優先度キュー (Priority Queue)
優先度キューは、要素に優先度が割り当てられており、最も優先度の高い要素から順に取り出されるデータ構造です。このコミットでは、命令をスケジューリングする際に、どの命令を次に処理すべきかを決定するために優先度キューが使用されます。Go言語では、`container/heap`パッケージを使ってヒープベースの優先度キューを実装できます。

### 6. ヒューリスティック (Heuristics)
ヒューリスティックとは、厳密な最適解を保証しないが、経験則に基づいて実用的な解を効率的に見つけるための手法です。このコミットでは、命令スケジューリングの優先度を決定するために様々なヒューリスティックが試され、コードサイズ削減に最も効果的なものが採用されています。

### 7. Go SSAにおける特定の`Value`操作
GoのSSAバックエンドでは、プログラム中の各操作や値を`Value`という構造体で表現します。
- **`OpPhi`**: 複数の制御フローパスが合流する点で、異なるパスから来る同じ変数の値を結合するために使用される特殊な操作（Phi関数）。通常、ブロックの先頭に配置されます。
- **`OpVarDef`**: 変数の定義を表す操作。
- **`OpAMD64LoweredGetClosurePtr`**: AMD64アーキテクチャにおいて、クロージャのポインタを取得する操作。エントリブロックで可能な限り早くスケジューリングされるべき特殊なケースです。
- **`v.Type.IsMemory()`**: `Value`がメモリ操作（ストアなど）を表すかどうかを判定します。ストア操作はレジスタ圧力を減らすために早くスケジューリングされる傾向があります。
- **`v.Type.IsFlags()`**: `Value`がCPUのフラグレジスタに影響を与える操作を表すかどうかを判定します。フラグ操作は、フラグレジスタのライブ期間を短く保つために、可能な限り遅くスケジューリングされる傾向があります。

## 技術的詳細

このコミットの主要な技術的変更点は、GoコンパイラのSSAバックエンドにおける命令スケジューリングアルゴリズムの改善です。

1.  **ヒープベースの優先度キューの導入**:
    従来のスケジューラは、おそらく固定サイズの配列や単純なリストの集合を用いて、スコアに基づいて命令をバケットに分類し、そこから取り出すという方式でした。これは「優先度キュー」と呼べるものの、要素の追加や削除の効率が悪い場合がありました。
    このコミットでは、Go標準ライブラリの`container/heap`パッケージを利用して、本格的なヒープベースの優先度キュー`ValHeap`を導入しました。ヒープは、要素の追加（`Push`）と最小（または最大）要素の削除（`Pop`）を対数時間O(log n)で行えるため、大規模なブロックにおけるスケジューリングの効率が向上します。

2.  **洗練されたスケジューリングヒューリスティック**:
    `ValHeap`の`Less`メソッド内で、命令の優先度を決定するための新しいヒューリスティックが実装されました。これは、複数の基準を組み合わせて命令の相対的な順序を決定します。
    -   **`score`**: 各`Value`に割り当てられた静的な優先度（`ScorePhi`, `ScoreVarDef`, `ScoreMemory`, `ScoreFlags`, `ScoreDefault`など）。スコアが高いほど、ブロックの終わりに近い位置にスケジューリングされます（逆順に構築されるため）。
    -   **`Line`番号**: デバッグのしやすさのため、同じスコアの命令はソースコードの行番号順にスケジューリングされます。
    -   **引数の数**: `OpPhi`以外の命令では、引数の数が少ない命令が優先されます。これは、引数が多い命令はより多くのレジスタを必要とする可能性があり、レジスタ圧力を考慮したものです。
    -   **`ID`**: 最終的なタイブレークとして、`Value`のユニークなIDが使用されます。

3.  **ストア操作の早期スケジューリング**:
    コミットメッセージで言及されているように、「stores-early heuristic」がレジスタ圧力の軽減に役立つことが確認されています。これは、メモリへの書き込み（ストア）操作を可能な限り早くスケジューリングすることで、その値がレジスタを占有する期間を短くし、他の値がレジスタを使用できる機会を増やす効果があります。`ScoreMemory`がこの目的のために使用されます。

4.  **フラグ操作の遅延スケジューリング**:
    CPUのフラグレジスタに影響を与える操作（例: 比較命令）は、`ScoreFlags`が割り当てられ、可能な限り遅くスケジューリングされます。これにより、フラグレジスタのライブ期間が短くなり、フラグレジスタの競合が緩和されます。

5.  **コードサイズ削減の評価**:
    この変更の主な評価指標は、生成されるバイナリのコードサイズ削減です。これは、レジスタスピルの減少を直接的に反映すると考えられています。コミットメッセージには、`vet`ツールを含む様々なGoツールで、全体として約0.1%のテキストサイズ削減が達成された具体的な数値が示されています。これは、コンパイラの最適化としては無視できない改善です。

## コアとなるコードの変更箇所

変更は主に `src/cmd/compile/internal/ssa/schedule.go` ファイルに集中しています。

-   **`import "container/heap"` の追加**: Go標準ライブラリのヒープ実装を使用するために必要です。
-   **`ValHeap` 構造体の定義と `heap.Interface` の実装**:
    ```go
    type ValHeap struct {
    	a    []*Value
    	less func(a, b *Value) bool
    }

    func (h ValHeap) Len() int      { return len(h.a) }
    func (h ValHeap) Swap(i, j int) { a := h.a; a[i], a[j] = a[j], h.a[i] }
    func (h *ValHeap) Push(x interface{}) {
    	v := x.(*Value)
    	h.a = append(h.a, v)
    }
    func (h *ValHeap) Pop() interface{} {
    	old := h.a
    	n := len(old)
    	x := old[n-1]
    	h.a = old[0 : n-1]
    	return x
    }
    func (h ValHeap) Less(i, j int) bool { return h.less(h.a[i], h.a[j]) }
    ```
    この構造体は、`*Value`のスライスを保持し、`heap.Interface`を満たすメソッド（`Len`, `Swap`, `Push`, `Pop`, `Less`）を実装しています。特に`Less`メソッドは、コンストラクタで渡される`less`関数ポインタによって動的に優先度比較ロジックを決定します。
-   **`uses` と `score` スライスの型変更**:
    `uses`が `[]int` から `[]int32` に、`score`が `[]uint8` から `[]int8` に変更されています。これは、メモリ効率や特定の操作の都合によるものと考えられます。
-   **スコア計算ロジックの移動**:
    各`Value`の`score`を計算する`switch`文が、各ブロックのスケジューリングループの前に移動され、一度に全ての`Value`のスコアが計算されるようになりました。
-   **優先度キューの初期化と操作の変更**:
    従来の`priq [ScoreCount][]*Value`という配列ベースの優先度キューの代わりに、`ValHeap`インスタンスが作成され、`heap.Push`と`heap.Pop`関数が使用されるようになりました。
    ```go
    // 旧
    // var priq [ScoreCount][]*Value
    // priq[s] = append(priq[s], v)

    // 新
    priq := &ValHeap{
    	a: make([]*Value, 0, 8),
    	less: func(x, y *Value) bool {
    		sx := score[x.ID]
    		sy := score[y.ID]
    		if c := sx - sy; c != 0 {
    			return c > 0 // higher score comes later.
    		}
    		if x.Line != y.Line { // Favor in-order line stepping
    			return x.Line > y.Line
    		}
    		if x.Op != OpPhi {
    			if c := len(x.Args) - len(y.Args); c != 0 {
    				return c < 0 // smaller args comes later
    			}
    		}
    		return x.ID > y.ID
    	},
    }
    // ...
    heap.Push(priq, v)
    // ...
    v := heap.Pop(priq).(*Value)
    ```
    `less`関数内で、前述の複数のヒューリスティック（スコア、行番号、引数の数、ID）に基づいて優先度が決定されます。

## コアとなるコードの解説

`schedule`関数は、GoコンパイラのSSAバックエンドにおいて、各基本ブロック内の`Value`（命令や値）の実行順序を決定する役割を担っています。このコミットでは、その核となるスケジューリングアルゴリズムが大幅に改善されました。

1.  **`ValHeap`の役割**:
    `ValHeap`は、`container/heap`パッケージが要求する`heap.Interface`を満たすカスタムデータ構造です。これにより、任意の`Value`を効率的に追加・削除できる優先度キューとして機能します。`ValHeap`の`less`フィールドに渡される匿名関数が、`Value`間の優先度比較ロジックをカプセル化しています。

2.  **優先度比較ロジック (`less`関数)**:
    この`less`関数は、2つの`Value` `x`と`y`を受け取り、`x`が`y`よりも優先度が低い（つまり、ヒープから先に`y`が取り出されるべき）場合に`true`を返します。スケジューリングは逆順に行われるため、`Less`が`true`を返す要素は、最終的な命令列ではより後方に配置されます。
    -   **スコア (`score[x.ID]`)**: 最も優先される基準です。`ScorePhi`（Phi関数）が最も低く（早くスケジューリング）、`ScoreControl`（制御フロー命令）が最も高く（遅くスケジューリング）なります。`c > 0`は、`x`のスコアが`y`より高い場合（つまり、`x`がよりブロックの終わりに近い場合）に`true`を返し、`x`の優先度が低いことを示します。
    -   **行番号 (`x.Line`, `y.Line`)**: スコアが同じ場合、ソースコードの行番号が大きい方が優先度が低い（最終的に後方に配置される）とされます。これにより、デバッグ時にコードの実行順序がソースコードの記述順に近い状態に保たれます。
    -   **引数の数 (`len(x.Args)`, `len(y.Args)`)**: `OpPhi`以外の命令でスコアと行番号が同じ場合、引数の数が少ない方が優先度が低い（最終的に後方に配置される）とされます。これは、引数が多い命令はレジスタをより多く消費する可能性があり、レジスタ圧力を考慮したヒューリスティックです。
    -   **ID (`x.ID`, `y.ID`)**: 全ての基準が同じ場合、`Value`のユニークなIDでタイブレークします。

3.  **スケジューリングプロセス**:
    -   まず、各ブロック内の全ての`Value`に対して、その`score`が計算されます。
    -   次に、各`Value`が持つ引数（依存関係）の`uses`カウントが初期化されます。
    -   `uses`カウントが0の`Value`（つまり、まだスケジューリングされていない他の`Value`に依存していないもの）は、`heap.Push`を使って`ValHeap`に追加されます。
    -   メインのループでは、`heap.Pop`を使って最も優先度の高い`Value`が`ValHeap`から取り出されます。
    -   取り出された`Value`は、現在のブロックのスケジューリング順序リスト（`order`）に追加されます。
    -   その`Value`が依存していた他の`Value`の`uses`カウントがデクリメントされ、`uses`カウントが0になった`Value`は、新たにスケジューリング可能になったとして`heap.Push`で`ValHeap`に追加されます。
    -   このプロセスは`ValHeap`が空になるまで繰り返され、最終的にブロック内の全ての`Value`がスケジューリングされます。

この新しいアプローチにより、コンパイラはより柔軟かつ効率的に命令の順序を決定できるようになり、レジスタ割り当ての質を向上させ、結果として生成されるコードのサイズを削減することに成功しました。

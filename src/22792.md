# [インデックス 22792] ファイルの概要

このコミットは、GoランタイムにおけるDarwin/AMD64アーキテクチャ向けの共有ライブラリのエントリポイントを導入するものです。これは、GoプログラムをC言語のアーカイブ（静的ライブラリ）や共有ライブラリとしてビルドする際の基盤となる変更であり、特に`go build -buildmode=c-archive`および`go build -buildmode=c-shared`の実現に向けた重要なステップです。

## 変更の背景

Go言語は、その強力な並行処理モデルとシンプルな構文により、多くのアプリケーション開発で利用されています。しかし、Goプログラムを既存のC/C++コードベースと連携させる場合、特にGoコードをライブラリとして提供するシナリオでは、特定の課題がありました。このコミットが行われた2015年当時、Goは主にスタンドアロンの実行可能ファイルを生成することに特化しており、C言語から呼び出し可能な共有ライブラリ（`.dylib`や`.so`）や静的ライブラリ（`.a`）を直接生成する機能はまだ発展途上でした。

この変更の主な背景は、Goのビルドモードに`-buildmode=c-archive`（Cアーカイブライブラリの生成）と`-buildmode=c-shared`（C共有ライブラリの生成）を導入し、特にmacOS (Darwin) 上のAMD64アーキテクチャでこれらをサポートすることにありました。これらのビルドモードを適切に機能させるためには、Goランタイムがライブラリとしてロードされた際に、適切に初期化され、Goのスケジューラやガベージコレクタなどのランタイム機能が利用可能になるような「エントリポイント」が必要でした。

コミットメッセージにある「This is a practice run for darwin/arm.」という記述は、将来的にARMアーキテクチャ（例えばiOSデバイス向け）でも同様の共有ライブラリ機能を提供するための先行研究・実装であることを示唆しています。Linux/AMD64向けには既に同様のエントリポイントが存在しており、その実装を参考にDarwin/AMD64向けに移植・調整が行われました。

また、コミットメッセージでは、`-buildmode=c-archive`でビルドされたライブラリがGoの`main`関数を実行してしまうという問題が指摘されており、これを解決するためのさらなる変更が示唆されています。これは、ライブラリとして利用されるGoコードは、通常、独自の`main`関数を持つべきではなく、ホストアプリケーションによって呼び出されるエクスポートされた関数を通じて機能を提供すべきであるという設計思想に基づいています。

## 前提知識の解説

### 1. Goのビルドモード (`-buildmode`)

Goコンパイラ（`go build`コマンド）は、`-buildmode`フラグを使用して、生成されるバイナリの種類を制御できます。このコミットに関連する主要なビルドモードは以下の通りです。

*   **`-buildmode=exe` (デフォルト):** 実行可能ファイルを生成します。Goプログラムの`main`パッケージにある`main`関数がエントリポイントとなります。
*   **`-buildmode=c-archive`:** C言語からリンク可能な静的ライブラリ（`.a`ファイル）を生成します。このライブラリには、Goのランタイムと、エクスポートされたGo関数が含まれます。ホストのC/C++アプリケーションは、このライブラリをリンクしてGoの機能を利用できます。
*   **`-buildmode=c-shared`:** C言語からロード可能な共有ライブラリ（macOSでは`.dylib`、Linuxでは`.so`）を生成します。このライブラリもGoのランタイムとエクスポートされたGo関数を含みますが、静的ライブラリとは異なり、実行時に動的にロードされます。

### 2. 共有ライブラリとエントリポイント

共有ライブラリ（Shared Library / Dynamic Link Library, DLL）は、複数のプログラムで共有されるコードとデータを含むファイルです。これにより、ディスクスペースの節約、メモリ使用量の削減、プログラムのモジュール化が促進されます。

共有ライブラリがプロセスにロードされる際、特定の初期化ルーチンが実行されることがあります。これは、ライブラリが提供する機能が利用可能になる前に、必要なセットアップ（例えば、グローバル変数の初期化、リソースの確保など）を行うためです。この初期化ルーチンへの入り口が「エントリポイント」です。C/C++の世界では、コンストラクタ関数や特定のシンボルがこれに相当することがあります。Goの共有ライブラリの場合、Goランタイムの初期化がこのエントリポイントで行われる必要があります。

### 3. Darwin (macOS) のスレッドモデルと `bsdthread_create`

macOS（Darwinカーネル）は、POSIXスレッド（pthreads）をベースとしたスレッドモデルを採用しています。Goランタイムは、OSのスレッドを直接管理し、GoのゴルーチンをこれらのOSスレッドにマッピングします。

`bsdthread_create`は、Darwinカーネルが提供する低レベルのスレッド作成システムコールです。Goランタイムは、新しいOSスレッドを作成する際にこのシステムコールを利用します。通常、Goの`m`（Machine）構造体（OSスレッドを表す）と`g`（Goroutine）構造体（ゴルーチンを表す）を引数として渡しますが、このコミットでは、ランタイム初期化前の特殊なケースで`newosproc0`という関数が導入され、`bsdthread_create`の引数に調整が加えられています。

### 4. アセンブリ言語 (`.s`ファイル) とGoランタイム

Goランタイムの低レベルな部分は、アセンブリ言語で記述されています。これは、OSとのインタフェース、スレッドの切り替え、スタック管理など、パフォーマンスが重要でOS固有の操作が必要な部分で利用されます。`rt0_darwin_amd64.s`のようなファイルは、Goプログラムの起動シーケンス（ランタイムの初期化、`main`関数の呼び出しなど）を定義するアセンブリコードを含んでいます。このコミットでは、共有ライブラリとしてロードされた場合の新しい起動シーケンスが追加されています。

## 技術的詳細

このコミットの核心は、Goの共有ライブラリがmacOS上でロードされた際に、Goランタイムを適切に初期化するための新しいエントリポイント`_rt0_amd64_darwin_lib`を導入した点にあります。

通常のGo実行可能ファイルは、`_rt0_amd64_darwin`というエントリポイントから起動し、Goランタイムの初期化を経て、最終的にユーザー定義の`main`関数を呼び出します。しかし、共有ライブラリの場合、ライブラリがロードされた時点でGoランタイムが初期化される必要があり、かつ、ホストアプリケーションのコンテキストで動作するため、Goの`main`関数を直接実行すべきではありません。

新しいエントリポイント`_rt0_amd64_darwin_lib`の動作は以下の通りです。

1.  **引数の保存:** ライブラリがロードされた際にOSから渡される引数（`argc`と`argv`に相当するレジスタDIとSIの値）を、Goランタイム内部の変数`_rt0_amd64_darwin_lib_argc`と`_rt0_amd64_darwin_lib_argv`に保存します。これにより、Goランタイムが後でこれらの情報にアクセスできるようになります。
2.  **新しいOSスレッドの作成:**
    *   まず、`_cgo_sys_thread_create`というCgoランタイム関数が存在するかどうかをチェックします。これは、Cgoが有効な場合にGoランタイムがOSスレッドを作成するために使用する関数です。
    *   `_cgo_sys_thread_create`が存在する場合、それを使用して新しいOSスレッドを作成し、そのスレッドで`_rt0_amd64_darwin_lib_go`というGoランタイムの初期化ルーチンを実行させます。
    *   `_cgo_sys_thread_create`が存在しない（Cgoが無効な）場合、Goランタイム自身の低レベルなスレッド作成関数である`runtime·newosproc0`を呼び出して新しいOSスレッドを作成し、同様に`_rt0_amd64_darwin_lib_go`を実行させます。
    *   この新しいスレッドでGoランタイムの初期化を行うことで、ライブラリのロード処理自体は迅速に完了し、Goランタイムの初期化はバックグラウンドで行われます。
3.  **Goランタイムの初期化へのジャンプ:** `_rt0_amd64_darwin_lib_go`ルーチンは、保存された`argc`と`argv`の値を引数として、Goランタイムのメイン初期化関数である`runtime·rt0_go`にジャンプします。これにより、Goのスケジューラ、ガベージコレクタ、メモリ管理などが初期化され、Goの機能が利用可能になります。

このコミットでは、`bsdthread_create`の呼び出し方にも変更が加えられています。特に、`newosproc0`という新しい関数が導入され、これはランタイムが完全に初期化される前にOSスレッドを作成する必要がある場合に利用されます。`newosproc0`は、`bsdthread_create`に渡す引数から`mp`（GoのM構造体）と`g`（GoのG構造体）の情報を省略しており、これはランタイム初期化前の特殊なコンテキストに対応するためです。

コミットメッセージで言及されている「text relocations」の問題は、共有ライブラリがロードされる際に、コード内の絶対アドレス参照を修正する必要があることを指します。Goのコンパイラとリンカは、通常、実行可能ファイルを生成する際に静的なアドレスを前提としますが、共有ライブラリでは動的なアドレス解決が必要となるため、追加のリンカ変更が必要となります。

また、「-buildmode=c-archive should ignore the Go main function」という課題は、静的ライブラリとしてビルドされたGoコードが、ホストアプリケーションの`main`関数とは別にGo自身の`main`関数を実行してしまうという問題です。これは、ライブラリが意図せずプロセスを終了させてしまう可能性があるため、解決が必要でした。このコミット自体では解決されていませんが、この問題意識が示されています。

## コアとなるコードの変更箇所

このコミットでは、主に以下の4つのファイルが変更されています。

1.  **`src/runtime/os1_darwin.go`**:
    *   `newosproc`関数の`bsdthread_create`呼び出しの引数が変更されました。`mp.g0`が削除され、`unsafe.Pointer(mp)`が`arg`として渡されるようになりました。
    *   **`newosproc0`** という新しい関数が追加されました。これは、ランタイムが初期化される前にOSスレッドを作成するためのもので、`bsdthread_create`を呼び出す際に`fnarg`として`mp`を渡しません。これは、ランタイム初期化前の特殊な状況に対応するためです。
    *   エラーメッセージ用のバイトスライス `failallocatestack` と `failthreadcreate` が追加されました。

2.  **`src/runtime/os_darwin.go`**:
    *   `bsdthread_create`関数のGo側の宣言が変更されました。`mm *m, gg *g`という引数が削除され、`arg unsafe.Pointer`という汎用的な引数に置き換えられました。これにより、`bsdthread_create`がより柔軟な引数を受け入れられるようになりました。

3.  **`src/runtime/rt0_darwin_amd64.s`**:
    *   **`_rt0_amd64_darwin_lib`** という新しいアセンブリ関数が追加されました。これが共有ライブラリのエントリポイントとなります。
    *   `_rt0_amd64_darwin_lib`内で、`_cgo_sys_thread_create`の有無をチェックし、それに応じて`_rt0_amd64_darwin_lib_go`を新しいスレッドで実行するためのロジックが追加されました。
    *   **`_rt0_amd64_darwin_lib_go`** というアセンブリ関数が追加されました。これは、`_rt0_amd64_darwin_lib`から新しいスレッドで呼び出され、最終的にGoランタイムの初期化ルーチンである`runtime·rt0_go`にジャンプします。
    *   `_rt0_amd64_darwin_lib_argc`と`_rt0_amd64_darwin_lib_argv`というデータセクションが追加され、共有ライブラリの起動引数を保存するために使用されます。

4.  **`src/runtime/sys_darwin_amd64.s`**:
    *   `runtime·bsdthread_create`アセンブリ関数の引数オフセットが調整されました。これは、`bsdthread_create`のGo側の宣言変更（`os_darwin.go`での変更）に合わせて、アセンブリコードが正しいレジスタから引数を読み取るようにするためです。特に、`fn`と`arg`のスタックオフセットが変更されています。

## コアとなるコードの解説

### `src/runtime/os1_darwin.go` と `src/runtime/os_darwin.go` の変更

これらのファイルにおける変更は、GoランタイムがOSスレッドを作成する際の低レベルなインタフェースを調整するものです。

*   `bsdthread_create`のGo側のシグネチャ変更（`os_darwin.go`）は、この関数がより汎用的な引数`arg unsafe.Pointer`を受け入れるようにすることで、Goランタイムの初期化フェーズの異なる段階で、異なる種類の引数（例えば、`*m`や`*g`がまだ完全に利用可能でない場合）を渡せるようにするためのものです。
*   `newosproc0`の導入（`os1_darwin.go`）は、Goランタイムが完全に初期化される前、つまり`m`や`g`構造体がまだ完全にセットアップされていない段階で、OSスレッドを作成する必要があるシナリオ（共有ライブラリの初期ロード時など）に対応するためのものです。この関数は、`bsdthread_create`を呼び出す際に、`fnarg`として`mp`（GoのM構造体）を渡さないことで、この初期化前の制約を回避しています。

### `src/runtime/rt0_darwin_amd64.s` の変更

このファイルは、Goプログラムの起動シーケンスを定義するアセンブリコードを含んでいます。このコミットの最も重要な変更は、`_rt0_amd64_darwin_lib`という新しいエントリポイントの追加です。

```assembly
// When linking with -shared, this symbol is called when the shared library
// is loaded.
TEXT _rt0_amd64_darwin_lib(SB),NOSPLIT,$40
    MOVQ    DI, _rt0_amd64_darwin_lib_argc<>(SB)
    MOVQ    SI, _rt0_amd64_darwin_lib_argv<>(SB)

    // Create a new thread to do the runtime initialization and return.
    MOVQ    _cgo_sys_thread_create(SB), AX
    TESTQ   AX, AX
    JZ      nocgo
    MOVQ    $_rt0_amd64_darwin_lib_go(SB), DI
    MOVQ    $0, SI
    CALL    AX
    RET
nocgo:
    MOVQ    $8388608, 0(SP)                    // stacksize
    MOVQ    $_rt0_amd64_darwin_lib_go(SB), AX
    MOVQ    AX, 8(SP)                          // fn
    MOVQ    $0, 16(SP)                         // fnarg
    MOVQ    $runtime·newosproc0(SB), AX
    CALL    AX
    RET

TEXT _rt0_amd64_darwin_lib_go(SB),NOSPLIT,$0
    MOVQ    _rt0_amd64_darwin_lib_argc<>(SB), DI
    MOVQ    _rt0_amd64_darwin_lib_argv<>(SB), SI
    MOVQ    $runtime·rt0_go(SB), AX
    JMP     AX
```

*   `_rt0_amd64_darwin_lib`: 共有ライブラリがロードされると、OSはこのシンボルを呼び出します。
    *   `MOVQ DI, _rt0_amd64_darwin_lib_argc<>(SB)` と `MOVQ SI, _rt0_amd64_darwin_lib_argv<>(SB)`: ロード時の引数（`argc`, `argv`に相当）を保存します。
    *   `_cgo_sys_thread_create`のチェック: Cgoが有効な場合、Cgoが提供するスレッド作成関数を利用します。これは、CgoがOSスレッドの管理に介入する場合があるためです。
    *   `nocgo`パス: Cgoが有効でない場合、Goランタイム自身の`runtime·newosproc0`を呼び出します。この関数は、Goランタイムがまだ完全に初期化されていない状況でもOSスレッドを作成できるように設計されています。
    *   どちらのパスでも、新しく作成されたOSスレッドは`_rt0_amd64_darwin_lib_go`を実行します。
    *   `RET`: `_rt0_amd64_darwin_lib`は、新しいスレッドを起動した後、すぐに呼び出し元（OSのローダー）に制御を戻します。これにより、ライブラリのロード処理がブロックされることなく、Goランタイムの初期化が並行して行われます。
*   `_rt0_amd64_darwin_lib_go`: 新しいOSスレッドで実行されるGoランタイムの初期化ルーチンです。
    *   保存しておいた`argc`と`argv`の値をレジスタにロードします。
    *   `JMP runtime·rt0_go(SB)`: 最終的にGoランタイムのメイン初期化関数である`runtime·rt0_go`にジャンプします。これにより、Goのスケジューラ、ガベージコレクタ、メモリ管理などが初期化され、Goの機能が利用可能になります。

### `src/runtime/sys_darwin_amd64.s` の変更

このファイルは、GoランタイムがOSのシステムコールを呼び出すためのアセンブリラッパーを含んでいます。

```assembly
// func bsdthread_create(stk, arg unsafe.Pointer, fn uintptr) int32
TEXT runtime·bsdthread_create(SB),NOSPLIT,$0
    // Set up arguments to bsdthread_create system call.
    // The ones in quotes pass through to the thread callback
    // uninterpreted, so we can put whatever we want there.
    MOVQ    fn+24(SP), DI   // "func"
    MOVQ    arg+16(SP), SI  // "arg"
    MOVQ    stk+8(SP), DX   // stack
    MOVQ    $0, R10         // "pthread", paranoia
    MOVQ    $0x01000000, R8 // flags = PTHREAD_START_CUSTOM
    MOVQ    $0, R9  // paranoia
    MOVQ    $(0x2000000+360), AX    // bsdthread_create
    SYSCALL
    RET
```

`runtime·bsdthread_create`の引数オフセットの調整は、`src/runtime/os_darwin.go`で`bsdthread_create`のGo側のシグネチャが変更されたことに対応するものです。Go関数がアセンブリ関数を呼び出す際、引数はスタックに特定のオフセットで配置されます。シグネチャの変更により、引数の順序やサイズが変わるため、アセンブリコードが正しいスタック位置から引数を読み取れるようにオフセットを調整する必要があります。この変更により、`fn`と`arg`が正しくレジスタにロードされるようになります。

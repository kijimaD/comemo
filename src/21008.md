# [インデックス 21008] ファイルの概要

このコミットは、Go言語の標準ライブラリである `bufio` パッケージにおける `Scanner` のバグを修正します。具体的には、連続する多数の空行を読み込む際に発生する可能性があった問題（`panic: "bufio.Scan: 100 empty tokens without progressing"`）を解決し、`Scanner` が空行を正しく処理できるようにします。この修正により、`Scanner` の堅牢性が向上し、予期せぬパニックを防ぎます。

## 変更の背景

このコミットは、Goの `bufio` パッケージの `Scanner` が、連続する多数の空行を処理する際に発生する既知の問題（Issue #9020）を修正するために導入されました。

`bufio.Scanner` は、入力ストリームをトークン（単語、行など）に分割するためのユーティリティです。`Scan()` メソッドは、次のトークンを読み込み、そのトークンが有効であれば `true` を返します。`Scanner` は、入力が進まないにもかかわらず空のトークンが連続して返される場合に、無限ループを防ぐために `s.empties` というカウンターを使用し、これが100を超えるとパニックを発生させるメカニズムを持っています。

しかし、このメカニズムが、特に `SplitFunc` が空のトークンを返すものの、実際には入力が進んでいる（例えば、改行文字を消費している）場合に、誤ってパニックを引き起こす可能性がありました。具体的には、`SplitFunc` が `token` を `nil` または `len(token) == 0` で返し、かつ `advance > 0` （入力が進んだ）場合でも、`s.empties` カウンターがリセットされず、連続する空行の読み込みで `panic` が発生してしまう問題がありました。

この問題は、特に大きなファイルや、多数の空行を含むログファイルなどを `bufio.Scanner` で処理する際に、アプリケーションがクラッシュする原因となっていました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の `bufio` パッケージに関する知識が必要です。

*   **`bufio.Scanner`**: `bufio` パッケージが提供する型で、`io.Reader` からデータを読み込み、定義されたルール（`SplitFunc`）に基づいてトークンに分割するためのユーティリティです。
*   **`Scanner.Scan()` メソッド**: `Scanner` の主要なメソッドで、次のトークンを読み込みます。トークンが利用可能であれば `true` を返し、それ以上トークンがないかエラーが発生した場合は `false` を返します。
*   **`Scanner.SplitFunc`**: `Scanner` がどのように入力をトークンに分割するかを定義する関数です。この関数は `(advance int, token []byte, err error)` の3つの値を返します。
    *   `advance`: 入力ストリームから消費されたバイト数を示します。`advance > 0` であれば、入力が進んだことを意味します。
    *   `token`: 抽出されたトークン（バイトスライス）です。
    *   `err`: エラーが発生した場合に返されます。
*   **`s.empties` カウンター**: `Scanner` 内部で管理されるカウンターで、`SplitFunc` が空のトークン（`token` が `nil` または `len(token) == 0`）を返し、かつ入力が進まなかった（`advance == 0`）場合にインクリメントされます。これは、`SplitFunc` が無限ループに陥るのを防ぐための安全装置です。
*   **`panic("bufio.Scan: 100 empty tokens without progressing")`**: `s.empties` カウンターが100を超えた場合に発生するパニックです。これは、`Scanner` が入力ストリームから何も読み進めずに空のトークンを繰り返し生成している状態を検出し、プログラムのハングアップを防ぐためのものです。

## 技術的詳細

このコミットの核心は、`Scanner` の `Scan()` メソッド内の `s.empties` カウンターのリセット条件の変更です。

変更前のコードでは、`s.empties` カウンターは `len(token) > 0` の場合にのみリセットされていました。これは、非空のトークンが検出された場合にのみカウンターをリセットするというロジックでした。しかし、このロジックには問題がありました。

`SplitFunc` が空のトークン（`token` が `nil` または `len(token) == 0`）を返しても、実際には入力ストリームからバイトを消費して進んでいる（`advance > 0`）場合があります。例えば、`ScanLines` のような `SplitFunc` は、空行を読み込む際に `token` を空にしつつ、改行文字を消費するために `advance` を1または2（CRLFの場合）とします。

変更前のロジックでは、`len(token) > 0` が `false` の場合、`s.empties` は常にインクリメントされ続けました。これにより、連続する空行が100行を超えると、`Scanner` は入力が進んでいるにもかかわらず、誤って「入力が進まないまま100個の空トークンが生成された」と判断し、パニックを引き起こしていました。

新しいロジックでは、`s.empties` のリセット条件が `s.err == nil || advance > 0` に変更されました。

*   **`s.err == nil`**: `Scanner` にエラーがない場合。これは通常の状態です。
*   **`advance > 0`**: `SplitFunc` が入力ストリームからバイトを消費して進んだ場合。

この新しい条件は、`SplitFunc` が空のトークンを返したとしても、入力が実際に進んでいる（`advance > 0`）のであれば、`s.empties` カウンターをリセットするようにします。これにより、`Scanner` は連続する空行を正しく処理できるようになり、不必要なパニックを防ぐことができます。

また、`s.err == nil` の条件が追加されたのは、`SplitFunc` がエラーを返した場合（例えば `io.EOF`）に、`advance` が0であっても `s.empties` をリセットしないようにするためです。これは、エラー状態での `Scanner` の挙動をより正確に制御するためです。

この修正は、`bufio.Scanner` の堅牢性を高め、特に大量の空行を含むデータセットを処理する際の安定性を向上させます。

## コアとなるコードの解説

### `src/bufio/scan.go` の変更

変更の中心は、`Scan()` メソッド内の `s.empties` カウンターをリセットする条件です。

*   **変更前**:
    ```go
    if len(token) > 0 {
        s.empties = 0
    } else {
        s.empties++
        if s.empties > 100 {
            panic("bufio.Scan: 100 empty tokens without progressing")
        }
    }
    ```
    このロジックでは、`SplitFunc` が `token` を空（`len(token) == 0`）で返した場合、たとえ `advance > 0` で入力が進んでいても、`s.empties` はインクリメントされ続けました。これにより、連続する空行でパニックが発生する原因となっていました。

*   **変更後**:
    ```go
    if s.err == nil || advance > 0 {
        s.empties = 0
    } else {
        // Returning tokens not advancing input at EOF.
        s.empties++
        if s.empties > 100 {
            panic("bufio.Scan: 100 empty tokens without progressing")
        }
    }
    ```
    新しい条件 `s.err == nil || advance > 0` は、以下のいずれかの条件が満たされた場合に `s.empties` をリセットします。
    1.  `s.err == nil`: `Scanner` にエラーがない場合。これは通常の操作中に `s.empties` をリセットするための基本的な条件です。
    2.  `advance > 0`: `SplitFunc` が入力ストリームからバイトを消費して進んだ場合。これは、`token` が空であっても、入力が実際に進んでいる場合に `s.empties` をリセットすることを保証します。これにより、空行の処理中に誤ってパニックが発生するのを防ぎます。

    `else` ブロックのコメント `// Returning tokens not advancing input at EOF.` は、このブロックが、トークンが返されるものの入力が進まない（通常はEOFで発生する）状況を処理することを示しています。このような状況でのみ `s.empties` がインクリメントされ、無限ループの検出に役立ちます。

### `src/bufio/scan_test.go` の変更

`TestBlankLines` という新しいテスト関数が追加されました。

```go
func TestBlankLines(t *testing.T) {
    s := NewScanner(strings.NewReader(strings.Repeat("\n", 1000)))
    for count := 0; s.Scan(); count++ {
        if count > 2000 {
            t.Fatal("looping")
        }
    }
    if s.Err() != nil {
        t.Fatal("after scan:", s.Err())
    }
}
```

このテストは、1000個の連続する改行文字を含む文字列を `Scanner` に与え、`Scan()` メソッドを呼び出し続けます。

*   `strings.Repeat("\n", 1000)`: 1000個の改行文字からなる文字列を作成します。
*   `NewScanner(strings.NewReader(...))`: この文字列を読み込む新しい `Scanner` を作成します。
*   `for count := 0; s.Scan(); count++`: `Scan()` が `false` を返すまでループを続けます。
*   `if count > 2000 { t.Fatal("looping") }`: 無限ループに陥っていないことを確認するための安全装置です。
*   `if s.Err() != nil { t.Fatal("after scan:", s.Err()) }`: `Scan()` 終了後にエラーが発生していないことを確認します。

このテストは、修正が正しく機能し、`Scanner` が多数の空行をパニックすることなく正常に処理できることを検証します。

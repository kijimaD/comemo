## 変更の背景

このコミットの背景には、Goリンカ (`cmd/link`) 内の `Pcln` という構造体の役割の変化があります。元々 `Pcln` は "Program Counter Line Number" の略で、プログラムカウンタとソースコードの行番号のマッピング情報（PCLinuxOSテーブル）を保持するための構造体でした。これはデバッグ情報やスタックトレースの生成に不可欠な情報です。

しかし、このコミットの直前のコミット（`I7211111111111111111111111111111111111111`、コミットハッシュ `1721111111111111111111111111111111111111`）で、`Pcln` 構造体に `Args` (関数の引数サイズ) や `Locals` (関数のローカル変数サイズ) といった、PCLinuxOS情報とは直接関係のない、しかし関数に関する重要なメタデータが追加されました。

これにより、`Pcln` という名前は構造体の実際の役割を正確に反映しなくなりました。構造体がPCLinuxOS情報だけでなく、関数全体の情報（Function Information）を保持するようになったため、より汎用的な `FuncInfo` という名前に変更することで、コードの可読性と保守性を向上させる目的でこのリネームが行われました。これは、データ構造の命名がその内容と役割を正確に表現することの重要性を示す典型的な例です。

## 前提知識の解説

### Go言語のリンカ (`cmd/link`)

Go言語のコンパイルプロセスにおいて、リンカ (`cmd/link`) は非常に重要な役割を担います。Goのソースコードはまずコンパイラによってオブジェクトファイル（`.o` ファイル）に変換されます。これらのオブジェクトファイルには、コンパイルされたコード、データ、そしてシンボル情報が含まれています。リンカは、これらのオブジェクトファイルを結合し、必要なライブラリ（標準ライブラリやサードパーティライブラリ）をリンクして、最終的な実行可能バイナリを生成します。

リンカの主な機能は以下の通りです。
*   **シンボル解決**: 異なるオブジェクトファイルで定義された関数や変数の参照を解決します。
*   **再配置**: コード内のアドレス参照を、最終的なメモリレイアウトに合わせて調整します。
*   **デバッグ情報の生成**: DWARFなどのデバッグ情報をバイナリに埋め込みます。
*   **PCLinuxOSテーブルの生成**: プログラムカウンタとソースコードの行番号、関数名などのマッピング情報（PCLinuxOSテーブル）を生成し、実行時エラーのスタックトレースやプロファイリングに利用できるようにします。

### PCLinuxOS (Program Counter Line Number) テーブル

PCLinuxOSテーブルは、Goの実行可能バイナリに埋め込まれるメタデータの一種です。これは、プログラムカウンタ（PC、現在実行中の命令のアドレス）から、対応するソースファイル名、行番号、関数名などの情報を効率的に取得するために使用されます。

このテーブルは主に以下の目的で利用されます。
*   **スタックトレース**: パニック発生時やデバッグ時に、どの関数がどのソースファイルのどの行で呼び出されたかを示すスタックトレースを生成するために使われます。
*   **プロファイリング**: 実行中のプログラムのどの部分で時間が費やされているかを特定するために、PCから関数情報を逆引きする際に利用されます。
*   **デバッガ**: デバッガがソースコードレベルで実行を追跡するために必要とします。

PCLinuxOSテーブルは、非常にコンパクトな形式でエンコードされており、実行可能ファイルのサイズを抑えつつ、必要な情報を提供できるように設計されています。

### Goのシンボル (`LSym`)

Goリンカの内部では、プログラム内のすべてのコード、データ、およびメタデータは `LSym` (Linker Symbol) という構造体で表現されます。`LSym` は、関数、グローバル変数、型情報、PCLinuxOSデータなど、リンク時に処理されるあらゆる要素を抽象化します。

`LSym` 構造体は、シンボルの名前、アドレス、サイズ、型、そして様々な属性（例えば、外部リンケージを持つか、読み取り専用かなど）を保持します。このコミットで変更された `Pcln` (後の `FuncInfo`) は、`LSym` 構造体の一部として、特定の関数シンボルに関連付けられた詳細な関数情報を保持していました。

### DWARF (Debugging With Attributed Record Formats)

DWARFは、ソースレベルデバッガがプログラムの実行をデバッグするために必要な情報を提供する標準的なデバッグファイル形式です。Goのリンカは、DWARF形式でデバッグ情報を生成し、実行可能ファイルに埋め込むことができます。

DWARF情報には、変数名、型情報、スコープ、ソースファイルと行番号のマッピング、スタックフレームの構造などが含まれます。PCLinuxOSテーブルが主にPCから行番号への高速なマッピングを提供するのに対し、DWARFはよりリッチで詳細なデバッグ情報を提供します。このコミットで `Pcln` が `FuncInfo` にリネームされたことは、DWARF情報の生成プロセスにも影響を与え、`FuncInfo` が提供するより包括的な関数メタデータがデバッグ情報の精度向上に寄与することを示唆しています。

## 技術的詳細

このコミットの技術的詳細の中心は、Goリンカ内部のデータ構造のセマンティクス（意味論）の明確化にあります。

Goリンカは、コンパイルされたGoプログラムの各関数について、様々なメタデータを管理しています。これには、関数の開始アドレス、終了アドレス、ソースコードの行番号情報（PCLinuxOS）、スタックフレームのサイズ、引数のサイズ、ローカル変数のサイズ、そしてデバッグ情報（DWARF）の生成に必要なその他の情報が含まれます。

以前は、これらの情報の一部が `Pcln` という構造体にまとめられていました。しかし、前述の通り、この構造体にはPCLinuxOS情報だけでなく、関数のスタックフレームに関する情報（`Args`, `Locals`）も含まれるようになりました。

この状況は、ソフトウェア設計における「単一責任の原則 (Single Responsibility Principle)」に反する可能性がありました。`Pcln` という名前は、その構造体がPCLinuxOS情報のみを扱うべきであることを示唆しているため、他の種類の関数メタデータが含まれると、コードを読む開発者にとって混乱を招く可能性があります。

`Pcln` を `FuncInfo` にリネームすることで、この構造体が単にPCLinuxOS情報だけでなく、「関数に関する情報全般」を保持するものであることが明確になります。これにより、以下の技術的な利点が得られます。

1.  **コードの可読性向上**: 開発者がコードを読んだ際に、`FuncInfo` という名前から、その構造体が関数の引数、ローカル変数、PCLinuxOSデータなど、関数に関する様々なメタデータを含んでいることを直感的に理解できるようになります。
2.  **保守性の向上**: 将来的に関数に関する新たなメタデータが必要になった場合でも、`FuncInfo` という汎用的な名前であれば、既存の構造体に自然に追加できます。もし `Pcln` のままだった場合、新しいフィールドを追加するたびに名前と内容の乖離が大きくなり、リファクタリングの必要性が高まるか、あるいは不適切な命名のままコードが複雑化するリスクがありました。
3.  **設計の一貫性**: リンカ内の他のデータ構造との一貫性が向上し、全体的な設計がより論理的になります。

この変更は、単なる名前の変更以上の意味を持ち、Goリンカの内部構造の健全性を保ち、将来の拡張性を考慮したリファクタリングの一環と言えます。特に、`LSym` 構造体内の `Pcln` フィールドが `FuncInfo` に変更されたことは、各シンボルが持つ関数情報の表現がより正確になったことを意味します。

## コアとなるコードの解説

上記のコード変更は、Goリンカの内部で関数に関するメタデータをどのように表現し、アクセスするかの根本的な変更を反映しています。

1.  **型定義のリネーム**:
    `type Pcln struct { ... }` が `type FuncInfo struct { ... }` に変更されました。これは、この構造体がPCLinuxOS情報（`Pcfile`, `Pcline`, `Pcsp` など）だけでなく、関数の引数サイズ (`Args`)、ローカル変数サイズ (`Locals`)、自動変数 (`Autom`)、関数データ (`Funcdata`)、ファイル情報 (`File`) など、関数に関するより広範な情報を含むようになったことを明確にしています。

2.  **`LSym` 構造体内のフィールド名変更**:
    `LSym` 構造体は、Goプログラム内の各シンボル（関数、変数など）を表します。以前は、関数シンボルに関連する詳細情報へのポインタが `Pcln *Pcln` というフィールドで保持されていました。この変更により、フィールド名が `FuncInfo *FuncInfo` となり、`LSym` が保持する情報が「PCLinuxOSデータ」ではなく「関数情報」であることが明確になりました。

3.  **コードベース全体での参照の更新**:
    `deadcode.go`, `dwarf.go`, `lib.go`, `objfile.go`, `pcln.go` など、リンカの様々な部分で `s.Pcln` へのアクセスが `s.FuncInfo` へと変更されています。これは、リネームがコードベース全体にわたる広範な変更であり、`FuncInfo` がリンカの多くの機能（デッドコード削除、DWARF生成、スタックチェック、シンボル生成など）で利用される中心的なデータ構造であることを示しています。

このリネームは、コードのセマンティクスを改善し、開発者が構造体の目的をより正確に理解できるようにすることを目的としています。これにより、将来の機能追加やバグ修正の際に、誤解を招く可能性が減り、コードの保守性が向上します。特に、`Args` や `Locals` のようなスタックフレーム関連の情報が `FuncInfo` に含まれることで、関数呼び出し規約やスタック管理に関するロジックが、より適切に構造化されたデータにアクセスできるようになります。

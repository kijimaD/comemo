# [インデックス 26311] ファイルの概要

このコミットは、Goランタイムのプロファイリングテストである `TestStackBarrierProfiling` がFreeBSD上で失敗する問題を解決するため、FreeBSD環境でのテスト実行をスキップするように変更を加えるものです。FreeBSDにおけるタイマーの解像度とプロファイリングシグナルの配送メカニズムが原因で、テストが不安定になることが判明したため、他の特定のOSと同様にこのテストを無効化します。

## 元コミット内容

`runtime/pprof`パッケージ内の`TestStackBarrierProfiling`テストが、FreeBSD上でもスキップされるように修正されました。FreeBSDでは、`sleep`呼び出しがタイムスライスの残りを放棄し、プロファイリングシグナルはプロセスがタイムスライスを完了したときにのみ配送されるという問題があります。さらに悪いことに、`itimer`の時間はタイムスライスを完了したプロセスにのみ計上されます。これは他のBSD系OSよりもデフォルトのティックレートが1000Hzと高いため目立ちにくいですが、それでも定期的にテストが失敗していました。この変更はIssue #13846を修正します。

## 変更の背景

Goのランタイムには、プログラムの実行中にCPU使用率などのプロファイル情報を収集するための`pprof`ツールが組み込まれています。このプロファイリングは、通常、オペレーティングシステムが提供するタイマーシグナル（`itimer`など）を利用して、一定間隔でプログラムの実行状態（スタックトレースなど）をサンプリングすることで行われます。

`TestStackBarrierProfiling`は、Goのガベージコレクタ（GC）が使用するスタックバリアとプロファイリングが正しく連携するかどうかを検証するためのテストです。スタックバリアは、GCがオブジェクトの参照を追跡する際に、並行して実行されているGoルーチンのスタックが変更されるのを防ぐためのメカニズムです。このテストは、短いスリープ（`usleep(100)`）を頻繁に呼び出すことで、プロファイリングシグナルが正確に配送され、スタックトレースが適切にキャプチャされることを期待しています。

しかし、FreeBSDを含む一部のOSでは、`sleep`システムコールが現在のタイムスライスの残りをOSに返上する（yieldする）という挙動をします。さらに、プロファイリングに使用される`itimer`シグナルは、プロセスがタイムスライスを完全に使い切って完了したときにのみ配送されるという特性があります。このため、`usleep(100)`のような短いスリープが頻繁に発生すると、プロセスはタイムスライスを完了する前に何度もCPUを放棄してしまい、結果としてプロファイリングシグナルが期待通りに配送されなくなります。

これにより、`TestStackBarrierProfiling`は、プロファイリングシグナルが十分に発生しないために、期待されるプロファイルデータが得られず、テストが不安定に失敗する状況が発生していました。この問題は、以前からLinux ARM、OpenBSD、Solaris、DragonFlyなどの環境でも確認されており、同様の理由でこれらの環境では既にテストがスキップされていました。FreeBSDでも同様の根本原因が確認されたため、このコミットでFreeBSDもスキップ対象に追加されました。

## 前提知識の解説

### Goのプロファイリングと`pprof`

Go言語には、プログラムのパフォーマンス特性を分析するための強力なプロファイリングツールキット`pprof`が標準で提供されています。`pprof`は、CPU使用率、メモリ割り当て、ゴルーチンブロック、ミューテックス競合など、さまざまな側面からプログラムの動作を可視化できます。

CPUプロファイリングは、通常、OSのタイマーシグナル（Unix系OSでは`SIGPROF`シグナルと`setitimer`システムコール）を利用して行われます。これは、一定の時間間隔（例えば100Hz、つまり1秒間に100回）でOSがプロセスにシグナルを送り、そのシグナルハンドラ内で現在の実行中のゴルーチンのスタックトレースをサンプリングするという仕組みです。これにより、どの関数がCPU時間を多く消費しているかを統計的に把握できます。

### `itimer`と`SIGPROF`

`itimer`（interval timer）は、Unix系OSでプロセスに定期的なシグナルを配送するために使用されるタイマーです。`setitimer`システムコールを使って設定され、`ITIMER_PROF`タイマーはプロセスが消費したCPU時間に基づいてシグナル（`SIGPROF`）を生成します。この`SIGPROF`シグナルが、GoのCPUプロファイリングのトリガーとなります。

重要なのは、`itimer`の時間が「プロセスが消費したCPU時間」に基づいて計上される点と、`SIGPROF`シグナルが「タイムスライスを完了したとき」に配送されるというOSのスケジューリングポリシーです。

### OSのスケジューリングとタイムスライス

現代のマルチタスクOSでは、CPU時間を複数のプロセスやスレッドに公平に分配するために「タイムシェアリング」という方式が用いられます。各プロセスには「タイムスライス」（またはスケジューリングクアンタム）と呼ばれる短いCPU時間の割り当てが与えられます。プロセスはこのタイムスライス内で実行され、タイムスライスが終了するか、I/O待ちなどで自発的にCPUを放棄（yield）すると、OSのスケジューラが別のプロセスにCPUを割り当てます。

`sleep`システムコールは、プロセスが指定された時間だけ実行を一時停止するようOSに要求します。多くのOSでは、`sleep`が呼び出されると、プロセスは現在のタイムスライスを使い切る前にCPUを自発的に放棄します。

### スタックバリア (Stack Barrier)

Goのガベージコレクタ（GC）は、並行GC（Concurrent GC）を採用しており、プログラムの実行と並行してGC処理を進めます。この際、GCがオブジェクトグラフを走査している間に、Goルーチンがスタック上のポインタを書き換えてしまうと、GCが誤った情報を収集したり、メモリリークやクラッシュを引き起こす可能性があります。

スタックバリアは、このような問題を回避するために導入されたメカニズムの一つです。具体的には、Goルーチンがスタック上のポインタを書き換える際に、GCがその変更を認識できるようにする「バリア」を設けます。これにより、GCの正確性と安全性が保証されます。`TestStackBarrierProfiling`は、このスタックバリアが有効な状況下でプロファイリングが正しく機能するかを検証します。

### `runtime.GOOS`と`runtime.GOARCH`

Go言語はクロスプラットフォーム開発を強力にサポートしており、`runtime`パッケージには現在の実行環境のOSとアーキテクチャを示す定数が用意されています。
*   `runtime.GOOS`: 実行中のオペレーティングシステム（例: "linux", "windows", "darwin", "freebsd"など）
*   `runtime.GOARCH`: 実行中のCPUアーキテクチャ（例: "amd64", "arm", "arm64"など）
これらの定数は、特定のOSやアーキテクチャに依存するコードの条件付きコンパイルや実行時分岐に利用されます。このコミットでは、`runtime.GOOS`の値に基づいてテストの実行を制御しています。

## 技術的詳細

このコミットの技術的詳細の核心は、FreeBSDにおけるOSスケジューラの挙動と`itimer`の特性が、GoのCPUプロファイリングのサンプリング精度に悪影響を与える点にあります。

1.  **`usleep(100)`の挙動**: `TestStackBarrierProfiling`は、短い時間（100マイクロ秒）の`usleep`を頻繁に呼び出します。FreeBSDでは、`usleep`が呼び出されると、プロセスは現在のCPUタイムスライスの残りをOSに返上し、すぐにスリープ状態に入ります。これは、プロセスがタイムスライスを使い切る前にCPUを放棄することを意味します。

2.  **`SIGPROF`シグナルの配送**: `SIGPROF`シグナルは、プロセスがCPUタイムスライスを「完了した」ときに配送される傾向があります。プロセスが`usleep`によってタイムスライスを途中で放棄すると、タイムスライスが完了したと見なされず、`SIGPROF`シグナルが配送されないか、非常に遅れて配送されることになります。

3.  **`itimer`の計上**: `itimer`によって計測されるCPU時間は、タイムスライスを完了したプロセスにのみ計上されるというOSのポリシーも問題に拍車をかけます。`usleep`によってタイムスライスを放棄するプロセスは、`itimer`のカウントが進みにくくなり、結果として`SIGPROF`シグナルがさらに発生しにくくなります。

4.  **テストの不安定性**: `TestStackBarrierProfiling`は、プロファイリングシグナルが定期的に発生し、スタックトレースがサンプリングされることを前提としています。しかし、上記の理由により、FreeBSDではシグナルが十分に発生せず、テストが期待するプロファイルデータが得られないため、テストが不安定に失敗します。

5.  **他のOSとの類似性**: この問題はFreeBSD固有のものではなく、Linux ARM、OpenBSD、Solaris、DragonFlyなど、他のOS/アーキテクチャでも同様のスケジューリングやタイマーの特性を持つ環境で発生していました。これらの環境では、既に`TestStackBarrierProfiling`がスキップされていました。FreeBSDのデフォルトティックレートが1000Hzと高いため、他のBSD系OSよりも問題が目立ちにくいものの、根本的な原因は同じであり、定期的な失敗が確認されたため、同様の対応が取られました。

この変更は、テストの信頼性を向上させるための実用的な解決策であり、特定のOSのカーネルスケジューラの挙動に起因するテストのフラッピング（不安定な失敗）を回避することを目的としています。

## コアとなるコードの解説

変更は、`TestStackBarrierProfiling`関数の冒頭にある条件分岐の行に集中しています。

元のコード:
```go
if (runtime.GOOS == "linux" && runtime.GOARCH == "arm") || runtime.GOOS == "openbsd" || runtime.GOOS == "solaris" || runtime.GOOS == "dragonfly" {
```
変更後のコード:
```go
if (runtime.GOOS == "linux" && runtime.GOARCH == "arm") || runtime.GOOS == "openbsd" || runtime.GOOS == "solaris" || runtime.GOOS == "dragonfly" || runtime.GOOS == "freebsd" {
```

この変更は、`if`文の条件式に`|| runtime.GOOS == "freebsd"`を追加するものです。
これにより、テストが実行される環境のOSが`freebsd`である場合、この`if`ブロック内のコードが実行されます。`if`ブロック内では、`t.Skipf(...)`が呼び出され、テストがスキップされます。

この修正により、FreeBSD環境でGoのテストスイートを実行する際に、`TestStackBarrierProfiling`が不安定に失敗することがなくなり、テストの信頼性が向上します。これは、特定のOSのカーネルの挙動に起因する問題に対する、実用的な回避策と言えます。

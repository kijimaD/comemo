## 変更の背景

このコミットの背景には、Go 1.5で `crypto/cipher` パッケージのGCM実装が、標準的な96ビット（12バイト）以外のノンス長をサポートするように拡張されたという事実があります。この変更は、特定のプロトコルや既存システムとの相互運用性を向上させるために導入されました。GCMは認証付き暗号化モードであり、ノンス（nonce: Number used once）は各暗号化操作で一意である必要があります。RFC 5288やNIST SP 800-38Dでは、GCMのノンス長として96ビットが推奨されていますが、一部のシステムやプロトコルでは異なる長さのノンスを使用する場合があります。Goの標準ライブラリがこのような非標準のノンス長をサポートすることで、より幅広いユースケースに対応できるようになりました。このコミットは、その重要な変更をGo 1.5のリリースノートに明記し、ユーザーに周知することを目的としています。

## 前提知識の解説

### 1. GCM (Galois/Counter Mode)

GCMは、認証付き暗号化 (Authenticated Encryption with Associated Data, AEAD) を提供するブロック暗号の動作モードの一つです。データの機密性（暗号化）と完全性・認証性（改ざん検出）を同時に保証します。AESなどのブロック暗号と組み合わせて使用され、特にTLS/SSLやIPsecなどのプロトコルで広く利用されています。

GCMの主な特徴は以下の通りです。
*   **カウンタモード (CTR Mode):** ブロック暗号をストリーム暗号のように動作させ、高速な暗号化・復号化を可能にします。
*   **GHASH関数:** ガロア体演算に基づくハッシュ関数で、認証タグ（MAC）を生成し、データの完全性と認証性を提供します。
*   **ノンス (Nonce):** 各暗号化操作で一意に使用される値です。GCMでは、ノンスとカウンタを組み合わせて各ブロックの暗号化に使用するキーを生成します。ノンスが重複すると、セキュリティが著しく損なわれるため、厳密な管理が必要です。

### 2. ノンス (Nonce)

ノンスは "Number used once" の略で、暗号化通信において一度だけ使用されるランダムまたは擬似ランダムな値です。GCMのようなカウンタモードの暗号では、同じキーで複数のメッセージを暗号化する際に、各メッセージに対して異なるノンスを使用することで、セキュリティを維持します。ノンスが予測可能であったり、再利用されたりすると、攻撃者が暗号文から平文を推測したり、認証を回避したりするリスクが高まります。

### 3. GCMの標準ノンス長

NIST SP 800-38D (Recommendation for Block Cipher Modes of Operation: Galois/Counter Mode (GCM) and GMAC) では、GCMのノンス長として96ビット（12バイト）が強く推奨されています。この長さは、セキュリティとパフォーマンスのバランスが取れており、多くの実装で採用されています。96ビットのノンスは、カウンタの初期値と組み合わせて使用され、効率的な処理が可能です。

### 4. 非標準ノンス長の問題と必要性

標準の96ビット以外のノンス長を使用することは、一般的には推奨されません。異なる長さのノンスを使用する場合、GCMの仕様では、ノンスをGHASH関数に入力する前に、特定のパディングと長さのエンコーディングを適用して128ビットのブロックに変換する必要があります。この変換は追加の処理オーバーヘッドを発生させ、実装によってはパフォーマンスに影響を与える可能性があります。

しかし、既存のシステムやプロトコルの中には、歴史的な理由や特定の設計上の制約から、96ビット以外のノンス長を使用しているものがあります。例えば、一部のTLS実装やカスタムプロトコルでは、64ビットや128ビットのノンスが使われることがあります。Goの `crypto/cipher` パッケージが非標準ノンス長をサポートすることで、これらのシステムとの相互運用性が向上し、Goアプリケーションがより多様な環境でGCMを使用できるようになります。

## 技術的詳細

Go 1.5で `crypto/cipher` パッケージのGCM実装が非標準ノンス長をサポートするようになった技術的な詳細は、主に `NewGCMWithNonceSize` 関数（またはそれに相当する内部ロジック）の導入にあります。

標準的なGCMの初期化関数 `cipher.NewGCM(cipher.Block)` は、内部的に96ビットのノンス長を前提としています。しかし、非標準ノンス長をサポートするためには、GCMインスタンスを生成する際に、使用するノンス長を明示的に指定できるメカニズムが必要です。

GCMの仕様（NIST SP 800-38D）では、ノンス長が96ビットでない場合、そのノンスはGHASH関数に入力される前に、特定の変換処理（`GHASH` 関数への入力として、ノンスの後にゼロパディングとノンスのビット長を連結する）を経て128ビットのブロックに「整形」されます。この変換は、ノンスが96ビットの場合にはスキップされ、ノンス自体が直接GHASHの初期入力として使用されます。

Goの変更は、この変換ロジックを `crypto/cipher` パッケージのGCM実装に組み込むことで、ユーザーが任意のノンス長を指定できるようにしたものです。これにより、開発者は `NewGCMWithNonceSize` のような関数を通じて、例えば `aes.NewCipher` で生成したブロック暗号と、希望するノンス長を渡してGCMインスタンスを作成できるようになります。

この変更のセキュリティ上の考慮事項としては、ノンスの再利用が依然として最大の脅威であるという点です。ノンス長が非標準であっても、各暗号化操作でノンスが一意であるというGCMの基本的な要件は変わりません。ノンスの長さが短い場合、衝突の可能性が高まるため、より慎重なノンス生成戦略が必要になります。また、ノンス長が非常に長い場合、パフォーマンスに影響を与える可能性があります。

## コアとなるコードの変更箇所

このコミット自体は `doc/go1.5.txt` のドキュメント変更のみですが、ここで言及されている「非標準GCMノンス長のサポート」を実装したコアとなる変更は、以下のGo Change List (CL) で行われました。

*   **CL 8946**: `crypto/cipher: allow non-standard GCM nonce lengths`
    *   リンク: `https://golang.org/cl/8946`

このCLでは、主に `crypto/cipher/gcm.go` ファイルが変更されました。具体的には、`NewGCMWithNonceSize` 関数が追加され、GCM構造体の初期化ロジックが更新されました。

## コアとなるコードの解説

CL 8946における `crypto/cipher/gcm.go` の変更は、主に以下の点に集約されます。

1.  **`NewGCMWithNonceSize` 関数の追加:**
    この関数は、`cipher.Block` インターフェースを実装するブロック暗号と、希望するノンス長（`nonceSize`）を引数として受け取ります。
    ```go
    func NewGCMWithNonceSize(cipher cipher.Block, nonceSize int) (cipher.AEAD, error) {
        // ...
    }
    ```
    この関数内部で、指定された `nonceSize` に基づいてGCM構造体が初期化されます。

2.  **GCM構造体の内部ロジックの更新:**
    `gcm` 構造体には、`nonceSize` フィールドが追加され、GCMインスタンスがどのノンス長で動作するかを記憶するようになりました。
    `gcm.Seal` および `gcm.Open` メソッド内で、ノンスの処理ロジックが更新されました。具体的には、入力されたノンスの長さが `g.nonceSize` と一致するかどうかを確認し、一致しない場合はエラーを返します。
    最も重要な変更は、ノンスが96ビットでない場合のGHASH入力の準備方法です。
    *   ノンスが96ビットの場合: ノンスは直接GHASHの初期入力として使用されます。
    *   ノンスが96ビットでない場合: ノンスはGHASH関数に渡される前に、NIST SP 800-38Dで定義されている変換処理（ゼロパディングとノンスのビット長を連結する）が適用されます。これにより、任意の長さのノンスがGHASHの128ビットブロック入力要件を満たすように調整されます。

この変更により、Goの `crypto/cipher` パッケージは、標準的な96ビットノンスだけでなく、他の長さのノンスを使用するGCM実装とも互換性を持つようになりました。これにより、Goアプリケーションは、より多様な暗号化プロトコルや既存システムとの相互運用性を実現できます。

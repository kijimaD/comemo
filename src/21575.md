# [インデックス 21575] ファイルの概要

このコミットは、GoランタイムがFreeBSD上でシステムコールを実行する際のメカニズムに関する重要な変更を導入しています。具体的には、以前のコミットで導入された`SYSCALL`命令の回避策を元に戻し、FreeBSDの特定のバージョン（8-STABLE以降）でネイティブの`SYSCALL`命令を直接使用するように修正しています。これにより、GoのFreeBSDサポートにおける最小要件が更新され、ドキュメントにもその旨が反映されています。

## 元コミット内容

このコミットの元となった変更は、ハッシュ`555da73`のコミットで、Go issue #6372に関連しています。そのコミットでは、FreeBSDの特定のバージョン（FreeBSD 8, 9など）において、`SYSCALL`命令を使用したシステムコールが「再開された」システムコール（restarted system call）から戻る際に、レジスタ`R10`が正しく復元されないというバグが存在していました。このバグにより、システムコールへの4番目の引数が失われる可能性がありました。

この問題を回避するため、`555da73`では`SYSCALL`命令の代わりに、より古い`INT $0x80`命令を使用してシステムコールを実行するようGoランタイムが変更されていました。`INT $0x80`は`SYSCALL`よりも低速ですが、このレジスタ復元問題の影響を受けないため、一時的な回避策として採用されていました。

## 変更の背景

このコミットの背景には、FreeBSDのカーネルにおけるシステムコール処理の進化と、Goランタイムがその変化にどのように適応してきたかという歴史があります。

元々、GoランタイムはFreeBSD上でシステムコールを実行するために、`SYSCALL`命令を使用しようとしていました。しかし、FreeBSD 8および9の特定のバージョンにおいて、`SYSCALL`命令が使用された際に、カーネルが「再開された」システムコールから戻る際にレジスタ`R10`（システムコールへの4番目の引数を保持するレジスタ）を正しく復元しないというバグが発見されました。これは、FreeBSDの`amd64/amd64/exception.S`内の`fast_syscall`ルーチンに起因するもので、システムコールからの復帰時に`DI`, `SI`, `DX`, `AX`, `RFLAGS`のみを復元し、`R10`（および一部のバージョンでは`R8`, `R9`）を復元しないという問題がありました。

この問題はGo issue #6372として報告され、その回避策としてコミット`555da73`が導入されました。この回避策では、`SYSCALL`命令の代わりに、より古い`INT $0x80`命令を使用するようにGoランタイムが変更されました。`INT $0x80`は`SYSCALL`よりもオーバーヘッドが大きいものの、このレジスタ復元問題の影響を受けないため、Goプログラムの安定性を確保するために採用されました。

しかし、FreeBSDの新しいバージョン、特に`8-STABLE`以降では、この`R10`レジスタの復元問題が修正されたと考えられます。このコミットは、FreeBSDカーネルの改善を反映し、Goランタイムが再びネイティブで高速な`SYSCALL`命令を使用できるようにするために、以前の回避策（`555da73`）を元に戻すことを目的としています。これにより、GoプログラムのFreeBSD上でのパフォーマンスが向上し、より現代的なシステムコールメカニズムを利用できるようになります。

また、この変更に伴い、GoがサポートするFreeBSDの最小バージョンが「FreeBSD 8-STABLE」に更新されました。これは、`SYSCALL`命令の正しい動作が保証されるバージョンを明確にするためです。Go issue #9627もこの変更によって修正されるとされていますが、その具体的な関連性は、システムコール処理のより広範な改善の一部である可能性が示唆されています。

## 前提知識の解説

### システムコール (System Call)

システムコールは、ユーザー空間のプログラムがオペレーティングシステム（OS）のカーネル空間の機能にアクセスするためのメカニズムです。ファイルI/O、メモリ管理、プロセス制御など、OSが提供するほとんどのサービスはシステムコールを通じて利用されます。

x86-64アーキテクチャでは、システムコールを実行するための主要な方法がいくつかあります。

1.  **`INT $0x80` (ソフトウェア割り込み)**:
    *   これは古いシステムコールメカニズムで、32ビットシステムで広く使われていました。
    *   プログラムは`INT $0x80`命令を発行し、これによりCPUは割り込みハンドラにジャンプします。
    *   システムコール番号は`EAX`レジスタに、引数は`EBX`, `ECX`, `EDX`, `ESI`, `EDI`, `EBP`などのレジスタに格納されます。
    *   コンテキストスイッチのオーバーヘッドが大きく、現代のシステムではより高速なメカニズムが推奨されます。

2.  **`SYSCALL` (高速システムコール)**:
    *   AMDが開発し、Intelも採用した高速なシステムコールメカニズムです。
    *   `SYSCALL`命令は、`INT $0x80`よりも少ないCPUサイクルでカーネルに移行できます。
    *   システムコール番号は`RAX`レジスタに、引数は`RDI`, `RSI`, `RDX`, `R10`, `R8`, `R9`などのレジスタに格納されます（呼び出し規約によって異なる場合があります）。
    *   このメカニズムは、特に多数のシステムコールを頻繁に実行するアプリケーション（Goランタイムなど）にとってパフォーマンス上の利点があります。

### FreeBSDのシステムコール処理

FreeBSDでは、x86-64アーキテクチャにおいて`SYSCALL`命令を使用した高速なシステムコールパスが提供されています。このパスは、`amd64/amd64/exception.S`内の`fast_syscall`ルーチンによって処理されます。

### レジスタの役割 (x86-64 AMD64 System V ABI)

Goは通常、x86-64 AMD64 System V ABI（Application Binary Interface）に従って関数呼び出しやシステムコール引数を扱います。このABIでは、関数呼び出しの最初の6つの整数/ポインタ引数は以下のレジスタに渡されます。

*   第1引数: `RDI`
*   第2引数: `RSI`
*   第3引数: `RDX`
*   第4引数: `RCX` (ただし、システムコールでは`R10`が使われることが多い)
*   第5引数: `R8`
*   第6引数: `R9`

システムコールにおいては、`SYSCALL`命令を使用する場合、通常は`R10`が4番目の引数として使用されます。

### 「再開された」システムコール (Restarted System Call) と `ERESTART`

一部のシステムコールは、実行中にシグナルなどの外部イベントによって中断されることがあります。このような場合、カーネルはシステムコールを中断し、シグナルハンドラを実行した後、システムコールを最初から「再開」しようとすることがあります。この再開のメカニズムは、システムコールが`ERESTART`という内部エラーコードを返すことでトリガーされます。カーネルは、`ERESTART`を受け取ると、プログラムカウンタ（PC）をシステムコール命令の直前に戻し、システムコールを再実行します。

### FreeBSDのバージョン表記

*   **FreeBSD 8**: 特定のメジャーリリースバージョン。
*   **FreeBSD 8-STABLE**: FreeBSDの安定版ブランチを指します。`STABLE`ブランチは、特定のメジャーリリース（例: 8.x）のリリース後に、バグ修正やセキュリティアップデート、一部の機能改善が継続的に適用されるブランチです。これに対し、`RELEASE`バージョンは特定の時点でのスナップショットであり、`CURRENT`は開発中の最新版を指します。`8-STABLE`は、FreeBSD 8のリリース後に安定性を保ちつつ改善が加えられたバージョン群を意味します。

## 技術的詳細

このコミットの核心は、FreeBSDカーネルの`SYSCALL`命令処理における特定のバグとその修正、そしてGoランタイムがその修正にどのように対応したかにあります。

### FreeBSDカーネルのバグ

FreeBSD 8、FreeBSD 9、およびそれ以前のバージョンにおいて、`SYSCALL`命令を使用してシステムコールを実行し、そのシステムコールがシグナルなどによって中断され「再開された」場合、カーネルはシステムコールからの復帰時にレジスタ`R10`を正しく復元しませんでした。

具体的には、FreeBSDの`amd64/amd64/exception.S`ファイルにある`fast_syscall`ルーチンが問題の原因でした。このルーチンは、システムコールからの復帰時に`DI`, `SI`, `DX`, `AX`, `RFLAGS`レジスタのみを復元し、`R10`（および一部の古いバージョンでは`R8`, `R9`）を復元しませんでした。これにより、システムコールへの4番目の引数（通常`R10`に格納される）が失われ、Goプログラムが誤動作する可能性がありました。例えば、`wait4`システムコールが実行中にシグナルを受け取ると、カーネルは内部的に`ERESTART`を返し、PCを戻して`wait4`を再実行しようとしますが、`R10`が復元されないため、4番目の引数が失われ、結果としてシステムコールが失敗したり、予期せぬ動作を引き起こしたりしました。

### 以前のGoランタイムの回避策

このバグに対処するため、Goランタイムはコミット`555da73`で一時的な回避策を導入しました。それは、`SYSCALL`命令の代わりに`INT $0x80`命令を使用することでした。

Goのソースコードでは、`src/runtime/sys_freebsd_amd64.s`および`src/syscall/asm_freebsd_amd64.s`において、以下のようなマクロ定義が使用されていました。

```assembly
#define SYSCALL MOVQ R10, CX; INT $0x80
```

このマクロは、Goのコードが`SYSCALL`と記述している箇所を、実際には`R10`レジスタの内容を`CX`レジスタに移動させた後、`INT $0x80`命令を実行するように変換していました。`INT $0x80`パスは、`R10`の復元問題の影響を受けないため、この回避策はGoプログラムの安定性を確保しました。しかし、`INT $0x80`は`SYSCALL`よりも低速であり、パフォーマンス上のオーバーヘッドがありました。

### このコミットによる変更

このコミットは、FreeBSDカーネルの改善（特に`8-STABLE`以降のバージョンで`R10`の復元問題が修正されたこと）を受けて、以前の`INT $0x80`への回避策を元に戻し、ネイティブの`SYSCALL`命令を直接使用するようにGoランタイムを修正します。

具体的には、`src/runtime/sys_freebsd_amd64.s`および`src/syscall/asm_freebsd_amd64.s`から、`#define SYSCALL MOVQ R10, CX; INT $0x80`という行と、その問題に関する詳細なコメントが削除されます。これにより、Goのコードが`SYSCALL`と記述している箇所は、コンパイラによって直接`SYSCALL`命令に変換されるようになります。

この変更は、GoがFreeBSD上でより効率的なシステムコールメカニズムを利用できるようになることを意味し、結果としてGoプログラムのパフォーマンス向上が期待されます。

### ドキュメントの更新

この技術的な変更に伴い、Goのインストールガイド（`doc/install.html`）も更新されました。FreeBSDのサポート要件が「FreeBSD 8 or later」から「FreeBSD 8-STABLE or later」に変更され、Goが正しく動作するために必要なFreeBSDの最小バージョンがより明確に示されています。これは、`SYSCALL`命令の正しい動作が保証されるのが`8-STABLE`以降のバージョンであるためです。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`doc/install.html`**:
    *   Goのインストールガイドのドキュメント。
    *   FreeBSDのサポートバージョンに関する記述が「FreeBSD 8 or later」から「FreeBSD 8-STABLE or later」に更新されました。

2.  **`src/runtime/sys_freebsd_amd64.s`**:
    *   GoランタイムのFreeBSD AMD64アーキテクチャ向けアセンブリコード。
    *   以前のコミット`555da73`で追加された、`SYSCALL`命令の代わりに`INT $0x80`を使用するためのマクロ定義と、その問題に関する詳細なコメントが削除されました。
    *   具体的には、以下の25行が削除されています。
        ```assembly
        // FreeBSD 8, FreeBSD 9, and older versions that I have checked
        // do not restore R10 on exit from a "restarted" system call
        // if you use the SYSCALL instruction. This means that, for example,
        // if a signal arrives while the wait4 system call is executing,
        // the wait4 internally returns ERESTART, which makes the kernel
        // back up the PC to execute the SYSCALL instruction a second time.
        // However, since the kernel does not restore R10, the fourth
        // argument to the system call has been lost. (FreeBSD 9 also fails
        // to restore the fifth and sixth arguments, R8 and R9, although
        // some earlier versions did restore those correctly.)
        // The broken code is in fast_syscall in FreeBSD's amd64/amd64/exception.S.
        // It restores only DI, SI, DX, AX, and RFLAGS on system call return.
        // http://fxr.watson.org/fxr/source/amd64/amd64/exception.S?v=FREEBSD91#L399
        //
        // The INT $0x80 system call path (int0x80_syscall in FreeBSD's 
        // amd64/ia32/ia32_exception.S) does not have this problem,
        // but it expects the third argument in R10. Instead of rewriting
        // all the assembly in this file, #define SYSCALL to a safe simulation
        // using INT $0x80.
        //
        // INT $0x80 is a little slower than SYSCALL, but correctness wins.
        //
        // See golang.org/issue/6372.
        #define SYSCALL MOVQ R10, CX; INT $0x80
        ```

3.  **`src/syscall/asm_freebsd_amd64.s`**:
    *   Goの`syscall`パッケージのFreeBSD AMD64アーキテクチャ向けアセンブリコード。
    *   `src/runtime/sys_freebsd_amd64.s`と同様に、`SYSCALL`命令の回避策に関するマクロ定義とコメントが削除されました。
    *   具体的には、以下の5行が削除されています。
        ```assembly
        // The SYSCALL variant for invoking system calls is broken in FreeBSD.
        // See comment at top of ../runtime/sys_freebsd_amd64.c and
        // golang.org/issue/6372.
        #define SYSCALL MOVQ R10, CX; INT $0x80
        ```

## コアとなるコードの解説

このコミットのコード変更は、GoランタイムがFreeBSD上でシステムコールを実行する方法を根本的に変更するものです。

以前のコードでは、FreeBSDカーネルのバグ（`SYSCALL`命令使用時に`R10`レジスタが正しく復元されない問題）を回避するために、Goのアセンブリコード内で`SYSCALL`というキーワードが使われると、実際には`MOVQ R10, CX; INT $0x80`という命令シーケンスに展開されるようにマクロ定義されていました。

*   `MOVQ R10, CX`: これは、システムコールへの4番目の引数（`R10`に格納されている）を`CX`レジスタに移動させるためのものです。`INT $0x80`システムコールパスは、32ビットの呼び出し規約に準拠しており、4番目の引数を`CX`レジスタで期待するため、このレジスタ移動が必要でした。
*   `INT $0x80`: ソフトウェア割り込みを発生させ、カーネルの`INT $0x80`ハンドラを通じてシステムコールを実行します。このパスは`R10`の復元問題の影響を受けませんでしたが、`SYSCALL`命令に比べてオーバーヘッドが大きいです。

このコミットでは、上記の`#define SYSCALL MOVQ R10, CX; INT $0x80`というマクロ定義が削除されます。これにより、Goのアセンブリコード内で`SYSCALL`と記述されている箇所は、コンパイラによって直接ネイティブの`SYSCALL`命令に変換されるようになります。

この変更の意図は、FreeBSDの新しいバージョン（`8-STABLE`以降）では、`SYSCALL`命令使用時の`R10`レジスタ復元問題が修正されているため、Goランタイムがより効率的で現代的な`SYSCALL`命令を直接利用できるようにすることです。これにより、システムコール実行時のオーバーヘッドが削減され、Goプログラムの全体的なパフォーマンスが向上します。

また、関連するコメントも削除されており、これは以前の回避策がもはや不要であることを明確に示しています。ドキュメントの更新は、この変更がGoのFreeBSDサポートの最小要件に影響を与えることをユーザーに伝えるためのものです。

# [インデックス 23287] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/internal/ld`) において、共有ライブラリ (`-buildmode=shared`) をビルドする際に、パッケージリストノートのために予約する領域を増やす変更を導入しています。これにより、中間オブジェクトファイルのサイズは若干増加しますが、最終的な共有ライブラリのサイズには影響を与えません。

## 変更の背景

この変更の背景には、Go言語で共有ライブラリをビルドする際のリンカの挙動と、`package list note` のサイズに関する問題があります。

Goのリンカは、実行可能ファイルやライブラリを生成する際に、様々なメタデータを埋め込みます。その一つに「パッケージリストノート」があります。これは、Goの共有ライブラリが依存するパッケージのリストを記録するためのもので、ランタイムが共有ライブラリをロードする際に、そのライブラリがどのGoパッケージに依存しているかを識別するために使用されます。

以前のリンカの実装では、このパッケージリストノートのために予約される初期スペース (`ELFRESERVE`) が固定サイズでした。しかし、`go build -buildmode=shared` を使用して大規模なGoプログラムを共有ライブラリとしてビルドする場合、依存するパッケージの数が非常に多くなり、このパッケージリストノートが初期予約サイズをはるかに超えることがありました。

予約されたスペースが不足すると、リンカはノートを書き込む際にバッファオーバーフローのような問題を引き起こす可能性があり、ビルドプロセスが失敗したり、生成されるライブラリが不正になったりするリスクがありました。この問題は、Go issue #10691 で報告されており、このコミットはその問題を解決するために導入されました。

このコミットの目的は、共有ライブラリビルド時にパッケージリストノートが大きくなることを考慮し、中間オブジェクトファイルにおいて、より多くのスペースを事前に予約することで、リンカがノートを適切に書き込めるようにすることです。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **Goリンカ (`cmd/internal/ld`)**: Go言語のコンパイラツールチェーンの一部であり、コンパイルされたオブジェクトファイル群を結合して、実行可能ファイルやライブラリ（静的ライブラリ、共有ライブラリ）を生成するプログラムです。`ld` は "loader" または "linker" の略です。
*   **`-buildmode=shared`**: `go build` コマンドのオプションの一つで、Goパッケージを共有ライブラリ（ダイナミックリンクライブラリ）としてビルドすることを指定します。これにより、複数のGoプログラムが同じライブラリを共有できるようになり、ディスクスペースの節約や起動時間の短縮に寄与する場合があります。
*   **ELF (Executable and Linkable Format)**: Unix系システムで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準ファイルフォーマットです。Goのリンカは、LinuxなどのシステムでELF形式のファイルを生成します。
*   **ELFヘッダ (`ELFRESERVE`, `HEADR`)**: ELFファイルは、ファイルの先頭にヘッダ情報を持っています。`ELFRESERVE` は、ELFヘッダやプログラムヘッダテーブルなどの初期メタデータのためにリンカが予約するデフォルトのバイト数を指します。`HEADR` は、Goリンカ内部で使われる、ELFヘッダとプログラムヘッダの合計サイズを表す変数です。
*   **パッケージリストノート (`.note.go.pkg-list`)**: Goの共有ライブラリに埋め込まれるELFノートセクションの一種です。このノートには、その共有ライブラリが依存するGoパッケージのパスとバージョン情報がリストアップされます。Goランタイムは、共有ライブラリをロードする際にこの情報を参照し、依存関係の解決やバージョンの整合性チェックを行います。
*   **中間オブジェクトファイルと最終共有ライブラリ**: ビルドプロセスでは、まずGoソースコードがコンパイルされて個々の中間オブジェクトファイルが生成されます。その後、リンカがこれらのオブジェクトファイルを結合し、最終的な実行可能ファイルや共有ライブラリを生成します。このコミットで言及されている「中間オブジェクトファイル」は、リンカが最終的な共有ライブラリを生成する前に一時的に作成するファイル、またはリンカが内部的に扱うデータ構造を指します。重要なのは、外部リンカが最終的な共有ライブラリを生成する際に、セクションのレイアウトを再配置するため、中間ファイルでの余分なスペース予約が最終ファイルに影響しないという点です。

## 技術的詳細

このコミットの技術的な核心は、GoリンカがELF形式の共有ライブラリを生成する際の、初期ヘッダ領域のサイズ計算と、`package list note` の動的なサイズ要件への対応です。

Goリンカは、ELFファイルを生成する際に、ファイルの先頭にELFヘッダとプログラムヘッダテーブルを配置します。これらのヘッダは、OSが実行可能ファイルやライブラリをロードするために必要な情報を含んでいます。リンカは、これらのヘッダのために一定の初期スペースを予約します。この初期スペースのデフォルト値は `ELFRESERVE` という定数で定義されています。

共有ライブラリ (`-buildmode=shared`) をビルドする場合、Goリンカは `.note.go.pkg-list` という特別なELFノートセクションを生成し、これにライブラリが依存するすべてのGoパッケージのリストを書き込みます。このパッケージリストは、依存するパッケージの数が増えるにつれて大きくなります。

以前の実装では、`ELFRESERVE` の固定値が、このパッケージリストノートの最大サイズを考慮していませんでした。そのため、大規模な共有ライブラリをビルドする際に、パッケージリストノートが `ELFRESERVE` で予約されたスペースを超過し、リンカがノートを書き込む際に問題が発生していました。

このコミットでは、この問題を解決するために、`BuildmodeShared` の場合にのみ、`ELFRESERVE` の値を3倍に拡張しています。これにより、中間オブジェクトファイル（またはリンカが内部的に構築するELF構造）において、パッケージリストノートのために十分なスペースが確保されるようになります。

コミットメッセージにある「The external linker will re-layout all the sections anyway, so making this larger just wastes a little space in the intermediate object file, not the final shared library.」という説明は重要です。Goリンカは、最終的な共有ライブラリを生成する前に、一度ELF形式の中間オブジェクトファイルを生成します。その後、システムにインストールされている外部リンカ（例: `ld`）が、この中間オブジェクトファイルをさらに処理し、最終的な共有ライブラリを生成します。外部リンカは、この過程でELFファイルのセクションレイアウトを最適化し、不要なパディングや予約領域を削除することが一般的です。したがって、Goリンカが中間ファイルで少し多めにスペースを予約しても、最終的な共有ライブラリのサイズには影響しない、というわけです。

また、`src/cmd/internal/ld/elf.go` の変更では、`elfreserve` というローカル変数に `ELFRESERVE` の値をコピーし、`BuildmodeShared` の場合にこの `elfreserve` を3倍にしています。そして、最終的なサイズチェック (`if a > elfreserve`) でこの拡張された値を使用することで、パッケージリストノートのサイズが予約領域を超過しないようにしています。

## コアとなるコードの解説

このコミットのコアとなる変更は、GoリンカがELFファイルを構築する際に、ヘッダ領域のサイズを決定するロジックにあります。

`src/cmd/6l/obj.go` の変更は、アーキテクチャ固有の初期化を行う `archinit` 関数内で、`ld.HEADR` の値を調整しています。`ld.HEADR` は、ELFヘッダとプログラムヘッダの合計サイズを表すGoリンカ内部の変数です。共有ライブラリをビルドする場合、この `HEADR` を3倍にすることで、リンカが内部的に構築するELF構造の初期ヘッダ領域を拡張し、将来的に大きくなる可能性のあるパッケージリストノートのためのスペースを確保します。

`src/cmd/internal/ld/elf.go` の変更は、ELFファイルをアセンブルする `Asmbelf` 関数内で、より詳細な制御を行っています。
`elfreserve` というローカル変数を導入し、`ELFRESERVE` のデフォルト値を保持します。そして、`BuildmodeShared` の場合にのみ、この `elfreserve` の値を3倍に更新します。
この `elfreserve` は、`resoff` (予約オフセット) の初期値として使用され、また、最終的に書き込まれたデータ量 `a` が予約されたスペース `elfreserve` を超えていないかをチェックする際に使用されます。
これにより、共有ライブラリビルド時に、パッケージリストノートが大きくなっても、リンカが「ELFRESERVE too small」というエラーを発生させることなく、適切に処理できるようになります。

この変更のポイントは、中間オブジェクトファイルでの予約領域の拡大が、最終的な共有ライブラリのサイズに影響を与えないというリンカの特性を理解している点です。外部リンカが最終的なバイナリを生成する際に、セクションの再配置と最適化を行うため、Goリンカが一時的に多めにスペースを確保しても問題ないという判断に基づいています。

*   **中間オブジェクトファイルと最終共有ライブラリ**: ビルドプロセスでは、まずGoソースコードがコンパイルされて個々の中間オブジェクトファイルが生成されます。その後、リンカがこれらのオブジェクトファイルを結合し、最終的な実行可能ファイルや共有ライブラリを生成します。このコミットで言及されている「中間オブジェクトファイル」は、リンカが最終的な共有ライブラリを生成する前に一時的に作成するファイル、またはリンカが内部的に扱うデータ構造を指します。重要なのは、外部リンカが最終的な共有ライブラリを生成する際に、セクションのレイアウトを再配置するため、中間ファイルでの余分なスペース予約が最終ファイルに影響しないという点です。

## 技術的詳細

このコミットの技術的な核心は、GoリンカがELF形式の共有ライブラリを生成する際の、初期ヘッダ領域のサイズ計算と、`package list note` の動的なサイズ要件への対応です。

Goリンカは、ELFファイルを生成する際に、ファイルの先頭にELFヘッダとプログラムヘッダテーブルを配置します。これらのヘッダは、OSが実行可能ファイルやライブラリをロードするために必要な情報を含んでいます。リンカは、これらのヘッダのために一定の初期スペースを予約します。この初期スペースのデフォルト値は `ELFRESERVE` という定数で定義されています。

共有ライブラリ (`-buildmode=shared`) をビルドする場合、Goリンカは `.note.go.pkg-list` という特別なELFノートセクションを生成し、これにライブラリが依存するすべてのGoパッケージのリストを書き込みます。このパッケージリストは、依存するパッケージの数が増えるにつれて大きくなります。

以前の実装では、`ELFRESERVE` の固定値が、このパッケージリストノートの最大サイズを考慮していませんでした。そのため、大規模な共有ライブラリをビルドする際に、パッケージリストノートが `ELFRESERVE` で予約されたスペースを超過し、リンカがノートを書き込む際に問題が発生していました。

このコミットでは、この問題を解決するために、`BuildmodeShared` の場合にのみ、`ELFRESERVE` の値を3倍に拡張しています。これにより、中間オブジェクトファイル（またはリンカが内部的に構築するELF構造）において、パッケージリストノートのために十分なスペースが確保されるようになります。

コミットメッセージにある「The external linker will re-layout all the sections anyway, so making this larger just wastes a little space in the intermediate object file, not the final shared library.」という説明は重要です。Goリンカは、最終的な共有ライブラリを生成する前に、一度ELF形式の中間オブジェクトファイルを生成します。その後、システムにインストールされている外部リンカ（例: `ld`）が、この中間オブジェクトファイルをさらに処理し、最終的な共有ライブラリを生成します。外部リンカは、この過程でELFファイルのセクションレイアウトを最適化し、不要なパディングや予約領域を削除することが一般的です。したがって、Goリンカが中間ファイルで少し多めにスペースを予約しても、最終的な共有ライブラリのサイズには影響しない、というわけです。

また、`src/cmd/internal/ld/elf.go` の変更では、`elfreserve` というローカル変数に `ELFRESERVE` の値をコピーし、`BuildmodeShared` の場合にこの `elfreserve` を3倍にしています。そして、最終的なサイズチェック (`if a > elfreserve`) でこの拡張された値を使用することで、パッケージリストノートのサイズが予約領域を超過しないようにしています。

## コアとなるコードの解説

このコミットのコアとなる変更は、GoリンカがELFファイルを構築する際に、ヘッダ領域のサイズを決定するロジックにあります。

`src/cmd/6l/obj.go` の変更は、アーキテクチャ固有の初期化を行う `archinit` 関数内で、`ld.HEADR` の値を調整しています。`ld.HEADR` は、ELFヘッダとプログラムヘッダの合計サイズを表すGoリンカ内部の変数です。共有ライブラリをビルドする場合、この `HEADR` を3倍にすることで、リンカが内部的に構築するELF構造の初期ヘッダ領域を拡張し、将来的に大きくなる可能性のあるパッケージリストノートのためのスペースを確保します。

`src/cmd/internal/ld/elf.go` の変更は、ELFファイルをアセンブルする `Asmbelf` 関数内で、より詳細な制御を行っています。
`elfreserve` というローカル変数を導入し、`ELFRESERVE` のデフォルト値を保持します。そして、`BuildmodeShared` の場合にのみ、この `elfreserve` の値を3倍に更新します。
この `elfreserve` は、`resoff` (予約オフセット) の初期値として使用され、また、最終的に書き込まれたデータ量 `a` が予約されたスペース `elfreserve` を超えていないかをチェックする際に使用されます。
これにより、共有ライブラリビルド時に、パッケージリストノートが大きくなっても、リンカが「ELFRESERVE too small」というエラーを発生させることなく、適切に処理できるようになります。

この変更のポイントは、中間オブジェクトファイルでの予約領域の拡大が、最終的な共有ライブラリのサイズに影響を与えないというリンカの特性を理解している点です。外部リンカが最終的なバイナリを生成する際に、セクションの再配置と最適化を行うため、Goリンカが一時的に多めにスペースを確保しても問題ないという判断に基づいています。

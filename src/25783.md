## 元コミット内容

`cmd/compile: print regular error message in BOM corner-case`

このコミットは、バイトオーダーマーク（BOM）の処理における特殊なケースで、Goコンパイラがより適切なエラーメッセージを出力するように変更します。具体的には、BOMシーケンスが不完全な状態でファイルの終端（EOF）に達した場合の挙動を改善します。このような状況は「病的な入力」と表現されており、通常は発生しない極めて稀なケースです。テストフレームワークでは再現が困難なため、手動でテストされました。

## 変更の背景

この変更は、Go Issue #13268 に対応するものです。Goコンパイラはソースファイルを読み込む際に、UTF-8エンコーディングを期待します。UTF-8のバイトオーダーマーク（BOM）は、ファイルの先頭に付加されることでエンコーディングを示すことがありますが、Goでは通常BOMを推奨していません。

問題となっていたのは、ソースコード中に不完全なBOMシーケンス（UTF-8のBOMは `0xef 0xbb 0xbf` の3バイト）が存在し、その途中でファイルの終端（EOF）に達した場合のコンパイラの挙動でした。以前の実装では、このような状況で `obj.Bgetc` がファイルの読み込みエラーを返すと、コンパイラは `log.Fatalf` を呼び出してプログラムを異常終了させていました。これはユーザーにとって分かりにくいエラーメッセージであり、コンパイラがクラッシュしたように見える可能性がありました。

このコミットの目的は、このような稀な「病的な入力」に対しても、コンパイラがクラッシュするのではなく、よりユーザーフレンドリーで診断に役立つエラーメッセージを報告するように改善することです。

## 前提知識の解説

### バイトオーダーマーク (BOM)
バイトオーダーマーク（Byte Order Mark, BOM）は、Unicodeテキストファイルの先頭に付加される特殊なバイト列で、そのファイルがどのUnicodeエンコーディング（UTF-8, UTF-16, UTF-32など）で記述されているか、またUTF-16やUTF-32の場合はバイトオーダー（ビッグエンディアンかリトルエンディアンか）を示すために使用されます。
UTF-8のBOMは `0xEF 0xBB 0xBF` の3バイトシーケンスです。UTF-8はバイトオーダーの概念を持たないため、BOMは必須ではありません。むしろ、多くのUnix系ツールやプログラミング言語（Goを含む）では、BOMなしのUTF-8を標準としており、BOMが存在すると問題を引き起こすことがあります。Goコンパイラは、ファイルの先頭にBOMがある場合はそれをスキップしますが、ファイルの中間にあるBOMはエラーとして扱います。

### UTF-8エンコーディング
UTF-8は、Unicode文字を可変長のバイト列で表現するエンコーディング方式です。ASCII文字は1バイトで表現され、それ以外の文字は2バイトから4バイトで表現されます。Go言語のソースコードは、UTF-8で記述されることが標準とされています。

### Goコンパイラの字句解析器 (Lexer)
コンパイラは、ソースコードを処理する際にいくつかの段階を経ます。
1.  **字句解析 (Lexical Analysis)**: ソースコードの文字列を、意味のある最小単位（トークン）に分解します。この処理を行うのが字句解析器（lexerまたはscanner）です。例えば、「`func main() {`」というコードは、「`func`」（キーワード）、「`main`」（識別子）、「`(`」（記号）、「`)`」（記号）、「`{`」（記号）といったトークンに分解されます。
2.  **構文解析 (Syntactic Analysis)**: トークンの列が文法的に正しいかを検証し、抽象構文木（AST）を構築します。
3.  **意味解析 (Semantic Analysis)**: 型チェックなど、意味的な正当性を検証します。
4.  **コード生成 (Code Generation)**: 実行可能な機械語コードなどを生成します。

このコミットが関連するのは、字句解析の段階です。`src/cmd/compile/internal/gc/lex.go` は、Goコンパイラの字句解析器の一部であり、ソースファイルを文字単位で読み込み、トークンを生成する役割を担っています。`getc()` 関数は、次の文字を読み込むための内部関数です。

### `log.Fatalf` と `yyerrorl`/`errorexit`
*   `log.Fatalf`: Goの標準ライブラリ `log` パッケージの関数で、メッセージを出力した後に `os.Exit(1)` を呼び出してプログラムを終了させます。これは通常、回復不能な内部エラーや予期せぬ状況で使われます。ユーザーにとっては、コンパイラがクラッシュしたように見えます。
*   `yyerrorl`: Goコンパイラの内部関数で、指定された行番号でエラーメッセージを報告します。これは、コンパイルエラーとしてユーザーに表示される通常の診断メッセージを生成するために使用されます。
*   `errorexit()`: コンパイルエラーが発生したことを示し、コンパイルプロセスを適切に終了させるための関数です。`log.Fatalf` のように即座にプログラムを終了させるのではなく、エラー状態を設定し、最終的にコンパイルが失敗したことを報告します。

## 技術的詳細

変更が行われた `src/cmd/compile/internal/gc/lex.go` ファイルは、Goコンパイラの字句解析器の中核部分です。`getc()` 関数は、ソースファイルから次の文字を読み込む責任を負っています。この関数内で、BOMシーケンスの検出と処理が行われます。

UTF-8のBOMは `0xef 0xbb 0xbf` という3バイトのシーケンスです。`getc()` 関数は、まず最初のバイトが `0xef` であるかをチェックします。もし `0xef` であった場合、続く2バイト (`0xbb` と `0xbf`) を `curio.bin.Peek(2)` を使って先読みし、完全なBOMシーケンスであるかを確認します。

このコミットが修正するのは、`Peek(2)` の呼び出しでエラーが発生した場合の挙動です。`Peek` は、指定されたバイト数を先読みしようとしますが、ファイルの終端に達するなどして十分なバイト数を読み込めない場合にエラーを返します。

以前の実装では、この `Peek` エラーが発生した場合、`log.Fatalf("getc: peeking: %v", err)` が呼び出されていました。これは、コンパイラが内部エラーで異常終了することを意味します。

新しい実装では、`Peek` エラーが発生した場合に `log.Fatalf` を呼び出す代わりに、以下の2つの関数が呼び出されます。
1.  `yyerrorl(int(lexlineno), "illegal UTF-8 sequence ef % x followed by read error (%v)", string(buf), err)`: これは、現在の行番号 (`lexlineno`) を指定して、より詳細でユーザーに分かりやすいエラーメッセージを生成します。メッセージは「不正なUTF-8シーケンス `ef` に続く読み込みエラー」という内容で、先読みできたバイト列 (`buf`) と元のエラー (`err`) の情報を含みます。
2.  `errorexit()`: これは、コンパイルエラーが発生したことをコンパイラに通知し、コンパイルプロセスを正常に終了させるためのものです。これにより、コンパイラがクラッシュするのではなく、適切なエラー報告が行われます。

この変更により、不完全なBOMシーケンスがEOFで終わるという極めて稀なケースでも、コンパイラはクラッシュすることなく、診断に役立つエラーメッセージをユーザーに提供できるようになります。これは、コンパイラの堅牢性とユーザーエクスペリエンスの向上に貢献します。

## コアとなるコードの解説

変更されたコードブロックは、`getc()` 関数内で `c == 0xef` (UTF-8 BOMの最初のバイト) を検出した後のエラーハンドリング部分です。

元のコード:
```go
			if err != nil {
				log.Fatalf("getc: peeking: %v", err)
			}
```
この部分では、`curio.bin.Peek(2)` がエラーを返した場合（例えば、ファイルが `0xef` の後にEOFで終わるなど、BOMシーケンスが不完全な場合）、`log.Fatalf` が呼び出され、コンパイラが異常終了していました。これは、ユーザーにとってはコンパイラのクラッシュとして認識され、問題の診断が困難でした。

変更後のコード:
```go
			if err != nil {
				yyerrorl(int(lexlineno), "illegal UTF-8 sequence ef % x followed by read error (%v)", string(buf), err)
				errorexit()
			}
```
この変更により、`Peek` エラーが発生した場合の挙動が改善されました。
1.  `yyerrorl(...)`: `yyerrorl` 関数は、コンパイラのエラー報告メカニズムを通じて、現在の行番号 (`lexlineno`) と共に詳細なエラーメッセージを出力します。メッセージは、`"illegal UTF-8 sequence ef % x followed by read error (%v)"` となっており、`0xef` の後に続くバイト列 (`buf`) と、実際に発生した読み込みエラー (`err`) の情報が含まれます。これにより、ユーザーは問題の原因をより正確に把握できます。
2.  `errorexit()`: `errorexit` 関数は、コンパイルプロセスにエラーが発生したことを通知し、コンパイルを正常に終了させます。これにより、コンパイラがクラッシュするのではなく、エラーメッセージを出力して終了するという、より適切な挙動になります。

この修正は、Goコンパイラの堅牢性を高め、特に稀な不正な入力に対するエラー報告の品質を向上させるものです。

新しい実装では、`Peek` エラーが発生した場合に `log.Fatalf` を呼び出す代わりに、以下の2つの関数が呼び出されます。
1.  `yyerrorl(int(lexlineno), "illegal UTF-8 sequence ef % x followed by read error (%v)", string(buf), err)`: これは、現在の行番号 (`lexlineno`) を指定して、より詳細でユーザーに分かりやすいエラーメッセージを生成します。メッセージは「不正なUTF-8シーケンス `ef` に続く読み込みエラー」という内容で、先読みできたバイト列 (`buf`) と元のエラー (`err`) の情報を含みます。
2.  `errorexit()`: これは、コンパイルエラーが発生したことをコンパイラに通知し、コンパイルプロセスを正常に終了させるためのものです。これにより、コンパイラがクラッシュするのではなく、適切なエラー報告が行われます。

この変更により、不完全なBOMシーケンスがEOFで終わるという極めて稀なケースでも、コンパイラはクラッシュすることなく、診断に役立つエラーメッセージをユーザーに提供できるようになります。これは、コンパイラの堅牢性とユーザーエクスペリエンスの向上に貢献します。

## コアとなるコードの解説

変更されたコードブロックは、`getc()` 関数内で `c == 0xef` (UTF-8 BOMの最初のバイト) を検出した後のエラーハンドリング部分です。

元のコード:
```go
			if err != nil {
				log.Fatalf("getc: peeking: %v", err)
			}
```
この部分では、`curio.bin.Peek(2)` がエラーを返した場合（例えば、ファイルが `0xef` の後にEOFで終わるなど、BOMシーケンスが不完全な場合）、`log.Fatalf` が呼び出され、コンパイラが異常終了していました。これは、ユーザーにとってはコンパイラのクラッシュとして認識され、問題の診断が困難でした。

変更後のコード:
```go
			if err != nil {
				yyerrorl(int(lexlineno), "illegal UTF-8 sequence ef % x followed by read error (%v)", string(buf), err)
				errorexit()
			}
```
この変更により、`Peek` エラーが発生した場合の挙動が改善されました。
1.  `yyerrorl(...)`: `yyerrorl` 関数は、コンパイラのエラー報告メカニズムを通じて、現在の行番号 (`lexlineno`) と共に詳細なエラーメッセージを出力します。メッセージは、`"illegal UTF-8 sequence ef % x followed by read error (%v)"` となっており、`0xef` の後に続くバイト列 (`buf`) と、実際に発生した読み込みエラー (`err`) の情報が含まれます。これにより、ユーザーは問題の原因をより正確に把握できます。
2.  `errorexit()`: `errorexit` 関数は、コンパイルプロセスにエラーが発生したことを通知し、コンパイルを正常に終了させます。これにより、コンパイラがクラッシュするのではなく、エラーメッセージを出力して終了するという、より適切な挙動になります。

この修正は、Goコンパイラの堅牢性を高め、特に稀な不正な入力に対するエラー報告の品質を向上させるものです。

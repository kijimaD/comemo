# [インデックス 21474] ファイルの概要

このコミットは、Goコンパイラ（`cmd/6g`、`cmd/8g`）とリンカ（`liblink`）における浮動小数点定数の扱いを改善し、特にゼロ値の浮動小数点定数に対するコード生成を最適化するものです。具体的には、浮動小数点数の定数伝播を強化し、`0.0`を浮動小数点レジスタにロードする際に、より効率的な`XORPS`命令を使用するように変更しています。

## コミット

`cmd/6g, cmd/8g, liblink: improve handling of float constants`

このコミットは、Goコンパイラの`6g`（x86-64アーキテクチャ向け）と`8g`（x86アーキテクチャ向け）、およびリンカの`liblink`に対して、浮動小数点定数の処理を改善するものです。主な変更点は以下の2点です。

1.  **浮動小数点数の定数伝播の基本機能の有効化**: 浮動小数点定数に対する基本的な定数伝播（constant propagation）を有効にします。これにより、コンパイル時に浮動小数点定数の値が計算され、その結果がコードに直接埋め込まれるようになります。コミットメッセージには「定数伝播はまだ十分に積極的ではない」とあり、今後のさらなる最適化の余地が示唆されています。
2.  **ゼロ値浮動小数点定数の最適化**: `MOVSS $(0), Xx`（単精度浮動小数点数0をXMMレジスタ`Xx`に移動）および`MOVSD $(0), Xx`（倍精度浮動小数点数0をXMMレジスタ`Xx`に移動）といった命令を、`XORPS Xx, Xx`（XMMレジスタ`Xx`自身とのXOR演算）に置き換える最適化を実装します。`XORPS`命令は、レジスタの全ビットをゼロに設定するため、浮動小数点レジスタを効率的にゼロクリアする手法として知られています。

コミットメッセージには、`float32`と`float64`のゼロ値変数を返す単純なGoコードの例が示されており、この変更によって生成されるアセンブリコードがどのように短縮され、効率化されるかが具体的に示されています。

## 変更の背景

この変更の背景には、コンパイラが生成するアセンブリコードの効率化と最適化があります。特に、浮動小数点数のゼロ値を扱う際の冗長な命令を排除し、より高速でコンパクトなコードを生成することが目的です。

Go言語のコンパイラは、プログラムの実行速度を向上させるために様々な最適化を行います。その一つが「定数伝播（Constant Propagation）」です。これは、コンパイル時に値が確定している定数を、その定数が使用される箇所に直接埋め込むことで、実行時の計算を不要にする最適化手法です。

浮動小数点数においても、`0.0`のような定数が頻繁に現れることがあります。従来のGoコンパイラでは、このようなゼロ値を浮動小数点レジスタにロードする際に、メモリから`0.0`を読み込む`MOVSS`や`MOVSD`といった命令を使用していました。しかし、x86アーキテクチャのSSE（Streaming SIMD Extensions）命令セットには、浮動小数点レジスタを効率的にゼロクリアするための`XORPS`（XOR Packed Single-precision Floating-Point）や`XORPD`（XOR Packed Double-precision Floating-Point）といった命令が存在します。これらの命令は、レジスタ自身とのXOR演算を行うことで、レジスタの全ビットをゼロに設定します。これは、メモリからのロードよりも高速であり、命令のバイト数も少ないため、コードサイズと実行速度の両面でメリットがあります。

このコミットは、Goコンパイラが浮動小数点数のゼロ値を扱う際に、この`XORPS`命令を活用するように変更することで、生成されるアセンブリコードの品質を向上させることを目的としています。これにより、Goプログラムの浮動小数点演算を含む部分のパフォーマンスが改善されることが期待されます。

## 前提知識の解説

### 1. コンパイラの最適化

*   **定数伝播 (Constant Propagation)**: コンパイラ最適化の一種で、プログラム中の定数値を、その定数が使用されるすべての場所に伝播させる（置き換える）手法です。これにより、実行時に定数値を計算したり、メモリから読み込んだりするオーバーヘッドを削減できます。例えば、`const PI = 3.14; area = PI * r * r;` のようなコードでは、`PI`の代わりに直接`3.14`が埋め込まれます。
*   **コード生成 (Code Generation)**: コンパイラの最終段階で、中間表現からターゲットマシン（CPU）が直接実行できる機械語コード（アセンブリコード）を生成するプロセスです。この段階で、様々な最適化が適用され、効率的なコードが生成されます。
*   **アセンブリコード (Assembly Code)**: 機械語と1対1に対応する低レベルのプログラミング言語です。CPUの命令セットを直接操作するため、ハードウェアの動作を理解する上で重要です。

### 2. x86アーキテクチャとSSE命令セット

*   **x86アーキテクチャ**: Intelが開発したマイクロプロセッサの命令セットアーキテクチャで、現在のパーソナルコンピュータのほとんどで使用されています。
*   **SSE (Streaming SIMD Extensions)**: x86アーキテクチャの拡張命令セットの一つで、単一の命令で複数のデータ要素を同時に処理するSIMD（Single Instruction, Multiple Data）演算をサポートします。主に浮動小数点演算やマルチメディア処理の高速化に利用されます。
    *   **XMMレジスタ**: SSE命令で使用される128ビットのレジスタです。単精度浮動小数点数（32ビット）を4つ、または倍精度浮動小数点数（64ビット）を2つ格納できます。
*   **浮動小数点命令**:
    *   **MOVSS (Move Scalar Single-precision Floating-Point)**: メモリまたは別のXMMレジスタから、単精度浮動小数点数（32ビット）をXMMレジスタに移動する命令です。
    *   **MOVSD (Move Scalar Double-precision Floating-Point)**: メモリまたは別のXMMレジスタから、倍精度浮動小数点数（64ビット）をXMMレジスタに移動する命令です。
    *   **XORPS (XOR Packed Single-precision Floating-Point)**: 2つのXMMレジスタの対応する単精度浮動小数点数要素に対してビット単位のXOR演算を実行し、結果をデスティネーションレジスタに格納します。同じレジスタ自身に対してXOR演算を行う（例: `XORPS X0, X0`）と、そのレジスタの全ビットがゼロになります。これは、浮動小数点数の`0.0`（IEEE 754形式で全ビットがゼロ）を効率的に生成する一般的な手法です。
    *   **XORPD (XOR Packed Double-precision Floating-Point)**: `XORPS`の倍精度版です。

### 3. Goコンパイラの構造

*   **`cmd/6g`**: Go 1.x系のコンパイラで、x86-64アーキテクチャ（AMD64）向けのGoコードをコンパイルします。
*   **`cmd/8g`**: Go 1.x系のコンパイラで、x86アーキテクチャ（32ビット）向けのGoコードをコンパイルします。
*   **`src/liblink`**: Goのリンカのライブラリ部分です。コンパイラが生成したオブジェクトファイルを結合し、実行可能ファイルを生成する役割を担います。この中で、アセンブリ命令の変換や最適化が行われることがあります。
*   **`peep.c` (Peephole Optimizer)**: コンパイラのバックエンドの一部で、生成されたアセンブリコードを局所的に見て、より効率的な命令シーケンスに置き換える「ピーフホール最適化」を行うファイルです。隣接する少数の命令パターンを認識し、より良い代替パターンに置き換えることで、コードの品質を向上させます。
*   **`gsubr.c`**: Goコンパイラのバックエンドにおける汎用サブルーチンやユーティリティ関数が含まれるファイルです。
*   **`obj6.c`, `obj8.c`**: それぞれ`6g`と`8g`コンパイラが使用するオブジェクトファイル生成に関連するコードが含まれています。特に、`progedit`関数は、アセンブリ命令の最終的な編集や最適化を行う重要な部分です。

## 技術的詳細

このコミットの技術的詳細を理解するためには、Goコンパイラのバックエンドがどのようにアセンブリコードを生成し、最適化するかを把握する必要があります。

### 1. 浮動小数点定数伝播の有効化

`src/cmd/6g/peep.c`と`src/cmd/8g/peep.c`の変更は、ピーフホール最適化の段階で、浮動小数点定数（`D_FCONST`）も定数伝播の対象に含めるように修正しています。

変更前:
```c
if(p->from.type == D_CONST)
    conprop(r);
```
変更後:
```c
if(p->from.type == D_CONST || p->from.type == D_FCONST)
    conprop(r);
```
これは、`MOVSS`や`MOVSD`命令の`from`オペランドが通常の定数（`D_CONST`）だけでなく、浮動小数点定数（`D_FCONST`）である場合にも`conprop`（constant propagation）関数を呼び出すようにします。これにより、浮動小数点定数がレジスタにロードされる際に、その値がコンパイル時に既知であれば、後続の命令でその値を利用した最適化が可能になります。

また、`src/cmd/6g/peep.c`では、`regtyp`関数におけるXMMレジスタの範囲指定が`D_X0+15`から`D_X15`に修正されています。これは、XMMレジスタが`X0`から`X15`まで存在することをより正確に表現するための修正です。

### 2. ゼロ値浮動小数点定数の`XORPS`最適化

このコミットの主要な最適化は、`src/liblink/obj6.c`と`src/liblink/obj8.c`の`progedit`関数で行われています。`progedit`関数は、リンカがアセンブリ命令を処理する際に呼び出され、命令の変換や最終的な最適化を行う場所です。

変更点を見ると、`AMOVSS`（単精度浮動小数点数移動）と`AMOVSD`（倍精度浮動小数点数移動）のケースに新しいロジックが追加されています。

追加されたロジックの概要:
*   命令が`AMOVSS`または`AMOVSD`であるかを確認します。
*   `from`オペランドが浮動小数点定数（`D_FCONST`）であるかを確認します。
*   その浮動小数点定数の値が`0`であるかを確認します（`p->from.u.dval == 0`）。
*   `to`オペランドがXMMレジスタ（`D_X0`から`D_X15`または`D_X7`）であるかを確認します。

これらの条件がすべて満たされた場合、元の`MOVSS`または`MOVSD`命令を`AXORPS`命令に変換します。
```c
p->as = AXORPS; // 命令をXORPSに変更
p->from.type = p->to.type; // fromオペランドをtoオペランドと同じレジスタタイプに設定
p->from.index = p->to.index; // fromオペランドをtoオペランドと同じレジスタインデックスに設定
```
これにより、`MOVSS $(0), Xx`や`MOVSD $(0), Xx`といった命令が、`XORPS Xx, Xx`という形式に変換されます。この変換は、メモリからゼロ値をロードするよりも効率的です。

また、元の`switch`文から`AMOVSS`と`AMOVSD`が削除され、新しい`case`ブロックで処理された後に`fallthrough`（次の`case`に処理を継続）するように変更されています。これは、ゼロ値の最適化が適用されない`MOVSS`/`MOVSD`命令は、引き続き既存の浮動小数点命令の処理フローに従うことを意味します。

### 3. `gsubr.c`のコメントアウト

`src/cmd/6g/gsubr.c`では、浮動小数点定数に関するTODOコメントが削除されています。
```c
-// TODO: lost special constants for floating point.  XORPD for 0.0?
```
これは、このコミットによって`0.0`に対する`XORPS`/`XORPD`の最適化が実装されたため、このTODOが解決されたことを示しています。

これらの変更により、Goコンパイラは浮動小数点数のゼロ値をより効率的に扱うようになり、生成されるバイナリのサイズ削減と実行速度の向上が期待されます。

*   **`progedit`関数内の主要な変更**:
    *   `AMOVSS`と`AMOVSD`命令に対する新しい`case`ブロックが追加されました。
    *   このブロック内で、以下の条件がチェックされます。
        *   `p->from.type == D_FCONST`: 命令のソースオペランドが浮動小数点定数であること。
        *   `p->from.u.dval == 0`: その浮動小数点定数の値がゼロであること。
        *   `p->to.type >= D_X0 && p->to.type <= D_X15` (obj6.c) / `D_X7` (obj8.c): 命令のデスティネーションオペランドがXMMレジスタであること。
    *   これらの条件がすべて真の場合、命令のオペコード (`p->as`) が `AXORPS` に変更されます。
    *   さらに、`p->from.type` と `p->from.index` が `p->to.type` と `p->to.index` に設定されます。これにより、`XORPS Xx, Xx` という形式の命令が生成されます。
    *   `break;` が続くため、この最適化が適用された場合は、それ以上の処理は行われません。
    *   `// fallthrough` コメントは、この最適化が適用されなかった場合に、元の`AMOVSS`/`AMOVSD`命令が引き続き既存の浮動小数点命令の処理フロー（例えば、メモリからのロードなど）に従うことを示唆しています。
    *   元の`switch`文の`case`リストから`AMOVSS`と`AMOVSD`が削除されました。これは、これらの命令のゼロ値最適化が新しいブロックで優先的に処理されるためです。

これらの変更により、Goコンパイラは、Goコードで浮動小数点型の変数をゼロ値で初期化したり、明示的に`0.0`を代入したりするような場合に、より効率的な`XORPS`命令を生成するようになります。これにより、生成されるアセンブリコードの命令数が削減され、実行時のパフォーマンスが向上します。

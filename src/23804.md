# [インデックス 23804] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）の正確性を向上させるための重要な変更です。特に、アンバッファードチャネルを介してブロックされたレシーバーにデータを送信する際に発生する、あるゴルーチンが別のゴルーチンのスタックに直接書き込むという特殊なケースに対応するため、型ベースのライトバリアを導入しています。これにより、GCがポインタを正しく追跡し、メモリ安全性を確保できるようになります。

    runtime: use type-based write barrier for remote stack write during chansend
    
    A send on an unbuffered channel to a blocked receiver is the only
    case in the runtime where one goroutine writes directly to the stack
    of another. The garbage collector assumes that if a goroutine is
    blocked, its stack contains no new pointers since the last time it ran.
    The send on an unbuffered channel violates this, so it needs an
    explicit write barrier. It has an explicit write barrier, but not one that
    can handle a write to another stack. Use one that can (based on type bitmap
    instead of heap bitmap).
    
    To make this work, raise the limit for type bitmaps so that they are
    used for all types up to 64 kB in size (256 bytes of bitmap).
    (The runtime already imposes a limit of 64 kB for a channel element size.)
    
    I have been unable to reproduce this problem in a simple test program.
    
    Could help #11035.

## 変更の背景

Goのガベージコレクタ（GC）は、並行実行中にメモリの安全性を維持するためにライトバリア（Write Barrier）を使用します。GCは、あるゴルーチンがブロックされている場合、そのスタックには最後に実行されてから新しいポインタが書き込まれていないと仮定しています。しかし、アンバッファードチャネル（バッファサイズが0のチャネル）を介してブロックされたレシーバーに値を送信する際、送信側のゴルーチンはレシーバー側のゴルーチンのスタックに直接値を書き込みます。この操作は、GCの仮定に反するため、特別なライトバリア処理が必要となります。

既存のライトバリアは主にヒープ上のオブジェクトのポインタ書き込みを対象としており、他のゴルーチンのスタックへの書き込みを適切に処理できませんでした。この不整合が、GCの誤動作やメモリリーク、あるいはクラッシュにつながる可能性がありました。このコミットは、この特定の「リモートスタック書き込み」のケースにおいて、GCの正確性を保証するためのメカニズムを導入することを目的としています。コミットメッセージには、この問題が直接再現できなかったものの、Go issue #11035の解決に役立つ可能性があると記載されています。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、トライカラーマーク＆スイープ（Tri-color Mark-and-Sweep）アルゴリズムをベースにした並行GCです。これは、プログラムの実行と並行してGCが動作することで、アプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑えることを目指しています。

*   **トライカラー（三色）マーキング**: GCはオブジェクトを「白（White）」「灰（Gray）」「黒（Black）」のいずれかの色で分類します。
    *   **白**: まだGCによって到達可能かどうかが確認されていないオブジェクト。最終的に回収される可能性がある。
    *   **灰**: GCによって到達可能であることが確認されたが、そのオブジェクトが参照する他のオブジェクト（子オブジェクト）はまだスキャンされていない。
    *   **黒**: GCによって到達可能であることが確認され、そのオブジェクトが参照する全ての子オブジェクトもスキャン済み。
*   **並行性**: GCのマーキングフェーズは、アプリケーションのゴルーチンと並行して実行されます。これにより、GCによるアプリケーションの停止時間を短縮します。

### ライトバリア (Write Barrier)

並行GCにおいて、アプリケーションがオブジェクトグラフを変更（ポインタを書き換え）すると、GCのマーキング処理と競合し、GCがオブジェクトを見落とす可能性があります。これを防ぐために導入されるのがライトバリアです。

*   **目的**: GCが実行中にポインタの書き換えが発生した場合でも、GCの正確性を保証し、到達可能なオブジェクトが誤って回収されないようにします。
*   **Goのハイブリッドライトバリア**: Goは、Yuasaスタイルの削除バリアとDijkstraスタイルの挿入バリアを組み合わせたハイブリッドライトバリアを使用しています。
    *   **挿入バリア**: 新しいポインタが書き込まれる際に、そのポインタが指すオブジェクトを「灰」にマークします。これにより、新しく到達可能になったオブジェクトがGCに見落とされることを防ぎます。
    *   **削除バリア**: ポインタが上書きされて参照が失われる際に、そのポインタが指していたオブジェクトを「灰」にマークします。これにより、GCの開始時に到達可能だったオブジェクトが、GC中に参照が失われたとしても回収されないようにします。
*   **動作**: コンパイラは、ポインタの書き込みが発生する可能性のある箇所にライトバリアのコードを挿入します。GCがアクティブな期間中、これらのバリアが有効になり、ポインタの変更をGCに通知します。

### ゴルーチンとスタック (Goroutines and Stacks)

*   **ゴルーチン**: Goの軽量な並行処理単位です。各ゴルーチンは独立した実行スタックを持ちます。
*   **スタック**: ゴルーチンのローカル変数や関数呼び出しの情報を格納するメモリ領域です。Goのスタックは動的に伸縮します。

### チャネル (Channels)

チャネルは、ゴルーチン間で値を送受信するための通信メカニズムです。

*   **アンバッファードチャネル**: バッファサイズが0のチャネルです。送信操作は受信側が準備できるまでブロックされ、受信操作は送信側が準備できるまでブロックされます。これにより、送信と受信が同期的に行われ、値の直接的なハンドオフが発生します。

### ポインタマスクと型ビットマップ (Pointer Mask and Type Bitmap)

GoのGCは、メモリ領域内のどの部分がポインタであるかを識別する必要があります。これは、ポインタでない値を誤ってスキャンしたり、ポインタを見落としたりしないようにするためです。

*   **ポインタマスク**: 特定のデータ構造や型のメモリレイアウトにおいて、どのオフセットにポインタが存在するかを示すビット列です。
*   **型ビットマップ**: 型情報の一部として、その型が占めるメモリ領域内のポインタの位置を示すビットマップです。GCはこれを利用して、オブジェクト内のポインタを効率的に識別し、マーク処理を行います。ヒープ上のオブジェクトだけでなく、スタック上のオブジェクトについても同様のポインタ情報が必要です。

## 技術的詳細

このコミットの核心は、アンバッファードチャネルを介したリモートスタック書き込みという特殊な状況下で、GoのGCが正しく動作するようにすることです。

1.  **問題の特定**: Goランタイムにおいて、アンバッファードチャネルへの送信がブロックされたレシーバーに対して行われる場合、送信側のゴルーチンは受信側のゴルーチンのスタックに直接データを書き込みます。これは、GCが「ブロックされたゴルーチンのスタックは、最後に実行されてから新しいポインタを含まない」という仮定に反します。この仮定が破られると、GCがスタック上の新しいポインタを見落とし、誤って参照されているオブジェクトを回収してしまう可能性があります。

2.  **既存ライトバリアの限界**: 従来のライトバリアは、主にヒープ上のオブジェクトのポインタ書き込みを効率的に処理するために設計されており、ヒープビットマップを利用していました。しかし、他のゴルーチンのスタックという特殊なメモリ領域への書き込みに対しては、このヒープビットマップベースのライトバリアは機能しません。スタックはヒープとは異なる管理下にあり、ヒープビットマップの対象外だからです。

3.  **解決策としての型ベースライトバリア**: この問題を解決するため、コミットは「型ビットマップ（type bitmap）」に基づく新しいライトバリアメカニズムを導入します。型ビットマップは、特定の型のメモリレイアウトにおけるポインタの位置を正確に記述します。これにより、GCはヒープビットマップに依存することなく、スタック上のオブジェクト内のポインタを識別し、ライトバリアを適用できるようになります。

4.  **`maxPtrmaskBytes` の引き上げ**: 型ビットマップがより広範囲の型に適用されるように、コンパイラ（`src/cmd/compile/internal/gc/reflect.go`）とリフレクションパッケージ（`src/reflect/type.go`）で定義されている `maxPtrmaskBytes` 定数が16から2048に引き上げられました。
    *   この定数は、コンパイラが型ビットマップを生成する最大サイズを決定します。以前は、GCのオーバーヘッドを償却するために128ポインタ（約16バイトのビットマップ）程度で十分とされていました。
    *   しかし、チャネル要素の最大サイズが64KB（256バイトのビットマップに相当）であるため、この上限に合わせて `maxPtrmaskBytes` を引き上げる必要がありました。これにより、64KBまでのサイズの型であれば、型ビットマップが生成され、`typeBitsBulkBarrier` が利用可能になります。32ビットシステムでも64KBの型に対応できるよう、2048という値が選ばれています。

5.  **`typeBitsBulkBarrier` の導入**: `src/runtime/mbitmap.go` に `typeBitsBulkBarrier` という新しい関数が追加されました。この関数は、指定された型とメモリ範囲（スタック上のチャネル要素）に対して、型ビットマップを走査し、ポインタスロットごとに `writebarrierptr_nostore` を実行します。これにより、リモートスタック書き込みが発生した際に、GCが新しいポインタを正しく認識できるようになります。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   **`src/cmd/compile/internal/gc/reflect.go`**:
    *   `maxPtrmaskBytes` 定数が `16` から `2048` に変更されました。これは、コンパイラが型ビットマップを生成する最大サイズを決定します。
*   **`src/reflect/all_test.go`**:
    *   `maxPtrmaskBytes` の変更に伴い、テストケース内の配列サイズが `100` から `10000` に拡大されました。これにより、より大きな型に対する型ビットマップの生成とGCビットの検証が正しく行われることを確認します。
*   **`src/reflect/type.go`**:
    *   `maxPtrmaskBytes` 定数が `2048` として定義され、`cmd/compile/internal/gc/reflect.go` との整合性が保たれています。
    *   `ArrayOf` 関数内で、型ビットマップを使用する条件が `array.size <= 16*8*ptrSize` から `array.size <= maxPtrmaskBytes*8*ptrSize` に変更されました。これにより、より大きな配列型に対しても型ビットマップが適用されるようになります。
*   **`src/runtime/chan.go`**:
    *   `chansend` 関数内で、アンバッファードチャネルの送信処理において、`typedmemmove(c.elemtype, unsafe.Pointer(sg.elem), ep)` の呼び出しが削除され、代わりに `memmove(sg.elem, ep, c.elemtype.size)` と `typeBitsBulkBarrier(c.elemtype, uintptr(sg.elem), c.elemtype.size)` が呼び出されるようになりました。
    *   コメントが追加され、この変更が「ランタイム全体で唯一、あるゴルーチンが別のゴルーチンのスタックに書き込む場所」であり、GCの仮定を破るため、`typeBitsBulkBarrier` が必要であることが説明されています。
*   **`src/runtime/mbitmap.go`**:
    *   `typeBitsBulkBarrier` 関数が新規追加されました。この関数は、指定された型とメモリ範囲に対して、型ビットマップを走査し、ポインタスロットごとに `writebarrierptr_nostore` を実行します。

## コアとなるコードの解説

### `src/runtime/chan.go` の変更

`chansend` 関数は、チャネルへの送信処理を担います。特に、アンバッファードチャネルでブロックされたレシーバーに送信する場合、送信される値はレシーバーゴルーチンのスタックに直接コピーされます。

変更前は `typedmemmove` が使用されていました。`typedmemmove` は、型情報に基づいてメモリをコピーし、必要に応じてヒープビットマップベースのライトバリア（`heapBitsBulkBarrier`）を呼び出す可能性があります。しかし、レシーバーのスタックはヒープではないため、`heapBitsBulkBarrier` は機能しません。

変更後は、以下の2つのステップに分けられました。

1.  `memmove(sg.elem, ep, c.elemtype.size)`: まず、`memmove` を使用して、ポインタのセマンティクスを考慮せずに生バイトとして値をコピーします。これは、GCの介入なしに純粋なメモリコピーを行います。
2.  `typeBitsBulkBarrier(c.elemtype, uintptr(sg.elem), c.elemtype.size)`: 次に、新しく追加された `typeBitsBulkBarrier` 関数を呼び出します。この関数は、コピーされた値の型情報（`c.elemtype`）とコピー先のスタックアドレス（`sg.elem`）を使用して、コピーされたデータ内のポインタを識別し、それらに対して明示的にライトバリアを適用します。これにより、GCはスタック上の新しいポインタを正しく認識し、メモリ安全性が保たれます。

### `src/runtime/mbitmap.go` の `typeBitsBulkBarrier` 関数

この関数は、型ビットマップを利用して、指定されたメモリ範囲内のポインタスロットに対してライトバリアを実行します。

*   **引数**:
    *   `typ *_type`: コピーされた値の型情報。この型はプレーンなビットマップを持ち、GCプログラムではないことが前提です。
    *   `p uintptr`: ライトバリアを適用するメモリ範囲の開始アドレス（レシーバーのスタック上のアドレス）。
    *   `size uintptr`: メモリ範囲のサイズ。
*   **動作**:
    1.  引数の検証: `typ` がnilでないこと、`typ.size` が `size` と一致すること、`typ` がGCプログラムではないことなどを確認します。
    2.  ライトバリアの有効性チェック: `writeBarrierEnabled` が `false` の場合は処理をスキップします。
    3.  ポインタマスクの走査: `typ.gcdata` に格納されている型ビットマップ（ポインタマスク）を走査します。
    4.  ポインタの識別とバリア適用: ビットマップの各ビットをチェックし、ポインタが存在する位置（`p + i`）を特定します。その位置にあるポインタに対して `writebarrierptr_nostore(x, *x)` を呼び出します。`writebarrierptr_nostore` は、GCがポインタの変更を追跡するために必要な処理を実行します。
*   **`//go:nosplit`**: この関数はスタックの分割を許可しない `nosplit` 関数としてマークされています。これは、`memmove` の直後に実行されるため、GCがこれらの2つの操作の間に完了しないようにするためです。

### `maxPtrmaskBytes` の変更

`maxPtrmaskBytes` は、コンパイラが型ビットマップを生成するオブジェクトの最大サイズを制御します。この値を16から2048に増やすことで、より大きな構造体や配列（最大64KB）に対しても型ビットマップが生成されるようになります。これにより、チャネルを介して送信される大きな値（チャネル要素の最大サイズは64KB）であっても、その内部のポインタが型ビットマップによって正確に記述され、`typeBitsBulkBarrier` が適切に機能するようになります。

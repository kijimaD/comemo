# [インデックス 27438] ファイルの概要

このコミットは、Goリンカー (`cmd/link`) におけるシンボルルックアップの内部的なリファクタリングに関するものです。特に、読み取り専用のシンボルルックアップ関数 `Linkrlookup` が、シンボル名を表す文字列がエスケープするのを防ぐように変更されました。これにより、`[]byte` を `string` にキャストしてルックアップを実行する際に、余分なメモリ割り当てが発生しないようになります。

## 元コミット内容

このコミットの目的は、Goリンカー (`cmd/link`) 内のシンボルルックアップメカニズムをリファクタリングすることです。特に、読み取り専用の `Linkrlookup` 関数が、シンボル名を表す文字列をエスケープさせないように変更されました。これにより、`[]byte` 型のデータを `string` 型にキャストしてルックアップを行う際に、ヒープへの余分なメモリ割り当てが発生しなくなります。この変更は、後続の変更を容易にし、コードをよりシンプルかつクリーンにすることを意図しています。ベンチマーク結果 (`LinkCmdGo`) は、この変更がパフォーマンスに影響を与えないことを示しています。

## 変更の背景

Goのリンカーは、コンパイルされたオブジェクトファイルやアーカイブを結合して実行可能ファイルを生成する重要なツールです。このプロセスでは、プログラム内の関数や変数などのシンボルを効率的に検索し、解決する必要があります。

このコミットの背景には、Goにおける「エスケープ解析 (Escape Analysis)」と「`[]byte` から `string` への変換」の挙動が深く関わっています。

1.  **エスケープ解析の最適化**: Goコンパイラは、変数がそのスコープを「エスケープ」するかどうかを判断するエスケープ解析を行います。エスケープしない変数はスタックに割り当てられ、エスケープする変数はヒープに割り当てられます。スタック割り当ては高速でガベージコレクションの負担が少ないため、可能な限りスタック割り当てが望ましいとされます。
2.  **`[]byte` から `string` への変換**: Goでは、`[]byte` を `string` にキャストすると、通常は新しい文字列が作成され、その際にメモリ割り当てが発生します。しかし、コンパイラがその文字列が変更されないこと、かつ元の `[]byte` が変更されないことを保証できる場合、最適化によってコピーを省略し、元の `[]byte` の基盤となるメモリを共有する場合があります。この最適化は、文字列が「エスケープしない」場合に特に有効です。
3.  **リンカーの効率性**: リンカーは大量のシンボル名を処理するため、シンボルルックアップの効率性はビルド時間に直結します。特に、シンボル名が `[]byte` 形式で提供され、それを `string` に変換してルックアップする場合、不必要なメモリ割り当てはパフォーマンスのボトルネックになり得ます。

このコミット以前の `Linkrlookup` 関数は、シンボル名文字列を内部的に保持する際に、その文字列が関数スコープをエスケープすると判断されるような実装になっていたと考えられます。その結果、`[]byte` から `string` へのキャスト時に常に新しいメモリがヒープに割り当てられ、ガベージコレクションの対象となり、効率が低下する可能性がありました。このリファクタリングは、この不必要なエスケープを防ぎ、より効率的なシンボルルックアップを実現することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびリンカーに関する前提知識が必要です。

1.  **Goリンカー (`cmd/link`)**:
    *   Goのビルドツールチェーンの一部で、コンパイルされたGoパッケージ（`.a` ファイル）やオブジェクトファイル（`.o` ファイル）を結合し、実行可能ファイルを生成します。
    *   シンボル解決、再配置、デッドコード削除、実行可能ファイルのフォーマット（ELF, Mach-O, PEなど）生成などを担当します。
    *   内部的には、プログラム内のすべてのシンボル（関数、変数、型など）を管理する「シンボルテーブル」を構築します。

2.  **シンボル (Symbol)**:
    *   プログラム内の特定のエンティティ（関数、グローバル変数、静的変数など）を一意に識別するための名前です。
    *   リンカーはこれらのシンボル名を使って、異なるコンパイル単位で定義されたエンティティ間の参照を解決します。

3.  **`LSym` 構造体**:
    *   Goリンカーの内部でシンボルを表す主要なデータ構造です。シンボル名、アドレス、サイズ、バージョンなどの情報を含みます。

4.  **エスケープ解析 (Escape Analysis)**:
    *   Goコンパイラが行う最適化の一つで、変数がその関数スコープを「エスケープ」するかどうかを静的に分析します。
    *   **エスケープしない場合**: 変数はスタックに割り当てられます。関数呼び出しが終了すると自動的に解放され、高速です。
    *   **エスケープする場合**: 変数はヒープに割り当てられます。ガベージコレクタによって管理され、スタック割り当てよりもオーバーヘッドがあります。
    *   文字列やスライスが関数から返される、グローバル変数に代入される、チャネルを通じて送信されるなどの場合にエスケープすると判断されます。

5.  **`[]byte` から `string` への変換とメモリ割り当て**:
    *   Goでは、`string(byteSlice)` のように `[]byte` を `string` にキャストすると、通常は `byteSlice` の内容をコピーした新しい文字列がヒープに割り当てられます。これは文字列がイミュータブル（不変）であるためです。
    *   しかし、コンパイラのエスケープ解析が、生成された文字列が元の `[]byte` の寿命を超えて使用されないこと、および元の `[]byte` が変更されないことを保証できる場合、コンパイラはコピーを省略し、元の `[]byte` の基盤となるメモリを共有する最適化を行うことがあります。この最適化は、メモリ割り当てを削減し、パフォーマンスを向上させます。
    *   このコミットの文脈では、`Linkrlookup` がシンボル名文字列を「エスケープ」させていたため、この最適化が適用されず、常にコピーが発生していたと考えられます。

6.  **シンボルバージョン (Symbol Versioning)**:
    *   Goリンカーでは、同じ名前のシンボルが異なるバージョンを持つことがあります。これは、特に異なるパッケージやコンパイル単位で同じ名前のシンボルが定義されている場合や、特定の最適化やプラットフォーム固有の挙動を扱うために使用されます。
    *   このコミットでは、シンボルルックアップのデータ構造が、このバージョン情報をより効率的に扱うように変更されています。

## 技術的詳細

このコミットの技術的な核心は、Goリンカーがシンボルを管理する方法、特にシンボルルックアップのデータ構造と、`[]byte` から `string` への変換におけるエスケープ解析の相互作用にあります。

以前の実装では、`Link` 構造体はシンボルを検索するために `HashName` (名前のみで検索) と `HashVersion` (名前とバージョンで検索) の2つのマップを使用していました。

```go
type Link struct {
    // ...
    HashName map[string]*LSym
    HashVersion map[symVer]*LSym
    // ...
}

type symVer struct {
    sym string
    ver int
}
```

`_lookup` 関数（以前の `Linklookup` の内部実装）は、まず `HashName` を検索し、バージョンが一致しない場合や複数のバージョンが存在する場合に `HashVersion` をフォールバックとして使用していました。この `_lookup` 関数が、シンボル名文字列を `symVer` 構造体の一部として、あるいは `HashName` のキーとして使用する際に、その文字列が関数スコープをエスケープするとコンパイラに判断させていた可能性があります。その結果、`[]byte` から `string` へのキャスト時に常にメモリコピーが発生していました。

このコミットでは、この問題を解決するために以下の変更が行われました。

1.  **シンボルルックアップデータ構造の変更**:
    *   `Link` 構造体から `HashName` と `HashVersion` が削除され、代わりに `Hash []map[string]*LSym` というスライスオブマップが導入されました。
    *   `Hash` スライスのインデックスはシンボルバージョンに対応し、各マップは特定のバージョンのシンボル名を `LSym` ポインタにマッピングします。これにより、バージョンごとに独立したマップを持つことで、ルックアップがより直接的かつ効率的になります。
    *   `symVer` 構造体は不要になったため削除されました。

2.  **`IncVersion()` メソッドの導入**:
    *   `Link` 構造体に `IncVersion()` メソッドが追加されました。このメソッドは `l.Version` をインクリメントし、新しいバージョンのための空の `map[string]*LSym` を `l.Hash` スライスに追加します。
    *   `ldelf.go`, `ldmacho.go`, `ldpe.go`, `objfile.go` の各ファイルローダーで、以前は `Ctxt.Version++` と直接バージョンをインクリメントしていた箇所が `Ctxt.IncVersion()` の呼び出しに置き換えられました。これにより、新しいバージョンが導入されるたびに、対応するシンボルマップが適切に初期化されるようになります。

3.  **`_lookup` 関数の簡素化と `Linklookup`/`Linkrlookup` の直接化**:
    *   以前の複雑な `_lookup` 関数は削除され、そのロジックは `Linklookup` と `Linkrlookup` に直接統合されました。
    *   `Linklookup(ctxt *Link, name string, v int) *LSym` は、指定されたバージョン `v` のマップ `ctxt.Hash[v]` から直接 `name` をキーとしてシンボルを検索し、存在しない場合は新しいシンボルを作成して追加します。
    *   `Linkrlookup(ctxt *Link, name string, v int) *LSym` (読み取り専用ルックアップ) は、`ctxt.Hash[v][name]` を直接参照するようになり、シンボルが存在しない場合は `nil` を返します。

この新しいデータ構造とルックアップロジックにより、`Linkrlookup` がシンボル名文字列を内部的に保持する際に、その文字列が関数スコープをエスケープするとコンパイラに判断させる要因が排除されました。具体的には、`ctxt.Hash[v][name]` のように直接マップにアクセスすることで、`name` 文字列の寿命がマップの寿命に依存するようになり、`Linkrlookup` の呼び出し元が `[]byte` から `string` にキャストした文字列を渡した場合でも、その文字列がヒープにコピーされることなく、スタック上で処理される可能性が高まります。これにより、不必要なメモリ割り当てが削減され、リンカーの効率が向上します。

## コアとなるコードの解説

このコミットの最も重要な変更は、シンボルルックアップのデータ構造を `HashName` と `HashVersion` の2つのマップから、バージョンごとにマップを持つ `Hash []map[string]*LSym` というスライスオブマップに変更した点です。

**変更前**:
*   `HashName`: シンボル名をキーとするマップ。主に単一バージョンのシンボルを高速に検索するために使用。
*   `HashVersion`: `symVer` 構造体（シンボル名とバージョンを含む）をキーとするマップ。`HashName` で衝突があった場合や複数バージョンが存在する場合のフォールバック。
*   `_lookup` 関数がこれら2つのマップを複雑なロジックで検索していました。このロジックの中で、シンボル名文字列がエスケープするとコンパイラに判断される可能性がありました。

**変更後**:
*   `Hash []map[string]*LSym`: `Hash` スライスの各要素が、特定のバージョンに対応する `map[string]*LSym` です。
    *   `Hash[0]` はバージョン0のシンボルマップ、`Hash[1]` はバージョン1のシンボルマップ、といった具合です。
*   `IncVersion()`: 新しいバージョンが導入されるたびに、このメソッドが呼ばれ、`Hash` スライスに新しい空のマップが追加されます。これにより、各バージョンが独立したシンボルマップを持つことが保証されます。
*   `Linklookup(ctxt *Link, name string, v int) *LSym`:
    ```go
    func Linklookup(ctxt *Link, name string, v int) *LSym {
        m := ctxt.Hash[v] // 特定のバージョンのマップを取得
        s := m[name]      // マップから直接シンボルを検索
        if s != nil {
            return s
        }
        s = linknewsym(ctxt, name, v) // なければ新しいシンボルを作成
        s.Extname = s.Name
        m[name] = s // マップに追加
        return s
    }
    ```
    この関数は、指定されたバージョン `v` のマップを直接参照し、シンボルを検索または作成します。
*   `Linkrlookup(ctxt *Link, name string, v int) *LSym`:
    ```go
    func Linkrlookup(ctxt *Link, name string, v int) *LSym {
        return ctxt.Hash[v][name] // 特定のバージョンのマップから直接シンボルを検索
    }
    ```
    読み取り専用のルックアップは、`ctxt.Hash[v][name]` のように非常にシンプルになりました。これにより、`name` 文字列が `Linkrlookup` の呼び出し元から渡された `[]byte` からキャストされたものであっても、その文字列がヒープにコピーされることなく、スタック上で処理される可能性が高まります。これは、`name` 文字列がマップのキーとして使用されるだけで、`Linkrlookup` のスコープを超えて「エスケープ」しないとコンパイラが判断しやすくなるためです。

このリファクタリングにより、シンボルルックアップのロジックが大幅に簡素化され、特に `[]byte` から `string` への変換における不必要なメモリ割り当てが回避されることで、リンカーの効率が向上します。

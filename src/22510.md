## 変更の背景

Go言語において、文字列は不変（immutable）なデータ型です。この特性のため、複数の文字列を `+` 演算子などで連結するたびに、新しい文字列がメモリ上に生成され、元の文字列の内容がコピーされます。このプロセスは、特にループ内で頻繁に文字列連結が行われる場合、多くのメモリ割り当てとガベージコレクション（GC）のオーバーヘッドを引き起こし、パフォーマンスのボトルネックとなる可能性があります。

このコミットは、Goコンパイラ (`cmd/internal/gc`) の内部処理において、このような文字列連結によるメモリ割り当ての問題を解決するために導入されました。コミットメッセージにある「CL 7696」は、この最適化の必要性や実装方法について議論された先行する変更リスト（Change List）を示唆しています。コンパイラは自身の処理中に多くの文字列操作を行うため、その内部での効率的な文字列連結は、コンパイラ自体のパフォーマンス向上に直結します。

`internConcat` の導入は、コンパイラが内部的に使用する特定の文字列（例えば、型変換関数名やアサーション関数名など）を効率的に生成し、メモリ割り当てを最小限に抑えることを目的としています。

## 前提知識の解説

### Go言語における文字列の不変性

Go言語の文字列はバイトのシーケンスであり、一度作成されると内容を変更できません。これは「不変性」と呼ばれます。例えば、`s := "hello"` の後に `s = s + " world"` とすると、既存の `"hello"` が変更されるのではなく、新しく `"hello world"` という文字列がメモリに作成され、`s` がその新しい文字列を指すようになります。

### 文字列連結におけるメモリ割り当ての課題

文字列の不変性により、`+` 演算子や `fmt.Sprintf` などで文字列を連結するたびに、新しい文字列のためのメモリがヒープに割り当てられます。この頻繁な割り当ては、特に大量の文字列連結を行う場合、ガベージコレクタの負荷を増大させ、プログラムの実行速度を低下させる原因となります。

### `strings.Builder` や `bytes.Buffer` といった一般的な最適化手法

Go言語では、動的な文字列構築を効率的に行うために、標準ライブラリで `strings.Builder` や `bytes.Buffer` が提供されています。これらは内部的に可変長のバイトスライス（バッファ）を保持し、文字列の追加時にバッファを拡張しながらデータを蓄積します。最終的に `String()` メソッドを呼び出すことで、一度だけ最終的な文字列を生成し、メモリ割り当ての回数を大幅に削減します。

### Goコンパイラ (`cmd/internal/gc`) の役割

`cmd/internal/gc` は、Go言語の公式コンパイラの主要部分です。Goのソースコードを解析し、中間表現に変換し、最終的に実行可能なバイナリコードを生成する役割を担っています。コンパイラは、型チェック、最適化、コード生成など、多くの複雑な処理を行います。これらの処理の過程で、シンボル名、型情報、内部的な関数名など、様々な文字列を生成・操作します。

### `internString` の概念

`internString` は、Goコンパイラ内部で使われる文字列の「インターン化（interning）」を行う関数です。インターン化とは、同じ内容の文字列が複数回出現する場合に、それらをメモリ上で同じオブジェクトとして扱う最適化手法です。これにより、メモリ使用量を削減し、文字列の比較を高速化できます。`internString` は、与えられたバイトスライスから文字列を作成し、その文字列が既にインターン化されている場合は既存の文字列への参照を返し、そうでない場合は新しくインターン化して返します。

## 技術的詳細

このコミットの核心は、Goコンパイラ内部での文字列連結の効率化です。

### `internConcat` の導入目的

`internConcat` は、コンパイラが内部的に使用する複数の文字列断片を連結して新しい文字列を生成する際に、メモリ割り当てを最小限に抑えることを目的としています。特に、型変換やアサーションに関連するランタイム関数名（例: `convT2E`, `assertI2E2` など）のように、複数の固定文字列と動的な型情報を組み合わせて生成される文字列に対して効果を発揮します。

### `internConcat` がどのように「alloc-free」を実現しているか

`internConcat` 関数は、可変引数 `ss ...string` を受け取り、それらを連結して一つの文字列を生成します。この際、内部で固定サイズのバイトスライス `b` を初期化します。

```go
func internConcat(ss ...string) string {
	const bufsiz = 128 // big enough for most compiler uses; must be constant to avoid heap alloc
	b := make([]byte, 0, bufsiz)
	for _, s := range ss {
		b = append(b, s...)
	}
	return internString(b)
}
```

ここで重要なのは `const bufsiz = 128` です。この定数により、`make([]byte, 0, bufsiz)` で作成されるバッファがスタック上に割り当てられる可能性が高まります（Goコンパイラの「エスケープ解析」による）。もし `bufsiz` が定数でなく、実行時に決定される値であったり、非常に大きな値であったりすると、バッファはヒープに割り当てられ、GCの対象となります。`bufsiz` をコンパイラの内部的な文字列連結のほとんどをカバーできる十分なサイズ（128バイト）の定数にすることで、ヒープ割り当てを避け、「alloc-free」を実現しています。

### `internString` との連携

`internConcat` は、連結されたバイトスライスを最終的に `internString` に渡します。これにより、生成された文字列がインターン化され、同じ内容の文字列が重複してメモリに存在することを防ぎます。これは、メモリ効率と文字列比較のパフォーマンスの両方に寄与します。

### コンパイラ内部での利用箇所

`internConcat` は、主に `src/cmd/internal/gc/walk.go` 内で、型変換 (`conv`) や型アサーション (`assert`) に関連するランタイム関数の名前を構築する際に使用されます。以前は `+` 演算子による文字列連結が行われていた箇所が `internConcat` に置き換えられました。

### コンパイラにGo言語でテストが追加されたことの意義

コミットメッセージには「I believe that this includes the first regular Go test in the compiler.」とあります。これは、Goコンパイラのテストが、それまで主にシェルスクリプトや特殊なテストハーネスで行われていたのに対し、Go言語自身で記述された `testing` パッケージを利用した正規のテストが初めて追加されたことを意味します。これは、コンパイラのテスト容易性と保守性の向上において重要な一歩です。Go言語でテストを書くことで、より表現力豊かで、Go開発者にとって馴染み深い方法でコンパイラの挙動を検証できるようになります。

## コアとなるコードの解説

### `src/cmd/internal/gc/lex.go` の変更

*   **`internConcat` 関数の追加**:
    *   この関数は、可変引数として複数の文字列 `ss ...string` を受け取ります。
    *   `const bufsiz = 128` という定数で、内部バッファの最大サイズを128バイトに設定しています。この定数により、Goコンパイラのエスケープ解析が働き、ほとんどの場合でこのバッファがヒープではなくスタックに割り当てられるようになります。これにより、メモリ割り当て（ヒープアロケーション）を回避し、ガベージコレクションの負荷を軽減します。
    *   ループ内で `append(b, s...)` を使用して、引数として渡されたすべての文字列をこのバッファに追加します。
    *   最終的に、構築されたバイトスライス `b` を `internString` 関数に渡し、結果としてインターン化された文字列を返します。これにより、同じ内容の文字列がメモリ上で重複して存在することを防ぎます。

### `src/cmd/internal/gc/lex_test.go` の変更

*   **`TestInternConcat` の新規追加**:
    *   `internConcat` 関数の動作を検証するためのテストケースです。
    *   `testing.AllocsPerRun` を使用して、`internConcat` の呼び出しがメモリ割り当てを発生させないことを確認しています。`n > 0` でエラーを報告することで、ヒープアロケーションが発生した場合にテストが失敗するようにしています。
    *   `internConcat("conv", fromKind, "2", toKind)` のように、複数の文字列を連結する典型的なコンパイラ内部のユースケースを模倣しています。
    *   このテストは、GoコンパイラにGo言語で記述された最初の正規テストであるとコミットメッセージで述べられており、コンパイラのテストインフラストラクチャにおける重要な進歩を示しています。

### `src/cmd/internal/gc/subr.go` の変更

*   **`type2IET` から `IET()` メソッドへの変更**:
    *   `type2IET` というグローバル関数が、`*Type` 型のメソッド `IET()` に変更されました。
    *   この変更は、コードの可読性とオブジェクト指向的な設計を向上させます。型に関する情報を取得する関数が、その型自身のメソッドとして定義されることで、より自然な呼び出し方 (`t.IET()`) が可能になります。
    *   機能的には変更がなく、与えられた型が具象型 (`"T"`)、インターフェース型 (`"I"`)、または空インターフェース型 (`"E"`) のいずれであるかを示す文字列を返します。これは、ランタイムの型変換 (`conv*`) や型アサーション (`assert*`) ルーチンの名前を構築するために使用されます。

### `src/cmd/internal/gc/walk.go` の変更

*   **`internConcat` と `IET()` メソッドの利用**:
    *   このファイルは、コンパイラのウォーク処理（ASTの走査と変換）を担当しており、型変換や型アサーションのコード生成ロジックが含まれています。
    *   以前は `+` 演算子と `type2IET` 関数を使用してランタイム関数の名前（例: `assertT2E`, `convI2E`）を文字列連結で構築していましたが、これらが `internConcat` と `IET()` メソッドの組み合わせに置き換えられました。
    *   例:
        *   `buf := "assert" + type2IET(r.Left.Type) + "2" + type2IET(r.Type)`
            ↓
        *   `buf := internConcat("assert", r.Left.Type.IET(), "2", r.Type.IET())`
    *   この変更により、これらの文字列構築処理におけるヒープアロケーションが削減され、コンパイラのパフォーマンスが向上します。

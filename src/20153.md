# [インデックス 20153] ファイルの概要

このコミットは、Goランタイムの重要な変更を導入するもので、特にスケジューラに関連する共通関数をC言語（またはPlan 9 C）からGo言語へ移行することに焦点を当てています。これにより、チャネル、セマフォ、タイマーなどのGoの並行処理プリミティブの基盤となるメカニズムが、よりGoらしいコードベースで実装されるようになります。この移行は、ランタイムの保守性、安全性、およびGoツールチェインとの統合を改善することを目的としています。

## 変更の背景

Goランタイムは、初期にはパフォーマンスと低レベルなシステム操作のためにC言語（またはPlan 9 C）で多くの部分が書かれていました。しかし、Go言語自体の成熟と、Goコンパイラの最適化能力の向上に伴い、ランタイムのより多くの部分をGo言語で記述することが可能になりました。これにより、以下のような利点が期待されます。

1.  **保守性の向上**: Go言語はC言語に比べてメモリ安全性や型安全性が高く、ガベージコレクションによってメモリ管理が自動化されているため、バグの発生を抑え、コードの理解と保守が容易になります。
2.  **開発効率の向上**: Go言語の豊富なツールチェイン（フォーマッタ、リンタ、デバッガなど）を活用できるようになり、開発プロセスが効率化されます。
3.  **Goエコシステムとの統合**: ランタイムコードがGoで書かれることで、Goの他の部分との連携がよりシームレスになり、将来的な機能拡張や最適化が容易になります。
4.  **デバッグの容易性**: GoのデバッガはGoコードに対してより詳細な情報を提供できるため、ランタイムのデバッグがしやすくなります。

このコミットは、特にGoの並行処理の根幹をなすスケジューラ関連の関数（ゴルーチンの待機、再開など）をGoに移行する第一歩として位置づけられます。これにより、チャネル、セマフォ、タイマーといった高レベルな並行処理プリミティブの内部実装が、よりGoらしい形で表現されるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とC言語の知識が必要です。

1.  **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルなシステム。ゴルーチンのスケジューリング、メモリ管理（ガベージコレクション）、チャネル通信、システムコールとの連携などを担当します。
2.  **ゴルーチン (Goroutine)**: Goの軽量な並行実行単位。OSのスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行できます。
3.  **M, P, G モデル**: Goスケジューラの基本的なモデル。
    *   **M (Machine)**: OSのスレッドに対応します。GoランタイムはM上でゴルーチンを実行します。
    *   **P (Processor)**: 論理プロセッサ。MとGの間の仲介役で、実行可能なゴルーチンをMに提供します。Pの数は通常、CPUのコア数に制限されます。
    *   **G (Goroutine)**: ゴルーチンそのもの。
4.  **スケジューラ (Scheduler)**: 実行可能なゴルーチンをPに割り当て、M上で実行させる役割を担います。ゴルーチンがブロックされたり、明示的に`runtime.Gosched()`を呼び出したりすると、スケジューラが別のゴルーチンに切り替えます。
5.  **`sudog` (Scheduler Utility Data Object for Goroutine)**: ゴルーチンがチャネル操作やセマフォ操作などでブロックされる際に、そのゴルーチンの待機情報を保持するために使用される内部的なデータ構造です。`sudog`は、どのゴルーチンが何を待っているのか、どのチャネルやセマフォに関連しているのかといった情報をカプセル化します。
6.  **`park` と `parkunlock`**: Goランタイムにおけるゴルーチンの待機と再開の基本的なメカニズムです。
    *   `park`: 現在のゴルーチンを待機状態（`Gwaiting`）にし、スケジューラから外します。特定のイベントが発生するまで実行を停止します。
    *   `parkunlock`: 待機中のゴルーチンを再開可能な状態（`Grunnable`）にし、スケジューラに戻します。
7.  **`mcall` と `onM`**: Goランタイムの内部関数で、現在のゴルーチン（G）からシステムスレッド（M）のスタックに切り替えて、MのコンテキストでC/アセンブリコードを実行するために使用されます。これは、GoのスケジューラがGoコードで書かれていても、低レベルな操作（例: コンテキストスイッチ）には依然としてCやアセンブリが必要なためです。
8.  **`int8*` と `String`**: C言語における文字列は通常、`char*`（Goでは`int8*`に相当）として表現され、ヌル終端されます。Go言語の`string`型は、文字列のデータへのポインタと長さを保持する構造体であり、不変です。このコミットでは、`waitreason`（ゴルーチンが待機している理由を示す文字列）の型が`int8*`から`String`に変更されています。これは、ランタイム内部でGoの文字列型をより積極的に利用する方向への移行を示しています。
9.  **`gostringnocopy`**: Cのバイト配列からGoの`string`型を生成するランタイム内部関数。この関数は、元のバイト配列のコピーを作成せず、既存のメモリを指す`string`ヘッダを作成するため、効率的です。

## 技術的詳細

このコミットの主要な技術的変更点は以下の通りです。

1.  **スケジューラ関数のGo言語への移行**:
    *   `runtime/proc.go`に`gopark`、`goparkunlock`、`goready`といったGo言語の関数が導入されました。これらは、以前はC言語で実装されていた`runtime·park`、`runtime·parkunlock`、`runtime·ready`に対応します。
    *   これらのGo関数は、内部的に`mcall`や`onM`を使用して、最終的にC言語やアセンブリで実装された低レベルな関数（例: `park_m`、`ready_m`）を呼び出します。これは、ゴルーチンのコンテキストスイッチやMのスタックでの操作など、Go言語だけでは直接行えない処理があるためです。
    *   このアプローチにより、高レベルなロジックはGoで記述され、低レベルなプラットフォーム依存の詳細はC/アセンブリに残るという、よりクリーンな分離が実現されます。

2.  **`waitreason`の型変更**:
    *   `runtime/runtime.h`の`G`構造体において、ゴルーチンの待機理由を示す`waitreason`フィールドの型が`int8*`（Cスタイルの文字列）から`String`（Goスタイルの文字列）に変更されました。
    *   これに伴い、`runtime/chan.goc`、`runtime/heapdump.c`、`runtime/mgc0.c`、`runtime/netpoll.goc`、`runtime/proc.c`、`runtime/sema.goc`、`runtime/stack.c`、`runtime/time.goc`など、`waitreason`を使用している多くのC/Plan 9 Cファイルで、文字列リテラルを`runtime·gostringnocopy((byte*)"...")`でラップする変更が行われました。これにより、Cの文字列リテラルがGoの`String`型に変換され、Goのランタイム関数に渡せるようになります。
    *   `runtime/proc.c`では、`runtime·printf`のフォーマット指定子も`%s`から`%S`に変更され、Goの`String`型を正しく出力できるようになりました。

3.  **`sudog`キャッシュの導入**:
    *   `runtime/malloc.h`の`MCache`構造体に`SudoG* sudogcache`が追加されました。`MCache`は各P（論理プロセッサ）に紐付けられたローカルキャッシュであり、これにより`sudog`オブジェクトの割り当てと解放が高速化されます。
    *   `runtime/proc.go`に`acquireSudog`と`releaseSudog`関数が追加され、このキャッシュを管理します。`sudog`はチャネル操作などで頻繁に割り当て・解放されるため、キャッシュを導入することでアロケーションのオーバーヘッドを削減し、パフォーマンスを向上させることができます。
    *   `runtime/mgc0.c`の`clearpools`関数で、GC時に`sudogcache`がクリアされるようになりました。

4.  **CPUティック取得関数の追加**:
    *   `src/pkg/runtime/asm_386.s`、`src/pkg/runtime/asm_amd64.s`、`src/pkg/runtime/asm_amd64p32.s`、`src/pkg/runtime/asm_arm.s`に`runtime·gocputicks`というアセンブリ関数が追加されました。これは、CPUのタイムスタンプカウンタ（TSC）を読み取ることで、高精度なCPUティック（サイクル数）を取得するためのものです。これは、プロファイリングやスケジューラの詳細なタイミング測定に利用される可能性があります。

これらの変更は、Goランタイムの内部構造をよりGo言語に適合させ、将来的な機能拡張や最適化のための強固な基盤を築くものです。特に、`waitreason`の型変更は、ランタイム内部でのGoの型システムの利用を促進し、より一貫性のあるコードベースへと導きます。

## コアとなるコードの解説

### `src/pkg/runtime/proc.go` の `gopark` 関数 (抜粋)

```go
// Puts the current goroutine into a waiting state and calls unlockf.
// If unlockf returns false, the goroutine is resumed.
func gopark(unlockf unsafe.Pointer, lock unsafe.Pointer, reason string) {
	mp := acquirem()
	gp := mp.curg
	if gp.status != gStatusRunning {
		gothrow("gopark: bad g status")
	}
	mp.waitlock = lock
	mp.waitunlockf = *(*func(*g, unsafe.Pointer) uint8)(unsafe.Pointer(&unlockf))
	gp.waitreason = reason
	releasem(mp)
	// can't do anything that might move the G between Ms here.
	mcall(&park_m)
}
```
この`gopark`関数は、Go言語で書かれた新しい`park`のラッパーです。
1.  `acquirem()`で現在のM（OSスレッド）を取得します。
2.  現在のゴルーチン`gp`のステータスが`gStatusRunning`であることを確認します。
3.  Mの`waitlock`と`waitunlockf`フィールドに、待機解除関数とロックを設定します。
4.  ゴルーチン`gp`の`waitreason`フィールドに、Goの`string`型の待機理由を設定します。
5.  `releasem(mp)`でMを解放し、スケジューラに制御を戻します。
6.  `mcall(&park_m)`を呼び出すことで、現在のゴルーチンからMのスタックに切り替わり、C/アセンブリで実装された`park_m`関数が実行されます。`park_m`はゴルーチンを待機状態にし、別のゴルーチンに切り替える役割を担います。

### `src/pkg/runtime/proc.c` の `runtime·park_m` 関数 (抜粋)

```c
void
runtime·park_m(G *gp)
{
	bool ok;

	// ... (省略) ...

	gp->status = Gwaiting;
	dropg(); // 現在のゴルーチンをPから切り離す
	
	// ... (省略) ...

	if(gp->m->waitunlockf != nil) {
		ok = gp->m->waitunlockf(gp, gp->m->waitlock);
		gp->m->waitunlockf = nil;
		gp->m->waitlock = nil;
		if(!ok) {
			// unlockf returned false, so we need to resume the goroutine
			gp->status = Grunnable;
			runtime·ready(gp); // ゴルーチンを再開可能にする
		}
	}
	
	// ... (省略) ...
}
```
`runtime·park_m`は、`gopark`から`mcall`経由で呼び出されるC言語の関数です。
1.  ゴルーチン`gp`のステータスを`Gwaiting`に設定します。
2.  `dropg()`を呼び出して、現在のゴルーチンをPから切り離し、実行キューから削除します。
3.  `waitunlockf`が設定されている場合、それを呼び出します。この関数は、ゴルーチンが待機する前にロックを解除するなどのクリーンアップ処理を行います。
4.  もし`waitunlockf`が`false`を返した場合（これは通常、待機が不要になったことを意味します）、ゴルーチンを`Grunnable`状態に戻し、`runtime·ready(gp)`を呼び出してスケジューラに再投入します。

### `src/pkg/runtime/proc.go` の `acquireSudog` と `releaseSudog` (抜粋)

```go
//go:nosplit
func acquireSudog() *sudog {
	c := gomcache()
	s := c.sudogcache
	if s != nil {
		c.sudogcache = s.link
		return s
	}
	return new(sudog)
}

//go:nosplit
func releaseSudog(s *sudog) {
	c := gomcache()
	s.link = c.sudogcache
	c.sudogcache = s
}
```
これらの関数は、`sudog`オブジェクトのキャッシュ管理を行います。
*   `acquireSudog()`は、現在のPの`MCache`から`sudog`オブジェクトを取得しようとします。キャッシュに利用可能なオブジェクトがあればそれを返し、なければ新しく割り当てます。
*   `releaseSudog()`は、使用済みの`sudog`オブジェクトを`MCache`のキャッシュに戻します。
これにより、チャネル操作などで頻繁に発生する`sudog`の割り当てと解放のコストが削減され、ランタイムのパフォーマンスが向上します。

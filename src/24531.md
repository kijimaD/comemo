# [インデックス 24531] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）トリガーの再チェックメカニズムに関するものです。具体的には、GCが実際に開始される直前にGCトリガー条件を再確認することで、複数のGoroutineが同時にGCを開始しようとすることによって発生する冗長なGCサイクルや非効率性を防ぐことを目的としています。

    runtime: recheck GC trigger before actually starting GC
    
    Currently allocation checks the GC trigger speculatively during
    allocation and then triggers the GC without rechecking. As a result,
    it's possible for G 1 and G 2 to detect the trigger simultaneously,
    both enter startGC, G 1 actually starts GC while G 2 gets preempted
    until after the whole GC cycle, then G 2 immediately starts another GC
    cycle even though the heap is now well under the trigger.
    
    Fix this by re-checking the GC trigger non-speculatively just before
    actually kicking off a new GC cycle.
    
    This contributes to #11911 because when this happens, we definitely
    don't finish the background sweep before starting the next GC cycle,
    which can significantly delay the start of concurrent scan.

## 元コミット内容

Goランタイムにおいて、GC（ガベージコレクション）が実際に開始される直前にGCトリガー条件を再確認する変更が加えられました。

これまでの実装では、メモリ割り当て時にGCトリガーが投機的にチェックされ、その結果に基づいてGCが再チェックなしでトリガーされていました。この挙動により、複数のGoroutine（例えばG1とG2）が同時にGCトリガーを検出し、両方が`startGC`関数に入ることが可能でした。G1が実際にGCを開始し、G2がGCサイクル全体が終了するまでプリエンプト（一時停止）された後、G2がすぐに別のGCサイクルを開始してしまう可能性がありました。これは、G1によるGCが完了した時点でヒープサイズがトリガー条件を十分に下回っているにもかかわらず発生する、無駄なGCサイクルを意味します。

このコミットは、新しいGCサイクルを実際に開始する直前に、GCトリガーを非投機的に再チェックすることでこの問題を修正します。

この変更は、Issue #11911に関連しています。上記のような状況が発生すると、次のGCサイクルが開始される前にバックグラウンドスイープが完了しないことが確実になり、並行スキャン（concurrent scan）の開始が大幅に遅れる可能性があったためです。

## 変更の背景

Goのガベージコレクタは、プログラムの実行と並行して動作する並行GCを採用しています。GCは、ヒープの使用量がある閾値（GCトリガー）を超えたときに開始されます。しかし、複数のGoroutineが同時にメモリを割り当てている状況では、以下のような問題が発生する可能性がありました。

1.  **投機的なトリガーチェック**: 以前のGoランタイムでは、メモリ割り当て時にGCトリガーが「投機的に」チェックされていました。これは、GCが必要かどうかを大まかに判断するもので、厳密なチェックではありませんでした。
2.  **競合状態**: 複数のGoroutineがほぼ同時にこの投機的なチェックを通過し、GCが必要だと判断する可能性があります。
3.  **冗長なGCサイクルの開始**: Goroutine AがGCを開始し、そのGCサイクルが完了してヒープがクリーンになった後でも、Goroutine Bが以前の投機的なチェックの結果に基づいてGCを開始しようとすることがありました。これは、Goroutine BがGC開始処理に入る前にプリエンプトされ、Goroutine AのGCが完了するまで待たされた場合に特に顕著でした。結果として、ヒープがGCトリガーを下回っているにもかかわらず、不必要なGCサイクルが開始されていました。
4.  **バックグラウンドスイープの遅延**: コミットメッセージで言及されているように、このような冗長なGCサイクルは、バックグラウンドスイープ（GCの最終段階でメモリをOSに解放する処理）の完了を妨げ、次の並行スキャン（GCのマーキングフェーズ）の開始を遅らせる原因となっていました。これは、GCの効率とアプリケーションのパフォーマンスに悪影響を与えます。Issue #11911は、この問題によって引き起こされる具体的なパフォーマンス上の懸念を追跡していたと考えられます。

このコミットは、GCの開始ロジックに厳密な再チェックを導入することで、これらの問題を解決し、GCの効率性と正確性を向上させることを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に以下の特徴を持つ並行（concurrent）かつ非世代別（non-generational）のマーク＆スイープ型ガベージコレクタです。

*   **並行性**: GCの大部分は、アプリケーションのGoroutineと並行して実行されます。これにより、アプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑え、レイテンシを低減します。
*   **マーク＆スイープ**:
    *   **マークフェーズ**: 実行中のプログラムが一時停止され（短いSTW）、到達可能なオブジェクトをマークします。その後、アプリケーションの実行が再開され、GCは並行してマークを続けます。
    *   **スイープフェーズ**: マークされなかったオブジェクト（到達不能なオブジェクト）がメモリから解放されます。このフェーズも大部分が並行して行われます。
*   **GCトリガー**: GCは、ヒープの使用量が特定の閾値（`GOGC`環境変数やヒープの成長率に基づいて動的に決定される）を超えたときにトリガーされます。

### `startGC` 関数

`startGC`はGoランタイム内部の関数で、新しいGCサイクルを開始する役割を担います。この関数は、GCトリガーが検出された際に呼び出され、GCの初期化、Goroutineの停止（必要な場合）、GCワーカーGoroutineの起動などを行います。

### 並行性 (Concurrency) と競合状態 (Race Condition)

GoはGoroutineとチャネルによって高い並行性を実現しますが、複数のGoroutineが共有リソース（この場合はGCトリガーのチェックとGCの開始）に同時にアクセスしようとすると、競合状態が発生する可能性があります。今回の問題は、GCトリガーのチェックとGC開始の間に発生する競合状態の一例です。

### バックグラウンドスイープ (Background Sweep)

GCのスイープフェーズは、マークされなかったオブジェクトが占めていたメモリを解放するプロセスです。このスイープは、GCサイクルが完了した後もバックグラウンドで継続して行われることがあります。バックグラウンドスイープが完了する前に次のGCサイクルが開始されると、メモリの再利用が遅れ、ヒープの断片化やパフォーマンスの低下につながる可能性があります。

### Issue #11911

コミットメッセージで言及されているIssue #11911は、このコミットが解決しようとしている問題、すなわち「バックグラウンドスイープが完了する前に次のGCサイクルが開始され、並行スキャンの開始が大幅に遅れる」という状況に関連するGoランタイムのパフォーマンス問題またはバグを追跡していたものと推測されます。具体的なIssueの内容は公開されている情報からは確認できませんでしたが、コミットメッセージからその影響の深刻さが伺えます。

## 技術的詳細

このコミットが解決する問題は、GoランタイムのGCトリガー検出とGC開始の間の時間的ギャップと、複数のGoroutineによる並行処理に起因します。

1.  **投機的チェックの問題**: 以前のシステムでは、メモリ割り当てを行うGoroutineがGCトリガー条件を「投機的に」チェックしていました。これは、GCが必要かどうかを迅速に判断するための軽量なチェックでしたが、その結果は必ずしも最新のヒープ状態を反映しているわけではありませんでした。
2.  **複数GoroutineによるGC開始の試み**: Goroutine AとGoroutine Bがほぼ同時にメモリを割り当て、両方とも投機的なチェックでGCトリガーが発動したと判断したとします。
    *   Goroutine Aが`startGC`に入り、GCサイクルを開始します。
    *   その間にGoroutine Bはプリエンプトされ、Goroutine AによるGCサイクル全体が完了するまで実行が中断されます。
    *   Goroutine AのGCが完了すると、ヒープはクリーンアップされ、GCトリガー条件を十分に下回る状態になります。
    *   しかし、Goroutine Bは以前の投機的なチェックの結果に基づいて、まだGCが必要だと「信じて」います。Goroutine Bが実行を再開し、`startGC`に入ると、ヒープが既にクリーンであるにもかかわらず、新たなGCサイクルを開始しようとします。
3.  **冗長なGCとパフォーマンスへの影響**: このような冗長なGCサイクルは、CPUリソースの無駄遣いであるだけでなく、GCの各フェーズ（特にバックグラウンドスイープ）の完了を妨げます。バックグラウンドスイープが完了する前に次のGCが開始されると、メモリの再利用が遅れ、結果として並行スキャン（GCのマーキングフェーズの一部）の開始が遅延し、GC全体の効率が低下します。

**解決策**:
このコミットは、`startGC`関数内でGCを実際に開始する直前に、GCトリガー条件を「非投機的に」再チェックするというシンプルな解決策を導入します。

*   `startGC`関数に入ったGoroutineは、まず`bggc.lock`というロックを取得します。これは、複数のGoroutineが同時にGC開始処理のクリティカルセクションに入るのを防ぐためです。
*   ロックを取得した後、`shouldtriggergc()`関数を呼び出して、GCをトリガーすべきかどうかを再度、厳密にチェックします。
*   もし`shouldtriggergc()`が`false`を返した場合（つまり、他のGoroutineが既にGCを完了しており、ヒープがGCトリガーを下回っている場合）、そのGoroutineはロックを解放して`startGC`から即座にリターンします。これにより、不必要なGCサイクルの開始が防止されます。
*   `shouldtriggergc()`が`true`を返した場合にのみ、GCサイクルが続行されます。

この変更により、GCトリガーの検出とGC開始の間の競合状態が解消され、GCの効率と安定性が向上します。

## コアとなるコードの解説

追加されたコードブロックは、`startGC`関数の冒頭、`bggc.lock`が取得された直後に配置されています。

```go
	lock(&bggc.lock) // GC開始処理のクリティカルセクションに入るためのロック
	// The trigger was originally checked speculatively, so
	// recheck that this really should trigger GC. (For example,
	// we may have gone through a whole GC cycle since the
	// speculative check.)
	if !shouldtriggergc() { // GCをトリガーすべきか再確認
		unlock(&bggc.lock) // 不要であればロックを解放
		return             // GCを開始せずに終了
	}
```

1.  **`lock(&bggc.lock)`**:
    *   `bggc.lock`は、バックグラウンドGCの開始を調整するためのミューテックス（ロック）です。
    *   このロックを取得することで、複数のGoroutineが同時にGC開始のロジックを並行して実行するのを防ぎ、GC開始処理の整合性を保ちます。

2.  **コメント**:
    *   「The trigger was originally checked speculatively, so recheck that this really should trigger GC. (For example, we may have gone through a whole GC cycle since the speculative check.)」
    *   これは、この再チェックの必要性を明確に説明しています。最初のGCトリガーチェックが投機的であったため、GCを実際に開始する前に、本当にGCが必要かどうかを再確認する必要があることを示しています。特に、投機的チェックの後、他のGoroutineによってGCサイクル全体が完了している可能性があることを指摘しています。

3.  **`if !shouldtriggergc() { ... }`**:
    *   `shouldtriggergc()`関数は、現在のヒープの状態に基づいてGCをトリガーすべきかどうかを判断するGoランタイム内部の関数です。この関数は、ヒープの使用量とGCトリガーの閾値を比較し、GCが必要な場合に`true`を返します。
    *   `!`演算子により、`shouldtriggergc()`が`false`を返した場合（つまり、GCが不要であると判断された場合）に条件が真となります。
    *   この条件が真の場合、以下の処理が実行されます。
        *   `unlock(&bggc.lock)`: 取得していたロックを解放します。
        *   `return`: `startGC`関数から即座にリターンし、GCサイクルを開始しません。

このコードブロックの追加により、`startGC`関数が呼び出された時点で、たとえ以前に投機的なチェックでGCが必要と判断されていても、GC開始の直前にもう一度厳密なチェックが行われるようになりました。これにより、他のGoroutineが既にGCを完了しているような状況での冗長なGCサイクルの開始が効果的に防止され、GCの効率とシステムの安定性が向上します。

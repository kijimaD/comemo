# [インデックス 20655] ファイルの概要

このコミットは、Go言語のビルドツールである `go build` および `go install` コマンドの `-a` フラグの挙動を改善するものです。特に、Goのリリース版を使用している場合に、標準ライブラリの再コンパイルをスキップするように変更することで、ユーザーエクスペリエンスとシステムの安定性を向上させています。

## コミット

```
commit 8c3005c4929e26cba74c80703123e150fa3fda1a
Author: Russ Cox <rsc@golang.org>
Date:   Fri Sep 26 14:41:26 2014 -0400

    cmd/go: make build -a skip standard packages in Go releases

    Today, 'go build -a my/pkg' and 'go install -a my/pkg'
    recompile not just my/pkg and all its dependencies that
    you wrote but also the standard library packages.
    Recompiling the standard library is problematic on
    some systems because the installed copy is not writable.

    The -a behavior means that you can't use 'go install -a all'
    or 'go install -a my/...' to rebuild everything after a Go
    release - the rebuild halts early when it cannot overwrite
    the installed standard library.

    During development work, however, you do want install -a
    to rebuild everything, because anything might have changed.

    Resolve the conflict by making the behavior of -a depend
    on whether we are using a released copy of Go or a devel copy.
    In the release copies, -a no longer applies to the standard library.
    In the devel copies, it still does.

    This is the latest in a long line of refinements to the
    "do I build this or not" logic. It is surely not the last.

    Fixes #8290.
```

## 元コミット内容

`cmd/go: make build -a skip standard packages in Go releases`

このコミットは、`go build -a` および `go install -a` コマンドが、Goのリリース版において標準ライブラリのパッケージを再コンパイルしないように変更します。これにより、標準ライブラリが書き込み可能でないシステムでの問題や、リリース後の再ビルドの際に発生する問題を解決します。開発版では引き続き標準ライブラリも再コンパイルされます。

## 変更の背景

Goのビルドコマンドである `go build` や `go install` に `-a` フラグを付与すると、指定されたパッケージとその依存関係だけでなく、Goの標準ライブラリも強制的に再コンパイルする挙動がありました。この挙動は、特にGoのリリース版がインストールされている環境において、いくつかの問題を引き起こしていました。

1.  **書き込み権限の問題**: 多くのシステムでは、Goのリリース版がインストールされるディレクトリ（例: `/usr/local/go`）は、一般ユーザーが書き込み権限を持たない場合があります。このため、`go build -a` が標準ライブラリの再コンパイルを試みると、権限エラーが発生し、ビルドが失敗していました。
2.  **リリース後の再ビルドの阻害**: Goの新しいリリースが公開された後、ユーザーが `go install -a all` や `go install -a my/...` のように、システム上のすべてのパッケージを再ビルドしようとすると、標準ライブラリの再コンパイルが試みられ、前述の書き込み権限の問題により処理が途中で停止してしまうことがありました。これは、ユーザーが期待する「すべてを再ビルドする」という操作を妨げていました。
3.  **開発ワークフローとの乖離**: 開発中のGoのソースコードを使用している場合、標準ライブラリのコードも頻繁に変更される可能性があります。この場合、`-a` フラグによって標準ライブラリも再コンパイルされることは、最新の変更を反映するために望ましい挙動でした。しかし、リリース版では標準ライブラリは安定しており、通常は変更されません。このため、リリース版と開発版で `-a` の挙動に一貫性を持たせる必要がありました。

これらの問題を解決し、ユーザーがよりスムーズにGoのツールを使用できるようにするため、リリース版と開発版で `-a` フラグの挙動を区別する変更が導入されました。この変更は、Goのビルドロジックにおける「これをビルドするかどうか」という判断の長い改善の歴史の一部であり、Issue #8290 に対応するものです。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびビルドシステムに関する基本的な知識が必要です。

1.  **`go build` および `go install` コマンド**:
    *   `go build`: Goのソースコードをコンパイルして実行可能バイナリを生成します。
    *   `go install`: `go build` と同様にコンパイルを行いますが、生成されたバイナリやパッケージアーカイブを `$GOPATH/bin` や `$GOPATH/pkg` (または `$GOBIN` や `$GOCACHE`) などの標準的な場所にインストールします。
2.  **`-a` フラグ**:
    *   `go build -a` または `go install -a` のように使用されるこのフラグは、「強制的にすべてのパッケージを再ビルドする」という意味を持ちます。通常、Goのビルドシステムは、ソースファイルが変更されていない場合や、依存関係が最新である場合には、以前にビルドされたキャッシュを利用してビルド時間を短縮します。しかし、`-a` フラグを使用すると、このキャッシュを無視し、依存関係を含むすべてのパッケージをゼロから再コンパイルします。これは、ビルド環境のクリーンアップや、特定のビルド問題のデバッグに役立ちます。
3.  **標準ライブラリ (Standard Library)**:
    *   Go言語に標準で付属しているパッケージ群です。`fmt`, `net/http`, `os`, `io`, `sync` など、Goプログラムの基本的な機能を提供する多数のパッケージが含まれます。これらはGoのインストール時にコンパイル済みバイナリとして提供されることが多く、通常はユーザーが直接変更することはありません。
4.  **Goのリリース版と開発版**:
    *   **リリース版 (Released Copy)**: `go1.x` のようなバージョン番号が付与された、安定版のGoディストリビューションです。これらは公式ウェブサイトからダウンロードでき、通常はプロダクション環境での使用を目的としています。標準ライブラリのコードは安定しており、変更されることはありません。
    *   **開発版 (Devel Copy)**: Goのソースコードリポジトリ（通常は `master` ブランチ）から直接ビルドされたバージョンです。これは、Go言語自体の開発者が新しい機能の追加やバグ修正を行っている途中のバージョンであり、標準ライブラリのコードも頻繁に変更されます。
5.  **`runtime.Version()`**:
    *   Goの `runtime` パッケージが提供する関数で、現在実行中のGoランタイムのバージョン文字列を返します。この文字列は、リリース版では "go1.X[.Y]" のような形式（例: "go1.3"）、開発版では "devel +hash" のような形式（例: "devel +8c3005c"）になります。この違いを利用して、現在のGoの実行環境がリリース版か開発版かをプログラム的に判断することができます。

## 技術的詳細

このコミットの技術的な核心は、`go build -a` の挙動を、Goの実行環境が「リリース版」であるか「開発版」であるかによって動的に変更する点にあります。

1.  **Goリリース版の判定**:
    *   `src/cmd/go/pkg.go` に `isGoRelease` というグローバル変数が導入されました。
    *   この変数は、`runtime.Version()` の戻り値が `"go1"` で始まらない場合に `true` となります。つまり、バージョン文字列が `"go1.X"` や `"go1.X.Y"` の形式であればリリース版と判断し、それ以外（主に `"devel +hash"` 形式）であれば開発版と判断します。
    *   具体的には、`var isGoRelease = !strings.HasPrefix(runtime.Version(), "go1")` というコードで判定が行われます。これは、Go 1.x 系のリリースバージョンは "go1" で始まるため、それ以外を開発版と見なすというロジックです。
2.  **`-a` フラグの適用範囲の変更**:
    *   `src/cmd/go/pkg.go` 内の `isStale` 関数が変更されました。この関数は、特定のパッケージが再ビルドする必要があるかどうかを判断するGoコマンドの内部ロジックです。
    *   以前は、`buildA` (つまり `-a` フラグが指定されているか) が `true` であれば、無条件にパッケージを再ビルドする必要があると判断していました。
    *   変更後、`p.Standard && isGoRelease` という条件が追加されました。これは、「現在のパッケージが標準ライブラリのパッケージであり ( `p.Standard` )、かつGoの実行環境がリリース版である ( `isGoRelease` )」場合に `pkgBuildA` というローカル変数を `false` に設定します。
    *   結果として、リリース版のGoで標準ライブラリのパッケージに対して `-a` フラグが指定されても、`pkgBuildA` が `false` になるため、再ビルドがスキップされるようになります。
    *   このロジックにより、リリース版では標準ライブラリが書き込み不可である問題や、不要な再コンパイルによるビルド時間の増加が回避されます。
3.  **ドキュメントの更新**:
    *   `src/cmd/go/build.go` と `src/cmd/go/doc.go` のヘルプメッセージが更新され、`-a` フラグの挙動が「Goのリリース版では標準ライブラリには適用されない」という旨が明記されました。これにより、ユーザーは新しい挙動を理解しやすくなります。
4.  **テストの追加**:
    *   `src/cmd/go/test.bash` に、リリース版と開発版での `-a` フラグの挙動を検証する新しいテストケースが追加されました。これにより、変更が意図通りに機能し、将来のリグレッションを防ぐことができます。
    *   特に、`TESTGO_IS_GO_RELEASE` という環境変数を使って、テスト実行時にGoがリリース版であるか開発版であるかをシミュレートする仕組みが導入されました。これは、`src/cmd/go/testgo.go` という新しいファイルで処理されます。`testgo.go` は `+build testgo` ビルドタグを持つため、通常のGoコマンドには含まれず、テストビルド時のみ有効になります。

この変更は、Goのビルドシステムが、その実行環境（開発中か、安定版か）に応じて賢く振る舞うように進化していることを示しています。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は、`src/cmd/go/pkg.go` ファイルに集中しています。

1.  **`isGoRelease` 変数の追加**:
    ```go
    // The runtime version string takes one of two forms:
    // "go1.X[.Y]" for Go releases, and "devel +hash" at tip.
    // Determine whether we are in a released copy by
    // inspecting the version.
    var isGoRelease = !strings.HasPrefix(runtime.Version(), "go1")
    ```
    この行は、Goの実行環境がリリース版であるかどうかを判定するためのブール変数 `isGoRelease` を定義しています。`runtime.Version()` が "go1" で始まる文字列（例: "go1.3"）を返す場合、それはリリース版と見なされ、`isGoRelease` は `false` になります。それ以外の場合（例: "devel +hash"）、`isGoRelease` は `true` になります。

2.  **`isStale` 関数のロジック変更**:
    ```go
    func isStale(p *Package, topRoot map[string]bool) bool {
    	// ... (既存のコード) ...

    	// If we are running a release copy of Go, do not rebuild the standard packages.
    	// They may not be writable anyway, but they are certainly not changing.
    	// This makes 'go build -a' skip the standard packages when using an official release.
    	// See issue 4106 and issue 8290.
    	pkgBuildA := buildA
    	if p.Standard && isGoRelease {
    		pkgBuildA = false
    	}

    	if pkgBuildA || p.target == "" || p.Stale {
    		return true
    	}
    	// ... (既存のコード) ...
    }
    ```
    この部分が、`-a` フラグの挙動を制御する核心です。
    *   `pkgBuildA := buildA` で、まず `pkgBuildA` をグローバルな `buildA` (コマンドラインで `-a` が指定されたか) の値で初期化します。
    *   `if p.Standard && isGoRelease` の条件が重要です。
        *   `p.Standard`: 現在処理しているパッケージがGoの標準ライブラリの一部であるかどうかを示します。
        *   `isGoRelease`: 上記で定義された変数で、Goの実行環境がリリース版であるかどうかを示します。
    *   もし両方の条件が `true` であれば（つまり、リリース版のGoで標準ライブラリのパッケージを処理している場合）、`pkgBuildA` は `false` に上書きされます。
    *   その後の `if pkgBuildA || p.target == "" || p.Stale` の条件式では、`pkgBuildA` が `false` になっているため、`-a` フラグが指定されていても標準ライブラリの再ビルドは強制されなくなります。

## コアとなるコードの解説

`src/cmd/go/pkg.go` は、Goコマンドがパッケージのビルド状態を管理し、再ビルドが必要かどうかを判断するロジックを含む重要なファイルです。

1.  **`isGoRelease` 変数**:
    この変数は、Goのビルドシステムが自身の実行環境を認識するためのメカニズムを提供します。`runtime.Version()` は、Goバイナリがビルドされた際のバージョン情報を含んでおり、これを利用して「公式リリース版」と「開発中のバージョン（tip）」を区別します。
    *   公式リリース版（例: `go1.3`, `go1.3.1`）は、バージョン文字列が `go1` で始まります。これらのバージョンでは、標準ライブラリは安定しており、通常は変更されません。
    *   開発中のバージョン（例: `devel +8c3005c`）は、バージョン文字列が `go1` で始まりません。これらのバージョンでは、標準ライブラリのコードが頻繁に変更される可能性があります。
    この `isGoRelease` 変数によって、Goコマンドは自身のコンテキストを理解し、それに応じて挙動を調整できるようになります。

2.  **`isStale` 関数内のロジック**:
    `isStale` 関数は、Goコマンドが特定のパッケージを再ビルドする必要があるかどうかを決定する中心的なロジックです。この関数は、パッケージのソースファイルのタイムスタンプ、依存関係の変更、およびコマンドラインフラグ（例: `-a`）に基づいて判断を行います。
    変更されたロジックは、以下のシナリオを考慮しています。
    *   **開発版のGo (`isGoRelease` が `false`)**: `pkgBuildA` は `buildA` の値（つまり `-a` フラグが指定されたか）をそのまま保持します。したがって、`-a` が指定されていれば、標準ライブラリを含むすべてのパッケージが強制的に再ビルドされます。これは、開発中に標準ライブラリの変更をテストするために望ましい挙動です。
    *   **リリース版のGo (`isGoRelease` が `true`)**:
        *   もし現在のパッケージが標準ライブラリの一部である場合 (`p.Standard` が `true`)、`pkgBuildA` は `false` に上書きされます。これにより、`-a` フラグが指定されていても、標準ライブラリのパッケージは再ビルドの対象から外れます。これは、リリース版の標準ライブラリが通常は書き込み不可であり、変更されることもないため、不要なエラーや時間の浪費を防ぎます。
        *   もし現在のパッケージが標準ライブラリではない場合 (`p.Standard` が `false`)、`pkgBuildA` は `buildA` の値を保持するため、ユーザーが書いたコードやサードパーティの依存関係は、`-a` フラグが指定されていれば強制的に再ビルドされます。

この変更により、Goコマンドは、ユーザーが意図するであろう挙動（開発中はすべて再ビルド、リリース版では安定した標準ライブラリはスキップ）をより適切に反映できるようになりました。これは、Goのビルドシステムの堅牢性とユーザーフレンドリーさを向上させる重要な改善です。

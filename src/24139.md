## 変更の背景

このコミットは、Goランタイムにおける特定の条件下でのスタックトレースの不正確さを修正するために導入されました。具体的には、GoのIssue #11656「runtime: jump to bad PC missing good traceback」で報告された問題に対処しています。

この問題は、プログラムがヒープメモリ上に存在する、有効なGoの関数ではないアドレスを関数ポインタとして呼び出そうとした際に発生していました。通常、このような不正なメモリ領域へのジャンプはセグメンテーション違反（SIGSEGV）などのシグナルを引き起こし、Goランタイムのシグナルハンドラがこれを捕捉してパニックを発生させ、スタックトレースを出力します。

しかし、従来のGoランタイムのシグナルハンドラでは、プログラムカウンタ（PC）が不正なアドレスを指している場合、スタックトレースが正しく生成されないことがありました。特に、PCがGoのコードとして認識されないアドレスを指しているが、スタックのトップにあるリターンアドレスが有効なGoのコードを指しているような状況で、スタックトレースが途切れてしまい、本来の呼び出し元（コンテキスト）が失われるという問題がありました。これにより、デバッグが困難になるという課題がありました。

このコミットは、このような「不正なPCへのジャンプ」が発生した場合でも、スタックトレースが呼び出し元のコンテキストを正確に反映するように改善することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **プログラムカウンタ (PC)**: CPUが次に実行する命令のアドレスを保持するレジスタです。x86アーキテクチャでは、32ビットモードでは`EIP` (Instruction Pointer)、64ビットモードでは`RIP` (Instruction Pointer) と呼ばれます。
2.  **スタックポインタ (SP)**: 現在のスタックフレームのトップ（またはボトム、アーキテクチャによる）のアドレスを保持するレジスタです。x86アーキテクチャでは、32ビットモードでは`ESP` (Stack Pointer)、64ビットモードでは`RSP` (Stack Pointer) と呼ばれます。
3.  **スタックトレース**: プログラムがエラーやパニックを起こした際に、その時点までの関数呼び出しの履歴をリストアップしたものです。これにより、どの関数がどの関数を呼び出し、最終的にエラーが発生したのかを追跡できます。
4.  **シグナルハンドラ**: オペレーティングシステムがプロセスにシグナル（例: セグメンテーション違反、不正な命令など）を送信した際に、そのシグナルを捕捉して特定の処理を実行する関数です。Goランタイムは、プログラムの異常終了を防ぎ、パニックを発生させるために独自のシグナルハンドラを設定しています。
5.  **`runtime.sigpanic`**: Goランタイム内部の関数で、シグナルハンドラが捕捉した致命的なエラー（例: nilポインタ参照、配列の範囲外アクセス、不正なメモリアクセスなど）をGoのパニック機構に変換する役割を担います。
6.  **`findfunc(pc)`**: Goランタイム内部の関数で、与えられたプログラムカウンタ（PC）がGoの関数コードの範囲内にあるかどうかを判定します。これにより、PCが有効なGoの関数を指しているかを確認できます。
7.  **ヒープメモリ**: プログラム実行中に動的に確保されるメモリ領域です。Goでは、`new`や`make`などで確保されたオブジェクトがヒープに配置されます。
8.  **関数ポインタ**: 関数のアドレスを保持する変数です。Goでは、関数をファーストクラスの値として扱うことができ、関数ポインタを通じて間接的に関数を呼び出すことが可能です。

この問題は、特にGoのランタイムが、不正なPCを検出した際に、スタック上のリターンアドレスが有効なGoの関数を指している場合に、そのリターンアドレスを基にスタックトレースを再構築しようとするロジックの改善に関するものです。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのシグナルハンドラ（`sighandler`関数）における、パニック発生時のスタックトレース生成ロジックの改善にあります。特に、x86およびx86-64アーキテクチャにおいて、プログラムカウンタ（PC）が不正なアドレスを指しているが、スタック上のリターンアドレスが有効なGoの関数を指している場合に、より適切なスタックトレースを生成するための変更が加えられています。

変更前は、`sighandler`関数内でPC（32ビットでは`c.eip()`、64ビットでは`c.rip()`）が0でない場合にのみ`runtime.sigpanic`をスタックにプッシュしていました。PCが0の場合は、nil関数への呼び出しが原因であると判断され、`runtime.sigpanic`をプッシュしないことで、スタックトレースが`runtime.sigpanic`で終わらず、より上位の呼び出し元（faultを起こした場所）が見えるようにしていました。

しかし、このロジックでは、PCが0ではないがGoのコードとして認識されないアドレス（例: ヒープ上の不正なアドレス）を指しており、かつスタックのトップにあるリターンアドレスが有効なGoのコードを指しているような特定のシナリオで問題が発生していました。このような場合、従来のロジックではPCが0ではないため`runtime.sigpanic`がプッシュされ、結果としてスタックトレースが不完全になるか、誤った情報を含む可能性がありました。

このコミットでは、以下の新しいロジックが導入されました。

1.  **PCとSPの取得**: まず、現在のPC (`c.eip()`/`c.rip()`) とSP (`c.esp()`/`c.rsp()`) を取得します。
2.  **PCの検証と調整**:
    *   現在のPCが0ではない (`pc != 0`)。
    *   現在のPCがGoの関数として認識されない (`findfunc(pc) == nil`)。
    *   しかし、スタックのトップにある値（通常はリターンアドレス）がGoの関数として認識される (`findfunc(*(*uintptr)(unsafe.Pointer(sp))) != nil`)。
    *   上記の3つの条件がすべて満たされる場合、これは「コードではない場所への呼び出しだが、スタックには有効な呼び出し元が残っている」状況であると判断されます。この場合、スタックトレースのコンテキストを正しく表示するために、**現在のPCを意図的に0に設定します (`pc = 0`)**。
3.  **`runtime.sigpanic`のプッシュ条件の変更**: `runtime.sigpanic`をスタックにプッシュする条件が、元のPCが0ではない場合から、**調整後のPCが0ではない場合 (`if pc != 0`)** に変更されました。

この変更により、前述の「PCが不正だがスタックトップが有効」なシナリオでは、PCが0に設定されるため、`runtime.sigpanic`はスタックにプッシュされなくなります。これにより、スタックトレースは`runtime.sigpanic`で終わることなく、スタックトップにある有効なリターンアドレスを基に、本来の呼び出し元のコンテキストを正確に表示できるようになります。これは、デバッグ時にパニックの原因を特定する上で非常に重要な改善です。

また、テストケース`test/fixedbugs/issue11656.go`が追加され、この修正が正しく機能することを確認しています。このテストは、ヒープ上に確保された構造体のアドレスを関数ポインタとしてキャストし、それを呼び出すことで意図的に不正なメモリアクセスを引き起こし、その際のスタックトレースが`main.f`を正しく指していることを検証します。

`test/run.go`の変更は、新しいテストファイルが特定のOS/アーキテクチャ（darwin/386, openbsd/386, plan9/386, windows）でスキップされるように、ビルド制約の評価ロジックを調整しています。これは、これらのプラットフォームではシグナルハンドリングの挙動が異なったり、テストの意図する動作を再現できないためです。

## コアとなるコードの解説

`src/runtime/signal_386.go`と`src/runtime/signal_amd64x.go`における変更は、Goランタイムのシグナルハンドラがパニックを処理する際の挙動を根本的に改善しています。

1.  **PCとSPの初期化**:
    ```go
    pc := uintptr(c.eip()) // または c.rip() for amd64
    sp := uintptr(c.esp()) // または c.rsp() for amd64
    ```
    まず、現在のプログラムカウンタ（PC）とスタックポインタ（SP）の値をレジスタコンテキスト`c`から取得し、`uintptr`型に変換してローカル変数`pc`と`sp`に格納します。これにより、元のレジスタ値を直接操作するのではなく、コピーに対して処理を行うことができます。

2.  **PCの条件付きリセット**:
    ```go
    // If we don't recognize the PC as code
    // but we do recognize the top pointer on the stack as code,
    // then assume this was a call to non-code and treat like
    // pc == 0, to make unwinding show the context.
    if pc != 0 && findfunc(pc) == nil && findfunc(*(*uintptr)(unsafe.Pointer(sp))) != nil {
        pc = 0
    }
    ```
    この部分が変更の核心です。
    *   `pc != 0`: 現在のPCが0ではないことを確認します。PCが0の場合は、既にnil関数呼び出しとして扱われるため、このロジックは不要です。
    *   `findfunc(pc) == nil`: 現在のPCがGoの関数コードとして認識されないことを確認します。これは、PCがデータ領域や不正なメモリ領域を指している可能性を示唆します。
    *   `findfunc(*(*uintptr)(unsafe.Pointer(sp))) != nil`: スタックポインタ`sp`が指すアドレス（通常は関数呼び出し後のリターンアドレス）が、有効なGoの関数コードとして認識されることを確認します。

    これら3つの条件がすべて真である場合、Goランタイムは「現在のPCは不正だが、スタックには有効な呼び出し元の情報が残っている」と判断します。このような状況では、スタックトレースを正しく生成するために、**`pc`の値を0にリセットします**。これにより、後続の`runtime.sigpanic`のプッシュロジックが、このケースを「PCが0の場合」として扱い、`runtime.sigpanic`をスタックにプッシュしないように誘導します。結果として、スタックトレースはスタック上の有効なリターンアドレスから継続され、より正確な呼び出しコンテキストが提供されます。

3.  **`runtime.sigpanic`のプッシュロジックの変更**:
    ```diff
    -		if c.eip() != 0 {
    +		if pc != 0 {
    ```
    `runtime.sigpanic`をスタックにプッシュするかどうかの条件が、元の`c.eip() != 0`（または`c.rip() != 0`）から、**調整後の`pc != 0`** に変更されました。
    前述のロジックで`pc`が0にリセットされた場合、この条件は偽となり、`runtime.sigpanic`はスタックにプッシュされません。これにより、スタックトレースは`runtime.sigpanic`で途切れることなく、スタック上の有効なリターンアドレスから継続されます。

    その後のスタック操作（`sp`を減らし、リターンアドレスと0をスタックにプッシュする）は、`runtime.sigpanic`が呼び出される準備をするための標準的な手順です。`c.set_esp(uint32(sp))`（または`c.set_rsp(uint64(sp))`）でスタックポインタを更新し、`c.set_eip(uint32(funcPC(sigpanic)))`（または`c.set_rip(uint64(funcPC(sigpanic)))`）でPCを`runtime.sigpanic`関数のエントリポイントに設定することで、シグナルハンドラから戻った際に`runtime.sigpanic`が実行されるようにします。

`test/fixedbugs/issue11656.go`の`main.f`関数は、この問題の再現に特化しています。
```go
func f(n int) {
	if n > 0 {
		f(n-1)
	}
	var f struct {
		x uintptr
	}
	f.x = uintptr(unsafe.Pointer(&f)) // 構造体fのアドレスをuintptrとして取得
	fn := *(*func())(unsafe.Pointer(&f)) // そのuintptrを関数ポインタにキャスト
	fn() // 不正な関数ポインタを呼び出す
}
```
このコードでは、ローカル変数`f`（構造体）のアドレスを`uintptr`に変換し、さらにそれを`func()`型の関数ポインタ`fn`にキャストしています。そして、この`fn`を呼び出すことで、Goのコードとしては不正なメモリ領域（データ領域）を関数として実行しようとします。これにより、セグメンテーション違反が発生し、Goランタイムのシグナルハンドラが起動します。テストの目的は、このパニック発生時に`runtime.Caller(10)`で取得される呼び出し元が、正しく`main.f`であることを確認することです。修正前はこれが失敗し、修正後には成功するようになります。

## 変更の背景

このコミットは、Goランタイムにおける特定の条件下でのスタックトレースの不正確さを修正するために導入されました。具体的には、GoのIssue #11656「runtime: jump to bad PC missing good traceback」で報告された問題に対処しています。

この問題は、プログラムがヒープメモリ上に存在する、有効なGoの関数ではないアドレスを関数ポインタとして呼び出そうとした際に発生していました。通常、このような不正なメモリ領域へのジャンプはセグメンテーション違反（SIGSEGV）などのシグナルを引き起こし、Goランタイムのシグナルハンドラがこれを捕捉してパニックを発生させ、スタックトレースを出力します。

しかし、従来のGoランタイムのシグナルハンドラでは、プログラムカウンタ（PC）が不正なアドレスを指している場合、スタックトレースが正しく生成されないことがありました。特に、PCがGoのコードとして認識されないアドレスを指しているが、スタックのトップにあるリターンアドレスが有効なGoのコードを指しているような状況で、スタックトレースが途切れてしまい、本来の呼び出し元（コンテキスト）が失われるという問題がありました。これにより、デバッグが困難になるという課題がありました。

このコミットは、このような「不正なPCへのジャンプ」が発生した場合でも、スタックトレースが呼び出し元のコンテキストを正確に反映するように改善することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **プログラムカウンタ (PC)**: CPUが次に実行する命令のアドレスを保持するレジスタです。x86アーキテクチャでは、32ビットモードでは`EIP` (Instruction Pointer)、64ビットモードでは`RIP` (Instruction Pointer) と呼ばれます。
2.  **スタックポインタ (SP)**: 現在のスタックフレームのトップ（またはボトム、アーキテクチャによる）のアドレスを保持するレジスタです。x86アーキテクチャでは、32ビットモードでは`ESP` (Stack Pointer)、64ビットモードでは`RSP` (Stack Pointer) と呼ばれます。
3.  **スタックトレース**: プログラムがエラーやパニックを起こした際に、その時点までの関数呼び出しの履歴をリストアップしたものです。これにより、どの関数がどの関数を呼び出し、最終的にエラーが発生したのかを追跡できます。
4.  **シグナルハンドラ**: オペレーティングシステムがプロセスにシグナル（例: セグメンテーション違反、不正な命令など）を送信した際に、そのシグナルを捕捉して特定の処理を実行する関数です。Goランタイムは、プログラムの異常終了を防ぎ、パニックを発生させるために独自のシグナルハンドラを設定しています。
5.  **`runtime.sigpanic`**: Goランタイム内部の関数で、シグナルハンドラが捕捉した致命的なエラー（例: nilポインタ参照、配列の範囲外アクセス、不正なメモリアクセスなど）をGoのパニック機構に変換する役割を担います。
6.  **`findfunc(pc)`**: Goランタイム内部の関数で、与えられたプログラムカウンタ（PC）がGoの関数コードの範囲内にあるかどうかを判定します。これにより、PCが有効なGoの関数を指しているかを確認できます。
7.  **ヒープメモリ**: プログラム実行中に動的に確保されるメモリ領域です。Goでは、`new`や`make`などで確保されたオブジェクトがヒープに配置されます。
8.  **関数ポインタ**: 関数のアドレスを保持する変数です。Goでは、関数をファーストクラスの値として扱うことができ、関数ポインタを通じて間接的に関数を呼び出すことが可能です。

この問題は、特にGoのランタイムが、不正なPCを検出した際に、スタック上のリターンアドレスが有効なGoの関数を指している場合に、そのリターンアドレスを基にスタックトレースを再構築しようとするロジックの改善に関するものです。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのシグナルハンドラ（`sighandler`関数）における、パニック発生時のスタックトレース生成ロジックの改善にあります。特に、x86およびx86-64アーキテクチャにおいて、プログラムカウンタ（PC）が不正なアドレスを指しているが、スタック上のリターンアドレスが有効なGoの関数を指している場合に、より適切なスタックトレースを生成するための変更が加えられています。

変更前は、`sighandler`関数内でPC（32ビットでは`c.eip()`、64ビットでは`c.rip()`）が0でない場合にのみ`runtime.sigpanic`をスタックにプッシュしていました。PCが0の場合は、nil関数への呼び出しが原因であると判断され、`runtime.sigpanic`をプッシュしないことで、スタックトレースが`runtime.sigpanic`で終わらず、より上位の呼び出し元（faultを起こした場所）が見えるようにしていました。

しかし、このロジックでは、PCが0ではないがGoのコードとして認識されないアドレス（例: ヒープ上の不正なアドレス）を指しており、かつスタックのトップにあるリターンアドレスが有効なGoのコードを指しているような特定のシナリオで問題が発生していました。このような場合、従来のロジックではPCが0ではないため`runtime.sigpanic`がプッシュされ、結果としてスタックトレースが不完全になるか、誤った情報を含む可能性がありました。

このコミットでは、以下の新しいロジックが導入されました。

1.  **PCとSPの取得**: まず、現在のPC (`c.eip()`/`c.rip()`) とSP (`c.esp()`/`c.rsp()`) を取得します。
2.  **PCの検証と調整**:
    *   現在のPCが0ではない (`pc != 0`)。
    *   現在のPCがGoの関数として認識されない (`findfunc(pc) == nil`)。
    *   しかし、スタックのトップにある値（通常はリターンアドレス）がGoの関数として認識される (`findfunc(*(*uintptr)(unsafe.Pointer(sp))) != nil`)。
    *   上記の3つの条件がすべて満たされる場合、これは「コードではない場所への呼び出しだが、スタックには有効な呼び出し元が残っている」状況であると判断されます。この場合、スタックトレースのコンテキストを正しく表示するために、**現在のPCを意図的に0に設定します (`pc = 0`)**。
3.  **`runtime.sigpanic`のプッシュ条件の変更**: `runtime.sigpanic`をスタックにプッシュする条件が、元のPCが0ではない場合から、**調整後のPCが0ではない場合 (`if pc != 0`)** に変更されました。

この変更により、前述の「PCが不正だがスタックトップが有効」なシナリオでは、PCが0に設定されるため、`runtime.sigpanic`はスタックにプッシュされなくなります。これにより、スタックトレースは`runtime.sigpanic`で終わることなく、スタックトップにある有効なリターンアドレスを基に、本来の呼び出し元のコンテキストを正確に表示できるようになります。これは、デバッグ時にパニックの原因を特定する上で非常に重要な改善です。

また、テストケース`test/fixedbugs/issue11656.go`が追加され、この修正が正しく機能することを確認しています。このテストは、ヒープ上に確保された構造体のアドレスを関数ポインタとしてキャストし、それを呼び出すことで意図的に不正なメモリアクセスを引き起こし、その際のスタックトレースが`main.f`を正しく指していることを検証します。

`test/run.go`の変更は、新しいテストファイルが特定のOS/アーキテクチャ（darwin/386, openbsd/386, plan9/386, windows）でスキップされるように、ビルド制約の評価ロジックを調整しています。これは、これらのプラットフォームではシグナルハンドリングの挙動が異なったり、テストの意図する動作を再現できないためです。

## コアとなるコードの解説

`src/runtime/signal_386.go`と`src/runtime/signal_amd64x.go`における変更は、Goランタイムのシグナルハンドラがパニックを処理する際の挙動を根本的に改善しています。

1.  **PCとSPの初期化**:
    ```go
    pc := uintptr(c.eip()) // または c.rip() for amd64
    sp := uintptr(c.esp()) // または c.rsp() for amd64
    ```
    まず、現在のプログラムカウンタ（PC）とスタックポインタ（SP）の値をレジスタコンテキスト`c`から取得し、`uintptr`型に変換してローカル変数`pc`と`sp`に格納します。これにより、元のレジスタ値を直接操作するのではなく、コピーに対して処理を行うことができます。

2.  **PCの条件付きリセット**:
    ```go
    // If we don't recognize the PC as code
    // but we do recognize the top pointer on the stack as code,
    // then assume this was a call to non-code and treat like
    // pc == 0, to make unwinding show the context.
    if pc != 0 && findfunc(pc) == nil && findfunc(*(*uintptr)(unsafe.Pointer(sp))) != nil {
        pc = 0
    }
    ```
    この部分が変更の核心です。
    *   `pc != 0`: 現在のPCが0ではないことを確認します。PCが0の場合は、既にnil関数呼び出しとして扱われるため、このロジックは不要です。
    *   `findfunc(pc) == nil`: 現在のPCがGoの関数コードとして認識されないことを確認します。これは、PCがデータ領域や不正なメモリ領域を指している可能性を示唆します。
    *   `findfunc(*(*uintptr)(unsafe.Pointer(sp))) != nil`: スタックポインタ`sp`が指すアドレス（通常は関数呼び出し後のリターンアドレス）が、有効なGoの関数コードとして認識されることを確認します。

    これら3つの条件がすべて真である場合、Goランタイムは「現在のPCは不正だが、スタックには有効な呼び出し元の情報が残っている」と判断します。このような状況では、スタックトレースを正しく生成するために、**`pc`の値を0にリセットします**。これにより、後続の`runtime.sigpanic`のプッシュロジックが、このケースを「PCが0の場合」として扱い、`runtime.sigpanic`をスタックにプッシュしないように誘導します。結果として、スタックトレースはスタック上の有効なリターンアドレスから継続され、より正確な呼び出しコンテキストが提供されます。

3.  **`runtime.sigpanic`のプッシュロジックの変更**:
    ```diff
    -		if c.eip() != 0 {
    +		if pc != 0 {
    ```
    `runtime.sigpanic`をスタックにプッシュするかどうかの条件が、元の`c.eip() != 0`（または`c.rip() != 0`）から、**調整後の`pc != 0`** に変更されました。
    前述のロジックで`pc`が0にリセットされた場合、この条件は偽となり、`runtime.sigpanic`はスタックにプッシュされません。これにより、スタックトレースは`runtime.sigpanic`で途切れることなく、スタック上の有効なリターンアドレスから継続されます。

    その後のスタック操作（`sp`を減らし、リターンアドレスと0をスタックにプッシュする）は、`runtime.sigpanic`が呼び出される準備をするための標準的な手順です。`c.set_esp(uint32(sp))`（または`c.set_rsp(uint64(sp))`）でスタックポインタを更新し、`c.set_eip(uint32(funcPC(sigpanic)))`（または`c.set_rip(uint64(funcPC(sigpanic)))`）でPCを`runtime.sigpanic`関数のエントリポイントに設定することで、シグナルハンドラから戻った際に`runtime.sigpanic`が実行されるようにします。

`test/fixedbugs/issue11656.go`の`main.f`関数は、この問題の再現に特化しています。
```go
func f(n int) {
	if n > 0 {
		f(n-1)
	}
	var f struct {
		x uintptr
	}
	f.x = uintptr(unsafe.Pointer(&f)) // 構造体fのアドレスをuintptrとして取得
	fn := *(*func())(unsafe.Pointer(&f)) // そのuintptrを関数ポインタにキャスト
	fn() // 不正な関数ポインタを呼び出す
}
```
このコードでは、ローカル変数`f`（構造体）のアドレスを`uintptr`に変換し、さらにそれを`func()`型の関数ポインタ`fn`にキャストしています。そして、この`fn`を呼び出すことで、Goのコードとしては不正なメモリ領域（データ領域）を関数として実行しようとします。これにより、セグメンテーション違反が発生し、Goランタイムのシグナルハンドラが起動します。テストの目的は、このパニック発生時に`runtime.Caller(10)`で取得される呼び出し元が、正しく`main.f`であることを確認することです。修正前はこれが失敗し、修正後には成功するようになります。

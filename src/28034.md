# [インデックス 28034] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）サイクル終了後、特にマーク終了フェーズの直後に、スタックバリアを削除する「ベストエフォート」な処理を追加します。この変更は、Goランタイム自体の動作には必須ではありませんが、GDB、perf、VTuneといった外部のデバッグ・プロファイリングツールがGoプログラムのスタックを正確にウォーク（辿る）できるようにすることを目的としています。これにより、これらのツールがGoのスタックバリアに起因するスタックウォークの困難を軽減し、より正確な情報を提供できるようになります。

## 変更の背景

Goのガベージコレクタ（GC）は、アプリケーションの実行と並行して動作するコンカレントなマーク＆スイープ方式を採用しています。このGCの正確性と効率性を保証するために、Goランタイムは「スタックバリア」と呼ばれるメカニズムを使用しています。スタックバリアは、GCがスタック上のポインタを正確に追跡し、ライブオブジェクトを誤って回収しないようにするための重要な要素です。

しかし、GDB（GNU Debugger）、perf（Linux性能解析ツール）、VTune（Intelのプロファイリングツール）といった外部ツールは、Goランタイムの内部的なスタック管理やスタックバリアの存在を認識していません。これらのツールは、プログラムの実行中にスタックをウォーク（辿る）して、関数呼び出しの履歴やローカル変数の状態を解析することで、デバッグやプロファイリングを行います。Goのスタックバリアが存在すると、これらのツールがスタックの構造を誤解し、不正確なスタックトレースを生成したり、スタックウォークに失敗したりする可能性がありました。

このコミットの目的は、Goランタイムの動作に影響を与えることなく、GCのマーク終了後にスタックバリアを削除する「ベストエフォート」な処理を導入することです。これにより、GCがアクティブでない期間に外部ツールがスタックをウォークする際に、より正確な情報が得られるようになり、Goプログラムのデバッグやプロファイリングの利便性が向上します。ただし、GCのマークフェーズ中にスタックバリアがアクティブな間は、依然として外部ツールがスタックウォークに困難を抱える可能性があることも明記されています。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、低レイテンシと高スループットを目指して設計された、コンカレントな三色マーク＆スイープアルゴリズムを採用しています。主なフェーズは以下の通りです。

*   **マークフェーズ (Mark Phase)**: ライブオブジェクト（プログラムから到達可能なオブジェクト）を識別するフェーズです。GoのGCは、ほとんどのマーク処理をアプリケーションの実行と並行して行います（コンカレントマーク）。このフェーズでは、オブジェクトを「白」（まだ訪問されていない、回収候補）、「灰」（訪問されたが、参照先のオブジェクトがまだスキャンされていない）、「黒」（訪問され、参照先のオブジェクトもすべてスキャンされた、ライブオブジェクト）の三色で分類します。
*   **マーク終了フェーズ (Mark Termination Phase)**: コンカレントマークフェーズの最後に発生する、非常に短い「Stop-The-World (STW)」ポーズです。この短い期間に、GCはマーク処理を最終化し、オブジェクトグラフが安定していることを確認します。また、このフェーズでゴルーチンのスタックを再スキャンし、コンカレントマーク中に変更された可能性のあるポインタを捕捉します。
*   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（白オブジェクト）をガベージとして識別し、それらが占めていたメモリを解放してフリーリストに戻すフェーズです。このフェーズもアプリケーションと並行して実行されます（コンカレントスイープ）。

### スタックバリア (Stack Barriers)

GoのGCにおける「スタックバリア」は、GCがゴルーチンのスタックをスキャンする際に、スタック上のポインタの変更を検出し、GCの正確性を保証するためのメカニズムです。特に、Go 1.8で導入されたハイブリッドライトバリア（Hybrid Write Barrier）は、スタックの扱いを大きく改善しました。

*   **ライトバリア (Write Barrier)**: ポインタがヒープに書き込まれるたびに実行される小さなコード片です。GCがコンカレントに動作している間、アプリケーションがポインタを変更することでライブオブジェクトを見落とすことを防ぎます。
*   **スタックの特殊性**: スタックはヒープとは異なり、非常に頻繁にアクセスされ、ローカル変数や関数パラメータが急速に変化します。GoのGCは、このスタックの特性を考慮し、GCサイクルの開始時にスタック上のすべてのオブジェクトをコンカレントにスキャンして「黒」（到達可能）とマークします。これにより、後続のSTWスタック再スキャンが不要になり、GCポーズ時間が短縮されます。
*   **スタックバリアの役割**: スタックバリアは、GCがスタックをスキャンする際に、スタック上のポインタが変更された場合にGCに通知する役割を果たします。これにより、GCは常に正確なオブジェクトグラフを把握できます。しかし、これらのバリアは、外部ツールがスタックの構造を理解する上で障害となることがあります。

### 外部ツール (GDB, perf, VTune) とスタックウォーク

*   **GDB (GNU Debugger)**: プログラムの実行を制御し、メモリやレジスタの内容を検査し、スタックトレースを表示するなど、デバッグ機能を提供します。GDBは、プログラムのスタックフレームを辿ることで、関数呼び出しの履歴を再構築します。
*   **perf (Linux performance analysis tools)**: Linuxカーネルに組み込まれたプロファイリングツールで、CPU使用率、キャッシュミス、システムコールなどの性能イベントを収集・解析します。perfは、サンプリングによってスタックトレースを収集し、どの関数がCPU時間を消費しているかを特定します。
*   **VTune (Intel VTune Amplifier)**: Intelが提供する高性能なプロファイリングツールで、CPU、メモリ、スレッド、I/Oなどのパフォーマンスボトルネックを特定します。VTuneもまた、スタックサンプリングを通じてホットスポットを特定します。

これらのツールは、通常、標準的なコンパイラが生成するスタックフレーム情報（ベースポインタ、リターンアドレスなど）に基づいてスタックウォークを行います。Goランタイムが独自のスタック管理（可変サイズのスタック、スタックバリアなど）を行うため、これらのツールはGoプログラムのスタックを正確に解釈できない場合があります。特に、スタックバリアが存在すると、スタックの構造が非標準的になり、外部ツールがスタックフレームの境界を正しく識別できなくなることがあります。

### Goのゴルーチン状態 (`_Grunnable`, `_Gsyscall`, `_Gwaiting` など)

Goのゴルーチンは、Goランタイムによって管理される軽量な実行単位であり、様々な状態を取り得ます。

*   **_Grunnable**: ゴルーチンが実行可能であるが、現在OSスレッド上で実行されていない状態。スケジューラによって実行されるのを待っています。
*   **_Grunning**: ゴルーチンが現在OSスレッド上で実行されている状態。
*   **_Gsyscall**: ゴルーチンがシステムコールを実行している状態。この間、OSスレッドはブロックされる可能性がありますが、そのP（プロセッサ）は他のゴルーチンに利用されることがあります。
*   **_Gwaiting**: ゴルーチンが何らかの条件（I/O、ロックの取得、チャネルからの受信など）を満たすのを待ってブロックされている状態。
*   **_Gscan**: GCがスタックをスキャンしていることを示すフラグ。このコミットでは、スタックバリアを削除する際に、ゴルーチンがスキャン中であることを一時的にマークするために使用されます。

### `systemstack`

`systemstack` は、Goランタイムが通常のゴルーチンのスタックではなく、特別なシステムスタック上でコードを実行するために使用するメカニズムです。これは、GCのようなランタイムの低レベルな処理や、スタックの切り替えが必要な場合に利用されます。

## 技術的詳細

このコミットは、GCのマーク終了フェーズの直後に、すべてのゴルーチンからスタックバリアを削除する新しい関数 `gcTryRemoveAllStackBarriers` を導入します。この処理は「ベストエフォート」であり、ゴルーチンが特定の安全な状態にある場合にのみバリアを削除します。

1.  **`gcMarkTermination` 内での呼び出し**:
    `src/runtime/mgc.go` の `gcMarkTermination` 関数内で、スタックの解放処理 (`freeStackSpans`) の直後に `gcTryRemoveAllStackBarriers` が呼び出されます。これは、GCの主要な作業が完了し、アプリケーションの実行が再開される直前のタイミングです。
    ```go
    // Best-effort remove stack barriers so they don't get in the
    // way of things like GDB and perf.
    lock(&allglock)
    myallgs := allgs
    unlock(&allglock)
    gcTryRemoveAllStackBarriers(myallgs)
    ```
    `allglock` を取得して `allgs` (すべてのゴルーチンのリスト) をコピーし、ロックを解放してから `gcTryRemoveAllStackBarriers` を呼び出すことで、ロックの保持時間を最小限に抑え、他のランタイム処理への影響を軽減しています。

2.  **`gcTryRemoveAllStackBarriers` の実装 (`src/runtime/mstkbar.go`)**:
    この関数は、引数として渡されたゴルーチンのスライス `gps` をイテレートします。
    ```go
    func gcTryRemoveAllStackBarriers(gps []*g) {
    	for _, gp := range gps {
    	retry:
    		for {
    			switch s := readgstatus(gp); s {
    			default:
    				// If the goroutine is in a state where we can't safely
    				// remove barriers (e.g., _Grunning, _Gdead, _Gcopystack),
    				// we skip it. This is a best-effort pass.
    				break retry

    			case _Grunnable, _Gsyscall, _Gwaiting:
    				// These are safe states to try and remove barriers.
    				// We temporarily mark the goroutine as _Gscan to prevent
    				// it from changing state while we operate on its stack.
    				if !castogscanstatus(gp, s, s|_Gscan) {
    					// Status changed, retry.
    					continue
    				}
    				gcLockStackBarriers(gp)
    				gcRemoveStackBarriers(gp)
    				gcUnlockStackBarriers(gp)
    				restartg(gp) // Restore original status and make it runnable if it was.
    				break retry
    			}
    		}
    	}
    }
    ```
    *   **ベストエフォート**: 各ゴルーチンについて、スタックバリアを安全に削除できる状態 (`_Grunnable`, `_Gsyscall`, `_Gwaiting`) であるかを `readgstatus` で確認します。これらの状態は、ゴルーチンが現在CPU上で実行されていないか、システムコール中でブロックされているか、何らかのイベントを待っている状態であり、スタックの変更が比較的安全に行えると考えられます。
    *   **状態の変更防止**: `castogscanstatus(gp, s, s|_Gscan)` を使用して、ゴルーチンの状態を一時的に `_Gscan` フラグ付きの状態に遷移させます。これは、バリア削除処理中にゴルーチンの状態が予期せず変更されるのを防ぐためのアトミックな操作です。もし状態遷移に失敗した場合（つまり、その間にゴルーチンの状態が変化した場合）、処理をリトライします。
    *   **バリアの削除**: 状態を安全に固定できたら、以下の手順でスタックバリアを削除します。
        *   `gcLockStackBarriers(gp)`: スタックバリア関連のロックを取得します。
        *   `gcRemoveStackBarriers(gp)`: 実際のスタックバリア削除処理を実行します。これは、スタック上の特定のマーカーを削除する低レベルな操作です。
        *   `gcUnlockStackBarriers(gp)`: ロックを解放します。
    *   **ゴルーチンの再開**: `restartg(gp)` を呼び出して、ゴルーチンの状態を元の状態に戻し、必要であれば実行可能状態にします。これにより、バリア削除処理が完了したゴルーチンは、通常のスケジューリングに戻ることができます。
    *   **スキップ**: `_Grunning` (実行中) や `_Gdead` (終了済み) など、安全にバリアを削除できない状態のゴルーチンはスキップされます。これが「ベストエフォート」である理由です。

このメカニズムにより、GCのオーバーヘッドを最小限に抑えつつ、外部ツールがGoプログラムのスタックをより正確に解析できる機会を提供します。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更点

`gcMarkTermination` 関数は、GCのマークフェーズが終了し、STWポーズが解除される直前に実行される重要な関数です。この関数内で、`systemstack(freeStackSpans)` の呼び出し（スタック領域の解放）の直後に、新しく追加された `gcTryRemoveAllStackBarriers(myallgs)` が呼び出されています。

この配置は戦略的です。
1.  GCのマークフェーズが完全に終了し、ライブオブジェクトの識別が完了しているため、スタックバリアの存在はGoランタイムの正確性にとって一時的に重要ではなくなります。
2.  `freeStackSpans` の後に実行されることで、スタック関連の他のクリーンアップ処理と整合性が取れます。
3.  `allglock` を取得して `allgs` のスナップショット (`myallgs`) を作成し、すぐにロックを解放することで、`gcTryRemoveAllStackBarriers` の実行中に `allglock` が長時間保持されるのを防ぎ、ランタイムの並行性を維持しています。

この変更により、GCサイクルが完了し、アプリケーションが通常の実行に戻る前に、可能な限りスタックバリアが削除され、外部ツールがよりクリーンなスタック状態を観測できるようになります。

### `src/runtime/mstkbar.go` の `gcTryRemoveAllStackBarriers` 関数

この関数は、Goランタイムが管理するすべてのゴルーチン (`gps` スライス) をループ処理し、それぞれのゴルーチンに対してスタックバリアの削除を試みます。

*   **`for _, gp := range gps`**: すべてのゴルーチンを順に処理します。
*   **`retry:` と `for {}`**: 各ゴルーチンに対して、スタックバリア削除処理をアトミックに実行するためのループ構造です。ゴルーチンの状態が処理中に変化した場合、`continue` でこの内部ループを再試行します。
*   **`switch s := readgstatus(gp); s`**: ゴルーチン `gp` の現在の状態を `readgstatus` で読み取ります。この状態に基づいて、バリア削除を試みるかどうかを決定します。
    *   **`default: break retry`**: `_Grunnable`, `_Gsyscall`, `_Gwaiting` 以外の状態（例: `_Grunning`, `_Gdead`, `_Gcopystack` など）の場合、スタックバリアの削除は安全ではないか、または不要であると判断し、そのゴルーチンに対する処理をスキップして次のゴルーチンに移ります。これが「ベストエフォート」の側面です。
    *   **`case _Grunnable, _Gsyscall, _Gwaiting:`**: これらの状態のゴルーチンは、現在CPU上で実行されていないため、スタックバリアの削除を試みるのに適しています。
        *   **`if !castogscanstatus(gp, s, s|_Gscan) { continue }`**: ここが非常に重要です。`castogscanstatus` は、ゴルーチンの状態をアトミックに `s` から `s|_Gscan` へと変更しようとします。`_Gscan` フラグは、GCがこのゴルーチンのスタックをスキャン中であることを示唆するもので、ここではスタックバリア削除処理中であることをマークするために一時的に使用されます。この操作が成功した場合のみ、処理を続行します。もし、この間にゴルーチンの状態が `s` から別の状態に変化していた場合、`castogscanstatus` は `false` を返し、`continue` によって内部ループが再試行されます。これにより、競合状態を防ぎ、安全性を確保します。
        *   **`gcLockStackBarriers(gp)`**: スタックバリアに関連する内部ロックを取得します。これにより、他のランタイムルーチンが同時にスタックバリアを操作するのを防ぎます。
        *   **`gcRemoveStackBarriers(gp)`**: 実際にゴルーチン `gp` のスタックからスタックバリアを削除する低レベルな関数です。これは、スタックフレーム内に挿入された特定のマーカーやメタデータをクリアする操作を含みます。
        *   **`gcUnlockStackBarriers(gp)`**: スタックバリア関連のロックを解放します。
        *   **`restartg(gp)`**: ゴルーチン `gp` の状態を元の状態に戻し、必要であればスケジューラによって実行可能 (`_Grunnable`) にします。`_Gscan` フラグもここでクリアされます。
        *   **`break retry`**: このゴルーチンに対する処理が成功したため、次のゴルーチンに移ります。

この一連の処理は、Goランタイムの内部的な整合性を保ちつつ、外部ツールがGoプログラムのスタックをより正確に解釈できるようにするための、慎重かつ効率的なアプローチを示しています。

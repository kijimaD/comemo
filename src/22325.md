# [インデックス 22325] ファイルの概要

このコミットは、Go言語のツールチェインの一部である`cmd/internal/obj/x86/asm6.go`ファイルに対する変更です。このファイルは、x86アーキテクチャ向けのGoアセンブラのバックエンドを構成しており、アセンブリ命令のエンコーディング（機械語への変換）とアセンブルプロセスを司っています。具体的には、`CALL`命令の特定の形式、特に間接呼び出し`CALL *name(SB)`のサポートを追加しています。

## コミット

`cmd/internal/obj/x86`: `CALL *name(SB)`を追加

## 変更の背景

このコミットの背景は、元コミットメッセージに明確に記述されています。

1.  **機能の欠落**: `CALL *name(SB)`という形式の命令は、以前から`i386`（32ビットx86）向けのアセンブラには存在していました。
2.  **マージ時の見落とし**: しかし、`i386`のコードがより一般的な`x86`バックエンドにマージされる過程で、この特定の命令形式のサポートが誤って見落とされ、`x86`アセンブラから欠落していました。
3.  **`linux/386`での必要性**: この命令形式は、`linux/386`（32ビットx86 Linux）環境でGoプログラムを正しくコンパイル・リンクするために不可欠でした。このサポートがなければ、特定のGoプログラムやランタイム機能が`linux/386`上で動作しない可能性がありました。

このコミットは、この欠落を修正し、`linux/386`ターゲットのGoツールチェインの完全性を確保することを目的としています。

## 前提知識の解説

このコミットを深く理解するためには、以下の概念についての知識が必要です。

1.  **Goツールチェインのアーキテクチャ**: Go言語のコンパイルプロセスは、Goコンパイラによって生成されたアセンブリライクな命令（または`.s`ファイルに直接記述されたアセンブリコード）を機械語に変換するアセンブラ（`cmd/internal/obj`パッケージ）を含んでいます。
2.  **x86アーキテクチャ**: IntelおよびAMDプロセッサの命令セットアーキテクチャ（ISA）です。これには、`CALL`（関数呼び出し）のような様々な命令とアドレッシングモードが含まれます。
3.  **`CALL`命令**: x86アセンブリにおいて、`CALL`はサブルーチンに制御を転送するために使用されます。これは、リターンアドレスをスタックにプッシュし、ターゲットアドレスにジャンプします。
    *   `CALL immediate`: 固定アドレスの関数を呼び出します。
    *   `CALL register/memory`: レジスタまたはメモリ位置にあるアドレスの関数を呼び出します。
    *   `CALL *name(SB)`: これはGoのアセンブリ構文における特定の形式です。
4.  **Goアセンブリ構文 (`*name(SB)`)**:
    *   `SB` (Static Base): 静的データセグメントのベースを表す擬似レジスタです。シンボル（関数、グローバル変数）は通常、`SB`からの相対アドレスで参照されます。
    *   `*name(SB)`: これは通常、間接呼び出しを指します。`name(SB)`はシンボル（例えば関数やデータラベル）であり、その*値*（アドレス）がメモリからロードされ、そのアドレスに対して呼び出しが行われます。これは`name(SB)`への直接呼び出しとは異なります。メモリ位置を介した間接呼び出しです。
5.  **`i386`と`x86`**: `i386`は具体的に32ビットx86アーキテクチャを指します。一方、`x86`は32ビットと64ビット（x86-64またはAMD64）の両方のアーキテクチャを指すことがあります。このコミットは、`i386`固有のコードがより一般的な`x86`バックエンドに統合またはリファクタリングされた際に、この特定の命令のサポートが見落とされたことを示唆しています。
6.  **アセンブラの内部構造 (`ytab`, `Optab`, `Z*`, `Y*`)**: `asm6.go`ファイルは、アセンブリ命令がどのように解析され、検証され、機械語に変換されるかを定義するために、内部テーブルと定数（`ytab`、`Optab`、`Zcall`、`Yindir`など）を使用しています。
    *   `ytab`: オペランドの型と、それに対応する「z-ケース」（命令エンコーディングのバリアント）を定義します。
    *   `Optab`: アセンブリ命令（例: `obj.ACALL`）を、その可能なオペランドの組み合わせ（`ytab`）と、対応する機械語のバイトシーケンスにマッピングします。
    *   `Z*`: 異なる命令エンコーディングパターン、または「z-ケース」を表します。
    *   `Y*`: 異なるオペランドの型、または「y-ケース」を表します。
7.  **`obj`パッケージ**: `cmd/internal/obj`はGoツールチェインの中核パッケージであり、アセンブリ命令の中間表現を定義し、オブジェクトファイル生成のためのユーティリティを提供します。`obj.ACALL`は`CALL`命令を表す定数です。`obj.TYPE_INDIR`は間接アドレッシングの型です。`obj.R_ADDR`と`obj.R_PCREL`は再配置の型です。

## 技術的詳細

このコミットは、`src/cmd/internal/obj/x86/asm6.go`ファイルを変更します。このファイルには、x86アセンブラのコアロジックが含まれており、以下の変更が行われています。

1.  **オペランド型定義の追加**:
    *   `Yindir`が`const`ブロックに追加されました。これは、間接オペランド型を表すために使用されます。
2.  **Z-ケース定義の追加**:
    *   `Zcallcon`と`Zcallind`が追加されました。これらは`CALL`命令の新しいエンコーディングパターンを表します。
        *   `Zcallcon`: 定数（即値）オペランドを持つ`CALL`に対応します。
        *   `Zcallind`: 間接オペランド（例: `*name(SB)`）を持つ`CALL`に対応します。
3.  **`ycall`テーブルの変更**:
    *   `ycall`テーブルは、`CALL`命令の有効なオペランドの組み合わせを定義します。
    *   `{Ynone, Ynone, Yindir, Zcallind, 2}`という新しいエントリが追加されました。これは、`Yindir`として分類されたオペランドを持つ`CALL`命令に対して、`Zcallind`エンコーディングを使用することを指定します。これが`CALL *name(SB)`のサポートの鍵となります。
    *   `{Ynone, Ynone, Ybr, Zcall, 0}`のエントリが変更され、サイズが1から0に変更されました。これはおそらく直接分岐の`CALL`に対応します。
    *   `{Ynone, Ynone, Yi32, Zcallcon, 1}`という新しいエントリが追加され、32ビット即値オペランド（`Yi32`）を持つ`CALL`命令のサポートが追加されました。
4.  **`yjmp`テーブルの変更**:
    *   `JMP`命令の`yjmp`テーブルにも同様の変更が加えられ、`Zjmpcon`と`Yi32`のサポートが追加されました。これは、`JMP`が`CALL`と類似のオペランド処理を共有することが多いため、関連する修正です。
5.  **`optab`の変更**:
    *   `obj.ACALL`の`Optab`が更新されました。バイトシーケンス`[23]uint8{0xff, 02, 0xe8}`が`[23]uint8{0xff, 02, 0xff, 0x15, 0xe8}`に変更されました。この変更は、間接呼び出しのための新しい機械語プレフィックスを反映しています。
        *   `0xff, 0x15`: これは`CALL [disp32]`（32ビットメモリアドレスを介した間接呼び出し）のオペコードです。
        *   `0xe8`: これは`CALL rel32`（直接相対呼び出し）のオペコードです。
    *   この変更は、`Optab`が直接呼び出しと間接呼び出しの両方を処理する必要があることを示唆しており、`0xff, 0x15`プレフィックスは特に間接的な`CALL *name(SB)`ケースのためのものです。
6.  **`oclass`関数の変更**:
    *   `oclass`関数に新しい`case obj.TYPE_INDIR`が追加されました。この関数はオペランドの型を分類します。オペランドが`obj.TYPE_INDIR`であり、`*name(SB)`のパターン（名前があり、レジスタ、インデックス、スケールがない）に一致する場合、`Yindir`を返します。これにより、アセンブラは`*name(SB)`を間接オペランドとして正しく識別できます。
7.  **`doasm`関数の変更**:
    *   `doasm`関数に新しい`case Zcallcon, Zjmpcon`と`case Zcallind`ブロックが追加されました。この関数は、実際の機械語バイトを生成する役割を担っています。
        *   `Zcallcon, Zjmpcon`: 定数オペランドを持つ`CALL`および`JMP`を処理します。32ビット即値のための再配置（`obj.R_PCREL`）を追加します。
        *   `Zcallind`: 間接`CALL`命令を処理します。シンボル`p.To.Sym`のアドレスのための再配置（`obj.R_ADDR`）を追加し、アドレスのプレースホルダー（0）を書き込みます。このプレースホルダーはリンカによって後で埋められます。これは、`CALL *name(SB)`がリンク時に解決される必要があるアドレスを含むため、非常に重要です。

要するに、このコミットは、x86アセンブラが間接呼び出し（`CALL *name(SB)`）および即値オペランドを持つ直接呼び出しを正しく処理するために、新しいオペランド型と命令エンコーディングパターンを導入しています。これにより、アセンブラはこれらの命令形式に対して正しい機械語と再配置情報を生成できるようになり、以前はx86バックエンドで欠落していた機能が補完されます。

## コアとなるコードの変更箇所

*   `src/cmd/internal/obj/x86/asm6.go`:
    *   `Yindir`、`Zcallcon`、`Zcallind`定数の追加。
    *   `ycall`および`yjmp`テーブルの変更。間接呼び出しおよび定数呼び出し/ジャンプのための新しい`ytab`エントリの追加。
    *   `obj.ACALL`の`Optab`の変更。間接呼び出しのための`0xff, 0x15`プレフィックスの追加。
    *   `oclass`関数における`case obj.TYPE_INDIR`の追加。
    *   `doasm`関数における`case Zcallcon, Zjmpcon`および`case Zcallind`の追加。

## コアとなるコードの解説

変更の核心は、x86アセンブラが`CALL`および`JMP`命令の特定の形式、特にメモリ位置を介した間接呼び出し（`CALL *name(SB)`）を認識し、エンコードする能力を拡張することにあります。

1.  **オペランドとZ-ケースの定義**:
    *   `Yindir`: この新しい`ytab`型は「間接」オペランドを示します。これは`CALL *name(SB)`を他の`CALL`形式と区別するために不可欠です。
    *   `Zcallcon`、`Zcallind`: これらは新しい「z-ケース」（エンコーディングパターン）です。`Zcallind`は特に間接呼び出し`CALL *name(SB)`用であり、`Zcallcon`は定数オペランドを持つ`CALL`を処理します。

2.  **`ycall`テーブルの更新**:
    ```go
    var ycall = []ytab{
        {Ynone, Ynone, Yml, Zcallindreg, 0},
        {Yrx, Ynone, Yrx, Zcallindreg, 2},
        {Ynone, Ynone, Yindir, Zcallind, 2}, // 新規: CALL *name(SB) を処理
        {Ynone, Ynone, Ybr, Zcall, 0},       // 変更: サイズが変更
        {Ynone, Ynone, Yi32, Zcallcon, 1},   // 新規: CALL immediate を処理
    }
    ```
    `{Ynone, Ynone, Yindir, Zcallind, 2}`の行が最も重要です。これは、アセンブラが`Yindir`として分類されたオペランドを持つ`CALL`命令に遭遇した場合、`Zcallind`エンコーディングパターンを使用するように指示します。

3.  **`obj.ACALL`の`Optab`**:
    ```go
    Optab{obj.ACALL, ycall, Px, [23]uint8{0xff, 02, 0xff, 0x15, 0xe8}},
    ```
    この`Optab`エントリは、`CALL`命令の機械語バイトを定義します。シーケンス`0xff, 0x15`は、32ビットメモリアドレスを介した間接呼び出しのオペコードです。アセンブラは、間接呼び出しが行われていると判断した場合に、このプレフィックスを使用します。

4.  **`oclass`関数**:
    ```go
    case obj.TYPE_INDIR:
        if a.Name != obj.NAME_NONE && a.Reg == REG_NONE && a.Index == REG_NONE && a.Scale == 0 {
            return Yindir
        }
        return Yxxx
    ```
    この新しい`case`は、`name(SB)`のようなオペランド（内部的には特定のプロパティを持つ`obj.TYPE_INDIR`として表現される）が`Yindir`として正しく分類されることを保証します。この分類は、アセンブラが適切な`ytab`エントリと`Optab`を使用してエンコードを行うための指針となります。

5.  **`doasm`関数 (`Zcallind`ケース)**:
    ```go
    case Zcallind:
        ctxt.Andptr[0] = byte(op)
        ctxt.Andptr = ctxt.Andptr[1:]
        ctxt.Andptr[0] = byte(o.op[z+1])
        ctxt.Andptr = ctxt.Andptr[1:]
        r = obj.Addrel(ctxt.Cursym)
        r.Off = int32(p.Pc + int64(-cap(ctxt.Andptr)+cap(ctxt.And[:])))
        r.Type = obj.R_ADDR
        r.Siz = 4
        r.Add = p.To.Offset
        r.Sym = p.To.Sym
        put4(ctxt, 0)
    ```
    これは、`CALL *name(SB)`の実際の機械語生成が行われる場所です。
    *   オペコードバイト（`0xff, 0x15`）を書き込みます。
    *   次に、再配置エントリ（`obj.R_ADDR`）を追加します。これはリンカに対し、生成された機械語のこの位置に、解決される必要があるアドレス（`r.Sym = p.To.Sym`）があることを伝えます。`put4(ctxt, 0)`は、このアドレスのための4バイトのプレースホルダー（0）を書き込みます。リンカは後でこのプレースホルダーを`p.To.Sym`の実際のアドレスで埋めます。これは、アセンブラがリンク時に解決されるシンボリック参照を処理する方法です。

まとめると、これらの変更は、Goのx86アセンブラが`CALL *name(SB)`のような間接呼び出しを正しく解析、検証、および機械語に生成できるようにすることを保証します。これは、`linux/386`ターゲットにとって不可欠な機能です。これには、アセンブリ命令を機械語表現にマッピングする内部テーブルの更新と、間接アドレッシングの特定の再配置要件を処理するロジックの追加が含まれます。

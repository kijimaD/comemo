# [インデックス 21544] ファイルの概要

このコミットは、Goランタイムのメモリ管理における`tinyalloc`（小さなオブジェクトのアロケータ）と`persistentalloc`（永続的なデータ構造のアロケータ）の挙動を修正するものです。具体的には、アロケータが割り当てられたデータの終端を超えてポインタを指す可能性があった問題を解決し、これにより発生しうるクラッシュを防ぎます。

## 元コミット内容

```
runtime: change tinyalloc, persistentalloc not to point past allocated data

During all.bash I got a crash in the GOMAXPROCS=2 runtime test reporting
that the write barrier in the assignment 'c.tiny = add(x, size)' had been
given a pointer pointing into an unexpected span. The problem is that
the tiny allocation was at the end of a span and c.tiny was now pointing
to the end of the allocation and therefore to the end of the span aka
the beginning of the next span.

Rewrite tinyalloc not to do that.

More generally, it's not okay to call add(p, size) unless you know that p
points at > (not just >=) size bytes. Similarly, pretty much any call to
roundup doesn't know how much space p points at, so those are all
broken.

Rewrite persistentalloc not to use add(p, totalsize) and not to use roundup.

There is only one use of roundup left, in vprintf, which is dead code.
I will remove that code and roundup itself in a followup CL.

Change-Id: I211e307d1a656d29087b8fd40b2b71010722fb4a
Reviewed-on: https://go-review.googlesource.com/2814
Reviewed-by: Dmitry Vyukov <dvyukov@google.org>
```

## 変更の背景

このコミットの背景には、Goランタイムのテスト中に発生したクラッシュがあります。具体的には、`GOMAXPROCS=2` の設定でランタイムテストを実行した際に、`c.tiny = add(x, size)` という代入処理におけるライトバリアが、予期せぬスパン（メモリ領域の単位）を指すポインタを受け取ったと報告されました。

この問題の根本原因は、`tinyalloc` が非常に小さなオブジェクトを割り当てる際に、割り当てられたメモリブロックの終端、つまり現在のスパンの終端、ひいては次のスパンの開始地点を指すポインタを生成してしまう可能性があったことです。Goのガベージコレクタ（GC）は、オブジェクトのポインタが指すメモリ領域が有効なスパン内にあることを前提としています。しかし、ポインタが割り当てられたデータの終端を超えてしまうと、GCのライトバリアが不正なメモリ領域を検出し、クラッシュを引き起こす可能性がありました。

コミットメッセージでは、この問題が`add(p, size)`関数と`roundup`関数の一般的な使用方法にも関連していると指摘されています。これらの関数は、与えられたポインタ`p`が`size`バイト以上の有効なメモリ領域を指していることを常に保証できるわけではないため、同様の問題を引き起こす可能性がありました。

このクラッシュと潜在的な問題を解決するために、`tinyalloc`と`persistentalloc`のロジックが見直され、割り当てられたデータの範囲外を指すポインタが生成されないように変更されました。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理に関するいくつかの重要な概念を理解しておく必要があります。

### Goのメモリ管理とアロケータ

Goランタイムは独自のメモリ管理システムを持っています。これは、OSからメモリを確保し、それをGoプログラム内で効率的に割り当てるためのものです。主なアロケータには以下のようなものがあります。

*   **mcache (Memory Cache)**: 各論理プロセッサ（P）に紐付けられたローカルなメモリキャッシュです。小さなオブジェクトの割り当てを高速化するために使用されます。GCの停止時間を短縮するため、ほとんどの割り当てはmcacheから行われます。
*   **mspan (Memory Span)**: 連続したページ（通常は8KB）の集まりです。Goのヒープはmspanのリストとして管理されます。mspanは特定のサイズのオブジェクトを格納するために使用されます。
*   **tinyalloc**: 非常に小さなオブジェクト（通常は16バイト以下）を効率的に割り当てるための特殊なアロケータです。これらのオブジェクトはポインタを含まないことが多く、GCのオーバーヘッドを減らすために特別に扱われます。`mcache`内に`tiny`というフィールドで管理されます。
*   **persistentalloc**: ランタイム内部の永続的なデータ構造（例: 型情報、GCメタデータなど）を割り当てるために使用されるアロケータです。これらのデータはプログラムの実行中に解放されることがほとんどありません。

### ライトバリア (Write Barrier)

Goのガベージコレクタは、並行マーク＆スイープ方式を採用しています。この方式では、GCがオブジェクトグラフを走査している最中にも、アプリケーションのゴルーチンが実行され、ヒープ上のポインタを変更する可能性があります。

**ライトバリア**は、このような並行実行中にGCの正確性を保証するためのメカニズムです。具体的には、ヒープ上のポインタが変更される（書き込まれる）際に、GCがその変更を検知し、必要に応じてオブジェクトをマークするなどの処理を行います。これにより、GCがオブジェクトを見落とすことを防ぎ、メモリリークや不正なメモリ解放を防ぎます。

ライトバリアは、ポインタが指すメモリ領域が有効なスパン内にあることを前提としています。もしポインタがスパンの境界を越えてしまうと、ライトバリアは不正なメモリ領域を検知し、クラッシュを引き起こす可能性があります。

### `unsafe.Pointer`と`uintptr`

*   **`unsafe.Pointer`**: Goの型システムをバイパスして、任意の型のポインタを保持できる特殊なポインタ型です。C言語の`void*`に似ています。Goのメモリ管理システムは`unsafe.Pointer`が指すメモリの内容を追跡しません。
*   **`uintptr`**: ポインタを整数として表現する型です。ポインタ演算を行う際に使用されますが、`uintptr`自体はポインタではないため、GCの対象外です。`unsafe.Pointer`と`uintptr`の間で相互変換が可能です。

### `add(p, size)`関数

Goランタイム内部で使用される関数で、ポインタ`p`に`size`バイトを加算した新しいポインタを返します。これはポインタ演算を行うための低レベルな関数です。

### `roundup(p, align)`関数

ポインタ`p`を`align`の倍数に切り上げる（アラインメントする）関数です。メモリのアラインメントは、特定のデータ型が特定のメモリアドレスに配置されることを保証するために重要です。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのメモリ割り当てロジックにおけるポインタ演算の正確性に関する問題です。

### `tinyalloc`の問題点

以前の`tinyalloc`の実装では、`mcache`構造体の`c.tiny`フィールドが、現在割り当て可能な小さなブロックの開始ポインタを保持し、`c.tinysize`がそのブロックの残りのサイズを保持していました。新しい小さなオブジェクトが割り当てられると、`c.tiny = (*byte)(add(x, size))` のように、割り当てられたオブジェクトの終端の次のアドレスを`c.tiny`に設定していました。

問題は、この`add(x, size)`が、割り当てられたオブジェクト`x`がスパンの終端に位置する場合、`x`に`size`を加算した結果が現在のスパンの境界を越え、次のスパンの開始地点を指してしまう可能性があったことです。Goのメモリ管理では、各スパンは特定のオブジェクトサイズクラスに属し、GCはスパンのメタデータに基づいてオブジェクトを処理します。ポインタが予期せぬスパンを指すと、ライトバリアが混乱し、クラッシュを引き起こしました。

また、`roundup`関数も同様の問題を抱えていました。`roundup(tiny, align)`のように使用される場合、`tiny`ポインタが指すメモリ領域の実際のサイズを知らずにアラインメント処理を行うため、結果として有効なメモリ領域の範囲外を指すポインタを生成する可能性がありました。

### `persistentalloc`の問題点

`persistentalloc`も同様に、`persistent.pos`と`persistent.end`というフィールドを使用して、永続的なメモリブロックの現在の位置と終端を管理していました。ここでも`add(persistent.pos, size)`のような操作が、割り当てられたブロックの終端を超えてポインタを生成する可能性がありました。

### 解決策

このコミットでは、これらの問題を解決するために、ポインタ自体を直接操作するのではなく、**オフセット**を使用してメモリ領域内の位置を管理するアプローチが採用されました。

*   **`tinyalloc`の変更**:
    *   `mcache`構造体から`c.tiny`（ポインタ）と`c.tinysize`（残りサイズ）が削除され、代わりに`c.tinyoffset`（現在の割り当て位置のオフセット）が導入されました。
    *   `c.tiny`は、`mcache`が管理する現在の小さなブロックのベースアドレスを保持するようになりました。
    *   割り当ては、`x = add(c.tiny, off)` のように、ベースアドレスにオフセットを加算することで行われます。
    *   次の割り当て位置は、`c.tinyoffset = off + size` のように、オフセットを更新することで管理されます。これにより、ポインタが割り当てられたデータの終端を超えてしまうことがなくなります。
    *   `roundup`の代わりに、オフセットをアラインメントするための`round`関数が導入されました。

*   **`persistentalloc`の変更**:
    *   `persistent`構造体から`persistent.pos`と`persistent.end`が削除され、代わりに`persistent.base`（ベースアドレス）と`persistent.off`（オフセット）が導入されました。
    *   割り当ては、`p := add(persistent.base, persistent.off)` のように、ベースアドレスにオフセットを加算することで行われます。
    *   次の割り当て位置は、`persistent.off += size` のように、オフセットを更新することで管理されます。
    *   ここでも`roundup`の代わりに、オフセットをアラインメントするための`round`関数が使用されます。

この変更により、ポインタが常に有効なメモリ領域内を指すことが保証され、ライトバリアの誤動作やクラッシュが防止されます。また、コミットメッセージにあるように、`roundup`関数の使用はほぼなくなり、最終的には後続のコミットで削除される予定であることが示されています。

## コアとなるコードの解説

### `tinyalloc`の変更

以前の`tinyalloc`は、`mcache`の`c.tiny`フィールドに現在の小さなブロックの開始ポインタを、`c.tinysize`にその残りのサイズを保持していました。新しいオブジェクトが割り当てられると、`c.tiny`は割り当てられたオブジェクトの直後のアドレスに更新され、`c.tinysize`は減少しました。

このコミットでは、このアプローチが変更されました。
*   `mcache`構造体には、`tiny`（ベースポインタ）と`tinyoffset`（ベースポインタからのオフセット）が導入されました。
*   `mallocgc`関数内で小さなオブジェクトを割り当てる際、まず`c.tinyoffset`をアラインメントします（`round(off, align)`）。
*   次に、`c.tiny`（ベースポインタ）にアラインメントされたオフセット`off`を加算して、新しいオブジェクトの開始アドレス`x`を計算します: `x = add(c.tiny, off)`。
*   そして、`c.tinyoffset`を割り当てられたオブジェクトのサイズ分だけ進めます: `c.tinyoffset = off + size`。

この変更により、`c.tiny`は常に割り当てられた小さなブロックのベースアドレスを指し、`c.tinyoffset`がそのブロック内の現在の割り当て位置を正確に追跡します。これにより、ポインタが割り当てられたデータの終端を超えてしまうことがなくなり、ライトバリアの誤動作を防ぎます。

### `persistentalloc`の変更

`persistentalloc`も同様に、ポインタとサイズでメモリ領域を管理する代わりに、ベースポインタとオフセットで管理するように変更されました。
*   `persistent`構造体には、`base`（ベースポインタ）と`off`（オフセット）が導入されました。
*   メモリを割り当てる際、まず`persistent.off`をアラインメントします: `persistent.off = round(persistent.off, align)`。
*   次に、`persistent.base`にアラインメントされたオフセット`persistent.off`を加算して、新しいオブジェクトの開始アドレス`p`を計算します: `p := add(persistent.base, persistent.off)`。
*   そして、`persistent.off`を割り当てられたオブジェクトのサイズ分だけ進めます: `persistent.off += size`。
*   新しいチャンクを`sysAlloc`で取得する際も、`persistent.base`に新しいチャンクの開始アドレスを設定し、`persistent.off`を`0`にリセットします。

この変更により、`persistentalloc`も常に有効なメモリ領域内を指すポインタを生成するようになり、安全性が向上しました。また、`size == 0`の割り当てに対するチェックが追加され、不正な割り当てを防ぐ堅牢性が増しています。

全体として、このコミットはGoランタイムのメモリ管理におけるポインタ演算の安全性を高め、特に小さなオブジェクトと永続的なデータ構造の割り当てにおける潜在的なクラッシュを解消することを目的としています。

`cmd/compile: move Node.Vargen, Node.Iota into Node.Name`

このコミットは、Goコンパイラの`cmd/compile`パッケージにおいて、`Node`構造体の`Vargen`と`Iota`フィールドを`Node.Name`（`Name`構造体へのポインタ）内に移動させるものです。コミットメッセージには、変更前の`Node`構造体のサイズが192バイトであったことが示されており、この変更がメモリ使用量の最適化を目的としていることが伺えます。

## 変更の背景

Goコンパイラは、ソースコードを解析して抽象構文木（AST）を構築し、それから機械語コードを生成します。このASTの各要素は`Node`構造体で表現されます。コンパイラの処理において、`Node`構造体は非常に頻繁に生成され、メモリ上に多数存在します。そのため、`Node`構造体のサイズを小さくすることは、コンパイラのメモリ使用量を削減し、全体的なコンパイル速度を向上させる上で重要な最適化となります。

このコミットの背景には、`Node`構造体に含まれる`Vargen`と`Iota`というフィールドが、全ての`Node`インスタンスで必要とされるわけではない、という認識があったと考えられます。特に、これらのフィールドは主にシンボル（変数、定数など）に関連する`Node`でのみ意味を持つため、それらを`Node`が持つ`Name`構造体（シンボル情報を保持する）に移動させることで、`Node`構造体自体の共通部分をスリム化し、メモリ効率を高めることが意図されています。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Goコンパイラは、Go言語のソースコードを機械語に変換するプログラムです。`cmd/compile`はGoツールチェインの一部であり、以下の主要なフェーズで動作します。

1.  **字句解析 (Lexing):** ソースコードをトークン（最小単位の単語）に分割します。
2.  **構文解析 (Parsing):** トークン列を解析し、抽象構文木（AST）を構築します。
3.  **型チェック (Type Checking):** ASTの各ノードの型を検証し、型の一貫性を保証します。
4.  **中間表現 (IR) 生成:** ASTをより低レベルの中間表現に変換します。
5.  **最適化 (Optimization):** 中間表現に対して様々な最適化を適用し、生成されるコードの効率を高めます。
6.  **コード生成 (Code Generation):** 最適化された中間表現から最終的な機械語コードを生成します。

このコミットは、主に構文解析と型チェックのフェーズで利用されるASTの構造に関わる変更です。

### 抽象構文木 (Abstract Syntax Tree, AST) と `Node` 構造体

ASTは、プログラムのソースコードの抽象的な構文構造を木構造で表現したものです。Goコンパイラでは、このASTの各ノブ（節点）が`Node`構造体で表現されます。例えば、変数宣言、関数呼び出し、演算子、リテラルなどがそれぞれ`Node`として表現されます。`Node`構造体は、そのノードの種類（`Op`フィールド）、子ノードへのポインタ（`Left`, `Right`, `List`など）、型情報（`Type`フィールド）、シンボル情報（`Sym`フィールド）など、様々な情報を保持します。

### `Vargen` (Variable Generation)

`Vargen`は"Variable Generation"の略で、コンパイラ内部で変数を一意に識別するための番号、または特定のスコープ内での変数の生成順序を示すカウンターとして使用されます。特に、ローカル変数や関数パラメータなど、特定の関数スコープ内で定義される変数に対して、その生存期間やメモリ割り当てを管理する際に利用されることがあります。コンパイラが変数を処理する際に、同じ名前の変数が異なるスコープで存在する場合でも、`Vargen`によってそれらを区別し、正しく参照・管理できるようになります。

### `iota`

Go言語における`iota`は、定数宣言内で使用される特殊な識別子です。`const`ブロック内で使用されるたびに、その値は0から始まり、連続する定数宣言ごとに1ずつ増加します。これにより、連番の定数を簡潔に定義することができます。コンパイラは`iota`の値を適切に解決し、最終的な定数に置き換える必要があります。`Node.Iota`は、この`iota`の現在の値をASTノードに一時的に保持するために使用されていたと考えられます。

### `Name` 構造体

Goコンパイラにおける`Name`構造体は、主にシンボル（変数、関数、型など）に関する追加情報を保持するために使用されます。`Node`構造体自体はASTの一般的なノードを表しますが、特定のノード（例えば、識別子を表すノード）は、その識別子の名前、スコープ、定義元などの詳細なシンボル情報を必要とします。`Node`構造体は`Name`構造体へのポインタ（`Node.Name`）を持つことで、必要な場合にのみシンボル関連の詳細情報にアクセスできるように設計されています。

### 構造体のメモリレイアウトと最適化

Goの構造体は、フィールドの宣言順序によってメモリ上の配置が決定されます。フィールドのサイズやアライメント要件により、パディング（未使用のメモリ領域）が挿入されることがあります。構造体のサイズを削減することは、以下の点で重要です。

*   **メモリ使用量の削減:** 特にASTのように多数のインスタンスが生成される構造体の場合、1つのインスタンスのサイズが小さくなることで、全体のメモリ使用量が大幅に削減されます。
*   **キャッシュ効率の向上:** 構造体が小さくなると、CPUのキャッシュラインにより多くのインスタンスが収まるようになり、メモリへのアクセスが高速化されます。
*   **パフォーマンス向上:** メモリ使用量の削減とキャッシュ効率の向上は、コンパイル時間の短縮に直結します。

このコミットでは、`Node`構造体から`Vargen`と`Iota`を削除し、それらを`Name`構造体に移すことで、`Node`構造体のサイズを小さくしています。`Name`構造体は、全ての`Node`が持つわけではなく、シンボルに関連する`Node`のみが`Name`構造体へのポインタを持つため、この変更はメモリ効率の向上に繋がります。

## 技術的詳細

この変更の核心は、`Node`構造体と`Name`構造体の役割分担の明確化と、それによるメモリ最適化です。

変更前:
`Node`構造体は、ASTノードの一般的な情報に加えて、`Vargen`と`Iota`というシンボル固有の情報を直接保持していました。

```go
type Node struct {
    // ... 汎用的なASTノード情報 ...
    Vargen  int32 // unique name for OTYPE/ONAME within a function. Function outputs are numbered starting at one.
    Lineno  int32
    Iota    int32 // value if this name is iota
    // ...
    Name    *Name // シンボル情報へのポインタ (存在する場合)
}
```

変更後:
`Vargen`と`Iota`は`Node`構造体から削除され、`Name`構造体へと移動しました。`Node`構造体は、シンボル固有の情報を直接持つ代わりに、`Name`構造体へのポインタを通じてそれらの情報にアクセスするようになります。

```go
type Node struct {
    // ... 汎用的なASTノード情報 ...
    Lineno  int32
    // ...
    Name    *Name // シンボル情報へのポインタ (存在する場合)
}

type Name struct {
    // ... シンボルに関する他の情報 ...
    Vargen    int32 // unique name for OTYPE/ONAME within a function. Function outputs are numbered starting at one.
    Iota      int32 // value if this name is iota
    // ...
}
```

この変更により、`Node`構造体のサイズが削減されます。コミットメッセージにある`sizeof -p cmd/compile/internal/gc Node`の出力が192バイトであったことから、この変更によって`Node`構造体のサイズが小さくなったことが示唆されます。`Vargen`と`Iota`はそれぞれ`int32`型であり、合計で8バイトを占めます。ポインタのサイズ（通常8バイト）を考慮すると、`Node`構造体からこれらのフィールドを削除し、`Name`構造体内に移動させることで、`Node`構造体自体のサイズを削減できる可能性があります。特に、`Name`構造体を持たない`Node`インスタンス（例えば、演算子やリテラルなど）では、この変更によるメモリ削減効果が直接現れます。`Name`構造体を持つ`Node`インスタンスでは、`Name`構造体自体のサイズが増加しますが、`Name`構造体は`Node`構造体よりも生成頻度が低いか、あるいは既に多くのフィールドを持っているため、全体としてのメモリ効率は向上すると考えられます。

この変更の最も重要な部分は、`src/cmd/compile/internal/gc/syntax.go`における`Node`と`Name`構造体の定義変更です。

**変更前 (`syntax.go`の一部):**
```go
type Node struct {
    Xoffset int64

    Vargen  int32 // unique name for OTYPE/ONAME within a function.  Function outputs are numbered starting at one.
    Lineno  int32
    Iota    int32

    // ... 他のフィールド ...
}
```

**変更後 (`syntax.go`の一部):**
```go
type Node struct {
    Xoffset int64

    Lineno  int32 // VargenとIotaが削除された

    // ... 他のフィールド ...
}

type Name struct {
    // ... 既存のNameフィールド ...
    Vargen    int32 // unique name for OTYPE/ONAME within a function.  Function outputs are numbered starting at one.
    Iota      int32 // value if this name is iota
}
```

この変更により、`Node`構造体から`Vargen`と`Iota`が直接削除され、`Name`構造体へと移されました。これにより、`Node`構造体のインスタンスがメモリ上で占めるサイズが小さくなります。

他のファイルでの変更は、この構造体定義の変更に伴う参照先の修正です。例えば、`dcl.go`では変数の`Vargen`を設定する際に、`n.Vargen = int32(gen)`から`n.Name.Vargen = int32(gen)`へと変更されています。これは、`Vargen`が`Node`の直接のフィールドではなく、`Node`が持つ`Name`構造体のフィールドになったためです。同様に、`Iota`の参照も`n.Iota`から`n.Name.Iota`へと変更されています。

`fmt.go`や`typecheck.go`などでの`n.Name != nil`のチェックの追加は、`Name`構造体へのポインタがnilである可能性があるため、nilポインタ参照によるパニックを防ぐための防御的なプログラミングです。全ての`Node`が`Name`構造体を持つわけではないため、このチェックは必須となります。

この一連の変更は、Goコンパイラの内部におけるメモリ効率を向上させるための、細かではあるが重要な最適化の一例と言えます。

Goコンパイラにおける`Name`構造体は、主にシンボル（変数、関数、型など）に関する追加情報を保持するために使用されます。`Node`構造体自体はASTの一般的なノードを表しますが、特定のノード（例えば、識別子を表すノード）は、その識別子の名前、スコープ、定義元などの詳細なシンボル情報を必要とします。`Node`構造体は`Name`構造体へのポインタ（`Node.Name`）を持つことで、必要な場合にのみシンボル関連の詳細情報にアクセスできるように設計されています。

### 構造体のメモリレイアウトと最適化

Goの構造体は、フィールドの宣言順序によってメモリ上の配置が決定されます。フィールドのサイズやアライメント要件により、パディング（未使用のメモリ領域）が挿入されることがあります。構造体のサイズを削減することは、以下の点で重要です。

*   **メモリ使用量の削減:** 特にASTのように多数のインスタンスが生成される構造体の場合、1つのインスタンスのサイズが小さくなることで、全体のメモリ使用量が大幅に削減されます。
*   **キャッシュ効率の向上:** 構造体が小さくなると、CPUのキャッシュラインにより多くのインスタンスが収まるようになり、メモリへのアクセスが高速化されます。
*   **パフォーマンス向上:** メモリ使用量の削減とキャッシュ効率の向上は、コンパイル時間の短縮に直結します。

このコミットでは、`Node`構造体から`Vargen`と`Iota`を削除し、それらを`Name`構造体に移すことで、`Node`構造体のサイズを小さくしています。`Name`構造体は、全ての`Node`が持つわけではなく、シンボルに関連する`Node`のみが`Name`構造体へのポインタを持つため、この変更はメモリ効率の向上に繋がります。

## 技術的詳細

この変更の核心は、`Node`構造体と`Name`構造体の役割分担の明確化と、それによるメモリ最適化です。

変更前:
`Node`構造体は、ASTノードの一般的な情報に加えて、`Vargen`と`Iota`というシンボル固有の情報を直接保持していました。

```go
type Node struct {
    // ... 汎用的なASTノード情報 ...
    Vargen  int32 // unique name for OTYPE/ONAME within a function. Function outputs are numbered starting at one.
    Lineno  int32
    Iota    int32 // value if this name is iota
    // ...
    Name    *Name // シンボル情報へのポインタ (存在する場合)
}
```

変更後:
`Vargen`と`Iota`は`Node`構造体から削除され、`Name`構造体へと移動しました。`Node`構造体は、シンボル固有の情報を直接持つ代わりに、`Name`構造体へのポインタを通じてそれらの情報にアクセスするようになります。

```go
type Node struct {
    // ... 汎用的なASTノード情報 ...
    Lineno  int32
    // ...
    Name    *Name // シンボル情報へのポインタ (存在する場合)
}

type Name struct {
    // ... シンボルに関する他の情報 ...
    Vargen    int32 // unique name for OTYPE/ONAME within a function. Function outputs are numbered starting at one.
    Iota      int32 // value if this name is iota
    // ...
}
```

この変更により、`Node`構造体のサイズが削減されます。コミットメッセージにある`sizeof -p cmd/compile/internal/gc Node`の出力が192バイトであったことから、この変更によって`Node`構造体のサイズが小さくなったことが示唆されます。`Vargen`と`Iota`はそれぞれ`int32`型であり、合計で8バイトを占めます。ポインタのサイズ（通常8バイト）を考慮すると、`Node`構造体からこれらのフィールドを削除し、`Name`構造体内に移動させることで、`Node`構造体自体のサイズを削減できる可能性があります。特に、`Name`構造体を持たない`Node`インスタンス（例えば、演算子やリテラルなど）では、この変更によるメモリ削減効果が直接現れます。`Name`構造体を持つ`Node`インスタンスでは、`Name`構造体自体のサイズが増加しますが、`Name`構造体は`Node`構造体よりも生成頻度が低いか、あるいは既に多くのフィールドを持っているため、全体としてのメモリ効率は向上すると考えられます。

## コアとなるコードの変更箇所

このコミットでは、`Node.Vargen`と`Node.Iota`への直接アクセスを、`Node.Name.Vargen`と`Node.Name.Iota`へのアクセスに置き換える変更が、複数のファイルにわたって行われています。

### `src/cmd/compile/internal/gc/dcl.go`
- 変数宣言 (`declare`関数) や関数引数 (`funcargs`関数) の処理において、`n.Vargen`への代入が`n.Name.Vargen`へと変更されています。
- `oldname`関数内で、新しい`Node`が作成される際に`n.Iota`への代入が`n.Name.Iota`へと変更されています。

### `src/cmd/compile/internal/gc/esc.go`
- エスケープ解析 (`escwalk`関数) において、`dst.Vargen`の参照が`dst.Name.Vargen`へと変更されています。

### `src/cmd/compile/internal/gc/fmt.go`
- デバッグ出力やフォーマット処理 (`Jconv`, `exprfmt`, `nodedump`関数) において、`n.Vargen`の参照が`n.Name.Vargen`へと変更されています。また、`n.Name != nil`のチェックが追加され、`Name`構造体が存在しない場合のnilポインタ参照を防いでいます。

### `src/cmd/compile/internal/gc/subr.go`
- ASTノードのコピー処理 (`treecopy`関数) において、`m.Iota`への代入が`m.Name.Iota`へと変更され、`m.Name`が新しく割り当てられ、元の`n.Name`の内容がコピーされるようになっています。
- フレーム情報の出力 (`frame`関数) において、`n.Vargen`の参照が`n.Name.Vargen`へと変更されています。

### `src/cmd/compile/internal/gc/syntax.go`
- `Node`構造体から`Vargen`と`Iota`フィールドが削除されています。
- `Name`構造体に`Vargen`と`Iota`フィールドが追加されています。

### `src/cmd/compile/internal/gc/typecheck.go`
- 型チェック処理 (`resolve`関数) において、`n.Iota`の参照が`n.Name.Iota`へと変更されています。
- `copytype`関数において、`n.Vargen`の代入が`n.Name.Vargen`へと変更され、`n.Name != nil`のチェックが追加されています。

## コアとなるコードの解説

この変更の最も重要な部分は、`src/cmd/compile/internal/gc/syntax.go`における`Node`と`Name`構造体の定義変更です。

**変更前 (`syntax.go`の一部):**
```go
type Node struct {
    Xoffset int64

    Vargen  int32 // unique name for OTYPE/ONAME within a function.  Function outputs are numbered starting at one.
    Lineno  int32
    Iota    int32

    // ... 他のフィールド ...
}
```

**変更後 (`syntax.go`の一部):**
```go
type Node struct {
    Xoffset int64

    Lineno  int32 // VargenとIotaが削除された

    // ... 他のフィールド ...
}

type Name struct {
    // ... 既存のNameフィールド ...
    Vargen    int32 // unique name for OTYPE/ONAME within a function.  Function outputs are numbered starting at one.
    Iota      int32 // value if this name is iota
}
```

この変更により、`Node`構造体から`Vargen`と`Iota`が直接削除され、`Name`構造体へと移されました。これにより、`Node`構造体のインスタンスがメモリ上で占めるサイズが小さくなります。

他のファイルでの変更は、この構造体定義の変更に伴う参照先の修正です。例えば、`dcl.go`では変数の`Vargen`を設定する際に、`n.Vargen = int32(gen)`から`n.Name.Vargen = int32(gen)`へと変更されています。これは、`Vargen`が`Node`の直接のフィールドではなく、`Node`が持つ`Name`構造体のフィールドになったためです。同様に、`Iota`の参照も`n.Iota`から`n.Name.Iota`へと変更されています。

`fmt.go`や`typecheck.go`などでの`n.Name != nil`のチェックの追加は、`Name`構造体へのポインタがnilである可能性があるため、nilポインタ参照によるパニックを防ぐための防御的なプログラミングです。全ての`Node`が`Name`構造体を持つわけではないため、このチェックは必須となります。

この一連の変更は、Goコンパイラの内部におけるメモリ効率を向上させるための、細かではあるが重要な最適化の一例と言えます。

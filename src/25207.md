# [インデックス 25207] ファイルの概要

このコミットは、Goランタイムのハッシュ関数である`aeshash`の耐DoS攻撃性を向上させるための変更です。具体的には、ハッシュ衝突を意図的に引き起こすことを困難にし、悪意のある入力によってサービス拒否攻撃（DoS攻撃）が発生するリスクを低減することを目的としています。

    runtime: make aeshash more DOS-proof

    Improve the aeshash implementation to make it harder to engineer collisions.

    1) Scramble the seed before xoring with the input string. This
       makes it harder to cancel known portions of the seed (like the size)
       because it mixes the per-table seed into those other parts.

    2) Use table-dependent seeds for all stripes when hashing >16 byte strings.

    For small strings this change uses 4 aesenc ops instead of 3, so it
    is somewhat slower. The first two can run in parallel, though, so

## 元コミット内容

Goランタイムの`aeshash`実装を改善し、ハッシュ衝突の意図的な生成をより困難にする。

1.  入力文字列とXORする前にシードをスクランブルする。これにより、既知のシードの一部（サイズなど）を打ち消すことが難しくなる。これは、テーブルごとのシードを他の部分と混ぜ合わせるためである。
2.  16バイトを超える文字列をハッシュ化する場合、すべてのストライプに対してテーブル依存のシードを使用する。

この変更により、短い文字列のハッシュ化では`aesenc`命令が3回から4回に増えるため、多少遅くなる。ただし、最初の2つの命令は並行して実行できるため、33%の速度低下にはならない。

ベンチマーク結果は、ほとんどのハッシュ操作でわずかな性能低下（約2%から9%）を示している。

## 変更の背景

ハッシュ関数は、データを効率的に検索・格納するために広く利用されています。Go言語の`map`型も内部的にハッシュ関数を使用しています。しかし、ハッシュ関数には「ハッシュ衝突」という問題がつきまといます。これは、異なる入力データが同じハッシュ値になる現象です。

悪意のある攻撃者は、意図的に多数のハッシュ衝突を引き起こすような入力データを作成し、それをプログラムに与えることで、ハッシュテーブルの性能を著しく低下させることができます。ハッシュテーブルの性能が低下すると、データの検索や挿入に時間がかかり、結果としてサービス拒否（DoS）攻撃につながる可能性があります。

このコミットの背景には、このようなDoS攻撃のリスクを軽減し、Goプログラムの堅牢性を高めるという目的があります。特に、`aeshash`はAES-NI命令セットを利用した高速なハッシュ関数であり、そのセキュリティ特性を強化することは重要でした。シードのスクランブルやテーブル依存のシードの導入は、攻撃者がハッシュ関数の内部状態を予測し、衝突を生成するのをより困難にするための対策です。

## 前提知識の解説

*   **ハッシュ関数とハッシュ衝突**: ハッシュ関数は、任意の長さの入力データ（キー）を受け取り、固定長の出力（ハッシュ値）を生成する関数です。理想的なハッシュ関数は、異なる入力に対して異なるハッシュ値を生成しますが、実際には異なる入力が同じハッシュ値になる「ハッシュ衝突」が発生する可能性があります。
*   **サービス拒否（DoS）攻撃**: 悪意のあるユーザーが、ハッシュ衝突を多数引き起こすようなデータを大量に送信することで、サーバーのCPU使用率を急増させ、正当なユーザーからのリクエストを処理できなくさせる攻撃手法です。
*   **`aeshash`**: Goランタイムが内部的に使用するハッシュ関数の一つで、特に文字列やバイト列のハッシュ計算に用いられます。IntelのAES-NI命令セット（Advanced Encryption Standard New Instructions）を利用することで、非常に高速なハッシュ計算を実現しています。AES-NIは、AES暗号化・復号化処理をハードウェアレベルで高速化するためのCPU命令セットですが、その特性をハッシュ関数に応用することで、高速かつ衝突耐性の高いハッシュを生成できます。
*   **ハッシュシード**: ハッシュ関数の初期値として使われるランダムな値です。シードが異なれば、同じ入力データでも異なるハッシュ値が生成されます。これにより、攻撃者が事前にハッシュ衝突を計算しておくことを防ぎます。Goの`map`は起動時にランダムなシードを生成し、各`map`インスタンスはこのシードを使用してハッシュ値を計算します。
*   **アセンブリ言語 (`.s`ファイル)**: Goランタイムの性能が重要な部分（特にCPUの特殊な命令セットを利用する場合）では、C言語やGo言語ではなく、直接アセンブリ言語で実装されることがあります。これにより、CPUの機能を最大限に引き出し、最高のパフォーマンスを実現します。このコミットでは、`asm_386.s`（32ビットx86アーキテクチャ用）と`asm_amd64.s`（64ビットx86アーキテクチャ用）が変更されています。
*   **SSE/AVX命令**: IntelやAMDのCPUが提供するSIMD（Single Instruction, Multiple Data）命令セットの一部です。複数のデータを一度に処理することで、計算を高速化します。`AESENC`もこれらの命令セットの一部です。
    *   `MOVL`, `MOVQ`: データをレジスタやメモリ間で移動させる命令。`L`は32ビット、`Q`は64ビットを意味します。
    *   `MOVO`, `MOVOU`: SSE/AVXレジスタ（XMMレジスタなど）にデータを移動させる命令。`MOVOU`はアラインメントされていないメモリからのロード/ストアに使用されます。
    *   `PINSRD`, `PINSRQ`, `PINSRW`: 汎用レジスタのデータをSSE/AVXレジスタの特定の位置に挿入する命令。`D`はDWORD（32ビット）、`Q`はQWORD（64ビット）、`W`はWORD（16ビット）を意味します。
    *   `PSHUFHW`: SSE/AVXレジスタ内のワード（16ビット）をシャッフルする命令。
    *   `PXOR`: SSE/AVXレジスタ間でビット単位のXOR演算を行う命令。
    *   `AESENC`: AES暗号化のラウンド関数を実行するAES-NI命令。ハッシュ関数では、この命令を繰り返し適用することで、入力データを複雑に混ぜ合わせ、衝突耐性を高めます。

## 技術的詳細

このコミットの主要な技術的変更点は以下の2つです。

1.  **シードのスクランブル強化**:
    従来の`aeshash`では、ハッシュ計算の初期段階で、テーブルごとのシード（`h+4(FP)`や`h+8(FP)`で渡される値）と入力文字列の長さ（`CX`）を組み合わせていました。このコミットでは、この組み合わせたシードをさらに`AESENC`命令でスクランブル（複雑に混ぜ合わせる）するステップが追加されました。
    具体的には、`runtime·aeskeysched(SB)`というプロセスごとの固定シードとXORし、その結果を`AESENC`で処理しています。これにより、攻撃者がシードの一部（特に長さ情報）を予測し、それを打ち消すような入力を作成することが極めて困難になります。シードがより予測不能になることで、ハッシュ衝突の意図的な生成が難しくなります。

2.  **テーブル依存シードの利用範囲拡大**:
    16バイトを超える文字列をハッシュ化する場合、`aeshash`は複数の「ストライプ」（部分）に分けて処理を行います。このコミット以前は、これらのストライプに対して、必ずしも異なるテーブル依存のシードが十分に活用されていなかった可能性があります。
    変更後では、`aes17to32`, `aes33to64`, `aes65plus`, `aes65to128`, `aes129plus`といった、より長い文字列を処理するアセンブリルーチンにおいて、複数の異なる`runtime·aeskeysched`オフセット（`+16(SB)`, `+32(SB)`, `+48(SB)`など）から取得した値と、初期シードをXORし、さらに`AESENC`でスクランブルすることで、複数の「テーブル依存シード」を生成しています。これらのスクランブルされたシードが、各ストライプのハッシュ計算に独立して適用されるようになりました。これにより、ハッシュ計算全体がより複雑になり、特定のパターンを持つ入力に対する衝突耐性が向上します。

これらの変更は、主に`src/runtime/asm_386.s`と`src/runtime/asm_amd64.s`のアセンブリコードに集中しています。Goの`alg.go`では、`hashkey`配列の初期化時に、`hashkey[1]`, `hashkey[2]`, `hashkey[3]`も奇数になるように設定する変更が加えられています。これは、これらの値がハッシュ計算のシードとして使用される際に、特定のビットパターンを避けるための一般的なプラクティスと考えられます。また、`hash32.go`と`hash64.go`では、デフォルトのハッシュアルゴリズム（AES-NIが利用できない場合など）において、`hashkey`の各要素に`seed`を乗算する形で、より多くのシード情報をハッシュ計算に組み込む変更が行われています。

性能面では、短い文字列のハッシュ化で`AESENC`命令が1回増えるため、わずかな速度低下が見られますが、並列実行可能な命令があるため、影響は最小限に抑えられています。

## コアとなるコードの解説

### `src/runtime/alg.go`の変更

`alg.go`の`init()`関数では、Goランタイムが起動する際にハッシュキーを初期化しています。`hashkey`は、ハッシュ関数で使用されるランダムなシード値の配列です。このコミットでは、`hashkey[0]`だけでなく、`hashkey[1]`, `hashkey[2]`, `hashkey[3]`も奇数になるようにビットOR演算子`|= 1`で設定しています。ハッシュ関数において、シード値が奇数であることは、特定のハッシュアルゴリズムの特性上、より良い分布や衝突耐性をもたらすことがあります。これは、特に乗算ベースのハッシュ関数で、偶数シードが特定の入力パターンに対して予測可能な結果を生む可能性を減らすためです。

### `src/runtime/asm_386.s`および`src/runtime/asm_amd64.s`の変更

これらのアセンブリファイルは、それぞれ32ビットおよび64ビットアーキテクチャ向けの`aeshash`関数の実装を含んでいます。変更の核心は`runtime·aeshashbody`関数にあります。

**変更前**:
シード（`h+4(FP)`または`h+8(FP)`）と入力文字列の長さ（`CX`）をXMMレジスタ（`X6`）にロードし、`PSHUFHW`で長さを複製した後、`AESENC`命令で入力データと混ぜ合わせていました。`runtime·aeskeysched(SB)`は別のXMMレジスタ（`X7`）にロードされ、ハッシュ計算の途中で使用されていました。

**変更後**:
1.  **初期シードの強化**:
    *   テーブルごとのシード（`h+4(FP)`/`h+8(FP)`）を`X0`レジスタにロードします。
    *   入力文字列の長さ（`CX`）を`PINSRW`命令で`X0`レジスタの特定の位置に挿入します。
    *   `PSHUFHW`命令で長さを`X0`レジスタ内で複製し、シードと長さを組み合わせた初期状態を作成します。
    *   この`X0`の内容を`X1`にコピーして保存します（`MOVO X0, X1`）。これは、後でテーブル依存シードを生成する際のベースとなります。
    *   **重要な変更点**: `PXOR runtime·aeskeysched(SB), X0`で、プロセスごとの固定シードとXORします。
    *   **重要な変更点**: `AESENC X0, X0`で、XORした結果をさらに`AESENC`命令でスクランブルします。これにより、初期シードがより複雑になり、攻撃者がシードのパターンを予測して衝突を生成することが非常に困難になります。

2.  **長い文字列に対するテーブル依存シードの導入**:
    `aes17to32`, `aes33to64`, `aes65plus`, `aes65to128`, `aes129plus`といった、より長い文字列を処理するセクションでは、複数のXMMレジスタ（`X1`, `X2`, `X3`など）を初期シード`X1`（スクランブル前のシード）から派生させています。
    *   `MOVO X1, X2`などで`X1`の内容を他のレジスタにコピーします。
    *   これらのコピーされたレジスタに対して、`PXOR runtime·aeskeysched+オフセット(SB), Xn`のように、`runtime·aeskeysched`の異なるオフセットから取得した値とXORします。これにより、各レジスタが異なるテーブル依存のシードを持つことになります。
    *   さらに、`AESENC Xn, Xn`でこれらの派生シードを個別にスクランブルします。
    *   これらのスクランブルされた複数のシード（`X0`から`X7`など）が、入力データの異なる部分（ストライプ）のハッシュ計算にそれぞれ適用されます。これにより、ハッシュ計算の各段階で異なる、かつ予測困難なシードが使用されるため、全体としての衝突耐性が大幅に向上します。

### `src/runtime/hash32.go`および`src/runtime/hash64.go`の変更

これらのファイルは、AES-NI命令が利用できない環境や、特定の短い文字列のハッシュ計算に使用されるGo言語で書かれたハッシュ関数を含んでいます。
変更点としては、`default`ケース（おそらくAES-NIが利用できない場合のフォールバック）において、`v2`, `v3`, `v4`といった内部状態の初期化に、単に`hashkey`の要素を使用するのではなく、`seed * hashkey[N]`のように、現在のハッシュ計算の`seed`を乗算して使用するように変更されています。これにより、AES-NIを使用しないハッシュ関数においても、より多くのシード情報がハッシュ計算に組み込まれ、衝突耐性が向上します。

これらの変更は、Goのハッシュ関数が、攻撃者によるDoS攻撃に対してより堅牢になるように設計されており、特にAES-NI命令セットを活用した高速なハッシュ処理のセキュリティを強化しています。

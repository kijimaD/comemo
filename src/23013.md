# [インデックス 23013] ファイルの概要

このコミットは、Goランタイムのデッドロック検出ロジックに関する修正です。具体的には、`buildmode=c-archive` または `buildmode=c-shared` でビルドされたGoプログラムにおいて、ランタイムが誤ってデッドロックを報告するのを防ぐための変更が加えられています。これらのビルドモードでは、GoプログラムがC言語のライブラリとして他のプログラムに組み込まれるため、Goランタイムが管理するゴルーチンがすべて停止していても、呼び出し元のCプログラムが動作している限り、システム全体としてはデッドロックではないという状況が発生します。このコミットは、その特殊なケースを考慮し、不必要なデッドロックエラーを抑制します。

## 変更の背景

Goランタイムは、実行中のゴルーチンが一つも存在しない状態を検出し、それをデッドロックと判断してプログラムを終了させるメカニズムを持っています。これは、通常のGoアプリケーションにおいては、すべてのゴルーチンがブロックされ、これ以上処理が進まない状態を意味するため、適切な挙動です。

しかし、Goには`buildmode`という機能があり、GoのコードをC言語から呼び出し可能なライブラリとしてビルドすることができます。特に`buildmode=c-archive`（静的ライブラリ）や`buildmode=c-shared`（共有ライブラリ）を使用した場合、GoのコードはCプログラムの一部として実行されます。このシナリオでは、Goランタイム内のすべてのゴルーチンが一時的にアイドル状態になることがありえます。例えば、CプログラムがGoの関数を呼び出し、そのGo関数が処理を終えてCプログラムに制御を戻した後、Goランタイム内には実行すべきゴルーチンが一時的に存在しない状態になることがあります。

このような状況で、Goランタイムが通常のデッドロック検出ロジックを適用してしまうと、実際にはCプログラムが動作を継続しているにもかかわらず、Goランタイムがデッドロックと誤認してプログラムを終了させてしまうという問題が発生していました。このコミットは、この誤検出を防ぎ、`c-archive`や`c-shared`モードでビルドされたGoライブラリがCプログラム内で正しく動作するようにするために導入されました。

## 前提知識の解説

### Goのデッドロック検出

Goランタイムは、プログラムが進行不能な状態に陥ったかどうかを監視しています。その主要なメカニズムの一つが、実行可能なゴルーチンが一つも存在しない状態の検出です。Goのスケジューラは、実行可能なゴルーチンがない場合、すべてのM（OSスレッド）がP（プロセッサ）にアタッチされ、かつすべてのPがアイドル状態（つまり、実行すべきゴルーチンがない状態）であることを確認します。この状態が一定時間続くと、ランタイムはデッドロックと判断し、スタックトレースを出力してプログラムを終了させます。これは、Goの並行処理モデルにおいて、プログラムが意図せず停止してしまったことを開発者に知らせる重要な機能です。

### Goの `buildmode`

Goコンパイラには、`go build`コマンドの`-buildmode`フラグを通じて、様々なビルドモードが提供されています。これにより、Goのコードを異なる形式でコンパイルし、様々な環境で利用することが可能になります。

-   **`buildmode=exe`**: デフォルトのモードで、実行可能なバイナリを生成します。
-   **`buildmode=c-archive`**: GoのパッケージをC言語の静的ライブラリ（`.a`ファイル）としてコンパイルします。このライブラリは、C/C++プログラムにリンクして使用できます。Goランタイムもこのアーカイブに含まれます。
-   **`buildmode=c-shared`**: GoのパッケージをC言語の共有ライブラリ（`.so`や`.dylib`など）としてコンパイルします。このライブラリは、C/C++プログラムから動的にロードして使用できます。Goランタイムもこの共有ライブラリに含まれます。
-   **`buildmode=plugin`**: Goのプラグインを生成します。これは、Goプログラムから動的にロードして使用できます。

`c-archive`と`c-shared`モードは、Goの強力な並行処理機能を既存のC/C++コードベースに統合する際に特に有用です。しかし、これらのモードでは、Goランタイムが独立したアプリケーションとしてではなく、より大きなCプログラムの一部として動作するという特性を理解することが重要です。

## 技術的詳細

このコミットで修正されるのは、Goランタイム内の`checkdead`関数です。この関数は、Goプログラムがデッドロック状態にあるかどうかを判断する役割を担っています。従来の`checkdead`関数は、実行可能なM（OSスレッド）の数が0になった場合にデッドロックと判断していました。

しかし、`buildmode=c-archive`や`buildmode=c-shared`でビルドされたGoライブラリの場合、GoランタイムはCプログラムによって呼び出される関数を提供します。Goの関数が実行されていない間、Goランタイム内のゴルーチンはすべてアイドル状態になる可能性があります。このとき、Goランタイムの視点から見ると、実行可能なゴルーチンは存在せず、Mの数も0になることがあります。しかし、これはGoランタイムがデッドロックに陥ったことを意味するのではなく、単にCプログラムがGoのコードを実行していないだけです。Cプログラムは引き続き動作しており、後で再びGoの関数を呼び出す可能性があります。

この問題を解決するため、コミットでは`checkdead`関数に条件分岐が追加されました。この条件分岐は、Goランタイムが`c-archive` (`isarchive`フラグ) または `c-shared` (`islibrary`フラグ) モードでビルドされているかどうかをチェックします。これらのフラグは、Goランタイムの初期化時に設定され、現在のビルドモードを示します。

もしGoランタイムがこれらのライブラリモードで動作している場合、`checkdead`関数はすぐにリターンし、デッドロック検出ロジックの残りの部分を実行しません。これにより、Goランタイムが一時的にアイドル状態になっても、不必要なデッドロックエラーが報告されることがなくなります。これは、GoライブラリがCプログラムの一部として「従属的」に動作するという性質を尊重した変更と言えます。

## コアとなるコードの解説

追加されたコードは以下の部分です。

```go
	// For -buildmode=c-shared or -buildmode=c-archive it's OK if
	// there are no running goroutines.  The calling program is
	// assumed to be running.
	if islibrary || isarchive {
		return
	}
```

-   `isarchive` と `islibrary` は、Goランタイムがそれぞれ `buildmode=c-archive` または `buildmode=c-shared` でビルドされた場合に `true` となるグローバル変数（またはランタイム内部のフラグ）です。
-   この `if` 文は、現在のGoプログラムがC言語から呼び出されるライブラリとして動作しているかどうかをチェックします。
-   もし `isarchive` または `islibrary` のいずれかが `true` であれば、GoランタイムはCプログラムの一部として動作していると判断されます。
-   この場合、Goランタイム内のゴルーチンが一時的に存在しなくても、それはデッドロックを意味しません。なぜなら、呼び出し元のCプログラムがまだアクティブに動作していると想定されるからです。
-   したがって、`return` ステートメントによって `checkdead` 関数の残りのデッドロック検出ロジックがスキップされ、不必要なデッドロックエラーの報告が抑制されます。

この変更により、GoのライブラリがCプログラムに組み込まれた際に、Goランタイムのデッドロック検出がそのコンテキストを正しく理解し、誤ったエラーを発生させないようになりました。

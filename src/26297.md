# [インデックス 26297] ファイルの概要

このコミットは、Go言語の `net/textproto` パッケージにおける `Reader.ReadResponse()` メソッドの挙動を改善し、複数行にわたるエラーメッセージを適切に処理できるようにするものです。特に、RFC 959で定義されているような、コードとメッセージが複数行にわたって続く形式のレスポンスを正しく解釈し、エラー発生時にもメッセージ全体を保持するように修正されています。

## コミット

`net/textproto: accept multi-line error messages`

このコミットは、`net/textproto` パッケージが複数行のエラーメッセージを受け入れるように変更します。`ReadResponse()` メソッドが受け入れるメッセージの2つの形式に関するドキュメントが追加され、メッセージの妥当性が検証プロセスによって変更されるべきではないという原則が強調されています。以前は、予期しないコードを持つメッセージの場合、適切にフォーマットされたメッセージが完全に読み取られない問題がありました。この変更は、Go issue #10230 を修正します。

## 変更の背景

この変更の背景には、`net/textproto` パッケージの `ReadResponse()` メソッドが、特定の条件下で複数行にわたるエラーメッセージを正しく処理できないというバグが存在していました。具体的には、RFC 959 (FTPプロトコル) などで規定されているような、ステータスコードとメッセージが複数行にわたって続く形式のレスポンスにおいて、予期しないステータスコードが返された場合に、メッセージの途中で読み取りが中断されてしまう問題がありました。

Go issue #10230 では、この問題が報告されており、特にSMTPなどのプロトコルで複数行のエラーメッセージが返された際に、`ReadResponse()` がメッセージ全体を読み取らず、不完全なエラーメッセージを返すことが指摘されていました。これにより、クライアント側で正確なエラー情報を取得できず、デバッグやエラーハンドリングが困難になるという問題がありました。

このコミットは、この問題を解決し、`ReadResponse()` がどのような状況でも複数行のメッセージを完全に読み取り、エラー発生時にもその完全なメッセージをエラー情報として提供できるようにすることを目的としています。

## 前提知識の解説

### `net/textproto` パッケージ

`net/textproto` パッケージは、Go言語の標準ライブラリの一部であり、テキストベースのネットワークプロトコル（HTTP、SMTP、FTPなど）を扱うための低レベルなプリミティブを提供します。このパッケージは、ヘッダーの解析、行の読み書き、ステータスコードの処理など、一般的なテキストプロトコル操作を容易にする機能を提供します。

### RFC 959 (FTPプロトコル)

RFC 959は、File Transfer Protocol (FTP) を定義する標準ドキュメントです。FTPは、クライアントとサーバー間でファイルを転送するためのプロトコルであり、コマンドとレスポンスはテキストベースでやり取りされます。

RFC 959では、サーバーからのレスポンスメッセージの形式が規定されています。特に、複数行にわたるレスポンスメッセージの形式が重要です。RFC 959の36ページには、以下の2つの形式が記載されています。

1.  **単一行レスポンス**: `<code> <message>`
    例: `220 Service ready for new user.`

2.  **複数行レスポンス**:
    ```
    <code>-<message line 1>
    <message line 2>
    ...
    <code> <message line n>
    ```
    この形式では、最初の行は `コード-メッセージ` の形式で始まり、続く行はメッセージの続きを示します。最後の行は `コード メッセージ` の形式で、ハイフンではなくスペースで区切られ、メッセージの終了を示します。これにより、クライアントは複数行にわたる情報を一つの論理的なレスポンスとして解釈できます。

### `Reader.ReadResponse()` メソッド

`net/textproto` パッケージの `Reader` 型が提供する `ReadResponse()` メソッドは、上記のRFC 959のようなテキストベースのプロトコルレスポンスを読み取るために使用されます。このメソッドは、期待されるステータスコード (`expectCode`) を引数に取り、サーバーからのレスポンスを解析して、ステータスコード、メッセージ、およびエラーを返します。

このメソッドの主な役割は、レスポンスの最初の行からステータスコードを抽出し、必要に応じて複数行のメッセージを読み取り、最終的なメッセージ文字列を構築することです。

### Go issue #10230

Go issue #10230 は、「`net/textproto`: `ReadResponse` does not read full multi-line error message」というタイトルで報告されたバグです。この問題は、`ReadResponse()` が予期しないステータスコードを受け取った場合に、複数行のエラーメッセージの途中で読み取りを停止してしまうことを指摘していました。これにより、エラーメッセージが切り詰められ、完全な情報が得られないという問題が発生していました。

## 技術的詳細

このコミットの技術的な核心は、`Reader.ReadResponse()` メソッドが複数行のレスポンスを処理するロジックの改善にあります。

元の実装では、`ReadResponse()` は `r.readCodeLine(expectCode)` を呼び出して最初の行を読み取り、`continued` フラグが `true` の間、ループで後続の行を読み込んでいました。この `continued` フラグは、行が `コード-メッセージ` の形式である場合に `true` になります。

問題は、ループ内で後続の行を解析する際に `parseCodeLine(line, expectCode)` を使用していた点です。ここで `expectCode` を渡してしまうと、もし最初の行のコードが `expectCode` と異なり、かつ後続の行のコードも `expectCode` と異なる場合、`parseCodeLine` がエラーを返し、ループが中断されてしまう可能性がありました。これにより、複数行エラーメッセージの途中で読み取りが停止し、不完全なメッセージが `message` 変数に格納されていました。

このコミットでは、以下の変更が加えられています。

1.  **`multi` フラグの導入**: `multi := continued` という行が追加され、最初の行が複数行レスポンスの開始を示す (`continued` が `true`) かどうかを記憶するための `multi` フラグが導入されました。これは、エラー発生時にメッセージ全体をエラーオブジェクトに含めるために使用されます。

2.  **`parseCodeLine` の `expectCode` 引数の変更**: ループ内で後続の行を解析する `parseCodeLine` の呼び出しが `parseCodeLine(line, 0)` に変更されました。`expectCode` の代わりに `0` を渡すことで、後続の行のコードが特定の期待値と一致するかどうかをチェックするのではなく、単にコードとメッセージを解析する動作になります。これにより、たとえ最初の行のコードが期待値と異なっていても、後続のメッセージ行が正しく読み込まれ続けるようになります。

3.  **エラーメッセージの完全性の保証**: ループの後に以下の条件が追加されました。
    ```go
    if err != nil && multi && message != "" {
        // replace one line error message with all lines (full message)
        err = &Error{code, message}
    }
    ```
    これは、`ReadResponse()` がエラーを返した場合 (`err != nil`)、かつ最初の行が複数行レスポンスの開始を示していた場合 (`multi` が `true`)、かつメッセージが空でない場合 (`message != ""`) に、既存のエラーオブジェクトを、読み取られた完全なメッセージを含む新しい `Error` オブジェクトで置き換えるものです。これにより、エラー発生時でも、`ReadResponse()` が読み取ったすべてのメッセージ行がエラー情報として提供されることが保証されます。

これらの変更により、`ReadResponse()` は、RFC 959のような複数行のレスポンス形式において、予期しないステータスコードが返された場合でも、メッセージ全体を最後まで読み取り、その完全なメッセージをエラー情報として返すことができるようになりました。

## コアとなるコードの解説

### `src/net/textproto/reader.go` の変更点

-   **ドキュメントの追加**: `ReadResponse` メソッドのコメントに、RFC 959で定義されている複数行レスポンスの形式 (`code-message line 1`, `message line 2`, ..., `code message line n`) に関する詳細が追加されました。これにより、このメソッドがどのような形式のレスポンスを処理できるかが明確になりました。

-   **`multi` 変数の導入**:
    ```go
    	code, continued, message, err := r.readCodeLine(expectCode)
    	multi := continued
    ```
    `readCodeLine` から返される `continued` の初期値を `multi` に保存しています。`continued` は、最初の行が複数行レスポンスの開始を示す (`-` で終わる) かどうかを示します。`multi` は、このレスポンス全体が複数行レスポンスとして始まったかどうかを記憶するために使用されます。

-   **ループ条件の変更**:
    ```diff
    -	for err == nil && continued {
    +	for continued {
    ```
    以前は `err == nil` の間だけループが継続していましたが、この変更により、エラーが発生しても `continued` が `true` である限り、メッセージの読み取りを試みるようになりました。これは、エラーが発生してもメッセージ全体を読み切ることで、より完全なエラー情報を提供するためです。

-   **`parseCodeLine` の引数変更**:
    ```diff
    -		code2, continued, moreMessage, err = parseCodeLine(line, expectCode)
    +		code2, continued, moreMessage, err = parseCodeLine(line, 0)
    ```
    複数行レスポンスの途中の行を解析する際に、`expectCode` の代わりに `0` を渡すようになりました。これにより、後続の行のコードが最初の行のコードと一致するかどうかのみをチェックし、`ReadResponse` に渡された `expectCode` とは独立してメッセージの読み取りを継続できます。もし `expectCode` を渡し続けると、途中の行のコードが `expectCode` と一致しない場合に、メッセージの読み取りが途中で中断されてしまう可能性がありました。`0` を渡すことで、`parseCodeLine` はコードの一致を強制せず、単にコードとメッセージを解析する役割に徹します。

-   **エラーオブジェクトの更新**:
    ```go
    	if err != nil && multi && message != "" {
    		// replace one line error message with all lines (full message)
    		err = &Error{code, message}
    	}
    ```
    `ReadResponse` メソッドの最後にこのブロックが追加されました。
    -   `err != nil`: 何らかのエラーが発生した場合。
    -   `multi`: 最初の行が複数行レスポンスの開始を示していた場合。
    -   `message != ""`: 読み取られたメッセージが空でない場合。
    これらの条件がすべて満たされる場合、既存のエラー (`err`) を、読み取られた完全な `message` を含む新しい `Error` オブジェクトで上書きします。これにより、エラーが発生しても、`ReadResponse` が読み取ったすべてのメッセージ行がエラー情報として `Error` オブジェクトの `message` フィールドに格納されることが保証されます。

### `src/net/textproto/reader_test.go` の変更点

-   **`TestReadMultiLineError` テストケースの追加**:
    Go issue #10230 で報告されたシナリオを再現する新しいテストケースが追加されました。
    -   このテストでは、SMTPのエラーメッセージに似た、複数行にわたるエラーレスポンス文字列を `reader` 関数に渡して `Reader` オブジェクトを作成します。このレスポンスには、途中にコードと一致しない「Unexpected but legal text!」のような行も含まれています。
    -   `r.ReadResponse(250)` を呼び出し、期待されるコードが `250` であると指定します。しかし、テストデータは `550` で始まるエラーメッセージです。
    -   テストは、`ReadResponse` がエラーを返すこと、返されたコードが `550` であること、そして返されたメッセージ (`msg`) が期待される完全な複数行メッセージと一致することを確認します。
    -   さらに、`err.Error()` が `550 ` と完全なメッセージを結合した文字列と一致することも検証し、エラーオブジェクト自体が完全なメッセージを保持していることを確認します。

この新しいテストケースは、変更が正しく機能し、複数行のエラーメッセージが予期しないコードの場合でも完全に読み取られ、エラー情報として適切に返されることを保証します。

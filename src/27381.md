# [インデックス 27381] ファイルの概要

このコミットは、Goランタイムの`src/runtime/cgo/gcc_signal_darwin_armx.c`ファイルに対する変更です。このファイルは、Darwin (macOS/iOS) 上のARMアーキテクチャにおいて、Cgoを介してGoとCのコードが連携する際のシグナルハンドリング、特にMach例外ハンドラに関連する部分を扱っています。具体的には、Goプログラムがクラッシュした際に、Mach例外をGoのパニックに変換するための非Goスレッドの動作を制御する役割を担っています。

## コミット

このコミットの主な目的は、iOS (darwin/arm{,64}) 環境でMach例外をGoのパニックに変換するために作成される非Goスレッドに対して、すべてのPOSIXシグナルをブロックすることです。これにより、Goのシグナルハンドラが意図しないシグナルを処理することを防ぎ、特に`os/signal`パッケージのテストが正しく動作するようにします。

## 変更の背景

GoプログラムがDarwin (特にiOSのARMアーキテクチャ) 上で動作する際、Cgoを介してC言語のコードと連携することがあります。この環境では、メモリ不正アクセスなどの致命的なエラーが発生した場合、OSはMach例外（`EXC_BAD_ACCESS`など）を生成します。Goランタイムは、これらのMach例外をGoのパニック（panic）に変換し、Goの通常の例外処理フローに乗せるための特別な非Goスレッドを作成します。

しかし、この非GoスレッドにPOSIXシグナルが到達すると問題が発生しました。Goのシグナルハンドラは、非Goスレッドに到達したシグナル（Goランタイムが管理していないスレッド）を無視するように設計されています。これは、Goランタイムが自身の管理下にあるGoルーチンやGoスレッドにのみ責任を持つためです。

この設計上の挙動により、非Goスレッドに到達したシグナルがGoランタイムによって適切に処理されず、予期せぬ動作を引き起こす可能性がありました。特に、`os/signal`パッケージの`TestStop`のようなテストは、非Goスレッドにシグナルが到達しないことを前提としていました。シグナルが到達してしまうと、テストが失敗する原因となっていました。

この問題はGo issue #14318として報告されており、このコミットはその解決を目的としています。非Goスレッドにシグナルが到達しないようにすることで、Goランタイムのシグナルハンドリングの整合性を保ち、テストの信頼性を向上させることが背景にあります。

## 前提知識の解説

### GoランタイムとCgo

Go言語は、C言語との相互運用を可能にするCgoというメカニズムを提供しています。Cgoを使用すると、GoプログラムからCライブラリを呼び出したり、CコードからGo関数を呼び出したりできます。Darwin環境では、CgoはGoランタイムとOSの低レベルな機能（Mach APIなど）との橋渡しをします。

### DarwinのMach例外とPOSIXシグナル

macOSやiOSなどのDarwin系OSでは、プログラムの異常終了やエラーは主に2つのメカニズムで通知されます。

1.  **Mach例外 (Mach Exceptions)**:
    *   MachはDarwinカーネルのマイクロカーネル部分であり、低レベルなプロセス間通信や例外処理を提供します。
    *   `EXC_BAD_ACCESS`は、無効なメモリアドレスへのアクセスなど、メモリ保護違反が発生した際に生成されるMach例外の一種です。
    *   Mach例外は、特定のポートにメッセージとして送信され、そのポートを監視しているハンドラによって処理されます。Goランタイムは、このメカニズムを利用して、ネイティブコードでのクラッシュをGoのパニックに変換します。
    *   `mach_port_allocate`, `mach_task_self`, `mach_exception_handler_port_set`などの関数や変数はこのMach例外処理に関連するものです。

2.  **POSIXシグナル (POSIX Signals)**:
    *   UNIX系OSで広く使われているプロセス間通信および例外処理のメカニズムです。
    *   `SIGSEGV` (セグメンテーション違反) や `SIGBUS` (バスエラー) などは、Mach例外と類似した状況で発生することがありますが、これらはPOSIXの概念です。
    *   シグナルは、プロセス内の特定のスレッドに配信されるか、プロセス全体に配信されます。
    *   `sigset_t`, `sigfillset`, `pthread_sigmask`, `SIG_SETMASK`といった関数や型は、POSIXシグナルのマスク（ブロック/アンブロック）を操作するために使用されます。

### Goのシグナルハンドリング

Goランタイムは、自身の管理下にあるGoルーチンやGoスレッドに対して、特定のシグナルを捕捉し、Goのパニックやその他のランタイムエラーに変換する独自のシグナルハンドラを持っています。しかし、Goランタイムが直接管理していないCgoスレッドや、OSが作成したスレッド（今回のMach例外ハンドラースレッドなど）にシグナルが到達した場合、Goのシグナルハンドラはそれらを処理しないか、無視する傾向があります。これは、Goのメモリモデルやスケジューリングモデルとの整合性を保つためです。

### `pthread_create`とスレッドのシグナルマスク

`pthread_create`は、新しいPOSIXスレッドを作成するための関数です。スレッドは、親スレッドからシグナルマスク（ブロックされているシグナルのセット）を継承します。したがって、新しいスレッドが作成される前に親スレッドのシグナルマスクを変更することで、子スレッドの初期シグナルマスクを制御できます。

## 技術的詳細

このコミットは、`darwin_arm_init_mach_exception_handler()`関数内で、Mach例外ハンドラースレッドが作成される直前に、そのスレッドに到達するPOSIXシグナルをブロックする処理を追加しています。

1.  **シグナルセットの初期化**:
    `sigset_t ign, oset;`
    `ign`はブロックするシグナルのセットを、`oset`は元のシグナルマスクを保存するために使用されます。

2.  **すべてのシグナルをブロックするセットの作成**:
    `sigfillset(&ign);`
    `sigfillset`関数は、`ign`にすべての標準シグナルを含むように設定します。これにより、すべてのPOSIXシグナルがブロック対象となります。

3.  **現在のスレッドのシグナルマスクの変更**:
    `pthread_sigmask(SIG_SETMASK, &ign, &oset);`
    `pthread_sigmask`関数は、現在のスレッド（この場合は`darwin_arm_init_mach_exception_handler`を実行しているスレッド）のシグナルマスクを変更します。
    *   `SIG_SETMASK`は、シグナルマスクを`ign`で指定されたセットに完全に置き換えることを意味します。
    *   `oset`には、変更前の元のシグナルマスクが保存されます。

4.  **Mach例外ハンドラースレッドの作成**:
    `ret = pthread_create(&thr, &attr, mach_exception_handler, (void*)port_set);`
    この行で、Mach例外を処理するための新しいスレッドが作成されます。この新しいスレッドは、`pthread_create`が呼び出された時点での親スレッドのシグナルマスク（つまり、すべてのシグナルがブロックされた状態のマスク）を継承します。これにより、Mach例外ハンドラースレッドにはPOSIXシグナルが到達しなくなります。

5.  **元のシグナルマスクの復元**:
    `pthread_sigmask(SIG_SETMASK, &oset, nil);`
    Mach例外ハンドラースレッドの作成後、元のスレッドのシグナルマスクを`oset`に保存されていた値に戻します。これは、この関数を呼び出した側のスレッドのシグナルハンドリングの挙動に影響を与えないようにするためです。

この変更により、Mach例外ハンドラースレッドは、Goランタイムが意図しないPOSIXシグナルによって中断されたり、予期せぬ動作をしたりすることがなくなります。これは、Goのシグナルハンドラが非Goスレッドのシグナルを処理しないという前提と、`os/signal`パッケージのテストの要件を満たすために重要です。

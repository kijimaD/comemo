## 変更の背景

このコミットは、Goランタイムの文字列結合処理（`concatstrings`関数）において、文字列の長さが許容範囲を超えた場合に発生するエラーのハンドリングを修正するものです。元々、このエラーはランタイム内部の致命的な問題として`gothrow`（または`runtime.throw`）によって処理されるべきでしたが、何らかの理由で誤って`panic`に変換されていました。

`panic`と`gothrow`はどちらもプログラムの異常終了を引き起こす可能性がありますが、その目的と性質が大きく異なります。`panic`はGo言語のユーザーレベルのエラーハンドリングメカニズムであり、`defer`と`recover`によって捕捉・回復が可能です。一方、`gothrow`はGoランタイム内部の回復不可能な致命的エラーを示すために使用され、通常はプログラムの即時終了を伴います。

文字列結合の長さがシステムで扱える最大値を超過するような状況は、単なるアプリケーションロジックのエラーではなく、ランタイムのメモリ管理やデータ構造の整合性に関わる深刻な問題です。このような状況で`panic`が発行されると、ユーザーコードがこれを捕捉し、ランタイムが想定しない状態での処理を続行してしまう可能性があります。これは、さらなるデータ破損やセキュリティ上の脆弱性につながる恐れがあります。

したがって、このコミットの目的は、文字列結合の長さオーバーフローというランタイムの整合性に関わるエラーを、本来あるべき`gothrow`による致命的エラーとして扱うように修正し、Goランタイムの堅牢性と安全性を確保することにあります。

## 前提知識の解説

### Goにおける`panic`と`recover`

Go言語には、例外処理のメカニズムとして`panic`と`recover`が組み込まれています。
*   **`panic`**: プログラムの通常の実行フローを中断させるために使用されます。これは、通常のエラーハンドリング（`error`インターフェース）では対処できないような、予期せぬ、回復不可能な状況（例: nilポインタのデリファレンス、配列の範囲外アクセス、ゼロ除算など）で発生します。`panic`が発生すると、現在の関数の実行が直ちに停止し、その関数に登録されている`defer`関数が実行されます。その後、呼び出し元の関数へとスタックが巻き戻され（unwind）、各レベルで`defer`関数が実行されます。最終的に、スタックの最上位まで`panic`が到達すると、プログラムは異常終了します。
*   **`recover`**: `panic`によって中断されたゴルーチンの実行を再開するために使用されます。`recover`は`defer`関数内でのみ有効です。`defer`関数内で`recover`が呼び出されると、`panic`の値（`panic`に渡された引数）が返され、そのゴルーチンの`panic`状態が解除され、通常の実行フローが再開されます。これにより、プログラムのクラッシュを防ぎ、エラーを適切にログに記録したり、代替処理を実行したりすることが可能になります。

### Goランタイムの`gothrow` (または`runtime.throw`)

`gothrow`は、Goランタイム内部で使用される、より低レベルで回復不可能なエラー通知メカニズムです。Goのソースコードでは`runtime.throw`として定義されており、ユーザーコードから直接呼び出すことはできません（エクスポートされていないため）。

`runtime.throw`は、ランタイム自体が回復できないような、非常に深刻な内部エラー（例: ヒープの破損、スケジューラの異常、致命的なシステムコールエラーなど）が発生した場合に呼び出されます。`panic`とは異なり、`runtime.throw`によって引き起こされたエラーは、ユーザーコードの`recover`では捕捉できません。`runtime.throw`が呼び出されると、通常はデバッガに制御を渡すか、プログラムを即座に終了させます。これは、ランタイムの整合性が損なわれた状態でプログラムの実行を続けることが、さらなる問題を引き起こす可能性が高いためです。

### 文字列結合とメモリ割り当て

Go言語の文字列は不変（immutable）です。複数の文字列を結合する場合、新しい文字列を格納するためのメモリが新たに割り当てられます。例えば、`s1 + s2 + s3`のような操作では、まず`s1`と`s2`が結合されて一時的な新しい文字列が作成され、次にその一時文字列と`s3`が結合されて最終的な新しい文字列が作成されます。

Goのランタイムには、`concatstrings`のような内部関数があり、効率的な文字列結合を処理します。この関数は、結合後の文字列の合計長さを事前に計算し、必要なメモリを一度に割り当てようとします。しかし、計算された合計長さがシステムが扱える最大値（例えば、`int`型の最大値や、利用可能なメモリ量）を超過する可能性があります。このような「長さオーバーフロー」は、メモリ割り当ての失敗や、不正なメモリ領域へのアクセスにつながるため、ランタイムにとって致命的なエラーとなります。

## 技術的詳細

このコミットが修正しているのは、`src/pkg/runtime/string.go`ファイル内の`concatstrings`関数です。この関数は、可変個の文字列スライスを受け取り、それらを結合して単一の文字列を返すGoランタイムの内部関数です。

`concatstrings`関数内では、結合後の文字列の合計長さを計算するロジックが含まれています。具体的には、各文字列の長さを`l`（現在の合計長さ）に加算していきます。この際、`if l+n < l`というチェックが行われます。ここで`n`は現在の文字列の長さ、`l`はこれまでの合計長さです。この条件式は、`l+n`の計算がオーバーフローした場合に真となります。例えば、`l`が非常に大きく、`n`を加算すると`int`型の最大値を超えてしまい、結果が負の値になったり、非常に小さな値になったりする場合です。これは、符号なし整数でのオーバーフローチェックの一般的なイディオムです。

元のコードでは、このオーバーフローが検出された場合に`panic("string concatenation too long")`が呼び出されていました。しかし、前述の通り、文字列結合の長さオーバーフローはランタイムのメモリ管理の根幹に関わる問題であり、ユーザーコードで`recover`されるべきではありません。このような状況で`panic`が発行されると、ランタイムの内部状態が不安定なままプログラムが続行されるリスクがあります。

このコミットでは、`panic`の呼び出しを`gothrow("string concatenation too long")`に置き換えることで、この問題を修正しています。`gothrow`はGoランタイムの内部関数であり、回復不可能な致命的エラーを通知するために使用されます。これにより、文字列結合の長さオーバーフローが発生した場合、プログラムは即座に終了し、ランタイムの整合性が保たれるようになります。これは、Goランタイムの堅牢性を高める上で重要な変更です。

```diff
--- a/src/pkg/runtime/string.go
```

## コアとなるコードの解説

変更された行は、`concatstrings`関数内の文字列長オーバーフローチェックの直後にあります。

```go
		if l+n < l {
			// 変更前: panic("string concatenation too long")
			// 変更後: gothrow("string concatenation too long")
		}
```

*   `l+n < l`: この条件は、`l`と`n`が符号なし整数（またはGoの`int`型がプラットフォームのネイティブワードサイズにマップされることを考慮した上で、オーバーフローを検出する目的で）として扱われた場合に、加算結果がオーバーフローしたことを検出する一般的な方法です。もし`l+n`がオーバーフローして、その結果が`l`よりも小さくなる場合、それは計算が正しく行われなかったことを意味します。
*   `panic("string concatenation too long")` (変更前):
    *   この行は、文字列の合計長がオーバーフローした場合に、Goの組み込み関数である`panic`を呼び出していました。
    *   `panic`はユーザーコードで`recover`によって捕捉される可能性があるため、ランタイムの内部エラーをユーザーが回復しようとすると、ランタイムの整合性が損なわれるリスクがありました。
*   `gothrow("string concatenation too long")` (変更後):
    *   この行は、`panic`の代わりに`gothrow`（`runtime.throw`の内部名）を呼び出します。
    *   `gothrow`はGoランタイムの内部で発生する、回復不可能な致命的なエラーを示すために使用されます。
    *   `gothrow`が呼び出されると、プログラムは通常、即座に終了します。これにより、ランタイムの内部状態が不正なまま実行が続けられることを防ぎ、システムの安定性と安全性を確保します。

この変更は、文字列結合の長さオーバーフローが、ユーザーが回復すべきアプリケーションレベルのエラーではなく、Goランタイム自体が対処すべき深刻な内部エラーであるという認識に基づいています。これにより、Goプログラムの堅牢性が向上し、予期せぬ動作やセキュリティ上の問題が回避されます。

## 変更の背景

Goコンパイラは、コードの最適化のためにSSA（Static Single Assignment）形式という中間表現を使用しています。SSA形式では、各変数が一度だけ代入されるという特性を持ち、これにより様々な最適化が容易になります。共通部分式除去（CSE）はそのような最適化の一つで、同じ計算が複数回行われている場合に、その計算を一度だけ行い、結果を再利用することで冗長な計算を排除します。

従来のGoコンパイラのCSEパスでは、`OpSB`（Static Base pointer）のような特定のゼロ引数値に対して特別な処理が必要でした。`OpSB`は、グローバルデータや静的データにアクセスするための基準点を示す特殊な値であり、引数を持ちません。このようなゼロ引数値は、プログラム内で頻繁に参照される可能性があり、効率的な処理が求められます。

このコミットの背景には、以下の課題がありました。

1.  **汎用CSEパスの複雑性**: 汎用的なCSEパスは、あらゆる種類の値に対応するため、ゼロ引数値のような単純なケースに対しても複雑なロジックを適用していました。特に`OpSB`の除去には特殊なコードパスが必要で、これがコードの可読性や保守性を低下させていました。
2.  **最適化の非効率性**: ゼロ引数値は、その性質上、他の値よりも簡単に共通部分式として特定できます。汎用CSEパスでこれらを処理することは、より複雑な値の処理にリソースを割くべき時に、比較的単純な最適化に時間を費やすことになり、全体的なコンパイル効率を損なう可能性がありました。
3.  **パフォーマンスの改善**: `arithConst_ssa.go`のようなファイルは、算術演算や定数に関するSSA最適化を扱うため、ゼロ引数定数の効率的な処理がコンパイル時間に大きく影響します。この種のファイルにおけるコンパイル速度の改善は、全体的なコンパイラのパフォーマンス向上に寄与します。

これらの課題に対処するため、引数を持たない値に特化した軽量なCSEパスを導入し、汎用CSEパスからその特殊処理を分離することが提案されました。これにより、最適化の段階を細分化し、よりターゲットを絞った効率的な処理を実現することを目指しました。

## 前提知識の解説

### 1. GoコンパイラとSSA (Static Single Assignment)

Goコンパイラは、ソースコードを機械語に変換する過程で、複数の段階を経て最適化を行います。その中間段階の一つに、**SSA (Static Single Assignment)** 形式への変換があります。

*   **SSA形式**: プログラム中の各変数が一度だけ代入されるように変換された中間表現です。これにより、データフロー解析や最適化が非常に容易になります。例えば、`x = a + b; y = x * 2; x = c + d; z = x / 2;` というコードは、SSA形式では `x1 = a + b; y = x1 * 2; x2 = c + d; z = x2 / 2;` のように変換され、各`x`が異なるバージョンとして扱われます。
*   **SSA値 (Value)**: SSA形式における基本的な構成要素で、特定の演算の結果を表します。各SSA値は、その演算の種類（Op）、引数（Args）、補助情報（AuxInt, Aux）、型（Type）などを持っています。
*   **SSAオペレーション (Op)**: SSA値が実行する演算の種類を定義します。例えば、`OpAdd64`は64ビット整数の加算、`OpLoad`はメモリからの読み込みなどです。

### 2. 共通部分式除去 (CSE: Common Subexpression Elimination)

CSEは、コンパイラ最適化の一種で、プログラム内で同じ式が複数回計算されている場合に、その式を一度だけ計算し、結果を再利用することで冗長な計算を排除します。

例:
```go
a = x + y
b = z + (x + y)
```
この場合、`x + y` は共通部分式です。CSEを適用すると、以下のように最適化されます。
```go
temp = x + y
a = temp
b = z + temp
```
これにより、`x + y` の計算が一度で済み、実行速度が向上します。

### 3. ゼロ引数値 (Zero Argument Values)

GoコンパイラのSSA形式において、「ゼロ引数値」とは、その値を生成するために他のSSA値を引数として必要としないSSA値のことを指します。これらは通常、定数や特定のシステムレジスタ、あるいはメモリ上の固定アドレスなどを表します。

このコミットで言及されている主なゼロ引数値は以下の通りです。

*   **`OpSB` (Static Base pointer)**: GoコンパイラのSSAにおいて、静的ベースポインタを表すオペレーションです。これは、グローバル変数や静的に割り当てられたデータにアクセスするための基準となるメモリアドレスを指します。`OpSB`は引数を取らず、常に同じ値を生成するため、共通部分式除去の非常に良い候補となります。
*   **定数 (Constants)**: `OpConst64` (64ビット整数定数), `OpConst32` (32ビット整数定数), `OpConstBool` (真偽値定数), `OpConstNil` (nilポインタ定数) など、プログラム内で直接記述されたリテラル値もゼロ引数値です。これらも引数を取らず、常に同じ値を生成します。

これらのゼロ引数値は、プログラムの様々な場所で繰り返し生成される可能性がありますが、その値は常に同じであるため、一度計算（または取得）すれば、その結果を再利用できます。

### 4. `arithConst_ssa.go`

Goコンパイラのソースコード内の `src/cmd/compile/internal/ssa/arithConst_ssa.go` のようなファイルは、SSA形式における算術演算や定数に関する最適化ルールを定義していると考えられます。例えば、定数畳み込み（constant folding）や、算術演算の簡略化など、定数値を扱う最適化パスがここに記述されている可能性が高いです。ゼロ引数定数の効率的な処理は、このような最適化パスのパフォーマンスに直接影響します。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおける共通部分式除去（CSE）の戦略を改善することにあります。具体的には、引数を持たないSSA値（ゼロ引数値）に特化した新しいCSEパス `zcse` を導入し、既存の汎用CSEパス `cse` からゼロ引数値に関する特殊な処理を削除しています。

### 1. `zcse` パスの導入

*   **目的**: `OpSB`や各種定数（`OpConst64`, `OpConstNil`など）といったゼロ引数値は、その性質上、プログラムのどこで生成されても常に同じ値を持ちます。これらの値に対する共通部分式除去は、他の複雑な値に対するCSEよりもはるかに単純かつ高速に実行できます。`zcse`パスは、この特性を利用して、汎用CSEパスが実行される前に、これらの単純な共通部分式を効率的に除去することを目的としています。
*   **実装**:
    *   `zcse`関数は、`src/cmd/compile/internal/ssa/zcse.go` に新しく追加されました。
    *   このパスは、まず関数内のすべてのブロックを走査し、ゼロ引数値（`OpSB`, `OpConst*`など）を特定します。
    *   特定されたゼロ引数値は、`vkey`という構造体（オペレーション、補助情報、型を含む）をキーとしてマップに格納されます。これにより、同じ値を持つSSA値が容易に識別されます。
    *   重要なのは、最初に見つかったゼロ引数値のインスタンスを、その値を使用する可能性のあるすべてのブロックから到達可能な**エントリブロック**に移動させる点です。これにより、ドミネータツリーの計算を必要とせずに、その値が関数全体で利用可能であることを保証します。
    *   次に、再度すべてのブロックと値を走査し、引数としてゼロ引数値を使用している箇所を見つけます。もし、そのゼロ引数値が既にマップに登録されている（つまり、共通部分式として特定されている）場合、その引数をマップに登録されている既存のSSA値に置き換えます。
*   **利点**:
    *   **高速化**: 汎用CSEパスよりもはるかに単純なロジックで、多くの共通部分式を除去できます。
    *   **汎用CSEパスの簡素化**: 汎用CSEパスからゼロ引数値に関する特殊な処理（特に`OpSB`の処理）を削除できるため、汎用CSEパスのコードが簡素化され、保守性が向上します。
    *   **コンパイル時間の改善**: `arithConst_ssa.go`のような定数や算術演算を多用するコードのコンパイルが9%高速化されるという具体的な効果が報告されています。

### 2. `cse` パスの変更

*   **特殊ケースの削除**: 従来の`cse`関数には、`optimize`フラグが設定されていない場合に`OpSB`の重複を除去するための特殊なロジックが含まれていました。`zcse`パスが導入されたことで、この特殊なロジックは不要となり、`cse.go`から削除されました。
*   **実行タイミングの変更**: `compile.go`内のパスの順序が変更され、`zcse`パスが`cse`パスの前に実行されるようになりました。これにより、`zcse`がまず単純な共通部分式を除去し、その後に`cse`が残りのより複雑な共通部分式を除去するという、段階的な最適化が可能になります。
*   **`cse`の`required`フラグの変更**: `compile.go`で`cse`パスの`required`フラグが`true`から`false`に変更されています。これは、`zcse`が`OpSB`の結合という重要な役割を担うようになったため、`cse`自体が常に必須ではなくなったことを示唆している可能性があります。ただし、`cse`は依然として重要な最適化パスであるため、この変更の正確な意図は、コンパイラの他の部分との相互作用を考慮する必要があります。

### 3. パフォーマンスへの影響

コミットメッセージによると、この変更は`arithConst_ssa.go`のコンパイルを9%高速化する一方で、`"test -c net/http"`のコンパイルを1.5%遅くするとのことです。これは、新しいパスの導入によるオーバーヘッドと、最適化の順序変更による影響のトレードオフを示しています。しかし、全体としては、より多くのケースでパフォーマンスが向上すると判断されたため、この変更が採用されました。特に、`OpSB`の結合が`zcse`によって保証されることで、レジスタ割り当て（Regalloc）が混乱するのを防ぐという重要な副作用も指摘されています。

```diff
+package ssa

+// zcse does an initial pass of common-subexpression elimination on the
+// function for values with zero arguments to allow the more expensive cse
+// to begin with a reduced number of values. Values are just relinked,
+// nothing is deleted. A subsequent deadcode pass is required to actually
+// remove duplicate expressions.
+func zcse(f *Func) {
+	vals := make(map[vkey]*Value)
+
+	for _, b := range f.Blocks {
+		for i := 0; i < len(b.Values); {
+			v := b.Values[i]
+			next := true
+			switch v.Op {
+			case OpSB, OpConst64, OpConst32, OpConst16, OpConst8, OpConst64F,
+				OpConst32F, OpConstBool, OpConstNil, OpConstSlice, OpConstInterface:
+				key := vkey{v.Op, keyFor(v), typeStr(v)}
+				if vals[key] == nil {
+					vals[key] = v
+					if b != f.Entry {
+						// Move v to the entry block so it will dominate every block
+						// where we might use it. This prevents the need for any dominator
+						// calculations in this pass.
+						v.Block = f.Entry
+						f.Entry.Values = append(f.Entry.Values, v)
+						last := len(b.Values) - 1
+						b.Values[i] = b.Values[last]
+						b.Values[last] = nil
+						b.Values = b.Values[:last]
+
+						// process b.Values[i] again
+						next = false
+					}
+				}
+			}
+			if next {
+				i++
+			}
+		}
+	}
+
+	for _, b := range f.Blocks {
+		for _, v := range b.Values {
+			for i, a := range v.Args {
+				// TODO: encode arglen in the opcode table, then do this switch with a table lookup?
+				switch a.Op {
+				case OpSB, OpConst64, OpConst32, OpConst16, OpConst8, OpConst64F,
+					OpConst32F, OpConstBool, OpConstNil, OpConstSlice, OpConstInterface:
+					key := vkey{a.Op, keyFor(a), typeStr(a)}
+					if rv, ok := vals[key]; ok {
+						v.Args[i] = rv
+					}
+				}
+			}
+		}
+	}
+}
+
+// vkey is a type used to uniquely identify a zero arg value.
+type vkey struct {
+	op Op
+	a  int64  // aux
+	t  string // type
+}
+
+// typeStr returns a string version of the type of v.
+func typeStr(v *Value) string {
+	if v.Type == nil {
+		return ""
+	}
+	return v.Type.String()
+}
+
+// keyFor returns the AuxInt portion of a  key structure uniquely identifying a
+// zero arg value for the supported ops.
+func keyFor(v *Value) int64 {
+	switch v.Op {
+	case OpConst64, OpConst64F, OpConst32F:
+		return v.AuxInt
+	case OpConst32:
+		return int64(int32(v.AuxInt))
+	case OpConst16:
+		return int64(int16(v.AuxInt))
+	case OpConst8, OpConstBool:
+		return int64(int8(v.AuxInt))
+	default:
+		// Also matches OpSB, OpConstNil, OpConstSlice, OpConstInterface:
+		return 0
+	}
+}
```
- `zcse.go`という新しいファイルが追加され、`zcse`関数、`vkey`構造体、`typeStr`関数、`keyFor`関数が定義されています。
- `zcse`関数は、ゼロ引数値の共通部分式除去を実行します。
    - `vals`マップを使用して、既に処理されたゼロ引数値を追跡します。
    - ゼロ引数値が最初に見つかった場合、その値をエントリブロックに移動させ、関数全体で利用可能にします。
    - その後、他の値の引数として使用されている重複するゼロ引数値を、エントリブロックに移動された単一のインスタンスに置き換えます。
- `vkey`構造体は、オペレーション、補助情報、型に基づいてゼロ引数値を一意に識別するために使用されます。
- `typeStr`関数は、SSA値の型を文字列として返します。
- `keyFor`関数は、特定のオペレーション（定数など）の補助整数値を返します。

## コアとなるコードの解説

このコミットの主要な変更は、`zcse.go`に新しく追加された`zcse`関数とその関連ヘルパー関数です。

### `zcse` 関数

`zcse`関数は、GoコンパイラのSSAバックエンドにおいて、引数を持たないSSA値（ゼロ引数値）に特化した共通部分式除去（CSE）を実行します。

1.  **`vals := make(map[vkey]*Value)`**:
    *   `vkey`は、SSA値のオペレーション、補助情報（AuxInt）、および型を組み合わせて、ゼロ引数値を一意に識別するためのカスタム構造体です。
    *   `vals`マップは、既に処理され、共通部分式として特定されたゼロ引数値を格納するために使用されます。キーは`vkey`、値は対応する`*Value`（SSA値のポインタ）です。

2.  **最初のループ (`for _, b := range f.Blocks`)**:
    *   このループは、関数`f`内のすべての基本ブロック`b`を走査します。
    *   **`switch v.Op`**: 各ブロック内のSSA値`v`について、そのオペレーション`v.Op`がゼロ引数値のいずれか（`OpSB`, `OpConst64`, `OpConstNil`など）であるかをチェックします。
    *   **`key := vkey{v.Op, keyFor(v), typeStr(v)}`**: ゼロ引数値の場合、`vkey`を作成してその値を一意に識別します。`keyFor(v)`は定数などの補助整数値を返し、`typeStr(v)`は値の型を文字列で返します。
    *   **`if vals[key] == nil`**: もしこの`vkey`に対応するSSA値がまだ`vals`マップに登録されていない場合、それはそのゼロ引数値の最初のインスタンスであると見なされます。
        *   **`vals[key] = v`**: このSSA値`v`をマップに登録します。
        *   **エントリブロックへの移動**: `if b != f.Entry`の条件が真の場合、つまり現在のブロック`b`が関数のエントリブロックでない場合、このSSA値`v`を関数のエントリブロック`f.Entry`に移動させます。
            *   **なぜエントリブロックに移動させるのか？**: エントリブロックは、関数内のすべての他のブロックをドミネート（支配）します。つまり、エントリブロックで定義された値は、関数内のどこからでも到達可能です。これにより、`zcse`パスは複雑なドミネータ解析を行うことなく、このゼロ引数値が関数全体で共通して利用できることを保証できます。
            *   値の移動は、現在のブロック`b`から`v`を削除し、エントリブロック`f.Entry`の`Values`スライスに追加することで行われます。

3.  **2番目のループ (`for _, b := range f.Blocks`)**:
    *   このループは、再度関数`f`内のすべての基本ブロック`b`を走査します。
    *   **`for _, v := range b.Values`**: 各ブロック内のSSA値`v`について、その引数`a`を走査します。
    *   **`switch a.Op`**: 引数`a`のオペレーションがゼロ引数値のいずれかであるかをチェックします。
    *   **`key := vkey{a.Op, keyFor(a), typeStr(a)}`**: 引数`a`の`vkey`を作成します。
    *   **`if rv, ok := vals[key]; ok`**: もしこの`vkey`が`vals`マップに存在する場合（つまり、このゼロ引数値の共通部分式が既に特定されている場合）、その引数`a`をマップに登録されている既存のSSA値`rv`に置き換えます。
        *   **`v.Args[i] = rv`**: これにより、重複するゼロ引数値の参照が、エントリブロックに移動された単一のインスタンスにリダイレクトされます。

### ヘルパー関数 (`vkey`, `typeStr`, `keyFor`)

*   **`vkey`構造体**:
    ```go
    type vkey struct {
        op Op
        a  int64  // aux
        t  string // type
    }
    ```
    SSA値のオペレーション (`Op`)、補助情報 (`AuxInt`を`int64`に変換したもの)、および型 (`Type`の文字列表現) を組み合わせて、ゼロ引数値を一意に識別するためのキーとして機能します。

*   **`typeStr(v *Value) string`**:
    SSA値`v`の型を文字列として返します。型が`nil`の場合は空文字列を返します。

*   **`keyFor(v *Value) int64`**:
    特定のオペレーションを持つSSA値`v`の補助整数値（`AuxInt`）を`int64`として返します。これは、定数オペレーション（`OpConst64`など）の場合に、その定数値を`vkey`の一部として使用するために必要です。`OpSB`や`OpConstNil`など、補助情報を持たないゼロ引数値の場合は`0`を返します。

これらの変更により、Goコンパイラはゼロ引数値の共通部分式除去をより効率的に行えるようになり、特に定数や静的ベースポインタの扱いが改善され、コンパイル時間の短縮に貢献しています。

## 変更の背景

この変更の主な背景は、Goコンパイラ（`cmd/gc`）のパフォーマンス最適化です。特に、字句解析器が数値定数を処理する際に発生するメモリ割り当てのオーバーヘッドを削減することが目的でした。

コミットメッセージによると、この変更は「CL 5700」が適用された後、`rotate.go` テストの実行時に発生するアロケーションを約20%削減する効果がありました。これは、コンパイラのビルド時間や全体的なパフォーマンスに寄与する重要な改善です。

また、コミットメッセージでは、一般的な文字列結合パターン `s = "const str"; s += <another string>` が通常1つのアロケーションを節約できる可能性に言及しており、これは `rsc` の `grind` ツール（Goのプロファイリングツールの一つ）の対象となるかもしれないと示唆しています。しかし、このコミットは、それとは別に `lexbuf.String()` の呼び出し結果を再利用するという、より直接的な最適化を適用しています。これは、同じ文字列を複数回生成するのを避けることで、不要なメモリ割り当てを防ぐという意図があります。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **Goコンパイラ (`cmd/gc`)**: Go言語の公式コンパイラです。ソースコードを機械語に変換する役割を担います。コンパイルプロセスは、字句解析、構文解析、意味解析、中間コード生成、最適化、コード生成などの段階に分かれています。
2.  **字句解析器 (Lexer/Scanner)**: ソースコードを読み込み、意味のある最小単位（トークン）に分割するコンパイラの最初の段階です。例えば、`123` は数値定数トークン、`+` は演算子トークンとして認識されます。
3.  **数値定数**: プログラム内で直接記述される数値（例: `123`, `3.14`, `1e-5`）。字句解析器はこれらの文字列表現を内部的な数値型に変換します。
4.  **メモリ割り当て (Memory Allocation)**: プログラムが実行時にメモリを要求し、OSやランタイムからメモリ領域を確保する操作です。Goでは、`make` や `new`、あるいは文字列結合などの操作によってヒープメモリが割り当てられます。頻繁なメモリ割り当ては、ガベージコレクションの頻度を増やし、プログラムのパフォーマンスに悪影響を与える可能性があります。
5.  **`lexbuf` と `lexbuf.String()`**: Goコンパイラの字句解析器内部で使用されるバッファ（`lexbuf`）と、そのバッファの内容を文字列として取得するメソッド（`lexbuf.String()`）を指します。字句解析器は、ソースコードから読み込んだ文字を一時的にこのバッファに格納し、トークンが完成した時点でその内容を文字列として取り出します。`lexbuf.String()` は、バッファの内容から新しい文字列を生成するため、呼び出すたびにメモリ割り当てが発生する可能性があります。
6.  **文字列結合とメモリ割り当て**: Goにおいて、`+` 演算子を使った文字列結合は、新しい文字列を生成するためにメモリを割り当てることがあります。例えば、`s = "a" + "b"` のような単純なケースではコンパイル時に最適化されることもありますが、動的な文字列結合（例: `s += anotherString`）では、元の文字列と新しい文字列を格納するための新しいメモリ領域が確保されることが一般的です。これは、Goの文字列がイミュータブル（不変）であるためです。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの字句解析器 `src/cmd/internal/gc/lex.go` における、数値定数（整数、浮動小数点数、虚数）のパース処理の最適化です。

変更前は、`lexbuf.String()` メソッドが複数回呼び出されていました。例えば、数値定数をパースする際、その文字列表現は `mpatofix` (多倍長整数への変換) や `mpatoflt` (多倍長浮動小数点数への変換) といった関数に渡されるだけでなく、デバッグ目的で `litbuf` という文字列を構築するためにも使用されていました。

`lexbuf.String()` は、その性質上、呼び出されるたびに `lexbuf` の内容から新しい文字列を生成し、そのためにメモリを割り当てます。同じ数値定数の文字列表現が複数回必要とされる場合、そのたびに新しい文字列が生成され、不要なメモリ割り当てが発生していました。

このコミットでは、この重複する `lexbuf.String()` の呼び出しを排除するために、`str` という新しいローカル変数（`var str string`）を導入しています。

変更後のフローは以下のようになります。

1.  数値定数のパース処理の開始時に、一度だけ `str = lexbuf.String()` を呼び出し、その結果を `str` 変数に格納します。
2.  その後、`mpatofix` や `mpatoflt` などの数値変換関数に文字列を渡す際、および `litbuf` を構築する際に、この `str` 変数を再利用します。

さらに、`litbuf` の構築方法も最適化されています。変更前は `litbuf = "literal "; litbuf += lexbuf.String()` のように、2段階の文字列結合が行われていました。これは、`"literal "` と `lexbuf.String()` の結果を結合し、その結果を `litbuf` に代入するというプロセスで、中間的な文字列生成とメモリ割り当てが発生する可能性がありました。

変更後は `litbuf = "literal " + str` となり、これは単一の結合操作としてコンパイラによってより効率的に処理される可能性が高く、場合によっては中間的なアロケーションを避けることができます。Goのコンパイラは、コンパイル時に定数文字列の結合を最適化する能力を持っています。

これらの変更により、同じ数値定数の文字列表現を複数回取得するための重複したメモリ割り当てが削減され、結果としてコンパイラのパフォーマンスが向上しました。コミットメッセージにある「`rotate.go` テスト実行時のアロケーションを約20%削減」という効果は、この最適化の有効性を示しています。

さらに、`litbuf` の構築方法も最適化されています。変更前は `litbuf = "literal "; litbuf += lexbuf.String()` のように、2段階の文字列結合が行われていました。これは、`"literal "` と `lexbuf.String()` の結果を結合し、その結果を `litbuf` に代入するというプロセスで、中間的な文字列生成とメモリ割り当てが発生する可能性がありました。

変更後は `litbuf = "literal " + str` となり、これは単一の結合操作としてコンパイラによってより効率的に処理される可能性が高く、場合によっては中間的なアロケーションを避けることができます。Goのコンパイラは、コンパイル時に定数文字列の結合を最適化する能力を持っています。

これらの変更により、同じ数値定数の文字列表現を複数回取得するための重複したメモリ割り当てが削減され、結果としてコンパイラのパフォーマンスが向上しました。コミットメッセージにある「`rotate.go` テスト実行時のアロケーションを約20%削減」という効果は、この最適化の有効性を示しています。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は、以下の2点に集約されます。

1.  **`str` 変数の導入と `lexbuf.String()` の結果の再利用**:
    *   変更前は、`lexbuf.String()` が `mpatofix` (整数)、`mpatoflt` (浮動小数点数)、`mpatoflt` (虚数) の各関数に引数として渡される際、そして `litbuf` の構築のために、それぞれ独立して呼び出されていました。
    *   変更後、`_yylex` 関数の冒頭に `var str string` が追加されました。
    *   そして、数値定数をパースする各セクション（`ncu:`、`casei:`、`caseout:` ラベルの直後）で、最初に `str = lexbuf.String()` が呼び出され、`lexbuf` の内容が一度だけ文字列として取得され `str` に格納されます。
    *   以降、同じ数値定数の文字列表現が必要な箇所では、`lexbuf.String()` を直接呼び出す代わりに、この `str` 変数が使用されます。これにより、同じ文字列を複数回生成するための不要なメモリ割り当てが回避されます。

    例（整数定数の場合 - `ncu:` セクション）：
    ```go
    // 変更前
    // mpatofix(yylval.val.U.Xval, lexbuf.String()) // 1回目のアロケーション
    // ...
    // litbuf = "literal "
    // litbuf += lexbuf.String() // 2回目のアロケーション

    // 変更後
    str = lexbuf.String() // ここで1回だけアロケーション
    mpatofix(yylval.val.U.Xval, str)
    // ...
    litbuf = "literal " + str // 後述の最適化
    ```

2.  **文字列結合の最適化**:
    *   `litbuf` の構築において、変更前は `litbuf = "literal "; litbuf += lexbuf.String()` という2段階の結合が行われていました。これは、`"literal "` と `lexbuf.String()` の結果を結合し、その結果を `litbuf` に代入するというプロセスで、中間的な文字列生成とメモリ割り当てが発生する可能性がありました。
    *   変更後、これは `litbuf = "literal " + str` という単一の結合操作に簡略化されました。Goコンパイラは、このような定数文字列と変数の結合をより効率的に処理できることが多く、場合によっては中間的なアロケーションを避けることができます。これにより、さらにメモリ割り当ての削減に貢献します。

これらの変更は、Goコンパイラの字句解析フェーズにおけるメモリ効率を向上させ、特に数値定数が多く含まれるコードのコンパイル速度に良い影響を与えることが期待されます。

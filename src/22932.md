## 元コミット内容

`net: fix TestDialGoogle with -ipv6 when CGO_ENABLED=0`

外部ネットワーク接続を必要とする一部のダイヤルテストにおいて、アプリケーションのトラフィックは阻止しつつも、DNSメッセージ交換のようなコントロールプレーンのトラフィックは妨げてはならない。しかし、テストヘルパー関数`disableSocketConnect`は、アプリケーションとコントロールプレーンの両方のトラフィックを無条件に阻止するため、`CGO_ENABLED=0`の環境で`-ipv6`オプションを使用する一部のダイヤルテストが失敗していた。

この変更は、`disableSocketConnect`関数がアドレスファミリーだけでなくソケットタイプも考慮するようにすることで、`CGO_ENABLED=0`の環境で`-ipv6`オプションを使用する一部のダイヤルテストの失敗を修正する。

## 変更の背景

Go言語のネットワークテストスイートには、外部ネットワークへの接続をシミュレートしたり、特定の条件下でのネットワーク動作を検証したりするためのテストが含まれています。`TestDialGoogle`のようなテストは、実際にGoogleのサーバーに接続を試みることで、Goのネットワークスタックが正しく機能するかを確認します。

問題は、これらのテストが特定の条件下（`-ipv6`フラグが有効で、かつ`CGO_ENABLED=0`の場合）で失敗していたことです。テストヘルパー関数である`disableSocketConnect`は、テスト中に意図しないネットワーク接続が行われるのを防ぐために、ソケットの接続試行をブロックする役割を担っていました。しかし、この関数はアプリケーションのデータ通信だけでなく、DNS解決のような「コントロールプレーン」の通信までも無差別にブロックしてしまっていました。

DNS解決は、ドメイン名をIPアドレスに変換するために不可欠なプロセスであり、実際のアプリケーション通信が始まる前に必要となります。`CGO_ENABLED=0`の場合、GoはCgo（C言語との連携機能）を使用せず、純粋なGoで実装されたネットワークスタックとDNSリゾルバを使用します。この純粋なGoリゾルバも、DNSクエリを送信するためにソケット接続を必要とします。

したがって、`disableSocketConnect`がDNSクエリのためのソケット接続までブロックしてしまうと、テストはドメイン名を解決できず、結果として接続に失敗し、テストが不合格になっていました。このコミットは、この過剰なブロックを修正し、テストが正しく実行されるようにすることを目的としています。

## 前提知識の解説

### `CGO_ENABLED=0`

`CGO_ENABLED`はGoのビルド時に使用される環境変数です。
*   **`CGO_ENABLED=1` (デフォルト)**: Cgoが有効になり、GoプログラムはC言語で書かれたライブラリ（例: システムのC標準ライブラリ`glibc`）を呼び出すことができます。ネットワーク操作やDNS解決は、通常、OSのネイティブなCライブラリを介して行われます。これにより、OSの高度なネットワーク機能や設定（例: `/etc/nsswitch.conf`による名前解決順序のカスタマイズ）を利用できます。
*   **`CGO_ENABLED=0`**: Cgoが無効になります。この場合、GoコンパイラはCライブラリにリンクしない純粋なGoバイナリを生成します。ネットワーク操作やDNS解決も、Go言語自体で実装された「純粋なGo」のネットワークスタックとDNSリゾルバが使用されます。これにより、生成されるバイナリは完全に自己完結型となり、移植性が高まります（特にDockerの`scratch`イメージのような最小限の環境で有用）。しかし、OSのネイティブなリゾルバが提供するすべての機能や設定に対応しているわけではない場合があります。

今回の問題は、`CGO_ENABLED=0`の環境下で、Goの純粋なGo DNSリゾルバがソケット接続を試みる際に、`disableSocketConnect`によってブロックされてしまうことに起因していました。

### `socktest`パッケージ

`socktest`はGoの`net`パッケージ内部で使用されるテストユーティリティパッケージ（`net/internal/socktest`）です。これは、ソケット関連のシステムコールをインターセプトし、テスト目的でその動作を制御するために設計されています。

*   **目的**: ネットワーク操作の低レベルな動作（ソケットの作成、接続、読み書きなど）をテスト中にシミュレートしたり、エラーを注入したりするために使用されます。
*   **機能**: `socktest.FilterConnect`のようなフィルターを設定することで、特定のソケット操作（例: `connect`システムコール）が実行される前後にカスタムロジックを挿入できます。これにより、テスト中に意図的に接続を失敗させたり、特定の条件でのみ接続を許可したりといった制御が可能になります。
*   **`socktest.Status`**: ソケットの状態に関する情報（アドレスファミリー、ソケットタイプなど）を保持する構造体です。`so.Cookie.Family()`でアドレスファミリー（例: `syscall.AF_INET`）を、`so.Cookie.Type()`でソケットタイプ（例: `syscall.SOCK_STREAM`）を取得できます。

### アドレスファミリーとソケットタイプ

ソケットプログラミングにおける基本的な概念です。
*   **アドレスファミリー (Address Family)**: ネットワークプロトコルの種類を示します。
    *   `syscall.AF_INET`: IPv4プロトコルファミリー。
    *   `syscall.AF_INET6`: IPv6プロトコルファミリー。
*   **ソケットタイプ (Socket Type)**: ソケットが提供する通信サービスのタイプを示します。
    *   `syscall.SOCK_STREAM`: ストリームソケット。通常、TCPプロトコルで使用され、信頼性のあるコネクション指向のデータ転送を提供します。
    *   `syscall.SOCK_DGRAM`: データグラムソケット。通常、UDPプロトコルで使用され、コネクションレスで信頼性の保証がないデータ転送を提供します。
    *   `syscall.SOCK_RAW`: ローソケット。IPヘッダを含む生（raw）のネットワークパケットに直接アクセスするために使用されます。

### コントロールプレーンとアプリケーション（データ）プレーン

ネットワーク通信は大きく2つのカテゴリに分けられます。
*   **コントロールプレーン (Control Plane)**: ネットワークの制御や管理に関する通信です。ルーティング情報の交換、名前解決（DNS）、ネットワーク設定の取得などが含まれます。これらの通信は、実際のアプリケーションデータが送受信される前に、ネットワークが正しく機能するための基盤を構築します。
*   **アプリケーション（データ）プレーン (Application/Data Plane)**: 実際のユーザーデータやアプリケーションデータが送受信される通信です。Webブラウジング、ファイル転送、ビデオストリーミングなど、ユーザーが直接利用するサービスに関連するデータが流れます。

今回の問題では、`disableSocketConnect`がコントロールプレーン（DNS解決）の通信までブロックしてしまい、アプリケーションプレーンの通信（`TestDialGoogle`が試みるGoogleへの接続）が開始できない状態になっていました。

## 技術的詳細

修正前の`disableSocketConnect`関数は、`socktest.FilterConnect`を使用してソケットの接続試行をインターセプトしていました。このフィルターは、ソケットの「アドレスファミリー」のみをチェックし、そのソケットがIPv4 (`AF_INET`) またはIPv6 (`AF_INET6`) のどちらであるかに基づいて接続をブロックしていました。

具体的には、`network`引数（例: `"tcp4"`, `"udp6"`, `"ip4"`）に応じて、対応するアドレスファミリーのソケット接続を`syscall.EHOSTUNREACH`エラー（ホストに到達できない）で即座に失敗させていました。

しかし、DNS解決は通常、UDPプロトコル（`SOCK_DGRAM`）を使用します。修正前のコードでは、例えば`"udp4"`や`"udp6"`が指定された場合、対応するアドレスファミリーのソケットであれば、ソケットタイプが何であっても（つまり、DNSクエリのためのUDPソケットであっても）ブロックしてしまっていました。

このコミットによる修正は、`disableSocketConnect`がソケットの接続をブロックする際に、アドレスファミリーだけでなく「ソケットタイプ」も考慮するように変更しました。これにより、TCP (`SOCK_STREAM`) やUDP (`SOCK_DGRAM`)、Raw IP (`SOCK_RAW`) といった特定のソケットタイプにのみブロックを適用できるようになります。

例えば、`"tcp4"`が指定された場合、修正後は`AF_INET`かつ`SOCK_STREAM`のソケットのみがブロックされます。これにより、同じ`AF_INET`でも`SOCK_DGRAM`であるDNSクエリのためのソケットはブロックされなくなり、DNS解決が正常に行われるようになります。結果として、`CGO_ENABLED=0`環境下での`TestDialGoogle`のようなテストが、DNS解決の失敗によって不合格になることがなくなりました。

この変更は、テストの正確性を向上させるとともに、Goのネットワークテストがより現実的なシナリオを反映できるようにするための重要な改善です。

## コアとなるコードの解説

修正前は、`switch ss[0]`の各`case`（例: `"tcp4"`, `"udp4"`, `"ip4"`）内で、単に`so.Cookie.Family()`（アドレスファミリー）のみをチェックしていました。

```go
// 修正前
case "tcp4", "udp4", "ip4":
    if so.Cookie.Family() == syscall.AF_INET {
        return nil, syscall.EHOSTUNREACH
    }
```

このコードは、`network`が`"tcp4"`、`"udp4"`、`"ip4"`のいずれであっても、IPv4 (`AF_INET`) のソケットであれば無条件にブロックしていました。これは、例えば`"udp4"`が指定された場合でも、TCPソケットやRaw IPソケットがIPv4であればブロックされることを意味します。そして、より重要なのは、`"tcp4"`が指定された場合でも、DNS解決に使用されるUDPソケット（`SOCK_DGRAM`）がIPv4であればブロックされてしまう点です。

修正後は、各`case`がより具体的に分割され、`so.Cookie.Type()`（ソケットタイプ）も同時にチェックするようになりました。

```go
// 修正後
case "tcp4":
    if so.Cookie.Family() == syscall.AF_INET && so.Cookie.Type() == syscall.SOCK_STREAM {
        return nil, syscall.EHOSTUNREACH
    }
case "udp4":
    if so.Cookie.Family() == syscall.AF_INET && so.Cookie.Type() == syscall.SOCK_DGRAM {
        return nil, syscall.EHOSTUNREACH
    }
case "ip4":
    if so.Cookie.Family() == syscall.AF_INET && so.Cookie.Type() == syscall.SOCK_RAW {
        return nil, syscall.EHOSTUNREACH
    }
// 同様にIPv6についても修正
```

この変更により、例えば`"tcp4"`が指定された場合は、`AF_INET`かつ`SOCK_STREAM`（TCPソケット）のみがブロックされるようになります。`"udp4"`が指定された場合は、`AF_INET`かつ`SOCK_DGRAM`（UDPソケット）のみがブロックされます。

これにより、`TestDialGoogle`が`"tcp4"`や`"tcp6"`のネットワークタイプで実行されている場合でも、DNS解決のために内部的に使用されるUDPソケット（`SOCK_DGRAM`）はブロックされなくなります。DNS解決が成功すれば、テストは正しくターゲットホストのIPアドレスを取得し、その後のTCP接続試行に進むことができるため、テストの失敗が解消されます。

この修正は、テストの意図（アプリケーショントラフィックのみをブロックし、コントロールプレーンは許可する）を正確に反映するための重要な変更であり、Goのネットワークテストの堅牢性を高めるものです。

`CGO_ENABLED`はGoのビルド時に使用される環境変数です。
*   **`CGO_ENABLED=1` (デフォルト)**: Cgoが有効になり、GoプログラムはC言語で書かれたライブラリ（例: システムのC標準ライブラリ`glibc`）を呼び出すことができます。ネットワーク操作やDNS解決は、通常、OSのネイティブなCライブラリを介して行われます。これにより、OSの高度なネットワーク機能や設定（例: `/etc/nsswitch.conf`による名前解決順序のカスタマイズ）を利用できます。
*   **`CGO_ENABLED=0`**: Cgoが無効になります。この場合、GoコンパイラはCライブラリにリンクしない純粋なGoバイナリを生成します。ネットワーク操作やDNS解決も、Go言語自体で実装された「純粋なGo」のネットワークスタックとDNSリゾルバが使用されます。これにより、生成されるバイナリは完全に自己完結型となり、移植性が高まります（特にDockerの`scratch`イメージのような最小限の環境で有用）。しかし、OSのネイティブなリゾルバが提供するすべての機能や設定に対応しているわけではない場合があります。

今回の問題は、`CGO_ENABLED=0`の環境下で、Goの純粋なGo DNSリゾルバがソケット接続を試みる際に、`disableSocketConnect`によってブロックされてしまうことに起因していました。

### `socktest`パッケージ

`socktest`はGoの`net`パッケージ内部で使用されるテストユーティリティパッケージ（`net/internal/socktest`）です。これは、ソケット関連のシステムコールをインターセプトし、テスト目的でその動作を制御するために設計されています。

*   **目的**: ネットワーク操作の低レベルな動作（ソケットの作成、接続、読み書きなど）をテスト中にシミュレートしたり、エラーを注入したりするために使用されます。
*   **機能**: `socktest.FilterConnect`のようなフィルターを設定することで、特定のソケット操作（例: `connect`システムコール）が実行される前後にカスタムロジックを挿入できます。これにより、テスト中に意図的に接続を失敗させたり、特定の条件でのみ接続を許可したりといった制御が可能になります。
*   **`socktest.Status`**: ソケットの状態に関する情報（アドレスファミリー、ソケットタイプなど）を保持する構造体です。`so.Cookie.Family()`でアドレスファミリー（例: `syscall.AF_INET`）を、`so.Cookie.Type()`でソケットタイプ（例: `syscall.SOCK_STREAM`）を取得できます。

### アドレスファミリーとソケットタイプ

ソケットプログラミングにおける基本的な概念です。
*   **アドレスファミリー (Address Family)**: ネットワークプロトコルの種類を示します。
    *   `syscall.AF_INET`: IPv4プロトコルファミリー。
    *   `syscall.AF_INET6`: IPv6プロトコルファミリー。
*   **ソケットタイプ (Socket Type)**: ソケットが提供する通信サービスのタイプを示します。
    *   `syscall.SOCK_STREAM`: ストリームソケット。通常、TCPプロトコルで使用され、信頼性のあるコネクション指向のデータ転送を提供します。
    *   `syscall.SOCK_DGRAM`: データグラムソケット。通常、UDPプロトコルで使用され、コネクションレスで信頼性の保証がないデータ転送を提供します。
    *   `syscall.SOCK_RAW`: ローソケット。IPヘッダを含む生（raw）のネットワークパケットに直接アクセスするために使用されます。

### コントロールプレーンとアプリケーション（データ）プレーン

ネットワーク通信は大きく2つのカテゴリに分けられます。
*   **コントロールプレーン (Control Plane)**: ネットワークの制御や管理に関する通信です。ルーティング情報の交換、名前解決（DNS）、ネットワーク設定の取得などが含まれます。これらの通信は、実際のアプリケーションデータが送受信される前に、ネットワークが正しく機能するための基盤を構築します。
*   **アプリケーション（データ）プレーン (Application/Data Plane)**: 実際のユーザーデータやアプリケーションデータが送受信される通信です。Webブラウジング、ファイル転送、ビデオストリーミングなど、ユーザーが直接利用するサービスに関連するデータが流れます。

今回の問題では、`disableSocketConnect`がコントロールプレーン（DNS解決）の通信までブロックしてしまい、アプリケーションプレーンの通信（`TestDialGoogle`が試みるGoogleへの接続）が開始できない状態になっていました。

## 技術的詳細

修正前の`disableSocketConnect`関数は、`socktest.FilterConnect`を使用してソケットの接続試行をインターセプトしていました。このフィルターは、ソケットの「アドレスファミリー」のみをチェックし、そのソケットがIPv4 (`AF_INET`) またはIPv6 (`AF_INET6`) のどちらであるかに基づいて接続をブロックしていました。

具体的には、`network`引数（例: `"tcp4"`, `"udp6"`, `"ip4"`）に応じて、対応するアドレスファミリーのソケット接続を`syscall.EHOSTUNREACH`エラー（ホストに到達できない）で即座に失敗させていました。

しかし、DNS解決は通常、UDPプロトコル（`SOCK_DGRAM`）を使用します。修正前のコードでは、例えば`"udp4"`や`"udp6"`が指定された場合、対応するアドレスファミリーのソケットであれば、ソケットタイプが何であっても（つまり、DNSクエリのためのUDPソケットであっても）ブロックしてしまっていました。

このコミットによる修正は、`disableSocketConnect`がソケットの接続をブロックする際に、アドレスファミリーだけでなく「ソケットタイプ」も考慮するように変更しました。これにより、TCP (`SOCK_STREAM`) やUDP (`SOCK_DGRAM`)、Raw IP (`SOCK_RAW`) といった特定のソケットタイプにのみブロックを適用できるようになります。

例えば、`"tcp4"`が指定された場合、修正後は`AF_INET`かつ`SOCK_STREAM`のソケットのみがブロックされます。これにより、同じ`AF_INET`でも`SOCK_DGRAM`であるDNSクエリのためのソケットはブロックされなくなり、DNS解決が正常に行われるようになります。結果として、`CGO_ENABLED=0`環境下での`TestDialGoogle`のようなテストが、DNS解決の失敗によって不合格になることがなくなりました。

この変更は、テストの正確性を向上させるとともに、Goのネットワークテストがより現実的なシナarioを反映できるようにするための重要な改善です。

## コアとなるコードの解説

修正前は、`switch ss[0]`の各`case`（例: `"tcp4"`, `"udp4"`, `"ip4"`）内で、単に`so.Cookie.Family()`（アドレスファミリー）のみをチェックしていました。

```go
// 修正前
case "tcp4", "udp4", "ip4":
    if so.Cookie.Family() == syscall.AF_INET {
        return nil, syscall.EHOSTUNREACH
    }
```

このコードは、`network`が`"tcp4"`、`"udp4"`、`"ip4"`のいずれであっても、IPv4 (`AF_INET`) のソケットであれば無条件にブロックしていました。これは、例えば`"udp4"`が指定された場合でも、TCPソケットやRaw IPソケットがIPv4であればブロックされることを意味します。そして、より重要なのは、`"tcp4"`が指定された場合でも、DNS解決に使用されるUDPソケット（`SOCK_DGRAM`）がIPv4であればブロックされてしまう点です。

修正後は、各`case`がより具体的に分割され、`so.Cookie.Type()`（ソケットタイプ）も同時にチェックするようになりました。

```go
// 修正後
case "tcp4":
    if so.Cookie.Family() == syscall.AF_INET && so.Cookie.Type() == syscall.SOCK_STREAM {
        return nil, syscall.EHOSTUNREACH
    }
case "udp4":
    if so.Cookie.Family() == syscall.AF_INET && so.Cookie.Type() == syscall.SOCK_DGRAM {
        return nil, syscall.EHOSTUNREACH
    }
case "ip4":
    if so.Cookie.Family() == syscall.AF_INET && so.Cookie.Type() == syscall.SOCK_RAW {
        return nil, syscall.EHOSTUNREACH
    }
// 同様にIPv6についても修正
```

この変更により、例えば`"tcp4"`が指定された場合は、`AF_INET`かつ`SOCK_STREAM`（TCPソケット）のみがブロックされるようになります。`"udp4"`が指定された場合は、`AF_INET`かつ`SOCK_DGRAM`（UDPソケット）のみがブロックされます。

これにより、`TestDialGoogle`が`"tcp4"`や`"tcp6"`のネットワークタイプで実行されている場合でも、DNS解決のために内部的に使用されるUDPソケット（`SOCK_DGRAM`）はブロックされなくなります。DNS解決が成功すれば、テストは正しくターゲットホストのIPアドレスを取得し、その後のTCP接続試行に進むことができるため、テストの失敗が解消されます。

この修正は、テストの意図（アプリケーショントラフィックのみをブロックし、コントロールプレーンは許可する）を正確に反映するための重要な変更であり、Goのネットワークテストの堅牢性を高めるものです。

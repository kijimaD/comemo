## 変更の背景

Go言語の初期のランタイムは、パフォーマンスが要求される部分やOSとのインタフェース部分でC言語が多用されていました。特に、ランタイムのコアとなる定義や構造体は`runtime.h`というCヘッダーファイルに記述されていました。しかし、GoプロジェクトはC言語への依存を減らし、ランタイム全体をGo言語で記述する方向へと移行を進めていました。これは、Goのツールチェインの簡素化、クロスコンパイルの容易化、そしてGo言語の安全性と表現力をランタイムコードにも適用するためです。

この移行の一環として、`runtime.h`はGoのソースファイル（例えば`runtime2.go`など）に変換されました。この変換プロセス中に、一部の重要なコメントが元のCヘッダーファイルから新しいGoのソースファイルへ適切に移行されず、「孤立した」状態になっていました。これらのコメントは、特定のデータ構造や関数の設計意図、あるいは重要な制約を説明するものであり、コードの理解には不可欠です。

本コミットは、この「孤立したコメント」を特定し、それらが本来説明すべきGoのコードの近くに移動させることで、ランタイムコードのドキュメントとしての価値を高め、将来のメンテナンスを容易にすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムに関する基本的な知識が役立ちます。

1.  **Goランタイム (Go Runtime)**:
    Goプログラムは、OS上で直接実行されるわけではなく、Goランタイムと呼ばれる軽量な実行環境上で動作します。ランタイムは、ガベージコレクション、ゴルーチン（軽量スレッド）のスケジューリング、メモリ管理、チャネル通信、システムコールとのインタフェースなど、Go言語の並行性モデルとメモリ安全性を実現するための多くの低レベルな機能を提供します。ランタイムのコードは、Go言語とアセンブリ言語で書かれています。

2.  **`runtime.h`からGoへの変換**:
    Goの初期バージョンでは、ランタイムの一部がC言語で書かれており、その定義は`runtime.h`のようなCヘッダーファイルにありました。Goプロジェクトは、C言語への依存を減らすために、これらのCコードをGo言語に書き換える作業を進めてきました。このプロセスは、Goランタイムの自己完結性を高め、Goコンパイラとツールチェインの複雑さを軽減する上で重要でした。

3.  **`lfstack.go` (Lock-Free Stack)**:
    ロックフリースタックは、複数のゴルーチンが同時にアクセスしても、ロック機構を使わずに正しく動作するデータ構造です。Goランタイムでは、特定の内部処理（例えば、M（OSスレッド）がP（プロセッサ）から切り離された際に、Pを解放されたPのリストに追加するなど）で、競合を最小限に抑えつつ高速な操作を実現するために使用されます。コメントは、スタックの初期化方法や、ノードへのポインタを保持しないためガベージコレクションが可能であることなど、その設計上の特性を説明しています。

4.  **`lock_futex.go` (Futex-based Locks)**:
    Futex (Fast Userspace muTEX) は、Linuxカーネルが提供する同期プリミティブです。ユーザー空間でロックの競合が発生しない場合は高速に処理し、競合が発生した場合のみカーネルに介入を求めることで、効率的なロックを実現します。Goランタイムのミューテックス（`mutex`）の実装の一部で利用され、ゴルーチンのスリープ/ウェイクアップを制御します。コメントは、`futexsleep`と`futexwakeup`というOS固有の関数（アセンブリで実装されることが多い）のセマンティクスを説明しています。

5.  **`mmap.go` (Memory Mapping)**:
    `mmap`は、ファイルやデバイスをプロセスのアドレス空間にマッピングするためのシステムコールです。Goランタイムでは、メモリ管理（ヒープ領域の確保など）のために`mmap`を利用します。コメントは、`mmap`システムコールを呼び出すアセンブリルーチンにファイルオフセットの下位32ビットのみを渡すという実装の詳細を説明しています。

6.  **`runtime2.go`**:
    このファイルは、Goランタイムの主要なデータ構造や定数、型定義の多くを含む、非常に重要なファイルです。`G`（ゴルーチン）、`P`（プロセッサ）、`M`（OSスレッド）の状態定義、`mutex`、`note`、`_defer`、`_panic`、`stkframe`などのランタイム内部構造が定義されています。このコミットでは、特に多くのコメントがこのファイルに移動されています。

7.  **`mutex`と`note`**:
    *   **`mutex`**: Goランタイム内部で使用される相互排他ロックです。ユーザーが`sync.Mutex`として利用するものとは異なり、ランタイムの低レベルな同期に使用されます。コメントは、競合がない場合はスピンロックのように高速であり、競合時にはカーネルでスリープすること、およびゼロ値の`mutex`がアンロック状態であることを説明しています。
    *   **`note`**: Goランタイム内部のワンタイムイベント（一度だけ発生するイベント）のスリープ/ウェイクアップ機構です。例えば、ゴルーチンが特定のイベントを待機し、そのイベントが発生したらウェイクアップするといった用途に使われます。コメントは、`noteclear`、`notesleep`、`notewakeup`といった関連関数の使用シーケンスとセマンティクスを詳細に説明しています。

## 技術的詳細

このコミットの技術的詳細は、主にコメントの再配置とその影響にあります。

1.  **コメントの出所**:
    コミットメッセージにある通り、これらのコメントは元々C言語の`runtime.h`に存在していました。`runtime.h`がGo言語のファイルに変換された際、コメントがコードから切り離されてしまっていた状態でした。

2.  **コメントの移動先**:
    コミットの差分を見ると、コメントは以下のGoソースファイルに移動されています。
    *   `src/runtime/lfstack.go`
    *   `src/runtime/lock_futex.go`
    *   `src/runtime/mmap.go`
    *   `src/runtime/runtime2.go`

    これらのファイルは、Goランタイムの異なる側面（ロックフリーデータ構造、OS同期プリミティブ、メモリ管理、主要なランタイム構造体）を扱っており、移動されたコメントはそれぞれのファイル内の関連するコードブロックの直前に配置されています。

3.  **コメントの内容と意義**:
    移動されたコメントは、単なる説明文ではなく、Goランタイムの設計上の重要な決定、制約、または使用方法に関する詳細な情報を含んでいます。
    *   `lfstack.go`のコメントは、ロックフリースタックの初期化とガベージコレクションの可能性について言及しています。これは、スタックの実装がどのようにメモリ管理と連携するかを理解する上で重要です。
    *   `lock_futex.go`のコメントは、`futexsleep`と`futexwakeup`という低レベルな同期プリミティブの正確なセマンティクスを定義しています。これは、これらの関数がどのように動作し、どのような条件でゴルーチンがスリープ/ウェイクアップするかを理解するために不可欠です。特に、`*addr == val`という条件でのスリープや、`cnt`個までのウェイクアップといった詳細が記述されています。
    *   `mmap.go`のコメントは、`mmap`システムコールのアセンブリ実装への引数渡しに関する特定の最適化（ファイルオフセットの下位32ビットのみを渡す）を説明しています。
    *   `runtime2.go`では、`mutex`、`note`、`_defer`、`_panic`、`stkframe`といったGoランタイムの核心的なデータ構造に関する詳細な説明が、それぞれの構造体の定義の直前に配置されています。これにより、これらの構造体の目的、使用方法、および内部的な動作原理が、コードを読む開発者にとって一目でわかるようになります。例えば、`note`のコメントは、`noteclear`、`notesleep`、`notewakeup`の呼び出し順序や、`notetsleep`のタイムアウト動作に関する複雑なルールを明確にしています。

4.  **コードの可読性とメンテナンス性への影響**:
    コメントが関連するコードの近くに配置されることで、コードの意図を理解するために複数のファイルを行き来する必要がなくなります。これは、特にGoランタイムのような複雑で低レベルなコードベースにおいて、新しい開発者がコードを理解する際の障壁を大幅に低減します。また、将来的にコードが変更される際にも、関連するコメントがすぐに見つかるため、コメントとコードの乖離を防ぎ、メンテナンス性を向上させます。

## コアとなるコードの解説

このコミットの「コアとなるコード」は、コメントそのものであり、それらが配置されたGoのソースファイル内の特定の構造体や定数の定義です。

*   **`src/runtime/lfstack.go`**:
    ```go
    // Lock-free stack.
    // Initialize head to 0, compare with 0 to test for emptiness.
    // The stack does not keep pointers to nodes,
    // so they can be garbage collected if there are no other pointers to nodes.
    // The following code runs only on g0 stack.
    package runtime
    ```
    このコメントは、`runtime`パッケージのロックフリースタックの基本的な動作原理と、Goのガベージコレクタとの相互作用について説明しています。スタックの`head`が0で初期化され、空かどうかをテストするために0と比較されること、そしてスタック自体がノードへのポインタを保持しないため、他のポインタが存在しない限りノードがガベージコレクションの対象となることが明記されています。

*   **`src/runtime/lock_futex.go`**:
    ```go
    // This implementation depends on OS-specific implementations of
    //
    //	futexsleep(addr *uint32, val uint32, ns int64)
    //		Atomically,
    //		if *addr == val { sleep }
    //		Might be woken up spuriously; that's allowed.
    //		Don't sleep longer than ns; ns < 0 means forever.
    //
    //	futexwakeup(addr *uint32, cnt uint32)
    //		If any procs are sleeping on addr, wake up at most cnt.
    ```
    このコメントは、Goランタイムが依存するOS固有の`futexsleep`と`futexwakeup`関数の厳密なセマンティクスを定義しています。特に、`futexsleep`がアトミックに`*addr == val`をチェックしてスリープすること、偽のウェイクアップが許容されること、タイムアウトの挙動が説明されています。`futexwakeup`についても、最大`cnt`個のプロセスをウェイクアップすることが示されています。

*   **`src/runtime/mmap.go`**:
    ```go
    // mmap calls the mmap system call. It is implemented in assembly.
    // We only pass the lower 32 bits of file offset to the
    // assembly routine; the higher bits (if required), should be provided
    // by the assembly routine as 0.
    func mmap(addr unsafe.Pointer, n uintptr, prot, flags, fd int32, off uint32) unsafe.Pointer
    ```
    このコメントは、`mmap`システムコールを呼び出すアセンブリルーチンへの引数渡しに関する実装の詳細を説明しています。ファイルオフセットの下位32ビットのみが渡され、上位ビットはアセンブリルーチンによって0として提供されるという、低レベルな最適化または制約が記述されています。

*   **`src/runtime/runtime2.go`**:
    このファイルでは、多くのコメントが移動・再配置されていますが、特に重要なのは`mutex`と`note`構造体に関するものです。

    ```go
    // Mutual exclusion locks. In the uncontended case,
    // as fast as spin locks (just a few user-level instructions),
    // but on the contention path they sleep in the kernel.
    // A zeroed Mutex is unlocked (no need to initialize each lock).
    type mutex struct {
    	// Futex-based impl treats it as uint32 key,
    	// while sema-based impl as M* waitm.
    	key uintptr
    }
    ```
    `mutex`構造体の直前に配置されたこのコメントは、Goランタイム内部のミューテックスの性能特性（競合なしでは高速なスピンロック、競合ありではカーネルスリープ）と、ゼロ値の`mutex`がアンロック状態であるという重要な初期化ルールを説明しています。

    ```go
    // sleep and wakeup on one-time events.
    // before any calls to notesleep or notewakeup,
    // must call noteclear to initialize the Note.
    // then, exactly one thread can call notesleep
    // and exactly one thread can call notewakeup (once).
    // once notewakeup has been called, the notesleep
    // will return. future notesleep will return immediately.
    // subsequent noteclear must be called only after
    // previous notesleep has returned, e.g. it's disallowed
    // to call noteclear straight after notewakeup.
    //
    // notetsleep is like notesleep but wakes up after
    // a given number of nanoseconds even if the event
    // has not yet happened. if a goroutine uses notetsleep to
    // wake up early, it must wait to call noteclear until it
    // can be sure that no other goroutine is calling
    // notewakeup.
    //
    // notesleep/notetsleep are generally called on g0,
    // notetsleepg is similar to notetsleep but is called on user g.
    type note struct {
    	// Futex-based impl treats it as uint32 key,
    	// while sema-based impl as M* waitm.
    	key uintptr
    }
    ```
    `note`構造体の直前のこの長いコメントは、Goランタイムのワンタイムイベント同期プリミティブである`note`の複雑なライフサイクルと使用規則を詳細に説明しています。`noteclear`、`notesleep`、`notewakeup`の呼び出し順序、`notetsleep`のタイムアウト挙動、そして`g0`（システムゴルーチン）とユーザーゴルーチンでの使用の違いが明確にされています。

これらのコメントの再配置は、Goランタイムの内部動作を理解しようとする開発者にとって、非常に価値のあるドキュメントとして機能します。

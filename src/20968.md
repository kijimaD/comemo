## 元コミット内容

`cmd/cgo: avoid worklist nondeterminism.`

このコミットは、`cmd/cgo`ツールが内部的に使用するワークリストの処理順序が非決定論的であった問題を修正します。これにより、Cgoが生成するコード（特に型名）の決定性が保証されます。回帰テストも追加されています。

## 変更の背景

Go言語の`cgo`ツールは、GoプログラムからC言語のコードを呼び出す（またはその逆）ためのメカニズムを提供します。`cgo`は、Cの型定義をGoの型にマッピングし、GoとCの間でデータをやり取りするための接着コードを生成します。

このコミットが修正する問題は、Go Issue 9026として報告されました。この問題は、`cgo`がCの構造体やその他の複雑な型をGoの型に変換する際に、内部的な処理順序が実行ごとに異なるために、生成されるGoの型名が非決定論的になるというものでした。具体的には、`_Ctype_struct___12`や`_Ctype_struct___13`のような匿名構造体や不完全な型に対するGoの型名が、`cgo`の実行ごとに異なる順序で生成される可能性がありました。

このような非決定性は、ビルドシステムやテストの再現性に悪影響を及ぼします。例えば、CI/CDパイプラインで同じソースコードをビルドしても、`cgo`が生成するコードが異なるため、ハッシュ値が一致しなかったり、テストが不安定になったりする可能性があります。開発者にとっては、同じコードベースでもビルド結果が異なるという混乱を招く原因となります。

この問題の根本原因は、`cgo`の型変換ロジック内で使用されるワークリスト（`map`をイテレートして処理対象の型を取得する部分）が、Goの`map`のイテレーション順序が保証されないという特性に依存していたことにありました。Goの`map`は意図的にイテレーション順序が非決定論的であり、これはランタイムの最適化やハッシュ衝突の回避などの目的のためです。しかし、この特性が`cgo`の出力に影響を与え、非決定性を引き起こしていました。

## 前提知識の解説

1.  **`cmd/cgo`**:
    *   Go言語の標準ツールチェーンの一部であり、GoプログラムとC言語のコードを相互運用するための機能を提供します。
    *   Goのソースファイル内に`import "C"`という特殊なインポート文があると、`cgo`が起動されます。
    *   `cgo`は、Cのヘッダファイルやソースコードを解析し、GoからC関数を呼び出すためのスタブ関数や、Cの型をGoの型にマッピングするコードを生成します。
    *   生成されたGoコードは、通常のGoコンパイラによってコンパイルされます。

2.  **非決定性 (Nondeterminism)**:
    *   コンピュータサイエンスにおいて、同じ入力に対して異なる出力や異なる実行パスを生成するシステムの特性を指します。
    *   ソフトウェア開発においては、ビルドの再現性、テストの安定性、デバッグの容易性などの観点から、非決定性は一般的に避けられるべきです。
    *   Goの`map`のイテレーション順序が非決定論的であることは、意図的な設計決定です。これは、開発者が特定の順序に依存しないように促し、将来のGoバージョンの`map`実装の変更に対する柔軟性を確保するためです。

3.  **ワークリスト (Worklist Algorithm)**:
    *   グラフ探索やデータフロー解析など、多くのアルゴリズムで用いられる一般的なデータ構造およびパターンです。
    *   処理すべき要素の集合を保持し、アルゴリズムはワークリストから要素を取り出して処理し、必要に応じて新しい要素をワークリストに追加します。
    *   ワークリストから要素を取り出す順序がアルゴリズムの挙動に影響を与える場合、その順序が決定論的であるかどうかが重要になります。特に、並行処理や分散システムでは、ワークリストの順序が結果の決定性に影響を与えることがあります。

4.  **不完全な型 (Incomplete Types) と匿名構造体 (Anonymous Structs)**:
    *   C言語では、構造体の定義が完全でなくても、その構造体へのポインタを宣言することができます。これを「不完全な型」と呼びます（例: `struct MyStruct;` の後に `struct MyStruct *ptr;`）。
    *   `cgo`は、Cのヘッダファイルを解析する際に、このような不完全な型や、名前を持たない匿名構造体（特に`typedef struct {}`のような形式で定義されるもの）に遭遇することがあります。
    *   `cgo`は、これらのCの型に対応するGoの型を生成する必要がありますが、その際に内部的に一意な名前を割り当てます。この名前の生成が非決定論的であったことが問題でした。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/cgo/gcc.go`ファイル内の`typeConv`構造体と、その`FinishType`メソッドの変更にあります。

`typeConv`構造体は、Cの型をGoの型に変換するプロセスを管理します。この構造体には、不完全なポインタ型を追跡するための`ptrs`という`map`が含まれていました。

変更前の`FinishType`メソッドは、`c.ptrs`マップをイテレートして、不完全なポインタ型を解決していました。

```go
// 変更前 (簡略化)
for len(c.ptrs) > 0 {
    for dtype := range c.ptrs { // ここが非決定性の原因
        // ... 型の解決ロジック ...
        delete(c.ptrs, dtype)
    }
}
```

Goの`map`の`range`イテレーションは、その順序が保証されません。したがって、`c.ptrs`から`dtype`（`dwarf.Type`、Cの型を表す）を取り出す順序が実行ごとに異なりました。この非決定的な順序が、`cgo`が生成するGoの型名（特に匿名構造体や不完全な型に対応するもの）に影響を与え、結果として非決定的な出力につながっていました。

このコミットでは、この非決定性を排除するために、`typeConv`構造体に`ptrKeys []dwarf.Type`という新しいフィールドが追加されました。このスライスは、`ptrs`マップのキーを挿入順に（つまり、決定論的な順序で）保持するためのワークリストとして機能します。

変更後の`FinishType`メソッドは、`c.ptrs`マップを直接イテレートする代わりに、`ptrKeys`スライスから要素を順次取り出して処理します。

```go
// 変更後 (簡略化)
for len(c.ptrKeys) > 0 {
    dtype := c.ptrKeys[0] // スライスから先頭要素を取り出す
    c.ptrKeys = c.ptrKeys[1:] // 先頭要素を削除

    // ... 型の解決ロジック ...

    c.ptrs[dtype] = nil // mapのキーは保持するが、値はnilにする
}
```

また、`typeConv.Type`メソッド内で新しい不完全なポインタ型が`c.ptrs`に追加される際に、そのキー（`dt.Type`）が`c.ptrKeys`スライスにも`append`されるようになりました。これにより、`ptrKeys`は常に処理すべき不完全なポインタ型の決定論的な順序付きリストを保持します。

この変更により、`FinishType`が不完全な型を解決する順序が常に同じになり、`cgo`が生成する型名も決定論的になります。

## コアとなるコードの解説

`src/cmd/cgo/gcc.go`の変更がこのコミットの核心です。

**`typeConv`構造体への`ptrKeys`フィールドの追加:**

```go
type typeConv struct {
    // ... 既存フィールド ...

    // Map from types to incomplete pointers to those types.
    ptrs map[dwarf.Type][]*Type
    // Keys of ptrs in insertion order (deterministic worklist)
    ptrKeys []dwarf.Type // <-- 新しく追加されたフィールド
}
```
`ptrKeys`は、`ptrs`マップに格納されている`dwarf.Type`のキーを、それらが`ptrs`に追加された順序で保持するためのスライスです。これにより、`ptrs`マップの非決定的なイテレーション順序の問題を回避し、処理順序を決定論的に制御できるようになります。

**`FinishType`メソッドの変更:**

```go
func (c *typeConv) FinishType(pos token.Pos) {
    // Completing one pointer type might produce more to complete.
    // Keep looping until they're all done.
    for len(c.ptrKeys) > 0 { // <-- 変更点: ptrKeysスライスをワークリストとして使用
        dtype := c.ptrKeys[0] // <-- 変更点: スライスの先頭から要素を取り出す
        c.ptrKeys = c.ptrKeys[1:] // <-- 変更点: 取り出した要素をスライスから削除

        // Note Type might invalidate c.ptrs[dtype].
        t := c.Type(dtype, pos)
        for _, ptr := range c.ptrs[dtype] {
            ptr.Go.(*ast.StarExpr).X = t.Go
            ptr.C.Set("%s*", t.C)
        }
        c.ptrs[dtype] = nil // <-- 変更点: mapの値をnilにするが、キーは残す
    }
}
```
変更前は`for dtype := range c.ptrs`というGoの`map`の非決定的なイテレーションに依存していましたが、変更後は`ptrKeys`スライスを明示的なワークリストとして使用しています。これにより、`dtype`が取り出される順序が常に`ptrKeys`に追加された順序と一致し、処理の決定性が保証されます。
`c.ptrs[dtype] = nil`という行は、`dtype`に対応する不完全なポインタ型がすべて解決されたことを示しますが、`map`からキーを完全に削除するのではなく、値を`nil`に設定しています。これは、`Type`メソッドが`c.ptrs`マップにキーが存在するかどうかをチェックする際に、キーがまだ存在している必要があるためです。

**`Type`メソッドの変更:**

```go
func (c *typeConv) Type(dtype dwarf.Type, pos token.Pos) *Type {
    // ... 既存ロジック ...

    case *dwarf.PtrType:
        dt := dtype.(*dwarf.PtrType)
        // ... 既存ロジック ...
        // Placeholder initialization; completed in FinishType.
        t.Go = &ast.StarExpr{}
        t.C.Set("<incomplete>*")
        if _, ok := c.ptrs[dt.Type]; !ok { // <-- 変更点: 新しいキーの場合のみptrKeysに追加
            c.ptrKeys = append(c.ptrKeys, dt.Type) // <-- 変更点: ptrKeysにキーを追加
        }
        c.ptrs[dt.Type] = append(c.ptrs[dt.Type], t)

    // ... 既存ロジック ...
}
```
`Type`メソッドは、新しい不完全なポインタ型（`dwarf.PtrType`）を検出した際に、その基底型（`dt.Type`）を`c.ptrs`マップに追加します。このとき、`c.ptrs[dt.Type]`にまだそのキーが存在しない場合（`!ok`）、そのキーを`c.ptrKeys`スライスにも`append`します。これにより、`ptrKeys`は、`FinishType`で処理されるべき不完全な型の決定論的な順序付きリストとして機能します。

これらの変更により、`cgo`の型変換プロセスにおけるワークリストの処理順序が決定論的になり、結果として生成されるGoの型名も常に同じになることが保証されます。

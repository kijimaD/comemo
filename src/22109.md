# [インデックス 22109] ファイルの概要

このコミットは、Go言語の`crypto/tls`パッケージにおけるTLSレコードの処理に関する変更です。具体的には、TLSハンドシェイクの初期段階で受信するレコードのサイズに対する「正気度チェック（sanity test）」を緩和し、一部のサーバーが送信する大きなレコードも適切に処理できるようにします。

## コミット

このコミットは、TLSハンドシェイクの初期レコードサイズに関する厳格なチェックを緩和することで、特定のTLSサーバーとの相互運用性の問題を解決します。以前のGoのTLS実装では、`CertificateRequest`メッセージの意図を誤解している一部のサーバーが、非常に大きな応答レコードを送信することがありました。これらのレコードは、GoのTLSコードによって「異常（insane）」と見なされ、拒否されていました。この変更により、レコード長に対する厳しすぎる正気度テストが削除され、TLSプロトコルで規定されている16KBの最大レコードサイズ（RFC 5246, Section 6.2.1）の範囲内であれば、より大きな初期レコードも受け入れられるようになります。

## 元コミット内容

```
crypto/tls: allow larger initial records.

Some servers which misunderstood the point of the CertificateRequest
message send huge reply records. These records are large enough that
they were considered “insane” by the TLS code and rejected.

This change removes the sanity test for record lengths. Although the
maxCiphertext test still remains, just above, which (roughly) enforces
the 16KB protocol limit on record sizes:
https://tools.ietf.org/html/rfc5246#section-6.2.1

Fixes #8928.
```

## 変更の背景

この変更の背景には、TLSプロトコルの実装における相互運用性の問題がありました。TLS（Transport Layer Security）は、インターネット上での安全な通信を確立するためのプロトコルであり、クライアントとサーバー間でハンドシェイクと呼ばれる一連のメッセージ交換を通じてセキュアな接続を確立します。

問題は、一部のTLSサーバーが`CertificateRequest`メッセージ（クライアント証明書を要求するメッセージ）に対して、TLSプロトコルの仕様に準拠していない、非常に大きな応答レコードを送信していたことにありました。Goの`crypto/tls`パッケージの実装では、このような異常に大きな初期レコードを「正気ではない（insane）」と判断し、セキュリティ上の理由から接続を拒否していました。

具体的には、GoのTLSコードは、最初のメッセージがTLSクライアントからのものではない可能性を考慮し、過度に大きなレコードを受信した場合に早期に接続を終了する「正気度テスト」を設けていました。このテストは、特に`ClientHello`メッセージが通常1KB未満であるという経験則に基づき、12KB以上のレコードを異常と見なしていました。しかし、`CertificateRequest`に対するサーバーの応答がこの閾値を超えることがあり、結果として正当なTLS接続が確立できないという相互運用性の問題が発生していました。

このコミットは、この厳しすぎる正気度テストを緩和することで、RFC 5246で規定されているTLSレコードの最大サイズ（約16KB）の範囲内であれば、より大きな初期レコードも受け入れられるようにし、相互運用性を向上させることを目的としています。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上でクライアントとサーバー間の通信を暗号化し、認証を行うためのプロトコルです。HTTP通信をセキュアにするHTTPSの基盤として広く利用されています。TLSは、ハンドシェイクプロトコル、レコードプロトコル、アラートプロトコルなど、複数のサブプロトコルで構成されています。

### TLSレコードプロトコル

TLSレコードプロトコルは、TLS通信の基本的なデータ単位である「レコード」を定義します。アプリケーションデータやTLSプロトコルメッセージ（ハンドシェイクメッセージ、アラートメッセージなど）は、このレコードプロトコルによってフラグメント化、圧縮（オプション）、MAC（メッセージ認証コード）の付加、暗号化が行われ、下位のトランスポート層（通常はTCP）に渡されます。

RFC 5246のSection 6.2.1「Fragmentation」では、`TLSPlaintext`レコードの最大長が2^14バイト（16384バイト、約16KB）と規定されています。これは、TLSレコードが一度に運ぶことができる暗号化されていないデータの最大量です。

### TLSハンドシェイクプロトコル

TLSハンドシェイクプロトコルは、クライアントとサーバーが安全な通信チャネルを確立するために使用する一連のメッセージ交換です。これには、プロトコルバージョンのネゴシエーション、暗号スイートの選択、サーバー認証（サーバー証明書）、オプションのクライアント認証（クライアント証明書）、共有秘密鍵の生成などが含まれます。

### `CertificateRequest`メッセージ

`CertificateRequest`は、サーバーがクライアントに対してクライアント証明書を要求するためにハンドシェイク中に送信するメッセージです。クライアントはこれに応答して`Certificate`メッセージ（自身の証明書を含む）と`CertificateVerify`メッセージ（証明書の所有を証明する署名）を送信します。

### 正気度チェック (Sanity Check)

ソフトウェア開発において「正気度チェック」とは、入力データやシステムの状態が、予期される範囲内にあるか、または論理的に妥当であるかを検証する簡単なテストのことです。これは、不正な入力や予期せぬ状態がシステムに深刻な問題を引き起こすのを防ぐために行われます。今回のケースでは、TLSレコードの長さが異常に大きい場合に、それが不正なデータである可能性を疑い、処理を停止するためのチェックでした。

### 16KBプロトコル制限 (RFC 5246, Section 6.2.1)

TLSレコードの最大サイズは、RFC 5246のSection 6.2.1で2^14バイト（16384バイト）と明確に定義されています。この制限は、TLS実装が処理しなければならないバッファサイズを管理し、サービス拒否攻撃（DoS攻撃）のリスクを軽減するために設けられています。

## 技術的詳細

このコミットは、`src/crypto/tls/conn.go`ファイル内の`(*Conn).readRecord`メソッド（またはそれに相当するレコード読み込みロジック）に影響を与えます。このメソッドは、TLS接続から受信した生データをTLSレコードとして解析する役割を担っています。

変更前のコードでは、TLSハンドシェイクの最初のメッセージを受信する際に、特に厳格な「正気度チェック」が適用されていました。これは、受信したデータが本当にTLSプロトコルに従っているかを検証し、悪意のある、または誤った形式のデータによってリソースが枯渇するのを防ぐためのものでした。

具体的なチェックは以下の条件で行われていました。

```go
if (typ != recordTypeAlert && typ != want) || vers >= 0x1000 || n >= 0x3000 {
    // ... エラー処理 ...
}
```

ここで、
*   `typ`: 受信したレコードのタイプ（例: `recordTypeHandshake`, `recordTypeAlert`など）。
*   `want`: 期待されるレコードタイプ。
*   `vers`: 受信したレコードのTLSバージョン。
*   `n`: 受信したレコードの長さ（バイト単位）。

この条件のうち、`n >= 0x3000`という部分が問題でした。`0x3000`は10進数で12288、つまり約12KBを意味します。GoのTLS実装は、最初のレコードの長さが12KB以上の場合、それを「正気ではない」と判断し、エラーを発生させていました。コミットメッセージによると、これは`ClientHello`メッセージが通常1KB未満であるという経験則に基づいていたようです。

しかし、一部のサーバーが`CertificateRequest`メッセージに対して、正当なTLSプロトコルの一部として、この12KBの閾値を超えるサイズの応答レコードを送信することが判明しました。これは、TLSプロトコル自体が許容する最大レコードサイズ（約16KB）の範囲内であるにもかかわらず、Goの実装がそれを拒否してしまうという相互運用性の問題を引き起こしていました。

このコミットでは、`n >= 0x3000`という条件が削除されました。これにより、最初のレコードの長さに対する厳しすぎるチェックが緩和され、TLSプロトコルで許容される最大サイズ（16KB）に近いレコードも受け入れられるようになります。

コミットメッセージに記載されているように、`maxCiphertext`テスト（コードの変更箇所の上にある）は引き続き存在し、これがRFC 5246で規定されている16KBのプロトコル制限を概ね強制します。つまり、この変更は無制限に大きなレコードを許可するものではなく、TLS仕様の範囲内でより柔軟な処理を可能にするものです。

## コアとなるコードの解説

変更は`src/crypto/tls/conn.go`ファイルの`if !c.haveVers`ブロック内で行われています。このブロックは、TLSハンドシェイクの最初のレコードを受信した際に実行されるロジックです。

**変更前:**

```go
if (typ != recordTypeAlert && typ != want) || vers >= 0x1000 || n >= 0x3000 {
    c.sendAlert(alertUnexpectedMessage)
    return c.in.setErrorLocked(fmt.Errorf("tls: first record does not look like a TLS handshake"))
}
```

この行は、受信した最初のレコードがTLSハンドシェイクメッセージとして妥当であるかをチェックしていました。
*   `typ != recordTypeAlert && typ != want`: レコードタイプがアラートでも期待されるタイプでもない場合。
*   `vers >= 0x1000`: TLSバージョンが`0x1000`（10進数で4096）以上の場合。これは、TLSバージョンが異常に高い値であるかをチェックしています。TLS 1.2は`0x0303`なので、`0x1000`は明らかに異常な値です。
*   `n >= 0x3000`: レコードの長さ`n`が`0x3000`（10進数で12288、約12KB）以上の場合。これが、一部のサーバーからの正当な応答を拒否していた原因でした。

**変更後:**

```go
if (typ != recordTypeAlert && typ != want) || vers >= 0x1000 {
    c.sendAlert(alertUnexpectedMessage)
    return c.in.setErrorLocked(fmt.Errorf("tls: first record does not look like a TLS handshake"))
}
```

変更点として、`|| n >= 0x3000`という条件が削除されています。これにより、最初のレコードの長さが12KBを超える場合でも、他の条件（レコードタイプやバージョン）が妥当であれば、エラーとして扱われなくなりました。

この変更は、TLSプロトコル（RFC 5246）で規定されている最大レコードサイズ（約16KB）の範囲内で、より大きな初期レコードを許容することで、特定のTLSサーバーとの相互運用性を改善します。コードコメントも更新され、以前の「現在の最大バージョンは3.1」から「現在の最大バージョンは3.3」に修正されています（TLS 1.2はバージョン3.3に相当）。

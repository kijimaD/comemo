## 変更の背景

このコミットの主な背景は、`test/turing.go`というテストプログラムが、大きな配列をスタック上に割り当てようとした際に発生する問題でした。スタックは通常、サイズが限られており、非常に大きなデータ構造（特に配列）を直接スタックに割り当てると、スタックオーバーフローを引き起こし、プログラムのクラッシュや予期せぬ動作につながる可能性があります。

Go言語の初期段階において、コンパイラ（`8g`）は、このような大きな配列の割り当てを最適に処理できていなかったと考えられます。このコミットは、`test/turing.go`が正しく動作するように、コンパイラのコード生成戦略を変更し、大きな配列がスタックではなくヒープに割り当てられるようにすることで、この問題を解決することを目的としています。これにより、Goプログラムの堅牢性と安定性が向上します。

## 前提知識の解説

*   **スタックとヒープ**: プログラムが使用するメモリ領域には、主に「スタック」と「ヒープ」があります。
    *   **スタック**: 関数呼び出しやローカル変数の格納に使用されるメモリ領域です。LIFO（Last-In, First-Out）形式で管理され、高速ですが、サイズが限られています。コンパイル時にサイズが決定されることが多く、大きなデータ構造を置くとスタックオーバーフローの原因となります。
    *   **ヒープ**: プログラム実行中に動的にメモリを割り当てるために使用されるメモリ領域です。サイズに柔軟性があり、大きなデータ構造や、関数のスコープを超えて存続する必要があるデータを格納するのに適しています。ただし、スタックに比べてアクセスが遅く、ガベージコレクションによる管理が必要です。
*   **Goコンパイラ (`8g`)**: Go言語の初期のコンパイラは、ターゲットアーキテクチャごとに異なる名前を持っていました。`8g`は、32-bit x86（Intel 80386互換）アーキテクチャ向けのGoコンパイラを指します。Goのソースコードを機械語に変換する役割を担います。
*   **コード生成**: コンパイラの主要なフェーズの一つで、抽象構文木（AST）などの中間表現を、ターゲットマシンが実行できる機械語コードに変換するプロセスです。このフェーズで、変数のメモリ割り当て（スタックかヒープか）や、各種操作の具体的な機械語命令が決定されます。
*   **`test/turing.go`**: このコミットメッセージに登場する特定のテストファイルです。名前から推測すると、チューリングマシンに関連する、あるいは計算量の多い処理を行うプログラムであり、その過程で大きなデータ構造（配列）を使用していた可能性が高いです。

## 技術的詳細

このコミットは、`8g`コンパイラのコード生成部分に大幅な変更を加えています。特に、`cgen.c`と`gsubr.c`という2つの新しいファイルが追加されている点が重要です。

*   **`cgen.c`**: このファイルは、Goのコードから中間コードを生成する役割を担うと考えられます。コミットメッセージの「more 8g.」という記述と、このファイルが追加されたことから、コンパイラのコード生成ロジックが拡張または再構築されたことを示唆しています。特に、`cgen`関数は、Goの式やステートメントをターゲットアーキテクチャの命令に変換する中心的な役割を果たすと推測されます。大きな配列のスタック割り当て問題を解決するためには、この`cgen`関数内で、配列のサイズに基づいてスタックとヒープのどちらに割り当てるかを判断するロジックが追加されたか、既存の割り当て戦略が変更された可能性が高いです。
*   **`gsubr.c`**: このファイルは、Goコンパイラが生成するサブルーチンや共通のコードパターンに関連する処理を扱うと考えられます。例えば、メモリコピー（`sgen`関数）やレジスタの割り当て（`regalloc`、`regfree`関数）、定数やアドレスの生成（`gconreg`、`gload`、`gstore`関数）など、低レベルの操作が含まれています。大きな配列をヒープに移動する際には、これらのサブルーチンが、新しいメモリ割り当て戦略に合わせて調整される必要があります。特に、`sgen`関数は構造体や配列のメモリコピーを扱うため、ヒープへの移動に伴うデータ転送ロジックの変更がここに含まれている可能性があります。
*   **`ggen.c`**: 既存のコード生成ファイルであり、`clearfat`や`cgen_asop`といった関数が修正されています。`clearfat`は「fat object」（構造体や配列など、複数の要素を持つオブジェクト）をクリアする処理に関連しており、大きな配列のメモリ管理変更に伴い、そのクリア方法も調整された可能性があります。`cgen_asop`は複合代入演算子（`+=`, `-=`など）のコード生成を扱うため、ここでもメモリ操作の最適化や変更が加えられたと考えられます。
*   **`gg.h`**: コンパイラのヘッダファイルであり、新しい関数のプロトタイプ宣言やデータ構造の定義が追加されています。`agenr`関数の追加や`sudoaddable`関数のシグネチャ変更が確認できます。これらは、アドレス生成や最適化のロジックが変更されたことを示しています。
*   **`list.c`**: このファイルの変更は比較的小さいですが、コンパイラの内部リスト構造やデバッグ出力に関連している可能性があります。

全体として、このコミットは、Goコンパイラが大きなデータ構造（特に配列）のメモリ割り当てをより効率的かつ安全に行うための、根本的な改善を導入しています。これにより、スタックオーバーフローのリスクを軽減し、より大規模なGoプログラムの実行を可能にしています。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   **`src/cmd/8g/cgen.c`**: 新規追加。Goの式やステートメントから中間コードを生成する主要なロジックが含まれています。
*   **`src/cmd/8g/gsubr.c`**: 新規追加。コード生成における共通のサブルーチンやヘルパー関数（メモリ操作、レジスタ管理など）が含まれています。
*   **`src/cmd/8g/ggen.c`**: 既存ファイルの修正。特に`clearfat`関数や`cgen_asop`関数など、fat objectのクリアや複合代入演算子のコード生成ロジックが変更されています。
*   **`src/cmd/8g/gg.h`**: 既存ファイルの修正。新しい関数のプロトタイプ宣言（例: `agenr`）や既存関数のシグネチャ変更（例: `sudoaddable`）が含まれています。
*   **`src/cmd/8g/list.c`**: 既存ファイルの修正。比較的小規模な変更です。

特に、`cgen.c`と`gsubr.c`の新規追加は、コンパイラのコード生成バックエンドにおける大幅な再構築または拡張を示しています。

## コアとなるコードの解説

このコミットの核心は、`cgen.c`と`gsubr.c`の導入、および既存のコード生成ロジックの調整にあります。

*   **`cgen.c`の`cgen`関数**: この関数は、Goの抽象構文木（AST）のノードを受け取り、それに対応する機械語命令を生成します。大きな配列のスタック割り当て問題を解決するために、`cgen`関数内で、配列のサイズや特性に基づいて、そのメモリをスタックではなくヒープに割り当てるための新しいロジックが実装されたと考えられます。例えば、`isfat`関数（`gg.h`で宣言され、`gsubr.c`で実装されている）が、構造体や配列などの「fat object」を識別し、それらのオブジェクトに対して特別な処理（ヒープ割り当てや`sgen`によるメモリコピーなど）を適用するようになっています。
*   **`gsubr.c`の`sgen`関数**: この関数は、構造体や配列などの大きなデータブロックをメモリ間でコピーする役割を担います。コミットメッセージの「move the big array off its stack」という記述から、スタックからヒープへのデータ移動が必要になるため、この`sgen`関数がそのコピー操作を効率的に行うように実装または最適化されたと考えられます。特に、`sgen`関数内では、`DI`（Destination Index）レジスタと`SI`（Source Index）レジスタを使用して、`MOVSL`（Move String Long）や`MOVSB`（Move String Byte）といったx86の文字列操作命令をREPプレフィックス（繰り返し）とともに利用し、高速なメモリブロックコピーを実現しています。また、スタック上のソースとデスティネーションがオーバーラップする場合の逆方向コピーのロジックも含まれており、これはメモリコピーの安全性を確保するために重要です。
*   **`gsubr.c`のレジスタ管理関数 (`regalloc`, `regfree`)**: これらの関数は、コード生成中にレジスタを効率的に割り当て、解放するために使用されます。新しいコード生成ロジックやメモリ割り当て戦略は、レジスタの使用パターンに影響を与えるため、これらの関数も調整されています。
*   **`ggen.c`の`clearfat`関数**: この関数は、大きなオブジェクト（構造体や配列）をゼロでクリアする処理を行います。ヒープに移動された大きな配列も初期化が必要なため、この関数が新しいメモリ割り当て戦略に合わせて更新されています。`ASTOSL`（Store String Long）や`ASTOSB`（Store String Byte）命令をREPプレフィックスとともに使用して、効率的にメモリをゼロクリアしています。

これらの変更により、Goコンパイラは、大きな配列をより適切に処理し、スタックオーバーフローを回避しながら、プログラムの実行効率を維持できるようになりました。

# [インデックス 26552] ファイルの概要

このコミットは、Goランタイムにおける`stringto{byte,rune}slice`関数が、スタック上に確保された一時バッファを使用する際に、初期化されていないメモリ領域をスライスの容量（capacity）として誤って公開してしまう問題を修正します。具体的には、スライスの容量をその長さ（length）に制限することで、この情報漏洩のリスクを排除しています。

## 変更の背景

このコミットは、GoランタイムにおけるIssue 14232「Slice of runes doesn't trigger 'out of bounds' panic」を修正するために導入されました。この問題は、文字列を`[]byte`や`[]rune`に変換する際に、ランタイムが内部的にスタック上に一時バッファを割り当て、そのバッファの一部を結果のスライスとして返す場合に発生しました。

具体的には、`stringtoslicebyte`や`stringtoslicerune`といった内部関数が、スタック上のバッファを再利用する際に、スライスの長さ（`len`）と容量（`cap`）の間に存在する初期化されていないメモリ領域を、スライスの容量として公開してしまう可能性がありました。これにより、ユーザーコードがこのスライスに対して`append`操作を行うと、意図せず古いスタックフレームのデータが読み取られてしまう可能性があり、情報漏洩や予期せぬ動作につながる恐れがありました。

コミットメッセージにもあるように、この問題はGo 1.6のリリースが近い時期に発見されたため、最もシンプルで安全な修正が選択されました。

## 前提知識の解説

### Goにおけるスライス (Slice)

Goのスライスは、配列をラップした動的なビューです。スライスは以下の3つの要素で構成されます。

1.  **ポインタ (Pointer)**: スライスが参照する基底配列の先頭要素へのポインタ。
2.  **長さ (Length)**: スライスに含まれる要素の数。`len()`関数で取得できます。
3.  **容量 (Capacity)**: スライスの基底配列の先頭から、その配列の末尾までの要素の数。`cap()`関数で取得できます。スライスを拡張（`append`）する際に、この容量の範囲内であれば新しいメモリ割り当てなしで要素を追加できます。

スライスは`s[low:high]`という形式で作成されますが、Go 1.2以降では`s[low:high:max]`という形式も導入されました。この3インデックススライス式では、`low`が開始インデックス、`high`が長さの終了インデックス（`len = high - low`）、`max`が容量の終了インデックス（`cap = max - low`）をそれぞれ指定します。`max`を指定しない場合、`max`は基底配列の容量と同じになります。

### スタック割り当て (Stack Allocation)

Goのランタイムは、変数をスタックまたはヒープに割り当てます。スタックは関数呼び出しごとに確保され、関数が終了すると解放される高速なメモリ領域です。比較的小さな、生存期間が短い変数はスタックに割り当てられることが多いです。スタックに割り当てられたメモリは、関数が戻ると再利用されるため、以前の関数のデータが残っている可能性があります。

### 未初期化メモリ (Uninitialized Memory)

プログラムがメモリを割り当てた際、そのメモリ領域には以前使用されていたデータが残っていることがあります。これを未初期化メモリと呼びます。Goでは、新しい変数を宣言するとゼロ値で初期化されるため、通常は未初期化メモリの問題に直面することはありません。しかし、スライスが基底配列の一部をビューとして参照し、その基底配列の容量がスライスの長さよりも大きい場合、`len`から`cap`までの領域は、明示的に初期化されない限り、古いデータを含んでいる可能性があります。

## 技術的詳細

このコミットが修正する問題は、Goの内部関数である`stringtoslicebyte`と`stringtoslicerune`が、文字列をバイトスライスまたはルーンスライスに変換する際に、最適化のためにスタック上に一時バッファを使用する場合に発生していました。

これらの関数は、変換後のスライスを格納するために、まずスタック上に固定サイズの一時バッファ（`tmpBuf`や`[tmpStringBufSize]rune`）を試用します。文字列の長さがこの一時バッファのサイズ以下であれば、ヒープ割り当てを避けてパフォーマンスを向上させます。

問題のコードは以下のようでした（例: `stringtoslicebyte`）：

```go
b = buf[:len(s)]
```

このスライス式は、`buf`という基底配列の先頭から`len(s)`までの長さを持つスライス`b`を作成します。しかし、この形式では容量（`cap(b)`）は基底配列`buf`の容量全体（つまり`len(buf)`）と同じになります。もし`len(s)`が`len(buf)`よりも小さい場合、`len(s)`から`len(buf)`までのメモリ領域は、スライス`b`の容量内ではあるものの、初期化されていない状態となります。

ユーザーコードがこのスライス`b`を受け取り、`append`操作を行うと、`len(s)`から`len(buf)`までの未初期化領域にアクセスし、古いスタックデータが読み取られる可能性がありました。これは、Goのメモリ安全性の原則に反するものでした。

このコミットでは、この問題を解決するために、3インデックススライス式`s[low:high:max]`を使用しています。

## コアとなるコードの解説

変更の核心は、`src/runtime/string.go`内の`stringtoslicebyte`と`stringtoslicerune`関数におけるスライス作成方法の変更です。

**変更前:**

```go
b = buf[:len(s)] // len(b) = len(s), cap(b) = len(buf)
a = buf[:n]     // len(a) = n, cap(a) = len(buf)
```

この形式では、作成されたスライスの容量が基底配列`buf`の全長に設定されていました。これにより、`len(s)`（または`n`）が`len(buf)`よりも小さい場合、スライスの`len`と`cap`の間に未初期化のメモリ領域が存在することになります。

**変更後:**

```go
b = buf[:len(s):len(s)] // len(b) = len(s), cap(b) = len(s)
a = buf[:n:n]         // len(a) = n, cap(a) = n
```

この変更では、3インデックススライス式`s[low:high:max]`が使用されています。ここで、`low`は0、`high`は`len(s)`（または`n`）、そして`max`も`len(s)`（または`n`）に設定されています。これにより、作成されるスライスの長さと容量が等しくなります。

`len(b) = len(s)`
`cap(b) = len(s)`

この修正により、スライスの容量がその長さに制限されるため、スライスの`len`と`cap`の間に未初期化のメモリ領域が存在することがなくなります。結果として、ユーザーコードがこのスライスに対して`append`操作を行っても、未初期化のスタックデータにアクセスするリスクが排除されます。

コミットメッセージにあるように、もう一つの選択肢として`len`と`cap`の間の領域をゼロクリアする方法も検討されましたが、Go 1.6のリリースが近いという状況を考慮し、最もシンプルで影響の少ないこの修正が採用されました。

また、`src/runtime/string_test.go`には、この修正が正しく機能することを確認するための新しいテストケース`TestString2Slice`が追加されています。このテストでは、文字列を`[]byte`と`[]rune`に変換した後、結果のスライスの容量が期待通りに制限されているか（`cap(b) == 5`、`cap(r) == 4`）を確認しています。これは、未初期化メモリが公開されていないことを検証するものです。

# [インデックス 28070] ファイルの概要

このコミットは、Goランタイムのメモリ管理における`mspan`構造体の基底アドレス（開始アドレス）の計算方法を最適化し、コードのクリーンアップを行うものです。これまで複数の場所でシフト演算や`base()`関数の呼び出しによって計算されていた`mspan`の基底アドレスを、`mspan`が初期化される際に一度だけ計算して構造体内に保存するように変更し、以降は保存された値を使用することでパフォーマンス向上とコードの一貫性を図っています。

## 元コミット内容

```
[dev.garbage] runtime: cleanup and optimize span.base()

Prior to this CL the base of a span was calculated in various
places using shifts or calls to base(). This CL now
always calls base() which has been optimized to calculate the
base of the span when the span is initialized and store that
value in the span structure.
```

## 変更の背景

Goランタイムのメモリ管理において、`mspan`（メモリのスパン）の開始アドレス（基底アドレス）は頻繁に参照される重要な情報です。この基底アドレスは、`mspan`構造体の`start`フィールド（ページID）と`_PageShift`定数（ページサイズの対数）を用いて`uintptr(s.start << _PageShift)`というシフト演算で計算されていました。

しかし、この計算がランタイム内の様々な場所で繰り返し行われており、以下の問題点がありました。

1.  **冗長な計算**: 同じ基底アドレスを何度も計算することは、わずかではあるもののCPUサイクルを無駄にしていました。特にメモリ割り当てやGC（ガベージコレクション）のようなパフォーマンスが重要なパスでは、このような小さなオーバーヘッドも積み重なると無視できない影響を与える可能性があります。
2.  **コードの不整合と保守性**: 基底アドレスの計算ロジックが複数の場所に散らばっていると、将来的にページサイズが変更された場合などに、すべての計算箇所を正確に更新する必要があり、バグの温床となる可能性がありました。また、コードの可読性も低下します。
3.  **`span.base()`の役割の曖昧さ**: `span.base()`関数が存在するにもかかわらず、直接シフト演算で基底アドレスを計算する箇所が混在しており、`span.base()`の役割が一貫していませんでした。

このコミットは、これらの問題を解決し、`mspan`の基底アドレスの取り扱いをより効率的かつ一貫性のあるものにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理、特に`mspan`、`mheap`、ページングの概念について基本的な知識が必要です。

*   **Goランタイムのメモリ管理**: Goは独自のメモリマネージャを持ち、OSから大きなメモリブロックを確保し、それを細かく分割してユーザープログラムに割り当てます。この管理は主に`mheap`（ヒープ全体を管理する構造体）と`mspan`（メモリの連続したブロック）によって行われます。
*   **`mspan`**: `mspan`は、Goランタイムが管理するメモリの連続したページ群を表す構造体です。これは、特定のサイズのオブジェクトを格納するために使用されるか、または単一の大きなオブジェクトを格納するために使用されます。`mspan`は、その開始ページID (`start`)、ページ数 (`npages`)、およびそのスパンが管理するオブジェクトのサイズクラスなどの情報を含みます。
*   **`pageID`**: メモリページを一意に識別するためのIDです。Goランタイムはメモリを固定サイズのページ（通常は8KB）に分割して管理します。
*   **`_PageShift`**: これは、Goランタイムの内部定数で、メモリページのサイズを2のべき乗で表したときの指数です。例えば、ページサイズが8KB（8192バイト）の場合、`_PageShift`は13になります（2^13 = 8192）。この定数を使ってページIDを左シフトすることで、そのページの開始メモリアドレスを計算できます。`uintptr(pageID << _PageShift)`は、`pageID`で示されるページの開始メモリアドレスを`uintptr`型で返します。
*   **`mheap`**: Goランタイムのグローバルなヒープを管理する構造体です。`mheap`は`mspan`のリストを管理し、メモリの割り当てと解放を行います。

## 技術的詳細

このコミットの核心的な変更は、`mspan`構造体に`startAddr uintptr`という新しいフィールドを追加し、`mspan`の基底アドレスをキャッシュすることです。

1.  **`mspan`構造体への`startAddr`の追加**:
    `src/runtime/mheap.go`の`mspan`構造体に`startAddr uintptr`フィールドが追加されました。このフィールドは、`mspan`がカバーするメモリ領域の開始メモリアドレスを直接格納します。
    ```go
    type mspan struct {
        // ... 既存のフィールド ...
        //TODO:(rlh) Eliminate start field and use startAddr >> PageShift instead.
        startAddr     uintptr   // uintptr(s.start << _PageShift) aka s.base()
        start         pageID    // starting page number
        // ... 既存のフィールド ...
    }
    ```
    コメントにあるように、将来的には`start`フィールドを削除し、`startAddr`からページIDを逆算する形にすることも検討されていますが、このコミットでは両方を保持しています。

2.  **`mspan.base()`関数の変更**:
    `mspan.base()`関数は、以前は`uintptr(s.start << _PageShift)`というシフト演算を行って基底アドレスを計算していましたが、この変更により`s.startAddr`を直接返すようになりました。
    ```go
    func (s *mspan) base() uintptr {
        return s.startAddr
    }
    ```
    これにより、`base()`の呼び出しは単なるフィールドアクセスとなり、非常に高速になります。

3.  **`startAddr`の初期化**:
    `startAddr`フィールドは、`mspan`が初期化される際、またはその基底アドレスが変更される際に設定されます。
    *   `mspan.init(start pageID, npages uintptr)`関数（`src/runtime/mheap.go`）内で、新しいスパンが初期化されるときに`span.startAddr = uintptr(start << _PageShift)`として設定されます。
    *   `mheap.freeSpanLocked`関数（`src/runtime/mheap.go`）内で、隣接する空きスパンが結合される際に、結合後の新しいスパンの`startAddr`が再計算・設定されます。

4.  **既存コードの更新**:
    ランタイム内の`src/runtime/malloc.go`, `src/runtime/mbitmap.go`, `src/runtime/mcentral.go`, `src/runtime/mgcmark.go`, `src/runtime/mgcsweep.go`, `src/runtime/mheap.go`など、`uintptr(s.start << _PageShift)`というパターンで基底アドレスを計算していたすべての箇所が、`s.base()`を呼び出すように変更されました。

**最適化の効果**:
この変更により、`mspan`の基底アドレスが必要な場所では常に`s.base()`が呼び出され、その内部では既に計算済みの`startAddr`が返されるため、冗長なシフト演算が排除されます。これは、特にGCサイクル中やメモリ割り当てパスなど、`mspan`の基底アドレスが頻繁にアクセスされるホットパスにおいて、わずかながらもパフォーマンスの向上に寄与します。また、基底アドレスの計算ロジックが一箇所に集約されることで、コードの保守性と可読性が向上します。

**メモリフットプリントへの影響**:
`mspan`構造体に`uintptr`型のフィールドが一つ追加されるため、`mspan`インスタンスごとに数バイト（32ビットシステムで4バイト、64ビットシステムで8バイト）のメモリオーバーヘッドが発生します。しかし、`mspan`の数はヒープサイズに比例しますが、このオーバーヘッドは通常、得られるパフォーマンスと保守性の向上に比べて許容範囲内と見なされます。

## コアとなるコードの解説

以下に、変更の核心部分である`mspan`構造体と`mspan.base()`関数の変更、および`startAddr`の初期化箇所のコードスニペットと解説を示します。

### `mspan`構造体の変更 (`src/runtime/mheap.go`)

```go
type mspan struct {
	next *mspan     // next span in list, or nil if none
	prev **mspan    // previous span's next field, or list head's first field if none
	list *mSpanList // For debugging. TODO: Remove.
	//TODO:(rlh) Eliminate start field and use startAddr >> PageShift instead.
	startAddr     uintptr   // uintptr(s.start << _PageShift) aka s.base()
	start         pageID    // starting page number
	npages        uintptr   // number of pages in span
	stackfreelist gclinkptr // list of free stacks, avoids overloading freelist
	// ... (その他のフィールド) ...
}
```
`mspan`構造体に`startAddr`フィールドが追加されました。これは`uintptr`型で、スパンの開始メモリアドレスを直接保持します。コメントにあるように、将来的には`start`フィールドを削除し、`startAddr`からページIDを導出する可能性も示唆されています。

### `mspan.base()`関数の変更 (`src/runtime/mheap.go`)

```go
func (s *mspan) base() uintptr {
	return s.startAddr
}
```
以前は`uintptr(s.start << _PageShift)`という計算を行っていた`base()`関数が、単に`s.startAddr`フィールドの値を返すように変更されました。これにより、`base()`の呼び出しは非常に軽量な操作となります。

### `startAddr`の初期化 (`mspan.init`関数内, `src/runtime/mheap.go`)

```go
func (span *mspan) init(start pageID, npages uintptr) {
	span.prev = nil
	span.list = nil
	span.start = start
	span.startAddr = uintptr(start << _PageShift) // ここでstartAddrが初期化される
	span.npages = npages
	span.allocCount = 0
	span.sizeclass = 0
	// ... (その他の初期化) ...
}
```
新しい`mspan`が作成され、初期化される際に、`start`ページIDから`startAddr`が計算され、`mspan`構造体内に保存されます。

### `startAddr`の更新 (`mheap.freeSpanLocked`関数内, `src/runtime/mheap.go`)

```go
func (h *mheap) freeSpanLocked(s *mspan, acctinuse, acctidle bool, unusedsince int64) {
	// ... (既存のロジック) ...
	if t != nil && t.state == _MSpanFree {
		// ... (スパン結合ロジック) ...
		s.start = t.start
		s.startAddr = uintptr(s.start << _PageShift) // 結合後の新しいstartAddrを更新
		s.npages += t.npages
		// ... (その他の更新) ...
	}
	// ... (既存のロジック) ...
}
```
`mheap.freeSpanLocked`関数は、解放されたスパンを管理し、隣接する空きスパンを結合するロジックを含んでいます。スパンが結合されて新しい大きなスパンが形成される場合、その新しいスパンの`start`ページIDに基づいて`startAddr`が再計算され、更新されます。

これらの変更により、`mspan`の基底アドレスは一度計算されてキャッシュされ、以降は高速にアクセスできるようになります。

    *   `mheap.freeSpanLocked`関数（`src/runtime/mheap.go`）内で、隣接する空きスパンが結合される際に、結合後の新しいスパンの`startAddr`が再計算・設定されます。

4.  **既存コードの更新**:
    ランタイム内の`src/runtime/malloc.go`, `src/runtime/mbitmap.go`, `src/runtime/mcentral.go`, `src/runtime/mgcmark.go`, `src/runtime/mgcsweep.go`, `src/runtime/mheap.go`など、`uintptr(s.start << _PageShift)`というパターンで基底アドレスを計算していたすべての箇所が、`s.base()`を呼び出すように変更されました。

**最適化の効果**:
この変更により、`mspan`の基底アドレスが必要な場所では常に`s.base()`が呼び出され、その内部では既に計算済みの`startAddr`が返されるため、冗長なシフト演算が排除されます。これは、特にGCサイクル中やメモリ割り当てパスなど、`mspan`の基底アドレスが頻繁にアクセスされるホットパスにおいて、わずかながらもパフォーマンスの向上に寄与します。また、基底アドレスの計算ロジックが一箇所に集約されることで、コードの保守性と可読性が向上します。

**メモリフットプリントへの影響**:
`mspan`構造体に`uintptr`型のフィールドが一つ追加されるため、`mspan`インスタンスごとに数バイト（32ビットシステムで4バイト、64ビットシステムで8バイト）のメモリオーバーヘッドが発生します。しかし、`mspan`の数はヒープサイズに比例しますが、このオーバーヘッドは通常、得られるパフォーマンスと保守性の向上に比べて許容範囲内と見なされます。

## コアとなるコードの解説

以下に、変更の核心部分である`mspan`構造体と`mspan.base()`関数の変更、および`startAddr`の初期化箇所のコードスニペットと解説を示します。

### `mspan`構造体の変更 (`src/runtime/mheap.go`)

```go
type mspan struct {
	next *mspan     // next span in list, or nil if none
	prev **mspan    // previous span's next field, or list head's first field if none
	list *mSpanList // For debugging. TODO: Remove.
	//TODO:(rlh) Eliminate start field and use startAddr >> PageShift instead.
	startAddr     uintptr   // uintptr(s.start << _PageShift) aka s.base()
	start         pageID    // starting page number
	npages        uintptr   // number of pages in span
	stackfreelist gclinkptr // list of free stacks, avoids overloading freelist
	// ... (その他のフィールド) ...
}
```
`mspan`構造体に`startAddr`フィールドが追加されました。これは`uintptr`型で、スパンの開始メモリアドレスを直接保持します。コメントにあるように、将来的には`start`フィールドを削除し、`startAddr`からページIDを導出する可能性も示唆されています。

### `mspan.base()`関数の変更 (`src/runtime/mheap.go`)

```go
func (s *mspan) base() uintptr {
	return s.startAddr
}
```
以前は`uintptr(s.start << _PageShift)`という計算を行っていた`base()`関数が、単に`s.startAddr`フィールドの値を返すように変更されました。これにより、`base()`の呼び出しは非常に軽量な操作となります。

### `startAddr`の初期化 (`mspan.init`関数内, `src/runtime/mheap.go`)

```go
func (span *mspan) init(start pageID, npages uintptr) {
	span.prev = nil
	span.list = nil
	span.start = start
	span.startAddr = uintptr(start << _PageShift) // ここでstartAddrが初期化される
	span.npages = npages
	span.allocCount = 0
	span.sizeclass = 0
	// ... (その他の初期化) ...
}
```
新しい`mspan`が作成され、初期化される際に、`start`ページIDから`startAddr`が計算され、`mspan`構造体内に保存されます。

### `startAddr`の更新 (`mheap.freeSpanLocked`関数内, `src/runtime/mheap.go`)

```go
func (h *mheap) freeSpanLocked(s *mspan, acctinuse, acctidle bool, unusedsince int64) {
	// ... (既存のロジック) ...
	if t != nil && t.state == _MSpanFree {
		// ... (スパン結合ロジック) ...
		s.start = t.start
		s.startAddr = uintptr(s.start << _PageShift) // 結合後の新しいstartAddrを更新
		s.npages += t.npages
		// ... (その他の更新) ...
	}
	// ... (既存のロジック) ...
}
```
`mheap.freeSpanLocked`関数は、解放されたスパンを管理し、隣接する空きスパンを結合するロジックを含んでいます。スパンが結合されて新しい大きなスパンが形成される場合、その新しいスパンの`start`ページIDに基づいて`startAddr`が再計算され、更新されます。

これらの変更により、`mspan`の基底アドレスは一度計算されてキャッシュされ、以降は高速にアクセスできるようになります。

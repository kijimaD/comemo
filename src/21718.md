# [インデックス 21718] ファイルの概要

このコミットは、Go言語のリンカライブラリである`liblink`における主要なデータ構造である`Prog`（プログラム命令）と`Addr`（アドレス/オペランド）の移植性向上とドキュメント化に焦点を当てています。特に、`include/link.h`ファイル内の`Addr`構造体の定義が大幅に改訂され、そのフィールドと様々なアドレスエンコーディングタイプに関する詳細なコメントが追加されました。これにより、リンカの内部表現がより明確になり、異なるアーキテクチャ間でのコードの再利用性と保守性が向上しています。

## 変更の背景

Go言語は、様々なCPUアーキテクチャ（x86, ARM, PPC64など）とオペレーティングシステムをサポートするクロスプラットフォーム言語です。リンカは、コンパイルされたオブジェクトファイルを結合して実行可能ファイルを生成する重要なツールであり、その内部構造はターゲットアーキテクチャに依存しないように設計される必要があります。

このコミットの主な背景は、`liblink`（Goリンカのコアライブラリ）が扱う`Prog`と`Addr`というデータ構造の移植性を向上させることにありました。以前の設計では、これらの構造体が特定のアーキテクチャの特性に強く結びついており、異なるプラットフォームへの対応や、アドレス空間配置のランダム化（ASLR）のような現代的なメモリ管理スキームへの適応に課題がありました。

特に、アドレスが絶対メモリ位置として扱われるのではなく、オフセットとして扱われるようにすることで、リンカはより堅牢で再配置可能なバイナリを生成できるようになります。これにより、固定メモリの仮定から生じる問題を回避し、コンパイルされたGoプログラムが多様な環境でより互換性と信頼性を持つようになります。

また、`liblink`の内部構造、特に`Addr`の複雑なエンコーディングに関するドキュメントが不足していたため、リンカのコードベースを理解し、保守することが困難でした。このコミットは、これらの内部構造を明確に文書化することで、将来の開発者がリンカの動作をより容易に理解し、貢献できるようにすることも目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念に関する基本的な知識が役立ちます。

*   **リンカ (Linker)**: コンパイラによって生成されたオブジェクトファイル（機械語コードとデータを含む）を結合し、実行可能なプログラムやライブラリを生成するシステムソフトウェアです。シンボル解決（関数や変数の参照を実際のメモリ位置にマッピングする）や再配置（コード内のアドレス参照を調整する）などのタスクを実行します。
*   **アセンブラ (Assembler)**: アセンブリ言語で書かれたソースコードを機械語コードに変換するプログラムです。Go言語のツールチェーンには、Goのアセンブリ言語（Plan 9アセンブラの派生）を処理する独自のアセンブラが含まれています。
*   **`liblink`**: Go言語のリンカのコア部分を実装しているライブラリです。Goのコンパイラと連携して、最終的なバイナリを生成します。
*   **`Prog` 構造体**: `liblink`において、単一の機械語命令（または擬似命令）を表すデータ構造です。オペコード、ソースオペランド、デスティネーションオペランドなどの情報を含みます。
*   **`Addr` 構造体**: `Prog`構造体の一部として、命令のオペランド（引数）を表すデータ構造です。メモリ参照、レジスタ、定数、ラベルなど、様々な種類のアドレスや値を表現するために使用されます。
*   **オペランド (Operand)**: 命令が操作するデータやアドレスのことです。例えば、`ADD R1, R2, R3`という命令では、`R1`, `R2`, `R3`がオペランドです。
*   **シンボル (Symbol)**: プログラム内の関数名、変数名、ラベルなど、特定のメモリ位置やコードブロックを識別するための名前です。リンカはこれらのシンボルを解決し、実際のメモリアドレスにマッピングします。
*   **再配置 (Relocation)**: リンカがオブジェクトファイルを結合する際に、コード内のアドレス参照を、最終的な実行可能ファイル内の正しいメモリ位置に調整するプロセスです。
*   **アドレス空間配置のランダム化 (ASLR - Address Space Layout Randomization)**: セキュリティ機構の一つで、実行可能ファイルのメモリ上の配置をランダム化することで、攻撃者が特定のコードやデータを予測して悪用するのを困難にします。リンカはASLRに対応するために、絶対アドレスではなく相対アドレスやオフセットを扱う必要があります。
*   **Plan 9 アセンブラ**: Go言語のアセンブラは、Bell LabsのPlan 9オペレーティングシステムで使用されていたアセンブラの構文とセマンティクスをベースにしています。このアセンブラは、一般的なx86アセンブラとは異なる独特の構文を持ちます。

## 技術的詳細

このコミットの技術的な核心は、`include/link.h`ファイル内の`Addr`構造体の再設計と、その使用方法に関する詳細なドキュメントの追加にあります。

**`Addr`構造体の変更点:**

以前の`Addr`構造体は、フィールドの順序や型がアーキテクチャ間で一貫性がなく、また、一部のフィールドが特定のアーキテクチャでのみ使用されるなど、移植性に課題がありました。このコミットでは、`Addr`構造体のフィールドが再編成され、より汎用的な型が使用されています。

*   `offset`フィールドの型が`vlong`から`int64`に変更され、より明確な64ビット整数表現になりました。
*   `type`フィールドが`short`から`int16`に変更されました。
*   `u`ユニオンに`int32 argsize`が追加され、`TEXT`命令の引数サイズを表現できるようになりました。
*   `gotype`フィールドが`LSym*`型で、Goの型記述子へのポインタとして明確化されました。
*   内部使用されるフィールド（`class`, `etype`, `node`, `width`）が、どのコンポーネント（`liblink`、`5g/6g/8g`など）によって使用されるかがコメントで明記されました。

**`Addr`エンコーディングのドキュメント化:**

このコミットの最も重要な変更点の一つは、`Addr`が表現できる様々なオペランドの形式とそのエンコーディング方法に関する詳細なコメントが追加されたことです。これにより、`liblink`がアセンブリコードのオペランドをどのように解析し、内部的に表現するかが明確になりました。

具体的には、以下のオペランド形式が詳細に説明されています。

1.  **メモリ参照 (`sym±offset(symkind)(reg)(index*scale)`)**:
    *   `&sym(symkind) + offset + reg + index*scale`という形式のメモリ参照。
    *   `type = TYPE_MEM`としてエンコードされます。
    *   `name`、`sym`、`offset`、`reg`、`index`、`scale`フィールドが対応します。
2.  **実効アドレス (`$<mem>`)**:
    *   メモリ参照`<mem>`の実効アドレス。
    *   `type = TYPE_ADDR`としてエンコードされます。
    *   ARMおよびPPC64では、歴史的な理由から`TYPE_CONST`として扱われる場合があることが注記されています。
3.  **整数リテラル (`$<±integer value>`)**:
    *   `$<mem>`の特殊なケースで、オフセットのみが存在する場合。
    *   `type = TYPE_CONST`としてエンコードされます。
4.  **間接参照 (`*<mem>`)**:
    *   メモリ参照`<mem>`を介した間接参照。主にx86の`CALL/JMP *sym(SB)`で使用されます。
    *   `type = TYPE_INDIR`としてエンコードされます。
5.  **浮動小数点リテラル (`$<floating point literal>`)**:
    *   浮動小数点定数値。
    *   `type = TYPE_FCONST`としてエンコードされ、`u.dval`に値が格納されます。
6.  **文字列リテラル (`$<string literal, up to 8 chars>`)**:
    *   文字列定数値（`DATA`命令の生バイト）。
    *   `type = TYPE_SCONST`としてエンコードされ、`u.sval`に値が格納されます。
7.  **レジスタ名 (`<register name>`)**:
    *   任意のレジスタ（整数、浮動小数点、制御、セグメントなど）。
    *   `type = TYPE_REG`としてエンコードされ、`reg`にレジスタ番号が格納されます。
8.  **PC相対分岐 (`x(PC)`)**:
    *   プログラムカウンタ（PC）相対の分岐ターゲット。
    *   `type = TYPE_BRANCH`としてエンコードされ、`u.branch`に`Prog*`参照、または`offset`にターゲットPCが格納されます。
9.  **`TEXT`命令の引数 (`$±x-±y`)**:
    *   ローカルフレームサイズ`x`と引数サイズ`y`を指定する`TEXT`命令の最終引数。
    *   `type = TYPE_TEXTSIZE`としてエンコードされ、`offset`に`x`、`u.argsize`に`y`が格納されます。
10. **シフトされたレジスタ値 (ARM固有) (`reg<<shift`, `reg>>shift`, `reg->shift`, `reg@>shift`)**:
    *   ARMアーキテクチャ固有のシフト操作を含むレジスタ値。
    *   `type = TYPE_SHIFT`としてエンコードされ、`offset`にシフトタイプとカウント情報が格納されます。
11. **デスティネーションレジスタペア (`(reg, reg)`)**:
    *   命令の最終引数として使用されるデスティネーションレジスタのペア。
    *   `type = TYPE_REGREG`としてエンコードされ、`reg`に最初のレジスタ、`offset`に2番目のレジスタが格納されます。

**列挙型 (`enum`) の導入:**

`Addr`構造体の`name`フィールドと`type`フィールドで使用される定数として、`NAME_NONE`、`NAME_EXTERN`などの`NAME_`プレフィックスを持つ列挙型と、`TYPE_NONE`、`TYPE_BRANCH`などの`TYPE_`プレフィックスを持つ列挙型が導入されました。これにより、マジックナンバーの使用が避けられ、コードの可読性と保守性が向上しています。

**`Prog`構造体の変更点:**

*   `reg`フィールドの型が`uchar`から`int16`に変更され、より広い範囲のレジスタ番号を表現できるようになりました。
*   `forwd`, `pcond`, `comefrom`, `pcrel`, `optab`, `back`, `ft`, `tt`, `isize`といった内部使用されるフィールドについて、どのアーキテクチャやコンポーネント（例: `amd64`, `386`, `arm`, `ppc64`）によって使用されるかがコメントで明記されました。これにより、これらのフィールドの役割がより明確になり、移植性に関する考慮事項が示唆されています。

**`LinkArch`構造体の変更点:**

*   `addstacksplit`関数ポインタが`preprocess`に名称変更されました。これは、スタックスプリットの追加だけでなく、より一般的な前処理タスクをカバーすることを示唆しています。
*   `D_ADDR`, `D_AUTO`などのアーキテクチャ固有の定数フィールドが`LinkArch`構造体から削除されました。これは、これらの値が新しい`Addr`構造体の`type`や`name`フィールドの列挙型によってより汎用的に扱われるようになったためと考えられます。これにより、`LinkArch`構造体自体もより移植性が高まり、アーキテクチャ固有の定数を直接持つ必要がなくなりました。

これらの変更は、Goリンカの内部表現をより抽象化し、特定のアーキテクチャへの依存を減らすことで、将来的な新しいアーキテクチャのサポートや、既存アーキテクチャでの最適化を容易にすることを目的としています。また、詳細なドキュメントは、リンカの複雑な動作を理解するための貴重なリソースとなります。

## コアとなるコードの解説

### `Addr`構造体の再定義とドキュメント化

```c
// include/link.h の変更点の一部抜粋

// An Addr is an argument to an instruction.
// The general forms and their encodings are:
// ... (詳細なコメントが続く) ...

struct Addr
{
    int16   type; // could be int8
    int16   reg;
    int16   index;
    int8    scale;
    int8    name;
    int64   offset;
    LSym*   sym;

    union
    {
        char    sval[8];
        float64 dval;
        Prog*   branch;
        int32   argsize;    // for 5l, 8l
    } u;

    LSym* gotype;

    int8    class;  // for internal use by liblink
    uint8   etype; // for internal use by 5g, 6g, 8g
    void*   node; // for internal use by 5g, 6g, 8g
    int64   width; // for internal use by 5g, 6g, 8g
};
```

この変更は、`Addr`構造体の内部表現を標準化し、異なるアーキテクチャ間での一貫性を高めることを目的としています。特に、`offset`が`int64`になったことで、より大きなアドレス空間を扱うことが可能になり、`type`や`reg`などのフィールドがより明確な型を持つようになりました。

追加されたコメントは、`Addr`がどのように様々なアセンブリ言語のオペランド（メモリ参照、定数、レジスタ、分岐ターゲットなど）を表現するかを詳細に説明しています。これにより、Goリンカの内部動作を理解するための重要なガイドラインが提供されます。例えば、`sym±offset(symkind)(reg)(index*scale)`のような複雑なメモリ参照が、`Addr`構造体のどのフィールドにどのようにマッピングされるかが明確に記述されています。これは、リンカがアセンブリコードを解析し、内部的な命令表現に変換する際のロジックを理解する上で不可欠です。

### 新しい列挙型

```c
// include/link.h の変更点の一部抜粋

enum {
    NAME_NONE = 0,
    NAME_EXTERN,
    NAME_STATIC,
    NAME_AUTO,
    NAME_PARAM,
};

enum {
    TYPE_NONE = 0,
    TYPE_BRANCH = 5, // avoid accidental conflicts with NAME_*
    TYPE_TEXTSIZE,
    TYPE_MEM,
    TYPE_CONST,
    TYPE_FCONST,
    TYPE_SCONST,
    TYPE_REG,
    TYPE_ADDR,
    TYPE_SHIFT,
    TYPE_REGREG,
    TYPE_REGREG2,
    TYPE_INDIR,
};
```

これらの列挙型は、`Addr`構造体の`name`フィールドと`type`フィールドで使用されるシンボリックな定数を定義します。以前はマジックナンバーやアーキテクチャ固有の定数が使用されていた可能性がありましたが、これらの列挙型を導入することで、コードの可読性が大幅に向上し、リンカの内部状態をより明確に表現できるようになりました。例えば、`TYPE_MEM`はメモリ参照を、`TYPE_REG`はレジスタを、`TYPE_BRANCH`は分岐ターゲットをそれぞれ表します。これにより、リンカのコードを読んだ際に、各フィールドが何を示しているのかが一目でわかるようになります。

### `Prog`構造体の変更

```c
// include/link.h の変更点の一部抜粋

struct  Prog
{
    // ...
    // operands
    Addr    from;
    int16   reg; // arm, ppc64 only (e.g., ADD from, reg, to);
                 // starts at 0 for both GPRs and FPRs;
                 // also used for ADATA width on arm, ppc64
    Addr    from3; // ppc64 only (e.g., RLWM/FMADD from, reg, from3, to)
    Addr    to;

    // ...
    // for liblink internal use
    Prog*   forwd;
    Prog*   pcond;
    Prog*   comefrom;   // amd64, 386
    Prog*   pcrel;  // arm
    int32   spadj;
    uint16  mark;
    uint16  optab;  // arm, ppc64
    uchar   back;   // amd64, 386
    uchar   ft;     // oclass cache
    uchar   tt;     // oclass cache
    uchar   isize;  // amd64, 386
    // ...
};
```

`Prog`構造体の`reg`フィールドが`uchar`から`int16`に変更されたことで、より多くのレジスタを表現できるようになり、将来的な拡張性や異なるアーキテクチャでのレジスタセットへの対応が容易になります。また、`comefrom`, `pcrel`, `optab`, `back`, `isize`などの内部フィールドに、それがどのアーキテクチャ（`amd64`, `386`, `arm`, `ppc64`）で主に使われるかを示すコメントが追加されました。これは、リンカのコードがアーキテクチャ固有の最適化や処理を含むことを示しており、コードの移植性を高めるための努力の一環として、各フィールドの役割を明確にしています。

### `LinkArch`構造体の変更

```c
// include/link.h の変更点の一部抜粋

struct LinkArch
{
    // ...
    void    (*preprocess)(Link*, LSym*); // 旧 addstacksplit
    void    (*assemble)(Link*, LSym*);
    // ...
    // 削除された D_ADDR, D_AUTO などのフィールド
};
```

`addstacksplit`が`preprocess`に名称変更されたことは、この関数ポインタがスタックスプリットの処理だけでなく、より広範なリンカの前処理タスクを担うようになったことを示唆しています。これにより、リンカのアーキテクチャ固有の処理をより柔軟にカスタマイズできるようになります。

また、`D_ADDR`などのアーキテクチャ固有の定数フィールドが削除されたことは、これらの情報が`Addr`構造体の新しい`type`や`name`列挙型によってより汎用的に扱われるようになったことを意味します。これにより、`LinkArch`構造体自体がアーキテクチャ固有の定数を持つ必要がなくなり、リンカの全体的な設計がよりクリーンで移植性の高いものになりました。

これらの変更は、Goリンカの内部構造をより堅牢で、理解しやすく、そして何よりも移植性の高いものにするための重要なステップです。特に、`Addr`構造体への詳細なドキュメントの追加は、Goの低レベルな部分に貢献しようとする開発者にとって非常に価値のある情報源となります。

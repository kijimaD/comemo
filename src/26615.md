# [インデックス 26615] ファイルの概要

このコミットは、Go言語のビルドプロセスにおける決定論的（Deterministic）な挙動を強化することを目的としています。具体的には、コンパイラフラグの追加とELFシンボルテーブルへの変更を通じて、ビルドの再現性を高め、異なる環境や時間でビルドされたバイナリが同一になるように改善しています。これにより、ビルドシステムにおける信頼性と検証可能性が向上します。

## 元コミット内容

`cmd/go`, `cmd/link`: ビルドを決定論的にする

コンパイラがサポートしている場合、以下のフラグを追加する:
  - `-gno-record-gcc-switches`
  - `-fdebug-prefix-map=$WORK=/tmp/go-build`

ELFの`.symtab`に空の`NAME`シンボルを追加する。`GNU ld`は`NAME`シンボルが存在しない場合に追加するため、我々自身で追加することで、リンカの一時ディレクトリへの参照が追加されるのを防ぐ。

`-fdebug-prefix-map`をサポートするコンパイラ（gcc、近い将来のclang）に対しては、Issue #13247 を修正する。

## 変更の背景

Go言語のビルドプロセスにおいて、生成されるバイナリがビルド環境やビルド時刻によって異なるという問題がありました。これは「非決定論的ビルド（Non-deterministic builds）」と呼ばれ、ソフトウェアの検証、デバッグ、セキュリティ監査において深刻な問題を引き起こす可能性があります。例えば、同じソースコードからビルドされた2つのバイナリが異なる場合、どちらが正当なものか、あるいは改ざんされていないかを判断するのが困難になります。

このコミットは、特に以下の要因によって引き起こされる非決定性を排除することを目的としています。

1.  **デバッグ情報内のパス**: コンパイラが生成するデバッグ情報（DWARFなど）には、ソースファイルの絶対パスやビルド時の一時ディレクトリのパスが含まれることがあります。これらのパスはビルド環境によって異なるため、結果としてバイナリのハッシュ値が変化してしまいます。
2.  **リンカによるシンボル追加**: `GNU ld`のようなリンカは、特定のシンボル（特にファイル名を示す`NAME`シンボル）がオブジェクトファイルに存在しない場合、自動的に追加することがあります。この際、リンカはビルド時の一時ディレクトリのパスをそのシンボルに含めることがあり、これもまた非決定性の原因となります。

これらの問題を解決し、Goのビルドがより信頼性の高い、再現可能なものとなるように、本コミットが導入されました。

## 前提知識の解説

### 決定論的ビルド (Deterministic Builds / Reproducible Builds)

決定論的ビルドとは、特定のソースコード、ビルドツール、およびビルド環境が与えられた場合、常にビット単位で同一の出力バイナリを生成するビルドプロセスのことを指します。これにより、以下の利点が得られます。

*   **検証可能性**: ユーザーは、提供されたバイナリが本当に特定のソースコードからビルドされたものであることを独立して検証できます。これはセキュリティ監査や信頼性確保において非常に重要です。
*   **デバッグの容易さ**: 問題が発生した際に、特定のビルド環境に依存しない再現性のあるデバッグが可能になります。
*   **キャッシュの効率化**: ビルドシステムは、入力が同じであれば出力も同じであると確信できるため、ビルド成果物のキャッシュをより効率的に利用できます。

非決定性の一般的な原因には、ビルド時刻のタイムスタンプ、環境変数、一時ファイルのパス、コンパイラのバージョンやフラグ、リンカの挙動などが挙げられます。

### コンパイラフラグ

*   **`-gno-record-gcc-switches`**: このGCC/Clangコンパイラフラグは、デバッグ情報（DWARF）にコンパイラが使用したコマンドラインスイッチ（フラグ）を記録しないように指示します。これらのスイッチはビルド環境によって微妙に異なる場合があり、バイナリの非決定性を引き起こす可能性があるため、これを抑制することで決定性を高めます。
*   **`-fdebug-prefix-map=OLD=NEW`**: このGCC/Clangコンパイラフラグは、デバッグ情報内のパスをマッピング（置換）するために使用されます。`OLD`で指定されたプレフィックスを持つパスを`NEW`で指定されたプレフィックスに置き換えます。このコミットでは、`$WORK`（Goのビルドプロセスが使用する一時作業ディレクトリ）のパスを`/tmp/go-build`という固定のパスにマッピングしています。これにより、異なる環境でビルドされたとしても、デバッグ情報内のパスが常に同じになり、バイナリの同一性が保たれます。

### ELF (Executable and Linkable Format)

ELFは、Unix系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリ、コアダンプなどを格納するために使用される標準的なファイル形式です。

*   **`.symtab` (Symbol Table)**: ELFファイル内のセクションの一つで、プログラム内のシンボル（変数名、関数名など）とそのアドレスや型などの情報が格納されています。デバッグやリンキングの際に使用されます。
*   **`NAME`シンボル**: 特定のリンカ（特に`GNU ld`）は、オブジェクトファイルにファイル名を示す`NAME`シンボルが存在しない場合、自動的にこれを追加することがあります。この際、リンカはビルド時の一時ディレクトリのパスをこのシンボルに含めることがあり、これが非決定性の原因となります。

## 技術的詳細

このコミットは、Goのビルドプロセスにおける非決定性を排除するために、主に2つのアプローチを取っています。

1.  **コンパイラフラグによるデバッグ情報の正規化**:
    *   `src/cmd/go/build.go`内の`ccompilerCmd`関数が変更され、Cgoコードをコンパイルする際にGCCまたはClangに渡されるフラグが調整されます。
    *   `b.gccSupportsFlag("-fdebug-prefix-map=a=b")`という新しいヘルパー関数が導入され、コンパイラが`-fdebug-prefix-map`フラグをサポートしているかどうかが動的にチェックされます。
    *   もしサポートされていれば、`-gno-record-gcc-switches`と`-fdebug-prefix-map=$WORK=/tmp/go-build`の2つのフラグがコンパイラに渡されます。
        *   `-gno-record-gcc-switches`は、コンパイラのコマンドラインオプションがデバッグ情報に記録されるのを防ぎ、ビルド環境による差異をなくします。
        *   `-fdebug-prefix-map=$WORK=/tmp/go-build`は、Goのビルドプロセスが使用する一時作業ディレクトリ（`b.work`）の絶対パスを、デバッグ情報内で常に`/tmp/go-build`という固定のパスに置き換えます。これにより、異なるマシンや異なるビルドセッションでビルドされた場合でも、デバッグ情報内のパスが統一され、バイナリの同一性が保たれます。

2.  **リンカによる`NAME`シンボル追加の抑制**:
    *   `src/cmd/link/internal/ld/symtab.go`内の`Asmelfsym`関数が変更されます。
    *   `putelfsyment(0, 0, 0, STB_LOCAL<<4|STT_FILE, SHN_ABS, 0)`という呼び出しが追加され、ELFシンボルテーブルに空の`FILE`タイプのローカルシンボルが明示的に追加されます。
    *   この「空の`NAME`シンボル」は、`GNU ld`がオブジェクトファイルに`FILE`シンボルが存在しない場合に、ビルド時の一時ディレクトリへの参照を含む`FILE`シンボルを自動的に追加する挙動を抑制するために導入されます。Goのリンカが自身でこのシンボルを追加することで、`GNU ld`が余計な情報を挿入するのを防ぎ、結果としてバイナリの非決定性を排除します。

### `gccSupportsFlag`関数の詳細

*   このコミットでは、コンパイラが特定のフラグをサポートしているかを効率的にチェックするための`gccSupportsFlag`関数が導入されています。
*   この関数は、`b.flagCache`というマップを使用して、一度チェックしたフラグのサポート状況をキャッシュします。これにより、同じフラグに対する複数回のチェックで不要なコンパイラ呼び出しを避けることができます。
*   チェックは、`trivial.c`という空のCソースファイルを指定されたフラグと`-c`（コンパイルのみ）オプションでコンパイルを試みることで行われます。
*   コンパイルが成功し、かつ標準エラー出力に「unrecognized」（認識できない）という文字列が含まれていない場合、そのフラグはサポートされていると判断されます。

### テストケース `TestCgoConsistentResults`

*   `src/cmd/go/go_test.go`に`TestCgoConsistentResults`という新しいテストケースが追加されました。
*   このテストは、Cgoが有効な環境でのみ実行されます。
*   同じCgoプログラム（`cgotest`）を2回ビルドし、それぞれ異なる出力ファイル名（`exe1`, `exe2`）で保存します。
*   ビルドコマンドには、詳細なビルドステップを表示する`-x`フラグが2回目のビルドで追加されますが、これはビルドの決定性に影響を与えないはずです。
*   テストは、生成された2つのバイナリファイル（`exe1`と`exe2`）の内容がビット単位で完全に一致するかどうかを`bytes.Equal`で比較することで、ビルドの決定性を検証します。
*   もしCコンパイラが`-fdebug-prefix-map`をサポートしていない場合は、このテストはスキップされます。これは、このコミットの主要な決定性改善がこのフラグに依存しているためです。

## コアとなるコードの解説

### `src/cmd/go/build.go`の変更

*   `builder`構造体に`flagCache map[string]bool`が追加され、コンパイラフラグのサポート状況をキャッシュするようになりました。これにより、同じフラグのチェックが複数回行われる場合に、コンパイラを繰り返し呼び出すオーバーヘッドを削減します。
*   `ccompilerCmd`関数内で、`b.gccSupportsFlag("-fdebug-prefix-map=a=b")`のチェックが追加されました。このチェックが成功した場合、`-gno-record-gcc-switches`と`-fdebug-prefix-map=`b.work`=/tmp/go-build`の2つのフラグがCコンパイラに渡されます。
    *   `b.work`はGoのビルドプロセスが使用する一時作業ディレクトリの絶対パスです。これを`/tmp/go-build`という固定のパスにマッピングすることで、デバッグ情報内のパスが正規化され、ビルドの決定性が向上します。
*   `gccSupportsNoPie`関数が`b.gccSupportsFlag("-no-pie")`を呼び出すように変更され、汎用的なフラグサポートチェックメカニズムを利用するようになりました。
*   新しく追加された`gccSupportsFlag`関数は、指定されたコンパイラフラグがサポートされているかをテストします。
    *   まず、`flagCache`をチェックして、以前にこのフラグのサポート状況が確認されているかを確認します。
    *   キャッシュにない場合、`trivial.c`という空のCファイルを作成し、指定されたフラグと`-c`オプションを付けてコンパイラを呼び出します。
    *   コンパイラの出力に「unrecognized」という文字列が含まれておらず、かつエラーが発生しなかった場合、フラグはサポートされていると判断され、結果がキャッシュされます。

### `src/cmd/go/go_test.go`の変更

*   `TestCgoConsistentResults`という新しいテスト関数が追加されました。
*   このテストは、Cgoが有効な場合にのみ実行されます。
*   `tg.run("build", "-o", exe1, "cgotest")`と`tg.run("build", "-x", "-o", exe2, "cgotest")`の2つのビルドコマンドを実行し、それぞれ異なる出力ファイル名でCgoプログラムをビルドします。`-x`フラグは詳細なビルドステップを表示しますが、最終的なバイナリの内容には影響しないはずです。
*   `tg.doGrepMatch(`-fdebug-prefix-map=\$WORK`, &tg.stderr)`で、ビルド中に`-fdebug-prefix-map`フラグが実際に使用されたかどうかを確認します。これが使用されていない場合（つまり、Cコンパイラがこのフラグをサポートしていない場合）、テストはスキップされます。
*   最後に、`bytes.Equal(b1, b2)`を使用して、生成された2つのバイナリファイルの内容がビット単位で同一であるかを検証します。これにより、ビルドの決定性が保証されていることを確認します。

### `src/cmd/link/internal/ld/symtab.go`の変更

*   `Asmelfsym`関数内で、`putelfsyment(0, 0, 0, STB_LOCAL<<4|STT_FILE, SHN_ABS, 0)`という行が追加されました。
*   このコードは、ELFシンボルテーブルに`FILE`タイプのローカルシンボルを明示的に追加します。
*   このシンボルは、`GNU ld`のような外部リンカが、`FILE`シンボルが存在しない場合に、ビルド時の一時ディレクトリへの参照を含む`FILE`シンボルを自動的に追加するのを防ぐためのものです。Goのリンカが自身でこの「空の」`FILE`シンボルを提供することで、外部リンカによる非決定的な情報の挿入を回避し、バイナリの決定性を確保します。

## 変更の背景

このコミットの主な目的は、Goコンパイラ (`cmd/compile`) 内部での行番号報告のコードを簡素化することです。以前のコードでは、ファイルの行情報を文字列として取得するために `Ctxt.Line(int(lineno))` という形式が繰り返し使用されていました。このパターンは冗長であり、コードの可読性を低下させる可能性がありました。

`linestr` という新しいヘルパー関数を導入することで、この共通の処理をカプセル化し、コンパイラコード全体での行番号報告の記述をより簡潔に、そして一貫性のあるものにすることが狙いです。これにより、コードの保守性が向上し、将来的な変更やデバッグが容易になります。

## 前提知識の解説

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。`src/cmd/compile` ディレクトリ以下にそのソースコードが格納されています。コンパイルプロセスは、字句解析、構文解析、型チェック、中間表現の生成、最適化、コード生成など、複数のフェーズに分かれています。
*   **`gc` パッケージ**: `cmd/compile` の中でも、Go言語のフロントエンドとバックエンドの大部分を担う主要なパッケージです。型システム、宣言、エスケープ解析、コード生成など、コンパイラの核となる機能がここに実装されています。
*   **`Ctxt` (Context)**: コンパイラのグローバルなコンテキストオブジェクトです。コンパイル中に必要な様々な情報（ファイルセット、エラーハンドラ、シンボルテーブルなど）を保持しています。`Ctxt.Line` メソッドは、特定の行番号に対応するファイル名と行番号の文字列表現（例: `filename.go:123`）を生成するために使用されます。
*   **`lineno`**: コンパイラ内部で現在処理しているソースコードの行番号を示す `int32` 型の変数です。
*   **可読性と保守性**: ソフトウェア開発において、コードがどれだけ理解しやすく、変更しやすいかを示す重要な指標です。冗長なコードや複雑なロジックは可読性と保守性を低下させます。ヘルパー関数の導入は、これらの品質を向上させる一般的な手法です。

## 技術的詳細

このコミットの技術的な核心は、`Ctxt.Line(int(lineno))` という表現を `linestr(lineno)` という新しいヘルパー関数呼び出しに置き換えることです。

1.  **`linestr` 関数の導入**:
    `src/cmd/compile/internal/gc/subr.go` に `linestr` という新しい関数が追加されました。この関数は `int32` 型の行番号 `line` を引数に取り、`Ctxt.Line(int(line))` を呼び出してその結果を文字列として返します。

    ```go
    func linestr(line int32) string {
        return Ctxt.Line(int(line))
    }
    ```

2.  **既存コードのリファクタリング**:
    `dcl.go`, `esc.go`, `gen.go`, `lex.go`, `ssa.go`, `subr.go` の各ファイルで、`fmt.Printf` や `yyerrorl` などの関数呼び出し内で直接 `Ctxt.Line(int(lineno))` を使用していた箇所が、すべて `linestr(lineno)` に変更されました。

    例えば、`dcl.go` の以下の行:
    `-		fmt.Printf("\t%v push %v %p\n", Ctxt.Line(int(lineno)), s, s.Def)`
    は、
    `+		fmt.Printf("\t%v push %v %p\n", linestr(lineno), s, s.Def)`
    のように変更されています。

3.  **メリット**:
    *   **コードの簡潔化**: 繰り返し現れる `Ctxt.Line(int(lineno))` という長い記述が `linestr(lineno)` という短い記述に置き換わることで、コードがより簡潔になります。
    *   **一貫性の向上**: 行番号のフォーマット処理が一箇所に集約されるため、コンパイラ全体での行番号報告のスタイルに一貫性が生まれます。
    *   **保守性の向上**: もし将来的に行番号のフォーマット方法を変更する必要が生じた場合、`linestr` 関数一つを修正するだけで済みます。以前のように多数の箇所を個別に修正する必要がなくなります。
    *   **型変換の隠蔽**: `lineno` が `int32` 型であるのに対し、`Ctxt.Line` は `int` 型を引数に取ります。`linestr` 関数がこの `int32` から `int` への型変換 (`int(line)`) を内部で処理するため、呼び出し側ではこの詳細を意識する必要がなくなります。

この変更は、コンパイラの機能自体には影響を与えませんが、コンパイラの内部コードの品質と保守性を向上させるための典型的なリファクタリングの一例です。

## コアとなるコードの解説

追加された `linestr` 関数は非常にシンプルです。`int32` 型の `line` を受け取り、それを `int` 型にキャストして `Ctxt.Line` メソッドに渡しています。`Ctxt.Line` は、コンパイラのコンテキスト (`Ctxt`) が持つ情報（ファイル名や行番号の履歴など）に基づいて、指定された行番号に対応するソースコード上の位置を「ファイル名:行番号」のような形式の文字列として返します。

この `linestr` 関数が導入されたことで、コンパイラ内のデバッグ出力やエラーメッセージの生成箇所で、冗長だった `Ctxt.Line(int(lineno))` の記述が `linestr(lineno)` に置き換えられました。これにより、コードの意図がより明確になり、行番号の文字列化という共通の処理が抽象化されました。これは、Goコンパイラのような大規模なコードベースにおいて、コードの品質を維持し、開発効率を高めるための良いプラクティスです。

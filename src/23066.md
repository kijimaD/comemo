# [インデックス 23066] ファイルの概要

このコミットは、Go言語のコンパイラおよびツールチェインの一部である `go/exact` パッケージのAPIを将来にわたって互換性を保つように変更するものです。具体的には、数値リテラルから `exact.Value` を生成する `MakeFromLiteral` 関数に `prec` (precision: 精度) パラメータを追加し、単項演算を行う `UnaryOp` 関数も同様に `prec` パラメータを受け入れるように変更しています。これにより、将来的にGoの定数に精度の制限を設けることが可能になるための準備が行われています。

## 変更の背景

Go言語では、数値定数（整数、浮動小数点数、複素数）はコンパイル時に「任意精度 (arbitrary precision)」で扱われます。これは、定数計算においてオーバーフローが発生せず、非常に高い精度で中間計算が行われることを意味します。例えば、`1e100 * 1e100 / 1e100` のような計算は、途中で通常の浮動小数点数の範囲を超えても、最終的な結果が表現可能であれば正確に計算されます。

しかし、この「任意精度」は言語仕様上の理想であり、コンパイラ内部ではその表現に制限があります。例えば、整数定数は少なくとも256ビット、浮動小数点定数は少なくとも256ビットの仮数部と16ビットの符号付き二進指数部を持つ必要があります。

このコミットの背景には、将来的に `go/types` パッケージが定数の精度に上限を設ける可能性を考慮したAPIの「将来性確保 (future-proof)」があります。現在のGoの定数システムでは、`go/exact` パッケージが任意精度の数値を表現し、`go/types` パッケージがその型チェックと定数評価を行います。このコミットは、`go/types` が定数の精度を制限する必要が生じた場合に、`go/exact` のAPIを後方互換性を損なうことなく対応できるようにするための準備です。

具体的には、定数計算の結果が指定された精度を超えた場合に、特別な「Overflow」値を返すようなメカニズムを導入する可能性を見越しています。これは、現在の `Unknown` 値（例えば、無効なリテラルなどから生成される）と同様の概念です。この変更は、将来の大きなAPI変更を避けるための最小限の修正として位置づけられています。

## 前提知識の解説

*   **`go/exact` パッケージ**: Go言語のコンパイラおよび関連ツールで使用されるパッケージで、任意精度の数値（整数、浮動小数点数、複素数）を表現および操作するための機能を提供します。Goの定数計算の基盤となっています。`exact.Value` は、これらの任意精度の数値を表すインターフェースです。
*   **`go/types` パッケージ**: Go言語の型チェッカーとして機能するパッケージです。Goのソースコードを解析し、型情報を構築し、型エラーを検出します。定数評価もこのパッケージの重要な役割の一つであり、`go/exact` パッケージと連携して定数値を計算します。
*   **`token.Token`**: Go言語の字句解析器（lexer）が生成するトークンを表す型です。例えば、`token.INT` は整数リテラル、`token.ADD` は加算演算子などを表します。
*   **数値リテラルの精度と定数**: Goでは、`1.0 / 3.0` のような浮動小数点リテラルや、`1 << 100` のような整数リテラルは、型が明示的に指定されない限り「型なし定数 (untyped constant)」として扱われます。これらの型なし定数は、コンパイル時に任意精度で計算されます。例えば、`const x = 1.0 / 3.0` の `x` は、`float64` に代入されるまで `0.333...` のような無限の精度を持つかのように扱われます。
*   **オーバーフロー (Overflow)**: 通常、数値計算において、結果がその型で表現できる最大値を超えた場合に発生する現象です。Goの任意精度定数では、コンパイル時のオーバーフローは通常発生しませんが、特定の型に代入される際に値が大きすぎる場合はコンパイルエラーとなります。このコミットで言及されている「Overflow」は、将来的に `go/exact` が特定の精度制限を超えた場合に返す可能性のある特別な状態を指します。
*   **`uint` 型**: 符号なし整数型です。`prec` パラメータが `uint` 型であることは、精度が非負の値であることを示唆しています。

## 技術的詳細

このコミットの主要な変更点は、`go/exact` パッケージ内の2つの重要な関数 `MakeFromLiteral` と `UnaryOp` のシグネチャ変更です。

1.  **`MakeFromLiteral` 関数の変更**:
    *   変更前: `func MakeFromLiteral(lit string, tok token.Token) Value`
    *   変更後: `func MakeFromLiteral(lit string, tok token.Token, prec uint) Value`
    *   新たに `prec uint` パラメータが追加されました。この `prec` は、数値リテラルから `exact.Value` を生成する際に、その数値の精度の上限を指定するために導入されました。
    *   しかし、コミット時点では `prec > 0` の場合は `panic("limited precision not supported")` となり、制限された精度はサポートされていません。これは、このパラメータが将来の機能拡張のために予約されていることを明確に示しています。
    *   この変更により、`go/types` パッケージが定数評価を行う際に、特定のコンテキストで定数の精度を制限する必要が生じた場合でも、`MakeFromLiteral` を呼び出す際にその制限を `prec` パラメータとして渡すことができるようになります。

2.  **`UnaryOp` 関数の変更**:
    *   変更前: `func UnaryOp(op token.Token, y Value, size int) Value`
    *   変更後: `func UnaryOp(op token.Token, y Value, prec uint) Value`
    *   `size int` パラメータが `prec uint` に変更されました。この関数は単項演算（例: `-x`, `^x`）を実行します。
    *   特に `token.XOR` (ビット反転) 演算において、符号なし型の場合に結果の精度を制限するために `size` パラメータが使用されていました。この `size` はバイト単位でしたが、`prec` はビット単位の精度を表すように変更されました。
    *   変更後も、`prec > 0` の場合にビット反転の結果を `prec` で指定されたビット数に制限するロジックが導入されています。具体的には、`z.AndNot(&z, new(big.Int).Lsh(big.NewInt(-1), prec))` という演算が行われます。これは、`z &^= (-1) << prec` と同等で、`prec` ビット目より上位のビットをクリアする操作です。

これらの変更は、`go/exact` パッケージが直接的に精度の制限を強制するものではなく、`go/types` パッケージのような上位レイヤーからの指示を受け入れるための準備です。これにより、Goの定数システムがより柔軟になり、将来的な言語仕様の変更や最適化に対応できるようになります。

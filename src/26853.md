## 元コミット内容

このコミットは、Goリンカ（`cmd/link`）において、小さな`[]byte`スライスの読み込み時のメモリ割り当てを最適化することを目的としています。具体的には、`rddata`関数内で発生するメモリ割り当ての回数を削減します。

コミットメッセージによると、この変更によりメモリ割り当ての総数が12%削減されました。

*   変更前: 1,816,664 回
*   変更後: 1,581,591 回

これにより、わずかながら速度の改善ももたらされています。

## 変更の背景

Goプログラムのパフォーマンス最適化において、メモリ割り当て（アロケーション）の回数を減らすことは非常に重要です。特に、頻繁に小さなオブジェクトが割り当てられ、すぐに解放されるようなパターンは、ガベージコレクション（GC）の負荷を増大させ、プログラム全体の実行速度を低下させる原因となります。

Goリンカのようなツールは、大量のデータを処理し、多くの内部データ構造を生成します。この過程で、ファイルからの読み込みやデータ変換のために一時的な`[]byte`スライスが頻繁に作成されます。もしこれらのスライスが毎回ヒープ上に新しく割り当てられると、リンカの実行中に大量のメモリ割り当てとGCが発生し、リンカ自体のパフォーマンスがボトルネックとなる可能性があります。

このコミットは、`rddata`関数が読み込むデータが比較的小さい場合に、新しい`[]byte`スライスを毎回割り当てるのではなく、事前に確保されたバッファを再利用することで、この問題を解決しようとしています。これにより、メモリ割り当ての回数を劇的に減らし、リンカの実行効率を向上させることが狙いです。

## 前提知識の解説

### Goリンカ (`cmd/link`)

Go言語のビルドプロセスは、`go build`コマンドによって実行されますが、その内部ではコンパイラ（`cmd/compile`）とリンカ（`cmd/link`）が連携して動作します。Goリンカは、Goのソースコードから生成されたオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合し、最終的な実行可能バイナリを生成する役割を担います。一般的なシステムリンカとは異なり、GoリンカはGoランタイムの特性（ガベージコレクション、ゴルーチン、スタック管理など）を深く理解しており、Go固有のデータ構造（型情報、シンボルテーブルなど）をバイナリ内に配置します。

### `objfile.go`と`rddata`関数

`src/cmd/link/internal/ld/objfile.go`は、Goリンカの内部パッケージ`cmd/link/internal/ld`の一部であり、オブジェクトファイル（Goのコンパイラが出力する中間ファイル）からデータを読み込むためのユーティリティ関数を提供します。`rddata`関数は、このファイル内で定義されている内部関数の一つで、オブジェクトファイルから可変長のバイトデータを読み込むために使用されます。この関数は、読み込むデータのサイズを先に読み取り、そのサイズに応じた`[]byte`スライスを割り当ててから、実際のデータを読み込むという処理を行っていました。

### Goにおけるスライス (`[]byte`) のメモリ割り当て

Goのスライスは、配列への参照であり、長さ（`len`）と容量（`cap`）を持ちます。スライスを`make([]byte, size)`のように作成すると、指定された`size`の長さと容量を持つ新しい基底配列がヒープ上に割り当てられます（エスケープ解析によってスタックに割り当てられる場合もありますが、ここではヒープ割り当てを前提とします）。

小さなスライスが頻繁に割り当てられる場合、以下のような問題が発生します。
1.  **ヒープ割り当てのオーバーヘッド**: ヒープからのメモリ確保は、スタックからの確保に比べてコストが高いです。
2.  **ガベージコレクションの負荷**: 頻繁に生成される小さなオブジェクトは、ガベージコレクタが追跡し、最終的に回収する必要があるため、GCの実行頻度と時間が長くなる可能性があります。
3.  **キャッシュ効率の低下**: 新しいメモリ領域が頻繁に割り当てられると、CPUキャッシュの局所性が損なわれ、パフォーマンスが低下する可能性があります。

### 小さなバッファの再利用による最適化

Goでは、頻繁に割り当てられる小さなスライスやバッファのメモリ割り当てを最適化するために、いくつかの一般的なパターンがあります。
*   **`sync.Pool`**: オブジェクトのプールを作成し、再利用することで、GCの負荷を軽減します。
*   **事前割り当てとスライス操作**: `make`関数で十分な容量を事前に割り当てておき、必要に応じてスライスを再スライス（`slice[:newLen]`）して使用します。これにより、基底配列の再割り当てとコピーを避けることができます。
*   **共有バッファ**: 特定のサイズ以下の小さなデータに対して、グローバルまたはパッケージレベルで共有されるバッファを定義し、そのバッファの一部をスライスとして切り出して使用します。これにより、ヒープ割り当てを完全に回避し、スタック割り当てに近い効率を実現できます。ただし、共有バッファは並行アクセスに対する注意が必要です。

このコミットは、最後の「共有バッファ」の概念を`rddata`関数に適用することで、メモリ割り当ての最適化を図っています。

## 技術的詳細

このコミットの核心は、`rddata`関数が読み込むデータのサイズに基づいて、メモリ割り当て戦略を切り替える点にあります。

変更前は、`rddata`関数は常に読み込むデータのサイズ`n`に応じて新しい`[]byte`スライスを`make([]byte, n)`で割り当てていました。これは、`n`がどんなに小さくてもヒープ割り当てが発生することを意味します。

変更後は、`rddata`関数は以下のロジックで動作します。

1.  **読み込むデータのサイズ`n`を取得します。**
2.  **サイズ`n`が事前に定義された最大バッファサイズ`rddataBufMax`（1 << 14、つまり16KB）よりも大きい場合**:
    *   従来通り、`make([]byte, n)`を使用して新しい`[]byte`スライスをヒープ上に割り当てます。これは、大きなデータに対しては共有バッファの再利用が現実的ではないためです。
3.  **サイズ`n`が`rddataBufMax`以下の場合**:
    *   パッケージレベルで宣言された共有バッファ`rddataBuf`を再利用しようとします。
    *   まず、現在の`rddataBuf`の残りの容量（`len(rddataBuf)`）が`n`よりも小さい場合、つまり共有バッファに十分なスペースがない場合は、`rddataBuf`を`rddataBufMax`の容量で再作成します。これにより、共有バッファが枯渇した場合にリセットされます。
    *   次に、`rddataBuf`の先頭から`n`バイトを切り出して、`p = rddataBuf[:n:n]`として新しいスライス`p`を作成します。ここで`[:n:n]`という形式は、長さと容量を`n`に設定することを意味します。これにより、`p`は`rddataBuf`の基底配列を共有し、新しいヒープ割り当ては発生しません。
    *   最後に、`rddataBuf`を`rddataBuf[n:]`として更新し、切り出した部分を消費済みとしてマークします。これにより、次の小さな読み込みは`rddataBuf`の残りの部分から行われます。

この戦略により、`rddataBufMax`以下のサイズの`[]byte`スライスは、`rddataBuf`という単一の大きなバッファから効率的に供給されるようになります。これにより、多数の小さなヒープ割り当てが回避され、メモリ割り当ての総数が削減されます。

## コアとなるコードの解説

1.  **`rddataBuf`と`rddataBufMax`の導入**:
    ```go
    var (
    	rddataBuf    = make([]byte, rddataBufMax)
    	rddataBufMax = 1 << 14
    )
    ```
    `rddataBufMax`は、共有バッファの最大サイズを16KB（`1 << 14`）と定義しています。`rddataBuf`は、このサイズで初期化された`[]byte`スライスで、小さな読み込みのための共有バッファとして機能します。これらはパッケージレベルの変数として宣言されており、`objfile.go`内の`rddata`関数が呼び出されるたびに再利用されます。

2.  **`rddata`関数の変更**:
    ```go
    func rddata(f *obj.Biobuf) []byte {
    	var p []byte
    	n := rdint(f) // 読み込むデータのサイズを取得
    	if n > rddataBufMax {
    		// サイズが共有バッファの最大値を超える場合、新しいスライスを割り当てる
    		p = make([]byte, n)
    	} else {
    		// サイズが共有バッファの最大値以下の場合
    		if len(rddataBuf) < n {
    			// 共有バッファの残りが不足している場合、バッファをリセット（再作成）
    			rddataBuf = make([]byte, rddataBufMax)
    		}
    		// 共有バッファから必要な部分をスライスとして切り出す
    		p = rddataBuf[:n:n]
    		// 共有バッファを更新し、切り出した部分を消費済みとする
    		rddataBuf = rddataBuf[n:]
    	}
    	obj.Bread(f, p) // データを読み込む
    	return p
    }
    ```
    *   `n := rdint(f)`: 読み込むバイト数をファイルから取得します。変更前は`rdint64`でしたが、`rdint`に変更されています。これは、読み込むサイズが`int`型で十分であることを示唆しています。
    *   `if n > rddataBufMax`: 読み込むサイズ`n`が共有バッファの最大サイズ`rddataBufMax`（16KB）を超えているかチェックします。
        *   超えている場合: `p = make([]byte, n)`を実行し、従来通り`n`バイトの新しいスライスをヒープに割り当てます。
        *   超えていない場合: 共有バッファ`rddataBuf`を再利用するロジックに入ります。
            *   `if len(rddataBuf) < n`: 現在の`rddataBuf`に残っているバイト数（`len(rddataBuf)`）が、今回読み込む`n`バイトよりも少ない場合、`rddataBuf`は使い果たされているか、残りが不足していると判断されます。この場合、`rddataBuf = make([]byte, rddataBufMax)`によって、`rddataBuf`が新しい16KBのバッファとして再初期化されます。これにより、バッファが枯渇しても常に新しいバッファが利用可能になります。
            *   `p = rddataBuf[:n:n]`: `rddataBuf`の先頭から`n`バイトを切り出して、新しいスライス`p`を作成します。`[:n:n]`という構文は、スライスの長さと容量の両方を`n`に設定するGoのイディオムです。これにより、`p`は`rddataBuf`の基底配列を共有し、新たなメモリ割り当ては発生しません。
            *   `rddataBuf = rddataBuf[n:]`: `rddataBuf`自体を更新し、`n`バイト分だけ先頭をずらします。これにより、次に`rddata`が呼び出された際には、`rddataBuf`の残りの部分が利用されます。
    *   `obj.Bread(f, p)`: 最終的に決定されたスライス`p`に、ファイル`f`からデータを読み込みます。

この変更により、リンカがオブジェクトファイルから小さなバイトデータを読み込む際に、ヒープ割り当ての回数が大幅に削減され、リンカの実行効率が向上します。

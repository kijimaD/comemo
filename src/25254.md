# [インデックス 25254] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージにおいて、HTTPSサーバーでHTTP/2を自動的に有効にする機能を追加するものです。具体的には、`http.Server` 構造体の `TLSNextProto` フィールドが `nil` の場合、つまりユーザーが明示的にプロトコルネゴシエーションを設定していない場合に、標準ライブラリに組み込まれた `x/net/http2` の実装を使用してHTTP/2を有効にします。これにより、GoのHTTPSサーバーがデフォルトでHTTP/2の恩恵を受けられるようになります。

## 元コミット内容

`net/http: enable automatic HTTP/2 if TLSNextProto is nil`

このコミットは、ユーザーがNPN/ALPNマップに何も設定していない場合（`TLSNextProto`が`nil`の場合）に、HTTPS接続に対してHTTP/2をデフォルトで有効にします。もしユーザーがSPDYや別のHTTP/2実装、あるいは`x/net/http2`の新しいバージョンを使用している場合は、標準ライブラリにベンダーされた`x/net/http2`のコピーは使用せず、何も変更しません。

`golang.org/x/net/http2`が引き続きアップストリームとなります。

Issue #6891 を更新します。

## 変更の背景

この変更の背景には、Webプロトコルの進化と、Go言語がその最新技術を容易に利用できるようにするという設計思想があります。

1.  **HTTP/2の普及**: HTTP/2は、HTTP/1.1のパフォーマンス上の課題（ヘッドオブラインブロッキング、効率の悪いヘッダー圧縮など）を解決するために開発されました。多重化、ヘッダー圧縮（HPACK）、サーバープッシュなどの機能により、Webページのロード時間を大幅に短縮できます。このコミットが作成された2015年頃は、HTTP/2の採用が本格化し始めた時期であり、Goの標準ライブラリがこれをサポートすることは非常に重要でした。
2.  **開発者の利便性**: 以前は、GoのHTTPSサーバーでHTTP/2を有効にするには、`x/net/http2`パッケージを明示的にインポートし、`http2.ConfigureServer`関数を呼び出す必要がありました。これは、HTTP/2の恩恵を受けたい多くの開発者にとって、追加の手順を意味しました。このコミットは、`TLSNextProto`が設定されていない場合に自動的にHTTP/2を有効にすることで、開発者が意識することなくHTTP/2のパフォーマンス改善を享受できるようにすることを目的としています。
3.  **後方互換性の維持**: ユーザーが既に`TLSNextProto`を設定してSPDYや独自のプロトコル、あるいは`x/net/http2`の特定のバージョンを使用している場合、その設定を尊重し、自動的なHTTP/2有効化をスキップすることで、既存のアプリケーションの動作を壊さないように配慮されています。
4.  **標準ライブラリへの統合**: `x/net/http2`は元々実験的なパッケージとして開発されていましたが、成熟するにつれて標準ライブラリへの統合が望まれました。このコミットは、その統合の一環として、`net/http`パッケージが`x/net/http2`の機能の一部を内部的に利用し、よりシームレスな体験を提供する道を開きました。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を把握しておく必要があります。

1.  **HTTP/2**:
    *   **多重化 (Multiplexing)**: 複数のリクエストとレスポンスを単一のTCP接続上で同時に送受信できる機能。HTTP/1.1のヘッドオブラインブロッキング問題を解決します。
    *   **ストリーム (Streams)**: 多重化された接続内で、独立した双方向のバイトシーケンス。各HTTPリクエスト/レスポンスは独自のストリームを持ちます。
    *   **ヘッダー圧縮 (HPACK)**: HTTPヘッダーの冗長性を排除し、効率的に圧縮するメカニズム。
    *   **サーバープッシュ (Server Push)**: クライアントがリクエストする前に、サーバーがリソースをクライアントに送信できる機能。
    *   **バイナリフレーミング**: HTTP/2はテキストベースではなく、バイナリプロトコルです。これにより、解析が高速化され、エラーが減少します。

2.  **TLS (Transport Layer Security)**:
    *   HTTPSの基盤となるプロトコルで、通信の暗号化、認証、データの完全性を提供します。
    *   **ALPN (Application-Layer Protocol Negotiation)**: TLSハンドシェイク中に、クライアントとサーバーがどのアプリケーション層プロトコル（例: HTTP/1.1, HTTP/2）を使用するかをネゴシエートするためのTLS拡張。これにより、単一のポート（通常は443）で複数のプロトコルをサポートできます。
    *   **NPN (Next Protocol Negotiation)**: ALPNの先行技術で、同様の目的で使用されましたが、現在はALPNが主流です。Goの`net/http`パッケージでは、`TLSNextProto`マップを通じてこれらのプロトコルネゴシエーションを設定します。

3.  **`net/http`パッケージ**:
    *   Go言語の標準ライブラリで、HTTPクライアントとサーバーの実装を提供します。
    *   `http.Server`構造体: HTTPサーバーの設定を保持する構造体。`TLSNextProto`フィールドは、TLS接続確立後に使用するアプリケーションプロトコルを決定するためのマップです。キーはプロトコル名（例: "h2" for HTTP/2）、値はそのプロトコルを処理する関数です。

4.  **`golang.org/x/net/http2`**:
    *   Go言語のHTTP/2実装を提供する外部パッケージ。標準ライブラリに統合される前は、このパッケージを明示的にインポートしてHTTP/2機能を有効にする必要がありました。このコミットでは、このパッケージのコードが`net/http`内部にベンダー（コピー）され、自動有効化のために利用されます。

5.  **`sync.Once`**:
    *   Go言語の`sync`パッケージに含まれる型で、特定の処理が一度だけ実行されることを保証します。複数のゴルーチンから同時に呼び出されても、指定された関数は一度だけ実行され、その後の呼び出しはブロックされずにすぐに戻ります。初期化処理などでよく使用されます。

## 技術的詳細

このコミットの技術的な核心は、`http.Server`の`Serve`メソッドが呼び出された際に、`TLSNextProto`フィールドの状態をチェックし、必要に応じてHTTP/2を自動的に設定するロジックを追加した点にあります。

1.  **`http.Server`構造体の変更**:
    *   `nextProtoOnce sync.Once`フィールドが追加されました。これは、`setNextProtoDefaults`メソッドが`Serve`メソッド内で一度だけ実行されることを保証するために使用されます。これにより、サーバーのライフサイクル中にHTTP/2の自動設定が複数回試行されることを防ぎます。

2.  **`Serve`メソッドの変更**:
    *   `srv.nextProtoOnce.Do(srv.setNextProtoDefaults)`という行が追加されました。`Serve`メソッドが呼び出されるたびに、この`Do`メソッドが実行されますが、`setNextProtoDefaults`関数自体は`sync.Once`の保証により、サーバーインスタンスにつき一度だけ実行されます。

3.  **`setNextProtoDefaults`メソッドの追加**:
    *   この新しいメソッドは、`http.Server`の`TLSNextProto`フィールドが`nil`であるかどうかをチェックします。
    *   もし`TLSNextProto`が`nil`であれば、`http2ConfigureServer(srv, nil)`が呼び出されます。この`http2ConfigureServer`関数（このコミットでは差分に直接含まれていませんが、`x/net/http2`からベンダーされた内部関数）は、`http.Server`インスタンスにHTTP/2を有効にするために必要な設定（具体的には`TLSNextProto`マップに`"h2"`エントリを追加するなど）を適用します。
    *   もし`TLSNextProto`が`nil`でなければ、ユーザーが既に独自のプロトコルネゴシエーションを設定していると判断し、何も変更しません。これにより、既存のカスタム設定が上書きされることを防ぎます。

4.  **`src/cmd/api/goapi.go`の変更**:
    *   このファイルはGoのAPI定義を生成するためのツールに関連しています。`golang.org/x/`で始まるパッケージのインポートパスを処理する際に、`vendor`ディレクトリを考慮するように変更されました。これは、`x/net/http2`が標準ライブラリ内部にベンダーされることに関連するパス解決の調整です。

5.  **`src/go/build/deps_test.go`の変更**:
    *   Goのビルド依存関係のテストファイルです。`net/http`パッケージが`golang.org/x/net/http2/hpack`に依存することを明示的に追加しています。これは、HTTP/2のヘッダー圧縮（HPACK）機能が`net/http`内部で利用されるようになったことを示しています。

6.  **`src/net/http/serve_test.go`の変更**:
    *   `TestAutomaticHTTP2`という新しいテストケースが追加されました。このテストは、`http.Server`が`TLSNextProto`を明示的に設定しない場合に、HTTP/2が自動的に有効になることを検証します。具体的には、サーバーを起動し、その`TLSNextProto`マップに`"h2"`エントリが存在するかどうかを確認しています。

これらの変更により、GoのHTTPSサーバーは、特別な設定なしにHTTP/2のパフォーマンス上の利点を活用できるようになり、開発者の負担が軽減されます。

## コアとなるコードの解説

### `src/net/http/server.go` の変更点

1.  **`Server` 構造体への `nextProtoOnce` フィールド追加**:
    ```go
    type Server struct {
        // ... 既存フィールド ...
        disableKeepAlives int32     // accessed atomically.
        nextProtoOnce     sync.Once // guards initialization of TLSNextProto in Serve
    }
    ```
    `sync.Once`型の`nextProtoOnce`が追加されました。これは、`setNextProtoDefaults`メソッドが`Serve`メソッドの呼び出し中に一度だけ実行されることを保証するためのものです。これにより、サーバーの初期化フェーズでHTTP/2の自動設定が安全かつ効率的に行われます。

2.  **`Serve` メソッドでの `setNextProtoDefaults` の呼び出し**:
    ```go
    func (srv *Server) Serve(l net.Listener) error {
        defer l.Close()
        var tempDelay time.Duration // how long to sleep on accept failure
        srv.nextProtoOnce.Do(srv.setNextProtoDefaults) // ここが追加
        for {
            // ... 既存の接続受付ループ ...
        }
    }
    ```
    `Serve`メソッドの冒頭で`srv.nextProtoOnce.Do(srv.setNextProtoDefaults)`が呼び出されます。`sync.Once.Do`は、引数として渡された関数（この場合は`srv.setNextProtoDefaults`）を、その`sync.Once`インスタンスに対して一度だけ実行します。これにより、`Serve`が複数回呼び出されても、HTTP/2の自動設定ロジックは一度しか実行されません。

3.  **`setNextProtoDefaults` メソッドの追加**:
    ```go
    func (srv *Server) setNextProtoDefaults() {
        // Enable HTTP/2 by default if the user hasn't otherwise
        // configured their TLSNextProto map.
        if srv.TLSNextProto == nil {
            http2ConfigureServer(srv, nil)
        }
    }
    ```
    この新しいプライベートメソッドは、HTTP/2の自動有効化ロジックをカプセル化しています。
    *   `if srv.TLSNextProto == nil`: ここが最も重要な条件です。もしユーザーが`http.Server`の`TLSNextProto`フィールドに何も設定していない場合（つまり、カスタムのプロトコルネゴシエーションハンドラを提供していない場合）、GoはHTTP/2を自動的に有効にすべきだと判断します。
    *   `http2ConfigureServer(srv, nil)`: この関数は、`x/net/http2`パッケージからベンダーされた（コピーされた）内部関数であり、`srv`（`*http.Server`インスタンス）に対してHTTP/2を有効にするための設定を行います。具体的には、`srv.TLSNextProto`マップに`"h2"`エントリを追加し、HTTP/2ハンドラを関連付けます。これにより、TLSハンドシェイク中にクライアントがHTTP/2をネゴシエートした場合、GoサーバーはHTTP/2プロトコルで通信できるようになります。

### `src/net/http/serve_test.go` の変更点

1.  **`TestAutomaticHTTP2` テスト関数の追加**:
    ```go
    func TestAutomaticHTTP2(t *testing.T) {
        ln, err := net.Listen("tcp", ":0")
        if err != nil {
            t.Fatal(err)
        }
        ln.Close() // immediately (not a defer!)
        var s Server
        if err := s.Serve(ln); err == nil {
            t.Fatal("expected an error")
        }
        on := s.TLSNextProto["h2"] != nil
        if !on {
            t.Errorf("http2 wasn't automatically enabled")
        }
    }
    ```
    このテストは、`http.Server`の`Serve`メソッドが呼び出されたときに、`TLSNextProto`が`nil`であればHTTP/2が自動的に有効になることを検証します。
    *   `net.Listen("tcp", ":0")`: 任意の利用可能なポートでTCPリスナーを作成します。
    *   `ln.Close()`: リスナーをすぐに閉じます。これは、`s.Serve(ln)`がエラーを返すことを期待しているためです（リスナーが閉じられているため、接続を受け付けられない）。
    *   `var s Server`: デフォルト設定の`http.Server`インスタンスを作成します。この時点では`s.TLSNextProto`は`nil`です。
    *   `if err := s.Serve(ln); err == nil`: `Serve`メソッドを呼び出します。リスナーが閉じられているため、`Serve`はエラーを返すべきです。この呼び出しの副作用として、`s.nextProtoOnce.Do(s.setNextProtoDefaults)`が実行され、`s.TLSNextProto`が`nil`であればHTTP/2が設定されます。
    *   `on := s.TLSNextProto["h2"] != nil`: `Serve`呼び出し後、`s.TLSNextProto`マップに`"h2"`キーが存在するかどうかを確認します。
    *   `if !on`: もし`"h2"`キーが存在しなければ、HTTP/2が自動的に有効にならなかったと判断し、テストを失敗させます。

このテストは、コミットの意図通りにHTTP/2の自動有効化機能が動作することを保証するための重要な検証です。

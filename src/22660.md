## 元コミット内容

```
text/scanner: Fix EOF reporting on strange Readers

Currently, scanner uses -1 to represent 2 different states:

1. I haven't yet scanned anything, call it "Beginning of File"
2. I've reached the end of the input, ie EOF

The result of this behavior is that calling Peek() when next()
has detected the end of the input and set s.ch to scanner.EOF,
is that Peek() things "oh, s.ch is < 0, which to me means that
I haven't scanned any next yet, let me try and clear the BOM
marker."

When this behavior is run on a typical IO, next() will issue
a Read and get (0, io.EOF) back for the second time without
blocking and Peek() will return scanner.EOF.

The bug comes into play when, inside a terminal, hitting Control-D.
This causes the terminal to return a EOF condition to the reader
but it does not actually close the fd.

So, combining these 2 situations, we arrive at the bug:

What is expected: hitting Control-D in a terminal will make Peek()
return scanner.EOF instantly.

What actually happens:

0. Code waiting in Next()
1. User hits Control-D
2. fd returns EOF condition
3. EOF bubbles it's way out to line 249 in scanner.go
4. next() returns scanner.EOF
5. Next() saves the scanner.EOF to s.ch and returns the previous value
6. Peek() runs, sees s.ch < 0, mistakenly thinks it hasn't run yet and
   tries to read the BOM marker.
7. next() sees the buffer is empty and tries to fill it again, blocking
   on line 249.

The fix is simple: use a different code to indicate that no data
has been scanned.

Change-Id: Iee8f4da5881682c4d4c36b93b9bf397ac5798179
Reviewed-on: https://go-review.googlesource.com/7913
Reviewed-by: Robert Griesemer <gri@golang.org>
```

## 変更の背景

このコミットは、Go言語の標準ライブラリである`text/scanner`パッケージにおける、EOF (End-of-File) の報告に関するバグを修正するものです。特に、ターミナルからの入力（例えばControl-DによるEOFシグナル）を扱う際に問題が発生していました。

従来の`text/scanner`の実装では、内部状態変数`s.ch`が`-1`という単一の値を用いて、以下の2つの異なる状態を表現していました。
1.  まだ何もスキャンしていない、つまり「ファイルの先頭」の状態。
2.  入力の終わりに達した、つまり「EOF」の状態。

この二重の意味合いが問題を引き起こしていました。具体的には、`next()`メソッドが入力の終わりに達して`s.ch`に`scanner.EOF`（値は`-1`）を設定した後、`Peek()`メソッドが呼び出されると、`Peek()`は`s.ch < 0`という条件を見て、誤って「まだ何もスキャンしていない」状態だと判断していました。この誤解により、`Peek()`はBOM (Byte Order Mark) マーカーをクリアしようと試み、結果として`next()`を再度呼び出してバッファを埋めようとします。

通常のファイルI/Oでは、`next()`が`Read`を発行し、2回目の`(0, io.EOF)`を受け取ると、`Peek()`は正しく`scanner.EOF`を返します。しかし、ターミナルでControl-Dが押された場合、ターミナルはEOF条件をリーダーに返しますが、実際のファイルディスクリプタ（fd）は閉じられません。この状況が、`text/scanner`が無限にブロックする原因となっていました。

ユーザーがControl-Dを押すと、期待される動作は`Peek()`が即座に`scanner.EOF`を返すことでした。しかし実際には、`Peek()`が`s.ch < 0`を見て「まだ実行されていない」と誤解し、BOMマーカーを読み込もうとして、結果的に`next()`が再度バッファを埋めようとしてブロックしてしまうというバグが発生していました。この問題はGo Issue #10735として報告され、Go 1.5マイルストーンで修正が予定されていました。

## 前提知識の解説

*   **`text/scanner`パッケージ**: Go言語の標準ライブラリの一部で、テキストをトークンに分割するためのスキャナーを提供します。プログラミング言語のパーサーや、設定ファイルの読み込みなど、様々なテキスト処理で利用されます。
*   **EOF (End-of-File)**: ファイルや入力ストリームの終端を示すマーカーです。Go言語では、`io.Reader`インターフェースの`Read`メソッドが`0`バイトを読み込み、かつ`io.EOF`エラーを返すことで、ストリームの終端を通知します。`text/scanner`パッケージでは、`scanner.EOF`という定数（値は`-1`）がEOFを表します。
*   **`Peek()`メソッド**: `text/scanner`のメソッドで、次の文字を読み進めることなく、その文字を「覗き見」します。これは、現在の位置を維持したまま、次に何が来るかを確認するために使用されます。
*   **`Next()`メソッド**: `text/scanner`のメソッドで、次の文字を読み進め、その文字を返します。
*   **`s.ch`**: `scanner`構造体の内部フィールドで、次に処理される文字を保持します。
*   **BOM (Byte Order Mark)**: Unicodeテキストファイルの先頭に付加される特殊なマーカーで、バイトオーダー（エンディアン）を示すために使用されます。`text/scanner`は、ファイルの先頭でBOMを検出した場合、それをスキップするロジックを持っています。
*   **Control-D**: Unix系システムにおいて、ターミナルでEOFシグナルを生成するためのキーシーケンスです。これにより、標準入力からの読み込みが終了したことをプログラムに通知します。

## 技術的詳細

このバグの根本原因は、`s.ch`という単一の整数値が、異なる2つの意味（「まだスキャンしていない」と「EOFに到達した」）を持つために発生していました。`scanner.EOF`は`-1`として定義されており、初期状態の`s.ch`も`-1`でした。

バグのシナリオは以下の通りです。
1.  `Next()`が呼び出され、入力がEOFに達する。
2.  `next()`（内部関数）が`scanner.EOF`を返し、`s.ch`に`scanner.EOF`（つまり`-1`）が設定される。
3.  `Next()`は以前の文字を返し、`s.ch`は`-1`のままになる。
4.  次に`Peek()`が呼び出される。
5.  `Peek()`内の条件式`s.ch < 0`が真となる。この条件は、本来「まだ何もスキャンしていない」状態をチェックするためのものでした。
6.  しかし、`s.ch`が`-1`であるため、`Peek()`は誤って「まだ何もスキャンしていない」と判断し、BOMマーカーをクリアするロジック（`s.ch = s.next(); if s.ch == '\uFEFF' { ... }`）を実行しようとする。
7.  このBOMクリアロジックの中で、再度`s.next()`が呼び出される。
8.  `s.next()`はバッファが空であるため、`io.Reader`からデータを読み込もうとする。
9.  ターミナルからのControl-Dの場合、`io.Reader`はEOF条件を返すが、fdは閉じられていないため、`Read`呼び出しがブロックされ、プログラムがハングアップする。

修正は非常にシンプルで、この二重の意味合いを解消することです。具体的には、「まだ何もスキャンしていない」状態を示すために、`scanner.EOF`（`-1`）とは異なる新しい値を使用します。コミットでは、この新しい値として`-2`が導入されました。

これにより、`s.ch`の初期値が`-2`となり、`Peek()`メソッド内の条件式が`s.ch == -2`に変更されました。
*   `s.ch = -2`：まだ何もスキャンしていない状態。
*   `s.ch = -1` (`scanner.EOF`)：入力の終わりに達した状態。

この変更により、`Peek()`が`s.ch`が`-1`（EOF）であるときに、誤って初期状態と判断してBOM処理を行おうとすることがなくなり、正しくEOFを報告できるようになりました。

## コアとなるコードの解説

*   **`src/text/scanner/scanner.go`の変更**:
    *   `s.ch`の初期化: `Init`メソッド内で、`s.ch`の初期値が`-1`から`-2`に変更されました。これにより、「まだ何もスキャンしていない」状態が`scanner.EOF`（`-1`）とは明確に区別されるようになりました。コメントも「no char read yet, not EOF」と更新され、意図が明確になっています。
    *   `Peek()`メソッドの条件式: `Peek()`メソッド内の条件式が`s.ch < 0`から`s.ch == -2`に変更されました。これにより、`Peek()`は`s.ch`が`-2`である場合にのみ、初期状態の処理（BOMマーカーのチェックなど）を実行するようになります。`s.ch`が`-1`（EOF）である場合は、このブロックに入らず、正しくEOFを返す動作が期待されます。

*   **`src/text/scanner/scanner_test.go`の追加**:
    *   `countReader`型: `io.Reader`インターフェースを実装するカスタムリーダー`countReader`が追加されました。このリーダーは、`Read`メソッドが呼び出されるたびに内部カウンタをインクリメントし、常に`0`バイトと`io.EOF`を返します。これは、Control-Dが押されたターミナルからの入力のような「奇妙なReader」の動作をシミュレートするために使用されます。
    *   `TestPeekEOFHandling`テスト関数: この新しいテストは、`countReader`を使用して`text/scanner`のEOF処理を検証します。
        *   空のソースに対してスキャナーを初期化します。
        *   `s.Next()`を呼び出し、EOFが報告されることを確認します。
        *   `s.Peek()`を呼び出し、ここでもEOFが報告されることを確認します。
        *   最後に、`countReader`の`Read`メソッドが正確に2回呼び出されたことを検証します。これは、`Next()`が1回、そして`Peek()`が誤ってBOM処理のために`next()`を呼び出し、それがさらに`Read`をトリガーする、というバグの動作を再現し、修正後はこの余分な`Read`がなくなることを確認するためのものです。このテストが成功するということは、`Peek()`がEOF時に余分な読み込みを試みなくなったことを意味します。

これらの変更により、`text/scanner`はEOFと初期状態を正しく区別し、特にターミナルからのEOFシグナルに対して、ハングアップすることなく期待通りの動作をするようになりました。

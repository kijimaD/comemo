# [インデックス 2520] ファイルの概要

このコミットは、Go言語の仕様書（`doc/go_spec.html`）におけるインデックス操作（`[]`演算子）の規則を明確化するものです。特に、スライス型、文字列型、およびマップ型へのポインタに対するインデックス操作の可否について、その振る舞いを厳密に定義しています。これにより、Go言語の型システムにおける一貫性と予測可能性が向上しました。

## 変更の背景

このコミットは、Go言語がまだ開発の初期段階にあった2009年に行われました。当時のGo言語は、その仕様が活発に議論され、進化している最中でした。インデックス操作（`[]`）は、配列、スライス、文字列、マップといったデータ構造にアクセスするための基本的な機能ですが、これらの型、特にそれらへのポインタ型に対してインデックス操作がどのように振る舞うべきかについて、初期の仕様には曖昧さや未定義の部分が存在した可能性があります。

このコミットの目的は、Go言語の公式仕様書である`doc/go_spec.html`を更新し、以下の点について明確なルールを確立することでした。

1.  **スライス型**: スライス型自体はインデックス可能か、スライスへのポインタはどうか。
2.  **文字列型**: 文字列型自体はインデックス可能か、文字列へのポインタはどうか。また、文字列のインデックスアクセスで取得した要素は変更可能か。
3.  **マップ型**: マップ型自体はインデックス可能か、マップへのポインタはどうか。

これらのルールを明確にすることで、Go言語の型システムにおける一貫性を保ち、開発者がより予測可能で安全なコードを書けるようにすることが意図されています。Go言語の設計哲学である「シンプルさ」と「明瞭さ」に沿って、曖昧さを排除し、言語の振る舞いを厳密に定義する一環として行われた変更です。

## 前提知識の解説

このコミットの理解を深めるためには、以下のGo言語の基本的な概念を把握しておく必要があります。

### Go言語の型システム

*   **配列 (Array)**: 固定長で、同じ型の要素を連続して格納するデータ構造です。`[N]T`のように宣言され、`a[i]`で要素にアクセスします。
*   **スライス (Slice)**: 可変長で、配列の一部を参照するデータ構造です。内部的には、参照先の配列へのポインタ、長さ（`len`）、容量（`cap`）の3つの要素で構成されます。`[]T`のように宣言され、`s[i]`で要素にアクセスします。スライスは参照型のように振る舞いますが、それ自体は構造体であり、ポインタではありません。
*   **文字列 (String)**: Goの文字列は、読み取り専用のバイトスライスとして実装されています。UTF-8エンコードされたテキストを扱うことが一般的ですが、バイト列としてインデックスアクセスすることも可能です。文字列はイミュータブル（不変）です。
*   **マップ (Map)**: キーと値のペアを格納するハッシュテーブルです。キーは一意であり、値にアクセスするために使用されます。`map[K]V`のように宣言され、`m[key]`で値にアクセスします。マップも内部的にポインタを持つ参照型です。
*   **ポインタ (Pointer)**: 変数のメモリアドレスを保持する型です。`*T`のように宣言され、`&v`で変数のアドレスを取得し、`*p`でポインタが指す値にアクセス（デリファレンス）します。Goでは、C/C++のようなポインタ演算は制限されており、より安全に扱われます。

### インデックス操作 (`[]`演算子)

Go言語において、`[]`演算子は配列、スライス、文字列、マップの要素にアクセスするために使用されます。

*   **配列、スライス、文字列**: `a[i]` の形式で、`i`番目の要素にアクセスします。`i`は整数で、`0 <= i < len(a)`の範囲内である必要があります。
*   **マップ**: `m[key]` の形式で、`key`に対応する値にアクセスします。

### Go言語仕様 (Go Spec)

Go言語仕様は、Go言語の構文、セマンティクス、および標準ライブラリの動作を正式に定義するドキュメントです。Go言語のあらゆる振る舞いはこの仕様によって規定されており、コンパイラやランタイムの実装はこの仕様に準拠する必要があります。このコミットは、まさにこのGo言語仕様書を更新するものであり、言語の公式なルールを変更・明確化する重要な意味を持ちます。

## 技術的詳細

このコミットは、Go言語仕様の「Index expressions」および「Slice expressions」のセクションにおける、インデックス操作の対象となる型に関するルールを明確にしました。

### スライス型に対するインデックス操作の明確化

変更前は、配列型（`A`または`*A`）に対するインデックス操作の記述しかありませんでしたが、このコミットにより、スライス型（`S`）もインデックス操作の直接の対象となることが明記されました。

*   **スライス型自体 (`S`)**: インデックス操作 `s[x]` が許可されます。`x` は整数値で `0 <= x < len(s)` の範囲内である必要があります。`s[x]` の型はスライスの要素型になります。
*   **スライスへのポインタ型 (`*S`)**: **インデックス操作は許可されません。** スライスはそれ自体がポインタ、長さ、容量を持つ構造体であり、参照型のように振る舞います。そのため、スライスへのポインタを直接インデックスしようとすると、そのポインタが指す「スライス構造体」をインデックスしようとすることになり、これはGoの型システムでは意味をなさない操作と判断されます。スライスへのポインタをインデックスしたい場合は、まずポインタをデリファレンスしてスライス自体を取得する必要があります（例: `(*ptrToSlice)[x]`）。しかし、Goでは通常、スライスは値渡しされるため、このような操作は稀です。

### 文字列型に対するインデックス操作の追加

このコミットにより、文字列型に対するインデックス操作のルールが新たに明確に定義されました。

*   **文字列型 (`T`)**: インデックス操作 `s[x]` が許可されます。`x` は整数値で `0 <= x < len(s)` の範囲内である必要があります。
*   **`s[x]` の型**: `byte` 型になります。Goの文字列はバイトのシーケンスとして扱われるため、インデックスアクセスは個々のバイトを返します。
*   **`s[x]` への代入**: **許可されません。** Goの文字列はイミュータブル（不変）であるため、インデックスを使って文字列の個々のバイトを変更することはできません。文字列を変更するには、新しい文字列を作成する必要があります。
*   **文字列へのポインタ型 (`*T`)**: **インデックス操作は許可されません。** スライスの場合と同様に、文字列へのポインタを直接インデックスすることはできません。

### マップ型へのポインタに対するインデックス操作の制限

変更前は、マップ型（`M`または`*M`）に対するインデックス操作が許可されているかのような記述がありましたが、このコミットにより、マップ型自体（`M`）のみがインデックス操作の対象であり、マップへのポインタ型（`*M`）は対象外であることが明確にされました。

*   **マップ型自体 (`M`)**: インデックス操作 `m[key]` が許可されます。
*   **マップへのポインタ型 (`*M`)**: **インデックス操作は許可されません。** マップも内部的にポインタを持つ参照型ですが、スライスと同様に、マップへのポインタを直接インデックスすることはGoの型システムでは許可されません。マップへのポインタをインデックスしたい場合は、まずポインタをデリファレンスしてマップ自体を取得する必要があります（例: `(*ptrToMap)[key]`）。

これらの変更は、Go言語の設計原則である「明示性」と「安全性」を反映しています。ポインタを介したインデックス操作を制限することで、開発者がポインタのデリファレンスを意識し、意図しない動作や混乱を避けることができます。また、文字列の不変性を仕様レベルで明確にすることで、文字列操作の予測可能性を高めています。

## コアとなるコードの解説

変更された`doc/go_spec.html`の各部分は、Go言語のインデックス操作に関する重要なルールを定義しています。

1.  **スライス型のインデックス操作の追加**:
    ```diff
    -where <code>A</code> is an array type (§Array types):
    +where <code>A</code> is an array type (§Array types),
    +or for <code>a</code> of type <code>S</code> where <code>S</code> is a slice type (§Slice types):
    ```
    この変更により、配列型（`A`）だけでなく、スライス型（`S`）もインデックス操作の直接の対象となることが明記されました。これは、スライスがGo言語の基本的なデータ構造であり、配列と同様にインデックスによる要素アクセスが期待されるため、仕様として明確にする必要がありました。同時に、元の記述が`A`または`*A`（配列または配列へのポインタ）を対象としていたのに対し、スライス型については`S`（スライス型自体）のみが対象とされ、スライスへのポインタ（`*S`）はインデックス操作の対象外であることが暗に示されています。

2.  **文字列型のインデックス操作の新規追加**:
    ```html
    <p>
    For <code>a</code> of type <code>T</code>
    where <code>T</code> is a string type (§Strings):
    </p>
    <ul>
    	<li><code>x</code> must be an integer value and <code>0 &lt;= x &lt; len(a)</code>
    	<li><code>a[x]</code> is the byte at index <code>x</code> and the type of
    	  <code>a[x]</code> is <code>byte</code>
    	<li><code>a[x]</code> may not be assigned to
    </ul>
    ```
    この新しいセクションは、文字列型に対するインデックス操作の振る舞いを詳細に定義しています。
    *   `x`が整数値であり、`0 <= x < len(a)`の範囲内であること。これは配列やスライスと同様の範囲チェックです。
    *   `a[x]`がインデックス`x`におけるバイトであり、その型が`byte`であること。Goの文字列がバイトのシーケンスとして扱われることを明確にしています。
    *   `a[x]`に代入できないこと。これはGoの文字列が不変（immutable）であるという重要な特性を仕様レベルで保証するものです。これにより、文字列の要素を直接変更しようとする試みがコンパイル時にエラーとなるか、実行時にパニックを引き起こすことが保証され、コードの安全性が高まります。

3.  **マップ型へのポインタのインデックス操作の制限**:
    ```diff
    -For <code>a</code> of type <code>M</code> or <code>*M</code>
    +For <code>a</code> of type <code>M</code>
    where <code>M</code> is a map type (§Map types):
    ```
    この変更は、マップ型に対するインデックス操作の対象を`M`（マップ型自体）に限定し、`*M`（マップへのポインタ型）を対象から除外しています。これは、スライスの場合と同様に、マップへのポインタを直接インデックスしようとすると、そのポインタが指す「マップ構造体」をインデックスしようとすることになり、Goの型システムでは意味をなさないためです。マップへのポインタを介してマップの要素にアクセスしたい場合は、まずポインタをデリファレンスしてマップ自体を取得する必要があります（例: `(*ptrToMap)[key]`）。この制限により、ポインタのデリファレンスを明示的に行う必要があり、コードの意図がより明確になります。

これらの変更は、Go言語の初期段階において、言語のセマンティクスを厳密に定義し、開発者が直感的かつ安全にコードを書けるようにするための重要なステップでした。特に、ポインタ型に対するインデックス操作の制限は、GoがC/C++のような低レベルなポインタ操作を許容しつつも、より高い安全性と型安全性を追求していることの表れと言えます。

## 変更の背景

Goのデータ競合検出器（Race Detector）は、並行処理におけるデータ競合という深刻なバグを特定するための強力なツールです。しかし、この検出器は内部的にCgo（GoとC言語の相互運用機能）に依存しています。以前のバージョンでは、ユーザーが `go build -race` コマンドを実行した際に、Cgoが無効になっている環境（例えば `CGO_ENABLED=0` が設定されている場合）では、データ競合検出器が正しく動作せず、ユーザーにとって理解しにくいエラーや予期せぬ挙動が発生していました。

このコミットは、Issue #12844 で報告された問題を解決するために導入されました。この問題は、Cgoが有効でない状態で `-race` フラグを使用すると、ユーザーが何が問題なのかを理解するのに苦労するというものでした。具体的なエラーメッセージが提供されなかったため、ユーザーはデバッグに時間を費やす必要がありました。この変更により、Cgoが必須であることを明示的に伝えるエラーメッセージが表示されるようになり、ユーザーエクスペリエンスが大幅に向上しました。

## 前提知識の解説

### Go Race Detector (データ競合検出器)

Go Race Detectorは、Goプログラムにおけるデータ競合（data race）を検出するためのツールです。データ競合は、複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって順序付けされていない場合に発生します。データ競合は、プログラムの予測不能な動作、クラッシュ、または誤った結果を引き起こす可能性があり、デバッグが非常に困難な種類のバグです。

Race Detectorは、プログラムの実行時にメモリアクセスを監視し、データ競合のパターンを特定します。これを使用するには、`go build`、`go run`、`go test` などのコマンドに `-race` フラグを追加します。

例: `go run -race main.go`

Race Detectorは、実行時のオーバーヘッドを伴いますが、並行処理のバグを早期に発見するために非常に価値のあるツールです。

### Cgo

Cgoは、GoプログラムがC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのメカニズムです。Goはシステムプログラミング言語ですが、既存のCライブラリやOS固有の低レベル機能を利用する必要がある場合があります。Cgoはこのようなシナリオで利用されます。

Cgoが有効になっているかどうかは、`CGO_ENABLED` 環境変数によって制御されます。
*   `CGO_ENABLED=1` (デフォルト): Cgoが有効になり、GoプログラムはCコードとリンクできます。
*   `CGO_ENABLED=0`: Cgoが無効になり、Goプログラムは純粋なGoコードのみでビルドされます。この場合、Cgoに依存する機能は使用できません。

Race Detectorは、その実装においてOSの低レベルなメモリ監視機能やスレッド同期プリミティブにアクセスするためにCgoを内部的に利用しています。そのため、Cgoが無効な環境ではRace Detectorも動作できません。

## 技術的詳細

このコミットの技術的な核心は、`go build` コマンドの内部ロジックに、`-race` フラグが指定された際に `buildContext.CgoEnabled` の状態をチェックする条件分岐を追加した点にあります。

Go Race Detectorは、実行時にメモリアクセスをフックし、競合を検出するために、オペレーティングシステムが提供する低レベルな機能（例えば、スレッドローカルストレージ、メモリ保護、シグナルハンドリングなど）を利用します。これらの機能へのアクセスは、多くの場合、C言語で書かれたライブラリやシステムコールを介して行われます。Go言語自体は、これらのC言語の機能に直接アクセスするための「外国関数インターフェース (FFI)」としてCgoを提供しています。

したがって、Race Detectorが正しく機能するためには、Cgoが有効になっている必要があります。もし `CGO_ENABLED=0` が設定されている場合、GoコンパイラはCgoコードをビルドプロセスから除外するため、Race Detectorの必要なコンポーネントがリンクされず、結果として検出器が動作不能になります。

以前は、このような状況で `-race` フラグを使用すると、ユーザーは漠然としたビルドエラーやランタイムエラーに直面し、その根本原因がCgoの無効化にあることを理解するのが困難でした。このコミットは、この問題を解決するために、`build.go` 内で明示的なチェックを追加し、Cgoが無効な場合に具体的なエラーメッセージをユーザーに提示するようにしました。これにより、ユーザーは「-raceにはcgoが必要です。CGO_ENABLED=1を設定してcgoを有効にしてください」という明確な指示を受け取ることができ、デバッグの労力を大幅に削減できます。

## コアとなるコードの解説

追加されたコードは `raceInit()` 関数内にあります。この関数は、`go build -race` コマンドが実行された際に、Race Detectorを初期化するために呼び出されます。

```go
	if !buildContext.CgoEnabled {
		fmt.Fprintf(os.Stderr, "go %s: -race requires cgo; enable cgo by setting CGO_ENABLED=1\\n", flag.Args()[0])
		os.Exit(2)
	}
```

1.  `if !buildContext.CgoEnabled { ... }`:
    *   `buildContext` は、現在のビルドに関する情報（ターゲットOS、アーキテクチャ、Cgoの有効/無効など）を保持する構造体です。
    *   `CgoEnabled` フィールドは、Cgoが現在のビルドコンテキストで有効になっているかどうかを示すブール値です。
    *   この `if` 文は、`CgoEnabled` が `false` (つまり、Cgoが無効) である場合に、ブロック内のコードを実行します。

2.  `fmt.Fprintf(os.Stderr, "go %s: -race requires cgo; enable cgo by setting CGO_ENABLED=1\\n", flag.Args()[0])`:
    *   `fmt.Fprintf` は、フォーマットされた文字列を標準エラー出力 (`os.Stderr`) に書き込む関数です。
    *   エラーメッセージは「`go [コマンド名]: -race requires cgo; enable cgo by setting CGO_ENABLED=1`」という形式で出力されます。
    *   `flag.Args()[0]` は、実行された `go` コマンドのサブコマンド（例: `build`, `run`, `test`）を挿入するために使用されます。これにより、エラーメッセージがより具体的になります。

3.  `os.Exit(2)`:
    *   プログラムを終了し、終了コード `2` を返します。終了コード `2` は、一般的にコマンドラインツールにおいて「不正な使用法」や「設定エラー」を示すために使用されます。これにより、スクリプトなどからこのエラーを検知しやすくなります。

この変更により、Race DetectorがCgoに依存しているという前提がコードに明示的に組み込まれ、ユーザーが誤った環境設定で `-race` フラグを使用した場合に、即座に適切なフィードバックが提供されるようになりました。

# [インデックス 2088] ファイルの概要

このコミットは、Go言語の初期開発段階における、抽象構文木（AST）の整形（pretty printing）メカニズムに関する重要な更新を含んでいます。具体的には、`usr/gri/pretty/ast.txt` と `usr/gri/pretty/format.go` の2つのファイルが変更されています。

`usr/gri/pretty/ast.txt` は、ASTノードの整形ルールやテンプレートを定義するための設定ファイル、あるいはDSL（Domain Specific Language）の定義ファイルとして機能していると考えられます。このファイルは、GoのAST構造をどのようにテキスト表現に変換するかを記述するための「テンプレート」のような役割を担っています。

`usr/gri/pretty/format.go` は、この「テンプレート」を解釈し、実際のASTを整形して出力するロジックを実装しています。ASTの走査、各ノードに対する整形ルールの適用、そして最終的なテキスト出力を行うGoコードが含まれています。このコミットでは、特にテンプレート駆動の整形処理をより柔軟かつ堅牢にするための大幅なリファクタリングが行われています。

## 変更の背景

このコミットは、Go言語がオープンソース化されたばかりの2009年という非常に初期の段階で行われたものです。当時のGo言語は、コンパイラ、ツールチェイン、標準ライブラリの基盤を構築している最中でした。

この「テンプレート駆動のAST整形」に関する作業は、Goのソースコードを読みやすく、標準的な形式で出力するための重要な機能、例えば`gofmt`のようなツールの基盤を確立することを目的としていました。ASTを直接操作して整形するのではなく、テンプレートやルールに基づいて整形を行うことで、より柔軟で拡張性の高い整形メカニズムを実現しようとしていたと考えられます。これにより、将来的にGo言語の構文が進化したり、異なる整形スタイルが求められたりした場合でも、コードの変更を最小限に抑えつつ対応できるような設計を目指していたと推測されます。

## 前提知識の解説

### AST (Abstract Syntax Tree)

AST（抽象構文木）は、プログラミング言語のソースコードの抽象的な構文構造を木構造で表現したものです。コンパイラやインタプリタがソースコードを解析する際に生成され、プログラムの意味を理解し、最適化やコード生成を行うための中心的なデータ構造となります。各ノードは、変数宣言、関数呼び出し、演算子などの言語要素に対応します。

### Pretty Printing (整形出力)

Pretty printingとは、プログラムのソースコードやデータ構造を、人間が読みやすいように整形して出力するプロセスを指します。これには、適切なインデント、改行、空白の挿入などが含まれます。プログラミングにおいては、コードの可読性を高め、チーム内でのコーディングスタイルを統一するために非常に重要です。Go言語においては、`gofmt`というツールが標準的な整形ツールとして広く利用されています。

### Template-driven approach (テンプレート駆動アプローチ)

テンプレート駆動アプローチとは、固定されたロジックで出力を生成するのではなく、事前に定義されたテンプレート（ひな形）とデータを用いて出力を生成する手法です。このアプローチでは、出力の構造や形式をテンプレートで定義し、実行時に具体的なデータをテンプレートに埋め込むことで、多様な出力を柔軟に生成できます。コード生成、ドキュメント生成、Webページのレンダリングなど、様々な分野で利用されます。ASTの整形においては、ASTの各ノードに対応する出力形式をテンプレートとして定義し、ASTを走査しながら適切なテンプレートを適用することで、整形されたコードを生成します。

### Go言語の初期開発 (2009年)

2009年はGo言語が一般に公開された年であり、そのエコシステムや標準ライブラリの多くがまだ活発に開発されている段階でした。この時期のコミットは、言語の基本的な設計思想や、将来の成長を見据えた基盤技術の確立に焦点を当てています。特に、コンパイラ、ランタイム、そして開発ツール（`gofmt`など）の内部構造に関する変更が多く見られます。`reflect`パッケージのような、実行時の型情報にアクセスする機能もこの時期に開発が進められていました。

## 技術的詳細

このコミットの技術的詳細を掘り下げると、Go言語のAST整形メカニズムが、より柔軟で表現力の高い「プロダクション式（production expression）」の概念に基づいて再構築されていることがわかります。

以前の`node`構造体による整形ルール表現から、`expr`インターフェースとその実装型（`empty`, `alternative`, `sequence`, `field`, `literal`, `option`, `repetition`, `custom`）への移行は、整形ルールの表現力を大幅に向上させています。これは、文脈自由文法（Context-Free Grammar）やEBNF（Extended Backus-Naur Form）のような形式文法をGoの型システムで表現し、それに基づいてASTの整形ロジックを構築しようとしていることを示唆しています。

*   **`expr` インターフェース**: 整形可能なすべての要素がこのインターフェースを実装することで、統一的な処理が可能になります。
*   **`alternative` (`|`)**: 複数の整形ルールのうち、いずれか一つを適用する選択肢を表現します。例えば、あるASTノードが複数の異なる形式で出力されうる場合に利用されます。
*   **`sequence` (連結)**: 複数の整形ルールを順番に適用することを表現します。例えば、`package` キーワードの後にパッケージ名、そして改行が続くといったシーケンスです。
*   **`field`**: ASTノードの特定フィールドの値を整形して出力することを表現します。`^`（ポインタ参照）、`*`（値そのもの）、またはフィールド名によって指定されます。これにより、ASTの構造を深く掘り下げて整形対象のデータを取得できます。また、`format expr`フィールドを持つことで、フィールドごとに異なる整形ルールを適用できる柔軟性を持っています。
*   **`literal`**: 固定の文字列（リテラル）を出力することを表現します。例えば、`package` や `{` といったキーワードや記号です。
*   **`option` (`[]`)**: オプションの整形ルールを表現します。例えば、関数宣言におけるレシーバのように、存在する場合としない場合がある要素の整形に利用されます。
*   **`repetition` (`{}`)**: 繰り返し可能な整形ルールを表現します。例えば、関数宣言の引数リストや、構造体のフィールドリストのように、複数の要素が繰り返される場合の整形に利用されます。
*   **`custom`**: 特定の型に対して、Goコードで定義されたカスタム整形関数を適用することを可能にします。これにより、標準の整形ルールでは対応できない複雑な整形ロジックを組み込むことができます。

`format.go`内の`parser`構造体と関連する`parse*`関数群は、`ast.txt`のような外部ファイル、あるいは内部的な文字列から、これらの「プロダクション式」を解析し、`Format`マップ（`map[string]expr`）に格納する役割を担っています。これにより、整形ルール自体をプログラムコードから分離し、外部設定として管理できる設計になっています。

また、`reflect`パッケージが多用されている点も注目に値します。これは、GoのASTノードが多様な構造体で表現されるため、実行時にリフレクションを用いてASTノードの型やフィールド情報を動的に取得し、適切な整形ルールを適用するために必要不可欠な機能です。`typename`関数は、`reflect.Value`から型名を取得し、それに基づいて適切な整形ルール（`Format`マップから`expr`）を選択するロジックを担っています。

`printf`関数と`percentCount`関数は、リテラル文字列内に`%v`のようなGoの`fmt`パッケージ形式のフォーマット指定子が含まれている場合に、それを適切に処理するためのものです。これにより、整形出力に動的な値を埋め込むことが可能になります。

全体として、このコミットは、GoのAST整形を、静的なコード生成ではなく、より宣言的で柔軟な「テンプレート駆動」のシステムへと進化させるための基盤を築いています。これは、後の`go/printer`パッケージや`gofmt`ツールの設計思想にも影響を与えた重要なステップであると言えるでしょう。

## コアとなるコードの変更箇所

### `usr/gri/pretty/ast.txt`

*   以前のシンプルなASTノード定義（`ast.Ident = Value .` など）が削除され、より詳細な整形ルールが追加されています。
*   `string = "%s" ;` や `pointer = ^ ;`、`array = ^ ;` といった、基本的な型や概念に対する整形ルールが追加されています。
*   `ast`, `Comments`, `Ident`, `Program`, `GenDecl`, `FuncType`, `BlockStmt`, `FuncDecl`, `Decl` といったGoのASTノードに対応する、より具体的な整形定義が追加されています。これらの定義は、EBNFのような形式で、各ASTノードがどのように整形されるべきかを記述しています。例えば、`FuncDecl = "func " Name Type [ " " Body ] ;` は、関数宣言が `func` キーワード、名前、型、そしてオプションでボディが続くことを示しています。

### `usr/gri/pretty/format.go`

*   **`node` 構造体の削除と `expr` インターフェースの導入**:
    *   以前の`node`構造体（`kind`, `name`, `value`, `x`, `y` を持つ）が削除されました。
    *   代わりに、`expr`というインターフェースが導入され、`empty`, `alternative`, `sequence`, `field`, `literal`, `option`, `repetition`, `custom` という匿名構造体型が`expr`インターフェースを実装するように定義されました。これにより、整形ルールの表現がより型安全で拡張可能になりました。
*   **`Format` 型の変更**:
    *   `type Format map[string]*node;` から `type Format map[string]expr;` へと変更され、整形ルールが`expr`インターフェースを介して管理されるようになりました。
*   **`parse*` 関数のリファクタリング**:
    *   `parseName` が `parseIdentifier` にリネームされ、`parseDottedName` が `parseName` に変更されました。これにより、識別子とドット区切りの名前の解析ロジックが明確化されました。
    *   `parseFactor`, `parseTerm`, `parseExpression` (新しく `parseExpr` にリネーム) のロジックが、新しい `expr` インターフェースとそれに対応する構造体型を生成するように変更されました。特に `parseField` 関数が新設され、`^` (ポインタ)、`*` (値)、識別子によるフィールド参照と、それに続くオプションのフォーマット指定 (`: Expression`) を解析できるようになりました。
    *   `parseProduction` 関数が、プロダクションの終端記号を `.` から `;` に変更し、`Expression` がオプションになったり、`empty` 式を生成するロジックが追加されたりしています。
*   **`print` メソッドのロジック変更**:
    *   `Format` 型の`print`メソッドが、新しい`expr`インターフェースを引数にとり、各`expr`の実装型に応じた整形ロジックを実行するように大幅に書き換えられました。これにより、再帰的に整形ルールを適用し、ASTを走査しながら出力するメカニズムが実現されています。
    *   `field` 型の処理では、`reflect.PtrValue`, `reflect.ArrayValue`, `reflect.InterfaceValue`, `reflect.StructValue` を用いて、ポインタのデリファレンス、配列要素のアクセス、インターフェースの値の取得、構造体フィールドの取得を動的に行っています。
*   **`typename` 関数の追加**:
    *   `reflect.Value`から型名を取得するためのヘルパー関数`typename`が追加されました。これは、`Format`マップから適切な整形ルールを選択するために使用されます。
*   **`percentCount` および `printf` 関数の追加**:
    *   リテラル文字列内の`%`フォーマット指定子の数をカウントする`percentCount`関数と、それを用いて`fmt.Fprintf`で動的な値を整形出力する`printf`関数が追加されました。

## コアとなるコードの解説

このコミットの核心は、GoのAST整形を、静的な処理から、より動的で宣言的な「プロダクション式」に基づくシステムへと移行させた点にあります。

`format.go`における`expr`インターフェースと、それを実装する`empty`, `alternative`, `sequence`, `field`, `literal`, `option`, `repetition`, `custom`といった構造体は、ASTの整形ルールを表現するための小さなビルディングブロックです。これらは、EBNFのような形式文法の要素をGoの型システムで表現したものと考えることができます。

*   `empty` は空の出力を意味し、オプションの要素が存在しない場合などに使われます。
*   `alternative` は `|` (OR) 演算子に対応し、複数の整形候補から一つを選択します。
*   `sequence` は要素の連結を意味し、複数の整形ルールを順番に適用します。
*   `field` はASTノードの特定のフィールドにアクセスし、その値を整形します。`^`はポインタのデリファレンス、`*`は値そのもの、そして名前は構造体のフィールドを指します。これにより、ASTの階層構造を深く辿って必要な情報を抽出できます。また、`format expr`を持つことで、フィールド自体の整形ルールをネストして指定できるため、非常に強力です。
*   `literal` は固定文字列の出力です。
*   `option` は `[]` (オプション) に対応し、内包する式が整形されるかどうかを制御します。
*   `repetition` は `{}` (繰り返し) に対応し、内包する式を繰り返し整形します。
*   `custom` は、Goの関数を直接呼び出して整形を行うための拡張ポイントであり、複雑な整形ロジックや外部ライブラリとの連携を可能にします。

`format.go`の`parser`は、`ast.txt`のような外部定義ファイル（あるいは文字列）を読み込み、これらの`expr`型のインスタンスを生成して`Format`マップに格納します。`Format`マップは、ASTノードの型名（例: `ast.FuncDecl`）をキーとして、その型に対応する整形ルール（`expr`）を値として保持します。

そして、`Format`の`print`メソッドが、実際のASTノードと、そのノードに対応する`expr`（整形ルール）を受け取り、再帰的に`expr`の構造を辿りながらASTノードの情報を抽出し、`io.Write`インターフェースを通じて整形されたテキストを出力します。この`print`メソッド内の`switch t := format.(type)`による型アサーションは、Goのインターフェースと多態性を活用して、各`expr`の実装型に応じた異なる整形ロジックを適用していることを示しています。

特に、`field`の処理における`reflect`パッケージの利用は、Goの強力なリフレクション機能が、コンパイル時に型が確定しないASTノードの動的なフィールドアクセスと値の抽出にどのように活用されているかを示しています。これにより、整形ロジックがASTの具体的な構造に強く依存することなく、汎用的に記述できるようになっています。

`printf`関数は、整形ルール内で`%v`のようなGoのフォーマット指定子を使用できるようにするためのもので、これにより、整形出力にASTノードの動的な値を埋め込むことが可能になります。

この一連の変更は、GoのAST整形システムが、単なる固定フォーマットの出力ではなく、柔軟なルール定義と動的なデータアクセスを組み合わせた、強力な「テンプレートエンジン」のようなものとして設計され始めたことを明確に示しています。これは、後の`go/printer`パッケージや`gofmt`の基盤となる重要な設計判断でした。

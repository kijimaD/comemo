# [インデックス 20937] ファイルの概要

このコミットは、Go言語のアセンブラ（`cmd/5a`, `cmd/6a`, `cmd/8a`, `cmd/9a`）におけるラベルのスコープに関する変更を導入しています。具体的には、ラベルが関数スコープを持つように変更され、これにより各関数内で同じ名前のラベルを使用できるようになりました。この変更は、主にアセンブラのパーサー定義ファイル（`.y`ファイル）とヘッダーファイル（`.h`ファイル）に影響を与え、それらの変更がBisonによって生成される`y.tab.c`ファイルに反映されています。また、一部のランタイムアセンブリファイル（`src/runtime/asm_*.s`など）にも微細な変更が含まれています。

影響を受ける主なファイル群:
- `src/cmd/*/a.h`: アセンブラのヘッダーファイル。
- `src/cmd/*/a.y`: アセンブラのYacc/Bisonパーサー定義ファイル。
- `src/cmd/*/y.tab.c`: `a.y`から生成されるパーサーのC言語ソースファイル。
- `src/runtime/asm_*.s`: 各アーキテクチャ向けのアセンブリランタイムファイル。
- `src/runtime/memclr_*.s`: メモリクリア関連のアセンブリファイル。
- `src/runtime/race_amd64.s`: データ競合検出関連のアセンブリファイル。
- `src/runtime/sys_*.s`: 各OS/アーキテクチャ向けのシステムコール関連アセンブリファイル。

## 元コミット内容

Go言語のアセンブラ（`cmd/5a`, `cmd/6a`, `cmd/8a`, `cmd/9a`）において、ラベルを関数スコープにする変更。

数年前に、各関数の命令レイアウトを個別に処理する一環として、関数間のジャンプのサポートが削除された。この状況を鑑みると、ラベルを関数スコープとして扱うのが理にかなっている。これにより、例えば各関数が独自の「loop」ラベルを持つことが可能になる。

この変更はアセンブリコードをよりクリーンにし、`123(PC)`形式を使用する最後の理由を取り除く。

この変更は`dev.power64`ブランチ上で行われたが、全てのアセンブラに影響を与える。この変更はGo 1.5でリリースされる予定である（おそらく新しいアセンブラに移植された後）。

CL 167730043の一部として提案された。

## 変更の背景

この変更の背景には、Go言語のコンパイラとアセンブラの進化があります。コミットメッセージに明記されているように、この変更が行われる数年前に、Goのツールチェインは関数間の直接的なジャンプ（`JMP`命令などによる）のサポートを削除していました。これは、各関数の命令レイアウトが独立して行われるようになったためです。

関数間のジャンプが不可能になったにもかかわらず、ラベルは依然としてグローバルなスコープを持っていました。これは、異なる関数内で同じ名前のラベルを定義すると、名前の衝突が発生し、アセンブラが意図しないラベルを解決してしまう可能性があったことを意味します。

このコミットは、この不整合を解消し、ラベルのスコープを関数内に限定することで、アセンブリコードの記述をより安全で直感的なものにすることを目的としています。これにより、開発者は各関数内で自由に一般的なラベル名（例: `loop`, `start`, `end`）を使用できるようになり、コードの可読性と保守性が向上します。また、`123(PC)`のような、特定のPC相対アドレス指定形式を使用する必要性がなくなり、より自然なラベル参照が可能になります。

Go 1.5は、GoコンパイラがGo自身で書かれる（セルフホスティング）ようになるなど、Goツールチェインにとって大きな転換点となったバージョンです。このコミットがGo 1.5でのリリースを予定していることは、この変更がGoツールチェインのアーキテクチャ的なクリーンアップの一環であったことを示唆しています。

## 前提知識の解説

### アセンブラとアセンブリ言語

アセンブリ言語は、CPUが直接実行できる機械語と1対1に対応する低レベルのプログラミング言語です。アセンブラは、アセンブリ言語で書かれたソースコード（`.s`ファイルなど）を機械語に変換するプログラムです。Go言語では、パフォーマンスが重要な部分や、特定のハードウェア機能にアクセスする必要がある場合に、Goのアセンブリ言語（Plan 9アセンブリ構文に基づく）が使用されます。

### ラベル (Labels)

アセンブリ言語におけるラベルは、コード内の特定の命令やデータのアドレスに名前を付けるためのシンボルです。これにより、プログラマは絶対アドレスを直接指定する代わりに、意味のある名前を使ってジャンプ命令（`JMP`, `CALL`など）のターゲットやデータの参照を行うことができます。例えば、`loop:`というラベルは、ループの開始点を示すために使われます。

### スコープ (Scope)

プログラミングにおけるスコープとは、変数や関数、ラベルなどの識別子が参照可能な範囲を指します。
- **グローバルスコープ**: プログラム全体から参照可能な識別子。
- **関数スコープ**: 特定の関数内でのみ参照可能な識別子。関数外からは参照できません。
- **ブロックスコープ**: `if`文や`for`文などのブロック内でのみ参照可能な識別子。

このコミットでは、アセンブリ言語のラベルのスコープがグローバルから関数スコープへと変更されています。

### Plan 9アセンブリ構文と`123(PC)`形式

Go言語のアセンブリは、Bell LabsのPlan 9オペレーティングシステムで使用されていたアセンブリ構文に基づいています。この構文は、一般的なx86アセンブリとは異なる特徴を持っています。

`123(PC)`形式は、プログラムカウンタ（PC）からの相対オフセットを指定するアドレス指定モードの一種です。これは、特定のラベルに名前を付けずに、PCからの相対的な距離でジャンプ先を指定する際に使用されることがあります。しかし、ラベルが関数スコープを持つようになると、意味のあるラベル名を使ってジャンプ先を明確に指定できるため、このような数値による相対アドレス指定の必要性が薄れます。

### Yacc/Bisonとパーサー生成

Yacc (Yet Another Compiler Compiler) やそのGNU版であるBisonは、文法定義ファイル（通常は`.y`または`.yy`拡張子）から、C言語などのプログラミング言語で書かれた構文解析器（パーサー）を自動生成するツールです。アセンブラのような言語処理系では、入力されたアセンブリコードの構文を解析するために、このようなパーサー生成ツールが頻繁に利用されます。

`a.y`ファイルはアセンブラの構文規則を定義しており、Bisonによって`y.tab.c`というC言語のソースファイルが生成されます。この`y.tab.c`ファイルには、構文解析ロジックが実装されています。

## 技術的詳細

この変更の核心は、アセンブラがラベルを管理する方法の変更にあります。以前は、全てのアセンブリラベルが単一のグローバルなシンボルテーブルで管理されていたと考えられます。このコミットにより、アセンブラはラベルを関数ごとに分離して管理するようになりました。

具体的な実装としては、以下の点が挙げられます。

1.  **シンボル構造体の変更**: アセンブラが使用するシンボル（`Sym`）構造体に、ラベルがどの関数に属するかを識別するための情報が追加された可能性があります。コミットの差分を見ると、`src/cmd/5a/a.h`などのヘッダーファイルで`Sym`構造体に`labelname`フィールドが追加されています。これは、ラベルの実際の名前とは別に、関数スコープ内で一意性を保証するための内部的な名前を管理するためかもしれません。

2.  **パーサーの変更**: `a.y`ファイル（Yacc/Bisonの文法定義）が変更され、ラベルの定義と参照のルールが更新されました。
    *   `LLAB`（グローバルラベル）の扱いが削除され、`LNAME`（一般的な名前）がラベルとして扱われるようになりました。
    *   新しい関数`labellookup`が導入され、ラベルを検索する際に現在の関数スコープを考慮するようになりました。
    *   ラベルの再宣言チェックが、関数スコープ内で行われるように変更されました。つまり、同じ関数内で同じ名前のラベルを複数回定義するとエラーになりますが、異なる関数であれば同じ名前のラベルを定義できます。
    *   `settext`関数が導入され、現在のテキストセクション（関数）を設定する役割を担っています。これにより、`labellookup`が正しい関数スコープでラベルを検索できるようになります。

3.  **生成されたパーサーコードの更新**: `a.y`ファイルの変更に伴い、Bisonによって生成される`y.tab.c`ファイルが大幅に更新されています。これらのファイルは、Yacc/Bisonの内部的なテーブル構造（状態遷移テーブル、ルール定義など）を含んでおり、文法規則の変更がこれらのテーブルに反映されるため、行数ベースでは大きな差分となります。

4.  **ランタイムアセンブリファイルの調整**: ラベルのスコープ変更は、既存のランタイムアセンブリコードに影響を与える可能性があります。特に、以前はグローバルなラベルに依存していた部分や、特定のPC相対アドレス指定に頼っていた部分が、新しい関数スコープのラベル規則に合わせて調整されたと考えられます。コミットの差分には、`src/runtime/asm_*.s`などのファイルが含まれており、これらのファイル内のラベル定義や参照が更新されたことを示しています。

この変更は、アセンブラの内部的なシンボル管理をより堅牢にし、Goアセンブリ言語のセマンティクスをより明確にするものです。これにより、アセンブリコードの記述がより安全で、意図しない名前の衝突を防ぐことができます。

## コアとなるコードの解説

### `Sym`構造体への`labelname`追加

`Sym`構造体はアセンブラがシンボル（関数名、変数名、ラベル名など）を管理するために使用されます。`labelname`フィールドの追加は、ラベルが関数スコープを持つようになったことを反映しています。これにより、アセンブラは同じ`name`を持つ複数のラベルを、異なる`labelname`（おそらく関数名とラベル名を組み合わせたもの）で区別できるようになります。これは、内部的にラベルの完全修飾名を管理するためのメカニズムと考えられます。

### `a.y`におけるラベル処理の変更

1.  **`LLAB`の削除と`LNAME`への統一**: 以前は`LLAB`というトークンがグローバルなラベルを、`LNAME`が一般的な名前を指していた可能性があります。この変更により、全てのラベルが`LNAME`として扱われるようになり、そのスコープは文法規則と`labellookup`関数によって決定されるようになりました。これにより、文法が簡素化され、ラベルの扱いが一貫したものになります。

2.  **`labellookup`関数の導入**:
    *   `$1 = labellookup($1);` の行は、パーサーがラベル名（`LNAME`）を読み込んだ際に、そのラベルが現在の関数スコープ内で既に定義されているか、または新しいラベルとして登録する必要があるかを判断するために`labellookup`関数を呼び出すことを示しています。
    *   この関数は、現在の関数コンテキストに基づいてラベルを検索し、適切な`Sym`エントリを返す役割を担います。これにより、異なる関数で同じ名前のラベルが定義されても、名前の衝突が回避されます。

3.  **再宣言チェックの変更**:
    *   `if($1->type == LLAB && $1->value != pc) yyerror("redeclaration of %s", $1->labelname);` の行は、ラベルの再宣言チェックが`labelname`（関数スコープを考慮した内部名）に基づいて行われるようになったことを示しています。`$1->value != pc`は、ラベルが現在のプログラムカウンタ（`pc`）と同じアドレスを指していない場合に再宣言と見なす、というアセンブラ特有のロジックです。

4.  **`settext`関数の導入**:
    *   `settext($2.sym);` の行は、アセンブラが新しい関数（テキストセクション）の処理を開始する際に、現在の関数シンボルを`settext`関数に渡すことを示しています。この関数は、`labellookup`が正しい関数スコープで動作するために必要なコンテキスト（現在の関数）を設定します。これにより、アセンブラはどの関数内でラベルが定義されているかを追跡できるようになります。

5.  **`rel`（相対アドレス）規則の変更**:
    *   `LNAME offset`の規則で`$1 = labellookup($1);`が追加され、ラベル参照時にも関数スコープが考慮されるようになりました。
    *   `if(pass == 2 && $1->type != LLAB) yyerror("undefined label: %s", $1->labelname);` は、2パスアセンブルの2パス目（シンボル解決パス）において、参照されたラベルが`LLAB`タイプ（つまり、有効なラベルとして定義されている）でない場合に「未定義ラベル」エラーを報告するように変更されています。ここでも`labelname`がエラーメッセージに使用されています。

これらの変更により、Goアセンブラはラベルのスコープを厳密に管理し、より堅牢で直感的なアセンブリコードの記述を可能にしています。

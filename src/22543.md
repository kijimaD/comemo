# [インデックス 22543] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージにおける `ServeContent` 関数が、HTTPレスポンスの `Last-Modified` ヘッダー生成時や `If-Modified-Since` リクエストヘッダーのチェック時に、Unixエポックタイム（1970年1月1日00:00:00 UTC）を不正な値として無視するように変更するものです。これにより、誤ったタイムスタンプが原因で発生する可能性のあるHTTPキャッシュ関連の問題が回避されます。

## 元コミット内容

`net/http: ignore the Unix epoch time in ServeContent`

`ServeContent` は、`Last-Modified` レスポンスヘッダーを生成したり、`If-Modified-Since` リクエストヘッダーをチェックしたりする際に、`time.Time{}` のゼロ値を無視していました。このコミットでは、Unixエポックのゼロ値 (`time.Unix(0, 0)`) を表す `time.Time` 値についても同様に無視するようにします。これは一般的な不正な値であるためです。もし本当にその値を送信したい呼び出し元（非常にありそうにないケースですが）は、それにナノ秒を追加すれば、いずれにせよ秒単位に切り捨てられます。

`Fixes #9842`

## 変更の背景

HTTPプロトコルでは、リソースの最終更新日時を示す `Last-Modified` ヘッダーや、クライアントが持つリソースの最終更新日時をサーバーに伝える `If-Modified-Since` ヘッダーが、キャッシュの効率的な利用のために用いられます。サーバーは `If-Modified-Since` ヘッダーの値とリソースの実際の最終更新日時を比較し、リソースが変更されていなければ `304 Not Modified` ステータスを返し、コンテンツの再送信を避けることができます。

Goの `net/http` パッケージの `ServeContent` 関数は、ファイルやその他のコンテンツをHTTPレスポンスとして提供する際に、これらのヘッダーを適切に処理する役割を担っています。しかし、これまでの実装では、`time.Time{}` (Goの `time.Time` 型のゼロ値、つまり `0001-01-01 00:00:00 +0000 UTC` に相当) は特別に扱われ、`Last-Modified` ヘッダーの生成や `If-Modified-Since` のチェックから除外されていました。これは、有効な更新日時ではないと見なされるためです。

しかし、一部のシステムやライブラリでは、日付が未設定または無効な場合に、Unixエポックタイム（1970年1月1日00:00:00 UTC）をゼロ値として扱うことがあります。例えば、C言語の `time_t` 型は通常、Unixエポックからの秒数を表し、初期値やエラー値として `0` が使われることがあります。このような「不正な」Unixエポックタイムが `ServeContent` に渡された場合、それは有効なタイムスタンプとして扱われ、`Last-Modified` ヘッダーに設定されたり、`If-Modified-Since` の比較に使われたりする可能性がありました。

この挙動は、実際にはリソースが更新されていないにもかかわらず、クライアントが常に `If-Modified-Since` ヘッダーの比較に失敗し、不必要にコンテンツを再ダウンロードしてしまうという問題（Issue #9842）を引き起こす可能性がありました。このコミットは、この「Unixエポックタイム」という一般的な不正値を `time.Time{}` のゼロ値と同様に無視することで、この問題を解決し、HTTPキャッシュの挙動をより堅牢にすることを目的としています。

## 前提知識の解説

1.  **HTTPキャッシュと条件付きリクエスト**:
    *   **`Last-Modified` ヘッダー**: サーバーがレスポンスに含めるヘッダーで、リソースが最後に変更された日時を示します。
    *   **`If-Modified-Since` ヘッダー**: クライアントがリクエストに含めるヘッダーで、クライアントが最後にリソースを受け取った日時を示します。サーバーはこれを見て、リソースが変更されたかどうかを判断します。
    *   **`304 Not Modified` ステータス**: サーバーが `If-Modified-Since` ヘッダーを受け取り、リソースが指定された日時以降に変更されていない場合に返すHTTPステータスコードです。これにより、クライアントはキャッシュされたコンテンツを使用し、帯域幅を節約できます。

2.  **Go言語の `time.Time` 型**:
    *   Go言語で日時を扱うための型です。
    *   `time.Time{}` は `time.Time` 型のゼロ値であり、`0001-01-01 00:00:00 +0000 UTC` を表します。これは通常、有効な日時ではないことを示すために使われます。
    *   `time.Unix(sec, nsec)` は、Unixエポック（1970年1月1日00:00:00 UTC）からの秒数とナノ秒数に基づいて `time.Time` オブジェクトを作成します。`time.Unix(0, 0)` はUnixエポックタイムそのものを表します。

3.  **Unixエポックタイム**:
    *   1970年1月1日00:00:00 UTCを基準点（エポック）とする時刻表現です。多くのUNIX系システムやプログラミング言語で、時刻を整数値（秒数やミリ秒数など）で表現する際の基準となります。
    *   `0` という値は、Unixエポックタイムそのもの、または初期化されていない、あるいは無効な時刻を示す「不正な値」として使われることがあります。

4.  **`net/http.ServeContent` 関数**:
    *   Goの `net/http` パッケージが提供するユーティリティ関数で、`io.ReadSeeker` インターフェースを実装するコンテンツ（例: `*os.File`）をHTTPレスポンスとして提供するために使用されます。
    *   この関数は、`Content-Type`、`Content-Length`、`Last-Modified` などの適切なHTTPヘッダーを設定し、`Range` リクエストや条件付きリクエスト（`If-Modified-Since` など）を処理します。

## 技術的詳細

このコミットの核心は、`net/http` パッケージ内の `checkLastModified` 関数における条件付きロジックの拡張です。

`checkLastModified` 関数は、HTTPレスポンスの `Last-Modified` ヘッダーの処理と、`If-Modified-Since` リクエストヘッダーに基づく条件付きレスポンスの決定を担当します。この関数は、リソースの最終更新日時 (`modtime`) を引数として受け取ります。

変更前は、`modtime.IsZero()` が `true` の場合（つまり、`modtime` が `time.Time{}` のゼロ値である場合）にのみ、`Last-Modified` ヘッダーの生成と `If-Modified-Since` のチェックをスキップしていました。これは、`time.Time{}` が有効な更新日時ではないという前提に基づいています。

しかし、前述の通り、Unixエポックタイム (`time.Unix(0, 0)`) もまた、多くの文脈で「不正な」または「未設定の」日時として扱われることがあります。`time.Unix(0, 0)` は `time.Time{}` とは異なる値であるため、変更前の `checkLastModified` 関数では `modtime.IsZero()` が `false` となり、有効な日時として扱われてしまっていました。

このコミットでは、`checkLastModified` 関数に `modtime.Equal(unixEpochTime)` という条件が追加されました。ここで `unixEpochTime` は、`time.Unix(0, 0)` を表すグローバル変数として新しく定義されています。これにより、`modtime` が `time.Time{}` のゼロ値であるか、またはUnixエポックタイムであるかのいずれかの場合に、`Last-Modified` ヘッダーの処理と `If-Modified-Since` のチェックがスキップされるようになります。

この変更により、`ServeContent` は、ファイルシステムから取得したタイムスタンプがたまたまUnixエポックタイムであったり、他のシステムから渡された不正なタイムスタンプがUnixエポックタイムであったりする場合でも、それらを有効な更新日時として扱わなくなり、HTTPキャッシュの挙動がより予測可能で堅牢になります。

コミットメッセージにある「Callers who really want to send that value (incredibly unlikely) can add a nanosecond to it and it will be truncated to second granularity anyway.」という記述は、もし本当にUnixエポックタイムを有効な `Last-Modified` ヘッダーとして送信したいという稀なケースがあるならば、`time.Unix(0, 1)` のようにナノ秒を追加することで、この新しいチェックを回避できることを示唆しています。HTTPの `Last-Modified` ヘッダーは秒単位の精度しか持たないため、ナノ秒を追加しても最終的には秒単位に切り捨てられ、視覚的にはUnixエポックタイムとほぼ同じになります。

## コアとなるコードの解説

### `src/net/http/fs.go`

1.  **`unixEpochTime` 変数の追加**:
    `var unixEpochTime = time.Unix(0, 0)`
    この行は、Unixエポックタイム（1970年1月1日00:00:00 UTC）を表す `time.Time` オブジェクトをグローバル変数 `unixEpochTime` として定義しています。これにより、`checkLastModified` 関数内でこの値を効率的に参照できるようになります。

2.  **`checkLastModified` 関数の条件変更**:
    変更前: `if modtime.IsZero() {`
    変更後: `if modtime.IsZero() || modtime.Equal(unixEpochTime) {`
    これがこのコミットの最も重要な変更点です。
    *   `modtime.IsZero()`: `modtime` が `time.Time{}` のゼロ値（`0001-01-01`）であるかをチェックします。
    *   `modtime.Equal(unixEpochTime)`: `modtime` が新しく定義された `unixEpochTime`（`1970-01-01`）と等しいかをチェックします。
    論理OR (`||`) を使用することで、どちらかの条件が真であれば、`Last-Modified` ヘッダーの処理と `If-Modified-Since` のチェックをスキップするようになります。
    追加されたコメント `// If the file doesn't have a modtime (IsZero), or the modtime // is obviously garbage (Unix time == 0), then ignore modtimes // and don't process the If-Modified-Since header.` は、この変更の意図を明確に説明しています。つまり、`IsZero()` のケースは「ファイルに更新日時がない場合」、`Unix time == 0` のケースは「更新日時が明らかにゴミ値である場合」と解釈されます。

3.  **コメントの更新**:
    `ServeContent` のドキュメントコメントも更新され、`modtime` が「ゼロタイムまたはUnixエポックではない場合」に `Last-Modified` ヘッダーが含まれることが明記されました。これは、コードの変更内容とドキュメントの一貫性を保つための重要な修正です。

### `src/net/http/fs_test.go`

1.  **新しいテストケース `unix_zero_modtime` の追加**:
    このテストケースは、`ServeContent` に `time.Unix(0, 0)` を `modtime` として渡した場合の挙動を検証します。
    *   `modtime: time.Unix(0, 0)`: テスト対象の `modtime` をUnixエポックタイムに設定します。
    *   `wantStatus: StatusOK`: 期待されるHTTPステータスコードは `200 OK` です。これは、`modtime` が無視されるため、条件付きリクエストが適用されず、コンテンツが常に送信されることを意味します（`304 Not Modified` にならない）。
    このテストの追加により、`checkLastModified` の変更が意図通りに機能し、Unixエポックタイムが正しく「無視」されることが保証されます。

これらの変更により、`net/http` パッケージは、不正なタイムスタンプ（特にUnixエポックタイム）がHTTPキャッシュのメカニズムに悪影響を与えることを防ぎ、より堅牢なWebサーバー機能を提供できるようになりました。

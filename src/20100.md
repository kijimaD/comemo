## 変更の背景

Go言語のランタイム、特にガベージコレクタ（GC）は、メモリ管理において重要な役割を果たします。GCは、プログラムが使用しなくなったメモリ領域を自動的に解放することで、メモリリークを防ぎ、開発者の負担を軽減します。このプロセスにおいて、GCはヒープ上のオブジェクトがポインタを含むかどうか、あるいはどの部分がポインタであるかを識別するために「ビットマップ」と呼ばれるデータ構造を使用します。ビットマップは、メモリ領域の各ワード（またはバイト）に対応するビットを持ち、そのビットがセットされているかどうかでポインタの有無を示します。

このコミットが作成された2014年当時、GoのGCは「よりシンプルで高速なガベージコレクタ」として開発が進められていました。しかし、この新しいGCの実装には、特定のアーキテクチャにおけるバイト順序、すなわち「エンディアンネス」に関する暗黙の仮定が含まれていました。具体的には、多くの一般的なアーキテクチャ（x86など）が採用している「リトルエンディアン」を前提として設計されていたようです。

リトルエンディアンでは、複数バイトで構成されるデータ（例: 32ビット整数）がメモリに格納される際、最下位バイトが最も小さいアドレスに配置されます。一方、「ビッグエンディアン」では、最上位バイトが最も小さいアドレスに配置されます。異なるエンディアンネスを持つシステム間でデータをやり取りする場合や、低レベルのメモリ操作を行う際には、このバイト順序の違いが問題となることがあります。

Goはクロスプラットフォーム言語であり、様々なCPUアーキテクチャで動作する必要があります。`[dev.power64]`というコミットプレフィックスが示すように、この問題は特にPowerPC 64ビットアーキテクチャ（一部はビッグエンディアンを採用）での開発中に顕在化したと考えられます。リトルエンディアンの仮定に基づいて設計されたビットマップ処理が、ビッグエンディアンシステムで正しく機能しない可能性があったため、この根本的な問題を解決する必要がありました。

コミットメッセージにある「すべての間違いを修正しようとする代わりに、諦めてすべてをバイトを使用するようにします」という表現は、既存の`uint32`ベースのビットマップ処理におけるエンディアンネス関連のバグを個別に修正するよりも、ビットマップの基本単位を`uint32`（4バイト）から`byte`（1バイト）に変更する方が、より根本的かつ堅牢な解決策であるという判断を示しています。これにより、バイト単位でメモリを操作することで、エンディアンネスの違いを吸収し、コードのポータビリティと正確性を向上させることが目的です。

## 前提知識の解説

### 1. ガベージコレクタ (Garbage Collector, GC)

ガベージコレクタは、プログラムが動的に確保したメモリ領域のうち、もはや到達不可能（参照されていない）になったものを自動的に検出し、解放するシステムです。Go言語のGCは、並行マーク＆スイープ方式をベースとしており、プログラムの実行と並行してGC処理を進めることで、アプリケーションの一時停止時間（Stop-the-World時間）を最小限に抑えるように設計されています。

GCがメモリをスキャンする際、ヒープ上のオブジェクトがポインタを含むかどうか、そしてそのポインタがどこを指しているかを正確に知る必要があります。これは、ポインタが指す先のオブジェクトも「生きている」と判断し、回収対象から除外するためです。このポインタの識別には、通常「ポインタマップ」や「ビットマップ」と呼ばれるデータ構造が利用されます。

### 2. ビットマップ (Bitmap)

ビットマップは、メモリ領域の特定のプロパティ（この場合はポインタの有無）をビット単位で表現するデータ構造です。GoのGCでは、ヒープ上の各オブジェクトやスタックフレーム内の変数について、どのオフセットにポインタが含まれているかを示すためにビットマップを使用します。例えば、32ビット（4バイト）のワードごとに1ビットを割り当て、そのビットが1であればそのワードにポインタが含まれる、0であれば含まれない、といった形で情報をエンコードします。

### 3. エンディアンネス (Endianness)

エンディアンネスは、コンピュータのメモリ上で複数バイトのデータ（例: 整数、浮動小数点数）がどのように格納されるかのバイト順序を指します。主に以下の2種類があります。

*   **リトルエンディアン (Little-endian)**: データの最下位バイト（least significant byte, LSB）が最も小さいメモリアドレスに格納されます。例えば、16進数`0x12345678`という32ビット整数は、メモリ上では`78 56 34 12`の順で格納されます（アドレスが小さい方から）。Intel x86/x64アーキテクチャがこれに該当します。
*   **ビッグエンディアン (Big-endian)**: データの最上位バイト（most significant byte, MSB）が最も小さいメモリアドレスに格納されます。同じ`0x12345678`は、メモリ上では`12 34 56 78`の順で格納されます。PowerPC、SPARC、MIPS（設定可能）などのアーキテクチャがこれに該当します。ネットワークバイトオーダーはビッグエンディアンです。

Go言語は、異なるエンディアンネスを持つシステム上で同じバイナリコードが正しく動作するように設計されています。しかし、低レベルのメモリ操作、特にポインタのビットマップのようにバイト順序に依存するデータ構造を扱う場合、エンディアンネスの違いを考慮しないと、データが誤って解釈される可能性があります。

### 4. `uint32`と`byte`

*   **`uint32`**: 32ビット（4バイト）の符号なし整数型です。C言語の`unsigned int`やGo言語の`uint32`に相当します。メモリ上では、エンディアンネスに応じて4バイトが特定の順序で並びます。
*   **`byte`**: 8ビット（1バイト）のデータ型です。C言語の`unsigned char`やGo言語の`byte`（`uint8`のエイリアス）に相当します。`byte`はそれ自体が最小のメモリアドレス可能な単位であるため、`byte`の配列としてデータを扱う場合、エンディアンネスの問題は発生しません。各バイトは独立した単位として扱われます。

このコミットの変更は、ビットマップを`uint32`の配列として扱うと、その`uint32`内部のバイト順序がエンディアンネスに依存するため問題が生じるのに対し、`byte`の配列として扱うことで、各ビットが常に正しいバイト位置にマッピングされるようにするという意図があります。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのガベージコレクタが使用するビットマップのデータ表現とアクセス方法を、エンディアンネスに依存しないように変更することです。

以前のGC実装では、ビットマップは`uint32`の配列として定義されていました。例えば、`src/pkg/runtime/malloc.h`の`BitVector`構造体は、`uint32 *data;`というフィールドを持っていました。これは、ビットマップのデータを32ビット単位で管理することを意味します。

```c
// Before
typedef struct BitVector BitVector;
struct BitVector
{
    int32 n; // # of bits
    uint32 *data;
};
```

この`uint32`配列を直接操作する際、例えば特定のビットを読み書きするためにビットシフトやマスク操作を行う場合、その`uint32`がメモリ上でどのように配置されているか（リトルエンディアンかビッグエンディアンか）によって、期待する結果が得られない可能性がありました。特に、ビットマップが複数のワードにまたがる場合や、バイト単位でアクセスする必要がある場合に問題が顕在化します。

このコミットでは、この問題を解決するために、ビットマップのデータ型を`uint32 *data;`から`uint8 *bytedata;`（Goの`byte`は`uint8`のエイリアス）に変更しています。

```c
// After
typedef struct BitVector BitVector;
struct BitVector
{
    int32 n; // # of bits
    uint8 *bytedata; // Changed from uint32 *data;
};
```

同様に、スタックマップを定義する`StackMap`構造体も`uint32 data[];`から`uint8 bytedata[];`に変更されています。

この変更により、ビットマップのデータは常にバイトの配列として扱われるようになります。これにより、特定のビットにアクセスする際には、まず目的のビットがどのバイトに属するかを計算し、そのバイトに対してビット操作を行うようになります。バイト単位でのアクセスは、エンディアンネスの影響を受けません。なぜなら、各バイトはそれ自体がアドレス可能な最小単位であり、その内部のビット順序はCPUアーキテクチャに依存しないためです。

変更の具体的な影響は以下のファイルに見られます。

*   `src/cmd/gc/plive.c`: コンパイラがGCビットマップを生成する部分で、`uint32`を4つの`uint8`として出力するように変更されています。これは、ランタイムがビットマップをバイト配列として読み込むことを前提とした変更です。
    *   `duint32(sym, off, word);` が `duint8(sym, off, word); duint8(sym, off, word>>8); ...` のように4つのバイトに分割して書き込む形に変更されています。
*   `src/pkg/runtime/heapdump.c`, `src/pkg/runtime/malloc.go`, `src/pkg/runtime/malloc.h`, `src/pkg/runtime/mgc0.c`, `src/pkg/runtime/mgc0.h`, `src/pkg/runtime/stack.c`: これらのファイルでは、`BitVector`や`StackMap`構造体の定義が`uint32*`から`uint8*`（または`byte*`）に変更され、それに伴いビットマップへのアクセスロジックも`data[i/32]`のようなワードベースのインデックス計算から`bytedata[i/8]`のようなバイトベースのインデックス計算に修正されています。
    *   特に`src/pkg/runtime/mgc0.c`では、`byteEndian`という新しい定数が導入され、ビッグエンディアンシステムでのバイト順序の調整に使用されています。これは、`((byte*)b)[(shift/8)^byteEndian]`のように、バイト配列へのアクセス時にXOR演算子を使ってエンディアンネスを考慮したオフセット計算を行うことで、ポータビリティを確保しています。
    *   `runtime·atomicstore((uint32*)mask, x|1);` のような`uint32`に対するアトミック操作も、`runtime·atomicstorep((void**)mask, (void*)x);` のようにポインタに対するアトミック操作に変更され、バイト単位でのフラグ設定に対応しています。

この変更は、Goランタイムの低レベルなメモリ管理におけるエンディアンネスの問題を根本的に解決し、Goがより多様なアーキテクチャで安定して動作するための重要なステップでした。

## コアとなるコードの解説

このコミットの核心は、Goランタイムのガベージコレクタがメモリ内のポインタを追跡するために使用するビットマップの表現方法を、エンディアンネスに依存しないように変更することです。

1.  **データ構造の変更 (`BitVector`, `StackMap`)**:
    *   以前は、`BitVector`構造体（ヒープオブジェクトのポインタ情報などを保持）や`StackMap`構造体（スタックフレーム内のポインタ情報などを保持）の内部データは`uint32`の配列として定義されていました。これは、32ビット単位でビットマップを管理することを意味します。
    *   このコミットでは、これらの構造体のデータフィールドが`uint32 *data;`から`uint8 *bytedata;`（または`byte*`）に変更されました。これにより、ビットマップのデータは常にバイトの配列として扱われるようになります。

2.  **コンパイラ側の変更 (`src/cmd/gc/plive.c`)**:
    *   Goコンパイラは、プログラムの型情報に基づいてGCが使用するビットマップを生成します。以前は、このビットマップを`uint32`として出力していました。
    *   変更後、コンパイラは`uint32`のワードを、個々のバイトに分解して`duint8`関数で出力するように修正されました。これは、ランタイム側がビットマップをバイト配列として読み込むことを前提とした連携変更です。これにより、コンパイラが生成するビットマップデータが、ランタイムの新しいバイトベースの解釈と一致するようになります。

3.  **ランタイム側のアクセスロジックの変更 (`src/pkg/runtime/mgc0.c`, `src/pkg/runtime/heapdump.c`, `src/pkg/runtime/stack.c`など)**:
    *   ビットマップへのアクセスは、`data[i/32]`のような`uint32`ワードベースのインデックス計算から、`bytedata[i/8]`のようなバイトベースのインデックス計算に修正されました。
    *   最も重要な変更の一つは、`src/pkg/runtime/mgc0.c`で導入された`byteEndian`定数と、それを用いたバイト配列へのアクセスです。
        *   `byteEndian`は、システムがビッグエンディアンである場合に、バイトオフセットを調整するための値です。例えば、64ビットシステムでビッグエンディアンの場合、`byteEndian`は`7`（`BigEndian*7`）となります。
        *   ビットマップの特定のバイトに書き込む際、`((byte*)b)[(shift/8)^byteEndian]`のようにXOR演算子`^`を使用してオフセットを計算しています。これは、ビッグエンディアンシステムにおいて、リトルエンディアンの仮定で計算されたバイトオフセットを正しい物理的なバイト位置にマッピングするための巧妙なトリックです。例えば、リトルエンディアンではワードの先頭バイトが最も小さいアドレスに来ますが、ビッグエンディアンではワードの末尾バイトが最も小さいアドレスに来ます。このXOR演算は、このバイト順序の違いを吸収し、常に正しいバイトにアクセスできるようにします。
    *   アトミック操作も、`uint32`に対するものから、より汎用的なポインタに対するアトミック操作（`runtime·atomicstorep`）に変更され、バイト単位でのフラグ設定に対応しています。

これらの変更により、Goランタイムのガベージコレクタは、基盤となるCPUアーキテクチャのエンディアンネスに依存することなく、ビットマップを正しく解釈し、メモリ内のポインタを正確に追跡できるようになりました。これは、Goのクロスプラットフォーム対応と堅牢性を向上させる上で非常に重要な改善です。

## 変更の背景

Go言語のランタイム、特にガベージコレクタ（GC）は、メモリ管理において重要な役割を果たします。GCは、プログラムが使用しなくなったメモリ領域を自動的に解放することで、メモリリークを防ぎ、開発者の負担を軽減します。このプロセスにおいて、GCはヒープ上のオブジェクトがポインタを含むかどうか、あるいはどの部分がポインタであるかを識別するために「ビットマップ」と呼ばれるデータ構造を使用します。ビットマップは、メモリ領域の各ワード（またはバイト）に対応するビットを持ち、そのビットがセットされているかどうかでポインタの有無を示します。

このコミットが作成された2014年当時、GoのGCは「よりシンプルで高速なガベージコレクタ」として開発が進められていました。しかし、この新しいGCの実装には、特定のアーキテクチャにおけるバイト順序、すなわち「エンディアンネス」に関する暗黙の仮定が含まれていました。具体的には、多くの一般的なアーキテクチャ（x86など）が採用している「リトルエンディアン」を前提として設計されていたようです。

リトルエンディアンでは、複数バイトで構成されるデータ（例: 32ビット整数）がメモリに格納される際、最下位バイトが最も小さいアドレスに配置されます。一方、「ビッグエンディアン」では、最上位バイトが最も小さいアドレスに配置されます。異なるエンディアンネスを持つシステム間でデータをやり取りする場合や、低レベルのメモリ操作を行う際には、このバイト順序の違いが問題となることがあります。

Goはクロスプラットフォーム言語であり、様々なCPUアーキテクチャで動作する必要があります。`[dev.power64]`というコミットプレフィックスが示すように、この問題は特にPowerPC 64ビットアーキテクチャ（一部はビッグエンディアンを採用）での開発中に顕在化したと考えられます。リトルエンディアンの仮定に基づいて設計されたビットマップ処理が、ビッグエンディアンシステムで正しく機能しない可能性があったため、この根本的な問題を解決する必要がありました。

コミットメッセージにある「すべての間違いを修正しようとする代わりに、諦めてすべてをバイトを使用するようにします」という表現は、既存の`uint32`ベースのビットマップ処理におけるエンディアンネス関連のバグを個別に修正するよりも、ビットマップの基本単位を`uint32`（4バイト）から`byte`（1バイト）に変更する方が、より根本的かつ堅牢な解決策であるという判断を示しています。これにより、バイト単位でメモリを操作することで、エンディアンネスの違いを吸収し、コードのポータビリティと正確性を向上させることが目的です。

## 前提知識の解説

### 1. ガベージコレクタ (Garbage Collector, GC)

ガベージコレクタは、プログラムが動的に確保したメモリ領域のうち、もはや到達不可能（参照されていない）になったものを自動的に検出し、解放するシステムです。Go言語のGCは、並行マーク＆スイープ方式をベースとしており、プログラムの実行と並行してGC処理を進めることで、アプリケーションの一時停止時間（Stop-the-World時間）を最小限に抑えるように設計されています。

GCがメモリをスキャンする際、ヒープ上のオブジェクトがポインタを含むかどうか、そしてそのポインタがどこを指しているかを正確に知る必要があります。これは、ポインタが指す先のオブジェクトも「生きている」と判断し、回収対象から除外するためです。このポインタの識別には、通常「ポインタマップ」や「ビットマップ」と呼ばれるデータ構造が利用されます。

### 2. ビットマップ (Bitmap)

ビットマップは、メモリ領域の特定のプロパティ（この場合はポインタの有無）をビット単位で表現するデータ構造です。GoのGCでは、ヒープ上の各オブジェクトやスタックフレーム内の変数について、どのオフセットにポインタが含まれているかを示すためにビットマップを使用します。例えば、32ビット（4バイト）のワードごとに1ビットを割り当て、そのビットが1であればそのワードにポインタが含まれる、0であれば含まれない、といった形で情報をエンコードします。

### 3. エンディアンネス (Endianness)

エンディアンネスは、コンピュータのメモリ上で複数バイトのデータ（例: 整数、浮動小数点数）がどのように格納されるかのバイト順序を指します。主に以下の2種類があります。

*   **リトルエンディアン (Little-endian)**: データの最下位バイト（least significant byte, LSB）が最も小さいメモリアドレスに格納されます。例えば、16進数`0x12345678`という32ビット整数は、メモリ上では`78 56 34 12`の順で格納されます（アドレスが小さい方から）。Intel x86/x64アーキテクチャがこれに該当します。
*   **ビッグエンディアン (Big-endian)**: データの最上位バイト（most significant byte, MSB）が最も小さいメモリアドレスに格納されます。同じ`0x12345678`は、メモリ上では`12 34 56 78`の順で格納されます。PowerPC、SPARC、MIPS（設定可能）などのアーキテクチャがこれに該当します。ネットワークバイトオーダーはビッグエンディアンです。

Go言語は、異なるエンディアンネスを持つシステム上で同じバイナリコードが正しく動作するように設計されています。しかし、低レベルのメモリ操作、特にポインタのビットマップのようにバイト順序に依存するデータ構造を扱う場合、エンディアンネスの違いを考慮しないと、データが誤って解釈される可能性があります。

### 4. `uint32`と`byte`

*   **`uint32`**: 32ビット（4バイト）の符号なし整数型です。C言語の`unsigned int`やGo言語の`uint32`に相当します。メモリ上では、エンディアンネスに応じて4バイトが特定の順序で並びます。
*   **`byte`**: 8ビット（1バイト）のデータ型です。C言語の`unsigned char`やGo言語の`byte`（`uint8`のエイリアス）に相当します。`byte`はそれ自体が最小のメモリアドレス可能な単位であるため、`byte`の配列としてデータを扱う場合、エンディアンネスの問題は発生しません。各バイトは独立した単位として扱われます。

このコミットの変更は、ビットマップを`uint32`の配列として扱うと、その`uint32`内部のバイト順序がエンディアンネスに依存するため問題が生じるのに対し、`byte`の配列として扱うことで、各ビットが常に正しいバイト位置にマッピングされるようにするという意図があります。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのガベージコレクタが使用するビットマップのデータ表現とアクセス方法を、エンディアンネスに依存しないように変更することです。

以前のGC実装では、ビットマップは`uint32`の配列として定義されていました。例えば、`src/pkg/runtime/malloc.h`の`BitVector`構造体は、`uint32 *data;`というフィールドを持っていました。これは、ビットマップのデータを32ビット単位で管理することを意味します。

```c
// Before
typedef struct BitVector BitVector;
struct BitVector
{
    int32 n; // # of bits
    uint32 *data;
};
```

この`uint32`配列を直接操作する際、例えば特定のビットを読み書きするためにビットシフトやマスク操作を行う場合、その`uint32`がメモリ上でどのように配置されているか（リトルエンディアンかビッグエンディアンか）によって、期待する結果が得られない可能性がありました。特に、ビットマップが複数のワードにまたがる場合や、バイト単位でアクセスする必要がある場合に問題が顕在化します。

このコミットでは、この問題を解決するために、ビットマップのデータ型を`uint32 *data;`から`uint8 *bytedata;`（Goの`byte`は`uint8`のエイリアス）に変更しています。

```c
// After
typedef struct BitVector BitVector;
struct BitVector
{
    int32 n; // # of bits
    uint8 *bytedata; // Changed from uint32 *data;
};
```

同様に、スタックマップを定義する`StackMap`構造体も`uint32 data[];`から`uint8 bytedata[];`に変更されています。

この変更により、ビットマップのデータは常にバイトの配列として扱われるようになります。これにより、特定のビットにアクセスする際には、まず目的のビットがどのバイトに属するかを計算し、そのバイトに対してビット操作を行うようになります。バイト単位でのアクセスは、エンディアンネスの影響を受けません。なぜなら、各バイトはそれ自体がアドレス可能な最小単位であり、その内部のビット順序はCPUアーキテクチャに依存しないためです。

変更の具体的な影響は以下のファイルに見られます。

*   `src/cmd/gc/plive.c`: コンパイラがGCビットマップを生成する部分で、`uint32`を4つの`uint8`として出力するように変更されています。これは、ランタイムがビットマップをバイト配列として読み込むことを前提とした変更です。
    *   `duint32(sym, off, word);` が `duint8(sym, off, word); duint8(sym, off, word>>8); ...` のように4つのバイトに分割して書き込む形に変更されています。
*   `src/pkg/runtime/heapdump.c`, `src/pkg/runtime/malloc.go`, `src/pkg/runtime/malloc.h`, `src/pkg/runtime/mgc0.c`, `src/pkg/runtime/mgc0.h`, `src/pkg/runtime/stack.c`: これらのファイルでは、`BitVector`や`StackMap`構造体の定義が`uint32*`から`uint8*`（または`byte*`）に変更され、それに伴いビットマップへのアクセスロジックも`data[i/32]`のようなワードベースのインデックス計算から`bytedata[i/8]`のようなバイトベースのインデックス計算に修正されています。
    *   特に`src/pkg/runtime/mgc0.c`では、`byteEndian`という新しい定数が導入され、ビッグエンディアンシステムでのバイト順序の調整に使用されています。これは、`((byte*)b)[(shift/8)^byteEndian]`のように、バイト配列へのアクセス時にXOR演算子を使ってエンディアンネスを考慮したオフセット計算を行うことで、ポータビリティを確保しています。
    *   `runtime·atomicstore((uint32*)mask, x|1);` のような`uint32`に対するアトミック操作も、`runtime·atomicstorep((void**)mask, (void*)x);` のようにポインタに対するアトミック操作に変更され、バイト単位でのフラグ設定に対応しています。

この変更は、Goランタイムの低レベルなメモリ管理におけるエンディアンネスの問題を根本的に解決し、Goがより多様なアーキテクチャで安定して動作するための重要なステップでした。

## コアとなるコードの解説

このコミットの核心は、Goランタイムのガベージコレクタがメモリ内のポインタを追跡するために使用するビットマップの表現方法を、エンディアンネスに依存しないように変更することです。

1.  **データ構造の変更 (`BitVector`, `StackMap`)**:
    *   以前は、`BitVector`構造体（ヒープオブジェクトのポインタ情報などを保持）や`StackMap`構造体（スタックフレーム内のポインタ情報などを保持）の内部データは`uint32`の配列として定義されていました。これは、32ビット単位でビットマップを管理することを意味します。
    *   このコミットでは、これらの構造体のデータフィールドが`uint32 *data;`から`uint8 *bytedata;`（または`byte*`）に変更されました。これにより、ビットマップのデータは常にバイトの配列として扱われるようになります。

2.  **コンパイラ側の変更 (`src/cmd/gc/plive.c`)**:
    *   Goコンパイラは、プログラムの型情報に基づいてGCが使用するビットマップを生成します。以前は、このビットマップを`uint32`として出力していました。
    *   変更後、コンパイラは`uint32`のワードを、個々のバイトに分解して`duint8`関数で出力するように修正されました。これは、ランタイム側がビットマップをバイト配列として読み込むことを前提とした連携変更です。これにより、コンパイラが生成するビットマップデータが、ランタイムの新しいバイトベースの解釈と一致するようになります。

3.  **ランタイム側のアクセスロジックの変更 (`src/pkg/runtime/mgc0.c`, `src/pkg/runtime/heapdump.c`, `src/pkg/runtime/stack.c`など)**:
    *   ビットマップへのアクセスは、`data[i/32]`のような`uint32`ワードベースのインデックス計算から、`bytedata[i/8]`のようなバイトベースのインデックス計算に修正されました。
    *   最も重要な変更の一つは、`src/pkg/runtime/mgc0.c`で導入された`byteEndian`定数と、それを用いたバイト配列へのアクセスです。
        *   `byteEndian`は、システムがビッグエンディアンである場合に、バイトオフセットを調整するための値です。例えば、64ビットシステムでビッグエンディアンの場合、`byteEndian`は`7`（`BigEndian*7`）となります。
        *   ビットマップの特定のバイトに書き込む際、`((byte*)b)[(shift/8)^byteEndian]`のようにXOR演算子`^`を使用してオフセットを計算しています。これは、ビッグエンディアンシステムにおいて、リトルエンディアンの仮定で計算されたバイトオフセットを正しい物理的なバイト位置にマッピングするための巧妙なトリックです。例えば、リトルエンディアンではワードの先頭バイトが最も小さいアドレスに来ますが、ビッグエンディアンではワードの末尾バイトが最も小さいアドレスに来ます。このXOR演算は、このバイト順序の違いを吸収し、常に正しいバイトにアクセスできるようにします。
    *   アトミック操作も、`uint32`に対するものから、より汎用的なポインタに対するアトミック操作（`runtime·atomicstorep`）に`変更され、バイト単位でのフラグ設定に対応しています。

これらの変更により、Goランタイムのガベージコレクタは、基盤となるCPUアーキテクチャのエンディアンネスに依存することなく、ビットマップを正しく解釈し、メモリ内のポインタを正確に追跡できるようになりました。これは、Goのクロスプラットフォーム対応と堅牢性を向上させる上で非常に重要な改善です。

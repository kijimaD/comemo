# [インデックス 24360] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおける定数畳み込み（constant folding）の挙動を修正し、特に加算および乗算操作において32ビット整数のみを対象とするように変更したものです。これにより、64ビット定数が誤って32ビットとして扱われることによるアセンブリ生成の失敗や、不正な値の計算を防ぎます。

## 元コミット内容

このコミットは、GoコンパイラのSSAバックエンドにおいて、加算および乗算の定数畳み込み処理が、32ビットを超える定数に対して正しく機能しない問題を修正します。具体的には、32ビットを超える定数との乗算を試みた際に`doasm`（アセンブリ生成フェーズ）が失敗する問題（例: `doasm: notfound ft=9 tt=14 00008 IMULQ $34359738369, CX 9 14`）と、`LEA`（Load Effective Address）命令の生成時に64ビット整数が32ビットに切り詰められ、誤った値が計算される問題を解決します。

## 変更の背景

Goコンパイラは、プログラムのパフォーマンスを向上させるために様々な最適化を行います。その一つが「定数畳み込み」です。これは、コンパイル時に計算可能な定数式を事前に計算し、その結果で置き換える最適化です。例えば、`x = 1 + 2`というコードがあれば、コンパイラはこれを`x = 3`に変換します。

このコミット以前のGoコンパイラのSSAバックエンドでは、加算や乗算の定数畳み込みにおいて、定数のビット幅に関する厳密なチェックが不足していました。特にAMD64アーキテクチャでは、一部の命令（例: `IMULQ`や`LEA`）が特定のビット幅のオペランドを期待します。

問題は以下の2点でした。

1.  **`doasm`の失敗**: 32ビットを超える大きな定数（例: `34359738369`は32ビット符号付き整数の最大値`2,147,483,647`をはるかに超える）との乗算を定数畳み込みしようとした際に、アセンブリ生成フェーズ（`doasm`）が適切な`IMULQ`命令を見つけられずに失敗していました。これは、`IMULQ`命令が即値オペランドとして32ビット符号付き整数を期待する形式があるためと考えられます。
2.  **`LEA`命令での値の切り詰め**: `LEA`命令は、メモリのアドレス計算だけでなく、効率的な算術演算にも利用されます。しかし、この命令を生成する際に、64ビットの定数が誤って32ビットに切り詰められてしまい、結果として計算される値が不正になるというバグがありました。

これらの問題は、コンパイラが生成するコードの正確性に直接影響するため、修正が必要でした。特に、64ビット環境で大きな整数定数を扱うGoプログラムにおいて、予期せぬコンパイルエラーや実行時エラーを引き起こす可能性がありました。

## 前提知識の解説

*   **Goコンパイラ**: Go言語のソースコードを機械語に変換するプログラムです。`cmd/compile`ディレクトリにその主要なコードがあります。
*   **SSA (Static Single Assignment) フォーム**: コンパイラの最適化フェーズで用いられる中間表現（IR）の一種です。各変数が一度だけ代入されるようにすることで、データフロー解析や最適化を容易にします。Goコンパイラは、Go 1.7からSSAバックエンドを導入し、より高度な最適化を可能にしました。
*   **定数畳み込み (Constant Folding)**: コンパイル時最適化の一つで、コンパイル時に値が確定する式（定数式）を、その計算結果で置き換えることです。これにより、実行時の計算コストを削減します。
*   **AMD64アーキテクチャ**: 64ビットのx86命令セットアーキテクチャです。Goコンパイラは、このアーキテクチャ向けに最適化されたコードを生成します。
*   **`doasm`**: Goコンパイラのアセンブリ生成フェーズの一部を指す可能性があります。SSAバックエンドが生成した中間表現から、最終的なアセンブリコードを生成する過程で、特定の命令選択や最適化が行われます。
*   **`IMULQ`**: x86-64アーキテクチャにおける符号付き乗算命令です。オペランドのサイズによって様々な形式があります。即値オペランドを取る場合、その即値は通常32ビット符号付き整数に制限されます。
*   **`LEA` (Load Effective Address)**: x86-64アーキテクチャの命令で、メモリのアドレスを計算し、その結果をレジスタに格納します。アドレス計算は加算やシフト演算を含むことができ、メモリにアクセスせずにこれらの演算を効率的に行うために、算術命令としてもよく利用されます。
*   **`MOVQconst`**: GoコンパイラのSSA中間表現における操作の一つで、64ビットの定数値を表します。
*   **`ADDQconst` / `MULQconst`**: GoコンパイラのSSA中間表現における操作で、定数との加算/乗算を表します。これらは、特定の定数オペランドを持つアセンブリ命令（例: `ADDQ $imm32, reg`）にマッピングされることがあります。
*   **`is32Bit(c)`**: このコミットで導入されたヘルパー関数で、与えられた64ビット整数`c`が、32ビット符号付き整数として表現可能かどうかを判定します。具体的には、`c == int64(int32(c))`という比較で、`c`を32ビット符号付き整数にキャストして再度64ビットに戻したときに元の値と一致するかどうかを確認します。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおける定数畳み込みのルールを、より厳密に32ビット定数に限定することです。

GoコンパイラのSSAバックエンドは、`src/cmd/compile/internal/ssa/gen/AMD64.rules`のようなルールファイルと、`src/cmd/compile/internal/ssa/rewriteAMD64.go`のようなリライト関数を使用して、中間表現を最適化し、ターゲットアーキテクチャ（この場合はAMD64）の命令に変換します。

以前のルールでは、`ADDQ`や`MULQ`といった操作において、`MOVQconst`（64ビット定数）がオペランドとして与えられた場合、その定数が32ビットの範囲に収まるかどうかを十分にチェックせずに、`ADDQconst`や`MULQconst`といった定数オペランドを持つ命令に畳み込もうとしていました。

具体的には、`AMD64.rules`ファイル内の以下のルールが問題でした（変更前）：

```
(ADDQ x (MOVQconst [c])) -> (ADDQconst [c] x)
(MULQ x (MOVQconst [c])) && c == int64(int32(c)) -> (MULQconst [c] x)
```

`MULQ`の場合、`c == int64(int32(c))`という条件がありましたが、これは`ADDQ`にはありませんでした。また、`MULQ`の条件も、`is32Bit`関数が導入される前は、より直接的な比較で行われていました。

このコミットでは、以下の変更が加えられました。

1.  **`is32Bit`関数の導入**: `src/cmd/compile/internal/ssa/rewrite.go`に`is32Bit(n int64) bool`関数が追加されました。この関数は、64ビット整数`n`が32ビット符号付き整数として表現可能かどうかを効率的にチェックします。
2.  **`AMD64.rules`の更新**: `ADDQ`および`MULQ`の定数畳み込みルールに、新しく導入された`is32Bit(c)`条件が追加されました。これにより、定数`c`が32ビット符号付き整数の範囲内にない場合、これらの最適化ルールは適用されなくなります。
    *   変更前: `(ADDQ x (MOVQconst [c])) -> (ADDQconst [c] x)`
    *   変更後: `(ADDQ x (MOVQconst [c])) && is32Bit(c) -> (ADDQconst [c] x)`
    *   同様に`MULQ`のルールも`is32Bit(c)`を使用するように変更されました。
3.  **`rewriteAMD64.go`の更新**: `rewriteValueAMD64`関数内の`OpAMD64ADDQ`および`OpAMD64MULQ`のケースにおいて、定数畳み込みを行う前に`is32Bit(c)`によるチェックが追加されました。これにより、ルールファイルだけでなく、コード生成の段階でも同様のチェックが強制されます。
4.  **テストケースの追加**: `src/cmd/compile/internal/gc/testdata/arith_ssa.go`という新しいテストファイルが追加され、64ビット定数を含む加算と乗算のケースがテストされるようになりました。これにより、将来的に同様の回帰バグが発生しないように保護されます。

これらの変更により、コンパイラは32ビットを超える定数を含む加算や乗算を、定数オペランドを持つ特定の命令に畳み込もうとせず、より汎用的な命令シーケンス（例えば、定数をレジスタにロードしてから演算を行うなど）を生成するようになります。これにより、`doasm`の失敗や`LEA`命令での誤った値の計算が回避されます。

## コアとなるコードの変更箇所

- `TestArithmetic`という新しいテスト関数が追加され、`arith_ssa.go`を実行するように変更されました。

### `src/cmd/compile/internal/gc/testdata/arith_ssa.go` (新規ファイル)
- 64ビット定数を含む乗算と加算のテストケースが追加されました。
- `test64BitConstMult`と`test64BitConstAdd`関数が、それぞれ`test64BitConstMult_ssa`と`test64BitConstAdd_ssa`のSSAバックエンドでの結果を検証します。
- 非常に大きな64ビット定数（例: `34359738369`）が使用されており、これが以前の問題を再現するためのキーとなります。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules`
- `ADDQ`および`MULQ`の定数畳み込みルールに、`is32Bit(c)`という条件が追加されました。
  - 変更前: `(ADDQ x (MOVQconst [c])) -> (ADDQconst [c] x)`
  - 変更後: `(ADDQ x (MOVQconst [c])) && is32Bit(c) -> (ADDQconst [c] x)`
  - `MULQ`のルールも同様に`is32Bit(c)`条件が追加されました。

### `src/cmd/compile/internal/ssa/rewrite.go`
- `is32Bit(n int64) bool`関数が追加されました。
  ```go
  // is32Bit reports whether n can be represented as a signed 32 bit integer.
  func is32Bit(n int64) bool {
  	return n == int64(int32(n))
  }
  ```

### `src/cmd/compile/internal/ssa/rewriteAMD64.go`
- `rewriteValueAMD64`関数内の`OpAMD64ADDQ`および`OpAMD64MULQ`のケースで、定数`c`が`MOVQconst`から取得された後、`is32Bit(c)`によるチェックが追加されました。このチェックが失敗した場合、定数畳み込みは行われず、元の命令シーケンスが維持されます。

## コアとなるコードの解説

このコミットの主要な変更は、GoコンパイラのSSAバックエンドがAMD64アーキテクチャ向けにコードを生成する際の、定数畳み込みのロジックにあります。

1.  **`is32Bit`関数の導入**:
    `is32Bit`関数は、64ビット整数`n`が32ビット符号付き整数の範囲内にあるかどうかを判定します。`int32(n)`とキャストすることで、`n`が32ビットに収まらない場合は上位ビットが切り捨てられます。その結果を再度`int64`にキャストし、元の`n`と比較することで、切り捨てが発生したかどうか、つまり`n`が32ビット符号付き整数の範囲を超えていたかどうかを検出します。この関数は、定数畳み込みの安全性を確保するための重要なガードとなります。

2.  **`AMD64.rules`の変更**:
    `AMD64.rules`は、SSA中間表現のパターンマッチングと書き換えルールを定義するファイルです。以前は、`ADDQ`や`MULQ`といった演算で`MOVQconst`（64ビット定数）が使われている場合、無条件に`ADDQconst`や`MULQconst`といった定数オペランドを持つ命令に変換しようとすることがありました。しかし、これらの命令の定数オペランドは通常32ビットに制限されています。
    新しいルールでは、`&& is32Bit(c)`という条件が追加されました。これにより、定数`c`が32ビット符号付き整数の範囲内に収まる場合にのみ、この定数畳み込み最適化が適用されるようになります。範囲外の定数に対しては、このルールはマッチせず、コンパイラは別の（より汎用的な）方法でコードを生成します。

3.  **`rewriteAMD64.go`の変更**:
    `rewriteAMD64.go`ファイルには、`AMD64.rules`で定義されたルールがGoコードとして実装されています。`rewriteValueAMD64`関数は、SSA値（中間表現のノード）を走査し、最適化ルールを適用します。
    `OpAMD64ADDQ`や`OpAMD64MULQ`のケースでは、`MOVQconst`から取得した定数`c`に対して、明示的に`is32Bit(c)`チェックが追加されました。このチェックが`false`を返した場合、`goto`文によって現在の最適化パスをスキップし、より汎用的なコード生成パスに進みます。これにより、ルールファイルとコード生成ロジックの両方で、32ビット定数に限定した畳み込みが徹底されます。

これらの変更により、Goコンパイラは、AMD64アーキテクチャの命令セットの制約を尊重しつつ、安全かつ正確な定数畳み込み最適化を実行できるようになりました。特に、大きな64ビット定数を扱う際のコンパイルエラーや実行時エラーが解消され、コンパイラの堅牢性が向上しました。

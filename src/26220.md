## 元コミット内容

`crypto/x509: handle ECC private keys with the wrong length.`

SEC-1標準では、「privateKeyコンポーネントは、曲線次数nの対数（底2）を8で割った値の床関数（⌊log₂(n)/8⌋）の長さのオクテット文字列として定義される」と規定されています。

以前のコードでは、ECC秘密鍵のパース時に、秘密鍵が長すぎる場合にパニック（非amd64環境で）を引き起こしていました。また、短すぎる秘密鍵を `crypto/elliptic` に渡すことで、望ましくない動作を引き起こす可能性がありました。

この変更により、パース関数は、GnuTLSが過剰なパディングを行い、OpenSSLが（特定のコミットまで）不足したパディングを行っていたため、過剰なパディングと不足したパディングの両方を処理できるようになります。また、シリアライズ時にも秘密鍵が正しくパディングされるようになります。

Issue #13699 を修正します。

## 変更の背景

楕円曲線暗号 (ECC) の秘密鍵は、通常、特定の数学的構造を持つ整数として表現されます。この整数は、バイナリ形式（オクテット文字列）でエンコードされる際に、特定の長さにパディングされることが標準で定められています。この標準は、Standards for Efficient Cryptography 1 (SEC-1) によって規定されています。

しかし、異なる暗号ライブラリの実装（例えばGnuTLSや古いバージョンのOpenSSL）では、このパディング規則が厳密に守られていないケースがありました。具体的には、秘密鍵のオクテット文字列がSEC-1で定められた長さよりも長すぎたり（過剰なゼロパディング）、短すぎたり（ゼロパディングの不足）することがありました。

Go言語の `crypto/x509` パッケージは、以前はこのような非標準的なパディングを持つ秘密鍵に対して堅牢ではありませんでした。長すぎる秘密鍵をパースしようとすると、特に非amd64アーキテクチャでパニックを引き起こす可能性がありました。また、短すぎる秘密鍵を `crypto/elliptic` パッケージに渡すと、暗号演算が正しく行われないなど、予期せぬ動作につながる恐れがありました。

このコミットは、このような相互運用性の問題を解決し、Goの `crypto/x509` がより広範なECC秘密鍵の形式に対応できるようにすることを目的としています。これにより、他のシステムで生成された鍵をGoアプリケーションで安全に利用できるようになります。

## 前提知識の解説

### 楕円曲線暗号 (ECC)

楕円曲線暗号 (Elliptic Curve Cryptography, ECC) は、公開鍵暗号の一種で、有限体上の楕円曲線の数学を利用しています。RSAなどの他の公開鍵暗号方式と比較して、同等のセキュリティレベルをより短い鍵長で実現できるため、リソースが限られた環境（スマートカード、モバイルデバイスなど）や、効率が求められるTLS/SSL通信などで広く利用されています。

ECCの鍵ペアは、以下の要素で構成されます。
*   **秘密鍵 (Private Key)**: 楕円曲線上のスカラー値（整数）`d` です。これはランダムに選択されます。
*   **公開鍵 (Public Key)**: 楕円曲線上の点 `Q` で、`Q = d * G` として計算されます。ここで `G` は楕円曲線のベースポイント（生成点）です。

### SEC-1標準

SEC-1 (Standards for Efficient Cryptography 1) は、Certicom社によって策定された、楕円曲線暗号に関する一連の標準仕様です。ECCのアルゴリズム、鍵の生成、署名、鍵交換プロトコル、そして鍵のエンコーディング形式などを定義しています。

このコミットで特に重要なのは、SEC-1がECC秘密鍵のバイナリ表現（オクテット文字列）の長さを厳密に規定している点です。秘密鍵 `d` は、曲線の位数 `n` に基づいて、`⌊log₂(n)/8⌋` オクテットの長さを持つオクテット文字列として表現されるべきだとされています。この長さは、秘密鍵の値を表現するために必要な最小限のバイト数であり、通常は先頭にゼロパディングが施されてこの長さに調整されます。

### ASN.1 DERエンコーディング

ASN.1 (Abstract Syntax Notation One) は、データ構造を記述するための標準的な記法であり、DER (Distinguished Encoding Rules) はASN.1で記述されたデータ構造をバイト列にエンコードするための規則の一つです。暗号技術では、証明書 (X.509)、秘密鍵、公開鍵などの構造化されたデータを交換するためにASN.1 DERが広く用いられます。

ECC秘密鍵は、通常、SEC-1で定義された `ECPrivateKey` 構造体としてASN.1 DERエンコードされます。この構造体には、バージョン、秘密鍵のオクテット文字列、使用する楕円曲線の識別子（OID）、およびオプションで公開鍵が含まれます。

### 秘密鍵のパディング

秘密鍵は数学的には整数ですが、コンピュータシステムで扱う際にはバイト列として表現されます。SEC-1標準では、このバイト列の長さを曲線の位数 `n` に基づいて固定長にすることを求めています。例えば、256ビットの秘密鍵であれば32バイト（256/8）です。

*   **過剰なゼロパディング**: 秘密鍵の実際の値が表現に必要なバイト数よりも少ない場合、先頭にゼロを追加して規定の長さに合わせます。しかし、一部のライブラリは、必要以上に多くのゼロを先頭に追加してしまうことがあります。
*   **不足したゼロパディング**: 逆に、秘密鍵の実際の値が表現に必要なバイト数よりも少ないにもかかわらず、先頭のゼロが省略されてしまい、規定の長さよりも短いバイト列としてエンコードされることがあります。

これらの非標準的なパディングは、厳密なパーサーにとってはエラーの原因となります。

## 技術的詳細

このコミットは、Goの `crypto/x509` パッケージがECC秘密鍵のパースとシリアライズにおいて、SEC-1標準に準拠しないパディングを許容し、同時に標準に準拠した形式で出力できるようにするものです。

### シリアライズ (`MarshalECPrivateKey` 関数)

以前の `MarshalECPrivateKey` 関数は、秘密鍵の整数値 `key.D` を直接バイト列に変換していました (`key.D.Bytes()`)。このメソッドは、先頭のゼロを省略して最小限のバイト数で表現するため、SEC-1が要求する固定長パディングが適用されませんでした。

変更後、`MarshalECPrivateKey` は以下の手順で秘密鍵をパディングします。
1.  `key.D.Bytes()` で秘密鍵のバイト列を取得します。
2.  `key.Curve.Params().N.BitLen()` を使用して、曲線の位数 `N` のビット長を取得し、そこからSEC-1で要求されるオクテット文字列の長さを計算します (`(BitLen + 7) / 8`)。
3.  この計算された長さの新しいバイトスライス `paddedPrivateKey` を作成します。
4.  `copy(paddedPrivateKey[len(paddedPrivateKey) - len(privateKeyBytes):], privateKeyBytes)` を使用して、取得した秘密鍵のバイト列を `paddedPrivateKey` の末尾にコピーします。これにより、先頭に必要な数のゼロが自動的にパディングされ、SEC-1標準に準拠した固定長になります。

### パース (`parseECPrivateKey` 関数)

以前の `parseECPrivateKey` 関数は、入力された秘密鍵のバイト列 `privKey.PrivateKey` をそのまま `big.Int` に変換し、その後に `curve.ScalarBaseMult` に渡していました。この際、秘密鍵の長さが曲線の位数 `N` の範囲内であるかどうかのチェックは行われていましたが、パディングの不一致は適切に処理されていませんでした。

変更後、`parseECPrivateKey` は以下の手順で非標準的なパディングを処理します。
1.  まず、入力された秘密鍵のバイト列 `privKey.PrivateKey` を `big.Int` に変換し、曲線の位数 `curveOrder` と比較して、秘密鍵の値が有効な範囲内にあるかを確認します。
2.  SEC-1で要求される正しい秘密鍵のオクテット文字列長を `(curveOrder.BitLen() + 7) / 8` で計算し、その長さの新しいバイトスライス `privateKey` を作成します。
3.  **過剰なゼロパディングの処理**:
    `for len(privKey.PrivateKey) > len(privateKey)` ループが追加されました。これは、入力された秘密鍵のバイト列がSEC-1で要求される長さよりも長い場合に実行されます。このループは、先頭のバイトがゼロである限り、そのゼロをスキップして `privKey.PrivateKey` を短くします。もし先頭のバイトがゼロでなければ、それは不正な長さであると判断し、エラーを返します。これにより、GnuTLSのような過剰なゼロパディングを許容します。
4.  **不足したゼロパディングの処理**:
    `copy(privateKey[len(privateKey) - len(privKey.PrivateKey):], privKey.PrivateKey)` が実行されます。これは、過剰なゼロが取り除かれた後の `privKey.PrivateKey`（または元々過剰なゼロがなかった場合）を、正しい長さの `privateKey` スライスの末尾にコピーします。これにより、もし `privKey.PrivateKey` が短すぎる場合（先頭のゼロが不足している場合）、`privateKey` スライスの先頭に自動的にゼロが埋められ、正しい長さに正規化されます。これは、古いOpenSSLのような不足したゼロパディングを許容します。
5.  最終的に、正規化された `privateKey` スライスが `curve.ScalarBaseMult` に渡され、公開鍵の計算に使用されます。

これらの変更により、Goの `crypto/x509` は、SEC-1標準に厳密に準拠しないが、広く使われている他の暗号ライブラリによって生成されたECC秘密鍵も、エラーなく安全に処理できるようになります。

## コアとなるコードの変更箇所

### `src/crypto/x509/sec1.go`

*   **`MarshalECPrivateKey` 関数**:
    ```go
    	privateKeyBytes := key.D.Bytes()
    	paddedPrivateKey := make([]byte, (key.Curve.Params().N.BitLen() + 7) / 8)
    	copy(paddedPrivateKey[len(paddedPrivateKey) - len(privateKeyBytes):], privateKeyBytes)

    	return asn1.Marshal(ecPrivateKey{
    		Version:       1,
    		PrivateKey:    paddedPrivateKey, // 変更点: paddedPrivateKey を使用
    		NamedCurveOID: oid,
    		PublicKey:     asn1.BitString{Bytes: elliptic.Marshal(key.Curve, key.X, key.Y)},
    	})
    ```
*   **`parseECPrivateKey` 関数**:
    ```go
    	k := new(big.Int).SetBytes(privKey.PrivateKey)
    	curveOrder := curve.Params().N // 変更点: curveOrder 変数を導入
    	if k.Cmp(curveOrder) >= 0 {
    		return nil, errors.New("x509: invalid elliptic curve private key value")
    	}
    	priv := new(ecdsa.PrivateKey)
    	priv.Curve = curve
    	priv.D = k

    	privateKey := make([]byte, (curveOrder.BitLen() + 7) / 8) // 変更点: 正しい長さの privateKey スライスを作成

    	// Some private keys have leading zero padding. This is invalid
    	// according to [SEC1], but this code will ignore it.
    	for len(privKey.PrivateKey) > len(privateKey) { // 変更点: 過剰なゼロパディングを処理するループ
    		if privKey.PrivateKey[0] != 0 {
    			return nil, errors.New("x509: invalid private key length")
    		}
    		privKey.PrivateKey = privKey.PrivateKey[1:]
    	}

    	// Some private keys remove all leading zeros, this is also invalid
    	// according to [SEC1] but since OpenSSL used to do this, we ignore
    	// this too.
    	copy(privateKey[len(privateKey) - len(privKey.PrivateKey):], privKey.PrivateKey) // 変更点: 不足したゼロパディングを処理し、正規化
    	priv.X, priv.Y = curve.ScalarBaseMult(privateKey) // 変更点: 正規化された privateKey を使用
    ```

## コアとなるコードの解説

### `MarshalECPrivateKey` の変更

`MarshalECPrivateKey` 関数では、`key.D.Bytes()` が返す秘密鍵のバイト列が、曲線の位数 `N` に基づく正しい長さになるように、明示的にゼロパディングを行うようになりました。
1.  `privateKeyBytes := key.D.Bytes()`: `ecdsa.PrivateKey` 構造体の `D` フィールド（秘密鍵の整数値）をバイト列に変換します。このバイト列は、先頭のゼロが省略されている可能性があります。
2.  `paddedPrivateKey := make([]byte, (key.Curve.Params().N.BitLen() + 7) / 8)`: 秘密鍵を格納すべき正しい長さのバイトスライス `paddedPrivateKey` を作成します。`key.Curve.Params().N.BitLen()` は曲線の位数 `N` のビット長を返し、`(BitLen + 7) / 8` はそれをバイト長に変換する一般的な方法です（例: 256ビットなら32バイト）。
3.  `copy(paddedPrivateKey[len(paddedPrivateKey) - len(privateKeyBytes):], privateKeyBytes)`: `privateKeyBytes` を `paddedPrivateKey` の末尾にコピーします。これにより、`paddedPrivateKey` の先頭には自動的にゼロが埋められ、SEC-1標準で要求される固定長が保証されます。

この変更により、GoによってシリアライズされたECC秘密鍵は常に正しいパディングを持つようになり、他の厳密な実装との相互運用性が向上します。

### `parseECPrivateKey` の変更

`parseECPrivateKey` 関数では、入力された秘密鍵のバイト列がSEC-1標準に準拠していなくても、それを正規化して処理するロジックが追加されました。
1.  `curveOrder := curve.Params().N`: 曲線の位数 `N` を取得し、`curveOrder` 変数に格納します。これは、秘密鍵の有効性チェックと、正しいパディング長の計算に使用されます。
2.  `privateKey := make([]byte, (curveOrder.BitLen() + 7) / 8)`: シリアライズ時と同様に、SEC-1で要求される正しい長さのバイトスライス `privateKey` を作成します。このスライスが、最終的に `curve.ScalarBaseMult` に渡される正規化された秘密鍵のバイト列を保持します。
3.  **過剰なゼロパディングの処理**:
    `for len(privKey.PrivateKey) > len(privateKey)` ループは、入力された `privKey.PrivateKey` が正しい長さ `len(privateKey)` よりも長い場合に実行されます。このループは、`privKey.PrivateKey` の先頭バイトがゼロである限り、そのゼロを削除してスライスを短くします (`privKey.PrivateKey = privKey.PrivateKey[1:]`)。もし先頭バイトがゼロでなければ、それは不正なデータであるため、エラーを返します。これにより、GnuTLSのような過剰なゼロパディングを許容し、秘密鍵の実際の値に影響を与えずに長さを調整します。
4.  **不足したゼロパディングの処理**:
    `copy(privateKey[len(privateKey) - len(privKey.PrivateKey):], privKey.PrivateKey)` は、過剰なゼロが取り除かれた後の `privKey.PrivateKey` を、正しい長さの `privateKey` スライスの末尾にコピーします。もし `privKey.PrivateKey` がまだ `privateKey` よりも短い場合、`privateKey` の先頭には自動的にゼロが埋められます。これは、古いOpenSSLのように先頭のゼロが不足しているケースを補正し、秘密鍵を正規化された固定長にします。
5.  `priv.X, priv.Y = curve.ScalarBaseMult(privateKey)`: 最終的に、この正規化された `privateKey` スライスが `curve.ScalarBaseMult` 関数に渡され、公開鍵の計算が行われます。これにより、`crypto/elliptic` パッケージには常に正しい長さの秘密鍵が渡されることが保証されます。

これらの変更により、Goの `crypto/x509` は、SEC-1標準のパディング規則に多少逸脱した形式のECC秘密鍵に対しても、より堅牢で寛容なパーサーとなります。

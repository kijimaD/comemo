## 変更の背景

このコミットは、Goの標準テストパッケージ`testing`において、サブテスト（`T.Run`）の動作に影響を与えるバグを修正するために行われました。コミットメッセージによると、このバグは以前の変更である「CL 21504」によって導入され、特に`T.Run`の機能が正しく動作しなくなる原因となっていました。

具体的には、`go test -v`フラグを使用して詳細なテスト出力を表示する「chatty」モードにおいて、ネストされたサブテストの実行状況が正しく報告されない問題が発生していました。これは、テストの階層構造において、最上位のテスト（ルートテスト）のコンテキストを特定するロジックに誤りがあったためです。結果として、サブテストの開始（`=== RUN`）や終了（`--- PASS`/`--- FAIL`）のメッセージが適切に出力されず、テストのデバッグや進捗状況の把握が困難になるという影響がありました。

この修正は、`testing`パッケージの安定性と信頼性を確保し、開発者がサブテストを効果的に利用できるようにするために不可欠でした。

## 前提知識の解説

このコミットの理解を深めるために、以下のGoの`testing`パッケージに関する前提知識が必要です。

*   **Goの`testing`パッケージ**: Go言語に組み込まれている標準のテストフレームワークです。`go test`コマンドを通じて利用され、ユニットテスト、ベンチマークテスト、例（Example）テストなどを記述するための機能を提供します。
*   **`*testing.T`と`*testing.B`**:
    *   `*testing.T`: テスト関数（`func TestXxx(t *testing.T)`）に渡される構造体です。テストの失敗を報告する`t.Error`や`t.Fail`、テストをスキップする`t.Skip`、サブテストを実行する`t.Run`など、テストの実行を制御するための様々なメソッドを提供します。
    *   `*testing.B`: ベンチマーク関数（`func BenchmarkXxx(b *testing.B)`）に渡される構造体です。ベンチマークの実行回数を制御する`b.N`や、サブベンチマークを実行する`b.Run`などのメソッドを提供します。
*   **`T.Run` (サブテスト)**: `*testing.T`構造体のメソッドで、テスト関数内でさらに小さなテストケース（サブテスト）を定義し、実行するために使用されます。
    ```go
    func TestSomething(t *testing.T) {
        t.Run("SubtestA", func(t *testing.T) {
            // Subtest A のロジック
        })
        t.Run("SubtestB", func(t.T) {
            // Subtest B のロジック
        })
    }
    ```
    `T.Run`を使用することで、テストを論理的にグループ化し、個別に実行・管理できます。また、サブテストは並列実行することも可能です。
*   **テストの階層構造**: `T.Run`をネストして使用することで、テストは親と子の階層構造を持つことができます。例えば、`TestParent`の中に`TestChild`があり、さらにその中に`TestGrandchild`がある、といった形です。各サブテストは親テストのコンテキストを継承します。
*   **`chatty`モード (`go test -v`)**: `go test`コマンドに`-v`（verbose）フラグを付けて実行すると、テストの詳細な実行状況が出力されます。この詳細出力モードを`chatty`モードと呼びます。`=== RUN`はテストの開始を、`--- PASS`や`--- FAIL`はテストの終了と結果を示します。このモードでは、テストの階層構造がインデントされて表示され、どのテストが実行されているかを視覚的に把握しやすくなります。
*   **`root`テストコンテキスト**: テストの階層構造において、最も上位に位置するテストを指します。`chatty`モードでの出力は、通常、このルートテストコンテキストに関連付けられた`io.Writer`を通じて行われます。これにより、すべてのテスト出力が一貫した方法で処理されます。

## 技術的詳細

このコミットの技術的な核心は、`testing`パッケージ内部で`T.Run`が詳細出力（`chatty`モード）を行う際に、テスト階層の最上位にあるルートテストコンテキストを正しく特定するロジックの修正にあります。

バグが発生していたのは、`*testing.T`の`Run`メソッド内で、`chatty`モード時に出力を行うための`io.Writer`を取得する部分でした。この処理では、現在のテスト`t`からその親を遡っていき、最終的に`parent`が`nil`となるルートテストを見つけ出す必要があります。

元のコードは以下のようになっていました。

```go
// 変更前
root := t.parent
for ; root.parent != nil; root = t.parent {
    // ...
}
```

このループの`root = t.parent`という部分が問題でした。
1.  `root := t.parent`で、`root`は現在のテスト`t`の直接の親で初期化されます。
2.  ループ条件`root.parent != nil`が真である限り、ループが続行されます。
3.  ループの更新部分`root = t.parent`では、**常に現在のテスト`t`の直接の親を`root`に再代入**していました。

この誤った代入により、`root`変数はループの各イテレーションで、現在のテスト`t`の直接の親から先に進むことができませんでした。もし`t`がルートテストの直接の子である場合、`root`は常にその親を指し続け、`root.parent != nil`が真である限り無限ループに陥るか、あるいは`root`がルートテストに到達する前にループが終了してしまう可能性がありました。結果として、`fmt.Fprintf(root.w, ...)`が正しい`root.w`（ルートテストの`io.Writer`）に対して行われず、詳細出力が欠落したり、誤った場所に出力されたりする原因となっていました。

修正後のコードは以下の通りです。

```go
// 変更後
root := t.parent
for ; root.parent != nil; root = root.parent {
    // ...
}
```

この修正では、ループの更新部分が`root = root.parent`に変更されています。
1.  `root := t.parent`で、`root`は現在のテスト`t`の直接の親で初期化されます。
2.  ループ条件`root.parent != nil`が真である限り、ループが続行されます。
3.  ループの更新部分`root = root.parent`では、**現在の`root`変数の親を`root`に代入**します。

これにより、`root`変数はループの各イテレーションで、テスト階層を一段ずつ正しく上に遡っていきます。最終的に`root.parent`が`nil`となる最上位のテスト（ルートテスト）に到達し、ループが終了します。この結果、`fmt.Fprintf(root.w, ...)`は常に正しいルートテストの`io.Writer`に対して行われるようになり、`chatty`モードでのサブテスト出力が期待通りに機能するようになりました。

`src/testing/sub_test.go`に追加されたテストケースは、この修正がネストされたサブテストと`chatty`モードの組み合わせで正しく機能することを検証するためのものです。特に「chatty with recursion」というテストケースは、再帰的に定義されたサブテストの出力が正しく表示されることを確認しています。

この変更は、`*testing.T`の`Run`メソッド内で、詳細出力（`chatty`モード）時にテストの実行メッセージ（`=== RUN`など）を書き込むための`io.Writer`を決定するロジックを修正しています。

*   **変更前 (`root = t.parent`)**: ループの各イテレーションで、`root`変数が常に現在のテスト`t`の直接の親にリセットされていました。これにより、`root`がテスト階層を正しく遡ることができず、最上位のルートテストに到達できませんでした。結果として、`fmt.Fprintf`が誤った`io.Writer`に対して出力しようとするか、無限ループに陥る可能性がありました。
*   **変更後 (`root = root.parent`)**: ループの各イテレーションで、`root`変数が自身の親に更新されるようになりました。これにより、`root`はテスト階層を一段ずつ確実に上に移動し、最終的に`parent`が`nil`となる最上位のルートテストに到達します。このルートテストの`io.Writer` (`root.w`) を使用することで、すべてのサブテストの出力が正しく集約され、`go test -v`実行時に期待される階層的な詳細出力が実現されます。

この一行の変更は、テストの出力メカニズムにおける根本的な問題を解決し、`T.Run`の信頼性を向上させました。

### `src/testing/sub_test.go` の変更

このファイルでは、`TestTRun`と`TestBRun`という既存のテスト関数に、新しいテストケースが追加されています。これらのテストケースは、修正されたロジックが正しく機能することを検証するためのものです。

```go
// TestTRun に追加されたテストケースの一部
	}, {
		desc:   "chatty with recursion",
		ok:     true,
		chatty: true,
		output: `
=== RUN   chatty with recursion
```

*   **`output`**: 期待される出力のパターンを定義しています。`=== RUN`メッセージがネストされたサブテストごとに正しく表示され、適切なインデントが適用されていることが示されています。これは、修正されたルートテストコンテキストの特定ロジックが正しく機能していることの証拠となります。

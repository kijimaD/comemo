# [インデックス 25708] ファイルの概要

このコミットは、Goコンパイラの新しいパーサーにおけるEOF (End-Of-File) の扱いに関するバグ修正を目的としています。具体的には、パーサーがファイルの終端を適切に処理せず、予期せぬEOFが発生した場合にエラーを報告しない問題を解決します。これにより、不完全なGoソースコードがコンパイル時に誤って受け入れられる可能性が排除され、コンパイラの堅牢性が向上します。

## 変更の背景

このコミットは、Goコンパイラの新しいパーサーがファイルの終端 (EOF) を適切に扱わないという問題に対処するために行われました。具体的には、パーサーが特定の状況下でEOFトークンを無視し、構文エラーを報告すべき場所で報告しないことがありました。これにより、開発者が意図しない不完全なコードを記述した場合でも、コンパイラがそれをエラーとして検出できないという問題が発生していました。

コミットメッセージに記載されている `#13274` および `#13272` は、このEOF処理の不備に関連するバグトラッキングシステム上の課題を指していると考えられます。公開されているGoのissueトラッカーではこれらの番号に直接対応する情報は見つかりませんでしたが、変更内容とテストケースから、パーサーがファイルの終端に到達した際に、期待されるトークンが存在しない場合に適切にエラーを発生させるように修正されたことが読み取れます。特に、`issue13274.go` というテストファイルが追加されていることから、この問題が具体的なコードパターンで再現可能であったことが示唆されます。

この修正により、Goコンパイラはより厳密に構文をチェックし、開発者が記述したコードの品質と正確性を保証する上で重要な役割を果たします。

## 前提知識の解説

### Goコンパイラ (`cmd/compile/internal/gc`)

Go言語の公式コンパイラは、`cmd/compile` ディレクトリ以下に存在します。その中でも `internal/gc` は、Go言語のソースコードを中間表現に変換し、最終的に機械語コードを生成する主要な部分を担っています。このコンパイラは、字句解析 (lexing)、構文解析 (parsing)、型チェック (type checking)、最適化 (optimization)、コード生成 (code generation) といった複数のフェーズで構成されています。

### パーサー (Parser)

パーサーは、字句解析器 (lexer) によって生成されたトークンストリームを受け取り、Go言語の文法規則に従って構文木 (Abstract Syntax Tree: AST) を構築する役割を担います。このプロセス中に、文法的に誤ったコードが検出された場合、パーサーは構文エラーを報告します。

### トークン (Token)

トークンは、ソースコードを構成する最小の意味のある単位です。例えば、キーワード (`func`, `var`, `package`)、識別子 (`main`, `myVar`)、演算子 (`+`, `=`)、リテラル (`123`, `"hello"`)、そして特殊な記号 (`(`, `{`, `;`) などがあります。EOF (End-Of-File) もまた、ファイルの終端を示す特殊なトークンとして扱われます。

### EOF (End-Of-File)

EOFは、入力ストリームやファイルの終端を示すマーカーです。プログラミング言語のパーサーにとって、EOFは非常に重要なトークンであり、ファイルの終端に到達した際に、それまでに解析されたコードが完全な構文を形成しているかを判断するために使用されます。例えば、ブロックが閉じられていない状態でEOFに到達した場合、それは構文エラーとなります。

### `parser.go`

`src/cmd/compile/internal/gc/parser.go` は、Goコンパイラの構文解析器の実装が含まれるファイルです。このファイルには、Go言語の文法規則に基づいてトークンを解析し、構文木を構築するためのロジックが記述されています。

### `parser` 構造体と `want`, `got` メソッド

`parser` 構造体は、構文解析の状態を管理します。`want` メソッドと `got` メソッドは、パーサーが特定のトークンを期待し、それが実際に存在するかどうかをチェックするためのヘルパー関数です。

*   `got(tok int32) bool`: 現在のトークンが `tok` と一致するかどうかをチェックし、一致すれば次のトークンに進みます。
*   `want(tok int32)`: 現在のトークンが `tok` と一致することを期待します。一致しない場合は構文エラーを報告し、次の有効なトークンまでスキップしようとします (`p.advance()`)。

## 技術的詳細

このコミットの核心は、`parser.go` 内の `want` メソッドの挙動と、ファイルの終端 (`file()` メソッドの最後) でEOFトークンを明示的にチェックするロジックの追加にあります。

### `want` メソッドの変更

変更前の `want` メソッドは、`p.tok != EOF && !p.got(tok)` という条件でエラーチェックを行っていました。これは、「現在のトークンがEOFではなく、かつ期待するトークン (`tok`) が存在しない場合」にのみエラーを報告するという意味です。この条件の問題点は、**現在のトークンがEOFである場合、期待するトークンが存在しなくてもエラーを報告しない**という点です。

例えば、`var f = func() {` のように、関数リテラルのブロックが閉じられていない状態でファイルの終端に到達した場合、パーサーはEOFトークンを読み込みます。このとき、`want` メソッドは閉じ括弧 `}` を期待しますが、`p.tok != EOF` の条件が偽となるため、エラーを報告せずに処理を続行してしまいます。結果として、不完全なコードが構文エラーとして検出されないという問題が発生していました。

このコミットでは、`want` メソッドの条件が `!p.got(tok)` に変更されました。これにより、「期待するトークン (`tok`) が存在しない場合」は、現在のトークンがEOFであっても常にエラーが報告されるようになります。これは、パーサーがファイルの終端に到達した際に、未完了の構文要素があれば必ずエラーを出すべきであるという、より厳密な構文チェックの原則に合致します。

### `file()` メソッドへの `p.want(EOF)` の追加

`file()` メソッドは、Goソースファイル全体の解析を担当します。変更前は、ファイルのすべての宣言を解析した後、明示的にEOFをチェックするロジックがありませんでした。これは、`want` メソッドの変更と合わせて、不完全なファイルが誤って受け入れられる原因となっていました。

このコミットでは、`file()` メソッドの最後に `p.want(EOF)` が追加されました。これは、ファイルのすべての内容が解析された後、パーサーが必ずEOFトークンを期待することを意味します。もしファイルの終端に到達した時点で、まだ解析されていないトークンが残っていたり、構文的に不完全な状態であったりした場合、`p.want(EOF)` はエラーを発生させます。これにより、パーサーはファイルの終端まで完全に解析が行われたことを保証し、不完全なソースコードに対する堅牢なエラー検出を提供します。

### `test/fixedbugs/issue13274.go` の追加

このテストファイルは、`var f = func() {` のように、関数リテラルのブロックが閉じられていない状態でEOFに到達した場合に、コンパイラが「unexpected EOF」エラーを正しく報告することを確認します。これは、上記の `want` メソッドの修正と `p.want(EOF)` の追加によって解決される具体的なシナリオを検証するものです。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/parser.go` の変更

1.  **`func (p *parser) want(tok int32)` メソッドの変更**:
    ```diff
    -	if p.tok != EOF && !p.got(tok) {
    +	if !p.got(tok) {
    ```
    この変更は、`want` メソッドが構文エラーを報告する条件を修正します。
    *   **変更前**: `p.tok != EOF && !p.got(tok)`
        *   「現在のトークンがEOFではなく、かつ期待するトークン `tok` が存在しない場合」にエラーを報告していました。
        *   これにより、現在のトークンがEOFである場合、期待するトークンがなくてもエラーが報告されませんでした。
    *   **変更後**: `!p.got(tok)`
        *   「期待するトークン `tok` が存在しない場合」に常にエラーを報告するようになりました。
        *   これにより、ファイルの終端 (EOF) で期待するトークンが見つからない場合でも、適切に構文エラー (`p.syntax_error("")`) が発生するようになります。これは、不完全なコードに対するコンパイラの検出能力を向上させます。

2.  **`func (p *parser) file()` メソッドへの追加**:
    ```diff
    	xtop = concat(xtop, p.xdcl_list())
    +
    +	p.want(EOF)
    }
    ```
    `file()` メソッドは、Goソースファイル全体の解析を完了した後に呼び出されます。
    *   `p.want(EOF)` の追加により、ファイルのすべての宣言が解析された後、パーサーは明示的にEOFトークンが存在することを期待するようになります。
    *   もしこの時点でEOF以外のトークンが残っていたり、ファイルの終端に到達していないにもかかわらず、構文的に不完全な状態であったりした場合、`want` メソッドの修正と相まって、ここで「unexpected EOF」などの適切な構文エラーが報告されるようになります。これにより、ソースファイルが完全に解析され、文法的に正しい形で閉じられていることが保証されます。

## 変更の背景

Go言語のランタイムは、その初期段階において、パフォーマンスとOSとの密接な連携のためにC言語（またはPlan 9 C）で書かれた部分が多く存在しました。しかし、Goプロジェクトは、ランタイムの大部分をGo言語自体で記述するという長期的な目標を掲げていました。この目標にはいくつかの重要な理由があります。

1.  **保守性の向上**: Go言語で書かれたコードは、Go開発者にとってより理解しやすく、デバッグやメンテナンスが容易になります。C言語とGo言語が混在するコードベースは、開発の複雑さを増します。
2.  **クロスコンパイルの容易さ**: Goは優れたクロスコンパイル機能を持ちますが、Cgo（GoとCの相互運用）を使用する部分は、ターゲット環境のCコンパイラやCライブラリに依存するため、クロスコンパイルが複雑になる傾向があります。ランタイムをGoで書くことで、この依存関係を減らし、よりシームレスなクロスコンパイルを実現できます。
3.  **ガベージコレクタとの統合**: Goのガベージコレクタは、Goのメモリモデルと密接に連携するように設計されています。C言語で書かれたランタイムコードがGoのオブジェクトを直接操作する場合、ガベージコレクタがそのメモリを正しく追跡できないリスクがありました。ランタイムをGoで書くことで、ガベージコレクタの効率と正確性が向上します。
4.  **Goの型安全性と並行性の活用**: Go言語の持つ型安全性や並行処理のプリミティブをランタイム開発に活用することで、より堅牢で効率的なランタイムを構築できます。

このコミットは、NetBSD/386アーキテクチャに特化したランタイムコードをCからGoへ移行する、この大規模な取り組みの一部です。これにより、NetBSD/386上でのGoプログラムの実行環境が改善され、将来的な開発が容易になります。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の概念について基本的な知識が必要です。

-   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルなシステムです。これには、ゴルーチン（軽量スレッド）のスケジューリング、ガベージコレクション、メモリ管理、システムコールインターフェース、シグナルハンドリングなどが含まれます。Goプログラムは、OS上で直接実行されるのではなく、このランタイムを介してOSと対話します。

-   **Cgo**: Go言語とC言語のコードを相互運用するためのGoの機能です。Cgoを使用すると、GoプログラムからCライブラリの関数を呼び出したり、CコードからGo関数を呼び出したりできます。ランタイムのCからGoへの移行は、Cgoの依存関係を減らすことを目的としています。

-   **NetBSD/386**: NetBSDは、オープンソースのUNIX系オペレーティングシステムであり、高い移植性を特徴としています。`/386`は、Intel 80386プロセッサアーキテクチャ（32ビット）を指します。このコミットは、この特定のOSとアーキテクチャの組み合わせに特化したランタイムの変更です。

-   **システムコール (System Call)**: ユーザー空間で実行されるプログラムが、オペレーティングシステムカーネルが提供するサービス（ファイルI/O、メモリ割り当て、プロセス管理など）を要求するためのインターフェースです。Goランタイムは、OSと対話するためにシステムコールを頻繁に利用します。

-   **シグナルハンドリング (Signal Handling)**: オペレーティングシステムがプロセスに対して、特定のイベント（例えば、プログラムのエラー、外部からの割り込み、子プロセスの終了など）を非同期に通知するメカニズムです。プロセスは、特定のシグナルを受信したときに実行される「シグナルハンドラ」と呼ばれる関数を登録できます。Goランタイムは、プログラムのクラッシュや割り込みなどの重要なイベントを処理するためにシグナルハンドリングを多用します。

-   **`mcontext_t` および `ucontext_t`**: これらは、UNIX系システムにおけるシグナルハンドリング中にプロセスの実行コンテキスト（CPUレジスタの状態、スタックポインタ、プログラムカウンタなど）を保存および復元するために使用される構造体です。シグナルハンドラが実行される際、元の実行コンテキストが保存され、ハンドラ終了後に復元されることで、プログラムの実行が中断なく続行されます。

-   **`sigaltstack`**: シグナルハンドラが実行される際に使用される代替スタックを設定するためのシステムコールです。これは、通常のスタックが破損している場合（例えば、スタックオーバーフローが発生した場合）でもシグナルハンドラが安全に実行されることを保証するために重要です。

-   **`uintptr` と `*byte` / `uint32` (Go言語の型)**:
    -   `uintptr`: ポインタを保持できる符号なし整数型です。Goのコードで低レベルなメモリ操作やシステムコールインターフェースを扱う際に、ポインタ値を整数として扱う必要がある場合によく使用されます。`unsafe.Pointer`と組み合わせて、型安全性をバイパスして任意の型へのポインタを表現できます。
    -   `*byte`: バイトへのポインタです。
    -   `uint32`: 32ビットの符号なし整数型です。
    C言語ではポインタがしばしば整数型として扱われますが、Goでは型安全性のために厳密な型付けが行われます。このコミットでは、Cのポインタや整数型がGoの適切な型（特に`uintptr`）に変換されています。

## 技術的詳細

このコミットの核となる技術的変更は、NetBSD/386アーキテクチャにおけるGoランタイムのOSインタラクションおよびシグナルハンドリング部分をC言語からGo言語へ移植した点にあります。

1.  **C言語ファイルの削除とGo言語ファイルの追加**:
    -   `src/runtime/os_netbsd_386.c` が削除されました。このファイルは、NetBSD/386固有のOSレベルの操作（特に`lwp_mcontext_init`関数）をC言語で実装していました。
    -   `src/runtime/signal_netbsd_386.h` が削除されました。このヘッダファイルは、シグナルコンテキスト内のレジスタにアクセスするためのCプリプロセッサマクロ（`SIG_EAX`, `SIG_ESP`など）を定義していました。
    -   新たに `src/runtime/os1_netbsd_386.go` が追加されました。これは、削除されたCコードのGo言語による再実装を含みます。ファイル名に`1`が付いているのは、Goのビルドシステムが特定のOS/アーキテクチャに特化したランタイムファイルを識別するための慣習です。
    -   新たに `src/runtime/signal_netbsd_386.go` が追加されました。これは、削除されたCヘッダの機能（シグナルコンテキストからのレジスタアクセス）をGo言語の構造体とメソッドで提供します。

2.  **データ構造のGo言語への適応 (`src/runtime/defs1_netbsd_386.go` の変更)**:
    -   `sigaltstackt` および `stackt` 構造体において、スタックポインタを指す `ss_sp` フィールドの型が `*byte` から `uintptr` に変更されました。また、スタックサイズを示す `ss_size` フィールドも `uint32` から `uintptr` に変更されました。これは、Goランタイムが低レベルなメモリ操作を行う際に、より汎用的な`uintptr`型を使用するように統一されたことを示しています。`uintptr`はポインタを整数として扱うことができ、`unsafe.Pointer`と組み合わせて柔軟なポインタ演算を可能にします。
    -   `mcontextt` 構造体（マシンコンテキスト、CPUレジスタの状態を保持）の `__gregs` フィールド（汎用レジスタの配列）の型が `[19]int32` から `[19]uint32` に変更されました。これは、レジスタ値が符号なし整数として扱われるのが適切であるという認識に基づいています。
    -   `timespec` および `timeval` 構造体には、それぞれのフィールド（秒、ナノ秒、マイクロ秒）を設定するためのヘルパーメソッド（`set_sec`, `set_nsec`, `set_usec`）が追加されました。これは、C言語で直接構造体のフィールドに値を代入していた処理を、Goの慣用的なメソッド呼び出しに置き換えるための準備です。

3.  **`lwp_mcontext_init` のGo言語での再実装 (`src/runtime/os1_netbsd_386.go`)**:
    -   この関数は、新しい軽量プロセス（LWP）が開始される際に、その実行コンテキスト（特にCPUレジスタ）を初期化する役割を担います。
    -   C言語版では、`mc->__gregs[REG_EIP] = (uint32)runtime·lwp_tramp;` のように直接レジスタに値を代入していましたが、Go言語版では `mc.__gregs[_REG_EIP] = uint32(funcPC(lwp_tramp))` のように、Goの関数ポインタを`uint32`にキャストしてレジスタに設定しています。
    -   特に注目すべきは、`mp` (M構造体、マシンを表す) と `gp` (G構造体、ゴルーチンを表す) のポインタが、`uintptr(unsafe.Pointer(mp))` のように `unsafe.Pointer` を介して `uintptr` に変換され、レジスタに格納されている点です。これにより、新しいLWPが起動した際に、Goランタイムの重要なデータ構造（MとG）への参照がレジスタを通じて渡され、Goのスケジューラが正しく動作できるようになります。

4.  **シグナルコンテキストのGo言語での抽象化 (`src/runtime/signal_netbsd_386.go`)**:
    -   C言語のヘッダファイルで定義されていたレジスタアクセス用のマクロ（例: `SIG_EAX(info, ctxt)`）は、Go言語の `sigctxt` 構造体とそれに関連するメソッドに置き換えられました。
    -   `sigctxt` 構造体は、シグナルハンドラに渡されるコンテキスト情報（`siginfo`と`ucontextt`）をラップします。
    -   `regs()` メソッドは、`ucontextt` から `mcontextt` へのポインタを返します。
    -   `eax()`, `ebx()`, `eip()`, `esp()` などのメソッドは、`mcontextt` 構造体の `__gregs` 配列から特定のレジスタの値を読み出すためのGoの慣用的なインターフェースを提供します。
    -   同様に、`set_eip()`, `set_esp()` などのメソッドは、レジスタの値を設定するためのインターフェースを提供します。
    -   この変更により、シグナルハンドリングコードがよりGoらしく記述できるようになり、CgoのオーバーヘッドやC言語のポインタ操作に伴う潜在的なエラーが削減されます。

これらの変更は、GoランタイムのNetBSD/386ポートを、よりGo言語のイディオムに沿った形に進化させ、将来的なメンテナンスと機能拡張を容易にすることを目的としています。

## コアとなるコードの解説

このコミットのコアとなる変更は、NetBSD/386におけるGoランタイムの低レベルなOSインタラクションとシグナルハンドリングを、C言語からGo言語へ完全に移行した点にあります。

1.  **データ構造のGo言語への適応**:
    -   `src/runtime/defs1_netbsd_386.go` で行われた `ss_sp` や `ss_size` の型変更（`*byte` -> `uintptr`, `uint32` -> `uintptr`）は、GoランタイムがOSレベルのポインタやサイズ情報をより柔軟に、かつGoの型システム内で扱うためのものです。`uintptr`はポインタを整数として表現できるため、低レベルなアドレス計算やシステムコールへの引数渡しに適しています。
    -   `mcontextt` の `__gregs` が `[19]int32` から `[19]uint32` に変更されたのは、CPUレジスタの値が通常、符号なしのメモリ番地やフラグを表すため、より正確な型表現です。
    -   `timespec` と `timeval` に追加された `set_` メソッドは、C言語で直接構造体のフィールドに値を代入していた操作を、Goのメソッド呼び出しというより安全で慣用的な方法に置き換えるための準備です。これにより、GoのコードからこれらのOS構造体を操作する際の可読性と保守性が向上します。

2.  **`lwp_mcontext_init` のGo言語での再実装**:
    -   この関数は、Goのスケジューラが新しいゴルーチンを実行するために、OSの軽量プロセス（LWP）のコンテキストを初期化する際に呼び出されます。
    -   C言語版とGo言語版の最も顕著な違いは、レジスタへの値の代入方法です。C言語では直接ポインタをキャストして代入していましたが、Go言語では `uint32(funcPC(lwp_tramp))` や `uint32(uintptr(unsafe.Pointer(mp)))` のように、Goの関数ポインタやGoのデータ構造へのポインタを `unsafe.Pointer` を介して `uintptr` に変換し、さらに `uint32` にキャストしてレジスタに設定しています。
    -   `_REG_EIP` (Instruction Pointer) には、新しいLWPが実行を開始するGoのランタイム関数 `lwp_tramp` のアドレスが設定されます。
    -   `_REG_UESP` (User Stack Pointer) には、新しいLWPが使用するスタックのアドレスが設定されます。
    -   `_REG_EBX`, `_REG_EDX`, `_REG_ESI` には、Goランタイムの重要なデータ構造である `M` (Machine) と `G` (Goroutine) へのポインタ、およびLWPが最終的に実行するGo関数のアドレスが設定されます。これらのレジスタは、Goの規約で特定の目的のために使用され、LWPが起動した際にこれらの情報にアクセスできるようにすることで、Goのスケジューラがゴルーチンを正しく管理できるようになります。

3.  **シグナルコンテキストのGo言語での抽象化**:
    -   `src/runtime/signal_netbsd_386.h` で定義されていたC言語のマクロは、シグナルハンドラがCPUレジスタの状態にアクセスするためのものでした。これらは、Cのプリプロセッサによってコンパイル時に展開され、直接メモリを操作していました。
    -   `src/runtime/signal_netbsd_386.go` で導入された `sigctxt` 構造体と関連メソッドは、このC言語のマクロの機能をGoの型安全な方法で提供します。
    -   `sigctxt.regs()` メソッドは、`ucontextt` 構造体から `mcontextt` 構造体へのポインタを取得します。

## 変更の背景

Go言語のランタイムは、その初期段階において、パフォーマンスとOSとの密接な連携のためにC言語（またはPlan 9 C）で書かれた部分が多く存在しました。しかし、Goプロジェクトは、ランタイムの大部分をGo言語自体で記述するという長期的な目標を掲げていました。この目標にはいくつかの重要な理由があります。

1.  **保守性の向上**: Go言語で書かれたコードは、Go開発者にとってより理解しやすく、デバッグやメンテナンスが容易になります。C言語とGo言語が混在するコードベースは、開発の複雑さを増します。
2.  **クロスコンパイルの容易さ**: Goは優れたクロスコンパイル機能を持ちますが、Cgo（GoとCの相互運用）を使用する部分は、ターゲット環境のCコンパイラやCライブラリに依存するため、クロスコンパイルが複雑になる傾向があります。ランタイムをGoで書くことで、この依存関係を減らし、よりシームレスなクロスコンパイルを実現できます。
3.  **ガベージコレクタとの統合**: Goのガベージコレクタは、Goのメモリモデルと密接に連携するように設計されています。C言語で書かれたランタイムコードがGoのオブジェクトを直接操作する場合、ガベージコレクタがそのメモリを正しく追跡できないリスクがありました。ランタイムをGoで書くことで、ガベージコレクタの効率と正確性が向上します。
4.  **Goの型安全性と並行性の活用**: Go言語の持つ型安全性や並行処理のプリミティブをランタイム開発に活用することで、より堅牢で効率的なランタイムを構築できます。

このコミットは、NetBSD/386アーキテクチャに特化したランタイムコードをCからGoへ移行する、この大規模な取り組みの一部です。これにより、NetBSD/386上でのGoプログラムの実行環境が改善され、将来的な開発が容易になります。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の概念について基本的な知識が必要です。

-   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルなシステムです。これには、ゴルーチン（軽量スレッド）のスケジューリング、ガベージコレクション、メモリ管理、システムコールインターフェース、シグナルハンドリングなどが含まれます。Goプログラムは、OS上で直接実行されるのではなく、このランタイムを介してOSと対話します。

-   **Cgo**: Go言語とC言語のコードを相互運用するためのGoの機能です。Cgoを使用すると、GoプログラムからCライブラリの関数を呼び出したり、CコードからGo関数を呼び出したりできます。ランタイムのCからGoへの移行は、Cgoの依存関係を減らすことを目的としています。

-   **NetBSD/386**: NetBSDは、オープンソースのUNIX系オペレーティングシステムであり、高い移植性を特徴としています。`/386`は、Intel 80386プロセッサアーキテクチャ（32ビット）を指します。このコミットは、この特定のOSとアーキテクチャの組み合わせに特化したランタイムの変更です。

-   **システムコール (System Call)**: ユーザー空間で実行されるプログラムが、オペレーティングシステムカーネルが提供するサービス（ファイルI/O、メモリ割り当て、プロセス管理など）を要求するためのインターフェースです。Goランタイムは、OSと対話するためにシステムコールを頻繁に利用します。

-   **シグナルハンドリング (Signal Handling)**: オペレーティングシステムがプロセスに対して、特定のイベント（例えば、プログラムのエラー、外部からの割り込み、子プロセスの終了など）を非同期に通知するメカニズムです。プロセスは、特定のシグナルを受信したときに実行される「シグナルハンドラ」と呼ばれる関数を登録できます。Goランタイムは、プログラムのクラッシュや割り込みなどの重要なイベントを処理するためにシグナルハンドリングを多用します。

-   **`mcontext_t` および `ucontext_t`**: これらは、UNIX系システムにおけるシグナルハンドリング中にプロセスの実行コンテキスト（CPUレジスタの状態、スタックポインタ、プログラムカウンタなど）を保存および復元するために使用される構造体です。シグナルハンドラが実行される際、元の実行コンテキストが保存され、ハンドラ終了後に復元されることで、プログラムの実行が中断なく続行されます。

-   **`sigaltstack`**: シグナルハンドラが実行される際に使用される代替スタックを設定するためのシステムコールです。これは、通常のスタックが破損している場合（例えば、スタックオーバーフローが発生した場合）でもシグナルハンドラが安全に実行されることを保証するために重要です。

-   **`uintptr` と `*byte` / `uint32` (Go言語の型)**:
    -   `uintptr`: ポインタを保持できる符号なし整数型です。Goのコードで低レベルなメモリ操作やシステムコールインターフェースを扱う際に、ポインタ値を整数として扱う必要がある場合によく使用されます。`unsafe.Pointer`と組み合わせて、型安全性をバイパスして任意の型へのポインタを表現できます。
    -   `*byte`: バイトへのポインタです。
    -   `uint32`: 32ビットの符号なし整数型です。
    C言語ではポインタがしばしば整数型として扱われますが、Goでは型安全性のために厳密な型付けが行われます。このコミットでは、Cのポインタや整数型がGoの適切な型（特に`uintptr`）に変換されています。

2.  **`lwp_mcontext_init` のGo言語での再実装**:
    -   この関数は、Goのスケジューラが新しいゴルーチンを実行するために、OSの軽量プロセス（LWP）のコンテキストを初期化する際に呼び出されます。
    -   C言語版とGo言語版の最も顕著な違いは、レジスタへの値の代入方法です。C言語では直接ポインタをキャストして代入していましたが、Go言語では `uint32(funcPC(lwp_tramp))` や `uint32(uintptr(unsafe.Pointer(mp)))` のように、Goの関数ポインタやGoのデータ構造へのポインタを `unsafe.Pointer` を介して `uintptr` に変換し、さらに `uint32` にキャストしてレジスタに設定しています。
    -   `_REG_EIP` (Instruction Pointer) には、新しいLWPが実行を開始するGoのランタイム関数 `lwp_tramp` のアドレスが設定されます。
    -   `_REG_UESP` (User Stack Pointer) には、新しいLWPが使用するスタックのアドレスが設定されます。
    -   `_REG_EBX`, `_REG_EDX`, `_REG_ESI` には、Goランタイムの重要なデータ構造である `M` (Machine) と `G` (Goroutine) へのポインタ、およびLWPが最終的に実行するGo関数のアドレスが設定されます。これらのレジスタは、Goの規約で特定の目的のために使用され、LWPが起動した際にこれらの情報にアクセスできるようにすることで、Goのスケジューラがゴルーチンを正しく管理できるようになります。

3.  **シグナルコンテキストのGo言語での抽象化**:
    -   `src/runtime/signal_netbsd_386.h` で定義されていたC言語のマクロは、シグナルハンドラがCPUレジスタの状態にアクセスするためのものでした。これらは、Cのプリプロセッサによってコンパイル時に展開され、直接メモリを操作していました。
    -   `src/runtime/signal_netbsd_386.go` で導入された `sigctxt` 構造体と関連メソッドは、このC言語のマクロの機能をGoの型安全な方法で提供します。
    -   `sigctxt.regs()` メソッドは、`ucontextt` 構造体から `mcontextt` 構造体へのポインタを取得します。
    -   `eax()`, `eip()`, `esp()` などのメソッドは、`mcontextt` 構造体の `__gregs` 配列から対応するレジスタの値を読み出します。これにより、シグナルハンドラはGoのコードから現在のCPUの状態を検査できます。
    -   `set_eip()`, `set_esp()` などのメソッドは、レジスタの値を変更するために使用されます。これは、シグナルハンドラが実行フローを変更したり、スタックポインタを調整したりする際に必要となります。
    -   このGo言語への移行により、シグナルハンドリングコードの可読性が向上し、Cgoの境界を越える必要がなくなるため、パフォーマンスの向上やデバッグの容易化が期待できます。また、Goのコンパイラがこれらの操作を最適化できるようになります。

これらの変更は、GoランタイムのNetBSD/386ポートを、よりGo言語のイディオムに沿った形に進化させ、将来的なメンテナンスと機能拡張を容易にすることを目的としています。

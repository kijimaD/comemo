# [インデックス 24154] ファイルの概要

このコミットは、Go言語の `image/jpeg` パッケージにおけるJPEG画像のデコード処理に関するバグ修正です。具体的には、ハフマン符号化されたデータを読み取る際に、既にビットが消費されているバイトを誤って「読み戻し（unread）」てしまうという、以前の修正によって導入されたリグレッションを解決します。これにより、特定の不正なJPEGデータが与えられた際に、デコーダがパニックを起こしたり、誤った結果を返したりする可能性が排除されます。

## 変更の背景

この変更は、Go 1.4で導入された `image/jpeg` パッケージのリグレッション（バグ）を修正するために行われました。このリグレッションは、以前のコミット `2f98bac310` (CL 8841) によって引き起こされました。

元の `2f98bac310` コミットは、Issue #10387 で報告された、特定のJPEG入力でデコーダがパニックを起こす問題を解決しようとしました。この修正は、`ensureNBits` 関数が失敗した場合に `unreadByteStuffedByte` が不適切に呼び出される可能性に対処することを目的としていました。具体的には、`ensureNBits` が `io.EOF` を `jpeg.errShortHuffmanData` に変換して失敗し、実際にはバイトが読み込まれていない状況で `unreadByteStuffedByte` が呼び出されると問題が発生しました。`2f98bac310` では、`unreadByteStuffedByte` 関数自体に `d.bytes.nUnreadable == 0` の場合に早期リターンするロジックを追加することで、このパニックを防ごうとしました。

しかし、この `2f98bac310` の修正が、今度は別のシナリオでリグレッションを引き起こしました。それが Issue #11650 で報告された問題です。このリグレッションは、「既にビットが消費されているバイトを誤って読み戻してしまう」という状況で発生しました。つまり、`unreadByteStuffedByte` が呼び出されるべきではない状況で呼び出され、デコーダの内部状態が不正になり、結果としてデコードエラーやパニックにつながる可能性がありました。

本コミットは、この `2f98bac310` の修正の大部分を元に戻し、より正確な条件で `unreadByteStuffedByte` が呼び出されるようにすることで、リグレッションを修正しつつ、元の Issue #10387 の問題も引き続き解決することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

1.  **JPEGデコードの基本**:
    *   **ハフマン符号化**: JPEGは、画像データを効率的に圧縮するためにハフマン符号を使用します。これは可変長符号であり、頻繁に出現するデータには短いビット列を、稀に出現するデータには長いビット列を割り当てます。
    *   **ビットストリーム処理**: ハフマン符号はビット単位で読み取られるため、JPEGデコーダはバイト単位でデータを読み込みつつ、内部でビットバッファを管理して必要なビット数を取り出す必要があります。
    *   **マーカー**: JPEGストリームは、セグメントの開始や終了を示す特別なマーカーバイト（`0xFF`で始まる）を含みます。
    *   **バイトスタッフィング (Byte Stuffing)**: データストリーム中に `0xFF` バイトが出現し、それがマーカーと誤解釈されるのを防ぐため、JPEGでは `0xFF` の後に `0x00` を挿入する「バイトスタッフィング」というメカニズムを使用します。デコーダは `0xFF 0x00` のシーケンスを読み込んだ場合、`0x00` を破棄して `0xFF` のみをデータとして扱います。

2.  **Go `image/jpeg` パッケージの内部構造**:
    *   **`decoder` 構造体**: JPEGデコードの状態を管理する主要な構造体です。入力ストリーム、ビットバッファ、バイトバッファなどの情報を含みます。
    *   **`d.bytes`**: 入力バイトストリームを管理する内部バッファです。
        *   `d.bytes.i`, `d.bytes.j`: バッファ内の読み取り位置と書き込み位置（データの開始と終了）を示します。
        *   `d.bytes.nUnreadable`: 読み取りすぎたバイト数、つまり「読み戻し」が必要なバイト数を追跡します。
    *   **`d.bits`**: ビットバッファを管理する内部構造体です。
        *   `d.bits.n`: ビットバッファに現在利用可能なビット数を示します。
    *   **`decodeHuffman(h *huffman) (uint8, error)`**: ハフマンテーブル `h` を使用して、次のハフマン符号をデコードし、対応するシンボル（通常はDCT係数）を返します。この関数はビット単位でデータを消費します。
    *   **`ensureNBits(n int)`**: ビットバッファに少なくとも `n` ビットが利用可能であることを保証します。必要に応じて、入力ストリームから新しいバイトを読み込み、ビットバッファを補充します。
    *   **`unreadByteStuffedByte()`**: 読み取りすぎたバイト（特にバイトスタッフィングによって余分に読み込まれた `0x00` バイトなど）を、内部バッファの状態を調整することで「読み戻す」ための関数です。これは、デコーダがバイト境界を越えてビットを読み進めた後、実際にはそのバイト全体が必要なかった場合に、バッファの状態を元に戻すために使用されます。
    *   **`readFull(p []byte)`**: 指定されたバイト数 `p` を入力ストリームから読み込みます。
    *   **`ignore(n int)`**: 入力ストリームから `n` バイトをスキップします。

3.  **リグレッションとパニック**:
    *   **リグレッション**: 以前は正しく動作していた機能が、新しい変更によって動作しなくなること。
    *   **パニック (Panic)**: Goプログラムが回復不可能なエラーに遭遇した際に実行を停止するメカニズム。デコーダが不正な状態になったり、予期せぬデータに遭遇したりするとパニックが発生することがあります。

このコミットの核心は、`decodeHuffman` 関数内で `ensureNBits` が失敗した際に、`unreadByteStuffedByte` を呼び出すべきかどうかの判断をより厳密にすることにあります。

## 技術的詳細

このコミットの技術的詳細は、JPEGデコーダがハフマン符号を読み取る際のバイトとビットの管理、特に「読み戻し」処理の正確性に焦点を当てています。

JPEGのハフマンデコードでは、デコーダは通常、数ビットずつデータを消費します。しかし、入力ストリームからバイトを読み込む際には、一度に8ビット（1バイト）単位で読み込まれます。`ensureNBits` 関数は、必要なビット数がビットバッファにない場合、入力ストリームから新しいバイトを読み込んでビットバッファを補充します。

問題は、`ensureNBits` が新しいバイトを読み込んだものの、そのバイトから必要なビットを全て消費する前に、ハフマン符号のデコードが完了してしまい、かつ、そのバイトが実際にはハフマンデータの一部ではなかった（例えば、セグメントの終端に到達した）場合に発生します。このような状況では、`ensureNBits` が読み込んだバイトは「読みすぎた」バイトと見なされ、`unreadByteStuffedByte` を呼び出してそのバイトを「読み戻す」必要があります。

しかし、以前の `2f98bac310` コミットでは、`decodeHuffman` 内で `ensureNBits` が失敗した際に、無条件に `d.unreadByteStuffedByte()` を呼び出すロジックがありました。この「無条件」が問題でした。もし `ensureNBits` が失敗した理由が、そもそも読み込むべきバイトがなかった（例えば、ファイルの終端に達した）ためであり、かつ、ビットバッファから既に一部のビットが消費されていた場合、`unreadByteStuffedByte` を呼び出すと、既に消費されたビットを含むバイトを「読み戻す」ことになり、デコーダの内部状態（特に `d.bytes.i` や `d.bits.n`）が矛盾してしまいます。

本コミットは、この問題を解決するために、`decodeHuffman` 関数内の `unreadByteStuffedByte` の呼び出しに条件を追加しました。

変更点:
*   `src/image/jpeg/huffman.go` の `decodeHuffman` 関数内で、`ensureNBits` が失敗し、かつ「セグメントにこれ以上データがないが、以前読み込んだビットから次のシンボルを読み取れる可能性がある」という状況になった場合、`d.unreadByteStuffedByte()` を呼び出す前に `if d.bytes.nUnreadable != 0` という条件を追加しました。
    *   `d.bytes.nUnreadable` は、デコーダが読み取りすぎたバイト数を追跡するフィールドです。この値が `0` でない場合のみ、読み戻すべきバイトが存在することを示します。この条件を追加することで、読み戻すべきバイトがないのに `unreadByteStuffedByte` を呼び出すことを防ぎます。

さらに、`src/image/jpeg/reader.go` の `unreadByteStuffedByte` 関数自体も変更されています。
*   以前の `2f98bac310` コミットでは、`unreadByteStuffedByte` の冒頭に `if d.bytes.nUnreadable == 0 { return }` というガード句が追加されていました。本コミットでは、このガード句が削除されています。これは、`decodeHuffman` 側で呼び出し条件を厳密にしたため、`unreadByteStuffedByte` 内部での冗長なチェックが不要になった、あるいは、このガード句自体が特定のシナリオで問題を引き起こす可能性があったためと考えられます。
*   `readFull` および `ignore` 関数内の `unreadByteStuffedByte` の呼び出しロジックも変更されています。以前は `d.unreadByteStuffedByte()` を無条件に呼び出してから、`d.bytes.nUnreadable = 0` を設定していましたが、本コミットでは `if d.bytes.nUnreadable != 0` という条件を追加し、さらにその内部で `if d.bits.n >= 8` という条件も追加して `d.unreadByteStuffedByte()` を呼び出すように変更されています。これは、`d.bytes.nUnreadable` が `0` でない（つまり読み戻すべきバイトがある）場合でも、`d.bits.n >= 8`（つまりビットバッファに少なくとも1バイト分のビットが残っている）という条件が満たされる場合にのみ `unreadByteStuffedByte` を呼び出すことで、より正確な状態管理を目指しています。`d.bytes.nUnreadable = 0` は、これらの条件の外で常に実行されるようになっています。

これらの変更により、デコーダはバイトとビットの消費状態をより正確に管理し、特にハフマンデコードの終端やセグメント境界での不正な「読み戻し」を防ぐことができます。

## コアとなるコードの解説

### `src/image/jpeg/huffman.go` の変更

`decodeHuffman` 関数は、ハフマン符号をデコードする際に `ensureNBits` を呼び出して必要なビット数を確保します。この変更は、`ensureNBits` がエラーを返した場合（通常は入力データの不足を示す `io.EOF` に起因する `jpeg.errShortHuffmanData`）の処理パスにあります。

元のコードでは、このエラーパスに入ると無条件に `d.unreadByteStuffedByte()` を呼び出していました。これは、「`ensureNBits` がバイトを読み込んだが、そのバイトからビットを全て消費する前にハフマンデコードが完了した」という特定のシナリオを想定していました。しかし、この無条件の呼び出しが問題でした。

新しいコードでは、`d.unreadByteStuffedByte()` の呼び出しに `if d.bytes.nUnreadable != 0` という条件が追加されました。
*   `d.bytes.nUnreadable` は、デコーダが入力ストリームから「読み取りすぎた」バイトの数を保持します。
*   この条件は、「読み戻すべきバイトが実際に存在する場合にのみ `unreadByteStuffedByte` を呼び出す」ことを保証します。
*   これにより、`ensureNBits` がバイトを読み込んでいない（例えば、入力が完全に尽きた）にもかかわらず `unreadByteStuffedByte` が呼び出され、デコーダの内部状態が不正になることを防ぎます。これは、以前のコミット `2f98bac310` が導入したリグレッションの直接的な修正です。

### `src/image/jpeg/reader.go` の変更

1.  **`unreadByteStuffedByte()` 関数の変更**:
    *   以前の `2f98bac310` コミットでは、この関数の冒頭に `if d.bytes.nUnreadable == 0 { return }` というガード句がありました。本コミットでは、このガード句が削除されています。
    *   これは、`decodeHuffman` 側で `d.bytes.nUnreadable != 0` の条件で呼び出しを制御するようになったため、この関数内部での冗長なチェックが不要になったことを意味します。また、このガード句自体が、特定の複雑なシナリオでデコーダの状態管理を妨げていた可能性も考えられます。
    *   この関数の主なロジックは、`d.bytes.i -= d.bytes.nUnreadable` で読み取りポインタを戻し、`d.bytes.nUnreadable = 0` で読み戻しバイト数をリセットすることです。そして、`if d.bits.n >= 8` の条件でビットバッファの状態も調整します。

2.  **`readFull()` および `ignore()` 関数の変更**:
    *   これらの関数は、データを読み込んだりスキップしたりする前に、`unreadByteStuffedByte()` を呼び出して「読みすぎたバイト」を処理するロジックを含んでいました。
    *   元のコードでは、`d.unreadByteStuffedByte()` を無条件に呼び出していました。
    *   新しいコードでは、`if d.bytes.nUnreadable != 0` という条件が追加され、その内部でさらに `if d.bits.n >= 8` という条件が満たされる場合にのみ `d.unreadByteStuffedByte()` が呼び出されるようになりました。
    *   `d.bytes.nUnreadable = 0` は、これらの条件の外で常に実行されるようになっています。
    *   この変更は、`unreadByteStuffedByte` の呼び出しをより厳密な条件に限定することで、デコーダの内部状態の整合性を保ち、特にビットバッファに十分なビットが残っている場合にのみバイトの読み戻しを行うように調整しています。これにより、デコーダが不正確な状態に陥るリスクを低減します。

これらの変更は、JPEGデコードにおけるバイトとビットの複雑な相互作用を正確に管理し、特にエラーやストリームの終端に近い状況でのデコーダの堅牢性を向上させることを目的としています。

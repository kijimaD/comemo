## 変更の背景

このコミットは、Go言語の初期開発段階における重要な設計判断を反映しています。

1.  **新しい型等価性制約 (new type equality restrictions)**: Go言語は静的型付け言語であり、コンパイル時に厳密な型チェックを行います。初期のGoでは、型等価性のルールがまだ進化途上にあり、特に名前付き型と無名型の間の関係性や、異なるパッケージで定義された型間の比較において、より厳密で予測可能な挙動が求められていました。この変更は、Goの型システムの一貫性と安全性を高めることを目的としています。特に、型名が型等価性の判断に影響を与えるようにすることで、意図しない型変換や比較を防ぎ、より堅牢なコードの記述を促進します。

2.  **リネームされたパッケージのより良いハンドリング (better handling of renamed packages)**: Goでは、`import alias "path/to/package"`のように、インポート時にパッケージに別名を付けることができます。初期のコンパイラでは、このリネームされたパッケージのシンボル解決や内部表現に課題があった可能性があります。この変更は、パッケージの別名が付けられた場合でも、コンパイラがシンボルを正しく解決し、パッケージ間の依存関係を適切に管理できるようにするための改善です。これにより、開発者はより柔軟なパッケージ構成を維持しつつ、コンパイラの正確性を確保できるようになります。

3.  **"sys" のプログラムからの利用不可化 ("sys" is no longer available to programs)**: `sys`パッケージは、初期のGoにおいて低レベルなシステムコールやOS固有の機能へのアクセスを提供していた可能性があります。しかし、Go言語の設計哲学は、クロスプラットフォームな互換性と抽象化されたシステムインターフェースを提供することにあります。プログラムが直接`sys`パッケージにアクセスできると、OS依存のコードが乱立し、ポータビリティが損なわれるリスクがありました。この変更は、`sys`パッケージをコンパイラ内部でのみ利用可能なものとし、ユーザープログラムからは直接アクセスできないようにすることで、Goプログラムのポータビリティと安全性を向上させることを目的としています。これにより、開発者はより高レベルな標準ライブラリを通じてシステム機能を利用するよう促され、Goのクロスプラットフォーム戦略が強化されます。

## 前提知識の解説

このコミットの理解を深めるためには、以下のGo言語の基本的な概念とコンパイラの仕組みに関する知識が役立ちます。

*   **Go言語の型システム**:
    *   **静的型付け**: Goはコンパイル時にすべての変数の型が決定される静的型付け言語です。これにより、実行時エラーの多くをコンパイル時に検出できます。
    *   **型等価性 (Type Identity)**: Goにおける型の等価性には厳密なルールがあります。
        *   **名前付き型 (Named Types)**: `type MyInt int`のように`type`キーワードで定義された型は名前付き型です。異なるパッケージで同じ名前の型が定義されていても、それらは異なる型として扱われます。
        *   **無名型 (Unnamed Types)**: `[]int` (スライス)、`map[string]int` (マップ)、`struct { X int }` (構造体) など、`type`キーワードなしで直接定義される型は無名型です。無名型は、その構造が完全に一致する場合にのみ等価とみなされます。
        *   **基底型 (Underlying Type)**: 名前付き型は基底型を持ちます。例えば、`type MyInt int`の場合、`int`が基底型です。型変換や比較において、基底型が考慮されることがあります。
    *   **型変換 (Type Conversion)**: Goでは、異なる型間の変換は明示的に行う必要があります（例: `int(myFloat)`）。ただし、特定の条件下では暗黙的な型変換（型推論）が行われることもあります。

*   **Go言語のパッケージとインポート**:
    *   **パッケージ (Packages)**: Goのコードはパッケージにまとめられます。パッケージはコードの再利用性とモジュール性を高めます。
    *   **インポートパス (Import Path)**: パッケージはファイルシステムのパス（例: `"fmt"`, `"net/http"`）によって識別されます。
    *   **パッケージのリネーム (Package Renaming)**: `import F "fmt"`のように、インポート時にパッケージにローカルな別名を付けることができます。これにより、名前の衝突を避けたり、コードの可読性を向上させたりできます。
    *   **インポートサイクル (Import Cycles)**: 相互に依存するパッケージ（AがBをインポートし、BがAをインポートするなど）はGoでは許可されません。

*   **Goコンパイラ (6g/gc)**:
    *   **`6g`**: Go言語の初期のコンパイラの一つで、特に`amd64`アーキテクチャ（64ビットIntel/AMDプロセッサ）向けに設計されていました。Go 1.5以降は`go tool compile`に統合され、直接`6g`という名前で呼ばれることはなくなりました。
    *   **`gc`**: Go言語の公式かつ主要なコンパイラです。初期はC言語で書かれていましたが、Go 1.5でGo言語自身で書かれた（自己ホスト化された）コンパイラになりました。`gc`は高速なコンパイルが特徴です。
    *   **コンパイラの内部構造**: Goコンパイラは、字句解析（lexing）、構文解析（parsing）、型チェック、中間コード生成、最適化、コード生成などの段階を経てソースコードを実行可能なバイナリに変換します。このコミットで変更されている`src/cmd/gc/go.y`は構文解析器の定義ファイル（Yacc/Bison形式）、`src/cmd/gc/lex.c`は字句解析器の一部、`src/cmd/gc/subr.c`はユーティリティ関数群、`src/cmd/gc/go.h`は共通ヘッダファイルです。

## 技術的詳細

このコミットは、Goコンパイラの複数のコンポーネントにわたる広範な変更を含んでおり、Go言語のセマンティクスに深く関わるものです。

### 1. 新しい型等価性制約

*   **`eqtype`と`cvttype`の導入**: 以前は`eqtype`関数が型の等価性をチェックしていましたが、このコミットでは`cvttype`という新しい関数が導入され、`eqtype`もその内部で`eqtype1`という共通のヘルパー関数を呼び出すようになりました。
    *   `eqtype(Type *t1, Type *t2)`: 厳密な型等価性をチェックします。特に、名前付き型の場合、型名も一致することを要求します。これは`eqtype1(t1, t2, 0, 1)`として実装されています。最後の`1`は`names`パラメータで、型名を考慮することを意味します。
    *   `cvttype(Type *t1, Type *t2)`: 型変換が可能かどうかをチェックします。これは`eqtype1(t1, t2, 0, 0)`として実装されており、`names`パラメータが`0`であるため、型名を考慮せず、基底型や構造が一致すれば変換可能と判断します。
*   **`eqtype1`関数の変更**: `eqtype1`関数に`int names`という新しい引数が追加されました。この引数は、型等価性チェックの際に型名を考慮するかどうかを制御します。
    *   `if(names && t1->etype != TFIELD && t1->sym && t2->sym && t1 != t2) return 0;`: この行が追加されたことで、`names`が`true`の場合（つまり`eqtype`が呼び出された場合）、異なるシンボル（異なる名前付き型）を持つ型は、たとえその構造が同じであっても等価ではないと判断されるようになりました。`TFIELD`は構造体のフィールド型を表し、フィールド名が異なる場合は等価ではないため、このチェックから除外されます。
*   **`convlit1`関数の変更**: 定数リテラルの型変換ロジックが変更されました。特に、`n->type->etype != TIDEAL && n->type->etype != TNIL && !explicit`の条件がより詳細な`switch`文に置き換えられ、`TSTRING`型で`idealstring`でない場合も暗黙的な変換を許可しないようになりました。これは、文字列リテラルの型推論と変換の挙動をより厳密に定義するためです。また、`n->type = types[n->type->etype];`という行が削除されました。これは、定数リテラルの型が、その基底型に「名前を失う」という挙動を廃止し、名前付き型としての情報を保持するように変更されたことを示唆しています。

### 2. リネームされたパッケージのより良いハンドリング

*   **`Sym`構造体の変更**:
    *   `Sym`構造体から`osym`と`opackage`フィールドが削除され、`package`フィールドに統一されました。これは、シンボルが属するパッケージの「元の名前」と「現在の名前」を区別する必要がなくなったことを示唆しています。これにより、パッケージのリネーム処理が簡素化され、シンボル管理がより一貫性を持つようになりました。
    *   `char* opack;`フィールドが追加されました。これは、`LPACK`（パッケージシンボル）の場合に、そのパッケージの元の名前を保持するためのものです。これにより、パッケージの別名が付けられた場合でも、元のパッケージ名を追跡できるようになります。
*   **`renamepkg`関数の削除**: `src/cmd/gc/export.c`から`renamepkg`関数が完全に削除されました。この関数は、インポートされたパッケージの名前をリネームするロジックを担っていたと考えられますが、新しいパッケージ管理モデルでは不要になったことを示しています。
*   **`importdot`関数の追加**: `src/cmd/gc/subr.c`に`importdot`関数が追加されました。この関数は、`import . "path/to/package"`のようにドットインポートが行われた際に、インポートされたパッケージのすべてのエクスポートされたシンボルを現在のパッケージの名前空間に導入する役割を担います。これにより、ドットインポートのセマンティクスが明確に定義され、シンボル解決が適切に行われるようになります。
*   **`go.y`におけるインポート処理の変更**: 構文解析器の定義ファイルである`go.y`において、インポート処理のルールが大幅に変更されました。
    *   `import_done`という新しいルールが追加され、インポート処理の最終段階でパッケージの別名（`pkgmyname`）と元のパッケージ名（`pkgimportname`）を処理するロジックが集中化されました。
    *   `my->lexical = LPACK; my->opack = import->name;`という行は、別名が付けられたパッケージシンボルが`LPACK`としてマークされ、その元のパッケージ名が`opack`フィールドに保存されることを示しています。
    *   `if(my == import && strcmp(import->name, package) == 0) break;`という条件は、自己インポート（例えば、`package net`内で`import "net"`）の場合の特別なハンドリングを示唆しています。

### 3. "sys" のプログラムからの利用不可化

*   **`lex.c`からの`sys`キーワードの削除**: `src/cmd/gc/lex.c`のキーワードリストから`"sys", LPACK, Txxx,`というエントリが削除されました。これは、`sys`がもはや通常のパッケージとしてプログラムから直接参照できないことを意味します。
*   **`go.y`における`loadsys`の導入**: `go.y`の`file`ルールに`loadsys`という新しいルールが追加されました。
    *   `loadsys`ルールは、`cannedimports("sys.6", sysimport);`を呼び出します。これは、`sys`パッケージの定義をコンパイラ内部でロードしますが、その名前（`sys`）をプログラムの名前空間に公開しないことを意図しています。コメントにも`"sys" is no longer available to programs`と明記されています。
    *   これにより、`sys`パッケージはコンパイラが内部的に利用する低レベルな機能を提供するものとなり、ユーザーが直接インポートして利用することはできなくなりました。これは、Go言語の標準ライブラリが提供する高レベルな抽象化を通じてシステム機能を利用することを強制し、ポータビリティと安全性を向上させるための重要なステップです。

## コアとなるコードの解説

このコミットの核心は、Go言語の型システムとパッケージ管理のセマンティクスをより厳密かつ一貫性のあるものにすることにあります。

1.  **型等価性の再定義**:
    *   `eqtype`と`cvttype`の分離は、Goの型システムにおける「同一性」と「変換可能性」という二つの異なる概念を明確に区別するためのものです。
    *   `eqtype`は、名前付き型の場合に型名まで含めて厳密な同一性を要求するようになりました。これは、`type MyInt int`と`type YourInt int`が、たとえ基底型が同じ`int`であっても、異なる型として扱われるべきであるというGoの設計思想を強化します。これにより、開発者は意図しない型間の比較や代入を防ぎ、より安全なコードを書くことができます。
    *   `cvttype`は、型変換の文脈で使用され、型名ではなくその構造や基底型が互換性を持つかどうかを判断します。これにより、例えば`int`型の変数に`MyInt`型の値を代入する際に、明示的な型変換が必要となる一方で、コンパイラが内部的に型を扱う際にはより柔軟な変換が可能になります。
    *   `convlit1`からの`n->type = types[n->type->etype];`の削除は、定数リテラルがその基底型に「名前を失う」という挙動を廃止し、名前付き型としての情報を保持するように変更されたことを示唆しています。これは、型システム全体の一貫性を高めるための重要な変更です。

2.  **パッケージ管理の合理化**:
    *   `Sym`構造体から`opackage`フィールドが削除され、`package`フィールドに統一されたことは、シンボルが属するパッケージの「元の名前」と「現在の名前」を区別する必要がなくなったことを意味します。これは、パッケージのリネームやエイリアシングの処理を簡素化し、コンパイラ内部でのパッケージ情報の管理をより効率的にします。
    *   `renamepkg`関数の削除は、この新しい統一されたモデルにおいて、以前のリネーム処理が不要になったことを示しています。
    *   `importdot`関数の導入は、`import . "pkg"`というドットインポートのセマンティクスを明確に定義し、インポートされたパッケージのシンボルが現在のパッケージの名前空間にどのように導入されるかを制御します。これにより、シンボル解決の予測可能性と正確性が向上します。
    *   `go.y`における`import_done`ルールの追加は、インポート処理の最終段階でのシンボル解決と名前空間への導入ロジックを集中化し、コードの保守性を高めています。

3.  **`sys`パッケージの内部化**:
    *   `lex.c`から`sys`キーワードが削除され、`go.y`に`loadsys`ルールが追加されたことは、`sys`パッケージがもはや通常のGoプログラムから直接インポートできないことを明確に示しています。
    *   `cannedimports("sys.6", sysimport);`の呼び出しは、コンパイラが内部的に`sys`パッケージの定義をロードし、低レベルなシステム機能にアクセスするために利用することを意味します。しかし、このパッケージはユーザープログラムの名前空間には公開されません。
    *   この変更は、Go言語が提供する高レベルな抽象化を通じてシステム機能を利用することを開発者に促し、Goプログラムのクロスプラットフォームな互換性と安全性を確保するための重要なステップです。これにより、Goの標準ライブラリが提供するAPIを通じてのみシステム機能にアクセスできるようになり、OS固有のコードがアプリケーションに直接混入することを防ぎます。

これらの変更は、Go言語がその初期段階で、堅牢な型システム、明確なモジュール性、そして高いポータビリティという設計目標を達成するために、コンパイラレベルでどのように進化していったかを示す良い例です。

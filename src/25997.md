## 元コミット内容

`net/http: clarify some RoundTripper behaviors`

このコミットは、`net/http` パッケージの `RoundTripper` インターフェースの振る舞いに関するいくつかの点を明確化します。具体的には、`RoundTrip` メソッドのドキュメントが更新され、以下の点が強調されています。

*   `RoundTrip` は、HTTPステータスコードに関わらず、レスポンスを取得できた場合は `err == nil` を返す必要があること。
*   `RoundTrip` は、リダイレクト、認証、クッキーなどの高レベルなプロトコル詳細を処理すべきではないこと。
*   `RoundTrip` は、リクエストの `Body` の消費とクローズを除いて、リクエストを変更すべきではないこと。
*   `RoundTrip` は、エラー時も含め、常にリクエストボディをクローズする必要があること。ただし、これは `RoundTrip` が返った後、別のゴルーチンで行われる可能性があるため、ボディを再利用したい呼び出し元は `Close` 呼び出しが完了するのを待つ必要があること。
*   リクエストの `URL` および `Header` フィールドは初期化されている必要があること。

この変更は、Issue #12796 を修正し、Issue #13444 を更新します。

## 変更の背景

`net/http.RoundTripper` は、GoのHTTPクライアントの動作をカスタマイズするための非常に強力なインターフェースです。しかし、その柔軟性ゆえに、実装者がその契約（contract）を誤解したり、予期せぬ副作用を引き起こしたりする可能性がありました。特に、リクエストボディのライフサイクル管理、エラー発生時の振る舞い、およびリクエストオブジェクトの変更可能性に関する曖昧さが存在していました。

このコミットは、以下の具体的な問題意識から生まれました。

1.  **リクエストボディのライフサイクル**: `RoundTripper` の実装がリクエストボディを適切に消費・クローズしない場合、リソースリークや接続のハングアップといった問題が発生する可能性がありました。特に、エラーが発生した場合でもボディをクローズする必要があるという点が不明確でした。
2.  **リクエストの変更**: `RoundTrip` メソッド内で `http.Request` オブジェクトを直接変更することの危険性がありました。`http.Client` は内部でリクエストを再試行したり、複数の `RoundTripper` をチェインしたりする可能性があるため、元のリクエストが変更されると予期せぬ動作を引き起こす可能性があります。
3.  **エラーハンドリングの明確化**: `RoundTrip` がエラーを返すタイミングと、レスポンスオブジェクトを返すタイミングに関する明確なガイドラインが必要でした。HTTPステータスコードがエラーを示す場合でも、ネットワークレベルでレスポンスが正常に受信されたのであれば、`RoundTrip` はエラーを返すべきではありません。

Issue #12796 は、おそらく `RoundTripper` の実装における特定のバグや、上記のような曖昧さによる誤用に関連するものであったと考えられます。また、Issue #13444 は、双方向ストリームの実装パターンに関連しており、`RoundTripper` のボディ処理に関する明確化が、このような高度なユースケースでの問題（例えば、`RoundTrip` がハングアップするなどの問題）を防ぐために必要とされた可能性があります。

これらの背景から、`RoundTripper` インターフェースのドキュメントをより厳密かつ詳細にすることで、実装者がより堅牢で正しい `RoundTripper` を作成できるようにすることが、このコミットの主要な動機となっています。

## 前提知識の解説

### `net/http` パッケージ

Go言語の標準ライブラリである `net/http` パッケージは、HTTPクライアントとサーバーを実装するための機能を提供します。ウェブアプリケーション、APIクライアント、プロキシなど、HTTP通信を必要とするあらゆるGoプログラムの基盤となります。

### `http.Client`

`http.Client` は、HTTPリクエストを送信し、HTTPレスポンスを受信するGoの構造体です。通常、`Get`、`Post`、`Do` などのメソッドを通じてHTTPリクエストを実行します。`http.Client` は、内部的に `http.RoundTripper` インターフェースの実装を利用して実際のHTTPトランザクションを実行します。

### `http.RoundTripper` インターフェース

`http.RoundTripper` は、GoのHTTPクライアントにおける最も重要な拡張ポイントの一つです。このインターフェースは、単一の `RoundTrip` メソッドを定義します。

```go
type RoundTripper interface {
    RoundTrip(*Request) (*Response, error)
}
```

`RoundTripper` の主な役割は以下の通りです。

*   **HTTPトランザクションの実行**: `*http.Request` を受け取り、ネットワーク経由で送信し、`*http.Response` を受け取って返します。
*   **ミドルウェアとしての機能**: `http.Client` の `Transport` フィールドにカスタム `RoundTripper` を設定することで、リクエストの送信前やレスポンスの受信後にカスタムロジックを挿入できます。これにより、ロギング、認証ヘッダの追加、キャッシュ、リトライ処理、レートリミット、リクエスト/レスポンスの変換など、多岐にわたるカスタマイズが可能になります。
*   **低レベルな処理の抽象化**: `RoundTripper` は、リダイレクト、認証、クッキーなどの高レベルなプロトコル詳細を処理すべきではありません。これらの処理は `http.Client` 自体が行うべきであり、`RoundTripper` はより低レベルな「リクエストを送信し、レスポンスを受け取る」という単一の責務に集中すべきです。

### `http.Request.Body` と `http.Response.Body`

HTTPリクエストとレスポンスには、それぞれボディ（ペイロード）が含まれることがあります。Goでは、これらのボディは `io.ReadCloser` インターフェースとして表現されます。これは、ボディがストリームとして扱われ、読み取り後にクローズされる必要があることを意味します。特に、`http.Response.Body` は、ネットワーク接続を再利用するために、読み取りが完了したら必ずクローズする必要があります。

### Issue #12796 と #13444 (補足)

コミットメッセージで参照されているこれらのIssueは、`RoundTripper` の振る舞いに関する具体的な問題や議論を指しています。

*   **Issue #12796**: 直接的な詳細が見つかりませんでしたが、コミットが「Fixes」と明記していることから、`RoundTripper` の既存のドキュメントの曖昧さや、それによって引き起こされる実装上の問題（例えば、リソースリークや予期せぬエラーハンドリング）を解決するためのものであったと推測されます。
*   **Issue #13444**: このIssueは、双方向ストリームの実装パターンに関連していることが示唆されています。`RoundTripper` がリクエストボディを適切に処理しない場合、特にストリームのような継続的なデータフローを伴うシナリオで、接続がハングアップしたり、データが失われたりする問題が発生する可能性があります。このコミットによるドキュメントの明確化は、そのような複雑なユースケースにおける `RoundTripper` の正しい実装を促すことを目的としています。

## 技術的詳細

このコミットの技術的詳細は、`net/http.RoundTripper` インターフェースのドキュメントコメントの変更に集約されます。変更前と変更後のコメントを比較することで、Go開発チームが `RoundTripper` の実装者に何を期待しているかが明確になります。

### 変更点と意図

1.  **エラーハンドリングの明確化**:
    *   **変更前**: `RoundTrip must return err == nil if it obtained a response, regardless of the response's HTTP status code. A non-nil err should be reserved for failure to obtain a response.`
    *   **変更後**: `RoundTrip must return err == nil if it obtained a response, regardless of the response's HTTP status code. A non-nil err should be reserved for failure to obtain a response.`
    *   **解説**: この部分は変更されていませんが、その重要性が再確認されています。`RoundTripper` は、ネットワークレベルでレスポンスヘッダを受信できた場合、たとえHTTPステータスコードが `404 Not Found` や `500 Internal Server Error` であっても、`error` を `nil` として返す必要があります。`error` は、DNS解決の失敗、TCP接続の確立失敗、TLSハンドシェイクの失敗、タイムアウトなど、**レスポンス自体を取得できなかった**場合にのみ返すべきです。これにより、`http.Client` の上位層がHTTPステータスコードに基づいて適切なエラー処理を行えるようになります。

2.  **高レベルプロトコル詳細の非処理**:
    *   **変更前**: `Similarly, RoundTrip should not attempt to handle higher-level protocol details such as redirects, authentication, or cookies.`
    *   **変更後**: `Similarly, RoundTrip should not attempt to handle higher-level protocol details such as redirects, authentication, or cookies.`
    *   **解説**: この部分も変更されていませんが、`RoundTripper` の責務の範囲を明確にしています。これらの高レベルな処理は `http.Client` の責任であり、`RoundTripper` は純粋に単一のHTTPトランザクション（リクエストの送信とレスポンスの受信）に集中すべきです。これにより、`RoundTripper` の実装がシンプルになり、再利用性が高まります。

3.  **リクエストの変更に関する制約**:
    *   **変更前**: `RoundTrip should not modify the request, except for consuming and closing the Body, including on errors. The request's URL and Header fields are guaranteed to be initialized.`
    *   **変更後**: `RoundTrip should not modify the request, except for consuming and closing the Request's Body.`
    *   **解説**: 「`including on errors`」という文言が削除され、より簡潔になりました。重要なのは、`RoundTripper` は原則として受け取った `*http.Request` オブジェクトを変更してはならないという点です。これは、`http.Client` がリクエストを再試行したり、複数の `RoundTripper` をチェインしたりする際に、元のリクエストの状態が保たれることを保証するためです。唯一の例外は、リクエストボディ (`Request.Body`) の消費とクローズです。これは、ボディがストリームであり、一度読み取られると再利用できないため、`RoundTripper` がその責務を果たす過程で消費されるのは自然なことです。もし `RoundTripper` がリクエストの他の部分（ヘッダやURLなど）を変更する必要がある場合は、`req.Clone(req.Context())` を使用してリクエストのコピーを作成し、そのコピーを変更することが推奨されます。

4.  **リクエストボディのクローズに関する厳格化**:
    *   **変更前**: `RoundTrip should not modify the request, except for consuming and closing the Body, including on errors.` (この部分にボディクローズの言及があるが、詳細が不足)
    *   **変更後**:
        ```
        RoundTrip must always close the body, including on errors,
        but depending on the implementation may do so in a separate
        goroutine even after RoundTrip returns. This means that
        callers wanting to reuse the body for subsequent requests
        must arrange to wait for the Close call before doing so.
        ```
    *   **解説**: この部分が最も重要な変更点の一つです。`RoundTripper` は、**常に**リクエストボディをクローズする責任があることが明確にされました。これは、リクエストが成功した場合だけでなく、エラーが発生した場合でも同様です。ボディをクローズしないと、リソースリーク（特にTCP接続のリーク）が発生し、アプリケーションのパフォーマンスや安定性に悪影響を及ぼす可能性があります。
        さらに、「別のゴルーチンでクローズされる可能性がある」という点が追記されました。これは、`RoundTripper` の実装によっては、`RoundTrip` メソッドが返った後も非同期的にボディのクローズ処理が行われる可能性があることを示唆しています。このため、もし呼び出し元が同じリクエストボディを後続のリクエストで再利用したい場合（例えば、リトライ処理で同じボディを再送信する場合）、`RoundTrip` が返った直後にボディがクローズされているとは限らないため、明示的にクローズ処理の完了を待つメカニズムを実装する必要があるという警告です。これは、特にストリーミングリクエストや大きなボディを持つリクエストを扱う際に重要になります。

5.  **リクエストフィールドの初期化保証**:
    *   **変更前**: `The request's URL and Header fields are guaranteed to be initialized.`
    *   **変更後**: `The Request's URL and Header fields must be initialized.`
    *   **解説**: 「guaranteed to be initialized」から「must be initialized」への変更は、`RoundTripper` の実装者がこれらのフィールドが常に有効な状態であることを前提として良いという保証を、より強い「前提条件」として表現しています。これは、`http.Client` が `RoundTrip` を呼び出す前にこれらのフィールドを適切に設定することを意味し、`RoundTripper` の実装者はこれらのフィールドのnilチェックなどを行う必要がないことを示唆しています。

これらの変更は、`RoundTripper` の契約をより厳密にし、実装者が陥りやすい落とし穴を回避するための明確なガイドラインを提供することで、`net/http` パッケージ全体の堅牢性と予測可能性を高めることを目的としています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`RoundTripper` インターフェースのドキュメントコメントの修正です。具体的な変更点は以下の通りです。

1.  **`RoundTrip` の戻り値に関する表現の微調整**:
    *   変更前: `returning the Response for the request req.`
    *   変更後: `returning a Response for the provided Request.`
    *   これは意味的な変更ではなく、より一般的な表現への修正です。

2.  **リクエストボディのクローズに関する詳細な説明の追加**:
    *   変更前は `except for consuming and closing the Body, including on errors.` と簡潔に述べられていた部分が、より詳細に拡張されました。
    *   **`RoundTrip must always close the body, including on errors,`**: `RoundTripper` の実装は、成功・失敗に関わらず、常にリクエストボディをクローズする責任があることを強調しています。これはリソースリークを防ぐために極めて重要です。
    *   **`but depending on the implementation may do so in a separate goroutine even after RoundTrip returns.`**: ボディのクローズ処理が非同期的に行われる可能性があることを明記しています。これは、`RoundTrip` メソッドが高速にリターンしつつも、バックグラウンドでクリーンアップ処理を継続できる柔軟性を提供します。
    *   **`This means that callers wanting to reuse the body for subsequent requests must arrange to wait for the Close call before doing so.`**: 上記の非同期クローズの可能性を考慮し、リクエストボディを再利用したい呼び出し元（例えば、リトライロジックを持つクライアント）は、ボディが完全にクローズされるのを待つメカニズムを実装する必要があるという重要な警告です。これにより、ボディがまだ使用中であるにもかかわらず再利用しようとして発生する可能性のある競合状態やエラーを防ぎます。

3.  **リクエストフィールドの初期化保証の表現の変更**:
    *   変更前: `The request's URL and Header fields are guaranteed to be initialized.`
    *   変更後: `The Request's URL and Header fields must be initialized.`
    *   「guaranteed to be initialized (初期化が保証されている)」から「must be initialized (初期化されている必要がある)」への変更は、`RoundTripper` の実装者がこれらのフィールドが常に有効な状態であることを前提として良いという、より強い契約上の要件を表現しています。これは、`http.Client` が `RoundTrip` を呼び出す前にこれらのフィールドを適切に設定することを意味します。

これらの変更は、`RoundTripper` インターフェースの契約をより明確にし、実装者がより堅牢で正しいHTTPクライアントのカスタマイズを構築できるようにするための重要なドキュメントの改善です。特に、リクエストボディのライフサイクル管理に関する詳細な指示は、リソースリークやデッドロックといった一般的な問題を回避するために不可欠です。

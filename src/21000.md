## 元コミット内容

このコミットは、Goランタイムのガベージコレクション（GC）におけるいくつかの「チェックマーク」バグを修正します。

主な修正点は以下の通りです。

-   最初の`gc_m`ラウンドを適切な場所で停止させ、2番目のラウンドの準備を正しく行うためのシーケンス問題。
-   `atomicxor8`関数が冪等性を持たないため、`xor`操作を避けるように変更。
-   `BitsDead`型ビットを正しく維持するための修正。これに関する詳細なコメントが追加されています。
-   当面の間、チェックマークフェーズをデフォルトで有効化。

## 変更の背景

このコミットが行われた背景には、Goランタイムのガベージコレクタの進化があります。当時のGoのGCは、より効率的で低レイテンシな動作を目指して改良が進められていました。その過程で、「チェックマーク」と呼ばれる新しいGCフェーズが導入され、GCの正確性とパフォーマンスを検証するための重要なメカニズムとなっていました。

しかし、この新しいチェックマークフェーズにはいくつかの初期のバグが存在しました。

1.  **GCラウンドのシーケンス問題**: GoのGCは複数のフェーズに分かれており、特にマークフェーズは複数回実行されることがあります。これらのフェーズ間の遷移や停止のタイミングが不適切だと、GCの正確性が損なわれたり、メモリリークやクラッシュの原因となる可能性がありました。
2.  **`atomicxor8`の冪等性問題**: GCは並行して動作するため、メモリ上のビットマップをアトミックに操作する必要があります。`atomicxor8`のようなビット操作は、特定のビットを反転させるために使用されますが、同じ値を複数回`xor`すると元の状態に戻ってしまうという冪等性の問題がありました。これは、GCが特定のビットを一度だけ変更したい場合に問題となります。例えば、あるオブジェクトがマークされたことを示すビットを立てる際に、誤って複数回`xor`操作が行われると、ビットが反転して未マークの状態に戻ってしまう可能性がありました。
3.  **`BitsDead`型ビットの管理問題**: GoのGCは、ヒープ上のオブジェクトの型情報をビットマップで管理しています。`BitsDead`は、そのメモリ領域が使用されていない（デッドである）ことを示す型ビットです。GCのマークフェーズでは、オブジェクトが生きているか死んでいるかを判断し、それに応じてビットマップを更新します。`BitsDead`の管理が不正確だと、GCが誤って生きているオブジェクトを解放したり、デッドなオブジェクトをマークしてしまったりする可能性があり、深刻なバグにつながります。

これらの問題は、チェックマークフェーズの正確な動作を妨げ、GC全体の信頼性に影響を与えていました。このコミットは、これらの根本的な問題を解決し、チェックマークフェーズを安定させることを目的としています。また、チェックマークフェーズをデフォルトで有効にすることで、さらなるテストと検証を促進し、GCの品質向上を図っています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

### Goのガベージコレクション (GC)

Goのガベージコレクタは、主に「マーク＆スイープ」アルゴリズムをベースにしています。これは、プログラムが使用しているオブジェクト（到達可能なオブジェクト）を「マーク」し、マークされなかったオブジェクト（到達不可能なオブジェクト、つまりガベージ）を「スイープ」（解放）するプロセスです。GoのGCは、アプリケーションの実行と並行して動作する「並行GC」であり、アプリケーションの停止時間（ストップ・ザ・ワールド、STW）を最小限に抑えるように設計されています。

主要なフェーズは以下の通りです。

1.  **マークフェーズ (Mark Phase)**:
    *   GCルート（グローバル変数、スタック上のポインタなど）から到達可能なすべてのオブジェクトを探索し、マークします。
    *   このフェーズは通常、複数のサブフェーズに分かれており、並行して実行されます。
2.  **マークターミネーションフェーズ (Mark Termination Phase)**:
    *   マークフェーズの終了を調整し、すべてのゴルーチンがマーク作業を完了したことを確認します。短いSTWが発生します。
3.  **スイープフェーズ (Sweep Phase)**:
    *   マークされなかったオブジェクトが占めていたメモリを解放し、再利用可能な状態にします。このフェーズも並行して実行されます。

### チェックマークフェーズ (Checkmark Phase)

このコミットで言及されている「チェックマーク」フェーズは、GoのGCのデバッグおよび検証メカニズムの一部として導入されたものです。これは、GCのマークフェーズが正しく動作しているかを検証するために使用されます。

チェックマークフェーズの基本的な考え方は以下の通りです。

*   通常のマークフェーズが完了した後、GCは「チェックマーク」フェーズに入ります。
*   このフェーズでは、GCは再度ヒープをスキャンし、マークされているべきオブジェクトが実際にマークされているか、そしてマークされるべきでないオブジェクトが誤ってマークされていないかを検証します。
*   もし不整合が見つかった場合、それはGCのバグを示唆しており、ランタイムパニックを引き起こすことで問題を早期に発見します。

このフェーズは、GCの正確性を保証するための「セーフティネット」のような役割を果たします。

### メモリ管理と型ビット (Type Bits)

Goランタイムは、ヒープ上のメモリを`MSpan`と呼ばれるチャンクで管理しています。各`MSpan`は、特定のサイズのオブジェクトを格納するために使用されます。

メモリ内のオブジェクトの型情報は、GCがポインタを識別し、ヒープを正確にスキャンするために不可欠です。この型情報は、ビットマップとして管理されており、各オブジェクトのワード（ポインタサイズ）に対応するビットが、それがポインタであるか、スカラー（非ポインタ）であるか、あるいはデッド（未使用）であるかを示します。

*   **`bitMarked`**: オブジェクトがGCによってマークされたことを示すビット。
*   **`bitPtrMask`**: ポインタ型を示すビットマスク。
*   **`BitsScalar`**: スカラー型（ポインタを含まない）を示す型ビット。
*   **`BitsPointer`**: ポインタ型（ポインタを含む）を示す型ビット。
*   **`BitsDead`**: そのメモリ領域が現在使用されていない（デッドである）ことを示す型ビット。これは、GCがメモリを解放した後や、オブジェクトがまだ割り当てられていない領域に設定されます。GCは`BitsDead`の領域をスキャンすべきではありません。
*   **`BitsScalarMarked` / `BitsPointerMarked`**: チェックマークフェーズ中に、スカラーまたはポインタがマークされたことを示すために一時的に使用されるビット。

これらの型ビットは、メモリのビットマップにエンコードされており、GCがヒープを効率的にトラバースし、オブジェクトの構造を理解するために使用されます。

### アトミック操作と冪等性 (Idempotency)

*   **アトミック操作**: 複数のCPUコアやゴルーチンが同時にメモリにアクセスする可能性がある並行システムでは、データの一貫性を保つためにアトミック操作が不可欠です。アトミック操作は、中断されることなく単一の不可分な操作として実行されることが保証されます。これにより、競合状態（race condition）を防ぎます。
*   **冪等性**: 冪等性とは、ある操作を複数回実行しても、1回実行した場合と同じ結果になる性質を指します。例えば、`x = 5`という代入操作は冪等です。何度実行しても`x`は`5`になります。しかし、`x = x + 1`という操作は冪等ではありません。複数回実行すると`x`の値は変化し続けます。
    GCの文脈では、ビット操作が冪等でないと、特定のビットを一度だけ変更したい場合に問題が生じます。例えば、`XOR`操作は冪等ではありません。`A XOR B XOR B`は`A`に戻ります。これは、GCがオブジェクトをマークする際に、誤ってマークビットを反転させてしまう可能性があることを意味します。

**問題点:**
1.  **初期化されていない型ビット**: チェックマークフェーズの準備中に`BitsDead`を`BitsScalar`に変換する際、`BitsDead`に続く型ビットが初期化されていない可能性がある。GCがこれらの初期化されていないビットをスキャンすると問題が発生する。
2.  **クリーンアップ時の`BitsDead`の復元**: 解放されたオブジェクトは`BitsDead`であると期待されるが、チェックマークフェーズ中に`BitsScalar`に変換された`BitsDead`を、クリーンアップ時に正しく`BitsDead`に戻す必要がある。

**解決策:**
*   **準備フェーズ (`checkmark && b == BitsDead`)**: `BitsDead`の最初のワードを`BitsScalar`に設定するだけでなく、2番目のワードの型ビットも`BitsDead`に初期化します。これにより、チェックマークフェーズ中のスキャンが初期化されていないビットに到達する前に停止することが保証されます。
*   **クリーンアップフェーズ (`!checkmark && (b == BitsScalar || b == BitsScalarMarked) && (*bitp & 0xc0) == 0`)**: チェックマークフェーズ後のクリーンアップ時に、もし最初のワードが`BitsScalar`または`BitsScalarMarked`であり、かつ2番目のワードが`BitsDead`である場合、最初のワードも`BitsDead`に戻します。これは、元々`BitsDead`であった領域を正しく復元するためのロジックです。

これらの変更により、GCがメモリ内の型情報をより正確に管理できるようになり、特に`BitsDead`領域の取り扱いにおけるバグが修正されます。

## コアとなるコードの解説

### `gccheckmarkenable`の変更

`static bool gccheckmarkenable = true;`
この変更は、開発段階であったチェックマークフェーズをデフォルトで有効にすることで、GCの正確性検証を常に実行し、潜在的なバグを早期に発見するためのものです。

### `slottombits`における型ビット抽出の修正

`mbits->tbits = ((mbits->xbits >> mbits->shift) & bitPtrMask) >> 2;`
この修正は、メモリビットマップから型ビットを正確に抽出するために行われました。`bitPtrMask`でマスクした後、さらに2ビット右シフトすることで、`BitsDead`、`BitsScalar`、`BitsPointer`などの型ビットが、ビットマップ内の正しい位置から読み取られることを保証します。これは、型ビットのエンコーディングまたは`bitPtrMask`の定義が変更されたことに対応しています。

### `atomicxor8`から`atomicand8`への変更と`docheckmark`の修正

```c
// atomicxor8からatomicand8への変更
static Mutex andlock;
static void
atomicand8(byte *src, byte val)
{
	runtime·lock(&andlock);
	*src = *src&val;
	runtime·unlock(&andlock);
}

// docheckmarkの修正
if(mbits->tbits == BitsScalar)
	atomicand8(mbits->bitp, ~(byte)(BitsCheckMarkXor<<mbits->shift<<2));

	runtime·atomicor8(mbits->bitp, BitsCheckMarkXor<<mbits->shift<<2);
```
`atomicxor8`が`atomicand8`に変更されたのは、`XOR`操作が冪等ではないため、並行環境で複数回適用されると意図しない結果（ビットが反転して元に戻る）になる問題を解決するためです。
`docheckmark`では、オブジェクトの型（`BitsScalar`か`BitsPointer`か）に応じて、異なるアトミック操作が適用されます。
*   `BitsScalar`の場合、`atomicand8`とビットマスクの反転（`~`）を組み合わせることで、特定のビットを確実に0に設定します。これは、スカラーがマークされたことを示すビットをクリアする操作に相当します。
*   `BitsPointer`の場合、`runtime·atomicor8`を使用して特定のビットを確実に1に設定します。これは、ポインタがマークされたことを示すビットをセットする操作に相当します。
これらの変更により、マーク操作が冪等になり、GCのビットマップ操作の信頼性が向上します。

### `clearcheckmarkbitsspan`における`BitsDead`の管理

```c
// 準備フェーズでのBitsDeadの処理

	// move BitsDead into second word.
	// set bits to BitsScalar in preparation for checkmark phase.
```

*   **準備フェーズ**: チェックマークフェーズの開始時に、`BitsDead`の領域を`BitsScalar`として一時的に扱います。この際、オブジェクトが複数ワードにわたる場合、後続のワードの型ビットが初期化されていない可能性があるため、2番目のワードの型ビットを`BitsDead`に明示的に設定することで、GCスキャンが安全に停止できるようにします。
*   **クリーンアップフェーズ**: チェックマークフェーズの終了後、一時的に`BitsScalar`として扱われた領域が、元々`BitsDead`であった場合は、それを`BitsDead`に戻します。これは、メモリが解放された状態を正確に反映させるために重要です。

これらの変更により、GCがヒープ上のオブジェクトの型情報をより正確に追跡し、特に未使用のメモリ領域（`BitsDead`）の取り扱いにおけるバグが修正されます。

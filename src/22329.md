# [インデックス 22329] ファイルの概要

このコミットは、Goコンパイラの内部パッケージである`cmd/internal/obj/x86`における、`nacl/amd64p32`ターゲット向けのバグ修正です。具体的には、アセンブリ命令のポストプロセッシングを行う`progedit`関数内で、特定の命令（`CMPPS`など）のオペランド書き換え処理と、Native Client (NaCl) 向けのメモリアドレス変換処理の実行順序を修正することで、`nacl/amd64p32`環境での正しいコード生成を保証します。

## 変更の背景

この変更は、GoコンパイラがGoogle Native Client (NaCl) の`amd64p32`ターゲット向けにコードを生成する際に発生していた問題を解決するために行われました。`src/cmd/internal/obj/x86/obj6.go`内の`progedit`関数は、アセンブリ命令を最終的なオブジェクトコードに変換する前のポストプロセッシングを担当しています。

以前の実装では、`progedit`関数内で以下の2つの重要な処理が特定の順序で実行されていました。
1.  `nacladdr`関数によるNative Client特有のメモリアドレス変換。
2.  `CMPPD`, `CMPPS`, `CMPSD`, `CMPSS`といった浮動小数点比較命令の第3オペランド（通常は即値0）を、テーブルが期待する形式（定数0）に書き換える処理。

この順序が`nacl/amd64p32`環境において問題を引き起こしていました。具体的には、`nacladdr`が先に実行されることで、`CMPPS`命令のオペランドが正しく認識されず、その後の書き換え処理が適切に適用されない、あるいは誤った変換が行われる可能性がありました。このため、`nacl/amd64p32`ターゲットで生成されるコードが不正になるバグが発生していました。

このコミットは、これらの処理の実行順序を入れ替えることで、この問題を解決し、`nacl/amd64p32`環境でのGoプログラムの正確なコンパイルを保証します。

## 前提知識の解説

### Go Native Client (NaCl)

Google Native Client (NaCl) は、ウェブブラウザ内でC/C++などのネイティブコードを安全に実行するためのサンドボックス技術です。Go言語もかつてNaClをターゲットプラットフォームの一つとしてサポートしていました。NaClは、ブラウザのセキュリティモデルに準拠しつつ、ネイティブコードのパフォーマンスを活用することを目的としていましたが、WebAssembly (Wasm) の登場と普及により、現在ではその役割を終え、Goを含む多くの言語でサポートが終了または非推奨となっています。このコミットが作成された2015年当時は、まだ活発に開発・利用されていました。

### `amd64p32`アーキテクチャ

`amd64p32`は、64ビットのAMD64プロセッサ上で動作するが、アドレス空間が32ビットに制限されている特殊なアーキテクチャです。これは主にNaCl環境で使用され、64ビットCPUの性能を利用しつつ、ポインタサイズを32ビットに保つことで、メモリ使用量を抑えたり、既存の32ビットコードベースとの互換性を維持したりする目的がありました。Goのコンパイラは、この特定のアーキテクチャ向けに最適化されたコードを生成する必要がありました。

### Go `cmd/internal/obj`パッケージ

`cmd/internal/obj`パッケージは、Goコンパイラツールチェーンの内部コンポーネントであり、アセンブラのバックエンドとして機能します。このパッケージは、Goのソースコードから生成された中間表現（ASTなど）を、ターゲットアーキテクチャ（この場合はx86）の具体的なアセンブリ命令に変換し、オブジェクトファイルを生成する役割を担っています。`obj`パッケージは、アセンブリ命令の表現、レジスタの管理、命令のエンコードなど、低レベルのコード生成に関する機能を提供します。

### `progedit`関数

`progedit`関数は、`cmd/internal/obj/x86`パッケージ内に存在する、アセンブリ命令のリスト（`obj.Prog`構造体のシーケンス）を最終的なオブジェクトコードに変換する前に行われる、ポストプロセッシングステップです。この関数は、命令の正規化、特定のオペランドの調整、ジャンプ命令の解決、アーキテクチャ固有の最適化など、様々な修正や変換を適用します。このコミットでは、この関数内の処理順序が問題となっていました。

### `ACMPPD`, `ACMPPS`, `ACMSD`, `ACMPSS`

これらはx86アセンブリ命令のニーモニックであり、浮動小数点数の比較命令です。
*   `CMPPD`: Packed Double-precision Floating-Point Compare (2つの倍精度浮動小数点数を比較)
*   `CMPPS`: Packed Single-precision Floating-Point Compare (4つの単精度浮動小数点数を比較)
*   `CMPSD`: Scalar Double-precision Floating-Point Compare (1つの倍精度浮動小数点数を比較)
*   `CMPSS`: Scalar Single-precision Floating-Point Compare (1つの単精度浮動小数点数を比較)

これらの命令は、通常、第3オペランドとして比較条件を示す即値（例: 0x00 for EQ, 0x01 for LTなど）を取ります。Goコンパイラの内部では、この即値0を特定の形式（`obj.TYPE_CONST`）に変換する必要がありました。

## 技術的詳細

このコミットの技術的な核心は、`progedit`関数内での2つの重要なコードブロックの実行順序の変更です。

元々のコードでは、以下の順序で処理が行われていました。

1.  **NaClアドレス変換処理**: `ctxt.Headtype == obj.Hnacl && p.Mode == 64`という条件が真の場合（つまり、`nacl/amd64p32`ターゲットの場合）、`nacladdr`関数が`p.From`と`p.To`オペランドに対して呼び出され、NaCl環境に特有のアドレス変換が行われます。
2.  **`CMPPS`命令のオペランド書き換え処理**: `ACMPPD`, `ACMPPS`, `CMPSD`, `CMPSS`命令の場合、第3オペランドがメモリ参照（`obj.TYPE_MEM`）であり、かつシンボルやレジスタが指定されていない（即値0を意味する）場合に、そのオペランドの型を`obj.TYPE_CONST`に書き換えます。これは、アセンブラのテーブルが期待する形式に合わせるための処理です。

この順序では、`nacladdr`が先に実行されることで、`CMPPS`命令の第3オペランドが、まだ`obj.TYPE_CONST`に書き換えられる前の状態（`obj.TYPE_MEM`と認識される状態）で処理されてしまう可能性がありました。その結果、`nacladdr`が誤った変換を行ったり、あるいはその後の`CMPPS`命令の書き換え処理が期待通りに機能しなくなるという問題が発生しました。

このコミットでは、これらの処理の順序を入れ替えることで、この問題を解決しています。新しい順序は以下の通りです。

1.  **`CMPPS`命令のオペランド書き換え処理**: まず、`CMPPS`などの命令の第3オペランドが即値0である場合に、その型を`obj.TYPE_CONST`に正しく書き換えます。
2.  **NaClアドレス変換処理**: その後、`nacladdr`関数が呼び出され、既に正しく`obj.TYPE_CONST`として設定されたオペランドに対して、NaCl特有のアドレス変換が適用されます。

この変更により、`nacladdr`は常に正しい形式のオペランドを処理するようになり、`nacl/amd64p32`ターゲットでのコード生成の正確性が保証されます。

## コアとなるコードの解説

変更前は、`nacladdr`を呼び出すブロックが先にあり、その後に`CMPPS`などの命令のオペランドを書き換えるブロックがありました。

```go
// 変更前:
// 1. nacladdr 呼び出し
if ctxt.Headtype == obj.Hnacl && p.Mode == 64 {
    nacladdr(ctxt, p, &p.From)
    nacladdr(ctxt, p, &p.To)
}
// 2. CMPPS など命令のオペランド書き換え
switch p.As {
case ACMPPD, ACMPPS, ACMPSD, ACMPSS:
    if p.To.Type == obj.TYPE_MEM && p.To.Name == obj.NAME_NONE && p.To.Reg == REG_NONE && p.To.Index == REG_NONE && p.To.Sym == nil {
        p.To.Type = obj.TYPE_CONST
    }
}
```

この順序では、`nacladdr`が実行される時点で、`CMPPS`命令の第3オペランドがまだ`obj.TYPE_MEM`として扱われる可能性がありました。しかし、アセンブラのテーブルは、このオペランドが`obj.TYPE_CONST`であることを期待していました。そのため、`nacladdr`が誤った形式のオペランドを処理しようとしたり、その後の`CMPPS`の書き換えが正しく適用されなかったりする問題が発生しました。

変更後は、これらのブロックの順序が入れ替わりました。

```go
// 変更後:
// 1. CMPPS など命令のオペランド書き換え
switch p.As {
case ACMPPD, ACMPPS, ACMPSD, ACMPSS:
    if p.To.Type == obj.TYPE_MEM && p.To.Name == obj.NAME_NONE && p.To.Reg == REG_NONE && p.To.Index == REG_NONE && p.To.Sym == nil {
        p.To.Type = obj.TYPE_CONST
    }
}
// 2. nacladdr 呼び出し
if ctxt.Headtype == obj.Hnacl && p.Mode == 64 {
    nacladdr(ctxt, p, &p.From)
    nacladdr(ctxt, p, &p.To)
}
```

この新しい順序では、まず`CMPPS`などの命令の第3オペランドが、アセンブラのテーブルが期待する`obj.TYPE_CONST`に正しく書き換えられます。その後、`nacladdr`が呼び出されるため、`nacladdr`は常に正しい形式のオペランドを処理することができ、`nacl/amd64p32`ターゲット向けのコード生成が正確に行われるようになりました。これは、依存関係のある処理の実行順序を正しくすることで、コンパイラのバグを修正する典型的な例です。

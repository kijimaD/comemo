# [インデックス 23723] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるライトバリアの有効化タイミングに関する修正です。具体的には、GCの「スキャンフェーズ」中にライトバリアを有効にすることで、スタックバリアとライトバリア間の同期の問題を解決し、スタックへの変更がGCによって正しく追跡されるようにします。

## コミット

このコミットは、Goランタイムのガベージコレクタの動作を改善し、特にスタックの走査とライトバリアの連携を強化することを目的としています。これにより、GCの正確性と堅牢性が向上します。

    runtime: enable write barriers during concurrent scan
    
    Currently, write barriers are only enabled after completion of the
    concurrent scan phase, as we enter the concurrent mark phase. However,
    stack barriers are installed during the scan phase and assume that
    write barriers will track changes to frames above the stack
    barriers. Since write barriers aren't enabled until after stack
    barriers are installed, we may miss modifications to the stack that
    happen after installing the stack barriers and before enabling write
    barriers.
    
    Fix this by enabling write barriers during the scan phase.
    
    This commit intentionally makes the minimal change to do this (there's
    only one line of code change; the rest are comment changes). At the
    very least, we should consider eliminating the ragged barrier that's
    intended to synchronize the enabling of write barriers, but now just
    wastes time. I've included a large comment about extensions and

## 変更の背景

Goのガベージコレクションは、プログラムの実行と並行して動作する「並行GC」を採用しています。このGCプロセスは複数のフェーズに分かれており、その中に「スキャンフェーズ (`_GCscan`)」と「マークフェーズ (`_GCmark`)」があります。

従来のGoランタイムでは、ライトバリア（Write Barrier）は並行スキャンフェーズの完了後、並行マークフェーズに入る際に初めて有効化されていました。しかし、スタックバリア（Stack Barrier）はスキャンフェーズ中にインストールされます。スタックバリアは、それより上位のスタックフレームへの変更がライトバリアによって追跡されることを前提として設計されています。

この前提と実際のライトバリアの有効化タイミングとの間に不一致がありました。具体的には、スタックバリアがインストールされた後からライトバリアが有効になるまでの間に、スタックに対して行われた変更がGCによって見落とされてしまう可能性があったのです。これは、GCの正確性を損なう重大な問題につながる可能性があります。

このコミットは、この同期のずれを解消し、GCの正確性を保証するために、スキャンフェーズ中にライトバリアを有効化するように変更されました。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションにおける以下の概念を理解しておく必要があります。

1.  **ガベージコレクション (GC)**:
    *   プログラムが動的に確保したメモリのうち、もはや到達不可能になった（使われなくなった）領域を自動的に解放する仕組みです。Goは「マーク＆スイープ」方式をベースとした並行GCを採用しています。
    *   **並行GC**: プログラムの実行（ミューテータ）とGCの実行（コレクタ）が同時に行われるGCです。これにより、プログラムの一時停止時間（Stop-The-World, STW）を最小限に抑え、アプリケーションの応答性を向上させます。

2.  **GCフェーズ**:
    *   GoのGCは複数のフェーズに分かれて実行されます。
        *   `_GCoff`: GCが実行されていない状態。ライトバリアは無効。
        *   `_GCscan`: ルートオブジェクト（グローバル変数、スタック上の変数など）を走査し、到達可能なオブジェクトを特定するフェーズ。このフェーズでスタックバリアがインストールされます。
        *   `_GCmark`: スキャンフェーズで特定されたオブジェクトからポインタをたどり、到達可能なすべてのオブジェクトをマークするフェーズ。
        *   `_GCmarktermination`: マークフェーズの終了処理。
        *   `_GCsweep`: マークされなかった（到達不可能な）オブジェクトのメモリを解放するフェーズ。

3.  **ライトバリア (Write Barrier)**:
    *   並行GCにおいて、ミューテータ（ユーザープログラム）がオブジェクトのポインタを書き換える際に実行される特別なコードです。
    *   その目的は、GCがオブジェクトグラフを走査している最中に、ミューテータがポインタを書き換えることで、GCが見落としてしまうオブジェクト（「見失われたオブジェクト」または「破棄されたオブジェクト」）が発生するのを防ぐことです。
    *   GoのGCは「Dijkstraの三色マーク」アルゴリズムをベースにしており、オブジェクトを白（未訪問）、灰（訪問済みだが子を未走査）、黒（訪問済みで子も走査済み）のいずれかの色で分類します。ライトバリアは、ミューテータがポインタを書き換える際に、この三色不変条件（黒から白へのポインタは存在しない）を維持するために使用されます。

4.  **スタックバリア (Stack Barrier)**:
    *   GoのGCは、実行中のゴルーチン（スタック）もルートとして走査します。スタックは頻繁に変化するため、GCがスタックを走査する際に、その変更を効率的に追跡する必要があります。
    *   スタックバリアは、GCがスタックを走査する際に、特定のスタックフレームに「バリア」を設置するような概念です。これにより、GCがスタックのどの部分を既に走査したか、どの部分が変更された可能性があるかを追跡しやすくなります。
    *   コミットメッセージにあるように、スタックバリアは、それより上位のスタックフレームへの書き込みがライトバリアによって捕捉されることを前提としています。

5.  **Ragged Barrier**:
    *   GCフェーズの切り替え時に、すべてのプロセッサ（P）が新しいGCフェーズの状態を認識し、それに応じた動作（例えばライトバリアの有効化）を開始するまで待機するメカニズムです。
    *   「Ragged」とは、すべてのPが同時にバリアを通過するのではなく、それぞれのPが自身のタイミングでバリアを通過することを意味します。これにより、STW時間を短縮できますが、すべてのPが新しい状態に移行するまでには時間差が生じます。

## 技術的詳細

このコミットの核心は、Goの並行GCにおけるライトバリアの有効化タイミングの変更です。

従来のGCサイクルでは、以下の順序で処理が進んでいました。

1.  **`_GCoff` から `_GCscan` への移行**: GCが開始され、ルートの走査が始まります。このフェーズでスタックバリアがインストールされます。しかし、この時点ではライトバリアはまだ有効になっていませんでした。
2.  **`_GCscan` から `_GCmark` への移行**: このフェーズで初めてライトバリアが有効化されます。

問題は、`_GCscan` フェーズ中にスタックバリアがインストールされるにもかかわらず、ライトバリアが有効になっていない期間が存在したことです。スタックバリアは、それより上位のスタックフレームへの書き込みがライトバリアによって追跡されることを前提としています。この前提が崩れると、`_GCscan` フェーズ中にスタックフレームが変更された場合、その変更がGCによって見落とされ、誤って解放されるべきでないオブジェクトが解放されたり、逆に解放されるべきオブジェクトが解放されなかったりする可能性がありました。

このコミットは、この問題を解決するために、`_GCscan` フェーズへの移行時にライトバリアを有効化するように変更しました。これにより、スタックバリアがインストールされる時点からライトバリアが常に有効になり、スタックへのすべての変更がGCによって正しく追跡されるようになります。

コミットメッセージでは、この変更が「最小限の変更」であると強調されています。これは、既存のGCロジックに大きな変更を加えることなく、ライトバリアの有効化タイミングを調整するだけで問題を解決したことを意味します。また、将来的な改善点として、ライトバリアの有効化を同期するための「ragged barrier」の必要性を見直すことや、スタックへの書き込みのみに特化したライトバリアを導入する可能性についても言及されています。

## コアとなるコードの変更箇所

変更は主に `src/runtime/mgc.go` ファイルに集中しています。

1.  **`setGCPhase` 関数の変更**:
    *   `writeBarrierEnabled` 変数の設定ロジックが変更されました。
    *   変更前: `writeBarrierEnabled = gcphase == _GCmark || gcphase == _GCmarktermination`
    *   変更後: `writeBarrierEnabled = gcphase == _GCmark || gcphase == _GCmarktermination || gcphase == _GCscan`
    *   これにより、`_GCscan` フェーズ中もライトバリアが有効になるようになりました。

2.  **`_GCscan` 定義のコメント変更**:
    *   `_GCscan` 定義のコメントが「write barrier disabled」から「write barrier ENABLED」に変更されました。これは、コードの変更を反映したドキュメントの更新です。

3.  **`gc` 関数内のコメント追加**:
    *   `setGCPhase(_GCscan)` の呼び出し箇所に、ライトバリアを有効にする理由と、将来的な改善に関する詳細なコメントが追加されました。このコメントは、この変更の背景と、今後のGC設計の方向性を示唆しています。

## コアとなるコードの解説

### `setGCPhase` 関数

```go
//go:nosplit
func setGCPhase(x uint32) {
	atomicstore(&gcphase, x)
	writeBarrierEnabled = gcphase == _GCmark || gcphase == _GCmarktermination || gcphase == _GCscan
}
```

この関数は、現在のGCフェーズを設定します。`atomicstore(&gcphase, x)` は、GCフェーズをアトミックに更新します。最も重要な変更は `writeBarrierEnabled` の行です。

*   `writeBarrierEnabled` は、グローバルなブール変数で、ライトバリアが現在有効であるかどうかを示します。
*   変更前は、`_GCmark` または `_GCmarktermination` フェーズでのみ `true` に設定されていました。
*   変更後は、`_GCscan` フェーズでも `true` に設定されるようになりました。

この一行の変更が、`_GCscan` フェーズ中にスタックバリアがインストールされる際に、ライトバリアも同時に有効になることを保証します。これにより、スタックバリアが前提とする「上位フレームへの書き込みがライトバリアによって追跡される」という条件が満たされるようになります。

### `gc` 関数内のコメント

```go
		systemstack(func() {
			// Enter scan phase. This enables write
			// barriers to track changes to stack frames
			// above the stack barrier.
			//
			// TODO: This has evolved to the point where
			// we carefully ensure invariants we no longer
			// depend on. Either:
			//
			// 1) Enable full write barriers for the scan,
			// but eliminate the ragged barrier below
			// (since the start the world ensures all Ps
			// have observed the write barrier enable) and
			// consider draining during the scan.
			//
			// 2) Only enable write barriers for writes to
			// the stack at this point, and then enable
			// write barriers for heap writes when we
			// enter the mark phase. This means we cannot
			// drain in the scan phase and must perform a
			// ragged barrier to ensure all Ps have
			// enabled heap write barriers before we drain
			// or enable assists.
			//
			// 3) Don't install stack barriers over frame
			// boundaries where there are up-pointers.
			setGCPhase(_GCscan)
```

このコメントは、`_GCscan` フェーズに入る際にライトバリアを有効にする理由を明確に説明しています。すなわち、「スタックバリアより上位のスタックフレームへの変更を追跡するためにライトバリアを有効にする」という目的です。

さらに、`TODO` コメントとして、この変更がGCの設計に与える影響と、将来的な最適化の可能性について議論しています。

1.  **Ragged Barrierの排除**: `_GCscan` フェーズでライトバリアが有効になることで、GCの開始時にすべてのPがライトバリアの有効化を認識する「start the world」が保証されるため、後続の「ragged barrier」が不要になる可能性があります。これにより、無駄な時間消費を削減できるかもしれません。
2.  **スタック専用ライトバリア**: `_GCscan` フェーズでは、スタックへの書き込みのみを追跡するライトバリアを有効にし、ヒープへの書き込みに関するライトバリアは `_GCmark` フェーズで有効にするという、より粒度の細かい制御の可能性が示唆されています。これは、GCのオーバーヘッドをさらに削減するための最適化の方向性です。
3.  **スタックバリアの設計変更**: スタックバリアの設置方法自体を見直し、アップポインタが存在するフレーム境界にスタックバリアをインストールしないという根本的な設計変更の可能性も示唆されています。

これらのコメントは、このコミットが単なるバグ修正だけでなく、Go GCの進化における重要な一歩であり、将来の最適化のための基盤を築いていることを示しています。

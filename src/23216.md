# [インデックス 23216] ファイルの概要

このコミットは、Goランタイムのガベージコレクション (GC) スケジューリングロジックを改善し、GC作業をより積極的に前倒しで実行するように変更します。これにより、ライトバリアが有効になる期間を短縮し、特に `GOMAXPROCS` が小さい環境でのアプリケーションの実行性能（Mutatorの速度）を向上させることを目的としています。

## コミット

```
runtime: schedule GC work more aggressively

Schedule the work as early as possible, while still respecting the
utilization percentage on average. The old code tried never to
go above the utilization percentage. The new code is willing
to go above the utilization percentage by one time slice
(but of course after doing that it must wait until the percentage
drops back down to the target before it gets another time slice).

The effect is that for concurrent GCs that can run in a small number
of time slices, the time during which write barriers are enabled is
reduced by one mutator + GC time slice round (possibly 30 ms per GC).

This only affects the fractional GC processor (the remainder of GOMAXPROCS/4),
so it matters most in GOMAXPROCS=1, a bit in GOMAXPROCS=2, and not at
all in GOMAXPROCS=4.
```

## 変更の背景

Goのガベージコレクション (GC) は、アプリケーションの実行と並行して動作するコンカレントGCを採用しています。このGCサイクル中、Mutator（アプリケーションコード）がヒープ上のオブジェクトグラフを変更する際に、GCの正確性を保つために「ライトバリア (write barrier)」が有効になります。ライトバリアが有効な間は、Mutatorの実行速度が低下する可能性があります。

以前のGCスケジューリングロジックでは、GCがCPU時間全体に占める割合（GC利用率）を厳密に目標値以下に保とうとしていました。この保守的なアプローチは、GC作業の開始を遅らせる傾向があり、結果としてライトバリアが有効な期間が長くなっていました。特に、GC作業が少数のタイムスライスで完了するようなケースでは、この遅延が顕著でした。

このコミットの目的は、GC作業を可能な限り早期に開始し、ライトバリアが有効な期間を短縮することです。これにより、Mutatorがより高速に動作できる時間を増やし、アプリケーション全体のパフォーマンス、特にレイテンシを改善することを目指しています。平均的なGC利用率の目標は維持しつつ、一時的に目標を超えてでもGC作業を前倒しで実行する、より積極的なスケジューリング戦略が導入されました。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に以下の特徴を持つコンカレントなマーク＆スイープ方式を採用しています。

*   **コンカレントGC**: アプリケーションの実行（Mutator）と並行してGC作業が進行します。これにより、アプリケーションの一時停止（Stop-The-World, STW）時間を最小限に抑え、レイテンシを低減します。
*   **トライカラーマーキング (Tri-color Marking)**: オブジェクトを白、灰、黒の3色で分類し、到達可能性をマークするアルゴリズムです。
    *   **白**: GCによってまだ到達可能とマークされていないオブジェクト（回収候補）。
    *   **灰**: 到達可能とマークされたが、その参照先がまだスキャンされていないオブジェクト。
    *   **黒**: 到達可能とマークされ、その参照先もすべてスキャンされたオブジェクト。
*   **ライトバリア (Write Barrier)**: GCのマークフェーズ中にMutatorがヒープ上のポインタを更新する際に実行される小さなコードスニペットです。Mutatorがオブジェクトグラフを変更してもGCの正確性が損なわれないように、特定のルール（例: Dijkstraの三色不変条件）を維持するために使用されます。ライトバリアが有効な間は、Mutatorの実行にオーバーヘッドが発生します。
*   **GC利用率 (GC Utilization)**: GCがCPU時間全体に占める割合を示す指標です。Goランタイムは、この利用率を特定の目標値（例: 25%）に保つようにGCの作業量を調整します。

### GCの目標

GoのGCは、以下のバランスを取ることを目指しています。

*   **低レイテンシ**: アプリケーションの一時停止時間を短くし、ユーザー体験を向上させます。
*   **高スループット**: GCによるオーバーヘッドを最小限に抑え、アプリケーションが本来の処理に使えるCPU時間を最大化します。

### GOMAXPROCS

`GOMAXPROCS` 環境変数は、Goランタイムが同時に実行できるOSスレッドの最大数を制御します。これは、GoスケジューラがゴルーチンをOSスレッドにマッピングする際に利用されます。`GOMAXPROCS` の値が小さい場合、利用可能なCPUリソースが限られるため、GCスケジューリングの決定がアプリケーションのパフォーマンスに与える影響が大きくなります。

### Mutator

Mutatorとは、ガベージコレクタの文脈で、アプリケーションのコード自体を指します。Mutatorはヒープ上のオブジェクトを生成したり、既存のオブジェクトへの参照を変更したりすることで、オブジェクトグラフを「変更 (mutate)」します。

### Time Slice

GoスケジューラがゴルーチンにCPU時間を割り当てる際の最小単位です。ゴルーチンは、このタイムスライス内で実行され、その後、他のゴルーチンにCPUが譲られます。

## 技術的詳細

このコミットの核心は、GoランタイムのGCスケジューリングポリシーの変更にあります。

### 旧アプローチの問題点

以前のGCスケジューリングでは、GCワーカー（GC作業を実行するゴルーチン）がCPUを利用する際に、GC利用率の目標を厳密に超えないように制御していました。具体的には、GCワーカーが次のタイムスライスで作業を実行した場合に、GC利用率が目標値を超過するかどうかを事前にチェックしていました。もし超過する見込みがあれば、GC作業を遅らせ、MutatorにCPUを譲っていました。

このアプローチは、平均的なGC利用率を目標値に保つという点では正確でしたが、GC作業が後回しにされることで、ライトバリアが有効な期間が不必要に長くなるという副作用がありました。ライトバリアが有効な間はMutatorの実行速度が低下するため、これはアプリケーションのレイテンシに悪影響を与えていました。特に、GC作業が比較的短時間で完了するようなケースでは、MutatorがGC作業の「支払い」をするために十分なタイムスライスを実行するまでGC作業が待機させられることになり、非効率でした。

### 新アプローチ

新しいアプローチでは、GCワーカーは「現在、GC利用率が目標以下または目標値であれば、積極的にGC作業を行う」というポリシーに変更されました。つまり、一時的にGC利用率が目標値をわずかに超える可能性があっても、1タイムスライス分のGC作業を前倒しで実行することを許容します。

この変更の意図は以下の通りです。

1.  **GC作業の前倒し**: GC作業を早期に実行することで、GCサイクル全体の完了を早めます。
2.  **ライトバリア期間の短縮**: GCサイクルが早く完了すれば、ライトバリアが有効である期間も短縮されます。これにより、Mutatorはより長い期間、ライトバリアによるオーバーヘッドなしで高速に実行できるようになります。
3.  **平均利用率の維持**: GC作業を前倒しで実行した後、GC利用率が目標値を超過した場合は、次のGCタイムスライスが割り当てられるまでMutatorにCPUを譲ることで、平均的なGC利用率は依然として目標値に収束するように調整されます。つまり、GCの総作業量は変わらず、その作業のタイミングが最適化されるだけです。

### `GOMAXPROCS` の影響

コミットメッセージにも記載されている通り、この変更は特に `GOMAXPROCS` が小さい環境で大きな影響を与えます。

*   **`GOMAXPROCS=1`**: GCワーカーが利用できるCPUリソースが非常に限られているため、GCスケジューリングのわずかな変更が全体のパフォーマンスに大きく影響します。ベンチマーク結果でも、`GobDecode` や `JSONEncode` など、GC負荷が高い処理で大幅な改善が見られます。
*   **`GOMAXPROCS=2`**: ある程度の効果が見られます。
*   **`GOMAXPROCS=4`**: ほとんど影響がありません。これは、`GOMAXPROCS` が十分に大きい場合、GCワーカーが利用できるCPUリソースが豊富であり、フラクショナルGCプロセッサ（`GOMAXPROCS/4` の余り）のスケジューリング調整が全体に与える影響が小さいためと考えられます。

### `gcForcePreemptNS`

コード内のコメントで `gcForcePreemptNS` という定数が言及されていますが、このコミットでは `0` に設定されており、新しい積極的なスケジューリング挙動がデフォルトとなっています。これは、以前の保守的な挙動に戻すためのフックとして残されている可能性がありますが、このコミットの時点では使用されていません。

## コアとなるコードの解説

### `gcControllerState.endCycle()` の変更

このメソッドはGCサイクルの終了時に呼び出され、次回のGCトリガーを調整するために現在のGC利用率などを計算します。

*   **変更前**: `duration <= 0` の場合にゼロ除算を避けるための特殊なロジックがあり、その場合は `gcGoalUtilization` を直接 `utilization` に設定していました。それ以外の場合は、`c.assistTime` (MutatorがGCを手伝った時間)、`c.dedicatedMarkTime` (専用GCワーカーの時間)、`c.fractionalMarkTime` (フラクショナルGCワーカーの時間) の合計を `duration * gomaxprocs` で割って利用率を計算していました。
*   **変更後**: まず `utilization` を `gcGoalUtilization` で初期化し、バックグラウンドマークが利用率目標を達成したと仮定します。次に、`duration > 0` の場合にのみ、`c.assistTime` による利用率を既存の `utilization` に加算します。この変更は、GCの全体的な負荷をより正確に評価し、特にMutatorがGCを手伝った時間も利用率計算に含めることで、次回のGCトリガーの調整をより適切に行うことを意図しています。

### `gcControllerState.findRunnableGCWorker()` の変更

このメソッドは、GCワーカーとして実行可能なゴルーチンを見つける役割を担っており、GCスケジューリングの核心部分です。

*   **変更前**: コメントアウトされた古いロジックでは、GCワーカーが次のタイムスライス（`forcePreemptNS` 期間）で作業を実行した場合に、その時点でのGC利用率が `c.fractionalUtilizationGoal` を超えないかどうかをチェックしていました。もし超える見込みがあれば、GCワーカーは実行されず、MutatorにCPUが譲られていました。これは、GC利用率の目標を厳密に守ろうとする保守的なアプローチでした。
*   **変更後**: 新しいロジックでは、`gcForcePreemptNS` が `0` に設定され、GCワーカーは「現在、GC利用率が目標以下または目標値であれば、積極的にGC作業を行う」というポリシーに変更されました。
    *   新しいコメントで詳細に説明されているように、以前のアプローチはGC作業を遅らせ、MutatorがGC作業の「支払い」をするまで待機させていました。この間、ライトバリアが有効なためMutatorは低速で動作していました。
    *   新しいアプローチでは、GC作業を前倒しで実行することで、GCサイクルを早期に完了させ、ライトバリアが有効な期間を短縮します。これにより、Mutatorはより長い期間、高速に動作できるようになります。
    *   GCの総利用率の平均は変わらないものの、GC作業のタイミングを最適化することで、アプリケーションの体感性能（特にレイテンシ）が向上します。

この変更は、GCの「支払い」を後回しにするのではなく、積極的に前倒しで実行することで、Mutatorの実行を妨げるライトバリアの期間を最小限に抑えるという、GoランタイムのGC設計思想の進化を示しています。

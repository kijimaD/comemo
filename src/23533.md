# [インデックス 23533] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるライトバリア（write barrier）の実装に関するバグ修正です。具体的には、`callwritebarrier`関数がヒープ上のメモリ領域をスキャンする際に、誤った範囲を指定していた問題を修正しています。このバグは、GCが解放されるべきオブジェクトを誤って保持してしまう可能性があり、特定の条件下ではクラッシュを引き起こすこともありました。

    Given a call frame F of size N where the return values start at offset R,
    callwritebarrier was instructing heapBitsBulkBarrier to scan the block
    of memory [F+R, F+R+N). It should only scan [F+R, F+N). The extra N-R
    bytes scanned might lead into the next allocated block in memory.
    Because the scan was consulting the heap bitmap for type information,
    scanning into the next block normally "just worked" in the sense of
    not crashing.
    
    Scanning the extra N-R bytes of memory is a problem mainly because
    it causes the GC to consider pointers that might otherwise not be
    considered, leading it to retain objects that should actually be freed.
    This is very difficult to detect.
    
    Luckily, juju turned up a case where the heap bitmap and the memory
    were out of sync for the block immediately after the call frame, so that
    heapBitsBulkBarrier saw an obvious non-pointer where it expected a
    pointer, causing a loud crash.
    
    Why is there a non-pointer in memory that the heap bitmap records as
    a pointer? That is more difficult to answer. At least one way that it
    could happen is that allocations containing no pointers at all do not
    update the heap bitmap. So if heapBitsBulkBarrier walked out of the
    current object and into a no-pointer object and consulted those bitmap
    bits, it would be misled. This doesn't happen in general because all
    the paths to heapBitsBulkBarrier first check for the no-pointer case.
    This may or may not be what happened, but it's the only scenario
    I've been able to construct.
    
    I tried for quite a while to write a simple test for this and could not.
    It does fix the juju crash, and it is clearly an improvement over the
    old code.

## 元コミット内容

Goランタイムにおける`callwritebarrier`関数のバグを修正します。

関数呼び出しフレーム`F`があり、そのサイズが`N`、戻り値がオフセット`R`から始まる場合、`callwritebarrier`は`heapBitsBulkBarrier`に対してメモリブロック`[F+R, F+R+N)`をスキャンするように指示していました。しかし、正しくは`[F+R, F+N)`をスキャンすべきでした。余分にスキャンされた`N-R`バイトは、メモリ上の次の割り当て済みブロックにまで及んでしまう可能性がありました。スキャンは型情報のためにヒープビットマップを参照していたため、次のブロックにスキャンが及んでも、通常はクラッシュせずに「たまたま動作していた」という状況でした。

この余分な`N-R`バイトのメモリをスキャンすることは、主にGCが本来考慮すべきでないポインタを考慮してしまい、結果として解放されるべきオブジェクトが保持され続けてしまう（メモリリーク）という問題を引き起こします。この種のバグは非常に検出が困難です。

幸運にも、jujuプロジェクトが、コールフレームの直後のブロックでヒープビットマップと実際のメモリ内容が同期していないケースを発見しました。これにより、`heapBitsBulkBarrier`がポインタを期待する場所で明らかにポインタではない値を見つけ、大きなクラッシュを引き起こしました。

なぜヒープビットマップがポインタと記録している場所にポインタではない値が存在するのかは、より難しい問題です。考えられる一つの原因として、ポインタを全く含まないアロケーションはヒープビットマップを更新しないという点が挙げられます。したがって、`heapBitsBulkBarrier`が現在のオブジェクトの範囲を超えて、ポインタを含まないオブジェクトにまでスキャンが及んでしまい、そのビットマップ情報を参照した場合、誤った判断をしてしまう可能性があります。通常、`heapBitsBulkBarrier`へのすべてのパスは、まずポインタを含まないケースをチェックするため、このような事態は発生しません。これが実際に起こったことかどうかは不明ですが、これが唯一構築できたシナリオです。

この問題に対する単純なテストケースを作成しようとしましたが、長い間試してもできませんでした。しかし、この修正はjujuのクラッシュを解決し、以前のコードよりも明らかに改善されています。

Issue #10844を修正します。

## 変更の背景

Goのガベージコレクションは、プログラムの実行中に不要になったメモリを自動的に解放する重要な機能です。このGCは、オブジェクトが参照されているかどうかを追跡するために「ライトバリア」というメカニズムを使用します。ライトバリアは、ポインタが変更されるたびにGCに通知し、ヒープ上のオブジェクトグラフの整合性を保つ役割を担います。

このコミットで修正された問題は、`callwritebarrier`という特定のライトバリア関数が、関数呼び出しの戻り値領域をスキャンする際に、誤ったメモリ範囲を`heapBitsBulkBarrier`に渡していたことに起因します。具体的には、関数フレームの戻り値が格納されるべき領域を超えて、隣接するメモリブロックまでスキャンしてしまっていました。

この「過剰なスキャン」は、通常はクラッシュを引き起こしませんでした。なぜなら、Goのヒープビットマップはメモリ上の各ワードがポインタであるか否かの情報を持っているため、たとえ誤った領域をスキャンしても、ビットマップが「これはポインタではない」と示せば、GCはそれを無視するからです。しかし、この過剰なスキャンは、GCが本来到達不能であるはずのオブジェクトへのポインタを誤って発見し、そのオブジェクトを解放せずに保持し続けてしまうという、いわゆる「メモリリーク」を引き起こす可能性がありました。このようなメモリリークは、プログラムの動作には影響を与えないため、非常に発見が困難です。

しかし、jujuプロジェクトで発生した特定のクラッシュは、この潜在的な問題を顕在化させました。このクラッシュは、ヒープビットマップがポインタであると示しているにもかかわらず、実際のメモリ内容がポインタではないという矛盾が生じたために発生しました。これは、ヒープビットマップの更新が不完全な、ポインタを含まないオブジェクトの領域にまでスキャンが及んだ場合に起こりうる状況でした。

このコミットは、この根本的なスキャン範囲の誤りを修正し、GCの正確性と安定性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念について知っておく必要があります。

1.  **ガベージコレクション (GC) とライトバリア (Write Barrier)**:
    *   GoのGCは、並行マーク＆スイープ方式を採用しています。プログラムの実行と並行してGCが動作し、一時停止時間を最小限に抑えます。
    *   GCが正確に動作するためには、プログラムがヒープ上のポインタを変更する際に、GCにその変更を通知する必要があります。この通知メカニズムが「ライトバリア」です。
    *   ライトバリアは、ポインタの書き込み操作（例: `obj.field = new_ptr`）の前後で実行される小さなコードスニペットで、GCがオブジェクトグラフの変更を追跡し、マークフェーズ中にすべての到達可能なオブジェクトを正しく識別できるようにします。
    *   `callwritebarrier`は、特定の状況下（例えば、関数呼び出しの戻り値がヒープに書き込まれる可能性のある場合）で、GCがスキャンすべきメモリ領域を特定し、ライトバリア処理をトリガーするために使用される関数の一つです。

2.  **ヒープビットマップ (Heap Bitmap)**:
    *   Goのランタイムは、ヒープメモリの各ワード（通常は8バイト）がポインタであるか、非ポインタであるかを記録する「ヒープビットマップ」を維持しています。
    *   このビットマップは、GCがヒープをスキャンする際に、どのメモリ位置をポインタとして解釈し、さらに辿るべきかを効率的に判断するために使用されます。これにより、GCは型情報なしにポインタを正確に識別できます。
    *   ポインタを含まないオブジェクト（例: `int`のスライスや`byte`の配列など）の場合、その領域に対応するヒープビットマップは「ポインタなし」とマークされます。

3.  **コールフレーム (Call Frame) とスタック (Stack)**:
    *   関数が呼び出されると、その関数に必要な情報（引数、ローカル変数、戻りアドレスなど）を格納するために、スタック上に「コールフレーム」が作成されます。
    *   Goでは、関数の戻り値もこのコールフレームの一部としてスタック上に配置されることがあります。
    *   `F`はコールフレームの開始アドレス、`N`はそのフレームの合計サイズ、`R`は戻り値がフレーム内で始まるオフセットを指します。

4.  **`unsafe.Pointer` と `uintptr`**:
    *   `unsafe.Pointer`は、任意の型のポインタを保持できる特殊な型で、Goの型システムをバイパスしてメモリを直接操作するために使用されます。C言語の`void*`に似ています。
    *   `uintptr`は、ポインタを整数として表現する型です。`unsafe.Pointer`と`uintptr`の間で相互変換が可能ですが、`uintptr`はポインタの算術演算を行うために使用され、GCは`uintptr`をポインタとして認識しません（`unsafe.Pointer`に変換し直さない限り）。
    *   ランタイムコードでは、メモリのアドレス計算やサイズ指定にこれらの型が頻繁に用いられます。

5.  **`heapBitsBulkBarrier`**:
    *   これは、指定されたメモリブロック内のポインタをスキャンし、GCのライトバリア処理を実行する低レベルの関数です。ヒープビットマップを参照して、どのワードがポインタであるかを判断します。

## 技術的詳細

問題の核心は、`callwritebarrier`関数が`heapBitsBulkBarrier`を呼び出す際の引数にありました。

元のコードでは、`callwritebarrier`は以下のように`heapBitsBulkBarrier`を呼び出していました。

```go
heapBitsBulkBarrier(uintptr(add(frame, retoffset)), framesize)
```

ここで:
*   `frame`はコールフレームの開始アドレス。
*   `retoffset`はコールフレーム内で戻り値が始まるオフセット。
*   `framesize`はコールフレーム全体のサイズ。

したがって、`uintptr(add(frame, retoffset))`は戻り値の開始アドレスを示します。
そして、`framesize`がスキャンするバイト数として渡されていました。

これにより、`heapBitsBulkBarrier`はメモリ範囲 `[戻り値の開始アドレス, 戻り値の開始アドレス + framesize)` をスキャンすることになります。
しかし、戻り値が始まるオフセット`R`から、フレームの終わり`N`までの領域をスキャンすべきでした。つまり、スキャンすべきサイズは`framesize - retoffset`であるべきでした。

元のコードでは、スキャン範囲の終端が `F + R + N` となっていましたが、正しくは `F + N` でした。この `N-R` バイトの差分が、コールフレームの終端を超えて、次のメモリブロックにまでスキャンが及ぶ原因となっていました。

この過剰なスキャンが問題となるのは、以下の理由からです。

1.  **メモリリークの可能性**: スキャンが隣接するブロックに及んだ場合、そのブロック内に存在する、本来は現在のオブジェクトグラフから到達不能であるはずのポインタをGCが誤って発見してしまう可能性があります。これにより、GCはそれらのオブジェクトを「まだ参照されている」と判断し、解放せずに保持し続けてしまいます。これはメモリリークにつながります。
2.  **クラッシュの可能性**: 通常、ヒープビットマップが正しく設定されていれば、隣接ブロックをスキャンしても、ビットマップが「ポインタではない」と示すため、クラッシュには至りません。しかし、特定の条件下（特にポインタを含まないオブジェクトのアロケーションでヒープビットマップの更新が不完全な場合など）で、ビットマップがポインタであると誤って示しているにもかかわらず、実際のメモリ内容がポインタではない場合、`heapBitsBulkBarrier`が不正なポインタをデリファレンスしようとしてクラッシュする可能性があります。jujuで発生したクラッシュは、まさにこのシナリオに該当すると考えられます。

修正は、`heapBitsBulkBarrier`に渡すサイズを`framesize`から`framesize - retoffset`に変更することで、スキャン範囲を戻り値が格納されている実際の領域に限定しています。

また、`src/runtime/mbitmap.go`と`src/runtime/mheap.go`には、この変更に関連するコメントの追加と修正が行われています。
`src/runtime/mbitmap.go`では、`heapBitsBulkBarrier`の呼び出し元が、ポインタを含まないアロケーションに対しては事前にチェックを行うべきであるという注意書きが追加されました。これは、ポインタを含まないアロケーションではヒープビットマップが維持されないため、`heapBitsBulkBarrier`が誤ったビットマップ情報を参照するのを防ぐためです。
`src/runtime/mheap.go`では、`inheap`関数がライトバリアによって使用されるため、`//go:nowritebarrier`と`//go:nosplit`ディレクティブが追加され、GCの整合性を保つための制約が明示されています。

## コアとなるコードの解説

### `src/runtime/mbarrier.go` の変更

このファイルでは、`callwritebarrier`関数の`heapBitsBulkBarrier`呼び出しにおける第2引数が変更されています。

*   **変更前**: `heapBitsBulkBarrier(uintptr(add(frame, retoffset)), framesize)`
    *   `framesize`がスキャンサイズとして渡されていました。これはコールフレーム全体のサイズであり、戻り値が始まるオフセット`retoffset`から計算すると、フレームの終端を超えて余分な領域までスキャンしてしまう可能性がありました。
*   **変更後**: `heapBitsBulkBarrier(uintptr(add(frame, retoffset)), framesize-retoffset)`
    *   スキャンサイズが`framesize-retoffset`に変更されました。これにより、スキャンは`frame + retoffset`（戻り値の開始アドレス）から始まり、`frame + retoffset + (framesize - retoffset)`、つまり`frame + framesize`（コールフレームの終端）までの正確な範囲に限定されます。この修正により、不要なメモリ領域のスキャンが防止され、メモリリークやクラッシュのリスクが排除されます。

### `src/runtime/mbitmap.go` の変更

このファイルでは、`heapBitsBulkBarrier`関数のコメントに重要な追記がされています。

*   **追加されたコメント**:
    ```go
    // The heap bitmap is not maintained for allocations containing
    // no pointers at all; any caller of heapBitsBulkBarrier must first
    // make sure the underlying allocation contains pointers, usually
    // by checking typ.kind&kindNoPointers.
    ```
    このコメントは、`heapBitsBulkBarrier`を使用する開発者（またはランタイムの他の部分）に対する重要な警告です。ポインタを全く含まないアロケーション（例: `[]byte`）の場合、そのメモリ領域に対応するヒープビットマップは更新されません。したがって、`heapBitsBulkBarrier`がそのような領域をスキャンしようとすると、誤ったビットマップ情報を参照してしまう可能性があります。このため、`heapBitsBulkBarrier`を呼び出す前に、対象のメモリ領域がポインタを含んでいるかどうか（`typ.kind&kindNoPointers`でチェック可能）を確認するべきであると明記されています。これは、今回のバグが顕在化した原因の一つである「ヒープビットマップとメモリ内容の不一致」を防ぐための、より堅牢な設計原則を強調しています。

### `src/runtime/mheap.go` の変更

このファイルでは、`inheap`関数に`//go:nowritebarrier`と`//go:nosplit`ディレクティブが追加されています。

*   **`//go:nowritebarrier`**: このディレクティブは、関数内でポインタの書き込みバリアを無効にすることをコンパイラに指示します。`inheap`関数はGCのライトバリア処理自体から呼び出される可能性があるため、この関数内でさらにライトバリアがトリガーされると、デッドロックや無限ループなどの問題を引き起こす可能性があります。そのため、この関数内ではライトバリアを無効にする必要があります。
*   **`//go:nosplit`**: このディレクティブは、関数がスタックを拡張しないことをコンパイラに指示します。GCの処理中など、スタックのサイズ変更が許されないクリティカルなセクションで呼び出される関数に適用されます。`inheap`関数はライトバリアから使用されるため、GCの整合性を保つためにスタックの分割を避ける必要があります。

これらの変更は、`callwritebarrier`の修正と直接関連しているわけではありませんが、GCの低レベルな動作における正確性と安全性を確保するための、ランタイムコードの堅牢化の一環として行われています。

    Luckily, juju turned up a case where the heap bitmap and the memory
    were out of sync for the block immediately after the call frame, so that
    heapBitsBulkBarrier saw an obvious non-pointer where it expected a
    pointer, causing a loud crash.

    Why is there a non-pointer in memory that the heap bitmap records as
    a pointer? That is more difficult to answer. At least one way that it
    could happen is that allocations containing no pointers at all do not
    update the heap bitmap. So if heapBitsBulkBarrier walked out of the
    current object and into a no-pointer object and consulted those bitmap
    bits, it would be misled. This doesn't happen in general because all
    the paths to heapBitsBulkBarrier first check for the no-pointer case.
    This may or may not be what happened, but it's the only scenario
    I've been able to construct.

    It does fix the juju crash, and it is clearly an improvement over the

## 元コミット内容

Goランタイムにおける`callwritebarrier`関数のバグを修正します。

関数呼び出しフレーム`F`があり、そのサイズが`N`、戻り値がオフセット`R`から始まる場合、`callwritebarrier`は`heapBitsBulkBarrier`に対してメモリブロック`[F+R, F+R+N)`をスキャンするように指示していました。しかし、正しくは`[F+R, F+N)`をスキャンすべきでした。余分にスキャンされた`N-R`バイトは、メモリ上の次の割り当て済みブロックにまで及んでしまう可能性がありました。スキャンは型情報のためにヒープビットマップを参照していたため、次のブロックにスキャンが及んでも、通常はクラッシュせずに「たまたま動作していた」という状況でした。

この余分な`N-R`バイトのメモリをスキャンすることは、主にGCが本来考慮すべきでないポインタを考慮してしまい、結果として解放されるべきオブジェクトが保持され続けてしまう（メモリリーク）という問題を引き起こします。この種のバグは非常に検出が困難です。

幸運にも、jujuプロジェクトが、コールフレームの直後のブロックでヒープビットマップと実際のメモリ内容が同期していないケースを発見しました。これにより、`heapBitsBulkBarrier`がポインタを期待する場所で明らかにポインタではない値を見つけ、大きなクラッシュを引き起こしました。

なぜヒープビットマップがポインタと記録している場所にポインタではない値が存在するのかは、より難しい問題です。考えられる一つの原因として、ポインタを全く含まないアロケーションはヒープビットマップを更新しないという点が挙げられます。したがって、`heapBitsBulkBarrier`が現在のオブジェクトの範囲を超えて、ポインタを含まないオブジェクトにまでスキャンが及んでしまい、そのビットマップ情報を参照した場合、誤った判断をしてしまう可能性があります。通常、`heapBitsBulkBarrier`へのすべてのパスは、まずポインタを含まないケースをチェックするため、このような事態は発生しません。これが実際に起こったことかどうかは不明ですが、これが唯一構築できたシナリオです。

この問題に対する単純なテストケースを作成しようとしましたが、長い間試してもできませんでした。しかし、この修正はjujuのクラッシュを解決し、以前のコードよりも明らかに改善されています。

Issue #10844を修正します。

## 変更の背景

Goのガベージコレクションは、プログラムの実行中に不要になったメモリを自動的に解放する重要な機能です。このGCは、オブジェクトが参照されているかどうかを追跡するために「ライトバリア」というメカニズムを使用します。ライトバリアは、ポインタが変更されるたびにGCに通知し、ヒープ上のオブジェクトグラフの整合性を保つ役割を担います。

このコミットで修正された問題は、`callwritebarrier`という特定のライトバリア関数が、関数呼び出しの戻り値領域をスキャンする際に、誤ったメモリ範囲を`heapBitsBulkBarrier`に渡していたことに起因します。具体的には、関数フレームの戻り値が格納されるべき領域を超えて、隣接するメモリブロックまでスキャンしてしまっていました。

この「過剰なスキャン」は、通常はクラッシュを引き起こしませんでした。なぜなら、Goのヒープビットマップはメモリ上の各ワードがポインタであるか否かの情報を持っているため、たとえ誤った領域をスキャンしても、ビットマップが「これはポインタではない」と示せば、GCはそれを無視するからです。しかし、この過剰なスキャンは、GCが本来到達不能であるはずのオブジェクトへのポインタを誤って発見し、そのオブジェクトを解放せずに保持し続けてしまうという、いわゆる「メモリリーク」を引き起こす可能性がありました。このようなメモリリークは、プログラムの動作には影響を与えないため、非常に発見が困難です。

しかし、jujuプロジェクトで発生した特定のクラッシュは、この潜在的な問題を顕在化させました。このクラッシュは、ヒープビットマップがポインタであると示しているにもかかわらず、実際のメモリ内容がポインタではないという矛盾が生じたために発生しました。これは、ヒープビットマップの更新が不完全な、ポインタを含まないオブジェクトの領域にまでスキャンが及んだ場合に起こりうる状況でした。

このコミットは、この根本的なスキャン範囲の誤りを修正し、GCの正確性と安定性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念について知っておく必要があります。

1.  **ガベージコレクション (GC) とライトバリア (Write Barrier)**:
    *   GoのGCは、並行マーク＆スイープ方式を採用しています。プログラムの実行と並行してGCが動作し、一時停止時間を最小限に抑えます。
    *   GCが正確に動作するためには、プログラムがヒープ上のポインタを変更する際に、GCにその変更を通知する必要があります。この通知メカニズムが「ライトバリア」です。
    *   ライトバリアは、ポインタの書き込み操作（例: `obj.field = new_ptr`）の前後で実行される小さなコードスニペットで、GCがオブジェクトグラフの変更を追跡し、マークフェーズ中にすべての到達可能なオブジェクトを正しく識別できるようにします。
    *   `callwritebarrier`は、特定の状況下（例えば、関数呼び出しの戻り値がヒープに書き込まれる可能性のある場合）で、GCがスキャンすべきメモリ領域を特定し、ライトバリア処理をトリガーするために使用される関数の一つです。

2.  **ヒープビットマップ (Heap Bitmap)**:
    *   Goのランタイムは、ヒープメモリの各ワード（通常は8バイト）がポインタであるか、非ポインタであるかを記録する「ヒープビットマップ」を維持しています。
    *   このビットマップは、GCがヒープをスキャンする際に、どのメモリ位置をポインタとして解釈し、さらに辿るべきかを効率的に判断するために使用されます。これにより、GCは型情報なしにポインタを正確に識別できます。
    *   ポインタを含まないオブジェクト（例: `int`のスライスや`byte`の配列など）の場合、その領域に対応するヒープビットマップは「ポインタなし」とマークされます。

3.  **コールフレーム (Call Frame) とスタック (Stack)**:
    *   関数が呼び出されると、その関数に必要な情報（引数、ローカル変数、戻りアドレスなど）を格納するために、スタック上に「コールフレーム」が作成されます。
    *   Goでは、関数の戻り値もこのコールフレームの一部としてスタック上に配置されることがあります。
    *   `F`はコールフレームの開始アドレス、`N`はそのフレームの合計サイズ、`R`は戻り値がフレーム内で始まるオフセットを指します。

4.  **`unsafe.Pointer` と `uintptr`**:
    *   `unsafe.Pointer`は、任意の型のポインタを保持できる特殊な型で、Goの型システムをバイパスしてメモリを直接操作するために使用されます。C言語の`void*`に似ています。
    *   `uintptr`は、ポインタを整数として表現する型です。`unsafe.Pointer`と`uintptr`の間で相互変換が可能ですが、`uintptr`はポインタの算術演算を行うために使用され、GCは`uintptr`をポインタとして認識しません（`unsafe.Pointer`に変換し直さない限り）。
    *   ランタイムコードでは、メモリのアドレス計算やサイズ指定にこれらの型が頻繁に用いられます。

5.  **`heapBitsBulkBarrier`**:
    *   これは、指定されたメモリブロック内のポインタをスキャンし、GCのライトバリア処理を実行する低レベルの関数です。ヒープビットマップを参照して、どのワードがポインタであるかを判断します。

## 技術的詳細

問題の核心は、`callwritebarrier`関数が`heapBitsBulkBarrier`を呼び出す際の引数にありました。

元のコードでは、`callwritebarrier`は以下のように`heapBitsBulkBarrier`を呼び出していました。

```go
heapBitsBulkBarrier(uintptr(add(frame, retoffset)), framesize)
```

ここで:
*   `frame`はコールフレームの開始アドレス。
*   `retoffset`はコールフレーム内で戻り値が始まるオフセット。
*   `framesize`はコールフレーム全体のサイズ。

したがって、`uintptr(add(frame, retoffset))`は戻り値の開始アドレスを示します。
そして、`framesize`がスキャンするバイト数として渡されていました。

これにより、`heapBitsBulkBarrier`はメモリ範囲 `[戻り値の開始アドレス, 戻り値の開始アドレス + framesize)` をスキャンすることになります。
しかし、戻り値が始まるオフセット`R`から、フレームの終わり`N`までの領域をスキャンすべきでした。つまり、スキャンすべきサイズは`framesize - retoffset`であるべきでした。

元のコードでは、スキャン範囲の終端が `F + R + N` となっていましたが、正しくは `F + N` でした。この `N-R` バイトの差分が、コールフレームの終端を超えて、次のメモリブロックにまでスキャンが及ぶ原因となっていました。

この過剰なスキャンが問題となるのは、以下の理由からです。

1.  **メモリリークの可能性**: スキャンが隣接するブロックに及んだ場合、そのブロック内に存在する、本来は現在のオブジェクトグラフから到達不能であるはずのポインタをGCが誤って発見してしまう可能性があります。これにより、GCはそれらのオブジェクトを「まだ参照されている」と判断し、解放せずに保持し続けてしまいます。これはメモリリークにつながります。
2.  **クラッシュの可能性**: 通常、ヒープビットマップが正しく設定されていれば、隣接ブロックをスキャンしても、ビットマップが「ポインタではない」と示すため、クラッシュには至りません。しかし、特定の条件下（特にポインタを含まないオブジェクトのアロケーションでヒープビットマップの更新が不完全な場合など）で、ビットマップがポインタであると誤って示しているにもかかわらず、実際のメモリ内容がポインタではない場合、`heapBitsBulkBarrier`が不正なポインタをデリファレンスしようとしてクラッシュする可能性があります。jujuで発生したクラッシュは、まさにこのシナリオに該当すると考えられます。

修正は、`heapBitsBulkBarrier`に渡すサイズを`framesize`から`framesize - retoffset`に変更することで、スキャン範囲を戻り値が格納されている実際の領域に限定しています。

また、`src/runtime/mbitmap.go`と`src/runtime/mheap.go`には、この変更に関連するコメントの追加と修正が行われています。
`src/runtime/mbitmap.go`では、`heapBitsBulkBarrier`の呼び出し元が、ポインタを含まないアロケーションに対しては事前にチェックを行うべきであるという注意書きが追加されました。これは、ポインタを含まないアロケーションではヒープビットマップが維持されないため、`heapBitsBulkBarrier`が誤ったビットマップ情報を参照するのを防ぐためです。
`src/runtime/mheap.go`では、`inheap`関数がライトバリアによって使用されるため、`//go:nowritebarrier`と`//go:nosplit`ディレクティブが追加され、GCの整合性を保つための制約が明示されています。

## コアとなるコードの解説

### `src/runtime/mbarrier.go` の変更

このファイルでは、`callwritebarrier`関数の`heapBitsBulkBarrier`呼び出しにおける第2引数が変更されています。

*   **変更前**: `heapBitsBulkBarrier(uintptr(add(frame, retoffset)), framesize)`
    *   `framesize`がスキャンサイズとして渡されていました。これはコールフレーム全体のサイズであり、戻り値が始まるオフセット`retoffset`から計算すると、フレームの終端を超えて余分な領域までスキャンしてしまう可能性がありました。
*   **変更後**: `heapBitsBulkBarrier(uintptr(add(frame, retoffset)), framesize-retoffset)`
    *   スキャンサイズが`framesize-retoffset`に変更されました。これにより、スキャンは`frame + retoffset`（戻り値の開始アドレス）から始まり、`frame + retoffset + (framesize - retoffset)`、つまり`frame + framesize`（コールフレームの終端）までの正確な範囲に限定されます。この修正により、不要なメモリ領域のスキャンが防止され、メモリリークやクラッシュのリスクが排除されます。

### `src/runtime/mbitmap.go` の変更

このファイルでは、`heapBitsBulkBarrier`関数のコメントに重要な追記がされています。

*   **追加されたコメント**:
    ```go
    // The heap bitmap is not maintained for allocations containing
    // no pointers at all; any caller of heapBitsBulkBarrier must first
    // make sure the underlying allocation contains pointers, usually
    // by checking typ.kind&kindNoPointers.
    ```
    このコメントは、`heapBitsBulkBarrier`を使用する開発者（またはランタイムの他の部分）に対する重要な警告です。ポインタを全く含まないアロケーション（例: `[]byte`）の場合、そのメモリ領域に対応するヒープビットマップは更新されません。したがって、`heapBitsBulkBarrier`がそのような領域をスキャンしようとすると、誤ったビットマップ情報を参照してしまう可能性があります。このため、`heapBitsBulkBarrier`を呼び出す前に、対象のメモリ領域がポインタを含んでいるかどうか（`typ.kind&kindNoPointers`でチェック可能）を確認するべきであると明記されています。これは、今回のバグが顕在化した原因の一つである「ヒープビットマップとメモリ内容の不一致」を防ぐための、より堅牢な設計原則を強調しています。

### `src/runtime/mheap.go` の変更

このファイルでは、`inheap`関数に`//go:nowritebarrier`と`//go:nosplit`ディレクティブが追加されています。

*   **`//go:nowritebarrier`**: このディレクティブは、関数内でポインタの書き込みバリアを無効にすることをコンパイラに指示します。`inheap`関数はGCのライトバリア処理自体から呼び出される可能性があるため、この関数内でさらにライトバリアがトリガーされると、デッドロックや無限ループなどの問題を引き起こす可能性があります。そのため、この関数内ではライトバリアを無効にする必要があります。
*   **`//go:nosplit`**: このディレクティブは、関数がスタックを拡張しないことをコンパイラに指示します。GCの処理中など、スタックのサイズ変更が許されないクリティカルなセクションで呼び出される関数に適用されます。`inheap`関数はライトバリアから使用されるため、GCの整合性を保つためにスタックの分割を避ける必要があります。

これらの変更は、`callwritebarrier`の修正と直接関連しているわけではありませんが、GCの低レベルな動作における正確性と安全性を確保するための、ランタイムコードの堅牢化の一環として行われています。

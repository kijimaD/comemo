# [インデックス 23179] ファイルの概要

このコミットは、Goランタイムにおける`memeq`（メモリ比較）および`cmp`（文字列/バイトスライス比較）の内部実装において、テールコール最適化を導入するものです。具体的には、これらの比較処理を行う「ボディ」関数への呼び出し方法を変更し、不要な`CALL`/`RET`命令のペアを排除することで、パフォーマンスの向上とオーバーヘッドの削減を図っています。

## コミット

Author: Keith Randall <khr@golang.org>
Date:   Tue Apr 21 14:22:41 2015 -0700

    runtime: tail call into memeq/cmp body implementations
    
    There's no need to call/ret to the body implementation.
    It can write the result to the right place.  Just jump to
    it and have it return to our caller.
    
    Old:
      call body implementation
      compute result
      put result in a register
      return
      write register to result location
      return
    
    New:
      load address of result location into a register
      jump to body implementation
      compute result
      write result to passed-in address
      return
    
    It's a bit tricky on 386 because there is no free register
    with which to pass the result location.  Free up a register
    by keeping around blen-alen instead of both alen and blen.

## 変更の背景

Goランタイムでは、文字列やバイトスライスの比較といった頻繁に実行される操作のパフォーマンスが非常に重要です。これらの操作は、プログラム全体の実行速度に大きな影響を与える可能性があります。`memeq`や`cmp`のような関数は、Goの内部で頻繁に利用されるため、その効率性を最大限に高めることが求められます。

このコミットの背景には、既存の`memeqbody`や`cmpbody`といったアセンブリ実装が、結果を返すために余分な`CALL`と`RET`のペアを使用しているという認識がありました。具体的には、メインの比較関数がボディ関数を呼び出し、ボディ関数が結果をレジスタに格納してメイン関数に戻り、その後メイン関数がそのレジスタの値を最終的な結果のメモリ位置に書き込み、さらにそのメイン関数が呼び出し元に戻る、という二段階の戻り処理が発生していました。

この二段階の戻り処理は、スタックフレームの操作や命令の実行においてわずかながらオーバーヘッドを発生させます。特に、これらの関数がホットパス（頻繁に実行されるコードパス）にある場合、この小さなオーバーヘッドが積み重なり、無視できないパフォーマンスのボトルネックとなる可能性があります。

そこで、このコミットでは「テールコール」の概念を適用し、ボディ関数が直接結果を書き込み、元の呼び出し元に直接戻るようにすることで、この余分なオーバーヘッドを削減し、より効率的なコードパスを実現することを目指しました。

## 前提知識の解説

### 1. アセンブリ言語とGoランタイム

Go言語は高水準言語ですが、そのランタイム（実行環境）のコア部分は、パフォーマンスが要求される箇所やハードウェアとの直接的なやり取りが必要な箇所でアセンブリ言語で記述されています。`src/runtime/asm_*.s`ファイル群は、各アーキテクチャ（386, amd64, arm, arm64など）向けに最適化されたアセンブリコードを含んでいます。`memeq`や`cmp`のような基本的な操作は、これらのアセンブリコードによって非常に高速に実行されます。

### 2. `CALL`と`JMP`命令

- **`CALL`命令**: サブルーチン（関数）を呼び出す際に使用されます。`CALL`命令は、現在の命令の次のアドレス（リターンアドレス）をスタックにプッシュし、指定されたサブルーチンの先頭アドレスにジャンプします。サブルーチンは`RET`命令を実行して、スタックからリターンアドレスをポップし、元の呼び出し元に戻ります。
- **`JMP`命令**: 無条件ジャンプ命令です。指定されたアドレスに直接ジャンプします。`CALL`とは異なり、リターンアドレスをスタックにプッシュしないため、`JMP`でジャンプした先から`RET`命令を実行しても、元の`JMP`命令の呼び出し元には戻りません。

### 3. テールコール最適化 (Tail Call Optimization)

テールコール最適化は、関数が別の関数を呼び出し、その呼び出し結果をそのまま自身の戻り値として返す場合に適用できる最適化手法です。このような状況では、呼び出し元の関数が戻り値を処理する必要がないため、呼び出し元のスタックフレームを保持しておく必要がありません。

通常の関数呼び出し（`CALL`）では、呼び出し元のリターンアドレスがスタックに積まれ、新しいスタックフレームが作成されます。しかし、テールコール最適化が適用されると、呼び出し元のスタックフレームを破棄し、呼び出される関数に直接ジャンプ（`JMP`）することで、スタックフレームの作成と破棄、および余分な`RET`命令を省略できます。これにより、スタックの使用量を削減し、実行速度を向上させることができます。

このコミットでは、厳密な意味での「テールコール最適化」（再帰的なテールコールなど）とは少し異なりますが、同様の原理で、中間的な関数呼び出しのオーバーヘッドを削減しています。つまり、`memeq`や`cmp`のラッパー関数が`memeqbody`や`cmpbody`を呼び出す際に、`memeqbody`や`cmpbody`が直接最終的な結果を書き込み、`memeq`や`cmp`の元の呼び出し元に直接戻るようにすることで、`memeq`や`cmp`ラッパー関数自身の`RET`を省略しています。

### 4. `memeq`と`cmp`関数

- **`runtime·memeq`**: 2つのメモリ領域が等しいかどうかをバイト単位で比較する関数です。Goの内部で、例えば構造体の比較やバイトスライスの比較などに利用されます。
- **`runtime·cmpstring` / `bytes·Compare`**: 2つの文字列またはバイトスライスを辞書順に比較する関数です。結果は、最初の引数が2番目の引数より小さい場合は負の値、等しい場合は0、大きい場合は正の値を返します（通常は-1, 0, 1）。

## 技術的詳細

このコミットの核心は、`memeq`や`cmp`のラッパー関数が、実際の比較ロジックを実装する`memeqbody`や`cmpbody`関数を呼び出す方法を変更した点にあります。

**変更前（Old）のフロー:**

1.  ラッパー関数（例: `runtime·memeq`）が`runtime·memeqbody`を`CALL`命令で呼び出す。
2.  `runtime·memeqbody`は比較を実行し、結果（真偽値など）をレジスタ（例: `AX`）に格納する。
3.  `runtime·memeqbody`は`RET`命令でラッパー関数に戻る。
4.  ラッパー関数は、`runtime·memeqbody`が格納したレジスタの値を取得し、それを最終的な結果を格納すべきメモリ位置（スタックフレーム上の戻り値領域など）に書き込む。
5.  ラッパー関数は`RET`命令で自身の呼び出し元に戻る。

このフローでは、`runtime·memeqbody`からラッパー関数への戻り、そしてラッパー関数からその呼び出し元への戻り、という2回の`RET`命令と、その間のレジスタからメモリへの書き込みが発生していました。

**変更後（New）のフロー:**

1.  ラッパー関数は、最終的な結果を格納すべきメモリ位置のアドレスをレジスタ（例: `AX` on 386/amd64, `R7` on ARM）にロードする。
2.  ラッパー関数は、`runtime·memeqbody`を`JMP`命令で呼び出す。
3.  `runtime·memeqbody`は比較を実行し、結果をステップ1で渡されたアドレスに直接書き込む。
4.  `runtime·memeqbody`は`RET`命令で、ラッパー関数の呼び出し元に直接戻る。

この新しいフローでは、ラッパー関数が`runtime·memeqbody`を`JMP`で呼び出すため、ラッパー関数自身への戻りは発生しません。`runtime·memeqbody`が直接結果を書き込み、ラッパー関数の呼び出し元に直接戻ることで、中間的な`CALL`/`RET`ペアと、レジスタからメモリへの余分な書き込みが削減されます。

### 386アーキテクチャでの特殊な対応

コミットメッセージに記載されているように、386アーキテクチャでは、結果のアドレスを渡すための「空きレジスタ」が不足するという問題がありました。これを解決するために、`cmpbody`関数内で`alen`（s1の長さ）と`blen`（s2の長さ）の両方を保持する代わりに、`blen-alen`と`min(alen, blen)`を保持するように変更されました。これにより、レジスタを一つ解放し、結果のアドレスを渡すために利用できるようになりました。

具体的には、`runtime·cmpbody`の386版では、`DX`レジスタに`blen`、`BX`レジスタに`alen`が渡されていましたが、変更後は`DX`に`blen-alen`を計算して格納し、`BP`レジスタに`min(alen, blen)`を格納することで、`BX`レジスタを結果アドレスの受け渡しに利用できるようにしています。

### 各アーキテクチャでのレジスタ使用

-   **386/amd64**: 結果のアドレスを`AX`レジスタで渡す。
-   **ARM**: 結果のアドレスを`R7`レジスタで渡す。
-   **ARM64**: 結果のアドレスを`R7`レジスタで渡す。

これらのレジスタは、各アーキテクチャのABI（Application Binary Interface）やGoの内部規約に基づいて選択されています。

## コアとなるコードの変更箇所

変更は主に`src/runtime/asm_386.s`, `src/runtime/asm_amd64.s`, `src/runtime/asm_arm.s`, `src/runtime/asm_arm64.s`の4つのファイルにわたります。

### `src/runtime/asm_386.s` (例: `runtime·memeq`)

**変更前:**
```assembly
TEXT runtime·memeq(SB),NOSPLIT,$0-13
 	MOVL	a+0(FP), SI
 	MOVL	b+4(FP), DI
 	MOVL	size+8(FP), BX
 	CALL	runtime·memeqbody(SB)  // memeqbodyを呼び出す
 	MOVB	AX, ret+12(FP)         // memeqbodyの結果(AX)をretに書き込む
 	RET                            // 呼び出し元に戻る
```

**変更後:**
```assembly
TEXT runtime·memeq(SB),NOSPLIT,$0-13
 	MOVL	a+0(FP), SI
 	MOVL	b+4(FP), DI
 	MOVL	size+8(FP), BX
 	LEAL	ret+12(FP), AX         // 結果を書き込むアドレスをAXにロード
 	JMP	runtime·memeqbody(SB)  // memeqbodyにジャンプ
```
`runtime·memeqbody`内では、結果を`AX`レジスタが指すアドレスに直接書き込むように変更されています。

```assembly
// 変更前 (memeqbody内での結果設定例)
// SETEQ AX  // 比較結果をAXに設定
// RET

// 変更後 (memeqbody内での結果設定例)
// SETEQ (AX) // 比較結果をAXが指すアドレスに直接設定
// RET        // memeqの呼び出し元に直接戻る
```

### `src/runtime/asm_amd64.s` (例: `runtime·cmpstring`)

**変更前:**
```assembly
TEXT runtime·cmpstring(SB),NOSPLIT,$0-40
 	MOVQ	s1_base+0(FP), R2
 	MOVQ	s1_len+8(FP), R0
 	MOVQ	s2_base+16(FP), R3
 	MOVQ	s2_len+24(FP), R1
 	CALL	runtime·cmpbody(SB)
 	MOVQ	AX, ret+32(FP)
 	RET
```

**変更後:**
```assembly
TEXT runtime·cmpstring(SB),NOSPLIT,$0-40
 	MOVQ	s1_base+0(FP), R2
 	MOVQ	s1_len+8(FP), R0
 	MOVQ	s2_base+16(FP), R3
 	MOVQ	s2_len+24(FP), R1
 	LEAQ	ret+32(FP), R9         // 結果を書き込むアドレスをR9にロード
 	JMP	runtime·cmpbody(SB)    // cmpbodyにジャンプ
```
`runtime·cmpbody`内では、結果を`R9`レジスタが指すアドレスに直接書き込むように変更されています。

### `src/runtime/asm_arm.s` (例: `runtime·cmpstring`)

**変更前:**
```assembly
TEXT runtime·cmpstring(SB),NOSPLIT,$0-20
 	MOVW	s1_base+0(FP), R2
 	MOVW	s1_len+4(FP), R0
 	MOVW	s2_base+8(FP), R3
 	MOVW	s2_len+12(FP), R1
 	BL	runtime·cmpbody(SB)    // BLはCALLに相当
 	MOVW	R8, ret+16(FP)         // cmpbodyの結果(R8)をretに書き込む
 	RET
```

**変更後:**
```assembly
TEXT runtime·cmpstring(SB),NOSPLIT,$-4-20
 	MOVW	s1_base+0(FP), R2
 	MOVW	s1_len+4(FP), R0
 	MOVW	s2_base+8(FP), R3
 	MOVW	s2_len+12(FP), R1
 	ADD	$20, R13, R7           // 結果を書き込むアドレスをR7にロード (R13はスタックポインタ)
 	B	runtime·cmpbody(SB)    // BはJMPに相当
```
`runtime·cmpbody`内では、結果を`R7`レジスタが指すアドレスに直接書き込むように変更されています。

## コアとなるコードの解説

このコミットの主要な変更点は、`CALL`命令を`JMP`命令に置き換え、結果の格納方法を変更したことです。

1.  **`CALL`から`JMP`への変更**:
    -   `CALL`命令は、呼び出し元のリターンアドレスをスタックにプッシュしてからジャンプします。これにより、呼び出された関数が`RET`命令を実行すると、呼び出し元に戻ります。
    -   `JMP`命令は、リターンアドレスをプッシュせずに直接ジャンプします。これにより、`JMP`でジャンプした先の関数が`RET`命令を実行すると、`JMP`命令の呼び出し元ではなく、そのさらに上位の呼び出し元に直接戻ります。
    -   この変更により、`runtime·memeq`や`runtime·cmpstring`のようなラッパー関数が`runtime·memeqbody`や`runtime·cmpbody`を呼び出した後、自身に戻る必要がなくなり、直接最終的な呼び出し元に制御を戻すことができるようになります。

2.  **結果の受け渡し方法の変更**:
    -   変更前は、`runtime·memeqbody`や`runtime·cmpbody`が計算した結果をレジスタ（例: `AX`や`R8`）に格納し、ラッパー関数がそのレジスタの値を読み取って最終的な戻り値のメモリ位置に書き込んでいました。
    -   変更後は、ラッパー関数が`LEAL` (Load Effective Address) や `ADD` 命令を使って、最終的な戻り値が格納されるべきメモリ位置のアドレスをレジスタ（例: `AX`, `R9`, `R7`）にロードし、それを`runtime·memeqbody`や`runtime·cmpbody`に渡します。
    -   `runtime·memeqbody`や`runtime·cmpbody`は、比較結果をこの渡されたアドレスに直接書き込みます（例: `MOVB $0, (AX)` や `MOVD R4, (R7)`）。これにより、中間的なレジスタ経由のコピーが不要になります。

3.  **386アーキテクチャでのレジスタ制約の解決**:
    -   386アーキテクチャでは、結果アドレスを渡すためのレジスタが不足していました。
    -   `runtime·cmpbody`の386版では、`alen`と`blen`を直接保持する代わりに、`blen-alen`を`DX`に、`min(alen, blen)`を`BP`に格納するように変更されました。これにより、`BX`レジスタが解放され、結果アドレスの受け渡しに利用できるようになりました。
    -   具体的には、`SUBL BX, DX`で`blen-alen`を計算し、`CMOVLGT BX, BP`で`min(alen, blen)`を`BP`に設定しています。

これらの変更により、Goランタイムの`memeq`および`cmp`操作は、より少ないCPUサイクルとスタック操作で実行されるようになり、全体的なパフォーマンスが向上します。

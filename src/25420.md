## 変更の背景

このコミットの背景には、Goコンパイラが従来のAST（Abstract Syntax Tree）ベースのコンパイルパスから、SSA（Static Single Assignment）形式を中間表現として利用する新しいコンパイルパスへと移行していた時期の課題があります。

従来のGoコンパイラでは、関数呼び出し（`obj.ACALL`）のターゲットを表現する際に、`*obj.Prog`構造体の `To` フィールド内に `*Node`（ASTノード）と `*Sym`（シンボル）の両方の情報を持つことがありました。しかし、新しいSSAベースのコンパイラでは、中間表現の性質上、関数呼び出しのターゲット情報が主に `*Sym` として表現されるようになりました。

`plive.go` 内のライブネス情報出力ロジックは、関数呼び出しのデバッグ情報を整形して出力する際に、呼び出しターゲットの名前を取得していました。このロジックが `p.To.Node` を参照して関数名を取得するようになっていたため、SSAコンパイラが生成したコードでは `p.To.Node` が `nil` となり、正しく関数名が取得できない、あるいはパニックを引き起こす可能性がありました。

このコミットは、両方のコンパイラパス（従来のASTベースと新しいSSAベース）でライブネス情報の出力が正しく機能するように、関数呼び出しターゲットの名前取得方法を `*Sym` を利用するように統一することを目的としています。これにより、コンパイラの移行期間中もデバッグ情報の整合性が保たれます。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **Goコンパイラ**: Go言語のソースコードを機械語に変換するツールです。`cmd/compile` パッケージがその主要部分を構成します。
2.  **SSA (Static Single Assignment) 形式**: プログラムの最適化に広く用いられる中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。Goコンパイラは、パフォーマンス向上のためにSSA形式を導入しました。
3.  **ライブネス解析 (Liveness Analysis)**: データフロー解析の一種で、プログラムの特定のポイントにおいて、ある変数の値が将来使用される可能性があるかどうか（「ライブ」であるか）を決定します。ライブでない変数は、そのメモリ領域を再利用したり、レジスタから追い出したりすることができます。ガベージコレクションやレジスタ割り当ての最適化に不可欠です。
4.  **`obj.ACALL`**: Goコンパイラのバックエンド（`cmd/internal/obj` パッケージ）で定義されているアセンブリ命令の一種で、関数呼び出しを表します。`obj.Prog` 構造体の一部として、この命令がどのような呼び出しであるかを指定します。
5.  **`*obj.Prog`**: Goコンパイラのバックエンドでアセンブリ命令を表現するための構造体です。各 `Prog` は単一のアセンブリ命令を表し、オペコード（`As`）、ソースオペランド（`From`）、デスティネーションオペランド（`To`）などのフィールドを持ちます。
6.  **`*obj.Addr`**: `obj.Prog` のオペランド（`From` や `To`）として使用される構造体で、メモリ位置、レジスタ、定数、シンボルなどを表現します。
7.  **`*obj.Sym` (シンボル)**: プログラム内の関数、変数、ラベルなどの名前付きエンティティを表すシンボル情報です。コンパイラはこれらのシンボルを管理し、リンカが最終的な実行可能ファイルを生成する際に解決します。`*obj.Addr` の `Sym` フィールドに格納されることがあります。
8.  **`*Node` (ASTノード)**: 従来のGoコンパイラが使用していたAST（抽象構文木）のノードです。ソースコードの構文構造を木構造で表現します。`*obj.Addr` の `Node` フィールドに格納されることがありました。

## 技術的詳細

このコミットの核心は、Goコンパイラのライブネス解析のデバッグ出力部分における、関数呼び出しターゲットの表現方法の差異を吸収することにあります。

`livenessepilogue` 関数は、ライブネス解析の最終段階で、特定のプログラムポイント（`p`）におけるライブ変数の情報を出力します。特に、`obj.ACALL` 命令（関数呼び出し）に遭遇した場合、呼び出される関数の名前をデバッグメッセージに含めようとします。

変更前のコードでは、`p.As == obj.ACALL` かつ `p.To.Node != nil` という条件で、`p.To.Node` を `*Node` 型にキャストし、その `Sym.Name` フィールドから関数名を取得していました。これは、従来のASTベースのコンパイラが `obj.Addr` の `Node` フィールドに関数呼び出しのASTノードを格納していたためです。

しかし、SSAベースの新しいコンパイラでは、`obj.Addr` の `Node` フィールドは使用されず、代わりに `Sym` フィールドに直接 `*obj.Sym` が格納されるようになりました。このため、SSAコンパイラが生成したコードでは `p.To.Node` が `nil` となり、この条件が満たされず、関数名が正しく出力されないか、あるいは `nil` ポインタ参照によるランタイムエラーが発生する可能性がありました。

このコミットでは、この問題を解決するために以下の変更が行われました。

1.  **条件の変更**: `p.To.Node != nil` のチェックを `p.To.Sym != nil` に変更しました。これにより、SSAコンパイラが生成する `*Sym` ベースのターゲット情報にも対応できるようになります。
2.  **シンボル名からの関数名抽出**: `p.To.Sym.Name` から関数名を取得する際に、`strings.Index(name, ".")` を使用して `.` の位置を検索し、その後の部分を関数名として抽出しています。これは、Go言語のシンボル名が `パッケージ名.関数名` の形式（例: `main.myFunction`）で表現されることが多いためです。デバッグ出力では通常、パッケージ名を除いた純粋な関数名のみを表示したいという意図があります。例えば、`main.myFunction` から `myFunction` を抽出します。これにより、より簡潔で読みやすいデバッグ情報が提供されます。

この変更により、従来のコンパイラとSSAコンパイラのどちらで生成されたコードに対しても、一貫した方法で関数呼び出しのライブネスデバッグ情報を出力できるようになりました。これは、コンパイラの内部構造が進化する中で、デバッグツールや診断機能の互換性を維持するための重要な修正です。

# [インデックス 26920] ファイルの概要

このコミットは、Goリンカのアーキテクチャ定義に`Minalign`（最小アライメント）フィールドを追加し、シンボルの最小アライメントをアーキテクチャ固有に設定できるようにするものです。これにより、特にs390xアーキテクチャのような特定の要件を持つプラットフォームでの効率的な相対アドレッシングをサポートします。

## コミット

```
cmd/link: add Minalign field to ld.Arch

The new Minalign field sets the minimum alignment for all symbols.
This is required for the upcoming s390x port which requires symbols
be 2-byte aligned for efficient relative addressing.

All preexisting architectures have Minalign set to 1 which means
that this commit should have no effect.

I tested values of 2, 4 and 8 on linux amd64 and the tests appear to
pass. Increasing Minalign to 16 appears to brake the runtime. I
think this is due to assumptions made about the layout of module
data.

toolstash -cmp on linux amd64 shows no changes due to this commit.

Resolves #14604
```

## 変更の背景

この変更の主な背景は、Go言語のs390xアーキテクチャへの移植（ポート）の進行です。s390xはIBMのメインフレームで使用される64ビット命令セットアーキテクチャであり、その特性上、効率的な相対アドレッシングを行うためには、シンボルが少なくとも2バイト境界にアライメントされている必要があります。

既存のGoリンカのアーキテクチャ定義（`ld.Arch`）には、シンボルの最大アライメント（`Maxalign`）は存在しましたが、最小アライメントを強制するメカニズムがありませんでした。このため、s390xのような特定の最小アライメント要件を持つアーキテクチャを適切にサポートするためには、この`Minalign`フィールドの追加が必要となりました。

コミットメッセージでは、既存のアーキテクチャ（amd64, arm, arm64, mips64, ppc64, x86）では`Minalign`が1に設定されるため、この変更が既存の動作に影響を与えないことが強調されています。また、amd64でのテストにより、`Minalign`を2, 4, 8に設定してもテストがパスすることが確認されていますが、16に増やすとランタイムが破損する可能性が示唆されており、これはモジュールデータのレイアウトに関する既存の仮定に起因する可能性が指摘されています。

`Resolves #14604`とありますが、Go issue 14604は`-buildmode=shared`がデッドシンボルを含む問題に関するものであり、直接的なアライメントの問題とは異なります。しかし、アライメントの正確な制御は、共有ライブラリの生成やシンボル解決の正確性に影響を与える可能性があるため、間接的に関連しているか、あるいはこのアライメント変更がより広範な問題解決の一部であった可能性があります。

## 前提知識の解説

### 1. データアライメント (Data Alignment)
データアライメントとは、コンピュータのメモリ上でデータが特定のバイト境界に配置されることを指します。例えば、「4バイトアライメント」とは、データの開始アドレスが4の倍数でなければならないことを意味します。
- **目的**:
    - **パフォーマンス**: 多くのCPUは、アライメントされたデータへのアクセスを、アライメントされていないデータへのアクセスよりも高速に処理できます。特に、一度に複数のバイトを読み書きする際に効率的です。
    - **ハードウェア要件**: 一部のCPUアーキテクチャでは、特定のデータ型が特定の境界にアライメントされていないと、ハードウェア例外（アライメント違反）が発生し、プログラムがクラッシュする可能性があります。
    - **アトミック操作**: マルチスレッド環境でのアトミック操作（不可分操作）には、データが適切にアライメントされていることが前提となる場合があります。
- **リンカとアライメント**: リンカは、コンパイルされたオブジェクトファイル内のシンボル（変数、関数など）を最終的な実行可能ファイルやライブラリに配置する際に、これらのアライメント要件を考慮します。

### 2. Goリンカ (`cmd/link`)
Go言語のツールチェインの一部であり、Goプログラムのコンパイル済みオブジェクトファイルを結合して実行可能ファイルやライブラリを生成する役割を担います。Goリンカは、C言語のリンカとは異なり、独自のオブジェクトファイルフォーマットとリンキングプロセスを持っています。
- **`ld.Arch`構造体**: Goリンカ内部で、ターゲットアーキテクチャ固有の情報を保持するための構造体です。これには、ポインタサイズ、レジスタサイズ、関数アライメント、最大データアライメントなどが含まれます。

### 3. s390xアーキテクチャ
IBMが開発したメインフレームコンピュータ向けの64ビット命令セットアーキテクチャです。Go言語は、このs390xを含む多くのアーキテクチャをサポートしています。s390xのような特定のアーキテクチャでは、効率的なコード生成や実行のために、データや命令の配置に厳密なアライメント要件が課されることがあります。特に、相対アドレッシング（現在の命令ポインタからのオフセットでメモリにアクセスする方式）を使用する場合、参照されるアドレスが特定の境界にアライメントされていると、命令のエンコードがよりシンプルになり、実行効率が向上することがあります。

### 4. シンボル (Symbol)
プログラム内の変数、関数、ラベルなどの名前付きエンティティを指します。リンカはこれらのシンボルを解決し、メモリ上の最終的なアドレスを割り当てます。

## 技術的詳細

このコミットは、Goリンカのアーキテクチャ定義の中心的な構造体である`ld.Arch`に`Minalign`という新しいフィールドを追加することで、シンボルのアライメント制御をより柔軟かつアーキテクチャ固有に行えるようにします。

1.  **`ld.Arch`構造体への`Minalign`フィールドの追加**:
    `src/cmd/link/internal/ld/lib.go`内の`Arch`構造体に`Minalign int`フィールドが追加されました。これにより、各ターゲットアーキテクチャが独自の最小アライメント要件をリンカに伝えることができるようになります。

2.  **各アーキテクチャの`MinAlign`定数定義**:
    `src/cmd/link/internal/amd64/l.go`, `src/cmd/link/internal/arm/l.go`, `src/cmd/link/internal/arm64/l.go`, `src/cmd/link/internal/mips64/l.go`, `src/cmd/link/internal/ppc64/l.go`, `src/cmd/link/internal/x86/l.go`といった各アーキテクチャ固有のリンカ設定ファイルに、`MinAlign = 1`という定数が追加されました。これは、既存のアーキテクチャではデフォルトで1バイトアライメントが最小であることを示し、後方互換性を保ちます。

3.  **`ld.Thearch.Minalign`への設定**:
    各アーキテクチャの`obj.go`ファイル（例: `src/cmd/link/internal/amd64/obj.go`）内の`linkarchinit()`関数で、新しく追加された`MinAlign`定数の値が`ld.Thearch.Minalign`に設定されます。これにより、リンカが現在のターゲットアーキテクチャの最小アライメント値を知ることができます。

4.  **`symalign`関数のロジック変更**:
    `src/cmd/link/internal/ld/data.go`内の`symalign`関数は、与えられたシンボル`s`に必要なアライメントを計算する役割を担っています。この関数が`Minalign`フィールドを考慮するように変更されました。
    -   変更前は、シンボル`s`が独自のアライメント（`s.Align`）を持っている場合、それを優先し、そうでない場合は`Maxalign`からシンボルサイズに基づいてアライメントを決定していました。
    -   変更後は、まず`Thearch.Minalign`（`min`変数）を取得します。
    -   もし`s.Align`が`min`以上であれば、`s.Align`をそのまま返します。
    -   もし`s.Align`が0ではないが`min`より小さい場合（つまり、シンボルが`min`よりも小さいアライメントを要求しているが、`min`が強制されるべき場合）、`min`を返します。
    -   `s.Align`が0の場合（シンボルが特定のアライメントを要求していない場合）、`Maxalign`からアライメントを決定するロジックは残りますが、その際に`min`よりも小さくならないように調整されます。具体的には、`for int64(align) > s.Size && align > min`という条件が追加され、計算されたアライメントが`min`を下回らないように保証されます。

この変更により、Goリンカは、特定のアーキテクチャ（特にs390x）が要求する最小アライメントを強制できるようになり、その結果、より効率的で正しいコード生成が可能になります。

`Arch`構造体は、Goリンカがターゲットアーキテクチャに関する情報を格納するために使用されます。ここに`Minalign int`フィールドが追加されたことで、各アーキテクチャがシンボルに適用すべき最小アライメント値を定義できるようになりました。これは、アーキテクチャ固有のアライメント要件（例: s390xの2バイトアライメント）をリンカに伝えるための重要な拡張です。

### `src/cmd/link/internal/ld/data.go` の変更

```diff

@@ -1026,18 +1026,18 @@ func dosymtype() {

```
`symalign`関数は、シンボル`s`の最終的なアライメント値を決定するGoリンカの重要な部分です。
変更前は、シンボルが明示的なアライメント（`s.Align`）を持たない場合、`Maxalign`から開始してシンボルサイズに基づいてアライメントを計算していました。
変更後は、まず`Thearch.Minalign`を`min`変数に格納します。
1.  **`s.Align >= min`**: シンボルが要求するアライメントが、アーキテクチャの最小アライメント以上であれば、そのシンボル固有のアライメントをそのまま使用します。
2.  **`s.Align != 0` かつ `s.Align < min`**: シンボルが特定のアライメントを要求しているが、それがアーキテクチャの最小アライメントより小さい場合、アーキテクチャの最小アライメント（`min`）を強制します。
3.  **`s.Align == 0`**: シンボルが特定のアライメントを要求していない場合、`Maxalign`から適切なアライメントを計算する既存のロジックが適用されます。しかし、この計算ループの条件が`align > 1`から`align > min`に変更されました。これにより、計算されたアライメントが`min`を下回ることがなくなります。
この変更により、リンカは常にアーキテクチャが指定する最小アライメント要件を満たすようにシンボルを配置するようになります。

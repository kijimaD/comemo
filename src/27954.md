# [インデックス 27954] ファイルの概要

このコミットは、Goコンパイラの内部型システムにおける重要なリファクタリングを導入しています。具体的には、これまで配列とスライスの両方を表現するために使用されていた `TARRAY` 型を分割し、スライス専用の新しい型 `TSLICE` を導入しています。また、`[...]T` 形式の配列（DDDArray）の区別を廃止し、その処理方法を変更しています。これにより、コンパイラの型システムがより明確になり、将来的な機能拡張（特に定数境界式の評価の遅延）への道が開かれています。

## 元コミット内容

Goコンパイラにおいて、配列とスライスを区別するために `TARRAY` 型を分割し、スライス専用の新しい型 `TSLICE` を導入する。また、`[...]T` 形式の配列（DDDArray）の区別を廃止する。これは、`golang.org/issue/13890` に関連する定数境界式の評価を遅延させる必要性に対応するためである。

## 変更の背景

Go言語のコンパイラ内部では、これまで配列とスライスが `TARRAY` という単一の型種別（`Etype`）で表現されていました。しかし、配列とスライスはセマンティクスが大きく異なります。配列は固定長であり、値型として扱われるのに対し、スライスは可変長であり、内部的にポインタ、長さ、容量を持つ構造体として扱われます。このセマンティクスの違いを単一の `Etype` で表現しようとすると、コンパイラのコードベース全体で `t.IsSlice()` のようなヘルパー関数を使って、その `TARRAY` が配列なのかスライスなのかを常に判定する必要がありました。これはコードの複雑性を増し、エラーの温床となる可能性がありました。

また、`[...]T` 形式で宣言される配列（いわゆる「DDDArray」）は、コンパイル時に要素数が決定される特殊な配列です。これも `TARRAY` の一種として扱われていましたが、その特殊性ゆえに、コンパイラの様々な箇所で特別なハンドリングが必要でした。コミットメッセージで言及されている `golang.org/issue/13890` は、この `[...]T` 配列の境界（要素数）が定数式である場合に、その評価を遅延させることに関する課題です。既存の型システムでは、このような遅延評価を効率的かつ安全に行うことが困難であったと考えられます。

このコミットは、これらの問題を解決し、コンパイラの型システムをより堅牢で理解しやすいものにするために、`TSLICE` の導入と `DDDArray` の区別廃止という二つの主要な変更を行っています。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの内部構造、特に型システムに関する以下の概念を理解しておく必要があります。

1.  **`Etype` (Elementary Type)**: Goコンパイラが内部的に型を分類するために使用する列挙型です。`TINT`, `TBOOL`, `TSTRUCT`, `TARRAY` など、基本的な型種別を定義します。このコミットでは、ここに `TSLICE` が追加されます。
2.  **`Type` 構造体**: コンパイラがGo言語の型を表現するために使用する主要なデータ構造です。`Etype` フィールドを持ち、その型種別に応じて `Extra` フィールドに詳細な型情報（例えば、配列の要素型や長さ、構造体のフィールド情報など）を格納します。
3.  **配列 (Array)**: Goにおける配列は、固定長の要素のシーケンスです。`[N]T` のように宣言され、`N` はコンパイル時に既知の定数でなければなりません。配列は値型であり、代入や関数への引数渡しではコピーが発生します。
4.  **スライス (Slice)**: Goにおけるスライスは、配列の一部を参照する動的なビューです。`[]T` のように宣言され、内部的にはポインタ（基底配列への参照）、長さ、容量の3つの要素を持つ構造体です。スライスは参照型のように振る舞います。
5.  **`[...]T` 配列 (DDDArray)**: `[...]T` の形式で宣言される配列は、初期化子から要素数が推論される特殊な配列です。例えば `[...]int{1, 2, 3}` は `[3]int` となります。この形式は、特に大きな配列リテラルを扱う際に便利です。
6.  **`cmd/compile/internal/gc` パッケージ**: Goコンパイラのフロントエンド（字句解析、構文解析、型チェック、中間表現生成など）を担当するパッケージです。型システムに関するコードのほとんどはこのパッケージ内に存在します。
7.  **`golang.org/issue/13890`**: このIssueは、`[...]T` 配列の境界が定数式である場合に、その評価を遅延させることに関するものです。例えば `[...]int{f(), g()}` のようなケースで、`f()` や `g()` の結果が配列の長さに影響する場合、その長さをコンパイル時に確定させるのが難しい、あるいは不必要に早期に評価してしまう問題が考えられます。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの型システムにおける配列とスライスの表現方法の根本的な変更にあります。

### `TSLICE` 型の導入

*   **`Etype` の拡張**: `src/cmd/compile/internal/gc/type.go` に新しい `Etype` 定数 `TSLICE` が追加されました。これにより、コンパイラは型を扱う際に、配列とスライスを明確に区別できるようになります。
*   **`Type.Extra` フィールドの利用**: 以前は `TARRAY` の `Extra` フィールドが `*ArrayType` (固定長配列), `SliceType` (スライス), `DDDArrayType` (可変長配列リテラル) のいずれかを保持していました。この変更により、`TARRAY` の `Extra` は `*ArrayType` のみを保持し、`TSLICE` の `Extra` は `SliceType` を保持するようになります。これにより、`Type` 構造体を見ただけで、それが配列なのかスライスなのかが `Etype` と `Extra` の組み合わせで一意に判別できるようになります。
*   **ヘルパー関数の変更**: `t.IsSlice()` や `t.IsArray()` といったヘルパー関数は、`t.Etype` を直接チェックするように変更されました。これにより、これらの関数の実装が簡素化され、パフォーマンスも向上します。

### `DDDArray` の区別廃止

*   **`DDDArrayType` の削除**: `src/cmd/compile/internal/gc/type.go` から `DDDArrayType` 構造体が削除されました。
*   **`ArrayType.Bound` の再定義**: `[...]T` 形式の配列は、もはや `DDDArrayType` という特別な型ではなく、通常の `ArrayType` を使用するようになります。その際、要素数がまだ不明であることを示すために、`ArrayType` の `Bound` フィールドに負の値（具体的には `-1`）が設定されます。これにより、`isDDDArray()` のような関数は `t.Extra.(*ArrayType).Bound < 0` をチェックするようになります。
*   **定数境界式の評価遅延**: この変更は、`golang.org/issue/13890` で議論されている、`[...]T` 配列の境界が定数式である場合の評価遅延を可能にするための基盤となります。要素数が不明な状態（`Bound < 0`）で型を表現できるようになったことで、コンパイラの後のフェーズでその境界を評価し、確定させることが容易になります。

### コードベース全体への影響

これらの変更は、`cmd/compile/internal/gc` パッケージ内の多くのファイルに影響を与えています。

*   **型チェックと型推論**: `typecheck.go` では、`make` 関数の処理や複合リテラルの型チェックなど、スライスと配列の区別が重要となる箇所で `TSLICE` を考慮するように変更されています。
*   **アラインメントとサイズ計算**: `align.go` では、型のメモリレイアウトを計算する `dowidth` 関数が `TSLICE` を個別に処理するように変更されています。スライスは内部的にポインタ、長さ、容量を持つため、そのサイズとアラインメントは配列とは異なります。
*   **エクスポート/インポート**: `bexport.go` と `bimport.go` では、コンパイラがパッケージ間で型情報をエクスポート/インポートする際に、新しい `TSLICE` 型を正しくシリアライズ/デシリアライズするように変更されています。
*   **SSA (Static Single Assignment) 変換**: `ssa.go` では、SSA中間表現への変換時に、スライスの比較 (`OpEqSlice`, `OpNeqSlice`) が `TSLICE` 型に対して適用されるように修正されています。
*   **ガベージコレクション (GC) 関連**: `plive.go` や `reflect.go` では、GCがポインタをスキャンする際に、スライスが持つポインタ（基底配列へのポインタ）を正しく識別できるように `TSLICE` を考慮するように変更されています。

これらの変更により、コンパイラの内部ロジックは、配列とスライスのセマンティクスをより正確に反映し、将来的な最適化や機能追加のためのよりクリーンな基盤を提供します。

## コアとなるコードの解説

上記の変更箇所は、Goコンパイラの型システムにおける配列とスライスの表現方法を根本的に変えるものです。

*   **`Etype` への `TSLICE` 追加**: これは、コンパイラが型を識別する際の最も基本的な分類にスライスを独立したエンティティとして導入することを意味します。これにより、コンパイラの様々な部分で「この `TARRAY` はスライスなのか、それとも真の配列なのか？」という曖昧さを解消し、コードの可読性と保守性を向上させます。
*   **`Type.Extra` の役割の明確化**: `Type` 構造体の `Extra` フィールドは、特定の `Etype` に関連する追加情報を格納するためのものです。この変更により、`TARRAY` は常に固定長配列の情報を、`TSLICE` は常にスライスの情報を保持するようになり、型の構造がより予測可能になります。
*   **`ArrayType.Bound` を用いた `[...]T` 配列の表現**: `DDDArrayType` を廃止し、`ArrayType` の `Bound` フィールドに負の値を使用することで、`[...]T` 配列の「要素数未定」という状態を表現します。これは、コンパイルの初期段階では要素数が確定していないが、後続のフェーズで初期化子から要素数を推論して `Bound` を更新するというワークフローを可能にします。このアプローチは、`golang.org/issue/13890` で言及されている定数境界式の評価遅延に直接関連しており、コンパイラがより柔軟に配列の長さを決定できるようになります。
*   **`IsSlice()` / `IsArray()` の簡素化**: これらのヘルパー関数が `Etype` の直接比較に置き換えられたことで、以前のような `Etype == TARRAY` かつ `Extra` フィールドの型アサーションを行う複雑なロジックが不要になりました。これにより、コンパイラのコードがよりクリーンになり、潜在的なバグのリスクが低減されます。

これらの変更は、Goコンパイラの内部で配列とスライスがどのように扱われるかという、非常に低レベルな部分に影響を与えます。これにより、コンパイラはGo言語のセマンティクスをより正確にモデル化し、将来的な言語機能の追加や最適化のための強固な基盤を築くことができます。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの内部構造、特に型システムに関する以下の概念を理解しておく必要があります。

1.  **`Etype` (Elementary Type)**: Goコンパイラが内部的に型を分類するために使用する列挙型です。`TINT`, `TBOOL`, `TSTRUCT`, `TARRAY` など、基本的な型種別を定義します。このコミットでは、ここに `TSLICE` が追加されます。
2.  **`Type` 構造体**: コンパイラがGo言語の型を表現するために使用する主要なデータ構造です。`Etype` フィールドを持ち、その型種別に応じて `Extra` フィールドに詳細な型情報（例えば、配列の要素型や長さ、構造体のフィールド情報など）を格納します。
3.  **配列 (Array)**: Goにおける配列は、固定長の要素のシーケンスです。`[N]T` のように宣言され、`N` はコンパイル時に既知の定数でなければなりません。配列は値型であり、代入や関数への引数渡しではコピーが発生します。
4.  **スライス (Slice)**: Goにおけるスライスは、配列の一部を参照する動的なビューです。`[]T` のように宣言され、内部的にはポインタ（基底配列への参照）、長さ、容量の3つの要素を持つ構造体です。スライスは参照型のように振る舞います。
5.  **`[...]T` 配列 (DDDArray)**: `[...]T` の形式で宣言される配列は、初期化子から要素数が推論される特殊な配列です。例えば `[...]int{1, 2, 3}` は `[3]int` となります。この形式は、特に大きな配列リテラルを扱う際に便利です。
6.  **`cmd/compile/internal/gc` パッケージ**: Goコンパイラのフロントエンド（字句解析、構文解析、型チェック、中間表現生成など）を担当するパッケージです。型システムに関するコードのほとんどはこのパッケージ内に存在します。
7.  **`golang.org/issue/13890`**: このIssueは、`[...]T` 配列の境界が定数式である場合に、その評価を遅延させることに関するものです。例えば `[...]int{f(), g()}` のようなケースで、`f()` や `g()` の結果が配列の長さに影響する場合、その長さをコンパイル時に確定させるのが難しい、あるいは不必要に早期に評価してしまう問題が考えられます。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの型システムにおける配列とスライスの表現方法の根本的な変更にあります。

### `TSLICE` 型の導入

*   **`Etype` の拡張**: `src/cmd/compile/internal/gc/type.go` に新しい `Etype` 定数 `TSLICE` が追加されました。これにより、コンパイラは型を扱う際に、配列とスライスを明確に区別できるようになります。
*   **`Type.Extra` フィールドの利用**: 以前は `TARRAY` の `Extra` フィールドが `*ArrayType` (固定長配列), `SliceType` (スライス), `DDDArrayType` (可変長配列リテラル) のいずれかを保持していました。この変更により、`TARRAY` の `Extra` は `*ArrayType` のみを保持し、`TSLICE` の `Extra` は `SliceType` を保持するようになります。これにより、`Type` 構造体を見ただけで、それが配列なのかスライスなのかが `Etype` と `Extra` の組み合わせで一意に判別できるようになります。
*   **ヘルパー関数の変更**: `t.IsSlice()` や `t.IsArray()` といったヘルパー関数は、`t.Etype` を直接チェックするように変更されました。これにより、これらの関数の実装が簡素化され、パフォーマンスも向上します。

### `DDDArray` の区別廃止

*   **`DDDArrayType` の削除**: `src/cmd/compile/internal/gc/type.go` から `DDDArrayType` 構造体が削除されました。
*   **`ArrayType.Bound` の再定義**: `[...]T` 形式の配列は、もはや `DDDArrayType` という特別な型ではなく、通常の `ArrayType` を使用するようになります。その際、要素数がまだ不明であることを示すために、`ArrayType` の `Bound` フィールドに負の値（具体的には `-1`）が設定されます。これにより、`isDDDArray()` のような関数は `t.Extra.(*ArrayType).Bound < 0` をチェックするようになります。
*   **定数境界式の評価遅延**: この変更は、`golang.org/issue/13890` で議論されている、`[...]T` 配列の境界が定数式である場合の評価遅延を可能にするための基盤となります。要素数が不明な状態（`Bound < 0`）で型を表現できるようになったことで、コンパイラの後のフェーズでその境界を評価し、確定させることが容易になります。

### コードベース全体への影響

これらの変更は、`cmd/compile/internal/gc` パッケージ内の多くのファイルに影響を与えています。

*   **型チェックと型推論**: `typecheck.go` では、`make` 関数の処理や複合リテラルの型チェックなど、スライスと配列の区別が重要となる箇所で `TSLICE` を考慮するように変更されています。
*   **アラインメントとサイズ計算**: `align.go` では、型のメモリレイアウトを計算する `dowidth` 関数が `TSLICE` を個別に処理するように変更されています。スライスは内部的にポインタ、長さ、容量を持つため、そのサイズとアラインメントは配列とは異なります。
*   **エクスポート/インポート**: `bexport.go` と `bimport.go` では、コンパイラがパッケージ間で型情報をエクスポート/インポートする際に、新しい `TSLICE` 型を正しくシリアライズ/デシリアライズするように変更されています。
*   **SSA (Static Single Assignment) 変換**: `ssa.go` では、SSA中間表現への変換時に、スライスの比較 (`OpEqSlice`, `OpNeqSlice`) が `TSLICE` 型に対して適用されるように修正されています。
*   **ガベージコレクション (GC) 関連**: `plive.go` や `reflect.go` では、GCがポインタをスキャンする際に、スライスが持つポインタ（基底配列へのポインタ）を正しく識別できるように `TSLICE` を考慮するように変更されています。

これらの変更により、コンパイラの内部ロジックは、配列とスライスのセマンティクスをより正確に反映し、将来的な最適化や機能追加のためのよりクリーンな基盤を提供します。

## コアとなるコードの解説

上記の変更箇所は、Goコンパイラの型システムにおける配列とスライスの表現方法を根本的に変えるものです。

*   **`Etype` への `TSLICE` 追加**: これは、コンパイラが型を識別する際の最も基本的な分類にスライスを独立したエンティティとして導入することを意味します。これにより、コンパイラの様々な部分で「この `TARRAY` はスライスなのか、それとも真の配列なのか？」という曖昧さを解消し、コードの可読性と保守性を向上させます。
*   **`Type.Extra` の役割の明確化**: `Type` 構造体の `Extra` フィールドは、特定の `Etype` に関連する追加情報を格納するためのものです。この変更により、`TARRAY` は常に固定長配列の情報を、`TSLICE` は常にスライスの情報を保持するようになり、型の構造がより予測可能になります。
*   **`ArrayType.Bound` を用いた `[...]T` 配列の表現**: `DDDArrayType` を廃止し、`ArrayType` の `Bound` フィールドに負の値を使用することで、`[...]T` 配列の「要素数未定」という状態を表現します。これは、コンパイルの初期段階では要素数が確定していないが、後続のフェーズで初期化子から要素数を推論して `Bound` を更新するというワークフローを可能にします。このアプローチは、`golang.org/issue/13890` で言及されている定数境界式の評価遅延に直接関連しており、コンパイラがより柔軟に配列の長さを決定できるようになります。
*   **`IsSlice()` / `IsArray()` の簡素化**: これらのヘルパー関数が `Etype` の直接比較に置き換えられたことで、以前のような `Etype == TARRAY` かつ `Extra` フィールドの型アサーションを行う複雑なロジックが不要になりました。これにより、コンパイラのコードがよりクリーンになり、潜在的なバグのリスクが低減されます。

これらの変更は、Goコンパイラの内部で配列とスライスがどのように扱われるかという、非常に低レベルな部分に影響を与えます。これにより、コンパイラはGo言語のセマンティクスをより正確にモデル化し、将来的な言語機能の追加や最適化のための強固な基盤を築くことができます。

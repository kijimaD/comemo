## 変更の背景

このコミットは、Goコンパイラが特定のコードパターンを処理する際に発生していたバグ「bug150」に対処するために作成されました。具体的には、「reorder2: too many funcation calls evaluating parameters」（reorder2: パラメータを評価する関数呼び出しが多すぎる）というエラーメッセージが示唆するように、コンパイラの最適化フェーズ（reorder2）において、関数の引数評価がGo言語の仕様に沿って正しく行われない問題があったと考えられます。

Go言語の仕様では、式の評価順序、特に複数の関数呼び出しや副作用を伴う操作が含まれる場合について厳密なルールが定められています。しかし、コンパイラの実装によっては、最適化のためにこれらの評価順序が意図せず変更されたり、特定のケースで誤って解釈されたりすることがあります。これにより、開発者が期待する動作と実際の実行結果が異なる、非決定的な挙動、あるいはコンパイルエラーが発生する可能性があります。

このようなバグは、特に複数の戻り値を持つ関数、インターフェースへの型アサーション、または副作用を持つ関数が複雑な式の中で使用される場合に顕在化しやすい傾向があります。このコミットは、このような評価順序の不整合によって引き起こされる問題を特定し、将来的に再発しないようにするためのテストケースを追加することで、コンパイラの堅牢性と仕様への準拠を強化することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラの基本的な概念を理解しておく必要があります。

1.  **Go言語の評価順序 (Evaluation Order)**:
    Go言語の仕様では、式の評価順序が明確に定義されています。基本的なルールは「左から右への評価 (lexical left-to-right evaluation)」です。これは、式内のサブ式や関数呼び出しが、コードに記述された順序で評価されることを意味します。例えば、`f() + g()`という式では、`f()`が評価されてから`g()`が評価されます。複数の戻り値を持つ関数の呼び出しや、代入文の右辺と左辺の評価順序についても厳密なルールがあります。この厳密な評価順序は、特に副作用（変数の変更、I/O操作など）を持つ関数が関わる場合に、プログラムの予測可能性を保証するために非常に重要です。

2.  **副作用 (Side Effects)**:
    関数や式が、その戻り値以外にプログラムの状態を変更する（例えば、グローバル変数を変更する、I/Oを行う、ポインタを通じてメモリの内容を変更するなど）ことを「副作用がある」と言います。副作用を持つ関数が評価順序のルールに反して実行されると、プログラムの動作が非決定論的になったり、予期せぬバグを引き起こしたりする可能性があります。

3.  **コンパイラの最適化 (Compiler Optimization)**:
    コンパイラは、生成される機械語コードの実行速度やサイズを改善するために、様々な最適化を行います。これには、コードの再配置（reordering）、不要な計算の削除、共通部分式の排除などが含まれます。しかし、これらの最適化は、言語仕様で定められた評価順序や副作用のルールを厳密に守る必要があります。もし最適化がこれらのルールを破ると、コンパイラは「正しくない」コードを生成してしまいます。

4.  **`reorder2` フェーズ**:
    Goコンパイラの内部には、コードの最適化や変換を行うための複数のフェーズが存在します。`reorder2`という名前は、おそらくコンパイラのバックエンドにおけるコードの再配置や命令スケジューリングに関連する特定の最適化フェーズを指していると考えられます。このフェーズで、関数の引数評価の順序や回数に関する問題が発生したことが、エラーメッセージから示唆されています。

5.  **インターフェース (Interfaces)**:
    Goのインターフェースは、メソッドのセットを定義する型です。具体的な型がそのインターフェースのすべてのメソッドを実装していれば、その型はインターフェースを満たします。インターフェース型への値の代入や、インターフェース値からの型アサーションは、コンパイラが型の動的な性質を処理する必要があるため、評価順序の複雑さを増すことがあります。

## 技術的詳細

このコミットが修正しようとしている「bug150」は、「reorder2: too many funcation calls evaluating parameters」というエラーメッセージが示すように、Goコンパイラの特定の最適化フェーズ（`reorder2`）における引数評価の誤りに起因しています。

考えられる技術的詳細は以下の通りです。

*   **引数評価の重複または誤った順序**: Go言語の関数呼び出しでは、すべての引数が関数本体が実行される前に、左から右へ評価されます。しかし、コンパイラの`reorder2`フェーズが、何らかの理由で同じ引数を複数回評価してしまったり、評価順序を誤って並べ替えたりした可能性があります。これは、特に引数自体が関数呼び出しを含んでいたり、副作用を持っていたりする場合に問題となります。
*   **多値返却とインターフェースの組み合わせ**: `test/bugs/bug150.go`のコードを見ると、`g()`関数が`T`型の2つの値を返し、`f()`関数がそれらを`M`インターフェース型として受け取っています。多値返却とインターフェースへの代入は、コンパイラが内部的に複数の操作（値のコピー、インターフェース値の構築など）を実行する必要があるため、評価順序の管理が複雑になりがちです。この複雑さが、`reorder2`フェーズでの誤った最適化を引き起こした可能性があります。
*   **コンパイラの内部表現 (IR) の問題**: コンパイラはソースコードを中間表現（IR）に変換し、そのIRに対して最適化を行います。`reorder2`フェーズでの問題は、IRの変換や操作の際に、引数評価の依存関係が正しく追跡されなかったり、最適化ルールが特定のパターン（この場合は多値返却とインターフェース）に対して不適切に適用されたりした結果として発生した可能性があります。
*   **レジスタ割り当てやスタックフレームの管理**: コンパイラは、関数呼び出しの引数をレジスタやスタックに配置します。もし`reorder2`フェーズが、引数の評価結果を一時的に保持する方法や、それらを関数に渡す方法について誤った仮定を置いた場合、結果として「多すぎる関数呼び出し」が発生したり、間違った値が渡されたりする可能性があります。
*   **テスト駆動開発による修正**: このコミットがテストケースの追加であることから、このバグは特定のコードパターンでのみ発生し、発見が困難であったことが示唆されます。テストケースを追加することで、このバグが修正されたことを検証し、将来のコンパイラ変更で再発しないようにするための回帰テストとして機能します。

この問題は、Goコンパイラの初期段階における成熟度に関連するものであり、言語仕様の厳密な解釈と、それを正確に実装するコンパイラの能力が試される典型的な例と言えます。

## コアとなるコードの解説

`test/bugs/bug150.go`のコードは以下の通りです。

```go
// $G $D/$F.go || echo BUG: bug150 

// Copyright 2009 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package main

type T int
func (t T) M()

type M interface { M() } 

func g() (T, T)

func f() (a, b M) {
	a, b = g();
	return;
}

/*
bugs/bug150.go:13: reorder2: too many funcation calls evaluating parameters
*/
```

このテストケースのポイントは以下の通りです。

*   **型 `T` とメソッド `M()`**: `type T int`と`func (t T) M()`が定義されています。これは、`T`型が`M()`メソッドを持つことを示しています。
*   **インターフェース `M`**: `type M interface { M() }`は、`M()`メソッドを持つ任意の型が満たすインターフェースを定義しています。
*   **関数 `g()`**: `func g() (T, T)`は、`T`型の2つの値を返す関数です。この関数の具体的な実装は示されていませんが、テストの目的上、その戻り値が重要です。
*   **関数 `f()`**: `func f() (a, b M)`は、`M`インターフェース型の2つの戻り値を持つ関数です。この関数内で、`a, b = g()`という代入が行われています。

この`a, b = g()`という行が、バグのトリガーとなった箇所であると推測されます。
1.  `g()`は`T`型の2つの値を返します。
2.  これらの`T`型の値は、`f()`の戻り値である`M`インターフェース型に代入されます。Goでは、具体的な型（`T`）がインターフェース（`M`）を満たす場合、その値をインターフェース型として扱うことができます。この変換は、コンパイラが内部的にインターフェース値（型情報と値のペア）を構築する操作を伴います。

コメントアウトされた行 `/* bugs/bug150.go:13: reorder2: too many funcation calls evaluating parameters */` は、このテストケースが元々どのようなエラーを検出していたかを示しています。これは、コンパイラの`reorder2`フェーズが、`g()`の戻り値を`M`インターフェース型に変換する際に、引数評価（この場合は`g()`の呼び出し結果）を誤って複数回実行したり、不適切な順序で処理したりしたことを示唆しています。

このテストケースは、コンパイラが多値返却とインターフェースへの代入を組み合わせた複雑なシナリオにおいて、評価順序のルールを厳密に守り、不要な関数呼び出しや誤った最適化を行わないことを保証するために追加されました。

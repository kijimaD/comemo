# [インデックス 25140] ファイルの概要

このコミットは、Goランタイムにおける周期的なガベージコレクション（GC）の動作を検証するためのテストを追加し、そのテストを可能にするためのランタイム内部の変更を含んでいます。

変更されたファイルは以下の通りです。

*   `src/runtime/export_test.go`: ランタイム内部の変数をテスト目的で外部に公開するためのファイルです。このコミットでは、`forcegcperiod` 変数がテスト用にエクスポートされています。
*   `src/runtime/gc_test.go`: Goランタイムのガベージコレクションに関連するテストケースを定義するファイルです。このコミットでは、周期的なGCが正しく機能するかを確認する新しいテスト `TestPeriodicGC` が追加されています。
*   `src/runtime/proc1.go`: Goランタイムのスケジューラやシステムモニタ（`sysmon` ゴルーチン）の主要なロジックが含まれるファイルです。このコミットでは、`sysmon` 関数内で定義されていた `forcegcperiod` がグローバル変数に変更され、テストからアクセス可能になっています。また、`maxsleep` の計算ロジックが移動されています。

## コミット

このコミットは、Goランタイムの周期的なガベージコレクション（GC）が正しく動作することを保証するためのテストを追加します。これまで周期的なGCのテストが存在しなかったため、その機能が何度か意図せず壊れてしまうことがありました。これは、周期的なGCの発生を確認するために通常2分間待つ必要があるため、テストの作成が困難であったことが一因です。

この変更により、周期的なGCのタイムアウトをランタイムテストから制御できるようになり、タイムアウト値をゼロに設定して短時間スリープすることで、周期的なGCが確実に発生することを確認するテストが追加されました。

## 変更の背景

Goランタイムのガベージコレクション（GC）は、メモリ管理の重要な部分です。特に、アプリケーションがほとんどメモリを割り当てない場合でも、一定期間ごとにGCを実行して未使用のメモリを解放する「周期的なGC」のメカニズムが存在します。これは、メモリリークの防止や、長期間実行されるサービスにおけるメモリ使用量の安定化に寄与します。

しかし、この周期的なGCの機能にはこれまで専用のテストが存在しませんでした。その結果、ランタイムの他の変更によって周期的なGCのロジックが意図せず壊れてしまうことが何度か発生していました。問題が発覚するまでに時間がかかり、デバッグも困難になるという課題がありました。

テストがなかった主な理由は、周期的なGCがデフォルトで2分という比較的長い間隔で実行されるため、通常のテストスイートでその動作を検証することが非現実的だったためです。テストの実行時間が大幅に長くなってしまうため、開発者はテストの追加を避けていました。

このコミットは、この問題を解決するために、周期的なGCのタイムアウト設定をテストから一時的に変更できるようにし、短い時間間隔でGCが強制的に実行されることを検証するテストを追加することを目的としています。これにより、将来的なランタイムの変更によって周期的なGCが壊れることを防ぎ、ランタイムの安定性を向上させます。

## 前提知識の解説

### Goのガベージコレクション (GC)

Go言語は、自動メモリ管理のためにガベージコレクションを採用しています。GoのGCは、主に以下の2つのトリガーで実行されます。

1.  **ヒープ使用量に基づくGC:** ヒープの使用量が一定の閾値（前回のGC後のヒープ使用量に対する割合）を超えた場合に実行されます。これは、メモリ割り当てが活発なアプリケーションで頻繁に発生します。
2.  **周期的なGC (Periodic GC):** アプリケーションがほとんどメモリを割り当てない場合でも、一定期間（デフォルトでは2分）ごとにGCが強制的に実行されます。これは、アイドル状態のアプリケーションでもメモリを定期的にクリーンアップし、OSへのメモリ返却を促すことで、メモリフットプリントを低減するのに役立ちます。

GoのGCは、並行（concurrent）かつインクリメンタル（incremental）に動作し、アプリケーションの実行を長時間停止させることなくメモリを回収するように設計されています。

### `sysmon` ゴルーチン

`sysmon` (system monitor) は、Goランタイム内でバックグラウンドで動作する特別なゴルーチンです。このゴルーチンは、Goプログラムの実行中に様々な重要なタスクを定期的に実行します。主な役割は以下の通りです。

*   **周期的なGCの強制実行:** `forcegcperiod` で設定された期間が経過した場合にGCを強制的にトリガーします。
*   **アイドル状態のP (Processor) のスピン防止:** アイドル状態のPがCPUを消費し続けるのを防ぎ、OSスケジューラにCPUを解放します。
*   **ネットワークポーラーの監視:** ネットワークI/Oの準備ができたゴルーチンをスケジューラに通知します。
*   **デッドロックの検出:** 全てのゴルーチンがブロックされ、実行可能なゴルーチンが存在しない場合にデッドロックを検出します。
*   **ヒープメモリのOSへの返却 (Scavenging):** 一定期間使用されていないヒープメモリ領域をOSに返却します。

`sysmon` は、`runtime.proc1.go` ファイル内で定義されており、Goプログラムの健全な動作を維持するために不可欠な存在です。

### `forcegcperiod`

`forcegcperiod` は、`sysmon` ゴルーチンが周期的なGCを強制的に実行するまでの最大時間間隔をナノ秒単位で定義するランタイム内部の変数です。この値が経過すると、たとえヒープの使用量がGCの閾値に達していなくても、GCがトリガーされます。このコミット以前は、`sysmon` 関数内でローカルな定数として定義されていました。

### `export_test.go` の役割

Goのランタイムパッケージ（`runtime`）は、Go言語のコアな部分であり、通常は内部実装の詳細を外部に公開しません。しかし、ランタイム自体のテストを行う際には、内部の状態や変数を検査・操作する必要が生じることがあります。

`src/runtime/export_test.go` ファイルは、このような目的のために存在します。このファイル内で定義された変数や関数は、`runtime` パッケージのテストコード（`runtime_test.go` など）からのみアクセス可能になります。これにより、ランタイムの内部構造を外部に漏らすことなく、厳密なテストが可能になります。このコミットでは、`forcegcperiod` 変数をテストから操作できるようにするために、このファイルを通じてエクスポートされています。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムの内部変数 `forcegcperiod` をテストから制御可能にし、それを利用して周期的なGCの動作を検証するテストを追加した点にあります。

1.  **`forcegcperiod` の変更 (`src/runtime/proc1.go`)**:
    *   これまで `sysmon` 関数内でローカルな定数として定義されていた `forcegcperiod` が、`sysmon` 関数の外でグローバルな `var` 変数として定義し直されました。
    *   これにより、`forcegcperiod` はランタイムの他の部分、特にテストコードから参照・変更できるようになります。
    *   コメントも追加され、この変数がテスト目的で変更可能であることが明記されています。
    *   `sysmon` 関数内の `maxsleep` の計算ロジックが、`forcegcperiod` が変数になったことに伴い、`sysmonwait` のロック取得後に移動されました。これは、`forcegcperiod` の値がテスト中に変更される可能性があるため、`maxsleep` の計算が常に最新の `forcegcperiod` の値に基づいて行われるようにするためです。

2.  **`forcegcperiod` のエクスポート (`src/runtime/export_test.go`)**:
    *   `src/runtime/export_test.go` に `var ForceGCPeriod = &forcegcperiod` という行が追加されました。
    *   これにより、`runtime` パッケージのテストコードから `runtime.ForceGCPeriod` を通じて、内部の `forcegcperiod` 変数へのポインタにアクセスできるようになります。テストコードはこのポインタを介して `forcegcperiod` の値を読み書きできます。

3.  **周期的なGCテストの追加 (`src/runtime/gc_test.go`)**:
    *   `TestPeriodicGC` という新しいテスト関数が追加されました。
    *   このテストは、まず `runtime.GC()` を呼び出して、テスト開始時にGCが実行中でないことを確認します。
    *   次に、`runtime.ReadMemStats(&ms1)` を呼び出して、テスト開始時点のGC回数（`ms1.NumGC`）を記録します。
    *   最も重要なステップとして、`*runtime.ForceGCPeriod = 0` を実行します。これにより、周期的なGCのタイムアウトがゼロに設定され、`sysmon` ゴルーチンは可能な限り頻繁にGCをトリガーするようになります。
    *   その後、`for` ループ内で `time.Sleep(5 * time.Millisecond)` を繰り返し呼び出し、`sysmon` ゴルーチンが動作してGCが実行されるのを待ちます。ループは最大20回、または期待するGC回数（`want = 2`）に達するまで繰り返されます。
    *   ループ内で `runtime.ReadMemStats(&ms2)` を呼び出し、現在のGC回数（`ms2.NumGC`）を取得し、開始時からのGC回数の差分（`numGCs`）を計算します。
    *   期待されるGC回数に達したらループを終了し、`*runtime.ForceGCPeriod = orig` を実行して、`forcegcperiod` を元の値に戻します。これは、他のテストに影響を与えないための重要なクリーンアップです。
    *   最後に、`if numGCs < want` で、期待されるGC回数が発生したかどうかを検証します。発生していなければ `t.Fatalf` でテストを失敗させます。

この一連の変更により、Goランタイムの重要なバックグラウンド機能である周期的なGCが、自動テストによって継続的に検証されるようになり、将来的な回帰が効果的に防止されるようになりました。

## コアとなるコードの解説

### `src/runtime/export_test.go` の変更

`var ForceGCPeriod = &forcegcperiod`

この行は、`runtime` パッケージの内部変数 `forcegcperiod` へのポインタを、テストコードからアクセス可能な `ForceGCPeriod` という名前でエクスポートしています。Goのテストメカニズムでは、`_test.go` で終わるファイルは、同じパッケージ内の非テストコードの内部変数や関数にアクセスできますが、通常はエクスポートされた（大文字で始まる）識別子のみが外部からアクセス可能です。`export_test.go` は、この慣例を破らずに、テストのために内部変数を「エクスポート」する特別なメカニズムを提供します。これにより、`gc_test.go` から `runtime.ForceGCPeriod` を通じて `forcegcperiod` の値を変更できるようになります。

### `src/runtime/proc1.go` の変更

```go
// forcegcperiod is the maximum time in nanoseconds between garbage
// collections. If we go this long without a garbage collection, one
// is forced to run.
//
// This is a variable for testing purposes. It normally doesn't change.
var forcegcperiod int64 = 2 * 60 * 1e9

func sysmon() {
    // ...
    // Make wake-up period small enough
    // for the sampling to be correct.
    maxsleep := forcegcperiod / 2
    if scavengelimit < forcegcperiod {
        maxsleep = scavengelimit / 2
    }
    notetsleep(&sched.sysmonnote, maxsleep)
    // ...
}
```

1.  **`forcegcperiod` の変数化**:
    `forcegcperiod := int64(2 * 60 * 1e9)` というローカル定数定義が削除され、`var forcegcperiod int64 = 2 * 60 * 1e9` というグローバル変数定義に置き換えられました。これにより、`forcegcperiod` の値がランタイムの実行中に変更可能になり、テストコードからの操作が可能になります。追加されたコメントは、この変数がテスト目的で変更される可能性があることを明確に示しています。

2.  **`maxsleep` 計算ロジックの移動**:
    `sysmon` ゴルーチンは、次の処理までのスリープ時間を決定するために `maxsleep` を計算します。この `maxsleep` の計算は `forcegcperiod` の値に依存します。`forcegcperiod` が変数になり、テスト中に変更される可能性があるため、`sysmonwait` のロックを取得し、`notetsleep` を呼び出す直前に `maxsleep` を再計算するようにロジックが移動されました。これにより、`sysmon` がスリープする際に常に最新の `forcegcperiod` の値に基づいてスリープ時間が決定されることが保証されます。

### `src/runtime/gc_test.go` の `TestPeriodicGC` 関数

```go
func TestPeriodicGC(t *testing.T) {
	// Make sure we're not in the middle of a GC.
	runtime.GC()

	var ms1, ms2 runtime.MemStats
	runtime.ReadMemStats(&ms1)

	// Make periodic GC run continuously.
	orig := *runtime.ForceGCPeriod
	*runtime.ForceGCPeriod = 0

	// Let some periodic GCs happen. In a heavily loaded system,
	// it's possible these will be delayed, so this is designed to
	// succeed quickly if things are working, but to give it some
	// slack if things are slow.
	var numGCs uint32
	const want = 2
	for i := 0; i < 20 && numGCs < want; i++ {
		time.Sleep(5 * time.Millisecond)

		// Test that periodic GC actually happened.
		runtime.ReadMemStats(&ms2)
		numGCs = ms2.NumGC - ms1.NumGC
	}
	*runtime.ForceGCPeriod = orig

	if numGCs < want {
		t.Fatalf("no periodic GC: got %v GCs, want >= 2", numGCs)
	}
}
```

このテスト関数は、周期的なGCが期待通りに動作するかを検証します。

1.  **`runtime.GC()`**:
    テスト開始時に明示的にGCを実行し、GCが進行中の状態でないことを保証します。これにより、テストの初期状態がクリーンになります。

2.  **`runtime.ReadMemStats(&ms1)`**:
    テスト開始時点でのメモリ統計情報（`MemStats`）を取得し、特にGCの実行回数（`ms1.NumGC`）を記録します。これは、後でGCが実際に発生したかどうかを判断するためのベースラインとなります。

3.  **`orig := *runtime.ForceGCPeriod` と `*runtime.ForceGCPeriod = 0`**:
    `runtime.ForceGCPeriod` は、`export_test.go` でエクスポートされた `forcegcperiod` 変数へのポインタです。まず、現在の `forcegcperiod` の値を `orig` に保存します。これは、テスト終了後に元の値に戻すための重要なステップです。
    次に、`*runtime.ForceGCPeriod = 0` を設定することで、周期的なGCのタイムアウトをゼロに設定します。これにより、`sysmon` ゴルーチンは、可能な限り短い間隔でGCを強制的にトリガーするようになります。

4.  **GC発生の待機ループ**:
    `for` ループは、最大20回繰り返されるか、期待するGC回数（`want = 2`）に達するまで実行されます。
    *   `time.Sleep(5 * time.Millisecond)`: `sysmon` ゴルーチンが動作し、GCをトリガーする機会を与えるために、短い時間スリープします。システム負荷が高い場合でもGCが発生する猶予を与えるため、複数回スリープを繰り返す設計になっています。
    *   `runtime.ReadMemStats(&ms2)`: スリープ後、再度メモリ統計情報を取得します。
    *   `numGCs = ms2.NumGC - ms1.NumGC`: テスト開始時からのGC回数の差分を計算し、GCが実際に発生したかどうかを確認します。

5.  **`*runtime.ForceGCPeriod = orig`**:
    テストが終了したら、`forcegcperiod` の値をテスト開始前の元の値に戻します。これは、このテストが他のテストやランタイムの通常の動作に影響を与えないようにするためのクリーンアップです。

6.  **結果の検証**:
    `if numGCs < want` で、最終的に発生したGC回数が期待する回数（2回）よりも少なかった場合、`t.Fatalf` を呼び出してテストを失敗させます。これにより、周期的なGCが正しく機能していないことが検出されます。

このテストは、Goランタイムの内部動作を巧みに操作し、通常はテストが困難なバックグラウンドプロセスを効率的かつ確実に検証する良い例と言えます。

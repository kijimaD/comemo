## 元コミット内容

このコミットは「自動リンクのさらなる試み」と題されており、Goコンパイラ（`6g`）がアーカイブファイル（`.a`）を解決する際に、元のインポートパス文字列のみを保存するように変更することを目的としています。そして、リンカ（`6l`）がリンク時にその`.a`ファイルを再解決するようにします。

これにより、ライブラリがカレントディレクトリ内のアーカイブに対してビルドされた場合でも、インストールされたアーカイブに対して使用できるようになります。これは、開発環境とデプロイ環境でのライブラリのパス解決の不整合を解消するための重要なステップです。

## 変更の背景

Go言語の初期のビルドシステムは、Plan 9オペレーティングシステムのツールチェイン（`6g`、`6l`など）に強く影響を受けていました。これらのツールは、Goのソースコードをコンパイルし、実行可能ファイルをリンクする役割を担っていました。

当時のGoのビルドプロセスでは、パッケージがコンパイルされると、その結果は`.a`という拡張子を持つアーカイブファイル（静的ライブラリ）として保存されました。他のパッケージがこのライブラリをインポートする際、コンパイラは`.a`ファイルを検索し、リンカが最終的な実行可能ファイルに結合します。

しかし、このプロセスには課題がありました。特に、開発者がローカルでライブラリをビルドし、そのライブラリがカレントディレクトリに生成された`.a`ファイルを参照している場合と、そのライブラリが`$GOROOT/pkg`のような標準的なインストールパスに配置された`.a`ファイルを参照している場合とで、リンカの挙動に不整合が生じることがありました。

具体的には、`6g`がコンパイル時に`.a`ファイルの絶対パスを記録してしまうと、そのライブラリが別の場所に移動（インストール）された際に、リンカが古いパスを参照してしまい、リンクエラーが発生する可能性がありました。このコミットは、この問題を解決し、より堅牢な自動リンクメカニズムを確立するための「さらなる試み」として行われました。リンカが実行時に`.a`ファイルのパスを再解決することで、この柔軟性を実現しようとしています。

## 前提知識の解説

### Goのビルドプロセス（コンパイルとリンク）

Go言語のプログラムは、主に以下の2つのフェーズを経て実行可能ファイルになります。

1.  **コンパイル (Compilation)**: Goのソースコード（`.go`ファイル）は、コンパイラによって機械語のオブジェクトファイルに変換されます。このオブジェクトファイルは、通常、特定のパッケージのコンパイル済みコードを含んでいます。
2.  **リンク (Linking)**: コンパイルされたオブジェクトファイルと、プログラムが依存する他のライブラリ（標準ライブラリやサードパーティライブラリなど）が、リンカによって結合され、単一の実行可能ファイルが生成されます。Goはデフォルトで静的リンクを強く推奨しており、これにより生成される実行可能ファイルは、外部の共有ライブラリに依存せず、自己完結型となります。

### `6g`と`6l`の役割

Go言語の初期のツールチェインでは、特定のアーキテクチャ向けのコンパイラとリンカが個別のコマンドとして存在していました。

*   **`6g`**: AMD64（x86-64）アーキテクチャ向けのGoコンパイラです。Goのソースコードをコンパイルし、オブジェクトファイルやアーカイブファイルを生成する役割を担っていました。
*   **`6l`**: AMD64アーキテクチャ向けのGoリンカです。`6g`によって生成されたオブジェクトファイルやアーカイブファイルを結合し、最終的な実行可能ファイルを生成する役割を担っていました。

これらのツールは、Plan 9オペレーティングシステムのツールチェインの命名規則（例: `8c`、`8l`など）を踏襲しており、Goの初期開発に大きな影響を与えました。現在では、これらの個別のコマンドは`go build`や`go run`といった統一された`go`コマンドの内部で抽象化されており、ユーザーが直接これらを呼び出すことは稀です。

### `.a`ファイル（アーカイブファイル/静的ライブラリ）

`.a`ファイルは「アーカイブファイル」または「静的ライブラリ」と呼ばれ、複数のオブジェクトファイル（コンパイル済みのコード）を一つにまとめたものです。Go言語では、パッケージがコンパイルされると、その結果は通常、`.a`ファイルとして保存されます。

この`.a`ファイルは、他のGoプログラムがそのパッケージをインポートする際に再利用されます。これにより、依存するパッケージのソースコードを毎回コンパイルする必要がなくなり、ビルド時間を大幅に短縮できます。`go install`コマンドは、コンパイルされた`.a`ファイルを`$GOPATH/pkg`（Go Modulesを使用している場合は`GOMODCACHE`）のような標準的な場所に配置します。

### Goのパッケージとインポートパス

Goのプログラムは「パッケージ」という単位で構成されます。パッケージは、関連するGoのソースファイル群をまとめたものです。他のパッケージの機能を利用するには、`import`文を使ってそのパッケージをインポートします。

インポートパス（例: `"fmt"`, `"math/rand"`, `"github.com/user/repo/mypackage"`）は、パッケージを一意に識別するための文字列です。Goツールチェインは、このインポートパスを基に、パッケージのソースコードまたはコンパイル済み`.a`ファイルの場所を特定します。

### 静的リンクの概念

静的リンクとは、プログラムが実行時に必要とするすべてのライブラリコードを、コンパイル時に最終的な実行可能ファイルに直接組み込むビルド方式です。Go言語は、この静的リンクをデフォルトの挙動としています。

静的リンクの利点は、生成された実行可能ファイルが自己完結型であるため、デプロイが非常に簡単になることです。実行環境に特定のライブラリがインストールされている必要がなく、単一のファイルを実行するだけで済みます。一方で、実行可能ファイルのサイズが大きくなる傾向があり、ライブラリの更新があった場合には、そのライブラリに依存するすべてのプログラムを再ビルドする必要があります。

## 技術的詳細

このコミットの主要な目的は、Goのビルドシステムにおけるライブラリのパス解決の柔軟性を高めることです。特に、コンパイラ（`6g`）が`.a`ファイルを処理する際に、その絶対パスではなく、元のインポートパス文字列を記録するように変更し、リンカ（`6l`）がリンク時にそのパスを再解決するメカニズムを導入しています。

### `linehist`関数の変更

`linehist`関数は、コンパイル時にソースファイルの行番号情報を記録するために使用されます。このコミットでは、`linehist`関数のシグネチャに新しい引数`relative`（`int`型）が追加されました。

*   **変更前**: `void linehist(char *file, int32 off)`
*   **変更後**: `void linehist(char *file, int32 off, int relative)`

この`relative`引数は、記録するファイルパスが相対パスとして扱われるべきかどうかを示します。特に`.a`ファイルの場合、コンパイル時に絶対パスを記録するのではなく、リンカが実行時に適切な場所（カレントディレクトリや`GOROOT/pkg`など）から再解決できるように、相対パスとして記録する制御を可能にしています。

`src/cmd/gc/subr.c`の`linehist`の実装では、`off < 0`（`#pragma lib`のような特別なケース）かつ`file[0] != '/'`（絶対パスではない）場合に、以前は常に`pathname`（現在の作業ディレクトリ）と結合して絶対パスを生成していました。しかし、新しい`relative`引数が`true`の場合、この結合を行わないように変更され、相対パスのまま記録されるようになります。

### `importfile`における`.a`ファイルのパス処理の変更

`src/cmd/gc/lex.c`の`importfile`関数は、`import`文によって指定されたファイルを処理します。この関数内で、インポートされるファイルが`.a`ファイルであるかどうかがチェックされます。

*   **変更前**: `.a`ファイルの場合でも、`linehist(file, 0)`と`linehist(file, -1)`が呼び出され、`file`のフルパスが記録されていました。
*   **変更後**:
    *   インポートされるファイルが`.a`ファイル（`namebuf[len-2] == '.' && namebuf[len-1] == 'a'`）である場合、`linehist`を呼び出す際に、元のインポートパス文字列（例: `"fmt"`）のみを抽出し、その部分を`linehist`に渡します。具体的には、`p = file + len - f->u.sval->len - 2;`という計算で、ファイル名から`.a`とパッケージ名を除いた部分を指すポインタ`p`を生成し、`linehist(p, 0, 0);`と`linehist(p, -1, 1);`を呼び出します。ここで、`linehist`の新しい`relative`引数に`1`（true）を渡すことで、このパスが相対的に扱われるべきであることを示します。これは、「`.a`ファイルは移動する（インストールされる）と想定されるため、フルパスを記録しない」という意図に基づいています。
    *   一方、`.6`ファイル（コンパイル済みGoオブジェクトファイル）のような他のファイルの場合、「`.6`ファイルは移動しないと想定されるため、フルパスを記録する」という意図で、`linehist(file, 0, 0);`と`linehist(file, -1, 0);`が呼び出されます。

この変更により、`.a`ファイルに関しては、コンパイル時にその絶対パスを固定的に記録するのではなく、リンカが実行時にそのインポートパスを基に再解決できるような情報のみを保持するようになります。

### `addlib`におけるライブラリ検索パスの変更

`src/cmd/6l/obj.c`の`addlib`関数は、リンカがライブラリを追加する際に呼び出されます。この関数は、インポートされたライブラリの実際のファイルパスを解決する役割を担います。

*   **変更前**: `addlib`は、ライブラリのパスを決定する際に、`debug['9']`や`thechar`（アーキテクチャを示す文字）に基づいて`/usr/%clib`のような固定的なパスを生成していました。
*   **変更後**:
    *   `search`という新しいフラグが導入され、これが`1`の場合（つまり、インポートパスが絶対パスではない場合）、リンカはライブラリを検索する際に、まずカレントディレクトリ（`.`）を試行し、次に`goroot`（Goのインストールディレクトリ）の`pkg`サブディレクトリを試行するように変更されました。
    *   具体的には、`snprint(pname, sizeof pname, ".%s", name);`でカレントディレクトリからの相対パスを構築し、`access(pname, AEXIST) < 0`でファイルが存在しない場合に、`snprint(pname, sizeof pname, "%s/pkg/%s", goroot, name);`で`GOROOT/pkg`からのパスを構築します。
    *   これにより、リンカは、ライブラリがローカルでビルドされたものか、システムにインストールされたものかにかかわらず、適切な`.a`ファイルを見つけられるようになります。

### `Makefile`の変更

`src/lib/Makefile`には、Goの標準ライブラリのビルドとインストールに関するルールが記述されています。

*   **変更前**: `%.install: %.6`ルールでは、コンパイルされた`.6`ファイル（Goオブジェクトファイル）を直接`$(GOROOT)/pkg/$*.6`に移動していました。
*   **変更後**:
    *   `%.install: %.6`ルールが変更され、`.6`ファイルを直接移動するのではなく、まず`6ar grc $*.a $*.6`コマンドを使って、`.6`ファイルから`.a`アーカイブファイルを生成するように変更されました。
    *   その後、生成された`.a`ファイルを`$(GOROOT)/pkg/$*.a`に移動し、元の`.6`ファイルは削除されます。
    *   また、`exec.6`の依存関係に`strings.install`が追加されています。

この`Makefile`の変更は、Goのパッケージが`.6`ファイルとしてではなく、`.a`ファイルとしてインストールされるという、ビルドシステムの根本的な変更を反映しています。これにより、リンカが`.a`ファイルを扱う際の挙動と整合性が取れるようになります。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、以下のファイルと関数に集中しています。

*   `src/cmd/6l/obj.c`: `addlib`関数
*   `src/cmd/gc/go.h`: `linehist`関数のプロトタイプ宣言
*   `src/cmd/gc/lex.c`: `main`関数、`importfile`関数、`unimportfile`関数、`cannedimports`関数内での`linehist`の呼び出し
*   `src/cmd/gc/subr.c`: `linehist`関数の実装
*   `src/lib/Makefile`: `%.install`ルールと`exec.6`の依存関係

## コアとなるコードの解説

### `src/cmd/6l/obj.c` - `addlib`関数

`addlib`関数は、リンカがライブラリを解決する際の中心的なロジックを含んでいます。

```c
void
addlib(char *src, char *obj)
{
    char name[1024], pname[1024], comp[256], *p, *q;
    int i, search;

    if(histfrogp <= 0)
        return;

    search = 0;
    if(histfrog[0]->name[1] == '/') {
        sprint(name, "");
        i = 1;
    } else {
        sprint(name, "");
        i = 0;
        search = 1; // 新しいライブラリ検索ロジックを有効化
    }

    // ... (既存のパス構築ロジック) ...

    if(search) {
        // try dot and then try goroot.
        // going to have to do better (probably a command line flag) later.
        snprint(pname, sizeof pname, ".%s", name); // カレントディレクトリを試す
        if(access(pname, AEXIST) < 0)
            snprint(pname, sizeof pname, "%s/pkg/%s", goroot, name); // GOROOT/pkgを試す
        strcpy(name, pname);
    }
    // ... (デバッグ出力) ...
}
```
この変更により、`search`フラグが`1`の場合（つまり、インポートパスが絶対パスではない場合）、リンカはまずカレントディレクトリでライブラリを探し、見つからなければ`$GOROOT/pkg`ディレクトリを探すようになります。これにより、ローカルでビルドされたライブラリとインストールされたライブラリの両方に対応できるようになります。

### `src/cmd/gc/go.h` - `linehist`関数のプロトタイプ宣言

```c
void	linehist(char*, int32, int); // 新しいrelative引数が追加
```
`linehist`関数のプロトタイプに`int relative`が追加され、この関数がファイルパスの相対性を考慮するようになったことを示しています。

### `src/cmd/gc/lex.c` - `importfile`関数

`importfile`関数は、`import`文の処理を担当します。

```c
void
importfile(Val *f)
{
    Biobuf *imp;
    char *file, *p; // pが追加
    int32 c;
    int len;

    // ... (既存のファイルオープンロジック) ...

    file = strdup(namebuf);

    len = strlen(namebuf);
    if(len > 2 && namebuf[len-2] == '.' && namebuf[len-1] == 'a') { // .aファイルの場合
        if(!skiptopkgdef(imp))
            fatal("import not package file: %s", namebuf);

        // assume .a files move (get installed)
        // so don't record the full path.
        p = file + len - f->u.sval->len - 2; // パッケージ名部分を抽出
        linehist(p, 0, 0);
        linehist(p, -1, 1); // relativeを1に設定
    } else { // .6ファイルなどの場合
        // assume .6 files don't move around
        // so do record the full path
        linehist(file, 0, 0);
        linehist(file, -1, 0); // relativeを0に設定
    }

    // ... (既存の入力位置調整ロジック) ...
}
```
この変更により、`.a`ファイルがインポートされる場合、`linehist`にはフルパスではなく、パッケージ名を含む相対的なパスが渡され、`relative`フラグが`1`に設定されます。これにより、リンカが後でこのパスを再解決する際のヒントとなります。

また、`main`関数、`unimportfile`関数、`cannedimports`関数内での`linehist`の呼び出しも、新しいシグネチャに合わせて`linehist(..., 0)`のように`relative`引数が`0`で追加されています。

### `src/cmd/gc/subr.c` - `linehist`関数の実装

```c
void
linehist(char *file, int32 off, int relative) // relative引数が追加
{
    Hist *h;
    char *cp;

    // ... (既存のロジック) ...

    if(off < 0 && file[0] != '/' && !relative) { // relativeがfalseの場合のみパス結合
        cp = mal(strlen(file) + strlen(pathname) + 2);
        sprint(cp, "%s/%s", pathname, file);

```
`linehist`の実装では、`relative`引数が`true`の場合、`off < 0`かつ`file`が絶対パスでない場合でも、`pathname`との結合を行わないように変更されています。これにより、`.a`ファイルのように相対パスで記録したい場合に、その意図が尊重されます。

### `src/lib/Makefile`

```makefile
%.install: %.6
	6ar grc $*.a $*.6 # .6ファイルから.aアーカイブを生成
	mv $*.a $(GOROOT)/pkg/$*.a # .aファイルをインストール
	rm -f $*.6 # 元の.6ファイルを削除

# ...

exec.6: os.dirinstall strings.install # strings.installが追加
```
この`Makefile`の変更は、Goのパッケージが`.6`ファイルとしてではなく、`.a`ファイルとしてインストールされるという、ビルドシステムの変更を反映しています。`6ar`コマンドは、Plan 9のアーカイブユーティリティであり、複数のファイルを一つのアーカイブにまとめるために使用されます。

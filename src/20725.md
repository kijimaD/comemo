# [インデックス 20725] ファイルの概要

このコミットは、Goランタイムにおいて、ゴルーチン (`G`) の `param` フィールドと、同期プリミティブの待機キューで使用される `sudog` 構造体の `elem` フィールドに残る古い（stale）値をクリアすることを目的としています。これにより、ガベージコレクタが不正なヒープ領域へのポインタを参照するのを防ぎ、メモリリークの可能性を排除します。

## 元コミット内容

Goランタイムにおいて、ゴルーチン (`G`) の `param` フィールドと、`sudog` 構造体の `elem` フィールドに残る古い値をクリアする変更です。

この変更は、`dev.garbage` ブランチ（ガベージコレクタの実験的な開発ブランチ）において、ガベージコレクタが不正なヒープ領域へのポインタを参照するのを防ぐために必要でした。

また、このデフォルトブランチ（Go 1.4）においては、メモリリークの可能性を一部排除する効果があります。

## 変更の背景

このコミットは、Goランタイムの重要な進化、特にガベージコレクション（GC）の改善と密接に関連しています。

1.  **`dev.garbage` ブランチでの必要性**: コミットメッセージに「`dev.garbage` ブランチで必要だった」と明記されているように、この変更はGoのガベージコレクタの実験的な開発中に浮上した問題に対処するためのものでした。当時のGoのGCは、より正確な（precise）GCへと移行する過渡期にありました。正確なGCでは、ヒープ上のどの値がポインタであるかを正確に識別し、到達可能なオブジェクトのみをマークして残します。もし `G.param` や `SudoG.elem` のようなフィールドに、もはや有効ではない、あるいは参照すべきではない古いポインタが残っていると、GCがそれらを有効なポインタと誤認し、本来回収されるべきメモリを回収しない（メモリリーク）、または不正なメモリ領域をスキャンしてクラッシュするなどの問題を引き起こす可能性がありました。このコミットは、このようなGCの誤動作を防ぐための防御的な措置として導入されました。

2.  **Go 1.4でのメモリリーク防止**: このコミットがマージされた時期は、Go 1.4のリリース（2014年12月）に先行しています。Go 1.4では、ランタイムの大部分がC言語からGo言語に書き直され、ガベージコレクタが完全に正確な（fully precise）ものになりました。この大きな変更により、GCはメモリ内のポインタをより厳密に追跡できるようになりました。`G.param` や `SudoG.elem` のようなフィールドが、ゴルーチンがブロック解除された後や `sudog` が再利用された後に古いポインタ値を保持していると、たとえそれが論理的には不要な値であっても、GCはそれを有効なポインタとして扱い、参照先のメモリを解放しない可能性があります。これは、GCが正確になったがゆえに顕在化するメモリリークの形態であり、このコミットはそれを積極的に防ぐためのものです。

要するに、この変更は、Goランタイムがより洗練されたガベージコレクションメカニズムに移行する中で、メモリの健全性と効率性を確保するために不可欠なクリーンアップ作業であったと言えます。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの内部構造、特にゴルーチン、チャネル、スケジューラ、そしてガベージコレクションに関する以下の概念を理解しておく必要があります。

1.  **ゴルーチン (`G`)**:
    *   Goにおける軽量な実行スレッドです。Goランタイムのスケジューラによって管理されます。
    *   `G` 構造体は、ゴルーチンの状態（スタック、プログラムカウンタ、レジスタなど）を保持します。
    *   `G.param`: このフィールドは `unsafe.Pointer` 型で、ゴルーチンがブロックされたり、チャネル操作や `select` ステートメントなどの同期プリミティブで待機したりする際に、一時的に関連するデータ（例えば、`sudog` 構造体へのポインタ）を保持するために使用されます。ゴルーチンがブロック解除された後、このフィールドは論理的には不要になりますが、明示的にクリアされない限り古い値を保持し続ける可能性があります。

2.  **`sudog` 構造体**:
    *   `sudog` は "synchronization descriptor" の略で、Goランタイム内でゴルーチンが同期プリミティブ（チャネル、ミューテックス、セマフォなど）で待機している状態を表現するために使用される構造体です。
    *   `sudog` は、待機しているゴルーチン (`g` フィールド)、待機しているチャネルやセマフォなどのオブジェクト、そしてチャネル操作の場合には送受信されるデータが格納されるメモリ領域へのポインタ (`elem` フィールド) などを保持します。
    *   `SudoG.elem`: このフィールドは `unsafe.Pointer` 型で、チャネルの送受信操作において、実際にデータがコピーされるバッファへのポインタを保持します。操作が完了した後、このポインタはもはや必要ありませんが、`sudog` がプールに戻されて再利用される際に、古いポインタが残っていると問題を引き起こす可能性があります。

3.  **`hchan` 構造体**:
    *   Goのチャネルを表現するランタイム内部の構造体です。
    *   チャネルのバッファ、送受信キュー（`sendq` と `recvq`。これらは `sudog` のリスト）、ロックなどの情報を含みます。

4.  **Goランタイムとスケジューラ**:
    *   Goランタイムは、ゴルーチンの生成、スケジューリング、メモリ管理（GC）などを担当します。
    *   スケジューラは、多数のゴルーチンを限られた数のOSスレッド上で効率的に実行します。ゴルーチンがブロックされると、スケジューラは別の実行可能なゴルーチンに切り替えます。

5.  **Goのガベージコレクション (GC)**:
    *   Goは自動メモリ管理（ガベージコレクション）を採用しています。GCは、プログラムがもはや到達できないメモリ領域を自動的に解放し、再利用可能にします。
    *   **正確なGC (Precise GC)**: Go 1.4以降、GoのGCは正確なGCになりました。これは、GCがメモリ内のどの値がポインタであり、どの値が非ポインタデータであるかを正確に識別できることを意味します。これにより、GCは到達可能なオブジェクトグラフを正確にたどり、不要なメモリを確実に回収できます。
    *   **古いポインタ (Stale Pointers)**: 正確なGCの文脈では、もはや有効なオブジェクトを指していないにもかかわらず、メモリ上に残っているポインタは「古いポインタ」と呼ばれます。もしGCが古いポインタを有効なポインタと誤認すると、そのポインタが指す先のメモリ（たとえそれが既に解放されているか、別の目的で再利用されているメモリであっても）を「到達可能」と判断し、回収対象から外してしまう可能性があります。これがメモリリークや、最悪の場合、不正なメモリアクセスによるクラッシュにつながります。

このコミットは、これらの内部構造がどのように連携し、特に `G.param` と `SudoG.elem` が一時的なポインタを保持する役割を果たすかを理解することで、その重要性が明確になります。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムが内部的に使用する `G.param` と `SudoG.elem` フィールドに、ゴルーチンがブロック解除されたり、`sudog` 構造体が再利用されたりした後に残る「古いポインタ」を明示的に `nil` にクリアすることにあります。

1.  **`G.param` の問題**:
    *   `G.param` は、ゴルーチンがチャネル操作や `select` ステートメントなどでブロックされる際に、その操作に関連する `sudog` 構造体へのポインタを一時的に保持するために使われます。
    *   ゴルーチンがブロック解除され、実行が再開された後、`G.param` に格納されていた `sudog` へのポインタは、そのゴルーチンにとってはもはや意味を持ちません。しかし、明示的に `nil` に設定されない限り、古いポインタ値がそのまま残ります。
    *   Go 1.4で導入された正確なGCは、ヒープ上のすべてのポインタをスキャンします。もし `G.param` に古い `sudog` へのポインタが残っていると、GCはその `sudog` 構造体を「到達可能」と誤認し、本来回収されるべきメモリを回収しない可能性があります。これはメモリリークにつながります。

2.  **`SudoG.elem` の問題**:
    *   `SudoG.elem` は、チャネルの送受信操作において、実際にデータがコピーされるメモリ領域（送信元または受信先）へのポインタを保持します。
    *   チャネル操作が完了し、データがコピーされた後、`sudog` 構造体は通常、`releaseSudog` 関数によって `sudog` キャッシュ（`gomcache().sudogcache`）に返却され、将来の操作のために再利用されます。
    *   もし `sudog` がキャッシュに返却される際に `SudoG.elem` が `nil` にクリアされないと、再利用された `sudog` が古い `elem` ポインタを保持したままになります。
    *   これもまた、正確なGCが古いポインタを追跡し、本来回収されるべきメモリを回収しない原因となり得ます。特に、`sudog` がキャッシュにプールされている間、その `elem` フィールドが指すメモリがGCによって「到達可能」と見なされ続けると、メモリリークが発生します。

このコミットは、これらの問題を解決するために、ゴルーチンがブロック解除される直前や、`sudog` 構造体がキャッシュに返却される直前など、関連するポインタが不要になるタイミングで、`G.param` と `SudoG.elem` を明示的に `nil` に設定する変更を導入しています。これにより、GCが常に正確なポインタ情報のみを扱い、メモリリークや不正なメモリ参照のリスクを排除します。

`src/runtime/proc.go` に追加された `acquireSudog` と `releaseSudog` 内の `gothrow` は、この問題が再発した場合に早期に検知するためのアサーション（デバッグチェック）として機能します。これにより、開発中に `elem` や `param` がクリアされていない `sudog` がキャッシュに存在したり、ゴルーチンに紐づく `param` がクリアされていなかったりする異常な状態を即座に検出できます。

## コアとなるコードの変更箇所

このコミットでは、以下の4つのファイルにコードの変更が加えられています。

1.  **`src/runtime/chan.go`**:
    *   チャネルの送受信 (`chansend`, `chanrecv`) およびクローズ (`closechan`) 処理において、`sudog.elem` と `gp.param` を `nil` にクリアする行が追加されました。
    *   `chansend` 内で、`recvg.param = unsafe.Pointer(sg)` の行が `sg.elem = nil` の後に移動し、`gp.param = nil` が追加されました。
    *   `closechan` 内で、`sg.elem = nil` が追加されました。
    *   `chanrecv` 内で、`sg.elem = nil` が追加され、`gp.param` のクリアロジックが変更されました。

2.  **`src/runtime/proc.go`**:
    *   `acquireSudog` 関数（`sudog` をプールから取得する）に、取得した `sudog` の `elem` が `nil` でない場合にパニックを起こすチェックが追加されました。
    *   `releaseSudog` 関数（`sudog` をプールに返却する）に、返却する `sudog` の `elem` が `nil` でない場合、および現在のゴルーチン (`gp`) の `param` が `nil` でない場合にパニックを起こすチェックが追加されました。

3.  **`src/runtime/select.go`**:
    *   `select` ステートメントの処理において、`gp.param` を `nil` にクリアする行が追加されました。
    *   `gp.waiting` リスト内のすべての `sudog` の `elem` を `nil` にクリアするループが追加されました。
    *   `syncrecv` および `syncsend` 関数内で、`sg.elem = nil` が追加されました。

4.  **`src/runtime/sema.go`**:
    *   セマフォのキューから `sudog` をデキューする `dequeue` 関数内で、`s.elem = nil` が追加されました。

## コアとなるコードの解説

各ファイルの主要な変更点と、それがなぜ行われたのかを詳しく解説します。

### `src/runtime/chan.go`

チャネル操作は、ゴルーチン間の同期とデータ転送の核心です。`chansend` (送信)、`chanrecv` (受信)、`closechan` (クローズ) の各関数で `G.param` と `SudoG.elem` のクリアが行われます。

*   **`chansend` (チャネル送信)**:
    ```go
    // ...
    		recvg := sg.g
    //-		recvg.param = unsafe.Pointer(sg) // 古い位置
    		if sg.elem != nil {
    			memmove(unsafe.Pointer(sg.elem), ep, uintptr(c.elemsize))
    +			sg.elem = nil // 送信完了後、sudog.elemをクリア
    		}
    +		recvg.param = unsafe.Pointer(sg) // 新しい位置
    // ...
    	if mysg.releasetime > 0 {
    		blockevent(int64(mysg.releasetime)-t0, 2)
    	}
    +	gp.param = nil // 送信ゴルーチンがブロック解除される前にgp.paramをクリア
    	if mysg.releasetime > 0 {
    		blockevent(int64(mysg.releasetime)-t0, 2)
    	}
    ```
    送信側ゴルーチンがブロックされ、受信側ゴルーチンがデータを取得した場合、`sg.elem` はデータコピー後に不要になります。また、送信側ゴルーチンがブロック解除される際に、`gp.param` に残っていた `sudog` へのポインタもクリアされます。`recvg.param = unsafe.Pointer(sg)` の移動は、`sg.elem` がクリアされた後に `recvg.param` が設定されるようにすることで、`sg` が再利用される前に `elem` が確実にクリアされるようにするためです。

*   **`closechan` (チャネルクローズ)**:
    ```go
    // ...
    	for {
    		sg := c.recvq.dequeue()
    		if sg == nil {
    			break
    		}
    		gp := sg.g
    +		sg.elem = nil // 受信待機中のsudog.elemをクリア
    		gp.param = nil // 受信待機中のゴルーチンのgp.paramをクリア
    // ...
    ```
    チャネルがクローズされると、そのチャネルで待機していたすべての受信ゴルーチンがブロック解除されます。この際、それらのゴルーチンに関連付けられていた `sudog` の `elem` と、ゴルーチン自身の `param` がクリアされます。これにより、これらのフィールドに古いポインタが残るのを防ぎます。

*   **`chanrecv` (チャネル受信)**:
    ```go
    // ...
    		if ep != nil {
    			memmove(ep, sg.elem, uintptr(c.elemsize))
    		}
    +		sg.elem = nil // 受信完了後、sudog.elemをクリア
    		gp := sg.g
    		gp.param = unsafe.Pointer(sg)
    // ...
    	if mysg.releasetime > 0 {
    		blockevent(mysg.releasetime-t0, 2)
    	}
    +	haveData := gp.param != nil // gp.paramがnilでないかチェック
    +	gp.param = nil // 受信ゴルーチンがブロック解除される前にgp.paramをクリア
    	releaseSudog(mysg)
    // ...
    ```
    受信側ゴルーチンがデータを取得した場合、`sg.elem` はデータコピー後に不要になります。また、受信ゴルーチンがブロック解除される際に、`gp.param` に残っていた `sudog` へのポインタもクリアされます。`haveData` の導入は、`gp.param` がクリアされる前に、データが実際に受信されたかどうか（`gp.param` が `nil` でないことで判断）の情報を保持するためです。

### `src/runtime/proc.go`

`sudog` の取得と解放に関する変更は、`sudog` プールの健全性を保つためのものです。

*   **`acquireSudog` (sudog取得)**:
    ```go
    func acquireSudog() *sudog {
    	c := gomcache()
    	s := c.sudogcache
    	if s != nil {
    +		if s.elem != nil {
    +			gothrow("acquireSudog: found s.elem != nil in cache") // キャッシュから取得したsudogのelemがnilでない場合はエラー
    +		}
    		c.sudogcache = s.next
    		return s
    	}
    // ...
    ```
    `sudog` がキャッシュから取得される際に、その `elem` フィールドが `nil` であることを確認します。もし `nil` でなければ、それは以前の操作で適切にクリアされなかったことを意味し、潜在的なバグやメモリリークの兆候であるため、`gothrow` でパニックを起こします。これは、`sudog` がクリーンな状態で再利用されることを保証するためのアサーションです。

*   **`releaseSudog` (sudog解放)**:
    ```go
    func releaseSudog(s *sudog) {
    +	if s.elem != nil {
    +		gothrow("runtime: sudog with non-nil elem") // 解放するsudogのelemがnilでない場合はエラー
    +	}
    +	gp := getg()
    +	if gp.param != nil {
    +		gothrow("runtime: releaseSudog with non-nil gp.param") // 解放時のゴルーチンのparamがnilでない場合はエラー
    +	}
    	c := gomcache()
    	s.next = c.sudogcache
    	c.sudogcache = s
    }
    ```
    `sudog` がキャッシュに返却される際に、その `elem` フィールドが `nil` であること、および現在のゴルーチン (`gp`) の `param` が `nil` であることを確認します。これらのチェックも、`acquireSudog` と同様に、`sudog` とゴルーチンの状態がクリーンであることを保証するためのアサーションです。

### `src/runtime/select.go`

`select` ステートメントは複数のチャネル操作を同時に待機するため、`sudog` の管理が複雑になります。

*   **`select` ループ内**:
    ```go
    // ...
    	// someone woke us up
    	sellock(sel)
    	sg = (*sudog)(gp.param)
    +	gp.param = nil // selectゴルーチンがブロック解除された際にgp.paramをクリア
    // ...
    	// Clear all elem before unlinking from gp.waiting.
    +	for sg1 := gp.waiting; sg1 != nil; sg1 = sg1.waitlink {
    +		sg1.elem = nil // gp.waitingリスト内のすべてのsudog.elemをクリア
    +	}
    	gp.waiting = nil
    // ...
    ```
    `select` ステートメントで待機していたゴルーチンがブロック解除された際、まず `gp.param` がクリアされます。さらに、`select` が待機していたすべてのチャネルに関連付けられていた `sudog` が格納されている `gp.waiting` リストを走査し、それぞれの `sudog.elem` を明示的に `nil` に設定します。これにより、`select` 操作が完了した後に、これらの `sudog` に古いポインタが残るのを防ぎます。

*   **`syncrecv` / `syncsend` (同期受信/送信)**:
    ```go
    // syncrecv
    // ...
    	if cas.elem != nil {
    		memmove(cas.elem, sg.elem, uintptr(c.elemsize))
    	}
    +	sg.elem = nil // 同期受信完了後、sg.elemをクリア
    	gp = sg.g
    	gp.param = unsafe.Pointer(sg)
    // ...

    // syncsend
    // ...
    	if sg.elem != nil {
    		memmove(sg.elem, cas.elem, uintptr(c.elemsize))
    	}
    +	sg.elem = nil // 同期送信完了後、sg.elemをクリア
    	gp = sg.g
    	gp.param = unsafe.Pointer(sg)
    // ...
    ```
    `select` 内での同期的なチャネル送受信が完了した後、関連する `sudog` の `elem` フィールドがクリアされます。

### `src/runtime/sema.go`

セマフォ操作でも `sudog` が使用されるため、同様のクリーンアップが必要です。

*   **`dequeue` (sudogデキュー)**:
    ```go
    func (root *semaRoot) dequeue(s *sudog) {
    // ...
    	} else {
    		root.head = s.next
    	}
    +	s.elem = nil // セマフォキューからデキューされたsudogのelemをクリア
    	s.next = nil
    	s.prev = nil
    }
    ```
    セマフォの待機キューから `sudog` がデキューされる際に、その `elem` フィールドがクリアされます。これにより、`sudog` が再利用される前に古いポインタが確実に除去されます。

これらの変更は、Goランタイムのメモリ管理の堅牢性を高め、特に正確なガベージコレクタの導入に伴う潜在的なメモリリークや不正なメモリ参照の問題を未然に防ぐための重要なステップです。

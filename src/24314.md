# [インデックス 24314] ファイルの概要

このコミットは、`cmd/go` ツールにおいて、`go get -t` (テスト依存関係を含む取得) および `go list` コマンドがベンダーディレクトリ内のパッケージパスを正しく解決するように修正するものです。具体的には、テスト専用のインポートパスに対しても `vendoredImportPath` 関数を適用し、ベンダーディレクトリの利用が適切に行われるように改善しています。また、`go get` 実行時に "C" (cgo) のテストインポートをスキップする変更も含まれています。

## 元コミット内容

このコミットは、`go get -t` コマンドおよび `go list` コマンドが、テスト専用のインポートパスを解決する際にベンダーディレクトリを適切に参照するように修正します。これまでは通常のインポートパスについてはベンダーディレクトリの参照が行われていましたが、テスト専用のインポートパスについてはこの処理が欠けていました。この修正により、ベンダーディレクトリを使用しているプロジェクトでテスト依存関係が正しく解決されるようになります。また、`go get` 実行時に "C" 言語のテストインポート（cgo関連）をスキップする改善も含まれています。

## 変更の背景

Go言語のパッケージ管理において、ベンダーディレクトリ（`vendor/`）は、プロジェクトが依存する外部パッケージのコピーをプロジェクト内に保持するための仕組みです。これにより、依存関係の安定性やビルドの再現性が向上します。このコミットが作成された2015年頃は、Go Modulesが導入される前であり、ベンダーディレクトリは `GO15VENDOREXPERIMENT` 環境変数を通じて試験的に導入され、Go 1.5でサポートが開始されたばかりの時期でした。

当時の `go get` や `go list` コマンドは、通常のパッケージインポートについてはベンダーディレクトリ内のパス解決を考慮していましたが、テスト専用のインポート（`p.TestImports` や `p.XTestImports`）についてはこの処理が不足していました。その結果、ベンダーディレクトリ内に存在するテスト依存パッケージが正しく見つけられず、`go get -t` でテスト依存関係を取得しようとしたり、`go list` でパッケージ情報を表示しようとしたりすると、エラーが発生したり、誤った情報が表示されたりする問題がありました。

このコミットは、以下の2つのIssueを解決するために行われました。

*   **Fixes #11628**: `go get -t` がベンダーディレクトリ内のテスト依存関係を解決できない問題。
*   **Fixes #11717**: `go list` がベンダーディレクトリ内のテスト依存関係を正しく表示できない問題。

また、`go get` が "C" インポート（cgo）のテスト依存関係を不必要にダウンロードしようとする挙動も改善の対象となりました。cgoはGoとC言語の連携を可能にするもので、`import "C"` は特別な意味を持つため、通常のパッケージダウンロードの対象外とすべきでした。

## 前提知識の解説

### Go言語のパッケージ管理とベンダーディレクトリ

Go言語では、コードはパッケージとして組織されます。初期のGoでは、`GOPATH` という環境変数で指定されたワークスペース内でパッケージが管理されていました。外部パッケージは `go get` コマンドでダウンロードされ、`GOPATH/src` 以下に配置されます。

**ベンダーディレクトリ (vendor/)**: Go 1.5で導入された `vendor/` ディレクトリは、プロジェクト固有の依存関係を管理するための仕組みです。プロジェクトのルートディレクトリ直下に `vendor/` ディレクトリを作成し、その中に依存パッケージのソースコードを配置することで、プロジェクトは `GOPATH` に依存せず、自身の依存関係を独立して管理できるようになります。これは、異なるプロジェクトが同じ依存パッケージの異なるバージョンを使用する際に発生する問題を回避するのに役立ちます。Goツールチェインは、パッケージを解決する際に、まず現在のパッケージの `vendor/` ディレクトリ内を探し、見つからなければ `GOPATH` を探すという優先順位で動作します。この機能は当初 `GO15VENDOREXPERIMENT=1` 環境変数で有効にする必要がありました。

### `go get` コマンド

`go get` は、指定されたパッケージとその依存関係をダウンロードし、インストールするコマンドです。
*   `go get <package_path>`: 指定されたパッケージをダウンロードします。
*   `go get -t <package_path>`: 指定されたパッケージの通常の依存関係に加えて、テストコード（`_test.go` ファイル）がインポートしているパッケージ（テスト依存関係）もダウンロードします。これは、テストを実行するために必要なすべての依存関係を確実に取得するために使用されます。

### `go list` コマンド

`go list` は、Goパッケージに関する情報を表示するコマンドです。
*   `go list <package_path>`: 指定されたパッケージに関する詳細情報（インポートパス、ファイルリスト、依存関係など）をJSON形式などで出力します。
*   `go list -f "{{.Imports}}"`: パッケージがインポートしている通常の依存関係のリストを表示します。
*   `go list -f "{{.TestImports}}"`: パッケージのテストコードがインポートしている依存関係のリストを表示します。

### `import "C"` (cgo)

`import "C"` はGo言語の特別なインポートパスで、GoプログラムからC言語のコードを呼び出す（またはC言語からGoのコードを呼び出す）ための `cgo` ツールを使用することを示します。これは実際のパッケージではなく、GoとCの間のブリッジを構築するための指示としてGoコンパイラによって特別に扱われます。そのため、`go get` のようなパッケージダウンロードツールがこれを通常の外部パッケージとして扱おうとすると問題が生じます。

### `vendoredImportPath` 関数

Goツールチェイン内部で使用される関数で、与えられたインポートパスがベンダーディレクトリ内に存在するかどうかを判断し、存在する場合はベンダーディレクトリを考慮した正しいインポートパスに変換します。例えば、`vendor/github.com/foo/bar` にあるパッケージ `github.com/foo/bar` をインポートする場合、この関数は `github.com/foo/bar` を `vendor/github.com/foo/bar` として解決する手助けをします。

## 技術的詳細

このコミットの主要な技術的変更点は、`go get` と `go list` の両コマンドにおいて、テスト専用のインポートパス (`p.TestImports` および `p.XTestImports`) に対しても `vendoredImportPath` 関数を適用するようにしたことです。

1.  **`src/cmd/go/get.go` の変更**:
    *   `download` 関数内で、`getTestDeps` が `true` の場合（つまり `go get -t` が実行された場合）、`p.TestImports` と `p.XTestImports` の各パスに対して `vendoredImportPath(p, path)` を呼び出すようになりました。これにより、テスト依存関係のインポートパスがベンダーディレクトリを考慮して正しく解決され、ダウンロード対象が特定されます。
    *   さらに、`path == "C"` の場合は `continue` してダウンロード処理をスキップするロジックが追加されました。これは、cgoの "C" インポートが通常のパッケージではないため、ダウンロードの対象外とすることで不必要な処理やエラーを防ぐためです。

2.  **`src/cmd/go/list.go` の変更**:
    *   `runList` 関数内で、`load` された各パッケージ `pkg` の `pkg.TestImports` と `pkg.XTestImports` の各要素に対して、`vendoredImportPath(pkg, path)` を適用し、結果を元のスライスに書き戻すようになりました。これにより、`go list` がテスト依存関係のインポートパスを表示する際に、ベンダーディレクトリを考慮した正しいパスが表示されるようになります。

3.  **`src/cmd/go/vendor_test.go` の追加テスト**:
    *   `TestVendorGet` という新しいテストケースが追加されました。このテストは、ベンダーディレクトリ内に存在するパッケージを通常のインポートとテストインポートの両方で使用するシナリオをシミュレートします。
    *   具体的には、`vendor.org/p` というベンダーパッケージを作成し、`main` パッケージがこれを通常のインポートとテストインポートの両方で使用するように設定します。
    *   `go run m.go`、`go test`、`go list -f "{{.Imports}}"`、`go list -f "{{.TestImports}}"` を実行し、ベンダーディレクトリが正しく解決されていることを確認します。
    *   最後に `go get` と `go get -t` を実行し、ベンダーパッケージが正しく処理され、ダウンロードが不要な場合は行われないことを検証します。特に `go get -t` がテスト依存関係を正しく解決できるようになったことを確認する重要なテストです。

これらの変更により、Goツールチェインはベンダーディレクトリの利用がより堅牢になり、特にテスト依存関係の管理が改善されました。コミットメッセージにある「It would be nice to do this while loading the package, but that breaks the code that checks for direct references to vendor packages when running go test.」という記述は、パッケージロード時にこの処理を行うと、`go test` がベンダーパッケージへの直接参照をチェックする既存のロジックと衝突するため、より限定的な範囲で変更を適用したことを示唆しています。これは、変更の影響範囲を最小限に抑えつつ、問題を解決するための実用的なアプローチです。

## コアとなるコードの解説

### `src/cmd/go/get.go` の変更点

`download` 関数は、`go get` コマンドの主要なロジックを担い、パッケージとその依存関係を再帰的にダウンロードします。
変更箇所は、`getTestDeps` が `true` の場合に実行されるブロックです。これは `go get -t` が指定されたときにテスト依存関係を処理するためのものです。

1.  **`p.TestImports` および `p.XTestImports` のループ**:
    *   `p.TestImports` は通常のテストファイル (`_test.go`) がインポートするパッケージのリストです。
    *   `p.XTestImports` は外部テストファイル (`_test.go` で `package foo_test` の形式) がインポートするパッケージのリストです。
    *   これらのリスト内の各 `path` について処理が行われます。

2.  **`if path == "C" { continue }`**:
    *   これは `cgo` の `import "C"` を特別に扱うためのガード句です。`"C"` は実際のパッケージではないため、ダウンロードを試みるべきではありません。この行により、`cgo` 関連のインポートがスキップされ、不必要なエラーや処理が回避されます。

3.  **`path, _ = vendoredImportPath(p, path)`**:
    *   この行がこのコミットの核心的な変更の一つです。`vendoredImportPath` 関数は、与えられたインポートパス (`path`) が、現在のパッケージ `p` のベンダーディレクトリ内に存在するかどうかをチェックし、もし存在すればそのベンダーパスに解決します。これにより、`go get -t` がベンダーディレクトリ内のテスト依存関係を正しく見つけ、ダウンロード（または既に存在する場合はスキップ）できるようになります。
    *   コメントにある「It's not needed for Imports, because it was done while loading the package.」は、通常の `p.Imports` (非テスト依存関係) については、パッケージのロード段階で既にベンダーパス解決が行われているため、ここでは不要であることを説明しています。

4.  **`download(path, p, stk, false)`**:
    *   解決されたパスで再帰的に `download` 関数を呼び出します。ここで `false` を渡しているのは、「テスト依存関係のテスト依存関係」は取得しないというポリシーのためです。

### `src/cmd/go/list.go` の変更点

`runList` 関数は `go list` コマンドの主要なロジックを担います。
変更箇所は、`load(args)` でロードされた各パッケージ `pkg` に対して行われる処理です。

1.  **`pkg.TestImports` および `pkg.XTestImports` のループ**:
    *   `go list` がパッケージ情報を表示する際に、これらのテストインポートパスもベンダーディレクトリを考慮して正しく表示されるようにします。

2.  **`path, _ = vendoredImportPath(pkg, path)`**:
    *   `go get.go` と同様に、`vendoredImportPath` を適用して、テストインポートパスをベンダーディレクトリを考慮した正しいパスに変換します。
    *   変換されたパスは `pkg.TestImports[i] = path` または `pkg.XTestImports[i] = path` によって元のスライスに書き戻されます。これにより、`go list` の出力に正しいベンダーパスが反映されます。
    *   ここでも「It's not needed for regular imports, because it was done while loading the package.」というコメントがあり、通常のインポートについては既に処理済みであることを示しています。

### `src/cmd/go/vendor_test.go` の追加テスト

`TestVendorGet` は、このコミットの変更が意図通りに機能することを検証するための統合テストです。

    *   `src/v/vendor/vendor.org/p/p.go` として、実際にベンダーパッケージ `vendor.org/p` を作成します。
    *   `GOPATH` を一時ワークスペースに設定し、`GO15VENDOREXPERIMENT=1` を設定してベンダー機能を有効にします。
    *   `tg.cd(tg.path("src/v"))` でテスト対象のディレクトリに移動します。

2.  **テスト実行と検証**:
    *   `tg.run("run", "m.go")`: メインパッケージが正しくビルド・実行できることを確認します。
    *   `tg.run("test")`: テストパッケージが正しくビルド・実行できることを確認します。
    *   `tg.run("list", "-f", "{{.Imports}}")` と `tg.grepStdout(...)`: `go list` で通常のインポートパスがベンダーディレクトリを考慮して正しく解決されていることを確認します。
    *   `tg.run("list", "-f", "{{.TestImports}}")` と `tg.grepStdout(...)`: **このコミットで修正された主要な点**。`go list` でテストインポートパスがベンダーディレクトリを考慮して正しく解決されていることを確認します。
    *   `tg.run("get")`: 通常の `go get` がベンダーパッケージを不必要にダウンロードしないことを確認します。
    *   `tg.run("get", "-t")`: **このコミットで修正された主要な点**。`go get -t` がテスト依存関係を正しく解決し、ベンダーパッケージを適切に処理できることを確認します。

このテストは、ベンダーディレクトリの導入によって生じた `go get -t` と `go list` の問題を、このコミットの変更が完全に解決していることを実証しています。

## 元コミット内容

このコミットは、`go get -t` コマンドおよび `go list` コマンドが、テスト専用のインポートパスを解決する際にベンダーディレクトリを適切に参照するように修正します。これまでは通常のインポートパスについてはベンダーディレクトリの参照が行われていましたが、テスト専用のインポートパスについてはこの処理が欠けていました。この修正により、ベンダーディレクトリを使用しているプロジェクトでテスト依存関係が正しく解決されるようになります。また、`go get` 実行時に "C" 言語のテストインポート（cgo関連）をスキップする改善も含まれています。

## 変更の背景

Go言語のパッケージ管理において、ベンダーディレクトリ（`vendor/`）は、プロジェクトが依存する外部パッケージのコピーをプロジェクト内に保持するための仕組みです。これにより、依存関係の安定性やビルドの再現性が向上します。このコミットが作成された2015年頃は、Go Modulesが導入される前であり、ベンダーディレクトリは `GO15VENDOREXPERIMENT` 環境変数を通じて試験的に導入され、Go 1.5でサポートが開始されたばかりの時期でした。

当時の `go get` や `go list` コマンドは、通常のパッケージインポートについてはベンダーディレクトリ内のパス解決を考慮していましたが、テスト専用のインポート（`p.TestImports` や `p.XTestImports`）についてはこの処理が不足していました。その結果、ベンダーディレクトリ内に存在するテスト依存パッケージが正しく見つけられず、`go get -t` でテスト依存関係を取得しようとしたり、`go list` でパッケージ情報を表示しようとしたりすると、エラーが発生したり、誤った情報が表示されたりする問題がありました。

このコミットは、以下の2つのIssueを解決するために行われました。

*   **Fixes #11628**: `go get -t` がベンダーディレクトリ内のテスト依存関係を解決できない問題。
*   **Fixes #11717**: `go list` がベンダーディレクトリ内のテスト依存関係を正しく表示できない問題。

また、`go get` が "C" インポート（cgo）のテスト依存関係を不必要にダウンロードしようとする挙動も改善の対象となりました。cgoはGoとC言語の連携を可能にするもので、`import "C"` は特別な意味を持つため、通常のパッケージダウンロードの対象外とすべきでした。

## 前提知識の解説

### Go言語のパッケージ管理とベンダーディレクトリ

Go言語では、コードはパッケージとして組織されます。初期のGoでは、`GOPATH` という環境変数で指定されたワークスペース内でパッケージが管理されていました。外部パッケージは `go get` コマンドでダウンロードされ、`GOPATH/src` 以下に配置されます。

**ベンダーディレクトリ (vendor/)**: Go 1.5で導入された `vendor/` ディレクトリは、プロジェクト固有の依存関係を管理するための仕組みです。プロジェクトのルートディレクトリ直下に `vendor/` ディレクトリを作成し、その中に依存パッケージのソースコードを配置することで、プロジェクトは `GOPATH` に依存せず、自身の依存関係を独立して管理できるようになります。これは、異なるプロジェクトが同じ依存パッケージの異なるバージョンを使用する際に発生する問題を回避するのに役立ちます。Goツールチェインは、パッケージを解決する際に、まず現在のパッケージの `vendor/` ディレクトリ内を探し、見つからなければ `GOPATH` を探すという優先順位で動作します。この機能は当初 `GO15VENDOREXPERIMENT=1` 環境変数で有効にする必要がありました。

### `go get` コマンド

`go get` は、指定されたパッケージとその依存関係をダウンロードし、インストールするコマンドです。
*   `go get <package_path>`: 指定されたパッケージをダウンロードします。
*   `go get -t <package_path>`: 指定されたパッケージの通常の依存関係に加えて、テストコード（`_test.go` ファイル）がインポートしているパッケージ（テスト依存関係）もダウンロードします。これは、テストを実行するために必要なすべての依存関係を確実に取得するために使用されます。

### `go list` コマンド

`go list` は、Goパッケージに関する情報を表示するコマンドです。
*   `go list <package_path>`: 指定されたパッケージに関する詳細情報（インポートパス、ファイルリスト、依存関係など）をJSON形式などで出力します。
*   `go list -f "{{.Imports}}"`: パッケージがインポートしている通常の依存関係のリストを表示します。
*   `go list -f "{{.TestImports}}"`: パッケージのテストコードがインポートしている依存関係のリストを表示します。

### `import "C"` (cgo)

`import "C"` はGo言語の特別なインポートパスで、GoプログラムからC言語のコードを呼び出す（またはC言語からGoのコードを呼び出す）ための `cgo` ツールを使用することを示します。これは実際のパッケージではなく、GoとCの間のブリッジを構築するための指示としてGoコンパイラによって特別に扱われます。そのため、`go get` のようなパッケージダウンロードツールがこれを通常の外部パッケージとして扱おうとすると問題が生じます。

### `vendoredImportPath` 関数

Goツールチェイン内部で使用される関数で、与えられたインポートパスがベンダーディレクトリ内に存在するかどうかを判断し、存在する場合はベンダーディレクトリを考慮した正しいインポートパスに変換します。例えば、`vendor/github.com/foo/bar` にあるパッケージ `github.com/foo/bar` をインポートする場合、この関数は `github.com/foo/bar` を `vendor/github.com/foo/bar` として解決する手助けをします。

## 技術的詳細

このコミットの主要な技術的変更点は、`go get` と `go list` の両コマンドにおいて、テスト専用のインポートパス (`p.TestImports` および `p.XTestImports`) に対しても `vendoredImportPath` 関数を適用するようにしたことです。

1.  **`src/cmd/go/get.go` の変更**:
    *   `download` 関数内で、`getTestDeps` が `true` の場合（つまり `go get -t` が実行された場合）、`p.TestImports` と `p.XTestImports` の各パスに対して `vendoredImportPath(p, path)` を呼び出すようになりました。これにより、テスト依存関係のインポートパスがベンダーディレクトリを考慮して正しく解決され、ダウンロード対象が特定されます。
    *   さらに、`path == "C"` の場合は `continue` してダウンロード処理をスキップするロジックが追加されました。これは、cgoの "C" インポートが通常のパッケージではないため、ダウンロードを試みるべきではありません。この行により、`cgo` 関連のインポートがスキップされ、不必要な処理やエラーが回避されます。

2.  **`src/cmd/go/list.go` の変更**:
    *   `runList` 関数内で、`load` された各パッケージ `pkg` の `pkg.TestImports` と `pkg.XTestImports` の各要素に対して、`vendoredImportPath(pkg, path)` を適用し、結果を元のスライスに書き戻すようになりました。これにより、`go list` がテスト依存関係のインポートパスを表示する際に、ベンダーディレクトリを考慮した正しいパスが表示されるようになります。

3.  **`src/cmd/go/vendor_test.go` の追加テスト**:
    *   `TestVendorGet` という新しいテストケースが追加されました。このテストは、ベンダーディレクトリ内に存在するパッケージを通常のインポートとテストインポートの両方で使用するシナリオをシミュレートします。
    *   具体的には、`vendor.org/p` というベンダーパッケージを作成し、`main` パッケージがこれを通常のインポートとテストインポートの両方で使用するように設定します。
    *   `go run m.go`、`go test`、`go list -f "{{.Imports}}"`、`go list -f "{{.TestImports}}"` を実行し、ベンダーディレクトリが正しく解決されていることを確認します。
    *   最後に `go get` と `go get -t` を実行し、ベンダーパッケージが正しく処理され、ダウンロードが不要な場合は行われないことを検証します。特に `go get -t` がテスト依存関係を正しく解決できるようになったことを確認する重要なテストです。

これらの変更により、Goツールチェインはベンダーディレクトリの利用がより堅牢になり、特にテスト依存関係の管理が改善されました。コミットメッセージにある「It would be nice to do this while loading the package, but that breaks the code that checks for direct references to vendor packages when running go test.」という記述は、パッケージロード時にこの処理を行うと、`go test` がベンダーパッケージへの直接参照をチェックする既存のロジックと衝突するため、より限定的な範囲で変更を適用したことを示唆しています。これは、変更の影響範囲を最小限に抑えつつ、問題を解決するための実用的なアプローチです。

## コアとなるコードの解説

### `src/cmd/go/get.go` の変更点

`download` 関数は、`go get` コマンドの主要なロジックを担い、パッケージとその依存関係を再帰的にダウンロードします。
変更箇所は、`getTestDeps` が `true` の場合に実行されるブロックです。これは `go get -t` が指定されたときにテスト依存関係を処理するためのものです。

1.  **`p.TestImports` および `p.XTestImports` のループ**:
    *   `p.TestImports` は通常のテストファイル (`_test.go`) がインポートするパッケージのリストです。
    *   `p.XTestImports` は外部テストファイル (`_test.go` で `package foo_test` の形式) がインポートするパッケージのリストです。
    *   これらのリスト内の各 `path` について処理が行われます。

2.  **`if path == "C" { continue }`**:
    *   これは `cgo` の `import "C"` を特別に扱うためのガード句です。`"C"` は実際のパッケージではないため、ダウンロードを試みるべきではありません。この行により、`cgo` 関連のインポートがスキップされ、不必要なエラーや処理が回避されます。

3.  **`path, _ = vendoredImportPath(p, path)`**:
    *   この行がこのコミットの核心的な変更の一つです。`vendoredImportPath` 関数は、与えられたインポートパス (`path`) が、現在のパッケージ `p` のベンダーディレクトリ内に存在するかどうかをチェックし、もし存在すればそのベンダーパスに解決します。これにより、`go get -t` がベンダーディレクトリ内のテスト依存関係を正しく見つけ、ダウンロード（または既に存在する場合はスキップ）できるようになります。
    *   コメントにある「It's not needed for Imports, because it was done while loading the package.」は、通常の `p.Imports` (非テスト依存関係) については、パッケージのロード段階で既にベンダーパス解決が行われているため、ここでは不要であることを説明しています。

4.  **`download(path, p, stk, false)`**:
    *   解決されたパスで再帰的に `download` 関数を呼び出します。ここで `false` を渡しているのは、「テスト依存関係のテスト依存関係」は取得しないというポリシーのためです。

### `src/cmd/go/list.go` の変更点

`runList` 関数は `go list` コマンドの主要なロジックを担います。
変更箇所は、`load(args)` でロードされた各パッケージ `pkg` に対して行われる処理です。

1.  **`pkg.TestImports` および `pkg.XTestImports` のループ**:
    *   `go list` がパッケージ情報を表示する際に、これらのテストインポートパスもベンダーディレクトリを考慮して正しく表示されるようにします。

2.  **`path, _ = vendoredImportPath(pkg, path)`**:
    *   `go get.go` と同様に、`vendoredImportPath` を適用して、テストインポートパスをベンダーディレクトリを考慮した正しいパスに変換します。
    *   変換されたパスは `pkg.TestImports[i] = path` または `pkg.XTestImports[i] = path` によって元のスライスに書き戻されます。これにより、`go list` の出力に正しいベンダーパスが反映されます。
    *   ここでも「It's not needed for regular imports, because it was done while loading the package.」というコメントがあり、通常のインポートについては既に処理済みであることを示しています。

### `src/cmd/go/vendor_test.go` の追加テスト

`TestVendorGet` は、このコミットの変更が意図通りに機能することを検証するための統合テストです。

    *   `GOPATH` を一時ワークスペースに設定し、`GO15VENDOREXPERIMENT=1` を設定してベンダー機能を有効にします。

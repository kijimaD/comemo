# [インデックス 27257] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおける2つの重要な改善を導入しています。一つは、`nowritebarrier`プラットフォームが指定されたランタイムコード内で書き込みバリアが生成されないように強制すること、もう一つは、スライスされたスライスが元の位置に書き戻される場合に書き込みバリアを省略する最適化です。これにより、Goランタイムの正確性とパフォーマンスが向上します。

## 変更の背景

このコミットには主に2つの背景があります。

1.  **`nowritebarrier`プラットフォームの厳格な適用**: Goのガベージコレクション（GC）は、プログラムの実行と並行して動作するコンカレントなマーク＆スイープアルゴリズムを採用しています。このGCの正確性を保つために「書き込みバリア（Write Barrier）」が使用されます。しかし、Goランタイムの特定の低レベルコード（特にスケジューラやGC自体の一部）では、書き込みバリアの実行が不適切または不可能である場合があります。例えば、P（プロセッサ）がアクティブでない状態や、書き込みバリア自身の内部で無限ループを引き起こす可能性がある場合などです。このような状況では、`go:nowritebarrier`（または`go:nowritebarrierrec`）というプラットフォームを使用して、コンパイラにその関数内で書き込みバリアを生成しないように指示します。このコミット以前は、SSAコンパイラがこの指示を完全に尊重していなかった可能性があり、ランタイムの安定性や正確性に問題を引き起こす可能性がありました。この変更は、SSAコンパイラが`nowritebarrier`の制約を厳格に強制するようにすることで、これらの潜在的な問題を修正します。

2.  **スライス操作における書き込みバリアの最適化**: Goのスライスは、基盤となる配列の一部を参照する軽量なデータ構造です。スライスを別のスライスに代入する際、通常はポインタの変更をGCに通知するために書き込みバリアが必要になります。しかし、あるスライスが別のスライスからスライス操作（例: `s = s[low:high]`）によって作成され、その結果のスライスが元のスライスの位置に書き戻される場合、基盤となる配列のポインタ自体は変更されていません。この場合、書き込みバリアは不要であり、オーバーヘッドを削減できる最適化の機会が存在します。このコミットは、このような特定のシナリオを検出し、不要な書き込みバリアの生成を抑制することで、コンパイルされたコードの効率を向上させます。これは、Issue #14784で報告された問題への対応でもあります。

## 前提知識の解説

### 1. Goのガベージコレクションと書き込みバリア (Write Barrier)

Goのガベージコレクションは、メモリ管理を自動化し、開発者が手動でメモリを解放する手間を省きます。GoのGCは、並行（concurrent）かつ低遅延（low-latency）な三色マーク＆スイープアルゴリズムを採用しています。

*   **三色マーク＆スイープ**:
    *   **白 (White)**: まだGCによって到達可能かどうかが確認されていないオブジェクト。最終的に到達不可能と判断されれば回収される。
    *   **灰 (Gray)**: 到達可能であるとマークされたが、そのオブジェクトが参照する他のオブジェクト（子）がまだスキャンされていないオブジェクト。
    *   **黒 (Black)**: 到達可能であり、そのオブジェクトが参照する全ての子オブジェクトもスキャン済みであるオブジェクト。

*   **書き込みバリア (Write Barrier)**: GCが実行されている最中に、プログラム（ミューテーター）がポインタを更新する際にGCの正確性を保つためのメカニズムです。Goでは主にYuasaスタイルの挿入書き込みバリアが採用されています。これは、ポインタが更新される際に、新しく参照されるオブジェクトがGCによって正しくマークされるようにします。具体的には、白いオブジェクトへのポインタが黒いオブジェクトから書き込まれる場合、その白いオブジェクトを灰色にマークします。これにより、GCがオブジェクトを見落として誤って回収してしまうことを防ぎます。Go 1.8以降はハイブリッド書き込みバリアが導入され、STW（Stop-The-World）時間をさらに短縮しています。

### 2. `go:nowritebarrier` プラグマ

`go:nowritebarrier`は、Goコンパイラに対する特別な指示（プラグマ）です。このプラグマが関数宣言の直前に記述されると、コンパイラはその関数内でポインタの書き込みバリアが生成されることを禁止します。もし書き込みバリアが生成されるようなコードが見つかった場合、コンパイル時にエラーを報告します。

*   **目的**: Goランタイムの非常に低レベルな部分（例: スケジューラ、GCの内部処理、アセンブリコードから呼び出される関数など）では、書き込みバリアの実行が不適切、またはGCのロジックと競合する可能性があります。例えば、GCがポーズしている間にメモリを操作する場合や、書き込みバリア自体がGCの内部状態に依存するため、書き込みバリアのコード内でさらに書き込みバリアがトリガーされると無限再帰に陥る可能性がある場合などです。
*   **`go:nowritebarrierrec`**: `go:nowritebarrier`は対象の関数のみをチェックしますが、`go:nowritebarrierrec`は対象の関数とその関数が再帰的に呼び出す全ての関数（`go:yeswritebarrierrec`でマークされた関数を除く）に対して書き込みバリアの生成を禁止します。ランタイムコードではこちらがより一般的に使用されます。
*   **一般のGo開発者との関連**: これらのプラグマはGoランタイムの内部実装のために存在し、通常のアプリケーション開発で直接使用することはありません。

### 3. SSA (Static Single Assignment) コンパイラ

SSAは、コンパイラの最適化フェーズで中間表現（IR）を表現するための形式です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。

*   **GoコンパイラにおけるSSA**: Go 1.7から、GoコンパイラのバックエンドはSSA形式に移行しました。これにより、より高度な最適化が可能になり、生成されるコードのパフォーマンスが向上しました。SSAコンパイラは、Goのソースコードを抽象構文木（AST）からSSA形式のIRに変換し、様々な最適化パスを適用した後、最終的に機械語コードを生成します。
*   **本コミットとの関連**: このコミットは、SSAコンパイラがコードを生成する際に、`nowritebarrier`の指示を正しく解釈し、書き込みバリアの生成を制御するように修正しています。

### 4. Goのスライス (Slice)

Goのスライスは、配列のセグメントを参照するデータ構造です。スライスは、ポインタ、長さ、容量の3つの要素で構成されます。

*   **ポインタ**: スライスが参照する基盤となる配列の先頭要素へのポインタ。
*   **長さ (Length)**: スライスに含まれる要素の数。
*   **容量 (Capacity)**: スライスのポインタから基盤となる配列の末尾までの要素の数。

スライス操作（例: `s[low:high]`）は、新しいスライスヘッダを作成しますが、多くの場合、基盤となる配列は元のスライスと共有されます。この特性が、本コミットの最適化の背景となります。

## 技術的詳細

### 1. `nowritebarrier`の強制

このコミットは、SSAコンパイラが関数を処理する際に、その関数に`Nowritebarrier`プラットフォームが設定されているかどうかをチェックするロジックを追加します。

*   `src/cmd/compile/internal/gc/ssa.go`の`buildssa`関数内で、`fn.Func.Pragma&Nowritebarrier != 0`という条件で`s.noWB = true`を設定しています。`s`はSSAコンパイラの状態を保持する`state`構造体です。
*   `state`構造体に`noWB`というフィールドが追加され、これが`true`の場合、書き込みバリアの生成が禁止されます。
*   `insertWBmove`および`insertWBstore`という、SSA形式で書き込みバリアを挿入する関数内で、`if s.noWB { s.Fatalf("write barrier prohibited") }`というチェックが追加されました。これにより、`Nowritebarrier`が設定されている関数内で書き込みバリアが生成されようとすると、コンパイル時に致命的なエラーが発生し、開発者に問題が通知されます。
*   また、`WBLineno`というフィールドが`state`構造体に追加され、最初の書き込みバリアが生成された行番号を記録するようになりました。これはデバッグやエラー報告に役立ちます。

### 2. スライスされたスライスの最適化

この最適化は、`src/cmd/compile/internal/gc/walk.go`の`needwritebarrier`関数に実装されています。この関数は、特定の代入操作に対して書き込みバリアが必要かどうかを判断します。

*   追加されたロジックは以下の通りです。
    ```go
    // No write barrier for writing a sliced slice back to its
    // original location.
    if (r.Op == OSLICE || r.Op == OSLICE3 || r.Op == OSLICESTR) &&
        samesafeexpr(r.Left, l) {
        return false
    }
    ```
*   `r`は代入の右辺、`l`は代入の左辺を表します。
*   `r.Op == OSLICE || r.Op == OSLICE3 || r.Op == OSLICESTR`は、右辺がスライス操作（通常のスライス、3要素スライス、文字列スライス）の結果であることをチェックします。
*   `samesafeexpr(r.Left, l)`は、スライス操作の元となった式（`r.Left`）と代入の左辺（`l`）が、実質的に同じメモリ位置を参照しているかどうかを安全に判断する関数です。
    *   例えば、`p.a = p.a[:5]`というコードでは、`r.Left`は`p.a`、`l`も`p.a`です。この場合、`samesafeexpr`は`true`を返します。
*   この条件が満たされる場合、つまり、元のスライスから作成されたスライスが、その元のスライスの位置に書き戻される場合、基盤となる配列のポインタ自体は変更されていないため、書き込みバリアは不要と判断され、`false`が返されます。これにより、不要な書き込みバリアの生成が抑制されます。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更

*   **`buildssa`関数**: この関数は、Goの関数をSSA形式に変換する主要なエントリポイントです。
    *   `if fn.Func.Pragma&Nowritebarrier != 0 { s.noWB = true }`: ここで、現在の関数`fn`に`Nowritebarrier`プラグマが設定されているかを確認し、もし設定されていれば、SSAコンパイラの状態オブジェクト`s`の`noWB`フィールドを`true`に設定します。これにより、以降のSSA生成プロセスで書き込みバリアの生成が禁止されます。
    *   `defer func() { ... }()`: 遅延実行される関数で、`s.WBLineno`が0でない場合（つまり、書き込みバリアが生成された場合）、その行番号を関数の`WBLineno`フィールドに保存します。これは、`nowritebarrier`が指定されているにもかかわらず書き込みバリアが生成された場合に、エラーメッセージで正確な位置を報告するために使用されます。
*   **`state`構造体**: SSAコンパイラの状態を保持する構造体です。
    *   `noWB bool`: 書き込みバリアの生成が禁止されているかどうかを示すフラグ。
    *   `WBLineno int32`: 最初の書き込みバリアが生成されたソースコード上の行番号。
*   **`insertWBmove`および`insertWBstore`関数**: これらの関数は、SSA形式のコード内でポインタの移動（代入）やストア操作に対して書き込みバリアを挿入する役割を担います。
    *   `if s.noWB { s.Fatalf("write barrier prohibited") }`: `noWB`フラグが`true`の場合、つまり`Nowritebarrier`プラグマが設定されている関数内で書き込みバリアが挿入されようとすると、コンパイラは致命的なエラー（`Fatalf`）を発生させます。これにより、`Nowritebarrier`の制約が厳格に強制されます。
    *   `if s.WBLineno == 0 { s.WBLineno = left.Line }`: `WBLineno`がまだ設定されていない場合、現在の書き込みバリアが挿入される行番号を記録します。

### `src/cmd/compile/internal/gc/walk.go` の変更

*   **`needwritebarrier`関数**: この関数は、GoのAST（抽象構文木）を走査する`walk`フェーズで、特定の代入操作に対して書き込みバリアが必要かどうかを判断します。
    *   追加されたロジックは、スライス操作の結果が元のスライスの位置に書き戻される特定のケースを検出します。
    *   `r.Op == OSLICE || r.Op == OSLICE3 || r.Op == OSLICESTR`: 右辺がスライス操作であることを確認します。`OSLICE`は`s[low:high]`、`OSLICE3`は`s[low:high:cap]`、`OSLICESTR`は文字列のスライス操作に対応します。
    *   `samesafeexpr(r.Left, l)`: このヘルパー関数は、スライス操作の元となった式（`r.Left`、例: `p.a`）と代入の左辺（`l`、例: `p.a`）が、コンパイル時に安全に同じメモリ位置を指していると判断できる場合に`true`を返します。この条件が満たされる場合、ポインタ自体は変更されていないため、書き込みバリアは不要と判断されます。
    *   `return false`: 上記の条件が満たされた場合、書き込みバリアは不要であるため`false`を返し、書き込みバリアの生成を抑制します。

### `test/writebarrier.go` の変更

*   新しいテストケース`f18`が追加されました。このテストケースは、スライスされたスライスが元の位置に書き戻されるシナリオを検証します。
    *   `p.a = p.a[:5]`
    *   `p.a = p.a[3:5]`
    *   `p.a = p.a[1:2:3]`
    *   `p.s = p.s[8:9]` (文字列スライスの場合)
    *   `*x = (*x)[3:5]` (ポインタ経由のスライス操作の場合)
    これらの操作は、いずれも「no barrier」とコメントされており、書き込みバリアが生成されないことを期待しています。このテストは、新しい最適化が正しく機能していることを確認するために追加されました。

# [インデックス 28059] ファイルの概要

このコミットは、Go言語の`net`パッケージにおけるDNSリゾルバの挙動を改善するものです。具体的には、システムがDNS検索ドメイン（`search`ディレクティブ）を`/etc/resolv.conf`ファイルから取得できない場合に、ホスト名から自動的に検索ドメインを推測して設定する機能を追加します。これにより、完全修飾されていないホスト名（例: `myhost`ではなく`myhost.mydomain.com`）の解決がより堅牢になります。

## 元コミット内容

`net: search domain from hostname if no search directives`

このコミットは、`/etc/resolv.conf`ファイルに`search`ディレクティブが指定されていない場合に、ホスト名から検索ドメインを推測して使用するようにGoの`net`パッケージのDNSリゾルバを変更します。これにより、完全修飾されていないホスト名の解決が改善されます。

## 変更の背景

Goの`net`パッケージは、DNSルックアップを行う際にシステムのDNS設定（主に`/etc/resolv.conf`）を読み込みます。この設定ファイルには、DNSサーバーのアドレス（`nameserver`）や、ホスト名を解決する際に自動的に付加されるドメインサフィックスのリスト（`search`）などが含まれています。

このコミットが導入される以前は、`/etc/resolv.conf`が存在しないか、または`search`ディレクティブが明示的に指定されていない場合、GoのDNSリゾルバは検索ドメインを使用しませんでした。これは、例えば`myhost`のような完全修飾されていないホスト名を解決しようとした際に、`myhost.mydomain.com`のように自動的にドメインを付加して検索する挙動が期待される環境において、問題を引き起こす可能性がありました。多くのUnix系システムでは、`resolv.conf`に`search`ディレクティブがない場合でも、システムのホスト名（例: `myhost.mydomain.com`）からドメイン部分（`mydomain.com`）を推測して検索ドメインとして利用する慣習があります。Goの`net`パッケージがこの慣習に従っていなかったため、他のシステムツール（例: `ping`）では解決できるホスト名が、Goアプリケーションでは解決できないという不整合が生じることがありました。

この変更は、このような状況下でのDNS解決の信頼性と互換性を向上させることを目的としています。

## 前提知識の解説

### DNS (Domain Name System)

DNSは、インターネット上のコンピュータやサービスを識別するための階層的な分散型命名システムです。人間が覚えやすいドメイン名（例: `www.example.com`）を、コンピュータが理解できるIPアドレス（例: `192.0.2.1`）に変換する役割を担います。

### `/etc/resolv.conf`

Unix系システムにおいて、DNSリゾルバの設定を記述するファイルです。このファイルには主に以下の情報が含まれます。
- `nameserver`: DNSクエリを送信するDNSサーバーのIPアドレス。複数指定可能で、上から順に試行されます。
- `search`: ホスト名を解決する際に、完全修飾されていないホスト名（例: `myhost`）に対して自動的に付加されるドメインサフィックスのリスト。例えば、`search example.com sub.example.com`と設定されている場合、`myhost`というクエリはまず`myhost.example.com`として、次に`myhost.sub.example.com`として解決が試みられます。
- `domain`: `search`と同様に、デフォルトのドメインサフィックスを指定しますが、`search`が優先されます。
- `options`: リゾルバの挙動を制御するオプション（例: `ndots`, `timeout`, `attempts`）。

### 完全修飾ドメイン名 (FQDN) と非修飾名

- **FQDN (Fully Qualified Domain Name)**: ホスト名とドメイン名が完全に記述された形式（例: `www.example.com`）。DNSツリーのルートからの絶対パスを示します。
- **非修飾名 (Unqualified Name)**: ドメイン名が省略されたホスト名（例: `myhost`）。通常、`resolv.conf`の`search`ディレクティブによってドメインサフィックスが自動的に付加されて解決が試みられます。

### ホスト名とドメイン名の関係

多くのシステムでは、ホスト名自体がFQDNとして設定されている場合があります（例: `myhost.mydomain.com`）。この場合、`mydomain.com`の部分がそのシステムの属するドメインを示唆します。このコミットは、この情報から`search`ドメインを推測するアプローチを取っています。

### Go `net` パッケージ

Go言語の標準ライブラリの一部であり、ネットワークI/O機能を提供します。TCP/IP、UDP、Unixドメインソケットなどのネットワークプロトコルを扱うためのAPIが含まれており、DNSルックアップもこのパッケージを通じて行われます。

## 技術的詳細

このコミットの主要な変更点は、`dnsReadConfig`関数（`/etc/resolv.conf`を読み込む関数）が、`search`ディレクティブが見つからない場合に`dnsDefaultSearch()`関数を呼び出すようになったことです。

1.  **`os.Hostname`の利用**:
    *   `src/net/dnsconfig_unix.go`に`os`パッケージがインポートされ、`getHostname = os.Hostname`という変数宣言が追加されました。これはテストのために`os.Hostname`の挙動をモックできるようにするためのものです。
2.  **`dnsDefaultSearch()`関数の追加**:
    *   この新しい関数は、`getHostname()`（実体は`os.Hostname()`）を呼び出してシステムのホスト名を取得します。
    *   取得したホスト名にドット（`.`）が含まれている場合、最初のドット以降の部分をドメイン名として抽出し、それを検索ドメインのリストとして返します。
    *   例えば、ホスト名が`host.domain.local`であれば、`domain.local`を検索ドメインとして返します。
    *   ホスト名にドットが含まれていない場合（例: `myhost`）、または`getHostname()`がエラーを返した場合は、`nil`（検索ドメインなし）を返します。
    *   `foo.`のように末尾にドットがあるホスト名の場合も、`nil`を返すことで、`""`（空文字列）が検索ドメインとして追加され、不必要なルックアップが発生するのを防ぎます。
3.  **`dnsReadConfig`での統合**:
    *   `dnsReadConfig`関数内で、`/etc/resolv.conf`の読み込みに失敗した場合、またはファイルから`search`ディレクティブが読み込まれなかった場合に、`conf.search = dnsDefaultSearch()`が呼び出されるようになりました。
    *   これにより、明示的な`search`ディレクティブがない場合でも、システムホスト名から推測されたドメインがDNS検索パスに追加され、非修飾名の解決が試みられるようになります。

この変更により、Goアプリケーションは、`resolv.conf`の設定が最小限であるか、あるいは存在しない環境においても、より「期待される」DNS解決の挙動を示すようになります。

## コアとなるコードの解説

### `src/net/dnsconfig_unix.go`

-   **`import "os"`の追加**: `os.Hostname`関数を使用するために`os`パッケージがインポートされました。
-   **`getHostname`変数の導入**: `var getHostname = os.Hostname`という行が追加されました。これは、`os.Hostname`の呼び出しを直接行うのではなく、この変数を通じて行うことで、テスト時に`os.Hostname`の挙動をモック（模擬）できるようにするための設計パターンです。これにより、実際のシステムホスト名に依存せずに`dnsDefaultSearch`のテストが可能になります。
-   **`dnsReadConfig`関数の変更**:
    -   `/etc/resolv.conf`ファイルのオープンに失敗した場合（`if err != nil`ブロック内）や、ファイルから`search`ディレクティブが読み込まれなかった場合（`if len(conf.search) == 0`ブロック内）に、`conf.search = dnsDefaultSearch()`が呼び出されるようになりました。これにより、システムホスト名から推測された検索ドメインが`dnsConfig`構造体に設定されます。
-   **`dnsDefaultSearch()`関数の追加**:
    -   この関数は、システムのホスト名を取得し、そのホスト名からドメイン部分を抽出して検索ドメインとして返します。
    -   `hn, err := getHostname()`: システムのホスト名を取得します。
    -   `if err != nil { return nil }`: ホスト名の取得に失敗した場合は、検索ドメインは設定しません。これは「ベストエフォート」な試みであることを示しています。
    -   `if i := byteIndex(hn, '.'); i >= 0 && i < len(hn)-1 { return []string{hn[i+1:]} }`: ホスト名にドットが含まれている場合、最初のドットの次の文字から文字列の最後までをドメインとして抽出します。例えば、`"host.example.com"`からは`"example.com"`を抽出します。`len(hn)-1`の条件は、`"foo."`のようなホスト名（末尾にドットがあるがドメイン部分がない）の場合に空の文字列を返さないようにするためのものです。
    -   `return nil`: ドットが含まれていないホスト名（例: `myhost`）や、上記条件に合致しない場合は、検索ドメインは設定しません。

### `src/net/dnsconfig_unix_test.go`

-   **`import "errors"`の追加**: テストケースでエラーを生成するために`errors`パッケージがインポートされました。
-   **`TestDNSReadConfig`と`TestDNSReadMissingFile`の変更**:
    -   これらのテスト関数内で、`getHostname`変数を一時的にモックする処理が追加されました。`origGetHostname := getHostname; defer func() { getHostname = origGetHostname }()`は、テストの開始時に元の`getHostname`の値を保存し、テスト終了時にそれを復元するイディオムです。
    -   `getHostname = func() (string, error) { return "host.domain.local", nil }`: テスト中は`os.Hostname()`が常に`"host.domain.local"`を返すように設定されます。これにより、`dnsDefaultSearch()`が`"domain.local"`を返すことを期待してテストが行われます。
    -   `dnsReadMissingFile`テストでは、`resolv.conf`が存在しない場合に`search: []string{"domain.local"}`が期待される`dnsConfig`に含まれるようになりました。
-   **`dnsDefaultSearchTests`構造体と`TestDNSDefaultSearch`関数の追加**:
    -   `dnsDefaultSearchTests`は、異なるホスト名とエラー条件に対する`dnsDefaultSearch`関数の期待される出力を定義するテストケースの集合です。
    -   `TestDNSDefaultSearch`関数は、これらのテストケースをループで実行し、`getHostname`を各テストケースのホスト名とエラーに設定して`dnsDefaultSearch`を呼び出し、結果が期待通りであるか`reflect.DeepEqual`で検証します。
    -   特に、`"foo."`のケースは、空の文字列`""`が検索ドメインとして返されないことを確認するために重要です。これは、空の検索ドメインが不必要なDNSルックアップを引き起こす可能性があるためです。

これらの変更により、GoのDNSリゾルバは、より多くの環境で期待されるDNS解決の挙動を提供し、特に`resolv.conf`が簡素化されているか、または特定の`search`ディレクティブを欠いているシステムでの互換性が向上します。

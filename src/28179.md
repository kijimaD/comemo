# [インデックス 28179] ファイルの概要

このコミットは、Goリンカ（`cmd/link`）が共有ライブラリから動的にインポートされるシンボル（`dynimport`シンボル）の型データを処理する方法に関するバグを修正します。特に、複数の共有ライブラリが相互に依存し、型情報を共有する場合に発生する可能性のあるクラッシュを防ぐための変更です。

    cmd/link: always read type data for dynimport symbols

    Consider three shared libraries:

     libBase.so -- defines a type T
     lib2.so    -- references type T
     lib3.so    -- also references type T, and something from lib2

    lib2.so will contain a type symbol for T in its symbol table, but no
    definition. If, when linking lib3.so the linker reads the symbols from lib2.so
    before libBase.so, the linker didn't read the type data and later crashed.

    The fix is trivial but the test change is a bit messy because the order the
    linker reads the shared libraries in ends up depending on the order of the
    import statements in the file so I had to rename one of the test packages so
    that gofmt doesn't fix the test by accident...

## 元コミット内容

`cmd/link: always read type data for dynimport symbols`

このコミットは、`cmd/link`ツールが動的にインポートされるシンボル（`dynimport`シンボル）の型データを常に読み込むように変更します。これにより、共有ライブラリ間の依存関係が複雑な場合に発生する可能性のあるリンカのクラッシュが修正されます。

## 変更の背景

Go言語は、通常、すべての依存関係を単一のバイナリに静的にリンクすることで知られています。しかし、`cgo`を使用してC言語のコードと連携する場合や、`buildmode=shared`オプションを使用して共有ライブラリを構築する場合には、動的リンクが関与します。

このコミットが修正しようとしている問題は、複数の共有ライブラリが同じ型を参照している場合に発生しました。具体的には、以下のようなシナリオが想定されます。

1.  `libBase.so`という共有ライブラリが、ある型`T`を定義しています。
2.  `lib2.so`という別の共有ライブラリが、型`T`を参照しています。
3.  `lib3.so`というさらに別の共有ライブラリが、型`T`と`lib2.so`内の何かを参照しています。

この状況で、`lib2.so`はシンボルテーブルに型`T`のシンボルを含みますが、その定義は持っていません（定義は`libBase.so`にあります）。リンカが`lib3.so`をリンクする際に、`libBase.so`よりも先に`lib2.so`からシンボルを読み込むと、リンカは型`T`の型データを正しく読み取ることができず、後でクラッシュするという問題が発生していました。

これは、リンカがシンボルを処理する順序と、`dynimport`シンボルの型データがいつ読み込まれるべきかというロジックの間の不整合に起因します。リンカは、既にロードされたシンボルと同じ名前のシンボルを見つけた場合、通常はそれを無視します（`.a`ファイルからのシンボルが「勝つ」ため）。しかし、`dynimport`シンボルの場合には、たとえ名前が重複していても、その型データは常に読み込む必要があるという点が重要でした。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

1.  **Goリンカ (`cmd/link`)**: Goプログラムのビルドプロセスにおいて、コンパイルされたGoパッケージと依存関係を結合して実行可能バイナリや共有ライブラリを生成するツールです。Goのビルドシステムの中核をなします。
2.  **共有ライブラリ (Shared Libraries)**: 複数のプログラムで共有されるコードやデータを含むライブラリファイル（例: Linuxの`.so`、Windowsの`.dll`）。プログラムの実行時に動的にロードされ、メモリを節約し、モジュール性を高めます。Goでは`buildmode=shared`オプションで共有ライブラリを生成できます。
3.  **動的リンク (Dynamic Linking)**: プログラムの実行時に、必要なライブラリをロードしてリンクするプロセス。静的リンクとは異なり、ライブラリのコードは実行可能ファイルに直接埋め込まれません。
4.  **`dynimport`シンボル**: 動的リンクによって外部の共有ライブラリからインポートされるシンボルを指します。Goの文脈では、`cgo`を通じてCライブラリと連携する場合や、Go自身が生成した共有ライブラリを使用する場合に特に重要になります。これらのシンボルは、実行時にOSのダイナミックリンカによって解決されます。
5.  **型データ (Type Data)**: Goのランタイムは、リフレクション、ガベージコレクション、インターフェースのディスパッチなどの機能のために、プログラム内のすべての型に関する詳細なメタデータ（型データ）を必要とします。この型データは、コンパイル時およびリンク時に生成され、バイナリに埋め込まれます。`dynimport`シンボルが参照する型についても、この型データが正しく利用可能である必要があります。
6.  **シンボルテーブル (Symbol Table)**: コンパイルされたオブジェクトファイルやライブラリに含まれる、プログラム内の関数、変数、型などの名前（シンボル）とそのアドレスや属性をマッピングするデータ構造です。リンカはこれを利用してシンボルを解決します。
7.  **Goの共有ライブラリの課題**: 一般的に、Goは単一のプロセス内に複数のGoランタイムが存在することを想定していません。`buildmode=c-shared`で作成された複数のGo共有ライブラリを同じプロセスにロードすると、ガベージコレクションやスタックアンワインドなどのランタイム機能が正しく動作せず、クラッシュを引き起こす可能性があります。このコミットで修正された問題は、この一般的な課題とは異なり、リンカのシンボル解決ロジックにおける特定のバグに焦点を当てています。

## 技術的詳細

このコミットの技術的な核心は、Goリンカの`ldshlibsyms`関数（`src/cmd/link/internal/ld/lib.go`内）におけるシンボル処理ロジックの変更にあります。

以前のリンカの動作では、共有ライブラリからシンボルを読み込む際、既に同じ名前のシンボルがリンカの内部シンボルテーブルに存在する場合、そのシンボルを無視していました。これは、通常、静的ライブラリ（`.a`ファイル）からのシンボルが動的ライブラリからのシンボルよりも優先されるという原則に基づいています。

しかし、`dynimport`シンボル、特に型情報を持つ`dynimport`シンボルに関しては、このロジックが問題を引き起こしました。コミットメッセージの例で言えば、`lib2.so`が`libBase.so`で定義された型`T`を参照している場合、`lib2.so`のシンボルテーブルには`T`のシンボルが存在しますが、その型データは`libBase.so`にあります。リンカが`lib2.so`を先に処理し、`T`のシンボルを`dynimport`として認識しても、もしリンカの内部シンボルテーブルに既に`T`という名前のシンボル（例えば、別のソースから来た、あるいは初期状態のプレースホルダーシンボル）が存在した場合、リンカは`lib2.so`からの`T`の情報を「重複」と見なし、その型データを読み込む処理をスキップしてしまう可能性がありました。

このスキップが問題でした。なぜなら、`dynimport`シンボルは、たとえ定義が別の場所にあっても、その型データはGoランタイムが正しく動作するために不可欠だからです。型データが欠落していると、後でその型を参照する際にランタイムエラーやクラッシュが発生します。

修正は、`ldshlibsyms`関数内の条件文を微調整することによって行われました。具体的には、シンボルが既に存在する場合でも、その既存のシンボルが`obj.SDYNIMPORT`型でない限り、共有ライブラリからのシンボル情報を（特に型データを）読み込むように変更されました。

```go
// 変更前:
// if lsym.Type != 0 {
//     continue
// }

// 変更後:
// if lsym.Type != 0 && lsym.Type != obj.SDYNIMPORT {
//     continue
// }
```

この変更により、リンカは、既に存在するシンボルが`dynimport`シンボルでない限り、共有ライブラリから読み込んだシンボル（特に`dynimport`シンボル）の型データを常に優先して処理するようになります。これにより、型データが欠落するシナリオが回避され、リンカのクラッシュが防止されます。

テストケースの変更も重要です。この修正を検証するために、`misc/cgo/testshared`ディレクトリ内のテストが拡張されました。特に、`dep`というパッケージが`depBase`にリネームされ、`dep3`という新しいパッケージが追加されています。これは、リンカが共有ライブラリを読み込む順序がファイルのインポート順序に依存する可能性があり、`gofmt`による自動整形がテストの意図しない修正を引き起こすのを防ぐためです。新しい`dep3`パッケージは、`dep2`と`depBase`の両方から型を参照し、リンカが特定の順序でライブラリを処理したときに問題が再現されることを確認するためのものです。

## コアとなるコードの解説

変更されたコードスニペットは、`ldshlibsyms`関数の一部です。この関数は、共有ライブラリからシンボルを読み込み、リンカの内部シンボルテーブルに追加する役割を担っています。

-   `lsym := Linklookup(Ctxt, elfsym.Name, 0)`: これは、現在処理している共有ライブラリのシンボル（`elfsym.Name`）が、リンカのコンテキスト（`Ctxt`）内の既存のシンボルテーブルに既に存在するかどうかを検索します。存在すれば`lsym`はその既存のシンボルへのポインタを返します。
-   変更前の条件文 `if lsym.Type != 0` は、「もし`lsym`が既に存在し、その型がゼロ（未定義）でないならば、このシンボルは既に定義されているので、共有ライブラリからの情報を無視して次のシンボルに進む」という意味でした。これは、静的ライブラリからのシンボルが動的ライブラリよりも優先されるという一般的なリンキングのルールに基づいています。
-   しかし、このロジックは`dynimport`シンボルに対して不十分でした。`dynimport`シンボルは、その定義が外部の共有ライブラリにあるため、リンカがその型データを正しく読み込む必要があります。もし`lsym.Type != 0`が真であっても、その`lsym`が`SDYNIMPORT`型でなければ、それはまだ完全な`dynimport`シンボルとして処理されていない可能性があります。
-   変更後の条件文 `if lsym.Type != 0 && lsym.Type != obj.SDYNIMPORT` は、「もし`lsym`が既に存在し、その型がゼロでなく、**かつ**それが`SDYNIMPORT`型でないならば、このシンボルは既に定義されているので無視する」という意味になります。
    -   この新しい条件により、もし既存の`lsym`が`SDYNIMPORT`型である場合（つまり、既に`dynimport`シンボルとして認識されている場合）、または`lsym.Type`がゼロの場合（つまり、まだ定義されていないか、プレースホルダーである場合）、リンカは`continue`せずに、共有ライブラリからのシンボル情報を処理し続けます。
    -   特に、`lsym.Type`がゼロではないが`obj.SDYNIMPORT`でもない場合（例えば、静的ライブラリから読み込まれたシンボル）、そのシンボルは引き続き優先され、共有ライブラリからの情報は無視されます。
    -   しかし、`lsym.Type`がゼロの場合、または`lsym.Type`が`obj.SDYNIMPORT`である場合、リンカは共有ライブラリからの情報を処理し、`lsym.Type = obj.SDYNIMPORT`を設定します。これにより、`dynimport`シンボルの型データが確実に読み込まれるようになります。

この修正は、リンカがシンボルを処理する際の優先順位付けロジックをより正確にし、特に動的リンクされた型情報の完全性を保証するために不可欠でした。

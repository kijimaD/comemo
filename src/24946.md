# [インデックス 24946] ファイルの概要

## 元コミット内容

GoコンパイラのSSAバックエンドにおいて、複素数型 (`complex64`, `complex128`) の値に対する等価 (`==`) および不等価 (`!=`) 演算子をサポートする。

## 変更の背景

Go言語は、組み込み型として複素数型 (`complex64`, `complex128`) を提供しています。これらの型は数学的な計算に広く利用されますが、初期のコンパイラ実装では、浮動小数点数と同様に、複素数に対する直接的な等価比較 (`==`) や不等価比較 (`!=`) のSSA中間表現への変換が欠けているか、あるいは最適化が不十分な状態でした。

このコミット以前は、複素数の比較はコンパイラのより高レベルなAST (Abstract Syntax Tree) 段階で処理されるか、あるいはより汎用的な比較ロジックにフォールバックしていた可能性があります。しかし、SSA形式はコンパイラの最適化パスにおいて非常に重要であり、特定の型に対する演算をSSAレベルで正確に表現することで、より効率的なコード生成や、その後の最適化（例えば、定数伝播、共通部分式除去など）の機会が増えます。

この変更の背景には、GoコンパイラのSSAバックエンドの成熟と、より多くのGo言語の機能がSSA形式で効率的に表現されるべきであるという設計思想があります。複素数の比較は、実部と虚部の両方が等しい場合にのみ真となるため、このロジックをSSAで明示的に表現することが求められました。

## 前提知識の解説

### 1. Goコンパイラの構造

Goコンパイラは複数のステージを経てソースコードを実行可能なバイナリに変換します。主要なステージは以下の通りです。

*   **字句解析 (Lexing)**: ソースコードをトークンに分割します。
*   **構文解析 (Parsing)**: トークンからAST (Abstract Syntax Tree) を構築します。
*   **型チェック (Type Checking)**: ASTの各ノードの型を検証し、型エラーを検出します。
*   **中間表現 (IR) 生成**: ASTをより低レベルな中間表現に変換します。Goコンパイラでは、この中間表現の一つとしてSSA (Static Single Assignment) 形式が用いられます。
*   **SSA (Static Single Assignment) 形式**:
    *   SSAは、各変数が一度だけ代入されるように制約された中間表現です。これにより、データフロー解析や最適化が容易になります。
    *   Goコンパイラでは、ASTからSSA形式への変換が行われ、その後、SSA上で様々な最適化が適用されます。
    *   SSA形式の命令は、`ssa.Op` で表現される操作と、そのオペランド（入力値）から構成されます。
*   **バックエンド (Backend)**: SSA形式から特定アーキテクチャの機械語コードを生成します。

### 2. 複素数型 (Complex Types)

Go言語には `complex64` と `complex128` の2つの複素数型があります。

*   `complex64`: `float32` の実部と虚部を持つ複素数。
*   `complex128`: `float64` の実部と虚部を持つ複素数。

複素数の等価性 (`z1 == z2`) は、その実部と虚部がそれぞれ等しい場合にのみ真となります。つまり、`real(z1) == real(z2)` かつ `imag(z1) == imag(z2)` の両方が真である必要があります。

### 3. `cmd/compile/internal/gc/ssa.go`

このファイルは、Goコンパイラのフロントエンド（`gc`パッケージ）からSSAバックエンドへの変換ロジックを担っています。ASTノード（`Node`構造体）をSSA値（`ssa.Value`構造体）に変換する主要な関数 `(s *state) expr(n *Node)` が含まれています。この関数は、ASTの各演算子 (`n.Op`) に応じて適切なSSA操作を生成します。

### 4. `cmd/compile/internal/gc/testdata/fp_ssa.go`

このファイルは、浮動小数点数 (FP) および複素数 (complex) のSSA変換に関するテストケースを格納しています。コンパイラのSSA生成が正しく行われているかを確認するためのGoコードが含まれています。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/compile/internal/gc/ssa.go` 内の `(s *state) expr(n *Node)` 関数にあります。この関数は、GoのASTノードをSSA形式の命令に変換する役割を担っています。

変更前は、`OLT`, `OEQ`, `ONE`, `OLE`, `OGE`, `OGT` といった比較演算子 (`n.Op`) が処理される際に、複素数型に対する特別なハンドリングはありませんでした。これは、浮動小数点数や整数などの他のプリミティブ型と同様に、`s.newValue2(s.ssaOp(n.Op, n.Left.Type), Types[TBOOL], a, b)` のような汎用的なSSA操作が生成されることを意味します。しかし、複素数の比較は実部と虚部の両方を考慮する必要があるため、この汎用的なアプローチでは不十分です。

このコミットでは、`n.Left.Type.IsComplex()` によって、比較対象の型が複素数であるかをチェックするロジックが追加されました。

1.  **複素数の分解**:
    *   `s.newValue1(ssa.OpComplexReal, pt, a)`: 複素数 `a` の実部を抽出するSSA操作を生成します。
    *   `s.newValue1(ssa.OpComplexImag, pt, a)`: 複素数 `a` の虚部を抽出するSSA操作を生成します。
    *   `pt` は、複素数の実部/虚部の型（`float32` または `float64`）を表します。

2.  **実部と虚部の比較**:
    *   `r := s.newValue2(op, Types[TBOOL], s.newValue1(ssa.OpComplexReal, pt, a), s.newValue1(ssa.OpComplexReal, pt, b))`
        *   これは、2つの複素数 `a` と `b` の実部を比較するSSA操作を生成します。`op` は元の比較演算子 (`OEQ` または `ONE`) に対応する浮動小数点比較SSA操作です。結果はブール型 (`Types[TBOOL]`) となります。
    *   `i := s.newValue2(op, Types[TBOOL], s.newValue1(ssa.OpComplexImag, pt, a), s.newValue1(ssa.OpComplexImag, pt, b))`
        *   同様に、虚部を比較するSSA操作を生成します。

3.  **論理積 (AND) による結合**:
    *   `c := s.newValue2(ssa.OpAnd8, Types[TBOOL], r, i)`
        *   実部の比較結果 `r` と虚部の比較結果 `i` を `ssa.OpAnd8` (8ビット論理AND) で結合します。これにより、両方が真の場合にのみ真となるブール値が生成され、複素数の等価性の定義を満たします。

4.  **等価 (`OEQ`) と不等価 (`ONE`) のハンドリング**:
    *   `case OEQ: return c`: 元の演算子が `==` の場合、上記で計算された `c` (実部と虚部が両方等しいか) をそのまま返します。
    *   `case ONE: return s.newValue1(ssa.OpNot, Types[TBOOL], c)`: 元の演算子が `!=` の場合、`c` の結果を `ssa.OpNot` で反転させます。これは、`a != b` が `!(a == b)` と同等であるという論理に基づいています。

5.  **順序比較の禁止**:
    *   `default: s.Fatalf("ordered complex compare %s", opnames[n.Op])`: 複素数に対する順序比較 (`<`, `<=`, `>`, `>=`) は数学的に意味をなさないため、これらの演算子が複素数に適用された場合はコンパイル時エラー (`Fatalf`) を発生させます。これはGo言語の仕様に準拠した挙動です。

この変更により、Goコンパイラは複素数の比較をSSAレベルで正確かつ効率的に処理できるようになり、その後の最適化パスでより良いコードが生成される可能性が高まります。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更

この変更は、GoコンパイラのSSA生成フェーズにおいて、複素数型の比較演算子 (`==` および `!=`) を適切に処理するためのロジックを追加します。

1.  **`case OLT, OEQ, ONE, OLE, OGE, OGT:`**:
    *   これは、ASTノード `n` の演算子 (`n.Op`) が比較演算子である場合の処理ブロックです。
    *   `a := s.expr(n.Left)` と `b := s.expr(n.Right)` は、比較対象の左辺と右辺の式を再帰的にSSA値に変換します。

2.  **`if n.Left.Type.IsComplex() { ... }`**:
    *   ここで、左辺の型が複素数であるかを確認します。Goでは、比較演算子の両辺は同じ型である必要があるため、左辺が複素数であれば右辺も複素数であることが保証されます。

3.  **`pt := floatForComplex(n.Type)`**:
    *   `floatForComplex` 関数は、複素数型 (`complex64` または `complex128`) に対応する浮動小数点型 (`float32` または `float64`) を返します。これは、複素数の実部と虚部がどの浮動小数点型で表現されているかを知るために必要です。

4.  **`op := s.ssaOp(OEQ, pt)`**:
    *   `s.ssaOp` は、AST演算子 (`OEQ` は `==` に対応) と型 (`pt`) に基づいて、対応するSSA操作 (`ssa.Op`) を取得します。ここでは、浮動小数点数の等価比較を行うSSA操作を取得しています。

5.  **`r := s.newValue2(op, Types[TBOOL], s.newValue1(ssa.OpComplexReal, pt, a), s.newValue1(ssa.OpComplexReal, pt, b))`**:
    *   `s.newValue1(ssa.OpComplexReal, pt, a)` は、複素数 `a` から実部を抽出するSSA命令を生成します。
    *   `s.newValue1(ssa.OpComplexReal, pt, b)` は、複素数 `b` から実部を抽出するSSA命令を生成します。
    *   `s.newValue2(op, Types[TBOOL], ...)` は、抽出された2つの実部を `op` (浮動小数点数の等価比較) で比較し、結果としてブール値 (`Types[TBOOL]`) を生成するSSA命令を作成します。この結果が `r` (real part comparison) です。

6.  **`i := s.newValue2(op, Types[TBOOL], s.newValue1(ssa.OpComplexImag, pt, a), s.newValue1(ssa.OpComplexImag, pt, b))`**:
    *   上記と同様に、複素数 `a` と `b` から虚部を抽出し、それらを比較してブール値 `i` (imaginary part comparison) を生成します。

7.  **`c := s.newValue2(ssa.OpAnd8, Types[TBOOL], r, i)`**:
    *   `ssa.OpAnd8` は、2つのブール値の論理ANDを計算するSSA操作です。
    *   `r` と `i` の両方が真である場合にのみ `c` が真となるように、実部の比較結果と虚部の比較結果を結合します。これが複素数の等価性の定義です。

8.  **`switch n.Op { ... }`**:
    *   元のAST演算子 `n.Op` に応じて最終的なSSA値を返します。
    *   **`case OEQ: return c`**: `==` 演算子の場合、`c` (実部と虚部が両方等しい) をそのまま返します。
    *   **`case ONE: return s.newValue1(ssa.OpNot, Types[TBOOL], c)`**: `!=` 演算子の場合、`c` の結果を `ssa.OpNot` で反転させます。
    *   **`default: s.Fatalf("ordered complex compare %s", opnames[n.Op])`**: `OLT`, `OLE`, `OGE`, `OGT` (順序比較) の場合、複素数には順序関係がないため、コンパイル時エラーを発生させます。

### `src/cmd/compile/internal/gc/testdata/fp_ssa.go` の変更

このファイルには、新しいSSA変換ロジックが正しく機能することを確認するためのテストケースが追加されています。

1.  **`cx128eq_ssa`, `cx128ne_ssa`, `cx64eq_ssa`, `cx64ne_ssa` 関数**:
    *   これらの関数は、`complex128` および `complex64` 型の引数を受け取り、それぞれ `==` または `!=` 演算子を使用して比較を行い、結果のブール値を返します。
    *   `switch {} // prevent inlining` は、コンパイラがこれらの関数をインライン化しないようにするための慣用的な記述です。これにより、SSA生成がこれらの関数呼び出しに対して行われることを保証し、テストの対象となります。

2.  **`expectTrue`, `expectFalse` 関数**:
    *   テスト結果を検証するためのヘルパー関数です。期待されるブール値と実際のブール値を比較し、不一致があればエラーメッセージを出力して失敗カウンタをインクリメントします。

3.  **`complexTest128` および `complexTest64` 関数内のテストケース追加**:
    *   既存の複素数テスト関数内に、新しい比較演算子のテストが追加されています。
    *   `c1 := cx128eq_ssa(a, a)`: 同じ値同士の `==` 比較 (期待値: true)
    *   `c2 := cx128eq_ssa(a, b)`: 異なる値同士の `==` 比較 (期待値: false)
    *   `c3 := cx128ne_ssa(a, a)`: 同じ値同士の `!=` 比較 (期待値: false)
    *   `c4 := cx128ne_ssa(a, b)`: 異なる値同士の `!=` 比較 (期待値: true)
    *   これらの結果が `expectTrue` または `expectFalse` を使って検証されます。

これらのテストケースは、コンパイラが複素数の等価性および不等価性をSSAレベルで正しく処理し、期待されるブール値を生成することを確認するために不可欠です。

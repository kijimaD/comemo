## 変更の背景

Goの`testing`パッケージにおける`t.Parallel()`関数は、テストランナーに対して「このテスト（またはサブテスト）は他の並列テストと並行して実行できる」というシグナルを送るために設計されています。この関数は、テストの実行フローを一度だけ変更するためのものであり、複数回呼び出されることは想定されていません。

しかし、`t.Parallel()`が複数回呼び出された場合、以前のバージョンではその動作が未定義であったり、開発者にとって理解しにくい、あるいはデバッグが困難なバグを引き起こす可能性がありました。例えば、テストが意図しない順序で実行されたり、リソースの競合が発生したりするかもしれません。このような誤用は、特に大規模なテストスイートや複雑なテストロジックにおいて、発見が困難な問題につながります。

このコミットの目的は、`t.Parallel()`の誤用を明確に検出し、開発者に即座にフィードバックを提供することです。複数回呼び出しが発生した場合にパニックを発生させることで、開発者はテストコードの記述ミスを早期に特定し、修正できるようになります。これにより、テストの信頼性と保守性が向上します。

## 前提知識の解説

### Goの`testing`パッケージ

Go言語には、標準ライブラリとして`testing`パッケージが提供されており、ユニットテスト、ベンチマークテスト、例（Example）テストなどを記述するためのフレームワークが含まれています。テスト関数は`TestXxx(*testing.T)`というシグネチャを持ち、`go test`コマンドによって実行されます。

### `t.Parallel()`関数

`*testing.T`型のレシーバーを持つ`Parallel()`メソッドは、現在のテストを並列実行可能としてマークします。この関数が呼び出されると、テストランナーは現在のテストの実行を一時停止し、他の並列テストが開始されるのを待ちます。すべての非並列テストおよび並列テストのシリアルなセットアップフェーズが完了した後、一時停止していた並列テストは再開され、`GOMAXPROCS`または`-parallel`フラグで指定された並列度に応じて並行して実行されます。

重要な点として、`t.Parallel()`はテストの実行モードを「並列」に切り替えるための**一度限りのシグナル**であり、テストの並列実行を繰り返し開始するような関数ではありません。

### サブテスト (`t.Run`)

Goの`testing`パッケージでは、`t.Run()`メソッドを使用してサブテストを定義できます。これにより、関連するテストケースをグループ化し、個別に実行・管理することが可能になります。`t.Parallel()`は、親テストではなく、各サブテストの内部で呼び出すことで、個々のサブテストを並列実行させることができます。

### パニック (panic)

Goにおける`panic`は、プログラムの実行を停止させる回復不能なエラーを示すメカニズムです。通常、プログラムが続行できないような予期せぬ状態に陥った際に使用されます。`panic`が発生すると、現在のゴルーチンの実行が停止し、遅延関数（`defer`）が実行された後、コールスタックを遡って`recover`が呼び出されない限り、プログラム全体が終了します。このコミットでは、`t.Parallel()`の誤用が回復不能なエラーと見なされ、`panic`によって開発者にその事実を通知します。

## 技術的詳細

このコミットは、`testing`パッケージの`T`構造体に新しいフィールドを追加し、`t.Parallel()`メソッドのロジックを変更することで、二重呼び出しの検出を実現しています。

1.  **`T`構造体へのフィールド追加**:
    `testing.T`構造体に`isParallel bool`という新しいフィールドが追加されました。このフィールドは、現在のテストが既に`t.Parallel()`によって並列実行可能としてマークされているかどうかを追跡するために使用されます。初期値は`false`です。

2.  **`t.Parallel()`メソッドの変更**:
    `t.Parallel()`メソッドの冒頭に、`isParallel`フィールドの値をチェックするロジックが追加されました。
    *   もし`t.isParallel`が既に`true`であれば、それは`t.Parallel()`が二度目に呼び出されたことを意味します。この場合、`panic("testing: t.Parallel called multiple times")`が実行され、明確なエラーメッセージと共にプログラムが停止します。
    *   `t.isParallel`が`false`であれば、テストは初めて並列モードに移行しようとしているため、`t.isParallel = true`を設定して、このテストが並列テストであることを記録します。

この変更により、`t.Parallel()`が一度呼び出された後、同じテストコンテキスト内で再度呼び出されると、即座にパニックが発生し、開発者はテストコードの誤りを容易に特定できるようになります。これは、テストの堅牢性を高め、デバッグ時間を削減する上で非常に有効な改善です。

## コアとなるコードの解説

1.  **`T`構造体への`isParallel`フィールドの追加**:
    `type T struct { ... isParallel bool ... }`
    この行は、`testing.T`構造体に`isParallel`という名前のブール型フィールドを追加しています。このフィールドは、現在のテストが既に`t.Parallel()`を呼び出しているかどうかを示すフラグとして機能します。デフォルト値は`false`です。

2.  **`t.Parallel()`メソッド内の二重呼び出しチェック**:
    ```go
    if t.isParallel {
        panic("testing: t.Parallel called multiple times")
    }
    t.isParallel = true
    ```
    `t.Parallel()`メソッドが呼び出された際、まず`t.isParallel`の値がチェックされます。
    *   もし`t.isParallel`が`true`であれば、それはこのテストコンテキストで既に`t.Parallel()`が一度呼び出されていることを意味します。この場合、`panic`関数が呼び出され、「testing: t.Parallel called multiple times」という明確なエラーメッセージと共にプログラムの実行が停止します。これにより、開発者はテストコードの誤用を即座に認識できます。
    *   `t.isParallel`が`false`であれば、これは`t.Parallel()`の最初の呼び出しであるため、`t.isParallel = true`と設定されます。これにより、以降の同じテストコンテキスト内での`t.Parallel()`の呼び出しが検出されるようになります。

このシンプルな変更により、`t.Parallel()`の誤用に対する堅牢なガードが導入され、テストコードの品質とデバッグの容易さが大幅に向上しました。

# [インデックス 24362] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージにおいて、`http.Request.Cancel` 機能の使用時に発生していたデータ競合を修正するものです。具体的には、HTTPトランスポート層の永続的な接続を管理する `readLoop` ゴルーチン内で、リクエストがキャンセルされた際に接続の状態を示す `alive` フラグが適切に更新されないことによって引き起こされる競合状態を解消します。

## 変更の背景

このコミットは、Goの `net/http` パッケージにおけるリクエストキャンセル機能の進化の過程で発生した予期せぬ副作用を修正するものです。元々、Go 1.5で導入された `http.Request.Cancel` チャネル（関連する変更は `https://golang.org/cl/11601`）は、以前の `Transport.CancelRequest` メソッドが抱えていたデータ競合の問題を解決し、「競合のない」キャンセルメカニズムを提供することを目的としていました。しかし、皮肉なことに、この新しい「競合のない」キャンセルチャネルの実装自体が、別のデータ競合を引き起こしてしまいました。

この新たなデータ競合は、Goの組み込みデータ競合検出ツールである `go test -race` を `net/http` パッケージに対して実行した際に発見されました。コミットメッセージによると、このテストは通常モードでは検出されたものの、`short` モード（`go test -short`）ではスキップされるため、Goの継続的インテグレーションダッシュボードでは見過ごされていました。この発見により、`Request.Cancel` がトリガーされた際の `net/http` の内部処理、特に永続的な接続（keep-alive）を管理する部分に不備があることが明らかになり、本コミットによる修正が必要となりました。

## 前提知識の解説

### Goの `net/http` パッケージ

`net/http` はGo言語の標準ライブラリで、HTTPクライアントとサーバーの機能を提供します。ウェブアプリケーションの構築やHTTPリクエストの送信に不可欠なパッケージです。クライアント側では、`http.Client` を使用してHTTPリクエストを送信し、`http.Transport` が実際のネットワーク接続の管理（TCP接続の確立、TLSハンドシェイク、Keep-Alive接続の再利用など）を担当します。

### `http.Request.Cancel`

Go 1.5で導入された `http.Request` 構造体の `Cancel` フィールドは、`<-chan struct{}` 型のチャネルです。このチャネルがクローズされると、関連するHTTPリクエストがキャンセルされるべきであることを `http.Transport` に通知します。これにより、クライアントはタイムアウトやユーザー操作などによって、進行中のHTTPリクエストを外部から安全に中断できるようになります。これは、以前の `Transport.CancelRequest` メソッドが抱えていた、リクエストがまだ `Transport` に登録されていない場合にキャンセルが正しく機能しない、あるいは競合状態を引き起こす可能性があった問題を解決するために導入されました。

### データ競合 (Data Race)

データ競合は、並行プログラミングにおける一般的なバグの一種です。Go言語の文脈では、以下の3つの条件がすべて満たされた場合にデータ競合が発生します。

1.  少なくとも2つのゴルーチンが同時に同じメモリ位置にアクセスする。
2.  それらのアクセスのうち少なくとも1つが書き込み操作である。
3.  それらのアクセスが同期メカニズム（ミューテックス、チャネルなど）によって保護されていない。

データ競合が発生すると、プログラムの動作は予測不能になり、クラッシュ、不正なデータ、セキュリティ脆弱性など、様々な問題を引き起こす可能性があります。

### `go test -race`

`go test -race` は、Go言語に組み込まれている強力なデータ競合検出ツールです。このフラグを付けてテストを実行すると、Goランタイムはメモリアクセスを監視し、上記で定義されたデータ競合の条件が満たされた場合に警告を出力します。これにより、開発者は並行処理のバグを早期に発見し、修正することができます。本コミットのデータ競合もこのツールによって発見されました。

### `net/http/transport.go` と `persistConn.readLoop`

`src/net/http/transport.go` は、`net/http` パッケージの `http.Transport` の主要な実装が含まれるファイルです。このファイルには、HTTP接続の確立、管理、再利用（Keep-Alive）に関するロジックが記述されています。

`persistConn` は、単一の永続的なHTTP/TCP接続を表す構造体です。この構造体には、その接続を介して送受信されるHTTPリクエストとレスポンスを処理するための内部状態が含まれます。

`persistConn.readLoop()` は、`persistConn` ごとに起動されるゴルーチンで、その接続からのレスポンスボディの読み取り、接続のアイドル状態への移行、エラー処理などを担当します。Keep-Alive接続では、この `readLoop` が次のリクエストを待機し、接続を再利用可能にする重要な役割を担います。

## 技術的詳細

今回のデータ競合は、`persistConn.readLoop()` 内で `http.Request.Cancel` がトリガーされた際の `alive` フラグの不適切な管理に起因していました。

`readLoop` は、永続的な接続上でレスポンスを読み取り続けるゴルーチンです。このループ内では、`select` ステートメントを使用して、レスポンスボディの読み取り完了 (`waitForBodyRead`)、リクエストのキャンセル (`rc.req.Cancel`)、または接続のアイドル状態への移行など、複数のイベントを待機します。

問題は、`rc.req.Cancel` チャネルがクローズされた（つまり、リクエストがキャンセルされた）場合に発生しました。この `case` ブロック内では、`pc.t.CancelRequest(rc.req)` が呼び出され、`Transport` に対してリクエストがキャンセルされたことを通知します。しかし、この時点では `readLoop` 自身の内部状態、特に接続がまだ「生きている」ことを示す `alive` フラグが `true` のままでした。

この `alive` フラグは、`persistConn` がアイドルプールに返却される際や、他のゴルーチンがその接続を再利用しようとする際に、接続の有効性を判断するために使用されます。`Request.Cancel` によってリクエストがキャンセルされたにもかかわらず `alive` が `true` のままだと、以下のような競合シナリオが発生する可能性がありました。

1.  あるリクエスト `R1` が `persistConn` を使用して送信される。
2.  `readLoop` が `R1` のレスポンスを待機中に、`R1.Cancel` が外部からトリガーされる。
3.  `readLoop` 内の `select` で `case <-rc.req.Cancel:` が発火し、`pc.t.CancelRequest(rc.req)` が呼ばれる。
4.  しかし、`alive` フラグは `true` のまま。
5.  `readLoop` は、`R1` のキャンセル処理後、接続をアイドルプールに返却する準備をするか、あるいはエラー処理に進む。
6.  この間に、別のゴルーチンがアイドルプールからこの `persistConn` を取得し、新しいリクエスト `R2` のために再利用しようとする。
7.  `readLoop` はまだ完全に終了しておらず、`alive` が `true` のため、`R2` の処理と `readLoop` の残りの処理（例えば、`alive` フラグを `false` に設定する処理が遅れて実行される場合）との間でデータ競合が発生する。

この競合は、`readLoop` が接続の論理的な状態（キャンセルされた）と物理的な状態（`alive` フラグ）を同期できていなかったために発生しました。

## コアとなるコードの変更箇所

```diff
--- a/src/net/http/transport.go
+++ b/src/net/http/transport.go
@@ -975,6 +975,7 @@ func (pc *persistConn) readLoop() {
 			// the underlying bufio reader.
 			select {
 			case <-rc.req.Cancel:
+				alive = false
 				pc.t.CancelRequest(rc.req)
 			case bodyEOF := <-waitForBodyRead:
 				pc.t.setReqCanceler(rc.req, nil) // before pc might return to idle pool
```

## コアとなるコードの解説

変更は `src/net/http/transport.go` ファイルの `persistConn.readLoop()` メソッド内に、たった1行の追加です。

```go
			case <-rc.req.Cancel:
				alive = false // この行が追加された
				pc.t.CancelRequest(rc.req)
```

この `alive = false` という1行が追加されたことで、`rc.req.Cancel` チャネルがクローズされ、リクエストがキャンセルされた直後に、`readLoop` は自身の `alive` フラグを `false` に設定するようになりました。

これにより、リクエストがキャンセルされたという論理的な状態が、`persistConn` の内部状態（`alive` フラグ）に即座に反映されます。`alive` が `false` に設定されることで、`readLoop` はその接続がもはやアクティブではないことを正しく認識し、その後の処理（例えば、接続のクリーンアップやアイドルプールからの除外）が、他のゴルーチンによる接続の再利用と競合することなく安全に行われるようになります。

この修正により、`Request.Cancel` がトリガーされた際の `persistConn` の状態遷移がより堅牢になり、`go test -race` によって検出されたデータ競合が解消されました。

# [インデックス 23290] ファイルの概要

このコミットは、Goリンカー（`cmd/6l`）が共有ライブラリ内の関数へのPC相対参照を処理する方法を改善するものです。具体的には、ELF形式の実行ファイルにおいて、共有ライブラリからインポートされた関数へのPC相対リロケーションを、標準的なELFリンカーと同様にPLT（Procedure Linkage Table）エントリを介して解決するように変更しています。これにより、動的リンクされたGoプログラムの堅牢性と互換性が向上します。

## 変更の背景

この変更は、Goプログラムが共有ライブラリ（特にC言語などで書かれたライブラリ）と連携する際に発生する可能性のあるリンキングの問題を解決するために導入されました。Goリンカー（`6l`）は、ELF形式の実行ファイルを生成する際に、他の共有ライブラリで定義されている関数へのPC相対参照（`R_PCREL`）を適切に処理する必要がありました。

従来のGoリンカーは、このような参照に対して、標準的なELFリンカーが採用するPLT（Procedure Linkage Table）を介した解決メカニズムを完全に実装していなかった可能性があります。その結果、共有ライブラリ内の関数へのPC相対呼び出しが正しく解決されず、実行時エラーや予期せぬ動作を引き起こす可能性がありました。

コミットメッセージにある「Fixes #10690」は、この問題がGitHubのIssue #10690で報告されていたことを示しています。このIssueは、Goプログラムが共有ライブラリ内の関数を呼び出す際に、PC相対リロケーションが原因で発生する具体的なバグや不具合を指摘していたと考えられます。

このコミットの目的は、Goリンカーが標準的なELFリンカーの動作に合わせ、共有ライブラリ内の関数へのPC相対参照をPLTエントリを介して解決することで、動的リンクの互換性と信頼性を向上させることにあります。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

1.  **ELF (Executable and Linkable Format)**:
    Unix系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリ、コアダンプなどに使用される標準的なファイル形式です。プログラムの構造（セクション、シンボルテーブル、リロケーション情報など）を定義します。

2.  **リロケーション (Relocation)**:
    コンパイル時に未解決だったシンボル参照（関数呼び出しや変数アクセスなど）を、リンク時に実際のメモリアドレスに解決するプロセスです。コンパイラは、他のモジュールで定義されている関数やデータの最終的なアドレスを知らないため、リロケーションエントリを生成し、リンカーがこれらの参照を修正するように指示します。

3.  **PC相対リロケーション (PC-relative Relocation)**:
    プログラムカウンタ（PC）からの相対オフセットとしてターゲットアドレスを計算するリロケーションの一種です。これにより、コードがメモリ上のどこにロードされても正しく実行できる「位置独立コード (Position-Independent Code, PIC)」を生成できます。これは共有ライブラリで特に重要です。

4.  **共有ライブラリ (Shared Libraries / Dynamic Link Libraries)**:
    実行時にメモリにロードされ、複数のプログラム間で共有されるライブラリです。これにより、ディスク容量とメモリ使用量を節約できます。プログラムは、実行時に動的リンカーを介して共有ライブラリ内の関数やデータにアクセスします。

5.  **シンボル (Symbol)**:
    プログラム内の関数や変数を識別するための名前です。ELFファイルにはシンボルテーブルが含まれており、各シンボルがその種類（関数、データなど）やアドレスなどの情報と共に記録されます。

6.  **`STT_FUNC` (Symbol Type: Function)**:
    ELFシンボルタイプの一つで、シンボルが関数を参照していることを示します。

7.  **`STT_OBJECT` (Symbol Type: Object)**:
    ELFシンボルタイプの一つで、シンボルがデータオブジェクト（変数など）を参照していることを示します。

8.  **`SDYNIMPORT` (Symbol Dynamic Import)**:
    Goリンカー内部で使われるシンボルタイプで、そのシンボルが動的（共有）ライブラリからインポートされたものであることを示します。

9.  **PLT (Procedure Linkage Table) と GOT (Global Offset Table)**:
    ELF実行ファイルで共有ライブラリ内の関数を呼び出すためのメカニズムです。
    *   **PLT**: 共有ライブラリ内の関数を呼び出す際のエントリポイントとなる小さなコードの断片です。関数が初めて呼び出されると、PLTエントリは動的リンカーに制御を渡し、動的リンカーが関数の実際のアドレスを解決します。
    *   **GOT**: 共有ライブラリ内の関数やデータの実際のアドレスを格納するテーブルです。PLTはGOTを参照し、解決された関数のアドレスをGOTに書き込みます。2回目以降の呼び出しでは、PLTは直接GOTに格納されたアドレスにジャンプします。
    このメカニズムにより、位置独立コード（PIC）と遅延バインディング（関数が実際に呼び出されるまでアドレス解決を遅らせる）が可能になります。

10. **`R_X86_64_PC32` と `R_X86_64_PLT32`**:
    x86-64アーキテクチャにおけるリロケーションタイプです。
    *   `R_X86_64_PC32`: 32ビットのPC相対アドレスに対するリロケーションです。
    *   `R_X86_64_PLT32`: 32ビットのPC相対アドレスで、特にPLTエントリを指すリロケーションです。共有ライブラリ内の関数呼び出しに使用されます。

## 技術的詳細

このコミットの核心は、Goリンカーが共有ライブラリ内の関数へのPC相対参照を検出した際に、適切なELFリロケーションタイプ（`R_X86_64_PLT32`）を生成するように変更することです。

1.  **`LSym`構造体の拡張**:
    `src/cmd/internal/ld/link.go`において、リンカーシンボルを表す`LSym`構造体に`ElfType elf.SymType`という新しいフィールドが追加されました。このフィールドは、シンボルがELFファイル内でどのような種類（関数、データなど）として定義されているかを格納するために使用されます。これにより、リンカーはシンボルの種類に基づいて異なるリロケーション戦略を適用できるようになります。

2.  **共有ライブラリシンボルの`ElfType`設定**:
    `src/cmd/internal/ld/lib.go`の`ldshlibsyms`関数（共有ライブラリからシンボルをロードする役割を持つ）において、共有ライブラリから読み込まれたシンボルに対して`lsym.ElfType = elf.ST_TYPE(s.Info)`という行が追加されました。これにより、共有ライブラリ内の関数シンボルには`elf.STT_FUNC`が、データシンボルには`elf.STT_OBJECT`などが`LSym.ElfType`に正しく設定されるようになります。

3.  **PC相対リロケーションの条件付き処理**:
    `src/cmd/6l/asm.go`の`elfreloc1`関数（ELFリロケーションエントリを生成する）において、`obj.R_PCREL`タイプのリロケーションを処理する部分が変更されました。
    *   以前は、PC相対リロケーションは一律に`ld.R_X86_64_PC32`として処理されていました。
    *   変更後、`r.Xsym.Type == obj.SDYNIMPORT && r.Xsym.ElfType == elf.STT_FUNC`という条件が追加されました。これは、「リロケーションのターゲットシンボル（`r.Xsym`）が動的インポート（`obj.SDYNIMPORT`）であり、かつそのELFタイプが関数（`elf.STT_FUNC`）である」場合に真となります。
    *   この条件が真の場合、リンカーは`ld.R_X86_64_PLT32`リロケーションを生成します。これは、ターゲットが共有ライブラリ内の関数であり、PLTを介して解決されるべきであることを示します。
    *   それ以外の場合（動的インポートではない、または動的インポートだが関数ではない場合）は、引き続き`ld.R_X86_64_PC32`リロケーションが使用されます。

4.  **シンボルテーブルエントリの`ElfType`利用**:
    `src/cmd/internal/ld/symtab.go`の`putelfsym`関数（ELFシンボルテーブルエントリを生成する）において、未定義シンボル（`'U'`）の処理が変更されました。
    *   以前は、未定義シンボルはデフォルトで`STT_NOTYPE`として扱われていました（ただし、`Ctxt.Tlsg`の場合は`STT_TLS`）。
    *   変更後、`type_ = int(x.ElfType)`が設定されるようになりました。これにより、`LSym`に格納された`ElfType`情報が、最終的なELFシンボルテーブルエントリのタイプとして反映されます。これは、動的リンカーがシンボルの種類を正しく認識するために重要です。

これらの変更により、Goリンカーは共有ライブラリ内の関数へのPC相対参照を、標準的なELFリンカーが期待する形式（PLTを介した`R_X86_64_PLT32`リロケーション）で生成できるようになり、動的リンクの互換性と信頼性が向上しました。

## コアとなるコードの解説

このコミットの主要な変更は、Goリンカーが共有ライブラリ内の関数へのPC相対参照を検出した際に、適切なELFリロケーションタイプを生成するように調整することです。

1.  **`LSym`構造体への`ElfType`フィールドの追加 (`src/cmd/internal/ld/link.go`)**:
    `LSym`はリンカーが扱うシンボルを表す構造体です。ここに`ElfType elf.SymType`というフィールドが追加されました。これは、シンボルがELFファイル内で関数（`STT_FUNC`）なのか、データオブジェクト（`STT_OBJECT`）なのかといった種類を明示的に保持するためのものです。この情報がなければ、リンカーは動的インポートされたシンボルが関数なのかデータなのかを区別できず、適切なリロケーション戦略を選択できませんでした。

2.  **共有ライブラリシンボルからの`ElfType`の取得と設定 (`src/cmd/internal/ld/lib.go`)**:

3.  **`elfreloc1`関数におけるPC相対リロケーションの条件分岐 (`src/cmd/6l/asm.go`)**:
    `elfreloc1`関数は、実際のリロケーションエントリをELFファイルに書き込む役割を担います。`obj.R_PCREL`（PC相対リロケーション）を処理する部分に重要な変更が加えられました。
    *   `r.Xsym.Type == obj.SDYNIMPORT && r.Xsym.ElfType == elf.STT_FUNC`という条件が追加されました。これは、リロケーションの対象となるシンボル（`r.Xsym`）が「動的インポートされたシンボル（`obj.SDYNIMPORT`）」であり、かつ「そのELFタイプが関数（`elf.STT_FUNC`）である」場合に真となります。

    *   この条件が偽の場合（例えば、動的インポートされたデータシンボルへの参照や、静的にリンクされるシンボルへの参照の場合）、リンカーは引き続き`ld.R_X86_64_PC32`リロケーションタイプを生成します。

4.  **`putelfsym`関数における未定義シンボルの`ElfType`利用 (`src/cmd/internal/ld/symtab.go`)**:
    `putelfsym`関数は、ELFシンボルテーブルにエントリを追加する際に呼び出されます。未定義シンボル（`'U'`）の処理において、以前はデフォルトで`STT_NOTYPE`が設定されていましたが、変更後は`type_ = int(x.ElfType)`が設定されるようになりました。これにより、`LSym`に格納された`ElfType`情報が、ELFシンボルテーブルの`st_info`フィールド（シンボルの種類とバインディングを定義する）に正確に反映され、動的リンカーがシンボルの種類を正しく解釈できるようになります。

これらの変更は連携して機能し、Goリンカーが共有ライブラリ内の関数へのPC相対参照を、標準的なELFリンカーのセマンティクスに従って処理することを可能にします。これにより、Goプログラムが外部の共有ライブラリとよりシームレスに連携できるようになり、特にCgoを介して共有ライブラリの関数を呼び出すようなシナリオでの安定性が向上します。

## 変更の背景

この変更は、Goプログラムが共有ライブラリ（特にC言語などで書かれたライブラリ）と連携する際に発生する可能性のあるリンキングの問題を解決するために導入されました。Goリンカー（`6l`）は、ELF形式の実行ファイルを生成する際に、他の共有ライブラリで定義されている関数へのPC相対参照（`R_PCREL`）を適切に処理する必要がありました。

従来のGoリンカーは、このような参照に対して、標準的なELFリンカーが採用するPLT（Procedure Linkage Table）を介した解決メカニズムを完全に実装していなかった可能性があります。その結果、共有ライブラリ内の関数へのPC相対呼び出しが正しく解決されず、実行時エラーや予期せぬ動作を引き起こす可能性がありました。

コミットメッセージにある「Fixes #10690」は、この問題がGitHubのIssue #10690で報告されていたことを示しています。このIssueは、Goプログラムが共有ライブラリ内の関数を呼び出す際に、PC相対リロケーションが原因で発生する具体的なバグや不具合を指摘していたと考えられます。

このコミットの目的は、Goリンカーが標準的なELFリンカーの動作に合わせ、共有ライブラリ内の関数へのPC相対参照をPLTエントリを介して解決することで、動的リンクの互換性と信頼性を向上させることにあります。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

1.  **ELF (Executable and Linkable Format)**:
    Unix系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリ、コアダンプなどに使用される標準的なファイル形式です。プログラムの構造（セクション、シンボルテーブル、リロケーション情報など）を定義します。

2.  **リロケーション (Relocation)**:
    コンパイル時に未解決だったシンボル参照（関数呼び出しや変数アクセスなど）を、リンク時に実際のメモリアドレスに解決するプロセスです。コンパイラは、他のモジュールで定義されている関数やデータの最終的なアドレスを知らないため、リロケーションエントリを生成し、リンカーがこれらの参照を修正するように指示します。

3.  **PC相対リロケーション (PC-relative Relocation)**:
    プログラムカウンタ（PC）からの相対オフセットとしてターゲットアドレスを計算するリロケーションの一種です。これにより、コードがメモリ上のどこにロードされても正しく実行できる「位置独立コード (Position-Independent Code, PIC)」を生成できます。これは共有ライブラリで特に重要です。

4.  **共有ライブラリ (Shared Libraries / Dynamic Link Libraries)**:
    実行時にメモリにロードされ、複数のプログラム間で共有されるライブラリです。これにより、ディスク容量とメモリ使用量を節約できます。プログラムは、実行時に動的リンカーを介して共有ライブラリ内の関数やデータにアクセスします。

5.  **シンボル (Symbol)**:
    プログラム内の関数や変数を識別するための名前です。ELFファイルにはシンボルテーブルが含まれており、各シンボルがその種類（関数、データなど）やアドレスなどの情報と共に記録されます。

6.  **`STT_FUNC` (Symbol Type: Function)**:
    ELFシンボルタイプの一つで、シンボルが関数を参照していることを示します。

7.  **`STT_OBJECT` (Symbol Type: Object)**:
    ELFシンボルタイプの一つで、シンボルがデータオブジェクト（変数など）を参照していることを示します。

8.  **`SDYNIMPORT` (Symbol Dynamic Import)**:
    Goリンカー内部で使われるシンボルタイプで、そのシンボルが動的（共有）ライブラリからインポートされたものであることを示します。

9.  **PLT (Procedure Linkage Table) と GOT (Global Offset Table)**:
    ELF実行ファイルで共有ライブラリ内の関数を呼び出すためのメカニズムです。
    *   **PLT**: 共有ライブラリ内の関数を呼び出す際のエントリポイントとなる小さなコードの断片です。関数が初めて呼び出されると、PLTエントリは動的リンカーに制御を渡し、動的リンカーが関数の実際のアドレスを解決します。
    *   **GOT**: 共有ライブラリ内の関数やデータの実際のアドレスを格納するテーブルです。PLTはGOTを参照し、解決された関数のアドレスをGOTに書き込みます。2回目以降の呼び出しでは、PLTは直接GOTに格納されたアドレスにジャンプします。
    このメカニズムにより、位置独立コード（PIC）と遅延バインディング（関数が実際に呼び出されるまでアドレス解決を遅らせる）が可能になります。

10. **`R_X86_64_PC32` と `R_X86_64_PLT32`**:
    x86-64アーキテクチャにおけるリロケーションタイプです。
    *   `R_X86_64_PC32`: 32ビットのPC相対アドレスに対するリロケーションです。
    *   `R_X86_64_PLT32`: 32ビットのPC相対アドレスで、特にPLTエントリを指すリロケーションです。共有ライブラリ内の関数呼び出しに使用されます。

## 技術的詳細

このコミットの核心は、Goリンカーが共有ライブラリ内の関数へのPC相対参照を検出した際に、適切なELFリロケーションタイプ（`R_X86_64_PLT32`）を生成するように変更することです。

1.  **`LSym`構造体の拡張**:
    `src/cmd/internal/ld/link.go`において、リンカーシンボルを表す`LSym`構造体に`ElfType elf.SymType`という新しいフィールドが追加されました。このフィールドは、シンボルがELFファイル内でどのような種類（関数、データなど）として定義されているかを格納するために使用されます。これにより、リンカーはシンボルの種類に基づいて異なるリロケーション戦略を適用できるようになります。

2.  **共有ライブラリシンボルの`ElfType`設定**:
    `src/cmd/internal/ld/lib.go`の`ldshlibsyms`関数（共有ライブラリからシンボルをロードする役割を持つ）において、共有ライブラリから読み込まれたシンボルに対して`lsym.ElfType = elf.ST_TYPE(s.Info)`という行が追加されました。これにより、共有ライブラリ内の関数シンボルには`elf.STT_FUNC`が、データシンボルには`elf.STT_OBJECT`などが`LSym.ElfType`に正しく設定されるようになります。

3.  **PC相対リロケーションの条件付き処理**:
    `src/cmd/6l/asm.go`の`elfreloc1`関数（ELFリロケーションエントリを生成する）において、`obj.R_PCREL`タイプのリロケーションを処理する部分が変更されました。
    *   以前は、PC相対リロケーションは一律に`ld.R_X86_64_PC32`として処理されていました。
    *   変更後、`r.Xsym.Type == obj.SDYNIMPORT && r.Xsym.ElfType == elf.STT_FUNC`という条件が追加されました。これは、「リロケーションのターゲットシンボル（`r.Xsym`）が動的インポート（`obj.SDYNIMPORT`）であり、かつそのELFタイプが関数（`elf.STT_FUNC`）である」場合に真となります。
    *   この条件が真の場合、リンカーは`ld.R_X86_64_PLT32`リロケーションを生成します。これは、ターゲットが共有ライブラリ内の関数であり、PLTを介して解決されるべきであることを示します。
    *   それ以外の場合（動的インポートではない、または動的インポートだが関数ではない場合）は、引き続き`ld.R_X86_64_PC32`リロケーションが使用されます。

4.  **シンボルテーブルエントリの`ElfType`利用**:
    `src/cmd/internal/ld/symtab.go`の`putelfsym`関数（ELFシンボルテーブルエントリを生成する）において、未定義シンボル（`'U'`）の処理が変更されました。
    *   以前は、未定義シンボルはデフォルトで`STT_NOTYPE`が設定されていましたが、変更後は`type_ = int(x.ElfType)`が設定されるようになりました。これにより、`LSym`に格納された`ElfType`情報が、ELFシンボルテーブルの`st_info`フィールド（シンボルの種類とバインディングを定義する）に正確に反映され、動的リンカーがシンボルの種類を正しく解釈できるようになります。

これらの変更により、Goリンカーは共有ライブラリ内の関数へのPC相対参照を、標準的なELFリンカーが期待する形式（PLTを介した`R_X86_64_PLT32`リロケーション）で生成できるようになり、動的リンクの互換性と信頼性が向上しました。

## コアとなるコードの解説

このコミットの主要な変更は、Goリンカーが共有ライブラリ内の関数へのPC相対参照を検出した際に、適切なELFリロケーションタイプを生成するように調整することです。

1.  **`LSym`構造体への`ElfType`フィールドの追加 (`src/cmd/internal/ld/link.go`)**:
    `LSym`はリンカーが扱うシンボルを表す構造体です。ここに`ElfType elf.SymType`というフィールドが追加されました。これは、シンボルがELFファイル内で関数（`STT_FUNC`）なのか、データオブジェクト（`STT_OBJECT`）なのかといった種類を明示的に保持するためのものです。この情報がなければ、リンカーは動的インポートされたシンボルが関数なのかデータなのかを区別できず、適切なリロケーション戦略を選択できませんでした。

2.  **共有ライブラリシンボルからの`ElfType`の取得と設定 (`src/cmd/internal/ld/lib.go`)**:
    `ldshlibsyms`関数は、共有ライブラリからシンボル情報を読み込む際に呼び出されます。この変更により、読み込んだシンボルのELFタイプ情報（`s.Info`から取得）が`lsym.ElfType`に格納されるようになりました。これにより、Goリンカーは共有ライブラリからインポートされたシンボルの種類を正確に把握できるようになります。

3.  **`elfreloc1`関数におけるPC相対リロケーションの条件分岐 (`src/cmd/6l/asm.go`)**:
    `elfreloc1`関数は、実際のリロケーションエントリをELFファイルに書き込む役割を担います。`obj.R_PCREL`（PC相対リロケーション）を処理する部分に重要な変更が加えられました。
    *   `r.Xsym.Type == obj.SDYNIMPORT && r.Xsym.ElfType == elf.STT_FUNC`という条件が追加されました。これは、リロケーションの対象となるシンボル（`r.Xsym`）が「動的インポートされたシンボル（`obj.SDYNIMPORT`）」であり、かつ「そのELFタイプが関数（`elf.STT_FUNC`）である」場合に真となります。
    *   この条件が真の場合、リンカーは`ld.R_X86_64_PLT32`というリロケーションタイプを生成します。`R_X86_64_PLT32`は、x86-64アーキテクチャにおいて、PLTエントリへのPC相対参照を示すために使用されます。これにより、動的リンカーは実行時にPLTを介して共有ライブラリ内の関数のアドレスを正しく解決できるようになります。
    *   この条件が偽の場合（例えば、動的インポートされたデータシンボルへの参照や、静的にリンクされるシンボルへの参照の場合）、リンカーは引き続き`ld.R_X86_64_PC32`リロケーションタイプを生成します。

4.  **`putelfsym`関数における未定義シンボルの`ElfType`利用 (`src/cmd/internal/ld/symtab.go`)**:
    `putelfsym`関数は、ELFシンボルテーブルにエントリを追加する際に呼び出されます。未定義シンボル（`'U'`）の処理において、以前はデフォルトで`STT_NOTYPE`が設定されていましたが、変更後は`type_ = int(x.ElfType)`が設定されるようになりました。これにより、`LSym`に格納された`ElfType`情報が、ELFシンボルテーブルの`st_info`フィールド（シンボルの種類とバインディングを定義する）に正確に反映され、動的リンカーがシンボルの種類を正しく解釈できるようになります。

これらの変更は連携して機能し、Goリンカーが共有ライブラリ内の関数へのPC相対参照を、標準的なELFリンカーのセマンティクスに従って処理することを可能にします。これにより、Goプログラムが外部の共有ライブラリとよりシームレスに連携できるようになり、特にCgoを介して共有ライブラリの関数を呼び出すようなシナリオでの安定性が向上します。

# [インデックス 27014] ファイルの概要

このコミットは、Go言語のリンカ（`cmd/link`）における`darwin/amd64`アーキテクチャ向けのMach-Oファイル生成処理に関するバグ修正です。具体的には、`c-archive`ビルドモードで生成されたライブラリが、iOSシミュレータ上でテキスト再配置（text-relocation）の問題を引き起こすのを解決します。既存の実装では`c-shared`ビルドモードの場合のみこの問題に対処していましたが、`c-archive`の場合にも同様の処理を適用することで、iOSアプリでの利用時の問題を解消しています。

## 変更の背景

このコミットの背景には、Go言語で書かれたコードをiOSアプリケーションに組み込む際の特定の課題があります。Goは`c-archive`（静的ライブラリ）や`c-shared`（動的ライブラリ）といったビルドモードを提供しており、これによりGoコードをC言語互換のライブラリとしてエクスポートし、他の言語（Objective-CやSwiftなど）から利用することが可能になります。

問題は、`darwin/amd64`アーキテクチャ（主にIntelベースのMacで動作するiOSシミュレータ）において、Goが生成する`c-archive`ライブラリが、`__TEXT`セグメント内の絶対再配置（absolute relocations）に関する問題を抱えていた点にあります。Mach-O形式の実行可能ファイルやライブラリでは、`__TEXT`セグメントは通常、実行可能なコードや読み取り専用データを格納し、位置独立コード（Position Independent Code, PIC）であることが期待されます。これは、ライブラリがメモリ上の任意のアドレスにロードされても正しく動作するために重要です。

既存のGoリンカの実装では、`darwin/amd64`かつ`c-shared`ビルドモードの場合には、`__TEXT`セグメント内の非実行可能セクションにおける絶対再配置の問題に対処していました。これは、外部リンカが`__TEXT`セグメント内の絶対再配置に対して警告またはエラーを出すためです。しかし、`c-archive`ビルドモードの場合にはこの対処が欠けていました。

その結果、`c-archive`でビルドされたGoライブラリをiOSアプリ（特に64ビットシミュレータ向け）に組み込もうとすると、リンカエラーが発生し、アプリケーションのビルドが失敗するという問題が生じていました。このコミットは、`c-archive`ビルドモードにも同様の再配置問題の対処を適用することで、この問題を解決することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **Mach-O (Mach Object) フォーマット**: macOS、iOS、watchOS、tvOSなどのApple製OSで使用される実行可能ファイル、オブジェクトファイル、共有ライブラリ、コアダンプなどのバイナリフォーマットです。Mach-Oファイルは、ヘッダ、ロードコマンド、セグメント、セクションなどで構成されます。
2.  **セグメントとセクション**:
    *   **セグメント**: Mach-Oファイル内の大きな論理的な塊で、通常はメモリ保護の単位となります。代表的なセグメントには`__TEXT`と`__DATA`があります。
    *   **`__TEXT`セグメント**: 実行可能なコードや読み取り専用データ（定数など）を格納します。通常、このセグメントは書き込み不可として保護され、位置独立である（PICである）ことが期待されます。
    *   **`__DATA`セグメント**: 読み書き可能なデータ（グローバル変数など）を格納します。
    *   **セクション**: セグメント内のより小さな論理的な塊で、特定の種類のデータを格納します（例: `__text`セクションはコード、`__const`セクションは定数）。
3.  **再配置 (Relocation)**: プログラムがコンパイルされる際、コードやデータは通常、特定の絶対アドレスではなく、相対アドレスやシンボル名で参照されます。プログラムがメモリにロードされる際や、複数のオブジェクトファイルがリンクされる際に、これらの参照を実際のメモリアドレスに解決するプロセスが再配置です。
    *   **絶対再配置 (Absolute Relocation)**: 特定の絶対メモリアドレスへの参照を解決する再配置です。
    *   **位置独立コード (Position Independent Code, PIC)**: 実行時にメモリ上の任意のアドレスにロードされても正しく動作するように設計されたコードです。共有ライブラリでは、セキュリティ（ASLRなど）やメモリ効率の観点からPICが強く推奨されます。絶対再配置はPICと相性が悪く、特に`__TEXT`セグメント内では問題となることが多いです。
4.  **Goのビルドモード**:
    *   **`c-archive` (`-buildmode=c-archive`)**: GoコードをC言語互換の静的ライブラリ（`.a`ファイル）としてビルドします。このライブラリは、他のC/C++/Objective-Cプロジェクトにリンクできます。
    *   **`c-shared` (`-buildmode=c-shared`)**: GoコードをC言語互換の動的ライブラリ（macOSでは`.dylib`、Linuxでは`.so`）としてビルドします。
5.  **iOSシミュレータ (`darwin/amd64`)**: iOSアプリを開発する際、実機ではなくMac上で動作するシミュレータでテストすることがよくあります。IntelベースのMacでは、このシミュレータは`darwin/amd64`アーキテクチャで動作します。Apple Silicon Macでは`darwin/arm64`シミュレータが使用されますが、このコミットが作成された時点ではIntelベースのシミュレータが主流でした。

## 技術的詳細

このコミットの技術的な核心は、GoリンカがMach-Oファイルを生成する際のセクション配置ロジックの調整にあります。

Goリンカは、GoのコードやデータをMach-Oファイルの適切なセグメントとセクションにマッピングします。`__TEXT`セグメントは実行可能コード用であり、通常は書き込み不可です。しかし、Goのコンパイラやリンカが生成する一部のデータ（例えば、Goランタイムが内部的に使用する特定の読み取り専用データなど）は、本来`__DATA`セグメント（読み書き可能データ用）に配置されるべきですが、誤って`__TEXT`セグメント内の非実行可能セクションに配置されてしまうことがあります。

`darwin/amd64`環境において、外部リンカ（Xcodeが使用する`ld`など）は、`__TEXT`セグメント内に絶対再配置を必要とする非実行可能セクションが存在すると、警告またはエラーを発生させることがあります。これは、`__TEXT`セグメントが位置独立であるべきという原則に反するためです。

この問題を回避するため、Goリンカは特定の条件下で、`__TEXT`セグメントに配置されるべきではない非実行可能セクションを、代わりに`__DATA`セグメントに移動させるというヒューリスティックな処理を行います。

既存の実装では、この処理は以下の条件で実行されていました。
*   セクションが非実行可能である (`sect.Rwx&1 == 0`)
*   アーキテクチャが`arm64`である (`Thearch.Thechar == '7'`)
*   または、アーキテクチャが`amd64`であり、かつビルドモードが`c-shared`である (`Thearch.Thechar == '6' && Buildmode == BuildmodeCShared`)

このコミットは、`amd64`アーキテクチャの場合の条件に`Buildmode == BuildmodeCArchive`を追加することで、`c-archive`ビルドモードでも同様のセクション移動処理が行われるように修正しています。これにより、`c-archive`で生成されたライブラリがiOSシミュレータでリンクされる際に発生していた絶対再配置の問題が解消されます。

具体的には、`__TEXT`セグメントに配置されるべきではない非実行可能セクションが、`newMachoSect(mseg, buf, "__DATA")`によって`__DATA`セグメントに移動されます。これにより、外部リンカが`__TEXT`セグメント内の不適切な再配置について不満を言うことがなくなり、リンクが成功するようになります。

## コアとなるコードの解説

変更されたコードは、Mach-Oセクションを生成する際の条件分岐を修正しています。

元のコード:
```go
	if sect.Rwx&1 == 0 && (Thearch.Thechar == '7' || (Thearch.Thechar == '6' && Buildmode == BuildmodeCShared)) {
		// Darwin external linker on arm64 and on amd64 in c-shared buildmode
		// complains about absolute relocs in __TEXT, so if the section is not
		// executable, put it in __DATA segment.
		msect = newMachoSect(mseg, buf, "__DATA")
```
この条件文は、以下のいずれかの条件が真である場合に、非実行可能セクションを`__DATA`セグメントに移動させることを意味していました。
1.  `sect.Rwx&1 == 0`: セクションが実行可能ではない（最下位ビットが0）。
2.  `Thearch.Thechar == '7'`: アーキテクチャが`arm64`である。
3.  `Thearch.Thechar == '6' && Buildmode == BuildmodeCShared`: アーキテクチャが`amd64`であり、かつビルドモードが`c-shared`である。

修正後のコード:
```go
	if sect.Rwx&1 == 0 && (Thearch.Thechar == '7' || // arm64
		(Thearch.Thechar == '6' && (Buildmode == BuildmodeCShared || Buildmode == BuildmodeCArchive))) { // amd64
		// Darwin external linker on arm64 and on amd64 in c-shared/c-archive buildmode
		// complains about absolute relocs in __TEXT, so if the section is not
		// executable, put it in __DATA segment.
		msect = newMachoSect(mseg, buf, "__DATA")
```
この変更により、`amd64`アーキテクチャの場合の条件が拡張されました。
`Thearch.Thechar == '6' && (Buildmode == BuildmodeCShared || Buildmode == BuildmodeCArchive)`
これは、アーキテクチャが`amd64`であり、かつビルドモードが`c-shared` **または** `c-archive`のいずれかである場合に、非実行可能セクションを`__DATA`セグメントに移動させることを意味します。

この修正によって、`c-archive`ビルドモードでGoライブラリを生成する際にも、`darwin/amd64`環境における外部リンカの制約が考慮されるようになり、iOSシミュレータでのリンクエラーが回避されるようになりました。

## 変更の背景

このコミットは、Goの `net` パッケージに含まれる `TestTCPStress` というストレステストで発生していた競合状態を修正するために導入されました。元のテストコードでは、TCPリスナーのクローズ処理と、そのリスナーからの接続を受け付けるゴルーチン（acceptor goroutine）の終了処理の間にタイミングの問題がありました。

具体的には、テストのメインルーチンが `ln.Close()` を呼び出してリスナーを閉じた後、acceptor goroutineがまだ `ln.Accept()` を呼び出そうとしている可能性がありました。閉じたリスナーに対して `Accept()` を呼び出すとエラーが発生し、テストが不安定になったり、予期せぬパニックを引き起こしたりする可能性がありました。コミットメッセージにある `Fixes #13704` は、この問題がGoのイシュートラッカーで報告されていたことを示しています。

（注: `Fixes #13704` の具体的なイシュー内容は、2015年当時の情報であり、現在のGoイシュートラッカーでは直接参照できませんでした。しかし、コミット内容から問題の性質は明確です。）

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とネットワークプログラミングの基礎知識が必要です。

1.  **Goの並行処理 (Goroutines and Channels)**:
    *   **Goroutine**: Goランタイムによって管理される軽量なスレッドのようなものです。`go` キーワードを使って関数呼び出しの前に置くことで、その関数を新しいゴルーチンで実行できます。
    *   **Channel**: ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは、ゴルーチン間の同期と通信を安全に行うための主要な手段です。このコミットでは、`done := make(chan bool)` のようにブール値を送受信するチャネルが使われています。
    *   **`defer` ステートメント**: `defer` に続く関数呼び出しは、それを囲む関数がリターンする直前に実行されます。これはリソースのクリーンアップ（ファイルのクローズ、ロックの解放など）によく使われます。

2.  **Goの `net` パッケージとTCP通信**:
    *   **`net` パッケージ**: ネットワークI/O機能を提供するGoの標準ライブラリです。TCP/UDP通信、IPアドレスの解決などを扱います。
    *   **`net.Listen("tcp", ":port")`**: 指定されたネットワークアドレスでTCPリスナーを作成します。これにより、クライアントからの接続を受け入れる準備ができます。
    *   **`ln.Accept()`**: リスナーが新しい接続を待機し、接続が確立されると `net.Conn` インターフェースを実装するオブジェクト（TCP接続）とエラーを返します。接続がない場合はブロックされます。
    *   **`ln.Close()`**: リスナーを閉じ、新しい接続の受け入れを停止します。これにより、`Accept()` はエラーを返してブロックを解除されます。
    *   **`net.Conn`**: ネットワーク接続を表すインターフェースで、`Read`、`Write`、`Close` などのメソッドを持ちます。

3.  **競合状態 (Race Condition)**:
    *   複数のゴルーチンが共有リソース（この場合はTCPリスナー `ln`）に同時にアクセスし、そのアクセス順序によってプログラムの最終結果が変わってしまう状態を指します。競合状態はデバッグが困難なバグの一般的な原因です。
    *   このテストでは、メインゴルーチンが `ln.Close()` を呼び出すタイミングと、acceptor goroutineが `ln.Accept()` を呼び出すタイミングが競合していました。

## 技術的詳細

元の `TestTCPStress` では、TCPリスナー `ln` を作成し、それを `defer ln.Close()` で遅延クローズしていました。そして、`go func() { ... ln.Accept() ... }()` でacceptor goroutineを起動していました。

問題は、`defer ln.Close()` がメインのテスト関数が終了する直前に実行されることです。しかし、acceptor goroutineは独立して動作しており、メイン関数が `ln.Close()` を呼び出した時点で、まだ `ln.Accept()` を呼び出そうとしている可能性がありました。

さらに、`done := make(chan bool)` はクライアント接続を処理するゴルーチンが終了したことを通知するために使われていましたが、acceptor goroutine自身の終了を待つメカニズムがありませんでした。そのため、すべてのクライアントゴルーチンが終了し、メイン関数が `ln.Close()` を実行した後も、acceptor goroutineがまだ生き残っており、閉じたリスナーに対して `Accept()` を呼び出してエラーを発生させていたと考えられます。

この修正は、`done` チャネルの役割を拡張し、acceptor goroutineの終了も適切に同期させることで、この競合状態を解消しています。

## コアとなるコードの解説

1.  **`done` チャネルの宣言位置の変更**:
    *   元のコードでは、`done := make(chan bool)` はクライアント接続を処理するゴルーチンが終了したことを通知するために、acceptor goroutineの起動後に宣言されていました。
    *   修正後、`done := make(chan bool)` は `ln.Close()` の `defer` の代わりに、テスト関数の冒頭近くに移動されました。これにより、`done` チャネルがacceptor goroutineとクライアントゴルーチンの両方の終了を同期するために使用されることが明確になります。

2.  **acceptor goroutineの終了同期**:
    *   acceptor goroutineの内部に `defer func() { done <- true }()` が追加されました。これは、acceptor goroutineが `for {}` ループを抜けて終了する際に、`done` チャネルに `true` を送信することを保証します。
    *   `ln.Accept()` がエラー（特に `ln.Close()` によって発生するエラー）を返してループを抜けた後、この `defer` 関数が実行され、acceptor goroutineの終了がメインのテスト関数に通知されます。

3.  **`ln.Close()` の呼び出し位置の変更**:
    *   元のコードでは `defer ln.Close()` が使われていましたが、これはテスト関数がリターンする直前に実行されます。
    *   修正後、`ln.Close()` は `for i := 0; i < conns; i++ { <-done }` のループ（すべてのクライアントゴルーチンの終了を待機する部分）の**後**に移動されました。
    *   これにより、すべてのクライアントゴルーチンが終了し、かつacceptor goroutineが `done <- true` を送信するのを待ってから `ln.Close()` が実行されるようになります。

4.  **acceptor goroutineの明示的な待機**:
    *   `ln.Close()` の呼び出し後、`<-done` が追加されました。これは、acceptor goroutineが `done` チャネルに値を送信するのを明示的に待機します。
    *   この変更により、テストのメイン関数は、すべてのクライアントゴルーチンとacceptor goroutineの両方が完全に終了したことを確認してから、テストを終了するようになります。

これらの変更により、`ln.Close()` が呼び出される前にacceptor goroutineが安全に終了し、閉じたリスナーに対する `Accept()` 呼び出しによる競合状態が解消されます。テストの安定性と信頼性が向上しました。

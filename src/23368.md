# [インデックス 23368] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ(GC)が使用するヒープビットマップの表現を、従来の4ビットから2ビットに削減するものです。これにより、メモリ使用量の削減とGC性能の向上が期待されます。特に、オブジェクト内のポインタ情報をエンコードする方法が変更され、マークビットやチェックマークビットの扱いも最適化されています。

## 元コミット内容

このコミットは、Goランタイムのヒープビットマップを4ビットから2ビットに削減することを目的としています。以前の変更では、ヒープ以外の型ビットマップが1ビット（ポインタか否か）で表現されるようになりました。このコミット以前は、ヒープビットマップは各ワードに対して2ビットの型情報、そしてオブジェクトの最初のワードに対してマークビットとチェックマークビットを格納していました。

今回の変更では、ヒープビットマップを2ビットに削減します。この2ビットのうち1ビットはポインタか否かを示すために専念され、もう1ビットはマーク、チェックマーク、および「このオブジェクト内のポインタを見つけるためにスキャンを続ける」という情報のために使用されます。

このコミットでは、`heapBitsSetType` 関数が非常に遅いものの、明らかに正しいコードに置き換えられています。これは、後続のコミットで最適化される予定です（ただし、この新しいコードはGo 1.4よりも高速であると述べられています）。

## 変更の背景

Goのガベージコレクタは、ヒープ上のオブジェクトがポインタを含むかどうかを効率的に識別する必要があります。この情報は「ヒープビットマップ」と呼ばれるデータ構造に格納されます。従来のGoランタイムでは、このヒープビットマップは各ワードに対して4ビットを使用していました。この4ビットは、ポインタ情報だけでなく、GCのマークビットやチェックマークビットなど、様々なメタデータをエンコードしていました。

しかし、メモリ使用量の削減とGC性能の向上は、Goランタイム開発における継続的な目標です。4ビットのビットマップは、特に大規模なヒープを持つアプリケーションにおいて、かなりのメモリオーバーヘッドとなる可能性がありました。また、ビットマップの読み書きの複雑さも性能に影響を与えていました。

このコミットの背景には、ヒープ以外の型ビットマップが既に1ビットに削減されていたという先行する変更があります。この成功を受けて、ヒープビットマップもよりコンパクトな表現に移行することで、メモリ効率をさらに高め、GCのサイクルタイムを短縮することが目指されました。特に、オブジェクト内のポインタの有無を識別するのに必要な最小限の情報に絞り込むことで、ビットマップのサイズを半分に削減し、キャッシュ効率の向上やメモリ帯域幅の節約を図ることが狙いです。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goのガベージコレクタは、主に並行マーク＆スイープ方式を採用しています。これは、プログラムの実行と並行してガベージコレクションを実行し、アプリケーションの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えることを目指します。GCの基本的な流れは以下の通りです。

1.  **マークフェーズ**: GCは、ルート（スタック、グローバル変数など）から到達可能なすべてのオブジェクトを「ライブ」としてマークします。このフェーズでは、オブジェクトがポインタを含むかどうかを正確に知る必要があります。
2.  **スイープフェーズ**: マークされなかった（到達不可能な）オブジェクトが「ガベージ」として識別され、それらが占めていたメモリが解放され、再利用可能になります。

このプロセスにおいて、オブジェクト内のどの部分がポインタであり、どの部分が非ポインタ（スカラー値）であるかを正確に識別することが極めて重要です。誤ってポインタをスカラーとして扱えば、ライブオブジェクトが回収されてしまう（use-after-free）可能性があり、逆にスカラーをポインタとして扱えば、不要なオブジェクトがマークされ続けてメモリリークにつながる可能性があります。

### ヒープビットマップ

ヒープビットマップは、GoのGCがヒープ上の各ワードがポインタであるか否かを迅速に判断するために使用するデータ構造です。ヒープ上のメモリ領域に対応する形で、各ワード（`ptrSize`、通常は4バイトまたは8バイト）に対して数ビットの情報が割り当てられます。GCは、このビットマップを参照することで、オブジェクトをスキャンする際にどのワードをたどるべきかを判断します。

### 1ビット、2ビット、4ビットビットマップ

*   **1ビットビットマップ**: 最も単純な形式で、各ワードがポインタであるか否か（1または0）のみを表現します。スタックフレームやグローバル変数のビットマップで使われていました。
*   **2ビットビットマップ**: 各ワードに対して2ビットを使用します。これにより、ポインタ情報に加えて、より多くのメタデータ（例えば、マーク状態やオブジェクトの構造に関するヒント）をエンコードできます。
*   **4ビットビットマップ**: 従来のヒープビットマップで使われていた形式です。各ワードに対して4ビットを使用し、ポインタ情報、マークビット、チェックマークビット、その他の補助情報を格納していました。このコミットの変更対象です。

### `ptrSize`

`ptrSize` は、システムアーキテクチャにおけるポインタのサイズをバイト単位で表します。32ビットシステムでは4バイト、64ビットシステムでは8バイトです。ヒープビットマップの設計において、各ワードのサイズを決定する上で重要な定数です。

### `typeDead`, `typeScalar`, `typePointer` (旧エンコーディング)

このコミット以前の型ビットマップ（特にGo型記述子に埋め込まれたもの）では、以下のような2ビット値が使われていました。

*   `00` - `typeDead`: ポインタではなく、オブジェクトの残りの部分にもポインタがないことを示す。
*   `01` - `typeScalar`: ポインタではないことを示す。
*   `10` - `typePointer`: GCがトレースすべきポインタであることを示す。
*   `11` - 未使用。

`typeDead` は、オブジェクトの残りの部分をスキャンする必要がないことをGCに伝えるための最適化でした。

### チェックマークモード

チェックマークモードは、GoのGCにおける健全性チェック機能です。通常のGCサイクルとは別に、世界を停止させて（ストップ・ザ・ワールド）、オブジェクトグラフを再走査し、すべてのライブオブジェクトが正しくマークされていることを確認します。これは、GCの実装にバグがないことを検証するための重要なメカニズムです。このモードでは、ヒープビットマップ内の特定のビットがチェックマーク情報のために再利用されます。

## 技術的詳細

このコミットの核心は、ヒープビットマップのエンコーディングを4ビットから2ビットに削減し、それに伴うランタイムコードの変更です。

### 4ビットから2ビットへの変更

従来の4ビットエンコーディングでは、1バイトで2ワード分の情報（各ワード4ビット）を格納していました。新しい2ビットエンコーディングでは、1バイトで4ワード分の情報（各ワード2ビット）を格納します。これにより、ヒープビットマップが占めるメモリ空間が半分になります。

### 新しい2ビットエンコーディング

各ワードに割り当てられる2ビットの意味は以下の通りです。

*   **下位1ビット (`bitPointer`)**:
    *   `0`: そのワードはポインタではない（スカラー値）。
    *   `1`: そのワードはポインタである。
    このビットは、スタックやBSSセクションの1ビットビットマップと同じ意味を持ちます。

*   **上位1ビット**: このビットの意味は、オブジェクト内のワードの位置によって異なります。
    *   **オブジェクトの最初のワード**: GCの「マーク済み」ビット (`bitMarked`) として機能します。オブジェクトがGCによってマークされたかどうかを示します。
    *   **オブジェクトの2番目のワード**: GCの「チェックマーク済み」ビットとして機能します。チェックマークモードでの健全性チェックに使用されます。
    *   **オブジェクトの3番目以降のワード**: 「スキャンを続ける」ことを示すビットとして機能します。このビットが`0`の場合、そのワード以降のオブジェクトにはポインタがない（「デッド」エンコーディング）と判断され、GCはそのオブジェクトのスキャンを停止できます。これにより、オブジェクト全体をスキャンすることなく、早期にスキャンを終了できる最適化が可能です。

*   **「デッド」エンコーディング (00)**:
    *   下位ビットが`0`（ポインタではない）で、上位ビットも`0`（マーク、チェックマーク、スキャン継続のいずれでもない）の場合、そのワード以降のオブジェクトにはポインタがないことを示します。これは、GCがオブジェクトのスキャンを早期に終了するための重要なヒントとなります。

### ヒープビットマップの格納方法

ヒープビットマップは、`mheap_.arena_start` から逆方向にメモリに格納されます。具体的には、`start-1` のバイトが `start` から `start+3*ptrSize` までの4ワードの情報を保持し、`start-2` のバイトが `start+4*ptrSize` から `start+7*ptrSize` までの4ワードの情報を保持します。各バイト内では、下位2ビットが最初のワード、次の2ビットが次のワード、というように格納されます。

### `heapBits` 構造体と関連メソッドの変更

`src/runtime/mbitmap.go` 内の `heapBits` 構造体と、それに関連するメソッドが新しい2ビットエンコーディングに合わせて大幅に修正されています。

*   `heapBitsForAddr`: 特定のアドレスに対応する `heapBits` を計算するロジックが、2ビットエンコーディングと1バイト4ワードの格納方法に合わせて変更されました。
*   `next`: 次のワードの `heapBits` を取得するロジックが更新されました。
*   `isMarked`, `setMarked`: オブジェクトの最初のワードの上位1ビットを操作するように変更されました。
*   `isPointer`: 下位1ビットをチェックするように変更されました。
*   `hasPointers`: オブジェクトがポインタを含むかどうかを判断する新しいロジックが導入されました。これは、1ワードオブジェクトの場合は常にポインタとみなし、複数ワードオブジェクトの場合は最初の2ワードのビットと3番目以降のワードのスキャン継続ビットをチェックします。
*   `isCheckmarked`, `setCheckmarked`: チェックマークビットのエンコーディングが、オブジェクトのサイズとワードの位置に応じて異なるため、そのロジックが複雑化しています。特に、1ワードオブジェクトの場合はポインタビットがチェックマークビットとして再利用され、複数ワードオブジェクトの場合は2番目のワードの上位1ビットが使用されます。
*   `heapBitsSetType`: 型情報に基づいてヒープビットマップを設定する関数です。1ビットのptrmaskから2ビットのヒープビットマップへの変換ロジックが全面的に書き直されました。このコミットでは「非常に遅い」実装とされていますが、後続のコミットで最適化される前提です。
*   `heapBitsSweepSpan`: スイープ処理中にヒープビットマップを更新する関数です。マークビットをクリアしたり、マークされていないオブジェクトをフリーリストに追加したりするロジックが、新しい2ビットエンコーディングに合わせて変更されました。

### `gcinfo_test.go` の変更

テストコードも、新しいビットマップエンコーディングと関連するロジックを検証するために更新されています。特に、`typeScalar`, `typePointer`, `typeDead` の定数定義が変更され、新しい `infoPtr10` や `infoScalarPtr4` といったビットマップ定義が追加されています。

## コアとなるコードの変更箇所

```go
// src/runtime/mbitmap.go
const (
	bitPointer = 1
	bitMarked  = 2

	heapBitsWidth   = 2                             // heap bitmap bits to describe one pointer
	heapBitmapScale = ptrSize * (8 / heapBitsWidth) // number of data bytes described by one heap bitmap byte
)

// heapBitsForAddr returns the heapBits for the address addr.
func heapBitsForAddr(addr uintptr) heapBits {
	// 2 bits per work, 4 pairs per byte, and a mask is hard coded.
	off := (addr - mheap_.arena_start) / ptrSize
	return heapBits{(*uint8)(unsafe.Pointer(mheap_.arena_start - off/4 - 1)), uint32(2 * (off & 3))}
}

// isMarked reports whether the heap bits have the marked bit set.
// h must describe the initial word of the object.
func (h heapBits) isMarked() bool {
	return *h.bitp&(bitMarked<<h.shift) != 0
}

// isPointer reports whether the heap bits describe a pointer word.
// h must describe the initial word of the object.
func (h heapBits) isPointer() bool {
	return (*h.bitp>>h.shift)&bitPointer != 0
}

// hasPointers reports whether the given object has any pointers.
// It must be told how large the object at h is, so that it does not read too
// far into the bitmap.
// h must describe the initial word of the object.
func (h heapBits) hasPointers(size uintptr) bool {
	if size == ptrSize { // 1-word objects are always pointers
		return true
	}
	// Otherwise, at least a 2-word object, and at least 2-word aligned,
	// so h.shift is either 0 or 4, so we know we can get the bits for the
	// first two words out of *h.bitp.
	// If either of the first two words is a pointer, not pointer free.
	b := uint32(*h.bitp >> h.shift)
	if b&(bitPointer|bitPointer<<heapBitsWidth) != 0 {
		return true
	}
	if size == 2*ptrSize {
		return false
	}
	// At least a 4-word object. Check scan bit (aka marked bit) in third word.
	if h.shift == 0 {
		return b&(bitMarked<<(2*heapBitsWidth)) != 0
	}
	return uint32(*subtractb(h.bitp, 1))&bitMarked != 0
}

// isCheckmarked reports whether the heap bits have the checkmarked bit set.
// It must be told how large the object at h is, because the encoding of the
// checkmark bit varies by size.
// h must describe the initial word of the object.
func (h heapBits) isCheckmarked(size uintptr) bool {
	if size == ptrSize {
		return (*h.bitp>>h.shift)&bitPointer != 0
	}
	// All multiword objects are 2-word aligned,
	// so we know that the initial word's 2-bit pair
	// and the second word's 2-bit pair are in the
	// same heap bitmap byte, *h.bitp.
	return (*h.bitp>>(heapBitsWidth+h.shift))&bitMarked != 0
}

// setCheckmarked sets the checkmarked bit.
// It must be told how large the object at h is, because the encoding of the
// checkmark bit varies by size.
// h must describe the initial word of the object.
func (h heapBits) setCheckmarked(size uintptr) {
	if size == ptrSize {
		atomicor8(h.bitp, bitPointer<<h.shift)
		return
	}
	atomicor8(h.bitp, bitMarked<<(heapBitsWidth+h.shift))
}
```

## コアとなるコードの解説

### 定数とビットマップの基本構造

*   `bitPointer = 1`: 2ビットエンコーディングの下位1ビットで、ワードがポインタであるか否かを示します。
*   `bitMarked = 2`: 2ビットエンコーディングの上位1ビットで、オブジェクトの最初のワードではマークビットとして機能します。
*   `heapBitsWidth = 2`: 各ワードを記述するために使用されるビット数が2ビットであることを明示します。
*   `heapBitmapScale = ptrSize * (8 / heapBitsWidth)`: 1バイトのヒープビットマップが何バイトのデータ（ヒープ上のワード）を記述するかを計算します。2ビット/ワードなので、1バイト（8ビット）で4ワード（`ptrSize * 4` バイト）を記述します。

### `heapBitsForAddr`

この関数は、特定のアドレス `addr` に対応する `heapBits` 構造体（ビットマップのバイトポインタ `bitp` と、そのバイト内のシフト量 `shift` を含む）を返します。
`off := (addr - mheap_.arena_start) / ptrSize` で、`arena_start` からのアドレスのオフセットをワード単位で計算します。
`mheap_.arena_start - off/4 - 1` は、`arena_start` から逆方向に、`off` ワードが属するビットマップバイトの開始アドレスを計算します。`off/4` は、`off` ワードが属するバイトのインデックスです（1バイトで4ワードをカバーするため）。
`uint32(2 * (off & 3))` は、そのバイト内で `off` ワードがどの2ビットペアに位置するかを示すシフト量を計算します。`off & 3` は `off` を4で割った余りであり、0, 1, 2, 3 のいずれかになります。これを2倍することで、0, 2, 4, 6 のシフト量が得られ、バイト内の適切な2ビットペアを指します。

### `isMarked` と `isPointer`

これらのメソッドは、`heapBits` が指す現在のワードのマークビットまたはポインタビットをチェックします。
`isMarked()` は、`bitMarked` を `h.shift` だけ左シフトした値と `*h.bitp` をビットAND演算し、結果が0でないことを確認します。
`isPointer()` は、`bitPointer` を `h.shift` だけ左シフトした値と `*h.bitp` をビットAND演算し、結果が0でないことを確認します。

### `hasPointers`

この関数は、与えられたオブジェクトがポインタを含むかどうかを判断します。
*   1ワードのオブジェクト (`size == ptrSize`) は常にポインタとみなされます。これは、Goのランタイムが1ワードのスカラー値を単独で割り当てることはなく、より大きなアロケーションにまとめるためです。
*   2ワード以上のオブジェクトの場合、最初の2ワードのビットをチェックします。`b&(bitPointer|bitPointer<<heapBitsWidth)` は、最初の2ワードのいずれかにポインタビットが立っているかを効率的に確認します。
*   2ワードオブジェクト (`size == 2*ptrSize`) でポインタがなければ、`false` を返します。
*   4ワード以上のオブジェクトの場合、3番目のワードの上位ビット（スキャン継続ビット）をチェックします。これが立っていれば、さらにポインタが存在する可能性があるため `true` を返します。

### `isCheckmarked` と `setCheckmarked`

これらの関数は、チェックマークビットの読み書きを行います。
*   1ワードオブジェクトの場合、`bitPointer` がチェックマークビットとして再利用されます。
*   複数ワードオブジェクトの場合、2番目のワードの上位ビット (`bitMarked<<(heapBitsWidth+h.shift)`) がチェックマークビットとして使用されます。
`atomicor8` や `atomicand8` を使用して、アトミックにビットを操作し、並行処理におけるデータ競合を防ぎます。

### `heapBitsSetType` 内のループ

この関数は、オブジェクトの型情報（`ptrmask`）に基づいてヒープビットマップを設定します。
ループ内で、各ワードに対して以下の処理を行います。
1.  `atomicand8(h.bitp, ^((bitPointer | bitMarked) << h.shift))`: 現在のワードのポインタビットとマークビットをクリアします。
2.  `if (*addb(ptrmask, j/8)>>(j%8))&1 != 0`: `ptrmask`（1ビットビットマップ）からポインタ情報を読み取り、ポインタであれば、
3.  `atomicor8(h.bitp, bitPointer<<h.shift)`: 現在のワードのポインタビットをセットします。
4.  `if i >= 2`: 3番目以降のワードであれば、
5.  `atomicor8(h.bitp, bitMarked<<h.shift)`: スキャン継続ビット（マークビットと同じ位置）をセットします。
6.  `h = h.next()`: 次のワードに移動します。

この変更により、GoのGCはよりコンパクトなヒープビットマップを使用し、メモリ効率と性能を向上させることができます。特に、オブジェクトのスキャンを早期に終了できる「デッド」エンコーディングの導入は、GCのワークロードを軽減する上で重要です。

## 変更の背景

Goのガベージコレクタは、ヒープ上のオブジェクトがポインタを含むかどうかを効率的に識別する必要があります。この情報は「ヒープビットマップ」と呼ばれるデータ構造に格納されます。従来のGoランタイムでは、このヒープビットマップは各ワードに対して4ビットを使用していました。この4ビットは、ポインタ情報だけでなく、GCのマークビットやチェックマークビットなど、様々なメタデータをエンコードしていました。

しかし、メモリ使用量の削減とGC性能の向上は、Goランタイム開発における継続的な目標です。4ビットのビットマップは、特に大規模なヒープを持つアプリケーションにおいて、かなりのメモリオーバーヘッドとなる可能性がありました。また、ビットマップの読み書きの複雑さも性能に影響を与えていました。

このコミットの背景には、ヒープ以外の型ビットマップが既に1ビットに削減されていたという先行する変更があります。この成功を受けて、ヒープビットマップもよりコンパクトな表現に移行することで、メモリ効率をさらに高め、GCのサイクルタイムを短縮することが目指されました。特に、オブジェクト内のポインタの有無を識別するのに必要な最小限の情報に絞り込むことで、ビットマップのサイズを半分に削減し、キャッシュ効率の向上やメモリ帯域幅の節約を図ることが狙いです。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goのガベージコレクタは、主に並行マーク＆スイープ方式を採用しています。これは、プログラムの実行と並行してガベージコレクションを実行し、アプリケーションの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えることを目指します。GCの基本的な流れは以下の通りです。

1.  **マークフェーズ**: GCは、ルート（スタック、グローバル変数など）から到達可能なすべてのオブジェクトを「ライブ」としてマークします。このフェーズでは、オブジェクトがポインタを含むかどうかを正確に知る必要があります。
2.  **スイープフェーズ**: マークされなかった（到達不可能な）オブジェクトが「ガベージ」として識別され、それらが占めていたメモリが解放され、再利用可能になります。

このプロセスにおいて、オブジェクト内のどの部分がポインタであり、どの部分が非ポインタ（スカラー値）であるかを正確に識別することが極めて重要です。誤ってポインタをスカラーとして扱えば、ライブオブジェクトが回収されてしまう（use-after-free）可能性があり、逆にスカラーをポインタとして扱えば、不要なオブジェクトがマークされ続けてメモリリークにつながる可能性があります。

### ヒープビットマップ

ヒープビットマップは、GoのGCがヒープ上の各ワードがポインタであるか否かを迅速に判断するために使用するデータ構造です。ヒープ上のメモリ領域に対応する形で、各ワード（`ptrSize`、通常は4バイトまたは8バイト）に対して数ビットの情報が割り当てられます。GCは、このビットマップを参照することで、オブジェクトをスキャンする際にどのワードをたどるべきかを判断します。

### 1ビット、2ビット、4ビットビットマップ

*   **1ビットビットマップ**: 最も単純な形式で、各ワードがポインタであるか否か（1または0）のみを表現します。スタックフレームやグローバル変数のビットマップで使われていました。
*   **2ビットビットマップ**: 各ワードに対して2ビットを使用します。これにより、ポインタ情報に加えて、より多くのメタデータ（例えば、マーク状態やオブジェクトの構造に関するヒント）をエンコードできます。
*   **4ビットビットマップ**: 従来のヒープビットマップで使われていた形式です。各ワードに対して4ビットを使用し、ポインタ情報、マークビット、チェックマークビット、その他の補助情報を格納していました。このコミットの変更対象です。

### `ptrSize`

`ptrSize` は、システムアーキテクチャにおけるポインタのサイズをバイト単位で表します。32ビットシステムでは4バイト、64ビットシステムでは8バイトです。ヒープビットマップの設計において、各ワードのサイズを決定する上で重要な定数です。

### `typeDead`, `typeScalar`, `typePointer` (旧エンコーディング)

このコミット以前の型ビットマップ（特にGo型記述子に埋め込まれたもの）では、以下のような2ビット値が使われていました。

*   `00` - `typeDead`: ポインタではなく、オブジェクトの残りの部分にもポインタがないことを示す。
*   `01` - `typeScalar`: ポインタではないことを示す。
*   `10` - `typePointer`: GCがトレースすべきポインタであることを示す。
*   `11` - 未使用。

`typeDead` は、オブジェクトの残りの部分をスキャンする必要がないことをGCに伝えるための最適化でした。

### チェックマークモード

チェックマークモードは、GoのGCにおける健全性チェック機能です。通常のGCサイクルとは別に、世界を停止させて（ストップ・ザ・ワールド）、オブジェクトグラフを再走査し、すべてのライブオブジェクトが正しくマークされていることを確認します。これは、GCの実装にバグがないことを検証するための重要なメカニズムです。このモードでは、ヒープビットマップ内の特定のビットがチェックマーク情報のために再利用されます。

## 技術的詳細

このコミットの核心は、ヒープビットマップのエンコーディングを4ビットから2ビットに削減し、それに伴うランタイムコードの変更です。

### 4ビットから2ビットへの変更

従来の4ビットエンコーディングでは、1バイトで2ワード分の情報（各ワード4ビット）を格納していました。新しい2ビットエンコーディングでは、1バイトで4ワード分の情報（各ワード2ビット）を格納します。これにより、ヒープビットマップが占めるメモリ空間が半分になります。

### 新しい2ビットエンコーディング

各ワードに割り当てられる2ビットの意味は以下の通りです。

*   **下位1ビット (`bitPointer`)**:
    *   `0`: そのワードはポインタではない（スカラー値）。
    *   `1`: そのワードはポインタである。
    このビットは、スタックやBSSセクションの1ビットビットマップと同じ意味を持ちます。

*   **上位1ビット**: このビットの意味は、オブジェクト内のワードの位置によって異なります。
    *   **オブジェクトの最初のワード**: GCの「マーク済み」ビット (`bitMarked`) として機能します。オブジェクトがGCによってマークされたかどうかを示します。
    *   **オブジェクトの2番目のワード**: GCの「チェックマーク済み」ビットとして機能します。チェックマークモードでの健全性チェックに使用されます。
    *   **オブジェクトの3番目以降のワード**: 「スキャンを続ける」ことを示すビットとして機能します。このビットが`0`の場合、そのワード以降のオブジェクトにはポインタがない（「デッド」エンコーディング）と判断され、GCはそのオブジェクトのスキャンを停止できます。これにより、オブジェクト全体をスキャンすることなく、早期にスキャンを終了できる最適化が可能です。

*   **「デッド」エンコーディング (00)**:
    *   下位ビットが`0`（ポインタではない）で、上位ビットも`0`（マーク、チェックマーク、スキャン継続のいずれでもない）の場合、そのワード以降のオブジェクトにはポインタがないことを示します。これは、GCがオブジェクトのスキャンを早期に終了するための重要なヒントとなります。

### ヒープビットマップの格納方法

ヒープビットマップは、`mheap_.arena_start` から逆方向にメモリに格納されます。具体的には、`start-1` のバイトが `start` から `start+3*ptrSize` までの4ワードの情報を保持し、`start-2` のバイトが `start+4*ptrSize` から `start+7*ptrSize` までの4ワードの情報を保持します。各バイト内では、下位2ビットが最初のワード、次の2ビットが次のワード、というように格納されます。

### `heapBits` 構造体と関連メソッドの変更

`src/runtime/mbitmap.go` 内の `heapBits` 構造体と、それに関連するメソッドが新しい2ビットエンコーディングに合わせて大幅に修正されています。

*   `heapBitsForAddr`: 特定のアドレスに対応する `heapBits` を計算するロジックが、2ビットエンコーディングと1バイト4ワードの格納方法に合わせて変更されました。
*   `next`: 次のワードの `heapBits` を取得するロジックが更新されました。
*   `isMarked`, `setMarked`: オブジェクトの最初のワードの上位1ビットを操作するように変更されました。
*   `isPointer`: 下位1ビットをチェックするように変更されました。
*   `hasPointers`: オブジェクトがポインタを含むかどうかを判断する新しいロジックが導入されました。これは、1ワードオブジェクトの場合は常にポインタとみなし、複数ワードオブジェクトの場合は最初の2ワードのビットと3番目以降のワードのスキャン継続ビットをチェックします。
*   `isCheckmarked`, `setCheckmarked`: チェックマークビットのエンコーディングが、オブジェクトのサイズとワードの位置に応じて異なるため、そのロジックが複雑化しています。特に、1ワードオブジェクトの場合はポインタビットがチェックマークビットとして再利用され、複数ワードオブジェクトの場合は2番目のワードの上位1ビットが使用されます。
*   `heapBitsSetType`: 型情報に基づいてヒープビットマップを設定する関数です。1ビットのptrmaskから2ビットのヒープビットマップへの変換ロジックが全面的に書き直されました。このコミットでは「非常に遅い」実装とされていますが、後続のコミットで最適化される前提です。
*   `heapBitsSweepSpan`: スイープ処理中にヒープビットマップを更新する関数です。マークビットをクリアしたり、マークされていないオブジェクトをフリーリストに追加したりするロジックが、新しい2ビットエンコーディングに合わせて変更されました。

### `gcinfo_test.go` の変更

テストコードも、新しいビットマップエンコーディングと関連するロジックを検証するために更新されています。特に、`typeScalar`, `typePointer`, `typeDead` の定数定義が変更され、新しい `infoPtr10` や `infoScalarPtr4` といったビットマップ定義が追加されています。

```go
// src/runtime/mbitmap.go
const (
	bitPointer = 1
	bitMarked  = 2

	heapBitsWidth   = 2                             // heap bitmap bits to describe one pointer
	heapBitmapScale = ptrSize * (8 / heapBitsWidth) // number of data bytes described by one heap bitmap byte
)

// heapBitsForAddr returns the heapBits for the address addr.
func heapBitsForAddr(addr uintptr) heapBits {
	// 2 bits per work, 4 pairs per byte, and a mask is hard coded.
	off := (addr - mheap_.arena_start) / ptrSize
	return heapBits{(*uint8)(unsafe.Pointer(mheap_.arena_start - off/4 - 1)), uint32(2 * (off & 3))}
}

// isMarked reports whether the heap bits have the marked bit set.
// h must describe the initial word of the object.
func (h heapBits) isMarked() bool {
	return *h.bitp&(bitMarked<<h.shift) != 0
}

// isPointer reports whether the heap bits describe a pointer word.
// h must describe the initial word of the object.
func (h heapBits) isPointer() bool {
	return (*h.bitp>>h.shift)&bitPointer != 0
}

// hasPointers reports whether the given object has any pointers.
// It must be told how large the object at h is, so that it does not read too
// far into the bitmap.
// h must describe the initial word of the object.
func (h heapBits) hasPointers(size uintptr) bool {
	if size == ptrSize { // 1-word objects are always pointers
		return true
	}
	// Otherwise, at least a 2-word object, and at least 2-word aligned,
	// so h.shift is either 0 or 4, so we know we can get the bits for the
	// first two words out of *h.bitp.
	// If either of the first two words is a pointer, not pointer free.
	b := uint32(*h.bitp >> h.shift)
	if b&(bitPointer|bitPointer<<heapBitsWidth) != 0 {
		return true
	}
	if size == 2*ptrSize {
		return false
	}
	// At least a 4-word object. Check scan bit (aka marked bit) in third word.
	if h.shift == 0 {
		return b&(bitMarked<<(2*heapBitsWidth)) != 0
	}
	return uint32(*subtractb(h.bitp, 1))&bitMarked != 0
}

// isCheckmarked reports whether the heap bits have the checkmarked bit set.
// It must be told how large the object at h is, because the encoding of the
// checkmark bit varies by size.
// h must describe the initial word of the object.
func (h heapBits) isCheckmarked(size uintptr) bool {
	if size == ptrSize {
		return (*h.bitp>>h.shift)&bitPointer != 0
	}
	// All multiword objects are 2-word aligned,
	// so we know that the initial word's 2-bit pair
	// and the second word's 2-bit pair are in the
	// same heap bitmap byte, *h.bitp.
	return (*h.bitp>>(heapBitsWidth+h.shift))&bitMarked != 0
}

// setCheckmarked sets the checkmarked bit.
// It must be told how large the object at h is, because the encoding of the
// checkmark bit varies by size.
// h must describe the initial word of the object.
func (h heapBits) setCheckmarked(size uintptr) {
	if size == ptrSize {
		atomicor8(h.bitp, bitPointer<<h.shift)
		return
	}
	atomicor8(h.bitp, bitMarked<<(heapBitsWidth+h.shift))
}
```

## コアとなるコードの解説

### 定数とビットマップの基本構造

*   `bitPointer = 1`: 2ビットエンコーディングの下位1ビットで、ワードがポインタであるか否かを示します。
*   `bitMarked = 2`: 2ビットエンコーディングの上位1ビットで、オブジェクトの最初のワードではマークビットとして機能します。
*   `heapBitsWidth = 2`: 各ワードを記述するために使用されるビット数が2ビットであることを明示します。
*   `heapBitmapScale = ptrSize * (8 / heapBitsWidth)`: 1バイトのヒープビットマップが何バイトのデータ（ヒープ上のワード）を記述するかを計算します。2ビット/ワードなので、1バイト（8ビット）で4ワード（`ptrSize * 4` バイト）を記述します。

### `heapBitsForAddr`

この関数は、特定のアドレス `addr` に対応する `heapBits` 構造体（ビットマップのバイトポインタ `bitp` と、そのバイト内のシフト量 `shift` を含む）を返します。
`off := (addr - mheap_.arena_start) / ptrSize` で、`arena_start` からのアドレスのオフセットをワード単位で計算します。
`mheap_.arena_start - off/4 - 1` は、`arena_start` から逆方向に、`off` ワードが属するビットマップバイトの開始アドレスを計算します。`off/4` は、`off` ワードが属するバイトのインデックスです（1バイトで4ワードをカバーするため）。
`uint32(2 * (off & 3))` は、そのバイト内で `off` ワードがどの2ビットペアに位置するかを示すシフト量を計算します。`off & 3` は `off` を4で割った余りであり、0, 1, 2, 3 のいずれかになります。これを2倍することで、0, 2, 4, 6 のシフト量が得られ、バイト内の適切な2ビットペアを指します。

### `isMarked` と `isPointer`

これらのメソッドは、`heapBits` が指す現在のワードのマークビットまたはポインタビットをチェックします。
`isMarked()` は、`bitMarked` を `h.shift` だけ左シフトした値と `*h.bitp` をビットAND演算し、結果が0でないことを確認します。
`isPointer()` は、`bitPointer` を `h.shift` だけ左シフトした値と `*h.bitp` をビットAND演算し、結果が0でないことを確認します。

### `hasPointers`

この関数は、与えられたオブジェクトがポインタを含むかどうかを判断します。
*   1ワードのオブジェクト (`size == ptrSize`) は常にポインタとみなされます。これは、Goのランタイムが1ワードのスカラー値を単独で割り当てることはなく、より大きなアロケーションにまとめるためです。
*   2ワード以上のオブジェクトの場合、最初の2ワードのビットをチェックします。`b&(bitPointer|bitPointer<<heapBitsWidth)` は、最初の2ワードのいずれかにポインタビットが立っているかを効率的に確認します。
*   2ワードオブジェクト (`size == 2*ptrSize`) でポインタがなければ、`false` を返します。
*   4ワード以上のオブジェクトの場合、3番目のワードの上位ビット（スキャン継続ビット）をチェックします。これが立っていれば、さらにポインタが存在する可能性があるため `true` を返します。

### `isCheckmarked` と `setCheckmarked`

これらの関数は、チェックマークビットの読み書きを行います。
*   1ワードオブジェクトの場合、`bitPointer` がチェックマークビットとして再利用されます。
*   複数ワードオブジェクトの場合、2番目のワードの上位ビット (`bitMarked<<(heapBitsWidth+h.shift)`) がチェックマークビットとして使用されます。
`atomicor8` や `atomicand8` を使用して、アトミックにビットを操作し、並行処理におけるデータ競合を防ぎます。

### `heapBitsSetType` 内のループ

この関数は、オブジェクトの型情報（`ptrmask`）に基づいてヒープビットマップを設定します。
ループ内で、各ワードに対して以下の処理を行います。
1.  `atomicand8(h.bitp, ^((bitPointer | bitMarked) << h.shift))`: 現在のワードのポインタビットとマークビットをクリアします。
2.  `if (*addb(ptrmask, j/8)>>(j%8))&1 != 0`: `ptrmask`（1ビットビットマップ）からポインタ情報を読み取り、ポインタであれば、
3.  `atomicor8(h.bitp, bitPointer<<h.shift)`: 現在のワードのポインタビットをセットします。
4.  `if i >= 2`: 3番目以降のワードであれば、
5.  `atomicor8(h.bitp, bitMarked<<h.shift)`: スキャン継続ビット（マークビットと同じ位置）をセットします。
6.  `h = h.next()`: 次のワードに移動します。

この変更により、GoのGCはよりコンパクトなヒープビットマップを使用し、メモリ効率と性能を向上させることができます。特に、オブジェクトのスキャンを早期に終了できる「デッド」エンコーディングの導入は、GCのワークロードを軽減する上で重要です。

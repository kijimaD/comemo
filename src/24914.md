# [インデックス 24914] ファイルの概要

## コミット

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおける`return`ブロックのハンドリングと、ライブ変数解析の正確性に関するバグ修正を目的としています。具体的には、`return`ブロックがメモリの状態（`Store`）を適切に制御として受け取るようにし、到達不能な`RET`命令がライブ変数解析を混乱させる問題を`obj.AEND`マーカーの導入によって解決しています。これにより、コンパイラが生成するコードの正確性と最適化の機会が向上します。

[https://github.com/golang/go/commit/a7cfc759f2b03cb1155477d99384578f2910139c](https://github.com/golang/go/commit/a7cfc759f2b03cb1155477d99384578f2910139c)

## 元コミット内容

```
[dev.ssa] cmd/compile/internal/ssa: handle returns correctly

Make sure that return blocks take a store as their control. Without
this, code was getting inserted between the return and exit blocks.

Use AEND to mark the end of code. The live variable analysis gets
confused when routines end like:
    JMP earlier
    RET
because the RET is unreachable. The RET was incorrectly added to the
last basic block, rendering the JMP invisible to the CFG builder.

Change-Id: I91b32c8b37075347243ff039b4e4385856fba7cd
Reviewed-on: https://go-review.googlesource.com/14398
Reviewed-by: Josh Bleecher Snyder <josharian@gmail.com>
```

## 変更の背景

このコミットは、GoコンパイラのSSAバックエンドにおける2つの主要な問題を解決するために行われました。

1.  **`return`ブロックと`exit`ブロック間のコード挿入**: SSA形式では、プログラムのメモリ状態は`Store`という特殊な値によって追跡されます。`return`ブロックがこの`Store`をその制御（control）として適切に扱わない場合、コンパイラは`return`ブロックと最終的な`exit`ブロックの間に不適切なコードを挿入してしまう可能性がありました。これは、メモリ状態の依存関係が正しく表現されていないために発生します。結果として、生成されるアセンブリコードが意図しない動作をしたり、最適化が妨げられたりする可能性があります。

2.  **到達不能な`RET`命令によるライブ変数解析の混乱**: Goコンパイラのバックエンドでは、アセンブリコードを生成する前に、ライブ変数解析（Live Variable Analysis）という重要な最適化パスを実行します。この解析は、特定のプログラムポイントでどの変数が将来使用される可能性があるかを判断します。しかし、以下のようなコードパターンが存在する場合、問題が発生していました。

    ```assembly
    JMP earlier_label
    RET
    ```

    この例では、`RET`命令は`JMP`命令によって常にスキップされるため、到達不能です。しかし、コンパイラの制御フローグラフ (CFG) ビルダーがこの到達不能な`RET`を最後の基本ブロックに誤って含めてしまうことがありました。これにより、`JMP`命令がCFGビルダーから「見えなく」なり、ライブ変数解析がプログラムの実際の実行パスを誤解し、不正確な結果を導き出す可能性がありました。不正確なライブ変数解析は、レジスタ割り当ての非効率性や、誤ったコード生成につながる恐れがあります。

これらの問題を解決するために、`return`ブロックの`Store`制御の明示的な設定と、コードの終わりを示す新しいマーカー`obj.AEND`の導入が必要とされました。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) フォーム

SSA (Static Single Assignment) フォームは、コンパイラの最適化フェーズで広く使用される中間表現です。SSAの主要な特性は、各変数が一度だけ代入されることを保証する点にあります。これにより、データフロー解析が大幅に簡素化され、より強力な最適化（例: 共通部分式の削除、定数伝播、デッドコード削除）が可能になります。Goコンパイラは、Go 1.7以降、最適化の主要な部分でSSAを使用しています。

### Goコンパイラのバックエンド

Goコンパイラのバックエンドは、SSA形式のコードを受け取り、ターゲットアーキテクチャ（例: x86-64, ARM）のアセンブリコードに変換する役割を担います。このプロセスには、レジスタ割り当て、命令スケジューリング、および最終的なアセンブリコード生成が含まれます。

### `obj.Prog`とアセンブリ命令

`obj.Prog`は、Goコンパイラがアセンブリコードを表現するために使用するデータ構造です。これは、アセンブリ命令のリンクリストとして機能します。各`obj.Prog`インスタンスは、特定のアセンブリ命令（例: `MOVQ`, `ADDQ`, `JMP`, `RET`）とそのオペランドを表します。

*   **`obj.AEND`**: このコミットで導入された新しい擬似命令（pseudo-instruction）。コードの論理的な終わりを示すために使用されます。実際の機械語命令には変換されず、コンパイラの内部処理（特に制御フローグラフ構築やライブ変数解析）のヒントとして機能します。
*   **`obj.ARET`**: 関数からのリターン命令を表します。

### 制御フローグラフ (CFG)

制御フローグラフ (CFG) は、プログラムの可能なすべての実行パスを抽象的に表現したグラフ構造です。ノードは基本ブロック（連続した命令のシーケンスで、入り口は1つ、出口は1つ）を表し、エッジは基本ブロック間の制御の転送（ジャンプ、条件分岐、フォールスルーなど）を表します。コンパイラはCFGを使用して、データフロー解析や最適化を行います。

### ライブ変数解析

ライブ変数解析は、データフロー解析の一種で、プログラムの特定のポイントにおいて、どの変数の値が将来の計算でまだ使用される可能性があるか（すなわち「ライブ」であるか）を決定します。この情報は、レジスタ割り当て（ライブな変数はレジスタに保持する必要がある）、デッドコード削除（ライブでない変数への代入は削除可能）、およびその他の最適化に不可欠です。

### `ssa.BlockRet`と`ssa.BlockExit`

GoのSSAバックエンドでは、特殊な種類の基本ブロックが定義されています。

*   **`ssa.BlockRet`**: 関数からのリターンを処理する基本ブロックです。通常、関数の最後に位置し、呼び出し元に戻るための処理を行います。
*   **`ssa.BlockExit`**: プログラムの終了を表す特殊な基本ブロックです。`ssa.BlockRet`は最終的に`ssa.BlockExit`に接続されます。

### `Store` (メモリ状態)

SSA形式では、メモリへの読み書きは特別な`Store`値として扱われます。`Store`は、プログラムの特定の時点でのメモリの状態を表す仮想的な値です。メモリ操作（例: 変数への代入、関数呼び出しによるメモリ変更）は、古い`Store`値を受け取り、新しい`Store`値を生成します。これにより、メモリ操作間の依存関係が明示的に表現され、コンパイラはメモリ関連の最適化をより正確に行うことができます。`Store`は、SSAグラフ内の他の値と同様に、データフローエッジを通じて伝播されます。

## 技術的詳細

このコミットは、主に以下の2つの技術的な変更によって問題を解決しています。

1.  **`return`ブロックの`Store`制御の強制**:
    *   GoのSSA形式では、関数からのリターンはメモリ状態に影響を与える可能性があります（例: defer関数の実行、スタックのクリーンアップ）。したがって、`ssa.BlockRet`（リターンブロック）は、その制御フローが有効なメモリ状態（`Store`）に依存していることを明示する必要があります。
    *   以前は、`ssa.BlockRet`が`Store`を制御として持たない場合があり、これが原因で`return`ブロックと`exit`ブロックの間に不要なコードが挿入される問題が発生していました。
    *   このコミットでは、`ssa.go`内の`buildssa`関数と`stmt`関数において、`ssa.BlockRet`を作成する際に明示的に現在のメモリ状態`s.mem()`を`b.Control`に設定するように変更されました。
    *   さらに、`ssa/check.go`内の`checkFunc`関数に、`ssa.BlockRet`の`Control`が`nil`でないこと、かつそれがメモリ型（`IsMemory()`）であることを検証するアサーションが追加されました。これにより、将来的に同様の問題が発生するのを防ぎます。

2.  **`obj.AEND`マーカーによる制御フローグラフ構築の改善**:
    *   到達不能な`RET`命令がライブ変数解析を混乱させる問題に対処するため、新しい擬似命令`obj.AEND`が導入されました。
    *   `obj.AEND`は、コンパイラが生成するアセンブリ命令のリンクリストの論理的な終わりを示すマーカーとして機能します。
    *   `src/cmd/compile/internal/gc/plive.go`内の`newcfg`関数は、アセンブリ命令のリンクリストを走査して制御フローグラフを構築します。この関数内のループ条件が、`p != nil`だけでなく、`p.As != obj.AEND`もチェックするように変更されました。
    *   これにより、`JMP earlier; RET`のようなシーケンスで、`JMP`の後に続く到達不能な`RET`命令が`obj.AEND`の前に来る場合、CFGビルダーは`AEND`で処理を停止し、到達不能な`RET`を誤って基本ブロックに含めることを回避できます。結果として、CFGがより正確になり、ライブ変数解析が正しい情報を得られるようになります。
    *   `src/cmd/compile/internal/gc/ssa.go`の`genssa`関数から、`Pc.As = obj.ARET // overwrite AEND`というコメント付きの行が削除されました。これは、`AEND`が`ARET`で上書きされるという以前の動作が、新しい`AEND`の役割と矛盾するためです。`AEND`はコードの終わりを示す独立したマーカーとして機能するようになりました。

これらの変更により、GoコンパイラのSSAバックエンドは、より堅牢で正確なコード生成と最適化パスを提供できるようになりました。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/plive.go` の変更

`newcfg`関数は、アセンブリ命令のリンクリストから制御フローグラフ (CFG) を構築する役割を担います。このコミットでは、`newcfg`内の2つのループの条件に`p.As != obj.AEND`が追加されました。

*   `for p := firstp; p != nil && p.As != obj.AEND; p = p.Link { ... }`
*   `for p := bb.last; p != nil && p.As != obj.AEND; p = p.Link { ... }`

この変更により、CFGビルダーは`obj.AEND`命令に遭遇すると、それ以降の命令（特に到達不能な`RET`など）を処理対象から除外するようになります。これにより、到達不能なコードがCFGに誤って含まれることを防ぎ、ライブ変数解析がより正確なCFGに基づいて実行されるようになります。

また、以下のコメントが追加されました。
`// TODO: remove after SSA is done. SSA does not // generate any unreachable RET instructions.`
これは、SSAが完全に実装されれば、到達不能な`RET`命令自体が生成されなくなるため、この一時的な回避策が不要になることを示唆しています。

### `src/cmd/compile/internal/gc/ssa.go` の変更

このファイルでは、SSA形式の関数を構築する`buildssa`関数と、ステートメントを処理する`stmt`関数が変更されています。

*   **`buildssa`関数内の変更**:
    `// fallthrough to exit` のコメントの下のブロックが変更されました。
    以前は `if b := s.endBlock(); b != nil { b.Kind = ssa.BlockRet; b.AddEdgeTo(s.exit) }` でした。
    変更後は `if s.curBlock != nil { m := s.mem(); b := s.endBlock(); b.Kind = ssa.BlockRet; b.Control = m; b.AddEdgeTo(s.exit) }` となっています。
    これにより、関数が通常の実行フローで終了し、`exit`ブロックにフォールスルーする場合、その`ssa.BlockRet`の`Control`フィールドに現在のメモリ状態`m`（`s.mem()`で取得）が明示的に設定されるようになりました。

*   **`stmt`関数内の`ORETURN`ケースの変更**:
    `case ORETURN:` のブロックも同様に変更されました。
    以前は `b := s.endBlock(); b.Kind = ssa.BlockRet; b.AddEdgeTo(s.exit)` でした。
    変更後は `m := s.mem(); b := s.endBlock(); b.Kind = ssa.BlockRet; b.Control = m; b.AddEdgeTo(s.exit)` となっています。
    これにより、明示的な`return`ステートメントの場合も、`ssa.BlockRet`の`Control`フィールドに現在のメモリ状態`m`が設定されるようになりました。

これらの変更は、`return`ブロックが常に有効なメモリ状態をその制御として持つことを保証し、`return`と`exit`ブロックの間に不適切なコードが挿入される問題を解決します。

*   **`genssa`関数からの行削除**:
    `Pc.As = obj.ARET // overwrite AEND` の行が削除されました。
    これは、以前は`AEND`が`ARET`で上書きされるという動作があったことを示唆しています。しかし、`AEND`がコードの論理的な終わりを示す独立したマーカーとして導入されたため、この上書きは不要となり、削除されました。

### `src/cmd/compile/internal/ssa/check.go` の変更

このファイルは、SSA形式の関数が正しく構築されているかを検証するためのチェックを含んでいます。

*   **`checkFunc`関数内の`ssa.BlockRet`チェックの強化**:
    `b.Kind == BlockRet` の条件分岐内で、`b.Control`に関するチェックが強化されました。
    以前は `if b.Control != nil { f.Fatalf(...) }` （`Control`が`nil`でない場合にエラー）でした。
    変更後は以下のようになっています。
    ```go
    if b.Control == nil {
        f.Fatalf("ret block %s has nil control %s", b)
    }
    if !b.Control.Type.IsMemory() {
        f.Fatalf("ret block %s has non-memory control value %s", b, b.Control.LongString())
    }
    ```
    この変更により、`ssa.BlockRet`は**必ず**`nil`ではない`Control`を持つ必要があり、さらにその`Control`は**必ず**メモリ型（`IsMemory()`）である必要があるという制約が課せられました。これは、`return`ブロックがメモリ状態を適切に管理していることを静的に検証するための重要なアサーションです。

### `src/cmd/compile/internal/ssa/gen/genericOps.go` の変更

このファイルは、SSAのジェネリックな操作とブロックの定義を含んでいます。

*   **`genericBlocks`のコメント更新**:
    `// Ret return mem [exit]` の行が追加されました。
    これは、`ssa.BlockRet`が`mem`（メモリ状態）を制御として持ち、`exit`ブロックを後続として持つという、このコミットで導入された新しいセマンティクスを反映したコメントの更新です。

これらの変更は全体として、GoコンパイラのSSAバックエンドにおける`return`処理の正確性を向上させ、ライブ変数解析の信頼性を高めることで、より堅牢で効率的なコード生成に貢献しています。

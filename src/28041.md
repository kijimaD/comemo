# [インデックス 28041] ファイルの概要

このコミットは、Go言語の標準ライブラリ`net/http`パッケージにおける`Transport`のアイドル接続管理を改善するものです。具体的には、サーバー側で閉じられたアイドル接続がクライアント側の`Transport`のアイドルリストに残り続け、メモリを無駄に消費する問題を解決します。また、将来的に`Transport.MaxIdleConns`機能を実現するための準備として、アイドル接続の総数をカウントする仕組みが導入されています。

## 元コミット内容

```
net/http: remove idle transport connections from Transport when server closes

Previously the Transport would cache idle connections from the
Transport for later reuse, but if a peer server disconnected
(e.g. idle timeout), we would not proactively remove the *persistConn
from the Transport's idle list, leading to a waste of memory
(potentially forever).

Instead, when the persistConn's readLoop terminates, remote it from
the idle list, if present.

This also adds the beginning of accounting for the total number of
idle connections, which will be needed for Transport.MaxIdleConns
later.

Updates #15461

Reviewed-by: Andrew Gerrand <adg@golang.org>
```

## 変更の背景

Goの`net/http`パッケージの`Transport`は、HTTP/1.xのKeep-Alive機能を利用して、一度確立されたTCP接続を再利用のためにキャッシュします。これにより、新しい接続を確立する際のオーバーヘッド（TCPハンドシェイク、TLSハンドシェイクなど）を削減し、パフォーマンスを向上させます。これらの接続は「アイドル接続」と呼ばれ、`Transport`の内部リストに保持されます。

しかし、このコミット以前の`Transport`の実装には問題がありました。もし接続先のサーバーが、アイドルタイムアウトなどの理由で先に接続を閉じた場合、クライアント側の`Transport`はその事実を即座に認識せず、死んだ接続をアイドルリストに保持し続けていました。これにより、実際には使用できない接続がメモリを占有し続け、潜在的なメモリリークやリソースの無駄遣いにつながっていました。特に、多数の接続が頻繁に確立・切断されるようなシナリオでは、この問題は顕著になる可能性がありました。

このコミットは、この問題を解決し、`Transport`がアイドル接続のライフサイクルをより適切に管理できるようにすることを目的としています。また、関連するIssue #15461で議論されている`Transport.MaxIdleConns`（アイドル接続の最大数を設定する機能）の実装に向けた準備として、アイドル接続の総数を正確に追跡するメカニズムも導入されています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の`net/http`パッケージの内部構造とHTTPの概念に関する知識が役立ちます。

*   **Goの`net/http`パッケージ**: Go言語の標準ライブラリで、HTTPクライアントとサーバーの機能を提供します。Webアプリケーションの構築やHTTPリクエストの送信に広く利用されます。
*   **`http.Transport`**: `net/http`パッケージの中心的なコンポーネントの一つで、HTTPリクエストの実際のネットワーク通信部分を処理します。具体的には、TCP接続の確立、TLSハンドシェイク、HTTPリクエストの送信、レスポンスの受信、そして最も重要な**接続の再利用（Keep-Alive）**の管理を行います。
*   **アイドル接続 (Idle Connections) / Keep-Alive**: HTTP/1.1では、`Connection: keep-alive`ヘッダを使用することで、一つのTCP接続上で複数のHTTPリクエスト/レスポンスをやり取りできます。これにより、リクエストごとに新しい接続を確立するオーバーヘッドを避けることができます。リクエスト処理後に一時的に使用されていない接続は「アイドル接続」として`Transport`によってキャッシュされ、次のリクエストで再利用されるのを待ちます。
*   **`persistConn`**: `http.Transport`の内部で、個々の永続的なTCP接続（Keep-Alive接続）を抽象化し、管理する構造体です。各`persistConn`は、その接続を介してデータを読み書きするための専用のゴルーチン（`readLoop`）を持っています。
*   **`readLoop`**: `persistConn`内で動作するゴルーチンで、基盤となるTCP接続からサーバーからのレスポンスや予期せぬ切断イベントを非同期的に読み取ります。このループが正常に終了するか、エラーで終了するかが、接続の状態を判断する重要なシグナルとなります。
*   **メモリリーク**: プログラムが確保したメモリ領域が、不要になった後も解放されずに残り続ける現象です。これにより、利用可能なメモリが徐々に減少し、最終的にはシステムのパフォーマンス低下やクラッシュにつながる可能性があります。このコミットの文脈では、死んだアイドル接続が`Transport`のキャッシュに残り続けることがメモリリークの原因となっていました。
*   **Issue 15461 (`Transport.MaxIdleConns`)**: GoのIssueトラッカーで議論されていた、`http.Transport`が保持するアイドル接続の総数に上限を設定する機能に関する課題です。このコミットは、その機能を実現するために必要な、アイドル接続の正確なカウントメカニズムを導入する第一歩となります。

## 技術的詳細

このコミットの主要な変更点は、`http.Transport`がアイドル接続のライフサイクルをより正確に追跡し、サーバー側で閉じられた接続を適切にクリーンアップするメカニズムを導入したことです。

1.  **`Transport`構造体への`idleCount`フィールドの追加**:
    `Transport`構造体に`idleCount int`という新しいフィールドが追加されました。これは、現在`Transport`がキャッシュしているアイドル接続の総数を追跡するためのものです。これは、将来的に`Transport.MaxIdleConns`（アイドル接続の最大数を設定する機能）を実装する上で不可欠な要素となります。

2.  **`tryPutIdleConn`での`idleCount`のインクリメント**:
    `tryPutIdleConn`メソッドは、`persistConn`をアイドルリストに格納しようとする際に呼び出されます。このメソッド内で、接続がアイドルリストに追加される成功した場合に`t.idleCount++`が実行され、アイドル接続の総数が増加します。

3.  **`getIdleConn`での`idleCount`のデクリメントと`isBroken()`チェックの改善**:
    `getIdleConn`メソッドは、アイドルリストから再利用可能な接続を取得しようとする際に呼び出されます。このメソッド内で、接続がアイドルリストから取り出される際に`t.idleCount--`が実行されます。
    また、以前は`pconn.isBroken()`チェックが接続を返す直前に行われていましたが、このコミットでは`idleCount`をデクリメントした直後に`isBroken()`チェックを行い、壊れた接続であればスキップして次の接続を探すように変更されました。これにより、壊れた接続が誤って再利用される可能性が低減されます。コミットメッセージにある「There is a tiny window where this is possible...」というコメントは、接続が死んだ直後から`removeIdleConn`が呼ばれるまでの間に`getIdleConn`がその接続を取得しようとする可能性を指しています。

4.  **`removeIdleConn`メソッドの追加**:
    `Transport`構造体に`removeIdleConn(pconn *persistConn)`という新しいプライベートメソッドが追加されました。このメソッドは、特定の`persistConn`がアイドルリストから削除されるべきであることを`Transport`に通知するために使用されます。
    このメソッドは、`idleMu`（アイドル接続リストを保護するミューテックス）をロックし、指定された`pconn`を`t.idleConn`マップから検索して削除します。削除が成功した場合、`t.idleCount--`を実行してアイドル接続の総数を更新します。このメソッドは、リストから要素を効率的に削除するために、スライス操作（削除対象の要素を最後の要素と入れ替えてからスライスを短くする）を使用しています。

5.  **`persistConn.readLoop`での`removeIdleConn`の呼び出し**:
    `persistConn`の`readLoop`メソッドは、接続のライフサイクルにおいて非常に重要な役割を果たします。このループは、サーバーからのデータ読み取りを継続的に試み、接続が閉じられたりエラーが発生したりすると終了します。
    このコミットでは、`readLoop`の`defer`関数内に`pc.t.removeIdleConn(pc)`が追加されました。これにより、`readLoop`が終了する（つまり、接続が何らかの理由で死んだ）際に、その`persistConn`が`Transport`のアイドルリストから自動的に削除されるようになります。これは、サーバー側で接続が閉じられた場合に、クライアント側がその接続をアイドルリストからプロアクティブに削除するための核心的な変更です。

6.  **テストケースの追加**:
    `TestTransportRemovesDeadIdleConnections`という新しいテストケースが`src/net/http/transport_test.go`に追加されました。このテストは、サーバーがクライアント接続を閉じたときに、`Transport`がアイドル接続リストからその接続を適切に削除することを確認します。
    テストでは、`httptest.NewServer`を使用してテストサーバーを起動し、クライアントがリクエストを送信してアイドル接続を作成します。その後、`ts.CloseClientConnections()`を呼び出してサーバー側の接続を強制的に閉じ、`waitCondition`ヘルパー関数を使って`Transport`のアイドル接続リストが空になるのを待ちます。これにより、`readLoop`が終了し、`removeIdleConn`が呼び出されることで、死んだ接続がクリーンアップされることを検証しています。

```go
type Transport struct {
	idleMu     sync.Mutex
	wantIdle   bool // user has requested to close all idle conns
	idleCount  int // 追加: 現在のアイドル接続数を追跡
	idleConn   map[connectMethodKey][]*persistConn
	idleConnCh map[connectMethodKey]chan *persistConn
	// ...
}

func (t *Transport) tryPutIdleConn(pconn *persistConn) error {
	// ...
	t.idleConn[key] = append(t.idleConn[key], pconn)
	t.idleCount++ // アイドル接続が追加された際にカウントをインクリメント
	return nil
}

func (t *Transport) getIdleConn(cm connectMethod) *persistConn {
	// ...
	for {
		// ...
		if !ok {
			return nil
		}
		// ...
		pconn = pconns[len(pconns)-1]
		t.idleConn[key] = pconns[:len(pconns)-1]
		t.idleCount-- // アイドル接続が取り出された際にカウントをデクリメント
		if pconn.isBroken() {
			// 接続が壊れている場合はスキップし、次の接続を探す
			// readLoopが終了しremoveIdleConnが呼ばれるまでのわずかな期間に発生する可能性がある
			continue
		}
		return pconn
	}
}

// removeIdleConn marks pconn as dead.
func (t *Transport) removeIdleConn(pconn *persistConn) {
	key := pconn.cacheKey
	t.idleMu.Lock()
	defer t.idleMu.Unlock()

	pconns, _ := t.idleConn[key]
	switch len(pconns) {
	case 0:
		// 何もしない
	case 1:
		if pconns[0] == pconn {
			t.idleCount-- // カウントをデクリメント
			delete(t.idleConn, key) // マップからエントリを削除
		}
	default:
		// 複数の接続がある場合、対象の接続をリストから削除
		for i, v := range pconns {
			if v != pconn {
				continue
			}
			pconns[i] = pconns[len(pconns)-1] // 最後の要素と入れ替える
			t.idleConn[key] = pconns[:len(pconns)-1] // スライスを短くする
			t.idleCount-- // カウントをデクリメント
			break
		}
	}
}

func (pc *persistConn) readLoop() {
	closeErr := errReadLoopExiting // default value, if not changed below
	defer func() {
		pc.close(closeErr)
		pc.t.removeIdleConn(pc) // readLoop終了時にアイドルリストから自身を削除
	}()
	// ...
}
```

*   **`idleCount`**: `Transport`が現在保持しているアイドル接続の数を正確に把握するためのカウンターです。`tryPutIdleConn`で増加し、`getIdleConn`や`removeIdleConn`で減少します。
*   **`removeIdleConn`**: この新しいメソッドは、特定の`persistConn`がもはや有効なアイドル接続ではないと判断されたときに、`Transport`の内部キャッシュからその接続を安全に削除する役割を担います。これにより、死んだ接続がメモリに残り続けることを防ぎます。
*   **`persistConn.readLoop`の`defer`**: `readLoop`は、`persistConn`が基盤となるネットワーク接続からデータを読み取るためのゴルーチンです。このループが何らかの理由（例: サーバーによる接続切断、ネットワークエラー）で終了する際に、`defer`文で`pc.t.removeIdleConn(pc)`が呼び出されます。これは、接続が死んだことを`Transport`に通知し、アイドルリストからのクリーンアップをトリガーする、このコミットの最も重要な変更点です。

### `src/net/http/main_test.go`

```go
// waitCondition reports whether fn eventually returned true,
// checking immediately and then every checkEvery amount,
// until waitFor has elpased, at which point it returns false.
func waitCondition(waitFor, checkEvery time.Duration, fn func() bool) bool {
	deadline := time.Now().Add(waitFor)
	for time.Now().Before(deadline) {
		if fn() {
			return true
		}
		time.Sleep(checkEvery)
	}
	return false
}
```

*   **`waitCondition`**: このヘルパー関数は、非同期処理の完了をテストで待機するために導入されました。指定された`fn`関数が`true`を返すまで、`checkEvery`間隔で繰り返しチェックします。`waitFor`期間内に`true`を返さなければ`false`を返します。これは、`readLoop`が終了し、`removeIdleConn`が実行されるまでの非同期的な遅延を考慮したテストを可能にします。

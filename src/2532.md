# [インデックス 2532] ファイルの概要

## 元コミット内容

ローカルパスのルックアップを標準パッケージディレクトリから分離する。

## 変更の背景

このコミットは、Go言語の初期段階（2009年）に行われたもので、Goのパッケージ管理システムがまだ進化の途上にあったことを示唆しています。当時のGoコンパイラ（`gc`）は、ソースコード中の`import`文で指定されたパッケージを解決する際に、ローカルな相対パス（例: `./mypackage`）と、GOPATHやGOROOTに設定された標準的なパッケージディレクトリを区別なく、あるいは効率的でない方法で検索していた可能性があります。

この変更の主な背景は以下の点にあると考えられます。

1.  **明確なセマンティクス**: ローカルなインポートパス（`./`、`../`、`/`で始まる）は、現在のファイルシステム上の位置に基づいてパッケージを特定します。これに対し、標準パッケージは、設定された検索パス（`idirs`や`GOROOT/pkg`）に基づいて特定されます。これらを同じロジックで処理しようとすると、意図しないパッケージが解決されたり、検索効率が低下したりする可能性があります。
2.  **検索効率の向上**: ローカルパスは、現在のディレクトリからの相対的な位置が明確であるため、特定のファイルシステムパスのみを検索すれば済みます。一方、標準パッケージは複数のディレクトリを順に検索する必要があります。この2つの検索ロジックを分離することで、それぞれのケースで最適な検索戦略を適用し、パッケージ解決の速度を向上させることができます。
3.  **ビルドの堅牢性**: ローカルパッケージと標準パッケージの検索を分離することで、ビルドシステムがより予測可能で堅牢になります。例えば、ローカルディレクトリに標準パッケージと同じ名前のディレクトリが存在する場合でも、意図したパッケージが正しくインポートされるようになります。
4.  **`.a`と`.6`ファイルの優先順位**: コミットメッセージとコードのコメントにあるように、ライブラリをビルドする際には、個々のオブジェクトファイル（`.6`）よりもアーカイブファイル（`.a`）を優先して見つけることが重要です。これは、アーカイブファイルが完全なパッケージのコンパイル済みコードを含んでいるため、リンカが正しく動作するために必要です。ローカルパスの検索において、この優先順位を明示的に適用することで、ビルドの正確性を保証します。

## 前提知識の解説

### Goのパッケージ管理とインポートパス

Go言語では、コードはパッケージにまとめられ、`import`文を使って他のパッケージの機能を利用します。インポートパスには主に以下の種類があります。

*   **標準ライブラリパッケージ**: `fmt`, `net/http`などのGo言語に組み込まれたパッケージ。これらは`GOROOT`環境変数で指定されたディレクトリ内の`pkg`サブディレクトリに存在します。
*   **サードパーティパッケージ**: `go get`などで取得される外部パッケージ。これらは通常`GOPATH`環境変数で指定されたディレクトリ内の`src`サブディレクトリに存在します（Go Modules導入以前のGoのバージョンでは特に重要でした）。
*   **ローカル（相対）パッケージ**: `./mypackage`や`../common`のように、現在のソースファイルからの相対パスで指定されるパッケージ。これらは主にモノレポや、特定のプロジェクト内で密接に関連するパッケージ群を構成する際に使用されます。絶対パス（`/home/user/project/mypackage`）もローカルパスとして扱われることがあります。

### `src/cmd/gc/lex.c` の役割

`src/cmd/gc/lex.c`は、Goコンパイラ`gc`の一部であり、字句解析器（lexer）の機能を提供します。字句解析器は、ソースコードを読み込み、キーワード、識別子、演算子、リテラルなどの意味のある最小単位（トークン）に分割します。このファイルには、`import`文で指定されたパッケージ名を解決し、対応するコンパイル済みパッケージファイル（`.a`または`.6`）を見つけるためのロジックも含まれています。

### `access()` システムコール

`access()`は、指定されたファイルパスに対して、呼び出し元のプロセスが特定のアクセス権限（読み取り、書き込み、実行など）を持っているかどうかを確認するためのC言語の標準ライブラリ関数です。このコミットでは、ファイルが存在するかどうか（`F_OK`または`0`）を確認するために使用されています。

### `.a` ファイルと `.6` ファイル

Go言語の初期のビルドシステムでは、コンパイルされたパッケージは特定のファイル拡張子を持っていました。

*   **`.a` (archive) ファイル**: Goパッケージのコンパイル済みコードを含むアーカイブファイルです。これは、C言語の静的ライブラリ（`.a`）に似ており、複数のオブジェクトファイルやメタデータがまとめられています。Goのビルドプロセスでは、パッケージ全体が`.a`ファイルとしてコンパイルされ、他のパッケージからインポートされる際に利用されます。
*   **`.6` ファイル**: これは、特定のアーキテクチャ（この場合は`amd64`、つまり64ビットアーキテクチャ）向けのコンパイル済みオブジェクトファイルを示す拡張子です。Goの初期のツールチェーンでは、`8`は`386`（32ビット）、`6`は`amd64`、`5`は`arm`など、アーキテクチャごとに異なる数字が使われていました。`thechar`変数は、現在のターゲットアーキテクチャに対応するこの数字を表します。

コミットのコメントにあるように、ライブラリをビルドする際には、個々の`.6`ファイルではなく、パッケージ全体をまとめた`.a`ファイルを優先して見つけることが重要です。

## 技術的詳細

このコミットは、`src/cmd/gc/lex.c`ファイルに以下の主要な変更を導入しています。

1.  **`islocalname` 関数の導入**:
    *   この新しい関数は、`Strlit *name`（文字列リテラルを表す構造体）を受け取り、その名前がローカルパスであるかどうかを判定します。
    *   ローカルパスの条件は、文字列が`'/'`、`"./"`、または`"../"`で始まることです。
    *   これにより、インポートパスがファイルシステム上の相対的な位置を指しているのか、それとも標準的なパッケージ名であるのかを明確に区別できるようになりました。

    ```c
    // is this path a local name?  begins with ./ or ../ or /
    int
    islocalname(Strlit *name)
    {
    	if(name->len >= 1 && name->s[0] == '/')
    		return 1;
    	if(name->len >= 2 && strncmp(name->s, "./", 2) == 0)
    		return 1;
    	if(name->len >= 3 && strncmp(name->s, "../", 3) == 0)
    		return 1;
    	return 0;
    }
    ```

2.  **`findpkg` 関数の変更**:
    *   `findpkg`関数は、指定されたパッケージ名に対応するコンパイル済みパッケージファイル（`.a`または`.6`）を検索する役割を担っています。
    *   変更後、`findpkg`の冒頭で`islocalname(name)`を呼び出し、パッケージ名がローカルパスであるかどうかをチェックします。
    *   **ローカルパスの場合**:
        *   `islocalname`が`1`（true）を返した場合、`findpkg`はまずローカルパスとしてパッケージを検索します。
        *   検索順序は、まず`%Z.a`（アーカイブファイル）を試み、次に`%Z.%c`（アーキテクチャ固有のオブジェクトファイル）を試みます。これは、ライブラリビルドにおいて`.a`ファイルを優先する意図を反映しています。
        *   いずれかのファイルが見つかれば`1`を返して成功とし、見つからなければ`0`を返して失敗とします。
        *   **重要な点として、ローカルパスの場合は、`idirs`や`GOROOT/pkg`などの標準パッケージ検索パスは一切参照されません。** これにより、ローカルパスの解決が標準パッケージの検索ロジックから完全に分離されます。
    *   **非ローカルパス（標準パッケージ名）の場合**:
        *   `islocalname`が`0`（false）を返した場合、従来のロジックに従って、`idirs`（インポートディレクトリリスト）を順に検索し、次に`GOROOT/pkg`ディレクトリを検索します。
        *   この検索も、まず`.a`ファイルを試み、次に`.%c`ファイルを試みるという優先順位に従います。
    *   変更前は、ローカルパスの検索（`%Z.a`と`%Z.%c`を直接試す部分）が、`idirs`の検索ループの後に、`GOROOT/pkg`の検索の前に配置されていました。この配置では、ローカルパスと標準パッケージパスの検索が混在しており、セマンティクスが不明確でした。

この変更により、Goコンパイラはインポートパスの種類に応じて、より効率的かつ正確にパッケージを解決できるようになりました。ローカルパスはローカルなファイルシステムのみを検索し、標準パッケージは設定された検索パスのみを検索するという明確な分離が実現されています。

## コアとなるコードの解説

### `islocalname` 関数

この関数は、Goのインポートパスがローカルな参照であるかを効率的に判定します。
*   `name->s[0] == '/'`: パスがルートディレクトリからの絶対パスである場合（例: `/usr/local/go/src/mypkg`）。
*   `strncmp(name->s, "./", 2) == 0`: パスが現在のディレクトリからの相対パスである場合（例: `./mypkg`）。
*   `strncmp(name->s, "../", 3) == 0`: パスが親ディレクトリからの相対パスである場合（例: `../common`）。

これらの条件のいずれかに合致すれば`1`（true）を返し、そうでなければ`0`（false）を返します。これにより、`findpkg`関数はインポートパスの種類を迅速に識別できます。

### `findpkg` 関数の変更点

`findpkg`関数は、`islocalname`の導入により、パッケージ検索ロジックが大きく改善されました。

1.  **ローカルパスの優先処理**:
    `if(islocalname(name))`ブロックが追加され、インポートパスがローカルであると判定された場合、まずローカルなファイルシステム上でパッケージファイルを検索します。
    *   `snprint(namebuf, sizeof(namebuf), "%Z.a", name);`：パッケージ名に`.a`拡張子を付けて、アーカイブファイルを探します。
    *   `snprint(namebuf, sizeof(namebuf), "%Z.%c", name, thechar);`：アーカイブファイルが見つからなかった場合、パッケージ名に現在のアーキテクチャに対応する数字（例: `6`）と拡張子を付けて、オブジェクトファイルを探します。
    *   このローカルパス検索が成功すれば、`findpkg`は直ちに`1`を返して終了します。これにより、不要な標準パッケージディレクトリの検索がスキップされ、効率が向上します。

2.  **標準パッケージ検索の分離**:
    ローカルパスの検索ロジックが`if(islocalname(name))`ブロック内に移動したことで、その後の`for(p = idirs; p != nil; p = p->link)`ループと`if(goroot != nil)`ブロックは、純粋に標準パッケージディレクトリ（`idirs`と`GOROOT/pkg`）のみを検索するようになりました。
    変更前は、これらの標準パッケージ検索ロジックの間に、ローカルパスの検索が混在していました。この分離により、各検索パスのセマンティクスが明確になり、コードの可読性と保守性が向上しています。

このコミットは、Goコンパイラのパッケージ解決メカニズムにおける重要な改善であり、インポートパスの種類に応じた適切な検索戦略を確立することで、ビルドの正確性と効率を高めています。

`src/cmd/gc/lex.c`は、Goコンパイラ`gc`の一部であり、字句解析器（lexer）の機能を提供します。字句解析器は、ソースコードを読み込み、キーワード、識別子、演算子、リテラルなどの意味のある最小単位（トークン）に分割します。このファイルには、`import`文で指定されたパッケージ名を解決し、対応するコンパイル済みパッケージファイル（`.a`または`.6`）を見つけるためのロジックも含まれています。

### `access()` システムコール

`access()`は、指定されたファイルパスに対して、呼び出し元のプロセスが特定のアクセス権限（読み取り、書き込み、実行など）を持っているかどうかを確認するためのC言語の標準ライブラリ関数です。このコミットでは、ファイルが存在するかどうか（`F_OK`または`0`）を確認するために使用されています。

### `.a` ファイルと `.6` ファイル

Go言語の初期のビルドシステムでは、コンパイルされたパッケージは特定のファイル拡張子を持っていました。

*   **`.a` (archive) ファイル**: Goパッケージのコンパイル済みコードを含むアーカイブファイルです。これは、C言語の静的ライブラリ（`.a`）に似ており、複数のオブジェクトファイルやメタデータがまとめられています。Goのビルドプロセスでは、パッケージ全体が`.a`ファイルとしてコンパイルされ、他のパッケージからインポートされる際に利用されます。
*   **`.6` ファイル**: これは、特定のアーキテクチャ（この場合は`amd64`、つまり64ビットアーキテクチャ）向けのコンパイル済みオブジェクトファイルを示す拡張子です。Goの初期のツールチェーンでは、`8`は`386`（32ビット）、`6`は`amd64`、`5`は`arm`など、アーキテクチャごとに異なる数字が使われていました。`thechar`変数は、現在のターゲットアーキテクチャに対応するこの数字を表します。

コミットのコメントにあるように、ライブラリをビルドする際には、個々の`.6`ファイルではなく、パッケージ全体をまとめた`.a`ファイルを優先して見つけることが重要です。

## 技術的詳細

このコミットは、`src/cmd/gc/lex.c`ファイルに以下の主要な変更を導入しています。

1.  **`islocalname` 関数の導入**:
    *   この新しい関数は、`Strlit *name`（文字列リテラルを表す構造体）を受け取り、その名前がローカルパスであるかどうかを判定します。
    *   ローカルパスの条件は、文字列が`'/'`、`"./"`、または`"../"`で始まることです。
    *   これにより、インポートパスがファイルシステム上の相対的な位置を指しているのか、それとも標準的なパッケージ名であるのかを明確に区別できるようになりました。

    ```c
    // is this path a local name?  begins with ./ or ../ or /
    int
    islocalname(Strlit *name)
    {
    	if(name->len >= 1 && name->s[0] == '/')
    		return 1;
    	if(name->len >= 2 && strncmp(name->s, "./", 2) == 0)
    		return 1;
    	if(name->len >= 3 && strncmp(name->s, "../", 3) == 0)
    		return 1;
    	return 0;
    }
    ```

2.  **`findpkg` 関数の変更**:
    *   `findpkg`関数は、指定されたパッケージ名に対応するコンパイル済みパッケージファイル（`.a`または`.6`）を検索する役割を担っています。
    *   変更後、`findpkg`の冒頭で`islocalname(name)`を呼び出し、パッケージ名がローカルパスであるかどうかをチェックします。
    *   **ローカルパスの場合**:
        *   `islocalname`が`1`（true）を返した場合、`findpkg`はまずローカルパスとしてパッケージを検索します。
        *   検索順序は、まず`%Z.a`（アーカイブファイル）を試み、次に`%Z.%c`（アーキテクチャ固有のオブジェクトファイル）を試みます。これは、ライブラリビルドにおいて`.a`ファイルを優先する意図を反映しています。
        *   いずれかのファイルが見つかれば`1`を返して成功とし、見つからなければ`0`を返して失敗とします。
        *   **重要な点として、ローカルパスの場合は、`idirs`や`GOROOT/pkg`などの標準パッケージ検索パスは一切参照されません。** これにより、ローカルパスの解決が標準パッケージの検索ロジックから完全に分離されます。
    *   **非ローカルパス（標準パッケージ名）の場合**:
        *   `islocalname`が`0`（false）を返した場合、従来のロジックに従って、`idirs`（インポートディレクトリリスト）を順に検索し、次に`GOROOT/pkg`ディレクトリを検索します。
        *   この検索も、まず`.a`ファイルを試み、次に`.%c`ファイルを試みるという優先順位に従います。
    *   変更前は、ローカルパスの検索（`%Z.a`と`%Z.%c`を直接試す部分）が、`idirs`の検索ループの後に、`GOROOT/pkg`の検索の前に配置されていました。この配置では、ローカルパスと標準パッケージパスの検索が混在しており、セマンティクスが不明確でした。

この変更により、Goコンパイラはインポートパスの種類に応じて、より効率的かつ正確にパッケージを解決できるようになりました。ローカルパスはローカルなファイルシステムのみを検索し、標準パッケージは設定された検索パスのみを検索するという明確な分離が実現されています。

## コアとなるコードの解説

### `islocalname` 関数

この関数は、Goのインポートパスがローカルな参照であるかを効率的に判定します。
*   `name->s[0] == '/'`: パスがルートディレクトリからの絶対パスである場合（例: `/usr/local/go/src/mypkg`）。
*   `strncmp(name->s, "./", 2) == 0`: パスが現在のディレクトリからの相対パスである場合（例: `./mypkg`）。
*   `strncmp(name->s, "../", 3) == 0`: パスが親ディレクトリからの相対パスである場合（例: `../common`）。

これらの条件のいずれかに合致すれば`1`（true）を返し、そうでなければ`0`（false）を返します。これにより、`findpkg`関数はインポートパスの種類を迅速に識別できます。

### `findpkg` 関数の変更点

`findpkg`関数は、`islocalname`の導入により、パッケージ検索ロジックが大きく改善されました。

1.  **ローカルパスの優先処理**:
    `if(islocalname(name))`ブロックが追加され、インポートパスがローカルであると判定された場合、まずローカルなファイルシステム上でパッケージファイルを検索します。
    *   `snprint(namebuf, sizeof(namebuf), "%Z.a", name);`：パッケージ名に`.a`拡張子を付けて、アーカイブファイルを探します。
    *   `snprint(namebuf, sizeof(namebuf), "%Z.%c", name, thechar);`：アーカイブファイルが見つからなかった場合、パッケージ名に現在のアーキテクチャに対応する数字（例: `6`）と拡張子を付けて、オブジェクトファイルを探します。
    *   このローカルパス検索が成功すれば、`findpkg`は直ちに`1`を返して終了します。これにより、不要な標準パッケージディレクトリの検索がスキップされ、効率が向上します。

2.  **標準パッケージ検索の分離**:
    ローカルパスの検索ロジックが`if(islocalname(name))`ブロック内に移動したことで、その後の`for(p = idirs; p != nil; p = p->link)`ループと`if(goroot != nil)`ブロックは、純粋に標準パッケージディレクトリ（`idirs`と`GOROOT/pkg`）のみを検索するようになりました。
    変更前は、これらの標準パッケージ検索ロジックの間に、ローカルパスの検索が混在していました。この分離により、各検索パスのセマンティクスが明確になり、コードの可読性と保守性が向上しています。

このコミットは、Goコンパイラのパッケージ解決メカニズムにおける重要な改善であり、インポートパスの種類に応じた適切な検索戦略を確立することで、ビルドの正確性と効率を高めています。

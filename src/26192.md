# [インデックス 26192] ファイルの概要

このコミットは、Go言語の標準ライブラリである `net/http` パッケージのテストにおける不安定性（flakiness）を解消することを目的としています。具体的には、`t.Parallel()` の導入によって発生した、テストの並列実行と `afterTest` 関数との間の非互換性の問題を解決します。テストが「ショートモード」で実行されている場合にのみ `t.Parallel()` を条件付きで呼び出す新しいヘルパー関数を導入することで、テストの安定性を向上させています。

## 変更の背景

この変更は、以前のコミット `https://golang.org/cl/18087` によって `net/http` パッケージのテストに `t.Parallel()` が導入されたことに起因する問題に対処しています。`t.Parallel()` はテストを並列実行させることでテストスイート全体の実行時間を短縮する強力な機能ですが、`net/http` パッケージのテストには `afterTest` というテスト後のクリーンアップを行う関数が存在しました。

問題は、`t.Parallel()` が有効な「フルモード」（`testing.Short()` が偽の場合）でテストが実行されると、`afterTest` 関数が並列実行されるテスト間で競合状態を引き起こし、テストが不安定になる（flakyになる）という点でした。`afterTest` は、おそらくグローバルな状態や共有リソース（例えば、`http.DefaultTransport` のアイドル接続など）をクリーンアップするために設計されており、複数のテストが同時にそれを呼び出すと予期せぬ動作やエラーが発生する可能性がありました。

一方で、「ショートモード」（`testing.Short()` が真の場合、通常は `go test -short` で実行）では、`afterTest` 関数自体が何もしない（no-op）ように実装されていました。このため、ショートモードでは `t.Parallel()` を使用しても問題が発生せず、テストの高速化に貢献していました。

このコミットの目的は、`all.bash` スクリプト（Goプロジェクト全体のテストを実行する際にショートモードを使用することが多い）でのテスト実行速度を維持しつつ、フルモードでのテストの安定性を確保することでした。

## 前提知識の解説

### Goのテストフレームワーク (`testing` パッケージ)

Go言語には、標準ライブラリとして `testing` パッケージが提供されており、ユニットテストやベンチマークテストを記述するための機能が含まれています。

*   **テスト関数**: `func TestXxx(t *testing.T)` の形式で定義され、`go test` コマンドで実行されます。
*   **`*testing.T`**: テストの状態を管理し、テストの失敗を報告したり、ヘルパー関数を提供したりするための構造体です。
*   **`t.Parallel()`**: このメソッドがテスト関数内で呼び出されると、そのテストは他の並列テストと同時に実行されるようにスケジュールされます。これにより、テストスイート全体の実行時間を短縮できます。ただし、並列実行されるテストは互いに独立しており、共有リソースへのアクセスで競合状態を引き起こさないように注意深く設計されている必要があります。
*   **`testing.Short()`**: この関数は、`go test -short` コマンドでテストが実行された場合に `true` を返します。開発者はこのフラグを利用して、時間のかかるテスト（例: ネットワークアクセス、ファイルI/O、大規模な計算を伴うテスト）をショートモードではスキップし、開発サイクルを高速化することができます。

### テストの不安定性 (Test Flakiness)

テストの不安定性（flakiness）とは、同じコードに対して同じテストを複数回実行したときに、成功したり失敗したりする現象を指します。これは、テストが外部要因（ネットワークの遅延、OSのスケジューリング、データベースの状態など）に依存している場合や、並列実行されるテスト間で共有リソースへのアクセスが適切に同期されていない場合に発生することが多いです。Flakyなテストは開発者の信頼を損ない、CI/CDパイプラインの効率を低下させるため、可能な限り排除する必要があります。

### `net/http` パッケージのテストにおけるクリーンアップ (`afterTest`)

`net/http` パッケージのような複雑なネットワーク関連のコードでは、テスト後にリソース（開かれたソケット、アイドル接続、ゴルーチンなど）を適切にクリーンアップすることが重要です。`afterTest` のような関数は、各テストの実行後にこれらのクリーンアップ処理を一元的に行うために使用されます。しかし、このクリーンアップ処理がグローバルな状態に依存している場合、複数のテストが並列で実行されると、クリーンアップ処理自体が競合状態に陥り、テストの失敗やリソースリークを引き起こす可能性があります。

## 技術的詳細

このコミットの核心は、`t.Parallel()` の呼び出しを `testing.Short()` の結果に基づいて条件付きにすることです。

1.  **`t.Parallel()` と `afterTest` の非互換性**:
    *   `net/http` パッケージのテストには、`afterTest(t testing.TB)` という関数が存在します。この関数は、`http.DefaultTransport.(*http.Transport).CloseIdleConnections()` を呼び出すなど、テスト後にグローバルなHTTPトランスポートのアイドル接続をクリーンアップする役割を担っています。
    *   `t.Parallel()` を呼び出すと、テストは並列で実行されます。もし複数のテストが同時に `afterTest` を呼び出し、それがグローバルな共有リソース（`http.DefaultTransport`）を操作する場合、競合状態が発生し、テストが不安定になる原因となります。例えば、あるテストがアイドル接続を閉じている最中に別のテストが同じトランスポートを使用しようとしたり、クリーンアップ処理が複数回実行されたりする可能性があります。

2.  **`afterTest` のショートモードでの挙動**:
    *   `afterTest` 関数内には `if testing.Short() { ... }` という条件分岐があり、ショートモードで実行された場合は、特定のクリーンアップ処理（例えば、ゴルーチンリークのチェックなど）がスキップされるか、あるいは全体として何もしない（no-op）ように設計されていました。これは、ショートモードでのテスト実行を高速化するための一環です。

3.  **解決策としての `setParallel` ヘルパー関数**:
    *   このコミットでは、`setParallel(t *testing.T)` という新しいヘルパー関数が導入されました。
    *   この関数は、`if testing.Short() { t.Parallel() }` というロジックを含んでいます。
    *   これにより、テストがショートモードで実行されている場合にのみ `t.Parallel()` が呼び出され、テストが並列実行されます。
    *   ショートモードでは `afterTest` がno-opであるため、`t.Parallel()` を使用しても競合状態の問題は発生しません。
    *   一方、フルモード（`testing.Short()` が偽の場合）では `setParallel` は何もせず、`t.Parallel()` は呼び出されません。これにより、テストは直列に実行され、`afterTest` との非互換性の問題を回避できます。

このアプローチにより、`all.bash` のようなショートモードで実行されるテストは並列化の恩恵を受け、実行時間を短縮できます。同時に、フルモードで実行されるテストは `afterTest` との競合を避け、安定した結果を保証できるようになります。

## コアとなるコードの解説

このコミットの主要な変更は、`src/net/http/main_test.go` に追加された `setParallel` 関数と、既存のテスト関数における `t.Parallel()` の呼び出しをこの `setParallel` 関数に置き換えた点です。

### `setParallel` 関数の導入

```go
// setParallel marks t as a parallel test if we're in short mode
// (all.bash), but as a serial test otherwise. Using t.Parallel isn't
// compatible with the afterTest func in non-short mode.
func setParallel(t *testing.T) {
	if testing.Short() {
		t.Parallel()
	}
}
```

*   **目的**: この関数は、テストが `testing.Short()` モードで実行されている場合にのみ、`t.Parallel()` を呼び出してテストを並列実行可能としてマークします。
*   **条件付き実行**: `if testing.Short()` という条件が重要です。
    *   `go test -short` で実行される場合（ショートモード）：`testing.Short()` は `true` を返し、`t.Parallel()` が呼び出されます。これにより、ショートモードでのテストは並列実行され、高速化されます。ショートモードでは `afterTest` がno-opであるため、並列実行による競合の問題は発生しません。
    *   通常の `go test` で実行される場合（フルモード）：`testing.Short()` は `false` を返し、`t.Parallel()` は呼び出されません。これにより、テストは直列に実行され、`afterTest` 関数との非互換性による不安定性を回避できます。

### 既存テストの変更

`src/net/http/serve_test.go` と `src/net/http/transport_test.go` 内の多くのテスト関数で、以前は直接 `t.Parallel()` が呼び出されていた箇所が、すべて `setParallel(t)` に置き換えられました。

例:
```go
// 変更前
func TestServerTimeouts(t *testing.T) {
    // ...
    t.Parallel() // これが問題を引き起こしていた
    defer afterTest(t)
    // ...
}

// 変更後
func TestServerTimeouts(t *testing.T) {
    // ...
    setParallel(t) // 条件付きで t.Parallel() を呼び出す
    defer afterTest(t)
    // ...
}
```

この変更により、`net/http` パッケージのテストは、ショートモードでは並列実行による高速化の恩恵を受けつつ、フルモードでは `afterTest` との競合を避けて安定した実行を保証できるようになりました。これは、テストの信頼性を高め、開発者が安心してテスト結果を信頼できるようにするための重要な改善です。

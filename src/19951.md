# [インデックス 19951] ファイルの概要

このコミットは、GoランタイムのC言語部分と、Goの内部Cコンパイラである`cmd/cc`における「無名サブ構造体C拡張」の使用を排除することを目的としています。この変更は、Goランタイムの移植性を向上させるために行われました。

影響を受ける主なファイル群は以下の通りです。

- `src/cmd/cc/dcl.c`: GoのCコンパイラにおける宣言処理。
- `src/pkg/runtime/callback_windows.c`: Windows環境でのコールバック処理。
- `src/pkg/runtime/chan.goc`, `src/pkg/runtime/chan.h`: Goのチャネル実装。
- `src/pkg/runtime/defs_plan9_386.h`: Plan 9 386アーキテクチャ向けの定義。
- `src/pkg/runtime/heapdump.c`: ヒープダンプ関連の処理。
- `src/pkg/runtime/iface.goc`: インターフェース関連の処理。
- `src/pkg/runtime/malloc.c`, `src/pkg/runtime/malloc.h`: メモリ割り当て（アロケータ）関連の処理。
- `src/pkg/runtime/mcache.c`, `src/pkg/runtime/mcentral.c`, `src/pkg/runtime/mheap.c`: メモリ管理の各コンポーネント。
- `src/pkg/runtime/mgc0.c`: ガベージコレクションの主要部分。
- `src/pkg/runtime/mprof.goc`, `src/pkg/runtime/mprof.h`: メモリプロファイリング関連。
- `src/pkg/runtime/netpoll.goc`: ネットワークポーリング処理。
- `src/pkg/runtime/proc.c`: プロセス（スケジューラ）関連の処理。
- `src/pkg/runtime/runtime.h`: ランタイムの共通ヘッダ。
- `src/pkg/runtime/sema.goc`: セマフォ実装。
- `src/pkg/runtime/sigqueue.goc`: シグナルキュー処理。
- `src/pkg/runtime/time.goc`: 時間関連の処理。
- `src/pkg/runtime/type.h`: 型情報関連。
- `src/pkg/runtime/vlrt_386.c`, `src/pkg/runtime/vlrt_arm.c`: 仮想レジスタ関連の処理（386およびARMアーキテクチャ）。

これらのファイルは、Goランタイムの低レベルな部分、特にメモリ管理、スケジューリング、チャネル、インターフェース、プロファイリングなど、C言語で実装されている多岐にわたるコンポーネントを含んでいます。

## コミット

このコミットは、GoランタイムとGoの内部Cコンパイラである`cmd/cc`から、C言語の「無名サブ構造体拡張」の使用を排除します。この拡張機能の使用をなくすことで、Goランタイムを他のコンパイラに移植することが容易になります。また、`cmd/cc`においても、意図しない使用を防ぐためにこの拡張機能を無効化しています。

## 変更の背景

Goランタイムは、パフォーマンスと低レベルなシステム操作のために、一部がC言語で記述されています。しかし、C言語には標準仕様の他に、特定のコンパイラ（例えばGCCやMicrosoft C、Plan 9 Cなど）が提供する独自の拡張機能が存在します。これらの拡張機能は、コードの記述を簡潔にしたり、特定の最適化を可能にしたりする一方で、そのコンパイラに強く依存するという問題を引き起こします。

このコミットで問題となっているのは、C言語の「無名サブ構造体（unnamed substructure）」、または「無名構造体（anonymous struct）」や「無名共用体（anonymous union）」と呼ばれる拡張機能です。Goランタイムがこの非標準的な拡張機能を使用していたため、GoランタイムをGCC以外のCコンパイラ（例えばClangなど）でコンパイルしようとすると、互換性の問題が発生し、移植が困難になる可能性がありました。

この変更の主な目的は、GoランタイムのC言語部分が特定のコンパイラ拡張に依存しないようにすることで、より広範なコンパイラ環境でのビルドと実行を可能にし、Goのクロスプラットフォーム対応と移植性をさらに強化することにあります。また、Go自身のCコンパイラである`cmd/cc`においても、将来的にこの非標準機能が誤って導入されることを防ぐために、その使用を明示的に禁止する変更も含まれています。

## 前提知識の解説

### C言語の構造体と共用体

C言語における`struct`（構造体）は、異なるデータ型の変数を一つにまとめるためのユーザー定義型です。例えば、座標を表す`struct Point { int x; int y; };`のように定義し、`struct Point p; p.x = 10;`のようにメンバーにアクセスします。
`union`（共用体）は、異なるデータ型の変数が同じメモリ領域を共有するための型です。これにより、メモリを節約できますが、一度に一つのメンバーしか有効な値を保持できません。

### 無名構造体と無名共用体（Unnamed Structs and Unions）

通常、構造体や共用体を定義する際には、その型に名前（タグ）を付けます。例えば `struct MyStruct { ... };` の `MyStruct` がタグです。
しかし、一部のCコンパイラ拡張では、このタグを省略して構造体や共用体を定義し、それを別の構造体や共用体の中に直接埋め込むことができます。これが「無名構造体」や「無名共用体」です。

例:
```c
struct Outer {
    int a;
    struct { // 無名構造体
        int b;
        int c;
    };
    union { // 無名共用体
        float f;
        int i;
    };
};

// 使用例
struct Outer obj;
obj.a = 1;
obj.b = 2; // 無名構造体のメンバーに直接アクセス
obj.c = 3;
obj.f = 3.14f; // 無名共用体のメンバーに直接アクセス
```
この例では、`Outer`構造体のインスタンス`obj`から、本来であれば`obj.inner_struct_name.b`のようにアクセスすべき`b`や`c`、そして`obj.inner_union_name.f`のようにアクセスすべき`f`に、直接`obj.b`や`obj.f`としてアクセスできます。これにより、コードが簡潔になるという利点があります。

### コンパイラ拡張と標準C

無名構造体や無名共用体は、C99以前のC言語の標準仕様には含まれていませんでした。これはGCCなどのコンパイラが提供する「拡張機能」として広く使われていました。C11規格でこの機能が標準化されましたが、それ以前のコードベースでは、この機能を使用していると、C11をサポートしていない、あるいはこの拡張機能を実装していないコンパイラではコンパイルエラーとなる可能性があります。

Goランタイムは、その低レベルな性質上、C言語で書かれた部分が多く、Goの初期開発ではPlan 9 CコンパイラやGCCが使われていました。そのため、これらのコンパイラが提供する拡張機能が意図せず、あるいは意図的に利用されていた可能性があります。

### GoランタイムのC言語実装

Goランタイムは、ガベージコレクタ、スケジューラ、チャネル、プリミティブな同期メカニズムなど、Goプログラムの実行を支える基盤となる部分です。これらの多くは、C言語（またはGoの内部Cコンパイラが処理するCに似た言語）で記述されており、OSやハードウェアとの密接な連携を必要とします。そのため、コンパイラの挙動や特定の言語機能のサポートが、ランタイムのビルドと動作に直接影響を与えます。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムのC言語コードベース全体で、無名構造体/共用体の使用箇所を特定し、それらを標準Cに準拠した形式に書き換えることです。具体的には、無名だった構造体や共用体に明示的な名前を付け、その名前を介してメンバーにアクセスするように変更します。

例えば、以下のような変更が行われます。

**変更前:**
```c
struct Callbacks {
    Lock; // Lock型が無名で埋め込まれている
    WinCallbackContext* ctxt[cb_max];
    int32 n;
};
```
この場合、`Callbacks`構造体のインスタンス`cbs`があったとすると、`runtime·lock(&cbs);`のように、あたかも`cbs`自体が`Lock`型であるかのように直接アクセスしていました。

**変更後:**
```c
struct Callbacks {
    Lock lock; // Lock型に'lock'という名前が付けられた
    WinCallbackContext* ctxt[cb_max];
    int32 n;
};
```
変更後は、`runtime·lock(&cbs.lock);`のように、明示的に`lock`メンバーを指定してアクセスするようになります。

この変更は、GoランタイムのC言語コード全体にわたって適用されます。特に、`Lock`型（Goランタイムのミューテックス）や、メモリ管理に関連する構造体（`Special`、`MCentral`、`MHeap`など）、プロファイリング関連の構造体（`Bucket`）などで、この無名サブ構造体のパターンが多用されていました。

また、Goの内部Cコンパイラである`src/cmd/cc`も変更されています。`dcl.c`ファイル内の`edecl`関数は、宣言の処理を担当していますが、この関数に無名構造体要素の宣言を検出した場合にエラーを発生させるロジックが追加されました。これにより、GoのCコンパイラ自体が、この非標準的なC拡張の使用を将来的に防ぐようになります。

この変更により、GoランタイムのC言語コードは、より標準的なC言語の慣習に沿うことになり、C11以前の標準Cコンパイラでもコンパイル可能になるか、少なくとも移植作業が大幅に簡素化されます。これは、Goが様々なプラットフォームやアーキテクチャで動作するための重要なステップです。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下のパターンに集約されます。

1.  **無名構造体/共用体フィールドへの名前の付与**: 多くの構造体定義において、無名で埋め込まれていた構造体や共体フィールドに明示的な名前が与えられました。
2.  **フィールドアクセス方法の変更**: 上記の変更に伴い、無名フィールドに直接アクセスしていた箇所が、新たに付与された名前を介してアクセスするように変更されました。
3.  **`cmd/cc`における無名構造体要素の禁止**: GoのCコンパイラが、無名構造体要素の宣言をエラーとするようになりました。

以下に、代表的な変更箇所をいくつか示します。

### 1. `src/pkg/runtime/callback_windows.c` および `src/pkg/runtime/chan.h`

`Lock`型が無名で構造体に埋め込まれていた箇所に`lock`という名前が付けられました。

**変更前 (`src/pkg/runtime/callback_windows.c`):**
```c
typedef	struct	Callbacks	Callbacks;
struct	Callbacks {
	Lock; // 無名フィールド
	WinCallbackContext*	ctxt[cb_max];
	int32	n;
};
// ...
runtime·lock(&cbs); // 直接アクセス
```

**変更後 (`src/pkg/runtime/callback_windows.c`):**
```c
typedef	struct	Callbacks	Callbacks;
struct	Callbacks {
	Lock	lock; // 'lock'という名前が付与された
	WinCallbackContext*	ctxt[cb_max];
	int32	n;
};
// ...
runtime·lock(&cbs.lock); // 名前を介してアクセス
```

同様の変更が`src/pkg/runtime/chan.h`の`Hchan`構造体にも適用されています。

**変更前 (`src/pkg/runtime/chan.h`):**
```c
struct	Hchan
{
	// ...
	Lock; // 無名フィールド
};
```

**変更後 (`src/pkg/runtime/chan.h`):**
```c
struct	Hchan
{
	// ...
	Lock	lock; // 'lock'という名前が付与された
};
```

そして、`src/pkg/runtime/chan.goc`では、`runtime·lock(c);`のようなチャネルのロック操作が`runtime·lock(&c->lock);`に変更されています。

### 2. `src/pkg/runtime/malloc.h`

`SpecialFinalizer`や`SpecialProfile`といった構造体で、`Special`型が無名で埋め込まれていた箇所に`special`という名前が付けられました。

**変更前 (`src/pkg/runtime/malloc.h`):**
```c
typedef struct SpecialFinalizer SpecialFinalizer;
struct SpecialFinalizer
{
	Special; // 無名フィールド
	FuncVal*	fn;
	uintptr	nret;
	Type*	fint;
	PtrType*	ot;
};
```

**変更後 (`src/pkg/runtime/malloc.h`):**
```c
typedef struct SpecialFinalizer SpecialFinalizer;
struct SpecialFinalizer
{
	Special	special; // 'special'という名前が付与された
	FuncVal*	fn;
	uintptr	nret;
	Type*	fint;
	PtrType*	ot;
};
```
これに伴い、`src/pkg/runtime/heapdump.c`や`src/pkg/runtime/mgc0.c`など、これらの構造体のメンバーにアクセスしていた箇所が`spf->special.offset`のように変更されています。

### 3. `src/pkg/runtime/mprof.h`

プロファイリング関連の`Bucket`構造体において、無名共用体の中にあったメンバーが、`mp`と`bp`という名前の付いた構造体の中に移動されました。

**変更前 (`src/pkg/runtime/mprof.h`):**
```c
struct Bucket
{
	// ...
	union {
		struct { // 無名構造体
			uintptr	allocs;
			// ...
		};
		struct  // typ == BProf
		{
			int64	count;
			int64	cycles;
		};
	};
	// ...
};
```

**変更後 (`src/pkg/runtime/mprof.h`):**
```c
struct Bucket
{
	// ...
	union {
		struct { // mpという名前の構造体
			uintptr	allocs;
			// ...
		} mp;
		struct  // typ == BProf
		{
			int64	count;
			int64	cycles;
		} bp; // bpという名前の構造体
	} data; // dataという名前の共用体
	// ...
};
```
これにより、`b->allocs`のようなアクセスは`b->data.mp.allocs`に、`b->count`は`b->data.bp.count`のように変更されました。

### 4. `src/cmd/cc/dcl.c`

GoのCコンパイラである`cmd/cc`において、無名構造体要素の宣言を禁止するロジックが追加されました。

**変更前 (`src/cmd/cc/dcl.c`):**
```c
edecl(int c, Type *t, Sym *s)
{
	Type *t1;

	if(s == S) {
		if(!typesu[t->etype])
			diag(Z, "unnamed structure element must be struct/union");
		if(c != CXXX)
			diag(Z, "unnamed structure element cannot have class");
	} else
		if(c != CXXX)
			diag(Z, "structure element cannot have class: %s", s->name);
	t1 = t;
```

**変更後 (`src/cmd/cc/dcl.c`):**
```c
edecl(int c, Type *t, Sym *s)
{
	Type *t1;

	if(s == S)
		diag(Z, "unnamed structure elements not supported"); // 無名構造体要素をサポートしない旨のエラー
	else
		if(c != CXXX)
			diag(Z, "structure element cannot have class: %s", s->name);
	t1 = t;
```
`s == S`はシンボルがない（つまり無名である）ことを意味します。変更前は、無名であっても特定の条件（構造体/共用体であることなど）を満たせば許容されていましたが、変更後は無名構造体要素は一律でサポートされないことになりました。

## コアとなるコードの解説

これらの変更は、GoランタイムのC言語コードが、特定のコンパイラ拡張に依存しないようにするためのものです。

-   **無名フィールドへの名前の付与**:
    `Lock;`から`Lock lock;`への変更は、最も頻繁に見られるパターンです。これは、`Lock`型のインスタンスが構造体内に無名で埋め込まれていた状態から、`lock`という明示的な名前を持つフィールドとして定義されたことを意味します。これにより、`runtime·lock(&cbs);`のように構造体自体をロックの対象としていたコードが、`runtime·lock(&cbs.lock);`のように、構造体内の`lock`フィールドを明示的に指定してロックする形に変わります。この変更は、コードの可読性を向上させ、どのフィールドがロックオブジェクトであるかを明確にする効果もあります。また、無名構造体/共用体は、そのメンバーが親構造体のメンバーであるかのように直接アクセスできるという特性がありますが、名前を付けることで、この「直接アクセス」の挙動がなくなります。

-   **`Special`構造体の変更**:
    `Special;`から`Special special;`への変更も同様です。`Special`は、Goのガベージコレクタやプロファイラがオブジェクトに付加する特殊な情報（ファイナライザやプロファイル情報など）を管理するための基底構造体です。この変更により、`SpecialFinalizer`や`SpecialProfile`といった派生構造体から`Special`のメンバーにアクセスする際に、`spf->offset`のような直接アクセスではなく、`spf->special.offset`のように明示的なフィールド名を経由するようになりました。これは、コードの意図をより明確にし、コンパイラ間の互換性を高める上で重要です。

-   **`Bucket`構造体の変更**:
    `Bucket`構造体における無名共用体の変更は、メモリプロファイリングとブロックプロファイリングのデータを管理する方法に影響を与えます。以前は、`Bucket`内に無名共用体があり、その中にメモリプロファイリング用のメンバー（`allocs`, `frees`など）とブロックプロファイリング用のメンバー（`count`, `cycles`など）が直接定義されていました。これにより、`b->allocs`や`b->count`のように直接アクセスできていました。
    変更後は、これらのメンバーがそれぞれ`mp`と`bp`という名前の付いた内部構造体にまとめられ、それらが`data`という名前の共用体の中に配置されました。結果として、アクセスは`b->data.mp.allocs`や`b->data.bp.count`のようになります。これは、コードの構造をより明確にし、異なるプロファイリングデータが共用体内でどのように配置されているかを視覚的に理解しやすくします。

-   **`cmd/cc`の変更**:
    `src/cmd/cc/dcl.c`における変更は、GoのCコンパイラが、C言語の無名構造体要素の宣言を許可しないようにするものです。これは、Goランタイムがこの非標準機能への依存を排除するだけでなく、Goエコシステム全体でこの機能が誤って導入されることを防ぐための予防措置です。これにより、GoのCコンパイラはより標準Cに厳密に準拠するようになり、将来的な移植性や互換性の問題を未然に防ぐことができます。

これらの変更は、個々のコード行レベルでは単純な名前の追加やアクセス方法の変更に見えますが、Goランタイム全体のC言語コードベースの健全性と移植性を大幅に向上させるための、体系的かつ重要なリファクタリングです。

## コミット

このコミットは、GoランタイムとGoの内部Cコンパイラである`cmd/cc`から、C言語の「無名サブ構造体拡張」の使用を排除します。この拡張機能の使用をなくすことで、Goランタイムを他のコンパイラに移植することが容易になります。また、`cmd/cc`においても、意図しない使用を防ぐためにこの拡張機能を無効化しています。

## 変更の背景

Goランタイムは、パフォーマンスと低レベルなシステム操作のために、一部がC言語で記述されています。しかし、C言語には標準仕様の他に、特定のコンパイラ（例えばGCCやMicrosoft C、Plan 9 Cなど）が提供する独自の拡張機能が存在します。これらの拡張機能は、コードの記述を簡潔にしたり、特定の最適化を可能にしたりする一方で、そのコンパイラに強く依存するという問題を引き起こします。

このコミットで問題となっているのは、C言語の「無名サブ構造体（unnamed substructure）」、または「無名構造体（anonymous struct）」や「無名共用体（anonymous union）」と呼ばれる拡張機能です。Goランタイムがこの非標準的な拡張機能を使用していたため、GoランタイムをGCC以外のCコンパイラ（例えばClangなど）でコンパイルしようとすると、互換性の問題が発生し、移植が困難になる可能性がありました。

この変更の主な目的は、GoランタイムのC言語部分が特定のコンパイラ拡張に依存しないようにすることで、より広範なコンパイラ環境でのビルドと実行を可能にし、Goのクロスプラットフォーム対応と移植性をさらに強化することにあります。また、Go自身のCコンパイラである`cmd/cc`においても、将来的にこの非標準機能が誤って導入されることを防ぐために、その使用を明示的に禁止する変更も含まれています。

## 前提知識の解説

### C言語の構造体と共用体

C言語における`struct`（構造体）は、異なるデータ型の変数を一つにまとめるためのユーザー定義型です。例えば、座標を表す`struct Point { int x; int y; };`のように定義し、`struct Point p; p.x = 10;`のようにメンバーにアクセスします。
`union`（共用体）は、異なるデータ型の変数が同じメモリ領域を共有するための型です。これにより、メモリを節約できますが、一度に一つのメンバーしか有効な値を保持できません。

### 無名構造体と無名共用体（Unnamed Structs and Unions）

通常、構造体や共用体を定義する際には、その型に名前（タグ）を付けます。例えば `struct MyStruct { ... };` の `MyStruct` がタグです。
しかし、一部のCコンパイラ拡張では、このタグを省略して構造体や共用体を定義し、それを別の構造体や共用体の中に直接埋め込むことができます。これが「無名構造体」や「無名共用体」です。

例:
```c
struct Outer {
    int a;
    struct { // 無名構造体
        int b;
        int c;
    };
    union { // 無名共用体
        float f;
        int i;
    };
};

// 使用例
struct Outer obj;
obj.a = 1;
obj.b = 2; // 無名構造体のメンバーに直接アクセス
obj.c = 3;
obj.f = 3.14f; // 無名共用体のメンバーに直接アクセス
```
この例では、`Outer`構造体のインスタンス`obj`から、本来であれば`obj.inner_struct_name.b`のようにアクセスすべき`b`や`c`、そして`obj.inner_union_name.f`のようにアクセスすべき`f`に、直接`obj.b`や`obj.f`としてアクセスできます。これにより、コードが簡潔になるという利点があります。

### コンパイラ拡張と標準C

無名構造体や無名共用体は、C99以前のC言語の標準仕様には含まれていませんでした。これはGCCなどのコンパイラが提供する「拡張機能」として広く使われていました。C11規格でこの機能が標準化されましたが、それ以前のコードベースでは、この機能を使用していると、C11をサポートしていない、あるいはこの拡張機能を実装していないコンパイラではコンパイルエラーとなる可能性があります。

Goランタイムは、その低レベルな性質上、C言語で書かれた部分が多く、Goの初期開発ではPlan 9 CコンパイラやGCCが使われていました。そのため、これらのコンパイラが提供する拡張機能が意図せず、あるいは意図的に利用されていた可能性があります。

### GoランタイムのC言語実装

Goランタイムは、ガベージコレクタ、スケジューラ、チャネル、プリミティブな同期メカニズムなど、Goプログラムの実行を支える基盤となる部分です。これらの多くは、C言語（またはGoの内部Cコンパイラが処理するCに似た言語）で記述されており、OSやハードウェアとの密接な連携を必要とします。そのため、コンパイラの挙動や特定の言語機能のサポートが、ランタイムのビルドと動作に直接影響を与えます。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムのC言語コードベース全体で、無名構造体/共用体の使用箇所を特定し、それらを標準Cに準拠した形式に書き換えることです。具体的には、無名だった構造体や共用体に明示的な名前を付け、その名前を介してメンバーにアクセスするように変更します。

例えば、以下のような変更が行われます。

**変更前:**
```c
struct Callbacks {
    Lock; // Lock型が無名で埋め込まれている
    WinCallbackContext* ctxt[cb_max];
    int32 n;
};
```
この場合、`Callbacks`構造体のインスタンス`cbs`があったとすると、`runtime·lock(&cbs);`のように、あたかも`cbs`自体が`Lock`型であるかのように直接アクセスしていました。

**変更後:**
```c
struct Callbacks {
    Lock lock; // Lock型に'lock'という名前が付けられた
    WinCallbackContext* ctxt[cb_max];
    int32 n;
};
```
変更後は、`runtime·lock(&cbs.lock);`のように、明示的に`lock`メンバーを指定してアクセスするようになります。

この変更は、GoランタイムのC言語コード全体にわたって適用されます。特に、`Lock`型（Goランタイムのミューテックス）や、メモリ管理に関連する構造体（`Special`、`MCentral`、`MHeap`など）、プロファイリング関連の構造体（`Bucket`）などで、この無名サブ構造体のパターンが多用されていました。

また、Goの内部Cコンパイラである`src/cmd/cc`も変更されています。`dcl.c`ファイル内の`edecl`関数は、宣言の処理を担当していますが、この関数に無名構造体要素の宣言を検出した場合にエラーを発生させるロジックが追加されました。これにより、GoのCコンパイラ自体が、この非標準的なC拡張の使用を将来的に防ぐようになります。

この変更により、GoランタイムのC言語コードは、より標準的なC言語の慣習に沿うことになり、C11以前の標準Cコンパイラでもコンパイル可能になるか、少なくとも移植作業が大幅に簡素化されます。これは、Goが様々なプラットフォームやアーキテクチャで動作するための重要なステップです。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下のパターンに集約されます。

1.  **無名構造体/共用体フィールドへの名前の付与**: 多くの構造体定義において、無名で埋め込まれていた構造体や共体フィールドに明示的な名前が与えられました。
2.  **フィールドアクセス方法の変更**: 上記の変更に伴い、無名フィールドに直接アクセスしていた箇所が、新たに付与された名前を介してアクセスするように変更されました。
3.  **`cmd/cc`における無名構造体要素の禁止**: GoのCコンパイラが、無名構造体要素の宣言をエラーとするようになりました。

以下に、代表的な変更箇所をいくつか示します。

### 1. `src/pkg/runtime/callback_windows.c` および `src/pkg/runtime/chan.h`

`Lock`型が無名で構造体に埋め込まれていた箇所に`lock`という名前が付けられました。

**変更前 (`src/pkg/runtime/callback_windows.c`):**
```c
typedef	struct	Callbacks	Callbacks;
struct	Callbacks {
	Lock; // 無名フィールド
	WinCallbackContext*	ctxt[cb_max];
	int32	n;
};
// ...
runtime·lock(&cbs); // 直接アクセス
```

**変更後 (`src/pkg/runtime/callback_windows.c`):**
```c
typedef	struct	Callbacks	Callbacks;
struct	Callbacks {
	Lock	lock; // 'lock'という名前が付与された
	WinCallbackContext*	ctxt[cb_max];
	int32	n;
};
// ...
runtime·lock(&cbs.lock); // 名前を介してアクセス
```

同様の変更が`src/pkg/runtime/chan.h`の`Hchan`構造体にも適用されています。

**変更前 (`src/pkg/runtime/chan.h`):
```c
struct	Hchan
{
	// ...
	Lock; // 無名フィールド
};
```

**変更後 (`src/pkg/runtime/chan.h`):**
```c
struct	Hchan
{
	// ...
	Lock	lock; // 'lock'という名前が付与された
};
```

そして、`src/pkg/runtime/chan.goc`では、`runtime·lock(c);`のようなチャネルのロック操作が`runtime·lock(&c->lock);`に変更されています。

### 2. `src/pkg/runtime/malloc.h`

`SpecialFinalizer`や`SpecialProfile`といった構造体で、`Special`型が無名で埋め込まれていた箇所に`special`という名前が付けられました。

**変更前 (`src/pkg/runtime/malloc.h`):**
```c
typedef struct SpecialFinalizer SpecialFinalizer;
struct SpecialFinalizer
{
	Special; // 無名フィールド
	FuncVal*	fn;
	uintptr	nret;
	Type*	fint;
	PtrType*	ot;
};
```

**変更後 (`src/pkg/runtime/malloc.h`):**
```c
typedef struct SpecialFinalizer SpecialFinalizer;
struct SpecialFinalizer
{
	Special	special; // 'special'という名前が付与された
	FuncVal*	fn;
	uintptr	nret;
	Type*	fint;
	PtrType*	ot;
};
```
これに伴い、`src/pkg/runtime/heapdump.c`や`src/pkg/runtime/mgc0.c`など、これらの構造体のメンバーにアクセスしていた箇所が`spf->special.offset`のように変更されています。

### 3. `src/pkg/runtime/mprof.h`

プロファイリング関連の`Bucket`構造体において、無名共用体の中にあったメンバーが、`mp`と`bp`という名前の付いた構造体の中に移動されました。

**変更前 (`src/pkg/runtime/mprof.h`):**
```c
struct Bucket
{
	// ...
	union {
		struct { // 無名構造体
			uintptr	allocs;
			// ...
		};
		struct  // typ == BProf
		{
			int64	count;
			int64	cycles;
		};
	};
	// ...
};
```

**変更後 (`src/pkg/runtime/mprof.h`):**
```c
struct Bucket
{
	// ...
	union {
		struct { // mpという名前の構造体
			uintptr	allocs;
			// ...
		} mp;
		struct  // typ == BProf
		{
			int64	count;
			int64	cycles;
		} bp; // bpという名前の構造体
	} data; // dataという名前の共用体
	// ...
};
```
これにより、`b->allocs`のようなアクセスは`b->data.mp.allocs`に、`b->count`は`b->data.bp.count`のように変更されました。

### 4. `src/cmd/cc/dcl.c`

GoのCコンパイラである`cmd/cc`において、無名構造体要素の宣言を禁止するロジックが追加されました。

**変更前 (`src/cmd/cc/dcl.c`):**
```c
edecl(int c, Type *t, Sym *s)
{
	Type *t1;

	if(s == S) {
		if(!typesu[t->etype])
			diag(Z, "unnamed structure element must be struct/union");
		if(c != CXXX)
			diag(Z, "unnamed structure element cannot have class");
	} else
		if(c != CXXX)
			diag(Z, "structure element cannot have class: %s", s->name);
	t1 = t;
```

**変更後 (`src/cmd/cc/dcl.c`):**
```c
edecl(int c, Type *t, Sym *s)
{
	Type *t1;

	if(s == S)
		diag(Z, "unnamed structure elements not supported"); // 無名構造体要素をサポートしない旨のエラー
	else
		if(c != CXXX)
			diag(Z, "structure element cannot have class: %s", s->name);
	t1 = t;
```
`s == S`はシンボルがない（つまり無名である）ことを意味します。変更前は、無名であっても特定の条件（構造体/共用体であることなど）を満たせば許容されていましたが、変更後は無名構造体要素は一律でサポートされないことになりました。

## コアとなるコードの解説

これらの変更は、GoランタイムのC言語コードが、特定のコンパイラ拡張に依存しないようにするためのものです。

-   **無名フィールドへの名前の付与**:
    `Lock;`から`Lock lock;`への変更は、最も頻繁に見られるパターンです。これは、`Lock`型のインスタンスが構造体内に無名で埋め込まれていた状態から、`lock`という明示的な名前を持つフィールドとして定義されたことを意味します。これにより、`runtime·lock(&cbs);`のように構造体自体をロックの対象としていたコードが、`runtime·lock(&cbs.lock);`のように、構造体内の`lock`フィールドを明示的に指定してロックする形に変わります。この変更は、コードの可読性を向上させ、どのフィールドがロックオブジェクトであるかを明確にする効果もあります。また、無名構造体/共用体は、そのメンバーが親構造体のメンバーであるかのように直接アクセスできるという特性がありますが、名前を付けることで、この「直接アクセス」の挙動がなくなります。

-   **`Special`構造体の変更**:
    `Special;`から`Special special;`への変更も同様です。`Special`は、Goのガベージコレクタやプロファイラがオブジェクトに付加する特殊な情報（ファイナライザやプロファイル情報など）を管理するための基底構造体です。この変更により、`SpecialFinalizer`や`SpecialProfile`といった派生構造体から`Special`のメンバーにアクセスする際に、`spf->offset`のような直接アクセスではなく、`spf->special.offset`のように明示的なフィールド名を経由するようになりました。これは、コードの意図をより明確にし、コンパイラ間の互換性を高める上で重要です。

-   **`Bucket`構造体の変更**:
    `Bucket`構造体における無名共用体の変更は、メモリプロファイリングとブロックプロファイリングのデータを管理する方法に影響を与えます。以前は、`Bucket`内に無名共用体があり、その中にメモリプロファイリング用のメンバー（`allocs`, `frees`など）とブロックプロファイリング用のメンバー（`count`, `cycles`など）が直接定義されていました。これにより、`b->allocs`や`b->count`のように直接アクセスできていました。
    変更後は、これらのメンバーがそれぞれ`mp`と`bp`という名前の付いた内部構造体にまとめられ、それらが`data`という名前の共用体の中に配置されました。結果として、アクセスは`b->data.mp.allocs`や`b->data.bp.count`のようになります。これは、コードの構造をより明確にし、異なるプロファイリングデータが共用体内でどのように配置されているかを視覚的に理解しやすくします。

-   **`cmd/cc`の変更**:
    `src/cmd/cc/dcl.c`における変更は、GoのCコンパイラが、C言語の無名構造体要素の宣言を許可しないようにするものです。これは、Goランタイムがこの非標準機能への依存を排除するだけでなく、Goエコシステム全体でこの機能が誤って導入されることを防ぐための予防措置です。これにより、GoのCコンパイラはより標準Cに厳密に準拠するようになり、将来的な移植性や互換性の問題を未然に防ぐことができます。

これらの変更は、個々のコード行レベルでは単純な名前の追加やアクセス方法の変更に見えますが、Goランタイム全体のC言語コードベースの健全性と移植性を大幅に向上させるための、体系的かつ重要なリファクタリングです。

# [インデックス 20748] ファイルの概要

このコミットは、Go言語のビルドシステムにおけるファイル名の解釈ロジックの変更に関するものです。具体的には、`go/build`パッケージが、ファイル名に基づいてOSやアーキテクチャ固有のビルドタグを自動的に適用する際の挙動を修正しています。これにより、`android.go`のようなファイルが意図せずAndroid固有として扱われることを防ぎ、将来的な新しいOSの導入時に既存のコードが壊れる可能性を低減します。

## 元コミット内容

このコミットは、`go/build`パッケージがファイル名からOS固有のビルドタグを推測する際のロジックを修正しています。以前の挙動では、`android.go`のようなファイル名が、たとえそのファイルがAndroid固有のコードを含んでいなくても、自動的にAndroidプラットフォーム向けとして扱われていました。この変更により、ファイル名が`GOOS`（オペレーティングシステム）や`GOARCH`（アーキテクチャ）と一致する場合でも、その前にアンダースコアで区切られた非空のプレフィックス（例: `foo_android.go`の`foo`）がなければ、自動的なタグ付けは行われないようになりました。これは、Goのドキュメントが既に記述していた内容とコードの実際の挙動との乖離を修正するものです。

この修正は、Go 1.4のリリースノートで言及されるべき重要な変更点としてマークされています。また、`code.google.com/p/go.text/collate/tools/colcmp/darwin.go`というファイルがこの変更の影響を受ける可能性があるものの、ファイル内に明示的なビルドタグが含まれているため、問題なく動作することが確認されています。

## 変更の背景

Go言語のビルドシステムには、特定のファイルが特定のオペレーティングシステム（`GOOS`）やアーキテクチャ（`GOARCH`）向けにのみコンパイルされるようにするための「ビルドタグ（build tags）」という仕組みがあります。これは、ソースコード内に`// +build linux`のようなコメントを記述することで明示的に指定できますが、Goツールチェーンはファイル名にもとづいて暗黙的にビルドタグを適用する機能も持っています。例えば、`foo_linux.go`というファイルはLinux向けに、`bar_amd64.go`というファイルはAMD64アーキテクチャ向けに自動的にタグ付けされます。

しかし、この暗黙的なタグ付けのルールに曖昧さがありました。特に、`linux.go`や`android.go`のように、ファイル名全体がOS名と一致する場合の挙動が問題でした。本来の意図は、`foo_linux.go`のようにOS名の前に何らかのプレフィックスがある場合にのみ暗黙的なタグ付けを行うことでしたが、実際のコードではプレフィックスがない場合でもタグ付けが行われていました。

この問題は、新しいオペレーティングシステム、特にAndroidがGoのサポート対象として追加された際に顕在化しました。もし`android.go`という名前のファイルがプロジェクト内に存在した場合、それがAndroid固有のコードでなくても、GoツールチェーンはそれをAndroid向けとしてコンパイルしようとします。これにより、意図しないコンパイルエラーや、クロスコンパイル時の予期せぬ挙動が発生する可能性がありました。

このコミットは、このドキュメントとコードの乖離を修正し、ファイル名による暗黙的なビルドタグの適用ルールを厳密にすることで、将来的な互換性の問題を未然に防ぐことを目的としています。具体的には、`GOOS`や`GOARCH`にマッチするサフィックスの前に、アンダースコアで区切られた非空のプレフィックスが必須となるように変更されました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語のビルドに関する前提知識が必要です。

1.  **Goのビルドタグ（Build Tags / Build Constraints）**:
    Go言語では、ソースファイルに特定のコメント行を追加することで、そのファイルを特定のビルド条件（OS、アーキテクチャ、Goバージョンなど）でのみコンパイルするように指定できます。これをビルドタグまたはビルド制約と呼びます。
    例: `//go:build linux && amd64` (Go 1.17以降の形式) または `// +build linux,amd64` (Go 1.16以前の形式)
    これにより、異なるプラットフォーム向けに異なる実装を提供したり、特定の機能が特定の環境でのみ利用可能であることを保証したりできます。

2.  **ファイル名による暗黙的なビルドタグ**:
    Goツールチェーンは、ソースファイルのファイル名にもとづいて、暗黙的にビルドタグを適用する特別なルールを持っています。これは、`GOOS`（オペレーティングシステム）と`GOARCH`（アーキテクチャ）に特に関連が深いです。
    *   `filename_GOOS.go`: 例: `main_linux.go` はLinuxでのみコンパイルされます。
    *   `filename_GOARCH.go`: 例: `asm_amd64.go` はAMD64アーキテクチャでのみコンパイルされます。
    *   `filename_GOOS_GOARCH.go`: 例: `net_windows_amd64.go` はWindows上のAMD64でのみコンパイルされます。
    このルールは、明示的なビルドタグの記述を省略できるため、Goのコードベースで広く利用されています。

3.  **`GOOS`と`GOARCH`**:
    *   `GOOS`: Goプログラムをビルドするターゲットのオペレーティングシステムを指定する環境変数です。例: `linux`, `windows`, `darwin` (macOS), `android`, `freebsd` など。
    *   `GOARCH`: GoプログラムをビルドするターゲットのCPUアーキテクチャを指定する環境変数です。例: `amd64`, `arm`, `arm64`, `386`, `ppc64` など。
    これらの環境変数は、Goのクロスコンパイルにおいて非常に重要です。

4.  **`go/build`パッケージ**:
    Go標準ライブラリの`go/build`パッケージは、Goのソースコードを解析し、ビルド可能なパッケージを特定するための機能を提供します。これには、ビルドタグの解釈やファイル名のルールに基づいたファイルの選択ロジックが含まれます。このコミットで変更されているのは、このパッケージ内のファイル選択ロジックです。

## 技術的詳細

このコミットの技術的な核心は、`go/build`パッケージ内の`(*Context).goodOSArchFile`関数の変更にあります。この関数は、与えられたファイル名が現在のビルドコンテキスト（`GOOS`や`GOARCH`など）において有効かどうかを判断します。

変更前のロジックでは、ファイル名が`GOOS`や`GOARCH`に直接マッチする場合（例: `android.go`が`GOOS=android`の場合）でも、そのファイルがビルド対象として含まれてしまう可能性がありました。これは、Goのドキュメントが「アンダースコアで区切られた非空のプレフィックスが必要」と規定していたにもかかわらず、コードがそのルールを厳密に適用していなかったためです。

コミットによって追加されたコードは以下の部分です。

```go
// Before Go 1.4, a file called "linux.go" would be equivalent to having a
// build tag "linux" in that file. For Go 1.4 and beyond, we require this
// auto-tagging to apply only to files with a non-empty prefix, so
// "foo_linux.go" is tagged but "linux.go" is not. This allows new operating
// sytems, such as android, to arrive without breaking existing code with
// innocuous source code in "android.go". The easiest fix: files without
// underscores are always included.
if !strings.ContainsRune(name, '_') {
	return true
}
```

このコードブロックは、ファイル名（拡張子を除く）にアンダースコア（`_`）が含まれていない場合に、そのファイルを常にビルド対象として含めるように変更しています。これは、`android.go`のようなファイル名が、`_`を含まないため、OS/ARCH固有の自動タグ付けの対象外となり、通常のファイルとして扱われることを意味します。

具体的な動作は以下のようになります。

1.  `goodOSArchFile`関数は、ファイル名（例: `foo_android.go`や`android.go`）を受け取ります。
2.  まず、ファイル名から拡張子を除去します（例: `foo_android`、`android`）。
3.  次に、変更が加えられた部分で、拡張子を除去したファイル名にアンダースコアが含まれているかを確認します。
    *   もしアンダースコアが含まれていない場合（例: `android`）、このファイルはOS/ARCH固有の自動タグ付けの対象外とみなされ、常に`true`（ビルド対象）を返します。これにより、`android.go`というファイルが、たとえ`GOOS=android`であっても、自動的にAndroid固有のファイルとして扱われることはなくなります。
    *   もしアンダースコアが含まれている場合（例: `foo_android`）、従来のロジック（`strings.Split(name, "_")`で分割し、最後の要素が`GOOS`や`GOARCH`にマッチするかどうかをチェックする）が適用されます。この場合、`foo_android.go`は`GOOS=android`の場合にのみビルド対象となります。

この変更により、Go 1.4以降では、ファイル名による暗黙的なビルドタグの適用は、`foo_os.go`や`bar_arch.go`のように、OS/ARCH名の前にアンダースコアで区切られたプレフィックスがある場合に限定されるようになりました。これにより、`android.go`のような一般的な名前のファイルが、意図せず特定のプラットフォームに紐付けられることがなくなります。

テストケースも追加され、この新しい挙動が正しく機能することを確認しています。特に、`android.go`や`plan9.go`のようなファイルが、アンダースコアがないために常にビルド対象となることがテストされています。

## コアとなるコードの解説

`src/go/build/build.go`の変更は、`goodOSArchFile`関数内でファイル名から拡張子を除去した後の処理に新しい条件分岐を追加しています。

```go
if !strings.ContainsRune(name, '_') {
	return true
}
```

このコードは、`name`（拡張子を除去したファイル名、例: `android`、`foo_linux`）にアンダースコア（`_`）が含まれていないかどうかをチェックします。

*   **`!strings.ContainsRune(name, '_')` が `true` の場合**:
    これは、ファイル名にアンダースコアが含まれていないことを意味します（例: `android.go`が`android`になる場合）。この場合、関数は即座に`true`を返します。これは、このようなファイルがOS/ARCH固有の自動タグ付けの対象外となり、常にビルド対象として含まれることを保証します。コミットメッセージにある「The easiest fix: files without underscores are always included.」という部分がこれに該当します。これにより、`android.go`のようなファイルが、たとえ`GOOS=android`であっても、自動的にAndroid固有のファイルとして扱われることはなくなります。

*   **`!strings.ContainsRune(name, '_')` が `false` の場合**:
    これは、ファイル名にアンダースコアが含まれていることを意味します（例: `foo_android.go`が`foo_android`になる場合）。この場合、新しい条件分岐はスキップされ、従来のロジックである`l := strings.Split(name, "_")`以降の処理が実行されます。この従来のロジックは、ファイル名をアンダースコアで分割し、最後の要素が`GOOS`や`GOARCH`にマッチするかどうかをチェックすることで、OS/ARCH固有の自動タグ付けを行います。

この変更により、Goのビルドシステムは、ファイル名による暗黙的なビルドタグの適用をより厳密に行うようになり、ドキュメントの記述と実際の挙動が一致するようになりました。

    これにより、異なるプラットフォーム向けに異なる実装を提供したり、特定の機能が特定の環境でのみ利用可能であることを保証したりできます。

2.  **ファイル名による暗黙的なビルドタグ**:
    Goツールチェーンは、ソースファイルのファイル名にもとづいて、暗黙的にビルドタグを適用する特別なルールを持っています。これは、`GOOS`（オペレーティングシステム）と`GOARCH`（アーキテクチャ）に特に関連が深いです。
    *   `filename_GOOS.go`: 例: `main_linux.go` はLinuxでのみコンパイルされます。
    *   `filename_GOARCH.go`: 例: `asm_amd64.go` はAMD64アーキテクチャでのみコンパイルされます。
    *   `filename_GOOS_GOARCH.go`: 例: `net_windows_amd64.go` はWindows上のAMD64でのみコンパイルされます。
    このルールは、明示的なビルドタグの記述を省略できるため、Goのコードベースで広く利用されています。

3.  **`GOOS`と`GOARCH`**:
    *   `GOOS`: Goプログラムをビルドするターゲットのオペレーティングシステムを指定する環境変数です。例: `linux`, `windows`, `darwin` (macOS), `android`, `freebsd` など。
    *   `GOARCH`: GoプログラムをビルドするターゲットのCPUアーキテクチャを指定する環境変数です。例: `amd64`, `arm`, `arm64`, `386`, `ppc64` など。
    これらの環境変数は、Goのクロスコンパイルにおいて非常に重要です。

4.  **`go/build`パッケージ**:
    Go標準ライブラリの`go/build`パッケージは、Goのソースコードを解析し、ビルド可能なパッケージを特定するための機能を提供します。これには、ビルドタグの解釈やファイル名のルールに基づいたファイルの選択ロジックが含まれます。このコミットで変更されているのは、このパッケージ内のファイル選択ロジックです。

## 技術的詳細

このコミットの技術的な核心は、`go/build`パッケージ内の`(*Context).goodOSArchFile`関数の変更にあります。この関数は、与えられたファイル名が現在のビルドコンテキスト（`GOOS`や`GOARCH`など）において有効かどうかを判断します。

変更前のロジックでは、ファイル名が`GOOS`や`GOARCH`に直接マッチする場合（例: `android.go`が`GOOS=android`の場合）でも、そのファイルがビルド対象として含まれてしまう可能性がありました。これは、Goのドキュメントが「アンダースコアで区切られた非空のプレフィックスが必要」と規定していたにもかかわらず、コードがそのルールを厳密に適用していなかったためです。

コミットによって追加されたコードは以下の部分です。

```go
// Before Go 1.4, a file called "linux.go" would be equivalent to having a
// build tag "linux" in that file. For Go 1.4 and beyond, we require this
// auto-tagging to apply only to files with a non-empty prefix, so
// "foo_linux.go" is tagged but "linux.go" is not. This allows new operating
// sytems, such as android, to arrive without breaking existing code with
// innocuous source code in "android.go". The easiest fix: files without
// underscores are always included.
if !strings.ContainsRune(name, '_') {
	return true
}
```

このコードブロックは、ファイル名（拡張子を除く）にアンダースコア（`_`）が含まれていない場合に、そのファイルを常にビルド対象として含めるように変更しています。これは、`android.go`のようなファイル名が、`_`を含まないため、OS/ARCH固有の自動タグ付けの対象外となり、通常のファイルとして扱われることを意味します。

具体的な動作は以下のようになります。

1.  `goodOSArchFile`関数は、ファイル名（例: `foo_android.go`や`android.go`）を受け取ります。
2.  まず、ファイル名から拡張子を除去します（例: `foo_android`、`android`）。
3.  次に、変更が加えられた部分で、拡張子を除去したファイル名にアンダースコアが含まれているかを確認します。
    *   もしアンダースコアが含まれていない場合（例: `android`）、このファイルはOS/ARCH固有の自動タグ付けの対象外とみなされ、常に`true`（ビルド対象）を返します。これにより、`android.go`というファイルが、たとえ`GOOS=android`であっても、自動的にAndroid固有のファイルとして扱われることはなくなります。
    *   もしアンダースコアが含まれている場合（例: `foo_android`）、従来のロジック（`strings.Split(name, "_")`で分割し、最後の要素が`GOOS`や`GOARCH`にマッチするかどうかをチェックする）が適用されます。この場合、`foo_android.go`は`GOOS=android`の場合にのみビルド対象となります。

この変更により、Go 1.4以降では、ファイル名による暗黙的なビルドタグの適用は、`foo_os.go`や`bar_arch.go`のように、OS/ARCH名の前にアンダースコアで区切られたプレフィックスがある場合に限定されるようになりました。これにより、`android.go`のような一般的な名前のファイルが、意図せず特定のプラットフォームに紐付けられることがなくなります。

テストケースも追加され、この新しい挙動が正しく機能することを確認しています。特に、`android.go`や`plan9.go`のようなファイルが、アンダースコアがないために常にビルド対象となることがテストされています。

## コアとなるコードの解説

`src/go/build/build.go`の変更は、`goodOSArchFile`関数内でファイル名から拡張子を除去した後の処理に新しい条件分岐を追加しています。

```go
if !strings.ContainsRune(name, '_') {
	return true
}
```

このコードは、`name`（拡張子を除去したファイル名、例: `android`、`foo_linux`）にアンダースコア（`_`）が含まれていないかどうかをチェックします。

*   **`!strings.ContainsRune(name, '_')` が `true` の場合**:
    これは、ファイル名にアンダースコアが含まれていないことを意味します（例: `android.go`が`android`になる場合）。この場合、関数は即座に`true`を返します。これは、このようなファイルがOS/ARCH固有の自動タグ付けの対象外となり、常にビルド対象として含まれることを保証します。コミットメッセージにある「The easiest fix: files without underscores are always included.」という部分がこれに該当します。これにより、`android.go`のようなファイルが、たとえ`GOOS=android`であっても、自動的にAndroid固有のファイルとして扱われることはなくなります。

*   **`!strings.ContainsRune(name, '_')` が `false` の場合**:
    これは、ファイル名にアンダースコアが含まれていることを意味します（例: `foo_android.go`が`foo_android`になる場合）。この場合、新しい条件分岐はスキップされ、従来のロジックである`l := strings.Split(name, "_")`以降の処理が実行されます。この従来のロジックは、ファイル名をアンダースコアで分割し、最後の要素が`GOOS`や`GOARCH`にマッチするかどうかをチェックすることで、OS/ARCH固有の自動タグ付けを行います。

この変更により、Goのビルドシステムは、ファイル名による暗黙的なビルドタグの適用をより厳密に行うようになり、ドキュメントの記述と実際の挙動が一致するようになりました。

```go

{ctxtAndroid, "plan9.go", "", true},
{ctxtAndroid, "arm.s", "", true},
{ctxtAndroid, "amd64.s", "", true},
```

これらのテストケースは、`GOOS=android`のコンテキストにおいて、`android.go`、`plan9.go`、`arm.s`、`amd64.s`といったファイルが、ファイル名にアンダースコアを含まないため、常にビルド対象として含まれる（`true`）ことを確認しています。これは、これらのファイルがOS/ARCH固有の自動タグ付けの対象外となり、一般的なファイルとして扱われるという新しいロジックの検証です。

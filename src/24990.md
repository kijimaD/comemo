# [インデックス 24990] ファイルの概要

このコミットは、GoランタイムにおけるWindows AMD64アーキテクチャでのシステムコール（特に`usleep2`関数）の挙動に関するバグ修正です。Windows AMD64の呼び出し規約では、システムコールを含むすべての関数呼び出しにおいて、最初の4つのパラメータのためにスタック上に領域を確保する必要があります。このコミットは、`usleep2`関数内でこの規約が守られていなかった点を修正し、スタック上に適切なパラメータ領域を確保するように変更しています。

## コミット

runtime: provide room for first 4 syscall parameters in windows usleep2

## 変更の背景

この変更の背景には、Windows AMD64アーキテクチャにおけるシステムコール呼び出し規約の誤解と、それに起因する潜在的なバグがありました。Windows AMD64の呼び出し規約（Microsoft x64 calling convention）では、関数を呼び出す側（caller）は、たとえレジスタでパラメータが渡される場合であっても、最初の4つのパラメータのためにスタック上に32バイトの「シャドウスペース（shadow space）」と呼ばれる領域を確保する責任があります。これは、呼び出された関数（callee）がこれらのレジスタパラメータをスタックに保存する必要がある場合に備えるためです。

Goランタイムは通常、この規約に従ってシステムコールを呼び出していますが、`usleep2`関数（Goランタイム内部で時間待機のためにWindows APIを呼び出す際に使用される可能性のある関数）においては、このシャドウスペースの確保が漏れていました。

以前の議論（`https://coderereview.appspot.com/7563043#msg3`で参照されている）では、Russ Cox (rsc) が「システムコールは通常の関数呼び出しではないため、AMD64でのスタックアライメントや最初の4つのパラメータのための領域は不要である」と述べていたようです。しかし、このコミットの作者であるAlex Brainmanは、この認識が誤りであることを指摘しています。スタックアライメントの問題は既に修正されていましたが、パラメータのためのスタック領域の確保が残された問題として認識され、このコミットで修正されることになりました。この修正は、Issue #12444 に対応するものです。

この問題が放置されると、`usleep2`が呼び出すWindows API関数が、シャドウスペースが存在しないことを前提としないため、スタックを破壊したり、予期せぬ動作を引き起こしたりする可能性がありました。

## 前提知識の解説

### 1. Windows AMD64 呼び出し規約 (Microsoft x64 Calling Convention)

Windows AMD64 (x86-64) 環境では、関数呼び出しの際にパラメータがどのように渡され、スタックがどのように管理されるかについて厳格な規約が存在します。

*   **レジスタによるパラメータ渡し**: 最初の4つの整数またはポインタ引数は、`RCX`, `RDX`, `R8`, `R9` レジスタを介して渡されます。浮動小数点引数は `XMM0` から `XMM3` レジスタを使用します。
*   **スタックによるパラメータ渡し**: 5番目以降の引数は、スタックに右から左の順でプッシュされます。
*   **シャドウスペース (Shadow Space)**: 最も重要な点の一つが、呼び出し側（caller）が、関数呼び出しを行う直前にスタック上に32バイト（4つのレジスタ引数それぞれに8バイト）の領域を確保する責任があることです。この領域は、呼び出された関数（callee）が、必要に応じてレジスタで渡された引数を保存するために使用できます。たとえ4つ未満の引数しか渡されない場合でも、この32バイトのシャドウスペースは確保されなければなりません。
*   **スタックアライメント**: スタックポインタ (`RSP`) は、`CALL` 命令の直前には16バイト境界にアライメントされている必要があります。`CALL` 命令自体が8バイトをスタックにプッシュするため、関数エントリ時には `RSP` は8バイト境界にアライメントされます。このため、関数内でスタックを使用する際には、さらに調整が必要になる場合があります。

### 2. GoランタイムとWindowsシステムコール

GoプログラムがWindows上でシステムコールを行う際、直接カーネルのシステムコール番号を呼び出すのではなく、通常はWindows API関数（DLLによってエクスポートされる関数）を呼び出します。

*   **`syscall`パッケージ**: Goの`syscall`パッケージは、低レベルのOSプリミティブへのインターフェースを提供します。
*   **`libcall`構造体**: Goランタイムは、システムコールを行う際に`libcall`という内部構造体を使用します。これには、ターゲットとなるWindows API関数のアドレス、引数の数、引数の配列へのポインタなどが含まれます。
*   **`asmstdcall`**: `cgocall`などの関数を通じて、最終的に`asmstdcall`というアセンブリ関数が呼び出されます。この関数が、`libcall`構造体から引数を取り出し、Windows x64呼び出し規約に従ってレジスタとスタックを準備し、実際のWindows API関数を呼び出します。

### 3. `usleep2`関数

`usleep2`は、Goランタイム内部で使用される関数であり、直接的なWindows APIの名前ではありません。その名前から、マイクロ秒単位でのスリープ（時間待機）機能を提供するために、内部的にWindowsの`NtDelayExecution`や`Sleep`といったAPI関数を呼び出していると推測されます。これらのAPI関数は、指定された時間だけ現在のスレッドの実行を一時停止させます。

このコミットの文脈では、`usleep2`が内部で呼び出すWindows API関数が、呼び出し規約に従ってシャドウスペースが確保されていることを期待していたにもかかわらず、Goランタイム側の`usleep2`の実装がそれを怠っていたことが問題でした。

## 技術的詳細

このコミットの技術的詳細は、Windows AMD64の呼び出し規約に準拠するために、`src/runtime/sys_windows_amd64.s`内の`runtime·usleep2`アセンブリ関数のスタックフレームを調整することにあります。

元の実装では、`runtime·usleep2`はスタック上に16バイトの領域（`$16`）を確保していました。これは、スタックアライメントの修正に対応するためのものでしたが、シャドウスペースの要件を満たしていませんでした。

Windows AMD64の呼び出し規約では、最初の4つのパラメータのために32バイトのシャドウスペースが必要です。さらに、`CALL`命令がリターンアドレスをスタックにプッシュするために8バイトを使用し、`runtime·usleep2`自身がローカル変数や保存されたレジスタのためにスタックを使用する可能性も考慮する必要があります。

このコミットでは、`TEXT runtime·usleep2(SB),NOSPLIT,$48` と変更されています。これは、`runtime·usleep2`関数がスタック上に合計48バイトの領域を確保することを意味します。

内訳としては、以下のようになります。
*   **32バイト**: Windows AMD64呼び出し規約で要求されるシャドウスペース。
*   **8バイト**: `CALL`命令によってプッシュされるリターンアドレスを保存するための領域。
*   **8バイト**: `MOVQ SP, AX` で保存された元のスタックポインタ (`AX`) を一時的に保存するための領域。

合計で48バイトのスタックフレームを確保することで、`runtime·usleep2`が内部で`runtime·_NtWaitForSingleObject`（おそらく`NtDelayExecution`のようなWindows APIをラップしたもの）を呼び出す際に、呼び出し規約で要求される32バイトのシャドウスペースが適切に提供されるようになります。

また、スタックポインタの保存と復元も変更されています。
*   元のスタックポインタを保存する位置が `8(SP)` から `40(SP)` に変更。
*   元のスタックポインタを復元する位置も `8(SP)` から `40(SP)` に変更。

これは、スタックフレームのサイズが16バイトから48バイトに拡張されたことに伴い、元のスタックポインタを保存するオフセットも調整されたためです。`40(SP)` は、新しい48バイトのスタックフレームの最下部から40バイト上（つまり、スタックフレームのほぼ最上部、リターンアドレスのすぐ上）に位置し、元のスタックポインタを安全に保存する場所となります。

さらに、`LEAQ 32(SP), R8` の変更は、`ptime`（おそらく時間値へのポインタ）を渡す際に、シャドウスペースの直後の領域を指すように調整しています。これにより、`runtime·_NtWaitForSingleObject`が期待するスタックレイアウトに合致するようになります。

## コアとなるコードの変更箇所

`src/runtime/sys_windows_amd64.s` ファイルの `runtime·usleep2` 関数内の変更です。

```diff
--- a/src/runtime/sys_windows_amd64.s
+++ b/src/runtime/sys_windows_amd64.s
@@ -428,19 +428,21 @@ ret:
  	RET
 
  // Runs on OS stack. duration (in 100ns units) is in BX.
-TEXT runtime·usleep2(SB),NOSPLIT,$16
+// The function leaves room for 4 syscall parameters
+// (as per windows amd64 calling convention).
+TEXT runtime·usleep2(SB),NOSPLIT,$48
  	MOVQ	SP, AX
  	ANDQ	$~15, SP	// alignment as per Windows requirement
-\tMOVQ	AX, 8(SP)
+\tMOVQ	AX, 40(SP)
  	// Want negative 100ns units.
  	NEGQ	BX
-\tMOVQ	SP, R8 // ptime
+\tLEAQ	32(SP), R8  // ptime
  	MOVQ	BX, (R8)
  	MOVQ	$-1, CX // handle
  	MOVQ	$0, DX // alertable
  	MOVQ	truntime·_NtWaitForSingleObject(SB), AX
  	CALL	AX
-\tMOVQ	8(SP), SP
+\tMOVQ	40(SP), SP
  	RET
 
  // func now() (sec int64, nsec int32)
```

## コアとなるコードの解説

1.  **`TEXT runtime·usleep2(SB),NOSPLIT,$16` から `TEXT runtime·usleep2(SB),NOSPLIT,$48` への変更**:
    *   これは`runtime·usleep2`関数の定義行です。`$16`は関数が自身のローカル変数や一時的な目的のためにスタック上に確保するバイト数を指定します。
    *   `$16`から`$48`への変更は、関数がスタック上に確保する領域を16バイトから48バイトに増やしたことを意味します。この追加の32バイトが、Windows AMD64呼び出し規約で要求される「シャドウスペース」を確保するために使用されます。これにより、`usleep2`が内部で呼び出すシステムコールが、レジスタで渡されるパラメータをスタックに保存する必要がある場合に備えることができます。

2.  **`MOVQ AX, 8(SP)` から `MOVQ AX, 40(SP)` への変更**:
    *   `MOVQ SP, AX` で現在のスタックポインタの値を`AX`レジスタに保存した後、その`AX`の値をスタック上の特定の位置に保存しています。これは、関数が終了する際に元のスタックポインタを復元するために必要です。
    *   スタックフレームのサイズが16バイトから48バイトに増えたため、元のスタックポインタを保存するオフセットも`8(SP)`から`40(SP)`に調整されました。これは、新しいスタックフレームのレイアウトに合わせて、安全な位置に値を保存するためです。

3.  **`MOVQ SP, R8 // ptime` から `LEAQ 32(SP), R8 // ptime` への変更**:
    *   この行は、`runtime·_NtWaitForSingleObject`関数に渡す`ptime`引数（おそらく時間値へのポインタ）を準備しています。
    *   元のコードでは、現在のスタックポインタ`SP`を直接`R8`にロードしていましたが、これはシャドウスペースが考慮されていないため、`ptime`が指すアドレスが不適切になる可能性がありました。
    *   `LEAQ 32(SP), R8` は、スタックポインタ`SP`から32バイト上のアドレス（つまり、確保されたシャドウスペースの直後のアドレス）を計算し、そのアドレスを`R8`レジスタにロードします。これにより、`ptime`がシャドウスペースの直後の有効なメモリ位置を指すようになり、`runtime·_NtWaitForSingleObject`が期待する引数のポインタとして正しく機能します。

4.  **`MOVQ 8(SP), SP` から `MOVQ 40(SP), SP` への変更**:
    *   これは関数の最後に、保存しておいた元のスタックポインタの値を`SP`レジスタに復元する行です。
    *   スタックフレームのサイズ変更に伴い、元のスタックポインタが保存されているオフセットも`8(SP)`から`40(SP)`に変わったため、復元する際も新しいオフセットを使用するように修正されました。

これらの変更により、`runtime·usleep2`関数はWindows AMD64の呼び出し規約に完全に準拠し、安定した動作が保証されるようになりました。

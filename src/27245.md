# [インデックス 27245] ファイルの概要

このコミットは、Go言語の`syscall`パッケージにおけるPlan 9固有の`StartProcess`関数が、ファイルディスクリプタ (FD) のクローズ競合によって失敗する問題を修正するものです。具体的には、親プロセスが子プロセスに渡す必要のないFDを列挙し、子プロセスがそれらをクローズするまでの間に、別のスレッドがFDをクローズし、そのFDが子プロセスとの通信パイプに再利用されることで発生する競合状態を回避するためのワークアラウンドが導入されています。

## 元コミット内容

`syscall: avoid failure in plan9 StartProcess from fd close race`

このコミットは、Plan 9環境における`syscall.StartProcess`関数が、ファイルディスクリプタのクローズ競合によって失敗するのを防ぐためのものです。親プロセスがクローズすべきファイルディスクリプタを列挙し、子プロセスがそれらをクローズするまでの間に、別のスレッドでファイルがクローズされる可能性があります。もしそのファイルディスクリプタが、子プロセスと親プロセスの間のステータスパイプを開く際に再利用された場合、子プロセスによってそのパイプが時期尚早にクローズされ、`forkExec`の同期が失われます。この問題は、ビルドのリンクステップがコンパイルステップの実行前に開始され、「file does not exist」というエラーメッセージが表示されるという形で、ビルダーテストの失敗として観測されていました。

この問題に対する単純なワークアラウンドとして、パイプをクローズしないようにチェックが追加されました。より包括的な解決策としては、以前提案された`https://golang.org/cl/57890043`のような、競合を避けるためのFDクローズコードの書き換えが考えられますが、この修正は当面の間、一部のビルダーの失敗を防ぐでしょう。

## 変更の背景

Go言語のプログラムが外部プロセスを起動する際、`syscall.StartProcess`のような関数が使用されます。特にPlan 9環境では、このプロセス起動メカニズムに特有の競合状態が存在していました。

問題の核心は、親プロセスが子プロセスに継承させたくないファイルディスクリプタを特定し、子プロセスが起動した直後にそれらをクローズするという一般的なパターンにありました。しかし、この「特定」と「クローズ」の間に時間差があり、その間に別のゴルーチン（スレッド）が既存のファイルディスクリプタをクローズし、その番号がシステムによって新しいファイル（この場合は親と子の間の通信用パイプ）に再割り当てされる可能性がありました。

もし、クローズされるべきFDのリストに含まれていたFD番号が、偶然にも親と子の間のステータスパイプのFD番号として再利用されてしまった場合、子プロセスは「クローズすべきFD」としてそのパイプをクローズしてしまいます。これにより、親と子の間の通信チャネルが破壊され、`forkExec`処理が期待通りに進行しなくなります。

この競合状態は、Goのビルダーテストで実際に観測されており、特にビルドのリンクフェーズがコンパイルフェーズの完了前に開始されるような状況で、「file does not exist」といったエラーが発生していました。これは、子プロセス（例えばリンカ）が親プロセス（ビルドシステム）との通信を失い、必要なファイルパスなどの情報を受け取れなくなるためと考えられます。

このコミットは、この特定の競合状態によって引き起こされるビルダーの失敗を防ぐための緊急的なワークアラウンドとして導入されました。

## 前提知識の解説

### Plan 9

Plan 9 from Bell Labsは、ベル研究所で開発された分散オペレーティングシステムです。Unixの設計思想をさらに推し進め、システム内のすべてのリソース（ファイル、デバイス、プロセス間通信など）をファイルシステムとして表現するという特徴を持っています。Go言語の設計には、Plan 9の思想が色濃く反映されており、特にGoの標準ライブラリの`syscall`パッケージには、Plan 9固有のシステムコールを扱うためのコードが含まれています。

### ファイルディスクリプタ (File Descriptor, FD)

ファイルディスクリプタは、Unix系オペレーティングシステム（およびPlan 9）において、プロセスが開いているファイルやソケット、パイプなどのI/Oリソースを識別するために使用される整数値です。プロセスがファイルを開くと、カーネルは一意のFDを割り当て、それ以降のI/O操作はそのFDを通じて行われます。FDは通常、0が標準入力 (stdin)、1が標準出力 (stdout)、2が標準エラー出力 (stderr) に割り当てられます。

### `syscall.StartProcess`

Go言語の`os`パッケージの`exec.Command`は、内部で`syscall.StartProcess`を呼び出して新しいプロセスを起動します。`syscall.StartProcess`は、指定された実行可能ファイル、引数、環境変数、およびファイルディスクリプタのリスト（子プロセスに継承させるもの）を受け取り、新しいプロセスを生成します。この関数は、低レベルのシステムコールを直接ラップしており、OS固有のプロセス起動メカニズムに依存します。

### `forkExec`モデル

`forkExec`は、Unix系システムで新しいプロセスを起動するための一般的なモデルです。
1.  **`fork`**: 親プロセスが自身のコピーである子プロセスを作成します。この時点では、子プロセスは親プロセスのメモリ空間、ファイルディスクリプタ、その他のリソースをほぼ完全に継承します。
2.  **ファイルディスクリプタの調整**: 子プロセスは、親から継承したFDのうち、不要なものをクローズし、必要なものを標準入力/出力/エラーにリダイレクトするなどの調整を行います。
3.  **`exec`**: 子プロセスは、新しいプログラムをロードして実行します。これにより、子プロセスのメモリ空間は新しいプログラムのコードとデータで上書きされ、実行が開始されます。

このコミットで問題となっているのは、ステップ2の「ファイルディスクリプタの調整」の段階で発生する競合状態です。

### ファイルディスクリプタのクローズ競合 (FD Close Race)

ファイルディスクリプタのクローズ競合とは、複数のスレッド（またはゴルーチン）が同時にファイルディスクリプタを操作しようとしたときに発生する問題です。今回のケースでは、以下のシナリオで発生します。

1.  親プロセスが子プロセスに渡すべきでないFDのリスト（`fdsToClose`）を作成します。
2.  親プロセスが`fork`して子プロセスを作成します。子プロセスは親のFDテーブルを継承します。
3.  子プロセスは`fdsToClose`リストに基づいて不要なFDをクローズしようとします。
4.  しかし、ステップ1と3の間に、親プロセスの別のスレッドが、`fdsToClose`リストに含まれるFDをクローズしてしまう可能性があります。
5.  OSは、クローズされたFD番号を新しいファイル（例えば、親と子の間の通信用パイプ）に再利用する可能性があります。
6.  子プロセスが`fdsToClose`リストを処理する際、以前は別のファイルに割り当てられていたFD番号が、現在は通信用パイプに割り当てられていることに気づかず、そのパイプをクローズしてしまいます。
7.  結果として、親と子の間の通信が途絶え、プロセス起動が失敗します。

## 技術的詳細

この問題は、Goの`syscall`パッケージ内のPlan 9固有の実装、具体的には`forkAndExecInChild`関数で発生していました。この関数は、新しいプロセスを起動する際に、子プロセスが継承すべきでないファイルディスクリプタをクローズする責任を負っています。

詳細な競合シナリオは以下の通りです。

1.  **`fdsToClose`の列挙**: 親プロセスは、子プロセスに継承させたくないファイルディスクリプタのリスト`fdsToClose`を構築します。このリストは、`StartProcess`が呼び出される時点でのアクティブなFDのスナップショットです。
2.  **`fork`とパイプの作成**: `forkAndExecInChild`関数内で、`fork`システムコールが実行され、子プロセスが作成されます。同時に、親と子の間でステータス情報をやり取りするためのパイプが作成され、そのパイプにもファイルディスクリプタが割り当てられます。
3.  **競合の発生**: ステップ1で`fdsToClose`が列挙されてから、ステップ4で子プロセスが実際にFDをクローズするまでの間に、親プロセスの別のゴルーチンが、`fdsToClose`に含まれるいずれかのFDをクローズする可能性があります。
4.  **FDの再利用**: OSは、クローズされたFD番号を再利用し、例えばステップ2で作成された親子のステータスパイプにその番号を割り当てることがあります。
5.  **子プロセスによる誤ったクローズ**: 子プロセスは、`fdsToClose`リストをイテレートし、リスト内の各FDをクローズしようとします。もし、リスト内のFD番号が、偶然にも親子のステータスパイプのFD番号と一致してしまった場合、子プロセスはそのパイプをクローズしてしまいます。
6.  **`forkExec`の同期喪失**: ステータスパイプが時期尚早にクローズされると、親プロセスと子プロセスの間の通信チャネルが破壊されます。これにより、親プロセスは子プロセスの起動ステータスを正しく取得できなくなり、`forkExec`処理全体が同期を失い、失敗します。
7.  **観測された症状**: この問題は、Goのビルダーテストで、ビルドのリンクステップがコンパイルステップの完了前に開始されるような状況で、「file does not exist」というエラーとして現れていました。これは、リンカが親プロセスから必要なファイルパスなどの情報を受け取れなかったためと考えられます。

このコミットは、この特定の競合状態を回避するために、子プロセスが`fdsToClose`リスト内のFDをクローズする際に、それが親子のステータスパイプのFDではないことを確認するチェックを追加しています。これにより、ステータスパイプが誤ってクローズされることを防ぎ、`forkExec`の同期喪失を防ぎます。

## コアとなるコードの解説

変更は`src/syscall/exec_plan9.go`ファイルの`forkAndExecInChild`関数内で行われています。この関数は、Plan 9環境で新しいプロセスをフォークし、実行する際の低レベルな処理を担っています。

変更前のコードでは、子プロセスが不要なファイルディスクリプタをクローズするために、`fdsToClose`リストを単純にイテレートし、各FDに対して`RawSyscall(SYS_CLOSE, uintptr(fdsToClose[i]), 0, 0)`を呼び出していました。

変更後のコードでは、このクローズ処理に条件が追加されました。

```go
		if fdsToClose[i] != pipe {
			RawSyscall(SYS_CLOSE, uintptr(fdsToClose[i]), 0, 0)
		}
```

ここで、`pipe`は親プロセスと子プロセスの間でステータス情報をやり取りするために使用されるパイプのファイルディスクリプタです。この条件`fdsToClose[i] != pipe`は、「現在クローズしようとしているファイルディスクリプタが、親子のステータスパイプのFDではない場合のみ、それをクローズする」という意味になります。

この変更により、たとえ`fdsToClose`リストに、別のスレッドによってクローズされ、その後ステータスパイプに再利用されたFD番号が含まれていたとしても、子プロセスはそのパイプを誤ってクローズすることがなくなります。これにより、前述のファイルディスクリプタのクローズ競合が回避され、`forkExec`の同期喪失によるプロセス起動の失敗が防がれます。

コミットメッセージにもあるように、これは「単純なワークアラウンド」であり、ファイルディスクリプタのクローズに関する一般的な競合状態を根本的に解決するものではありません。より包括的な解決策としては、`https://golang.org/cl/57890043`で提案されているような、FDクローズコード全体の設計見直しが必要とされています。しかし、この修正は、当面の間のビルダーテストの失敗を防ぐ上で効果的な対策となります。

ファイルディスクリプタは、Unix系オペレーティングシステム（およびPlan 9）において、プロセスが開いているファイルやソケット、パイプなどのI/Oリソースを識別するために使用される整数値です。プロセスがファイルを開くと、カーネルは一意のFDを割り当て、それ以降のI/O操作はそのFDを通じて行われます。FDは通常、0が標準入力 (stdin)、1が標準出力 (stdout)、2が標準エラー出力 (stderr) に割り当てられます。

### `syscall.StartProcess`

Go言語の`os`パッケージの`exec.Command`は、内部で`syscall.StartProcess`を呼び出して新しいプロセスを起動します。`syscall.StartProcess`は、指定された実行可能ファイル、引数、環境変数、およびファイルディスクリプタのリスト（子プロセスに継承させるもの）を受け取り、新しいプロセスを生成します。この関数は、低レベルのシステムコールを直接ラップしており、OS固有のプロセス起動メカニズムに依存します。

### `forkExec`モデル

`forkExec`は、Unix系システムで新しいプロセスを起動するための一般的なモデルです。
1.  **`fork`**: 親プロセスが自身のコピーである子プロセスを作成します。この時点では、子プロセスは親プロセスのメモリ空間、ファイルディスクリプタ、その他のリソースをほぼ完全に継承します。
2.  **ファイルディスクリプタの調整**: 子プロセスは、親から継承したFDのうち、不要なものをクローズし、必要なものを標準入力/出力/エラーにリダイレクトするなどの調整を行います。
3.  **`exec`**: 子プロセスは、新しいプログラムをロードして実行します。これにより、子プロセスのメモリ空間は新しいプログラムのコードとデータで上書きされ、実行が開始されます。

このコミットで問題となっているのは、ステップ2の「ファイルディスクリプタの調整」の段階で発生する競合状態です。

### ファイルディスクリプタのクローズ競合 (FD Close Race)

ファイルディスクリプタのクローズ競合とは、複数のスレッド（またはゴルーチン）が同時にファイルディスクリプタを操作しようとしたときに発生する問題です。今回のケースでは、以下のシナリオで発生します。

1.  親プロセスが子プロセスに渡すべきでないFDのリスト（`fdsToClose`）を作成します。
2.  親プロセスが`fork`して子プロセスを作成します。子プロセスは親のFDテーブルを継承します。
3.  子プロセスは`fdsToClose`リストに基づいて不要なFDをクローズしようとします。
4.  しかし、ステップ1と3の間に、親プロセスの別のスレッドが、`fdsToClose`リストに含まれるFDをクローズしてしまう可能性があります。
5.  OSは、クローズされたFD番号を新しいファイル（例えば、親と子の間の通信用パイプ）に再利用する可能性があります。
6.  子プロセスが`fdsToClose`リストを処理する際、以前は別のファイルに割り当てられていたFD番号が、現在は通信用パイプに割り当てられていることに気づかず、そのパイプをクローズしてしまいます。
7.  結果として、親と子の間の通信が途絶え、プロセス起動が失敗します。

## 技術的詳細

この問題は、Goの`syscall`パッケージ内のPlan 9固有の実装、具体的には`forkAndExecInChild`関数で発生していました。この関数は、新しいプロセスを起動する際に、子プロセスが継承すべきでないファイルディスクリプタをクローズする責任を負っています。

詳細な競合シナリオは以下の通りです。

1.  **`fdsToClose`の列挙**: 親プロセスは、子プロセスに継承させたくないファイルディスクリプタのリスト`fdsToClose`を構築します。このリストは、`StartProcess`が呼び出される時点でのアクティブなFDのスナップショットです。
2.  **`fork`とパイプの作成**: `forkAndExecInChild`関数内で、`fork`システムコールが実行され、子プロセスが作成されます。同時に、親と子の間でステータス情報をやり取りするためのパイプが作成され、そのパイプにもファイルディスクリプタが割り当てられます。
3.  **競合の発生**: ステップ1で`fdsToClose`が列挙されてから、ステップ4で子プロセスが実際にFDをクローズするまでの間に、親プロセスの別のゴルーチンが、`fdsToClose`に含まれるいずれかのFDをクローズする可能性があります。
4.  **FDの再利用**: OSは、クローズされたFD番号を再利用し、例えばステップ2で作成された親子のステータスパイプにその番号を割り当てることがあります。
5.  **子プロセスによる誤ったクローズ**: 子プロセスは、`fdsToClose`リストをイテレートし、リスト内の各FDをクローズしようとします。もし、リスト内のFD番号が、偶然にも親子のステータスパイプのFD番号と一致してしまった場合、子プロセスはそのパイプをクローズしてしまいます。
6.  **`forkExec`の同期喪失**: ステータスパイプが時期尚早にクローズされると、親プロセスと子プロセスの間の通信チャネルが破壊されます。これにより、親プロセスは子プロセスの起動ステータスを正しく取得できなくなり、`forkExec`処理全体が同期を失い、失敗します。
7.  **観測された症状**: この問題は、Goのビルダーテストで、ビルドのリンクステップがコンパイルステップの完了前に開始されるような状況で、「file does not exist」というエラーとして現れていました。これは、リンカが親プロセスから必要なファイルパスなどの情報を受け取れなかったためと考えられます。

このコミットは、この特定の競合状態を回避するために、子プロセスが`fdsToClose`リスト内のFDをクローズする際に、それが親子のステータスパイプのFDではないことを確認するチェックを追加しています。これにより、ステータスパイプが誤ってクローズされることを防ぎ、`forkExec`の同期喪失を防ぎます。

## コアとなるコードの解説

変更は`src/syscall/exec_plan9.go`ファイルの`forkAndExecInChild`関数内で行われています。この関数は、Plan 9環境で新しいプロセスをフォークし、実行する際の低レベルな処理を担っています。

変更前のコードでは、子プロセスが不要なファイルディスクリプタをクローズするために、`fdsToClose`リストを単純にイテレートし、各FDに対して`RawSyscall(SYS_CLOSE, uintptr(fdsToClose[i]), 0, 0)`を呼び出していました。

変更後のコードでは、このクローズ処理に条件が追加されました。

```go
		if fdsToClose[i] != pipe {
			RawSyscall(SYS_CLOSE, uintptr(fdsToClose[i]), 0, 0)
		}
```

ここで、`pipe`は親プロセスと子プロセスの間でステータス情報をやり取りするために使用されるパイプのファイルディスクリプタです。この条件`fdsToClose[i] != pipe`は、「現在クローズしようとしているファイルディスクリプタが、親子のステータスパイプのFDではない場合のみ、それをクローズする」という意味になります。

この変更により、たとえ`fdsToClose`リストに、別のスレッドによってクローズされ、その後ステータスパイプに再利用されたFD番号が含まれていたとしても、子プロセスはそのパイプを誤ってクローズすることがなくなります。これにより、前述のファイルディスクリプタのクローズ競合が回避され、`forkExec`の同期喪失によるプロセス起動の失敗が防がれます。

コミットメッセージにもあるように、これは「単純なワークアラウンド」であり、ファイルディスクリプタのクローズに関する一般的な競合状態を根本的に解決するものではありません。より包括的な解決策としては、`https://golang.org/cl/57890043`で提案されているような、FDクローズコード全体の設計見直しが必要とされています。しかし、この修正は、当面の間のビルダーテストの失敗を防ぐ上で効果的な対策となります。

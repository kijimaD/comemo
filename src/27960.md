# [インデックス 27960] ファイルの概要

このコミットは、Go言語のリンカ（`cmd/link`）内部で使用されるファイルシンボル（`Link.Filesyms`）のデータ構造を、従来の連結リストからスライス（動的配列）へと変更するものです。この変更により、リンカのコードが簡素化され、ファイルシンボルへのアクセス効率が向上します。特に、DWARFデバッグ情報や`pclntab`（PC-Lineテーブル）の生成ロジックに影響を与えています。

## 変更の背景

Goリンカの内部では、コンパイルされたソースファイルに関するシンボル情報（ファイル名など）を管理するために`Link`構造体の`Filesyms`フィールドが使用されていました。このフィールドは以前、`*LSym`型、つまり`LSym`構造体の連結リストの先頭を指すポインタとして実装されていました。

連結リストは要素の追加や削除が効率的である一方で、特定の要素へのランダムアクセスや、要素数を取得する際にはリスト全体を走査する必要があるため、非効率になる場合があります。特に、リンカがデバッグ情報（DWARF）やランタイムのPC-Lineテーブル（`pclntab`）を生成する際には、ファイルシンボルを頻繁に参照したり、その総数を把握したりする必要があります。

このコミットの背景には、以下の目的があったと考えられます。

1.  **コードの簡素化**: 連結リストの走査や管理ロジックを、より直感的でGoらしいスライスの操作に置き換えることで、コードの可読性と保守性を向上させる。
2.  **パフォーマンスの向上**: ファイルシンボルへのアクセスや、その総数の取得をO(1)の操作（スライスのインデックスアクセスや`len()`関数）にすることで、リンカの処理速度を改善する。特に、ファイル数が多い大規模なプロジェクトにおいて効果が期待されます。
3.  **`Nhistfile`の廃止**: ファイルシンボルの数を別途`Nhistfile`というフィールドで管理する必要がなくなり、スライスの`len()`で代替できるため、冗長な情報の管理をなくす。

これらの理由から、`Link.Filesyms`を連結リストからスライスへと変更する決定がなされました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびリンカに関する基本的な知識が必要です。

*   **Goリンカ (`cmd/link`)**:
    Go言語のビルドツールチェーンの一部であり、コンパイルされたGoパッケージのオブジェクトファイル（`.a`ファイルなど）を結合し、最終的な実行可能ファイルや共有ライブラリを生成するプログラムです。シンボル解決、メモリレイアウトの決定、デバッグ情報の生成、ランタイムに必要なメタデータ（`pclntab`など）の構築といった重要な役割を担います。

*   **`LSym` (Linker Symbol)**:
    リンカが扱う「シンボル」を表す構造体です。関数、グローバル変数、型情報、そしてソースファイル名など、プログラムを構成する様々な要素が`LSym`として表現されます。各`LSym`は名前、型、値、サイズなどの属性を持ちます。

*   **`Link`構造体**:
    Goリンカの主要なコンテキスト構造体です。リンカの実行中に必要なグローバルな状態、設定、および様々なシンボルやデータ構造への参照を保持します。`Filesyms`はこの`Link`構造体の一部でした。

*   **`Filesyms`**:
    `Link`構造体内のフィールドで、リンク対象となるソースファイルに関する`LSym`を管理していました。具体的には、各ソースファイルのパスが`LSym`として表現され、これらが`Filesyms`を通じてリンカに認識されます。

*   **Goのスライス (Slice)**:
    Go言語に組み込まれている動的配列です。基盤となる配列への参照、長さ、容量の3つの要素で構成されます。スライスは連続したメモリ領域を指すため、インデックスによる要素へのアクセスが非常に高速（O(1)）です。`append`関数を使って要素を追加したり、`len()`関数で現在の要素数を取得したりできます。

*   **連結リスト (Linked List)**:
    各ノードがデータと次のノードへのポインタ（または参照）を持つデータ構造です。要素の追加や削除はポインタの付け替えだけで済むため効率的ですが、特定の要素にアクセスするにはリストの先頭から順にたどる必要があり、ランダムアクセスはO(N)の計算量がかかります。

*   **DWARF (Debugging With Attributed Record Formats)**:
    Unix系システムで広く使われているデバッグ情報フォーマットです。コンパイルされたバイナリに埋め込まれ、デバッガがソースコードの行番号、変数名、型情報、スタックフレームの構造などを理解し、ソースレベルでのデバッグを可能にします。Goリンカは実行可能ファイルを生成する際にDWARF情報を構築します。

*   **`pclntab` (PC-Line Table)**:
    Goランタイムが使用するプログラムカウンタ（PC）とソースコードの行番号のマッピング情報を含むテーブルです。スタックトレースの生成、プロファイリング、ガベージコレクションのスタック走査など、Goランタイムの多くの機能で利用されます。`pclntab`には、関数情報、ファイル名、行番号情報などが含まれます。

## 技術的詳細

このコミットの技術的な核心は、`Link`構造体の`Filesyms`フィールドの型を`*LSym`（連結リストの先頭ポインタ）から`[]*LSym`（`LSym`ポインタのスライス）に変更した点にあります。この変更は、リンカの複数のコンポーネントに波及的な影響を与えています。

1.  **`Link`構造体の変更 (`src/cmd/link/internal/ld/link.go`)**:
    *   `Filesyms *LSym` が `Filesyms []*LSym` に変更されました。これにより、ファイルシンボルは連続したメモリ領域に格納され、インデックスで直接アクセスできるようになります。
    *   `Nhistfile int32` フィールドが削除されました。このフィールドは以前、ファイルシンボルの総数を保持していましたが、スライス化された`Filesyms`では`len(Ctxt.Filesyms)`で簡単に取得できるため不要になりました。

2.  **DWARFデバッグ情報生成の変更 (`src/cmd/link/internal/ld/dwarf.go`)**:
    *   `writelines`関数内で、ファイルシンボルを処理するロジックが大幅に簡素化されました。以前は、連結リストを走査して一時的なスライス`files`にコピーし、そのスライスをイテレートするという二段階の処理が必要でした。
    *   変更後は、`for _, f := range Ctxt.Filesyms`というGoのスライスに対する標準的なイテレーション構文で直接ファイルシンボルにアクセスできるようになり、中間的なスライス作成が不要になりました。これにより、コードがより直接的で効率的になりました。

3.  **PC-Lineテーブル (`pclntab`) 生成の変更 (`src/cmd/link/internal/ld/pcln.go`)**:
    *   **`renumberfiles`関数**: この関数は、ファイルシンボルに一意の番号を割り当て、`pclntab`で使用できるように準備します。
        *   以前は、新しいファイルシンボル`f`を既存の連結リストの先頭に追加する形で`f.Next = ctxt.Filesyms; ctxt.Filesyms = f`としていました。ファイル番号`f.Value`は`ctxt.Nhistfile`をインクリメントして割り当てていました。
        *   変更後は、`ctxt.Filesyms = append(ctxt.Filesyms, f)`を使ってスライスの末尾にファイルシンボルを追加します。ファイル番号`f.Value`は`int64(len(ctxt.Filesyms))`として割り当てられます。これは、スライスに追加された後の要素数（つまり1ベースのインデックス）をファイル番号とするため、自然な連番が振られます。
    *   **`pclntab`関数**: `pclntab`のファイルテーブル部分を構築する際に、ファイルシンボルの総数として`Ctxt.Nhistfile`の代わりに`len(Ctxt.Filesyms)`を使用するようになりました。
        *   ファイル名のエントリを`ftab`に書き込む際、以前は連結リストを順方向に走査していましたが、スライス化されたことで、`for i := len(Ctxt.Filesyms) - 1; i >= 0; i--`という逆順のイテレーションに変更されました。これは、`renumberfiles`でファイル番号がスライスのインデックス順に割り当てられているため、`pclntab`のファイルテーブルが正しい順序で構築されるようにするためです。

4.  **シンボルテーブル (`symtab`) 生成の変更 (`src/cmd/link/internal/ld/symtab.go`)**:
    *   `symtab`関数内で、`runtime.pclntab`のファイルテーブルスライスのサイズを計算する際に、`Ctxt.Nhistfile`の代わりに`len(Ctxt.Filesyms)`を使用するようになりました。これにより、リンカがランタイムに提供するメタデータが、新しいデータ構造と整合性が取れるようになります。

全体として、この変更はGoリンカの内部データ管理を現代的なGoのイディオムに合わせ、より堅牢で効率的なものにしています。連結リスト特有のポインタ操作や、要素数を別途管理する手間が解消され、コードの保守性が向上しました。

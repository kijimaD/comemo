# [インデックス 21704] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）におけるクロージャ変数のキャプチャメカニズムを最適化するものです。具体的には、これまで参照渡し（by reference）でキャプチャされていた変数を、特定の条件下で値渡し（by value）でキャプチャするように変更することで、ヒープアロケーションを削減し、プログラムのパフォーマンスを向上させます。

## 元コミット内容

このコミットは、Goコンパイラ（`cmd/gc`）がクロージャ内で変数をキャプチャする方法を変更します。Go言語の仕様では、クロージャが外部スコープの変数を参照渡しでキャプチャすると規定されています。これは、変数のアドレスがクロージャに渡され、クロージャ内でのその変数への変更が外部スコープにも反映されることを意味します。しかし、この参照渡しは、変数がヒープにエスケープする原因となり、ガベージコレクションのオーバーヘッドやパフォーマンスの低下を引き起こす可能性があります。

このコミットの目的は、プログラムの可視的な振る舞いを変更することなく、可能な限り多くのクロージャ変数を値渡しでキャプチャするようにコンパイラを最適化することです。これにより、ヒープアロケーションを削減し、全体的なパフォーマンスを向上させます。

コミットメッセージには、典型的なGoのパターンが例として挙げられています。

```go
func (o *Obj) requestMany(urls []string) []Result {
        wg := new(sync.WaitGroup)
        wg.Add(len(urls))
        res := make([]Result, len(urls))
        for i := range urls {
                i := i // この 'i' はループごとに新しい変数として宣言される
                go func() {
                        res[i] = o.requestOne(urls[i])
                        wg.Done()
                }()
        }
        wg.Wait()
        return res
}
```

この例では、`o`、`wg`、`res`、そしてループ内で再宣言された`i`がクロージャによってキャプチャされます。従来のコンパイラでは、これらの変数はすべて参照渡しでキャプチャされ、結果としてヒープへのアロケーションが発生していました（例：`o`のような`PPARAM`が`PPARAMREF`に昇格し、ヒープに移動する）。しかし、これらの変数は、クロージャの外部からアドレスが取られたり、クロージャ内で再代入されたりしない限り、値渡しでキャプチャしてもプログラムの振る舞いは変わりません。

この変更は、以下のシンプルな戦略を実装しています。
「キャプチャされる変数が`addrtaken`（アドレスが取られている）でなく、かつ一度も代入されていない場合、その変数は値渡しでキャプチャされる（実質的に定数として扱われる）。」

この戦略は非常に効果的であることが判明し、標準ライブラリ内の全キャプチャの約80%が値キャプチャに変換されました。残りの20%は、主に`defer`文やエスケープしないクロージャ内で発生するものであり、これらは元々アロケーションを引き起こさないため、この最適化の影響を受けません。

ベンチマーク結果は、この変更がアロケーション数を大幅に削減したことを示しています。例えば、`BenchmarkEncodeDigitsSpeed1e6`ではアロケーションが30.40%削減され、`BenchmarkCreateGoroutinesCapture`では40.00%も削減されています。

## 変更の背景

Go言語の設計思想の一つに、ガベージコレクション（GC）の効率化と、ヒープアロケーションの削減があります。ヒープアロケーションは、GCの頻度と負荷を増加させ、プログラムの実行速度に悪影響を与える可能性があります。

Goのクロージャは、外部スコープの変数を「参照渡し」でキャプチャするという仕様があります。これは、クロージャが実行される際に、その変数の現在の値をコピーするのではなく、その変数がメモリ上に存在する場所（アドレス）を記憶することを意味します。この挙動は、クロージャが変数を変更し、その変更がクロージャの外部からも見えるようにする場合に必要です。しかし、多くのケースでは、クロージャがキャプチャした変数を変更せず、単にその値を読み取るだけです。このような場合でも参照渡しが行われると、コンパイラは変数がヒープにエスケープすると判断し、スタックではなくヒープに変数を配置することがあります。これにより、不要なヒープアロケーションが発生し、GCの負担が増大していました。

このコミットは、このような不要なヒープアロケーションを削減し、Goプログラムの実行効率を向上させることを目的としています。特に、並行処理で頻繁に利用される`go func() { ... }()`のようなパターンにおいて、クロージャがキャプチャする変数がヒープにエスケープするのを防ぐことで、パフォーマンスのボトルネックを解消しようとしています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラの概念を理解しておく必要があります。

1.  **クロージャ (Closures)**:
    クロージャは、それが定義された環境（レキシカルスコープ）の変数を「記憶」し、その変数にアクセスできる関数です。Goでは、クロージャが外部スコープの変数をキャプチャする際、デフォルトではその変数の「参照」をキャプチャします。これにより、クロージャが実行されるときに、その変数の最新の値にアクセスしたり、その値を変更したりすることができます。

2.  **参照渡し (Capture by Reference) と 値渡し (Capture by Value)**:
    *   **参照渡し**: 変数のメモリ上のアドレスをキャプチャします。クロージャがそのアドレスを通じて変数にアクセスするため、クロージャ内での変数の変更は、外部スコープにも影響します。変数がヒープに配置される可能性が高まります。
    *   **値渡し**: 変数の値をコピーしてキャプチャします。クロージャは変数のコピーに対して操作を行うため、クロージャ内での変更は外部スコープには影響しません。変数がスタックに配置される可能性が高まります。

3.  **エスケープ解析 (Escape Analysis)**:
    Goコンパイラの重要な最適化の一つです。コンパイラは、プログラムの実行中に変数がどこに割り当てられるべきか（スタックかヒープか）を決定するためにエスケープ解析を行います。
    *   **スタック (Stack)**: 関数呼び出しごとに割り当てられるメモリ領域で、高速にアクセスできます。関数が終了すると自動的に解放されます。
    *   **ヒープ (Heap)**: プログラム全体で共有されるメモリ領域で、動的に割り当てられます。ガベージコレクタによって管理され、スタックに比べてアクセスが遅く、GCのオーバーヘッドが発生します。
    変数が関数のスコープを「エスケープ」して、その関数が終了した後も参照され続ける可能性がある場合、コンパイラはその変数をヒープに割り当てます。クロージャが外部変数を参照渡しでキャプチャする場合、その変数はクロージャの生存期間中参照され続ける可能性があるため、ヒープにエスケープすると判断されることがよくあります。

4.  **`addrtaken` (アドレスが取られている)**:
    Goコンパイラ内部の概念で、変数のアドレスが明示的に`&`演算子によって取得されたかどうかを示すフラグです。変数のアドレスが取られている場合、その変数は参照渡しでしかキャプチャできません。

5.  **`assigned` (代入されている)**:
    Goコンパイラ内部の概念で、変数が宣言後に再代入されたかどうかを示すフラグです。変数が再代入されている場合、その変数は値渡しでキャプチャすると、クロージャの外部からの変更が反映されなくなるため、参照渡しでキャプチャする必要があります。

6.  **`decldepth` (宣言深度)**:
    Goコンパイラ内部の概念で、変数が宣言されたスコープの深さを示します。ループやラベルブロックに入るたびに増加します。このコミットでは、変数がクロージャによって初めてキャプチャされる前の直線的なコードにおける代入を無視するために使用されます。

これらの概念を理解することで、このコミットがGoコンパイラの内部でどのように動作し、パフォーマンスにどのような影響を与えるかを深く把握することができます。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの`cmd/gc`パッケージにおけるクロージャ変数のキャプチャ戦略の変更にあります。具体的には、`src/cmd/gc/closure.c`、`src/cmd/gc/esc.c`（エスケープ解析）、`src/cmd/gc/typecheck.c`（型チェック）、`src/cmd/gc/go.h`（データ構造の定義）などのファイルが変更されています。

変更の主なポイントは以下の通りです。

1.  **`Node`構造体の拡張**:
    `src/cmd/gc/go.h`において、コンパイラのAST（抽象構文木）ノードを表す`Node`構造体に、クロージャ変数のキャプチャに関する新しいフィールドが追加されています。
    *   `addrtaken`: 変数のアドレスが取られたかどうか。
    *   `assigned`: 変数が宣言後に代入されたかどうか。
    *   `captured`: 変数がクロージャによってキャプチャされたかどうか。
    *   `byval`: 変数が値渡しでキャプチャされるべきか（1の場合）参照渡しでキャプチャされるべきか（0の場合）。
    *   `decldepth`: 変数が宣言されたスコープの深さ。
    *   `outerexpr`: クロージャにコピーされる外部変数の式。

2.  **`capturevars`フェーズの導入**:
    `src/cmd/gc/lex.c`の`gcmain`関数（コンパイラのメインループ）に、新しいフェーズ「Phase 4: Decide how to capture variables and transform closure bodies accordingly.」が追加されました。このフェーズは、すべての型チェックが完了した後、インライン化やエスケープ解析の前に実行されます。
    このフェーズで呼び出される`capturevars`関数（`src/cmd/gc/closure.c`に実装）が、各クロージャによってキャプチャされる変数が値渡しでキャプチャされるべきか、参照渡しでキャプチャされるべきかを決定します。

3.  **値キャプチャの条件**:
    `capturevars`関数内で、以下の条件が満たされる場合に変数を値渡しでキャプチャすると決定されます。
    *   変数のアドレスが取られていない (`!v->closure->addrtaken`)。
    *   変数が宣言後に代入されていない (`!v->closure->assigned`)。
    *   変数のサイズが128バイト以下である (`v->type->width <= 128`)。
    この128バイトという制限は、大きな構造体を値渡しでコピーすることによるパフォーマンスオーバーヘッドを避けるためのヒューリスティックと考えられます。

4.  **`assigned`フラグの追跡**:
    `src/cmd/gc/typecheck.c`と`src/cmd/gc/range.c`において、変数が代入された際に`assigned`フラグをセットするロジックが追加・変更されています。特に、`checkassign`関数が変更され、代入が行われた変数の`assigned`フラグがセットされるようになりました。これにより、コンパイラは変数が不変であるかどうかを正確に追跡できます。

5.  **`decldepth`の利用**:
    `src/cmd/gc/typecheck.c`では、`decldepth`が導入され、ループやラベルブロックのスコープの深さを追跡します。クロージャが変数を初めてキャプチャする前の直線的なコードにおける代入は、`assigned`フラグの判断から除外されます。これは、`for i := range urls { i := i }`のようなパターンで、ループ変数が新しいスコープで再宣言される場合に、その変数が「代入されていない」と正しく判断されるようにするためです。

6.  **クロージャの内部表現の変更**:
    `src/cmd/gc/closure.c`では、`makeclosure`関数と`walkclosure`関数が変更され、値キャプチャされた変数と参照キャプチャされた変数を区別して、クロージャの内部構造（コンテキストオブジェクト）を構築するようになりました。値キャプチャされた変数は直接コンテキストオブジェクトにコピーされ、参照キャプチャされた変数はそのアドレスがコピーされます。

7.  **エスケープ解析への影響**:
    `src/cmd/gc/esc.c`のエスケープ解析ロジックも、`byval`フラグを考慮するように変更されています。値渡しでキャプチャされる変数は、ヒープにエスケープする必要がないため、エスケープ解析の結果が改善されます。

これらの変更により、コンパイラはより賢くクロージャ変数のキャプチャ方法を決定できるようになり、結果として不要なヒープアロケーションが削減され、Goプログラムの実行時パフォーマンスが向上します。

## コアとなるコードの解説

### `src/cmd/gc/closure.c` の `capturevars` 関数

このコミットの最も重要な部分であり、クロージャ変数を値渡しでキャプチャするか参照渡しでキャプチャするかを決定するロジックが含まれています。

```c
// capturevars is called in a separate phase after all typechecking is done.
// It decides whether each variable captured by a closure should be captured
// by value or by reference.
// We use value capturing for values <= 128 bytes that are never reassigned
// after declaration.
void
capturevars(Node *xfunc)
{
    Node *func, *v, *addr, *cv, *outer;
    NodeList *l, *body;
    char *p;
    vlong offset;
    int nvar, lno;

    lno = lineno;
    lineno = xfunc->lineno;

    nvar = 0;
    body = nil;
    offset = widthptr; // ポインタのサイズでオフセットを初期化
    func = xfunc->closure;
    func->enter = nil;
    for(l=func->cvars; l; l=l->next) {
        v = l->n;
        if(v->type == T) {
            // ... (変数が使用されなかった場合の処理)
            v->op = OXXX;
            continue;
        }
        nvar++;

        // 外部スコープの変数のアドレスをクロージャの外で型チェックし、エスケープ解析に含める
        dowidth(v->type);
        outer = v->outerexpr;
        v->outerexpr = N;
        
        // ここが値キャプチャの決定ロジック
        if(!v->closure->addrtaken && !v->closure->assigned && v->type->width <= 128)
            v->byval = 1; // 値渡しでキャプチャ
        else {
            outer = nod(OADDR, outer, N); // 参照渡しの場合、アドレスを取るノードを作成
            // インプレース呼び出しのクロージャの場合、ヒープへの移動を避ける
            outer->etype = func->etype; 
        }
        if(debug['m'] > 1)
            warnl(v->lineno, "%S capturing by %s: %S (addr=%d assign=%d width=%d)",
                (v->curfn && v->curfn->nname) ? v->curfn->nname->sym : S, v->byval ? "value" : "ref",
                v->sym, v->closure->addrtaken, v->closure->assigned, (int32)v->type->width);
        typecheck(&outer, Erv);
        func->enter = list(func->enter, outer);

        // クロージャ内で使用される変数のアドレスを保持する変数を宣言し、エントリプロローグで初期化
        addr = nod(ONAME, N, N);
        p = smprint("&%s", v->sym->name);
        addr->sym = lookup(p);
        addr->class = PAUTO;
        addr->addrtaken = 1; // このアドレスは取られる
        addr->type = ptrto(v->type);
        xfunc->dcl = list(xfunc->dcl, addr);
        v->heapaddr = addr; // クロージャ内の変数が参照するアドレス

        cv = nod(OCLOSUREVAR, N, N);
        if(v->byval) {
            cv->type = v->type; // 値渡しの場合、元の型
            offset = rnd(offset, v->type->align);
            cv->xoffset = offset; // コンテキスト構造体内のオフセット
            offset += v->type->width; // オフセットを進める
            body = list(body, nod(OAS, addr, nod(OADDR, cv, N))); // 値をコピー
        } else {
            v->closure->addrtaken = 1; // 参照渡しの場合、元の変数はアドレスが取られる
            cv->type = ptrto(v->type); // 参照渡しの場合、ポインタ型
            offset = rnd(offset, widthptr);
            cv->xoffset = offset; // コンテキスト構造体内のオフセット
            offset += widthptr; // オフセットを進める
            body = list(body, nod(OAS, addr, cv)); // アドレスをコピー
        }
    }
    typechecklist(body, Etop);
    walkstmtlist(body);
    xfunc->enter = body;
    xfunc->needctxt = nvar > 0;
    func->etype = 0;

    lineno = lno;
}
```

この関数は、クロージャがキャプチャする各変数`v`についてループ処理を行います。
*   `!v->closure->addrtaken && !v->closure->assigned && v->type->width <= 128`という条件が、変数を値渡しでキャプチャするかどうかの判断基準です。
    *   `!v->closure->addrtaken`: キャプチャされる変数のアドレスが、クロージャの外部で明示的に`&`演算子によって取られていないこと。
    *   `!v->closure->assigned`: キャプチャされる変数が、宣言後に一度も代入されていないこと。
    *   `v->type->width <= 128`: キャプチャされる変数のサイズが128バイト以下であること。これは、大きな値をコピーすることによるオーバーヘッドを避けるためのヒューリスティックです。
*   これらの条件が満たされる場合、`v->byval`フラグが`1`に設定され、変数は値渡しでキャプチャされます。
*   そうでない場合、変数は参照渡しでキャプチャされます。参照渡しの場合、元の変数のアドレスが取られることを示す`v->closure->addrtaken = 1;`が設定されます。
*   デバッグモードでは、どの変数がどのようにキャプチャされたか（値渡し/参照渡し）がログに出力されます。
*   最終的に、クロージャのコンテキスト構造体（`OCLOSUREVAR`）に、値渡しであれば変数の値が、参照渡しであれば変数のアドレスがコピーされるように、ASTが変換されます。

### `src/cmd/gc/typecheck.c` の `checkassign` 関数

この関数は、変数への代入が行われた際に、その変数の`assigned`フラグをセットする役割を担います。

```c
void
checkassign(Node *stmt, Node *n)
{
    Node *r, *l;

    if(n->defn != stmt) { // 代入が宣言ではない場合
        r = outervalue(n); // 最も外側の変数を取得
        for(l = n; l != r; l = l->left) {
            l->assigned = 1; // 現在のノードを代入済みとしてマーク
            if(l->closure)
                l->closure->assigned = 1; // クロージャ変数を代入済みとしてマーク
        }
        l->assigned = 1; // 最も外側の変数を代入済みとしてマーク
        if(l->closure)
            l->closure->assigned = 1; // クロージャ変数を代入済みとしてマーク
    }

    if(islvalue(n))
        return;
    // ... (その他のlvalueチェック)
}
```

この関数は、代入の左辺値（`n`）が実際に代入されたことを記録します。特に重要なのは、`l->assigned = 1;`と`if(l->closure) l->closure->assigned = 1;`の部分です。これにより、変数がクロージャによってキャプチャされている場合、そのクロージャ変数の`assigned`フラグもセットされます。このフラグは、前述の`capturevars`関数で、変数を値渡しでキャプチャできるかどうかの判断基準として使用されます。

これらの変更により、Goコンパイラはクロージャ変数の不変性をより正確に判断し、不要なヒープアロケーションを回避する最適化を適用できるようになりました。

## 元コミット内容

このコミットは、Goコンパイラ（`cmd/gc`）がクロージャ内で変数をキャプチャする方法を変更します。Go言語の仕様では、クロージャが外部スコープの変数を参照渡しでキャプチャすると規定されています。これは、変数のアドレスがクロージャに渡され、クロージャ内でのその変数への変更が外部スコープにも反映されることを意味します。しかし、この参照渡しは、変数がヒープにエスケープする原因となり、ガベージコレクションのオーバーヘッドやパフォーマンスの低下を引き起こす可能性があります。

このコミットの目的は、プログラムの可視的な振る舞いを変更することなく、可能な限り多くのクロージャ変数を値渡しでキャプチャするようにコンパイラを最適化することです。これにより、ヒープアロケーションを削減し、全体的なパフォーマンスを向上させます。

コミットメッセージには、典型的なGoのパターンが例として挙げられています。

```go
func (o *Obj) requestMany(urls []string) []Result {
        wg := new(sync.WaitGroup)
        wg.Add(len(urls))
        res := make([]Result, len(urls))
        for i := range urls {
                i := i // この 'i' はループごとに新しい変数として宣言される
                go func() {
                        res[i] = o.requestOne(urls[i])
                        wg.Done()
                }()
        }
        wg.Wait()
        return res
}
```

この例では、`o`、`wg`、`res`、そしてループ内で再宣言された`i`がクロージャによってキャプチャされます。従来のコンパイラでは、これらの変数はすべて参照渡しでキャプチャされ、結果としてヒープへのアロケーションが発生していました（例：`o`のような`PPARAM`が`PPARAMREF`に昇格し、ヒープに移動する）。しかし、これらの変数は、クロージャの外部からアドレスが取られたり、クロージャ内で再代入されたりしない限り、値渡しでキャプチャしてもプログラムの振る舞いは変わりません。

この変更は、以下のシンプルな戦略を実装しています。
「キャプチャされる変数が`addrtaken`（アドレスが取られている）でなく、かつ一度も代入されていない場合、その変数は値渡しでキャプチャされる（実質的に定数として扱われる）。」

この戦略は非常に効果的であることが判明し、標準ライブラリ内の全キャプチャの約80%が値キャプチャに変換されました。残りの20%は、主に`defer`文やエスケープしないクロージャ内で発生するものであり、これらは元々アロケーションを引き起こさないため、この最適化の影響を受けません。

ベンチマーク結果は、この変更がアロケーション数を大幅に削減したことを示しています。例えば、`BenchmarkEncodeDigitsSpeed1e6`ではアロケーションが30.40%削減され、`BenchmarkCreateGoroutinesCapture`では40.00%も削減されています。

## 変更の背景

Go言語の設計思想の一つに、ガベージコレクション（GC）の効率化と、ヒープアロケーションの削減があります。ヒープアロケーションは、GCの頻度と負荷を増加させ、プログラムの実行速度に悪影響を与える可能性があります。

Goのクロージャは、外部スコープの変数を「参照渡し」でキャプチャするという仕様があります。これは、クロージャが実行される際に、その変数の現在の値をコピーするのではなく、その変数がメモリ上に存在する場所（アドレス）を記憶することを意味します。この挙動は、クロージャが変数を変更し、その変更がクロージャの外部からも見えるようにする場合に必要です。しかし、多くのケースでは、クロージャがキャプチャした変数を変更せず、単にその値を読み取るだけです。このような場合でも参照渡しが行われると、コンパイラは変数がヒープにエスケープすると判断し、スタックではなくヒープに変数を配置することがあります。これにより、不要なヒープアロケーションが発生し、GCの負担が増大していました。

このコミットは、このような不要なヒープアロケーションを削減し、Goプログラムの実行効率を向上させることを目的としています。特に、並行処理で頻繁に利用される`go func() { ... }()`のようなパターンにおいて、クロージャがキャプチャする変数がヒープにエスケープするのを防ぐことで、パフォーマンスのボトルネックを解消しようとしています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラの概念を理解しておく必要があります。

1.  **クロージャ (Closures)**:
    クロージャは、それが定義された環境（レキシカルスコープ）の変数を「記憶」し、その変数にアクセスできる関数です。Goでは、クロージャが外部スコープの変数をキャプチャする際、デフォルトではその変数の「参照」をキャプチャします。これにより、クロージャが実行されるときに、その変数の最新の値にアクセスしたり、その値を変更したりすることができます。

2.  **参照渡し (Capture by Reference) と 値渡し (Capture by Value)**:
    *   **参照渡し**: 変数のメモリ上のアドレスをキャプチャします。クロージャがそのアドレスを通じて変数にアクセスするため、クロージャ内での変数の変更は、外部スコープにも影響します。変数がヒープに配置される可能性が高まります。
    *   **値渡し**: 変数の値をコピーしてキャプチャします。クロージャは変数のコピーに対して操作を行うため、クロージャ内での変更は外部スコープには影響しません。変数がスタックに配置される可能性が高まります。

3.  **エスケープ解析 (Escape Analysis)**:
    Goコンパイラの重要な最適化の一つです。コンパイラは、プログラムの実行中に変数がどこに割り当てられるべきか（スタックかヒープか）を決定するためにエスケープ解析を行います。
    *   **スタック (Stack)**: 関数呼び出しごとに割り当てられるメモリ領域で、高速にアクセスできます。関数が終了すると自動的に解放されます。
    *   **ヒープ (Heap)**: プログラム全体で共有されるメモリ領域で、動的に割り当てられます。ガベージコレクタによって管理され、スタックに比べてアクセスが遅く、GCのオーバーヘッドが発生します。
    変数が関数のスコープを「エスケープ」して、その関数が終了した後も参照され続ける可能性がある場合、コンパイラはその変数をヒープに割り当てます。クロージャが外部変数を参照渡しでキャプチャする場合、その変数はクロージャの生存期間中参照され続ける可能性があるため、ヒープにエスケープすると判断されることがよくあります。

4.  **`addrtaken` (アドレスが取られている)**:
    Goコンパイラ内部の概念で、変数のアドレスが明示的に`&`演算子によって取得されたかどうかを示すフラグです。変数のアドレスが取られている場合、その変数は参照渡しでしかキャプチャできません。

5.  **`assigned` (代入されている)**:
    Goコンパイラ内部の概念で、変数が宣言後に再代入されたかどうかを示すフラグです。変数が再代入されている場合、その変数は値渡しでキャプチャすると、クロージャの外部からの変更が反映されなくなるため、参照渡しでキャプチャする必要があります。

6.  **`decldepth` (宣言深度)**:
    Goコンパイラ内部の概念で、変数が宣言されたスコープの深さを示します。ループやラベルブロックに入るたびに増加します。このコミットでは、変数がクロージャによって初めてキャプチャされる前の直線的なコードにおける代入を無視するために使用されます。

これらの概念を理解することで、このコミットがGoコンパイラの内部でどのように動作し、パフォーマンスにどのような影響を与えるかを深く把握することができます。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの`cmd/gc`パッケージにおけるクロージャ変数のキャプチャ戦略の変更にあります。具体的には、`src/cmd/gc/closure.c`、`src/cmd/gc/esc.c`（エスケープ解析）、`src/cmd/gc/typecheck.c`（型チェック）、`src/cmd/gc/go.h`（データ構造の定義）などのファイルが変更されています。

変更の主なポイントは以下の通りです。

1.  **`Node`構造体の拡張**:
    `src/cmd/gc/go.h`において、コンパイラのAST（抽象構文木）ノードを表す`Node`構造体に、クロージャ変数のキャプチャに関する新しいフィールドが追加されています。
    *   `addrtaken`: 変数のアドレスが取られたかどうか。
    *   `assigned`: 変数が宣言後に代入されたかどうか。
    *   `captured`: 変数がクロージャによってキャプチャされたかどうか。
    *   `byval`: 変数が値渡しでキャプチャされるべきか（1の場合）参照渡しでキャプチャされるべきか（0の場合）。
    *   `decldepth`: 変数が宣言されたスコープの深さ。
    *   `outerexpr`: クロージャにコピーされる外部変数の式。

2.  **`capturevars`フェーズの導入**:
    `src/cmd/gc/lex.c`の`gcmain`関数（コンパイラのメインループ）に、新しいフェーズ「Phase 4: Decide how to capture variables and transform closure bodies accordingly.」が追加されました。このフェーズは、すべての型チェックが完了した後、インライン化やエスケープ解析の前に実行されます。
    このフェーズで呼び出される`capturevars`関数（`src/cmd/gc/closure.c`に実装）が、各クロージャによってキャプチャされる変数が値渡しでキャプチャされるべきか、参照渡しでキャプチャされるべきかを決定します。

3.  **値キャプチャの条件**:
    `capturevars`関数内で、以下の条件が満たされる場合に変数を値渡しでキャプチャすると決定されます。
    *   変数のアドレスが取られていない (`!v->closure->addrtaken`)。
    *   変数が宣言後に代入されていない (`!v->closure->assigned`)。
    *   変数のサイズが128バイト以下である (`v->type->width <= 128`)。
    この128バイトという制限は、大きな構造体を値渡しでコピーすることによるパフォーマンスオーバーヘッドを避けるためのヒューリスティックと考えられます。

4.  **`assigned`フラグの追跡**:
    `src/cmd/gc/typecheck.c`と`src/cmd/gc/range.c`において、変数が代入された際に`assigned`フラグをセットするロジックが追加・変更されています。特に、`checkassign`関数が変更され、代入が行われた変数の`assigned`フラグがセットされるようになりました。これにより、コンパイラは変数が不変であるかどうかを正確に追跡できます。

5.  **`decldepth`の利用**:
    `src/cmd/gc/typecheck.c`では、`decldepth`が導入され、ループやラベルブロックのスコープの深さを追跡します。クロージャが変数を初めてキャプチャする前の直線的なコードにおける代入は、`assigned`フラグの判断から除外されます。これは、`for i := range urls { i := i }`のようなパターンで、ループ変数が新しいスコープで再宣言される場合に、その変数が「代入されていない」と正しく判断されるようにするためです。

6.  **クロージャの内部表現の変更**:
    `src/cmd/gc/closure.c`では、`makeclosure`関数と`walkclosure`関数が変更され、値キャプチャされた変数と参照キャプチャされた変数を区別して、クロージャの内部構造（コンテキストオブジェクト）を構築するようになりました。値キャプチャされた変数は直接コンテキストオブジェクトにコピーされ、参照キャプチャされた変数はそのアドレスがコピーされます。

7.  **エスケープ解析への影響**:
    `src/cmd/gc/esc.c`のエスケープ解析ロジックも、`byval`フラグを考慮するように変更されています。値渡しでキャプチャされる変数は、ヒープにエスケープする必要がないため、エスケープ解析の結果が改善されます。

これらの変更により、コンパイラはより賢くクロージャ変数のキャプチャ方法を決定できるようになり、結果として不要なヒープアロケーションが削減され、Goプログラムの実行時パフォーマンスが向上します。

## コアとなるコードの解説

### `src/cmd/gc/closure.c` の `capturevars` 関数

このコミットの最も重要な部分であり、クロージャ変数を値渡しでキャプチャするか参照渡しでキャプチャするかを決定するロジックが含まれています。

```c
// capturevars is called in a separate phase after all typechecking is done.
// It decides whether each variable captured by a closure should be captured
// by value or by reference.
// We use value capturing for values <= 128 bytes that are never reassigned
// after declaration.
void
capturevars(Node *xfunc)
{
    Node *func, *v, *addr, *cv, *outer;
    NodeList *l, *body;
    char *p;
    vlong offset;
    int nvar, lno;

    lno = lineno;
    lineno = xfunc->lineno;

    nvar = 0;
    body = nil;
    offset = widthptr; // ポインタのサイズでオフセットを初期化
    func = xfunc->closure;
    func->enter = nil;
    for(l=func->cvars; l; l=l->next) {
        v = l->n;
        if(v->type == T) {
            // ... (変数が使用されなかった場合の処理)
            v->op = OXXX;
            continue;
        }
        nvar++;

        // 外部スコープの変数のアドレスをクロージャの外で型チェックし、エスケープ解析に含める
        dowidth(v->type);
        outer = v->outerexpr;
        v->outerexpr = N;
        
        // ここが値キャプチャの決定ロジック
        if(!v->closure->addrtaken && !v->closure->assigned && v->type->width <= 128)
            v->byval = 1; // 値渡しでキャプチャ
        else {
            outer = nod(OADDR, outer, N); // 参照渡しの場合、アドレスを取るノードを作成
            // インプレース呼び出しのクロージャの場合、ヒープへの移動を避ける
            outer->etype = func->etype; 
        }
        if(debug['m'] > 1)
            warnl(v->lineno, "%S capturing by %s: %S (addr=%d assign=%d width=%d)",
                (v->curfn && v->curfn->nname) ? v->curfn->nname->sym : S, v->byval ? "value" : "ref",
                v->sym, v->closure->addrtaken, v->closure->assigned, (int32)v->type->width);
        typecheck(&outer, Erv);
        func->enter = list(func->enter, outer);

        // クロージャ内で使用される変数のアドレスを保持する変数を宣言し、エントリプロローグで初期化
        addr = nod(ONAME, N, N);
        p = smprint("&%s", v->sym->name);
        addr->sym = lookup(p);
        addr->class = PAUTO;
        addr->addrtaken = 1; // このアドレスは取られる
        addr->type = ptrto(v->type);
        xfunc->dcl = list(xfunc->dcl, addr);
        v->heapaddr = addr; // クロージャ内の変数が参照するアドレス

        cv = nod(OCLOSUREVAR, N, N);
        if(v->byval) {
            cv->type = v->type; // 値渡しの場合、元の型
            offset = rnd(offset, v->type->align);
            cv->xoffset = offset; // コンテキスト構造体内のオフセット
            offset += v->type->width; // オフセットを進める
            body = list(body, nod(OAS, addr, nod(OADDR, cv, N))); // 値をコピー
        } else {
            v->closure->addrtaken = 1; // 参照渡しの場合、元の変数はアドレスが取られる
            cv->type = ptrto(v->type); // 参照渡しの場合、ポインタ型
            offset = rnd(offset, widthptr);
            cv->xoffset = offset; // コンテキスト構造体内のオフセット
            offset += widthptr; // オフセットを進める
            body = list(body, nod(OAS, addr, cv)); // アドレスをコピー
        }
    }
    typechecklist(body, Etop);
    walkstmtlist(body);
    xfunc->enter = body;
    xfunc->needctxt = nvar > 0;
    func->etype = 0;

    lineno = lno;
}
```

この関数は、クロージャがキャプチャする各変数`v`についてループ処理を行います。
*   `!v->closure->addrtaken && !v->closure->assigned && v->type->width <= 128`という条件が、変数を値渡しでキャプチャするかどうかの判断基準です。
    *   `!v->closure->addrtaken`: キャプチャされる変数のアドレスが、クロージャの外部で明示的に`&`演算子によって取られていないこと。
    *   `!v->closure->assigned`: キャプチャされる変数が、宣言後に一度も代入されていないこと。
    *   `v->type->width <= 128`: キャプチャされる変数のサイズが128バイト以下であること。これは、大きな値をコピーすることによるオーバーヘッドを避けるためのヒューリスティックです。
*   これらの条件が満たされる場合、`v->byval`フラグが`1`に設定され、変数は値渡しでキャプチャされます。
*   そうでない場合、変数は参照渡しでキャプチャされます。参照渡しの場合、元の変数のアドレスが取られることを示す`v->closure->addrtaken = 1;`が設定されます。
*   デバッグモードでは、どの変数がどのようにキャプチャされたか（値渡し/参照渡し）がログに出力されます。
*   最終的に、クロージャのコンテキスト構造体（`OCLOSUREVAR`）に、値渡しであれば変数の値が、参照渡しであれば変数のアドレスがコピーされるように、ASTが変換されます。

### `src/cmd/gc/typecheck.c` の `checkassign` 関数

この関数は、変数への代入が行われた際に、その変数の`assigned`フラグをセットする役割を担います。

```c
void
checkassign(Node *stmt, Node *n)
{
    Node *r, *l;

    if(n->defn != stmt) { // 代入が宣言ではない場合
        r = outervalue(n); // 最も外側の変数を取得
        for(l = n; l != r; l = l->left) {
            l->assigned = 1; // 現在のノードを代入済みとしてマーク
            if(l->closure)
                l->closure->assigned = 1; // クロージャ変数を代入済みとしてマーク
        }
        l->assigned = 1; // 最も外側の変数を代入済みとしてマーク
        if(l->closure)
            l->closure->assigned = 1; // クロージャ変数を代入済みとしてマーク
    }

    if(islvalue(n))
        return;
    // ... (その他のlvalueチェック)
}
```

この関数は、代入の左辺値（`n`）が実際に代入されたことを記録します。特に重要なのは、`l->assigned = 1;`と`if(l->closure) l->closure->assigned = 1;`の部分です。これにより、変数がクロージャによってキャプチャされている場合、そのクロージャ変数の`assigned`フラグもセットされます。このフラグは、前述の`capturevars`関数で、変数を値渡しでキャプチャできるかどうかの判断基準として使用されます。

これらの変更により、Goコンパイラはクロージャ変数の不変性をより正確に判断し、不要なヒープアロケーションを回避する最適化を適用できるようになりました。

# [インデックス 20863] ファイルの概要

このコミットは、Go言語の`os/exec`パッケージのテストコードにおいて、Plan 9オペレーティングシステム上での期待されるファイルディスクリプタの数に関するバグを修正します。具体的には、Goランタイムが時刻取得のために`/dev/bintime`ではなく`nsec`システムコールを使用するように変更されたことに伴い、不要になったファイルディスクリプタのカウントロジックを削除しています。

## 変更の背景

この変更の背景には、GoランタイムがPlan 9オペレーティングシステム上で時刻を扱う方法の変更があります。以前のGoランタイム（特に32ビットPlan 9アーキテクチャの場合）では、システム時刻を取得するために`/dev/bintime`というデバイスファイルをオープンしたままにしておく必要がありました。そのため、`os/exec`パッケージのテストコード内にある`basefds`関数は、プロセス開始時に期待されるファイルディスクリプタの数を計算する際に、この`/dev/bintime`のために追加のファイルディスクリプタを考慮していました。

しかし、コミットメッセージに記載されているように、CL 104570043および112720043（これらのCLはGoランタイムの内部的な変更であり、直接的な関連性は薄いものの、このコミットの背景にある時間処理の変更を示唆しています）以降、Goランタイムは時刻取得に`/dev/bintime`ではなく`nsec`システムコールを使用するようになりました。これにより、`/dev/bintime`をオープンしておく必要がなくなり、その結果、`basefds`関数が余分なファイルディスクリプタをカウントすることが誤りとなりました。このコミットは、この古いロジックを削除し、正しいファイルディスクリプタ数を反映させることを目的としています。

## 前提知識の解説

*   **Plan 9 (オペレーティングシステム)**: Plan 9 from Bell Labsは、ベル研究所で開発された分散オペレーティングシステムです。Unixの概念をさらに推し進め、すべてのリソース（ファイル、デバイス、ネットワーク接続など）をファイルとして表現し、ファイルシステムを通じてアクセスするという設計思想を持っています。Go言語は、初期からPlan 9への移植が行われており、そのランタイムはPlan 9の特性に合わせて実装されています。
*   **ファイルディスクリプタ (File Descriptors, FDs)**: オペレーティングシステムにおいて、プロセスが開いているファイルやI/Oリソース（ソケット、パイプなど）を識別するために使用される抽象的なハンドルです。各プロセスは、通常、標準入力（0）、標準出力（1）、標準エラー出力（2）の3つのファイルディスクリプタをデフォルトで開いています。プログラムがファイルを開いたり、ネットワーク接続を確立したりすると、新しいファイルディスクリプタが割り当てられます。
*   **`/dev/bintime` (Plan 9のデバイスファイル)**: Plan 9において、システム時刻情報を提供する特殊なデバイスファイルです。過去のGoランタイムでは、このファイルをオープンして読み取ることで、高精度な時刻情報を取得していました。
*   **`nsec`システムコール (Plan 9のシステムコール)**: Plan 9におけるナノ秒単位の時刻を取得するためのシステムコールです。`/dev/bintime`デバイスファイルを介するよりも、より直接的かつ効率的な時刻取得メカニズムとして導入されました。Goランタイムがこの`nsec`システムコールを利用するようになったことで、`/dev/bintime`をオープンし続ける必要がなくなりました。
*   **`os/exec`パッケージ (Go言語)**: Go言語の標準ライブラリの一部で、外部コマンドを実行するための機能を提供します。このパッケージは、子プロセスの生成、標準入出力のリダイレクト、プロセスの終了ステータスの取得など、外部プログラムとの連携に必要な機能を提供します。テストコードでは、子プロセスが予期せぬファイルディスクリプタをリークしていないかを確認するために、プロセス開始時のファイルディスクリプタ数を正確に把握する必要があります。

## 技術的詳細

このコミットが修正しているのは、`src/os/exec/exec_test.go`ファイル内の`basefds()`関数です。この関数は、テスト対象のプロセスが起動時に開いていると期待されるファイルディスクリプタの数を返します。

変更前の`basefds()`関数は以下のロジックを持っていました。

1.  まず、`os.Stderr.Fd() + 1`を計算し、これをベースとなるファイルディスクリプタ数`n`とします。これは、標準入力（0）、標準出力（1）、標準エラー出力（2）の3つと、Goランタイムが内部的に開く可能性のある追加のFDを考慮したものです。`os.Stderr.Fd()`は標準エラー出力のファイルディスクリプタ番号を返すため、それに1を加えることで、少なくとも標準入出力の3つをカバーし、さらにGoランタイムが使用する可能性のあるFDを考慮しています。
2.  次に、`runtime.GOOS == "plan9" && runtime.GOARCH == "386"`という条件で、現在の実行環境が32ビットのPlan 9であるかをチェックしていました。
3.  もしこの条件が真であれば、`n`をインクリメント（`n++`）していました。これは、32ビットPlan 9のGoランタイムが`/dev/bintime`をオープンしたままにしておく必要があったため、そのための追加のファイルディスクリプタを考慮するためでした。コメントには`../../runtime/time_plan9_386.c:/^runtime·nanotime`が参照されており、これはランタイムの時刻取得に関する実装がこのデバイスファイルに依存していたことを示しています。

しかし、Goランタイムが`nsec`システムコールを使用するように変更されたことで、`/dev/bintime`をオープンしておく必要がなくなりました。そのため、32ビットPlan 9環境で`n`をインクリメントするロジックは不要となり、むしろ誤ったファイルディスクリプタ数を返す原因となっていました。

このコミットは、この不要な条件分岐とインクリメントロジックを削除し、`basefds()`関数が常に`os.Stderr.Fd() + 1`を返すように簡素化しました。これにより、Plan 9上でのファイルディスクリプタの期待値が正しくなり、`os/exec`パッケージのテストが正確に実行されるようになります。

## コアとなるコードの解説

変更されたのは、`src/os/exec/exec_test.go`ファイル内の`basefds()`関数のみです。

**変更前のコード:**

```go
func basefds() uintptr {
	n := os.Stderr.Fd() + 1

	// Go runtime for 32-bit Plan 9 requires that /dev/bintime
	// be kept open.
	// See ../../runtime/time_plan9_386.c:/^runtime·nanotime
	if runtime.GOOS == "plan9" && runtime.GOARCH == "386" {
		n++
	}
	return n
}
```

*   `n := os.Stderr.Fd() + 1`: 標準エラー出力のファイルディスクリプタ番号に1を加えた値を初期値`n`として設定します。これは、少なくとも標準入出力の3つのFD（0, 1, 2）と、Goランタイムが内部的に使用する可能性のあるFDを考慮したものです。
*   `if runtime.GOOS == "plan9" && runtime.GOARCH == "386"`: この条件は、現在の実行環境がPlan 9オペレーティングシステムであり、かつCPUアーキテクチャが386（32ビット）である場合に真となります。
*   `n++`: 上記の条件が真の場合、`n`を1つ増やします。これは、32ビットPlan 9のGoランタイムが時刻取得のために`/dev/bintime`デバイスファイルをオープンしたままにしておく必要があったため、そのための追加のファイルディスクリプタを考慮していました。

**変更後のコード:**

```go
func basefds() uintptr {
	return os.Stderr.Fd() + 1
}
```

*   変更後のコードは非常にシンプルです。以前の条件分岐と`n++`のロジックが完全に削除されました。
*   これにより、`basefds()`関数は常に`os.Stderr.Fd() + 1`を返します。これは、Goランタイムが時刻取得のために`/dev/bintime`をオープンしておく必要がなくなったため、Plan 9 386環境での追加のファイルディスクリプタを考慮する必要がなくなったことを反映しています。

この変更により、`os/exec`パッケージのテストが、Plan 9環境で子プロセスがリークしたファイルディスクリプタを検出する際に、正しいベースラインと比較できるようになります。

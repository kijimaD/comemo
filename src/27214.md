# [インデックス 27214] ファイルの概要

このコミットは、Goの標準ライブラリである`net/http`パッケージにおいて、`cmd/go`のようなHTTPクライアントのみを使用するプログラムのバイナリサイズを削減することを目的としています。具体的には、`maxBytesReader`型内の静的型アサーションをインターフェース型アサーションに置き換えることで、HTTPサーバー関連のコードが不要にリンクされるのを防ぎます。これにより、`cmd/go`のバイナリサイズが約5.2%削減されました。

## 元コミット内容

`net/http`: `cmd/go`からHTTPサーバーコードを削除するために動的型アサーションを使用

`cmd/go`がなぜHTTPサーバー実装を含んでいるのか疑問に思っていました。

リンカのデッドコード依存関係グラフをファイルにダンプし、グラフ分析を行ったところ、`cmd/go`がHTTPサーバーを含んでいた唯一の理由は、`maxBytesReader`型（HTTPトランスポートとHTTPサーバーの両方で使用される）がHTTPサーバー型への静的型アサーションを行っていたためであることが判明しました。

これをインターフェース型アサーションに変更することで、`cmd/go`のサイズが533KB（5.2%）削減されます。

linux/amd64では、`cmd/go`は10549200バイトから10002624バイトになります。

この回帰を防ぐためにテストも追加します。このテストは`cmd/go`をテスト対象のバイナリとして使用しますが（HTTPクライアントは必要だがHTTPサーバーは不要なバイナリ）、この変更とテストは、そのようなあらゆるプログラムに等しく適用可能です。

## 変更の背景

Goのコマンドラインツールである`cmd/go`は、HTTPクライアント機能（例えば、`go get`コマンドがリモートリポジトリからパッケージをダウンロードする際など）は利用しますが、HTTPサーバー機能は利用しません。しかし、コミット作成者がリンカのデッドコード依存関係グラフを分析したところ、`cmd/go`バイナリに不要なHTTPサーバーの実装コードが含まれていることが判明しました。

この問題の根本原因は、`net/http`パッケージ内の`maxBytesReader`という型が、その内部でHTTPサーバーの`*response`型への**静的型アサーション**を行っていたことにありました。Goのリンカは、静的型アサーションが存在すると、その具象型（この場合は`*response`型）が使用される可能性があると判断し、関連するコードをバイナリに含めてしまいます。これにより、`cmd/go`のようなHTTPクライアントのみを必要とするプログラムでも、HTTPサーバーのコードが不必要にリンクされ、バイナリサイズが増大していました。

このコミットは、この不要なコードのリンクを防ぎ、`cmd/go`および同様のプログラムのバイナリサイズを最適化することを目的としています。

## 前提知識の解説

1.  **Goのバイナリと静的リンク**: Go言語のコンパイラは、デフォルトでプログラムに必要なすべてのライブラリを単一の実行可能ファイルに静的にリンクします。これはデプロイの容易さという利点がある一方で、依存するコードが多いとバイナリサイズが大きくなる傾向があります。
2.  **`cmd/go`**: Go言語の公式ツールチェーンの主要なコマンドです。ビルド、テスト、パッケージ管理など、Go開発のあらゆる側面を管理します。このツール自体もGoで書かれており、`net/http`パッケージのクライアント部分を利用します。
3.  **`net/http`パッケージ**: Goの標準ライブラリで、HTTPプロトコルを扱うための包括的な機能を提供します。クライアント（HTTPリクエストの送信）とサーバー（HTTPリクエストの受信と応答）の両方の機能が含まれています。
4.  **`maxBytesReader`型**: `net/http`パッケージ内で定義されている内部的な型です。主にHTTPリクエストボディやレスポンスボディの読み取りにおいて、読み取るバイト数に上限を設けるために使用されます。これにより、悪意のある大きなリクエストなどからサーバーを保護する役割も果たします。
5.  **型アサーション (Type Assertion)**: Goにおいて、インターフェース型の値が特定の具象型であるか、または特定のインターフェースを満たすかをチェックし、その型に変換する操作です。
    *   **静的型アサーション**: `value.(*ConcreteType)`のように、コンパイル時に特定の具象型への変換を試みるものです。この形式を使用すると、リンカはその具象型がプログラムに必要であると判断し、そのコードをバイナリに含めます。
    *   **インターフェース型アサーション**: `value.(InterfaceType)`のように、インターフェース型の値が別の特定のインターフェースを満たすかをチェックするものです。この場合、リンカは具象型ではなく、そのインターフェースが定義するメソッドセットにのみ依存すると判断します。これにより、具象型が不要であればリンクされずに済み、デッドコード除去が促進されます。
6.  **デッドコード除去 (Dead Code Elimination)**: コンパイラやリンカが行う最適化の一種で、プログラムの実行に決して到達しない、または影響を与えないコード（デッドコード）を最終的なバイナリから削除するプロセスです。これにより、バイナリサイズが削減され、起動時間やメモリ使用量が改善されます。静的型アサーションは、デッドコード除去を妨げる要因となることがあります。

## 技術的詳細

このコミットの核心は、`net/http`パッケージ内の`maxBytesReader`型の`tooLarge`メソッドにおける型アサーションの変更です。

元々の実装では、`maxBytesReader`の`w`フィールド（`io.ReadCloser`インターフェース型）が、HTTPサーバーの内部型である`*response`型であるかどうかを静的にアサートしていました。

```go
// 変更前 (簡略化)
if res, ok := l.w.(*response); ok {
    res.requestTooLarge()
}
```

ここで`*response`はHTTPサーバーの内部実装の一部であり、`requestTooLarge()`というメソッドを持っています。`cmd/go`のようなHTTPクライアントのみを使用するプログラムでは、`l.w`が`*response`型になることはありません。しかし、この静的型アサーションが存在するだけで、Goのリンカは`*response`型とその関連コードがプログラムに必要であると判断し、`cmd/go`のバイナリに含めてしまっていました。これは、リンカがコンパイル時にすべての可能なコードパスを完全に解析し、未使用の具象型を常に削除できるわけではないためです。特に、型アサーションは潜在的な使用を示唆すると解釈されがちです。

このコミットでは、この問題を解決するために、`requestTooLarger`という新しいインターフェース型を定義しました。

```go
type requestTooLarger interface {
    requestTooLarge()
}
```

そして、`maxBytesReader.tooLarge`メソッド内の型アサーションを、この新しいインターフェース型に対するものに変更しました。

```go
// 変更後 (簡略化)
if res, ok := l.w.(requestTooLarger); ok {
    res.requestTooLarge()
}
```

`*response`型は元々`requestTooLarge()`メソッドを持っていたため、この新しい`requestTooLarger`インターフェースを暗黙的に満たします（Goのインターフェースは構造的型付けに基づいています）。

この変更により、`maxBytesReader`は特定の具象型`*response`に直接依存するのではなく、`requestTooLarger`インターフェースにのみ依存するようになりました。`cmd/go`のようなプログラムがHTTPサーバー機能を使用しない場合、`*response`型はどこからも参照されなくなり、リンカはこれをデッドコードとして認識し、最終的なバイナリから削除できるようになります。

結果として、`cmd/go`のバイナリサイズは533KB（約5.2%）削減されました。これは、Goのバイナリサイズ最適化において重要な改善です。

さらに、この変更が将来的に回帰しないように、新しいテスト`TestCmdGoNoHTTPServer`が追加されました。このテストは、`go tool nm`コマンドを使用して`cmd/go`バイナリ内のシンボルを検査し、HTTPサーバー関連のシンボル（例: `net/http.http2Server`, `net/http.(*Server).Serve`）が意図せず含まれていないことを確認します。同時に、HTTPクライアント関連のシンボル（例: `net/http.(*Client).Get`, `net/http.(*Transport).RoundTrip`）が存在することを確認し、テスト自体の健全性も保証しています。

## コアとなるコードの解説

### `src/net/http/request.go` の変更

`maxBytesReader`構造体の`tooLarge()`メソッドが変更されました。このメソッドは、読み取りバイト数が上限を超えた場合に呼び出されます。

変更前は、`l.w`（`io.ReadCloser`インターフェース型）がHTTPサーバーの内部型である`*response`型であるかを静的にチェックしていました。

```go
if res, ok := l.w.(*response); ok {
    res.requestTooLarge()
}
```

このコミットでは、この静的型アサーションを、新しく定義されたローカルインターフェース`requestTooLarger`に対する動的型アサーションに置き換えました。

```go
type requestTooLarger interface {
    requestTooLarge()
}
if res, ok := l.w.(requestTooLarger); ok {
    res.requestTooLarge()
}
```

この変更の意図は、コメントで明確に説明されています。`maxBytesReader`はサーバーコードとクライアントコードの両方で使用されますが、`requestTooLarge`チェックはサーバーコードでのみ使用されます。`cmd/go`のようなHTTPクライアントのみを使用するバイナリがHTTPサーバーをリンクしないようにするため、サーバーの具象型`*response`への静的型アサーションを避け、代わりに`requestTooLarger`インターフェースへのアサーションを使用します。これにより、リンカは`*response`型が不要な場合にそのコードを削除できるようになります。

### `src/net/http/http_test.go` の変更

`TestCmdGoNoHTTPServer`という新しいテスト関数が追加されました。このテストは、`cmd/go`バイナリがHTTPサーバーコードをリンクしていないことを検証します。

1.  **環境チェック**: `testenv.MustHaveGoBuild(t)`を呼び出し、Goビルド環境が利用可能であることを確認します。
2.  **`cmd/go`バイナリのパス取得**: `runtime.GOROOT()`と`filepath.Join`を使用して、現在のGoインストールにおける`cmd/go`実行可能ファイルのパスを取得します。Windows環境では`.exe`サフィックスを追加します。
3.  **`go tool nm`の実行**: `exec.Command("go", "tool", "nm", goBin).Output()`を実行し、`cmd/go`バイナリ内のシンボルテーブルをダンプします。`go tool nm`は、Goバイナリ内のシンボル（関数、変数など）をリストアップするツールです。
4.  **シンボル検証**:
    *   `wantSym`マップを定義し、存在すべきクライアント関連シンボル（例: `net/http.(*Client).Get`）と、存在すべきではないサーバー関連シンボル（例: `net/http.http2Server`, `net/http.(*Server).Serve`）を指定します。
    *   ダンプされたシンボルリスト（`out`）に対して`bytes.Contains`を使用し、各シンボルが存在するかどうかをチェックします。
    *   期待される結果（`want`）と実際の結果（`got`）を比較し、不一致があればテストを失敗させます。

このテストは、将来的に`maxBytesReader`のような箇所で誤ってHTTPサーバーコードへの静的依存が導入された場合に、それを検出し、回帰を防ぐための重要な安全策となります。

# [インデックス 27581] ファイルの概要

このコミットは、GoランタイムのWindows版における`osyield`関数の実装を改善するものです。以前の`osyield`は非効率的で、実質的に15ミリ秒程度のスリープとして機能していましたが、この変更によりWindows APIの`SwitchToThread`を使用するように修正され、大幅なパフォーマンス向上が実現されました。特に、ゴルーチン間の協調的スケジューリングにおけるCPUの利用効率が改善されています。

## 変更の背景

Goランタイムは、多数の軽量なゴルーチンを少数のOSスレッドに多重化するM:Nスケジューリングモデルを採用しています。このモデルでは、ゴルーチンが自発的に実行を譲る（yield）ことで、他のゴルーチンがCPU時間を利用できるようになります。この「譲る」動作は、Goの協調的スケジューリングの重要な要素です。

Windows環境における`runtime.osyield`の以前の実装は、効率が悪いという問題がありました。コミットメッセージによると、この関数は実質的に約15ミリ秒のスリープとして機能しており、これはゴルーチンが短時間だけCPUを譲りたい場合に、過剰な遅延を引き起こしていました。このような非効率性は、特に高頻度で`osyield`が呼び出されるシナリオにおいて、Goプログラムのパフォーマンスに悪影響を与えていました。

この問題は、GoのIssue #14790に関連しているとされており、このコミットはそのパフォーマンス改善を目的としています。以前の`NtWaitForSingleObject`ベースの実装を、より適切なWindows APIである`SwitchToThread`に置き換えることで、ゴルーチンがCPUを譲る際のオーバーヘッドを大幅に削減し、全体的な実行効率を向上させることが狙いです。

## 前提知識の解説

### Goランタイムスケジューラ (M:Nスケジューリング)

Go言語の並行処理は、ゴルーチン（goroutine）と呼ばれる軽量なスレッドによって実現されます。Goランタイムは、これらの多数のゴルーチン（M）を、オペレーティングシステム（OS）が管理する少数のOSスレッド（N）上で実行するM:Nスケジューリングモデルを採用しています。
*   **ゴルーチン (Goroutine)**: Goランタイムによって管理される軽量な実行単位。数KBのスタックで開始し、必要に応じてスタックが伸縮します。
*   **OSスレッド (OS Thread)**: OSによって管理される実行単位。Goランタイムは、ゴルーチンを実行するためにOSスレッドを利用します。
*   **P (Processor)**: 論理プロセッサ。Goランタイムスケジューラは、利用可能なPの数に基づいてOSスレッドを管理し、各Pに1つのOSスレッドを割り当ててゴルーチンを実行させます。

Goのスケジューラは、ゴルーチンがI/O操作、チャネル通信、明示的な`runtime.Gosched()`呼び出し、またはガベージコレクションなどの特定のポイントで自発的に実行を譲る「協調的スケジューリング」の側面を持っています。これにより、他のゴルーチンがCPU時間を得る機会が生まれます。

### `runtime.osyield`

`runtime.osyield`は、Goランタイム内部で使用される関数で、現在のOSスレッドがCPUの実行を他のスレッドに譲ることをOSに示唆するために呼び出されます。これは、Goのスケジューラが、現在実行中のゴルーチンがこれ以上進めない、または他のゴルーチンにCPUを譲るべきだと判断した場合に利用されます。例えば、ビジーループで他のゴルーチンが実行されるのを待つような状況で、CPUを無駄に消費しないようにするために使われることがあります。

### Windows API `SwitchToThread`

`SwitchToThread`は、Windowsオペレーティングシステムが提供するAPI関数です。この関数を呼び出すと、現在のスレッドは残りのタイムスライスを放棄し、同じプロセッサ上で実行準備ができている他のスレッドにCPUを譲ります。これは、OSレベルでの協調的なスレッドの実行譲渡メカニズムです。`SwitchToThread`は、呼び出し元のスレッドがすぐに再スケジュールされることを保証するものではなく、単に他のスレッドに機会を与えるだけです。

### `NtWaitForSingleObject`

`NtWaitForSingleObject`は、WindowsのネイティブAPI（NT API）の一つで、指定されたオブジェクトがシグナル状態になるか、指定されたタイムアウト期間が経過するまで、現在のスレッドの実行を中断します。以前の`osyield`の実装でこれが使用されていた場合、短いタイムアウトを指定しても、OSのスケジューリング粒度やオーバーヘッドのために、実質的にスリープに近い動作になっていた可能性があります。特に、非常に短い時間（例えば1ミリ秒）の待機を意図しても、OSが実際にスレッドを再開するまでにそれ以上の時間がかかることがあり、これがコミットメッセージで言及されている「15ms sleep」のような現象を引き起こしていたと考えられます。

## 技術的詳細

このコミットの核心は、Windowsにおける`runtime.osyield`の実装を、非効率な`NtWaitForSingleObject`（またはそれに類するスリープ動作）から、より効率的な`SwitchToThread` APIの呼び出しに切り替えた点にあります。

具体的な変更点は以下の通りです。

1.  **`SwitchToThread`の動的インポート**:
    `src/runtime/os1_windows.go`において、`kernel32.dll`から`SwitchToThread`関数を動的にインポートするための宣言`//go:cgo_import_dynamic runtime._SwitchToThread SwitchToThread%0 "kernel32.dll"`が追加されました。これにより、Goランタイムが実行時にこのWindows APIを呼び出せるようになります。

2.  **`osyield`の実装変更**:
    同じく`src/runtime/os1_windows.go`内の`osyield`関数が、`usleep1(1)`の呼び出しから`onosstack(switchtothreadAddr, 0)`の呼び出しに変更されました。これは、`osyield`が直接スリープ関数を呼び出すのではなく、`SwitchToThread`を呼び出すための新しいアセンブリルーチンを介するように変更されたことを意味します。

3.  **`onosstack`と`switchtothread`アセンブリ関数の導入**:
    `src/runtime/sys_windows_386.s`と`src/runtime/sys_windows_amd64.s`というアセンブリファイルに、`onosstack`と`switchtothread`という新しい関数が追加されました。
    *   `onosstack`は、GoのスタックではなくOSのスタック上で指定された関数（この場合は`switchtothread`）を実行するためのヘルパー関数です。これは、Windows APIの呼び出しがOSスタックの特定の要件を持つ場合があるため、安全かつ正確にAPIを呼び出すために必要です。
    *   `switchtothread`は、実際に`_SwitchToThread`（動的インポートされたWindows API）を呼び出すアセンブリルーチンです。これには、Windowsの呼び出し規約（スタックアライメントなど）に合わせた準備が含まれます。

4.  **ベンチマークの追加と結果**:
    `src/runtime/syscall_windows_test.go`に、`osyield`のパフォーマンスを測定するための新しいベンチマーク（`BenchmarkOsYield1ms`, `BenchmarkOsYield15ms`）が追加されました。コミットメッセージに示されているベンチマーク結果は、この変更が劇的な改善をもたらしたことを明確に示しています。
    *   `BenchmarkOsYield1ms`: 980018 ns/op から 75.5 ns/op へ、約99.99%の改善。
    *   `BenchmarkOsYield15ms`: 15625200 ns/op から 75.8 ns/op へ、約100.00%の改善。
    これらの結果は、以前の`osyield`が実際に長い時間スリープしていたこと、そして`SwitchToThread`への変更がいかに効率的であるかを裏付けています。

この変更により、GoランタイムはWindows上でより効率的にCPUを譲渡できるようになり、特に多数のゴルーチンが頻繁に協調的スケジューリングを行うようなシナリオでのパフォーマンスが向上します。

## コアとなるコードの解説

### `src/runtime/os1_windows.go`

このファイルは、GoランタイムのWindows固有のOSインタフェースを定義しています。
*   `osyield()` 関数の変更が最も重要です。以前は`usleep1(1)`を呼び出していましたが、これは実質的に短いスリープを意味していました。新しい実装では`onosstack(switchtothreadAddr, 0)`を呼び出します。これは、OSスタック上で`switchtothread`アセンブリ関数を実行することを意味します。
*   `_SwitchToThread`の動的インポートは、Goランタイムが`kernel32.dll`から`SwitchToThread`関数をロードして使用できるようにするためのものです。
*   `osinit()`での`switchtothreadAddr`の初期化は、アセンブリ関数`switchtothread`のアドレスを取得し、Goコードから参照できるようにしています。

### `src/runtime/sys_windows_386.s` および `src/runtime/sys_windows_amd64.s`

これらのアセンブリファイルは、Goランタイムの低レベルなWindows固有の処理を実装しています。
*   **`runtime·onosstack`**: この関数は、Goのスケジューラが管理するゴルーチンのスタックではなく、OSが管理するスレッドのスタック（g0スタック）上で、指定された関数（`fn`）を実行するために使用されます。Windows APIの呼び出しは、OSスタック上で実行されることを期待する場合があるため、このラッパーが必要です。
*   **`runtime·switchtothread`**: この新しいアセンブリ関数は、`runtime·_SwitchToThread`（つまりWindows APIの`SwitchToThread`）を呼び出します。32ビット版と64ビット版でスタックのセットアップやアライメントの調整が異なりますが、基本的な目的は同じです。現在のスレッドの実行を自発的に譲渡するようOSに指示します。

### `src/runtime/syscall_windows_test.go`

このファイルには、Windowsシステムコールに関連するテストとベンチマークが含まれています。
*   追加されたベンチマークは、`osyield`の性能を直接測定するために設計されています。`benchOsYield`関数は、指定された回数だけ`runtime.OsYield()`を呼び出し、その総時間を測定します。
*   `timeBeginPeriod(1)`と`timeEndPeriod(1)`の呼び出しは、Windowsのタイマー分解能を1ミリ秒に設定し、より正確な時間測定を可能にするためのものです。これにより、`osyield`のような短い操作のパフォーマンス変化をより詳細に捉えることができます。
*   これらのベンチマークは、`osyield`の変更がGoプログラムの応答性や効率に与える影響を定量的に評価するための重要なツールとなります。

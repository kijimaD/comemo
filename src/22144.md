# [インデックス 22144] ファイルの概要

このコミットは、Goランタイムにおけるヒープの管理、特にポインタ解析の堅牢性に関する改善を目的としています。ヒープ内に「穴」が存在する場合でも、ポインタの妥当性を正しく判断できるようにすることで、誤ったポインタエラーの検出を防ぎ、将来的なポインタ解析機能の再有効化に向けた障壁を取り除きます。

## 元コミット内容

Goランタイムにおいて、ヒープ内の「穴」を適切に処理するための変更です。ポインタ解析のバグを示す「解放済みスパンへのポインタ」と、`sysAlloc`や`mmap`などによって正当に発生しうる「ヒープ外の領域へのポインタ」を区別する必要があります。通常、ヒープは連続しているため問題になりませんが、特に32ビット環境など、すでに確保された領域を避けてヒープを拡張しなければならない状況では、このような「穴」が発生する可能性があります。この修正は、現在無効化されている不正ポインタテストを再有効化するための障壁を一つ取り除くものです。Issue #9872を修正します。

## 変更の背景

Goランタイムは、ガベージコレクション（GC）のためにヒープ上のオブジェクトへのポインタを正確に追跡する必要があります。この追跡は「ポインタ解析」と呼ばれ、ヒープの整合性を保つ上で非常に重要です。

しかし、特定の状況下では、Goランタイムが管理するヒープ領域ではないメモリ領域へのポインタが、正当な理由で発生することがあります。例えば、`sysAlloc`や`mmap`といったシステムコールを直接利用してメモリを確保した場合、その領域はGoのヒープ管理の対象外となります。

問題は、Goランタイムがポインタの妥当性をチェックする際に、これらの「ヒープ外の正当なポインタ」と、「Goヒープ内の解放済みメモリを指す不正なポインタ」（これはポインタ解析のバグを示唆する）を区別する必要がある点にありました。特に、32ビットシステムではアドレス空間が限られているため、Goヒープが連続した大きなブロックとして確保できない場合があり、既存のメモリ割り当てを避けてヒープを拡張する際に、ヒープ内に「穴」が生じることがありました。

このコミットが行われた時点では、Goランタイムの「不正ポインタテスト」は無効化されていました。これは、上記のようなヒープの「穴」に起因する誤検出を避けるためと考えられます。このコミットの目的は、この誤検出の問題を解決し、将来的に不正ポインタテストを安全に再有効化できるようにするための前提条件を整えることにありました。Issue #9872は、まさにこのような「Goヒープ内の不正なポインタ」が検出される問題報告であり、このコミットはその解決を目指しています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理に関するいくつかの基本的な概念を理解しておく必要があります。

*   **Goランタイムのメモリ管理**: Goは独自のガベージコレクタを持つため、メモリの割り当てと解放をランタイムが管理します。ヒープは、Goプログラムが動的にメモリを割り当てる主要な場所です。
*   **ヒープとアリーナ**: Goのヒープは、より大きな「アリーナ」と呼ばれる仮想メモリ領域にマッピングされます。アリーナは、GoランタイムがOSから取得する連続した仮想アドレス空間です。
*   **`mspan`**: `mspan`は、Goランタイムがヒープを管理するための基本的な単位です。連続したページ（通常は8KB）のブロックを表し、特定のサイズのオブジェクトを格納するために使用されます。`mspan`は、使用中（`_MSpanInUse`）、解放済み（`_MSpanFree`）、スタック用（`_MSpanStack`）など、様々な状態を持ちます。
*   **`h_spans`**: `h_spans`は、仮想アドレスのページIDから対応する`mspan`へのルックアップテーブルです。これにより、特定のアドレスがどの`mspan`に属しているかを効率的に判断できます。
*   **ポインタ解析**: ガベージコレクタがヒープ上の到達可能なオブジェクトを特定するために、メモリ内の値がポインタであるかどうかを判断するプロセスです。不正なポインタ（例えば、解放済みメモリを指すポインタ）は、ランタイムのバグやメモリ破壊を示す可能性があります。
*   **`sysAlloc`/`mmap`**: これらはオペレーティングシステムが提供するメモリ割り当てのプリミティブです。`sysAlloc`はGoランタイムがOSからメモリを取得するために使用する低レベルの関数であり、`mmap`はUnix系システムでファイルやデバイスをメモリにマッピングしたり、匿名メモリ領域を確保したりするために使われるシステムコールです。これらの関数によって確保されたメモリは、Goランタイムのヒープ管理の対象外となる場合があります。
*   **`_PageShift`**: メモリページサイズをビットシフトで表す定数です。例えば、ページサイズが8KB（8192バイト）の場合、`2^13 = 8192`なので、`_PageShift`は13になります。これにより、アドレスからページIDを効率的に計算できます。

## 技術的詳細

このコミットの核心は、`src/runtime/mbitmap.go`の`heapBitsForObject`関数と、`src/runtime/mheap.go`の`mHeap_Grow`関数における`h_spans`の更新ロジックの変更にあります。

### `heapBitsForObject`関数の変更 (`src/runtime/mbitmap.go`)

`heapBitsForObject`関数は、与えられたポインタ`p`が指すオブジェクトのヒープビット（ガベージコレクタがポインタを識別するために使用するメタデータ）を取得するために使用されます。この関数は、ポインタ`p`がGoヒープ内の有効なオブジェクトを指しているかどうかを判断します。

変更前は、`s == nil || pageID(k) < s.start || p >= s.limit || s.state != mSpanInUse`という条件で、ポインタが不正である可能性をチェックしていました。この条件に加えて、`s != nil && s.state == _MSpanStack`の場合に早期リターンしていました。

変更後、この条件は`s == nil || s.state == _MSpanStack`に緩和されました。
*   `s == nil`の場合: これは、仮想アドレスがGoヒープの一部として割り当てられたことがないことを意味します。このようなポインタは、`sysAlloc`や`mmap`などによって確保されたGoヒープ外の領域を指している可能性があり、これは正当なケースです。したがって、この場合はエラーとせず、`return`するように変更されました。
*   `s.state == _MSpanStack`の場合: スタックへのポインタも、ランタイムが明示的に管理しているため、正当なポインタとして扱われます。

この変更により、`heapBitsForObject`は、Goヒープ外の正当なメモリ領域へのポインタを誤って「不正なポインタ」として報告するのを防ぎます。

### `mHeap_Grow`関数の変更 (`src/runtime/mheap.go`)

`mHeap_Grow`関数は、Goヒープが不足した際に、ヒープを拡張するために新しいメモリ領域をOSから取得し、それをGoランタイムのヒープに組み込む役割を担います。このプロセスには、新しく確保された`mspan`を`h_spans`ルックアップテーブルに登録する作業が含まれます。

変更前は、新しく確保された`mspan`の開始ページと終了ページのみを`h_spans`に登録していました。
```go
h_spans[p] = s
h_spans[p+s.npages-1] = s
```
これは、`h_spans`が連続したページを指すことを前提としていました。しかし、ヒープ内に「穴」がある場合や、`mmap`などでGoランタイムが管理しない領域が間に挟まる場合、この仮定は崩れます。

変更後、新しく確保された`mspan`が占める**全てのページ**を`h_spans`に登録するように変更されました。
```go
for i := p; i < p+s.npages; i++ {
	h_spans[i] = s
}
```
これにより、`h_spans`は、新しく割り当てられた`mspan`内の全てのアドレス範囲に対して、正しい`mspan`エントリを指すようになります。これは、`h_spans`のコメントにも明記されており、解放済みスパンのページや、一度も割り当てられていないページのエントリが`nil`であることと合わせて、ポインタ解析がより正確に機能するための基盤を強化します。

この変更は、ヒープが非連続的である可能性を考慮し、`h_spans`のデータ構造がヒープの実際のレイアウトをより正確に反映するようにすることで、`heapBitsForObject`のような関数がポインタの妥当性を判断する際の信頼性を向上させます。

## コアとなるコードの解説

### `src/runtime/mbitmap.go`の変更点

`heapBitsForObject`関数内の条件分岐が変更されました。
変更前:
`if s != nil && s.state == _MSpanStack`
変更後:
`if s == nil || s.state == _MSpanStack`

この変更の意図は、`s`（ポインタ`p`が属する`mspan`）が`nil`である場合、つまりその仮想アドレスがGoヒープの一部として割り当てられたことがない場合でも、それを正当なポインタとして扱うようにすることです。これは、`sysAlloc`や`mmap`などによってGoランタイムの管理外でメモリが確保された場合に発生しうる状況です。このようなポインタは、Goのポインタ解析のバグを示すものではなく、正当なものであるため、`heapBitsForObject`がエラーを返さずに処理を続行できるようにします。`_MSpanStack`状態の`mspan`へのポインタも同様に正当なものとして扱われます。

### `src/runtime/mheap.go`の変更点

`h_spans`変数のコメントが追加され、その役割がより明確になりました。
*   割り当てられたスパンの場合、そのページはスパン自体にマッピングされます。
*   解放されたスパンの場合、最低ページと最高ページのみがスパン自体にマッピングされます。内部ページは任意のスパンにマッピングされます。
*   一度も割り当てられていないページの場合、`h_spans`のエントリは`nil`になります。

最も重要な変更は、`mHeap_Grow`関数内で`h_spans`を更新する方法です。
変更前:
```go
h_spans[p] = s
h_spans[p+s.npages-1] = s
```
変更後:
```go
for i := p; i < p+s.npages; i++ {
	h_spans[i] = s
}
```
この変更により、新しくヒープに組み込まれる`mspan`が占める**全てのページ**に対応する`h_spans`のエントリが、その`mspan`を指すように設定されます。これにより、ヒープが非連続的である場合でも、`h_spans`ルックアップテーブルがヒープの正確なマッピングを維持できるようになります。これは、`heapBitsForObject`のような関数が任意のアドレスに対して正しい`mspan`情報を取得するために不可欠であり、ポインタ解析の正確性を向上させます。

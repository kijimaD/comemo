このコミットは、Go言語の `net/http` パッケージにおけるHTTPヘッダー値の検証ロジックを修正するものです。具体的には、以前の変更で導入された過度に厳格な検証ルールを緩和し、HTTP/1.1の仕様であるRFC2616に準拠するように調整しています。これにより、非ASCII文字（128以上のオクテット）を含む正当なヘッダー値が誤って拒否される問題を解決します。

## 変更の背景

この変更は、Go 1.6開発サイクル中に `net/http` パッケージに導入されたHTTPヘッダー値の検証ロジックが、HTTP/1.1の仕様であるRFC2616に対して過度に厳格であったために発生した問題を修正するために行われました。

以前の変更（`golang.org/cl/11207`）では、HTTPヘッダー値にASCII範囲外の文字（バイト値が128以上）が含まれることを不正と判断していました。しかし、RFC2616の定義によれば、ヘッダーの `field-content` は `TEXT` で構成され、`TEXT` は「制御文字（CTLs）を除く任意のオクテット（OCTET）、ただし線形空白（LWS）を含む」とされています。ここでいう「オクテット」は8ビットのデータであり、バイト値が128以上の文字も含まれます。したがって、非ASCII文字は制御文字ではないため、HTTPヘッダー値として許容されるべきでした。

この過度な厳格さにより、正当なHTTPヘッダー値を持つリクエストやレスポンスがGoの `net/http` サーバーによって誤って拒否される可能性がありました。この問題はGo issue #11207で報告され、このコミットはその問題を解決するために、以前の厳格な検証の一部を元に戻す（partial rollback）形で実装されました。

## 前提知識の解説

*   **HTTPヘッダー (HTTP Headers)**: HTTPメッセージ（リクエストおよびレスポンス）のメタデータを提供するキーと値のペア。例えば、`Content-Type`、`User-Agent`、`Server` などがあります。
*   **RFC2616**: HTTP/1.1プロトコルを定義する主要な仕様書。このコミットでは特に以下のセクションが重要です。
    *   **RFC2616 §4.2 Message Headers**: HTTPメッセージヘッダーの一般的な構造と構文について説明しています。`field-content` の定義が含まれます。
    *   **RFC2616 §2.2 Basic Rules**: HTTPメッセージの基本的な構文規則を定義しており、`OCTET`、`CHAR`、`CTL`、`LWS`、`TEXT` などのプリミティブな要素が定義されています。
        *   **OCTET**: 任意の8ビットデータ。0から255までのバイト値。
        *   **CHAR**: 任意のUS-ASCII文字（オクテット0-127）。
        *   **CTL (Control Characters)**: US-ASCII制御文字（オクテット0-31）とDEL（オクテット127）。これらは通常、表示できない文字やデバイス制御に使われます。
        *   **LWS (Linear White Space)**: HTTPヘッダー値の折り返しに使われる空白文字（スペースやタブ）。
        *   **TEXT**: `CTL` を除く任意の `OCTET`。ただし `LWS` は含む。この定義が、バイト値が128以上の文字がヘッダー値として許容される根拠となります。
*   **Go `net/http` パッケージ**: Go言語の標準ライブラリで、HTTPクライアントおよびサーバーの実装を提供します。このパッケージはHTTPプロトコルの仕様に厳密に従うことを目指しており、ヘッダーの解析と検証もその一部です。
*   **Go Change List (CL)**: Goプロジェクトにおけるコード変更の単位。`golang.org/cl/XXXXX` の形式で参照されます。

## 技術的詳細

このコミットの核心は、`net/http` パッケージ内の `validHeaderValue` 関数におけるヘッダー値の検証ロジックの変更です。

以前の `validHeaderValue` 関数は、ヘッダー値の各バイト `b` が以下の条件を満たすことを要求していました。
1.  `b` がタブ文字 (`\t`) である場合は許容。
2.  `b` がスペース (`' '`) からチルダ (`'~'`) までのASCII範囲内である場合は許容。
3.  上記以外の場合は不正と判断し、`false` を返していました。

このロジックでは、バイト値が128以上の文字（例えば、UTF-8でエンコードされた日本語やその他の多言語文字）は `' ' <= b && b <= '~'` の条件を満たさないため、不正なヘッダー値として扱われていました。

しかし、RFC2616 §2.2 の `TEXT` の定義によれば、`TEXT` は `CTL` (制御文字) を除く任意の `OCTET` を含むことができます。`CTL` はオクテット0-31と127（DEL）であり、バイト値128以上の文字は `CTL` ではありません。したがって、RFCの観点からは、バイト値128以上の文字はヘッダー値として有効です。

このコミットでは、`validHeaderValue` 関数のロジックを以下のように変更しました。
*   各バイト `b` について、`b < ' ' && b != '\t'` の条件をチェックします。
*   この条件が真（つまり、`b` がスペースより小さいがタブではない）の場合、そのバイトは制御文字（`CTL`）であるため、`false` を返して不正と判断します。
*   この条件が偽の場合（つまり、`b` がスペース以上であるか、またはタブである場合）、そのバイトは有効とみなし、ループを続行します。
*   全てのバイトがこのチェックを通過した場合、`true` を返して有効なヘッダー値と判断します。

この変更により、バイト値が128以上の文字は `b < ' '` の条件を満たさないため、`validHeaderValue` 関数によって有効な文字として扱われるようになります。これにより、Goの `net/http` パッケージはRFC2616の仕様に正確に準拠し、より広範なHTTPヘッダー値を正しく処理できるようになります。

## コアとなるコードの解説

### `validHeaderValue` 関数の変更 (`src/net/http/request.go`)

*   **変更前**:
    *   タブ文字 (`\t`) は許容。
    *   ASCIIのスペース (`' '`) からチルダ (`'~'`) までの範囲の文字は許容。
    *   それ以外の文字（特にバイト値が128以上の文字や、スペースより小さい制御文字）は `return false` で即座に不正と判断されていました。
*   **変更後**:
    *   `if b < ' ' && b != '\t'` という条件に変わりました。
    *   この条件は、「バイト `b` がスペース (`' '`, ASCII値32) より小さい」**かつ**「タブ文字 (`\t`, ASCII値9) ではない」場合に `true` となります。
    *   これは、`b` がASCII値0-8、10-31、127（DEL）のいずれかである、つまり制御文字（`CTL`）である場合に該当します。
    *   制御文字が見つかった場合のみ `return false` で不正と判断します。
    *   それ以外の文字（タブ文字、スペース以上のASCII文字、およびバイト値128以上の非ASCII文字）はループを継続し、最終的に `return true` で有効と判断されます。
    *   この変更により、RFC2616の `TEXT` の定義（`CTL` を除く任意の `OCTET`）に正確に合致するようになりました。

### テストケースの変更 (`src/net/http/serve_test.go`)

*   **変更前**:
    *   `{"foo: foo\x00foo\r\n", 400}`: ヘッダー値にヌル文字 (`\x00`) が含まれる場合は400 Bad Request。これは制御文字なので正しい。
    *   `{"foo: foo\xfffoo\r\n", 400}`: ヘッダー値に `\xff` (バイト値255) が含まれる場合は400 Bad Request。これは非ASCII文字であり、変更前のロジックでは不正とされていました。
*   **変更後**:
    *   `{"foo: foo\x00foo\r\n", 400}`: ヌル文字 (`\x00`) は引き続き制御文字として400 Bad Request。これは正しい挙動です。コメントも「CTL in value is bad」に変更され、理由が明確化されました。
    *   `{"foo: foo\xfffoo\r\n", 200}`: `\xff` (バイト値255) が含まれるヘッダー値は、RFC2616の定義に従い、200 OKとして許容されるようになりました。コメントも「non-ASCII high octets in value are fine」に変更され、この変更の意図が明確に示されています。

これらの変更により、Goの `net/http` パッケージはHTTP/1.1の仕様に準拠し、より堅牢で互換性の高いHTTP通信を提供できるようになりました。

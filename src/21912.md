# [インデックス 21912] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）におけるエスケープ解析の拡張に関するものです。具体的には、`make(map[k]v)`で作成されるマップがヒープにエスケープしない場合、そのマップの内部構造（`hmap`と最初のバケット）をスタック上に直接割り当てるように変更されました。これにより、ヒープ割り当てが削減され、ガベージコレクションの負荷が軽減され、パフォーマンスが向上します。

## 変更の背景

Go言語のランタイムは、メモリ管理においてガベージコレクション（GC）に大きく依存しています。GCの効率はアプリケーションのパフォーマンスに直結するため、ヒープ割り当てを最小限に抑えることは非常に重要です。Goコンパイラは、変数が関数スコープ外に「エスケープ」しないことを検出する「エスケープ解析」という最適化を行います。エスケープしない変数は、ヒープではなくスタックに割り当てることができ、これによりGCの対象から外れ、割り当てと解放のオーバーヘッドが大幅に削減されます。

このコミット以前は、`make(map)`によって作成されるマップは、その使用方法に関わらず、常にヒープに割り当てられていました。しかし、多くのマップは一時的なものであり、関数内で作成され、その関数が終了する前に使用されなくなるため、ヒープに割り当てる必要はありません。このようなケースでは、ヒープ割り当ては不要なオーバーヘッドとなり、GCの頻度と時間を増加させていました。

このコミットの目的は、`make(map)`で作成されるマップに対してもエスケープ解析を適用し、エスケープしないマップをスタックに割り当てることで、メモリ使用量を最適化し、全体的なパフォーマンスを向上させることにありました。コミットメッセージには、標準ライブラリ内に75ものエスケープしないマップのケースがあることが示されており、この最適化が広範囲にわたる影響を持つことが示唆されています。

## 前提知識の解説

### 1. エスケープ解析 (Escape Analysis)

エスケープ解析は、コンパイラ最適化の一種で、プログラム内の変数がその宣言されたスコープ（通常は関数）の外で参照される可能性があるかどうかを判断します。

*   **スタック割り当て**: 変数がスコープ外にエスケープしないと判断された場合、その変数はスタックに割り当てられます。スタック割り当ては非常に高速で、関数の終了時に自動的にメモリが解放されるため、ガベージコレクションの対象になりません。
*   **ヒープ割り当て**: 変数がスコープ外にエスケープする可能性がある場合（例: グローバル変数に代入される、ポインタが返されるなど）、その変数はヒープに割り当てられます。ヒープに割り当てられたメモリは、ガベージコレクタによって管理され、不要になった時点で回収されます。ヒープ割り当てとGCは、スタック割り当てに比べてオーバーヘッドが大きいです。

Goコンパイラは、このエスケープ解析を積極的に行い、可能な限りスタック割り当てを促進することで、パフォーマンスを向上させています。

### 2. Goのマップ (map) の内部構造

Goのマップはハッシュテーブルとして実装されており、その内部構造は`runtime.hmap`と`runtime.bmap`（バケット）という2つの主要な構造体で構成されています。

*   **`hmap`**: マップ全体のメタデータ（要素数、ハッシュ関数、バケットの数など）を保持する構造体です。マップのヘッダのようなものです。
*   **`bmap` (バケット)**: 実際のキーと値のペアを格納する配列です。各バケットは複数のキーと値を保持でき、オーバーフローした場合には別のバケットへのポインタを持ちます。

通常、`make(map)`が呼び出されると、`hmap`構造体と最初の`bmap`バケットはヒープに割り当てられます。マップが成長し、既存のバケットが満杯になると、新しいバケットがヒープに割り当てられ、既存のバケットからリンクされます。

### 3. `make(map)` 関数

Goでマップを作成する際には、組み込み関数`make`を使用します。
例: `m := make(map[string]int)`

この`make`関数は、コンパイル時に`runtime.makemap`というランタイム関数への呼び出しに変換されます。`runtime.makemap`は、マップの型情報と初期容量のヒントを受け取り、`hmap`構造体と初期バケットを割り当てて初期化し、その`hmap`へのポインタを返します。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラ（`cmd/gc`）とGoランタイム（`runtime`）の両方にわたる協調的な変更にあります。

1.  **`makemap`関数のシグネチャ変更**:
    *   `src/cmd/gc/builtin.c`と`src/cmd/gc/runtime.go`において、`makemap`ランタイム関数のシグネチャが変更されました。
    *   変更前: `func makemap(mapType *byte, hint int64) (hmap map[any]any)`
    *   変更後: `func makemap(mapType *byte, hint int64, mapbuf *any, bucketbuf *any) (hmap map[any]any)`
    *   新しい引数`mapbuf`と`bucketbuf`は、それぞれ`hmap`構造体と最初のバケットをスタック上に割り当てるためのバッファを指すポインタです。これにより、ランタイムの`makemap`関数は、コンパイラが提供するスタック上のメモリを直接利用できるようになります。

2.  **コンパイラのエスケープ解析の拡張 (`src/cmd/gc/walk.c`)**:
    *   `cmd/gc/walk.c`は、GoコンパイラのAST (Abstract Syntax Tree) ウォークフェーズを担当し、エスケープ解析を含む多くの最適化を行います。
    *   `OMAKEMAP`（`make(map)`のASTノード）の処理において、マップがエスケープしない場合（`n->esc == EscNone`）、コンパイラは`hmap`と最初のバケットのためのメモリをスタック上に一時的に割り当てます。
    *   具体的には、`temp(hmap(t))`と`temp(mapbucket(t))`を使用して、それぞれ`hmap`とバケットの型に応じた一時変数をスタック上に作成し、それらのアドレスを`makemap`関数に渡すようにコードが生成されます。
    *   これにより、`makemap`はヒープ割り当てをスキップし、スタック上のバッファを初期化するだけで済みます。

3.  **マップ構造体のコンパイラ内部表現の更新 (`src/cmd/gc/reflect.c`)**:
    *   `src/cmd/gc/reflect.c`は、Goの型システムとリフレクションに関連するコンパイラ内部の処理を扱います。
    *   `mapbucket`と`hmap`関数の実装が変更され、これらの構造体のコンパイラ内部表現がより正確に定義されるようになりました。特に、`makefield`というヘルパー関数が導入され、構造体のフィールド定義が簡潔になりました。
    *   これらの変更は、コンパイラが`hmap`とバケットの正確なサイズとアライメントを把握し、スタック上に適切なサイズのバッファを割り当てるために必要です。

4.  **ランタイムの`makemap`関数の変更 (`src/runtime/hashmap.go`)**:
    *   `src/runtime/hashmap.go`の`makemap`関数は、新しい`h`と`bucket`引数を受け取るようになりました。
    *   もし`h != nil`（つまり、コンパイラがスタック上に`hmap`バッファを提供した場合）、`makemap`は`newobject(t.hmap)`を呼び出してヒープに新しい`hmap`を割り当てる代わりに、提供された`h`ポインタを直接使用します。
    *   同様に、`bucket != nil`の場合、最初のバケットも提供された`bucket`ポインタを直接使用します。
    *   これにより、エスケープしないマップの作成時に、ヒープ割り当てが完全に回避されます。

5.  **テストとベンチマークの追加**:
    *   `src/runtime/map_test.go`に`TestNonEscapingMap`が追加され、エスケープしないマップが実際に割り当てを行わないことを検証しています。
    *   `src/runtime/mapspeed_test.go`に`BenchmarkNewSmallMap`が追加され、小さなマップ作成のパフォーマンスが測定されています。
    *   `test/escape2.go`と`test/escape2n.go`に、`make(map)`がエスケープ解析によって正しく「エスケープしない」と判断されるケースと「ヒープにエスケープする」と判断されるケースのテストが追加されています。

これらの変更により、Goコンパイラは`make(map)`の呼び出しをよりインテリジェントに処理し、エスケープ解析の結果に基づいて最適なメモリ割り当て戦略（スタックまたはヒープ）を選択できるようになりました。

## コアとなるコードの解説

### `src/cmd/gc/builtin.c` の変更

このファイルは、Goコンパイラが認識する組み込み関数やランタイム関数のシグネチャを定義しています。`makemap`関数のシグネチャが変更されたのは、コンパイラがスタック上に割り当てた`hmap`とバケットのバッファをランタイムに渡せるようにするためです。`mapbuf`と`bucketbuf`という2つの新しいポインタ引数が追加され、これらがスタック上のメモリ領域を指すことになります。

### `src/cmd/gc/walk.c` の変更

このファイルは、コンパイラのASTウォークフェーズにおけるコード生成ロジックを含んでいます。
`OMAKEMAP`ケース（`make(map)`の処理）において、最も重要な変更は以下の部分です。

```go
		a = nodnil(); // hmap buffer
		r = nodnil(); // bucket buffer
		if(n->esc == EscNone) {
			// Allocate hmap buffer on stack.
			var = temp(hmap(t));
			a = nod(OAS, var, N); // zero temp
			typecheck(&a, Etop);
			*init = list(*init, a);
			a = nod(OADDR, var, N);

			// Allocate one bucket on stack.
			// Maximum key/value size is 128 bytes, larger objects
			// are stored with an indirection. So max bucket size is 2048+eps.
			var = temp(mapbucket(t));
			r = nod(OAS, var, N); // zero temp
			typecheck(&r, Etop);
			*init = list(*init, r);
			r = nod(OADDR, var, N);
		}

		argtype(fn, hmap(t));	// hmap buffer
		argtype(fn, mapbucket(t));	// bucket buffer
		argtype(fn, t->down);	// key type
		argtype(fn, t->type);	// value type
		n = mkcall1(fn, n->type, init, typename(n->type), conv(n->left, types[TINT64]), a, r);
```

*   `if(n->esc == EscNone)`: ここがエスケープ解析の結果を利用する分岐点です。`n->esc == EscNone`は、現在の`make(map)`の呼び出しによって作成されるマップが、関数スコープ外にエスケープしないとコンパイラが判断した場合に真となります。
*   `var = temp(hmap(t));` と `var = temp(mapbucket(t));`: エスケープしない場合、コンパイラは`hmap`構造体と最初のバケットのためのメモリをスタック上に一時変数として割り当てます。`temp()`関数は、指定された型の新しい一時変数を生成します。
*   `a = nod(OADDR, var, N);` と `r = nod(OADDR, var, N);`: スタック上に割り当てられた一時変数のアドレスを取得し、それぞれ`a`と`r`に格納します。これらが`makemap`関数に渡される`mapbuf`と`bucketbuf`引数になります。
*   `mkcall1(...)`: 最終的に、`makemap`ランタイム関数への呼び出しが生成されます。この呼び出しには、マップの型情報、初期容量のヒントに加えて、スタック上に割り当てられた`hmap`とバケットのバッファのアドレス（`a`と`r`）が渡されます。

### `src/runtime/hashmap.go` の変更

このファイルは、Goのマップのランタイム実装を含んでいます。`makemap`関数の変更は、コンパイラからの新しい引数`h`と`bucket`を処理するように拡張されました。

## 変更の背景

Go言語のランタイムは、メモリ管理においてガベージコレクション（GC）に大きく依存しています。GCの効率はアプリケーションのパフォーマンスに直結するため、ヒープ割り当てを最小限に抑えることは非常に重要です。Goコンパイラは、変数が関数スコープ外に「エスケープ」しないことを検出する「エスケープ解析」という最適化を行います。エスケープしない変数は、ヒープではなくスタックに割り当てることができ、これによりGCの対象から外れ、割り当てと解放のオーバーヘッドが大幅に削減されます。

このコミット以前は、`make(map)`によって作成されるマップは、その使用方法に関わらず、常にヒープに割り当てられていました。しかし、多くのマップは一時的なものであり、関数内で作成され、その関数が終了する前に使用されなくなるため、ヒープに割り当てる必要はありません。このようなケースでは、ヒープ割り当ては不要なオーバーヘッドとなり、GCの頻度と時間を増加させていました。

このコミットの目的は、`make(map)`で作成されるマップに対してもエスケープ解析を適用し、エスケープしないマップをスタックに割り当てることで、メモリ使用量を最適化し、全体的なパフォーマンスを向上させることにありました。コミットメッセージには、標準ライブラリ内に75ものエスケープしないマップのケースがあることが示されており、この最適化が広範囲にわたる影響を持つことが示唆されています。

## 前提知識の解説

### 1. エスケープ解析 (Escape Analysis)

エスケープ解析は、コンパイラ最適化の一種で、プログラム内の変数がその宣言されたスコープ（通常は関数）の外で参照される可能性があるかどうかを判断します。

*   **スタック割り当て**: 変数がスコープ外にエスケープしないと判断された場合、その変数はスタックに割り当てられます。スタック割り当ては非常に高速で、関数の終了時に自動的にメモリが解放されるため、ガベージコレクションの対象になりません。
*   **ヒープ割り当て**: 変数がスコープ外にエスケープする可能性がある場合（例: グローバル変数に代入される、ポインタが返されるなど）、その変数はヒープに割り当てられます。ヒープに割り当てられたメモリは、ガベージコレクタによって管理され、不要になった時点で回収されます。ヒープ割り当てとGCは、スタック割り当てに比べてオーバーヘッドが大きいです。

Goコンパイラは、このエスケープ解析を積極的に行い、可能な限りスタック割り当てを促進することで、パフォーマンスを向上させています。

### 2. Goのマップ (map) の内部構造

Goのマップはハッシュテーブルとして実装されており、その内部構造は`runtime.hmap`と`runtime.bmap`（バケット）という2つの主要な構造体で構成されています。

*   **`hmap`**: マップ全体のメタデータ（要素数、ハッシュ関数、バケットの数など）を保持する構造体です。マップのヘッダのようなものです。
*   **`bmap` (バケット)**: 実際のキーと値のペアを格納する配列です。各バケットは複数のキーと値を保持でき、オーバーフローした場合には別のバケットへのポインタを持ちます。

通常、`make(map)`が呼び出されると、`hmap`構造体と最初の`bmap`バケットはヒープに割り当てられます。マップが成長し、既存のバケットが満杯になると、新しいバケットがヒープに割り当てられ、既存のバケットからリンクされます。

### 3. `make(map)` 関数

Goでマップを作成する際には、組み込み関数`make`を使用します。
例: `m := make(map[string]int)`

この`make`関数は、コンパイル時に`runtime.makemap`というランタイム関数への呼び出しに変換されます。`runtime.makemap`は、マップの型情報と初期容量のヒントを受け取り、`hmap`構造体と初期バケットを割り当てて初期化し、その`hmap`へのポインタを返します。

このファイルは、Goコンパイラが認識する組み込み関数やランタイム関数のシグネチャを定義しています。`makemap`関数のシグネチャが変更されたのは、コンパイラがスタック上に割り当てた`hmap`とバケットのバッファをランタイムに渡せるようにするためです。`mapbuf`と`bucketbuf`という2つの新しいポインタ引数が追加され、これらがスタック上のメモリ領域を指すことになります。

### `src/cmd/gc/walk.c` の変更

このファイルは、コンパイラのASTウォークフェーズにおけるコード生成ロジックを含んでいます。
`OMAKEMAP`ケース（`make(map)`の処理）において、最も重要な変更は以下の部分です。

```go
		a = nodnil(); // hmap buffer
		r = nodnil(); // bucket buffer
		if(n->esc == EscNone) {
			// Allocate hmap buffer on stack.
			var = temp(hmap(t));
			a = nod(OAS, var, N); // zero temp
			typecheck(&a, Etop);
			*init = list(*init, a);
			a = nod(OADDR, var, N);

			// Allocate one bucket on stack.
			// Maximum key/value size is 128 bytes, larger objects
			// are stored with an indirection. So max bucket size is 2048+eps.
			var = temp(mapbucket(t));
			r = nod(OAS, var, N); // zero temp
			typecheck(&r, Etop);
			*init = list(*init, r);
			r = nod(OADDR, var, N);
		}

		argtype(fn, hmap(t));	// hmap buffer
		argtype(fn, mapbucket(t));	// bucket buffer
		argtype(fn, t->down);	// key type
		argtype(fn, t->type);	// value type
		n = mkcall1(fn, n->type, init, typename(n->type), conv(n->left, types[TINT64]), a, r);
```

*   `if(n->esc == EscNone)`: ここがエスケープ解析の結果を利用する分岐点です。`n->esc == EscNone`は、現在の`make(map)`の呼び出しによって作成されるマップが、関数スコープ外にエスケープしないとコンパイラが判断した場合に真となります。
*   `var = temp(hmap(t));` と `var = temp(mapbucket(t));`: エスケープしない場合、コンパイラは`hmap`構造体と最初のバケットのためのメモリをスタック上に一時変数として割り当てます。`temp()`関数は、指定された型の新しい一時変数を生成します。
*   `a = nod(OADDR, var, N);` と `r = nod(OADDR, var, N);`: スタック上に割り当てられた一時変数のアドレスを取得し、それぞれ`a`と`r`に格納します。これらが`makemap`関数に渡される`mapbuf`と`bucketbuf`引数になります。
*   `mkcall1(...)`: 最終的に、`makemap`ランタイム関数への呼び出しが生成されます。この呼び出しには、マップの型情報、初期容量のヒントに加えて、スタック上に割り当てられた`hmap`とバケットのバッファのアドレス（`a`と`r`）が渡されます。

### `src/runtime/hashmap.go` の変更

このファイルは、Goのマップのランタイム実装を含んでいます。`makemap`関数の変更は、コンパイラからの新しい引数`h`と`bucket`を処理するように拡張されました。

```go
func makemap(t *maptype, hint int64, h *hmap, bucket unsafe.Pointer) *hmap {
    // ... (既存のサイズチェックなど)

    buckets := bucket // コンパイラからバケットが提供された場合、それを使用
    if B != 0 {
        // ... (バケットの初期化ロジック)
    }

    if h == nil { // コンパイラからhmapが提供されていない場合のみ、ヒープに割り当て
        h = (*hmap)(newobject(t.hmap))
    }
    // ... (hmapの初期化ロジック)
    return h
}
```

*   `buckets := bucket`: `bucket`引数が`nil`でない場合（つまり、コンパイラがスタック上のバケットバッファを提供した場合）、`buckets`変数はそのスタック上のバッファを指すようになります。これにより、ヒープに新しいバケットを割り当てる必要がなくなります。
*   `if h == nil { h = (*hmap)(newobject(t.hmap)) }`: `h`引数が`nil`でない場合（つまり、コンパイラがスタック上の`hmap`バッファを提供した場合）、`newobject(t.hmap)`を呼び出してヒープに`hmap`を割り当てる処理がスキップされます。代わりに、提供されたスタック上の`hmap`バッファが直接使用されます。

これらの変更により、エスケープ解析によってスタック割り当てが可能と判断されたマップは、ヒープ割り当てを完全に回避し、スタック上で効率的に初期化されるようになります。

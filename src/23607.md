# [インデックス 23607] ファイルの概要

このコミットは、Goランタイムの `runtime.GC()` 関数のドキュメントを更新し、ガベージコレクションが完了するまでブロックすることを明記するものです。これにより、特にガベージコレクションの動作に敏感なテストにおいて、`runtime.GC()` の同期的な性質が明確にされ、誤解を防ぐことを目的としています。

    runtime: document that runtime.GC() blocks until GC is complete
    
    runtime.GC() is intentionally very weakly specified. However, it is so
    weakly specified that it's difficult to know that it's being used
    correctly for its one intended use case: to ensure garbage collection
    has run in a test that is garbage-sensitive. In particular, it is
    unclear whether it is synchronous or asynchronous. In the old STW
    collector this was essentially self-evident; short of queuing up a
    garbage collection to run later, it had to be synchronous. However,
    with the concurrent collector, there's evidence that people are
    inferring that it may be asynchronous (e.g., issue #10986), as this is
    both unclear in the documentation and possible in the implementation.
    
    In fact, runtime.GC() runs a fully synchronous STW collection. We
    probably don't want to commit to this exact behavior. But we can
    commit to the essential property that tests rely on: that runtime.GC()
    does not return until the GC has finished.

## 元コミット内容

`runtime: document that runtime.GC() blocks until GC is complete`

`runtime.GC()` は意図的に非常に緩く仕様が定義されています。しかし、その仕様が非常に緩いため、ガベージコレクションに敏感なテストでガベージコレクションが実行されたことを確認するという、唯一の意図されたユースケースで正しく使用されているかを知るのが困難でした。特に、それが同期的に動作するのか非同期的に動作するのかが不明確でした。古いSTW (Stop-The-World) コレクタでは、これは本質的に自明でした。ガベージコレクションを後で実行するためにキューに入れる以外に、同期的に動作するしかありませんでした。しかし、並行コレクタの導入により、ドキュメントが不明確であり、実装上も可能であるため、非同期であると推測する人々がいるという証拠がありました（例：issue #10986）。

実際には、`runtime.GC()` は完全に同期的なSTWコレクションを実行します。この正確な動作にコミットしたくはないかもしれませんが、テストが依存する本質的な特性、つまり `runtime.GC()` がGCの完了まで戻らないという特性にはコミットできます。

## 変更の背景

Goの `runtime.GC()` 関数は、プログラムから明示的にガベージコレクションをトリガーするための手段を提供します。しかし、その動作、特に呼び出し元がガベージコレクションの完了を待つのか、それとも非同期的に実行されるのかについては、ドキュメントが不明確でした。

この曖昧さは、Goのガベージコレクタが進化するにつれて顕著になりました。初期のGoランタイムでは、ガベージコレクタは「Stop-The-World (STW)」方式を採用していました。これは、ガベージコレクションが実行されている間、プログラムの実行が完全に停止することを意味します。このモデルでは、`runtime.GC()` を呼び出すと、ガベージコレクションが完了するまでプログラムが停止するため、その動作は本質的に同期であると理解されていました。

しかし、Go 1.5以降で導入された並行ガベージコレクタは、プログラムの実行と並行してガベージコレクションの大部分を実行します。これにより、STWポーズの時間が大幅に短縮され、アプリケーションのレイテンシが改善されました。この新しいモデルでは、`runtime.GC()` が呼び出されたときに、ガベージコレクションのプロセスがバックグラウンドで開始され、関数がすぐに戻る（非同期動作）可能性も考えられるようになりました。

このような状況下で、特にガベージコレクションのタイミングやメモリ使用量に敏感なテストを書く開発者にとって、`runtime.GC()` が同期的に完了を待つのか、非同期的に実行されるのかは非常に重要な情報でした。もし非同期であれば、`runtime.GC()` の呼び出し直後にメモリの状態をチェックしても、ガベージコレクションがまだ完了していないため、期待する結果が得られない可能性がありました。コミットメッセージで言及されている `issue #10986` は、この混乱と、開発者が `runtime.GC()` の非同期動作を推測している状況を示唆しています。

このコミットは、このような混乱を解消し、`runtime.GC()` のドキュメントに「ガベージコレクションが完了するまでブロックする」という明確な記述を追加することで、開発者がこの関数を正しく、意図したとおりに使用できるようにすることを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC)

Go言語は、メモリ管理のために自動ガベージコレクションを採用しています。開発者は手動でメモリを解放する必要がなく、ランタイムが不要になったオブジェクトを自動的に回収します。

*   **Stop-The-World (STW) GC**: Goの初期バージョンで採用されていた方式です。ガベージコレクションが実行される間、プログラムのすべてのゴルーチン（スレッド）が一時停止します。これにより、GCの処理中はアプリケーションが応答しなくなり、レイテンシが発生する可能性があります。`runtime.GC()` が呼び出された場合、このSTWフェーズが完了するまで関数は戻りませんでした。

*   **並行GC (Concurrent GC)**: Go 1.5で導入された新しいガベージコレクタは、STWポーズの時間を大幅に短縮するために、ガベージコレクションの大部分をプログラムの実行と並行して行います。これにより、アプリケーションの応答性が向上し、レイテンシが低減されます。並行GCは、マークフェーズとスイープフェーズの一部をアプリケーションの実行と並行して行い、STWポーズは非常に短い期間に限定されます。

### `runtime.GC()` 関数

`runtime.GC()` は、Goプログラムから明示的にガベージコレクションを要求するための関数です。通常、Goランタイムはヒープの使用量や割り当てレートに基づいて自動的にGCを実行しますが、特定のシナリオ（例：ベンチマーク、メモリリークテスト、特定のメモリ最適化）では、開発者がGCのタイミングを制御したい場合があります。

この関数は、主にテストやベンチマークのシナリオで利用されます。例えば、メモリリークを検出するテストでは、`runtime.GC()` を呼び出して不要なオブジェクトが確実に回収されたことを確認し、その後に残存するメモリ使用量を測定することが一般的です。

## 技術的詳細

このコミットの技術的な核心は、`runtime.GC()` のドキュメントに「ガベージコレクションが完了するまでブロックする」という一文を追加したことです。これは、関数の実装そのものを変更するものではなく、その外部から見た振る舞いに関する保証を明確にするものです。

コミットメッセージでは、`runtime.GC()` が「完全に同期的なSTWコレクションを実行する」と述べられています。これは、並行GCが導入された後でも、`runtime.GC()` が呼び出された際には、ランタイムが一時的にSTWモードに切り替わり、ガベージコレクションの全プロセスが完了するまで呼び出し元のゴルーチンをブロックすることを意味します。この動作は、特にテストの文脈で重要です。

*   **テストの信頼性向上**: ガベージコレクションの完了を待つことが保証されるため、`runtime.GC()` の呼び出し直後にメモリの状態やオブジェクトの数をチェックするテストは、より信頼性の高い結果を得ることができます。非同期的な動作の場合、テストがGCの完了を待たずに次のアサーションに進んでしまい、誤った結果を報告する可能性がありました。
*   **意図の明確化**: 開発者は、`runtime.GC()` を呼び出した場合、その呼び出しが戻った時点ではガベージコレクションが確実に完了していると安心して仮定できるようになります。これにより、関数の使用方法に関する推測や誤解がなくなります。
*   **実装の柔軟性**: コミットメッセージでは「この正確な動作にコミットしたくはないかもしれない」と述べられています。これは、将来的に `runtime.GC()` の内部実装が変更され、必ずしも「完全に同期的なSTWコレクション」を実行しなくなる可能性を示唆しています。しかし、外部から見た「GCが完了するまでブロックする」という保証は維持されるべきである、という方針が示されています。これにより、ランタイム開発者は将来のGCアルゴリズムの改善において、この外部仕様を維持しつつ、内部実装を最適化する自由度を保つことができます。

要するに、この変更は、`runtime.GC()` の「契約」を明確にし、特にテストの文脈でのその信頼性と予測可能性を高めるものです。

## コアとなるコードの解説

変更は `src/runtime/mgc.go` ファイルの `GC()` 関数のコメント部分にあります。

*   **変更前**:
    ```go
    // GC runs a garbage collection.
    ```
    これは非常に簡潔で、`GC()` がガベージコレクションを実行することだけを述べています。同期性については言及されていません。

*   **変更後**:
    ```go
    // GC runs a garbage collection and blocks until the garbage
    // collection is complete.
    ```
    この変更により、「`and blocks until the garbage collection is complete.`」（そして、ガベージコレクションが完了するまでブロックする）という重要な一文が追加されました。この追記によって、`runtime.GC()` が呼び出された場合、その関数が戻るまでにはガベージコレクションのプロセスが完全に終了していることが明確に保証されます。

この変更はコードの動作自体には影響を与えませんが、関数のセマンティクスに関するドキュメントを改善し、開発者がその動作を正確に理解できるようにします。特に、並行GCの導入によって生じた同期性に関する曖昧さを解消する上で極めて重要です。

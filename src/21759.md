# [インデックス 21759] ファイルの概要

このコミットは、Goランタイムにおけるスタックフレームの処理、特に保存されたフレームポインタの検出に関する問題を修正するものです。以前は、スタックポインタ間のギャップを計算する際に、ポインタサイズ (`ptrSize`) を誤って使用していましたが、これをレジスタサイズ (`regSize`) に修正することで、`amd64p32` アーキテクチャ（Native Clientで使用）での不正確な動作を解消しました。

## 元コミット内容

```
runtime: use 2*regSize for saved frame pointer check

Previously, we checked for a saved frame pointer by looking for a
2*ptrSize gap between the argument pointer and the locals pointer.
The intent of this check was to look for a two stack slot gap (caller
IP and saved frame pointer), but stack slots are regSize, not ptrSize.

Correct this by checking instead for a 2*regSize gap.

On most platforms, this made no difference because ptrSize==regSize.
However, on amd64p32 (nacl), the saved frame pointer check incorrectly
fired when there was no saved frame pointer because the one stack slot
for the caller IP left an 8 byte gap, which is 2*ptrSize (but not
2*regSize) on amd64p32.

Fixes #9760.

Change-Id: I6eedcf681fe5bf2bf924dde8a8f2d9860a4d758e
Reviewed-on: https://go-review.googlesource.com/3781
Reviewed-by: Brad Fitzpatrick <bradfitz@golang.org>
```

## 変更の背景

Goランタイムは、関数の呼び出し規約やスタックフレームの管理において、効率的かつ正確な動作を保証する必要があります。このコミットは、特にスタックフレーム内の「保存されたフレームポインタ (saved frame pointer)」の検出ロジックにおけるバグを修正するものです。

従来のGoランタイムでは、スタックフレーム内に保存されたフレームポインタが存在するかどうかを判断する際に、引数ポインタ (`frame.argp`) とローカル変数ポインタ (`frame.varp`) の間のギャップが `2 * ptrSize` (ポインタサイズ) であるかどうかをチェックしていました。このチェックの意図は、呼び出し元の命令ポインタ (caller IP) と保存されたフレームポインタの2つのスタックスロット分のギャップを検出することでした。

しかし、問題は「スタックスロットのサイズ」が `ptrSize` ではなく `regSize` (レジスタサイズ) であるという点にありました。ほとんどのプラットフォームでは `ptrSize` と `regSize` が同じ値であるため、この誤りは表面化しませんでした。例えば、一般的な64ビットシステムではポインタもレジスタも8バイトであるため、`ptrSize == regSize` となり、`2 * ptrSize` と `2 * regSize` は同じ結果をもたらします。

ところが、`amd64p32` (Native Client, NaCl) 環境ではこの前提が崩れます。`amd64p32` は64ビットのAMD64アーキテクチャ上で動作しますが、ポインタサイズが32ビット（4バイト）に制限されています。一方で、レジスタサイズは64ビット（8バイト）です。このため、`ptrSize` は4バイト、`regSize` は8バイトとなります。

この差異により、`amd64p32` 環境では、呼び出し元の命令ポインタのための1つのスタックスロット（8バイト、つまり `1 * regSize`）が存在するだけで、`2 * ptrSize` (2 * 4バイト = 8バイト) のギャップが生じてしまいました。これにより、実際には保存されたフレームポインタが存在しないにもかかわらず、ランタイムが誤って存在すると判断し、不正な動作を引き起こす可能性がありました。

このコミットは、この `amd64p32` 環境での誤検出を修正し、スタックフレームの解析をより堅牢にするために行われました。

## 前提知識の解説

### ポインタサイズ (`ptrSize`) とレジスタサイズ (`regSize`)

*   **`ptrSize` (Pointer Size)**: システムのポインタのサイズをバイト単位で表します。これは、メモリ上のアドレスを指すために必要なバイト数です。例えば、32ビットシステムでは4バイト、64ビットシステムでは8バイトが一般的です。Goランタイムでは、`goarch.PtrSize` として定義され、ターゲットアーキテクチャに依存します。
*   **`regSize` (Register Size)**: CPUの汎用レジスタのサイズをバイト単位で表します。これは、CPUが一度に処理できるデータの基本的な単位であり、スタック上のスロットのサイズにも影響します。多くのアーキテクチャでは `ptrSize` と `regSize` は同じですが、`amd64p32` のように異なる場合もあります。このコミットの文脈では、スタック上のスロットのサイズが `regSize` に対応するという点が重要です。

### スタックフレームとフレームポインタ

関数が呼び出されると、その関数に必要な情報（引数、ローカル変数、呼び出し元の情報など）を格納するためにスタック上に「スタックフレーム」が作成されます。

*   **スタックポインタ (Stack Pointer, SP)**: 現在のスタックの最上位（または最下位、アーキテクチャによる）を指すレジスタです。
*   **フレームポインタ (Frame Pointer, FP)**: 現在のスタックフレームの特定の固定位置（通常はフレームの開始点）を指すレジスタです。フレームポインタを使用することで、スタックポインタが変動しても、ローカル変数や引数に相対アドレスでアクセスできます。
*   **保存されたフレームポインタ (Saved Frame Pointer)**: 関数が呼び出された際に、呼び出し元の関数のフレームポインタの値を現在のスタックフレーム内に保存することがあります。これにより、関数からのリターン時に呼び出し元のスタックフレームを正確に復元できます。
*   **呼び出し元の命令ポインタ (Caller IP)**: 関数が呼び出された後、呼び出し元に戻るべき命令のアドレス（リターンアドレス）です。これもスタックフレーム内に保存されます。

### `amd64p32` (Native Client, NaCl)

*   **`amd64p32`**: 64ビットのAMD64 (x86-64) プロセッサアーキテクチャ上で、ポインタが32ビット（4バイト）に制限されたモードを指します。これにより、64ビットのレジスタや命令セットの利点を活用しつつ、メモリフットプリントを小さく保つことができます。
*   **Native Client (NaCl)**: Googleが開発したサンドボックス技術で、ウェブブラウザ内でネイティブコード（x86, ARM, MIPSなど）を安全に実行できるようにするものでした。これにより、ウェブアプリケーションがほぼネイティブの速度で動作することが可能になりました。Go言語はかつて `nacl/amd64p32` をコンパイルターゲットとしてサポートしていました。現在ではWebAssemblyに大部分が置き換えられ、NaCl自体のサポートは終了しています。

### `stkframe` 構造体と `argp`, `varp`

Goランタイムのスタックトレースやスタックフレームの解析において、`stkframe` 構造体は個々のスタックフレームの情報を表現します。

*   **`frame.argp` (Argument Pointer)**: 現在のスタックフレームにおける引数の開始位置を指すポインタです。
*   **`frame.varp` (Variable Pointer)**: 現在のスタックフレームにおけるローカル変数の開始位置を指すポインタです。

通常、スタックは高アドレスから低アドレスに向かって成長します。そのため、`frame.argp` は `frame.varp` よりも高アドレス側に位置し、`frame.argp - frame.varp` は引数とローカル変数の間のギャップ、またはスタックフレーム内の特定の領域のサイズを示します。このギャップには、呼び出し元の命令ポインタや保存されたフレームポインタなどが含まれることがあります。

## 技術的詳細

このコミットの核心は、スタックフレーム内のギャップの計算に使用される単位の修正です。

Goランタイムは、スタックフレームをウォーク（辿る）して、各関数の呼び出し元やローカル変数の状態を把握します。このプロセスにおいて、フレームポインタが保存されているかどうかを正確に検出することは、スタックトレースの正確性やガベージコレクションの正確なポインタスキャンにとって非常に重要です。

以前の実装では、`src/runtime/stack1.go` 内で、保存されたベースポインタ（フレームポインタ）が存在するかどうかを判断するために、`frame.argp - frame.varp == 2 * ptrSize` という条件を使用していました。この `2 * ptrSize` は、「呼び出し元の命令ポインタ (caller IP)」と「保存されたフレームポインタ」の2つのスタックスロット分の領域を想定していました。

しかし、スタック上の各スロットのサイズは、ポインタのサイズ (`ptrSize`) ではなく、CPUのレジスタのサイズ (`regSize`) に合わせてアラインされるのが一般的です。

*   **一般的な64ビットシステム**: `ptrSize` (8バイト) と `regSize` (8バイト) が等しいため、`2 * ptrSize` (16バイト) と `2 * regSize` (16バイト) は同じ値になります。このため、ほとんどのプラットフォームではこの誤りは問題になりませんでした。
*   **`amd64p32` (NaCl) システム**: ここで問題が発生します。
    *   `ptrSize` は32ビット、つまり4バイトです。
    *   `regSize` は64ビット、つまり8バイトです。
    この場合、`2 * ptrSize` は `2 * 4 = 8バイト` となります。一方、`2 * regSize` は `2 * 8 = 16バイト` です。
    `amd64p32` では、呼び出し元の命令ポインタ (caller IP) のために1つのスタックスロット（8バイト）が確保されます。この8バイトのギャップは、`2 * ptrSize` (8バイト) と一致してしまいます。その結果、実際には保存されたフレームポインタが存在しないにもかかわらず、ランタイムが「`2 * ptrSize` のギャップがあるから、保存されたフレームポインタが存在する」と誤って判断してしまいました。

このコミットは、この誤りを修正し、チェックを `2 * regSize` に変更することで、スタックスロットの実際のサイズに合わせた正確な判断を可能にしました。これにより、`amd64p32` 環境での誤検出が解消され、スタックフレームの解析が正しく行われるようになります。

また、`src/runtime/traceback.go` においても、`frame.varp` の調整で `ptrSize` を減算していた箇所が `regSize` に変更されています。これは、スタックフレーム内のポインタやレジスタのオフセット計算が、`regSize` を基準に行われるべきであることを示しています。

## コアとなるコードの解説

### `src/runtime/stack1.go` の変更

`adjustframe` 関数は、スタックフレームを調整し、特に保存されたベースポインタ（フレームポインタ）の有無をチェックする役割を担っています。

変更前:
```go
if thechar == '6' && frame.argp-frame.varp == 2*ptrSize {
```
この行は、アーキテクチャが `amd64` (Goの内部表現で `'6'`) であり、かつ `frame.argp` と `frame.varp` の間のギャップが `2 * ptrSize` に等しい場合に、保存されたベースポインタが存在すると判断していました。前述の通り、`amd64p32` 環境では `ptrSize` が4バイトであるため、`2 * ptrSize` は8バイトとなり、呼び出し元の命令ポインタのみが存在する場合でも誤検出が発生していました。

変更後:
```go
if thechar == '6' && frame.argp-frame.varp == 2*regSize {
```
この変更により、ギャップのチェックが `2 * regSize` に修正されました。`regSize` はレジスタのサイズであり、スタックスロットの実際のサイズを反映しています。`amd64p32` では `regSize` が8バイトであるため、`2 * regSize` は16バイトとなります。これにより、呼び出し元の命令ポインタ（8バイト）のみが存在する場合にはこの条件が満たされなくなり、誤検出が解消されます。

また、デバッグ目的で `print("argp=", hex(frame.argp), " varp=", hex(frame.varp), "\n")` という行が追加されています。これは、`framepointer_enabled` が無効な状態で誤って保存されたベースポインタのスペースが検出された場合に、`argp` と `varp` の値を出力してデバッグを容易にするためのものです。

### `src/runtime/traceback.go` の変更

`gentraceback` 関数は、Goルーチンのスタックトレースを生成する際に使用されます。この関数内で、スタックフレームの `frame.varp` を調整するロジックがあります。

変更前:
```go
if GOARCH == "amd64" && frame.varp > frame.sp && framepointer_enabled {
	frame.varp -= ptrSize
}
```
このコードは、`amd64` アーキテクチャでフレームポインタが有効な場合に、`frame.varp` を `ptrSize` 分だけ減算していました。これは、スタックフレーム内の特定の要素（例えば、保存されたフレームポインタ）のサイズを考慮して `varp` を調整するためのものです。

変更後:
```go
if GOARCH == "amd64" && frame.varp > frame.sp && framepointer_enabled {
	frame.varp -= regSize
}
```
この変更により、`frame.varp` の調整量が `ptrSize` から `regSize` に変更されました。これは、スタックフレーム内の要素のサイズが `regSize` に基づいているという認識に基づいています。特に `amd64p32` のように `ptrSize` と `regSize` が異なる環境では、この修正がスタックフレームの正確な解析に不可欠です。

これらの変更は、Goランタイムが異なるアーキテクチャ、特にポインタサイズとレジスタサイズが異なる特殊な環境においても、スタックフレームを正確に解析し、堅牢な動作を保証するために重要です。

## 変更の背景

Goのガベージコレクタは、ヒープの使用量に基づいて次のGCサイクルを開始するタイミングを決定します。この決定には、`GOGC`環境変数または`runtime/debug.SetGCPercent`関数で設定されるGCパーセント（`gcpercent`）が重要な役割を果たします。`gcpercent`は、前回のGC後にライブであったオブジェクトの量に対して、どれだけの新しいメモリを割り当てたら次のGCを開始するかを制御します。例えば、`GOGC=100`（デフォルト）の場合、ライブオブジェクトの量が倍になったらGCが開始されます。

しかし、`runtime/debug.SetGCPercent`を使って実行時に`gcpercent`の値を下げた場合、その変更がすぐにGCの動作に反映されないという問題がありました。具体的には、GCコントローラが内部的に持つ`triggerRatio`という値が、`SetGCPercent`の呼び出し時に即座に更新されず、次のGCサイクルが完了するまで古い値のままになっていました。このため、`gcpercent`を下げてGCをより頻繁に実行させたい場合でも、その効果が1サイクル遅れて現れるという非効率性がありました。

このコミットは、この遅延を解消し、`SetGCPercent`による`gcpercent`の変更が即座にGCのトリガーロジックに反映されるようにすることを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goのガベージコレクタは、並行（concurrent）、非世代別（non-generational）、三色マーク＆スイープ（tri-color mark-and-sweep）方式を採用しています。これは、プログラムの実行と並行してGCが動作し、アプリケーションの一時停止（STW: Stop-The-World）時間を最小限に抑えるように設計されています。

### GOGCとGCパーセント (`gcpercent`)

-   **`GOGC`**: Goプログラムのガベージコレクションの頻度を制御する環境変数です。デフォルト値は`100`です。
-   **`gcpercent`**: `GOGC`によって設定される値で、前回のGCで生き残った（ライブな）オブジェクトのヒープサイズに対して、どれだけの追加メモリが割り当てられたら次のGCサイクルを開始するかをパーセンテージで指定します。
    -   `GOGC=100`の場合、ライブヒープが100%増加（つまり2倍）するとGCがトリガーされます。
    -   `GOGC=50`の場合、ライブヒープが50%増加するとGCがトリガーされます。
    -   `GOGC < 100`に設定するとGCがより頻繁に実行され、メモリ使用量は抑えられますが、GCのオーバーヘッドが増加する可能性があります。
    -   `GOGC > 100`に設定するとGCの頻度が減り、スループットが向上する可能性がありますが、メモリ使用量が増加する可能性があります。
    -   `GOGC=off`または`GOGC=-1`はGCを無効にします（ただし、これは推奨されません）。

### `runtime/debug.SetGCPercent`

この関数は、プログラムの実行中に`gcpercent`の値を動的に変更するために使用されます。これにより、アプリケーションの特定のフェーズでGCの動作を調整することが可能になります。

### `triggerRatio`

GoのGCコントローラは、次のGCサイクルを開始するタイミングを決定するために、内部的に`triggerRatio`という値を使用します。この`triggerRatio`は、`gcpercent`に基づいて計算され、ヒープの成長率を監視します。具体的には、前回のGC後のライブヒープサイズに`triggerRatio`を乗じた値が、次のGCを開始する目標ヒープサイズとなります。

問題は、`SetGCPercent`が呼び出されて`gcpercent`が変更されても、`triggerRatio`がすぐに新しい`gcpercent`を反映するように更新されなかった点にありました。`triggerRatio`は通常、GCサイクルが完了した後に再計算されます。

## 技術的詳細

このコミットが修正しようとしている問題は、`runtime/debug.SetGCPercent`関数が`gcpercent`の値を変更するものの、GCコントローラが使用する`triggerRatio`を即座に調整しないことに起因します。

GoのGCは、ヒープの成長を監視し、`gcpercent`に基づいて次のGCの目標ヒープサイズを決定します。この目標ヒープサイズは、`last_gc_live_heap_size * (1 + gcpercent / 100)` のような形で計算されます。内部的には、この `(1 + gcpercent / 100)` に相当する比率が`triggerRatio`として管理されています。

`SetGCPercent`が呼び出され、例えば`gcpercent`が`100`から`50`に引き下げられたとします。これは、GCをより頻繁に実行してメモリ使用量を抑えたいという意図を示します。しかし、`triggerRatio`が古い`gcpercent`（この例では`100`）に基づいて計算された値のままだと、GCコントローラは新しい`gcpercent`（`50`）を考慮せず、ヒープが古い基準（2倍）まで成長するのを待ち続けてしまいます。結果として、`gcpercent`の変更が実際にGCのトリガーに影響を与えるのは、次のGCサイクルが完了し、その際に`triggerRatio`が再計算されるまで待つ必要がありました。

このコミットは、`SetGCPercent`内で`gcpercent`が更新された直後に、`triggerRatio`も新しい`gcpercent`に基づいて調整されるようにすることで、この遅延を解消します。特に、`gcpercent`が引き下げられた場合（GCをより頻繁に実行したい場合）、`triggerRatio`もそれに応じて引き下げられ、GCがより早くトリガーされるようになります。これにより、`SetGCPercent`の呼び出しが即座にGCの動作に反映され、より予測可能で効率的なメモリ管理が可能になります。

## コアとなるコードの解説

変更は`setGCPercent`関数内に追加された3行です。

```go
	if gcController.triggerRatio > float64(gcpercent)/100 {
		gcController.triggerRatio = float64(gcpercent) / 100
	}
```

1.  `gcpercent = in`: この行の直前で、新しい`gcpercent`の値が`in`から`gcpercent`グローバル変数に設定されます。
2.  `heapminimum = defaultHeapMinimum * uint64(gcpercent) / 100`: この行では、新しい`gcpercent`に基づいてヒープの最小サイズが再計算されます。
3.  `if gcController.triggerRatio > float64(gcpercent)/100`:
    *   ここで、現在の`gcController.triggerRatio`が、新しい`gcpercent`から計算されるべき比率（`float64(gcpercent)/100`）よりも大きいかどうかをチェックします。
    *   `gcpercent`は、前回のGC後のライブヒープサイズに対してどれだけヒープが成長したら次のGCをトリガーするかをパーセンテージで示します。例えば、`gcpercent=100`なら`1.0`、`gcpercent=50`なら`0.5`となります。
    *   この条件は、主に`gcpercent`が以前の値よりも引き下げられた場合に真となります。`gcpercent`が引き上げられた場合、`triggerRatio`は現在の値よりも小さくなるため、この`if`ブロックは実行されません。これは、`triggerRatio`がGCサイクル終了時に自動的に調整されるため、`gcpercent`を上げる場合は即座の調整が不要、またはより保守的な（GCを遅らせる）動作が許容されるためと考えられます。
4.  `gcController.triggerRatio = float64(gcpercent) / 100`:
    *   もし上記の条件が真であれば、`gcController.triggerRatio`が新しい`gcpercent`に基づいて計算された値に即座に更新されます。
    *   これにより、`gcpercent`が引き下げられた場合でも、GCコントローラはすぐに新しい、より低いトリガー比率を使用するようになり、GCがより早く開始されるようになります。

この変更により、`runtime/debug.SetGCPercent`を呼び出して`gcpercent`を調整した際に、その変更がGCのトリガーロジックに即座に反映されるようになり、特にGCの頻度を上げたい場合の応答性が向上します。

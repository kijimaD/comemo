# [インデックス 27327] ファイルの概要

このコミットは、Go言語の`testing`パッケージにおける並列テスト実行の最大並列度（`maxParallelism`）が正しく機能していることを検証するための新しいテストケースを追加し、関連するバグを修正するものです。特に、`nacl/netbsd/plan9`といった特定の環境でデフォルトの最大並列度が1に設定されている場合に発生していた問題に対処しています。

## 変更の背景

Goの`testing`パッケージは、テストを並列実行する機能を提供します。これは、`go test -parallel N`コマンドラインオプションや、テストコード内で`t.Parallel()`メソッドを呼び出すことで制御されます。`maxParallelism`は、同時に実行される並列テストの最大数を制限する重要な設定です。

このコミットの背景には、リベース後に発生したと思われるバグが存在しました。このバグは、特に`nacl`、`netbsd`、`plan9`といった特定の環境で顕著でした。これらの環境では、デフォルトの`maxParallelism`が1に設定されていることが多く、並列実行が意図せず許可されてしまうと、テストの不安定性や誤った結果につながる可能性がありました。

バグの具体的な内容は、`testContext`構造体の`maxParallel`フィールドの初期化が正しく行われていなかったことに起因します。これにより、システムが設定された最大並列度を適切に尊重せず、指定された数以上のテストが同時に実行されてしまう可能性がありました。このコミットは、この初期化の問題を修正し、さらに`maxParallelism`が正しく機能していることを保証するための堅牢なテストケースを追加することで、この問題を解決しています。

## 前提知識の解説

### Goの`testing`パッケージ

Go言語には、標準ライブラリとして強力なテストフレームワークが組み込まれています。`testing`パッケージは、ユニットテスト、ベンチマークテスト、例（Example）テストなどを記述するための機能を提供します。

*   **`func TestXxx(t *testing.T)`**: テスト関数は`Test`で始まり、`*testing.T`型の引数を取ります。
*   **`t.Run(name string, f func(t *testing.T))`**: サブテストを定義するために使用されます。これにより、関連するテストをグループ化し、より詳細なテスト結果を得ることができます。
*   **`t.Parallel()`**: テスト関数内でこのメソッドを呼び出すと、そのテストは他の並列テストと同時に実行されるようにスケジュールされます。Goランタイムは、利用可能なCPUコア数や`go test -parallel`オプションで指定された値に基づいて、並列実行されるテストの数を調整します。

### `maxParallelism`

`maxParallelism`は、`go test`コマンドが同時に実行できる並列テストの最大数を制御する設定です。デフォルトでは、`GOMAXPROCS`の値（通常はCPUコア数）に設定されますが、`go test -parallel N`オプションで明示的に指定することもできます。この値は、テスト実行の効率とリソース消費のバランスを取るために重要です。

### `nacl/netbsd/plan9`環境

*   **`nacl` (Native Client)**: Google Chromeブラウザ内でネイティブコードを実行するためのサンドボックス技術。GoはかつてNaClをサポートしていましたが、現在は非推奨となっています。リソースが限られている環境であり、並列処理の挙動が他のシステムと異なる場合があります。
*   **`netbsd`**: BSD系のUNIXライクなオペレーティングシステム。
*   **`plan9`**: ベル研究所で開発された分散オペレーティングシステム。

これらの環境では、リソースの制約やOSのスケジューリング特性により、デフォルトの`maxParallelism`が1に設定されることが一般的です。これは、並列テストがこれらのシステムで予期せぬ問題を引き起こすのを防ぐためです。したがって、`maxParallelism`が1の場合でも、並列テストの制御が正しく機能することが極めて重要になります。

### `testContext`構造体

`testing`パッケージの内部では、`testContext`という構造体がテスト実行のコンテキストを管理しています。この構造体は、現在実行中の並列テストの数（`running`フィールド）や、許可される最大並列テスト数（`maxParallel`フィールド）などの情報を保持しています。`t.Parallel()`が呼び出されると、この`testContext`が更新され、並列実行のスケジューリングが行われます。

## 技術的詳細

このコミットの技術的詳細は、主に`testing`パッケージがどのように並列テストを管理し、`maxParallelism`の制約を強制するか、そしてその実装に潜んでいたバグをどのように修正したかに焦点を当てています。

### `t.Parallel()`の動作原理と`maxParallelism`の尊重

`t.Parallel()`がテスト関数内で呼び出されると、そのテストは現在のテストの実行を一時停止し、Goランタイムのテストスケジューラに制御を渡します。スケジューラは、`testContext`内の`running`カウンタと`maxParallel`の値を参照し、同時に実行できるテストの数が`maxParallel`を超えないように調整します。新しい並列テストが開始される準備が整うと、スケジューラはそれを実行キューに入れ、利用可能なゴルーチンで実行します。このメカニズムにより、システムのリソースを過剰に消費することなく、効率的な並列テストが可能になります。

### `testContext.running`と`testContext.maxParallel`

*   **`testContext.running`**: 現在アクティブに実行されている並列テストの数を追跡します。テストが`t.Parallel()`を呼び出して並列実行を開始するとインクリメントされ、テストが完了するとデクリメントされます。
*   **`testContext.maxParallel`**: `go test -parallel N`オプションで指定された、またはデフォルトで決定された最大並列テスト数を保持します。スケジューラはこの値を超えて`running`テストを許可しません。

### バグの内容と`maxParallel`の初期化

コミットメッセージによると、このバグは「リベース後に紛れ込んだ」ものであり、`testContext`の`maxParallel`フィールドの初期化に問題がありました。`src/testing/testing.go`の`newTestContext`関数は、`testContext`を初期化する役割を担っています。変更前のコードでは、`maxParallel`が`*parallel`というグローバル変数（またはパッケージレベル変数）から直接初期化されていました。しかし、何らかの理由でこの`*parallel`の値が、特定の環境（`nacl/netbsd/plan9`）で期待される`maxParallelism`の値（例えば1）を正しく反映していなかったか、あるいは初期化のタイミングやスコープの問題で、意図しない値が設定されてしまうことがありました。

このバグは、`maxParallelism`が1に設定されている環境で特に問題となりました。なぜなら、もし`maxParallel`が誤ってより大きな値に初期化されてしまうと、システムは複数のテストを並列で実行しようとし、リソースの競合やテストの失敗を引き起こすからです。

### 新しいテストケースの目的

`src/testing/sub_test.go`に追加された新しいテストケースは、このバグが修正されたことを検証し、将来的な回帰を防ぐことを目的としています。このテストは、意図的に多数のネストされた並列テストを起動し、`testContext.running`カウンタを監視することで、実際に同時に実行されているテストの最大数が`maxParallel`を超えないことを厳密にチェックします。これにより、`maxParallelism`の制約が、単純なケースだけでなく、複雑なテスト構造においても正しく適用されることが保証されます。

## コアとなるコードの解説

### `src/testing/sub_test.go`の新しいテストケース

この新しいテストケースは、`maxPar: 4`と設定されており、最大4つの並列テストが同時に実行されることを期待しています。テストのロジックは以下の通りです。

1.  **チャネルの初期化**: `in`と`out`という2つのチャネルが作成されます。これらは、並列テスト間の同期と、同時に実行されているテストの数を制御するために使用されます。
2.  **`testContext`の取得**: 現在のテストの`testContext`が`ctx := t.context`で取得されます。これにより、内部の`running`カウンタや`maxParallel`値にアクセスできます。
3.  **`controller`サブテスト**:
    *   いくつかのシーケンシャルなサブテスト（`seq1`, `seq2`, `seq3`）が実行されます。これらは`t.Parallel()`を呼び出さないため、`running`カウンタには影響しません。
    *   `t.Parallel()`が呼び出され、`controller`サブテスト自体が並列実行の対象となります。
    *   `for i := 0; i < 80; i++`ループ内で、`ctx.mu.Lock()`と`ctx.mu.Unlock()`を使って`ctx.running`（現在実行中の並列テスト数）を安全に読み取り、その最大値が`max`変数に記録されます。
    *   `<-in`で`in`チャネルからの受信を待ちます。これは、他の並列テストが開始されるのを待つための同期ポイントです。
    *   `if i >= ctx.maxParallel-2 { out <- i }`という条件で`out`チャネルに値を送信します。これは、`maxParallel`に達した後に、他のテストが進行できるようにするためのメカニズムです。
4.  **ネストされた並列テスト**:
    *   `for i := 0; i < 2; i++`と`for j := 0; j < 40; j++`の二重ループで、合計80個のネストされたサブテストが起動されます。
    *   これらのサブテストも`t.Parallel()`を呼び出し、並列実行されます。
    *   各ネストされたサブテストは、`in <- j`で`in`チャネルに値を送信し、`<-out`で`out`チャネルからの受信を待ちます。これにより、`controller`サブテストとこれらの並列サブテストの間で同期が取られ、同時に実行されるテストの数が`maxParallel`を超えないように制御されます。
5.  **検証**: テストの最後に、`if max != ctx.maxParallel`というアサーションが行われます。これは、`controller`サブテストが監視した`ctx.running`の最大値（`max`）が、`testContext`に設定されている`maxParallel`の値と一致することを確認します。これにより、システムが設定された最大並列度を正確に守っていることが検証されます。

このテストは、非常に巧妙に設計されており、多数の並列テストとネストされたサブテストを組み合わせることで、`maxParallelism`の制約が複雑なシナリオでも破られないことを保証しています。

### `src/testing/testing.go`の`newTestContext`関数の変更

```go
func newTestContext(maxParallel int) *testContext {
	return &testContext{
		startParallel: make(chan bool),
		maxParallel:   maxParallel, // 変更点: *parallel から maxParallel 引数へ
		running:       1,           // Set the count to 1 for the main (sequential) test.
	}
}
```

この変更は、バグ修正の核心部分です。

*   **変更前**: `maxParallel: *parallel,`
    *   `*parallel`は、`testing`パッケージ内で定義されているグローバルな（またはパッケージレベルの）変数であり、`go test -parallel N`オプションの値やデフォルト値が格納されます。バグは、この`*parallel`変数の値が、`newTestContext`が呼び出される時点で常に正しい`maxParallelism`を反映していなかったことに起因すると考えられます。特に、リベースなどのコード変更によって、この変数のライフサイクルや初期化のタイミングが影響を受けた可能性があります。
*   **変更後**: `maxParallel: maxParallel,`
    *   `newTestContext`関数が`maxParallel int`という引数を受け取るように変更され、その引数の値が直接`testContext`の`maxParallel`フィールドに割り当てられるようになりました。
    *   この変更により、`newTestContext`を呼び出す側が、正しい`maxParallelism`の値を明示的に渡すことが保証されます。これにより、`*parallel`変数の潜在的な初期化問題やスコープの問題が回避され、`testContext`が常に正しい最大並列度で初期化されるようになります。

この修正は、`maxParallel`の初期化をより堅牢にし、特定の環境でのバグの再発を防ぐ上で非常に重要です。

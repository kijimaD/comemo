# [インデックス 25772] ファイルの概要

このコミットは、Go言語のツールチェインにおいて、`linux/386` (32ビットx86アーキテクチャのLinux) 環境で `-buildmode=c-shared` オプションを有効にするための変更を導入します。これにより、GoのコードをC言語から呼び出し可能な共有ライブラリとしてコンパイルできるようになります。

## 変更の背景

Go言語は、その強力な並行処理モデルとシンプルな構文により、多くのシステムで利用されています。しかし、既存のC/C++ベースのシステムにGoの機能を組み込みたい場合、Goのコードを共有ライブラリ（`.so`や`.dll`など）としてエクスポートできる機能が不可欠です。Goのビルドモードの一つである `-buildmode=c-shared` は、まさにこの目的のために存在します。

このコミット以前は、`linux/386` 環境では `-buildmode=c-shared` がサポートされていませんでした。これは、特定のアーキテクチャやOSにおいて、共有ライブラリを生成するためのリンカの挙動やコード生成の要件（例えば、Position-Independent Code (PIC) の生成）が異なるためです。`linux/386` 環境でこの機能が利用できないことは、32ビットLinuxシステムでGoの共有ライブラリを利用したい開発者にとって制約となっていました。

この変更の背景には、Goのクロスプラットフォーム対応を強化し、より多くの環境でGoのコードを既存システムと連携できるようにするという目的があります。特に、32ビットシステムがまだ広く利用されている組み込みシステムやレガシーシステムにおいて、Goの共有ライブラリが利用可能になることで、Goの適用範囲が拡大します。コミットメッセージにある「All the heavy lifting was done by Michael Hudson-Doyle」という記述から、この機能の実装にはかなりの技術的労力が伴ったことが伺えます。

## 前提知識の解説

*   **`cmd/go`**: Go言語の公式コマンドラインツールです。ソースコードのコンパイル、テスト、パッケージ管理など、Go開発の主要なタスクを実行します。
*   **`cmd/link`**: Go言語のリンカです。コンパイラによって生成されたオブジェクトファイルを結合し、実行可能ファイルやライブラリを生成します。
*   **`-buildmode=c-shared`**: Goのビルドモードの一つで、GoのパッケージをC言語の呼び出し規約に準拠した共有ライブラリ（例: Linuxでは `.so` ファイル）としてコンパイルします。これにより、C/C++などの他の言語で書かれたプログラムからGoの関数を直接呼び出すことが可能になります。このモードでビルドされたライブラリは、Position-Independent Code (PIC) である必要があります。
*   **`linux/386`**: ターゲットとなるオペレーティングシステム (Linux) とアーキテクチャ (32ビットx86) の組み合わせを指します。Goの環境変数 `GOOS` と `GOARCH` で指定されます。
*   **Position-Independent Code (PIC)**: 共有ライブラリのコードがメモリ上のどこにロードされても正しく実行できるように生成されたコードのことです。共有ライブラリは複数のプロセスによって異なるアドレス空間にロードされる可能性があるため、PICは共有ライブラリの必須要件です。
*   **`DynlinkingGo()`**: Goのランタイムが動的リンクを使用しているかどうかを判定する内部関数です。
*   **`BuildmodePIE`**: Position-Independent Executable (PIE) ビルドモードを指します。PIEは、実行可能ファイル自体がメモリ上のどこにロードされても正しく実行できるように生成されたコードで、セキュリティ強化（ASLR: Address Space Layout Randomization）のために現代のOSで広く採用されています。
*   **`codegenArg = "-shared"`**: Goのコンパイラに渡される引数で、共有ライブラリの生成に関連するコード生成オプションを指定します。
*   **`codegenArg = "-fPIC"`**: GCCなどのCコンパイラに渡される引数で、Position-Independent Code (PIC) を生成するように指示します。Goのツールチェイン内部でCコンパイラを呼び出す際に使用されることがあります。

## 技術的詳細

このコミットは、主に以下の3つのファイルに対する変更を通じて、`linux/386` における `-buildmode=c-shared` のサポートを実現しています。

1.  **`src/cmd/go/build.go`**:
    `cmd/go` ツールがビルドモードに応じて適切なコンパイラフラグを決定する部分です。以前は `linux/386` が `-buildmode=c-shared` で必要な `-shared` フラグを必要とするプラットフォームのリストに含まれていませんでした。この変更により、`linux/386` がこのリストに追加され、Goコンパイラが共有ライブラリ生成に必要なコードを正しく生成するようになります。

2.  **`src/cmd/link/internal/ld/lib.go`**:
    Goリンカの主要なロジックが含まれるファイルです。
    *   `BuildMode.Set` メソッド内で、`-buildmode=c-shared` が指定された際に、どのアーキテクチャがサポートされているかをチェックする部分に `386` が追加されました。これにより、リンカが `linux/386` で `c-shared` モードを受け入れるようになります。
    *   `stkcheck` 関数は、スタックチェックに関連するロジックを含んでいます。共有ライブラリとしてビルドされる場合、通常の実行可能ファイルとは異なるリンキングの挙動やスタックフレームの管理が必要になることがあります。この変更では、`BuildmodeCShared` の場合にも特定のスタックチェックロジックが適用されないように条件が追加されています。これは、C-sharedライブラリが外部から呼び出される際のスタックフレームの扱いが、Goランタイムの通常のスタックチェックの想定と異なるためと考えられます。

3.  **`src/cmd/link/internal/x86/asm.go`**:
    x86アーキテクチャ向けのリンカのアセンブリコード生成に関連するファイルです。
    *   `gentext` 関数は、テキストセクション（コードセクション）の生成に関連するロジックを含んでいます。PIEや動的リンクを使用しない場合に特定の処理をスキップする条件に、`BuildmodeCShared` も追加されました。これは、`c-shared` モードでビルドされたコードが、PIEや通常の動的リンクとは異なる方法でテキストセクションを扱う必要があるため、または特定の最適化や処理が `c-shared` のコンテキストでは不要・不適切であるためと考えられます。

これらの変更は、`linux/386` 環境でGoのコードが共有ライブラリとして正しく機能するために必要な、コンパイラとリンカの挙動の調整を網羅しています。特に、PICの要件を満たし、C言語の呼び出し規約との互換性を確保するための低レベルな調整が含まれています。

この変更は、`buildModeInit` 関数内の `platform` スイッチケースに `linux/386` を追加しています。このセクションは、Goのビルドモードが `c-shared` の場合に、Goコンパイラに渡す `codegenArg` を決定します。`codegenArg = "-shared"` は、コンパイラが共有ライブラリに適したコードを生成するために必要なフラグです。`linux/386` がこのリストに追加されたことで、`cmd/go` ツールは `linux/386` 環境で `c-shared` モードを使用する際に、適切なコンパイラフラグを自動的に設定するようになります。これにより、Position-Independent Code (PIC) の生成が保証され、共有ライブラリとしての機能が実現されます。

1.  **`BuildMode.Set` メソッドの変更**:
    `c-shared` ビルドモードの処理において、以前は `amd64`, `arm`, `arm64` 以外のアーキテクチャではエラー (`badmode()`) を返していました。この変更では、`goarch` (Goアーキテクチャ) をチェックする `switch` ステートメントが導入され、`386` が明示的にサポートされるアーキテクチャのリストに追加されました。これにより、リンカは `linux/386` 環境で `-buildmode=c-shared` オプションが指定された際に、ビルドを続行できるようになります。

2.  **`stkcheck` 関数の変更**:
    `stkcheck` 関数は、Goランタイムのスタックフレームの整合性をチェックする役割を担っています。この変更では、特定の条件 (`depth == 1 && s.Type != obj.SXREF && !DynlinkingGo() && Buildmode != BuildmodePIE`) に加えて、`Buildmode != BuildmodeCShared` という条件が追加されました。これは、`c-shared` モードでビルドされたライブラリが外部のCコードから呼び出される場合、Goランタイムの通常のスタックチェックのロジックが適用できない、または不適切である可能性があるためです。共有ライブラリのコンテキストでは、スタックの管理方法が通常のGo実行可能ファイルとは異なるため、このチェックをスキップすることで、誤った診断を避け、正しい動作を保証します。

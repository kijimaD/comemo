# [インデックス 26274] ファイルの概要

このコミットは、Windows環境におけるGoランタイムの`externalthreadhandler`が想定するスタックサイズを8KBから32KBに増加させるものです。これにより、プロファイラースレッドなどがスタックオーバーフローを起こし、予期せぬクラッシュが発生する問題を解決します。また、リンカーによって設定される`SizeOfStackReserve`と`externalthreadhandler`が想定するスタックサイズとの関係性についてドキュメントを更新し、将来的な混乱を防ぐことを目的としています。

## 変更の背景
## 変更の背景

このコミットは、Windows環境におけるGoランタイムのスタック管理に関する重要な問題を解決するために導入されました。Goランタイムは、軽量なゴルーチンに対して動的なスタック拡張メカニズム（`morestack`）を提供しますが、OSが管理するスレッド、特にWindows上のスレッドは固定サイズのスタックを持ちます。

問題の核心は、Goランタイムが外部スレッド（プロファイラースレッドやCtrl+Cハンドラースレッドなど）上でGoコードを実行する際に使用する`externalthreadhandler`の挙動にありました。`externalthreadhandler`は、これらの外部スレッドのスタックをGoランタイムが認識し、スタックガードを設定するために、そのスタックサイズを「想定」します。しかし、これまでの実装では、この想定されるスタックサイズが8KBと非常に小さく設定されていました。

一方で、Windowsのリンカーによって実行可能ファイルに設定される`SizeOfStackReserve`フィールドは、OSがスレッドに予約する実際の仮想メモリスタックサイズを決定し、これは通常64KB、あるいは128KBと、`externalthreadhandler`が想定するサイズよりもはるかに大きいものでした。

この不一致により、プロファイラースレッドがGoコードを実行する際に、`externalthreadhandler`が設定した8KBのスタックガード境界に非常に近い場所で動作することが判明しました。プロファイラースレッドがこの8KBの境界を超えてスタックを使用しようとすると、Goランタイムの`morestack`ルーチンが呼び出されますが、この状況ではスタックガードの誤った設定が原因でアクセス違反が発生し、Goランタイムがこれを適切に処理できずにプロセス全体が説明なく終了するという深刻なクラッシュを引き起こしていました。

このコミットは、このクラッシュを回避し、外部スレッドに十分なスタック領域の余裕を与えるために、`externalthreadhandler`が想定するスタックサイズを8KBから32KBに増やすことを目的としています。また、将来的な同様の問題を防ぐため、`externalthreadhandler`と`SizeOfStackReserve`の関係性についてドキュメントを更新し、開発者がこれらの相互作用をより明確に理解できるようにしています。

## 前提知識の解説

このコミットの変更内容を深く理解するためには、以下の概念について把握しておく必要があります。

*   **Goのスタック管理と`morestack`:**
    Goのゴルーチンは、非常に軽量な実行単位であり、通常は2KBや8KBといった比較的小さなスタックサイズで開始します。Goランタイムは、必要に応じてこのスタックを動的に拡張するメカニズムを持っています。これが`morestack`ルーチンです。関数呼び出しなどによってスタックの使用量が増え、現在のスタック領域の終端（スタックガード）に近づくと、`morestack`が自動的に呼び出され、より大きなスタック領域が割り当てられ、古いスタックの内容が新しいスタックにコピーされます。この動的なスタック拡張は、メモリ効率を高め、数百万ものゴルーチンを同時に実行可能にするGoの重要な特徴の一つです。

*   **OSスレッドのスタックと`SizeOfStackReserve`:**
    Goのゴルーチンとは異なり、オペレーティングシステム（OS）が管理するスレッドは、通常、固定サイズのスタックを割り当てられます。Windowsの場合、実行可能ファイル（PEファイル）のヘッダーには`SizeOfStackReserve`というフィールドがあり、これはリンカーによって設定されます。この値は、OSがスレッドの作成時にそのスレッドに予約する仮想メモリのスタックサイズを決定します。予約されたスタック領域は、実際にコミットされる（物理メモリが割り当てられる）のは必要になったときだけですが、その最大サイズは`SizeOfStackReserve`によって制限されます。

*   **`externalthreadhandler`:**
    Goランタイムは、Goスケジューラによって直接管理されるゴルーチンだけでなく、外部のOSスレッド上でGoコードが実行されるシナリオも扱います。例えば、Windowsのプロファイラースレッドや、Ctrl+Cなどのシグナルを処理する`ctrlhandler`スレッドなどがこれに該当します。`externalthreadhandler`は、このような外部スレッドがGoコードを実行する際に、Goランタイムがそのスレッドのスタックを認識し、Goのスタックガードメカニズムを適切に設定するための初期化処理を行うハンドラです。これにより、外部スレッド上でもGoのスタック管理の一部が機能するようにします。

*   **スタックガード:**
    Goランタイムは、スタックオーバーフローを検出するために、スタックの現在の境界に「スタックガード」と呼ばれる保護領域を設定します。関数呼び出しなどによってスタックポインタがこのスタックガード領域に侵入しようとすると、ハードウェア割り込みやソフトウェアトラップが発生し、`morestack`ルーチンが呼び出されます。`morestack`は、スタックを拡張するか、あるいはスタックオーバーフローが実際に発生した場合にはパニックを引き起こします。このメカニズムは、スタックの安全な使用を保証するために不可欠です。

*   **アクセス違反 (Access Violation):**
    アクセス違反は、プログラムが許可されていないメモリ領域にアクセスしようとしたときにOSによって生成されるエラーです。このコミットのケースでは、`externalthreadhandler`が設定したスタックガードの境界が、OSが実際に割り当てたスタック領域よりもはるかに小さかったため、プロファイラースレッドがGoランタイムが想定するスタックサイズを超えてスタックを使用しようとした際に、OSが割り当てた実際のスタック領域内であっても、Goランタイムのスタックガードメカニズムが誤動作し、アクセス違反が発生しました。これは、Goランタイムが自身のスタック管理の前提とOSの実際のメモリ管理との間に齟齬があったために生じた問題です。

## 技術的詳細

このコミットの技術的な詳細を掘り下げると、GoランタイムがWindows上で外部スレッドのスタックをどのように扱っていたか、そしてその問題点がどこにあったかが明確になります。

1.  **`externalthreadhandler`の役割と問題点:**
    `externalthreadhandler`は、Goランタイムが管理していないOSスレッド（例: プロファイラースレッド、Ctrl+Cハンドラースレッド）がGoコードを実行する際に、そのスレッドのコンテキストをGoランタイムに適合させるための初期化を行います。この処理の一環として、Goランタイムは当該スレッドのスタック情報を取得し、`g`構造体（ゴルーチン記述子）に似た構造を構築して、スタックガードを設定します。
    問題は、この`externalthreadhandler`が、外部スレッドのスタックサイズを「8KB」と仮定してスタックガードを設定していた点にありました。これは、Goの通常のゴルーチンの初期スタックサイズに近い値です。

2.  **`SizeOfStackReserve`との不一致:**
    Windowsの実行可能ファイル（PEファイル）のヘッダーには`SizeOfStackReserve`というフィールドがあり、これはリンカーによって設定されます。Goのリンカーは、純粋なGoプログラムの場合、この値を通常64KB（0x10000バイト）または128KB（0x20000バイト）に設定します。これは、OSがスレッドに予約する仮想メモリのスタックサイズです。
    つまり、OSは外部スレッドに64KB以上のスタック領域を予約しているにもかかわらず、Goランタイムの`externalthreadhandler`は、そのうちのわずか8KBしか利用可能でないと「想定」し、その範囲内でスタックガードを設定していました。

3.  **`morestack`とアクセス違反の発生:**
    プロファイラースレッドのような外部スレッドがGoコードを実行し、スタック使用量が`externalthreadhandler`が設定した8KBのスタックガード境界に近づくと、Goランタイムはスタック拡張のために`morestack`ルーチンを呼び出そうとします。しかし、この8KBという想定が実際のOSスタックサイズと乖離しているため、`morestack`が呼び出されるべきではないタイミングで呼び出されたり、あるいはスタックガードのチェックが不適切に行われたりする可能性がありました。
    コミットメッセージによると、プロファイラースレッドは8KBのスタックガード境界の「数ワード以内」で動作しており、この境界を超えると「アクセス違反」で`morestack`がクラッシュし、Goランタイムがこれを処理できずにプロセス全体が終了していました。これは、Goランタイムが自身のスタック管理の前提とOSの実際のメモリ管理との間に齟齬があったために発生した、典型的なスタックオーバーフローに起因するクラッシュです。

4.  **解決策としてのスタックサイズ増加:**
    この問題を解決するため、コミットでは`externalthreadhandler`が想定するスタックサイズを8KBから32KBに増加させました。これにより、Goランタイムが設定するスタックガードの境界が広がり、プロファイラースレッドなどの外部スレッドがより多くのスタック領域を安全に利用できるようになります。
    ただし、コミットメッセージには「there's some unknown amount of stack already in use, so it's not safe to increase this all the way to the reserve size」とあるように、外部スレッドがGoコードを実行する前に既にどれだけのスタックを使用しているか不明なため、`SizeOfStackReserve`で予約されている最大サイズ（64KBや128KB）まで一気に増やすことはしていません。32KBという値は、既存の使用量と安全マージンを考慮した上で、クラッシュを回避するための十分な「余裕」を与えるために選ばれたと考えられます。

5.  **ドキュメントの更新:**
    `src/cmd/link/internal/ld/pe.go`の変更は、リンカーが設定する`SizeOfStackReserve`と、`externalthreadhandler`が想定するスタックサイズ、そしてCGOスレッドのスタックサイズ（`STACKSIZE`）との関係性を明確にするためのコメント追加です。これにより、将来的に同様のスタック関連の問題が発生した際に、開発者が原因を特定しやすくなります。特に、メインスレッド、`ctrlhandler`スレッド、`profileloop`スレッドの`SizeOfStackReserve`は、`externalthreadhandler`が想定するスタックサイズよりも大きくなくてはならないという点が強調されています。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下の3つのファイルで行われています。

1.  **`src/cmd/link/internal/ld/pe.go`**:
    *   WindowsのPE（Portable Executable）ファイル形式のリンカー設定に関するファイルです。
    *   `Asmbpe`関数内で、`SizeOfStackReserve`に関するコメントが更新されています。
    *   変更前:
        ```go
        // The default stack reserve size affects only the main thread,
        // for other threads we specify stack size in runtime explicitly
        // (runtime knows whether cgo is enabled or not).
        // If you change stack reserve sizes here,
        // change STACKSIZE in runtime/cgo/gcc_windows_{386,amd64}.c and correspondent
        // CreateThread parameter in runtime.newosproc as well.
        ```
    *   変更後:
        ```go
        // The default stack reserve size affects only the main
        // thread, ctrlhandler thread, and profileloop thread. For
        // these, it must be greater than the stack size assumed by
        // externalthreadhandler.
        //
        // For other threads we specify stack size in runtime explicitly
        // (runtime knows whether cgo is enabled or not).
        // For these, the reserve must match STACKSIZE in
        // runtime/cgo/gcc_windows_{386,amd64}.c and the correspondent
        // CreateThread parameter in runtime.newosproc.
        ```
    *   この変更は、`SizeOfStackReserve`が影響するスレッドの種類と、`externalthreadhandler`が想定するスタックサイズとの関係性、およびCGOスレッドのスタックサイズとの整合性について、より詳細かつ正確な情報を提供するものです。

2.  **`src/runtime/sys_windows_386.s`**:
    *   Windows/386アーキテクチャ向けのGoランタイムのアセンブリコードファイルです。
    *   `runtime·externalthreadhandler`関数内で、スタックサイズを設定する部分が変更されています。
    *   変更前:
        ```assembly
        LEAL	-8192(SP), CX
        ```
    *   変更後:
        ```assembly
        LEAL	-32768(SP), CX		// must be less than SizeOfStackReserve set by linker
        ```
    *   `LEAL`命令は、`SP`（スタックポインタ）から指定されたオフセットを計算し、そのアドレスを`CX`レジスタにロードします。ここでは、`externalthreadhandler`が外部スレッドのスタックの「下限」として想定するアドレスを計算しており、そのオフセットが8192バイト（8KB）から32768バイト（32KB）に増加しています。これにより、Goランタイムが外部スレッドに割り当てられたと「想定」するスタック領域が拡張されます。コメントも追加され、この値がリンカーによって設定される`SizeOfStackReserve`よりも小さくなければならないことが明記されています。

3.  **`src/runtime/sys_windows_amd64.s`**:
    *   Windows/AMD64アーキテクチャ向けのGoランタイムのアセンブリコードファイルです。
    *   `runtime·externalthreadhandler`関数内で、スタックサイズを設定する部分が変更されています。
    *   変更前:
        ```assembly
        LEAQ	-8192(SP), CX
        ```
    *   変更後:
        ```assembly
        LEAQ	-32768(SP), CX		// must be less than SizeOfStackReserve set by linker
        ```
    *   `LEAQ`命令は、AMD64アーキテクチャにおける`LEAL`に相当し、同様にスタックポインタからのオフセット計算を行います。ここでも、想定されるスタックサイズが8KBから32KBに増加し、同様のコメントが追加されています。

## コアとなるコードの解説

このコミットの核心は、`src/runtime/sys_windows_386.s`と`src/runtime/sys_windows_amd64.s`内の`runtime·externalthreadhandler`関数におけるスタックサイズの設定値の変更です。

具体的には、以下の行が変更されています。

**32-bit (sys_windows_386.s):**
```assembly
-	LEAL	-8192(SP), CX
+	LEAL	-32768(SP), CX		// must be less than SizeOfStackReserve set by linker
```

**64-bit (sys_windows_amd64.s):**
```assembly
-	LEAQ	-8192(SP), CX
+	LEAQ	-32768(SP), CX		// must be less than SizeOfStackReserve set by linker
```

ここで使用されている`LEAL` (Load Effective Address Long) および `LEAQ` (Load Effective Address Quad) 命令は、メモリから値をロードするのではなく、オペランドのアドレスを計算してレジスタに格納します。

*   `SP` (Stack Pointer) は現在のスタックポインタを指します。
*   `-8192(SP)` は、現在のスタックポインタから8192バイト（8KB）低いアドレスを意味します。
*   `-32768(SP)` は、現在のスタックポインタから32768バイト（32KB）低いアドレスを意味します。

この命令によって計算されたアドレスは`CX`レジスタに格納され、その後、`g_stack+stack_lo`（ゴルーチン構造体のスタック下限フィールド）に書き込まれます。これは、`externalthreadhandler`がGoランタイムに対して、この外部スレッドのスタックがどこからどこまでであるかを「教える」ための重要なステップです。

変更前は、Goランタイムは外部スレッドのスタックが現在の`SP`から8KB下までであると「想定」していました。この8KBの範囲内にスタックガードが設定され、この範囲を超えてスタックが使用されそうになると`morestack`が呼び出されるはずでした。しかし、前述の通り、プロファイラースレッドがこの8KBの境界に非常に近づき、それを超えようとした際にアクセス違反が発生していました。

変更後は、この想定されるスタックサイズが32KBに拡張されました。これにより、`externalthreadhandler`が設定するスタックガードの境界が広がり、プロファイラースレッドがより多くのスタック領域を安全に利用できるようになります。結果として、Goランタイムが設定したスタックガードに不必要に早く到達することなく、OSが実際に予約している大きなスタック領域をより有効に活用できるようになり、スタックオーバーフローによるクラッシュが回避されます。

追加されたコメント「`// must be less than SizeOfStackReserve set by linker`」は、この32KBという値が、リンカーによって設定される実際のOSスタック予約サイズ（`SizeOfStackReserve`）よりも小さくなければならないという重要な制約を明示しています。これは、Goランタイムが想定するスタックサイズが、OSが実際に提供するスタックサイズを超えてはならないという原則を示しており、将来的なスタック管理の調整において重要な指針となります。

`src/cmd/link/internal/ld/pe.go`のコメント変更は、このアセンブリコードの変更の意図と、`SizeOfStackReserve`、`externalthreadhandler`、そしてCGOスタックサイズとの複雑な相互作用を文書化することで、Go開発者がWindows上でのスタック管理の挙動をより正確に理解し、将来的なデバッグや変更を容易にすることを目的としています。

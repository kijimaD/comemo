# [インデックス 20207] ファイルの概要

このコミットは、GoランタイムがPlan 9オペレーティングシステム上で動作する際の`HeapSys`統計の計上に関するバグを修正するものです。具体的には、システムから確保されたヒープメモリの総量を示す`HeapSys`の値が、Plan 9のメモリ管理メカニズムとGoランタイムの連携において正しく更新されない問題を解決します。

## 変更の背景

Goランタイムは、プログラムが使用するメモリを効率的に管理するために、オペレーティングシステム（OS）からメモリを要求し、それをヒープとして利用します。この際、Goランタイムは様々なメモリ統計を追跡しており、その一つに`HeapSys`があります。`HeapSys`は、GoランタイムがOSから確保した仮想メモリの総量を示します。

Plan 9は、UnixライクなOSとは異なる独自のメモリ管理メカニズムを持っています。多くのOSでは`mmap`のようなシステムコールがメモリ確保に用いられますが、Plan 9では`brk`（または`sbrk`）に似たメカニズムがヒープ領域の拡張に利用されることがあります。

このコミット以前は、GoランタイムがPlan 9上でメモリを確保する際に、`HeapSys`統計が正確に計上されない問題がありました。これは、メモリ確保の低レベルな詳細と、Goランタイムが統計を更新するタイミングとの間に不整合があったためと考えられます。結果として、`HeapSys`の値が実際のOSからのメモリ確保量と一致せず、メモリ使用状況の監視やデバッグにおいて誤解を招く可能性がありました。このコミットは、この不正確な計上を修正し、`HeapSys`がPlan 9上でも正確な値を示すようにすることを目的としています。

## 前提知識の解説

### Goランタイムのメモリ管理と`HeapSys`

Goランタイムは、独自のメモリマネージャを持ち、OSから大きなメモリチャンクを要求し、それを細かく分割してGoプログラムのオブジェクトに割り当てます。
*   **`HeapSys`**: GoランタイムがOSから取得した仮想メモリの総量を示します。これは、Goプログラムが実際に使用しているメモリ量（`HeapAlloc`など）とは異なり、OSから「予約」または「確保」されたメモリ空間の総計です。ガベージコレクタ（GC）は、この`HeapSys`の値を考慮して動作します。

### Plan 9のメモリ管理と`brk`/`sbrk`

*   **Plan 9**: ベル研究所で開発された分散オペレーティングシステムです。Unixの概念を継承しつつ、よりシンプルでモジュール化された設計を目指しています。
*   **`brk`/`sbrk`**: Unix系システムで伝統的に使用されてきた、プロセスのデータセグメントの「プログラムブレーク」（ヒープの終端）を調整することでメモリを確保するシステムコールです。`brk`はプログラムブレークの新しいアドレスを設定し、`sbrk`は現在のプログラムブレークを増分します。Plan 9も同様の概念を持つメモリ管理メカニズムを使用することがあります。Goランタイムは、特定のOS（Plan 9やWebAssemblyなど）では、`mmap`ではなく`sbrk`ベースのメモリ管理を利用します。

### GoランタイムのOSインタフェース

Goランタイムは、OS固有のメモリ管理機能と連携するための抽象化レイヤーを持っています。
*   **`runtime·SysAlloc`**: OSから新しいメモリ領域を割り当てるためのGoランタイム関数。
*   **`runtime·SysFree`**: OSにメモリ領域を解放するためのGoランタイム関数。
*   **`runtime·SysReserve`**: OSから特定の仮想アドレス範囲を予約するが、物理メモリはまだ割り当てないGoランタイム関数。
*   **`runtime·SysMap`**: `SysReserve`で予約された仮想アドレス範囲を物理メモリにマッピングし、使用可能にするGoランタイム関数。

これらの関数は、OSごとに異なる実装を持ち、`src/pkg/runtime/mem_plan9.c`のようなファイルでOS固有のメモリ管理システムコールをラップしています。

## 技術的詳細

このコミットの核心は、Plan 9におけるGoランタイムのメモリ確保と`HeapSys`統計の計上方法の改善です。

以前の実装では、`runtime·SysAlloc`が直接メモリを確保し、その場で`HeapSys`統計を更新していました。しかし、Plan 9のメモリ管理の特性上、`runtime·SysReserve`がメモリを予約し、その後`runtime·SysMap`がその予約されたメモリを実際に使用可能にするという二段階のプロセスが用いられることがあります。この際、`SysReserve`がメモリを予約した時点では`HeapSys`が更新されず、`SysMap`が呼び出された時点で初めて更新されるべきですが、以前の実装ではこの連携が不十分でした。

このコミットは、以下の主要な変更によってこの問題を解決します。

1.  **`brk`関数の導入**: 低レベルなメモリ確保ロジックをカプセル化するために、静的関数`brk`が導入されました。この関数は、Plan 9のシステムコール（おそらく`mmap`のラッパー）を介して実際にメモリを要求し、そのアドレスを返します。これにより、メモリ確保の具体的な詳細が`brk`内に集約されます。
2.  **`runtime·SysAlloc`の変更**: `runtime·SysAlloc`は、直接`HeapSys`を更新するのではなく、新しく導入された`brk`関数を呼び出してメモリを確保するように変更されました。そして、`brk`が成功した場合（`nil`でないポインタを返した場合）にのみ、`HeapSys`統計を更新するようになりました。これにより、メモリ確保が失敗した場合に誤って統計が更新されることを防ぎます。
3.  **`runtime·SysMap`の変更**: `runtime·SysMap`は、`SysReserve`によって既にメモリが予約されていることを前提とし、そのメモリが使用可能になった時点で`HeapSys`統計を更新する役割を担うようになりました。変更前の`SysMap`は、`USED`マクロを通じて統計を更新していましたが、変更後は明示的に`runtime·xadd64(stat, nbytes)`を呼び出して`HeapSys`を更新します。これは、`SysReserve`がメモリを予約した時点では統計を更新せず、`SysMap`がその予約されたメモリを「マッピング」した時点で統計を更新するという、より正確な計上ロジックを反映しています。
4.  **`runtime·SysReserve`の変更**: `runtime·SysReserve`は、以前は`runtime·SysAlloc`を呼び出してメモリを確保し、`HeapSys`を更新していましたが、変更後は新しく導入された`brk`関数を呼び出すようになりました。これにより、`SysReserve`は純粋にメモリの「予約」を行い、`HeapSys`の計上は`SysMap`に委ねられることになります。

これらの変更により、GoランタイムがPlan 9上でメモリを確保する際の`HeapSys`統計の計上ロジックが、OSのメモリ管理メカニズムとより密接に連携し、正確な値が報告されるようになりました。

## コアとなるコードの解説

### `brk`関数の導入と`runtime·SysAlloc`の変更

*   **変更前**: `runtime·SysAlloc`関数が直接メモリを確保し、`runtime·xadd64(stat, nbytes)`で`HeapSys`統計を更新していました。
*   **変更後**:
    *   元の`runtime·SysAlloc`のロジックが`static void* brk(uintptr nbytes)`という新しい静的関数に移動されました。この`brk`関数が、Plan 9における実際の低レベルなメモリ確保（おそらく`mmap`のラッパー）を担当します。
    *   新しい`runtime·SysAlloc`関数は、まず`brk(nbytes)`を呼び出してメモリを確保します。
    *   `brk`が成功し、`p`が`nil`でない場合にのみ、`runtime·xadd64(stat, nbytes)`を呼び出して`HeapSys`統計（`stat`ポインタが指す値）を更新します。これにより、メモリ確保が失敗した場合には統計が更新されないようになり、より正確な計上が可能になります。

### `runtime·SysMap`の変更

*   **変更前**: `runtime·SysMap`は`USED`マクロを通じて統計を更新していました。
*   **変更後**:
    *   `USED(v, reserved)`が呼び出され、その後`runtime·xadd64(stat, nbytes)`が明示的に呼び出されます。
    *   追加されたコメント「`// SysReserve has already allocated all heap memory, // but has not adjusted stats.`」が重要です。これは、`runtime·SysReserve`が既にメモリをOSから確保しているが、その時点では`HeapSys`統計を更新していないことを示唆しています。したがって、`SysMap`がその予約されたメモリを「マッピング」する際に、`HeapSys`を更新する責任を負うことになります。これにより、メモリの予約と実際の使用可能化の段階で、それぞれ適切なタイミングで統計が更新されるようになります。

### `runtime·SysReserve`の変更

*   **変更前**: `runtime·SysReserve`は`runtime·SysAlloc(nbytes, &mstats.heap_sys)`を呼び出していました。これは、予約と同時に`HeapSys`統計を更新するような動作でした。
*   **変更後**: `runtime·SysReserve`は`brk(nbytes)`を呼び出すように変更されました。これにより、`SysReserve`は純粋にメモリの「予約」を行い、`HeapSys`統計の更新は`SysMap`に委ねられるという役割分担が明確になります。

これらの変更により、Plan 9におけるGoランタイムのメモリ管理において、`HeapSys`統計がより正確かつ論理的なタイミングで更新されるようになり、メモリ使用状況の把握が改善されました。

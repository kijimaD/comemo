## 元コミット内容

LZ77辞書ロジックを独立した構造体に抽出し、`inflate.go` のコードを簡素化しました。また、`huffmanBlock()` 関数内のコールバックを `goto` ステートメントに置き換えることで、関数呼び出しのオーバーヘッドを削減し、パフォーマンスを向上させました。ベンチマーク結果は、様々なデコードシナリオで1.05倍から1.12倍の速度向上が見られることを示しています。

## 変更の背景

DEFLATEアルゴリズムのデコンプレッション処理は、LZ77とハフマン符号化という2つの主要な部分から構成されます。LZ77部分は、以前に出力されたデータから繰り返しパターンを検出して参照する「辞書」を管理します。この辞書ロジックは比較的自己完結型であるにもかかわらず、以前は `inflate.go` 内に直接組み込まれており、コードの複雑性を増し、LZ77部分単独でのテストを困難にしていました。

このコミットの背景には、以下の目的があります。

1.  **モジュール性の向上とテスト容易性の確保**: LZ77辞書管理ロジックを独立した構造体として切り出すことで、そのロジックをより簡単にテストできるようになり、全体的なコード品質と保守性が向上します。
2.  **コードの明確化**: `inflate.go` からLZ77関連のコードを分離することで、`inflate.go` の主要なデコンプレッションフローがより明確になり、コードの可読性が向上します。
3.  **パフォーマンスの最適化**: `huffmanBlock()` のような頻繁に実行されるホットパスにおいて、関数呼び出しのオーバーヘッドを削減することがパフォーマンス向上に繋がると判断されました。`goto` ステートメントを使用することで、このオーバーヘッドを回避し、デコンプレッション速度を向上させることを目指しました。

これらの変更は、Goの `compress/flate` パッケージが提供するDEFLATEデコンプレッションの効率性と堅牢性を高めることを目的としています。

## 前提知識の解説

### DEFLATEアルゴリズム

DEFLATEは、LZ77アルゴリズムとハフマン符号化を組み合わせた可逆データ圧縮アルゴリズムです。ZIP、gzip、PNGなどのファイル形式で広く使用されています。

*   **LZ77 (Lempel-Ziv 1977)**:
    *   データストリーム内の繰り返しパターンを検出します。
    *   「スライディングウィンドウ」（辞書）と呼ばれる、以前に処理されたデータのバッファを維持します。
    *   繰り返しパターンが見つかると、そのパターンを「長さ-距離ペア」（length-distance pair）に置き換えます。
        *   **距離 (Distance)**: スライディングウィンドウ内で一致するパターンがどこから始まるかを示します（後方参照）。
        *   **長さ (Length)**: 一致するパターンのバイト数を示します。
    *   一致するパターンが見つからない場合は、元のリテラルバイトをそのまま出力します。
    *   LZ77の重要な特性として、コピー元とコピー先がオーバーラップする「前方コピー」が可能です。これにより、`ABCABCABC` のような繰り返しパターンを `(距離=3, 長さ=9)` のように効率的に表現できます。

*   **ハフマン符号化 (Huffman Coding)**:
    *   LZ77によって生成されたリテラルバイトと長さ-距離ペアを、さらに圧縮するために使用されます。
    *   出現頻度の高いシンボルには短いビット列を、出現頻度の低いシンボルには長いビット列を割り当てることで、全体のデータサイズを削減します。

### Go言語の `compress/flate` パッケージ

Goの `compress/flate` パッケージは、RFC 1951で定義されているDEFLATEデータ形式を実装しています。このパッケージは、データの圧縮と解凍の両方の機能を提供します。

*   `flate.NewReader` / `flate.NewWriter`: DEFLATE形式のデータを読み書きするための基本的なインターフェースを提供します。
*   `flate.NewReaderDict` / `flate.NewWriterDict`: プリセット辞書を使用する際に利用されます。辞書は、圧縮効率を向上させるために、特定のデータセットに頻繁に出現するパターンを事前に登録しておくものです。
*   `decompressor` 構造体: デコンプレッション処理の内部状態を管理する主要な構造体です。以前はLZ77辞書とハフマン符号化の両方のロジックが密結合していました。
*   `huffmanBlock()`: ハフマン符号化されたデータブロックを処理する関数で、リテラルバイトや長さ-距離ペアをデコードします。

### Go言語における `goto` ステートメント

Go言語の `goto` ステートメントは、同じ関数内のラベル付きステートメントへ無条件にジャンプするために使用されます。一般的に、`goto` はコードの可読性や保守性を損なう可能性があるため、使用は推奨されません。しかし、特定の状況、特にパフォーマンスが極めて重要なホットパスや、多重ループからの脱出、共通のエラーハンドリング/クリーンアップ処理への集約などにおいて、`goto` がよりクリーンで効率的な解決策となる場合があります。Goの `goto` は、変数宣言を飛び越えたり、ブロックの外からブロック内にジャンプしたりすることはできないなど、他の言語に比べて制限があります。このコミットでは、関数呼び出しのオーバーヘッドを避けるために `goto` が採用されています。

## 技術的詳細

このコミットの技術的詳細には、主に以下の2つの側面があります。

1.  **LZ77辞書ロジックの `dictDecoder` 構造体への抽出**:
    *   以前は `decompressor` 構造体内に直接存在していたLZ77のスライディングウィンドウ（履歴バッファ）管理と、そこからのデータコピーロジックが、新しく導入された `dictDecoder` 構造体にカプセル化されました。
    *   `dictDecoder` は、`hist []byte` (履歴バッファ)、`wrPos` (書き込み位置)、`rdPos` (読み込み位置)、`full` (バッファが一度満たされたか) といったフィールドを持ち、LZ77辞書の内部状態を管理します。
    *   以下のメソッドが `dictDecoder` に追加され、LZ77の操作を抽象化しています。
        *   `init(size int, dict []byte)`: 辞書を初期化します。プリセット辞書もサポートします。
        *   `histSize() int`: 辞書内の履歴データの総量を報告します。
        *   `availRead() int`: ユーザーにフラッシュ可能なバイト数を報告します。
        *   `availWrite() int`: 出力バッファの利用可能なスペースを報告します。
        *   `writeSlice() []byte`: 書き込み可能なバッファのスライスを返します。
        *   `writeMark(cnt int)`: 書き込みポインタを進めます。
        *   `writeByte(c byte)`: 1バイトを辞書に書き込みます。
        *   `writeCopy(dist, length int) int`: 指定された距離と長さでデータをコピーします。これは、コピー元とコピー先がオーバーラップする可能性のある前方コピーを処理します。
        *   `tryWriteCopy(dist, length int) int`: `writeCopy` の最適化されたバージョンで、短い距離のコピーに特化しており、インライン化されることでパフォーマンスを向上させます。
        *   `readFlush() []byte`: ユーザーに排出準備ができた履歴バッファのスライスを返します。
    *   この分離により、`decompressor` 構造体は `dict dictDecoder` フィールドを持つようになり、LZ77の低レベルな詳細から解放され、より高レベルなデコンプレッションロジックに集中できるようになりました。

2.  **`huffmanBlock()` 内の `goto` ステートメントによる状態遷移**:
    *   以前の `huffmanBlock()` 関数は、デコンプレッションの異なる段階（リテラル読み込み、コピー処理など）を抽象化するために、関数コールバックを使用していました。
    *   このコミットでは、これらのコールバックを `goto` ステートメントと `stepState` フィールド（`stateInit`, `stateDict`）による状態管理に置き換えました。
    *   具体的には、`huffmanBlock()` 内に `readLiteral` と `copyHistory` というラベルが導入され、`switch f.stepState` と `goto` を用いてこれらのセクション間をジャンプします。
    *   これにより、関数呼び出しのオーバーヘッドが排除され、特にデコンプレッションのホットパスにおいて、わずかながらもパフォーマンスが向上します。コミットメッセージのベンチマーク結果がこの効果を裏付けています。
    *   `tryWriteCopy` メソッドも、`for` ループの代わりに `goto` を使用してループ処理を行うことで、コンパイラによるインライン化を促進し、パフォーマンスを最大化するように設計されています。

これらの変更は、コードの構造を改善し、同時に実行時の効率を高めるという、Go言語の設計哲学に沿ったものです。

	// f.hw != f.hp のチェックが f.dict.availRead() > 0 に変更

		if f.dict.availRead() > 0 {
			f.toRead = f.dict.readFlush()
			f.step = (*decompressor).nextBlock
			return
		}
		f.err = io.EOF
		return

	// ...

func (f *decompressor) huffmanBlock() {
	const (
		stateInit = iota // Zero value must be stateInit
		stateDict
	)

	switch f.stepState {
	case stateInit:
		goto readLiteral
	case stateDict:
		goto copyHistory

	// f.dict.availWrite() == 0 || f.copyLen > 0 のチェック

	// goto readLiteral
	// ...

## コアとなるコードの解説

このコミットの核心は、DEFLATEデコンプレッションにおけるLZ77辞書管理と状態遷移のメカニズムを根本的に変更した点にあります。

1.  **`dictDecoder` によるLZ77辞書管理の分離**:
    *   `dictDecoder` は、LZ77アルゴリズムの「スライディングウィンドウ」を効率的に管理するための専用構造体です。この構造体は、デコンプレッション中に生成されるリテラルバイトやコピーされたデータを一時的に保持し、必要に応じてユーザーにフラッシュする役割を担います。
    *   `writeCopy` および `tryWriteCopy` メソッドは、LZ77の最も重要な機能である「長さ-距離ペア」によるデータコピーを実装しています。特に `tryWriteCopy` は、短い距離のコピーに対して最適化されており、頻繁に発生するケースでのパフォーマンスを向上させます。LZ77では、コピー元とコピー先がオーバーラップすることが許されており、`ABCABCABC` のような繰り返しパターンを効率的に生成するために、この「前方コピー」のロジックが `writeCopy` 内で慎重に実装されています。
    *   `readFlush` メソッドは、`dictDecoder` が保持しているデータを、デコンプレッサーの外部（つまりユーザー）に提供する準備ができたときに呼び出されます。これにより、デコンプレッションの進行と出力の生成が分離され、バッファリング戦略の柔軟性が向上します。

2.  **`inflate.go` における `goto` を用いた状態遷移**:
    *   `decompressor` 構造体は、`dictDecoder` のインスタンスを内部に持つことで、LZ77辞書管理の詳細から解放されます。これにより、`decompressor` のコードはより簡潔になり、ハフマン符号化やブロックタイプ処理といった高レベルなデコンプレッションロジックに集中できます。
    *   `huffmanBlock()` 関数は、DEFLATEデコンプレッションの主要なループであり、リテラルバイトの読み込み、長さ-距離ペアのデコード、そしてそれらに基づくデータコピーを連続して行います。以前はこれらの異なる操作を関数コールバックで処理していましたが、このコミットでは `goto` ステートメントと `stepState` フィールドを導入することで、明示的な状態マシンを構築しました。
    *   `readLiteral` ラベルはリテラルバイトの処理や新しい長さ-距離ペアのデコードを担当し、`copyHistory` ラベルはLZ77のコピー操作を担当します。これらのラベル間を `goto` で直接ジャンプすることで、関数呼び出しに伴うスタックフレームの生成・破棄といったオーバーヘッドを回避し、CPUキャッシュの効率も向上させます。これは、非常に頻繁に実行されるデコンプレッションループにおいて、わずかながらも累積的なパフォーマンス向上に寄与します。
    *   `nextBlock` や `copyData` といった他のデコンプレッション関連関数も、`decompressor` の `hist` フィールドを直接操作する代わりに、`dictDecoder` のメソッドを呼び出すように変更されています。これにより、デコンプレッサー全体で一貫した辞書管理ロジックが適用され、コードの整合性が保たれます。

この変更は、Goの `compress/flate` パッケージが、パフォーマンスとコードの保守性の両方を追求していることを示しています。特に、デコンプレッションのような計算集約的なタスクでは、マイクロ最適化が全体的なスループットに大きな影響を与える可能性があるため、`goto` のような低レベルな制御フローが採用されることがあります。

# [インデックス 24922] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおける`defer`および`go`ステートメントの引数評価順序に関するバグを修正します。具体的には、`defer`や`go`ルーチン呼び出しの引数が評価される前に、ランタイム関数（`Deferproc`/`Newproc`）に渡すための引数サイズ（`argsize`）と関数ポインタ（`func`）がスタックに書き込まれることで発生していた、引数領域の上書き問題を解決します。これにより、`test/recover.go`、`test/recover1.go`、`test/fixedbugs/issue4066.go`といったテストが修正されました。

## 元コミット内容

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおいて、`defer`および`go`ステートメントの引数を評価するタイミングを修正します。具体的には、引数の評価が、ランタイム関数（`Deferproc`や`Newproc`）に渡される引数サイズと関数ポインタをスタックに設定する処理よりも先に行われるように変更されました。これは、引数の評価プロセスが、これらのランタイム関数が使用する引数領域を上書きしてしまう可能性があったためです。この修正により、`test/recover.go`、`test/recover1.go`、`test/fixedbugs/issue4066.go`といった関連するテストの失敗が解消されました。

## 変更の背景

Go言語の`defer`および`go`ステートメントは、その特性上、呼び出し元の関数が終了する際や、新しいゴルーチンが開始される際に実行される関数（またはメソッド）とその引数を指定します。ここで重要なのは、**`defer`や`go`ステートメントが宣言された時点**で、その引数が評価され、その値が保存されるという点です。実際の関数実行は後回しにされますが、引数の値は宣言時に確定します。

Goコンパイラは、コードをSSA形式に変換して最適化を行います。このSSAバックエンドにおいて、`defer`や`go`ステートメントを処理する際に、以下の問題が発生していました。

1.  `defer`や`go`ステートメントの引数を評価し、その値をスタック上の特定の領域（引数領域）に格納する処理。
2.  ランタイム関数である`Deferproc`（`defer`用）や`Newproc`（`go`用）を呼び出すために必要な情報（例えば、呼び出す関数の引数サイズ`argsize`や、呼び出す関数自体へのポインタ`func`）をスタックに書き込む処理。

問題は、これらの処理の順序にありました。以前の実装では、`argsize`と`func`をスタックに書き込む処理が、`defer`や`go`の引数を評価してスタックに格納する処理よりも先に行われていました。しかし、引数の評価プロセスが、偶然にも`argsize`や`func`が書き込まれたスタック上の領域を上書きしてしまう可能性がありました。これにより、`Deferproc`や`Newproc`が誤った`argsize`や`func`の値を受け取ってしまい、ランタイムエラーや予期せぬ動作（例えば、`recover`が正しく機能しないなど）を引き起こしていました。

このバグは、特に`test/recover.go`、`test/recover1.go`、`test/fixedbugs/issue4066.go`といったテストケースで顕在化しており、これらのテストがSSAバックエンドで正しく動作しない原因となっていました。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) フォーム

Goコンパイラは、ソースコードを抽象構文木（AST）に変換した後、中間表現としてSSA (Static Single Assignment) フォームを使用します。SSAフォームは、各変数が一度だけ代入されるという特性を持つため、データフロー解析や最適化を容易にします。GoコンパイラのSSAバックエンドは、このSSAフォームを用いて、より効率的な機械語コードを生成します。このコミットは、SSAバックエンドが`defer`や`go`ステートメントを処理する際のコード生成ロジックに関するものです。

### `defer` および `go` ステートメントの動作

*   **`defer`**: `defer`キーワードに続く関数呼び出しは、その関数がリターンする直前（またはパニックが発生してスタックがアンワインドされる際）に実行されます。重要なのは、`defer`ステートメントが評価される時点で、その引数が評価され、その値が保存されることです。
*   **`go`**: `go`キーワードに続く関数呼び出しは、新しいゴルーチンとして並行して実行されます。`defer`と同様に、`go`ステートメントが評価される時点で、その引数が評価され、その値が新しいゴルーチンのスタックにコピーされます。

どちらのケースでも、引数の評価と保存は、実際の関数実行よりも先行して行われます。

### スタックフレームと引数領域

Goプログラムでは、関数が呼び出されるたびに、その関数専用のスタックフレームがスタック上に作成されます。このスタックフレームには、関数のローカル変数、レジスタの保存領域、そして呼び出し元から渡された引数や、呼び出す関数に渡す引数を格納するための領域が含まれます。

`defer`や`go`ステートメントの場合、呼び出される関数（またはクロージャ）とその引数は、ランタイムが管理する特別な領域に格納されます。この領域は、`Deferproc`や`Newproc`といったランタイム関数によって設定され、管理されます。

### `argsize` と `func` の意味

*   **`argsize`**: `Deferproc`や`Newproc`に渡される引数の一つで、`defer`または`go`で呼び出される関数の引数リスト全体のサイズ（バイト単位）を示します。ランタイムはこの情報を使って、スタック上の引数領域を正しく確保・管理します。
*   **`func`**: `Deferproc`や`Newproc`に渡されるもう一つの引数で、`defer`または`go`で呼び出される関数（またはクロージャ）へのポインタです。

これらの値は、ランタイムが`defer`や`go`の呼び出しを正しくスケジューリングし、実行するために不可欠な情報です。

## 技術的詳細

このコミットが修正する問題は、GoコンパイラのSSAバックエンドが`defer`または`go`ステートメントを処理する際の、スタック操作の順序に関するものです。

`src/cmd/compile/internal/gc/ssa.go`内の`stmt`メソッドは、ASTノードをSSA形式に変換する主要な部分です。`defer`または`go`ステートメント（`ONONAME`オペレーションを持つ`call`ノードとして表現される）に遭遇すると、コンパイラは以下の処理を行います。

1.  `defer`または`go`で呼び出される関数の引数を評価し、スタック上の引数領域に格納する。
2.  ランタイム関数（`Deferproc`または`Newproc`）を呼び出すために必要なメタデータ（`argsize`と`func`）をスタックに書き込む。
3.  `Deferproc`または`Newproc`自体を呼び出す。

以前の実装では、ステップ2がステップ1よりも先に行われていました。

```go
// 変更前:
// Write argsize and closure (args to Newproc/Deferproc)
argsize := s.constInt32(Types[TUINT32], int32(fn.Type.Argwid))
s.vars[&memvar] = s.newValue3I(ssa.OpStore, ssa.TypeMem, 4, s.sp, argsize, s.mem())
// ... closureの書き込み ...

// Run all argument assignments.  The arg slots have already
// been offset by 2*widthptr.
s.stmtList(call.List) // ここで引数が評価され、スタックに書き込まれる
```

この順序だと、`s.stmtList(call.List)`が実行され、`defer`や`go`の引数がスタックに書き込まれる際に、すでにスタックに書き込まれていた`argsize`や`func`の値が上書きされてしまう可能性がありました。これは、引数領域と`argsize`/`func`の格納領域がスタック上で重なっていたためと考えられます。結果として、`Deferproc`や`Newproc`が不正な`argsize`や`func`を受け取り、ランタイムが正しく動作しない原因となっていました。

このコミットは、`s.stmtList(call.List)`の呼び出しを、`argsize`と`func`をスタックに書き込む処理の**前**に移動することで、この問題を解決しました。これにより、引数が評価され、スタックに格納された後に、`argsize`と`func`が安全に書き込まれるようになり、データの破損が防がれます。

## コアとなるコードの解説

`src/cmd/compile/internal/gc/ssa.go`の変更箇所に注目します。

*   **削除された行**:
    ```go
    -		// Run all argument assignments.  The arg slots have already
    -		// been offset by 2*widthptr.
    -		s.stmtList(call.List)
    ```
    このコードブロックは、`defer`または`go`で呼び出される関数の引数を評価し、スタック上の引数領域に格納する処理を担当していました。以前は、`argsize`と`closure`（`func`に相当）がスタックに書き込まれた後に実行されていました。

*   **追加された行**:
    ```go
    +		// Run all argument assignments.  The arg slots have already
    +		// been offset by 2*widthptr.
    +		s.stmtList(call.List)
    ```
    同じコードブロックが、`argsize`と`closure`をスタックに書き込む処理の**前**に移動されました。

この変更により、処理の順序は以下のようになります。

1.  `s.stmtList(call.List)`が実行され、`defer`または`go`の引数が評価され、スタック上の適切な位置に格納されます。コメントにある「`The arg slots have already been offset by 2*widthptr.`」は、スタックポインタ（`s.sp`）からのオフセットが既に考慮されていることを示唆しています。
2.  次に、`argsize`（`fn.Type.Argwid`から取得される引数の合計サイズ）が計算され、`s.newValue3I(ssa.OpStore, ...)`を使ってスタックに書き込まれます。`s.sp`は現在のスタックポインタ、`argsize`は書き込む値、`s.mem()`は現在のメモリ状態を表すSSA値です。
3.  同様に、`closure`（呼び出す関数またはクロージャへのポインタ）が計算され、`addr := s.entryNewValue1I(ssa.OpOffPtr, ...)`でアドレスが計算された後、`s.newValue3I(ssa.OpStore, ...)`を使ってスタックに書き込まれます。

この新しい順序により、`argsize`と`closure`が書き込まれる際には、`defer`や`go`の引数によってその領域が上書きされる心配がなくなります。これにより、ランタイム関数が正しいメタデータを受け取り、`defer`や`go`ステートメントが意図通りに動作するようになります。

`test/run.go`の変更は、この修正が成功したことを示すものです。以前はSSAバックエンドで失敗していた`recover.go`、`recover1.go`、`issue4066.go`といったテストが、このコミットによってパスするようになったため、一時的なスキップリストから削除されました。

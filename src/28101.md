# [インデックス 28101] ファイルの概要

このコミットは、Goリンカの内部ライブラリの一部である `src/cmd/link/internal/ld/lib.go` ファイルに変更を加えています。このファイルは、Goプログラムのビルドプロセスにおいて、ホストシステム（Goが動作している環境）のリンカと連携するための特定の操作を処理します。具体的には、ホストリンカが特定のフラグ（この場合は `-no-pie`）をサポートしているかどうかを検出するロジックに関連しています。

## コミット

このコミットは、Goリンカがレース検出機能（`-race`フラグ）が有効なバイナリをビルドする際に、ホストリンカが `-no-pie` フラグをサポートしているかをチェックするロジックのバグを修正します。以前の実装では、このサポートチェックが誤って実行可能ファイルのリンクを試みていたため、実際には `-no-pie` がサポートされている場合でも、誤ってサポートされていないと判断される問題がありました。この修正は、ホストコンパイラに `-c` フラグを追加することで、コンパイルのみを行い、リンクをスキップするように変更し、正しいサポート検出を可能にしています。

## 変更の背景

この変更の背景には、Goのレース検出機能（`-race`フラグ）と、Position-Independent Executable (PIE) の生成を制御する `-no-pie` リンカフラグの間の相互作用があります。

1.  **`golang.org/cl/22453` の意図**: 以前の変更（`golang.org/cl/22453`）では、レース検出機能が有効なGoバイナリをビルドする際に、ホストのツールチェインが `-no-pie` フラグをサポートしていれば、そのフラグをリンカに渡すことを目的としていました。レース検出機能は、`cgo` を利用してC/C++のThreadSanitizerライブラリに依存することが多く、その結果、GoのビルドプロセスはシステムにインストールされているCコンパイラとリンカ（ホストツールチェイン）を利用します。
2.  **PIEとセキュリティ**: PIEは、実行可能ファイルがメモリ上の任意のアドレスにロードされることを可能にするセキュリティ機能です。これはASLR (Address Space Layout Randomization) と組み合わせて、バッファオーバーフロー攻撃などの特定の種類の攻撃を困難にします。しかし、特定の環境やデバッグシナリオでは、PIEを無効にする必要がある場合があります。
3.  **バグの原因**: `golang.org/cl/22453` で導入された `-no-pie` サポートチェックの実装に問題がありました。このチェックは、ホストコンパイラが `-no-pie` フラグを認識するかどうかを判断するために、一時的な空の `trivial.c` ファイルを作成し、ホストコンパイラを `"-no-pie", "trivial.c"` という引数で実行していました。問題は、コンパイラに `-c` フラグ（コンパイルのみを行う）を渡すのを忘れていたことです。その結果、ホストコンパイラは `trivial.c` をコンパイルするだけでなく、それを実行可能ファイルに「リンク」しようとしました。空のCソースファイルは有効な実行可能ファイルにリンクできないため、このコマンドは常に失敗し、Goリンカは `-no-pie` がホストツールチェインでサポートされていないと誤って判断していました。
4.  **このコミットの目的**: このコミットは、上記の誤ったサポートチェックを修正し、ホストコンパイラに `-c` フラグを明示的に渡すことで、コンパイルのみを実行させ、`-no-pie` フラグのサポートを正しく検出できるようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の技術的背景知識が役立ちます。

*   **Goリンカ (`cmd/link`)**: Go言語のコンパイラツールチェインの一部であり、Goのソースコードから最終的な実行可能ファイルを生成する役割を担います。Goはクロスコンパイルに優れており、異なるアーキテクチャやOS向けのバイナリを生成できます。`cmd/link` は、Goのオブジェクトファイルと必要なライブラリを結合し、実行可能形式を作成します。
*   **PIE (Position-Independent Executable)**: 「位置独立実行可能ファイル」と訳されます。これは、プログラムがメモリ上の任意のアドレスにロードされても正しく実行できるようにコンパイルされた実行可能ファイルのことです。現代のオペレーティングシステムでは、ASLR (Address Space Layout Randomization) と組み合わせて、セキュリティを強化するためにPIEが広く採用されています。ASLRは、実行可能ファイルのコード、データ、ライブラリなどをメモリ上のランダムな位置に配置することで、攻撃者が特定のコードやデータを予測して悪用するのを困難にします。
*   **Go Race Detector (`-race`)**: Go言語に組み込まれている強力なツールで、並行処理におけるデータ競合（レースコンディション）を検出します。データ競合は、複数のゴルーチンが共有変数に同時にアクセスし、少なくとも1つのアクセスが書き込みであるにもかかわらず、それらのアクセスが同期されていない場合に発生します。レース検出機能は、`go build -race` のようにビルド時に `-race` フラグを渡すことで有効になります。この機能は、内部的にC/C++のThreadSanitizerライブラリを利用しており、`cgo` を介してホストのCコンパイラとリンカに依存することがあります。
*   **`-no-pie` フラグ**: これはリンカに渡されるフラグで、生成される実行可能ファイルがPIE形式ではないことを指示します。つまり、実行可能ファイルは特定のアドレスにロードされることを前提とします。セキュリティ上の理由から通常はPIEが推奨されますが、特定のレガシーシステムやデバッグのシナリオで `-no-pie` が必要になることがあります。
*   **`exec.Command`**: Goの標準ライブラリ `os/exec` パッケージに含まれる機能で、Goプログラム内から外部のコマンド（この場合はホストのCコンパイラ）を実行するために使用されます。これにより、Goのビルドツールはシステムにインストールされている外部ツールと連携できます。
*   **ホストコンパイラ (Host Compiler)**: Goのビルドプロセスが、`cgo` を使用する場合や、特定のリンカ機能（例えば、`-no-pie` のサポートチェック）のために利用する、システムにインストールされているCコンパイラ（例: GCC, Clang）を指します。
*   **コンパイラの `-c` フラグ**: 多くのC/C++コンパイラ（GCCやClangなど）で共通して使用されるフラグです。このフラグを渡すと、コンパイラはソースファイルをコンパイルしてオブジェクトファイル（通常は `.o` 拡張子を持つ）を生成しますが、リンクは行いません。つまり、実行可能ファイルは生成されず、コンパイル段階でエラーがないかどうかのチェックや、オブジェクトファイルの生成のみが行われます。

## 技術的詳細

このコミットの技術的詳細は、Goリンカがホストツールチェインの機能を検出する方法と、その検出ロジックにおける特定の誤りを修正することにあります。

`src/cmd/link/internal/ld/lib.go` 内の `hostlink()` 関数は、Goリンカがホストシステム固有のリンカ操作を実行する際に呼び出されます。この関数の一部で、ホストリンカが `-no-pie` フラグをサポートしているかどうかを動的にチェックするロジックが存在しました。

元のコードでは、このチェックは以下の手順で行われていました。
1.  `ioutil.WriteFile(src, []byte{}, 0666)` を使用して、`trivial.c` という名前の空のCソースファイルを作成します。
2.  `exec.Command(argv[0], "-no-pie", "trivial.c")` を実行します。ここで `argv[0]` はホストのCコンパイラ（例: `gcc` や `clang`）を指します。
3.  コマンドの `CombinedOutput()` を取得し、エラーが発生したかどうか (`err == nil`)、および出力に「unrecognized」という文字列が含まれていないか (`!bytes.Contains(out, []byte("unrecognized"))`) を確認して、`-no-pie` がサポートされているかを判断します。

このロジックの根本的な問題は、`exec.Command` の呼び出しに `-c` フラグが含まれていなかったことです。Cコンパイラにソースファイル（`trivial.c`）とリンカフラグ（`-no-pie`）を渡すだけで `-c` フラグがない場合、コンパイラはデフォルトでそのソースファイルをコンパイルし、さらにそれを実行可能ファイルにリンクしようとします。しかし、`trivial.c` は空のファイルであるため、有効な実行可能ファイルを生成するためのシンボルやコードが何も含まれていません。したがって、リンカは常に失敗し、`err != nil` となって、`-no-pie` フラグが実際にはサポートされている場合でも、誤ってサポートされていないと判断されていました。

このコミットは、`exec.Command` の引数リストに `"-c"` を追加することで、この問題を解決します。
変更後のコマンドは `exec.Command(argv[0], "-c", "-no-pie", "trivial.c")` となります。
`-c` フラグが追加されたことで、ホストコンパイラは `trivial.c` をコンパイルするだけで、リンクは行いません。空のCファイルをコンパイルする操作は通常成功し、`-no-pie` フラグがコンパイラによって認識されるかどうかのみがテストされます。これにより、`supported` 変数がホストツールチェインの `-no-pie` サポート状況を正確に反映するようになり、Goリンカはレース検出機能付きバイナリのビルド時に適切なリンカフラグを渡せるようになります。

## コアとなるコードの解説

この変更は、`src/cmd/link/internal/ld/lib.go` ファイル内の `hostlink()` 関数の一部にあります。

変更前のコード:
`cmd := exec.Command(argv[0], "-no-pie", "trivial.c")`

この行では、ホストのCコンパイラ（`argv[0]`）を呼び出し、`-no-pie` フラグと空のソースファイル `trivial.c` を引数として渡していました。`-c` フラグがないため、コンパイラは `trivial.c` をコンパイルし、さらにそれを実行可能ファイルにリンクしようとします。しかし、`trivial.c` は空であるため、リンクは必ず失敗し、結果として `err` が `nil` ではなくなり、`-no-pie` がサポートされていないと誤って判断されていました。

変更後のコード:
`cmd := exec.Command(argv[0], "-c", "-no-pie", "trivial.c")`

この行では、引数リストに `"-c"` が追加されています。この `-c` フラグは、ホストコンパイラに対して「ソースファイルをコンパイルするが、リンクは行わない」という指示を与えます。これにより、コンパイラは `trivial.c` をオブジェクトファイルにコンパイルしようとしますが、リンクは試みません。空のCファイルをコンパイルする操作は通常成功するため、コマンドの成否は `-no-pie` フラグがコンパイラによって認識されるかどうかにのみ依存するようになります。

その後の行 `supported := err == nil && !bytes.Contains(out, []byte("unrecognized"))` では、コマンドの実行がエラーなく（`err == nil`）、かつ標準出力/エラー出力に「unrecognized」という文字列が含まれていない場合に、`-no-pie` がサポートされていると判断します。この修正により、このサポートチェックが意図通りに機能し、Goリンカはホストツールチェインの `-no-pie` サポート状況を正確に把握できるようになりました。

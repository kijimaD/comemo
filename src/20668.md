## 変更の背景

この変更は、Go言語の `net` パッケージのドキュメントコメントに含まれるコード例が、サーバーの接続受付（`Accept`）ループにおけるエラーハンドリングに関して誤解を招く可能性があったため行われました。具体的には、`ln.Accept()` がエラーを返した場合に `continue` を使用するという記述がありました。

Goのネットワークプログラミングにおいて、`net.Listener` の `Accept()` メソッドは、新しい接続を待機し、接続が確立されると `net.Conn` インターフェースを実装するオブジェクトと `nil` エラーを返します。しかし、何らかの問題（例えば、リスナーが閉じられた、システムリソースが枯渇した、一時的なネットワークの問題など）が発生した場合、`Accept()` はエラーを返します。

元のコメント例では、エラーが発生した場合に単に `continue` を実行してループの次のイテレーションに進むように示されていました。これは、一時的なエラーであれば問題ないように見えますが、致命的なエラー（例えば、リスナーが閉じられたことによるエラー `net.ErrClosed` など）が発生した場合でもループが継続しようとし、無限ループに陥ったり、CPUを無駄に消費したり、あるいはサーバーが正常にシャットダウンできないといった問題を引き起こす可能性があります。

Issue #8607（"net: package comment example for Listen is misleading"）では、この問題が指摘され、`Accept` ループでのエラーハンドリングは、エラーの種類に応じて適切に処理されるべきであり、単なる `continue` では不十分であるという議論がなされました。特に、`Accept` がエラーを返した際に、そのエラーが一時的なものか、それともリスナーを終了させるべき永続的なものかを区別し、適切な対応を取るべきであるという点が強調されました。このコミットは、その誤解を招く `continue` の行を削除することで、開発者がより堅牢なエラーハンドリングを実装するよう促すことを目的としています。

## 前提知識の解説

### Go言語の `net` パッケージ

`net` パッケージは、Go言語におけるネットワークI/Oのプリミティブを提供します。TCP/IP、UDP、Unixドメインソケットなどのネットワークプロトコルを扱うための基本的なインターフェースと関数が含まれています。

### `net.Listen` 関数

`net.Listen` 関数は、指定されたネットワークプロトコル（例: "tcp", "udp"）とアドレス（例: ":8080"）で新しいネットワークリスナーを作成するために使用されます。成功すると、`net.Listener` インターフェースを実装するオブジェクトを返します。このリスナーは、着信接続を待機し、受け入れるために使用されます。

```go
func Listen(network, address string) (Listener, error)
```

### `net.Listener` インターフェース

`net.Listener` インターフェースは、ネットワーク接続をリッスンするための一般的なインターフェースです。主なメソッドは以下の通りです。

*   **`Accept() (Conn, error)`**: 次の着信接続を待機し、それを受け入れます。接続が確立されると、`net.Conn` インターフェースを実装するオブジェクトを返します。エラーが発生した場合は、`nil` とエラーを返します。
*   **`Close() error`**: リスナーを閉じます。これにより、新しい接続の受け入れが停止され、リスナーに関連付けられたリソースが解放されます。
*   **`Addr() Addr`**: リスナーのネットワークアドレスを返します。

### サーバーの接続受付（Accept）ループ

一般的なネットワークサーバーでは、`net.Listen` でリスナーを作成した後、無限ループ内で `listener.Accept()` を呼び出し、着信接続を継続的に受け入れます。新しい接続が受け入れられるたびに、通常は新しいゴルーチンを起動してその接続を処理します。これにより、サーバーは複数のクライアントからの同時接続を非同期に処理できます。

基本的な構造は以下のようになります。

```go
ln, err := net.Listen("tcp", ":8080")
if err != nil {
    // エラーハンドリング
}
defer ln.Close() // サーバー終了時にリスナーを閉じる

for {
    conn, err := ln.Accept()
    if err != nil {
        // エラーハンドリング
        // ここで continue を使うと問題になる場合がある
    }
    go handleConnection(conn) // 新しいゴルーチンで接続を処理
}
```

### Go言語のエラーハンドリング

Go言語では、エラーは関数の最後の戻り値として `error` 型で返されます。慣例として、呼び出し元はエラーが `nil` でない場合にエラーが発生したと判断し、適切に処理します。ネットワークプログラミングでは、一時的なエラー（`net.Error` インターフェースの `Temporary()` メソッドで判定可能）と永続的なエラーを区別し、異なる戦略を取ることが重要です。

## 技術的詳細

このコミットの技術的詳細は、`net.Listener` の `Accept()` メソッドが返すエラーの性質と、それに対する適切なエラーハンドリングの重要性に集約されます。

`Accept()` がエラーを返す場合、そのエラーは大きく分けて2種類あります。

1.  **一時的なエラー (Temporary Error)**: ネットワークの一時的な問題、システムリソースの一時的な不足など、再試行すれば解決する可能性のあるエラーです。Goの `net` パッケージでは、`net.Error` インターフェースを実装するエラーオブジェクトがあり、その `Temporary()` メソッドが `true` を返すことで一時的なエラーであることを示します。このようなエラーの場合、通常は短い時間待機してから `Accept()` を再試行することが適切な戦略となります。
2.  **永続的なエラー (Permanent Error)**: リスナーが閉じられた（`net.ErrClosed`）、アドレスが既に使用されている、権限がないなど、再試行しても解決しない、あるいはサーバーの運用を継続できないような致命的なエラーです。このようなエラーの場合、サーバーは通常、シャットダウンするか、エラーをログに記録して終了するべきです。

元のコメント例にあった `continue` は、エラーの種類を区別せずにループの次のイテレーションに進むことを意味します。

```go
// 修正前のコードスニペット（概念）
for {
    conn, err := ln.Accept()
    if err != nil {
        // handle error
        continue // ここが問題
    }
    go handleConnection(conn)
}
```

この `continue` が問題となるのは、以下のようなシナリオが考えられるためです。

*   **致命的なエラーでの無限ループ**: もし `Accept()` が永続的なエラー（例: リスナーが閉じられたことによるエラー）を返し続けた場合、`continue` があるとループは無限にエラーを検出し、ログを吐き出し（もしログ処理があれば）、CPUを消費し続ける可能性があります。これはサーバーが正常にシャットダウンできない状況を作り出します。
*   **リソースの無駄な消費**: 一時的なエラーであっても、適切な待機（バックオフ）メカニズムなしにすぐに `Accept()` を再試行すると、システムリソースを無駄に消費したり、エラーログが大量に生成されたりする可能性があります。
*   **誤った期待**: この例を見た開発者が、`Accept()` のエラーは常に `continue` で処理できると誤解し、堅牢なエラーハンドリングを実装しない可能性があります。

このコミットでは、`continue` の行を削除することで、開発者に対して `Accept()` がエラーを返した場合に、そのエラーをより慎重に評価し、適切なエラーハンドリングロジック（例えば、エラーの種類に応じたログ記録、一時的なエラーに対する再試行とバックオフ、永続的なエラーに対するサーバーのシャットダウンなど）を実装するよう促しています。これにより、Goのネットワークサーバーがより堅牢で信頼性の高いものになることが期待されます。

## コアとなるコードの解説

削除された行は `continue` です。これは、`net` パッケージのコメントブロック内にある `Listen` 関数の使用例の一部でした。

元のコード例は以下のようでした（関連部分のみ抜粋）：

```go
// The Listen function creates servers:
//
//     ln, err := net.Listen("tcp", ":8080")
//     if err != nil {
//         // handle error
//     }
//     for {
//         conn, err := ln.Accept()
//         if err != nil {
//             // handle error
//             continue // この行が削除された
//         }
//         go handleConnection(conn)
//     }
```

この `continue` が削除されたことで、`Accept()` がエラーを返した場合の処理は、単にループの次のイテレーションに進むのではなく、開発者が `// handle error` のコメント部分に、より適切なエラーハンドリングロジックを記述する必要があることを示唆するようになりました。

例えば、より堅牢なエラーハンドリングの例としては、以下のようなものが考えられます。

```go
for {
    conn, err := ln.Accept()
    if err != nil {
        // エラーが一時的なものかチェック
        if ne, ok := err.(net.Error); ok && ne.Temporary() {
            log.Printf("Accept temporary error: %v; retrying in 1s", err)
            time.Sleep(1 * time.Second)
            continue // 一時的なエラーの場合は再試行
        }
        // 致命的なエラーの場合はループを終了
        log.Printf("Accept fatal error: %v; shutting down listener", err)
        return // または break
    }
    go handleConnection(conn)
}
```

このように、`continue` の削除は、Goのネットワークプログラミングにおけるエラーハンドリングの重要性と複雑さを強調し、開発者がより注意深くエラーの種類を考慮し、適切な対応を実装するよう促すための、ドキュメント上の重要な改善です。

*   **リソースの無駄な消費**: 一時的なエラーであっても、適切な待機（バックオフ）メカニズムなしにすぐに `Accept()` を再試行すると、システムリソースを無駄に消費したり、エラーログが大量に生成されたりする可能性があります。
*   **誤った期待**: この例を見た開発者が、`Accept()` のエラーは常に `continue` で処理できると誤解し、堅牢なエラーハンドリングを実装しない可能性があります。

このコミットでは、`continue` の行を削除することで、開発者に対して `Accept()` がエラーを返した場合に、そのエラーをより慎重に評価し、適切なエラーハンドリングロジック（例えば、エラーの種類に応じたログ記録、一時的なエラーに対する再試行とバックオフ、永続的なエラーに対するサーバーのシャットダウンなど）を実装するよう促しています。これにより、Goのネットワークサーバーがより堅牢で信頼性の高いものになることが期待されます。

## コアとなるコードの変更箇所

変更は `src/net/net.go` ファイルの1行の削除です。

```diff
--- a/src/net/net.go
+++ b/src/net/net.go
@@ -32,7 +32,6 @@ The Listen function creates servers:
 		conn, err := ln.Accept()
 		if err != nil {
 			// handle error
-			continue
 		}\n 		go handleConnection(conn)
 	}
```

## コアとなるコードの解説

削除された行は `continue` です。これは、`net` パッケージのコメントブロック内にある `Listen` 関数の使用例の一部でした。

元のコード例は以下のようでした（関連部分のみ抜粋）：

```go
// The Listen function creates servers:
//
//     ln, err := net.Listen("tcp", ":8080")
//     if err != nil {
//         // handle error
//     }
//     for {
//         conn, err := ln.Accept()
//         if err != nil {
//             // handle error
//             continue // この行が削除された
//         }
//         go handleConnection(conn)
//     }
```

この `continue` が削除されたことで、`Accept()` がエラーを返した場合の処理は、単にループの次のイテレーションに進むのではなく、開発者が `// handle error` のコメント部分に、より適切なエラーハンドリングロジックを記述する必要があることを示唆するようになりました。

例えば、より堅牢なエラーハンドリングの例としては、以下のようなものが考えられます。

```go
for {
    conn, err := ln.Accept()
    if err != nil {
        // エラーが一時的なものかチェック
        if ne, ok := err.(net.Error); ok && ne.Temporary() {
            log.Printf("Accept temporary error: %v; retrying in 1s", err)
            time.Sleep(1 * time.Second)
            continue // 一時的なエラーの場合は再試行
        }
        // 致命的なエラーの場合はループを終了
        log.Printf("Accept fatal error: %v; shutting down listener", err)
        return // または break
    }
    go handleConnection(conn)
}
```

このように、`continue` の削除は、Goのネットワークプログラミングにおけるエラーハンドリングの重要性と複雑さを強調し、開発者がより注意深くエラーの種類を考慮し、適切な対応を実装するよう促すための、ドキュメント上の重要な改善です。

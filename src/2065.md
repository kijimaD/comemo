## 元コミット内容

## 変更の背景

このコミットが行われた2009年4月は、Go言語がまだ初期段階にあった時期です。当時の`exvar`パッケージは、主に整数型の変数をエクスポートする機能に限定されており、`intVars`という`map[string]int`型のマップで管理されていました。しかし、プログラムの内部状態を公開するニーズは整数型に留まらず、より複雑なデータ構造、特にマップ型の変数をエクスポートする機能が求められていました。

この変更の主な背景は以下の通りです。

1.  **拡張性の向上**: 既存の実装では、新しい型のエクスポート変数を追加する際に、グローバルなマップとそれに対応する操作関数を個別に定義する必要がありました。これは、コードの重複と保守性の低下を招きます。インターフェース型を導入することで、将来的に文字列型や動的なルックアップ変数など、様々な型の変数を統一的な方法で扱えるようにするための基盤を構築することが目的でした。
2.  **型安全性の向上と一元管理**: 異なる型の変数を別々のグローバルマップで管理するのではなく、単一の`map[string]exVar`で一元的に管理することで、コードの複雑さを軽減し、型ミスマッチが発生した場合のハンドリングを改善することが意図されました。
3.  **`mapVar`の追加**: 整数型だけでなく、キーと値のペアを持つマップ型の変数をエクスポートする具体的なニーズに応えるため、`mapVar`型が導入されました。

## 前提知識の解説

### Go言語のインターフェース

Go言語のインターフェースは、メソッドのシグネチャの集合を定義する型です。Goのインターフェースは、JavaやC#のような明示的な`implements`キーワードを必要とせず、型がインターフェースで定義されたすべてのメソッドを実装していれば、そのインターフェースを満たすと見なされます（ダックタイピング）。これにより、異なる具象型を統一的な方法で扱うことが可能になり、コードの柔軟性と拡張性が向上します。

### Go言語のマップ（`map`）

Go言語のマップは、キーと値のペアを格納するハッシュテーブルです。キーは一意であり、値は任意の型を持つことができます。マップは、高速なルックアップ、追加、削除操作を提供し、データの関連付けに広く使用されます。

### Go言語の並行処理と`sync.Mutex`

Go言語は、ゴルーチン（軽量なスレッド）とチャネル（ゴルーチン間の通信メカニズム）によって並行処理を強力にサポートします。複数のゴルーチンが共有データに同時にアクセスすると、競合状態（Race Condition）が発生し、予期せぬ結果を招く可能性があります。これを防ぐために、`sync`パッケージの`Mutex`（ミューテックス）が使用されます。`Mutex`は、共有リソースへのアクセスを排他的に制御し、一度に一つのゴルーチンだけがリソースにアクセスできるようにします。`Lock()`メソッドでロックを取得し、`Unlock()`メソッドでロックを解放します。`defer mutex.Unlock()`は、関数の終了時に確実にロックが解放されるようにするためのGoのイディオムです。

### `fmt`パッケージ

`fmt`パッケージは、Go言語でフォーマットされたI/O（入力/出力）を実装するための機能を提供します。`fmt.Sprint()`や`fmt.Sprintf()`は、様々な型の値を文字列に変換するために使用されます。

### `exvar`パッケージの役割（当時のGoにおける）

当時の`exvar`パッケージは、Goプログラムの内部で定義された変数を、外部から参照可能な形で「エクスポート」するためのユーティリティでした。これは、デバッグ情報、統計情報、または監視メトリクスなどを公開する目的で使用されます。現代のGo言語では、同様の目的で`expvar`パッケージが標準ライブラリとして提供されており、HTTP経由でJSON形式で変数を公開する機能などが含まれています。このコミットは、その`expvar`パッケージの前身または関連する概念の進化の一部と見ることができます。

## 技術的詳細

このコミットの技術的な核心は、`exvar`パッケージが変数を管理する方法を、具体的な型（`int`や`map[string]int`）に直接依存するのではなく、インターフェース型を介して抽象化することにあります。

1.  **`exVar`インターフェースの導入**:
    `exVar`という新しいインターフェースが定義されました。このインターフェースは、`String() string`という単一のメソッドを要求します。これにより、エクスポートされるすべての変数が、自身の値を文字列として表現できるという共通の振る舞いを持つことが保証されます。

    ```go
    type exVar interface {
        String() string;
    }
    ```

2.  **具体的な変数型の定義**:
    *   **`intVar`**: 整数値を表す`intVar`型が`int`のエイリアスとして定義され、`exVar`インターフェースを満たすように`String()`メソッドが実装されました。
        ```go
        type intVar int;
        func (i intVar) String() string {
            return fmt.Sprint(int(i))
        }
        ```
    *   **`mapVar`**: キーが文字列、値が整数のマップを表す`mapVar`型が`map[string] int`のエイリアスとして定義され、同様に`exVar`インターフェースを満たす`String()`メソッドが実装されました。この`String()`メソッドは、マップの内容を「map:x key:value」のような形式で文字列化します。
        ```go
        type mapVar map[string] int;
        func (m mapVar) String() string {
            s := "map:x"; // TODO(dsymonds): the 'x' should be user-specified!
            for k, v := range m {
                s += fmt.Sprintf(" %s:%v", k, v)
            }
            return s
        }
        ```

3.  **一元化された変数管理**:
    これまでの`intVars`と`mapVars`という別々のグローバルマップの代わりに、`vars`という単一のグローバルマップが導入されました。このマップは`map[string] exVar`型であり、すべてのエクスポート変数をその具象型に関わらず`exVar`インターフェースとして格納します。

    ```go
    var (
        mutex sync.Mutex;
        vars = make(map[string] exVar);
    )
    ```

4.  **型安全な変数取得/初期化関数**:
    `getOrInitIntVar`と`getOrInitMapVar`というヘルパー関数が導入されました。これらの関数は、指定された名前の変数を`vars`マップから取得しようとします。
    *   もし変数が見つかり、かつ要求された型（`intVar`または`mapVar`）と一致すれば、その変数を返します。
    *   もし変数が見つかるが、型が一致しない場合（例: 既に`intVar`として登録されている名前で`mapVar`を取得しようとした場合）、予約された名前（`x-mismatched-int`または`x-mismatched-map`）の変数を代わりに返します。これにより、型ミスマッチによるパニックを防ぎ、問題のある操作を別の変数にリダイレクトすることで、エラーを可視化します。
    *   もし変数が見つからない場合、新しい変数を初期化して`vars`マップに登録し、それを返します。

5.  **APIの変更と追加**:
    既存の関数名が、扱う変数の型を明確にするために変更されました。
    *   `Increment` -> `IncrementInt`
    *   `Set` -> `SetInt`
    *   `Get` -> `GetInt`
    さらに、`mapVar`を操作するための新しい関数が追加されました。
    *   `IncrementMap(name string, key string, inc int)`: マップ変数の特定のキーの値を増減させます。
    *   `SetMap(name string, key string, value int)`: マップ変数の特定のキーの値を設定します。
    *   `GetMap(name string, key string) int`: マップ変数の特定のキーの値を取得します。

6.  **`String()`関数の変更**:
    すべてのエクスポート変数を文字列として出力する`String()`関数も、`intVars`ではなく`vars`マップをイテレートするように変更されました。これにより、`exVar`インターフェースの`String()`メソッドが呼び出され、各変数の適切な文字列表現が得られます。

## コアとなるコードの解説

### `exVar`インターフェースと具象型の導入

*   `exVar`インターフェースは、エクスポートされるすべての変数が共通して持つべき`String()`メソッドを定義します。これにより、異なる型の変数を統一的に扱うための契約が確立されます。
*   `intVar`は`int`型、`mapVar`は`map[string]int`型をそれぞれラップし、`exVar`インターフェースの`String()`メソッドを実装しています。これにより、これらの具象型が`exVar`として扱えるようになります。

### `vars`マップによる一元管理

*   以前は`intVars`と`mapVars`という別々のマップで管理されていた変数が、`vars = make(map[string] exVar)`という単一のマップで管理されるようになりました。これにより、変数の種類が増えてもグローバルな状態管理がシンプルになります。

### `getOrInitIntVar`と`getOrInitMapVar`関数

*   これらの関数は、指定された名前の変数を`vars`マップから取得し、必要であれば初期化します。
*   最も重要なのは、**型ミスマッチのハンドリング**です。例えば、`IncrementInt("myVar", 1)`が呼び出された際に、`myVar`が既に`mapVar`として登録されていた場合、`getOrInitIntVar`は`myVar`を`intVar`として扱う代わりに、`x-mismatched-int`という予約された名前の`intVar`を返します。これにより、プログラムのクラッシュを防ぎつつ、開発者に型ミスマッチの問題を通知する（`x-mismatched-int`の値を監視することで）メカニズムを提供します。これは、Goの初期段階におけるエラーハンドリングと堅牢性の考慮を示しています。

### `IncrementInt`, `SetInt`, `GetInt` および `IncrementMap`, `SetMap`, `GetMap`

*   これらの関数は、それぞれ整数型とマップ型の変数を操作するための公開APIです。
*   内部的には、`getOrInitIntVar`や`getOrInitMapVar`を呼び出して適切な`exVar`を取得し、その具象型に型アサーション（`*intVar`や`*mapVar`へのポインタ操作）を行って値を更新または取得します。これにより、外部からは型に応じた明確なAPIが提供されつつ、内部ではインターフェースによる抽象化が活用されています。

### テストファイルの変更

*   `exvar_test.go`では、新しいAPI（`GetInt`, `IncrementInt`, `GetMap`, `IncrementMap`など）を使用するようにテストが更新されています。
*   特に`TestMismatchedCounters`は、型ミスマッチが発生した場合の`x-mismatched-int`や`x-mismatched-map`へのリダイレクトが正しく機能するかを検証しています。これは、このコミットの重要な設計意図の一つである堅牢性を保証するためのテストです。

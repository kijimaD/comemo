# [インデックス 26021] ファイルの概要

このコミットは、Go言語の標準ライブラリ`math/rand`パッケージにおける`Float64()`および`Float32()`関数の乱数の一様性を改善することを目的としています。具体的には、これらの関数が生成する浮動小数点数が`1.0`に丸められてしまう稀なケースにおいて、以前は`0.0`に強制的にマッピングしていた挙動を改め、乱数を再生成する（`goto again`）方式に変更することで、乱数分布の一様性を回復させています。

## 変更の背景

`math/rand`パッケージの`Float64()`および`Float32()`関数は、`[0.0, 1.0)`の半開区間（0.0を含み、1.0を含まない）の浮動小数点乱数を生成するように設計されています。しかし、以前の実装では、`r.Int63()`によって生成された63ビット整数を`1 << 63`で割ることで`float64`値を生成する際に、ごく稀に結果が`1.0`に丸められてしまうことがありました。

この`1.0`という結果は、`[0.0, 1.0)`の区間外であるため、以前のコードではこれを`0.0`に強制的にマッピングしていました。この「`1.0`を`0.0`に置換する」という処理は、結果が区間内に収まることを保証する一方で、乱数の一様性を損なうという問題を引き起こしていました。具体的には、`0.0`が他の値よりもわずかに多く出現する可能性があり、乱数分布が厳密には一様ではなくなっていました。

この問題はGo issue #12290として報告され、`math/rand.Float64`が純粋に一様ではないことが議論されました。特に、浮動小数点数の表現の性質上、0に近い値の方が1に近い値よりも表現可能な数が密であるため、1を0にマッピングすると0の確率が理論的に過剰になるという点が指摘されました。このコミットは、この一様性の問題を解決し、より正確な乱数分布を実現するために導入されました。

## 前提知識の解説

### 1. `math/rand`パッケージと乱数生成
Go言語の`math/rand`パッケージは、擬似乱数ジェネレータを提供します。これは、シード値に基づいて決定論的な数列を生成するため、厳密には「真の乱数」ではありませんが、多くのアプリケーションで十分なランダム性を提供します。
- `Int63()`: 符号なし63ビットの擬似乱数整数を生成します。これは`Float64()`の基盤となります。
- `Float64()`: `[0.0, 1.0)`の範囲の`float64`型の擬似乱数を生成します。
- `Float32()`: `[0.0, 1.0)`の範囲の`float32`型の擬似乱数を生成します。

### 2. 浮動小数点数（IEEE 754）
コンピュータにおける浮動小数点数は、IEEE 754標準で定義されており、有限のビット数で実数を近似的に表現します。
- **`float64`**: 倍精度浮動小数点数で、通常64ビット（符号1ビット、指数11ビット、仮数52ビット）で表現されます。
- **`float32`**: 単精度浮動小数点数で、通常32ビット（符号1ビット、指数8ビット、仮数23ビット）で表現されます。
浮動小数点数は、その性質上、0に近いほど表現できる値が密になり、絶対値が大きくなるにつれて疎になります。また、すべての実数を正確に表現できるわけではなく、丸め誤差が発生します。

### 3. 乱数の一様性
乱数の一様性とは、生成される乱数が特定の範囲内で均等に分布していることを指します。例えば、`[0.0, 1.0)`の範囲で一様な乱数であれば、この区間内のどのサブ区間も同じ確率で乱数が出現するべきです。乱数の一様性は、シミュレーション、統計分析、ゲームなど、多くの分野で重要となります。

### 4. 丸め誤差
浮動小数点演算では、計算結果が正確に表現できない場合に、最も近い表現可能な値に丸められます。この丸め処理によって、意図しない結果が生じることがあります。今回のケースでは、`r.Int63() / (1 << 63)`の計算結果が、本来`1.0`未満であるべきにもかかわらず、丸めによって`1.0`になってしまうことが問題でした。

## 技術的詳細

このコミットの技術的詳細を理解するためには、`Float64()`がどのように乱数を生成しているかを深く掘り下げる必要があります。

1.  **初期の乱数生成**: `Float64()`はまず、`r.Int63()`によって生成された63ビットの符号なし整数を`float64`型に変換し、それを`1 << 63`（つまり`2^63`）で割ることで、`[0.0, 1.0)`の範囲の浮動小数点数を生成しようとします。
    ```go
    f := float64(r.Int63()) / (1 << 63)
    ```
    ここで、`r.Int63()`が生成する最大値は`2^63 - 1`です。したがって、理論的には`float64(2^63 - 1) / 2^63`という計算になり、これは厳密に`1.0`未満の値になります。

2.  **丸めによる`1.0`の発生**: しかし、`float64`の精度には限界があります。`float64(r.Int63())`の変換やその後の除算において、ごく稀に丸め誤差が発生し、結果が正確に`1.0`になってしまうことがあります。この現象は、`r.Int63()`が`2^63 - 1`に近い非常に大きな値を生成した場合に起こりえます。コミットメッセージによると、この事象は「1/2⁵³の頻度」で発生するとされています。これは、`float64`の仮数部が52ビットであることと関連しています。

3.  **以前の`1.0`から`0.0`へのマッピングの問題**: 以前の実装では、この`f == 1`となった場合に、`f = 0`としていました。
    ```go
    if f == 1 {
        f = 0
    }
    ```
    このアプローチは、結果が`[0.0, 1.0)`の範囲に収まることを保証しますが、乱数の一様性を損ないます。なぜなら、`0.0`という値は、通常の乱数生成プロセスで生成される確率に加えて、`1.0`に丸められた値が強制的に`0.0`に変換される確率も加わるため、他の値よりも出現頻度が高くなってしまうからです。特に、浮動小数点数の表現密度が0に近いほど高いため、この「1を0にマッピングする」という行為は、0の過剰表現を理論的に大きくする原因となります。

4.  **新しい「再試行」アプローチ**: このコミットでは、`f == 1`となった場合に`f = 0`とする代わりに、`goto again`を使用して乱数生成プロセスを最初からやり直すように変更しました。
    ```go
    again:
    f := float64(r.Int63()) / (1 << 63)
    if f == 1 {
        goto again // resample; this branch is taken O(never)
    }
    return f
    ```
    この「再試行」アプローチは、`1.0`という不正な値が生成された場合に、その値を破棄して新しい乱数を生成し直すため、`0.0`の過剰表現を防ぎ、乱数分布の一様性を回復させます。`1.0`が生成される頻度は非常に稀であるため、この再試行によるパフォーマンスへの影響は無視できるほど小さいと判断されています。

5.  **`Float32()`への影響**: `Float32()`関数は、内部で`Float64()`を呼び出し、その結果を`float32`にキャストすることで乱数を生成しています。
    ```go
    f := float32(r.Float64())
    if f == 1 {
        goto again // resample; this branch is taken O(very rarely)
    }
    return f
    ```
    `Float64()`が改善されたことで、`Float32()`も間接的に恩恵を受けますが、`float32`へのキャスト時にも同様に丸め誤差によって`1.0`が発生する可能性があります。そのため、`Float32()`にも同様の`goto again`ロジックが適用され、`1.0`が生成された場合には再試行するようになっています。これにより、`Float32()`においても一様性が保証されます。

この変更は、既存の乱数ストリーム（シード値から生成される乱数のシーケンス）に与える影響を最小限に抑えつつ、乱数の一様性を改善するという点で非常に重要です。

## コアとなるコードの解説

### `Float64()`関数の変更点

1.  **コメントの変更**:
    -   以前のコメントでは、`1.0`に丸められた値を`0.0`にマッピングする理由として、「0が過小評価されていたため、1を0にマッピングすることでバランスが回復する」と説明されていました。
    -   新しいコメントでは、この「1を0にマッピングする」方法が、0に近い`float64`値の密度が高いという性質上、「0を返す確率の理論的に有意なオーバーシュート」を引き起こすことを明確に指摘しています。
    -   そして、その代わりに「1に丸められた場合は、もう一度試す」という新しいアプローチが導入されたことを説明しています。

2.  **`again:`ラベルの追加**:
    -   `f := float64(r.Int63()) / (1 << 63)`の行の直前に`again:`というラベルが追加されました。これは`goto`文のターゲットとなります。

3.  **`if f == 1`ブロックの変更**:
    -   以前は`f = 0`としていた箇所が、`goto again`に変更されました。
    -   これにより、`f`が`1.0`になった場合、乱数生成の処理が`again:`ラベルの場所から再開され、新しい乱数が生成されるようになります。この再試行は、`1.0`が生成される頻度が非常に低いため、パフォーマンスにほとんど影響を与えません。

### `Float32()`関数の変更点

1.  **コメントの変更**:
    -   `Float32()`も`Float64()`と同様に、`1.0`を`0.0`にマッピングする以前のロジックに関するコメントが削除されました。これは、`Float64()`の変更に伴い、`Float32()`も同様の「再試行」ロジックを採用するためです。

2.  **`again:`ラベルの追加**:
    -   `f := float32(r.Float64())`の行の直前に`again:`というラベルが追加されました。

3.  **`if f == 1`ブロックの変更**:
    -   `Float64()`と同様に、`f = 0`としていた箇所が`goto again`に変更されました。
    -   `Float32()`は`Float64()`の結果を`float32`にキャストするため、ここでも丸め誤差によって`1.0`が発生する可能性があります。この変更により、`Float32()`でも`1.0`が生成された場合には再試行が行われ、一様性が保たれます。

これらの変更により、`math/rand`パッケージの`Float64()`と`Float32()`は、`[0.0, 1.0)`の範囲でより厳密に一様な乱数を生成するようになりました。

## 参考にした情報源リンク

*   Go issue 12290, titled "math/rand: rand.Float64 is not purely uniform," discusses the non-uniformity of the `math/rand.Float64()` function in the Go standard library. The issue was opened on August 24, 2015.
*   The core of the problem stems from how `Float64()` generates floating-point numbers from uniformly distributed 63-bit integers produced by `Int63()`. While `Int63()` provides uniform integer distribution, the conversion to `float64` values in the half-open interval `[0.0, 1.0)` does not maintain perfect uniformity. This is due to the inherent nature of floating-point representation, where numbers are not evenly distributed across the range; there are more representable `float64` values closer to 0 than to 1.
*   Specifically, the mantissa of a `float64` is 52 bits. The original implementation of `Float64()` involved dividing the result of `Int63()` by `(1 << 63)`. To ensure the result was strictly less than 1.0, any value that would round up to 1.0 was effectively mapped to 0.0. This process, while ensuring the correct range, introduced a slight deviation from perfect uniformity.
*   During the discussion, alternative implementations, such as those used in Mersenne Twister algorithms, were suggested to improve uniformity. However, a significant concern raised by the Go team was the desire to preserve the existing value stream generated by `(*Rand).Float64` for compatibility and determinism across Go releases. Changing the algorithm would alter the sequence of numbers produced, which could impact applications relying on reproducible random sequences.
*   Ultimately, the issue was added to the "Unplanned milestone," and the `math/rand.Float64` documentation continues to describe its output as a "pseudo-random number in the half-open interval [0.0, 1.0)," without explicitly guaranteeing perfect uniformity. For applications requiring higher quality or more rigorously uniform random numbers, especially in security-sensitive contexts, the `crypto/rand` package is recommended, or users might consider the `math/rand/v2` package, which offers improved performance and quality.

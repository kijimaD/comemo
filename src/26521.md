このコミットは、Goランタイムの`src/runtime/cgo_mmap.go`ファイルに対する変更です。このファイルは、GoプログラムがCgoを介して`mmap`システムコールを呼び出す際のメモリマッピング処理を扱っています。特に、Goのガベージコレクションにおけるライトバリアと`mmap`の戻り値の扱いに起因する潜在的な問題を解決することを目的としています。

## 変更の背景

このコミットの背景には、Goのガベージコレクタ (GC) の「ライトバリア (write barrier)」と、`mmap`システムコールの戻り値の特殊な性質が関係しています。

GoのGCは、プログラムが実行中にメモリを解放する際に、ポインタの変更を監視するためにライトバリアを使用します。ライトバリアは、ポインタが書き換えられる際に特定の処理（例えば、GCがオブジェクトを追跡できるようにマークする）を挿入するメカニズムです。これにより、GCが実行中でもプログラムが安全に動作し、誤って使用中のメモリが解放されることを防ぎます。

しかし、`mmap`システムコールは、成功時にはマップされたメモリ領域へのポインタを返し、失敗時にはエラーコード（通常は`-1`）を返します。このエラーコードは、ポインタとして解釈されると無効なアドレスとなり、Goの`unsafe.Pointer`型で受け取った場合に問題を引き起こす可能性があります。特に、`unsafe.Pointer`型の変数に`mmap`の戻り値を代入する際にライトバリアが発動すると、その値がポインタであるかエラーコードであるかを区別できず、GCが誤った動作をする可能性がありました。

このコミットは、この問題を一時的に回避するためのものです。具体的には、`mmap`の戻り値を`unsafe.Pointer`として直接扱うのではなく、`uintptr`として一時的に保持することで、ライトバリアが不要なタイミングで発動するのを防ぎます。コミットメッセージにある「For 1.7 we should fix mmap properly to avoid using the same value as both a pointer and an errno value.」という記述から、これは根本的な解決策ではなく、Go 1.7でのより適切な`mmap`の戻り値のハンドリングに向けた暫定的な修正であることがわかります。

この問題は、GoのIssue #14149で報告されていました。

## 前提知識の解説

### Goランタイム

Goランタイムは、Goプログラムの実行を管理するシステムです。ガベージコレクション、ゴルーチン（軽量スレッド）のスケジューリング、メモリ管理、システムコールとのインターフェースなど、Goプログラムが動作するために必要な低レベルの機能を提供します。Goプログラムは、Goランタイムなしには実行できません。

### Cgo

Cgoは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoのツールです。これにより、既存のCライブラリをGoプログラムで利用したり、パフォーマンスが重要な部分をCで記述したりすることが可能になります。Cgoを使用する際には、GoとCのメモリモデルや型システムの違いを理解し、`unsafe.Pointer`などを適切に利用する必要があります。

### mmapシステムコール

`mmap`は、Unix系OSで提供されるシステムコールの一つで、ファイルやデバイスをプロセスの仮想アドレス空間にマッピングするために使用されます。これにより、ファイルの内容をメモリとして直接アクセスできるようになり、ディスクI/Oの効率化やプロセス間通信（共有メモリ）などに利用されます。`mmap`は、成功時にはマップされたメモリ領域の開始アドレスを返し、失敗時には`MAP_FAILED`（通常は`-1`）を返します。

### ライトバリア (Write Barrier)

ライトバリアは、Goの並行ガベージコレクタにおいて重要なメカニズムです。GCがメモリをスキャンしている最中に、プログラム（ミューテータ）がポインタを書き換えることで、GCがオブジェクトを見落とすことを防ぎます。GoのGCは、三色マーク＆スイープ方式を採用しており、ライトバリアはポインタの書き込み時に、書き込まれるオブジェクトがGCによって適切にマークされるように介入します。これにより、GCがプログラムの実行を長時間停止させることなく、メモリを安全に管理できます。

### unsafe.Pointerとuintptr

*   **`unsafe.Pointer`**: Goの`unsafe`パッケージに含まれる特殊な型で、C言語の`void*`に似ています。任意の型のポインタと相互に変換可能であり、Goの型安全性を一時的にバイパスして低レベルのメモリ操作を可能にします。`unsafe.Pointer`はGCによって追跡されるため、`unsafe.Pointer`が指すオブジェクトはGCの対象から外れません。しかし、ポインタ演算は直接行えません。
*   **`uintptr`**: 符号なし整数型で、ポインタのビットパターンを保持するのに十分な大きさを持っています。`uintptr`はメモリアドレスを単なる数値として扱います。`unsafe.Pointer`とは異なり、`uintptr`はGCによって追跡されません。そのため、`uintptr`のみがオブジェクトへの参照を保持している場合、GCはそのオブジェクトを解放してしまう可能性があります。しかし、`uintptr`は整数であるため、ポインタ演算を行うことができます。`unsafe.Pointer`と`uintptr`は相互に変換可能ですが、その使用には細心の注意が必要です。

### systemstack

`systemstack`は、Goランタイムの内部関数で、現在のゴルーチンをシステムスタックに切り替えて、特定の関数を実行するために使用されます。Goのゴルーチンは独自のスタック（ユーザー空間スタック）を持っていますが、システムコールやGCなどの低レベルの操作は、より安全で固定されたサイズのシステムスタック上で実行される必要があります。`systemstack`は、このような状況でスタックを切り替える役割を担います。

## 技術的詳細

このコミットが対処している技術的な問題は、`cgo`を介して`mmap`システムコールを呼び出す際の、Goのライトバリアと`mmap`の戻り値の間のミスマッチです。

`mmap`システムコールは、成功時にはメモリ領域への有効なポインタを返しますが、失敗時にはエラーを示す`-1`を返します。Goの`cgo`ラッパーである`callCgoMmap`関数は、この`mmap`の戻り値を`unsafe.Pointer`型で受け取るように定義されていました。

Goのガベージコレクタは、`unsafe.Pointer`型の変数への書き込みを監視し、ライトバリアを適用します。ライトバリアは、書き込まれる値が有効なポインタであると仮定して動作します。しかし、`mmap`が失敗して`-1`を返した場合、この`-1`は有効なポインタではありません。`unsafe.Pointer`型の変数に`-1`が代入される際にライトバリアが発動すると、GCがこの無効な値をポインタとして解釈しようとし、予期せぬ動作やクラッシュを引き起こす可能性がありました。特に、GCがこの`-1`を指すオブジェクトを追跡しようとすると、メモリ破壊につながる恐れがあります。

この問題は、`mmap`の戻り値が「ポインタ」と「エラーコード」という二つの異なる意味を持つ値を、単一の型（この場合は`unsafe.Pointer`）で表現していることに起因します。Goの型システムとGCは、このような曖昧な値の扱いに対応していません。

このコミットは、この問題を回避するために、`mmap`の戻り値を一時的にGCの監視対象外である`uintptr`型で保持するというアプローチを取っています。これにより、`mmap`の戻り値が`-1`であっても、ライトバリアが誤って発動することなく、安全に処理できるようになります。

## コアとなるコードの解説

変更の核心は、`mmap`関数内で`callCgoMmap`の戻り値を扱う方法と、`callCgoMmap`自体の戻り値の型にあります。

1.  **`mmap`関数の変更**:
    *   変更前: `mmap`関数は`ret unsafe.Pointer`という名前付き戻り値を持っていました。`systemstack`内で`ret = callCgoMmap(...)`と直接代入していました。
    *   変更後: `mmap`関数は名前付き戻り値ではなく、直接`unsafe.Pointer`を返すようになりました。そして、`systemstack`のクロージャ内で`var ret uintptr`というローカル変数を宣言し、`callCgoMmap`の戻り値をこの`uintptr`型の`ret`に代入しています。`systemstack`の実行後、`unsafe.Pointer(ret)`として`uintptr`を`unsafe.Pointer`にキャストし直して返しています。

    この変更の意図は、コメントに明記されています。
    ```go
    // Make ret a uintptr so that writing to it in the
    // function literal does not trigger a write barrier.
    // A write barrier here could break because of the way
    // that mmap uses the same value both as a pointer and
    // an errno value.
    // TODO: Fix mmap to return two values.
    ```
    `uintptr`はGCによって追跡されないため、`uintptr`型の変数への書き込みはライトバリアをトリガーしません。これにより、`mmap`がエラーコード（`-1`）を返した場合でも、ライトバリアが誤って発動し、GCが不正なポインタを処理しようとする問題を回避できます。

2.  **`callCgoMmap`関数の変更**:
    *   変更前: `func callCgoMmap(...) unsafe.Pointer`
    *   変更後: `func callCgoMmap(...) uintptr`

    `callCgoMmap`はアセンブリで実装されており、Cgoを介して実際の`mmap`システムコールを呼び出します。この関数の戻り値の型を`unsafe.Pointer`から`uintptr`に変更することで、`mmap`の生の結果（ポインタまたはエラーコード）を、Goの型システムやGCのセマンティクスに影響を与えることなく、純粋な数値として扱うことが可能になります。これにより、`mmap`関数内で`uintptr`型のローカル変数`ret`に代入する際に型の一貫性が保たれます。

この修正は、`mmap`の戻り値がポインタとエラーコードという二重の意味を持つという根本的な問題に対する「暫定的な」回避策です。コメントにある`TODO: Fix mmap to return two values.`は、将来的には`mmap`のGoラッパーが、成功した場合はポインタと`nil`エラー、失敗した場合はゼロポインタと非`nil`エラーというように、Goの慣習に従って二つの値を返すように変更されるべきであることを示唆しています。これにより、`unsafe.Pointer`と`uintptr`間の変換やライトバリアの回避といった複雑なロジックが不要になり、よりクリーンで安全なコードになります。

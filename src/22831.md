# [インデックス 22831] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）の動作、特にコンカレントGCの開始タイミングに関する改善です。変更は主に`src/runtime/mgc.go`と`src/runtime/proc1.go`の2つのファイルにわたります。

- `src/runtime/mgc.go`: ガベージコレクションの主要なロジックとトリガーを管理するファイルです。この変更では、GC開始のトリガーに達した際のコンカレントGCのスケジューリング方法が修正されています。
- `src/runtime/proc1.go`: Goランタイムのスケジューラとゴルーチン（G）の管理に関する基本的な関数が含まれるファイルです。この変更では、GCゴルーチンを即座に実行するための新しい関数`readyExecute`が追加されています。

## 変更の背景

Goのガベージコレクション（GC）は、ヒープサイズが特定のトリガーに達したときに開始されます。しかし、このコミット以前のGoランタイムでは、GCがトリガーされた際に、GCを実行するゴルーチン（G）が単に現在のプロセッサ（P）の実行キューの末尾に追加されるだけでした。

この挙動にはいくつかの問題がありました。

1.  **GC開始の遅延**: GCゴルーチンが実行キューの末尾に追加されるため、現在実行中のゴルーチンや、すでにキューに存在する他のゴルーチンが先に実行される可能性がありました。これにより、GCが実際に開始されるまでにタイムラグが生じました。
2.  **ヒープサイズの肥大化**: GCが遅延している間も、ミューテータ（ユーザープログラム）はメモリ割り当てを継続します。その結果、GCが実際に開始される時点では、意図したよりもはるかに大きなヒープサイズになってしまう可能性がありました。これは、メモリ使用量の予測可能性を低下させ、場合によってはメモリ不足につながる可能性もありました。
3.  **予測不可能性**: GC開始までの遅延がスケジューラの状態に依存するため、ヒープがどれだけ肥大化するかが予測困難でした。

このコミットは、これらの問題を解決し、GCトリガーに達した際にコンカレントGCをより迅速かつ予測可能に開始することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の概念について理解しておく必要があります。

### 1. Goのガベージコレクション (GC)

Goはトレース型GCを採用しており、不要になったメモリを自動的に解放します。GoのGCは主に以下のフェーズで構成されます。

*   **マークフェーズ (Mark Phase)**: ライブオブジェクト（到達可能なオブジェクト）を特定し、マークします。Go 1.5以降では、このフェーズの大部分がミューテータと並行して実行される「コンカレントマーク」として実装されています。
*   **マークターミネーションフェーズ (Mark Termination Phase)**: マークフェーズの終了処理を行います。このフェーズはSTW (Stop-The-World) を伴うことがあります。
*   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（不要なオブジェクト）が占めていたメモリを解放し、再利用可能にします。このフェーズもミューテータと並行して実行されます。
*   **スイープターミネーションフェーズ (Sweep Termination Phase)**: スイープフェーズの終了処理を行います。

GoのGCは、ヒープの割り当て量が特定の閾値（GCトリガー）に達すると開始されます。この閾値は、前回のGCでライブだったヒープサイズに基づいて動的に調整されます。

### 2. Goスケジューラ (M, P, G)

Goランタイムは、独自のユーザーレベルスケジューラを持っています。このスケジューラは、以下の3つの主要なエンティティで構成されます。

*   **G (Goroutine)**: Goにおける軽量な実行スレッドです。Goプログラムのすべての並行処理はゴルーチンとして実行されます。
*   **M (Machine)**: オペレーティングシステムのスレッド（OSスレッド）を表します。MはGを実行するためのコンテキストを提供します。
*   **P (Processor)**: 論理プロセッサを表します。PはMにGをディスパッチするためのコンテキストを提供し、実行可能なGのキュー（ローカル実行キュー）を保持します。`GOMAXPROCS`環境変数によって設定されるPの数は、同時に実行できるOSスレッドの最大数を決定します。

Goスケジューラは、Pのローカル実行キューからGを取り出し、M上で実行します。Gがシステムコールなどでブロックされた場合、MはPを解放し、別のMがそのPを引き継いで他のGを実行できます。

### 3. `ready` と `execute` 関数

*   `ready(gp *g, traceskip int)`: 指定されたゴルーチン`gp`を実行可能状態にし、現在のPのローカル実行キューの末尾に追加します。これにより、`gp`は将来的にスケジューラによって選択され、実行されることになります。
*   `execute(gp *g)`: 指定されたゴルーチン`gp`を即座に実行します。これは、現在のゴルーチンを中断し、`gp`に制御を移すような動作をします。

### 4. `mcall` 関数

`mcall`は、現在のゴルーチン（G）のスタックからMのスタックに切り替えて関数を実行するためのランタイム関数です。これは、スケジューラやGCのような低レベルの操作で、現在のGのコンテキストから独立してMのコンテキストで処理を行う必要がある場合に使用されます。

## 技術的詳細

このコミットの核心は、GCトリガーに達した際にコンカレントGCゴルーチン（`bggc.g`）をスケジューリングする方法を変更することにあります。

**変更前の挙動:**
GCトリガーに達すると、`startGC`関数内で`ready(bggc.g, 0)`が呼び出されていました。これは、`bggc.g`を現在のPのローカル実行キューの末尾に追加するだけでした。その結果、以下のような問題が発生していました。

1.  **キューの遅延**: 現在実行中のゴルーチンが完了するまで、またはPの実行キューにある他のゴルーチンがすべて実行されるまで、`bggc.g`は実行されませんでした。
2.  **ミューテータの継続**: GCが開始されるまでの間、ユーザープログラム（ミューテータ）はメモリ割り当てを継続し、ヒープサイズが不必要に増加していました。

**変更後の挙動:**
このコミットでは、`startGC`関数が修正され、新しい関数`readyExecute`が導入されました。

1.  **`startGC`の変更**:
    *   GCトリガーに達し、かつ`bggc.g`がまだ作業中でない場合（`bggc.working == 0`）、GCを開始しようとします。
    *   ここで、現在のMがロックされたゴルーチン（`getg().m.lockedg != nil`）を持っているかどうかをチェックします。
        *   もしロックされたゴルーチンがある場合、`readyExecute`は使用できません（後述の`readyExecute`の制約のため）。この場合、以前と同様に`ready(bggc.g, 0)`を呼び出し、GCゴルーチンを実行キューに追加します。これは、Mが特定のゴルーチンにロックされているため、即座にプリエンプションを行うことができないためです。
        *   ロックされたゴルーチンがない場合、`bggc.lock`をアンロックし、新しく追加された`readyExecute(bggc.g, 0)`を呼び出します。そして、`startGC`関数から即座に`return`します。これにより、GCゴルーチンへの制御の切り替えが迅速に行われます。

2.  **`readyExecute`関数の導入**:
    *   `readyExecute(gp *g, traceskip int)`は、指定されたゴルーチン`gp`を即座に実行するために設計された新しいランタイム関数です。
    *   この関数は`mcall`を使用して、現在のMのコンテキストで実行されます。
    *   **プリエンプション**: `readyExecute`は、現在実行中のゴルーチン（`_g_`）をプリエンプト（中断）します。具体的には、`_g_`のステータスを`_Grunning`から`_Grunnable`に変更し、現在のPのローカル実行キューの先頭ではなく、通常のキュー（`runqput`）に戻します。そして、`dropg()`を呼び出して現在のGのコンテキストを解除します。
    *   **即時実行**: その後、ターゲットのGCゴルーチン`gp`のステータスを`_Gwaiting`から`_Grunnable`に変更し、`execute(gp)`を呼び出して`gp`に制御を直接切り替えます。これにより、GCゴルーチンは他のゴルーチンが実行されるのを待つことなく、直ちに実行を開始できます。
    *   **制約**: `readyExecute`は、現在のMがロックを保持している場合（`_g_.m.locks != 0`）や、Mが特定のゴルーチンにロックされている場合（`_g_.m.lockedg != nil`）には使用できません。これらの条件下では、即座のプリエンプションとコンテキスト切り替えが安全に行えないため、`throw`（パニック）が発生します。

この変更により、GCトリガーに達した際に、Goランタイムは現在のミューテータゴルーチンを中断し、GCゴルーチンに直接制御を渡すことで、GCの開始を大幅に迅速化します。これにより、GC開始までの不要なメモリ割り当てが削減され、ヒープサイズの予測可能性と効率が向上します。

コミットメッセージに記載されているように、この変更は特定のベンチマークにおいて、GCトリガーからスイープターミネーション開始までの時間を10〜30ミリ秒短縮し、トリガー後の割り当てを最大10MB削減する効果がありました。

また、コミットメッセージには、スイープファイナライゼーションがGC開始の遅延の別の原因であるというTODOコメントが追加されています。これは、このコミットが解決した問題とは直交する（独立した）問題であり、将来的な改善点として認識されています。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更点

`startGC`関数は、GCがトリガーされたときにバックグラウンドGCゴルーチン（`bggc.g`）を起動または再開する役割を担っています。

変更前は、`bggc.working == 0`（GCゴルーチンが現在作業中でない）の場合、単に`ready(bggc.g, 0)`を呼び出してGCゴルーチンを実行キューに追加していました。

変更後は、以下のロジックが追加されました。

```go
		if getg().m.lockedg != nil {
			// We can't directly switch to GC on a locked
			// M, so put it on the run queue and someone
			// will get to it.
			ready(bggc.g, 0)
		} else {
			unlock(&bggc.lock)
			readyExecute(bggc.g, 0)
			return
		}
```

*   `getg().m.lockedg != nil` のチェック: これは、現在のM（OSスレッド）が特定のゴルーチンにロックされているかどうかを確認します。例えば、`runtime.LockOSThread()`が呼び出されている場合などです。Mがロックされている場合、そのMは特定のゴルーチンに専属しており、他のゴルーチンへの即座の切り替え（プリエンプション）はできません。この場合、以前と同様に`ready(bggc.g, 0)`を呼び出し、GCゴルーチンを実行キューの末尾に追加します。
*   `else` ブロック: Mがロックされていない通常のケースです。
    *   `unlock(&bggc.lock)`: `startGC`関数は`bggc.lock`を保持して呼び出されるため、`readyExecute`を呼び出す前にロックを解放します。これは、`readyExecute`がMのスタックで実行され、GCゴルーチンに切り替わるため、ロックを保持したままではデッドロックや競合状態を引き起こす可能性があるためです。
    *   `readyExecute(bggc.g, 0)`: 新しく追加された関数を呼び出し、GCゴルーチン`bggc.g`を即座に実行します。
    *   `return`: `readyExecute`が呼び出された後、現在のゴルーチンはプリエンプトされ、GCゴルーチンに制御が移るため、`startGC`関数はここで終了します。

また、`gc`関数内には、スイープファイナライゼーションに関するTODOコメントが追加されました。これは、ヒープが縮小した場合にスイープが不十分になり、GC開始前にミューテータが余分な割り当てを行う可能性があるという、別の最適化の機会を示しています。

### `src/runtime/proc1.go` の変更点

このファイルには、新しい関数`readyExecute`が追加されました。

```go
func readyExecute(gp *g, traceskip int) {
	mcall(func(_g_ *g) {
		// ... (trace logging, error checks) ...

		// Preempt the current g
		casgstatus(_g_, _Grunning, _Grunnable)
		runqput(_g_.m.p, _g_)
		dropg()

		// Ready gp and switch to it
		casgstatus(gp, _Gwaiting, _Grunnable)
		execute(gp)
	})
}
```

*   `mcall(func(_g_ *g) { ... })`: `readyExecute`の主要なロジックは、`mcall`によってMのスタック上で実行される匿名関数内にカプセル化されています。`_g_`は現在実行中のゴルーチンを指します。これにより、現在のゴルーチンのスタックを操作することなく、Mのコンテキストで安全にスケジューリング操作を行うことができます。
*   **エラーチェック**:
    *   `if _g_.m.locks != 0`: 現在のMがランタイムロックを保持している場合、`readyExecute`は実行できません。これは、ロックを保持したままゴルーチンを切り替えると、ロックの所有権が不明確になり、デッドロックや競合状態を引き起こす可能性があるためです。
    *   `if _g_.m.lockedg != nil`: 現在のMが特定のゴルーチンにロックされている場合（`runtime.LockOSThread`など）、即座の切り替えはできません。
    *   `if readgstatus(gp)&^_Gscan != _Gwaiting`: ターゲットのゴルーチン`gp`が`_Gwaiting`状態でない場合、つまり実行可能状態ではない場合、エラーをスローします。`readyExecute`は、待機中のゴルーチンを即座に実行するために設計されています。
*   **現在のGのプリエンプション**:
    *   `casgstatus(_g_, _Grunning, _Grunnable)`: 現在実行中のゴルーチン`_g_`のステータスを`_Grunning`から`_Grunnable`（実行可能）に変更します。これはアトミック操作です。
    *   `runqput(_g_.m.p, _g_)`: プリエンプトされた`_g_`を、現在のPのローカル実行キューに戻します。これにより、`_g_`は後で再びスケジューラによって実行される機会を得ます。
    *   `dropg()`: 現在のMから`_g_`の関連付けを解除します。これにより、Mは新しいゴルーチンを実行する準備ができます。
*   **GCゴルーチンへの切り替え**:
    *   `casgstatus(gp, _Gwaiting, _Grunnable)`: ターゲットのGCゴルーチン`gp`のステータスを`_Gwaiting`から`_Grunnable`に変更します。
    *   `execute(gp)`: `gp`に制御を直接切り替えます。これにより、GCゴルーチンは他のゴルーチンが実行されるのを待つことなく、直ちに実行を開始します。

この`readyExecute`関数は、GCトリガーに達した際に、ミューテータの実行を中断し、GCゴルーチンに優先的にCPU時間を割り当てることで、GCの開始を迅速化し、ヒープの肥大化を抑制する重要な役割を果たします。

このコミットは、Goランタイムのガベージコレクション（GC）の動作、特にコンカレントGCの開始タイミングに関する改善です。変更は主に`src/runtime/mgc.go`と`src/runtime/proc1.go`の2つのファイルにわたります。

- `src/runtime/mgc.go`: ガベージコレクションの主要なロジックとトリガーを管理するファイルです。この変更では、GC開始のトリガーに達した際のコンカレントGCのスケジューリング方法が修正されています。
- `src/runtime/proc1.go`: Goランタイムのスケジューラとゴルーチン（G）の管理に関する基本的な関数が含まれるファイルです。この変更では、GCゴルーチンを即座に実行するための新しい関数`readyExecute`が追加されています。

## 変更の背景

Goのガベージコレクション（GC）は、ヒープサイズが特定のトリガーに達したときに開始されます。しかし、このコミット以前のGoランタイムでは、GCがトリガーされた際に、GCを実行するゴルーチン（G）が単に現在のプロセッサ（P）の実行キューの末尾に追加されるだけでした。

この挙動にはいくつかの問題がありました。

1.  **GC開始の遅延**: GCゴルーチンが実行キューの末尾に追加されるため、現在実行中のゴルーチンや、すでにキューに存在する他のゴルーチンが先に実行される可能性がありました。これにより、GCが実際に開始されるまでにタイムラグが生じました。
2.  **ヒープサイズの肥大化**: GCが遅延している間も、ミューテータ（ユーザープログラム）はメモリ割り当てを継続します。その結果、GCが実際に開始される時点では、意図したよりもはるかに大きなヒープサイズになってしまう可能性がありました。これは、メモリ使用量の予測可能性を低下させ、場合によってはメモリ不足につながる可能性もありました。
3.  **予測不可能性**: GC開始までの遅延がスケジューラの状態に依存するため、ヒープがどれだけ肥大化するかが予測困難でした。

このコミットは、これらの問題を解決し、GCトリガーに達した際にコンカレントGCをより迅速かつ予測可能に開始することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の概念について理解しておく必要があります。

### 1. Goのガベージコレクション (GC)

Goはトレース型GCを採用しており、不要になったメモリを自動的に解放します。GoのGCは主に以下のフェーズで構成されます。

*   **マークフェーズ (Mark Phase)**: ライブオブジェクト（到達可能なオブジェクト）を特定し、マークします。Go 1.5以降では、このフェーズの大部分がミューテータと並行して実行される「コンカレントマーク」として実装されています。
*   **マークターミネーションフェーズ (Mark Termination Phase)**: マークフェーズの終了処理を行います。このフェーズはSTW (Stop-The-World) を伴うことがあります。
*   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（不要なオブジェクト）が占めていたメモリを解放し、再利用可能にします。このフェーズもミューテータと並行して実行されます。
*   **スイープターミネーションフェーズ (Sweep Termination Phase)**: スイープフェーズの終了処理を行います。

GoのGCは、ヒープの割り当て量が特定の閾値（GCトリガー）に達すると開始されます。この閾値は、前回のGCでライブだったヒープサイズに基づいて動的に調整されます。

### 2. Goスケジューラ (M, P, G)

Goランタイムは、独自のユーザーレベルスケジューラを持っています。このスケジューラは、以下の3つの主要なエンティティで構成されます。

*   **G (Goroutine)**: Goにおける軽量な実行スレッドです。Goプログラムのすべての並行処理はゴルーチンとして実行されます。
*   **M (Machine)**: オペレーティングシステムのスレッド（OSスレッド）を表します。MはGを実行するためのコンテキストを提供します。
*   **P (Processor)**: 論理プロセッサを表します。PはMにGをディスパッチするためのコンテキストを提供し、実行可能なGのキュー（ローカル実行キュー）を保持します。`GOMAXPROCS`環境変数によって設定されるPの数は、同時に実行できるOSスレッドの最大数を決定します。

Goスケジューラは、Pのローカル実行キューからGを取り出し、M上で実行します。Gがシステムコールなどでブロックされた場合、MはPを解放し、別のMがそのPを引き継いで他のGを実行できます。

### 3. `ready` と `execute` 関数

*   `ready(gp *g, traceskip int)`: 指定されたゴルーチン`gp`を実行可能状態にし、現在のPのローカル実行キューの末尾に追加します。これにより、`gp`は将来的にスケジューラによって選択され、実行されることになります。
*   `execute(gp *g)`: 指定されたゴルーチン`gp`を即座に実行します。これは、現在のゴルーチンを中断し、`gp`に制御を移すような動作をします。

### 4. `mcall` 関数

`mcall`は、現在のゴルーチン（G）のスタックからMのスタックに切り替えて関数を実行するためのランタイム関数です。これは、スケジューラやGCのような低レベルの操作で、現在のGのコンテキストから独立してMのコンテキストで処理を行う必要がある場合に使用されます。

## 技術的詳細

このコミットの核心は、GCトリガーに達した際にコンカレントGCゴルーチン（`bggc.g`）をスケジューリングする方法を変更することにあります。

**変更前の挙動:**
GCトリガーに達すると、`startGC`関数内で`ready(bggc.g, 0)`が呼び出されていました。これは、`bggc.g`を現在のPのローカル実行キューの末尾に追加するだけでした。その結果、以下のような問題が発生していました。

1.  **キューの遅延**: 現在実行中のゴルーチンが完了するまで、またはPの実行キューにある他のゴルーチンがすべて実行されるまで、`bggc.g`は実行されませんでした。
2.  **ミューテータの継続**: GCが開始されるまでの間、ユーザープログラム（ミューテータ）はメモリ割り当てを継続し、ヒープサイズが不必要に増加していました。

**変更後の挙動:**
このコミットでは、`startGC`関数が修正され、新しい関数`readyExecute`が導入されました。

1.  **`startGC`の変更**:
    *   GCトリガーに達し、かつ`bggc.g`がまだ作業中でない場合（`bggc.working == 0`）、GCを開始しようとします。
    *   ここで、現在のMがロックされたゴルーチン（`getg().m.lockedg != nil`）を持っているかどうかをチェックします。
        *   もしロックされたゴルーチンがある場合、`readyExecute`は使用できません（後述の`readyExecute`の制約のため）。この場合、以前と同様に`ready(bggc.g, 0)`を呼び出し、GCゴルーチンを実行キューに追加します。これは、Mが特定のゴルーチンにロックされているため、即座にプリエンプションを行うことができないためです。
        *   ロックされたゴルーチンがない場合、`bggc.lock`をアンロックし、新しく追加された`readyExecute(bggc.g, 0)`を呼び出します。そして、`startGC`関数から即座に`return`します。これにより、GCゴルーチンへの制御の切り替えが迅速に行われます。

2.  **`readyExecute`関数の導入**:
    *   `readyExecute(gp *g, traceskip int)`は、指定されたゴルーチン`gp`を即座に実行するために設計された新しいランタイム関数です。
    *   この関数は`mcall`を使用して、現在のMのコンテキストで実行されます。
    *   **プリエンプション**: `readyExecute`は、現在実行中のゴルーチン（`_g_`）をプリエンプト（中断）します。具体的には、`_g_`のステータスを`_Grunning`から`_Grunnable`に変更し、現在のPのローカル実行キューの先頭ではなく、通常のキュー（`runqput`）に戻します。そして、`dropg()`を呼び出して現在のGのコンテキストを解除します。
    *   **即時実行**: その後、ターゲットのGCゴルーチン`gp`のステータスを`_Gwaiting`から`_Grunnable`に変更し、`execute(gp)`を呼び出して`gp`に制御を直接切り替えます。これにより、GCゴルーチンは他のゴルーチンが実行されるのを待つことなく、直ちに実行を開始できます。
    *   **制約**: `readyExecute`は、現在のMがロックを保持している場合（`_g_.m.locks != 0`）や、Mが特定のゴルーチンにロックされている場合（`_g_.m.lockedg != nil`）には使用できません。これらの条件下では、即座のプリエンプションとコンテキスト切り替えが安全に行えないため、`throw`（パニック）が発生します。

この変更により、GCトリガーに達した際に、Goランタイムは現在のミューテータゴルーチンを中断し、GCゴルーチンに直接制御を渡すことで、GCの開始を大幅に迅速化します。これにより、GC開始までの不要なメモリ割り当てが削減され、ヒープサイズの予測可能性と効率が向上します。

コミットメッセージに記載されているように、この変更は特定のベンチマークにおいて、GCトリガーからスイープターミネーション開始までの時間を10〜30ミリ秒短縮し、トリガー後の割り当てを最大10MB削減する効果がありました。

また、コミットメッセージには、スイープファイナライゼーションがGC開始の遅延の別の原因であるというTODOコメントが追加されています。これは、このコミットが解決した問題とは直交する（独立した）問題であり、将来的な改善点として認識されています。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更点

`startGC`関数は、GCがトリガーされたときにバックグラウンドGCゴルーチン（`bggc.g`）を起動または再開する役割を担っています。

変更前は、`bggc.working == 0`（GCゴルーチンが現在作業中でない）の場合、単に`ready(bggc.g, 0)`を呼び出してGCゴルーチンを実行キューに追加していました。

変更後は、以下のロジックが追加されました。

```go
		if getg().m.lockedg != nil {
			// We can't directly switch to GC on a locked
			// M, so put it on the run queue and someone
			// will get to it.
			ready(bggc.g, 0)
		} else {
			unlock(&bggc.lock)
			readyExecute(bggc.g, 0)
			return
		}
```

*   `getg().m.lockedg != nil` のチェック: これは、現在のM（OSスレッド）が特定のゴルーチンにロックされているかどうかを確認します。例えば、`runtime.LockOSThread()`が呼び出されている場合などです。Mがロックされている場合、そのMは特定のゴルーチンに専属しており、他のゴルーチンへの即座の切り替え（プリエンプション）はできません。この場合、以前と同様に`ready(bggc.g, 0)`を呼び出し、GCゴルーチンを実行キューの末尾に追加します。
*   `else` ブロック: Mがロックされていない通常のケースです。
    *   `unlock(&bggc.lock)`: `startGC`関数は`bggc.lock`を保持して呼び出されるため、`readyExecute`を呼び出す前にロックを解放します。これは、`readyExecute`がMのスタックで実行され、GCゴルーチンに切り替わるため、ロックを保持したままではデッドロックや競合状態を引き起こす可能性があるためです。
    *   `readyExecute(bggc.g, 0)`: 新しく追加された関数を呼び出し、GCゴルーチン`bggc.g`を即座に実行します。
    *   `return`: `readyExecute`が呼び出された後、現在のゴルーチンはプリエンプトされ、GCゴルーチンに制御が移るため、`startGC`関数はここで終了します。

また、`gc`関数内には、スイープファイナライゼーションに関するTODOコメントが追加されました。これは、ヒープが縮小した場合にスイープが不十分になり、GC開始前にミューテータが余分な割り当てを行う可能性があるという、別の最適化の機会を示しています。

### `src/runtime/proc1.go` の変更点

このファイルには、新しい関数`readyExecute`が追加されました。

```go
func readyExecute(gp *g, traceskip int) {
	mcall(func(_g_ *g) {
		// ... (trace logging, error checks) ...

		// Preempt the current g
		casgstatus(_g_, _Grunning, _Grunnable)
		runqput(_g_.m.p, _g_)
		dropg()

		// Ready gp and switch to it
		casgstatus(gp, _Gwaiting, _Grunnable)
		execute(gp)
	})
}
```

*   `mcall(func(_g_ *g) { ... })`: `readyExecute`の主要なロジックは、`mcall`によってMのスタック上で実行される匿名関数内にカプセル化されています。`_g_`は現在実行中のゴルーチンを指します。これにより、現在のゴルーチンのスタックを操作することなく、Mのコンテキストで安全にスケジューリング操作を行うことができます。
*   **エラーチェック**:
    *   `if _g_.m.locks != 0`: 現在のMがランタイムロックを保持している場合、`readyExecute`は実行できません。これは、ロックを保持したままゴルーチンを切り替えると、ロックの所有権が不明確になり、デッドロックや競合状態を引き起こす可能性があるためです。
    *   `if _g_.m.lockedg != nil`: 現在のMが特定のゴルーチンにロックされている場合（`runtime.LockOSThread`など）、即座の切り替えはできません。
    *   `if readgstatus(gp)&^_Gscan != _Gwaiting`: ターゲットのゴルーチン`gp`が`_Gwaiting`状態でない場合、つまり実行可能状態ではない場合、エラーをスローします。`readyExecute`は、待機中のゴルーチンを即座に実行するために設計されています。
*   **現在のGのプリエンプション**:
    *   `casgstatus(_g_, _Grunning, _Grunnable)`: 現在実行中のゴルーチン`_g_`のステータスを`_Grunning`から`_Grunnable`（実行可能）に変更します。これはアトミック操作です。
    *   `runqput(_g_.m.p, _g_)`: プリエンプトされた`_g_`を、現在のPのローカル実行キューに戻します。これにより、`_g_`は後で再びスケジューラによって実行される機会を得ます。
    *   `dropg()`: 現在のMから`_g_`の関連付けを解除します。これにより、Mは新しいゴルーチンを実行する準備ができます。
*   **GCゴルーチンへの切り替え**:
    *   `casgstatus(gp, _Gwaiting, _Grunnable)`: ターゲットのGCゴルーチン`gp`のステータスを`_Gwaiting`から`_Grunnable`に変更します。
    *   `execute(gp)`: `gp`に制御を直接切り替えます。これにより、GCゴルーチンは他のゴルーチンが実行されるのを待つことなく、直ちに実行を開始します。

この`readyExecute`関数は、GCトリガーに達した際に、ミューテータの実行を中断し、GCゴルーチンに優先的にCPU時間を割り当てることで、GCの開始を迅速化し、ヒープの肥大化を抑制する重要な役割を果たします。

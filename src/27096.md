# [インデックス 27096] ファイルの概要

このコミットは、Go言語の`crypto/x509/pkix`パッケージにおけるCRL (Certificate Revocation List) のバージョン処理に関する修正です。具体的には、CRLのバージョンをASN.1エンコーディングする際のデフォルト値を、RFC 5280の解釈とOpenSSLの実装に合わせるために変更しています。これにより、CRLのバージョンが「v1」の場合にワイヤー上で「0」として表現されるように調整され、相互運用性が向上します。

## コミット

```
crypto/x509/pkix: make 'v1' the default CRL version.

PKIX versions are off-by-one, so v1 is actually a zero on the wire, v2
is a one, and so on.

The RFC says that the version in a CRL is optional, but doesn't say what
the default is. Since v2 is the only accepted version, I had made the
default v2. However, OpenSSL considers the default to be v1. Also, if
the default is v2 and the element is optional then we'll never actually
write v2 on the wire. That's contrary to the RFC which clearly assumes
that v2 will be expressed on the wire in some cases.

Therefore, this change aligns with OpenSSL and assumes that v1 is the
default CRL version.

Fixes #13931

[1] https://tools.ietf.org/html/rfc5280#section-5.1

Reviewed-on: https://go-review.googlesource.com/20544
Reviewed-by: Brad Fitzpatrick <bradfitz@golang.org>
```

## 元コミット内容

Go言語の`crypto/x509/pkix`パッケージにおいて、CRL (Certificate Revocation List) のデフォルトバージョンを「v1」に設定する変更です。PKIXのバージョンは「オフバイワン」であり、v1はワイヤー上では0、v2は1として表現されます。RFC 5280ではCRLのバージョンはオプションとされていますが、デフォルト値については明記されていません。以前の実装では、唯一受け入れられているバージョンがv2であるという理由から、デフォルトをv2としていました。しかし、OpenSSLはデフォルトをv1と解釈しており、また、もしデフォルトがv2で要素がオプションである場合、ワイヤー上にv2が書き込まれることは決してありません。これは、RFCがv2がワイヤー上で表現される場合があることを明確に想定していることに反します。このため、OpenSSLとの整合性を図り、v1をデフォルトのCRLバージョンと見なすように変更されました。この変更はIssue #13931を修正します。

## 変更の背景

この変更の背景には、X.509証明書およびCRLの標準を定義するRFC 5280の解釈と、広く利用されている暗号ライブラリであるOpenSSLとの相互運用性の問題がありました。

1.  **RFC 5280の曖昧さ**: RFC 5280のセクション5.1では、CRLのバージョンフィールドがオプションであると規定されていますが、そのデフォルト値については明示されていません。この曖昧さが、異なる実装間での解釈の不一致を引き起こしていました。
2.  **Go言語の初期実装**: Go言語の`crypto/x509/pkix`パッケージの初期実装では、「v2が唯一受け入れられているバージョンである」という理由から、CRLのデフォルトバージョンをv2（ワイヤー上では1）としていました。
3.  **OpenSSLとの不一致**: しかし、OpenSSLはCRLのデフォルトバージョンをv1（ワイヤー上では0、またはフィールドが省略される）と解釈していました。これにより、Goで生成されたCRLとOpenSSLで処理されるCRLの間で互換性の問題が生じる可能性がありました。
4.  **ワイヤー上での表現の問題**: もしデフォルトがv2（ワイヤー上では1）であり、かつバージョンフィールドがオプションである場合、Goの実装はバージョンがv2であってもワイヤー上にバージョン情報を書き出さないことになります。これは、RFCがv2がワイヤー上で明示的に表現されるケースを想定しているという記述と矛盾します。つまり、デフォルト値がワイヤー上で表現されないというASN.1の特性と、RFCの意図との間に齟齬が生じていました。
5.  **相互運用性の確保**: 異なるシステム間でX.509証明書やCRLを交換する際には、厳密な標準準拠と主要な実装との互換性が不可欠です。この不一致を解消し、Goの`crypto/x509`パッケージがより広範なPKIエコシステムとシームレスに連携できるようにするために、OpenSSLの解釈に合わせてデフォルトバージョンをv1に変更する必要がありました。

これらの理由から、Goの`crypto/x509/pkix`パッケージは、CRLのデフォルトバージョンをv1（ワイヤー上では0）に修正することになりました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **PKIX (Public Key Infrastructure X.509)**:
    *   公開鍵基盤 (PKI) は、公開鍵暗号方式を用いてデジタル証明書を発行・管理し、公開鍵の正当性を保証する仕組みです。
    *   X.509は、PKIにおける公開鍵証明書の標準フォーマットを定義するITU-Tの勧告です。PKIXは、インターネット環境でのX.509証明書の使用方法を具体的に定めたものです。
    *   PKIXは、証明書、証明書失効リスト (CRL)、証明書パス検証アルゴリズムなど、PKIの様々な要素を標準化しています。

2.  **X.509 証明書と CRL (Certificate Revocation List)**:
    *   **X.509 証明書**: 公開鍵と、その公開鍵の所有者（エンティティ）の身元情報を結びつけるデジタル文書です。認証局 (CA) によって署名され、公開鍵の信頼性を保証します。
    *   **CRL (Certificate Revocation List)**: 認証局によって発行される、失効した（有効期限内であっても信頼できない）証明書のリストです。証明書が秘密鍵の漏洩、所有者の情報変更、不正使用などの理由で失効した場合、そのシリアル番号がCRLに記載されます。これにより、利用者は証明書がまだ有効であるかを確認できます。

3.  **RFC 5280**:
    *   「Internet X.509 Public Key Infrastructure Certificate and Certificate Revocation List (CRL) Profile」というタイトルのRFC (Request For Comments) です。
    *   X.509 v3証明書とX.509 v2 CRLのフォーマットおよびセマンティクスをインターネットで使用するために詳細に定義しています。
    *   このコミットでは、特にセクション5.1「Certificate Revocation List (CRL) Format」が関連しています。

4.  **ASN.1 (Abstract Syntax Notation One)**:
    *   データ構造を記述するための標準的な記法です。通信プロトコルやデータストレージにおいて、異なるシステム間でデータを交換する際に、データがどのように構造化され、エンコードされるかを定義するために使用されます。
    *   X.509証明書やCRLは、ASN.1で定義された構造を持ち、DER (Distinguished Encoding Rules) などのエンコーディングルールに従ってバイナリ形式に変換されます。

5.  **ASN.1の`DEFAULT`キーワードとエンコーディング**:
    *   ASN.1の定義において、フィールドに`DEFAULT`キーワードが指定されている場合、そのフィールドの値がデフォルト値と一致するときは、ワイヤー上（バイナリエンコーディング）でそのフィールドが省略されることがあります。
    *   これは、データ量を削減し、効率的な通信を可能にするための仕組みです。しかし、この挙動が、RFCの意図と実装の解釈の間に不一致を生じさせることがあります。

6.  **CRLのバージョン**:
    *   CRLにはバージョンフィールドがあり、CRLのフォーマットの進化を示します。
    *   RFC 5280では、CRLのバージョンはv1とv2が定義されています。v2 CRLは、v1にはない拡張機能（CRLエントリ拡張など）をサポートします。
    *   PKIXのバージョンは、ワイヤー上での表現と概念的なバージョン番号が「オフバイワン」の関係にあります。
        *   概念的なv1は、ワイヤー上では0としてエンコードされるか、省略されます。
        *   概念的なv2は、ワイヤー上では1としてエンコードされます。

## 技術的詳細

このコミットの技術的な核心は、Go言語のASN.1マーシャリング/アンマーシャリングにおける`asn1:"optional,default:X"`タグの挙動と、RFC 5280で定義されるCRLのバージョンフィールドの解釈の調整にあります。

1.  **`asn1:"optional,default:X"`タグ**:
    *   Goの`encoding/asn1`パッケージでは、構造体フィールドに`asn1`タグを付与することで、ASN.1エンコーディングの挙動を制御できます。
    *   `optional`キーワードは、そのフィールドがASN.1シーケンス内でオプションであることを示します。つまり、値が存在しない場合でもエラーにはなりません。
    *   `default:X`キーワードは、そのフィールドのデフォルト値を指定します。ASN.1のDER (Distinguished Encoding Rules) エンコーディングでは、フィールドの値がこのデフォルト値と一致する場合、そのフィールドはエンコードされたバイナリストリームから**省略**されます。これは、データ量を削減するための標準的な最適化です。

2.  **CRLバージョンと「オフバイワン」**:
    *   RFC 5280のセクション5.1.1では、`TBSCertificateList`構造体（CRLの主要部分）のバージョンフィールドについて言及しています。
    *   概念的なCRLバージョン（v1, v2など）と、ASN.1エンコードされる整数値の間には「オフバイワン」の関係があります。
        *   CRL v1は、ASN.1では整数値 `0` に対応します。
        *   CRL v2は、ASN.1では整数値 `1` に対応します。
    *   RFC 5280では、バージョンフィールドが省略された場合、それはv1 CRL（つまりASN.1値の0）を意味すると解釈されます。

3.  **以前の実装の問題点**:
    *   コミットメッセージによると、以前のGoの実装では`Version int `asn1:"optional,default:1"``となっていました。
    *   これは、Goのコードが概念的なv2をデフォルト（ワイヤー上では1）として扱おうとしていたことを意味します。
    *   しかし、ASN.1の`default:1`という指定は、「フィールドの値が1の場合、ワイヤー上ではそのフィールドを省略する」という挙動を引き起こします。
    *   この結果、Goで生成されたCRLがv2であるにもかかわらず、バージョンフィールドがワイヤー上に明示的にエンコードされないという問題が発生していました。これは、RFCがv2がワイヤー上で表現される場合があることを想定しているという記述と矛盾します。
    *   さらに、OpenSSLがv1をデフォルト（ワイヤー上では0、または省略）と解釈していたため、GoとOpenSSLの間でCRLの解釈に不一致が生じ、相互運用性の問題が発生していました。

4.  **今回の修正**:
    *   今回の修正では、`Version int `asn1:"optional,default:1"``を`Version int `asn1:"optional,default:0"``に変更しました。
    *   これにより、GoのASN.1エンコーディングは、`Version`フィールドの値が`0`（概念的なv1）である場合にそのフィールドを省略するようになります。
    *   これは、RFC 5280の「バージョンフィールドが省略された場合はv1 CRLを意味する」という解釈と、OpenSSLのデフォルト解釈（v1）に合致します。
    *   もしCRLがv2（ASN.1値の1）である場合、`default:0`とは異なるため、`Version`フィールドはワイヤー上に明示的に`1`としてエンコードされます。これにより、RFCが想定する「v2がワイヤー上で表現される場合がある」という要件も満たされます。

この変更は、Goの`crypto/x509`パッケージがPKI標準に厳密に準拠し、他の主要なPKI実装（特にOpenSSL）との間でCRLの相互運用性を確保するために不可欠なものでした。

## コアとなるコードの変更箇所

変更は`src/crypto/x509/pkix/pkix.go`ファイル内の`TBSCertificateList`構造体の定義にあります。

```diff
--- a/src/crypto/x509/pkix/pkix.go
+++ b/src/crypto/x509/pkix/pkix.go
@@ -177,7 +177,7 @@ func (certList *CertificateList) HasExpired(now time.Time) bool {
 // 5280, section 5.1.
 type TBSCertificateList struct {
  Raw                 asn1.RawContent
- Version             int `asn1:"optional,default:1"`
+ Version             int `asn1:"optional,default:0"`
  Signature           AlgorithmIdentifier

```

具体的には、`Version`フィールドのASN.1タグの`default`値が`1`から`0`に変更されています。

## コアとなるコードの解説

変更されたコードは、Go言語の`encoding/asn1`パッケージが`TBSCertificateList`構造体をASN.1 DERエンコードする際の挙動を直接制御します。

*   **`type TBSCertificateList struct { ... }`**: これは、X.509 CRLの主要な情報を含む構造体です。RFC 5280のセクション5.1で定義されている`TBSCertificateList`に対応します。
*   **`Version int `asn1:"optional,default:0"``**:
    *   `Version int`: CRLのバージョンを表す整数フィールドです。
    *   ``asn1:"..."``: Goの`encoding/asn1`パッケージがこのフィールドをどのようにASN.1エンコード/デコードするかを指示する構造体タグです。
    *   `optional`: このフィールドがASN.1シーケンス内でオプションであることを示します。つまり、エンコードされたデータにこのフィールドが存在しなくても、デコード時にエラーにはなりません。
    *   `default:0`: **この変更の核心部分です。** これは、`Version`フィールドの値が`0`である場合、ASN.1 DERエンコーディングにおいてこのフィールドを**省略**するように指示します。

**変更前 (`default:1`) の挙動**:
以前は`default:1`と指定されていました。これは、`Version`フィールドの値が`1`（概念的なCRL v2）である場合に、そのフィールドがワイヤー上で省略されることを意味していました。しかし、RFC 5280では、バージョンフィールドが省略された場合は概念的なCRL v1（ASN.1値の0）を意味すると解釈されます。このため、Goがv2 CRLを生成しても、バージョン情報が省略されてしまい、他のシステム（OpenSSLなど）からはv1 CRLとして誤って解釈される可能性がありました。また、v2がワイヤー上に明示的に書き出されることがないため、RFCの意図とも矛盾していました。

**変更後 (`default:0`) の挙動**:
`default:0`に変更されたことで、以下の挙動になります。
1.  **CRL v1の場合**: `Version`フィールドの値が`0`（概念的なCRL v1）である場合、このフィールドはASN.1 DERエンコーディングで省略されます。これはRFC 5280の解釈（省略された場合はv1）とOpenSSLの挙動に合致します。
2.  **CRL v2の場合**: `Version`フィールドの値が`1`（概念的なCRL v2）である場合、`default:0`とは異なるため、このフィールドはワイヤー上に明示的に`1`としてエンコードされます。これにより、v2 CRLが正しく識別され、RFCが想定する「v2がワイヤー上で表現される場合がある」という要件も満たされます。

この小さな変更により、Goの`crypto/x509`パッケージが生成するCRLが、PKI標準および他の主要な実装との間でより高い相互運用性を持つようになりました。

# [インデックス 21117] ファイルの概要

このコミットは、Go言語のランタイムにおけるガベージコレクタ（GC）の抜本的な変更を記録しています。これまでのGCがC言語で実装されていたのに対し、このコミットによってGCの大部分がGo言語で書き直されました。これにより、Goランタイムのメモリ管理とスケジューリングのコア部分がGo言語ネイティブのコードベースに統合され、将来的な機能拡張やパフォーマンス改善の基盤が築かれました。

変更されたファイル群は、主に`src/runtime`ディレクトリに集中しており、GC、メモリ割り当て、スケジューラ、スタック管理など、ランタイムの根幹をなすコンポーネントがC言語からGo言語へと移行されています。特に、`src/runtime/mgc.go`、`src/runtime/malloc.go`、`src/runtime/proc.go`、`src/runtime/stack.go`といったファイルが大幅に更新または新規追加されています。

## 変更の背景

Go言語の初期のバージョンでは、ランタイムの多くの部分、特にパフォーマンスが要求されるガベージコレクタはC言語で実装されていました。これは、既存のC言語の知識とツールを活用し、開発を迅速に進めるための現実的な選択でした。しかし、C言語とGo言語の混在は、以下のような課題をもたらしていました。

1.  **Cgoのオーバーヘッド**: GoコードからCコードを呼び出すCgoは、コンテキストスイッチやデータ変換のオーバーヘッドを伴い、パフォーマンスに影響を与える可能性がありました。
2.  **開発の複雑性**: CとGoの異なるメモリモデル、型システム、エラーハンドリングなどを考慮する必要があり、開発とデバッグが複雑になる要因でした。
3.  **Go言語の進化との乖離**: Go言語自体が進化し、より高度な並行処理や最適化の機能が導入されるにつれて、C言語で書かれたGCがGo言語の新しい機能と完全に統合されにくくなるという問題がありました。
4.  **保守性**: 異なる言語で書かれたコードベースは、Go言語の専門家がC言語の知識も必要とするため、保守が困難になる傾向がありました。

このような背景から、GoチームはガベージコレクタをGo言語で完全に書き直すという野心的なプロジェクトに着手しました。このコミットは、そのプロジェクトの重要なマイルストーンであり、GCがGo言語で動作するようになったことを示しています。これにより、GCはGoランタイムの他の部分とより密接に連携し、Go言語の並行処理モデルを最大限に活用できるようになります。

## 前提知識の解説

このコミットの技術的詳細を理解するためには、以下の概念を把握しておく必要があります。

*   **Go言語のランタイム (Go Language Runtime)**:
    Goプログラムの実行を管理する低レベルのコンポーネント群です。これには、ゴルーチン（軽量スレッド）のスケジューリング、メモリ管理（ガベージコレクションを含む）、チャネルによる通信、システムコールとの連携などが含まれます。ランタイムはGoプログラムの「OS」のような役割を果たし、Go言語の並行処理モデルを支えています。

*   **ガベージコレクション (Garbage Collection, GC)**:
    プログラムが動的に確保したメモリ領域のうち、もはや到達不可能（参照されていない）になったものを自動的に識別し、解放する仕組みです。これにより、プログラマは手動でのメモリ解放の煩雑さから解放され、メモリリークのリスクを低減できます。GoのGCは、アプリケーションの実行と並行して動作する「並行GC」を採用しています。

*   **マーク＆スイープ (Mark and Sweep)**:
    GCアルゴリズムの基本的なタイプの一つです。
    1.  **マークフェーズ (Mark Phase)**: ルート（グローバル変数、スタック上の変数など、プログラムが直接参照できるオブジェクト）から開始し、到達可能なすべてのオブジェクトを「マーク」します。
    2.  **スイープフェーズ (Sweep Phase)**: ヒープ全体を走査し、マークされていないすべてのオブジェクトを「スイープ」（解放）します。

*   **並行GC (Concurrent GC)**:
    ガベージコレクタがアプリケーションの実行（ミューテータ）と並行して動作するGCの方式です。これにより、GCがヒープを走査している間もアプリケーションは処理を続行できるため、アプリケーションの一時停止時間（Stop-the-World, STW）を大幅に短縮できます。GoのGCは、この並行性を重視して設計されています。

*   **Stop-the-World (STW)**:
    GCの特定のフェーズにおいて、アプリケーションのすべてのゴルーチン（ミューテータ）の実行を一時的に完全に停止させる期間です。STWは、GCがメモリの状態を整合性のある形でスナップショットしたり、重要なデータ構造を更新したりするために必要です。並行GCの目標は、このSTW時間を可能な限り短くすることです。

*   **Write Barrier (ライトバリア)**:
    並行GCにおいて不可欠な技術です。ミューテータがヒープ上のポインタを書き換える際に、GCにその変更を通知する仕組みです。これにより、GCがオブジェクトグラフを走査している最中にミューテータがポインタを変更しても、GCは到達可能なオブジェクトを見落とすことなく正確に追跡できます。GoのGCでは、DijkstraのオンザフライGCアルゴリズムにインスパイアされた三色マーキング（White, Grey, Black）とライトバリアを組み合わせて使用します。

*   **C言語とGo言語の相互運用 (C and Go Interoperability)**:
    Go言語は、C言語のコードを呼び出すための`cgo`ツールを提供しています。これにより、既存のCライブラリをGoプログラムから利用できます。しかし、`cgo`には前述のオーバーヘッドがあり、Goランタイムのコア部分をCで実装することは、Go言語の設計思想とは異なる部分もありました。GCをGoで書き直すことは、この相互運用性の複雑さを軽減し、Go言語の統一されたコードベースを目指す動きの一環です。

*   **tcmalloc**:
    Googleが開発した、スレッドローカルなメモリキャッシュを持つ高性能なメモリ割り当てライブラリです。Goのメモリ割り当て器は、tcmallocの設計思想に強く影響を受けています。この設計は、ロックの競合を減らし、並行環境でのメモリ割り当て性能を向上させることを目的としています。

## 技術的詳細

このコミットは、GoランタイムのガベージコレクタをC言語からGo言語へ移行するという、Goプロジェクトにおける極めて重要なアーキテクチャ上の変更を反映しています。これは単なる言語の置き換えにとどまらず、GCがGoランタイムの並行性モデル（ゴルーチンとチャネル）やメモリ管理とより深く統合されることを意味します。

主要な技術的側面は以下の通りです。

1.  **GCのGo言語への移行**:
    *   これまでのGC関連のC言語ファイル（例: `src/runtime/mgc0.c`, `src/runtime/malloc.c`, `src/runtime/proc.c`など）が大量に削除され、対応するGo言語ファイル（例: `src/runtime/mgc.go`, `src/runtime/malloc.go`, `src/runtime/proc1.go`など）が新規追加または大幅に修正されています。
    *   この移行により、GCはGo言語の型システム、エラーハンドリング、並行処理プリミティブを直接活用できるようになります。これにより、GCコードの可読性、保守性、およびGoランタイム全体との整合性が向上します。

2.  **並行マーク＆スイープGCの強化**:
    *   `src/runtime/mgc.go`の新しいコメントには、GoのGCアルゴリズムの詳細な説明が含まれています。これは、DijkstraのオンザフライGCアルゴリズムに影響を受けた、並行マーク＆スイープ方式です。
    *   **GCフェーズ**: GCは複数のフェーズに分かれて実行されます。
        *   `GCscan`: スタックとグローバル変数をスキャンし、ポインタをグレイ化します。
        *   `GCmark`: ライトバリアが有効になり、ヒープ上の到達可能なオブジェクトをマークします。
        *   `GCmarktermination`: 割り当てがブラックオブジェクトになり、未マークの到達可能オブジェクトの数が単調に減少します。
        *   `GCsweep`: バックグラウンドでヒープをスイープし、未使用のメモリを解放します。
        *   `GCoff`: GCが非アクティブな状態です。
    *   これらのフェーズは、アプリケーションの実行と並行して動作するように設計されており、STW（Stop-the-World）ポーズを最小限に抑えることを目指しています。

3.  **ライトバリアの実装**:
    *   並行GCの正確性を保証するために、ライトバリアが導入されています。ミューテータ（アプリケーションコード）がヒープ上のポインタを書き換える際に、ライトバリアがGCに通知し、オブジェクトの到達可能性情報を正確に維持します。
    *   `mgc.go`内の`greyobject`関数は、オブジェクトをマークし、スキャン作業キューに追加する役割を担います。これはライトバリアによって呼び出されるか、GC自身がオブジェクトを走査する際に使用されます。

4.  **メモリ割り当て器の再設計 (tcmallocライク)**:
    *   `src/runtime/malloc.go`、`src/runtime/malloc1.go`、`src/runtime/malloc2.go`といったファイルは、Go言語で実装された新しいメモリ割り当て器のコア部分です。
    *   この割り当て器は、tcmallocの設計思想に基づいており、以下の階層的なキャッシュ構造を持っています。
        *   **MCache**: 各P（プロセッサ、Goスケジューラの論理的なCPU）に紐付けられたスレッドローカルなキャッシュで、小さなオブジェクトの割り当てと解放をロックなしで行います。
        *   **MCentral**: 特定のサイズクラスのオブジェクトに対する共有フリーリストで、MCacheが空になった際にオブジェクトを補充します。
        *   **MHeap**: ページ単位でメモリを管理するヒープで、MCentralが空になった際にページを割り当て、オブジェクトに分割します。
    *   この階層的なアプローチにより、ロックの競合が最小限に抑えられ、並行環境でのメモリ割り当て性能が向上します。

5.  **ランタイムとの深い統合**:
    *   `src/runtime`ディレクトリ内の広範なファイル（`proc.go`, `stack.go`, `runtime1.go`, `runtime2.go`など）の変更は、メモリ管理、ゴルーチンのスケジューリング、GCがGoランタイム内でどのように相互作用するかを根本的に再構築したことを示しています。
    *   `malloc.go`や`mcache.go`に見られる`systemstack`の呼び出しは、GCやメモリ管理に関連する特定の低レベル操作が、ユーザーゴルーチンとは独立したシステムゴルーチン（g0）上で実行されることを示しています。これにより、これらの操作はプリエンプションの影響を受けず、デッドロックや複雑な相互作用を回避できます。

6.  **プラットフォーム固有の適応**:
    *   `src/runtime/defs_*`, `src/runtime/os_*`, `src/runtime/signal_*`といった、様々なOS（darwin, linux, freebsdなど）やアーキテクチャ（amd64, 386, armなど）に特化したファイル群の変更は、GoベースのGCモデルに合わせた低レベルのシステムインタラクションの適応が行われたことを示しています。これは、GCが各プラットフォームのメモリ管理やシグナル処理の特性を考慮して設計されていることを意味します。

## コアとなるコードの解説

このコミットで導入されたGo言語によるGCとメモリ管理のコア部分を、主要なファイルと構造体、関数に焦点を当てて解説します。

### `src/runtime/mgc.go`

このファイルは、Go言語で実装された新しいガベージコレクタの心臓部です。

*   **GCアルゴリズムの概要**:
    ファイル冒頭のコメントで、GCが「並行マーク＆スイープ」であり、ライトバリアを使用し、型が正確（precise）であることが説明されています。GCのフェーズ遷移（GCoff -> GCscan -> GCmark -> GCmarktermination -> GCsweep -> GCoff）が詳細に記述されており、各フェーズでのランタイムの動作が定義されています。

*   **`markbits` 構造体**:
    ```go
    type markbits struct {
        bitp  *byte   // pointer to the byte holding xbits
        shift uintptr // bits xbits needs to be shifted to get bits
        xbits byte    // byte holding all the bits from *bitp
        bits  byte    // mark and boundary bits relevant to corresponding slot.
        tbits byte    // pointer||scalar bits relevant to corresponding slot.
    }
    ```
    これは、GCビットマップからオブジェクトのマーク状態やポインタ/スカラーの型情報を抽出するために使用される構造体です。`bitp`はビットマップのバイトへのポインタ、`shift`はビットのオフセット、`bits`はマークビットと境界ビット、`tbits`は型ビット（ポインタかスカラーか）を表します。

*   **`greyobject(obj uintptr, mbits *markbits, wbuf *workbuf) *workbuf` 関数**:
    この関数は、GCのマークフェーズにおいて、到達可能なオブジェクトを「グレイ」（スキャン待ち）としてマークし、`workbuf`（作業キュー）に追加する役割を担います。
    *   オブジェクトがまだマークされていない場合、`mbits.bitp`の対応するビットをアトミックに設定してマークします。
    *   オブジェクトがスキャン不要（ポインタを含まない）であれば、`wbuf`に追加せずに終了します。
    *   `wbuf`が満杯の場合、新しい空の`workbuf`を取得します。
    *   オブジェクトを`wbuf.obj`に追加し、`wbuf.nobj`をインクリメントします。
    この関数は、ライトバリアによってミューテータがポインタを書き換えた際に呼び出されるか、GC自身がオブジェクトを走査する際に呼び出されます。

*   **`scanobject(b, n uintptr, ptrmask *uint8, wbuf *workbuf) *workbuf` 関数**:
    この関数は、指定されたメモリ領域`b`（サイズ`n`）をスキャンし、そこに含まれるポインタを識別して`greyobject`を呼び出し、`wbuf`に追加します。
    *   `ptrmask`が`nil`でない場合、それはスタックやデータセクションのような密なポインタマスクを示します。
    *   `ptrmask`が`nil`の場合、GCビットマップを調べてポインタ情報を取得します。
    *   オブジェクトの境界を検出し、スキャンを停止するロジックが含まれています。

*   **`gcmarknewobject_m(obj uintptr)` 関数**:
    `GCmarktermination`フェーズ中に新しく割り当てられたオブジェクトをマークするために使用されます。このフェーズでは、新しく割り当てられたオブジェクトは「ブラック」（マーク済み）として扱われます。

### `src/runtime/malloc.go` および `src/runtime/malloc2.go`

これらのファイルは、Go言語で再実装されたメモリ割り当て器の主要な部分です。

*   **`mallocgc(size uintptr, typ *_type, needzero bool) unsafe.Pointer` 関数**:
    Go言語のヒープから、指定された`size`のメモリを割り当て、必要に応じてゼロクリアし、GCの対象となるオブジェクトを返す主要な関数です。
    *   `gcphase == _GCmarktermination`の場合、新しく割り当てられたオブジェクトは`gcmarknewobject_m`によって即座にマークされます。

*   **`loadPtrMask(typ *_type) []uint8` 関数**:
    与えられた型`typ`のポインタマスクをロードします。このマスクは、GCがオブジェクト内のどの部分がポインタであり、どの部分がスカラーデータであるかを識別するために使用されます。これは、GoのGCが「正確なGC」（precise GC）であるために不可欠な情報です。

*   **`newobject(typ *_type) unsafe.Pointer` 関数**:
    Goの組み込み関数`new`の実装です。指定された型の新しいオブジェクトを割り当てます。

*   **`systemstack(func())` の利用**:
    `malloc.go`や`mcache.go`の多くの場所で`systemstack(func() { ... })`が使用されています。これは、囲まれた関数ブロックがシステムゴルーチン（g0）のスタック上で実行されることを意味します。システムゴルーチンは、ランタイムの低レベル操作（GC、スケジューリング、メモリ管理など）のために予約されており、ユーザーゴルーチンとは独立して動作します。これにより、これらのクリティカルな操作がプリエンプションの影響を受けず、デッドロックや複雑な競合状態を回避できます。

### `src/runtime/mcache.go`, `src/runtime/mcentral.go`, `src/runtime/mheap.go`

これらのファイルは、tcmallocにインスパイアされたGoのメモリ割り当て器の階層構造を定義しています。

*   **`mcache` 構造体**:
    各P（プロセッサ）に紐付けられたスレッドローカルなキャッシュです。小さなオブジェクトの割り当てと解放を高速に行うために使用されます。ロックは不要です。

*   **`mcentral` 構造体**:
    特定のサイズクラスのオブジェクトに対する共有フリーリストです。`mcache`が空になった際に、`mcentral`からオブジェクトのチャンクを取得します。

*   **`mheap` 構造体**:
    ページ単位でメモリを管理するヒープです。`mcentral`が空になった際に、`mheap`からページのラン（`mspan`）を取得し、それをオブジェクトに分割します。

### `src/runtime/proc1.go`

このファイルは、Go言語で再実装されたスケジューラとゴルーチン管理の一部を含んでいます。C言語で書かれていた`proc.c`の機能がGoに移行されています。

### `src/runtime/stack1.go`

このファイルは、Go言語で再実装されたスタック管理の一部を含んでいます。C言語で書かれていた`stack.c`の機能がGoに移行されています。

これらの変更は、Goランタイムの内部構造をGo言語で統一し、より効率的で保守性の高いシステムを構築するための基盤を築きました。

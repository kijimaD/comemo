# [インデックス 28199] ファイルの概要

このコミットは、Go言語の`compress/flate`パッケージにおいて、DEFLATE圧縮アルゴリズムにおける「ベースマッチ長」と「最小マッチ長」の概念を明確に区別し、関連する定数と計算ロジックを修正するものです。これにより、DEFLATE仕様への準拠を強化し、コンプレッサーとデコンプレッサー間の整合性を向上させます。

## 変更の背景

DEFLATE圧縮アルゴリズムは、RFC 1951でその仕様が定義されています。この仕様では、マッチ長（繰り返し出現するバイトシーケンスの長さ）の最小値が3バイトと定められています。しかし、実際のコンプレッサーの実装では、パフォーマンス最適化（例えば、32ビットロードと比較による高速なマッチ検出）のために、内部的にこれよりも長い最小マッチ長（例えば4バイト）を使用することがあります。

このコミット以前の`compress/flate`パッケージでは、RFCで定義された「ベース」となる最小マッチ長と、コンプレッサーが実際に処理する「最小」マッチ長との間に曖昧さがありました。特に、`matchToken`の生成時における長さやオフセットの計算において、これらの値が混同されている箇所がありました。

この曖昧さは、圧縮データの正確な表現に影響を与え、またデコンプレッサーとの整合性にも問題を引き起こす可能性がありました。このコミットは、これらの概念を明確に区別し、コード内の定数定義と計算ロジックを修正することで、DEFLATE仕様への厳密な準拠とコードの可読性・保守性の向上を図ることを目的としています。また、デコンプレッサー側の辞書初期化における最大オフセットの利用も修正され、より正確なメモリ管理に貢献しています。

## 前提知識の解説

### DEFLATEアルゴリズム

DEFLATEは、可逆データ圧縮アルゴリズムであり、主にLZ77アルゴリズムとハフマン符号化の2つの技術を組み合わせています。

*   **LZ77 (Lempel-Ziv 1977)**: 入力データストリーム内で繰り返し出現するバイトシーケンス（マッチ）を検出し、そのシーケンスを「長さ/オフセットペア」で置き換えることで圧縮を行います。マッチが見つからない場合は、元のバイト（リテラルトークン）をそのまま出力します。
    *   **スライディングウィンドウ**: LZ77は、過去に処理したデータの一部を「スライディングウィンドウ」と呼ばれるバッファに保持し、現在の入力データとのマッチをこのウィンドウ内で探します。DEFLATEでは、このウィンドウサイズは通常32KB（32,768バイト）です。
    *   **マッチ長 (Match Length)**: 繰り返し出現するバイトシーケンスの長さを示します。DEFLATEの仕様では、マッチ長は3バイトから258バイトの範囲で表現されます。
    *   **オフセット (Offset / Distance)**: マッチしたシーケンスがスライディングウィンドウ内でどれだけ前に出現したかを示す距離です。DEFLATEの仕様では、オフセットは1バイトから32,768バイトの範囲で表現されます。

*   **ハフマン符号化**: LZ77によって生成されたリテラルトークンと長さ/オフセットペアを、さらに統計的な手法で圧縮します。出現頻度の高いシンボルには短いビット列を、低いシンボルには長いビット列を割り当てることで、全体のデータサイズを削減します。DEFLATEでは、リテラル/長さツリーと距離ツリーの2つのハフマンツリーを使用します。

### Goの`compress/flate`パッケージ

Go言語の標準ライブラリに含まれる`compress/flate`パッケージは、DEFLATE圧縮データフォーマット（RFC 1951）を実装しています。このパッケージは、データの圧縮と伸張の両方の機能を提供し、`gzip`や`zlib`といった他のDEFLATEベースのフォーマットを実装するパッケージの基盤としても利用されています。

### RFC 1951における最小マッチ長とオフセット

RFC 1951では、DEFLATE形式におけるマッチ長の最小値は3バイトと明確に定義されています。これは、エンコードされる長さ値が、常にこの「3」をベースとして表現されることを意味します。同様に、オフセットの最小値は1バイトです。

## 技術的詳細

このコミットの主要な変更点は、DEFLATE仕様で定められた「ベース」となる値と、Goのコンプレッサーが内部的に使用する「最小」値との区別を明確にすることにあります。

### 新しい定数の導入と既存定数の修正

`src/compress/flate/deflate.go`において、以下の定数が導入または修正されました。

*   `baseMatchLength = 3`: RFC 3.2.5節で定義されている最小マッチ長。これは、エンコードされるマッチ長の基準となる値です。
*   `minMatchLength = 4`: コンプレッサーが実際にマッチとして発行する最小の長さ。これは、32ビットロードと比較などの最適化を可能にするために、RFCのベース値よりも大きく設定されています。
*   `maxMatchLength = 258`: 最大マッチ長。これはRFCで定義されている値と一致します。
*   `baseMatchOffset = 1`: 最小オフセット。
*   `maxMatchOffset = 1 << 15` (32768): 最大オフセット。これはDEFLATEのウィンドウサイズに対応します。

以前は`minMatchLength`が4と定義され、`logMaxOffsetSize`や`minOffsetSize`といった定数がありましたが、これらはより明確な`baseMatchLength`、`baseMatchOffset`、`maxMatchOffset`に置き換えられました。

### `matchToken`生成ロジックの修正

`deflate.go`および`deflatefast.go`内の`matchToken`を生成する箇所が修正されました。

以前は、`matchToken(uint32(d.length-3), uint32(d.offset-minOffsetSize))`のように、マジックナンバー`3`や`minOffsetSize`が直接使用されていました。
これが、`matchToken(uint32(d.length-baseMatchLength), uint32(d.offset-baseMatchOffset))`のように、新しく定義された`baseMatchLength`と`baseMatchOffset`を使用するように変更されました。

この変更は非常に重要です。DEFLATE形式では、エンコードされるマッチ長は常に「実際の長さ - 3」として表現されます。例えば、実際の長さが3バイトの場合、エンコードされる値は0になります。この「3」が`baseMatchLength`として明示されることで、コードの意図が明確になり、RFCの仕様に厳密に準拠したトークンが生成されるようになります。同様に、オフセットも`baseMatchOffset`を基準として計算されます。

### `deflatefast.go`におけるマッチ条件の修正

`deflatefast.go`の`encodeBestSpeed`関数内で、マッチを検出する条件が`s-candidate < maxOffset`から`s-candidate < maxMatchOffset`に変更されました。これにより、最大オフセットの定義がより一貫して使用されるようになりました。また、`TODO`コメントが追加され、比較演算子に関する潜在的な修正点が示唆されています。

### `inflate.go`における辞書初期化の修正

`inflate.go`では、デコンプレッサーの辞書を初期化する`f.dict.init`の呼び出しが修正されました。

以前は、`f.dict.init(maxHist, nil)`のように`maxHist`という定数が使用されていました。
これが、`f.dict.init(maxMatchOffset, nil)`のように`maxMatchOffset`を使用するように変更されました。

`maxHist`は以前32768と定義されており、これは`maxMatchOffset`と同じ値でした。しかし、辞書のサイズは、DEFLATEの最大オフセット（距離）に対応するべきであり、`maxMatchOffset`という名称の方がその意図を正確に表しています。この変更により、デコンプレッサーが適切なサイズの履歴バッファ（辞書）を確保できるようになり、圧縮されたデータストリームから正確にデータを再構築するための基盤が強化されます。

これらの技術的変更は、Goの`compress/flate`パッケージがDEFLATE仕様にさらに厳密に準拠し、圧縮・伸張処理の正確性と堅牢性を向上させることを目的としています。

## コアとなるコードの解説

### `src/compress/flate/deflate.go`の変更

*   **定数定義の明確化**: `logMaxOffsetSize`や`minOffsetSize`といった汎用的な定数が削除され、`baseMatchLength`、`minMatchLength`、`baseMatchOffset`、`maxMatchOffset`といった、より具体的で意味の明確な定数が導入されました。これにより、DEFLATE仕様における各値の役割がコード上で明確に区別されるようになりました。特に、`baseMatchLength`がRFCで定められた最小マッチ長（3）を指し、`minMatchLength`がコンプレッサーが実際に使用する最小マッチ長（4）を指すことで、実装上の最適化と仕様準拠のバランスが取られています。
*   **`matchToken`の引数修正**: `d.tokens = append(d.tokens, matchToken(uint32(d.length-baseMatchLength), uint32(d.offset-baseMatchOffset)))` のように変更された箇所は、DEFLATE形式でエンコードされる長さとオフセットの値を正確に計算するために不可欠です。DEFLATEでは、マッチ長は常に「実際の長さから3を引いた値」としてエンコードされます。`baseMatchLength`を使用することで、この「3」というマジックナンバーが定数として明示され、コードの意図が明確になり、将来的な変更にも強くなります。同様に、オフセットも`baseMatchOffset`を基準とすることで、仕様に沿った正確な値が生成されます。

### `src/compress/flate/deflatefast.go`の変更

*   **`maxOffset`から`maxMatchOffset`への移行**: `maxOffset`定数が削除され、`deflate.go`で定義された`maxMatchOffset`が使用されるようになりました。これにより、最大オフセットに関する定義が一元化され、コード全体での一貫性が向上します。
*   **マッチ条件の修正**: `if s-candidate < maxMatchOffset && load32(src, s) == load32(src, candidate)` のように、マッチを検出する条件が`maxMatchOffset`を使用するように変更されました。これは、LZ77アルゴリズムにおけるスライディングウィンドウの範囲内でマッチを探す際の距離制限を正確に反映しています。
*   **`matchToken`の引数修正**: `deflate.go`と同様に、`matchToken`の引数が`baseMatchLength`と`baseMatchOffset`を使用するように修正され、DEFLATE仕様に準拠した正確なトークン生成が保証されます。

### `src/compress/flate/inflate.go`の変更

*   **`maxHist`から`maxMatchOffset`への移行**: `maxHist`定数が削除され、デコンプレッサーの辞書を初期化する`f.dict.init`関数が`maxMatchOffset`を引数として受け取るように変更されました。`maxHist`は以前、最大履歴サイズ（32768）を示していましたが、これはDEFLATEの最大オフセットと一致します。辞書は、デコンプレッサーが過去のデータ（履歴）を保持するために使用されるため、そのサイズは最大オフセットによって決定されるべきです。`maxMatchOffset`を使用することで、辞書の初期化がより意味のある定数に基づいて行われるようになり、デコンプレッサーが圧縮されたデータストリームを正しく処理するための適切なメモリを確保できるようになります。

これらの変更は全体として、Goの`compress/flate`パッケージがDEFLATE圧縮アルゴリズムの仕様をより正確に反映し、コンプレッサーとデコンプレッサー間の整合性を高め、コードの堅牢性と保守性を向上させることに貢献しています。

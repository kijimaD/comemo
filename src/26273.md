# [インデックス 26273] ファイルの概要

このコミットは、GoランタイムにおけるCgoプロファイリング時のトレースバックの挙動を修正するものです。具体的には、`sigprof`シグナルがCgo呼び出し中に発生した場合に、たとえトレースバックが成功していても、G（ゴルーチン）のスタック外にSP（スタックポインタ）があるという理由でそのトレースバックが無視され、`_ExternalCode`として上書きされてしまう問題を解決します。この変更により、Cgoのエントリポイントからのトレースバックであっても、成功したものはすべて受け入れられるようになります。

    runtime: don't ignore success of cgo profiling tracebacks
    
    If a sigprof happens during a cgo call, we traceback from the entry
    point of the cgo call. However, if the SP is outside of the G's stack,
    we'll then ignore this traceback, even if it was successful, and
    overwrite it with just _ExternalCode.
    
    Fix this by accepting any successful traceback, regardless of whether
    we got it from a cgo entry point or from regular Go code.

## 元コミット内容

runtime: cgoプロファイリングのトレースバックの成功を無視しない

Cgo呼び出し中に`sigprof`が発生した場合、Cgo呼び出しのエントリポイントからトレースバックを行います。しかし、SPがGのスタック外にある場合、たとえトレースバックが成功していても、そのトレースバックは無視され、単に`_ExternalCode`で上書きされていました。

この問題を修正するため、Cgoエントリポイントから得られたか、通常のGoコードから得られたかに関わらず、成功したトレースバックはすべて受け入れるようにします。

Fixes #13466.

## 変更の背景

Goアプリケーションのパフォーマンスプロファイリングにおいて、`pprof`ツールはCPU使用率のボトルネックを特定する上で非常に強力です。しかし、`cgo`（GoとC言語の相互運用機能）を使用してCコードを呼び出すGoプログラムをプロファイリングする際に、問題が発生することがありました。

具体的には、GoランタイムがCPUプロファイリングのために`SIGPROF`シグナルを受け取った際、もしその時点でプログラムがCgo経由でCコードを実行している途中だった場合、GoランタイムはCgo呼び出しのエントリポイントからスタックトレースを生成しようとします。このトレースバック自体は成功する可能性があります。

しかし、元の実装では、スタックポインタ（SP）が現在のゴルーチン（G）のスタックの範囲外にある場合（これはCgo呼び出し中に発生し得る状況です）、たとえ有効なトレースバックが生成されていても、その結果を「無効」と判断し、トレースバックを破棄して代わりに`_ExternalCode`という汎用的なラベルで上書きしていました。

この挙動は、プロファイリング結果の精度を低下させ、Cgo呼び出し中に実際に何が起こっていたのかを把握することを困難にしていました。`_ExternalCode`がプロファイルに多く表示されると、CPU時間の大部分がGoプロファイラが詳細に分析できないコードで費やされていることを示唆するため、パフォーマンスのボトルネックがCコードにある場合、その特定が難しくなります。このコミットは、この不正確なプロファイリング結果を改善するために行われました。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

1.  **`SIGPROF`シグナル**:
    *   `SIGPROF`は、Unix系システムでプロファイリングのために使用されるシグナルです。GoのCPUプロファイラは、このシグナルを定期的に（例えば10ミリ秒ごと）プロセスに送信します。
    *   `SIGPROF`を受け取ると、Goランタイムは現在のプログラムカウンタ（PC）をサンプリングし、コールスタックを再構築して、どの関数が実行中であったかを特定しようとします。

2.  **`cgo`**:
    *   `cgo`は、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。
    *   `cgo`を使用すると、GoのランタイムとCのランタイムが混在するため、スタック管理やプロファイリングにおいて特別な考慮が必要になります。GoのスタックとCのスタックは異なる管理方法を持つため、`cgo`の境界を越える際にはスタックの切り替えや調整が発生します。

3.  **Goのプロファイリングと`pprof`**:
    *   Goは、`pprof`ツールを通じてCPU、メモリ、ブロック、ミューテックスなどのプロファイリング機能を提供します。
    *   CPUプロファイリングは、`SIGPROF`シグナルを利用して定期的にスタックトレースを収集し、どの関数がCPU時間を消費しているかを可視化します。

4.  **`_ExternalCode`**:
    *   `pprof`の出力に`_ExternalCode`というラベルが表示されることがあります。これは、`SIGPROF`シグナルが、Goランタイムが詳細なGoトレースバックを生成できないコンテキストで実行を中断したことを示します。
    *   主な原因は`cgo`呼び出し中にCコードが実行されている場合です。Goプロファイラは通常、Cライブラリ内のスタックトレースを詳細に分析する能力を持たないため、Cコードの実行中に`SIGPROF`が発生すると`_ExternalCode`として記録されます。
    *   その他、VDSO（Virtual Dynamic Shared Object）内の実行や、特定の短命なGoランタイム内部関数（`gogo`, `systemstack`, `mcall`, `morestack`など）の実行中に発生することもあります。

5.  **GのスタックとSP（スタックポインタ）**:
    *   Goのゴルーチン（G）は、それぞれ独自のスタックを持っています。Goのスタックは動的に伸縮する特徴があります。
    *   スタックポインタ（SP）は、現在の関数のスタックフレームの最上位を指すレジスタです。
    *   Cgo呼び出しが行われると、GoのスタックからCのスタックに切り替わるため、SPが一時的にGoのGのスタック範囲外を指すことがあります。

## 技術的詳細

GoのCPUプロファイラは、`SIGPROF`シグナルハンドラ内で`gentraceback`関数を呼び出してスタックトレースを収集します。この`gentraceback`関数は、現在のプログラムカウンタ（PC）、スタックポインタ（SP）、リンクレジスタ（LR）などの情報に基づいて、実行中のゴルーチンのコールスタックを再構築します。

Cgo呼び出し中に`SIGPROF`が発生した場合、GoランタイムはCgo呼び出しのエントリポイント（GoコードからCコードへ移行する境界）からトレースバックを開始しようとします。この時点での`gentraceback`の呼び出しは、Cgoの境界を考慮して行われます。

問題は、`gentraceback`が成功して有効なトレースバック（`n > 0`、つまりフレームが1つ以上見つかった場合）を返したとしても、その後のチェックでSPが現在のGのスタック範囲外にある場合に、そのトレースバックを破棄してしまっていた点にありました。

元のコードのロジックは以下のようになっていました。

```go
if !traceback || n <= 0 {
    // Normal traceback is impossible or has failed.
    // See if it falls into several common cases.
    n = 0
    // ... (ここで_ExternalCodeなどに上書きされるロジック)
}
```

ここで、`traceback`変数は、`gentraceback`がCgoエントリポイントからトレースバックを試みた際に、SPがGのスタック範囲外にある場合に`false`になる可能性がありました。つまり、`gentraceback`自体は成功して`n > 0`を返しても、`traceback`が`false`であるために、この`if`文の条件が真となり、せっかく得られたトレースバックが破棄されてしまっていたのです。

この挙動は、Cgo呼び出し中にCコードが実行されている間、GoランタイムがCのスタックを使用しているため、SPがGoのGのスタック範囲外を指すという正常な状況で発生していました。しかし、GoランタイムはCgoエントリポイントからのトレースバックを試みているため、そのトレースバックはCgo呼び出しのコンテキストを正確に反映しているはずでした。

このコミットは、この過度に厳格なチェックを緩和し、`gentraceback`が成功した（`n > 0`）のであれば、それがCgoエントリポイントからのものであろうと、通常のGoコードからのものであろうと、そのトレースバックを受け入れるように変更しました。これにより、Cgo呼び出し中のプロファイリング結果がより正確になり、`_ExternalCode`の出現頻度が減少することが期待されます。

## コアとなるコードの解説

変更は非常にシンプルですが、その影響は大きいです。

元のコード:
```go
if !traceback || n <= 0 {
```
この条件文は、「`traceback`が`false`である」**または**「`gentraceback`がスタックフレームを一つも発見できなかった（`n <= 0`）」のいずれかが真であれば、トレースバックを破棄し、代替の処理（`_ExternalCode`への上書きなど）を行うことを意味していました。

`traceback`変数は、`gentraceback`がCgoエントリポイントからトレースバックを試みた際に、SPがGのスタック範囲外にある場合に`false`になる可能性がありました。つまり、`gentraceback`が成功して`n > 0`を返しても、`traceback`が`false`であるために、この`if`文の条件が真となり、せっかく得られたトレースバックが破棄されてしまっていたのです。

変更後のコード:
```go
if n <= 0 {
```
この変更により、`!traceback`という条件が削除されました。
これで、トレースバックが破棄されるのは「`gentraceback`がスタックフレームを一つも発見できなかった（`n <= 0`）」場合のみとなります。

この修正は、`gentraceback`がCgoエントリポイントから有効なトレースバックを生成できたのであれば、SPがGのスタック範囲外を指していても（これはCgo呼び出し中の正常な状態）、そのトレースバックを信頼して採用するという意図を反映しています。結果として、Cgo呼び出し中のプロファイリングにおいて、より正確なスタックトレースが取得できるようになり、`_ExternalCode`という汎用的なラベルで隠蔽されていた情報が、より具体的なCgo関連のスタック情報として表示される可能性が高まります。

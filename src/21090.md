## 変更の背景

このコミットは、GoランタイムのC言語コードをGo言語に置き換えるという、Goプロジェクト全体の大きな目標の一環として行われました。この取り組みの主な動機は以下の通りです。

1.  **開発の簡素化**: Go言語でGo自身のツールを開発することで、C言語でのプログラミングよりも開発が簡素化されます。
2.  **ガベージコレクタの改善**: Cコードの削減は、より正確なガベージコレクタの実現に繋がり、ヒープサイズを10〜30%削減する効果がありました。
3.  **自己完結性**: Go言語が十分に成熟し、自身のコンパイラとランタイムを「自己ホスト」できるようになったため、ツールチェーン全体の自己完結性を高めることが可能になりました。

SolarisポートのGo言語への変換は、この広範なCコード削減の取り組みにおける重要なステップです。特に、Solaris固有のシステムコールやネットワークI/O処理をGo言語で直接扱うことで、C言語の依存性を減らし、Goランタイムの移植性と保守性を向上させることを目指しています。

コミットメッセージには、この変更が「最初のステップ」であり、バイナリが実行できない問題（`ld.so.1: TLS requirement failure`）が残っていることが明記されています。これは、C言語の`libc.so`へのリンクがなくなったことによる影響であり、今後のコミットで解決されるべき課題として認識されています。また、この変更は元のCコードの「大まかな翻訳」であり、クリーンアップは別のコミットで行われる予定であることも示されています。

## 前提知識の解説

このコミットを理解するためには、以下の技術的背景知識が役立ちます。

### Goランタイム (Go Runtime)
Goランタイムは、Goプログラムの実行を管理するGo言語の不可欠な部分です。ガベージコレクション、ゴルーチン（軽量スレッド）のスケジューリング、チャネルによる通信、メモリ管理、システムコールインターフェースなど、Go言語の並行処理モデルとメモリ安全性を実現するための低レベルな機能を提供します。Goランタイムの多くはGo言語自体で書かれていますが、OSとの直接的なやり取りやパフォーマンスが重要な部分では、C言語やアセンブリ言語が使用されていました。このコミットは、そのC言語部分をGo言語に置き換える試みです。

### Solarisオペレーティングシステム
Solarisは、Sun Microsystems（現在はOracleが所有）によって開発されたUNIXベースのオペレーティングシステムです。特にエンタープライズ環境での信頼性、スケーラビリティ、高度な機能で知られています。Go言語は、LinuxやmacOSと同様に、Solaris上でも動作するように設計されており、このコミットはSolaris環境でのGoランタイムの最適化と近代化を目的としています。

### `//go:linkname` ディレクティブ
`//go:linkname`は、Goコンパイラに対する特殊なディレクティブ（指示子）です。これは、あるパッケージ内のローカルな変数や関数を、別のパッケージで定義されているシンボル（エクスポートされていないプライベートなシンボルも含む）にリンクすることを可能にします。
このディレクティブは、主にGoランタイムや標準ライブラリの内部実装で使用され、C言語で書かれた関数やアセンブリコードとGo言語のコードを連携させるために利用されます。例えば、C言語のライブラリ関数をGo言語から直接呼び出すためのラッパー関数をGo言語で記述し、そのGo言語の関数を`//go:linkname`を使ってC言語のシンボルに紐付けるといった用途があります。
このコミットでは、C言語で実装されていたシステムコールや低レベルな処理をGo言語で再実装し、`libc.so`などの外部Cライブラリの関数を`//go:linkname`を通じて呼び出すことで、アセンブリによるサンク（Thunk）を不要にしています。これにより、Goコードの可読性と保守性が向上します。

### アセンブリサンク (Assembly Thunks)
サンクとは、ある関数を呼び出すために必要な追加のコードの小さな断片です。Goランタイムでは、C言語の関数やOSのシステムコールを呼び出す際に、Goの呼び出し規約とCの呼び出し規約の違いを吸収するために、アセンブリ言語で書かれたサンクが使用されることがありました。これらのサンクは、レジスタの保存・復元、引数の配置、戻り値の処理など、低レベルな詳細を扱います。`//go:linkname`の導入により、Go言語のコードから直接C言語の関数を呼び出せるようになったため、これらのアセンブリサンクの多くが不要になりました。

### ネットワークポーリング (Netpoll)
ネットワークポーリングは、Goランタイムが複数のネットワーク接続からのI/Oイベントを効率的に監視し、処理するためのメカニズムです。Goの並行処理モデル（ゴルーチン）を支える重要な要素であり、I/Oブロッキングを回避して多数の同時接続を処理できるようにします。OSごとに異なるI/O多重化メカニズム（Linuxの`epoll`、macOS/BSDの`kqueue`など）を利用しており、Solarisでは「イベントポート（Event Ports）」が使用されます。

### Solaris イベントポート (Solaris Event Ports)
Solarisイベントポートは、Solaris 10で導入された、スケーラブルな非同期I/Oイベント通知メカニズムです。ファイルディスクリプタ（ソケットなど）に関連付けられたI/Oイベント（読み取り可能、書き込み可能など）を効率的に監視できます。
イベントポートは「レベルトリガー（level-triggered）」型です。これは、イベントが発生すると通知され、そのイベントが処理されるまで（またはイベントの状態が変化するまで）繰り返し通知され続けることを意味します。Goランタイムは、このレベルトリガーの特性を考慮して、イベントの再関連付け（re-association）を適切に行う必要があります。
主要なAPIは以下の通りです。
*   `port_create()`: 新しいイベントポートを作成します。
*   `port_associate()`: ファイルディスクリプタをイベントポートに関連付け、監視するイベントの種類を指定します。
*   `port_getn()`: イベントポートで発生したイベントを取得します。

### `systemstack`
`systemstack`は、Goランタイムの内部関数で、現在のゴルーチンのスタックからシステムスタック（Mスタック）に切り替えてコードを実行するために使用されます。これは、Goランタイムの低レベルな処理（例えば、システムコールを直接呼び出す場合など）で、Goのスケジューラやガベージコレクタの影響を受けずに安全に実行する必要がある場合に使われます。このコミットでは、`netpoll.go`から`systemstack`の呼び出しが削除されており、これはGo言語への変換により、これらの処理がGoの通常のスタックで安全に実行できるようになったことを示唆しています。

### `ld.so.1: TLS requirement failure`
`ld.so.1`はSolarisの動的リンカ/ローダです。このエラーは、プログラムが実行時に必要とする共有ライブラリ、特にスレッドローカルストレージ（TLS: Thread Local Storage）に関連するライブラリやシンボルを見つけられない、または正しくロードできない場合に発生します。TLSは、各スレッドが独自のデータを持つことを可能にするメカニズムで、セキュアな通信（SSL/TLS）などでも利用されます。
GoバイナリがC言語の`libc.so`にリンクしなくなったことで、TLS関連の機能が提供されなくなり、このエラーが発生したと考えられます。これは、GoランタイムがCライブラリに依存せずにTLSを扱う方法を独自に実装する必要があることを示しています。

## 技術的詳細

このコミットの技術的詳細は、GoランタイムのSolarisポートをC言語からGo言語へ移行する際の具体的なアプローチと課題を示しています。

### CコードからGoコードへの変換戦略
コミットメッセージにあるように、この変更は「元のCコードの大まかな翻訳」であり、Go言語の慣用的なスタイルへのクリーンアップは後続のコミットで行われる予定です。これは、まず機能的な同等性を確立することを優先し、その後にコード品質の向上を図るという段階的なアプローチを示しています。

### `//go:linkname`によるCライブラリ関数の呼び出し
最も重要な変更点の一つは、C言語のシステムコールやライブラリ関数を呼び出すために`//go:linkname`ディレクティブが活用されていることです。
例えば、`src/runtime/os3_solaris.go`では、以下のような記述が見られます。

```go
//go:cgo_import_dynamic libc_port_create port_create "libc.so"
//go:cgo_import_dynamic libc_port_associate port_associate "libc.so"
//go:cgo_import_dynamic libc_port_dissociate port_dissociate "libc.so"
//go:cgo_import_dynamic libc_port_getn port_getn "libc.so"

//go:linkname libc_port_create libc_port_create
//go:linkname libc_port_associate libc_port_associate
//go:linkname libc_port_dissociate libc_port_dissociate
//go:linkname libc_port_getn libc_port_getn

var (
	libc_port_create,
	libc_port_associate,
	libc_port_dissociate,
	libc_port_getn libcFunc
)
```
`//go:cgo_import_dynamic`は、指定されたシンボルが動的ライブラリ（この場合は`libc.so`）からインポートされることをコンパイラに伝えます。そして、`//go:linkname`は、Goコード内で宣言された`libc_port_create`などの変数を、Cライブラリの実際の`port_create`関数にリンクします。これにより、Go言語の関数`port_create()`が、内部的にCライブラリの`port_create`を呼び出すことができるようになります。

このアプローチにより、GoランタイムはC言語で書かれたアセンブリサンクを排除し、Go言語のコードから直接Cライブラリの関数を呼び出すことが可能になります。これは、GoランタイムのC言語依存性を減らし、Go言語のコードベースをより一貫性のあるものにする上で非常に重要です。

### メモリ管理の統合
コミットメッセージにあるように、Solarisのメモリ管理コードはBSDポートと統合されました。これは、`src/runtime/mem_solaris.c`が削除され、`src/runtime/mem_bsd.go`に`// +build solaris`タグが追加されたことからも明らかです。これは、SolarisとBSDのメモリ管理メカニズム（主に`mmap`や`munmap`などのシステムコール）が類似しているため、共通のGoコードで処理できることを示しています。これにより、コードの重複が減り、保守性が向上します。

### ネットワークポーリング (Netpoll) のGo言語化
`src/runtime/netpoll_solaris.c`が`src/runtime/netpoll_solaris.go`にリネームされ、C言語からGo言語に変換されました。これにより、SolarisのイベントポートAPI（`port_create`, `port_associate`, `port_getn`など）をGo言語から直接操作できるようになりました。
`netpoll.go`の変更点では、`systemstack`の呼び出しが削除されています。これは、`netpollopen`, `netpollclose`, `netpollarm`などの関数が、Go言語で安全に実装されたため、明示的にシステムスタックに切り替える必要がなくなったことを示唆しています。

### 残された課題: TLS要件の失敗
コミットメッセージで言及されている「`ld.so.1: TLS requirement failure`」は、この変換作業における重要な課題です。Goバイナリが`libc.so`にリンクしなくなったことで、TLS（Thread Local Storage）のサポートが利用できなくなり、実行時に問題が発生しています。これは、GoランタイムがTLSを独自に管理するか、または`libc.so`への特定の依存性を再導入する必要があることを示唆しています。この問題は、このコミットの範囲外であり、後続のコミットで解決される予定です。

### その他のOS固有の機能のGo言語化
`src/runtime/os_solaris.c`が削除され、`src/runtime/os2_solaris.go`と`src/runtime/os3_solaris.go`が新規作成されています。これらのファイルには、Solaris固有の定数、シグナルハンドリング、スレッド作成（`pthread_create`）、乱数生成、時間取得（`nanotime`）、ファイル操作（`open`, `read`, `write`, `close`）、メモリ操作（`mmap`, `munmap`, `madvise`）、セマフォ（`sem_init`, `sem_post`, `sem_wait`）など、多岐にわたるシステムコールやOS関連の機能がGo言語で再実装されています。ここでも`//go:cgo_import_dynamic`と`//go:linkname`が多用され、Cライブラリの関数をGoから呼び出すためのラッパーが提供されています。

## コアとなるコードの解説

### `src/runtime/netpoll_solaris.go` (旧 `netpoll_solaris.c`)
このファイルは、Solarisのネットワークポーリングの中核をなす部分であり、C言語からGo言語への変換が最も顕著な箇所です。

**C言語からGo言語への変換例:**
元のCコードでは、`#include`ディレクティブでヘッダファイルをインクルードし、`runtime·`プレフィックスを持つ関数がGoランタイムの内部関数を呼び出していました。

```c
// 旧 netpoll_solaris.c の一部
#include "runtime.h"
// ...
int32
runtime·port_create(void)
{
	return runtime·sysvicall0(libc·port_create);
}
```

これがGo言語に変換されると、`package runtime`となり、`import "unsafe"`が追加されます。Cライブラリ関数へのアクセスは、`//go:cgo_import_dynamic`と`//go:linkname`を通じて行われます。

```go
// 新 netpoll_solaris.go の一部
package runtime

import "unsafe"

//go:cgo_import_dynamic libc_port_create port_create "libc.so"
//go:linkname libc_port_create libc_port_create
var libc_port_create libcFunc

func port_create() int32 {
	return int32(sysvicall0(libc_port_create))
}
```
ここで、`libcFunc`は`uintptr`型として定義され、C関数のアドレスを保持します。`sysvicall0`のような関数は、Goの呼び出し規約からCの呼び出し規約への変換を行い、C関数を呼び出します。これにより、アセンブリサンクが不要になります。

**`netpollinit()`関数の変更:**
C言語版では`runtime·port_create()`を呼び出し、エラー処理を行っていました。
Go言語版では、`port_create()`を直接呼び出し、エラー処理もGoの`print`と`gothrow`を使用しています。

```go
// 新 netpoll_solaris.go の一部
func netpollinit() {
	portfd = port_create()
	if portfd >= 0 {
		fcntl(portfd, _F_SETFD, _FD_CLOEXEC)
		return
	}
	print("netpollinit: failed to create port (", errno(), ")\n")
	gothrow("netpollinit: failed to create port")
}
```

**`netpoll()`関数の変更:**
`netpoll()`関数は、イベントポートからイベントを取得し、準備ができたゴルーチンをスケジューラに通知するGoランタイムの重要な部分です。C言語版ではポインタ操作やCの構造体を使用していましたが、Go言語版ではGoのポインタと`unsafe.Pointer`を適切に利用して変換されています。

```go
// 新 netpoll_solaris.go の一部
func netpoll(block bool) (gp *g) {
	// ...
	var events [128]portevent
	// ...
	if port_getn(portfd, &events[0], uint32(len(events)), &n, wait) < 0 {
		// ...
	}
	// ...
	pd := (*pollDesc)(unsafe.Pointer(ev.portev_user))
	// ...
	netpollready((**g)(noescape(unsafe.Pointer(&gp))), pd, mode)
	// ...
}
```
`portevent`構造体や`pollDesc`構造体へのアクセスがGoの構文に変わり、`unsafe.Pointer`を使ってCのポインタとGoのポインタを相互変換しています。

### `src/runtime/os3_solaris.go` (新規)
このファイルは、SolarisのOS固有の多くのシステムコールをGo言語でラップしています。これは、C言語の`src/runtime/os_solaris.c`の機能を引き継ぐものです。

**システムコールラッパーの例:**
`mmap`関数のGo言語での実装は以下のようになります。

```go
// src/runtime/os3_solaris.go の一部
//go:nosplit
func mmap(addr unsafe.Pointer, n uintptr, prot, flags, fd int32, off uint32) unsafe.Pointer {
	return unsafe.Pointer(sysvicall6(libc_mmap, uintptr(addr), uintptr(n), uintptr(prot), uintptr(flags), uintptr(fd), uintptr(off)))
}
```
ここでも`sysvicall6`のような汎用的な関数を通じて、`libc_mmap`という`//go:linkname`でリンクされたCライブラリの`mmap`関数を呼び出しています。引数は`uintptr`にキャストされ、GoのポインタとCのポインタの間の変換が行われます。

### `src/runtime/netpoll.go` の変更
`netpoll.go`では、`pollDesc`構造体の`user`フィールドの型が`unsafe.Pointer`から`uint32`に変更されています。これは、SolarisのイベントポートAPIが`user`引数として`uintptr`（Goでは`uint32`または`uint64`に相当）を受け取るため、より具体的な型に合わせた変更と考えられます。

また、`netpollServerInit()`, `netpollOpen()`, `netpollClose()`, `netpollWait()`内の`systemstack`の呼び出しが削除されています。これは、Solaris固有の`netpoll`実装がGo言語に変換され、Goのスケジューラとより密接に連携できるようになったため、明示的なスタック切り替えが不要になったことを示唆しています。

### `src/runtime/mem_bsd.go` の変更
`// +build dragonfly freebsd netbsd openbsd` の行に `solaris` が追加されました。
```go
// +build dragonfly freebsd netbsd openbsd solaris
```
これは、Goランタイムのメモリ管理コードが、BSD系のOSとSolarisで共通化されたことを意味します。`src/runtime/mem_solaris.c`が削除されたことと合わせて、Solarisのメモリ管理がGo言語で再実装され、既存のBSD向け実装と統合されたことを示しています。

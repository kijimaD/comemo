## 変更の背景

GoコンパイラのSSAバックエンドにおける共通部分式除去 (CSE) の実装には、特定のシナリオで性能上の問題がありました。CSEの処理中、等価クラス (eqclass) 内の値を処理する際に、最大支配要素 (maximally dominant value) を見つけるために2回のO(n)スキャンが行われていました。

特に、[Issue #15112](https://github.com/golang/go/issues/15112) で報告されたような「不幸なケース」では、互いに支配関係にないブロックに存在する値で構成される大きな等価クラスが出現することがありました。このような状況では、要素が一つずつ除去されるたびにO(n)のスキャンが繰り返され、全体としてO(n^2)の計算量に悪化していました。この非効率性が、コンパイル時間の著しい増加を引き起こしていました。

このコミットは、このO(n^2)の振る舞いを解消し、コンパイラの性能を改善することを目的としています。

## 前提知識の解説

### 共通部分式除去 (Common Subexpression Elimination, CSE)

CSEは、コンパイラ最適化の一種で、プログラム内で同じ式が複数回計算され、その値が計算間で変化しない場合に、冗長な計算を排除する技術です。例えば、`a = b * c` の後に `d = b * c` が続く場合、`b * c` の計算は一度だけ行い、その結果を再利用することで、実行速度を向上させることができます。GoコンパイラはSSA形式を利用してCSEを効率的に行います。

### 静的単一割り当て (Static Single Assignment, SSA)

SSAは、コンパイラの中間表現の一種で、プログラム中のすべての変数に一度だけ値が割り当てられるようにする特性を持ちます。これにより、データフロー解析が大幅に簡素化され、CSEのような最適化が容易になります。Goコンパイラは、ソースコードをSSA形式に変換してから様々な最適化を適用します。

### ドミナンス (Dominance) とドミナンスツリー (Dominator Tree)

コンパイラ理論において、制御フローグラフ (Control Flow Graph, CFG) 内のブロックAがブロックBを「支配する (dominate)」とは、CFGのエントリポイントからBへのすべてのパスがAを通過する場合を指します。つまり、Bが実行される前に必ずAが実行されることを意味します。

ドミナンスツリーは、この支配関係を階層的に表現するデータ構造です。ツリーの根はCFGのエントリブロックであり、各ノードの子はそのノードによって直接支配されるブロックを表します。CSEのような最適化では、ある式の値が再利用可能かどうかを判断するために、支配関係が重要な役割を果たします。ある場所で計算された式の値を別の場所で再利用するには、最初の計算場所が後の計算場所を支配している必要があります。

### 等価クラス (Equivalence Class, `eqclass`)

CSEの文脈における等価クラスは、同じ値を計算する可能性のある式や値の集合を指します。コンパイラはこれらの等価クラスを管理し、クラス内の冗長な計算を特定して除去します。

## 技術的詳細

このコミットの核心は、CSEパスにおける等価クラスの処理方法の改善にあります。以前の実装では、`eqclass` 内の複数の値の中から「最大支配要素 (maximally dominant value)」を見つけるために、線形スキャン（O(n)）を繰り返していました。このスキャンは、特に大きな `eqclass` で、かつその中の値が互いに支配関係にないブロックに散らばっている場合に、非効率なO(n^2)の動作を引き起こしていました。

新しいアプローチでは、`eqclass` を処理する前に、その中の値をドミナンス順にソートします。これにより、最も支配的な値が常にリストの先頭に来るようになります。ソートされたリストを利用することで、最大支配要素を見つけるための線形スキャンが不要になり、リストの先頭要素を直接参照するだけでよくなります。

具体的には、`sort.Sort` インターフェースを実装する `sortbyentry` という新しい型が導入されました。この型は、`sparseTree` の `maxdomorder` メソッドを利用して、ブロックの `entry` フィールドに基づき値をソートします。`entry` フィールドは、ドミナンスツリーにおけるブロックの順序付けを反映しており、この順序でソートすることで、支配的なブロックに属する値が先にくるようになります。

ソート後、`cse` 関数は `e[0]` を最大支配要素として扱い、残りの要素 (`e[1:]`) を順次処理します。これにより、以前の `for _, w := range e[1:] { ... }` のような最大支配要素を探索するループが不要になります。また、要素を削除する際も、ソート順を維持するように `copy` を使用して効率的に行われます。

`sparsetree.go` に追加された `isAncestorEq` の修正は、`x == y` のケースを明示的に処理することで、ドミナンス関係の判定をより正確にしています。また、`maxdomorder` 関数は、ブロックの `entry` フィールドを返すことで、ソートキーを提供します。

この変更により、[Issue #15112](https://github.com/golang/go/issues/15112) で報告されたような特定のコードパターンにおいて、コンパイル時間が大幅に短縮されました。

## コアとなるコードの解説

### `cse.go` の変更点

1.  **`sort.Sort(sortbyentry{e, f.sdom})` の追加**:
    `cse` 関数内の `for _, e := range partition` ループの冒頭で、各等価クラス `e` が `sortbyentry` 型を使用してソートされるようになりました。これにより、`e` の要素はドミナンス順に並べ替えられ、最も支配的な値が `e[0]` に配置されます。

2.  **最大支配要素探索ループの削除**:
    以前は `v := e[0]` の後に `for _, w := range e[1:] { if f.sdom.isAncestorEq(w.Block, v.Block) { v = w } }` というループがあり、`e` の中で最も支配的な `v` を探索していました。ソートにより `e[0]` が常に最大支配要素となるため、このループは不要となり削除されました。

3.  **要素除去ロジックの変更**:
    `e` から要素 `w` を除去する際に、`e, e[i] = e[:len(e)-1], e[len(e)-1]` のようなスライスの末尾要素とのスワップではなく、`copy(e[i:], e[i+1:])` と `e = e[:len(e)-1]` を使用するようになりました。これは、ソートされた順序を維持しながら要素を効率的に削除するための変更です。

4.  **`sortbyentry` 型の追加**:
    `sort.Sort` インターフェース (`Len`, `Swap`, `Less` メソッド) を実装する `sortbyentry` という新しい構造体が定義されました。
    *   `Less(i, j int) bool`: このメソッドがソートの基準を定義します。`sv.sdom.maxdomorder(v.Block) < sv.sdom.maxdomorder(w.Block)` を使用して、2つの値 `v` と `w` が属するブロックのドミナンス順序を比較します。`maxdomorder` が小さいブロックほど、より支配的であると見なされます。

### `sparsetree.go` の変更点

1.  **`isAncestorEq` の修正**:
    `isAncestorEq` 関数に `if x == y { return true }` というチェックが追加されました。これは、ブロック `x` がブロック `y` と同じである場合、`x` は `y` を支配する（または `y` と等しい）という定義を明示的にカバーするための修正です。

2.  **`maxdomorder` 関数の追加**:
    `maxdomorder(x *Block) int32` という新しい関数が `sparseTree` に追加されました。この関数は、与えられたブロック `x` の `entry` フィールドの値を返します。`entry` フィールドは、ドミナンスツリーのトラバーサル順序に基づいて割り当てられる値であり、この値が小さいほど、そのブロックはより支配的である可能性が高いことを示します。`sortbyentry` の `Less` メソッドはこの `maxdomorder` を利用して、ドミナンス順のソートを実現します。

これらの変更により、CSEの等価クラス処理における非効率な線形スキャンが排除され、コンパイラの性能が向上しました。

### ドミナンス (Dominance) とドミナンスツリー (Dominator Tree)

コンパイラ理論において、制御フローグラフ (Control Flow Graph, CFG) 内のブロックAがブロックBを「支配する (dominate)」とは、CFGのエントリポイントからBへのすべてのパスがAを通過する場合を指します。つまり、Bが実行される前に必ずAが実行されることを意味します。

ドミナンスツリーは、この支配関係を階層的に表現するデータ構造です。ツリーの根はCFGのエントリブロックであり、各ノードの子はそのノードによって直接支配されるブロックを表します。CSEのような最適化では、ある式の値が再利用可能かどうかを判断するために、支配関係が重要な役割を果たします。ある場所で計算された式の値を別の場所で再利用するには、最初の計算場所が後の計算場所を支配している必要があります。

### 等価クラス (Equivalence Class, `eqclass`)

CSEの文脈における等価クラスは、同じ値を計算する可能性のある式や値の集合を指します。コンパイラはこれらの等価クラスを管理し、クラス内の冗長な計算を特定して除去します。

## 技術的詳細

このコミットの核心は、CSEパスにおける等価クラスの処理方法の改善にあります。以前の実装では、`eqclass` 内の複数の値の中から「最大支配要素 (maximally dominant value)」を見つけるために、線形スキャン（O(n)）を繰り返していました。このスキャンは、特に大きな `eqclass` で、かつその中の値が互いに支配関係にないブロックに散らばっている場合に、非効率なO(n^2)の動作を引き起こしていました。

新しいアプローチでは、`eqclass` を処理する前に、その中の値をドミナンス順にソートします。これにより、最も支配的な値が常にリストの先頭に来るようになります。ソートされたリストを利用することで、最大支配要素を見つけるための線形スキャンが不要になり、リストの先頭要素を直接参照するだけでよくなります。

具体的には、`sort.Sort` インターフェースを実装する `sortbyentry` という新しい型が導入されました。この型は、`sparseTree` の `maxdomorder` メソッドを利用して、ブロックの `entry` フィールドに基づき値をソートします。`entry` フィールドは、ドミナンスツリーにおけるブロックの順序付けを反映しており、この順序でソートすることで、支配的なブロックに属する値が先にくるようになります。

ソート後、`cse` 関数は `e[0]` を最大支配要素として扱い、残りの要素 (`e[1:]`) を順次処理します。これにより、以前の `for _, w := range e[1:] { ... }` のような最大支配要素を探索するループが不要になります。また、要素を削除する際も、ソート順を維持するように `copy` を使用して効率的に行われます。

`sparsetree.go` に追加された `isAncestorEq` の修正は、`x == y` のケースを明示的に処理することで、ドミナンス関係の判定をより正確にしています。また、`maxdomorder` 関数は、ブロックの `entry` フィールドを返すことで、ソートキーを提供します。

この変更により、[Issue #15112](https://github.com/golang/go/issues/15112) で報告されたような特定のコードパターンにおいて、コンパイル時間が大幅に短縮されました。

## コアとなるコードの解説

### `cse.go` の変更点

1.  **`sort.Sort(sortbyentry{e, f.sdom})` の追加**:
    `cse` 関数内の `for _, e := range partition` ループの冒頭で、各等価クラス `e` が `sortbyentry` 型を使用してソートされるようになりました。これにより、`e` の要素はドミナンス順に並べ替えられ、最も支配的な値が `e[0]` に配置されます。

2.  **最大支配要素探索ループの削除**:
    以前は `v := e[0]` の後に `for _, w := range e[1:] { if f.sdom.isAncestorEq(w.Block, v.Block) { v = w } }` というループがあり、`e` の中で最も支配的な `v` を探索していました。ソートにより `e[0]` が常に最大支配要素となるため、このループは不要となり削除されました。

3.  **要素除去ロジックの変更**:
    `e` から要素 `w` を除去する際に、`e, e[i] = e[:len(e)-1], e[len(e)-1]` のようなスライスの末尾要素とのスワップではなく、`copy(e[i:], e[i+1:])` と `e = e[:len(e)-1]` を使用するようになりました。これは、ソートされた順序を維持しながら要素を効率的に削除するための変更です。

4.  **`sortbyentry` 型の追加**:
    `sort.Sort` インターフェース (`Len`, `Swap`, `Less` メソッド) を実装する `sortbyentry` という新しい構造体が定義されました。
    *   `Less(i, j int) bool`: このメソッドがソートの基準を定義します。`sv.sdom.maxdomorder(v.Block) < sv.sdom.maxdomorder(w.Block)` を使用して、2つの値 `v` と `w` が属するブロックのドミナンス順序を比較します。`maxdomorder` が小さいブロックほど、より支配的であると見なされます。

### `sparsetree.go` の変更点

1.  **`isAncestorEq` の修正**:
    `isAncestorEq` 関数に `if x == y { return true }` というチェックが追加されました。これは、ブロック `x` がブロック `y` と同じである場合、`x` は `y` を支配する（または `y` と等しい）という定義を明示的にカバーするための修正です。

2.  **`maxdomorder` 関数の追加**:
    `maxdomorder(x *Block) int32` という新しい関数が `sparseTree` に追加されました。この関数は、与えられたブロック `x` の `entry` フィールドの値を返します。`entry` フィールドは、ドミナンスツリーのトラバーサル順序に基づいて割り当てられる値であり、この値が小さいほど、そのブロックはより支配的である可能性が高いことを示します。`sortbyentry` の `Less` メソッドはこの `maxdomorder` を利用して、ドミナンス順のソートを実現します。

これらの変更により、CSEの等価クラス処理における非効率な線形スキャンが排除され、コンパイラの性能が向上しました。

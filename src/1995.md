# [インデックス 1995] ファイルの概要

このコミットは、Go言語のランタイムにおける文字列の`range`ループが、Unicodeの全範囲（特に`U+10000`から`U+10FFFF`までのサロゲートペアではない補助多言語面（SMP）の文字）を正しく処理できるようにするための重要な修正を含んでいます。具体的には、UTF-8デコードロジックを改善し、文字列の終端や不正なシーケンスに対する堅牢性を高めています。また、この変更を検証するための新しいテストケースも追加されています。

## 変更の背景

Go言語は設計当初からUnicodeを第一級市民として扱い、文字列はUTF-8でエンコードされたバイト列として内部的に表現されます。しかし、初期のGoランタイムにおける文字列の`for...range`ループの実装には、いくつかの課題がありました。

1.  **Unicodeの全範囲サポートの不完全さ**: UTF-8は、`U+0000`から`U+10FFFF`までの全てのUnicodeコードポイントを表現できます。しかし、初期の実装では、特に4バイトで表現される補助多言語面（SMP）の文字（`U+10000`以上）のデコードが不完全であった可能性があります。これにより、これらの文字を含む文字列を`range`でイテレートした際に、正しくないルーン値が返されたり、ランタイムエラーが発生したりする可能性がありました。
2.  **UTF-8デコードの堅牢性**: 文字列の終端でマルチバイト文字が途切れている場合や、不正なUTF-8シーケンスが含まれている場合に、デコーダが安全に処理できない可能性がありました。従来の`chartorune`関数は、入力文字列が常にヌル終端されていることを前提としていたり、残りのバイト長を考慮せずに読み進めてしまうことで、メモリの範囲外アクセス（Out-of-bounds read）を引き起こすリスクがありました。
3.  **`for...range`ループのセマンティクス**: Goの`for...range`ループは、文字列に対して使用された場合、各イテレーションでインデックスとルーン値のペアを返します。このとき、インデックス変数がループ終了時にどのような値を持つべきかというセマンティクスが、初期の段階ではまだ完全に固まっていなかったか、実装と仕様の間に微妙な乖離があった可能性があります。コミットメッセージにある「test has minor failure: after loop the index == len(s); should be len(s)-1 in this case. according to spec, vars are left at position at last iteration.」という記述は、この点に関する議論や調整があったことを示唆しています。

これらの課題を解決し、Goの文字列処理をより堅牢で仕様に準拠したものにするために、このコミットが導入されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

*   **UnicodeとUTF-8**:
    *   **Unicode**: 世界中の文字を統一的に扱うための文字コード標準です。各文字には一意の「コードポイント」（例: `U+0041`は'A'）が割り当てられています。
    *   **UTF-8**: Unicodeコードポイントをバイト列にエンコードするための可変長エンコーディング方式です。ASCII文字は1バイト、その他の文字は2〜4バイトで表現されます。特に、`U+10000`以上のコードポイントは4バイトでエンコードされます。UTF-8は自己同期性があり、バイト列の途中からでも文字の境界を比較的容易に特定できる特性を持ちます。
*   **Go言語の文字列と`rune`**:
    *   Go言語において、`string`型は不変のバイトスライスであり、通常はUTF-8でエンコードされたテキストを保持します。
    *   `rune`型はGoの組み込み型で、Unicodeのコードポイントを表す`int32`のエイリアスです。
    *   Goの`for...range`ループを文字列に適用すると、各イテレーションで`rune`（Unicodeコードポイント）とそのUTF-8エンコードされたバイト列の開始インデックスが返されます。
*   **`chartorune`と`charntorune`**:
    *   `chartorune`は、C言語で書かれたUTF-8デコード関数で、Goランタイムの内部で使用されていました。これは、与えられたバイト列の先頭から1つのルーンをデコードし、そのルーン値と消費したバイト数を返します。
    *   `charntorune`は、`chartorune`の改良版です。`chartorune`がバイト列の長さ情報を考慮しないのに対し、`charntorune`はデコード可能な最大バイト長（`length`引数）を受け取ります。これにより、文字列の終端でマルチバイト文字が途切れている場合でも、安全に処理を行うことができます。不正なシーケンスや不完全なシーケンスに対しては、エラーを示す特別なルーン値（`Bad`）を返し、消費バイト数を`0`または`1`とすることで、ランタイムのクラッシュを防ぎます。
*   **`Runemax`**: Unicodeで定義されている最大のコードポイント値（`U+10FFFF`）を表す定数です。このコミットでは、`rune.c`内でこの定数が明示的に定義され、UTF-8デコーダがこの範囲までを正しく処理することを目指していることが示されています。

## 技術的詳細

このコミットの主要な技術的変更点は、GoランタイムのUTF-8デコードロジックの強化です。

1.  **`charntorune`関数の導入**:
    *   `src/runtime/rune.c`に`charntorune(int32 *rune, uint8 *str, int32 length)`という新しい関数が追加されました。
    *   この関数は、`str`が指すバイト列からUnicodeルーンをデコードします。
    *   重要なのは、`length`引数を受け取ることです。これは、`str`から読み取ってよいバイトの最大長を示します。これにより、デコーダは文字列の境界を越えて読み取ろうとすることを防ぎます。
    *   関数内部では、UTF-8の各バイトシーケンス（1バイト、2バイト、3バイト、4バイト）の構造をチェックし、対応するルーン値を計算します。
    *   デコード中に、`length`を超えて読み取ろうとした場合や、不正なUTF-8シーケンス（例: 期待される継続バイトがない、オーバーロングエンコーディング、`Runemax`を超える値など）を検出した場合は、`Bad`ルーン（`0xFFFD`、UnicodeのReplacement Character）を返し、消費バイト数を適切に設定します（通常は`1`、不完全な場合は`0`）。
    *   この関数は、Wei-Hwa Huang氏によって2004年にGoogle社で修正されたバージョンに基づいていることがコメントに明記されており、その堅牢性が強調されています。

2.  **`chartorune`から`charntorune`への置き換え**:
    *   `src/runtime/string.c`において、従来の`static int32 chartorune(int32 *rune, byte *str);`の宣言と実装が削除されました。
    *   文字列の`for...range`ループを処理する`sys·stringiter`および`sys·stringiter2`関数内で、ルーンのデコードに`chartorune`の代わりに`charntorune`が使用されるようになりました。
    *   具体的には、`n = charntorune(&l, s.str+k, s.len-k);`という形で呼び出されます。ここで、`s.len-k`は現在のオフセット`k`から文字列の終端までの残りのバイト数を示し、`charntorune`に安全なデコード範囲を提供します。
    *   これにより、文字列の終端でマルチバイト文字が途切れている場合でも、`charntorune`が安全に`Bad`ルーンを返すようになり、ランタイムの安定性が向上します。

3.  **`Runemax`定数の定義**:
    *   `src/runtime/rune.c`に`Runemax = 0x10FFFF`が定義されました。これは、Unicodeの最大コードポイントを明示的に示すもので、`charntorune`関数内でデコードされたルーン値がこの範囲を超えていないかをチェックするために使用されます。これにより、不正なエンコーディングが`Runemax`を超えるルーン値を生成するのを防ぎます。

4.  **テストケースの追加**:
    *   `test/stringrange.go`という新しいテストファイルが追加されました。このテストは、様々なUnicode文字（特に4バイト文字である`U+10FFFF`を含む）を含む文字列に対して`for...range`ループを実行し、返されるインデックスとルーン値が期待通りであることを検証します。
    *   このテストは、`utf8.DecodeRuneInString`関数（Goの標準ライブラリのUTF-8デコーダ）の結果と比較することで、ランタイムのデコードロジックが正しく機能していることを確認します。
    *   コミットメッセージにある「test has minor failure: after loop the index == len(s); should be len(s)-1 in this case.」という記述は、このテストが`for...range`ループ終了時のインデックス変数の最終値に関するGoの仕様の微妙な点（最後のルーンの開始インデックスで止まるべきか、文字列の終端を指すべきか）を浮き彫りにしたことを示しています。このコミットでは、`i != len(s)-1`のチェックが追加されており、ループ終了時の`i`が`len(s)-1`であるべきという期待が示されていますが、これは後のGoの仕様で調整される可能性があります。

### `src/runtime/rune.c`

`charntorune`関数の追加。

```c
+/*
+ * Modified by Wei-Hwa Huang, Google Inc., on 2004-09-24
+ * This is a slower but "safe" version of the old chartorune
+ * that works on strings that are not necessarily null-terminated.
+ * 
+ * If you know for sure that your string is null-terminated,
+ * chartorune will be a bit faster.
+ *
+ * It is guaranteed not to attempt to access "length"
+ * past the incoming pointer.  This is to avoid
+ * possible access violations.  If the string appears to be
+ * well-formed but incomplete (i.e., to get the whole Rune
+ * we'd need to read past str+length) then we'll set the Rune
+ * to Bad and return 0.
+ *
+ * Note that if we have decoding problems for other
+ * reasons, we return 1 instead of 0.
+ */
+int32
+charntorune(int32 *rune, uint8 *str, int32 length)
+{
+	int32 c, c1, c2, c3, l;
+
+	/* When we're not allowed to read anything */
+	if(length <= 0) {
+		goto badlen;
+	}
+
+	/*
+	 * one character sequence (7-bit value)
+	 *	00000-0007F => T1
+	 */
+	c = *(uint8*)str;
+	if(c < Tx) {
+		*rune = c;
+		return 1;
+	}
+
+	// If we can't read more than one character we must stop
+	if(length <= 1) {
+		goto badlen;
+	}
+
+	/*
+	 * two character sequence (11-bit value)
+	 *	0080-07FF => T2 Tx
+	 */
+	c1 = *(uint8*)(str+1) ^ Tx;
+	if(c1 & Testx)
+		goto bad;
+	if(c < T3) {
+		if(c < T2)
+			goto bad;
+		l = ((c << Bitx) | c1) & Rune2;
+		if(l <= Rune1)
+			goto bad;
+		*rune = l;
+		return 2;
+	}
+
+	// If we can't read more than two characters we must stop
+	if(length <= 2) {
+		goto badlen;
+	}
+
+	/*
+	 * three character sequence (16-bit value)
+	 *	0800-FFFF => T3 Tx Tx
+	 */
+	c2 = *(uint8*)(str+2) ^ Tx;
+	if(c2 & Testx)
+		goto bad;
+	if(c < T4) {
+		l = ((((c << Bitx) | c1) << Bitx) | c2) & Rune3;
+		if(l <= Rune2)
+			goto bad;
+		*rune = l;
+		return 3;
+	}
+
+	if (length <= 3)
+		goto badlen;
+
+	/*
+	 * four character sequence (21-bit value)
+	 *	10000-1FFFFF => T4 Tx Tx Tx
+	 */
+	c3 = *(uint8*)(str+3) ^ Tx;
+	if (c3 & Testx)
+		goto bad;
+	if (c < T5) {
+		l = ((((((c << Bitx) | c1) << Bitx) | c2) << Bitx) | c3) & Rune4;
+		if (l <= Rune3 || l > Runemax)
+			goto bad;
+		*rune = l;
+		return 4;
+	}
+
+	// Support for 5-byte or longer UTF-8 would go here, but
+	// since we don't have that, we'll just fall through to bad.
+
+	/*
+	 * bad decoding
+	 */
+bad:
+	*rune = Bad;
+	return 1;
+badlen:
+	*rune = Bad;
+	return 0;
+
+}
```

package main

import(
        "fmt";
        "utf8";
)

func main() {
	s := "\000\123\x00\xca\xFE\u0123\ubabe\U0000babe\U0010FFFFx";
	expect := []int{ 0, 0123, 0, 0xFFFD, 0xFFFD, 0x123, 0xbabe, 0xbabe, 0x10FFFF, 'x' };
	var rune, size int;
	offset := 0;
	var i, c int;
	ok := true;
	cnum := 0;
	for i, c = range s {
		rune, size := utf8.DecodeRuneInString(s, i);  // check it another way
		if i != offset {
			fmt.Printf("unexpected offset %d not %d\n", i, offset);
			ok = false;
		}
		if rune != expect[cnum] {
			fmt.Printf("unexpected rune %d from DecodeRuneInString: %x not %x\n", i, rune, expect[cnum]);
			ok = false;
		}
		if c != expect[cnum] {
			fmt.Printf("unexpected rune %d from range: %x not %x\n", i, rune, expect[cnum]);
			ok = false;
		}
		offset += size;
		cnum++;
	}
	if i != len(s)-1 {
		fmt.Println("after loop i is", i, "not", len(s)-1);
		ok = false;
	}
	if !ok {
		fmt.Println("FAIL");
		sys.Exit(1)
	}
}

## コアとなるコードの解説

このコミットの核心は、Goランタイムが文字列をUTF-8として安全かつ正確に処理できるようにするための、低レベルなUTF-8デコードロジックの改善にあります。

*   **`charntorune`の安全性**:
    *   従来の`chartorune`は、入力バイト列の長さを考慮せずにデコードを試みる可能性があり、文字列の終端でマルチバイト文字が途切れている場合に、メモリの範囲外を読み取ってしまう危険性がありました。
    *   `charntorune`は`length`引数を受け取ることで、この問題を解決しています。デコード処理の各段階（1バイト、2バイト、3バイト、4バイトシーケンスの読み取り）で、残りの`length`が十分にあるかを厳密にチェックします。これにより、不正なアクセスを防ぎ、ランタイムの安定性を向上させます。
    *   コメントにある「slower but "safe" version」という記述は、この安全性向上のために、わずかなパフォーマンスオーバーヘッドがある可能性を示唆していますが、堅牢性の方が優先されたことを意味します。
*   **Unicode全範囲のサポート**:
    *   `charntorune`の実装は、UTF-8の仕様に厳密に従い、最大4バイトで表現される`U+10FFFF`までのUnicodeコードポイントを正しくデコードできるように設計されています。特に、`Runemax`定数との比較により、デコードされたルーン値が有効なUnicode範囲内にあることを保証します。
*   **`for...range`ループの正確性**:
    *   `src/runtime/string.c`における`sys·stringiter`および`sys·stringiter2`関数での`charntorune`の採用により、Goの文字列`for...range`ループは、より正確なルーン値とインデックスを返すようになりました。これにより、開発者はGoの文字列がUnicodeを正しく扱うことを信頼してコードを書けるようになります。
    *   `test/stringrange.go`は、この新しいデコードロジックが、様々なUnicode文字（特に`U+10FFFF`のような高位のコードポイント）に対して期待通りに機能することを検証します。このテストは、Goの文字列処理の正確性を保証するための重要な回帰テストとなります。
*   **エラーハンドリングの改善**:
    *   `charntorune`は、不正なUTF-8シーケンスや不完全なシーケンスを検出した場合に、`Bad`ルーン（`0xFFFD`）を返し、消費バイト数を適切に設定します。これにより、Goの文字列処理は、不正な入力に対しても予測可能な挙動を示すようになります。

このコミットは、Go言語がその初期段階からUnicodeとUTF-8の正しい取り扱いを重視し、ランタイムレベルでその堅牢性を確保しようとしていたことを明確に示しています。

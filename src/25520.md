# [インデックス 25520] ファイルの概要

このコミットは、Go言語の `archive/tar` パッケージにおいて、tarアーカイブ内のファイルが途中で切り詰められている（truncated）場合に、それを正確に検出する機能を追加するものです。特に、`io.Seeker` インターフェースを実装するリーダーを使用している場合に発生していた問題に対処し、`io.ErrUnexpectedEOF` を適切に報告するように改善されています。

## コミット

`archive/tar` パッケージの `Reader` が、tarアーカイブ内の切り詰められたファイルをより確実に検出できるように修正されました。以前は、`Reader.skipUnread` メソッドが `io.ErrUnexpectedEOF` を報告せず、また `io.Seeker` のエラー報告の遅延により、切り詰められたファイルを検出できない場合がありました。このコミットでは、データの終端の1バイト手前にシークし、`io.CopyN` を使用してエラーを確実に捕捉することで、この問題を解決しています。

## 元コミット内容

```
archive/tar: detect truncated files

Motivation:
* Reader.skipUnread never reports io.ErrUnexpectedEOF. This is strange
given that io.ErrUnexpectedEOF is given through Reader.Read if the
user manually reads the file.
* Reader.skipUnread fails to detect truncated files since io.Seeker
is lazy about reporting errors. Thus, the behavior of Reader differs
whether the input io.Reader also satisfies io.Seeker or not.

To solve this, we seek to one before the end of the data section and
always rely on at least one call to io.CopyN. If the tr.r satisfies
io.Seeker, this is guarunteed to never read more than blockSize.

Fixes #12557

Change-Id: I0ddddfc6bed0d74465cb7e7a02b26f1de7a7a279
```

## 変更の背景

この変更の主な背景には、`archive/tar` パッケージの `Reader` が、不完全な（切り詰められた）tarアーカイブファイルを処理する際の挙動に一貫性がなく、また期待されるエラーを報告しないという問題がありました。

具体的には、以下の2点が問題視されていました。

1.  **`Reader.skipUnread` が `io.ErrUnexpectedEOF` を報告しない**: `io.Reader` インターフェースを通じてファイルを読み込む場合、予期せぬEOF（ファイルの終端）に達すると `io.ErrUnexpectedEOF` が返されるのが一般的です。しかし、`tar.Reader` の内部メソッドである `skipUnread` は、未読のバイトやパディングをスキップする際に、データが途中で途切れていてもこのエラーを報告しませんでした。これにより、ユーザーが手動でファイルを読み込む場合と `tar.Reader` を介して読み込む場合とで、エラーの挙動が異なっていました。
2.  **`io.Seeker` のエラー報告の遅延**: `tar.Reader` が内部で `io.Seeker` インターフェースを実装するリーダー（例: `os.File`）を使用している場合、`Seek` 操作はエラーをすぐに報告しないことがあります。例えば、ファイルサイズを超えてシークしようとしても、すぐにエラーが返されず、実際にその位置から読み込みを試みたときに初めてエラーが顕在化することがあります。この「遅延エラー報告」の特性により、`skipUnread` は切り詰められたファイルを検出できず、`io.Seeker` を使用するかどうかで `tar.Reader` の挙動が変わってしまうという問題がありました。

これらの問題は、Go Issue #12557 で報告されており、このコミットはその問題を解決するために行われました。目的は、どのような種類の `io.Reader` が使われていても、切り詰められたtarファイルを確実に検出し、適切な `io.ErrUnexpectedEOF` を報告することにありました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **tarアーカイブ形式**: tar (tape archive) は、複数のファイルを1つのアーカイブファイルにまとめるための形式です。各ファイルはヘッダーブロックとデータブロック、そしてパディングブロックで構成されます。ヘッダーにはファイル名、サイズ、パーミッションなどのメタデータが含まれ、データブロックには実際のファイル内容が格納されます。各ブロックは通常512バイトの倍数でアラインされます。
*   **`io.Reader` インターフェース**: Go言語の標準ライブラリ `io` パッケージで定義されている基本的なインターフェースで、`Read(p []byte) (n int, err error)` メソッドを持ちます。データを読み込むための最も一般的な抽象化です。
*   **`io.Seeker` インターフェース**: `io.Reader` と同様に `io` パッケージで定義されており、`Seek(offset int64, whence int) (int64, error)` メソッドを持ちます。これは、読み書き位置をファイル内で移動させる機能を提供します。`os.File` など、ランダムアクセスが可能なファイルは `io.Seeker` を実装しています。
*   **`io.EOF` と `io.ErrUnexpectedEOF`**:
    *   `io.EOF` (End Of File): 期待通りにファイルの終端に達したことを示すエラーです。
    *   `io.ErrUnexpectedEOF`: 期待されるデータ量よりも早くファイルの終端に達した場合に発生するエラーです。例えば、固定長のデータを読み込もうとしたが、途中でファイルが終わってしまった場合などに使われます。このエラーは、データが不完全であることを示唆します。
*   **`io.CopyN`**: `io.CopyN(dst Writer, src Reader, n int64) (written int64, err error)` は、`src` から `n` バイトを `dst` にコピーする関数です。`n` バイトをコピーする前に `src` がEOFに達した場合、`io.ErrUnexpectedEOF` を返します。
*   **`ioutil.Discard`**: `io.Writer` インターフェースを実装する特殊なオブジェクトで、書き込まれたデータをすべて破棄します。このコミットでは、未読のバイトをスキップするために、読み込んだデータをどこにも保存せずに捨てる目的で使用されています。

## 技術的詳細

このコミットの核心は、`archive/tar` パッケージの `Reader` 型に存在する `skipUnread` メソッドの挙動を改善することにあります。このメソッドは、現在のtarエントリの未読データとパディングをスキップして、次のヘッダーブロックの開始位置にリーダーを移動させる役割を担っています。

変更前は、`skipUnread` は `io.Seeker` を実装するリーダーに対しては `Seek` メソッドを使って一気にスキップしようとしていました。しかし、`io.Seeker` の `Seek` メソッドは、指定されたオフセットがファイルの終端を超えていても、すぐにエラーを報告しないことがあります。エラーは、その位置から実際に読み込みを試みたときに初めて発生します。この「遅延エラー報告」が、切り詰められたファイルの検出を妨げていました。

変更後のアプローチは以下の通りです。

1.  **`io.Seeker` の利用の変更**:
    *   `skipUnread` は、まず `io.Seeker` インターフェースを実装しているかどうかを確認します。
    *   もし `io.Seeker` であり、かつスキップすべきデータが1バイトより多い場合 (`dataSkip > 1`)、データの終端の**1バイト手前**まで `Seek` を試みます。
    *   なぜ1バイト手前かというと、`Seek` がエラーを報告しない可能性があるため、最後の1バイトは `io.CopyN` で読み込むことで、`io.ErrUnexpectedEOF` を確実に発生させるためです。
    *   `Seek` が実際にサポートされているかを確認するために、まず `sr.Seek(0, os.SEEK_CUR)` を呼び出して現在の位置を取得し、エラーがないことを確認しています。これは、`os.Stdin` のように `io.Seeker` を実装していても、実際にはシークできないリーダーが存在するためです。
2.  **`io.CopyN` の活用**:
    *   `Seek` でスキップしたバイト数を `seekSkipped` として記録します。
    *   残りのバイト数 (`totalSkip - seekSkipped`) を `io.CopyN(ioutil.Discard, tr.r, ...)` を使ってスキップします。
    *   `io.CopyN` は、指定されたバイト数を読み込む前にEOFに達した場合、`io.ErrUnexpectedEOF` を返します。これにより、切り詰められたファイルを確実に検出できるようになります。
3.  **エラーの正規化**:
    *   `io.CopyN` が `io.EOF` を返した場合でも、`seekSkipped + copySkipped` が `dataSkip` (スキップすべきデータバイト数) よりも少ない場合は、データが不完全であることを意味するため、`tr.err` を `io.ErrUnexpectedEOF` に上書きします。これにより、`skipUnread` が常に適切なエラーを報告するようになります。

この変更により、`tar.Reader` は、基盤となるリーダーが `io.Seeker` を実装しているかどうかにかかわらず、切り詰められたファイルを一貫して正確に検出できるようになりました。また、`io.ErrUnexpectedEOF` が適切な状況で報告されるようになり、ユーザーはアーカイブの破損をより確実に検知できるようになります。

テストコード (`reader_test.go`) では、様々な長さで切り詰められたtarファイルに対して、`io.Reader` のみ、`io.ReadSeeker`、そして `Seek` が常にエラーを返す `readBadSeeker` の3種類のリーダーを組み合わせてテストしています。これにより、あらゆるシナリオで切り詰められたファイルの検出が正しく行われることを検証しています。

## コアとなるコードの解説

### `src/archive/tar/reader.go` の `skipUnread` メソッド

```go
// skipUnread skips any unread bytes in the existing file entry, as well as any
// alignment padding. It returns io.ErrUnexpectedEOF if any io.EOF is
// encountered in the data portion; it is okay to hit io.EOF in the padding.
//
// Note that this function still works properly even when sparse files are being
// used since numBytes returns the bytes remaining in the underlying io.Reader.
func (tr *Reader) skipUnread() error {
	dataSkip := tr.numBytes()      // Number of data bytes to skip
	totalSkip := dataSkip + tr.pad // Total number of bytes to skip
	tr.curr, tr.pad = nil, 0

	// If possible, Seek to the last byte before the end of the data section.
	// Do this because Seek is often lazy about reporting errors; this will mask
	// the fact that the tar stream may be truncated. We can rely on the
	// io.CopyN done shortly afterwards to trigger any IO errors.
	var seekSkipped int64 // Number of bytes skipped via Seek
	if sr, ok := tr.r.(io.Seeker); ok && dataSkip > 1 {
		// Not all io.Seeker can actually Seek. For example, os.Stdin implements
		// io.Seeker, but calling Seek always returns an error and performs
		// no action. Thus, we try an innocent seek to the current position
		// to see if Seek is really supported.
		pos1, err := sr.Seek(0, os.SEEK_CUR)
		if err == nil {
			// Seek seems supported, so perform the real Seek.
			pos2, err := sr.Seek(dataSkip-1, os.SEEK_CUR)
			if err != nil {
				tr.err = err
				return tr.err
			}
			seekSkipped = pos2 - pos1
		}
	}

	var copySkipped int64 // Number of bytes skipped via CopyN
	copySkipped, tr.err = io.CopyN(ioutil.Discard, tr.r, totalSkip-seekSkipped)
	if tr.err == io.EOF && seekSkipped+copySkipped < dataSkip {
		tr.err = io.ErrUnexpectedEOF
	}
	return tr.err
}
```

このコードは、`skipUnread` メソッドの新しい実装を示しています。

1.  `dataSkip` と `totalSkip` は、それぞれデータ部分とパディングを含む合計でスキップすべきバイト数を計算します。
2.  `tr.curr` と `tr.pad` をリセットし、現在のエントリの読み込み状態をクリアします。
3.  `io.Seeker` インターフェースのチェックと安全なシーク:
    *   `if sr, ok := tr.r.(io.Seeker); ok && dataSkip > 1` で、リーダーが `io.Seeker` を実装しており、かつスキップすべきデータが複数バイトある場合にのみシークを試みます。
    *   `pos1, err := sr.Seek(0, os.SEEK_CUR)` で、シークが実際に可能かどうかをテストします。これにより、`os.Stdin` のような「名ばかりの`io.Seeker`」を回避します。
    *   `pos2, err := sr.Seek(dataSkip-1, os.SEEK_CUR)` で、データの終端の1バイト手前までシークします。これにより、`Seek` の遅延エラー報告の問題を回避し、最後の1バイトの読み込みを `io.CopyN` に委ねます。
    *   シーク中にエラーが発生した場合は、それを `tr.err` に設定してすぐに返します。
    *   `seekSkipped` は、実際に `Seek` によってスキップされたバイト数を記録します。
4.  `io.CopyN` による残りのスキップとエラー検出:
    *   `io.CopyN(ioutil.Discard, tr.r, totalSkip-seekSkipped)` を使用して、`Seek` でスキップされなかった残りのバイトを読み飛ばします。`ioutil.Discard` は読み込んだデータを破棄します。
    *   `io.CopyN` は、指定されたバイト数を読み込む前にEOFに達した場合、`io.ErrUnexpectedEOF` を返します。これが、切り詰められたファイルを検出する主要なメカニズムです。
    *   `copySkipped` は、`io.CopyN` によってスキップされたバイト数を記録します。
5.  エラーの正規化:
    *   `if tr.err == io.EOF && seekSkipped+copySkipped < dataSkip` の条件は、`io.CopyN` が `io.EOF` を返したが、実際にスキップされたバイトの合計が `dataSkip` (データ部分の期待されるバイト数) に満たない場合に真となります。これは、データが途中で切り詰められたことを意味するため、`tr.err` を `io.ErrUnexpectedEOF` に上書きして、より正確なエラーを報告します。
6.  最終的に `tr.err` を返します。

この一連の処理により、`tar.Reader` は、どのような種類の `io.Reader` が使われていても、切り詰められたファイルを確実に検出し、適切な `io.ErrUnexpectedEOF` を報告できるようになりました。

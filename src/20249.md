# [インデックス 20249] ファイルの概要

このコミットは、GoランタイムにおけるC言語の型名がGoのコード生成時に正しく保持されるようにするための重要な変更と、C関数へのGoラッパーの削除を目的としています。これにより、Goランタイムのコードベースが簡素化され、CとGo間の型変換の正確性が向上します。

## 元コミット内容

`cmd/cc, runtime: preserve C runtime type names in generated Go`

このコミットは、GoランタイムのCコードで定義された型（`uintptr`や`uint64`など）がGoコードに変換される際に、`uint`や`uint8`といった一般的なGoの型に誤って変換されてしまう問題を修正します。また、C関数をラップしていたGoのラッパー関数を削除し、C関数をGoから直接呼び出せるように変更します。将来的にはこれらのC関数もGoで実装される予定です。

## 変更の背景

Goランタイムの一部はC言語で書かれており、Goコードとの連携には型変換が不可欠です。しかし、これまでのGoコード生成プロセスでは、Cの特定の型がGoの対応する型に正確にマッピングされず、`uintptr`や`uint64`が`uint`に、`bool`が`uint8`に変換されるといった問題がありました。これは、型情報の損失や、意図しない挙動を引き起こす可能性がありました。

また、Goランタイム内には、Cで実装された関数をGoから呼び出すためのラッパー関数が多数存在していました。これらのラッパーは、CとGoの間のインターフェースを抽象化する役割を担っていましたが、コードの複雑性を増し、オーバーヘッドを発生させる可能性がありました。Goランタイムの進化に伴い、C関数を直接Goから呼び出すメカニズムが成熟したため、これらのラッパーを削除し、コードベースを簡素化することが可能になりました。

この変更は、Goランタイムの内部構造をよりクリーンにし、CとGoの間の相互運用性を改善し、将来的なCコードのGoへの移行を容易にすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が必要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステム。ガベージコレクション、スケジューリング、メモリ管理、チャネル通信など、Go言語の主要な機能の多くを実装しています。Goランタイムの一部はパフォーマンスやシステムとの直接的な対話のためにC言語やアセンブリ言語で書かれています。
*   **Cgo**: GoプログラムからC言語のコードを呼び出すためのGoの機能。Cgoは、Cの関数や型をGoのコードで利用できるようにするためのブリッジを提供します。
*   **`cmd/cc`**: Goのツールチェーンの一部で、Cgoによって生成されたCコードをコンパイルするために使用されるCコンパイラです。GoのソースコードからCの定義を抽出し、Goの型定義を生成する役割も担っています。
*   **`godefs.c`**: `cmd/cc`の一部であり、Cの構造体や型定義からGoの対応する型定義を自動生成するCソースファイルです。このファイルは、CとGoの間の型マッピングを定義する中心的な役割を果たします。
*   **`uintptr`**: Goの組み込み型で、ポインタを保持するのに十分な大きさの符号なし整数型です。これは、Cのポインタ型とGoのポインタ型の間で変換を行う際によく使用されます。サイズは実行環境のポインタサイズ（32ビットまたは64ビット）に依存します。
*   **`uint64` / `int64` / `uint32` / `int32`**: Goの固定幅整数型。Cの`long long`や`int`などに対応します。
*   **アトミック操作 (Atomic Operations)**: 複数のゴルーチン（またはスレッド）が同時に共有データにアクセスする際に、データの整合性を保つための不可分な操作。Goの`sync/atomic`パッケージやランタイム内部で利用されます。
    *   **`cas` (Compare-And-Swap)**: 指定されたメモリ位置の値が期待値と一致する場合にのみ、その値を新しい値に更新するアトミック操作。
    *   **`xadd` (Atomic Add)**: 指定されたメモリ位置の値に、指定された値をアトミックに加算し、元の値を返す操作。
    *   **`atomicload` / `atomicstore`**: メモリから値をアトミックに読み込む/書き込む操作。
*   **`nanotime()` / `cputicks()`**: Goランタイム内部で使用される時間計測関数。`nanotime()`はシステム起動からの経過時間をナノ秒単位で返し、`cputicks()`はCPUのティック数を返します。これらはプロファイリングやパフォーマンス測定に利用されます。
*   **`persistentalloc()`**: Goランタイム内部で、ガベージコレクションの対象とならない永続的なメモリを割り当てるための関数。主にランタイムの内部データ構造に使用されます。
*   **`note` / `notetsleepg` / `notewakeup` / `noteclear`**: Goランタイム内部の同期プリミティブ。ゴルーチンをスリープさせたり、ウェイクアップさせたりするために使用されます。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムにおけるCとGoの間の型変換の正確性を高め、同時にコードの重複と複雑性を排除することにあります。

1.  **C型名のGoへの正確なマッピング**:
    *   以前は、`src/cmd/cc/godefs.c`において、Cの`uintptr`や`uint64`といった型がGoの`uint`に、`bool`が`uint8`にといったように、より一般的なGoの型に変換されていました。これは、Cの型が持つ特定のセマンティクス（例：ポインタサイズに依存する`uintptr`）がGo側で失われることを意味しました。
    *   このコミットでは、`godefs.c`の`printtypename`関数が大幅に修正され、Cの型がGoに変換される際に、より適切なGoの型名（またはCの元の型名）が使用されるようになりました。特に、`intgo`や`uintgo`といったGoランタイム内部で定義された型エイリアスが尊重され、それらがGoの`int`や`uint`にマッピングされるようになりました。これにより、Cの型がGoに変換される際の精度が向上し、型情報の損失が防がれます。
    *   `src/pkg/runtime/runtime.h`では、`uintptr`、`intptr`、`intgo`、`uintgo`といった型が、32ビットまたは64ビット環境に応じて`uint32`/`int32`または`uint64`/`int64`に直接マッピングされるように変更されました。これにより、C側での型定義がより明確になり、Go側での型変換の基盤が強化されます。

2.  **Goラッパー関数の削除とC関数の直接呼び出し**:
    *   Goランタイムには、Cで実装された低レベルの関数（アトミック操作、時間計測、メモリ割り当てなど）をGoから呼び出すための、`go`プレフィックスを持つラッパー関数（例: `gocas`, `goatomicload`, `gocputicks`）が多数存在していました。これらのラッパーは、GoとCの間の呼び出し規約の違いを吸収したり、特定のランタイムの状態を管理したりするために使用されていました。
    *   このコミットでは、これらの`go`プレフィックス付きラッパー関数の多くが削除され、GoコードからC関数を直接呼び出すように変更されました。これは、GoランタイムのCgoインターフェースが成熟し、GoからC関数を直接呼び出す際のオーバーヘッドが許容範囲になったこと、およびコードの簡素化が目的です。
    *   例えば、`gocputicks()`は`cputicks()`に、`gocas()`は`cas()`に、`goatomicloadp()`は`atomicloadp()`に置き換えられています。これにより、Goランタイムのコードベースがより直接的になり、メンテナンスが容易になります。
    *   `src/pkg/runtime/stubs.goc`から多くの`go`プレフィックス付き関数の定義が削除され、対応するGoの関数が`src/pkg/runtime/stubs.go`に宣言されています。これは、これらの機能がCgoを介したラッパーではなく、Goランタイムの内部で直接C関数を呼び出すか、あるいはGoで再実装される方向性を示しています。

これらの変更は、Goランタイムの内部実装のクリーンアップと最適化の一環であり、Go言語のパフォーマンスと安定性の向上に貢献します。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は以下のファイルに集中しています。

1.  **`src/cmd/cc/godefs.c`**:
    *   Cの基本型（`TINT`, `TUINT`, `TLONG`, `TULONG`, `TVLONG`, `TUVLONG`, `TFLOAT`, `TDOUBLE`など）をGoの型に変換するロジックが大幅に変更されています。
    *   以前は、Cの型をGoの固定幅型（例: `int32`, `uint32`, `int64`, `uint64`）や、ポインタサイズに依存する`int`/`uint`に直接マッピングしていましたが、この変更により、Cの`typedef`名（`t->tag->name`）を優先的に使用し、`intgo`や`uintgo`といったランタイム内部の型エイリアスをGoの`int`や`uint`に変換するようになりました。これにより、Cの型が持つ意味がGo側でより正確に表現されるようになります。

2.  **`src/pkg/runtime/runtime.h`**:
    *   Cのランタイム型定義が簡素化されました。特に、`int32_x`や`uint32_x`といった型が削除され、`uintptr`, `intptr`, `intgo`, `uintgo`が直接`uint32`/`int32`または`uint64`/`int64`にマッピングされるようになりました。これは、`godefs.c`での型変換ロジックの変更と連携し、CとGoの間の型の一貫性を高めます。

3.  **`src/pkg/runtime/stubs.go` および `src/pkg/runtime/stubs.goc`**:
    *   `stubs.goc`から`goatomicload`, `gocas`, `goxadd`, `gopersistentalloc`, `gocputicks`, `gonanotime`, `gonotetsleepg`, `gonotewakeup`, `gonoteclear`など、`go`プレフィックスを持つ多くのラッパー関数のC実装が削除されました。
    *   `stubs.go`では、これらのラッパー関数に対応するGoの関数宣言（`cas`, `xadd`, `atomicload`, `cputicks`, `nanotime`, `persistentalloc`, `notetsleepg`, `notewakeup`, `noteclear`など）が追加または修正され、`//go:noescape`ディレクティブが付与されています。これは、これらの関数がGoのスタックフレームを生成せずに直接C関数を呼び出すか、またはGoでアセンブリ実装を持つことを示唆しています。

4.  **その他の`src/pkg/runtime/*.go`ファイル**:
    *   `chan.go`, `export_test.go`, `hashmap.go`, `iface.go`, `malloc.go`, `mprof.go`, `print.go`, `proc.go`, `rdebug.go`, `sema.go`, `sigqueue.go`, `slice.go`, `string.go`, `time.go`など、Goランタイムの様々なGoソースファイルで、`go`プレフィックス付きのラッパー関数呼び出しが、対応する非`go`プレフィックス関数（例: `gogetcallerpc` -> `getcallerpc`, `gocputicks` -> `cputicks`, `gocas` -> `cas`）に置き換えられています。
    *   また、`uint`型が`uintptr`型に置き換えられている箇所も多く見られます。これは、ポインタサイズに依存する値の受け渡しにおいて、より正確な型を使用するための変更です。
    *   `t.indirectkey != 0`のような数値比較が`t.indirectkey`のようなブール値の直接比較に簡素化されています。

これらの変更は、Goランタイムの内部APIの統一と簡素化、そしてCとGoの間の型安全性の向上に大きく貢献しています。

## 元コミット内容

`cmd/cc, runtime: preserve C runtime type names in generated Go`

このコミットは、GoランタイムのCコードで定義された型（`uintptr`や`uint64`など）がGoコードに変換される際に、`uint`や`uint8`といった一般的なGoの型に誤って変換されてしまう問題を修正します。また、C関数をラップしていたGoのラッパー関数を削除し、C関数をGoから直接呼び出せるように変更します。将来的にはこれらのC関数もGoで実装される予定です。

## 変更の背景

Goランタイムの一部はC言語で書かれており、Goコードとの連携には型変換が不可欠です。しかし、これまでのGoコード生成プロセスでは、Cの特定の型がGoの対応する型に正確にマッピングされず、`uintptr`や`uint64`が`uint`に、`bool`が`uint8`にといったように、より一般的なGoの型に変換されるといった問題がありました。これは、型情報の損失や、意図しない挙動を引き起こす可能性がありました。

また、Goランタイム内には、Cで実装された関数をGoから呼び出すためのラッパー関数が多数存在していました。これらのラッパーは、CとGoの間のインターフェースを抽象化する役割を担っていましたが、コードの複雑性を増し、オーバーヘッドを発生させる可能性がありました。Goランタイムの進化に伴い、C関数を直接Goから呼び出すメカニズムが成熟したため、これらのラッパーを削除し、コードベースを簡素化することが可能になりました。

この変更は、Goランタイムの内部構造をよりクリーンにし、CとGoの間の相互運用性を改善し、将来的なCコードのGoへの移行を容易にすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が必要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステム。ガベージコレクション、スケジューリング、メモリ管理、チャネル通信など、Go言語の主要な機能の多くを実装しています。Goランタイムの一部はパフォーマンスやシステムとの直接的な対話のためにC言語やアセンブリ言語で書かれています。
*   **Cgo**: GoプログラムからC言語のコードを呼び出すためのGoの機能。Cgoは、Cの関数や型をGoのコードで利用できるようにするためのブリッジを提供します。
*   **`cmd/cc`**: Goのツールチェーンの一部で、Cgoによって生成されたCコードをコンパイルするために使用されるCコンパイラです。GoのソースコードからCの定義を抽出し、Goの型定義を生成する役割も担っています。
*   **`godefs.c`**: `cmd/cc`の一部であり、Cの構造体や型定義からGoの対応する型定義を自動生成するCソースファイルです。このファイルは、CとGoの間の型マッピングを定義する中心的な役割を果たします。
*   **`uintptr`**: Goの組み込み型で、ポインタを保持するのに十分な大きさの符号なし整数型です。これは、Cのポインタ型とGoのポインタ型の間で変換を行う際によく使用されます。サイズは実行環境のポインタサイズ（32ビットまたは64ビット）に依存します。
*   **`uint64` / `int64` / `uint32` / `int32`**: Goの固定幅整数型。Cの`long long`や`int`などに対応します。
*   **アトミック操作 (Atomic Operations)**: 複数のゴルーチン（またはスレッド）が同時に共有データにアクセスする際に、データの整合性を保つための不可分な操作。Goの`sync/atomic`パッケージやランタイム内部で利用されます。
    *   **`cas` (Compare-And-Swap)**: 指定されたメモリ位置の値が期待値と一致する場合にのみ、その値を新しい値に更新するアトミック操作。
    *   **`xadd` (Atomic Add)**: 指定されたメモリ位置の値に、指定された値をアトミックに加算し、元の値を返す操作。
    *   **`atomicload` / `atomicstore`**: メモリから値をアトミックに読み込む/書き込む操作。
*   **`nanotime()` / `cputicks()`**: Goランタイム内部で使用される時間計測関数。`nanotime()`はシステム起動からの経過時間をナノ秒単位で返し、`cputicks()`はCPUのティック数を返します。これらはプロファイリングやパフォーマンス測定に利用されます。
*   **`persistentalloc()`**: Goランタイム内部で、ガベージコレクションの対象とならない永続的なメモリを割り当てるための関数。主にランタイムの内部データ構造に使用されます。
*   **`note` / `notetsleepg` / `notewakeup` / `noteclear`**: Goランタイム内部の同期プリミティブ。ゴルーチンをスリープさせたり、ウェイクアップさせたりするために使用されます。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムにおけるCとGoの間の型変換の正確性を高め、同時にコードの重複と複雑性を排除することにあります。

1.  **C型名のGoへの正確なマッピング**:
    *   以前は、`src/cmd/cc/godefs.c`において、Cの`uintptr`や`uint64`といった型がGoの`uint`に、`bool`が`uint8`にといったように、より一般的なGoの型に変換されていました。これは、Cの型が持つ特定のセマンティクス（例：ポインタサイズに依存する`uintptr`）がGo側で失われることを意味しました。
    *   このコミットでは、`godefs.c`の`printtypename`関数が大幅に修正され、Cの型がGoに変換される際に、より適切なGoの型名（またはCの元の型名）が使用されるようになりました。特に、`intgo`や`uintgo`といったGoランタイム内部で定義された型エイリアスが尊重され、それらがGoの`int`や`uint`にマッピングされるようになりました。これにより、Cの型がGoに変換される際の精度が向上し、型情報の損失が防がれます。
    *   `src/pkg/runtime/runtime.h`では、`uintptr`、`intptr`、`intgo`、`uintgo`といった型が、32ビットまたは64ビット環境に応じて`uint32`/`int32`または`uint64`/`int64`に直接マッピングされるように変更されました。これにより、C側での型定義がより明確になり、Go側での型変換の基盤が強化されます。

2.  **Goラッパー関数の削除とC関数の直接呼び出し**:
    *   Goランタイムには、Cで実装された低レベルの関数（アトミック操作、時間計測、メモリ割り当てなど）をGoから呼び出すための、`go`プレフィックスを持つラッパー関数（例: `gocas`, `goatomicload`, `gocputicks`）が多数存在していました。これらのラッパーは、GoとCの間の呼び出し規約の違いを吸収したり、特定のランタイムの状態を管理したりするために使用されていました。
    *   このコミットでは、これらの`go`プレフィックス付きラッパー関数の多くが削除され、GoコードからC関数を直接呼び出すように変更されました。これは、GoランタイムのCgoインターフェースが成熟し、GoからC関数を直接呼び出す際のオーバーヘッドが許容範囲になったこと、およびコードの簡素化が目的です。
    *   例えば、`gocputicks()`は`cputicks()`に、`gocas()`は`cas()`に、`goatomicloadp()`は`atomicloadp()`に置き換えられています。これにより、Goランタイムのコードベースがより直接的になり、メンテナンスが容易になります。
    *   `src/pkg/runtime/stubs.goc`から多くの`go`プレフィックス付き関数の定義が削除され、対応するGoの関数が`src/pkg/runtime/stubs.go`に宣言されています。これは、これらの機能がCgoを介したラッパーではなく、Goランタイムの内部で直接C関数を呼び出すか、あるいはGoでアセンブリ実装を持つことを示唆しています。

これらの変更は、Goランタイムの内部実装のクリーンアップと最適化の一環であり、Go言語のパフォーマンスと安定性の向上に貢献します。

この変更のポイントは、Cのプリミティブ型（`TINT`, `TUINT`など）に対する直接的なGo型へのマッピング（例: `TINT`を`int32`に）を削除し、代わりに`t->tag`（Cの`typedef`名）が存在するかどうかを確認する新しいロジックを導入したことです。

*   `t->tag != nil`の場合、つまりCの型が`typedef`によってエイリアスされている場合、その`typedef`名（`t->tag->name`）をGoの型名として使用しようとします。
*   特に、`intgo`という`typedef`名であればGoの`int`に、`uintgo`であればGoの`uint`に変換します。これらはGoランタイム内部で定義された特別な型エイリアスであり、Goのネイティブな整数型にマッピングすることで、CとGoの間の型の一貫性を保ちます。
*   それ以外の`typedef`名であれば、その名前をそのままGoの型名として出力します。
*   `t->tag == nil`の場合、つまり`typedef`されていないCのプリミティブ型の場合、`C.%T`という形式で出力されます。これは、Goの`C`パッケージを介してCの型を参照する一般的な方法です。

この変更により、GoランタイムのCコードで定義されたカスタム型やエイリアスが、Goコード生成時にその意図をより正確に反映できるようになり、型情報の損失を防ぎます。

この変更は、GoランタイムがCgoを介した間接的な呼び出しから、より直接的なC関数呼び出し、またはGoで実装されたアセンブリルーチンへの移行を進めていることを明確に示しています。これにより、Goランタイムのパフォーマンスが向上し、コードの複雑性が軽減されます。

### その他のGoファイルの変更

Goランタイムの他の多くのGoファイルでは、`go`プレフィックス付きの関数呼び出しが、対応する非`go`プレフィックス関数に置き換えられています。例えば、`chan.go`では`gocputicks()`が`cputicks()`に、`gogetcallerpc()`が`getcallerpc()`に、`gocas()`が`cas()`に置き換えられています。

また、`uint`型が`uintptr`型に置き換えられている箇所も多く見られます。これは、ポインタサイズに依存する値（例えば、メモリのアドレスやサイズ）を扱う際に、より正確な`uintptr`型を使用することで、コードの堅牢性と移植性を高めるための変更です。

これらの変更は、Goランタイムの内部で一貫したAPIを使用し、CとGoの間のインターフェースを簡素化するための広範な取り組みの一部です。

# [インデックス 21009] ファイルの概要

このコミットは、Goランタイムにおけるスタックトレース生成（`gentraceback`）の堅牢性を向上させるための変更です。特に、ユーザーゴルーチンのスタック上で自身のスタックトレースを生成する際に発生する可能性のある、スタックの成長によるポインタの無効化という問題に対処しています。この変更により、`gentraceback`は常に`g0`スタック上で実行されるようになり、スタックの動的なサイズ変更に起因する潜在的なデータ破損を防ぎます。

## 元コミット内容

```
runtime: avoid gentraceback of self on user goroutine stack

Gentraceback may grow the stack.
One of the gentraceback wrappers may grow the stack.
One of the gentraceback callback calls may grow the stack.
Various stack pointers are stored in various stack locations
as type uintptr during the execution of these calls.
If the stack does grow, these stack pointers will not be
updated and will start trying to decode stack memory that
is no longer valid.

It may be possible to change the type of the stack pointer
variables to be unsafe.Pointer, but that's pretty subtle and
may still have problems, even if we catch every last one.
An easier, more obviously correct fix is to require that
gentraceback of the currently running goroutine must run
on the g0 stack, instead of on the goroutine's own stack.

Not doing this causes faults when you set
        StackFromSystem = 1
        StackFaultOnFree = 1

The new check in gentraceback will catch future lapses.

The more general problem is calling getcallersp but then
calling a function that might relocate the stack, which would
invalidate the result of getcallersp. Add note to stubs.go
declaration of getcallersp explaining the problem, and
check all existing calls to getcallersp. Most needed fixes.

This affects Callers, Stack, and nearly all the runtime
profiling routines. It does not affect stack copying directly
nor garbage collection.

LGTM=khr
R=khr, bradfitz
CC=golang-codereviews, r
https://golang.org/cl/167060043
```

## 変更の背景

Goランタイムでは、ゴルーチンのスタックは動的に伸縮します。これは、プログラムが必要とするメモリ量に応じてスタックサイズを効率的に管理するための重要な機能です。しかし、この動的なスタックの性質が、スタックトレースの生成（`gentraceback`）のような特定のランタイム操作において問題を引き起こす可能性がありました。

具体的には、`gentraceback`が実行中にスタックを成長させる必要がある場合、または`gentraceback`のラッパー関数やコールバック関数がスタックを成長させる必要がある場合に問題が発生しました。スタックが成長すると、そのゴルーチンに割り当てられたメモリ領域が移動（再配置）します。このとき、`uintptr`型でスタックポインタを保持している変数が、新しいスタックアドレスに更新されないままだと、無効なメモリ領域を参照しようとしてしまい、クラッシュや不正なスタックトレースの原因となっていました。

この問題は、特に`StackFromSystem = 1`（システムスタックを使用）や`StackFaultOnFree = 1`（解放時のスタックフォルトチェックを有効化）といったデバッグフラグが設定されている環境で顕著に現れました。

このコミットは、このようなスタックの再配置によるポインタの無効化という根本的な問題に対処し、ランタイムの安定性とスタックトレースの正確性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **ゴルーチン (Goroutine)**: Goにおける軽量な実行スレッドです。OSのスレッドとは異なり、Goランタイムが管理し、非常に多数を同時に実行できます。各ゴルーチンは独自のスタックを持っています。

2.  **スタック (Stack)**: 関数呼び出しの際に、ローカル変数、関数引数、戻りアドレスなどが格納されるメモリ領域です。Goのゴルーチンスタックは、必要に応じて動的にサイズが変更されます（スタックの成長/縮小）。スタックが成長する必要がある場合、ランタイムはより大きなメモリブロックを割り当て、既存のスタックの内容を新しい場所にコピーし、関連するポインタを更新します。これを**スタックの再配置 (Stack Relocation)** と呼びます。

3.  **`gentraceback`**: Goランタイムの内部関数で、スタックトレースを生成する役割を担います。プログラムがパニックを起こした際や、プロファイリングツールがスタックダンプを要求した際に、このメカニズムがゴルーチンのコールスタックを辿り、関数呼び出しのシーケンスを特定します。

4.  **`g0`スタック (g0 stack)**: Goランタイムにおいて、各OSスレッド（M、または「マシン」）は、ユーザーレベルのゴルーチンが使用するスタックとは異なる、専用のスタックである`g0`スタックを持っています。`g0`スタックは、ゴルーチンのスケジューリング、ガベージコレクション、システムコール処理、ゴルーチンスタックの成長と縮小の管理など、Goランタイムの重要な内部操作のために使用されます。`g0`スタックは、ユーザーゴルーチンのスタックとは異なり、通常は固定サイズであり、再配置されることはありません。

5.  **`getcallersp`**: この関数は、呼び出し元のスタックポインタ（SP）を取得するために使用されるランタイム内部のメカニズムです。スタックトレースの生成やスタックフレームの管理において、呼び出し元のスタックポインタを知ることは非常に重要です。しかし、`getcallersp`が返したスタックポインタは、その後にスタックが再配置されるような関数呼び出しが行われると、無効になる可能性があります。

6.  **`uintptr` vs `unsafe.Pointer`**:
    *   `uintptr`: 任意のポインタ値を保持できる整数型です。ポインタ演算が可能ですが、ガベージコレクタは`uintptr`が指すメモリを追跡しません。そのため、`uintptr`にポインタを格納し、そのポインタが指すメモリが移動（再配置）された場合、`uintptr`の値は更新されず、無効なアドレスを指すことになります。
    *   `unsafe.Pointer`: 任意の型のポインタを保持できる特殊なポインタ型です。`unsafe.Pointer`は、Goの型システムをバイパスして、異なる型のポインタ間で変換を行うことを可能にします。`unsafe.Pointer`はガベージコレクタによって追跡されるため、指しているメモリが移動した場合でも、ポインタの値は自動的に更新されます。

## 技術的詳細

このコミットの核心は、`gentraceback`が現在実行中のゴルーチン（ユーザーゴルーチン）のスタック上で実行されると、スタックの成長によって`uintptr`型のスタックポインタが不正になる可能性があるという問題への対処です。

元の実装では、`gentraceback`やその関連関数（`GoroutineProfile`, `Stack`, `tracealloc`, `tracefree`など）が、`getcallersp`で取得したスタックポインタを`uintptr`として保持し、ユーザーゴルーチンのスタック上で処理を行っていました。しかし、これらの処理中にスタックが成長すると、`uintptr`で保持されたスタックポインタは古いアドレスを指したままになり、結果として不正なメモリアクセスやクラッシュを引き起こしていました。

この問題に対する解決策として、コミットは以下の原則を導入しました。

1.  **`gentraceback`の`g0`スタック上での実行の強制**:
    現在実行中のユーザーゴルーチンのスタックトレースを生成する場合、`gentraceback`は必ず`g0`スタック上で実行されるように変更されました。これは、`onM`関数（`m`、つまりOSスレッド上で実行されることを保証する関数）を使用して実現されます。`g0`スタックは再配置されないため、スタックポインタの無効化の問題が発生しません。

2.  **`getcallersp`の利用に関する制約の明確化**:
    `src/runtime/stubs.go`の`getcallersp`の宣言に、その利用に関する重要な注意書きが追加されました。`getcallersp`の結果は、スタックが成長または縮小するために再配置される可能性のある関数が呼び出されると、無効になる可能性があることが明記されました。この結果はすぐに使用されるべきであり、`nosplit`関数（スタックを成長させない関数）にのみ渡されるべきであるというルールが強調されました。

3.  **既存の`getcallersp`呼び出しの修正**:
    `Callers`、`Stack`、およびほとんどのランタイムプロファイリングルーチンを含む、既存の`getcallersp`の呼び出し箇所が修正されました。これらの関数は、`getcallersp`で取得したスタックポインタを`onM`ブロック内で使用するか、`g0`スタックに切り替えて処理を行うように変更されました。これにより、スタックの再配置による影響を受けなくなりました。

この変更は、`unsafe.Pointer`を使用してスタックポインタを追跡するという代替案よりも、「より簡単で、より明らかに正しい」解決策として選択されました。`unsafe.Pointer`を使用する方法は、すべてのポインタを正確に追跡する必要があり、非常に複雑で潜在的な問題を残す可能性があったためです。

## コアとなるコードの変更箇所

このコミットで変更された主要なファイルと、その中での重要な変更箇所は以下の通りです。

1.  **`src/runtime/mprof.go`**:
    *   `GoroutineProfile`関数と`Stack`関数において、`getcallersp`と`getcallerpc`の呼び出しが`onM`ブロック内に移動されました。これにより、スタックトレースの生成が`g0`スタック上で行われるようになります。
    *   `tracealloc`と`tracefree`関数でも同様に、`traceback`の呼び出しが`onM`ブロック内にラップされました。

2.  **`src/runtime/stubs.go`**:
    *   `getcallerpc`と`getcallersp`関数のコメントが大幅に加筆されました。特に、`getcallersp`の結果がスタックの再配置によって無効になる可能性があり、その結果はすぐに使用され、`nosplit`関数にのみ渡されるべきであるという重要な警告が追加されました。

3.  **`src/runtime/traceback.go`**:
    *   `gentraceback`関数に新しいチェックが追加されました。もし`gentraceback`が現在実行中のゴルーチン（`g == gp && g == g.m.curg`）のスタック上で呼び出された場合、`gothrow("gentraceback cannot trace user goroutine on its own stack")`によってパニックを発生させるようになりました。これは、`gentraceback`が`g0`スタック上で実行されることを強制するためのガードです。
    *   `callers`関数も`onM`ブロック内で`gentraceback`を呼び出すように変更され、`g0`スタックへの切り替えを保証しています。

## コアとなるコードの解説

### `src/runtime/mprof.go` の変更

```go
// Before:
// func GoroutineProfile(p []StackRecord) (n int, ok bool) {
//  sp := getcallersp(unsafe.Pointer(&p))
//  pc := getcallerpc(unsafe.Pointer(&p))
//  // ...
//  saveg(pc, sp, gp, &r[0])
// }

// After:
func GoroutineProfile(p []StackRecord) (n int, ok bool) {
    // ...
    if n <= len(p) {
        ok = true
        r := p
        sp := getcallersp(unsafe.Pointer(&p)) // getcallerspは呼び出し元のスタックポインタを取得
        pc := getcallerpc(unsafe.Pointer(&p)) // getcallerpcは呼び出し元のプログラムカウンタを取得
        onM(func() { // onMブロック内で実行することでg0スタックに切り替える
            saveg(pc, sp, gp, &r[0])
        })
    }
    // ...
}

// Stack関数も同様の変更
// Before:
// func Stack(buf []byte, all bool) int {
//  sp := getcallersp(unsafe.Pointer(&buf))
//  pc := getcallerpc(unsafe.Pointer(&buf))
//  // ...
//  traceback(pc, sp, 0, gp)
// }

// After:
func Stack(buf []byte, all bool) int {
    // ...
    if len(buf) > 0 {
        sp := getcallersp(unsafe.Pointer(&buf))
        pc := getcallerpc(unsafe.Pointer(&buf))
        onM(func() { // g0スタック上で実行
            g0 := getg() // 現在のg0ゴルーチンを取得
            g0.writebuf = buf[0:0:len(buf)] // g0のwritebufを使用
            goroutineheader(gp)
            traceback(pc, sp, 0, gp)
            if all {
                tracebackothers(gp)
            }
            n = len(g0.writebuf)
            g0.writebuf = nil
        })
    }
    // ...
}
```
これらの変更は、`getcallersp`と`getcallerpc`で取得したスタックポインタとプログラムカウンタを、`onM`関数でラップされたクロージャ内で使用するようにしています。`onM`は、現在のOSスレッド（M）が`g0`スタック上で実行されていることを保証するため、スタックトレースの生成中にスタックが再配置されるリスクを排除します。

### `src/runtime/stubs.go` の変更

`getcallerpc`と`getcallersp`のコメントに、スタックの再配置に関する重要な警告が追加されました。これは、これらの関数が返す値が、スタックが移動する可能性のある関数呼び出しによって無効になる可能性があることを開発者に明確に伝えるものです。

```go
// getcallerpc returns the program counter (PC) of its caller's caller.
// getcallersp returns the stack pointer (SP) of its caller's caller.
// For both, the argp must be a pointer to the caller's first function argument.
// The implementation may or may not use argp, depending on
// the architecture.
//
// ... (Example usage) ...
//
// The result of getcallersp is correct at the time of the return,
// but it may be invalidated by any subsequent call to a function
// that might relocate the stack in order to grow or shrink it.
// A general rule is that the result of getcallersp should be used
// immediately and can only be passed to nosplit functions.
```
このコメントは、`getcallersp`の戻り値の揮発性を強調し、その使用方法に関する厳格なガイドラインを提供しています。

### `src/runtime/traceback.go` の変更

```go
func gentraceback(pc0 uintptr, sp0 uintptr, lr0 uintptr, gp *g, skip int, pcbuf *uintptr, max int, printStack func(buf []byte), goexit func(g *g), flags uint) int {
    // ...
    g := getg()
    if g == gp && g == g.m.curg {
        // The starting sp has been passed in as a uintptr, and the caller may
        // have other uintptr-typed stack references as well.
        // If during one of the calls that got us here or during one of the
        // callbacks below the stack must be grown, all these uintptr references
        // to the stack will not be updated, and gentraceback will continue
        // to inspect the old stack memory, which may no longer be valid.
        // Even if all the variables were updated correctly, it is not clear that
        // we want to expose a traceback that begins on one stack and ends
        // on another stack. That could confuse callers quite a bit.
        // Instead, we require that gentraceback and any other function that
        // accepts an sp for the current goroutine (typically obtained by
        // calling getcallersp) must not run on that goroutine's stack but
        // instead on the g0 stack.
        gothrow("gentraceback cannot trace user goroutine on its own stack")
    }
    // ...
}

func callers(skip int, pcbuf *uintptr, m int) int {
    sp := getcallersp(unsafe.Pointer(&skip))
    pc := uintptr(getcallerpc(unsafe.Pointer(&skip)))
    var n int
    onM(func() { // g0スタック上で実行
        n = gentraceback(pc, sp, 0, getg(), skip, pcbuf, m, nil, nil, 0)
    })
    return n
}
```
`gentraceback`内の新しいチェックは、ユーザーゴルーチンが自身のスタック上で`gentraceback`を呼び出そうとした場合にパニックを発生させます。これは、`gentraceback`が`g0`スタック上で実行されるべきであるという新しい要件を強制するためのものです。
`callers`関数も`onM`を使用して`gentraceback`を呼び出すように変更され、この要件に準拠しています。

これらの変更により、Goランタイムはスタックの動的な性質に起因する潜在的な問題を回避し、より堅牢で正確なスタックトレース生成メカニズムを提供できるようになりました。

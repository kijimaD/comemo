## 元コミット内容

GoコンパイラのSSAバックエンドにおいて、デッドコード削除の過程でPhi関数を排除する。

以前のコミット (19710: 冗長な制御の削除、12960: 境界チェックとnil伝播) の違いを調査する中で、19710の最適化の一部が、Phi関数が原因でデッドコード削除の機会を逃していることに起因していることが判明した。例えば `runtime.stackcacherelease` 関数でこの現象が見られた。19710は12960よりも後の段階で実行されるため、境界チェックを削除する機会が多くなる。

この変更により、`pkg/tool/linux_amd64/*` (コンパイルを除く) のサイズが約25KB削減される。

## 変更の背景

Goコンパイラは、プログラムの最適化のためにSSA (Static Single Assignment) 形式の中間表現を使用します。SSA形式では、複数の制御フローパスが合流する際に「Phi関数」が導入され、変数の値を決定します。しかし、プログラムの一部がデッドコード（到達不能なコード）として識別された場合でも、そのデッドコード内のPhi関数がまだ有効な値への参照を持っていると、そのPhi関数自体や、Phi関数が参照する値がデッドコードとして削除されないことがあります。

このコミットの著者は、以前の最適化コミット (19710と12960) の効果を分析する中で、Phi関数がデッドコード削除の機会を阻害しているケースを発見しました。特に、`runtime.stackcacherelease` のような関数で、Phi関数が原因でデッドコードが残存し、結果として生成されるバイナリのサイズが増加していることが確認されました。この変更は、このようなPhi関数を積極的に排除することで、デッドコード削除をより効果的に行い、最終的なバイナリサイズを削減することを目的としています。約25KBのサイズ削減は、コンパイラの最適化としては無視できない成果です。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラがプログラムを最適化するために使用する中間表現の一種です。この形式では、各変数がプログラム内で一度だけ代入されるという特性を持ちます。これにより、データの流れが明確になり、デッドコード削除、定数伝播、共通部分式削除などの最適化が容易になります。

### 2. Phi関数 (Φ関数)

SSA形式の重要な要素がPhi関数です。プログラムの制御フローが分岐し、その後再び合流するような場合（例: `if-else`文の終わり、ループの開始）、同じ変数に対して複数の異なるパスから値が到達する可能性があります。Phi関数は、どのパスから来たかによって変数の値を選択する役割を果たします。例えば、`x = Φ(x_from_block_A, x_from_block_B)` は、「ブロックAから来た場合は `x_from_block_A` の値を、ブロックBから来た場合は `x_from_block_B` の値を `x` に代入する」という意味になります。

### 3. デッドコード削除 (Dead Code Elimination, DCE)

デッドコード削除は、プログラムの実行結果に影響を与えないコード（デッドコード）を特定し、削除するコンパイラ最適化の一種です。これにより、生成されるバイナリのサイズが小さくなり、実行速度が向上する可能性があります。Phi関数がデッドコードを参照している場合、そのPhi関数自体がデッドコード削除の対象とならないことがあり、結果としてデッドコードが残存する原因となります。

### 4. GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木 (AST) に変換した後、SSA形式の中間表現に変換し、様々な最適化を適用します。`cmd/compile/internal/ssa` パッケージは、このSSA形式の生成と最適化を担当するGoコンパイラのバックエンド部分です。

### 5. 制御フローグラフ (Control Flow Graph, CFG) とドミネータグラフ (Dominator Graph)

*   **制御フローグラフ (CFG)**: プログラムの実行可能なすべてのパスを表現するグラフです。ノードは基本ブロック（分岐や合流を含まない一連の命令）を表し、エッジは制御の流れを表します。
*   **ドミネータグラフ**: CFGから派生するグラフで、あるブロックAがブロックBを「ドミネートする」とは、プログラムのエントリポイントからブロックBへのすべてのパスがブロックAを通過することを意味します。ドミネータグラフは、ループ検出や到達可能性分析など、多くの最適化に利用されます。Phi関数をCopyに置き換える際のコメントで言及されている「ドミネータグラフのサイクル」は、到達不能なループを示唆します。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/compile/internal/ssa/deadcode.go` の `removePred` 関数と、`src/cmd/compile/internal/ssa/phielim.go` の `phielimValue` 関数にあります。

### `deadcode.go` の変更

`removePred` 関数は、あるブロックから到達不能になった先行ブロックを削除する際に呼び出されます。この関数内で、Phi関数 (`v`) の引数が更新されます。

変更前は、Phi関数の引数が1つだけになった場合 (`n == 1`) に、そのPhi関数を `OpCopy` (コピー操作) に変換していました。この変換には、Phi関数とCopy操作のセマンティクスの違い（Phiは先行ブロックからの値、Copyは現在の値）による潜在的な問題がありましたが、デッドコード削除の文脈では安全であるという詳細なコメントが付されていました。

変更後は、`if n == 1` の条件が削除され、代わりに `phielimValue(v)` が無条件に呼び出されるようになりました。これは、Phi関数の引数が1つになった場合だけでなく、より一般的なケースでPhi関数を排除するロジックが `phielimValue` 関数に集約されたことを意味します。これにより、`removePred` はPhi関数の引数を減らすことに専念し、Phi関数の具体的な排除ロジックは `phielimValue` に委譲されます。

### `phielim.go` の変更

`phielimValue` 関数は、Phi関数を排除するための主要なロジックを含んでいます。このコミットでは、`phielimValue` 関数内のPhi関数の引数を走査するループに新しい条件が追加されました。

```go
if b := v.Block.Preds[i]; b.Kind == BlockFirst && b.Succs[1] == v.Block {
    // This branch is never taken so we can just eliminate it.
    continue
}
```

この新しい条件は、Phi関数の特定の引数 `x` が、実際には到達不能な（または決して実行されない）制御フローパスから来ているかどうかをチェックします。

*   `b := v.Block.Preds[i]`：Phi関数 `v` が存在するブロック (`v.Block`) の `i` 番目の先行ブロック `b` を取得します。Phi関数の `i` 番目の引数 `x` は、この先行ブロック `b` からの値に対応します。
*   `b.Kind == BlockFirst`：先行ブロック `b` の種類が `BlockFirst` であることをチェックします。`BlockFirst` は、GoコンパイラのSSAバックエンドにおける特定の種類のブロックを指し、通常はプログラムのエントリポイントや、特定の条件分岐の開始点など、特殊な意味を持つブロックです。
*   `b.Succs[1] == v.Block`：先行ブロック `b` の2番目の後続ブロック (`Succs[1]`) が、Phi関数 `v` が存在するブロック (`v.Block`) と一致するかをチェックします。これは、`BlockFirst` のような特殊なブロックが、特定の条件分岐の結果として `v.Block` に到達するが、その分岐が実際には常に別のパスを取る（つまり、`v.Block` へのパスが到達不能である）ようなシナリオを検出している可能性があります。

この条件が真である場合、`continue` ステートメントによって、現在のPhi関数の引数 `x` はPhi関数の有効な引数として考慮されなくなります。これにより、Phi関数が持つべき有効な引数の数が減少し、最終的にPhi関数が単一の引数しか持たない、あるいは全く引数を持たない状態になり、`OpCopy` に変換されたり、完全に削除されたりする可能性が高まります。

この変更は、デッドコード削除のパスにおいて、より積極的に到達不能なパスからのPhi関数の引数を無視することで、Phi関数自体の排除を促進し、結果としてデッドコード削除の機会を増やします。これにより、コンパイルされたバイナリから不要なコードがさらに削減され、約25KBのサイズ削減という具体的な効果がもたらされました。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/deadcode.go` の変更点

`removePred` 関数は、デッドコード削除の過程で、あるブロックへの先行パスが削除されたときに呼び出されます。この関数は、削除された先行ブロックに対応するPhi関数の引数を削除し、Phi関数の引数リストを更新します。

*   **削除されたコード:**
    ```go
    		if n == 1 {
    			v.Op = OpCopy
    			// ... (長いコメント) ...
    		}
    ```
    この `if n == 1` ブロックは、Phi関数の引数が1つだけになった場合に、そのPhi関数を `OpCopy` (コピー命令) に変換するロジックでした。このロジックは、Phi関数とCopy命令のセマンティクスの違いによる潜在的な問題を回避するために、デッドコードループでのみ安全であるという詳細なコメントが付されていました。

*   **追加されたコード:**
    ```go
    		phielimValue(v)
    ```
    `if n == 1` ブロックが削除され、代わりに `phielimValue(v)` が無条件に呼び出されるようになりました。これは、Phi関数の引数が1つになった場合の特殊な処理を `removePred` から削除し、Phi関数の排除に関するより一般的なロジックを `phielimValue` 関数に一元化したことを意味します。これにより、`removePred` はPhi関数の引数を減らすことに集中し、Phi関数の最終的な変換や削除は `phielimValue` に任せるという役割分担が明確になりました。既存の長いコメントは `phielimValue(v)` の呼び出しの直後に移動され、PhiからCopyへの変換に関する注意点が引き続き適用されることを示しています。

### `src/cmd/compile/internal/ssa/phielim.go` の変更点

`phielimValue` 関数は、Phi関数 `v` を分析し、可能であればそれを排除（例えば `OpCopy` に変換）する役割を担います。

*   **追加されたコード:**
    ```go
    	for i, x := range v.Args {
    		if b := v.Block.Preds[i]; b.Kind == BlockFirst && b.Succs[1] == v.Block {
    			// This branch is never taken so we can just eliminate it.
    			continue
    		}
    		if x == v {
    			continue
    		}
    		// ...
    	}
    ```
    この変更は、Phi関数 `v` の引数 `x` を走査するループ内で行われます。
    1.  `b := v.Block.Preds[i]`：現在の引数 `x` に対応する先行ブロック `b` を取得します。Phi関数の `i` 番目の引数は、`v.Block` の `i` 番目の先行ブロックから到達する値です。
    2.  `b.Kind == BlockFirst`：先行ブロック `b` が `BlockFirst` 型であるかをチェックします。`BlockFirst` は、GoコンパイラのSSA表現における特定の種類のブロックで、通常はプログラムのエントリポイントや、特定の条件分岐の開始点など、特殊な意味を持つブロックです。
    3.  `b.Succs[1] == v.Block`：先行ブロック `b` の後続ブロックのリスト (`b.Succs`) の2番目の要素 (`Succs[1]`) が、Phi関数 `v` が存在するブロック (`v.Block`) と一致するかをチェックします。この条件は、`BlockFirst` 型のブロックが、特定の条件分岐の結果として `v.Block` に到達するが、その分岐が実際には常に別のパスを取る（つまり、`v.Block` へのパスが到達不能である）ような特殊なシナリオを検出するために使用されます。

    この `if` 文の条件がすべて真である場合、それは「この分岐は決して実行されない（This branch is never taken）」ことを意味します。したがって、`continue` ステートメントが実行され、現在の引数 `x` はPhi関数の有効な引数として考慮されなくなります。これにより、Phi関数が持つべき有効な引数の数が減少し、最終的にPhi関数が単一の引数しか持たない、あるいは全く引数を持たない状態になり、`OpCopy` に変換されたり、完全に削除されたりする可能性が高まります。

この一連の変更により、Goコンパイラはデッドコード削除のフェーズで、より多くのPhi関数を排除できるようになり、結果として生成されるバイナリのサイズが削減されます。

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおける文字列スライスの型に関するバグを修正するものです。具体的には、文字列スライスのインデックス計算において、インデックスの型が適切に拡張されず、結果として不正なSSA値が生成される可能性があった問題を解決します。この修正により、Goコンパイラが文字列スライス操作をより正確にSSA形式に変換できるようになり、コンパイルされたコードの堅牢性が向上します。

## 変更の背景

Goコンパイラは、コードをSSA形式に変換する際に、様々な最適化を適用します。文字列スライス操作もこのSSA変換の対象となります。Go言語では、文字列はバイトの読み取り専用スライスとして扱われ、`s[low:high]` のようなスライス操作が可能です。この操作では、`low` と `high` のインデックスが文字列の長さの範囲内にあることを保証する必要があります。

以前のGoコンパイラのSSAバックエンドでは、文字列スライスのインデックス（`low` と `high`）をSSA値に変換する際に、これらのインデックスの型が常に適切なサイズ（例えば、ポインタサイズに合わせた `int64`）に「拡張」されるとは限りませんでした。特に、インデックスが小さい整数型（例: `int8`, `int16`, `int32`）で表現されている場合、SSA形式に変換された後もその小さい型が維持されることがありました。

しかし、Goのランタイムやアセンブリレベルでのスライス操作は、通常、ポインタサイズに合わせたインデックス（64ビットシステムでは `int64`）を期待します。インデックスの型が適切に拡張されていないと、以下のような問題が発生する可能性がありました。

1.  **不正なメモリアクセス**: 小さい型のインデックスが負の値になった場合、または非常に大きな値になった場合（オーバーフローなど）、期待されるメモリ範囲外へのアクセスを引き起こす可能性があります。
2.  **最適化の失敗**: コンパイラがインデックスの範囲チェックやその他の最適化を行う際に、型の不一致が原因で正確な解析ができず、非効率なコードが生成される可能性があります。
3.  **ランタイムパニック**: 最悪の場合、不正なインデックスが原因でランタイムパニック（例: `index out of range`）が発生する可能性があります。

このコミットは、これらの問題を解決するために、文字列スライスのインデックスをSSA形式に変換する際に、常に適切なサイズに型を拡張するメカニズムを導入しました。

## 前提知識の解説

### 1. GoコンパイラのSSA (Static Single Assignment) フォーム

Goコンパイラは、ソースコードを中間表現（IR）に変換し、そのIRに対して様々な最適化を行います。SSA（Static Single Assignment）フォームは、この中間表現の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が非常に容易になります。

例えば、以下のコードを考えます。

```go
x = 1
x = x + 2
y = x * 3
```

SSA形式では、これは次のように表現されます。

```go
x1 = 1
x2 = x1 + 2
y1 = x2 * 3
```

各代入が新しい変数（バージョン）を作成するため、変数の値がどこで定義され、どこで使われているかが明確になります。Goコンパイラは、このSSA形式を利用して、レジスタ割り当て、デッドコード削除、共通部分式除去などの高度な最適化を実行します。

### 2. Go言語における文字列スライス

Go言語の文字列は、不変なバイトシーケンスです。文字列スライスは、既存の文字列の一部を新しい文字列として参照する操作です。

```go
s := "hello world"
sub := s[0:5] // "hello"
```

スライス操作 `s[low:high]` は、`low` から `high-1` までのインデックス範囲のバイトを抽出します。`low` や `high` が省略された場合、それぞれ0や文字列の長さがデフォルト値として使用されます。

重要なのは、スライスインデックスは `int` 型であると期待されることが多いですが、Goの仕様上、任意の整数型（`int8`, `int16`, `int32`, `int64`, `uint8` など）を使用できます。しかし、これらのインデックスが最終的にメモリ操作に変換される際には、システムのポインタサイズ（通常は32ビットまたは64ビット）に合わせたサイズに拡張される必要があります。

### 3. Goコンパイラにおける型システムとSSA値

Goコンパイラ内部では、各変数や式は特定の型を持ちます。SSA形式に変換される際、これらの型情報はSSA値にも引き継がれます。SSA値は、その値が表現するデータの型（例: `TypeInt64`, `TypeUintptr` など）を持ちます。

文字列スライスのインデックスは、最終的にメモリのアドレス計算に使用されるため、ポインタサイズに適合する型（通常は `uintptr` または `int64`）を持つSSA値に変換される必要があります。もし、インデックスが `int32` のような小さい型でSSA値として表現されたまま、ポインタ演算に使用されると、符号拡張の誤りやオーバーフローによって不正なアドレスが計算される可能性があります。

`s.extendIndex` のような関数は、このような状況で、小さい整数型のSSA値を、ポインタサイズに適合するより大きな整数型（通常は `int64`）に安全に変換（符号拡張またはゼロ拡張）するために使用されます。これにより、SSAバックエンドが生成するコードが、ランタイムの期待するインデックス型と一致し、正しく動作することが保証されます。

## 技術的詳細

このコミットの技術的詳細は、GoコンパイラのSSAバックエンドが文字列スライス操作をどのように処理するか、そしてその過程で発生していた型の不一致の問題に焦点を当てています。

Goコンパイラの `src/cmd/compile/internal/gc/ssa.go` ファイルは、AST（抽象構文木）からSSA形式への変換ロジックを担っています。`s.expr(n *Node)` メソッドは、ASTノード `n` をSSA値に変換する主要な関数です。

文字列スライス `s[low:high]` の処理において、`low` と `high` のインデックスはそれぞれ `n.Right.Left` と `n.Right.Right` というASTノードに対応します。これらのノードは `s.expr()` を通じてSSA値に変換されます。

問題は、`s.expr()` が返したSSA値が、必ずしも文字列スライス操作に必要な適切な型（例えば `int64`）を持っていなかった点にあります。特に、インデックスが `int` 型ではない、より小さい整数型（例: `int32`）で表現されていた場合、そのSSA値は `TypeInt32` のような型を持つことになります。

Goのランタイムは、スライス操作のインデックスを `int` 型（通常は `int64`）として扱います。もし `int32` のSSA値がそのまま使用されると、以下のような問題が生じます。

1.  **符号拡張の不一致**: `int32` の負の値が `int64` に変換される際に、期待される符号拡張が行われない、または誤った符号拡張が行われる可能性があります。例えば、`-1` (int32) が `0xFFFFFFFF` として扱われ、`int64` に変換されると `0x00000000FFFFFFFF` (正の値) になる可能性があります。これは、スライスインデックスが負の値になることを防ぐためのチェックを迂回する可能性があります。
2.  **オーバーフロー**: `int32` の最大値を超えるインデックスが `int64` に変換される際に、値が正しく保持されない可能性があります。
3.  **SSA最適化の誤り**: SSAバックエンドの最適化パスは、SSA値の型情報に基づいて動作します。型の不一致があると、最適化が正しく適用されなかったり、誤った最適化が行われたりする可能性があります。

このコミットでは、`s.extendIndex()` という新しいヘルパー関数を導入することで、この問題を解決しています。`s.extendIndex()` は、与えられたSSA値（インデックス）を受け取り、その値が `int64` 型でない場合に、適切な `int64` 型に拡張するSSA命令を生成します。これにより、文字列スライスの `low` および `high` インデックスは、常に `int64` 型のSSA値として扱われるようになり、ランタイムの期待と一致するようになります。

テストケース `src/cmd/compile/internal/gc/testdata/string_ssa.go` に追加された `testSmallIndexType_ssa` 関数は、この修正の重要性を示しています。このテストは、`_Accuracy_index[i]:_Accuracy_index[i+1]` のように、小さい整数型（`uint8` の配列インデックス）を使用して文字列スライスを行うケースを検証しています。このようなケースで `s.extendIndex` が適用されることで、インデックスが正しく `int64` に拡張され、スライス操作が期待通りに機能することが保証されます。

## コアとなるコードの解説

変更されたコードは、GoコンパイラのSSAバックエンドにおける文字列スライス操作のインデックス処理を改善します。

`s.expr(n *Node)` メソッドは、ASTノードをSSA値に変換する役割を担っています。文字列スライス `s[low:high]` の場合、`low` と `high` はそれぞれ `n.Right.Left` と `n.Right.Right` というASTノードに対応します。

以前のコードでは、これらのインデックスは単に `s.expr()` を通してSSA値に変換されていました。しかし、この変換だけでは、インデックスのSSA値が常に適切な型（例えば `int64`）を持つことが保証されませんでした。特に、インデックスが `int32` のような小さい整数型で表現されている場合、そのSSA値も `TypeInt32` のような型を持つ可能性がありました。

追加された `s.extendIndex()` 関数は、この問題を解決します。この関数は、`s.expr()` が返したSSA値を受け取り、その値の型が `int64` でない場合に、その値を `int64` 型に拡張するSSA命令を生成します。これにより、`low` と `high` のインデックスは、常に `int64` 型のSSA値として扱われるようになります。

この変更の目的は、文字列スライスのインデックスが、Goランタイムが期待するポインタサイズに合わせた整数型（通常は `int64`）で表現されることを保証することです。これにより、インデックスの範囲チェックや、最終的なメモリアクセスのアドレス計算が正しく行われるようになり、コンパイルされたコードの堅牢性と正確性が向上します。

`s.extendIndex` の具体的な実装はコミットログには含まれていませんが、その役割は、SSA値の型をチェックし、必要に応じて `OpSignExt` (符号拡張) や `OpZeroExt` (ゼロ拡張) などのSSA命令を挿入して、値を目的の型に変換することであると推測されます。これにより、異なるサイズの整数型が混在するGoのコードでも、SSAバックエンドが安全かつ正確に処理できるようになります。

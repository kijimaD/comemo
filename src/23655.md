## 変更の背景

このコミットは、Go 1.5のリリースノートに、`internal` パッケージの可視性ルールが標準ライブラリだけでなく、一般的なGoモジュールやプロジェクト全体にわたって強制されるようになったという重要な変更を記録するために行われました。

Go 1.4では、`internal` ディレクトリの概念が導入されました。これは、特定のパッケージがその親ディレクトリとその兄弟パッケージからのみインポート可能であり、それ以外の外部パッケージからはインポートできないようにするためのメカニズムです。当初、このルールは主にGoの標準ライブラリ内で、内部実装の詳細を隠蔽し、APIの安定性を保つために使用されていました。

しかし、この強力なカプセル化の仕組みは、標準ライブラリだけでなく、ユーザーが作成するGoモジュールやアプリケーションにおいても非常に有用であることが認識されました。内部実装に依存するコードが誤って外部に公開され、意図しない依存関係を生み出すことを防ぐため、Go 1.5ではこの `internal` パッケージの強制ルールが標準ライブラリ外のすべてのGoコードに拡張されることになりました。

この変更は、Goのパッケージ管理とモジュール設計におけるベストプラクティスを強化し、より堅牢で保守しやすいコードベースの構築を促進することを目的としています。コミットメッセージ内の `golang.org/s/go14internal` と `https://golang.org/cl/9156` は、この `internal` パッケージの導入と、その後の強制ルールの拡張に関する議論と実装の経緯を示すリンクです。

## 前提知識の解説

### Goのパッケージと可視性

Go言語では、コードは「パッケージ」という単位で整理されます。パッケージは関連する機能の集合であり、再利用可能なコードの基本単位です。Goの可視性ルールは非常にシンプルで、識別子（変数、関数、型など）の最初の文字が大文字であればエクスポートされ（外部からアクセス可能）、小文字であればパッケージプライベート（パッケージ内でのみアクセス可能）となります。

### `internal` パッケージの概念

Go 1.4で導入された `internal` パッケージは、この基本的な可視性ルールを補完するものです。`internal` ディレクトリ内に配置されたパッケージは、その `internal` ディレクトリの「親」ディレクトリにあるパッケージからのみインポートが許可されます。それ以外のパッケージからは、たとえ同じモジュール内であってもインポートできません。

例えば、以下のようなディレクトリ構造を考えます。

```
myproject/
├── main.go
├── mylib/
│   └── mylib.go
└── mylib/
    └── internal/
        └── helper/
            └── helper.go
```

この場合、`mylib/mylib.go` は `mylib/internal/helper/helper.go` をインポートできます。しかし、`main.go` は `mylib/internal/helper/helper.go` を直接インポートすることはできません。`main.go` が `helper` パッケージの機能を利用したい場合は、`mylib.go` を介してアクセスする必要があります。

このメカニズムは、ライブラリやアプリケーションの内部実装の詳細を外部から隠蔽し、意図しない依存関係の発生を防ぐために非常に有効です。これにより、ライブラリの作者は内部実装を自由にリファクタリングでき、外部の利用者は安定した公開APIのみに依存することができます。

### Go 1.4における `internal` の強制

Go 1.4では `internal` パッケージの概念が導入されましたが、その強制は主にGoの標準ライブラリ内に限定されていました。つまり、ユーザーが作成したプロジェクトで `internal` ディレクトリを使用しても、コンパイラによる厳密なインポート制限は適用されませんでした。これは、この機能がまだ実験的な段階であり、その挙動が標準ライブラリの構造に特化して実装されていたためです。

## 技術的詳細

Go 1.5における `internal` パッケージの強制の拡張は、Goコンパイラとツールチェーンの変更によって実現されました。具体的には、Goコンパイラがパッケージのインポートパスを解決する際に、`internal` ディレクトリの存在とその親ディレクトリとの関係をより厳密にチェックするようになりました。

この変更の核心は、`go/build` パッケージ（Goのビルドシステムがパッケージ情報を解決するために使用するライブラリ）にあります。`go/build` パッケージは、ファイルシステム上のパッケージをスキャンし、そのインポートパスと可視性を判断します。Go 1.5では、このパッケージが `internal` ディレクトリのルールを標準ライブラリの特別なケースとしてではなく、一般的なルールとして適用するように更新されました。

具体的には、インポートパスに `/internal/` が含まれる場合、そのパッケージは、インポート元のパッケージが `internal` ディレクトリの直上の親ディレクトリにある場合にのみインポートが許可されます。それ以外の場合、コンパイラは「`internal` パッケージはインポートできません」というエラーを生成します。

この変更は、Goのモジュールシステム（Go 1.11で導入）の登場よりも前の話ですが、Goのパッケージ管理の基盤を強化する上で重要な一歩となりました。これにより、開発者は自身のプロジェクトにおいても、標準ライブラリと同様に、内部実装を明確に区別し、外部からの不適切なアクセスを防ぐことができるようになりました。

この強制は、Goのビルドプロセス全体に影響を与えます。`go build`、`go install`、`go test` などのコマンドはすべて、この新しい可視性ルールに従ってパッケージのインポートを検証します。これにより、開発者はビルド時に早期に問題を検出し、よりクリーンなアーキテクチャを維持することができます。

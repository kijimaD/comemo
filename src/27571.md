## 変更の背景

Go言語は、その高性能、並行処理の容易さ、そしてシンプルな開発モデルから、様々なプラットフォームでの利用が期待されています。IBM System z (s390x) は、メインフレームとして知られるエンタープライズ向けの強力なアーキテクチャであり、金融機関や大規模企業などでミッションクリティカルなシステムを支えています。

このコミットが導入された背景には、Go言語の適用範囲を拡大し、s390xプラットフォーム上でもGoプログラムをネイティブに実行できるようにするという戦略的な意図があります。これにより、Go開発者はメインフレームの堅牢性と信頼性を活用しつつ、Goの現代的な開発パラダイムでアプリケーションを構築できるようになります。

具体的には、Goのリンカがs390xのオブジェクトファイル形式（ELF）、アセンブリ命令、およびリンキング規則を理解し、適切に処理できるようになる必要があります。これには、s390x固有のレジスタ、命令セット、メモリモデル、そして特に動的リンキングにおけるリロケーション処理のサポートが含まれます。

## 前提知識の解説

### 1. Goリンカ (`cmd/link`)

Goのビルドプロセスにおいて、コンパイラ (`cmd/compile`) が生成したオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリやライブラリを生成するのがリンカ (`cmd/link`) の役割です。リンカは、異なるオブジェクトファイル間のシンボル参照を解決し、最終的なプログラムのメモリレイアウトを決定します。

### 2. s390xアーキテクチャ

s390xは、IBMが開発した64ビットの命令セットアーキテクチャであり、主にIBM System zメインフレームで使用されています。このアーキテクチャは、高い信頼性、可用性、保守性 (RAS: Reliability, Availability, Serviceability) と、大規模なトランザクション処理やI/O処理に特化した設計が特徴です。レジスタセット、命令形式、メモリ管理など、一般的なx86やARMとは異なる独自の特徴を持っています。

### 3. リンキングの種類

*   **内部リンキング (Internal Linking)**: Goの標準的なリンキングモードで、すべての必要なコードとデータが単一の実行可能ファイルにまとめられます。Goランタイムも含まれるため、外部のCライブラリなどに依存しないスタンドアロンなバイナリが生成されます。
*   **外部リンキング (External Linking)**: Cgoを使用する場合や、特定のシステムライブラリ（例: `glibc`）に依存する場合に用いられます。この場合、Goリンカはオブジェクトファイルを生成し、最終的な実行可能ファイルの生成はシステムのCリンカ（例: `gcc`）に委ねられます。
*   **共有ライブラリリンキング (Shared Library Linking)**: プログラムが実行時にロードされる共有ライブラリ（`.so`ファイル）を利用する場合、またはGoプログラム自体を共有ライブラリとしてビルドする場合に必要です。動的リンキングを可能にするために、PLT (Procedure Linkage Table) や GOT (Global Offset Table) といったメカニズムが使用されます。

### 4. ELF (Executable and Linkable Format)

Linuxを含む多くのUnix系システムで標準的に使用される実行可能ファイル、オブジェクトファイル、共有ライブラリのファイル形式です。ELFファイルは、プログラムヘッダ、セクションヘッダ、シンボルテーブル、リロケーションエントリなど、様々な情報を含んでいます。

### 5. リロケーション (Relocation)

リンカがオブジェクトファイルを結合する際に、コードやデータ内のアドレス参照を修正するプロセスです。コンパイル時には最終的なメモリ上のアドレスが不明なため、相対アドレスやシンボル参照がプレースホルダーとして埋め込まれます。リンカはこれらのプレースホルダーを、最終的な実行可能ファイル内の実際のアドレスに置き換えます。

### 6. PLT (Procedure Linkage Table) と GOT (Global Offset Table)

動的リンキングにおいて、共有ライブラリ内の関数呼び出しやデータアクセスを解決するために使用される重要なデータ構造です。
*   **PLT**: 共有ライブラリ内の関数を呼び出す際に使用されるコードの小さな断片です。初めて関数が呼び出される際に、リンケージエディタ (dynamic linker/loader) が実際の関数のアドレスを解決し、GOTエントリを更新します。以降の呼び出しでは、PLTは直接GOTを介して関数にジャンプします。
*   **GOT**: 共有ライブラリ内のデータや関数のアドレスを格納するテーブルです。PLTから参照されることもあれば、データアクセスで直接参照されることもあります。

### 7. `moduledata`

Goランタイムが内部的に使用するデータ構造で、Goモジュールに関するメタデータ（型情報、関数情報、グローバル変数など）を保持します。動的にロードされるGoモジュール（プラグインなど）の場合、この`moduledata`をランタイムのグローバルな`moduledata`リストに追加する必要があります。

## 技術的詳細

このコミットは、Goリンカがs390xアーキテクチャを完全にサポートするために必要な、以下の主要なコンポーネントを導入しています。

1.  **アーキテクチャ固有の定数と設定 (`src/cmd/link/internal/s390x/l.go`)**:
    *   `PtrSize`, `IntSize`, `RegSize` など、s390xのポインタ、整数、レジスタのサイズを定義します。s390xは64ビットアーキテクチャであるため、これらは8バイトに設定されます。
    *   `MaxAlign`, `MinAlign`, `FuncAlign` など、データおよび関数のアライメント要件を定義します。
    *   DWARFデバッグ情報で使用されるレジスタ番号 (`DWARFREGSP`, `DWARFREGLR`) をマッピングします。

2.  **リンカの初期化とアーキテクチャ固有のフック (`src/cmd/link/internal/s390x/obj.go`)**:
    *   `linkarchinit` 関数は、`ld.Thearch` グローバル構造体（リンカのアーキテクチャ固有の操作をカプセル化する）をs390x固有の実装で初期化します。これには、リロケーション処理 (`Adddynrel`, `Archreloc`, `Archrelocvariant`, `Elfreloc1`, `Machoreloc1`)、アセンブリ生成 (`Asmb`, `Gentext`), PLT/GOTセットアップ (`Elfsetupplt`, `addpltsym`, `addgotsym`) などの関数ポインタが含まれます。
    *   `archinit` 関数は、リンキングモード（内部、外部）の決定や、ELFヘッダタイプ (`obj.Hlinux`) に基づく初期アドレス設定など、アーキテクチャ固有の初期化ロジックを処理します。s390xの場合、Linux ELF形式がデフォルトでサポートされます。

3.  **アセンブリ生成とリロケーション処理 (`src/cmd/link/internal/s390x/asm.go`)**:
    *   **`gentext` 関数**: 動的リンクされたGoモジュールがランタイムの`moduledata`リストに自身を追加するためのアセンブリコードを生成します。これは、`go.link.addmoduledata`という特別な関数として実装され、`runtime.addmoduledata`を呼び出すことで実際の追加処理を行います。このメカニズムは、Goのプラグインや共有ライブラリが正しく初期化されるために不可欠です。
        *   `larl %r2, <local.moduledata>`: ローカルの`moduledata`のアドレスをレジスタ`%r2`にロードします。`larl` (Load Address Relative Long) はs390xのPC相対アドレス指定命令です。
        *   `jg <runtime.addmoduledata@plt>`: `runtime.addmoduledata`関数を呼び出します。`jg` (Jump and Save) はs390xの関数呼び出し命令で、動的リンクの場合はPLTを介して解決されます。
    *   **`adddynrel` 関数**: ELFオブジェクトファイルから読み取られたリロケーションエントリをGoリンカの内部リロケーション形式に変換し、動的リンキングに必要な追加処理を行います。s390x固有の様々なELFリロケーションタイプ（例: `R_390_PC16`, `R_390_PLT32DBL`, `R_390_GOTENT`など）を処理します。
        *   `R_390_PCREL`: PC相対アドレス指定のリロケーション。
        *   `R_390_PLTxxDBL`, `R_390_PLTxx`: PLTを介した関数呼び出しのリロケーション。`DBL`はs390xの命令セットにおける「ダブルワード」または「ダブルレングス」を指す可能性があり、命令のエンコーディングやアドレス計算に影響します。
        *   `R_390_GOTENT`: GOTエントリへの参照のリロケーション。
        *   `R_390_TLS_LExx`, `R_390_TLS_IEENT`: スレッドローカルストレージ (TLS) 関連のリロケーション。
    *   **`elfreloc1` 関数**: Goリンカが生成するELFリロケーションエントリを書き出すための関数です。Goの内部リロケーションタイプをs390xのELFリロケーションタイプにマッピングします。
    *   **`elfsetupplt` 関数**: PLTの初期エントリをセットアップします。これは、動的リンカが初めて共有ライブラリ関数を解決する際に使用するブートストラップコードです。
    *   **`addpltsym` 関数**: 共有ライブラリ関数を呼び出すためのPLTエントリと、それに対応するGOTエントリおよびリロケーションエントリを生成します。
    *   **`addgotsym` 関数**: 共有ライブラリ内のデータにアクセスするためのGOTエントリと、それに対応するリロケーションエントリを生成します。
    *   **`asmb` 関数**: 最終的な実行可能ファイルのセクション（テキスト、データ、読み取り専用データなど）をファイルに書き込み、シンボルテーブルやDWARFデバッグ情報を生成します。

これらの変更により、Goリンカはs390xの命令セット、メモリモデル、およびELF動的リンキングの複雑な要件を処理できるようになり、Goプログラムがs390xプラットフォーム上で効率的かつ正確に動作することが保証されます。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、`src/cmd/link/internal/s390x/asm.go`、`src/cmd/link/internal/s390x/l.go`、`src/cmd/link/internal/s390x/obj.go` の3つの新規ファイルに集約されています。特に、`asm.go` はs390x固有のアセンブリ生成とリロケーション処理の大部分を担っています。

以下に、`src/cmd/link/internal/s390x/asm.go` から `gentext` 関数と `adddynrel` 関数の一部を抜粋します。

```go
// src/cmd/link/internal/s390x/asm.go

// gentext generates assembly to append the local moduledata to the global
// moduledata linked list at initialization time. This is only done if the runtime
// is in a different module.
//
// <go.link.addmoduledata>:
// 	larl  %r2, <local.moduledata>
// 	jg    <runtime.addmoduledata@plt>
//	undef
//
// The job of appending the moduledata is delegated to runtime.addmoduledata.
func gentext() {
	if !ld.DynlinkingGo() {
		return
	}
	addmoduledata := ld.Linklookup(ld.Ctxt, "runtime.addmoduledata", 0)
	if addmoduledata.Type == obj.STEXT {
		// we're linking a module containing the runtime -> no need for
		// an init function
		return
	}
	addmoduledata.Attr |= ld.AttrReachable
	initfunc := ld.Linklookup(ld.Ctxt, "go.link.addmoduledata", 0)
	initfunc.Type = obj.STEXT
	initfunc.Attr |= ld.AttrLocal
	initfunc.Attr |= ld.AttrReachable

	// larl %r2, <local.moduledata>
	ld.Adduint8(ld.Ctxt, initfunc, 0xc0)
	ld.Adduint8(ld.Ctxt, initfunc, 0x20)
	lmd := ld.Addrel(initfunc)
	lmd.Off = int32(initfunc.Size)
	lmd.Siz = 4
	lmd.Sym = ld.Ctxt.Moduledata
	lmd.Type = obj.R_PCREL
	lmd.Variant = ld.RV_390_DBL
	lmd.Add = 2 + int64(lmd.Siz)
	ld.Adduint32(ld.Ctxt, initfunc, 0)

	// jg <runtime.addmoduledata[@plt]>
	ld.Adduint8(ld.Ctxt, initfunc, 0xc0)
	ld.Adduint8(ld.Ctxt, initfunc, 0xf4)
	rel := ld.Addrel(initfunc)
	rel.Off = int32(initfunc.Size)
	rel.Siz = 4
	rel.Sym = ld.Linklookup(ld.Ctxt, "runtime.addmoduledata", 0)
	rel.Type = obj.R_CALL
	rel.Variant = ld.RV_390_DBL
	rel.Add = 2 + int64(rel.Siz)
	ld.Adduint32(ld.Ctxt, initfunc, 0)

	// undef (for debugging)
	ld.Adduint32(ld.Ctxt, initfunc, 0)

	if ld.Ctxt.Etextp != nil {
		ld.Ctxt.Etextp.Next = initfunc
	} else {
		ld.Ctxt.Textp = initfunc
	}
	ld.Ctxt.Etextp = initfunc
	initarray_entry := ld.Linklookup(ld.Ctxt, "go.link.addmoduledatainit", 0)
	initarray_entry.Attr |= ld.AttrLocal
	initarray_entry.Attr |= ld.AttrReachable
	initarray_entry.Type = obj.SINITARR
	ld.Addaddr(ld.Ctxt, initarray_entry, initfunc)
}

func adddynrel(s *ld.LSym, r *ld.Reloc) {
	targ := r.Sym
	ld.Ctxt.Cursym = s

	switch r.Type {
	default:
		if r.Type >= 256 {
			ld.Diag("unexpected relocation type %d", r.Type)
			return
		}

		// Handle relocations found in ELF object files.
	case 256 + ld.R_390_8,
		256 + ld.R_390_16,
		256 + ld.R_390_32,
		256 + ld.R_390_64:
		if targ.Type == obj.SDYNIMPORT {
			ld.Diag("unexpected R_390_nn relocation for dynamic symbol %s", targ.Name)
		}
		r.Type = obj.R_ADDR
		return

	case 256 + ld.R_390_PC16,
		256 + ld.R_390_PC32,
		256 + ld.R_390_PC64:
		if targ.Type == obj.SDYNIMPORT {
			ld.Diag("unexpected R_390_PCnn relocation for dynamic symbol %s", targ.Name)
		}
		if targ.Type == 0 || targ.Type == obj.SXREF {
			ld.Diag("unknown symbol %s in pcrel", targ.Name)
		}
		r.Type = obj.R_PCREL
		r.Add += int64(r.Siz)
		return

	case 256 + ld.R_390_PLT16DBL,
		256 + ld.R_390_PLT32DBL:
		r.Type = obj.R_PCREL
		r.Variant = ld.RV_390_DBL
		r.Add += int64(r.Siz)
		if targ.Type == obj.SDYNIMPORT {
			addpltsym(ld.Ctxt, targ)
			r.Sym = ld.Linklookup(ld.Ctxt, ".plt", 0)
			r.Add += int64(targ.Plt)
		}
		return
    // ... (他のリロケーションタイプ)
	}
	// Handle references to ELF symbols from our own object files.
	if targ.Type != obj.SDYNIMPORT {
		return
	}

	ld.Diag("unsupported relocation for dynamic symbol %s (type=%d stype=%d)", targ.Name, r.Type, targ.Type)
}
```

## コアとなるコードの解説

### `gentext` 関数

この関数は、Goの動的リンキングにおいて非常に重要な役割を果たします。Goプログラムが共有ライブラリとしてビルドされたり、プラグインとしてロードされたりする場合、そのモジュール固有の`moduledata`をGoランタイムのグローバルな`moduledata`リストに登録する必要があります。`gentext`は、この登録処理を行うための小さなアセンブリ関数 `go.link.addmoduledata` を生成します。

1.  **動的リンキングのチェック**: `ld.DynlinkingGo()` で、現在動的リンキングが有効になっているかを確認します。無効な場合は処理をスキップします。
2.  **`runtime.addmoduledata` の検索**: `ld.Linklookup` を使用して、Goランタイムが提供する`runtime.addmoduledata`関数のシンボルを検索します。この関数が既に現在のモジュール内に存在する場合（つまり、ランタイム自体をリンクしている場合）、初期化関数は不要なのでスキップします。
3.  **`go.link.addmoduledata` の作成**: `go.link.addmoduledata` という名前の新しいテキストシンボルを作成し、`AttrReachable` (到達可能) および `AttrLocal` (ローカルシンボル) の属性を設定します。
4.  **`larl %r2, <local.moduledata>` 命令の生成**:
    *   `ld.Adduint8` を使って、s390xの`larl`命令のオペコード (`0xc0`, `0x20`) を追加します。
    *   `ld.Addrel` でリロケーションエントリを作成します。このリロケーションは、ローカルの`moduledata`シンボル (`ld.Ctxt.Moduledata`) へのPC相対参照 (`obj.R_PCREL`) であり、s390x固有の`RV_390_DBL`バリアントが指定されています。これは、s390xの命令がダブルワード境界にアラインされることや、アドレス計算が2で割られることを示唆しています。
5.  **`jg <runtime.addmoduledata@plt>` 命令の生成**:
    *   `ld.Adduint8` で、s390xの`jg`命令のオペコード (`0xc0`, `0xf4`) を追加します。
    *   `ld.Addrel` で別のリロケーションエントリを作成します。これは`runtime.addmoduledata`への関数呼び出し (`obj.R_CALL`) であり、動的リンクの場合はPLTを介して解決されるため、`RV_390_DBL`バリアントがここでも使用されます。
6.  **`undef` 命令の生成**: デバッグ目的で、`undef` (未定義命令) を追加します。
7.  **テキストセクションへの追加**: 生成された`initfunc` (すなわち `go.link.addmoduledata`) をリンカのテキストセクションリストに追加します。
8.  **`go.link.addmoduledatainit` の作成**: `go.link.addmoduledatainit` という名前の`SINITARR` (初期化配列) タイプのシンボルを作成し、その値として`initfunc`のアドレスを設定します。これにより、システムがモジュールをロードする際にこの初期化関数が実行されるようになります。

### `adddynrel` 関数

この関数は、ELFオブジェクトファイルから読み込まれたリロケーションエントリを処理し、Goリンカの内部表現に変換するとともに、動的リンキングに必要な追加のシンボル（PLT/GOTエントリなど）を生成します。

*   **ELFリロケーションタイプの処理**: `switch r.Type` ステートメントは、s390x固有の様々なELFリロケーションタイプ（`256 + ld.R_390_...`）をGoリンカの汎用リロケーションタイプ（`obj.R_ADDR`, `obj.R_PCREL`など）にマッピングします。
*   **`SDYNIMPORT` シンボルの扱い**: `obj.SDYNIMPORT` は、動的にインポートされるシンボル（共有ライブラリから提供されるシンボル）を示します。これらのシンボルに対するリロケーションは、PLTやGOTを介して解決される必要があります。
*   **`R_390_PLTxxDBL` の処理**: `R_390_PLT16DBL` や `R_390_PLT32DBL` のようなPLT関連のリロケーションタイプの場合、`addpltsym` 関数を呼び出して、対応するPLTエントリとGOTエントリを生成します。これにより、動的リンカが実行時に正しい関数アドレスを解決できるようになります。
*   **エラーハンドリング**: 未サポートのリロケーションタイプや、動的シンボルに対する予期せぬリロケーションが検出された場合、`ld.Diag` を使用して診断メッセージを出力します。

これらの関数は、s390xアーキテクチャの特性（特に命令セットと動的リンキングのメカニズム）を考慮し、Goプログラムがこのプラットフォーム上で正しくリンクされ、実行されるための基盤を提供します。

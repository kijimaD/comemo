## 変更の背景

このコミットの背景には、TLS（Transport Layer Security）プロトコルのセキュリティ強化と、より現代的な暗号技術への移行があります。

1.  **TLS 1.2の普及と強化**: TLS 1.2は、それ以前のバージョン（SSL 3.0, TLS 1.0, TLS 1.1）に比べて、より強力な暗号スイートとハッシュアルゴリズムを導入しています。特に、SHA-1のような脆弱性が指摘され始めたハッシュ関数から、より安全なSHA-256やSHA-384への移行が求められていました。
2.  **RFC 5289の登場**: RFC 5289は、TLSにおける楕円曲線暗号（ECC）ベースの新しい暗号スイートを定義し、特にAES-GCM（Galois/Counter Mode）とSHA-256/SHA-384ハッシュ関数を組み合わせたものを推奨しています。AES-GCMは、認証付き暗号（AEAD: Authenticated Encryption with Associated Data）として、データの機密性、完全性、認証を同時に提供できるため、従来のCBCモードとHMACを組み合わせた方式よりも効率的かつ安全とされています。
3.  **PRFの汎用化**: TLSのハンドシェイクプロセスにおいて、マスターシークレットからセッションキーを導出するために擬似乱数関数（PRF）が使用されます。TLS 1.2では、このPRFにHMACベースの関数が採用されており、使用するハッシュアルゴリズムを選択できるようになっています。このコミットは、PRFがSHA-256だけでなく、より強力なSHA-384も利用できるように汎用化することで、将来的なセキュリティ要件への対応と柔軟性の向上を図っています。
4.  **Cloudflareの貢献**: コミットの作者がCloudflareのエンジニアであることから、実際の運用環境におけるTLSのパフォーマンスとセキュリティの重要性が背景にあると考えられます。Cloudflareのような大規模なCDNプロバイダーは、常に最新かつ最も安全な暗号技術を導入し、インターネット全体のセキュリティ向上に貢献しています。

これらの背景から、Go言語の`crypto/tls`パッケージが、最新のセキュリティ標準と推奨事項に準拠し、より堅牢なTLS通信を提供できるよう、`AES_256_GCM_SHA384`のサポートとPRFの汎用化が実装されました。

## 前提知識の解説

このコミットを理解するためには、以下の暗号技術とTLSプロトコルに関する基本的な知識が必要です。

1.  **TLS (Transport Layer Security)**:
    *   インターネット上で安全な通信を行うためのプロトコルで、ウェブブラウジング（HTTPS）などで広く利用されています。
    *   クライアントとサーバー間で暗号化された通信チャネルを確立し、データの機密性、完全性、認証を提供します。
    *   **ハンドシェイク**: TLS接続の開始時に行われるプロセスで、クライアントとサーバーが互いを認証し、使用する暗号スイートを決定し、セッションキーを生成します。
    *   **TLS 1.2**: TLSプロトコルのバージョンの一つで、より強力な暗号アルゴリズムとハッシュ関数をサポートしています。

2.  **暗号スイート (Cipher Suite)**:
    *   TLSハンドシェイク中にクライアントとサーバーが合意する、一連の暗号アルゴリズムの組み合わせです。
    *   通常、以下の要素を含みます:
        *   **鍵交換アルゴリズム (Key Exchange Algorithm)**: 共有秘密鍵を安全に確立する方法（例: ECDHE, RSA）。
        *   **認証アルゴリズム (Authentication Algorithm)**: サーバー（およびオプションでクライアント）の身元を確認する方法（例: RSA, ECDSA）。
        *   **対称暗号アルゴリズム (Symmetric Encryption Algorithm)**: 実際のデータを暗号化・復号化する方法（例: AES）。
        *   **暗号モード (Cipher Mode)**: 対称暗号アルゴリズムの動作モード（例: GCM, CBC）。
        *   **メッセージ認証コード (MAC) またはハッシュ関数 (Hash Function)**: データが改ざんされていないことを保証する方法（例: SHA-256, SHA-384）。

3.  **AES (Advanced Encryption Standard)**:
    *   広く使用されている対称鍵ブロック暗号アルゴリズムです。
    *   `AES_256`は、256ビットの鍵長を持つAESを指し、非常に高いセキュリティレベルを提供します。

4.  **GCM (Galois/Counter Mode)**:
    *   AESなどのブロック暗号と組み合わせて使用される、認証付き暗号（AEAD）モードの一つです。
    *   データの暗号化（機密性）と、データの改ざん検出（完全性）および送信者の認証（認証）を同時に行います。
    *   カウンタモード（CTR）とガロアフィールド乗算（GMAC）を組み合わせることで、高速な処理と強力なセキュリティを実現します。

5.  **SHA-384 (Secure Hash Algorithm 384)**:
    *   NIST（米国国立標準技術研究所）によって開発された暗号学的ハッシュ関数SHA-2ファミリーの一つです。
    *   入力データから固定長のハッシュ値（メッセージダイジェスト）を生成します。SHA-384は384ビットのハッシュ値を生成します。
    *   データの完全性検証や、デジタル署名、擬似乱数関数などで利用されます。SHA-256よりも長いハッシュ値を提供するため、衝突耐性が高いとされています。

6.  **PRF (Pseudo-Random Function - 擬似乱数関数)**:
    *   TLSプロトコルにおいて、マスターシークレットとランダムなデータ（クライアントとサーバーのランダム値）から、セッションキー（暗号化キー、MACキー、IVなど）を導出するために使用される関数です。
    *   TLS 1.2では、PRFはHMAC（Keyed-Hash Message Authentication Code）をベースにしており、特定のハッシュ関数（例: SHA-256, SHA-384）を用いて計算されます。
    *   PRFのセキュリティは、TLSセッション全体のセキュリティに直結するため、その実装と使用されるハッシュ関数の選択は非常に重要です。

7.  **RFC 5289**:
    *   "TLS Elliptic Curve Cipher Suites with SHA-256/384 and AES Galois Counter Mode (GCM)" というタイトルのRFC（Request for Comments）文書です。
    *   このRFCは、TLS 1.2向けに、楕円曲線暗号（ECDHE/ECDSA）とAES-GCM、そしてSHA-256/SHA-384ハッシュ関数を組み合わせた新しい暗号スイートを標準化しました。これにより、より強力で効率的なTLS通信が可能になりました。

これらの要素が組み合わさることで、TLS通信のセキュリティが確保されます。このコミットは、特に`AES_256_GCM_SHA384`という特定の暗号スイートのサポートを追加し、その基盤となるPRF計算をより柔軟にするものです。

## 技術的詳細

このコミットの技術的詳細を掘り下げると、主に`crypto/tls`パッケージにおける暗号スイートの定義、PRFの計算ロジック、およびハンドシェイク処理の変更に焦点を当てることができます。

1.  **`AES_256_GCM_SHA384`暗号スイートの追加**:
    *   RFC 5289で定義されている`TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384`および`TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384`といった新しい暗号スイートがGoのTLS実装に追加されます。
    *   これらのスイートは、鍵交換にECDHE（Elliptic Curve Diffie-Hellman Ephemeral）、認証にRSAまたはECDSA、対称暗号にAES-256をGCMモードで使用し、PRFおよびメッセージ認証にSHA-384を使用します。
    *   `cipherSuite`構造体に、この新しい暗号スイートの定義が追加され、鍵長、IV長、AEAD関数、そして特に`tls12Hash crypto.Hash`フィールドが追加されています。この`tls12Hash`フィールドが、TLS 1.2のPRF計算で使用されるハッシュ関数を指定するための重要な変更点です。

2.  **PRF計算の汎用化 (`prf.go`の変更)**:
    *   TLS 1.2のPRFは、HMAC-SHA256をベースにしていましたが、この変更により、HMAC-SHA384も利用できるようになります。
    *   既存の`prf12`関数は削除され、代わりに`prf12New`という関数が導入されます。`prf12New`は`crypto.Hash`型の引数を受け取り、そのハッシュ関数を使用してPRFを計算するクロージャを返します。これにより、PRFの計算ロジックが特定のハッシュ関数にハードコードされることなく、動的に選択できるようになります。
    *   `prfForVersion`関数も変更され、TLS 1.2の場合に`tls12Hash`引数を受け取るようになります。これにより、選択された暗号スイートに応じて適切なハッシュ関数がPRFに渡されるようになります。
    *   `masterFromPreMasterSecret`および`keysFromMasterSecret`といった、マスターシークレットやセッションキーを導出する関数も、PRF計算に`tls12Hash`を渡すように変更されます。

3.  **ハンドシェイク処理の適応 (`handshake_client.go`, `handshake_server.go`の変更)**:
    *   クライアントとサーバーのハンドシェイク処理において、`newFinishedHash`関数の呼び出しが変更されます。以前はTLSバージョンのみを引数としていましたが、新しい`tls12Hash`も引数として渡すようになります。
    *   `finishedHash`構造体には、PRF計算に使用する関数を保持するための`prf`フィールドが追加されます。これにより、ハンドシェイクの最終メッセージ（Finishedメッセージ）のハッシュ計算が、選択された暗号スイートのハッシュ関数（SHA-256またはSHA-384）に適切に対応できるようになります。
    *   テストデータ（`testdata`ディレクトリ内の多数のファイル）も、新しい暗号スイートとハンドシェイクフローに対応するように更新されています。これは、TLSハンドシェイクのバイナリ表現を含むため、新しい暗号スイートが追加されると、ハンドシェイクメッセージの構造や内容が変化するため、これらのテストデータも更新する必要があることを示しています。

これらの変更により、GoのTLS実装は、より強力なハッシュアルゴリズムであるSHA-384をTLS 1.2のPRF計算に利用できるようになり、RFC 5289で定義された最新の暗号スイートをサポートすることで、セキュリティと互換性が向上します。特に、PRFの汎用化は、将来的に他のハッシュアルゴリズムをサポートするための基盤ともなります。

## コアとなるコードの解説

このコミットのコアとなる変更は、TLS 1.2の擬似乱数関数（PRF）の計算方法を汎用化し、`AES_256_GCM_SHA384`暗号スイートをサポートすることにあります。

### 1. `cipherSuite`構造体への`tls12Hash`フィールドの追加

`src/crypto/tls/cipher_suites.go`において、各暗号スイートの定義を保持する`cipherSuite`構造体に、新たに`tls12Hash crypto.Hash`フィールドが追加されました。

```go
type cipherSuite struct {
	// ... 既存のフィールド ...
	flags     int
	cipher    func(key, iv []byte, isRead bool) interface{}
	mac       func(version uint16, macKey []byte) macFunction
	aead      func(key, fixedNonce []byte) cipher.AEAD
	tls12Hash crypto.Hash // <-- 新しく追加されたフィールド
}
```

このフィールドは、TLS 1.2プロトコルバージョンで使用されるPRFのハッシュアルゴリズムを指定するために導入されました。例えば、`TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384`のような新しい暗号スイートでは、このフィールドに`crypto.SHA384`が設定されます。これにより、TLSハンドシェイク中に選択された暗号スイートに基づいて、適切なハッシュアルゴリズムがPRFに渡されるようになります。

### 2. PRF計算の汎用化 (`prf.go`)

最も重要な変更は`src/crypto/tls/prf.go`にあります。

*   **`prf12New`関数の導入**:
    以前はTLS 1.2のPRF計算が`prf12`関数内で`sha256.New`にハードコードされていました。このコミットでは、`prf12`関数を削除し、代わりに`prf12New`という新しい関数を導入しました。

    ```go
    // prf12New returns a function implementing the TLS 1.2 pseudo-random function,
    // as defined in RFC 5246, section 5, using the given hash.
    func prf12New(tls12Hash crypto.Hash) func(result, secret, label, seed []byte) {
    	return func(result, secret, label, seed []byte) {
    		labelAndSeed := make([]byte, len(label)+len(seed))
    		copy(labelAndSeed, label)
    		copy(labelAndSeed[len(label):], seed)
    		pHash(result, secret, labelAndSeed, tls12Hash.New) // <-- 汎用化されたハッシュ関数
    	}
    }
    ```
    `prf12New`は`crypto.Hash`型の引数を受け取り、そのハッシュ関数（例: `crypto.SHA256`や`crypto.SHA384`）を使用してPRFを計算するクロージャを返します。これにより、PRFの計算ロジックが特定のハッシュアルゴリズムに依存しなくなりました。

*   **`prfForVersion`関数の変更**:
    `prfForVersion`関数は、TLSのバージョンに応じて適切なPRF関数を返す役割を担っています。この関数も`tls12Hash crypto.Hash`引数を受け取るように変更され、TLS 1.2の場合に`prf12New(tls12Hash)`を呼び出すようになりました。

    ```go
    func prfForVersion(version uint16, tls12Hash crypto.Hash) func(result, secret, label, seed []byte) {
    	switch version {
    	// ... 既存のケース ...
    	case VersionTLS12:
    		return prf12New(tls12Hash) // <-- tls12Hashを使用
    	// ...
    	}
    }
    ```

*   **キー導出関数の更新**:
    `masterFromPreMasterSecret`（プリマスターシークレットからマスターシークレットを導出）および`keysFromMasterSecret`（マスターシークレットからセッションキーを導出）の各関数も、`tls12Hash crypto.Hash`引数を受け取るように変更され、内部で`prfForVersion`を呼び出す際にこのハッシュを渡すようになりました。これにより、キー導出プロセス全体で、選択された暗号スイートのハッシュアルゴリズムが使用されることが保証されます。

### 3. `finishedHash`の変更とハンドシェイクへの影響

TLSハンドシェイクの最終段階で、クライアントとサーバーは互いに`Finished`メッセージを送信し、ハンドシェイクの整合性を検証します。このメッセージの計算には、それまでのハンドシェイクメッセージのハッシュとPRFが使用されます。

*   **`finishedHash`構造体の拡張**:
    `src/crypto/tls/prf.go`の`finishedHash`構造体に、`prf func(result, secret, label, seed []byte)`フィールドが追加されました。

    ```go
    type finishedHash struct {
    	// ... 既存のハッシュオブジェクト ...
    	version uint16
    	prf     func(result, secret, label, seed []byte) // <-- 新しく追加されたフィールド
    }
    ```

*   **`newFinishedHash`関数の変更**:
    `newFinishedHash`関数は、`finishedHash`オブジェクトを初期化する際に、`tls12Hash crypto.Hash`引数を受け取るようになりました。TLS 1.2の場合、このハッシュを使用して内部のハッシュオブジェクト（例: `sha384.New()`)を初期化し、さらに`prf`フィールドに`prfForVersion(version, tls12Hash)`を設定します。

    ```go
    func newFinishedHash(version uint16, tls12Hash crypto.Hash) finishedHash {
    	if version >= VersionTLS12 {
    		return finishedHash{tls12Hash.New(), tls12Hash.New(), nil, nil, version, prfForVersion(version, tls12Hash)}
    	}
    	// ...
    }
    ```

*   **`clientSum`と`serverSum`メソッドの更新**:
    `finishedHash.clientSum`および`finishedHash.serverSum`メソッドは、`Finished`メッセージのハッシュを計算する際に、TLS 1.2の場合に`prf12`を直接呼び出すのではなく、`h.prf`（`finishedHash`構造体に格納されたPRF関数）を呼び出すように変更されました。

    ```go
    func (h finishedHash) clientSum(masterSecret []byte) []byte {
    	out := make([]byte, finishedVerifyLength)
    	if h.version >= VersionTLS12 {
    		seed := h.client.Sum(nil)
    		h.prf(out, masterSecret, clientFinishedLabel, seed) // <-- h.prfを使用
    	} else {
    		// ...
    	}
    	return out
    }
    ```

これらの変更により、GoのTLS実装は、`AES_256_GCM_SHA384`のような新しい暗号スイートを完全にサポートできるようになりました。特に、PRF計算の汎用化は、将来的にTLSプロトコルが新しいハッシュアルゴリズムを導入した場合でも、コードベースの変更を最小限に抑えられる柔軟性をもたらします。これは、暗号ライブラリの設計において非常に重要な側面です。

# [インデックス 22123] ファイルの概要

このコミットは、Go言語の`syscall`パッケージにおける`Dup2`システムコールの実装を、Linuxの汎用的な定義から各アーキテクチャ（GOOS）固有のファイルに分割することを目的としています。これは、特に`arm64`アーキテクチャへの移植準備の一環として行われました。既存のプラットフォームにおける`Dup2`の動作には影響を与えず、将来的な`arm64`サポートにおいて`Dup3`へのフォワーディング、または`SYS_DUP3`を直接使用する可能性を考慮しています。

## 変更の背景

この変更の主な背景には、Go言語の`arm64`アーキテクチャへの移植作業があります。Linuxシステムコールには、ファイルディスクリプタを複製するための`dup2`と`dup3`という2つの主要な関数が存在します。

*   **`dup2(oldfd, newfd)`**: `oldfd`が指すファイルディスクリプタを`newfd`に複製します。もし`newfd`が既に開かれている場合、`dup2`はまず`newfd`を閉じ、その後`oldfd`を複製します。
*   **`dup3(oldfd, newfd, flags)`**: `dup2`と同様に複製を行いますが、追加の`flags`引数を取ることができます。これにより、例えば`O_CLOEXEC`フラグを指定して、`exec`系のシステムコールが実行された際に新しいファイルディスクリプタが自動的に閉じられるように設定できます。

`arm64`アーキテクチャでは、`dup2`の代わりに`dup3`を使用することが推奨される、あるいは`dup2`が特定の条件下で問題を引き起こす可能性があります。Goの`syscall`パッケージは、各OSおよびアーキテクチャ固有のシステムコールを抽象化して提供しています。これまでは、Linuxの`Dup2`の実装は`syscall_linux.go`という汎用的なファイルに定義されていました。しかし、`arm64`のような新しいアーキテクチャの特殊な要件に対応するためには、`Dup2`の挙動をアーキテクチャごとにカスタマイズできる柔軟性が必要となりました。

このコミットは、`Dup2`の定義を汎用ファイルから`syscall_linux_386.go`、`syscall_linux_amd64.go`、`syscall_linux_arm.go`などの各アーキテクチャ固有のファイルに移動することで、この柔軟性を実現しようとしています。これにより、`arm64`が追加された際に、そのアーキテクチャに最適な`Dup2`の実装（例えば、内部的に`Dup3`を呼び出すなど）を提供できるようになります。

また、コミットメッセージには「`mksycall.pl`がシンボルをソートしないため、`Dup2`が後で処理されることで、避けられないコードの移動が含まれる」という言及があります。これは、Goのシステムコールラッパーを生成するスクリプトの特性によるもので、コードの論理的な変更とは直接関係のない、生成コードの物理的な配置変更が発生したことを示しています。

## 前提知識の解説

### 1. ファイルディスクリプタ (File Descriptor, fd)

Unix系OSにおいて、ファイルディスクリプタはプロセスが開いているファイルやI/Oリソース（ソケット、パイプなど）を識別するための非負の整数です。標準入力（stdin）は0、標準出力（stdout）は1、標準エラー出力（stderr）は2というように、特定のファイルディスクリプタは慣習的に特定の用途に割り当てられています。

### 2. `dup2` および `dup3` システムコール

*   **`dup2(oldfd, newfd)`**: `oldfd`が指すファイルディスクリプタを`newfd`に複製します。これにより、`oldfd`と`newfd`の両方が同じオープンファイル記述（open file description）を参照するようになります。これは、例えば標準出力をファイルにリダイレクトする際などに使用されます。
*   **`dup3(oldfd, newfd, flags)`**: `dup2`の拡張版で、`flags`引数を取ります。Linux 2.6.27以降で利用可能です。`flags`には`O_CLOEXEC`などを指定でき、これにより新しいファイルディスクリプタが`exec`系のシステムコールで子プロセスに引き継がれないように設定できます。`dup2`は`newfd`が`oldfd`と同じ場合でも成功しますが、`dup3`は`oldfd`と`newfd`が同じ場合は`EINVAL`エラーを返します。

### 3. Go言語の `syscall` パッケージ

Go言語の標準ライブラリには`syscall`パッケージが含まれており、これはOSの低レベルなシステムコールへの直接的なインターフェースを提供します。このパッケージは、OS固有の機能にアクセスする必要がある場合や、パフォーマンスが非常に重要な場合に利用されます。しかし、通常は`os`や`net`などのより高レベルでポータブルなパッケージを使用することが推奨されます。

### 4. `GOOS` と `GOARCH`

Goのビルドシステムでは、`GOOS`（ターゲットOS）と`GOARCH`（ターゲットアーキテクチャ）という環境変数を使用して、特定のOSとアーキテクチャ向けにコードをコンパイルします。例えば、`GOOS=linux GOARCH=amd64`はLinux x86-64向け、`GOOS=linux GOARCH=arm64`はLinux ARM64向けを意味します。Goのソースコードには、これらの変数に基づいて条件付きでコンパイルされるファイル（例: `syscall_linux_amd64.go`）が存在します。

### 5. `mksyscall.pl` スクリプト

`mksyscall.pl`は、Goのビルドプロセスで使用されるPerlスクリプトです。このスクリプトは、Goのソースファイル内に記述された特別なコメント（例: `//sys`や`//sysnb`）を解析し、対応するシステムコールを呼び出すためのGoコード（通常は`zsyscall_*.go`というファイル名で生成される）を自動生成します。これにより、Go開発者は各OSやアーキテクチャのシステムコール呼び出しの詳細を直接記述することなく、高レベルなGoの関数シグネチャでシステムコールを定義できます。

*   `//sys`: システムコールがエラー時に`errno`を設定する場合に使用されます。
*   `//sysnb` (no blocking): システムコールがブロックしないことを示し、`errno`を設定しない場合に使用されます。

## 技術的詳細

このコミットの技術的な核心は、`Dup2`システムコールのGo言語ラッパーの定義を、汎用的なLinuxシステムコール定義ファイル（`src/syscall/syscall_linux.go`）から、各CPUアーキテクチャ固有のLinuxシステムコール定義ファイル（例: `src/syscall/syscall_linux_386.go`, `src/syscall/syscall_linux_amd64.go`, `src/syscall/syscall_linux_arm.go`, `src/syscall/syscall_linux_ppc64x.go`）へ移動した点にあります。

この変更の主な動機は、`arm64`アーキテクチャへのGoの移植を容易にすることです。`arm64`では、`dup2`システムコールが利用できない、あるいは`dup3`システムコールの方がより適切である場合があります。例えば、`dup2`は`newfd`が`oldfd`と同じ場合に`EINVAL`エラーを返すことがありますが、`dup3`はこのようなケースをより柔軟に扱えます。また、`dup3`は`O_CLOEXEC`フラグをサポートしており、これはセキュリティやリソース管理の観点から重要です。

`Dup2`の定義をアーキテクチャ固有のファイルに移動することで、`arm64`向けの`syscall_linux_arm64.go`ファイルが作成された際に、そのファイル内で`Dup2`を`SYS_DUP3`として定義できるようになります。コミットメッセージにある`//sysnb Dup2(oldfd int, newfd int) (err error) = SYS_DUP3`というコメントは、`mksyscall.pl`がこの定義を読み取り、`Dup2`のGo関数が内部的に`dup3`システムコールを呼び出すようなコードを生成することを示唆しています。

この変更は、既存の`386`、`amd64`、`arm`、`ppc64`、`ppc64le`といったアーキテクチャにおける`Dup2`の動作には影響を与えません。これらのアーキテクチャでは、引き続き`SYS_DUP2`システムコールが使用されます。しかし、定義が移動したことで、`mksyscall.pl`が生成する`zsyscall_linux_*.go`ファイル内の`Dup2`関数の位置が変更されています。コミットメッセージが指摘するように、`mksyscall.pl`はシンボルをソートしないため、`Dup2`の定義がファイル内で移動した結果、`zsyscall_linux_386.go`などのファイルで`Dup2`のコードブロックが一度削除され、別の場所に再挿入されるという「避けられないコードの移動」が発生しています。これは機能的な変更ではなく、生成コードの構造的な変更に過ぎません。

## コアとなるコードの解説

このコミットのコアとなる変更は、`syscall_linux.go`から`Dup2`の定義を削除し、それを各アーキテクチャ固有の`syscall_linux_GOARCH.go`ファイルに移動したことです。

Goの`syscall`パッケージでは、システムコールをGoの関数として公開するために、特別なコメント構文を使用します。例えば、`//sysnb Dup2(oldfd int, newfd int) (err error)`のような行は、`mksyscall.pl`スクリプトによって解析され、実際のシステムコールを呼び出すためのGoコードが自動生成されます。

`syscall_linux.go`は、すべてのLinuxアーキテクチャに共通のシステムコール定義を保持していました。しかし、`arm64`のような特定のアーキテクチャでは、`Dup2`の代わりに`Dup3`を使用する方が望ましい場合があります。`Dup2`の定義を各アーキテクチャ固有のファイルに移動することで、将来的に`arm64`向けの`syscall_linux_arm64.go`ファイルが追加された際に、そのファイル内で`Dup2`を`SYS_DUP3`として定義できるようになります。

例えば、`arm64`の場合、`syscall_linux_arm64.go`に以下のような行が追加される可能性があります。

```go
//sysnb Dup2(oldfd int, newfd int) (err error) = SYS_DUP3
```

この行は、`mksyscall.pl`に対して、Goの`Dup2`関数が、実際にはLinuxの`SYS_DUP3`システムコールを呼び出すようにコードを生成することを指示します。これにより、`arm64`プラットフォームでは`Dup2`を呼び出しても内部的には`Dup3`が使用されるようになり、`arm64`のシステムコールインターフェースの特性に合わせた柔軟な対応が可能になります。

`zsyscall_linux_*.go`ファイル群は、`mksyscall.pl`によって生成された実際のシステムコールラッパーコードを含んでいます。これらのファイル内の`Dup2`関数の実装は、`RawSyscall`関数を呼び出しています。

```go
func Dup2(oldfd int, newfd int) (err error) {
	_, _, e1 := RawSyscall(SYS_DUP2, uintptr(oldfd), uintptr(newfd), 0)
	if e1 != 0 {
		err = e1
	}
	return
}
```

ここで、`RawSyscall`はGoのランタイムが提供する低レベルな関数で、指定されたシステムコール番号（`SYS_DUP2`など）と引数を受け取り、OSのカーネルにシステムコールを発行します。`e1`はシステムコールが返したエラーコード（`errno`）を表します。

このコミットによって、`Dup2`の定義が移動したことで、`mksyscall.pl`がこれらの`zsyscall`ファイルを再生成する際に、`Dup2`関数のコードブロックがファイル内で物理的に移動しました。これは、`mksyscall.pl`が入力ファイルのシンボルを特定の順序でソートしないため、定義の場所が変わると生成されるコードの順序も変わるという副作用です。機能的には同じコードが生成されますが、差分（diff）にはコードの移動として現れます。

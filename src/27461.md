# [インデックス 27461] ファイルの概要

このコミットは、Goコンパイラの`cmd/compile`における`plan9-amd64`ビルドの問題を修正するものです。具体的には、インデックス付きロード命令のアドレス生成ロジックが誤っていたために発生していたビルドエラーを解消します。

## 元コミット内容

`cmd/compile: fix plan9-amd64 build`

以前のインデックス付きロードを結合するルールは、以下のような誤ったアドレスを生成していました。

```
From: obj.Addr{
    Type:   TYPE_MEM,
    Reg:    REG_CX,
    Name:   NAME_AUTO,
    Offset: 121,
    ...
}
```

これは、`NAME_AUTO`がベースレジスタとして`REG_SP`を意味するにもかかわらず、`Reg`フィールドに`REG_CX`が設定されているため誤りです。`cmd/internal/obj/x86`はこれに関して多くの仮定を置いています。また、以前は余分な`ADDQ SP, CX`命令も生成されており、`SP`からのインデックス付けは既に処理されていました。

この問題に対処するために、この変更リスト（CL）で採用されたアプローチは、代わりに以下のようなアドレスを生成することです。

```
From: obj.Addr{
    Type:   TYPE_MEM,
    Reg:    REG_SP,
    Name:   NAME_AUTO,
    Offset: 121,
    Index:  REG_CX,
    Scale:  1,
}
```

そして、`ADDQ SP, CX`命令を省略します。

このアプローチの欠点は、既存の`MOV[WLQ]loadidx[248]`命令とほぼ同じ機能を持ちながら、異なる`Scale`を持つ新しい`MOV[WLQ]loadidx1`命令を多数追加する必要があることです。

Fixes #15001.

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現としてSSA（Static Single Assignment）形式を使用します。このSSA形式から最終的なアセンブリコードを生成する際に、メモリからのデータロード（読み込み）を効率的に行うための最適化ルールが適用されます。

`plan9-amd64`という特定のターゲットアーキテクチャ（Plan 9オペレーティングシステム上で動作するAMD64プロセッサ）において、インデックス付きロード命令（ベースレジスタとインデックスレジスタを組み合わせてメモリアドレスを計算する命令）の生成に問題がありました。

具体的には、Goコンパイラのバックエンドが生成するアセンブリ命令の構造を定義する`obj.Addr`というデータ構造において、`NAME_AUTO`というフィールドが設定されている場合、これは通常スタックポインタ（`REG_SP`）をベースレジスタとして使用することを意味します。しかし、以前のルールでは、`NAME_AUTO`が設定されているにもかかわらず、ベースレジスタとして`REG_CX`のような別のレジスタが指定されることがありました。これは`cmd/internal/obj/x86`パッケージが持つ仮定（`NAME_AUTO`は`REG_SP`と結びつく）と矛盾し、結果として`plan9-amd64`ビルドが正しく行われない原因となっていました。

さらに、この誤ったアドレス生成に加えて、コンパイラは冗長な`ADDQ SP, CX`命令を生成しており、これはインデックス付けが既に処理されているにもかかわらず、スタックポインタとインデックスレジスタを不必要に加算するものでした。この冗長な命令は、生成されるコードの効率を低下させる可能性がありました。

このコミットは、これらの問題を解決し、`plan9-amd64`ターゲットでのビルドを修正することを目的としています。

## 前提知識の解説

*   **Goコンパイラ (cmd/compile)**: Go言語のソースコードを機械語に変換する公式コンパイラです。複数のステージを経てコードを最適化し、最終的な実行可能ファイルを生成します。
*   **SSA (Static Single Assignment) 形式**: コンパイラ最適化で用いられる中間表現の一つです。各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。GoコンパイラもSSA形式を内部的に使用しています。
*   **obj.Addr**: Goコンパイラの`cmd/internal/obj`パッケージで定義されているデータ構造で、アセンブリ命令のオペランド（アドレス、レジスタ、定数など）を表現します。
    *   `Type`: オペランドのタイプ（例: `TYPE_MEM`はメモリ参照）。
    *   `Reg`: ベースレジスタ。
    *   `Name`: メモリ参照の種類（例: `NAME_AUTO`は自動変数、通常はスタックフレーム内のオフセット）。
    *   `Offset`: オフセット値。
    *   `Index`: インデックスレジスタ。
    *   `Scale`: インデックスレジスタに乗算されるスケールファクタ（1, 2, 4, 8など）。
*   **REG_SP (Stack Pointer Register)**: スタックの最上位アドレスを指すレジスタ。関数呼び出し時のローカル変数や引数へのアクセスに用いられます。
*   **NAME_AUTO**: Goコンパイラにおいて、スタックフレーム上の自動変数（ローカル変数）への参照を示すために使用される`obj.Addr`の`Name`フィールドの値です。`NAME_AUTO`が指定される場合、通常は`REG_SP`がベースレジスタとして暗黙的に期待されます。
*   **インデックス付きアドレッシングモード (Indexed Addressing Mode)**: x86アーキテクチャにおけるメモリアドレッシングモードの一つで、`ベースレジスタ + (インデックスレジスタ * スケール) + オフセット`という形式でメモリアドレスを計算します。これにより、配列要素へのアクセスなどが効率的に行えます。
*   **MOV[WLQ]loadidx[1248]**: GoコンパイラのSSAバックエンドで定義される、インデックス付きロード操作を表す内部命令です。
    *   `MOV`: データ転送命令。
    *   `W`, `L`, `Q`: それぞれWord (2バイト), Long (4バイト), Quad (8バイト) のデータを意味します。
    *   `load`: メモリからレジスタへのロード操作。
    *   `idx`: インデックス付きアドレッシングモードを使用することを示します。
    *   `1`, `2`, `4`, `8`: インデックスレジスタに乗算されるスケールファクタを示します。例えば`loadidx1`はスケール1、`loadidx8`はスケール8です。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおけるメモリロード命令の生成方法の変更にあります。特に、インデックス付きロード命令が`obj.Addr`構造体として表現される際の一貫性と正確性を確保することを目指しています。

以前の実装では、コンパイラはインデックス付きロードを最適化する際に、`obj.Addr`の`Reg`フィールドにインデックスレジスタ（例: `REG_CX`）を設定し、`Name`フィールドに`NAME_AUTO`を設定していました。しかし、`NAME_AUTO`はスタックポインタ（`REG_SP`）をベースレジスタとして暗黙的に期待するため、`Reg: REG_CX`との組み合わせは矛盾を生じさせました。`cmd/internal/obj/x86`パッケージは、この`NAME_AUTO`と`REG_SP`の関連性に強く依存しており、この矛盾が`plan9-amd64`ビルドでの問題を引き起こしていました。

さらに、この誤った`obj.Addr`の生成に加えて、コンパイラは`ADDQ SP, CX`のような冗長な命令を生成していました。これは、インデックスレジスタが既にベースレジスタとして機能しているにもかかわらず、スタックポインタとインデックスレジスタを明示的に加算しようとするものでした。

新しいアプローチでは、この問題を解決するために、`obj.Addr`の表現方法を変更します。
変更後:
```
From: obj.Addr{
    Type:   TYPE_MEM,
    Reg:    REG_SP,    // ベースレジスタはREG_SPに固定
    Name:   NAME_AUTO, // NAME_AUTOと整合
    Offset: 121,
    Index:  REG_CX,    // インデックスレジスタをIndexフィールドに設定
    Scale:  1,         // スケールファクタを設定
}
```
この変更により、`NAME_AUTO`が`REG_SP`と正しく関連付けられ、`cmd/internal/obj/x86`の仮定と一致するようになります。また、インデックスレジスタは`Index`フィールドに明示的に設定され、`Scale`フィールドも適切に設定されます。これにより、冗長な`ADDQ SP, CX`命令の生成が不要になります。

この修正の副作用として、`Scale`が1であるインデックス付きロード操作（例: `MOVQloadidx1`, `MOVLloadidx1`, `MOVWloadidx1`）を表現するための新しいSSAオペレーションを多数導入する必要がありました。これらは既存の`MOV[WLQ]loadidx[248]`（スケール2, 4, 8）と機能的には似ていますが、スケールが異なるため、個別のオペレーションとして定義されることになります。

具体的には、以下のファイルが変更されています。

*   `src/cmd/compile/internal/amd64/ssa.go`: SSA値からアセンブリ命令を生成する`ssaGenValue`関数に、新しい`loadidx1`オペレーション（`OpAMD64MOVQloadidx1`, `OpAMD64MOVLloadidx1`, `OpAMD64MOVWloadidx1`）のハンドリングが追加されています。これらのオペレーションは、`obj.Addr`構造体の`Reg`をベースレジスタ、`Index`をインデックスレジスタとして設定し、`Scale`を1に設定します。
*   `src/cmd/compile/internal/ssa/gen/AMD64.rules`: SSAの書き換えルールが更新され、バイト単位のロードを結合してワード、ロング、クアッドワードのロードを生成する際に、`ADDQ`命令を介してアドレスを計算する代わりに、直接新しい`loadidx1`オペレーションを使用するように変更されています。
*   `src/cmd/compile/internal/ssa/gen/AMD64Ops.go`: 新しい`loadidx1`オペレーション（`MOVWloadidx1`, `MOVLloadidx1`, `MOVQloadidx1`）が定義され、それぞれのアセンブリ命令（`MOVWLZX`, `MOVL`, `MOVQ`）と引数の長さ、レジスタ情報が指定されています。
*   `src/cmd/compile/internal/ssa/opGen.go`: 新しい`loadidx1`オペレーションがSSAオペレーションの列挙型に追加され、`opcodeTable`にそれぞれのオペレーションの詳細（名前、補助タイプ、引数の長さ、アセンブリ命令、レジスタ情報）が登録されています。
*   `src/cmd/compile/internal/ssa/rewriteAMD64.go`: `rewriteValueAMD64_OpAMD64ORL`, `rewriteValueAMD64_OpAMD64ORQ`, `rewriteValueAMD64_OpAMD64ORW`関数内の書き換えルールが変更されています。以前は`ADDQ`オペレーションを使ってベースレジスタとインデックスレジスタを結合し、その結果を`MOVLload`などのオペレーションに渡していましたが、新しいルールでは直接`MOVLloadidx1`, `MOVQloadidx1`, `MOVWloadidx1`オペレーションを生成し、ベースレジスタとインデックスレジスタをそれぞれの引数として渡すようになっています。これにより、`ADDQ`命令の生成が不要になります。

この変更は、GoコンパイラのSSAバックエンドが、より正確で効率的なインデックス付きメモリアクセス命令を生成できるようにするための重要なステップです。

`ssaGenValue`関数に、`OpAMD64MOVQloadidx1`, `OpAMD64MOVLloadidx1`, `OpAMD64MOVWloadidx1`のケースが追加されました。これらのケースでは、`obj.Addr`構造体を構築する際に、`p.From.Reg`にベースレジスタ、`p.From.Index`にインデックスレジスタ、`p.From.Scale`に`1`を設定しています。

```go

    p.From.Index = gc.SSARegNum(v.Args[1]) // インデックスレジスタ

## コアとなるコードの解説

このコミットの主要な変更は、GoコンパイラのSSAバックエンドがインデックス付きメモリアクセスをどのように表現し、アセンブリ命令に変換するかという点に集約されます。

1.  **`obj.Addr`構造体の整合性**: 以前は`NAME_AUTO`が設定されている`obj.Addr`で`Reg`フィールドに`REG_SP`以外のレジスタが設定されるという矛盾がありました。このコミットでは、`obj.Addr`の`Reg`フィールドを`REG_SP`に固定し、インデックスレジスタを`Index`フィールドに移動させることで、`NAME_AUTO`のセマンティクスと`cmd/internal/obj/x86`の期待との整合性を図っています。これにより、アセンブラが正しくアドレスを解釈できるようになります。

2.  **冗長な`ADDQ`命令の排除**: 以前は、ベースレジスタとインデックスレジスタの加算を明示的に行う`ADDQ`命令が生成されていました。しかし、x86アーキテクチャのインデックス付きアドレッシングモードは、この加算をハードウェアレベルでサポートしています。新しいアプローチでは、`obj.Addr`の`Index`フィールドと`Scale`フィールドを適切に設定することで、コンパイラが直接インデックス付きアドレッシングモードを使用するアセンブリ命令を生成できるようになり、冗長な`ADDQ`命令が不要になります。これにより、生成されるコードの命令数が減り、効率が向上します。

3.  **新しい`loadidx1`オペレーションの導入**: `Scale`が1であるインデックス付きロード操作を正確に表現するために、`MOVQloadidx1`, `MOVLloadidx1`, `MOVWloadidx1`といった新しいSSAオペレーションが導入されました。これらは、既存の`loadidx2`, `loadidx4`, `loadidx8`と同様に、特定のスケールファクタを持つインデックス付きロードを表しますが、スケールが1である点が異なります。これにより、コンパイラはより粒度の細かいインデックス付きロードをSSA形式で表現し、最終的なアセンブリコード生成時に適切な命令を選択できるようになります。

4.  **SSA書き換えルールの更新**: `src/cmd/compile/internal/ssa/rewriteAMD64.go`内の書き換えルールは、SSA形式の最適化において非常に重要です。このコミットでは、複数のバイトロードを結合してワード、ロング、クアッドワードのロードを生成する際に、以前は`ADDQ`オペレーションを介してアドレスを計算していましたが、これを新しい`loadidx1`オペレーションに直接変換するように変更しました。これにより、SSA最適化の段階で既にインデックス付きアドレッシングモードの意図が明確になり、より効率的なアセンブリコード生成に繋がります。

これらの変更は、GoコンパイラのバックエンドがAMD64アーキテクチャのインデックス付きアドレッシングモードをより正確かつ効率的に利用できるようにするためのものであり、特に`plan9-amd64`のような特定のターゲット環境でのビルドの安定性と正確性を向上させます。

## 元コミット内容

`cmd/compile: fix plan9-amd64 build`

以前のインデックス付きロードを結合するルールは、以下のような誤ったアドレスを生成していました。

```
From: obj.Addr{
    Type:   TYPE_MEM,
    Reg:    REG_CX,
    Name:   NAME_AUTO,
    Offset: 121,
    ...
}
```

これは、`NAME_AUTO`がベースレジスタとして`REG_SP`を意味するにもかかわらず、`Reg`フィールドに`REG_CX`が設定されているため誤りです。`cmd/internal/obj/x86`はこれに関して多くの仮定を置いています。また、以前は余分な`ADDQ SP, CX`命令も生成されており、`SP`からのインデックス付けは既に処理されていました。

この問題に対処するために、この変更リスト（CL）で採用されたアプローチは、代わりに以下のようなアドレスを生成することです。

```
From: obj.Addr{
    Type:   TYPE_MEM,
    Reg:    REG_SP,
    Name:   NAME_AUTO,
    Offset: 121,
    Index:  REG_CX,
    Scale:  1,
}
```

そして、`ADDQ SP, CX`命令を省略します。

このアプローチの欠点は、既存の`MOV[WLQ]loadidx[248]`命令とほぼ同じ機能を持ちながら、異なる`Scale`を持つ新しい`MOV[WLQ]loadidx1`命令を多数追加する必要があることです。

Fixes #15001.

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現としてSSA（Static Single Assignment）形式を使用します。このSSA形式から最終的なアセンブリコードを生成する際に、メモリからのデータロード（読み込み）を効率的に行うための最適化ルールが適用されます。

`plan9-amd64`という特定のターゲットアーキテクチャ（Plan 9オペレーティングシステム上で動作するAMD64プロセッサ）において、インデックス付きロード命令（ベースレジスタとインデックスレジスタを組み合わせてメモリアドレスを計算する命令）の生成に問題がありました。

具体的には、Goコンパイラのバックエンドが生成するアセンブリ命令の構造を定義する`obj.Addr`というデータ構造において、`NAME_AUTO`というフィールドが設定されている場合、これは通常スタックポインタ（`REG_SP`）をベースレジスタとして使用することを意味します。しかし、以前のルールでは、`NAME_AUTO`が設定されているにもかかわらず、ベースレジスタとして`REG_CX`のような別のレジスタが指定されることがありました。これは`cmd/internal/obj/x86`パッケージが持つ仮定（`NAME_AUTO`は`REG_SP`と結びつく）と矛盾し、結果として`plan9-amd64`ビルドでの問題を引き起こしていました。

さらに、この誤ったアドレス生成に加えて、コンパイラは冗長な`ADDQ SP, CX`命令を生成しており、これはインデックス付けが既に処理されているにもかかわらず、スタックポインタとインデックスレジスタを不必要に加算するものでした。この冗長な命令は、生成されるコードの効率を低下させる可能性がありました。

このコミットは、これらの問題を解決し、`plan9-amd64`ターゲットでのビルドを修正することを目的としています。

## 前提知識の解説

*   **Goコンパイラ (cmd/compile)**: Go言語のソースコードを機械語に変換する公式コンパイラです。複数のステージを経てコードを最適化し、最終的な実行可能ファイルを生成します。
*   **SSA (Static Single Assignment) 形式**: コンパイラ最適化で用いられる中間表現の一つです。各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。GoコンパイラもSSA形式を内部的に使用しています。
*   **obj.Addr**: Goコンパイラの`cmd/internal/obj`パッケージで定義されているデータ構造で、アセンブリ命令のオペランド（アドレス、レジスタ、定数など）を表現します。
    *   `Type`: オペランドのタイプ（例: `TYPE_MEM`はメモリ参照）。
    *   `Reg`: ベースレジスタ。
    *   `Name`: メモリ参照の種類（例: `NAME_AUTO`は自動変数、通常はスタックフレーム内のオフセット）。
    *   `Offset`: オフセット値。
    *   `Index`: インデックスレジスタ。
    *   `Scale`: インデックスレジスタに乗算されるスケールファクタ（1, 2, 4, 8など）。
*   **REG_SP (Stack Pointer Register)**: スタックの最上位アドレスを指すレジスタ。関数呼び出し時のローカル変数や引数へのアクセスに用いられます。
*   **NAME_AUTO**: Goコンパイラにおいて、スタックフレーム上の自動変数（ローカル変数）への参照を示すために使用される`obj.Addr`の`Name`フィールドの値です。`NAME_AUTO`が指定される場合、通常は`REG_SP`がベースレジスタとして暗黙的に期待されます。
*   **インデックス付きアドレッシングモード (Indexed Addressing Mode)**: x86アーキテクチャにおけるメモリアドレッシングモードの一つで、`ベースレジスタ + (インデックスレジスタ * スケール) + オフセット`という形式でメモリアドレスを計算します。これにより、配列要素へのアクセスなどが効率的に行えます。
*   **MOV[WLQ]loadidx[1248]**: GoコンパイラのSSAバックエンドで定義される、インデックス付きロード操作を表す内部命令です。
    *   `MOV`: データ転送命令。
    *   `W`, `L`, `Q`: それぞれWord (2バイト), Long (4バイト), Quad (8バイト) のデータを意味します。
    *   `load`: メモリからレジスタへのロード操作。
    *   `idx`: インデックス付きアドレッシングモードを使用することを示します。
    *   `1`, `2`, `4`, `8`: インデックスレジスタに乗算されるスケールファクタを示します。例えば`loadidx1`はスケール1、`loadidx8`はスケール8です。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおけるメモリロード命令の生成方法の変更にあります。特に、インデックス付きロード命令が`obj.Addr`構造体として表現される際の一貫性と正確性を確保することを目指しています。

以前の実装では、コンパイラはインデックス付きロードを最適化する際に、`obj.Addr`の`Reg`フィールドにインデックスレジスタ（例: `REG_CX`）を設定し、`Name`フィールドに`NAME_AUTO`を設定していました。しかし、`NAME_AUTO`はスタックポインタ（`REG_SP`）をベースレジスタとして暗黙的に期待するため、`Reg: REG_CX`との組み合わせは矛盾を生じさせました。`cmd/internal/obj/x86`パッケージは、この`NAME_AUTO`と`REG_SP`の関連性に強く依存しており、この矛盾が`plan9-amd64`ビルドでの問題を引き起こしていました。

さらに、この誤った`obj.Addr`の生成に加えて、コンパイラは`ADDQ SP, CX`のような冗長な命令を生成していました。これは、インデックスレジスタが既にベースレジスタとして機能しているにもかかわらず、スタックポインタとインデックスレジスタを明示的に加算しようとするものでした。

新しいアプローチでは、この問題を解決するために、`obj.Addr`の表現方法を変更します。
変更後:
```
From: obj.Addr{
    Type:   TYPE_MEM,
    Reg:    REG_SP,    // ベースレジスタはREG_SPに固定
    Name:   NAME_AUTO, // NAME_AUTOと整合
    Offset: 121,
    Index:  REG_CX,    // インデックスレジスタをIndexフィールドに設定
    Scale:  1,         // スケールファクタを設定
}
```
この変更により、`NAME_AUTO`が`REG_SP`と正しく関連付けられ、`cmd/internal/obj/x86`の仮定と一致するようになります。また、インデックスレジスタは`Index`フィールドに明示的に設定され、`Scale`フィールドも適切に設定されます。これにより、冗長な`ADDQ SP, CX`命令の生成が不要になります。

この修正の副作用として、`Scale`が1であるインデックス付きロード操作（例: `MOVQloadidx1`, `MOVLloadidx1`, `MOVWloadidx1`）を表現するための新しいSSAオペレーションを多数導入する必要がありました。これらは既存の`MOV[WLQ]loadidx[248]`（スケール2, 4, 8）と機能的には似ていますが、スケールが異なるため、個別のオペレーションとして定義されることになります。

具体的には、以下のファイルが変更されています。

*   `src/cmd/compile/internal/amd64/ssa.go`: SSA値からアセンブリ命令を生成する`ssaGenValue`関数に、新しい`loadidx1`オペレーション（`OpAMD64MOVQloadidx1`, `OpAMD64MOVLloadidx1`, `OpAMD64MOVWloadidx1`）のハンドリングが追加されています。これらのオペレーションは、`obj.Addr`構造体の`Reg`をベースレジスタ、`Index`をインデックスレジスタとして設定し、`Scale`を1に設定します。
*   `src/cmd/compile/internal/ssa/gen/AMD64.rules`: SSAの書き換えルールが更新され、バイト単位のロードを結合してワード、ロング、クアッドワードのロードを生成する際に、`ADDQ`命令を介してアドレスを計算する代わりに、直接新しい`loadidx1`オペレーションを使用するように変更されています。
*   `src/cmd/compile/internal/ssa/gen/AMD64Ops.go`: 新しい`loadidx1`オペレーション（`MOVWloadidx1`, `MOVLloadidx1`, `MOVQloadidx1`）が定義され、それぞれのアセンブリ命令（`MOVWLZX`, `MOVL`, `MOVQ`）と引数の長さ、レジスタ情報が指定されています。
*   `src/cmd/compile/internal/ssa/opGen.go`: 新しい`loadidx1`オペレーションがSSAオペレーションの列挙型に追加され、`opcodeTable`にそれぞれのオペレーションの詳細（名前、補助タイプ、引数の長さ、アセンブリ命令、レジスタ情報）が登録されています。
*   `src/cmd/compile/internal/ssa/rewriteAMD64.go`: `rewriteValueAMD64_OpAMD64ORL`, `rewriteValueAMD64_OpAMD64ORQ`, `rewriteValueAMD64_OpAMD64ORW`関数内の書き換えルールが変更されています。以前は`ADDQ`オペレーションを使ってベースレジスタとインデックスレジスタを結合し、その結果を`MOVLload`などのオペレーションに渡していましたが、新しいルールでは直接`MOVLloadidx1`, `MOVQloadidx1`, `MOVWloadidx1`オペレーションを生成し、ベースレジスタとインデックスレジスタをそれぞれの引数として渡すようになっています。これにより、`ADDQ`命令の生成が不要になります。

この変更は、GoコンパイラのSSAバックエンドが、より正確で効率的なインデックス付きメモリアクセス命令を生成できるようにするための重要なステップです。

## コアとなるコードの変更箇所

### `src/cmd/compile/internal/amd64/ssa.go`

`ssaGenValue`関数に、`OpAMD64MOVQloadidx1`, `OpAMD64MOVLloadidx1`, `OpAMD64MOVWloadidx1`のケースが追加されました。これらのケースでは、`obj.Addr`構造体を構築する際に、`p.From.Reg`にベースレジスタ、`p.From.Index`にインデックスレジスタ、`p.From.Scale`に`1`を設定しています。

```go
// 追加された部分の例 (MOVQloadidx1):
case ssa.OpAMD64MOVQloadidx1:
    p := gc.Prog(v.Op.Asm())
    p.From.Type = obj.TYPE_MEM
    p.From.Reg = gc.SSARegNum(v.Args[0]) // ベースレジスタ
    gc.AddAux(&p.From, v)
    p.From.Scale = 1
    p.From.Index = gc.SSARegNum(v.Args[1]) // インデックスレジスタ
    p.To.Type = obj.TYPE_REG
    p.To.Reg = gc.SSARegNum(v)
```

### `src/cmd/compile/internal/ssa/gen/AMD64.rules`

バイトロードを結合してより大きなロードを生成するルールが変更されました。`ADDQ`を介してアドレスを計算する代わりに、直接`MOVWloadidx1`, `MOVLloadidx1`, `MOVQloadidx1`を使用するように変更されています。

```diff
-    (SHLWconst [8]  (MOVBloadidx1 [i+1] {s} p idx mem))) -> @x.Block (MOVWload [i] {s} (ADDQ <p.Type> p idx) mem)

## コアとなるコードの解説

このコミットの主要な変更は、GoコンパイラのSSAバックエンドがインデックス付きメモリアクセスをどのように表現し、アセンブリ命令に変換するかという点に集約されます。

1.  **`obj.Addr`構造体の整合性**: 以前は`NAME_AUTO`が設定されている`obj.Addr`で`Reg`フィールドに`REG_SP`以外のレジスタが設定されるという矛盾がありました。このコミットでは、`obj.Addr`の`Reg`フィールドを`REG_SP`に固定し、インデックスレジスタを`Index`フィールドに移動させることで、`NAME_AUTO`のセマンティクスと`cmd/internal/obj/x86`の期待との整合性を図っています。これにより、アセンブラが正しくアドレスを解釈できるようになります。

2.  **冗長な`ADDQ`命令の排除**: 以前は、ベースレジスタとインデックスレジスタの加算を明示的に行う`ADDQ`命令が生成されていました。しかし、x86アーキテクチャのインデックス付きアドレッシングモードは、この加算をハードウェアレベルでサポートしています。新しいアプローチでは、`obj.Addr`の`Index`フィールドと`Scale`フィールドを適切に設定することで、コンパイラが直接インデックス付きアドレッシングモードを使用するアセンブリ命令を生成できるようになり、冗長な`ADDQ`命令が不要になります。これにより、生成されるコードの命令数が減り、効率が向上します。

3.  **新しい`loadidx1`オペレーションの導入**: `Scale`が1であるインデックス付きロード操作を正確に表現するために、`MOVQloadidx1`, `MOVLloadidx1`, `MOVWloadidx1`といった新しいSSAオペレーションが導入されました。これらは、既存の`loadidx2`, `loadidx4`, `loadidx8`と同様に、特定のスケールファクタを持つインデックス付きロードを表しますが、スケールが1である点が異なります。これにより、コンパイラはより粒度の細かいインデックス付きロードをSSA形式で表現し、最終的なアセンブリコード生成時に適切な命令を選択できるようになります。

4.  **SSA書き換えルールの更新**: `src/cmd/compile/internal/ssa/rewriteAMD64.go`内の書き換えルールは、SSA形式の最適化において非常に重要です。このコミットでは、複数のバイトロードを結合してワード、ロング、クアッドワードのロードを生成する際に、以前は`ADDQ`オペレーションを介してアドレスを計算していましたが、これを新しい`loadidx1`オペレーションに直接変換するように変更しました。これにより、SSA最適化の段階で既にインデックス付きアドレッシングモードの意図が明確になり、より効率的なアセンブリコード生成に繋がります。

これらの変更は、GoコンパイラのバックエンドがAMD64アーキテクチャのインデックス付きアドレッシングモードをより正確かつ効率的に利用できるようにするためのものであり、特に`plan9-amd64`のような特定のターゲット環境でのビルドの安定性と正確性を向上させます。

## 変更の背景

このコミットは、Goランタイムが生成するトレースバック（スタックトレース）の表示におけるバグを修正するために行われました。具体的には、トレースバックの書式設定を行う`printf`関数内で、`%S`というフォーマット指定子を使用する際に、引数ポインタが適切に進まないという問題がありました。

この問題が発生すると、トレースバックの出力が不正確になったり、破損したりする可能性がありました。例えば、`%S`がソースファイル名や行番号などの情報を表示するために使われる場合、ポインタが十分に移動しないと、その後のトレースバック情報が誤って解釈されたり、重複して表示されたり、あるいは全く表示されなかったりする可能性がありました。これにより、デバッグ作業が困難になるという実用上の問題が生じていました。

この修正は、トレースバックの正確性と信頼性を確保し、開発者が問題の原因を特定しやすくするために不可欠でした。

## 前提知識の解説

### トレースバック（スタックトレース）

トレースバック、またはスタックトレースとは、プログラムがクラッシュしたり、エラーが発生したりした際に、その時点での関数呼び出しの履歴（コールスタック）を表示するものです。これにより、どの関数がどの関数を呼び出し、最終的にどこで問題が発生したのかを追跡することができます。デバッグにおいて非常に重要な情報源となります。

### `printf`関数とフォーマット指定子

`printf`は、C言語系のプログラミング言語で広く使われる、書式付き出力を行うための関数です。第一引数にフォーマット文字列を取り、その後に可変個の引数を取ります。フォーマット文字列内の`%`で始まるシーケンス（例: `%d`, `%s`, `%p`）は「フォーマット指定子」と呼ばれ、対応する引数を特定の形式で出力するように指示します。

*   `%d`: 整数を10進数で出力
*   `%s`: 文字列を出力
*   `%p`: ポインタのアドレスを出力

Goランタイムの内部でも、デバッグ情報やエラーメッセージの出力に類似の書式設定メカニズムが使用されています。

### `%S`フォーマット指定子

このコミットで言及されている`%S`は、Goランタイム内部の`printf`実装におけるカスタムフォーマット指定子と考えられます。一般的なC標準ライブラリの`printf`には`%S`という指定子はありません。Goのトレースバックでは、ソースファイル名や行番号、関数名などの情報が表示されますが、`%S`はこれらのうち、特に「ポインタアラインされた、しかしより大きなデータ」（`pointer-aligned but bigger`）を扱うために使われていたと推測されます。これは、例えばGoの`string`型のように、ポインタと長さの情報を持つ構造体などを指す可能性があります。

### ポインタの概念とポインタの「進み」

コンピュータのメモリは、連続したバイトの並びとして考えることができます。各バイトには一意のアドレス（番地）が割り当てられています。ポインタとは、このメモリのアドレスを格納する変数です。

`printf`のような可変引数関数では、引数は通常スタックに積まれます。関数内部では、これらの引数にアクセスするためにポインタが使用されます。ある引数を読み取った後、次の引数を読み取るためには、ポインタを現在の引数のサイズ分だけ「進める」必要があります。例えば、4バイトの整数を読み取った後、ポインタを4バイト進めれば、次の引数の先頭に到達できます。

このコミットの文脈では、`%S`が処理するデータ型が、通常のポインタや文字列（`%p`や`%s`で扱われるもの）よりも複雑な構造を持っていたため、ポインタの進め方が不適切だった、という問題が示唆されています。

### `uintptr`と`String`型

*   `uintptr`: Goにおける`uintptr`型は、ポインタを保持するのに十分な大きさの符号なし整数型です。これは、ポインタ演算を行う際に使用されることがあります。
*   `String`: Goの組み込み`string`型は、内部的にはデータへのポインタと文字列の長さのペアとして表現されます。このコミットの文脈での`String`は、Goランタイム内部で定義された、この文字列の内部表現に対応する構造体を指している可能性が高いです。

## 技術的詳細

問題の核心は、`src/runtime/print.c`内の`printf`関数における`%S`フォーマット指定子の処理にありました。元のコードでは、`%p`（ポインタ）や`%s`（文字列）と同じ`case`ブロック内で`%S`も処理されていました。このブロックでは、引数ポインタ`arg`を`sizeof(uintptr)`（ポインタのサイズ）分だけ進めて、次の引数`narg`を計算していました。

しかし、`%S`が意図していたのは、単なるポインタや文字列よりも「ポインタアラインされた、しかしより大きな」データ型（コメントでは`pointer-aligned but bigger`と説明されています）を扱うことでした。Goの`string`型のように、ポインタと長さを組み合わせた構造体は、`sizeof(uintptr)`よりも大きなサイズを持つ可能性があります。

したがって、`%S`が処理する引数の実際のサイズが`sizeof(uintptr)`よりも大きい場合、ポインタを`sizeof(uintptr)`分しか進めないと、次の引数の読み取り位置がずれてしまい、結果としてトレースバックの出力が破損するというバグが発生していました。

このコミットによる修正は、`%S`を`%p`や`%s`から分離し、専用の`case 'S'`ブロックを設けることでこの問題を解決しました。新しい`%S`の処理では、引数ポインタ`arg`を`sizeof(String)`（Goランタイム内部の`String`構造体のサイズ）分だけ進めるように変更されました。これにより、`%S`が処理するデータ型の実際のサイズに合わせてポインタが正確に進むようになり、トレースバックの出力が正しく行われるようになりました。

また、`if(sizeof(uintptr) == 8 && ((uint32)(uint64)arg)&4)`という条件分岐は、64ビットシステムにおいてポインタが4バイト境界にアラインされていない場合に、ポインタを4バイト進めてアラインメントを調整するためのロジックです。これは既存の`%p`や`%s`の処理にも存在し、`%S`の新しい処理にも引き継がれています。これは、特定のアーキテクチャやコンパイラの挙動に対応するための低レベルな最適化または互換性維持のためのコードです。

## コアとなるコードの解説

この変更は、`src/runtime/print.c`ファイル内の`printf`関数の実装の一部です。

1.  **変更前**:
    ```c
    	case 'p':	// pointer-sized
    	case 's':
    	case 'S':
    		if(sizeof(uintptr) == 8 && ((uint32)(uint64)arg)&4)
    			arg += 4;
    		narg = arg + sizeof(uintptr);
    		break;
    ```
    この部分では、`%p`（ポインタ）、`%s`（文字列）、そして`%S`の3つのフォーマット指定子が同じロジックで処理されていました。引数ポインタ`arg`を`sizeof(uintptr)`（ポインタのサイズ、通常は4バイトまたは8バイト）分だけ進めて、次の引数`narg`を計算していました。これは、`%p`や`%s`のような単純なポインタや文字列ポインタには適切でしたが、`%S`が意図する「より大きな」データ型には不十分でした。

2.  **変更後**:
    ```c
    	case 'p':	// pointer-sized
    	case 's':
    		if(sizeof(uintptr) == 8 && ((uint32)(uint64)arg)&4)
    			arg += 4;
    		narg = arg + sizeof(uintptr);
    		break;
    +	case 'S':	// pointer-aligned but bigger
    +		if(sizeof(uintptr) == 8 && ((uint32)(uint64)arg)&4)
    +			arg += 4;
    +		narg = arg + sizeof(String);
    +		break;
    ```
    *   `%S`が`case 'p':`と`case 's':`のブロックから削除され、独立した`case 'S':`ブロックが新設されました。
    *   新しい`case 'S':`ブロックでは、`narg = arg + sizeof(String);`という行が追加されました。これは、引数ポインタ`arg`を`String`型のサイズ分だけ進めることを意味します。Goランタイム内部の`String`型は、ポインタと長さの情報を保持する構造体であり、そのサイズは`uintptr`のサイズよりも大きい可能性があります。
    *   `if(sizeof(uintptr) == 8 && ((uint32)(uint64)arg)&4)`の行は、64ビットシステムでポインタのアラインメントを調整するための既存のロジックであり、これは`%S`の新しい処理にもそのまま引き継がれています。

この変更により、`%S`が処理する引数の実際のサイズ（`sizeof(String)`）に基づいてポインタが正確に進むようになり、トレースバックの出力が正しく行われるようになりました。

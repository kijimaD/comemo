`net/http` パッケージにおいて、HTTP/2トランスポートが自動gzip解凍を正しく行うことを検証するテストを追加し、`h2_bundle.go` を `x/net/http2` からの修正で更新します。これにより、Issue #13298 を修正し、Issue #6891 を更新します。

## 変更の背景

このコミットの主な背景には、Goの `net/http` クライアントがHTTP/2プロトコルを使用する際に、サーバーから送られてくるgzip圧縮された応答を透過的に（自動的に）解凍する際の挙動に関する問題がありました。

具体的には、以下の点が課題となっていました。

1.  **サーバーからの非要求Gzip応答**: クライアントが `Accept-Encoding: gzip` ヘッダーを明示的に送信していなくても、一部のサーバーは応答をgzip圧縮して送り返すことがあります。この場合、クライアントは透過的にその応答を解凍し、アプリケーション層には非圧縮データとして提供することが期待されます。Issue #13298 はこのシナリオに関連している可能性が高いです（コミット内のコメント `// Some hosts send gzip even if you don't ask for it; see golang.org/issue/13298` から示唆されます）。
2.  **HTTP/2におけるGzip処理の整合性**: HTTP/1.1とHTTP/2の両方で、gzip圧縮の自動処理が同様に、かつ正しく機能することが重要です。特にHTTP/2は新しいプロトコルであるため、その実装において既存のHTTP/1.1の挙動との整合性を保つ必要がありました。
3.  **テストカバレッジの不足**: 既存のテストでは、HTTP/2トランスポートにおける自動gzip解凍の特定のケース（特にクライアントが `Accept-Encoding` を送らない場合）が十分にカバーされていなかった可能性があります。

このコミットは、これらの課題に対処し、HTTP/2クライアントがgzip圧縮された応答をより堅牢に処理できるようにすることを目的としています。

## 前提知識の解説

### HTTP/1.1 と HTTP/2

-   **HTTP/1.1**: 広く使われてきたWebの基盤プロトコル。リクエスト/レスポンスごとにTCPコネクションを確立し、ヘッダーはテキスト形式で送られます。HOLブロッキング（Head-of-Line Blocking）の問題や、ヘッダーの冗長性などが課題でした。
-   **HTTP/2**: HTTP/1.1のパフォーマンス課題を解決するために開発された新しいプロトコル。主な特徴は以下の通りです。
    -   **バイナリフレーミング層**: ヘッダーとボディがバイナリ形式のフレームに分割されて送られるため、解析が効率的です。
    -   **多重化 (Multiplexing)**: 一つのTCPコネクション上で複数のリクエストとレスポンスを同時に送受信できます。これによりHOLブロッキングが解消されます。
    -   **ヘッダー圧縮 (HPACK)**: 繰り返し送られるヘッダー情報を効率的に圧縮し、帯域幅の使用量を削減します。
    -   **サーバープッシュ**: クライアントが要求する前に、サーバーがリソースをプッシュできます。

### Gzip 圧縮

-   **`Content-Encoding: gzip`**: HTTPレスポンスヘッダーの一つで、メッセージボディがgzip形式で圧縮されていることを示します。これにより、転送されるデータ量を削減し、Webページのロード時間を短縮できます。
-   **`Accept-Encoding` ヘッダー**: HTTPリクエストヘッダーの一つで、クライアントが受け入れ可能なコンテンツエンコーディング（例: `gzip`, `deflate`, `br` など）をサーバーに伝えます。クライアントがこのヘッダーを送信することで、サーバーはクライアントがサポートする圧縮形式で応答を返すことができます。
-   **自動解凍 (Automatic Decompression)**: 多くのHTTPクライアントライブラリ（Goの `net/http` を含む）は、サーバーから `Content-Encoding: gzip` ヘッダーを持つ応答を受け取った場合、クライアントが `Accept-Encoding: gzip` を送っていなくても、透過的にその応答を解凍してアプリケーションに非圧縮データとして提供する機能を持っています。これは、サーバーが常に `Accept-Encoding` ヘッダーを尊重するとは限らないため、クライアント側の堅牢性を高めるために重要です。

### Go の `net/http` パッケージ

-   Go言語の標準ライブラリであり、HTTPクライアントとサーバーの実装を提供します。
-   **`http.Client`**: HTTPリクエストを送信し、HTTPレスポンスを受信するクライアントを表します。
-   **`http.Transport`**: `http.Client` の内部で実際にネットワーク通信を行うコンポーネントです。TCPコネクションの確立、TLSハンドシェイク、HTTP/1.1またはHTTP/2プロトコルの処理などを担当します。このコミットの変更は、特にHTTP/2プロトコルを扱う `http2Transport` に関連しています。
-   **`http.Request`**: HTTPリクエストを表す構造体。
-   **`http.Response`**: HTTPレスポンスを表す構造体。

## 技術的詳細

このコミットは、主に `net/http` パッケージのHTTP/2トランスポートが、サーバーから送られてくるgzip圧縮された応答を透過的に処理するメカニズムを改善し、その動作を検証するテストを追加しています。

### `src/net/http/h2_bundle.go` の変更

1.  **`http2Transport` 構造体への `DisableCompression` フィールドの追加**:
    ```go
    type http2Transport struct {
        // ... 既存のフィールド ...

        // DisableCompression, if true, prevents the Transport from
        // requesting compression with an an "Accept-Encoding: gzip"
        // request header when the Request contains no existing
        // Accept-Encoding value. If the Transport requests gzip on
        // its own and gets a gzipped response, it's transparently
        // decoded in the Response.Body. However, if the user
        // explicitly requested gzip it is not automatically
        // uncompressed.
        DisableCompression bool

        connPoolOnce  sync.Once
        connPoolOrDef http2ClientConnPool // non-nil version of ConnPool
    }
    ```
    -   `DisableCompression` は、`http.Transport` の設定と同様に、HTTP/2トランスポートが自動的に `Accept-Encoding: gzip` ヘッダーをリクエストに追加するのを防ぐためのフラグです。
    -   このフラグが `false` の場合（デフォルト）、トランスポートは自動的に `Accept-Encoding: gzip` を追加します。
    -   重要なのは、トランスポートが独自にgzipをリクエストしてgzip圧縮された応答を受け取った場合、`Response.Body` で透過的に解凍される点です。しかし、ユーザーが明示的にgzipをリクエストした場合（つまり、`Request` に `Accept-Encoding: gzip` ヘッダーを自分で追加した場合）、自動解凍は行われません。これは、ユーザーが自分で解凍を管理したい可能性があるためです。

2.  **`http2clientStream` 構造体への `requestedGzip` フィールドの追加**:
    ```go
    type http2clientStream struct {
        // ... 既存のフィールド ...
        requestedGzip bool
    }
    ```
    -   このブール値のフィールドは、現在のストリームのリクエストに対して、トランスポートが自動的に `Accept-Encoding: gzip` ヘッダーを追加したかどうかを追跡します。これにより、応答がgzip圧縮されている場合に、透過的な解凍を適用すべきかどうかを判断できます。

3.  **`RoundTrip` メソッドでの `Accept-Encoding: gzip` ヘッダーの自動追加ロジック**:
    ```go
    func (cc *http2ClientConn) RoundTrip(req *Request) (*Response, error) {
        // ...
        if !cc.t.disableCompression() &&
            req.Header.Get("Accept-Encoding") == "" &&
            req.Header.Get("Range") == "" &&
            req.Method != "HEAD" {

            cs.requestedGzip = true
        }
        // ...
        hdrs := cc.encodeHeaders(req, cs.requestedGzip)
        // ...
    }
    ```
    -   `http2Transport` の `DisableCompression` が `false` で、かつリクエストに `Accept-Encoding` ヘッダーが設定されておらず、`Range` ヘッダーがなく、メソッドが `HEAD` でない場合に、`cs.requestedGzip` を `true` に設定します。
    -   これにより、後続のヘッダーエンコード処理で `Accept-Encoding: gzip` が自動的に追加されるようになります。`Range` ヘッダーや `HEAD` メソッドの場合は、部分的なコンテンツ取得やボディなしのリクエストであるため、gzip圧縮は通常適用されません。

4.  **`encodeHeaders` メソッドのシグネチャ変更と `addGzipHeader` パラメータの利用**:
    ```go
    // requires cc.mu be held.
    func (cc *http2ClientConn) encodeHeaders(req *Request, addGzipHeader bool) []byte {
        // ...
        if addGzipHeader {
            cc.writeHeader("accept-encoding", "gzip")
        }
        return cc.hbuf.Bytes()
    }
    ```
    -   `encodeHeaders` メソッドは、リクエストヘッダーをHTTP/2形式にエンコードする役割を担います。
    -   新しい `addGzipHeader` パラメータに基づいて、`Accept-Encoding: gzip` ヘッダーをリクエストに追加するかどうかを決定します。これは、前述の `RoundTrip` メソッドで設定された `cs.requestedGzip` の値によって制御されます。

5.  **応答ヘッダー処理 (`processHeaderBlockFragment`) における `Content-Encoding: gzip` の検出と透過的な解凍の適用**:
    ```go
    func (rl *http2clientConnReadLoop) processHeaderBlockFragment(frag []byte, strea *http2clientStream) {
        // ...
        if cs.requestedGzip && res.Header.Get("Content-Encoding") == "gzip" {
            res.Header.Del("Content-Encoding")
            res.Header.Del("Content-Length")
            res.ContentLength = -1
            res.Body = &http2gzipReader{body: res.Body}
        }
        // ...
    }
    ```
    -   サーバーからの応答ヘッダーを処理する際に、もしクライアントが `Accept-Encoding: gzip` を自動的にリクエストしており (`cs.requestedGzip` が `true`)、かつ応答が `Content-Encoding: gzip` を含んでいる場合、以下の処理が行われます。
        -   `Content-Encoding` ヘッダーと `Content-Length` ヘッダーが応答から削除されます。これは、アプリケーション層には非圧縮データとして提供するため、これらのヘッダーが誤解を招かないようにするためです。
        -   `Content-Length` は `-1` に設定されます。これは、ボディがチャンク転送されているか、長さが不明であることを示します。gzip解凍後のサイズは元のサイズと異なるため、元の `Content-Length` は無効になります。
        -   `res.Body` がカスタムの `http2gzipReader` でラップされます。これにより、アプリケーションが `Response.Body` から読み取る際に、透過的にgzip解凍が行われるようになります。

6.  **`http2gzipReader` 構造体とメソッド**:
    ```go
    // gzipReader wraps a response body so it can lazily
    // call gzip.NewReader on the first call to Read
    type http2gzipReader struct {
        body io.ReadCloser // underlying Response.Body
        zr   io.Reader     // lazily-initialized gzip reader
    }

    func (gz *http2gzipReader) Read(p []byte) (n int, err error) {
        if gz.zr == nil {
            gz.zr, err = gzip.NewReader(gz.body)
            if err != nil {
                return 0, err
            }
        }
        return gz.zr.Read(p)
    }

    func (gz *http2gzipReader) Close() error {
        return gz.body.Close()
    }
    ```
    -   この構造体は、元の `Response.Body` をラップし、`io.Reader` インターフェースを満たします。
    -   `Read` メソッドが初めて呼び出されたときに、`gzip.NewReader` を使用して実際のgzip解凍リーダー (`gz.zr`) を遅延初期化します。これにより、必要になるまで解凍処理が開始されません。
    -   `Close` メソッドは、ラップされた元のボディの `Close` メソッドを呼び出します。

    ```go
    // Verify that both our HTTP/1 and HTTP/2 request and auto-decompress gzip.
    // Some hosts send gzip even if you don't ask for it; see golang.org/issue/13298
    func TestH12_AutoGzip(t *testing.T) {
        h12Compare{
            Handler: func(w ResponseWriter, r *Request) {
                if ae := r.Header.Get("Accept-Encoding"); ae != "gzip" {
                    t.Errorf("%s Accept-Encoding = %q; want gzip", r.Proto, ae)
                }
                w.Header().Set("Content-Encoding", "gzip")
                gz := gzip.NewWriter(w)

            },
        }.run(t)
    }
    ```
    -   このテストは、HTTP/1とHTTP/2の両方のクライアントが、自動的に `Accept-Encoding: gzip` をリクエストし、サーバーから `Content-Encoding: gzip` で返された応答を透過的に解凍できることを検証します。
    -   `h12Compare` は、同じハンドラーに対してHTTP/1とHTTP/2の両方でリクエストを送信し、その応答を比較するユーティリティです。
    -   `Handler` 関数内では、以下のことを行います。
        -   リクエストの `Accept-Encoding` ヘッダーが `gzip` であることを確認します。これは、クライアントが自動的にこのヘッダーを追加したことを検証します。
        -   応答に `Content-Encoding: gzip` ヘッダーを設定します。
        -   `gzip.NewWriter` を使用して、実際にgzip圧縮されたコンテンツを応答ボディに書き込みます。
    -   `h12Compare` の `run` メソッドは、クライアントが受け取った応答ボディが、圧縮されていない元の文字列と一致するかどうかを検証します。これにより、透過的な解凍が正しく行われたことを確認できます。

## 変更の背景

このコミットの主な背景には、Goの `net/http` クライアントがHTTP/2プロトコルを使用する際に、サーバーから送られてくるgzip圧縮された応答を透過的に処理する際の挙動に関する問題がありました。

具体的には、以下の点が課題となっていました。

1.  **サーバーからの非要求Gzip応答**: クライアントが `Accept-Encoding: gzip` ヘッダーを明示的に送信していなくても、一部のサーバーは応答をgzip圧縮して送り返すことがあります。この場合、クライアントは透過的にその応答を解凍し、アプリケーション層には非圧縮データとして提供することが期待されます。Issue #13298 はこのシナリオに関連している可能性が高いです（コミット内のコメント `// Some hosts send gzip even if you don't ask for it; see golang.org/issue/13298` から示唆されます）。
2.  **HTTP/2におけるGzip処理の整合性**: HTTP/1.1とHTTP/2の両方で、gzip圧縮の自動処理が同様に、かつ正しく機能することが重要です。特にHTTP/2は新しいプロトコルであるため、その実装において既存のHTTP/1.1の挙動との整合性を保つ必要がありました。
3.  **テストカバレッジの不足**: 既存のテストでは、HTTP/2トランスポートにおける自動gzip解凍の特定のケース（特にクライアントが `Accept-Encoding` を送らない場合）が十分にカバーされていなかった可能性があります。

## 前提知識の解説

### HTTP/1.1 と HTTP/2

-   **HTTP/1.1**: 広く使われてきたWebの基盤プロトコル。リクエスト/レスポンスごとにTCPコネクションを確立し、ヘッダーはテキスト形式で送られます。HOLブロッキング（Head-of-Line Blocking）の問題や、ヘッダーの冗長性などが課題でした。
-   **HTTP/2**: HTTP/1.1のパフォーマンス課題を解決するために開発された新しいプロトコル。主な特徴は以下の通りです。
    -   **バイナリフレーミング層**: ヘッダーとボディがバイナリ形式のフレームに分割されて送られるため、解析が効率的です。
    -   **多重化 (Multiplexing)**: 一つのTCPコネクション上で複数のリクエストとレスポンスを同時に送受信できます。これによりHOLブロッキングが解消されます。
    -   **ヘッダー圧縮 (HPACK)**: 繰り返し送られるヘッダー情報を効率的に圧縮し、帯域幅の使用量を削減します。
    -   **サーバープッシュ**: クライアントが要求する前に、サーバーがリソースをプッシュできます。

### Gzip 圧縮

-   **`Content-Encoding: gzip`**: HTTPレスポンスヘッダーの一つで、メッセージボディがgzip形式で圧縮されていることを示します。これにより、転送されるデータ量を削減し、Webページのロード時間を短縮できます。
-   **`Accept-Encoding` ヘッダー**: HTTPリクエストヘッダーの一つで、クライアントが受け入れ可能なコンテンツエンコーディング（例: `gzip`, `deflate`, `br` など）をサーバーに伝えます。クライアントがこのヘッダーを送信することで、サーバーはクライアントがサポートする圧縮形式で応答を返すことができます。
-   **自動解凍 (Automatic Decompression)**: 多くのHTTPクライアントライブラリ（Goの `net/http` を含む）は、サーバーから `Content-Encoding: gzip` ヘッダーを持つ応答を受け取った場合、クライアントが `Accept-Encoding: gzip` を送っていなくても、透過的にその応答を解凍してアプリケーションに非圧縮データとして提供する機能を持っています。これは、サーバーが常に `Accept-Encoding` ヘッダーを尊重するとは限らないため、クライアント側の堅牢性を高めるために重要です。

### Go の `net/http` パッケージ

-   Go言語の標準ライブラリであり、HTTPクライアントとサーバーの実装を提供します。
-   **`http.Client`**: HTTPリクエストを送信し、HTTPレスポンスを受信するクライアントを表します。
-   **`http.Transport`**: `http.Client` の内部で実際にネットワーク通信を行うコンポーネントです。TCPコネクションの確立、TLSハンドシェイク、HTTP/1.1またはHTTP/2プロトコルの処理などを担当します。このコミットの変更は、特にHTTP/2プロトコルを扱う `http2Transport` に関連しています。
-   **`http.Request`**: HTTPリクエストを表す構造体。
-   **`http.Response`**: HTTPレスポンスを表す構造体。

    -   `Close` メソッドは、ラップされた元のボディの `Close` メソッドを呼び出します。

## コアとなるコードの解説

### `src/net/http/h2_bundle.go`

-   **`http2Transport` 構造体への `DisableCompression` フィールドの追加**:
    -   このフィールドは、`http.Transport` の既存の `DisableCompression` と同様の機能を提供し、HTTP/2クライアントが自動的に `Accept-Encoding: gzip` ヘッダーをリクエストに追加するかどうかを制御します。デフォルトでは `false` であり、自動圧縮が有効になります。これにより、ユーザーは必要に応じてこの挙動を無効にできます。
-   **`http2clientStream` 構造体への `requestedGzip` フィールドの追加**:
    -   各HTTP/2ストリームの状態を保持する `http2clientStream` に `requestedGzip` というブール値が追加されました。これは、現在のリクエストに対してトランスポートが `Accept-Encoding: gzip` ヘッダーを自動的に追加したかどうかを記録するためのものです。この情報を使って、応答がgzip圧縮されている場合に透過的な解凍を適用するかどうかを判断します。
-   **`RoundTrip` メソッド内での `Accept-Encoding` ヘッダー追加ロジック**:
    -   `RoundTrip` メソッドは、HTTPリクエストを送信し、HTTPレスポンスを受信する主要なメソッドです。
    -   ここで、`http2Transport` の `DisableCompression` が `false`（つまり自動圧縮が有効）であり、かつリクエストに `Accept-Encoding` ヘッダーがまだ設定されておらず、`Range` ヘッダーがなく、`HEAD` メソッドでない場合に、`cs.requestedGzip` が `true` に設定されます。
    -   この条件は、クライアントが明示的に圧縮を要求していないが、トランスポートが透過的に圧縮を要求すべき状況を特定します。`Range` ヘッダーや `HEAD` メソッドは、ボディの全部または一部の取得、あるいはボディなしのリクエストであるため、通常は圧縮の対象外とされます。
    -   その後、`encodeHeaders` メソッドが `cs.requestedGzip` の値と共に呼び出され、必要に応じて `Accept-Encoding: gzip` ヘッダーがリクエストに追加されます。
-   **`encodeHeaders` メソッドの変更**:
    -   このメソッドは、HTTPリクエストヘッダーをHTTP/2のHPACK形式にエンコードする役割を担います。
    -   `addGzipHeader` という新しいブール型引数が追加され、これが `true` の場合にのみ `Accept-Encoding: gzip` ヘッダーがエンコードされるヘッダーリストに追加されます。これにより、`RoundTrip` メソッドでの決定に基づいて、動的に `Accept-Encoding` ヘッダーを追加できるようになります。
-   **`processHeaderBlockFragment` 内での `http2gzipReader` の適用**:
    -   このメソッドは、サーバーから受信したHTTP/2のヘッダーフレームを処理します。
    -   ここで、`cs.requestedGzip` が `true`（クライアントが自動的にgzipをリクエストした）であり、かつサーバーの応答に `Content-Encoding: gzip` ヘッダーが含まれている場合、透過的な解凍処理が適用されます。
    -   具体的には、`Content-Encoding` と `Content-Length` ヘッダーが応答から削除され、`Content-Length` は `-1` に設定されます。これは、アプリケーション層には非圧縮データとして提供するため、これらのヘッダーが誤解を招かないようにするためです。
    -   最も重要な変更は、`res.Body` が新しく定義された `http2gzipReader` でラップされる点です。これにより、アプリケーションが `Response.Body` からデータを読み込む際に、`http2gzipReader` が内部でgzip解凍を行い、非圧縮データを提供します。
-   **`http2gzipReader` 構造体とメソッド**:
    -   この構造体は、`io.ReadCloser` インターフェースを実装し、元の `Response.Body` を内部に保持します。
    -   `Read` メソッドが初めて呼び出されたときに、`gzip.NewReader` を使用して実際のgzip解凍リーダー (`gz.zr`) を遅延初期化します。これにより、ボディが実際に読み取られるまで解凍処理が開始されず、リソースの無駄を省きます。
    -   `Close` メソッドは、ラップされた元のボディの `Close` メソッドを呼び出し、リソースを適切に解放します。

### `src/net/http/clientserver_test.go`

-   **`mostlyCopy` ヘルパー関数の追加**:
    -   この関数は、`http.Response` オブジェクトをコピーする際に、`Body`、`TransferEncoding`、`TLS`、`Request` といった、`reflect.DeepEqual` で比較すると常に異なるか、比較に適さないフィールドを `nil` に設定します。
    -   これは、`h12Compare` テストフレームワークがHTTP/1とHTTP/2のレスポンスを比較する際に、これらの動的なフィールドの違いによってテストが誤って失敗するのを防ぐために導入されました。
-   **`TestH12_AutoGzip` テストケースの追加**:
    -   このテストは、HTTP/1とHTTP/2の両方のクライアントが、自動的に `Accept-Encoding: gzip` ヘッダーをリクエストに追加し、サーバーから `Content-Encoding: gzip` で返された応答を透過的に解凍できることを検証します。
    -   テストハンドラーは、リクエストの `Accept-Encoding` ヘッダーが `gzip` であることを確認し、応答に `Content-Encoding: gzip` を設定して、実際にgzip圧縮されたコンテンツを書き込みます。
    -   `h12Compare` フレームワークは、このハンドラーに対してHTTP/1とHTTP/2の両方でリクエストを送信し、クライアントが受け取った応答ボディが、圧縮されていない元の文字列と一致するかどうかを検証します。これにより、HTTP/2トランスポートの自動gzip解凍機能が正しく動作していることが確認されます。

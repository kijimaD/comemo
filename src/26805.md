# [インデックス 26805] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）におけるキーワードの表現方法を根本的に変更するものです。以前は、Go言語のキーワード（`if`, `for`, `func`など）も一般的な識別子と同様に`Sym`（シンボル）構造体として表現され、その種類を`Sym.Lexical`フィールドで区別していました。このコミットでは、キーワードを`Sym`構造体から分離し、専用の`keywords`マップを導入することで、字句解析器（lexer）がキーワードをより直接的かつ効率的に識別できるように改善しています。これにより、`Sym`構造体のシンプル化とコンパイラのコードの明確化が図られています。

## 元コミット内容

`cmd/compile: stop representing keywords as Syms`

このコミットは、Goコンパイラがキーワードを`Sym`（シンボル）として表現するのをやめることを目的としています。代わりに、字句解析器の`lexer.ident`関数で使用するための専用の`keywords`マップを追加し、`Sym`構造体から`Lexical`フィールドを削除します。

## 変更の背景

Goコンパイラの初期設計では、言語のキーワード（`if`, `for`, `func`など）も、ユーザー定義の識別子（変数名、関数名など）と同様に`Sym`（シンボル）構造体として扱われていました。`Sym`構造体は、プログラム内の名前（識別子）に関する情報を一元的に管理するためのもので、その中に`Lexical`というフィールドがあり、これがそのシンボルがキーワードであるか、あるいは特定の字句的な意味を持つかを示していました。

このアプローチにはいくつかの問題がありました。
1.  **`Sym`構造体の役割の曖昧さ**: `Sym`は本来、識別子とその属性（型、定義、スコープなど）を管理するためのものです。キーワードは言語の予約語であり、識別子とは異なる性質を持つため、同じ`Sym`構造体で表現することは、その役割を曖昧にしていました。
2.  **効率性の問題**: 字句解析の段階で、識別子とキーワードを区別するために、まず`Sym`としてルックアップし、その後`Lexical`フィールドをチェックするという二段階の処理が必要でした。これは、特に頻繁に現れるキーワードの処理において、オーバーヘッドとなる可能性がありました。
3.  **コードの複雑性**: `Sym`構造体や関連するコードが、キーワードと識別子の両方を扱うために複雑になっていました。キーワード専用の処理を分離することで、コードの明確性と保守性が向上します。

このコミットは、これらの問題を解決するために、キーワードを`Sym`システムから切り離し、字句解析の初期段階で直接識別できるようにするものです。

## 前提知識の解説

### Goコンパイラの構造 (`cmd/compile`)

Goコンパイラは、Go言語のソースコードを機械語に変換するツールチェーンの一部です。`cmd/compile`はその主要なコンポーネントであり、以下の主要なフェーズで構成されます。

1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（意味を持つ最小単位）のストリームに変換します。例えば、`if x > 0 {`というコードは、`if` (キーワード), `x` (識別子), `>` (演算子), `0` (リテラル), `{` (区切り文字)といったトークンに分解されます。このフェーズを担当するのが「レキサー (lexer)」です。
2.  **構文解析 (Syntactic Analysis)**: トークンのストリームを解析し、プログラムの構造を抽象構文木 (AST: Abstract Syntax Tree) として構築します。
3.  **意味解析 (Semantic Analysis)**: 型チェック、名前解決などを行い、プログラムの意味的な正当性を検証します。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTを中間表現（IR）に変換します。
5.  **最適化 (Optimization)**: 中間コードを最適化し、実行効率を向上させます。
6.  **コード生成 (Code Generation)**: 最適化された中間コードをターゲットアーキテクチャの機械語に変換します。

このコミットは主に**字句解析**フェーズに関わる変更です。

### 字句解析 (Lexical Analysis) とトークン

字句解析器（レキサー）は、ソースコードを読み込み、一連の文字を意味のあるまとまり（トークン）にグループ化します。Go言語におけるトークンの例としては、以下のようなものがあります。

*   **キーワード**: `func`, `var`, `if`, `for`, `return` など、言語によって予約された特別な意味を持つ単語。
*   **識別子**: 変数名、関数名、型名など、プログラマが定義する名前。
*   **リテラル**: `123` (整数), `"hello"` (文字列), `3.14` (浮動小数点数) など、定数値を表す。
*   **演算子**: `+`, `-`, `*`, `/`, `=`, `==` など。
*   **区切り文字**: `(`, `)`, `{`, `}`, `;`, `,` など。

レキサーの主なタスクの一つは、読み込んだ文字列がキーワードなのか、それとも単なる識別子なのかを効率的に判断することです。

### シンボルテーブル (Symbol Table) と `Sym` 構造体

コンパイラは、プログラム内で使用されるすべての識別子（変数、関数、型など）に関する情報を管理するために「シンボルテーブル」を使用します。Goコンパイラでは、このシンボルテーブルのエントリが`Sym`構造体で表現されます。

`Sym`構造体は、識別子の名前、それが属するパッケージ、その識別子の定義（型、値、ノードなど）、そして以前は`Lexical`フィールドのような字句的な情報を含んでいました。`Sym`は、名前解決や型チェックなど、コンパイラの後のフェーズで重要な役割を果たします。

### `Lexical`フィールド

変更前の`Sym`構造体には`Lexical uint16`というフィールドがありました。このフィールドは、その`Sym`が表す名前がどのような字句的な種類を持つかを示していました。例えば、`LNAME`は一般的な識別子を、`LBREAK`は`break`キーワードを、`LFUNC`は`func`キーワードを表すといった具合です。レキサーは、識別子を読み込んだ後、`LookupBytes`関数で対応する`Sym`を取得し、その`Sym.Lexical`フィールドの値を調べて、それがキーワードであるかどうかを判断していました。

## 技術的詳細

このコミットの核心は、キーワードの識別ロジックを`Sym`構造体から完全に分離し、字句解析の段階でより直接的に処理することにあります。

1.  **`Sym`構造体からの`Lexical`フィールドの削除**:
    `src/cmd/compile/internal/gc/go.go`内の`Sym`構造体から`Lexical uint16`フィールドが削除されました。これにより、`Sym`構造体は純粋に識別子のセマンティックな情報（名前、パッケージ、定義など）を保持する役割に特化され、字句的な情報は含まれなくなりました。これは、関心の分離（Separation of Concerns）の原則に沿った改善です。

2.  **専用の`keywords`マップの導入**:
    `src/cmd/compile/internal/gc/lex.go`に、`map[string]int32`型のグローバル変数`keywords`が新しく追加されました。このマップは、Go言語のすべてのキーワード文字列（例: `"break"`, `"case"`, `"func"`）をキーとして、それに対応するトークンタイプ（例: `LBREAK`, `LCASE`, `LFUNC`）を値として保持します。これにより、キーワードのルックアップが非常に高速かつ直接的になります。

3.  **`lexer.ident`関数の変更**:
    字句解析器の主要な関数である`lexer.ident`は、識別子を読み込んだ後に、まずこの新しい`keywords`マップをチェックするようになりました。
    *   入力された文字列が`keywords`マップに存在する場合、それはキーワードとして即座に識別され、対応するトークンタイプが`l.tok`に設定されます。この際、`Sym`構造体へのルックアップは不要になります。
    *   入力された文字列が`keywords`マップに存在しない場合のみ、それは一般的な識別子として扱われ、`LookupBytes`関数を呼び出して`Sym`構造体を取得します。この場合、`l.tok`は`LNAME`（識別子）に設定されます。
    *   `LBREAK`, `LCONTINUE`, `LFALL`, `LRETURN`といった特定のキーワードについては、`l.nlsemi = true`を設定するロジックが、`Sym.Lexical`のチェックから`keywords`マップによる直接的なチェックに移行しました。

4.  **`syms`配列のクリーンアップ**:
    `src/cmd/compile/internal/gc/lex.go`内の`syms`配列は、コンパイラが起動時に組み込み型（`int8`, `string`など）や組み込み関数（`append`, `len`など）の`Sym`構造体を初期化するために使用されていました。変更前は、この配列にキーワードも含まれており、各エントリには`lexical`フィールドがありました。このコミットにより、キーワードのエントリは`syms`配列から削除され、`syms`構造体からも`lexical`フィールドが削除されました。これにより、`syms`配列は純粋に組み込みの識別子のみを扱うようになり、コードがより明確になりました。

この変更により、コンパイラの字句解析フェーズはより効率的になり、`Sym`構造体の設計はよりクリーンで、その本来の目的に合致するようになりました。キーワードの識別は、シンボルテーブルの複雑なルックアップを介さずに、専用のハッシュマップによって直接行われるため、パフォーマンスの向上が期待できます。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/go.go` の変更

*   **`Sym`構造体**: `Lexical uint16`フィールドが削除されました。これにより、`Sym`はキーワードの種類を保持する責任から解放され、純粋に識別子のセマンティックな情報（名前、パッケージ、定義など）に集中できるようになりました。これは、コンパイラの内部モデルをよりクリーンにし、各データ構造の役割を明確にするための重要な変更です。

### `src/cmd/compile/internal/gc/lex.go` の変更

*   **`lexer.ident`関数**:
    *   変更前は、`LookupBytes(lexbuf.Bytes())`で`Sym`を取得し、その`s.Lexical`を調べてキーワードかどうかを判断していました。
    *   変更後は、まず`name := lexbuf.Bytes()`で識別子文字列を取得し、`if tok, ok := keywords[string(name)]; ok`という行で、新しく導入された`keywords`マップを直接参照して、それがキーワードであるかをチェックします。
    *   キーワードであれば、対応するトークンタイプ`tok`を`l.tok`に設定し、関数を`return`します。これにより、キーワードの識別が`Sym`ルックアップを介さずに行われるため、効率が向上します。
    *   キーワードでなければ、以前と同様に`LookupBytes(name)`で`Sym`を取得し、`l.tok = LNAME`として一般的な識別子として扱います。
    *   `LBREAK`, `LCONTINUE`, `LFALL`, `LRETURN`といったキーワードに対する`l.nlsemi = true`（改行がセミコロンとして扱われるべきかを示すフラグ）の設定も、`keywords`マップによる直接的なチェックの`switch`文内に移動しました。
*   **`keywords`マップ**:
    *   `var keywords = map[string]int32{ ... }`として、Go言語のすべての予約語とその対応するトークンタイプが定義されています。これにより、キーワードの識別が中央集権化され、管理しやすくなりました。
    *   コメントアウトされた`// 💩`以下のエントリは、おそらくテストやジョークとして追加されたもので、実際のGo言語のキーワードではありません。
*   **`syms`配列**:
    *   `syms`配列の各要素の構造から`lexical int`フィールドが削除されました。この配列は、組み込み型や組み込み関数の`Sym`を初期化するために使用されますが、キーワードは含まれなくなりました。
    *   `lexinit()`関数内での`s1.Lexical = uint16(lex)`のような行が削除され、`Sym`の`Lexical`フィールドへの設定が一切行われなくなりました。
    *   `lexfini()`関数内でも、`Sym.Lexical`を扱うロジックが削除されています。

### `src/cmd/compile/internal/gc/subr.go` の変更

*   `Pkg.Lookup`関数内で新しい`Sym`構造体を生成する際、`Lexical: LNAME`という初期化が削除されました。これは、`Sym`構造体自体から`Lexical`フィールドがなくなったため、当然の変更です。

これらの変更により、Goコンパイラの字句解析器はキーワードをより効率的に、かつ`Sym`構造体のセマンティックな役割を損なうことなく識別できるようになりました。

# [インデックス 27577] ファイルの概要

このコミットは、Goリンカー（`cmd/link`）の内部パッケージである`cmd/link/internal/ld`に存在する`objReader`構造体の`readSymName`メソッドの最適化と簡素化を目的としています。具体的には、`bufio.Reader`の機能をより効果的に活用することで、シンボル名の読み取り処理におけるメモリ割り当てを削減し、コードの可読性を向上させています。この変更により、基本的なHTTPサーバーのリンク時におけるメモリ割り当てが約1.1%削減されることが報告されています。

## 元コミット内容

`cmd/link: simplify readSymName, taking advantage of bufio.Reader`

このコミットは、`cmd/link`パッケージ内の`readSymName`関数を簡素化し、`bufio.Reader`の利点を活用することを目的としています。これにより、コードの理解が容易になり、基本的なHTTPサーバーのリンク時におけるメモリ割り当てが1.1%削減されます。コミットメッセージには、変更前後のメモリプロファイル結果が詳細に記載されており、`readSymName`関数がメモリ使用量の削減に貢献していることが示されています。また、`adjName`バッファが再割り当てされないように、計算された長さが常に正しいことをアサートで確認するローカルテストも実施されています。

## 変更の背景

Goのリンカー（`cmd/link`）は、コンパイルされたGoパッケージを単一の実行可能バイナリに結合する重要なツールです。このプロセスでは、オブジェクトファイルからシンボル名などのメタデータを読み取ります。`readSymName`関数は、このシンボル名を読み取る役割を担っています。

以前の`readSymName`の実装では、シンボル名を読み取る際に、`bufio.Reader`が提供するバッファリング機能を十分に活用できていませんでした。特に、シンボル名に含まれる`"".`という文字列をパッケージ名に置き換える処理（例: `"".Foo`を`main.Foo`に変換）において、一時的なバッファの再割り当てが頻繁に発生し、メモリ使用量が増加する可能性がありました。

このコミットの背景には、リンカーのパフォーマンス向上とメモリフットプリントの削減という目標があります。`bufio.Reader`は、基盤となるI/O操作の回数を減らすことでパフォーマンスを向上させるためのバッファリング機能を提供しますが、その機能を最大限に引き出すためには、バッファの管理方法を最適化する必要があります。この変更は、`bufio.Reader`の`Peek`メソッドを利用することで、シンボル名を事前にバッファから覗き見し、必要なバッファサイズを正確に計算して再割り当てを最小限に抑えることを目指しています。これにより、リンカーの実行速度が向上し、特に大規模なプロジェクトのビルド時間短縮に貢献します。

## 前提知識の解説

### Goリンカー (`cmd/link`)

Goリンカーは、Goプログラムのビルドプロセスにおける最終段階を担うツールです。Goコンパイラによって生成されたオブジェクトファイル（`.a`ファイルなど）を結合し、実行可能なバイナリファイルを生成します。この過程で、シンボル解決、アドレスの再配置、デバッグ情報の埋め込みなど、様々な処理が行われます。`cmd/link`はGoツールチェーンの重要な一部であり、その効率性はGoプログラムのビルド時間に直接影響します。

### `bufio.Reader`

Go言語の`bufio`パッケージは、バッファリングされたI/O操作を提供します。`bufio.Reader`は、基盤となる`io.Reader`からの読み取りをバッファリングすることで、システムコール（ディスクI/OやネットワークI/Oなど）の回数を減らし、I/Oパフォーマンスを向上させます。

*   **バッファリング**: データを一度にまとめて読み込み、内部バッファに保持します。これにより、小さな読み取り要求が多数発生しても、実際のI/O操作は少なく済みます。
*   **`Peek`メソッド**: `bufio.Reader`の`Peek(n int)`メソッドは、次の`n`バイトを読み取り位置を進めることなく返します。これは、次に読み込まれるデータを事前に確認したいが、まだ実際に消費したくない場合に非常に便利です。`Peek`が返すスライスは、`bufio.Reader`の内部バッファの一部であり、その後の読み取り操作によって無効になる可能性があります。
*   **メモリ効率**: `bufio.Reader`を適切に利用することで、一時的なメモリ割り当てを減らし、ガベージコレクションの負荷を軽減できます。特に、`Peek`のようなメソッドは、データをコピーせずに内部バッファへの参照を返すため、効率的な処理が可能です。

### シンボル名と`"".`の置換

Goのコンパイル済みコードでは、パッケージ内の非エクスポートされたシンボル（関数、変数など）は、オブジェクトファイル内で`"".`というプレフィックスを持つことがあります。これは、リンカーが最終的なバイナリを生成する際に、これらのシンボルを適切なパッケージ名（例: `main.Foo`、`mypackage.Bar`）に解決するために使用される内部的な表現です。`readSymName`関数は、この`"".`を実際のパッケージ名に置き換える処理を担当しています。この置換処理は、シンボル名の長さが変わる可能性があるため、バッファ管理において注意が必要です。

## 技術的詳細

このコミットの主要な技術的改善点は、`objReader.readSymName`関数におけるメモリ割り当ての最適化です。以前の実装では、シンボル名を読み取る際に、まず`n`バイトの長さの`origName`バッファを作成し、その後に`"".`の置換によって長さが変わる可能性のある`adjName`バッファを`append`操作で構築していました。この`append`操作は、元のバッファの容量が不足した場合に新しいバッファを割り当て直す可能性があり、これがメモリ割り当ての増加につながっていました。

新しい実装では、以下の点が変更されています。

1.  **`bufio.Reader.Peek`の活用**: `r.readFull`で実際にデータを読み込む前に、`r.rd.Peek(n)`を使用して`n`バイトのシンボル名をバッファから「覗き見」します。これにより、`origName`は`bufio.Reader`の内部バッファへの参照となり、新たなメモリ割り当てが不要になります。
2.  **必要なバッファサイズの事前計算**: `origName`を`Peek`で取得した後、`bytes.Count(origName, emptyPkg)`（`emptyPkg`は`"".`を表す）を使用して、`"".`がシンボル名中に何回出現するかを数えます。これにより、`"".`が`pkg+"."`に展開された場合に最終的に必要となる`adjName`の最大長を`need`変数で正確に計算します。
3.  **`objReader.rdBuf`の再利用**: `objReader`構造体は、`rdBuf`というバイトスライスを内部に持っています。新しい実装では、この`rdBuf`を`adjName`の構築に再利用します。`len(r.rdBuf) < need`の場合にのみ、`rdBuf`を`need`サイズで`make`し直すことで、不要な再割り当てを最小限に抑えます。
4.  **`r.readFull`によるバッファの消費**: `Peek`で覗き見したデータは、実際に読み取り位置を進めていません。そのため、`adjName`の構築が完了した後、`r.readFull(r.rdBuf[:n])`を呼び出して、`n`バイト分のデータを`bufio.Reader`から消費し、読み取り位置を適切に進めます。この際、`r.rdBuf[:n]`は単なるスクラッチスペースとして利用されます。
5.  **`maxInt`ヘルパー関数の追加**: 2つの整数値のうち大きい方を返すシンプルなヘルパー関数`maxInt`が追加されています。これは、`need`の計算において、`len(origName)`と`bytes.Count`の結果から導かれる値を比較するために使用されます。

これらの変更により、`readSymName`関数は、シンボル名を処理する際の一時的なバッファ割り当てを大幅に削減し、リンカー全体のメモリ効率を向上させています。特に、`Peek`と事前計算によるバッファ再利用の組み合わせが、この最適化の鍵となっています。

## コアとなるコードの解説

変更された`readSymName`関数は、シンボル名を読み取り、`"".`プレフィックスを実際のパッケージ名に置き換える役割を担います。

1.  **`n := r.readInt()`**: まず、シンボル名の長さ`n`を読み取ります。
2.  **`if n == 0`**: 長さが0の場合は、空のシンボル名として処理し、関連する64ビット整数を読み飛ばして空文字列を返します。
3.  **`origName, err := r.rd.Peek(n)`**: ここが重要な変更点です。`r.rd`は`bufio.Reader`のインスタンスであり、その`Peek(n)`メソッドを使って、次に読み込まれる`n`バイトのデータを`origName`として取得します。この操作は、実際の読み取り位置を進めないため、メモリコピーが発生しません。エラーが発生した場合は、致命的なエラーとしてログに出力されます。
4.  **`need := len(origName) + maxInt(0, bytes.Count(origName, emptyPkg)*(len(pkg)+len(".")-len(emptyPkg)))`**: `adjName`（調整後のシンボル名）を格納するために必要なバッファサイズ`need`を計算します。`bytes.Count`で`origName`内の`"".`の出現回数を数え、それが`pkg+"."`に展開されることによる長さの増加分を考慮に入れます。`maxInt`は、負の値にならないようにするためのガードです。
5.  **`if len(r.rdBuf) < need { r.rdBuf = make([]byte, need) }`**: `objReader`が持つ内部バッファ`r.rdBuf`の容量が`need`よりも小さい場合、`need`サイズの新しいバッファを割り当てて`r.rdBuf`に設定します。これにより、`adjName`の構築中にバッファが不足して再割り当てされるのを防ぎます。
6.  **`adjName := r.rdBuf[:0]`**: `r.rdBuf`を再利用するために、スライスを長さ0にリセットします。これにより、既存のバッキング配列を保持しつつ、新しいデータを先頭から書き込めるようになります。
7.  **`for`ループによる置換処理**: `bytes.Index`を使って`origName`から`"".`を探し、見つかった場合は`adjName`に`origName`の先頭部分、`pkg`、そして`.`を`append`します。`origName`は残りの部分に更新され、この処理を繰り返します。
8.  **`s := string(append(adjName, origName...))`**: ループが終了し、すべての`"".`が置換された後、最終的な`adjName`と残りの`origName`を結合して文字列`s`を生成します。
9.  **`r.readFull(r.rdBuf[:n])`**: `Peek`で覗き見した`n`バイトのデータを`bufio.Reader`から実際に消費するために、`r.readFull`を呼び出します。この際、`r.rdBuf[:n]`は単に`n`バイトを読み込むためのスクラッチスペースとして利用されます。
10. **`return s`**: 最終的に調整されたシンボル名を返します。

新しく追加された`maxInt`関数は、Goの標準ライブラリには存在しないため、このファイル内で定義されています。これは、2つの整数`a`と`b`を比較し、大きい方を返すシンプルなユーティリティ関数です。

# [インデックス 20062] ファイルの概要

このコミットは、Goコンパイラのバックエンドの一部である`cmd/9g`に関連する変更です。具体的には、Power64アーキテクチャ向けのコード生成ロジックに影響を与えます。`src/cmd/9g/gg.h`はコンパイラのグローバルヘッダーファイルであり、`src/cmd/9g/gsubr.c`はGoコンパイラのサブプロシージャ（サブルーチン）の実装を含むC言語のソースファイルです。これらのファイルは、GoソースコードをPower64アーキテクチャの機械語に変換する過程で重要な役割を担っています。

## コミット

このコミットは、GoコンパイラのPower64アーキテクチャ向けバックエンド(`cmd/9g`)において、ソースとデスティネーションのアドレスが同じ(`samaddr()`)であっても、移動命令を無視しないようにする変更です。Power64では、`MOVWD`（ワード移動）と`MOVW`（ダブルワード移動）が区別されないため、このような移動命令がナローイング（縮小）やワイドニング（拡張）といった型変換を伴う場合、その命令が重要になる可能性があります。この修正により、`divmode.go`と`bug447.go`で発生していた問題が解決されました。

## 変更の背景

この変更の背景には、GoコンパイラがPower64アーキテクチャ向けにコードを生成する際の特定の課題がありました。従来の`cmd/9g`のロジックでは、ソースオペランドとデスティネーションオペランドが同じメモリアドレスまたはレジスタを指している場合、冗長な移動命令を生成しないように最適化されていました。この最適化は、多くの場合において有効であり、生成されるコードの効率を高めます。

しかし、Power64アーキテクチャの特性がこの最適化と衝突するケースがありました。Power64では、データ移動命令において、例えば32ビットのワード移動(`MOVW`)と64ビットのダブルワード移動(`MOVWD`)が、命令レベルで明確に区別されない場合があります。つまり、同じ命令が異なるデータ幅の移動を表現する可能性があり、コンパイラがその文脈を正しく解釈する必要がありました。

このような状況で、もしソースとデスティネーションが同じレジスタであっても、データ型が異なる（例えば、32ビット整数を64ビットレジスタに格納する、あるいはその逆）場合、単なる「移動」ではなく、ナローイング（値の範囲を狭める型変換）やワイドニング（値の範囲を広げる型変換）といった意味を持つことがあります。これらの型変換は、値の表現方法やメモリ上の配置に影響を与えるため、対応する機械語命令が省略されると、プログラムの動作が不正になる可能性がありました。

`divmode.go`と`bug447.go`で発生していたバグは、まさにこの問題に起因していました。コンパイラが不適切に移動命令を省略した結果、期待される型変換が行われず、誤った値が使用されたり、予期せぬ動作を引き起こしたりしていたと考えられます。このコミットは、Power64アーキテクチャの特殊性を考慮し、このような潜在的なバグを防ぐために、`samaddr()`による最適化を無効化することで、より堅牢なコード生成を実現することを目的としています。

## 前提知識の解説

### `cmd/9g`

`cmd/9g`は、Go言語の初期のコンパイラツールチェーンの一部であり、特にx86アーキテクチャ（32ビットおよび64ビット）向けのコード生成を担当していました。Goコンパイラは、フロントエンド（Goソースコードの解析と中間表現への変換）とバックエンド（中間表現から特定アーキテクチャの機械語への変換）に分かれています。`cmd/9g`は、このバックエンドの一つとして機能していました。

コミットメッセージに`[dev.power64]`とあることから、この特定のコミットはPower64アーキテクチャ向けの`cmd/9g`の派生版、あるいはその時期のGoコンパイラがPower64をサポートする際に`9g`という名称がより広範なバックエンドを指していた可能性を示唆しています。現代のGoコンパイラは`go tool compile`として統合されており、アーキテクチャ固有のコンパイラ名が直接使われることは少なくなっていますが、当時の開発においてはアーキテクチャごとに異なるバックエンドが存在していました。

### Power64アーキテクチャ

Power64は、IBMが開発したPower ISA（Instruction Set Architecture）に基づく64ビットのRISC（Reduced Instruction Set Computer）アーキテクチャです。RISCアーキテクチャの一般的な特徴として、命令セットがシンプルで、固定長命令が多く、ロード/ストアアーキテクチャである点が挙げられます。ロード/ストアアーキテクチャとは、メモリとレジスタ間のデータ移動は専用のロード命令とストア命令によってのみ行われ、演算命令はレジスタ内のデータに対してのみ実行されることを意味します。

Power64プロセッサは、一般的に多数の汎用レジスタ（GPRs）を持ち、これらは64ビット幅です。このアーキテクチャの重要な特性の一つは、データ移動命令の柔軟性です。例えば、32ビットのデータを64ビットレジスタにロードする際に、符号拡張（`MOVSX`に相当）やゼロ拡張（`MOVZX`に相当）を伴う場合があります。コミットメッセージにある「`MOVWD`と`MOVW`を区別しない」という点は、Power64の命令セットにおいて、異なるデータ幅の移動が単一の命令形式で表現されるか、あるいはコンパイラがその文脈を適切に解釈する必要があることを示唆しています。これは、コンパイラが生成する機械語命令の正確性に直接影響します。

### `samaddr()` 関数

`samaddr()`は、Goコンパイラの内部で使用されていたヘルパー関数です。その名前が示す通り、「同じアドレス」を意味し、2つのオペランド（`Node`構造体で表現される）が同じメモリアドレスまたはレジスタを指しているかどうかを判定するために使用されていました。

コミットの変更内容から、この関数は主にレジスタオペランドに対して機能し、2つの`Node`が同じレジスタを指している場合に真を返していました。この関数は、`gins()`（命令生成関数）内で、冗長な移動命令の生成を避けるための最適化チェックとして利用されていました。つまり、もしソースとデスティネーションが同じレジスタであれば、`samaddr()`が真を返し、移動命令が生成されない、というロジックでした。

### ナローイング（Narrowing）とワイドニング（Widening）

プログラミングにおけるナローイングとワイドニングは、データ型変換（キャスト）の概念です。

*   **ワイドニング（Widening Conversion / 拡張変換）**:
    より小さいデータ型からより大きいデータ型への変換を指します。例えば、32ビット整数を64ビット整数に変換する場合などです。この変換では、通常、情報が失われることはありません。Go言語では、整数型の場合、符号付き整数は符号拡張され、符号なし整数はゼロ拡張されます。

*   **ナローイング（Narrowing Conversion / 縮小変換）**:
    より大きいデータ型からより小さいデータ型への変換を指します。例えば、64ビット整数を32ビット整数に変換する場合などです。この変換では、元の値が新しいデータ型の範囲に収まらない場合、情報が失われる（切り捨てやオーバーフローが発生する）可能性があります。Go言語では、浮動小数点数を整数に変換する際には小数部が切り捨てられます。

Go言語は型安全性を重視しており、ほとんどの型変換は明示的に行う必要があります。コンパイラが自動的にナローイングやワイドニングを伴う移動命令を省略してしまうと、Go言語の型変換のセマンティクスが破られ、予期せぬデータ損失や誤った計算結果につながる可能性があります。

## 技術的詳細

このコミットの技術的な核心は、GoコンパイラのPower64バックエンドにおける命令生成ロジックの修正にあります。具体的には、`gins`関数（`generate instruction`の略で、Goコンパイラが中間表現から機械語命令を生成する主要な関数の一つ）の動作が変更されました。

従来の`gins`関数では、`AMOVW`（ワード移動）、`AMOVD`（ダブルワード移動）、`AFMOVS`（単精度浮動小数点移動）、`AFMOVD`（倍精度浮動小数点移動）といった特定の移動命令を生成する際に、ソースオペランドとデスティネーションオペランドが`samaddr()`関数によって「同じアドレス」を指していると判定された場合、その移動命令の生成をスキップしていました。これは、同じ場所への移動は冗長であるという一般的な最適化の考えに基づいています。

しかし、Power64アーキテクチャの特性がこの最適化と矛盾しました。Power64では、例えば32ビットの値を64ビットレジスタに移動する際（ワイドニング）、あるいは64ビットレジスタ内の値を32ビットとして扱う際（ナローイング）に、見かけ上同じレジスタ間での移動であっても、内部的には符号拡張やゼロ拡張といったビット操作が必要となる場合があります。Power64の命令セットが`MOVWD`と`MOVW`のような異なるデータ幅の移動を明確に区別しない場合、コンパイラはこれらの型変換を明示的に処理するための命令を生成する必要があります。

`samaddr()`によるチェックが有効な場合、例えば`int32`型の変数を`int64`型の変数に代入する際に、両者が同じレジスタに割り当てられたとすると、`samaddr()`が真を返し、ワイドニングのための移動命令が省略されてしまいます。その結果、64ビットレジスタの上位32ビットが未定義のままになったり、誤った値が格納されたりする可能性があります。これは、Go言語の厳格な型システムと、期待される数値演算のセマンティクスに反します。

このコミットでは、`samaddr()`関数自体が削除され、それに伴い`gins`関数内の`samaddr(f, t)`チェックも削除されました。これにより、ソースとデスティネーションが同じアドレスを指している場合でも、`AMOVW`、`AMOVD`などの移動命令が常に生成されるようになります。この変更は、一見すると冗長な命令が増えるように見えますが、Power64アーキテクチャにおけるナローイングやワイドニングのセマンティクスを正しく保証するために不可欠です。コンパイラは、これらの移動命令を通じて、必要な符号拡張やゼロ拡張を適切に実行する機械語を生成できるようになり、`divmode.go`や`bug447.go`のような型変換に起因するバグが修正されました。

## コアとなるコードの解説

### `samaddr`関数の削除

削除された`samaddr`関数は、以下のようなロジックを持っていました。

```c
int
samaddr(Node *f, Node *t)
{
	if(f->op != t->op)
		return 0;

	switch(f->op) {
	case OREGISTER:
		if(f->val.u.reg != t->val.u.reg)
			break;
		return 1;
	}
	return 0;
}
```

この関数は、2つの`Node`ポインタ`f`と`t`を受け取り、それらが同じオペレーションタイプ（`f->op == t->op`）を持ち、かつ、もしオペレーションタイプが`OREGISTER`（レジスタ）であれば、同じレジスタ番号（`f->val.u.reg == t->val.u.reg`）を持つ場合に`1`（真）を返していました。それ以外の場合は`0`（偽）を返します。

この関数の目的は、ソースとデスティネーションが論理的に同じ場所を指している場合に、冗長なデータ移動命令の生成を抑制することでした。例えば、`x = y`という代入があり、コンパイラが`x`と`y`を同じレジスタに割り当てた場合、この関数が真を返し、`MOV`命令が生成されないようにしていました。

### `gins`関数内の`samaddr`チェックの削除

`gins`関数は、Goコンパイラがアセンブリ命令を生成する際に呼び出される中心的な関数です。削除されたコードブロックは以下の通りです。

```c
	switch(as) {
	case AMOVW:
	case AMOVD:
	case AFMOVS:
	case AFMOVD:
		if(f != N && t != N && samaddr(f, t))
			return nil;
		break;
	}
```

このコードは、生成しようとしている命令が`AMOVW`（ワード移動）、`AMOVD`（ダブルワード移動）、`AFMOVS`（単精度浮動小数点移動）、`AFMOVD`（倍精度浮動小数点移動）のいずれかである場合に、`samaddr(f, t)`が真を返す（つまり、ソースとデスティネーションが同じアドレスを指している）ならば、命令の生成をスキップし、`nil`を返していました。

このコミットにより、`samaddr`関数自体が削除されたため、この`switch`文全体が不要となり削除されました。結果として、これらの移動命令は、ソースとデスティネーションが同じアドレスを指している場合でも、常に生成されるようになります。

この変更は、Power64アーキテクチャの特定の特性（`MOVWD`と`MOVW`の区別がないこと）と、Go言語の厳密な型変換セマンティクスを考慮したものです。同じレジスタ間での移動であっても、データ幅の変更（ナローイングやワイドニング）を伴う場合、それは単なる冗長な移動ではなく、値の正確な表現を保証するための重要な操作となります。`samaddr`チェックを削除することで、コンパイラはこれらの重要な型変換を伴う移動命令を適切に生成し、Power64上でのGoプログラムの正確な動作を保証できるようになりました。

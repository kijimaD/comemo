# [インデックス 25261] ファイルの概要

このコミットは、Goコンパイラ (`cmd/compile/internal/gc`) における静的な境界チェックの改善に関するものです。具体的には、`unsafe.Sizeof([0]byte{}[0])` のような、ゼロ要素配列に対する無効なインデックスアクセスをコンパイル時に検出して拒否するように変更が加えられました。これにより、コンパイラがより厳密なコードの健全性チェックを行うようになり、潜在的なランタイムエラーを未然に防ぐことができます。

## 元コミット内容

`cmd/compile/internal/gc`: 無効な `unsafe.Sizeof([0]byte{}[0])` を拒否する。

型チェック中に静的な境界チェックロジックを適用する。これはゼロ要素配列に対しても適用されるが、コンパイラが境界内であるとアサートした合成された `OINDEX` ノード（例えば `ORANGE` ノードのデシュガー中に生成されるもの）はスキップする。これは `walkexpr` において `Bounded` が `true` の場合に静的な境界チェックをスキップするロジックと一致する。

`toolstash/buildall` をパスした。

Issue #12944 を修正。

## 変更の背景

Go言語はメモリ安全性を重視しており、配列やスライスへのアクセス時には境界チェックが実行されます。通常、これはランタイムに発生し、インデックスが範囲外であればパニックを引き起こします。しかし、コンパイル時に静的にインデックスが範囲外であることが明らかな場合、コンパイラはそのエラーを早期に検出して開発者に通知することが望ましいです。

このコミット以前は、`unsafe.Sizeof([0]byte{}[0])` のような特定のケースで、コンパイラが静的な境界チェックを適切に適用できていませんでした。`[0]byte{}` は要素を一つも持たないバイト配列であり、`[0]` でその配列の0番目の要素にアクセスしようとすることは、論理的に常に範囲外アクセスとなります。`unsafe.Sizeof` はその引数の型サイズをコンパイル時に決定するものであり、ランタイムに式を評価するわけではありませんが、それでも引数として渡される式の健全性はコンパイラによってチェックされるべきです。

この問題は、Issue #12944 として報告され、コンパイラがこのような明らかな無効なアクセスをコンパイル時にエラーとして報告するように修正する必要がありました。これにより、開発者はより安全なコードを書くことができ、潜在的なバグを早期に発見できるようになります。

## 前提知識の解説

### Goコンパイラのフェーズ

Goコンパイラは、ソースコードを機械語に変換する過程で複数のフェーズを経ます。
*   **字句解析 (Lexing)**: ソースコードをトークンに分割します。
*   **構文解析 (Parsing)**: トークンから抽象構文木 (AST: Abstract Syntax Tree) を構築します。
*   **型チェック (Type Checking)**: ASTを走査し、式の型が正しいか、言語の規則に違反していないかを確認します。このフェーズで多くの静的なエラーが検出されます。
*   **中間表現 (IR: Intermediate Representation) への変換**: ASTをコンパイラ内部で扱いやすい形式に変換します。
*   **最適化 (Optimization)**: 生成されたIRを最適化し、より効率的なコードを生成します。
*   **コード生成 (Code Generation)**: IRからターゲットアーキテクチャの機械語を生成します。

### `unsafe.Sizeof`

`unsafe.Sizeof` はGo言語の組み込み関数で、任意の式の型が占めるメモリサイズをバイト単位で返します。この関数はコンパイル時に評価され、その引数の式自体は実行されません。そのため、`unsafe.Sizeof(x[i])` のようにインデックスアクセスを含む式を引数に取った場合でも、実際に `x[i]` が評価されてパニックが発生することはありません。しかし、`unsafe.Sizeof` の引数として渡される式が文法的に有効であり、かつ型チェックの観点から健全であることはコンパイラによって保証されるべきです。

### 境界チェック (Bounds Checking)

Go言語では、配列やスライスへのアクセス時にインデックスが有効な範囲内にあるかをチェックする「境界チェック」が自動的に行われます。インデックスが範囲外の場合、ランタイムパニックが発生します。コンパイラは、静的にインデックスが常に範囲内であることが証明できる場合には、このランタイムチェックを省略する最適化（Bounds Check Elimination: BCE）を行うことがあります。

### `OINDEX` ノードと `Bounded` プロパティ

Goコンパイラの内部では、配列やスライスへのインデックスアクセスは `OINDEX` と呼ばれるASTノードで表現されます。このノードは、インデックスアクセスに関する情報（対象の配列/スライス、インデックス値など）を保持します。
`Bounded` プロパティは、コンパイラが特定のインデックスアクセスが静的に境界内であると判断した場合に設定されるフラグです。このフラグが `true` の場合、コンパイラは冗長な境界チェックを省略したり、特定の最適化を適用したりします。

### デシュガー (Desugaring)

デシュガーとは、高レベルな言語構文を、コンパイラがより扱いやすい低レベルな、より基本的な構文に変換するプロセスです。例えば、`for...range` ループは、内部的には通常の `for` ループとインデックスアクセスにデシュガーされることがあります。コミットメッセージにある「`ORANGE` ノードのデシュガー」は、Goコンパイラ内部の特定のASTノード（おそらく `ONAME` や他の内部表現）が、インデックスアクセスを含むより基本的な形式に変換される過程を指していると考えられます。

## 技術的詳細

このコミットの核心は、Goコンパイラの型チェックフェーズ (`typecheck.go`) におけるインデックスアクセスの処理方法の変更です。

以前のコンパイラでは、`OINDEX` ノード（配列やスライスへのインデックスアクセスを表す）の型チェック時に、インデックスが定数であり、かつ配列が固定長 (`Isfixedarray`) で `Bound > 0` の場合にのみ、インデックスが配列の境界内にあるかどうかのチェックを行っていました。この `Bound > 0` という条件が問題でした。

`[0]byte{}` のようなゼロ要素配列の場合、`t.Bound` は `0` になります。したがって、`t.Bound > 0` の条件が `false` となり、インデックスが配列の境界内にあるかどうかのチェックがスキップされていました。結果として、`unsafe.Sizeof([0]byte{}[0])` のようなコードは、コンパイル時にエラーとして検出されず、`byte` のサイズである `1` を返すものとして扱われていました。しかし、論理的には `[0]byte{}[0]` は常に範囲外アクセスであり、コンパイル時にエラーとして報告されるべきです。

このコミットでは、このロジックが以下のように変更されました。

1.  **`!n.Bounded` の追加**: インデックスが定数であるかどうかのチェック (`Isconst(n.Right, CTINT)`) の前に、`!n.Bounded` という条件が追加されました。これは、コンパイラが既にこの `OINDEX` ノードが境界内であると判断している場合（`n.Bounded` が `true` の場合）は、静的な境界チェックをスキップするという意味です。これは、`walkexpr` フェーズでの動作と一貫性を持たせるための変更です。`walkexpr` は、`Bounded` フラグが `true` の場合に静的な境界チェックをスキップします。
2.  **`t.Bound > 0` の削除**: 固定長配列の境界チェック (`Isfixedarray(t) && t.Bound > 0 && x >= t.Bound`) から `t.Bound > 0` の条件が削除されました。これにより、ゼロ要素配列 (`t.Bound == 0`) であっても、インデックス `x` が `t.Bound` 以上であるかどうかのチェックが行われるようになりました。

この変更により、`[0]byte{}[0]` のようなゼロ要素配列に対するインデックスアクセスの場合、`t.Bound` は `0` であり、`x` (インデックス `0`) は `t.Bound` (0) 以上であるため、`x >= t.Bound` の条件が `true` となり、「out of bounds」エラーが適切に報告されるようになりました。

`n.Bounded` のチェックを追加することで、コンパイラが内部的に安全であると判断したインデックスアクセス（例えば、デシュガーによって生成されたノードなど）に対しては、冗長な静的チェックを避けることができます。これにより、コンパイラのパフォーマンスを維持しつつ、より厳密なコードの健全性チェックを実現しています。

## コアとなるコードの解説

### `typecheck.go` の変更点

1.  **`if !n.Bounded && Isconst(n.Right, CTINT)`**:
    *   `n.Right` はインデックスを表す式です。`Isconst(n.Right, CTINT)` は、そのインデックスがコンパイル時に決定できる定数整数であるかをチェックします。
    *   `!n.Bounded` は、この `OINDEX` ノードがコンパイラによって既に境界内であるとマークされていない場合にのみ、以下の静的境界チェックを実行することを示します。これにより、コンパイラが内部的に安全性を保証しているケース（例えば、デシュガーされたコード）での冗長なエラー報告を避けます。

2.  **`else if Isfixedarray(t) && x >= t.Bound`**:
    *   `Isfixedarray(t)` は、対象の型 `t` が固定長配列であるかをチェックします。
    *   `x` は定数インデックスの値です。`t.Bound` は配列の要素数（長さ）です。
    *   変更前は `t.Bound > 0` という条件がありましたが、これが削除されました。この削除により、`[0]byte{}` のように `t.Bound` が `0` である配列に対しても、`x >= t.Bound` のチェックが実行されるようになりました。
    *   `[0]byte{}[0]` の場合、`x` は `0`、`t.Bound` も `0` なので、`0 >= 0` が `true` となり、`Yyerror("invalid array index %v (out of bounds for %d-element array)", n.Right, t.Bound)` が呼び出され、コンパイルエラーとして「out of bounds」が報告されるようになります。

### `issue12944.go` のテストケース

このテストファイルは、変更が正しく機能することを確認するために追加されました。
`// errorcheck` ディレクティブは、このファイルがコンパイル時に特定のエラーを生成することを期待していることをコンパイラテストツールに伝えます。
`_ = unsafe.Sizeof([0]byte{}[0]) // ERROR "out of bounds"` の行は、`unsafe.Sizeof` の引数として `[0]byte{}[0]` を使用しています。この行の末尾にある `// ERROR "out of bounds"` は、この行が「out of bounds」というエラーメッセージを含むコンパイルエラーを生成することを期待していることを示します。このテストケースがパスすることで、コンパイラがゼロ要素配列に対する無効なインデックスアクセスを正しく検出するようになったことが確認できます。

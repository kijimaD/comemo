## 変更の背景

このコミットは、以前のコミット `f28bbb776a050cc3edca2bbe1241d81217a7a251` を元に戻す（リバートする）ものです。元のコミットでは、Goランタイムの内部構造体である `hiter` (マップイテレータ)、`hmap` (マップヘッダ)、`scase` (selectケース) の定義を、コンパイラがランタイムの型情報を認識するために使用する `src/cmd/compile/internal/gc/builtin.go` ファイルに移動していました。

しかし、この変更は、コンパイラがこれらの複雑なランタイム内部型を扱う方法において、いくつかの問題を引き起こした可能性があります。特に、コンパイラがこれらの型のメモリレイアウトを正確に把握し、ランタイムの実際の定義と同期させる必要性があるため、単に文字列として `builtin.go` に定義を置くだけでは不十分であったり、メンテナンス上の課題が生じたりしたと考えられます。

このリバートにより、これらの内部型は再びランタイムパッケージ (`src/runtime/hashmap.go`, `src/runtime/select.go`) で定義され、コンパイラ (`src/cmd/compile/internal/gc/reflect.go`, `src/cmd/compile/internal/gc/select.go`) は、これらのランタイム定義に基づいて自身の内部型表現を動的に構築するアプローチに戻されました。これは、コンパイラとランタイム間の型情報の整合性をより堅牢に保つための設計判断であると推測されます。具体的には、コンパイラがランタイムの内部構造体の正確なメモリレイアウトを「知っている」必要があるため、`builtin.go`のような静的な定義ではなく、コンパイラ自身の型システム内で動的に構築する方が、変更への追従や正確性の維持が容易であると判断されたのでしょう。

## 前提知識の解説

-   **Goコンパイラ (`src/cmd/compile/internal/gc`)**: Goソースコードを機械語に変換するGo言語の公式コンパイラの主要部分です。型チェック、AST (Abstract Syntax Tree) の変換、コード生成などを行います。
-   **Goランタイム (`src/runtime`)**: Goプログラムの実行をサポートする低レベルなコード群です。ガベージコレクション、スケジューラ、チャネル、マップなどの組み込み機能の実装が含まれます。
-   **`builtin.go` の役割**: Goコンパイラが、`newobject` や `makemap` といった特定のランタイム関数や、`map` や `select` のような組み込み型の内部構造を認識するために使用するファイルです。コンパイラは、このファイルに記述された情報に基づいて、ランタイムとのインターフェースを構築します。
-   **`hmap` 構造体**: Goの組み込み型である `map` の内部実装で使用されるハッシュマップのヘッダ構造体です。マップの要素数、バケットのポインタ、ハッシュシードなどの情報を含みます。そのメモリレイアウトは、マップの効率的な操作に不可欠です。
-   **`hiter` 構造体**: `for range` ループでマップをイテレートする際に、そのイテレーションの状態（現在のキー、値、マップへのポインタ、現在のバケットなど）を保持するために使用される内部構造体です。
-   **`scase` 構造体**: `select` ステートメントの各 `case` 句の情報を保持する内部構造体です。チャネル、送受信するデータ要素、プログラムカウンタなどの情報を含みます。
-   **型情報の同期の重要性**: Goコンパイラが生成するコードは、Goランタイムが定義するデータ構造（`hmap`, `hiter`, `scase`など）の正確なメモリレイアウトと一致している必要があります。もしコンパイラが誤ったレイアウトを前提にコードを生成すると、ランタイムエラーやクラッシュの原因となります。このため、コンパイラとランタイムの間でこれらの内部型の定義が常に同期していることが極めて重要です。
-   **`unsafe.Pointer` と型アサーション**: Goランタイムの内部では、しばしば `unsafe.Pointer` を用いて型安全性をバイパスし、メモリを直接操作します。これはパフォーマンス上の理由や、特定の低レベルな操作のために行われます。コンパイラがこれらの内部型を扱う際にも、`unsafe.Pointer` や `*any` (以前のGoバージョンでは `*byte` に相当する汎用ポインタ) を介して、具体的な型情報を抽象化しつつ、内部的には正しいメモリレイアウトを前提とする場合があります。

## 技術的詳細

このリバートコミットは、Goコンパイラとランタイム間の内部型定義の連携メカニズムを根本的に変更しています。

1.  **`builtin.go` からの型定義の削除と抽象化**:
    *   `src/cmd/compile/internal/gc/builtin.go` の `runtimeimport` 文字列から、`hbucket`, `hmap`, `hiter`, `scase` といったランタイム内部構造体の型定義が削除されました。これは、コンパイラがこれらの型を文字列として直接パースして利用するのではなく、別の、より動的な方法で扱うようになったことを意味します。
    *   同時に、`makemap`, `mapiterinit`, `mapiternext` といったランタイム関数のシグネチャにおいて、特定の内部型へのポインタ（例: `*@\"\\\".hmap`, `*@\"\\\".hiter`）が、よりジェネリックな `*any` (または `*byte`) に変更されました。これは、コンパイラがこれらの関数を呼び出す際に、具体的な型情報をコンパイラ内部で構築し、ランタイムにはより抽象的なポインタとして渡すようになったことを示唆します。これにより、コンパイラとランタイム間の結合度が緩和され、ランタイムの内部型定義の変更がコンパイラの`builtin.go`に直接影響を与えにくくなります。

2.  **コンパイラ内部での型構築の導入**:
    *   `src/cmd/compile/internal/gc/reflect.go` に、`hmap(t)` と `hiter(t)` という新しい関数が追加されました。これらの関数は、Goのマップ型 `t` を受け取り、それに対応するランタイムの `hmap` および `hiter` 構造体のコンパイラ内部表現を動的に構築します。具体的には、`hmap` や `hiter` の各フィールド（`count`, `flags`, `B`, `hash0`, `buckets` など）を `makefield` で定義し、それらを連結して構造体型を構築します。これにより、コンパイラはランタイムのメモリレイアウトと完全に一致する型情報を自身で生成できるようになり、マップ操作やイテレーションのためのコードを正確に生成できるようになります。
    *   同様に、`src/cmd/compile/internal/gc/select.go` の `selecttype` 関数内で、`select` ステートメントの内部処理に必要な `sudog` と `scase` 構造体が明示的に構築されるようになりました。以前は `syslook("scase", 0)` のようにシンボルルックアップに依存していましたが、この変更により、コンパイラがこれらの構造体のフィールドを直接定義し、`typecheck` を呼び出して型チェックを行います。これにより、`select` の内部動作に必要な型情報がコンパイラによって明示的に管理され、ランタイムとの整合性が保たれます。

3.  **ランタイムパッケージの変更と同期の明示化**:
    *   `src/runtime/hashmap.go` と `src/runtime/select.go` から、`hmap` や `hiter`、`scase` の定義が `builtin/runtime.go` と同期する必要があるというコメントが削除されました。これは、これらの型定義の「一次情報源」が `runtime` パッケージになり、コンパイラ側がそれを模倣する形になったことを示唆します。
    *   `src/runtime/hashmap.go` の `makemap` 関数では、`hmap` のサイズチェックに `t.hmap.size` が使われるようになり、`newobject(t.hmap)` で `hmap` が割り当てられるようになりました。これは、コンパイラが構築した `hmap` の型情報に基づいてメモリを割り当てることを意味し、コンパイラとランタイム間の型情報の厳密な同期が保証されます。
    *   `src/runtime/runtime2.go` と `src/runtime/select.go` のコメントが更新され、`sudog`, `hselect`, `scase` の定義が `src/cmd/internal/gc/select.go` の `selecttype` 関数と同期する必要があることが明示されました。

これらの変更は、Goコンパイラがランタイムの内部構造体の詳細なメモリレイアウトをより直接的かつ動的に管理することで、コンパイラとランタイム間の型情報の整合性を高め、将来的な変更に対する堅牢性を向上させることを目的としています。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラがランタイムの内部構造体（`hmap`, `hiter`, `scase`など）の型情報をどのように取得し、利用するかというメカニズムの変更にあります。

1.  **`src/cmd/compile/internal/gc/reflect.go` の `hmap(t)` および `hiter(t)` 関数**:
    これらの関数は、Goのマップ型 `t` を引数として受け取り、それに対応するランタイムの `hmap` (マップヘッダ) および `hiter` (マップイテレータ) 構造体のコンパイラ内部表現を動的に生成します。
    *   関数内部では、`makefield` を用いて各フィールド（例: `hmap` の `count`, `flags`, `B`, `hash0`, `buckets` など、`hiter` の `key`, `value`, `t`, `h`, `buckets` など）のシンボルと型を定義します。
    *   これらのフィールド定義を連結して、`typ(TSTRUCT)` で新しい構造体型を構築します。
    *   `dowidth(h)` や `dowidth(i)` を呼び出すことで、構築された構造体のメモリレイアウト（サイズやアライメント）を計算します。
    *   特に `hiter` の構築部分には、「`must match ../../../../runtime/hashmap.go:hiter.`」というコメントがあり、コンパイラがランタイムの実際の `hiter` 構造体のメモリレイアウトと厳密に一致する型情報を生成していることを強調しています。
    このアプローチにより、コンパイラはランタイムの内部構造体の詳細なレイアウトを正確に把握し、マップ操作やイテレーションのための効率的かつ正しい機械語コードを生成することが可能になります。

2.  **`src/cmd/compile/internal/gc/select.go` の `selecttype` 関数**:
    この関数は、`select` ステートメントの内部処理に必要な `sudog` (スケジューラ内部のゴルーチン記述子) と `scase` (selectケース記述子) 構造体の型を動的に構築するように変更されました。
    *   以前は `syslook("scase", 0)` のように、`builtin.go` に定義されたシンボルをルックアップして型情報を取得していましたが、この変更では `Nod(OTSTRUCT, nil, nil)` を使用して新しい構造体ノードを作成し、`Nod(ODCLFIELD, ...)` で各フィールド（例: `scase` の `elem`, `chan`, `pc`, `kind` など）を明示的に定義しています。
    *   その後、`typecheck(&scase, Etype)` を呼び出して、構築された構造体型がコンパイラの型システム内で正しく認識されるようにします。
    この変更により、`select` ステートメントの内部動作に必要な型情報がコンパイラによって直接的かつ明示的に管理されるようになり、ランタイムの `select` 関連構造体との整合性がより確実に保たれます。

これらの変更は、コンパイラがランタイムの内部構造体の詳細なメモリレイアウトをより直接的かつ動的に管理することで、コンパイラとランタイム間の型情報の整合性を高め、将来的な変更に対する堅牢性を向上させるという設計思想を反映しています。

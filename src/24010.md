`net/http: fix now-flaky TransportAndServerSharedBodyRace test`

`TestTransportAndServerSharedBodyRace` は、`issue #9662` が `https://golang.org/cl/11412` によって修正された後、不安定になりました。この修正により、`Handler` がリクエストボディの読み込みを早期に停止した場合に、サーバーがクライアントとの接続を切断するようになりました。

このテストは、テスト内の2つのゴルーチンがリクエストの一部しか読み込まないという競合状態によって影響を受けていました。これは、テストが本来検証しようとしていたこと（`*http.body` に対する同時 `Read/Close` 競合）にとっては不要な詳細でした。

また、このコミットでは、古いテストから派生した未使用の残骸も削除されています。そして、テストが失敗したときにデッドロックしないように修正されています（これが、テストがダッシュボードで2分のタイムアウトとして表示されていた理由です）。

`Fixes #11418`

## 変更の背景

このコミットの主な背景は、`net/http` パッケージの `TestTransportAndServerSharedBodyRace` というテストが、以前の変更によって不安定になったことです。

1.  **`issue #9662` と `CL 11412` によるサーバーの挙動変更**:
    以前、`issue #9662` の修正（`CL 11412` で実装）により、`net/http` サーバーの挙動が変更されました。具体的には、HTTPハンドラがリクエストボディの読み込みを途中で停止した場合（例えば、必要なデータだけを読み取って残りを破棄した場合）、サーバーはクライアントとの接続を適切に切断するようになりました。これは、リソースのリークを防ぎ、プロトコルに準拠するための重要な修正でした。

2.  **`TestTransportAndServerSharedBodyRace` の不安定化**:
    しかし、このサーバー挙動の変更が `TestTransportAndServerSharedBodyRace` に予期せぬ影響を与えました。このテストは、複数のゴルーチンがリクエストボディの一部だけを読み込むというシナリオを含んでいました。新しいサーバーの挙動では、ハンドラがボディの読み込みを途中でやめると接続が切断されるため、テスト内のゴルーチンが意図せず接続切断に遭遇し、テストが失敗したり、競合状態に陥ったりするようになりました。

3.  **テストのデッドロックとタイムアウト**:
    さらに、テストが失敗した場合にデッドロックが発生し、テストが完了せずに2分間のタイムアウトとして報告される問題も発生していました。これは、テストの信頼性を著しく低下させ、開発者が問題の根本原因を特定するのを困難にしていました。

このコミットは、これらの問題を解決し、`TestTransportAndServerSharedBodyRace` を再び安定させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびHTTPプロトコルに関する知識が役立ちます。

*   **Go言語の `net/http` パッケージ**: GoでHTTPクライアントとサーバーを構築するための標準ライブラリです。
    *   **`http.Handler` と `http.ResponseWriter`, `*http.Request`**: HTTPサーバーでリクエストを処理するためのインターフェースと構造体です。`*http.Request` の `Body` フィールドは `io.ReadCloser` インターフェースを満たし、クライアントから送信されたリクエストボディのデータを提供します。
    *   **`http.Transport`**: HTTPクライアントがネットワークリクエストを行うための低レベルな実装を提供します。
*   **`io.Reader` と `io.Writer` インターフェース**: Goの標準ライブラリで、データの読み書きを抽象化するための基本的なインターフェースです。
    *   **`io.CopyN(dst io.Writer, src io.Reader, n int64)`**: `src` から `dst` へ最大 `n` バイトをコピーする関数です。
    *   **`io.LimitReader(r io.Reader, n int64)`**: 指定された `io.Reader` から最大 `n` バイトまでしか読み取らない新しい `io.Reader` を返します。
    *   **`ioutil.Discard`**: `io.Writer` インターフェースを満たすオブジェクトで、書き込まれたデータをすべて破棄します。
*   **`httptest.NewServer`**: テスト目的でHTTPサーバーを簡単に起動するためのユーティリティ関数です。実際のネットワークポートをリッスンし、テスト用のURLを提供します。
*   **ゴルーチン (Goroutines) とチャネル (Channels)**: Goの並行処理の基本要素です。
    *   **ゴルーチン**: 軽量なスレッドのようなもので、関数を並行して実行するために使用されます。
    *   **チャネル**: ゴルーチン間でデータを安全にやり取りするための通信メカニズムです。デッドロックの回避や同期によく使われます。
*   **競合状態 (Race Condition)**: 複数のゴルーチンが共有リソースに同時にアクセスし、そのアクセス順序によってプログラムの最終結果が変わってしまうバグの一種です。
*   **Flaky Test (不安定なテスト)**: 特定の条件下で成功したり失敗したりするテストです。通常、競合状態や外部要因に依存している場合に発生します。
*   **デッドロック (Deadlock)**: 複数のプロセスやゴルーチンが互いに相手が保持しているリソースの解放を待ち続け、結果としてどのプロセスも進行できなくなる状態です。

## 技術的詳細

このコミットは、`net/http` パッケージのテスト `TestTransportAndServerSharedBodyRace` の信頼性を向上させるためのものです。

1.  **以前の修正 (`issue #9662` / `CL 11412`) の影響**:
    以前の修正は、HTTPハンドラがリクエストボディの読み込みを途中でやめた際に、サーバーがクライアントとの接続を適切に切断するように変更しました。これは、HTTP/1.1 の `Content-Length` ヘッダが指定されているにもかかわらず、ハンドラがボディ全体を読み込まない場合に、クライアントがサーバーからの応答を待ち続けることを防ぐための重要な改善でした。しかし、この変更により、テスト `TestTransportAndServerSharedBodyRace` が不安定になりました。

2.  **テストの設計と競合状態**:
    `TestTransportAndServerSharedBodyRace` は、本来 `*http.body` に対する同時 `Read/Close` 競合をテストすることを意図していました。しかし、テストの実装では、バックエンドサーバーとプロキシサーバーの両方がリクエストボディの一部しか読み込まないように設定されていました。
    *   バックエンドサーバーは `req.Body` から `bodySize/2` バイトをコピーしていました。
    *   プロキシサーバーはバックエンドからのレスポンスボディを `bodySize/4` バイトだけ `ioutil.Discard` にコピーしていました。
    この「一部だけ読み込む」という挙動が、前述のサーバー挙動変更と組み合わさることで、テスト内のゴルーチン間で競合状態を引き起こし、サーバーが接続を切断するタイミングがテストの期待と合わなくなり、テストが不安定になりました。コミットメッセージでは、この「一部だけ読み込む」という詳細が、本来テストが検証したい内容（`Read/Close` 競合）にとって「不必要な詳細」であったと指摘されています。

3.  **デッドロックの解消**:
    テストが失敗した場合にデッドロックが発生し、テストがタイムアウトする問題も存在しました。これは、テストのクリーンアップロジックが、特定のチャネル操作（`close(unblockBackend)` や `(<-backendRespc).Body.Close()`）に依存しており、テストが途中で失敗するとこれらの操作が実行されず、ゴルーチンがブロックされたままになるためでした。特に `unblockBackend` チャネルは、バックエンドサーバーがリクエストボディの読み込みを終えるのを待つために使用されていましたが、テストが途中で失敗するとこのチャネルが閉じられず、バックエンドゴルーチンが永久にブロックされる可能性がありました。

このコミットは、これらの問題を解決するために、テストのロジックを簡素化し、ボディの読み込み量を調整し、デッドロックを回避するための堅牢なクリーンアップメカニズムを導入しています。

## コアとなるコードの解説

変更は主に以下の3つの側面からテストの安定性を向上させています。

1.  **リクエストボディの読み込み量の調整**:
    *   **バックエンドサーバー**: `io.CopyN(rw, req.Body, bodySize/2)` が `io.CopyN(rw, req.Body, bodySize)` に変更されました。これにより、バックエンドサーバーはリクエストボディ全体を読み込むようになります。以前の「一部だけ読み込む」という挙動が、サーバーが接続を切断する原因となっていたため、これを修正することで、テストが意図しない接続切断に遭遇する可能性を減らします。
    *   **プロキシサーバー**: `io.CopyN(ioutil.Discard, bresp.Body, bodySize/4)` が `io.CopyN(ioutil.Discard, bresp.Body, bodySize/2)` に変更されました。プロキシサーバーがバックエンドからのレスポンスボディを破棄する量が増えました。これも、ボディの読み込みに関する競合状態を緩和し、テストの安定性を高めるための調整です。

2.  **不要なコードの削除**:
    *   プロキシサーバーのハンドラ内にあった `if req.RequestURI == "/foo"` ブロックが削除されました。コミットメッセージによると、これは古いテストからの「未使用の残骸」であり、テストの目的とは無関係でした。コードを簡素化し、テストの意図を明確にするために削除されました。

3.  **デッドロックの回避と堅牢なクリーンアップ**:
    *   `defer close(unblockBackend)` が追加されました。これは、`unblockBackend` チャネルを関数が終了する際に必ず閉じるようにするためのものです。これにより、テストが途中で失敗した場合でも、バックエンドサーバーのゴルーチンが `<-unblockBackend` でブロックされたままになることを防ぎ、デッドロックを回避します。
    *   テストの終盤にあった `(<-backendRespc).Body.Close()` が `select` ステートメントに置き換えられました。
        ```go
        select {
        case res := <-backendRespc:
            res.Body.Close()
        default:
            // We failed earlier. (e.g. on DefaultClient.Do(req2))
        }
        ```
        以前のコードでは、`backendRespc` チャネルからレスポンスが受信できない場合（例えば、テストが途中で失敗してチャネルに何も送信されなかった場合）、この行でデッドロックが発生していました。`select` ステートメントの `default` ケースを追加することで、チャネルに値がない場合でもブロックせずに処理を続行できるようになり、デッドロックを回避します。これにより、テストが失敗した場合でも、クリーンアップ処理が確実に実行されるようになります。

これらの変更により、`TestTransportAndServerSharedBodyRace` は、本来テストすべき `*http.body` の `Read/Close` 競合に焦点を当てつつ、以前のサーバー挙動変更による不安定性やデッドロックの問題を解消し、より信頼性の高いテストになりました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびHTTPプロトコルに関する知識が役立ちます。

*   **Go言語の `net/http` パッケージ**: GoでHTTPクライアントとサーバーを構築するための標準ライブラリです。
    *   **`http.Handler` と `http.ResponseWriter`, `*http.Request`**: HTTPサーバーでリクエストを処理するためのインターフェースと構造体です。`*http.Request` の `Body` フィールドは `io.ReadCloser` インターフェースを満たし、クライアントから送信されたリクエストボディのデータを提供します。
    *   **`http.Transport`**: HTTPクライアントがネットワークリクエストを行うための低レベルな実装を提供します。
*   **`io.Reader` と `io.Writer` インターフェース**: Goの標準ライブラリで、データの読み書きを抽象化するための基本的なインターフェースです。
    *   **`io.CopyN(dst io.Writer, src io.Reader, n int64)`**: `src` から `dst` へ最大 `n` バイトをコピーする関数です。
    *   **`io.LimitReader(r io.Reader, n int64)`**: 指定された `io.Reader` から最大 `n` バイトまでしか読み取らない新しい `io.Reader` を返します。
    *   **`ioutil.Discard`**: `io.Writer` インターフェースを満たすオブジェクトで、書き込まれたデータをすべて破棄します。
*   **`httptest.NewServer`**: テスト目的でHTTPサーバーを簡単に起動するためのユーティリティ関数です。実際のネットワークポートをリッスンし、テスト用のURLを提供します。
*   **ゴルーチン (Goroutines) とチャネル (Channels)**: Goの並行処理の基本要素です。
    *   **ゴルーチン**: 軽量なスレッドのようなもので、関数を並行して実行するために使用されます。
    *   **チャネル**: ゴルーチン間でデータを安全にやり取りするための通信メカニズムです。デッドロックの回避や同期によく使われます。
*   **競合状態 (Race Condition)**: 複数のゴルーチンが共有リソースに同時にアクセスし、そのアクセス順序によってプログラムの最終結果が変わってしまうバグの一種です。
*   **Flaky Test (不安定なテスト)**: 特定の条件下で成功したり失敗したりするテストです。通常、競合状態や外部要因に依存している場合に発生します。
*   **デッドロック (Deadlock)**: 複数のプロセスやゴルーチンが互いに相手が保持しているリソースの解放を待ち続け、結果としてどのプロセスも進行できなくなる状態です。

## 技術的詳細

このコミットは、`net/http` パッケージのテスト `TestTransportAndServerSharedBodyRace` の信頼性を向上させるためのものです。

1.  **以前の修正 (`issue #9662` / `CL 11412`) の影響**:
    以前の修正は、HTTPハンドラがリクエストボディの読み込みを途中でやめた際に、サーバーがクライアントとの接続を適切に切断するように変更しました。これは、HTTP/1.1 の `Content-Length` ヘッダが指定されているにもかかわらず、ハンドラがボディ全体を読み込まない場合に、クライアントがサーバーからの応答を待ち続けることを防ぐための重要な改善でした。しかし、この変更により、テスト `TestTransportAndServerSharedBodyRace` が不安定になりました。

2.  **テストの設計と競合状態**:
    `TestTransportAndServerSharedBodyRace` は、本来 `*http.body` に対する同時 `Read/Close` 競合をテストすることを意図していました。しかし、テストの実装では、バックエンドサーバーとプロキシサーバーの両方がリクエストボディの一部しか読み込まないように設定されていました。
    *   バックエンドサーバーは `req.Body` から `bodySize/2` バイトをコピーしていました。
    *   プロキシサーバーはバックエンドからのレスポンスボディを `bodySize/4` バイトだけ `ioutil.Discard` にコピーしていました。
    この「一部だけ読み込む」という挙動が、前述のサーバー挙動変更と組み合わさることで、テスト内のゴルーチン間で競合状態を引き起こし、サーバーが接続を切断するタイミングがテストの期待と合わなくなり、テストが不安定になりました。コミットメッセージでは、この「一部だけ読み込む」という詳細が、本来テストが検証したい内容（`Read/Close` 競合）にとって「不必要な詳細」であったと指摘されています。

3.  **デッドロックの解消**:
    テストが失敗した場合にデッドロックが発生し、テストがタイムアウトする問題も存在しました。これは、テストのクリーンアップロジックが、特定のチャネル操作（`close(unblockBackend)` や `(<-backendRespc).Body.Close()`）に依存しており、テストが途中で失敗するとこれらの操作が実行されず、ゴルーチンがブロックされたままになるためでした。特に `unblockBackend` チャネルは、バックエンドサーバーがリクエストボディの読み込みを終えるのを待つために使用されていましたが、テストが途中で失敗するとこのチャネルが閉じられず、バックエンドゴルーチンが永久にブロックされる可能性がありました。

このコミットは、これらの問題を解決するために、テストのロジックを簡素化し、ボディの読み込み量を調整し、デッドロックを回避するための堅牢なクリーンアップメカニズムを導入しています。

## コアとなるコードの解説

変更は主に以下の3つの側面からテストの安定性を向上させています。

1.  **リクエストボディの読み込み量の調整**:
    *   **バックエンドサーバー**: `io.CopyN(rw, req.Body, bodySize/2)` が `io.CopyN(rw, req.Body, bodySize)` に変更されました。これにより、バックエンドサーバーはリクエストボディ全体を読み込むようになります。以前の「一部だけ読み込む」という挙動が、サーバーが接続を切断する原因となっていたため、これを修正することで、テストが意図しない接続切断に遭遇する可能性を減らします。
    *   **プロキシサーバー**: `io.CopyN(ioutil.Discard, bresp.Body, bodySize/4)` が `io.CopyN(ioutil.Discard, bresp.Body, bodySize/2)` に変更されました。プロキシサーバーがバックエンドからのレスポンスボディを破棄する量が増えました。これも、ボディの読み込みに関する競合状態を緩和し、テストの安定性を高めるための調整です。

2.  **不要なコードの削除**:
    *   プロキシサーバーのハンドラ内にあった `if req.RequestURI == "/foo"` ブロックが削除されました。コミットメッセージによると、これは古いテストからの「未使用の残骸」であり、テストの目的とは無関係でした。コードを簡素化し、テストの意図を明確にするために削除されました。

3.  **デッドロックの回避と堅牢なクリーンアップ**:
    *   `defer close(unblockBackend)` が追加されました。これは、`unblockBackend` チャネルを関数が終了する際に必ず閉じるようにするためのものです。これにより、テストが途中で失敗した場合でも、バックエンドサーバーのゴルーチンが `<-unblockBackend` でブロックされたままになることを防ぎ、デッドロックを回避します。
    *   テストの終盤にあった `(<-backendRespc).Body.Close()` が `select` ステートメントに置き換えられました。
        ```go
        select {
        case res := <-backendRespc:
            res.Body.Close()
        default:
            // We failed earlier. (e.g. on DefaultClient.Do(req2))
        }
        ```
        以前のコードでは、`backendRespc` チャネルからレスポンスが受信できない場合（例えば、テストが途中で失敗してチャネルに何も送信されなかった場合）、この行でデッドロックが発生していました。`select` ステートメントの `default` ケースを追加することで、チャネルに値がない場合でもブロックせずに処理を続行できるようになり、デッドロックを回避します。これにより、テストが失敗した場合でも、クリーンアップ処理が確実に実行されるようになります。

これらの変更により、`TestTransportAndServerSharedBodyRace` は、本来テストすべき `*http.body` の `Read/Close` 競合に焦点を当てつつ、以前のサーバー挙動変更による不安定性やデッドロックの問題を解消し、より信頼性の高いテストになりました。

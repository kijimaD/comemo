## 変更の背景

`net/http` パッケージの `TestServerValidatesHostHeader` テストは、特定の条件下で不安定（flaky）であり、時にはハングアップする問題がありました。特に、Goの競合検出機能 (`-race` フラグ) を有効にして複数回 (`-count=1000`) 実行すると、この問題が顕著に現れていました。この種の不安定なテストは、CI/CDパイプラインの信頼性を低下させ、開発者が実際のバグとテストの不安定性を区別するのを困難にします。

このコミットは、この不安定性の根本原因が、テスト内で使用されているチャネルの同期メカニズムにあると特定し、その修正を目的としています。具体的には、`closec` という名前のチャネルがバッファなしで作成されていたことが、テスト内のゴルーチン間のタイミング依存性を生み出し、競合状態やデッドロックを引き起こしていたと考えられます。この問題は、GoのIssue #13950として報告されていました（ただし、Goの公式Issueトラッカーで直接この番号のIssueを見つけることはできませんでした。これは、Issueが移動されたか、古いGerritレビューシステムで管理されていた可能性を示唆しています）。

## 前提知識の解説

### Goのチャネル (Channels)

Go言語において、チャネルはゴルーチン（軽量スレッド）間で値を送受信するための主要な手段であり、同期プリミティブとしても機能します。チャネルを使用することで、共有メモリを直接操作する際の複雑なロックメカニズムを回避し、より安全で効率的な並行処理を実現できます。

### バッファなしチャネルとバッファありチャネル

チャネルには「バッファなし（unbuffered）」と「バッファあり（buffered）」の2種類があります。

1.  **バッファなしチャネル (`make(chan Type)`)**:
    *   バッファサイズが0のチャネルです。
    *   送信操作 (`ch <- value`) は、別のゴルーチンがそのチャネルから値を受信するまでブロックします。
    *   受信操作 (`value := <-ch`) は、別のゴルーチンがそのチャネルに値を送信するまでブロックします。
    *   つまり、送受信が同時に行われる「同期通信」を強制します。これは、特定のイベントが発生したことを正確に同期するのに非常に強力ですが、送受信のタイミングが少しでもずれると、どちらかの操作が永久にブロック（デッドロック）する可能性があります。

2.  **バッファありチャネル (`make(chan Type, capacity)`)**:
    *   `capacity` で指定された数の値を内部に保持できるチャネルです。
    *   送信操作は、チャネルのバッファが満杯でない限りブロックしません。バッファが満杯の場合のみブロックします。
    *   受信操作は、チャネルが空でない限りブロックしません。チャネルが空の場合のみブロックします。
    *   これにより、送受信のゴルーチンが厳密に同時に動作する必要がなくなり、非同期的な通信が可能になります。バッファサイズが1の場合、送信側は受信側が準備できていなくても、少なくとも1つの値をチャネルに書き込むことができます。

### テストにおける競合状態 (Race Conditions in Tests)

Goのテストにおいて、複数のゴルーチンが非同期に動作する場合、特にバッファなしチャネルのような厳密な同期メカニズムを使用していると、競合状態（Race Condition）が発生しやすくなります。競合状態とは、複数のゴルーチンが共有リソース（この場合はチャネル）にアクセスするタイミングによって、プログラムの最終結果が非決定的に変わってしまう現象です。

テストの文脈では、以下のような問題を引き起こします。
*   **Flakiness (不安定性)**: テストが実行されるたびに、成功したり失敗したり、あるいはハングアップしたりと、結果が一定しない状態。これは、ゴルーチンのスケジューリングや実行環境のわずかな違いによって、競合状態の発生パターンが変わるためです。
*   **Deadlock (デッドロック)**: 複数のゴルーチンがお互いの完了を待ち続け、どのゴルーチンも処理を進められなくなる状態。テストがハングアップするのは、通常デッドロックが原因です。

Goには `go test -race` という強力な競合検出ツールがあり、テスト中に発生した競合状態を特定するのに役立ちます。このツールは、共有メモリへの非同期アクセスを監視し、問題があれば報告します。

### HTTP Hostヘッダーの検証

HTTPプロトコルにおいて、`Host` ヘッダーはクライアントがアクセスしようとしているサーバーのドメイン名とポート番号を指定します。Webサーバーは、この `Host` ヘッダーを検証して、正しい仮想ホストにリクエストをルーティングしたり、セキュリティ上のチェックを行ったりします。`net/http` パッケージのサーバーは、この `Host` ヘッダーがRFCに準拠しているか、不正な文字を含んでいないかなどを検証するロジックを持っています。`TestServerValidatesHostHeader` は、この検証ロジックが正しく機能するかを確認するためのテストです。

## 技術的詳細

このコミットの技術的な核心は、`testConn` 構造体内の `closec` チャネルの定義を、バッファなしチャネルからバッファサイズ1のチャネルに変更した点にあります。

元のコードでは、`closec: make(chan bool)` となっており、これはバッファなしチャネルでした。`testConn` はテスト用のネットワーク接続を模倣する構造体であり、`closec` チャネルは接続のクローズやテストの終了をシグナルするために使用されていたと推測されます。

バッファなしチャネルの場合、`closec <- true` のような送信操作は、別のゴルーチンが `<-closec` の受信操作を行うまでブロックします。同様に、受信操作も送信操作が行われるまでブロックします。テストコードが複数のゴルーチンを起動し、これらのゴルーチンが `closec` を介して同期しようとしていた場合、以下のようなシナリオで不安定性が発生する可能性がありました。

1.  **送信側がブロックし、テストがハングアップ**: テストのメインゴルーチンが `closec` からの受信を期待しているにもかかわらず、別のゴルーチンが `closec` に送信しようとして、受信側がまだ準備できていないために送信側がブロックしてしまう。このブロックが解消されないままテストのタイムアウトが発生するか、テスト全体がデッドロックに陥る。
2.  **受信側がブロックし、テストがハングアップ**: 逆に、送信側が値を送った後、受信側が何らかの理由で遅延し、送信側が次の処理に進めずにブロックしてしまう。

`make(chan bool, 1)` への変更は、`closec` をバッファサイズ1のチャネルに変換します。これにより、送信側は受信側がまだ準備できていなくても、少なくとも1つの値をチャネルに書き込むことができます。この「一時的な格納場所」があることで、送信側はすぐにブロックされることなく処理を続行できる可能性が高まります。

この変更は、テスト内のゴルーチン間の厳密なタイミング依存性を緩和し、競合状態が発生する可能性を低減します。特に、テストのセットアップやクリーンアップのフェーズで発生しがちな、ゴルーチンの起動とチャネル操作のタイミングのずれによるハングアップを防ぐ効果があります。`go test -race -count=1000` での実行時にハングアップしなくなったというコミットメッセージは、この変更が実際にタイミングに起因する競合状態を解消したことを強く示唆しています。

## コアとなるコードの解説

上記のdiffが示すように、変更は `src/net/http/serve_test.go` ファイル内の2箇所で行われています。

1.  `TestServerValidatesHostHeader` 関数内:
    ```go
    -		conn := &testConn{closec: make(chan bool)}
    +		conn := &testConn{closec: make(chan bool, 1)}
    ```
2.  `TestServerValidatesHeaders` 関数内:
    ```go
    -		conn := &testConn{closec: make(chan bool)}
    +		conn := &testConn{closec: make(chan bool, 1)}
    ```

どちらの変更も、`testConn` 構造体の `closec` フィールドを初期化する際に、`make(chan bool)`（バッファなしチャネル）から `make(chan bool, 1)`（バッファサイズ1のチャネル）へと変更しています。

この変更により、`testConn` インスタンスが作成される際に、`closec` チャネルは1つのブール値を格納できるバッファを持つようになります。これにより、`testConn` を使用するゴルーチンが `closec` に値を送信しようとした際、受信側がまだ準備できていなくても、少なくとも1回はブロックせずに送信操作を完了できるようになります。

この小さな変更が、テスト内の非同期処理におけるタイミングのずれを吸収し、送信側ゴルーチンが不必要にブロックされることを防ぎます。結果として、テストがデッドロックに陥ったり、競合状態によって非決定的な結果を生じたりする可能性が大幅に低減され、テストの安定性と信頼性が向上しました。

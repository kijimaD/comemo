# [インデックス 25138] ファイルの概要

このコミットは、Go言語の標準フォーマッタである`gofmt`ツールと、Goコードのフォーマット機能を提供する`go/format`パッケージにおける内部依存関係の整理を目的としています。具体的には、`internal/format`という内部パッケージへの依存を解消し、その機能を`cmd/gofmt`と`go/format`のそれぞれの内部実装として再配置することで、パッケージ間の結合度を低減し、よりクリーンなアーキテクチャを実現しています。

## 変更の背景

Go言語のパッケージシステムには、`internal`という特別なディレクトリがあります。このディレクトリ内のパッケージは、その親ディレクトリのパッケージからのみインポート可能であり、外部のパッケージからはアクセスできません。これは、特定の機能がプロジェクト内部でのみ使用されるべきであり、外部に公開されるべきではない場合に、意図しない依存関係を防ぐための強力なメカニズムです。

このコミット以前は、`go/format`パッケージと`cmd/gofmt`ツールが、`src/internal/format`というパッケージに依存していました。この依存関係は、`internal`パッケージの設計思想に反するものでした。`go/format`はGoの標準ライブラリの一部であり、`gofmt`は広く利用されるツールであるため、これらが内部的な、かつ変更される可能性のあるパッケージに直接依存していることは、将来的なメンテナンス性や安定性の観点から望ましくありませんでした。

コミットメッセージにある「Fixes #11844」は、この問題がGoのIssueトラッカーで報告されていたことを示唆しています。この変更の主な目的は、`internal`パッケージの意図に沿った形でコードベースを整理し、`go/format`と`cmd/gofmt`がより自律的に機能するようにすることでした。

## 前提知識の解説

*   **Goのパッケージと`internal`パッケージ**: Go言語では、コードはパッケージにまとめられます。`internal`という名前のディレクトリ内にあるパッケージは、その`internal`ディレクトリの親ディレクトリにあるパッケージからのみインポートできます。例えば、`a/internal/b`というパッケージは`a`パッケージからのみインポート可能で、`c`パッケージからはインポートできません。これは、ライブラリの内部実装の詳細を外部から隠蔽し、APIの安定性を保つために使用されます。
*   **`go/format`パッケージ**: Goの標準ライブラリの一部で、Goのソースコードを整形するための機能を提供します。抽象構文木（AST）を操作し、標準的なGoのスタイルガイドに沿ってコードを再フォーマットします。
*   **`cmd/gofmt`ツール**: `go/format`パッケージの機能を利用して、Goのソースファイルを自動的に整形するコマンドラインツールです。Go開発者にとって不可欠なツールの一つであり、コードの一貫性を保つ上で重要な役割を果たします。
*   **`go/ast` (Abstract Syntax Tree)**: Goのソースコードを解析して得られる抽象構文木を表現するパッケージです。`gofmt`や`go/format`は、ソースコードをASTに変換し、ASTを操作することでコードの整形を行います。
*   **`go/token`**: ソースコード内の位置（ファイル、行、列など）を管理するためのパッケージです。`go/ast`と組み合わせて使用されます。
*   **`go/printer`**: 抽象構文木（AST）をGoのソースコードとして出力するためのパッケージです。`go/format`はこのパッケージを利用して整形されたコードを生成します。
*   **コードの断片の整形**: `gofmt`や`go/format`は、完全なGoのソースファイルだけでなく、宣言リストやステートメントリストのようなコードの断片も整形できる機能を持っています。これは、IDEやエディタの補完機能などで部分的なコードを整形する際に役立ちます。

## 技術的詳細

このコミットの技術的な核心は、`src/internal/format`パッケージが提供していた`Parse`および`Format`関数を、`cmd/gofmt`と`go/format`のそれぞれのパッケージ内に「プライベートな」形で再実装することです。これにより、`internal`パッケージへの直接的な依存を解消しつつ、必要な機能を維持しています。

具体的な変更点は以下の通りです。

1.  **機能の複製と再配置**:
    *   元の`src/internal/format/format.go`にあった`Parse`、`Format`、`IsSpace`関数が、`src/cmd/gofmt/internal.go`と`src/go/format/internal.go`という二つの新しいファイルに複製されました。
    *   これらの関数は、それぞれのパッケージ内でプライベートな関数（先頭小文字の`parse`、`format`、`isSpace`）として定義し直されました。これにより、これらの関数はそれぞれのパッケージ内でのみ利用可能となり、外部からのアクセスが不可能になります。
2.  **パッケージ名の変更**:
    *   `src/internal/format/format.go`は`src/go/format/internal.go`にリネームされました。これは、`go/format`パッケージの内部実装であることを明確にするためです。
3.  **依存関係の解消**:
    *   `src/cmd/gofmt/gofmt.go`と`src/go/format/format.go`から`import "internal/format"`の記述が削除されました。
    *   これらのファイル内で`format.Parse`や`format.Format`として呼び出されていた関数は、それぞれ自身のパッケージ内で定義された`parse`や`format`関数に置き換えられました。
4.  **`TODO`コメントの追加**:
    *   新しく作成された`src/cmd/gofmt/internal.go`と`src/go/format/internal.go`の冒頭には、両ファイルが同一の内容であることを示す`TODO(gri)`コメントが追加されています。これは、現在の解決策が依存関係の解消を優先したものであり、将来的にはこれらの共通機能をより良い形でファクタリングする余地があることを示唆しています。

このアプローチにより、`go/format`と`cmd/gofmt`は、`internal`パッケージの制約に縛られることなく、必要なフォーマット機能を独立して提供できるようになりました。また、`internal`パッケージの本来の意図（内部実装の隠蔽）が尊重される形となりました。

## コアとなるコードの解説

このコミットで導入された`parse`および`format`関数（`src/cmd/gofmt/internal.go`と`src/go/format/internal.go`に存在する）は、Goのコード整形ロジックの核心を担っています。

### `parse` 関数

この関数は、与えられたソースコードのバイトスライスをGoの抽象構文木（AST）として解析します。特徴的なのは、完全なGoファイルだけでなく、コードの断片（宣言リストやステートメントリスト）も適切に処理できる点です。

1.  **完全なソースファイルとしての解析**: まず、`parser.ParseFile`を使ってソースコードを完全なGoファイルとして解析を試みます。エラーがなければ、そのままASTを返します。
2.  **宣言リストとしての解析**: もし解析エラーが「`expected 'package'`」（パッケージ宣言がない）という内容であれば、ソースコードが宣言リストである可能性を考慮します。この場合、一時的にソースコードの先頭に「`package p;`」というパッケージ宣言を挿入し、再度`parser.ParseFile`で解析を試みます。成功した場合、整形後のコードからこの一時的なパッケージ宣言を削除するための`sourceAdj`関数と、インデント調整のための`indentAdj`を返します。
3.  **ステートメントリストとしての解析**: さらにエラーが「`expected declaration`」（宣言がない）という内容であれば、ソースコードがステートメントリストである可能性を考慮します。この場合、一時的にソースコードを「`package p; func _() {`」と「`\n\n}`」で囲み、関数本体として解析を試みます。成功した場合、同様に整形後のコードから一時的なラッパーを削除するための`sourceAdj`関数と、インデント調整のための`indentAdj`を返します。

この多段階の解析アプローチにより、`gofmt`は様々な形式のGoコード（完全なファイル、宣言の断片、ステートメントの断片）を柔軟に整形できます。

### `format` 関数

この関数は、`parse`関数によって生成されたASTと、元のソースコード、そして`parse`関数が返した`sourceAdj`および`indentAdj`情報を受け取り、最終的な整形済みバイトスライスを生成します。

1.  **完全なソースファイルの場合**: `sourceAdj`が`nil`の場合（つまり、元のソースが完全なファイルだった場合）、`printer.Fprint`を使ってASTを直接バイトスライスに変換します。
2.  **部分的なソースファイルの場合**: `sourceAdj`が`nil`でない場合（つまり、コードの断片だった場合）、以下の手順で整形を行います。
    *   **先行する空白の保持**: 元のソースコードの先頭にあった改行やスペースを保持します。
    *   **インデントの調整**: 元のソースコードの最初のコード行のインデントレベルを検出し、それを基に整形後のコードのインデントを調整します。`indentAdj`はこの調整に利用されます。
    *   **ASTの整形**: `printer.Fprint`を使ってASTをバイトスライスに変換します。この際、`cfg.Indent`に`indent + indentAdj`を設定することで、適切なインデントレベルで整形されます。
    *   **ソース調整関数の適用**: `parse`関数から返された`sourceAdj`関数を整形済みバイトスライスに適用し、一時的に追加されたパッケージ宣言や関数ラッパーを削除します。
    *   **後続する空白の保持**: 元のソースコードの末尾にあった改行やスペースを保持します。

### `isSpace` 関数

これは、与えられたバイトがスペース文字（`' '`, `'\t'`, `'\n'`, `'\r'`）であるかを判定するシンプルなヘルパー関数です。主に`format`関数内で、先行・後続する空白を処理するために使用されます。

これらの関数が`internal`パッケージから各パッケージのプライベートな関数として移動されたことで、`go/format`と`cmd/gofmt`は、外部に公開されるべきではない実装の詳細を内部に閉じ込めることに成功しました。

## 元コミット内容

このコミットの元の内容は、`net/http` パッケージの `client_test.go` ファイルにおいて、`TestClientTimeout_Headers` テストがHTTP/2モードで実行されないように変更することです。これは、特定のHTTP/2関連のバグ（golang.org/issue/13540）が存在するため、テストが失敗するのを避けるための暫定的な措置です。また、テストコード自体も `newClientServerTest` ヘルパー関数を使用するようにリファクタリングされ、HTTP/1とHTTP/2の両方のシナリオをより明確にテストできるように分割されています。

## 変更の背景

この変更の主な背景は、Goの `net/http` クライアントにおけるタイムアウト処理がHTTP/2プロトコルで正しく機能しない、または期待通りに動作しないという問題（golang.org/issue/13540）が存在したためです。`TestClientTimeout_Headers` は、クライアントがヘッダーを受信する前にタイムアウトするシナリオをテストするものでしたが、HTTP/2モードではこのテストが不安定になるか、誤って失敗する可能性がありました。

Go言語はHTTP/2のサポートを導入していましたが、新しいプロトコルスタックと既存のタイムアウトメカニズムとの間に互換性の問題や未解決のバグが存在することがありました。このコミットは、その問題が解決されるまでの間、テストスイートの安定性を保つために、問題のあるテストをHTTP/2モードで一時的にスキップすることを目的としています。これにより、CI/CDパイプラインが不必要な失敗で中断されるのを防ぎつつ、根本的な問題の調査と修正に集中できる環境を確保しました。

## 前提知識の解説

### Go言語の `net/http` パッケージ

`net/http` パッケージは、Go言語でHTTPクライアントおよびサーバーを実装するための標準ライブラリです。Webアプリケーションの構築やHTTPリクエストの送信に広く利用されます。

### HTTP/1.1 と HTTP/2

*   **HTTP/1.1**: 広く普及しているHTTPプロトコルのバージョンです。リクエスト/レスポンスのシーケンスは通常、1つのTCP接続につき1つであり、複数のリソースを並行して取得するには複数のTCP接続が必要になります。
*   **HTTP/2**: HTTP/1.1のパフォーマンス上の課題を解決するために設計された新しいプロトコルです。主な特徴として、多重化（Multiplexing）、ヘッダー圧縮（HPACK）、サーバープッシュなどがあります。これにより、単一のTCP接続上で複数のリクエストとレスポンスを並行して処理でき、Webページのロード時間を大幅に短縮できます。

### `Client.Timeout`

Goの `net/http.Client` 構造体には `Timeout` フィールドがあります。これは、HTTPリクエスト全体（接続確立、リクエスト送信、ヘッダー受信、ボディ受信を含む）にかかる時間の最大値を設定します。この時間を超えると、リクエストはキャンセルされ、エラーが返されます。このテストは、特にヘッダーを受信する前のタイムアウト動作を検証しようとしています。

### `httptest` パッケージ

`httptest` パッケージは、HTTPハンドラーやクライアントのテストを容易にするためのユーティリティを提供します。`httptest.NewServer` は、テスト中に使用できるローカルのHTTPサーバーを起動し、実際のネットワーク通信をシミュレートします。

### `t.Skip()`

Goのテストフレームワーク `testing` パッケージの一部で、`t.Skip()` は現在のテストをスキップするために使用されます。これは、特定の条件（例: 短時間テストモード、特定の環境、既知のバグ）下でテストを実行したくない場合に便利です。

### `golang.org/issue/13540`

これはGoプロジェクトのIssueトラッカーにおける特定のバグ報告へのリンクです。このIssueは、`net/http` クライアントのタイムアウト処理がHTTP/2で正しく機能しない問題について議論していると考えられます。コミットメッセージから、このIssueがこのテストスキップの直接的な原因であることがわかります。

## 技術的詳細

このコミットの技術的な変更点は以下の通りです。

1.  **テストの分割**: 元々 `TestClientTimeout_Headers` という単一のテスト関数でHTTP/1とHTTP/2の両方をカバーしようとしていたものを、`TestClientTimeout_Headers_h1` と `TestClientTimeout_Headers_h2` の2つの関数に分割しました。これにより、各プロトコルモードでのテストの意図が明確になります。
2.  **HTTP/2テストのスキップ**: `TestClientTimeout_Headers_h2` 関数内で `t.Skip("skipping in http2 mode; golang.org/issue/13540")` が呼び出されています。これは、Issue 13540で報告されているHTTP/2モードでのタイムアウト問題が解決されるまで、このテストを意図的にスキップすることを意味します。
3.  **`newClientServerTest` ヘルパーの導入/利用**: 変更されたコードでは、`httptest.NewServer` を直接使用する代わりに `newClientServerTest` というヘルパー関数（またはそれに相当するロジック）が利用されています。このヘルパーは、HTTP/1とHTTP/2の両方でテストサーバーとクライアントをセットアップするための共通のロジックをカプセル化していると考えられます。これにより、テストコードの重複が減り、保守性が向上します。
4.  **テストサーバーのライフサイクル管理**: `httptest.NewServer` の代わりに `newClientServerTest` を使用することで、テストサーバーのクリーンアップ（`defer ts.Close()` から `defer cst.close()` へ）も一元的に管理されるようになっています。
5.  **タイムアウト設定の変更**: クライアントのタイムアウト設定 (`c.Timeout = 500 * time.Millisecond`) が、`newClientServerTest` が返すクライアント (`cst.c`) に対して行われるよう変更されています。

この変更は、Goの `net/http` パッケージがHTTP/2をサポートする過程で発生した、プロトコル固有の複雑性に対処する典型的な例です。HTTP/2は多重化やストリームの概念を導入するため、HTTP/1.1とは異なる方法でタイムアウトや接続管理を処理する必要があります。この違いが、特定のタイムアウトシナリオでテストの失敗を引き起こしたと考えられます。

## コアとなるコードの解説

このコミットでは、`src/net/http/client_test.go` ファイルが変更されています。

1.  **新しいテスト関数の追加**:
    *   `func TestClientTimeout_Headers_h1(t *testing.T) { testClientTimeout_Headers(t, h1Mode) }`
    *   `func TestClientTimeout_Headers_h2(t *testing.T) { t.Skip("skipping in http2 mode; golang.org/issue/13540"); testClientTimeout_Headers(t, h2Mode) }`
    これらの行は、元の `TestClientTimeout_Headers` 関数を、HTTP/1モード (`h1Mode`) とHTTP/2モード (`h2Mode`) のそれぞれで実行されるように分割しています。特に `TestClientTimeout_Headers_h2` では、`t.Skip()` を呼び出して、Issue 13540で報告されている問題が解決されるまでHTTP/2モードでのテストをスキップしています。

2.  **元のテスト関数のリファクタリング**:
    *   `func TestClientTimeout_Headers(t *testing.T)` が `func testClientTimeout_Headers(t *testing.T, h2 bool)` に変更されました。これにより、この関数は内部ヘルパー関数となり、`h2` 引数によってHTTP/1とHTTP/2のどちらのモードでテストを実行するかを制御できるようになりました。

3.  **テストサーバーのセットアップの変更**:
    *   `- ts := httptest.NewServer(...)` から `+ cst := newClientServerTest(t, h2, ...)` へ変更されています。これは、テストサーバーのセットアップに `newClientServerTest` というヘルパー関数を使用するように切り替えたことを示しています。このヘルパー関数は、HTTP/1とHTTP/2の両方に対応したテストクライアントとサーバーのペア (`cst`) を提供します。
    *   `- defer ts.Close()` から `+ defer cst.close()` へ変更され、テストサーバーのクリーンアップも `cst` オブジェクトを通じて行われるようになりました。

4.  **クライアントのタイムアウト設定とリクエストの実行**:
    *   `- c := &Client{Timeout: 500 * time.Millisecond}` と `- _, err := c.Get(ts.URL)` が、
    *   `+ cst.c.Timeout = 500 * time.Millisecond` と `+ _, err := cst.c.Get(cst.ts.URL)` に変更されています。
    これは、`newClientServerTest` が提供するクライアント (`cst.c`) に対してタイムアウトを設定し、そのクライアントを使用してリクエスト (`cst.ts.URL`) を送信するように変更されたことを意味します。

これらの変更により、テストコードはよりモジュール化され、HTTP/1とHTTP/2のテストシナリオを個別に管理できるようになりました。また、HTTP/2における既知の問題に対しては、一時的なスキップメカニズムが導入されています。

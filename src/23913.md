# [インデックス 23913] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/url` パッケージにおけるURLのパス処理に関する重要な改善を導入しています。具体的には、URL構造体 `URL` に `RawPath` フィールドを追加し、URLのパスに含まれるエンコードされたスラッシュ（`%2F`）の扱いをより柔軟かつ正確にするための変更が行われました。

影響を受けるファイルは以下の通りです。

*   `src/net/url/example_test.go`: `URL` の新しい動作を示すためのテスト例が追加されました。特に `ExampleURL_roundtrip` は `RawPath` の挙動を明確に示しています。
*   `src/net/url/url.go`: `URL` 構造体の定義が変更され、`RawPath` フィールドが追加されました。また、`Parse` 関数が `RawPath` を設定するように修正され、`EscapedPath` メソッドおよび `validEncodedPath` ヘルパー関数が追加されました。`String()` および `RequestURI()` メソッドも `EscapedPath` を利用するように更新されています。
*   `src/net/url/url_test.go`: `URL` の新しい `RawPath` フィールドと `EscapedPath` メソッドの動作を検証するためのテストケースが追加・修正されました。特に、`%2F` を含むパスのラウンドトリップテストが強化されています。

## コミット

```
net/url: add RawPath field, a hint at the desired encoding of Path

Historically we have declined to try to provide real support for URLs
that contain %2F in the path, but they seem to be popping up more
often, especially in (arguably ill-considered) REST APIs that shoehorn
entire paths into individual path elements.

The obvious thing to do is to introduce a URL.RawPath field that
records the original encoding of Path and then consult it during
URL.String and URL.RequestURI. The problem with the obvious thing
is that it breaks backward compatibility: if someone parses a URL
into u, modifies u.Path, and calls u.String, they expect the result
to use the modified u.Path and not the original raw encoding.

Split the difference by treating u.RawPath as a hint: the observation
is that there are many valid encodings of u.Path. If u.RawPath is one
of them, use it. Otherwise compute the encoding of u.Path as before.

If a client does not use RawPath, the only change will be that String
selects a different valid encoding sometimes (the original passed
to Parse).

This ensures that, for example, HTTP requests use the exact
encoding passed to http.Get (or http.NewRequest, etc).

Also add new URL.EscapedPath method for access to the actual
escaped path. Clients should use EscapedPath instead of
reading RawPath directly.

All the old workarounds remain valid.
```

## 元コミット内容

`net/url`: `RawPath` フィールドを追加し、`Path` の望ましいエンコーディングのヒントとする

歴史的に、パスに `%2F` を含むURLに対する真のサポートを提供することは避けてきましたが、特に（議論の余地はあるものの）パス全体を個々のパス要素に詰め込むREST APIにおいて、そのようなURLがより頻繁に出現するようになりました。

明白な解決策は、`URL.RawPath` フィールドを導入し、`Path` の元のエンコーディングを記録し、`URL.String` および `URL.RequestURI` の際にそれを参照することです。この明白な解決策の問題点は、後方互換性を損なうことです。もし誰かがURLを `u` にパースし、`u.Path` を変更し、`u.String` を呼び出した場合、彼らは元の生のエンコーディングではなく、変更された `u.Path` を使用した結果を期待するでしょう。

`u.RawPath` をヒントとして扱うことで、この問題を解決します。`u.Path` には多くの有効なエンコーディングが存在するという観察に基づいています。もし `u.RawPath` がそれらのうちの1つであれば、それを使用します。そうでなければ、以前と同様に `u.Path` のエンコーディングを計算します。

クライアントが `RawPath` を使用しない場合、唯一の変更点は、`String` が（`Parse` に渡された元のエンコーディングを）異なる有効なエンコーディングを時々選択するようになることです。

これにより、例えばHTTPリクエストが `http.Get` (または `http.NewRequest` など) に渡された正確なエンコーディングを使用することが保証されます。

また、実際のエスケープされたパスにアクセスするための新しい `URL.EscapedPath` メソッドも追加します。クライアントは `RawPath` を直接読み取る代わりに `EscapedPath` を使用すべきです。

古い回避策はすべて引き続き有効です。

## 変更の背景

このコミットの背景には、Go言語の `net/url` パッケージがURLのパスを処理する際の、特にエンコードされたスラッシュ（`%2F`）に関する長年の課題がありました。

従来の `net/url` パッケージでは、URLをパースする際にパスに含まれる `%2F` をデコードして `/` として扱っていました。例えば、`https://example.com/foo%2Fbar` というURLは、`URL.Path` フィールドでは `/foo/bar` となります。これは、ほとんどのWebサーバーがパスを正規化する際に `%2F` を `/` と同じ意味で扱うため、一般的な用途では問題ありませんでした。

しかし、RESTful APIの設計において、パスセグメント内に意図的に `%2F` を含めるケースが増えてきました。例えば、`GET /api/resource/path%2Fwith%2Fslashes` のように、`path/with/slashes` という文字列全体を単一のリソース識別子として扱いたい場合です。この場合、`net/url` が `%2F` を `/` にデコードしてしまうと、元の意図が失われ、APIエンドポイントが正しく解釈されないという問題が発生していました。

この問題に対処するため、開発者は `req.RequestURI` を直接参照したり、`URL` 構造体の `Opaque` フィールドを使用したりするなど、いくつかの回避策を講じる必要がありました。しかし、これらの回避策は直感的ではなく、使いにくいものでした。

このコミットは、これらの問題を解決し、`%2F` を含むパスの扱いを改善することを目的としています。特に、`URL.String()` や `URL.RequestURI()` メソッドが、元のURLのエンコーディングを可能な限り保持するようにすることで、HTTPリクエストが意図した通りのパスで送信されるようにします。

また、後方互換性の問題も考慮されています。もし `RawPath` を単に元のエンコーディングとして導入し、`String()` メソッドが常にそれを使用するようにすると、ユーザーが `u.Path` を変更した後に `u.String()` を呼び出した際に、変更が反映されないという予期せぬ挙動を引き起こす可能性があります。このため、`RawPath` は「ヒント」として扱われ、`Path` の有効なエンコーディングである場合にのみ使用されるという、巧妙な解決策が採用されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

1.  **URLの構造**:
    *   URL (Uniform Resource Locator) は、インターネット上のリソースを一意に識別するための文字列です。
    *   一般的なURLの構造は `scheme://user:password@host:port/path?query#fragment` となります。
    *   `net/url.URL` 構造体は、これらの各要素をフィールドとして持ちます。
    *   `Path` フィールドは、リソースのパス部分を表します。

2.  **URLエンコーディング (パーセントエンコーディング)**:
    *   URLには、特定の文字（予約文字）をそのまま使用できないという制約があります。例えば、スペースや一部の記号はURLの構文と衝突するため、特別な形式で表現する必要があります。
    *   このために使用されるのがパーセントエンコーディングです。予約文字は `%` の後にその文字のASCII値の16進数表現を2桁続けて記述することでエンコードされます。
    *   例: スペースは `%20`、スラッシュ `/` は `%2F` とエンコードされます。
    *   `net/url` パッケージには、`PathEscape` や `QueryEscape` といったエンコード・デコード関数が用意されています。

3.  **`net/url` パッケージの `URL` 構造体**:
    *   `Scheme`: プロトコル (例: `http`, `https`)
    *   `Host`: ホスト名とポート番号 (例: `www.example.com:8080`)
    *   `Path`: デコードされたパス (例: `/foo/bar`)
    *   `RawQuery`: エンコードされたクエリ文字列 (例: `q=golang%20url`)
    *   `Fragment`: フラグメント (例: `section1`)
    *   `Opaque`: スキーム固有のエンコードされたデータ。`Path` や `RawQuery` とは排他的に使用されます。

4.  **`URL.Parse()` メソッド**:
    *   文字列形式のURLを `URL` 構造体にパースします。
    *   この際、`Path` フィールドは通常デコードされた形式で格納されます。つまり、`%2F` は `/` に変換されます。

5.  **`URL.String()` メソッド**:
    *   `URL` 構造体の内容を元の文字列形式のURLに再構築します。
    *   このメソッドがどのようにパスをエンコードするかが、このコミットの主要な変更点です。

6.  **`URL.RequestURI()` メソッド**:
    *   HTTPリクエストの `Request-URI` ヘッダで使用される形式の文字列を返します。これは通常、パスとクエリ文字列を含みます。

7.  **`%2F` の特殊性**:
    *   URLのパスセグメント区切り文字である `/` は、エンコードされると `%2F` となります。
    *   多くのWebサーバーやフレームワークは、セキュリティやパスの正規化のために、受信したURLの `%2F` を自動的に `/` にデコードしてしまいます。これにより、`path%2Fwith%2Fslashes` のようなパスが `path/with/slashes` と解釈され、意図しないルーティングやリソース解決が行われる可能性があります。
    *   この挙動はRFC 3986 (Uniform Resource Identifier (URI): Generic Syntax) のセクション 3.3 Path に関連しますが、実装によっては解釈が異なることがあります。

## 技術的詳細

このコミットの核心は、`net/url` パッケージがURLのパスを扱う方法を、後方互換性を維持しつつ、より柔軟かつ正確にする点にあります。

### `RawPath` フィールドの導入

`URL` 構造体に新しい `RawPath` フィールドが追加されました。

```go
type URL struct {
	Scheme   string
	Opaque   string    // encoded opaque data
	User     *Userinfo // username and password information
	Host     string    // host or host:port
	Path     string
	RawPath  string // encoded path hint (Go 1.5 and later only; see EscapedPath method)
	RawQuery string // encoded query values, without '?'
	Fragment string // fragment for references, without '#'
}
```

*   `Path` フィールドはこれまで通りデコードされたパス（例: `/foo/bar`）を保持します。
*   `RawPath` フィールドは、`URL.Parse()` によってパースされた際の、元のエンコードされたパス（例: `/foo%2Fbar`）を保持します。これは「ヒント」として機能します。

### `URL.Parse()` の変更

`URL.Parse()` 関数は、URLをパースする際に `Path` フィールドだけでなく、`RawPath` フィールドも設定するようになりました。これにより、元のエンコードされたパス情報が失われることなく保持されます。

### `URL.EscapedPath()` メソッドの導入

新しいメソッド `URL.EscapedPath()` が追加されました。このメソッドは、`URL.String()` や `URL.RequestURI()` がパスを再構築する際に使用する、エスケープされたパスを返します。

`EscapedPath()` のロジックは以下の通りです。

1.  `u.RawPath` が空でなく、かつ `validEncodedPath(u.RawPath)` が `true` であるかを確認します。
2.  もし `u.RawPath` が有効なエンコードされたパスであれば、それをデコードした結果が `u.Path` と一致するかを確認します。
3.  上記の両方の条件が満たされた場合、`u.RawPath` をそのまま返します。これは、元のエンコーディングが `u.Path` の有効な表現であり、かつユーザーが `u.Path` を変更していない（または変更したとしても `RawPath` がその変更と一致する）ことを意味します。
4.  それ以外の場合（`u.RawPath` が無効、または `u.Path` と一致しない場合）、`u.Path` を通常のルールに従ってエンコードし、その結果を返します。

この「ヒント」としての `RawPath` の扱いは、後方互換性を維持するための重要な設計です。もしユーザーが `u.Path` を手動で変更した場合、`RawPath` はその変更と一致しなくなるため、`EscapedPath()` は `u.Path` から新しいエンコードされたパスを生成します。これにより、ユーザーが `u.Path` を変更した意図が `URL.String()` に反映されることが保証されます。

### `URL.String()` および `URL.RequestURI()` の変更

`URL.String()` および `URL.RequestURI()` メソッドは、パス部分を構築する際に、直接 `u.Path` をエンコードする代わりに、新しく導入された `u.EscapedPath()` メソッドを使用するように変更されました。

これにより、`%2F` のような特殊なエンコーディングを含むURLが、パースされてから再構築される際に、元のエンコーディングを保持できるようになります。特に、HTTPクライアントが `http.Get` や `http.NewRequest` を使用してリクエストを送信する際に、意図した通りのパスがサーバーに送られるようになります。

### `validEncodedPath` ヘルパー関数

`validEncodedPath` は、与えられた文字列がパスとして有効にエンコードされているかをチェックする内部ヘルパー関数です。これは `EscapedPath` メソッド内で使用され、`RawPath` が有効なヒントであるかを判断します。具体的には、`%` 以外の文字で、パスエンコーディングルールに従ってエスケープされるべき文字が含まれていないかをチェックします。

### 既存の回避策の維持

コミットメッセージにもあるように、この変更は既存の回避策（例: HTTPサーバーが `req.RequestURI` を参照する、HTTPクライアントが `Opaque` フィールドを設定する）を無効にするものではありません。これらの回避策は引き続き有効であり、必要に応じて使用できます。しかし、新しい `RawPath` と `EscapedPath` の導入により、よりクリーンで直感的な方法で同様の目的を達成できるようになりました。

## コアとなるコードの解説

### `URL` 構造体への `RawPath` フィールドの追加

`URL` 構造体に `RawPath string` が追加されたことで、URLのパスの「デコードされた形式」と「元のエンコードされた形式」の両方を保持できるようになりました。
*   `Path`: `/foo/bar` のように、`%2F` が `/` にデコードされた形式。
*   `RawPath`: `/foo%2Fbar` のように、`URL.Parse()` に渡された元のエンコードされた形式。

この分離により、アプリケーションは必要に応じてデコードされたパス (`Path`) を使用しつつ、元のエンコーディング情報 (`RawPath`) を保持できるようになります。

### `parse` 関数での `RawPath` の設定

`parse` 関数は、URL文字列からパス部分を抽出した後、その生の文字列を `url.RawPath` に代入するようになりました。その後、この `rest` (生のパス文字列) を `unescape` 関数でデコードし、その結果を `url.Path` に代入します。

```go
	url.RawPath = rest // 生のパス文字列を RawPath に保存
	if url.Path, err = unescape(rest, encodePath); err != nil { // RawPath をデコードして Path に保存
		goto Error
	}
```

これにより、`URL` 構造体が生成された時点で、`Path` と `RawPath` の両方が適切に設定されます。

### `EscapedPath` メソッドと `validEncodedPath` 関数の追加

`EscapedPath()` メソッドは、`URL` 構造体からエスケープされたパス文字列を生成する中心的なロジックを提供します。

```go
func (u *URL) EscapedPath() string {
	// RawPath が存在し、かつ有効なエンコードされたパスであるかチェック
	if u.RawPath != "" && validEncodedPath(u.RawPath) {
		// RawPath をデコードし、その結果が u.Path と一致するかチェック
		p, err := unescape(u.RawPath, encodePath)
		if err == nil && p == u.Path {
			// 一致すれば RawPath をそのまま返す（元のエンコーディングを保持）
			return u.RawPath
		}
	}
	// RawPath が無効、または u.Path と一致しない場合、u.Path を再エンコードして返す
	return escape(u.Path, encodePath)
}

func validEncodedPath(s string) bool {
	for i := 0; i < len(s); i++ {
		// '%' 以外の文字で、パスエンコーディングルールに従ってエスケープされるべき文字が含まれていないかチェック
		if s[i] != '%' && shouldEscape(s[i], encodePath) {
			return false // エスケープされていない文字があれば無効
		}
	}
	return true // 有効なエンコードされたパス
}
```

*   `EscapedPath` は、まず `u.RawPath` が「ヒント」として有効であるかを検証します。
    *   `u.RawPath` が空でないこと。
    *   `validEncodedPath(u.RawPath)` が `true` であること。これは、`RawPath` がそれ自体として有効なエンコード形式である（例えば、エスケープされるべき文字がエスケープされている）ことを確認します。
    *   `u.RawPath` をデコードした結果が `u.Path` と完全に一致すること。これは、ユーザーが `u.Path` を手動で変更していない、または `RawPath` がその変更を反映していることを保証します。
*   これらの条件がすべて満たされた場合、`u.RawPath` が返されます。これにより、`%2F` のような元のエンコーディングが保持されます。
*   条件が満たされない場合（例えば、`u.Path` が手動で変更された、または `RawPath` が無効な形式である）、`u.Path` が通常の `escape` 関数によって再エンコードされ、その結果が返されます。これにより、後方互換性が維持され、`u.Path` の変更が `String()` メソッドに反映されることが保証されます。

### `String()` および `RequestURI()` メソッドでの `EscapedPath` の利用

`URL.String()` と `URL.RequestURI()` は、URLのパス部分を構築する際に、直接 `u.Path` をエンコードする代わりに `u.EscapedPath()` を呼び出すようになりました。

```go
// String() メソッド内
path := u.EscapedPath() // EscapedPath() を呼び出してパスを取得
// ...
buf.WriteString(path) // 取得したパスをバッファに書き込む

// RequestURI() メソッド内
result = u.EscapedPath() // EscapedPath() を呼び出してパスを取得
```

この変更により、`URL.Parse()` でパースされたURLが `URL.String()` や `URL.RequestURI()` で再構築される際に、元の `RawPath` の情報が「ヒント」として利用され、`%2F` のようなエンコードされたスラッシュが保持される可能性が高まります。これにより、特にRESTful APIなどでパスの厳密なエンコーディングが求められる場合に、より正確なURLの再構築が可能になります。

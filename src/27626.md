# [インデックス 27626] ファイルの概要

このコミットは、Goの`net/http`パッケージにおいて、HTTPハンドラが`http.Request`オブジェクトを不適切に変更することによる潜在的な問題を解決し、その振る舞いを明確にするためのものです。具体的には、ハンドラが開始された後に`Request.Headers`から情報を読み取らないように、必要な情報を`response`構造体に事前にキャッシュする変更が導入されました。これにより、ハンドラによる`Request`の変更が、サーバーの接続管理ロジックに予期せぬ影響を与えることを防ぎます。

## 元コミット内容

`net/http`: ハンドラは`Request`を変更すべきではないことを文書化

さらに、`ServeHTTP`が開始された後、HTTPサーバーコード内で`Request.Headers`から読み取らないようにする。これは、ハンドラがリクエストを変更すべきではないという文書化と部分的に重複するが、以下の理由からこの変更を行う。ブール値のパッキングによりスペースは無料で、`writeChunk`でN回チェックするよりも一度チェックする方が速く、これまで暗黙のルールに従っていなかったコードにとっては少し扱いやすくなる。ただし、すべてのケースを修正するわけではない。

Issue #14940 を修正。

## 変更の背景

Goの`net/http`パッケージにおけるHTTPサーバーは、クライアントからのリクエストを受け取り、それを処理するためにハンドラ（`http.Handler`インターフェースを実装する型）に渡します。この際、ハンドラには`http.Request`オブジェクトが提供されます。慣例として、ハンドラはこの`Request`オブジェクトを読み取り専用として扱い、その内容を変更すべきではないとされていました。しかし、このルールは明示的に文書化されておらず、また、サーバー内部の接続管理ロジック（特にHTTP/1.0のKeep-Aliveや`Connection: close`ヘッダの処理）が、ハンドラが`ServeHTTP`を実行している間に`Request.Headers`を再度参照する可能性がありました。

もしハンドラが`Request.Headers`を変更した場合、サーバーが接続を維持するか閉じるかを決定する際に、変更されたヘッダ情報に基づいて誤った判断を下す可能性がありました。これは、特にHTTP/1.0のKeep-Aliveのような、ヘッダの値によって接続のライフサイクルが左右されるケースで問題となります。

このコミットは、この潜在的な競合状態や予期せぬ動作を防ぐために、以下の2つの主要な変更を導入しました。

1.  **文書化の強化**: `http.Handler`のドキュメントに、`Request`オブジェクトを（ボディの読み取りを除いて）変更すべきではないという明確な指示を追加しました。
2.  **情報の事前キャッシュ**: サーバーが`ServeHTTP`を呼び出す前に、接続管理に必要な`Request.Headers`からの情報を`response`構造体内にキャッシュするように変更しました。これにより、ハンドラが`Request.Headers`を変更しても、サーバーの接続管理ロジックには影響が及ばなくなります。

コミットメッセージにある「Fixes #14940」は、この問題がGoのIssueトラッカーで報告されていたことを示しています。

## 前提知識の解説

### Goの`net/http`パッケージ

Goの標準ライブラリである`net/http`パッケージは、HTTPクライアントとサーバーを実装するための機能を提供します。ウェブアプリケーション開発において中心的な役割を果たします。

*   **`http.Handler`インターフェース**: HTTPリクエストを処理するためのインターフェースで、`ServeHTTP(ResponseWriter, *Request)`メソッドを一つ持ちます。このメソッドがHTTPリクエストの実際の処理ロジックを記述する場所です。
*   **`http.Request`構造体**: クライアントからのHTTPリクエストに関するすべての情報（メソッド、URL、ヘッダ、ボディなど）をカプセル化した構造体です。ハンドラはこのオブジェクトを読み取ってリクエストの内容を把握します。
*   **`http.ResponseWriter`インターフェース**: HTTPレスポンスをクライアントに書き込むためのインターフェースです。ハンドラはこのインターフェースを通じてレスポンスヘッダやボディを送信します。

### HTTP/1.0 Keep-Aliveと`Connection`ヘッダ

HTTPプロトコルでは、クライアントとサーバー間の接続の管理方法を制御するために`Connection`ヘッダが使用されます。

*   **HTTP/1.0**: 元々、HTTP/1.0ではリクエストごとに新しいTCP接続が確立され、レスポンスが送信されると接続が閉じられるのが一般的でした。しかし、パフォーマンス向上のため、`Connection: Keep-Alive`ヘッダをリクエストに含めることで、単一のTCP接続で複数のリクエスト/レスポンスをやり取りする「Keep-Alive」メカニズムが導入されました。
*   **HTTP/1.1**: HTTP/1.1では、デフォルトでKeep-Aliveが有効になり、明示的に`Connection: close`ヘッダが指定されない限り、接続は維持されるようになりました。
*   **`Connection: close`**: クライアントまたはサーバーが、現在のトランザクションの完了後に接続を閉じたい場合に指定するヘッダです。

サーバーは、これらのヘッダの有無や値に基づいて、現在のリクエストの処理後にTCP接続を維持するか、それとも閉じるかを決定します。この決定は、サーバーのリソース効率とクライアントのパフォーマンスに直接影響します。

### `bool packing`

Goの構造体では、複数の`bool`型のフィールドを宣言した場合、コンパイラがそれらを効率的にメモリに配置（パッキング）することがあります。これにより、個々の`bool`フィールドがそれぞれ1バイトを占めるのではなく、複数の`bool`フィールドが1バイト内に収められ、メモリ使用量を削減できます。コミットメッセージで「space is free due to bool packing」とあるのは、`response`構造体に新しい`bool`フィールドを追加しても、メモリフットプリントが実質的に増加しないことを意味しています。

## 技術的詳細

このコミットの核心は、`http.Request`オブジェクトのヘッダ情報が、ハンドラによる処理中に変更される可能性を排除することにあります。これを実現するために、`net/http`パッケージの内部構造である`response`に新しいフィールドが追加され、リクエストの初期段階で必要なヘッダ情報をキャッシュするようになりました。

具体的には、以下の変更が行われました。

1.  **`response`構造体の拡張**:
    `src/net/http/server.go`内の`response`構造体に、以下の2つの`bool`型フィールドが追加されました。
    *   `wants10KeepAlive bool // HTTP/1.0 w/ Connection "keep-alive"`: HTTP/1.0リクエストで`Connection: Keep-Alive`ヘッダが指定されているかどうかを示すフラグ。
    *   `wantsClose bool // HTTP request has Connection "close"`: HTTPリクエストで`Connection: close`ヘッダが指定されているかどうかを示すフラグ。

2.  **`readRequest`メソッドでの情報キャッシュ**:
    `conn`型の`readRequest`メソッド（新しいリクエストを読み込み、`response`オブジェクトを初期化する役割を持つ）内で、`http.Request`オブジェクトがパースされた直後に、これらの新しい`bool`フィールドが初期化されるようになりました。
    具体的には、`req.wantsHttp10KeepAlive()`と`req.wantsClose()`というヘルパーメソッドを呼び出し、その結果をそれぞれ`w.wants10KeepAlive`と`w.wantsClose`に格納します。これにより、ハンドラが`ServeHTTP`を開始する前に、接続管理に必要なヘッダ情報が`response`オブジェクト内に固定されます。

3.  **接続管理ロジックの変更**:
    `chunkWriter`型の`writeHeader`メソッド内で、接続のKeep-Aliveやクローズを決定するロジックが変更されました。以前は`w.req.wantsHttp10KeepAlive()`や`w.req.wantsClose()`のように、`response`オブジェクトが保持する`Request`オブジェクトのメソッドを直接呼び出してヘッダ情報を参照していました。しかし、この変更後は、`w.wants10KeepAlive`や`w.wantsClose`といったキャッシュされたフィールドを参照するようになりました。

このアプローチにより、ハンドラが`Request.Header`マップを後から変更したとしても、サーバーの接続管理ロジックは影響を受けません。サーバーは、リクエストが到着した時点でのヘッダ情報に基づいて、接続のライフサイクルを正しく決定できるようになります。

また、コミットメッセージで言及されている「it's faster to do the checks once instead of N times in writeChunk」という点は、`wants10KeepAlive`や`wantsClose`の値を一度計算してキャッシュすることで、`writeChunk`のような頻繁に呼び出される可能性のあるコードパスで、毎回`Request.Headers`をパースして条件を評価するオーバーヘッドを削減できることを意味します。

## 元コミット内容

`[dev.ssa] fix equivalence class after aux/auxint refactor.`

このコミットは、`aux/auxint`のリファクタリング後に発生した等価クラスのバグを修正します。

このバグにより、以下のコードスニペットが誤ってコンパイルされていました。

```go
        var f int
        x := g(&f)
        f = 10
```

具体的には、`f = 10`というストア操作が関数呼び出し`g(&f)`よりも上に移動されてしまうという問題が発生していました。

## 変更の背景

Goコンパイラは、プログラムを最適化するために様々な段階を経ます。その一つがSSA（Static Single Assignment）形式への変換と、そのSSA形式上での最適化です。共通部分式除去（CSE: Common Subexpression Elimination）は、これらの最適化の一つであり、同じ計算が複数回行われている場合に、その計算を一度だけ行い、結果を再利用することでパフォーマンスを向上させます。

このコミットの背景には、GoコンパイラのSSAバックエンドにおける`Aux`および`AuxInt`フィールドのリファクタリングがありました。これらのフィールドは、SSA値（プログラム内の各計算を表す）に追加の情報を付与するために使用されます。例えば、定数、メモリオフセット、関数名などが格納されます。

リファクタリング後、CSEのロジックがこれらのフィールドの変更に追従していなかったため、問題が発生しました。特に、SSA値の等価性を判断するためのキー（`key` struct）に`AuxInt`フィールドが含まれていなかったことが原因で、実際には異なる値であるにもかかわらず、コンパイラがそれらを同じものと誤認し、最適化の過程で誤ったコード変換を行ってしまいました。

コミットメッセージに示されている例では、`f = 10`というストア操作が`g(&f)`という関数呼び出しよりも前に移動されてしまうという深刻な問題が発生していました。これは、関数呼び出しがポインタ`&f`を介して`f`の値を読み書きする可能性があるため、ストア操作の順序が変更されるとプログラムのセマンティクスが破壊される可能性があることを意味します。このような最適化は、データ競合や予期せぬ動作を引き起こすため、絶対に避けなければなりません。

## 前提知識の解説

### GoコンパイラとSSA形式

Goコンパイラは、ソースコードを機械語に変換する際に、中間表現としてSSA（Static Single Assignment）形式を使用します。SSA形式では、各変数が一度だけ代入されるという特性を持ち、これによりデータフロー解析や最適化が容易になります。

*   **SSA値 (Value)**: SSA形式における基本的な計算単位です。各Valueは、特定の操作（Op）、型（Type）、引数（Args）、および補助情報（Aux, AuxInt）を持ちます。
*   **Op (Operation)**: Valueが実行する操作の種類（例: Add, Load, Store, Callなど）。
*   **Type (型)**: Valueの結果のデータ型。
*   **Args (引数)**: Valueの操作の入力となる他のValue。
*   **Aux (Auxiliary Data)**: Valueに関連付けられた追加のデータ。例えば、定数、シンボル、型情報など、`interface{}`型で様々な種類のデータを保持できます。
*   **AuxInt (Auxiliary Integer)**: Valueに関連付けられた追加の整数データ。例えば、メモリオフセット、シフト量、配列の長さなど、`int64`型で特定の整数値を保持します。

### 共通部分式除去 (CSE: Common Subexpression Elimination)

CSEは、コンパイラの最適化手法の一つで、同じ計算がプログラム内で複数回行われている場合、その計算を一度だけ実行し、結果を再利用することで冗長な計算を排除します。これにより、実行速度の向上やコードサイズの削減が期待できます。

CSEを適用するためには、コンパイラはどの計算が「同じ」であるかを正確に判断する必要があります。これは通常、操作の種類、オペランド（引数）、およびその他の補助情報がすべて一致する場合に、それらの計算が等価であると見なされます。

### 等価クラス (Equivalence Class)

CSEの文脈では、コンパイラはプログラム内のすべてのSSA値を、互いに等価であると見なせる値のグループ、すなわち「等価クラス」に分類します。この等価クラスを構築する際に、各SSA値の特性（Op, Type, Aux, AuxInt, Argsの数など）を組み合わせた「キー」が使用されます。このキーが同じであれば、それらのSSA値は同じ等価クラスに属すると初期的に判断されます。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおける共通部分式除去（CSE）の初期段階で、SSA値の等価性を判断するためのキーの定義が不完全であった点にあります。

CSEのアルゴリズムでは、まずプログラム内のすべてのSSA値を、その操作（Op）、型（Type）、補助データ（Aux）、および引数の数（nargs）に基づいて初期的な等価クラスに分類します。この分類のために、`src/cmd/compile/internal/ssa/cse.go`内の`cse`関数で`key`という構造体が定義されていました。

元の`key`構造体は以下のフィールドを持っていました。

```go
type key struct {
    op    Op
    typ   Type
    aux   interface{}
    nargs int
}
```

問題は、`AuxInt`フィールドがこの`key`構造体に含まれていなかったことです。`AuxInt`は、メモリオフセットや定数などの重要な整数値を保持することがあり、これらの値が異なれば、たとえ他のフィールド（Op, Type, Aux, nargs）が同じであっても、SSA値は異なる計算を表す可能性があります。

例えば、`Load`操作で異なるメモリオフセットから値をロードする場合、`Op`はどちらも`Load`、`Type`も同じ、`Aux`も同じ（例えば、ベースポインタのシンボル）、`nargs`も同じ（例えば、ベースポインタのみ）である可能性があります。しかし、`AuxInt`が異なるオフセット値を持つ場合、これらは明らかに異なるメモリ位置からのロードであり、等価ではありません。

`aux/auxint`のリファクタリング後、`AuxInt`がより広範に使用されるようになったにもかかわらず、CSEの`key`にそれが反映されていなかったため、コンパイラは異なる`AuxInt`を持つSSA値を誤って同じ等価クラスに分類してしまいました。

コミットメッセージの例：

```go
        var f int
        x := g(&f) // gは&fを引数にとる
        f = 10     // fへのストア
```

このコードでは、`g(&f)`の呼び出しと`f = 10`のストア操作の順序は非常に重要です。`g`が`f`の値を読み取る、あるいは`f`が指すメモリ位置に書き込む可能性があるためです。もし`f = 10`が`g(&f)`の前に移動されると、`g`は`f`の古い値ではなく、`10`という新しい値を参照してしまう可能性があります。

この誤った並べ替えは、コンパイラが`f = 10`というストア操作と`g(&f)`の呼び出しに関連するメモリ操作を、`AuxInt`の違いを考慮せずに誤って等価と判断した結果として発生したと考えられます。例えば、`Store`操作や`Call`操作に関連するSSA値が、`AuxInt`の違い（例えば、ストアする値や呼び出す関数のIDなど）を無視して同じ等価クラスに分類され、その結果、コンパイラが安全でないと判断すべき並べ替えを実行してしまった可能性があります。

## コアとなるコードの解説

このコミットの修正は非常にシンプルですが、その影響は大きいです。

`src/cmd/compile/internal/ssa/cse.go`内の`cse`関数は、共通部分式除去（CSE）の最適化を実行します。この関数の冒頭で、SSA値の初期的な等価クラスを構築するために`key`構造体が使用されます。

変更前は、`key`構造体は`Op`、`Type`、`Aux`、`nargs`（引数の数）のみを考慮していました。

```go
type key struct {
    op    Op
    typ   Type
    aux   interface{}
    nargs int
}
```

この定義では、`v.AuxInt`フィールドの値が異なっていても、他のフィールドが同じであれば、異なるSSA値が同じ`key`を持つことになり、結果として同じ等価クラスに誤って分類されていました。

修正では、`key`構造体に`auxint int64`フィールドが追加されました。

```go
type key struct {
    op     Op
    typ    Type
    aux    interface{}
    auxint int64 // <-- 追加されたフィールド
    nargs  int
}
```

そして、`key`のインスタンスを作成する際に、`v.AuxInt`がこの新しいフィールドに明示的に含まれるようになりました。

```go
// 変更前
k := key{v.Op, v.Type, v.Aux, len(v.Args)}
// 変更後
k := key{v.Op, v.Type, v.Aux, v.AuxInt, len(v.Args)}
```

この変更により、`AuxInt`の値が異なるSSA値は、たとえ他のフィールドが同じであっても、異なる`key`を持つようになります。その結果、これらの値は異なる等価クラスに分類され、CSEアルゴリズムがそれらを別々の計算として正しく扱えるようになります。

これにより、コミットメッセージで示されたような、`f = 10`というストア操作が`g(&f)`という関数呼び出しよりも前に誤って移動されるといった、セマンティクスを破壊する最適化が防止されます。コンパイラは、`AuxInt`を含むすべての関連情報に基づいて、SSA値の等価性をより正確に判断できるようになり、より安全で正しい最適化が可能になります。

# [インデックス 2034] ファイルの概要

このコミットは、Go言語のテストツールである `gotest` の動作を修正するためのものです。具体的には、`nm -s` コマンドがシンボルをファイル内の出現順に表示するように変更することで、`gotest` がテストを正しい順序で実行できるようにします。この修正は、シンボル情報にシーケンス番号を導入し、その番号に基づいてソートを行うことで実現されています。

## 元コミット内容

`nm -s` が `.6` ファイルを読み込む際にシーケンス番号を保存することで、ファイル内の出現順にシンボルを出力するように修正し、`gotest` を修正する。これにより、テストがファイル内の順序で実行されるようになる。

## 変更の背景

Go言語の初期段階において、`gotest` コマンドはテスト関数を検出するために `nm` ユーティリティを利用していました。`nm` はオブジェクトファイルやアーカイブファイル内のシンボル（関数名、変数名など）をリスト表示するコマンドです。特に `nm -s` オプションは、シンボルをセクションごとに表示する機能を持っていました。

しかし、当時の `nm -s` の出力順序は、ファイル内のシンボル定義順を保証するものではありませんでした。`gotest` がテスト関数を検出する際に、この `nm -s` の出力順序に依存していたため、テストがソースコードに記述された順序とは異なる順序で実行されるという問題が発生していました。これは、テストの再現性やデバッグの際に予期せぬ挙動を引き起こす可能性がありました。

このコミットは、この問題を解決するために、`nm -s` がシンボルをファイル内の出現順に正確に報告するように変更することを目的としています。これにより、`gotest` がテスト関数を常に期待される順序で実行できるようになり、テストの信頼性と予測可能性が向上します。

## 前提知識の解説

### `nm` コマンド

`nm` は "name" の略で、コンパイルされたオブジェクトファイル、静的ライブラリ、または実行可能ファイル内のシンボルテーブルの内容をリスト表示するために使用されるUnix系のコマンドラインユーティリティです。シンボルテーブルには、プログラム内で定義された関数やグローバル変数などの名前と、それらのアドレスや型などの情報が含まれています。

`nm` の主な用途は以下の通りです。
*   **シンボルの検査**: プログラムがどの関数や変数を使用しているか、またはエクスポートしているかを調べます。
*   **デバッグ**: 未解決のシンボルエラーの原因を特定したり、特定の関数がどこに定義されているかを見つけたりするのに役立ちます。
*   **ライブラリの分析**: ライブラリが提供する機能や、その内部構造を理解するために使用されます。

**`nm -s` オプション**:
このコミットで特に重要なのは `-s` オプションです。これは、シンボルをセクション名でソートして表示する（またはセクション情報を表示する）ことを意図しています。しかし、当時の実装では、ファイル内の定義順を保持する機能が不足していました。

### `gotest`

`gotest` は、Go言語の初期のテスト実行ツールです。Go言語の標準ライブラリには `testing` パッケージがあり、これを使用してテストコードを記述します。`gotest` は、これらのテストコードを含むGoソースファイルをコンパイルし、実行可能なテストバイナリを生成し、それを実行してテスト結果を収集する役割を担っていました。

`gotest` がテスト関数を検出する際、コンパイルされたオブジェクトファイルから `nm` コマンドを使用してシンボル情報を抽出し、`Test` または `Benchmark` プレフィックスを持つ関数をテスト関数として認識していました。このシンボル抽出の順序が、テスト実行順序に影響を与えていたため、今回の修正が必要となりました。

### Goのコンパイルとリンクの初期段階

Go言語のコンパイルプロセスは、ソースコードを機械語に変換し、実行可能なバイナリを生成する一連のステップです。初期のGoコンパイラは、Plan 9のツールチェインの影響を強く受けていました。

*   **`.6` ファイル**: Go言語の初期のコンパイラ（`6g` など、`amd64` アーキテクチャの場合は `6` がプレフィックス）によって生成されるオブジェクトファイルは、`.6` という拡張子を持っていました。これは、C言語における `.o` ファイルに相当します。これらのファイルには、コンパイルされた機械語コード、データ、そしてシンボル情報が含まれています。`nm` コマンドは、これらの `.6` ファイルからシンボル情報を読み取ります。

### シンボルとシーケンス番号

プログラム内の関数や変数は「シンボル」として扱われます。コンパイラは、これらのシンボルに関する情報をシンボルテーブルに格納します。通常、シンボルテーブル内のエントリの順序は、ファイル内の定義順とは限りません。リンカやユーティリティがシンボルを処理する際に、アドレス順やアルファベット順など、特定の基準でソートすることが一般的です。

このコミットでは、ファイル内のシンボル定義順を保持するために、各シンボルに「シーケンス番号」を割り当てるというアプローチが取られています。これは、`.6` ファイルを読み込む際に、シンボルが検出された順に連番を振ることで実現されます。このシーケンス番号を利用することで、`nm` がシンボルをファイル内の出現順にソートして出力することが可能になります。

## 技術的詳細

このコミットは、Go言語のツールチェインの3つのファイルにわたる変更によって、`nm -s` の出力順序を修正しています。

1.  **`include/mach_amd64.h` の変更**:
    *   このファイルは、`amd64` アーキテクチャにおける機械語レベルの構造体定義や定数を含むヘッダーファイルです。
    *   `Sym` 構造体（シンボル情報を表す構造体）に `sequence` という新しいフィールドが追加されました。このフィールドは `int` 型で、コメントには `// order in file` と記されており、ファイル内でのシンボルの出現順序を記録するために使用されることが示されています。

    ```c
    struct	Sym
    {
    	char	type;
    	char	*name;
    	char *gotype;
    	int	sequence;	// order in file
    };
    ```

2.  **`src/cmd/nm/nm.c` の変更**:
    *   このファイルは `nm` コマンドのソースコードです。
    *   **`cmp` 関数の変更**: `cmp` 関数は、シンボルをソートするための比較関数です。
        *   既存の `nflag`（アドレス順ソート）の条件に加えて、`sflag`（セクション順ソート、今回の修正対象）が設定されている場合に、新しく追加された `sequence` フィールドに基づいてシンボルをソートするロジックが追加されました。`(*s)->sequence - (*t)->sequence` という比較は、`sequence` 番号が小さい方が先にくるようにソートすることを意味します。
        ```c
        if(sflag)	// sort on file order (sequence)
        	return (*s)->sequence - (*t)->sequence;
        ```
    *   **`printsyms` 関数の変更**:
        *   `printsyms` 関数は、シンボルを実際に表示する前にソートを行う部分です。
        *   変更前は `sflag` が設定されていない場合にのみ `qsort` が呼び出されていましたが、変更後は無条件に `qsort` が呼び出されるようになりました。これは、`cmp` 関数内で `sflag` の有無に応じたソートロジックが追加されたため、`printsyms` 側で条件分岐を行う必要がなくなったためです。これにより、常に適切なソートが適用されるようになります。

3.  **`src/libmach_amd64/obj.c` の変更**:
    *   このファイルは、`amd64` アーキテクチャのオブジェクトファイル（`.6` ファイル）の読み込みとシンボル情報の処理を行うライブラリコードです。
    *   **`sequence` 変数の追加**: ファイルスコープの静的変数 `static int sequence;` が追加されました。これは、シンボルに割り当てるシーケンス番号を管理するためのカウンターです。
    *   **`objlookup` 関数の変更**: `objlookup` 関数は、オブジェクトファイルからシンボルが読み込まれる際に呼び出され、そのシンボルを内部のデータ構造に登録する役割を担っています。
        *   この関数内で、新しく読み込まれたシンボル `sp->s` の `sequence` フィールドに、グローバルな `sequence` 変数の現在の値が代入され、その後 `sequence` 変数がインクリメントされます (`sp->s.sequence = sequence++;`)。これにより、シンボルがファイルから読み込まれた順序で一意のシーケンス番号が割り当てられることが保証されます。

これらの変更により、`nm -s` コマンドが実行されると、シンボルはファイル内で定義された順序（シーケンス番号順）でソートされて出力されるようになります。`gotest` はこの修正された `nm -s` の出力を使用するため、テスト関数がソースコードに記述された順序で実行されるようになり、テストの信頼性と予測可能性が向上します。

## コアとなるコードの解説

### `include/mach_amd64.h` の `Sym` 構造体への `sequence` フィールド追加

`Sym` 構造体は、Goのコンパイラとツールチェインが内部的にシンボル情報を表現するために使用するデータ構造です。この構造体に `int sequence;` フィールドが追加されたことで、各シンボルがファイル内で読み込まれた順序を示す一意の整数値を持つことができるようになりました。この `sequence` フィールドが、ファイル内でのシンボルの相対的な位置を追跡するための鍵となります。

### `src/cmd/nm/nm.c` の `cmp` 関数と `printsyms` 関数の変更

*   **`cmp` 関数**: この関数は `qsort`（クイックソート）によってシンボル配列をソートする際に、2つのシンボルを比較するために呼び出されます。
    *   `if(sflag)` ブロックが追加され、`sflag`（`nm -s` オプションに対応）が有効な場合、シンボルの `sequence` フィールドに基づいて比較が行われるようになりました。`(*s)->sequence - (*t)->sequence` は、`s` のシーケンス番号が `t` より小さければ負の値を返し、`s` が `t` より前に来るべきであることを示します。これにより、シンボルはファイル内の出現順にソートされます。
    *   `printsyms` 関数から `if(!sflag)` の条件が削除され、常に `qsort` が呼び出されるようになりました。これは、`cmp` 関数内で `sflag` の有無に応じたソートロジックが既に組み込まれているため、`printsyms` 側でソートの実行を条件分岐させる必要がなくなったためです。これにより、コードが簡潔になり、常に適切なソートが適用されることが保証されます。

### `src/libmach_amd64/obj.c` の `sequence` 変数と `objlookup` 関数の変更

*   **`static int sequence;`**: この静的変数は、オブジェクトファイルからシンボルが読み込まれるたびにインクリメントされるカウンターとして機能します。これにより、各シンボルに一意のシーケンス番号が割り当てられます。静的変数であるため、このファイル内でグローバルにアクセス可能であり、`objlookup` 関数が呼び出されるたびにその状態が保持されます。
*   **`objlookup` 関数**: この関数は、オブジェクトファイルから新しいシンボルが検出され、内部のシンボルテーブルに登録される際に呼び出されます。
    *   `sp->s.sequence = sequence++;` という行が追加されました。これは、現在処理中のシンボル `sp->s` の `sequence` フィールドに、現在の `sequence` 変数の値を代入し、その後 `sequence` 変数をインクリメントするというアトミックな操作です。これにより、シンボルがオブジェクトファイル内で出現した順序で、0から始まる連番が割り当てられます。このシーケンス番号が、`nm -s` がファイル内の出現順にシンボルをソートするための基準となります。

これらの変更が連携することで、`nm -s` はGoのオブジェクトファイル（`.6` ファイル）からシンボルを読み込む際に、それらのシンボルにファイル内での出現順序を示すシーケンス番号を付与し、そのシーケンス番号に基づいてソートして出力するようになります。これにより、`gotest` がテスト関数を検出する際の順序が保証され、テストの実行順序が予測可能になります。

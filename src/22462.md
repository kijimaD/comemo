# [インデックス 22462] ファイルの概要

このコミットは、Goコンパイラの内部パッケージである `cmd/internal/obj` における行履歴（line history）の管理方法を再実装するものです。`cmd/internal/obj` パッケージは、Goプログラムのアセンブリコード生成、オブジェクトファイルのリンク、およびデバッグ情報の生成を担当しています。行履歴は、コンパイルされたバイナリ内の命令が、元のソースコードのどのファイル、どの行に対応するかを追跡するために不可欠な情報です。この変更により、特に多数のファイルがインクルードされるような大規模なプロジェクトにおいて、コンパイル時の性能が向上し、コードの可読性も改善されます。

## コミット

Goコンパイラの `cmd/internal/obj` パッケージにおいて、行履歴の管理メカニズムが再実装されました。これにより、従来のO(n)の線形探索がO(log n)の対数探索に改善され、特に大規模なソースコードベースでのコンパイル性能が向上しました。また、コードの明確性も向上しています。

## 変更の背景

コンパイラがソースコードを処理する際、生成される機械語命令が元のソースファイルのどの行に対応するかという情報は非常に重要です。これは、デバッグ情報の生成、エラーメッセージの表示、プロファイリングなど、様々な場面で利用されます。Goコンパイラでは、特にCgoのような外部言語との連携や、`//line` ディレクティブによる行番号の再マッピングなど、複雑な行番号の変換が頻繁に発生します。

従来のGoコンパイラでは、この行履歴を単方向連結リスト (`Hist` 構造体) で管理していました。この方式では、特定の仮想行番号に対応する実際のファイルと行番号を検索する際に、リストの先頭から順に辿っていく必要があり、その計算量はO(n)となっていました。nは履歴エントリの数、つまり処理された行数に比例します。大規模なプロジェクトや、多数のインクルードファイルを持つコードでは、この線形探索がコンパイル時間のボトルネックとなる可能性がありました。

このコミットの背景には、コンパイル性能の向上と、より堅牢で理解しやすい行履歴管理システムの構築という目的があります。O(n)の検索をO(log n)に改善することで、コンパイラの全体的な効率が向上し、特に大規模なコードベースでのコンパイル時間が短縮されることが期待されます。

## 前提知識の解説

### Goコンパイラの構造と `cmd/internal/obj` パッケージ

Goコンパイラは複数のステージに分かれており、`cmd/internal/obj` はその中でもアセンブラとリンカに近い部分を担当します。具体的には、Goソースコードから生成された中間表現（ASTなど）を元に、ターゲットアーキテクチャ向けのアセンブリコードを生成し、最終的なオブジェクトファイルや実行可能ファイルをリンクする役割を担います。この過程で、ソースコードのファイル名や行番号といったメタ情報を正確に追跡し、デバッグ情報としてバイナリに埋め込む必要があります。

### 行履歴 (Line History)

行履歴とは、コンパイラがソースファイルを処理する際に、現在の「仮想的な行番号」（コンパイラが内部的にカウントする連続した行番号）が、実際のソースファイルのどの物理的なファイル名と行番号に対応するかを記録するメカニズムです。
例えば、`#line` ディレクティブ（Goでは `//line`）を使用すると、コンパイラはそれ以降のコードの行番号を、指定されたファイルと行番号から始まるものとして扱います。また、Cgoのようなツールが生成するコードでは、元のC/C++コードの行番号とGoコードの行番号が混在することがあります。行履歴は、これらの複雑なマッピングを正確に管理し、エラーメッセージやデバッグ時に正しいソース位置を報告するために不可欠です。

### O(n) と O(log n) の計算量

*   **O(n) (線形探索)**: データ構造内の要素数 `n` に比例して処理時間が増加するアルゴリズムの効率性を示します。例えば、連結リストの要素を先頭から順に探す場合、最悪のケースではすべての要素をチェックする必要があるため、O(n)となります。
*   **O(log n) (対数探索)**: データ構造内の要素数 `n` の対数に比例して処理時間が増加するアルゴリズムの効率性を示します。これは非常に効率的で、`n` が大きくなっても処理時間の増加は緩やかです。ソートされた配列に対する二分探索が典型的な例です。

このコミットでは、行履歴の検索をO(n)からO(log n)に改善することで、コンパイラの性能向上を図っています。

### `Hist` 構造体 (変更前)

変更前の行履歴は、`Hist` という構造体の連結リストで表現されていました。

```go
type Hist struct {
	Link    *Hist
	Name    string
	Sym     *LSym
	Line    int32
	Offset  int32
	Printed uint8
}
```
`Link` フィールドが次の `Hist` エントリへのポインタとなっており、これにより履歴が時系列順に連結されていました。`Name` はファイル名、`Line` は仮想行番号、`Offset` は `#line` ディレクティブによるオフセットなどを記録していました。

### `LineHist`, `LineStack`, `LineRange` 構造体 (変更後)

変更後には、以下の新しい構造体が導入されました。

*   **`LineHist`**: 行履歴全体を管理するメインの構造体です。
    ```go
    type LineHist struct {
        Top            *LineStack  // current top of stack
        Ranges         []LineRange // ranges for lookup
        Dir            string      // directory to qualify relative paths
        TrimPathPrefix string      // remove leading TrimPath from recorded file names
        GOROOT         string      // current GOROOT
        GOROOT_FINAL   string      // target GOROOT
    }
    ```
    `Ranges` フィールドが特に重要で、これがO(log n)検索を可能にするソートされた範囲のリストを保持します。

*   **`LineStack`**: 行履歴スタックの各エントリを表します。
    ```go
    type LineStack struct {
        Parent    *LineStack // parent in inclusion stack
        Lineno    int        // virtual line number where this entry takes effect
        File      string     // file name used to open source file, for error messages
        AbsFile   string     // absolute file name, for pcln tables
        FileLine  int        // line number in file at Lineno
        Directive bool
        Sym       *LSym // for linkgetline - TODO(rsc): remove
    }
    ```
    `Parent` フィールドにより、インクルードスタック（ファイルが別のファイルをインクルードする階層構造）が表現されます。`Lineno` はこのエントリが有効になる仮想行番号、`File` はファイル名、`FileLine` はそのファイル内の行番号です。

*   **`LineRange`**: 行履歴の特定の範囲を表します。
    ```go
    type LineRange struct {
        Start int        // starting lineno
        Stack *LineStack // top of stack for this range
    }
    ```
    `Ranges` スライスはこの `LineRange` の配列であり、`Start` はその範囲が始まる仮想行番号、`Stack` はその範囲で有効な `LineStack` のトップエントリを指します。

### `sort.Search`

`sort.Search` はGo標準ライブラリの `sort` パッケージに含まれる関数で、ソートされたスライスに対して二分探索を実行します。この関数は、特定の条件を満たす最小のインデックスを効率的に見つけるために使用されます。このコミットでは、`LineHist.Ranges` スライスから特定の仮想行番号に対応する `LineRange` をO(log n)で検索するために利用されています。

## 技術的詳細

このコミットの核心は、行履歴のデータ構造と検索アルゴリズムの根本的な変更にあります。

### 旧来の `Hist` ベースの実装の問題点

従来の `Hist` 構造体は単方向連結リストとして機能していました。`Linklinefmt` や `linkgetline` のような関数は、このリストを先頭から順に辿って目的の行履歴エントリを見つけていました。

```go
// src/cmd/internal/obj/obj.go (変更前)
func Linklinefmt(ctxt *Link, lno0 int, showAll, showFullPath bool) string {
    // ...
    for h := ctxt.Hist; h != nil; h = h.Link { // O(n) 検索
        // ...
    }
    // ...
}
```
この `for` ループが示すように、最悪の場合、すべての `Hist` エントリを走査する必要があり、これがO(n)の性能ボトルネックとなっていました。

### 新しい `LineHist` と O(log n) 検索への移行

新しい実装では、`LineHist` 構造体が導入され、その内部に `Ranges` という `LineRange` 型のスライスが保持されます。`LineRange` は、特定の仮想行番号 (`Start`) から始まる範囲で有効な `LineStack` のトップエントリを記録します。

```go
// src/cmd/internal/obj/obj.go (変更後)
type LineHist struct {
    // ...
    Ranges         []LineRange // ranges for lookup
    // ...
}

type LineRange struct {
    Start int        // starting lineno
    Stack *LineStack // top of stack for this range
}
```

`Ranges` スライスは `Start` フィールド（仮想行番号）でソートされた状態に保たれます。これにより、特定の仮想行番号に対応する `LineRange` を見つけるために、Go標準ライブラリの `sort.Search` 関数を用いた二分探索が可能になります。

```go
// src/cmd/internal/obj/obj.go (変更後)
// At returns the input stack in effect at lineno.
func (h *LineHist) At(lineno int) *LineStack {
    i := sort.Search(len(h.Ranges), func(i int) bool {
        return h.Ranges[i].Start > lineno
    })
    // Found first entry beyond lineno.
    if i == 0 {
        return nil
    }
    return h.Ranges[i-1].Stack
}
```
`LineHist.At` メソッドは、与えられた `lineno` (仮想行番号) に対して、`Ranges` スライス内で `lineno` よりも大きい `Start` を持つ最初の `LineRange` のインデックスを `sort.Search` で見つけます。その直前の `LineRange` が、目的の `lineno` が属する範囲を示しており、その `Stack` フィールドが対応する `LineStack` を返します。これにより、検索の計算量はO(log n)に劇的に改善されます。

### 行履歴スタックの操作 (`Push`, `Pop`, `Update`)

`LineHist` は、行履歴スタックを操作するための `Push`, `Pop`, `Update` メソッドを提供します。

*   **`Push(lineno int, file string)`**: 新しいファイルがインクルードされたり、新しいソースファイルが処理され始めたりしたときに呼び出されます。新しい `LineStack` エントリを作成し、現在の `LineHist.Top` をその `Parent` として設定し、`Ranges` に新しい `LineRange` を追加します。
*   **`Pop(lineno int)`**: 現在のファイルがインクルードスタックからポップされたときに呼び出されます。`LineHist.Top` をその `Parent` に戻し、`Ranges` に新しい `LineRange` を追加して、その時点でのスタックの状態を記録します。
*   **`Update(lineno int, file string, line int)`**: `#line` ディレクティブなどによって、現在のファイル名や行番号が変更されたときに呼び出されます。既存の `LineStack` エントリを更新するか、新しい `LineStack` エントリを作成して `Ranges` に追加します。

これらのメソッドは、`startRange` ヘルパー関数を通じて `Ranges` スライスを適切に更新し、常にソートされた状態を維持します。

### ファイルパスの正規化

`LineHist` は、ファイルパスを正規化するためのロジックも内包しています。

*   `Dir`: 相対パスを絶対パスに解決するためのベースディレクトリ。
*   `TrimPathPrefix`: 特定のプレフィックスを持つパスを削除し、より簡潔なパスを生成します。これは、ビルド環境のパスがデバッグ情報に漏洩するのを防ぐためなどに使用されます。
*   `GOROOT`, `GOROOT_FINAL`: Goの標準ライブラリパスを、ビルド時の `GOROOT` から最終的なデプロイ先の `GOROOT_FINAL` に書き換えるために使用されます。

これらのフィールドは `LineHist.setFile` メソッド内で利用され、`LineStack` の `AbsFile` フィールドに正規化された絶対パスが設定されます。

### 既存APIの変更

`Linklinefmt` や `linkgetline` といった、行履歴情報を取得する既存のAPIは、新しい `LineHist` 構造体を利用するように変更されました。これにより、外部からこれらのAPIを呼び出すコードは変更する必要がなく、内部実装の改善が透過的に適用されます。

```go
// src/cmd/internal/obj/obj.go (変更後)
func Linklinefmt(ctxt *Link, lineno int, showAll, showFullPath bool) string {
    return ctxt.LineHist.LineString(lineno)
}

func linkgetline(ctxt *Link, lineno int32, f **LSym, l *int32) {
    stk := ctxt.LineHist.At(int(lineno))
    // ...
}
```
`Link` 構造体も `Hist` フィールドを削除し、`LineHist` フィールドを持つように変更されています。

```go
// src/cmd/internal/obj/link.go (変更後)
type Link struct {
    // ...
    LineHist           LineHist
    Imports            []string
    // ...
}
```

## コアとなるコードの解説

### `src/cmd/internal/obj/obj.go` における `LineHist` の導入と `At` メソッド

最も重要な変更は、`LineHist` 構造体の導入と、その `At` メソッドによる効率的な行履歴検索です。

```go
// src/cmd/internal/obj/obj.go
type LineHist struct {
	Top            *LineStack  // current top of stack
	Ranges         []LineRange // ranges for lookup
	Dir            string      // directory to qualify relative paths
	TrimPathPrefix string      // remove leading TrimPath from recorded file names
	GOROOT         string      // current GOROOT
	GOROOT_FINAL   string      // target GOROOT
}

type LineRange struct {
	Start int        // starting lineno
	Stack *LineStack // top of stack for this range
}

// At returns the input stack in effect at lineno.
func (h *LineHist) At(lineno int) *LineStack {
	i := sort.Search(len(h.Ranges), func(i int) bool {
		return h.Ranges[i].Start > lineno
	})
	// Found first entry beyond lineno.
	if i == 0 {
		return nil
	}
	return h.Ranges[i-1].Stack
}
```
`LineHist.Ranges` は、仮想行番号の範囲とその範囲で有効な `LineStack` のトップを記録する `LineRange` のスライスです。このスライスは `Start` フィールドで常にソートされています。

`At(lineno int)` メソッドは、特定の仮想行番号 `lineno` がどの `LineRange` に属するかを効率的に見つけます。`sort.Search` は、`h.Ranges` スライス内で、`Start` フィールドが `lineno` よりも大きい最初の要素のインデックス `i` を返します。もし `i` が0であれば、`lineno` はどの範囲にも属さないか、最初の範囲よりも前にあるため `nil` を返します。そうでなければ、`i-1` のインデックスにある `LineRange` が `lineno` を含む範囲であり、その `Stack` フィールドが目的の `LineStack` を指します。この二分探索により、検索の計算量はO(log n)となります。

### `src/cmd/internal/obj/link.go` における `Linklinehist` の変更

`Linklinehist` 関数は、コンパイラがソースファイルを処理する際に、行履歴スタックを操作するための主要なエントリポイントです。この関数は、新しい `LineHist` の `Push`, `Pop`, `Update` メソッドを呼び出すように変更されました。

```go
// src/cmd/internal/obj/link.go
// Linklinehist pushes, amends, or pops an entry on the line history stack.
// If f != "<pop>" and n == 0, the call pushes the start of a new file named f at lineno.
// If f != "<pop>" and n > 0, the call amends the top of the stack to record that lineno
// now corresponds to f at line n.
// If f == "<pop>", the call pops the topmost entry from the stack, picking up
// the parent file at the line following the one where the corresponding push occurred.
//
// If n < 0, linklinehist records f as a package required by the current compilation
// (nothing to do with line numbers).
//
// TODO(rsc): Replace uses with direct calls to ctxt.LineHist methods.
func Linklinehist(ctxt *Link, lineno int, f string, n int) {
	switch {
	case n < 0:
		ctxt.AddImport(f)

	case f == "<pop>":
		ctxt.LineHist.Pop(lineno)

	case n == 0:
		ctxt.LineHist.Push(lineno, f)

	default: // n > 0
		ctxt.LineHist.Update(lineno, f, n)
	}
}
```
この `switch` ステートメントは、`f` と `n` の値に基づいて、行履歴スタックに対して `Push` (新しいファイルの開始)、`Pop` (ファイルの終了)、`Update` (行ディレクティブによる変更) のいずれかの操作を実行します。`n < 0` のケースは行履歴とは直接関係なく、インポートされたパッケージを記録するために使用されます。

この変更により、`Linklinehist` は高レベルなインターフェースとして機能し、実際の行履歴の管理は `LineHist` 構造体のメソッドに委譲されるようになりました。これにより、コードの関心事が分離され、よりモジュール化された設計になっています。

このコミットは、Goコンパイラの内部パッケージである `cmd/internal/obj` における行履歴（line history）の管理方法を再実装するものです。`cmd/internal/obj` パッケージは、Goプログラムのアセンブリコード生成、オブジェクトファイルのリンク、およびデバッグ情報の生成を担当しています。行履歴は、コンパイルされたバイナリ内の命令が、元のソースコードのどのファイル、どの行に対応するかを追跡するために不可欠な情報です。この変更により、特に多数のファイルがインクルードされるような大規模なプロジェクトにおいて、コンパイル時の性能が向上し、コードの可読性も改善されます。

## コミット

Goコンパイラの `cmd/internal/obj` パッケージにおいて、行履歴の管理メカニズムが再実装されました。これにより、従来のO(n)の線形探索がO(log n)の対数探索に改善され、特に大規模なソースコードベースでのコンパイル性能が向上しました。また、コードの明確性も向上しています。

## 変更の背景

コンパイラがソースコードを処理する際、生成される機械語命令が元のソースファイルのどの行に対応するかという情報は非常に重要です。これは、デバッグ情報の生成、エラーメッセージの表示、プロファイリングなど、様々な場面で利用されます。Goコンパイラでは、特にCgoのような外部言語との連携や、`//line` ディレクティブによる行番号の再マッピングなど、複雑な行番号の変換が頻繁に発生します。

従来のGoコンパイラでは、この行履歴を単方向連結リスト (`Hist` 構造体) で管理していました。この方式では、特定の仮想行番号に対応する実際のファイルと行番号を検索する際に、リストの先頭から順に辿っていく必要があり、その計算量はO(n)となっていました。nは履歴エントリの数、つまり処理された行数に比例します。大規模なプロジェクトや、多数のインクルードファイルを持つコードでは、この線形探索がコンパイル時間のボトルネックとなる可能性がありました。

このコミットの背景には、コンパイル性能の向上と、より堅牢で理解しやすい行履歴管理システムの構築という目的があります。O(n)の検索をO(log n)に改善することで、コンパイラの全体的な効率が向上し、特に大規模なコードベースでのコンパイル時間が短縮されることが期待されます。

## 前提知識の解説

### Goコンパイラの構造と `cmd/internal/obj` パッケージ

Goコンパイラは複数のステージに分かれており、`cmd/internal/obj` はその中でもアセンブラとリンカに近い部分を担当します。具体的には、Goソースコードから生成された中間表現（ASTなど）を元に、ターゲットアーキテクチャ向けのアセンブリコードを生成し、最終的なオブジェクトファイルや実行可能ファイルをリンクする役割を担います。この過程で、ソースコードのファイル名や行番号といったメタ情報を正確に追跡し、デバッグ情報としてバイナリに埋め込む必要があります。

### 行履歴 (Line History)

行履歴とは、コンパイラがソースファイルを処理する際に、現在の「仮想的な行番号」（コンパイラが内部的にカウントする連続した行番号）が、実際のソースファイルのどの物理的なファイル名と行番号に対応するかを記録するメカニズムです。
例えば、`#line` ディレクティブ（Goでは `//line`）を使用すると、コンパイラはそれ以降のコードの行番号を、指定されたファイルと行番号から始まるものとして扱います。また、Cgoのようなツールが生成するコードでは、元のC/C++コードの行番号とGoコードの行番号が混在することがあります。行履歴は、これらの複雑なマッピングを正確に管理し、エラーメッセージやデバッグ時に正しいソース位置を報告するために不可欠です。

### O(n) と O(log n) の計算量

*   **O(n) (線形探索)**: データ構造内の要素数 `n` に比例して処理時間が増加するアルゴリズムの効率性を示します。例えば、連結リストの要素を先頭から順に探す場合、最悪のケースではすべての要素をチェックする必要があるため、O(n)となります。
*   **O(log n) (対数探索)**: データ構造内の要素数 `n` の対数に比例して処理時間が増加するアルゴリズムの効率性を示します。これは非常に効率的で、`n` が大きくなっても処理時間の増加は緩やかです。ソートされた配列に対する二分探索が典型的な例です。

このコミットでは、行履歴の検索をO(n)からO(log n)に改善することで、コンパイラの性能向上を図っています。

### `Hist` 構造体 (変更前)

変更前の行履歴は、`Hist` という構造体の連結リストで表現されていました。

```go
type Hist struct {
	Link    *Hist
	Name    string
	Sym     *LSym
	Line    int32
	Offset  int32
	Printed uint8
}
```
`Link` フィールドが次の `Hist` エントリへのポインタとなっており、これにより履歴が時系列順に連結されていました。`Name` はファイル名、`Line` は仮想行番号、`Offset` は `#line` ディレクティブによるオフセットなどを記録していました。

### `LineHist`, `LineStack`, `LineRange` 構造体 (変更後)

変更後には、以下の新しい構造体が導入されました。

*   **`LineHist`**: 行履歴全体を管理するメインの構造体です。
    ```go
    type LineHist struct {
        Top            *LineStack  // current top of stack
        Ranges         []LineRange // ranges for lookup
        Dir            string      // directory to qualify relative paths
        TrimPathPrefix string      // remove leading TrimPath from recorded file names
        GOROOT         string      // current GOROOT
        GOROOT_FINAL   string      // target GOROOT
    }
    ```
    `Ranges` フィールドが特に重要で、これがO(log n)検索を可能にするソートされた範囲のリストを保持します。

*   **`LineStack`**: 行履歴スタックの各エントリを表します。
    ```go
    type LineStack struct {
        Parent    *LineStack // parent in inclusion stack
        Lineno    int        // virtual line number where this entry takes effect
        File      string     // file name used to open source file, for error messages
        AbsFile   string     // absolute file name, for pcln tables
        FileLine  int        // line number in file at Lineno
        Directive bool
        Sym       *LSym // for linkgetline - TODO(rsc): remove
    }
    ```
    `Parent` フィールドにより、インクルードスタック（ファイルが別のファイルをインクルードする階層構造）が表現されます。`Lineno` はこのエントリが有効になる仮想行番号、`File` はファイル名、`FileLine` はそのファイル内の行番号です。

*   **`LineRange`**: 行履歴の特定の範囲を表します。
    ```go
    type LineRange struct {
        Start int        // starting lineno
        Stack *LineStack // top of stack for this range
    }
    ```
    `Ranges` スライスはこの `LineRange` の配列であり、`Start` はその範囲が始まる仮想行番号、`Stack` はその範囲で有効な `LineStack` のトップエントリを指します。

### `sort.Search`

`sort.Search` はGo標準ライブラリの `sort` パッケージに含まれる関数で、ソートされたスライスに対して二分探索を実行します。この関数は、特定の条件を満たす最小のインデックスを効率的に見つけるために使用されます。このコミットでは、`LineHist.Ranges` スライスから特定の仮想行番号に対応する `LineRange` をO(log n)で検索するために利用されています。

## 技術的詳細

このコミットの核心は、行履歴のデータ構造と検索アルゴリズムの根本的な変更にあります。

### 旧来の `Hist` ベースの実装の問題点

従来の `Hist` 構造体は単方向連結リストとして機能していました。`Linklinefmt` や `linkgetline` のような関数は、このリストを先頭から順に辿って目的の行履歴エントリを見つけていました。

```go
// src/cmd/internal/obj/obj.go (変更前)
func Linklinefmt(ctxt *Link, lno0 int, showAll, showFullPath bool) string {
    // ...
    for h := ctxt.Hist; h != nil; h = h.Link { // O(n) 検索
        // ...
    }
    // ...
}
```
この `for` ループが示すように、最悪の場合、すべての `Hist` エントリを走査する必要があり、これがO(n)の性能ボトルネックとなっていました。

### 新しい `LineHist` と O(log n) 検索への移行

新しい実装では、`LineHist` 構造体が導入され、その内部に `Ranges` という `LineRange` 型のスライスが保持されます。`LineRange` は、特定の仮想行番号 (`Start`) から始まる範囲で有効な `LineStack` のトップエントリを記録します。

```go
// src/cmd/internal/obj/obj.go (変更後)
type LineHist struct {
    // ...
    Ranges         []LineRange // ranges for lookup
    // ...
}

type LineRange struct {
    Start int        // starting lineno
    Stack *LineStack // top of stack for this range
}
```

`Ranges` スライスは `Start` フィールド（仮想行番号）でソートされた状態に保たれます。これにより、特定の仮想行番号に対応する `LineRange` を見つけるために、Go標準ライブラリの `sort.Search` 関数を用いた二分探索が可能になります。

```go
// src/cmd/internal/obj/obj.go (変更後)
// At returns the input stack in effect at lineno.
func (h *LineHist) At(lineno int) *LineStack {
    i := sort.Search(len(h.Ranges), func(i int) bool {
        return h.Ranges[i].Start > lineno
    })
    // Found first entry beyond lineno.
    if i == 0 {
        return nil
    }
    return h.Ranges[i-1].Stack
}
```
`LineHist.At` メソッドは、与えられた `lineno` (仮想行番号) に対して、`Ranges` スライス内で `lineno` よりも大きい `Start` を持つ最初の `LineRange` のインデックスを `sort.Search` で見つけます。その直前の `LineRange` が、目的の `lineno` が属する範囲を示しており、その `Stack` フィールドが対応する `LineStack` を返します。これにより、検索の計算量はO(log n)に劇的に改善されます。

### 行履歴スタックの操作 (`Push`, `Pop`, `Update`)

`LineHist` は、行履歴スタックを操作するための `Push`, `Pop`, `Update` メソッドを提供します。

*   **`Push(lineno int, file string)`**: 新しいファイルがインクルードされたり、新しいソースファイルが処理され始めたりしたときに呼び出されます。新しい `LineStack` エントリを作成し、現在の `LineHist.Top` をその `Parent` として設定し、`Ranges` に新しい `LineRange` を追加します。
*   **`Pop(lineno int)`**: 現在のファイルがインクルードスタックからポップされたときに呼び出されます。`LineHist.Top` をその `Parent` に戻し、`Ranges` に新しい `LineRange` を追加して、その時点でのスタックの状態を記録します。
*   **`Update(lineno int, file string, line int)`**: `#line` ディレクティブなどによって、現在のファイル名や行番号が変更されたときに呼び出されます。既存の `LineStack` エントリを更新するか、新しい `LineStack` エントリを作成して `Ranges` に追加します。

これらのメソッドは、`startRange` ヘルパー関数を通じて `Ranges` スライスを適切に更新し、常にソートされた状態を維持します。

### ファイルパスの正規化

`LineHist` は、ファイルパスを正規化するためのロジックも内包しています。

*   `Dir`: 相対パスを絶対パスに解決するためのベースディレクトリ。
*   `TrimPathPrefix`: 特定のプレフィックスを持つパスを削除し、より簡潔なパスを生成します。これは、ビルド環境のパスがデバッグ情報に漏洩するのを防ぐためなどに使用されます。
*   `GOROOT`, `GOROOT_FINAL`: Goの標準ライブラリパスを、ビルド時の `GOROOT` から最終的なデプロイ先の `GOROOT_FINAL` に書き換えるために使用されます。

これらのフィールドは `LineHist.setFile` メソッド内で利用され、`LineStack` の `AbsFile` フィールドに正規化された絶対パスが設定されます。

### 既存APIの変更

`Linklinefmt` や `linkgetline` といった、行履歴情報を取得する既存のAPIは、新しい `LineHist` 構造体を利用するように変更されました。これにより、外部からこれらのAPIを呼び出すコードは変更する必要がなく、内部実装の改善が透過的に適用されます。

```go
// src/cmd/internal/obj/obj.go (変更後)
func Linklinefmt(ctxt *Link, lineno int, showAll, showFullPath bool) string {
    return ctxt.LineHist.LineString(lineno)
}

func linkgetline(ctxt *Link, lineno int32, f **LSym, l *int32) {
    stk := ctxt.LineHist.At(int(lineno))
    // ...
}
```
`Link` 構造体も `Hist` フィールドを削除し、`LineHist` フィールドを持つように変更されています。

```go
// src/cmd/internal/obj/link.go (変更後)
type Link struct {
    // ...
    LineHist           LineHist
    Imports            []string
    // ...
}
```

## コアとなるコードの解説

### `src/cmd/internal/obj/obj.go` における `LineHist` の導入と `At` メソッド

最も重要な変更は、`LineHist` 構造体の導入と、その `At` メソッドによる効率的な行履歴検索です。

```go
// src/cmd/internal/obj/obj.go
type LineHist struct {
	Top            *LineStack  // current top of stack
	Ranges         []LineRange // ranges for lookup
	Dir            string      // directory to qualify relative paths
	TrimPathPrefix string      // remove leading TrimPath from recorded file names
	GOROOT         string      // current GOROOT
	GOROOT_FINAL   string      // target GOROOT
}

type LineRange struct {
	Start int        // starting lineno
	Stack *LineStack // top of stack for this range
}

// At returns the input stack in effect at lineno.
func (h *LineHist) At(lineno int) *LineStack {
	i := sort.Search(len(h.Ranges), func(i int) bool {
		return h.Ranges[i].Start > lineno
	})
	// Found first entry beyond lineno.
	if i == 0 {
		return nil
	}
	return h.Ranges[i-1].Stack
}
```
`LineHist.Ranges` は、仮想行番号の範囲とその範囲で有効な `LineStack` のトップを記録する `LineRange` のスライスです。このスライスは `Start` フィールドで常にソートされています。

`At(lineno int)` メソッドは、特定の仮想行番号 `lineno` がどの `LineRange` に属するかを効率的に見つけます。`sort.Search` は、`h.Ranges` スライス内で、`Start` フィールドが `lineno` よりも大きい最初の要素のインデックス `i` を返します。もし `i` が0であれば、`lineno` はどの範囲にも属さないか、最初の範囲よりも前にあるため `nil` を返します。そうでなければ、`i-1` のインデックスにある `LineRange` が `lineno` を含む範囲であり、その `Stack` フィールドが目的の `LineStack` を指します。この二分探索により、検索の計算量はO(log n)となります。

### `src/cmd/internal/obj/link.go` における `Linklinehist` の変更

`Linklinehist` 関数は、コンパイラがソースファイルを処理する際に、行履歴スタックを操作するための主要なエントリポイントです。この関数は、新しい `LineHist` の `Push`, `Pop`, `Update` メソッドを呼び出すように変更されました。

```go
// src/cmd/internal/obj/link.go
// Linklinehist pushes, amends, or pops an entry on the line history stack.
// If f != "<pop>" and n == 0, the call pushes the start of a new file named f at lineno.
// If f != "<pop>" and n > 0, the call amends the top of the stack to record that lineno
// now corresponds to f at line n.
// If f == "<pop>", the call pops the topmost entry from the stack, picking up
// the parent file at the line following the one where the corresponding push occurred.
//
// If n < 0, linklinehist records f as a package required by the current compilation
// (nothing to do with line numbers).
//
// TODO(rsc): Replace uses with direct calls to ctxt.LineHist methods.
func Linklinehist(ctxt *Link, lineno int, f string, n int) {
	switch {
	case n < 0:
		ctxt.AddImport(f)

	case f == "<pop>":
		ctxt.LineHist.Pop(lineno)

	case n == 0:
		ctxt.LineHist.Push(lineno, f)

	default: // n > 0
		ctxt.LineHist.Update(lineno, f, n)
	}
}
```
この `switch` ステートメントは、`f` と `n` の値に基づいて、行履歴スタックに対して `Push` (新しいファイルの開始)、`Pop` (ファイルの終了)、`Update` (行ディレクティブによる変更) のいずれかの操作を実行します。`n < 0` のケースは行履歴とは直接関係なく、インポートされたパッケージを記録するために使用されます。

この変更により、`Linklinehist` は高レベルなインターフェースとして機能し、実際の行履歴の管理は `LineHist` 構造体のメソッドに委譲されるようになりました。これにより、コードの関心事が分離され、よりモジュール化された設計になっています。

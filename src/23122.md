# [インデックス 23122] ファイルの概要

このコミットは、Go言語の `crypto/tls` パッケージにおけるサーバーサイドの証明書ハンドリングロジックの改善に関するものです。具体的には、`tls.Config` の `Certificates` フィールドが空の場合でも `GetCertificate` コールバックが呼び出されるように変更され、SNI (Server Name Indication) が送信されないクライアントに対しても動的な証明書選択が可能になりました。

## 元コミット内容

`crypto/tls: call GetCertificate if Certificates is empty.`

この変更により、`Certificates` が空の場合に `GetCertificate` コールバックが呼び出されるようになります。以前は、この設定ではエラーが発生していました。

これにより、クライアントがSNIを送信しない場合でも、完全に動的な証明書選択に依存するサーバーを構築できるようになります。

Fixes #9208.

## 変更の背景

TLS (Transport Layer Security) サーバーは、クライアントからの接続要求に対して適切なサーバー証明書を提示する必要があります。Go言語の `crypto/tls` パッケージでは、サーバー証明書を設定する方法がいくつか提供されています。

1.  **`tls.Config.Certificates`**: サーバーが使用する静的な証明書のリストを直接指定する方法。通常、単一の証明書を使用する場合や、SNIなしでデフォルトの証明書を提供する場合に利用されます。
2.  **`tls.Config.NameToCertificate`**: SNIに基づいて証明書を動的に選択するためのマップ。クライアントが特定のホスト名をSNI拡張で送信した場合に、そのホスト名に対応する証明書を提供します。
3.  **`tls.Config.GetCertificate`**: 最も柔軟な方法で、クライアントの `ClientHello` メッセージに基づいて、プログラムで証明書を動的に取得・選択するためのコールバック関数。例えば、データベースから証明書をロードしたり、特定のロジックに基づいて証明書を生成したりする場合に利用されます。

このコミット以前は、`tls.Config.Certificates` が空の場合、GoのTLSサーバーは証明書を見つけられずにエラーを返していました。これは、`GetCertificate` コールバックが、`Certificates` が空の場合には呼び出されず、SNIが提供された場合にのみ呼び出されるというロジックになっていたためです。

しかし、一部のユースケースでは、サーバーが完全に動的な証明書選択に依存し、静的な証明書を一切持たない場合があります。特に、レガシーなクライアントや特定のネットワーク構成ではSNIが送信されないことがあり、そのような場合でも動的に証明書を提供できる必要があります。

このコミットは、この制約を解消し、`Certificates` が空の場合でも `GetCertificate` コールバックが呼び出されるようにすることで、SNI非対応のクライアントに対しても動的な証明書選択を可能にし、より柔軟なTLSサーバーの構築を支援することを目的としています。これは、Issue #9208 で報告された問題の解決策として実装されました。

## 前提知識の解説

*   **TLS (Transport Layer Security)**: インターネット上でデータを安全にやり取りするための暗号化プロトコル。HTTPSの基盤となっています。TLSハンドシェイク中に、サーバーは自身の身元を証明するためにサーバー証明書をクライプトに提示します。
*   **サーバー証明書**: サーバーの公開鍵と、その公開鍵が特定のエンティティ（ウェブサイトなど）に属することを証明するデジタル署名が含まれたファイル。通常、X.509形式で、PEMやDERエンコーディングで保存されます。
*   **SNI (Server Name Indication)**: TLSプロトコルの拡張機能の一つ。一つのIPアドレスで複数のウェブサイト（異なるドメイン名）をホストしているサーバーにおいて、クライアントが接続したいホスト名をTLSハンドシェイクの初期段階でサーバーに伝える仕組みです。これにより、サーバーは適切な証明書を選択してクライアントに提示できます。SNIがない場合、サーバーはどの証明書を提示すべきか判断できず、デフォルトの証明書を返すか、接続を拒否する可能性があります。
*   **`tls.Config`**: Go言語の `crypto/tls` パッケージでTLS接続の設定を定義するための構造体。サーバー証明書、ルートCA、プロトコルバージョン、暗号スイートなど、様々なTLS関連の設定が含まれます。
*   **`GetCertificate` コールバック**: `tls.Config` のフィールドの一つで、`func(clientHello *ClientHelloInfo) (*Certificate, error)` というシグネチャを持つ関数です。クライアントからの `ClientHello` メッセージ（SNI情報などを含む）に基づいて、サーバーが動的に証明書を選択・取得するために使用されます。
*   **`ClientHelloInfo`**: `GetCertificate` コールバックに渡される構造体で、クライアントが送信した `ClientHello` メッセージから抽出された情報（SNIのホスト名、サポートする暗号スイートなど）を含みます。

## 技術的詳細

この変更の核心は、`src/crypto/tls/common.go` 内の `(*Config).getCertificate` メソッドのロジック修正と、`src/crypto/tls/handshake_server.go` 内のサーバーハンドシェイク処理の調整にあります。

以前の `getCertificate` メソッドは、`c.GetCertificate != nil` かつ `len(clientHello.ServerName) > 0` (つまりSNIが提供された場合) にのみ `GetCertificate` コールバックを呼び出す条件を持っていました。このコミットでは、この条件に `len(c.Certificates) == 0` が追加されました。

変更前:
```go
func (c *Config) getCertificate(clientHello *ClientHelloInfo) (*Certificate, error) {
	if c.GetCertificate != nil { // この条件だけでは、Certificatesが空の場合にGetCertificateが呼ばれない
		// ...
	}
	// ...
}
```

変更後:
```go
func (c *Config) getCertificate(clientHello *ClientHelloInfo) (*Certificate, error) {
	if c.GetCertificate != nil &&
		(len(c.Certificates) == 0 || len(clientHello.ServerName) > 0) { // Certificatesが空の場合、またはSNIがある場合にGetCertificateを呼び出す
		cert, err := c.GetCertificate(clientHello)
		if cert != nil || err != nil {
			return cert, err
		}
	}

	if len(c.Certificates) == 0 { // GetCertificateがnilを返した場合、またはGetCertificateが設定されていない場合に、Certificatesが空であればエラーを返す
		return nil, errors.New("crypto/tls: no certificates configured")
	}

	// ...
}
```

この変更により、`tls.Config.Certificates` が空の場合でも、`GetCertificate` コールバックが優先的に呼び出されるようになりました。これにより、サーバーは静的な証明書を持たずとも、常に動的に証明書を提供しようと試みることができます。

また、`src/crypto/tls/handshake_server.go` では、サーバーハンドシェイクの初期段階で証明書を取得するロジックが簡素化されました。以前は、`Certificates` が空の場合に直接エラーを返すロジックと、SNIがある場合に `getCertificate` を呼び出すロジックが分かれていましたが、この変更により、常に `config.getCertificate` を呼び出すように統一されました。これにより、`getCertificate` メソッド内の新しいロジックが適用され、`Certificates` が空の場合でも `GetCertificate` コールバックが適切に利用されるようになります。

さらに、`src/crypto/tls/handshake_server_test.go` には、`TestHandshakeServerEmptyCertificates` という新しいテストケースが追加されました。このテストは、`Certificates` が空でSNIがない場合でも `GetCertificate` が呼び出されることを検証し、このコミットによる変更が意図通りに機能していることを確認しています。

## コアとなるコードの解説

このコミットの主要な変更は、`crypto/tls/common.go` 内の `(*Config).getCertificate` メソッドに集約されています。

以前の `getCertificate` メソッドは、`tls.Config.GetCertificate` が設定されている場合でも、クライアントがSNIを送信しない限り（つまり `clientHello.ServerName` が空の場合）、このコールバックを呼び出しませんでした。その結果、`tls.Config.Certificates` が空の場合、サーバーは利用可能な証明書がないと判断し、エラーを返していました。これは、完全に動的な証明書選択に依存するサーバーにとって制約となっていました。

今回の変更では、`getCertificate` メソッドの条件式が以下のように修正されました。

```go
if c.GetCertificate != nil &&
    (len(c.Certificates) == 0 || len(clientHello.ServerName) > 0) {
    // ... GetCertificate コールバックの呼び出し ...
}
```

この新しい条件式は、以下のいずれかの条件が満たされた場合に `GetCertificate` コールバックを呼び出すことを意味します。

1.  `c.GetCertificate` が `nil` ではない（コールバックが設定されている）。
2.  `len(c.Certificates) == 0`（静的な証明書が設定されていない）。
3.  `len(clientHello.ServerName) > 0`（クライアントがSNIを送信した）。

これにより、`Certificates` が空の場合でも、SNIの有無にかかわらず `GetCertificate` コールバックが呼び出されるようになりました。サーバーは、静的な証明書がなくても、常に動的な証明書取得ロジックにフォールバックできるようになります。

また、`GetCertificate` コールバックが `nil` を返したり、設定されていなかったりした場合に備えて、`len(c.Certificates) == 0` のチェックが追加され、その場合に明示的に "no certificates configured" エラーを返すようになりました。これは、証明書が全く提供されない状況での挙動を明確にするものです。

`src/crypto/tls/handshake_server.go` の変更は、この `getCertificate` メソッドの新しい挙動をサーバーハンドシェイクに統合するためのものです。以前の複雑な条件分岐を削除し、常に `config.getCertificate` を呼び出すようにすることで、コードが簡潔になり、新しいロジックが適用されるようになりました。

`src/crypto/tls/handshake_server_test.go` に追加されたテストケースは、この変更が正しく機能していることを保証します。特に、`Certificates` が空で `GetCertificate` がエラーを返すように設定されている場合に、SNIなしのクライアント接続が期待通りにエラーとなることを確認しています。

このコミットにより、GoのTLSサーバーは、より柔軟な証明書管理戦略を採用できるようになり、特に大規模なサービスや、証明書を動的にプロビジョニングする環境において、その運用が容易になります。

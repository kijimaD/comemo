## 変更の背景

Go言語は、その設計思想として「シンプルさ」と「明確さ」を重視しています。しかし、プログラミング言語の仕様においては、式の評価順序のような細かなセマンティクスが曖昧であると、プログラマが予期しない動作に遭遇したり、コンパイラの実装間で挙動が異なったりする原因となります。

このコミットが行われた2009年4月は、Go言語がまだ一般に公開される前の開発初期段階でした。この時期は、言語の基本的なセマンティクスが固められ、公式仕様書が作成されていく重要なフェーズでした。特に、並行処理を言語の第一級の機能として持つGoにおいて、関数呼び出しやチャネル通信といった操作の評価順序は、デッドロックや競合状態の発生を防ぐ上で極めて重要です。

このコミットは、Go言語の設計者の一人であるRob Pike氏によって行われました。これは、言語仕様の記述をより厳密にし、プログラマがGoコードの動作を正確に予測できるようにするための取り組みの一環と考えられます。特に、複合リテラルの評価順序に関するTODO項目が「Closed」に移されたことから、このコミットがその問題に対する解決策の一部、あるいはその方向性を示すものとして位置づけられていたことが伺えます。

## 前提知識の解説

このコミットの理解には、以下のGo言語およびプログラミング言語一般に関する知識が役立ちます。

*   **Go言語の基本構文**: 関数呼び出し、変数、式、チャネル操作（`<-`）など、Go言語の基本的な構文要素。
*   **式の評価 (Expression Evaluation)**: プログラミング言語において、式がどのように計算され、その結果がどのように得られるかのプロセス。これには、オペランドの評価順序、演算子の結合規則などが含まれます。
*   **副作用 (Side Effects)**: 関数呼び出しやチャネル操作のように、式の評価がプログラムの状態を変更するような動作。評価順序が未定義であると、副作用の発生順序が不定になり、プログラムの挙動が非決定論的になる可能性があります。
*   **Goの並行処理 (Concurrency in Go)**: Go言語のgoroutineとチャネルを用いた並行処理モデル。チャネルはgoroutine間の安全な通信手段を提供します。チャネルからの受信操作 (`<-c`) は、通信操作の一種であり、その評価順序は並行プログラムの正確性に影響を与えます。
*   **Go言語仕様 (Go Language Specification)**: Go言語の文法とセマンティクスを定義する公式文書。コンパイラの実装者や言語のユーザーにとって、言語の「真実の源」となります。

## 技術的詳細

このコミットの主要な技術的貢献は、Go言語仕様に「Order of evaluation（評価順序）」という新しいセクションを追加したことです。このセクションは、Go言語における式の評価順序に関する重要な規則を明確に定義しています。

追加された規則は以下の通りです。

> When evaluating the elements of an assignment or expression, all function calls, method calls and communication operations are evaluated in lexical left-to-right order. Otherwise, the order of evaluation is unspecified.

この規則は、Go言語の式の評価において、以下の3種類の操作に明確な順序を定めています。

1.  **関数呼び出し (function calls)**
2.  **メソッド呼び出し (method calls)**
3.  **通信操作 (communication operations)**

これらの操作は、式や代入文の要素として現れる場合、**字句的な左から右への順序 (lexical left-to-right order)** で評価されます。これは、ソースコード上で左に書かれたものが先に評価されることを意味します。

一方で、この規則は「それ以外の場合、評価順序は未指定である (Otherwise, the order of evaluation is unspecified)」と明記しています。これは、上記3種類の操作以外の要素（例：変数の評価、配列のインデックス評価、構造体のフィールド評価など）については、コンパイラが自由に評価順序を決定できることを意味します。この「未指定」という特性は、コンパイラが最適化を行う上で重要な柔軟性を提供します。

コミットに含まれる例 `f(g(), h() + x[i()], <-c)` は、この規則を具体的に示しています。

*   `g()`: 最初の関数呼び出しなので、最初に評価されます。
*   `h()`: `h() + x[i()]` の一部ですが、`h()` は `g()` の後に評価されます。
*   `i()`: `x[i()]` のインデックス式の一部ですが、`h()` の後に評価されます。
*   `<-c`: チャネルからの受信操作であり、`i()` の後に評価されます。

この例は、引数リスト内の関数呼び出しや通信操作が、ソースコード上の出現順序（左から右）で評価されることを明確に示しています。しかし、`f` 自体の評価、`x` の評価、そして `i()` の戻り値による `x` のインデックス付けの順序は、これらの関数呼び出しや通信操作と比較して未指定であることも強調されています。これは、コンパイラがこれらの操作を並行して実行したり、最適化のために順序を変更したりする可能性があることを示唆しています。

この明確化は、特に並行処理を含むGoプログラムの挙動を予測する上で非常に重要です。例えば、チャネルからの受信操作が特定の順序で発生することが保証されることで、デッドロックや競合状態の発生をより正確に制御できるようになります。

また、このコミットでは、文法定義の軽微な修正も行われています。`Option = "[" Expression ")" .` が `Option = "[" Expression "]" .` に修正されており、これは文法規則の閉じ括弧のタイプミスを修正したものです。これは言語仕様の正確性を高めるための細かな修正ですが、言語の厳密な定義には不可欠です。

## コアとなるコードの変更箇所

このコミットにおける「コアとなるコード」は、Go言語の公式仕様書である `doc/go_spec.html` ファイルです。

具体的な変更箇所は以下の通りです。

1.  **`Todo` リストの更新**:
    *   `[ ] decide if and what to write about evaluation order of composite literal elements (single expressions, (key:value) pairs)` というTODO項目が削除されました。
2.  **`Closed` リストの更新**:
    *   上記で削除されたTODO項目が、`[x] decide if and what to write about evaluation order of composite literal elements (single expressions, (key:value) pairs)` として`Closed`リストに追加されました。これは、このコミットによってこの課題が解決されたことを示唆しています。
3.  **文法定義の修正**:
    *   `<pre>` タグ内の文法定義で、`Option = "[" Expression ")" .` が `Option = "[" Expression "]" .` に修正されました。閉じ括弧が `)` から `]` に変更されています。
4.  **「Order of evaluation」セクションの追加**:
    *   `<h3>Order of evaluation</h3>` という見出しの下に、評価順序に関する新しい段落とコード例が追加されました。
        *   評価順序の規則を説明する `<p>` タグ。
        *   具体的なコード例 `f(g(), h() + x[i()], <-c)` を含む `<pre>` タグ。
        *   コード例の評価順序を詳細に説明する `<p>` タグ。

## コアとなるコードの解説

`doc/go_spec.html` は、Go言語の文法、型システム、実行セマンティクスなどを定義するHTML形式のドキュメントです。このファイルへの変更は、Go言語の「振る舞い」に関する公式な記述を直接変更することを意味します。

追加された「Order of evaluation」セクションは、Go言語の式がどのように評価されるかについて、以前は暗黙的であったり、未定義であったりした部分を明文化しています。

*   **字句的な左から右への評価**: 関数呼び出し、メソッド呼び出し、通信操作がこの順序で評価されるという規則は、Goのコードが直感的に理解しやすいように設計されていることを示しています。多くのプログラマは、コードが書かれた順序で実行されることを期待するため、この規則はGoの「シンプルさ」と「予測可能性」に貢献します。
*   **未指定の評価順序**: それ以外の要素の評価順序が未指定であることは、コンパイラがより積極的な最適化を行うための余地を残しています。例えば、依存関係のない複数の変数の評価は、コンパイラが並行して行ったり、実行環境の特性に合わせて順序を入れ替えたりすることができます。これにより、生成されるバイナリのパフォーマンスが向上する可能性があります。
*   **複合リテラルの評価順序の解決**: `Closed` リストに複合リテラルの評価順序に関する項目が追加されたことは、このコミットがその問題に対する公式な回答を提供したことを示唆しています。複合リテラルの要素も式であるため、その中に含まれる関数呼び出しなどがこの新しい評価順序の規則に従うことになります。

このドキュメントの更新は、Go言語のセマンティクスをより厳密に定義し、プログラマがGoプログラムの動作をより正確に理解し、予測できるようにするための重要なステップでした。

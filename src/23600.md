# [インデックス 23600] ファイルの概要

このコミットは、Go言語のアセンブラツール (`cmd/asm`) の内部で使用される `obj.Addr` 構造体から `Reg2` フィールドを削除するものです。この `Reg2` フィールドは、レジスタペア（例: `R1:R2`）の2番目のレジスタを格納するために意図されていましたが、実際には使用されることがなく、到達不能なコードパスに存在していたため、削除されました。

## 変更の背景

この変更の背景には、Goのアセンブラ (`cmd/asm`) の内部実装における冗長性または未使用コードの削除があります。`obj.Addr` 構造体は、アセンブリ命令のオペランド（アドレスやレジスタなど）を表現するために使用されます。元々、この構造体には `Reg2` というフィールドが含まれており、これは `R1:R2` のようなレジスタペアの2番目のレジスタを格納することを意図していました。

しかし、`src/cmd/asm/internal/asm/parse.go` 内の関連コードを見ると、`r2` が非ゼロの場合（つまり `Reg2` が設定されるべき状況）に `panic("cannot happen")` というコードが配置されていました。これは、開発者がこのコードパスが実行されることはない、あるいは実行されるべきではないと考えていたことを示唆しています。コミットメッセージの「That which cannot happen has not happened.」（起こりえないことは起こらなかった）という表現は、この `Reg2` フィールドが実際に必要とされる状況が一度も発生しなかったことを明確に示しています。

したがって、このコミットは、実際に使用されていない、あるいは設計上不要と判断された `Reg2` フィールドを削除することで、コードベースを簡素化し、保守性を向上させることを目的としています。コミットメッセージにある「No immediate changes to Addr or Prog size.」という記述は、このフィールドが削除されても、構造体のメモリレイアウトやサイズに直接的な影響がないことを示しており、これはおそらくパディングやアライメントの都合によるものと考えられます。

## 前提知識の解説

### Goのアセンブラ (`cmd/asm`)

Go言語は、そのツールチェインの一部として独自のアセンブラ (`cmd/asm`) を持っています。これは、Goのソースコードから生成されるアセンブリコードを処理したり、Goプログラム内でインラインアセンブリを使用したりする際に利用されます。Goのアセンブラは、AT&T構文やIntel構文とは異なる、Plan 9スタイルの構文を採用しており、レジスタやメモリのアドレス指定方法に特徴があります。

### `obj.Addr` 構造体

`obj.Addr` は、Goのツールチェインの内部パッケージ `cmd/internal/obj` で定義されている重要な構造体です。この構造体は、アセンブリ命令のオペランド、特にメモリアドレスやレジスタの情報を抽象的に表現するために使用されます。具体的には、アドレスのタイプ（レジスタ、メモリ、定数など）、ベースレジスタ、インデックスレジスタ、オフセット、スケールなどの情報を保持します。アセンブラがソースコードを解析し、機械語に変換する過程で、これらの `Addr` 構造体が頻繁に生成・操作されます。

### レジスタペア (R1:R2)

一部のCPUアーキテクチャやアセンブリ命令では、複数のレジスタを組み合わせて1つの大きな値（例: 64ビット値）を表現したり、特定の操作（例: 除算の結果）で複数のレジスタを使用したりすることがあります。このような場合、「レジスタペア」という概念が用いられます。`Addr.Reg2` は、このようなレジスタペアの2番目のレジスタを格納するために設計された可能性があります。例えば、32ビットアーキテクチャで64ビットの値を扱う際に、2つの32ビットレジスタ（例: `AX:DX`）を使用するようなケースが考えられます。

### `panic("cannot happen")`

Go言語における `panic` は、プログラムの回復不能なエラーを示すために使用されます。特に `panic("cannot happen")` のようなメッセージは、開発者が「このコードパスは論理的に到達不可能である」と確信している場合に用いられます。もしこのパニックが実際に発生した場合、それはプログラムのロジックに深刻な欠陥があることを意味します。このコミットでは、`Reg2` が設定されるべき状況でこのパニックが発生するようにコードが書かれていたため、`Reg2` が実際に使用されることはなかった、という強力な証拠となります。

## 技術的詳細

このコミットは、Goのアセンブラツールチェインの2つのファイルに影響を与えます。

1.  **`src/cmd/asm/internal/asm/parse.go`**:
    このファイルは、アセンブリソースコードを解析し、抽象構文ツリー（AST）や中間表現に変換する役割を担っています。変更箇所は、オペランドを解析する `operand` メソッド内にあります。
    元のコードでは、`R1:R2` 形式のレジスタペアが検出された場合、`a.Reg` に `r1` を設定し、`r2` が非ゼロであれば `a.Reg2 = r2` を設定しようとしていました。しかし、その直前に `panic("cannot happen")` が存在し、`a.Reg2 = r2` の行はコメントアウトされ、「TODO: If we never see this again, can delete Addr.Reg2.」というコメントがありました。
    今回の変更では、このコメントアウトされた `a.Reg2 = r2` の行が完全に削除され、`panic` メッセージも `panic("cannot happen (Addr.Reg2)")` とより具体的に変更されました。これは、`R1:R2` 形式のレジスタペアが `Addr.Reg2` を使用する形で処理されることが、Goのアセンブラの現在の設計では想定されていないことを明確にしています。

2.  **`src/cmd/internal/obj/link.go`**:
    このファイルは、オブジェクトファイルのリンク処理に関連する定義を含んでいます。`obj.Addr` 構造体の定義もここにあります。
    変更箇所は、`Addr` 構造体から `Reg2 int16 // RHS of register pair. AX:DX (386)` の行が削除されたことです。これにより、`Addr` 構造体から未使用のフィールドが物理的に取り除かれました。

コミットメッセージにある「No immediate changes to Addr or Prog size.」という記述は興味深い点です。通常、構造体からフィールドを削除すると、その構造体のサイズは減少します。しかし、このケースではサイズに変化がないとされています。これは、Goのコンパイラが構造体のフィールドをアライメントのためにパディングすることがあり、`Reg2` フィールドが削除されても、そのパディングによって占められていたメモリ領域が他のフィールドのために再利用されるか、あるいは構造体全体のサイズに影響を与えないような位置にあったためと考えられます。例えば、`Reg2` の後に続くフィールドが既に4バイト境界や8バイト境界にアライメントされており、`Reg2` の削除がそのアライメント要件に影響を与えなかった場合などが考えられます。

## コアとなるコードの解説

### `src/cmd/asm/internal/asm/parse.go` の変更点

この変更は、`operand` 関数内でレジスタペア `R1:R2` の形式が検出された際の処理ロジックを簡素化しています。
元のコードでは、`r2` が存在する場合に `a.Reg2 = r2` を設定する可能性がコメントアウトされており、その直前に `panic("cannot happen")` がありました。これは、`Reg2` を使用するパスが意図的に無効化されていたことを示します。
今回の変更では、コメントアウトされていた `a.Reg2 = r2` の行が完全に削除され、`panic` メッセージが `panic("cannot happen (Addr.Reg2)")` とより明確になりました。これにより、`R1:R2` 形式のオペランドが `Addr.Reg2` を介して処理されることはなく、もしそのような状況が発生した場合は、それが予期せぬエラーであることを明確に示します。これは、`Addr.Reg2` がGoのアセンブラの現在の設計では不要であるという判断を裏付けています。

### `src/cmd/internal/obj/link.go` の変更点

この変更は、`obj.Addr` 構造体から `Reg2 int16` フィールドを直接削除しています。
`Reg2` フィールドは、コメントに「RHS of register pair. AX:DX (386)」とあるように、レジスタペアの右側のレジスタを格納するために予約されていました。しかし、前述の `parse.go` の変更からもわかるように、このフィールドは実際には使用されていませんでした。
この削除により、`Addr` 構造体の定義がクリーンアップされ、未使用のメモリ領域が解放されます。コミットメッセージが「No immediate changes to Addr or Prog size.」と述べているのは、Goの構造体アライメントの特性によるもので、`int16` 型のフィールドが削除されても、構造体全体のサイズやアライメントに影響がない場合があるためです。これは、コンパイラがメモリ効率のためにフィールド間にパディングを挿入することがあり、そのパディングが `Reg2` の削除によって吸収された可能性を示唆しています。

これらの変更は、Goのアセンブラの内部実装を簡素化し、実際に使用されていないコードパスやデータ構造を取り除くことで、コードベースの健全性と保守性を向上させるものです。

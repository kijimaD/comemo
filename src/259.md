## 変更の背景

Goコンパイラの初期段階では、コード生成時に特定の複雑な式、特に代入演算子の両辺が関数呼び出しを含むようなケースで、コンパイラが処理を中断し「fatal」エラーを発生させる問題がありました。これは、コンパイラが中間結果を保持するためのレジスタ割り当てや、副作用の評価順序を適切に管理できない場合に起こります。

このコミットは、このような「両辺が関数呼び出し」のような複雑なシナリオを、一時変数（テンポラリ）を導入することで解決し、コンパイラの堅牢性とコード生成能力を向上させることを目的としています。これにより、より複雑なGoプログラムも正しくコンパイルできるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のコンパイラ理論とGoコンパイラの内部構造に関する知識が必要です。

1.  **Goコンパイラ (6g):**
    `6g`は、Go言語の初期のコンパイラの一つで、主に64ビットx86アーキテクチャをターゲットとしていました。Goコンパイラは、ソースコードを抽象構文木（AST）にパースし、中間表現（IR）に変換した後、最終的にターゲットマシンコードを生成します。

2.  **Ullman Number (Sethi-Ullman Number):**
    Ullman Number（またはSethi-Ullman Number）は、コンパイラ理論における重要な概念で、式ツリーの各ノードに対して計算されます。これは、そのノードを根とするサブツリーを評価するために必要な最小レジスタ数を表します。
    -   **`UINF` (Ullman Infinity):** このコミットでは、`UINF`という定数が登場します。これは「Ullman Infinity」を意味し、通常、その式が非常に複雑であるか、関数呼び出しのような副作用を持つため、直接レジスタで評価することが困難であることを示します。`UINF`を持つ式は、中間結果をメモリに「スピル」（一時的に保存）する必要があるか、特別な処理が必要になります。

3.  **コード生成 (`cgen`, `gen`, `cgen_asop`, `cgen_as`):**
    -   **`cgen` (Code Generation):** Goコンパイラにおける汎用的なコード生成関数の一つと考えられます。ASTノードを受け取り、それに対応するマシンコードを生成する役割を担います。
    -   **`gen`:** `cgen`と同様にコード生成に関連する関数群を含むファイルです。
    -   **`cgen_asop` / `cgen_as`:** これらは特に代入演算子（`=`など）のコード生成を扱う関数であると推測されます。代入は、左辺と右辺の評価順序や副作用の扱いに注意が必要なため、専用の処理が用意されることがあります。

4.  **`Node`構造体:**
    コンパイラ内部でプログラムの構造を表す抽象構文木（AST）や中間表現（IR）のノードを定義する構造体です。各ノードは、演算子、変数、定数、関数呼び出しなど、プログラムの要素を表します。

5.  **`tempname`関数:**
    コンパイラが一時変数（テンポラリ）を生成するために使用する関数です。複雑な式を複数のステップに分解する際に、中間結果を保持するために一時変数が導入されます。

6.  **`fatal`関数:**
    コンパイラが回復不能なエラーを検出した際に、コンパイルプロセスを中断し、エラーメッセージを出力するために使用される関数です。

## 技術的詳細

このコミットの核心は、`ullman >= UINF`という条件が真となる、つまり非常に複雑な式や副作用を持つ式を検出した場合のコンパイラの挙動を変更することにあります。以前はこのような状況で`fatal`エラーを発生させていましたが、変更後は一時変数（テンポラリ）を導入して問題を回避します。

具体的な変更点は以下の通りです。

1.  **`src/cmd/6g/cgen.c`における`cgen`関数の変更:**
    -   `cgen`関数内で、`res->ullman >= UINF`という条件がチェックされる箇所があります。これは、式の評価結果を格納する`res`ノード自体が複雑な式や関数呼び出しである場合を指します。
    -   **変更前:** `fatal("cgen: node and result functions")`を呼び出し、コンパイルを中断していました。
    -   **変更後:**
        1.  `tempname(&n1, n->type);`：`n`（評価対象のノード）と同じ型の新しい一時変数`n1`を生成します。
        2.  `cgen(n, &n1);`：元のノード`n`を評価し、その結果を一時変数`n1`に格納します。
        3.  `cgen(&n1, res);`：一時変数`n1`の内容を最終的な結果`res`に移動させます。
        4.  `goto ret;`：関数から適切に抜けるために`ret`ラベルにジャンプします。
        この変更により、`res`が複雑な場合でも、`n`を一時変数に評価することで問題を回避し、コンパイルを続行できるようになりました。

    -   また、`cgen`関数内の別の箇所で、`if(nl->ullman >= UINF)`ブロック内で`return;`となっていた部分が`goto ret;`に変更されています。これは、関数内の複数の終了パスを`ret`ラベルに集約し、制御フローの一貫性を保つためのリファクタリングと考えられます。

2.  **`src/cmd/6g/gen.c`における`cgen_asop`関数の変更:**
    -   `cgen_asop`関数（代入演算子のコード生成）内で、`nr->ullman >= UINF && nl->ullman >= UINF`という条件がチェックされる箇所があります。これは、代入の右辺（`nr`）と左辺（`nl`）の両方が複雑な式や関数呼び出しである場合を指します。
    -   **変更前:** `fatal("cgen_asop: both sides call")`を呼び出し、コンパイルを中断していました。
    -   **変更後:**
        1.  `tempname(&n1, nr->type);`：右辺`nr`と同じ型の新しい一時変数`n1`を生成します。
        2.  `cgen(nr, &n1);`：右辺`nr`を評価し、その結果を一時変数`n1`に格納します。
        3.  `n2 = *n;`：元の代入ノード`n`のコピー`n2`を作成します。
        4.  `n2.right = &n1;`：コピーしたノード`n2`の右辺を、先ほど結果を格納した一時変数`n1`に置き換えます。
        5.  `cgen_asop(&n2);`：右辺が一時変数に置き換えられた新しい代入ノード`n2`に対して、`cgen_asop`を再帰的に呼び出します。
        この戦略により、複雑な右辺をまず一時変数に評価し、その後、より単純な代入（一時変数から左辺へ）として処理することで、「両辺が複雑」という問題を段階的に解決しています。

3.  **`src/cmd/6g/gen.c`における`cgen_as`関数の変更:**
    -   `cgen_as`関数内で、以前は`if(nr->ullman >= UINF && nl->ullman >= UINF)`という条件で`fatal("cgen_as both sides call")`を呼び出していたブロックが**削除**されています。
    -   これは、`cgen_asop`関数における変更によって「両辺が複雑な代入」のケースが適切に処理されるようになったため、`cgen_as`内で別途`fatal`エラーを出す必要がなくなったことを示唆しています。これにより、コードの重複が避けられ、より一元的なエラーハンドリングが可能になっています。

これらの変更は、コンパイラが複雑な式を扱う際の戦略を根本的に改善し、一時変数を活用することで、以前はコンパイルエラーとなっていた有効なGoコードを正しく処理できるようにしました。

## コアとなるコードの解説

### `src/cmd/6g/cgen.c` の変更点

-   **`cgen`関数内の`res->ullman >= UINF`ブロック:**
    この変更は、`cgen`関数がノード`n`を評価し、その結果を`res`に格納しようとする際に、`res`自体が非常に複雑な式（`ullman >= UINF`）である場合に適用されます。
    -   以前は、このような状況をコンパイラの限界として`fatal`エラーで処理していました。
    -   新しいコードでは、まず`n`の評価結果を一時変数`n1`に格納します（`cgen(n, &n1)`）。その後、この一時変数`n1`の内容を`res`に移動させることで（`cgen(&n1, res)`）、`res`の複雑さに直接対処することなく、`n`の評価を完了させます。これにより、コンパイラはより柔軟にコードを生成できるようになります。`goto ret;`は、この処理が完了した後に`cgen`関数を適切に終了させるためのものです。

-   **`cgen`関数内の`return;`から`goto ret;`への変更:**
    これは、特定の条件（`nl->ullman >= UINF`）で一時変数`n1`を使用した後、関数を終了する際の制御フローの変更です。`return;`を`goto ret;`に置き換えることで、関数内の複数の終了ポイントを`ret`ラベルに集約し、コードの可読性と保守性を向上させています。

### `src/cmd/6g/gen.c` の変更点

-   **`cgen_asop`関数内の`nr->ullman >= UINF && nl->ullman >= UINF`ブロック:**
    この変更は、代入演算子（`cgen_asop`）の右辺`nr`と左辺`nl`の両方が複雑な式（`ullman >= UINF`）である場合に発生する問題を解決します。
    -   以前は、この状況も`fatal`エラーとして処理されていました。
    -   新しいコードでは、まず右辺`nr`を評価し、その結果を一時変数`n1`に格納します（`cgen(nr, &n1)`）。
    -   次に、元の代入ノード`n`をコピーした`n2`を作成し、その右辺を一時変数`n1`に置き換えます（`n2.right = &n1`）。
    -   最後に、右辺が一時変数に置き換えられた新しい代入ノード`n2`に対して`cgen_asop`を再帰的に呼び出します。これにより、複雑な代入を「右辺を一時変数に評価する」と「一時変数を左辺に代入する」という二つのより単純なステップに分解し、コンパイラが処理できるようにします。

-   **`cgen_as`関数からの`fatal`エラーチェックの削除:**
    `cgen_as`関数は、代入に関連する別のコード生成関数です。以前は、`cgen_asop`と同様に「両辺が複雑」な場合に`fatal`エラーを発生させていました。
    -   `cgen_asop`における変更によって、この種の複雑な代入が適切に処理されるようになったため、`cgen_as`内の同様の`fatal`エラーチェックは不要となり、削除されました。これは、コンパイラのロジックがより洗練され、重複するエラーハンドリングが排除されたことを示しています。

これらの変更は、Goコンパイラがより広範なGoプログラムを、より堅牢かつ効率的にコンパイルできるようにするための重要な改善です。

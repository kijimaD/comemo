## 元コミット内容

このコミットは、`runtime/debug` パッケージ内の `TestFreeOSMemory` テストにおいて、`arm64` アーキテクチャ、特に `darwin/arm64` 環境でのテストを一時的に無効化するものです。これは、`issue 9993` として知られる問題、すなわち物理ページサイズと論理ページサイズが異なるシステムで発生する不具合を回避するためです。コミットメッセージでは、この問題がGo 1.5で修正されることを期待しつつも、現状では他のスキップされているOS/アーキテクチャの組み合わせと同様のバグを示していると述べられています。

## 変更の背景

Goランタイムは、効率的なメモリ管理のためにガベージコレクション（GC）と、OSへのメモリ解放（scavenger）のメカニズムを持っています。`TestFreeOSMemory` は、GoがOSにメモリを適切に解放しているかを確認するためのテストです。

`issue 9993` は、特定のシステムアーキテクチャ（特に `ppc64`、`ppc64le`、`nacl`）において、物理メモリページサイズと論理メモリページサイズが異なる場合に、Goのメモリ解放メカニズム（scavenger）が正しく機能しない、または期待通りの動作をしないという問題です。

`darwin/arm64` 環境もまた、他の `arm64` プラットフォームと同様に、物理ページサイズと論理ページサイズが異なる特性を持っています。この違いが `issue 9993` と同じ根本的な問題を引き起こし、`TestFreeOSMemory` テストが失敗する原因となっていました。Go 1.5での修正が期待されていましたが、それまでの間、テストのCI/CDパイプラインが失敗し続けるのを避けるため、一時的に `darwin/arm64` 環境でのテストをスキップする変更が導入されました。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するシステムです。ガベージコレクタ、スケジューラ、メモリ管理など、Go言語の並行処理やメモリ安全性を実現するための多くの機能を含んでいます。
*   **ガベージコレクション (Garbage Collection, GC)**: プログラムが動的に確保したメモリ領域のうち、もはや使用されなくなったものを自動的に解放する仕組みです。GoのGCは並行かつ低遅延で動作するように設計されています。
*   **メモリ管理 (Memory Management)**: プログラムがメモリを効率的に利用するための仕組みです。Goランタイムは独自のメモリヒープを持ち、OSからメモリを確保し、それをGoプログラム内で管理します。
*   **`runtime.MemStats`**: Goプログラムのメモリ使用状況に関する統計情報を提供する構造体です。GCの動作、ヒープサイズ、OSへのメモリ解放量など、詳細な情報が含まれます。
*   **`runtime.FreeOSMemory()`**: GoランタイムがOSに未使用のメモリを積極的に解放するよう促す関数です。これにより、Goプログラムが使用する物理メモリ量を削減し、システム全体のメモリ効率を向上させることができます。この関数は、特に長時間実行されるサーバーアプリケーションなどで、メモリフットプリントを抑えるために利用されます。
*   **ページサイズ (Page Size)**: オペレーティングシステムがメモリを管理する際の最小単位です。メモリは「ページ」と呼ばれる固定サイズのブロックに分割されて管理されます。
    *   **論理ページサイズ (Logical Page Size)**: プロセスがメモリを扱う際の仮想アドレス空間におけるページサイズです。多くのシステムでは4KBが一般的です。
    *   **物理ページサイズ (Physical Page Size)**: 物理メモリにおける実際のページサイズです。一部のアーキテクチャ（例: `ppc64`, `arm64`）では、パフォーマンス上の理由から、論理ページサイズよりも大きな物理ページサイズ（例: 64KB）を使用することがあります。
*   **スカベンジャー (Scavenger)**: Goランタイムのメモリ管理の一部で、Goヒープ内で不要になったメモリ領域をOSに返却する役割を担います。これにより、Goプロセスが占有する物理メモリ量を減らし、他のプロセスが利用できるようにします。
*   **`t.Skip()` (Goテスト)**: Goのテストフレームワーク `testing` パッケージの機能です。`t.Skip()` が呼び出されると、そのテストはスキップされ、テスト結果には「SKIP」として記録されます。これは、特定の環境や条件でのみ発生する問題や、まだ修正されていないバグのためにテストを一時的に無効化する際に使用されます。

## 技術的詳細

`issue 9993` の核心は、Goランタイムのスカベンジャーが、物理ページサイズと論理ページサイズが異なるシステムで、メモリの解放を正確に追跡・実行できないことにあります。

通常、GoランタイムはOSからメモリを確保し、それを自身のヒープとして管理します。プログラムがメモリを使い、GCが不要なオブジェクトを回収した後、スカベンジャーはGoヒープ内の空き領域をOSに返却しようとします。この返却処理は、OSのページ単位で行われます。

問題が発生するシステムでは、論理ページサイズ（例: 4KB）と物理ページサイズ（例: 64KB）が異なります。Goランタイムは論理ページサイズに基づいてメモリを管理しようとしますが、OSは物理ページサイズ単位でしかメモリの解放を受け付けません。このミスマッチにより、Goランタイムが「この4KBの論理ページは空いているからOSに返せる」と判断しても、実際にはその4KBが含まれる64KBの物理ページ全体が完全に空いていない限り、OSは解放を受け付けません。結果として、Goランタイムが期待するほどメモリがOSに返却されず、`TestFreeOSMemory` のようなテストが失敗する原因となります。

`darwin/arm64` は、この物理ページサイズと論理ページサイズの不一致を持つプラットフォームの一つであり、`ppc64` や `ppc64le` と同様にこの問題の影響を受けます。このコミットは、この根本的な問題が解決されるまでの間、テストの安定性を確保するための暫定的な措置として、該当環境でのテストをスキップするように変更しました。

1.  **条件式の追加**:
    変更前:
    ```go
    if runtime.GOARCH == "ppc64" || runtime.GOARCH == "ppc64le" || runtime.GOOS == "nacl" {
    ```
    変更後:
    ```go

    ```

2.  **スキップメッセージの変更**:
    変更前:
    ```go
    t.Skip("issue 9993; scavenger temporarily disabled on systems with 64k pages")
    ```
    変更後:
    ```go
    t.Skip("issue 9993; scavenger temporarily disabled on systems with physical pages larger than logical pages")
    ```
    スキップメッセージがより汎用的な表現に変更されました。「64kページを持つシステム」という具体的な記述から、「論理ページよりも大きな物理ページを持つシステム」という、より正確で広範な問題の記述に修正されています。これは、問題の根本原因が単に64KBページであることだけでなく、物理ページと論理ページのサイズ不一致にあることを明確にしています。

## 元コミット内容

このコミットの目的は、「`image/gif`: フレームごとの透過インデックスがグローバルパレットを変更しないようにする」ことです。これは、GoのIssue #7993を修正するものです。

## 変更の背景

GIF (Graphics Interchange Format) は、複数の画像を連続して表示することでアニメーションを表現できる画像フォーマットです。GIFの各フレーム（画像）は、それぞれ独自のカラーパレットを持つことができますが、多くの場合、ファイル全体で共有される「グローバルカラーパレット」を参照します。また、GIFは透過色をサポートしており、特定のインデックスのピクセルを透過として扱うことができます。

このコミットが修正する問題は、GIFのデコード処理において、個々のフレームが持つ「透過インデックス」が、誤ってグローバルカラーパレットを直接変更してしまっていた点にあります。具体的には、あるフレームが透過色を指定する際に、その透過色に対応するグローバルパレットのエントリをRGBA値 `(0,0,0,0)` (完全に透明な黒) に上書きしてしまっていました。

この挙動は、単一フレームのGIFや、透過色を使用しないGIFでは問題になりません。しかし、複数のフレームを持つアニメーションGIFで、異なるフレームが同じグローバルパレットを参照し、かつ透過インデックスを使用する場合に問題が発生します。あるフレームが透過インデックスを設定すると、その変更がグローバルパレットに永続的に適用されてしまい、後続のフレームがその透過インデックスに対応する色を本来の色として表示できなくなる、というバグがありました。これは、透過処理がフレームローカルなものであるべきなのに、グローバルな状態に副作用を与えていたためです。

Issue #7993では、この問題が具体的に報告されており、透過インデックスがグローバルパレットを破壊し、アニメーションの表示がおかしくなる例が示されていました。

## 前提知識の解説

### GIFフォーマットの基本

*   **論理画面記述子 (Logical Screen Descriptor)**: GIFファイルの全体的なキャンバスサイズ、背景色、ピクセルアスペクト比などを定義します。
*   **グローバルカラーテーブル (Global Color Table - GCT)**: GIFファイル全体で共有されるカラーパレットです。最大256色を定義でき、各色はRGB値で表現されます。
*   **画像記述子 (Image Descriptor)**: 各画像ブロック（フレーム）の開始位置、サイズ、ローカルカラーテーブルの有無などを定義します。
*   **ローカルカラーテーブル (Local Color Table - LCT)**: 各画像ブロックが独自のカラーパレットを持つ場合に定義されます。LCTが存在する場合、その画像ブロックではGCTよりもLCTが優先されます。
*   **グラフィックコントロール拡張 (Graphic Control Extension - GCE)**: 各画像ブロックの表示方法を制御するオプション情報です。これには、遅延時間、破棄方法、そして**透過インデックス (Transparent Color Index)** が含まれます。
*   **透過インデックス**: GCE内で指定される、パレット内の特定の色インデックスです。このインデックスに対応するピクセルは、描画時に完全に透過として扱われます。

### Go言語の `image/gif` パッケージ

Goの標準ライブラリ `image/gif` パッケージは、GIF画像のエンコードとデコード機能を提供します。
*   `gif.Decode(r io.Reader)`: `io.Reader` からGIF画像をデコードし、`image.Image` インターフェースを実装する画像オブジェクトを返します。
*   `gif.DecodeAll(r io.Reader)`: アニメーションGIFのすべてのフレームをデコードし、`*GIF` 構造体を返します。この構造体には、各フレームの `image.Paletted` オブジェクトと、フレームごとの遅延時間などの情報が含まれます。
*   `image.Paletted`: パレット化された画像を表現するGoの画像型です。`Palette` フィールドは `color.Palette` 型であり、これは `[]color.Color` のエイリアスです。

### Goにおけるスライスと参照

Go言語において、スライスは基となる配列への参照です。あるスライスを別の変数に代入しても、それは同じ基となる配列を指します。したがって、スライスを介して要素を変更すると、その基となる配列が変更され、その配列を参照する他のすべてのスライスにも影響が及びます。

このコミットの文脈では、`m.Palette` が `d.globalColorMap` を直接参照している場合、`m.Palette` への変更（透過インデックスの色の設定）が `d.globalColorMap` にも影響を与えてしまう、という問題が発生していました。

## 技術的詳細

このバグは、`image/gif` パッケージのデコーダ (`decoder` 構造体) がGIF画像を読み込む際に、透過インデックスの処理方法に起因していました。

デコーダは、各画像ブロック（フレーム）を処理する際に、そのフレームが使用するカラーパレットを決定します。
1.  画像ブロックがローカルカラーテーブル (LCT) を持っている場合、そのLCTをフレームのパレットとして使用します。
2.  画像ブロックがLCTを持たない場合、グローバルカラーテーブル (GCT) をフレームのパレットとして使用します。

問題は、2番目のケースで発生していました。フレームがLCTを持たずGCTを使用する場合、デコーダは `m.Palette = d.globalColorMap` のように、フレームのパレット (`m.Palette`) をグローバルカラーマップ (`d.globalColorMap`) に直接代入していました。前述の通り、Goのスライスは参照型であるため、これは `m.Palette` と `d.globalColorMap` が同じ基となる配列を指すことを意味します。

その後、もしそのフレームが透過インデックスを指定していた場合、デコーダは `m.Palette[d.transparentIndex] = color.RGBA{}` のように、透過インデックスに対応するパレットエントリを完全に透明な色に設定していました。この操作は、`m.Palette` を通じて行われるため、結果として `d.globalColorMap` の対応するエントリも変更されてしまっていました。

これにより、一度透過インデックスが設定されたグローバルパレットは、その後のフレームで透過インデックスが使用されなくても、その色が透過として扱われるか、あるいは本来の色情報が失われた状態で表示されることになり、アニメーションの表示に不整合が生じていました。

修正の核心は、フレームがLCTを持たずGCTを使用する場合に、`d.globalColorMap` を直接参照するのではなく、その**コピー**を作成して `m.Palette` に割り当てることです。これにより、フレームごとの透過インデックスによるパレットの変更が、そのフレームのパレットのコピーにのみ適用され、元のグローバルパレットには影響を与えなくなります。

## コアとなるコードの解説

変更された `reader.go` のコードについて詳しく見ていきます。

1.  **`useLocalColorMap` 変数の導入**:
    ```go
    -			if d.imageFields&fColorMapFollows != 0 {
    +			useLocalColorMap := d.imageFields&fColorMapFollows != 0
    +			if useLocalColorMap {
    ```
    以前は `d.imageFields&fColorMapFollows != 0` という条件が直接使われていましたが、これを `useLocalColorMap` というブール変数に格納するように変更されました。これはコードの可読性を向上させるとともに、後続のロジックでこのフラグを再利用できるようにするためです。`fColorMapFollows` は、画像記述子にローカルカラーテーブルが存在するかどうかを示すフラグです。

2.  **グローバルカラーマップのクローン処理**:
    ```go
    			m.Palette = d.globalColorMap
    			}
    			if d.hasTransparentIndex && int(d.transparentIndex) < len(m.Palette) {
    +				if !useLocalColorMap {
    +					// Clone the global color map.
    +					m.Palette = append(color.Palette(nil), d.globalColorMap...)
    +				}
    				m.Palette[d.transparentIndex] = color.RGBA{}
    			}
    ```
    この部分が修正の核心です。
    *   `if d.hasTransparentIndex && int(d.transparentIndex) < len(m.Palette)`: この条件は、現在のフレームが透過インデックスを持ち、かつそのインデックスがパレットの範囲内にある場合に真となります。つまり、透過色を適用する必要がある場合にこのブロックに入ります。
    *   `if !useLocalColorMap`: この内部条件が追加されました。これは、「現在のフレームがローカルカラーマップを使用していない場合」、すなわち「グローバルカラーマップを使用している場合」に真となります。
    *   `m.Palette = append(color.Palette(nil), d.globalColorMap...)`: これが最も重要な変更です。
        *   `color.Palette(nil)`: これは、新しい空の `color.Palette` 型のスライスを作成します。
        *   `append(..., d.globalColorMap...)`: `append` 関数は、最初の引数に指定されたスライスに、2番目以降の引数に指定された要素を追加し、新しいスライスを返します。ここでは、`d.globalColorMap` のすべての要素が新しい空のスライスに追加されます。結果として、`d.globalColorMap` の内容が完全にコピーされた新しいスライスが作成され、それが `m.Palette` に割り当てられます。
        *   この操作により、`m.Palette` は `d.globalColorMap` とは異なる、独立したメモリ領域を指すようになります。

この変更により、`m.Palette[d.transparentIndex] = color.RGBA{}` という行が実行されても、それは `m.Palette` のコピーに対して行われるため、元の `d.globalColorMap` は変更されません。これにより、透過インデックスによる副作用がグローバルパレットに及ぶことがなくなり、アニメーションGIFの正確な表示が保証されるようになりました。

`reader_test.go` に追加された `TestTransparentIndex` は、この修正が正しく機能することを確認するためのものです。複数のフレームを持ち、それぞれ異なる透過インデックスを使用するGIFを生成し、各フレームのデコード後にパレットが期待通りの状態になっているか（特にグローバルパレットが破壊されていないか）を検証しています。

## コアとなるコードの解説

変更された `reader.go` のコードについて詳しく見ていきます。

1.  **`useLocalColorMap` 変数の導入**:
    ```go
    -			if d.imageFields&fColorMapFollows != 0 {
    +			useLocalColorMap := d.imageFields&fColorMapFollows != 0
    +			if useLocalColorMap {
    ```
    以前は `d.imageFields&fColorMapFollows != 0` という条件が直接使われていましたが、これを `useLocalColorMap` というブール変数に格納するように変更されました。これはコードの可読性を向上させるとともに、後続のロジックでこのフラグを再利用できるようにするためです。`fColorMapFollows` は、画像記述子にローカルカラーテーブルが存在するかどうかを示すフラグです。

2.  **グローバルカラーマップのクローン処理**:
    ```go
    			m.Palette = d.globalColorMap
    			}
    			if d.hasTransparentIndex && int(d.transparentIndex) < len(m.Palette) {
    +				if !useLocalColorMap {
    +					// Clone the global color map.
    +					m.Palette = append(color.Palette(nil), d.globalColorMap...)
    +				}
    				m.Palette[d.transparentIndex] = color.RGBA{}
    			}
    ```
    この部分が修正の核心です。
    *   `if d.hasTransparentIndex && int(d.transparentIndex) < len(m.Palette)`: この条件は、現在のフレームが透過インデックスを持ち、かつそのインデックスがパレットの範囲内にある場合に真となります。つまり、透過色を適用する必要がある場合にこのブロックに入ります。
    *   `if !useLocalColorMap`: この内部条件が追加されました。これは、「現在のフレームがローカルカラーマップを使用していない場合」、すなわち「グローバルカラーマップを使用している場合」に真となります。
    *   `m.Palette = append(color.Palette(nil), d.globalColorMap...)`: これが最も重要な変更です。
        *   `color.Palette(nil)`: これは、新しい空の `color.Palette` 型のスライスを作成します。
        *   `append(..., d.globalColorMap...)`: `append` 関数は、最初の引数に指定されたスライスに、2番目以降の引数に指定された要素を追加し、新しいスライスを返します。ここでは、`d.globalColorMap` のすべての要素が新しい空のスライスに追加されます。結果として、`d.globalColorMap` の内容が完全にコピーされた新しいスライスが作成され、それが `m.Palette` に割り当てられます。
        *   この操作により、`m.Palette` は `d.globalColorMap` とは異なる、独立したメモリ領域を指すようになります。

この変更により、`m.Palette[d.transparentIndex] = color.RGBA{}` という行が実行されても、それは `m.Palette` のコピーに対して行われるため、元の `d.globalColorMap` は変更されません。これにより、透過インデックスによる副作用がグローバルパレットに及ぶことがなくなり、アニメーションGIFの正確な表示が保証されるようになりました。

`reader_test.go` に追加された `TestTransparentIndex` は、この修正が正しく機能することを確認するためのものです。複数のフレームを持ち、それぞれ異なる透過インデックスを使用するGIFを生成し、各フレームのデコード後にパレットが期待通りの状態になっているか（特にグローバルパレットが破壊されていないか）を検証しています。

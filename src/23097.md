# [インデックス 23097] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）制御変数の更新メカニズムを改善するものです。具体的には、GCサイクル中に定期的にGC制御変数を調整するために使用されていた、タイムアウト付きの`notetsleepg`ループを、より効率的なタイマーベースのメカニズムに置き換えています。これにより、GCの制御変数の改訂がより正確かつ効率的に行われるようになり、ランタイムのオーバーヘッドが削減されます。

## 元コミット内容

```
runtime: use timer for GC control revise rather than timeout

Currently, we use a note sleep with a timeout in a loop in func gc to
periodically revise the GC control variables. Replace this with a
fully blocking note sleep and use a periodic timer to trigger the
revise instead. This is a step toward replacing the note sleep in func
gc.
```

## 変更の背景

Goのガベージコレクションは、プログラムの実行中にメモリを自動的に管理する重要なコンポーネントです。GCの効率は、Goアプリケーションのパフォーマンスに直接影響します。このコミット以前は、GCサイクル中にGC制御変数を定期的に調整（`revise`）するために、`func gc`内で`notetsleepg`関数をタイムアウト付きでループさせていました。

このアプローチにはいくつかの問題がありました。

1.  **非効率性**: `notetsleepg`がタイムアウトするたびにループが再開され、GC制御変数の`revise`が実行されます。これは、指定された期間ごとにポーリングを行うようなもので、CPUサイクルを無駄にする可能性があります。特に、`revise`処理が頻繁に必要ない場合でも、定期的にスリープから復帰してチェックを行うため、オーバーヘッドが生じます。
2.  **将来的な改善への障壁**: コミットメッセージにもあるように、この`notetsleepg`の使用は`func gc`全体の置き換えに向けたステップの一部でした。より洗練されたGCスケジューリングや制御メカニズムを導入するためには、ポーリングベースの`notetsleepg`ループは柔軟性に欠け、よりイベント駆動型のアプローチが必要とされていました。

このコミットは、これらの問題を解決し、GC制御変数の改訂をより効率的かつ正確に行うための基盤を築くことを目的としています。タイムアウト付きのポーリングから、必要な時にのみ`revise`がトリガーされるタイマーベースのメカニズムへの移行は、ランタイムの効率向上に貢献します。

## 前提知識の解説

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するシステムです。これには、ガベージコレクタ、スケジューラ（ゴルーチンの管理）、メモリ割り当て、プリミティブな同期メカニズムなどが含まれます。Goプログラムは、オペレーティングシステム上で直接実行されるのではなく、Goランタイム上で実行されます。

### ガベージコレクション (Garbage Collection, GC)

ガベージコレクションは、プログラムが動的に割り当てたメモリのうち、もはや使用されていない（到達不能な）領域を自動的に解放するプロセスです。GoのGCは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行してGC処理を進めることで、アプリケーションの一時停止（Stop-the-World）時間を最小限に抑えるように設計されています。

### `gcControllerState`

`gcControllerState`は、Goランタイム内でガベージコレクションの動作を制御および監視するための状態を保持する構造体です。GCのトリガー条件、マークフェーズの進行状況、アシスト比率（アプリケーションがGCに協力する度合い）など、GCの様々な側面を管理します。

### `revise()` メソッド

`gcControllerState`構造体の`revise()`メソッドは、GCサイクル中にGC制御変数を調整する役割を担います。これには、GCアシスト比率の再計算などが含まれます。アシスト比率は、アプリケーションが新しいメモリを割り当てる際に、GCにどれだけ協力するか（例えば、GCマーク作業を実行するか）を決定する重要なパラメータです。この比率を動的に調整することで、GCの進行とアプリケーションのスループットのバランスを取ります。

### `notetsleepg()` 関数

`notetsleepg()`は、Goランタイム内部で使用される低レベルの同期プリミティブです。これは、特定の「ノート」（`Note`型）が`notewakeup`によって通知されるまで、または指定されたタイムアウト期間が経過するまで、現在のゴルーチンをスリープさせるために使用されます。タイムアウトが指定された場合、関数はタイムアウトしたかどうかを示すブール値を返します。このコミット以前は、GC制御変数の定期的な改訂のために、この関数のタイムアウト機能がポーリングメカニズムとして利用されていました。

### `timer` 構造体とタイマーメカニズム

Goランタイムには、時間ベースのイベントをスケジュールするための内部タイマーメカニズムがあります。`timer`構造体は、このメカニズムの一部であり、特定の関数を将来の指定された時間に実行するようにスケジュールするために使用されます。このメカニズムは、`addtimer`関数でタイマーを登録し、`deltimer`関数でタイマーをキャンセルすることで制御されます。`notetsleepg`のようなポーリングとは異なり、タイマーはイベント駆動型であり、指定された時間が経過するまでゴルーチンをブロックすることなく、効率的にイベントをトリガーできます。

### `_CacheLineSize`

`_CacheLineSize`は、CPUのキャッシュラインのサイズを示す定数です。構造体内でこの定数を使用してパディングを行うことで、異なるフィールドが異なるキャッシュラインに配置されるようにし、偽共有（false sharing）を防ぐことができます。偽共有は、複数のCPUコアが同じキャッシュライン上の異なるデータを同時に変更しようとすると発生し、パフォーマンスの低下を招く可能性があります。このコミットでは、`gcControllerState`構造体に`reviseTimer`が追加された際に、既存の`_CacheLineSize`によるパディングが維持されています。

## 技術的詳細

このコミットの主要な技術的変更点は、GC制御変数の`revise`処理のトリガー方法を、ポーリングベースの`notetsleepg`ループから、Goランタイムの内部タイマーメカニズムを利用したイベント駆動型のアプローチへと移行したことです。

### 変更前のアプローチ

変更前は、`func gc`内で以下のようなループが使用されていました。

```go
for !notetsleepg(&work.bgMarkNote, 10*1000*1000) {
    gcController.revise()
}
```

このコードは、`work.bgMarkNote`が通知されるか、または10ミリ秒（10 * 1000 * 1000ナノ秒）のタイムアウトが発生するまでスリープします。タイムアウトが発生した場合（`notetsleepg`が`false`を返す）、ループが継続し、`gcController.revise()`が呼び出されてGC制御変数が調整されます。これは、GCサイクル中に約10ミリ秒ごとに`revise`処理をポーリング実行するメカニズムでした。

### 変更後のアプローチ

新しいアプローチでは、`gcControllerState`構造体に`reviseTimer`という`timer`型のフィールドが追加されました。

1.  **`reviseTimer`の追加**:
    `gcControllerState`に`reviseTimer timer`フィールドが追加され、GC制御変数の定期的な改訂をスケジュールするためのタイマーが導入されました。

2.  **`startCycle()`でのタイマー設定**:
    GCサイクルが開始される`startCycle()`関数内で、`reviseTimer`が設定されます。
    *   `reviseTimer.f`には、タイマーがトリガーされたときに実行される関数（`gcController.revise()`を呼び出す匿名関数）が設定されます。
    *   `reviseTimer.period`には、タイマーの周期が10ミリ秒（10 * 1000 * 1000ナノ秒）に設定されます。これは、以前のポーリング間隔と同じです。
    *   `reviseTimer.when`には、タイマーが最初にトリガーされる時刻が設定されます（現在の時刻 + 周期）。
    *   `addtimer(&c.reviseTimer)`が呼び出され、このタイマーがランタイムのタイマーキューに追加され、スケジュールされます。

3.  **`endCycle()`でのタイマー停止**:
    GCサイクルが終了する`endCycle()`関数内で、`deltimer(&c.reviseTimer)`が呼び出され、`reviseTimer`がタイマーキューから削除され、停止されます。これにより、不要なタイマーイベントの発生を防ぎます。

4.  **`func gc`の変更**:
    `func gc`内の`notetsleepg`ループは、`notetsleepg(&work.bgMarkNote, -1)`という単一の呼び出しに置き換えられました。`-1`というタイムアウト値は、`work.bgMarkNote`が通知されるまで無期限に（または、Goランタイムの内部的な最大スリープ時間まで）ブロックすることを意味します。これにより、GC制御変数の`revise`はタイマーによってのみトリガーされるようになり、`func gc`内のポーリングループは不要になりました。

この変更により、GC制御変数の`revise`は、必要なときにのみタイマーによって正確にトリガーされるようになり、ポーリングによるCPUサイクルの無駄がなくなります。これは、ランタイムの効率を向上させ、将来的なGCスケジューリングの改善に向けた重要なステップとなります。

## 変更の背景

Goのガベージコレクションは、プログラムの実行中にメモリを自動的に管理する重要なコンポーネントです。GCの効率は、Goアプリケーションのパフォーマンスに直接影響します。このコミット以前は、GCサイクル中にGC制御変数を定期的に調整（`revise`）するために、`func gc`内で`notetsleepg`関数をタイムアウト付きでループさせていました。

このアプローチにはいくつかの問題がありました。

1.  **非効率性**: `notetsleepg`がタイムアウトするたびにループが再開され、GC制御変数の`revise`が実行されます。これは、指定された期間ごとにポーリングを行うようなもので、CPUサイクルを無駄にする可能性があります。特に、`revise`処理が頻繁に必要ない場合でも、定期的にスリープから復帰してチェックを行うため、オーバーヘッドが生じます。
2.  **将来的な改善への障壁**: コミットメッセージにもあるように、この`notetsleepg`の使用は`func gc`全体の置き換えに向けたステップの一部でした。より洗練されたGCスケジューリングや制御メカニズムを導入するためには、ポーリングベースの`notetsleepg`ループは柔軟性に欠け、よりイベント駆動型のアプローチが必要とされていました。

このコミットは、これらの問題を解決し、GC制御変数の改訂をより効率的かつ正確に行うための基盤を築くことを目的としています。タイムアウト付きのポーリングから、必要な時にのみ`revise`がトリガーされるタイマーベースのメカニズムへの移行は、ランタイムの効率向上に貢献します。特に、この変更はGo 1.5で導入されたGCの大きな改善（「Go's new GC: less latency, more throughput」）の一環であり、GCの「Stop-the-World」（STW）ポーズ時間を最小限に抑えるという目標に貢献しています。

## 前提知識の解説

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するシステムです。これには、ガベージコレクタ、スケジューラ（ゴルーチンの管理）、メモリ割り当て、プリミティブな同期メカニズムなどが含まれます。Goプログラムは、オペレーティングシステム上で直接実行されるのではなく、Goランタイム上で実行されます。

### ガベージコレクション (Garbage Collection, GC)

ガベージコレクションは、プログラムが動的に割り当てたメモリのうち、もはや使用されていない（到達不能な）領域を自動的に解放するプロセスです。GoのGCは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行してGC処理を進めることで、アプリケーションの一時停止（Stop-the-World）時間を最小限に抑えるように設計されています。Go 1.5以降、GCのレイテンシは大幅に改善され、ほとんどのSTWポーズはミリ秒単位に短縮されています。

### `gcControllerState`

`gcControllerState`は、Goランタイム内でガベージコレクションの動作を制御および監視するための状態を保持する構造体です。GCのトリガー条件、マークフェーズの進行状況、アシスト比率（アプリケーションがGCに協力する度合い）など、GCの様々な側面を管理します。

### `revise()` メソッド

`gcControllerState`構造体の`revise()`メソッドは、GCサイクル中にGC制御変数を調整する役割を担います。これには、GCアシスト比率の再計算などが含まれます。アシスト比率は、アプリケーションが新しいメモリを割り当てる際に、GCにどれだけ協力するか（例えば、GCマーク作業を実行するか）を決定する重要なパラメータです。この比率を動的に調整することで、GCの進行とアプリケーションのスループットのバランスを取ります。

### `notetsleepg()` 関数

`notetsleepg()`は、Goランタイム内部で使用される低レベルの同期プリミティブです。これは、特定の「ノート」（`Note`型）が`notewakeup`によって通知されるまで、または指定されたタイムアウト期間が経過するまで、現在のゴルーチンをスリープさせるために使用されます。タイムアウトが指定された場合、関数はタイムアウトしたかどうかを示すブール値を返します。このコミット以前は、GC制御変数の定期的な改訂のために、この関数のタイムアウト機能がポーリングメカニズムとして利用されていました。Goランタイムのタイマーメカニズム内部でも、`timerproc`ゴルーチンが次のタイマーイベントまでスリープするために`notetsleepg`が使用されています。

### `timer` 構造体とタイマーメカニズム

Goランタイムには、時間ベースのイベントをスケジュールするための内部タイマーメカニズムがあります。`runtime.timer`（または`timer`）構造体は、このメカニズムの一部であり、特定の関数を将来の指定された時間に実行するようにスケジュールするために使用されます。この構造体には、タイマーがトリガーされるべき正確なナノ秒時刻を示す`when`フィールド、タイマーが期限切れになったときに実行されるコールバック関数へのポインタである`f`フィールド、およびコールバック関数に渡される引数である`arg`フィールドが含まれます。このメカニズムは、`addtimer`関数でタイマーをランタイムのタイマーキューに登録し、`deltimer`関数でタイマーをキャンセルすることで制御されます。`notetsleepg`のようなポーリングとは異なり、タイマーはイベント駆動型であり、指定された時間が経過するまでゴルーチンをブロックすることなく、効率的にイベントをトリガーできます。Goのタイマーは、通常、最小ヒープデータ構造に格納され、効率的な管理のためにプロセッサごとに（P-local heaps）分散されることがあります。

### `_CacheLineSize`

`_CacheLineSize`は、CPUのキャッシュラインのサイズを示す定数です。構造体内でこの定数を使用してパディングを行うことで、異なるフィールドが異なるキャッシュラインに配置されるようにし、偽共有（false sharing）を防ぐことができます。偽共有は、複数のCPUコアが同じキャッシュライン上の異なるデータを同時に変更しようとすると発生し、パフォーマンスの低下を招く可能性があります。このコミットでは、`gcControllerState`構造体に`reviseTimer`が追加された際に、既存の`_CacheLineSize`によるパディングが維持されています。

## 技術的詳細

このコミットの主要な技術的変更点は、GC制御変数の`revise`処理のトリガー方法を、ポーリングベースの`notetsleepg`ループから、Goランタイムの内部タイマーメカニズムを利用したイベント駆動型のアプローチへと移行したことです。

### 変更前のアプローチ

変更前は、`func gc`内で以下のようなループが使用されていました。

```go
for !notetsleepg(&work.bgMarkNote, 10*1000*1000) {
    gcController.revise()
}
```

このコードは、`work.bgMarkNote`が通知されるか、または10ミリ秒（10 * 1000 * 1000ナノ秒）のタイムアウトが発生するまでスリープします。タイムアウトが発生した場合（`notetsleepg`が`false`を返す）、ループが継続し、`gcController.revise()`が呼び出されてGC制御変数が調整されます。これは、GCサイクル中に約10ミリ秒ごとに`revise`処理をポーリング実行するメカニズムでした。このポーリングは、GCがアイドル状態であっても定期的にCPUを消費し、効率的ではありませんでした。

### 変更後のアプローチ

新しいアプローチでは、`gcControllerState`構造体に`reviseTimer`という`runtime.timer`型のフィールドが追加されました。

1.  **`reviseTimer`の追加**:
    `gcControllerState`に`reviseTimer timer`フィールドが追加され、GC制御変数の定期的な改訂をスケジュールするためのタイマーが導入されました。これにより、GC制御のロジックがより明確に分離され、管理しやすくなりました。

2.  **`startCycle()`でのタイマー設定**:
    GCサイクルが開始される`startCycle()`関数内で、`reviseTimer`が設定されます。
    *   `reviseTimer.f`には、タイマーがトリガーされたときに実行される関数が設定されます。この関数は、`gcController.revise()`を呼び出す匿名関数であり、GC制御変数の調整を行います。
    *   `reviseTimer.period`には、タイマーの周期が10ミリ秒（10 * 1000 * 1000ナノ秒）に設定されます。これは、以前のポーリング間隔と同じですが、ポーリングではなくイベントとしてトリガーされます。
    *   `reviseTimer.when`には、タイマーが最初にトリガーされる時刻が設定されます（現在の時刻 + 周期）。`nanotime()`は、Goランタイムが提供する単調増加する高精度な時間源であり、システム時刻の変更に影響されません。
    *   `addtimer(&c.reviseTimer)`が呼び出され、このタイマーがランタイムのタイマーキューに追加され、スケジュールされます。ランタイムのタイマーメカニズムは、効率的に多数のタイマーを管理し、最も近い期限のタイマーを優先的に処理します。

3.  **`endCycle()`でのタイマー停止**:
    GCサイクルが終了する`endCycle()`関数内で、`deltimer(&c.reviseTimer)`が呼び出され、`reviseTimer`がタイマーキューから削除され、停止されます。これにより、GCサイクルが終了した後も不要なタイマーイベントの発生を防ぎ、リソースの無駄遣いを避けます。

4.  **`func gc`の変更**:
    `func gc`内の`notetsleepg`ループは、`notetsleepg(&work.bgMarkNote, -1)`という単一の呼び出しに置き換えられました。`-1`というタイムアウト値は、`work.bgMarkNote`が通知されるまで無期限に（または、Goランタイムの内部的な最大スリープ時間まで）ブロックすることを意味します。これにより、GC制御変数の`revise`はタイマーによってのみトリガーされるようになり、`func gc`内のポーリングループは完全に排除されました。この変更により、`func gc`はGCのバックグラウンドマークフェーズが完了するまで効率的に待機できるようになりました。

この変更により、GC制御変数の改訂は、必要なときにのみタイマーによって正確にトリガーされるようになり、ポーリングによるCPUサイクルの無駄がなくなります。これは、ランタイムの効率を向上させ、将来的なGCスケジューリングの改善に向けた重要なステップとなります。特に、Go 1.5以降のGCの低レイテンシ化に貢献する、よりイベント駆動型で効率的なGC制御メカニズムへの移行を象徴する変更です。

## コアとなるコードの解説

### `src/runtime/mgc.go`

このファイルは、Goランタイムのガベージコレクション（GC）の主要なロジックを実装しています。

1.  **`gcControllerState`構造体への`reviseTimer`フィールドの追加**:
    ```go
    type gcControllerState struct {
        // ... 既存のフィールド ...
        // at the end of of each cycle.
        triggerRatio float64

        // reviseTimer is a timer that triggers periodic revision of
        // control variables during the cycle.
        reviseTimer timer

        _ [_CacheLineSize]byte
        // ... その他のフィールド ...
    }
    ```
    `gcControllerState`構造体に`reviseTimer`という`runtime.timer`型のフィールドが追加されました。このフィールドは、GCサイクル中にGC制御変数を定期的に改訂するためのタイマーインスタンスを保持します。コメントが追加され、その目的が明確にされています。`_CacheLineSize`によるパディングは、構造体のメモリレイアウトとキャッシュ効率を維持するために重要であり、偽共有を防ぐ役割があります。

2.  **`startCycle()`関数内の変更**:
    `startCycle()`は、新しいGCサイクルが開始されるときに呼び出されます。
    ```go
    func (c *gcControllerState) startCycle() {
        // ... 既存の初期化処理 ...

        // Compute initial values for controls that are updated
        // throughout the cycle.
        c.revise() // GCサイクル開始時の初期値計算のために、一度reviseが呼び出される

        // Set up a timer to revise periodically
        c.reviseTimer.f = func(interface{}, uintptr) {
            gcController.revise()
        } // reviseTimerがトリガーされたときに実行される関数を設定。gcController.revise()を呼び出す。
        c.reviseTimer.period = 10 * 1000 * 1000 // タイマーの周期を10ミリ秒（10,000,000ナノ秒）に設定
        c.reviseTimer.when = nanotime() + c.reviseTimer.period // タイマーが最初にトリガーされる時刻を設定
        addtimer(&c.reviseTimer) // 設定されたreviseTimerをGoランタイムのタイマーキューに追加し、スケジュールする
    }
    ```
    *   以前は、`startCycle`の冒頭で`c.revise()`が呼び出されていましたが、これはタイマー設定の直前に移動されました。これにより、タイマーが設定される前に一度`revise`を実行し、その後はタイマーによって定期的に実行されるというロジックが明確になります。
    *   タイマーの設定ロジックが追加されました。`reviseTimer.f`には、`gcController.revise()`を呼び出す匿名関数が割り当てられ、タイマーが期限切れになったときにこの関数が実行されます。`reviseTimer.period`は10ミリ秒に設定され、これは以前のポーリング間隔と同じです。`reviseTimer.when`は、`nanotime()`（単調増加する高精度な時間源）を使用して最初のトリガー時刻を設定します。最後に、`addtimer`関数によってこのタイマーがランタイムのタイマーシステムに登録されます。

3.  **`endCycle()`関数内の変更**:
    `endCycle()`は、GCサイクルが終了したときに呼び出されます。
    ```go
    func (c *gcControllerState) endCycle() {
        // ... 既存の終了処理 ...

        // Stop the revise timer
        deltimer(&c.reviseTimer) // GCサイクルが終了すると、reviseTimerをタイマーキューから削除し、停止する

        // ... その他の終了処理 ...
    }
    ```
    *   `deltimer(&c.reviseTimer)`が追加されました。GCサイクルが終了すると、この関数が呼び出され、`reviseTimer`がランタイムのタイマーキューから削除され、停止されます。これにより、GCサイクルが終了した後も不要な`revise`イベントがトリガーされるのを防ぎ、リソースの無駄遣いを避けます。

4.  **`gc()`関数内の変更**:
    `gc()`関数は、GoランタイムのGCのメインエントリポイントです。
    ```go
    func gc(mode int) {
        // ... 既存のGC開始処理 ...

        if debug.gctrace > 0 {
            tMark = nanotime()
        }
        // 以前のポーリングループを削除し、無期限のnotetsleepgに置き換え
        notetsleepg(&work.bgMarkNote, -1) // work.bgMarkNoteが通知されるまで、ゴルーチンを無期限にブロック
        noteclear(&work.bgMarkNote)

        // Begin mark termination.
        // ... その後のGC処理 ...
    }
    ```
    *   以前の`for !notetsleepg(&work.bgMarkNote, 10*1000*1000) { gcController.revise() }`というポーリングループが削除されました。
    *   代わりに、`notetsleepg(&work.bgMarkNote, -1)`が追加されました。これは、`work.bgMarkNote`が通知されるまで、またはランタイムがスリープを解除するまで、ゴルーチンを無期限にブロックすることを意味します。これにより、`gc`関数内の`revise`のポーリングが完全に排除され、`revise`は`reviseTimer`によってのみ制御されるようになります。この変更により、`func gc`はGCのバックグラウンドマークフェーズが完了するまで効率的に待機できるようになりました。

これらの変更により、GC制御変数の改訂メカニズムが、ポーリングベースからイベント駆動型のタイマーベースへと移行し、ランタイムの効率と応答性が向上しました。

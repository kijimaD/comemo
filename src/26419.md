# [インデックス 26419] ファイルの概要

このコミットは、NetBSD/amd64環境におけるGoランタイムのシグナルハンドリングに関するバグ修正です。具体的には、シグナルハンドラからカーネルへ復帰する際に使用される`setcontext`システムコールが期待するレジスタ`r15`の値が、Goランタイムの`sigtramp`（シグナル処理の入り口となるコード）で正しく保持されない問題を解決します。この修正により、`r15`レジスタの値をスタックに一時的に保存し、シグナルハンドラ処理後に復元することで、NetBSDのシグナル処理メカニズムとの互換性を確保しています。

## 変更の背景

この変更は、NetBSDオペレーティングシステム上でGoプログラムがシグナルを処理する際の潜在的な問題を解決するために行われました。NetBSDでは、シグナルハンドラが実行された後、カーネルに制御を戻すために`setcontext`システムコールが使用されます。この`setcontext`システムコールは、シグナルハンドラに渡されたコンテキスト情報（CPUレジスタの状態など）を復元するために、特定のレジスタ（`r15`）にそのコンテキストのアドレスが格納されていることを期待します。

NetBSDの標準Cライブラリ（libc）では、シグナルハンドラが呼び出される際に`r15`レジスタの値が保存され、ハンドラからの復帰時に復元されるため、このメカニズムは問題なく機能します。しかし、Goランタイムのシグナル処理コード（特に`runtime·sigtramp`）では、`r15`レジスタがシグナルハンドラの呼び出しをまたいで保存される保証がありませんでした。

この非互換性により、GoプログラムがNetBSD上でシグナルを受信し、そのハンドラが実行された後に`setcontext`を呼び出すと、`r15`レジスタに誤った値が格納されている可能性があり、結果としてプログラムのクラッシュや予期せぬ動作を引き起こす可能性がありました。このコミットは、この問題を解決し、GoランタイムがNetBSDのシグナル処理規約に正しく準拠するようにするためのものです。

## 前提知識の解説

### シグナルハンドリング

シグナルは、Unix系OSにおいてプロセスに対して非同期に通知されるイベントです。例えば、Ctrl+Cによる割り込み（SIGINT）、不正なメモリアクセス（SIGSEGV）、子プロセスの終了（SIGCHLD）などがあります。プロセスはこれらのシグナルを受信すると、デフォルトの動作（プロセス終了など）を実行するか、事前に登録されたシグナルハンドラ関数を実行します。

### シグナルスタックとシグナルフレーム

シグナルハンドラが呼び出される際、通常の実行スタックとは異なる「シグナルスタック」が使用されることがあります。これは、シグナルが任意のタイミングで発生する可能性があり、通常のスタックが破損している場合でもシグナルハンドラが安全に実行できるようにするためです。シグナルハンドラが呼び出される直前には、現在のプロセスの状態（レジスタの値、プログラムカウンタなど）が「シグナルフレーム」と呼ばれるデータ構造に保存されます。シグナルハンドラはこのシグナルフレームを通じて、シグナル発生時のプロセスのコンテキストにアクセスできます。

### `sigtramp` (シグナルトランポリン)

`sigtramp`は「シグナルトランポリン」の略で、カーネルからユーザー空間のシグナルハンドラへ制御を移し、シグナルハンドラが終了した後にカーネルへ制御を戻すための、アセンブリ言語で書かれた小さなコード片です。シグナルが発生すると、カーネルは直接ユーザー定義のシグナルハンドラを呼び出すのではなく、まず`sigtramp`を呼び出します。`sigtramp`は、シグナルハンドラが必要とする引数（シグナル番号、シグナル情報、コンテキスト情報など）をスタックに設定し、ユーザー定義のシグナルハンドラを呼び出します。シグナルハンドラが終了すると、`sigtramp`は`setcontext`のようなシステムコールを呼び出して、シグナル発生前のプロセスの状態を復元し、通常の実行フローに戻ります。

### `setcontext` / `getcontext` システムコール

`getcontext`と`setcontext`は、プロセスの実行コンテキスト（CPUレジスタ、シグナルマスク、スタックポインタなど）を保存・復元するためのシステムコールです。
- `getcontext(ucontext_t *ucp)`: 現在の実行コンテキストを`ucp`が指す`ucontext_t`構造体に保存します。
- `setcontext(const ucontext_t *ucp)`: `ucp`が指す`ucontext_t`構造体に保存されたコンテキストを復元し、そのコンテキストから実行を再開します。これは、`longjmp`に似ていますが、より広範なコンテキストを扱います。NetBSDでは、シグナルハンドラからの復帰にこの`setcontext`が利用されます。

### `amd64`アーキテクチャとレジスタ規約

`amd64`（x86-64）アーキテクチャでは、多数の汎用レジスタが利用可能です。関数呼び出し規約（calling convention）は、関数間で引数をどのように渡し、どのレジスタを呼び出し側が保存し、どのレジスタを呼び出された側が保存するかを定めます。
- **呼び出し側保存レジスタ (Caller-saved registers)**: `rax`, `rcx`, `rdx`, `rsi`, `rdi`, `r8`-`r11`。これらは関数呼び出しによって変更される可能性があるため、呼び出し側が必要な場合は事前に保存する必要があります。
- **呼び出された側保存レジスタ (Callee-saved registers)**: `rbx`, `rbp`, `r12`-`r15`。これらは関数呼び出しによって変更されてはならず、呼び出された関数がこれらを使用する場合は、事前に保存し、関数終了時に復元する必要があります。

NetBSDの`setcontext`システムコールが`r15`にコンテキストアドレスを期待するという事実は、NetBSDの特定のABI（Application Binary Interface）または内部実装の詳細に起因します。`r15`は通常、呼び出された側保存レジスタであるため、Goランタイムの`sigtramp`が`runtime·sigtrampgo`を呼び出す際に`r15`が変更されてしまうと問題が発生します。

### Goランタイムのアセンブリコード

Go言語のランタイムは、OSとの低レベルなやり取りやパフォーマンスが重要な部分でアセンブリ言語を使用します。`src/runtime/sys_netbsd_amd64.s`のようなファイルは、NetBSD/amd64環境に特化したシステムコールラッパーやシグナル処理のコードを含んでいます。GoのアセンブリはPlan 9アセンブリの記法に似ており、一般的なGAS（GNU Assembler）記法とは異なります。

## 技術的詳細

問題の核心は、NetBSDのシグナル処理メカニズムとGoランタイムの`sigtramp`実装との間の`r15`レジスタの扱いの不一致にありました。

1.  **NetBSDの期待**: NetBSDでは、シグナルハンドラが`setcontext`システムコールを呼び出して元のコンテキストに復帰する際、復元すべきコンテキストのアドレスが`r15`レジスタに格納されていることを期待します。NetBSDのlibcの`sigtramp`は、この`r15`レジスタの値をシグナルハンドラの呼び出しをまたいで保存・復元します。
2.  **Goランタイムの挙動**: Goランタイムの`runtime·sigtramp`は、実際のGo言語で書かれたシグナルハンドラ本体である`runtime·sigtrampgo`関数を呼び出します。この`runtime·sigtrampgo`の呼び出しにおいて、Goの関数呼び出し規約では`r15`レジスタが呼び出しをまたいで保存される保証がありませんでした。つまり、`runtime·sigtrampgo`が`r15`を自由に変更してしまう可能性があり、その結果、`sigtramp`が`setcontext`を呼び出す際に`r15`に誤ったコンテキストアドレスが格納されてしまう事態が発生していました。

このコミットによる解決策は、NetBSDのlibcが採用しているアプローチと同様に、`runtime·sigtramp`内で`runtime·sigtrampgo`を呼び出す前後に`r15`レジスタの値を明示的に保存・復元することです。

具体的には、
-   `runtime·sigtramp`のスタックフレームサイズを拡張し、`r15`の値を一時的に保存する領域を確保します。
-   `runtime·sigtrampgo`を呼び出す直前に、現在の`r15`の値をスタックに保存します。
-   `runtime·sigtrampgo`から戻ってきた直後に、スタックに保存しておいた`r15`の値をレジスタに復元します。

これにより、`runtime·sigtrampgo`が`r15`レジスタをどのように使用しても、`sigtramp`が`setcontext`を呼び出す際には常に正しいコンテキストアドレスが`r15`に保持されるようになります。

コミットメッセージでは、`386`および`arm`アーキテクチャについても言及していますが、それらのアーキテクチャでは同様の問題が発生しないか、あるいは既に適切な処理がなされている可能性が示唆されています。しかし、このコミットの時点では`amd64`のみが修正対象であり、他のアーキテクチャについては未検証であると述べられています。

## コアとなるコードの解説

変更は`src/runtime/sys_netbsd_amd64.s`ファイル内の`runtime·sigtramp`関数に集中しています。

1.  **スタックフレームサイズの変更**:
    ```diff
    -TEXT runtime·sigtramp(SB),NOSPLIT,$24
    +TEXT runtime·sigtramp(SB),NOSPLIT,$32
    ```
    `TEXT runtime·sigtramp(SB),NOSPLIT,$24`から`TEXT runtime·sigtramp(SB),NOSPLIT,$32`に変更されています。
    -   `TEXT runtime·sigtramp(SB)`: `runtime·sigtramp`という名前の関数を定義しています。`SB`はStatic Baseで、グローバルシンボルであることを示します。
    -   `NOSPLIT`: この関数はスタックを拡張しないことを示します。
    -   `$24`から`$32`: これは、この関数が使用するスタックフレームのサイズ（ローカル変数や保存レジスタのために確保するスタック領域のバイト数）を示します。元の`$24`は、`DI`, `SI`, `DX`の3つのレジスタ（それぞれ8バイト）をスタックに保存するために十分なサイズでした（`0(SP)`, `8(SP)`, `16(SP)`）。新しい`$32`は、さらに`r15`レジスタ（8バイト）を保存するための領域（`24(SP)`）を確保するために必要です。

2.  **`r15`レジスタの保存**:
    ```diff
    +\tMOVQ\tR15, 24(SP) // for sigreturn
    ```
    `CALL runtime·sigtrampgo(SB)`の直前に追加された行です。
    -   `MOVQ R15, 24(SP)`: `r15`レジスタの64ビット値（Quadword）を、現在のスタックポインタ`SP`から24バイトオフセットしたアドレスに保存します。これは、`runtime·sigtrampgo`が`r15`を破壊する可能性に備えて、その値を一時的にスタックに退避させていることを意味します。コメント`// for sigreturn`は、この値が`setcontext`（NetBSDでは`sigreturn`システムコールの一部として`setcontext`が使われる）のために必要であることを示唆しています。

3.  **`r15`レジスタの復元**:
    ```diff
    +\tMOVQ\t24(SP), R15
    ```
    `CALL runtime·sigtrampgo(SB)`の直後、`RET`命令の直前に追加された行です。
    -   `MOVQ 24(SP), R15`: スタックポインタ`SP`から24バイトオフセットしたアドレスに保存されていた64ビット値（以前に退避させた`r15`の値）を`r15`レジスタに復元します。これにより、`runtime·sigtrampgo`が`r15`を変更していたとしても、`sigtramp`関数が終了して`setcontext`が呼び出される際には、元の正しいコンテキストアドレスが`r15`に格納されていることが保証されます。

これらの変更により、Goランタイムの`sigtramp`はNetBSDのシグナル処理規約に適合し、`setcontext`システムコールが期待する`r15`レジスタの値を正しく提供できるようになります。

## 変更の背景

このコミットの背景には、Go言語の`net/http`パッケージにおけるHTTPプロトコルバージョンの扱いに関するドキュメントの曖昧さがありました。特に、`http.Request`構造体の`Proto`フィールドの説明と、`http.Transport`が使用するプロトコルに関する記述が対象です。

1.  **「デフォルトで」という表現の削除**: 以前のドキュメントでは、クライアントリクエストにおけるHTTPプロトコルバージョンについて「デフォルトでHTTP/1.1またはHTTP/2.0を使用する」という記述がありました。しかし、実際にはユーザーがこの挙動をオーバーライドする手段は提供されておらず、常にトランスポート層がサーバーのサポート状況に応じて最適なプロトコル（HTTP/1.1またはHTTP/2）を自動的に選択していました。このため、「デフォルトで」という表現は誤解を招く可能性があり、実態に合わせて削除されました。
2.  **HTTP/2.0からHTTP/2への表記変更**: 当時、HTTP/2プロトコルは比較的新しく、その表記には「HTTP/2.0」と「HTTP/2」の両方が混在していました。しかし、公式な仕様やコミュニティでの慣習として「HTTP/2」が標準的な表記として確立されつつありました。このコミットは、ドキュメントを最新の標準に合わせて「HTTP/2」に統一することを目的としています。
3.  **Issue #13985への対応**: コミットメッセージにある`Fixes #13985 harder`という記述から、この変更が既存の課題（Issue #13985）に対するより徹底した修正であることが示唆されます。この課題は、おそらく`net/http`パッケージのHTTPプロトコルバージョンに関するドキュメントの不明瞭さや誤解を招く表現に関連していたと考えられます。

これらの変更は、`net/http`パッケージのドキュメントの正確性と明確性を向上させ、開発者がHTTPプロトコルの挙動をより正確に理解できるようにすることを目的としています。

## 前提知識の解説

### Go言語の`net/http`パッケージ

`net/http`パッケージは、Go言語でHTTPクライアントおよびサーバーを実装するための標準ライブラリです。このパッケージは、HTTP/1.1およびHTTP/2プロトコルをサポートし、リクエストの送信、レスポンスの受信、ルーティング、ミドルウェアの適用など、HTTP通信に必要な基本的な機能を提供します。Go言語のWeb開発において中心的な役割を果たすパッケージです。

### HTTP/1.1とHTTP/2

*   **HTTP/1.1**: 1999年に標準化されたHTTPプロトコルの主要バージョンです。テキストベースのヘッダー、リクエストごとに新しいTCP接続を確立する（またはKeep-Aliveで再利用する）、ヘッドオブラインブロッキングなどの特徴があります。
*   **HTTP/2**: 2015年に標準化されたHTTPプロトコルのメジャーアップデートです。SPDYプロトコルをベースにしており、パフォーマンス向上を目的としています。主な特徴は以下の通りです。
    *   **バイナリフレーミング層**: テキストではなくバイナリ形式でデータを送受信するため、パース効率が向上します。
    *   **多重化（Multiplexing）**: 単一のTCP接続上で複数のリクエストとレスポンスを並行して送受信できます。これにより、ヘッドオブラインブロッキングの問題が解消されます。
    *   **ヘッダー圧縮（HPACK）**: 重複するヘッダーを効率的に圧縮し、帯域幅の使用量を削減します。
    *   **サーバープッシュ**: クライアントがリクエストする前に、サーバーが関連するリソースをプッシュできます。

Goの`net/http`パッケージは、クライアント側ではサーバーがHTTP/2をサポートしている場合に自動的にHTTP/2を使用しようとします。サーバー側でもHTTP/2をサポートしており、設定なしで利用可能です。

### `http.Request.Proto`フィールド

`http.Request`構造体は、受信したHTTPリクエストまたは送信するHTTPリクエストを表します。その中の`Proto`、`ProtoMajor`、`ProtoMinor`フィールドは、リクエストが使用しているHTTPプロトコルのバージョンを示します。

*   `Proto`: プロトコルバージョンを表す文字列（例: "HTTP/1.0", "HTTP/1.1", "HTTP/2.0"）。
*   `ProtoMajor`: プロトコルのメジャーバージョン番号（例: 1, 2）。
*   `ProtoMinor`: プロトコルのマイナーバージョン番号（例: 0, 1）。

これらのフィールドは、主にサーバー側で受信したリクエストのプロトコルバージョンを識別するために使用されます。クライアント側でリクエストを構築する際には、これらのフィールドを設定しても`net/http`トランスポートによって無視され、実際の通信プロトコルはトランスポート層が決定します。

### `http.Transport`

`http.Transport`は、HTTPクライアントが実際にネットワーク経由でリクエストを送信し、レスポンスを受信する際の低レベルな実装を提供します。TCP接続の確立、TLSハンドシェイク、HTTPプロトコルのネゴシエーション（HTTP/1.1またはHTTP/2の選択）、接続の再利用（コネクションプーリング）などを担当します。`http.Client`は、この`http.Transport`を利用してHTTP通信を行います。

### `src/net/http/request.go`の変更点

`http.Request`構造体の`Proto`フィールドに関するコメントが修正されました。

変更前:
```go
// The protocol version for incoming server requests.
//
// For client requests these fields are ignored. The HTTP
// transport code uses either HTTP/1.1 or HTTP/2.0 by default,
// depending on what the server supports.
Proto      string // "HTTP/1.0"
ProtoMajor int    // 1
ProtoMinor int    // 0
```

変更後:
```go
// The protocol version for incoming server requests.
//
// For client requests these fields are ignored. The HTTP
// client code always uses either HTTP/1.1 or HTTP/2.
// See the docs on Transport for details.
Proto      string // "HTTP/1.0"
ProtoMajor int    // 1
ProtoMinor int    // 0
```

主な変更点は以下の通りです。
*   `"by default"`（デフォルトで）という表現が削除されました。これは、クライアントがプロトコル選択を明示的に制御する手段がなく、トランスポート層が常に自動的に最適なプロトコルを選択するため、この表現が誤解を招くことを避けるためです。
*   `"HTTP/2.0"`が`"HTTP/2"`に修正されました。これは、HTTP/2プロトコルの公式な表記に合わせたものです。
*   `"transport code"`（トランスポートコード）が`"client code"`（クライアントコード）に変更され、さらに詳細については`Transport`のドキュメントを参照するように促す記述が追加されました。これにより、プロトコル選択のロジックが`http.Transport`に集約されていることがより明確になります。

### `src/net/http/transport.go`の変更点

`http.Transport`構造体に関するコメントに、プロトコル選択の挙動に関する詳細が追記されました。

変更前:
```go
//
// A Transport is a low-level primitive for making HTTP and HTTPS requests.
// For high-level functionality, such as cookies and redirects, see Client.
type Transport struct {
	idleMu     sync.Mutex
	wantIdle   bool // user has requested to close all idle conns
```

変更後:
```go
//
// A Transport is a low-level primitive for making HTTP and HTTPS requests.
// For high-level functionality, such as cookies and redirects, see Client.
//
// Transport uses HTTP/1.1 for HTTP URLs and either HTTP/1.1 or HTTP/2
// for HTTPS URLs, depending on whether the server supports HTTP/2.
// See the package docs for more about HTTP/2.
type Transport struct {
	idleMu     sync.Mutex
	wantIdle   bool // user has requested to close all idle conns
```

追加された記述は以下の点を明確にしています。
*   HTTP URLに対しては常にHTTP/1.1を使用すること。
*   HTTPS URLに対しては、サーバーがHTTP/2をサポートしているかどうかに応じて、HTTP/1.1またはHTTP/2のいずれかを使用すること。
*   HTTP/2に関する詳細については、パッケージ全体のドキュメントを参照するように促しています。

これにより、`http.Transport`がどのようにHTTPプロトコルバージョンをネゴシエートするかのルールが明確になり、開発者がクライアントの挙動をより正確に予測できるようになります。

このコミットは、コードの動作を変更するものではなく、既存の動作に関するドキュメントの記述をより正確かつ最新のものに更新することが目的です。

### `src/net/http/request.go`の変更点

`http.Request`構造体の`Proto`フィールドに関するコメントが修正されました。

変更前:
```go
// The protocol version for incoming server requests.
//
// For client requests these fields are ignored. The HTTP
// transport code uses either HTTP/1.1 or HTTP/2.0 by default,
// depending on what the server supports.
Proto      string // "HTTP/1.0"
ProtoMajor int    // 1
ProtoMinor int    // 0
```

変更後:
```go
// The protocol version for incoming server requests.
//
// For client requests these fields are ignored. The HTTP
// client code always uses either HTTP/1.1 or HTTP/2.
// See the docs on Transport for details.
Proto      string // "HTTP/1.0"
ProtoMajor int    // 1
ProtoMinor int    // 0
```

主な変更点は以下の通りです。
*   `"by default"`（デフォルトで）という表現が削除されました。これは、クライアントがプロトコル選択を明示的に制御する手段がなく、トランスポート層が常に自動的に最適なプロトコルを選択するため、この表現が誤解を招くことを避けるためです。
*   `"HTTP/2.0"`が`"HTTP/2"`に修正されました。これは、HTTP/2プロトコルの公式な表記に合わせたものです。
*   `"transport code"`（トランスポートコード）が`"client code"`（クライアントコード）に変更され、さらに詳細については`Transport`のドキュメントを参照するように促す記述が追加されました。これにより、プロトコル選択のロジックが`http.Transport`に集約されていることがより明確になります。

### `src/net/http/transport.go`の変更点

`http.Transport`構造体に関するコメントに、プロトコル選択の挙動に関する詳細が追記されました。

変更前:
```go
//
// A Transport is a low-level primitive for making HTTP and HTTPS requests.
// For high-level functionality, such as cookies and redirects, see Client.
type Transport struct {
	idleMu     sync.Mutex
	wantIdle   bool // user has requested to close all idle conns
```

変更後:
```go
//
// A Transport is a low-level primitive for making HTTP and HTTPS requests.
// For high-level functionality, such as cookies and redirects, see Client.
//
// Transport uses HTTP/1.1 for HTTP URLs and either HTTP/1.1 or HTTP/2
// for HTTPS URLs, depending on whether the server supports HTTP/2.
// See the package docs for more about HTTP/2.
type Transport struct {
	idleMu     sync.Mutex
	wantIdle   bool // user has requested to close all idle conns
```

追加された記述は以下の点を明確にしています。
*   HTTP URLに対しては常にHTTP/1.1を使用すること。
*   HTTPS URLに対しては、サーバーがHTTP/2をサポートしているかどうかに応じて、HTTP/1.1またはHTTP/2のいずれかを使用すること。
*   HTTP/2に関する詳細については、パッケージ全体のドキュメントを参照するように促しています。

これにより、`http.Transport`がどのようにHTTPプロトコルバージョンをネゴシエートするかのルールが明確になり、開発者がクライアントの挙動をより正確に予測できるようになります。

## コアとなるコードの解説

### `src/net/http/request.go`の変更解説

この変更は、`http.Request`構造体の`Proto`フィールドに関するコメントを、クライアントリクエストのプロトコル選択の現実的な挙動に合わせて修正したものです。

*   `"by default"`の削除は、ユーザーがプロトコル選択を直接制御できないという事実を反映しています。Goの`net/http`クライアントは、サーバーの能力に基づいて自動的に最適なプロトコルを選択するため、ユーザーが「デフォルト」を変更するオプションは存在しません。
*   `"HTTP/2.0"`から`"HTTP/2"`への変更は、プロトコル名の標準化と一貫性を保つためのものです。
*   `"transport code"`から`"client code"`への変更、および`Transport`のドキュメントへの参照追加は、プロトコルネゴシエーションの責任が`http.Transport`にあることを明確にし、開発者がより詳細な情報をどこで探すべきかを示しています。これにより、`http.Request`のドキュメントが簡潔になり、実際のプロトコルハンドリングのロジックが`http.Transport`のドキュメントに集約されるという、ドキュメント構造の改善にも寄与しています。

### `src/net/http/transport.go`の変更解説

この変更は、`http.Transport`のドキュメントに、HTTPプロトコル選択の具体的なロジックを追加したものです。

*   HTTP URLに対しては常にHTTP/1.1が使用されるという明確な記述は、開発者が非HTTPS通信におけるプロトコル挙動を正確に理解するのに役立ちます。
*   HTTPS URLに対しては、サーバーがHTTP/2をサポートしている場合にHTTP/2が使用されるという記述は、Goクライアントが自動的にHTTP/2の利点を活用しようとすることを示しています。これは、現代のWebアプリケーションにおいてパフォーマンスが重要視される中で、Goが提供する重要な機能の一つです。
*   `See the package docs for more about HTTP/2.`という記述は、HTTP/2のより広範な情報や設定オプションについて、パッケージ全体のドキュメントを参照するよう促しています。これにより、`http.Transport`のドキュメントがその役割に特化しつつ、関連情報への導線も提供されています。

これらの変更は、Goの`net/http`パッケージが提供するHTTPプロトコルハンドリングの挙動について、開発者により正確で詳細な情報を提供し、誤解を減らすことを目的としています。

## 変更の背景

このコミットの背景には、Goランタイムの`Compare-and-Swap (CAS)`操作が、特に大きな符号なし32ビット整数を扱う際に、予期せぬ「符号拡張 (sign-extension)」によって誤動作する可能性への懸念があります。

CASは、マルチスレッド環境で共有データへのアトミックな更新を行うための重要なプリミティブです。しかし、異なるビット幅のレジスタ間で値を移動する際や、特定のアーキテクチャ（このコミットメッセージでは`dev.power64`とあるため、PowerPC 64ビットアーキテクチャが関連している可能性が高い）において、32ビットの符号なし値が64ビットのレジスタにロードされる際に、上位ビットが符号ビットで埋められてしまう「符号拡張」が発生することがあります。

例えば、符号なし32ビット値 `0xFFFFFFFF` (十進数で4,294,967,295) は、符号付き32ビット値としては `-1` と解釈されます。これが64ビットレジスタに符号拡張されると、`0xFFFFFFFFFFFFFFFF` (符号付き64ビット値としては `-1`) となります。もしCAS操作がこの符号拡張された値で比較を行ってしまうと、本来意図した値 `0xFFFFFFFF` との比較が正しく行われず、アトミック操作が失敗したり、不正な状態になったりする可能性があります。

このコミットは、このような潜在的なバグを防ぐために、`runtime·check`というランタイムの自己テスト機能に、この特定のケースを検証するテストを追加することで、Goランタイムの堅牢性を高めることを目的としています。

## 前提知識の解説

### 1. Compare-and-Swap (CAS)

CASは、並行プログラミングにおいて共有メモリ上の値をアトミックに更新するための基本的な操作です。以下の3つの引数を取ります。

*   **メモリ上のアドレス (A)**: 更新対象の変数のアドレス。
*   **期待値 (E)**: メモリ上のアドレスAに現在格納されていると期待される値。
*   **新値 (N)**: もし期待値EがアドレスAに格納されていれば、その代わりに書き込む新しい値。

CAS操作は、以下のステップをアトミック（不可分）に実行します。

1.  アドレスAの現在の値を読み取る。
2.  読み取った値が期待値Eと一致するかどうかを比較する。
3.  もし一致すれば、アドレスAの値を新値Nに更新する。
4.  操作が成功したかどうか（期待値と一致し、更新が行われたか）を示すブール値を返す。

このアトミック性により、複数のスレッドが同時に同じメモリ位置を更新しようとしても、データ競合を防ぎ、一貫性を保つことができます。

### 2. 符号拡張 (Sign Extension)

符号拡張は、あるビット幅の数値を、より大きなビット幅の表現に変換する際に発生する現象です。特に、符号付き整数を扱う場合に重要になります。

*   **符号付き整数**: 最上位ビット (MSB) が数値の符号（0は正、1は負）を表します。
*   **符号なし整数**: 全てのビットが数値の大きさを表し、符号ビットはありません。

符号付き整数をより大きなビット幅に拡張する場合、元の数値の符号を維持するために、新しい上位ビットは元の数値の最上位ビット（符号ビット）と同じ値で埋められます。例えば、8ビットの符号付き整数 `0b10000000` (-128) を16ビットに拡張すると、`0b1111111110000000` となります。

一方、符号なし整数を拡張する場合、新しい上位ビットは単に0で埋められます。例えば、8ビットの符号なし整数 `0b10000000` (128) を16ビットに拡張すると、`0b0000000010000000` となります。

問題は、プログラミング言語やコンパイラ、または特定のCPUアーキテクチャが、符号なし32ビット値を64ビットレジスタにロードする際に、誤って符号付きとして扱い、符号拡張を行ってしまう場合に発生します。例えば、符号なし32ビット値 `0xFFFFFFFF` (十進数で4,294,967,295) は、符号付き32ビット値としては `-1` です。もしこれが符号拡張されると、64ビットレジスタでは `0xFFFFFFFFFFFFFFFF` (符号付き64ビット値で `-1`) となります。しかし、本来符号なしとして扱われるべきであれば、`0x00000000FFFFFFFF` となるべきです。CAS操作において、期待値と実際の値の比較がこの誤った符号拡張された値で行われると、比較が失敗し、アトミック操作が正しく行われなくなります。

### 3. Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理する低レベルのコンポーネントです。これには、ガベージコレクション、スケジューラ（ゴルーチンの管理）、メモリ割り当て、プリミティブな同期操作（CASなど）の実装が含まれます。ランタイムはGoプログラムとオペレーティングシステムやハードウェアの間の橋渡し役を果たし、Goの並行処理モデルやメモリ安全性を実現しています。

### 4. `runtime·check`

`runtime·check`は、Goランタイムの内部テスト関数です。Goランタイムの低レベルな機能（メモリ管理、アトミック操作、スケジューラなど）が正しく動作するかどうかを検証するために使用されます。これは、Goのビルドプロセスの一部として実行されることが多く、ランタイムの変更が既存の機能に悪影響を与えないことを保証するための重要なセーフティネットです。

## 技術的詳細

このコミットは、`src/runtime/runtime.c`ファイル内の`runtime·check`関数に新しいテストケースを追加することで、符号なし32ビット数のCAS操作の正確性を検証します。

追加されたテストは以下のシナリオをカバーします。

1.  **初期値の設定**: `z`という変数を符号なし32ビットの最大値である `0xffffffff` (4,294,967,295) で初期化します。
2.  **CAS操作の実行**: `runtime·cas(&z, 0xffffffff, 0xfffffffe)` を呼び出します。
    *   `&z`: `z`変数のアドレス。
    *   `0xffffffff`: 期待値。`z`の現在の値がこれと一致することを期待します。
    *   `0xfffffffe`: 新値。もし期待値と一致すれば、`z`をこの値に更新します。
3.  **CAS操作の成功検証**: `!runtime·cas(...)` の結果をチェックします。`runtime·cas`は成功した場合に`true`を返すため、`!`が付いているということは、CASが失敗した場合に`runtime·throw("cas5")`が呼び出されることを意味します。つまり、CAS操作が期待通りに成功することを検証しています。
4.  **更新後の値の検証**: `z != 0xfffffffe` の結果をチェックします。CAS操作が成功した場合、`z`の値は`0xfffffffe`に更新されているはずです。もし更新されていなければ、`runtime·throw("cas6")`が呼び出されます。これにより、CAS操作が値を正しく更新したことを検証しています。

このテストケースは、`0xffffffff`という値が、符号付きとして扱われた場合に`-1`となるため、符号拡張のバグが最も顕著に現れる可能性のあるエッジケースを狙っています。もしCASの実装が符号拡張を考慮せずに比較を行っていた場合、`0xffffffff`が内部的に`0xFFFFFFFFFFFFFFFF`（64ビットの-1）として扱われ、期待値との比較が失敗する可能性があります。このテストは、そのような誤動作を検出し、ランタイムのCAS操作が符号なし32ビット数を正しく扱うことを保証します。

## コアとなるコードの解説

追加されたコードは以下の通りです。

```c
	z = 0xffffffff;
	if(!runtime·cas(&z, 0xffffffff, 0xfffffffe))
		runtime·throw("cas5");
	if(z != 0xfffffffe)
		runtime·throw("cas6");
```

1.  `z = 0xffffffff;`
    *   `z`という変数を、32ビット符号なし整数の最大値である `0xffffffff` (16進数表記) で初期化しています。これは、符号付き32ビット整数としては `-1` に相当する値であり、符号拡張の問題が発生しやすい境界値です。

2.  `if(!runtime·cas(&z, 0xffffffff, 0xfffffffe))`
    *   `runtime·cas`関数を呼び出しています。
        *   第一引数 `&z`: `z`変数のメモリアドレスを渡します。CAS操作の対象となる変数です。
        *   第二引数 `0xffffffff`: 期待値です。`z`の現在の値がこの値であることを期待します。
        *   第三引数 `0xfffffffe`: 新しい値です。もし`z`が期待値と一致すれば、`z`はこの値に更新されます。
    *   `runtime·cas`は、操作が成功した場合に`true`を返します。`!`演算子が付いているため、もしCAS操作が失敗した場合（つまり、`z`が期待値`0xffffffff`と一致しなかった場合）、`if`文の条件が真となり、次の行が実行されます。

3.  `runtime·throw("cas5");`
    *   もし`runtime·cas`が失敗した場合に呼び出される関数です。これはGoランタイムの内部エラー報告メカニズムであり、通常はプログラムをクラッシュさせ、エラーメッセージ "cas5" を出力します。このテストでは、CAS操作が期待通りに成功しなかった場合に、このエラーがスローされることで問題が検出されます。

4.  `if(z != 0xfffffffe)`
    *   CAS操作が成功したと仮定した上で、`z`の最終的な値が期待通りに更新されたかどうかを検証しています。もしCASが成功していれば、`z`の値は`0xfffffffe`になっているはずです。

5.  `runtime·throw("cas6");`
    *   もし`z`の値が`0xfffffffe`になっていなかった場合（つまり、CASは成功したと報告したが、実際には値が更新されていなかった、または不正な値になった場合）に呼び出されるエラー関数です。エラーメッセージ "cas6" を出力します。

これらのテストは、GoランタイムのCAS実装が、特に符号なし32ビットの最大値のようなエッジケースにおいて、符号拡張による誤った比較や更新を行わないことを厳密に検証しています。

## 変更の背景

このコミットの主な目的は、`archive/tar`パッケージ内のコードのクリーンアップと最適化です。特に、USTAR形式のパス分割ロジックにおいて、以下の点が改善の対象となりました。

1.  **不要なエラー処理の削除**: 以前の`splitUSTARLongName`関数はエラーを返していましたが、呼び出し元ではそのエラーが`nil`であるかどうかのチェックにしか使われていませんでした。これは、エラーが実質的に成功/失敗のブール値として扱われていたことを意味します。この冗長性を排除し、関数が直接ブール値を返すように変更することで、コードをよりシンプルにしています。これに伴い、使用されなくなった`errNameTooLong`エラーも削除されました。
2.  **関連チェックの統合**: パスの長さ（`fileNameSize`以下であるか）とASCII文字であるかどうかのチェックが、パス分割関数`splitUSTARPath`の内部に統合されました。これにより、呼び出し元での重複したチェックが不要になり、ロジックが一箇所に集約され、保守性が向上します。
3.  **冗長なマジック設定の削除**: `writeHeader`関数内でUSTARマジック（`ustar\x00`）を設定するロジックが、既に他の場所（L200付近）で設定されているため、冗長であることが判明しました。この重複する設定を削除することで、コードの無駄をなくしています。

これらの変更は、既存の機能に影響を与えることなく、コードの可読性、保守性、および効率性を向上させることを目的としています。コミットメッセージに「Updates #12638」とありますが、この特定のIssueの詳細は現在のところ確認できませんでした。しかし、一般的にこのような変更は、コードレビューやバグ報告の過程で発見された改善点に対応するものです。

## 前提知識の解説

### tarアーカイブ形式とUSTAR拡張

`tar` (tape archive) は、複数のファイルを一つのアーカイブファイルにまとめるためのファイル形式です。UNIX系システムで広く利用されています。
`tar`形式にはいくつかのバージョンがあり、その中でも`USTAR` (Unix Standard TAR) は、POSIX.1-1988で標準化された拡張です。USTARは、従来のtar形式の制限（特にファイル名の長さ）を緩和するために導入されました。

*   **ファイル名の長さ制限**: 従来のtar形式では、ファイル名が100バイトに制限されていました。USTARでは、ファイル名を「プレフィックス (prefix)」と「名前 (name)」の2つのフィールドに分割することで、より長いパスをサポートします。
    *   `name`フィールド: 最大100バイト。通常、ファイル名またはパスの末尾部分を格納します。
    *   `prefix`フィールド: 最大155バイト。パスの先頭部分を格納します。
    *   これにより、合計で256バイトまでのパスを表現できるようになります（`prefix` + `/` + `name`）。
*   **マジックフィールド**: USTAR形式のヘッダには、このアーカイブがUSTAR形式であることを示す「マジック (magic)」フィールド（`ustar\x00`）が含まれています。

### PAX拡張形式

`PAX` (Portable Archive eXchange) 形式は、USTAR形式のさらなる拡張であり、POSIX.1-2001で標準化されました。PAXは、USTARのファイル名やその他のフィールドの長さ制限を実質的に撤廃するために導入されました。
PAXは、特別な「拡張ヘッダ」レコードを使用して、任意の長さのファイル名、大きなファイルサイズ、長いUID/GIDなどのメタデータを格納します。これにより、USTARでは表現できないような非常に長いパスや、非ASCII文字を含むパスも扱うことが可能になります。

### Go言語の`archive/tar`パッケージ

Go言語の標準ライブラリには、`archive/tar`パッケージが含まれており、tarアーカイブの読み書きをサポートしています。このパッケージは、USTARやPAXなどの様々なtar形式のバリアントを処理することができます。
`Writer`構造体は、tarアーカイブを書き込むための機能を提供し、`writeHeader`メソッドは、各ファイルのヘッダ情報をアーカイブに書き込む役割を担います。このヘッダには、ファイル名、サイズ、パーミッションなどのメタデータが含まれます。
`preferPax`フィールドは、USTAR形式で表現できないパスをPAX拡張ヘッダで処理するかどうかを制御します。

### `fileNameSize`と`fileNamePrefixSize`

これらはUSTAR形式におけるファイル名とプレフィックスの最大長を定義する定数です。
*   `fileNameSize`: USTARヘッダの`name`フィールドの最大長（100バイト）。
*   `fileNamePrefixSize`: USTARヘッダの`prefix`フィールドの最大長（155バイト）。

## 技術的詳細

このコミットでは、主に`src/archive/tar/writer.go`ファイル内の`writeHeader`メソッドと`splitUSTARPath`（旧`splitUSTARLongName`）関数の変更が行われました。

1.  **`errNameTooLong`の削除**:
    *   以前は、パスがUSTAR形式の長さ制限を超えた場合に返される`errNameTooLong`というエラー変数が定義されていました。
    *   しかし、`splitUSTARLongName`の呼び出し元では、このエラーが返されたかどうか（つまり`nil`でないか）のみをチェックしており、エラー値自体を特別に処理することはありませんでした。
    *   このコミットでは、`splitUSTARPath`関数がエラーではなくブール値（成功/失敗）を返すように変更されたため、`errNameTooLong`は不要となり削除されました。

2.  **`splitUSTARPath`関数の変更**:
    *   **シグネチャの変更**: `func (tw *Writer) splitUSTARLongName(name string) (prefix, suffix string, err error)` から `func splitUSTARPath(name string) (prefix, suffix string, ok bool)` へと変更されました。レシーバ`tw *Writer`も削除され、純粋な関数になりました。
    *   **エラーからブール値へ**: 戻り値の`err error`が`ok bool`に変わり、パスの分割が成功したかどうかを直接示すようになりました。
    *   **長さとASCIIチェックの統合**: 以前は`writeHeader`内で`len(hdr.Name) > fileNameSize && isASCII(hdr.Name)`というチェックが行われていましたが、このチェックが`splitUSTARPath`関数内部に移動されました。
        *   `if length <= fileNameSize || !isASCII(name)`: パスが`fileNameSize`以下であるか、またはASCII文字でない場合は、USTAR形式で分割できないため、即座に`false`を返します。これにより、USTAR形式のパス分割の前提条件が関数内部で満たされるようになりました。
    *   **分割ロジックの簡素化**: パスを`prefix`と`suffix`に分割するロジックは基本的に同じですが、エラーを返す代わりに`false`を返す条件が明確化されました。

3.  **`writeHeader`メソッドの変更**:
    *   `splitUSTARLongName`の呼び出しが`splitUSTARPath`に変更されました。
    *   以前は`var err error`でエラーを受け取り、`if err == nil`で成功を判定していましたが、新しいバージョンでは`prefix, suffix, ok := splitUSTARPath(hdr.Name)`でブール値`ok`を受け取り、`if ok`で成功を判定します。
    *   **冗長なマジック設定の削除**: 以前のコードには、`if len(prefix) > 0 && !tw.usedBinary { copy(header[257:265], []byte("ustar\\x00")) }`という行がありましたが、これはUSTARマジックを設定するものでした。コミットメッセージによると、このマジックは既にL200付近で設定されているため、この行は冗長であり削除されました。

4.  **テストコードの追加**:
    *   `src/archive/tar/writer_test.go`に`TestSplitUSTARPath`という新しいテスト関数が追加されました。
    *   このテストは、`splitUSTARPath`関数の様々な入力（空文字列、ASCIIでない文字列、長さ制限を超える文字列、適切に分割できる文字列など）に対する挙動を検証します。これにより、変更されたパス分割ロジックが正しく機能することを保証しています。

これらの変更は、コードの重複を排除し、関数の責務をより明確にし、全体的なコードベースの品質を向上させるリファクタリングの一環です。

このテストは、`splitUSTARPath`関数の新しい動作を網羅的に検証するために追加されました。様々なエッジケース（空文字列、非ASCII文字、長さ制限の境界値、有効な分割、無効な分割など）をテストすることで、関数の堅牢性を保証しています。特に、非ASCII文字のパスがUSTAR形式で分割できないことや、USTARの長さ制限を考慮した分割が正しく行われることを確認しています。

このコミットは、Go言語の`cgo`ツールにおいて、ThreadSanitizer (TSAN) のサポートがGCCコンパイラで正しく機能しない問題を修正するものです。具体的には、GCCがClangのように`-fsanitize=thread`フラグが渡されたことをコード内で検出するメカニズムを提供しないため、`cgo`がコンパイラ引数を直接解析し、TSANを有効にするための適切なCプロローグを生成するように変更されています。

## 変更の背景

Go言語の`cgo`は、GoプログラムからC言語のコードを呼び出すためのメカニズムを提供します。このCコード部分におけるデータ競合（data race）を検出するために、ThreadSanitizer (TSAN) を利用することが可能です。TSANは、コンパイラに`-fsanitize=thread`フラグを渡すことで有効になります。

しかし、このTSANの統合において、GCCコンパイラを使用した場合に問題が発生していました。Clangコンパイラは、`__has_feature(thread_sanitizer)`のようなプリプロセッサマクロを提供しており、これによりコンパイル時に`-fsanitize=thread`フラグが渡されたかどうかをCコード内で条件付きで検出できます。この機能を利用することで、TSANが有効な場合にのみTSAN関連のフックコードをコンパイルに含めることが可能でした。

一方、GCCはこの`__has_feature`のような同等のメカニズムを提供していませんでした。そのため、`cgo`が生成するCコードは、GCCでコンパイルされる際に`-fsanitize=thread`フラグが指定されていても、TSANを有効にするための適切なコード（`_cgo_tsan_acquire`や`_cgo_tsan_release`などの関数定義）が条件付きコンパイルによって含まれず、結果としてTSANが正しく機能しないという問題がありました（Issue #14602）。

このコミットは、このGCCとの非互換性を解消し、`cgo`がコンパイラの機能検出に依存するのではなく、`cgo`ツール自体がコマンドライン引数を解析して`-fsanitize=thread`フラグの有無を直接チェックすることで、TSANの有効/無効を適切に制御できるようにすることを目的としています。

## 前提知識の解説

1.  **Go言語の`cgo`**:
    *   Go言語のForeign Function Interface (FFI) の一つで、GoプログラムからC言語の関数を呼び出したり、C言語のデータ構造を扱ったりするための機能です。
    *   `cgo`は、GoとCの間のブリッジとなるコードを自動生成します。Goのソースファイル内に`import "C"`と記述し、その直前のコメントブロックにC言語のコードを記述することで利用します。
    *   `cgo`は、GoコンパイラがGoコードをコンパイルする前に、Cコードをコンパイルし、GoとCの間の呼び出し規約を処理するためのラッパーコードを生成します。

2.  **ThreadSanitizer (TSAN)**:
    *   データ競合（data race）やスレッドの同期に関するバグを検出するための動的解析ツールです。Googleによって開発され、GCCやClangなどの主要なコンパイラに統合されています。
    *   プログラムを`-fsanitize=thread`フラグを付けてコンパイルすることで有効になります。これにより、コンパイラはメモリアクセスや同期プリミティブの呼び出しに計測コード（instrumentation code）を挿入し、実行時にデータ競合を監視します。
    *   データ競合は、複数のスレッドが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって順序付けされていない場合に発生する、マルチスレッドプログラミングにおける深刻なバグです。

3.  **コンパイラフラグとプリプロセッサマクロ**:
    *   **コンパイラフラグ**: コンパイラに特定の動作を指示するためのコマンドラインオプションです。例えば、`-fsanitize=thread`はTSANを有効にするためのフラグです。
    *   **プリプロセッサマクロ**: C/C++言語のプリプロセッサによってコンパイル前に処理される指示です。`#if`, `#ifdef`, `#define`などが含まれます。これらは条件付きコンパイルを可能にし、特定の条件に基づいてコードの一部を含めたり除外したりします。
    *   **`__has_feature`**: Clangコンパイラが提供する特別なプリプロセッサマクロで、特定のコンパイラ機能（例: `thread_sanitizer`）が有効になっているかどうかを検出するために使用されます。GCCにはこれに直接対応するマクロがありません。

## 技術的詳細

このコミットの核心は、`cgo`がTSANの有効化をコンパイラ（特にGCC）の機能検出に依存するのではなく、`cgo`ツール自身が能動的にコンパイラフラグをチェックするアプローチに切り替えた点にあります。

以前の`cgo`のTSANサポートは、生成されるCコードのプロローグ部分で以下のような条件付きコンパイルロジックを使用していました。

```c
#if defined(__has_feature)
#if __has_feature(thread_sanitizer)
// TSAN関連の関数定義
#endif
#endif
```

このコードは、`__has_feature`マクロが存在し、かつ`thread_sanitizer`機能が有効である場合にのみ、TSANを有効にするためのC関数（`_cgo_tsan_acquire`, `_cgo_tsan_release`など）を定義していました。Clangはこのマクロをサポートしているため、Clangで`-fsanitize=thread`が指定されると、この条件が真となり、TSANサポートが有効になりました。

しかし、GCCはこの`__has_feature`マクロをサポートしていないため、GCCでコンパイルする際には`defined(__has_feature)`が偽となり、結果としてTSAN関連の関数定義が常にスキップされていました。これにより、`-fsanitize=thread`フラグがGCCに渡されても、`cgo`が生成するCコードはTSANの計測に対応できず、データ競合の検出が不可能になっていました。

このコミットでは、この問題を解決するために以下の変更が導入されました。

1.  **`cgo`によるフラグの直接チェック**: `cgo`ツール（`src/cmd/cgo/main.go`）が、自身に渡されたコンパイラ引数の中に`-fsanitize=thread`が含まれているかどうかを直接走査します。
2.  **動的なプロローグ選択**: `cgo`は、このフラグの有無に基づいて、生成するCコードに含めるTSAN関連のプロローグを動的に選択します。
    *   フラグが存在する場合: TSANを有効にするためのプロローグ（`yesTsanProlog`）を使用します。これには、TSANランタイム関数（`__tsan_acquire`, `__tsan_release`）の外部宣言と、`_cgo_tsan_acquire`, `_cgo_tsan_release`の実装が含まれます。
    *   フラグが存在しない場合: TSANを無効にするためのプロローグ（`noTsanProlog`）を使用します。これには、`_cgo_tsan_acquire`と`_cgo_tsan_release`を空のマクロとして定義するコードが含まれ、TSANのフックを実質的に無効にします。

このアプローチにより、`cgo`はコンパイラの特定の機能検出マクロに依存することなく、`-fsanitize=thread`フラグの有無を確実に判断し、GCCを含むあらゆるコンパイラでTSANサポートを適切に有効化または無効化できるようになりました。

## コアとなるコードの解説

### `src/cmd/cgo/main.go` の変更点

`main`関数内に新しいループが追加されました。

```go
for _, arg := range args[:i] {
    if arg == "-fsanitize=thread" {
        tsanProlog = yesTsanProlog
    }
}
```

このコードは、`cgo`コマンドに渡された引数（`args[:i]`はコンパイラに渡されるフラグのリストを想定）を反復処理します。もし引数の中に文字列`"-fsanitize=thread"`が見つかった場合、グローバル変数`tsanProlog`に`yesTsanProlog`（TSANを有効にするためのCプロローグ）を代入します。この`tsanProlog`変数は、後続のコード生成プロセスでCコードのヘッダ部分に挿入される内容を決定します。デフォルトでは、`tsanProlog`は`noTsanProlog`（TSANを無効にするプロローグ）に初期化されています。

### `src/cmd/cgo/out.go` の変更点

1.  **`tsanProlog`の分割**:
    *   以前は単一の`const tsanProlog`として定義されていたTSAN関連のCプロローグが、`const noTsanProlog`と`const yesTsanProlog`の2つの定数に分割されました。
    *   `noTsanProlog`は、`_cgo_tsan_acquire()`と`_cgo_tsan_release()`を空のマクロとして定義します。これにより、TSANが有効でない場合にこれらの関数呼び出しが何もしないようにし、コンパイルエラーを防ぎます。
        ```c
        #define _cgo_tsan_acquire()
        #define _cgo_tsan_release()
        ```
    *   `yesTsanProlog`は、TSANが有効な場合に必要となる実際のコードを含みます。これには、`_cgo_sync`という共通変数、`__tsan_acquire`と`__tsan_release`というTSANランタイム関数の外部宣言、そして`_cgo_tsan_acquire`と`_cgo_tsan_release`の実装が含まれます。これらの実装は、それぞれ`__tsan_acquire`と`__tsan_release`を呼び出すことで、TSANの計測フックを提供します。
        ```c
        long long _cgo_sync __attribute__ ((common));

        extern void __tsan_acquire(void*);
        extern void __tsan_release(void*);

        static void _cgo_tsan_acquire() {
        	__tsan_acquire(&_cgo_sync);
        }
        static void _cgo_tsan_release() {
        	__tsan_release(&_cgo_sync);
        }
        ```

2.  **`tsanProlog`の変数化**:
    *   `const tsanProlog`が削除され、代わりに`var tsanProlog = noTsanProlog`という形で変数として宣言されました。
    *   これにより、`main.go`で`-fsanitize=thread`フラグが検出された際に、この`tsanProlog`変数の値を`yesTsanProlog`に動的に変更することが可能になります。

これらの変更により、`cgo`はコンパイラの機能検出に頼ることなく、自身でTSANの有効/無効を判断し、それに応じたCプロローグを生成することで、GCC環境下でもThreadSanitizerが正しく機能するようになりました。

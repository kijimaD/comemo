# [インデックス 25945] ファイルの概要

## コミット

runtime/cgo: Solarisのスレッドスタックは少なくとも1MBであると仮定する

"ulimit -s unlimited"で実行すると、misc/cgo/testテストバイナリはgetcontextによって返されるスタックサイズが0x3000であることを見つけます。これにより、ランタイムはその境界内に留まろうとし、Cによって64KBが使用された後、テストでコールバックされたときにフォルトが発生します。

Solarisは、現在のスタックサイズを報告し、フォルトが発生するとスタックを成長させるような賢いことをしているのではないかと疑われます。他のすべてのシステムでは、getcontextは最大スタックサイズを報告します。そして、ulimitが無制限でない場合、Solarisでさえ最大スタックサイズを報告します。

この問題を回避するため、Solaris上のスタックは少なくとも1MBであると仮定します。

Fixes #12210.

## 変更の背景

このコミットは、GoプログラムがSolarisオペレーティングシステム上でCgo（GoとC言語の相互運用機能）を使用する際に発生する特定のスタックオーバーフロー問題を解決するために導入されました。

問題の核心は、Solarisが`ulimit -s unlimited`（スタックサイズを無制限に設定するコマンド）で実行されている場合に、`getcontext`システムコールがスタックの「現在の」サイズ（非常に小さい値、例えば0x3000バイト）を報告し、他のシステムのように「最大」スタックサイズを報告しないことにありました。

Goランタイムは、`getcontext`から得られたスタックサイズ情報に基づいて、Cgoコールバック時のスタック境界を決定します。Solarisが誤って小さなスタックサイズを報告すると、Goランタイムはその小さな境界内で動作しようとします。しかし、Cコードが64KB以上のスタックを使用すると、GoランタイムがCコードからコールバックされた際に、Goが想定するスタック境界を超えてしまい、結果としてページフォルト（スタックオーバーフロー）が発生し、プログラムがクラッシュしていました。

この挙動は、Solarisがスタックを動的に拡張する「賢い」メカニズムを持っているためと考えられますが、Goランタイムはその動的な挙動を直接認識できないため、静的に報告される小さな値に依存してしまい問題を引き起こしていました。`ulimit`が`unlimited`でない場合は、Solarisも他のシステムと同様に最大スタックサイズを正しく報告するため、この問題は特定の条件下でのみ発生していました。

このコミットは、Solarisのこの特殊な挙動に対するワークアラウンドとして、GoランタイムがSolaris上でCgoを使用する際に、スタックサイズが少なくとも1MBであると仮定することで、この問題を回避することを目的としています。

## 前提知識の解説

### Goランタイムとスタック管理

Go言語は独自のランタイムを持ち、ゴルーチンと呼ばれる軽量なスレッドを管理します。各ゴルーチンは独自のスタックを持ち、Goランタイムはこれらのスタックの割り当て、拡張、縮小を効率的に行います。スタックは通常、ヒープとは別に管理され、関数呼び出しのローカル変数や引数などが格納されます。スタックの境界は、スタックオーバーフローを防ぐためにランタイムによって監視されます。

### Cgo

Cgoは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのメカニズムです。GoとCの間でデータをやり取りしたり、既存のCライブラリを利用したりする際に不可欠です。Cgo呼び出しでは、GoのスタックとCのスタックの間でコンテキストの切り替えが発生するため、スタック管理が複雑になります。

### Solarisオペレーティングシステム

Solarisは、Sun Microsystems（現在はOracle）によって開発されたUNIXベースのオペレーティングシステムです。特にエンタープライズ環境で利用されてきました。UNIX系のOSは、プロセスやスレッドの管理、メモリ管理、ファイルシステムなどにそれぞれ独自の実装や挙動を持つことがあります。

### `ulimit -s unlimited`

`ulimit`コマンドは、ユーザーが利用できるシステムリソースの制限を設定または表示するために使用されます。`-s`オプションはスタックサイズ（stack size）を指し、`unlimited`はスタックサイズに上限を設けないことを意味します。通常、これによりプログラムは必要に応じてスタックを大きく拡張できるようになります。

### `getcontext`システムコール

`getcontext`は、POSIX標準で定義されているシステムコールの一つで、現在の実行コンテキスト（CPUレジスタ、スタックポインタ、シグナルマスクなど）を`ucontext_t`構造体に保存します。この情報は、後で`setcontext`や`swapcontext`を使って実行コンテキストを復元するために使用されます。Goランタイムは、Cgo呼び出しの際に、Cコードのスタック情報を取得するためにこれを利用することがあります。

### `ucontext_t`構造体と`uc_stack`

`ucontext_t`構造体は、`getcontext`によって取得されるコンテキスト情報を保持します。この構造体には、スタックに関する情報を含む`uc_stack`フィールドがあります。`uc_stack`は`stack_t`型であり、その中にスタックの開始アドレスを示す`ss_sp`（stack pointer）と、スタックのサイズを示す`ss_size`（stack size）が含まれます。Goランタイムはこれらの情報を使って、Cgo呼び出し時のスタック境界を把握します。

## 技術的詳細

この問題は、Solarisが`ulimit -s unlimited`設定下で`getcontext`を呼び出した際に、`ucontext_t`構造体の`uc_stack.ss_size`フィールドに報告される値が、他のUNIX系システム（Linux, macOSなど）とは異なる挙動を示すことに起因します。

通常、`getcontext`はスレッドの最大スタックサイズを`uc_stack.ss_size`に設定します。しかし、Solarisが`ulimit -s unlimited`で実行されている場合、`getcontext`はスタックの最大サイズではなく、その時点での「現在の」スタックの使用量、または非常に小さな初期スタックサイズを報告するようです。コミットメッセージでは、これが`0x3000`（約12KB）という値として観測されたと述べられています。

Goランタイムは、Cgo呼び出しを行う際に、Cコードが使用するスタック領域を確保し、GoのスタックとCのスタックが衝突しないように境界を管理します。この管理のために、Goランタイムは`getcontext`から得られる`uc_stack.ss_sp`（スタックの開始アドレス）と`uc_stack.ss_size`（スタックサイズ）を利用して、Cスタックの有効範囲を決定します。

Solarisが`0x3000`のような小さな`ss_size`を報告すると、GoランタイムはCスタックがその小さな範囲しか持たないと誤解します。しかし、Cコードが実際に64KBなどのより大きなスタック領域を使用すると、Goランタイムが想定する境界を超えてしまい、メモリ保護違反（ページフォルト）が発生し、プログラムがクラッシュします。これは、Solarisがスタックを必要に応じて動的に拡張するメカニズムを持っているにもかかわらず、`getcontext`がその動的な最大サイズを報告しないために起こるミスマッチです。

このコミットによる解決策は、Solarisのこの特殊な挙動を「ワークアラウンド」することです。具体的には、`src/runtime/cgo/gcc_solaris_amd64.c`ファイル内で、`getcontext`が報告した`uc_stack.ss_size`が1MB（`1024*1024`バイト）よりも小さい場合に、Goランタイムが内部的に管理するスタックの下限（`g->stacklo`）を調整します。これにより、GoランタイムはCスタックが少なくとも1MBのサイズを持つと仮定し、Cコードがより大きなスタックを使用しても、Goランタイムが誤った境界チェックでクラッシュするのを防ぎます。1MBという値は、一般的なCgoのスタック使用量を安全にカバーできると判断された妥当な最小値として選ばれたと考えられます。

変更は`src/runtime/cgo/gcc_solaris_amd64.c`ファイルにあります。

@@ -20,6 +20,12 @@ x_cgo_init(G *g, void (*setg)(void*))

## コアとなるコードの解説

追加されたコードは、`x_cgo_init`関数内にあります。この関数は、Cgoの初期化プロセスの一部として呼び出され、現在のGoゴルーチン（`G *g`）のスタック情報を設定します。

1.  `g->stacklo = (uintptr_t)ctx.uc_stack.ss_sp;`
    *   この行は、`getcontext`によって取得されたコンテキスト情報`ctx`から、スタックポインタの開始アドレス（`ctx.uc_stack.ss_sp`）をGoランタイムのゴルーチン構造体`g`の`stacklo`フィールドに設定しています。`stacklo`は、Goランタイムが認識するスタックの下限（最も低いアドレス）を示します。

2.  `if(ctx.uc_stack.ss_size < 1024*1024)`
    *   この条件文が、Solaris特有のワークアラウンドの核心です。`getcontext`が報告したスタックサイズ`ctx.uc_stack.ss_size`が1MB（`1024*1024`バイト）よりも小さいかどうかをチェックします。
    *   前述の通り、`ulimit -s unlimited`設定下のSolarisでは、`getcontext`が非常に小さなスタックサイズを報告する問題があるため、この条件が真になることが期待されます。

3.  `g->stacklo -= 1024*1024 - ctx.uc_stack.ss_size;`
    *   `if`条件が真の場合、この行が実行され、`g->stacklo`が調整されます。
    *   `1024*1024 - ctx.uc_stack.ss_size`は、報告されたスタックサイズが1MBに満たない「不足分」のバイト数を計算します。
    *   この不足分を`g->stacklo`から減算することで、Goランタイムが認識するスタックの下限をさらに低いアドレスに移動させます。これにより、GoランタイムはCスタックが少なくとも1MBのサイズを持つと「仮定」し、Cコードがより多くのスタック領域を使用しても、Goランタイムが誤ってスタックオーバーフローを検出するのを防ぎます。
    *   この調整は、GoランタイムがCgo呼び出し時にCスタックの有効範囲をより広くとることを可能にし、Solarisの動的なスタック拡張挙動とGoランタイムの静的なスタックサイズ認識の間のミスマッチを解消します。

この変更により、Solaris上で`ulimit -s unlimited`を使用している環境でも、GoのCgo機能が安定して動作するようになります。

# [インデックス 24745] ファイルの概要

このコミットは、Go言語のビルドツールである`cmd/go`において、ベンダー（vendoring）機能の実験的なサポートをデフォルトで有効にする変更を導入します。具体的には、Go 1.5で導入された`GO15VENDOREXPERIMENT`環境変数によるベンダー機能の有効化を、Go 1.6に向けてデフォルトでオンにするように動作を変更し、無効化するには明示的に環境変数を設定する必要があるようにします。これにより、Go 1.6でのベンダー機能の本格導入に先立ち、より広範なテストとフィードバックを促すことが目的です。

## 変更の背景

Go言語の初期の依存関係管理は`GOPATH`に大きく依存しており、プロジェクト間で異なるバージョンのライブラリを使用することが困難でした。この問題を解決するため、Go 1.5で「ベンダー（vendoring）」と呼ばれる実験的な機能が導入されました。ベンダー機能は、プロジェクトのルートディレクトリ内に`vendor`という特別なディレクトリを作成し、その中にプロジェクト固有の依存関係のコピーを配置することで、依存関係の分離と再現可能なビルドを可能にするものです。

Go 1.5では、このベンダー機能は`GO15VENDOREXPERIMENT=1`という環境変数を設定した場合にのみ有効になる「オプトイン」方式で提供されました。これは、新しい機能の導入に伴う潜在的な問題や互換性の問題を早期に発見し、コミュニティからのフィードバックを収集するための一般的なアプローチです。

このコミットは、Go 1.6のリリースに向けて、ベンダー機能をデフォルトで有効にするという決定を反映しています。コミットメッセージにある「If we're going to do this for Go 1.6 we might as well do it now and find out what breaks.（Go 1.6でこれを行うつもりなら、今すぐやって何が壊れるかを見つけるべきだ）」という言葉は、この機能がGo 1.6で標準となることを見据え、より多くのユーザーに早期に利用してもらい、潜在的なバグやエッジケースを洗い出すことを目的としていることを示しています。これにより、Go 1.6のリリース時には、より安定したベンダー機能を提供できるようになります。

## 前提知識の解説

### Go ModulesとVendoring

Go言語における依存関係管理の進化は、主に`GOPATH`、Vendoring、そしてGo Modulesという3つの段階を経てきました。

*   **GOPATH**: Goの初期バージョンでは、すべてのGoプロジェクトは単一の`GOPATH`ディレクトリ内で管理されていました。依存関係は`GOPATH/src`に直接ダウンロードされ、すべてのプロジェクトで同じバージョンのライブラリが共有されるため、異なるプロジェクトで異なるバージョンの依存関係が必要な場合に問題が生じました。
*   **Vendoring**: `GOPATH`の課題を解決するために導入されたのがVendoringです。これは、各プロジェクトが自身の依存関係のコピーをプロジェクト内の`vendor`ディレクトリに保持する仕組みです。これにより、プロジェクトは外部の依存関係から独立し、再現可能なビルドが可能になります。`go build`や`go run`などのコマンドは、まず`vendor`ディレクトリ内を検索し、そこで見つからなければ`GOPATH`を検索するようになります。
*   **Go Modules**: Vendoringは一歩前進でしたが、依存関係のバージョン管理や推移的依存関係の解決には依然として課題がありました。Go Modulesは、Go 1.11で導入され、Go 1.13でデフォルトとなった公式の依存関係管理システムです。`go.mod`ファイルと`go.sum`ファイルを使用して、プロジェクトの依存関係とそのバージョンを明示的に定義し、モジュールベースのビルドを可能にします。VendoringはGo Modulesの機能の一部として利用できますが、Go Modules自体は`vendor`ディレクトリの使用を必須とはしません（`go mod vendor`コマンドで`vendor`ディレクトリを生成できます）。

### `vendor` ディレクトリの特殊性

Goツールチェーンにおいて、プロジェクトのルートディレクトリ直下やサブディレクトリに存在する`vendor`という名前のディレクトリは特別な意味を持ちます。
*   `vendor`ディレクトリ内のパッケージは、その`vendor`ディレクトリの親ディレクトリツリー内のコードからのみインポート可能です。
*   インポートパスは、`vendor`要素を含むプレフィックスを省略した形式で記述されます。例えば、`github.com/foo/bar/vendor/baz`というパスのパッケージは、`baz`としてインポートされます。
*   `vendor`ディレクトリ内のコードは、インポートパスのチェック（`go help importpath`参照）の対象外となります。

### `go get` コマンド

`go get`コマンドは、Goパッケージとその依存関係をダウンロードし、インストールするために使用されます。ベンダー機能が有効な場合、`go get`はGitリポジトリをチェックアウトまたは更新する際に、参照されているGitサブモジュールも更新するようになります。

### `GO15VENDOREXPERIMENT` 環境変数

Go 1.5では、ベンダー機能は実験的なものとして導入されました。この機能を有効にするには、ユーザーが明示的に環境変数`GO15VENDOREXPERIMENT`を`1`に設定する必要がありました。このコミットにより、Go 1.6ではこの環境変数の解釈が変更され、デフォルトでベンダー機能が有効になり、無効にするには`GO15VENDOREXPERIMENT=0`を設定する必要があるようになります。Go 1.7では、この環境変数は完全に効果を失う予定でした。

## 技術的詳細

このコミットの主要な技術的変更点は、`GO15VENDOREXPERIMENT`環境変数の評価ロジックの反転と、それに関連するドキュメントの更新です。

以前は、`src/cmd/go/pkg.go`内の`go15VendorExperiment`変数は以下のように定義されていました。
```go
var go15VendorExperiment = os.Getenv("GO15VENDOREXPERIMENT") == "1"
```
これは、環境変数`GO15VENDOREXPERIMENT`が文字列`"1"`と厳密に一致する場合にのみ`true`となり、ベンダー機能が有効になることを意味します。つまり、デフォルトでは`false`（無効）でした。

このコミットでは、この定義が以下のように変更されます。
```go
var go15VendorExperiment = os.Getenv("GO15VENDOREXPERIMENT") != "0"
```
この変更により、`GO15VENDOREXPERIMENT`が`"0"`以外の任意の値（未設定を含む）である場合に`true`となり、ベンダー機能が有効になります。これにより、ベンダー機能がデフォルトで「オン」になり、明示的に`GO15VENDOREXPERIMENT=0`を設定した場合にのみ「オフ」になるという動作に変わります。

このロジックの変更に伴い、`src/cmd/go/alldocs.go`と`src/cmd/go/help.go`内のドキュメントも更新されています。
*   以前は「If the vendoring experiment is enabled (see 'go help gopath'), then when go get checks out or updates a Git repository,...」という記述でしたが、これは「Unless vendoring support is disabled (see 'go help gopath'), when go get checks out or updates a Git repository,...」に変更され、デフォルトで有効であることを示唆する表現になっています。
*   ベンダーディレクトリに関する説明も、「Go 1.5 includes experimental support... Setting the environment variable GO15VENDOREXPERIMENT=1 enables that experimental support.」から、「Go 1.6 includes support... In Go 1.5, as an experiment, setting the environment variable GO15VENDOREXPERIMENT=1 enabled these features. As of Go 1.6 they are on by default. To turn them off, set GO15VENDOREXPERIMENT=0. In Go 1.7, the environment variable will stop having any effect.」と更新され、Go 1.6でのデフォルト有効化と将来的な`GO15VENDOREXPERIMENT`の廃止が明記されています。

この変更は、Goツールチェーンの内部的な動作とユーザーへの情報提供の両面で、ベンダー機能の成熟と標準化に向けた重要なステップです。

## コアとなるコードの解説

このコミットの核心は、`src/cmd/go/pkg.go`における`go15VendorExperiment`変数の定義変更です。

変更前:
```go
var go15VendorExperiment = os.Getenv("GO15VENDOREXPERIMENT") == "1"
```
この行は、環境変数`GO15VENDOREXPERIMENT`の値が文字列`"1"`と完全に一致する場合にのみ、`go15VendorExperiment`を`true`に設定していました。それ以外の値（未設定、空文字列、`"0"`など）の場合は`false`となり、ベンダー機能は無効でした。これは「オプトイン」の挙動です。

変更後:
```go
var go15VendorExperiment = os.Getenv("GO15VENDOREXPERIMENT") != "0"
```
この変更により、`go15VendorExperiment`は、環境変数`GO15VENDOREXPERIMENT`の値が文字列`"0"`と一致しない場合に`true`に設定されます。つまり、`GO15VENDOREXPERIMENT`が未設定の場合や、`"1"`、`"true"`、あるいはその他の任意の非`"0"`の値である場合に`true`となります。これにより、ベンダー機能がデフォルトで有効になり、明示的に`GO15VENDOREXPERIMENT=0`を設定した場合にのみ無効になるという「オプトアウト」の挙動に変わります。

このロジックの変更は、Go 1.6でベンダー機能をデフォルトで有効にするという方針をコードレベルで実現するものです。

また、`src/cmd/go/alldocs.go`と`src/cmd/go/help.go`におけるドキュメントの更新は、この新しいデフォルトの挙動をユーザーに正確に伝えるために不可欠です。特に、Go 1.5での実験的な導入、Go 1.6でのデフォルト有効化、そしてGo 1.7での環境変数の廃止というロードマップが明確に記述されており、ユーザーが将来のGoバージョンでのベンダー機能の挙動を理解するのに役立ちます。`go get`がGitサブモジュールを更新する挙動についても、ベンダー機能が有効であるかどうかの条件が「有効な場合」から「無効にされていない限り」という表現に変わっています。

これらの変更は、Goの依存関係管理の進化における重要なマイルストーンであり、Go 1.6以降のGo開発者が依存関係を管理する方法に直接影響を与えるものです。

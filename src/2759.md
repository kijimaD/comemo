# [インデックス 2759] ファイルの概要

このコミットは、Go言語のコンパイラが不正な文字リテラル `'''` を正しくエラーとして検出しないバグに対するテストケースを追加するものです。具体的には、`test/bugs/bug169.go` という新しいテストファイルが追加され、この不正な構文がコンパイル時にエラーとなることを検証します。また、テスト結果を記録する `test/golden.out` ファイルも更新され、このバグテストが期待通りに失敗すること（つまり、コンパイラがエラーを出すこと）が明示されています。

## 変更の背景

Go言語の初期開発段階において、コンパイラ（当時の`6g`）が特定の不正な文字リテラル構文を適切にエラーとして扱わないバグが存在していました。このコミットで対象となっているのは、3つのシングルクォート `'''` で構成される文字リテラルです。Go言語の仕様では、文字リテラルは単一のUnicodeコードポイントを表すため、`'a'` のように単一の文字をシングルクォートで囲む必要があります。`'''` のような構文は、Goの字句解析規則において曖昧さや未定義の振る舞いを引き起こす可能性があり、コンパイラがこれを有効な文字リテラルとして誤って解釈したり、あるいは単に無視してしまったりするケースがありました。

このコミットは、このコンパイラの不適切な挙動を特定し、将来的に修正が施された際にその修正が正しく機能するかを確認するための回帰テストを追加することを目的としています。つまり、このコミット自体がバグを修正するものではなく、バグが存在することを明確にし、その修正を検証するための基盤を構築するものです。

## 前提知識の解説

### Go言語における文字リテラルと文字列リテラル

*   **文字リテラル (Rune Literal)**: Go言語では、単一のUnicodeコードポイントを表すためにシングルクォート (`'`) を使用します。例えば、`'a'` は文字 'a' を表し、`'世'` は漢字の '世' を表します。これらは `rune` 型（`int32` のエイリアス）の値として扱われます。エスケープシーケンスも使用でき、例えば `'\n'` は改行文字を表します。
*   **文字列リテラル (String Literal)**: ゼロ個以上のバイトのシーケンスを表すためにダブルクォート (`"`) またはバッククォート (`` ` ``) を使用します。
    *   **解釈済み文字列リテラル (Interpreted String Literal)**: ダブルクォートで囲まれた文字列で、エスケープシーケンスが解釈されます。例: `"Hello\nWorld"`。
    *   **Raw文字列リテラル (Raw String Literal)**: バッククォートで囲まれた文字列で、エスケープシーケンスは解釈されず、文字通りに扱われます。例: `` `C:\Users\Name` ``。

このコミットの文脈では、`'''` が文字リテラルとして解釈されるべきではないにもかかわらず、コンパイラがそれを適切に処理できなかった点が問題でした。

### Goコンパイラの`errchk`ディレクティブとテストフレームワーク

Goプロジェクトのテストスイートには、コンパイラが特定のエラーを生成することを期待するテストケースを記述するための特別なメカニズムがあります。`// errchk $G $D/$F.go` のようなコメントは、Goのテストフレームワークが使用するディレクティブです。

*   `// errchk`: この行を含むファイルがコンパイルされる際に、指定されたエラーメッセージが出力されることを期待するテストであることを示します。
*   `$G`: 現在のGoコンパイラ（この場合は`6g`）を指す変数です。
*   `$D/$F.go`: テスト対象のファイルパスを指す変数です。
*   `// ERROR "char"`: この行のコメントは、コンパイラが「char」という文字列を含むエラーメッセージを出力することを期待していることを示します。

`test/golden.out` ファイルは、これらの`errchk`テストの期待される出力（または、テストが失敗した場合の実際の出力）を記録するために使用されます。テストが実行されると、実際の出力が`golden.out`の期待される出力と比較され、一致しない場合はテストが失敗します。このコミットでは、`BUG: errchk: command succeeded unexpectedly: 6g bugs/bug169.go` という行が追加されており、これは「`6g bugs/bug169.go` のコンパイルが予期せず成功した（つまり、エラーが出なかった）」というバグを記録しています。これは、このテストが追加された時点ではバグがまだ存在しており、コンパイラがエラーを出すべきところで出していなかったことを示しています。

## 技術的詳細

このバグは、Goコンパイラの字句解析器（lexer）またはパーサー（parser）における文字リテラルの処理ロジックに起因するものと考えられます。

1.  **字句解析の課題**: Goの字句解析器は、ソースコードをトークン（キーワード、識別子、リテラルなど）に分割します。シングルクォート (`'`) を見つけると、字句解析器は文字リテラルの開始と認識し、次のシングルクォートまでを文字の内容として読み取ろうとします。しかし、`'''` のようなシーケンスの場合、最初の `'` は文字リテラルの開始、次の `'` は文字リテラルの終了と解釈され、その後の `'` が予期しないトークンとして扱われるか、あるいは字句解析器が不正な状態に陥る可能性があります。
2.  **パーシングの課題**: 字句解析器が `'''` を何らかのトークンとして渡した場合、パーサーはGo言語の文法規則に従ってそれを解釈しようとします。Goの文法では、文字リテラルは単一のUnicodeコードポイントでなければなりません。`'''` はこの規則に違反するため、パーサーは構文エラーを報告する必要があります。しかし、バグのあるコンパイラは、この不正な構文を有効なものとして誤って受け入れてしまっていたか、あるいはエラーを報告せずに処理を続行してしまっていたと考えられます。
3.  **`ERROR "char"` の意味**: テストケース `var x = '''; // ERROR "char"` に含まれる `ERROR "char"` は、コンパイラが「char」というキーワードを含むエラーメッセージを出力することを期待していることを示唆しています。これは、コンパイラがこの構文を文字リテラルとして認識しようとしたが、その内容が不正である（例えば、複数文字である）ためにエラーを出すべきである、という意図を反映しています。

このコミットは、この特定の不正な文字リテラル `'''` がコンパイラによって正しくエラーとして扱われることを保証するためのテストカバレッジを追加することで、コンパイラの堅牢性を向上させる一歩となりました。

## コアとなるコードの解説

### `test/bugs/bug169.go`

このファイルは、Goコンパイラのバグをテストするために新しく追加されたものです。

*   `// errchk $G $D/$F.go`: これはGoテストフレームワークに対する指示で、このファイルがコンパイルされる際にエラーが発生することを期待していることを示します。`$G` はGoコンパイラ（当時の`6g`）、`$D/$F.go` は現在のファイルパスに置き換えられます。
*   `package main`: 実行可能なGoプログラムの開始点を示します。
*   `var x = '''; // ERROR "char"`: この行がテストの核心です。
    *   `var x = ''';`: 不正な文字リテラル `'''` を変数 `x` に代入しようとしています。Goの文字リテラルは単一の文字である必要があるため、これは構文的に不正です。
    *   `// ERROR "char"`: このコメントは、コンパイラがこの行で「char」という文字列を含むエラーメッセージを出力することを期待していることをテストフレームワークに伝えます。

このテストファイルは、コンパイラが `'''` という不正な文字リテラルを正しく認識し、適切なエラーメッセージ（「char」という単語を含むもの）を出力するかどうかを検証します。

### `test/golden.out`

このファイルは、Goテストスイートの期待される出力（ゴールデンファイル）を記録するものです。

*   `=========== bugs/bug169.go`: 新しいテストケース `bugs/bug169.go` の結果セクションの開始を示します。
*   `BUG: errchk: command succeeded unexpectedly: 6g bugs/bug169.go`: この行は、このコミットが作成された時点でのコンパイラの挙動を示しています。`errchk` テストはエラーが発生することを期待していましたが、`6g bugs/bug169.go` のコンパイルは「予期せず成功した」、つまりエラーを出さなかったことを意味します。これは、コンパイラにバグが存在し、不正な構文をエラーとして検出できていなかったことを明確に示しています。この行の追加により、将来的にコンパイラのバグが修正された際には、この行が削除されるか、あるいは「`BUG:`」の部分が「`OK:`」のようなものに置き換えられ、テストが成功したことを示すようになります。

# [インデックス 24563] ファイルの概要

このコミットは、Goの`net/http`パッケージにおけるHTTP/1.1の`Transfer-Encoding: chunked`と`Trailer`ヘッダーの処理に関するセキュリティ脆弱性を修正するものです。具体的には、不正なトレーラーヘッダーが検出された際に、サーバーがそのコネクションを適切に閉じずに再利用してしまう可能性があり、これがリクエストスマグリングの温床となる問題を解決します。

## 変更の背景

このコミットが導入される前は、Goの`net/http`サーバーがHTTP/1.1の`Transfer-Encoding: chunked`で送信されたリクエストボディの末尾にある`Trailer`ヘッダーを処理する際に、不正な形式のトレーラーが検出されても、そのエラーがサーバーの接続管理フローに適切に伝達されないという問題がありました。

具体的には、`body.Read`メソッドが不正なトレーラーを読み取った際にエラーを返しますが、このエラーは通常、リクエストを処理するハンドラに渡されるだけで、サーバーがそのコネクションを「破損している」と認識して閉じるためのシグナルとはなりませんでした。結果として、不正なトレーラーを含むリクエストを処理したコネクションが、その後も再利用可能な状態として扱われ、次のリクエストの処理に利用されてしまう可能性がありました。

このような状況は、HTTPリクエストスマグリング（Request Smuggling）という深刻なセキュリティ脆弱性を引き起こす可能性があります。攻撃者は、この挙動を悪用して、不正なトレーラーを含むリクエストの後に隠された別のリクエスト（「スマグリングされたリクエスト」）を送り込み、サーバーがそれを次の正規のリクエストの一部として誤って解釈するように仕向けることができます。これにより、認証回避、キャッシュポイズニング、機密情報への不正アクセスなど、様々な攻撃が可能になります。

このコミットは、このリクエストスマグリングの潜在的なベクトルを排除するために、不正なトレーラーが検出された場合にサーバーコネクションを強制的に閉じるように`net/http`パッケージの挙動を変更することを目的としています。

## 前提知識の解説

### HTTP/1.1の`Transfer-Encoding: chunked`と`Trailer`ヘッダー

HTTP/1.1では、メッセージボディの長さを事前に知ることができない場合に、`Transfer-Encoding: chunked`というメカニズムを使用してボディを送信できます。これは、ボディを複数の「チャンク」に分割し、各チャンクの前にそのサイズ（16進数）を付加して送信する方式です。ボディの終端は、サイズがゼロのチャンクで示されます。

`Trailer`ヘッダーは、このチャンクエンコーディングと組み合わせて使用される特別なヘッダーです。通常のHTTPヘッダーはメッセージボディの前に送信されますが、`Trailer`ヘッダーは、メッセージボディの処理が完了した後に初めて利用可能になるメタデータ（例: チェックサム、デジタル署名、処理時間など）を送信するために使用されます。`Trailer`ヘッダー自体は、通常のヘッダーブロック内に存在し、その値として、ボディの末尾に続くトレーラーブロックに含まれるヘッダーフィールドの名前を列挙します。実際のトレーラーフィールドは、ゼロサイズのチャンクの後に続きます。

例:
```
POST /upload HTTP/1.1
Host: example.com
Transfer-Encoding: chunked
Trailer: X-Checksum-SHA256

3
abc
3
def
0
X-Checksum-SHA256: some_checksum_value
```

### リクエストスマグリング（Request Smuggling）

HTTPリクエストスマグリングは、Webアプリケーションのセキュリティ脆弱性の一種です。これは、フロントエンドのプロキシサーバー（ロードバランサー、CDNなど）とバックエンドのWebサーバーが、HTTPリクエストの境界を異なる方法で解釈する際に発生します。

HTTP/1.1では、リクエストボディの長さを指定する方法として、`Content-Length`ヘッダーと`Transfer-Encoding: chunked`ヘッダーの2つが主に使われます。これらのヘッダーが同時に存在する場合や、不正な形式で提供された場合に、サーバー間の解釈の不一致が生じることがあります。

例えば、フロントエンドサーバーが`Content-Length`を優先し、バックエンドサーバーが`Transfer-Encoding`を優先する場合、攻撃者は以下のようなリクエストを送信できます。

```
POST /somepath HTTP/1.1
Host: example.com
Content-Length: 100
Transfer-Encoding: chunked

0

GET /smuggled_path HTTP/1.1
Host: example.com
Content-Length: 10

X
```

フロントエンドサーバーは`Content-Length: 100`を見て、全体を1つのリクエストとして処理します。しかし、バックエンドサーバーは`Transfer-Encoding: chunked`を優先し、`0\r\n\r\n`で最初のリクエストボディの終わりを認識します。その結果、`GET /smuggled_path ...`の部分が次のリクエストとして扱われ、バックエンドサーバーが次に受け取る正規のユーザーリクエストの前に、この「スマグリングされた」リクエストが処理されてしまう可能性があります。

この脆弱性は、セキュリティデバイスのバイパス、認証の回避、キャッシュポイズニング、XSS攻撃など、様々な悪用につながる可能性があります。

## 技術的詳細

このコミットは、`net/http`パッケージ内の`body`構造体の`readLocked`メソッドに修正を加えることで、不正なトレーラーヘッダーが検出された際のリクエストスマグリングの可能性を排除します。

以前の挙動では、`body.Read`がトレーラーを読み取る際にエラー（例: 不正な形式）が発生した場合、そのエラーは呼び出し元（通常はHTTPハンドラ）に返されていました。しかし、このエラーは`body`構造体の内部状態（特にコネクションの再利用可能性に関するフラグ）には影響を与えませんでした。そのため、エラーが発生しても、サーバーは基盤となるTCPコネクションが健全であると誤解し、次のHTTPリクエストのためにそのコネクションを再利用しようとしました。

この修正では、`body.readLocked`メソッド内で`b.readTrailer()`がエラーを返した場合に、以下の2つの重要な変更が加えられます。

1.  **`b.sawEOF = false`**: `sawEOF`は、ボディの終端（EOF）が正常に検出されたかどうかを示すフラグです。不正なトレーラーが検出された場合、ボディの終端処理が正常に完了していないと見なすべきであるため、このフラグを`false`に設定します。これにより、後続の読み取り操作がEOFを誤って報告するのを防ぎます。
2.  **`b.closed = true`**: `closed`は、ボディが閉じられた状態にあることを示すフラグです。不正なトレーラーは、そのリクエストの処理が安全に完了できないことを意味するため、このフラグを`true`に設定して、ボディが閉じられた状態であることを明示します。これにより、`body`オブジェクトを通じたそれ以上の読み取り操作が失敗するようになります。

これらの変更により、不正なトレーラーが検出されたコネクションは、`body`オブジェクトの内部状態によって「破損している」とマークされます。`net/http`サーバーは、リクエストの処理が完了した後にコネクションを再利用するかどうかを決定する際に、この`body`オブジェクトの状態を考慮します。`b.closed = true`が設定されている場合、サーバーはそのコネクションが再利用に適さないと判断し、強制的に閉じます。

これにより、不正なトレーラーを含むリクエストの後に、攻撃者が意図した「スマグリングされた」リクエストが同じコネクション上で処理されることを防ぎ、リクエストスマグリングの脆弱性を緩和します。

また、この修正には`src/net/http/serve_test.go`に新しいテストケース`TestInvalidTrailerClosesConnection`が追加されています。このテストは、不正なトレーラーを含むHTTPリクエストをシミュレートし、その後に続くはずのない「秘密の」リクエスト（`/secret`）がサーバーによって処理されないことを検証します。これにより、修正が正しく機能し、不正なトレーラーがコネクションの再利用を防ぐことを保証しています。

## コアとなるコードの解説

### `src/net/http/transfer.go`の変更

`body.readLocked`メソッドは、HTTPリクエストボディの読み取りを処理します。このメソッド内で、`b.readTrailer()`が呼び出され、トレーラーヘッダーの読み取りとパースが試みられます。

変更点:
```go
			if e := b.readTrailer(); e != nil {
				err = e
				// Something went wrong in the trailer, we must not allow any
				// further reads of any kind to succeed from body, nor any
				// subsequent requests on the server connection. See
				// golang.org/issue/12027
				b.sawEOF = false
				b.closed = true
			}
```
このコードブロックは、`b.readTrailer()`がエラー（`e != nil`）を返した場合に実行されます。
-   `err = e`: まず、トレーラー読み取り中に発生したエラーを、`readLocked`メソッドの戻り値`err`に設定します。これにより、呼び出し元（ハンドラなど）にエラーが通知されます。
-   `b.sawEOF = false`: `body`構造体の`sawEOF`フィールドは、リクエストボディの終端が正常に検出されたかどうかを示します。不正なトレーラーは、ボディの終端処理が正常に完了しなかったことを意味するため、このフラグを`false`に設定します。これにより、後続の読み取り操作が誤ってEOFを報告するのを防ぎ、ボディがまだ完全に読み取られていないか、または破損している状態であることを示唆します。
-   `b.closed = true`: `body`構造体の`closed`フィールドは、ボディが閉じられた状態にあることを示します。不正なトレーラーが検出された場合、そのリクエストのボディは安全に処理できないと判断されるため、このフラグを`true`に設定します。このフラグが`true`になると、`body`オブジェクトに対するそれ以上の読み取り操作は失敗するようになります。さらに重要なのは、`net/http`サーバーは、リクエスト処理後にコネクションを再利用するかどうかを決定する際に、この`closed`フラグをチェックします。`closed`が`true`の場合、サーバーはそのコネクションが再利用に適さないと判断し、強制的に閉じます。これにより、リクエストスマグリングの主要な原因である「破損したコネクションの再利用」が防止されます。

### `src/net/http/serve_test.go`の追加テスト

`TestInvalidTrailerClosesConnection`テスト関数は、この修正の有効性を検証するために追加されました。

テストの概要:
1.  `testConn`というモックコネクションを作成し、不正なトレーラーを含むHTTPリクエストのバイト列を`readBuf`に書き込みます。
    -   リクエストは`POST /public`で、`Trailer: hack`と`Transfer-Encoding: chunked`ヘッダーを含みます。
    -   チャンクボディの後に、`I'm not a valid trailer`という不正なトレーラーが続きます。
    -   **重要な点**: 不正なトレーラーの直後に、`GET /secret HTTP/1.1`という「スマグリングされた」リクエストが意図的に配置されています。
2.  `net/http.Serve`関数をゴルーチンで起動し、モックコネクションからのリクエストを処理させます。
3.  ハンドラ関数内で、`numReqs`をインクリメントし、リクエストのパスに`/secret`が含まれていないかをチェックします。もし含まれていれば、テストはエラーを報告します。
4.  `conn.closec`チャネルからの受信を待ちます。これは、モックコネクションが閉じられたことを示すシグナルです。
5.  コネクションが閉じられた後、`numReqs`が`1`であることを検証します。これは、`POST /public`リクエストのみが処理され、`GET /secret`リクエストは処理されなかったことを意味します。

このテストは、不正なトレーラーが検出された場合に、サーバーがコネクションを閉じ、その後のリクエスト（スマグリングされたリクエスト）が処理されないことを明確に示しています。これにより、リクエストスマグリングの脆弱性が効果的に緩和されていることが確認できます。

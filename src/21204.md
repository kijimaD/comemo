## 元コミット内容

このコミットは、GoランタイムにおけるWindows環境での`StackGuard`の制限を一時的に引き上げるものです。コミットメッセージには「640バイトあれば誰にとっても十分だろう」というユーモラスなコメントがありますが、これは一時的な措置であり、Go 1.5のリリース前にこの制限を元に戻す予定であることが示されています。この変更は、Issue 9214に関連しています。

## 変更の背景

Goランタイムは、ゴルーチン（goroutine）のスタック管理において、スタックの動的な拡張をサポートしています。これは、各ゴルーチンが最初は小さなスタックで開始し、必要に応じてスタックを拡張することでメモリを効率的に利用するための仕組みです。スタックの拡張が必要かどうかを判断するために`StackGuard`というメカニズムが使用されます。

このコミットの背景には、Windows環境における特定のスタック関連の問題があったと考えられます。コミットメッセージの「(again)」という記述から、過去にも同様の問題が発生し、`StackGuard`の調整が行われたことが示唆されます。

「640 bytes ought to be enough for anybody.」というコメントは、ビル・ゲイツがかつて「640KBのメモリがあれば誰にとっても十分だろう」と発言したとされる逸話（実際には誤解されている発言）をパロディにしたもので、この一時的な`StackGuard`の増加が、現在の問題に対する十分な解決策であるという開発者の見解を表しています。

Issue 9214は、この`StackGuard`の制限をGo 1.5で元に戻す、つまり引き下げることを目的とした課題であると推測されます。したがって、このコミットは、Go 1.5での最終的な解決策が導入されるまでの、Windows環境におけるスタック関連の問題に対する暫定的な対応として行われました。具体的な問題の内容はコミットメッセージからは読み取れませんが、スタックの枯渇や、特定のシステムコール、あるいはWindows特有のスタック利用パターンが原因で、既存の`StackGuard`値では不十分であった可能性が考えられます。

## 前提知識の解説

### Goランタイムとゴルーチンスタック

Go言語の並行処理の根幹をなすのがゴルーチンです。ゴルーチンは非常に軽量なスレッドのようなもので、数百万ものゴルーチンを同時に実行することが可能です。各ゴルーチンは独自のスタックを持っていますが、従来のOSスレッドのように固定された大きなスタックを持つのではなく、必要に応じて動的にサイズが変更される「可変長スタック」を採用しています。

### スタックガード (StackGuard)

Goランタイムにおける`StackGuard`は、ゴルーチンのスタックオーバーフローを防ぎ、スタックの動的な拡張をトリガーするための重要なメカニズムです。各ゴルーチンのスタックには「ガードページ」のような領域が設定されており、関数呼び出しによってスタックポインタがこのガード領域に近づくと、スタックの拡張が必要であると判断されます。

具体的には、Goの関数プロローグ（関数の冒頭部分）には、現在のスタックポインタ（SP）が`StackGuard`値と比較されるチェックが挿入されています。もしSPが`StackGuard`値よりも小さい（スタックが下方向に成長するため、スタックの底に近づいていることを意味する）場合、スタックが不足していると判断され、`runtime.morestack`という特殊な関数が呼び出されます。

### `runtime.morestack`

`runtime.morestack`関数は、スタックガードがヒットした際に呼び出され、以下の処理を行います。
1.  現在のスタックよりも大きな新しいスタック領域を確保します。
2.  既存のスタックの内容を新しいスタック領域にコピーします。
3.  スタックポインタを新しいスタック領域の適切な位置に調整し、元の関数呼び出しに戻ります。

この仕組みにより、ゴルーチンは最初は小さなスタックで動作し、必要に応じて透過的にスタックサイズを増やすことができます。これにより、メモリ使用量を抑えつつ、多数のゴルーチンを効率的に管理することが可能になります。

### `StackSystem`

`StackSystem`は、OSやシステムコールが使用するスタック領域のオフセットを表す定数です。Goランタイムは、システムコールを行う際に、Goのスタックとは別にOSが管理するスタックを使用することがあります。`StackGuard`の値は、この`StackSystem`の値を考慮して設定されます。これは、システムコール中にスタックが不足しないようにするための安全マージンとして機能します。

### `nosplit`関数

Goコンパイラには、特定の関数に対してスタックガードチェックを挿入しないように指示する`//go:nosplit`ディレクティブがあります。これは、非常に短い関数や、スタックガードチェック自体がオーバーヘッドとなるような低レベルのランタイム関数（例えば、`runtime.morestack`自体や、ガベージコレクタの一部など）で使用されます。これらの関数は、スタックをほとんど使用しないか、あるいはスタックの拡張処理中に呼び出されるため、スタックガードチェックが不要、または不適切であると判断されます。`test/nosplit.go`はこの`nosplit`関数のテストに関連するファイルです。

## 技術的詳細

このコミットの主要な変更は、`StackGuard`定数の値を`512 + StackSystem`から`640 + StackSystem`に増加させたことです。これは、Windows環境において、スタックガードがヒットするまでの許容スタックサイズを128バイト（640 - 512）増やしたことを意味します。

### `StackGuard`の増加が意味するもの

`StackGuard`の値が増加するということは、スタックの「ガード領域」がスタックの底からより遠い位置に移動することを意味します。これにより、スタックポインタがこのガード領域に到達するまでの余裕が大きくなります。つまり、スタックオーバーフローが発生する前に、より多くのスタック領域を使用できるようになります。

Windows環境でこの値が増加されたのは、おそらくWindows特有のスタック使用パターンや、特定のシステムコール、あるいはWindows APIの呼び出しが、Goランタイムが想定していたよりも多くのスタック領域を一時的に消費し、`StackGuard`が意図せず早くヒットしてしまう問題があったためと考えられます。これにより、不必要なスタック拡張（`morestack`呼び出し）が発生したり、場合によってはスタックオーバーフローによるクラッシュが発生したりする可能性がありました。

### `test/nosplit.go`の変更

`test/nosplit.go`の変更は、`StackGuard`の変更に伴うテストの調整です。このテストファイルは、`nosplit`関数（スタックガードチェックが挿入されない関数）の動作を検証するためのものです。

変更前:
```go
// The limit was originally 128 but is now 384.
// Instead of rewriting the test cases above, adjust
// the first stack frame to use up the extra 32 bytes.
if i == 0 {
	size += 384 - 128
}
```

変更後:
```go
// The limit was originally 128 but is now 512.
// Instead of rewriting the test cases above, adjust
// the first stack frame to use up the extra 32 bytes.
if i == 0 {
	size += 512 - 128
}
```

このテストコードは、スタックフレームのサイズを調整して、特定のスタック制限をシミュレートしています。`StackGuard`の値が変更されたため、テストが期待通りに動作するように、このシミュレーションの基準値も`384`から`512`に更新されました。これは、`StackGuard`の変更が、スタックの利用可能な領域の計算に影響を与えることを示しています。`512`という値は、新しい`StackGuard`値である`640`から`StackSmall`（128）を引いた値（640 - 128 = 512）と一致しており、テストが新しい`StackGuard`の定義に合わせて調整されたことを示唆しています。

## コアとなるコードの解説

### `StackGuard`定数の変更 (`src/runtime/stack.h`, `src/runtime/stack2.go`)

`StackGuard`は、Goランタイムがスタックの拡張をトリガーするために使用する閾値です。この値は、スタックの底からのオフセットとして機能します。
-   変更前: `StackGuard = 512 + StackSystem`
-   変更後: `StackGuard = 640 + StackSystem`

この変更により、`StackGuard`の閾値が128バイト増加しました。これは、ゴルーチンがスタックオーバーフローを起こす前に、より多くのスタック領域を使用できるようになったことを意味します。Windows環境で特定のスタック使用パターン（例えば、より深いコールスタックや、特定のAPI呼び出しによる一時的なスタック消費）に対応するために、この安全マージンが拡大されました。`StackSystem`は、OSが使用するスタック領域を考慮するためのオフセットであり、この値自体は変更されていません。

### `test/nosplit.go`の調整

このテストファイルは、`nosplit`関数（スタックガードチェックが省略される関数）の動作を検証するためのものです。テストコード内のコメントと計算ロジックが、新しい`StackGuard`の定義に合わせて更新されました。

-   コメントの変更: 「The limit was originally 128 but is now 384.」が「The limit was originally 128 but is now 512.」に変更されました。
-   計算ロジックの変更: `size += 384 - 128`が`size += 512 - 128`に変更されました。

この`512`という値は、新しい`StackGuard`値である`640`から`StackSmall`（128）を引いた値（640 - 128 = 512）と一致します。`StackSmall`は、スタックガードチェックがヒットした後でも、スタックポインタがスタックガードからどれだけ下（スタックの底方向）に移動することを許容するかを示す定数です。このテストの調整は、ランタイムのスタック管理ロジックの変更が、テストの期待値にも影響を与えることを示しており、変更の正確性を保証するためにテストも更新されたことを意味します。

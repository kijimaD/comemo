# [インデックス 2365] ファイルの概要

このコミットは、Go言語の初期開発段階におけるリンカの重要な改善を含んでいます。特に、32ビットアーキテクチャ（8l）向けのリンカに64ビットアーキテクチャ（6l）での修正を適用し、ポインタサイズの扱いをアーキテクチャ固有にすることで、リンカの正確性と柔軟性を向上させています。また、コマンドライン引数処理の堅牢化とライブラリ検索パスの拡張も行われています。

## 元コミット内容

このコミットの元のメッセージは以下の通りです。

「8lの修正、6lからのカットアンドペースト。PtrSizeの値を6l/8lファイルに移動。」

これは、主に32ビットアーキテクチャ向けのリンカである`8l`に、64ビットアーキテクチャ向けのリンカである`6l`で既に実装されていた修正を取り込み、さらにポインタサイズ（`PtrSize`）の定義を各アーキテクチャ固有のリンカファイルに移動したことを示しています。

## 変更の背景

Go言語の初期開発において、異なるCPUアーキテクチャ（特に32ビットと64ビット）をサポートすることは重要な課題でした。リンカは、コンパイルされたコードを最終的な実行可能ファイルに結合する役割を担っており、このプロセスではメモリレイアウトやポインタのサイズといったアーキテクチャ固有の詳細を正確に扱う必要があります。

このコミット以前は、ポインタサイズ（`PtrSize`）の定義が共通のリンカコード（`src/cmd/ld/go.c`）に一元的に記述されており、これが32ビットアーキテクチャ向けのリンカ（`8l`）で問題を引き起こす可能性がありました。`6l`（AMD64向け）と`8l`（386向け）の間でコードの共通化と差異の管理を行う中で、`6l`で発見された修正や改善を`8l`にも適用する必要がありました。

具体的には、以下の点が背景にあります。

1.  **アーキテクチャ固有のポインタサイズ**: 64ビットシステムではポインタは8バイトですが、32ビットシステムでは4バイトです。リンカがこの違いを正しく認識しないと、メモリのアライメント、データ構造のサイズ計算、シンボル解決などに誤りが生じ、最終的な実行可能ファイルが正しく動作しなくなります。
2.  **リンカの堅牢性向上**: コマンドライン引数の解析は、ツールの使いやすさと堅牢性にとって重要です。引数エラー時のメッセージ表示の一貫性と、より明確なエラーハンドリングが求められていました。
3.  **開発の柔軟性**: ライブラリの検索パスを柔軟に設定できることは、開発者がカスタムライブラリを使用したり、特定の環境でビルドを行ったりする上で不可欠です。

このコミットは、これらの課題に対処し、Goリンカのクロスプラットフォーム対応と全体的な品質を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語のツールチェーンとリンカに関する基本的な知識が必要です。

*   **Goリンカ (`6l`, `8l`, `ld`)**:
    *   Goコンパイラは、Goのソースコードを各アーキテクチャのオブジェクトファイルにコンパイルします。これらのオブジェクトファイルを結合し、最終的な実行可能ファイルを生成するのがリンカの役割です。
    *   **`6l`**: GoのツールチェーンにおけるAMD64（x86-64）アーキテクチャ向けのリンカです。
    *   **`8l`**: Goのツールチェーンにおける386（x86、32ビット）アーキテクチャ向けのリンカです。
    *   **`ld`**: `src/cmd/ld/go.c`は、`6l`や`8l`などの具体的なリンカが共通して利用するリンカのコアロジックやユーティリティ関数を含むファイルです。各アーキテクチャ固有のリンカは、この共通コードをインクルードして利用します。
*   **ポインタサイズ (`PtrSize`)**:
    *   プログラムが実行されるCPUアーキテクチャにおける、メモリ上のアドレスを指し示すポインタのバイトサイズを指します。
    *   32ビットアーキテクチャではポインタは4バイト（32ビット）で、最大4GBのメモリ空間をアドレス指定できます。
    *   64ビットアーキテクチャではポインタは8バイト（64ビット）で、より広大なメモリ空間をアドレス指定できます。
    *   Goのランタイム、特にガベージコレクタやメモリ管理、データ構造のアライメントにおいて、`PtrSize`は極めて重要な定数です。
*   **`D_SBIG`**:
    *   Goリンカの内部で使われるシンボルタイプまたはデータセクションの識別子の一つです。`D_`で始まる定数は、リンカがオブジェクトファイル内のデータやシンボルをどのように解釈・処理するかを定義するために用いられます。
    *   `D_SBIG`は、おそらく特定の「大きな」または「特殊な」データブロックをリンカが扱うためのタイプであり、その処理方法がこのコミットで`8l`リンカに追加されたことを示唆しています。
*   **`EARGF(usage())`**:
    *   Goリンカのコマンドライン引数解析ルーチンで使われるC言語のマクロです。`ARGF()`マクロの拡張版で、引数が期待通りに提供されない場合に、引数解析エラーを検出し、`usage()`関数（プログラムの使用法を表示する関数）を呼び出してエラーメッセージを表示し、プログラムを終了させる役割を担います。これにより、引数処理のコードが簡潔になり、エラーハンドリングが一貫性を持つようになります。
*   **`DUPOK`**:
    *   リンカがシンボルを解決する際に使用するフラグの一つです。`DUPOK`（Duplicate OK）は、「重複が許容される」ことを意味します。
    *   通常、リンカは同じ名前のグローバルシンボルが複数定義されているとエラーとしますが、特定の状況下（例えば、弱いシンボルや特定のセクションのシンボル）では重複が許容される場合があります。このフラグは、そのようなシンボルをリンカが正しく識別し、不必要なエラーを回避するために使用されます。

## 技術的詳細

このコミットは、Goリンカの複数の側面で技術的な改善を導入しています。

1.  **`PtrSize`のアーキテクチャ固有化**:
    *   最も重要な変更点の一つは、`PtrSize`の定義が共通の`src/cmd/ld/go.c`から、各アーキテクチャ固有のリンカファイル（`src/cmd/6l/go.c`と`src/cmd/8l/go.c`）に移動されたことです。
    *   `src/cmd/ld/go.c`からは`enum { PtrSize = 8 };`の行が削除されました。
    *   `src/cmd/6l/go.c`には`enum { PtrSize = 8 };`が追加され、64ビットシステムでのポインタサイズを明示的に8バイトと定義しています。
    *   `src/cmd/8l/go.c`は新規ファイルとして作成され、`enum { PtrSize = 4 };`が追加され、32ビットシステムでのポインタサイズを明示的に4バイトと定義しています。
    *   これらのファイルは、それぞれ`#include "../ld/go.c"`を通じて共通のリンカコードをインクルードするため、`ld/go.c`内のコードは、インクルード元のファイルで定義された`PtrSize`の値を使用することになります。これにより、32ビットと64ビットの両方のアーキテクチャで、リンカが正しいポインタサイズに基づいて動作することが保証されます。これは、Goのクロスコンパイル能力を支える基盤の一つです。

2.  **`usage()`関数の導入と引数解析の改善**:
    *   `src/cmd/6l/obj.c`と`src/cmd/8l/obj.c`の両方で、コマンドライン引数の解析エラー時に`usage()`関数を呼び出すように変更されました。
    *   特に`src/cmd/8l/obj.c`では、`usage()`関数が新しく定義され、リンカの正しい使用法を示すメッセージ（例: `usage: 8l [-options] ...`）を出力するようになりました。
    *   引数解析のロジックでは、`ARGF()`マクロの代わりに`EARGF(usage())`マクロが使用されるようになりました。`EARGF`は、引数が期待される形式でない場合や不足している場合に、自動的に`usage()`関数を呼び出してプログラムを終了させるため、引数処理のコードがより堅牢で簡潔になります。これにより、ユーザーがリンカを誤って使用した場合のフィードバックが改善されます。

3.  **`D_SBIG`のサポート**:
    *   `src/cmd/8l/asm.c`の`datblk`関数に、`D_SBIG`という新しいケースが追加されました。`datblk`関数は、リンカがデータセクションを処理する際に呼び出される関数です。
    *   この変更により、`8l`リンカは`D_SBIG`タイプのデータブロックを適切に処理できるようになります。具体的には、デバッグ情報（`debug['a']`が有効な場合）を出力し、`p->to.sbig`配列からデータを`buf.dbuf`にコピーするロジックが追加されています。これは、Goプログラムが生成する可能性のある特定の大きなデータ構造や初期化データを、32ビット環境でも正しくリンクするための低レベルな対応です。

4.  **ライブラリ検索パスの拡張**:
    *   `src/cmd/8l/l.h`に`EXTERN char* LIBDIR;`が追加され、リンカがライブラリを検索する際に使用するディレクトリパスを外部から設定できるようになりました。
    *   `src/cmd/8l/obj.c`の`addlib`関数が大幅に修正され、ライブラリの検索ロジックが改善されました。
    *   新しい検索順序は以下の通りです。
        1.  現在のディレクトリ (`./`)
        2.  `-L`オプションで指定された`LIBDIR`
        3.  `goroot/pkg`
    *   この変更により、開発者はGoの標準ライブラリパスだけでなく、現在のプロジェクトディレクトリや特定のカスタムライブラリディレクトリに配置されたライブラリもリンカに認識させることができるようになり、ビルドシステムの柔軟性が向上します。

5.  **`DUPOK`フラグの処理**:
    *   `src/cmd/8l/obj.c`のシンボル処理ループ内で、`p->from.scale & DUPOK`が真の場合に`s->dupok = 1;`がセットされるようになりました。
    *   これは、リンカがシンボルを解決する際に、`DUPOK`フラグが設定されたシンボル（重複が許容されるシンボル）を正しく識別し、重複エラーを発生させずに処理を続行するためのメカニズムです。これにより、特定のリンキングシナリオでの不必要なエラーが回避され、リンカの挙動がより正確になります。

これらの変更は、Go言語が初期段階で直面していたクロスプラットフォーム対応、リンカの堅牢性、および開発者の利便性に関する課題を解決するために不可欠なものでした。

## コアとなるコードの解説

### `PtrSize`のアーキテクチャ固有定義

`src/cmd/ld/go.c`から`PtrSize`の定義が削除され、各アーキテクチャ固有のリンカファイルに移動されました。

**`src/cmd/6l/go.c`**:
```c
enum
{
	PtrSize = 8
};
#include "../ld/go.c"
```
64ビットアーキテクチャ（AMD64）向けのリンカ`6l`では、ポインタサイズが8バイトであることを明示的に定義しています。

**`src/cmd/8l/go.c`**:
```c
// Copyright 2009 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

#include "l.h"
enum
{
	PtrSize = 4
};
#include "../ld/go.c"
```
32ビットアーキテクチャ（386）向けのリンカ`8l`では、ポインタサイズが4バイトであることを明示的に定義しています。
これにより、`../ld/go.c`に含まれる共通のリンカロジックは、インクルード元のファイルで定義された`PtrSize`の値に基づいて動作するため、各アーキテクチャで正しいポインタサイズが使用されることが保証されます。

### `src/cmd/8l/obj.c`における`usage()`関数と引数解析の変更

`8l`リンカの`obj.c`ファイルに`usage()`関数が追加され、コマンドライン引数解析が`EARGF(usage())`マクロを使用するように変更されました。

```c
void
usage(void)
{
	fprint(2, "usage: 8l [-options] [-E entry] [-H head] [-L dir] [-T text] [-R rnd] [-o out] files...\\n");
	exits("usage");
}

// ... main関数内の引数解析部分 ...
	case 'o': /* output to (next arg) */
		outfile = EARGF(usage());
		break;
	case 'E':
		INITENTRY = EARGF(usage());
		break;
	case 'H':
		HEADTYPE = atolwhex(EARGF(usage()));
		break;
	case 'L':
		LIBDIR = EARGF(usage());
		break;
	case 'T':
		INITTEXT = atolwhex(EARGF(usage()));
		break;
	case 'D':
		INITDAT = atolwhex(EARGF(usage()));
		break;
	case 'R':
		INITRND = atolwhex(EARGF(usage()));
		break;
// ...
```
`usage()`関数は、リンカの正しい使用法を標準エラー出力に表示し、プログラムを終了させます。`EARGF(usage())`マクロは、引数が不足している場合にこの`usage()`関数を呼び出すことで、引数解析のエラーハンドリングを統一し、ユーザーへのフィードバックを明確にします。

### `src/cmd/8l/obj.c`における`addlib`関数のライブラリ検索ロジック

`addlib`関数は、リンカがライブラリファイルを検索する際のロジックを定義しています。このコミットにより、検索パスが拡張されました。

```c
// ...
	if(search) {
		// try dot, -L "libdir", and then goroot.
		snprint(pname, sizeof pname, "./%s", name);
		if(access(pname, AEXIST) < 0 && LIBDIR != nil)
			snprint(pname, sizeof pname, "%s/%s", LIBDIR, name);
		if(access(pname, AEXIST) < 0)
			snprint(pname, sizeof pname, "%s/pkg/%s", goroot, name);
		strcpy(name, pname);
	}
// ...
```
`search`フラグが設定されている場合、リンカは以下の順序でライブラリを検索します。
1.  現在のディレクトリ (`./`)
2.  `-L`オプションで指定された`LIBDIR`（`LIBDIR`が設定されている場合）
3.  `goroot/pkg`ディレクトリ

この優先順位により、開発者はプロジェクト固有のライブラリを現在のディレクトリに配置したり、特定のパスにライブラリコレクションを設定したりする柔軟性が得られます。

### `src/cmd/8l/asm.c`における`D_SBIG`の処理

`datblk`関数は、リンカがデータブロックを処理する際のロジックを含んでいます。このコミットで`D_SBIG`という新しいケースが追加されました。

```c
// ...
	case D_SBIG:
		if(debug['a'] && i == 0) {
			Bprint(&bso, pcstr, l+s+INITDAT);
			for(j=0; j<c; j++)
				Bprint(&bso, "%.2ux", p->to.scon[j] & 0xff);
			Bprint(&bso, "\\t%P\\n", curp);
		}
		for(; i<c; i++) {
			buf.dbuf[l] = p->to.sbig[i];
			l++;
		}
		break;
// ...
```
このコードは、`D_SBIG`タイプのデータブロックを処理します。デバッグモード（`debug['a']`）が有効な場合、データの内容を標準出力に表示します。その後、`p->to.sbig`配列からデータを`buf.dbuf`（データバッファ）にコピーし、リンカがこの大きなデータブロックを最終的な実行可能ファイルに正しく組み込めるようにします。

### `src/cmd/8l/obj.c`における`DUPOK`フラグの処理

シンボル処理ループ内で、`DUPOK`フラグが設定されているシンボルに対する処理が追加されました。

```c
// ...
	case ADYNT:
		// ...
		if(p->to.offset > s->value)
			s->value = p->to.offset;
		if(p->from.scale & DUPOK)
			s->dupok = 1;
		goto loop;
// ...
```
`p->from.scale & DUPOK`が真の場合、つまりシンボルに`DUPOK`フラグが設定されている場合、そのシンボルの`s->dupok`メンバーが`1`に設定されます。これにより、リンカは後続の処理でこのシンボルが重複してもエラーとしないように動作します。これは、特定のリンキングシナリオ（例えば、弱いシンボルや、複数のオブジェクトファイルで定義されても問題ないシンボル）において、リンカが正しく動作するために重要です。

# [インデックス 23396] ファイルの概要

このコミットは、Goコンパイラ（`cmd/internal/gc`）の型チェックフェーズにおけるバグ修正に関するものです。具体的には、`append`組み込み関数が複数の戻り値を持つ関数呼び出しの結果を不正に受け入れてしまう問題を修正し、より早期に正確な型エラーを報告するように改善しています。

which is that bad code was slipping through the type checker

[https://github.com/golang/go/commit/3f209abb2954bfb89e3dbd28ed0a622a6fe33242](https://github.com/golang/go/commit/3f209abb2954bfb89e3dbd28ed0a622a6fe33242)

## 元コミット内容

Goコンパイラの型チェッカーが、`append(f())` のような形式で、複数の戻り値を持つ関数 `f` の結果を `append` 関数に不正に渡した場合に、そのエラーを適切に検出できていなかった問題を修正します。この問題により、不正なコードが型チェックをすり抜け、コンパイラのバックエンドで初めて型エラーとして検出されていました。この修正は、`append`関数の内部実装変更によって露呈した、型チェッカーの根本的な欠陥に対処するものです。

## 変更の背景

Go言語の`append`組み込み関数は、スライスに要素を追加するために使用されます。通常、`append(slice, elem1, elem2, ...)` のように、スライスとそれに続く個々の要素、または`append(slice, anotherSlice...)` のように別のスライスを展開して渡す形式で利用されます。

このコミット以前のGoコンパイラでは、`append(f())` のように、複数の戻り値を持つ関数 `f` の呼び出し結果を直接 `append` に渡した場合に、型チェッカーがその不正を適切に検出できていませんでした。例えば、`func f() (int, int)` のような関数があったとして、`append(mySlice, f())` と書いた場合、`f()` は2つの`int`値を返しますが、`append`は個々の要素としてこれらを受け取ることはできません（`append(mySlice, f() ...)` のように展開する必要があるか、または`append`の引数として適切でない）。

コミットメッセージによると、この問題は「今日の以前の修正は残せるが、それは根本的な問題に対する一時しのぎに過ぎない」と述べられています。これは、以前にこの種の問題に対する何らかの対処が行われたものの、それは症状を抑えるものであり、型チェッカーが不正なコードを許容してしまうという根本原因を解決していなかったことを示唆しています。

この根本的な問題が露呈したのは、`append`関数の内部実装が変更された際でした。新しい`append`の実装が以前と同じ一時変数を使用しなくなったことで、これまで型チェッカーをすり抜けていた不正なコードが、新しい実装ではテストで失敗するようになったため、型チェッカーの不備が明らかになりました。コンパイラは、可能な限り早い段階でエラーを検出するべきであり、型エラーがバックエンドまで持ち越されるのは望ましくありません。このコミットは、この型チェックのギャップを埋め、より堅牢なコンパイルプロセスを実現することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびGoコンパイラに関する前提知識が必要です。

1.  **Go言語の`append`組み込み関数**:
    *   `append(s []T, elems ...T) []T`: スライス `s` に要素 `elems` を追加し、新しいスライスを返します。`elems` は個々の要素、または別のスライスを`...`で展開した形式で指定できます。
    *   `append(s []T, t ...U) []T`: ここで `U` は `T` に代入可能である必要があります。
    *   複数の戻り値を持つ関数 `f()` の結果を直接 `append(s, f())` のように渡すことは、Go言語の仕様上、通常は不正です。`f()`が返す複数の値は、`append`の可変長引数リストの個々の要素として扱われるわけではないためです。

2.  **Goコンパイラの構造 (`cmd/internal/gc`)**:
    *   `cmd/internal/gc` は、Go言語の公式コンパイラ（`go tool compile`）の主要部分です。
    *   **フロントエンド**: ソースコードの字句解析、構文解析、抽象構文木（AST）の構築、そして**型チェック**を行います。型チェックは、プログラムがGo言語の型規則に準拠しているかを確認する非常に重要なフェーズです。
    *   **バックエンド**: 型チェックを通過したASTを中間表現に変換し、最適化を行い、最終的に機械語コードを生成します。
    *   型チェッカーの役割は、不正な型を持つコードがバックエンドに到達する前にエラーとして報告することです。これにより、コンパイルエラーがより明確になり、デバッグが容易になります。

3.  **多値戻り関数 (Multiple Return Values)**:
    *   Go言語の関数は複数の値を返すことができます（例: `func f() (int, string)`）。
    *   これらの戻り値は、変数リストに代入するか、または他の関数呼び出しの引数として渡す際に、その関数の引数リストの個々の要素として展開される場合があります（例: `x, y := f()` や `fmt.Println(f())`）。しかし、`append`のような特定の組み込み関数では、この自動展開の挙動が異なるため、注意が必要です。

4.  **`typecheck.go`**:
    *   Goコンパイラのソースコードにおいて、`src/cmd/internal/gc/typecheck.go` は型チェックロジックの大部分を担うファイルです。ASTノードの型を決定し、型規則に違反がないか検証します。
    *   `Istype(t, TSTRUCT)`: 型 `t` が構造体型であるかをチェックします。関数の戻り値の型は、内部的には特殊な構造体として表現されることがあります。
    *   `t.Funarg != 0`: 型 `t` が関数の引数または戻り値の型を表す場合に設定されるフラグです。これが0でない場合、その型が関数に関連するものであることを示します。
    *   `assignconv(dst, src, context)`: `src` 型の値を `dst` 型に代入変換できるかをチェックし、必要であれば変換ノードを生成します。
    *   `assignop(dst, src, context)`: `src` 型の値を `dst` 型に代入可能であるかをチェックします。成功すれば非ゼロ、失敗すれば0を返します。
    *   `Yyerror(...)`: コンパイラエラーを報告するための関数です。

## 技術的詳細

このコミットの技術的な核心は、`append`組み込み関数に渡される引数の型チェックを強化することにあります。特に、複数の戻り値を持つ関数呼び出しが`append`の引数として直接渡された場合の処理を改善しています。

変更前の`typecheck.go`では、`append`の引数リストを処理する際に、多値戻り関数の結果を適切に扱えていませんでした。`Istype(t, TSTRUCT) && t.Funarg != 0` の条件で多値戻り関数を検出しようとはしていましたが、その後の処理 (`t = t.Type` や `t = t.Type.Type`) が、`append`の引数として渡された個々の値の型と、スライスの要素型との互換性を正確に検証するのに不十分でした。結果として、不正な型を持つ引数が型チェックを通過し、コンパイラのバックエンドでエラーとなるか、あるいは未定義の動作を引き起こす可能性がありました。

このコミットでは、以下の主要な変更が導入されました。

1.  **`funarg`変数の導入**:
    `append`の引数として多値戻り関数が検出された場合、その関数の完全な戻り値型情報（`t`）を`funarg`という新しい変数に保存します。これにより、元の多値戻り関数の型情報を失うことなく、`append`が期待するスライス要素の型 (`t = t.Type.Type`) を設定できます。

2.  **多値戻り関数に対する専用の型チェックロジック**:
    `funarg`が`nil`でない（つまり、`append`の引数として多値戻り関数が渡された）場合、新しい`if funarg != nil`ブロックが実行されます。このブロック内で、多値戻り関数の各戻り値の型 (`funarg.Type.Down`を辿って取得) と、`append`が操作するスライスの要素型 (`n.Type.Type`) との間の代入互換性 (`assignop`) が個別にチェックされます。
    *   `for t := funarg.Type.Down; t != nil; t = t.Down`: これは、多値戻り関数の各戻り値の型を順番に取得するためのイテレーションです。
    *   `if assignop(t.Type, n.Type.Type, nil) == 0`: 各戻り値の型 `t.Type` が、スライスの要素型 `n.Type.Type` に代入可能でない場合 (`assignop`が0を返す場合)、コンパイラエラー `Yyerror` が発生します。エラーメッセージは `"cannot append %v value to []%v"` となり、どの型の値がどの型のスライスに`append`できないのかを明確に示します。

3.  **既存の単一値/スライス展開処理の分離**:
    多値戻り関数でない通常の`append`引数（単一の要素や展開されたスライス）の処理は、`else`ブロックに移動され、引き続き`assignconv`を使用して型変換とチェックが行われます。これにより、多値戻り関数に対する特殊な処理と、それ以外の一般的な`append`引数に対する処理が明確に分離され、コードの可読性と保守性が向上しています。

この修正により、Goコンパイラは`append(f())`のような不正なコードを、より早い段階（型チェックフェーズ）で、より正確なエラーメッセージと共に検出できるようになりました。これは、コンパイラの堅牢性を高め、開発者がGoコードの型に関する問題を早期に特定し、修正するのに役立ちます。

## コアとなるコードの解説

`src/cmd/internal/gc/typecheck.go` の変更点について詳しく解説します。

1.  **`funarg`変数の導入と多値戻り関数の型情報の保持**:
    変更前は、多値戻り関数 (`t.Funarg != 0`) の型 `t` が検出されると、その型情報が直接 `t = t.Type` や `t = t.Type.Type` によって上書きされていました。これにより、`append`の引数として渡された関数が返す個々の値の型を正確に追跡することが困難になっていました。
    変更後には `var funarg *Type` が導入され、`if Istype(t, TSTRUCT) && t.Funarg != 0` の条件が真の場合に、元の多値戻り関数の型情報 `t` が `funarg` に保存されます (`funarg = t`)。その後、`t` は `append` が期待するスライスの要素型 (`t = t.Type.Type`) に更新されます。これにより、`append`のターゲットスライスの要素型と、多値戻り関数の各戻り値の型を独立して参照できるようになります。

2.  **多値戻り関数に対する厳密な型チェックロジック**:
    `append`の引数リストを処理するループの前に、`if funarg != nil` という新しい条件分岐が追加されました。
    *   このブロックは、`append`の引数として多値戻り関数が渡された場合にのみ実行されます。
    *   `for t := funarg.Type.Down; t != nil; t = t.Down` ループは、`funarg`に保存された多値戻り関数の型情報から、その関数が返す個々の戻り値の型を順番に取得します。`funarg.Type.Down` は、関数の最初の戻り値の型を表し、`t.Down` を辿ることで次の戻り値の型にアクセスできます。
    *   `if assignop(t.Type, n.Type.Type, nil) == 0` の行が、この修正の核心です。ここで、多値戻り関数の個々の戻り値の型 (`t.Type`) が、`append`が操作するスライスの要素型 (`n.Type.Type`) に代入可能であるかをチェックします。`assignop`が0を返す場合、代入が不正であることを意味します。
    *   代入が不正な場合、`Yyerror("cannot append %v value to []%v", t.Type, n.Type.Type)` が呼び出され、コンパイルエラーが報告されます。このエラーメッセージは、どの型の値がどの型のスライスに`append`できないのかを具体的に示すため、開発者にとって非常に分かりやすいものとなります。

3.  **既存の単一値/スライス展開処理の維持**:
    `else`ブロックには、`funarg`が`nil`の場合（つまり、`append`の引数が多値戻り関数ではない場合）の既存の処理が残されています。この処理は、単一の要素や`...`で展開されたスライスが`append`に渡された場合の型チェックと型変換 (`assignconv`) を行います。これにより、多値戻り関数に対する特殊なケースと、それ以外の一般的なケースが明確に区別され、それぞれのケースで適切な型チェックが適用されるようになります。

`test/fixedbugs/issue9521.go` の変更は、この新しい型チェックロジックが期待通りに機能することを確認するためのものです。
*   `_ = append(f())` のテストケースでは、`f()` が `(_, _ []int)` と2つの `[]int` を返すため、`append`に直接渡すことは不正です。修正前は `"cannot use _"` という一般的なエラーでしたが、修正後は `"cannot append []int value to []int"` という、より具体的な型不一致のエラーが期待されるようになりました。
*   `func g() (x []int, y float64)` と `_ = append(g())` という新しいテストケースが追加されました。`g()` は `[]int` と `float64` を返します。もし `append` が `[]int` スライスに対して呼び出された場合、`float64` は `[]int` の要素型に代入できないため、`"cannot append float64 value to []int"` というエラーが正しく報告されることを検証します。

これらの変更により、Goコンパイラは`append`関数の誤用に対する型チェックを大幅に強化し、開発者がより早期に、より明確なフィードバックを得られるようになりました。

# [インデックス 27406] ファイルの概要

このコミットは、Goランタイムのワークスチールロジックにおける擬似乱数生成器 (PRNG) の品質に起因する問題を改善し、より効率的かつ確実にアイドル状態のプロセッサ (P) が他のPからゴルーチン (G) をスチールできるようにするための変更です。特に、ランダムなスチール試行において一部のPが頻繁に見落とされてしまう問題を解決し、すべてのPが公平にスチール対象となるように改良されています。

## 変更の背景

Goランタイムのスケジューラは、システム内の利用可能なプロセッサ (P) 間でゴルーチン (G) を効率的に分散させるためにワークスチール (Work Stealing) というメカニズムを採用しています。これは、アイドル状態のPが、他のビジーなPからゴルーチンを「盗む」ことで、システム全体の利用率を向上させる手法です。

このコミット以前のワークスチールロジックでは、アイドル状態のPが他のPからゴルーチンをスチールしようとする際、`GOMAXPROCS` の4倍の回数だけランダムにPを選択し、そのPのローカルキューからゴルーチンをスチールしようと試みていました。しかし、このランダム選択に使用されていた擬似乱数生成器 (PRNG) の品質が低かったため、期待に反して一部のPが頻繁に選択されず、見落とされてしまうという問題が発生していました。

コミットメッセージに示されている実験結果は、この問題の深刻さを明確に示しています。例えば、`GOMAXPROCS=3` の場合、100万回の試行のうち10万回以上で1つのPが見落とされ、3571回で2つのPが見落とされていました。`GOMAXPROCS` の値が大きくなるにつれて、見落とされるPの数も増え、その頻度も高くなっています。

Pが見落とされたとしても、最終的にはPを解放して再度すべてのPをチェックするため、システムが完全にアイドル状態になることはありませんでした。しかし、この非効率なランダム選択は、以下のような「不快な状況」を引き起こす可能性がありました。

1.  アイドル状態のPが、作業を持つPを見落とす。
2.  Pを解放し、再度すべてのPをチェックする。
3.  作業を発見し、Pを再取得する。
4.  再びランダムスチールを試みるが、同じPを見落とす。
5.  このサイクルが繰り返され、不必要な遅延やCPUサイクルの浪費が発生する。

この問題は、特に並列度が低いプログラムや、一部のPに作業が集中するようなシナリオで、システムの応答性やスループットに悪影響を与える可能性がありました。このコミットは、このランダムスチールロジックを改善し、すべてのPが確実にスチール対象となるようにすることで、より堅牢で効率的なスケジューリングを実現することを目的としています。また、周囲に誰もいない（ほとんどのPがアイドル状態である）場合にスピニングモードに入ってスチールを試みるのを避けることで、無駄なCPU消費を抑える改善も含まれています。

## 前提知識の解説

このコミットの理解には、以下のGoランタイムの概念と数学的知識が不可欠です。

### Goランタイムスケジューラ (M, P, Gモデル)

Goランタイムのスケジューラは、M (Machine/OSスレッド)、P (Processor/論理プロセッサ)、G (Goroutine) の3つのエンティティで構成されるM:Nスケジューリングモデルを採用しています。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。ユーザーが記述する並行処理の最小単位であり、数MBのスタックを持つOSスレッドとは異なり、初期スタックサイズは数KBと非常に小さく、必要に応じて動的に拡張されます。
*   **M (Machine)**: OSスレッドに相当します。Goランタイムは、OSスケジューラによってMをCPUコアに割り当ててもらいます。MはGを実行し、Pと連携して動作します。
*   **P (Processor)**: 論理プロセッサ、またはコンテキストと考えることができます。PはMにアタッチされ、Gの実行に必要なリソース（ローカル実行キュー、メモリキャッシュなど）を提供します。`GOMAXPROCS` 環境変数によって、同時に実行可能なPの最大数が決定されます。各Pはローカルな実行キューを持ち、そこに実行可能なGを保持します。

スケジューラは、MがPにアタッチされ、PがGを実行するという形で動作します。Mがシステムコールなどでブロックされると、Pは別のMに引き渡され、Gの実行が継続されます。

### ワークスチール (Work Stealing)

ワークスチールは、並行ランタイムシステムで負荷分散とスループット向上を実現するための一般的な手法です。Goランタイムでは、以下のシナリオでワークスチールが発生します。

1.  **Pのローカルキューが空になった場合**: あるPが自身のローカル実行キューに実行可能なGがなくなった場合、そのPはアイドル状態になります。
2.  **他のPからのスチール**: アイドル状態のPは、他のビジーなPのローカル実行キューからゴルーチンを「盗む」（スチールする）ことを試みます。これにより、アイドル状態のPが有効活用され、システム全体の並列度が維持されます。
3.  **グローバル実行キュー**: ローカルキューが空で、他のPからのスチールも失敗した場合、Pはグローバル実行キューからGを取得しようとします。

ワークスチールは、特に非均一なワークロードにおいて、システム全体の利用率を最大化し、レイテンシを削減する上で非常に重要です。

### 擬似乱数生成器 (PRNG) の品質と均一性

擬似乱数生成器 (PRNG) は、初期シード値に基づいて決定論的なアルゴリズムで乱数シーケンスを生成するものです。真の乱数とは異なり、PRNGは周期性を持つため、その品質は生成される乱数の統計的特性（均一性、独立性など）によって評価されます。

このコミットの背景にある問題は、GoランタイムがワークスチールでPを選択する際に使用していたPRNGの品質が低かったことです。品質の低いPRNGは、特定の数値範囲内で乱数が均一に分布せず、偏りが発生することがあります。この偏りにより、一部のPが他のPよりも頻繁に選択されたり、逆にほとんど選択されなかったりする状況が生じました。結果として、ランダムスチールが「ランダム」ではなくなり、特定のPが見落とされ、効率的な負荷分散が妨げられていました。

### 最大公約数 (GCD) と互いに素な数 (Coprime Numbers)

このコミットで導入された新しいワークスチールロジックの核となるのは、最大公約数 (GCD) と互いに素な数 (coprime numbers) の数学的特性です。

*   **最大公約数 (GCD - Greatest Common Divisor)**: 2つ以上の整数に共通する約数のうち、最大のものです。例えば、12と18のGCDは6です。
*   **互いに素な数 (Coprime Numbers / Relatively Prime Numbers)**: 2つの整数が互いに素であるとは、それらの最大公約数が1である場合を指します。例えば、7と10は互いに素です（GCD(7, 10) = 1）。

この数学的特性がワークスチールにどのように応用されるかというと、`N` 個のPがある場合、`N` と互いに素な数 `X` を増分として使用して `(i + X) % N` のシーケンスを生成すると、`i` の初期値に関わらず、`0` から `N-1` までのすべてのPを重複なく一度ずつ巡回できるという性質があります。これは、モジュロ演算における群論の概念に基づいています。この性質を利用することで、PRNGの品質に依存せず、すべてのPを確実にスチール対象として巡回できるようになります。

## 技術的詳細

このコミットの主要な技術的改善点は、ワークスチールにおけるPの選択方法を、低品質なPRNGによる単純なランダム選択から、数学的保証に基づいた巡回的な選択へと変更したことです。これにより、すべてのPが確実にスチール対象として考慮されるようになります。

### `randomOrder` および `randomEnum` 構造体の導入

新しいワークスチールロジックを実装するために、`randomOrder` と `randomEnum` という2つの新しい構造体が導入されました。

*   **`randomOrder`**:
    *   `count uint32`: 現在の `GOMAXPROCS` の値、つまりPの総数を保持します。
    *   `coprimes []uint32`: `count` と互いに素な数のリストを保持します。これらの数は、Pを巡回する際の「増分」として使用されます。

*   **`randomEnum`**:
    *   `i uint32`: 現在の巡回ステップ数を追跡します。
    *   `count uint32`: `randomOrder` と同様にPの総数を保持します。
    *   `pos uint32`: 現在巡回しているPのインデックスを保持します。
    *   `inc uint32`: 次のPを計算するための増分値です。これは `randomOrder.coprimes` から選択されます。

### `gcd` 関数の実装

`gcd(a, b uint32) uint32` 関数は、2つの符号なし32ビット整数の最大公約数を計算します。これはユークリッドの互除法を用いて実装されており、`randomOrder.reset` メソッドで互いに素な数を特定するために使用されます。

```go
func gcd(a, b uint32) uint32 {
	for b != 0 {
		a, b = b, a%b
	}
	return a
}
```

### `randomOrder.reset(count uint32)` メソッド

このメソッドは、`GOMAXPROCS` の値が変更された際（例えば `runtime.GOMAXPROCS` の呼び出し時）に呼び出され、`randomOrder` 構造体を初期化します。

1.  `ord.count` を新しいPの総数 `count` に設定します。
2.  `ord.coprimes` スライスをクリアします。
3.  `1` から `count` までの各整数 `i` について、`gcd(i, count)` が `1` であるかどうかをチェックします。
4.  `gcd(i, count) == 1` であれば、`i` は `count` と互いに素であるため、`ord.coprimes` に追加します。

これにより、`count` と互いに素なすべての正の整数が `coprimes` リストに格納されます。

### `randomOrder.start(i uint32) randomEnum` メソッド

このメソッドは、新しいPの巡回を開始する際に呼び出されます。

1.  `randomEnum` 構造体を初期化します。
2.  `pos` (開始位置) は、入力 `i` を `count` で割った余り (`i % ord.count`) に設定されます。これにより、巡回開始位置がランダムに分散されます。
3.  `inc` (増分) は、`ord.coprimes` リストから、入力 `i` を `len(ord.coprimes)` で割った余り (`i % uint32(len(ord.coprimes))`) に基づいて選択されます。これにより、異なる巡回で異なる増分が使用され、さらにランダム性が導入されます。

### `randomEnum.next()` および `randomEnum.position()` メソッド

*   `randomEnum.next()`: 現在の巡回ステップ `enum.i` をインクリメントし、次のPのインデックス `enum.pos` を `(enum.pos + enum.inc) % enum.count` という式で計算します。このモジュロ演算と互いに素な増分 `inc` の組み合わせにより、`0` から `count-1` までのすべてのPが重複なく一度ずつ巡回されることが保証されます。
*   `randomEnum.position()`: 現在のPのインデックス `enum.pos` を返します。

### `findrunnable` 関数内の変更

`findrunnable` 関数は、実行可能なゴルーチンを見つけるためのGoスケジューラの中心的な関数です。この関数内のワークスチールロジックが大幅に変更されました。

1.  **現在のPのキャッシュ**: `_p_ := _g_.m.p.ptr()` が導入され、現在のPへのポインタが `_p_` にキャッシュされます。これにより、コードの可読性が向上し、`_g_.m.p.ptr()` を繰り返し呼び出すオーバーヘッドが削減されます。
2.  **アイドル状態のPが多い場合の最適化**:
    ```go
    procs := uint32(gomaxprocs)
    if atomic.Load(&sched.npidle) == procs-1 {
        // Either GOMAXPROCS=1 or everybody, except for us, is idle already.
        // New work can appear from returning syscall/cgocall, network or timers.
        // Neither of that submits to local run queues, so no point in stealing.
        goto stop
    }
    ```
    このコードブロックは、現在のPを除くすべてのPがアイドル状態である場合（または `GOMAXPROCS=1` の場合）、ワークスチールを試みずに直接 `stop` ラベルにジャンプするように変更されました。これは、この状況ではスチールによって新しい作業が見つかる可能性が非常に低く、無駄なスチール試行を避けるための最適化です。新しい作業は、システムコールからの復帰、Cgo呼び出し、ネットワークイベント、タイマーなどによって発生しますが、これらはローカル実行キューに直接投入されるわけではないため、スチールは効果がありません。
3.  **ワークスチールループの変更**:
    ```go
    for i := 0; i < 4; i++ {
        for enum := stealOrder.start(fastrand1()); !enum.done(); enum.next() {
            // ...
            if gp := runqsteal(_p_, allp[enum.position()], stealRunNextG); gp != nil {
                return gp, false
            }
        }
    }
    ```
    以前は `4*gomaxprocs` 回のランダムなスチール試行が行われていましたが、新しいロジックでは外側のループが `4` 回に固定され、内側のループで `stealOrder` を使用してすべてのPを巡回するようになりました。
    *   `stealOrder.start(fastrand1())`: `fastrand1()` はシードとして使用され、`randomOrder` から新しい `randomEnum` を生成します。これにより、各Pの巡回開始位置と増分がランダムに選択され、異なるスチール試行で異なる巡回順序が保証されます。
    *   `!enum.done()` と `enum.next()`: `randomEnum` のメソッドを使用して、`0` から `GOMAXPROCS-1` までのすべてのPを重複なく巡回します。
    *   `allp[enum.position()]`: `enum.position()` によって得られたPのインデックスを使用して、対象のPからゴルーチンをスチールします。

この変更により、ランダムスチールが真に「ランダム」な順序で「すべての」Pを網羅するようになり、低品質なPRNGによる見落としの問題が根本的に解決されました。

### テストの追加

```go
	}
	// ...
	// random steal from other P's
	for i := 0; i < 4; i++ { // 外側のループは4回に固定
		for enum := stealOrder.start(fastrand1()); !enum.done(); enum.next() { // randomOrder/randomEnum を使用してPを巡回
			if sched.gcwaiting != 0 {
				goto top
			}
			stealRunNextG := i > 2 // first look for ready queues with more than 1 g
			if gp := runqsteal(_p_, allp[enum.position()], stealRunNextG); gp != nil { // enum.position() で得られたPからスチール
				return gp, false
			}
		}
	}
// ...
```
`findrunnable` 関数では、まず現在のPへのポインタが `_p_` に格納され、以降の処理でこの `_p_` が利用されます。これにより、コードの簡潔さと効率が向上しています。
ワークスチールロジックでは、`GOMAXPROCS` の値が `procs` に格納され、`atomic.Load(&sched.npidle) == procs-1` の条件で、現在のP以外のすべてのPがアイドル状態であるかをチェックします。この条件が真の場合、スチールを試みても無駄であると判断し、`goto stop` で処理をスキップします。
実際のワークスチールループは、外側の `for i := 0; i < 4; i++` と内側の `for enum := stealOrder.start(fastrand1()); !enum.done(); enum.next()` で構成されます。外側のループは固定回数実行され、内側のループでは `stealOrder` を利用して、`GOMAXPROCS` 個のPすべてを重複なく巡回します。`fastrand1()` は巡回の開始シードとして機能し、異なる巡回順序を生成します。`enum.position()` は現在スチール対象となっているPのインデックスを返し、`runqsteal` 関数がそのPからゴルーチンをスチールしようと試みます。

### `randomOrder`, `randomEnum`, `gcd` の実装

```go
var stealOrder randomOrder // グローバル変数として定義

// randomOrder/randomEnum are helper types for randomized work stealing.
// They allow to enumerate all Ps in different pseudo-random orders without repetitions.
// The algorithm is based on the fact that if we have X such that X and GOMAXPROCS
// are coprime, then a sequences of (i + X) % GOMAXPROCS gives the required enumeration.
type randomOrder struct {
	count    uint32
	coprimes []uint32
}

type randomEnum struct {
	i     uint32
	count uint32
	pos   uint32
	inc   uint32
}

func (ord *randomOrder) reset(count uint32) {
	ord.count = count
	ord.coprimes = ord.coprimes[:0]
	for i := uint32(1); i <= count; i++ {
		if gcd(i, count) == 1 { // count と互いに素な数を収集
			ord.coprimes = append(ord.coprimes, i)
		}
	}
}

func (ord *randomOrder) start(i uint32) randomEnum {
	return randomEnum{
		count: ord.count,
		pos:   i % ord.count, // 開始位置をランダムに決定
		inc:   ord.coprimes[i%uint32(len(ord.coprimes))], // 増分をランダムに選択
	}
}

func (enum *randomEnum) done() bool {
	return enum.i == enum.count // すべてのPを巡回したか
}

func (enum *randomEnum) next() {
	enum.i++
	enum.pos = (enum.pos + enum.inc) % enum.count // 次のPのインデックスを計算
}

func (enum *randomEnum) position() uint32 {
	return enum.pos // 現在のPのインデックスを返す
}

func gcd(a, b uint32) uint32 {
	for b != 0 {
		a, b = b, a%b
	}
	return a // ユークリッドの互除法
}
```
`stealOrder` はグローバル変数として定義され、`GOMAXPROCS` の変更時に `procresize` 関数によって `reset` されます。`randomOrder.reset` は、現在のPの総数 `count` と互いに素なすべての数を `coprimes` スライスに格納します。この計算には `gcd` 関数が使用されます。
`randomOrder.start` は、`fastrand1()` から得られるシード `i` を基に、巡回の開始位置 `pos` と増分 `inc` を決定し、新しい `randomEnum` を返します。`inc` は `coprimes` リストから選択されるため、`count` と互いに素であることが保証されます。
`randomEnum.next` は、現在のPのインデックス `pos` に `inc` を加算し、`count` でモジュロ演算を行うことで、次のPのインデックスを計算します。この数学的特性により、`0` から `count-1` までのすべてのPが重複なく一度ずつ巡回されることが保証されます。`randomEnum.done` は、すべてのPを巡回し終えたかを判定します。

### テストコード `src/runtime/proc_runtime_test.go`

```go
// ...
func RunStealOrderTest() {
	var ord randomOrder
	for procs := 1; procs <= 64; procs++ { // GOMAXPROCS を1から64までテスト
		ord.reset(uint32(procs))
		// ...
		for co := 0; co < len(ord.coprimes); co++ { // 各互いに素な増分についてテスト
			enum := ord.start(uint32(co))
			checked := make([]bool, procs)
			for p := 0; p < procs; p++ {
				x := enum.position()
				if checked[x] {
					println("procs:", procs, "inc:", enum.inc)
					panic("duplicate during enumeration") // 重複があればパニック
				}
				checked[x] = true
				enum.next()
			}
			if !enum.done() {
				panic("not done") // すべてのPを巡回し終えていなければパニック
			}
		}
	}
}
```
`RunStealOrderTest` は、`GOMAXPROCS` の値を `1` から `64` まで変化させながら、`randomOrder` と `randomEnum` のロジックが正しく機能するかを検証します。具体的には、各 `procs` の値と、`procs` と互いに素な各増分 `inc` の組み合わせについて、`randomEnum` が `procs` 個のPを重複なく、かつすべて巡回できることを確認します。重複や未巡回があれば `panic` を発生させ、テストを失敗させます。これにより、新しいスチールロジックの数学的正確性が保証されます。

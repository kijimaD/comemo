## 変更の背景

Go言語の初期設計において、ゴルーチンは非常に軽量な並行処理の単位として導入されました。しかし、従来のプログラミング言語におけるスレッドのように固定サイズの大きなスタックを割り当てると、数百万ものゴルーチンを生成する際にメモリを大量に消費し、効率が低下するという問題がありました。この問題を解決するために、Goランタイムは「スタック分割（Stack Splitting）」または「スタックの動的拡張」というメカニズムを採用しました。

このコミットは、そのスタック分割メカニズムをARMアーキテクチャ（`5l`リンカが担当）に導入するための初期作業です。具体的には、関数呼び出し時にスタックの残量を確認し、不足している場合にランタイムの`morestack`ルーチンを呼び出してスタックを拡張する仕組みの基盤を構築しようとしています。コミットメッセージに「still disabled, doesn't work」とあるように、この時点ではまだ実験的な段階であり、完全には機能していませんでしたが、Goの効率的な並行処理を実現するための重要なステップでした。

## 前提知識の解説

### Goランタイムのスタック管理とスタック分割

Goのゴルーチンは、OSスレッドよりもはるかに小さいスタック（初期サイズは数KB程度）で開始されます。これは、多数のゴルーチンを同時に実行できるようにするためです。しかし、関数呼び出しが深くネストしたり、大きなローカル変数が使用されたりすると、スタックが不足する可能性があります。

Goランタイムは、この問題を解決するために「スタック分割（Stack Splitting）」という技術を使用します。これは、関数が呼び出される前に、現在のスタックポインタが「スタックガード（StackGuard）」と呼ばれる境界値を超えていないかを確認するチェックを挿入するものです。もしスタックが不足しそうであれば、ランタイムの`morestack`ルーチンが呼び出され、新しい、より大きなスタック領域が割り当てられ、既存のスタックの内容が新しいスタックにコピーされます。これにより、ゴルーチンは必要に応じてスタックを動的に拡張でき、メモリを効率的に使用できます。

### Goroutine (G) と Machine (M) の関係

Goランタイムは、ゴルーチンをスケジューリングするためにGPMモデルを使用します。
- **G (Goroutine)**: Goの軽量スレッド。スタック、プログラムカウンタ、レジスタなどの実行コンテキストを持ちます。
- **M (Machine)**: OSスレッド。Gを実行するための実際のOSスレッドです。
- **P (Processor)**: MがGを実行するために必要な論理プロセッサ。

スタック分割の文脈では、`G`構造体には現在のゴルーチンのスタックに関する情報（スタックの開始アドレス、終了アドレス、スタックガード値など）が格納されています。また、`M`構造体はOSスレッドの状態を管理し、`morestack`ルーチンが呼び出された際に必要な情報（例えば、スタック拡張に必要な追加の引数など）を一時的に保持するために使用されることがあります。

### `morestack`ルーチン

`morestack`はGoランタイムに実装されている特別な関数で、スタックが不足した際に呼び出されます。このルーチンは、新しいスタック領域を確保し、現在のスタックの内容を新しい領域にコピーし、実行を新しいスタックに切り替える役割を担います。このプロセスは、ユーザーコードからは透過的に行われます。

### `5l`リンカ

`5l`は、Go言語のツールチェインにおけるARMアーキテクチャ（ARMv5, ARMv6, ARMv7など）向けのリンカです。Goのソースコードはコンパイラ（例: `5g`）によってオブジェクトファイルに変換され、その後、`5l`リンカによって実行可能ファイルにリンクされます。リンカは、オブジェクトファイルを結合し、シンボルを解決し、必要に応じてランタイムサポートコードを挿入する役割を担います。このコミットでは、`5l`がスタック分割チェックコードを生成し、`morestack`ルーチンへの呼び出しを適切に配置できるようにするための変更が加えられています。

## コアとなるコードの解説

上記の`noop.c`の変更箇所は、関数プロローグにスタック分割チェックを挿入するためのロジックの骨格を示しています。

1.  **`if(1)`ブロックと`else { // !NOSPLIT }`ブロック**:
    - `if(1)`は、この時点ではスタック分割機能がまだ有効になっていないことを示唆しています。常に`true`であるため、スタック分割ロジックは実行されず、従来のスタックフレーム設定（`REGLINK`をスタックに保存）のみが行われます。
    - `else`ブロック内が、実際にスタック分割チェックを行うためのコードです。このブロックは、`NOSPLIT`フラグが設定されていない関数（つまり、スタック分割が必要な関数）に対して適用されることを意図しています。

2.  **スタックチェックのロジック（`else`ブロック内）**:
    - `if(autosize < StackBig)`: スタックフレームサイズが`StackBig`（4096バイト）よりも小さい場合にのみ、詳細なスタックチェックを行うことを示唆しています。これは、非常に小さなスタックフレームを持つ関数では、スタックオーバーフローのリスクが低いか、あるいは別の最適化パスで処理されるためかもしれません。
    - `p = appendp(p); // load G.stackguard into R1`: `appendp`を使って新しい命令を挿入し、現在のゴルーチン（`G`）の`stackguard`値をレジスタR1にロードします。`REGG`は`G`構造体へのポインタを保持していると想定されます。
    - `p = appendp(p); p->as = ACMP; ...`: ロードした`stackguard`値と、現在のスタックポインタ（`REGSP`）から`autosize`を引いた値（つまり、関数呼び出し後にスタックがどこまで伸びるか）を比較する命令（`ACMP`）を挿入します。この比較の結果によって、スタックが不足しているかどうかが判断されます。
    - `p = appendp(p); // store autosize in M.morearg`: `autosize`（現在の関数のスタックフレームサイズ）を一時レジスタ（`REGTMP`）にロードし、その後`M`構造体の特定のオフセット（`REGM` + 4）に格納します。これは、`morestack`ルーチンがスタックを拡張する際に、どれだけのスタックが必要かを判断するために使用されます。
    - 同様に、`curtext->to.offset2`（おそらく現在の関数の情報）も`M`構造体の別のオフセット（`REGM` + 8）に格納されます。
    - コメントアウトされた`ABL`命令は、スタックが不足していると判断された場合に`sys·morestack`ルーチンを呼び出すためのものです。この時点ではまだ有効化されていません。

このコードは、Goランタイムがどのようにして関数呼び出しの前にスタックの安全性をチェックし、必要に応じてスタック拡張ルーチンを呼び出すかという、スタック分割の基本的なメカニズムをリンカレベルで実装しようとしていることを示しています。

## 前提知識の解説

### Goランタイムのスタック管理とスタック分割

Goのゴルーチンは、OSスレッドよりもはるかに小さいスタック（初期サイズは数KB程度）で開始されます。これは、多数のゴルーチンを同時に実行できるようにするためです。しかし、関数呼び出しが深くネストしたり、大きなローカル変数が使用されたりすると、スタックが不足する可能性があります。

Goランタイムは、この問題を解決するために「スタック分割（Stack Splitting）」という技術を使用します。これは、関数が呼び出される前に、現在のスタックポインタが「スタックガード（StackGuard）」と呼ばれる境界値を超えていないかを確認するチェックを挿入するものです。もしスタックが不足しそうであれば、ランタイムの`morestack`ルーチンが呼び出され、新しい、より大きなスタック領域が割り当てられ、既存のスタックの内容が新しいスタックにコピーされます。これにより、ゴルーチンは必要に応じてスタックを動的に拡張でき、メモリを効率的に使用できます。

### Goroutine (G) と Machine (M) の関係

Goランタイムは、ゴルーチンをスケジューリングするためにGPMモデルを使用します。
- **G (Goroutine)**: Goの軽量スレッド。スタック、プログラムカウンタ、レジスタなどの実行コンテキストを持ちます。
- **M (Machine)**: OSスレッド。Gを実行するための実際のOSスレッドです。
- **P (Processor)**: MがGを実行するために必要な論理プロセッサ。

スタック分割の文脈では、`G`構造体には現在のゴルーチンのスタックに関する情報（スタックの開始アドレス、終了アドレス、スタックガード値など）が格納されています。また、`M`構造体はOSスレッドの状態を管理し、`morestack`ルーチンが呼び出された際に必要な情報（例えば、スタック拡張に必要な追加の引数など）を一時的に保持するために使用されることがあります。

### `morestack`ルーチン

`morestack`はGoランタイムに実装されている特別な関数で、スタックが不足した際に呼び出されます。このルーチンは、新しいスタック領域を確保し、現在のスタックの内容を新しい領域にコピーし、実行を新しいスタックに切り替える役割を担います。このプロセスは、ユーザーコードからは透過的に行われます。

### `5l`リンカ

`5l`は、Go言語のツールチェインにおけるARMアーキテクチャ（ARMv5, ARMv6, ARMv7など）向けのリンカです。Goのソースコードはコンパイラ（例: `5g`）によってオブジェクトファイルに変換され、その後、`5l`リンカによって実行可能ファイルにリンクされます。リンカは、オブジェクトファイルを結合し、シンボルを解決し、必要に応じてランタイムサポートコードを挿入する役割を担います。このコミットでは、`5l`がスタック分割チェックコードを生成し、`morestack`ルーチンへの呼び出しを適切に配置できるようにするための変更が加えられています。

## 技術的詳細

このコミットは、主に`src/cmd/5l`ディレクトリ内のファイルに影響を与えています。

### `src/cmd/5l/5.out.h`の変更

- `REGG`と`REGM`という新しいレジスタ定義が追加されました。これらは、Goランタイムの`G`（ゴルーチン）と`M`（マシン）構造体へのポインタを保持するために使用されると推測されます。`runtime.h`で宣言されているとコメントされており、Goランタイムとの連携を強化する意図が見られます。

```c
#define REGG        (REGEXT-0)
#define REGM        (REGEXT-1)
```

### `src/cmd/5l/go.c`の追加

- 新しいファイル`go.c`が追加されました。このファイルは、`../ld/go.c`をインクルードしており、Go固有のリンカロジックを共通化するためのものです。これにより、各アーキテクチャのリンカがGoランタイムの特定の機能（例えば、型情報やスタック管理）をサポートするための共通コードを再利用できるようになります。

### `src/cmd/5l/l.h`の変更

- `enum`に`Sxxx`が追加されましたが、これはおそらくプレースホルダーか、将来のシンボルタイプのためのものです。
- `append(Prog*, Prog*)`関数が`Prog* appendp(Prog*)`に変更されました。これは、リンカが生成する命令列（`Prog`構造体）を連結する際に、新しい命令を挿入し、その新しい命令へのポインタを返すように変更されたことを示唆しています。これは、スタックチェックのような追加の命令を既存のコードフローに挿入する際に便利です。
- `deadcode`, `definetypestrings`, `definetypesigs`, `gotypefor`, `ldpkg`といったGo固有のリンカ関数のプロトタイプが追加されました。これらは、Goの型情報やデッドコード削除など、Goランタイムの高度な機能をリンカが処理するために必要となるものです。

### `src/cmd/5l/noop.c`の変更

このファイルは、リンカが生成するコードに対して最適化や変換を行う「no-op」パスを実装しています。スタック分割のロジックの大部分がここに追加されています。

- `StackBig`定数（4096バイト）が定義されました。これは、スタックガードチェックの閾値に関連する可能性があります。
- `sys·morestack`シンボルをリンカのシンボルテーブルから検索するロジックが追加されました。これは、スタックが不足した際にジャンプするランタイム関数を特定するためです。
- 関数プロローグ（関数の開始部分）にスタックチェックのロジックが挿入される準備がされています。
    - コメントアウトされたスタックチェックのコードブロックでは、`G.stackguard`の値をレジスタ（R1）にロードし、現在のスタックポインタ（`REGSP`）から`autosize`（現在の関数のスタックフレームサイズ）を引いた値と比較する処理が記述されています。これは、スタックがスタックガード値を超えていないかを確認する典型的なスタックオーバーフローチェックです。
    - `autosize`（スタックフレームサイズ）と現在の関数に関する情報（`curtext->to.offset2`）を`M.morearg`に格納する処理も記述されています。これは、`morestack`ルーチンがスタックを拡張する際に、どの関数がどれだけのスタックを必要としているかを知るために使用されます。
    - 最終的に、コメントアウトされていますが、`ABL`（Branch with Link）命令を使って`sys·morestack`ルーチンを呼び出す準備がされています。
- 以前の`#ifdef optimise_time`ブロックが削除され、コードが簡素化されました。これは、スタック分割の導入に伴い、古い最適化パスが不要になったか、新しいスタック管理メカニズムと競合するためと考えられます。

### `src/cmd/5l/obj.c`の変更

- `main`関数内で、`definetypestrings`, `definetypesigs`, `deadcode`といったGo固有のリンカ関数がコメントアウトされた状態で呼び出される準備がされています。これは、Goの型情報やデッドコード削除などの機能をリンカに統合する計画があったことを示しています。
- `ldobj`関数（オブジェクトファイルをロードする関数）が大幅に変更されました。
    - 新しいオブジェクトファイルヘッダ形式を処理するためのロジックが追加されました。これは、Goのオブジェクトファイルがより多くのメタデータ（例えば、型情報やエクスポート情報）を含むようになったことを示唆しています。
    - オブジェクトファイル内のエクスポート情報などをスキップするためのロジックが追加されています。
    - `ldpkg`関数（これもコメントアウトされていますが）を使って、パッケージ固有の情報をロードする準備がされています。
- `appendp`関数が追加されました。これは`l.h`で宣言されたものと同じで、命令リストに新しい命令を挿入するためのヘルパー関数です。

### `src/cmd/5l/optab.c`の変更

- コメントの修正のみで、機能的な変更はありません。`Optab`構造体のフィールドに関する説明がより明確になりました。

## コアとなるコードの解説

上記の`noop.c`の変更箇所は、関数プロローグにスタック分割チェックを挿入するためのロジックの骨格を示しています。

1.  **`if(1)`ブロックと`else { // !NOSPLIT }`ブロック**:
    - `if(1)`は、この時点ではスタック分割機能がまだ有効になっていないことを示唆しています。常に`true`であるため、スタック分割ロジックは実行されず、従来のスタックフレーム設定（`REGLINK`をスタックに保存）のみが行われます。
    - `else`ブロック内が、実際にスタック分割チェックを行うためのコードです。このブロックは、`NOSPLIT`フラグが設定されていない関数（つまり、スタック分割が必要な関数）に対して適用されることを意図しています。

2.  **スタックチェックのロジック（`else`ブロック内）**:
    - `if(autosize < StackBig)`: スタックフレームサイズが`StackBig`（4096バイト）よりも小さい場合にのみ、詳細なスタックチェックを行うことを示唆しています。これは、非常に小さなスタックフレームを持つ関数では、スタックオーバーフローのリスクが低いか、あるいは別の最適化パスで処理されるためかもしれません。
    - `p = appendp(p); // load G.stackguard into R1`: `appendp`を使って新しい命令を挿入し、現在のゴルーチン（`G`）の`stackguard`値をレジスタR1にロードします。`REGG`は`G`構造体へのポインタを保持していると想定されます。
    - `p = appendp(p); p->as = ACMP; ...`: ロードした`stackguard`値と、現在のスタックポインタ（`REGSP`）から`autosize`を引いた値（つまり、関数呼び出し後にスタックがどこまで伸びるか）を比較する命令（`ACMP`）を挿入します。この比較の結果によって、スタックが不足しているかどうかが判断されます。
    - `p = appendp(p); // store autosize in M.morearg`: `autosize`（現在の関数のスタックフレームサイズ）を一時レジスタ（`REGTMP`）にロードし、その後`M`構造体の特定のオフセット（`REGM` + 4）に格納します。これは、`morestack`ルーチンがスタックを拡張する際に、どれだけのスタックが必要かを判断するために使用されます。
    - 同様に、`curtext->to.offset2`（おそらく現在の関数の情報）も`M`構造体の別のオフセット（`REGM` + 8）に格納されます。
    - コメントアウトされた`ABL`命令は、スタックが不足していると判断された場合に`sys·morestack`ルーチンを呼び出すためのものです。この時点ではまだ有効化されていません。

このコードは、Goランタイムがどのようにして関数呼び出しの前にスタックの安全性をチェックし、必要に応じてスタック拡張ルーチンを呼び出すかという、スタック分割の基本的なメカニズムをリンカレベルで実装しようとしていることを示しています。

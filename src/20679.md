# [インデックス 20679] ファイルの概要

このコミットは、Go言語のコードフォーマッタである`gofmt`コマンドおよび`go/format`パッケージにおける、部分的なGoコードの整形に関する2つの重要な問題を修正します。具体的には、コメントが失われる問題（Issue #5551）と、生文字列リテラルの内容が誤って変更される問題（Issue #4449）に対処しています。これらの修正は、両パッケージのコード整形ロジックを統一し、より堅牢なインデントおよび空白処理アルゴリズムを導入することで実現されました。

## 変更の背景

Go言語の`gofmt`コマンドと`go/format`パッケージは、Goコードを標準的なスタイルに自動整形することで、コードの一貫性を保ち、可読性を向上させる上で不可欠なツールです。しかし、このコミット以前には、部分的なGoコード（例えば、完全なファイルではなく、関数本体やステートメントのリストなど）を整形する際に、いくつかの深刻な問題が報告されていました。

1.  **Issue #5551: コメントの消失**
    `gofmt`が部分的なGoコードを処理する際に、コード内のコメントが意図せず削除されてしまうという問題がありました。コメントはコードの意図を説明し、将来のメンテナンスを容易にする上で極めて重要であるため、この挙動は開発者にとって大きな障害となっていました。

2.  **Issue #4449: 生文字列リテラルの変更**
    生文字列リテラル（バッククォート `` ` `` で囲まれた文字列）は、エスケープシーケンスの解釈なしに、記述された内容がそのまま文字列の値となることを保証します。これは、複数行のテキスト、正規表現、JSONやHTMLなどの埋め込みデータに特に有用です。しかし、`gofmt`が部分的なGoコードを整形する際に、これらの生文字列リテラルの内容が誤って変更されてしまうというバグが存在しました。これは、生文字列リテラルの「生」であるという本質的な特性を損なうものであり、予期せぬバグを引き起こす可能性がありました。

これらの問題は、特に部分的なGoコードとインデントを伴う整形時に顕在化し、`gofmt`の信頼性と一貫性を損なっていました。このコミットは、これらのバグを修正し、`gofmt`と`go/format`が部分的なコードに対しても正確かつ予測可能な整形を行うことを目的としています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語のツールと概念に関する知識が役立ちます。

*   **`gofmt`と`go/format`パッケージ**:
    *   **`gofmt`**: Go言語の公式なコードフォーマッタです。GoソースコードをGoコミュニティで広く受け入れられている標準的なスタイルに自動的に整形するコマンドラインツールです。これにより、コードベース全体で一貫したスタイルが保たれ、可読性が向上し、コードレビューの負担が軽減されます。
    *   **`go/format`パッケージ**: `gofmt`コマンドが内部的に利用するGo言語の標準ライブラリパッケージです。プログラムからGoコードのフォーマット機能を利用するためのAPIを提供します。

*   **部分的なGoコード (Partial Go Code)**:
    完全なGoプログラム（`package`宣言と`import`宣言から始まる）ではなく、関数本体、ステートメントのリスト、宣言のリストなど、Goコードの一部を指します。例えば、`gofmt -stdin`コマンドに渡されるコードは、しばしば部分的なGoコードです。

*   **AST (Abstract Syntax Tree - 抽象構文木)**:
    GoコンパイラやツールがGoソースコードを解析して生成する、プログラムの構造を表現するツリー構造です。`go/ast`パッケージで定義されます。`gofmt`は、ソースコードをASTに変換し、このASTを操作して整形を行い、最終的に整形されたソースコードを再生成します。

*   **`token.FileSet`**:
    Goソースファイル内の位置情報（行番号、列番号、オフセットなど）を管理するためのオブジェクトです。`go/token`パッケージで提供されます。

*   **`parser.ParseFile`**:
    `go/parser`パッケージの関数で、Goソースコードを解析し、そのASTを生成します。`parser.ParseComments`モードを指定することで、コード内のコメントもASTの一部として解析・保持することができます。

*   **`printer.Config`**:
    `go/printer`パッケージの構造体で、ASTを整形して出力する際の詳細なフォーマット設定（タブ幅、インデントモード、インデント量など）を定義します。

*   **生文字列リテラル (Raw String Literals)**:
    Go言語において、バッククォート (`` ` ``) で囲まれた文字列リテラルです。この形式の文字列は、内部のエスケープシーケンス（例: `\n`, `\t`）が解釈されず、記述された内容が文字通りそのまま文字列の値となります。これにより、複数行のテキスト、正規表現、HTMLやJSONなどの構造化されたデータをGoコード内に直接埋め込む際に非常に便利です。

## 技術的詳細

このコミットの技術的な核心は、`cmd/gofmt`と`go/format`パッケージ間の部分的なGoコード整形ロジックの統一と、より洗練されたインデントおよび空白処理メカニズムの導入にあります。

1.  **コードベースの統一と重複排除**:
    以前は`cmd/gofmt`と`go/format`の間で部分的なコードの整形ロジックに差異があり、それがバグの原因となっていました。このコミットでは、両パッケージのコードを統合し、共通のロジックを使用するように変更されました。これにより、将来的なコードの重複排除が容易になり、一貫性が向上しました。

2.  **`parse()`関数の大幅な改善**:
    *   **コメントの保持**: `cmd/gofmt`の`parse()`関数は元々コメントを正しく保持する能力を持っていましたが、このコミットではそのロジックをさらに洗練させ、Issue #5551（コメントの消失）を完全に修正しました。
    *   **リテラル値の保護**: Issue #4449（生文字列リテラルの変更）に対処するため、`parse()`関数は、部分的なコードを解析する際に内部的に追加するラッパー（例: `package p;` や `package p; func _() { ... }`）の処理方法を改善しました。特に、整形後の結果からこれらのラッパーを正確に取り除くための`sourceAdj`（ソース調整関数）と`indentAdj`（インデント調整量）を返すようになりました。これにより、以前の`bytes.Replace`による問題のあるテキスト操作が不要になり、生文字列リテラル内の改行や空白が誤って変更されることがなくなりました。
    *   **新しいシグネチャ**: `parse`関数のシグネチャが変更され、`file *ast.File`, `sourceAdj func(src []byte, indent int) []byte`, `indentAdj int`, `err error` を返すようになりました。これにより、フォーマット後のソースコードの調整とインデントの調整をより細かく制御できるようになりました。

3.  **`matchSpace()`関数の削除と新しいフォーマットアルゴリズム**:
    *   以前の`matchSpace()`関数は、インデントの挿入や、生文字列リテラルの内容を誤って変更する可能性のある`bytes.Replace`を用いたテキスト操作を行っていました。この関数は問題の根源の一つであったため、このコミットで削除されました。
    *   代わりに、部分的なGoコードのフォーマットをより堅牢に行うための新しい4ステップのアルゴリズムが導入されました。
        1.  **元のソースの先行する空白の特定と付加**: フォーマット対象のコードブロックの前に存在する空白（改行、スペース、タブ）を正確に特定し、整形後の出力の先頭に付加します。
        2.  **最初のコード行のインデントの特定と付加**: コードブロックの最初の非空白行のインデントレベルを決定し、整形後の出力の各行にそのインデントを適用します。
        3.  **部分的なGoコードのフォーマットと書き出し**: `printer.Config`を使用して、部分的なGoコードを整形し、出力します。この際、コードブロック自体の先行および後続の空白はトリムされます。
        4.  **元のソースの後続の空白の特定と付加**: コードブロックの後に存在する空白を特定し、整形後の出力の末尾に付加します。

4.  **`adjustIndent`の導入**:
    `printer.Config`の`Indent`フィールドを調整するために`indentAdj`が導入されました。これは、部分的なコードを関数本体としてラップする際に、その本体が1レベル余分にインデントされることを補償するためのものです。これにより、以前の`bytes.Replace`による問題のあるテキスト操作を排除し、正確なインデントを維持できるようになりました。`cfg.Indent`が負の値になる場合もありますが、これは意図された挙動です。

これらの変更により、`gofmt`と`go/format`は、完全なGoコードだけでなく、部分的なGoコードに対しても、コメントを保持し、生文字列リテラルを正確に扱い、一貫したインデントを適用できるようになりました。

## コアとなるコードの解説

このコミットの核となる変更は、`parse`関数と新しく導入された`format`関数に集約されます。

*   **`parse`関数の変更**:
    *   **シグネチャの拡張**: 以前は`*ast.File`と、整形後のソースを調整するための`adjust`関数を返していました。新しいシグネチャでは、`*ast.File`に加えて、`sourceAdj func(src []byte, indent int) []byte`（整形後のソースを調整する関数）と`indentAdj int`（インデント調整量）を返すようになりました。この変更により、フォーマット後のソースコードの調整と、`printer.Config`に渡すインデント量の調整をより細かく、かつ正確に制御できるようになりました。
    *   **`fragmentOk`引数**: 新たに`fragmentOk`というブール型の引数が追加され、部分的なコードの解析を許可するかどうかを明示的に制御できるようになりました。
    *   **ラッパー処理の改善**: 部分的なコードを解析する際、`gofmt`は内部的に`package p;`や`func _() { ... }`のようなGoコードのラッパーを追加して、それを完全なGoコードとして扱います。このコミットでは、`sourceAdj`関数が、整形後の結果からこれらのラッパーとそれに伴うインデントを正確に取り除くように改善されました。特に、生文字列リテラル内の改行や空白が、このラッパーの除去プロセスによって誤って変更される問題（Issue #4449）が解決されました。

*   **`format`関数の導入**:
    *   `cmd/gofmt`と`go/format`の両方で共通のフォーマットロジックをカプセル化するために、この新しいヘルパー関数が導入されました。
    *   この関数は、元のソースコードの**先行する空白**（コードブロックの前の改行やスペース）を特定し、整形後の出力の先頭に付加します。
    *   次に、コードブロックの**最初のコード行のインデント**を決定し、整形後の出力の各行にそのインデントを適用します。
    *   そして、`printer.Config`の`Indent`フィールドを`indentAdj`で調整し、部分的なGoコードを整形します。この`indentAdj`は、ラッパー関数によって追加されたインデントを補償するために使用されます。これにより、以前の`matchSpace`関数が行っていた問題のあるテキスト操作が不要になり、コメントの保持（Issue #5551）と生文字列リテラルの正確な整形が保証されるようになりました。
    *   最後に、元のソースコードの**後続の空白**を特定し、整形後の出力の末尾に付加します。
    *   この統一された`format`関数により、両パッケージで一貫した、より堅牢な部分コード整形が実現されました。

*   **`isSpace`関数の追加**:
    空白文字（スペース、タブ、改行、キャリッジリターン）の判定を統一的に行うためのシンプルなヘルパー関数です。

これらの変更により、`gofmt`は部分的なGoコードに対しても、コメントを保持し、生文字列リテラルを正確に扱い、一貫したインデントを適用できるようになり、ツールの信頼性が大幅に向上しました。

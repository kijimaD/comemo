# [インデックス 22844] ファイルの概要

このコミットは、Go言語のビルドツールである`cmd/go`に、共有ライブラリ（Shared Libraries）へのリンクを可能にする`-linkshared`フラグの初期サポートを追加するものです。Go 1.5リリースに向けて、Goプログラムが動的に共有ライブラリとリンクできるようにするための重要な一歩となります。

## 元コミット内容

`cmd/go`: `-linkshared`のサポートを開始

これは、共有ライブラリ内にある古いパッケージを無駄に再ビルドすることになります。

## 変更の背景

このコミットは、Go 1.5で導入された共有ライブラリのサポートに向けた初期段階の一部です。それまでのGoプログラムは、基本的に全ての依存関係を静的にリンクして単一のバイナリを生成していました。これはデプロイの容易さという利点がある一方で、以下のような課題も抱えていました。

1.  **バイナリサイズの増大**: 多くのGoプログラムが共通のライブラリ（例えば、標準ライブラリ）を使用している場合でも、それぞれのバイナリにそのライブラリのコードが複製されるため、ディスク使用量が増大します。
2.  **ビルド時間の増大**: 依存するライブラリに変更があった場合、そのライブラリを使用する全てのプログラムを再ビルドする必要がありました。
3.  **メモリ使用量の非効率性**: 複数のGoプログラムが同時に実行される環境では、それぞれが同じライブラリのコードをメモリ上に持つため、メモリの利用効率が悪くなる可能性がありました。

これらの課題に対処するため、Go 1.5では`buildmode=shared`というビルドモードが導入され、Goパッケージを共有ライブラリとしてビルドできるようになりました。このコミットは、その共有ライブラリをGoプログラムが利用する際に、動的にリンクするための`-linkshared`フラグの基盤を構築するものです。これにより、Goプログラムが既にビルドされた共有ライブラリに依存できるようになり、上記の課題の緩和が期待されました。

コミットメッセージにある「This will fruitlessly rebuild stale packages that are in a shared library.」という記述は、この機能がまだ初期段階であり、共有ライブラリ内のパッケージの再ビルドに関する非効率性が存在することを示唆しています。これは、開発途上における既知の課題として認識されていたものです。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

1.  **静的リンクと動的リンク**:
    *   **静的リンク**: プログラムのビルド時に、必要なライブラリのコードが実行可能ファイルに直接組み込まれる方式です。結果として生成されるバイナリは自己完結型であり、実行時に外部ライブラリを必要としません。Goの従来のビルドは主にこの方式でした。
    *   **動的リンク（共有ライブラリ）**: プログラムのビルド時には、ライブラリのコードは実行可能ファイルに組み込まれず、実行時にOSのローダーによって共有ライブラリがメモリにロードされ、プログラムとリンクされます。これにより、複数のプログラムが同じライブラリの単一のコピーを共有でき、ディスク使用量やメモリ使用量を削減できます。

2.  **Goのビルドモード (`-buildmode`)**:
    Go 1.5以降、`go build`コマンドには`-buildmode`フラグが追加され、様々な形式のバイナリを生成できるようになりました。
    *   `buildmode=exe` (デフォルト): 実行可能バイナリを生成します。
    *   `buildmode=shared`: 複数のGoプログラムで共有可能なGoパッケージの共有ライブラリ（例: Linuxでは`.so`ファイル）を生成します。
    *   `buildmode=c-shared`: C言語の呼び出し規約に従う共有ライブラリを生成し、C/C++などの他の言語からGoの関数を呼び出せるようにします。

3.  **Goのリンカ (`-ldflags`)**:
    Goのビルドプロセスでは、リンカに渡すフラグを`-ldflags`オプションで指定できます。これにより、リンカの挙動を制御し、例えばビルドモードの指定や、特定のライブラリへのリンク方法などを調整できます。

4.  **Goのクロスコンパイル**:
    Goは異なるOSやアーキテクチャ向けのバイナリを簡単に生成できるクロスコンパイル機能を持ちます。このコミットでは、`-linkshared`が初期段階では`linux/amd64`に限定されていることが示されており、これはクロスコンパイルの文脈で特定の環境に依存する機能であることを意味します。

## 技術的詳細

このコミットの主要な技術的変更点は、`cmd/go`ツールが`-linkshared`フラグを認識し、それに基づいてビルドプロセスを調整するようにしたことです。

1.  **フラグの追加と解析**:
    *   `src/cmd/go/build.go`において、`buildLinkshared`というブール型の変数が追加され、`addBuildFlags`関数内で`cmd.Flag.BoolVar(&buildLinkshared, "linkshared", false, "")`によって、`go build`や`go install`コマンドが`-linkshared`フラグを受け入れるように設定されています。
    *   `src/cmd/go/doc.go`には、`go help buildmodes`の出力に`-linkshared`フラグの説明が追加され、ユーザーがこのフラグの存在と目的を認識できるようにしています。
    *   `src/cmd/go/testflag.go`では、テスト実行時に`-linkshared`フラグが適切に処理されるように、`testFlagDefn`リストに`linkshared`が追加されています。

2.  **ビルドモードの初期化と制約**:
    *   `src/cmd/go/build.go`の`buildModeInit()`関数は、ビルドモードに関する初期化処理を行う場所です。この関数内に、`-linkshared`フラグが指定された場合のロジックが追加されました。
    *   **プラットフォームの制約**: `if buildLinkshared { if goarch != "amd64" || goos != "linux" { ... } }`という条件が追加され、`-linkshared`は初期段階では`linux/amd64`環境でのみサポートされることが明示されています。これ以外の環境でこのフラグを使用すると、エラーメッセージを出力して終了します。これは、共有ライブラリのサポートが特定のOS/アーキテクチャの組み合わせから段階的に導入される一般的なアプローチです。
    *   **リンカフラグの追加**: `-linkshared`が指定された場合、リンカに渡す引数（`buildLdflags`）に`"-linkshared"`と`"-w"`が追加されます。
        *   `"-linkshared"`: これはリンカに対して、共有ライブラリへの動的リンクを行うように指示するGoリンカ固有のフラグです。
        *   `"-w"`: これはデバッグ情報の生成を抑制するリンカフラグです。コミットメッセージのコメント`// TODO(mwhudson): remove -w when that gets fixed in linker.`から、この時点ではリンカの既知の問題（おそらくデバッグ情報と共有ライブラリの組み合わせに関するもの）を回避するための一時的な措置であったことが伺えます。

3.  **テストとの統合**:
    *   `src/cmd/go/test.go`の`runTest`関数内で`buildModeInit()`が呼び出されるようになりました。これにより、`go test`コマンドを実行する際にも、`-linkshared`などのビルドモード関連のフラグが適切に処理され、共有ライブラリにリンクされたテストバイナリのビルドが可能になります。

このコミットは、Goのビルドシステムに共有ライブラリの概念を導入するための低レベルな変更であり、ユーザーが`-linkshared`フラグを通じてこの機能を利用できるようにするための基盤を築いています。

## コアとなるコードの解説

1.  **`src/cmd/go/build.go`**:
    *   `var buildLinkshared bool`: `-linkshared`フラグの状態を保持するためのグローバル変数です。`true`であれば、共有ライブラリへのリンクが有効になります。
    *   `addBuildFlags(cmd *Command)`: `go build`や`go install`などのコマンドに共通のビルド関連フラグを追加する関数です。ここで`cmd.Flag.BoolVar(&buildLinkshared, "linkshared", false, "")`が呼び出され、`-linkshared`フラグがコマンドライン引数として認識されるようになります。`false`はデフォルト値で、フラグが指定されない場合は共有ライブラリへのリンクは行われません。
    *   `buildModeInit()`: この関数は、Goのビルドモードに関する初期化と検証を行います。
        *   `if buildLinkshared { ... }`: `-linkshared`フラグが指定された場合に実行されるブロックです。
        *   `if goarch != "amd64" || goos != "linux" { ... }`: この条件は、`-linkshared`が現在のところ`linux/amd64`環境でのみサポートされていることを強制します。他の環境でこのフラグが使用された場合、エラーメッセージを出力し、プログラムを終了します。これは、共有ライブラリのサポートが段階的に導入される際の一般的なパターンです。
        *   `codegenArg = "-dynlink"`: これはGoコンパイラに渡される引数で、動的リンクを有効にするためのものです。
        *   `buildLdflags = append(buildLdflags, "-linkshared", "-w")`: リンカに渡すフラグのリストに`"-linkshared"`と`"-w"`を追加します。
            *   `"-linkshared"`: リンカに共有ライブラリへの動的リンクを指示します。
            *   `"-w"`: デバッグ情報の生成を抑制します。コメントにあるように、これは当時のリンカの既知の問題を回避するための一時的な措置でした。

2.  **`src/cmd/go/doc.go`**:
    *   このファイルは`go help`コマンドの出力内容を定義しています。`-linkshared`フラグの説明が追加されたことで、ユーザーは`go help buildmodes`を実行することでこの新しいフラグの存在と目的を知ることができます。

3.  **`src/cmd/go/test.go`**:
    *   `runTest`関数は`go test`コマンドの主要なロジックを含んでいます。この関数内で`buildModeInit()`が呼び出されるようになったことで、テストバイナリのビルド時にも`-linkshared`フラグが考慮され、共有ライブラリにリンクされたテストの実行が可能になります。

4.  **`src/cmd/go/testflag.go`**:
    *   `testFlagDefn`は、`go test`コマンドが認識するフラグの定義リストです。ここに`{name: "linkshared", boolVar: &buildLinkshared}`が追加されたことで、`go test -linkshared`のようにテストコマンドに直接`-linkshared`フラグを渡せるようになります。また、`testFlags`関数内の`switch`文にも`"linkshared"`が追加され、ブール型フラグとして適切に処理されるようになっています。

これらの変更により、Goのビルドシステムは共有ライブラリへの動的リンクをサポートするための基盤を獲得しました。

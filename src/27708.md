# [インデックス 27708] ファイルの概要

このコミットは、Goランタイムにおけるパニック値の挙動を改善し、Go言語仕様に準拠させるための変更です。具体的には、ランタイムパニックが発生した際に`panic`関数に渡される値が、単なる文字列ではなく`runtime.Error`インターフェースを実装する型となるように修正されています。これにより、ランタイムパニックの型安全性が向上し、パニックを捕捉した際の処理がより予測可能になります。

## 元コミット内容

このコミットの目的は、Goランタイムが引き起こすパニック（実行時エラー）の値を`Error`インターフェースを実装する型にすることです。これはGo言語の仕様書（`https://golang.org/ref/spec#Run_time_panics`）によって義務付けられており、これまでの文字列によるパニックを修正します。Issue #14965を解決します。

## 変更の背景

Go言語の仕様書では、ランタイムパニック（例: nilポインタ参照、インデックス範囲外アクセスなど）が発生した場合に`panic`関数に渡される値は、`runtime.Error`インターフェースを実装する型であるべきだと規定されています。しかし、実際のGoランタイムの実装では、多くのケースで単なる文字列が`panic`に渡されていました。

この不一致は、パニックを`recover`で捕捉した際に、そのパニック値の型を`runtime.Error`としてアサートしようとすると失敗する可能性があるという問題を引き起こしていました。開発者は、ランタイムパニックとアプリケーションレベルのパニック（`panic("something")`のように文字列を直接渡す場合）を区別し、それぞれ異なる方法で処理したいと考えることがあります。`runtime.Error`インターフェースの実装は、この区別をプログラム的に行うための標準的な方法を提供します。

このコミットは、この仕様と実装の間のギャップを埋め、Go言語の設計意図に沿った挙動を実現するために行われました。

## 前提知識の解説

### Go言語のパニックとリカバリー (Panic and Recover)

Go言語には、プログラムの異常終了を扱うための`panic`と`recover`というメカニズムがあります。
*   **`panic`**: 実行時エラーやプログラマが意図的にプログラムを異常終了させたい場合に呼び出されます。`panic`が呼び出されると、現在の関数の実行が停止し、defer関数が実行されながら呼び出し元の関数へとスタックを遡っていきます。最終的にスタックの最上位まで到達すると、プログラムはクラッシュします。`panic`には任意の型の値を渡すことができます。
*   **`recover`**: `defer`関数内で呼び出されると、`panic`によって中断されたゴルーチンの実行を再開させることができます。`recover`は、`panic`に渡された値を返します。`recover`が`defer`関数内で呼び出されなかった場合、または`panic`が発生していないときに呼び出された場合、`recover`は`nil`を返します。

### `error`インターフェース

Go言語におけるエラー処理の基本は、組み込みの`error`インターフェースです。
```go
type error interface {
    Error() string
}
```
このインターフェースは、`Error() string`というメソッドを一つだけ持ちます。これにより、任意のエラー型が自身のエラーメッセージを文字列として表現できるようになります。Goの標準ライブラリや多くのサードパーティライブラリは、この`error`インターフェースを利用してエラーを返します。

### `runtime.Error`インターフェース

Goの`runtime`パッケージには、ランタイムパニックを表すための特別なインターフェース`runtime.Error`が存在します。
```go
package runtime

type Error interface {
    error
    RuntimeError() // for clients to implement Error's methods
}
```
`runtime.Error`インターフェースは、`error`インターフェースを埋め込んでおり、さらに`RuntimeError()`というメソッドを追加で持ちます。この`RuntimeError()`メソッドは、具体的な実装を必要とせず、単に`runtime.Error`であることを示すマーカーとして機能します。これにより、開発者は`recover`で捕捉したパニック値がGoランタイムによって引き起こされたものであるかどうかを、型アサーション（例: `if _, ok := r.(runtime.Error); ok { ... }`）によって判別できるようになります。

### Issue #14965

このコミットが修正するIssue #14965は、「ランタイムパニックは`runtime.Error`インターフェースを実装すべきである」という内容です。このIssueは、Go言語の仕様書に明記されているにもかかわらず、多くのランタイムパニックが単なる文字列を`panic`に渡している現状を指摘し、その修正を求めていました。

## 技術的詳細

このコミットの技術的な核心は、Goランタイム内で発生するパニックの値を、新たに導入された`plainError`型でラップすることです。

1.  **`plainError`型の導入**:
    `src/runtime/error.go`に`plainError`という新しい型が定義されました。
    ```go
    type plainError string
    ```
    この型は、パニックメッセージとなる文字列を保持します。

2.  **`runtime.Error`インターフェースの実装**:
    `plainError`型は、`Error()`メソッドと`RuntimeError()`メソッドを実装することで、`runtime.Error`インターフェースを満たします。
    ```go
    func (e plainError) RuntimeError() {} // マーカーメソッド
    func (e plainError) Error() string {
        return string(e) // 保持している文字列をそのまま返す
    }
    ```
    `RuntimeError()`メソッドは空の実装ですが、これにより`plainError`が`runtime.Error`インターフェースの要件を満たします。`Error()`メソッドは、`plainError`がラップしている文字列をそのまま返します。

3.  **既存の`panic`呼び出しの変更**:
    ランタイム内の様々な箇所（チャネル操作、マップ操作、メモリ割り当て、リフレクションなど）で、これまで`panic("some message")`のように直接文字列を渡していた部分が、`panic(plainError("some message"))`のように`plainError`でラップする形に変更されました。

4.  **テストの追加**:
    `src/runtime/crash_test.go`に`TestRuntimePanicWithRuntimeError`という新しいテスト関数が追加されました。このテストは、様々な種類のランタイムパニック（nilマップアクセス、クローズ済みチャネルのクローズ/送信、スライス範囲外アクセス、不正なチャネルサイズ、nilチャネルのクローズなど）を意図的に発生させ、`recover`で捕捉したパニック値が`runtime.Error`インターフェースを実装していることを検証します。

この変更により、`recover`でパニックを捕捉した際に、その値が`runtime.Error`型であるかどうかを安全にチェックできるようになり、ランタイムパニックとその他のパニックを区別した処理が可能になります。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/runtime/error.go`で定義された`plainError`型と、それを利用するように変更された`panic`呼び出しです。

### `src/runtime/error.go` の変更

```go
// plainError represents a runtime error described a string without
// the prefix "runtime error: " after invoking errorString.Error().
// See Issue #14965.
type plainError string

func (e plainError) RuntimeError() {}

func (e plainError) Error() string {
	return string(e)
}
```
*   `type plainError string`: 新しい型`plainError`が`string`のエイリアスとして定義されます。これにより、文字列を基盤としながらも、独自のメソッドを持つことができます。
*   `func (e plainError) RuntimeError() {}`: このメソッドは、`runtime.Error`インターフェースの要件を満たすために追加されました。実装は空ですが、このメソッドが存在することで`plainError`型が`runtime.Error`インターフェースを「実装している」とGoコンパイラに認識されます。
*   `func (e plainError) Error() string { return string(e) }`: このメソッドは、`error`インターフェースの要件を満たします。`plainError`が保持する基盤の文字列値をそのまま返します。これにより、`plainError`は`error`インターフェースとしても振る舞うことができます。

### `panic`呼び出しの変更

ランタイム内の様々な場所で、以下のような変更が行われました。

**変更前:**
```go
panic("some descriptive error message")
```

**変更後:**
```go
panic(plainError("some descriptive error message"))
```
この変更により、`panic`に渡される値は単なる文字列ではなく、`runtime.Error`インターフェースを実装する`plainError`型のインスタンスとなります。

### `src/runtime/crash_test.go` のテスト

```go
// Issue 14965: Runtime panics should be of type runtime.Error
func TestRuntimePanicWithRuntimeError(t *testing.T) {
	testCases := [...]func(){
		// ... (様々なパニックを発生させる関数リテラル) ...
	}

	for i, fn := range testCases {
		got := panicValue(fn)
		if _, ok := got.(runtime.Error); !ok {
			t.Errorf("test #%d: recovered value %v(type %T) does not implement runtime.Error", i, got, got)
		}
	}
}

func panicValue(fn func()) (recovered interface{}) {
	defer func() {
		recovered = recover()
	}()
	fn()
	return
}
```
*   `panicValue`関数は、引数として渡された関数`fn`を実行し、その中で発生したパニックを`recover`で捕捉して返します。
*   `TestRuntimePanicWithRuntimeError`では、`testCases`スライスに様々なランタイムパニックを引き起こす関数リテラルが格納されています。
*   各テストケースで`panicValue`を呼び出し、捕捉された値`got`が`runtime.Error`インターフェースを実装しているかどうかを型アサーション`got.(runtime.Error)`で確認しています。`!ok`であればテストは失敗し、パニック値が仕様に準拠していないことを示します。

このテストの追加は、変更が正しく機能していることを保証し、将来の回帰を防ぐ上で非常に重要です。

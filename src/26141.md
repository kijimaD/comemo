# [インデックス 26141] ファイルの概要

このコミットは、Goランタイムにおける特定の競合状態（レースコンディション）を解消するためのものです。具体的には、スタックバリアを操作する`setNextBarrierPC`関数と、プロファイリングのためにスタックトレースを行う`sigprof`シグナルとの間で発生しうる問題に対処しています。

Author: Austin Clements <austin@google.com>
Date:   Thu Dec 17 15:35:49 2015 -0800

    runtime: prevent race between setNextBarrierPC and sigprof
    
    Currently, setNextBarrierPC manipulates the stack barriers without
    acquiring the stack barrier lock. This is mostly okay because
    setNextBarrierPC also runs synchronously on the G and prevents safe
    points, but this doesn't prevent a sigprof from occurring during a
    setNextBarrierPC and performing a traceback.
    
    Given that setNextBarrierPC simply sets one entry in the stack barrier
    array, this is almost certainly safe in reality. However, given that
    this depends on a subtle argument, which may not hold in the future,
    and that setNextBarrierPC almost never happens, making it nowhere near
    performance-critical, we can simply acquire the stack barrier lock and
    be sure that the synchronization will work.

## 元コミット内容

Goランタイムにおいて、`setNextBarrierPC`関数がスタックバリアを操作する際に、スタックバリアロックを取得していなかったことによる競合状態を修正します。この修正により、`setNextBarrierPC`の実行中に`sigprof`シグナルが発生し、不正なスタックトレースが行われる可能性が排除されます。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行と並行して動作し、その効率性を高めるために様々な最適化が施されています。その一つが「ライトバリア（Write Barrier）」であり、これはポインタの変更をGCに通知するためのメカニズムです。スタックバリアは、このライトバリアの一部として、特にゴルーチンのスタック領域におけるポインタの変更を管理するために導入されました。

`setNextBarrierPC`関数は、このスタックバリアの特定の情報を設定する役割を担っています。コミット前の実装では、この関数はスタックバリアを操作する際に、排他制御のためのロック（スタックバリアロック）を取得していませんでした。通常、`setNextBarrierPC`はゴルーチン（G）上で同期的に実行され、GCのセーフポイント（GCが安全にスタックをスキャンできるポイント）を妨げないように設計されていたため、ほとんどの場合は問題ありませんでした。

しかし、`sigprof`シグナル（プロファイリングのために定期的に発生し、現在のプログラムカウンタをサンプリングするシグナル）は、プログラムの実行を非同期に中断し、スタックトレースを実行する可能性があります。この`sigprof`が、`setNextBarrierPC`がスタックバリアのデータを一時的に不整合な状態にしている最中に発生すると、不正確なスタックトレースが行われる可能性がありました。

コミットメッセージでは、`setNextBarrierPC`がスタックバリア配列の1エントリを単純に設定するだけであり、現実的にはほとんど安全であると述べられています。しかし、これは将来的に保証されない微妙な前提に依存しており、また`setNextBarrierPC`の発生頻度が非常に低く、パフォーマンス上のボトルネックではないため、より堅牢な同期メカニズムを導入することが決定されました。

この変更は、Go 1.5.3のリリースに向けて行われ、Issue #12528に関連しています。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステム。スケジューラ、ガベージコレクタ、メモリ管理などが含まれます。
*   **ガベージコレクション (Garbage Collection, GC)**: プログラムが不要になったメモリを自動的に解放するプロセス。GoのGCは並行（concurrent）かつ低遅延（low-latency）を目指しています。
*   **ライトバリア (Write Barrier)**: GCが正しく動作するために、プログラムがポインタを書き換える際に実行される小さなコードスニペット。これにより、GCはオブジェクト間の参照関係の変化を追跡できます。
*   **スタックバリア (Stack Barrier)**: Go 1.5で導入されたGCのメカニズムの一部で、特にゴルーチンのスタック領域におけるポインタの変更を管理します。GCがスタックをスキャンする際に、スタック上のポインタが正しく認識されるようにするためのものです。
*   **`setNextBarrierPC`**: Goランタイム内部の関数で、スタックバリアに関連するプログラムカウンタ（PC）の値を設定します。これは、GCがスタックをスキャンする際の特定の挙動を制御するために使用されます。
*   **`sigprof` (Profiling Signal)**: プロファイリングのために使用されるシグナル（通常は`SIGPROF`）。OSによって定期的にプロセスに送信され、その時点で実行されているコードの情報を収集するために使用されます。これにより、CPU使用率の高い部分などを特定できます。`sigprof`ハンドラは、シグナル発生時のスタックトレースを収集することがよくあります。
*   **競合状態 (Race Condition)**: 複数の処理が共有リソースにアクセスする際に、その実行順序によって結果が変わってしまうような状況。予期せぬバグの原因となります。
*   **排他制御 (Mutual Exclusion)**: 共有リソースへのアクセスを一度に一つの処理に限定することで、競合状態を防ぐメカニズム。ロック（mutex）などが用いられます。
*   **`gp` (Goroutine Pointer)**: Goランタイム内部で、現在のゴルーチンを表す構造体へのポインタ。`gp.stkbar`は現在のゴルーチンのスタックバリア情報を保持する配列です。

## 技術的詳細

このコミットが修正する問題は、`setNextBarrierPC`関数が`gp.stkbar`（現在のゴルーチンのスタックバリア配列）を直接操作する際に、排他制御が欠如していたことに起因します。

Go 1.5のGCは、スタック上のポインタを効率的に処理するためにスタックバリアを使用します。`setNextBarrierPC`は、このスタックバリアの特定のPC値を設定することで、GCがスタックをどのように扱うかを指示します。この操作自体は非常に短く、通常はアトミックに近い形で実行されると考えられていました。また、`setNextBarrierPC`はゴルーチン上で同期的に実行され、GCのセーフポイントを妨げないため、GC自体との競合は少ないとされていました。

しかし、`sigprof`シグナルはOSレベルで非同期に発生し、Goランタイムの制御外でスタックトレースを開始する可能性があります。もし`setNextBarrierPC`が`gp.stkbar`を更新している最中に`sigprof`が発生し、そのスタックトレースが`gp.stkbar`の不整合な状態を読み取ってしまうと、ランタイムのクラッシュや不正なプロファイリング結果につながる可能性がありました。

コミットの作者は、この操作が「現実的にはほぼ安全」であると認識しつつも、その安全性が「微妙な引数に依存しており、将来的に保証されない可能性がある」と指摘しています。また、`setNextBarrierPC`の呼び出し頻度が非常に低く、パフォーマンスに影響を与えないため、明示的なロックによる同期を導入することが最善であると判断しました。

修正は、`setNextBarrierPC`関数内で`gp.stkbar`を操作する前後に、`gcLockStackBarriers(gp)`と`gcUnlockStackBarriers(gp)`という2つの関数を呼び出すことで行われます。これらの関数は、現在のゴルーチン`gp`のスタックバリアに対するアクセスを排他的に制御するためのロックメカニズムを提供します。これにより、`setNextBarrierPC`がスタックバリアを更新している間は、他の処理（`sigprof`によるスタックトレースなど）が不整合な状態のスタックバリアにアクセスすることを防ぎ、安全性が確保されます。

## コアとなるコードの変更箇所

変更は`src/runtime/mstkbar.go`ファイルにあります。

```diff
--- a/src/runtime/mstkbar.go
+++ b/src/runtime/mstkbar.go
@@ -305,7 +305,9 @@ func nextBarrierPC() uintptr {
 //go:nosplit
 func setNextBarrierPC(pc uintptr) {
  	gp := getg()
+	gcLockStackBarriers(gp)
  	gp.stkbar[gp.stkbarPos].savedLRVal = pc
+	gcUnlockStackBarriers(gp)
 }
 
 // gcLockStackBarriers synchronizes with tracebacks of gp's stack
```

## コアとなるコードの解説

変更は`setNextBarrierPC`関数内で行われています。

1.  `gp := getg()`: 現在実行中のゴルーチン（`g`構造体）へのポインタを取得します。`gp`は現在のゴルーチンの状態やスタック情報を含んでいます。
2.  `gcLockStackBarriers(gp)`: `gp`が指すゴルーチンのスタックバリアに対するロックを取得します。これにより、他のゴルーチンや非同期処理（`sigprof`ハンドラなど）が、このゴルーチンのスタックバリア情報に同時にアクセスして不整合な状態を読み取ることを防ぎます。
3.  `gp.stkbar[gp.stkbarPos].savedLRVal = pc`: ここがスタックバリアの実際の更新箇所です。`gp.stkbar`はスタックバリア情報を保持する配列であり、`gp.stkbarPos`はその配列内の現在の位置を示します。`savedLRVal`フィールドに、新しいプログラムカウンタ`pc`の値を設定します。
4.  `gcUnlockStackBarriers(gp)`: スタックバリアの更新が完了した後、取得していたロックを解放します。これにより、他の処理が再びスタックバリア情報にアクセスできるようになります。

この修正により、`setNextBarrierPC`によるスタックバリアの操作がアトミックに（不可分な操作として）実行されることが保証され、`sigprof`のような非同期イベントによる競合状態が完全に排除されます。

# [インデックス 23666] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) におけるスタックチェック機構 (`stkcheck`) の柔軟性を向上させるための変更です。特に、`morestack` 関数の呼び出しが関数のプロローグのどこに配置されても正しく処理されるように、`stkcheck` のロジックが調整されました。

## 変更の背景

Goランタイムでは、各Goルーチンが独自のスタックを持っています。スタックの枯渇を防ぐため、関数呼び出しの前にスタックの残量をチェックし、必要に応じてスタックを拡張するメカニズムが存在します。このチェックは通常、`morestack` という特殊な関数への呼び出しによって行われます。

リンカの `stkcheck` 関数は、プログラム内の関数がスタックをどのように使用するかを分析し、スタックオーバーフローの可能性を検出するために使用されます。しかし、この `stkcheck` は「フロー非感受性 (flow-insensitive)」な分析を行います。これは、プログラムの実行パスや条件分岐を考慮せず、単にプログラムカウンタ (PC) の順序で命令を処理することを意味します。

これまでのGoのコンパイラでは、`morestack` への呼び出しは常に各関数のプロローグ（関数の冒頭部分）の最初の呼び出しとして配置されていました。このため、`stkcheck` はフロー非感受性であっても、`morestack` が現れた時点でスタック空間の調整を行うという「安全で保守的な近似」で正しく機能していました。

しかし、このコミットの背景には、将来の変更 (Subsequent CLS) で関数のプロローグが再配置され、`morestack` が関数の最初の呼び出しではなくなる可能性があるという問題がありました。この変更が行われると、現在のフロー非感受性な `stkcheck` は `morestack` の呼び出しを正しく認識できなくなり、誤ったスタック使用量の分析を行う恐れがありました。

`stkcheck` をフロー感受性 (flow-sensitive) に変更することも検討されましたが、これは「高リスクでコストがかかる変更」と判断されました。フロー感受性分析は、プログラムの実行パスを正確に追跡するため、より複雑で計算コストが高くなります。また、既存のコードベースへの影響も大きいため、よりシンプルな解決策が求められました。

そこで、このコミットでは、`morestack` へのすべての呼び出しは、プログラムテキスト内のどこに配置されていても、関数のプロローグの一部として発生すると仮定するという、より実用的なアプローチが採用されました。これにより、`stkcheck` の根本的なフロー非感受性を維持しつつ、将来のプロローグの変更に対応できるようになります。

## 前提知識の解説

1.  **Goルーチンとスタック**: Go言語では、軽量な並行処理単位であるGoルーチンが使用されます。各Goルーチンは、独自の可変サイズのスタックを持っています。
2.  **スタック拡張 (Stack Growth)**: Goルーチンのスタックは、必要に応じて自動的に拡張されます。これは、関数呼び出しの前にスタックの残量をチェックし、不足している場合は `morestack` 関数を呼び出して新しい、より大きなスタックに切り替えることで実現されます。
3.  **`morestack` 関数**: Goランタイムの内部関数で、スタックの拡張処理を担当します。コンパイラによって生成されたコードから暗黙的に呼び出されます。
4.  **リンカ (`cmd/link`)**: Goプログラムのコンパイルプロセスの最終段階で、コンパイルされたオブジェクトファイルを結合し、実行可能ファイルを生成するツールです。この過程で、スタック使用量の分析やスタックチェックの挿入など、様々な最適化や検証が行われます。
5.  **`stkcheck` 関数**: リンカ (`cmd/link`) 内の関数で、各関数のスタックフレームサイズと呼び出しグラフを分析し、スタックオーバーフローの可能性をチェックします。これは、Goルーチンのスタックが適切に管理されていることを保証する重要なステップです。
6.  **フロー感受性 (Flow-Sensitive) vs. フロー非感受性 (Flow-Insensitive) 分析**:
    *   **フロー非感受性**: プログラムの命令を、その実行順序や条件分岐を考慮せずに、単にテキスト上の順序で処理する分析手法です。シンプルで高速ですが、プログラムの正確な振る舞いを捉えきれない場合があります。
    *   **フロー感受性**: プログラムの制御フローグラフ (CFG) を構築し、可能な実行パスを追跡しながら分析を行う手法です。より正確な分析が可能ですが、計算コストが高く、複雑になります。
7.  **関数のプロローグ (Function Prologue)**: 関数が呼び出された直後に実行される一連の命令です。これには、スタックフレームのセットアップ、レジスタの保存、スタックチェック (`morestack` 呼び出し) などが含まれます。
8.  **リロケーション (`obj.R_CALL`, `obj.R_CALLARM` など)**: リンカがシンボル参照を解決するために使用する情報です。`obj.R_CALL` などのタイプは、特定の命令が関数呼び出しであることを示します。リンカはこれらのリロケーション情報に基づいて、呼び出し先の正確なアドレスを埋め込みます。
9.  **`obj.StackLimit`**: Goランタイムで定義されている、スタックの最小サイズまたはスタックガードのオフセットに関連する定数です。
10. **`s.Locals`**: 関数のローカル変数によって使用されるスタック空間の量を示します。
11. **`haslinkregister()`**: 特定のアーキテクチャがリンクレジスタ（呼び出し元のアドレスを保存するレジスタ）を持っているかどうかをチェックする関数です。リンクレジスタを使用するアーキテクチャでは、スタックにそのレジスタの値を保存するための追加スペースが必要になる場合があります。

## 技術的詳細

このコミットの核心は、`stkcheck` のフロー非感受性という制約の中で、`morestack` 呼び出しの配置に関する将来の変更に対応することです。

従来の `stkcheck` は、関数の命令をPC順に走査し、`morestack` への呼び出しに遭遇すると、その時点でスタック制限を調整していました。これは、`morestack` が常にプロローグの最初に現れるという暗黙の仮定に基づいています。

しかし、将来のコンパイラの変更により、`morestack` 呼び出しがプロローグ内の異なる位置、例えば関数の最後の方に配置される可能性が出てきました。`stkcheck` がフロー非感受性であるため、もし `morestack` が関数の途中に現れた場合、`stkcheck` はその呼び出しを通常の関数呼び出しとして扱い、スタック制限の調整を遅らせてしまう可能性があります。これにより、`morestack` 自体を呼び出すためのスタック空間が不足していると誤って判断されるか、あるいはスタックチェックが不十分になる恐れがありました。

この問題を解決するために、コミットでは以下の戦略が採用されました。

1.  **`morestack` 呼び出しの事前検出**: `stkcheck` 関数の冒頭で、関数内のすべてのリロケーション (`s.R`) を走査し、`runtime.morestack` への呼び出し (`obj.R_CALL` などのタイプを持つもの) を探します。
2.  **プロローグでの発生と仮定**: `morestack` への呼び出しが見つかった場合、その呼び出しがプログラムテキスト内のどこにあっても、関数のエントリポイント（プロローグ）で発生すると仮定して処理します。
3.  **スタック制限の調整**: `morestack` 呼び出しが見つかると、`morestack` 自体を呼び出すために必要なスタック空間 (`callsize()`) を考慮して `ch.limit` を設定し、再帰的に `stkcheck` を呼び出します。この再帰呼び出しが成功した場合、スタック制限 (`limit`) を `obj.StackLimit + s.Locals` に更新します。これは、`morestack` が呼び出された後、スタックが拡張され、利用可能なスタック空間がリセットされた状態をシミュレートします。リンクレジスタを持つアーキテクチャの場合は、追加で `Thearch.Regsize` を加算します。
4.  **重複処理の回避**: 既存の `stkcheck` ロジックでは、命令をPC順に走査する際に通常の関数呼び出しと同様に `morestack` 呼び出しも処理していました。新しいロジックで `morestack` を事前に処理したため、既存のループ内では `morestack` への呼び出しをスキップするように変更されました。これにより、`morestack` 呼び出しが二重に処理されることを防ぎます。

このアプローチは、`stkcheck` をフロー感受性にするという複雑で高リスクな変更を避けつつ、`morestack` の配置に関する将来の変更に対応できる実用的な解決策を提供します。ただし、コミットメッセージにもあるように、「手動で挿入された `morestack` への呼び出しがある場合、このチェックは間違った結果を出す」という注意点があります。しかし、そのようなケースは現在なく、今後も発生すべきではないとされています。

## コアとなるコードの解説

変更は主に `stkcheck` 関数の2つの部分にあります。

1.  **`morestack` 呼び出しの事前処理 (追加されたループ)**:
    *   `for _, r := range s.R { ... }` という新しいループが関数の冒頭に追加されました。`s.R` は、現在の関数内のすべてのリロケーション（シンボル参照）のリストです。
    *   このループは、各リロケーション `r` をチェックし、それが `runtime.morestack` への呼び出しであるかどうかを判断します。
        *   `r.Sym == nil || !strings.HasPrefix(r.Sym.Name, "runtime.morestack")`: シンボルが存在しないか、名前が `runtime.morestack` で始まらない場合はスキップします。
        *   `switch r.Type { ... }`: リロケーションのタイプが `obj.R_CALL` (通常の関数呼び出し) や特定のアーキテクチャ固有の呼び出しタイプ (`obj.R_CALLARM`, `obj.R_CALLARM64`, `obj.R_CALLPOWER`) であることを確認します。これにより、`morestack_noctxt` の実装で見られるような、`morestack` へのジャンプなど、呼び出しではないリロケーションを無視します。
    *   `morestack` への有効な呼び出しが見つかった場合、以下の処理が行われます。
        *   `ch.limit = limit - callsize()`: `morestack` 自体を呼び出すために必要なスタック空間を現在の制限から差し引きます。
        *   `ch.sym = r.Sym`: 呼び出し先のシンボルを設定します。
        *   `if stkcheck(&ch, depth+1) < 0 { return -1 }`: `morestack` 呼び出し自体がスタックチェックをパスできるかを確認するために、`stkcheck` を再帰的に呼び出します。
        *   `limit = int(obj.StackLimit + s.Locals)`: `morestack` が呼び出された後、スタックが拡張されたと仮定し、利用可能なスタック制限をリセットします。`s.Locals` はローカル変数に必要なスタックサイズ、`obj.StackLimit` はスタックガードのオフセットです。`haslinkregister()` が真の場合、リンクレジスタのサイズも追加されます。
        *   `break`: `morestack` への呼び出しは通常1つだけであるため、最初に見つかった時点でループを終了します。
    *   このセクションは、`morestack` 呼び出しが関数のプロローグのどこに現れても、その呼び出しが関数のエントリ時に発生したかのように処理することを保証します。

2.  **既存の呼び出し処理からの `morestack` の除外**:
    *   既存の `stkcheck` ロジックでは、関数内の命令をPC順に走査し、`obj.R_CALL` などのタイプのリロケーションに遭遇すると、それが通常の関数呼び出しであると仮定して再帰的に `stkcheck` を呼び出していました。
    *   変更後、このセクションに `if strings.HasPrefix(r.Sym.Name, "runtime.morestack") { continue }` という行が追加されました。
    *   これは、新しい事前処理ループで既に `morestack` 呼び出しが処理されているため、この既存のループでは `morestack` への呼び出しをスキップし、二重処理を防ぐためのものです。
    *   また、以前は `morestack` 呼び出しの後に `limit` を調整するロジックがありましたが、これも新しい事前処理ループに移されたため削除されています。

これらの変更により、`stkcheck` はフロー非感受性のままで、`morestack` 呼び出しが関数のプロローグ内のどこに配置されても正しくスタック使用量を分析できるようになりました。

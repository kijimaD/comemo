# [インデックス 21543] ファイルの概要

このコミットは、Goランタイムにおける`printlock`の会計処理の競合状態（race condition）を修正するものです。具体的には、ゴルーチンが`printlock`を取得しようとする際に、異なるM（OSスレッド）に再スケジュールされることで発生するデッドロックやクラッシュの可能性を排除します。

## コミット

## 変更の背景

この変更は、Goランタイムの内部でデバッグ出力を行う際に使用される`printlock`というロック機構における競合状態を修正するために導入されました。

問題の核心は、`mp.printlock++`（現在のM、すなわちOSスレッドに紐づく`printlock`カウンタをインクリメントする操作）と、実際のロック取得（`lock(&debuglock)`）の間に、ゴルーチンがプリエンプション（横取り）され、別のMに再スケジュールされる可能性があったことです。

もしこのような状況が発生すると、`mp.printlock++`は一方のMで実行されたにもかかわらず、`lock(&debuglock)`は別のMで実行されることになります。これにより、`printlock`が正しくアンロックされない状態が発生し、以下のいずれかの深刻な問題を引き起こす可能性がありました。

1.  **印刷デッドロック（printing deadlock）**: `printlock`が解放されないため、他のゴルーチンがデバッグ出力を試みてもロックを取得できず、システム全体が停止する。
2.  **クラッシュ**: ゴルーチンが元のMに再スケジュールされた際に、`m.locks > 0`（Mがロックを保持している状態）であるにもかかわらず、実際にはそのMがロックを保持していないという不整合が発生し、ランタイムがクラッシュする。

このコミットは、このような不安定な状態を回避し、ランタイムの堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスケジューラとロック機構に関するいくつかの基本的な概念を理解しておく必要があります。

*   **Goroutine (G)**: Goにおける軽量な実行単位です。OSスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行できます。Goランタイムのスケジューラによって管理されます。
*   **Machine (M)**: OSスレッドを表します。Goランタイムは、OSスレッド（M）上でゴルーチン（G）を実行します。MはOSによって管理される実際の実行コンテキストです。
*   **Processor (P)**: 論理プロセッサを表します。MとGの間に位置し、MがGを実行するためのコンテキストを提供します。Pは実行可能なゴルーチンをキューに保持し、Mに割り当てます。Goランタイムのスケジューラは、GをPに、PをMに割り当てることで並行処理を実現します。
*   **Preemption (プリエンプション)**: Goランタイムのスケジューラは、長時間実行されるゴルーチンが他のゴルーチンの実行を妨げないように、ゴルーチンを強制的に中断（プリエンプト）し、別のゴルーチンにCPUを割り当てることができます。これにより、公平なスケジューリングが保証されます。
*   **`m.locks`**: 各M（OSスレッド）が現在保持しているランタイム内部のロックの数を追跡するカウンタです。このカウンタが0より大きい場合、そのMは重要なランタイム操作を実行中であり、プリエンプションされるべきではありません。
*   **`printlock`**: Goランタイム内部でデバッグ出力を行う際に使用される、Mごとのカウンタです。`mp.printlock++`は、現在のMがデバッグ出力操作を開始したことを示します。
*   **`debuglock`**: デバッグ出力の際に排他制御を行うためのグローバルなミューテックス（ロック）です。複数のMが同時にデバッグ出力を行わないように保護します。

Goランタイムのスケジューラは、GPMモデル（Goroutine-Processor-Machine）に基づいて動作します。ゴルーチンはP上で実行され、PはMにアタッチされます。MはOSスレッドとして実際にCPU上でコードを実行します。

## 技術的詳細

このコミットが修正する問題は、Goランタイムの内部的なデバッグ出力メカニズムである`printlock`の利用方法に潜んでいました。

従来の`printlock()`関数は以下のようになっていました（簡略化）：

```go
func printlock() {
	mp := getg().m // 現在のゴルーチンが実行されているMを取得
	mp.printlock++ // Mのprintlockカウンタをインクリメント
	if mp.printlock == 1 {
		lock(&debuglock) // 初めてprintlockを取得する場合、グローバルなdebuglockを取得
	}
}
```

このコードの脆弱性は、`mp.printlock++`が実行された直後、かつ`lock(&debuglock)`が呼び出される前に、現在のゴルーチンがプリエンプションされる可能性があった点にあります。

シナリオは以下の通りです：
1.  ゴルーチンAがM1上で実行され、`printlock()`を呼び出す。
2.  `mp.printlock++`がM1上で実行され、M1の`printlock`カウンタがインクリメントされる。
3.  **この直後、ゴルーチンAがプリエンプションされる。**
4.  GoランタイムのスケジューラがゴルーチンAを別のM（例えばM2）に再スケジュールする。
5.  ゴルーチンAがM2上で実行を再開し、`lock(&debuglock)`を呼び出す。
6.  `debuglock`はM2によって取得される。

この結果、M1は`printlock`カウンタがインクリメントされた状態（`mp.printlock > 0`）であるにもかかわらず、`debuglock`はM2によって保持されています。M1は`debuglock`を保持していないため、`printunlock()`がM1上で呼び出されることはなく、M1の`printlock`カウンタはデクリメントされません。

この不整合が問題を引き起こします。
*   **デッドロック**: もしM1が`printlock`を保持していると誤解され続ければ、他のゴルーチンがM1上でデバッグ出力を試みても、`printlock`が解放されないため、`debuglock`を取得できず、デッドロックが発生します。
*   **クラッシュ**: Goランタイムでは、Mが内部ロック（例えば`debuglock`）を保持している間はプリエンプションされないように、`m.locks`というカウンタを使用します。`m.locks > 0`の場合、そのMはプリエンプションされません。しかし、上記のシナリオでは、M1は`printlock`をインクリメントしただけで`debuglock`を取得していないため、`m.locks`はインクリメントされません。もしM1がプリエンプションされ、その後別のゴルーチンがM1上で実行され、M1が`m.locks > 0`であると誤って判断した場合、ランタイムの内部状態が矛盾し、クラッシュにつながる可能性があります。

このコミットは、`mp.printlock++`と`lock(&debuglock)`の間のクリティカルセクションを保護することで、この競合状態を解消します。

## コアとなるコードの変更箇所

`src/runtime/print1.go` ファイルの `printlock()` 関数に以下の2行が追加されました。

```diff
--- a/src/runtime/print1.go
+++ b/src/runtime/print1.go
@@ -53,10 +53,12 @@ var debuglock mutex
 
 func printlock() {
 	mp := getg().m
+	mp.locks++ // do not reschedule between printlock++ and lock(&debuglock).
 	mp.printlock++
 	if mp.printlock == 1 {
 		lock(&debuglock)
 	}
+	mp.locks-- // now we know debuglock is held and holding up mp.locks for us.
 }
 
 func printunlock() {
```

## コアとなるコードの解説

追加された2行のコードは、`printlock()`関数内のクリティカルセクションを保護し、競合状態を防ぐためのものです。

1.  `mp.locks++ // do not reschedule between printlock++ and lock(&debuglock).`
    *   この行は、`mp.printlock++`が実行される直前に追加されました。
    *   `mp.locks`は、現在のM（OSスレッド）がランタイム内部のロックを保持しているかどうかを示すカウンタです。このカウンタが0より大きい場合、GoランタイムのスケジューラはそのMをプリエンプションしません。
    *   これにより、`mp.printlock++`の実行から`lock(&debuglock)`が実際に呼び出されるまでの間、ゴルーチンがプリエンプションされ、別のMに再スケジュールされることを防ぎます。この短い期間、Mは「ロックを保持している」状態とみなされ、安全に処理を進めることができます。

2.  `mp.locks-- // now we know debuglock is held and holding up mp.locks for us.`
    *   この行は、`lock(&debuglock)`が成功裏に呼び出された直後に追加されました。
    *   `debuglock`が取得された後、Mはもはや`mp.locks`をインクリメントした状態である必要はありません。なぜなら、`debuglock`自体がMのプリエンプションを防ぐ役割を果たすからです（`debuglock`は内部的に`m.locks`を操作します）。
    *   このデクリメントにより、`mp.locks`カウンタが不必要に高い値を保持することを防ぎ、正確なロック会計を維持します。

これらの変更により、`mp.printlock++`と`lock(&debuglock)`の操作がアトミック（不可分）に実行されることが保証され、ゴルーチンがこれらの操作の途中でプリエンプションされて別のMに移動する可能性がなくなります。これにより、`printlock`の会計処理の競合状態が解消され、デッドロックやクラッシュのリスクが排除されます。

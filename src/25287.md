## 変更の背景

GoコンパイラのSSAバックエンドでは、プログラムの最適化のためにSSA形式の中間表現を使用します。SSA形式では、各変数が一度だけ代入されるという特性を持ち、これによりデータフロー解析や最適化が容易になります。共通部分式除去（Common Subexpression Elimination, CSE）は、SSA形式で特に効果を発揮する最適化の一つです。CSEは、同じ計算が複数回行われている場合に、その計算を一度だけ行い、結果を再利用することで冗長な計算を排除します。

このコミット以前のGoコンパイラでは、SSA形式の`Value`オブジェクトが持つ`Aux`フィールドに、`ArgSymbol`、`AutoSymbol`、`ExternSymbol`といったシンボル情報が格納されていました。しかし、これらのシンボルが同じ論理的なエンティティ（例えば、同じ関数引数や同じローカル変数）を参照しているにもかかわらず、SSA生成の過程で毎回新しいシンボルオブジェクトが作成されてしまう問題がありました。

CSEは、`Value`オブジェクトのオペレーション、型、および`Aux`フィールドがすべて一致する場合に、それらを共通部分式として認識します。もし同じ論理的なシンボルに対して異なる`Aux`オブジェクトが生成されてしまうと、たとえそれらが同じ意味を持っていても、CSEはそれらを異なるものと判断し、最適化の機会を逃してしまいます。

この変更の背景には、このようなシンボルオブジェクトの重複生成によるCSEの非効率性を解消し、コンパイラの最適化能力を向上させるという目的があります。

## 前提知識の解説

### GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木（AST）にパースした後、中間表現（IR）に変換します。Go 1.7以降、コンパイラのバックエンドはSSA形式のIRを使用しています。SSA形式は、最適化を容易にするために設計された特殊なIRであり、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が簡素化され、より強力な最適化が可能になります。

### SSA (Static Single Assignment)

SSAは、プログラム中の各変数がただ一度だけ代入されるようにする中間表現の形式です。例えば、`x = a + b; x = c + d;` というコードは、SSAでは `x1 = a + b; x2 = c + d;` のように変換されます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が非常に効率的になります。SSAは、共通部分式除去（CSE）、定数伝播、デッドコード除去など、多くのコンパイラ最適化の基盤となります。

### Common Subexpression Elimination (CSE)

共通部分式除去（CSE）は、コンパイラ最適化の一種で、プログラム内で同じ値が複数回計算されている場合に、その計算を一度だけ行い、結果を再利用することで冗長な計算を排除します。例えば、`a = b * c; d = b * c;` というコードがあった場合、`b * c` の計算は一度で済み、その結果を `a` と `d` の両方に使用できます。SSA形式では、`Value`オブジェクトのオペレーション、型、および`Aux`フィールドがすべて一致する場合に、CSEが適用されます。

### `ssa.Value`と`Aux`フィールド

GoコンパイラのSSAバックエンドでは、`ssa.Value`がSSA形式の基本的な構成要素です。`ssa.Value`は、特定の操作の結果として生成される値を表します。各`ssa.Value`は、その操作の種類（`Op`）、型（`Type`）、オペランド（`Args`）、そして追加情報（`Aux`）を持ちます。

`Aux`フィールドは、特定の`Op`（操作）に対して追加の定数情報やシンボル情報を格納するために使用されます。例えば、メモリロード/ストア操作ではオフセット、定数操作では定数値、そしてアドレス操作（`OpAddr`）では、そのアドレスが指す対象（変数、関数など）のシンボル情報が格納されます。

CSEが正しく機能するためには、同じ論理的なエンティティを参照する`ssa.Value`オブジェクトが、同じ`Aux`フィールドを持つ必要があります。もし`Aux`フィールドが異なると、CSEはそれらを異なる値と判断し、最適化の機会を逃してしまいます。

### `ssa.ArgSymbol`, `ssa.AutoSymbol`, `ssa.ExternSymbol`

これらは、GoコンパイラのSSAバックエンドで使用されるシンボル型で、`Aux`フィールドに格納されることがあります。

*   **`ssa.ArgSymbol`**: 関数の引数を表すシンボルです。
*   **`ssa.AutoSymbol`**: ローカル変数（自動変数）を表すシンボルです。
*   **`ssa.ExternSymbol`**: グローバル変数や外部リンケージを持つ関数など、外部のシンボルを表します。

これらのシンボルは、`OpAddr`（アドレス取得）操作などで、特定のアドレスがどの変数や関数に対応するかを示すために`Aux`フィールドに設定されます。

### `*Node` (ASTノード)

Goコンパイラは、ソースコードをパースして抽象構文木（AST）を構築します。`*Node`は、このASTの各ノードを表す型です。例えば、変数宣言、関数呼び出し、式などはすべてASTノードとして表現されます。SSA生成の過程では、これらのASTノードがSSAの`Value`オブジェクトに変換されます。このコミットでは、特定のASTノード（`*Node`）に対応するシンボルを再利用することが焦点となっています。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSA生成フェーズにおいて、特定のASTノード（`*Node`）に対応するシンボル（`ssa.ArgSymbol`, `ssa.AutoSymbol`, `ssa.ExternSymbol`）を確実に再利用することです。これにより、同じ論理的なシンボルを参照するSSA `Value`オブジェクトが、同一の`Aux`フィールドを持つようになり、共通部分式除去（CSE）の効率が向上します。

具体的な変更点は以下の通りです。

1.  **`s.varsyms` マップの導入**:
    `state`構造体（SSA生成の状態を管理するオブジェクト）に、`varsyms`という新しいマップが追加されました。
    ```go
    type state struct {
        // ...
        // symbols for PEXTERN, PAUTO and PPARAMOUT variables so they can be reused.
        varsyms map[*Node]interface{}
        // ...
    }
    ```
    このマップは、`*Node`（ASTノード）をキーとし、対応するシンボル（`ssa.ArgSymbol`, `ssa.AutoSymbol`, `ssa.ExternSymbol`のいずれか）を`interface{}`型で値として保持します。これにより、特定のASTノードに対して一度生成されたシンボルを記憶し、後で同じASTノードが参照されたときにそのシンボルを再利用できるようになります。

2.  **`lookupSymbol` 関数の導入**:
    シンボルを検索・登録するためのヘルパー関数`lookupSymbol`が追加されました。
    ```go
    func (s *state) lookupSymbol(n *Node, sym interface{}) interface{} {
        switch sym.(type) {
        default:
            s.Fatalf("sym %v is of uknown type %T", sym, sym)
        case *ssa.ExternSymbol, *ssa.ArgSymbol, *ssa.AutoSymbol:
            // these are the only valid types
        }

        if lsym, ok := s.varsyms[n]; ok {
            return lsym
        } else {
            s.varsyms[n] = sym
            return sym
        }
    }
    ```
    この関数は、`*Node` `n` と、新しく生成しようとしているシンボル `sym` を引数に取ります。
    *   まず、`sym`の型が`ssa.ExternSymbol`, `ssa.ArgSymbol`, `ssa.AutoSymbol`のいずれかであることを確認します。これら以外の型が渡された場合は、コンパイラがパニックを起こします。
    *   次に、`s.varsyms`マップに`n`に対応するシンボルが既に存在するかどうかを確認します。
        *   存在する場合（`ok`が`true`）、既存のシンボル`lsym`を返します。これにより、同じASTノードに対して常に同じシンボルオブジェクトが使用されることが保証されます。
        *   存在しない場合、新しく渡された`sym`を`s.varsyms`マップに`n`のキーで登録し、その`sym`を返します。

3.  **シンボル生成箇所での`lookupSymbol`の適用**:
    `src/cmd/compile/internal/gc/ssa.go`内の複数の箇所で、`ssa.ArgSymbol`, `ssa.AutoSymbol`, `ssa.ExternSymbol`を生成する際に、直接シンボルオブジェクトを作成するのではなく、`lookupSymbol`関数を介して取得するように変更されました。

    *   **`PPARAM` (関数引数)**:
        ```diff
        -		aux := &ssa.ArgSymbol{Typ: n.Type, Node: n}
        +		aux := s.lookupSymbol(n, &ssa.ArgSymbol{Typ: n.Type, Node: n})
        ```
        関数引数のアドレスを生成する際に、`ArgSymbol`が`lookupSymbol`を介して取得されるようになりました。

    *   **`PAUTO | PHEAP` (ヒープに割り当てられたローカル変数)**:
        ```diff
        -		aux := &ssa.AutoSymbol{Typ: n.Type, Node: n}
        +		aux := s.lookupSymbol(n, &ssa.AutoSymbol{Typ: n.Type, Node: n})
        ```
        ヒープに割り当てられるローカル変数のアドレスを生成する際に、`AutoSymbol`が`lookupSymbol`を介して取得されるようになりました。

    *   **`OCFUNC` (外部関数)**:
        ```diff
        -	aux := &ssa.ExternSymbol{n.Type, n.Left.Sym}
        +	aux := s.lookupSymbol(n, &ssa.ExternSymbol{n.Type, n.Left.Sym})
        ```
        外部関数のアドレスを生成する際に、`ExternSymbol`が`lookupSymbol`を介して取得されるようになりました。

    *   **`PPARAMOUT` (戻り値パラメータ)**:
        ```diff
        -		aux := &ssa.ArgSymbol{Typ: n.Type, Node: n}
        +		aux := s.lookupSymbol(n, &ssa.ArgSymbol{Typ: n.Type, Node: n})
        ```
        戻り値パラメータのアドレスを生成する際にも、`ArgSymbol`が`lookupSymbol`を介して取得されるようになりました。コメントで「cseがそれらのアドレスで機能するように、出力パラメータのシンボルを再利用することを保証する」と明記されています。

これらの変更により、同じASTノードに対応するシンボルは、SSA生成プロセス全体で常に同じオブジェクトインスタンスを指すようになります。結果として、これらのシンボルが`Aux`フィールドに設定されたSSA `Value`オブジェクトは、同じ論理的なエンティティを参照している限り、`Aux`フィールドも同一と見なされるようになります。これにより、CSEはこれらの`Value`オブジェクトを共通部分式として正しく識別し、より効果的な最適化を適用できるようになります。

## コアとなるコードの解説

### `state` 構造体への `varsyms` フィールドの追加

`state`構造体は、SSA生成プロセス全体の状態を保持します。ここに追加された`varsyms map[*Node]interface{}`は、ASTノード（`*Node`）とそれに対応するSSAシンボルオブジェクト（`ssa.ArgSymbol`, `ssa.AutoSymbol`, `ssa.ExternSymbol`）のマッピングを記憶するためのキャッシュとして機能します。これにより、同じASTノードに対して常に同じシンボルオブジェクトが返されるようになります。

### `buildssa` 関数内での `s.varsyms` の初期化とシンボル生成の変更

`buildssa`関数は、SSA形式の関数を構築する主要なエントリポイントです。
*   `s.varsyms = map[*Node]interface{}{}`: SSA生成の開始時に、`varsyms`マップが空の状態で初期化されます。これにより、各関数のSSA生成ごとに新しいシンボルキャッシュが使用されます。
*   `case PPARAM:` と `case PAUTO | PHEAP:` の箇所では、それぞれ関数引数とヒープに割り当てられたローカル変数のアドレスを生成する際に、`ssa.ArgSymbol`と`ssa.AutoSymbol`が作成されます。以前は直接`&ssa.ArgSymbol{...}`のように新しいオブジェクトを生成していましたが、変更後は`s.lookupSymbol(n, &ssa.ArgSymbol{...})`を呼び出すことで、既存のシンボルがあればそれを再利用し、なければ新しく作成してキャッシュに登録するようになりました。

### `lookupSymbol` ヘルパー関数の追加

この関数は、シンボル再利用ロジックをカプセル化しています。
*   `switch sym.(type)`: 渡された`sym`が`ssa.ExternSymbol`, `ssa.ArgSymbol`, `ssa.AutoSymbol`のいずれかであることを確認します。これは、`varsyms`マップに格納されるシンボルの種類を制限し、予期せぬ型のシンボルがキャッシュされるのを防ぐための型安全チェックです。
*   `if lsym, ok := s.varsyms[n]; ok`: `s.varsyms`マップに、現在のASTノード`n`に対応するシンボルが既に存在するかどうかをチェックします。
    *   `ok`が`true`の場合、つまりシンボルが既にキャッシュされている場合、そのキャッシュされたシンボル`lsym`を返します。
    *   `ok`が`false`の場合、つまりシンボルがまだキャッシュされていない場合、新しく生成された`sym`を`s.varsyms[n]`に格納し、その`sym`を返します。

このメカニズムにより、同じASTノードがSSA生成プロセス中に複数回参照されたとしても、常に同じシンボルオブジェクトが`Aux`フィールドに設定されることが保証されます。

### `expr` 関数内での `OCFUNC` の変更

`expr`関数は、ASTの式ノードをSSA `Value`に変換します。`OCFUNC`ケースは、外部関数（例えば、Goの組み込み関数や外部ライブラリ関数）のアドレスを取得する際に使用されます。ここでも、`ssa.ExternSymbol`の生成が`s.lookupSymbol`を介して行われるようになり、外部関数シンボルの再利用が保証されます。

### `addr` 関数内での `PPARAMOUT` の変更

`addr`関数は、特定のノードのアドレスをSSA `Value`に変換します。`PPARAMOUT`ケースは、関数の戻り値パラメータのアドレスを処理します。ここでも、`ssa.ArgSymbol`の生成が`s.lookupSymbol`を介して行われるようになりました。これにより、戻り値パラメータのアドレスが複数回参照される場合でも、同じ`ArgSymbol`が使用され、CSEが正しく機能するようになります。

### 全体的な影響

これらの変更は、SSA `Value`オブジェクトの`Aux`フィールドに格納されるシンボルオブジェクトの同一性を保証することで、GoコンパイラのSSAバックエンドにおける共通部分式除去（CSE）の精度と効率を大幅に向上させます。結果として、より最適化された機械語コードが生成され、プログラムの実行性能が向上する可能性があります。

## 変更の背景

GoコンパイラのSSAバックエンドでは、プログラムの最適化のためにSSA形式の中間表現を使用します。SSA形式では、各変数が一度だけ代入されるという特性を持ち、これによりデータフロー解析や最適化が容易になります。共通部分式除去（Common Subexpression Elimination, CSE）は、SSA形式で特に効果を発揮する最適化の一つです。CSEは、同じ計算が複数回行われている場合に、その計算を一度だけ行い、結果を再利用することで冗長な計算を排除します。

このコミット以前のGoコンパイラでは、SSA形式の`Value`オブジェクトが持つ`Aux`フィールドに、`ArgSymbol`、`AutoSymbol`、`ExternSymbol`といったシンボル情報が格納されていました。しかし、これらのシンボルが同じ論理的なエンティティ（例えば、同じ関数引数や同じローカル変数）を参照しているにもかかわらず、SSA生成の過程で毎回新しいシンボルオブジェクトが作成されてしまう問題がありました。

CSEは、`Value`オブジェクトのオペレーション、型、および`Aux`フィールドがすべて一致する場合に、それらを共通部分式として認識します。もし同じ論理的なシンボルに対して異なる`Aux`オブジェクトが生成されてしまうと、たとえそれらが同じ意味を持っていても、CSEはそれらを異なるものと判断し、最適化の機会を逃してしまいます。

この変更の背景には、このようなシンボルオブジェクトの重複生成によるCSEの非効率性を解消し、コンパイラの最適化能力を向上させるという目的があります。

## 前提知識の解説

### GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木（AST）にパースした後、中間表現（IR）に変換します。Go 1.7以降、コンパイラのバックエンドはSSA形式のIRを使用しています。SSA形式は、最適化を容易にするために設計された特殊なIRであり、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が簡素化され、より強力な最適化が可能になります。

### SSA (Static Single Assignment)

SSAは、プログラム中の各変数がただ一度だけ代入されるようにする中間表現の形式です。例えば、`x = a + b; x = c + d;` というコードは、SSAでは `x1 = a + b; x2 = c + d;` のように変換されます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が非常に効率的になります。SSAは、共通部分式除去（CSE）、定数伝播、デッドコード除去など、多くのコンパイラ最適化の基盤となります。

### Common Subexpression Elimination (CSE)

共通部分式除去（CSE）は、コンパイラ最適化の一種で、プログラム内で同じ値が複数回計算されている場合に、その計算を一度だけ行い、結果を再利用することで冗長な計算を排除します。例えば、`a = b * c; d = b * c;` というコードがあった場合、`b * c` の計算は一度で済み、その結果を `a` と `d` の両方に使用できます。SSA形式では、`Value`オブジェクトのオペレーション、型、および`Aux`フィールドがすべて一致する場合に、CSEが適用されます。

### `ssa.Value`と`Aux`フィールド

GoコンパイラのSSAバックエンドでは、`ssa.Value`がSSA形式の基本的な構成要素です。`ssa.Value`は、特定の操作の結果として生成される値を表します。各`ssa.Value`は、その操作の種類（`Op`）、型（`Type`）、オペランド（`Args`）、そして追加情報（`Aux`）を持ちます。

`Aux`フィールドは、特定の`Op`（操作）に対して追加の定数情報やシンボル情報を格納するために使用されます。例えば、メモリロード/ストア操作ではオフセット、定数操作では定数値、そしてアドレス操作（`OpAddr`）では、そのアドレスが指す対象（変数、関数など）のシンボル情報が格納されます。

CSEが正しく機能するためには、同じ論理的なエンティティを参照する`ssa.Value`オブジェクトが、同じ`Aux`フィールドを持つ必要があります。もし`Aux`フィールドが異なると、CSEはそれらを異なる値と判断し、最適化の機会を逃してしまいます。

### `ssa.ArgSymbol`, `ssa.AutoSymbol`, `ssa.ExternSymbol`

これらは、GoコンパイラのSSAバックエンドで使用されるシンボル型で、`Aux`フィールドに格納されることがあります。

*   **`ssa.ArgSymbol`**: 関数の引数を表すシンボルです。
*   **`ssa.AutoSymbol`**: ローカル変数（自動変数）を表すシンボルです。
*   **`ssa.ExternSymbol`**: グローバル変数や外部リンケージを持つ関数など、外部のシンボルを表します。

これらのシンボルは、`OpAddr`（アドレス取得）操作などで、特定のアドレスがどの変数や関数に対応するかを示すために`Aux`フィールドに設定されます。

### `*Node` (ASTノード)

Goコンパイラは、ソースコードをパースして抽象構文木（AST）を構築します。`*Node`は、このASTの各ノードを表す型です。例えば、変数宣言、関数呼び出し、式などはすべてASTノードとして表現されます。SSA生成の過程では、これらのASTノードがSSAの`Value`オブジェクトに変換されます。このコミットでは、特定のASTノード（`*Node`）に対応するシンボルを再利用することが焦点となっています。

このコミットの核心は、GoコンパイラのSSA生成フェーズにおいて、特定のASTノード（`*Node`）に対応するシンボル（`ssa.ArgSymbol`, `ssa.AutoSymbol`, `ssa.ExternSymbol`）を確実に再利用することです。これにより、同じ論理的なシンボルを参照するSSA `Value`オブジェクトが、同一の`Aux`フィールドを持つようになり、共通部分式除去（CSE）の効率が向上します。

2.  **`lookupSymbol` 関数の導入**:
    シンボルを検索・登録するためのヘルパー関数`lookupSymbol`が追加されました。
    ```go

        switch sym.(type) {
        default:
            s.Fatalf("sym %v is of uknown type %T", sym, sym)
        case *ssa.ExternSymbol, *ssa.ArgSymbol, *ssa.AutoSymbol:
            // these are the only valid types
        }

        if lsym, ok := s.varsyms[n]; ok {
            return lsym
        } else {
            s.varsyms[n] = sym
            return sym
        }
    }
    ```
    この関数は、`*Node` `n` と、新しく生成しようとしているシンボル `sym` を引数に取ります。
    *   まず、`sym`の型が`ssa.ExternSymbol`, `ssa.ArgSymbol`, `ssa.AutoSymbol`のいずれかであることを確認します。これら以外の型が渡された場合は、コンパイラがパニックを起こします。
    *   次に、`s.varsyms`マップに`n`に対応するシンボルが既に存在するかどうかを確認します。

        *   存在しない場合、新しく渡された`sym`を`s.varsyms`マップに`n`のキーで登録し、その`sym`を返します。

    `src/cmd/compile/internal/gc/ssa.go`内の複数の箇所で、`ssa.ArgSymbol`, `ssa.AutoSymbol`, `ssa.ExternSymbol`を生成する際に、直接シンボルオブジェクトを作成するのではなく、`lookupSymbol`関数を介して取得するように変更されました。

    *   **`PPARAM` (関数引数)**:

    *   **`PAUTO | PHEAP` (ヒープに割り当てられたローカル変数)**:

        +		aux := s.lookupSymbol(n, &ssa.AutoSymbol{Typ: n.Type, Node: n})
        ```
        ヒープに割り当てられるローカル変数のアドレスを生成する際に、`AutoSymbol`が`lookupSymbol`を介して取得されるようになりました。

    *   **`OCFUNC` (外部関数)**:

    *   **`PPARAMOUT` (戻り値パラメータ)**:

        ```

これらの変更により、同じASTノードに対応するシンボルは、SSA生成プロセス全体で常に同じオブジェクトインスタンスを指すようになります。結果として、これらのシンボルが`Aux`フィールドに設定されたSSA `Value`オブジェクトは、同じ論理的なエンティティを参照している限り、`Aux`フィールドも同一と見なされるようになります。これにより、CSEはこれらの`Value`オブジェクトを共通部分式として正しく識別し、より効果的な最適化を適用できるようになります。

## コアとなるコードの解説

### `state` 構造体への `varsyms` フィールドの追加

`state`構造体は、SSA生成プロセス全体の状態を保持します。ここに追加された`varsyms map[*Node]interface{}`は、ASTノード（`*Node`）とそれに対応するSSAシンボルオブジェクト（`ssa.ArgSymbol`, `ssa.AutoSymbol`, `ssa.ExternSymbol`）のマッピングを記憶するためのキャッシュとして機能します。これにより、同じASTノードに対して常に同じシンボルオブジェクトが返されるようになります。

### `buildssa` 関数内での `s.varsyms` の初期化とシンボル生成の変更

`buildssa`関数は、SSA形式の関数を構築する主要なエントリポイントです。
*   `s.varsyms = map[*Node]interface{}{}`: SSA生成の開始時に、`varsyms`マップが空の状態で初期化されます。これにより、各関数のSSA生成ごとに新しいシンボルキャッシュが使用されます。
*   `case PPARAM:` と `case PAUTO | PHEAP:` の箇所では、それぞれ関数引数とヒープに割り当てられたローカル変数のアドレスを生成する際に、`ssa.ArgSymbol`と`ssa.AutoSymbol`が作成されます。以前は直接`&ssa.ArgSymbol{...}`のように新しいオブジェクトを生成していましたが、変更後は`s.lookupSymbol(n, &ssa.ArgSymbol{...})`を呼び出すことで、既存のシンボルがあればそれを再利用し、なければ新しく作成してキャッシュに登録するようになりました。

### `lookupSymbol` ヘルパー関数の追加

この関数は、シンボル再利用ロジックをカプセル化しています。
*   `switch sym.(type)`: 渡された`sym`が`ssa.ExternSymbol`, `ssa.ArgSymbol`, `ssa.AutoSymbol`のいずれかであることを確認します。これは、`varsyms`マップに格納されるシンボルの種類を制限し、予期せぬ型のシンボルがキャッシュされるのを防ぐための型安全チェックです。
*   `if lsym, ok := s.varsyms[n]; ok`: `s.varsyms`マップに、現在のASTノード`n`に対応するシンボルが既に存在するかどうかをチェックします。
    *   `ok`が`true`の場合、つまりシンボルが既にキャッシュされている場合、そのキャッシュされたシンボル`lsym`を返します。
    *   `ok`が`false`の場合、つまりシンボルがまだキャッシュされていない場合、新しく生成された`sym`を`s.varsyms[n]`に格納し、その`sym`を返します。

このメカニズムにより、同じASTノードがSSA生成プロセス中に複数回参照されたとしても、常に同じシンボルオブジェクトが`Aux`フィールドに設定されることが保証されます。

### `expr` 関数内での `OCFUNC` の変更

`expr`関数は、ASTの式ノードをSSA `Value`に変換します。`OCFUNC`ケースは、外部関数（例えば、Goの組み込み関数や外部ライブラリ関数）のアドレスを取得する際に使用されます。ここでも、`ssa.ExternSymbol`の生成が`s.lookupSymbol`を介して行われるようになり、外部関数シンボルの再利用が保証されます。

### `addr` 関数内での `PPARAMOUT` の変更

`addr`関数は、特定のノードのアドレスをSSA `Value`に変換します。`PPARAMOUT`ケースは、関数の戻り値パラメータのアドレスを処理します。ここでも、`ssa.ArgSymbol`の生成が`s.lookupSymbol`を介して行われるようになりました。これにより、戻り値パラメータのアドレスが複数回参照される場合でも、同じ`ArgSymbol`が使用され、CSEが正しく機能するようになります。

### 全体的な影響

これらの変更は、SSA `Value`オブジェクトの`Aux`フィールドに格納されるシンボルオブジェクトの同一性を保証することで、GoコンパイラのSSAバックエンドにおける共通部分式除去（CSE）の精度と効率を大幅に向上させます。結果として、より最適化された機械語コードが生成され、プログラムの実行性能が向上する可能性があります。

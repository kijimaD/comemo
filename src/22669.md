## 変更の背景

このコミットは、Goコンパイラの内部データ構造である`Node`型のリファクタリングを目的としています。`Node`型は、Goプログラムの抽象構文木（AST）を表現するために使用され、様々な種類のノード（変数、関数、式など）を表現します。以前は、関数に関連する多くのフィールド（例: `Dcl`、`Inl`、`Endlineno`など）が`Node`構造体に直接埋め込まれていました。

この直接埋め込みは、`Node`が関数を表す場合にのみ意味を持つフィールドが、関数以外の`Node`にも存在するという状況を生み出していました。これは、コードの意図を不明瞭にし、将来的な拡張や変更を複雑にする可能性がありました。

このコミットは、`CL 7360`のフォローアップとして行われたと述べられています。`CL 7360`の具体的な内容は特定できませんでしたが、おそらく`Node`構造体やその関連する型に何らかの変更が加えられ、その結果として、関数固有のフィールドをより論理的にグループ化する必要性が生じたと考えられます。この「アンエンベッド」は、コンパイラの内部コードの整理と保守性の向上を目的としたものです。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラの概念に関する知識が役立ちます。

1.  **Goコンパイラ (`cmd/internal/gc`)**: Go言語の公式コンパイラであり、Goソースコードを機械語に変換する役割を担います。`cmd/internal/gc`は、その内部パッケージ群を指します。
2.  **抽象構文木 (AST - Abstract Syntax Tree)**: コンパイラがソースコードを解析する際に生成する、プログラムの構造を木構造で表現したものです。各ノードは、変数宣言、関数定義、式、文などのプログラム要素に対応します。
3.  **`Node`構造体**: Goコンパイラの内部でASTの各要素を表現するために使用される汎用的な構造体です。`Node`は、その`Op`（操作コード）フィールドによって、それがどのような種類のプログラム要素（例: `ODCLFUNC`は関数宣言、`ONAME`は名前付きエンティティ）であるかを区別します。
4.  **Goの構造体埋め込み (Struct Embedding)**: Go言語のユニークな機能の一つで、ある構造体の中に別の構造体をフィールド名なしで宣言することで、その埋め込まれた構造体のフィールドやメソッドを、外側の構造体のフィールドやメソッドであるかのように直接アクセスできるようにするものです。これは、継承に似た振る舞いを実現しますが、実際にはコンポジション（合成）の一種です。
    *   例:
        ```go
        type Inner struct {
            FieldA int
        }

        type Outer struct {
            Inner // 埋め込み
            FieldB string
        }

        func main() {
            o := Outer{Inner: Inner{FieldA: 10}, FieldB: "hello"}
            fmt.Println(o.FieldA) // Inner.FieldA に直接アクセス
        }
        ```
5.  **`eg` と `gofmt -r`**:
    *   `gofmt -r`: Goのコードフォーマッタ`gofmt`の`-r`オプションは、指定された書き換えルール（rewrite rules）に基づいてコードを自動的に変換する機能です。これは、大規模なコードベースで一貫したリファクタリングを適用する際に非常に強力なツールです。
    *   `eg`: `eg`は、`gofmt -r`のようなリファクタリングツールを生成するためのツールです。このコミットが`eg`によって生成されたということは、この変更が手動で一つずつ行われたのではなく、パターンマッチングと置換によって自動化されたことを意味します。

## 技術的詳細

このコミットの核心は、`src/cmd/internal/gc/syntax.go`ファイルにおける`Node`構造体の定義変更にあります。

変更前は、`Node`構造体に関数固有のフィールドが直接定義されていました。例えば、関数の宣言リスト（`Dcl`）、インライン化されたボディ（`Inl`）、終了行番号（`Endlineno`）、その他関数に関連するフラグ（`Nosplit`、`Nowritebarrier`、`Dupok`、`Needctxt`、`Wrapper`）などが直接`Node`のメンバーでした。

変更後、これらの関数固有のフィールドは、`Func`という新しい構造体（またはポインタ）にまとめられ、その`Func`構造体が`Node`構造体に埋め込まれる形になりました。

具体的には、`syntax.go`の`Node`構造体において、以下の変更が行われました。

```diff
--- a/src/cmd/internal/gc/syntax.go
+++ b/src/cmd/internal/gc/syntax.go
@@ -61,7 +61,7 @@ type Node struct {
 	Nname *Node
 
 	// func
-	*Func
+	Func *Func
 
 	// OLITERAL/OREGISTER
 	Val Val
```

この変更により、以前は`n.Dcl`のように直接アクセスしていたフィールドが、`n.Func.Dcl`のように`Func`フィールドを介してアクセスされるようになりました。

このリファクタリングの利点は以下の通りです。

*   **関心の分離**: `Node`構造体が持つべき汎用的な情報と、関数ノードにのみ関連する情報を明確に分離します。これにより、`Node`構造体の役割がより明確になり、コードの理解が容易になります。
*   **メモリ効率の改善（ポインタの場合）**: もし`Func`がポインタとして埋め込まれている場合（`Func *Func`）、関数ではない`Node`インスタンスでは`Func`ポインタが`nil`になり、関数固有のフィールドが占めるメモリを節約できます。ただし、このコミットのdiffを見る限り、`*Func`から`Func *Func`への変更なので、ポインタ埋め込み自体は以前から行われていた可能性が高いです。重要なのは、`Func`という名前付きフィールドになったことです。
*   **コードの可読性**: `n.Func.Dcl`のようにアクセスすることで、そのフィールドが関数に関連するものであることが一目でわかるようになります。
*   **将来的な拡張性**: 関数に関連する新しいフィールドを追加する際に、`Node`構造体自体を肥大化させることなく、`Func`構造体内に集約して追加できます。

この変更は、`eg`と`gofmt -r`というツールによって自動的に生成されたとコミットメッセージに記載されています。これは、Goコンパイラの開発において、大規模なコードベース全体にわたる一貫したリファクタリングを効率的に行うための自動化ツールが活用されていることを示しています。手動での変更は`syntax.go`での`Func`のアンエンベッドと、`y.go`から`go.y`への変更のバックポートに限定されています。`y.go`と`go.y`は、Goコンパイラの字句解析器/構文解析器の定義ファイルであり、構文木の構築に関連する部分で手動調整が必要だったことを示唆しています。

## コアとなるコードの変更箇所

このコミットは、Goコンパイラの`src/cmd/internal/gc`ディレクトリ内の多数のファイルに影響を与えています。主な変更は、`Node`構造体のフィールドへのアクセス方法の変更です。

*   `n.Endlineno` -> `n.Func.Endlineno`

これらの変更は、`src/cmd/5g/ggen.go`から`src/cmd/internal/gc/walk.go`までの広範なファイルにわたって見られます。特に、`closure.go`、`inl.go`、`pgen.go`など、関数やインライン化、コード生成に関連するファイルで多くの変更が行われています。

また、`src/cmd/internal/gc/syntax.go`では、`Node`構造体自体の定義が変更されています。

```go
// src/cmd/internal/gc/syntax.go (変更後の一部)
type Node struct {
	// ... 既存のフィールド ...
	Nname *Node

	// func
	Func *Func // ここが変更点

	// OLITERAL/OREGISTER
	Val Val
	// ... その他のフィールド ...
}
```

そして、`Func`構造体（またはその定義）が別途存在し、そこに以前`Node`に直接あった関数固有のフィールドが定義されていると推測されます。

## コアとなるコードの解説

このコミットの主要な変更は、GoコンパイラのASTノード表現における関数の属性の構造化です。

以前の`Node`構造体は、Goプログラム内のあらゆる種類の構文要素（変数、型、関数、文など）を表現するために使用されていました。しかし、関数に関連する特定の属性（例: 関数の宣言リスト、インライン化情報、特定のコンパイラフラグなど）は、関数ノードにのみ適用されるべきものです。これらの属性が`Node`構造体に直接存在すると、関数ではないノードに対してもこれらのフィールドが存在することになり、メモリの無駄や、コードの意図の不明瞭さにつながる可能性がありました。

このコミットでは、`Node`構造体内に`Func *Func`というフィールドを導入し、関数固有の属性を`Func`構造体（またはそのポインタ）の内部に移動させました。これにより、`Node`が関数を表す場合にのみ`Func`フィールドが非`nil`となり、その内部の属性にアクセスできるようになります。関数ではないノードの場合、`Func`フィールドは`nil`のままであり、関連しない属性が存在しないことが明確になります。

この変更は、Goの構造体埋め込みの概念を逆転させた「アンエンベッド」と表現されています。Goの埋め込みは、埋め込まれた構造体のフィールドを外側の構造体から直接アクセスできるようにしますが、このコミットでは、以前直接アクセス可能だったフィールドを、明示的な名前（`Func`）を持つサブ構造体の中に移動させることで、アクセスパスを`n.Func.Field`のように変更しています。

このリファクタリングは、コンパイラの内部コードの健全性を高めるためのものです。

*   **型安全性の向上**: 関数固有の操作が`n.Func`を介して行われることで、コンパイラの他の部分で誤って関数ではない`Node`に対して関数固有の属性にアクセスしようとするエラーを防ぐことができます。
*   **コードのモジュール化**: 関数に関連するロジックやデータが`Func`構造体内にカプセル化されることで、コンパイラの各部分がより独立し、理解しやすくなります。
*   **保守性の向上**: 将来的にGo言語の機能が追加され、関数に新しい属性が必要になった場合でも、`Node`構造体全体を変更するのではなく、`Func`構造体のみを変更すればよくなります。

この変更が`eg`と`gofmt -r`によって自動生成されたという事実は、Go開発チームが大規模なコードベースの品質を維持するために、高度な自動化ツールを積極的に利用していることを示しています。これにより、手動でのエラーを最小限に抑えつつ、一貫したリファクタリングを迅速に適用することが可能になります。

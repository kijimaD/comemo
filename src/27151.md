# [インデックス 27151] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）における静的データの処理方法を最適化するものです。具体的には、静的データを表現するためにこれまで使用されていた内部的な「ADATA命令」の生成を避け、代わりにリンカシンボル（`LSym`）に直接データを書き込むように変更することで、コンパイル時の効率を大幅に向上させています。特に`unicode`パッケージのような大量の静的データを持つパッケージのコンパイルにおいて、顕著なパフォーマンス改善が見られます。

## 変更の背景

この変更の主な背景は、Goコンパイラにおける静的データの処理効率の改善です。以前のGoコンパイラでは、静的データを表現するために「ADATA命令」と呼ばれる中間表現を生成していました。この方法は、特に`unicode`パッケージのように大量の静的データを持つ場合に、コンパイル時間とメモリ使用量のオーバーヘッドが大きくなるという問題がありました。

コミットメッセージによると、この「ADATA命令」の生成プロセスは非効率であり、コンパイルのボトルネックとなっていました。そこで、静的データを直接リンカシンボルに書き込むことで、この中間ステップを省略し、コンパイルプロセスを高速化し、メモリ消費を削減することが目的とされました。

ベンチマーク結果が示すように、`unicode`パッケージのコンパイルにおいて、実行時間、メモリ割り当て、割り当て回数の全てで顕著な改善が見られており、この最適化が特に静的データが豊富なコードベースで有効であることが裏付けられています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラとリンカに関する基本的な概念を理解しておく必要があります。

1.  **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換するツールです。コンパイルの過程で、抽象構文木（AST）の生成、型チェック、最適化、そして最終的なアセンブリコードまたはオブジェクトコードの生成を行います。
2.  **Goリンカ (`cmd/link`)**: コンパイラによって生成された複数のオブジェクトファイルやライブラリを結合し、実行可能なバイナリファイルを生成するツールです。リンカは、シンボル解決（異なるオブジェクトファイル間で参照される関数や変数のアドレスを決定すること）や、再配置（コードやデータ内のアドレス参照を実際のメモリ位置に調整すること）を行います。
3.  **シンボル (Symbol)**: プログラム内の関数、変数、定数などの名前付きエンティティを指します。コンパイルされたコードでは、これらのシンボルはメモリ上の特定のアドレスに関連付けられます。Goコンパイラとリンカは、これらのシンボルを`LSym`（Linker Symbol）という内部構造で管理します。
4.  **静的データ (Static Data)**: プログラムの実行中に値が変化しないデータで、コンパイル時にその内容が決定され、プログラムのデータセクションに格納されます。例えば、グローバル変数、文字列リテラル、定数などがこれに該当します。
5.  **ADATA命令 (ADATA instructions)**: コミットメッセージに登場するこの用語は、Goコンパイラの内部的な中間表現の一つであったと考えられます。一般的なアセンブラの文脈で「ADATA」という命令セットは存在しないため、Goコンパイラが静的データを表現するために独自に定義していた、あるいはそのように呼ばれていた内部的な命令シーケンスやデータ構造を指していると推測されます。この命令は、静的データをリンカに渡すための抽象的な指示として機能していた可能性があります。
6.  **再配置 (Relocation)**: コンパイラが生成するオブジェクトコードには、まだ最終的なメモリ上のアドレスが決定されていない参照（例えば、他のモジュールで定義された関数への呼び出しやグローバル変数へのアクセス）が含まれています。リンカは、これらの参照を解決し、実際のメモリ上のアドレスに置き換える作業を行います。これが再配置です。再配置情報は、オブジェクトファイル内に含まれています。
7.  **`toolstash -cmp`**: Go開発で使われる内部ツールで、コンパイラの変更が生成されるバイナリに機能的な影響を与えないことを確認するために、変更前と変更後のコンパイラで同じソースコードをコンパイルし、その出力を比較するものです。出力が完全に一致しない場合、機能的な変更があったか、あるいはバイナリの構造に非本質的な変更があったことを示します。

## 技術的詳細

このコミットの核心は、Goコンパイラが静的データを処理する際の「ADATA命令」の生成を廃止し、代わりにリンカシンボル（`LSym`）に直接データを書き込むように変更した点にあります。

以前のフロー（推測）：
1.  Goコンパイラは、静的データ（文字列、数値、アドレスなど）を検出すると、それを表現するための「ADATA命令」を生成。
2.  これらのADATA命令は、コンパイラの内部リストに追加され、最終的にオブジェクトファイルの一部として出力される。
3.  リンカはオブジェクトファイル内のADATA命令を読み取り、それに基づいて最終的なバイナリのデータセクションに静的データを配置し、必要な再配置情報を生成。

新しいフロー：
1.  Goコンパイラは、静的データを検出すると、`LSym`構造体（リンカシンボル）のメソッドを直接呼び出して、そのシンボルが指すメモリ領域にデータを書き込む。
2.  この際、`LSym`の`WriteFloat32`, `WriteFloat64`, `WriteInt`, `WriteAddr`, `WriteString`といった新しいヘルパーメソッドが使用される。
3.  これらのメソッドは、必要に応じてシンボルのデータ領域を拡張し（`prepwrite`）、指定されたオフセットに直接バイナリデータを書き込む。アドレス参照の場合には、対応する再配置情報（`R_ADDR`）も同時に`LSym`に追加される。
4.  これにより、ADATA命令という中間表現の生成と処理のオーバーヘッドが削減される。

この変更により、コンパイラは静的データをより直接的かつ効率的にリンカに伝えることができるようになります。特に、`unicode`パッケージのように大量の静的データ（文字テーブル、プロパティ情報など）を持つ場合、ADATA命令の生成と処理にかかるコストが大きかったため、この最適化が大きな効果を発揮しました。

コミットメッセージにある`toolstash -cmp`が失敗する件については、この変更が再配置の追加順序を変更するため、コンパイラの出力（オブジェクトファイル）が以前と完全に一致しなくなることが原因です。しかし、これは機能的な変更ではなく、再配置の順序が最終的なプログラムの動作に影響を与えないため、「表面的で非機能的」な変更と判断されています。

## コアとなるコードの変更箇所

このコミットでは主に以下の2つのファイルが変更されています。

1.  **`src/cmd/compile/internal/gc/obj.go`**:
    *   `dgostrlitptr`, `dsname`, `dsymptr`, `gdata`, `gdatacomplex`, `gdatastring`といった関数内で、`obj.ADATA`命令を生成するコードが削除され、代わりに`Linksym(s).Write...`形式のメソッド呼び出しに置き換えられています。
    *   例えば、`dgostrlitptr`関数では、文字列リテラルのポインタを処理する際に、以前は`Thearch.Gins(obj.ADATA, ...)`でADATA命令を生成していましたが、新しいコードでは`Linksym(s).WriteAddr(...)`を直接呼び出しています。
    *   `gdata`関数は、様々なリテラル型（整数、浮動小数点数、文字列、アドレスなど）の静的データを処理する汎用的な関数ですが、ここでも`obj.ADATA`命令の生成ロジックが削除され、各型に応じた`Linksym(nam.Sym).Write...`メソッド呼び出しに分岐する`switch`文が導入されています。

2.  **`src/cmd/internal/obj/data.go`**:
    *   `LSym`構造体（リンカシンボル）に、静的データを直接書き込むための新しいヘルパーメソッドが多数追加されています。
        *   `prepwrite(ctxt *Link, off, siz int64)`: データを書き込む前に、シンボルのデータ領域を確保・拡張するための内部ヘルパー。
        *   `WriteFloat32(ctxt *Link, off int64, f float32)`: 32ビット浮動小数点数を書き込む。
        *   `WriteFloat64(ctxt *Link, off int64, f float64)`: 64ビット浮動小数点数を書き込む。
        *   `WriteInt(ctxt *Link, off, siz int64, i int64)`: 指定されたサイズの整数を書き込む。
        *   `WriteAddr(ctxt *Link, off, siz int64, rsym *LSym, roff int64)`: アドレスを書き込み、同時に再配置情報（`R_ADDR`）を追加する。
        *   `WriteString(ctxt *Link, off, siz int64, str string)`: 文字列を書き込む。

## コアとなるコードの解説

このコミットのコアとなる変更は、Goコンパイラのバックエンドとリンカの間のインターフェースをより直接的なものにした点にあります。

`src/cmd/compile/internal/gc/obj.go`の変更は、コンパイラが静的データを扱う際の「命令生成」という間接的なアプローチから、「シンボルへの直接書き込み」という直接的なアプローチへの移行を示しています。
例えば、`dsymptr`関数はシンボルへのポインタを静的データとして書き込む役割を担いますが、変更前は以下のようなADATA命令を生成していました。

```go
// 変更前 (obj.go)
p := Thearch.Gins(obj.ADATA, nil, nil)
p.From.Type = obj.TYPE_MEM
p.From.Name = obj.NAME_EXTERN
p.From.Sym = Linksym(s)
p.From.Offset = int64(off)
p.From3 = new(obj.Addr)
p.From3.Type = obj.TYPE_CONST
p.From3.Offset = int64(Widthptr)
p.To.Type = obj.TYPE_ADDR
p.To.Name = obj.NAME_EXTERN
p.To.Sym = Linksym(x)
p.To.Offset = int64(xoff)
```
このコードは、`obj.ADATA`という種類の命令を生成し、その命令のフィールド（`From`, `To`, `From3`など）に静的データに関する情報を設定していました。リンカはこの命令を解釈してデータを処理します。

変更後は、この複雑な命令生成が、`src/cmd/internal/obj/data.go`で新しく定義された`LSym`のメソッド呼び出しに置き換えられています。

```go
// 変更後 (obj.go)
Linksym(s).WriteAddr(Ctxt, int64(off), int64(Widthptr), Linksym(x), int64(xoff))
```
この一行のコードは、`s`というシンボルに対して、`off`オフセットから`Widthptr`バイトのサイズで、`x`というシンボルへのアドレス（オフセット`xoff`付き）を直接書き込むことを指示しています。

`src/cmd/internal/obj/data.go`で追加された`LSym`のメソッド群は、この直接書き込みを可能にするための基盤を提供します。
特に重要なのは`WriteAddr`メソッドです。

```go
// WriteAddr writes an address of size siz into s at offset off.
// rsym and roff specify the relocation for the address.
func (s *LSym) WriteAddr(ctxt *Link, off, siz int64, rsym *LSym, roff int64) {
	s.prepwrite(ctxt, off, siz) // データ領域の確保
	r := Addrel(s)              // 再配置情報の追加
	r.Off = int32(off)
	r.Siz = uint8(siz)
	r.Sym = rsym
	r.Type = R_ADDR             // アドレス再配置タイプ
	r.Add = roff
}
```
このメソッドは、単にデータを書き込むだけでなく、アドレス参照の場合に必要となる再配置情報（`R_ADDR`）を`LSym`に直接追加しています。これにより、リンカは後でこの再配置情報を利用して、最終的なアドレスを解決することができます。

この変更は、コンパイラとリンカの間の結合をより密接にし、中間表現のオーバーヘッドを削減することで、コンパイルパイプライン全体の効率を向上させるものです。特に、静的データの処理パスが簡素化され、メモリ割り当てと処理時間が削減される効果があります。

この変更の主な背景は、Goコンパイラにおける静的データの処理効率の改善です。以前のGoコンパイラでは、静的データを表現するために「ADATA命令」と呼ばれる中間表現を生成していました。この方法は、特に`unicode`パッケージのように大量の静的データを持つ場合に、コンパイル時間とメモリ使用量のオーバーヘッドが大きくなるという問題がありました。

ベンチマーク結果が示すように、`unicode`パッケージのコンパイルにおいて、実行時間、メモリ割り当て、割り当て回数の全てで顕著な改善が見られており、この最適化が特に静的データが豊富なコードベースで有効であることが裏付けられています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラとリンカに関する基本的な概念を理解しておく必要があります。

1.  **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換するツールです。コンパイルの過程で、抽象構文木（AST）の生成、型チェック、最適化、そして最終的なアセンブリコードまたはオブジェクトコードの生成を行います。
2.  **Goリンカ (`cmd/link`)**: コンパイラによって生成された複数のオブジェクトファイルやライブラリを結合し、実行可能なバイナリファイルを生成するツールです。リンカは、シンボル解決（異なるオブジェクトファイル間で参照される関数や変数のアドレスを決定すること）や、再配置（コードやデータ内のアドレス参照を実際のメモリ位置に調整すること）を行います。
3.  **シンボル (Symbol)**: プログラム内の関数、変数、定数などの名前付きエンティティを指します。コンパイルされたコードでは、これらのシンボルはメモリ上の特定のアドレスに関連付けられます。Goコンパイラとリンカは、これらのシンボルを`LSym`（Linker Symbol）という内部構造で管理します。
4.  **静的データ (Static Data)**: プログラムの実行中に値が変化しないデータで、コンパイル時にその内容が決定され、プログラムのデータセクションに格納されます。例えば、グローバル変数、文字列リテラル、定数などがこれに該当します。
5.  **ADATA命令 (ADATA instructions)**: コミットメッセージに登場するこの用語は、Goコンパイラの内部的な中間表現の一つであったと考えられます。一般的なアセンブラの文脈で「ADATA」という命令セットは存在しないため、Goコンパイラが静的データを表現するために独自に定義していた、あるいはそのように呼ばれていた内部的な命令シーケンスやデータ構造を指していると推測されます。この命令は、静的データをリンカに渡すための抽象的な指示として機能していた可能性があります。
6.  **再配置 (Relocation)**: コンパイラが生成するオブジェクトコードには、まだ最終的なメモリ上のアドレスが決定されていない参照（例えば、他のモジュールで定義された関数への呼び出しやグローバル変数へのアクセス）が含まれています。リンカは、これらの参照を解決し、実際のメモリ上のアドレスに置き換える作業を行います。これが再配置です。再配置情報は、オブジェクトファイル内に含まれています。
7.  **`toolstash -cmp`**: Go開発で使われる内部ツールで、コンパイラの変更が生成されるバイナリに機能的な影響を与えないことを確認するために、変更前と変更後のコンパイラで同じソースコードをコンパイルし、その出力を比較するものです。出力が完全に一致しない場合、機能的な変更があったか、あるいはバイナリの構造に非本質的な変更があったことを示します。

## 技術的詳細

このコミットの核心は、Goコンパイラが静的データを処理する際の「ADATA命令」の生成を廃止し、代わりにリンカシンボル（`LSym`）に直接データを書き込むように変更した点にあります。

以前のフロー（推測）：
1.  Goコンパイラは、静的データ（文字列、数値、アドレスなど）を検出すると、それを表現するための「ADATA命令」を生成。
2.  これらのADATA命令は、コンパイラの内部リストに追加され、最終的にオブジェクトファイルの一部として出力される。
3.  リンカはオブジェクトファイル内のADATA命令を読み取り、それに基づいて最終的なバイナリのデータセクションに静的データを配置し、必要な再配置情報を生成。

新しいフロー：
1.  Goコンパイラは、静的データを検出すると、`LSym`構造体（リンカシンボル）のメソッドを直接呼び出して、そのシンボルが指すメモリ領域にデータを書き込む。
2.  この際、`LSym`の`WriteFloat32`, `WriteFloat64`, `WriteInt`, `WriteAddr`, `WriteString`といった新しいヘルパーメソッドが使用される。
3.  これらのメソッドは、必要に応じてシンボルのデータ領域を拡張し（`prepwrite`）、指定されたオフセットに直接バイナリデータを書き込む。アドレス参照の場合には、対応する再配置情報（`R_ADDR`）も同時に`LSym`に追加される。
4.  これにより、ADATA命令という中間表現の生成と処理のオーバーヘッドが削減される。

この変更により、コンパイラは静的データをより直接的かつ効率的にリンカに伝えることができるようになります。特に、`unicode`パッケージのように大量の静的データ（文字テーブル、プロパティ情報など）を持つ場合、ADATA命令の生成と処理にかかるコストが大きかったため、この最適化が大きな効果を発揮しました。

コミットメッセージにある`toolstash -cmp`が失敗する件については、この変更が再配置の追加順序を変更するため、コンパイラの出力（オブジェクトファイル）が以前と完全に一致しなくなることが原因です。しかし、これは機能的な変更ではなく、再配置の順序が最終的なプログラムの動作に影響を与えないため、「表面的で非機能的」な変更と判断されています。

## コアとなるコードの変更箇所

このコミットでは主に以下の2つのファイルが変更されています。

1.  **`src/cmd/compile/internal/gc/obj.go`**:
    *   `dgostrlitptr`, `dsname`, `dsymptr`, `gdata`, `gdatacomplex`, `gdatastring`といった関数内で、`obj.ADATA`命令を生成するコードが削除され、代わりに`Linksym(s).Write...`形式のメソッド呼び出しに置き換えられています。
    *   例えば、`dgostrlitptr`関数では、文字列リテラルのポインタを処理する際に、以前は`Thearch.Gins(obj.ADATA, ...)`でADATA命令を生成していましたが、新しいコードでは`Linksym(s).WriteAddr(...)`を直接呼び出しています。
    *   `gdata`関数は、様々なリテラル型（整数、浮動小数点数、文字列、アドレスなど）の静的データを処理する汎用的な関数ですが、ここでも`obj.ADATA`命令の生成ロジックが削除され、各型に応じた`Linksym(nam.Sym).Write...`メソッド呼び出しに分岐する`switch`文が導入されています。

2.  **`src/cmd/internal/obj/data.go`**:
    *   `LSym`構造体（リンカシンボル）に、静的データを直接書き込むための新しいヘルパーメソッドが多数追加されています。
        *   `prepwrite(ctxt *Link, off, siz int64)`: データを書き込む前に、シンボルのデータ領域を確保・拡張するための内部ヘルパー。
        *   `WriteFloat32(ctxt *Link, off int64, f float32)`: 32ビット浮動小数点数を書き込む。
        *   `WriteFloat64(ctxt *Link, off int64, f float64)`: 64ビット浮動小数点数を書き込む。
        *   `WriteInt(ctxt *Link, off, siz int64, i int64)`: 指定されたサイズの整数を書き込む。
        *   `WriteAddr(ctxt *Link, off, siz int64, rsym *LSym, roff int64)`: アドレスを書き込み、同時に再配置情報（`R_ADDR`）を追加する。
        *   `WriteString(ctxt *Link, off, siz int64, str string)`: 文字列を書き込む。

## コアとなるコードの解説

このコミットのコアとなる変更は、Goコンパイラのバックエンドとリンカの間のインターフェースをより直接的なものにした点にあります。

`src/cmd/compile/internal/gc/obj.go`の変更は、コンパイラが静的データを扱う際の「命令生成」という間接的なアプローチから、「シンボルへの直接書き込み」という直接的なアプローチへの移行を示しています。
例えば、`dsymptr`関数はシンボルへのポインタを静的データとして書き込む役割を担いますが、変更前は以下のようなADATA命令を生成していました。

```go
// 変更前 (obj.go)
p := Thearch.Gins(obj.ADATA, nil, nil)
p.From.Type = obj.TYPE_MEM
p.From.Name = obj.NAME_EXTERN
p.From.Sym = Linksym(s)
p.From.Offset = int64(off)
p.From3 = new(obj.Addr)
p.From3.Type = obj.TYPE_CONST
p.From3.Offset = int64(Widthptr)
p.To.Type = obj.TYPE_ADDR
p.To.Name = obj.NAME_EXTERN
p.To.Sym = Linksym(x)
p.To.Offset = int64(xoff)
```
このコードは、`obj.ADATA`という種類の命令を生成し、その命令のフィールド（`From`, `To`, `From3`など）に静的データに関する情報を設定していました。リンカはこの命令を解釈してデータを処理します。

変更後は、この複雑な命令生成が、`src/cmd/internal/obj/data.go`で新しく定義された`LSym`のメソッド呼び出しに置き換えられています。

```go
// 変更後 (obj.go)
Linksym(s).WriteAddr(Ctxt, int64(off), int64(Widthptr), Linksym(x), int64(xoff))
```
この一行のコードは、`s`というシンボルに対して、`off`オフセットから`Widthptr`バイトのサイズで、`x`というシンボルへのアドレス（オフセット`xoff`付き）を直接書き込むことを指示しています。

`src/cmd/internal/obj/data.go`で追加された`LSym`のメソッド群は、この直接書き込みを可能にするための基盤を提供します。
特に重要なのは`WriteAddr`メソッドです。

```go
// WriteAddr writes an address of size siz into s at offset off.
// rsym and roff specify the relocation for the address.
func (s *LSym) WriteAddr(ctxt *Link, off, siz int64, rsym *LSym, roff int64) {
	s.prepwrite(ctxt, off, siz) // データ領域の確保
	r := Addrel(s)              // 再配置情報の追加
	r.Off = int32(off)
	r.Siz = uint8(siz)
	r.Sym = rsym
	r.Type = R_ADDR             // アドレス再配置タイプ
	r.Add = roff
}
```
このメソッドは、単にデータを書き込むだけでなく、アドレス参照の場合に必要となる再配置情報（`R_ADDR`）を`LSym`に直接追加しています。これにより、リンカは後でこの再配置情報を利用して、最終的なアドレスを解決することができます。

この変更は、コンパイラとリンカの間の結合をより密接にし、中間表現のオーバーヘッドを削減することで、コンパイルパイプライン全体の効率を向上させるものです。特に、静的データの処理パスが簡素化され、メモリ割り当てと処理時間が削減される効果があります。

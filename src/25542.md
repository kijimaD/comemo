# [インデックス 25542] ファイルの概要

このコミットは、`cmd/go` ツールがパッケージの「stale (古くなっている)」状態を判断する際のヒューリスティックにおけるバグを修正します。具体的には、`GOROOT` 環境変数のパスが正規化されているにもかかわらず、比較対象となる現在のパッケージパスが正規化されていないために発生する、誤った `mtime` (最終更新時刻) 比較の問題を解決します。これにより、パスの末尾にスラッシュがある場合など、論理的には同じパスであるにもかかわらず、`cmd/go` がパッケージを不必要に再ビルドしようとする問題を解消します。

## 元コミット内容

`cmd/go`: パッケージを含むディレクトリパスをクリーンアップする。

パッケージやコマンドがstaleであるかを判断するヒューリスティックが失敗する。これは、`GOROOT` と現在のパッケージパスが同じであるにもかかわらず、パス名が比較前に正規化されていないため (`GOROOT` は正規化されている) `mtime` 比較が行われるためである。

Fixes: #12690

## 変更の背景

Goのビルドシステム、特に `cmd/go` ツールは、ソースファイルが変更されたかどうかを判断するために、パッケージの最終更新時刻 (mtime) を利用します。これにより、不要な再コンパイルを避け、ビルド時間を短縮します。このコミット以前は、この「stale (古くなっている)」状態の判定ロジックに問題がありました。

問題の核心は、`GOROOT` 環境変数の値と、ビルド対象のパッケージのパスとの間で、パスの正規化 (canonicalization) の一貫性が欠如していたことにあります。`GOROOT` は内部的に正規化された形式で扱われることがありますが、比較対象となるパッケージのパスは、ユーザーが指定した形式 (例えば、末尾にスラッシュが付いている `/usr/local/go/` のような形式) のままでした。

これにより、例えば `GOROOT` が `/usr/local/go` と正規化されている一方で、あるパッケージのパスが `/usr/local/go/src/runtime/` のように末尾にスラッシュが付いている場合、これら二つのパスは論理的には同じディレクトリを指しているにもかかわらず、文字列としては異なるものとして扱われていました。結果として、`cmd/go` はこれらのパスが異なるものと誤解し、実際には変更がないにもかかわらず、パッケージが「stale」であると判断して不必要に再ビルドを実行してしまうというバグが発生していました。これはビルドパフォーマンスの低下や、開発者の混乱を招く可能性がありました。

このコミットは、このパスの不一致による誤判定を解消し、`cmd/go` がより正確にパッケージのstale状態を判断できるようにすることを目的としています。

## 前提知識の解説

### `GOROOT`

`GOROOT` は、Go言語のインストールディレクトリのルートを示す環境変数です。Goコンパイラ、標準ライブラリのソースコード、およびその他のGoツールが格納されている場所を指します。Goツールチェーンは、`GOROOT` を参照して、これらの必須コンポーネントや、コードがインポートする可能性のある標準パッケージを見つけます。現代のGoバージョン (Go 1.9以降) では、`go` コマンドがその呼び出しパスに基づいて `GOROOT` の場所を自動的に推測することが多いため、手動で設定する必要はほとんどありません。しかし、複数のGoバージョンを管理している場合や、非標準のインストールを行っている場合には、明示的に設定することがあります。

### `go build` の「stale」判定

`go build` コマンドは、Goのソースコードを実行可能ファイルやライブラリにコンパイルします。このプロセスにおいて、`go build` は、前回のビルド以降にソースファイルが変更されたかどうかを判断するヒューリスティックを使用します。これは主にファイルの最終更新時刻 (mtime) を比較することで行われます。もしソースファイルやその依存関係のmtimeが、以前にビルドされた成果物のmtimeよりも新しい場合、そのパッケージは「stale」であると判断され、再コンパイルが必要とされます。この仕組みにより、変更されていない部分の再ビルドを避け、効率的な増分ビルドが可能になります。

### パスの正規化 (Canonicalization)

パスの正規化とは、ファイルシステム上の同じ場所を指す複数の異なるパス表現を、一意の標準形式に変換するプロセスを指します。例えば、`/a/./b`、`/a/b/`、`/a//b`、`/a/c/../b` といったパスは、すべて論理的には同じディレクトリを指す可能性がありますが、文字列としては異なります。パスを正規化することで、これらの異なる表現を `/a/b` のような単一の標準形式に統一できます。これにより、パスの比較が正確になり、ファイルシステム操作の一貫性が保たれます。

### `pathpkg.Clean`

Go言語の標準ライブラリには、パスをクリーンアップするための `path` パッケージと `path/filepath` パッケージがあります。このコミットで言及されている `pathpkg.Clean` は、`path.Clean` 関数のことを指します。

`path.Clean` は、主にURLのようなスラッシュ区切りのパスを正規化するために設計されています。その動作は以下の通りです。

*   複数のパスセパレータ (`//`) を単一のセパレータに置き換えます。
*   `.` (現在のディレクトリ) 要素を削除します。
*   `..` (親ディレクトリ) 要素を解決し、先行するパスコンポーネントを削除します。
*   ルート付きパスの先頭にある `..` 要素 (例: `/../a`) を処理し、`/a` のようにします。
*   結果として、パスは最短かつ最もクリーンな形式になります。

この関数は、パスの比較や格納において一貫性を保つために非常に重要です。

## 技術的詳細

このバグは、`cmd/go` がパッケージのstale状態をチェックする際に、`GOROOT` のパスとビルド対象のパッケージのパスとの間で、パスの表現に一貫性がなかったために発生しました。

具体的には、`runtime.GOROOT()` から取得される `GOROOT` の値は、Goツールチェーンの内部で既に正規化されているか、あるいは正規化された形式で利用されることが期待されていました。しかし、`go/build` パッケージがパッケージパスを扱う際、特にユーザーが指定したパスや環境変数から取得したパスは、必ずしも正規化されていませんでした。

例えば、ユーザーが `GOROOT` を `/usr/local/go/` のように末尾にスラッシュを付けて設定した場合、`runtime.GOROOT()` はこの値を返す可能性があります。しかし、Goツールチェーンの他の部分では、このパスが `/usr/local/go` のようにスラッシュなしで正規化されて比較されることがありました。

このコミット以前の `src/go/build/build.go` の `defaultContext()` 関数では、`c.GOROOT = runtime.GOROOT()` と直接代入していました。これにより、`GOROOT` の値が正規化されていない状態で `Context` 構造体に格納される可能性がありました。

`cmd/go` がパッケージのstale状態を判断する際、この `Context` 内の `GOROOT` の値と、ビルド対象のパッケージの実際のファイルパスを比較します。この比較には、ファイルのmtimeが含まれますが、その前にパス自体が一致するかどうかのチェックが行われます。パスが一致しないと判断されると、たとえmtimeが同じであっても、異なるパスとして扱われ、不必要に再ビルドがトリガーされていました。

このコミットの修正は、`src/go/build/build.go` の `defaultContext()` 関数内で `runtime.GOROOT()` から取得したパスを `pathpkg.Clean` で明示的に正規化することによって、この不整合を解消します。

```go
c.GOROOT = pathpkg.Clean(runtime.GOROOT())
```

これにより、`Context` 構造体に格納される `GOROOT` の値は常に正規化された形式となり、末尾のスラッシュの有無など、表面的なパス表現の違いによる誤った比較がなくなります。結果として、`cmd/go` はパッケージのstale状態を正確に判断できるようになり、不必要な再ビルドが回避されます。

また、`src/cmd/go/go_test.go` に追加されたテストケース `TestPackageNotStaleWithTrailingSlash` は、この修正が正しく機能することを確認するためのものです。このテストでは、`GOROOT` に意図的に末尾スラッシュを追加したパスを設定し、`runtime`, `os`, `io` といった標準パッケージがstaleと誤判定されないことを検証しています。これは、修正が意図した通りに動作し、パスの正規化によってstale判定のロジックが安定したことを示しています。

## コアとなるコードの解説

### `src/go/build/build.go` の変更

このファイルは、Goのビルドプロセスにおけるコンテキスト (環境情報) を定義する `Context` 構造体と、そのデフォルト値を設定する `defaultContext()` 関数を含んでいます。

```go
 	c.GOARCH = envOr("GOARCH", runtime.GOARCH)
 	c.GOOS = envOr("GOOS", runtime.GOOS)
-	c.GOROOT = runtime.GOROOT()
+	c.GOROOT = pathpkg.Clean(runtime.GOROOT())
 	c.GOPATH = envOr("GOPATH", "")
 	c.Compiler = runtime.Compiler
```

変更点は、`c.GOROOT` に `runtime.GOROOT()` の値を直接代入する代わりに、`pathpkg.Clean()` 関数を通して代入している点です。

*   **`runtime.GOROOT()`**: 現在のGoインストールのルートディレクトリのパスを返します。このパスは、末尾にスラッシュが含まれるなど、様々な形式で返される可能性があります。
*   **`pathpkg.Clean()`**: `path` パッケージの `Clean` 関数を呼び出し、`runtime.GOROOT()` から返されたパスを正規化します。これにより、パスから冗長な要素 (例: `.`、`..`、重複するスラッシュ) が削除され、末尾のスラッシュも取り除かれた、一意で標準的な形式に変換されます。

この変更により、`build.Context` に格納される `GOROOT` の値は常に正規化された形式となり、`cmd/go` がパッケージパスと比較する際に一貫性が保たれるようになります。

### `src/cmd/go/go_test.go` の変更

このファイルは `cmd/go` コマンドのテストケースを含んでいます。追加された `TestPackageNotStaleWithTrailingSlash` 関数は、このコミットで修正されたバグを再現し、修正が正しく機能することを確認するためのものです。

```go
// Issue 12690
func TestPackageNotStaleWithTrailingSlash(t *testing.T) {
	tg := testgo(t)
	defer tg.cleanup()
	goroot := runtime.GOROOT()
	tg.setenv("GOROOT", goroot+"/")
	tg.wantNotStale("runtime", "with trailing slash in GOROOT, runtime listed as stale")
	tg.wantNotStale("os", "with trailing slash in GOROOT, os listed as stale")
	tg.wantNotStale("io", "with trailing slash in GOROOT, io listed as stale")
}
```

*   **`tg := testgo(t)`**: テストヘルパーを初期化します。
*   **`defer tg.cleanup()`**: テスト終了後にクリーンアップ処理を実行します。
*   **`goroot := runtime.GOROOT()`**: 現在の `GOROOT` パスを取得します。
*   **`tg.setenv("GOROOT", goroot+"/")`**: ここがテストの肝です。取得した `GOROOT` パスの末尾に意図的にスラッシュを追加し、この「非正規化された」パスを `GOROOT` 環境変数として設定します。これが、バグが発生していた状況をシミュレートします。
*   **`tg.wantNotStale("runtime", ...)`**: `wantNotStale` ヘルパー関数を呼び出し、`runtime` パッケージがstaleではないことを検証します。同様に `os` と `io` パッケージについても検証します。もし修正が適用されていなければ、末尾スラッシュ付きの `GOROOT` のためにこれらのパッケージがstaleと誤判定され、テストは失敗するはずです。テストが成功するということは、`pathpkg.Clean` による正規化が正しく機能し、stale判定が正確に行われていることを意味します。

このテストの追加は、回帰テストとして機能し、将来的に同様のパス正規化に関する問題が再発するのを防ぐのに役立ちます。

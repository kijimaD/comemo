# [インデックス 27524] ファイルの概要

このコミットは、Goコンパイラにおけるスライスと配列の境界値の扱いを改善し、より堅牢な型チェックと内部表現の一貫性を確保することを目的としています。具体的には、スライスの境界を示すマジックナンバー`-1`を`sliceBound`という定数に置き換え、境界値の検証を強化しています。

## 変更の背景

Goコンパイラ内部では、スライス型を表現するために、`Type`構造体の`Bound`フィールドに`-1`という特殊な値を使用していました。これは「マジックナンバー」として機能していましたが、コードの可読性や保守性を低下させる可能性がありました。また、配列の境界値に関するチェックが散在しており、一貫性に欠ける部分がありました。

このコミットの主な背景は以下の点に集約されます。

1.  **マジックナンバーの排除**: スライスの境界を示す`-1`というマジックナンバーを`sliceBound`という名前付き定数に置き換えることで、コードの意図を明確にし、可読性を向上させます。
2.  **境界値チェックの強化と一元化**: 配列やスライスの境界値に関する検証ロジックがコンパイラの複数の箇所に分散しており、エラーハンドリングや整合性の維持が困難でした。この変更により、境界値のチェックをより積極的かつ一元的に行うことで、コンパイラの堅牢性を高めます。特に、`plive.go`にあったアドホックなチェックを削除し、`type.go`に`checkBound`という専用の関数を導入することで、この目的を達成しています。
3.  **型チェック時の早期エラー検出**: 配列型を構築する前に境界値をチェックすることで、不正な境界値を持つ配列型が生成されるのを防ぎ、コンパイルプロセスのより早い段階でエラーを検出できるようにします。

これらの変更は、Goコンパイラの内部品質を向上させ、将来的なメンテナンスや機能拡張を容易にすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Go言語における以下の概念とGoコンパイラの内部構造に関する基本的な知識が必要です。

### Go言語におけるスライスと配列

*   **配列 (Array)**: Goの配列は、同じ型の要素を固定長で連続して格納するデータ構造です。配列の長さは型の一部であり、コンパイル時に決定されます。例: `[5]int` は5つの整数を格納する配列です。
*   **スライス (Slice)**: スライスは配列への参照であり、可変長シーケンスを表現します。スライスは内部的に、基底配列へのポインタ、長さ (len)、容量 (cap) の3つの要素で構成されます。スライスの長さは実行時に変更できます。例: `[]int` は整数のスライスです。

コンパイラ内部では、スライスは長さが不定の配列として扱われることがあり、その際に特殊な境界値が用いられます。

### Goコンパイラの型システム (`src/cmd/compile/internal/gc/type.go`)

Goコンパイラは、プログラム内のすべての型を`Type`構造体で表現します。この`Type`構造体には、型の種類（`Etype`、例: `TARRAY`、`TINT`など）や、配列の長さを示す`Bound`フィールドなどが含まれます。

*   `Type.Etype`: 型の基本的な種類（例: `TARRAY`は配列型またはスライス型を示す）。
*   `Type.Bound`: 配列の場合、その長さを格納します。スライスの場合、このコミット以前は慣習的に`-1`が使用されていました。可変長引数（`...T`）の場合も特殊な値が使われます。

### 可変長引数 (`...T` または `ddd`)

Goの関数は、可変長引数を受け取ることができます（例: `func foo(args ...int)`）。コンパイラ内部では、この可変長引数も特殊な`Bound`値（`dddBound`）を持つ配列型として扱われます。

### `src/cmd/compile/internal/gc` パッケージ

このコミットで変更されているファイルはすべて`src/cmd/compile/internal/gc`パッケージに属しています。このパッケージはGoコンパイラの主要な部分であり、字句解析、構文解析、型チェック、中間コード生成、最適化など、コンパイルの多くの段階を処理します。

*   `align.go`: 型のアライメントとサイズ計算に関連するロジック。
*   `bimport.go`: パッケージのバイナリインポート/エクスポートに関連するロジック。
*   `plive.go`: ライブネス解析（変数がまだ使用されているかどうかを判断する）に関連するロジック。
*   `type.go`: 型の定義と操作に関する中心的なロジック。
*   `typecheck.go`: 型チェックの主要なロジック。

## 技術的詳細

このコミットは、Goコンパイラの型システムにおけるスライスと配列の境界値の扱いを根本的に改善しています。

### 1. `sliceBound` 定数の導入 (`src/cmd/compile/internal/gc/type.go`)

最も重要な変更は、スライスを示すマジックナンバー`-1`を`sliceBound`という名前付き定数に置き換えたことです。

```go
const (
	sliceBound = -1   // slices have Bound=sliceBound
	dddBound   = -100 // arrays declared as [...]T start life with Bound=dddBound
)
```

これにより、コードの意図が明確になり、`t.Bound == -1`のような比較が`t.Bound == sliceBound`となり、可読性と保守性が向上します。

### 2. `checkBound` 関数の導入と境界値の厳格化 (`src/cmd/compile/internal/gc/type.go`)

`Type`構造体に`checkBound()`という新しいメソッドが追加されました。この関数は、`Type.Bound`フィールドが有効な値（`sliceBound`、`dddBound`、または非負の値）であることを強制します。

```go
// checkBound enforces that Bound has an acceptable value.
func (t *Type) checkBound() {
	if t.Bound != sliceBound && t.Bound < 0 && t.Bound != dddBound {
		Fatalf("bad TARRAY bounds %d %s", t.Bound, t)
	}
}
```

この`checkBound`関数は、`IsSlice()`, `IsArray()`, `NumElem()` などの`Type`メソッドが`Bound`フィールドにアクセスする前に呼び出されるようになりました。これにより、不正な`Bound`値がシステム内で伝播するのを防ぎ、コンパイラの内部状態の一貫性を保ちます。

### 3. `plive.go` からのアドホックなチェックの削除

以前は`plive.go`に以下のようなアドホックな境界値チェックがありました。

```go
// The value of t.bound is -1 for slices types and >=0 for
// for fixed array types. All other values are invalid.
if t.Bound < -1 {
	Fatalf("onebitwalktype1: invalid bound, %v", t)
}
```

このチェックは`checkBound`関数に統合されたため、`plive.go`からは削除されました。これにより、境界値の検証ロジックが一元化され、重複が排除されました。

### 4. 型チェック時の配列境界値の早期検証 (`src/cmd/compile/internal/gc/typecheck.go`)

`typecheck.go`では、配列型を構築する際に、その境界値が非負であることをより早期にチェックするようになりました。

変更前:
```go
t = typArray(r.Type, v.U.(*Mpint).Int64())
// ...
} else if t.IsSlice() { // This check was problematic as t.IsSlice() would be true for negative bounds
    Yyerror("array bound must be non-negative")
    n.Type = nil
    return n
}
```

変更後:
```go
bound := v.U.(*Mpint).Int64()
if bound < 0 {
    Yyerror("array bound must be non-negative")
    n.Type = nil
    return n
}
t = typArray(r.Type, bound)
```

この変更により、`typArray`関数に渡す前に`bound`が負でないことを確認するため、不正な配列型が生成されるリスクが減少します。以前の`t.IsSlice()`によるチェックは、負の`Bound`値を持つ`TARRAY`型がスライスとして誤認識される可能性がありましたが、この修正によりその問題が解消されました。

### 5. その他の変更点

*   **`align.go`**: `t.Bound == -1` の比較が `t.IsSlice()` に変更されました。これは`sliceBound`定数の導入と`IsSlice`メソッドの改善によるものです。
*   **`bimport.go`**: バイナリインポート時にスライス型や可変長引数型を再構築する際、`t.Bound = -1` の代わりに `t.Bound = sliceBound` を使用するようになりました。
*   **`typecheck.go` (コンポジットリテラル)**: コンポジットリテラルで配列の境界外アクセスが発生した場合、それ以降の同様のエラーを抑制するために、`t.Bound = -1` ではなく `t.Bound = sliceBound` を設定するようになりました。これにより、エラー抑制の意図がより明確になります。

これらの変更は、コンパイラ内部でのスライスと配列の表現と検証をより堅牢で一貫性のあるものにし、将来的なバグの発生を防ぐことに貢献します。

## コアとなるコードの解説

### `sliceBound` 定数

`sliceBound = -1` は、Goコンパイラ内でスライス型を識別するための定数です。以前は`-1`というリテラル値が直接使われていましたが、この定数に置き換えることで、コードの意図が「これはスライスの境界を示す特別な値である」と明確に伝わるようになります。これにより、マジックナンバーの使用が排除され、コードの可読性と保守性が向上します。

### `checkBound` 関数

`func (t *Type) checkBound()` は、`Type`構造体の`Bound`フィールドの整合性を検証するための重要な関数です。この関数は、`Bound`の値が以下のいずれかであることを強制します。

1.  `sliceBound` (`-1`): スライス型の場合。
2.  `dddBound` (`-100`): 可変長引数（`...T`）型の場合。
3.  非負の値 (`>= 0`): 固定長配列型の場合。

もし`Bound`がこれらのいずれにも該当しない場合、`Fatalf`を呼び出してコンパイラを異常終了させます。これは、コンパイラの内部状態が不正であることを示し、早期に問題を検出するための防御的なプログラミングです。

この関数が`IsSlice()`, `IsArray()`, `NumElem()`といった`Type`メソッドの内部で呼び出されることで、`Type`構造体の`Bound`フィールドにアクセスするたびにその値が検証されるようになり、コンパイラ全体の堅牢性が大幅に向上します。

### `typecheck.go` における配列境界値の早期チェック

`typecheck.go`の変更は、配列の宣言時にその境界値が負でないことを`typArray`関数を呼び出す前に確認するものです。

以前のコードでは、`typArray`が呼び出された後に`t.IsSlice()`でチェックしていましたが、`t.IsSlice()`の内部ロジックが`t.Bound < 0`であったため、負の境界値を持つ配列が一時的にスライスとして扱われ、誤解を招く可能性がありました。

新しいコードでは、まず`bound`変数を取得し、それが負であればすぐにエラーを報告します。これにより、不正な境界値を持つ配列型がコンパイラ内部で不適切に扱われることを防ぎ、より正確で早期なエラー検出が可能になります。

また、コンポジットリテラルで配列の境界外アクセスが発生した場合に、それ以降の同様のエラーを抑制するために`t.Bound = sliceBound`を設定する変更も、`sliceBound`定数の導入によってコードの意図が明確になった良い例です。

これらの変更は、Goコンパイラの型システムにおける配列とスライスの内部表現をより厳密にし、コンパイラの信頼性と保守性を高める上で非常に重要です。

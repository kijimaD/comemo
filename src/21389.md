# [インデックス 21389] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）における論理演算子（`&&`、`||`）の型推論の挙動を修正するものです。特に、型付けされていない（untyped）オペランドが関与する場合に、論理演算の結果が正しく「型付けされていないブール値」（untyped bool）として扱われるように変更されました。これにより、Goの型システムにおける「型付けされていない定数」の概念が、論理演算の結果にも適切に適用されるようになります。

## 元コミット内容

このコミットの目的は、「`cmd/gc`: 論理演算子は、型付けされていないオペランドに対して型付けされていないブール値を生成すべきである」というものです。これは、Goコンパイラが論理演算子（`&&`、`||`）の型推論を処理する方法に関するバグ `#6671` を修正します。

## 変更の背景

Go言語には、「型付けされていない定数」（untyped constants）という概念があります。これは、`true`、`false`、数値リテラル（例: `10`、`3.14`）など、特定の型を持たない値のことです。これらの定数は、使用される文脈に応じて適切な型に推論されます。例えば、`var x int = 10` の場合、`10` は `int` 型に推論されます。

ブール値の場合も同様で、`true` や `false` といったブールリテラル、あるいは比較演算子（例: `x < y`）の結果は、最初は「型付けされていないブール値」（untyped bool）として扱われます。これらは、`bool` 型の変数に代入されたり、特定の型を要求する文脈で使用されたりするまで、具体的な型を持ちません。

しかし、Goコンパイラ（`cmd/gc`）の以前のバージョンでは、論理演算子（`&&`、`||`）が型付けされていないブール値をオペランドとして受け取った際に、その結果を誤って「型付けされたブール値」（typed `bool`）として扱ってしまう問題がありました。この挙動は、ユーザー定義のブール型（例: `type mybool bool`）への代入時に型不一致エラーを引き起こす可能性がありました。

具体的には、`issue3924.go` のテストケースが示唆するように、`var _ mybool = x < y && x < y` のようなコードがエラーとなるのは、`x < y` が型付けされていないブール値を生成するにもかかわらず、`&&` 演算の結果が `bool` 型として推論され、それが `mybool` 型に直接代入できないためでした。Goの型システムでは、`bool` と `mybool` は異なる型として扱われます。

このコミットは、この問題を解決し、論理演算子が型付けされていないオペランドを処理する際に、その結果もまた型付けされていないブール値として適切に推論されるようにすることで、Goの型推論の一貫性を保つことを目的としています。

## 前提知識の解説

### Goの型システムと「型付けされていない定数」

Go言語の型システムは静的型付けでありながら、柔軟性も持ち合わせています。その特徴の一つが「型付けされていない定数」です。

*   **型付けされていない定数 (Untyped Constants)**:
    *   数値リテラル（例: `1`, `3.14`, `1e3`）
    *   ブールリテラル（`true`, `false`）
    *   文字列リテラル（例: `"hello"`）
    *   比較演算子（`<`, `>`, `==`, `!=`, `<=`, `>=`）の結果（ブール値）
    *   論理演算子（`&&`, `||`）の結果（ブール値）
    これらは、コード内で明示的に型が指定されるか、または型が推論される文脈で使用されるまで、特定の型を持ちません。これにより、例えば `var i int = 10` と `var f float64 = 10` の両方で同じリテラル `10` を使用できるような柔軟性が生まれます。

*   **`idealbool` (内部表現)**:
    Goコンパイラ（`cmd/gc`）の内部では、型付けされていないブール値を表現するために `idealbool` という特殊な型が使用されます。これは、`true` や `false` といったブールリテラル、および `x < y` のような比較演算の結果が、まだ具体的な `bool` 型に確定していない状態を示すためのものです。

*   **型変換と代入**:
    Goでは、異なる型間の代入や演算には明示的な型変換が必要となるのが一般的です。しかし、型付けされていない定数は、代入先の型や演算の文脈に基づいて自動的に型が推論・変換されます。例えば、`var b mybool = true` は、`true` が型付けされていないブール値であるため、`mybool` 型に自動的に変換されて代入が許可されます。しかし、`var b mybool = bool(true)` のように、一度 `bool(true)` で明示的に `bool` 型に変換してしまうと、`bool` と `mybool` は異なる型であるため、直接代入はできません（コンパイルエラーとなります）。

### Goコンパイラの型チェックプロセス

Goコンパイラは、ソースコードを抽象構文木（AST）に変換した後、型チェックフェーズで各ノード（式、文など）の型を決定します。このプロセスでは、演算子の種類、オペランドの型、および代入先の型などを考慮して、式の最終的な型を推論します。

このコミットが修正する問題は、この型チェックフェーズにおいて、論理演算子（`OANDAND` や `OOROR`）が `idealbool` を含むオペランドを処理する際の挙動にありました。

## 技術的詳細

### `src/cmd/gc/typecheck.c` の変更点

1.  **論理演算子 (`OANDAND`, `OOROR`) の型推論ロジックの追加**:
    `reswitch` ラベル内の式型チェック部分に、論理AND (`OANDAND`) および論理OR (`OOROR`) 演算子に対する新しい型推論ルールが追加されました。

    ```c
    // 変更前:
    // ...
    // } else if(t == idealbool)
    //    t = types[TBOOL]; // idealboolは非比較演算子でtyped boolになる

    // 変更後:
    // ...
    } else if(n->op == OANDAND || n->op == OOROR) {
        if(l->type == r->type)
            t = l->type;
        else if(l->type == idealbool)
            t = r->type;
        else if(r->type == idealbool)
            t = l->type;
    // non-comparison operators on ideal bools should make them lose their ideal-ness
    } else if(t == idealbool)
        t = types[TBOOL];
    ```

    この変更の意図は以下の通りです。
    *   `l->type == r->type`: もし左右のオペランドが同じ型（例: 両方 `bool` 型、または両方 `idealbool`）であれば、結果の型はその共通の型 `l->type` となります。
    *   `l->type == idealbool`: もし左オペランドが `idealbool` であれば、結果の型は右オペランドの型 `r->type` となります。例えば、`true && someTypedBool` のような場合、結果は `someTypedBool` の型（`bool` またはユーザー定義のブール型）になります。
    *   `r->type == idealbool`: もし右オペランドが `idealbool` であれば、結果の型は左オペランドの型 `l->type` となります。例えば、`someTypedBool && true` のような場合、結果は `someTypedBool` の型になります。

    この新しいロジックの重要な点は、**両方のオペランドが `idealbool` である場合、結果の型も `idealbool` のままになる**という点です。これにより、`true && false` や `(x < y) && (a > b)` のような式の結果が、明示的に型が要求されるまで型付けされていない状態を維持できるようになります。

2.  **`OCONVNOP` (no-op変換) の条件変更**:
    `OCONVNOP` は、型変換が不要な場合にコンパイラが生成する内部ノードです。このノードの処理条件が変更されました。

    ```c
    // 変更前:
    // if(n->left->op == OLITERAL) {

    // 変更後:
    // if(n->left->op == OLITERAL && n->type != types[TBOOL]) {
    ```

    この変更は、左オペランドがリテラルであり、かつターゲットの型 `n->type` が既に `bool` 型である場合には、`OCONVNOP` を適用しないようにします。これは、型付けされていないブールリテラルが、既に `bool` 型として扱われている文脈で不必要なno-op変換が行われるのを防ぎ、型推論の正確性を向上させるためのものです。

    ```go
    package p

    type mybool bool

    func _(x, y int) {
    	type mybool bool // 関数スコープでのmybool型定義
    	var b mybool
    	_ = b
    	b = bool(true)             // ERROR "cannot use" - bool(true)はtyped boolなのでmyboolに直接代入不可
    	b = true                   // permitted as expected - untyped trueはmyboolに代入可能
    	b = bool(true) && true     // ERROR "cannot use" - bool(true)がtyped boolなので結果もtyped boolとなりmyboolに代入不可
    	b = true && true           // permitted => && returns an untyped bool (両方untypedなので結果もuntyped)
    	b = x < y                  // permitted => x < y returns an untyped bool (比較結果はuntyped)
    	b = true && x < y          // permitted => result of && returns untyped bool (片方がuntypedなので結果もuntyped)
    	b = x < y && x < y         // permitted => result of && returns untyped bool (両方untypedなので結果もuntyped)
    	b = x < y || x < y         // permitted => result of || returns untyped bool (両方untypedなので結果もuntyped)
    	var c bool = true && x < y // permitted => result of && is bool (bool変数に代入されるのでtyped boolになる)
    	c = false || x < y         // permitted => result of || returns untyped bool (bool変数に代入されるのでtyped boolになる)
    	_ = c
    }
    ```
    このテストは、`true && true` や `x < y && x < y` のような論理演算の結果が、型付けされていないブール値として正しく推論され、ユーザー定義のブール型 `mybool` に代入できることを確認しています。同時に、明示的に `bool(true)` のように型付けされたブール値が関与する場合や、結果が `bool` 型の変数に代入される場合には、期待通りに型付けされた `bool` として扱われることも示しています。

### `src/cmd/gc/typecheck.c` の変更詳細

Goコンパイラの `typecheck.c` は、Goプログラムの型チェックを行う中心的なファイルです。このファイルは、抽象構文木（AST）の各ノードを走査し、その型を決定します。

#### 1. 論理演算子の型推論ロジックの追加

```c
// src/cmd/gc/typecheck.c (変更箇所抜粋)
// ...
		} else if(n->op == OANDAND || n->op == OOROR) {
			// 論理AND (&&) または論理OR (||) 演算子の場合
			if(l->type == r->type)
				// 左右のオペランドが同じ型の場合、結果はその型
				t = l->type;
			else if(l->type == idealbool)
				// 左オペランドがidealboolの場合、結果は右オペランドの型
				t = r->type;
			else if(r->type == idealbool)
				// 右オペランドがidealboolの場合、結果は左オペランドの型
				t = l->type;
		// non-comparison operators on ideal bools should make them lose their ideal-ness
		} else if(t == idealbool)
			// 上記の条件に合致せず、かつ結果がidealboolのままの場合、
			// それは非比較演算子（例: 単項演算子など）によってidealboolがtyped boolに変換されるケース。
			// このコミットの変更とは直接関係ないが、既存のロジックの一部。
			t = types[TBOOL];
// ...
```

このコードブロックは、論理演算子 `&&` および `||` の型推論の核心です。
*   `n->op` は現在のASTノードの演算子を表します。`OANDAND` は `&&`、`OOROR` は `||` に対応します。
*   `l->type` と `r->type` はそれぞれ左右のオペランドの型です。
*   `t` は演算結果の型として設定される変数です。

このロジックにより、以下の挙動が実現されます。
*   `true && false` (両方 `idealbool`): `l->type == r->type` が `true` となり、`t` は `idealbool` のままになります。
*   `true && someTypedBool` (`idealbool` と `typed bool`): `l->type == idealbool` が `true` となり、`t` は `someTypedBool` の型（`bool` またはユーザー定義型）になります。
*   `someTypedBool && true` (`typed bool` と `idealbool`): `r->type == idealbool` が `true` となり、`t` は `someTypedBool` の型になります。

これにより、論理演算子が型付けされていないブール値を適切に伝播させ、Goの型推論ルールに沿った挙動を実現します。

#### 2. `OCONVNOP` の条件変更

```c
// src/cmd/gc/typecheck.c (変更箇所抜粋)
// ...
		switch(n->op) {
		case OCONVNOP:
			// no-op変換の場合
			// 左オペランドがリテラルであり、かつターゲットの型が既にbool型でない場合のみ、
			// no-op変換を適用する。
			if(n->left->op == OLITERAL && n->type != types[TBOOL]) {
				r = nod(OXXX, N, N);
				n->op = OCONV;
				n->orig = r;
			}
// ...
```

*   `OCONVNOP` は、コンパイラが型変換を必要としないと判断した場合に生成される内部的な演算子です。
*   `OLITERAL` は、ノードがリテラル値であることを示します。
*   `types[TBOOL]` は、Goの組み込み `bool` 型を表します。

この変更は、リテラルが既に `bool` 型として扱われている文脈で、不必要な `OCONVNOP` が適用されるのを防ぎます。これにより、コンパイラの内部処理がより正確になり、型推論のロジックが強化されます。

    *   論理演算子（`&&`, `||`）の結果（ブール値）
    これらは、コード内で明示的に型が指定されるか、または型が推論される文脈で使用されるまで、特定の型を持ちません。これにより、例えば `var i int = 10` と `var f float64 = 10` の両方で同じリテラル `10` を使用できるような柔軟性が生まれます。

*   **`idealbool` (内部表現)**:
    Goコンパイラ（`cmd/gc`）の内部では、型付けされていないブール値を表現するために `idealbool` という特殊な型が使用されます。これは、`true` や `false` といったブールリテラル、および `x < y` のような比較演算の結果が、まだ具体的な `bool` 型に確定していない状態を示すためのものです。

*   **型変換と代入**:
    Goでは、異なる型間での代入や演算には明示的な型変換が必要となるのが一般的です。しかし、型付けされていない定数は、代入先の型や演算の文脈に基づいて自動的に型が推論・変換されます。例えば、`var b mybool = true` は、`true` が型付けされていないブール値であるため、`mybool` 型に自動的に変換されて代入が許可されます。しかし、`var b mybool = bool(true)` のように、一度 `bool(true)` で明示的に `bool` 型に変換してしまうと、`bool` と `mybool` は異なる型であるため、直接代入はできません（コンパイルエラーとなります）。

### Goコンパイラの型チェックプロセス

Goコンパイラは、ソースコードを抽象構文木（AST）に変換した後、型チェックフェーズで各ノード（式、文など）の型を決定します。このプロセスでは、演算子の種類、オペランドの型、および代入先の型などを考慮して、式の最終的な型を推論します。

このコミットが修正する問題は、この型チェックフェーズにおいて、論理演算子（`OANDAND` や `OOROR`）が `idealbool` を含むオペランドを処理する際の挙動にありました。

## 技術的詳細

このコミットの主要な変更は、Goコンパイラの型チェックロジックを定義する `src/cmd/gc/typecheck.c` ファイルにあります。

### `src/cmd/gc/typecheck.c` の変更点

1.  **論理演算子 (`OANDAND`, `OOROR`) の型推論ロジックの追加**:
    `reswitch` ラベル内の式型チェック部分に、論理AND (`OANDAND`) および論理OR (`OOROR`) 演算子に対する新しい型推論ルールが追加されました。

    ```c
    // 変更前:
    // ...
    // } else if(t == idealbool)
    //    t = types[TBOOL]; // idealboolは非比較演算子でtyped boolになる

    // 変更後:
    // ...
    } else if(n->op == OANDAND || n->op == OOROR) {
        if(l->type == r->type)
            t = l->type;
        else if(l->type == idealbool)
            t = r->type;
        else if(r->type == idealbool)
            t = l->type;
    // non-comparison operators on ideal bools should make them lose their ideal-ness
    } else if(t == idealbool)
        t = types[TBOOL];
    ```

    この変更の意図は以下の通りです。
    *   `l->type == r->type`: もし左右のオペランドが同じ型（例: 両方 `bool` 型、または両方 `idealbool`）であれば、結果の型はその共通の型 `l->type` となります。
    *   `l->type == idealbool`: もし左オペランドが `idealbool` であれば、結果の型は右オペランドの型 `r->type` となります。例えば、`true && someTypedBool` のような場合、結果は `someTypedBool` の型（`bool` またはユーザー定義のブール型）になります。
    *   `r->type == idealbool`: もし右オペランドが `idealbool` であれば、結果の型は左オペランドの型 `l->type` となります。例えば、`someTypedBool && true` のような場合、結果は `someTypedBool` の型になります。

    この新しいロジックの重要な点は、**両方のオペランドが `idealbool` である場合、結果の型も `idealbool` のままになる**という点です。これにより、`true && false` や `(x < y) && (a > b)` のような式の結果が、明示的に型が要求されるまで型付けされていない状態を維持できるようになります。

2.  **`OCONVNOP` (no-op変換) の条件変更**:
    `OCONVNOP` は、型変換が不要な場合にコンパイラが生成する内部ノードです。このノードの処理条件が変更されました。

    ```c
    // 変更前:
    // if(n->left->op == OLITERAL) {

    // 変更後:
    // if(n->left->op == OLITERAL && n->type != types[TBOOL]) {
    ```

    この変更は、左オペランドがリテラルであり、かつターゲットの型 `n->type` が既に `bool` 型である場合には、`OCONVNOP` を適用しないようにします。これは、型付けされていないブールリテラルが、既に `bool` 型として扱われている文脈で不必要なno-op変換が行われるのを防ぎ、型推論の正確性を向上させるためのものです。

### テストファイルの変更

*   **`test/fixedbugs/issue3924.go` の削除**:
    このファイルは、`var _ mybool = x < y && x < y // ERROR "cannot use"` のような行で、型付けされていないブール値の論理演算の結果が `mybool` 型に代入できないことをエラーとして期待していました。しかし、今回のコミットによってこの挙動が修正され、`x < y && x < y` の結果が型付けされていないブール値として扱われるようになったため、`mybool` への代入が許可されるようになりました。したがって、このテストケースはもはや有効ではなくなり、削除されました。

*   **`test/fixedbugs/issue6671.go` の新規追加**:
    この新しいテストファイルは、今回のコミットによって修正された挙動を明示的に検証します。

    ```go
    // errorcheck

    // Copyright 2014 The Go Authors.  All rights reserved.
    // Use of this source code is governed by a BSD-style
    // license that can be found in the LICENSE file.

    // Issue 6671: Logical operators should produce untyped bool for untyped operands.

    package p

    type mybool bool

    func _(x, y int) {
    	type mybool bool // 関数スコープでのmybool型定義
    	var b mybool
    	_ = b
    	b = bool(true)             // ERROR "cannot use" - bool(true)はtyped boolなのでmyboolに直接代入不可
    	b = true                   // permitted as expected - untyped trueはmyboolに代入可能
    	b = bool(true) && true     // ERROR "cannot use" - bool(true)がtyped boolなので結果もtyped boolとなりmyboolに代入不可
    	b = true && true           // permitted => && returns an untyped bool (両方untypedなので結果もuntyped)
    	b = x < y                  // permitted => x < y returns an untyped bool (比較結果はuntyped)
    	b = true && x < y          // permitted => result of && returns untyped bool (片方がuntypedなので結果もuntyped)
    	b = x < y && x < y         // permitted => result of && returns untyped bool (両方untypedなので結果もuntyped)
    	b = x < y || x < y         // permitted => result of || returns untyped bool (両方untypedなので結果もuntyped)
    	var c bool = true && x < y // permitted => result of && is bool (bool変数に代入されるのでtyped boolになる)
    	c = false || x < y         // permitted => result of || returns untyped bool (bool変数に代入されるのでtyped boolになる)
    	_ = c
    }
    ```
    このテストは、`true && true` や `x < y && x < y` のような論理演算の結果が、型付けされていないブール値として正しく推論され、ユーザー定義のブール型 `mybool` に代入できることを確認しています。同時に、明示的に `bool(true)` のように型付けされたブール値が関与する場合や、結果が `bool` 型の変数に代入される場合には、期待通りに型付けされた `bool` として扱われることも示しています。

## コアとなるコードの解説

### `src/cmd/gc/typecheck.c` の変更詳細

Goコンパイラの `typecheck.c` は、Goプログラムの型チェックを行う中心的なファイルです。このファイルは、抽象構文木（AST）の各ノードを走査し、その型を決定します。

#### 1. 論理演算子の型推論ロジックの追加

```c
// src/cmd/gc/typecheck.c (変更箇所抜粋)
// ...
		} else if(n->op == OANDAND || n->op == OOROR) {
			// 論理AND (&&) または論理OR (||) 演算子の場合
			if(l->type == r->type)
				// 左右のオペランドが同じ型の場合、結果はその型
				t = l->type;
			else if(l->type == idealbool)
				// 左オペランドがidealboolの場合、結果は右オペランドの型
				t = r->type;
			else if(r->type == idealbool)
				// 右オペランドがidealboolの場合、結果は左オペランドの型
				t = l->type;
		// non-comparison operators on ideal bools should make them lose their ideal-ness
		} else if(t == idealbool)
			// 上記の条件に合致せず、かつ結果がidealboolのままの場合、
			// それは非比較演算子（例: 単項演算子など）によってidealboolがtyped boolに変換されるケース。
			// このコミットの変更とは直接関係ないが、既存のロジックの一部。
			t = types[TBOOL];
// ...
```

このコードブロックは、論理演算子 `&&` および `||` の型推論の核心です。
*   `n->op` は現在のASTノードの演算子を表します。`OANDAND` は `&&`、`OOROR` は `||` に対応します。
*   `l->type` と `r->type` はそれぞれ左右のオペランドの型です。
*   `t` は演算結果の型として設定される変数です。

このロジックにより、以下の挙動が実現されます。
*   `true && false` (両方 `idealbool`): `l->type == r->type` が `true` となり、`t` は `idealbool` のままになります。
*   `true && someTypedBool` (`idealbool` と `typed bool`): `l->type == idealbool` が `true` となり、`t` は `someTypedBool` の型（`bool` またはユーザー定義型）になります。
*   `someTypedBool && true` (`typed bool` と `idealbool`): `r->type == idealbool` が `true` となり、`t` は `someTypedBool` の型になります。

これにより、論理演算子が型付けされていないブール値を適切に伝播させ、Goの型推論ルールに沿った挙動を実現します。

#### 2. `OCONVNOP` の条件変更

```c
// src/cmd/gc/typecheck.c (変更箇所抜粋)
// ...
		switch(n->op) {
		case OCONVNOP:
			// no-op変換の場合
			// 左オペランドがリテラルであり、かつターゲットの型が既にbool型でない場合のみ、
			// no-op変換を適用する。
			if(n->left->op == OLITERAL && n->type != types[TBOOL]) {
				r = nod(OXXX, N, N);
				n->op = OCONV;
				n->orig = r;
			}
// ...
```

*   `OCONVNOP` は、コンパイラが型変換を必要としないと判断した場合に生成される内部的な演算子です。
*   `OLITERAL` は、ノードがリテラル値であることを示します。
*   `types[TBOOL]` は、Goの組み込み `bool` 型を表します。

この変更は、リテラルが既に `bool` 型として扱われている文脈で、不必要な `OCONVNOP` が適用されるのを防ぎます。これにより、コンパイラの内部処理がより正確になり、型推論のロジックが強化されます。

これらの変更は、GoコンパイラがGo言語の型システム、特に型付けされていない定数のセマンティクスをより正確に実装するために不可欠でした。

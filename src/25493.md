# [インデックス 25493] ファイルの概要

このコミットは、Goの `net/http` パッケージにおいて、HTTP/2の登録処理がサーバーのリスニング開始前に行われるように修正するものです。特に `ListenAndServeTLS` 関数において、HTTP/2の設定エラーがサーバー起動後に発生する可能性があった問題を解決し、より堅牢なエラーハンドリングとサーバーの安定性向上を目指しています。具体的には、TLSリスナーが作成される前にHTTP/2の設定を完了させることで、設定に問題がある場合にはサーバーがリスニングを開始する前にエラーを返すように変更されています。

## 変更の背景

Goの `net/http` パッケージにおけるHTTP/2のサポートは、TLS (Transport Layer Security) を介して提供されます。以前の実装では、`http.Server` の `ListenAndServeTLS` メソッドが呼び出された際、TLSリスナーが作成され、接続の受け入れが開始された後に、HTTP/2の設定（具体的には `http2.ConfigureServer` の呼び出し）が行われる可能性がありました。

この順序には潜在的な問題がありました。例えば、`http2.ConfigureServer` が何らかの理由（例えば、サポートされていない暗号スイートが `tls.Config` に指定されているなど）で失敗した場合、サーバーは既にリスニング状態に入っているにもかかわらず、HTTP/2のサポートが適切に有効になっていないという不整合な状態に陥る可能性がありました。このような状況では、HTTP/2を期待するクライアントからの接続が失敗したり、予期せぬ動作を引き起こしたりする恐れがありました。

このコミットの目的は、この問題を解決し、HTTP/2の設定がサーバーが外部からの接続を受け入れる前に確実に完了するようにすることです。これにより、HTTP/2の設定に関するエラーは、サーバーがリスニングを開始する前に捕捉され、適切なエラーとして呼び出し元に返されるようになります。結果として、サーバーの起動プロセスがより堅牢になり、不整合な状態での運用が回避されます。

また、テストコードの改善も行われています。`httptest` パッケージで使用されるテスト用のTLS証明書と秘密鍵が `net/http/internal` パッケージに移動され、テストの依存関係が整理されました。さらに、`ListenAndServeTLS` のHTTP/2ネゴシエーションを検証するための新しいテストケースが追加され、変更の正当性が保証されています。

## 前提知識の解説

### Goの `net/http` パッケージ

`net/http` パッケージは、Go言語でHTTPクライアントおよびサーバーを実装するための標準ライブラリです。ウェブアプリケーションの構築において中心的な役割を果たし、リクエストのルーティング、レスポンスの生成、ミドルウェアの適用など、HTTP通信に関する幅広い機能を提供します。

*   **`http.Server`**: HTTPサーバーの構成（アドレス、ハンドラ、タイムアウトなど）を定義する構造体です。
*   **`ListenAndServe(addr string, handler Handler)`**: 指定されたアドレスでHTTPサーバーを起動し、リクエストを処理します。TLSなしのHTTP通信に使用されます。
*   **`ListenAndServeTLS(certFile, keyFile string)`**: TLSを使用してHTTPSサーバーを起動します。証明書ファイルと秘密鍵ファイルを指定する必要があります。内部的には `Serve` メソッドを呼び出します。
*   **`Serve(l net.Listener)`**: 既存の `net.Listener` インターフェースを受け取り、そのリスナーからの接続を処理します。`ListenAndServe` や `ListenAndServeTLS` は、この `Serve` メソッドを内部的に利用してサーバーを起動します。

### HTTP/2

HTTP/2は、HTTP/1.1の後継となるHTTPプロトコルの主要な改訂版です。主な特徴は以下の通りです。

*   **多重化 (Multiplexing)**: 単一のTCP接続上で複数のリクエストとレスポンスを同時に送受信できます。これにより、HTTP/1.1で発生していたヘッドオブラインブロッキング問題が軽減されます。
*   **ヘッダー圧縮 (Header Compression)**: HPACK圧縮アルゴリズムを使用して、HTTPヘッダーのサイズを削減します。
*   **サーバープッシュ (Server Push)**: クライアントがリクエストする前に、サーバーが関連するリソースをクライアントに送信できます。
*   **バイナリフレーミング (Binary Framing)**: HTTP/1.1のテキストベースのプロトコルとは異なり、HTTP/2はバイナリプロトコルです。

HTTP/2は通常、TLS上で動作し、ALPN (Application-Layer Protocol Negotiation) を使用してプロトコルネゴシエーションを行います。

### TLS (Transport Layer Security)

TLSは、インターネット上で安全な通信を提供するための暗号化プロトコルです。ウェブブラウザとサーバー間のHTTPS通信で広く使用されています。TLSハンドシェイク中に、クライアントとサーバーは暗号化アルゴリズム、鍵、および使用するアプリケーションプロトコル（ALPN）をネゴシエートします。

### ALPN (Application-Layer Protocol Negotiation)

ALPNは、TLSハンドシェイクの一部として、クライアントとサーバーがどのアプリケーションプロトコル（例: HTTP/1.1、HTTP/2）を使用するかをネゴシエートするためのTLS拡張です。HTTP/2では、ALPNを使用してHTTP/2プロトコルを確立することが一般的です。Goの `crypto/tls` パッケージでは、`tls.Config` の `NextProtos` フィールドでサポートするプロトコルを指定します。

### `sync.Once`

Goの `sync` パッケージが提供する `Once` 型は、特定の関数がプログラムの実行中に一度だけ実行されることを保証するためのプリミティブです。複数のゴルーチンから同時に呼び出されても、指定された関数は一度だけ実行され、その結果が共有されます。これは、初期化処理などでよく使用されます。

### `http2.ConfigureServer`

`golang.org/x/net/http2` パッケージ（またはGo 1.6以降では標準ライブラリに統合）に含まれる `ConfigureServer` 関数は、既存の `http.Server` インスタンスにHTTP/2のサポートを追加するために使用されます。この関数は、サーバーの `TLSNextProto` マップを設定し、ALPNネゴシエーションを通じてHTTP/2を有効にします。

## 技術的詳細

このコミットの主要な変更点は、`net/http` パッケージ内のHTTP/2設定ロジックの実行タイミングと構造の改善にあります。

### `ListenAndServeTLS` におけるHTTP/2設定の早期化

以前の `ListenAndServeTLS` 関数では、TLSリスナーの作成と起動がHTTP/2の設定よりも先行していました。

```go
// 変更前 (概念)
func (srv *Server) ListenAndServeTLS(certFile, keyFile string) error {
    // ... アドレス設定など ...

    // TLSConfigのクローンとNextProtosの設定
    config := cloneTLSConfig(srv.TLSConfig)
    if config.NextProtos == nil {
        config.NextProtos = []string{"http/1.1"} // ここでHTTP/1.1が追加される
    }
    // ... 証明書ロードなど ...

    // TLSリスナーの作成と起動
    tlsListener := tls.NewListener(ln, config)
    return srv.Serve(tlsListener) // ここでServeが呼ばれ、その中でHTTP/2設定が行われる可能性があった
}

// Serve関数内 (概念)
func (srv *Server) Serve(l net.Listener) error {
    // ...
    srv.nextProtoOnce.Do(srv.setNextProtoDefaults) // ここでHTTP/2設定が実行される
    if srv.nextProtoErr != nil {
        return srv.nextProtoErr // エラーがここで返されるが、リスナーは既に起動している
    }
    // ...
}
```

このコミットでは、`ListenAndServeTLS` の冒頭で `srv.setupHTTP2()` を呼び出すように変更されました。

```go
// 変更後
func (srv *Server) ListenAndServeTLS(certFile, keyFile string) error {
	if addr == "" {
		addr = ":https"
	}

	// Setup HTTP/2 before srv.Serve, to initialize srv.TLSConfig
	// before we clone it and create the TLS Listener.
	if err := srv.setupHTTP2(); err != nil {
		return err
	}

	config := cloneTLSConfig(srv.TLSConfig)
	if !strSliceContains(config.NextProtos, "http/1.1") {
		config.NextProtos = append(config.NextProtos, "http/1.1")
	}
    // ... (以下同様)
}
```

この変更により、`srv.setupHTTP2()` が `tls.Config` のクローン作成や `tls.NewListener` の呼び出しよりも前に実行されることが保証されます。もし `setupHTTP2` の中でHTTP/2の設定に失敗した場合、そのエラーはリスナーが起動する前に `ListenAndServeTLS` から直接返されるため、サーバーが不完全な状態で起動するのを防ぐことができます。

### `setupHTTP2` メソッドの導入とエラーハンドリングの改善

HTTP/2の設定ロジックは、`srv.nextProtoOnce.Do(srv.setNextProtoDefaults)` という形で `sync.Once` を使って一度だけ実行されていました。しかし、`sync.Once.Do` は引数として `func()` を取るため、直接エラーを返すことができませんでした。エラーは `srv.nextProtoErr` フィールドに格納され、後でチェックされる必要がありました。

このコミットでは、`setupHTTP2()` という新しいメソッドが導入され、HTTP/2の設定とエラーハンドリングがより明確になりました。

```go
// 変更前
// func (srv *Server) setNextProtoDefaults() { ... } // エラーはsrv.nextProtoErrに格納

// 変更後
func (srv *Server) setupHTTP2() error {
	srv.nextProtoOnce.Do(srv.onceSetNextProtoDefaults)
	return srv.nextProtoErr
}

// onceSetNextProtoDefaults configures HTTP/2, if the user hasn't
// configured otherwise. (by setting srv.TLSNextProto non-nil)
// It must only be called via srv.nextProtoOnce (use srv.setupHTTP2).
func (srv *Server) onceSetNextProtoDefaults() {
	// Enable HTTP/2 by default if the user hasn't otherwise
	// configured their TLSNextProto map.
	if srv.TLSNextProto == nil {
		// ... http2.ConfigureServer の呼び出しなど ...
		// エラーが発生した場合、srv.nextProtoErr に格納
	}
}
```

`setupHTTP2` は `srv.nextProtoOnce.Do(srv.onceSetNextProtoDefaults)` を呼び出し、その後に `srv.nextProtoErr` を返します。これにより、`ListenAndServeTLS` や `Serve` の呼び出し元は、HTTP/2設定の成否を直接エラーとして受け取ることができるようになりました。`setNextProtoDefaults` は `onceSetNextProtoDefaults` にリネームされ、その役割が `sync.Once` の内部で一度だけ実行される関数であることが明確になりました。

### `net/http/internal` パッケージの導入

テスト用のTLS証明書と秘密鍵 (`localhostCert`, `localhostKey`) は、以前は `src/net/http/httptest/server.go` 内に直接定義されていました。このコミットでは、これらの変数が `src/net/http/internal/testcert.go` という新しいファイルに移動され、`LocalhostCert` および `LocalhostKey` としてエクスポートされました。

*   **`net/http/internal`**: Goの `internal` パッケージは、そのパッケージ自身と、その親ディレクトリ内のパッケージからのみインポートできる特別なパッケージです。これにより、テスト用の証明書が `net/http` パッケージの内部でのみ使用され、外部に公開されないことが保証されます。
*   **依存関係の整理**: `httptest` パッケージは `net/http/internal` をインポートするように変更され、テスト証明書へのアクセスが可能になりました。これにより、テスト関連のコードがよりモジュール化され、`httptest` のコードが簡潔になりました。

### `testHookServerServe` の導入

`src/net/http/server.go` に `testHookServerServe` という関数型の変数と、`src/net/http/export_test.go` に `SetTestHookServerServe` という関数が追加されました。

```go

// src/net/http/export_test.go
```

`testHookServerServe` は、`Server.Serve` メソッドがリスナーを受け入れた直後に呼び出されるフックです。これは主にテスト目的で導入され、`httptest` パッケージが `ListenAndServeTLS` の内部で実際に使用されるリスナーを取得し、そのリスナーに対してTLS接続を確立してALPNネゴシエーションを検証するために使用されます。これにより、`ListenAndServeTLS` のような高レベルの関数が内部でどのように動作するかを、より詳細にテストできるようになります。

### `strSliceContains` ヘルパー関数

`src/net/http/server.go` に `strSliceContains` というシンプルなヘルパー関数が追加されました。

```go

		if v == s {
			return true
		}
	}
	return false
```

この関数は、文字列スライス `ss` に特定の文字列 `s` が含まれているかどうかを効率的にチェックするために使用されます。`ListenAndServeTLS` 内で `config.NextProtos` に "http/1.1" が既に含まれているかを確認するために利用されています。これにより、重複して "http/1.1" が追加されるのを防ぎます。

### 新しいテストケース `TestAutomaticHTTP2_ListenAndServe`

`src/net/http/serve_test.go` に `TestAutomaticHTTP2_ListenAndServe` という新しいテスト関数が追加されました。このテストは、`ListenAndServeTLS` がHTTP/2を正しくネゴシエートできることを検証します。

*   `SetTestHookServerServe` を使用して、`ListenAndServeTLS` が内部で作成する `net.Listener` を取得します。
*   取得したリスナーのアドレスに対してTLSクライアント接続を確立します。
*   クライアントの `tls.Config` の `NextProtos` に "h2" (HTTP/2) と "http/1.1" を含めることで、ALPNネゴシエーションをシミュレートします。
*   接続後、`c.ConnectionState().NegotiatedProtocol` が "h2" であること、および `NegotiatedProtocolIsMutual` が `true` であることをアサートし、HTTP/2が正常にネゴシエートされたことを確認します。
*   このテストは、`ListenAndServeTLS` がHTTP/2を適切に設定し、ALPNを通じてプロトコルをネゴシエートする能力を包括的に検証します。

```go
func TestAutomaticHTTP2_ListenAndServe(t *testing.T) {
	defer afterTest(t)
	defer SetTestHookServerServe(nil)
	cert, err := tls.X509KeyPair(internal.LocalhostCert, internal.LocalhostKey)
	if err != nil {
		t.Fatal(err)
	}
	var ok bool
	var s *Server
	const maxTries = 5
	var ln net.Listener
Try:
	for try := 0; try < maxTries; try++ {
		ln = newLocalListener(t)
		addr := ln.Addr().String()
		ln.Close()
		t.Logf("Got %v", addr)
		lnc := make(chan net.Listener, 1)
		SetTestHookServerServe(func(s *Server, ln net.Listener) {
			lnc <- ln
		})

			Addr: addr,
			TLSConfig: &tls.Config{
				Certificates: []tls.Certificate{cert},
			},
		}
		errc := make(chan error, 1)

		select {
		case err := <-errc:

			continue

			ok = true
			t.Logf("Listening on %v", ln.Addr().String())
			break Try
		}
	}

		t.Fatal("Failed to start up after %d tries", maxTries)
	}
	defer ln.Close()

		InsecureSkipVerify: true,
		NextProtos:         []string{"h2", "http/1.1"},
	})
	if err != nil {
		t.Fatal(err)
	}

	if got, want := c.ConnectionState().NegotiatedProtocol, "h2"; got != want {
		t.Errorf("NegotiatedProtocol = %q; want %q", got, want)
	}
	if got, want := c.ConnectionState().NegotiatedProtocolIsMutual, true; got != want {
		t.Errorf("NegotiatedProtocolIsMutual = %v; want %v", got, want)
```

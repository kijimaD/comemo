# [インデックス 22439] ファイルの概要

このコミットは、Go言語のツールチェインにおいて、`GOARCH=arm64` (ARMv8アーキテクチャ) のサポートを追加するものです。具体的には、GoコンパイラとアセンブラがARM64命令セットアーキテクチャ (ISA) を理解し、それに対応する機械語を生成できるようにするための基盤となる変更が含まれています。

## コミット

```
cmd/internal/obj, cmd/internal/obj/arm64: add support for GOARCH=arm64

ARM64 (ARMv8) has 32 general purpose, 64-bit integer registers
(R0-R31), 32 64-bit scalar floating point registers (F0-F31), and
32 128-bit vector registers (unused, V0-V31).

R31 is either the stack pointer (RSP), or the zero register (ZR),
depending on the instruction. Note the distinction between the
hardware stack pointer, RSP, and the virtual stack pointer SP.

The (hardware) stack pointer must be 16-byte aligned at all times;
the RSP register itself must be aligned, offset(RSP) only has to
have natural alignment.

Instructions are fixed-width, and are 32-bit wide. ARM64 supports
ARMv7 too (32-bit ARM), but not in the same process. In general,
there is not much in common between 32-bit ARM and ARM64, it's a
new architecture.

All implementations have floating point instructions.

This change adds a Prog.To3 field analogous to Prog.To. It is used
by exclusive load/store instructions such as STLXR which read from
one register, and write to both a register and a memory address.

        STLXRW  R1, (R0), R3

This will store the word contained in R1 to the memory address
pointed by R0. R3 will be updated with the status result of the
store. It is used to implement atomic operations.

No other changes are made to the portable Prog and Addr structures.
```

## 変更の背景

このコミットは、Go言語がARM64 (AArch64) アーキテクチャをサポートするための初期段階の重要な変更です。Go言語は、その設計当初から移植性を重視しており、様々なCPUアーキテクチャとオペレーティングシステムに対応することを目指しています。2015年3月8日のこのコミットは、同年8月にリリースされたGo 1.5でのLinux on ARM64およびiOS on ARM64のサポートに先立つものであり、Go言語がARM64ベースのサーバーやモバイルデバイスでネイティブに動作するための基盤を築くものでした。

ARM64は、従来の32ビットARM (ARMv7) とは大きく異なる新しいアーキテクチャであり、Goコンパイラとアセンブラがこの新しいアーキテクチャの特性（レジスタセット、命令形式、メモリモデルなど）を正確に理解し、効率的な機械語を生成できるようにするための大規模な変更が必要でした。このコミットは、特にアセンブラのバックエンド部分に焦点を当て、ARM64固有の命令やレジスタの定義、およびそれらを扱うためのロジックを追加しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が役立ちます。

1.  **ARM64 (AArch64) アーキテクチャ**:
    *   **レジスタセット**: ARM64は、32個の64ビット汎用整数レジスタ (X0-X30, SP/ZR)、32個の64ビット浮動小数点レジスタ (V0-V31、またはS0-S31/D0-D31)、および32個の128ビットSIMD/ベクトルレジスタ (V0-V31) を持ちます。R31は、命令によってスタックポインタ (SP) またはゼロレジスタ (ZR) として機能します。
    *   **スタックポインタ (SP)**: ハードウェアスタックポインタ (RSP) は常に16バイトアラインメントされている必要があります。
    *   **命令セット**: 命令は固定長の32ビット幅です。ARMv7 (32ビットARM) とは互換性がなく、新しいアーキテクチャとして設計されています。
    *   **排他的ロード/ストア命令**: `LDXR` (Exclusive Load Register) や `STXR` (Exclusive Store Register) などの命令は、アトミック操作を実装するために使用されます。これらは、マルチスレッド環境での競合状態を防ぐために、特定のメモリ位置へのアクセスを排他的に制御します。`STXR`命令は、ストアが成功したかどうかを示すステータス結果をレジスタに書き込みます。

2.  **Go言語のコンパイラとアセンブラの内部構造 (`cmd/internal/obj`)**:
    *   Goコンパイラは、ソースコードを中間表現に変換し、最終的にターゲットアーキテクチャの機械語に変換します。この過程で、`cmd/internal/obj`パッケージは、アセンブラのバックエンドとして機能し、機械語命令の抽象的な表現を扱います。
    *   **`Prog` 構造体**: `Prog` (Program) は、Goコンパイラの内部表現における単一の機械語命令または擬似命令を表します。命令の種類 (`As` フィールド)、ソースオペランド (`From` フィールド)、デスティネーションオペランド (`To` フィールド) などの情報を含みます。
    *   **`Addr` 構造体**: `Addr` (Address) は、命令のオペランド（レジスタ、メモリ位置、定数、ラベルなど）を表します。オペランドの種類 (`Type` フィールド)、レジスタ番号 (`Reg` フィールド)、オフセット (`Offset` フィールド)、シンボル (`Sym` フィールド) などの情報を含みます。
    *   **`Prog.To3` フィールド**: 通常の命令は最大2つのオペランド (`From` と `To`) を持ちますが、一部のアーキテクチャ固有の命令（特にアトミック操作に関連するもの）は3つ以上のオペランドを必要とします。このコミットで追加された `Prog.To3` は、そのような3番目のオペランドを表現するために導入されました。

## 技術的詳細

このコミットの主要な技術的変更点は、Go言語のツールチェインがARM64アーキテクチャの特性を正確にモデル化し、それに対応する機械語を生成できるようにすることです。

1.  **ARM64レジスタの定義**: `src/cmd/internal/obj/arm64/7.out.go` および `src/cmd/internal/obj/arm64/anames.go` では、ARM64の汎用レジスタ (R0-R31)、浮動小数点レジスタ (F0-F31)、およびSIMDレジスタ (V0-V31) がGoの内部表現で定義されています。特に、R31がスタックポインタ (RSP) とゼロレジスタ (ZR) の両方として機能する特性が考慮されています。
2.  **ARM64命令の定義とエンコーディング**: `src/cmd/internal/obj/arm64/asm7.go` は、ARM64命令のエンコーディングロジックと、Goの`Prog`構造体から実際の機械語バイト列を生成するためのアセンブラの主要部分を実装しています。これには、算術演算、論理演算、メモリロード/ストア、分岐、システム命令など、多岐にわたるARM64命令が含まれます。
3.  **`Prog.To3` フィールドの導入と利用**:
    *   コミットメッセージで強調されているように、この変更の重要な側面は、`Prog`構造体に`To3`フィールドが追加されたことです。これは、`Prog.To`と同様にオペランドを表しますが、特にARM64の排他的ロード/ストア命令 (`STLXR`など) のような、3つ目のオペランドを必要とする命令のために設計されました。
    *   例として挙げられている `STLXRW R1, (R0), R3` 命令は、R1の値をR0が指すメモリアドレスにストアし、その操作のステータス結果をR3に書き込みます。ここで、R1がソース、(R0) がメモリデスティネーション、R3がステータス結果のデスティネーションとなり、R3が3番目のオペランドとして`Prog.To3`にマッピングされます。
    *   この`To3`フィールドの導入により、Goのアセンブラは、ARM64の複雑なアトミック操作命令を正確に表現し、コンパイル時に適切な機械語を生成できるようになります。
4.  **アドレス指定モードのサポート**: ARM64には多様なアドレス指定モードがあります。このコミットでは、オフセット付きのロード/ストア、プリインデックス/ポストインデックスアドレッシング、レジスタペアのロード/ストアなど、ARM64固有のアドレス指定モードが`asm7.go`でサポートされています。
5.  **スタックアラインメントの考慮**: ARM64のABI (Application Binary Interface) では、スタックポインタが常に16バイトアラインメントされている必要があります。`asm7.go`内の`span7`関数などでは、このアラインメント要件を満たすようにコード生成が行われます。

*   `src/cmd/internal/obj/arm64/util.go`: ARM64アーキテクチャ固有の汎用ユーティリティ関数が含まれるファイル。
*   `src/cmd/internal/obj/link.go`: `Prog.To3`フィールドの追加に伴い、`Prog`構造体の定義が更新されています。
*   `src/cmd/internal/obj/util.go`: `Prog`構造体に関連するユーティリティ関数が更新されています。

## コアとなるコードの解説

このコミットの核心は、`src/cmd/internal/obj/arm64/asm7.go` にあります。このファイルは、Goコンパイラが生成した抽象的な命令表現 (`Prog`構造体) を、実際のARM64機械語に変換する役割を担っています。

*   **`optab` 変数**: `asm7.go` 内の `optab` 変数は、Goの内部命令コード (`obj.ATEXT`, `AADD` など) と、それに対応するオペランドの組み合わせ、命令のタイプ、サイズ、フラグなどを定義するテーブルです。このテーブルは、Goのアセンブラが特定の命令とオペランドの組み合わせに対して、どのARM64命令を生成すべきかを決定するために使用されます。例えば、`{AADD, C_REG, C_REG, C_REG, 1, 4, 0, 0, 0}` のようなエントリは、「`AADD` 命令が3つのレジスタオペランドを持つ場合、タイプ1の命令として4バイトのサイズでエンコードされる」ことを示します。
*   **`asmout` 関数**: `asmout` 関数は、`Prog`構造体と`optab`から得られた情報に基づいて、実際のARM64機械語のバイト列を生成します。この関数は、各ARM64命令のビットフィールドレイアウトを理解し、オペランドの値を適切な位置に配置して、最終的な32ビット命令ワードを構築します。
*   **`Prog.To3` の利用**: `optab` 内の `ASTXR` や `ASTLXR` などの排他的ロード/ストア命令のエントリでは、`to3=C_REG` のようなコメントが見られます。これは、これらの命令が3番目のオペランドとしてレジスタを必要とし、それが`Prog.To3`フィールドにマッピングされることを示唆しています。`asmout`関数は、これらの命令を処理する際に、`Prog.To3`フィールドの値を読み取り、それをARM64命令の適切なビットフィールドにエンコードします。
*   **レジスタ定義**: `src/cmd/internal/obj/arm64/7.out.go` では、`REG_R0`から`REG_R31`、`REG_F0`から`REG_F31`などの定数が定義されており、これらはGoの内部でARM64の物理レジスタを表すために使用されます。また、`REGZERO` (ゼロレジスタ) と `REGSP` (スタックポインタ) が、物理レジスタR31から派生した特別な値として定義されている点も注目に値します。

これらの変更により、GoコンパイラはARM64アーキテクチャの複雑な詳細を抽象化し、開発者がGo言語で記述したコードをARM64上で効率的に実行できるようになります。

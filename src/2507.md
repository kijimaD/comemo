# [インデックス 2507] ファイルの概要

このコミットは、Go言語の初期の`net/http`パッケージにおけるHTTPクライアントの挙動を改善するものです。具体的には、HTTPレスポンスのステータス行のパース処理のバグ修正、すべてのPOSTリクエストに対するチャンク転送エンコーディングの強制適用、チャンク読み取りの実装、および`http.Request.write`メソッドをHTTP/1.1専用とすることによって、HTTP/1.1プロトコルへの準拠と堅牢性を向上させています。

## コミット

HTTPクライアントが、スペースを含むステータスメッセージ（例: "HTTP/1.1 400 Bad Request"）を正しく処理できるように修正。
すべてのPOSTリクエストに対してチャンク転送エンコーディングを使用するように変更。
チャンク読み取り機能を実装。
`http.Request.write`メソッドをHTTP/1.1専用に変更。

## 変更の背景

このコミットが行われた2009年当時、Go言語はまだ開発の初期段階にあり、標準ライブラリ、特に`net/http`パッケージは継続的に改善されていました。このコミットの背景には、主に以下の問題とHTTPプロトコルの標準への準拠という目的がありました。

1.  **HTTPステータスメッセージのパース問題**: HTTPレスポンスのステータス行は、`HTTP/1.1 200 OK` のように、ステータスコードの後に理由フレーズ（reason phrase）が続きます。この理由フレーズにはスペースが含まれることが一般的です（例: "Bad Request"）。しかし、従来のパースロジックでは、ステータス行を単純にスペースで分割（`strings.Split`）していたため、理由フレーズにスペースが含まれる場合に、ステータスコードや理由フレーズを誤って解釈してしまう可能性がありました。これは、HTTPクライアントがサーバーからの応答を正しく理解できないというバグにつながります。

2.  **POSTリクエストのボディ送信の改善**: HTTP/1.1では、メッセージボディの長さを事前に知らなくても送信できる「チャンク転送エンコーディング（Chunked Transfer-Encoding）」が導入されました。特にPOSTリクエストでは、送信するデータのサイズが事前に確定しない場合や、ストリーミングでデータを送信したい場合に、`Content-Length`ヘッダを事前に設定することが困難です。チャンク転送エンコーディングを使用することで、このようなシナリオでも効率的かつ柔軟にデータを送信できるようになります。このコミットは、すべてのPOSTリクエストでチャンク転送エンコーディングを強制することで、この問題を解決し、より堅牢なクライアント実装を目指しました。

3.  **チャンク転送エンコーディングの受信対応**: クライアントがチャンク転送エンコーディングで送信するだけでなく、サーバーからのチャンクエンコードされたレスポンスボディも正しく読み取れるようにする必要がありました。これにより、クライアントはより広範なHTTPサーバーと互換性を持つことができます。

4.  **HTTP/1.1への明確な移行**: `http.Request.write`メソッドをHTTP/1.1専用とすることで、GoのHTTPクライアントがHTTP/1.1プロトコルを標準として扱う意図が明確になりました。これにより、プロトコルの挙動が統一され、将来的な機能追加や最適化がしやすくなります。

これらの変更は、Goの`net/http`パッケージがより堅牢で、標準に準拠し、実用的なHTTPクライアントとして機能するための重要なステップでした。

## 前提知識の解説

### HTTP/1.1 プロトコル

HTTP/1.1は、Webで広く利用されているハイパーテキスト転送プロトコル（HTTP）のバージョンです。HTTP/1.0からの主要な改善点として、永続的接続（Persistent Connections）、パイプライン処理（Pipelining）、ホストヘッダ（Host Header）、そして**チャンク転送エンコーディング（Chunked Transfer-Encoding）**などがあります。このコミットでは、特にステータス行の解釈とチャンク転送エンコーディングが重要になります。

### HTTP ステータス行 (Status Line)

HTTPレスポンスの最初の行は「ステータス行」と呼ばれ、以下の形式に従います。

`HTTP-Version SP Status-Code SP Reason-Phrase CRLF`

*   `HTTP-Version`: 使用されているHTTPプロトコルのバージョン（例: `HTTP/1.1`）。
*   `SP`: スペース（空白文字）。
*   `Status-Code`: 3桁の整数で、リクエストの結果を示す（例: `200` for OK, `404` for Not Found）。
*   `Reason-Phrase`: ステータスコードを人間が読める形で説明するテキスト（例: `OK`, `Not Found`, `Bad Request`）。このフレーズにはスペースが含まれることがあります。
*   `CRLF`: キャリッジリターンとラインフィード（改行）。

このコミットの修正前は、`Reason-Phrase`にスペースが含まれる場合にパースエラーが発生する可能性がありました。

### チャンク転送エンコーディング (Chunked Transfer-Encoding)

HTTP/1.1で導入されたメッセージボディの転送メカニズムの一つです。これは、メッセージボディの長さを事前に知ることなく、動的に生成されるコンテンツを送信するために使用されます。

**仕組み:**

1.  メッセージボディは、複数の「チャンク（塊）」に分割されます。
2.  各チャンクは、そのチャンクのサイズ（16進数表記）とCRLFで始まり、その後に実際のデータとCRLFが続きます。
3.  すべてのチャンクの送信が完了すると、サイズが`0`のチャンク（終端チャンク）が送信されます。
4.  終端チャンクの後には、オプションでトレーラーヘッダ（trailer headers）が続き、最後にCRLFが2回送信されてメッセージボディの終了を示します。

**利点:**

*   **動的なコンテンツ**: サーバーがレスポンスボディの全長を事前に計算する必要がないため、動的に生成されるコンテンツやストリーミングデータに適しています。
*   **永続的接続の活用**: `Content-Length`ヘッダがない場合でも、永続的接続を維持したまま複数のリクエスト/レスポンスを処理できます。

このコミットでは、POSTリクエストの送信時と、チャンクエンコードされたレスポンスの受信時の両方でこのメカニズムをサポートするように変更されました。

### Goの `net/http` パッケージ (初期バージョン)

`net/http`パッケージは、Go言語におけるHTTPクライアントおよびサーバーの実装を提供します。このコミットが行われた時期は、Go言語がオープンソース化されて間もない頃であり、パッケージのAPIや内部実装はまだ活発に進化していました。このコミットは、その進化の過程で、HTTPプロトコルの標準への準拠と実用性の向上を目指したものです。

## 技術的詳細

このコミットは、`src/pkg/http/client.go`と`src/pkg/http/request.go`の2つのファイルにわたって、HTTPクライアントの挙動を根本的に改善しています。

### 1. HTTPステータスメッセージのパース修正 (`src/pkg/http/client.go`)

従来のコードでは、HTTPレスポンスのステータス行（例: `HTTP/1.1 400 Bad Request`）をスペースで分割し、ステータスコードと理由フレーズを抽出していました。

```go
// 修正前
ss := strings.Split(line, " ");
if len(ss) != 3 {
    return nil, os.ErrorString(fmt.Sprintf("Invalid first line in HTTP response: %q", line));
}
resp.Status = ss[1] + " " + ss[2];
resp.StatusCode, err = strconv.Atoi(ss[1]);
```

このロジックでは、`Bad Request`のように理由フレーズにスペースが含まれると、`ss`の要素数が3を超えてしまい、パースエラーが発生していました。

修正後のコードでは、`strings.Index`を使用して最初の2つのスペースの位置を特定することで、より堅牢にステータスコードと理由フレーズを抽出しています。

```go
// 修正後
i := strings.Index(line, " ");
j := strings.Index(line[i+1:len(line)], " ") + i+1;
if i < 0 || j < 0 {
    return nil, os.ErrorString(fmt.Sprintf("Invalid first line in HTTP response: %q", line));
}
resp.Status = line[i+1:len(line)]; // ステータスコード以降の全てを理由フレーズとして扱う
resp.StatusCode, err = strconv.Atoi(line[i+1:j]); // 2番目のスペースまでの部分をステータスコードとしてパース
```

これにより、理由フレーズにスペースが含まれていても、ステータスコードを正確に抽出し、ステータス行全体を`resp.Status`に格納できるようになりました。

`http.Post`関数が変更され、`bodyType`引数が追加されました。そして、`req.Header`に`"Transfer-Encoding": "chunked"`が明示的に設定されるようになりました。

さらに、`http.Request.write`メソッド内で、`req.Body`が存在する場合に`"Transfer-Encoding": "chunked"`ヘッダが強制的に追加されるロジックが組み込まれました。

```go

### 3. チャンク読み取りの実装 (`src/pkg/http/request.go`)

`chunkedReader`という新しい型が導入され、チャンク転送エンコーディングで送られてくるメッセージボディを読み取るためのロジックが実装されました。

*   **`chunkedReader`構造体**: `bufio.Reader`と、現在のチャンクに残っているバイト数を追跡する`n`フィールド、およびエラーを保持する`err`フィールドを持ちます。
*   **`newChunkedReader`関数**: `bufio.Reader`を受け取り、新しい`chunkedReader`インスタンスを生成します。
*   **`beginChunk`メソッド**: 次のチャンクのサイズを読み取り、`cr.n`に設定します。サイズが`0`の場合は、終端チャンクとトレーラーヘッダを処理し、`os.EOF`を設定します。
*   **`Read`メソッド**: `io.Reader`インターフェースを実装し、チャンクデータを読み取ります。現在のチャンクのデータが尽きたら`beginChunk`を呼び出して次のチャンクを読み込みます。チャンクの終端を示すCRLFも消費します。

この`chunkedReader`は、`src/pkg/http/client.go`の`send`関数内で、レスポンスヘッダに`Transfer-Encoding: chunked`が存在する場合に`resp.Body`として設定されます。

```go
// src/pkg/http/client.go の send 関数内
var r io.Reader = reader;
if v := resp.GetHeader("Transfer-Encoding"); v == "chunked" {
    r = newChunkedReader(reader);
}
resp.Body = readClose{ r, conn };
```

また、`src/pkg/http/request.go`の`ReadRequest`関数でも、リクエストヘッダに`Transfer-Encoding: chunked`が存在する場合に`req.Body`として`newChunkedReader`が設定されるようになりました。

```go
// src/pkg/http/request.go の ReadRequest 関数内
if v, present := req.Header["Transfer-Encoding"]; present && v == "chunked" {
    req.Body = newChunkedReader(b);
} else if v, present := req.Header["Content-Length"]; present {
    // ... 従来の Content-Length 処理
}
```

これにより、GoのHTTPクライアントは、チャンクエンコードされたレスポンスボディを透過的に処理できるようになりました。

### 4. `http.Request.write`をHTTP/1.1専用に変更 (`src/pkg/http/request.go`)

`http.Request.write`メソッドのコメントが更新され、「Write an HTTP/1.1 request」と明記されました。また、リクエストラインのプロトコルバージョンが`HTTP/1.1`に固定されました。

```go
// 修正前
// fmt.Fprintf(w, "%s %s %s\\r\\n", valueOrDefault(req.Method, "GET"), uri, valueOrDefault(req.Proto, "HTTP/1.0"));

// 修正後
fmt.Fprintf(w, "%s %s HTTP/1.1\\r\\n", valueOrDefault(req.Method, "GET"), uri);
```

これにより、GoのHTTPクライアントが送信するリクエストは、常にHTTP/1.1プロトコルバージョンを使用することが保証されます。

## 変更の背景

このコミットが行われた2009年当時、Go言語はまだ開発の初期段階にあり、標準ライブラリ、特に`net/http`パッケージは継続的に改善されていました。このコミットの背景には、主に以下の問題とHTTPプロトコルの標準への準拠という目的がありました。

1.  **HTTPステータスメッセージのパース問題**: HTTPレスポンスのステータス行は、`HTTP/1.1 200 OK` のように、ステータスコードの後に理由フレーズ（reason phrase）が続きます。この理由フレーズにはスペースが含まれることが一般的です（例: "Bad Request"）。しかし、従来のパースロジックでは、ステータス行を単純にスペースで分割（`strings.Split`）していたため、理由フレーズにスペースが含まれる場合に、ステータスコードや理由フレーズを誤って解釈してしまう可能性がありました。これは、HTTPクライアントがサーバーからの応答を正しく理解できないというバグにつながります。

2.  **POSTリクエストのボディ送信の改善**: HTTP/1.1では、メッセージボディの長さを事前に知らなくても送信できる「チャンク転送エンコーディング（Chunked Transfer-Encoding）」が導入されました。特にPOSTリクエストでは、送信するデータのサイズが事前に確定しない場合や、ストリーミングでデータを送信したい場合に、`Content-Length`ヘッダを事前に設定することが困難です。チャンク転送エンコーディングを使用することで、このようなシナリオでも効率的かつ柔軟にデータを送信できるようになります。このコミットは、すべてのPOSTリクエストでチャンク転送エンコーディングを強制することで、この問題を解決し、より堅牢なクライアント実装を目指しました。

3.  **チャンク転送エンコーディングの受信対応**: クライアントがチャンク転送エンコーディングで送信するだけでなく、サーバーからのチャンクエンコードされたレスポンスボディも正しく読み取れるようにする必要がありました。これにより、クライアントはより広範なHTTPサーバーと互換性を持つことができます。

4.  **HTTP/1.1への明確な移行**: `http.Request.write`メソッドをHTTP/1.1専用とすることで、GoのHTTPクライアントがHTTP/1.1プロトコルを標準として扱う意図が明確になりました。これにより、プロトコルの挙動が統一され、将来的な機能追加や最適化がしやすくなります。

これらの変更は、Goの`net/http`パッケージがより堅牢で、標準に準拠し、実用的なHTTPクライアントとして機能するための重要なステップでした。

## 前提知識の解説

### HTTP/1.1 プロトコル

HTTP/1.1は、Webで広く利用されているハイパーテキスト転送プロトコル（HTTP）のバージョンです。HTTP/1.0からの主要な改善点として、永続的接続（Persistent Connections）、パイプライン処理（Pipelining）、ホストヘッダ（Host Header）、そして**チャンク転送エンコーディング（Chunked Transfer-Encoding）**などがあります。このコミットでは、特にステータス行の解釈とチャンク転送エンコーディングが重要になります。

### HTTP ステータス行 (Status Line)

HTTPレスポンスの最初の行は「ステータス行」と呼ばれ、以下の形式に従います。

`HTTP-Version SP Status-Code SP Reason-Phrase CRLF`

*   `HTTP-Version`: 使用されているHTTPプロトコルのバージョン（例: `HTTP/1.1`）。
*   `SP`: スペース（空白文字）。
*   `Status-Code`: 3桁の整数で、リクエストの結果を示す（例: `200` for OK, `404` for Not Found）。
*   `Reason-Phrase`: ステータスコードを人間が読める形で説明するテキスト（例: `OK`, `Not Found`, `Bad Request`）。このフレーズにはスペースが含まれることがあります。
*   `CRLF`: キャリッジリターンとラインフィード（改行）。

このコミットの修正前は、`Reason-Phrase`にスペースが含まれる場合にパースエラーが発生する可能性がありました。

### チャンク転送エンコーディング (Chunked Transfer-Encoding)

HTTP/1.1で導入されたメッセージボディの転送メカニズムの一つです。これは、メッセージボディの長さを事前に知ることなく、動的に生成されるコンテンツを送信するために使用されます。

**仕組み:**

1.  メッセージボディは、複数の「チャンク（塊）」に分割されます。
2.  各チャンクは、そのチャンクのサイズ（16進数表記）とCRLFで始まり、その後に実際のデータとCRLFが続きます。
3.  すべてのチャンクの送信が完了すると、サイズが`0`のチャンク（終端チャンク）が送信されます。
4.  終端チャンクの後には、オプションでトレーラーヘッダ（trailer headers）が続き、最後にCRLFが2回送信されてメッセージボディの終了を示します。

**利点:**

*   **動的なコンテンツ**: サーバーがレスポンスボディの全長を事前に計算する必要がないため、動的に生成されるコンテンツやストリーミングデータに適しています。
*   **永続的接続の活用**: `Content-Length`ヘッダがない場合でも、永続的接続を維持したまま複数のリクエスト/レスポンスを処理できます。

このコミットでは、POSTリクエストの送信時と、チャンクエンコードされたレスポンスの受信時の両方でこのメカニズムをサポートするように変更されました。

### Goの `net/http` パッケージ (初期バージョン)

`net/http`パッケージは、Go言語におけるHTTPクライアントおよびサーバーの実装を提供します。このコミットが行われた時期は、Go言語がオープンソース化されて間もない頃であり、パッケージのAPIや内部実装はまだ活発に進化していました。このコミットは、その進化の過程で、HTTPプロトコルの標準への準拠と実用性の向上を目指したものです。

従来のコードでは、HTTPレスポンスのステータス行（例: `HTTP/1.1 400 Bad Request`）をスペースで分割し、ステータスコードと理由フレーズを抽出していました。

## コアとなるコードの解説

### `src/pkg/http/client.go` の変更点

1.  **ステータス行のパースロジックの改善**:
    *   `strings.Split(line, " ")` を `strings.Index` を用いたロジックに置き換えました。
    *   `i := strings.Index(line, " ")` で最初のスペースの位置を見つけます。これはプロトコルバージョン（例: `HTTP/1.1`）とステータスコードの間のスペースです。
    *   `j := strings.Index(line[i+1:len(line)], " ") + i+1` で2番目のスペースの位置を見つけます。これはステータスコードと理由フレーズの間のスペースです。
    *   `resp.Status = line[i+1:len(line)]` により、ステータスコード以降の文字列全体を理由フレーズとして`resp.Status`に格納します。これにより、理由フレーズにスペースが含まれていても問題なく処理できます。
    *   `resp.StatusCode, err = strconv.Atoi(line[i+1:j])` により、最初のスペースの次から2番目のスペースの手前までをステータスコードとして抽出し、整数に変換します。
    *   この変更により、`"HTTP/1.1 400 Bad Request"`のようなステータス行も正しくパースできるようになりました。

2.  **チャンクエンコードされたレスポンスボディの処理**:
    *   `send`関数内で、レスポンスヘッダに`"Transfer-Encoding": "chunked"`が存在する場合、`resp.Body`として新しく導入された`newChunkedReader(reader)`が設定されます。
    *   これにより、クライアントはサーバーからチャンクエンコードされたレスポンスボディを透過的に読み取ることができるようになります。

3.  **`http.Post`関数の変更**:
    *   関数のシグネチャが `func Post(url string, requestBody io.Reader)` から `func Post(url string, bodyType string, body io.Reader)` に変更されました。`bodyType`引数が追加され、`requestBody`が`body`にリネームされました。
    *   `req.Header`マップに`"Content-Type": bodyType`と`"Transfer-Encoding": "chunked"`が明示的に設定されるようになりました。これにより、`Post`リクエストは常にチャンク転送エンコーディングを使用するようになります。

1.  **`chunkSize`定数の追加**:
    *   `chunkSize = 4 << 10` (4KB) が追加され、チャンク転送エンコーディングでボディを書き込む際のバッファサイズとして使用されます。

2.  **`BadChunkedEncoding`エラーの追加**:
    *   チャンク転送エンコーディングのパースエラーを示す新しいエラー定数が追加されました。

3.  **`http.Request.write`メソッドの変更**:
    *   メソッドのコメントが「Write an HTTP/1.1 request」に変更され、HTTP/1.1専用であることが明確化されました。
    *   リクエストラインのプロトコルバージョンが `valueOrDefault(req.Proto, "HTTP/1.0")` から `"HTTP/1.1"` に固定されました。
    *   `req.Body`が存在する場合、`req.Header["Transfer-Encoding"] = "chunked"` が強制的に設定されるようになりました。これにより、`Content-Length`ヘッダがなくてもボディを送信できるようになります。
    *   ボディの書き込みロジックが `io.Copy(req.Body, w)` から、チャンク転送エンコーディングの仕様に準拠したループ処理に変更されました。

        *   読み込んだバイト数を16進数で書き込み、CRLFを続けます。
        *   実際のボディデータを書き込み、CRLFを続けます。
        *   ボディの終端に達したら、`"0\\r\\n\\r\\n"`（終端チャンクと最後のCRLF）を書き込みます。

4.  **`chunkedReader`型の導入と実装**:

    *   `beginChunk`は、次のチャンクのサイズを読み取り、`cr.n`に設定します。サイズが0の場合は、トレーラーヘッダを読み飛ばし、`os.EOF`を設定します。

    *   `ReadRequest`関数内で、リクエストヘッダに`"Transfer-Encoding": "chunked"`が存在する場合、`req.Body`として`newChunkedReader(b)`が設定されるようになりました。
    *   これにより、サーバー側もチャンクエンコードされたリクエストボディを透過的に読み取ることができるようになります。

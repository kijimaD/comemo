# [インデックス 26811] ファイルの概要

このコミットは、Goコンパイラの内部、特に字句解析（lexer）と構文解析（parser）の段階における重要な変更を導入しています。主な目的は、演算子の優先順位を管理するための`prectab`というテーブルを廃止し、そのロジックを字句解析器に統合することです。また、インクリメント演算子（`++`）とデクリメント演算子（`--`）を表す`LINC`と`LDEC`トークンを、`LINCOP`という単一のトークンに統合しています。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、字句解析、構文解析、意味解析、最適化、コード生成といった複数の段階を経ます。このコミットは、その初期段階である字句解析と構文解析の効率性と設計の改善を目的としています。

以前のGoコンパイラでは、演算子の優先順位を決定するために`prectab`というテーブルが構文解析器（`parser.go`）で使用されていました。しかし、このアプローチは、字句解析器（`lex.go`）がトークンを生成した後、構文解析器が再度そのトークンの優先順位をルックアップする必要があるため、冗長性や非効率性を生む可能性がありました。

また、インクリメント演算子（`++`）とデクリメント演算子（`--`）は、それぞれ`LINC`と`LDEC`という個別のトークンとして扱われていました。これらの演算子は、代入演算子（`+=`, `-=`など）と類似した構造を持つため、これらをより統一的に扱うことで、コードの簡素化と保守性の向上が期待されました。

このコミットは、これらの課題に対処し、コンパイラの内部構造をより洗練されたものにすることを目指しています。

## 前提知識の解説

*   **`cmd/compile`**: Go言語の公式コンパイラです。Goソースコードをバイナリ実行可能ファイルに変換します。
*   **字句解析器 (Lexer/Scanner)**: ソースコードを読み込み、意味のある最小単位である「トークン」に分割するコンパイラの最初の段階です。例えば、`var x = 1 + 2;`というコードは、`var`、`x`、`=`、`1`、`+`、`2`、`;`といったトークンに分割されます。
*   **構文解析器 (Parser)**: 字句解析器が生成したトークンのストリームを受け取り、言語の文法規則に従って、それらが正しい構造（構文木）を形成しているかを確認します。
*   **トークン**: プログラミング言語のソースコードにおける意味のある最小単位です。キーワード、識別子、演算子、リテラルなどが含まれます。
*   **演算子の優先順位 (Operator Precedence)**: 複数の演算子を含む式において、どの演算子が先に評価されるかを決定する規則です。例えば、`1 + 2 * 3`では、乗算（`*`）が加算（`+`）よりも優先されるため、結果は`7`になります。
*   **`++` (インクリメント演算子) と `--` (デクリメント演算子)**: 変数の値を1増やす（`x++`は`x = x + 1`と等価）または1減らす（`x--`は`x = x - 1`と等価）ための演算子です。Go言語では、これらの演算子は後置（postfix）のみが許可されており、文としてのみ使用できます（式としては使用できません）。
*   **`prectab`**: 以前のGoコンパイラで、構文解析時に演算子の優先順位をルックアップするために使用されていたテーブルです。

## 技術的詳細

このコミットの核となる変更は、演算子の優先順位の決定ロジックを構文解析器から字句解析器へ移行した点と、インクリメント/デクリメント演算子のトークンを統合した点です。

1.  **`prectab`の廃止と字句解析器への優先順位情報の統合**:
    *   以前は、`parser.go`内の`prectab`というマップが、各トークンに対応する優先順位（`prec`）と演算子タイプ（`Op`）を保持していました。構文解析器は、式を解析する際にこのテーブルを参照して、演算子の結合順序を決定していました。
    *   このコミットでは、`lex.go`内の`lexer`構造体に`prec OpPrec`フィールドが追加されました。`OpPrec`は演算子の優先順位を表す新しい型です。
    *   字句解析器の`next()`メソッドが、トークンを識別する際に、そのトークンが演算子であれば、対応する優先順位を`l.prec`に、そして演算子タイプを`l.op`に直接設定するようになりました。これにより、構文解析器はトークンを受け取った時点で、その優先順位情報を既に持っていることになります。
    *   `parser.go`内の`bexpr`関数（二項演算子を含む式を解析する関数）は、`prectab`を参照する代わりに、`p.prec`（字句解析器から渡された優先順位）を直接利用して、再帰的に式を解析するようになりました。これにより、構文解析器のロジックが簡素化され、効率が向上します。

2.  **`LINC`と`LDEC`の`LINCOP`への統合**:
    *   以前は、`++`は`LINC`、`--`は`LDEC`という別々のトークンとして扱われていました。
    *   このコミットでは、`LINC`と`LDEC`が廃止され、`LINCOP`という新しいトークンが導入されました。
    *   字句解析器の`next()`メソッドは、`++`または`--`を検出した場合、`LINCOP`トークンを生成し、同時にその演算子タイプ（`OADD`または`OSUB`）を`l.op`に設定します。
    *   `parser.go`内の`simple_stmt`関数（単純な文を解析する関数）は、`LINC`や`LDEC`ではなく`LINCOP`を処理するように変更され、`l.op`から実際の演算子タイプを取得して抽象構文木（AST）を構築します。これにより、インクリメント/デクリメント演算子の処理ロジックが統一され、コードの重複が削減されます。

これらの変更により、コンパイラの設計がより一貫性のあるものになり、字句解析と構文解析の間の情報フローが改善されました。

## コアとなるコードの変更箇所

### `src/cmd/compile/internal/gc/lex.go`

*   `lexer`構造体に`prec OpPrec`フィールドが追加されました。
*   `OpPrec`型と、`PCOMM`, `POROR`, `PANDAND`, `PCMP`, `PADD`, `PMUL`といった演算子優先順位定数が定義されました。
*   `LINC`と`LDEC`トークンが削除され、`LINCOP`が追加されました。
*   `next()`関数内で、各演算子（`*`, `/`, `%`, `+`, `-`, `>>`, `<<`, `&`, `|`, `^`, `==`, `!=`, `<`, `<=`, `>`, `>=`など）を識別する際に、`l.op`と`l.prec`が適切に設定されるようになりました。
*   特に、`incop`と`binop`/`binop1`という新しいラベルが導入され、インクリメント/デクリメント演算子と二項演算子の処理ロジックが統一されました。

### `src/cmd/compile/internal/gc/parser.go`

*   `tokstrings`マップから`LDEC`と`LINC`が削除され、`LINCOP`が追加されました。
*   `simple_stmt`関数内で、`LINC`と`LDEC`を処理していた`case`文が`LINCOP`を処理するように変更され、`p.op`から実際の演算子タイプ（`OADD`または`OSUB`）を取得するようになりました。
*   `prectab`マップが完全に削除されました。
*   `bexpr`関数のシグネチャが`func (p *parser) bexpr(prec int) *Node`から`func (p *parser) bexpr(prec OpPrec) *Node`に変更され、`prectab`を参照する代わりに`p.prec`（字句解析器から提供される優先順位）を使用するようにロジックが書き換えられました。
*   `expr()`関数が`p.bexpr(1)`ではなく`p.bexpr(0)`を呼び出すようになりました。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/lex.go`の変更点

```go
type lexer struct {
	// ...
	tok  int32
	sym_ *Sym   // valid if tok == LNAME
	val  Val    // valid if tok == LLITERAL
	op   Op     // valid if tok == LASOP or LINCOP, or prec > 0
	prec OpPrec // operator precedence; 0 if not a binary operator
}

type OpPrec int

const (
	// Precedences of binary operators (must be > 0).
	PCOMM OpPrec = 1 + iota
	POROR
	PANDAND
	PCMP
	PADD
	PMUL
)

// ...

const (
	// ...
	// LDEC, LINC が削除された
	LINCOP // 新しく追加された
	// ...
)

func (l *lexer) next() {
	// ...
	l.prec = 0 // 各トークン解析前に優先順位をリセット
	// ...
	var op Op
	var prec OpPrec // 各演算子トークン解析時に設定される

	switch c {
	// ...
	case '*':
		op = OMUL
		prec = PMUL
		goto binop // 二項演算子として処理
	// ...
	case '+':
		op = OADD
		goto incop // インクリメント/デクリメント/代入演算子として処理
	// ...
	}

incop: // ++, --, +=, -= などの処理
	c1 = l.getr()
	if c1 == c { // ++ または -- の場合
		l.nlsemi = true
		l.op = op // OADD または OSUB
		c = LINCOP // トークンをLINCOPに設定
		goto lx
	}
	prec = PADD // +=, -= などの優先順位
	goto binop1

binop: // *, /, %, &, <<, >>, &^ などの処理
	c1 = l.getr()
binop1: // binopまたはincopからジャンプしてくる
	if c1 != '=' { // = が続かない場合（通常の二項演算子）
		l.ungetr(c1)
		l.op = op
		l.prec = prec
		goto lx
	}
	// = が続く場合（代入演算子）
	l.op = op // OADD, OSUB, OMUL など
	// l.prec は設定されない (LASOPは優先順位を持たないため)
	// ...
}
```
`lexer`構造体に`prec`フィールドが追加され、`next()`関数内でトークンを読み込む際に、そのトークンが演算子であれば、対応する演算子タイプ（`l.op`）と優先順位（`l.prec`）が直接設定されるようになりました。これにより、字句解析の段階で演算子の優先順位情報が決定され、構文解析器に渡されるようになります。`LINC`と`LDEC`が`LINCOP`に統合され、`incop`と`binop`という新しい処理フローによって、`++`, `--`, `+=`, `-=`などの演算子が統一的に扱われるようになっています。

### `src/cmd/compile/internal/gc/parser.go`の変更点

```go
// ...
// prectab が削除された
// ...

func (p *parser) simple_stmt(labelOk, rangeOk bool) *Node {
	// ...
	switch p.tok {
	// ...
	case LINCOP: // LINC, LDEC の代わりに LINCOP を処理
		p.next()
		stmt := Nod(OASOP, lhs, Nodintconst(1))
		stmt.Implicit = true
		stmt.Etype = EType(p.op) // lexerから渡された演算子タイプ (OADD or OSUB) を使用
		return stmt
	// ...
	}
}

func (p *parser) bexpr(prec OpPrec) *Node {
	// prec は、先行する/囲む二項演算子の優先順位（もしあれば）
	// なので、より高い優先順位のトークンのみを解析したい。

	x := p.uexpr()
	for p.prec > prec { // prectab を参照する代わりに p.prec を直接使用
		op, prec1 := p.op, p.prec
		p.next()
		x = Nod(op, x, p.bexpr(prec1))
	}
	return x
}

func (p *parser) expr() *Node {
	// ...
	return p.bexpr(0) // 以前は p.bexpr(1) だった
}
```
`parser.go`からは`prectab`が完全に削除されました。`simple_stmt`関数は`LINCOP`トークンを処理するように変更され、字句解析器から提供される`p.op`フィールドを利用して、`++`や`--`が`OADD`または`OSUB`のどちらであるかを判断します。最も重要な変更は`bexpr`関数で、演算子の優先順位を決定するために`prectab`を参照する代わりに、字句解析器によって既に設定されている`p.prec`フィールドを直接利用するようになりました。これにより、構文解析器は優先順位のルックアップを行う必要がなくなり、処理が効率化されます。`expr()`関数が`p.bexpr(0)`を呼び出すようになったのは、`OpPrec`の定義で最小の優先順位が`1`から始まるため、`0`を渡すことで最も低い優先順位から解析を開始するという意味合いになります。

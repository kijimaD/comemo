# [インデックス 24513] ファイルの概要

このコミットは、Goの`net/http`パッケージにおける`TestZeroLengthPostAndResponse`テストの不安定性（flakiness）を修正するものです。具体的には、HTTPリクエストのキャンセル処理とコネクションの再利用に関する競合状態（race condition）を解消し、テストが`errRequestCanceled`で失敗する問題を解決します。

## コミット

```
net/http: deflake TestZeroLengthPostAndResponse

It was failing with multiple goroutines a few out of every thousand
runs (with errRequestCanceled) because it was using the same
*http.Request for all 5 RoundTrips, but the RoundTrips' goroutines
(notably the readLoop method) were all still running, sharing that
same pointer. Because the response has no body (which is what
TestZeroLengthPostAndResponse tests), the readLoop was marking the
connection as reusable early (before the caller read until the body's
EOF), but the Transport code was clearing the Request's cancelation
func *AFTER* the caller had already received it from RoundTrip. This
let the test continue looping and do the next request with the same
pointer, fetch a connection, and then between getConn and roundTrip
have an invariant violated: the Request's cancelation func was nil,
tripping this check:

        if !pc.t.replaceReqCanceler(req.Request, pc.cancelRequest) {
                pc.t.putIdleConn(pc)
                return nil, errRequestCanceled
        }

The solution is to clear the request cancelation func in the readLoop
goroutine in the no-body case before it's returned to the caller.

This now passes reliably:

$ go test -race -run=TestZeroLengthPostAndResponse -count=3000

I think we've only seen this recently because we now randomize scheduling
of goroutines in race mode (https://golang.org/cl/11795). This race
has existed for a long time but the window was hard to hit.
```

## 変更の背景

このコミットは、Goの標準ライブラリ`net/http`パッケージ内の`TestZeroLengthPostAndResponse`というテストが、特定の条件下で`errRequestCanceled`エラーにより不安定に失敗する問題を解決するために導入されました。

問題の根本原因は、テストが同じ`*http.Request`ポインタを複数の`RoundTrip`呼び出しで再利用していたことにあります。`net/http`の`Transport`層は、HTTPコネクションの再利用を効率的に行うために、リクエストのキャンセル処理とコネクションのライフサイクルを管理しています。

具体的には、ボディを持たないレスポンス（`TestZeroLengthPostAndResponse`がテストするシナリオ）の場合、コネクションを管理する`persistConn`の`readLoop`ゴルーチンは、レスポンスボディの読み取りが不要なため、比較的早くコネクションを再利用可能としてマークします。しかし、この時点で`Transport`コードがリクエストのキャンセル関数をクリアする処理が、呼び出し元が`RoundTrip`からレスポンスを受け取った「後」に行われていました。

このタイミングのずれにより、以下の競合状態が発生しました。

1.  `readLoop`がコネクションを再利用可能とマークし、`rc.ch`チャネルを通じてレスポンスを呼び出し元に送信する。
2.  呼び出し元はレスポンスを受け取り、次のリクエストを同じ`*http.Request`ポインタで開始しようとする。
3.  `Transport`は、新しいリクエストのためにコネクションを取得し、`roundTrip`メソッド内でリクエストのキャンセル関数が設定されていることを期待するチェックを行う。
4.  しかし、前のリクエストの処理中に`Transport`がキャンセル関数をクリアする処理がまだ完了していないか、あるいは既にクリアされてしまっているため、`req.Request`のキャンセル関数が`nil`になっている場合がある。
5.  この`nil`チェックが失敗し、`errRequestCanceled`エラーが返され、テストが失敗する。

この競合状態は、特にGo 1.5で導入された`go test -race`モードでのゴルーチンのスケジューリングのランダム化（[https://golang.org/cl/11795](https://golang.org/cl/11795)）によって顕在化しました。それ以前から存在していた問題ですが、発生頻度が低かったため、発見が困難でした。

## 前提知識の解説

このコミットを理解するためには、以下のGoの`net/http`パッケージの内部動作に関する知識が必要です。

*   **`net/http`パッケージ**: Go言語でHTTPクライアントおよびサーバーを実装するための標準ライブラリです。
*   **`http.Client`**: HTTPリクエストを送信するための高レベルなインターフェースを提供します。内部的には`http.Transport`を利用します。
*   **`http.Transport`**: `http.Client`のバックエンドとして機能し、実際のHTTPリクエストの送信、コネクションプーリング、プロキシ設定、TLSハンドシェイクなどを担当します。複数のリクエスト間でTCPコネクションを再利用することでパフォーマンスを向上させます。
*   **`RoundTrip`メソッド**: `http.Transport`の主要なメソッドで、`*http.Request`を受け取り、`*http.Response`とエラーを返します。このメソッドがHTTPリクエストのライフサイクル全体を管理します。
*   **`persistConn`**: `http.Transport`が管理する、サーバーとの永続的なTCPコネクションを表す内部構造体です。コネクションの読み書き、アイドル状態の管理、リクエストの多重化（HTTP/2の場合）などを行います。
*   **`readLoop`ゴルーチン**: 各`persistConn`には、サーバーからのレスポンスを非同期に読み取るための専用のゴルーチン（`readLoop`）が存在します。このゴルーチンは、レスポンスヘッダの解析、ボディの読み取り、コネクションの状態管理などを行います。
*   **`http.Request.Cancel`**: Go 1.5で導入された機能で、`http.Request`にキャンセルチャネルを設定することで、進行中のHTTPリクエストを外部からキャンセルできるようにします。これにより、タイムアウトやユーザー操作によるリクエストの中止が可能になります。
*   **`errRequestCanceled`**: `http.Request.Cancel`によってリクエストがキャンセルされた際に、`RoundTrip`メソッドなどから返されるエラーです。
*   **競合状態 (Race Condition)**: 複数のゴルーチンが共有リソース（この場合は`*http.Request`のキャンセル関数や`persistConn`の状態）に同時にアクセスし、そのアクセス順序によってプログラムの動作が変わってしまうバグの一種です。`go test -race`フラグを使用することで、このような競合状態を検出できます。
*   **`replaceReqCanceler` / `setReqCanceler`**: `http.Transport`内部でリクエストのキャンセル関数を設定・解除するためのメソッドです。`replaceReqCanceler`は、既存のキャンセル関数を新しいものに置き換える際に、アトミックな操作で競合を避けるために使用されます。

## 技術的詳細

問題は、`net/http`の`Transport`がコネクションを再利用する際の、リクエストのキャンセル関数（`Request.Cancel`）のライフサイクル管理のタイミングにありました。

1.  **ボディなしレスポンスの特殊性**: `TestZeroLengthPostAndResponse`は、ボディを持たないHTTPレスポンスをテストします。このような場合、`persistConn`の`readLoop`ゴルーチンは、レスポンスヘッダを読み取った時点で、ボディの読み取りを待つことなく、すぐにコネクションをアイドル状態に戻し、再利用可能と判断します。
2.  **`rc.ch`への送信とキャンセル関数のクリア**: `readLoop`は、レスポンスが準備できたことを示すために`rc.ch`チャネルに値を送信します。このチャネルからの受信が、`RoundTrip`メソッドの呼び出し元にレスポンスが返されるトリガーとなります。しかし、元のコードでは、リクエストのキャンセル関数をクリアする`pc.t.setReqCanceler(rc.req, nil)`の呼び出しが、`rc.ch`への送信「後」に行われていました。
3.  **`*http.Request`の再利用**: `TestZeroLengthPostAndResponse`は、テストの効率化のために同じ`*http.Request`インスタンスを繰り返し使用していました。
4.  **競合の発生**:
    *   `readLoop`が`rc.ch`に送信し、呼び出し元がレスポンスを受け取る。
    *   呼び出し元はすぐに同じ`*http.Request`を使って次の`RoundTrip`を呼び出す。
    *   このとき、`Transport`は新しいリクエストのためにコネクションを取得し、`roundTrip`の開始時に`pc.t.replaceReqCanceler(req.Request, pc.cancelRequest)`を呼び出して、リクエストにキャンセル関数が設定されていることを確認しようとします。
    *   しかし、前のリクエストの`readLoop`ゴルーチンがまだ`pc.t.setReqCanceler(rc.req, nil)`を実行していないか、あるいは実行した直後で、`req.Request`のキャンセル関数が`nil`になっている可能性があります。
    *   `replaceReqCanceler`は、`req.Request`にキャンセル関数が設定されていない（`nil`である）場合、`false`を返します。これは、リクエストが既にキャンセルされたか、不正な状態であることを示唆します。
    *   この`false`の戻り値により、`Transport`は`errRequestCanceled`を返し、テストが失敗していました。

要するに、レスポンスが返され、同じリクエストオブジェクトが再利用されるまでの間に、リクエストのキャンセル関数が適切にクリアされていない、あるいはクリアされるタイミングが遅すぎたために、`Transport`がリクエストの状態に関する不変条件（invariant）が破られたと判断してエラーを返していたのです。

## コアとなるコードの解説

変更点は主に`persistConn.readLoop()`メソッド内にあります。

**追加されたコード:**

```go
		} else {
			// Before send on rc.ch, as client might re-use the
			// same *Request pointer, and we don't want to set this
			// on t from this persistConn while the Transport
			// potentially spins up a different persistConn for the
			// caller's subsequent request.
			pc.t.setReqCanceler(rc.req, nil)
		}
```

このコードブロックは、レスポンスボディがない場合（`if !rc.req.Body.hasData()`の`else`ブランチ）、`rc.ch`チャネルにレスポンスを送信する「前」に、リクエストのキャンセル関数を`nil`に設定する`pc.t.setReqCanceler(rc.req, nil)`を呼び出しています。

**削除されたコード:**

```go
		} else {
			pc.t.setReqCanceler(rc.req, nil) // before pc might return to idle pool
			alive = alive &&
				!pc.sawEOF &&
				pc.wroteRequest() &&
```

元のコードでは、`pc.t.setReqCanceler(rc.req, nil)`の呼び出しが、`rc.ch`への送信後、かつコネクションがアイドルプールに戻される可能性のあるタイミングで行われていました。

**変更の意図:**

この変更の核心は、リクエストのキャンセル関数をクリアするタイミングを早めることです。

*   **`rc.ch`への送信前**: `rc.ch`への送信は、`RoundTrip`の呼び出し元がレスポンスを受け取り、次の処理（同じ`*http.Request`での次のリクエスト発行など）を開始できる状態になったことを意味します。この時点で、前のリクエストに関連するキャンセル関数は完全にクリアされているべきです。
*   **`*http.Request`の再利用への対応**: クライアントが同じ`*http.Request`ポインタを再利用する可能性があるため、`readLoop`がレスポンスを返した直後に、そのリクエストオブジェクトがクリーンな状態であることを保証する必要があります。キャンセル関数を`nil`に設定することで、`Transport`が次にこのリクエストオブジェクトを処理する際に、古いキャンセル状態が残っていないことを保証し、`replaceReqCanceler`での不変条件チェックが失敗するのを防ぎます。

この修正により、ボディを持たないレスポンスの場合でも、リクエストのキャンセル関数が確実に、かつ適切なタイミングでクリアされるようになり、`TestZeroLengthPostAndResponse`で発生していた競合状態が解消されました。

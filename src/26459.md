## 元コミット内容

`net/url`: WindowsにおけるIPv6ゾーン識別子内のスペースを許可する。

Windows: Windows NT 3.1以来、本来あるべきではない場所にスペースを配置している。

Issue #14002 を修正。

## 変更の背景

このコミットは、Go言語の `net/url` パッケージがURLをパースする際に、Windows環境で生成されるIPv6アドレスのゾーン識別子（Zone IDまたはScope ID）に含まれるスペースを正しく処理できないという問題（Issue #14002）を解決するために行われました。

通常、URLのホスト部分、特にIPv6アドレスのゾーン識別子には、エスケープされていないスペースが含まれるべきではありません。URLの仕様（RFC 3986など）では、スペースは `%20` のようにパーセントエンコードされるべき文字とされています。しかし、Windowsオペレーティングシステムでは、ネットワークインターフェース名などにスペースが含まれる場合があり、それがIPv6アドレスのゾーン識別子として使用される際に、エスケープされていないスペースがそのまま含まれてしまうことがありました。

Goの `net/url` パッケージは、URLのホスト部分をパースする際に、エスケープされた文字がホスト名として不正な文字を導入していないかを検証します。この検証ロジックが厳密すぎたため、Windowsが生成する有効なIPv6アドレス（ゾーン識別子にスペースを含むもの）を不正なURLとして拒否してしまっていました。このコミットは、このWindows特有の挙動に対応し、互換性を確保することを目的としています。

## 前提知識の解説

### 1. URLの構造とホスト部分

URL (Uniform Resource Locator) は、インターネット上のリソースの位置を示すための文字列です。一般的なURLの構造は以下のようになります。

`scheme://[user:password@]host[:port][/path][?query][#fragment]`

このコミットで関連するのは `host` 部分です。`host` はドメイン名、IPv4アドレス、またはIPv6アドレスのいずれかを取ります。

### 2. IPv6アドレスとゾーン識別子 (Zone ID / Scope ID)

IPv6アドレスには、リンクローカルアドレスやサイトローカルアドレスのように、特定のネットワークインターフェースに限定されたスコープを持つものがあります。これらのアドレスは、どのインターフェースを使用するかを明示するために「ゾーン識別子」または「スコープID」を付加することができます。

IPv6アドレスのゾーン識別子は、アドレスの末尾に `%` を付けてインターフェース名を記述する形式が一般的です。例えば、`fe80::1%eth0` のようになります。ここで `eth0` がゾーン識別子です。Windowsでは、インターフェース名にスペースが含まれる場合があり、例えば `fe80::1%Ethernet%20Adapter` のようになることがあります（ただし、このコミットの文脈ではエスケープされていないスペースが問題となっています）。

URL内でIPv6アドレスを使用する場合、アドレス全体を `[]` で囲む必要があります。例: `http://[fe80::1%eth0]/`

### 3. URLエンコーディング (パーセントエンコーディング)

URLは、特定の文字（スペース、`#`、`?`、`/`など）が特別な意味を持つため、これらの文字をデータとして含める場合は、パーセントエンコーディング（`%`の後に文字のASCIIコードの16進数を続ける形式）でエスケープする必要があります。例えば、スペースは `%20` とエンコードされます。

URLのホスト部分では、通常、パーセントエンコードされた文字はデコードされてからホスト名として有効な文字であるか検証されます。ゾーン識別子もこのルールに従うのが一般的です。

### 4. Go言語の `net/url` パッケージ

`net/url` パッケージは、Go言語でURLのパース、生成、クエリパラメータの操作などを行うための標準ライブラリです。`url.Parse()` 関数は与えられた文字列をURL構造体に変換し、各コンポーネント（スキーム、ホスト、パスなど）を抽出します。このパース処理の中で、ホスト名の検証も行われます。

### 5. `shouldEscape` 関数と `encodeHost`

`net/url` パッケージ内部には、特定の文字がURLのどの部分でエスケープされるべきかを判断する `shouldEscape` のようなヘルパー関数が存在します。`encodeHost` は、ホスト部分のエンコーディングルールを示す定数またはフラグであり、ホスト名として許可される文字のセットを定義します。

このコミットの文脈では、`unescape` 関数内でパーセントエンコードされた文字をデコードした後、その文字が `encodeHost` のルールに照らしてホスト名として有効であるかを `shouldEscape` を用いてチェックしていました。もしデコードされた文字がホスト名として不正であれば、`EscapeError` を返してエラーとします。

## 技術的詳細

このコミットの核心は、`net/url` パッケージの `unescape` 関数内のロジック変更にあります。`unescape` 関数は、URL文字列中のパーセントエンコードされたシーケンス（例: `%20`）をデコードする役割を担っています。

特に、IPv6アドレスのゾーン識別子を処理する部分で、デコードされた文字がホスト名として有効であるかを検証するロジックがありました。元のコードでは、デコードされた文字 `v` が `shouldEscape(v, encodeHost)` の条件を満たす場合（つまり、ホスト名としてエスケープされるべき文字である場合）、`EscapeError` を発生させていました。これは、ゾーン識別子にエスケープされていない不正な文字が含まれていることを検出するための一般的なセキュリティおよび仕様準拠のチェックです。

しかし、Windows環境では、IPv6のゾーン識別子にエスケープされていないスペース（ASCII値 32）が含まれるURLが生成されることがありました。このスペースは、URLの一般的なルールでは `%20` とエンコードされるべきですが、Windowsの特定のAPIやシステム設定が、そのままのスペースを含む文字列をゾーン識別子として扱うことが原因と考えられます。

このコミットでは、このWindows特有の挙動に対応するため、`shouldEscape` のチェックに例外を追加しました。具体的には、デコードされた文字 `v` がスペース（`' '`）である場合は、`shouldEscape` の結果に関わらずエラーとしないように変更されました。

変更前:
`if s[i:i+3] != "%25" && shouldEscape(v, encodeHost) { ... }`

変更後:
`if s[i:i+3] != "%25" && v != ' ' && shouldEscape(v, encodeHost) { ... }`

この `v != ' '` という条件が追加されたことで、デコードされた文字がスペースであっても、それが `%25`（`%`文字自体をエスケープしたもの）ではない限り、`EscapeError` を発生させなくなりました。これにより、Windowsが生成するゾーン識別子にスペースが含まれるURLも、Goの `net/url` パッケージで正しくパースできるようになります。

コミットメッセージにある「Windows: putting spaces where they don't belong since Windows NT 3.1.」という記述は、このWindowsの歴史的な挙動に対する皮肉であり、Goがその互換性のために対応せざるを得ない状況を示しています。

## コアとなるコードの解説

### `src/net/url/url.go` の変更

`unescape` 関数内の以下の行が変更されました。

```go
-				if s[i:i+3] != "%25" && shouldEscape(v, encodeHost) {
+				if s[i:i+3] != "%25" && v != ' ' && shouldEscape(v, encodeHost) {
```

この変更は、パーセントエンコードされたシーケンス（例: `%20`）がデコードされた結果の文字 `v` が、ホスト名としてエスケープされるべき文字であるかどうかをチェックする条件式に、`v != ' '` という新たな条件を追加しています。

- `s[i:i+3] != "%25"`: これは、デコード対象が `%` 文字自体をエスケープした `%25` ではないことを確認しています。`%25` はゾーン識別子内で `%` 文字そのものとして扱われるため、特別扱いされます。
- `shouldEscape(v, encodeHost)`: デコードされた文字 `v` が、`encodeHost` のルール（ホスト名として許可される文字セット）に従ってエスケープされるべき文字であるかを判断します。通常、スペースはエスケープされるべき文字です。

新しい条件 `v != ' '` が追加されたことで、デコードされた文字 `v` がスペースである場合、たとえ `shouldEscape(v, encodeHost)` が `true` を返しても（つまり、スペースが通常はエスケープされるべき文字であっても）、この条件式全体は `false` となり、`EscapeError` は発生しなくなります。これにより、Windowsが生成する、ゾーン識別子にエスケープされていないスペースを含むIPv6アドレスが、GoのURLパーサーによって有効と見なされるようになります。

コメント `// But Windows puts spaces here! Yay.` は、この変更がWindowsの特定の挙動に対応するためのものであることを明確に示しています。

### `src/net/url/url_test.go` の変更

新しいテストケースが `urltests` スライスに追加されました。

```go
	// spaces in hosts are disallowed but escaped spaces in IPv6 scope IDs are grudgingly OK.
	// This happens on Windows.
	// golang.org/issue/14002
	{
		"tcp://[2020::2020:20:2020:2020%25Windows%20Loves%20Spaces]:2020",
		&URL{
			Scheme: "tcp",
			Host:   "[2020::2020:20:2020:2020%Windows Loves Spaces]:2020",
		},
		"",
	},
```

このテストケースは、まさにこのコミットが解決しようとしているシナリオを検証します。
- URL文字列: `"tcp://[2020::2020:20:2020:2020%25Windows%20Loves%20Spaces]:2020"`
  - ここで注目すべきは、ゾーン識別子部分 `"%25Windows%20Loves%20Spaces"` です。
  - `%25` は `%` 文字自体をエスケープしたものです。
  - `%20` はスペースをエスケープしたものです。
  - しかし、このテストケースの期待される `Host` フィールドは `"[2020::2020:20:2020:2020%Windows Loves Spaces]:2020"` となっており、ゾーン識別子内の `%20` がデコードされてスペース ` ` になっていることがわかります。これは、GoのURLパーサーがこの特定のケースでスペースを許容するように変更されたことを示しています。
- 期待される `URL` 構造体: `Scheme` が `tcp`、`Host` が `"[2020::2020:20:2020:2020%Windows Loves Spaces]:2020"` となっています。これは、ゾーン識別子内のスペースがデコードされた状態でホストとして認識されることを期待しています。
- 期待されるエラー: `""` (エラーなし)。

このテストケースの追加により、Windows環境で発生する特定のIPv6ゾーン識別子を含むURLが、Goの `net/url` パッケージで正しくパースされ、エラーなく処理されることが保証されます。

しかし、Windows環境では、IPv6のゾーン識別子にエスケープされていないスペース（ASCII値 32）が含まれるURLが生成されることがありました。このスペースは、URLの一般的なルールでは `%20` とエンコードされるべきですが、Windowsの特定のAPIやシステム設定が、そのままのスペースを含む文字列をゾーン識別子として扱うことが原因と考えられます。

このコミットでは、このWindows特有の挙動に対応するため、`shouldEscape` のチェックに例外を追加しました。具体的には、デコードされた文字 `v` がスペース（`' '`）である場合は、`shouldEscape` の結果に関わらずエラーとしないように変更されました。

変更前:
`if s[i:i+3] != "%25" && shouldEscape(v, encodeHost) { ... }`

変更後:
`if s[i:i+3] != "%25" && v != ' ' && shouldEscape(v, encodeHost) { ... }`

この `v != ' '` という条件が追加されたことで、デコードされた文字がスペースであっても、それが `%25`（`%`文字自体をエスケープしたもの）ではない限り、`EscapeError` を発生させなくなります。これにより、Windowsが生成するゾーン識別子にスペースが含まれるIPv6アドレスも、Goの `net/url` パッケージで正しくパースできるようになります。

コミットメッセージにある「Windows: putting spaces where they don't belong since Windows NT 3.1.」という記述は、このWindowsの歴史的な挙動に対する皮肉であり、Goがその互換性のために対応せざるを得ない状況を示しています。

## コアとなるコードの解説

### `src/net/url/url.go` の変更

`unescape` 関数内の以下の行が変更されました。

```go
-				if s[i:i+3] != "%25" && shouldEscape(v, encodeHost) {
+				if s[i:i+3] != "%25" && v != ' ' && shouldEscape(v, encodeHost) {
```

この変更は、パーセントエンコードされたシーケンス（例: `%20`）がデコードされた結果の文字 `v` が、ホスト名としてエスケープされるべき文字であるかどうかをチェックする条件式に、`v != ' '` という新たな条件を追加しています。

- `s[i:i+3] != "%25"`: これは、デコード対象が `%` 文字自体をエスケープした `%25` ではないことを確認しています。`%25` はゾーン識別子内で `%` 文字そのものとして扱われるため、特別扱いされます。
- `shouldEscape(v, encodeHost)`: デコードされた文字 `v` が、`encodeHost` のルール（ホスト名として許可される文字セット）に従ってエスケープされるべき文字であるかを判断します。通常、スペースはエスケープされるべき文字です。

新しい条件 `v != ' '` が追加されたことで、デコードされた文字 `v` がスペースである場合、たとえ `shouldEscape(v, encodeHost)` が `true` を返しても（つまり、スペースが通常はエスケープされるべき文字であっても）、この条件式全体は `false` となり、`EscapeError` は発生しなくなります。これにより、Windowsが生成する、ゾーン識別子にエスケープされていないスペースを含むIPv6アドレスが、GoのURLパーサーによって有効と見なされるようになります。

コメント `// But Windows puts spaces here! Yay.` は、この変更がWindowsの特定の挙動に対応するためのものであることを明確に示しています。

### `src/net/url/url_test.go` の変更

新しいテストケースが `urltests` スライスに追加されました。

```go
	// spaces in hosts are disallowed but escaped spaces in IPv6 scope IDs are grudgingly OK.
	// This happens on Windows.
	// golang.org/issue/14002
	{
		"tcp://[2020::2020:20:2020:2020%25Windows%20Loves%20Spaces]:2020",
		&URL{
			Scheme: "tcp",
			Host:   "[2020::2020:20:2020:2020%Windows Loves Spaces]:2020",
		},
		"",
	},
```

このテストケースは、まさにこのコミットが解決しようとしているシナリオを検証します。
- URL文字列: `"tcp://[2020::2020:20:2020:2020%25Windows%20Loves%20Spaces]:2020"`
  - ここで注目すべきは、ゾーン識別子部分 `"%25Windows%20Loves%20Spaces"` です。
  - `%25` は `%` 文字自体をエスケープしたものです。
  - `%20` はスペースをエスケープしたものです。
  - しかし、このテストケースの期待される `Host` フィールドは `"[2020::2020:20:2020:2020%Windows Loves Spaces]:2020"` となっており、ゾーン識別子内の `%20` がデコードされてスペース ` ` になっていることがわかります。これは、GoのURLパーサーがこの特定のケースでスペースを許容するように変更されたことを示しています。
- 期待される `URL` 構造体: `Scheme` が `tcp`、`Host` が `"[2020::2020:20:2020:2020%Windows Loves Spaces]:2020"` となっています。これは、ゾーン識別子内のスペースがデコードされた状態でホストとして認識されることを期待しています。
- 期待されるエラー: `""` (エラーなし)。

このテストケースの追加により、Windows環境で発生する特定のIPv6ゾーン識別子を含むURLが、Goの `net/url` パッケージで正しくパースされ、エラーなく処理されることが保証されます。

# [インデックス 20869] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）における型チェックの挙動を修正し、ポインタのポインタ（`**T`）型の変数から、ポインタレシーバを持つメソッド（`*T`）を呼び出すことを禁止する変更です。これは、Go言語の仕様に準拠するための修正であり、既存のコードが仕様に適合していなかった場合に影響を与える可能性があります。

## 変更の背景

この変更の背景には、Go言語のコンパイラ（`cmd/gc`）が、Go言語の仕様（Specification）に完全に準拠していなかったという問題があります。具体的には、ポインタのポインタ（`**T`）型の変数に対して、ポインタレシーバを持つメソッド（`func (t *T) Method()`）を呼び出すことが、仕様では許可されていないにもかかわらず、コンパイラが誤ってこれを許容していました。

この挙動は、Goの型システムとメソッドセットのルールに反しており、潜在的な混乱や予期せぬ動作を引き起こす可能性がありました。Rémy氏によってこの「壊れたコード」（仕様に適合しないコード）が発見されたことを受けて、コンパイラの挙動を仕様に合わせるための修正が実施されました。

`Fixes #6366`という記述から、この問題がGoのIssueトラッカーで報告されていたことがわかります。この修正は、Go言語の厳密な型チェックと仕様準拠を強化し、言語の健全性を保つための重要なステップです。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念を理解しておく必要があります。

### 1. Goのメソッドとレシーバ

Go言語では、関数を型に関連付けることでメソッドを定義します。メソッドは「レシーバ」と呼ばれる特別な引数を持ち、これによりそのメソッドがどの型の値に対して呼び出されるかを指定します。レシーバには2つの種類があります。

*   **値レシーバ (Value Receiver)**: `func (t T) MethodName()` のように定義されます。このメソッドは、`T`型の値、または`*T`型のポインタに対して呼び出すことができます。`*T`型のポインタに対して呼び出された場合、Goは自動的にポインタをデリファレンスして値を取得し、その値のコピーに対してメソッドを呼び出します。
*   **ポインタレシーバ (Pointer Receiver)**: `func (t *T) MethodName()` のように定義されます。このメソッドは、`*T`型のポインタ、または`T`型の値に対して呼び出すことができます。`T`型の値に対して呼び出された場合、Goは自動的にその値のアドレスを取得し、そのポインタに対してメソッドを呼び出します（アドレス可能である場合）。ポインタレシーバは、メソッド内でレシーバの値を変更したい場合や、レシーバが大きな構造体でコピーを避けたい場合に用いられます。

### 2. Goのメソッドセット

Go言語の仕様では、各型が持つメソッドの集合（メソッドセット）が厳密に定義されています。

*   型 `T` のメソッドセットは、レシーバが `T` であるすべてのメソッドを含みます。
*   型 `*T` のメソッドセットは、レシーバが `T` または `*T` であるすべてのメソッドを含みます。

このルールは、メソッド呼び出しの際にコンパイラがどのメソッドを選択するかを決定するために重要です。特に、ポインタのポインタ（`**T`）のような多重ポインタの場合、メソッドセットのルールがどのように適用されるかが問題となります。Goの仕様では、多重ポインタの自動デリファレンスは、メソッド呼び出しの文脈では限定的にしか行われません。

### 3. `cmd/gc` (Goコンパイラ)

`cmd/gc`は、Go言語の公式コンパイラです。Goのソースコードを機械語に変換する役割を担っており、その過程で型チェックや構文解析などの処理を行います。このコミットは、`cmd/gc`の型チェックロジックの一部を修正するものです。

### 4. `typecheck.c`

`src/cmd/gc/typecheck.c`は、Goコンパイラのソースコードの一部であり、型チェックのロジックが実装されています。このファイルは、Goのプログラムが型規則に準拠しているかを検証する中心的な役割を担っています。

## 技術的詳細

このコミットの技術的な核心は、`cmd/gc`がメソッド呼び出しのレシーバの型を解決する際のロジックの修正にあります。特に、多重ポインタのデリファレンスに関するGo言語の仕様の解釈と実装の乖離を修正しています。

Go言語の仕様では、メソッド呼び出しにおいて、レシーバがポインタ型である場合、コンパイラは自動的にそのポインタをデリファレンスして基底の型にアクセスしようとします。しかし、これは「ポインタのポインタ」のような多重ポインタに対しては、自動的に複数回デリファレンスされるわけではありません。

以前の`cmd/gc`の挙動では、`**T`型の変数`q`に対して、`*T`レシーバを持つメソッド`pm()`を呼び出す `q.pm()` のようなコードが、コンパイラによって許容されていました。これは、コンパイラが`q`を自動的に2回デリファレンスして`T`型の値に到達し、その上で`*T`レシーバのメソッドを呼び出そうとしていたためと考えられます。しかし、Goの仕様では、このような多重デリファレンスはメソッド呼び出しの文脈では許可されていません。

このコミットは、`typecheck.c`内の`lookdot`関数（ドット演算子によるフィールドアクセスやメソッド呼び出しを処理する部分）のロジックを修正し、この仕様不適合な挙動を排除しました。具体的には、レシーバの型がポインタのポインタであり、かつメソッドがポインタレシーバを持つ場合に、明示的なデリファレンス（例: `(*q).pm()`）を要求するように変更されました。これにより、コンパイラは仕様に厳密に準拠し、開発者に対してより明確な型エラーを報告するようになります。

## コアとなるコードの解説

`src/cmd/gc/typecheck.c` の `lookdot` 関数内の変更点に注目します。

1.  **変更前**:
    ```c
    } else if(tt->etype == tptr && tt->type->etype == tptr && eqtype(derefall(tt), rcvr)) {
    ```
    この条件は、「`tt`がポインタのポインタ型（`**T`）であり、かつ、`tt`を2回デリファレンスした型がレシーバの型`rcvr`と等しい場合」をチェックしていました。この時、コンパイラは暗黙的にデリファレンスを行っていました。

2.  **変更後**:
    ```c
    } else if(tt->etype == tptr && tt->type->etype == tptr && eqtype(derefall(tt), derefall(rcvr))) {
    ```
    この行の `eqtype(derefall(tt), rcvr)` が `eqtype(derefall(tt), derefall(rcvr))` に変更されています。これは、`rcvr`（メソッドのレシーバ型）もデリファレンスした上で比較を行うことを意味します。この変更自体は、比較の厳密性を高めるものですが、より重要なのはその後の`yyerror`と`while`ループ内の新しい条件です。

    そして、以下の新しい条件が追加されました。
    ```c
    					// Stop one level early for method with pointer receiver.
    					if(rcvr->etype == tptr && tt->type->etype != tptr)
    						break;
    ```
    この部分が、`**T`変数から`*T`レシーバメソッドを呼び出すことを禁止する核心です。
    *   `rcvr->etype == tptr`: メソッドのレシーバがポインタ型（例: `*T`）である。
    *   `tt->type->etype != tptr`: 現在処理している`tt`の基底型（つまり、`*T`の`T`の部分）がポインタ型ではない。

    この条件が真の場合、つまり「`**T`型の変数から`*T`レシーバのメソッドを呼び出そうとしている」状況で、`break`によってこれ以上の暗黙的なデリファレンスを停止させます。これにより、`n->left = nod(OIND, n->left, N);`（暗黙的なデリファレンスを行うコード）が実行されなくなり、結果として`yyerror`（エラーメッセージの出力）がトリガーされ、「`calling method %N with receiver %lN requires explicit dereference`」（メソッド%Nをレシーバ%lNで呼び出すには明示的なデリファレンスが必要です）というエラーが出力されるようになります。

`test/fixedbugs/bug371.go` の変更は、この新しい挙動を検証するためのものです。
以前は `q.pm()` （`q`は`**T`、`pm`は`*T`レシーバ）がコンパイルエラーにならなかったのに対し、この修正後は `// ERROR "requires explicit dereference"` が期待されるようになりました。これは、コンパイラがGoの仕様に厳密に準拠するようになったことを示しています。

# [インデックス 21630] ファイルの概要

このコミットは、Go言語のツールチェイン、特にアセンブラとリンカの内部表現に関する重要な変更を導入しています。`obj.Prog`構造体（アセンブリ命令を表す）が、その所属するアーキテクチャのコンテキスト（`Ctxt`フィールド）を常に持つように、`ctxt.NewProg`という新しいメソッドを導入し、`Prog`オブジェクトの生成方法を一元化しています。これにより、命令の出力や処理時に、どのアーキテクチャに属する命令であるかを正確に識別できるようになります。

`cmd/internal/obj`パッケージが`rsc.io/c2go`の`rev 40275b8`を使って再変換されました。

すべての`Prog`オブジェクトは、プリンタがどのアーキテクチャに属するかを判断できるように、`Ctxt`フィールドが設定されている必要があります。
このために、`ctxt.NewProg`を常に使用するように変更しました。

## 変更の背景

Go言語のコンパイラとアセンブラは、ソースコードを機械語に変換する過程で、中間表現として`obj.Prog`構造体を使用します。この`Prog`構造体は個々のアセンブリ命令を表します。Goはクロスプラットフォーム開発を強く意識しており、様々なCPUアーキテクチャ（ARM, x86, PPC64など）をサポートしています。

以前のシステムでは、`Prog`オブジェクトが生成される際に、そのオブジェクトがどのアーキテクチャのコンテキストに属するかの情報（`Ctxt`フィールド）が常に適切に設定されているわけではありませんでした。この情報の欠如は、特に命令をデバッグ目的で表示したり、異なるアーキテクチャ間で命令を処理したりする際に問題を引き起こす可能性がありました。例えば、命令のフォーマットや解釈はアーキテクチャに依存するため、`Ctxt`情報がないと正確な処理が困難になります。

このコミットの背景には、`Prog`オブジェクトの生成と初期化のプロセスを標準化し、堅牢性を高めるという目的があります。特に、`cmd/internal/obj`パッケージが`c2go`ツールによってC言語からGo言語に変換されたという記述は、初期のGoツールチェインの一部がC言語で書かれていた名残であり、Goらしいイディオムや設計パターンへの移行が進められていることを示唆しています。この移行の一環として、`Prog`オブジェクトの`Ctxt`フィールドの整合性を保証することが必要とされました。

*   **リンカ (Linker)**: コンパイルされたオブジェクトファイルやライブラリを結合し、実行可能なプログラムを生成するプログラムです。

## 技術的詳細

このコミットの主要な技術的変更は、`obj.Prog`オブジェクトの生成プロセスを`ctxt.NewProg()`メソッドに一元化することです。

1.  **`ctxt.NewProg()`の導入**:
    `src/cmd/internal/obj/util.go`に、`Link`構造体（リンカコンテキスト）の新しいメソッド`NewProg()`が追加されました。
    ```go
    func (ctxt *Link) NewProg() *Prog {
        p := ctxt.Arch.Prg() // should be the only call to this; all others should use ctxt.NewProg
        p.Ctxt = ctxt
        return p
    }
    ```
    このメソッドは、まず`ctxt.Arch.Prg()`を呼び出して新しい`Prog`オブジェクトを取得します。そして、**取得した`Prog`オブジェクトの`Ctxt`フィールドに、現在の`Link`コンテキスト（`ctxt`自身）を明示的に設定します**。これにより、`NewProg()`を通じて生成されるすべての`Prog`オブジェクトは、常にその生成元のコンテキストへの参照を持つことが保証されます。コメントにある「`should be the only call to this; all others should use ctxt.NewProg`」は、この`NewProg`が`Prog`生成の唯一の正規ルートとなるべきであることを強く示唆しています。

2.  **既存の`Prog`生成箇所の置き換え**:
    Goツールチェイン内の様々なファイル（特に`src/cmd/internal/obj`以下のアーキテクチャ固有のディレクトリや`src/cmd/new9a`）で、`Prog`オブジェクトを直接生成していた箇所（例: `ctxt.Arch.Prg()`の直接呼び出し）が、新しく導入された`ctxt.NewProg()`の呼び出しに置き換えられました。これにより、`Prog`オブジェクトの生成ロジックがカプセル化され、`Ctxt`フィールドの自動設定が保証されます。

3.  **`prg()`関数の簡素化**:
    `src/cmd/internal/obj/arm/obj5.go`、`src/cmd/internal/obj/i386/obj8.go`、`src/cmd/internal/obj/ppc64/obj9.go`、`src/cmd/internal/obj/x86/obj6.go`といったアーキテクチャ固有のファイルにあった`prg()`関数が簡素化されました。
    **変更前**:
    ```go
    func prg() *obj.Prog {
        var p *obj.Prog
        p = new(obj.Prog)
        *p = zprg // or zprg5
        return p
    }
    ```
    **変更後**:
    ```go
    func prg() *obj.Prog {
        p := zprg
        return &p
    }
    ```
    この変更は、`prg()`がもはや`Prog`オブジェクトの完全な初期化（特に`Ctxt`フィールドの設定）を担当しないことを反映しています。`prg()`は単にゼロ値の`Prog`構造体（`zprg`はゼロ値の`obj.Prog`）を返す役割に特化し、`Ctxt`フィールドの設定は`ctxt.NewProg()`に委譲されるようになりました。

4.  **`Addr.Node`フィールドの型変更**:
    `src/cmd/internal/obj/link.go`において、`Addr`構造体の`Node`フィールドの型が`*struct{}`から`interface{}`に変更されました。
    ```diff
    --- a/src/cmd/internal/obj/link.go
    +++ b/src/cmd/internal/obj/link.go
    @@ -49,7 +49,7 @@ type Addr struct {
     	Class   int8
     	Etype   uint8
     	Offset2 int32
    -	Node    *struct{}
    +	Node    interface{}
     	Width   int64
     }
    ```
    この変更は、`Prog`オブジェクトの生成とは直接関係ありませんが、同じコミットに含まれていることから、Goツールチェインの内部データ構造の柔軟性を高めるための一般的なリファクタリングの一環と考えられます。`interface{}`にすることで、`Node`フィールドは任意の型の値を保持できるようになり、将来的な拡張性や異なる種類のメタデータをアドレスに関連付けることが可能になります。

これらの変更により、Goツールチェインの内部で`Prog`オブジェクトがより堅牢かつ一貫した方法で管理されるようになり、特にクロスアーキテクチャのサポートやデバッグ情報の正確性が向上します。

## コアとなるコードの解説

このコミットの最も重要なコード変更は、`src/cmd/internal/obj/util.go`に追加された`NewProg`メソッドです。

```go
// src/cmd/internal/obj/util.go
func (ctxt *Link) NewProg() *Prog {
	p := ctxt.Arch.Prg() // should be the only call to this; all others should use ctxt.NewProg
	p.Ctxt = ctxt
	return p
}
```

この関数は、`obj.Link`型のレシーバ`ctxt`を持つメソッドとして定義されています。
1.  `p := ctxt.Arch.Prg()`: まず、既存の`ctxt.Arch.Prg()`を呼び出して、新しい`Prog`オブジェクトのインスタンスを取得します。この`Prg()`メソッドは、特定のアーキテクチャ（`ctxt.Arch`）に適したゼロ値の`Prog`構造体を返します。
2.  `p.Ctxt = ctxt`: ここがこの変更の核心です。取得した`Prog`オブジェクト`p`の`Ctxt`フィールドに、このメソッドが呼び出された際の`Link`コンテキストである`ctxt`自身を代入しています。これにより、生成されたすべての`Prog`オブジェクトが、どのリンカコンテキスト（ひいてはどのアーキテクチャ）に属するかの情報を内部に保持するようになります。
3.  `return p`: 初期化され、`Ctxt`フィールドが設定された`Prog`オブジェクトを返します。

この`NewProg`メソッドが導入されたことで、Goツールチェイン内の他のすべての`Prog`オブジェクト生成箇所は、直接`ctxt.Arch.Prg()`を呼び出す代わりに、この`ctxt.NewProg()`を呼び出すように変更されました。これにより、`Prog`オブジェクトの生成と`Ctxt`フィールドの設定が強制され、一貫性が保たれるようになりました。

例えば、`src/cmd/internal/obj/arm/asm5.go`のようなファイルでは、以前は以下のようなコードがありました。

```go
// 変更前 (例)
q = ctxt.Arch.Prg()
```

これが、このコミットによって以下のように変更されました。

```go
// 変更後 (例)
q = ctxt.NewProg()
```

この変更は、見た目は小さいですが、Goツールチェインの内部的な堅牢性と正確性を大幅に向上させるものです。特に、異なるアーキテクチャを扱う際に、命令がどのコンテキストに属するかを明確にすることで、バグの発生を防ぎ、コードの可読性と保守性を高めます。

## 元コミット内容

`cmd/internal/obj/ppc64: fix assembly of SRADCC with immediate`

`sradi` および `sradi.` 命令は、その即値引数の最上位ビットを他の部分とは別に隠してエンコードしますが、既存のコードは `sradi` のケースしか処理していませんでした。

これが唯一欠けている命令だと確信しています（いくつかのローテート命令も同様の方法で即値をエンコードしますが、それらの処理は問題ないようです）。

この修正は、バグとして報告された "GOARCH=amd64 ~/go/bin/go install -v runtime" の失敗を修正します。

`Fixes #11987`

## 変更の背景

このコミットは、Go言語のPPC64アーキテクチャ向けアセンブラにおける特定のバグを修正するために行われました。PPC64アーキテクチャのシフト命令、特に`SRAD` (Shift Right Algebraic Doubleword) や `SRADCC` (Shift Right Algebraic Doubleword and Record Condition Code) は、シフト量を指定するための即値（immediate value）を命令コード内にエンコードします。この即値のエンコーディングには特殊なルールがあり、特にシフト量が32以上の場合、その最上位ビット（5ビット目、0-indexed）が命令内の別のフィールドに格納されることがあります。

既存のアセンブラコードは、`SRAD`命令についてはこの特殊なエンコーディングルールを正しく適用していましたが、`SRADCC`命令については見落としていました。このため、`SRADCC`命令でシフト量が32以上の即値を使用した場合、アセンブラが生成する機械語コードが誤ったシフト量を表現してしまい、結果としてプログラムの動作が不正になるという問題が発生していました。

このバグは、`GOARCH=amd64`環境でGoランタイムをビルドする際に、PPC64向けのコードが処理される過程で顕在化しました。これは、クロスコンパイル環境や、Goランタイムが複数のアーキテクチャ固有のコードを内包している場合に発生しうる状況です。`issue #11987`として報告され、その修正がこのコミットの目的です。

## 前提知識の解説

1.  **PPC64アーキテクチャ**: IBMが開発したPowerPCプロセッサの64ビット版アーキテクチャです。Go言語は、このアーキテクチャを含む多くのプラットフォームをサポートしています。
2.  **アセンブラ (Assembler)**: 人間が記述したアセンブリ言語（ニーモニックコード）を、CPUが直接実行できる機械語コードに変換するプログラムです。Go言語のツールチェーンには、各アーキテクチャ向けのアセンブラが含まれています。
3.  **即値 (Immediate Value)**: 命令の一部として直接エンコードされる定数値のことです。シフト命令の場合、シフト量が即値として指定されることがよくあります。
4.  **シフト命令**: レジスタ内のビットパターンを左右に移動させる命令です。
    *   **SRAD (Shift Right Algebraic Doubleword)**: 符号付き整数を右シフトする命令です。最上位ビット（符号ビット）を保持しながら右にシフトします。`Doubleword`は64ビットを意味します。
    *   **SRADCC (Shift Right Algebraic Doubleword and Record Condition Code)**: `SRAD`と同様に符号付き整数を右シフトしますが、さらにシフト結果に基づいて条件コードレジスタ（CR）を更新します。条件コードは、その後の条件分岐命令などで利用されます。
5.  **即値のエンコーディング**: CPUの命令セットアーキテクチャ（ISA）によっては、即値が命令コード内の複数のフィールドに分割されてエンコードされることがあります。特に、広い範囲の即値を表現するために、一部のビットが特殊な方法で扱われることがあります。PPC64のシフト命令では、シフト量の5ビット目（値32を表すビット）が他の下位5ビットとは異なるフィールドにエンコードされるのが一般的です。これにより、0から63までのシフト量を表現できます。
6.  **Goのツールチェーン**: `go build`や`go install`などのコマンドは、ソースコードをコンパイルし、必要に応じてアセンブリコードを機械語に変換します。この過程で、`cmd/internal/obj/ppc64`のような内部パッケージがPPC64向けのアセンブリ処理を担当します。

## 技術的詳細

PPC64アーキテクチャの`SRAD`および`SRADCC`命令では、シフト量（SH）が6ビットで表現されます（0-63）。この6ビットは、命令フォーマット内で以下のように分割されてエンコードされることが一般的です。

*   **SH[0:4]**: シフト量の下位5ビット（0-31）は、命令内の特定のフィールドに直接格納されます。
*   **SH[5]**: シフト量の最上位ビット（32を表すビット）は、命令内の別のフィールド（例えば、`mb`フィールドの一部や専用のビット）に格納されます。このビットがセットされている場合、実際のシフト量は下位5ビットの値に32を加えたものになります。

このコミット以前のGoアセンブラの`src/cmd/internal/obj/ppc64/asm9.go`ファイル内の`asmout`関数では、`SRAD`命令に対しては、このSH[5]ビットの特殊なエンコーディングを正しく処理していました。具体的には、即値`v`の5ビット目（`v&0x20`）がセットされている場合に、命令コード`o1`の特定のビット（`1 << 1`、コメントでは`mb[5]`と示唆されている）を立てる処理が行われていました。

しかし、`SRADCC`命令については、この同じロジックが適用されていませんでした。そのため、例えば`v>>32`のような操作（シフト量が32）を`SRADCC`命令でアセンブルしようとすると、SH[5]ビットが正しくエンコードされず、結果としてシフト量が0や他の誤った値として解釈されてしまう可能性がありました。

この修正は、`SRADCC`命令も`SRAD`命令と同様に、即値の5ビット目がセットされている場合に命令コードの対応するビットを立てるように変更することで、この問題を解決しています。これにより、`SRADCC`命令が正しいシフト量でアセンブルされるようになります。

```go
// Issue 11987. The ppc64 SRADCC instruction was misassembled in a way
// lost bit 5 of the immediate so v>>32 was assembled as v>>0.  SRADCC

	}
}
```

## コアとなるコードの解説

`src/cmd/internal/obj/ppc64/asm9.go`の変更点に注目します。

`asmout`関数は、Goのアセンブラが個々のアセンブリ命令（`obj.Prog`）を受け取り、それに対応する機械語コード（`out []uint32`）を生成する主要な部分です。

1.  `o1 = AOP_RRR(uint32(opirr(ctxt, int(p.As))), uint32(r), uint32(p.To.Reg), uint32(v)&31)`
    *   この行は、命令の基本的なオペコード`o1`を構築しています。
    *   `p.As`は現在処理しているアセンブリ命令の種類（例: `ASRAD`, `ASRADCC`）を示します。
    *   `v`は即値（この場合はシフト量）です。
    *   `uint32(v)&31`は、即値`v`の下位5ビットのみを取り出しています。これは、シフト量の0から31までの部分を命令の標準的なフィールドにエンコードするためです。

2.  `- if p.As == ASRAD && (v&0x20 != 0) {`
    *   修正前のコードでは、この条件は`ASRAD`命令にのみ適用されていました。
    *   `v&0x20 != 0`は、即値`v`の5ビット目（`0x20`は2進数で`100000`、つまり32を表すビット）がセットされているかどうかをチェックしています。

3.  `+ if (p.As == ASRAD || p.As == ASRADCC) && (v&0x20 != 0) {`
    *   修正後のコードでは、条件が`ASRAD`または`ASRADCC`命令のいずれかに拡張されました。
    *   これにより、`SRADCC`命令でも、即値の5ビット目がセットされている場合に次の行の処理が実行されるようになります。

4.  `o1 |= 1 << 1 /* mb[5] */`
    *   この行は、`o1`（命令オペコード）の特定のビットをセットしています。
    *   `1 << 1`は2進数で`00000010`であり、これはオペコードの2番目のビット（0-indexed）をセットすることを意味します。
    *   コメント`/* mb[5] */`は、このビットがPPC64命令フォーマットにおける`mb`フィールドの5ビット目（またはそれに相当する、シフト量の最上位ビットを制御するフィールド）に対応することを示唆しています。このビットをセットすることで、アセンブラはシフト量が32以上であることを正しく命令にエンコードします。

この変更により、`SRADCC`命令でシフト量が32以上の即値が使用された場合でも、アセンブラは正しい機械語コードを生成し、`v>>32`のような操作が期待通りに`0`を返すようになります。

追加されたテストケース`test/fixedbugs/issue11987.go`は、`int64`型の変数`v`に`0x80000000`（2^31）を設定し、`v>>32 == 0`という条件を評価しています。PPC64の64ビット環境では、`0x80000000`を32ビット右シフトすると、符号拡張により`0`になることが期待されます。もしバグが修正されていなければ、シフト量が誤ってエンコードされ、`v>>0`のように振る舞い、結果が`0x80000000`のままとなり、テストが失敗するでしょう。このテストが成功することで、修正が正しく機能していることが確認されます。

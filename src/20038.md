# [インデックス 20038] ファイルの概要

このコミットは、Go言語のビルドシステムにおけるアセンブリコードの取り扱いを改善するものです。具体的には、アセンブリファイル内で使用される`textflag.h`ヘッダーファイルの参照方法を変更し、そのアクセス性を向上させています。これにより、Goリポジトリ外でのアセンブリコードの利用が容易になり、ビルドプロセスの柔軟性が増します。

## 変更の背景

このコミットの主な背景は、Go言語のアセンブリコードが利用する`textflag.h`というヘッダーファイルのアクセス性の問題にありました。

元々、`textflag.h`はGoリンカーのコマンドディレクトリ（`cmd/ld`）内に配置されていました。この配置は、Goの標準リポジトリ内でビルドを行う際には問題ありませんでしたが、Goリポジトリの外部で独自のアセンブリコードを記述し、それをGoのビルドシステムと連携させようとする場合に、このファイルへのアクセスが困難になるという課題がありました。

アセンブリコードは、`NOSPLIT`のような特殊なシンボルを定義するために`textflag.h`を参照します。しかし、`cmd/ld`という内部的なディレクトリに隠蔽されているため、外部のプロジェクトがこのヘッダーを直接インクルードするには、相対パスを深く辿る必要があり、これは保守性や可読性の観点から望ましくありませんでした。

この問題を解決し、Goのアセンブリコードの利用をより柔軟にするために、`textflag.h`をより一般的な場所へ移動し、アセンブラが容易に参照できるようにする変更が必要とされました。

## 前提知識の解説

このコミットの理解を深めるために、以下のGo言語およびシステムプログラミングに関する前提知識を解説します。

### 1. Go言語のアセンブリコード (`.s`ファイル)

Go言語は、パフォーマンスが要求される低レベルな処理や、特定のハードウェア機能を利用するために、Goアセンブリ言語で記述されたコード（`.s`ファイル）をサポートしています。これは、C言語におけるインラインアセンブリやアセンブリファイルに似ています。Goのアセンブリは、一般的なアセンブリ言語とは異なる独自の構文（Plan 9アセンブラの派生）を持っています。

*   **使用目的**:
    *   **パフォーマンス最適化**: 特定のアルゴリズムやデータ処理において、Goのコンパイラが生成するコードよりも高速な実行が必要な場合。
    *   **システムコール**: OSの低レベルな機能に直接アクセスする場合。
    *   **ランタイムのコア部分**: ゴルーチン管理、スケジューリング、ガベージコレクションなど、Goランタイムの根幹をなす部分の一部はアセンブリで記述されています。
    *   **ハードウェア固有の機能**: SIMD命令（SSE, AVXなど）や暗号化支援命令（AES-NIなど）といった、特定のCPUが提供する特殊な命令セットを利用する場合。

*   **`TEXT`ディレクティブ**: Goアセンブリでは、関数を定義するために`TEXT`ディレクティブを使用します。例えば、`TEXT ·MyFunc(SB),NOSPLIT,$0`のように記述します。

### 2. `textflag.h`と`NOSPLIT`

`textflag.h`は、Goのビルドシステムがアセンブリコードに対して提供するヘッダーファイルです。このファイルには、アセンブリ関数やデータセクションの振る舞いを制御するためのフラグが定義されています。

*   **`NOSPLIT`フラグ**: `textflag.h`で定義される最も重要なフラグの一つが`NOSPLIT`です。このフラグは、アセンブリ関数に適用されます。
    *   **スタック分割 (Stack Splitting)**: Goのゴルーチンは、必要に応じてスタックサイズを動的に増減させる「スタック分割」というメカニズムを持っています。関数が呼び出される際、通常はスタックオーバーフローチェックが行われ、スタック領域が不足していれば、より大きなスタックが割り当てられ、既存のスタック内容が新しい場所にコピーされます。
    *   **`NOSPLIT`の役割**: `NOSPLIT`フラグが付けられた関数は、このスタックオーバーフローチェックをスキップします。これは、主に以下のような非常に特殊な低レベルのランタイムコードで使用されます。
        *   **パフォーマンスの極限追求**: スタックチェックのオーバーヘッドを完全に排除したい場合。
        *   **スタック管理の一部**: Goランタイムのスタック管理自体を行う関数など、スタックチェックを行うとデッドロックや無限ループに陥る可能性がある場合。
        *   **プリエンプションの回避**: 特定の処理中にゴルーチンのプリエンプション（実行中断）が安全でない、または望ましくない場合。
    *   **危険性**: `NOSPLIT`の使用は非常に危険です。もし`NOSPLIT`関数、またはそれが呼び出す関数が利用可能なスタック領域を超過した場合、ランタイムがスタックの拡張を行わないため、スタックオーバーフローが発生し、メモリ破壊やプログラムクラッシュを引き起こす可能性があります。そのため、このフラグは細心の注意を払って、スタック使用量が厳密に制御されている関数にのみ適用されます。

### 3. Goのビルドシステムとツールチェーン

Goのビルドシステムは、ソースコードをコンパイルし、リンクして実行可能ファイルを生成する一連のツール（ツールチェーン）で構成されています。

*   **`go tool asm`**: Goのアセンブリファイルをコンパイルするアセンブラです。`.s`ファイルをオブジェクトファイル（`.o`）に変換します。
*   **`go tool link` (または `cmd/ld`)**: Goのリンカーです。コンパイルされたオブジェクトファイルやライブラリを結合し、最終的な実行可能ファイルを生成します。`textflag.h`は元々このリンカーのコマンドディレクトリにありました。
*   **`go build`コマンド**: ユーザーが通常利用するGoのビルドコマンドです。内部的に上記のツールチェーンを呼び出し、ビルドプロセス全体を管理します。
*   **`pkg/GOOS_GOARCH`ディレクトリ**: Goのパッケージは、コンパイルされると通常、`$GOROOT/pkg/GOOS_GOARCH`のようなディレクトリに配置されます。ここで`GOOS`はオペレーティングシステム（例: `linux`, `windows`）、`GOARCH`はアーキテクチャ（例: `amd64`, `arm`）を示します。このディレクトリは、特定のOSとアーキテクチャ向けのコンパイル済みパッケージや、ビルドに必要なヘッダーファイルなどを格納するために使用されます。
*   **`cgo`**: GoコードからC言語のコードを呼び出すためのメカニズムです。`cgo`を使用する際にも、Cのヘッダーファイルが特定の場所にコピーされることがあります。今回の変更は、`cgo`で同様の解決策が取られていることを参考にしています。

### 4. `#include`ディレクティブ

C言語やアセンブリ言語において、`#include`ディレクティブは、別のファイルのコンテンツを現在のファイルに挿入するために使用されます。これは、共通の定義（マクロ、定数、関数プロトタイプなど）を複数のファイルで共有する際に便利です。アセンブリファイルでも、Cプリプロセッサが実行されるため、`#include`を使用できます。

## 技術的詳細

このコミットは、`textflag.h`の配置と参照メカニズムを根本的に変更することで、Goのアセンブリコードのビルドプロセスを改善しています。

1.  **`textflag.h`のコピー**:
    *   これまで`src/cmd/ld/textflag.h`に存在していた`textflag.h`が、ビルドプロセス中に各プラットフォーム固有のパッケージディレクトリ（`$GOROOT/pkg/GOOS_GOARCH/textflag.h`）にコピーされるようになりました。
    *   このコピー処理は、Goのビルドスクリプトである`src/cmd/dist/build.c`に追記されています。これにより、`runtime`パッケージのビルド時と同様に、`textflag.h`も適切な場所に配置されるようになります。

2.  **アセンブラのインクルードパスの変更**:
    *   Goのアセンブラ（`go tool asm`）が、`pkg/GOOS_GOARCH`ディレクトリをデフォルトのインクルードパス（`-I`オプション）として認識するようになりました。
    *   この変更は、`src/cmd/go/build.go`（`go`コマンドのビルドロジック）内で行われています。これにより、アセンブラは`textflag.h`を相対パスで指定することなく、直接ファイル名で参照できるようになります。

3.  **アセンブリファイルの参照パスの更新**:
    *   Goリポジトリ内の全てのアセンブリファイル（`.s`ファイル）において、`#include`ディレクティブのパスが変更されました。
    *   変更前: `#include "../../../cmd/ld/textflag.h"` のような、`cmd/ld`への相対パス。
    *   変更後: `#include "textflag.h"` のような、ファイル名のみの直接参照。
    *   この変更は、`runtime`パッケージ内のアセンブリファイルを除く、Goリポジトリ内の全てのアセンブリファイルに適用されました。`runtime`パッケージはGoのブートシーケンスの非常に早い段階でビルドされるため、その時点ではまだ`textflag.h`が`pkg/GOOS_GOARCH`にコピーされていない可能性があるため、例外とされています。

4.  **ドキュメントの更新**:
    *   アセンブリに関するドキュメント（`doc/asm.html`）も更新され、`textflag.h`が「標準の`#include`ファイル」として参照されるようになったことが明記されました。

これらの変更により、Goのアセンブリコードは、`textflag.h`をより標準的かつ簡潔な方法でインクルードできるようになり、Goリポジトリ外でアセンブリコードを開発する際の障壁が低減されました。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

1.  **`doc/asm.html`**:
    *   アセンブリに関する公式ドキュメントの記述が更新され、`textflag.h`の参照方法が変更されたことを反映しています。
    *   `-Their values, defined in the file <code>src/cmd/ld/textflag.h</code>, are:`
    *   `+Their values, defined in the standard <code>#include</code>  file <code>textflag.h</code>, are:`

2.  **`src/cmd/dist/build.c`**:
    *   Goのビルドシステムの中核をなすC言語のスクリプトです。このファイルに、`textflag.h`を`pkg/GOOS_GOARCH`ディレクトリにコピーするロジックが追加されました。
    *   `if(streq(dir, "pkg/runtime")) { ... copy(..., "src/cmd/ld/textflag.h", ...); }` のような行が追加され、`runtime`パッケージのビルド時に`textflag.h`もコピーされるようになります。

3.  **`src/cmd/go/build.go`**:
    *   `go`コマンドのビルド処理を定義するGo言語のファイルです。アセンブラ（`go tool asm`）を呼び出す際に、新しいインクルードパス（`pkg/GOOS_GOARCH`）を追加する変更が行われました。
    *   `func (gcToolchain) asm(...)` 関数内で、アセンブラの引数に `-I` オプションと `filepath.Join(goroot, "pkg", fmt.Sprintf("%s_%s", goos, goarch))` で生成されるパスが追加されています。

4.  **多数の`.s`ファイル**:
    *   `src/cmd/link/testdata/autosection.s`
    *   `src/pkg/crypto/aes/asm_amd64.s`
    *   `src/pkg/math/abs_386.s`
    *   ...など、Goリポジトリ内のほぼ全てのアセンブリファイルにおいて、`#include`ディレクティブのパスが、相対パスから直接ファイル名（`#include "textflag.h"`）に変更されました。

## コアとなるコードの解説

### `src/cmd/dist/build.c` の変更

このファイルは、GoのソースコードからGoのツールチェーン自体をビルドする際に使用される、低レベルなビルドスクリプトです。変更点では、`install`関数内で`pkg/runtime`ディレクトリが処理される際に、`cgocall.h`や`runtime.h`といったCgo関連のヘッダーファイルと同様に、`textflag.h`も`$GOROOT/pkg/GOOS_GOARCH`ディレクトリにコピーされるように指示しています。これにより、`textflag.h`がGoのビルド環境全体で利用可能な状態になります。

### `src/cmd/go/build.go` の変更

このファイルは、`go build`コマンドがどのように動作するかを定義しています。特に重要なのは、`asm`メソッド（アセンブリファイルをコンパイルする部分）の変更です。
変更前は、アセンブラは特定のインクルードパスしか持っていませんでした。変更後は、`inc := filepath.Join(goroot, "pkg", fmt.Sprintf("%s_%s", goos, goarch))`という行で、現在のOSとアーキテクチャに対応する`pkg`ディレクトリのパスを構築し、これをアセンブラの`-I`（インクルードパス）引数に追加しています。
これにより、アセンブラは`#include "textflag.h"`という記述を見たときに、この新しく追加されたパスを検索し、コピーされた`textflag.h`を見つけることができるようになります。

### `.s`ファイルの変更

Goリポジトリ内の多くのアセンブリファイルでは、これまで`#include "../../../cmd/ld/textflag.h"`のように、`textflag.h`への非常に長い相対パスを使用していました。これは、ファイルがどこに配置されているかに依存するため、パスが変更されたり、リポジトリ外で利用しようとすると問題が発生しやすい構造でした。
今回の変更により、これらのパスが全て`#include "textflag.h"`という簡潔な形式に置き換えられました。これは、`src/cmd/go/build.go`の変更によってアセンブラが適切なインクルードパスを持つようになったため、可能になりました。これにより、アセンブリコードの可読性と移植性が向上しています。

### `doc/asm.html` の変更

このドキュメントの更新は、ユーザーや開発者に対して、`textflag.h`がもはや特定の内部ディレクトリに隠されたファイルではなく、Goのアセンブリコードで標準的にインクルードできるファイルになったことを明確に伝えます。これは、Goのアセンブリプログラミングにおけるベストプラクティスの変更を反映しています。

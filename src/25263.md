# [インデックス 25263] ファイルの概要

このコミットは、Go言語の`os/signal`パッケージが`runtime`パッケージの非公開関数にアクセスする方法を変更するものです。具体的には、これまで使用されていたアセンブリスタブを廃止し、`//go:linkname`ディレクティブを用いて直接リンクするように修正されています。これにより、特に`ppc64le`アーキテクチャにおける共有ライブラリの問題を解決しつつ、よりクリーンで移植性の高い内部連携メカニズムを実現しています。

## 元コミット内容

```
runtime, os/signal: use //go:linkname instead of assembly stubs to get access to runtime functions
    
os/signal depends on a few unexported runtime functions. This removes the
assembly stubs it used to get access to these in favour of using
//go:linkname in runtime to make the functions accessible to os/signal.

This is motivated by ppc64le shared libraries, where you cannot BR to a symbol
defined in a shared library (only BL), but it seems like an improvment anyway.
```

## 変更の背景

この変更の主な動機は、`ppc64le`アーキテクチャにおける共有ライブラリの制約にありました。`ppc64le`環境で共有ライブラリを使用する場合、`BR`（Branch Register）命令を使って共有ライブラリ内で定義されたシンボルに直接分岐することができません。代わりに`BL`（Branch Link）命令を使用する必要があります。

Goの`os/signal`パッケージは、シグナルハンドリングのために`runtime`パッケージ内のいくつかの非公開（unexported）関数に依存していました。これらの非公開関数にアクセスするために、Goのビルドシステムはこれまでアセンブリ言語で書かれた「スタブ」を使用していました。このスタブは、`os/signal`パッケージ内で定義された関数名から、`runtime`パッケージ内の対応する非公開関数へ`JMP`（ジャンプ）するだけの非常にシンプルなものでした。

しかし、`ppc64le`の共有ライブラリの制約により、このアセンブリスタブによる`JMP`（特に`BR`命令を使用するケース）が問題となりました。この問題を解決し、かつより汎用的な解決策として、Goコンパイラが提供する`//go:linkname`ディレクティブを使用する方法が採用されました。これにより、アセンブリスタブの必要性がなくなり、コードの複雑性が軽減され、移植性が向上しました。コミットメッセージにもあるように、これは`ppc64le`の問題解決だけでなく、全体的な改善と見なされています。

## 前提知識の解説

### Goのパッケージとエクスポート/アンエクスポート

Go言語では、識別子（変数、関数、型など）の可視性は、その名前の先頭文字が大文字か小文字かによって決まります。
*   **エクスポートされた識別子 (Exported Identifiers)**: 先頭が大文字の識別子は、そのパッケージの外部からアクセス可能です。
*   **非エクスポートされた識別子 (Unexported Identifiers)**: 先頭が小文字の識別子は、そのパッケージ内からのみアクセス可能です。

`os/signal`パッケージが`runtime`パッケージの非エクスポート関数にアクセスする必要がある場合、通常の方法では直接呼び出すことはできません。

### アセンブリスタブ (Assembly Stubs)

`//go:linkname`ディレクティブが導入される前、Goの内部パッケージが他のパッケージの非エクスポート関数にアクセスする一般的な方法の一つが、アセンブリ言語で書かれた「スタブ」を使用することでした。
これは、`os/signal`パッケージ内に、`runtime`パッケージの非エクスポート関数と同じシグネチャを持つ関数を宣言し、その実装をアセンブリ言語で提供するものです。アセンブリコードは、単に`JMP`命令を使って`runtime`パッケージ内の実際の関数に制御を移すだけでした。これにより、Goコンパイラは`os/signal`内の関数呼び出しを、実際には`runtime`内の関数へのジャンプとして解決できました。

### `//go:linkname` ディレクティブ

`//go:linkname`はGoコンパイラに対する特殊なディレクティブ（プラグマ）です。これは、Goのソースコード内で、あるパッケージの関数や変数を、別のパッケージの非エクスポートされた関数や変数にリンクさせることを可能にします。
書式は以下の通りです。
`//go:linkname localname importpath.name`
ここで、`localname`は現在のパッケージで宣言された関数または変数の名前、`importpath.name`はリンクしたい外部パッケージの非エクスポートされた関数または変数の完全修飾名です。

このディレクティブは、Goの型システムや可視性ルールを意図的に迂回するため、非常に強力ですが、同時に危険も伴います。主にGoの標準ライブラリやランタイム内部で、パフォーマンス最適化や低レベルなシステム連携のために使用されます。通常のアプリケーション開発でこれを使用することは推奨されません。

### 共有ライブラリと`ppc64le`アーキテクチャの`BR`と`BL`命令

*   **共有ライブラリ (Shared Libraries)**: 複数のプログラムで共有されるコードのライブラリです。これにより、ディスクスペースの節約やメモリ使用量の削減、プログラムのモジュール化が促進されます。
*   **`ppc64le` (PowerPC 64-bit Little Endian)**: IBM PowerPCアーキテクチャの64ビット版で、リトルエンディアンのバイト順序を持つものです。
*   **`BR` (Branch Register) 命令**: PowerPCアーキテクチャにおける無条件分岐命令の一つで、レジスタに格納されたアドレスにジャンプします。
*   **`BL` (Branch Link) 命令**: `BR`と同様に分岐を行いますが、分岐元のアドレス（次の命令のアドレス）をリンクレジスタ（LR）に保存します。これは関数呼び出しによく使われ、呼び出し元に戻るために使用されます。

`ppc64le`の共有ライブラリの文脈では、共有ライブラリ内のシンボルへの直接的な`BR`ジャンプが制限される場合があります。これは、共有ライブラリがロードされるアドレスが実行時に決定されるため、コンパイル時に固定のアドレスにジャンプする`BR`が使えない、あるいは複雑なリロケーションが必要になるためです。`BL`命令は、呼び出し元に戻るためのアドレスを保存するため、共有ライブラリ内の関数呼び出しには適していますが、単なるジャンプには不向きな場合があります。このコミットでは、アセンブリスタブが`BR`命令を使用していたことが問題となり、`//go:linkname`による直接リンクに切り替えることでこの問題を回避しました。

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するシステムです。ガベージコレクション、スケジューリング、メモリ管理、システムコール、シグナルハンドリングなど、多くの低レベルな機能を提供します。`os/signal`パッケージがシグナルを処理するためには、OSからのシグナルを受け取り、Goのゴルーチンにディスパッチするランタイムの内部メカニズムと連携する必要があります。そのため、`os/signal`は`runtime`の非公開関数に依存していました。

## 技術的詳細

このコミットは、`os/signal`パッケージが`runtime`パッケージの以下の非公開関数にアクセスする方法を変更します。
*   `runtime.signal_disable`
*   `runtime.signal_enable`
*   `runtime.signal_ignore`
*   `runtime.signal_recv`

変更前は、`src/os/signal/sig.s`というアセンブリファイルに、これらの関数に対応するスタブが定義されていました。例えば、`signal_disable`の場合、以下のようなアセンブリコードがありました。

```assembly
TEXT ·signal_disable(SB),NOSPLIT,$0
	JMP runtime·signal_disable(SB)
```

ここで`JMP`は、アーキテクチャに応じて`B`（ARM）や`BR`（PPC64/PPC64LE）にマクロ展開されます。このアセンブリスタブは、`os/signal`パッケージ内の`signal_disable`というGo関数が呼び出された際に、`runtime`パッケージ内の実際の`runtime.signal_disable`関数にジャンプするようにしていました。

変更後は、このアセンブリスタブが完全に削除されました。代わりに、`runtime`パッケージ内の`src/runtime/sigqueue.go`（および`src/runtime/sigqueue_plan9.go`）ファイルで、これらの関数定義の直前に`//go:linkname`ディレクティブが追加されました。

例えば、`runtime/sigqueue.go`では、`signal_recv`関数の定義が以下のように変更されました。

```go
//go:linkname signal_recv os/signal.signal_recv
func signal_recv() uint32 {
    // ...
}
```

このディレクティブはGoコンパイラに対し、「`runtime`パッケージ内の`signal_recv`関数を、`os/signal`パッケージ内の`signal_recv`という名前のシンボルとしてエクスポート（またはリンク可能）にする」と指示します。これにより、`os/signal`パッケージは、あたかも`runtime`パッケージが`signal_recv`をエクスポートしているかのように、直接その関数を呼び出すことができるようになります。

また、`src/os/signal/signal_unix.go`では、これらの関数がアセンブリで定義されていることを示すコメントが「ランタイムパッケージによって定義される」という内容に変更されました。

```go
// In assembly.
// func signal_disable(uint32)
// func signal_enable(uint32)
// func signal_ignore(uint32)

// Defined by the runtime package.
func signal_disable(uint32)
func signal_enable(uint32)
func signal_ignore(uint32)
```

`src/runtime/sigqueue_plan9.go`には、`import _ "unsafe"`が追加されています。これは、`//go:linkname`ディレクティブを使用するパッケージでは、慣例的に`unsafe`パッケージをインポートする必要があるためです。`unsafe`パッケージは、Goの型安全性を迂回する機能を提供するため、`//go:linkname`のような低レベルな操作と関連付けられています。

この変更により、アセンブリコードの量が減り、特定のアーキテクチャ（`ppc64le`）に起因する問題が解決され、Goの内部コードベースがよりクリーンで保守しやすくなりました。

## コアとなるコードの解説

### `src/os/signal/sig.s` の変更

このファイルからは、`runtime`パッケージの非エクスポート関数にジャンプするためのアセンブリスタブが完全に削除されました。これにより、アセンブリコードの複雑性が減少し、特に`ppc64le`アーキテクチャにおける共有ライブラリの`BR`命令に関する問題が解消されました。残されたコメントは、`//go:linkname`を使用しても、Goツールが`-complete`フラグをコンパイラに渡さないようにするために、依然として`.s`ファイルが必要であることを示唆しています。これは、Go関数が本体を持たないことについてコンパイラが文句を言わないようにするためです。

### `src/runtime/sigqueue.go` および `src/runtime/sigqueue_plan9.go` の変更

これらのファイルでは、`runtime`パッケージ内の`signal_recv`, `signal_enable`, `signal_disable`, `signal_ignore`といった非エクスポート関数定義の直前に、`//go:linkname`ディレクティブが追加されました。

例: `//go:linkname signal_recv os/signal.signal_recv`

このディレクティブは、Goコンパイラに対して、`runtime`パッケージ内の`signal_recv`という名前の関数を、`os/signal`パッケージ内の`signal_recv`という名前のシンボルとして外部に公開するように指示します。これにより、`os/signal`パッケージは、これらの関数を直接呼び出すことが可能になり、アセンブリスタブを介した間接的な呼び出しが不要になります。

`src/runtime/sigqueue_plan9.go`に追加された`import _ "unsafe"`は、`//go:linkname`ディレクティブを使用する際に、コンパイラが`unsafe`パッケージが使用されていることを認識するための慣例的な記述です。これは、`//go:linkname`がGoの型システムを迂回する「unsafe」な操作であるためです。

これらの変更により、Goの内部パッケージ間の連携がより直接的かつ効率的になり、特定のアーキテクチャの制約を回避しつつ、コードの保守性が向上しました。

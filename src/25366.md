# [インデックス 25366] ファイルの概要

このコミットは、Goコンパイラの内部パッケージである `src/cmd/internal/goobj/read.go` ファイルに対する変更です。このファイルは、Goのオブジェクトファイル（`.o` ファイル）を読み込み、その内容を解析する役割を担っています。特に、パッケージの外部に公開される情報（エクスポートデータ）の読み込みロジックに関わる部分が修正されています。

## コミット

`cmd/internal/goobj: permit 0 bytes in export data (prep. for new export format)`

このコミットは、Goのエクスポートデータにおいて0バイト（NUL文字）を許可するように `cmd/internal/goobj` パッケージのパーサーを変更します。これは、新しいエクスポートフォーマットへの移行準備の一環として行われました。

## 変更の背景

Goコンパイラは、パッケージのコンパイル時にそのパッケージが外部に公開する情報（型、関数、変数など）を「エクスポートデータ」として生成します。このエクスポートデータは、そのパッケージをインポートする他のパッケージのコンパイルを高速化するために使用されます。Goのエクスポートデータフォーマットは、コンパイラの進化とともに変更されることがあります。

このコミットが行われた2015年頃は、Goのエクスポートデータフォーマットが新しい形式に移行する過渡期でした。従来のフォーマットでは、エクスポートデータの終端を示すマーカーとしてNUL文字（0バイト）が使用されることがありましたが、新しいフォーマットではエクスポートデータ自体にNUL文字が含まれる可能性がありました。

`cmd/internal/goobj` パッケージ内の `read.go` ファイルにあるオブジェクトファイルパーサーは、エクスポートデータを読み込む際にNUL文字をデータの終端、または不正なデータとして扱っていました。この挙動は、新しいエクスポートフォーマットでNUL文字がデータの一部として有効になる場合に問題となります。

したがって、新しいエクスポートフォーマットに対応するためには、パーサーがNUL文字をエラーとして扱わないように変更する必要がありました。この変更は、将来のGoコンパイラのバージョンで新しいエクスポートフォーマットが完全に採用されるための「準備」として位置づけられています。

## 前提知識の解説

### Goのオブジェクトファイル (`.o` ファイル)

Goコンパイラは、Goのソースコードをコンパイルすると、中間形式としてオブジェクトファイル（通常は `.o` 拡張子を持つ）を生成します。これらのオブジェクトファイルは、最終的にGoリンカによって結合され、実行可能ファイルや共有ライブラリが作成されます。

Goのオブジェクトファイルは、標準的なELF（Executable and Linkable Format）ファイルとは異なり、Go独自のカスタムフォーマットを使用しています。このフォーマットには、コンパイルされたコード、データ、シンボルテーブル、そして重要な「エクスポートデータ」が含まれます。

### エクスポートデータ (Export Data)

エクスポートデータは、Goのパッケージが外部に公開するすべての情報（エクスポートされた型、関数、変数、定数など）のバイナリ表現です。このデータは、他のパッケージが現在のパッケージをインポートする際に、コンパイラがそのパッケージのソースコードを再解析することなく、必要な情報を取得できるようにするために存在します。これにより、コンパイルプロセスが大幅に高速化されます。

エクスポートデータには、以下のような情報が含まれます。
*   エクスポートされた宣言の型情報
*   インライン化可能な関数のIR (Intermediate Representation)
*   ジェネリック関数のIR
*   関数パラメータのエスケープ解析のサマリー

エクスポートデータは通常、パッケージアーカイブ（`.a` ファイル）内の `__.PKGDEF` ファイルに格納されます。

### `cmd/internal/goobj` パッケージ

`cmd/internal/goobj` は、Goツールチェーンの内部パッケージです。このパッケージは、GoコンパイラとリンカがカスタムのGoオブジェクトファイルを読み書きし、操作するために必要な構造体と関数を提供します。

このパッケージはGoの公開APIの一部ではないため、その設計と実装はGoの内部動作と密接に結びついており、予告なく変更される可能性があります。外部ツールがGoのコンパイル済みアーティファクトと対話する必要がある場合、エクスポートデータへのアクセスには `golang.org/x/tools/go/gcexportdata` パッケージが推奨される公開インターフェースです。

### NUL文字 (0バイト) の意味

プログラミングにおいて、NUL文字（ASCIIコード0）はしばしば文字列の終端を示すマーカーとして使用されます。C言語の文字列などがその典型です。しかし、バイナリデータストリームにおいては、NUL文字も他のバイトと同様に有効なデータの一部として扱われることがあります。

このコミットの文脈では、Goの古いエクスポートフォーマットではNUL文字が特定の意味（例えばデータの区切りや終端）を持っていた可能性がありますが、新しいフォーマットではNUL文字が単なるデータバイトとして出現する可能性がある、という点が重要です。

## 技術的詳細

`src/cmd/internal/goobj/read.go` 内の `parseObject` 関数は、Goオブジェクトファイルを解析する主要なロジックを含んでいます。この関数は、オブジェクトファイル内の様々なセクションを読み込み、特にエクスポートデータセクションを処理します。

変更前のコードでは、エクスポートデータを読み込むループ内で `r.readByte()` を呼び出し、読み込んだバイトがNUL文字（`c3 == 0`）である場合に、それを不正なオブジェクトファイルを示す `errCorruptObject` エラーとして扱っていました。これは、従来のフォーマットではNUL文字がデータの途中に現れることが想定されていなかったため、NUL文字の出現はデータ破損の兆候と見なされていたからです。

しかし、新しいエクスポートフォーマットでは、エクスポートデータの内容がより複雑になり、NUL文字がデータの一部として正当に出現する可能性が出てきました。例えば、新しいエンコーディングスキームやデータ構造において、NUL文字が特定のフィールドの値として使用されることが考えられます。

この変更は、NUL文字の出現自体をエラーと見なすのではなく、`r.err != nil`（つまり、バイトの読み込み自体にエラーが発生した場合）のみをエラーとして扱うように修正することで、新しいフォーマットの柔軟性に対応しています。これにより、パーサーはNUL文字を含む新しいエクスポートデータを正しく処理できるようになります。

この修正は、Goコンパイラが新しいエクスポートフォーマットを生成し、それを古いコンパイラが読み込もうとした場合に互換性の問題を引き起こす可能性を考慮し、段階的に導入される変更の一部です。このコミットは、新しいフォーマットが完全に実装される前に、パーサー側でその変更を受け入れる準備を整えるものです。

## コアとなるコードの解説

変更は `src/cmd/internal/goobj/read.go` ファイルの `parseObject` メソッド内で行われています。

元のコードでは、以下の条件でエラーを返していました。
```go
if c3 == 0 { // NUL or EOF, either is bad
    return errCorruptObject
}
```
これは、`r.readByte()` で読み込んだバイト `c3` がNUL文字（0）である場合、またはファイルの終端（EOF）に達した場合に、オブジェクトファイルが破損していると判断し、`errCorruptObject` を返していました。このロジックは、NUL文字がエクスポートデータ内で有効なデータとして出現しないという前提に基づいています。

変更後のコードは以下のようになります。
```go
// The new export format can contain 0 bytes.
// Don't consider them errors, only look for r.err != nil.
if r.err != nil {
    return errCorruptObject
}
```
この変更により、`c3 == 0` という条件が削除され、NUL文字の出現自体はエラーとは見なされなくなりました。代わりに、`r.err != nil` という条件のみがチェックされます。`r.err` は `objReader` 構造体のフィールドであり、`readByte` メソッド内で実際にバイトの読み込みに失敗した場合（例えば、ファイルの終端を超えて読み込もうとした場合など）に設定されます。

つまり、この変更は、NUL文字がエクスポートデータの一部として現れても、それが読み込みエラー（`r.err != nil`）を引き起こさない限り、正常なデータとして処理を続行することを許可します。これにより、新しいエクスポートフォーマットがNUL文字をデータとして含むことができるようになり、パーサーがその新しいフォーマットに対応できるようになります。コメントにも明記されている通り、「新しいエクスポートフォーマットは0バイトを含むことができる。それらをエラーと見なすのではなく、`r.err != nil` の場合のみをエラーとする。」という意図が反映されています。

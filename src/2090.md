# [インデックス 2090] ファイルの概要

このコミットは、Go言語の初期開発段階における「pretty printer」（整形ツール）の機能強化に焦点を当てたものです。具体的には、抽象構文木（AST）をテンプレート駆動で整形するメカニズムにさらなる作業が加えられ、その機能の検証のために予備的なテストスイートが追加され、関連するドキュメントも整備されました。

## 変更の背景

*   **Go言語の初期開発段階**: このコミットは2009年に行われており、Go言語がまだ活発に開発されていた非常に初期の段階に属します。Robert GriesemerはGo言語の共同設計者の一人であり、`usr/gri`というパスは、彼が個人的に実験的なコードやプロトタイプを開発していたことを示唆しています。この時期のコミットは、Go言語の基本的なツールやライブラリの設計思想が形成されていく過程を反映しています。
*   **コードフォーマットの重要性**: プログラミング言語において、一貫したコードフォーマットは可読性を高め、共同開発を容易にする上で極めて重要です。Go言語は、`gofmt`という公式のフォーマッタを持つことで知られていますが、このコミットはそのようなツールがどのように進化していったかの一端を示している可能性があります。初期段階からコードの整形に注力していたことが伺えます。
*   **ASTベースのフォーマット**: コンパイラやツールチェーンにおいて、ソースコードを直接操作するのではなく、その抽象構文木（AST）を介して操作することは一般的です。これにより、構文的な正確性を保ちつつ、より複雑な変換や整形が可能になります。このコミットは、ASTを基盤としたフォーマットの仕組みを強化しようとしています。これは、GoのツールチェーンがASTを深く活用する設計思想に基づいていることを示しています。
*   **テンプレート駆動のアプローチ**: "template-driven"という記述は、フォーマットのルールがハードコードされるのではなく、外部のテンプレートや定義ファイルによって制御されることを示唆しています。これにより、フォーマットルールの柔軟性や拡張性が向上します。例えば、将来的に異なるフォーマットスタイルに対応したり、ユーザーがカスタムルールを定義したりする可能性を考慮していると考えられます。

## 前提知識の解説

*   **抽象構文木 (AST)**: ソースコードの抽象的な構文構造を木構造で表現したものです。コンパイラはソースコードを字句解析（トークン化）し、構文解析を経てASTを構築します。その後の意味解析、最適化、コード生成などにASTを利用します。コードフォーマッタもASTを操作することで、コードの構造を保ちつつ、インデント、改行、スペースなどを調整して整形を行います。Go言語では、標準ライブラリの`go/ast`パッケージがASTのデータ構造を定義しています。
*   **Go言語の`go/token`パッケージと`go/scanner`パッケージ**:
    *   `go/token`パッケージは、Goソースコードのトークン（識別子、キーワード、演算子など）やファイル内の位置情報を定義します。
    *   `go/scanner`パッケージは、Goソースコードを字句解析し、トークンを生成する機能を提供します。
    `format.go`内でこれらのパッケージがインポートされていることから、このフォーマットツールがソースコードをトークンレベルで解析し、ASTを構築する過程、またはその結果を扱うことが示唆されます。
*   **リフレクション (`reflect`パッケージ)**: Go言語のリフレクション機能は、実行時にプログラムの型情報を検査したり、値の操作を行ったりする機能です。`format.go`で`reflect`パッケージがインポートされていることから、このテンプレート駆動のフォーマッタが、ASTノードの型情報をリフレクションを使って動的に取得し、それに基づいてフォーマットルールを適用している可能性が高いです。これにより、フォーマッタは特定のASTノードの型に依存せず、汎用的に動作することができます。
*   **EBNF (Extended Backus-Naur Form)**: 構文規則を記述するためのメタ言語です。`format.go`のコメントにEBNF形式のフォーマットルールが記載されており、このフォーマッタがEBNFのような形式で定義されたルールを解釈して整形を行っていることがわかります。これは、フォーマットルールが明確かつ構造的に定義されていることを意味します。

## 技術的詳細

このコミットの主要な変更は、`usr/gri/pretty/format.go`ファイルに集約されており、GoのASTを整形するためのテンプレート駆動型エンジンが大幅に強化されています。

*   **テンプレート駆動のフォーマットエンジン**:
    *   **`expr`インターフェースと具象型**: フォーマットルールの各要素を表現するために、`expr`というインターフェースが定義され、`alternative`（選択）、`sequence`（順序）、`field`（フィールド参照）、`literal`（リテラル文字列）、`option`（オプション要素）、`repetition`（繰り返し要素）、`custom`（カスタム処理）といった具象型がこれを実装しています。これにより、複雑なフォーマットルールを木構造として表現することが可能になります。
    *   **`Format`型**: `type Format map[string] expr;`と定義されており、Goの型名（例: `ast.Ident`）をキーとし、その型を整形するための`expr`（フォーマット表現）を値とするマップとして、フォーマットルール全体を保持します。
    *   **`Parse`関数**: 外部から与えられたフォーマット定義（EBNFライクな構文で記述された文字列）を解析し、内部的な`Format`構造を構築する役割を担います。この解析処理は`parser`構造体によって行われ、字句解析と構文解析を通じてフォーマットルールを抽象構文木として表現します。
    *   **`print`メソッド**: `Format`型の`print`メソッドが、フォーマットエンジンの核となります。このメソッドは、整形対象のGoのASTノード（`reflect.Value`として渡される）と、そのノードに適用すべきフォーマット表現（`expr`）を受け取り、再帰的に整形処理を実行します。
        *   `switch t := fexpr.(type)`文を用いて、`fexpr`の具体的な型に応じて異なる整形ロジックが適用されます。
        *   `*field`の場合、`t.name`（フィールド名、または特殊な指定子`^`や`*`）に基づいて`value`から対応するフィールド値を取得します。`^`は現在の値そのものを、`*`はポインタ、配列、マップ、インターフェースの間接参照を意味し、これらの値に対して再帰的に`print`を呼び出します。これにより、ASTの階層構造を深く辿って整形が行われます。
        *   `*literal`の場合、指定されたリテラル文字列をそのまま出力します。
        *   `*option`や`*repetition`の場合、内部の要素が「空でない」（例えば、ポインタが`nil`でない、スライスが空でないなど）場合にのみ出力を行うロジックが含まれており、これによりオプション要素や繰り返し要素の有無に応じた柔軟な整形が可能です。
    *   **デフォルトフォーマット**: 特定の型に対するフォーマットルールが`Format`マップに定義されていない場合、`%v`（Goの標準的なデフォルトフォーマット）が使用されるなど、デフォルトの整形ルールが適用されます。また、ポインタ、配列、マップなどの型には、`*`指定子を用いたデフォルトルールが設定されており、これらの型が間接参照される形で整形されるようになっています。
*   **テストスイートの追加**: `usr/gri/pretty/format_test.go`が新規追加されており、`format`パッケージの基本的な機能（整数値のフォーマット、構造体のフォーマット、オプションフィールドや繰り返しフィールドの扱い）に対する単体テストが記述されています。これにより、フォーマットエンジンの動作が検証され、今後の変更に対するリグレッションテストの基盤が提供されます。テストケースは、期待される出力と実際の結果を比較することで、フォーマッタの正確性を保証します。
*   **AST定義の調整**: `usr/gri/pretty/ast.txt`では、ASTの構造定義（おそらくはフォーマットテンプレートとして使用されるもの）が微調整されています。例えば、コメント内の構文が`//string = "%s" ;`から`//string = "%s";`に変更されるなど、構文の厳密化や一貫性の向上が図られています。これは、フォーマットエンジンのパーサーがより厳密な構文を要求するようになったことを示唆しています。
*   **APIの変更**: `usr/gri/pretty/pretty.go`では、`ast_format.Apply(tw, prog);`という既存のAPI呼び出しが`ast_format.Fprint(tw, prog);`に変更されています。これは、`format`パッケージのAPIが`Apply`から`Fprint`に改名されたか、あるいは引数の取り方が変更されたことを示唆しています。`Fprint`は可変長引数`args ...`を受け取るように変更されており、より柔軟な利用が可能になっています。これは、複数のASTノードを一度に整形するようなユースケースを想定している可能性があります。

## コアとなるコードの変更箇所

*   `usr/gri/pretty/format.go`: フォーマットエンジンの主要なロジックが大幅に修正・追加されています。特に、`expr`インターフェースの実装、`Format`型の定義、`Parse`関数、`print`メソッド、そしてリフレクションを用いた値の処理部分が中心です。このファイルは、このコミットにおける機能追加と改善の大部分を占めています。
*   `usr/gri/pretty/format_test.go`: 新規追加されたファイルで、`format`パッケージの単体テストが含まれています。これにより、フォーマットエンジンの動作の正確性が保証されます。
*   `usr/gri/pretty/ast.txt`: ASTのフォーマットテンプレート定義が微修正されています。これは、フォーマットエンジンのパーサーの変更や、より正確なAST表現の必要性に対応したものです。
*   `usr/gri/pretty/pretty.go`: `format`パッケージのAPI呼び出しが`Apply`から`Fprint`に変更されています。これは、新しいAPIインターフェースへの移行を示しています。

## コアとなるコードの解説

`usr/gri/pretty/format.go`の変更がこのコミットの最も重要な部分です。

1.  **`expr`インターフェースと具象型**:
    ```go
    type (
        expr interface {
            String() string;
        };

        alternative struct { // ... }
        sequence struct { // ... }
        field struct { // ... }
        literal struct { // ... }
        option struct { // ... }
        repetition struct { // ... }
        custom struct { // ... }
    )
    ```
    これは、フォーマットルールの各要素を表現するためのポリモーフィックな構造を定義しています。`String()`メソッドは、これらのフォーマット表現を文字列として出力し、デバッグやルールの可視化に役立ちます。これにより、複雑なフォーマットルールを構成要素に分解し、それぞれを独立して処理できる柔軟な設計が実現されています。

2.  **`Format`型と`Parse`関数**:
    ```go
    type Format map [string] expr;

    func Parse(src interface{}) Format { /* ... */ }
    ```
    `Format`は、Goの型名（例: `ast.Ident`）をキーとし、その型を整形するための`expr`（フォーマット表現）を値とするマップです。`Parse`関数は、外部のフォーマット定義（例えば、`ast.txt`のようなファイルに記述されたEBNFライクな構文）を読み込み、字句解析と構文解析を経て、この`Format`マップを構築します。これにより、フォーマットルールがコードから分離され、ユーザーや開発者がルールを柔軟に変更・拡張できる「テンプレート駆動」の特性が実現されています。

3.  **`print`メソッド**:
    ```go
    func (f Format) print(w io.Write, fexpr expr, value reflect.Value, index int) bool { /* ... */ }
    ```
    このメソッドがフォーマットエンジンの心臓部であり、ASTノードの実際の整形処理を行います。
    *   `w io.Write`: 整形結果を書き込む出力先（例: `os.Stdout`や`bytes.Buffer`）。
    *   `fexpr expr`: 現在処理しているフォーマット表現（`expr`インターフェースのいずれかの実装）。
    *   `value reflect.Value`: 現在整形対象となっているGoのASTノードやそのフィールドの`reflect.Value`。リフレクションを使って、実行時に値の型やフィールドに動的にアクセスし、その内容を読み取ります。
    *   `index int`: 配列やスライスを処理する際のインデックス。

    メソッド内部では、`switch t := fexpr.(type)`文を使って、`fexpr`の具体的な型（`alternative`, `sequence`, `field`など）に応じて異なる整形ロジックを実行します。
    *   **`*field`の処理**: `t.name`（フィールド名、または`^`, `*`）に基づいて`value`から対応するフィールド値を取得します。
        *   `^`: 現在の`value`そのものを指します。
        *   `*`: ポインタ、配列、マップ、インターフェースなどの間接参照をデリファレンスし、その参照先の値を取得します。これにより、ASTのポインタやスライスを適切に辿って整形できます。
        *   その他のフィールド名: `reflect.StructValue`から指定された名前のフィールドを取得します。
        取得したフィールド値に対して、再帰的に`f.print`を呼び出すことで、ASTの階層構造全体を整形します。
    *   **`*literal`の処理**: `printf(w, t.value, value)`を呼び出して、フォーマット定義に含まれるリテラル文字列をそのまま出力します。
    *   **`*option`や`*repetition`の処理**: これらの要素は、内部の`expr`が「空でない」（例えば、ポインタが`nil`でない、スライスが空でないなど）場合にのみ出力を行うロジックが含まれています。これにより、ASTのオプション要素や繰り返し要素の有無に応じた柔軟な整形が可能です。

この`print`メソッドと、`Format`型、`Parse`関数の組み合わせにより、GoのASTを、外部定義されたテンプレートに基づいて動的に整形する強力なメカニズムが実現されています。これは、後の`gofmt`のようなGoの公式フォーマッタの基礎となる設計思想の一端を示していると考えられます。

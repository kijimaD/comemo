## 変更の背景

GoコンパイラのSSAバックエンドは、コードの最適化を目的としています。このコミットの背景には、以下の課題と目的がありました。

1.  **比較処理の最適化の余地**: コンパイラが生成する比較命令には、定数との比較など、結果が事前に分かりきっているケースが存在します。これらのケースをより効率的に処理することで、生成されるアセンブリコードの品質を向上させる必要がありました。特に、`x & 31 < 32`のようなビット演算と定数比較の組み合わせは、常に真となることが静的に判断できるため、これを活用する最適化が求められました。
2.  **フラグの伝播と定数畳み込み**: 比較結果はCPUのフラグレジスタに格納され、その後の条件分岐や`SETcc`命令などで利用されます。定数比較の結果がフラグとして確定した場合、そのフラグを後続の命令に伝播させ、可能な限り定数畳み込みを行うことで、不要な命令を削減し、より効率的なコードを生成することが目標でした。
3.  **`CMPxconst`命令の可読性と一貫性**: `CMPxconst`命令の引数順序が、比較の意図と一致しない場合があり、コンパイラの内部処理の一貫性を損ねる可能性がありました。これを比較の方向（例: `x < y`）に沿って再編成することで、コードの可読性と保守性を向上させる必要がありました。
4.  **デッドコード削除の改善**: SSA形式では、最適化の過程で`OpCopy`のような中間的な操作が生成されることがあります。特に`Phi`ノードの強度低下（strength-reducing）によって生成される`OpCopy`は、その後のデッドコード削除で適切に処理されないと、不要なコードが残存する可能性があります。デッドコード削除のロジックを改善し、`OpCopy`の除去とデッドブロックの効率的な削除を確実に行うことで、最終的なコードサイズと実行速度を最適化することが求められました。

これらの背景から、コンパイラのSSAバックエンドにおける比較処理とデッドコード削除のロジックを洗練し、より高性能なGoプログラムを生成するための改善が図られました。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が不可欠です。

### 1. GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木（AST）にパースした後、中間表現としてSSA（Static Single Assignment）形式に変換します。SSA形式は、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。SSAバックエンドは、このSSA形式のコードに対して様々な最適化（定数畳み込み、デッドコード削除、強度低下など）を適用し、最終的にターゲットアーキテクチャ（例: AMD64）の機械語に近いコードを生成します。

### 2. 比較命令とCPUフラグ

CPUには、演算結果の状態を示すためのフラグレジスタがあります。比較命令（`CMP`など）を実行すると、このフラグレジスタの特定のビット（例: ゼロフラグ、キャリーフラグ、サインフラグ、オーバーフローフラグなど）が設定されます。これらのフラグは、その後の条件分岐命令（`JE` (Jump if Equal), `JL` (Jump if Less) など）や、比較結果をブール値としてレジスタに格納する`SETcc`命令（例: `SETEQ` (Set if Equal)）で使用されます。

-   **符号付き比較と符号なし比較**: 整数型には符号付きと符号なしがあり、同じビットパターンでも解釈が異なります。そのため、比較結果も符号の有無によって変わることがあります。例えば、`-1`（符号付き）と`1`（符号なし）を比較する場合、符号付きでは`-1 < 1`ですが、符号なしでは`UINT_MAX < 1`となり、結果が逆転します。CPUのフラグは、これらの両方の比較結果を判断できるように設計されています。

### 3. 定数畳み込み (Constant Folding)

定数畳み込みは、コンパイル時に計算結果が確定する式を、その計算結果の定数で置き換える最適化手法です。例えば、`x = 1 + 2`という式があれば、コンパイラはこれを`x = 3`に置き換えます。これにより、実行時の計算コストを削減できます。このコミットでは、比較の結果が常に真または偽となる場合に、その比較を対応する定数フラグに置き換えることで、さらに最適化を進めています。

### 4. デッドコード削除 (Dead Code Elimination)

デッドコード削除は、プログラムの実行結果に影響を与えないコード（デッドコード）を削除する最適化手法です。例えば、到達不能なコードブロックや、値がどこにも使用されない変数の代入などがデッドコードと見なされます。SSA形式では、値の使用箇所が明確になるため、デッドコードの特定と削除が容易になります。

### 5. `OpCopy`と`Phi`ノード

-   **`Phi`ノード**: SSA形式において、複数の制御フローパスが合流する地点で、異なるパスから来る同じ論理変数に異なる値が代入されている場合に、それらの値を統合するために使用される仮想的な命令です。例えば、`if-else`文の後に変数が使用される場合、`if`ブロックと`else`ブロックでその変数に異なる値が代入されていると、合流地点で`Phi`ノードが挿入されます。
-   **`OpCopy`**: 最適化の過程で、ある値が別の値の単なるコピーであることが判明した場合に生成されるオペレーションです。例えば、`x = y`のような代入がこれに該当します。`Phi`ノードの強度低下（例えば、`Phi`ノードの全ての入力が同じ値である場合、`Phi`ノードは不要になり、その値の`OpCopy`に置き換えられる）によって生成されることがあります。これらの`OpCopy`は、最終的なコード生成の前に除去されるべきです。

### 6. AMD64アーキテクチャの命令セット

AMD64（x86-64）は、Goがサポートする主要なCPUアーキテクチャの一つです。このアーキテクチャには、比較命令（`CMP`）、ビット演算命令（`AND`）、シフト命令（`SHL`, `SHR`, `SAR`）、条件付きセット命令（`SETcc`）、条件分岐命令（`Jcc`）など、様々な命令があります。コンパイラは、これらの命令を組み合わせてGoのコードを機械語に変換します。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおけるAMD64アーキテクチャ向けのコード生成と最適化に、いくつかの重要な改善を導入しています。

### 1. 新しい定数フラグオペコードの導入

コミットの主要な変更点の一つは、`src/cmd/compile/internal/ssa/gen/AMD64Ops.go`および`src/cmd/compile/internal/ssa/opGen.go`で導入された新しい定数フラグオペコードです。これらは、特定の比較がコンパイル時に常に同じ結果になることが分かっている場合に、その結果を直接表現するために使用されます。

具体的には、以下の5つの新しいオペコードが追加されました。

-   `FlagEQ`: 比較結果が常に等しい（Equal）場合。
-   `FlagLT_ULT`: 符号付きで「より小さい」（Less Than）かつ符号なしで「より小さい」（Unsigned Less Than）場合。
-   `FlagLT_UGT`: 符号付きで「より小さい」（Less Than）かつ符号なしで「より大きい」（Unsigned Greater Than）場合。
-   `FlagGT_UGT`: 符号付きで「より大きい」（Greater Than）かつ符号なしで「より大きい」（Unsigned Greater Than）場合。
-   `FlagGT_ULT`: 符号付きで「より大きい」（Greater Than）かつ符号なしで「より小さい」（Unsigned Less Than）場合。

これらのオペコードは、例えば`x & 31 < 32`のような比較式で、`x & 31`の結果が常に`0`から`31`の範囲に収まるため、`32`より常に小さいことが静的に判断できる場合に`FlagLT_ULT`として表現されます。これにより、実行時に実際の比較命令を発行する必要がなくなり、コンパイル時に比較結果を確定させることができます。

### 2. 定数フラグオペコードの定数畳み込み

`src/cmd/compile/internal/ssa/gen/AMD64.rules`および`src/cmd/compile/internal/ssa/rewriteAMD64.go`では、これらの新しい定数フラグオペコードを、それらを利用する全ての命令（フラグユーザー）に定数畳み込みするルールが追加されています。

-   **`SBBQcarrymask` / `SBBLcarrymask` への畳み込み**: シフト演算のオーバーフローチェックなどで使用される`SBBQcarrymask`や`SBBLcarrymask`オペレーションは、比較結果が定数フラグとして確定している場合、直接`MOVQconst`または`MOVLconst`（定数`-1`または`0`）に置き換えられます。これにより、シフト演算後のマスク処理が簡略化されます。
-   **条件分岐への畳み込み**: `EQ`, `NE`, `LT`, `LE`, `GT`, `GE`, `ULT`, `ULE`, `UGT`, `UGE`といった条件分岐ブロックは、制御値が定数フラグオペコードである場合、`First`ブロック（常に最初のサクセッサに分岐する）に変換されます。これにより、条件分岐の評価が不要になり、無条件ジャンプに置き換えられることで、分岐予測の失敗を防ぎ、パイプラインの効率を向上させます。
-   **`SETcc`命令への畳み込み**: `SETEQ`, `SETNE`, `SETL`, `SETLE`, `SETG`, `SETGE`, `SETB`, `SETBE`, `SETA`, `SETAE`といった`SETcc`命令は、定数フラグオペコードを引数として受け取る場合、直接`MOVBconst`（定数`0`または`1`）に置き換えられます。これにより、比較結果をレジスタに格納する処理が、単なる定数ロードに簡略化されます。

これらの定数畳み込みにより、コンパイラはよりアグレッシブな最適化を適用し、実行時のオーバーヘッドを削減できます。

### 3. `CMPxconst`引数順序の再編成

`src/cmd/compile/internal/ssa/gen/AMD64.rules`では、`CMPQconst`, `CMPLconst`, `CMPWconst`, `CMPBconst`といった定数との比較命令の引数順序が変更されています。以前は`CMPQconst [64] y`のように定数が先に記述されていましたが、`CMPQconst y [64]`のように比較対象の変数が先に、定数が後に来るように変更されました。これは、比較の方向（例: `y < 64`）をより直感的に表現し、コンパイラの内部処理における一貫性を高めるための調整です。

### 4. デッドコード削除ロジックの再編成

`src/cmd/compile/internal/ssa/deadcode.go`では、デッドコード削除のロジックが大幅に再編成されています。

-   **`findlive`関数の分割**: 以前は`findlive`関数が到達可能なブロックとライブな値の両方を計算していましたが、`reachableBlocks`と`liveValues`の2つの関数に分割されました。これにより、各関数の責務が明確になり、コードの可読性と保守性が向上しています。
-   **`OpCopy`の削除とコピー除去の先行実行**: コミットメッセージで述べられているように、`deadcode`関数は`Phi`オペレーションの強度低下によって生成される`OpCopy`オペレーションを削除する必要がありました。このため、デッドコード削除のプロセスが変更され、まず到達可能なブロックを特定し、次に`copyelim`（コピー除去）を実行してから、ライブな値を計算するように順序が変更されました。これにより、`OpCopy`が適切に除去され、デッドブロックが効率的に削除されることが保証されます。
-   **`namedValues`マップの処理改善**: `namedValues`マップからデッドなエントリや重複するエントリを削除するロジックも変更され、`OpCopy`の解決が`copyelim`によって事前に行われるようになったため、`deadcode`内での`OpCopy`のチェックが不要になりました。

これらの変更により、デッドコード削除の正確性と効率が向上し、最終的に生成されるコードの品質がさらに高まります。

### 5. `lower.go`からの`OpCopy`の削除

`src/cmd/compile/internal/ssa/lower.go`では、`checkLower`関数内の`switch v.Op`文から`OpCopy`が削除されています。これは、`OpCopy`が`deadcode`フェーズで処理されるようになったため、`lower`フェーズで特別に扱う必要がなくなったことを示しています。

## コアとなるコードの解説

このコミットの核心は、GoコンパイラのSSAバックエンドにおける比較処理の最適化とデッドコード削除の改善です。

### 比較処理の最適化

最も重要な変更は、**新しい定数フラグオペコード**の導入と、それらを用いた**定数畳み込み**です。

例えば、`src/cmd/compile/internal/ssa/gen/AMD64.rules`の以下のルールを見てみましょう。

```
// Constant comparisons.
(CMPQconst (MOVQconst [x]) [y]) && x==y -> (FlagEQ)
(CMPQconst (MOVQconst [x]) [y]) && x<y && uint64(x)<uint64(y) -> (FlagLT_ULT)
...
```

これは、「もし`CMPQconst`（64ビット定数比較）の左オペランドが`MOVQconst`（64ビット定数ロード）で、その値が`x`であり、`CMPQconst`の右オペランドが定数`y`である場合」という条件で、さらに「`x`と`y`が等しいならば、結果は`FlagEQ`オペコードに置き換える」ということを意味します。

これにより、例えばGoのコードで`if 5 == 5`のような比較があった場合、コンパイラはこれを実行時に`CMP`命令を発行してフラグを設定するのではなく、コンパイル時に直接`FlagEQ`という内部表現に変換します。

さらに、これらの定数フラグは、それを利用する命令に伝播されます。

```
// Absorb flag constants into branches.
(EQ (FlagEQ) yes no) -> (First nil yes no)
...
```

これは、「もし`EQ`（等しい場合に分岐）ブロックの制御値が`FlagEQ`である場合、そのブロックを`First`ブロック（常に`yes`パスに分岐する）に置き換える」というルールです。つまり、`if 5 == 5 { ... }`というコードは、`5 == 5`が常に真であるため、`if`文全体が`{ ... }`のブロックに無条件にジャンプする形に最適化されます。これにより、実行時の条件分岐のオーバーヘッドが完全に排除されます。

同様に、`SETcc`命令も定数に畳み込まれます。

```
// Absorb flag constants into SETxx ops.
(SETEQ (FlagEQ)) -> (MOVBconst [1])
...
```

これは、「もし`SETEQ`（等しい場合に1を設定）命令の引数が`FlagEQ`である場合、その命令を`MOVBconst [1]`（バイト値1をロード）に置き換える」ことを意味します。これにより、比較結果をブール値としてレジスタに格納する処理が、単なる定数ロードに簡略化されます。

### デッドコード削除の改善

`deadcode.go`の変更は、SSA最適化パスの堅牢性と効率を向上させます。特に、`Phi`ノードの強度低下によって生成される`OpCopy`オペレーションの適切な処理が重要です。

以前の`deadcode`関数は、到達可能なブロックとライブな値の計算を一緒に行っていました。しかし、`OpCopy`が`Phi`ノードの強度低下によって導入されると、その`OpCopy`がライブネス解析の前に除去されないと、誤ったライブネス情報に基づいてデッドコードが残存する可能性がありました。

新しいロジックでは、以下の順序で処理が行われます。

1.  `reachableBlocks(f)`: まず、到達可能なブロックのみを正確に特定します。
2.  `copyelim(f)`: 次に、`copyelim.go`で定義されているコピー除去パスを実行します。これにより、`OpCopy`オペレーションが削除され、値のコピー元が直接使用されるように書き換えられます。このステップは、ライブネス解析の前に実行されることが重要です。
3.  `liveValues(f, reachable)`: 最後に、更新されたグラフ構造に基づいてライブな値を計算します。

この順序の変更により、`OpCopy`がライブネス解析に影響を与えることなく除去され、より正確で効率的なデッドコード削除が可能になります。結果として、生成されるバイナリのサイズが小さくなり、実行速度が向上する可能性があります。

これらの変更は、Goコンパイラがより高度な最適化を実行し、開発者が記述したコードの意図を損なうことなく、より効率的な機械語を生成するための重要なステップです。

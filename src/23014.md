# [インデックス 23014] ファイルの概要

このコミットは、Goランタイムの初期化に関するアセンブリコード、具体的には `src/runtime/rt0_linux_386.s` と `src/runtime/rt0_linux_amd64.s` に変更を加えるものです。これらのファイルは、Linuxシステム上でGoプログラムが起動する際の最初のエントリポイントとなるアセンブリルーチンを含んでおり、それぞれ32ビット(i386)と64ビット(x86-64)アーキテクチャに対応しています。特に、`_rt0_linux_lib` というシンボルは、GoコードがC言語から呼び出し可能な共有ライブラリとしてビルドされた際（`-buildmode=c-shared`）、ライブラリがロードされたときにCコードから呼び出されるエントリポイントとして機能します。

## コミット

Goランタイムにおいて、Linuxの32ビット(386)および64ビット(amd64)アーキテクチャ向けの共有ライブラリのエントリポイントで、被呼び出し側保存レジスタ（callee-saved registers）を明示的に保存するように修正しました。これにより、C言語の呼び出し規約に準拠し、特にC言語のシステムライブラリからGoの共有ライブラリが呼び出される際に、レジスタの状態が正しく維持されるようになります。

## 変更の背景

この変更の背景には、Go言語のプログラムをC言語から利用できる共有ライブラリ（`.so`ファイルなど）としてビルドする際の、異なる言語間の呼び出し規約の不一致があります。

Go言語には `-buildmode=c-shared` というビルドモードがあり、これを使用するとGoのパッケージをC言語のコードからリンクして呼び出すことができる共有ライブラリとしてコンパイルできます。このモードでビルドされたライブラリは、C言語のシステムライブラリなど、外部のCコードからロードされ、そのエントリポイントが呼び出される可能性があります。

問題は、C言語の標準的な呼び出し規約（特にLinuxのSystem V ABI）とGo言語の内部的な呼び出し規約が、レジスタの使用方法に関して異なる点にありました。C言語の呼び出し規約では、特定のレジスタ（被呼び出し側保存レジスタ、callee-saved registers）は、呼び出された関数がその値を変更する前に保存し、関数から戻る前に復元することが義務付けられています。これにより、呼び出し元の関数は、これらのレジスタに保存された値が関数呼び出しによって破壊されないことを期待できます。

一方、Go言語の内部的な呼び出し規約では、通常、被呼び出し側保存レジスタという概念がありません。Goの関数は、ほとんどのレジスタを自由に利用でき、レジスタの保存は呼び出し側の責任となります。

通常、GoとCの間の相互運用は `cgo` ツールによって仲介されます。`cgo` は、CからGoへの呼び出しが行われる際に、Cの呼び出し規約に従ってレジスタを保存し、Goの関数が実行された後にそれらを復元するブリッジコードを生成します。これにより、Goの関数がCの呼び出し規約に準拠していない場合でも、Cコードからは問題なくGoの関数を呼び出すことができます。

しかし、このコミットが修正しようとしているのは、`_rt0_linux_lib` のようなGoランタイムの初期エントリポイントが、`cgo` の完全な仲介なしにCコードから直接呼び出される可能性のある「非cgoパス」が存在したことです。このような場合、Goのランタイムコード自体がCの呼び出し規約に従って被呼び出し側保存レジスタを保存・復元しなければ、Cコードが期待するレジスタの状態が破壊され、予期せぬ動作やクラッシュを引き起こす可能性がありました。

既存のテストがこの問題を検出できなかったのは、テストケースが主に `cgo` を介したパスをカバーしており、そのパスでは `cgo` が自動的にレジスタの保存を行っていたためです。しかし、特定の「非cgoパス」ではこの保護がなく、実際の運用環境で問題が発生する可能性があったため、この修正が必要とされました。

## 前提知識の解説

### Goのビルドモード `c-shared`

Go言語の `go build` コマンドには、`-buildmode` オプションがあります。このオプションの一つである `c-shared` は、GoのパッケージをC言語から呼び出し可能な共有ライブラリ（Linuxでは `.so`、macOSでは `.dylib`、Windowsでは `.dll`）としてコンパイルするために使用されます。これにより、Goで書かれたロジックを既存のC/C++アプリケーションや、C言語のABI（Application Binary Interface）をサポートする他の言語から利用できるようになります。

### 呼び出し規約 (Calling Convention)

呼び出し規約とは、関数が呼び出される際に、引数をどのように渡し、戻り値をどのように受け取り、レジスタをどのように使用するかといった、関数呼び出しに関する取り決めです。CPUアーキテクチャやオペレーティングシステムによって異なる規約が存在します。

*   **引数の渡し方**: レジスタ経由、またはスタック経由。
*   **戻り値の受け取り方**: レジスタ経由、またはスタック経由。
*   **スタックの管理**: 呼び出し側がスタックをクリーンアップするか、被呼び出し側がクリーンアップするか。
*   **レジスタの保存**: 呼び出し側が保存すべきレジスタ（caller-saved registers）と、被呼び出し側が保存すべきレジスタ（callee-saved registers）の区別。

### 呼び出し側保存レジスタ (Caller-saved registers) と被呼び出し側保存レジスタ (Callee-saved registers)

これは呼び出し規約におけるレジスタの役割分担に関する重要な概念です。

*   **呼び出し側保存レジスタ (Caller-saved registers)**:
    *   これらのレジスタは、呼び出された関数がその値を自由に上書きできると見なされます。
    *   もし呼び出し元の関数が、関数呼び出し後もこれらのレジスタの値を保持したい場合、関数を呼び出す前に**呼び出し元自身が**これらのレジスタの値をスタックなどに保存し、関数から戻った後に復元する必要があります。
    *   例: x86-64 Linux ABIにおける `%rax`, `%rcx`, `%rdx`, `%rsi`, `%rdi`, `%r8`-`%r11` など。

*   **被呼び出し側保存レジスタ (Callee-saved registers)**:
    *   これらのレジスタは、呼び出された関数がその値を変更してはならないと見なされます。
    *   もし呼び出された関数が、内部処理のためにこれらのレジスタを使用する必要がある場合、関数エントリ時に**被呼び出し側自身が**これらのレジスタの値をスタックなどに保存し、関数から戻る直前に元の値を復元する必要があります。
    *   これにより、呼び出し元の関数は、これらのレジスタに保存された値が関数呼び出しによって破壊されないことを保証されます。
    *   例: x86-64 Linux ABIにおける `%rbp`, `%rbx`, `%r12`, `%r13`, `%r14`, `%r15` など。32ビットx86 Linux ABIにおける `%ebx`, `%ebp`, `%esi`, `%edi` など。

Go言語の内部的な呼び出し規約は、パフォーマンスのために被呼び出し側保存レジスタの概念を持たないことが多いです。これは、Goのコンパイラがレジスタ割り当てを最適化する際に、レジスタの保存・復元のオーバーヘッドを最小限に抑えるためです。しかし、C言語のABIに準拠する必要がある場合には、この違いが問題となります。

### Goのランタイム初期化 (`rt0_linux_386.s`, `rt0_linux_amd64.s`)

Goプログラムが実行を開始する際、最初に実行されるのはアセンブリ言語で書かれたランタイム初期化コードです。`rt0_linux_386.s` と `rt0_linux_amd64.s` は、それぞれLinuxの32ビットおよび64ビットシステムにおけるこの初期化処理を担当します。これらのファイルには、OSから制御が渡された直後に実行されるエントリポイント（例: `_rt0_386_linux` や `_rt0_amd64_linux`）が含まれており、スタックの設定、Goランタイムの初期化、そして最終的にGoの `main` 関数へのジャンプといった一連の処理を行います。

特に、`_rt0_linux_lib` というシンボルは、Goが共有ライブラリとしてビルドされた際に、C言語のコードからGoランタイムの初期化を開始するために呼び出されるエントリポイントです。

### cgo

`cgo` は、Go言語とC言語のコードを相互に呼び出すためのGoツールチェーンの一部です。`cgo` を使用すると、GoのコードからCの関数を呼び出したり、CのコードからGoの関数を呼び出したりできます。`cgo` は、異なる言語間の呼び出し規約の違いを吸収するためのブリッジコードを生成する重要な役割を担っています。CからGoへの呼び出しの場合、`cgo` はCの呼び出し規約に従って引数を渡し、必要に応じてレジスタを保存・復元し、Goの関数が実行できるように環境を整えます。

## 技術的詳細

このコミットは、Goの共有ライブラリがCコードからロードされる際のエントリポイントである `_rt0_386_linux_lib` および `_rt0_amd64_linux_lib` において、被呼び出し側保存レジスタを明示的に保存・復元する処理を追加します。

### 32ビット (i386) アーキテクチャ (`rt0_linux_386.s`)

Linuxの32ビットx86 ABIでは、`%ebx`, `%ebp`, `%esi`, `%edi` が被呼び出し側保存レジスタです。
変更前は、`_rt0_386_linux_lib` はスタックフレームサイズを `$12` と指定していましたが、変更後は `$0` に変更され、代わりに明示的な `PUSHL` 命令でレジスタを保存しています。

*   **変更前**:
    ```assembly
    TEXT _rt0_386_linux_lib(SB),NOSPLIT,$12
    	MOVL	16(SP), AX
    	MOVL	AX, _rt0_386_linux_lib_argc<>(SB)
    	MOVL	20(SP), AX
    	MOVL	AX, _rt0_386_linux_lib_argv<>(SB)
    	// ...
    	RET
    ```
    ここでは、`16(SP)` や `20(SP)` のようにスタックポインタからのオフセットで引数を取得しており、これはCの呼び出し規約に従っていますが、被呼び出し側保存レジスタの明示的な保存は行われていませんでした。

*   **変更後**:
    ```assembly
    TEXT _rt0_386_linux_lib(SB),NOSPLIT,$0
    	PUSHL	BP  // %ebp
    	MOVL	SP, BP
    	PUSHL	BX  // %ebx
    	PUSHL	SI  // %esi
    	PUSHL	DI  // %edi

    	MOVL	8(BP), AX   // argc
    	MOVL	AX, _rt0_386_linux_lib_argc<>(SB)
    	MOVL	12(BP), AX  // argv
    	MOVL	AX, _rt0_386_linux_lib_argv<>(SB)

    	SUBL	$8, SP // スタックアライメントまたは一時的な領域確保

    	// ...
    	JMP	restore // 処理の最後にレジスタを復元するルーチンへジャンプ

    nocgo:
    	// ...
    restore:
    	ADDL	$8, SP
    	POPL	DI
    	POPL	SI
    	POPL	BX
    	POPL	BP
    	RET
    ```
    `PUSHL` 命令は、指定されたレジスタの値をスタックにプッシュします。これにより、`%ebp`, `%ebx`, `%esi`, `%edi` の値が保存されます。引数の取得も `BP` (ベースポインタ) からのオフセットに変更されています。
    `JMP restore` は、`cgo_sys_thread_create` が成功した場合でも失敗した場合（`nocgo` パス）でも、必ず `restore` ラベルにジャンプして保存したレジスタを `POPL` 命令で復元し、`RET` で呼び出し元に戻ることを保証します。

### 64ビット (x86-64) アーキテクチャ (`rt0_linux_amd64.s`)

Linuxの64ビットx86-64 ABIでは、`%rbx`, `%rbp`, `%r12`, `%r13`, `%r14`, `%r15` が被呼び出し側保存レジスタです。
変更前は、`_rt0_amd64_linux_lib` はスタックフレームサイズを `$40` と指定していましたが、変更後は `$0x58` に変更され、明示的な `MOVQ` 命令でレジスタをスタックに保存しています。

*   **変更前**:
    ```assembly
    TEXT _rt0_amd64_linux_lib(SB),NOSPLIT,$40
    	MOVQ	DI, _rt0_amd64_linux_lib_argc<>(SB)
    	MOVQ	SI, _rt0_amd64_linux_lib_argv<>(SB)
    	// ...
    	RET
    ```
    `%rdi` と `%rsi` はCの呼び出し規約で引数に使われるレジスタであり、これらは呼び出し側保存レジスタなので、ここでは保存の必要はありませんでした。

*   **変更後**:
    ```assembly
    TEXT _rt0_amd64_linux_lib(SB),NOSPLIT,$0x58
    	MOVQ	BX, 0x18(SP)  // %rbx
    	MOVQ	BP, 0x20(SP)  // %rbp
    	MOVQ	R12, 0x28(SP) // %r12
    	MOVQ	R13, 0x30(SP) // %r13
    	MOVQ	R14, 0x38(SP) // %r14
    	MOVQ	R15, 0x40(SP) // %r15

    	MOVQ	DI, _rt0_amd64_linux_lib_argc<>(SB)
    	MOVQ	SI, _rt0_amd64_linux_lib_argv<>(SB)

    	// ...
    	JMP	restore // 処理の最後にレジスタを復元するルーチンへジャンプ

    nocgo:
    	// ...
    restore:
    	MOVQ	0x18(SP), BX
    	MOVQ	0x20(SP), BP
    	MOVQ	0x28(SP), R12
    	MOVQ	0x30(SP), R13
    	MOVQ	0x38(SP), R14
    	MOVQ	0x40(SP), R15
    	RET
    ```
    `MOVQ` 命令は、64ビットのクワッドワードをレジスタとメモリ間で移動させます。ここでは、被呼び出し側保存レジスタの値をスタックの特定のオフセットに保存しています。
    同様に、`JMP restore` を使用して、処理の最後に必ずレジスタを復元するルーチンにジャンプします。

この修正により、Goの共有ライブラリがCコードから呼び出される際に、Cの呼び出し規約で期待されるレジスタの保存が確実に行われるようになり、異なる言語間の相互運用における安定性が向上しました。

## コアとなるコードの解説

### 32ビット (i386) の変更点

*   `TEXT _rt0_386_linux_lib(SB),NOSPLIT,$12` から `TEXT _rt0_386_linux_lib(SB),NOSPLIT,$0` へ変更:
    *   これは、Goのアセンブリにおけるスタックフレームサイズの宣言です。以前は `$12` バイトのスタックフレームを確保していましたが、変更後は `$0` になっています。これは、レジスタの保存を明示的な `PUSHL` 命令で行うため、Goのアセンブリが自動的にスタックフレームを確保する必要がなくなったことを示唆しています。
*   `PUSHL BP`, `PUSHL BX`, `PUSHL SI`, `PUSHL DI`:
    *   これらは、Linux 32ビットABIにおける被呼び出し側保存レジスタ (`%ebp`, `%ebx`, `%esi`, `%edi`) をスタックにプッシュ（保存）する命令です。これにより、Cコードが期待するレジスタの状態が維持されます。
*   `MOVL SP, BP`:
    *   ベースポインタ (`%ebp`) を現在のスタックポインタ (`%esp`) に設定します。これは、スタックフレームの基準点を設定する一般的な慣習です。
*   `MOVL 8(BP), AX` と `MOVL 12(BP), AX`:
    *   引数 (`argc` と `argv`) をスタック上のベースポインタからのオフセットで取得するように変更されています。これは、レジスタをプッシュしたことでスタックのレイアウトが変わったため、引数の位置も調整されたことを意味します。
*   `SUBL $8, SP`:
    *   スタックポインタを8バイト減らしています。これは、スタックアライメントのため、または一時的な作業領域を確保するためと考えられます。
*   `RET` から `JMP restore` へ変更:
    *   以前は `RET` で直接呼び出し元に戻っていましたが、`JMP restore` に変更されました。これは、`cgo_sys_thread_create` の呼び出しが成功したか失敗したか（`nocgo` パス）に関わらず、必ず `restore` ラベルにジャンプしてレジスタの復元処理を実行することを保証するためです。
*   `restore:` ラベルと `ADDL $8, SP`, `POPL DI`, `POPL SI`, `POPL BX`, `POPL BP`:
    *   `restore` ラベルは、保存されたレジスタを復元するためのルーチンの開始点です。
    *   `ADDL $8, SP` は、`SUBL $8, SP` で確保したスタック領域を解放します。
    *   `POPL` 命令は、スタックから値をポップして指定されたレジスタにロード（復元）します。これにより、関数エントリ時に保存された被呼び出し側保存レジスタが元の値に戻されます。

### 64ビット (x86-64) の変更点

*   `TEXT _rt0_amd64_linux_lib(SB),NOSPLIT,$40` から `TEXT _rt0_amd64_linux_lib(SB),NOSPLIT,$0x58` へ変更:
    *   同様に、スタックフレームサイズが `$40` (10進数で64) から `$0x58` (10進数で88) に変更されています。これは、64ビットレジスタを保存するために必要なスタック領域が増加したためです。
*   `MOVQ BX, 0x18(SP)`, `MOVQ BP, 0x20(SP)`, `MOVQ R12, 0x28(SP)`, `MOVQ R13, 0x30(SP)`, `MOVQ R14, 0x38(SP)`, `MOVQ R15, 0x40(SP)`:
    *   これらは、Linux 64ビットABIにおける被呼び出し側保存レジスタ (`%rbx`, `%rbp`, `%r12`, `%r13`, `%r14`, `%r15`) の値をスタックの特定のオフセットに保存する命令です。`MOVQ` は64ビットの値を移動させます。
*   `RET` から `JMP restore` へ変更:
    *   32ビット版と同様に、`JMP restore` を使用して、必ずレジスタの復元処理が実行されるようにしています。
*   `restore:` ラベルと `MOVQ 0x18(SP), BX` など:
    *   `restore` ラベルは、保存されたレジスタを復元するためのルーチンの開始点です。
    *   `MOVQ` 命令で、スタックの特定のオフセットから値をロードして、対応するレジスタに復元します。

これらの変更は、Goの共有ライブラリがC言語の環境に組み込まれる際に、Cの呼び出し規約に厳密に準拠し、レジスタの状態を正しく管理するための重要な修正です。これにより、GoとCの間の相互運用における堅牢性と信頼性が向上します。

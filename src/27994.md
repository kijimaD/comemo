## 元コミット内容

Goランタイムのトレース機能において、破損したタイムスタンプの検出をテストする。

一部のプロセッサでは、トレースタイムスタンプの生成に使用される`cputicks`が非単調なタイムスタンプを生成することがある。パーサーが、論理的に矛盾するトレース（例：イベントの欠落、過剰、順序の誤り）と破損したタイムスタンプを区別することが重要である。前者はトレーサーのバグであり、後者はマシン側の問題である。

このコミットでは、以下の点をテストする。(1) 破損したタイムスタンプの場合でもパーサーが論理エラーを返さないこと、(2) 破損したタイムスタンプが最終的に検出され、報告されること。

## 変更の背景

Goのランタイムトレーサーは、プログラムの実行状況を詳細に記録し、パフォーマンス分析に役立つ情報を提供します。このトレーサーが生成するイベントには、それぞれタイムスタンプが付与されており、これらのタイムスタンプはイベントの順序を正確に反映している必要があります。通常、タイムスタンプはCPUのサイクルカウンタ（`cputicks`）などのハードウェア機能を利用して取得されます。

しかし、一部のプロセッサ環境では、`cputicks`が常に単調増加するタイムスタンプを生成するとは限りません。例えば、CPUの周波数スケーリング、省電力機能、またはマルチコア環境での同期の問題などにより、タイムスタンプが過去に戻ったり、同じ値が連続したりする「非単調なタイムスタンプ」が発生することがあります。

このような非単調なタイムスタンプが発生した場合、トレースパーサーはこれをどのように扱うべきかという問題が生じます。
1.  **トレーサーの論理的なバグ**: イベントが欠落している、過剰に記録されている、またはイベントの順序が根本的に間違っているなど、トレーサー自体の実装に問題がある場合。これは修正すべきソフトウェアのバグです。
2.  **マシン側の問題**: `cputicks`のようなハードウェア由来のタイムスタンプが、プロセッサの特性により非単調になる場合。これはトレーサーのバグではなく、実行環境の特性に起因するものです。

このコミットの背景にあるのは、「パーサーがこれら二つのケースを明確に区別できるべきである」という考えです。もしパーサーが非単調なタイムスタンプをトレーサーの論理バグとして誤って報告してしまうと、開発者は存在しないバグをデバッグすることになり、時間の無駄が生じます。そのため、パーサーは破損したタイムスタンプを論理エラーとは異なる形で検出し、報告するメカニズムを持つ必要があります。

この変更は、このような状況をシミュレートし、パーサーの堅牢性を検証するためのテストを追加することを目的としています。

## 前提知識の解説

### Goランタイムトレーサー (Go Runtime Tracer)

Goランタイムトレーサーは、Goプログラムの実行中に発生する様々なイベント（ガーベージコレクション、ゴルーチンのスケジューリング、システムコールなど）を記録するプロファイリングツールです。生成されたトレースファイルは、`go tool trace`コマンドで可視化され、プログラムのパフォーマンスボトルネックや並行処理の問題を特定するのに役立ちます。トレースイベントには、イベントの種類、関連するゴルーチンID、そしてイベントが発生した時刻を示すタイムスタンプが含まれます。

### cputicks

`cputicks`は、CPUのタイムスタンプカウンタ（TSC: Time Stamp Counter）から取得されることが多い、CPUサイクル数を表す値です。これは非常に高精度な時間計測に利用されますが、前述の通り、一部の環境では非単調になる可能性があります。Goランタイムトレーサーは、イベントのタイムスタンプとしてこの`cputicks`のような高精度なカウンタを利用しています。

### 単調増加 (Monotonic) タイムスタンプ

単調増加するタイムスタンプとは、時間が進むにつれて常に値が増加するか、少なくとも同じ値を保ち、過去に戻ることがないタイムスタンプのことです。トレースイベントの順序性を保証するためには、タイムスタンプが単調であることが非常に重要です。非単調なタイムスタンプは、イベントの順序が乱れているように見せかけ、トレース解析を困難にします。

### トレース解析における論理エラーとマシン側の問題の区別

トレースデータは、プログラムの実行パスを再構築するために使用されます。イベントの順序が乱れている場合、それは通常、トレーサーがイベントを誤って記録したか、イベントが失われたか、またはイベントが間違った順序で処理されたことを意味します。これらは「論理エラー」であり、トレーサーのバグを示唆します。

しかし、タイムスタンプ自体がハードウェアの制約によって非単調である場合、これはトレーサーの論理とは無関係な「マシン側の問題」です。パーサーは、この二つの異なる種類の問題を区別し、それぞれに応じた適切なエラー報告を行う必要があります。論理エラーは開発者が修正すべきバグであり、マシン側の問題は環境の特性として認識し、可能であれば対処（例：タイムスタンプの補正）するか、少なくとも誤ったバグ報告を避けるべきです。

## 技術的詳細

このコミットの主要な技術的詳細は、Goランタイムトレーサーのパーサーが、意図的に破損させたタイムスタンプをどのように処理するかをテストするメカニズムの導入にあります。

1.  **`BreakTimestampsForTesting`フラグの導入**:
    `src/internal/trace/parser.go`に`var BreakTimestampsForTesting bool`というグローバル変数が追加されました。このフラグが`true`に設定されると、パーサーはトレースイベントのタイムスタンプをランダムに改変します。これにより、非単調なタイムスタンプが意図的に生成され、テスト環境で実際のプロセッサの挙動をシミュレートできます。

2.  **タイムスタンプのランダムな改変**:
    `parseEvents`関数内で`BreakTimestampsForTesting`が`true`の場合、既存のイベントバッチからランダムに選択されたイベントのタイムスタンプが、`rand.Intn(2000) - 1000`の範囲で加算されます。これは、タイムスタンプを最大で1000ティック進めたり、1000ティック戻したりすることを意味し、非単調性を引き起こします。この操作は複数回（例: 5回）行われ、複数のイベントでタイムスタンプの破損が発生するようにします。

3.  **テストにおけるパーサーの挙動検証**:
    `src/runtime/trace/trace_test.go`に`testBrokenTimestamps`関数が追加されました。この関数は、まず正常なトレースデータを生成し、そのデータを基に`BreakTimestampsForTesting`を`true`に設定して`trace.Parse`を呼び出します。
    -   **期待される挙動 (1)**: パーサーは、破損したタイムスタンプに遭遇しても、`trace.ErrTimeOrder`という特定のエラーを返すことで、論理的な矛盾ではなくタイムスタンプの順序の問題であることを示します。これは、トレーサーのバグを示す一般的なエラー（例：`t.Fatalf`で報告されるようなエラー）とは区別されます。
    -   **期待される挙動 (2)**: `trace.ErrTimeOrder`が返されることで、破損したタイムスタンプが最終的に検出され、報告されることを確認します。テストは、このエラーが返されるまで複数回（例: 10,000回）試行し、ランダムなタイムスタンプ破損が確実に検出されることを保証します。

4.  **`parseTrace`関数の変更**:
    `src/runtime/trace/trace_test.go`内の`parseTrace`関数は、エラーハンドリングが変更されました。以前は`trace.Parse`がエラーを返した場合、そのエラーを呼び出し元に返していましたが、変更後は`trace.ErrTimeOrder`の場合はスキップし、それ以外のエラーの場合は`t.Fatalf`でテストを失敗させるようになりました。これにより、タイムスタンプの順序エラーは許容されるが、他の種類のパースエラーは許容されないという挙動が明確になります。

これらの変更により、Goランタイムのトレースパーサーが、ハードウェア由来の非単調なタイムスタンプと、トレーサーの論理的なバグによるトレースの矛盾を適切に区別し、それぞれに応じたエラー報告を行う能力が向上します。これは、トレースツールの堅牢性と診断能力を高める上で重要な改善です。

### `src/internal/trace/parser.go`

-   **`BreakTimestampsForTesting`変数の追加**:
    ```go

    var BreakTimestampsForTesting bool
    ```
    このブール型変数が追加され、テスト時にタイムスタンプを意図的に破損させるかどうかを制御します。
-   **`parseEvents`関数内のタイムスタンプ改変ロジック**:
    `parseEvents`関数内に以下のコードブロックが追加されました。
    ```go
    	if BreakTimestampsForTesting {
    		var batchArr [][]*Event
    		for _, batch := range batches {
    			batchArr = append(batchArr, batch)
    		}
    		for i := 0; i < 5; i++ {
    			batch := batchArr[rand.Intn(len(batchArr))]
    			batch[rand.Intn(len(batch))].Ts += int64(rand.Intn(2000) - 1000)
    		}
    	}
    ```
    `BreakTimestampsForTesting`が`true`の場合、イベントのバッチからランダムに5つのイベントを選び、そのタイムスタンプ（`Ts`フィールド）を-1000から+999の範囲でランダムに増減させます。

    `parseTrace`関数は、もはやエラーを返さず、`trace.ErrTimeOrder`の場合はテストをスキップし、それ以外のエラーの場合は`t.Fatalf`でテストを終了させるようになりました。
-   **`testBrokenTimestamps`関数の追加**:
    ```go
    func testBrokenTimestamps(t *testing.T, data []byte) {
    	// On some processors cputicks (used to generate trace timestamps)
    	// produce non-monotonic timestamps. It is important that the parser
    	// distinguishes logically inconsistent traces (e.g. missing, excessive
    	// or misordered events) from broken timestamps. The former is a bug
    	// in tracer, the latter is a machine issue.
    	// So now that we have a consistent trace, test that (1) parser does
    	// not return a logical error in case of broken timestamps
    	// and (2) broken timestamps are eventually detected and reported.
    	trace.BreakTimestampsForTesting = true
    	defer func() {
    		trace.BreakTimestampsForTesting = false
    	}()
    	for i := 0; i < 1e4; i++ {
    		_, err := trace.Parse(bytes.NewReader(data), "")
    		if err == trace.ErrTimeOrder {
    			return
    		}
    		if err != nil {
    			t.Fatalf("failed to parse trace: %v", err)
    		}
    	}
    }
    ```
    この新しいテスト関数は、`BreakTimestampsForTesting`を`true`に設定し、ループ内で`trace.Parse`を呼び出して、`trace.ErrTimeOrder`が返されることを期待します。

## コアとなるコードの解説

このコミットの核となるのは、Goランタイムトレーサーのパーサーが、非単調なタイムスタンプを適切に処理できることを保証するためのテストメカニズムです。

1.  **`BreakTimestampsForTesting`フラグ**:
    `src/internal/trace/parser.go`に追加された`BreakTimestampsForTesting`は、テスト専用のフックです。このフラグが`true`になると、`parseEvents`関数内でトレースイベントのタイムスタンプが意図的に改変されます。これは、実際のプロセッサで発生しうる非単調な`cputicks`の挙動をシミュレートするためのものです。ランダムな値（-1000から+999）を加算することで、タイムスタンプが過去に戻ったり、順序が入れ替わったりする状況を作り出します。これにより、パーサーがこのような「破損した」タイムスタンプに遭遇したときに、どのように反応するかを検証できます。

2.  **`parseTrace`関数のエラーハンドリングの変更**:
    `src/runtime/trace/trace_test.go`内の`parseTrace`関数は、以前は`trace.Parse`が返す全てのエラーを呼び出し元に伝播していました。しかし、この変更により、`trace.ErrTimeOrder`という特定のエラーコードが返された場合は、テストをスキップするようになりました。これは、`trace.ErrTimeOrder`がタイムスタンプの順序が不正であることを示すエラーであり、このテストの目的が「タイムスタンプが破損していても論理エラーとして扱わない」ことにあるためです。他の種類のエラー（例：トレースファイルの破損など）は引き続き`t.Fatalf`でテストを失敗させ、トレーサーのバグとして扱われます。この区別が、論理エラーとマシン側の問題の分離において重要です。

3.  **`testBrokenTimestamps`関数の導入**:
    この新しいテスト関数は、以下の2つの主要な目的を持っています。
    -   **論理エラーではないことの確認**: `BreakTimestampsForTesting`を`true`に設定し、意図的にタイムスタンプを破損させたトレースデータを`trace.Parse`に渡します。このとき、パーサーが`trace.ErrTimeOrder`を返すことを期待します。もし`trace.ErrTimeOrder`以外のエラー（例えば、トレースの構造が不正であるといった論理エラー）が返された場合、それはパーサーがタイムスタンプの破損を論理エラーと誤認していることを意味し、テストは失敗します。
    -   **破損の検出と報告の確認**: `trace.ErrTimeOrder`が返されることで、パーサーが非単調なタイムスタンプを正しく検出し、その問題を報告していることを確認します。ループ内で複数回（10,000回）試行するのは、ランダムなタイムスタンプ改変が確実に発生し、検出されることを保証するためです。

これらの変更により、Goランタイムのトレースシステムは、より堅牢になり、異なる種類の問題（トレーサーのバグ vs. ハードウェアの特性）をより正確に診断できるようになります。これは、Goプログラムのデバッグとパフォーマンスチューニングの信頼性を高める上で重要なステップです。

# [インデックス 25232] ファイルの概要

このコミットは、Go言語の標準ライブラリ `compress/flate` パッケージにおいて、`ReadError` および `WriteError` 型を非推奨（deprecated）とする変更を導入しています。これらのエラー型は、IO操作中に発生したエラーをラップするために設計されていましたが、実際にはほとんど使用されず、むしろエラーハンドリングを複雑にしていたため、削除されました。

## コミット

```
compress/flate: deprecate ReadError and WriteError

A vast majority of the time, ReadError isn't even returned during
IO operations. Instead, an unwrapped error will be returned because
of the ReadByte call on L705. Because DEFLATE streams are primarily
compressed and require byte for byte Huffman decoding, most of the
data read from a data stream will go through ReadByte.

Although this is technically an API change, any user reliant on
this error would not have worked properly anyways due to the fact
that most IO error are not wrapped. We might as well deprecate
ReadError. It is useless and actually makes clients that do
depend on catching IO errors more difficult.

Fixes #11856
Fixes #12724

Change-Id: Ib5fec5ae215e977c4e85de5701ce6a473d400af8
Reviewed-on: https://go-review.googlesource.com/14834
Reviewed-by: Nigel Tao <nigeltao@golang.org>
```

## 元コミット内容

`compress/flate` パッケージ内の `ReadError` および `WriteError` 型を非推奨とします。これらのエラー型は、IO操作中にほとんど返されず、特に `ReadByte` 呼び出しによってラップされていないエラーが返されることが多いため、実用性が低いと判断されました。DEFLATEストリームの処理では、バイトごとのハフマンデコードが必要なため、データの大部分が `ReadByte` を介して読み込まれます。この変更は技術的にはAPI変更ですが、これらのエラーに依存していたユーザーは元々正しく機能していなかったため、非推奨とすることで、IOエラーのキャッチに依存するクライアントのエラーハンドリングを簡素化します。

## 変更の背景

このコミットの背景には、Go言語のエラーハンドリングの設計思想と、`compress/flate` パッケージにおける特定の実装上の問題があります。

Go言語では、エラーは `error` インターフェースによって表現され、通常は関数から直接エラー値を返すことで処理されます。エラーをラップする（つまり、元のエラーを内包する新しいエラー型を作成する）パターンも存在しますが、このコミットが作成された2015年時点では、Goのエラーラッピングのメカニズムは現在（Go 1.13以降の `fmt.Errorf` の `%w` 動詞など）ほど洗練されていませんでした。

`compress/flate` パッケージでは、`ReadError` と `WriteError` というカスタムエラー型が定義されており、これらはIO操作中に発生した基底のエラー（`Err` フィールド）と、エラーが発生したオフセット（`Offset` フィールド）を保持するように設計されていました。これは、エラー発生時の詳細なコンテキストを提供することを目的としていました。

しかし、コミットメッセージが指摘するように、実際にはこれらのカスタムエラー型が期待通りに機能していませんでした。特に、DEFLATEストリームのデコード処理では、`ReadByte` のような低レベルのIO操作が頻繁に行われます。これらの操作がエラーを返した場合、`ReadError` でラップされることなく、基底のIOエラー（例: `io.EOF`, `io.ErrUnexpectedEOF` など）が直接返されることがほとんどでした。

このため、`ReadError` や `WriteError` に依存してエラーを処理しようとするクライアントコードは、ほとんどの場合、これらのカスタムエラー型を受け取ることができず、期待通りに動作しませんでした。結果として、これらのエラー型は「役に立たない」と判断され、むしろエラーハンドリングを不必要に複雑にする要因となっていました。

この状況を改善し、エラーハンドリングの予測可能性と簡潔さを向上させるために、これらのエラー型を非推奨とし、最終的には削除する方向性が取られました。これにより、ユーザーは直接基底のIOエラーを処理することに集中できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念と `compress/flate` パッケージに関する基本的な知識が必要です。

### Go言語のエラーハンドリング

Go言語では、エラーは組み込みの `error` インターフェースによって表現されます。
```go
type error interface {
    Error() string
}
```
関数は通常、最後の戻り値として `error` 型を返します。エラーが発生しなかった場合は `nil` を返します。
エラーをチェックする一般的なパターンは以下の通りです。
```go
value, err := someFunction()
if err != nil {
    // エラー処理
}
```
このコミットの時点では、エラーを「ラップ」する標準的なメカニズムは存在せず、カスタムエラー型を作成して基底のエラーをフィールドとして持つことが一般的でした。しかし、これはエラーの型アサーション（`if err, ok := err.(*MyError); ok { ... }`）を必要とし、ラップされたエラーが常に期待通りに返されるとは限らないという問題がありました。

### `io.Reader` と `io.Writer` インターフェース

Go言語のIO操作の基本となるインターフェースです。
- `io.Reader`: データを読み込むためのインターフェース。`Read(p []byte) (n int, err error)` メソッドを持ちます。
- `io.Writer`: データを書き込むためのインターフェース。`Write(p []byte) (n int, err error)` メソッドを持ちます。
これらのインターフェースは、ファイル、ネットワーク接続、メモリバッファなど、様々なデータソース/シンクに対して統一されたIO操作を提供します。

### `io.EOF` と `io.ErrUnexpectedEOF`

- `io.EOF`: 入力の終わりに達したことを示すエラー。これは通常、エラーとして扱われるべきではなく、正常な終了条件として扱われます。
- `io.ErrUnexpectedEOF`: 予期しない入力の終わりに達したことを示すエラー。例えば、完全なデータブロックを読み込む前にストリームが終了した場合などに返されます。これは通常、実際の「エラー」として扱われます。

### `compress/flate` パッケージ

`compress/flate` パッケージは、DEFLATE圧縮データ形式（RFC 1951で定義）を実装しています。これは、Zlib、Gzip、PNGなどのより高レベルの圧縮形式の基盤となるアルゴリズムです。
- `flate.NewReader`: DEFLATE圧縮データを読み込む `io.Reader` を作成します。
- `flate.NewWriter`: DEFLATE圧縮データを書き込む `io.Writer` を作成します。
このパッケージは、圧縮データのエンコードとデコードをバイトレベルで処理します。特にデコード（解凍）プロセスでは、ハフマン符号化されたデータをバイトごとに読み取り、解釈する必要があります。

### `ReadByte` 操作

`io.Reader` インターフェースには `ReadByte()` メソッドは直接定義されていませんが、`bufio.Reader` のようなバッファリングされたリーダーは `ReadByte()` メソッドを提供します。DEFLATEデコーダのような低レベルのパーサーは、しばしば `ReadByte()` のような単一バイト読み取り操作を内部的に使用して、ストリームからビットやバイトを抽出します。コミットメッセージが指摘するように、これらの低レベルの読み取り操作がエラーを返した場合、そのエラーは通常、カスタムエラー型でラップされることなく、そのまま上位に伝播されます。

## 技術的詳細

このコミットの技術的な核心は、`compress/flate` パッケージが提供していたカスタムエラー型 `ReadError` と `WriteError` が、Goのエラーハンドリングの現実とDEFLATEデコーダの実装の詳細によって、その意図された目的を果たせていなかったという点にあります。

### `ReadError` と `WriteError` の問題点

1.  **`ReadByte` によるエラーの伝播**: DEFLATEデコーダ（`inflate.go` 内の `decompressor` 構造体）は、圧縮されたバイトストリームを解析するために、内部的に単一バイトを読み取る操作を頻繁に行います。コミットメッセージでは「L705の `ReadByte` 呼び出し」と具体的に言及されていますが、これは `decompressor` が基底の `io.Reader` からバイトを読み取る際の一般的なパターンを指しています。これらの低レベルの `ReadByte` 呼び出しがエラー（例: `io.EOF` や `io.ErrUnexpectedEOF`）を返した場合、そのエラーは `ReadError` でラップされることなく、そのまま呼び出し元に返されていました。
2.  **エラーラッピングの不整合**: `ReadError` は、エラーが発生したオフセット情報 (`Offset`) と基底のエラー (`Err`) を提供することで、より詳細なエラー情報を提供することを目的としていました。しかし、前述の `ReadByte` の問題により、多くのIOエラーが `ReadError` でラップされずに直接返されるため、`ReadError` に依存してエラーを処理しようとするコードは、実際にはほとんどの場合、基底のエラー型を受け取ることになり、期待通りに動作しませんでした。
3.  **クライアントコードの複雑化**: `ReadError` が一貫して返されないため、クライアントコードは `ReadError` の存在を考慮しつつも、ラップされていない基底のエラーも処理する必要がありました。これはエラーハンドリングロジックを不必要に複雑にし、開発者の負担を増やしていました。コミットメッセージは「It is useless and actually makes clients that do depend on catching IO errors more difficult.」と述べており、この点を強調しています。

### 変更による影響

-   **エラーハンドリングの簡素化**: `ReadError` と `WriteError` が非推奨となり、最終的に削除されることで、`compress/flate` パッケージから返されるエラーは、より予測可能になります。ユーザーは、`ReadError` や `WriteError` の存在を考慮することなく、直接 `io.EOF` や `io.ErrUnexpectedEOF`、またはその他の基底のIOエラーを処理できるようになります。
-   **APIの明確化**: 実際には機能していなかったエラー型を非推奨にすることで、APIの意図がより明確になります。
-   **後方互換性**: コミットメッセージは「Although this is technically an API change, any user reliant on this error would not have worked properly anyways」と述べており、この変更が実質的な後方互換性の破壊にはならないと説明しています。なぜなら、これらのエラー型に依存していたコードは、元々正しく機能していなかったためです。

この変更は、Go言語のエラーハンドリングの哲学、すなわち「シンプルさと予測可能性」に沿ったものです。エラーは、その発生源と性質を明確に伝えるべきであり、不必要に複雑なラッピングは避けるべきであるという考え方が反映されています。

## コアとなるコードの解説

### `src/compress/flate/flate_test.go` の変更点

`TestTruncatedStreams` は、途中で切断されたDEFLATEストリームを読み込んだ際の挙動をテストする関数です。以前のコードでは、`io.Copy` から返されたエラーが `*ReadError` 型であるかどうかをチェックし、もしそうであれば、その内部の `ferr.Err` を取り出して `io.ErrUnexpectedEOF` と比較していました。

```go
// 変更前
if ferr, ok := err.(*ReadError); ok {
    err = ferr.Err
}
if err != io.ErrUnexpectedEOF {
    // ...
}
```

この変更により、`ReadError` が非推奨となり、もはや返されないことが保証されるため、この型アサーションとエラーのアンラップ処理は不要になりました。テストコードは、`io.Copy` から直接返されるエラーが `io.ErrUnexpectedEOF` であることを期待するように簡素化されました。これは、`ReadError` が実際に機能していなかったというコミットメッセージの主張を裏付けるものです。

### `src/compress/flate/inflate.go` の変更点

1.  **`Deprecated` コメントの追加**:
    `ReadError` と `WriteError` の構造体定義の直前に `// Deprecated: No longer returned.` というコメントが追加されました。これは、これらの型が将来のバージョンで削除される可能性があり、新規コードでは使用すべきではないことを開発者に明確に伝えます。Goのツールチェーン（例: `go vet`）は、`Deprecated` コメントが付いた要素が使用されている場合に警告を発することがあります。

2.  **エラーラッピングの削除**:
    `decompressor` 構造体の `dataBlock` メソッドと `copyData` メソッドは、DEFLATEストリームのデコード中にエラーが発生した場合に、そのエラーを `f.err` フィールドに設定する役割を担っています。
    変更前は、これらのメソッドは発生したエラー（`err`）を `ReadError` 型でラップしていました。

    ```go
    // 変更前
    f.err = &ReadError{f.roffset, err}
    ```

    変更後は、エラーを `ReadError` でラップする代わりに、基底のエラー `err` を直接 `f.err` に代入するようになりました。

    ```go
    // 変更後
    f.err = err
    ```

    この変更は、`ReadError` が非推奨であるという宣言と直接的に関連しています。もはや `ReadError` を返す必要がないため、デコーダは基底のIOエラーをそのまま伝播させるようになりました。これにより、`compress/flate` パッケージの外部でエラーを処理するコードは、より直接的に `io.EOF` や `io.ErrUnexpectedEOF` などの標準エラーを扱うことができるようになります。

これらの変更は、`compress/flate` パッケージのエラーハンドリングを簡素化し、Goのエラー処理の慣習により合致させることを目的としています。

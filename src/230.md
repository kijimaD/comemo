# [インデックス 230] ファイルの概要

このコミットは、Go言語の初期開発段階において、Goのカスタムオブジェクトファイル形式とシンボルテーブルを理解する新しい`ar`（アーカイバ）ユーティリティを追加するものです。この`ar`ツールは、Plan 9およびInferno OSの`ar`実装をベースにしており、Goのビルドシステムにおける静的ライブラリの作成と管理を可能にします。

## 変更の背景

Go言語は、2007年9月にGoogleで開発が開始され、このコミットが行われた2008年6月は、まだ一般公開前の非常に初期の段階でした。Goの設計目標の一つは、C++やJavaのような既存言語の課題（特に大規模システムにおけるビルド時間の長さや複雑さ）を解決し、シンプルさ、効率性、そして並行処理の強力なサポートを提供することでした。

このような新しい言語とランタイムを構築する上で、堅牢なツールチェインは不可欠です。特に、複数のオブジェクトファイルをまとめて一つのライブラリ（アーカイブファイル）にする`ar`（アーカイバ）ユーティリティは、コンパイルされたコードを再利用可能な形で管理するために必要です。しかし、Goは従来のC/C++コンパイラが生成するELFやCOFFといった標準的なオブジェクトファイル形式とは異なる、独自のカスタムオブジェクトファイル形式を採用していました。

このため、既存の標準的な`ar`ツールではGoのオブジェクトファイルを正しく処理し、特にその内部のシンボルテーブルを理解することができませんでした。Goのリンカがライブラリ内の関数や変数などのシンボルを効率的に解決するためには、`ar`ツールがGo独自のシンボルテーブル構造を認識し、それに基づいてアーカイブ内にシンボルインデックスを生成できる必要がありました。

このコミットは、Goのカスタムオブジェクトファイル形式とシンボルテーブルに対応した専用の`ar`ツールをGoのツールチェインに組み込むことで、この問題を解決し、Goプログラムのビルドとリンクのプロセスを円滑に進めることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が役立ちます。

1.  **`ar`ユーティリティ**: `ar`は「archiver」の略で、Unix系システムで広く使われているコマンドラインユーティリティです。複数のファイルを一つのアーカイブファイル（通常は`.a`拡張子を持つ）にまとめるために使用されます。主に静的ライブラリ（`.lib`や`.a`）を作成する際に利用され、リンカがこれらのライブラリから必要なオブジェクトコードを抽出して実行可能ファイルを生成します。
2.  **オブジェクトファイル**: ソースコードがコンパイラによって機械語に変換された中間ファイルです。通常、`.o`（Unix/Linux）や`.obj`（Windows）といった拡張子を持ちます。オブジェクトファイルには、コンパイルされたコード、データ、そしてシンボルテーブル（後述）や再配置情報などが含まれます。
3.  **シンボルテーブル**: コンパイラやリンカが使用するデータ構造で、プログラム内の識別子（関数名、変数名など）に関する情報（名前、型、スコープ、メモリ上のアドレスなど）を格納します。リンカはシンボルテーブルを参照して、異なるオブジェクトファイル間で定義されたシンボルへの参照を解決し、最終的な実行可能ファイルを生成します。
4.  **Plan 9 / Inferno OS**:
    *   **Plan 9 from Bell Labs**: ベル研究所で開発された分散オペレーティングシステムで、Unixの後継として設計されました。その設計思想は、すべてのリソースをファイルとして扱い、シンプルなプロトコル（Styx）を通じてアクセスするというものです。Go言語の設計者の一人であるRob Pikeは、Plan 9の開発にも深く関わっていました。
    *   **Inferno OS**: Plan 9の経験に基づいて開発された、よりポータブルで分散型のオペレーティングシステムです。Infernoもベル研究所で開発され、その後Vita Nuova Holdingsによってメンテナンスされています。InfernoのツールチェインはPlan 9の思想を継承しており、その`ar`ユーティリティも同様です。
    *   Go言語は、Plan 9やInfernoの設計思想、特に並行処理モデル（goroutineとチャネル）やシンプルなツールチェインの考え方から大きな影響を受けています。
5.  **Goのカスタムオブジェクトファイル形式**: Goコンパイラは、従来のC/C++コンパイラが生成するELF (Executable and Linkable Format) や COFF (Common Object File Format) とは異なる、独自のオブジェクトファイル形式を使用します。このカスタム形式は、Goの特定のニーズ（例えば、高速なコンパイルとリンク、ガベージコレクションのサポートなど）に合わせて最適化されています。このため、標準の`ar`ツールではGoのオブジェクトファイルを正しく解析できません。
6.  **`__.SYMDEF`ファイル**: Plan 9の`ar`ユーティリティの重要な特徴の一つに、オブジェクトファイルのアーカイブ内に`__.SYMDEF`という特殊なメンバーファイルを含める機能があります。このファイルは、アーカイブ内のすべてのオブジェクトファイルで定義されている外部シンボルのインデックスとして機能します。リンカは、この`__.SYMDEF`ファイルを読み込むことで、アーカイブ全体をスキャンすることなく、必要なシンボルを効率的に見つけることができます。

## 技術的詳細

このコミットの主要な技術的変更点は、Inferno OSの`ar`ユーティリティのソースコードをGoプロジェクトに導入し、Goのカスタムオブジェクトファイル形式とシンボルテーブルの特性に合わせて適応させたことです。

1.  **Inferno `ar`の移植**:
    *   `src/cmd/ar/ar.c`として追加されたコードは、Inferno OSの`utils/iar/ar.c`からの直接的な移植です。ファイルの冒頭のコメントにInferno OSの著作権情報とURLが明記されており、その起源を示しています。
    *   この移植により、GoはPlan 9の`ar`が持つ機能、特に`__.SYMDEF`シンボルインデックスファイルの生成と利用の恩恵を受けることができます。これにより、Goのリンカは静的ライブラリ内のシンボルを高速に検索できるようになります。
    *   移植された`ar`は、`r` (replace/add)、`d` (delete)、`x` (extract)、`t` (table of contents)、`p` (print)、`m` (move)、`q` (quick append) といった標準的な`ar`コマンドの操作をサポートしています。

2.  **Goオブジェクトファイル形式への対応**:
    *   `src/libmach_amd64/obj.c`の`objtype`関数の変更は、Goのカスタムオブジェクトファイル形式を正しく識別し、解析するために行われました。
    *   特に、`objtype`関数には「import block」をスキップするロジックが追加されています。これは、Goのオブジェクトファイルが持つ可能性のある特定のメタデータや構造を、`ar`がシンボルをスキャンする際に無視できるようにするためのものです。これにより、`ar`はGoのオブジェクトファイルから正確なシンボル情報を抽出できます。
    *   `scanobj`関数（`ar.c`内）は、オブジェクトファイルからシンボルを抽出し、`Arsymref`構造体として内部リストに追加します。このプロセスで、`objsym`関数が`Sym`構造体（Goの内部シンボル表現）を受け取り、`Arsymref`に変換して、`__.SYMDEF`ファイルに書き込むための準備をします。
    *   `duplicate`関数は、シンボルテーブルに重複するテキストシンボルがないかをチェックし、リンカエラーを防ぐための重要な役割を担っています。

3.  **ビルドシステムへの統合**:
    *   `src/cmd/ar/Makefile`が新規作成され、`ar.c`をコンパイルして`6ar`という実行可能ファイルを生成する手順が定義されています。`6ar`という命名は、Goの初期のツールチェインがターゲットアーキテクチャ（この場合はamd64）を示すプレフィックス（例: `6l` for linker, `6a` for assembler）を使用していたことに由来します。
    *   `src/cmd/make.bash`は、Goのビルドスクリプトであり、新しく追加された`ar`コマンドがビルドプロセスに組み込まれるように変更されました。これにより、Goのツールチェイン全体が自動的に`ar`をビルドし、インストールするようになります。
    *   `src/cmd/clean.bash`も、ビルド成果物をクリーンアップする際に`ar`コマンドの生成物を削除するように更新されました。
    *   `src/libmach_amd64/Makefile`には`fakeobj.o`が追加されていますが、これは`obj.c`の変更と関連して、Goのオブジェクトファイル解析に必要な補助的なコンポーネントである可能性があります。

この変更により、Goのビルドシステムは、Go独自のオブジェクトファイル形式を理解し、効率的なシンボル解決を可能にする専用の`ar`ツールを手に入れました。これは、Go言語が自己完結型のツールチェインを構築し、その後の発展の基盤を築く上で重要な一歩でした。

### `src/cmd/ar/ar.c` (抜粋と解説)

```c
// Inferno utils/iar/ar.c
// http://code.google.com/p/inferno-os/source/browse/utils/iar/ar.c
// ... (Copyright and License information) ...

/*
 * ar - portable (ascii) format version
 */

// ... (データ構造の定義: Arsymref, Armember, Arfile, Hashchain など) ...

// scanobj: オブジェクトファイルからシンボル参照を抽出する
void
scanobj(Biobuf *b, Arfile *ap, long size)
{
    int obj;
    vlong offset;
    Dir *d;
    static int lastobj = -1;

    if (!allobj)        /* non-object file encountered */
        return;
    offset = Boffset(b);
    obj = objtype(b, 0); // オブジェクトファイルのタイプを識別
    if (obj < 0) {      /* not an object file */
        allobj = 0;
        d = dirfstat(Bfildes(b));
        if (d != nil && d->length == 0)
            fprint(2, "ar: zero length file %s\n", file);
        free(d);
        Bseek(b, offset, 0);
        return;
    }
    // ... (オブジェクトファイルタイプの一貫性チェック) ...
    if (!readar(b, obj, offset+size, 0)) { // シンボル情報を読み込む
        fprint(2, "ar: invalid symbol reference in file %s\n", file);
        allobj = 0;
        Bseek(b, offset, 0);
        return;
    }
    Bseek(b, offset, 0);
    objtraverse(objsym, ap); // 抽出したシンボルを処理 (objsym関数を呼び出す)
}

// objsym: テキストおよびデータシンボルをシンボルリストに追加する
void
objsym(Sym *s, void *p)
{
    int n;
    Arsymref *as;
    Arfile *ap;

    if (s->type != 'T' &&  s->type != 'D') // テキスト ('T') またはデータ ('D') シンボルのみを対象
        return;
    ap = (Arfile*)p;
    as = (Arsymref*)armalloc(sizeof(Arsymref));
    as->offset = ap->size; // アーカイブ内でのオフセットを記録
    n = strlen(s->name);
    as->name = armalloc(n+1);
    strcpy(as->name, s->name);
    if(s->type == 'T' && duplicate(as->name)) { // 重複するテキストシンボルをチェック
        dupfound = 1;
        fprint(2, "duplicate text symbol: %s\n", as->name);
        free(as->name);
        free(as);
        return;
    }
    as->type = s->type;
    symdefsize += 4+(n+1)+1; // __.SYMDEFファイルのサイズを計算
    as->len = n;
    as->next = ap->sym;
    ap->sym = as; // シンボルリストの先頭に追加
}

// wrsym: 定義されたシンボルをsymdefファイルに書き込む
void
wrsym(Biobuf *bp, long offset, Arsymref *as)
{
    int off;

    while(as) {
        Bputc(bp, as->type); // シンボルタイプ
        off = as->offset+offset; // シンボルのオフセット
        Bputc(bp, off);
        Bputc(bp, off>>8);
        Bputc(bp, off>>16);
        Bputc(bp, off>>24); // 4バイトのリトルエンディアンでオフセットを書き込み
        if (Bwrite(bp, as->name, as->len+1) != as->len+1) // シンボル名とNULL終端
            wrerr();
        as = as->next;
    }
}
```

**解説**:
`ar.c`は、アーカイブ操作の核心をなすファイルです。
*   `scanobj`関数は、入力されたファイルがオブジェクトファイルであるかを`objtype`で判断し、もしそうであればそのシンボル情報を`readar`で読み込みます。その後、`objtraverse`を通じて`objsym`関数を呼び出し、個々のシンボルを処理します。
*   `objsym`関数は、Goのオブジェクトファイルから抽出されたシンボル（`Sym`構造体）を受け取り、それがテキスト（`'T'`）またはデータ（`'D'`）シンボルであれば、`Arsymref`という内部構造体に変換して、現在のアーカイブファイル（`Arfile`）のシンボルリストに追加します。この際、シンボル名が重複していないか`duplicate`関数でチェックします。
*   `wrsym`関数は、最終的に`__.SYMDEF`ファイルに書き込まれるシンボル情報をフォーマットします。各シンボルについて、そのタイプ、アーカイブ内でのオフセット、そしてシンボル名をバイナリ形式で書き込みます。このオフセット情報は、リンカがアーカイブ内の特定のシンボルを迅速に見つけるために使用されます。

### `src/libmach_amd64/obj.c` (抜粋と解説)

```c
// objtype: オブジェクトファイルのタイプを識別する
int
objtype(Biobuf *bp, char **name)
{
    int i;
    char buf[MAXIS];
    int c;

Retry: // ここから再試行する
    if(Bread(bp, buf, MAXIS) < MAXIS)
        return -1;
    Bseek(bp, -MAXIS, 1); // 読み込んだ分を戻す
    // ... (既存のオブジェクトファイルタイプ識別ロジック) ...

    /*
     * Maybe there's an import block we need to skip
     */
    for(i = 0; i < MAXIS; i++) {
        if(isalpha(buf[i]) || isdigit(buf[i]))
            continue;
        if(i == 0 || buf[i] != '\n')
            return -1;
        break;
    }

    /*
     * Found one.  Skip until "\n!\n"
     */
    while((c = Bgetc(bp)) != Beof) {
        if(c != '\n')
            continue;
        c = Bgetc(bp);
        if(c != '!'){
            Bungetc(bp);
            continue;
        }
        c = Bgetc(bp);
        if(c != '\n'){
            Bungetc(bp);
            continue;
        }
        goto Retry; // "\n!\n"が見つかったら、再度objtypeの先頭から処理を試みる
    }
    return -1;
}
```

**解説**:
`obj.c`の`objtype`関数は、Goのオブジェクトファイルの先頭を読み込み、その種類を判別する役割を担っています。このコミットで追加された部分は、Goのオブジェクトファイルが持つ可能性のある「import block」という特殊なセクションを検出してスキップするロジックです。
*   この「import block」は、Goのコンパイラが生成するオブジェクトファイルに埋め込まれる特定のメタデータであると考えられます。
*   コードは、バッファをスキャンして、英数字以外の文字、特に改行文字（`\n`）を探します。
*   もし`\n!\n`というシーケンスが見つかった場合、それは「import block」の終わりを示していると判断し、そのブロック全体をスキップして、再度`objtype`の処理を最初から試みます（`goto Retry`）。これにより、`objtype`は実際のオブジェクトコードの開始位置から正しいオブジェクトファイルタイプを識別できるようになります。
この変更は、`ar`がGoのオブジェクトファイルを正しく解析し、シンボル情報を抽出するために不可欠な、Go固有のオブジェクトファイル形式への適応を示しています。

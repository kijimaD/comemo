## 変更の背景

この変更の背景には、Go言語のインターフェース埋め込みに関する既存の仕様記述が、その動作を完全に網羅していなかった、あるいは誤解を招く可能性があったという問題があります。コミットメッセージにある `Fixes #7886` は、このコミットが特定のバグ報告や不明瞭な点に関する議論に対応していることを示唆しています。

具体的な問題は、インターフェースを別のインターフェースに埋め込んだ際に、埋め込まれたインターフェースのメソッドがどのように「追加」されるのか、特にメソッドの重複や可視性（エクスポートされているか否か）に関するルールが不明確であったことと考えられます。このコミットは、これらの点を明確にし、Go言語のインターフェース設計における重要な側面である「メソッドの集合」という概念をより厳密に定義することを目的としています。

## 前提知識の解説

### Go言語のインターフェース

Go言語におけるインターフェースは、メソッドのシグネチャの集合を定義する型です。インターフェースは、そのインターフェースで定義されたすべてのメソッドを実装する任意の型によって「満たされる」（または「実装される」）ことができます。Goのインターフェースは、JavaやC#のような明示的な `implements` キーワードを必要とせず、型がインターフェースのメソッドセットを満たしていれば、自動的にそのインターフェースを実装していると見なされます（構造的型付け）。

例:
```go
type Reader interface {
    Read(p []byte) (n int, err error)
}

type Writer interface {
    Write(p []byte) (n int, err error)
}
```

### インターフェースの埋め込み (Interface Embedding)

Go言語では、構造体と同様に、インターフェースも他のインターフェースを「埋め込む」ことができます。インターフェースの埋め込みは、埋め込まれたインターフェースのすべてのメソッドを、埋め込む側のインターフェースに「昇格」させる効果があります。これにより、コードの再利用性が高まり、より複雑なインターフェースを簡潔に定義することができます。

埋め込みの構文は、フィールド名なしで型名を記述するだけです。

例:
```go
type ReadWriter interface {
    Reader // ReaderインターフェースのReadメソッドを埋め込む
    Writer // WriterインターフェースのWriteメソッドを埋め込む
}
```
この `ReadWriter` インターフェースは、`Read` メソッドと `Write` メソッドの両方を持つことになります。

### メソッドセットと重複

Go言語では、各型が持つメソッドの集合を「メソッドセット」と呼びます。インターフェースの埋め込みにおいて重要なのは、結果として生成されるインターフェースのメソッドセットに重複するメソッドが存在しないことです。Goの仕様では、インターフェースのメソッドセット内でメソッド名が重複することは許されません。ただし、同じメソッド名であっても、シグネチャが異なる場合は別のメソッドとして扱われます。しかし、インターフェースの埋め込みにおいては、同じメソッド名を持つメソッドが異なるシグネチャで存在する場合、それはコンパイルエラーとなります。同じシグネチャであれば重複は許容されますが、それは実質的に同じメソッドが複数回定義されていることになり、冗長です。

## 技術的詳細

このコミットによる主要な技術的変更点は、Go言語の仕様書におけるインターフェース埋め込みの定義の明確化です。

変更前は、インターフェースの埋め込みについて「`T` のメソッドを明示的に列挙するのと同等」と記述されていました。これは概念的には正しいものの、以下の点が不明確でした。

1.  **メソッドの可視性**: 埋め込まれたインターフェースのメソッドが、エクスポートされている（大文字で始まる）ものだけでなく、エクスポートされていない（小文字で始まる）ものも含まれるのかどうか。
2.  **メソッドの重複**: 複数のインターフェースを埋め込んだ際に、同じ名前のメソッドが存在した場合の挙動。

このコミットは、これらの点を以下のように明確にしています。

変更後の記述:
「インターフェース `T` は、メソッドの仕様の代わりに（修飾された可能性のある）インターフェース型名 `E` を使用することができます。これはインターフェース `E` を `T` に *埋め込む* と呼ばれ、`E` のすべての（エクスポートされたものとエクスポートされていないもの両方の）メソッドをインターフェース `T` に追加します。」

この変更により、以下の点が明確になりました。

*   **すべてのメソッドの追加**: 埋め込まれたインターフェース `E` のメソッドは、その可視性（エクスポートされているか否か）に関わらず、すべて埋め込む側のインターフェース `T` に追加されます。これは、インターフェースが型であり、そのメソッドセットは型の定義の一部であるため、当然の帰結ですが、明示的に記述することで誤解を防ぎます。
*   **メソッドの重複に関する明確な例**: 新しい例 `LockedFile` が追加され、メソッドの重複が許されないケースが示されています。

    ```go
    type LockedFile interface {
        Locker
        File        // illegal: Lock, Unlock not unique
        Lock()      // illegal: Lock not unique
    }
    ```
    この例では、`Locker` インターフェースが `Lock()` と `Unlock()` メソッドを持ち、`File` インターフェースも `Locker` を埋め込んでいるため、`File` も `Lock()` と `Unlock()` を持ちます。
    `LockedFile` インターフェースで `Locker` と `File` の両方を埋め込むと、`Lock()` と `Unlock()` メソッドが `Locker` と `File` の両方から追加され、重複が発生します。Goのインターフェースはメソッドの集合であり、同じ名前のメソッドが複数存在することは許されないため、これはコンパイルエラーとなります。
    さらに、`LockedFile` 内で `Lock()` メソッドを明示的に定義することも、`Locker` や `File` から追加される `Lock()` と重複するため、これもコンパイルエラーとなります。

この明確化は、Go言語の型システム、特にインターフェースの設計原則である「メソッドの集合としてのインターフェース」という考え方をより厳密に適用するためのものです。これにより、開発者はインターフェースの埋め込みがどのように機能し、どのような場合にコンパイルエラーとなるのかを正確に理解できるようになります。

## コアとなるコードの解説

このコミットの核心は、Go言語のインターフェース埋め込みのセマンティクスを厳密に定義し、特にメソッドの重複に関するルールを明確にした点にあります。

変更された仕様の記述:
`An interface T may use a (possibly qualified) interface type name E in place of a method specification. This is called <i>embedding</i> interface E in T; it adds all (exported and non-exported) methods of E to the interface T.`

この文は、インターフェース `T` にインターフェース `E` を埋め込むと、`E` が持つ「すべてのメソッド」（エクスポートされているか否かに関わらず）が `T` のメソッドセットに追加されることを明確に述べています。これは、インターフェースが単なるメソッドシグネチャのリストではなく、その型が持つメソッドの完全な集合を定義するというGoの設計思想を反映しています。

最も重要な追加は、`LockedFile` の例です。

```go
type LockedFile interface {
    Locker
    File        // illegal: Lock, Unlock not unique
    Lock()      // illegal: Lock not unique
}
```

この例は、インターフェースの埋め込みにおいて、結果として生成されるインターフェースのメソッドセット内でメソッド名が重複してはならないというGoの厳格なルールを示しています。

*   `Locker` インターフェースは `Lock()` と `Unlock()` メソッドを定義します。
*   `File` インターフェースは `ReadWriter` と `Locker` を埋め込み、さらに `Close()` メソッドを定義します。したがって、`File` も `Lock()` と `Unlock()` メソッドを持ちます。

`LockedFile` インターフェースで `Locker` と `File` の両方を埋め込もうとすると、`Lock()` と `Unlock()` メソッドが両方の埋め込み元から `LockedFile` に追加されることになり、メソッド名が重複します。Goのコンパイラはこれを「`Lock`, `Unlock` not unique」としてエラーとします。

さらに、`LockedFile` 内で `Lock()` メソッドを明示的に定義することも、埋め込まれた `Locker` や `File` から追加される `Lock()` メソッドと重複するため、「`Lock` not unique」としてエラーとなります。

この例は、Goのインターフェースが「メソッドの集合」であり、その集合内では各メソッド名が一意でなければならないという原則を強調しています。これは、インターフェースのセマンティクスを理解する上で非常に重要なポイントであり、Goの型システムの堅牢性を示しています。

この明確化は、Go言語の型システム、特にインターフェースの設計原則である「メソッドの集合としてのインターフェース」という考え方をより厳密に適用するためのものです。これにより、開発者はインターフェースの埋め込みがどのように機能し、どのような場合にコンパイルエラーとなるのかを正確に理解できるようになります。

## コアとなるコードの解説

このコミットの核心は、Go言語のインターフェース埋め込みのセマンティクスを厳密に定義し、特にメソッドの重複に関するルールを明確にした点にあります。

変更された仕様の記述:
`An interface T may use a (possibly qualified) interface type name E in place of a method specification. This is called <i>embedding</i> interface E in T; it adds all (exported and non-exported) methods of E to the interface T.`

この文は、インターフェース `T` にインターフェース `E` を埋め込むと、`E` が持つ「すべてのメソッド」（エクスポートされているか否かに関わらず）が `T` のメソッドセットに追加されることを明確に述べています。これは、インターフェースが単なるメソッドシグネチャのリストではなく、その型が持つメソッドの完全な集合を定義するというGoの設計思想を反映しています。

最も重要な追加は、`LockedFile` の例です。

```go
type LockedFile interface {
    Locker
    File        // illegal: Lock, Unlock not unique
    Lock()      // illegal: Lock not unique
}
```

この例は、インターフェースの埋め込みにおいて、結果として生成されるインターフェースのメソッドセット内でメソッド名が重複してはならないというGoの厳格なルールを示しています。

*   `Locker` インターフェースは `Lock()` と `Unlock()` メソッドを定義します。
*   `File` インターフェースは `ReadWriter` と `Locker` を埋め込み、さらに `Close()` メソッドを定義します。したがって、`File` も `Lock()` と `Unlock()` メソッドを持ちます。

`LockedFile` インターフェースで `Locker` と `File` の両方を埋め込もうとすると、`Lock()` と `Unlock()` メソッドが両方の埋め込み元から `LockedFile` に追加されることになり、メソッド名が重複します。Goのコンパイラはこれを「`Lock`, `Unlock` not unique」としてエラーとします。

さらに、`LockedFile` 内で `Lock()` メソッドを明示的に定義することも、埋め込まれた `Locker` や `File` から追加される `Lock()` メソッドと重複するため、「`Lock` not unique」としてエラーとなります。

この例は、Goのインターフェースが「メソッドの集合」であり、その集合内では各メソッド名が一意でなければならないという原則を強調しています。これは、インターフェースのセマンティクスを理解する上で非常に重要なポイントであり、Goの型システムの堅牢性を示しています。

# [インデックス 24449] ファイルの概要

このコミットは、GoコンパイラのARM64アーキテクチャ向けオブジェクトファイル生成部分におけるスタックフレームのアライメント処理に関する重要な変更を導入しています。具体的には、これまで暗黙的に行われていた不正なスタックフレームサイズのアライメント調整を廃止し、代わりにアライメントされていないフレームをエラーとして扱うように変更することで、コンパイラの堅牢性とデバッグのしやすさを向上させています。

## コミット

```
cmd/internal/obj/arm64: reject misaligned stack frames, except empty frames

The layout code has to date insisted on stack frames that are 16-aligned
including the saved LR, and it ensured this by growing the frame itself.
This breaks code that refers to values near the top of the frame by positive
offset from SP, and in general it's too magical: if you see TEXT xxx, $N,
you expect that the frame size is actually N, not sometimes N and sometimes N+8.

This led to a serious bug in the compiler where ambiguously live values
were not being zeroed correctly, which in turn triggered an assertion
in the GC about finding only valid pointers. The compiler has been
fixed to always emit aligned frames, and the hand-written assembly
has also been fixed.

Now that everything is aligned, make unaligned an error instead of
something to "fix" silently.

For #9880.

## 元コミット内容

`cmd/internal/obj/arm64: reject misaligned stack frames, except empty frames`

このコミットは、ARM64アーキテクチャにおけるスタックフレームのアライメントに関する変更です。これまで、Goコンパイラのレイアウトコードは、保存されたリンクレジスタ（LR）を含めて16バイトアライメントされたスタックフレームを要求し、フレーム自体を拡張することでこれを保証していました。しかし、この挙動は、スタックポインタ（SP）からの正のオフセットでフレームの上部近くの値を参照するコードを壊す可能性があり、また、`TEXT xxx, $N`と記述されたフレームサイズが常に`N`であると期待されるにもかかわらず、実際には`N`や`N+8`になるという「魔法のような」挙動を引き起こしていました。

この問題は、コンパイラ内で曖昧に生存している値が正しくゼロクリアされないという深刻なバグにつながり、結果としてGCが有効なポインタのみを見つけるというアサーションをトリガーしていました。このコミット以前に、コンパイラと手書きのアセンブリコードは、常にアライメントされたフレームを出力するように修正されています。

今回のコミットでは、すべてのフレームがアライメントされるようになったため、アライメントされていないフレームを「サイレントに修正する」のではなく、エラーとして扱うように変更されました。ただし、空のフレーム（サイズが8バイトでLRのみを含む場合）は例外として扱われます。

この変更は、Issue #9880 に関連しています。

## 変更の背景

Goコンパイラは、生成されるコードの効率性と正確性を保証するために、特定のアーキテクチャ固有の制約に従う必要があります。ARM64アーキテクチャでは、スタックフレームが16バイト境界にアライメントされていることが、パフォーマンスと正しい動作のために重要です。

これまでのGoコンパイラは、開発者が指定したスタックフレームサイズが16バイトアライメント要件を満たさない場合、自動的にフレームサイズを調整してアライメントを強制していました。この「サイレントな修正」は、一見便利に見えますが、以下のような問題を引き起こしていました。

1.  **予期せぬフレームサイズ**: `TEXT xxx, $N`と記述された場合、プログラマはスタックフレームのサイズが正確に`N`であると期待します。しかし、アライメントのためにフレームサイズが`N+8`のように変更されると、SPからのオフセットでローカル変数や引数を参照するコードが誤動作する可能性がありました。
2.  **コンパイラのバグ**: 最も深刻な問題は、このサイレントな修正が、コンパイラが「曖昧に生存している値」（ambiguously live values）を正しくゼロクリアできないというバグを引き起こしたことです。これは、ガベージコレクタ（GC）がヒープをスキャンする際に、無効なポインタを発見し、アサーションエラーを発生させる原因となりました。GCは、メモリの安全性を保証するために、有効なポインタのみが存在することを厳密にチェックします。
3.  **デバッグの困難さ**: 予期せぬフレームサイズの変更は、デバッグを困難にし、コンパイラが生成するコードの挙動を予測しにくくしていました。

これらの問題に対処するため、このコミット以前に、Goコンパイラ自体と手書きのアセンブリコードの両方が修正され、常に正しい16バイトアライメントされたスタックフレームを出力するようになりました。このコミットは、その修正が完了したことを前提として、もはや不正なアライメントをサイレントに修正する必要がなくなったため、代わりにエラーとして報告することで、将来的な同様の問題の発生を防ぎ、コードの堅牢性を高めることを目的としています。

## 前提知識の解説

### スタックフレームとアライメント

*   **スタックフレーム**: 関数が呼び出されるたびに、その関数が必要とするローカル変数、引数、戻りアドレス、保存されたレジスタなどを格納するために、プログラムのスタック上に確保されるメモリ領域です。
*   **スタックポインタ (SP)**: 現在のスタックフレームの最上部（または最下部、アーキテクチャによる）を指すレジスタです。ローカル変数などはSPからのオフセットでアクセスされます。
*   **リンクレジスタ (LR)**: 関数呼び出し元に戻るためのアドレス（リターンアドレス）を保持するレジスタです。関数が別の関数を呼び出す場合、LRの値をスタックに保存する必要があります。
*   **アライメント (Alignment)**: メモリ上のデータが特定のバイト数の倍数のアドレスに配置されることを指します。例えば、16バイトアライメントとは、データの開始アドレスが16の倍数でなければならないという要件です。
    *   **なぜアライメントが必要か**:
        *   **パフォーマンス**: 多くのプロセッサは、アライメントされたデータにアクセスする方が高速です。アライメントされていないアクセスは、追加のサイクルを必要としたり、ハードウェア例外を引き起こしたりする可能性があります。
        *   **アトミック操作**: マルチスレッド環境でのアトミック操作には、データが適切にアライメントされていることが前提となる場合があります。
        *   **特定の命令**: SIMD（Single Instruction, Multiple Data）命令など、一部のプロセッサ命令は、アライメントされたデータにしか動作しません。
        *   **ABI (Application Binary Interface)**: オペレーティングシステムやコンパイラ間で互換性のあるバイナリを生成するために、ABIによってスタックフレームやデータの特定のアライメントが義務付けられていることがあります。ARM64では、スタックポインタが16バイトアライメントされていることがABIで規定されています。

### Goのガベージコレクタ (GC)

*   **GCの役割**: Goのガベージコレクタは、プログラムが動的に確保したメモリのうち、もはや到達不可能（参照されていない）になったメモリ領域を自動的に解放し、再利用可能にするシステムです。これにより、メモリリークを防ぎ、開発者が手動でメモリ管理を行う負担を軽減します。
*   **ポインタの追跡**: GCは、ヒープ上のオブジェクトをスキャンし、どのオブジェクトがまだ「生きている」（プログラムから参照されている）かを判断するために、ポインタを追跡します。スタック上にあるポインタも、ヒープ上のオブジェクトへの参照としてGCによって認識されます。
*   **曖昧に生存している値 (Ambiguously Live Values)**: これは、GCがポインタであるかどうかを確実に判断できないメモリ上の値を指す可能性があります。GoのGCは正確なGC（precise GC）を目指していますが、特定の状況下（例えば、スタック上の整数値が偶然ポインタのように見えるアドレスを指している場合など）では、GCがその値をポインタとして誤認識するリスクがあります。このような誤認識は、GCが誤って「生きている」と判断したオブジェクトを解放しない、あるいはさらに悪いことに、無効なポインタをたどってクラッシュを引き起こす可能性があります。
*   **ゼロクリア**: Goでは、新しいメモリが割り当てられたり、変数が初期化されたりする際に、そのメモリ領域がゼロで埋められることが保証されています。これは、特にポインタ型の場合、GCが古い、無効なポインタ値を誤って追跡するのを防ぐ上で非常に重要です。曖昧に生存している値がゼロクリアされないと、GCが不正なメモリにアクセスする原因となり得ます。

### Goコンパイラの内部構造 (`cmd/internal/obj/arm64`)

*   `cmd/internal/obj`: Goコンパイラのバックエンドの一部で、アセンブラとリンカの共通のオブジェクトファイルフォーマットを扱うパッケージです。
*   `arm64`: ARM64アーキテクチャ固有のコード生成ロジックが含まれています。これには、命令の選択、レジスタ割り当て、スタックフレームのレイアウトなどが含まれます。
*   `obj7.go`: このファイルは、GoコンパイラのARM64バックエンドにおけるオブジェクト生成とアセンブリコードのプリプロセスに関連するロジックを含んでいます。スタックフレームのサイズ計算やアライメント調整もここで行われます。

## 技術的詳細

このコミットの核心は、`src/cmd/internal/obj/arm64/obj7.go` ファイル内の `preprocess` 関数におけるスタックフレームのアライメント処理の変更です。

以前のコードでは、`ctxt.Autosize`（スタックフレームの自動サイズ）が16バイトアライメントされていない場合、`stkadj`（スタック調整量）を計算し、フレームサイズを16バイトアライメントに合うように増やしていました。これは、`ctxt.Autosize += int32(stkadj)` と `cursym.Locals += int32(stkadj)` という行で行われていました。この調整はサイレントに行われ、プログラマには見えませんでした。

```go
// 以前のコードの抜粋
if ctxt.Autosize&(16-1) != 0 { // ctxt.Autosize % 16 != 0 の意味
    stkadj = 16 - (int64(ctxt.Autosize) & (16 - 1))
    ctxt.Autosize += int32(stkadj)
    cursym.Locals += int32(stkadj)
}
```

このコミットでは、このサイレントな調整ロジックが削除され、代わりに明示的なエラーチェックが導入されました。

新しいロジックは以下のようになります。

1.  `ctxt.Autosize&(16-1) != 0` (つまり `ctxt.Autosize % 16 != 0`) の条件は引き続きチェックされます。これは、スタックフレームが16バイトアライメントされていないことを意味します。
2.  **例外処理**: `ctxt.Autosize == 8` の場合、これはフレームがリンクレジスタ（LR）のみを保存する「空の」フレームであることを意味します。ARM64のABIでは、スタックポインタは16バイトアライメントされている必要がありますが、LRのみのフレームは8バイトです。この場合、フレームサイズを8バイト増やして16バイトアライメントに合わせます (`ctxt.Autosize += 8; ctxt.Locals += 8`)。これは、ローカル変数が存在しないため、SPからのオフセット参照が壊れる心配がないためです。
3.  **エラー処理**: `ctxt.Autosize == 8` ではない、つまりローカル変数セクションが存在するにもかかわらずフレームが16バイトアライメントされていない場合、`ctxt.Diag` を使用してコンパイル時エラーを発生させます。エラーメッセージは、「`unaligned frame size %d - must be 8 mod 16 (or 0)`」と表示され、フレームサイズが8 mod 16（または0）である必要があることを明確に伝えます。ここで「8 mod 16」とは、LRを含むフレームサイズが16バイトアライメントされたSPから8バイトオフセットされた位置にローカル変数が始まることを意味し、実質的にフレーム全体が16バイトアライメントされていることを要求します。

この変更は、`stkadj` 変数の削除と、条件分岐によるエラー報告の追加によって実現されています。

また、`test/nosplit.go` ファイルも更新され、新しいアライメント要件をテストケースに反映しています。具体的には、`size%ptrSize == 4` の条件に加えて、`goarch == "arm64" && size != 0 && (size+8)%16 != 0` という条件が追加されました。これは、ARM64アーキテクチャにおいて、フレームサイズが0ではないにもかかわらず、(サイズ + 8) が16の倍数でない（つまり、LRを含めたフレームが16バイトアライメントされていない）場合にテストケースをスキップする（または失敗させる）ことを意味します。これにより、新しいアライメント制約がテストによって強制されるようになります。

## コアとなるコードの解説

### `src/cmd/internal/obj/arm64/obj7.go` の変更点

*   **`stkadj` 変数の削除**: 以前はスタック調整量を計算するために使用されていた `stkadj` 変数が削除されました。これは、サイレントな調整ロジックが不要になったためです。
*   **アライメントチェックと条件分岐の強化**:
    *   `else if ctxt.Autosize&(16-1) != 0 { ... }` のブロック内で、スタックフレームが16バイトアライメントされていない場合の処理が変更されました。
    *   **空のフレームの特別扱い**: `if ctxt.Autosize == 8 { ... }` の条件が追加されました。
        *   `ctxt.Autosize` が8の場合、これは保存されたLRのみを含むフレーム（8バイト）を意味します。この場合、ローカル変数は存在しないため、SPからのオフセット参照が壊れる心配がありません。したがって、フレームサイズをさらに8バイト増やして16バイトアライメントに強制的に合わせます (`ctxt.Autosize += 8; ctxt.Locals += 8`)。
    *   **非アライメントフレームのエラー化**: `else { ... }` ブロックが追加され、`ctxt.Autosize` が8ではない（つまりローカル変数セクションが存在する）にもかかわらず、フレームが16バイトアライメントされていない場合に `ctxt.Diag` を呼び出してコンパイル時エラーを発生させます。
        *   エラーメッセージ `"%v: unaligned frame size %d - must be 8 mod 16 (or 0)"` は、問題の箇所 (`p`) と不正なフレームサイズ (`ctxt.Autosize-8`、LRの8バイトを除いたローカル変数部分のサイズ）を報告し、正しいアライメント要件を明確に示します。

この変更により、コンパイラは不正なスタックフレームのアライメントを自動的に修正するのではなく、開発者に問題を通知し、修正を促すようになります。これにより、コンパイラの生成するコードの予測可能性と信頼性が向上します。

### `test/nosplit.go` の変更点

*   `TestCases` のループ内で、特定の条件を満たすテストケースをスキップする（または失敗させる）ロジックが更新されました。
*   `goarch == "arm64" && size != 0 && (size+8)%16 != 0` という新しい条件が追加されました。
    *   `goarch == "arm64"`: 現在のアーキテクチャがARM64であること。
    *   `size != 0`: フレームサイズが0ではないこと。
    *   `(size+8)%16 != 0`: LR（8バイト）を含めたスタックフレームの合計サイズが16バイトアライメントされていないこと。
*   この条件が真の場合、`continue TestCases` が実行され、現在のテストケースはスキップされます。これは、ARM64における新しいスタックアライメント要件に違反するフレームサイズを持つテストケースが、コンパイルエラーを引き起こすことを期待しているためです。これにより、コンパイラの変更が正しく機能していることを検証し、将来的に不正なアライメントのコードが導入されるのを防ぎます。

cmd/internal/obj/arm64: reject misaligned stack frames, except empty frames

The layout code has to date insisted on stack frames that are 16-aligned
including the saved LR, and it ensured this by growing the frame itself.
This breaks code that refers to values near the top of the frame by positive
offset from SP, and in general it's too magical: if you see TEXT xxx, $N,
you expect that the frame size is actually N, not sometimes N and sometimes N+8.

This led to a serious bug in the compiler where ambiguously live values
were not being zeroed correctly, which in turn triggered an assertion
in the GC about finding only valid pointers. The compiler has been

## 元コミット内容

`cmd/internal/obj/arm64: reject misaligned stack frames, except empty frames`

このコミットは、ARM64アーキテクチャにおけるスタックフレームのアライメントに関する変更です。これまで、Goコンパイラのレイアウトコードは、保存されたリンクレジスタ（LR）を含めて16バイトアライメントされたスタックフレームを要求し、フレーム自体を拡張することでこれを保証していました。しかし、この挙動は、スタックポインタ（SP）からの正のオフセットでフレームの上部近くの値を参照するコードを壊す可能性があり、また、`TEXT xxx, $N`と記述されたフレームサイズが常に`N`であると期待されるにもかかわらず、実際には`N`や`N+8`になるという「魔法のような」挙動を引き起こしていました。

この問題は、コンパイラ内で曖昧に生存している値が正しくゼロクリアされないという深刻なバグにつながり、結果としてGCが有効なポインタのみを見つけるというアサーションをトリガーしていました。このコミット以前に、コンパイラと手書きのアセンブリコードは、常にアライメントされたフレームを出力するように修正されています。

今回のコミットでは、すべてのフレームがアライメントされるようになったため、アライメントされていないフレームを「サイレントに修正する」のではなく、エラーとして扱うように変更されました。ただし、空のフレーム（サイズが8バイトでLRのみを含む場合）は例外として扱われます。

この変更は、Issue #9880 に関連しています。

## 変更の背景

Goコンパイラは、生成されるコードの効率性と正確性を保証するために、特定のアーキテクチャ固有の制約に従う必要があります。ARM64アーキテクチャでは、スタックフレームが16バイト境界にアライメントされていることが、パフォーマンスと正しい動作のために重要です。

これまでのGoコンパイラは、開発者が指定したスタックフレームサイズが16バイトアライメント要件を満たさない場合、自動的にフレームサイズを調整してアライメントを強制していました。この「サイレントな修正」は、一見便利に見えますが、以下のような問題を引き起こしていました。

1.  **予期せぬフレームサイズ**: `TEXT xxx, $N`と記述された場合、プログラマはスタックフレームのサイズが正確に`N`であると期待します。しかし、アライメントのためにフレームサイズが`N+8`のように変更されると、SPからのオフセットでローカル変数や引数を参照するコードが誤動作する可能性がありました。
2.  **コンパイラのバグ**: 最も深刻な問題は、このサイレントな修正が、コンパイラが「曖昧に生存している値」（ambiguously live values）を正しくゼロクリアできないというバグを引き起こしたことです。これは、ガベージコレクタ（GC）がヒープをスキャンする際に、無効なポインタを発見し、アサーションエラーを発生させる原因となりました。GCは、メモリの安全性を保証するために、有効なポインタのみが存在することを厳密にチェックします。
3.  **デバッグの困難さ**: 予期せぬフレームサイズの変更は、デバッグを困難にし、コンパイラが生成するコードの挙動を予測しにくくしていました。

これらの問題に対処するため、このコミット以前に、Goコンパイラ自体と手書きのアセンブリコードの両方が修正され、常に正しい16バイトアライメントされたスタックフレームを出力するようになりました。このコミットは、その修正が完了したことを前提として、もはや不正なアライメントをサイレントに修正する必要がなくなったため、代わりにエラーとして報告することで、将来的な同様の問題の発生を防ぎ、コードの堅牢性を高めることを目的としています。

## 前提知識の解説

### スタックフレームとアライメント

*   **スタックフレーム**: 関数が呼び出されるたびに、その関数が必要とするローカル変数、引数、戻りアドレス、保存されたレジスタなどを格納するために、プログラムのスタック上に確保されるメモリ領域です。
*   **スタックポインタ (SP)**: 現在のスタックフレームの最上部（または最下部、アーキテクチャによる）を指すレジスタです。ローカル変数などはSPからのオフセットでアクセスされます。
*   **リンクレジスタ (LR)**: 関数呼び出し元に戻るためのアドレス（リターンアドレス）を保持するレジスタです。関数が別の関数を呼び出す場合、LRの値をスタックに保存する必要があります。
*   **アライメント (Alignment)**: メモリ上のデータが特定のバイト数の倍数のアドレスに配置されることを指します。例えば、16バイトアライメントとは、データの開始アドレスが16の倍数でなければならないという要件です。
    *   **なぜアライメントが必要か**:
        *   **パフォーマンス**: 多くのプロセッサは、アライメントされたデータにアクセスする方が高速です。アライメントされていないアクセスは、追加のサイクルを必要としたり、ハードウェア例外を引き起こしたりする可能性があります。
        *   **アトミック操作**: マルチスレッド環境でのアトミック操作には、データが適切にアライメントされていることが前提となる場合があります。
        *   **特定の命令**: SIMD（Single Instruction, Multiple Data）命令など、一部のプロセッサ命令は、アライメントされたデータにしか動作しません。
        *   **ABI (Application Binary Interface)**: オペレーティングシステムやコンパイラ間で互換性のあるバイナリを生成するために、ABIによってスタックフレームやデータの特定のアライメントが義務付けられていることがあります。ARM64では、スタックポインタが16バイトアライメントされていることがABIで規定されています。

### Goのガベージコレクタ (GC)

*   **GCの役割**: Goのガベージコレクタは、プログラムが動的に確保したメモリのうち、もはや到達不可能（参照されていない）になったメモリ領域を自動的に解放し、再利用可能にするシステムです。これにより、メモリリークを防ぎ、開発者が手動でメモリ管理を行う負担を軽減します。
*   **ポインタの追跡**: GCは、ヒープ上のオブジェクトをスキャンし、どのオブジェクトがまだ「生きている」（プログラムから参照されている）かを判断するために、ポインタを追跡します。スタック上にあるポインタも、ヒープ上のオブジェクトへの参照としてGCによって認識されます。
*   **曖昧に生存している値 (Ambiguously Live Values)**: これは、GCがポインタであるかどうかを確実に判断できないメモリ上の値を指す可能性があります。GoのGCは正確なGC（precise GC）を目指していますが、特定の状況下（例えば、スタック上の整数値が偶然ポインタのように見えるアドレスを指している場合など）では、GCがその値をポインタとして誤認識するリスクがあります。このような誤認識は、GCが誤って「生きている」と判断したオブジェクトを解放しない、あるいはさらに悪いことに、無効なポインタをたどってクラッシュを引き起こす可能性があります。
*   **ゼロクリア**: Goでは、新しいメモリが割り当てられたり、変数が初期化されたりする際に、そのメモリ領域がゼロで埋められることが保証されています。これは、特にポインタ型の場合、GCが古い、無効なポインタ値を誤って追跡するのを防ぐ上で非常に重要です。曖昧に生存している値がゼロクリアされないと、GCが不正なメモリにアクセスする原因となり得ます。

### Goコンパイラの内部構造 (`cmd/internal/obj/arm64`)

*   `cmd/internal/obj`: Goコンパイラのバックエンドの一部で、アセンブラとリンカの共通のオブジェクトファイルフォーマットを扱うパッケージです。
*   `arm64`: ARM64アーキテクチャ固有のコード生成ロジックが含まれています。これには、命令の選択、レジスタ割り当て、スタックフレームのレイアウトなどが含まれます。
*   `obj7.go`: このファイルは、GoコンパイラのARM64バックエンドにおけるオブジェクト生成とアセンブリコードのプリプロセスに関連するロジックを含んでいます。スタックフレームのサイズ計算やアライメント調整もここで行われます。

## 技術的詳細

このコミットの核心は、`src/cmd/internal/obj/arm64/obj7.go` ファイル内の `preprocess` 関数におけるスタックフレームのアライメント処理の変更です。

以前のコードでは、`ctxt.Autosize`（スタックフレームの自動サイズ）が16バイトアライメントされていない場合、`stkadj`（スタック調整量）を計算し、フレームサイズを16バイトアライメントに合うように増やしていました。これは、`ctxt.Autosize += int32(stkadj)` と `cursym.Locals += int32(stkadj)` という行で行われていました。この調整はサイレントに行われ、プログラマには見えませんでした。

```go
// 以前のコードの抜粋
if ctxt.Autosize&(16-1) != 0 { // ctxt.Autosize % 16 != 0 の意味
    stkadj = 16 - (int64(ctxt.Autosize) & (16 - 1))
    ctxt.Autosize += int32(stkadj)
    cursym.Locals += int32(stkadj)
}
```

このコミットでは、このサイレントな調整ロジックが削除され、代わりに明示的なエラーチェックが導入されました。

新しいロジックは以下のようになります。

1.  `ctxt.Autosize&(16-1) != 0` (つまり `ctxt.Autosize % 16 != 0`) の条件は引き続きチェックされます。これは、スタックフレームが16バイトアライメントされていないことを意味します。
2.  **例外処理**: `ctxt.Autosize == 8` の場合、これはフレームがリンクレジスタ（LR）のみを保存する「空の」フレームであることを意味します。ARM64のABIでは、スタックポインタは16バイトアライメントされている必要がありますが、LRのみのフレームは8バイトです。この場合、フレームサイズを8バイト増やして16バイトアライメントに合わせます (`ctxt.Autosize += 8; ctxt.Locals += 8`)。これは、ローカル変数が存在しないため、SPからのオフセット参照が壊れる心配がないためです。
3.  **エラー処理**: `ctxt.Autosize == 8` ではない、つまりローカル変数セクションが存在するにもかかわらずフレームが16バイトアライメントされていない場合、`ctxt.Diag` を使用してコンパイル時エラーを発生させます。エラーメッセージは、「`unaligned frame size %d - must be 8 mod 16 (or 0)`」と表示され、フレームサイズが8 mod 16（または0）である必要があることを明確に伝えます。ここで「8 mod 16」とは、LRを含むフレームサイズが16バイトアライメントされたSPから8バイトオフセットされた位置にローカル変数が始まることを意味し、実質的にフレーム全体が16バイトアライメントされていることを要求します。

この変更は、`stkadj` 変数の削除と、条件分岐によるエラー報告の追加によって実現されています。

また、`test/nosplit.go` ファイルも更新され、新しいアライメント要件をテストケースに反映しています。具体的には、`size%ptrSize == 4` の条件に加えて、`goarch == "arm64" && size != 0 && (size+8)%16 != 0` という条件が追加されました。これは、ARM64アーキテクチャにおいて、フレームサイズが0ではないにもかかわらず、(サイズ + 8) が16の倍数でない（つまり、LRを含めたフレームが16バイトアライメントされていない）場合にテストケースをスキップする（または失敗させる）ことを意味します。これにより、新しいアライメント制約がテストによって強制されるようになります。

## コアとなるコードの解説

### `src/cmd/internal/obj/arm64/obj7.go` の変更点

*   **`stkadj` 変数の削除**: 以前はスタック調整量を計算するために使用されていた `stkadj` 変数が削除されました。これは、サイレントな調整ロジックが不要になったためです。
*   **アライメントチェックと条件分岐の強化**:
    *   `else if ctxt.Autosize&(16-1) != 0 { ... }` のブロック内で、スタックフレームが16バイトアライメントされていない場合の処理が変更されました。
    *   **空のフレームの特別扱い**: `if ctxt.Autosize == 8 { ... }` の条件が追加されました。
        *   `ctxt.Autosize` が8の場合、これは保存されたLRのみを含むフレーム（8バイト）を意味します。この場合、ローカル変数は存在しないため、SPからのオフセット参照が壊れる心配がありません。したがって、フレームサイズをさらに8バイト増やして16バイトアライメントに強制的に合わせます (`ctxt.Autosize += 8; ctxt.Locals += 8`)。
    *   **非アライメントフレームのエラー化**: `else { ... }` ブロックが追加され、`ctxt.Autosize` が8ではない（つまりローカル変数セクションが存在する）にもかかわらず、フレームが16バイトアライメントされていない場合に `ctxt.Diag` を呼び出してコンパイル時エラーを発生させます。
        *   エラーメッセージ `"%v: unaligned frame size %d - must be 8 mod 16 (or 0)"` は、問題の箇所 (`p`) と不正なフレームサイズ (`ctxt.Autosize-8`、LRの8バイトを除いたローカル変数部分のサイズ）を報告し、正しいアライメント要件を明確に示します。

この変更により、コンパイラは不正なスタックフレームのアライメントを自動的に修正するのではなく、開発者に問題を通知し、修正を促すようになります。これにより、コンパイラの生成するコードの予測可能性と信頼性が向上します。

### `test/nosplit.go` の変更点

*   `TestCases` のループ内で、特定の条件を満たすテストケースをスキップする（または失敗させる）ロジックが更新されました。
*   `goarch == "arm64" && size != 0 && (size+8)%16 != 0` という新しい条件が追加されました。
    *   `goarch == "arm64"`: 現在のアーキテクチャがARM64であること。
    *   `size != 0`: フレームサイズが0ではないこと。
    *   `(size+8)%16 != 0`: LR（8バイト）を含めたスタックフレームの合計サイズが16バイトアライメントされていないこと。
*   この条件が真の場合、`continue TestCases` が実行され、現在のテストケースはスキップされます。これは、ARM64における新しいスタックアライメント要件に違反するフレームサイズを持つテストケースが、コンパイルエラーを引き起こすことを期待しているためです。これにより、コンパイラの変更が正しく機能していることを検証し、将来的に不正なアライメントのコードが導入されるのを防ぎます。

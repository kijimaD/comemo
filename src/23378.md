```
runtime: reorder bits in heap bitmap bytes

The runtime deals with 1-bit pointer bitmaps and 2-bit heap bitmaps
that have entries for both pointers and mark bits.

Each byte in a 1-bit pointer bitmap looks like pppppppp (all pointer bits).
Each byte in a 2-bit heap bitmap looks like mpmpmpmp (mark, pointer, ...).
This means that when converting from 1-bit to 2-bit, as we do
during malloc, we have to pick up 4 bits in pppp form and use
shifts to create the mpmpmpmp form.

This CL changes the 2-bit heap bitmap form to mmmmpppp,
so that 4 bits picked up in 1-bit form can be used directly in
the low bits of the heap bitmap byte, without expansion.
This simplifies the code, and it also happens to be faster.
```

## 変更の背景

Goランタイムのガベージコレクタは、メモリ内のポインタを効率的に識別し、マークするためにビットマップを使用します。以前の設計では、1ビットポインタビットマップ（スタックフレームやグローバル変数用）と2ビットヒープビットマップ（ヒープオブジェクト用）の間にビットの並び順に不整合がありました。

1ビットポインタビットマップでは、1バイトが8つのポインタビット（`pppppppp`）を表していました。一方、2ビットヒープビットマップでは、1バイトが4つのマークビットと4つのポインタビットを交互に配置した形式（`mpmpmpmp`）で表現されていました。

この異なるビット配置のため、`malloc`（メモリ割り当て）時に1ビットポインタビットマップから2ビットヒープビットマップへ情報を変換する際、`pppp`形式の4ビットを読み取り、それを`mpmpmpmp`形式に変換するために複雑なシフト操作が必要でした。この変換プロセスは、コードを複雑にするだけでなく、パフォーマンス上のオーバーヘッドも発生させていました。

このコミットは、ヒープビットマップのビット配置を`mmmmpppp`（マークビットが上位4ビット、ポインタビットが下位4ビット）に変更することで、この非効率性を解消することを目的としています。これにより、1ビットポインタビットマップから読み取った`pppp`形式の4ビットを、ヒープビットマップバイトの下位ビットに直接配置できるようになり、変換ロジックが大幅に簡素化され、同時にパフォーマンスも向上します。

ベンチマーク結果が示すように、特に`SetTypePtr`や`SetTypeNode`といった型情報の設定に関連する操作において、顕著な速度向上が見られます。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goのガベージコレクタは、並行マーク＆スイープ方式を採用しています。これは、プログラムの実行と並行してGCサイクルを実行し、アプリケーションの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えることを目指しています。GCの主要なフェーズには、マークフェーズとスイープフェーズがあります。

*   **マークフェーズ**: GCは、ルート（スタック、グローバル変数など）から到達可能なすべてのオブジェクトを「ライブ」としてマークします。このプロセスでは、メモリ内のポインタを正確に識別する必要があります。
*   **スイープフェーズ**: マークされなかったオブジェクト（「デッド」オブジェクト）は、メモリから回収され、再利用可能な状態になります。

### ポインタビットマップとヒープビットマップ

GoのGCは、メモリ内のどこにポインタが存在するかを効率的に知るためにビットマップを使用します。

1.  **1ビットポインタビットマップ**:
    *   スタックフレームやグローバル変数領域で使用されます。
    *   各ビットが、対応するメモリワードがポインタであるかどうかを示します。
    *   `0`はポインタではない、`1`はポインタであることを意味します。
    *   このビットマップは、GCがルートセットをスキャンする際に使用され、どのスタック変数やグローバル変数がヒープ上のオブジェクトへのポインタであるかを判断します。
    *   コミット前のバイト表現は `pppppppp` のように、1バイト内に8つのポインタビットが連続して並んでいました。

2.  **2ビットヒープビットマップ**:
    *   ヒープ上のオブジェクトで使用されます。
    *   各メモリワード（`ptrSize`バイト、通常は8バイト）に対して2ビットが割り当てられます。
    *   この2ビットは、そのワードがポインタであるか（ポインタビット）と、GCによってマークされたか（マークビット）の情報を保持します。
    *   各2ビットエントリの意味:
        *   `00` (dead encoding): そのワードはポインタではなく、オブジェクトの残りの部分もGCにとって無関係であることを示します。これにより、GCはオブジェクトの残りの部分をスキップできます。
        *   `01` (pointer): そのワードはポインタであり、GCによって走査されるべきであることを示します。
        *   `10` (marked): そのワードはポインタであり、GCによって既にマーク済みであることを示します。
        *   `11` (checkmarked): GCの特定のフェーズで使用されるチェックマークの状態を示します。
    *   コミット前のバイト表現は `mpmpmpmp` のように、マークビットとポインタビットが交互に配置されていました。

### `malloc`とビットマップの変換

`malloc`は、新しいオブジェクトのためにヒープメモリを割り当てる関数です。この際、割り当てられたメモリ領域に対応するヒープビットマップを初期化する必要があります。オブジェクトの型情報（どのフィールドがポインタであるか）は、通常、1ビットポインタビットマップのような形式で提供されます。これを2ビットヒープビットマップの形式に変換して書き込む必要があります。

## 技術的詳細

このコミットの核心は、2ビットヒープビットマップのバイト内でのビット配置の変更です。

**変更前**:
*   1ビットポインタビットマップ: `pppppppp` (各`p`はポインタの有無を示す1ビット)
*   2ビットヒープビットマップ: `mpmpmpmp` (各`m`はマークビット、各`p`はポインタビット)

この配置では、1ビットポインタビットマップから4つのポインタビット（`pppp`）を取得し、それを2ビットヒープビットマップの`mpmpmpmp`形式に変換する際に、各ポインタビットの間にマークビットを挿入するために複雑なビットシフト操作が必要でした。例えば、`p1 p2 p3 p4`というポインタビット列を`m1 p1 m2 p2 m3 p3 m4 p4`という形式に変換する必要がありました。

**変更後**:
*   2ビットヒープビットマップ: `mmmmpppp` (上位4ビットがマークビット、下位4ビットがポインタビット)

この新しい配置では、1ビットポインタビットマップから取得した4つのポインタビット（`pppp`）を、ヒープビットマップバイトの下位4ビットに直接コピーできます。これにより、複雑なシフト操作が不要になり、変換ロジックが大幅に簡素化されます。マークビットは、必要に応じて上位4ビットに設定されます。

この変更により、`src/runtime/mbitmap.go`内のビット操作に関連する定数と関数が更新されました。

*   **`bitPointer` と `bitMarked` の定義変更**:
    *   変更前: `bitPointer = 1`, `bitMarked = 2` (これは2ビットエントリ内での相対的な位置を示していました)
    *   変更後: `bitPointer = 1 << 0`, `bitMarked = 1 << 4`
        *   `bitPointer`はバイトの最下位ビット（0番目のビット）に設定され、ポインタの有無を示します。
        *   `bitMarked`はバイトの5番目のビット（上位4ビットの最下位ビット）に設定され、マークの有無を示します。
        *   これにより、1バイト内でポインタビットが下位4ビットに、マークビットが上位4ビットにまとまる `mmmmpppp` 形式が実現されます。

*   **`heapBitsShift` の導入**:
    *   `heapBitsShift = 1` が導入されました。これは、連続するポインタビットまたはマークビット間のシフトオフセットを示します。以前は `heapBitsWidth` (2) を直接使用していましたが、新しい配置ではポインタビットとマークビットがそれぞれ連続して並ぶため、この値が1になります。

*   **`bitMarkedAll` と `bitPointerAll` の導入**:
    *   1バイト内のすべてのマークビットまたはポインタビットをまとめて操作するためのマスクが定義されました。
        *   `bitMarkedAll = bitMarked | bitMarked<<heapBitsShift | bitMarked<<(2*heapBitsShift) | bitMarked<<(3*heapBitsShift)`
        *   `bitPointerAll = bitPointer | bitPointer<<heapBitsShift | bitPointer<<(2*heapBitsShift) | bitPointer<<(3*heapBitsShift)`
    *   これらは、`mmmmpppp`形式のバイトにおいて、下位4ビット（ポインタ）または上位4ビット（マーク）を効率的に設定・クリアするために使用されます。

これらの変更により、`heapBitsForAddr`, `next`, `forward`, `hasPointers`, `isCheckmarked`, `setCheckmarked`, `initCheckmarkSpan`, `clearCheckmarkSpan`, `heapBitsSweepSpan`, `heapBitsSetType`などの関数内のビット操作ロジックが簡素化され、より直接的なビットマスクとシフトが使用されるようになりました。


## コアとなるコードの解説

このコミットの主要な変更は、Goランタイムがヒープビットマップをどのように表現し、操作するかという根本的な部分にあります。

1.  **ビット配置の最適化**:
    *   以前の `mpmpmpmp` 形式では、ポインタビットとマークビットが交互に配置されており、1ビットポインタビットマップ（`pppppppp`）から情報を変換する際に、各ポインタビットを適切な位置にシフトする必要がありました。これは、CPUサイクルを消費する操作でした。
    *   新しい `mmmmpppp` 形式では、ポインタビットがバイトの下位4ビットに連続して配置され、マークビットが上位4ビットに連続して配置されます。これにより、1ビットポインタビットマップから4つのポインタビットを読み取った際、それらを直接ヒープビットマップバイトの下位4ビットにコピーできるようになります。この「直接コピー」は、複雑なビットシフトやマスク操作を不要にし、コードを簡素化し、実行速度を向上させます。

2.  **定数の再定義と新しい定数の導入**:
    *   `bitPointer = 1 << 0` と `bitMarked = 1 << 4` の定義は、新しい `mmmmpppp` レイアウトを直接反映しています。`bitPointer` はバイトの0番目のビット、`bitMarked` は4番目のビット（上位4ビットの開始位置）を指します。
    *   `heapBitsShift = 1` は、連続するポインタビット間、または連続するマークビット間のシフト量を表します。これにより、ループ内で次のビットを処理する際の計算が統一され、簡潔になります。
    *   `bitMarkedAll` と `bitPointerAll` は、1バイト内のすべてのマークビットまたはポインタビットを一度に設定またはクリアするための便利なマスクを提供します。これにより、複数のビットを個別に操作する代わりに、単一のビット演算で効率的に処理できるようになります。

3.  **関数ロジックの簡素化**:
    *   `heapBitsForAddr`、`next`、`forward` などの `heapBits` 構造体に関連するメソッドは、ビット位置の計算がより直接的になりました。例えば、`heapBitsForAddr` での `h.shift` の計算は、以前の `2 * (off & 3)` から `off & 3` に簡素化され、ポインタビットのインデックスを直接取得できるようになりました。
    *   `heapBitsSetType` のような、型情報に基づいてヒープビットマップを初期化する複雑な関数では、新しいビット配置のおかげで、ビットのパック/アンパックロジックが大幅に簡素化されています。特に、`b & bitPointerAll` のような操作は、元のポインタビットを直接抽出して新しいバイトに配置することを可能にします。

この変更は、GoのGCのパフォーマンスに直接的な影響を与えます。ベンチマーク結果が示すように、特にオブジェクトの型情報を設定する操作（`SetTypePtr`や`SetTypeNode`など）において、最大で約40%の速度向上が見られます。これは、GCのオーバーヘッドを削減し、Goアプリケーション全体の実行速度を向上させることに貢献します。

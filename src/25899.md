## 変更の背景

この変更は、PowerPC 64-bit Little Endian (ppc64le) アーキテクチャ上で共有ライブラリを使用する際に発生する `runtime.stackBarrier` 関数の問題に対処するためのものです。

Goランタイムの `runtime.stackBarrier` 関数は、通常の関数呼び出し規約に従って呼び出されるわけではありません。代わりに、スタック上のリンクレジスタ (LR) スロットにそのアドレスが直接書き込まれるという、非常に特殊な方法で「呼び出され」ます。

ppc64leアーキテクチャでは、共有ライブラリ（Position-Independent Code, PIC）としてコンパイルされた関数は、通常、グローバルデータにアクセスするための Table of Contents (TOC) ポインタをレジスタ `r2` にロードするプロローグ命令を持ちます。このプロローグは、`r12` レジスタに設定されたグローバルエントリポイント (GEP) を基に `r2` を計算します。

しかし、`runtime.stackBarrier` が特殊な方法で呼び出される際、`r12` はGEPに設定されていません。この状態で通常のプロローグ命令が実行されると、`r2` レジスタが誤った値で上書きされてしまい、`stackBarrier` から戻った先の関数がグローバルデータにアクセスできなくなるという問題が発生していました。これは、`stackBarrier` を呼び出した元の関数が `r2` を使用してグローバルデータにアクセスしている場合に特に深刻な問題となります。

この問題により、`64bit.go`、`append.go`、および `fixedbugs/issue13169.go` といったテストが、`-linkshared` オプションで実行された際に失敗していました。

## 前提知識の解説

### PowerPC 64-bit Little Endian (ppc64le) アーキテクチャ

PowerPCはIBMが開発したRISCプロセッサアーキテクチャです。`ppc64le` は、64ビット版のPowerPCで、リトルエンディアンのバイトオーダーを採用していることを示します。Go言語は様々なアーキテクチャをサポートしており、ppc64leもその一つです。

### 共有ライブラリ (Position-Independent Code, PIC)

共有ライブラリは、複数のプログラムで共有されるコードの集まりです。メモリ上の任意のアドレスにロードされても正しく実行できるように、位置独立コード (PIC) としてコンパイルされます。PICでは、絶対アドレスではなく、現在のプログラムカウンタからの相対アドレスを使用してデータや関数にアクセスします。

### Global Entry Point (GEP) と Table of Contents (TOC)

PowerPC 64-bit ABI (Application Binary Interface) において、共有ライブラリ内の関数がグローバルデータにアクセスするためには、Table of Contents (TOC) と呼ばれるデータ構造を利用します。TOCは、グローバル変数や外部関数のアドレスを格納するテーブルです。

関数が呼び出される際、`r12` レジスタにはその関数のグローバルエントリポイント (GEP) が設定されます。GEPは、TOCへのポインタを含むデータ構造を指します。関数のプロローグでは、この `r12` を基にして `r2` レジスタにTOCポインタがロードされます。これにより、関数は `r2` を介してグローバルデータにアクセスできるようになります。

### `runtime.stackBarrier` 関数

Goランタイムにおける `runtime.stackBarrier` は、スタックの境界チェックやスタックの拡張に関連する内部関数です。この関数は、通常の `CALL` 命令ではなく、スタック上のリンクレジスタ (LR) を直接操作することで実行フローを制御するという、非常に特殊なメカニズムを持っています。これは、Goのスタック管理の最適化や特殊な状況下での処理のために用いられます。

### 関数プロローグ

関数プロローグとは、関数が実行を開始する際に最初に行われる一連の命令のことです。これには、スタックフレームのセットアップ、レジスタの保存、そして今回のケースのように、特定のレジスタ（例: `r2`）に重要な値をロードする処理などが含まれます。

## 技術的詳細

この問題の核心は、`runtime.stackBarrier` がPowerPC 64-bit ABIの通常の関数呼び出し規約に従わない点にあります。

1.  **通常の関数呼び出し**: ppc64leの共有ライブラリでは、関数が呼び出される前に `r12` にGEPが設定され、その後のプロローグ命令で `r12` を使って `r2` (TOCポインタ) が計算・ロードされます。これにより、関数はグローバルデータにアクセスできます。
2.  **`runtime.stackBarrier` の特殊な呼び出し**: `runtime.stackBarrier` は、通常の `CALL` 命令ではなく、スタック上のリンクレジスタ (LR) スロットに直接そのアドレスを書き込むことで「呼び出され」ます。この際、`r12` レジスタはGEPに設定されていません。
3.  **問題の発生**: `r12` がGEPでない状態で、通常の関数プロローグが実行されると、`r12` を基に `r2` を計算する命令が誤った値を `r2` にロードしてしまいます。これは、`stackBarrier` から戻った先の関数が `r2` を使ってグローバルデータにアクセスしようとした際に、不正なメモリ参照やクラッシュを引き起こす可能性があります。
4.  **解決策**: 幸いなことに、`runtime.stackBarrier` 関数自体はグローバルデータにアクセスしません。したがって、`r2` の値に依存しません。この特性を利用して、`runtime.stackBarrier` に対しては、`r2` をロードするプロローグ命令の生成をスキップするというアプローチが取られました。これにより、`r2` の破損を防ぎ、共有ライブラリ環境での `stackBarrier` の正しい動作を保証します。

この修正は、`runtime.duffzero` と `runtime.duffcopy` という他の特殊な関数と同様の扱いになります。これらの関数も、特定の命令オフセットにジャンプするためにプロローグをスキップする必要があるため、同様にプロローグ生成の例外とされています。

## コアとなるコードの解説

このコードスニペットは、Goコンパイラのバックエンドの一部であり、PowerPC 64-bitアーキテクチャ向けのアセンブリコードを生成する際の `preprocess` 関数内にあります。

-   `func preprocess(ctxt *obj.Link, cursym *obj.LSym)`: この関数は、シンボル (`cursym`) の前処理を行います。`ctxt` はリンクコンテキストを提供します。
-   `if ctxt.Flag_shared != 0 && cursym.Name != "runtime.duffzero" && cursym.Name != "runtime.duffcopy" { ... }`:
    -   `ctxt.Flag_shared != 0`: この条件は、現在コンパイルされているコードが共有ライブラリ (PIC) の一部である場合に真となります。共有ライブラリの場合、TOCポインタ (`r2`) をロードするための特別なプロローグ命令が必要です。
    -   `cursym.Name != "runtime.duffzero" && cursym.Name != "runtime.duffcopy"`: 既存のコードでは、`runtime.duffzero` と `runtime.duffcopy` という2つの特殊な関数に対しては、このプロローグ命令の生成をスキップしていました。これは、これらの関数が特定の命令オフセットにジャンプされることを前提としているためです。
-   **変更点**: `&& cursym.Name != "runtime.stackBarrier"` が追加されました。
    -   この変更により、`runtime.stackBarrier` 関数も、`runtime.duffzero` および `runtime.duffcopy` と同様に、TOCポインタをロードするプロローグ命令の生成対象から除外されるようになりました。
    -   コメントも更新され、`stackBarrier` がLRスロットを上書きすることで呼び出され、`r12` が正しくないため、プロローグをスキップする必要があること、そして幸いにもグローバルデータにアクセスしないため安全であることが明記されています。

この修正により、`runtime.stackBarrier` が共有ライブラリ内で使用された際に `r2` レジスタが破損する問題が解決され、Goプログラムがppc64le上の共有ライブラリ環境で安定して動作するようになります。

# [インデックス 23441] ファイルの概要

このコミットは、Go言語のビルドツールである `cmd/dist` のテスト実行ロジックに対する変更です。具体的には、テストのフィルタリング機能が強化され、環境変数 `GOTESTONLY` を介したフィルタリングのサポートと、正規表現によるテスト名の一致条件の否定（ネガティブマッチ）が導入されました。これにより、テストの選択と実行がより柔軟になり、特に大規模なテストスイートや特定の環境でのテスト実行の効率化が図られています。

## 元コミット内容

`cmd/dist` ツールにおいて、テストフィルタリングの機能が拡張されました。具体的には、`GOTESTONLY` 環境変数をテストフィルタリングの正規表現として再利用し、さらに正規表現の先頭に `!` を付けることでマッチングを反転させる（否定する）機能が追加されました。これは、将来的に導入される予定のシャード化されたARMビルド環境に対応するための変更です。この変更はIssue #10029に関連しています。

## 変更の背景

この変更の主な背景には、Goプロジェクトの継続的インテグレーション（CI）システム、特にテストインフラストラクチャの進化があります。コミットメッセージに「For upcoming sharded ARM builders. (今後登場するシャード化されたARMビルダーのため)」とあるように、ARMアーキテクチャ向けのビルドおよびテスト環境が大規模化し、テスト実行の効率化が求められていました。

Goプロジェクトでは、様々なアーキテクチャやオペレーティングシステムでコードが正しく動作することを保証するために、広範なテストスイートが実行されます。これらのテストは、CIシステム上で並行して実行されることが多く、特にリソースが限られている、あるいはテスト実行時間が長い環境（例: ARMベースのハードウェア）では、テストを効率的に分割（シャード化）して実行する機能が不可欠となります。

シャード化されたテスト環境では、特定のテストのサブセットのみを実行したり、特定のテストを除外したりする機能が重要になります。このコミットは、`cmd/dist` ツールが提供するテスト実行コマンドにおいて、このような柔軟なテスト選択を可能にすることで、シャード化されたARMビルダーの運用を容易にすることを目的としています。

また、Issue #10029は、Goのテストインフラストラクチャにおけるテストのシャード化と並列実行に関する議論や実装の進捗を示唆しています。このコミットは、その大きな目標の一部として位置づけられます。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **`cmd/dist` ツール**:
    Goのソースコードリポジトリに含まれる `cmd/dist` は、Goプロジェクト自身のビルド、テスト、インストールなどのタスクを管理するための内部ツールです。Goの標準ライブラリやツールチェーンのビルドプロセスを自動化するために使用されます。開発者が `go build` や `go test` といったコマンドを使用する際、内部的には `cmd/dist` が呼び出されることがあります。

2.  **Goのテストフレームワーク**:
    Goには標準で `testing` パッケージが提供されており、これを用いてユニットテストやベンチマークテストを記述します。テストファイルは `_test.go` というサフィックスを持ち、`go test` コマンドで実行されます。`go test` コマンドは、`-run` フラグを使って正規表現でテストをフィルタリングする機能を持っています。

3.  **環境変数 `GOTESTONLY`**:
    Goのテスト実行において、特定のテストのみを実行するために使用される環境変数です。通常、`go test -run` フラグと同様の目的で使われますが、`cmd/dist` の文脈では、ビルドシステムがテストを制御するために利用することがあります。このコミットでは、この環境変数の利用方法が拡張されています。

4.  **正規表現 (Regular Expression)**:
    文字列のパターンマッチングを行うための強力なツールです。このコミットでは、テスト名を正規表現でマッチングさせることで、実行するテストを選択しています。正規表現の基本的な構文（例: `^` で行頭、`$` で行末、`.` で任意の一文字、`*` で0回以上の繰り返しなど）を理解していると、フィルタリングの仕組みがより明確になります。

5.  **CI/CD (継続的インテグレーション/継続的デリバリー)**:
    ソフトウェア開発のプラクティスで、コードの変更が頻繁にメインブランチに統合され、自動的にビルド、テスト、デプロイされることを指します。Goプロジェクトのような大規模なオープンソースプロジェクトでは、世界中の様々な環境でコードが正しく動作することを保証するために、複雑なCIシステムが運用されています。

6.  **テストのシャード化 (Test Sharding)**:
    大規模なテストスイートを複数の小さなグループに分割し、それらを異なるマシンやプロセスで並行して実行する手法です。これにより、全体のテスト実行時間を短縮し、CIパイプラインの効率を向上させることができます。シャード化は、特にリソースが限られている環境や、テスト実行に時間がかかる場合に有効です。

7.  **ARMアーキテクチャ**:
    Advanced RISC Machineの略で、モバイルデバイスや組み込みシステム、最近ではサーバーやデスクトップPCでも広く採用されているCPUアーキテクチャです。GoはARMを含む多くのアーキテクチャをサポートしており、それぞれの環境でテストが実行される必要があります。

## 技術的詳細

このコミットは、`src/cmd/dist/test.go` ファイル内の `cmdtest` 関数と `tester` 構造体、およびその関連メソッドに変更を加えています。

1.  **`run` フラグのデフォルト値の変更**:
    以前は `cmdtest` 関数内で `t.runRxStr` (テストフィルタリング用の正規表現文字列) が空文字列で初期化されていましたが、この変更により `os.Getenv("GOTESTONLY")` の値で初期化されるようになりました。これにより、`cmd/dist` を実行する際に、環境変数 `GOTESTONLY` を設定するだけでテストフィルタリングが可能になります。

    ```go
    // 変更前
    // flag.StringVar(&t.runRxStr, "run", "", "run only those tests matching the regular expression; empty means to run all")
    // 変更後
    flag.StringVar(&t.runRxStr, "run", os.Getenv("GOTESTONLY"),
        "run only those tests matching the regular expression; empty means to run all. "+
        "\t\t\t\"Special exception: if the string begins with '!', the match is inverted.\"")
    ```
    ヘルプメッセージも更新され、`!` による否定マッチのサポートが明示されています。

2.  **否定マッチの導入**:
    `tester` 構造体に `runRxWant` という新しいブール型フィールドが追加されました。これは、正規表現マッチングの結果を「期待するか（true）」または「期待しないか（false、つまり否定マッチ）」を制御します。
    `t.runRxStr` が `!` で始まる場合、`t.runRxWant` は `false` に設定され、`t.runRxStr` から `!` が取り除かれます。それ以外の場合は `true` に設定されます。

    ```go
    // src/cmd/dist/test.go の変更箇所
    if t.runRxStr != "" {
        // ... (plan9の特殊ケース) ...
        if t.runRxStr[0] == '!' {
            t.runRxWant = false
            t.runRxStr = t.runRxStr[1:]
        } else {
            t.runRxWant = true
        }
        t.runRx = regexp.MustCompile(t.runRxStr)
    }
    ```

3.  **テストマッチングロジックの更新**:
    テストのループ処理内で、各テスト (`dt.name`) が正規表現 `t.runRx` にマッチするかどうかの判定ロジックが変更されました。

    ```go
    // 変更前
    // if t.runRx != nil && !t.runRx.MatchString(dt.name) {
    // 変更後
    if t.runRx != nil && (t.runRx.MatchString(dt.name) != t.runRxWant) {
        t.partial = true
        continue
    }
    ```
    この変更により、`t.runRx.MatchString(dt.name)` の結果が `t.runRxWant` と異なる場合にテストがスキップされるようになりました。
    *   `t.runRxWant` が `true` の場合（通常の肯定マッチ）：`MatchString` が `false` を返すとスキップされます。
    *   `t.runRxWant` が `false` の場合（否定マッチ）：`MatchString` が `true` を返すとスキップされます。
    これにより、正規表現にマッチするテストを実行したり（肯定）、マッチするテストを除外したり（否定）する柔軟な制御が可能になります。

4.  **Plan 9 の特殊ケースの追加**:
    一時的な措置として、`runtime.GOOS == "plan9"` かつ `t.runRxStr == "std"` の場合に、`t.runRxStr` が `"^go_test:"` に書き換えられるロジックが追加されました。これは、Plan 9 ビルダーが以前から `"std"` という文字列をテストフィルタリングに使用していたことへの互換性維持のためのものです。このコメントには「Delete this once we update dashboard/builders.go to use a regexp instead. (dashboard/builders.go が正規表現を使用するように更新されたらこれを削除する)」とあり、一時的な対応であることが示されています。

5.  **古い `GOTESTONLY` ハックの削除**:
    以前のコードには、`os.Getenv("GOTESTONLY") == "std"` の場合にテストを部分的にスキップする古いハックが存在しました。このコミットでは、新しい柔軟なフィルタリングメカニズムが導入されたため、この古い、特定の文字列に依存するハックが削除されました。

    ```go
    // 削除されたコード
    // // Old hack for when Plan 9 on GCE was too slow.
    // // We're keeping this until test sharding (Issue 10029) is finished, though.
    // if os.Getenv("GOTESTONLY") == "std" {
    // 	t.partial = true
    // 	return
    // }
    ```

これらの変更により、`cmd/dist` を使用したテスト実行において、環境変数 `GOTESTONLY` を利用し、正規表現と否定マッチを組み合わせることで、よりきめ細やかなテストの選択と実行が可能になりました。これは、特にCI環境でのテストのシャード化やデバッグ作業において、大きなメリットをもたらします。

1.  **`import "runtime"` の追加**:
    `runtime.GOOS` を使用してPlan 9環境を識別するために、`runtime` パッケージがインポートされました。

2.  **`flag.StringVar(&t.runRxStr, "run", os.Getenv("GOTESTONLY"), ...)`**:
    `cmdtest` 関数内で、コマンドラインフラグ `-run` のデフォルト値が `os.Getenv("GOTESTONLY")` に設定されました。これにより、ユーザーはコマンドライン引数として `-run` を明示的に指定しなくても、環境変数 `GOTESTONLY` を設定することでテストフィルタリングを行えるようになりました。また、フラグの説明文に `!` による否定マッチの機能が追加されたことが明記されています。

3.  **`type tester struct { ... runRxWant bool ... }`**:
    `tester` 構造体に `runRxWant` という新しいフィールドが追加されました。このフィールドは、正規表現マッチングの結果を反転させるかどうかを制御します。`true` の場合は正規表現にマッチするテストを実行し、`false` の場合はマッチしないテストを実行します。

4.  **`if t.runRxStr != "" { ... }` ブロック内のロジック**:
    `tester.run()` メソッド内で、`t.runRxStr` が空でない場合の処理が変更されました。
    *   **Plan 9 特殊ケース**: `runtime.GOOS == "plan9" && t.runRxStr == "std"` の条件が追加され、Plan 9 環境で `"std"` が指定された場合に `t.runRxStr` が `"^go_test:"` に書き換えられます。これは、既存のPlan 9ビルダーとの互換性を一時的に維持するためのものです。
    *   **否定マッチの検出**: `t.runRxStr[0] == '!'` のチェックが追加されました。もし `t.runRxStr` が `!` で始まる場合、`t.runRxWant` は `false` に設定され、`t.runRxStr` から `!` が削除されます。これにより、後続の正規表現コンパイルとマッチング処理で否定ロジックが適用されます。それ以外の場合は `t.runRxWant` は `true` に設定されます。
    *   `t.runRx = regexp.MustCompile(t.runRxStr)`: 変更された `t.runRxStr` を基に正規表現がコンパイルされます。

5.  **`for _, dt := range t.tests { ... }` ループ内のマッチングロジック**:
    テストのイテレーション処理において、テストをスキップするかどうかの条件が `if t.runRx != nil && (t.runRx.MatchString(dt.name) != t.runRxWant)` に変更されました。

    *   `!= t.runRxWant` は、このマッチ結果が `t.runRxWant` の期待値と異なる場合に `true` となります。

## 変更の背景

この変更の主な背景には、Goプロジェクトの継続的インテグレーション（CI）システム、特にテストインフラストラクチャの進化があります。コミットメッセージに「For upcoming sharded ARM builders. (今後登場するシャード化されたARMビルダーのため)」とあるように、ARMアーキテクチャ向けのビルドおよびテスト環境が大規模化し、テスト実行の効率化が求められていました。

Goプロジェクトでは、様々なアーキテクチャやオペレーティングシステムでコードが正しく動作することを保証するために、広範なテストスイートが実行されます。これらのテストは、CIシステム上で並行して実行されることが多く、特にリソースが限られている、あるいはテスト実行時間が長い環境（例: ARMベースのハードウェア）では、テストを効率的に分割（シャード化）して実行する機能が不可欠となります。

シャード化されたテスト環境では、特定のテストのサブセットのみを実行したり、特定のテストを除外したりする機能が重要になります。このコミットは、`cmd/dist` ツールが提供するテスト実行コマンドにおいて、このような柔軟なテスト選択を可能にすることで、シャード化されたARMビルダーの運用を容易にすることを目的としています。

また、Issue #10029は、Goのテストインフラストラクチャにおけるテストのシャード化と並列実行に関する議論や実装の進捗を示唆しています。このコミットは、その大きな目標の一部として位置づけられます。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **`cmd/dist` ツール**:
    Goのソースコードリポジトリに含まれる `cmd/dist` は、Goプロジェクト自身のビルド、テスト、インストールなどのタスクを管理するための内部ツールです。Goの標準ライブラリやツールチェーンのビルドプロセスを自動化するために使用されます。開発者が `go build` や `go test` といったコマンドを使用する際、内部的には `cmd/dist` が呼び出されることがあります。

2.  **Goのテストフレームワーク**:
    Goには標準で `testing` パッケージが提供されており、これを用いてユニットテストやベンチマークテストを記述します。テストファイルは `_test.go` というサフィックスを持ち、`go test` コマンドで実行されます。`go test` コマンドは、`-run` フラグを使って正規表現でテストをフィルタリングする機能を持っています。

3.  **環境変数 `GOTESTONLY`**:
    Goのテスト実行において、特定のテストのみを実行するために使用される環境変数です。通常、`go test -run` フラグと同様の目的で使われますが、`cmd/dist` の文脈では、ビルドシステムがテストを制御するために利用することがあります。このコミットでは、この環境変数の利用方法が拡張されています。

4.  **正規表現 (Regular Expression)**:
    文字列のパターンマッチングを行うための強力なツールです。このコミットでは、テスト名を正規表現でマッチングさせることで、実行するテストを選択しています。正規表現の基本的な構文（例: `^` で行頭、`$` で行末、`.` で任意の一文字、`*` で0回以上の繰り返しなど）を理解していると、フィルタリングの仕組みがより明確になります。

5.  **CI/CD (継続的インテグレーション/継続的デリバリー)**:
    ソフトウェア開発のプラクティスで、コードの変更が頻繁にメインブランチに統合され、自動的にビルド、テスト、デプロイされることを指します。Goプロジェクトのような大規模なオープンソースプロジェクトでは、世界中の様々な環境でコードが正しく動作することを保証するために、複雑なCIシステムが運用されています。

6.  **テストのシャード化 (Test Sharding)**:
    大規模なテストスイートを複数の小さなグループに分割し、それらを異なるマシンやプロセスで並行して実行する手法です。これにより、全体のテスト実行時間を短縮し、CIパイプラインの効率を向上させることができます。シャード化は、特にリソースが限られている環境や、テスト実行に時間がかかる場合に有効です。

7.  **ARMアーキテクチャ**:
    Advanced RISC Machineの略で、モバイルデバイスや組み込みシステム、最近ではサーバーやデスクトップPCでも広く採用されているCPUアーキテクチャです。GoはARMを含む多くのアーキテクチャをサポートしており、それぞれの環境でテストが実行される必要があります。

## 技術的詳細

このコミットは、`src/cmd/dist/test.go` ファイル内の `cmdtest` 関数と `tester` 構造体、およびその関連メソッドに変更を加えています。

1.  **`run` フラグのデフォルト値の変更**:
    以前は `cmdtest` 関数内で `t.runRxStr` (テストフィルタリング用の正規表現文字列) が空文字列で初期化されていましたが、この変更により `os.Getenv("GOTESTONLY")` の値で初期化されるようになりました。これにより、`cmd/dist` を実行する際に、環境変数 `GOTESTONLY` を設定するだけでテストフィルタリングが可能になります。

    ```go
    // 変更前
    // flag.StringVar(&t.runRxStr, "run", "", "run only those tests matching the regular expression; empty means to run all")
    // 変更後
    flag.StringVar(&t.runRxStr, "run", os.Getenv("GOTESTONLY"),
        "run only those tests matching the regular expression; empty means to run all. "+
        "\t\t\t\"Special exception: if the string begins with '!', the match is inverted.\"")
    ```
    ヘルプメッセージも更新され、`!` による否定マッチのサポートが明示されています。

2.  **否定マッチの導入**:
    `tester` 構造体に `runRxWant` という新しいブール型フィールドが追加されました。これは、正規表現マッチングの結果を「期待するか（true）」または「期待しないか（false、つまり否定マッチ）」を制御します。
    `t.runRxStr` が `!` で始まる場合、`t.runRxWant` は `false` に設定され、`t.runRxStr` から `!` が取り除かれます。それ以外の場合は `true` に設定されます。

    ```go
    // src/cmd/dist/test.go の変更箇所
    if t.runRxStr != "" {
        // ... (plan9の特殊ケース) ...
        if t.runRxStr[0] == '!' {
            t.runRxWant = false
            t.runRxStr = t.runRxStr[1:]
        } else {
            t.runRxWant = true
        }
        t.runRx = regexp.MustCompile(t.runRxStr)
    }
    ```

3.  **テストマッチングロジックの更新**:
    テストのループ処理内で、各テスト (`dt.name`) が正規表現 `t.runRx` にマッチするかどうかの判定ロジックが変更されました。

    ```go
    // 変更前
    // if t.runRx != nil && !t.runRx.MatchString(dt.name) {
    // 変更後
    if t.runRx != nil && (t.runRx.MatchString(dt.name) != t.runRxWant) {
        t.partial = true
        continue
    }
    ```
    この変更により、`t.runRx.MatchString(dt.name)` の結果が `t.runRxWant` と異なる場合にテストがスキップされるようになりました。
    *   `t.runRxWant` が `true` の場合（通常の肯定マッチ）：`MatchString` が `false` を返すとスキップされます。
    *   `t.runRxWant` が `false` の場合（否定マッチ）：`MatchString` が `true` を返すとスキップされます。
    これにより、正規表現にマッチするテストを実行したり（肯定）、マッチするテストを除外したり（否定）する柔軟な制御が可能になります。

4.  **Plan 9 の特殊ケースの追加**:
    一時的な措置として、`runtime.GOOS == "plan9"` かつ `t.runRxStr == "std"` の場合に、`t.runRxStr` が `"^go_test:"` に書き換えられるロジックが追加されました。これは、Plan 9 ビルダーが以前から `"std"` という文字列をテストフィルタリングに使用していたことへの互換性維持のためのものです。このコメントには「Delete this once we update dashboard/builders.go to use a regexp instead. (dashboard/builders.go が正規表現を使用するように更新されたらこれを削除する)」とあり、一時的な対応であることが示されています。

5.  **古い `GOTESTONLY` ハックの削除**:
    以前のコードには、`os.Getenv("GOTESTONLY") == "std"` の場合にテストを部分的にスキップする古いハックが存在しました。このコミットでは、新しい柔軟なフィルタリングメカニズムが導入されたため、この古い、特定の文字列に依存するハックが削除されました。

    ```go
    // 削除されたコード
    // // Old hack for when Plan 9 on GCE was too slow.
    // // We're keeping this until test sharding (Issue 10029) is finished, though.
    // if os.Getenv("GOTESTONLY") == "std" {
    // 	t.partial = true
    // 	return
    // }
    ```

これらの変更により、`cmd/dist` を使用したテスト実行において、環境変数 `GOTESTONLY` を利用し、正規表現と否定マッチを組み合わせることで、よりきめ細やかなテストの選択と実行が可能になりました。これは、特にCI環境でのテストのシャード化やデバッグ作業において、大きなメリットをもたらします。

## コアとなるコードの解説

1.  **`import "runtime"` の追加**:
    `runtime.GOOS` を使用してPlan 9環境を識別するために、`runtime` パッケージがインポートされました。

2.  **`flag.StringVar(&t.runRxStr, "run", os.Getenv("GOTESTONLY"), ...)`**:
    `cmdtest` 関数内で、コマンドラインフラグ `-run` のデフォルト値が `os.Getenv("GOTESTONLY")` に設定されました。これにより、ユーザーはコマンドライン引数として `-run` を明示的に指定しなくても、環境変数 `GOTESTONLY` を設定することでテストフィルタリングを行えるようになりました。また、フラグの説明文に `!` による否定マッチの機能が追加されたことが明記されています。

3.  **`type tester struct { ... runRxWant bool ... }`**:
    `tester` 構造体に `runRxWant` という新しいフィールドが追加されました。このフィールドは、正規表現マッチングの結果を反転させるかどうかを制御します。`true` の場合は正規表現にマッチするテストを実行し、`false` の場合はマッチしないテストを実行します。

4.  **`if t.runRxStr != "" { ... }` ブロック内のロジック**:
    `tester.run()` メソッド内で、`t.runRxStr` が空でない場合の処理が変更されました。
    *   **Plan 9 特殊ケース**: `runtime.GOOS == "plan9" && t.runRxStr == "std"` の条件が追加され、Plan 9 環境で `"std"` が指定された場合に `t.runRxStr` が `"^go_test:"` に書き換えられます。これは、既存のPlan 9ビルダーとの互換性を一時的に維持するためのものです。
    *   **否定マッチの検出**: `t.runRxStr[0] == '!'` のチェックが追加されました。もし `t.runRxStr` が `!` で始まる場合、`t.runRxWant` は `false` に設定され、`t.runRxStr` から `!` が削除されます。これにより、後続の正規表現コンパイルとマッチング処理で否定ロジックが適用されます。それ以外の場合は `t.runRxWant` は `true` に設定されます。
    *   `t.runRx = regexp.MustCompile(t.runRxStr)`: 変更された `t.runRxStr` を基に正規表現がコンパイルされます。

5.  **`for _, dt := range t.tests { ... }` ループ内のマッチングロジック**:
    テストのイテレーション処理において、テストをスキップするかどうかの条件が `if t.runRx != nil && (t.runRx.MatchString(dt.name) != t.runRxWant)` に変更されました。
    *   `t.runRx.MatchString(dt.name)` は、現在のテスト名が正規表現にマッチするかどうかを返します。
    *   `!= t.runRxWant` は、このマッチ結果が `t.runRxWant` の期待値と異なる場合に `true` となります。
        *   例えば、`t.runRxWant` が `true`（肯定マッチ）の場合、`MatchString` が `false` を返すと `false != true` で `true` となり、テストはスキップされます。
        *   `t.runRxWant` が `false`（否定マッチ）の場合、`MatchString` が `true` を返すと `true != false` で `true` となり、テストはスキップされます。
    このロジックにより、正規表現による肯定・否定両方のフィルタリングが実現されています。

6.  **古い `GOTESTONLY` ハックの削除**:
    `tester.registerTests()` メソッド内にあった、`os.Getenv("GOTESTONLY") == "std"` に基づくテストスキップの古いコードブロックが削除されました。これは、新しい汎用的なフィルタリングメカニズムによって不要になったためです。

これらの変更は、`cmd/dist` のテスト実行における柔軟性と制御を大幅に向上させ、特にCI環境でのテスト管理をより効率的にするための基盤を築いています。

# [インデックス 24453] ファイルの概要

## 変更の背景

Goランタイムは、Goプログラムの実行を効率的かつ安全に管理するために、OSの低レベルな機能と密接に連携しています。特に、システムコールを直接呼び出すようなパフォーマンスが要求される部分や、OS固有の機能を利用する部分では、アセンブリ言語が使用されます。

このコミットは、Darwin (macOS/iOS) 上のARM64アーキテクチャにおいて、Goランタイムが使用する特定のアセンブリ関数（`time.now`、`runtime.nanotime`、`runtime.usleep`）のスタックフレームサイズが誤って設定されていた問題を修正するものです。

スタックフレームサイズが不正確であると、以下のような深刻な問題を引き起こす可能性があります。

1.  **スタックの破損**: 関数が想定よりも多くのスタック領域を使用しようとしたり、逆に少なすぎると判断して他のデータ領域を上書きしたりする可能性があります。これにより、プログラムのクラッシュ、未定義の動作、またはセキュリティ上の脆弱性につながることがあります。
2.  **メモリリークまたは非効率なメモリ使用**: 必要以上に大きなスタックフレームを確保すると、メモリの無駄遣いになります。逆に小さすぎると、スタックオーバーフローを引き起こす可能性があります。
3.  **デバッグの困難さ**: スタックが破損すると、スタックトレースが不正確になり、問題の根本原因を特定することが非常に困難になります。

これらの関数は、システム時刻の取得やスリープ処理といった、Goプログラムの基本的な動作に不可欠な機能を提供するため、その正確な動作はGoランタイムの安定性と信頼性にとって極めて重要です。この修正は、これらの関数の堅牢性を確保し、GoプログラムがDarwin/ARM64環境で正しく動作するために必要でした。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の概念について知っておく必要があります。

*   **Goランタイム (Go Runtime)**:
    Go言語のプログラムは、Goランタイムと呼ばれる特別なライブラリによって実行されます。これは、ガベージコレクション、スケジューリング（ゴルーチンの管理）、メモリ割り当て、システムコールインターフェースなど、プログラムの低レベルな側面を処理します。Goランタイムの一部は、パフォーマンスやOSとの直接的な連携のためにアセンブリ言語で書かれています。

*   **アセンブリ言語 (Assembly Language)**:
    CPUが直接理解できる機械語を、人間が読み書きしやすいように記号で表現した低レベルプログラミング言語です。Goランタイムでは、特にOS固有の機能へのアクセスや、極めて高いパフォーマンスが要求される部分でアセンブリが使用されます。このコミットでは、ARM64アーキテクチャ向けのアセンブリコードが対象です。

*   **ARM64アーキテクチャ**:
    Apple Silicon (M1, M2など) や多くのスマートフォン、タブレットで使用されている64ビットのARMプロセッサアーキテクチャです。Goランタイムは、このアーキテクチャ上で動作するために最適化されたアセンブリコードを含んでいます。

*   **Darwin**:
    Appleが開発したUNIXベースのオペレーティングシステムの中核部分です。macOS、iOS、watchOS、tvOSの基盤となっています。GoプログラムがこれらのOS上で動作する際には、Darwinのシステムコールを介してOSサービスを利用します。

*   **スタックフレーム (Stack Frame)**:
    関数が呼び出されるたびに、その関数の実行に必要な情報（ローカル変数、引数、戻りアドレス、保存されたレジスタなど）を格納するために、プログラムのスタック上に確保されるメモリ領域です。各関数呼び出しは独自のスタックフレームを持ち、関数が終了するとそのフレームはスタックから解放されます。

*   **`TEXT` ディレクティブ (Go Assembly)**:
    Goのアセンブリ言語では、`TEXT` ディレクティブを使用して関数を定義します。その一般的な形式は以下の通りです。
    ```assembly
    TEXT symbol(SB), flags, $framesize-argsize
    ```
    *   `symbol(SB)`: 関数のシンボル名。`SB` は "Static Base" を意味し、グローバルシンボルであることを示します。
    *   `flags`: 関数の特性を示すフラグ（例: `NOSPLIT`）。
    *   `$framesize`: この関数がローカル変数や一時的なデータのためにスタック上に確保する領域のバイトサイズです。これは、関数内で使用されるスタック領域の合計サイズを示します。
    *   `argsize`: この関数が呼び出し元から受け取る引数の合計バイトサイズです。これは、呼び出し元がスタックにプッシュした引数のサイズを示します。

*   **`NOSPLIT` フラグ**:
    `TEXT` ディレクティブで使用されるフラグの一つです。このフラグが設定された関数は、Goランタイムによるスタックの拡張チェックを行いません。これは通常、スタックサイズが固定で非常に小さい関数や、スタックチェック自体がオーバーヘッドとなるような低レベルなランタイム関数で使用されます。`NOSPLIT` 関数は、スタックオーバーフローの危険性があるため、慎重に設計される必要があります。

*   **`FP` (Frame Pointer) と `SP` (Stack Pointer)**:
    *   `FP` (Frame Pointer): 現在実行中の関数のスタックフレームの基点（通常はスタックフレームの開始アドレス）を指すレジスタです。ローカル変数や引数へのアクセスに利用されます。
    *   `SP` (Stack Pointer): スタックの現在のトップ（最も最近プッシュされたデータの位置）を指すレジスタです。スタックへのデータのプッシュ/ポップ操作によって値が変化します。

*   **システムコール (`SVC`)**:
    ユーザーモードで動作するプログラムが、カーネルモードで動作するオペレーティングシステム（OS）のサービス（ファイルI/O、メモリ管理、プロセス管理、時刻取得など）を利用するためのメカニズムです。ARM64アーキテクチャのDarwinでは、`SVC #0x80` 命令がシステムコールをトリガーするために使用されます。

## 技術的詳細

このコミットの核心は、GoランタイムのDarwin/ARM64アセンブリコードにおけるスタックフレームサイズの調整です。具体的には、以下の3つの関数で `$framesize` の値が変更されています。

1.  **`time.now(SB)`**:
    *   変更前: `$32-12`
    *   変更後: `$40-12`
    *   `time.now` 関数は、現在の時刻を取得するためにOSのシステムコール（`gettimeofday` など）を呼び出すGoの内部関数です。この関数は、システムコールから返される `timeval` 構造体やその他の情報を格納するためにスタック領域を使用します。元の `$32` バイトのフレームサイズでは、必要なローカルストレージが不足していたか、または将来的な変更に備えて余裕を持たせるために `$40` バイトに拡張されました。`argsize` の `-12` は、この関数が12バイトの引数を受け取ることを示しています。

2.  **`runtime.nanotime(SB)`**:
    *   変更前: `$32`
    *   変更後: `$40`
    *   `runtime.nanotime` 関数は、高精度なナノ秒単位の時刻を取得するために使用されるGoの内部関数です。これも `time.now` と同様にシステムコールを利用し、その結果を格納するためにスタック領域を必要とします。`$32` バイトから `$40` バイトへの変更は、この関数が内部で必要とするスタック領域が実際には `$32` バイトよりも大きかったか、または将来的な互換性やアライメント要件のために拡張されたことを示唆しています。この関数は引数を受け取らないため、`argsize` は指定されていません（または `0` と解釈されます）。

3.  **`runtime.usleep(SB)`**:
    *   変更前: `$12`
    *   変更後: `$24`
    *   `runtime.usleep` 関数は、指定されたマイクロ秒数だけ現在のゴルーチンをスリープさせるGoの内部関数です。この関数もOSのシステムコール（`usleep` など）を呼び出します。元の `$12` バイトのフレームサイズでは不十分であり、`$24` バイトに拡張されました。これは、システムコールへの引数の準備、レジスタの保存、またはその他のローカル変数に、より多くのスタック領域が必要になったためと考えられます。この関数は12バイトの引数（`usec`）を受け取るため、`argsize` は `-12` となっています。

これらの変更は、GoランタイムがDarwin/ARM64上でシステムコールを正確に呼び出し、その結果を安全に処理するために、スタックフレームの管理をより厳密に行う必要があったことを示しています。特に、アセンブリレベルでのスタックフレームサイズの不一致は、予測不能なバグやクラッシュに直結するため、このような修正はランタイムの安定性にとって非常に重要です。

## コアとなるコードの解説

変更された各 `TEXT` ディレクティブについて詳しく見ていきます。

1.  **`TEXT time·now(SB),NOSPLIT,$32-12` から `TEXT time·now(SB),NOSPLIT,$40-12`**:
    *   `time·now(SB)`: Goの `time.now` 関数に対応するアセンブリシンボルです。
    *   `NOSPLIT`: この関数はスタックの拡張チェックを行いません。
    *   `$32-12` から `$40-12`:
        *   `$32` (変更前) および `$40` (変更後) は、この関数がローカル変数や一時的なデータのためにスタック上に確保するバイトサイズです。この値が32バイトから40バイトに増加しました。これは、関数内で使用されるスタック領域が実際には32バイトよりも大きかったか、またはアライメント要件や将来的な拡張のために余裕を持たせたことを意味します。
        *   `-12`: この関数が呼び出し元から受け取る引数の合計バイトサイズが12バイトであることを示します。これは、`time.now` が何らかの引数（例えば、時刻情報を格納するポインタなど）を12バイト分受け取ることを意味します。

2.  **`TEXT runtime·nanotime(SB),NOSPLIT,$32` から `TEXT runtime·nanotime(SB),NOSPLIT,$40`**:
    *   `runtime·nanotime(SB)`: Goの `runtime.nanotime` 関数に対応するアセンブリシンボルです。
    *   `NOSPLIT`: この関数はスタックの拡張チェックを行いません。
    *   `$32` から `$40`:
        *   `$32` (変更前) および `$40` (変更後) は、この関数がローカル変数や一時的なデータのためにスタック上に確保するバイトサイズです。この値が32バイトから40バイトに増加しました。`time.now` と同様に、この関数が内部で必要とするスタック領域が実際には32バイトよりも大きかったか、またはアライメント要件のために拡張されたことを示唆しています。
        *   この関数には `-argsize` の指定がないため、引数を受け取らない（または引数サイズが0）ことを意味します。

3.  **`TEXT runtime·usleep(SB),NOSPLIT,$12` から `TEXT runtime·usleep(SB),NOSPLIT,$24`**:
    *   `runtime·usleep(SB)`: Goの `runtime.usleep` 関数に対応するアセンブリシンボルです。
    *   `NOSPLIT`: この関数はスタックの拡張チェックを行いません。
    *   `$12` から `$24`:
        *   `$12` (変更前) および `$24` (変更後) は、この関数がローカル変数や一時的なデータのためにスタック上に確保するバイトサイズです。この値が12バイトから24バイトに増加しました。これは、`runtime.usleep` がシステムコールを呼び出す際に、引数の準備やレジスタの保存、またはその他のローカル変数に、より多くのスタック領域が必要になったためと考えられます。
        *   この関数には `-argsize` の指定がないため、引数を受け取らない（または引数サイズが0）ことを意味します。ただし、`MOVW usec+0(FP), R0` の行から、`usec` という引数がフレームポインタからのオフセットでアクセスされていることがわかります。これは、`TEXT` ディレクティブの `$framesize-argsize` の形式において、`argsize` が省略された場合でも、関数が引数を受け取ることがあるというGoアセンブリの慣習を示しています。この場合、`usec+0(FP)` は、呼び出し元から渡された `usec` 引数がスタックフレームのどこかに配置されていることを示唆しています。

これらの変更は、GoランタイムがDarwin/ARM64上でシステムコールを呼び出す際のスタックフレームの正確性を保証するために行われました。スタックフレームサイズの正確な設定は、プログラムの安定性とセキュリティにとって不可欠です。

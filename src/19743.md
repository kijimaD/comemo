# [インデックス 19743] ファイルの概要

このコミットは、GoランタイムにおいてゴルーチンIDの採番を1から開始するように変更するものです。これにより、メインゴルーチン（プログラムのエントリポイントとなるゴルーチン）のIDが常に1となることが保証され、デバッグやログ出力における識別がより直感的になります。

## 変更の背景

Goランタイムでは、各ゴルーチンに一意のID（`goid`）が割り当てられます。このIDは、デバッグ情報、プロファイリング、または特定のゴルーチンを識別する必要がある場合に利用されます。このコミット以前は、ゴルーチンIDの採番が0から開始されていた可能性があります。しかし、多くのシステムやプログラミング言語において、IDの採番は1から開始されるのが一般的であり、特にメインスレッドやメインプロセスにID 1を割り当てる慣習があります。

この変更の背景には、GoプログラムのメインゴルーチンにID 1を割り当てることで、以下のような利点があると考えられます。

*   **直感的な識別**: メインゴルーチンがID 1を持つことで、デバッグ時やログ解析時にどのゴルーチンがメインであるかを容易に識別できるようになります。これは、特に複数のゴルーチンが動作する複雑なアプリケーションにおいて、問題の切り分けを迅速に行う上で役立ちます。
*   **慣習との整合性**: 多くのプログラミング環境やOSにおいて、メインの実行単位（プロセスやスレッド）にID 1を割り当てる慣習があります。Goランタイムもこれに合わせることで、開発者が他のシステムからGoに移行する際の学習コストを低減し、より自然な感覚で開発を進められるようになります。
*   **テストの明確化**: `crash_test.go`に追加されたテストケースが示すように、メインゴルーチンがID 1を持つことを明示的に検証できるようになります。これにより、ランタイムの挙動が期待通りであることを保証し、将来的な変更による意図しない挙動の発生を防ぎます。

## 前提知識の解説

### Goにおけるゴルーチン (Goroutine)

ゴルーチンはGo言語における軽量な実行スレッドです。OSのスレッドよりもはるかに軽量であり、数千、数万といった単位で同時に実行することができます。ゴルーチンはGoランタイムによって管理され、GoスケジューラがOSスレッドへのマッピングや実行の切り替えを行います。`go`キーワードを使って関数を呼び出すことで、新しいゴルーチンが生成されます。

### ゴルーチンID (Goroutine ID)

各ゴルーチンには、ランタイムによって一意の整数IDが割り当てられます。このIDは、ゴルーチンのライフサイクルを通じて不変であり、主にデバッグやプロファイリングの目的で使用されます。例えば、パニック発生時のスタックトレースには、どのゴルーチンでパニックが発生したかを示すためにゴルーチンIDが含まれます。

### Goランタイムスケジューラ (Go Runtime Scheduler)

Goランタイムスケジューラは、ゴルーチンをOSスレッドにマッピングし、実行を管理するGoランタイムの中核部分です。G-M-Pモデル（Goroutine-Machine-Processor）に基づいて動作し、多数のゴルーチンを効率的に並行実行できるようにします。スケジューラは、ゴルーチンの生成、実行、停止、およびOSスレッドへの割り当てを制御します。

### アトミック操作 (Atomic Operations)

アトミック操作とは、複数のCPUコアやスレッドから同時にアクセスされた場合でも、その操作が中断されることなく完全に実行されることを保証する操作です。これにより、共有データへのアクセスにおける競合状態（Race Condition）を防ぎ、データの整合性を保ちます。Goランタイムでは、ゴルーチンIDの生成など、複数のゴルーチンから同時にアクセスされる可能性のあるカウンタの更新にアトミック操作が用いられます。`runtime·xadd64`は、Goランタイム内部で使用される64ビット整数に対するアトミックな加算操作です。

### `GoidCacheBatch`

`GoidCacheBatch`は、ゴルーチンIDを効率的に割り当てるためのバッチサイズを定義する定数です。Goランタイムは、ゴルーチンIDを一つずつアトミックに取得するのではなく、一度に`GoidCacheBatch`個のIDのブロックを確保し、それを各P（Processor、論理CPU）のローカルキャッシュに割り当てます。これにより、ID割り当ての際のグローバルなアトミック操作の回数を減らし、パフォーマンスを向上させます。

## 技術的詳細

このコミットの技術的な核心は、`src/pkg/runtime/proc.c`内のゴルーチンID割り当てロジックの変更にあります。具体的には、`runtime·newproc1`関数内で新しいゴルーチンにIDを割り当てる際に、`runtime·sched.goidgen`というグローバルなゴルーチンIDジェネレータの値を調整しています。

変更前は、`runtime·sched.goidgen`が0から始まり、最初のゴルーチン（メインゴルーチン）にID 0が割り当てられていた可能性があります。このコミットでは、`runtime·sched.goidgen`が初期値0の場合に、最初のIDブロックが`[1, GoidCacheBatch]`となるように調整が加えられています。

変更されたコードスニペットは以下の通りです。

```c
// Sched.goidgen is the last allocated id,
// this batch must be [sched.goidgen+1, sched.goidgen+GoidCacheBatch].
// At startup sched.goidgen=0, so main goroutine receives goid=1.
p->goidcache = runtime·xadd64(&runtime·sched.goidgen, GoidCacheBatch);
p->goidcache -= GoidCacheBatch - 1;
p->goidcacheend = p->goidcache + GoidCacheBatch;
```

ここで重要なのは以下の点です。

1.  **`runtime·xadd64(&runtime·sched.goidgen, GoidCacheBatch)`**:
    *   `runtime·sched.goidgen`は、最後に割り当てられたゴルーチンIDを保持するグローバルなカウンタです。
    *   `runtime·xadd64`は、`runtime·sched.goidgen`に`GoidCacheBatch`の値をアトミックに加算し、加算前の値を返します。
    *   例えば、`runtime·sched.goidgen`が初期値0の場合、この操作により`runtime·sched.goidgen`は`GoidCacheBatch`になり、`p->goidcache`には0が設定されます（加算前の値が返されるため）。

2.  **`p->goidcache -= GoidCacheBatch - 1;`**:
    *   この行が、IDの採番を1から開始するための鍵となる調整です。
    *   上記の例で`p->goidcache`が0の場合、`0 - (GoidCacheBatch - 1)`が計算されます。
    *   もし`GoidCacheBatch`が例えば16であれば、`0 - (16 - 1) = -15`となります。
    *   これにより、`p->goidcache`は、そのバッチで割り当てられる最初のIDの「一つ前」の値に設定されます。

3.  **`p->goidcacheend = p->goidcache + GoidCacheBatch;`**:
    *   `p->goidcacheend`は、現在のPが利用できるIDキャッシュの終了点を示します。

4.  **`newg->goid = p->goidcache++;`**:
    *   新しいゴルーチン`newg`にIDが割り当てられます。`p->goidcache`がインクリメントされるため、`p->goidcache`が指す値が現在のゴルーチンに割り当てられ、次のゴルーチンにはその次のIDが割り当てられます。

このロジックにより、`runtime·sched.goidgen`が0から始まる場合でも、最初の`p->goidcache`は1となり、結果としてメインゴルーチンにはID 1が割り当てられるようになります。その後のゴルーチンには、`GoidCacheBatch`の範囲内で連続したIDが割り当てられ、`p->goidcache`が尽きると再度グローバルな`runtime·sched.goidgen`から新しいバッチが取得されます。

`src/pkg/runtime/crash_test.go`への変更は、この新しい挙動を検証するためのテストケースの追加です。`TestMainGoroutineId`という新しいテスト関数が追加され、パニック発生時のスタックトレースにおいて、メインゴルーチンのIDが「1」であることを確認しています。これは、ランタイムの変更が期待通りに機能していることを保証するための重要なテストです。

## コアとなるコードの解説

### `src/pkg/runtime/proc.c` の変更

このファイルはGoランタイムのプロセッサ管理とゴルーチン生成に関するコードを含んでいます。変更は`runtime·newproc1`関数内で行われています。この関数は新しいゴルーチンを作成する際に呼び出されます。

*   **変更前**:
    `p->goidcache = runtime·xadd64(&runtime·sched.goidgen, GoidCacheBatch);`
    この行は、グローバルなゴルーチンIDジェネレータ`runtime·sched.goidgen`から`GoidCacheBatch`個のIDをアトミックに取得し、その開始IDを`p->goidcache`に設定していました。もし`runtime·sched.goidgen`が0から始まると、最初の`p->goidcache`も0になり、結果として最初のゴルーチン（メインゴルーチン）のIDが0になっていました。

*   **変更後**:
    ```c
    // Sched.goidgen is the last allocated id,
    // this batch must be [sched.goidgen+1, sched.goidgen+GoidCacheBatch].
    // At startup sched.goidgen=0, so main goroutine receives goid=1.
    p->goidcache = runtime·xadd64(&runtime·sched.goidgen, GoidCacheBatch);
    p->goidcache -= GoidCacheBatch - 1;
    p->goidcacheend = p->goidcache + GoidCacheBatch;
    ```
    追加されたコメントは、この変更の意図を明確に示しています。「起動時に`sched.goidgen=0`なので、メインゴルーチンは`goid=1`を受け取る」とあります。
    `p->goidcache = runtime·xadd64(&runtime·sched.goidgen, GoidCacheBatch);` の行は以前と同じく、`runtime·sched.goidgen`から`GoidCacheBatch`個のIDブロックを取得します。
    しかし、その直後に `p->goidcache -= GoidCacheBatch - 1;` という行が追加されています。
    この減算操作により、`p->goidcache`の値が調整されます。
    例えば、`GoidCacheBatch`が16で、`runtime·sched.goidgen`が初期値0の場合を考えます。
    1.  `runtime·xadd64(&runtime·sched.goidgen, GoidCacheBatch)` は、`runtime·sched.goidgen`を0から16に更新し、`p->goidcache`には加算前の値である0が設定されます。
    2.  `p->goidcache -= GoidCacheBatch - 1;` は、`p->goidcache = 0 - (16 - 1) = 0 - 15 = -15` となります。
    3.  次に`newg->goid = p->goidcache++;` が実行されると、`newg->goid`には`-15`が割り当てられ、`p->goidcache`は`-14`になります。
    これは一見するとIDが負の値になるように見えますが、Goの内部では`goid`は`int64`型であり、負の値も取り得ます。重要なのは、この調整によって、`p->goidcache`が指す最初の有効なIDが1になるように、オフセットが設定されることです。
    このロジックにより、`p->goidcache`が指す最初のIDが1となり、メインゴルーチンにID 1が割り当てられることが保証されます。

このファイルはGoランタイムのクラッシュテストに関するコードを含んでいます。変更は、メインゴルーチンIDが1であることを検証するための新しいテストケースの追加です。

アトミック操作とは、複数のCPUコアやスレッドから同時にアクセスされた場合でも、その操作が中断されることなく完全に実行されることを保証する操作です。これにより、共有データへのアクセスにおける競合状態（Race Condition）を防ぎ、データの整合性を保ちます。Goランタイムでは、ゴルーチンIDの生成など、複数のゴルーチンから同時にアクセスされる可能性のあるカウンタの更新にアトミック操作が用いられます。

### `sched.goidgen` と `GoidCacheBatch`

*   **`sched.goidgen`**: これはGoランタイム内のグローバルなカウンタであり、新しいゴルーチンIDを生成するための基点となります。初期値は0です。
*   **`GoidCacheBatch`**: これは、ゴルーチンIDを効率的に割り当てるためのバッチサイズを定義する定数です。Goランタイムは、ゴルーチンIDを一つずつアトミックに取得するのではなく、一度に`GoidCacheBatch`個のIDのブロックを確保し、それを各P（Processor、論理CPU）のローカルキャッシュに割り当てます。これにより、ID割り当ての際のグローバルなアトミック操作の回数を減らし、パフォーマンスを向上させます。各Pは、`goidcache`と`goidcacheend`という内部変数を用いて、現在利用可能なIDのバッチを管理します。

## 技術的詳細

このコミットの技術的な核心は、`src/pkg/runtime/proc.c`内のゴルーチンID割り当てロジックの変更にあります。具体的には、`runtime·newproc1`関数内で新しいゴルーチンにIDを割り当てる際に、`runtime·sched.goidgen`というグローバルなゴルーチンIDジェネレータの値を調整しています。

変更前は、`runtime·sched.goidgen`が0から始まり、最初のゴルーチン（メインゴルーチン）にID 0が割り当てられていた可能性があります。このコミットでは、`runtime·sched.goidgen`が初期値0の場合に、最初のIDブロックが`[1, GoidCacheBatch]`となるように調整が加えられています。

変更されたコードスニペットは以下の通りです。

```c
// Sched.goidgen is the last allocated id,
// this batch must be [sched.goidgen+1, sched.goidgen+GoidCacheBatch].
// At startup sched.goidgen=0, so main goroutine receives goid=1.
p->goidcache = runtime·xadd64(&runtime·sched.goidgen, GoidCacheBatch);
p->goidcache -= GoidCacheBatch - 1;
p->goidcacheend = p->goidcache + GoidCacheBatch;
```

ここで重要なのは以下の点です。

1.  **`p->goidcache = runtime·xadd64(&runtime·sched.goidgen, GoidCacheBatch);`**:
    *   `runtime·sched.goidgen`は、最後に割り当てられたゴルーチンIDを保持するグローバルなカウンタです。
    *   `runtime·xadd64`は、`runtime·sched.goidgen`に`GoidCacheBatch`の値をアトミックに加算し、**加算前の値**を返します。
    *   例えば、`runtime·sched.goidgen`が初期値0の場合、この操作により`runtime·sched.goidgen`は`GoidCacheBatch`になり、`p->goidcache`には0が設定されます（加算前の値が返されるため）。

2.  **`p->goidcache -= GoidCacheBatch - 1;`**:
    *   この行が、IDの採番を1から開始するための鍵となる調整です。
    *   上記の例で`p->goidcache`が0の場合、`0 - (GoidCacheBatch - 1)`が計算されます。
    *   もし`GoidCacheBatch`が例えば16であれば、`0 - (16 - 1) = -15`となります。
    *   これにより、`p->goidcache`は、そのバッチで割り当てられる最初のIDの「一つ前」の値に設定されます。この負の値は、Goの内部で`goid`が`int64`型であるため問題ありません。重要なのは、この調整によって、`p->goidcache`が指す最初の有効なIDが1になるように、オフセットが設定されることです。

3.  **`p->goidcacheend = p->goidcache + GoidCacheBatch;`**:
    *   `p->goidcacheend`は、現在のPが利用できるIDキャッシュの終了点を示します。

4.  **`newg->goid = p->goidcache++;`**:
    *   新しいゴルーチン`newg`にIDが割り当てられます。`p->goidcache`がインクリメントされるため、`p->goidcache`が指す値が現在のゴルーチンに割り当てられ、次のゴルーチンにはその次のIDが割り当てられます。

このロジックにより、`runtime·sched.goidgen`が0から始まる場合でも、最初の`p->goidcache`は1となり、結果としてメインゴルーチンにはID 1が割り当てられるようになります。その後のゴルーチンには、`GoidCacheBatch`の範囲内で連続したIDが割り当てられ、`p->goidcache`が尽きると再度グローバルな`runtime·sched.goidgen`から新しいバッチが取得されます。

`src/pkg/runtime/crash_test.go`への変更は、この新しい挙動を検証するためのテストケースの追加です。`TestMainGoroutineId`という新しいテスト関数が追加され、パニック発生時のスタックトレースにおいて、メインゴルーチンのIDが「1」であることを確認しています。これは、ランタイムの変更が期待通りに機能していることを保証するための重要なテストです。

## コアとなるコードの解説

### `src/pkg/runtime/proc.c` の変更

このファイルはGoランタイムのプロセッサ管理とゴルーチン生成に関するコードを含んでいます。変更は`runtime·newproc1`関数内で行われています。この関数は新しいゴルーチンを作成する際に呼び出されます。

*   **変更前**:
    `p->goidcache = runtime·xadd64(&runtime·sched.goidgen, GoidCacheBatch);`
    この行は、グローバルなゴルーチンIDジェネレータ`runtime·sched.goidgen`から`GoidCacheBatch`個のIDをアトミックに取得し、その開始IDを`p->goidcache`に設定していました。もし`runtime·sched.goidgen`が0から始まると、最初の`p->goidcache`も0になり、結果として最初のゴルーチン（メインゴルーチン）のIDが0になっていました。

*   **変更後**:
    ```c
    // Sched.goidgen is the last allocated id,
    // this batch must be [sched.goidgen+1, sched.goidgen+GoidCacheBatch].
    // At startup sched.goidgen=0, so main goroutine receives goid=1.
    p->goidcache = runtime·xadd64(&runtime·sched.goidgen, GoidCacheBatch);
    p->goidcache -= GoidCacheBatch - 1;
    p->goidcacheend = p->goidcache + GoidCacheBatch;
    ```
    追加されたコメントは、この変更の意図を明確に示しています。「起動時に`sched.goidgen=0`なので、メインゴルーチンは`goid=1`を受け取る」とあります。
    `p->goidcache = runtime·xadd64(&runtime·sched.goidgen, GoidCacheBatch);` の行は以前と同じく、`runtime·sched.goidgen`から`GoidCacheBatch`個のIDブロックを取得します。
    しかし、その直後に `p->goidcache -= GoidCacheBatch - 1;` という行が追加されています。
    この減算操作により、`p->goidcache`の値が調整されます。
    例えば、`GoidCacheBatch`が16で、`runtime·sched.goidgen`が初期値0の場合を考えます。
    1.  `runtime·xadd64(&runtime·sched.goidgen, GoidCacheBatch)` は、`runtime·sched.goidgen`を0から16に更新し、`p->goidcache`には加算前の値である0が設定されます。
    2.  `p->goidcache -= GoidCacheBatch - 1;` は、`p->goidcache = 0 - (16 - 1) = 0 - 15 = -15` となります。
    3.  次に`newg->goid = p->goidcache++;` が実行されると、`newg->goid`には`-15`が割り当てられ、`p->goidcache`は`-14`になります。
    これは一見するとIDが負の値になるように見えますが、Goの内部では`goid`は`int64`型であり、負の値も取り得ます。重要なのは、この調整によって、`p->goidcache`が指す最初の有効なIDが1になるように、オフセットが設定されることです。
    このロジックにより、`p->goidcache`が指す最初のIDが1となり、メインゴルーチンにID 1が割り当てられることが保証されます。

### `src/pkg/runtime/crash_test.go` の変更

このファイルはGoランタイムのクラッシュテストに関するコードを含んでいます。変更は、メインゴルーチンIDが1であることを検証するための新しいテストケースの追加です。

*   **`TestMainGoroutineId` 関数の追加**:
    このテスト関数は、`mainGoroutineIdSource`というGoプログラムを実行し、その出力（パニック時のスタックトレース）を検証します。
    `mainGoroutineIdSource`は非常にシンプルなプログラムで、`main`関数内で`panic("test")`を呼び出すだけです。
    テストは、出力が `"panic: test\n\ngoroutine 1 [running]:\n"` で始まることを期待しています。これは、パニックが発生したゴルーチンがID 1であることを明確に示しています。
    このテストの追加により、ランタイムがメインゴルーチンにID 1を正しく割り当てていることが自動的に検証されるようになり、将来のランタイム変更によってこの挙動が意図せず変更されることを防ぐことができます。

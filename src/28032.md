# [インデックス 28032] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における最適化に関するものです。具体的には、GCのマークフェーズの最終段階である「マーク終了（mark termination）」時に、不要なスパンルートのマーキングジョブがキューに入れられるのを防ぐ変更が加えられました。これにより、GCの効率が向上し、特にマーク終了時のオーバーヘッドが削減されます。

## 元コミット内容

現在の実装では、並行マークフェーズとマーク終了フェーズの両方でスパンルートのマークジョブがキューに入れられていました。しかし、マーク終了フェーズでキューに入れられたジョブは、実際には何もしない（no-op）処理となっていました。このコミットは、このような無駄なジョブのキューイングを最初から行わないようにすることで、この非効率性を解消します。

## 変更の背景

Goのガベージコレクタは、主に並行（concurrent）なマーク・アンド・スイープ方式を採用しています。このGCは、アプリケーションの実行と並行して動作し、短い「Stop-The-World (STW)」ポーズを最小限に抑えるように設計されています。GCのマークフェーズでは、到達可能なオブジェクト（ライブオブジェクト）を識別するために、プログラムの「ルート」（グローバル変数、スタック上のローカル変数、レジスタなど）からオブジェクトグラフを辿ります。

スパンルートのマーキングは、このルートスキャンの一部です。Goのメモリ管理では、メモリは「スパン（span）」と呼ばれる連続したブロックに分割されます。スパンルートのマーキングは、これらのスパン内に存在するルートオブジェクトを識別するプロセスです。

以前の実装では、並行マークフェーズでスパンルートのマーキングが適切に行われていたにもかかわらず、マーク終了フェーズでも同じ種類のジョブがキューに入れられていました。しかし、マーク終了フェーズでは、これらのジョブはすでに並行マークフェーズで処理済みであるため、実質的に何も行わない「no-op」として扱われていました。これは、GCの内部ロジックにおける冗長性と非効率性を示しており、不要な処理のキューイングとスケジューリングのオーバーヘッドが発生していました。このコミットは、この「無駄な」処理を排除し、GCの効率を向上させることを目的としています。

## 前提知識の解説

*   **Goのガベージコレクタ (GC):** GoのGCは、三色マーク・アンド・スイープアルゴリズムをベースにした並行GCです。主なフェーズは以下の通りです。
    *   **マーク開始 (Mark Start):** 短いSTWポーズでGCを開始し、初期ルートをスキャンします。
    *   **並行マーク (Concurrent Mark):** アプリケーションと並行して、オブジェクトグラフを辿り、到達可能なオブジェクトをマークします。
    *   **マーク終了 (Mark Termination):** 短いSTWポーズで、並行マーク中に発生した変更を処理し、マークフェーズを完了します。スタックのスキャンや、並行マーク中に見逃された可能性のあるオブジェクトの再スキャンなどが行われます。
    *   **並行スイープ (Concurrent Sweep):** アプリケーションと並行して、マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放します。
*   **GCルート (GC Roots):** ガベージコレクタがオブジェクトグラフの探索を開始する起点となるオブジェクトです。これには、実行中のゴルーチンのスタック上の変数、グローバル変数、レジスタなどが含まれます。
*   **スパン (Span):** Goランタイムのメモリ管理における基本的な単位です。ヒープメモリは、特定のサイズのオブジェクトを格納するために割り当てられた連続したページ（通常は8KB）のブロックであるスパンに分割されます。
*   **`gcWork`構造体:** GCの作業状態を管理するための内部構造体です。`work.nSpanRoots`は、スキャンする必要があるスパンルートの数を表します。`work.markrootDone`は、ルートマーキングが完了したかどうかを示すフラグです。
*   **`rootBlockSpans`:** スパンルートを処理する際のブロックサイズに関連する定数で、GCの並行処理の粒度を決定します。

## 技術的詳細

このコミットの核心は、`gcMarkRootPrepare`関数における`work.nSpanRoots`の計算ロジックの変更にあります。

GoのGCは、並行マークフェーズ中にほとんどのルートスキャンを実行します。このフェーズで、`work.nSpanRoots`が計算され、スパンルートのマーキングジョブがキューに入れられ、処理されます。マーク終了フェーズは、並行マークフェーズで取りこぼした可能性のあるルート（例えば、並行マーク中にスタックが変化したため）を処理するための最終的なSTWポーズです。

以前の実装では、`gcMarkRootPrepare`がマーク終了フェーズでも呼び出された際に、`work.nSpanRoots`が再度計算され、スパンルートのマーキングジョブがキューに入れられていました。しかし、`markrootSpans`関数内で`work.markrootDone`フラグがチェックされ、もしこのフラグが`true`であれば、`markrootSpans`は即座にリターンし、何も処理しないようになっていました。これは、並行マークフェーズで既にスパンルートが処理されているため、マーク終了フェーズでの再処理は不要だからです。

このコミットは、この冗長性を排除します。`gcMarkRootPrepare`内で`work.markrootDone`フラグをチェックし、もし`true`であれば（つまり、並行マークフェーズで既にスパンルートが処理済みであれば）、`work.nSpanRoots`を`0`に設定します。これにより、マーク終了フェーズではスパンルートのマーキングジョブがそもそもキューに入れられなくなり、無駄なジョブの作成とスケジューリングが回避されます。

また、`markrootSpans`関数も変更され、`work.markrootDone`が`true`の場合に`throw("markrootSpans during second markroot")`するように修正されました。これは、スパンルートのマーキングが二度行われるべきではないという不変条件を強制するためのアサーションとして機能します。

この変更により、GCのマーク終了フェーズにおける処理がより効率的になり、STWポーズの時間がわずかに短縮される可能性があります。

## コアとなるコードの解説

1.  **`gcMarkRootPrepare()` 関数内の変更:**
    *   以前は、`work.nSpanRoots`は常に`len(work.spans)`に基づいて計算されていました。
    *   変更後、`if !work.markrootDone`という条件が追加されました。
        *   もし`work.markrootDone`が`false`（つまり、これが最初のルートマーキングパスである）ならば、`work.nSpanRoots`は通常通り計算されます。これは、並行マークフェーズ中、またはSTW GC（非並行GC）のマーク終了フェーズで発生します。
        *   もし`work.markrootDone`が`true`（つまり、並行マークフェーズで既にスパンルートがスキャンされ、最新の状態に保たれている）ならば、`work.nSpanRoots`は`0`に設定されます。これにより、マーク終了フェーズでスパンルートのマーキングジョブがキューに入れられることがなくなります。

2.  **`markrootSpans()` 関数内の変更:**
    *   以前は、`if work.markrootDone { return }`となっており、2回目のルートマーキングパスでは単に処理をスキップしていました。
    *   変更後、`if work.markrootDone { throw("markrootSpans during second markroot") }`となりました。これは、`markrootSpans`が2回目のルートマーキングパスで呼び出されるべきではないという前提を強化するアサーションです。もし呼び出された場合は、ランタイムエラーを発生させ、予期せぬ動作を防ぎます。

これらの変更により、GoのGCは、スパンルートのマーキングに関して、並行マークフェーズで一度だけ処理を行い、マーク終了フェーズでの冗長なジョブのキューイングとチェックを完全に排除するようになりました。

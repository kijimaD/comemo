# [インデックス 24830] ファイルの概要

このコミットは、Goリンカー（`cmd/link`）の動作を修正し、`runtime.goarm`シンボルがGoランタイムパッケージを含むモジュールにのみ埋め込まれるように変更します。これにより、複数のモジュール（実行可能ファイルや共有ライブラリ）が存在する場合に、`runtime.goarm`が重複して埋め込まれるのを防ぎ、リンカーの効率性と正確性を向上させます。また、`runtime.firstmoduledata`シンボルの処理も改善され、ランタイムを含むモジュールでのみ適切に初期化されるようになります。

## 変更の背景

Goのプログラムは、複数のパッケージから構成され、最終的にリンカーによって実行可能ファイルや共有ライブラリにまとめられます。このプロセスにおいて、Goランタイムに関する特定の情報（例えば、ARMアーキテクチャにおける浮動小数点演算のサポートレベルを示す`GOARM`環境変数の値）は、生成されるバイナリに埋め込まれる必要があります。

以前の実装では、`runtime.goarm`というシンボルが、Goランタイムパッケージを含むかどうかに関わらず、リンクされるすべてのモジュール（実行可能ファイルや共有ライブラリ）に埋め込まれていました。これは、特に複数のGoモジュールがリンクされるような複雑なアプリケーションにおいて、冗長な情報となり、潜在的な競合や混乱を招く可能性がありました。`runtime.goarm`はランタイムの動作に影響を与えるため、その値は一意であるべきであり、ランタイム自体が管理するべき情報です。

また、Goのランタイムは、`runtime.firstmoduledata`というシンボルを通じて、プログラムのモジュール情報を管理しています。このシンボルは、プログラム内で最初にロードされるモジュール（通常はメインの実行可能ファイル）のモジュールデータ構造を指し示します。リンカーは、このシンボルを適切に設定することで、ランタイムが自身のモジュール情報を正確に把握できるようにする必要があります。

このコミットは、これらの問題を解決するために、`runtime.goarm`の埋め込みをランタイムパッケージを含むモジュールに限定し、`runtime.firstmoduledata`の処理ロジックを改善することで、リンカーの動作をより正確かつ効率的にすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoの内部概念とリンカーの動作に関する知識が必要です。

1.  **Goリンカー (`cmd/link`)**:
    Goコンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能ファイルや共有ライブラリを生成するツールです。シンボルの解決、メモリレイアウトの決定、ランタイム情報の埋め込みなど、多くの重要なタスクを担当します。

2.  **Goモジュール (Module)**:
    Go 1.11以降で導入された依存関係管理システムですが、ここではリンカーの文脈での「モジュール」は、より広義に「リンクされる単位」、つまり最終的な実行可能ファイルや共有ライブラリを指します。

3.  **`runtime.firstmoduledata`**:
    Goランタイムが内部的に使用するシンボルで、プログラム内で最初にロードされるモジュール（通常はメインの実行可能ファイル）の`moduledata`構造体へのポインタを保持します。この構造体には、モジュールの情報（シンボルテーブル、型情報、GC情報など）が含まれており、ランタイムがリフレクションやデバッグなどの機能を提供するために不可欠です。

4.  **`moduledata`構造体**:
    Goランタイムが各モジュールに関するメタデータを格納するために使用する内部構造体です。これには、モジュール内のシンボル、型、GC関連の情報などが含まれます。

5.  **`runtime.goarm`**:
    ARMアーキテクチャ向けのGoバイナリに埋め込まれるシンボルで、`GOARM`環境変数の値（通常は`5`、`6`、`7`など）を保持します。この値は、ARMプロセッサのバージョンや浮動小数点演算ユニット（FPU）の有無・種類に応じて、ランタイムが適切なコードパスを選択するために使用されます。例えば、`GOARM=7`はARMv7アーキテクチャでVFPv3-D16 FPUが利用可能であることを示唆します。

6.  **シンボルタイプ (`obj.SRODATA`, `obj.SDYNIMPORT`, `obj.SNOPTRDATA`)**:
    Goリンカーは、シンボルをその種類や特性に基づいて分類します。
    *   `obj.SRODATA`: 読み取り専用データセクションに配置されるシンボル。
    *   `obj.SDYNIMPORT`: 動的リンクされるシンボル。つまり、現在のモジュールでは定義されておらず、外部の共有ライブラリからインポートされるシンボル。
    *   `obj.SNOPTRDATA`: ポインタを含まないデータセクションに配置されるシンボル。GC（ガベージコレクション）の対象外となるため、GCスキャンを高速化できます。`moduledata`はGCの対象外とすべき情報であるため、このタイプが適用されます。

7.  **`Linklookup(Ctxt, name, version)`**:
    リンカーのコンテキスト（`Ctxt`）内で指定された名前（`name`）とバージョン（`version`）を持つシンボルを検索または作成する関数。

8.  **`Adduint8(Ctxt, s, val)`**:
    指定されたシンボル`s`に8ビットの符号なし整数値`val`を追加する関数。これは、シンボルにデータを埋め込むために使用されます。

## 技術的詳細

このコミットの主要な変更点は、`runtime.goarm`シンボルの埋め込みロジックと、`runtime.firstmoduledata`シンボルの処理方法にあります。

**1. `runtime.goarm`の埋め込みの限定:**

以前は、`src/cmd/link/internal/arm/obj.go`内の`archinit`関数で、無条件に`runtime.goarm`シンボルが作成され、現在のリンカーコンテキストの`Ctxt.Goarm`の値が埋め込まれていました。これは、Goランタイムパッケージがリンクされるかどうかに関わらず行われていました。

このコミットでは、`src/cmd/link/internal/arm/obj.go`から`runtime.goarm`の埋め込みコードが削除されました。代わりに、`src/cmd/link/internal/ld/lib.go`内の`loadlib`関数に移動され、`runtime.firstmoduledata`シンボルの存在をチェックするロジックの内部に配置されました。

新しいロジックでは、リンカーが処理しているモジュールが`runtime.firstmoduledata`シンボルを定義している場合（これはそのモジュールがGoランタイムパッケージを含んでいることを意味します）、そのモジュールにのみ`runtime.goarm`シンボルが作成され、`Ctxt.Goarm`の値が埋め込まれます。これにより、`runtime.goarm`がランタイムパッケージを含む単一のモジュールにのみ存在することが保証され、冗長な埋め込みが回避されます。

**2. `runtime.firstmoduledata`の処理改善:**

`loadlib`関数は、`runtime.firstmoduledata`シンボルを検索します。
*   **モジュールがランタイムパッケージを含む場合**: `moduledata.Type`が`0`（未定義）でも`obj.SDYNIMPORT`（動的インポート）でもない場合、そのモジュールが`runtime.firstmoduledata`を定義していると判断されます。この場合、リンカーはそのシンボルの`Size`を`0`に設定します。これは、`symtab.go:symtab()`でこのシンボルの内容全体を定義できるようにするためです。つまり、リンカーがこのモジュールに対して`moduledata`構造体の完全な内容を生成・埋め込む準備をします。このブロック内で、ARMアーキテクチャの場合にのみ`runtime.goarm`の埋め込みが行われます。
*   **モジュールがランタイムパッケージを含まない場合**: `moduledata.Type`が`0`または`obj.SDYNIMPORT`の場合、そのモジュールは`runtime.firstmoduledata`を定義していないと判断されます。この場合、リンカーは`local.moduledata`というローカルシンボルを作成し、それを`moduledata`として使用します。これは、ランタイムを含まないモジュールが自身のモジュールデータを持つ必要があるが、`runtime.firstmoduledata`を定義する責任はないためです。

**3. `moduledata`のGCからの隠蔽:**

どちらのケースでも、最終的に`moduledata`シンボルは`obj.SNOPTRDATA`タイプに設定され、`Reachable`が`true`に設定されます。`obj.SNOPTRDATA`は、そのデータがポインタを含まないことを示し、Goのガベージコレクタがこの領域をスキャンする必要がないことを意味します。これにより、GCのオーバーヘッドが削減され、パフォーマンスが向上します。

この変更により、Goリンカーは、`runtime.goarm`のようなアーキテクチャ固有のランタイム情報を、必要なモジュールにのみ正確に埋め込むようになり、Goのモジュールシステムとランタイムの連携がより堅牢になります。

## コアとなるコードの解説

### `src/cmd/link/internal/arm/obj.go` の変更

*   **削除されたコード**: `archinit`関数から、`runtime.goarm`シンボルを検索し、`obj.SRODATA`タイプに設定し、`Ctxt.Goarm`の値を埋め込む処理が完全に削除されました。
*   **意図**: これにより、ARMアーキテクチャ固有の初期化ロジックから、`runtime.goarm`の無条件な埋め込みがなくなりました。この責任は、より適切な場所である`lib.go`の`loadlib`関数に移管されます。

### `src/cmd/link/internal/ld/lib.go` の変更

*   **`moduledata`の条件分岐ロジックの変更**:
    *   変更前: `moduledata.Type == 0 || moduledata.Type == obj.SDYNIMPORT` の場合にローカルの`moduledata`を作成し、それ以外の場合（つまり、`runtime.firstmoduledata`が定義されている場合）に`moduledata.Size = 0`を設定していました。
    *   変更後: `moduledata.Type != 0 && moduledata.Type != obj.SDYNIMPORT` の場合に、そのモジュールがランタイムパッケージを含んでいると判断します。
        *   この条件が真の場合（ランタイムパッケージを含むモジュールの場合）:
            *   `moduledata.Size = 0` を設定し、`symtab.go:symtab()`で`moduledata`の全内容を定義できるようにします。
            *   **ARM固有のロジックを追加**: `Thearch.Thechar == '5'` (ARMアーキテクチャを示す) の場合にのみ、`runtime.goarm`シンボルを検索し、`obj.SRODATA`タイプに設定し、`Ctxt.Goarm`の値を埋め込みます。これにより、`runtime.goarm`はランタイムパッケージを含むモジュールにのみ埋め込まれるようになります。
        *   この条件が偽の場合（ランタイムパッケージを含まないモジュールの場合）:
            *   `local.moduledata`というローカルシンボルを作成し、`moduledata`として使用します。`moduledata.Local = true`を設定します。
*   **`moduledata`のタイプ設定**:
    *   変更前: `// Either way we mark it as noptrdata to hide it from the GC.` とコメントがあり、`moduledata.Type = obj.SNOPTRDATA` と `moduledata.Reachable = true` が設定されていました。
    *   変更後: `// In all cases way we mark the moduledata as noptrdata to hide it from // the GC.` とコメントが変更され、同様に`moduledata.Type = obj.SNOPTRDATA` と `moduledata.Reachable = true` が設定されています。これは、`moduledata`がポインタを含まないデータであり、GCの対象外とすべきであるという意図を明確にしています。

これらの変更により、`runtime.goarm`はGoランタイムパッケージを含むモジュールにのみ適切に埋め込まれるようになり、`runtime.firstmoduledata`の処理も、ランタイムの有無に応じて適切に分岐されるようになりました。これにより、リンカーの動作がより正確になり、特に複数のGoモジュールがリンクされるシナリオでの潜在的な問題が解消されます。

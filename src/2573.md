# [インデックス 2573] ファイルの概要

このコミットは、Goコンパイラの一つであるgccgoが生成するエラーメッセージを、Goのテストスイートが正しく認識できるようにするための変更です。具体的には、`len`や`cap`組み込み関数に不正な型の引数が渡された際に発生するエラーメッセージのパターンを、テストコードがより柔軟に受け入れるように修正しています。これにより、異なるコンパイラ（この場合はgcとgccgo）間でエラーメッセージの文言が多少異なっていても、テストがパスするようになります。

## 変更の背景

Go言語の開発初期段階において、Goには主に2つのコンパイラが存在しました。一つはGoチームが開発した公式コンパイラである`gc`（Go Compiler）、もう一つはGCC（GNU Compiler Collection）をベースにした`gccgo`です。これら2つのコンパイラは、Go言語の仕様に準拠しつつも、実装の詳細やエラーメッセージの生成方法において差異が生じることがありました。

Goのテストスイートは、コンパイラが特定のコードに対して期待されるエラーを正しく報告するかどうかを検証するために、エラーメッセージのテキストパターンをチェックする仕組みを持っています。このコミットが行われた2009年7月時点では、`gccgo`が生成するエラーメッセージが、既存の`gc`向けに書かれたテストの期待値と完全に一致しないケースがありました。

具体的には、`len`や`cap`といった組み込み関数に不正な型の引数を渡した場合、`gc`は「illegal」というキーワードを含むエラーメッセージを出すことが多かったのに対し、`gccgo`はより詳細な「argument must be string or array or slice or map」のようなメッセージを生成していました。この差異により、`gccgo`でテストを実行すると、本来は成功すべきテストがエラーメッセージの不一致で失敗してしまう問題が発生していました。

このコミットの目的は、`gccgo`が生成するエラーメッセージもテストスイートが正しく「認識」できるように、テストコード内のエラーメッセージ期待値を更新することでした。これにより、両方のコンパイラでGo言語のテストが安定して実行され、Go言語の移植性と互換性が確保されることに貢献しました。コミットメッセージにある「Amusing side note」は、GNUコーディング標準における「illegal」という言葉の使用に関する推奨事項に触れており、エラーメッセージの文言が単なる技術的な問題だけでなく、言葉遣いの規範にも関連していることを示唆しています。

## 前提知識の解説

### Go言語のコンパイラ (gcとgccgo)

*   **gc (Go Compiler)**: Go言語の公式コンパイラであり、Goチームによって開発されています。Go言語のリリースとともに提供され、Goの標準的なビルドツールチェーンの一部です。高速なコンパイルとGoランタイムとの密接な統合が特徴です。
*   **gccgo**: GCCのフロントエンドとして実装されたGoコンパイラです。GCCの最適化バックエンドを利用できるため、生成されるバイナリのパフォーマンスが向上する可能性があります。しかし、開発初期には`gc`とは異なる挙動やエラーメッセージを生成することがありました。

### Goのテストスイートとエラーメッセージの検証

Go言語のソースコードリポジトリには、言語仕様や標準ライブラリの動作を検証するための広範なテストスイートが含まれています。これらのテストの中には、コンパイルエラーやランタイムエラーが期待される特定のコードスニペットをコンパイル・実行し、その際に発生するエラーメッセージの内容をチェックするものがあります。

テストコードでは、期待されるエラーメッセージのパターンをコメントとして記述することが一般的です。例えば、`// ERROR "some pattern"` のように記述することで、その行でコンパイラが「some pattern」にマッチするエラーメッセージを出すことを期待します。この仕組みにより、コンパイラの実装がGoの仕様に準拠しているか、あるいは特定の不正なコードに対して適切な診断メッセージを出しているかを自動的に検証できます。

### `len`と`cap`組み込み関数

Go言語には、スライス、配列、マップ、文字列、チャネルの長さや容量を取得するための組み込み関数`len`と`cap`があります。

*   **`len(v)`**:
    *   配列`v`の要素数。
    *   配列ポインタ`v`が指す配列の要素数。
    *   スライス`v`の要素数。
    *   文字列`v`のバイト数。
    *   マップ`v`のキーと要素のペアの数。
    *   チャネル`v`のバッファ内のキューに入れられた要素の数。
    *   これらの型以外の引数に対して`len`を使用すると、コンパイルエラーになります。
*   **`cap(v)`**:
    *   配列`v`の要素数。
    *   配列ポインタ`v`が指す配列の要素数。
    *   スライス`v`の基底配列の容量。
    *   チャネル`v`のバッファ容量。
    *   これらの型以外の引数に対して`cap`を使用すると、コンパイルエラーになります。

このコミットで修正された`indirect1.go`のテストケースは、これらの`len`や`cap`関数に不正な型の引数を渡すことで、コンパイラが適切なエラーを報告するかどうかを検証していました。

## 技術的詳細

このコミットの技術的な核心は、Goのテストフレームワークにおけるエラーメッセージのパターンマッチングの柔軟性を高めることにあります。Goのテストファイルでは、特定の行でコンパイルエラーが発生することを期待する場合、その行の末尾に`// ERROR "pattern"`という形式のコメントを追加します。コンパイラがその行でエラーを報告し、かつそのエラーメッセージが指定された`pattern`にマッチすれば、テストは成功とみなされます。

このコミットでは、`test/indirect1.go`ファイル内の複数の行で、期待されるエラーパターンを`"illegal"`から`"illegal|must be"`に変更しています。

*   **変更前**: `// ERROR "illegal"`
    *   これは、エラーメッセージに「illegal」という文字列が**完全に一致**することを期待していました。
*   **変更後**: `// ERROR "illegal|must be"`
    *   これは、エラーメッセージに「illegal」または「must be」のいずれかの文字列が**含まれる**ことを期待します。`|`は正規表現のOR演算子として機能します。

この変更により、`gc`コンパイラが「illegal」を含むエラーメッセージを生成する場合でも、`gccgo`コンパイラが「argument must be string or array or slice or map」や「argument must be array or slice」のような「must be」を含むより詳細なエラーメッセージを生成する場合でも、両方のケースでテストが成功するようになります。

これは、コンパイラの実装詳細に依存するエラーメッセージの文言の差異を吸収し、テストの堅牢性を高めるための一般的な手法です。特に、複数のコンパイラ実装が存在する言語において、共通のテストスイートを維持するためにはこのような柔軟性が必要不可欠です。

コミットメッセージに記載されている`indirect1.go`のエラーメッセージ例は、`gccgo`が実際に生成していたエラーメッセージの具体的な内容を示しており、この変更がどのような具体的なエラーメッセージの差異に対応するためのものであったかを明確にしています。

## コアとなるコードの解説

`test/indirect1.go`ファイルは、Go言語の型システムと組み込み関数`len`および`cap`の挙動をテストするためのものです。このファイルには、意図的に不正な型の引数を`len`や`cap`に渡すコードが含まれており、コンパイラがこれらの不正な使用に対して適切なエラーを報告することを期待しています。

変更された行はすべて、`len`または`cap`関数が、その関数が適用できない型の変数（例: 整数型や構造体型など）に対して呼び出されている箇所です。

例えば、以下の行を見てみましょう。

```go
len(m1)+	// ERROR "illegal"  (変更前)
len(m1)+	// ERROR "illegal|must be" (変更後)
```

ここで`m1`は、`len`関数が適用できない型（おそらく数値型や構造体型）の変数であると想定されます。元のテストでは、この行でコンパイラが「illegal」という文字列を含むエラーメッセージを出すことを期待していました。しかし、`gccgo`が「argument must be string or array or slice or map」のようなメッセージを出すため、テストが失敗していました。

変更後の`"illegal|must be"`というパターンは、正規表現のOR演算子`|`を使用しています。これは、「エラーメッセージが`illegal`という文字列を含むか、または`must be`という文字列を含むか」のいずれかの条件を満たせばテストが成功することを意味します。

この修正により、`gc`コンパイラが引き続き「illegal」を含むエラーを報告する場合でも、`gccgo`コンパイラがより詳細な「argument must be...」という形式のエラーを報告する場合でも、両方のコンパイラでこのテストケースがパスするようになります。これは、Go言語のテストスイートが複数のコンパイラ実装に対して互換性を保つための重要な調整です。

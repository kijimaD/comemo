## 元コミット内容

`debug/dwarf`: Split DWARFのテストを追加

このコミットは、`debug/dwarf` がSplit DWARFイメージからスケルトンDWARFデータを読み取れることを確認するテストを追加します（ただし、外部DWARFデータを再結合する機能はまだサポートしていません）。スケルトンDWARFデータ自体には特別な違いがないため、この機能は動作するはずですが、以前は認識されない属性の不適切な処理が原因で失敗していました。

## 変更の背景

この変更の背景には、Go言語の `debug/dwarf` パッケージが、Split DWARF形式で生成されたデバッグ情報を含むバイナリファイルを適切に解析できないという問題がありました (Issue #12592)。

Split DWARFは、コンパイルされたバイナリのサイズを削減し、リンキング時間を短縮するために使用されるデバッグ情報の形式です。この形式では、デバッグ情報の一部（スケルトンDWARF）が実行可能ファイル内に残り、残りの大部分（外部DWARF）は別のファイル（通常は `.dwo` または `.debug` 拡張子を持つファイル）に格納されます。

`debug/dwarf` パッケージは、DWARFデバッグ情報を解析するためのGoの標準ライブラリですが、Split DWARF形式のファイルに遭遇した際に、特に認識できない（Goの `debug/dwarf` が直接サポートしていない）属性が含まれている場合に、その処理が不十分であったため、デバッグ情報の読み込み全体が失敗していました。このコミットは、この問題に対処し、少なくともスケルトンDWARFデータを読み取れるようにするためのテストを追加することで、パーサーの堅牢性を向上させることを目的としています。

## 前提知識の解説

### DWARF (Debugging With Arbitrary Record Formats)

DWARFは、コンパイラが生成するデバッグ情報の標準フォーマットです。プログラムのソースコードとコンパイルされたバイナリコードとの間のマッピングを提供し、デバッガがソースレベルでプログラムの実行を追跡できるようにします。これには、変数名、型情報、関数名、行番号とアドレスのマッピング、スタックフレームの構造などが含まれます。DWARF情報は通常、実行可能ファイル内の特別なセクション（例: `.debug_info`, `.debug_abbrev` など）に格納されます。

### Split DWARF

Split DWARFは、DWARFデバッグ情報のサイズを管理するための最適化手法です。従来のDWARFでは、すべてのデバッグ情報が単一の実行可能ファイルまたは共有ライブラリに埋め込まれていました。これにより、特に大規模なプロジェクトでは、バイナリのサイズが非常に大きくなり、リンキング時間が長くなるという問題がありました。

Split DWARFでは、デバッグ情報を「スケルトンDWARF」と「外部DWARF」の2つの部分に分割します。
*   **スケルトンDWARF (Skeleton DWARF)**: 実行可能ファイル内に残る最小限のデバッグ情報です。これには、コンパイル単位（ソースファイル）の基本的な情報や、外部DWARFファイルへの参照などが含まれます。デバッガはまずこのスケルトンDWARFを読み込み、必要に応じて外部DWARFファイルをロードします。
*   **外部DWARF (External DWARF)**: 大量の詳細なデバッグ情報（例: すべての変数や型の詳細）が格納される別のファイル（通常は `.dwo` または `.debug` 拡張子を持つ）です。

Split DWARFを使用することで、実行可能ファイルのサイズを削減し、リンキングプロセスを高速化できます。`gcc` コンパイラでは、`-gsplit-dwarf` オプションを使用してSplit DWARF形式のデバッグ情報を生成できます。

### `debug/dwarf` パッケージ

`debug/dwarf` はGo言語の標準ライブラリの一部であり、DWARFデバッグ情報を解析するための機能を提供します。このパッケージは、Goプログラムが他の言語（C/C++など）で書かれたライブラリや実行可能ファイルのデバッグ情報を検査したり、Go自身のデバッグ情報を処理したりするために使用されます。

### DWARF属性 (Attributes)

DWARF情報モデルでは、プログラムエンティティ（変数、関数、型など）は「デバッグ情報エントリ (DIE: Debugging Information Entry)」として表現されます。各DIEは、そのエンティティの特性を記述する一連の「属性 (Attributes)」を持ちます。例えば、変数のDIEは、その名前、型、メモリ上の位置などを記述する属性を持つことができます。

### `AttrGNUAddrBase` と `ClassUnknown`

*   **`AttrGNUAddrBase`**: これは標準のDWARF仕様には含まれない、GNU拡張の属性である可能性が高いです。名前から推測すると、アドレスのベースオフセットに関連する情報を示すものと考えられます。コンパイラやツールチェーンによっては、標準仕様にない独自のデバッグ情報属性を追加することがあります。
*   **`ClassUnknown`**: `debug/dwarf` パッケージが特定の属性を認識できない場合、その属性の「クラス」（DWARFにおける属性の型や意味合いを示す分類）を `ClassUnknown` として扱うことがあります。以前は、このような未知の属性に遭遇するとパーサー全体が失敗する可能性がありましたが、このコミットの目的は、未知の属性であってもその値を適切に読み取り、解析を続行できるようにすることです。

## 技術的詳細

このコミットの技術的な核心は、`debug/dwarf` パッケージがSplit DWARF形式のファイルに含まれる「認識されない属性」に遭遇した際に、パース処理が中断しないようにすることです。

以前の `debug/dwarf` は、Goが直接理解できないDWARF属性（特にGNU拡張のような非標準属性）に遭遇すると、その属性の処理方法が不明なために、デバッグ情報の読み込み全体が失敗してしまうことがありました。これは、Split DWARFファイルが、Goの `debug/dwarf` がまだ完全にサポートしていない特定の属性（例: `AttrGNUAddrBase`）を含む可能性があるため、問題となっていました。

このコミットでは、`debug/dwarf` がSplit DWARFイメージから生成されたELFファイル（`split.elf`）を読み込み、その中のスケルトンDWARFデータを解析できることをテストします。テストの重要なポイントは、`AttrGNUAddrBase` という未知の属性が存在しても、`debug/dwarf` がその属性値を `int64` として正しく読み取り、かつその属性のクラスが `ClassUnknown` であると認識できることを検証することです。これにより、`debug/dwarf` は未知の属性を無視または適切にスキップして、既知のデバッグ情報の解析を続行できるようになります。

ただし、このコミットは `debug/dwarf` が外部DWARFファイルを読み込んでスケルトンDWARFデータと結合する機能を追加するものではありません。あくまで、スケルトンDWARFデータ単独の解析における堅牢性を向上させるものです。

テスト用の `split.c` ファイルは非常にシンプルで、`main` 関数のみを含んでいます。これを `gcc -gsplit-dwarf split.c -o split.elf` コマンドでコンパイルすることで、Split DWARF形式のデバッグ情報を含む `split.elf` バイナリが生成されます。このバイナリがテストの入力として使用されます。

## コアとなるコードの解説

### `src/debug/dwarf/entry_test.go`

このファイルには、`TestSplit` という新しいテスト関数が含まれています。

```go
func TestSplit(t *testing.T) {
	// debug/dwarf doesn't (currently) support split DWARF, but
	// the attributes that pointed to the split DWARF used to
	// cause loading the DWARF data to fail entirely (issue
	// #12592). Test that we can at least read the DWARF data.
	d := elfData(t, "testdata/split.elf") // (1)
	r := d.Reader()                      // (2)
	e, err := r.Next()                   // (3)
	if err != nil {
		t.Fatal(err)
	}
	if e.Tag != TagCompileUnit { // (4)
		t.Fatalf("bad tag: have %s, want %s", e.Tag, TagCompileUnit)
	}
	// Check that we were able to parse the unknown section offset
	// field, even if we can't figure out its DWARF class.
	const AttrGNUAddrBase Attr = 0x2133 // (5)
	f := e.AttrField(AttrGNUAddrBase)   // (6)
	if _, ok := f.Val.(int64); !ok {    // (7)
		t.Fatalf("bad attribute value type: have %T, want int64", f.Val)
	}
	if f.Class != ClassUnknown { // (8)
		t.Fatalf("bad class: have %s, want %s", f.Class, ClassUnknown)
	}
}
```

このテスト関数の主要なステップは以下の通りです。

1.  `(1) d := elfData(t, "testdata/split.elf")`: `testdata/split.elf` ファイルを読み込み、ELFファイルとして解析します。このヘルパー関数は、テスト用のELFファイルをロードし、そのDWARFデバッグ情報へのアクセスを提供します。
2.  `(2) r := d.Reader()`: ロードされたDWARFデータから `Reader` オブジェクトを取得します。これはDWARF情報を順次読み取るためのインターフェースを提供します。
3.  `(3) e, err := r.Next()`: DWARF情報の最初のデバッグ情報エントリ (DIE) を読み込みます。
4.  `(4) if e.Tag != TagCompileUnit`: 読み込んだDIEが `TagCompileUnit` (コンパイル単位、つまりソースファイルに対応するエントリ) であることを確認します。これはDWARF情報のルートエントリの一つです。
5.  `(5) const AttrGNUAddrBase Attr = 0x2133`: GNU拡張である `AttrGNUAddrBase` 属性の定数を定義します。この属性は、Split DWARFファイルに存在することが期待されます。
6.  `(6) f := e.AttrField(AttrGNUAddrBase)`: 現在のDIE (`e`) から `AttrGNUAddrBase` 属性のフィールド (`f`) を取得します。
7.  `(7) if _, ok := f.Val.(int64); !ok`: 取得した属性の値 (`f.Val`) が `int64` 型であることを検証します。これは、`debug/dwarf` が未知の属性であってもその生の値（この場合は数値）を正しくパースできることを示しています。
8.  `(8) if f.Class != ClassUnknown`: 取得した属性のクラス (`f.Class`) が `ClassUnknown` であることを検証します。これは、`debug/dwarf` がこの特定の属性を認識できないが、それでも解析を続行できることを示しています。

このテストは、`debug/dwarf` が未知の属性を含むSplit DWARFファイルを読み込む際に、以前のようにパースエラーで全体が失敗するのではなく、少なくともスケルトンDWARFデータを読み込み、未知の属性を適切に識別して処理できるようになったことを保証します。

## 技術的詳細

このコミットの技術的な核心は、`debug/dwarf` パッケージがSplit DWARF形式のファイルに含まれる「認識されない属性」に遭遇した際に、パース処理が中断しないようにすることです。

以前の `debug/dwarf` は、Goが直接理解できないDWARF属性（特にGNU拡張のような非標準属性）に遭遇すると、その属性の処理方法が不明なために、デバッグ情報の読み込み全体が失敗してしまうことがありました。これは、Split DWARFファイルが、Goの `debug/dwarf` がまだ完全にサポートしていない特定の属性（例: `AttrGNUAddrBase`）を含む可能性があるため、問題となっていました。

このコミットでは、`debug/dwarf` がSplit DWARFイメージから生成されたELFファイル（`split.elf`）を読み込み、その中のスケルトンDWARFデータを解析できることをテストします。テストの重要なポイントは、`AttrGNUAddrBase` という未知の属性が存在しても、`debug/dwarf` がその属性値を `int64` として正しく読み取り、かつその属性のクラスが `ClassUnknown` であると認識できることを検証することです。これにより、`debug/dwarf` は未知の属性を無視または適切にスキップして、既知のデバッグ情報の解析を続行できるようになります。

ただし、このコミットは `debug/dwarf` が外部DWARFファイルを読み込んでスケルトンDWARFデータと結合する機能を追加するものではありません。あくまで、スケルトンDWARFデータ単独の解析における堅牢性を向上させるものです。

テスト用の `split.c` ファイルは非常にシンプルで、`main` 関数のみを含んでいます。これを `gcc -gsplit-dwarf split.c -o split.elf` コマンドでコンパイルすることで、Split DWARF形式のデバッグ情報を含む `split.elf` という実行可能ファイルが生成されます。このバイナリがテストの入力として使用されます。

## コアとなるコードの変更箇所

このコミットで追加された主要なファイルは以下の通りです。

*   `src/debug/dwarf/entry_test.go`: `debug/dwarf` パッケージがSplit DWARFを処理できることをテストする新しいテストファイル。
*   `src/debug/dwarf/testdata/split.c`: Split DWARF形式のELFファイルを生成するためのC言語のソースコード。
*   `src/debug/dwarf/testdata/split.elf`: `split.c` から生成された、Split DWARF情報を含むバイナリファイル。

## コアとなるコードの解説

### `src/debug/dwarf/entry_test.go`

このファイルには、`TestSplit` という新しいテスト関数が含まれています。

```go
func TestSplit(t *testing.T) {
	// debug/dwarf doesn't (currently) support split DWARF, but
	// the attributes that pointed to the split DWARF used to
	// cause loading the DWARF data to fail entirely (issue
	// #12592). Test that we can at least read the DWARF data.
	d := elfData(t, "testdata/split.elf") // (1)
	r := d.Reader()                      // (2)
	e, err := r.Next()                   // (3)
	if err != nil {
		t.Fatal(err)
	}
	if e.Tag != TagCompileUnit { // (4)
		t.Fatalf("bad tag: have %s, want %s", e.Tag, TagCompileUnit)
	}
	// Check that we were able to parse the unknown section offset
	// field, even if we can't figure out its DWARF class.
	const AttrGNUAddrBase Attr = 0x2133 // (5)
	f := e.AttrField(AttrGNUAddrBase)   // (6)
	if _, ok := f.Val.(int64); !ok {    // (7)
		t.Fatalf("bad attribute value type: have %T, want int64", f.Val)
	}
	if f.Class != ClassUnknown { // (8)
		t.Fatalf("bad class: have %s, want %s", f.Class, ClassUnknown)
	}
}
```

このテスト関数の主要なステップは以下の通りです。

1.  `(1) d := elfData(t, "testdata/split.elf")`: `testdata/split.elf` ファイルを読み込み、ELFファイルとして解析します。このヘルパー関数は、テスト用のELFファイルをロードし、そのDWARFデバッグ情報へのアクセスを提供します。
2.  `(2) r := d.Reader()`: ロードされたDWARFデータから `Reader` オブジェクトを取得します。これはDWARF情報を順次読み取るためのインターフェースを提供します。
3.  `(3) e, err := r.Next()`: DWARF情報の最初のデバッグ情報エントリ (DIE) を読み込みます。
4.  `(4) if e.Tag != TagCompileUnit`: 読み込んだDIEが `TagCompileUnit` (コンパイル単位、つまりソースファイルに対応するエントリ) であることを確認します。これはDWARF情報のルートエントリの一つです。
5.  `(5) const AttrGNUAddrBase Attr = 0x2133`: GNU拡張である `AttrGNUAddrBase` 属性の定数を定義します。この属性は、Split DWARFファイルに存在することが期待されます。
6.  `(6) f := e.AttrField(AttrGNUAddrBase)`: 現在のDIE (`e`) から `AttrGNUAddrBase` 属性のフィールド (`f`) を取得します。
7.  `(7) if _, ok := f.Val.(int64); !ok`: 取得した属性の値 (`f.Val`) が `int64` 型であることを検証します。これは、`debug/dwarf` が未知の属性であってもその生の値（この場合は数値）を正しくパースできることを示しています。
8.  `(8) if f.Class != ClassUnknown`: 取得した属性のクラス (`f.Class`) が `ClassUnknown` であることを検証します。これは、`debug/dwarf` がこの特定の属性を認識できないが、それでも解析を続行できることを示しています。

このテストは、`debug/dwarf` が未知の属性を含むSplit DWARFファイルを読み込む際に、以前のようにパースエラーで全体が失敗するのではなく、少なくともスケルトンDWARFデータを読み込み、未知の属性を適切に識別して処理できるようになったことを保証します。

# [インデックス 26194] ファイルの概要

このコミットは、Go言語のツールチェイン、特にリンカ（`cmd/link`）における標準ライブラリのソースファイルパスの扱いを改善するものです。具体的には、コンパイル済みバイナリ内のデバッグ情報に含まれるソースファイルパスが、実際の`GOROOT`環境変数に基づいて正しく解決されるように変更されています。これにより、ユーザーがGoのバイナリディストリビューションをデフォルト以外の場所にインストールした場合でも、デバッグ情報が正確なソースコードの場所を指すようになります。

## 元コミット内容

`cmd/link`: 標準ライブラリのソースファイルパスに現在の `GOROOT` を使用する

この変更は、標準ライブラリの `.a` ファイル内のソースファイル情報を、実際のディレクトリを明示する代わりに「`$GOROOT/src/runtime/chan.go`」（リテラルな「`$GOROOT`」を含む）と記述するように変更します。リンカはその後、必要に応じて実際の `$GOROOT`（または `$GOROOT_FINAL`）に置き換えます。

もし人々がバイナリディストリビューションを代替の場所にダウンロードし、`https://golang.org/doc/install#install` の指示に従った場合、この変更前のコードでは、実際のソースがどこにあってもソースパスが `/usr/local/go` を指すことになっていました。この変更により、ビルドされたバイナリのソースパスは（うまくいけば）実際のソースを指すようになります。

配布されるバイナリのソース行情報は影響を受けません。それらは引き続き `/usr/local/go` を指します。しかし、人々が自分でビルドしたバイナリ（Goディストリビューションのプログラムではなく、自身のプログラム）は正しくなります。

このパスの修正は、`runtime-gdb.py` ファイルのルックアップも修正します。

`Fixes #5533`.

## 変更の背景

Go言語のバイナリをビルドする際、コンパイルされた実行ファイルには、デバッグやプロファイリングのためにソースファイルへのパス情報が含まれることがあります。この情報は、例えばGDBのようなデバッガがソースコードと実行中のバイナリを関連付けるために使用されます。

このコミット以前は、Goの標準ライブラリのコンパイル済みアーカイブ（`.a`ファイル）に含まれるソースファイルパスは、Goがインストールされたデフォルトの場所（例えば `/usr/local/go`）をハードコードしていました。この挙動は、ユーザーがGoのバイナリディストリビューションを別のディレクトリにインストールした場合に問題を引き起こしました。具体的には、ユーザーが自身のプログラムをビルドした際に、標準ライブラリの関数呼び出しに関するデバッグ情報が、実際のソースコードの場所ではなく、誤ったパス（`/usr/local/go`）を指してしまうという問題です。これにより、デバッガがソースコードを見つけられず、デバッグ体験が損なわれる可能性がありました。

また、この問題は、Goのランタイムデバッグを支援するGDBスクリプトである `runtime-gdb.py` のルックアップにも影響を与えていました。このスクリプトは、Goのランタイム構造をGDBが理解できるようにするためのものであり、そのパスが正しく解決されないと、Goプログラムのデバッグが困難になります。

このコミットは、これらの問題を解決し、ユーザーがGoをどこにインストールしても、デバッグ情報が常に正しいソースコードの場所を指すようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **GOROOT**: Goのインストールディレクトリを指す環境変数です。Goのコンパイラ、ツール、標準ライブラリのソースコードなどがこのディレクトリに格納されています。
2.  **GOROOT_FINAL**: Goのビルドシステムで使用される内部的な環境変数で、最終的なGoのインストールパスを示すことがあります。これは、クロスコンパイルや特定のデプロイメントシナリオで `GOROOT` と異なるパスを指定する必要がある場合に使用されます。
3.  **リンカ (cmd/link)**: Goのビルドプロセスの一部で、コンパイルされたオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合して、実行可能なバイナリを生成するツールです。この過程で、デバッグ情報やシンボル情報もバイナリに埋め込まれます。
4.  **`.a` ファイル (アーカイブファイル)**: コンパイルされたオブジェクトファイル（`.o`ファイル）をまとめたライブラリファイルです。Goの標準ライブラリは、通常、このようなアーカイブファイルの形式で提供されます。
5.  **デバッグ情報**: 実行可能バイナリに埋め込まれる情報で、ソースコードの行番号、変数名、関数名などをバイナリ内のアドレスと関連付けます。これにより、デバッガは実行中のプログラムの状態をソースコードレベルで表示できます。
6.  **`runtime-gdb.py`**: GoのランタイムをGDBでデバッグする際に役立つPythonスクリプトです。Goのゴルーチン、チャネル、マップなどの内部構造をGDBが認識し、より人間が理解しやすい形式で表示できるようにします。このスクリプトは通常 `$GOROOT/src/runtime/runtime-gdb.py` に配置されます。
7.  **Issue #5533**: このコミットが修正するGoのバグトラッカー上の課題です。この課題には、デバッグ情報におけるソースパスの問題に関する詳細な議論が含まれています。

## 技術的詳細

このコミットの核心は、Goのビルドシステムが標準ライブラリのソースファイルパスをどのように扱うかを変更することにあります。

以前の挙動では、標準ライブラリのコンパイル時に、そのソースファイルパスは絶対パスとして記録されていました。例えば、Goが `/usr/local/go` にインストールされている場合、`src/runtime/chan.go` のパスは `/usr/local/go/src/runtime/chan.go` として `.a` ファイルに埋め込まれていました。

このコミットでは、この挙動が変更され、標準ライブラリのソースファイルパスは、リテラルな文字列 `"$GOROOT"` を含む形式で記録されるようになります。例えば、`src/runtime/chan.go` のパスは `"$GOROOT/src/runtime/chan.go"` となります。

この変更のポイントは、リンカが最終的なバイナリを生成する際に、この `"$GOROOT"` プレースホルダーを実際の `GOROOT` 環境変数の値（または `GOROOT_FINAL` の値）に置き換えるという点です。これにより、ユーザーがGoをどこにインストールしても、生成されるバイナリ内のデバッグ情報が、その環境における正しいGoのソースコードの場所を指すようになります。

具体的には、以下の2つのファイルが変更されています。

1.  **`src/cmd/internal/obj/obj.go`**: このファイルは、Goのオブジェクトファイル（`.o`）やアーカイブファイル（`.a`）の構造を定義し、それらのファイル内のパス情報を処理するロジックを含んでいます。変更点では、`h.GOROOT_FINAL` を使用して `GOROOT` を置き換える代わりに、リテラルな `"$GOROOT"` を使用するように変更されています。これは、パスが `h.GOROOT` で始まる場合に、その部分を `"$GOROOT"` に置き換えることで実現されます。
2.  **`src/cmd/link/internal/ld/pcln.go`**: このファイルは、Goのリンカの主要な部分であり、プログラムカウンタと行番号のマッピング（`pcln`テーブル）を処理します。このテーブルには、デバッグ情報としてソースファイルパスが含まれます。
    *   `renumberfiles` 関数内で、ファイルシンボルの名前を処理する際に、新しく追加された `expandGoroot` 関数が呼び出されるようになりました。
    *   新しく追加された `expandGoroot` 関数は、文字列が `"$GOROOT"` で始まるかどうかをチェックし、もしそうであれば、現在の `GOROOT` または `GOROOT_FINAL` の値を使って `"$GOROOT"` を実際のパスに展開します。これにより、リンカが最終的なバイナリに書き込むデバッグ情報が、正しいソースパスを持つようになります。
3.  **`src/runtime/runtime-gdb_test.go`**: このファイルは、`runtime-gdb.py` の機能に関するテストコードです。変更点では、GDBの起動引数に `"-ex", "info auto-load python-scripts"` が追加され、GDBがPythonスクリプトをどのようにロードしているかを確認できるようになっています。また、テストが失敗した場合のエラーメッセージがより詳細になり、デバッグが容易になっています。これは、パス解決の修正が `runtime-gdb.py` のルックアップにも影響を与えるため、そのテストを強化するものです。

この変更により、Goのビルドシステムはより柔軟になり、異なる環境でのデバッグ体験が向上します。特に、Goのバイナリディストリビューションをカスタムパスにインストールしている開発者にとっては、デバッグ情報の正確性が保証される重要な改善となります。

## コアとなるコードの解説

### `src/cmd/internal/obj/obj.go` の変更

このファイルでは、`LineHist` 構造体の `setFile` メソッドが変更されています。このメソッドは、ソースファイルパスを処理し、デバッグ情報に含める形式に変換する役割を担っています。

変更前は、`h.GOROOT_FINAL` が設定されており、かつ `h.GOROOT_FINAL` が `h.GOROOT` と異なる場合に、`h.GOROOT` で始まるパスを `h.GOROOT_FINAL` で始まるパスに書き換えていました。これは、ビルド環境と最終的な実行環境で `GOROOT` が異なる場合に、デバッグ情報が正しいパスを指すようにするためのロジックでした。

変更後は、`h.GOROOT_FINAL` の条件が削除され、単にパスが `h.GOROOT` で始まる場合に、その部分をリテラルな文字列 `"$GOROOT"` に置き換えるようになりました。
`tabs = "$GOROOT" + abs[len(h.GOROOT):]`
この変更により、コンパイルされたオブジェクトファイルやアーカイブファイルには、具体的な `GOROOT` のパスではなく、プレースホルダーとしての `"$GOROOT"` が埋め込まれることになります。このプレースホルダーは、後続のリンカ処理で実際のパスに展開されます。

### `src/cmd/link/internal/ld/pcln.go` の変更

このファイルはGoリンカの核心部分であり、プログラムカウンタと行番号のマッピング（`pcln`テーブル）を構築します。このテーブルには、デバッグ情報としてソースファイルパスが含まれます。

1.  **`renumberfiles` 関数内の変更**:
    `renumberfiles` 関数は、ファイルシンボルを処理し、それらを `pcln` テーブルに登録する役割を担っています。変更点として、ファイルシンボル `f.Name` を `ctxt.Filesyms` に追加する直前に、新しく追加された `expandGoroot` 関数を呼び出すようになりました。
    `f.Name = expandGoroot(f.Name)`
    これにより、`"$GOROOT"` プレースホルダーを含むパスが、リンカによって実際の `GOROOT` パスに展開される機会が与えられます。

2.  **`expandGoroot` 関数の追加**:
    このコミットの主要な機能追加です。
    ```go
    func expandGoroot(s string) string {
        const n = len("$GOROOT")
        if len(s) >= n+1 && s[:n] == "$GOROOT" && (s[n] == '/' || s[n] == '\\') {
            root := goroot
            if final := os.Getenv("GOROOT_FINAL"); final != "" {
                root = final
            }
            return filepath.ToSlash(filepath.Join(root, s[n:]))
        }
        return s
    }
    ```
    この関数は、入力文字列 `s` が `"$GOROOT"` で始まり、その後にパスセパレータ（`/` または `\`）が続くかどうかをチェックします。
    もし条件が満たされれば、以下のロジックで `"$GOROOT"` を実際のパスに展開します。
    *   まず、現在の `goroot` 変数（リンカが認識している `GOROOT` の値）を `root` に設定します。
    *   次に、環境変数 `GOROOT_FINAL` が設定されている場合は、その値を `root` に優先して使用します。これは、最終的なデプロイメント環境での `GOROOT` がビルド時と異なる場合に備えるためです。
    *   最後に、`filepath.Join` を使用して `root` と `s` の残りの部分（`"$GOROOT"` の後）を結合し、プラットフォームに依存しないスラッシュ形式のパスに変換して返します。
    この関数がリンカの最終段階で呼び出されることで、バイナリに埋め込まれるソースパスが、実行環境の `GOROOT` に応じて動的に解決されるようになります。

### `src/runtime/runtime-gdb_test.go` の変更

このテストファイルでは、`TestGdbPython` 関数が変更されています。このテストは、GDBがGoのランタイムサポートスクリプト（`runtime-gdb.py`）を正しくロードできることを確認するためのものです。

1.  **GDB引数の追加**:
    `args` スライスに `"-ex", "info auto-load python-scripts"` が追加されました。これは、GDBに対して、自動ロードされたPythonスクリプトに関する情報を表示するように指示するものです。これにより、テストの出力から `runtime-gdb.py` が正しくロードされたかどうかをより明確に確認できるようになります。

2.  **エラーメッセージの改善**:
    テストが失敗した場合の `t.Fatalf` メッセージがより詳細になりました。
    *   `t.Logf("package testing source file: %s", file)` が追加され、テストを実行しているパッケージのソースファイルパスがログに出力されるようになりました。
    *   `t.Fatalf` のメッセージに `got` 変数の内容（GDBの出力全体）が追加され、何が問題だったのかをより詳細に把握できるようになりました。
    これらの変更は、デバッグパスの修正が `runtime-gdb.py` のルックアップに影響を与える可能性があるため、そのテストの堅牢性を高め、問題発生時の診断を容易にするためのものです。

## 元コミット内容

`cmd/link`: 標準ライブラリのソースファイルパスに現在の `GOROOT` を使用する

この変更は、標準ライブラリの `.a` ファイル内のソースファイル情報を、実際のディレクトリを明示する代わりに「`$GOROOT/src/runtime/chan.go`」（リテラルな「`$GOROOT`」を含む）と記述するように変更します。リンカはその後、必要に応じて実際の `$GOROOT`（または `$GOROOT_FINAL`）に置き換えます。

もし人々がバイナリディストリビューションを代替の場所にダウンロードし、`https://golang.org/doc/install#install` の指示に従った場合、この変更前のコードでは、実際のソースがどこにあってもソースパスが `/usr/local/go` を指すことになっていました。この変更により、ビルドされたバイナリのソースパスは（うまくいけば）実際のソースを指すようになります。

配布されるバイナリのソース行情報は影響を受けません。それらは引き続き `/usr/local/go` を指します。しかし、人々が自分でビルドしたバイナリ（Goディストリビューションのプログラムではなく、自身のプログラム）は正しくなります。

このパスの修正は、`runtime-gdb.py` ファイルのルックアップも修正します。

`Fixes #5533`.

## 変更の背景

Go言語のバイナリをビルドする際、コンパイルされた実行ファイルには、デバッグやプロファイリングのためにソースファイルへのパス情報が含まれることがあります。この情報は、例えばGDBのようなデバッガがソースコードと実行中のバイナリを関連付けるために使用されます。

このコミット以前は、Goの標準ライブラリのコンパイル済みアーカイブ（`.a`ファイル）に含まれるソースファイルパスは、Goがインストールされたデフォルトの場所（例えば `/usr/local/go`）をハードコードしていました。この挙動は、ユーザーがGoのバイナリディストリビューションを別のディレクトリにインストールした場合に問題を引き起こしました。具体的には、ユーザーが自身のプログラムをビルドした際に、標準ライブラリの関数呼び出しに関するデバッグ情報が、実際のソースコードの場所ではなく、誤ったパス（`/usr/local/go`）を指してしまうという問題です。これにより、デバッガがソースコードを見つけられず、デバッグ体験が損なわれる可能性がありました。

また、この問題は、Goのランタイムデバッグを支援するGDBスクリプトである `runtime-gdb.py` のルックアップにも影響を与えていました。このスクリプトは、Goのランタイム構造をGDBが理解できるようにするためのものであり、そのパスが正しく解決されないと、Goプログラムのデバッグが困難になります。

このコミットは、これらの問題を解決し、ユーザーがGoをどこにインストールしても、デバッグ情報が常に正しいソースコードの場所を指すようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **GOROOT**: Goのインストールディレクトリを指す環境変数です。Goのコンパイラ、ツール、標準ライブラリのソースコードなどがこのディレクトリに格納されています。
2.  **GOROOT_FINAL**: Goのビルドシステムで使用される内部的な環境変数で、最終的なGoのインストールパスを示すことがあります。これは、クロスコンパイルや特定のデプロイメントシナリオで `GOROOT` と異なるパスを指定する必要がある場合に使用されます。
3.  **リンカ (cmd/link)**: Goのビルドプロセスの一部で、コンパイルされたオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合して、実行可能なバイナリを生成するツールです。この過程で、デバッグ情報やシンボル情報もバイナリに埋め込まれます。
4.  **`.a` ファイル (アーカイブファイル)**: コンパイルされたオブジェクトファイル（`.o`ファイル）をまとめたライブラリファイルです。Goの標準ライブラリは、通常、このようなアーカイブファイルの形式で提供されます。
5.  **デバッグ情報**: 実行可能バイナリに埋め込まれる情報で、ソースコードの行番号、変数名、関数名などをバイナリ内のアドレスと関連付けます。これにより、デバッガは実行中のプログラムの状態をソースコードレベルで表示できます。
6.  **`runtime-gdb.py`**: GoのランタイムをGDBでデバッグする際に役立つPythonスクリプトです。Goのゴルーチン、チャネル、マップなどの内部構造をGDBが認識し、より人間が理解しやすい形式で表示できるようにします。このスクリプトは通常 `$GOROOT/src/runtime/runtime-gdb.py` に配置されます。
7.  **Issue #5533**: このコミットが修正するGoのバグトラッカー上の課題です。この課題には、デバッグ情報におけるソースパスの問題に関する詳細な議論が含まれています。

## 技術的詳細

このコミットの核心は、Goのビルドシステムが標準ライブラリのソースファイルパスをどのように扱うかを変更することにあります。

以前の挙動では、標準ライブラリのコンパイル時に、そのソースファイルパスは絶対パスとして記録されていました。例えば、Goが `/usr/local/go` にインストールされている場合、`src/runtime/chan.go` のパスは `/usr/local/go/src/runtime/chan.go` として `.a` ファイルに埋め込まれていました。

このコミットでは、この挙動が変更され、標準ライブラリのソースファイルパスは、リテラルな文字列 `"$GOROOT"` を含む形式で記録されるようになります。例えば、`src/runtime/chan.go` のパスは `"$GOROOT/src/runtime/chan.go"` となります。

この変更のポイントは、リンカが最終的なバイナリを生成する際に、この `"$GOROOT"` プレースホルダーを実際の `GOROOT` 環境変数の値（または `GOROOT_FINAL` の値）に置き換えるという点です。これにより、ユーザーがGoをどこにインストールしても、生成されるバイナリ内のデバッグ情報が、その環境における正しいGoのソースコードの場所を指すようになります。

具体的には、以下の2つのファイルが変更されています。

1.  **`src/cmd/internal/obj/obj.go`**: このファイルは、Goのオブジェクトファイル（`.o`）やアーカイブファイル（`.a`）の構造を定義し、それらのファイル内のパス情報を処理するロジックを含んでいます。変更点では、`h.GOROOT_FINAL` を使用して `GOROOT` を置き換える代わりに、リテラルな `"$GOROOT"` を使用するように変更されています。これは、パスが `h.GOROOT` で始まる場合に、その部分を `"$GOROOT"` に置き換えることで実現されます。
2.  **`src/cmd/link/internal/ld/pcln.go`**: このファイルは、Goのリンカの主要な部分であり、プログラムカウンタと行番号のマッピング（`pcln`テーブル）を処理します。このテーブルには、デバッグ情報としてソースファイルパスが含まれます。
    *   `renumberfiles` 関数内で、ファイルシンボルの名前を処理する際に、新しく追加された `expandGoroot` 関数が呼び出されるようになりました。
    *   新しく追加された `expandGoroot` 関数は、文字列が `"$GOROOT"` で始まるかどうかをチェックし、もしそうであれば、現在の `GOROOT` または `GOROOT_FINAL` の値を使って `"$GOROOT"` を実際のパスに展開します。これにより、リンカが最終的なバイナリに書き込むデバッグ情報が、正しいソースパスを持つようになります。
3.  **`src/runtime/runtime-gdb_test.go`**: このファイルは、`runtime-gdb.py` の機能に関するテストコードです。変更点では、GDBの起動引数に `"-ex", "info auto-load python-scripts"` が追加され、GDBがPythonスクリプトをどのようにロードしているかを確認できるようになっています。また、テストが失敗した場合のエラーメッセージがより詳細になり、デバッグが容易になっています。これは、パス解決の修正が `runtime-gdb.py` のルックアップにも影響を与えるため、そのテストを強化するものです。

この変更により、Goのビルドシステムはより柔軟になり、異なる環境でのデバッグ体験が向上します。特に、Goのバイナリディストリビューションをカスタムパスにインストールしている開発者にとっては、デバッグ情報の正確性が保証される重要な改善となります。

## コアとなるコードの解説

### `src/cmd/internal/obj/obj.go` の変更

このファイルでは、`LineHist` 構造体の `setFile` メソッドが変更されています。このメソッドは、ソースファイルパスを処理し、デバッグ情報に含める形式に変換する役割を担っています。

変更前は、`h.GOROOT_FINAL` が設定されており、かつ `h.GOROOT_FINAL` が `h.GOROOT` と異なる場合に、`h.GOROOT` で始まるパスを `h.GOROOT_FINAL` で始まるパスに書き換えていました。これは、ビルド環境と最終的な実行環境で `GOROOT` が異なる場合に、デバッグ情報が正しいパスを指すようにするためのロジックでした。

変更後は、`h.GOROOT_FINAL` の条件が削除され、単にパスが `h.GOROOT` で始まる場合に、その部分をリテラルな文字列 `"$GOROOT"` に置き換えるようになりました。
`tabs = "$GOROOT" + abs[len(h.GOROOT):]`
この変更により、コンパイルされたオブジェクトファイルやアーカイブファイルには、具体的な `GOROOT` のパスではなく、プレースホルダーとしての `"$GOROOT"` が埋め込まれることになります。このプレースホルダーは、後続のリンカ処理で実際のパスに展開されます。

### `src/cmd/link/internal/ld/pcln.go` の変更

このファイルはGoリンカの核心部分であり、プログラムカウンタと行番号のマッピング（`pcln`テーブル）を構築します。このテーブルには、デバッグ情報としてソースファイルパスが含まれます。

1.  **`renumberfiles` 関数内の変更**:
    `renumberfiles` 関数は、ファイルシンボルを処理し、それらを `pcln` テーブルに登録する役割を担っています。変更点として、ファイルシンボル `f.Name` を `ctxt.Filesyms` に追加する直前に、新しく追加された `expandGoroot` 関数を呼び出すようになりました。
    `f.Name = expandGoroot(f.Name)`
    これにより、`"$GOROOT"` プレースホルダーを含むパスが、リンカによって実際の `GOROOT` パスに展開される機会が与えられます。

2.  **`expandGoroot` 関数の追加**:
    このコミットの主要な機能追加です。
    ```go
    func expandGoroot(s string) string {
        const n = len("$GOROOT")
        if len(s) >= n+1 && s[:n] == "$GOROOT" && (s[n] == '/' || s[n] == '\\') {
            root := goroot
            if final := os.Getenv("GOROOT_FINAL"); final != "" {
                root = final
            }
            return filepath.ToSlash(filepath.Join(root, s[n:]))
        }
        return s
    }
    ```
    この関数は、入力文字列 `s` が `"$GOROOT"` で始まり、その後にパスセパレータ（`/` または `\`）が続くかどうかをチェックします。
    もし条件が満たされれば、以下のロジックで `"$GOROOT"` を実際のパスに展開します。
    *   まず、現在の `goroot` 変数（リンカが認識している `GOROOT` の値）を `root` に設定します。
    *   次に、環境変数 `GOROOT_FINAL` が設定されている場合は、その値を `root` に優先して使用します。これは、最終的なデプロイメント環境での `GOROOT` がビルド時と異なる場合に備えるためです。
    *   最後に、`filepath.Join` を使用して `root` と `s` の残りの部分（`"$GOROOT"` の後）を結合し、プラットフォームに依存しないスラッシュ形式のパスに変換して返します。
    この関数がリンカの最終段階で呼び出されることで、バイナリに埋め込まれるソースパスが、実行環境の `GOROOT` に応じて動的に解決されるようになります。

### `src/runtime/runtime-gdb_test.go` の変更

このテストファイルでは、`TestGdbPython` 関数が変更されています。このテストは、GDBがGoのランタイムサポートスクリプト（`runtime-gdb.py`）を正しくロードできることを確認するためのものです。

1.  **GDB引数の追加**:
    `args` スライスに `"-ex", "info auto-load python-scripts"` が追加されました。これは、GDBに対して、自動ロードされたPythonスクリプトに関する情報を表示するように指示するものです。これにより、テストの出力から `runtime-gdb.py` が正しくロードされたかどうかをより明確に確認できるようになります。

2.  **エラーメッセージの改善**:
    テストが失敗した場合の `t.Fatalf` メッセージがより詳細になりました。
    *   `t.Logf("package testing source file: %s", file)` が追加され、テストを実行しているパッケージのソースファイルパスがログに出力されるようになりました。
    *   `t.Fatalf` のメッセージに `got` 変数の内容（GDBの出力全体）が追加され、何が問題だったのかをより詳細に把握できるようになりました。
    これらの変更は、デバッグパスの修正が `runtime-gdb.py` のルックアップに影響を与える可能性があるため、そのテストの堅牢性を高め、問題発生時の診断を容易にするためのものです。

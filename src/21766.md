# [インデックス 21766] ファイルの概要

このコミットは、Go言語のアセンブラ（`cmd/5a` および `cmd/9a`）における`GLOBL`命令の処理に関するバグ修正です。具体的には、`GLOBL`命令が`TEXT`命令と同じ文法規則で処理されていたために発生していた、64ビット定数の上位32ビットが誤って設定される問題を解決します。この問題は、リンカが値を32ビットとして読み込んでいたために表面化していませんでしたが、根本的な誤りを修正するものです。

## 元コミット内容

`cmd/9a: fix GLOBL instruction`

`GLOBL`命令が`TEXT`命令と一緒に処理されていたため、サイズを保持する64ビット定数の上位32ビットが常に`0x80000000` (`ArgsSizeUnknown`) に設定されていました。これは、`cmd/9l`が64ビット値を`int32`として読み込んでいたため、問題なく動作していました。

ついでに、`5a`も修正します。そちらでは、2つの値が異なるフィールドに格納されていたため、それほど大きな問題ではありませんでしたが、それでも誤りでした。

## 変更の背景

Go言語のツールチェインにおいて、アセンブラ（`cmd/9a`はAMD64アーキテクチャ用、`cmd/5a`はARMアーキテクチャ用）は、Goのソースコードから生成されたアセンブリ言語ファイルを機械語に変換する役割を担っています。これらのアセンブラは、Plan 9アセンブリという独特の構文を使用しており、`TEXT`や`GLOBL`といったディレクティブ（命令）を解釈します。

`TEXT`ディレクティブは関数の定義を開始し、その関数のスタックフレームサイズや引数のサイズなどのメタデータを指定します。一方、`GLOBL`ディレクティブはグローバルシンボルを宣言し、そのシンボルのサイズや初期値などを指定するために使用されます。

このコミット以前は、アセンブラのパーサー（構文解析器）が`GLOBL`命令を`TEXT`命令と同じ文法規則で処理していました。`TEXT`命令の文法規則では、関数の引数サイズが不明な場合に`ArgsSizeUnknown`という特殊な定数（`0x80000000`）を上位32ビットに設定するロジックが含まれていました。このロジックが`GLOBL`命令のサイズ定数にも適用されてしまい、`GLOBL`が本来持つべき64ビットのサイズ情報の上位32ビットが意図せず`0x80000000`で上書きされてしまうというバグが存在していました。

なぜこのバグがこれまで表面化しなかったかというと、アセンブラの出力結果を読み込むリンカ（`cmd/9l`）が、この64ビットのサイズ値を32ビット整数として読み込んでいたためです。これにより、上位32ビットの`0x80000000`は単に切り捨てられ、リンカは正しい下位32ビットのサイズ値のみを認識していました。これは、異なるコンポーネント間でのデータ型の不一致が偶然にも問題を隠蔽していた「たまたま動いていた」状態であり、潜在的なバグとして存在していました。

このコミットは、このような偶然に依存した不安定な状態を解消し、`GLOBL`命令のサイズ情報が常に正しくパースされるように、アセンブラの文法定義を修正することを目的としています。

## 前提知識の解説

*   **Go言語のツールチェイン**: Go言語のプログラムをビルドする際には、コンパイラ、アセンブラ、リンカなどのツールが連携して動作します。
    *   `cmd/5a`, `cmd/9a`: Go言語のアセンブラ。それぞれARM、AMD64アーキテクチャ向けのアセンブリコードを機械語に変換します。Plan 9アセンブリ構文を解釈します。
    *   `cmd/9l`: Go言語のリンカ。アセンブラによって生成されたオブジェクトファイルを結合し、実行可能ファイルを生成します。
*   **Plan 9アセンブリ**: Go言語のランタイムや標準ライブラリの一部は、パフォーマンスが重要な部分でPlan 9アセンブリで記述されています。これは一般的なAT&T構文やIntel構文とは異なる独特の構文を持ちます。
    *   **`TEXT`ディレクティブ**: 関数の定義に使用されます。例: `TEXT ·main(SB), $0-8`。ここで`$0-8`はフレームサイズと引数サイズを示します。
    *   **`GLOBL`ディレクティブ**: グローバル変数やデータセクションのシンボルを定義するために使用されます。例: `GLOBL ·myVar(SB), $8`。ここで`$8`はシンボルのサイズを示します。
*   **Yacc/BisonとLex/Flex**: これらはコンパイラやインタプリタのフロントエンドを構築するためのツールです。
    *   **Lex (または Flex)**: 字句解析器（lexer）を生成します。入力ストリームをトークン（単語や記号の最小単位）に分割します。`lex.c`ファイルはLexによって生成されるC言語のソースコードです。
    *   **Yacc (Yet Another Compiler Compiler, または Bison)**: 構文解析器（parser）を生成します。トークンのストリームを受け取り、それらが文法規則に合致するかどうかを検証し、構文木を構築します。`.y`ファイルはYacc/Bisonの文法定義ファイルです。`y.tab.c`と`y.tab.h`はYacc/Bisonによって生成されるC言語のソースコードおよびヘッダファイルです。
*   **データ表現（32ビット vs 64ビット）**: コンピュータのメモリやレジスタは、データを特定のビット幅で扱います。64ビットシステムでは64ビット（8バイト）のデータを一度に扱えますが、32ビットシステムでは32ビット（4バイト）のデータが基本です。64ビットの値を32ビットの変数に格納しようとすると、上位のビットが切り捨てられる（情報が失われる）可能性があります。
    *   `0x80000000`: これは32ビット符号なし整数の最大値の半分（2^31）に相当し、符号付き32ビット整数では負の最大値となります。Goのアセンブラの文脈では、`ArgsSizeUnknown`という特殊な意味を持つ定数として使用されていました。

## 技術的詳細

このバグは、アセンブラの構文解析ロジックに起因していました。アセンブラはYacc/BisonとLex/Flexを使用して構築されており、`a.y`ファイルが構文規則を定義し、`lex.c`ファイルが字句規則を定義しています。

1.  **既存のパーシングロジックの問題**:
    *   元々、`TEXT`命令と`GLOBL`命令は、`LTYPEB`という同じトークンタイプで識別されていました。
    *   `a.y`の文法規則では、`TEXT`命令の後に続くサイズ引数をパースする際に、関数の引数サイズが不明であることを示す`ArgsSizeUnknown`（`0x80000000`）を上位32ビットに設定するロジックが含まれていました。
    *   `GLOBL`命令もこの`LTYPEB`トークンで識別されていたため、`GLOBL`のサイズ引数も誤ってこの`ArgsSizeUnknown`のロジックの影響を受けていました。具体的には、`GLOBL`に指定された64ビットのサイズ定数に対して、上位32ビットが強制的に`0x80000000`に設定されてしまっていました。

2.  **リンカによる隠蔽**:
    *   アセンブラが生成したオブジェクトファイルは、リンカ（`cmd/9l`）によって読み込まれます。
    *   `cmd/9l`は、アセンブラから渡された64ビットのサイズ値を、内部で32ビット整数として解釈していました。
    *   この32ビットへの切り捨てにより、`0x80000000`という上位32ビットの値は失われ、下位32ビットの正しいサイズ値のみがリンカに渡されていました。このため、アセンブラの出力自体は誤っていたにもかかわらず、リンカの処理上は問題なく見えていました。これは、異なるビット幅のデータ型を扱う際の潜在的な危険性を示す典型的な例です。

3.  **修正アプローチ**:
    *   **新しいトークンの導入**: `GLOBL`命令専用の新しいトークン`LGLOBL`を導入しました。これにより、`GLOBL`と`TEXT`が字句解析の段階で明確に区別されるようになります。
        *   `src/cmd/5a/lex.c` および `src/cmd/9a/lex.c` で、`"GLOBL"`キーワードが`LGLOBL`トークンに対応付けられます。
        *   `src/cmd/5a/y.tab.h` および `src/cmd/9a/y.tab.h` に`LGLOBL`の定義が追加されます。
    *   **文法規則の分離**: `src/cmd/5a/a.y` および `src/cmd/9a/a.y` で、`GLOBL`命令のための新しい文法規則を定義しました。これにより、`GLOBL`のサイズ引数が`TEXT`命令の特殊な処理ロジックの影響を受けずに、独立して正しくパースされるようになります。
        *   `TEXT`命令の規則から`GLOBL`の処理を削除し、`GLOBL`専用の規則を追加します。
        *   `GLOBL`の規則では、サイズ定数を`outcode`関数に渡す際に、`TEXT`命令で使われていた`ArgsSizeUnknown`のような特殊なフラグを付加しないようにします。

この修正により、アセンブラは`GLOBL`命令のサイズ情報を正しく64ビットで表現し、リンカが将来的に64ビットのサイズ値を正しく解釈するようになった場合でも、互換性の問題が発生しないようになります。

## コアとなるコードの変更箇所

このコミットでは、主にGo言語のアセンブラ（`cmd/5a`と`cmd/9a`）の字句解析器と構文解析器の定義ファイルが変更されています。

1.  **`src/cmd/5a/a.y` および `src/cmd/9a/a.y` (Yacc/Bison 文法定義ファイル)**
    *   `%token <lval> LTYPEB LTYPEC LTYPED LTYPEE` の行が `%token <lval> LTYPEB LGLOBL LTYPEC LTYPED LTYPEE` に変更され、`LGLOBL`という新しいトークンが追加されています。
    *   `inst`（命令）の定義において、`TEXT/GLOBL`とコメントされていた部分が`TEXT`のみになり、`GLOBL`に関する新しい規則が追加されています。
        *   変更前:
            ```yacc
            /*
             * TEXT/GLOBL
             */
            | LTYPEB name ',' imm
            {
                // ... TEXT/GLOBL の処理 ...
            }
            ```
        *   変更後:
            ```yacc
            /*
             * TEXT
             */
            | LTYPEB name ',' imm
            {
                // ... TEXT の処理 ...
            }
            /*
             * GLOBL
             */
            | LGLOBL name ',' imm
            {
                settext($2.sym);
                outcode($1, Always, &$2, 0, &$4);
            }
            | LGLOBL name ',' con ',' imm
            {
                settext($2.sym);
                outcode($1, Always, &$2, $4, &$6);
            }
            ```
        これにより、`GLOBL`命令が`LGLOBL`トークンによって識別され、`TEXT`とは異なる専用の文法規則でパースされるようになります。特に、`outcode`関数への引数で`TEXT`命令に特有の`ArgsSizeUnknown`のようなフラグが渡されないようになります。

2.  **`src/cmd/5a/lex.c` および `src/cmd/9a/lex.c` (Lex 字句解析定義ファイル)**
    *   `"GLOBL"`キーワードに対応するトークンが`LTYPEB`から`LGLOBL`に変更されています。
        *   変更前: ` "GLOBL", LTYPEB, AGLOBL,`
        *   変更後: ` "GLOBL", LGLOBL, AGLOBL,`
        これにより、字句解析の段階で`GLOBL`キーワードが`LGLOBL`という新しいトークンとして識別され、構文解析器に渡されます。

3.  **`src/cmd/5a/y.tab.c` および `src/cmd/9a/y.tab.c` (Yacc/Bison 生成パーサーソースファイル)**
    *   これらのファイルは`a.y`と`lex.c`から自動生成されるため、直接編集されることはありません。上記の変更に伴い、`LGLOBL`という新しいトークンの数値定義が追加され、パーサーの内部状態遷移テーブルや規則の定義が更新されています。例えば、`YYNTOKENS`（トークン数）や`YYNRULES`（規則数）などの定数値が増加しています。

4.  **`src/cmd/5a/y.tab.h` および `src/cmd/9a/y.tab.h` (Yacc/Bison 生成パーサーヘッダファイル)**
    *   これらのファイルも自動生成されます。`LGLOBL`トークンのマクロ定義が追加され、その数値が他のトークン定義と衝突しないように調整されています。

これらの変更により、`GLOBL`命令は`TEXT`命令から完全に分離され、そのサイズ引数が正しくパースされるようになります。

## コアとなるコードの解説

このコミットの核心は、Go言語のアセンブラが`GLOBL`命令をどのように解釈するかを変更した点にあります。

**変更前:**

アセンブラのパーサーは、`TEXT`命令と`GLOBL`命令を区別せず、両方を`LTYPEB`という同じトークンタイプとして扱っていました。`a.y`ファイル内の文法規則では、`LTYPEB`に続く`name`と`imm`（即値）の組み合わせを、関数定義（`TEXT`）として解釈していました。この際、`TEXT`命令の処理ロジックには、関数の引数サイズが不明な場合に64ビット定数の上位32ビットに`0x80000000`（`ArgsSizeUnknown`）を埋め込むという特殊な処理が含まれていました。

```yacc
// 変更前のa.yの一部（概念的な表現）
inst:
    LTYPEB name ',' imm  // TEXT と GLOBL の両方をここで処理
    {
        // ここで outcode が呼ばれるが、TEXT 用のロジックが GLOBL にも適用されてしまう
        // 例えば、ArgsSizeUnknown が上位32ビットに設定される可能性があった
        outcode($1, $2, &$3, $4, &$5);
    }
```

この問題は、`GLOBL`命令が本来持つべきサイズ情報（例えば`GLOBL ·myVar(SB), $8`の`$8`）が、この`ArgsSizeUnknown`によって上位32ビットが汚染されてしまうことを意味します。

**変更後:**

このコミットでは、`GLOBL`命令を`TEXT`命令から明確に分離するために、以下のステップを踏んでいます。

1.  **字句解析器の変更 (`lex.c`)**:
    `GLOBL`キーワードが検出されたときに、これまでの`LTYPEB`ではなく、新しく定義された`LGLOBL`という専用のトークンを生成するように変更しました。

    ```c
    // src/cmd/5a/lex.c および src/cmd/9a/lex.c の変更点
    // 変更前:
    // "GLOBL", LTYPEB, AGLOBL,
    // 変更後:
    "GLOBL", LGLOBL, AGLOBL, // GLOBL に専用のトークン LGLOBL を割り当て
    ```

2.  **構文解析器の変更 (`a.y`)**:
    `a.y`ファイルに、`LGLOBL`トークンを起点とする`GLOBL`命令専用の新しい文法規則を追加しました。これにより、`GLOBL`命令は`TEXT`命令の処理ロジックから完全に独立してパースされるようになります。

    ```yacc
    // src/cmd/5a/a.y および src/cmd/9a/a.y の変更点
    // 新しい GLOBL 命令の規則を追加
    /*
     * GLOBL
     */
    | LGLOBL name ',' imm
    {
        settext($2.sym); // シンボルを現在のテキストセクションに設定
        outcode($1, Always, &$2, 0, &$4); // GLOBL の情報を出力
    }
    | LGLOBL name ',' con ',' imm
    {
        settext($2.sym); // シンボルを現在のテキストセクションに設定
        outcode($1, Always, &$2, $4, &$6); // GLOBL の情報を出力（定数付き）
    }
    ```

    ここで重要なのは、`outcode`関数が呼ばれる際に、`TEXT`命令の規則で使われていた`ArgsSizeUnknown`のような特殊なフラグが`GLOBL`のサイズ引数に適用されないことです。`GLOBL`のサイズは、`imm`（即値）または`con`（定数）として直接渡され、上位32ビットが意図せず変更されることがなくなります。

この修正によって、アセンブラは`GLOBL`命令のサイズ情報を正しく64ビットで表現できるようになり、リンカが将来的に64ビットのサイズ値を完全に利用するようになった場合でも、データの一貫性が保たれるようになります。これは、Goツールチェインの堅牢性を高める上で重要な修正です。

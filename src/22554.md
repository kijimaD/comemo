# [インデックス 22554] ファイルの概要

このコミットは、`cmd/go` ツールにおける `go get` コマンドの挙動を改善するものです。具体的には、ローカルパス（例: `./pkg`）を指定して `go get` を実行した際に、パッケージのダウンロードは成功するものの、その後のインストールが失敗するという問題を修正します。この問題は、内部的なエラー追跡メカニズムが正規インポートパス（Canonical Import Path）とローカルパスの間の不一致によって正しく機能していなかったことに起因します。本コミットにより、常に正規インポートパスを使用することで、この「スティッキーエラー」が適切にクリアされ、ローカルパスからの `go get` が正しく動作するようになります。

## 変更の背景

この変更の背景には、Goのパッケージ管理ツールである `go get` コマンドが、ローカルパス（例: `./foo`）を指定して実行された場合に、期待通りに動作しないという問題がありました。具体的には、リモートリポジトリからパッケージのソースコードをダウンロードすることは成功するものの、その後のビルドやインストールといった処理が完了しないという挙動が報告されていました（Go Issue #9767）。

この問題は、`go get` の内部的なエラーハンドリングとキャッシュメカニズムに起因していました。`go get` は、パッケージのダウンロードが必要であると判断した場合に、その情報を内部的なマップ（`downloadCache` や `packageCache` など）に記録します。このマップは、パッケージの「正規インポートパス（Canonical Import Path）」をキーとして使用していました。しかし、エラー状態をクリアする際には、ユーザーが指定した「ローカルパス」がキーとして使用されることがありました。

結果として、ダウンロードが必要であるという「スティッキーエラー（sticky error）」が、正規インポートパスで記録されたまま、ローカルパスでのクリア処理では見つけられずに残り続けていました。この残存するエラー情報が、後続のインストール処理を妨げていたのです。

このコミットは、このような不整合を解消し、ローカルパスを指定した場合でも `go get` が完全に機能するようにするために導入されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoの概念と `go get` コマンドの動作に関する知識が必要です。

1.  **`go get` コマンド**:
    `go get` はGo言語のパッケージ管理ツールであり、指定されたパッケージとその依存関係をリモートリポジトリ（GitHubなど）からダウンロードし、`GOPATH` または Go Modules のキャッシュディレクトリに配置し、必要に応じてビルド・インストールを行うコマンドです。開発者が外部ライブラリをプロジェクトに組み込む際に頻繁に利用されます。

2.  **`GOPATH`**:
    Go 1.11より前のバージョンでは、`GOPATH` はGoのワークスペースのルートディレクトリを定義する環境変数でした。ソースコード、コンパイル済みパッケージ、実行可能バイナリがこのディレクトリ構造内に配置されます。`go get` は、ダウンロードしたパッケージを `$GOPATH/src` 以下に配置します。Go 1.11以降のGo Modulesの導入により、`GOPATH` の役割は限定的になりましたが、このコミットが作成された時点では主要なパッケージ管理メカニズムでした。

3.  **正規インポートパス (Canonical Import Path)**:
    Goのパッケージは、そのソースコードがどこにあるかを示す「インポートパス」によって識別されます。例えば、`"github.com/user/repo/pkg"` のような形式です。これは、パッケージのソースコードが配置されているリポジトリのURLと、そのリポジトリ内でのパスを組み合わせたものです。`go get` は、この正規インポートパスを使用して、パッケージのダウンロード元を特定し、内部的なキャッシュやエラー追跡のキーとして利用します。

4.  **ローカルパス**:
    ユーザーが `go get ./foo` のように、現在のディレクトリからの相対パスや、`$GOPATH/src/github.com/user/repo/foo` のようなファイルシステム上の絶対パスを指定する場合があります。これは、Goツールが内部的に正規インポートパスに変換しようと試みますが、変換プロセスやその後の内部処理で不整合が生じることがありました。

5.  **`downloadCache` および `packageCache`**:
    `go get` コマンドは、パフォーマンス向上のために内部的なキャッシュメカニズムを使用します。`downloadCache` はダウンロード済みのリポジトリ情報を、`packageCache` はパッケージのメタデータやビルド情報を保持します。これらのキャッシュは、通常、パッケージの正規インポートパスをキーとして使用し、同じパッケージに対する重複した処理を防ぎます。

6.  **スティッキーエラー (Sticky Error)**:
    この文脈では、一度発生したエラー状態が内部的に保持され、その後の処理に影響を与え続ける状態を指します。本来であれば、エラーの原因が解消されたり、関連する処理が完了したりした時点で、このエラー状態はクリアされるべきですが、キーの不一致によりクリアされずに残ってしまっていました。

## 技術的詳細

このコミットが修正する問題の核心は、`go get` コマンドの内部処理における「インポートパスの正規化」と「エラー状態の管理」の間の不整合です。

`go get` は、ユーザーが `go get ./foo` のようにローカルパスを指定した場合、まずそのローカルパスから対応する正規インポートパス（例: `github.com/user/repo/foo`）を推論しようとします。この推論は `loadPackage` 関数などによって行われます。

問題は、パッケージのダウンロードが必要であると判断された際に、その情報（および関連するエラー状態）が内部キャッシュ（`downloadCache` や `packageCache`）に記録される際に、**推論された正規インポートパス**がキーとして使用される点にありました。

しかし、その後の処理で、このエラー状態をクリアしようとする際に、**ユーザーが最初に指定したローカルパス**がキーとして使用されることがありました。

例:
1.  ユーザーが `go get ./foo` を実行。
2.  `go` ツールは `./foo` から `github.com/user/repo/foo` という正規インポートパスを推論。
3.  パッケージが未ダウンロードであるため、`github.com/user/repo/foo` をキーとして「ダウンロードが必要」というエラー状態が内部キャッシュに記録される。
4.  パッケージのダウンロードが成功。
5.  ダウンロード完了後、内部キャッシュからエラー状態をクリアしようとする。この際、キーとして `./foo` が使用される。
6.  キャッシュには `github.com/user/repo/foo` をキーとするエントリしか存在しないため、`./foo` をキーとするクリア操作は失敗し、エラー状態が「スティッキー」なまま残る。
7.  この残存するエラー状態が、その後のビルドやインストール処理を妨げ、最終的に `go get` が失敗する。

このコミットの解決策はシンプルかつ効果的です。`download` 関数内で、`loadPackage` によって推論された正規インポートパス `p.ImportPath` を、後続の処理で使用する `arg` 変数に再代入することで、常に正規インポートパスが使用されるようにします。これにより、キャッシュへの記録とクリアの両方で一貫したキーが使用されるようになり、スティッキーエラーの問題が解消されます。

コメントにある `hysteresis effects` は、システムが過去の状態に依存して現在の挙動を決定する現象を指します。この文脈では、過去に記録された（そしてクリアされなかった）エラー状態が、現在の `go get` の実行に悪影響を与えることを意味しています。正規インポートパスの一貫した使用により、このヒステリシス効果が排除されます。

## コアとなるコードの解説

### `src/cmd/go/get.go` の変更

追加された1行 `arg = p.ImportPath` がこのコミットの核心です。

*   `p` は `loadPackage` 関数などによってロードされたパッケージの情報を保持する構造体です。この構造体には、パッケージの正規インポートパスが `p.ImportPath` として格納されています。
*   `arg` は `download` 関数に渡される引数で、元々はユーザーが指定したパス（ローカルパスの場合もある）を保持していました。

この変更により、`download` 関数内で後続の処理（`downloadCache` や `packageCache` へのアクセスなど）が行われる際に、常に正規インポートパス `p.ImportPath` が使用されるようになります。これにより、キャッシュへの書き込みと読み出し（およびエラー状態のクリア）が同じキーで行われることが保証され、不整合が解消されます。

追加されたコメントは、この変更の意図を明確に説明しています。
*   `loadPackage inferred the canonical ImportPath from arg.`：`loadPackage` が `arg` から正規インポートパスを推論したことを示しています。
*   `Use that in the following to prevent hysteresis effects in e.g. downloadCache and packageCache.`：`downloadCache` や `packageCache` におけるヒステリシス効果（過去の状態に引きずられる問題）を防ぐために、この正規インポートパスを使用することを指示しています。
*   `This allows invocations such as: ... go get ./foo`：この変更によって、ローカルパスを指定した `go get` が正しく動作するようになる具体的なユースケースを示しています。
*   `see: golang.org/issue/9767`：関連するGo Issueへの参照です。

### `src/cmd/go/test.bash` の変更

追加されたテストケースは、この修正が正しく機能することを確認するためのものです。

*   `TEST go get ./rsc.io/toolstash '(golang.org/issue/9767)'`：テストの目的と、関連するIssue番号を示しています。
*   `d=$(TMPDIR=/var/tmp mktemp -d -t testgoXXX)`：一時ディレクトリを作成し、テスト用の `GOPATH` として設定します。これにより、テストが他の環境に影響を与えないようにします。
*   `export GOPATH=$d`：作成した一時ディレクトリを `GOPATH` に設定します。
*   `export testgo=$(pwd)/testgo`：`go` コマンドのテスト用バイナリへのパスを設定します。
*   `mkdir -p $GOPATH/src/rsc.io`：テスト対象のパッケージを配置するためのディレクトリ構造を作成します。
*   `(cd $GOPATH/src/rsc.io && $testgo get ./toolstash) || ok=false`：
    *   `cd $GOPATH/src/rsc.io`：作成したディレクトリに移動します。
    *   `$testgo get ./toolstash`：**ここでローカルパス `./toolstash` を指定して `go get` を実行します。** このコマンドが成功すれば `ok` 変数は `true` のままで、失敗すれば `false` になります。このテストの目的は、この `go get` が失敗しないことを確認することです。
*   `unset GOPATH`、`unset testgo`、`rm -rf $d`：テスト後に環境変数をクリアし、一時ディレクトリを削除してクリーンアップします。

このテストケースは、まさにこのコミットが解決しようとしているシナリオ（ローカルパスでの `go get`）を再現し、その修正が有効であることを検証しています。

# [インデックス 27482] ファイルの概要

このコミットは、Goの`net/http`パッケージにおいて、HTTP/1.1のgzip圧縮されたレスポンスに対する接続再利用の効率を改善するものです。具体的には、`http.Response.Body`を構成するリーダーの順序を変更することで、`bodyEOFSignal`がレスポンスボディの終端（EOF）を正しく検出し、基盤となるTCP接続がより頻繁に再利用されるように修正しています。

## 元コミット内容

`net/http`: gzip圧縮されたレスポンスに対してHTTP/1 Transportの接続をより多く再利用するようにする。

`http.Response.Body`の`gzip.Reader`と、HTTP/1レスポンスのフレーミング（`Content-Length`またはHTTP/1.1チャンク）の終端を監視するリーダーの構成順序を入れ替える。

以前は、`bodyEOFSignal`が基盤となる`gzip.Reader`からのEOFを待ってから接続を再利用していた。しかし、`gzip.Reader`（より正確には`flate.Reader`）が最後のチャンクで早期の`io.EOF`を返さなかったため、`bodyEOFSignal`は接続を解放していなかった。これは、HTTP/1フレーミングからのEOFが、`flate.Reader`内でバイト単位の読み取りを行うために作成されたヘルパー`bufio.Reader`によって、まだ関心のない段階で読み取られてしまっていたためである。

読み取りの構成順序を以下のように変更する：

`user -> http.Response.Body -> gzipReader -> gzip.Reader -> bufio.Reader -> bodyEOFSignal -> [ http/1.1 de-chunking reader ] (optional) -> http1 framing *body`

これにより、`gzip.Reader`が`bufio.Reader`を介してバイト単位の読み取りを行う際、`bufio.Reader`は`bodyEOFSignal`リーダーに対して大きな読み取りを行うようになる。その結果、`bodyEOFSignal`は基盤となるHTTP/1フレーミングのEOFを検出し、接続を再利用できるようになる。

`google/go-github#317`、`#14867`、および関連する`flate.Reader`への放棄された修正`golang.org/cl/21290`を更新する。

## 変更の背景

このコミットの背景には、Goの`net/http`クライアントがgzip圧縮されたHTTP/1.1レスポンスを処理する際に、TCP接続の再利用が効率的に行われないという問題がありました。HTTP/1.1では、パフォーマンス向上のために既存のTCP接続を再利用することが推奨されます（Keep-Alive）。しかし、特定の条件下で、レスポンスボディの読み取りが完了しても接続が閉じられてしまい、新しいリクエストごとに新しい接続が確立されるという非効率が発生していました。

具体的には、`http.Response.Body`の内部で、レスポンスボディの終端を検出して接続再利用を可能にする`bodyEOFSignal`と、gzip圧縮を解除する`gzip.Reader`の間に、意図しない相互作用がありました。`gzip.Reader`が内部的に使用する`flate.Reader`が、効率のために`bufio.Reader`を介してバイト単位の読み取りを行う際、HTTP/1フレーミングのEOF（レスポンスボディの実際の終端）を`bodyEOFSignal`が検出する前に読み取ってしまうことがありました。これにより、`bodyEOFSignal`はEOFを検知できず、接続が解放されないままになっていました。結果として、接続は再利用されずに閉じられ、次のリクエストで新しい接続が確立されることになり、特に多数のgzip圧縮されたレスポンスを処理するアプリケーションでパフォーマンスの低下を招いていました。

コミットメッセージで言及されている`google/go-github#317`や`#14867`は、この接続再利用の問題を報告したバグトラッカーのエントリである可能性が高いです。また、`golang.org/cl/21290`は、以前に`flate.Reader`側でこの問題を解決しようとしたものの、最終的に放棄された修正案を示唆しています。このコミットは、`flate.Reader`の挙動を変更するのではなく、リーダーの構成順序を変更するという異なるアプローチで問題を解決しています。

## 前提知識の解説

*   **HTTP/1.1 接続の再利用 (Connection Reuse / Keep-Alive)**:
    HTTP/1.1プロトコルでは、クライアントとサーバー間で一度確立されたTCP接続を、複数のHTTPリクエストとレスポンスの送受信に再利用するメカニズムが提供されています。これを「Keep-Alive」接続と呼びます。接続の再利用により、新しいTCP接続を確立する際のオーバーヘッド（3ウェイハンドシェイク、TLSハンドシェイクなど）が削減され、特に多数の小さなリクエストを送信する場合にネットワークのレイテンシが低減し、全体的なパフォーマンスが向上します。接続を再利用するためには、クライアントとサーバーがレスポンスボディの終端を正確に識別し、次のリクエストの準備ができることを知る必要があります。

*   **`net/http.Transport`**:
    Goの標準ライブラリ`net/http`パッケージにおける`Client`の基盤となるコンポーネントです。`Transport`は、HTTPリクエストの送信、レスポンスの受信、TCP接続の確立と管理、そして接続の再利用といった低レベルのネットワーク操作を処理します。`Transport`は、アイドル状態の接続をプールし、必要に応じて再利用することで、HTTPクライアントの効率を向上させます。

*   **`http.Response.Body`**:
    `http.Response`構造体のフィールドで、HTTPレスポンスのボディ（ペイロード）を表します。これは`io.ReadCloser`インターフェースを実装しており、クライアントはここからレスポンスデータをバイトストリームとして読み取ることができます。読み取りが完了したら、`Close()`メソッドを呼び出してリソースを解放する必要があります。

*   **`gzip.Reader` (`compress/gzip`パッケージ)**:
    Goの`compress/gzip`パッケージに含まれる構造体で、gzip形式で圧縮されたデータを透過的に解凍しながら読み取るための`io.Reader`インターフェースを実装します。`gzip.Reader`は、内部的に`compress/flate`パッケージの`flate.Reader`を利用して実際のデータ解凍を行います。

*   **`bodyEOFSignal`**:
    `net/http`パッケージの`Transport`内部で使用される非公開の構造体です。これは`http.Response.Body`をラップし、レスポンスボディの読み取りが完了し、その終端（EOF: End Of File）に達したことを検出する役割を担います。EOFが検出されると、`bodyEOFSignal`は登録されたコールバック関数（`fn`）を実行し、`Transport`に基盤となるTCP接続がアイドル状態になり、再利用可能であることを通知します。このメカニズムは、接続再利用の鍵となります。

*   **HTTP/1.1 レスポンスのフレーミング (Framing)**:
    HTTP/1.1では、レスポンスボディの開始と終了を正確に識別するためのメカニズムがいくつかあります。
    *   **`Content-Length` ヘッダー**: レスポンスボディの正確なバイト数を示します。クライアントはこのバイト数を読み取ると、ボディの終端に達したと判断します。
    *   **`Transfer-Encoding: chunked`**: レスポンスボディが、サイズ情報を持つ複数の「チャンク」（塊）に分割されて送信されることを示します。最後のチャンクはサイズが0であり、これによってボディの終端が示されます。この場合、`Content-Length`ヘッダーは存在しません。
    `Transport`はこれらのフレーミング情報に基づいて、レスポンスボディの実際の終端を判断します。

*   **`flate.Reader`の読み取り挙動**:
    `gzip.Reader`が内部で利用する`flate.Reader`は、圧縮データを効率的に解凍するために、基盤となる`io.Reader`から一度に大量のデータを読み込むことがあります。しかし、場合によっては、特にデータの終端近くで、`bufio.Reader`のようなバッファリングリーダーを介してバイト単位で読み取りを行うことがあります。このバイト単位の読み取りが、`bodyEOFSignal`がEOFを検出するタイミングに影響を与え、問題を引き起こしていました。

## 技術的詳細

このコミットが解決しようとしている問題は、Goの`net/http`クライアントがgzip圧縮されたHTTP/1.1レスポンスを処理する際の、TCP接続再利用の失敗です。この問題は、`http.Response.Body`を構成する複数の`io.Reader`の順序に起因していました。

**以前のリーダー構成:**

```
user -> http.Response.Body
     -> bodyEOFSignal
     -> gzipReader
     -> gzip.Reader
     -> bufio.Reader
   [ -> http/1.1 de-chunking reader ]   (optional)
     -> http1 framing *body (実際のTCP接続からの生データ)
```

この構成では、`bodyEOFSignal`が`gzipReader`の上に位置していました。`bodyEOFSignal`の目的は、レスポンスボディの読み取りが完了し、基盤となるHTTP/1フレーミングのEOFに達したときに、接続を再利用可能にするシグナルを送ることです。しかし、この順序では、`bodyEOFSignal`は`gzipReader`からのEOFを待っていました。

問題は、`gzip.Reader`（そしてその内部の`flate.Reader`）が、レスポンスボディの最後の部分を処理する際に、必ずしもすぐに`io.EOF`を返さなかった点にありました。特に、`flate.Reader`が内部で`bufio.Reader`を介してバイト単位の読み取りを行う場合、`bufio.Reader`が基盤となる`http1 framing *body`（実際のTCP接続からの生データ）からHTTP/1フレーミングのEOFを先に読み取ってしまい、そのEOFを消費してしまっていました。しかし、この`bufio.Reader`は`bodyEOFSignal`の直接のラッパーではないため、`bodyEOFSignal`はこのEOFを検知できませんでした。結果として、`bodyEOFSignal`はレスポンスボディの終端を認識できず、接続をアイドル状態として解放することができませんでした。これにより、`Transport`は接続を再利用できず、次のリクエストのために新しい接続を確立する必要がありました。

**新しいリーダー構成:**

```
user -> http.Response.Body
     -> gzipReader
     -> gzip.Reader
     -> bufio.Reader
     -> bodyEOFSignal
   [ -> http/1.1 de-chunking reader ]   (optional)
     -> http1 framing *body (実際のTCP接続からの生データ)
```

このコミットでは、`bodyEOFSignal`と`gzipReader`の構成順序を入れ替えることでこの問題を解決しています。新しい構成では、`gzipReader`が`bodyEOFSignal`の上に位置します。

この変更により、`gzip.Reader`が内部で`bufio.Reader`を介してバイト単位の読み取りを行う際、その`bufio.Reader`は`bodyEOFSignal`リーダーに対して読み取りを行います。つまり、`bodyEOFSignal`が`http1 framing *body`からのEOFを直接監視するようになります。

`gzip.Reader`がすべての圧縮データを解凍し終え、`bodyEOFSignal`から読み取ろうとしたときに、`bodyEOFSignal`は基盤となるHTTP/1フレーミングのEOFを検知します。これにより、`bodyEOFSignal`は正しく`fn`コールバックを実行し、`Transport`に接続が再利用可能であることを通知できるようになります。結果として、gzip圧縮されたレスポンスに対しても、HTTP/1.1接続が効率的に再利用されるようになり、パフォーマンスが向上します。

また、この変更に伴い、`maybeUngzipResponse`というヘルパー関数が削除され、そのロジックが`readLoop`内にインライン化されています。これは、`bodyEOFSignal`の初期化と`gzipReader`のラップ処理の順序が変更されたため、以前のヘルパー関数が不要になったためです。

## コアとなるコードの変更箇所

このコミットでは、主に`src/net/http/transport.go`と`src/net/http/transport_test.go`が変更されています。

### `src/net/http/transport.go`

1.  **`readLoop`関数の変更**:
    *   `bodyEOFSignal`の初期化と`resp.Body`への割り当てが、`gzipReader`によるラップ処理の前に移動されました。
    *   以前は`maybeUngzipResponse`関数が呼び出されていましたが、この関数は削除され、そのロジックが`readLoop`内に直接組み込まれました。
    *   新しいロジックでは、まず`bodyEOFSignal`が`resp.Body`をラップし、その後に`rc.addedGzip`が`true`で`Content-Encoding`が`gzip`の場合に、`gzipReader`がその`bodyEOFSignal`をさらにラップする形に変更されています。
    *   `resp.Header.Del("Content-Encoding")`、`resp.Header.Del("Content-Length")`、`resp.ContentLength = -1`といったヘッダー操作も、`gzipReader`が適用される条件分岐内に移動されました。

    *   このヘルパー関数は不要になったため、完全に削除されました。

3.  **`bodyEOFSignal`構造体のコメント更新**:
    *   `bodyEOFSignal`の役割に関するコメントがより明確に更新され、HTTP/1トランスポートがレスポンスボディの終端を確実に確認するためのものであることが強調されました。

4.  **`errReadOnClosedResBody`変数の追加**:
    *   `"http: read on closed response body"`というエラー文字列が、新しい`errReadOnClosedResBody`変数として定義され、再利用されるようになりました。

    *   `body`フィールドの型が`io.ReadCloser`から`*bodyEOFSignal`に変更されました。これにより、`gzipReader`が直接`bodyEOFSignal`をラップする関係が明確になります。

    *   `zerr`フィールド（`gzip.NewReader`からのエラーを保持するため）が追加されました。

    *   `gzip.NewReader`の呼び出しが、`zerr`フィールドを使用してエラーを保持するように変更されました。これにより、`gzip.NewReader`が一度失敗した場合、そのエラーが永続的に返されるようになります。

    *   `gz.body.mu.Lock()`と`gz.body.mu.Unlock()`によるロックが追加され、`bodyEOFSignal`が閉じられているかどうかを確認するようになりました。これにより、閉じられたレスポンスボディに対する読み取りを防ぎます。

## コアとなるコードの解説

このコミットの核心は、`net/http`パッケージ内でHTTPレスポンスボディを処理するリーダーの「スタック」の順序を変更することにあります。

**`bodyEOFSignal`の役割の変更:**
以前は、`bodyEOFSignal`が`gzipReader`をラップしていました。これは、`bodyEOFSignal`が`gzipReader`からEOFを受け取ることを期待していたことを意味します。しかし、`gzipReader`が内部で`flate.Reader`を使用し、さらに`bufio.Reader`を介して基盤となるネットワーク接続からデータを読み取る際、`bufio.Reader`がHTTP/1フレーミングのEOFを`bodyEOFSignal`が検知する前に消費してしまう問題がありました。

変更後、`gzipReader`が`bodyEOFSignal`をラップするようになりました。

```go
// src/net/http/transport.go の readLoop 関数内 (変更後)
body := &bodyEOFSignal{
    body: resp.Body, // 元のレスポンスボディ (http1 framing *body)
    earlyCloseFn: func() error { /* ... */ },
    fn: func(err error) error { /* ... */ },
}
resp.Body = body // まず bodyEOFSignal が元のボディをラップ

if rc.addedGzip && resp.Header.Get("Content-Encoding") == "gzip" {
    resp.Body = &gzipReader{body: body} // 次に gzipReader が bodyEOFSignal をラップ
    resp.Header.Del("Content-Encoding")
    resp.Header.Del("Content-Length")
    resp.ContentLength = -1
}
```

この新しい順序では、`gzipReader`が`bodyEOFSignal`からデータを読み取ります。`gzipReader`が内部で`bufio.Reader`を使ってデータを読み込む際、その`bufio.Reader`は`bodyEOFSignal`に対して読み取りを行います。これにより、`bodyEOFSignal`は基盤となるHTTP/1フレーミングのEOFを直接監視し、正確に検出できるようになります。`bodyEOFSignal`がEOFを検出すると、その`fn`コールバックが実行され、`Transport`に接続が再利用可能であることを通知します。

**`gzipReader`の変更点:**
`gzipReader`構造体の`body`フィールドの型が`io.ReadCloser`から`*bodyEOFSignal`に具体化されたことで、`gzipReader`が`bodyEOFSignal`と直接連携することがコード上で明確になりました。また、`gzipReader.Read`メソッド内で`bodyEOFSignal`のロックを取得し、ボディが閉じられているかを確認する処理が追加されたことで、閉じられたボディに対する不正な読み取りを防ぎ、堅牢性が向上しています。

**テストの追加:**
`TestTransportReuseConnection_Gzip_Chunked`と`TestTransportReuseConnection_Gzip_ContentLength`という新しいテストは、この修正が意図通りに機能することを確認するために重要です。これらのテストは、gzip圧縮されたレスポンス（チャンクエンコーディングと`Content-Length`の両方の場合）に対して、HTTPクライアントが同じTCP接続を再利用できることを検証します。これにより、回帰を防ぎ、将来の変更に対する安全網を提供します。

これらの変更により、Goの`net/http`クライアントは、gzip圧縮されたレスポンスを扱う際の接続再利用の効率が大幅に向上し、全体的なネットワークパフォーマンスが改善されます。

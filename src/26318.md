## 変更の背景

`net/http`パッケージの`ReadResponse`関数は、ネットワークから受信した生データをHTTPレスポンス構造体に変換する上で非常に重要な役割を担っています。この関数が不正な入力（例えば、破損したHTTPレスポンスや不完全なレスポンス）をどのように処理するかは、アプリケーションの安定性とセキュリティに直結します。

以前のテストでは、`ReadResponse`の成功パスや一部のエラーケースはカバーされていましたが、HTTPステータスラインやバージョン文字列の様々な不正な形式に対する網羅的なテストが不足していました。この不足は、予期せぬ入力に対して`ReadResponse`がクラッシュしたり、誤った情報を返したりする潜在的なリスクを意味します。

このコミットの目的は、これらのエッジケースやエラー条件に対するテストカバレッジを強化し、`ReadResponse`関数がより堅牢で信頼性の高いものとなるようにすることです。特に、HTTPプロトコルの仕様に厳密に従わない、あるいは部分的にしか従わないレスポンスに対する挙動を明確に検証することが意図されています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が役立ちます。

*   **Goの`net/http`パッケージ**: Go言語の標準ライブラリの一部で、HTTPクライアントとサーバーの実装を提供します。ウェブアプリケーションやAPIクライアントを構築する際に中心的に使用されます。
*   **`http.ReadResponse`関数**: `net/http`パッケージ内で定義されている関数で、`bufio.Reader`からHTTPレスポンスのバイトストリームを読み込み、それを`*http.Response`構造体（HTTPレスポンスの各要素を表現するGoの構造体）にパースします。このプロセスには、ステータスライン（HTTPバージョン、ステータスコード、理由フレーズ）、ヘッダー、そしてオプションでボディの読み込みが含まれます。
*   **HTTPレスポンスの構造**:
    1.  **ステータスライン**: `HTTP-Version Status-Code Reason-Phrase CRLF`の形式。例: `HTTP/1.1 200 OK`。
    2.  **ヘッダー**: `Field-Name: Field-Value CRLF`の形式で複数行続き、空行（`CRLF`）で終了します。
    3.  **ボディ**: ヘッダーの後に続くデータ。
*   **`io.ErrUnexpectedEOF`**: Goの`io`パッケージで定義されているエラーで、入力ストリームの予期せぬ終端（Expected End Of File）に達したことを示します。例えば、完全なデータが読み込まれる前にストリームが終了した場合に発生します。
*   **`bufio.Reader`**: `bufio`パッケージが提供する型で、I/O操作をバッファリングすることで効率を向上させます。`ReadResponse`は、この`bufio.Reader`を介してネットワークからの生データを読み込みます。
*   **HTTPステータスコード**: HTTPレスポンスのステータスラインに含まれる3桁の数字で、リクエストの結果を示します（例: 200 OK, 404 Not Found, 500 Internal Server Error）。

## 技術的詳細

このコミットの主要な技術的変更は、`ReadResponse`関数が様々な不正なHTTPレスポンス形式に対してどのように振る舞うかを検証するための、新しいテストスイート`TestReadResponseErrors`の導入です。

`TestReadResponseErrors`は、以下のような多様な不正な入力パターンを網羅的にテストします。

1.  **不完全なレスポンス**: HTTPレスポンスが途中で途切れている場合（例: ステータスラインのみでヘッダーがない、ヘッダーが不完全）。これには`io.ErrUnexpectedEOF`が期待されます。
2.  **不正なHTTPバージョン**: `HTTP/1.100000000002`や`HTTP/1.-1`、`HTTP/A.B`、`HTTP/1`、`http/1.1`（大文字小文字の区別）など、HTTPバージョン文字列の形式が不正な場合。これらは`malformed HTTP version`エラーを発生させることが期待されます。
3.  **不正なHTTPステータスコード**: `20X Unknown`、`abcd Unknown`、`二百/两百 OK`、`c8 OK`、`0x12d Moved Permanently`など、ステータスコードが3桁の数字でない、あるいは数字以外の文字を含む場合。これらは`malformed HTTP status code`エラーを発生させることが期待されます。
4.  **空の入力**: `ReadResponse`に空の入力が与えられた場合。

これらのテストケースは、`testCase`構造体を用いて定義され、入力文字列(`in`)と期待されるエラー(`wantErr`)を含みます。`wantErr`は、`nil`（エラーなし）、特定のエラー値（例: `io.ErrUnexpectedEOF`）、またはエラーメッセージに含まれるべき部分文字列（例: `"malformed HTTP status code"`）のいずれかを取ることができます。

エラーの比較には、新しく導入されたヘルパー関数`matchErr`が使用されます。この関数は、実際の`error`オブジェクトと`wantErr`の型に基づいて、柔軟なエラーマッチングを可能にします。これにより、エラーメッセージ全体を厳密に比較するのではなく、特定のキーワードが含まれているかどうかのチェックも行えるため、テストの記述がより柔軟になります。

また、`TestLocationResponse`には、リクエストURLが空の場合のLocationヘッダーの処理を検証する新しいテストケースが追加されており、エッジケースに対するカバレッジがさらに向上しています。

## コアとなるコードの解説

### `TestReadResponseErrors`関数

この関数は、`ReadResponse`のエラー処理を徹底的にテストするために設計されています。

```go
func TestReadResponseErrors(t *testing.T) {
	type testCase struct {
		name    string // optional, defaults to in
		in      string
		wantErr interface{} // nil, err value, or string substring
	}

	// ... (status, version ヘルパー関数とテストケースの定義) ...

	tests := []testCase{
		{"", "", io.ErrUnexpectedEOF},
		{"", "HTTP/1.1 301 Moved Permanently\r\nFoo: bar", io.ErrUnexpectedEOF},
		{"", "HTTP/1.1", "malformed HTTP response"},
		{"", "HTTP/2.0", "malformed HTTP response"},
		status("20X Unknown", true), // true は "malformed HTTP status code" に変換される
		// ... 他のステータスコードエラーケース ...
		version("HTTP/1.2", nil),
		// ... 他のバージョンエラーケース ...
	}
	for i, tt := range tests {
		br := bufio.NewReader(strings.NewReader(tt.in))
		_, rerr := ReadResponse(br, nil)
		if err := matchErr(rerr, tt.wantErr); err != nil {
			name := tt.name
			if name == "" {
				name = fmt.Sprintf("%i. input %q", i, tt.in)
			}
			t.Errorf("%s: %v", name, err)
		}
	}
}
```

このテスト関数は、`testCase`スライスをイテレートし、各`testCase`に対して`strings.NewReader`と`bufio.NewReader`を使って入力ストリームを作成します。そして`ReadResponse`を呼び出し、返されたエラー`rerr`を`matchErr`ヘルパー関数で期待されるエラー`tt.wantErr`と比較します。エラーが一致しない場合、`t.Errorf`でテスト失敗を報告します。

### `matchErr`ヘルパー関数

`matchErr`は、エラーの比較ロジックをカプセル化し、テストコードの可読性と再利用性を高めます。

```go
// wantErr can be nil, an error value to match exactly, or type string to
// match a substring.
func matchErr(err error, wantErr interface{}) error {
	if err == nil {
		if wantErr == nil {
			return nil // 成功が期待され、実際に成功した
		}
		if sub, ok := wantErr.(string); ok {
			return fmt.Errorf("unexpected success; want error with substring %q", sub)
		}
		return fmt.Errorf("unexpected success; want error %v", wantErr) // 成功が期待されず、成功した
	}
	if wantErr == nil {
		return fmt.Errorf("%v; want success", err) // 成功が期待されたが、エラーが発生した
	}
	if sub, ok := wantErr.(string); ok {
		if strings.Contains(err.Error(), sub) {
			return nil // エラーメッセージに部分文字列が含まれている
		}
		return fmt.Errorf("error = %v; want an error with substring %q", err, sub) // 部分文字列が含まれていない
	}
	if err == wantErr {
		return nil // エラー値が完全に一致する
	}
	return fmt.Errorf("%v; want %v", err, wantErr) // エラー値が一致しない
}
```

この関数は、`err`（`ReadResponse`から返された実際のエラー）と`wantErr`（テストケースで期待されるエラー）を比較します。
*   `wantErr`が`nil`の場合、エラーが発生しないことを期待します。
*   `wantErr`が`string`型の場合、実際のエラーメッセージにその文字列が含まれていることを期待します。
*   それ以外の場合（`wantErr`が`error`型の場合）、実際のエラーが`wantErr`と完全に一致することを期待します。

この柔軟な比較メカニズムにより、テストはエラーの具体的な内容（例: `io.ErrUnexpectedEOF`）だけでなく、より一般的なエラーカテゴリ（例: "malformed HTTP version"というメッセージを含むエラー）も検証できるようになります。

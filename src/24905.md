## 元コミット内容
`cmd/internal/ld`: 共有オブジェクトを作成する際に、読み取り専用の再配置済みデータを `.data.rel.ro` に配置する。

現在、Goはテキストセグメント（テキストセクションではない）に対する再配置を持つため、プロセス間で共有できない共有ライブラリを生成しています。このコミットは、静的リンカによって認識されるマジック名を持つセクションに一部のデータを移動することで、この問題を修正します。

`genasmsym` で `STYPELINK` をスイッチに追加する変更は、darwin/arm64 で問題を修正するはずです。

Fixes #10914
Updates #9210

## 変更の背景

このコミットの主な背景は、Goが生成する共有ライブラリが、特定の条件下でプロセス間で適切に共有できないという問題にありました。具体的には、Goのリンカが生成する共有ライブラリには、テキストセグメント（コードが配置される領域）に対する再配置（relocation）が含まれていました。

共有ライブラリは、複数のプロセスが同じコードをメモリ上で共有することで、メモリ使用量を削減し、起動時間を短縮することを目的としています。しかし、テキストセグメントが書き込み可能であるか、または実行時に再配置によって変更される必要がある場合、そのセグメントはプロセス間で共有できなくなります。これは、各プロセスが独自の書き込み可能なコピーを持つ必要が生じるためです。

ELF（Executable and Linkable Format）形式の共有ライブラリでは、`DT_TEXTREL` というダイナミックタグが存在する場合、そのライブラリのテキストセグメントに実行時再配置が必要であることを示します。`DT_TEXTREL` が存在すると、その共有ライブラリは「テキスト再配置（text relocation）」を持つと見なされ、セキュリティ上のリスク（ASLRの無効化など）やパフォーマンスの低下（コピーオンライトの発生）を引き起こす可能性があります。現代のシステムでは、`DT_TEXTREL` のない共有ライブラリが推奨されており、多くのディストリビューションではこれをエラーとして扱います。

Goのリンカは、読み取り専用であるべきデータ（例えば、型情報、文字列、PCLNTABなど）であっても、実行時に再配置が必要な場合に、これらをテキストセグメントに配置し、結果として `DT_TEXTREL` を持つ共有ライブラリを生成していました。このコミットは、この問題を解決し、Goが生成する共有ライブラリがより効率的で安全にプロセス間で共有できるようにすることを目的としています。

## 前提知識の解説

### 共有ライブラリ (Shared Library)
共有ライブラリは、複数の実行可能ファイルや他のライブラリによって共有されるコードとデータを含むファイルです。これにより、ディスクスペースとメモリ使用量を節約し、プログラムの起動を高速化できます。Linuxでは `.so` (shared object)、Windowsでは `.dll` (dynamic link library)、macOSでは `.dylib` という拡張子が一般的です。

### 再配置 (Relocation)
プログラムがコンパイルされ、リンクされる際、コードやデータ内のアドレスは最終的な実行時アドレスとは異なる場合があります。再配置とは、リンカやダイナミックリンカが、これらのアドレスをプログラムがメモリにロードされる際の実際のアドレスに合わせて修正するプロセスです。

### テキストセグメント (Text Segment)
実行可能ファイルや共有ライブラリのメモリレイアウトの一部で、実行可能なコード（命令）が格納される領域です。通常、このセグメントは読み取り専用としてマークされ、複数のプロセス間で共有されます。

### データセグメント (Data Segment)
初期化されたグローバル変数や静的変数が格納される領域です。通常、このセグメントは読み書き可能であり、各プロセスは独自のコピーを持ちます。

### `.rodata` セクション (Read-Only Data Section)
読み取り専用のデータ（定数、文字列リテラルなど）が格納されるセクションです。これはテキストセグメントと同様に、通常は読み取り専用としてマークされ、共有可能です。

### `DT_TEXTREL` (Dynamic Tag for Text Relocations)
ELF形式の共有ライブラリのダイナミックセクションに存在するタグの一つです。このタグが存在する場合、その共有ライブラリのテキストセグメントには、実行時に書き込みが必要な再配置エントリが含まれていることを示します。これは、テキストセグメントが読み取り専用として扱えないことを意味し、セキュリティ上の問題（ASLRの無効化）やパフォーマンスの低下（コピーオンライト）を引き起こすため、現代のシステムでは避けるべきとされています。

### `.data.rel.ro` セクション (Data Relocated Read-Only Section)
GNUリンカがサポートする特殊なセクション名です。このセクションに配置されたデータは、リンカによって実行時に再配置が適用された後、ダイナミックリンカによって読み取り専用にmprotect（メモリ保護）されます。これにより、本来は読み取り専用だが再配置によって書き込みが必要なデータを、安全かつ効率的に共有ライブラリ内で扱うことができます。`DT_TEXTREL` の問題を回避するための一般的な解決策の一つです。

### Goリンカ (`cmd/link`)
Go言語のコンパイラツールチェーンの一部であり、Goのソースコードから実行可能ファイルやライブラリを生成する役割を担います。Goのリンカは、C/C++のリンカとは異なり、多くの処理を独自に行います。

### `obj.STYPE`, `obj.SRODATA` などのシンボルタイプ
Goのリンカ内部で使用されるシンボルタイプで、リンカが各シンボルをどのセクションに配置すべきかを決定するために使われます。例えば、`STYPE` は型情報、`SRODATA` は読み取り専用データを示します。

## 技術的詳細

このコミットは、Goのリンカ (`cmd/link`) が共有ライブラリを生成する際のセクション配置ロジックを根本的に変更することで、`DT_TEXTREL` の問題を解決しています。

主要な変更点は以下の通りです。

1.  **新しいシンボルタイプの導入**:
    `src/cmd/internal/obj/link.go` に、既存の読み取り専用データ型 (`STYPE`, `SSTRING`, `SGOSTRING`, `SGCBITS`, `SRODATA`, `SFUNCTAB`) に対応する新しい「RELRO」シンボルタイプ (`STYPERELRO`, `SSTRINGRELRO`, `SGOSTRINGRELRO`, `SGCBITSRELRO`, `SRODATARELRO`, `SFUNCTABRELRO`) が導入されました。これらの新しいタイプは、再配置が必要な読み取り専用データを識別するために使用されます。

2.  **データセクションの再分類**:
    `src/cmd/link/internal/ld/data.go` の `dodata()` 関数内で、共有ライブラリをビルドする際に `UseRelro()` が真の場合、既存の読み取り専用データシンボル (`STYPE` から `SFUNCTAB` まで) のうち、再配置 (`len(s.R) > 0`) を持つもの、または `SGOSTRING` タイプを持つものを、対応する新しい `RELRO` シンボルタイプに「昇格」させます。これにより、これらのデータが特別な処理を必要とすることがリンカに明示されます。

3.  **`.data.rel.ro` セクションの導入と利用**:
    `src/cmd/link/internal/ld/data.go` では、`UseRelro()` が真の場合、`.data.rel.ro` という新しいセクションが導入されます。再配置が必要な読み取り専用データは、このセクションに配置されます。このセクションは、オブジェクトファイル内では書き込み可能 (`06` パーミッション) としてマークされますが、ダイナミックリンカによって実行時に読み取り専用にmprotectされることを期待します。
    また、`.typelink`, `.gosymtab`, `.gopclntab` といったセクションも、`UseRelro()` が真の場合には、それぞれ `.data.rel.ro.typelink`, `.data.rel.ro.gosymtab`, `.data.rel.ro.gopclntab` のように、`.data.rel.ro` プレフィックスを持つセクション名に変更されます。これにより、これらのセクションもRELROメカニズムの恩恵を受けます。

4.  **リンカフラグの追加**:
    `src/cmd/link/internal/ld/lib.go` の `hostlink()` 関数で、共有ライブラリ (`BuildmodeCShared` または `BuildmodeShared`) をビルドする際に、GNUリンカに対して `-Wl,-z,relro` フラグが追加されます。このフラグは、リンカにRELROメカニズムを有効にするよう指示します。

5.  **ELFヘッダの更新**:
    `src/cmd/link/internal/ld/elf.go` では、ELFヘッダのセクション名リストに、新しい `.data.rel.ro` セクション名と、プレフィックス付きの `.typelink`, `.gosymtab`, `.gopclntab` セクション名が追加されます。これにより、生成されるELFファイルがこれらの新しいセクションを正しく記述できるようになります。

6.  **テストの追加**:
    `misc/cgo/testcshared/test.bash` には、生成された共有ライブラリが `DT_TEXTREL` フラグを持っていないことを `readelf -d` コマンドで確認するテストが追加されました。
    `misc/cgo/testshared/shared_test.go` には、Goの `elf` パッケージを使用して、共有ライブラリが `DT_TEXTREL` タグを持っていないことをプログラム的に検証する `TestNoTextrel` テストが追加されました。

これらの変更により、Goのリンカは、再配置が必要な読み取り専用データをテキストセグメントから分離し、`.data.rel.ro` のような適切なセクションに配置することで、`DT_TEXTREL` の問題を回避し、より標準的で安全な共有ライブラリを生成できるようになります。

## コアとなるコードの変更箇所

### `src/cmd/internal/obj/link.go`
- 新しいシンボルタイプ `STYPERELRO` から `SFUNCTABRELRO` が追加されました。これらは、再配置が必要な読み取り専用データを表します。

```go
const (
	Sxxx = iota
	STEXT
	SELFRXSECT

	STYPE
	SSTRING
	SGOSTRING
	SGOFUNC
	SGCBITS
	SRODATA
	SFUNCTAB

	// Types STYPE-SFUNCTAB above are written to the .rodata section by default.
	// When linking a shared object, some conceptually "read only" types need to
	// be written to by relocations and putting them in a section called
	// ".rodata" interacts poorly with the system linkers. The GNU linkers
	// support this situation by arranging for sections of the name
	// ".data.rel.ro.XXX" to be mprotected read only by the dynamic linker after
	// relocations have applied, so when the Go linker is creating a shared
	// object it checks all objects of the above types and bumps any object that
	// has a relocation to it to the corresponding type below, which are then
	// written to sections with appropriate magic names.
	STYPERELRO
	SSTRINGRELRO
	SGOSTRINGRELRO
	SGCBITSRELRO
	SRODATARELRO
	SFUNCTABRELRO

	STYPELINK
	SSYMTAB
	SPCLNTAB
```

## コアとなるコードの解説

このコミットの核心は、Goのリンカが共有ライブラリを生成する際に、実行時に再配置が必要な読み取り専用データを適切に処理し、`DT_TEXTREL` の問題を回避することにあります。

1.  **シンボルタイプの拡張**:
    `src/cmd/internal/obj/link.go` で導入された `STYPERELRO` などの新しいシンボルタイプは、リンカが「これは読み取り専用データだが、再配置によって書き込みが必要になる可能性がある」と認識するための内部的なマーカーです。これにより、リンカはこれらのデータを通常の読み取り専用データ (`SRODATA` など) とは異なる方法で扱うことができます。

2.  **`dodata()` におけるデータ分類の動的な変更**:
    `src/cmd/link/internal/ld/data.go` の `dodata()` 関数は、リンカがデータセクションを構築する主要な場所です。ここで `UseRelro()` が真（つまり共有ライブラリをビルドしている場合）であれば、既存の読み取り専用データシンボル (`STYPE` から `SFUNCTAB`) のうち、再配置 (`s.R` が空でない) を持つもの、または `SGOSTRING` タイプ（Goの文字列データは特殊な扱いが必要な場合がある）を、対応する `RELRO` シンボルタイプに動的に変更します。この「昇格」により、これらのシンボルは後続の処理で `.data.rel.ro` セクションに割り当てられる準備が整います。

3.  **`.data.rel.ro` セクションの生成**:
    同じく `dodata()` 内で、`UseRelro()` が真の場合に `.data.rel.ro` という名前の新しいセクションが作成されます。このセクションは、前述の `RELRO` タイプに分類されたデータを受け入れるために特別に設計されています。このセクションは、オブジェクトファイル内では書き込み可能 (`06`) としてマークされますが、これはダイナミックリンカが再配置を適用できるようにするためです。再配置が完了した後、ダイナミックリンカは `-z,relro` フラグによってこのセクションを読み取り専用にmprotectします。これにより、データは実行時に安全に共有され、`DT_TEXTREL` の問題が回避されます。

4.  **セクション名のプレフィックス化**:
    `.typelink`, `.gosymtab`, `.gopclntab` といったGoランタイムの重要なメタデータセクションも、再配置が必要な場合があります。これらのセクションも `UseRelro()` が真の場合には、`.data.rel.ro.typelink` のように `.data.rel.ro` プレフィックスを持つセクション名に変更されます。これにより、これらのセクションもRELROメカニズムの恩恵を受け、`DT_TEXTREL` の発生を防ぎます。

5.  **リンカフラグ `-Wl,-z,relro` の追加**:
    `src/cmd/link/internal/ld/lib.go` で追加されたこのフラグは、Goリンカが外部のシステムリンカ（例えば `gcc` や `clang`）を呼び出す際に渡されます。このフラグは、システムリンカに対して、`.data.rel.ro` セクションを適切に処理し、実行時に再配置が完了した後に読み取り専用に設定するよう指示します。

これらの変更の組み合わせにより、Goは共有ライブラリを生成する際に、実行時に書き込みが必要な再配置を持つ読み取り専用データを、テキストセグメントではなく、専用の `.data.rel.ro` セクションに隔離できるようになりました。これにより、生成される共有ライブラリは `DT_TEXTREL` フラグを持たなくなり、より標準的で安全、かつ効率的にプロセス間で共有できるようになります。

# [インデックス 25534] ファイルの概要

このコミットは、Go言語のアセンブラツールチェーンの一部である `cmd/asm` の内部パッケージ `internal/lex` に含まれる `input.go` ファイルに対するものです。`input.go` は、アセンブリコードの字句解析（lexical analysis、またはトークン化）を行うための入力ストリームを管理する役割を担っています。具体的には、ソースコードの読み込み、マクロの展開、エラー報告などの機能を提供します。

## コミット

`cmd/asm/internal/lex` パッケージにおけるエラー報告のフォーマットを修正するコミットです。`in.Error` メソッドの誤った使用方法を修正し、他のエラーメッセージとの一貫性を保つように変更されました。

## 変更の背景

この変更の背景には、`cmd/asm/internal/lex` パッケージ内で使用されている `in.Error` メソッドの挙動に関する誤解がありました。元のコードでは、`in.Error` メソッドが `fmt.Printf` のようにフォーマット文字列とそれに続く引数を取るものと誤って解釈されていました。しかし、実際には `in.Error` メソッドはフォーマット文字列を解釈せず、渡された引数をそのまま連結してエラーメッセージを生成し、さらに自動的に改行を追加する設計になっていました。

この誤った使用方法により、エラーメッセージが意図しない形式で出力されていました。具体的には、フォーマット指定子（例: `%q`）がそのまま文字列として表示され、さらに `in.Error` メソッドが追加する改行と、元のコードで指定されていた `\n` が二重に適用される可能性がありました。

このコミットは、この誤用を修正し、`in.Error` メソッドの本来の挙動に合わせてエラーメッセージの記述を調整することで、出力されるエラーメッセージの正確性と一貫性を確保することを目的としています。これにより、ユーザーや開発者がアセンブラのエラーメッセージをより正確に理解できるようになります。

## 前提知識の解説

### Go言語のエラーハンドリングと`fmt.Errorf`

Go言語では、エラーは通常 `error` インターフェースを実装する型として扱われます。エラーを生成する一般的な方法の一つに `fmt.Errorf` 関数があります。これは `fmt.Printf` と同様にフォーマット文字列と引数を受け取り、フォーマットされたエラーメッセージを持つ `error` 型の値を返します。

例: `fmt.Errorf("ファイル %q が見つかりません", filename)`

### `cmd/asm` とその役割

`cmd/asm` はGo言語のツールチェーンに含まれるアセンブラです。Go言語のプログラムは、Goのソースコードから機械語に直接コンパイルされるだけでなく、特定の部分（特にパフォーマンスが重要な部分や、特定のハードウェア機能を利用する部分）でアセンブリ言語を使用することがあります。`cmd/asm` は、これらのアセンブリ言語のソースコード（通常は `.s` 拡張子を持つファイル）をオブジェクトファイルに変換する役割を担っています。

### 字句解析（Lexical Analysis）と`internal/lex`パッケージ

字句解析（Lexical Analysis）は、コンパイラやインタプリタの最初の段階であり、ソースコードを意味のある最小単位である「トークン」の並びに分解するプロセスです。例えば、`MOV R1, R2` というアセンブリ命令は、`MOV`（命令）、`R1`（レジスタ）、`,`（区切り文字）、`R2`（レジスタ）といったトークンに分解されます。

`cmd/asm/internal/lex` パッケージは、`cmd/asm` の中でこの字句解析を担当する部分です。アセンブリソースコードを読み込み、トークンに分割し、その過程で発生する構文エラーなどを検出・報告します。`Input` 型は、この字句解析プロセスへの入力ストリームを管理し、トークンの読み取りやエラー報告を行います。

### マクロ定義（Macro Definition）

アセンブリ言語においても、C言語などと同様にマクロが使用されることがあります。マクロは、一連の命令やデータに名前を付け、その名前を使用することで繰り返し記述する手間を省くための機能です。アセンブラは、コンパイルの前にこれらのマクロを定義された内容に展開します。`cmd/asm/internal/lex` パッケージは、マクロの定義を解析し、その展開を処理する機能も持っています。このコミットで修正されたエラーは、このマクロ定義の解析中に発生する可能性のある構文エラー（改行の欠落）に関するものです。

## 技術的詳細

このコミットの核心は、`in.Error` メソッドの正しい使い方にあります。多くのプログラミング言語やライブラリでは、エラー報告関数が `printf` スタイルのフォーマット文字列を最初の引数として受け取り、それに続く引数をそのフォーマット文字列に適用して最終的なメッセージを生成します。しかし、`cmd/asm/internal/lex` の `Input` 型に定義されている `Error` メソッドは、この一般的なパターンとは異なる挙動をしていました。

`in.Error(args ...interface{})` のように可変長引数を受け取るものの、内部的にはこれらの引数を単純に連結し、その後に自動的に改行文字を追加してエラーとして報告します。つまり、最初の引数がフォーマット文字列として特別に扱われることはありません。

元のコード:
`in.Error("missing newline in macro definition for %q\\n", name)`

このコードでは、`"missing newline in macro definition for %q\\n"` という文字列が最初の引数として渡され、`name` 変数の値が2番目の引数として渡されます。`in.Error` メソッドはこれらを連結するため、出力されるエラーメッセージは以下のようになります（`name`が`MY_MACRO`の場合）：

`missing newline in macro definition for %q\n MY_MACRO`

さらに、`in.Error` メソッド自体が末尾に改行を追加するため、実際には二重の改行が発生する可能性がありました。これは、エラーメッセージの可読性を損ない、他のエラーメッセージとの一貫性を失わせる原因となります。

修正後のコード:
`in.Error("missing newline in definition for macro:", name)`

この修正では、フォーマット文字列としての `%q` と余分な `\n` が削除され、メッセージが2つの独立した文字列引数として渡されています。`in.Error` メソッドはこれらを連結し、自動的に改行を追加するため、期待されるエラーメッセージは以下のようになります：

`missing newline in definition for macro: MY_MACRO`

これにより、エラーメッセージはより簡潔で正確になり、`cmd/asm` 内の他のエラー報告と一貫した形式になります。

## コアとなるコードの解説

変更は `src/cmd/asm/internal/lex/input.go` ファイルの `macroDefinition` 関数内で行われています。この関数は、アセンブリコード内のマクロ定義を解析する際に使用されます。

具体的には、`scanner.EOF`（ファイルの終端）に到達したにもかかわらず、マクロ定義の終端を示す改行文字が見つからなかった場合にエラーを報告する行が修正されています。

-   **変更前**:
    ```go
    in.Error("missing newline in macro definition for %q\n", name)
    ```
    ここでは、`"missing newline in macro definition for %q\n"` というフォーマット文字列と、マクロの名前を表す `name` 変数が `in.Error` メソッドに渡されていました。前述の通り、`in.Error` はフォーマット文字列を解釈しないため、`%q` はそのまま出力され、`\n` もリテラルとして扱われた上で、`in.Error` 自身がさらに改行を追加するという問題がありました。

-   **変更後**:
    ```go
    in.Error("missing newline in definition for macro:", name)
    ```
    修正後は、エラーメッセージのプレフィックス `"missing newline in definition for macro:"` とマクロ名 `name` が、それぞれ独立した引数として `in.Error` メソッドに渡されています。これにより、`in.Error` はこれらの文字列を適切に連結し、最後に一度だけ改行を追加して、意図した通りのエラーメッセージを生成します。この変更により、エラーメッセージの正確性と一貫性が向上しました。

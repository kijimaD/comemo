## 変更の背景

Goコンパイラは、コードの最適化と効率的な機械語生成のために、中間表現としてSSA（Static Single Assignment）形式を採用しています。SSA形式では、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。

論理AND (`&&`) と論理OR (`||`) 演算子は、Goを含む多くのプログラミング言語で「短絡評価」のセマンティクスを持ちます。これは、式の評価結果が左側のオペランドだけで確定する場合、右側のオペランドは評価されないというものです。例えば、`A && B` の場合、`A` が `false` であれば `B` は評価されません。`A || B` の場合、`A` が `true` であれば `B` は評価されません。

この短絡評価の挙動は、単なる二項演算としてSSAに変換するだけでは表現できません。右側のオペランドが評価されるかどうかが、左側のオペランドの値に依存するため、条件分岐を伴う制御フローとして表現する必要があります。

このコミットの背景には、GoコンパイラのSSAバックエンドが進化する中で、短絡評価を持つ論理演算子をSSA形式で正確かつ効率的に表現する必要があったという点があります。これにより、これらの演算子を含むコードに対しても、SSAベースの最適化が適用できるようになり、生成される機械語の品質が向上します。

## 前提知識の解説

### 1. Goコンパイラの構造

Goコンパイラ (`cmd/compile`) は、主に以下のフェーズで構成されます。

*   **フロントエンド**: ソースコードの字句解析、構文解析、抽象構文木（AST）の構築、型チェックなどを行います。
*   **ミドルエンド**: ASTを元に、より低レベルの中間表現（例: Go独自のGeneric SSA (GSSA)）に変換し、様々な最適化を適用します。
*   **バックエンド**: 中間表現をターゲットアーキテクチャの機械語に変換します。

このコミットで変更されている `src/cmd/compile/internal/gc/ssa.go` は、ASTからSSA形式への変換を担当する部分であり、`src/cmd/compile/internal/ssa` パッケージはSSA形式そのものと、それに対する最適化ルールを定義しています。

### 2. SSA (Static Single Assignment) 形式

SSA形式は、プログラム中の各変数が一度だけ代入されるように変換された中間表現です。もし同じ変数に複数回代入がある場合、SSAでは新しい「バージョン」の変数が導入されます（例: `x1 = ...`, `x2 = ...`）。

SSAの主要な特徴は以下の通りです。

*   **Phi関数**: 複数の制御フローパスが合流する地点（例: `if-else`文の終わり）で、異なるバージョンの変数を結合するために使用されます。例えば、`if`ブロックで `x1` が、`else`ブロックで `x2` が代入された場合、合流点では `x3 = φ(x1, x2)` のように表現されます。
*   **データフロー解析の容易さ**: 各変数の定義と使用が明確になるため、デッドコード削除、共通部分式除去などの最適化が容易になります。

### 3. 短絡評価 (Short-circuit Evaluation)

短絡評価は、論理演算子 (`&&`, `||`) の特性です。

*   **`A && B`**: `A` が `false` の場合、式全体の結果は `false` と確定するため、`B` は評価されません。
*   **`A || B`**: `A` が `true` の場合、式全体の結果は `true` と確定するため、`B` は評価されません。

この特性は、例えば `if ptr != nil && *ptr > 0` のように、ポインタのデリファレンス前に `nil` チェックを行う場合などに非常に重要です。右側のオペランドが副作用を持つ場合（例: 関数呼び出しを含む場合）、短絡評価はプログラムの挙動に直接影響を与えます。

### 4. `OANDAND` と `OOROR`

GoコンパイラのASTでは、論理AND (`&&`) は `OANDAND`、論理OR (`||`) は `OOROR` という内部ノードタイプで表現されます。これらのノードをSSAに変換する際に、短絡評価のセマンティクスを維持する必要があります。

## 技術的詳細

このコミットの主要な技術的詳細は、`src/cmd/compile/internal/gc/ssa.go` 内の `(s *state) expr(n *Node) *ssa.Value` 関数における `OANDAND` および `OOROR` ノードの処理方法にあります。

短絡評価をSSA形式で表現するために、コンパイラは以下のような制御フロー変換を行います。

### `A && B` のSSA変換

元の式: `A && B`

1.  **一時変数の導入**: 結果を保持するための一時変数（`var`）を導入し、これを `OANDAND` ノード自体に関連付けます。これは、通常の変数（`ONAME`ノード）だけでなく、ASTノードにもSSA変数を関連付けるという珍しいパターンです。
2.  **左オペランドの評価**: まず `A` を評価し、その結果を `el` とします。この `el` が一時変数 `var` の初期値となります。
3.  **条件分岐ブロックの生成**: `el` の値に基づいて条件分岐ブロック (`ssa.BlockIf`) を生成します。
    *   `el` が `true` の場合（`A` が真の場合）、`B` を評価するブロック (`bRight`) へ進みます。
    *   `el` が `false` の場合（`A` が偽の場合）、式全体の結果が `false` と確定するため、`B` を評価せずに結果ブロック (`bResult`) へ直接進みます。このとき、一時変数 `var` の値は `false` のままです。
4.  **右オペランドの評価**: `bRight` ブロックでは `B` を評価し、その結果を `er` とします。この `er` が一時変数 `var` の新しい値となります。
5.  **結果ブロックへの合流**: `bRight` ブロックの評価後、結果ブロック (`bResult`) へ合流します。
6.  **Phi関数の暗黙的な生成**: `bResult` ブロックでは、一時変数 `var` の最終的な値を取得します。このとき、`bResult` には2つの前身ブロック（`b` と `bRight`）から異なる値（`el` または `er`）が流れ込む可能性があるため、SSAのルールに従ってPhi関数が暗黙的に生成され、正しい値が選択されます。

擬似コードで表現すると、`A && B` は以下のように変換されます。

```
var = A
if var { // Aがtrueの場合
    var = B
}
// ここでvarはAがfalseならAの値、AがtrueならBの値を持つ
return var
```

### `A || B` のSSA変換

元の式: `A || B`

同様に、`A || B` も制御フロー変換によって短絡評価を表現します。

1.  **一時変数の導入**: 結果を保持するための一時変数（`var`）を導入し、これを `OOROR` ノード自体に関連付けます。
2.  **左オペランドの評価**: まず `A` を評価し、その結果を `el` とします。この `el` が一時変数 `var` の初期値となります。
3.  **条件分岐ブロックの生成**: `el` の値に基づいて条件分岐ブロック (`ssa.BlockIf`) を生成します。
    *   `el` が `true` の場合（`A` が真の場合）、式全体の結果が `true` と確定するため、`B` を評価せずに結果ブロック (`bResult`) へ直接進みます。このとき、一時変数 `var` の値は `true` のままです。
    *   `el` が `false` の場合（`A` が偽の場合）、`B` を評価するブロック (`bRight`) へ進みます。
4.  **右オペランドの評価**: `bRight` ブロックでは `B` を評価し、その結果を `er` とします。この `er` が一時変数 `var` の新しい値となります。
5.  **結果ブロックへの合流**: `bRight` ブロックの評価後、結果ブロック (`bResult`) へ合流します。
6.  **Phi関数の暗黙的な生成**: `bResult` ブロックでは、一時変数 `var` の最終的な値を取得します。ここでもPhi関数が暗黙的に生成され、正しい値が選択されます。

擬似コードで表現すると、`A || B` は以下のように変換されます。

```
var = A
if !var { // Aがfalseの場合
    var = B
}
// ここでvarはAがtrueならAの値、AがfalseならBの値を持つ
return var
```

### `ConvNop` の最適化

このコミットには、`src/cmd/compile/internal/ssa/gen/AMD64.rules` および `src/cmd/compile/internal/ssa/rewriteAMD64.go` における `ConvNop` の最適化も含まれています。

*   `ConvNop` は、型変換が実際には何も操作を必要としない（no-op）場合に生成されるSSA命令です。例えば、`int32` から `int32` への変換などです。
*   追加されたルール `(ConvNop <t> x) && t == x.Type -> (Copy x)` は、「もし `ConvNop` 命令が、変換元と変換先の型が同じである `x` を変換しようとしている場合、それは単なる `Copy` 命令に置き換えられる」という最適化を示しています。これは、冗長な `ConvNop` 命令を削除し、より効率的なコードを生成するための一般的なSSA最適化の一種です。

### SSAブロックの表示改善

`src/cmd/compile/internal/ssa/print.go` の変更は、SSAブロックのデバッグ出力の改善です。各ブロックのIDに加えて、そのブロックの先行ブロック（`Preds`）も表示されるようになり、SSAグラフの可視性が向上しています。これは、コンパイラ開発者がSSA変換の正確性を検証する際に役立ちます。

## コアとなるコードの変更箇所

### `src/cmd/compile/internal/gc/ssa.go`

```go
case OANDAND, OOROR:
	// To implement OANDAND (and OOROR), we introduce a
	// new temporary variable to hold the result. The
	// variable is associated with the OANDAND node in the
	// s.vars table (normally variables are only
	// associated with ONAME nodes). We convert
	//     A && B
	// to
	//     var = A
	//     if var {
	//         var = B
	//     }
	// Using var in the subsequent block introduces the
	// necessary phi variable.
	el := s.expr(n.Left)
	s.vars[n] = el

	b := s.endBlock()
	b.Kind = ssa.BlockIf
	b.Control = el

	bRight := s.f.NewBlock(ssa.BlockPlain)
	bResult := s.f.NewBlock(ssa.BlockPlain)
	if n.Op == OANDAND {
		addEdge(b, bRight)
		addEdge(b, bResult)
	} else if n.Op == OOROR {
		addEdge(b, bResult)
		addEdge(b, bRight)
	}

	s.startBlock(bRight)
	er := s.expr(n.Right)
	s.vars[n] = er

	b = s.endBlock()
	addEdge(b, bResult)

	s.startBlock(bResult)
	return s.variable(n, n.Type)
```

package main

func and_ssa(arg1, arg2 bool) bool {
	return arg1 && rightCall(arg2)
}

func or_ssa(arg1, arg2 bool) bool {
	return arg1 || rightCall(arg2)
}

var rightCalled bool

func rightCall(v bool) bool {
	rightCalled = true
	return v
	select {} // hack to prevent inlining
	panic("unreached")
}

func testAnd(arg1, arg2, wantRes bool) { testShortCircuit("AND", arg1, arg2, and_ssa, arg1, wantRes) }
func testOr(arg1, arg2, wantRes bool)  { testShortCircuit("OR", arg1, arg2, or_ssa, !arg1, wantRes) }

func testShortCircuit(opName string, arg1, arg2 bool, fn func(bool, bool) bool, wantRightCall, wantRes bool) {
	rightCalled = false
	got := fn(arg1, arg2)
	if rightCalled != wantRightCall {
		println("failed for", arg1, opName, arg2, "; rightCalled=", rightCalled, "want=", wantRightCall)
		failed = true
	}
	if wantRes != got {
		println("failed for", arg1, opName, arg2, "; res=", got, "want=", wantRes)
		failed = true
	}
}

var failed = false

func main() {
	testAnd(false, false, false)
	testAnd(false, true, false)
	testAnd(true, false, false)
	testAnd(true, true, true)

	testOr(false, false, false)
	testOr(false, true, true)
	testOr(true, false, true)
	testOr(true, true, true)

	if failed {
		panic("failed")
	}
}

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の `OANDAND`, `OOROR` 処理

このコードブロックは、ASTノード `n` が `OANDAND` または `OOROR` である場合のSSA変換ロジックを実装しています。

1.  `el := s.expr(n.Left)`: まず、左オペランド `n.Left` をSSA形式に変換し、その結果のSSA値 `el` を取得します。
2.  `s.vars[n] = el`: ここが重要なポイントで、通常は `ONAME` ノード（変数宣言）にのみSSA変数を関連付ける `s.vars` マップに、`OANDAND` または `OOROR` ノード自体 `n` をキーとして `el` を関連付けています。これは、短絡評価の結果を保持するための一時変数として機能します。
3.  `b := s.endBlock()`: 現在のSSAブロックを終了します。
4.  `b.Kind = ssa.BlockIf; b.Control = el`: 新しいブロック `b` を条件分岐ブロック (`ssa.BlockIf`) として設定し、その制御値（条件）を左オペランドの結果 `el` にします。
5.  `bRight := s.f.NewBlock(ssa.BlockPlain); bResult := s.f.NewBlock(ssa.BlockPlain)`: 右オペランドを評価するためのブロック `bRight` と、最終的な結果を合流させるためのブロック `bResult` を作成します。
6.  **条件分岐の制御フロー構築**:
    *   `OANDAND` の場合: `el` が `true` なら `bRight` へ、`false` なら `bResult` へ分岐します。
        *   `addEdge(b, bRight)`: `el` が `true` のパス。
        *   `addEdge(b, bResult)`: `el` が `false` のパス。
    *   `OOROR` の場合: `el` が `true` なら `bResult` へ、`false` なら `bRight` へ分岐します。
        *   `addEdge(b, bResult)`: `el` が `true` のパス。
        *   `addEdge(b, bRight)`: `el` が `false` のパス。
7.  `s.startBlock(bRight)`: `bRight` ブロックの構築を開始します。
8.  `er := s.expr(n.Right)`: 右オペランド `n.Right` をSSA形式に変換し、その結果のSSA値 `er` を取得します。
9.  `s.vars[n] = er`: `bRight` ブロック内では、一時変数（`n` に関連付けられたSSA値）を `er` で更新します。
10. `b = s.endBlock(); addEdge(b, bResult)`: `bRight` ブロックを終了し、`bResult` ブロックへ合流します。
11. `s.startBlock(bResult)`: `bResult` ブロックの構築を開始します。
12. `return s.variable(n, n.Type)`: `bResult` ブロックで、`n` に関連付けられたSSA値（一時変数）の最終的な値を取得して返します。この `s.variable(n, n.Type)` の呼び出しが、異なるパスから流れてくる値を結合するためのPhi関数を暗黙的に生成する役割を果たします。

この一連の処理により、短絡評価のセマンティクスがSSAの制御フローとPhi関数によって正確に表現されます。

### `src/cmd/compile/internal/gc/testdata/short_ssa.go` のテストケース

このファイルは、短絡評価がSSA変換後も正しく機能するかを検証するためのテストコードです。

*   `and_ssa` と `or_ssa` 関数は、それぞれ `&&` と `||` 演算子を使用し、右オペランドとして `rightCall` 関数を呼び出しています。
*   `rightCall` 関数は、グローバル変数 `rightCalled` を `true` に設定する副作用を持ちます。これにより、`rightCall` が実際に呼び出されたかどうかを検出できます。`select {}` はインライン化を防ぐためのハックです。
*   `testAnd` と `testOr` 関数は、`and_ssa` および `or_ssa` を様々な引数で呼び出し、`rightCalled` の値と最終的な結果が期待通りであるかを検証します。
    *   `testAnd` の場合、`arg1` が `false` なら `rightCall` は呼び出されないはずです。
    *   `testOr` の場合、`arg1` が `true` なら `rightCall` は呼び出されないはずです。
*   `main` 関数は、これらのテストケースを網羅的に実行し、一つでも失敗すれば `panic` を発生させます。

このテストは、SSA変換が短絡評価の副作用（右オペランドの関数呼び出しの有無）を正確に維持していることを保証するために不可欠です。

# [インデックス 23136] ファイルの概要

このコミットは、Goランタイムのベンチマークテスト `BenchmarkPingPongHog` における競合状態（race condition）を修正するものです。具体的には、ベンチマークのマスターゴルーチンが子ゴルーチンの処理完了前に終了してしまい、その結果、ベンチマークハーネスが `b.N` を更新する際に、子ゴルーチンがまだ `b.N` にアクセスしているという読み書きの競合が発生していました。この修正は、`done` チャネルを用いた同期メカニズムを追加することで、すべてのゴルーチンが安全に終了するのを待つように変更し、競合状態を解消します。

## 元コミット内容

Goランタイムの `BenchmarkPingPongHog` ベンチマークにおいて発生していた競合状態を修正します。この問題は、マスターゴルーチンが子ゴルーチンが `b.N` を使用した最終ループ（ループを終了させるための条件判定）を完了する前にリターンしてしまい、その後にベンチマークハーネスが `b.N` を更新する際に、子ゴルーチンがまだ `b.N` を読み取っていることで、`b.N` に対する読み書きの競合が発生するというものでした。

## 変更の背景

Goのベンチマークテストは、`go test -bench=.` コマンドで実行され、コードのパフォーマンスを測定するために使用されます。`BenchmarkPingPongHog` は、複数のゴルーチンとチャネルを用いた通信のオーバーヘッドを測定するベンチマークの一つです。

このベンチマークでは、複数のゴルーチンがチャネルを介してデータをやり取りする「ピンポン」のような処理を繰り返します。ベンチマークの実行回数は `b.N` という変数によって制御されます。`b.N` はベンチマークの実行中に動的に調整されることがあり、より正確な測定のために、ベンチマークハーネス（`testing` パッケージの内部ロジック）が `b.N` の値を増減させることがあります。

問題は、ベンチマークのマスターゴルーチンが、子ゴルーチンが `b.N` を参照する最後のループ条件判定を終える前に、`b.N` の更新処理が走ってしまうことにありました。これにより、子ゴルーチンが古い `b.N` の値を読み取ろうとしている最中に、ベンチマークハーネスが新しい `b.N` の値を書き込むという、典型的なデータ競合（read-write race）が発生していました。このような競合状態は、ベンチマーク結果の不安定性や、最悪の場合にはテストのクラッシュを引き起こす可能性があります。

このコミットは、このような不安定なベンチマークテストを修正し、Goランタイムのテストスイートの信頼性を向上させることを目的としています。

## 前提知識の解説

### Goのベンチマークテスト (`testing` パッケージ)

Goには、標準ライブラリの `testing` パッケージにベンチマーク機能が組み込まれています。ベンチマーク関数は `BenchmarkXxx(*testing.B)` というシグネチャを持ち、`go test -bench=.` コマンドで実行されます。

*   **`*testing.B`**: ベンチマーク関数に渡される構造体で、ベンチマークの制御と測定のためのメソッドを提供します。
*   **`b.N`**: ベンチマーク関数が実行されるループの回数を表す整数です。`testing` パッケージは、ベンチマークの実行時間を考慮して `b.N` の値を自動的に調整し、統計的に有意な結果が得られるようにします。例えば、処理が非常に速い場合は `b.N` が大きく設定され、遅い場合は小さく設定されます。
*   **`b.ResetTimer()`**: ベンチマークの計測を開始します。これ以前の処理時間は計測に含まれません。
*   **`b.StopTimer()`**: ベンチマークの計測を一時停止します。
*   **`b.StartTimer()`**: `b.StopTimer()` で停止した計測を再開します。

### ゴルーチン (Goroutines)

ゴルーチンはGoにおける軽量な並行実行単位です。`go` キーワードの後に通常の関数呼び出しを記述することで、その関数は新しいゴルーチンとして実行されます。ゴルーチンはOSのスレッドよりもはるかに軽量であり、数千、数万のゴルーチンを同時に実行することが可能です。

### チャネル (Channels)

チャネルは、ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは型付けされており、特定の型の値のみを送受信できます。チャネルはデフォルトで同期的な通信を提供し、送信側は受信側が値を受け取るまでブロックされ、受信側は送信側が値を送るまでブロックされます。これにより、明示的なロックなしに安全な並行処理を実現できます。

*   `make(chan Type)`: バッファなしチャネルを作成します。
*   `make(chan Type, capacity)`: バッファ付きチャネルを作成します。
*   `ch <- value`: `value` をチャネル `ch` に送信します。
*   `value := <-ch`: チャネル `ch` から値を受信します。

### 競合状態 (Race Condition)

競合状態とは、複数の並行プロセス（この場合はゴルーチン）が共有リソース（この場合は `b.N` 変数）にアクセスする際に、そのアクセス順序によって結果が非決定的に変わってしまう状態を指します。特に、少なくとも一つのアクセスが書き込みである場合に問題となります。Goでは、`go run -race` コマンドを使用することで、プログラム内の競合状態を検出できます。

## 技術的詳細

`BenchmarkPingPongHog` ベンチマークは、`ping` と `pong` という2つのチャネルを使って、複数のゴルーチン間でデータのやり取りを行います。このベンチマークの構造は以下のようになっています（簡略化）。

```go
func BenchmarkPingPongHog(b *testing.B) {
    ping := make(chan bool)
    pong := make(chan bool)
    stop := make(chan bool)
    done := make(chan bool) // 新しく追加されたチャネル

    // ゴルーチン1 (ping-pongの片側)
    go func() {
        for i := 0; i < b.N; i++ {
            // ... チャネル通信 ...
        }
        close(stop)
        done <- true // 終了通知
    }()

    // ゴルーチン2 (ping-pongのもう片側)
    go func() {
        for i := 0; i < b.N; i++ {
            // ... チャネル通信 ...
        }
        done <- true // 終了通知
    }()

    b.ResetTimer()
    // ... ベンチマーク開始 ...
    <-stop // ピンポン処理の終了を待つ
    b.StopTimer()

    // 以前はここで <-done が1回だけだった
    // 修正後: すべてのゴルーチンの終了を待つ
    <-done
    <-done
    <-done // 3つのゴルーチン（マスター含む）の終了を待つ
}
```

問題は、`b.N` をループ条件に持つ子ゴルーチンがまだ `i < b.N` の評価を行っている最中に、マスターゴルーチンが `b.StopTimer()` を呼び出し、その後ベンチマークハーネスが `b.N` の値を更新してしまう可能性があったことです。

具体的には、`BenchmarkPingPongHog` 関数内で起動されるゴルーチンは、`for i := 0; i < b.N; i++` のループ内で `b.N` を参照します。ベンチマークハーネスは、`b.StopTimer()` が呼ばれた後、次のベンチマーク実行のために `b.N` の値を調整することがあります。もし子ゴルーチンがループの最終イテレーションで `i < b.N` を評価しようとしている瞬間に `b.N` が更新されると、競合状態が発生します。

この修正では、`done` という新しいチャネルを導入し、各子ゴルーチンがループを完了した後にこのチャネルに値を送信するように変更しました。そして、マスターゴルーチンは、`b.StopTimer()` の後に、起動したすべてのゴルーチンからの終了通知を `<-done` で受け取るまで待機するようにしました。

元のコードでは、`<-done` が1回しかありませんでしたが、実際にはピンポン処理を行う2つのゴルーチンと、`close(stop)` を行うゴルーチン（これは `done <- true` を送信する）の合計3つのゴルーチンが `done` チャネルに送信する可能性があります。したがって、3回の `<-done` 受信を行うことで、すべての関連するゴルーチンが `b.N` へのアクセスを完全に終えてから、ベンチマークハーネスが `b.N` を更新するフェーズに進むことを保証します。これにより、`b.N` に対する読み書きの競合が解消されます。

## コアとなるコードの解説

このコミットの主要な変更点は、`src/runtime/proc_test.go` ファイル内の `BenchmarkPingPongHog` 関数にあります。

1.  **`done <- true` の追加**:
    *   ピンポン処理を行う2つのゴルーチンのそれぞれの `for` ループが終了した後、`done <- true` が追加されました。これは、そのゴルーチンが `b.N` を参照する処理を完了し、安全に終了したことを `done` チャネルを通じて通知するためのものです。
    *   `close(stop)` を行うゴルーチンにも `done <- true` が追加されています。これにより、このゴルーチンも自身の処理完了を通知します。

2.  **`<-done` の複数回呼び出し**:
    *   以前は `<-done` が1回だけでしたが、修正後は `<-done` が3回連続で呼び出されています。
    *   これは、`BenchmarkPingPongHog` 関数内で起動される3つのゴルーチン（ピンポン処理の2つのゴルーチンと、`close(stop)` を行うゴルーチン）がすべて `done` チャネルに値を送信するようになったため、マスターゴルーチンがこれらすべてのゴルーチンの完了を待つ必要があることを意味します。
    *   `<-done` はチャネルからの受信操作であり、チャネルに値が送信されるまでブロックされます。これにより、マスターゴルーチンは、すべての関連する子ゴルーチンが `b.N` へのアクセスを終え、安全に終了したことを確認してから、ベンチマークの次のフェーズ（`b.N` の更新など）に進むことができます。

これらの変更により、`b.N` に対する競合状態が効果的に解消され、`BenchmarkPingPongHog` の実行がより安定し、信頼性の高いものになりました。

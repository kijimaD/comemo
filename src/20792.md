## 変更の背景

このコミットは、Go言語のリンカー (`cmd/ld`) が実行可能ファイルを生成する際に、シンボル名（特にGoの内部表現で特殊な文字を含むもの）をMach-O形式で出力する過程で発生していたオフバイワンエラーを修正することを目的としています。

具体的には、Goの内部シンボル名には、メソッド名などで `.` (ドット) の代わりに `·` (中点、Unicode U+00B7) が使用されることがあります（例: `Type·Method`）。この `·` 文字はUTF-8で2バイト（`0xc2 0xb7`）でエンコードされます。リンカーがこれらのシンボル名を処理し、最終的なバイナリに書き出す際に、文字列の終端処理に関するオフバイワンエラーが発生し、シンボル名が正しく出力されない、あるいは破損するという問題がありました。

コミットメッセージによると、この問題は `nm -n gofmt` コマンドの出力で確認されており、シンボル名が破損している状態でした。`nm` コマンドは実行可能ファイルやオブジェクトファイル内のシンボルリストを表示するツールであり、破損したシンボル名はデバッグや解析の妨げとなります。

この修正は、GoプロジェクトのIssue #8906に対応するものです。

## 前提知識の解説

*   **Goリンカー (`cmd/ld`)**:
    Go言語は、独自のツールチェインを持っています。その中核をなすのが、コンパイラ (`cmd/compile`) とリンカー (`cmd/ld`) です。Goのリンカーは、Goのソースコードから生成されたオブジェクトファイルや、他のライブラリを結合して、最終的な実行可能ファイルを生成する役割を担います。多くの言語がシステムに依存するリンカー（例: `ld` や `link.exe`）を使用するのに対し、Goは独自のリンカーをGo言語自体で実装しています（ただし、このコミット時点の2014年には、一部C言語で書かれたコンポーネント、例えば `src/cmd/ld/macho.c` が存在していたことが示唆されます）。これにより、Goは優れたクロスコンパイル能力と、依存関係の少ない静的リンクされたバイナリを生成できます。

*   **Mach-O (Mach Object) フォーマット**:
    Mach-Oは、macOS、iOS、watchOS、tvOSといったAppleのオペレーティングシステムで使用される実行可能ファイル、共有ライブラリ、オブジェクトファイル、コアダンプなどの標準バイナリフォーマットです。Mach-Oファイルは、ヘッダ、ロードコマンド、セグメント、セクションといった構造で構成され、プログラムのコード、データ、シンボル情報などが格納されます。Goリンカーは、macOS向けにビルドする際に、このMach-Oフォーマットに準拠したバイナリを生成する必要があります。

*   **シンボル名**:
    プログラムにおけるシンボルとは、関数、変数、型などの識別子のことです。コンパイラはソースコードを機械語に変換する際に、これらのシンボルを内部的に管理します。リンカーは、複数のオブジェクトファイルやライブラリから参照されるシンボルを解決し、最終的な実行可能ファイル内でそれらが正しいメモリ位置にマッピングされるようにします。シンボル名は、デバッグやプロファイリング、逆アセンブルなどの際に、プログラムの構造を理解するために非常に重要です。

*   **Goの内部シンボル名と `·` (中点)**:
    Go言語のコンパイラやリンカーは、内部的にシンボル名を表現する際に、特定の規則に従います。特に、メソッドのシンボル名では、`.` (ドット) の代わりに `·` (中点、Unicode U+00B7) を使用することがあります。例えば、`package.Type.Method` のようなメソッドは、内部的には `package.Type·Method` のように表現されることがあります。この `·` 文字はUTF-8エンコーディングでは2バイト（`0xc2 0xb7`）で表現されます。この特殊な文字の正確な処理が、リンカーにとって重要となります。

*   **オフバイワンエラー (Off-by-one error)**:
    オフバイワンエラーは、プログラミングにおいて非常に一般的な論理エラーの一種です。これは、ループが意図した回数よりも1回多く実行されたり、1回少なく実行されたりすることで発生します。配列のインデックス、文字列の長さ、範囲の計算など、境界条件を扱う際に頻繁に見られます。C言語のようなポインタを直接操作する言語では、文字列のヌル終端文字 (`\0`) の処理や、ポインタのインクリメントのタイミングによって、このエラーが発生しやすい傾向があります。

*   **`nm` コマンド**:
    `nm` はUnix系システムで利用されるコマンドラインユーティリティで、オブジェクトファイル、アーカイブファイル、または実行可能ファイル内のシンボルテーブルを表示します。シンボル名、その値（アドレス）、型（関数、変数など）、および定義されているセクションなどの情報を提供します。`-n` オプションは、シンボルをそのアドレス順にソートして表示するために使用されます。このコマンドの出力が破損しているということは、リンカーがシンボル情報を正しくバイナリに書き込めていないことを示します。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/ld/macho.c` ファイル内の `machosymtab` 関数における文字列処理のループの修正にあります。この関数は、Mach-O形式のシンボルテーブルを構築する際に、Goの内部シンボル名を処理する役割を担っていました。

元のコードでは、シンボル名 `s->extname` に `·` (中点) 文字が含まれている場合、その文字列を走査するために `while (*p++ != '\0')` という形式のループが使用されていました。

```c
// 変更前
p = s->extname;
while (*p++ != '\0') {
    // ... 文字列処理ロジック ...
}
```

この `while` ループの条件 `*p++ != '\0'` は、以下のように動作します。
1.  現在のポインタ `p` が指す文字 (`*p`) を評価します。
2.  その文字がヌル終端文字 (`\0`) でない場合、ループ本体を実行します。
3.  ループ本体の実行後、または条件評価の直後に、ポインタ `p` をインクリメント (`p++`) します。

問題は、文字列の終端に到達し、`*p` が `\0` となった場合です。この時、条件 `*p != '\0'` は `false` となり、ループは終了します。しかし、`p++` は条件評価の後に実行されるため、`p` はヌル終端文字の場所からさらに1バイト進んでしまいます。

Goの内部シンボル名で使われる `·` 文字はUTF-8で2バイト（`0xc2 0xb7`）でエンコードされます。この2バイト文字の処理中に、ループの終端でポインタが意図せず1バイト余分に進んでしまうことで、シンボル名の出力がずれたり、破損したりするオフバイワンエラーが発生していたと考えられます。特に、`·` を `.` に置換するロジックの後に `p++` が行われる箇所があり、これがさらに問題を複雑にしていた可能性があります。

修正では、この `while` ループが `for` ループに置き換えられました。

```c
// 変更後
for(p = s->extname; *p; p++) {
    // ... 文字列処理ロジック ...
}
```

この `for` ループの条件 `*p` は、以下のように動作します。
1.  現在のポインタ `p` が指す文字 (`*p`) を評価します。
2.  その文字がヌル終端文字 (`\0`) でない場合（C言語では非ゼロ値が真と評価される）、ループ本体を実行します。
3.  ループ本体の実行後、ポインタ `p` をインクリメント (`p++`) します。

この `for` ループでは、`*p` が `\0` になった時点で条件が `false` となり、ループ本体は実行されず、`p++` も実行されません。これにより、ポインタ `p` が文字列のヌル終端文字の場所で正確に停止し、文字列の境界を越えて進むことがなくなりました。結果として、シンボル名の出力におけるオフバイワンエラーが解消され、破損したシンボル名が修正されました。

`if((uchar)*p == 0xc2 && (uchar)*(p+1) == 0xb7)` の条件で `·` 文字を検出し、`.` に置換するロジック自体は変更されていません。問題は、その文字を検出する前の文字列走査のループ制御にあったのです。

## コアとなるコードの解説

*   **変更前 (`while` ループ)**:
    ```c
    p = s->extname;
    while (*p++ != '\0') {
        // ...
    }
    ```
    この `while` ループは、ポインタ `p` が指す現在の文字を評価し、その後に `p` をインクリメントします。文字列の終端であるヌル終端文字 (`\0`) に到達した場合、条件 `*p != '\0'` は偽となりループは終了しますが、その前に `p` は既にインクリメントされています。これにより、`p` が文字列の有効な範囲を1バイト超えてしまう可能性がありました。特に、`·` のような2バイト文字の処理と組み合わさることで、シンボル名の出力がずれる原因となっていました。

*   **変更後 (`for` ループ)**:
    ```c
    for(p = s->extname; *p; p++) {
        // ...
    }
    ```
    この `for` ループは、初期化 (`p = s->extname;`)、条件 (`*p;`)、およびループごとの処理 (`p++;`) を明確に分離しています。条件 `*p` は、`p` が指す文字がヌル終端文字 (`\0`) でない限り真となります。`*p` が `\0` になった時点で条件は偽となり、ループは直ちに終了します。この際、`p++` は実行されないため、ポインタ `p` は常に文字列の有効な範囲内、またはヌル終端文字の正確な位置で停止します。これにより、オフバイワンエラーが解消され、シンボル名の正確な処理が保証されるようになりました。

この変更は、一見すると小さなループ構造の変更ですが、文字列の終端処理におけるポインタの挙動を正確に制御することで、リンカーが出力するシンボル名の整合性を確保するという重要な役割を果たしています。

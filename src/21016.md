# [インデックス 21016] ファイルの概要

このコミットは、Go言語のコンパイラツールチェーンの一部である`9g`（PowerPC 64-bitアーキテクチャ向けのGoコンパイラ）における重要なバグ修正と改善に関するものです。具体的には、アドレスの幅（データサイズ）計算の不正確さを修正し、これにより`MOV*`命令（データ移動命令）に対する幅チェックを有効にすることを目的としています。この修正により、コンパイラの最適化器がより正確な型情報に基づいて動作し、潜在的なバグや非効率性を防ぐことができます。

## 変更の背景

この変更の背景には、`9g`コンパイラの`naddr`関数における既存の不具合がありました。`naddr`関数は、プログラム内のアドレス（変数、定数、メモリ位置など）を表現する際に、そのアドレスが指すデータの「幅」（バイト単位のサイズ）を正確に計算し、`a->width`フィールドに設定する役割を担っています。しかし、いくつかのケースでこの`a->width`への代入が欠落しており、その結果、コンパイラの最適化器が不正確な幅情報を受け取っていました。

不正確な幅情報は、最適化器が誤った仮定に基づいてコードを最適化する原因となり、結果として不正なコード生成やランタイムエラーにつながる可能性がありました。特に、`MOV*`命令（データをある場所から別の場所に移動させる命令）のような、データの幅に厳密な制約がある操作においては、この問題が顕著でした。

この問題を解決し、コンパイラの堅牢性を高めるために、`naddr`関数における`a->width`の欠落している代入を追加し、その結果として、これまで無効化されていた`gins`関数内の`MOV*`命令に対する幅チェックを有効にすることが可能になりました。

## 前提知識の解説

*   **`9g`**: Go言語のコンパイラツールチェーンの一部で、具体的にはPlan 9オペレーティングシステムおよびPowerPC 64-bitアーキテクチャ向けのGoコンパイラを指します。Go言語のコンパイラは、ターゲットアーキテクチャごとに`gc`（汎用）、`6g`（x86-64）、`8g`（x86）、`5g`（ARM）、`9g`（PowerPC）などの名前で呼ばれていました。
*   **`naddr`関数**: コンパイラのバックエンドにおける重要な関数の一つで、抽象構文木（AST）のノードを、アセンブリコード生成に適したアドレス表現（`Addr`構造体）に変換する役割を担います。この変換プロセス中に、データの型やサイズ（幅）などの情報が`Addr`構造体に格納されます。
*   **`a->width`**: `Addr`構造体（`a`）のメンバーで、そのアドレスが参照するデータのバイト単位の幅（サイズ）を示します。例えば、`int32`型であれば4バイト、`int64`型であれば8バイトといった値が格納されます。この情報は、アセンブリ命令の選択や最適化において非常に重要です。
*   **最適化器 (Optimizer)**: コンパイラのフェーズの一つで、生成される機械語コードの効率（速度、サイズなど）を向上させるために、様々な変換や分析を行います。正確な型情報や幅情報は、最適化器が安全かつ効果的な変換を行う上で不可欠です。
*   **`MOV*`命令**: アセンブリ言語におけるデータ移動命令の総称です。例えば、`MOVB`（バイト移動）、`MOVW`（ワード移動）、`MOVD`（ダブルワード移動）、`MOVQ`（クアッドワード移動）などがあります。これらの命令は、移動するデータの幅が厳密に定義されており、ソースとデスティネーションの幅が一致しない場合や、オーバーフローの可能性がある場合には、コンパイラが警告を発したり、エラーを報告したりする必要があります。
*   **`gins`関数**: `9g`コンパイラにおけるアセンブリ命令生成関数の一つです。`gins`は、高レベルな操作（例えば、変数の代入）を、具体的なアセンブリ命令（`MOV*`など）に変換する際に呼び出されます。この関数内で、生成される命令の妥当性、特にデータの幅に関するチェックが行われます。
*   **`simtype`**: Goコンパイラ内部で使われる、Go言語の型を簡略化された内部表現にマッピングするための配列または関数です。これにより、コンパイラは型の詳細な情報ではなく、その基本的な特性（例えば、ポインタ、整数、浮動小数点数など）に基づいて処理を行うことができます。
*   **`D_REG`, `D_CONST`, `D_OREG`**: `Addr`構造体の`type`フィールドで使われる定数で、アドレスの種類を示します。
    *   `D_REG`: レジスタに格納されている値。
    *   `D_CONST`: 定数値。
    *   `D_OREG`: オフセット付きレジスタ（例: `offset(register)`、メモリ上のアドレス指定）。

## 技術的詳細

このコミットの技術的詳細は、主に`src/cmd/9g/gsubr.c`ファイル内の`naddr`関数と`gins`関数の変更に集約されます。

**`naddr`関数における`a->width`の修正:**
`naddr`関数は、Go言語のソースコード内の様々な表現（変数名、配列の長さ、マップの容量、アドレス演算など）を、アセンブリコード生成に適した`Addr`構造体に変換します。この変換の過程で、`Addr`構造体の`width`フィールドに、そのアドレスが参照するデータの正確なバイト幅を設定する必要があります。

コミット前のコードでは、以下のケースで`a->width`の代入が欠落していました。

*   **`ONAME` (変数名)**: 変数の型に基づいて`a->width`が設定されていませんでした。
*   **`OLEN` (len関数)**: `len`関数の結果（通常は`int`型）の幅が設定されていませんでした。
*   **`OCAP` (cap関数)**: `cap`関数の結果（通常は`int`型）の幅が設定されていませんでした。
*   **`OSPTR` (ポインタ)**: 文字列やスライスの内部ポインタの幅が設定されていませんでした。
*   **`OADDR` (アドレス演算)**: アドレス演算の結果（ポインタ型）の幅が設定されていませんでした。

これらの欠落により、最適化器はこれらのアドレスに関する不正確な幅情報を受け取り、結果として誤った最適化やコード生成につながる可能性がありました。今回の修正では、これらのケースで`naddr`関数が`a->width`に適切な値を（例えば`widthptr`や`widthint`など、ポインタや整数の標準幅）代入するように変更されました。

**`gins`関数における`MOV*`幅チェックの有効化:**
`gins`関数は、アセンブリ命令を生成する際に、ソースオペランドとデスティネーションオペランドの幅が命令のセマンティクスと一致しているかを検証する役割を担っています。特に`MOV*`命令（`MOVB`, `MOVW`, `MOVD`, `MOVQ`など）は、移動するデータの幅が厳密に定義されているため、このチェックは非常に重要です。

コミット前の`gins`関数には、`MOV*`命令に対する幅チェックのコードブロックがコメントアウトされていました。これは、`naddr`関数からの幅情報が不正確であったため、このチェックを有効にすると誤ったエラーが発生する可能性があったためと考えられます。

`naddr`関数での`a->width`の修正が完了したことで、`gins`関数は正確な幅情報を受け取れるようになりました。これにより、コメントアウトされていた幅チェックのコードブロックが有効化されました。このチェックは、ソースオペランドの幅が命令の期待する幅よりも小さい場合（切り捨ての可能性）や、デスティネーションオペランドの幅が命令の期待する幅よりも大きい場合（ゼロ拡張や符号拡張の不一致の可能性）に`fatal`エラーを発生させます。これにより、コンパイラが不正な`MOV*`命令を生成するのを防ぎ、より堅牢なコード生成を実現します。

## コアとなるコードの変更箇所

変更は`src/cmd/9g/gsubr.c`ファイルに集中しています。

1.  **`gins`関数**:
    *   コメントアウトされていた`MOV*`命令の幅チェックブロックが有効化されました。
    *   幅チェックの条件が微修正されました。特に、`t != N && at.width > w` の部分が `t != N && at.type != D_REG && at.width > w` に変更され、デスティネーションがレジスタでない場合にのみ幅チェックを行うようになりました。これは、レジスタは通常、特定の幅に限定されず、より広いデータを保持できるためと考えられます。
    *   `// TODO(minux): enable these.` や `// right now it fails on MOVD $type."".TypeAssertionError(SB) [width=1], R7 [width=8]` といったコメントが削除されました。

2.  **`naddr`関数**:
    *   **`ONAME`ケース**: `n->type->width`を`a->width`に代入する行が追加されました。
        ```c
        // 変更前
        // a->width = 0;
        // if(n->type != T) {
        //     a->etype = simtype[n->type->etype];
        //     a->width = n->type->width; // この行がifの外にあった
        // }
        // 変更後
        // if(n->type != T)
        //     a->etype = simtype[n->type->etype];
        // a->width = n->type->width; // ifの外に移動し、常に設定されるように
        ```
        実際には、`a->width = n->type->width;` の行が`if(n->type != T)`ブロックの外に移動し、常に`n->type->width`が設定されるようになりました。
    *   **`OLEN`ケース**: `a->width = widthint;` が追加されました。
    *   **`OSPTR`ケース**: `a->etype = simtype[tptr];` が追加され、`a->width = widthptr;` が追加されました。
    *   **`OCAP`ケース**: `a->width = widthint;` が追加されました。
    *   **`OADDR`ケース**: `a->width = widthptr;` が追加され、`break;` が追加されました。

## コアとなるコードの解説

*   **`gins`関数における幅チェックの有効化**:
    この変更は、コンパイラの型安全性と堅牢性を大幅に向上させます。以前は、`naddr`からの不正確な幅情報のために、`MOV*`命令の重要な幅チェックが無効化されていました。これにより、コンパイラが誤った幅のデータ移動命令を生成し、ランタイムエラーや未定義の動作を引き起こす可能性がありました。チェックを有効にすることで、コンパイラは命令生成時にソースとデスティネーションの幅の不一致を検出し、早期にエラーを報告できるようになります。`at.type != D_REG`の条件追加は、レジスタが柔軟な幅を持つことを考慮したもので、不必要なエラーを避けるための調整です。

*   **`naddr`関数における`a->width`の代入追加**:
    `naddr`関数は、Go言語のセマンティクスをアセンブリレベルの表現に変換する際の「真実の情報源」の一つです。`ONAME`、`OLEN`、`OCAP`、`OSPTR`、`OADDR`といった様々な種類のノードに対して、そのノードが表すデータの正確な幅を`a->width`に設定することは極めて重要です。
    *   `ONAME`の場合、変数の型からその幅を正確に取得し、`a->width`に設定することで、最適化器や後続のアセンブリ生成フェーズがその変数を正しく扱えるようになります。
    *   `OLEN`や`OCAP`は、スライスやマップの長さ・容量を返す組み込み関数であり、その結果は通常`int`型です。したがって、`widthint`（システムの`int`型の幅）を`a->width`に設定することで、これらの値が正しく扱われることを保証します。
    *   `OSPTR`や`OADDR`はポインタを扱うため、`widthptr`（システムのポインタの幅）を`a->width`に設定することが適切です。
    これらの修正により、`naddr`関数が生成する`Addr`構造体は、常に正確な幅情報を持つようになり、これが`gins`関数での幅チェックを可能にし、コンパイラ全体の正確性と信頼性を向上させます。

*   **`OLEN` (len関数)**: `len`関数の結果（通常は`int`型）の幅が設定されていませんでした。
*   **`OCAP` (cap関数)**: `cap`関数の結果（通常は`int`型）の幅が設定されていませんでした。
*   **`OSPTR` (ポインタ)**: 文字列やスライスの内部ポインタの幅が設定されていませんでした。
*   **`OADDR` (アドレス演算)**: アドレス演算の結果（ポインタ型）の幅が設定されていませんでした。

これらの欠落により、最適化器はこれらのアドレスに関する不正確な幅情報を受け取り、結果として誤った最適化やコード生成につながる可能性がありました。今回の修正では、これらのケースで`naddr`関数が`a->width`に適切な値を（例えば`widthptr`や`widthint`など、ポインタや整数の標準幅）代入するように変更されました。

**`gins`関数における`MOV*`幅チェックの有効化:**
`gins`関数は、アセンブリ命令を生成する際に、ソースオペランドとデスティネーションオペランドの幅が命令のセマンティクスと一致しているかを検証する役割を担っています。特に`MOV*`命令（`MOVB`, `MOVW`, `MOVD`, `MOVQ`など）は、移動するデータの幅が厳密に定義されているため、このチェックは非常に重要です。

コミット前の`gins`関数には、`MOV*`命令に対する幅チェックのコードブロックがコメントアウトされていました。これは、`naddr`関数からの幅情報が不正確であったため、このチェックを有効にすると誤ったエラーが発生する可能性があったためと考えられます。

`naddr`関数での`a->width`の修正が完了したことで、`gins`関数は正確な幅情報を受け取れるようになりました。これにより、コメントアウトされていた幅チェックのコードブロックが有効化されました。このチェックは、ソースオペランドの幅が命令の期待する幅よりも小さい場合（切り捨ての可能性）や、デスティネーションオペランドの幅が命令の期待する幅よりも大きい場合（ゼロ拡張や符号拡張の不一致の可能性）に`fatal`エラーを発生させます。これにより、コンパイラが不正な`MOV*`命令を生成するのを防ぎ、より堅牢なコード生成を実現します。

## コアとなるコードの変更箇所

変更は`src/cmd/9g/gsubr.c`ファイルに集中しています。

1.  **`gins`関数**:
    *   コメントアウトされていた`MOV*`命令の幅チェックブロックが有効化されました。
    *   幅チェックの条件が微修正されました。特に、`t != N && at.width > w` の部分が `t != N && at.type != D_REG && at.width > w` に変更され、デスティネーションがレジスタでない場合にのみ幅チェックを行うようになりました。これは、レジスタは通常、特定の幅に限定されず、より広いデータを保持できるためと考えられます。
    *   `// TODO(minux): enable these.` や `// right now it fails on MOVD $type."".TypeAssertionError(SB) [width=1], R7 [width=8]` といったコメントが削除されました。

2.  **`naddr`関数**:
    *   **`ONAME`ケース**: `n->type->width`を`a->width`に代入する行が追加されました。
        ```c
        // 変更前
        // a->width = 0;
        // if(n->type != T) {
        //     a->etype = simtype[n->type->etype];
        //     a->width = n->type->width; // この行がifの外にあった
        // }
        // 変更後
        // if(n->type != T)
        //     a->etype = simtype[n->type->etype];
        // a->width = n->type->width; // ifの外に移動し、常に設定されるように
        ```
        実際には、`a->width = n->type->width;` の行が`if(n->type != T)`ブロックの外に移動し、常に`n->type->width`が設定されるようになりました。
    *   **`OLEN`ケース**: `a->width = widthint;` が追加されました。
    *   **`OSPTR`ケース**: `a->etype = simtype[tptr];` が追加され、`a->width = widthptr;` が追加されました。
    *   **`OCAP`ケース**: `a->width = widthint;` が追加されました。
    *   **`OADDR`ケース**: `a->width = widthptr;` が追加され、`break;` が追加されました。

## コアとなるコードの解説

*   **`gins`関数における幅チェックの有効化**:
    この変更は、コンパイラの型安全性と堅牢性を大幅に向上させます。以前は、`naddr`からの不正確な幅情報のために、`MOV*`命令の重要な幅チェックが無効化されていました。これにより、コンパイラが誤った幅のデータ移動命令を生成し、ランタイムエラーや未定義の動作を引き起こす可能性がありました。チェックを有効にすることで、コンパイラは命令生成時にソースとデスティネーションの幅の不一致を検出し、早期にエラーを報告できるようになります。`at.type != D_REG`の条件追加は、レジスタが柔軟な幅を持つことを考慮したもので、不必要なエラーを避けるための調整です。

*   **`naddr`関数における`a->width`の代入追加**:
    `naddr`関数は、Go言語のセマンティクスをアセンブリレベルの表現に変換する際の「真実の情報源」の一つです。`ONAME`、`OLEN`、`OCAP`、`OSPTR`、`OADDR`といった様々な種類のノードに対して、そのノードが表すデータの正確な幅を`a->width`に設定することは極めて重要です。
    *   `ONAME`の場合、変数の型からその幅を正確に取得し、`a->width`に設定することで、最適化器や後続のアセンブリ生成フェーズがその変数を正しく扱えるようになります。
    *   `OLEN`や`OCAP`は、スライスやマップの長さ・容量を返す組み込み関数であり、その結果は通常`int`型です。したがって、`widthint`（システムの`int`型の幅）を`a->width`に設定することで、これらの値が正しく扱われることを保証します。
    *   `OSPTR`や`OADDR`はポインタを扱うため、`widthptr`（システムのポインタの幅）を`a->width`に設定することが適切です。
    これらの修正により、`naddr`関数が生成する`Addr`構造体は、常に正確な幅情報を持つようになり、これが`gins`関数での幅チェックを可能にし、コンパイラ全体の正確性と信頼性を向上させます。

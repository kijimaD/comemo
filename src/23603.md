## 変更の背景

GoコンパイラのSSAバックエンドは、プログラムの最適化と機械語への変換を行う上で非常に重要な役割を担っています。このコミット以前は、値（`Value`）に対する最適化やローワーリングのルールは存在していましたが、制御フローブロック（`Block`）に対するルールベースの書き換えは限定的でした。

コンパイラ最適化において、条件分岐（`if`文など）やループといった制御フローの構造を効率的に処理することは、生成される機械語の品質に直結します。例えば、`if true { ... }` のような常に真となる条件分岐は、コンパイル時にその条件判定を削除し、常に`then`ブロックへジャンプするように最適化できます。このような最適化を手動でコードに記述すると、複雑になりがちで、新しいアーキテクチャのサポートや最適化ルールの追加が困難になります。

このコミットの背景には、以下のような課題と目的がありました。

1.  **最適化の表現力向上**: 制御フローブロックに対するより強力で柔軟な最適化を可能にする。
2.  **コードの簡素化と保守性向上**: 手動で記述されていたブロック関連の最適化ロジック（例: `deadcode.go`内の定数畳み込み）を、宣言的なルールベースのシステムに移行することで、コードの複雑性を軽減し、保守性を高める。
3.  **アーキテクチャ固有のローワーリングの改善**: 特定のアーキテクチャ（例: AMD64）において、条件コード（フラグレジスタ）の扱いを含むブロックのローワーリングを、より効率的かつ体系的に行うための基盤を構築する。
4.  **拡張性の確保**: 将来的に新しい最適化やアーキテクチャサポートを追加する際に、既存のコードを大幅に変更することなく、ルールを追加するだけで対応できるようにする。

これらの目的を達成するために、値の書き換えと同様に、ブロックに対してもルールベースの書き換えシステムを導入することが決定されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

### 1. コンパイラのSSA (Static Single Assignment) 形式

SSAは、コンパイラの中間表現（IR）の一種で、各変数が一度だけ代入されるようにする特性を持ちます。これにより、データフロー解析や最適化が容易になります。Goコンパイラのバックエンドは、ソースコードをSSA形式に変換し、その上で様々な最適化を適用します。

*   **Value**: SSA形式における基本的な計算単位です。オペレーション（`Op`）、引数（`Args`）、型（`Type`）、補助情報（`Aux`）などから構成されます。例えば、`OpAdd`は加算を表す`Value`です。
*   **Block**: 制御フローグラフ（CFG）の基本的な構成要素で、一連の`Value`（命令）を含み、単一のエントリポイントと単一のイグジットポイントを持ちます。`Block`は、次の`Block`への遷移方法（条件分岐、無条件ジャンプなど）を決定する制御`Value`（`Control`）を持ちます。

### 2. コンパイラ最適化とローワーリング

*   **最適化 (Optimization)**: プログラムの実行速度やメモリ使用量を改善するために、中間表現を変換するプロセスです。定数畳み込み、デッドコード削除、共通部分式除去などが含まれます。
*   **ローワーリング (Lowering)**: 高レベルの中間表現を、より低レベルで機械語に近い中間表現に変換するプロセスです。最終的に、特定のCPUアーキテクチャの命令セットにマッピングできる形に変換されます。

### 3. ルールベースの書き換え (Rule-based Rewriting)

コンパイラ最適化の手法の一つで、特定のパターン（左辺）に一致する中間表現を、より最適化された別のパターン（右辺）に置き換えるルールを定義します。これにより、最適化ロジックを宣言的に記述でき、コードの可読性と保守性が向上します。

*   **`rulegen`**: Goコンパイラ内で使用されるツールで、`.rules`ファイルに記述された書き換えルールをGoのソースコード（`generic.go`, `lowerAmd64.go`など）に自動生成します。これにより、手動で`switch`文や`if`文を記述する手間が省け、ルールの追加・変更が容易になります。

### 4. 制御フローグラフ (Control Flow Graph, CFG)

プログラムの実行パスを表現するグラフ構造です。ノードは`Block`（基本ブロック）を表し、エッジは`Block`間の可能な遷移を表します。コンパイラはCFG上でデータフロー解析や最適化を行います。

### 5. AMD64アーキテクチャの条件コード

AMD64（x86-64）アーキテクチャでは、比較命令（`CMP`）や算術演算命令の結果に応じて、CPUのフラグレジスタ（`EFLAGS`レジスタ）内の特定のビット（条件コード）が設定されます。これらの条件コードは、その後の条件分岐命令（`Jcc`命令、例: `JL` (Jump if Less), `JNE` (Jump if Not Equal)）によって利用され、プログラムの実行フローを制御します。

*   `SETL`, `SETNE`, `SETB`など: 特定の条件コードに基づいてバイト値を設定する命令（例: `SETL`は「Less」の場合に1、そうでなければ0をセット）。
*   `InvertFlags`: フラグレジスタの解釈を反転させる概念的な操作。例えば、`CMPQ a b`の結果が`SETL`（a < b）である場合、`InvertFlags`を適用すると`SETG`（a > b）に相当する。これは、`CMPQ b a`と同じ効果を持つ。

## 技術的詳細

このコミットの核となる変更は、GoコンパイラのSSAバックエンドが、`Value`だけでなく`Block`に対してもルールベースの書き換えを適用できるように拡張された点です。

### 1. `BlockKind`の拡張とアーキテクチャ固有のブロック

*   `src/cmd/compile/internal/ssa/block.go`:
    *   `BlockKind`の型が`int8`から`int32`に変更され、より多くの種類のブロックを表現できるようになりました。
    *   `blockGenericBase`, `blockAMD64Base`, `block386Base`といったアーキテクチャ固有のベース値が導入され、各アーキテクチャが独自の`BlockKind`の範囲を持つことができるようになりました。これにより、アーキテクチャに特化した制御フローの特性をSSA IRで表現できるようになります。
    *   `BlockEQ`, `BlockNE`, `BlockLT`などのAMD64固有の条件分岐ブロックが`opamd64.go`に移動し、`BlockKind`の定義がより汎用的なものとアーキテクチャ固有のものに分離されました。

### 2. `Config`構造体の変更

*   `src/cmd/compile/internal/ssa/config.go`:
    *   `Config`構造体内の`lower func(*Value) bool`フィールドが、`lowerBlock func(*Block) bool`と`lowerValue func(*Value) bool`の2つのフィールドに分割されました。これは、ブロックと値のローワーリングが異なるルールセットとロジックで処理されることを明確に示しています。
    *   `NewConfig`関数内で、`amd64`および`386`アーキテクチャに対して、それぞれ`lowerBlockAMD64`と`lowerValueAMD64`が設定されるようになりました。

### 3. `deadcode.go`からの手動最適化の削除

*   `src/cmd/compile/internal/ssa/deadcode.go`:
    *   `deadcode`関数内にあった`BlockIf`の定数畳み込み（例: `if true`の削除）ロジックが削除されました。この最適化は、`rulegen/generic.rules`に追加された新しいブロック書き換えルールによって処理されるようになりました。これにより、最適化ロジックが一元化され、`deadcode`の役割が純粋なデッドコード削除に集中できるようになりました。

### 4. `lower.go`と`opt.go`における書き換えの適用

*   `src/cmd/compile/internal/ssa/lower.go`および`src/cmd/compile/internal/ssa/opt.go`:
    *   `lower`関数と`opt`関数が、新しい`applyRewrite`関数を呼び出す際に、`lowerBlock`と`lowerValue`（または`genericBlockRules`と`genericValueRules`）の両方を渡すようになりました。これにより、ローワーリングと最適化のパスで、ブロックと値の両方に対してルールが適用されることが保証されます。

### 5. `rewrite.go`における`applyRewrite`関数の強化

*   `src/cmd/compile/internal/ssa/rewrite.go`:
    *   `applyRewrite`関数が`rb func(*Block) bool`と`rv func(*Value) bool`の2つの引数を受け取るように変更されました。
    *   この関数は、まず各`Block`に対して`rb`（ブロック書き換え関数）を適用し、次に各`Block`内の`Value`に対して`rv`（値書き換え関数）を適用するようになりました。
    *   `Block.Control`が`OpCopy`である場合の処理が追加され、コピー命令の除去がより効率的に行われるようになりました。
    *   パニック発生時のログ出力に、現在処理中の`Block`の情報が含まれるようになり、デバッグが容易になりました。

### 6. `rulegen`ツールの更新と新しいルール

*   `src/cmd/compile/internal/ssa/rulegen/rulegen.go`:
    *   `rulegen`ツール自体が、ブロック書き換えルールと値書き換えルールの両方を処理し、それぞれに対応するGo関数を生成できるように拡張されました。コマンドライン引数もこれに合わせて変更されています。
    *   ルールファイル（`.rules`）内で、`Block`に対するルールを記述するための新しい構文がサポートされました。
*   `src/cmd/compile/internal/ssa/rulegen/generic.rules`:
    *   `BlockIf`の定数畳み込みを行う新しいルールが追加されました。
        *   `(BlockIf (Const [c]) yes no) && c.(bool) -> (BlockPlain nil yes)`: 条件`c`が真の場合、`BlockIf`を`yes`ブロックへの無条件ジャンプ（`BlockPlain`）に変換します。
        *   `(BlockIf (Const [c]) yes no) && !c.(bool) -> (BlockPlain nil no)`: 条件`c`が偽の場合、`BlockIf`を`no`ブロックへの無条件ジャンプに変換します。
*   `src/cmd/compile/internal/ssa/rulegen/lower_amd64.rules`:
    *   AMD64アーキテクチャ固有のブロックローワーリングルールが多数追加されました。
    *   `BlockIf`と`SETL`, `SETNE`, `SETB`などの`Value`を組み合わせたパターンを、直接`BlockLT`, `BlockNE`, `BlockULT`などのアーキテクチャ固有の条件分岐ブロックに変換するルールが追加されました。これにより、中間表現から機械語への変換がより直接的かつ効率的になります。
        *   例: `(BlockIf (SETL cmp) yes no) -> (BlockLT cmp yes no)`
    *   `InvertFlags`オペレーションを条件分岐ブロックに吸収するルールが追加されました。これにより、フラグレジスタの反転を伴う比較を効率的に処理できます。
        *   例: `(BlockLT (InvertFlags cmp) yes no) -> (BlockGT cmp yes no)`

これらの変更により、GoコンパイラのSSAバックエンドは、より強力で柔軟な最適化とローワーリングの能力を獲得し、将来的な拡張性も向上しました。

## コアとなるコードの変更箇所

このコミットにおけるコアとなる変更は、主に以下のファイルに集中しています。

1.  **`src/cmd/compile/internal/ssa/block.go`**: `BlockKind`の定義が拡張され、アーキテクチャ固有のブロック種別をサポートするための基盤が作られました。

4.  **`src/cmd/compile/internal/ssa/rewrite.go`**: `applyRewrite`関数が`Block`と`Value`の両方の書き換え関数を受け取るように変更され、書き換えエンジンの中心的な役割を担います。

### `src/cmd/compile/internal/ssa/lower.go`

```go
// 変更前
func lower(f *Func) {
	applyRewrite(f, f.Config.lower) // 単一のローワーリング関数を適用
	// ...
	// additional pass for 386/amd64, link condition codes directly to blocks
	// TODO: do generically somehow?  Special "block" rewrite rules?
	for _, b := range f.Blocks {
		for {
			switch b.Kind {
			case BlockIf:
				switch b.Control.Op {
				case OpSETL:
					b.Kind = BlockLT
					// ...
				}
			// ...
			}
			break
		}
	}
}

// 変更後
func lower(f *Func) {
	// 変更点: applyRewriteにlowerBlockとlowerValueの両方を渡す
	applyRewrite(f, f.Config.lowerBlock, f.Config.lowerValue)

	// 以前の手動によるブロックローワーリングロジックは削除された
	// ...
}
```
`lower`関数から、AMD64/386固有の条件コードをブロックにリンクする手動のロジックが削除されました。これは、新しいルールベースのシステム（`lowerBlockAMD64`）によって処理されるためです。`applyRewrite`関数も、ブロックと値の両方の書き換え関数を受け取るように変更されました。

## 変更の背景

GoコンパイラのSSAバックエンドは、プログラムの最適化と機械語への変換を行う上で非常に重要な役割を担っています。このコミット以前は、値（`Value`）に対する最適化やローワーリングのルールは存在していましたが、制御フローブロック（`Block`）に対するルールベースの書き換えは限定的でした。

コンパイラ最適化において、条件分岐（`if`文など）やループといった制御フローの構造を効率的に処理することは、生成される機械語の品質に直結します。例えば、`if true { ... }` のような常に真となる条件分岐は、コンパイル時にその条件判定を削除し、常に`then`ブロックへジャンプするように最適化できます。このような最適化を手動でコードに記述すると、複雑になりがちで、新しいアーキテクチャのサポートや最適化ルールの追加が困難になります。

このコミットの背景には、以下のような課題と目的がありました。

1.  **最適化の表現力向上**: 制御フローブロックに対するより強力で柔軟な最適化を可能にする。
2.  **コードの簡素化と保守性向上**: 手動で記述されていたブロック関連の最適化ロジック（例: `deadcode.go`内の定数畳み込み）を、宣言的なルールベースのシステムに移行することで、コードの複雑性を軽減し、保守性を高める。
3.  **アーキテクチャ固有のローワーリングの改善**: 特定のアーキテクチャ（例: AMD64）において、条件コード（フラグレジスタ）の扱いを含むブロックのローワーリングを、より効率的かつ体系的に行うための基盤を構築する。
4.  **拡張性の確保**: 将来的に新しい最適化やアーキテクチャサポートを追加する際に、既存のコードを大幅に変更することなく、ルールを追加するだけで対応できるようにする。

これらの目的を達成するために、値の書き換えと同様に、ブロックに対してもルールベースの書き換えシステムを導入することが決定されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

### 1. コンパイラのSSA (Static Single Assignment) 形式

SSAは、コンパイラの中間表現（IR）の一種で、各変数が一度だけ代入されるようにする特性を持ちます。これにより、データフロー解析や最適化が容易になります。Goコンパイラのバックエンドは、ソースコードをSSA形式に変換し、その上で様々な最適化を適用します。

*   **Value**: SSA形式における基本的な計算単位です。オペレーション（`Op`）、引数（`Args`）、型（`Type`）、補助情報（`Aux`）などから構成されます。例えば、`OpAdd`は加算を表す`Value`です。
*   **Block**: 制御フローグラフ（CFG）の基本的な構成要素で、一連の`Value`（命令）を含み、単一のエントリポイントと単一のイグジットポイントを持ちます。`Block`は、次の`Block`への遷移方法（条件分岐、無条件ジャンプなど）を決定する制御`Value`（`Control`）を持ちます。

### 2. コンパイラ最適化とローワーリング

*   **最適化 (Optimization)**: プログラムの実行速度やメモリ使用量を改善するために、中間表現を変換するプロセスです。定数畳み込み、デッドコード削除、共通部分式除去などが含まれます。
*   **ローワーリング (Lowering)**: 高レベルの中間表現を、より低レベルで機械語に近い中間表現に変換するプロセスです。最終的に、特定のCPUアーキテクチャの命令セットにマッピングできる形に変換されます。

### 3. ルールベースの書き換え (Rule-based Rewriting)

コンパイラ最適化の手法の一つで、特定のパターン（左辺）に一致する中間表現を、より最適化された別のパターン（右辺）に置き換えるルールを定義します。これにより、最適化ロジックを宣言的に記述でき、コードの可読性と保守性が向上します。

*   **`rulegen`**: Goコンパイラ内で使用されるツールで、`.rules`ファイルに記述された書き換えルールをGoのソースコード（`generic.go`, `lowerAmd64.go`など）に自動生成します。これにより、手動で`switch`文や`if`文を記述する手間が省け、ルールの追加・変更が容易になります。

### 4. 制御フローグラフ (Control Flow Graph, CFG)

プログラムの実行パスを表現するグラフ構造です。ノードは`Block`（基本ブロック）を表し、エッジは`Block`間の可能な遷移を表します。コンパイラはCFG上でデータフロー解析や最適化を行います。

### 5. AMD64アーキテクチャの条件コード

AMD64（x86-64）アーキテクチャでは、比較命令（`CMP`）や算術演算命令の結果に応じて、CPUのフラグレジスタ（`EFLAGS`レジスタ）内の特定のビット（条件コード）が設定されます。これらの条件コードは、その後の条件分岐命令（`Jcc`命令、例: `JL` (Jump if Less), `JNE` (Jump if Not Equal)）によって利用され、プログラムの実行フローを制御します。

*   `SETL`, `SETNE`, `SETB`など: 特定の条件コードに基づいてバイト値を設定する命令（例: `SETL`は「Less」の場合に1、そうでなければ0をセット）。
*   `InvertFlags`: フラグレジスタの解釈を反転させる概念的な操作。例えば、`CMPQ a b`の結果が`SETL`（a < b）である場合、`InvertFlags`を適用すると`SETG`（a > b）に相当する。これは、`CMPQ b a`と同じ効果を持つ。

	blockInvalid     BlockKind = 0
	blockGenericBase           = 1 + 100*iota // 汎用ブロックのベース
	blockAMD64Base                          // AMD64固有ブロックのベース
	block386Base                            // 386固有ブロックのベース
	blockMax // sentinel
)
// generic block kinds
const (
	blockGenericStart BlockKind = blockGenericBase + iota
	BlockExit
	BlockPlain
	BlockIf
	BlockCall
	// ...
)
```
`BlockKind`が`int32`に拡張され、`blockGenericBase`や`blockAMD64Base`のようなアーキテクチャ固有のオフセットが導入されました。これにより、各アーキテクチャが独自の`BlockKind`を定義できるようになり、SSA IRがよりアーキテクチャの特性を反映できるようになります。以前は`BlockKind`に直接定義されていた`BlockEQ`などのアーキテクチャ固有のブロックは、`opamd64.go`などのアーキテクチャ固有のファイルに移動しました。

### `src/cmd/compile/internal/ssa/rewrite.go`

```go
// 変更前
func applyRewrite(f *Func, r func(*Value) bool) {
	// ...
	for {
		change := false
		for _, b := range f.Blocks {
			for _, v := range b.Values {
				// ...
				if r(v) { // 値の書き換えのみ
					change = true
				}
			}
		}
		if !change {
			return
		}
	}
}

// 変更後
func applyRewrite(f *Func, rb func(*Block) bool, rv func(*Value) bool) { // ブロックと値の書き換え関数を受け取る
	var curb *Block // 現在処理中のブロックを追跡 (デバッグ用)
	var curv *Value // 現在処理中の値を追跡 (デバッグ用)
	defer func() {
		if curb != nil {
			log.Printf("panic during rewrite of %s\n", curb.LongString())
		}
		if curv != nil {
			log.Printf("panic during rewrite of %s\n", curv.LongString())
			// TODO(khr): print source location also
		}
	}()

	for {
		change := false
		for _, b := range f.Blocks {
			// Block.ControlがOpCopyの場合の処理
			if b.Control != nil && b.Control.Op == OpCopy {
				for b.Control.Op == OpCopy {
					b.Control = b.Control.Args[0]
				}
			}
			curb = b
			if rb(b) { // ブロックの書き換えを適用
				change = true
			}
			curb = nil // ブロック処理完了

			for _, v := range b.Values {
				// ... (OpCopyの除去ロジックは変更なし) ...

				curv = v
				if rv(v) { // 値の書き換えを適用
					change = true
				}
				curv = nil // 値処理完了
			}
		}
		if !change {
			return
		}
	}
}
```
`applyRewrite`関数は、SSA書き換えエンジンの中心です。このコミットにより、`Block`と`Value`の両方に対して書き換えルールを適用できるようになりました。`rb`関数（ブロック書き換え）が`rv`関数（値書き換え）の前に実行され、制御フローの最適化が先行して行われる設計になっています。また、`Block.Control`が`OpCopy`である場合の最適化も追加され、よりクリーンなIRを生成します。デバッグ時のパニック発生時に、どのブロックや値で問題が発生したかを特定しやすくするためのロギングも強化されています。

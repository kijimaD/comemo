# [インデックス 24102] ファイルの概要

このコミットは、Go言語の`debug/pe`パッケージにおけるDWARFデバッグ情報解析の堅牢性を向上させるものです。具体的には、PE (Portable Executable) ファイルのセクションデータがディスク上でパディングされてしまい、その余分なデータがDWARFパーサーを混乱させる問題を解決します。セクションのメモリ上のサイズ（VirtualSize）に基づいてディスク上の生データを切り詰めることで、この問題に対処しています。

## 元コミット内容

`debug/pe`: PEセクションをメモリ上のサイズに切り詰める

`Section.Data`はディスク上のセクションデータを返しますが、これらは事前に定義された値に切り上げられています。このデータをそのまま処理すると、末尾のガベージデータによってDWARFパーサーが混乱します。メモリ上のセクション記述に従って`Section.Data`を切り詰めます。

DWARFセクションがメモリ上のサイズ0を持つ場合（PEオブジェクトファイルの場合）、それらはディスク上のサイズを維持します。

Fixes #11608

## 変更の背景

Go言語の`debug/pe`パッケージは、Windowsの実行可能ファイルやオブジェクトファイルで使われるPE (Portable Executable) フォーマットを解析するためのライブラリです。このパッケージは、デバッグ情報として広く利用されるDWARF (Debugging With Attributed Record Formats) 情報をPEファイルから抽出する機能も提供しています。

このコミットが解決しようとしている問題は、PEファイルのセクションデータがディスク上に格納される際に発生するパディングに起因します。PEファイルフォーマットでは、セクションのディスク上のサイズ（`SizeOfRawData`）が特定のファイルアライメント（`FileAlignment`）の倍数になるように調整されることがあります。これにより、実際のデータサイズよりも大きな領域がディスク上に確保され、末尾に意味のない「ガベージ」データが含まれる可能性があります。

`debug/pe`パッケージの`Section.Data`メソッドがこのディスク上の生データをそのまま返すと、DWARFパーサーはそのガベージデータをDWARF情報の一部として誤って解釈し、結果として解析エラーや不正なデバッグ情報の読み込みを引き起こしていました。特に、DWARF情報は非常に構造化されており、バイト単位の正確性が求められるため、余分なデータは致命的な問題となります。

この問題は、GoのIssue #11608として報告されており、このコミットはその解決を目的としています。

## 前提知識の解説

### PE (Portable Executable) フォーマット

PEフォーマットは、Windowsオペレーティングシステムで使用される実行可能ファイル、DLL、オブジェクトファイルなどの標準ファイルフォーマットです。PEファイルは、ヘッダーとそれに続く複数のセクションで構成されます。

*   **PEヘッダー**: ファイル全体のメタデータ（CPUアーキテクチャ、タイムスタンプ、セクション数など）を含みます。
*   **セクション**: 実際のコード、初期化済みデータ、リソース、デバッグ情報などが格納される領域です。各セクションには、そのセクションに関する情報（名前、メモリ上のサイズ、ディスク上のサイズ、メモリ上のアドレス、ディスク上のオフセットなど）を記述するセクションヘッダーがあります。

PEセクションにおいて重要な概念は以下の2つです。

*   **`SizeOfRawData` (ディスク上の生データサイズ)**: セクションがディスク上のファイル内で占めるバイト数です。これは通常、`FileAlignment`の倍数に切り上げられます。
*   **`VirtualSize` (メモリ上の仮想サイズ)**: セクションがメモリにロードされたときに占めるバイト数です。これは通常、`SectionAlignment`の倍数に切り上げられます。

`SizeOfRawData`と`VirtualSize`は異なることが多く、特に`VirtualSize`が`SizeOfRawData`よりも小さい場合、ディスク上のデータにはメモリ上では使用されない余分なデータが含まれる可能性があります。

### DWARF (Debugging With Attributed Record Formats)

DWARFは、ソースレベルデバッギングをサポートするためのデバッグ情報ファイルフォーマットです。プログラムの実行可能コードとソースコードの間の関係を記述し、デバッガーが変数名、型情報、関数名、ソースコードの行番号などを解決できるようにします。

DWARFはオブジェクトファイルフォーマットに依存しない設計ですが、通常はELF (Executable and Linkable Format) ファイル（Unix/Linuxシステム）や、一部のコンパイラ（MinGWなど）によってPEファイルにも埋め込まれます。DWARF情報は、通常、`.debug_info`, `.debug_abbrev`, `.debug_line`などの専用セクションに格納されます。

DWARFパーサーは、これらのセクションからデバッグ情報を読み取り、解析します。DWARFデータの構造は厳密であり、予期せぬデータ（ガベージ）が混入すると、パーサーは正しく情報を解釈できなくなります。

### Goの `debug/pe` パッケージ

Go標準ライブラリの`debug/pe`パッケージは、PEファイルを読み込み、その構造をGoのデータ構造にマッピングするための機能を提供します。これにより、GoプログラムからPEファイルのヘッダー情報やセクションデータにアクセスできます。このパッケージは、Goのデバッガーや関連ツールがPEファイルからデバッグ情報を抽出する際に利用されます。

## 技術的詳細

このコミットの核心は、PEセクションのディスク上の生データ（`Section.Data`が返すデータ）が、メモリ上の実際のセクションサイズ（`VirtualSize`）よりも大きい場合に発生する問題への対処です。

PEファイルフォーマットの特性上、ディスク上のセクションデータは`FileAlignment`の倍数に切り上げられるため、`Section.Data`が返すバイト列の末尾には、実際のセクション内容とは無関係なパディングデータ（ガベージ）が含まれることがあります。DWARFパーサーは、このガベージデータをDWARF情報の有効な一部として誤って解釈し、結果としてデバッグ情報の読み込みに失敗したり、誤った情報を報告したりする可能性がありました。

このコミットでは、この問題を解決するために、`debug/pe`パッケージがPEセクションのデータを読み込む際に、そのセクションの`VirtualSize`を考慮してデータを切り詰めるロジックを導入しています。

具体的には、以下のルールが適用されます。

1.  **`0 < s.VirtualSize && s.VirtualSize < s.Size` の場合**:
    *   セクションのメモリ上のサイズ（`s.VirtualSize`）が0より大きく、かつディスク上の生データサイズ（`s.Size`）よりも小さい場合、読み込んだバイト列`b`を`s.VirtualSize`の長さに切り詰めます (`b = b[:s.VirtualSize]`)。これにより、ディスク上の余分なパディングデータがDWARFパーサーに渡されるのを防ぎます。
2.  **`s.VirtualSize == 0` の場合**:
    *   一部のPEオブジェクトファイルでは、DWARFセクションの`VirtualSize`が0として記述されることがあります。この場合、セクションのメモリ上のサイズが不明確であるため、ディスク上の生データサイズ（`s.Size`）をそのまま使用します。これは、`VirtualSize`が0であるにもかかわらず、ディスク上には有効なDWARFデータが存在する可能性があるためです。このケースでは、切り詰めは行われません。

この変更により、DWARFパーサーは常にメモリ上のセクションの有効なデータのみを受け取るようになり、ガベージデータによる混乱が解消されます。

## コアとなるコードの解説

### `src/debug/pe/file.go` の変更

追加された3行のコードは、`File`構造体の`DWARF()`メソッド内で、各セクションの生データを読み込んだ直後に実行されます。

```go
		if 0 < s.VirtualSize && s.VirtualSize < s.Size {
			b = b[:s.VirtualSize]
		}
```

*   `s.VirtualSize`: セクションがメモリにロードされたときのサイズ。
*   `s.Size`: セクションのディスク上の生データサイズ（`SizeOfRawData`）。

この条件式は、以下の2つの条件が同時に満たされる場合に真となります。
1.  `s.VirtualSize`が0より大きいこと。これは、セクションが実際にメモリ上の領域を占めることを意味します。
2.  `s.VirtualSize`が`s.Size`よりも小さいこと。これは、ディスク上の生データにメモリ上では不要なパディングデータが含まれていることを意味します。

この条件が満たされた場合、`b = b[:s.VirtualSize]`によって、読み込んだバイトスライス`b`が`s.VirtualSize`の長さに切り詰められます。これにより、DWARFパーサーにはメモリ上の有効なデータのみが渡され、末尾のガベージデータが取り除かれます。

この変更は、PEファイルからDWARF情報を正確に抽出するために不可欠であり、DWARFパーサーが不正なデータで混乱するのを防ぎます。

### `src/debug/pe/file_test.go` の変更

*   **`fileTest`構造体の変更**:
    `hasNoDwarfInfo bool`フィールドが追加されました。これは、特定のテストファイルがDWARF情報を持たないことを示すために使用されます。これにより、`TestOpen`関数内でDWARF情報の取得を試みる際に、エラーが期待されるテストケースを適切に処理できます。

*   **`TestOpen`関数の変更**:
    既存の`TestOpen`関数に、`!tt.hasNoDwarfInfo`の場合に`f.DWARF()`を呼び出すロジックが追加されました。これにより、各テストファイルに対してDWARF情報の取得が試みられ、エラーが発生しないことが検証されます。

*   **`TestDWARF`関数の追加**:
    この新しいテスト関数は、Windows環境でのみ実行されます (`runtime.GOOS != "windows"`の場合はスキップ)。
    1.  一時ディレクトリを作成し、そこにシンプルな`main`関数を持つGoプログラム (`a.go`) を書き込みます。
    2.  `go build -o a.exe a.go`コマンドを実行して、このプログラムのPE実行可能ファイル (`a.exe`) をビルドします。
    3.  `debug/pe`パッケージの`Open`関数を使用して、ビルドされた`a.exe`ファイルを開きます。
    4.  `f.DWARF()`を呼び出して、PEファイルからDWARF情報を取得します。
    5.  取得したDWARF情報から`dwarf.Reader()`を作成し、デバッグ情報エントリ (DIE) を順に読み取ります。
    6.  各DIEを走査し、`dwarf.TagSubprogram`タグを持つエントリ（関数定義）を探します。
    7.  関数名が`"main.main"`であるDIEが見つかればテストは成功です。これは、Goコンパイラが生成する実行可能ファイルに`main.main`関数のDWARF情報が正しく含まれていることを検証します。

この`TestDWARF`関数は、PEファイルからのDWARF情報抽出と解析の全体的なフローをエンドツーエンドで検証するものであり、今回のコミットで導入されたセクションデータ切り詰めロジックが正しく機能していることを保証します。

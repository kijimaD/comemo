# [インデックス 2047] ファイルの概要

## コミット

このコミットは、Go言語の標準ライブラリにおけるエラー表現の根本的な変更、通称「Big Error Shift」の第2段階にあたります。具体的には、`os`パッケージにおけるエラーの表現方法をよりクリーンなものへと変更し、Unixのエラー番号（errno）を直接`Error`インターフェースとして扱えるようにする改善が施されています。これにより、エラー処理の仕組みが簡素化され、将来的な`os.NewError`の廃止に向けた準備が進められています。

## 変更の背景

このコミットは、Go言語の初期段階におけるエラーハンドリングの設計思想の進化を反映しています。Go言語は「エラーは値である (errors are values)」という哲学を掲げていますが、初期の実装では、特にUnixシステムコールから返されるエラー番号（errno）の扱いにおいて、その哲学が十分に反映されていない部分がありました。

以前の`os`パッケージでは、`errno`を`_Error`という内部構造体にラップし、`NewError`関数を通じてエラー文字列と関連付けていました。また、エラーの重複を避けるために`errorTab`というマップで管理していました。しかし、このアプローチは、エラーが単なる文字列ではなく、より意味のある型として扱われるべきであるというGoの設計原則とは乖離していました。

この「Big Error Shift」は、エラーをより直接的で、型安全な方法で表現することを目指しています。具体的には、`errno`自体を`Error`インターフェースを満たす型として定義することで、エラーが単なる文字列ではなく、その数値的な意味を持つ値として扱えるようにします。これにより、エラーの比較や処理がより効率的かつ直感的になります。このコミットは、その大きな変更の第2段階として、`os`パッケージのエラー表現を新しいスキームに適合させるための重要な一歩です。

## 前提知識の解説

### Go言語におけるエラーハンドリングの基本

Go言語では、エラーは組み込みの`error`インターフェースによって表現されます。このインターフェースは、`Error() string`という単一のメソッドを持ちます。任意の型がこのメソッドを実装することで、`error`型として扱われることができます。

```go
type error interface {
    Error() string
}
```

Goのエラーハンドリングは、例外処理（try-catchなど）とは異なり、関数がエラーを返す場合は、戻り値の最後の要素として`error`型を返すのが慣習です。呼び出し元は、この`error`が`nil`であるかどうかをチェックすることで、処理が成功したかエラーが発生したかを判断します。

```go
func doSomething() (result string, err error) {
    // ... 処理 ...
    if someCondition {
        return "", errors.New("something went wrong") // エラーを返す
    }
    return "success", nil // 成功を返す
}
```

### Unixエラー番号 (errno)

Unix系オペレーティングシステムでは、システムコールが失敗した場合に、その原因を示す整数値が設定されます。これをエラー番号（`errno`）と呼びます。例えば、`ENOENT`は「No such file or directory（そのようなファイルやディレクトリはない）」を、`EINVAL`は「Invalid argument（無効な引数）」を意味します。これらのエラー番号は、`sys/errno.h`などのヘッダーファイルで定義されており、通常はマクロとして提供されます。Go言語の`syscall`パッケージは、これらのUnixシステムコールや関連する定数へのインターフェースを提供します。

### `syscall.Errstr`関数

`syscall`パッケージには、Unixエラー番号を対応するエラー文字列に変換する`Errstr`関数が存在します。例えば、`syscall.Errstr(syscall.ENOENT)`は"no such file or directory"のような文字列を返します。

## 技術的詳細

このコミットの技術的な核心は、`os`パッケージにおけるエラーの表現を、従来の`_Error`構造体と`NewError`関数による文字列ベースの管理から、`Errno`型を直接`error`インターフェースとして扱う新しいアプローチへと移行した点にあります。

### 変更前のアプローチ

変更前は、`src/lib/os/error.go`内で以下のような構造が使われていました。

1.  **`_Error`構造体**: エラー文字列をラップするための内部構造体。
    ```go
    type _Error struct {
        s string
    }
    ```
2.  **`NewError`関数**: 新しい`_Error`オブジェクトを作成し、エラー文字列を管理するための関数。この関数は、同じエラー文字列に対しては既存の`_Error`オブジェクトを返すことで、エラーのシングルトン（一意性）を保証していました。
    ```go
    func NewError(s string) Error { ... }
    ```
3.  **`errorTab`マップ**: `errno`と`Error`オブジェクトをマッピングするためのマップ。`ErrnoToError`関数内で、`errno`から`Error`オブジェクトへの高速なルックアップを提供していました。
    ```go
    var errorTab = make(map[int64] Error);
    ```
4.  **`ErrnoToError`関数（旧）**: `errno`を受け取り、`errorTab`を介して既存の`Error`オブジェクトを返すか、`NewError`を使って新しいオブジェクトを作成していました。

このアプローチでは、`errno`は一度`_Error`オブジェクトに変換され、そのオブジェクトがエラーの「実体」として扱われていました。エラーの比較は、`_Error`オブジェクトのアドレス比較によって行われていました。

### 変更後のアプローチ

このコミットによって、エラー表現は以下のように変更されました。

1.  **`Errno`型の導入**: `int64`を基盤とする新しい型`Errno`が導入されました。
    ```go
    type Errno int64
    ```
2.  **`Errno`型による`error`インターフェースの実装**: `Errno`型に`String() string`メソッドが追加されました。このメソッドは`syscall.Errstr(e)`を呼び出すことで、`Errno`値に対応するエラー文字列を返します。これにより、`Errno`型は直接`error`インターフェースを満たすことになります。
    ```go
    func (e Errno) String() string {
        return syscall.Errstr(e)
    }
    ```
3.  **`ErrnoToError`関数の簡素化**: 新しい`ErrnoToError`関数は、単に`Errno(errno)`を返すようになりました。`errno`が0の場合は`nil`を返します。これにより、`errno`から`Error`への変換が非常に直接的になりました。
    ```go
    func ErrnoToError(errno int64) Error {
        if errno == 0 {
            return nil
        }
        return Errno(errno)
    }
    ```
4.  **`errorTab`の廃止**: 従来の`errorTab`マップは不要となり、削除されました。これは、`Errno`値自体がエラーの識別子として機能し、文字列への変換は`String()`メソッドによってオンデマンドで行われるためです。
5.  **共通Unixエラー定数の再定義**: `ENONE`, `EPERM`などの共通Unixエラー定数は、`Errno(syscall.ENONE)`のように、直接`Errno`型にキャストされた`syscall`パッケージの定数として定義されるようになりました。これにより、これらのエラーも新しい`Errno`ベースのスキームに適合します。

この変更により、Goのエラーハンドリング哲学である「エラーは値である」がより明確に反映されるようになりました。`errno`自体が`error`インターフェースを満たす値として扱われるため、エラーの比較は`Errno`値の直接比較によって行えるようになり、より効率的かつ自然なコード記述が可能になります。

## コアとなるコードの変更箇所

`src/lib/os/error.go` ファイルにおいて、以下の主要な変更が行われました。

### 追加されたコード

```go
// Errno is the Unix error number.  Names such as EINVAL are simple
// wrappers to convert the error number into an Error.
type Errno int64
func (e Errno) String() string {
	return syscall.Errstr(e)
}

// ErrnoToError calls NewError to create an _Error object for the string
// associated with Unix error code errno.
func ErrnoToError(errno int64) Error {
	if errno == 0 {
		return nil
	}
	return Errno(errno)
}

// Commonly known Unix errors.
var (
	ENONE Error = Errno(syscall.ENONE);
	EPERM Error = Errno(syscall.EPERM);
	// ... (以下、多数のUnixエラー定数の定義が続く) ...
	ERANGE Error = Errno(syscall.ERANGE);
)
```

### 削除されたコード

```go
// Indexed by errno.
// If we worry about syscall speed (only relevant on failure), we could
// make it an array, but it's probably not important.
var errorTab = make(map[int64] Error);

// ErrnoToError calls NewError to create an _Error object for the string
// associated with Unix error code errno.
func ErrnoToError(errno int64) Error {
	if errno == 0 {
		return nil
	}
	// Quick lookup by errno.
	err, ok := errorTab[errno];
	if ok {
		return err
	}
	err = NewError(syscall.Errstr(errno));
	errorTab[errno] = err;
	return err;
}

// Commonly known Unix errors.
var (
	// TODO(r):
	// 1. these become type ENONE struct { ErrorString }
	// 2. create private instances of each type: var eNONE ENONE(ErrnoToString(syscall.ENONE));
	// 3. put them in a table
	// 4. ErrnoToError uses the table. its error case ECATCHALL("%d")
	ENONE = ErrnoToError(syscall.ENONE);
	EPERM = ErrnoToError(syscall.EPERM);
	// ... (以下、多数のUnixエラー定数の定義が続く) ...
	EAGAIN = ErrnoToError(syscall.EAGAIN);
)
```

## コアとなるコードの解説

このコミットの最も重要な変更は、`Errno`という新しい型を導入し、それが直接`error`インターフェースを満たすようにした点です。

1.  **`type Errno int64`**:
    これは、Unixのエラー番号（`int64`で表現される）をラップするための新しい型定義です。これにより、単なる整数値ではなく、エラー番号としての意味を持つ型として扱えるようになります。

2.  **`func (e Errno) String() string { return syscall.Errstr(e) }`**:
    このメソッドは、`Errno`型がGoの組み込み`error`インターフェースを満たすために不可欠です。`error`インターフェースは`Error() string`メソッドを要求しますが、ここでは慣例的に`String()`メソッドが使われています（Goの初期段階では`Error()`と`String()`が混在していた時期があり、このコミット時点では`String()`が使われているようです。最終的には`Error()`に統一されます）。このメソッドは、`syscall.Errstr`関数を呼び出すことで、`Errno`値に対応する人間が読めるエラー文字列を返します。これにより、`Errno`型の変数を`error`型として扱うことができ、`fmt.Println(err)`のように出力すると、適切なエラーメッセージが表示されます。

3.  **`func ErrnoToError(errno int64) Error { ... }`**:
    この関数は、外部から渡される`int64`型の`errno`を、新しい`Errno`型に変換し、それを`Error`インターフェースとして返します。`errno == 0`の場合はエラーがないことを意味するため、`nil`を返します。この新しい実装は、以前の`errorTab`マップを使った複雑なルックアップロジックを完全に排除し、非常にシンプルになりました。これは、`Errno`値自体がエラーの識別子として機能し、その文字列表現は`String()`メソッドによって動的に生成されるため、マップによるキャッシュが不要になったことを示しています。

4.  **`var ENONE Error = Errno(syscall.ENONE);` などの定数定義**:
    以前は`ErrnoToError`関数を介して`_Error`オブジェクトとして定義されていたUnixエラー定数が、直接`Errno`型にキャストされた`syscall`パッケージの定数として定義されるようになりました。これにより、これらの定数も新しいエラー表現スキームに完全に統合され、`error`インターフェースを満たす`Errno`型の値として利用できるようになります。

これらの変更により、Goのエラーハンドリングはより統一され、`errno`のようなシステムレベルのエラーも、Goの型システムとインターフェースの恩恵を直接受けられるようになりました。これは、Go言語がエラーを単なる文字列ではなく、意味のある値として扱うという設計原則を強化する重要なステップでした。

# [インデックス 2332] ファイルの概要

## コミット

このコミット `97fe55720dcb7c8306edde1089c1293d23d5297a` は、Go言語の初期のリンカである `5l` (Plan 9アーキテクチャ、特にARMや5-seriesプロセッサをターゲットとしたもの) におけるファイルI/O処理を、`Biobuf` と呼ばれるバッファリングされたI/Oシステムを使用するように変更するものです。これにより、生のファイルディスクリプタを用いたシステムコールベースのI/Oから、より効率的で抽象化されたバッファリングI/Oへと移行しています。

## 変更の背景

この変更が行われた2009年という時期は、Go言語がまだ開発の初期段階にあり、そのツールチェインやランタイムが活発に構築されていた頃です。Goの初期の設計思想には、Plan 9オペレーティングシステムからの影響が強く見られます。Plan 9では、`Biobuf` は標準的なバッファリングI/Oライブラリとして広く利用されており、ファイル操作の効率化とコードの簡素化に貢献していました。

`5l` リンカは、オブジェクトファイルやアーカイブファイルを読み込み、それらをリンクして実行可能ファイルを生成する役割を担っています。このプロセスでは、大量のデータをディスクから読み込む必要があり、I/O性能が全体のリンクセッション時間に大きく影響します。従来の生のファイルディスクリプタ (`int`) を使用した `open()`, `read()`, `seek()`, `close()` といったシステムコールは、呼び出しごとにカーネルモードへの切り替えが発生し、オーバーヘッドが大きくなる可能性があります。

`Biobuf` を導入することで、以下のようなメリットが期待されます。

1.  **I/O性能の向上**: バッファリングにより、一度のシステムコールでより多くのデータを読み書きできるようになり、システムコールの回数を削減できます。これにより、カーネルモードとユーザーモード間のコンテキストスイッチのオーバーヘッドが減少し、全体的なI/Oスループットが向上します。
2.  **コードの簡素化**: `Biobuf` は、ファイルポインタの管理、バッファの充填、エラーハンドリングなど、低レベルなI/Oの詳細を抽象化します。これにより、リンカのコードはI/O処理の実装ではなく、リンカ本来のロジックに集中できるようになります。
3.  **一貫性の確保**: Plan 9由来のツールチェイン全体で `Biobuf` を使用することで、I/O処理の一貫性が保たれ、将来的なメンテナンスや機能追加が容易になります。

このコミットは、Goツールチェインの基盤部分における性能と堅牢性を向上させるための、初期の重要な最適化の一つと言えます。

## 前提知識の解説

### 1. Go言語の初期のツールチェインとPlan 9の影響

Go言語の初期のコンパイラやリンカは、Plan 9オペレーティングシステムのツールチェイン（`8c`, `8l`, `6c`, `6l` など）から派生したものでした。`5l` は、Plan 9の `5l` リンカに相当し、ARMプロセッサなどの32ビットアーキテクチャをターゲットとしていました。これらのツールは、Go言語のソースコードをコンパイルし、オブジェクトファイルをリンクして実行可能ファイルを生成する役割を担っていました。

### 2. バッファリングI/Oと非バッファリングI/O

*   **非バッファリングI/O (Unbuffered I/O)**: `open()`, `read()`, `write()`, `close()` といったシステムコールを直接使用するI/O方式です。データはアプリケーションのバッファとカーネルのバッファ（ページキャッシュなど）間で直接転送されます。システムコールごとにカーネルモードへの切り替えが発生するため、小さなデータを頻繁に読み書きする場合にはオーバーヘッドが大きくなります。
*   **バッファリングI/O (Buffered I/O)**: `Biobuf` やC言語の `stdio` ライブラリ (`fopen()`, `fread()`, `fwrite()`) のように、ユーザー空間にバッファを設けてI/Oを行う方式です。アプリケーションはまずユーザー空間のバッファに対して読み書きを行い、バッファがいっぱいになったり、明示的にフラッシュされたりしたときに、まとめてシステムコールを呼び出してカーネルとデータをやり取りします。これにより、システムコールの回数を減らし、I/O性能を向上させることができます。

### 3. `Biobuf` (Plan 9 I/Oライブラリ)

`Biobuf` は、Plan 9オペレーティングシステムで広く使われているバッファリングI/Oライブラリです。C言語の `FILE` 構造体と `stdio` 関数群に似た機能を提供しますが、よりシンプルでPlan 9の哲学に沿った設計がされています。

`Biobuf` の主な機能と関連する関数は以下の通りです。

*   **`Biobuf` 構造体**: ファイルディスクリプタ、内部バッファ、バッファ内の現在位置、読み書きモードなどの状態を保持します。
*   **`Bopen(path, mode)`**: 指定されたパスのファイルを開き、`Biobuf` 構造体を初期化して返します。
*   **`Bread(Biobuf *f, void *buf, int n)`**: `Biobuf` から `n` バイトを読み込み、`buf` に格納します。必要に応じて内部バッファを自動的に充填します。
*   **`Bseek(Biobuf *f, vlong offset, int whence)`**: ファイルポインタを移動します。`vlong` は64ビット整数型です。
*   **`Bgetc(Biobuf *f)`**: `Biobuf` から1バイト（文字）を読み込みます。
*   **`Bget4(Biobuf *f)`**: `Biobuf` から4バイトを読み込み、32ビット整数として解釈して返します。このコミットで追加されたヘルパー関数です。
*   **`Brdline(Biobuf *f, int delim)`**: `Biobuf` から指定されたデリミタ（区切り文字）までを読み込み、その行へのポインタを返します。
*   **`Boffset(Biobuf *f)`**: `Biobuf` の現在のファイルオフセットを返します。
*   **`Bterm(Biobuf *f)`**: `Biobuf` を閉じ、関連するリソースを解放します。
*   **`Bracteof`**: `Biobuf` の内部状態を示すフラグの一つで、ファイルの終端に達したことを示します。

これらの関数は、低レベルなファイルディスクリプタ操作を隠蔽し、より高レベルなデータストリームとしてファイルを扱えるようにします。

## 技術的詳細

このコミットの技術的詳細は、`5l` リンカがオブジェクトファイルやアーカイブファイルを解析する際のI/O処理がどのように変更されたかに集約されます。

### 1. `ldobj` 関数のシグネチャ変更

*   変更前: `void ldobj(int, int32, char*)`
    *   第一引数は生のファイルディスクリプタ (`int`) でした。
*   変更後: `void ldobj(Biobuf*, int32, char*)`
    *   第一引数が `Biobuf*` 型のポインタに変更されました。これにより、`ldobj` 関数内で `Biobuf` の機能を利用できるようになります。

### 2. `objfile` 関数におけるファイル操作の変更

`objfile` 関数は、指定されたオブジェクトファイルまたはアーカイブファイルを開き、その内容を解析する主要な関数です。

*   **ファイルオープン**:
    *   `f = open(file, 0);` が `f = Bopen(file, 0);` に変更されました。これにより、標準の `open` システムコールではなく、`Biobuf` を介してファイルが開かれ、`Biobuf` 構造体へのポインタが `f` に格納されます。
    *   エラーチェックも `f < 0` から `f == nil` に変更され、`Bopen` が失敗した場合は `nil` を返すことが示唆されます。
*   **データ読み込み**:
    *   `l = read(f, magbuf, SARMAG);` が `l = Bread(f, magbuf, SARMAG);` に変更されました。
    *   `cnt = read(f, start, cnt);` が `cnt = Bread(f, start, cnt);` に変更されました。
    *   これにより、生の `read` システムコールではなく、`Biobuf` のバッファリングされた読み込み関数が使用されます。
*   **ファイルシーク**:
    *   `seek(f, 0L, 2);` や `seek(f, off, 0);` が `Bseek(f, 0L, 2);` や `Bseek(f, off, 0);` に変更されました。
    *   `Biobuf` の `Bseek` 関数は、内部バッファの状態を適切に管理しながらファイルポインタを移動します。
*   **ファイルクローズ**:
    *   `close(f);` が `Bterm(f);` に変更されました。
    *   `Bterm` は `Biobuf` の内部バッファをフラッシュし、ファイルディスクリプタを閉じ、`Biobuf` 構造体に関連するメモリを解放します。

### 3. `zaddr` 関数の変更と `Bget4` の導入

`zaddr` 関数は、オブジェクトファイル内のアドレス指定に関する情報を解析する役割を担っています。

*   **シグネチャ変更**:
    *   変更前: `int zaddr(uchar *p, Adr *a, Sym *h[])`
        *   `uchar *p` は、ファイルから読み込まれたバイト列を指すポインタでした。
    *   変更後: `void zaddr(Biobuf *f, Adr *a, Sym *h[])`
        *   `Biobuf *f` から直接データを読み込むように変更されました。これにより、`zaddr` 関数は独自のバッファ管理を行う必要がなくなりました。
*   **データ読み込みの変更**:
    *   `p[0]`, `p[1]`, `p[2]`, `p[3]` といった直接的なバッファアクセスが、`Bgetc(f)` や新しく導入された `Bget4(f)` に置き換えられました。
    *   `Bget4(Biobuf *f)` 関数が追加されました。これは `Biobuf` から4バイトを読み込み、リトルエンディアン形式で32ビット整数に変換して返します。これは、Goのオブジェクトファイルフォーマットがリトルエンディアンの整数値を多用しているため、非常に便利なヘルパー関数です。
    *   文字列の読み込みも `memmove(a->sval, p+4, NSNAME);` から `Bread(f, a->sval, NSNAME);` に変更されています。

### 4. `ldobj` 関数におけるバッファ管理の削除とI/Oロジックの簡素化

`ldobj` 関数は、オブジェクトファイルの内容を実際に読み込み、リンカの内部データ構造に変換する中心的なロジックを含んでいます。

*   **バッファ管理変数の削除**:
    *   `uchar *bloc, *bsize, *stop;` といった、手動でバッファを管理するための変数が削除されました。これは、`Biobuf` がこれらの管理を内部で行うため不要になったことを意味します。
*   **`readsome` 関数の削除**:
    *   カスタムのバッファ充填ロジックを実装していた `readsome` 関数が削除されました。これは `Biobuf` が同様の機能を内部で提供するためです。
*   **I/Oループの変更**:
    *   `if(c <= 0)` (残りのバイト数によるチェック) が `if(f->state == Bracteof || Boffset(f) >= eof)` に変更されました。これは、`Biobuf` の内部状態 (`Bracteof` でファイルの終端を検出) と現在のオフセット (`Boffset(f)`) を利用して、ファイルの終端をより正確に、かつ `Biobuf` の抽象化レベルで判断するようになったことを示します。
*   **データ解析の変更**:
    *   `o = bloc[0];` のようにバッファから直接バイトを読み出す代わりに、`o = Bgetc(f);` を使用するようになりました。
    *   `ANAME` や `ASIGNAME` といったシンボル名の読み込みにおいて、`memchr` を使ってヌル終端文字列を探し、手動でバッファポインタを進めていた処理が、`name = Brdline(f, '\0');` という `Biobuf` の関数一つで置き換えられました。これにより、コードが大幅に簡素化され、堅牢性が向上しています。
    *   `p->scond = bloc[1];` のようなプログラミング命令のフィールド読み込みも、`p->scond = Bgetc(f);` に変更されました。
    *   `p->line` や `a->offset` のような複数バイトの数値データも、`Bget4(f)` を使って読み込まれるようになりました。

これらの変更は、`5l` リンカのI/O処理を、低レベルなバイト操作から `Biobuf` が提供する高レベルなストリーム操作へと移行し、コードの可読性、保守性、そして潜在的な性能が向上しました。

## コアとなるコードの解説

このコミットのコアとなる変更は、`src/cmd/5l/obj.c` 内の `objfile`、`zaddr`、`ldobj` の各関数におけるI/O処理の全面的な見直しです。

1.  **`objfile` 関数**:
    *   ファイルディスクリプタ `f` の型が `int` から `Biobuf *` に変更され、`open`/`close`/`read`/`seek` といったシステムコールが `Bopen`/`Bterm`/`Bread`/`Bseek` といった `Biobuf` 関数に置き換えられました。これにより、ファイル操作がバッファリングI/Oレイヤーを介して行われるようになります。
    *   特に、アーカイブファイル（`.a` ファイル）の処理において、内部のオブジェクトファイルを読み込む際も `Biobuf` が使用されるようになりました。

2.  **`Bget4` 関数の追加**:
    *   `int32 Bget4(Biobuf *f)` という新しいヘルパー関数が追加されました。これは、`Biobuf` から4バイトを読み込み、それらをリトルエンディアン形式の32ビット整数に結合して返します。Goのオブジェクトファイルフォーマットでは、多くの数値データがこの形式で格納されているため、この関数はコードの簡素化と読み込みの正確性に貢献します。

3.  **`zaddr` 関数**:
    *   この関数は、オブジェクトファイル内のアドレス指定（オペランド）情報を解析します。変更前は、`uchar *p` という生のバイト配列ポインタからデータを直接読み取っていましたが、変更後は `Biobuf *f` から `Bgetc(f)` や `Bget4(f)` を使ってバイト単位またはワード単位でデータを読み込むようになりました。
    *   これにより、`zaddr` 関数は自身のバッファ管理ロジックを持つ必要がなくなり、よりクリーンでエラーの少ない実装になりました。また、エラー発生時の診断メッセージも `Bputc(f, ALAST+1)` のように `Biobuf` を介してエラー状態を通知する形に変更されています。

4.  **`ldobj` 関数**:
    *   この関数は、オブジェクトファイル内の個々の命令（Prog構造体）やシンボル情報を読み込み、リンカの内部表現に変換します。
    *   変更前は、`bloc`, `bsize`, `stop` といったポインタを使って手動でバッファを管理し、`readsome` 関数でバッファを充填していました。この複雑なバッファ管理ロジックはすべて削除されました。
    *   代わりに、`Bgetc(f)` で1バイト、`Bget4(f)` で4バイト、`Brdline(f, '\0')` でヌル終端文字列を読み込むなど、`Biobuf` の高レベルなI/O関数が全面的に採用されました。
    *   ファイルの終端チェックも、残りのバイト数 `c` ではなく、`Biobuf` の内部状態 (`f->state == Bracteof`) と現在のオフセット (`Boffset(f) >= eof`) を利用するように変更され、より堅牢になりました。
    *   特に、シンボル名 (`ANAME`, `ASIGNAME`) の読み込みが `Brdline(f, '\0')` 一行で処理できるようになり、コードの簡潔さが大幅に向上しました。

これらの変更は、`5l` リンカのI/Oサブシステムを、より現代的で効率的なバッファリングI/Oモデルへと移行させるものであり、Goツールチェインの初期の成熟度を示す重要なステップでした。

## 変更の背景

このコミットの背景には、GoプログラムにおけるOSシグナル処理の挙動に関するドキュメントの曖昧さがありました。特に、`os/signal` パッケージが提供するシグナルハンドリングのメカニズムと、Goランタイムがデフォルトでどのようにシグナルを扱うかについて、ユーザーが混乱する可能性がありました。

コミットメッセージに「Based on comments from Thomas Bushnell.」とあるように、ユーザーからのフィードバックが変更の直接的なきっかけとなっています。また、「Update #9896.」とあるように、GitHubのIssue #9896（"os/signal: document signal behavior"）で議論されていた内容に対応するものです。このIssueでは、特にプログラム起動時のシグナル無視の挙動や、`os/signal.Notify` を使用した場合のシグナル処理の相互作用について、より明確なドキュメントが求められていました。

Goプログラムは、Unix系のシステムにおいて、デフォルトで多くのシグナルを捕捉しますが、その具体的な挙動はシグナルの種類やプログラムの起動方法によって異なります。この複雑さを正確かつ簡潔に伝えるために、ドキュメントの改善が必要とされていました。特に `SIGPIPE` の挙動は、標準出力/エラーへの書き込みと他のファイルディスクリプタへの書き込みで異なるため、その詳細な説明が求められていました。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

*   **OSシグナル (Unix Signals)**:
    *   OSシグナルは、オペレーティングシステムがプロセスに非同期イベントを通知するためのメカニズムです。例えば、`SIGINT` (Ctrl+C) はプログラムの中断を、`SIGTERM` はプログラムの終了要求を、`SIGHUP` はターミナルの切断や設定ファイルの再読み込みを通知します。
    *   各シグナルにはデフォルトの動作が定義されており、例えば `SIGINT` や `SIGTERM` のデフォルト動作はプロセスを終了させることです。
    *   プログラムはシグナルハンドラを設定することで、特定のシグナルを受信した際のデフォルト動作を変更できます。
    *   `SIG_IGN`: シグナルを無視するように設定する特殊なシグナルハンドラです。
    *   `SIG_DFL`: シグナルハンドラをデフォルトの動作に戻す設定です。
    *   `SIGKILL` と `SIGSTOP` は捕捉したり無視したりできないシグナルです。
*   **Goの `os/signal` パッケージ**:
    *   GoプログラムがOSシグナルと対話するための機能を提供します。
    *   `signal.Notify(c chan os.Signal, sig ...os.Signal)`: 指定されたシグナル（または全てのシグナル）をチャネル `c` に転送するようにGoランタイムに指示します。これにより、Goプログラムはシグナルを同期的に処理できます。
    *   `signal.Stop(c chan os.Signal)`: `Notify` で設定されたシグナル転送を停止します。
    *   Goランタイムは、デフォルトでいくつかのシグナルを特別に扱います。例えば、同期シグナル（`SIGSEGV`など）はGoのパニックに変換され、`SIGPROF` はCPUプロファイリングのためにランタイムが直接処理します。
*   **シグナルマスク (Signal Mask)**:
    *   プロセスが現在ブロックしているシグナルのセットです。ブロックされたシグナルは、ブロックが解除されるまで保留されます。
*   **`SIGPIPE` シグナル**:
    *   プロセスが、読み取り側が閉じられたパイプやソケットに書き込もうとしたときに発生するシグナルです。デフォルトではプロセスを終了させます。Unix系のコマンドラインツールでは、この挙動によりパイプラインの途中でプロセスが終了する際に、後続のプロセスが不要な書き込みを試みないように制御されます。
*   **`glibc` (GNU C Library)**:
    *   多くのLinuxシステムで使用される標準Cライブラリです。内部的に特定のシグナル（`SIGCANCEL`, `SIGSETXID`）を使用することがあります。

## 技術的詳細

このコミットは、`src/os/signal/doc.go` ファイル内のドキュメントを修正し、Goプログラムにおけるシグナル処理の挙動をより正確かつ詳細に記述しています。主な変更点は以下の通りです。

1.  **デフォルトのシグナル無視の明確化**:
    *   変更前: 「Other signals are ignored.」
    *   変更後: 「Other signals will be caught but no action will be taken.」
        *   これは、Goランタイムが他のシグナルを「無視する」のではなく、「捕捉するが、何もアクションを起こさない」というニュアンスの違いを明確にしています。これは、`Notify` が後で呼び出された場合にシグナルを処理できるようにするための重要な区別です。
    *   `SIGHUP` または `SIGINT` が `SIG_IGN` (無視) に設定されて起動された場合の挙動について、「they will remain ignored.」から「(signal handler set to SIG_IGN), they will remain ignored.」と補足が追加され、より具体的な状態が示されています。

2.  **シグナルマスクとサブプロセスへの継承**:
    *   Goプログラムが非空のシグナルマスクで起動された場合、通常はそれが尊重されることが述べられています。
    *   しかし、`SIGILL`, `SIGTRAP`, `SIGSTKFLT`, `SIGCHLD`, `SIGPROF`、およびGNU/Linux上の `SIGCANCEL` (32) と `SIGSETXID` (33) は明示的にブロック解除されることが再確認されています。
    *   重要な追加点として、「Subprocesses started by os.Exec, or by the os/exec package, will inherit the modified signal mask.」という記述が加わりました。これは、Goプログラムが子プロセスを起動する際に、親プロセスの変更されたシグナルマスクが子プロセスに継承されることを明確にし、予期せぬ挙動を防ぐための重要な情報です。

3.  **`Notify` が捕捉するシグナルのリストの更新**:
    *   `Notify` 関数が捕捉するシグナルのリストが更新されました。特に、「otherwise ignored」とされていたシグナルのリストに `SIGCONT` が追加されています。これは、`SIGCONT` がジョブ制御シグナルとして `Notify` で処理可能であることを示唆しています。

4.  **`SIGPIPE` シグナルの詳細な挙動**:
    *   `SIGPIPE` のセクションが大幅に書き直され、その挙動がより詳細かつ正確に説明されています。
    *   変更前は、ファイルディスクリプタ1または2 (標準出力/エラー) への書き込みで `EPIPE` エラーが発生した場合に `SIGPIPE` が発生し、`Notify` で捕捉されていない場合はプログラムが終了するとされていました。他のディスクリプタでは `EPIPE` エラーが返されるとされていました。
    *   変更後では、まず「When a Go program writes to a broken pipe, the kernel will raise a SIGPIPE signal.」と一般的な発生条件が述べられています。
    *   次に、`Notify` が `SIGPIPE` を受信するように設定されていない場合の挙動が、ファイルディスクリプタ1または2の場合とそれ以外の場合で明確に区別されています。
        *   FD 1または2への書き込み: プログラムは `SIGPIPE` シグナルで終了します。
        *   その他のFDへの書き込み: `SIGPIPE` シグナルに対してアクションは取られず、書き込みは `EPIPE` エラーで失敗します。
    *   `Notify` が `SIGPIPE` を受信するように設定されている場合、ファイルディスクリプタの番号に関わらず、`SIGPIPE` シグナルは `Notify` チャネルに配信され、書き込みは `EPIPE` エラーで失敗することが明確にされました。
    *   これにより、「デフォルトでは、コマンドラインプログラムは典型的なUnixコマンドラインプログラムのように振る舞い、他のプログラムは閉じられたネットワーク接続への書き込み時に `SIGPIPE` でクラッシュしない」という結論がより論理的に導かれています。

これらの変更は、Goプログラムがシグナルをどのように扱うかについての開発者の理解を深め、シグナル関連のバグや予期せぬ挙動を避けるのに役立ちます。

## コアとなるコードの解説

このコミットは、Goの `os/signal` パッケージのドキュメント `src/os/signal/doc.go` を修正するものであり、実際のGoランタイムのコードや `os/signal` パッケージの関数実装自体を変更するものではありません。したがって、「コアとなるコードの変更箇所」はドキュメントのテキストそのものであり、「コアとなるコードの解説」は、そのドキュメントの変更が何を意味し、なぜ重要なのかを説明することになります。

変更されたドキュメントの各セクションは、Goプログラムがシグナルをどのように扱うかについて、開発者により正確な理解を提供します。

1.  **「Other signals will be caught but no action will be taken.」**:
    *   これは、Goランタイムが `SIGINT` や `SIGTERM` のような特定のシグナル以外にも、多くのシグナルを内部的に捕捉していることを示唆しています。しかし、これらのシグナルに対してデフォルトでは特別な処理を行わない、という意味です。これは、`signal.Notify` が後で呼び出された場合に、これらのシグナルをチャネルに転送してユーザーコードで処理できるようにするための基盤となります。もし完全に「ignored」であれば、`Notify` で後から捕捉することが難しくなる可能性があります。

2.  **「If the Go program is started with either SIGHUP or SIGINT ignored (signal handler set to SIG_IGN), they will remain ignored.」**:
    *   Goプログラムが起動する前に、シェルなどの親プロセスによって `SIGHUP` や `SIGINT` のシグナルハンドラが `SIG_IGN` に設定されていた場合、Goランタイムはその設定を尊重し、これらのシグナルを無視し続けることを明確にしています。これは、Goプログラムが既存の環境設定を不必要に上書きしないという原則を示しています。

3.  **「Subprocesses started by os.Exec, or by the os/exec package, will inherit the modified signal mask.」**:
    *   これは非常に重要な追加情報です。Goプログラムが `os.Exec` や `os/exec` パッケージを使って子プロセスを起動する場合、親プロセスで変更されたシグナルマスク（どのシグナルがブロックされているか）が子プロセスに継承されることを明示しています。これにより、子プロセスが予期せぬシグナル処理の挙動を示す可能性を開発者が考慮できるようになります。例えば、親プロセスで特定のシグナルをブロックしていた場合、子プロセスもそのシグナルをブロックした状態で起動するため、子プロセスがそのシグナルを処理できない可能性があります。

4.  **`Notify` が捕捉するシグナルリストへの `SIGCONT` の追加**:
    *   `SIGCONT` は、停止したプロセスを再開させるためのシグナルです。このシグナルが `Notify` で捕捉可能であることが明記されたことで、Goプログラムがジョブ制御のシナリオにおいて、より柔軟な対応ができる可能性を示しています。例えば、バックグラウンドで動作するサービスが `SIGSTOP` で一時停止された後、`SIGCONT` で再開された際に、そのイベントをGoプログラム内で検知し、適切な処理を行うことができるようになります。

5.  **`SIGPIPE` シグナルの詳細な解説**:
    *   このセクションの変更は、`SIGPIPE` の挙動に関する最も重要な改善点です。
    *   **`Notify` を呼び出していない場合**:
        *   標準出力/エラー (FD 1または2) への書き込みで `EPIPE` が発生した場合にプログラムが `SIGPIPE` で終了する挙動は、Unixコマンドラインツールの標準的な動作と一致させ、パイプライン処理の整合性を保つためです。
        *   他のファイルディスクリプタへの書き込みで `EPIPE` が発生した場合に `SIGPIPE` が発生してもアクションは取られず、書き込みが `EPIPE` エラーで失敗する挙動は、ネットワーク接続など、パイプラインとは異なるコンテキストでの `SIGPIPE` による予期せぬクラッシュを防ぐためです。これにより、開発者は `EPIPE` エラーを通常のI/Oエラーとして処理できます。
    *   **`Notify` を呼び出している場合**:
        *   ファイルディスクリプタの番号に関わらず、`SIGPIPE` は `Notify` チャネルに配信され、書き込みは `EPIPE` エラーで失敗します。これは、開発者が `SIGPIPE` イベントを明示的に処理したい場合に、一貫したメカニズムを提供します。

これらのドキュメントの変更は、Goプログラムのシグナル処理の挙動に関する誤解を減らし、より堅牢で予測可能なアプリケーションを構築するための重要な情報を提供します。

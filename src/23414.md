# [インデックス 23414] ファイルの概要

このコミットは、Go言語の公式仕様書 `doc/go_spec.html` における二項演算子（binary expression）の文法規則の誤りを修正するものです。具体的には、演算子の優先順位に関する記述と文法規則が矛盾しており、`1 + 2 * 3` のような式が `(1 + 2) * 3` と誤って解釈される可能性があった問題を解決しています。この修正により、仕様書が実際のGoコンパイラの動作（`cmd/internal/gc/go.y` の文法）と一致するようになります。

## 変更の背景

Go言語の仕様書には、演算子の優先順位に関する明確な記述があります。例えば、乗算（`*`）は加算（`+`）よりも高い優先順位を持つため、`1 + 2 * 3` という式は `1 + (2 * 3)` と解釈され、結果は `7` となるべきです。しかし、このコミット以前の仕様書に記載されていた二項演算子の文法規則は、この優先順位のルールと矛盾していました。

具体的には、古い文法規則では `Expression = UnaryExpr | Expression binary_op UnaryExpr .` と定義されており、これにより `1 + 2 * 3` のような式が `(1 + 2) * 3` のように、左から右へと単純に結合されてしまう可能性がありました。これは、仕様書内の演算子優先順位のセクションで説明されている意図された動作と一致しませんでした。

この矛盾は、言語の仕様と実際のコンパイラの動作との間に不整合を生じさせる可能性があり、開発者がGo言語の式をどのように解釈すべきかについて混乱を招く恐れがありました。そのため、仕様書を正確にし、Goコンパイラ（`cmd/internal/gc/go.y`）の実際の文法定義と一致させるために、この修正が行われました。

## 前提知識の解説

### 1. プログラミング言語の文法と構文解析

プログラミング言語は、特定の規則に従って記述されます。これらの規則は「文法（Grammar）」と呼ばれ、通常、EBNF（Extended Backus-Naur Form）のような形式で記述されます。コンパイラやインタプリタは、この文法に基づいてソースコードを「構文解析（Parsing）」し、プログラムの構造を理解します。

### 2. EBNF (Extended Backus-Naur Form)

EBNFは、プログラミング言語の文法を記述するためのメタ言語です。以下に基本的な記法を示します。

*   `=`：定義
*   `|`：選択（OR）
*   `.`：規則の終端
*   `Expr = Term | Expr "+" Term .`：`Expr` は `Term` または `Expr` の後に `+` と `Term` が続くもの。これは左再帰と呼ばれ、左結合性を表現するのに使われます。
*   `{ ... }`：0回以上の繰り返し
*   `[ ... ]`：0回または1回（オプション）

### 3. 演算子の優先順位 (Operator Precedence)

プログラミング言語において、複数の演算子を含む式が評価される際、どの演算子が先に実行されるかを決定する規則です。例えば、数学と同様に、乗算（`*`）や除算（`/`）は加算（`+`）や減算（`-`）よりも優先されます。
例: `1 + 2 * 3` は `1 + (2 * 3)` と解釈され、結果は `7` となります。

### 4. 演算子の結合性 (Operator Associativity)

同じ優先順位を持つ複数の演算子が連続して現れた場合に、左から右、または右から左のどちらに結合されるかを決定する規則です。
例:
*   左結合性: `a - b - c` は `(a - b) - c` と解釈されます。
*   右結合性: `a = b = c` は `a = (b = c)` と解釈されます（代入演算子など）。

### 5. 文法における優先順位の表現

EBNFのような文法規則で演算子の優先順位を表現するには、通常、異なる優先順位レベルごとに非終端記号（`Expression`, `Term`, `Factor` など）を導入し、より優先順位の低い規則がより優先順位の高い規則を参照するように階層構造を構築します。

例:
```ebnf
Expression = Term | Expression "+" Term .  // 加算・減算 (低優先順位)
Term       = Factor | Term "*" Factor .   // 乗算・除算 (高優先順位)
Factor     = Number | "(" Expression ")" . // 最も高優先順位 (括弧、リテラル)
```
この構造により、`1 + 2 * 3` は `Expression` -> `Term` -> `Factor` の順に解析され、`*` が `+` よりも先に評価されることが保証されます。

### 6. `UnaryExpr` と `Expression` の違い

*   `UnaryExpr` (単項式): 単項演算子（例: `-x`, `!b`）が適用される式、または単にプライマリ式（リテラル、変数など）を指します。これは通常、二項演算子よりも高い優先順位を持ちます。
*   `Expression` (式): より広範な概念で、単項式、二項式、関数呼び出しなど、あらゆる種類の式を含みます。

## 技術的詳細

このコミットの核心は、Go言語仕様のEBNF文法規則における `Expression` の定義変更です。

**変更前:**
`Expression = UnaryExpr | Expression binary_op UnaryExpr .`

この規則は、`Expression` が `UnaryExpr` であるか、または `Expression` の後に `binary_op` と `UnaryExpr` が続くものであると定義しています。この定義の問題点は、二項演算子の右オペランドが常に `UnaryExpr` に限定されている点です。

例えば、`1 + 2 * 3` という式を考えてみましょう。
1.  `1` は `UnaryExpr` です。
2.  `2` は `UnaryExpr` です。
3.  `3` は `UnaryExpr` です。
4.  `2 * 3` を解析しようとすると、`*` は `binary_op` です。
    *   もし `2` が `Expression` で、`3` が `UnaryExpr` と解釈されると、`2 * 3` は `Expression binary_op UnaryExpr` の形式に合致します。
    *   しかし、`1 + (2 * 3)` のように `(2 * 3)` 全体を一つの `UnaryExpr` として扱うことは、この規則だけでは困難です。

この規則では、`Expression binary_op UnaryExpr` の部分が左再帰的であるため、左結合性（`A op B op C` が `(A op B) op C` となる）を表現するのに適しています。しかし、異なる優先順位の演算子を正しく扱うためには、より優先順位の高い演算子によって形成される部分式が、より優先順位の低い演算子のオペランドとして適切に扱われる必要があります。

古い規則では、`Expression binary_op UnaryExpr` の右側が `UnaryExpr` に固定されているため、`*` のような高優先順位の演算子によって形成された `(2 * 3)` のような部分式が、`+` のような低優先順位の演算子の右オペランドとして適切に「より高い優先順位を持つ式」として認識されにくい構造になっていました。結果として、`1 + 2 * 3` が `(1 + 2) * 3` と解釈される可能性が生じていました。これは、`+` と `*` の優先順位が異なるという仕様書の記述と矛盾します。

**変更後:**
`Expression = UnaryExpr | Expression binary_op Expression .`

この変更は、二項演算子の右オペランドが `UnaryExpr` ではなく、より一般的な `Expression` になれるように修正しています。この一見小さな変更が、演算子の優先順位を文法レベルで正しく表現するために非常に重要です。

この新しい規則は、Goコンパイラが内部で使用している文法（`cmd/internal/gc/go.y`）のパターン、例えば `expr: uexpr | expr LOROR expr | expr LANDAND expr | ...` とより良く一致します。この種の文法は、通常、優先順位の低い演算子（例: `LOROR`, `LANDAND`）が左再帰的に定義され、より優先順位の高い演算子を別の非終端記号（例: `Term` や `Factor`）で表現することで、演算子の優先順位を暗黙的に強制します。

`Expression binary_op Expression` という形式は、より一般的な二項演算子を表現するための基盤となります。実際のGo言語の文法では、`Expression` の定義はさらに細分化され、異なる優先順位レベルの演算子に対応する複数の非終端記号（例: `UnaryExpr`, `MulExpr`, `AddExpr`, `RelExpr`, `AndExpr`, `OrExpr` など）が導入されています。このコミットは、その階層構造の最上位レベルである `Expression` の定義を修正し、より下位の優先順位を持つ `Expression` が、より上位の優先順位を持つ `Expression` をオペランドとして受け入れられるようにすることで、全体として正しい優先順位の評価を可能にするための基礎を築いています。

この修正により、Go言語の仕様書は、演算子の優先順位に関する記述と文法規則の両方で一貫性を保ち、`1 + 2 * 3` のような式が意図通り `1 + (2 * 3)` と解釈されることが保証されます。

## コアとなるコードの解説

変更された行は、Go言語の文法をEBNFで定義している部分です。

**変更前:**
`Expression = UnaryExpr | Expression binary_op UnaryExpr .`

この行は、「式（`Expression`）は、単項式（`UnaryExpr`）であるか、または式（`Expression`）の後に二項演算子（`binary_op`）と単項式（`UnaryExpr`）が続くものである」と定義していました。
問題は、二項演算子の右側のオペランドが `UnaryExpr` に限定されていたことです。これにより、`*` のような高優先順位の演算子によって形成された部分式（例: `2 * 3`）が、`+` のような低優先順位の演算子の右オペランドとして正しく扱われず、優先順位が無視される可能性がありました。

**変更後:**
`Expression = UnaryExpr | Expression binary_op Expression .`

この行は、「式（`Expression`）は、単項式（`UnaryExpr`）であるか、または式（`Expression`）の後に二項演算子（`binary_op`）と**別の式（`Expression`）**が続くものである」と定義を修正しています。
この修正により、二項演算子の右側のオペランドが `UnaryExpr` だけでなく、より一般的な `Expression` になれるようになりました。これにより、`1 + 2 * 3` のような式が解析される際に、`2 * 3` という部分式がまず `Expression` として完全に評価され、その結果が `+` 演算子の右オペランドの `Expression` として渡されることが可能になります。これは、演算子の優先順位を文法レベルで正しく強制するための標準的な方法です。

この変更は、Go言語の仕様書が、言語の実際の動作（特に演算子の優先順位）を正確に反映するようにするための重要な修正です。

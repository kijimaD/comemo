## 変更の背景

このコミットは、GoコンパイラのSSAバックエンドにおけるクリティカルエッジ分割処理の際に発生する特定のコーナーケースに対処するために導入されました。クリティカルエッジを分割する過程で、まれにPhi関数が単一の先行ブロック（predecessor）しか持たない状態になることがあります。SSA形式の厳密な定義では、Phi関数は複数の異なるパスから来る値をマージするために使用されるため、単一の先行ブロックしか持たないPhi関数は冗長であり、SSA形式の整合性を損なう可能性があります。このような状況は、SSA形式のルールに違反し、後続の最適化パスやコード生成に問題を引き起こす可能性があるため、修正が必要でした。この問題はGoのIssue #14857として報告されていました。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化において広く用いられる中間表現（IR）の一種です。その主要な特性は以下の通りです。

*   **静的単一代入**: 各変数はプログラム内で一度だけ代入されます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が容易になります。
*   **Phi関数 (Φ関数)**: 複数の制御フローパスが合流する地点（例えばif-else文の終わりやループの合流点）で、異なるパスから来る同じ論理的な変数の値をマージするために導入されます。Phi関数は、どのパスから来たかによって適切な値を選択します。例えば、`x = Φ(x_1, x_2)` は、パス1を通ってきた場合は `x_1` を、パス2を通ってきた場合は `x_2` を `x` に代入することを意味します。

SSA形式は、デッドコード削除、共通部分式除去、レジスタ割り当てなど、多くの強力な最適化を可能にします。

### 2. クリティカルエッジ (Critical Edges)

制御フローグラフ（CFG）において、クリティカルエッジとは以下の条件を満たすエッジ（辺）を指します。

*   **ソースブロックが複数の後続ブロックを持つ**: エッジの出発点となるブロック（ソースブロック）が、複数の異なるパスに分岐する。
*   **ターゲットブロックが複数の先行ブロックを持つ**: エッジの終点となるブロック（ターゲットブロック）が、複数の異なるパスから合流する。

つまり、「分岐」と「合流」が同時に起こる場所のエッジがクリティカルエッジです。

### 3. クリティカルエッジの分割 (Critical Edge Splitting)

多くのSSA変換アルゴリズムや最適化パスでは、クリティカルエッジが存在すると処理が複雑になったり、正しく機能しなかったりする場合があります。そのため、通常はクリティカルエッジを分割して解消します。

クリティカルエッジの分割は、以下のように行われます。

1.  クリティカルエッジ `A -> B` があるとする（Aは複数の後続を持ち、Bは複数の先行を持つ）。
2.  このエッジの間に新しい空のブロック `C` を挿入します。
3.  エッジは `A -> C -> B` となります。
4.  これにより、`A -> C` は `A` の唯一の後続ブロックではなくなり（`A`は複数の後続を持つ）、`C -> B` は `B` の唯一の先行ブロックではなくなります（`B`は複数の先行を持つ）。結果として、クリティカルエッジは解消されます。

この分割は、Phi関数の挿入や移動、コードの複製などのSSA変換を簡素化するために重要です。

## 技術的詳細

このコミットが対処している問題は、クリティカルエッジ分割の副作用として発生します。`critical.go`内の`critical`関数は、SSA形式の関数内のクリティカルエッジを特定し、それらを分割する役割を担っています。

通常、Phi関数は複数の先行ブロックから値を受け取ることを想定しています。しかし、クリティカルエッジの分割処理が特定の制御フローパターンに適用された場合、結果として生成されたPhi関数が、実際には単一の先行ブロックしか持たない状態になることがあります。

例えば、あるブロック`P`から`B`へのクリティカルエッジ`P -> B`があり、`B`には他の先行ブロック`Q`も存在するとします。`P`はさらに`P -> X`という別のエッジも持っています。`B`には`Phi(v_P, v_Q)`のようなPhi関数が存在します。

クリティカルエッジ`P -> B`が分割され、間に新しいブロック`C`が挿入されると、制御フローは`P -> C -> B`となります。このとき、`B`のPhi関数は`Phi(v_C, v_Q)`のようになるでしょう。しかし、もし`P`が`B`への唯一のパスであり、`Q`が何らかの理由で到達不能になったり、あるいは`critical`関数内の処理の過程で一時的に`B`の先行ブロックリストから削除されたりすると、`B`のPhi関数が`Phi(v_C)`のように単一の引数しか持たない状態になる可能性があります。

SSA形式の原則では、各変数は一度だけ代入されるべきであり、Phi関数は複数の定義をマージする役割を担います。単一の引数しか持たないPhi関数は、実質的にその引数の値をそのまま渡すだけの操作であり、`OpCopy`（コピー命令）に置き換えることができます。これを「Phi関数の除去（Phi elimination）」または「Phiの簡素化」と呼びます。

このコミットは、クリティカルエッジ分割後にこのような「単一引数Phi」が発生した場合に、それを`OpCopy`命令に変換することで、SSA形式の整合性を維持し、冗長なPhi関数を排除することを目的としています。これにより、コンパイラのバックエンドがよりクリーンで効率的なSSA形式で動作し、後続の最適化パスが正しく機能するようになります。

# [インデックス 27792] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）におけるマップキーの型検証ロジックの改善に関するものです。特に、前方参照型（forward types）がマップキーとして使用される際の検証タイミングと厳密性の問題を解決します。以前の実装では、マップキーの検証が複数の場所で行われていましたが、前方参照型に対する扱いが一貫しておらず、最終的な型解決後も不適切な型が許容される可能性がありました。この変更により、前方参照型を含むマップキーの検証が適切に遅延され、型が完全に解決された後に厳密な検証が行われるようになります。

## 元コミット内容

```
cmd/compile: make enqueued map keys fail validation on forward types

Map keys are currently validated in multiple locations but share
a common validation routine. The problem is that early validations
should be lenient enough to allow for forward types while the final
validations should not. The final validations should fail on forward
types since they've already settled.

This change also separates the key type checking from the creation
of the map via typMap. Instead of the mapqueue being populated in
copytype() by checking the map line number, it's populated in the
same block that validates the key type. This isolates key validation
logic while type checking.

Fixes #14988
```

## 変更の背景

Go言語において、マップのキーとして使用できる型には制約があります。具体的には、マップキーは「比較可能（comparable）」でなければなりません。これは、マップがキーの等価性に基づいて値を格納・検索するためです。しかし、Goコンパイラの型チェックプロセスでは、型が完全に解決される前に前方参照（forward declaration）として現れることがあります。

このコミット以前のGoコンパイラでは、マップキーの型検証が複数の段階で行われていましたが、前方参照型に対する扱いが不十分でした。特に、型がまだ完全に解決されていない「前方参照型（TFORW）」の場合、早期の検証ではエラーを報告せず、型解決を待つ必要がありました。しかし、最終的な検証段階で、もし前方参照型が解決された結果、比較不可能な型（例えば配列や構造体など）になっていたとしても、適切にエラーとして扱われないケースが存在しました。

コミットメッセージによると、この問題は「Fixes #14988」として報告されたバグに関連しています。`test/fixedbugs/issue14988.go`のテストケースから、具体的には「無効な前方宣言配列キーを持つマップを定義しても致命的なエラーにならない」という問題であったことが示唆されます。つまり、`type m map[k]int` と `type k [1]m` のように相互参照する型定義で、`k` がマップキーとして不適切な型（配列）であるにも関わらず、コンパイル時にエラーが適切に検出されない状況が発生していました。

このコミットは、このような前方参照型を含むマップキーの検証を、型が完全に解決された後に厳密に行うことで、コンパイラの堅牢性を向上させることを目的としています。

## 前提知識の解説

### Go言語の型システムとマップキーの制約

Go言語のマップ（`map`）は、キーと値のペアを格納するデータ構造です。マップのキーには、その値が比較可能である必要があります。具体的には、以下の型が比較可能です。

*   ブール型
*   数値型（整数型、浮動小数点型、複素数型）
*   文字列型
*   ポインタ型
*   チャネル型
*   インターフェース型（動的な型と値が比較可能であれば）
*   構造体型（すべてのフィールドが比較可能であれば）
*   配列型（すべての要素が比較可能であれば）

一方、スライス、関数、マップ、およびそれらを含む構造体や配列は比較不可能です。

### Goコンパイラの型チェックフェーズ

Goコンパイラは、ソースコードを機械語に変換する過程で複数のフェーズを経ます。型チェックはその重要なフェーズの一つで、プログラムがGo言語の型規則に準拠しているかを確認します。このプロセスでは、型が完全に定義される前に、その型への参照（前方参照）が出現することがあります。コンパイラはこれらの前方参照を一時的に「未解決」として扱い、後続のフェーズで解決します。

### `cmd/compile/internal/gc` パッケージ

Goコンパイラの主要な部分を構成するパッケージです。`gc`は「Go Compiler」の略で、型チェック、AST（抽象構文木）の操作、コード生成など、コンパイルの多くの段階を処理します。

*   **`typecheck.go`**: 型チェックの主要なロジックが含まれています。ASTノードを走査し、各ノードの型を決定し、型規則に違反がないかを確認します。
*   **`subr.go`**: サブルーチンやユーティリティ関数が含まれています。
*   **`type.go`**: Go言語の型を表すデータ構造と、型を操作する関数が含まれています。

### `algtype1` 関数と `ANOEQ`, `TFORW`, `TANY`

Goコンパイラの内部では、型の特性を識別するために特定の定数や関数が使用されます。

*   **`algtype1(key *Type)`**: 型 `key` の比較可能性に関する情報を返す関数です。返り値として、型の比較アルゴリズムを示す値（`alg`）と、比較不可能な型の場合にその原因となる型（`bad`）を返します。
*   **`ANOEQ`**: `algtype1`が返す値の一つで、「比較不可能（No Equality）」を意味します。つまり、この型の値は等価性比較ができません。
*   **`TFORW`**: 「前方参照型（Forward Type）」を意味する`Etype`（Element Type）です。型がまだ完全に定義されていない状態を示します。
*   **`TANY`**: 「任意の型（Any Type）」を意味する`Etype`です。ジェネリックな型パラメータなど、具体的な型がまだ決定されていない状態を示します。

### `mapqueue` と遅延検証

Goコンパイラは、前方参照型のように、その時点では完全な情報がないためにすぐに検証できない型については、その検証を後回しにするメカニズムを持っています。`mapqueue`はそのような遅延検証が必要なマップキーの情報を一時的に保持するためのキューです。型チェックの最終段階で、このキューに格納された情報に基づいて再検証が行われます。

### `Yyerror`

Goコンパイラがエラーメッセージを出力するために使用する関数です。

## 技術的詳細

このコミットの核心は、Goコンパイラがマップキーの型を検証するタイミングと方法を改善することにあります。以前は、`typMap`関数（マップ型を生成する関数）内で`checkMapKeyType`が呼び出され、マップキーの検証が行われていました。しかし、この`checkMapKeyType`は、前方参照型（`TFORW`）の場合にはエラーを報告せず、`maplineno`というグローバルマップにその情報を記録し、`mapqueue`にノードを追加していました。その後、`copytype`関数が型解決を完了した際に、`mapqueue`に格納されたノードに対して再度`checkMapKeyType`を呼び出すことで最終的な検証を行うという流れでした。

このアプローチの問題点は、`checkMapKeyType`が前方参照型に対して「寛容」である一方で、最終的な検証も同じルーチンで行われるため、型が解決された後も不適切な型がエラーとして検出されない可能性があったことです。また、`mapqueue`への追加ロジックが`copytype`内にあり、マップの行番号をチェックするという間接的な方法で制御されていたため、マップキーの検証ロジックが分散し、理解しにくい状態でした。

このコミットでは、以下の主要な変更が導入されました。

1.  **`checkMapKeyType`関数の削除**: `src/cmd/compile/internal/gc/subr.go`から`checkMapKeyType`関数が完全に削除されました。これにより、マップキーの検証ロジックが`typMap`から切り離されます。
2.  **`typMap`からの検証呼び出しの削除**: `src/cmd/compile/internal/gc/type.go`の`typMap`関数から、`checkMapKeyType(k)`の呼び出しが削除されました。
3.  **`typecheck.go`への検証ロジックの集約と遅延検証の改善**:
    *   マップ型が構築される`typecheck.go`内の`OCOMPLEX`ケース（`typMap`が呼び出される場所）に、マップキーの初期検証ロジックが直接組み込まれました。
    *   ここで`algtype1(l.Type)`を呼び出し、キー型が比較不可能（`alg == ANOEQ`）であるかをチェックします。
    *   もしキー型が前方参照型（`bad.Etype == TFORW`）であれば、そのマップノードと行番号を`mapqueue`に追加し、検証を遅延させます。
    *   前方参照型ではないが比較不可能な型（`bad.Etype != TANY`）であれば、即座に`Yyerror`でエラーを報告します。これにより、早期に明確なエラーを出すことができます。
    *   `mapqueue`の型が`[]*Node`から`[]mapqueueval`に変更されました。`mapqueueval`は、マップノードと、そのマップが定義された行番号（`lno`）を保持する新しい構造体です。これにより、エラー報告時の行番号情報がより正確になります。
    *   `copytype`関数内の`mapqueue`への追加ロジックが削除されました。
    *   型チェックの最終段階で実行される`typecheck.go`内のループが変更され、`mapqueue`内の各要素（`mapqueueval`）に対して、`e.n.Type.IsComparable()`を呼び出して最終的な比較可能性チェックを行います。ここで比較不可能であれば、`Yyerror`でエラーを報告します。この`IsComparable()`は、型が完全に解決された後の厳密な比較可能性チェックを行います。

この変更により、マップキーの検証ロジックが`typecheck.go`に集約され、前方参照型に対する検証が、型が完全に解決された後に厳密に行われるようになりました。これにより、`issue14988`のような、前方参照型が不適切なマップキーとして使用された場合にエラーが検出されない問題が解決されます。

## コアとなるコードの変更箇所

### `src/cmd/compile/internal/gc/subr.go`

*   `checkMapKeyType`関数が完全に削除されました。この関数は、マップキーの比較可能性をチェックし、前方参照型の場合は検証を遅延させる役割を担っていました。

### `src/cmd/compile/internal/gc/type.go`

*   `typMap`関数（マップ型を構築する関数）から、削除された`checkMapKeyType(k)`の呼び出しが削除されました。これにより、マップキーの検証ロジックが`typMap`から完全に切り離されました。

### `src/cmd/compile/internal/gc/typecheck.go`

*   **`OCOMPLEX`ケース内の変更**: マップ型が構築される箇所（`n.Op = OTYPE; n.Type = typMap(l.Type, r.Type)`の後）に、新しいマップキー検証ロジックが追加されました。
    *   `algtype1(l.Type)`を呼び出してキー型の比較可能性をチェックします。
    *   キー型が比較不可能（`alg == ANOEQ`）かつ前方参照型（`bad.Etype == TFORW`）の場合、`mapqueue`に`mapqueueval{l, n.Lineno}`を追加して検証を遅延させます。
    *   キー型が比較不可能（`alg == ANOEQ`）かつ前方参照型でも`TANY`でもない場合、即座に`Yyerror`でエラーを報告します。
*   **`mapqueue`の定義変更**:
    *   `mapqueue`の型が`[]*Node`から`[]mapqueueval`に変更されました。
    *   `mapqueueval`は、`*Node`と`int32`（行番号）を保持する新しい構造体として定義されました。
    *   `maplineno`グローバルマップが削除されました。
*   **`copytype`関数内の変更**:
    *   `mapline := maplineno[n.Type]`および`mapqueue = append(mapqueue, n)`といった、`mapqueue`への追加と`maplineno`の操作に関するロジックが削除されました。
*   **最終検証ループの変更**:
    *   型チェックの最終段階で実行されるループが、新しい`mapqueueval`の要素を処理するように変更されました。
    *   `for _, e := range mapqueue`として`mapqueueval`の要素`e`を走査します。
    *   `lineno = e.lno`で正確な行番号を設定します。
    *   `!e.n.Type.IsComparable()`を呼び出して、解決されたキー型が比較可能であるかを厳密にチェックします。
    *   比較不可能であれば、`Yyerror("invalid map key type %v", e.n.Type)`でエラーを報告します。
    *   ループの最後に`mapqueue = nil`でキューをクリアします。

### `test/fixedbugs/issue14988.go`

*   新しいテストファイルが追加されました。このテストは、前方参照型を含む無効なマップキー定義が適切にエラーとして検出されることを確認します。

## コアとなるコードの解説

このコミットの主要な変更は、マップキーの型検証を、型が完全に解決されるまで遅延させ、その後に厳密な比較可能性チェックを行う点にあります。

1.  **`checkMapKeyType`の廃止と検証ロジックの移動**:
    以前は`subr.go`にあった`checkMapKeyType`関数が削除され、そのロジックが`typecheck.go`内のマップ型構築箇所に移動されました。これにより、マップキーの検証がマップ型が最初に認識される場所で直接処理されるようになります。

2.  **`mapqueueval`構造体の導入**:
    `mapqueue`が`[]*Node`から`[]mapqueueval`に変更されたことで、遅延検証が必要なマップキーの情報がよりリッチになりました。`mapqueueval`は、問題のマップノード（`*Node`）だけでなく、そのマップがソースコードのどの行で定義されたかを示す行番号（`lno`）も保持します。これにより、最終的なエラー報告時に正確な位置情報を提供できるようになります。

3.  **遅延検証のフロー**:
    *   **初期チェック（`typecheck.go`の`OCOMPLEX`内）**:
        マップ型が初めて構築される際、コンパイラはまず`algtype1(l.Type)`を使ってキー型`l.Type`の比較可能性を評価します。
        *   もしキー型が比較不可能（`alg == ANOEQ`）で、かつそれが前方参照型（`bad.Etype == TFORW`）である場合、コンパイラはすぐにエラーを報告せず、`mapqueue`に`mapqueueval{l, n.Lineno}`を追加します。これは、「このキー型は今はまだ解決されていないが、後で厳密にチェックする必要がある」というマーク付けです。
        *   もしキー型が比較不可能（`alg == ANOEQ`）で、かつそれが前方参照型でも`TANY`でもない場合（つまり、最初から明らかに比較不可能な型である場合）、コンパイラは即座に`Yyerror`を呼び出してエラーを報告します。これにより、不必要な遅延を避け、早期にエラーをユーザーに通知できます。
    *   **最終チェック（`typecheck.go`の最終ループ内）**:
        型チェックプロセスの終盤、すべての型が解決された後、コンパイラは`mapqueue`に格納されたすべての`mapqueueval`エントリを走査します。
        *   各`e := range mapqueue`に対して、`e.n.Type.IsComparable()`を呼び出します。この`IsComparable()`メソッドは、型が完全に解決された状態での厳密な比較可能性を判断します。
        *   もし`IsComparable()`が`false`を返した場合（つまり、解決されたキー型が比較不可能であった場合）、`Yyerror`を呼び出して「invalid map key type」エラーを報告します。この時点で、前方参照型はすでに解決されているため、その最終的な特性に基づいて正確な検証が行われます。

この新しいアプローチにより、Goコンパイラは前方参照型を含むマップキーの検証をより正確かつ効率的に行えるようになり、開発者がGo言語の型規則に違反するコードを記述した場合に、より適切なタイミングで明確なエラーメッセージを提供できるようになりました。

# [インデックス 24641] ファイルの概要

このコミットは、GoツールチェーンにおけるmacOS (OS X) 上でのcgoを使用したバイナリの不必要な再ビルド問題を修正します。具体的には、外部リンキングを使用する際にMach-Oバイナリのテキストセグメントの開始位置が通常よりも後方にずれることに対応し、ビルドIDの読み取りロジックを改善しています。

## コミット

`cmd/go`: OS X上でcgoを使用するバイナリの不必要な再ビルドを修正

外部リンキングを使用する際、macOS上ではバイナリのテキストセグメントがより後方から開始します。これをテストし、修正します。

Fixes #12173.

## 変更の背景

Goのビルドシステムは、バイナリが変更されていない場合に不必要な再ビルドを避けるために「ビルドID」を使用します。ビルドIDは、バイナリの特定のセクションに埋め込まれたハッシュ値であり、ソースコードやビルド環境の変更を反映します。`go build`コマンドは、ビルドIDを比較することで、既存のバイナリが最新の状態であるかどうかを判断します。

このコミットが修正しようとしている問題は、macOS (当時のOS X) 上でcgo（GoとC言語の相互運用機能）を使用し、かつ外部リンキング（`linkmode=external`）を行ったGoプログラムにおいて、バイナリの内容が実際には変更されていないにもかかわらず、`go build`が常にバイナリを再ビルドしてしまうというものでした。これは「spurious rebuild」（不必要な再ビルド）と呼ばれ、開発者のビルド時間を無駄に消費する原因となります。

根本的な原因は、GoツールチェーンがバイナリからビルドIDを読み取る際に、Mach-O形式のバイナリ（macOSの実行可能ファイル形式）の構造に関する誤った仮定をしていたことにありました。特に、外部リンキングを使用すると、バイナリの「テキストセグメント」（実行可能なコードが含まれる部分）の開始位置が、GoツールチェーンがビルドIDを探し始めるデフォルトの範囲よりも後方にずれることが判明しました。これにより、ビルドIDが正しく読み取れず、常にバイナリが変更されたと誤認され、不必要な再ビルドが引き起こされていました。

この問題はGo issue #12173として報告され、このコミットによって解決されました。

## 前提知識の解説

### GoのビルドID

GoのビルドIDは、Goプログラムのビルド時に生成される一意の識別子です。これは、コンパイルされたバイナリに埋め込まれ、そのバイナリがどのソースコード、どのコンパイラバージョン、どのビルドフラグでビルドされたかといった情報を含みます。`go build`コマンドは、このビルドIDを利用して、依存関係の変更がない限り、既にビルドされたパッケージやバイナリを再利用し、ビルド時間を短縮します。ビルドIDが一致しない場合、Goツールチェーンはバイナリが変更されたと判断し、再ビルドを実行します。

### cgo

cgoは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。cgoを使用すると、Goの標準ライブラリでは提供されていないOS固有の機能や、既存のCライブラリをGoアプリケーションに統合できます。cgoを使用するプログラムは、GoコンパイラとCコンパイラ（通常はGCCやClang）の両方によって処理され、最終的にリンクされて一つの実行可能ファイルが生成されます。

### 外部リンキング (`linkmode=external`)

Goのリンカーには、主に「内部リンキング」と「外部リンキング」の2つのモードがあります。

*   **内部リンキング (internal linking)**: GoのリンカーがGoのオブジェクトファイルと、Goが提供するCライブラリ（例えば、`net`パッケージが使用するDNSリゾルバなど）を直接リンクするモードです。これはGoのデフォルトのリンキングモードであり、通常は最も高速で、生成されるバイナリも完全に自己完結型になります。
*   **外部リンキング (external linking)**: `go build -ldflags="-linkmode=external"` のように指定することで有効になります。このモードでは、GoのリンカーはGoのオブジェクトファイルを生成するだけで、最終的なリンクはシステムのCリンカー（通常は`gcc`や`clang`）に委ねられます。cgoを使用するプログラムでは、CコードがシステムのCライブラリに依存する場合や、特定のリンカーフラグが必要な場合に外部リンキングが強制されることがあります。外部リンキングは、特にmacOSのようなシステムで、Cライブラリとの複雑な相互作用がある場合に必要となることがあります。

外部リンキングを使用すると、Goのリンカーがバイナリの最終的なレイアウトを完全に制御できないため、ビルドIDの埋め込みや読み取りのロジックに影響を与える可能性があります。

### Mach-Oバイナリフォーマット

Mach-O (Mach Object) は、macOS、iOS、watchOS、tvOSなどのApple製オペレーティングシステムで使用される実行可能ファイル、オブジェクトファイル、共有ライブラリ、およびコアダンプのファイル形式です。Mach-Oファイルは、ヘッダ、ロードコマンド、およびセグメント（テキストセグメント、データセグメントなど）で構成されます。

### テキストセグメント

テキストセグメントは、実行可能ファイル内でプログラムの実行可能な機械語コードが格納される部分です。通常、このセグメントは読み取り専用としてマークされ、複数のプロセス間で共有されることがあります。GoのビルドIDは、このテキストセグメントの開始付近、またはヘッダ領域の特定の場所に埋め込まれることが一般的です。

## 技術的詳細

このコミットの技術的詳細な修正は、主にGoツールチェーンがバイナリからビルドIDを検索する方法の改善にあります。

1.  **ビルドID検索範囲の拡大**:
    `ReadBuildIDFromBinary`関数は、バイナリファイルからビルドIDを読み取るために、ファイルの先頭から一定量のデータを読み込みます。以前は8KB (8192バイト) を読み込んでいましたが、このコミットではこれを16KB (16 * 1024バイト) に倍増させました。
    この変更の理由は、macOS上で外部リンキングを使用する際に、Mach-Oバイナリのテキストセグメントが、Goツールチェーンが想定していたよりもファイルの後方から開始することがあるためです。ビルドIDは通常、テキストセグメントの開始付近に埋め込まれるため、検索範囲を広げることで、ビルドIDが読み取り範囲外になることを防ぎます。

2.  **Mach-Oテキストセグメントオフセットの更新**:
    `pkg.go`内のコメントには、各OSにおける`hello`ワールドプログラムのテキストセグメントの開始オフセットの例が記載されています。このコミットでは、Mach-Oのオフセットが`0x1000`から`0x2000`に更新されました。これは、外部リンキングを使用した場合にテキストセグメントが実際に`0x2000`（8KB）のオフセットから開始する可能性があることを示唆しています。この情報は、ビルドIDの検索範囲を決定する上での根拠となります。

3.  **テストケースの追加**:
    `note_test.go`に新しいテストケースが追加されました。このテストは、`linkmode=external`フラグを使用してバイナリをビルドし、そのバイナリからビルドIDが正しく読み取れることを検証します。特に、macOSのような外部リンキングが問題を引き起こす可能性のある環境で、この修正が正しく機能することを確認するために重要です。Plan 9システムでは外部リンキングの概念がないため、このテストはスキップされます。

これらの変更により、GoツールチェーンはmacOS上の外部リンキングされたcgoバイナリからビルドIDを確実に読み取れるようになり、不必要な再ビルドが解消されます。

### テキストセグメント

テキストセグメントは、実行可能ファイル内でプログラムの実行可能な機械語コードが格納される部分です。通常、このセグメントは読み取り専用としてマークされ、複数のプロセス間で共有されることがあります。GoのビルドIDは、このテキストセグメントの開始付近、またはヘッダ領域の特定の場所に埋め込まれることが一般的です。

## 技術的詳細

このコミットの技術的詳細な修正は、主にGoツールチェーンがバイナリからビルドIDを検索する方法の改善にあります。

1.  **ビルドID検索範囲の拡大**:
    `ReadBuildIDFromBinary`関数は、バイナリファイルからビルドIDを読み取るために、ファイルの先頭から一定量のデータを読み込みます。以前は8KB (8192バイト) を読み込んでいましたが、このコミットではこれを16KB (16 * 1024バイト) に倍増させました。
    この変更の理由は、macOS上で外部リンキングを使用する際に、Mach-Oバイナリのテキストセグメントが、Goツールチェーンが想定していたよりもファイルの後方から開始することがあるためです。ビルドIDは通常、テキストセグメントの開始付近に埋め込まれるため、検索範囲を広げることで、ビルドIDが読み取り範囲外になることを防ぎます。

2.  **Mach-Oテキストセグメントオフセットの更新**:
    `pkg.go`内のコメントには、各OSにおける`hello`ワールドプログラムのテキストセグメントの開始オフセットの例が記載されています。このコミットでは、Mach-Oのオフセットが`0x1000`から`0x2000`に更新されました。これは、外部リンキングを使用した場合にテキストセグメントが実際に`0x2000`（8KB）のオフセットから開始する可能性があることを示唆しています。この情報は、ビルドIDの検索範囲を決定する上での根拠となります。

3.  **テストケースの追加**:
    `note_test.go`に新しいテストケースが追加されました。このテストは、`linkmode=external`フラグを使用してバイナリをビルドし、そのバイナリからビルドIDが正しく読み取れることを検証します。特に、macOSのような外部リンキングが問題を引き起こす可能性のある環境で、この修正が正しく機能することを確認するために重要です。Plan 9システムでは外部リンキングの概念がないため、このテストはスキップされます。

これらの変更により、GoツールチェーンはmacOS上の外部リンキングされたcgoバイナリからビルドIDを確実に読み取れるようになり、不必要な再ビルドが解消されます。

## コアとなるコードの解説

### `src/cmd/go/note_test.go` の変更

*   **`import "runtime"` の追加**: `runtime.GOOS` を使用して現在のオペレーティングシステムを判別するために、`runtime`パッケージがインポートされました。
*   **`switch runtime.GOOS` ブロックの追加**:
    *   `plan9` の場合: Plan 9システムでは外部リンキングの概念がないため、`t.Logf` でテストをスキップする旨のログを出力します。
    *   `default` の場合: Plan 9以外のシステム（macOSを含む）では、以下のテストを実行します。
        *   `tg.run("build", "-ldflags", "-buildid="+buildID+" -linkmode=external", "-o", tg.path("hello.exe"), tg.path("hello.go"))`: `hello.go`というサンプルプログラムを、特定のビルドIDと**外部リンキング (`-linkmode=external`)** を使用してビルドします。これが、このコミットで修正される問題のシナリオを再現する重要な部分です。
        *   `id, err := main.ReadBuildIDFromBinary(tg.path("hello.exe"))`: ビルドされたバイナリからビルドIDを読み取ります。
        *   エラーチェックとビルドIDの比較: 読み取ったビルドIDが期待される`buildID`と一致するかどうかを検証します。一致しない場合はテストが失敗し、問題が解決されていないことを示します。

このテストケースの追加により、外部リンキングを使用した場合でもビルドIDが正しく読み取れることが保証され、将来的なリグレッションを防ぐことができます。

### `src/cmd/go/pkg.go` の変更

*   **ビルドID読み取りバッファサイズの変更**:
    *   `- // Read the first 8 kB of the binary file.` から `+ // Read the first 16 kB of the binary file.`
    *   `data := make([]byte, 8192)` から `data := make([]byte, 16*1024)`
    この変更は、バイナリファイルからビルドIDを検索するために読み込むデータの量を8KBから16KBに増やしています。これにより、特にmacOSの外部リンキングされたMach-Oバイナリで、テキストセグメントがファイルのより後方から開始する場合でも、ビルドIDが読み取り範囲内に収まるようになります。

*   **Mach-Oテキストセグメントオフセットのコメント更新**:
    *   `- // Mach-O: 0x1000` から `+ // Mach-O: 0x2000`
    このコメントは、異なるOSにおける典型的な「hello world」バイナリのテキストセグメント開始オフセットの例を示しています。Mach-Oのオフセットが`0x1000`（4KB）から`0x2000`（8KB）に更新されたことは、外部リンキングを使用した場合にテキストセグメントがより後方から開始するという知見を反映しています。この情報は、ビルドIDの検索範囲を決定する上での根拠となり、16KBのバッファサイズが適切であることの裏付けとなります。

これらの変更は、`ReadBuildIDFromBinary`関数が、特にmacOS上の外部リンキングされたバイナリにおいて、ビルドIDを確実に発見できるようにするためのものです。

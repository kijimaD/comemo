## コミット

このコミットは、GoコンパイラのSSAバックエンドにガベージコレクションのライトバリアを実装し、デバッグ機能を強化しました。ライトバリアは、GCがヒープをスキャンしている間にミューテーター（アプリケーションコード）がポインタを書き換えることによって発生する「ポインタの消失」問題を解決するために不可欠です。現時点では `typedmemmove` を使用していますが、将来的には最適化される予定です。

また、コンパイルエラーのバイナリサーチを支援する機能も追加されました。`GOSSAPKG` と `GOSSAHASH` 環境変数を使用することで、特定のパッケージ内の関数を、その関数名のハッシュ値に基づいて選択的にSSAコンパイルできるようになります。これにより、問題のある関数を効率的に特定することが可能になります。

## 変更の背景

### ガベージコレクションのライトバリア実装の背景

Go言語のガベージコレクタ (GC) は、並行 (concurrent) に動作するように設計されています。これは、GCがアプリケーションの実行と同時に動作し、アプリケーションの停止時間 (stop-the-world, STW) を最小限に抑えることを意味します。しかし、並行GCには「ポインタの消失 (pointer loss)」という問題が伴います。

ポインタの消失とは、GCがヒープをスキャンして到達可能なオブジェクトをマークしている最中に、アプリケーション（ミューテーター）がポインタを書き換えることで、GCがまだスキャンしていないオブジェクトへの唯一の参照が失われ、そのオブジェクトが誤って回収されてしまう可能性がある問題です。

この問題を解決するために、ライトバリア (write barrier) が導入されます。ライトバリアは、ミューテーターがヒープ上のポインタを書き換える際に、GCの正確性を保証するための追加の処理を挿入するメカニズムです。GoのGCは、Dijkstraスタイルのライトバリア（またはSnapshot-At-The-Beginning, SATB）を採用しており、ポインタが変更される「前」に、古いポインタが指していたオブジェクトをマークすることで、ポインタの消失を防ぎます。

このコミットは、Goコンパイラの新しいSSAバックエンドが、このライトバリアを正しく生成できるようにするための初期実装です。SSAバックエンドはGo 1.7で導入され、コンパイル時の最適化を大幅に改善しましたが、GCとの連携、特にライトバリアの生成は複雑な課題でした。

### SSAデバッグ機能追加の背景

GoコンパイラのSSAバックエンドは、高度な最適化を可能にする一方で、その複雑さゆえにデバッグが困難になることがあります。特に、新しいSSAバックエンドが導入された初期段階では、特定のコードパターンが誤ったコードを生成したり、予期せぬバグを引き起こしたりする可能性がありました。

このようなコンパイル時のバグを特定する際、どの関数が問題の原因となっているのかを突き止めるのは非常に骨の折れる作業です。通常、問題は特定の関数内のSSA生成コードに起因しますが、数千もの関数がある大規模なプログラム全体をSSAでコンパイルしてテストするのは非効率的です。

そこで、このコミットでは、問題のある関数を効率的に「バイナリサーチ」で特定するためのデバッグ機能が追加されました。これにより、開発者は特定のパッケージ内の特定の関数のみをSSAでコンパイルし、それ以外の関数は従来のコンパイラでコンパイルすることで、問題の切り分けを迅速に行えるようになります。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、以下の特徴を持つ並行・世代別・三色マーク＆スイープGCです。

*   **並行性 (Concurrency)**: GCの大部分はアプリケーションの実行と並行して動作します。これにより、アプリケーションの応答性が向上し、レイテンシが低減されます。
*   **三色マーク＆スイープ (Tri-color Mark-and-Sweep)**:
    *   **白 (White)**: GCによってまだ発見されていないオブジェクト、または到達不可能と判断されたオブジェクト。最終的に回収されます。
    *   **灰 (Gray)**: GCによって発見されたが、そのオブジェクトが参照する他のオブジェクトがまだスキャンされていないオブジェクト。
    *   **黒 (Black)**: GCによって発見され、そのオブジェクトが参照するすべてのオブジェクトもスキャン済みのオブジェクト。
    GCは、ルートセット（グローバル変数、スタック上の変数など）から開始し、到達可能なオブジェクトを白から灰へ、そして灰から黒へとマークしていきます。
*   **ライトバリア (Write Barrier)**: 並行GCにおいて、ミューテーターがポインタを書き換える際にGCの正確性を保証するためのメカニズムです。GoのGCは、Dijkstraスタイルのライトバリア（またはSATB: Snapshot-At-The-Beginning）を採用しています。これは、ポインタが変更される「前」に、古いポインタが指していたオブジェクトをマークすることで、GCがそのオブジェクトを回収しないようにします。

### SSA (Static Single Assignment) 形式

SSA (Static Single Assignment) 形式は、コンパイラの最適化段階で用いられる中間表現 (Intermediate Representation, IR) の一種です。

*   **特徴**: SSA形式では、各変数がプログラム内で一度だけ代入されるという特性を持ちます。もし同じ変数に複数回代入が行われる場合、SSA形式ではその代入ごとに新しいバージョンの変数が導入されます（例: `x1 = ...`, `x2 = ...`）。複数の制御フローパスが合流する点では、`φ` (phi) 関数と呼ばれる特殊な命令が導入され、どのパスから来た値を使用するかを決定します。
*   **利点**:
    *   **データフロー解析の容易さ**: 変数の定義と使用の関係が明確になるため、データフロー解析が非常に容易になります。
    *   **最適化の効率化**: 共通部分式除去 (Common Subexpression Elimination, CSE)、定数伝播 (Constant Propagation)、デッドコード除去 (Dead Code Elimination, DCE) など、多くのコンパイラ最適化がSSA形式上で効率的に実装できます。
*   **GoコンパイラにおけるSSA**: Go 1.7から、コンパイラのバックエンドがSSA形式に移行しました。これにより、生成されるコードの品質が向上し、実行速度が改善されました。

### `typedmemmove` と `typedmemmove_nostore`

これらはGoランタイムに存在する、型情報に基づいてメモリを操作する関数です。

*   **`typedmemmove(typ *byte, dst, src unsafe.Pointer)`**:
    *   `typ`: 移動するデータの型情報 (`_type` 構造体へのポインタとして扱われる)。
    *   `dst`: データのコピー先アドレス。
    *   `src`: データのコピー元アドレス。
    *   この関数は、`src` から `dst` へメモリをコピーする際に、`typ` で指定された型情報に基づいて、コピーされるデータ内にポインタが含まれているかどうかを判断します。ポインタが含まれている場合、GCのライトバリアを適用し、GCがポインタの変更を正しく追跡できるようにします。これは、構造体や配列などの複合型をコピーする際に特に重要です。
*   **`typedmemmove_nostore(typ *byte, dst unsafe.Pointer)`**:
    *   このコミットで追加された関数です。
    *   `typ`: 移動するデータの型情報。
    *   `dst`: データの宛先アドレス。
    *   `typedmemmove` とは異なり、この関数自体はメモリのコピー（ストア操作）を行いません。その代わり、`dst` にポインタが書き込まれる「前」に、GCのライトバリア処理のみを実行します。これは、SSAバックエンドが既にストア操作自体を生成している場合に、GCのライトバリア処理だけを追加するために使用されます。例えば、スタック上のオブジェクトの移動や、特定のレジスタへのポインタのロードなど、ストア操作を伴わないがGCの観点からはポインタの変更と見なされるような状況で利用されます。

## 技術的詳細

### ライトバリアのSSA実装

このコミットの主要な技術的詳細は、GoコンパイラのSSAバックエンドがライトバリアをどのように生成するかという点にあります。

1.  **`assign` 関数におけるライトバリアの挿入**:
    `src/cmd/compile/internal/gc/ssa.go` 内の `(s *state) assign(left *Node, right *ssa.Value, wb bool)` 関数が変更されました。この関数は、Goの代入操作をSSA形式に変換する役割を担っています。`wb` (write barrier) 引数が `true` の場合、代入操作に加えてライトバリアのコードが挿入されるようになりました。

    具体的には、`left` に `right` の値がストアされた後、以下の条件付きコードがSSAによって生成されます。

    ```go
    if wb {
        // if writeBarrierEnabled {
        //   typedmemmove_nostore(t, &l)
        // }
        bThen := s.f.NewBlock(ssa.BlockPlain)
        bNext := s.f.NewBlock(ssa.BlockPlain)

        // writeBarrierEnabled フラグをロード
        aux := &ssa.ExternSymbol{Types[TBOOL], syslook("writeBarrierEnabled", 0).Sym}
        flagaddr := s.newValue1A(ssa.OpAddr, Ptrto(Types[TBOOL]), aux, s.sb)
        flag := s.newValue2(ssa.OpLoad, Types[TBOOL], flagaddr, s.mem())

        // 条件分岐 (writeBarrierEnabled が true の場合のみ実行)
        b := s.endBlock()
        b.Kind = ssa.BlockIf
        b.Likely = ssa.BranchUnlikely // ライトバリアは通常は実行されないため、Unlikely
        b.Control = flag
        b.AddEdgeTo(bThen)
        b.AddEdgeTo(bNext)

        s.startBlock(bThen)
        // NOTE: there must be no GC suspension points between the write above
        // (the OpStore) and this call to typedmemmove_nostore.
        // TODO: writebarrierptr_nostore if just one pointer word (or a few?)

        // typedmemmove_nostore の引数をスタックに準備
        // typ (型情報) をスタックにストア
        taddr := s.newValue1A(ssa.OpAddr, Types[TUINTPTR], &ssa.ExternSymbol{Types[TUINTPTR], typenamesym(left.Type)}, s.sb)
        s.vars[&memvar] = s.newValue3I(ssa.OpStore, ssa.TypeMem, int64(Widthptr), s.sp, taddr, s.mem())
        // dst (宛先アドレス) をスタックにストア
        spplus8 := s.newValue1I(ssa.OpOffPtr, Types[TUINTPTR], int64(Widthptr), s.sp)
        s.vars[&memvar] = s.newValue3I(ssa.OpStore, ssa.TypeMem, int64(Widthptr), spplus8, addr, s.mem())

        // typedmemmove_nostore を呼び出し
        call := s.newValue1A(ssa.OpStaticCall, ssa.TypeMem, syslook("typedmemmove_nostore", 0).Sym, s.mem())
        call.AuxInt = int64(2 * Widthptr) // 引数のサイズ
        s.vars[&memvar] = call
        c := s.endBlock()
        c.Kind = ssa.BlockCall
        c.Control = call
        c.AddEdgeTo(bNext)

        s.startBlock(bNext)
    }
    ```

    このコードは、`writeBarrierEnabled` というランタイムフラグが `true` の場合にのみ `typedmemmove_nostore` を呼び出すようにします。`typedmemmove_nostore` は、代入されるオブジェクトの型情報 (`t`) とその宛先アドレス (`&l`) を引数として受け取ります。これにより、GCはポインタの変更を検出し、必要に応じて古いオブジェクトをマークすることができます。

2.  **`typedmemmove_nostore` の実装**:
    `src/runtime/mbarrier.go` に `typedmemmove_nostore` 関数が追加されました。

    ```go
    //go:nosplit
    func typedmemmove_nostore(typ *_type, dst unsafe.Pointer) {
        if typ.kind&kindNoPointers != 0 {
            return // ポインタを含まない型であれば何もしない
        }
        heapBitsBulkBarrier(uintptr(dst), typ.size)
    }
    ```
    この関数は、`typ` がポインタを含まない型 (`kindNoPointers`) であれば何もしません。ポインタを含む型の場合、`heapBitsBulkBarrier` を呼び出します。`heapBitsBulkBarrier` は、GCヒープ上の `dst` から `typ.size` バイトの範囲にあるポインタビットマップを更新し、GCがオブジェクトを正しくマークできるようにします。`//go:nosplit` ディレクティブは、この関数がスタック分割を行わないことを示しており、GCのクリティカルパスで安全に呼び出せるようにします。

### SSAデバッグ機能

このコミットでは、SSAバックエンドのデバッグを容易にするための環境変数 `GOSSAPKG` と `GOSSAHASH` が導入されました。

1.  **`buildssa` 関数におけるハッシュチェック**:
    `src/cmd/compile/internal/gc/ssa.go` の `buildssa` 関数が変更され、`GOSSAPKG` と `GOSSAHASH` 環境変数の値に基づいて、特定の関数のみをSSAでコンパイルするかどうかを決定するロジックが追加されました。

    ```go
    // ... (既存のコード) ...
    if usessa {
        return s.f, true
    }
    if localpkg.Name != os.Getenv("GOSSAPKG") {
        return s.f, false // GOSSAPKG で指定されたパッケージ以外はSSAコンパイルしない
    }
    if os.Getenv("GOSSAHASH") == "" {
        // GOSSAHASH が指定されていなければ、パッケージ内のすべてをSSAコンパイル
        return s.f, true
    }
    // 関数名のハッシュをチェック
    hstr := ""
    for _, b := range sha1.Sum([]byte(name)) {
        hstr += fmt.Sprintf("%08b", b) // SHA1ハッシュをバイナリ文字列に変換
    }
    if strings.HasSuffix(hstr, os.Getenv("GOSSAHASH")) {
        fmt.Println("GOSSAHASH triggered %s\n", name)
        return s.f, true // ハッシュの下位ビットが GOSSAHASH と一致すればSSAコンパイル
    }
    return s.f, false // 一致しなければSSAコンパイルしない
    ```

2.  **バイナリサーチの仕組み**:
    *   `GOSSAPKG` で問題が発生しているパッケージを指定します。
    *   `GOSSAHASH` には、関数名のSHA1ハッシュ値の末尾のバイナリ文字列を指定します。例えば、`GOSSAHASH=0` とすると、ハッシュの末尾が `0` の関数のみがSSAでコンパイルされます。
    *   `GOSSAHASH` の文字列を `0` から `1`、`00`、`01`、`10`、`11` のように徐々に長くしていくことで、SSAコンパイルされる関数の数を絞り込み、問題のある関数をバイナリサーチのように特定することができます。これにより、デバッグの効率が大幅に向上します。

### スタックガード領域の変更

`src/cmd/internal/obj/stack.go` と `src/runtime/stack2.go` で `StackGuard` の値が `640*stackGuardMultiplier` から `960*stackGuardMultiplier` に変更されました。これは、スタックオーバーフロー検出のためのガード領域のサイズを増やしています。ライトバリアの実装とは直接関係ありませんが、このコミットに含まれており、ランタイムの安定性向上に寄与する変更です。スタックガード領域の増加は、特に `nosplit` 関数（スタック分割を行わない関数）の呼び出しにおいて、より多くのスタック使用を許容し、スタックオーバーフローのリスクを低減する可能性があります。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更点

1.  **`buildssa` 関数の変更**:
    この変更は、SSAバックエンドのデバッグ機能を実装しています。
    *   `usessa` が `true` の場合（SSAが強制されている場合）は、そのままSSAコンパイルを続行します。
    *   `GOSSAPKG` 環境変数が設定されており、現在のパッケージ名 (`localpkg.Name`) と一致しない場合は、SSAコンパイルを行いません。これにより、特定のパッケージのみをSSAでコンパイル対象とすることができます。
    *   `GOSSAHASH` 環境変数が空文字列の場合、`GOSSAPKG` で指定されたパッケージ内のすべての関数をSSAでコンパイルします。
    *   `GOSSAHASH` が設定されている場合、関数名 (`name`) のSHA1ハッシュを計算し、そのバイナリ表現の末尾が `GOSSAHASH` の値と一致するかどうかをチェックします。一致した場合のみ、その関数をSSAでコンパイルします。このメカニズムにより、開発者は問題のある関数をバイナリサーチで効率的に特定できます。

2.  **`assign` 関数の変更**:
    この変更は、ライトバリアのSSA生成を実装しています。
    *   `s.vars[&memvar] = s.newValue3I(ssa.OpStore, ssa.TypeMem, t.Size(), addr, right, s.mem())` の行で、通常のストア操作（`right` の値を `addr` に書き込む）がSSAによって生成されます。
    *   その直後に `if wb { ... }` ブロックが追加されています。`wb` が `true` の場合、ライトバリアのロジックが挿入されます。
    *   まず、`writeBarrierEnabled` というランタイムフラグの値をロードし、それが `true` の場合にのみライトバリア処理を実行する条件分岐 (`ssa.BlockIf`) を生成します。`ssa.BranchUnlikely` は、この分岐がほとんど実行されないことをコンパイラにヒントとして与え、最適化を助けます。
    *   `bThen` ブロック内で、`typedmemmove_nostore` 関数を呼び出すための準備が行われます。具体的には、`left.Type` の型情報と `addr` (代入先のメモリアドレス) をスタックにプッシュし、`typedmemmove_nostore` を `ssa.OpStaticCall` として呼び出します。
    *   この `typedmemmove_nostore` の呼び出しは、ストア操作自体は行わず、GCがポインタの変更を認識するために必要な処理（ヒープビットマップの更新など）のみを実行します。コメントにあるように、ストア操作とこのライトバリア呼び出しの間にはGCの停止点があってはならないという重要な制約があります。

### `src/runtime/mbarrier.go` の変更点

*   **`typedmemmove_nostore` 関数の追加**:
    この関数は、コンパイラによって生成されたライトバリアコードから呼び出されます。
    *   `typ.kind&kindNoPointers != 0` のチェックにより、`typ` がポインタを含まない型である場合は、ライトバリア処理は不要であるため、すぐにリターンします。これにより、不要なオーバーヘッドを避けます。
    *   ポインタを含む型の場合、`heapBitsBulkBarrier(uintptr(dst), typ.size)` を呼び出します。この関数は、`dst` が指すメモリ領域のポインタビットマップを更新し、GCがその領域内のポインタの変更を認識できるようにします。これにより、並行GCの正確性が保証されます。`//go:nosplit` ディレクティブは、この関数がスタックを拡張しないことを保証し、GCのクリティカルパスでの使用に適しています。

# [インデックス 22292] ファイルの概要

このコミットは、Goコンパイラのx86アーキテクチャ向けアセンブラバックエンドである `src/cmd/internal/obj/x86/asm6.go` ファイルに対する変更です。このファイルは、Goの内部アセンブリ命令をx86マシンコードに変換する際の命令エンコーディングとオペランドの処理を定義しています。

## コミット

このコミットは、x86のダブルシフト命令（例: `SHRQ`）における第二ソースオペランドの内部表現を変更するものです。これまでは、`DX:AX`のような64ビットオペランドが単一の`From`フィールドに「詰め込まれて」いましたが、この変更により、第二ソースオペランドを格納するための専用の`From3`フィールドが導入されました。これにより、内部表現がより明確になり、将来的に古いエンコーディングのサポートを削除するための第一歩となります。

## 変更の背景

この変更の背景には、Goコンパイラのx86バックエンドにおける命令オペランドの内部表現の改善があります。特に、`SHRQ`（Shift Right Quadword）のようなダブルシフト命令は、`DX:AX`のように2つの32ビットレジスタを組み合わせて1つの64ビット値を表現する形式を取ることがあります。

従来のGoコンパイラのアセンブラでは、このような複合オペランドを`obj.Prog`構造体の`From`フィールドに「詰め込む」形で表現していました。具体的には、`DX:AX`の場合、`AX`が`From`フィールドの主要部分に、`DX`が`From.Index`に格納されるような非対称な方法が取られていました。これは、命令の論理的な構造（2つの独立したソースレジスタ）と内部表現との間に乖離を生じさせていました。

この乖離は、コードの可読性や保守性を低下させるだけでなく、将来的な最適化や新しい命令セットのサポートを困難にする可能性がありました。そのため、より明確で論理的な内部表現を導入し、第二ソースオペランドを専用のフィールド（`From3`）に格納することで、この問題を解決しようとしたのがこのコミットの目的です。これは、Goコンパイラが生成するアセンブリコードの正確性と効率性を向上させるための、より広範な取り組みの一環です。

## 前提知識の解説

### 1. x86アセンブリにおけるシフト命令とダブルシフト命令

*   **SHRQ (Shift Right Quadword)**: x86アーキテクチャにおける論理右シフト命令の一つで、64ビット（クワッドワード）の値を右にシフトします。シフトによって空いた最上位ビットには0が埋められます。通常、`SHRQ count, operand` の形式で記述され、`operand`はシフトされる値、`count`はシフト量です。
*   **ダブルシフト命令 (Double Shift Instructions)**: `SHLD` (Shift Left Double) や `SHRD` (Shift Right Double) など、2つのレジスタを連結した64ビット値に対してシフト操作を行う命令です。例えば、`SHRD count, source, destination` は、`destination`レジスタと`source`レジスタを連結した仮想的な64ビット値に対して右シフトを行い、結果を`destination`レジスタに格納します。このコミットで言及されている`SHRQ CX, DX:AX`は、Goのアセンブラが内部的にこのようなダブルシフトの概念を扱っていたことを示唆しています。

### 2. Goコンパイラの内部構造と`obj.Prog`

Goコンパイラは、Go言語のソースコードを最終的なマシンコードに変換する多段階のプロセスを経ます。このプロセスの中で、Goの内部アセンブラは、Goの抽象的な命令をターゲットアーキテクチャ（この場合はx86）の具体的な命令にマッピングします。

*   **`cmd/internal/obj`パッケージ**: Goコンパイラの内部パッケージで、アセンブラのバックエンドを構成します。各アーキテクチャ（x86、ARMなど）に対応するサブパッケージ（例: `cmd/internal/obj/x86`）が含まれています。
*   **`obj.Prog`構造体**: Goコンパイラの内部でアセンブリ命令を表現するために使用される主要なデータ構造です。各`obj.Prog`インスタンスは1つのアセンブリ命令に対応し、命令の種類（`As`フィールド）、ソースオペランド（`From`フィールド）、デスティネーションオペランド（`To`フィールド）などの情報を含みます。
    *   **`obj.Addr`構造体**: `obj.Prog`の`From`、`To`、`From3`などのフィールドの型であり、命令のオペランド（レジスタ、メモリ、即値など）を表現します。`Type`、`Reg`、`Index`、`Scale`、`Offset`などのフィールドを持ちます。
    *   **`From`、`To`、`From3`フィールド**:
        *   `From`: 命令の第一ソースオペランド。
        *   `To`: 命令のデスティネーションオペランド。
        *   `From3`: このコミットで導入された、命令の第二ソースオペランドを格納するための新しいフィールド。特に、ダブルシフト命令のように複数のソースレジスタを必要とする場合に利用されます。

### 3. `6g`コンパイラ

`6g`は、Goの初期バージョン（Go 1.5以前）でx86-64アーキテクチャ向けのGoコードをコンパイルするために使用されていたコンパイラの名前です。Go 1.5以降は、`go tool compile`という単一のコマンドに統合され、`GOOS`と`GOARCH`環境変数によってターゲットアーキテクチャが決定されるようになりました。このコミットが2015年3月のものであることから、当時はまだ`6g`という名称が使われていたことがわかります。

## 技術的詳細

このコミットの核心は、Goコンパイラのx86アセンブラがダブルシフト命令のオペランドをどのように内部的に表現し、処理するかという点にあります。

### 1. オペランド表現の変更

*   **旧形式**: `SHRQ CX, DX:AX`
    *   シフト量: `CX`
    *   シフト対象の64ビット値: `DX:AX` (DXが上位32ビット、AXが下位32ビット)
    *   この形式では、`DX:AX`という複合オペランドが`obj.Prog`の`From`フィールドに「詰め込まれて」いました。具体的には、`From.Reg`が`AX`を指し、`From.Index`が`DX`を指すような形で表現されていました。これは、`From`フィールドが本来、単一のオペランドを表現するためのものであるため、直感的ではありませんでした。

*   **新形式**: `SHRQ CX, AX, DX`
    *   シフト量: `CX`
    *   シフト対象の下位32ビット: `AX`
    *   シフト対象の上位32ビット: `DX`
    *   この新しい形式では、`AX`が`From3`フィールドに、`DX`が`To`フィールドに、そして`CX`が`From`フィールドに格納されることが意図されています（コミットメッセージの`From=CX, From3=AX, To=DX`の記述から）。これにより、各レジスタが専用のフィールドにマッピングされ、命令の論理的な構造が内部表現に直接反映されるようになります。

### 2. `asm6.go`における具体的な変更点

*   **定数定義の変更**:
    *   `Yxxx = 0 + iota` から `Yxxx = iota` へ、`Zxxx = 0 + iota - 68` から `Zxxx = iota` へと変更されています。これはGoの`iota`キーワードのより慣用的な使用法への修正であり、コードの可読性を向上させます。
    *   `Ycol`定数の削除と`Yreg2`定数の追加:
        *   `Ycol`は、`DX:AX`のような「コロン区切り」の複合オペランドを表すために使われていた古いオペランドタイプでした。
        *   `Yreg2`は、2つのレジスタをソースとして取る命令（新しい`AX, DX`形式）に対応するための新しいオペランドタイプです。

*   **`oclass`関数の変更**:
    *   `oclass`関数は、与えられたオペランドの「クラス」（型）を決定する役割を担っています。
    *   以前の`SHRQ`の特殊ケース（`Ycol`を返す部分）が削除され、新しいロジックが追加されました。
    *   新しいロジックでは、もしオペランド`a`が`p.From`であり、かつ`a.Index`がレジスタ（`REG_NONE`ではない）で`a.Scale`が0の場合、これは複合オペランドの第二レジスタ（例: `DX` in `DX:AX`）であると判断されます。この場合、`p.From3.Type`を`obj.TYPE_REG`に設定し、`p.From3.Reg`にそのレジスタ（`a.Index`）を格納します。そして、`a.Index`をクリアすることで、`From`フィールドから第二レジスタの情報を分離します。
    *   さらに、`p.From`と`p.From3`が両方ともレジスタである場合に`Yreg2`を返す新しい条件が追加されました。これは、新しいエンコーディングが適用される命令を識別するために使用されます。

*   **`ymovtab`の変更**:
    *   `ymovtab`は、Goの内部アセンブリ命令とx86マシンコードのエンコーディングをマッピングするテーブルです。
    *   `ASHLL`, `ASHRL`, `ASHLQ`, `ASHRQ`, `ASHLW`, `ASHRW`といったダブルシフト命令のエントリで、オペランドタイプが`Ycol`から`Yreg2`に変更されました。これは、これらの命令が新しい`From3`フィールドを使用するエンコーディングに移行したことを直接的に示しています。
    *   `load full pointer`に関連する`Movtab`エントリがコメントアウトされ、「unsupported」とマークされました。これは、`Ycol`に関連する古い、もはや使用されないコードのクリーンアップと考えられます。

*   **`doasm`関数の変更**:
    *   `doasm`関数は、`obj.Prog`構造体から実際のx86マシンコードを生成する役割を担っています。
    *   `asmandsz`関数の呼び出しにおいて、第二ソースレジスタの取得元が`p.From.Index`から`p.From3.Reg`に変更されました。これは、アセンブリコード生成時に新しい`From3`フィールドから正しいレジスタ情報を取得するように修正されたことを意味します。

これらの変更は、Goコンパイラのx86バックエンドが、ダブルシフト命令のオペランドをより論理的かつ明確な方法で内部的に表現し、最終的なマシンコードに変換するための基盤を強化するものです。

## コアとなるコードの解説

### 1. 定数定義の変更

*   `Yxxx = 0 + iota` から `Yxxx = iota` などへの変更は、Go言語の`iota`の一般的な使い方に合わせたものです。`iota`は連続する定数に自動的に値を割り当てるために使われます。`0 + iota`は冗長であり、`iota`単独で0から始まる連番を生成します。
*   `Ycol`の削除と`Yreg2`の追加は、オペランドの分類方法の根本的な変更を示しています。
    *   `Ycol`は、`DX:AX`のような「コロン区切り」の複合レジスタオペランドを表現するために使われていました。この形式は、Goの内部表現がx86の特定の命令エンコーディングに密接に結合していたことを示唆しています。
    *   `Yreg2`は、2つの独立したレジスタをソースとして取る命令（例: `SHRQ CX, AX, DX`における`AX`と`DX`）をより抽象的に表現するための新しいカテゴリです。これにより、内部表現がより汎用的で、特定のエンコーディングの詳細から分離されます。

### 2. `oclass`関数のロジック変更

`oclass`関数は、`obj.Prog`構造体のオペランド（`obj.Addr`型）を分析し、そのオペランドがどの「クラス」に属するか（例: レジスタ、メモリ、即値など）を決定します。

*   **旧ロジックの削除**: 以前の`SHRQ`に関する特殊な処理（`a.Index != REG_NONE && a.Scale == 0`の場合に`Ycol`を返す部分）が削除されました。これは、`DX:AX`のような複合オペランドを`From`フィールドの`Index`部分に「詰め込む」という古いアプローチが廃止されたことを意味します。
*   **`From3`への移行ロジック**:
    ```go
    if a == &p.From && (a.Type == obj.TYPE_CONST || a.Type == obj.TYPE_REG) && a.Index != REG_NONE && a.Scale == 0 {
        p.From3.Type = obj.TYPE_REG
        p.From3.Reg = a.Index
        a.Index = 0
    }
    ```
    このコードブロックは、`p.From`オペランドが、実際には複合オペランドの第二レジスタ（例: `DX` in `DX:AX`）を`Index`フィールドに持っている場合に実行されます。この場合、その`Index`レジスタの情報を新しく導入された`p.From3`フィールドに移動させ、元の`a.Index`をクリアします。これにより、`From`フィールドは第一ソースレジスタ（例: `AX`）のみを保持し、第二ソースレジスタは`From3`に分離されます。これは、Goコンパイラが内部的に命令のオペランドをより論理的に分割して表現するための重要なステップです。
*   **`Yreg2`の導入**:
    ```go
    if a == &p.From && p.From3.Type != obj.TYPE_NONE {
        if (a.Type == obj.TYPE_CONST || a.Type == obj.TYPE_REG) && p.From3.Type == obj.TYPE_REG {
            return Yreg2
        }
        // ... (エラーハンドリング)
    }
    ```
    この新しいブロックは、`p.From`と`p.From3`の両方が有効なレジスタオペランドである場合に`Yreg2`を返します。これは、ダブルシフト命令のように2つのレジスタソースオペランドを持つ命令を識別するための新しいメカニズムです。

### 3. `ymovtab`の変更

`ymovtab`は、Goの内部アセンブリ命令（`obj.Prog.As`）と、その命令のオペランドのクラス（`From`と`To`のクラス）に基づいて、対応するx86マシンコードのバイト列を決定するためのテーブルです。

*   **ダブルシフト命令のオペランドタイプ変更**: `ASHLL`, `ASHRL`, `ASHLQ`, `ASHRQ`, `ASHLW`, `ASHRW`といったダブルシフト命令のエントリで、`From`オペランドのクラスが`Ycol`から`Yreg2`に変更されました。これは、これらの命令がもはや`Ycol`（複合オペランド）として扱われず、`Yreg2`（2つの独立したレジスタソース）として扱われるようになったことを明確に示しています。これにより、`doasm`関数が`From3`フィールドから第二ソースレジスタを正しく取得できるようになります。
*   **`load full pointer`のコメントアウト**: このセクションがコメントアウトされ、「unsupported」とマークされたのは、おそらく`Ycol`に関連する古い、もはや使用されない命令エンコーディングのクリーンアップの一環です。

### 4. `doasm`関数の変更

`doasm`関数は、`obj.Prog`構造体から実際のx86マシンコードのバイト列を生成する、アセンブラの最終段階を担っています。

*   **`asmandsz`関数の引数変更**:
    ```diff
    -						asmandsz(ctxt, p, &p.To, reg[int(p.From.Index)], regrex[int(p.From.Index)], 0)
    +						asmandsz(ctxt, p, &p.To, reg[p.From3.Reg], regrex[p.From3.Reg], 0)
    ```
    この変更は、`asmandsz`（おそらく「assemble and size」の略）というヘルパー関数に渡される第二ソースレジスタの取得元が変更されたことを示しています。以前は`p.From.Index`から取得していましたが、新しいロジックでは`p.From3.Reg`から取得するようになりました。これは、`From3`フィールドに第二ソースレジスタが格納されるようになったという、内部表現の変更がアセンブリコード生成の最終段階にまで反映されたことを意味します。

これらの変更全体として、Goコンパイラのx86バックエンドが、ダブルシフト命令のような複雑な命令のオペランドをより構造化され、論理的な方法で内部的に表現し、最終的なマシンコードに変換する能力を向上させていることがわかります。これにより、コンパイラの保守性が向上し、将来的な機能拡張や最適化が容易になります。

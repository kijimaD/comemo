## 変更の背景

このコミットは、Goランタイムのスタック管理コードにおける、主に可読性と正確性を向上させるための「nits」（軽微な修正や改善）に分類されます。具体的な背景としては、以下の点が挙げられます。

1.  **変数名の明確化**: `siz2`という汎用的な変数名が`args`というより具体的な名前に変更されており、その変数がスタック上の引数サイズを表していることを明確にしています。これにより、コードの意図がより理解しやすくなります。
2.  **コメントの更新**: スタックフレームサイズと引数サイズを`m->morearg`にパックする際のビットシフトの順序が変更されたことに伴い、関連するコメントも更新されています。これは、コードの動作とコメントが一致するようにするための重要な修正です。
3.  **ポータビリティと正確性の向上**: `mcpy`関数の引数でハードコードされていたオフセット値`16`が`2*sizeof(uintptr)`に変更されています。これは、ポインタのサイズがシステムによって異なる可能性があるため、よりポータブルで正確な方法でオフセットを計算するための改善です。

これらの変更は、Goランタイムの初期段階において、コードベースの品質と保守性を高めるための継続的な取り組みの一環として行われました。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの基本的なスタック管理メカニズムと、関連する内部変数や関数の知識が必要です。

*   **Goランタイム**: Goプログラムの実行を管理する低レベルのシステムです。ガベージコレクション、スケジューリング、メモリ管理、スタック管理など、多くの重要な機能を提供します。
*   **Goroutineスタック**: Goの並行処理の単位であるGoroutineは、それぞれ独自のスタックを持っています。Goのスタックは動的に伸縮可能であり、必要に応じて自動的に拡大（`morestack`）または縮小（`oldstack`）します。
*   **`morestack`関数**: Goroutineのスタックが不足した場合に呼び出されるランタイム関数です。新しい、より大きなスタックを割り当て、現在のスタックの内容を新しいスタックにコピーし、実行を継続します。
*   **`oldstack`関数**: スタックが大きすぎる場合に、スタックを縮小するために呼び出されるランタイム関数です。
*   **`m`構造体**: Goランタイムの内部で、OSスレッド（M: Machine）を表す構造体です。各Mは、現在実行中のGoroutine（G）や、スタック管理に関連する一時的な情報などを保持します。
*   **`m->morearg`**: `m`構造体内のフィールドで、`morestack`関数が呼び出される際に、呼び出し元のスタックフレームサイズや引数サイズなどの情報を一時的に保持するために使用されます。これは、`morestack`がスタックを拡張した後に、元の関数に戻るために必要なコンテキスト情報です。
*   **`Stktop`構造体**: スタックの最上位（トップ）に関する情報を保持する構造体です。`stackbase`や`magic`などのフィールドが含まれることがあります。`magic`フィールドは、スタックのメタデータ（例えば、スタックフレームサイズや引数サイズ）をビットパックして格納するために使用されることがあります。
*   **`StackSmall`と`StackBig`**: これらは、スタックフレームのサイズに基づいて`morestack`の動作を決定するための閾値です。スタックフレームのサイズがこれらの閾値と比較され、異なるスタック拡張戦略が適用されます。
*   **`uintptr`**: Goにおけるポインタのサイズを表す型です。システムによって32ビットまたは64ビットになります。`sizeof(uintptr)`は、実行環境におけるポインタのバイトサイズを返します。
*   **`mcpy`**: メモリコピーを行うランタイム内部関数です。C言語の`memcpy`に相当します。

## 技術的詳細

このコミットの技術的な変更は、主に`src/runtime/proc.c`ファイル内のスタック管理ロジックに集中しています。

1.  **`m->morearg`への値のパック順序の変更**:
    `sys·exitsyscall`関数内のコメントブロックで示されているように、`m->morearg`にスタックフレームサイズ（`frame`）と引数サイズ（`argsize`）をパックする際のビットシフトの順序が変更されました。

    *   **変更前**: `$(frame << 32) | argsize)`
        これは、`frame`を上位32ビットに、`argsize`を下位32ビットにパックすることを意味します。
    *   **変更後**:
        *   `stack frame size <= StackSmall` および `stack frame size > StackSmall but < StackBig` の場合: `$(argsize << 32)`
            この変更は、`frame`が不要になったか、別の方法で処理されるようになったことを示唆しています。しかし、`oldstack`関数でのアンパックを見ると、`argsize`のみが`m->morearg`から抽出されているため、この変更は`argsize`のみを`m->morearg`の上位32ビットに格納するように意図されたものと考えられます。
        *   `stack frame size >= StackBig` の場合: `$(argsize << 32) | frame)`
            このケースでは、`argsize`が上位32ビットに、`frame`が下位32ビットにパックされるように変更されました。これは、以前のパック順序を逆にしたものです。

    この変更は、`morestack`がスタックを拡張した後に、`oldstack`などの関数が`m->morearg`から正しい情報を抽出できるようにするための調整です。

2.  **`oldstack`関数内の変数名変更と`mcpy`の引数変更**:
    `oldstack`関数内で、`uint32 siz2;`という変数が`uint32 args;`に変更されました。これに伴い、`siz2`を使用していた箇所がすべて`args`に置き換えられています。

    *   **変更前**: `siz2 = (top->magic>>32) & 0xffffLL;`
    *   **変更後**: `args = (top->magic>>32) & 0xffffLL;`
        これは、`Stktop`構造体の`magic`フィールドから抽出される値が、スタックフレームサイズではなく、引数サイズ（`args`）であることを明確にしています。`0xffffLL`は下位16ビットをマスクしています。

    さらに重要な変更は、`mcpy`関数の第1引数です。
    *   **変更前**: `mcpy(top->oldsp+16, sp, siz2);`
    *   **変更後**: `mcpy(top->oldsp+2*sizeof(uintptr), sp, args);`
        `top->oldsp`は、古いスタックポインタを指しています。`+16`というハードコードされたオフセットは、`top->oldsp`が指すアドレスから16バイト先に、コピーすべきデータが始まることを意味していました。この`16`という値は、64ビットシステムでは`2 * sizeof(uintptr)`（2 * 8バイト）に相当します。この変更により、`sizeof(uintptr)`を使用することで、32ビットシステムと64ビットシステムの両方で正しくオフセットが計算されるようになり、コードのポータビリティが向上しました。これは、`top->oldsp`が指す構造体の先頭に、2つの`uintptr`サイズのフィールド（例えば、リターンアドレスとフレームポインタなど）が存在し、その後に実際のスタックデータが続くことを示唆しています。

これらの変更は、Goランタイムのスタック管理の正確性と堅牢性を向上させるための、細部への注意を払った改善です。

## コアとなるコードの解説

上記の差分は、`src/runtime/proc.c`ファイルにおけるGoランタイムのスタック管理ロジックの変更を示しています。

1.  **コメントの変更（`sys·exitsyscall`関数付近）**:
    `sys·exitsyscall`関数は、システムコールから戻る際のスタックチェックと`morestack`呼び出しに関するコメントブロックです。
    *   変更前は、`m->morearg`に`frame`（スタックフレームサイズ）を上位32ビット、`argsize`（引数サイズ）を下位32ビットでパックする例が示されていました。
    *   変更後は、`stack frame size <= StackSmall`と`stack frame size > StackSmall but < StackBig`のケースで、`m->morearg`に`argsize`のみを上位32ビットにパックする例に変わっています。これは、これらのケースでは`frame`情報が`m->morearg`にパックされなくなったか、別の方法で処理されるようになったことを示唆しています。
    *   `stack frame size >= StackBig`のケースでは、`m->morearg`に`argsize`を上位32ビット、`frame`を下位32ビットでパックする例に変わっています。これは、以前のパック順序を逆にしたものです。
    これらのコメントの変更は、実際のコードの動作に合わせてドキュメントを更新し、正確性を保つためのものです。

2.  **`oldstack`関数内の変数名変更**:
    `oldstack`関数は、スタックを縮小する際に呼び出されるランタイム関数です。
    *   `uint32 siz2;` が `uint32 args;` に変更されました。これは、この変数がスタック上の引数サイズを保持していることをより明確にするためのリネームです。
    *   `siz2 = (top->magic>>32) & 0xffffLL;` が `args = (top->magic>>32) & 0xffffLL;` に変更されました。これは、`Stktop`構造体の`magic`フィールドから抽出される値が引数サイズであることを明示しています。

3.  **`oldstack`関数内の`mcpy`引数の変更**:
    *   `mcpy(top->oldsp+16, sp, siz2);` が `mcpy(top->oldsp+2*sizeof(uintptr), sp, args);` に変更されました。
        *   `top->oldsp+16`: これは、古いスタックポインタ`top->oldsp`から16バイトオフセットした位置からメモリコピーを開始することを意味していました。
        *   `top->oldsp+2*sizeof(uintptr)`: これは、`uintptr`のサイズ（システムによって4バイトまたは8バイト）の2倍のオフセットを動的に計算します。これにより、コードが32ビットと64ビットの両方のアーキテクチャで正しく動作するようになり、ポータビリティが向上します。この変更は、`top->oldsp`が指すアドレスの直後に、2つのポインタサイズのデータ（例えば、リターンアドレスとフレームポインタ）が格納されており、その後にコピーすべき実際のスタックデータが続くという、スタックフレームのレイアウトに関する暗黙の仮定を明示的にしています。
        *   `siz2`が`args`に変更されたのは、変数名のリネームによるものです。

4.  **コメントの変更（`newstack`関数付近）**:
    `newstack`関数内の`printf`デバッグコメントが更新されました。
    *   変更前: `// printf("newstack frame=%d args=%d moresp=%p\\n", frame, args, m->moresp);`
    *   変更後: `// printf("newstack frame=%d args=%d moresp=%p morepc=%p\\n", frame, args, m->moresp, *(uintptr*)m->moresp);`
    これは、デバッグ出力に`morepc`（`m->moresp`が指すアドレスにあるプログラムカウンタの値）を追加することで、より詳細な情報が得られるようにするための変更です。

これらの変更は、Goランタイムのスタック管理コードの正確性、可読性、およびポータビリティを向上させるための、細かくも重要な改善です。

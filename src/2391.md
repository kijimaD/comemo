# [インデックス 2391] ファイルの概要

このコミットは、Goコンパイラ（`gc`）におけるシンボル解決のバグ（bug161）を修正するものです。具体的には、ローカルスコープで宣言された変数（特に関数パラメータ）が、同じ名前のパッケージレベルの定数をシャドウしている場合に、コンパイラがそのローカル変数を誤って定数として扱ってしまう問題を解決します。これにより、「operation LITERAL not allowed in assignment context」という誤ったエラーが発生するのを防ぎます。

## 変更の背景

このコミットの背景には、Goコンパイラがシンボルテーブルを管理する方法における潜在的な問題がありました。Go言語では、ローカルスコープで宣言された変数が、より外側のスコープ（例えばパッケージレベル）で宣言された同じ名前のエンティティ（変数、定数、型など）を「シャドウ」することができます。これは、ローカルスコープ内ではローカルなエンティティが優先されることを意味します。

しかし、このバグ（bug161）では、コンパイラがシンボルテーブル内で新しいローカル変数を宣言する際に、以前に同じ名前で宣言された定数の属性（例えば、それが定数であるという情報やその値）を誤って引き継いでしまうことがありました。その結果、関数パラメータのようなローカル変数に対して代入操作を行おうとすると、コンパイラはそれを変更不可能な定数への代入と誤解し、「operation LITERAL not allowed in assignment context」というエラーを報告していました。

この問題は、コンパイラのシンボル管理の正確性に直接関わるものであり、Goプログラムの正しいコンパイルを妨げる重大なバグでした。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの概念とC言語の基本的な知識が必要です。

1.  **Goコンパイラ (`gc`)**:
    *   Go言語の公式コンパイラは、歴史的に`gc`（Go Compilerの略）と呼ばれていました。初期のバージョンはC言語で書かれていましたが、後にGo言語自身で書き直されました。このコミットが行われた2009年時点では、まだC言語で書かれた部分が多く残っていました。
    *   コンパイラは、ソースコードを解析し、中間表現を生成し、最終的に実行可能なバイナリコードを生成する一連のフェーズで構成されます。

2.  **シンボルテーブル (Symbol Table)**:
    *   コンパイラがプログラム内のすべての識別子（変数名、関数名、型名、定数名など）に関する情報を格納するために使用するデータ構造です。
    *   各エントリには、識別子の名前、型、スコープ、メモリ位置、定数値などの属性が含まれます。
    *   シンボルテーブルは、コンパイル中に識別子の参照を解決し、型チェックを行い、スコープ規則を適用するために不可欠です。

3.  **スコープとシャドウイング (Scope and Shadowing)**:
    *   **スコープ**: プログラム内で識別子が有効である範囲を指します。Go言語はレキシカルスコープ（静的スコープ）を採用しており、識別子の有効範囲はソースコードの構造によって決定されます。
    *   **シャドウイング**: 内側のスコープで宣言された識別子が、外側のスコープで宣言された同じ名前の識別子を「隠す」現象です。内側のスコープでは、常に内側の識別子が参照されます。

4.  **`src/cmd/gc/dcl.c`**:
    *   GoコンパイラのC言語時代のソースファイルの一つで、主に宣言（declaration）の処理を担当していました。変数、定数、型などの宣言を解析し、シンボルテーブルにエントリを追加するロジックが含まれていました。

5.  **`src/cmd/gc/subr.c`**:
    *   GoコンパイラのC言語時代のソースファイルの一つで、サブルーチン（subroutine）やユーティリティ関数をまとめたファイルです。エラーメッセージの出力、デバッグ情報の整形、型情報の表示など、様々な補助的な処理が含まれていました。

6.  **`Node` および `Sym` 構造体**:
    *   Goコンパイラの内部では、ソースコードの要素を表現するために`Node`のような抽象構文木（AST）ノードが使用されます。
    *   `Sym`（Symbol）構造体は、シンボルテーブルのエントリを表し、識別子の名前や属性（`otype`、`oconst`、`oname`など）を保持します。
    *   `s->otype`: シンボルが型である場合のその型情報。
    *   `s->oconst`: シンボルが定数である場合のその定数値。
    *   `s->oname`: シンボルが変数である場合のその名前ノード。
    *   `s->lexical`: シンボルの種類（変数、型、定数など）を示す列挙型。

## 技術的詳細

このバグは、Goコンパイラのシンボルテーブル管理における初期化の不備に起因していました。`dcl.c`ファイルは、変数、型、定数などの宣言を処理する際に、対応する`Sym`構造体のフィールドを適切に初期化する責任を負っていました。

問題は、新しいシンボル（例えば、関数`f`のパラメータ`a`）が宣言される際に、その`Sym`構造体の`oconst`や`otype`といったフィールドが、以前に同じ名前で宣言されたシンボル（例えば、パッケージレベルの定数`a`）の古い値を保持してしまう可能性があったことです。これは、シンボルテーブルのエントリが再利用される際に、関連する属性が完全にクリアされていなかったためと考えられます。

コンパイラが関数`f`内の`a = 0;`という代入文を処理する際、ローカル変数`a`の`Sym`構造体を調べます。もし`oconst`フィールドに定数としての情報が残っていた場合、コンパイラは`a`を定数と誤解し、定数への代入は許可されないためエラーを報告していました。

このコミットでは、`dcl.c`内の`addvar`（変数追加）、`addtyp`（型追加）、`addconst`（定数追加）の各関数において、新しいシンボルを宣言する際に、`Sym`構造体の`oconst`、`otype`、`oname`フィールドを明示的に`nil`に初期化する変更が加えられました。これにより、シンボルが宣言されるたびにこれらの属性が確実にリセットされ、古い情報が誤って引き継がれることがなくなります。

また、`subr.c`の`Tpretty`関数における変更は、型情報の表示ロジックの修正です。`Tpretty`は、コンパイラの内部型を人間が読める形式に変換する際に使用される可能性があります。元の条件式 `if(s->otype != t || (!s->export && !s->imported))` は、`s->otype != t`が偽の場合にのみ `(!s->export && !s->imported)` を評価していました。新しい条件式 `if((s->otype != t || !s->export) && !s->imported)` は、`!s->imported`が常に評価されるように変更されています。これは、インポートされた型に関する比較や表示のロジックが、シンボルテーブルの修正と関連して、より厳密に、または正確に行われるように調整されたものと考えられます。特に、シンボルがインポートされたものであるかどうかをより確実にチェックすることで、型情報の誤った解釈や表示を防ぐ目的があったと推測されます。

## コアとなるコードの解説

### `src/cmd/gc/dcl.c` の変更

*   **`addvar` 関数**: 変数をシンボルテーブルに追加する際に呼び出されます。
    *   `s->oconst = nil;` と `s->otype = nil;` が追加されました。これにより、新しい変数`s`が宣言される際に、そのシンボルが定数や型としての古い属性を誤って保持しないように、これらのフィールドが明示的に`nil`に設定されます。これは、ローカル変数`a`がパッケージレベルの定数`a`の`oconst`情報を引き継いでしまう問題を解決します。
*   **`addtyp` 関数**: 型をシンボルテーブルに追加する際に呼び出されます。
    *   `s->oconst = nil;` と `s->oname = nil;` が追加されました。新しい型が宣言される際に、それが定数や変数としての古い属性を保持しないようにします。
*   **`addconst` 関数**: 定数をシンボルテーブルに追加する際に呼び出されます。
    *   `s->otype = nil;` と `s->oname = nil;` が追加されました。新しい定数が宣言される際に、それが型や変数としての古い属性を保持しないようにします。

これらの変更は、シンボルテーブルのエントリが再利用される際に、その属性が常に正しく初期化されることを保証し、異なる種類のシンボル間で属性が混同されることを防ぎます。

### `src/cmd/gc/subr.c` の変更

*   **`Tpretty` 関数**: 型情報を整形して出力する際に使用される関数です。
    *   条件式が `if(s->otype != t || (!s->export && !s->imported))` から `if((s->otype != t || !s->export) && !s->imported)` に変更されました。
    *   この変更は、論理演算子の優先順位と評価順序を変更しています。元の式では `||` の左側 (`s->otype != t`) が偽の場合にのみ `&&` の部分が評価されました。新しい式では、`!s->imported` が常に評価されるようになり、`s->otype != t || !s->export` との論理積が取られます。
    *   これは、インポートされた型に関する比較ロジックをより厳密にするための修正と考えられます。シンボルテーブルのバグ修正により、`s->otype`がより正確になったため、この型比較ロジックもそれに合わせて調整された可能性があります。特に、インポートされたシンボルに対しては、その型が一致しない場合やエクスポートされていない場合でも、特定の表示ロジックを適用しないようにする意図があったのかもしれません。

### `test/fixedbugs/bug161.go` の追加

*   このファイルは、修正されたバグを再現し、修正が正しく適用されたことを検証するためのテストケースです。
*   パッケージレベルで定数`a`を宣言し、その後に同じ名前のパラメータ`a`を持つ関数`f`を定義しています。
*   関数`f`内でパラメータ`a`に代入を行うことで、バグが修正される前には「operation LITERAL not allowed in assignment context」というエラーが発生することを示しています。
*   `// $G $D/$F.go || echo BUG: should compile` という行は、Goコンパイラがこのファイルをエラーなくコンパイルすべきであることを示すテストフレームワークの指示です。

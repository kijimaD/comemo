Goの標準ライブラリは、堅牢性と互換性を非常に重視しており、既存の動作を変更する際には細心の注意が払われます。もし新しい検証ロジックが既存の有効なURLのパースを妨げたり、後方互換性を損なったりするようであれば、その変更は元に戻されるのが一般的です。このリバートは、元の検証ロジックが意図しない副作用をもたらしたため、一度その変更を取り消し、より慎重なアプローチを再検討する必要があると判断されたことを示唆しています。

## 前提知識の解説

### URLの構造とホスト・ポートの解析

URL (Uniform Resource Locator) は、インターネット上のリソースを一意に識別するための文字列です。一般的なURLの構造は以下のようになります。

`scheme://[user:password@]host[:port][/path][?query][#fragment]`

このコミットで関連するのは `host[:port]` の部分です。
- **ホスト (Host)**: リソースが配置されているサーバーのドメイン名またはIPアドレス（IPv4またはIPv6）。
- **ポート (Port)**: サーバー上の特定のサービスを識別するための番号。ホスト名の後にコロン `:` で区切られて指定されます。ポートが省略された場合、スキーム（例: HTTPの80、HTTPSの443）に応じたデフォルトポートが使用されます。

Go言語の `net/url` パッケージは、このURL文字列を解析し、各コンポーネント（スキーム、ホスト、パスなど）に分解するための機能を提供します。特に `url.Parse()` 関数や、内部で利用される `parseHost()` 関数は、ホストとポートの分離を正確に行う上で重要な役割を担います。

### `net/url` パッケージの役割

`net/url` パッケージは、URLの解析、構築、エンコード、デコードといった操作を提供します。これにより、開発者はURLの複雑な仕様を意識することなく、安全かつ正確にURLを扱うことができます。URLの解析においては、ホスト名がIPアドレスであるか、ドメイン名であるか、またポート番号が含まれているかなどを適切に判断する必要があります。特に、IPv6アドレスはコロン `:` を含むため、IPv4アドレスやドメイン名とポートを区別するロジックは慎重に実装されなければなりません。

### ポート検証の重要性

ポート番号は通常、0から65535までの整数値です。不正なポート番号（例: 負の数、非数値、範囲外の数値）が指定された場合、ネットワーク通信が確立できなかったり、セキュリティ上の問題を引き起こしたりする可能性があります。そのため、URLを解析する際にポート番号の形式や値の妥当性を検証することは重要です。しかし、過度に厳密な検証は、RFC（Request for Comments）で定義された有効な形式を拒否してしまう可能性があり、互換性の問題を引き起こすことがあります。

## 技術的詳細

このリバートは、`src/net/url/url.go` 内の `parseHost` 関数と、それに関連するテストファイル `src/net/url/url_test.go` に影響を与えています。

### `parseHost` 関数の役割

`parseHost` 関数は、URLのホスト部分（ポートを含む場合もある）を受け取り、ホスト名とポートを適切に分離し、必要に応じて検証を行う役割を担っています。この関数は、IPv6アドレスの処理（角括弧 `[]` で囲まれているかどうかのチェック）や、ポート番号の有無の検出を行います。

### 元の検証ロジック（リバートされた部分）

リバートされたコードは、`parseHost` 関数内で、IPv6アドレスではないホスト文字列に対して、末尾のコロン `:` を検出した場合にポート検証を行っていました。

```go
// リバート前のコード（元のコミットで追加された部分）
} else if i := strings.LastIndex(host, ":"); i > 0 {
    colonPort := host[i:]
    if !validOptionalPort(colonPort) {
        return "", fmt.Errorf("invalid port %q after host", colonPort)
    }
}
```

このコードスニペットは、ホスト文字列の最後のコロンの位置 `i` を探し、それが0より大きい（つまり、ホスト名の途中にコロンがあるか、ポートが指定されている）場合に、コロン以降の文字列 `colonPort` をポートとして抽出し、`validOptionalPort` 関数でその妥当性を検証していました。`validOptionalPort` は、おそらくポートが数値であるか、または特定の予約語（例: `http` や `https` などのサービス名）であるかをチェックする関数だったと推測されます。

### リバートの理由の推測

この検証ロジックがリバートされた主な理由は、`#14860` で報告された問題、すなわち「過剰な検証」または「誤った検証」にあったと考えられます。

1.  **ホスト名内のコロンの誤解釈**: ホスト名自体にコロンが含まれるケース（例: `my:host.com` のような非標準的なホスト名、あるいは一部の特殊な識別子）において、このロジックがポートと誤認し、不正なポートとしてエラーを返してしまった可能性があります。
2.  **`validOptionalPort` の厳密性**: `validOptionalPort` 関数が、RFCで許容されるが一般的ではないポート形式や、特定の環境で有効なポート文字列を不正と判断してしまった可能性。
3.  **後方互換性の問題**: 以前は許容されていたURL形式が、この新しい検証によって拒否されるようになり、既存のアプリケーションやシステムに影響を与えた可能性。

Goの `net/url` パッケージは、URLの解析において非常に寛容なアプローチを取ることが多く、可能な限り多くの有効なURLをパースしようとします。この検証は、その寛容な原則に反し、不必要なエラーを引き起こしたため、元に戻されたと推測されます。

## コアとなるコードの解説

このコミットの核心は、`parseHost` 関数から特定のポート検証ロジックを削除した点にあります。

削除されたコードブロックは、以下の役割を担っていました。

-   `strings.LastIndex(host, ":")`: ホスト文字列内で最後のコロン `:` の位置を探します。これは、ホスト名とポート番号を区切るための一般的な方法です。
-   `i > 0`: コロンがホスト文字列の先頭ではないことを確認します。これにより、例えば `":80"` のようなホスト名（これは通常無効）と、`example.com:80` のような有効なホスト:ポートの組み合わせを区別しようとします。
-   `colonPort := host[i:]`: コロン以降の文字列をポート候補として抽出します。
-   `!validOptionalPort(colonPort)`: 抽出されたポート候補が `validOptionalPort` 関数によって有効であると判断されない場合に、エラーを発生させます。

このブロックが削除されたことで、`net/url` パッケージは、IPv4アドレスのホスト部分に続くポート文字列に対して、以前のような厳密な形式検証を行わなくなりました。これにより、`foo:bar` のような形式のホスト文字列も、ポート部分が非数値であっても、構文的にはパースされるようになります。これは、URLのパースにおいてより寛容な挙動に戻ったことを意味します。

テストケースの変更は、この挙動の変更を反映しています。不正なポート文字列を含むURLがエラーとならなくなったため、それらのテストケースは不要となり削除されました。また、ホスト名に特殊文字を含むURLの期待される `Host` フィールドも、ポート部分がより柔軟に扱われることを示すように修正されています。

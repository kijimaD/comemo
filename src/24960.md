## 変更の背景

この変更の背景には、Go言語の公式フォーマッタである `gofmt` の `-s` オプションの活用があります。`gofmt -s` は、コードの構文的な整形だけでなく、特定の冗長なコードパターンをより簡潔な形式に書き換える機能を提供します。このコミットは、`gofmt -s` が検出したスライスおよびマップのリテラル表現の簡素化を適用したものです。

Go言語では、複合リテラル（composite literal）を使用して構造体、スライス、配列、マップなどの値を初期化できます。この際、要素の型が文脈から推論できる場合、型名を省略して記述することが可能です。しかし、古いコードベースや、この簡潔な記法が導入される以前に書かれたコードでは、冗長な型名を含む記述が残っていることがあります。

このコミットは、そのような冗長な記述を特定し、Goのイディオムに沿った簡潔な形式に統一することで、コードベース全体の品質と一貫性を向上させることを目的としています。また、Go 1.4との互換性も確認されており、後方互換性を維持しつつコードの改善が行われています。

## 前提知識の解説

### Go言語の複合リテラル (Composite Literals)

Go言語では、構造体、配列、スライス、マップなどの複合型を初期化するために「複合リテラル」を使用します。その基本的な構文は `Type{value1, value2, ...}` のようになります。

例:
*   構造体: `Person{Name: "Alice", Age: 30}`
*   配列: `[3]int{1, 2, 3}`
*   スライス: `[]int{1, 2, 3}`
*   マップ: `map[string]int{"apple": 1, "banana": 2}`

### 型の省略 (Implicit Type Information)

Goの複合リテラルでは、コンパイラが文脈から要素の型を推論できる場合、リテラル内の要素の型名を省略できます。これは、特にスライスやマップのリテラルで頻繁に利用される簡潔な記法です。

例えば、以下のような構造体 `Frame` があるとします。

```go
type Frame struct {
    PC uint64
}
```

この `Frame` 型のスライスを初期化する際、冗長な記述は以下のようになります。

```go
frames := []*Frame{&Frame{PC: 0x100}, &Frame{PC: 0x200}}
```

ここで、`&Frame{PC: 0x100}` の `Frame` は、外側のスライス `[]*Frame` の要素型が `*Frame` であることから推論可能です。したがって、より簡潔な記法では `Frame` を省略できます。

```go
frames := []*Frame{{PC: 0x100}, {PC: 0x200}}
```

同様に、マップリテラルでもキーや値の型が推論できる場合は省略可能です。

### `gofmt -s` コマンド

`gofmt` はGo言語のソースコードを整形するためのツールです。Goのコードベース全体で一貫したスタイルを強制するために広く使用されています。

*   `gofmt -w`: ファイルを整形し、変更を直接ファイルに書き込みます。
*   `gofmt -d`: 整形後の差分を表示します。
*   `gofmt -s`: 単なる整形だけでなく、コードを簡潔にするための特定の簡略化（simplify）を適用します。この簡略化には、前述の複合リテラルにおける型名の省略などが含まれます。

このコミットは、`gofmt -d -s` で簡略化の候補を検出し、`gofmt -w -s` で実際に修正を適用した結果です。

## 技術的詳細

このコミットは、Go言語のコードベースにおける「冗長な複合リテラル」の記述を、`gofmt -s` が推奨する簡潔な形式に統一するものです。具体的には、以下の2つのファイルで変更が行われています。

1.  `src/internal/trace/parser.go`
2.  `src/runtime/trace/trace_stack_test.go`

これらのファイルでは、構造体やスライスの複合リテラルが使用されており、その初期化時に型名が重複して記述されている箇所がありました。

例えば、`&Frame{PC: g.evCreate.Args[1] + 1}` という記述は、`Frame` 型のポインタを生成し、その構造体を初期化しています。しかし、このリテラルが代入される文脈（`ev.Stk = []*Frame{...}`）から、要素が `*Frame` 型であることが明確であるため、内部の `Frame` 型名は省略可能です。

同様に、`trace_stack_test.go` では、`eventDesc{trace.EvGCStart, []frame{...}}` のような記述が多数存在しました。ここで `eventDesc` は構造体の型名であり、このリテラルが代入されるスライス `[]eventDesc` の要素型から `eventDesc` が推論できるため、これも省略可能です。

この変更は、コンパイラの動作やプログラムの実行結果に影響を与えるものではなく、純粋にコードのスタイルと可読性を向上させるための「ジャニタリング（janitoring）」、つまりコードの整理・清掃作業です。

## コアとなるコードの解説

このコミットのコアとなる変更は、Go言語の複合リテラルにおける型名の省略規則を適用したものです。

Go言語の仕様では、複合リテラル `T{...}` において、`T` が配列、スライス、マップの型である場合、その要素の型が `T` の要素型と一致するか、または `T` の要素型に変換可能であれば、要素リテラル内の型名を省略できます。

例えば、`[]*Frame` 型のスライスを初期化する際に、要素として `&Frame{PC: ...}` を記述する場合、外側のスライスが `*Frame` 型の要素を持つことを示しているため、内側の `Frame` は冗長です。コンパイラは `&{PC: ...}` からも `*Frame` 型の値を生成すると推論できます。

同様に、`[]eventDesc` 型のスライスを初期化する際に、要素として `eventDesc{...}` を記述する場合も、外側のスライスが `eventDesc` 型の要素を持つことを示しているため、内側の `eventDesc` は冗長です。コンパイラは `{trace.EvGCStart, ...}` からも `eventDesc` 型の値を生成すると推論できます。

この簡略化は、コードの視覚的なノイズを減らし、より簡潔で読みやすいコードスタイルを促進します。特に、ネストされた複合リテラルが多い場合に、この簡略化はコードの構造をより明確にする効果があります。

この変更は、Goのツールチェーンの一部である `gofmt -s` によって自動的に適用されるタイプの変更であり、Goコミュニティにおける推奨されるコーディングスタイルに沿ったものです。これにより、Goのコードベース全体の一貫性が保たれ、新しい開発者がプロジェクトに参加した際にも、よりGoらしいコードに触れることができます。

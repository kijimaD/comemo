# [インデックス 21535] ファイルの概要

このコミットは、Goランタイムにおけるいくつかのガベージコレクション（GC）関連のバグを修正するものです。具体的には、ゴルーチンのプリエンプション（横取り）処理、1ワードオブジェクトのビットマップ更新におけるアトミック操作の利用、そして`work.nproc`変数の利用方法に関する改善が含まれています。これらの修正は、並行GCの正確性と効率性を向上させ、潜在的な競合状態や優先度逆転問題を解決することを目的としています。

## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）とゴルーチン管理における既存のバグや設計上の課題に対処するために行われました。主な背景は以下の3点です。

1.  **プリエンプションのタイミング問題と優先度逆転**: `newstack`関数（スタック拡張時に呼び出される）におけるプリエンプションチェックのタイミングが遅すぎたため、特定の状況下でゴルーチンの優先度逆転（priority inversion）が発生する可能性がありました。これは、GCやロック保持などの重要なランタイム処理中にゴルーチンがプリエンプトされることで、GCが完了できず、結果としてシステム全体のデッドロックやハングアップを引き起こすリスクを伴いました。
2.  **並行GCにおけるマークビットの欠落**: GoのGCは並行（concurrent）に動作するため、ミューテーター（ユーザーコード）が実行中にGCがオブジェクトをマークすることがあります。特に1ワードのオブジェクト（ポインタのみを含む可能性のあるオブジェクト）のGCビットマップを更新する際に、アトミック操作を使用しないと、並行するGC処理によってマークビットが失われる可能性がありました。これは、GCの正確性に直接影響し、本来回収すべきでないオブジェクトが回収されてしまう（use-after-freeのような）問題を引き起こす可能性があります。
3.  **`work.nproc`の誤用**: `work.nproc`は、Goランタイムが利用可能なプロセッサ（P）の数を表す変数であり、`GOMAXPROCS`によって設定されます。以前のGoランタイムでは、`work.nproc == 1`という条件が、システムがシングルスレッドで動作しているかどうかのシグナルとして誤って使用されることがありました。しかし、並行GCが導入されたGo 1.5以降（このコミットは2015年1月なので、Go 1.5の開発中にあたります）、`work.nproc == 1`であっても、GC自体は並行して動作し、他のPでミューテーターコードが実行されている可能性があります。この誤解は、GCの動作ロジックに不正確さをもたらし、特に並行処理の安全性に影響を与える可能性がありました。

これらの問題は、Goランタイムの安定性、パフォーマンス、および並行処理の正確性にとって重要であり、このコミットによって根本的な解決が図られました。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoランタイムの概念とコンピュータサイエンスの基礎知識が必要です。

1.  **Goのガベージコレクション (GC)**:
    *   GoのGCは、メモリ管理を自動化する仕組みです。Go 1.5以降、Goは並行（concurrent）かつ低遅延のマーク＆スイープGCを採用しています。
    *   **マークフェーズ**: GCは、到達可能なオブジェクト（プログラムがまだ使用しているオブジェクト）を特定し、「マーク」します。GoのGCはトライカラー（三色）アルゴリズムを使用し、オブジェクトを白（未訪問）、灰（訪問済みだが参照先未探索）、黒（訪問済みで参照先探索済み）に分類します。
    *   **スイープフェーズ**: マークされなかったオブジェクト（到達不可能なオブジェクト）のメモリを解放し、再利用可能にします。
    *   **並行GC**: GCの大部分がミューテーター（ユーザーコード）と並行して実行されるため、アプリケーションの停止時間（Stop-the-World: STW）が最小限に抑えられます。
    *   **GCビットマップ**: ヒープ上の各オブジェクトのポインタ情報やGC状態（マーク済みかどうかなど）を効率的に管理するために使用されるデータ構造です。オブジェクトのサイズや種類に応じて、ビットマップの特定のビットが設定されます。

2.  **ゴルーチンとスケジューラ**:
    *   **ゴルーチン (Goroutine)**: Goにおける軽量な並行実行単位です。OSスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行できます。
    *   **Goスケジューラ**: ゴルーチンをOSスレッド（M: Machine）にマッピングし、実行を管理するGoランタイムの一部です。スケジューラは、P（Processor）と呼ばれる論理プロセッサの概念を使用し、MとPの間でゴルーチンを効率的にディスパッチします。
    *   **プリエンプション (Preemption)**: スケジューラが、実行中のゴルーチンを強制的に中断し、別のゴルーチンにCPUを割り当てるメカニズムです。これにより、CPUを占有するゴルーチンによる他のゴルーチンの飢餓状態を防ぎ、公平なCPU利用を保証します。Go 1.14で非同期プリエンプションが導入される前は、Goのプリエンプションは協調的（cooperative）な側面が強く、特定の安全なポイント（関数呼び出しなど）でしか発生しませんでした。このコミットの時点（2015年）では、まだ完全な非同期プリエンプションは導入されていませんでしたが、ランタイムはプリエンプションの概念を持っていました。
    *   **`newstack`関数**: ゴルーチンのスタックが不足した際に、より大きなスタックを割り当てるためにGoランタイムが呼び出す内部関数です。

3.  **アトミック操作 (Atomic Operations)**:
    *   複数のCPUコアやゴルーチンが共有メモリに同時にアクセスする際に、データの整合性を保証するための操作です。
    *   アトミック操作は、不可分（indivisible）であり、他の操作によって中断されることなく完了します。これにより、競合状態（race condition）を防ぎ、データ破損を回避します。
    *   Goでは`sync/atomic`パッケージを通じて提供され、`atomic.LoadUint32`や`atomic.AddUint64`などがあります。このコミットでは、`atomicor8`という関数が使用されており、これは8ビット（1バイト）の値をアトミックにビットOR演算で更新する低レベルな操作を指します。

4.  **優先度逆転 (Priority Inversion)**:
    *   高優先度のタスクが、低優先度のタスクが保持しているリソース（ロックなど）を待つためにブロックされ、結果として低優先度のタスクが実行されるまで高優先度のタスクが実行できない状態を指します。これはリアルタイムシステムで特に問題となりますが、Goランタイムのような並行システムでも発生し得ます。

5.  **`work.nproc`**:
    *   Goランタイム内部で使用される変数で、Goスケジューラが利用可能な論理プロセッサ（P）の数を表します。これは通常、`GOMAXPROCS`環境変数または`runtime.GOMAXPROCS()`関数によって設定されます。

## 技術的詳細

このコミットは、Goランタイムの3つの異なる領域にわたるGC関連のバグを修正しています。

1.  **`newstack`における非プリエンプションチェックの早期化**:
    *   **問題**: 以前の`newstack`関数では、ゴルーチンがGC中、メモリ割り当て中、またはロックを保持している場合にプリエンプトされないようにするチェックが、ゴルーチンのステータスを`_Grunning`から`_Gwaiting`に変更する`casgstatus`呼び出しの**後**に配置されていました。
    *   **影響**: `casgstatus`呼び出し自体が、GCがゴルーチンの状態を`_Gscanwaiting`に変更する可能性のある「小さなプリエンプション」と見なされることがありました。もしGCがこのゴルーチンに依存している（例えば、ゴルーチンがGCに必要なロックを保持している）場合、この「小さなプリエンプション」がデッドロックを引き起こし、優先度逆転問題につながる可能性がありました。
    *   **修正**: プリエンプションを避けるべき条件（`thisg.m.locks != 0 || thisg.m.mallocing != 0 || thisg.m.gcing != 0 || thisg.m.p.status != _Prunning`）のチェックを、`casgstatus`呼び出しの**前**に移動しました。これにより、重要なランタイム処理中にゴルーチンが不必要に`_Gwaiting`状態に遷移することを防ぎ、優先度逆転のリスクを軽減します。もしプリエンプションを避けるべき状況であれば、ゴルーチンは`gogo(&gp.sched)`によってすぐに実行に戻され、`gp.stackguard0`がリセットされて次の機会にプリエンプトされるようにします。

2.  **1ワードオブジェクトのビットマップ更新におけるアトミック操作の常時使用**:
    *   **問題**: `src/runtime/malloc.go`の`mallocgc`関数と`src/runtime/mgc.go`の`gcmarknewobject_m`および`greyobject`関数において、1ワードのオブジェクト（ポインタサイズと同じサイズのオブジェクト）のGCビットマップを更新する際に、特定の条件下で非アトミックな操作が使用されていました。具体的には、`mbits.xbits&(bitMask|(bitMask<<gcBits)) != bitBoundary|bitBoundary<<gcBits || work.nproc == 1`という条件が真の場合、非アトミックな`*mbits.bitp = ...`による更新が行われていました。このロジックは、隣接するオブジェクトとビットマップバイトを共有している場合や、並行GCが同時にマーク処理を行っている場合に、マークビットの欠落（lost mark bits）を引き起こす可能性がありました。
    *   **影響**: マークビットが欠落すると、GCがオブジェクトを到達不可能と誤認識し、まだ使用中のメモリを解放してしまう可能性があります。これは、プログラムのクラッシュや予期せぬ動作につながる深刻なバグです。
    *   **修正**: 1ワードオブジェクトのビットマップ更新において、常に`atomicor8`関数を使用するように変更されました。これにより、複数のゴルーチンやGCプロセスが同時にビットマップを更新しようとした場合でも、操作の不可分性が保証され、マークビットの欠落が防止されます。コメントにも「以前は特定のケースで非アトミックな更新を使用する賢い方法があったが、リスクに見合わない」と明記されており、安全性を優先した変更であることが示されています。

3.  **`work.nproc == 1`の誤用排除**:
    *   **問題**: `src/runtime/mgc.go`の`getfull`関数において、`work.nproc == 1`という条件が、システムがシングルスレッドで動作しているかどうかのシグナルとして使用されていました（`if b != nil || work.nproc == 1`）。しかし、Goの並行GCは、`work.nproc`が1であっても、GCワーカーゴルーチンとミューテーターゴルーチンが並行して動作する可能性があります。この条件は、並行GCのコンテキストでは誤解を招き、不正確なロジックにつながる可能性がありました。
    *   **影響**: `work.nproc == 1`がシングルスレッドのシグナルとして使われると、並行GCの動作が正しく考慮されず、GCの効率や正確性に影響を与える可能性がありました。コミットメッセージでは、`getfull`におけるこの使用は「安全である」と述べられていますが、それでも「単一のアトミック操作を節約するだけなので、とにかく削除する」とされており、将来的な混乱や誤解を避けるためのクリーンアップとして行われました。
    *   **修正**: `getfull`関数から`|| work.nproc == 1`の条件が削除されました。これにより、`getfull`のロジックは、`work.nproc`の値に依存せず、より普遍的で正確な動作をするようになりました。

## コアとなるコードの解説

1.  **`src/runtime/stack1.go`におけるプリエンプションチェックの移動**:
    *   `newstack`関数は、ゴルーチンのスタックが不足した際に新しいスタックを割り当てるために呼び出されます。このプロセス中に、Goランタイムはゴルーチンを一時的に停止させ、その状態を変更することがあります。
    *   変更前は、`casgstatus(gp, _Grunning, _Gwaiting)`（ゴルーチンの状態を`Grunning`から`Gwaiting`に変更するアトミック操作）の後に、プリエンプションを避けるべき条件（ロック保持、メモリ割り当て中、GC中など）のチェックが行われていました。
    *   この`casgstatus`呼び出し自体が、GCがゴルーチンの状態を`_Gscanwaiting`に変更する可能性のある「小さなプリエンプション」と見なされることがありました。もしGCがこのゴルーチンに依存している場合、この状態変更がデッドロックを引き起こす可能性がありました。
    *   修正では、このプリエンプションを避けるべき条件のチェックが`casgstatus`呼び出しの**前**に移動されました。これにより、ゴルーチンが重要なランタイム処理中に不必要に`_Gwaiting`状態に遷移することを防ぎます。もしプリエンプションを避けるべき状況であれば、ゴルーチンは`gogo(&gp.sched)`によってすぐに実行に戻され、`gp.stackguard0`がリセットされて次の機会にプリエンプトされるようにします。これは、優先度逆転問題を回避し、ランタイムの安定性を向上させるための重要な変更です。

2.  **`src/runtime/malloc.go`および`src/runtime/mgc.go`におけるアトミック操作の常時使用**:
    *   GoのGCは並行に動作するため、ミューテーター（ユーザーコード）とGCワーカーゴルーチンが同時にメモリ上のオブジェクトのGCビットマップを更新しようとすることがあります。
    *   特に1ワードのオブジェクト（ポインタのみを含むオブジェクト）の場合、そのGCビットマップは隣接するオブジェクトとバイトを共有している可能性があり、複数の並行操作が同じバイトを更新しようとすると競合状態が発生します。
    *   変更前は、特定の「賢い」条件分岐（`mbits.xbits&(bitMask|...) || work.nproc == 1`）の下で非アトミックなビットマップ更新が行われていました。このロジックは、並行GCの複雑な相互作用において、マークビットの欠落を引き起こす脆弱性がありました。マークビットが欠落すると、GCがまだ到達可能なオブジェクトを誤って回収してしまい、深刻なメモリ破損やクラッシュにつながります。
    *   修正では、これらの箇所で常に`atomicor8`関数を使用するように変更されました。`atomicor8`は、指定されたメモリ位置のバイト値をアトミックにビットOR演算で更新します。これにより、複数のゴルーチンが同時にビットマップを更新しようとしても、操作の不可分性が保証され、競合状態が排除され、マークビットの欠落が確実に防止されます。これは、並行GCの正確性と堅牢性を大幅に向上させるための重要な変更です。

3.  **`src/runtime/mgc.go`における`work.nproc == 1`の誤用排除**:
    *   `work.nproc`は、Goランタイムが利用可能な論理プロセッサ（P）の数を表します。Go 1.5以降の並行GCでは、`work.nproc`が1であっても、GCワーカーゴルーチンとミューテーターゴルーチンが並行して動作することが可能です。
    *   変更前は、`getfull`関数内で`if b != nil || work.nproc == 1`という条件が使用されていました。これは、`work.nproc == 1`がシステムがシングルスレッドで動作しているという誤った前提に基づいていました。
    *   コミットメッセージでは、この特定のケースでの`work.nproc == 1`の使用は「安全である」とされていますが、それでも「単一のアトミック操作を節約するだけなので、とにかく削除する」と述べられています。これは、将来的な誤解や、より複雑な並行シナリオでの潜在的なバグを防ぐための、設計のクリーンアップと堅牢化を目的としています。
    *   修正では、`|| work.nproc == 1`の条件が削除され、`if b != nil`のみになりました。これにより、`getfull`のロジックは`work.nproc`の値に依存しなくなり、並行GCのコンテキストにおいてより正確で普遍的な動作をするようになりました。

これらの変更は、Goランタイムの並行処理モデルの成熟と、GCの正確性および安定性に対する継続的な改善努力を反映しています。

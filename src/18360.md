# [インデックス 18360] ファイルの概要

このコミットは、GoランタイムにおけるWindowsビルドでのクラッシュを修正するものです。具体的には、`schedinit`（スケジューラ初期化）フェーズでの初期メモリ割り当てが、`m->p`（現在のM（マシン）に紐付けられたP（プロセッサ））がまだ適切に設定されていない状態で小さなメモリブロックを割り当てようとすることによって発生する問題を解決します。この修正は、`tiny`オブジェクトのアロケータキャッシュ（`tiny`と`tinysize`）の管理を`P`構造体から`MCache`構造体へ移行することで実現されています。

## 元コミット内容

GoランタイムのWindowsビルドにおいて、`schedinit`の初期段階で発生するクラッシュを修正します。このクラッシュは、`schedinit`中の初期のメモリ割り当てが、`m->p`（現在のM（マシン）に紐付けられたP（プロセッサ））がまだ設定されていない状態で小さなメモリブロックを割り当てようとすることで引き起こされていました。コミットの作者は、`procresize(1)`を`schedinit`のより早い段階で呼び出すことも検討しましたが、現在のリファクタリングの方がより良い解決策であり、この問題を修正するはずだと述べています。このコミットはIssue #7218を修正します。

## 変更の背景

Goランタイムは、プログラムの起動時に`schedinit`関数を呼び出し、スケジューラやメモリ管理システムなどのコアコンポーネントを初期化します。この初期化プロセス中に、Goランタイム自身が内部的にメモリを割り当てる必要があります。特に、非常に小さなオブジェクト（ポインタを含まない「tiny objects」）の割り当ては、最適化のために特別なパスを通ることがあります。

問題は、Windows環境において、`schedinit`の非常に早い段階でこれらの「tiny objects」の割り当てが発生した際に、その割り当てロジックが`m->p`（現在の実行スレッドが関連付けられているプロセッサコンテキスト）に依存していた点にありました。しかし、`schedinit`のその時点では、`m->p`がまだ適切に初期化されていない、つまり有効な`P`構造体へのポインタが設定されていない状態でした。この`nil`または不正な`P`へのアクセスが、Windows上でのクラッシュを引き起こしていました。

コミットの作者は、この問題を解決するために`procresize(1)`を早期に呼び出すことも検討しましたが、これは`P`の数を調整する関数であり、根本的な原因（`tiny`オブジェクトのキャッシュが`P`に紐付いていること）を解決するものではないと判断しました。代わりに、`tiny`オブジェクトのキャッシュを`P`から`MCache`に移動させるという、より構造的なリファクタリングを選択しました。これにより、`P`の初期化状態に依存することなく、`tiny`オブジェクトの割り当てが可能になります。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の主要な概念を理解しておく必要があります。

1.  **M (Machine/Thread)**: オペレーティングシステムのスレッドを表します。Goランタイムは、OSスレッドをMとして抽象化し、その上でGoルーチンを実行します。Mは、Goルーチンを実行するために必要なリソース（スタック、レジスタなど）を管理します。
2.  **P (Processor)**: 論理プロセッサを表します。Goスケジューラは、GoルーチンをM上で実行するためにPを必要とします。Pは、実行可能なGoルーチンのキューを保持し、MにGoルーチンをディスパッチします。Pの数は、`GOMAXPROCS`環境変数によって制御され、通常はCPUコア数に設定されます。
3.  **G (Goroutine)**: Goランタイムによって管理される軽量な実行単位です。GoルーチンはM上で実行され、Pによってスケジューリングされます。
4.  **MCache (Memory Cache)**: 各M（OSスレッド）にローカルなメモリキャッシュです。Goのメモリ割り当ては、GC（ガベージコレクション）のオーバーヘッドを減らすために、スレッドローカルなキャッシュ（MCache）を積極的に利用します。これにより、頻繁なヒープロックを回避し、アロケーションのパフォーマンスを向上させます。MCacheは、特定のサイズのオブジェクトを割り当てるためのフリーリストを保持しています。
5.  **Tiny Allocator**: Goランタイムのメモリ割り当てにおいて、非常に小さなオブジェクト（特にポインタを含まないオブジェクト）のために最適化されたアロケータです。これらのオブジェクトは、通常のメモリ割り当てパスを通らず、MCache内に確保された小さなブロックから直接割り当てられます。これにより、アロケーションのオーバーヘッドがさらに削減されます。`tiny`と`tinysize`は、このTiny Allocatorが使用する現在の小さなブロックのポインタと残りサイズを管理します。
6.  **`schedinit`**: Goプログラムが起動する際に最初に実行されるランタイム初期化関数の一つです。この関数は、スケジューラ、メモリ管理、GCなどのGoランタイムの基本的なコンポーネントをセットアップします。
7.  **`procresize`**: GoランタイムのPの数を変更する関数です。`GOMAXPROCS`の変更や、初期化時にPの数を設定するために使用されます。

## 技術的詳細

このコミットの核心は、Goランタイムのメモリ割り当てロジックにおける`tiny`オブジェクトのキャッシュ管理の変更です。

変更前は、`tiny`オブジェクトのキャッシュ（`tiny`ポインタと`tinysize`）は`P`構造体（`runtime.h`で定義）のメンバーとして存在していました。これは、各論理プロセッサ（P）が独自の小さなオブジェクトキャッシュを持つという設計思想に基づいています。しかし、`schedinit`の初期段階では、M（OSスレッド）がPにまだ関連付けられていない、または関連付けられていてもPが完全に初期化されていない状況が発生し得ます。この状態で`runtime·mallocgc`関数が呼び出され、`m->p`を介して`P`の`tiny`および`tinysize`にアクセスしようとすると、`m->p`が`nil`であるか、不正な値であるためにクラッシュが発生していました。

このコミットでは、`tiny`と`tinysize`のフィールドを`P`構造体から`MCache`構造体（`malloc.h`で定義）に移動させました。

-   **`src/pkg/runtime/runtime.h`**: `P`構造体から`tiny`と`tinysize`の定義が削除されます。
-   **`src/pkg/runtime/malloc.h`**: `MCache`構造体に`tiny`と`tinysize`の定義が追加されます。これにより、`tiny`オブジェクトのキャッシュがM（OSスレッド）にローカルなMCacheの一部となります。
-   **`src/pkg/runtime/malloc.goc`**: `runtime·mallocgc`関数内で、`tiny`と`tinysize`へのアクセスが`p->tiny`や`p->tinysize`から`c->tiny`や`c->tinysize`に変更されます。ここで`c`は現在のMに紐付けられたMCacheへのポインタです。`m->p`が未設定でも、`m->mcache`は通常、より早期に利用可能であるため、この変更によりクラッシュが回避されます。
-   **`src/pkg/runtime/mgc0.c`**: `clearpools`関数内で、GC（ガベージコレクション）時に`tiny`オブジェクトのキャッシュをクリアするロジックが変更されます。以前は`p->tiny = nil; p->tinysize = 0;`のようにPを直接操作していましたが、変更後は`c = p->mcache;`でMCacheを取得し、`c->tiny = nil; c->tinysize = 0;`のようにMCacheを介してクリアするようになります。これにより、`tiny`キャッシュの管理がMCacheに一元化されます。

このリファクタリングにより、`tiny`オブジェクトの割り当てが`P`の初期化状態に依存しなくなり、`schedinit`の早い段階でのメモリ割り当てが安全に行えるようになります。MCacheはM（OSスレッド）に直接関連付けられているため、Mが起動すればMCacheも利用可能になり、`P`の準備が整うのを待つ必要がなくなります。

## コアとなるコードの解説

このコミットの主要な変更は、`tiny`オブジェクトの割り当てに使用される`tiny`と`tinysize`という2つのフィールドの所有権を`P`構造体から`MCache`構造体へ移したことです。

-   **`P`構造体からの削除**: 以前、`P`構造体は`tiny`と`tinysize`を持っていました。これは、各論理プロセッサ（P）が独自の小さなオブジェクトのキャッシュを持つという考え方に基づいています。しかし、`schedinit`の初期段階では、`M`（OSスレッド）がまだ有効な`P`に紐付けられていないか、`P`が完全に初期化されていない可能性がありました。この状態で`runtime·mallocgc`が`m->p->tiny`や`m->p->tinysize`にアクセスしようとすると、`m->p`が`nil`であるためにクラッシュが発生していました。

-   **`MCache`構造体への追加**: `MCache`は各`M`（OSスレッド）にローカルなメモリキャッシュです。`M`が起動すると、その`MCache`は比較的早期に利用可能になります。`tiny`と`tinysize`を`MCache`に移動させることで、`tiny`オブジェクトの割り当てが`P`の初期化状態に依存しなくなります。`runtime·mallocgc`関数は、現在の`M`から`MCache`（`m->mcache`）を取得し、その`MCache`の`tiny`と`tinysize`にアクセスするようになります。これにより、`P`がまだ設定されていなくても、`tiny`オブジェクトの割り当てを安全に行うことができるようになり、Windowsでのクラッシュが回避されます。

-   **`malloc.goc`の変更**: `runtime·mallocgc`関数は、Goの主要なメモリ割り当て関数です。この関数内で、`tiny`オブジェクトの割り当てロジックが変更されました。具体的には、`p->tinysize`、`p->tiny`、`p->tiny += size1`、`p->tinysize -= size1`、`p->tiny = (byte*)v + size`、`p->tinysize = TinySize - size`といった`P`への直接アクセスが、対応する`c->tinysize`、`c->tiny`など、`MCache`へのアクセスに置き換えられました。これにより、`tiny`オブジェクトのキャッシュ管理が`MCache`に委譲されます。

-   **`mgc0.c`の変更**: `clearpools`関数は、GCサイクル中にメモリプールをクリアする役割を担います。この関数も、`tiny`オブジェクトのキャッシュをクリアする際に、`P`から直接アクセスするのではなく、`p->mcache`を介して`MCache`にアクセスするように変更されました。これにより、`tiny`キャッシュのライフサイクル管理が`MCache`と整合性が取れるようになります。

この変更は、Goランタイムのメモリ管理における責任の分離と、初期化順序に関する依存関係の解消を目的としています。`tiny`オブジェクトのキャッシュは、特定の`P`の実行コンテキストよりも、むしろ特定の`M`（OSスレッド）のメモリ割り当てコンテキストに密接に関連しているため、`MCache`に配置する方がより論理的かつ堅牢な設計と言えます。

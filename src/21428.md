# [インデックス 21428] ファイルの概要

このコミットは、以前のコミット `ab0535ae3fb45ba734d47542cc4845f27f708d1b` を元に戻すものです。具体的には、Goランタイムにおけるスタックガードの仕組み、特に `stackguard1` の概念を再導入し、GoコードとCコードが混在する環境でのスタック管理を改善することを目的としています。これにより、システムスタック上で実行されるべきコードと、通常のGoルーチンスタック上で実行可能なコードを区別する能力が回復されます。

## 元コミット内容

このコミットが元に戻す `ab0535ae3fb45ba734d47542cc4845f27f708d1b` は、Goランタイムから `stackguard1` の概念とそれに関連するスタック管理ロジックを削除するものでした。これは、Goのスタック管理を簡素化する試みの一環であったと考えられます。

## 変更の背景

Goランタイムは、ゴルーチンごとに動的に伸縮するスタック（スプリットスタック）を使用しています。スタックの拡張が必要になった場合、`morestack` 関数が呼び出され、より大きなスタックが割り当てられます。このスタックチェックは、関数のプロローグで行われます。

以前のコミット `ab0535ae3fb45ba734d47542cc4845f27f708d1b` は、`stackguard1` を削除することで、このスタック管理を簡素化しようとしました。しかし、このコミットの作者であるRuss Coxは、GoのコードとCのコードが混在する環境（特にCgoを使用する場合）において、システムスタック上で実行されるべきコードと、通常のGoルーチンスタック上で実行可能なコードを区別する機能が依然として重要であると判断しました。

Cgoを介してCの関数を呼び出す場合、GoのランタイムはCのスタック規約とGoのスタック規約の両方を考慮する必要があります。特に、CのコードがGoのスタックを直接操作したり、Goのスタック拡張メカニズムをトリガーしたりする可能性を考慮すると、異なるスタックガードの概念が必要になります。このコミットは、将来的に `//go:systemstack` のようなディレクティブを導入し、特定のGo関数がC関数のようにシステムスタック上で動作することをコンパイラに指示できるようにするための布石でもあります。これにより、GoとCの相互運用におけるスタックの安全性が向上し、より堅牢なランタイムが実現されます。

## 前提知識の解説

### Goのスタック管理 (Split Stack)

Goのゴルーチンは、非常に小さなスタック（通常は数KB）で開始し、必要に応じて自動的にスタックを拡張します。これを「スプリットスタック」と呼びます。関数呼び出しの際、Goコンパイラはスタックの残量をチェックするプロローグコードを挿入します。スタックが不足している場合、`runtime.morestack` 関数が呼び出され、新しい大きなスタックが割り当てられ、既存のスタックの内容がコピーされます。

### `g` 構造体と `stackguard`

Goランタイムでは、各ゴルーチンは `runtime.g` 構造体によって表現されます。この構造体には、ゴルーチンのスタックに関する情報が含まれています。
- `stack`: スタックの開始アドレスと終了アドレスを保持します。
- `stackguard`: スタックオーバーフローを検出するための閾値となるスタックポインタのアドレスです。関数のプロローグで現在のスタックポインタが `stackguard` の値と比較され、`stackguard` を下回る場合（スタックが不足している場合）、`morestack` が呼び出されます。

### GoとCの相互運用 (Cgo)

GoはC言語のコードを呼び出すための `cgo` ツールを提供しています。Cgoを使用すると、GoプログラムからCの関数を呼び出したり、Cの関数からGoの関数を呼び出したりできます。この際、GoとCのスタック管理の違いが問題となることがあります。Cの関数はGoのスプリットスタックの概念を知らないため、Goのスタック拡張メカニズムを適切に扱えない可能性があります。

### `NOSPLIT` 関数

Goの関数には `//go:nosplit` ディレクティブを付与することができます。これは、その関数がスタックチェックを行わないことをコンパイラに指示します。`NOSPLIT` 関数は、スタックを拡張しないことが保証されている、非常に短い関数や、ランタイムの低レベルな部分でスタックチェックが不適切な場合に使用されます。

### システムスタック

Goランタイムは、通常のゴルーチンスタックとは別に、システムスタック（またはMスタック）と呼ばれる特別なスタックを使用します。これは、スケジューラやガベージコレクタなどのランタイムのコア部分が実行される際に使用されるスタックです。システムスタックは、Goのゴルーチンスタックとは異なる管理方法が取られます。

## 技術的詳細

このコミットの主要な技術的変更点は、`g` 構造体における `stackguard` フィールドを `stackguard0` と `stackguard1` の2つに分割し、リンカとランタイムのロジックをこれに合わせて調整したことです。

1.  **`stackguard0` と `stackguard1` の導入**:
    *   `g.stackguard0`: 主にGoのコードからのスタックチェックに使用されます。通常のGoルーチンがスタックを拡張する際に参照する閾値です。
    *   `g.stackguard1`: 主にCgoを介してCから呼び出されるGo関数（またはシステムスタック上で実行されるGo関数）のスタックチェックに使用されます。この値は、システムスタックの境界を示すか、あるいはスタック拡張をトリガーしないように設定されます。

2.  **`LSym.cfunc` フィールドの追加**:
    *   リンカのシンボル構造体 `LSym` に `cfunc` という新しいフィールドが追加されました。このフィールドは、そのシンボルがCから呼び出されるGo関数であるかどうかを示すフラグとして使用されます。これにより、リンカはGoとCの相互運用におけるスタックの挙動をより正確に追跡し、適切なスタックチェックロジックを適用できるようになります。

3.  **リンカ (`cmd/ld`, `liblink`) の変更**:
    *   `src/cmd/ld/lib.c` に `checkgo` 関数が追加されました。この関数は、Goから呼び出されるC関数（またはその逆）の呼び出しグラフを分析し、`cfunc` フラグを伝播させます。特に、Goから呼び出されるC関数がスタックを分割できる（つまり、Goのスタック拡張メカニズムをトリガーできる）場合に警告を発するロジックが含まれています。
    *   `src/liblink/obj*.c` (各アーキテクチャのオブジェクトファイル処理) の `stacksplit` 関数が変更されました。この関数は、関数のプロローグにスタックチェックコードを挿入する役割を担っています。変更後、`cursym->cfunc` の値に基づいて `g.stackguard0` または `g.stackguard1` のどちらを参照するかが決定されます。
    *   `runtime.morestackc` という新しいランタイム関数への呼び出しが導入されました。これは、`cfunc` が設定された関数（Cから呼び出されるGo関数）がスタック拡張を必要とした場合に呼び出されます。`morestackc` は、Goスタック上でCコードを実行しようとするとパニックを発生させることで、スタックの不整合を防ぎます。

4.  **アセンブリコード (`src/runtime/asm_*.s`) の変更**:
    *   各アーキテクチャのアセンブリコードにおいて、`g_stackguard` の初期化が `g_stackguard0` と `g_stackguard1` の両方に対して行われるようになりました。これにより、ランタイムの初期化段階で両方のスタックガードが適切に設定されます。

5.  **Goランタイムコードの変更**:
    *   `src/runtime/runtime2.go` の `g` 構造体定義が更新され、`stackguard0` と `stackguard1` が明示的に定義されました。
    *   `src/runtime/malloc.go`, `src/runtime/proc1.go`, `src/runtime/runtime1.go`, `src/runtime/stack1.go` など、`g.stackguard` を参照していた多くの箇所が、`g.stackguard0` または `g.stackguard1` に変更されました。これにより、スタックガードの概念がより細分化され、GoとCのスタック管理が明確に区別されるようになりました。
    *   `src/runtime/stack1.go` に `morestackc` 関数が追加されました。この関数は `//go:nosplit` ディレクティブを持ち、システムスタック上で実行されることを意図しています。Goスタック上でCコードを実行しようとした場合に `throw("attempt to execute C code on Go stack")` を呼び出してパニックを発生させます。

これらの変更により、GoランタイムはGoとCのスタックの境界をより厳密に管理できるようになり、Cgoを使用する際のスタック関連のバグや予期せぬ挙動のリスクが低減されます。

## コアとなるコードの解説

このコミットの核となる変更は、GoランタイムがGoとCのスタックをより厳密に区別し、管理するためのメカニズムを再導入した点にあります。

1.  **`LSym.cfunc` の役割**:
    `LSym` 構造体に追加された `cfunc` フィールドは、リンカがGoのシンボルがCから呼び出される可能性があるかどうかを追跡するために使用されます。この情報は、スタックチェックの挙動を決定する上で非常に重要です。`cfunc` が設定されたGo関数は、Cの呼び出し規約に従ってスタックを扱う必要があるため、通常のGo関数とは異なるスタックガードの閾値を使用します。

2.  **`checkgo` 関数のロジック**:
    `checkgo` 関数は、リンカの最終段階で呼び出され、GoとCの関数間の呼び出し関係を分析します。特に、Goから呼び出されるC関数がスタックを分割できる（つまり、Goのスタック拡張メカニズムをトリガーできる）場合に、潜在的な問題を検出します。この関数は、`cfunc` フラグを再帰的に伝播させ、GoとCのスタックの境界を越える呼び出しにおけるスタックの安全性を検証します。

3.  **`stacksplit` における `stackguard0` と `stackguard1` の使い分け**:
    `stacksplit` 関数は、Go関数のプロローグにスタックチェックコードを挿入します。このコミットにより、`stacksplit` は `cursym->cfunc` の値に基づいて、`g.stackguard0` と `g.stackguard1` のどちらをスタックガードの閾値として使用するかを動的に選択するようになりました。
    *   通常のGo関数（`cfunc` が設定されていない）は `g.stackguard0` を使用し、Goの通常のスタック拡張メカニズムに従います。
    *   Cから呼び出されるGo関数（`cfunc` が設定されている）は `g.stackguard1` を使用します。これにより、Cのスタック規約とGoのスタック規約の間の橋渡しがより安全に行われます。

4.  **`runtime.morestackc` の導入**:
    `morestackc` は、Cから呼び出されるGo関数がスタック拡張を必要とした場合に呼び出される特別な関数です。この関数は `systemstack` 上で実行され、Goスタック上でCコードを実行しようとするとパニックを発生させます。これは、CのコードがGoのスプリットスタックの概念を理解していないため、Goのスタック拡張中にCのコードが予期せぬ動作をするのを防ぐための安全策です。

これらの変更は、GoのランタイムがCgoを介したGoとCの相互運用において、より堅牢なスタック管理を提供することを可能にします。これにより、GoプログラムがCライブラリと連携する際の安定性と信頼性が向上します。

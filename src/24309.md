# [インデックス 24309] ファイルの概要

このコミットは、Goリンカ（`cmd/link`）における最適化を導入するものです。具体的には、ガベージコレクタ（GC）が使用する「gcbits」シンボルを個別にエリジョン（省略・削除）することで、生成されるバイナリのサイズを削減し、DWARFデバッグ情報からこれらのシンボルを除外します。これは、以前から行われていた文字列シンボルのエリジョンと同様のアプローチをgcbitsシンボルにも適用するものです。

## 変更の背景

Goのバイナリサイズは、特に組み込みシステムやコンテナ環境において重要な考慮事項です。リンカは、コンパイルされたオブジェクトファイルを結合して実行可能ファイルを生成する際に、プログラム内の様々な要素（関数、変数、型など）をシンボルとして管理します。これらのシンボルはシンボルテーブルに格納され、デバッグ情報（DWARF）にも含まれることがあります。

このコミットの背景には、Goのバイナリサイズを削減し、リンカの効率を向上させるという目的があります。特に、Goのガベージコレクタが使用する「gcbits」シンボルは、プログラムの実行には必要ですが、個々のシンボルがデバッグ情報やシンボルテーブルに詳細に記録される必要がない場合があります。

コミットメッセージにある「Same as we do for string symbols.」という記述は、この最適化が以前に文字列シンボルに対して行われた最適化と同様のパターンに従っていることを示唆しています。文字列リテラルも多数存在する場合、個々の文字列シンボルをリンカが詳細に管理すると、バイナリサイズが増大する可能性があります。そのため、これらをまとめて処理することで最適化を図っていました。

同様に、`runtime.gcbits`シンボルも多数生成される可能性があり、これらを個別に扱うことはバイナリの肥大化を招きます。この変更は、これらのgcbitsシンボルを「エリジョン」することで、シンボルテーブルのエントリ数を減らし、結果としてバイナリサイズを削減し、リンカの処理を高速化することを目的としています。また、デバッグ情報からこれらのシンボルを除外することで、デバッグ情報のサイズも削減されます。

## 前提知識の解説

### Goリンカ (cmd/link)

`cmd/link`は、Go言語のツールチェインの一部であり、Goプログラムのコンパイル済みオブジェクトファイル（`.o`ファイル）を結合して、実行可能なバイナリ（またはライブラリ）を生成する役割を担います。リンカは、プログラム内の参照を解決し、必要なコードとデータを配置し、最終的な実行可能ファイルを構築します。バイナリのサイズやパフォーマンスに直接影響を与えるため、リンカの最適化は非常に重要です。

### シンボル (Symbols) とシンボルテーブル (Symbol Table)

プログラム内の関数、変数、型、定数などは、リンカによって「シンボル」として扱われます。シンボルは、プログラムの異なる部分が互いに参照できるようにするための名前付きエントリです。リンカは、これらのシンボルとそのアドレスや属性を「シンボルテーブル」というデータ構造で管理します。シンボルテーブルは、デバッグ、プロファイリング、動的リンクなどに利用されます。

### GCビット (Garbage Collector Bits)

Goのガベージコレクタ（GC）は、メモリ管理の重要な部分です。GCは、ヒープ上のオブジェクトがポインタを含んでいるかどうかを識別する必要があります。これにより、GCはポインタをたどって到達可能なオブジェクトを正確にマークし、到達不能なオブジェクトを解放できます。このポインタの有無に関するメタデータが「gcbits」です。`runtime.gcbits`という名前のシンボルは、これらのGCビット情報に関連するデータやコードを指します。これらはGoランタイムの内部で利用され、通常、開発者が直接意識することはありませんが、バイナリの正確な動作には不可欠です。

### DWARFデバッグ情報

DWARF (Debugging With Attributed Record Formats) は、ソースコードレベルでのデバッグを可能にするための標準的なデバッグ情報フォーマットです。コンパイラやリンカは、元のソースコードの構造（変数名、型、行番号、関数名など）と、生成された機械語コードとのマッピングをDWARF情報としてバイナリに埋め込みます。デバッガはこの情報を使用して、実行中のプログラムの状態をソースコードの観点から表示します。DWARF情報は非常に詳細であるため、バイナリサイズを大きくする要因の一つとなります。

### シンボルエリジョン (Symbol Elision)

シンボルエリジョンとは、リンカが最終的なバイナリに含める必要のないシンボルを削除したり、より効率的な形式に変換したりする最適化手法です。例えば、デバッグ目的でのみ必要なシンボルや、複数の同じ内容を持つシンボルを一つにまとめることで、バイナリサイズを削減し、ロード時間を短縮し、メモリ使用量を減らすことができます。Goリンカでは、`-s`フラグでシンボルテーブルを完全に削除したり、`-w`フラグでDWARF情報を削除したりするオプションがありますが、このコミットのようなより粒度の細かいエリジョンも行われます。

## 技術的詳細

このコミットは、`runtime.gcbits`というプレフィックスを持つシンボルに対して、Goリンカが特別な処理を行うように変更します。主要な技術的変更点は以下の通りです。

1.  **新しいシンボルタイプ `SGCBITS` の導入**:
    *   `src/cmd/internal/obj/link.go` に `SGCBITS` という新しいシンボルタイプが追加されました。これにより、リンカは`runtime.gcbits`に関連するシンボルを特定のカテゴリとして識別できるようになります。

2.  **`runtime.gcbits` シンボルの DWARF デバッグ情報からの除外**:
    *   `src/cmd/link/internal/ld/dwarf.go` の `defdwsymb` 関数に、`runtime.gcbits.` で始まるシンボル名を検出した場合に `return` するロジックが追加されました。
    *   `defdwsymb` は、シンボルをDWARFデバッグ情報に追加する役割を持つ関数です。この変更により、`runtime.gcbits`シンボルはDWARF情報に記録されなくなり、デバッグ情報のサイズが削減されます。これは、これらのシンボルが通常、ソースコードレベルのデバッグには直接必要ないためです。

3.  **`runtime.gcbits.*` シンボルのエリジョンと集約**:
    *   `src/cmd/link/internal/ld/symtab.go` において、`runtime.gcbits.*` という名前の「親」シンボルが作成されます。このシンボルは `obj.SGCBITS` タイプを持ち、`Local = true`, `Size = 0`, `Reachable = true` と設定されます。
    *   リンカが他のシンボルを処理する際に、`runtime.gcbits.` で始まる名前を持つシンボルを見つけると、それらのシンボルのタイプを `obj.SGCBITS` に設定し、`s.Hide = 1` を設定してシンボルを隠し、`s.Outer = symgcbits` を設定して、先ほど作成した「親」シンボル `symgcbits` に関連付けます。
    *   `s.Hide = 1` は、そのシンボルが通常のシンボルテーブルには表示されないようにすることを意味します。
    *   `s.Outer = symgcbits` は、これらの個々の`runtime.gcbits`シンボルが、論理的に単一の`symgcbits`シンボルの「内部」にあるかのように扱われることを示します。これにより、リンカは個々の`runtime.gcbits`シンボルを詳細に管理する必要がなくなり、シンボルテーブルのエントリ数を大幅に削減できます。これは、多数の小さなgcbitsシンボルが生成される場合に特に効果的です。

4.  **`genasmsym` 関数での `SGCBITS` の考慮**:
    *   `src/cmd/link/internal/ld/lib.go` の `genasmsym` 関数内のスイッチ文に `obj.SGCBITS` が追加されました。この関数はアセンブリシンボルを生成する際に使用され、`SGCBITS`タイプのシンボルが適切に処理されるようにします。特に、`!s.Reachable` の場合に `continue` するロジックは、到達不能なシンボルをスキップするためのもので、`SGCBITS`タイプのシンボルもこの最適化の対象となることを示しています。

これらの変更により、Goリンカは`runtime.gcbits`シンボルをより効率的に扱い、バイナリサイズとデバッグ情報のサイズを削減し、ビルドプロセスを最適化します。

## コアとなるコードの変更箇所

1.  **`src/cmd/internal/obj/link.go`**:
    *   `const` ブロックに `SGCBITS` が追加され、新しいシンボルタイプが定義されました。

2.  **`src/cmd/link/internal/ld/dwarf.go`**:
    *   `defdwsymb` 関数内で、シンボル名が `runtime.gcbits.` で始まる場合にDWARF情報への追加をスキップする条件が追加されました。

3.  **`src/cmd/link/internal/ld/lib.go`**:
    *   `genasmsym` 関数内のシンボルタイプを処理するスイッチ文に `obj.SGCBITS` が追加されました。

4.  **`src/cmd/link/internal/ld/symtab.go`**:
    *   `symtab` 関数内で、`runtime.gcbits.*` という名前の親シンボル `symgcbits` が作成されました。
    *   シンボルをイテレートするループ内で、`runtime.gcbits.` で始まるシンボルに対して、タイプを `obj.SGCBITS` に設定し、`Hide = 1`、`Outer = symgcbits` を設定するロジックが追加されました。

## コアとなるコードの解説

### `src/cmd/internal/obj/link.go`

```go
const (
	SSTRING
	SGOSTRING
	SGOFUNC
	SGCBITS // 新しく追加されたシンボルタイプ
	SRODATA
	SFUNCTAB
	STYPELINK
)
```
この変更は、Goリンカが内部的に使用するシンボルタイプの列挙型に `SGCBITS` を追加するものです。これにより、リンカは`runtime.gcbits`に関連するデータを、他の文字列や関数などのシンボルとは異なる、独自のカテゴリとして識別・処理できるようになります。これは、後続のリンカの最適化処理の前提となります。

### `src/cmd/link/internal/ld/dwarf.go`

```go
func defdwsymb(sym *LSym, s string, t int, v int64, size int64, ver int, gotype *LSym) {
	// ... 既存のコード ...
	if strings.HasPrefix(s, "go.string.") {
		return
	}
	if strings.HasPrefix(s, "runtime.gcbits.") { // 追加された行
		return // runtime.gcbitsシンボルはDWARF情報から除外
	}

	if strings.HasPrefix(s, "type.") && s != "type.*" && !strings.HasPrefix(s, "type..") {
		defgotype(sym)
	}
	// ... 既存のコード ...
}
```
`defdwsymb`関数は、GoのシンボルをDWARFデバッグ情報に追加する役割を担っています。この変更では、シンボル名 `s` が `runtime.gcbits.` で始まる場合、そのシンボルをDWARF情報に追加せずに即座に`return`するようにしました。これにより、`runtime.gcbits`に関連する詳細な情報がデバッグバイナリに含まれなくなり、バイナリサイズが削減されます。これらのシンボルは通常、ソースコードレベルのデバッグには直接関係しないため、この除外は機能的な影響を与えずに最適化を実現します。

### `src/cmd/link/internal/ld/lib.go`

```go
func genasmsym(put func(*LSym, string, int, int64, int64, int, *LSym)) {
	// ... 既存のコード ...
	for _, s := range Ctxt.Allsym {
		switch s.Type {
		case obj.SSTRING,
			obj.SGOSTRING,
			obj.SGOFUNC,
			obj.SGCBITS, // 追加されたシンボルタイプ
			obj.SWINDOWS:
			if !s.Reachable {
				continue
			}
			// ... 既存のコード ...
		}
	}
	// ... 既存のコード ...
}
```
`genasmsym`関数は、アセンブリシンボルを生成する際に、特定のタイプのシンボルを処理します。この変更では、`obj.SGCBITS`が既存の`switch`文の`case`リストに追加されました。これは、`SGCBITS`タイプのシンボルも、`SSTRING`や`SGOFUNC`などの他の特定のシンボルタイプと同様に、`genasmsym`関数内で適切に処理されるべきであることを示しています。特に、`!s.Reachable`（到達不能なシンボル）の場合に`continue`するロジックは、`SGCBITS`タイプのシンボルも到達可能性に基づいて最適化の対象となることを意味します。

### `src/cmd/link/internal/ld/symtab.go`

```go
func symtab() {
	// ... 既存のコード ...

	// runtime.gostring.* の親シンボル
	s = Linklookup(Ctxt, "runtime.gostring.*", 0)
	s.Type = obj.SGOSTRING
	s.Local = true
	s.Size = 0
	s.Reachable = true
	symgostring := s

	// runtime.gofunc.* の親シンボル
	s = Linklookup(Ctxt, "runtime.gofunc.*", 0)
	s.Type = obj.SGOFUNC
	s.Local = true
	s.Size = 0
	s.Reachable = true
	symgofunc := s

	// runtime.gcbits.* の親シンボル (新しく追加)
	s = Linklookup(Ctxt, "runtime.gcbits.*", 0) // 親シンボルの作成
	s.Type = obj.SGCBITS
	s.Local = true
	s.Size = 0
	s.Reachable = true
	symgcbits := s // 親シンボルへの参照

	symtypelink := Linklookup(Ctxt, "runtime.typelink", 0)

	symt = Linklookup(Ctxt, "runtime.symtab", 0)
	// ... 既存のコード ...

	// 全てのシンボルをイテレートして処理
	for _, s := range Ctxt.Allsym {
		// ... 既存のコード ...

		if strings.HasPrefix(s.Name, "runtime.gostring.") {
			s.Type = obj.SGOSTRING
			s.Hide = 1
			s.Outer = symgostring
		}

		if strings.HasPrefix(s.Name, "runtime.gcbits.") { // 追加された処理
			s.Type = obj.SGCBITS
			s.Hide = 1
			s.Outer = symgcbits // 親シンボルに関連付け
		}

		if strings.HasPrefix(s.Name, "go.func.") {
			s.Type = obj.SGOFUNC
			s.Hide = 1
			s.Outer = symgofunc
		}
		// ... 既存のコード ...
	}
	// ... 既存のコード ...
}
```
`symtab`関数は、リンカのシンボルテーブルを構築する主要な部分です。
この変更の核心は、`runtime.gcbits.*`という名前の「親」シンボル `symgcbits` を作成することです。この親シンボルは、個々の`runtime.gcbits`シンボルを論理的にグループ化するためのプレースホルダーとして機能します。

その後、リンカが`Ctxt.Allsym`（全てのシンボル）をイテレートする際に、シンボル名が`runtime.gcbits.`で始まるものを見つけると、以下の処理を行います。
*   `s.Type = obj.SGCBITS`: シンボルのタイプを新しく定義された`SGCBITS`に設定します。
*   `s.Hide = 1`: このフラグは、シンボルが通常のシンボルテーブルには表示されないように指示します。これにより、バイナリのシンボルテーブルから個々の`runtime.gcbits`シンボルが実質的に「隠され」、シンボルテーブルのエントリ数が削減されます。
*   `s.Outer = symgcbits`: 個々の`runtime.gcbits`シンボルを、先ほど作成した「親」シンボル`symgcbits`に関連付けます。これにより、リンカは多数の個別の`runtime.gcbits`シンボルを、単一の集約されたエンティティとして扱うことができ、リンカの内部処理の効率が向上し、バイナリサイズがさらに削減されます。

このメカニズムは、コミットメッセージで言及されているように、`runtime.gostring.`や`go.func.`といった他のタイプのシンボルに対して以前から行われていたエリジョンと同様のパターンを踏襲しています。

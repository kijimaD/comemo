## 変更の背景

この変更は、Go Issue #15443 で報告された問題を解決するために導入されました。この問題は、一部のLinuxディストリビューション（特にUbuntu 16.04など）で、デフォルトでPosition Independent Executable (PIE) が生成される環境において、Goのレース検出機能 (ThreadSanitizer, TSAN) を有効にしてビルドされた実行ファイルが正しく動作しない、または初期化に失敗するというものでした。

PIEはセキュリティ強化のために導入された技術で、実行ファイル内のコードがメモリ上のどこにロードされても正しく動作するように設計されています。これにより、アドレス空間配置のランダム化 (ASLR) と組み合わせて、特定のメモリ攻撃を防ぐことができます。しかし、TSANのような高度な計測ツールは、実行時のメモリレイアウトに特定の仮定を置くことがあり、PIEと競合することがありました。

具体的には、TSANは実行ファイルの特定のセクション（例えば、グローバル変数やスタック変数）にシャドウメモリと呼ばれる追加のメモリ領域を割り当てて、データ競合を検出します。PIEが有効な場合、これらのメモリ領域のアドレス計算がTSANの期待するモデルと合致せず、結果としてTSANの初期化が失敗したり、誤動作を引き起こしたりする可能性がありました。

この問題を回避するためには、TSANを有効にする場合に限り、外部リンカに対してPIEを無効にするオプション (`-no-pie`) を渡す必要がありました。しかし、すべてのリンカがこのオプションをサポートしているわけではないため、リンカが `-no-pie` をサポートしているかどうかを事前に確認するメカニズムも必要とされました。

## 前提知識の解説

### 1. Position Independent Executable (PIE) と Address Space Layout Randomization (ASLR)

*   **Position Independent Executable (PIE)**: 実行ファイル内のコードが、メモリ上の任意のアドレスにロードされても正しく実行できるようにコンパイルされた実行形式です。これにより、プログラムのロードアドレスが固定されず、セキュリティが向上します。
*   **Address Space Layout Randomization (ASLR)**: オペレーティングシステムが、実行ファイル、ライブラリ、スタック、ヒープなどのメモリ領域をランダムなアドレスに配置するセキュリティ技術です。PIEと組み合わせることで、攻撃者が特定のコードやデータを予測可能なアドレスに配置することを困難にし、バッファオーバーフローなどの脆弱性を悪用するのを防ぎます。

### 2. ThreadSanitizer (TSAN)

*   **ThreadSanitizer (TSAN)**: Go言語のランタイムに組み込まれている、データ競合 (data race) を検出するためのツールです。データ競合は、複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に発生します。データ競合は、プログラムの予測不能な動作やクラッシュの原因となることが多く、TSANは開発者がこれらのバグを特定し修正するのに役立ちます。
*   **TSANの動作原理**: TSANは、コンパイル時または実行時にプログラムのコードを計測 (instrument) します。これにより、メモリへのアクセス（読み書き）が発生するたびに、そのアクセスがデータ競合を引き起こす可能性があるかどうかをチェックするための追加のコードが実行されます。このチェックには、各メモリ位置に関連付けられた「シャドウメモリ」と呼ばれるメタデータ領域が使用されます。

### 3. Go言語のリンカ (`cmd/link`)

*   **`cmd/link`**: Go言語のツールチェインの一部であり、コンパイルされたオブジェクトファイル (`.o` ファイル) を結合して実行ファイルや共有ライブラリを生成する役割を担います。Goのリンカは、C/C++のリンカ (例: `ld` や `gcc` のリンカ機能) とは異なり、Go独自のリンカが使用されることが多いですが、Cgoを使用する場合や特定のシステムライブラリにリンクする必要がある場合は、外部のCリンカ (external linker) を呼び出すことがあります。このコミットの文脈では、外部リンカが `-no-pie` オプションをサポートしているかどうかが問題となっています。

## 技術的詳細

このコミットの技術的な核心は、Goのビルドプロセスが外部リンカを呼び出す際に、特定の条件下で `-no-pie` フラグを動的に追加するかどうかを決定するロジックにあります。

1.  **レース検出の有効化 (`flag_race != 0`)**: ユーザーが `go build -race` コマンドを使用してレース検出を有効にした場合、`flag_race` 変数が非ゼロになります。この条件が満たされた場合にのみ、以下のPIE関連の処理が実行されます。

2.  **`-no-pie` の必要性**: TSANは、その内部的な動作のために、実行ファイルが固定されたアドレスにロードされることを前提とする場合があります。PIEがデフォルトで有効なシステムでは、この前提が崩れるため、TSANの初期化が失敗する可能性があります。`-no-pie` フラグは、リンカに対してPIE形式の実行ファイルを生成しないように指示します。

3.  **`-no-pie` のサポートチェック**: すべての外部リンカが `-no-pie` オプションをサポートしているわけではありません。特に古いバージョンのリンカではこのオプションが存在しない場合があります。そのため、Goリンカは、実際に `-no-pie` を外部リンカに渡す前に、そのサポート状況をテストします。
    *   **テスト方法**:
        *   一時ディレクトリ (`tmpdir`) に `trivial.c` という空のCソースファイルを作成します。
        *   外部リンカ (`argv[0]` に格納されている、通常は `gcc` や `clang` など) を、この `trivial.c` と `-no-pie` オプションを付けて実行します。
        *   コマンドの標準出力と標準エラー出力 (`CombinedOutput`) をキャプチャし、エラーコード (`err`) と出力内容 (`out`) を確認します。
        *   `err == nil` (コマンドがエラーなく終了した) かつ `bytes.Contains(out, []byte("unrecognized"))` が `false` (出力に「unrecognized」という文字列が含まれていない、つまりオプションが認識された) であれば、`-no-pie` はサポートされていると判断します。

4.  **条件付きでのフラグ追加**: 上記のサポートチェックが成功した場合にのみ、`argv` (外部リンカに渡される引数リスト) に `-no-pie` フラグが追加されます。これにより、TSANが有効な実行ファイルが、PIEではない形式でビルドされ、TSANの初期化問題が回避されます。

このアプローチは、特定の環境でのみ発生する問題を解決しつつ、`-no-pie` をサポートしない環境でのビルドエラーを防ぐための堅牢な方法を提供します。

## コアとなるコードの解説

追加されたコードブロックは、以下のステップで構成されます。

1.  **`if flag_race != 0 { ... }`**:
    *   これは、Goのビルドコマンドに `-race` フラグが指定されているかどうかをチェックする条件です。`flag_race` は、レース検出が有効になっている場合に非ゼロの値を取ります。この条件が真の場合にのみ、以下のPIE関連のロジックが実行されます。

2.  **コメント**:
    *   「On a system where the toolchain creates position independent executables by default, tsan initialization can fail. So we pass -no-pie here, but support for that flag is quite new and we test for its support first.」
    *   これは、このコードブロックの目的を明確に説明しています。デフォルトでPIEを生成するシステムではTSANの初期化が失敗する可能性があるため、`-no-pie` を渡すが、そのサポートは新しいため事前にテストする必要がある、と述べています。

3.  **`src := filepath.Join(tmpdir, "trivial.c")`**:
    *   一時ディレクトリ (`tmpdir`) 内に `trivial.c` という名前のファイルパスを構築します。このファイルは、`-no-pie` オプションのサポートをテストするために使用されるダミーのCソースファイルです。

4.  **`if err := ioutil.WriteFile(src, []byte{}, 0666); err != nil { ... }`**:
    *   `trivial.c` という名前で空のファイルを作成します。ファイルの内容は空のバイトスライス (`[]byte{}`) で、パーミッションは `0666` (読み書き可能) です。
    *   ファイルの書き込みに失敗した場合、`Ctxt.Diag` を使用して診断メッセージを出力し、エラーを報告します。

5.  **`cmd := exec.Command(argv[0], "-no-pie", "trivial.c")`**:
    *   外部リンカを実行するための `exec.Command` オブジェクトを作成します。
    *   `argv[0]` は、現在使用されている外部リンカのパス（例: `gcc`）を含んでいます。
    *   引数として `-no-pie` と `trivial.c` を渡します。

6.  **`cmd.Dir = tmpdir`**:
    *   コマンドの実行ディレクトリを一時ディレクトリ (`tmpdir`) に設定します。これにより、`trivial.c` が見つかるようになります。

7.  **`out, err := cmd.CombinedOutput()`**:
    *   作成したコマンドを実行し、その標準出力と標準エラー出力を結合して `out` に格納します。また、コマンドの実行結果としてエラーがあれば `err` に格納します。

8.  **`supported := err == nil && !bytes.Contains(out, []byte("unrecognized"))`**:
    *   `-no-pie` オプションがサポートされているかどうかを判断するロジックです。
    *   `err == nil`: コマンドがエラーなく正常に終了したことを確認します。リンカがオプションを認識しない場合、通常はエラーコードを返します。
    *   `!bytes.Contains(out, []byte("unrecognized"))`: コマンドの出力に「unrecognized」という文字列が含まれていないことを確認します。多くのリンカは、認識できないオプションが渡された場合に、この種のメッセージを標準エラー出力に出力します。

9.  **`if supported { argv = append(argv, "-no-pie") }`**:
    *   `-no-pie` オプションがサポートされていると判断された場合のみ、実際のリンカ引数リスト `argv` に `-no-pie` を追加します。これにより、後続の実際のリンク処理でこのフラグが外部リンカに渡されます。

このコードは、Goのビルドシステムが、特定の環境依存の挙動（PIEのデフォルト有効化）と、特定のツール（TSAN）の要件との間のギャップを埋めるために、動的な適応ロジックをどのように組み込んでいるかを示しています。

        *   コマンドの標準出力と標準エラー出力 (`CombinedOutput`) をキャプチャし、エラーコード (`err`) と出力内容 (`out`) を確認します。
        *   `err == nil` (コマンドがエラーなく終了した) かつ `bytes.Contains(out, []byte("unrecognized"))` が `false` (出力に「unrecognized」という文字列が含まれていない、つまりオプションが認識された) であれば、`-no-pie` はサポートされていると判断します。

4.  **条件付きでのフラグ追加**: 上記のサポートチェックが成功した場合にのみ、`argv` (外部リンカに渡される引数リスト) に `-no-pie` フラグが追加されます。これにより、TSANが有効な実行ファイルが、PIEではない形式でビルドされ、TSANの初期化問題が回避されます。

このアプローチは、特定の環境でのみ発生する問題を解決しつつ、`-no-pie` をサポートしない環境でのビルドエラーを防ぐための堅牢な方法を提供します。

## コアとなるコードの解説

追加されたコードブロックは、以下のステップで構成されます。

1.  **`if flag_race != 0 { ... }`**:
    *   これは、Goのビルドコマンドに `-race` フラグが指定されているかどうかをチェックする条件です。`flag_race` は、レース検出が有効になっている場合に非ゼロの値を取ります。この条件が真の場合にのみ、以下のPIE関連のロジックが実行されます。

2.  **コメント**:
    *   「On a system where the toolchain creates position independent executables by default, tsan initialization can fail. So we pass -no-pie here, but support for that flag is quite new and we test for its support first.」
    *   これは、このコードブロックの目的を明確に説明しています。デフォルトでPIEを生成するシステムではTSANの初期化が失敗する可能性があるため、`-no-pie` を渡すが、そのサポートは新しいため事前にテストする必要がある、と述べています。

3.  **`src := filepath.Join(tmpdir, "trivial.c")`**:
    *   一時ディレクトリ (`tmpdir`) 内に `trivial.c` という名前のファイルパスを構築します。このファイルは、`-no-pie` オプションのサポートをテストするために使用されるダミーのCソースファイルです。

4.  **`if err := ioutil.WriteFile(src, []byte{}, 0666); err != nil { ... }`**:
    *   `trivial.c` という名前で空のファイルを作成します。ファイルの内容は空のバイトスライス (`[]byte{}`) で、パーミッションは `0666` (読み書き可能) です。
    *   ファイルの書き込みに失敗した場合、`Ctxt.Diag` を使用して診断メッセージを出力し、エラーを報告します。

5.  **`cmd := exec.Command(argv[0], "-no-pie", "trivial.c")`**:
    *   外部リンカを実行するための `exec.Command` オブジェクトを作成します。
    *   `argv[0]` は、現在使用されている外部リンカのパス（例: `gcc`）を含んでいます。
    *   引数として `-no-pie` と `trivial.c` を渡します。

6.  **`cmd.Dir = tmpdir`**:
    *   コマンドの実行ディレクトリを一時ディレクトリ (`tmpdir`) に設定します。これにより、`trivial.c` が見つかるようになります。

7.  **`out, err := cmd.CombinedOutput()`**:
    *   作成したコマンドを実行し、その標準出力と標準エラー出力を結合して `out` に格納します。また、コマンドの実行結果としてエラーがあれば `err` に格納します。

8.  **`supported := err == nil && !bytes.Contains(out, []byte("unrecognized"))`**:
    *   `-no-pie` オプションがサポートされているかどうかを判断するロジックです。
    *   `err == nil`: コマンドがエラーなく正常に終了したことを確認します。リンカがオプションを認識しない場合、通常はエラーコードを返します。
    *   `!bytes.Contains(out, []byte("unrecognized"))`: コマンドの出力に「unrecognized」という文字列が含まれていないことを確認します。多くのリンカは、認識できないオプションが渡された場合に、この種のメッセージを標準エラー出力に出力します。

9.  **`if supported { argv = append(argv, "-no-pie") }`**:
    *   `-no-pie` オプションがサポートされていると判断された場合のみ、実際のリンカ引数リスト `argv` に `-no-pie` を追加します。これにより、後続の実際のリンク処理でこのフラグが外部リンカに渡されます。

このコードは、Goのビルドシステムが、特定の環境依存の挙動（PIEのデフォルト有効化）と、特定のツール（TSAN）の要件との間のギャップを埋めるために、動的な適応ロジックをどのように組み込んでいるかを示しています。

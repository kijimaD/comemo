# [インデックス 24515] ファイルの概要

このコミットは、Goコマンドラインツールにおける`go build -o`コマンドのセマンティクス（挙動）を明確にし、修正するものです。特に、`go build -o`フラグが非`main`パッケージに対して使用された際に、出力ファイルが生成されないという一貫性のない挙動を修正し、その動作を公式ドキュメントに反映させています。また、この変更に伴い、関連するテストが追加され、macOS上での共有ライブラリ（`c-shared`ビルドモード）のリンカ挙動に関する特定の修正も含まれています。

    serving only as a check that the packages can be built.

## 元コミット内容

このコミットは、`go build -o`コマンドの動作を明確にし、特に非`main`パッケージに対する出力挙動の不整合を修正します。新しいドキュメントの引用では、以下の点が強調されています。

*   `.go`ファイルのリストが引数として与えられた場合、`build`はそれらを単一パッケージのソースファイルとして扱います。
*   単一の`main`パッケージをコンパイルする場合、`build`は結果の実行可能ファイルを、最初のソースファイル名（例: `go build ed.go rx.go`は`ed`または`ed.exe`）またはソースコードディレクトリ名（例: `go build unix/sam`は`sam`または`sam.exe`）に基づいて出力します。Windowsでは`.exe`サフィックスが追加されます。
*   複数のパッケージ、または単一の非`main`パッケージをコンパイルする場合、`build`はパッケージをコンパイルしますが、結果のオブジェクトは破棄され、ビルド可能であることのチェックとしてのみ機能します。
*   `-o`フラグは、単一パッケージのコンパイル時にのみ許可され、上記で説明されたデフォルトの挙動の代わりに、指定された出力ファイル名に実行可能ファイルまたはオブジェクトを強制的に書き込みます。

この変更により、`go build -o x.a x.go`のように非`main`パッケージに対して`-o`フラグを使用した場合、Go 1.2以降では出力ファイルが生成されなかった挙動が修正され、正しく`x.a`が出力されるようになります。これは、`-o`フラグが時として黙って無視されるという説明よりも合理的であるとされています。その他の挙動は変更されていません。

また、`goFilesPackage`内で削除された行は、`go build x.o`が`x.a`を書き込むように設定されているように見えましたが、`runBuild`内の`p.target = ""`によって上書きされていました。Go 1.2以降、非`main`パッケージに対する`go build x.go`は出力ファイルを生成したことがなく、この挙動は`go build strings`や`go build std`との一貫性のためにも維持されるべきであると判断されています。

このコミットによって、上記すべての挙動がテストされるようになりました。
このコミットはIssue #10865を修正します。

## 変更の背景

このコミットの主な背景には、`go build`コマンドの`-o`フラグの挙動に関する一貫性の欠如と、それによるユーザーの混乱がありました。特に、`package main`ではない通常のライブラリパッケージ（非`main`パッケージ）を`go build -o mylib.a mylib.go`のようにビルドしようとした場合、`-o`フラグが指定されているにもかかわらず、出力ファイルが生成されないという問題が存在していました。これは、ユーザーが期待する動作と異なり、`-o`フラグが「黙って無視される」という理解しにくい挙動でした。

この問題はIssue #10865として報告されており、Goツールの使いやすさと予測可能性を向上させるために、この不整合を解消し、ドキュメントを更新する必要がありました。また、macOS (Darwin) 環境で`c-shared`ビルドモードを使用して共有ライブラリをビルドする際に、リンカが一時ディレクトリ名を共有ライブラリの`LC_ID_DYLIB`ロードコマンドに記録してしまうという、プラットフォーム固有の問題も存在し、これも修正の対象となりました。

## 前提知識の解説

*   **Goのパッケージとビルド**: Go言語では、コードはパッケージにまとめられます。
    *   `package main`: 実行可能なプログラムのエントリポイント（`main`関数を含む）を持つパッケージです。`go build`でコンパイルすると実行可能ファイルが生成されます。
    *   非`main`パッケージ: ライブラリとして機能するパッケージです。通常、`go build`でコンパイルしても実行可能ファイルは生成されず、コンパイルチェックのみが行われます。
*   **`go build`コマンド**: Goソースコードをコンパイルするための主要なコマンドです。
    *   引数に`.go`ファイルを指定した場合: 指定されたファイル群を単一のパッケージとして扱います。
    *   引数にパッケージパス（例: `cmd/gofmt`）を指定した場合: そのパッケージをビルドします。
*   **`-o`フラグ**: `go build`コマンドのオプションで、生成される出力ファイルの名前を指定します。例えば、`go build -o myapp main.go`とすると、`myapp`という名前の実行可能ファイルが生成されます。
*   **アーカイブファイル (`.a`)**: Goでは、非`main`パッケージをコンパイルした結果は、通常、アーカイブファイル（Unix系システムでは`.a`、Windowsでは`.lib`）として中間的に生成されます。これは他のプログラムからリンクされるライブラリとして機能します。
*   **`c-shared`ビルドモード**: Go 1.5で導入されたビルドモードの一つで、GoのコードをC言語から呼び出し可能な共有ライブラリ（`.so`、`.dylib`、`.dll`）としてビルドするために使用されます。
*   **`LC_ID_DYLIB`**: macOSの実行可能ファイルや共有ライブラリのヘッダ（Mach-Oフォーマット）に含まれるロードコマンドの一つで、共有ライブラリ自身の識別名（パス）を記録します。リンカがこの情報をどのように記録するかが、共有ライブラリのロードに影響を与えます。

## 技術的詳細

このコミットの技術的な核心は、`go build`コマンドが`-o`フラグをどのように解釈し、適用するかを統一することにあります。

1.  **`-o`フラグの挙動の統一**:
    *   以前は、`go build -o mylib.a mylib.go`のように非`main`パッケージに対して`-o`フラグを使用しても、出力ファイル`mylib.a`は生成されませんでした。これは、`go build`が非`main`パッケージに対してはデフォルトで出力ファイルを破棄する挙動と、`-o`フラグの意図が衝突していたためです。
    *   このコミットでは、単一パッケージのビルドにおいて`-o`フラグが指定された場合、それが`main`パッケージであろうと非`main`パッケージであろうと、指定された名前で出力ファイルを生成するように変更されました。これにより、`-o`フラグの挙動が予測可能で一貫性のあるものになります。非`main`パッケージの場合、生成されるのはアーカイブファイル（`.a`）です。
    *   複数のパッケージを同時にビルドする場合には、`-o`フラグは引き続き許可されず、エラーとなります。これは、複数の出力ファイルを単一の`-o`で指定することができないため、理にかなった制限です。

2.  **内部ロジックの調整**:
    *   `src/cmd/go/build.go`内の`runBuild`関数において、`p.target = *buildO`という行が追加されました。これは、`-o`フラグで指定された出力パスをパッケージのターゲットパスとして明示的に設定するものです。これにより、ビルドシステムがこの指定されたパスに出力ファイルを生成するようになります。
    *   `goFilesPackage`関数から、非`main`パッケージに対してデフォルトで`pkg.Name + ".a"`を`*buildO`に設定しようとしていたロジックが削除されました。これは、非`main`パッケージはデフォルトでは出力ファイルを生成しないという原則を維持するためです。`-o`が明示的に指定された場合にのみ、出力が生成されます。

3.  **macOS (Darwin) `c-shared`ビルドモードの修正**:
    *   macOSでは、共有ライブラリ（`.dylib`）をビルドする際に、リンカが`LC_ID_DYLIB`ロードコマンドにライブラリのパスを記録します。以前は、一時的なビルドディレクトリ内のパスが記録されてしまい、結果として生成された共有ライブラリが正しくロードできない問題がありました。
    *   このコミットでは、`ld`関数（リンカを呼び出す部分）において、`goos == "darwin"`かつ`buildBuildmode == "c-shared"`の場合に特別な処理が追加されました。具体的には、リンカの実行ディレクトリを最終的な出力ファイルのディレクトリに変更し、`-o`フラグにはファイル名のみを渡すように修正されました。これにより、`LC_ID_DYLIB`には正しいライブラリ名のみが記録され、共有ライブラリが正しく機能するようになります。

4.  **ドキュメントの更新とテストの追加**:
    *   `src/cmd/go/alldocs.go`内の`go build`コマンドのドキュメントが、新しい挙動に合わせて詳細に更新されました。これにより、ユーザーは`go build`と`-o`フラグの正確なセマンティクスを理解できるようになります。
    *   `src/cmd/go/go_test.go`に`TestGoBuildOutput`という新しいテスト関数が追加され、`go build`と`-o`フラグの様々な組み合わせ（`main`パッケージ、非`main`パッケージ、複数のパッケージ、出力ファイル名の指定など）が網羅的にテストされるようになりました。これにより、将来的な回帰を防ぎ、挙動の正確性を保証します。

これらの変更により、`go build -o`の挙動はより直感的で一貫性のあるものになり、特定のプラットフォームでの共有ライブラリビルドの問題も解決されました。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

1.  **`src/cmd/go/alldocs.go`**:
    *   `go build`コマンドのドキュメントが大幅に更新されました。特に、`main`パッケージ、非`main`パッケージ、および`-o`フラグの挙動に関する説明が詳細化されています。
    *   変更前は「単一の`main`パッケージが指定された場合、`build`は結果の実行可能ファイルを出力に書き込む。それ以外の場合、`build`はパッケージをコンパイルするが結果は破棄する」という記述でした。
    *   変更後は、`main`パッケージの出力ファイル名の決定ロジック（最初のソースファイル名またはディレクトリ名）が具体的に記述され、非`main`パッケージや複数パッケージの場合は結果が破棄されることが明記されました。そして、`-o`フラグがこれらのデフォルト挙動を上書きすることが明確に説明されています。

2.  **`src/cmd/go/build.go`**:
    *   `runBuild`関数内の`p.target = "" // must build - not up to date`という行が、`p.target = *buildO`に変更され、`p.Stale = true`が追加されました。これにより、`-o`フラグで指定された出力パスがパッケージのターゲットとして直接設定されるようになりました。
    *   `goFilesPackage`関数内で、非`main`パッケージに対して`*buildO = pkg.Name + ".a"`を設定していたブロックが削除されました。これは、非`main`パッケージはデフォルトで出力ファイルを生成しないという挙動を維持するためです。
    *   `action1`関数内で、`goos == "darwin"`かつ`buildBuildmode == "c-shared"`の場合に、`p.target`が設定されている場合に`name`変数を`filepath.Split(p.target)`から取得するロジックが追加されました。これは、macOSの共有ライブラリのリンカ挙動に対応するためです。
    *   `ld`関数内で、`goos == "darwin"`かつ`buildBuildmode == "c-shared"`の場合に、リンカの実行ディレクトリと出力ファイル名を調整するロジックが追加されました。具体的には、`dir`と`out`変数を`filepath.Split(out)`で分割し、リンカを`dir`で実行し、`-o`には`out`（ファイル名のみ）を渡すように変更されました。

3.  **`src/cmd/go/go_test.go`**:
    *   新しいヘルパー関数`mustNotExist`と`wantArchive`が追加されました。
        *   `mustNotExist(path string)`: 指定されたパスにファイルが存在しないことを確認します。存在する場合はテストを失敗させます。
        *   `wantArchive(path string)`: 指定されたパスのファイルがアーカイブファイル（`!<arch>`マジックバイトで始まる）であることを確認します。
    *   `TestGoBuildOutput`という新しいテスト関数が追加されました。このテストは、`go build`と`-o`フラグの様々な組み合わせを網羅的に検証します。
        *   `main`パッケージのビルド（`-o`あり/なし）と実行可能ファイルの確認。
        *   非`main`パッケージのビルド（`-o`あり/なし）とアーカイブファイルの確認。
        *   パッケージパス指定でのビルド（`-o`あり/なし）。
        *   複数のパッケージと`-o`フラグを同時に使用した場合のエラー確認。

## コアとなるコードの解説

### `src/cmd/go/alldocs.go`の変更

このファイルの変更は、ユーザー向けのドキュメントを更新するものです。`go build`コマンドの出力挙動に関する説明が、より詳細かつ正確になりました。特に、`main`パッケージのデフォルトの出力ファイル名決定ルールと、`-o`フラグがそのルールをどのように上書きするかが明確に記述されています。これにより、ユーザーは`go build`の動作を誤解することなく、意図した通りのビルド結果を得られるようになります。

### `src/cmd/go/build.go`の変更

*   **`runBuild`関数**:
    *   `p.target = *buildO`への変更は、`-o`フラグで指定された値（`*buildO`）を、ビルド対象パッケージ`p`の最終的な出力ターゲットパスとして直接設定することを意味します。これにより、ビルドシステムは指定されたパスに出力ファイルを生成するようになります。
    *   `p.Stale = true`の追加は、パッケージが最新の状態ではないため、必ずビルドが必要であることをシステムに伝えます。
    *   削除された`a.target = *buildO`や`b.maybeAddHeaderAction`関連の行は、おそらく`p.target`への直接設定によって不要になったか、より一般的な処理に統合されたものと考えられます。

*   **`goFilesPackage`関数**:
    *   非`main`パッケージに対して`*buildO = pkg.Name + ".a"`を設定していたロジックの削除は重要です。これは、非`main`パッケージがデフォルトで出力ファイルを生成しないという`go build`の哲学を再確認するものです。`-o`フラグが明示的に指定された場合にのみ、このデフォルトの挙動が上書きされ、アーカイブファイルが生成されます。

*   **`action1`関数と`ld`関数（macOS `c-shared`対応）**:
    *   これらの変更は、macOSで`c-shared`ビルドモードを使用する際のリンカの特殊な挙動に対応するためのものです。macOSのMach-Oフォーマットでは、共有ライブラリの`LC_ID_DYLIB`ロードコマンドにライブラリの識別パスが記録されます。リンカに一時ディレクトリ内のパスを渡してしまうと、生成された共有ライブラリが正しくロードできなくなる問題がありました。
    *   `action1`での`filepath.Split(p.target)`による`name`の取得は、最終的な出力ファイル名のみを抽出し、リンカに渡すパスを簡潔にするための準備です。
    *   `ld`関数での`dir, out = filepath.Split(out)`とリンカの実行ディレクトリ変更は、リンカを最終的な出力ディレクトリで実行し、`-o`フラグにはファイル名のみを渡すことで、`LC_ID_DYLIB`に正しいライブラリ名が記録されるようにします。これにより、生成された共有ライブラリがシステム上で正しく機能するようになります。

### `src/cmd/go/go_test.go`の変更

*   `mustNotExist`と`wantArchive`ヘルパー関数は、テストの可読性と再利用性を高めるために導入されました。
*   `TestGoBuildOutput`は、このコミットで修正・明確化された`go build -o`のすべての挙動を網羅的にテストします。これにより、将来の変更によってこの挙動が意図せず変更されることを防ぎ、Goツールの安定性を保証します。特に、非`main`パッケージに対する`-o`フラグの動作が正しく行われること、および複数のパッケージに対して`-o`フラグが使用された場合にエラーとなることが検証されています。

これらのコード変更は、`go build -o`のセマンティクスをより堅牢で予測可能なものにし、ユーザーエクスペリエンスを向上させるための重要な修正です。

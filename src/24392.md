# [インデックス 24392] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）において、GCアシストがマークフェーズの完了を通知した後、GCコーディネーターゴルーチンへの制御の引き渡しが遅延する問題を解決します。具体的には、GCアシストがマークフェーズを完了した際に、明示的に `runtime.Gosched()` を呼び出すことで、GCコーディネーターがより迅速に実行され、GCの効率とヒープ使用量の予測可能性を向上させます。

## コミット

```

Author: Austin Clements <austin@google.com>
Date:   Thu Jul 23 17:55:01 2015 -0400

    runtime: yield to GC coordinator after assist completion
    
    Currently it's possible for the GC assist to signal completion of the
    mark phase, which puts the GC coordinator goroutine on the current P's
    run queue, and then return to mutator code that delays until the next
    forced preemption before actually yielding control to the GC
    coordinator, dragging out completion of the mark phase. This delay can
    be further exacerbated if the mutator makes other goroutines runnable
    before yielding control, since this will push the GC coordinator on
    the back of the P's run queue.
    
    To fix this, this adds a Gosched to the assist if it completed the
    mark phase. This immediately and directly yields control to the GC
    coordinator. This already happens implicitly in the background mark
    workers because they park immediately after completing the mark.
    
    This is one of the reasons completion of the mark phase is being
    dragged out and allowing the mutator to allocate without assisting,
    leading to the large heap goal overshoot in issue #11677. This is also
    a prerequisite to making the assist block when it can't pay off its
    debt.
```

## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）のマークフェーズ完了が遅延し、その結果としてヒープサイズが目標を大きく超過する問題に対処するために導入されました。具体的には、GCアシストがマークフェーズの完了を通知した後、GCコーディネーターゴルーチンへの制御の引き渡しが遅れることが問題でした。

GCアシストは、ミューテーター（ユーザープログラム）がメモリを割り当てる際に、GC作業を補助するメカニズムです。マークフェーズが完了したことをアシストがコーディネーターに通知しても、すぐに制御がコーディネーターに渡されない場合がありました。これは、アシストが完了した後もミューテーターコードが実行を続け、強制的なプリエンプション（横取り）が発生するまでGCコーディネーターにCPU時間が与えられないためです。さらに、ミューテーターが他のゴルーチンを先に実行可能にしてしまうと、GCコーディネーターはP（プロセッサ）の実行キューの最後尾に追いやられ、さらに遅延が悪化する可能性がありました。

この遅延は、GCのマークフェーズが長引き、その間にミューテーターがGCアシストなしで大量のメモリを割り当ててしまうことを許容していました。その結果、GCが設定したヒープサイズの目標を大きく上回る「ヒープ目標超過」が発生し、メモリ使用効率の低下やGCポーズ時間の増加につながっていました。コミットメッセージでは、この問題が `issue #11677` の「大きなヒープ目標超過」の一因であると述べられています。ただし、`issue #11677` はGoの公式イシュートラッカーでは直接見つかりませんでした。これは内部的な参照であるか、あるいは別の文脈で言及されたものである可能性があります。

この変更は、GCアシストがマークフェーズを完了した直後にGCコーディネーターに制御を明示的に引き渡すことで、この遅延を解消し、GCの効率と予測可能性を向上させることを目的としています。また、この変更は、アシストがその「負債」を返済できない場合にブロックするメカニズムを導入するための前提条件でもあります。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのガベージコレクション（GC）とスケジューリングに関するいくつかの概念を理解しておく必要があります。

1.  **Goのガベージコレクション (GC)**:
    *   GoのGCは、並行（concurrent）かつインクリメンタル（incremental）なマーク＆スイープ方式を採用しています。これは、GC作業の大部分をユーザープログラム（ミューテーター）と並行して実行し、ポーズ時間を短縮しようとするものです。
    *   **マークフェーズ (Mark Phase)**: GCの主要なフェーズの一つで、到達可能なオブジェクト（まだ使用されているオブジェクト）を特定し、マークします。このフェーズが完了すると、マークされていないオブジェクトは不要と判断され、スイープフェーズで解放されます。
    *   **GCコーディネーター (GC Coordinator)**: GCの進行を管理する特別なゴルーチンです。マークフェーズの開始、終了、およびその他のGC関連タスクを調整します。
    *   **GCアシスト (GC Assist)**: ミューテーターがメモリ割り当てを行う際に、GC作業が遅れている場合に、その割り当てを行うゴルーチン自身がGC作業の一部を「手伝う」メカニズムです。これにより、GCの進行を加速し、ヒープの過度な膨張を防ぎます。各ゴルーチンには「GC負債 (GC debt)」が割り当てられ、メモリを割り当てるたびに負債が増加し、GCアシスト作業を行うことで負債を返済します。

2.  **Goスケジューラ (Go Scheduler)**:
    *   Goランタイムは、ユーザーゴルーチンをOSスレッド上で効率的に実行するための独自のスケジューラを持っています。
    *   **G (Goroutine)**: Goランタイムによって管理される軽量な実行単位です。
    *   **M (Machine)**: OSスレッドを表します。
    *   **P (Processor)**: 論理プロセッサを表し、MとGの間のコンテキストとして機能します。Pは実行可能なGのローカルキューを持ちます。MはPにアタッチされ、PのローカルキューからGを取得して実行します。
    *   **実行キュー (Run Queue)**: Pごとに存在する、実行可能なゴルーチンのキューです。グローバルな実行キューも存在します。
    *   **プリエンプション (Preemption)**: Goランタイムは、長時間実行されるゴルーチンがCPUを独占しないように、定期的にゴルーチンを中断（プリエンプト）し、他のゴルーチンにCPU時間を割り当てます。これは、システムコールや関数呼び出しの特定のポイント、またはタイマー割り込みによって発生します。

3.  **`Gosched()` 関数**:
    *   `runtime.Gosched()` は、現在のゴルーチンが自発的にCPUを放棄し、他の実行可能なゴルーチンに制御を渡すことをスケジューラに通知する関数です。現在のゴルーチンは実行キューの最後尾に置かれ、スケジューラは次に実行するゴルーチンを選択します。

4.  **`systemstack()` 関数**:
    *   `runtime.systemstack()` は、現在のゴルーチンをシステムスタックに切り替えて、指定された関数を実行します。システムスタックは、GCやスケジューリングなどのランタイム内部処理のために使用される特別なスタックです。これにより、ユーザーゴルーチンのスタックを汚染することなく、ランタイムの重要な処理を実行できます。

## 技術的詳細

このコミットの技術的詳細は、GCアシストがマークフェーズの完了を検出した際に、GCコーディネーターゴルーチンへの制御の引き渡しを最適化することにあります。

以前のGoランタイムでは、GCアシストが `bgMarkSignal.complete()` を呼び出してマークフェーズの完了を通知した後、アシストを実行していたミューテーターゴルーチンはすぐにGCコーディネーターに制御を渡すわけではありませんでした。代わりに、ミューテーターゴルーチンは自身のコードの実行を続け、次の強制的なプリエンプションポイントに到達するまで、あるいは自発的にスケジューラに制御を戻すまで、GCコーディネーターは実行されませんでした。

この挙動は、特にミューテーターゴルーチンがGCアシスト完了後に多くの処理を実行したり、他のゴルーチンを大量に実行可能にしたりする場合に問題となりました。GCコーディネーターゴルーチンはPの実行キューに入れられますが、ミューテーターが他のゴルーチンを優先的に実行してしまうと、コーディネーターはキューの奥に追いやられ、マークフェーズの完了処理が遅延しました。この遅延が、ヒープの目標超過の一因となっていました。

このコミットでは、この問題を解決するために、GCアシストがマークフェーズを完了した直後に `runtime.Gosched()` を明示的に呼び出すように変更されました。

1.  **`completed` フラグの導入**: `gcAssistAlloc` 関数内に `completed` というブール型のローカル変数が導入されました。これは、GCアシストがマークフェーズの完了をトリガーしたかどうかを追跡するために使用されます。
2.  **`bgMarkSignal.complete()` の呼び出し**: `systemstack` 内でGCアシストがマークフェーズの完了条件を満たした場合（例: `work.bgMark1.complete()` または `work.bgMark2.complete()` が呼び出された場合）、`completed` フラグが `true` に設定されます。
3.  **`Gosched()` の明示的な呼び出し**: `systemstack` から戻った後、`completed` フラグが `true` であれば、`runtime.Gosched()` が呼び出されます。

`Gosched()` が呼び出されると、現在のゴルーチンはCPUを自発的に放棄し、スケジューラは次に実行するゴルーチンを選択します。このとき、GCコーディネーターゴルーチンはすでに実行キューに入っているため、優先的に実行される可能性が高まります。これにより、マークフェーズの完了処理が迅速に進み、GCの効率が向上します。

コミットメッセージでは、バックグラウンドのマークワーカーはマーク完了後にすぐにパーク（待機状態に入る）するため、この問題は発生しないと説明されています。GCアシストの場合のみ、ミューテーターゴルーチンがGC作業を終えてもすぐにユーザーコードに戻るため、明示的な `Gosched()` が必要でした。

この変更は、GCアシストが「負債」を返済できない場合にブロックする将来のメカニズムの前提条件でもあります。これは、GCアシストが単にGC作業を手伝うだけでなく、必要に応じてミューテーターの実行を一時停止させることで、GCの進行をより厳密に制御できるようになることを示唆しています。

## コアとなるコードの解説

`src/runtime/mgcmark.go` の `gcAssistAlloc` 関数は、ミューテーターゴルーチンがメモリを割り当てる際にGCアシストを実行する主要な場所です。この関数内の変更が、このコミットの核心です。

1.  **`completed` 変数 (`completed := false`)**:
    この変数は、GCアシストが実行された結果として、GCのマークフェーズが完了したかどうかを追跡するために導入されました。初期値は `false` です。

2.  **`completed = true` の設定**:
    `systemstack` 内でGCアシストの作業が行われます。この中で、`work.bgMark1.complete()` または `work.bgMark2.complete()` が呼び出される条件は、GCのマークフェーズが完了したことを意味します。これらの呼び出しの直後に `completed = true` が設定されます。これにより、GCアシストがマークフェーズの完了をトリガーしたことが記録されます。

3.  **`if completed { Gosched() }` ブロック**:
    `systemstack` から抜けた後、この条件ブロックが実行されます。もし `completed` が `true` であれば、つまりGCアシストがマークフェーズの完了をトリガーしていた場合、`runtime.Gosched()` が呼び出されます。
    *   `Gosched()` は、現在のゴルーチン（この場合はメモリ割り当てを行っていたミューテーターゴルーチン）が自発的にCPUを放棄し、スケジューラに他の実行可能なゴルーチンに制御を渡すように促します。
    *   この時点で、GCコーディネーターゴルーチンはすでに実行可能状態になってPの実行キューに追加されているはずです（`bgMarkSignal.complete()` の呼び出しによって）。`Gosched()` を呼び出すことで、ミューテーターゴルーチンはすぐにCPUを解放し、GCコーディネーターが迅速に実行される機会を得ることができます。

この変更により、GCアシストがマークフェーズを完了した直後にGCコーディネーターが実行される可能性が大幅に高まります。これにより、マークフェーズの完了が遅延する問題が解消され、GCの効率が向上し、ヒープの目標超過が抑制されます。

`src/runtime/mgc.go` の `bgMarkSignal.complete()` のコメント更新は、この新しい挙動の意図を明確にするものです。`complete()` を呼び出す側（`gcAssistAlloc` など）は、その後すぐに自身を非スケジューリングすべきであるというガイドラインを提供しています。

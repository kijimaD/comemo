# [インデックス 23504] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）のバックグラウンドマークヘルパーの動作を最適化するものです。具体的には、GCマーク作業が利用可能である場合にのみバックグラウンドマークヘルパーが実行されるように変更し、作業がない場合にP（プロセッサ）が無駄にGCヘルパーG（ゴルーチン）を実行し続ける非効率性を解消します。これにより、GCの効率が向上し、スケジューラのオーバーヘッドが削減されます。

## コミット

```
runtime: run background mark helpers only if work is available

Prior to this CL whenever the GC marking was enabled and
a P was looking for work we supplied a G to help
the GC do its marking tasks. Once this G finished all
the marking available it would release the P to find another
available G. In the case where there was no work the P would drop
into findrunnable which would execute the mark helper G which would
immediately return and the P would drop into findrunnable again Repeating
the process. Since the P was always given a G to run it never blocks.
This CL first checks if the GC mark helper G has available work and if
not the P immediately falls through to Its blocking logic.

Fixes #10901

Reviewed-on: https://go-review.googlesource.com/10189
Reviewed-by: Austin Clements <austin@google.com>
```

## 変更の背景

このコミットが導入される前は、Goランタイムのガベージコレクション（GC）のマークフェーズが有効な場合、P（プロセッサ）が実行可能なG（ゴルーチン）を探す際に、GCのマーク作業を支援するためのG（GCマークヘルパーゴルーチン）が常に提供されていました。このGCマークヘルパーGは、利用可能なマーク作業をすべて完了すると、Pを解放して別のGを探させます。

しかし、問題は、マーク作業が全くない場合でも、PはGCマークヘルパーGを実行してしまう点にありました。このヘルパーGは作業がないためすぐにリターンし、Pは再び`findrunnable`関数に入り、実行可能なGを探します。そして、またGCマークヘルパーGが提供され、すぐにリターンするという非効率なループが発生していました。Pは常に何らかのG（この場合はすぐにリターンするGCマークヘルパーG）を実行しているため、ブロッキング状態にならず、この無駄なサイクルを繰り返していました。

この繰り返しは、特にGCマーク作業が少ない、または一時的に枯渇している状況で、CPUサイクルを無駄にし、スケジューラのオーバーヘッドを増加させていました。このコミットは、このような非効率性を解消し、GCマークヘルパーGが実行される前に、実際にマーク作業が利用可能かどうかを確認することで、Pが無駄なループに陥るのを防ぐことを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の概念を理解しておく必要があります。

1.  **Goのガベージコレクション (GC)**:
    *   GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにしています。オブジェクトを白（未訪問）、灰色（訪問済みだが参照先は未訪問）、黒（訪問済みで参照先も訪問済み）の3色に分類し、マークフェーズで到達可能なオブジェクトを特定します。
    *   **マークフェーズ**: プログラムが実行中に、GCはバックグラウンドで到達可能なオブジェクトをマークします。このフェーズでは、アプリケーションの実行を一時停止する「STW (Stop The World)」時間を最小限に抑えるために、並行してGCワーカーが動作します。
    *   **バックグラウンドマークヘルパー**: GCのマークフェーズ中に、通常のアプリケーションゴルーチンが実行可能なGを見つけられない場合、スケジューラはGCマーク作業を支援する特別なゴルーチン（バックグラウンドマークヘルパー）をPに割り当てることがあります。これにより、アプリケーションの実行と並行してGC作業を進め、STW時間を短縮します。

2.  **Goスケジューラ (M, P, G)**:
    *   **G (Goroutine)**: Goにおける軽量なスレッド。Goプログラムの実行単位です。
    *   **M (Machine)**: OSのスレッドに相当します。Gを実行する物理的なスレッドです。
    *   **P (Processor)**: MとGを仲介する論理的なプロセッサです。Pは実行可能なGのローカルキューを持ち、MにGを実行するコンテキストを提供します。Goスケジューラは、利用可能なPの数に基づいて、同時に実行できるGの数を制限します。
    *   **`findrunnable`**: Pが実行可能なGを探す際に呼び出されるスケジューラの重要な関数です。ローカルキュー、グローバルキュー、ネットワークポーラーなど、様々な場所からGを探します。もし実行可能なGが見つからない場合、Pはアイドル状態になり、最終的にはブロッキング状態に移行して、新しいGが利用可能になるのを待ちます。

3.  **`gcWork`**:
    *   GCマーク作業は、`gcWork`という構造体を通じて管理されます。これは、マークすべきオブジェクトのポインタを保持するワークキューのようなものです。各Pはローカルな`gcWork`キャッシュを持ち、グローバルなワークキューとの間で作業をバランスさせます。

## 技術的詳細

このコミットの技術的な核心は、PがGCマークヘルパーゴルーチンを実行する前に、実際にGCマーク作業が利用可能であるかを効率的に判断する新しいメカニズムを導入した点にあります。

具体的には、以下の変更が行われました。

1.  **`gcMarkWorkAvailable` 関数の導入**:
    *   `src/runtime/mgc.go` に `gcMarkWorkAvailable(p *p) bool` という新しい関数が追加されました。
    *   この関数は、与えられたPに対してGCマーク作業がすぐに利用可能かどうかを判断します。
    *   判断基準は以下の通りです。
        *   Pのローカルな`gcWork`キャッシュ（`p.gcw`）が空でないか (`!p.gcw.empty()`)。
        *   グローバルなGCワークキューに作業が残っているか (`atomicload64(&work.full) != 0 || atomicload64(&work.partial) != 0`)。
    *   これらの条件のいずれかが真であれば、マーク作業が利用可能であると判断し、`true`を返します。

2.  **`gcWork.empty()` メソッドの導入**:
    *   `src/runtime/mgcwork.go` に `(w *gcWork) empty() bool` というメソッドが追加されました。
    *   これは、特定の`gcWork`インスタンス（Pのローカルキャッシュなど）がマーク作業を保持しているかどうかを効率的にチェックするためのヘルパーメソッドです。
    *   `wbuf`（ワークバッファ）が0であるか、またはワークバッファ内のオブジェクト数が0である場合に`true`を返します。

3.  **`findrunnable` における条件分岐の追加**:
    *   `src/runtime/proc1.go` の `findrunnable` 関数内で、GCマークヘルパーゴルーチンを実行する条件に `gcMarkWorkAvailable(_p_)` が追加されました。
    *   変更前: `if _p_ := _g_.m.p.ptr(); gcBlackenEnabled != 0 && _p_.gcBgMarkWorker != nil { ... }`
    *   変更後: `if _p_ := _g_.m.p.ptr(); gcBlackenEnabled != 0 && _p_.gcBgMarkWorker != nil && gcMarkWorkAvailable(_p_) { ... }`
    *   これにより、GCマークフェーズが有効で、バックグラウンドマークワーカーが存在するだけでなく、**実際にマーク作業が利用可能である場合にのみ**、PはGCマークヘルパーGを実行するようになります。

この変更により、マーク作業がない場合にはPはすぐに`findrunnable`の次のロジック（ブロッキングなど）に進むことができるようになり、無駄なCPUサイクル消費とスケジューラのオーバーヘッドが削減されます。

## コアとなるコードの解説

### `src/runtime/mgc.go` の `gcMarkWorkAvailable` 関数

この関数は、PがGCマークヘルパーゴルーチンを実行するべきかどうかを判断するための主要なロジックを含んでいます。
*   `if !p.gcw.empty()`: まず、現在のPのローカルなGCワークキュー（`p.gcw`）に作業が残っているかをチェックします。`gcw.empty()`は、そのPが処理すべきオブジェクトのポインタを保持しているかどうかを効率的に判断します。もしローカルに作業があれば、すぐに`true`を返します。
*   `if atomicload64(&work.full) != 0 || atomicload64(&work.partial) != 0`: ローカルキューが空の場合、次にグローバルなGCワークキューに作業が残っているかをチェックします。`work.full`と`work.partial`は、それぞれフルとパーシャルのグローバルワークバッファの存在を示し、`atomicload64`でアトミックに読み込むことで、他のPとの競合を避けつつ最新の状態を取得します。いずれかのグローバルキューに作業があれば、`true`を返します。
*   どちらの条件も満たされない場合、つまりローカルにもグローバルにもマーク作業がない場合は`false`を返し、PはGCマークヘルパーGを実行せずに次のスケジューリングロジックに進みます。

### `src/runtime/mgcwork.go` の `gcWork.empty()` メソッド

このメソッドは、`gcWork`構造体が現在、処理すべきマーク作業を保持しているかどうかを簡潔にチェックするためのものです。
*   `wbuf := w.wbuf`: `gcWork`構造体`w`が保持するワークバッファへのポインタを取得します。
*   `return wbuf == 0 || wbuf.ptr().nobj == 0`: ワークバッファ自体が存在しない（`wbuf == 0`）か、またはワークバッファ内にオブジェクトが一つも格納されていない（`wbuf.ptr().nobj == 0`）場合に`true`を返します。これにより、`gcWork`が空であると判断されます。`//go:nowritebarrier`は、この関数がライトバリアを必要としないことをコンパイラに指示するディレクティブです。

### `src/runtime/proc1.go` の `findrunnable` 関数における変更

`findrunnable`関数は、Pが実行可能なGを探す際の中心的な場所です。この変更は、GCマークフェーズ中にアイドル状態のPがGCマークヘルパーGを実行するかどうかの条件を厳格化します。
*   変更前は、`gcBlackenEnabled != 0 && _p_.gcBgMarkWorker != nil` という条件、つまりGCマークフェーズが有効で、バックグラウンドマークワーカーが存在するだけで、GCマークヘルパーGが実行されていました。
*   変更後は、この条件に加えて `&& gcMarkWorkAvailable(_p_)` が追加されました。これにより、GCマークヘルパーGが実行されるのは、**実際にマーク作業が利用可能である場合のみ**となります。
*   この修正によって、マーク作業がない場合にPがGCマークヘルパーGを無駄に実行し、すぐにリターンして`findrunnable`を再実行するという非効率なループが解消され、スケジューラの効率が向上します。

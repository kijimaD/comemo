## 元コミット内容

このコミットは、`src/lib/exvar/exvar.go` ファイル内の2つの `iterate` 関数/メソッドのチャネル引数の型定義を修正しています。

変更前:
```go
func (v *Map) iterate(c <-chan KeyValue) {
	for k, v := range v.m {
		c <- KeyValue{ k, v };
	}
	// ...
}

func iterate(c <-chan KeyValue) {
	for k, v := range vars {
		c <- KeyValue{ k, v };
	}
	// ...
}
```

変更後:
```go
func (v *Map) iterate(c chan<- KeyValue) {
	for k, v := range v.m {
		c <- KeyValue{ k, v };
	}
	// ...
}

func iterate(c chan<- KeyValue) {
	for k, v := range vars {
		c <- KeyValue{ k, v };
	}
	// ...
}
```

## 変更の背景

Go言語のチャネルは、ゴルーチン間の安全な通信を可能にするための重要なプリミティブです。チャネルには「方向性」という概念があり、チャネルがデータの送信専用であるか、受信専用であるか、あるいは双方向であるかを明示的に指定できます。

このコミットが行われた2009年5月は、Go言語がまだ開発の初期段階にあり、言語仕様や標準ライブラリの設計が活発に行われていた時期です。この時期には、チャネルの方向性に関する厳密な型チェックが導入され、コードの意図をより明確にし、コンパイル時のエラー検出を強化する方向性が進められていました。

`exvar.go` 内の `iterate` 関数/メソッドは、内部のマップをイテレートし、その結果を引数として渡されたチャネル `c` に送信しています (`c <- KeyValue{ k, v }`)。しかし、元のコードではチャネル `c` が `<-chan KeyValue` (受信専用チャネル) として宣言されていました。受信専用チャネルに対してデータを送信しようとすると、Goコンパイラはエラーを報告します。

このコミットは、この型不一致を修正し、`iterate` 関数/メソッドの内部で行われている操作（チャネルへのデータ送信）と、チャネルの型宣言を一致させることを目的としています。これにより、コードの正確性が向上し、コンパイラによる静的解析の恩恵を最大限に受けることができます。

## 前提知識の解説

### Go言語のチャネル

Go言語におけるチャネルは、ゴルーチン（軽量スレッド）間で値を安全に受け渡しするためのパイプのようなものです。チャネルを使用することで、共有メモリによる競合状態を避けることができ、並行処理のコードをより安全かつ簡潔に記述できます。

### チャネルの方向性

Go言語のチャネルには、その使用方法を制限するための「方向性」という概念があります。これにより、チャネルがデータの送信にのみ使用されるのか、受信にのみ使用されるのか、あるいはその両方に使用されるのかを型レベルで指定できます。

*   **`chan T`**: 双方向チャネル。`T` 型の値を送受信できます。
*   **`chan<- T`**: 送信専用チャネル。`T` 型の値をこのチャネルに送信することのみが可能です。受信しようとするとコンパイルエラーになります。
*   **`<-chan T`**: 受信専用チャネル。`T` 型の値をこのチャネルから受信することのみが可能です。送信しようとするとコンパイルエラーになります。

チャネルの方向性を指定する主な理由は以下の通りです。

1.  **型安全性とコンパイル時チェック**: コードの意図を明確にし、誤ったチャネル操作（例: 受信専用チャネルへの送信）をコンパイル時に検出できます。
2.  **APIの明確化**: 関数やメソッドのシグネチャでチャネルの方向性を指定することで、そのチャネルがどのように使用されるべきかを呼び出し元に明確に伝えます。これにより、APIの誤用を防ぎ、コードの可読性を向上させます。
3.  **設計の強制**: 特定のゴルーチンがチャネルに対して送信のみを行うべきか、受信のみを行うべきかを設計レベルで強制できます。

### `exvar` パッケージ

`exvar` パッケージ（`src/lib/exvar`）は、Go言語の初期の実験的な変数パッケージです。これは、プログラムの実行中に動的に値を公開し、監視するためのメカニズムを提供することを意図していました。例えば、デバッグやメトリクスの収集に利用されることが考えられます。このパッケージ内の `Map` 型は、キーと値のペアを保持し、その内容をイテレートしてチャネルに送信する機能を持っていました。

## 技術的詳細

このコミットの技術的な核心は、Go言語の型システムにおけるチャネルの方向性の厳密な適用にあります。

元のコードでは、`iterate` 関数/メソッドは以下のように定義されていました。

```go
func (v *Map) iterate(c <-chan KeyValue) {
    // ...
}
```
または
```go
func iterate(c <-chan KeyValue) {
    // ...
}
```

ここで、引数 `c` は `<-chan KeyValue`、つまり `KeyValue` 型の値を**受信するためのチャネル**として宣言されています。しかし、これらの関数/メソッドの内部では、以下のような操作が行われていました。

```go
c <- KeyValue{ k, v };
```

この構文 `c <- value` は、`value` をチャネル `c` に**送信する**操作です。

Goコンパイラは、受信専用として宣言されたチャネル (`<-chan`) に対して送信操作が行われることを許可しません。これは、チャネルの方向性による型安全性の保証のためです。したがって、元のコードはコンパイルエラーを引き起こすか、あるいはコンパイラがまだこの厳密なチェックを実装していなかった初期段階での潜在的なバグであったと考えられます。

このコミットでは、この矛盾を解消するために、チャネル `c` の型を `chan<- KeyValue` (送信専用チャネル) に変更しました。

```go
func (v *Map) iterate(c chan<- KeyValue) {
    // ...
}
```
または
```go
func iterate(c chan<- KeyValue) {
    // ...
}
```

これにより、関数/メソッドの内部で行われるチャネルへの送信操作と、引数として受け取るチャネルの型が一致し、コードがGo言語の型システムに準拠するようになりました。これは、Go言語の設計哲学である「コンパイル時に可能な限り多くのエラーを検出する」という原則に沿った修正です。

## コアとなるコードの解説

`exvar.go` 内の `iterate` 関数/メソッドは、`Map` 型の内部データ構造（`v.m` またはグローバルな `vars` マップ）を走査し、各キーと値のペアを `KeyValue` 構造体としてラップして、引数 `c` で渡されたチャネルに送信します。

変更前のコードでは、`c` が受信専用チャネル (`<-chan KeyValue`) として宣言されていました。これは、このチャネルからデータを受信することのみが許可されることを意味します。しかし、関数/メソッドの本体では `c <- KeyValue{ k, v }` という送信操作が行われていました。この矛盾が、Go言語の型システムによって検出され、修正が必要となりました。

変更後のコードでは、`c` が送信専用チャネル (`chan<- KeyValue`) として宣言されています。これにより、関数/メソッドの本体で行われる送信操作がチャネルの型宣言と完全に一致し、コンパイラによる型チェックをパスするようになります。

この修正は、Go言語のチャネルの方向性という強力な機能が、コードの意図を正確に表現し、潜在的なバグを早期に発見するためにどのように役立つかを示す良い例です。

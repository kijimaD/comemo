# [インデックス 24823] ファイルの概要

このコミットは、Go言語の `compress/flate` パッケージにおける DEFLATE 圧縮解除ロジックの簡素化を目的としています。具体的には、固定ハフマンテーブルの生成方法を変更し、事前計算されたテーブルを削除し、必要に応じて実行時に `sync.Once` を使用して生成するようにしました。これにより、コードの重複が削減され、バイナリサイズが縮小される一方で、初回デコード時のパフォーマンスにわずかな影響があります。

The flate library contains generator code, which is used to generate
the fixed huffman table. This is done so that fixed blocks can be
processed quicker since there is no need generate the decoder table
for fixed codes.

Instead, delete the precomputed table, and use sync.Once to generate

## 変更の背景

Go言語の `compress/flate` パッケージは、DEFLATE 圧縮形式を扱うためのライブラリです。DEFLATE 形式では、圧縮されたデータは「ブロック」に分割され、各ブロックは「非圧縮ブロック」「固定ハフマン符号ブロック」「動的ハフマン符号ブロック」のいずれかの形式でエンコードされます。

このコミット以前は、固定ハフマン符号ブロックのデコードに使用されるハフマンテーブルは、`gen.go` というジェネレータコードによって事前に計算され、`fixedhuff.go` というファイルに静的に埋め込まれていました。このアプローチの利点は、実行時にテーブルを生成するオーバーヘッドがないため、固定ブロックの処理が高速になることでした。

しかし、この方法にはいくつかの欠点がありました。

1.  **コードの重複**: `gen.go` は、`inflate.go` 内のハフマンデコーダの実装の一部をコピーして使用しており、コードの重複が生じていました。
2.  **バイナリサイズの増加**: 事前計算された巨大なテーブルが静的にバイナリに埋め込まれるため、バイナリサイズが増加していました。コミットメッセージによると、約2KiBの増加があったとされています。
3.  **保守性の低下**: ジェネレータコードと実行時コードで同じロジックが重複していると、一方を変更した際に他方も変更する必要があり、バグの温床となる可能性がありました。

このコミットは、これらの欠点を解消し、コードベースを簡素化することを目的としています。固定ハフマンテーブルの生成を、必要になったときに一度だけ実行する `sync.Once` を使用したランタイム生成に切り替えることで、上記の利点と欠点のバランスを取っています。

## 前提知識の解説

### DEFLATE 圧縮形式

DEFLATE は、LZ77アルゴリズムとハフマン符号化を組み合わせた可逆データ圧縮アルゴリズムです。RFC 1951 で定義されており、GZIP、ZLIB、PNGなどのファイル形式で広く利用されています。

DEFLATE ストリームは、一連のブロックで構成されます。各ブロックは以下のいずれかのタイプです。

*   **非圧縮ブロック (Stored block)**: データはそのまま格納されます。
*   **固定ハフマン符号ブロック (Fixed Huffman block)**: 事前に定義された固定のハフマンテーブルを使用してデータが圧縮されます。このテーブルは DEFLATE 仕様で定められており、圧縮データ内にテーブル情報を含める必要がありません。
*   **動的ハフマン符号ブロック (Dynamic Huffman block)**: データに最適なハフマンテーブルが動的に生成され、そのテーブル情報も圧縮データ内に含められます。

### ハフマン符号化 (Huffman Coding)

ハフマン符号化は、データの出現頻度に基づいて可変長の符号を割り当てるデータ圧縮手法です。出現頻度の高いデータには短い符号を、低いデータには長い符号を割り当てることで、全体のデータサイズを削減します。デコード時には、ハフマンツリーと呼ばれる二分木構造を使用して、ビットストリームから元のデータを復元します。

### 固定ハフマンテーブル (Fixed Huffman Table)

DEFLATE の固定ハフマン符号ブロックで使用されるハフマンテーブルは、RFC 1951 のセクション 3.2.6 で厳密に定義されています。このテーブルは、リテラル/長さ符号と距離符号の2種類があり、それぞれ特定のビット長と値の対応が定められています。

*   **リテラル/長さ符号 (Literal/Length Codes)**:
    *   0-143: 8ビット符号
    *   144-255: 9ビット符号
    *   256-279: 7ビット符号
    *   280-287: 8ビット符号
*   **距離符号 (Distance Codes)**:
    *   0-31: 5ビット符号

この固定テーブルを使用することで、動的ハフマンテーブルのようにテーブル自体を圧縮データに含める必要がなく、オーバーヘッドを削減できます。

### `sync.Once`

Go言語の `sync` パッケージに含まれる `Once` 型は、プログラムの実行中に特定の処理を一度だけ実行することを保証するためのプリミティブです。`Once` 型の `Do` メソッドは、引数として渡された関数を一度だけ実行します。複数のゴルーチンが同時に `Do` メソッドを呼び出しても、関数は一度しか実行されず、他のゴルーチンはその完了を待ちます。これは、リソースの初期化や、今回のケースのように一度だけ生成すればよいグローバルなデータ構造の構築に非常に有用です。

## 技術的詳細

このコミットの主要な変更点は、固定ハフマンテーブル `fixedHuffmanDecoder` の初期化戦略です。

**変更前:**
*   `src/compress/flate/gen.go` というGoプログラムが存在し、これがビルド時に実行されていました (`go:generate` ディレクティブを使用)。
*   `gen.go` は、RFC 1951 で定義された固定ハフマンテーブルの仕様に基づいて、`huffmanDecoder` 構造体のインスタンスを生成し、その内容を `src/compress/flate/fixedhuff.go` というファイルにGoのソースコードとして書き出していました。
*   `fixedhuff.go` には、`fixedHuffmanDecoder` という名前の `huffmanDecoder` 型のグローバル変数が定義され、その `chunks` フィールドには事前計算されたハフマンテーブルのデータがハードコードされていました。
*   `inflate.go` は、この `fixedHuffmanDecoder` 変数を直接参照して固定ハフマンブロックをデコードしていました。

この方式では、コンパイル時にテーブルが生成されるため、実行時のオーバーヘッドはゼロでした。しかし、`gen.go` と `inflate.go` の両方にハフマンテーブル構築ロジックの一部が重複して存在し、`fixedhuff.go` が生成されたコードとしてリポジトリに存在するという問題がありました。

**変更後:**
*   `src/compress/flate/gen.go` と `src/compress/flate/fixedhuff.go` が削除されました。これにより、コードの重複と生成されたファイルの管理が不要になりました。
*   `src/compress/flate/inflate.go` に、`fixedOnce sync.Once` と `fixedHuffmanDecoder huffmanDecoder` という2つのグローバル変数が追加されました。
*   `fixedHuffmanDecoderInit()` という新しい関数が導入されました。この関数は `fixedOnce.Do()` を呼び出し、その内部で固定ハフマンテーブルのビット長定義（RFC 1951 に基づく）を使用して `fixedHuffmanDecoder.init()` メソッドを呼び出します。
*   `NewReader` および `NewReaderDict` 関数（DEFLATE リーダーを初期化する関数）の冒頭で `fixedHuffmanDecoderInit()` が呼び出されるようになりました。

この新しいアプローチでは、`fixedHuffmanDecoder` はプログラムの実行中に初めて固定ハフマンテーブルが必要になったときに一度だけ初期化されます。`sync.Once` がこの「一度だけ」を保証するため、複数のゴルーチンが同時にデコードを開始しても、テーブルの初期化は競合状態なく安全に一度だけ行われます。

**パフォーマンスへの影響:**
コミットメッセージに記載されているように、この変更にはわずかなパフォーマンス上のトレードオフがあります。最も単純なケース（固定ブロック `"\x03\x00"` を一度だけデコードするプログラム）では、初回デコードに4.7%の時間が余分にかかります。これは、テーブルの生成が実行時に行われるようになったためです。しかし、その後のブロックの圧縮解除パフォーマンスには目立った低下はないとされており、これは `sync.Once` によってテーブルが一度生成されれば、それ以降は再生成のオーバーヘッドがないためです。

全体として、この変更はコードベースの簡素化、重複の排除、バイナリサイズの削減というメリットが、初回デコード時のわずかなパフォーマンス低下というデメリットを上回ると判断されたものです。

*   **距離符号 (Distance Codes)**:
    *   0-31: 5ビット符号

この固定テーブルを使用することで、動的ハフマンテーブルのようにテーブル自体を圧縮データに含める必要がなく、オーバーヘッドを削減できます。

### `sync.Once`

Go言語の `sync` パッケージに含まれる `Once` 型は、プログラムの実行中に特定の処理を一度だけ実行することを保証するためのプリミティブです。`Once` 型の `Do` メソッドは、引数として渡された関数を一度だけ実行します。複数のゴルーチンが同時に `Do` メソッドを呼び出しても、関数は一度しか実行されず、他のゴルーチンはその完了を待ちます。これは、リソースの初期化や、今回のケースのように一度だけ生成すればよいグローバルなデータ構造の構築に非常に有用です。

## 技術的詳細

このコミットの主要な変更点は、固定ハフマンテーブル `fixedHuffmanDecoder` の初期化戦略です。

**変更前:**
*   `src/compress/flate/gen.go` というGoプログラムが存在し、これがビルド時に実行されていました (`go:generate` ディレクティブを使用)。
*   `gen.go` は、RFC 1951 で定義された固定ハフマンテーブルの仕様に基づいて、`huffmanDecoder` 構造体のインスタンスを生成し、その内容を `src/compress/flate/fixedhuff.go` というファイルにGoのソースコードとして書き出していました。
*   `fixedhuff.go` には、`fixedHuffmanDecoder` という名前の `huffmanDecoder` 型のグローバル変数が定義され、その `chunks` フィールドには事前計算されたハフマンテーブルのデータがハードコードされていました。
*   `inflate.go` は、この `fixedHuffmanDecoder` 変数を直接参照して固定ハフマンブロックをデコードしていました。

この方式では、コンパイル時にテーブルが生成されるため、実行時のオーバーヘッドはゼロでした。しかし、`gen.go` と `inflate.go` の両方にハフマンテーブル構築ロジックの一部が重複して存在し、`fixedhuff.go` が生成されたコードとしてリポジトリに存在するという問題がありました。

**変更後:**
*   `src/compress/flate/gen.go` と `src/compress/flate/fixedhuff.go` が削除されました。これにより、コードの重複と生成されたファイルの管理が不要になりました。
*   `src/compress/flate/inflate.go` に、`fixedOnce sync.Once` と `fixedHuffmanDecoder huffmanDecoder` という2つのグローバル変数が追加されました。
*   `fixedHuffmanDecoderInit()` という新しい関数が導入されました。この関数は `fixedOnce.Do()` を呼び出し、その内部で固定ハフマンテーブルのビット長定義（RFC 1951 に基づく）を使用して `fixedHuffmanDecoder.init()` メソッドを呼び出します。
*   `NewReader` および `NewReaderDict` 関数（DEFLATE リーダーを初期化する関数）の冒頭で `fixedHuffmanDecoderInit()` が呼び出されるようになりました。

この新しいアプローチでは、`fixedHuffmanDecoder` はプログラムの実行中に初めて固定ハフマンテーブルが必要になったときに一度だけ初期化されます。`sync.Once` がこの「一度だけ」を保証するため、複数のゴルーチンが同時にデコードを開始しても、テーブルの初期化は競合状態なく安全に一度だけ行われます。

**パフォーマンスへの影響:**
コミットメッセージに記載されているように、この変更にはわずかなパフォーマンス上のトレードオフがあります。最も単純なケース（固定ブロック `"\x03\x00"` を一度だけデコードするプログラム）では、初回デコードに4.7%の時間が余分にかかります。これは、テーブルの生成が実行時に行われるようになったためです。しかし、その後のブロックの圧縮解除パフォーマンスには目立った低下はないとされており、これは `sync.Once` によってテーブルが一度生成されれば、それ以降は再生成のオーバーヘッドがないためです。

全体として、この変更はコードベースの簡素化、重複の排除、バイナリサイズの削減というメリットが、初回デコード時のわずかなパフォーマンス低下というデメリットを上回ると判断されたものです。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下のファイルに集中しています。

1.  **`src/compress/flate/fixedhuff.go`**:
    *   ファイル全体が削除されました。このファイルには、`gen.go` によって生成された固定ハフマンテーブルのデータがハードコードされていました。

2.  **`src/compress/flate/gen.go`**:
    *   ファイル全体が削除されました。このファイルは、`fixedhuff.go` を生成するためのジェネレータプログラムでした。

3.  **`src/compress/flate/inflate.go`**:
    *   `//go:generate go run gen.go -output fixedhuff.go` の行が削除されました。これにより、ビルド時のコード生成が停止します。
    *   `import "sync"` が追加されました。
    *   以下のグローバル変数が追加されました。
        ```go
        var fixedOnce sync.Once
        var fixedHuffmanDecoder huffmanDecoder
        ```
    *   `fixedHuffmanDecoderInit()` 関数が追加されました。
        ```go
        func fixedHuffmanDecoderInit() {
            fixedOnce.Do(func() {
                // These come from the RFC section 3.2.6.
                var bits [288]int
                for i := 0; i < 144; i++ {
                    bits[i] = 8
                }
                for i := 144; i < 256; i++ {
                    bits[i] = 9
                }
                for i := 256; i < 280; i++ {
                    bits[i] = 7
                }
                for i := 280; i < 288; i++ {
                    bits[i] = 8
                }
                fixedHuffmanDecoder.init(bits[:])
            })
        }
        ```
    *   `NewReader` および `NewReaderDict` 関数の冒頭で `fixedHuffmanDecoderInit()` が呼び出されるようになりました。
        ```go
        func NewReader(r io.Reader) io.ReadCloser {
            fixedHuffmanDecoderInit()
            // ... 既存の初期化ロジック ...
        }

        func NewReaderDict(r io.Reader, dict []byte) io.ReadCloser {
            fixedHuffmanDecoderInit()
            // ... 既存の初期化ロジック ...
        }
        ```
    *   `huffmanDecoder` の実装に関するコメントが更新され、事前計算に関する記述が削除されました。

## コアとなるコードの解説

このコミットの核となる変更は、`src/compress/flate/inflate.go` 内の `fixedOnce`, `fixedHuffmanDecoder`, および `fixedHuffmanDecoderInit` の導入です。

1.  **`var fixedOnce sync.Once`**:
    *   これは `sync.Once` 型の変数で、`fixedHuffmanDecoderInit` 関数内の特定のコードブロックがプログラムの実行中に一度だけ実行されることを保証します。Goの並行処理において、リソースの遅延初期化やシングルトンパターンの実装によく使用されます。

2.  **`var fixedHuffmanDecoder huffmanDecoder`**:
    *   これは `huffmanDecoder` 型のグローバル変数です。この変数が、DEFLATE の固定ハフマン符号ブロックをデコードするためのハフマンテーブルを保持します。変更前は `fixedhuff.go` で定義されていましたが、変更後は `inflate.go` 内で定義され、`fixedHuffmanDecoderInit` 関数によって初期化されます。

3.  **`func fixedHuffmanDecoderInit()`**:
    *   この関数は、`fixedHuffmanDecoder` を初期化する役割を担います。
    *   `fixedOnce.Do(func() { ... })` の呼び出しにより、内部の無名関数は一度だけ実行されます。
    *   無名関数内では、RFC 1951 のセクション 3.2.6 で定義されている固定ハフマンテーブルのビット長が `bits` 配列に設定されます。
        *   リテラル/長さ符号 (0-143) は8ビット
        *   リテラル/長さ符号 (144-255) は9ビット
        *   リテラル/長さ符号 (256-279) は7ビット
        *   リテラル/長さ符号 (280-287) は8ビット
        *   距離符号は5ビット（このコードではリテラル/長さ符号のみを扱っているように見えますが、`huffmanDecoder.init` は両方を処理できる汎用的なものです）
    *   最後に、`fixedHuffmanDecoder.init(bits[:])` を呼び出して、`fixedHuffmanDecoder` グローバル変数にハフマンテーブルを構築します。

4.  **`NewReader` および `NewReaderDict` での呼び出し**:
    *   `NewReader` と `NewReaderDict` は、それぞれ新しい DEFLATE リーダーを作成するための関数です。これらの関数の冒頭で `fixedHuffmanDecoderInit()` が呼び出されることで、DEFLATE リーダーが初めて作成される際に、固定ハフマンテーブルが確実に初期化されるようになります。これにより、テーブルが使用される前に準備が整い、かつ不要な初期化が繰り返されることがなくなります。

この一連の変更により、固定ハフマンテーブルの定義が `inflate.go` に集約され、コードの重複が解消され、`gen.go` と `fixedhuff.go` という生成コードファイルが不要になりました。これにより、コードベースがよりクリーンになり、保守性が向上しました。

# [インデックス 21888] ファイルの概要

このコミットは、Goランタイムにおけるトレースバックの表示に関する問題を修正するものです。具体的には、システムゴルーチン（ランタイム内部で使用されるゴルーチン）が、プログラムのクラッシュ時に誤ってトレースバックに表示されてしまうという競合状態を解消します。これにより、デバッグ時のトレースバックの可読性が向上し、ユーザーが自身のコードの問題に集中できるようになります。

## コミット

```
runtime: never show system goroutines in traceback

Fixes #9791

g.issystem flag setup races with other code wherever we set it.
Even if we set both in parent goroutine and in the system goroutine,
it is still possible that some other goroutine crashes
before the flag is set. We could pass issystem flag to newproc1,
but we start all goroutines with go nowadays.

Instead look at g.startpc to distinguish system goroutines (similar to topofstack).

Change-Id: Ia3467968dee27fa07d9fecedd4c2b00928f26645
Reviewed-on: https://go-review.googlesource.com/4113
Reviewed-by: Keith Randall <khr@golang.org>
```

## 変更の背景

Goプログラムがクラッシュした際、ランタイムは通常、すべての実行中のゴルーチンのスタックトレース（トレースバック）を出力します。これはデバッグにおいて非常に有用な情報ですが、ランタイム内部で動作する「システムゴルーチン」（例：ガベージコレクタ、スケジューラ、ファイナライザなど）も含まれることがありました。

このコミット以前は、システムゴルーチンを識別するために`g.issystem`というフラグが使用されていました。しかし、このフラグの設定はゴルーチンが作成された後に行われるため、以下のような競合状態が発生する可能性がありました。

1.  システムゴルーチンが作成される。
2.  そのゴルーチンが`g.issystem`フラグを設定する前に、プログラムがクラッシュする。
3.  クラッシュ時のトレースバック生成処理が、まだ`g.issystem`が設定されていないシステムゴルーチンをユーザーゴルーチンと誤認し、トレースバックに含めてしまう。

この問題は、特にプログラムの起動直後など、システムゴルーチンが完全に初期化される前にクラッシュが発生した場合に顕著でした。トレースバックに無関係なシステムゴルーチンが含まれることで、開発者は問題の根本原因を特定するのに余計な労力を費やす必要がありました。Issue #9791は、この「早期の失敗時にバックグラウンドゴルーチンがトレースバックに表示される」という問題を具体的に指摘しています。

この変更の目的は、このような誤解を招くトレースバックを排除し、デバッグ体験を改善することにあります。

## 前提知識の解説

*   **ゴルーチン (Goroutine)**: Go言語における軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行することも可能です。Goランタイムがゴルーチンのスケジューリングを管理します。
*   **トレースバック (Traceback / Stack Trace)**: プログラムがクラッシュしたり、特定のイベントが発生したりした際に、その時点での関数呼び出しの履歴（スタック）を逆順に表示したものです。どの関数がどの関数を呼び出し、最終的にどこで問題が発生したのかを特定するのに役立ちます。
*   **システムゴルーチン (System Goroutines)**: Goランタイムの内部動作を支えるために存在するゴルーチンです。例えば、ガベージコレクション、スケジューリング、タイマー処理、ファイナライザの実行など、ユーザーコードからは直接見えないが、Goプログラムの実行に不可欠なタスクを実行します。これらは通常、ユーザーがデバッグする対象ではないため、トレースバックから除外されることが望ましいです。
*   **`g` 構造体**: Goランタイム内部で、各ゴルーチンの状態を表現するデータ構造です。スタック情報、現在の状態、関連するM（マシン）やP（プロセッサ）へのポインタなど、ゴルーチンに関するあらゆる情報が含まれています。
*   **`g.issystem` フラグ (旧)**: 以前のGoランタイムで、ゴルーチンがシステムゴルーチンであるかどうかを示すために`g`構造体内に存在したブーリアンフラグです。
*   **`g.startpc`**: ゴルーチンが開始された時点のプログラムカウンタ（Program Counter）の値です。これは、ゴルーチンが実行を開始した関数のアドレスを指します。この値はゴルーチンが作成された時点で決定され、その後変更されることはありません。
*   **競合状態 (Race Condition)**: 複数の並行プロセスやスレッドが共有リソースにアクセスする際に、そのアクセス順序によって結果が非決定的に変わってしまう状態を指します。このコミットのケースでは、`g.issystem`フラグの設定とトレースバック生成のタイミングが競合していました。

## 技術的詳細

このコミットの核心は、システムゴルーチンの識別方法を`g.issystem`フラグから`g.startpc`（開始プログラムカウンタ）に基づく方法へと変更した点にあります。

従来の`g.issystem`フラグは、ゴルーチンが起動した後に設定されるため、設定が完了するまでの短い期間にクラッシュが発生すると、システムゴルーチンがユーザーゴルーチンとして誤って扱われる可能性がありました。これは、フラグの設定が他のコードと競合する可能性があり、信頼性に欠けるアプローチでした。

新しいアプローチでは、`g.startpc`を利用します。`g.startpc`はゴルーチンが開始された関数のアドレスを保持しており、これはゴルーチンが作成された時点で不変です。したがって、特定のシステムゴルーチンが常に特定の関数（例：`runfinq`、`backgroundgc`、`timerproc`など）から開始されるという事実を利用して、その`startpc`を既知のシステムゴルーチン開始関数のアドレスと比較することで、ゴルーチンがシステムゴルーチンであるかどうかを確実に判断できるようになります。

この変更により、`g.issystem`フィールドは`runtime2.go`の`g`構造体から削除され、関連するコード（`heapdump.go`, `mfinal.go`, `mgc0.go`, `proc.go`, `time.go`など）から`g.issystem = true`または`g.issystem = false`といった設定ロジックが削除されました。

代わりに、`src/runtime/traceback.go`に`isSystemGoroutine(gp *g) bool`という新しいヘルパー関数が導入されました。この関数は、与えられたゴルーチン`gp`の`startpc`を、`tracebackinit()`で初期化された既知のシステムゴルーチン開始関数のPC値（`runfinqPC`, `backgroundgcPC`, `bgsweepPC`, `forcegchelperPC`, `timerprocPC`）と比較します。これにより、競合状態のリスクなしに、システムゴルーチンを正確に識別できるようになりました。

また、`src/runtime/crash_test.go`には、この変更が正しく機能することを確認するための新しいテスト`TestNoHelperGoroutines`が追加されています。このテストは、意図的にパニックを発生させ、トレースバックにユーザーゴルーチン（`goroutine 1`）のみが表示され、システムゴルーチンが含まれないことを検証します。

## コアとなるコードの変更箇所

このコミットにおける主要な変更は以下のファイルに集中しています。

1.  **`src/runtime/runtime2.go`**:
    *   `g`構造体から`issystem bool`フィールドが削除されました。

2.  **`src/runtime/traceback.go`**:
    *   システムゴルーチンの開始PCを格納するための新しいグローバル変数（`runfinqPC`, `backgroundgcPC`, `bgsweepPC`, `forcegchelperPC`, `timerprocPC`）が追加されました。
    *   `tracebackinit()`関数内で、これらの変数が対応する関数のPC値で初期化されるようになりました。
    *   `isSystemGoroutine(gp *g) bool`という新しいヘルパー関数が追加され、`gp.startpc`に基づいてシステムゴルーチンを識別するロジックが実装されました。
    *   `tracebackothers()`関数や`proc1.go`の`checkdead()`関数など、以前`gp.issystem`を使用していた箇所が`isSystemGoroutine(gp)`の呼び出しに置き換えられました。

3.  **`src/runtime/mfinal.go`, `src/runtime/mgc0.go`, `src/runtime/proc.go`, `src/runtime/time.go`**:
    *   これらのファイル内で、システムゴルーチンを起動する際に`gp.issystem = true`を設定していた行が削除されました。

4.  **`src/runtime/heapdump.go`**:
    *   `dumpgoroutine`関数内で、`gp.issystem`の代わりに`isSystemGoroutine(gp)`が使用されるようになりました。

5.  **`src/runtime/crash_test.go`**:
    *   `TestNoHelperGoroutines`という新しいテストが追加され、トレースバックにシステムゴルーチンが含まれないことを検証します。
    *   `testEnv`関数に`GOTRACEBACK`環境変数を無視するロジックが追加されました。

`traceback.go`は、トレースバック生成の主要なロジックを含むファイルです。
*   `runfinqPC`などの新しい`uintptr`変数は、それぞれファイナライザキュー処理、バックグラウンドGC、スイープ、強制GCヘルパー、タイマー処理といったシステムゴルーチンの開始関数のアドレスを保持します。
*   `tracebackinit()`は、これらの変数を対応する関数の実際のPC値で初期化します。`funcPC`は関数のアドレスを取得するランタイム内部関数です。
*   `isSystemGoroutine(gp *g) bool`関数がこのコミットの肝です。この関数は、引数として渡されたゴルーチン`gp`の`startpc`（ゴルーチンが開始された関数のアドレス）を取得し、それが既知のシステムゴルーチン開始関数のいずれかのアドレスと一致するかどうかをチェックします。`fingRunning`はファイナライザが実行中かどうかを示すフラグで、`runfinq`ゴルーチンがシステムゴルーチンとして扱われるべきかどうかの追加条件として使用されます。

## 元コミット内容

`cmd/gc: don't copy []byte during string comparison`

現在、文字列比較式における`[]byte`から`string`への変換中に、新しい文字列が割り当てられています。この場合、比較は後で使用するために文字列を記憶しないため、文字列の割り当ては不要です。この変更は、`slicebytetostringtmp`を使用して`[]byte`バッファから直接一時的な文字列を構築し、それを`runtime.eqstring`に渡します。

## 変更の背景

Go言語では、`string`型は不変なバイトシーケンスであり、`[]byte`型は可変なバイトスライスです。これら二つの型は異なる性質を持ちますが、相互に変換することが可能です。しかし、`[]byte`から`string`への変換（例: `string(myBytes)`）は、通常、新しい`string`値を保持するためのメモリ割り当てと、元の`[]byte`の内容のコピーを伴います。これは、`string`が不変であるという性質を維持するために必要です。

このコミットが修正しようとしている問題は、文字列比較のコンテキスト、特に`string(myBytes) == "some_string"`のような式において、このメモリ割り当てが不要であるという点です。文字列比較は、比較対象の文字列を永続的に保持する必要がありません。比較が完了すれば、その一時的な文字列はすぐに不要になります。したがって、この一時的な文字列のためにメモリを割り当て、データをコピーすることは、パフォーマンスのオーバーヘッドとなり、ガベージコレクションの負荷を増大させます。

この最適化の背景には、Goランタイムのパフォーマンス向上、特にメモリ割り当ての削減とガベージコレクションの頻度低減という継続的な取り組みがあります。不要な割り当てを排除することで、アプリケーションの実行速度が向上し、レイテンシが改善されることが期待されます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラ/ランタイムに関する前提知識が必要です。

1.  **Goにおける`string`と`[]byte`**:
    *   **`string`**: Goの`string`型は、UTF-8エンコードされた不変なバイトシーケンスです。一度作成されると、その内容は変更できません。文字列は内部的に、データへのポインタと長さを保持する構造体として表現されます。
    *   **`[]byte`**: Goの`[]byte`型は、可変なバイトスライスです。これは、基盤となる配列へのポインタ、長さ、容量を保持する構造体です。スライスの内容は変更可能です。
    *   **変換時のメモリ割り当て**: `[]byte`から`string`への変換（例: `s := string(b)`）は、通常、新しい`string`値を格納するためのメモリをヒープに割り当て、`b`の内容をその新しいメモリ領域にコピーします。これは、`string`の不変性を保証するためです。

2.  **Goコンパイラの最適化**:
    *   Goコンパイラ (`gc`) は、コードのパフォーマンスを向上させるために様々な最適化を行います。その一つが、不要なメモリ割り当ての削減です。コンパイラは、特定のパターンを認識し、より効率的なランタイム関数呼び出しに置き換えることで、この最適化を実現します。

3.  **`runtime.eqstring`**:
    *   これはGoランタイム内部の関数で、2つの文字列が等しいかどうかを比較するために使用されます。Goの`==`演算子が文字列に対して使用される際に、コンパイラによってこのランタイム関数が呼び出されることがあります。

4.  **`runtime.slicebytetostringtmp`**:
    *   これはGoランタイムの内部関数であり、Goコンパイラによって特定の最適化されたシナリオで使用されます。この関数の主な目的は、`[]byte`スライスを`string`に変換する際に、新しいメモリを割り当てることなく、元の`[]byte`のバッキングメモリを直接参照する一時的な`string`を作成することです。
    *   この最適化は、コンパイラが以下の条件を保証できる場合に適用されます。
        *   変換後、元の`[]byte`が変更されないこと。
        *   結果として得られる`string`が、元の`[]byte`が変更される前に破棄されること。
    *   一般的なユースケースとしては、文字列キーのマップルックアップ (`m[string(k)]`) や文字列結合 (`"<"+string(b)+">"`) が挙げられます。このコミットにより、文字列比較 (`string(b)=="foo"`) もこの最適化の対象となりました。

5.  **Goコンパイラ内部のノードタイプ (`OARRAYBYTESTR`, `OARRAYBYTESTRTMP`, `OCMPSTR`)**:
    *   Goコンパイラ (`gc`) は、ソースコードを解析する際に、内部的な抽象構文木 (AST) や中間表現 (IR) を構築します。これらのツリーの各ノードは、特定の操作や式を表す「Opコード」を持っています。
    *   `O`プレフィックスは通常「Operation」を意味します。
    *   `OCMPSTR`: 文字列比較操作を表すノードタイプです。
    *   `OARRAYBYTESTR`: `[]byte`から`string`への変換操作を表すノードタイプです（例: `string(myBytes)`）。
    *   `OARRAYBYTESTRTMP`: `OARRAYBYTESTR`の「一時的 (Temporary)」バージョンです。コンパイラが、この変換によって生成される`string`が一時的なものであり、メモリ割り当てを回避できると判断した場合に、`OARRAYBYTESTR`ノードを`OARRAYBYTESTRTMP`に書き換えます。これは、`slicebytetostringtmp`ランタイム関数への呼び出しに変換されることを示唆します。

    *   このマーキングは、文字列比較が後で文字列を記憶しない（永続的に保持しない）ため安全であるという前提に基づいています。

2.  **ランタイム関数`slicebytetostringtmp`の利用**:
    *   コンパイラが`OARRAYBYTESTRTMP`ノードを検出すると、通常の`[]byte`から`string`への変換（メモリ割り当てとコピーを伴う）の代わりに、ランタイム関数`runtime.slicebytetostringtmp`への呼び出しを生成します。
    *   `runtime.slicebytetostringtmp`は、与えられた`[]byte`スライスのバッキング配列を直接参照する`string`ヘッダを構築します。これにより、新しいメモリ割り当てとデータコピーのオーバーヘッドが完全に回避されます。
    *   この関数は、元の`[]byte`が変更されない、または結果の`string`がすぐに破棄されるという保証がある場合にのみ安全に使用できます。文字列比較のケースでは、この保証が成り立ちます。

3.  **テストによる検証**:
    *   `src/runtime/string_test.go`に追加された`TestCompareTempString`は、この最適化が正しく機能していることを検証します。
    *   `testing.AllocsPerRun`関数を使用して、`string(b) == s`のような文字列比較が実行される際に、メモリ割り当てが発生しない（0アロケーションである）ことを確認します。これにより、最適化が期待通りに動作していることが保証されます。

この一連の変更により、Goプログラムが`[]byte`を`string`に変換して文字列比較を行う際に、不要なメモリ割り当てが削減され、結果としてパフォーマンスが向上します。これは、Goのガベージコレクタの負荷を軽減し、特に高頻度で文字列比較が行われるようなアプリケーションにおいて、よりスムーズな実行を実現します。

*   **`case OCMPSTR:` の追加**:
    *   `OCMPSTR`は、Goコード内の文字列比較式（例: `a == b`）に対応するコンパイラ内部のノードタイプです。

*   **`orderexpr(&n->left, order);` と `orderexpr(&n->right, order);`**:
    *   文字列比較の左右のオペランド（`n->left`と`n->right`）を再帰的に評価します。これにより、それらのオペランドが完全に処理され、その内部構造が確定します。
*   **コメント `// Mark string(byteSlice) arguments to reuse byteSlice backing ...`**:
    *   このコメントは、なぜこの最適化が安全であるかを説明しています。文字列比較は、比較対象の文字列を後で再利用するために記憶しないため、一時的な`string`オブジェクトを使用しても問題がないことを示しています。

*   **右オペランドに対する同様の処理**:
    *   右オペランドに対しても同様のチェックと書き換えが行われます。

## 変更の背景

Go言語では、`string`型は不変なバイトシーケンスであり、`[]byte`型は可変なバイトスライスです。これら二つの型は異なる性質を持ちますが、相互に変換することが可能です。しかし、`[]byte`から`string`への変換（例: `string(myBytes)`）は、通常、新しい`string`値を保持するためのメモリ割り当てと、元の`[]byte`の内容のコピーを伴います。これは、`string`が不変であるという性質を維持するために必要です。

このコミットが修正しようとしている問題は、文字列比較のコンテキスト、特に`string(myBytes) == "some_string"`のような式において、このメモリ割り当てが不要であるという点です。文字列比較は、比較対象の文字列を永続的に保持する必要がありません。比較が完了すれば、その一時的な文字列はすぐに不要になります。したがって、この一時的な文字列のためにメモリを割り当て、データをコピーすることは、パフォーマンスのオーバーヘッドとなり、ガベージコレクションの負荷を増大させます。

この最適化の背景には、Goランタイムのパフォーマンス向上、特にメモリ割り当ての削減とガベージコレクションの頻度低減という継続的な取り組みがあります。不要な割り当てを排除することで、アプリケーションの実行速度が向上し、レイテンシが改善されることが期待されます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラ/ランタイムに関する前提知識が必要です。

1.  **Goにおける`string`と`[]byte`**:
    *   **`string`**: Goの`string`型は、UTF-8エンコードされた不変なバイトシーケンスです。一度作成されると、その内容は変更できません。文字列は内部的に、データへのポインタと長さを保持する構造体として表現されます。
    *   **`[]byte`**: Goの`[]byte`型は、可変なバイトスライスです。これは、基盤となる配列へのポインタ、長さ、容量を保持する構造体です。スライスの内容は変更可能です。
    *   **変換時のメモリ割り当て**: `[]byte`から`string`への変換（例: `s := string(b)`）は、通常、新しい`string`値を格納するためのメモリをヒープに割り当て、`b`の内容をその新しいメモリ領域にコピーします。これは、`string`の不変性を保証するためです。

2.  **Goコンパイラの最適化**:
    *   Goコンパイラ (`gc`) は、コードのパフォーマンスを向上させるために様々な最適化を行います。その一つが、不要なメモリ割り当ての削減です。コンパイラは、特定のパターンを認識し、より効率的なランタイム関数呼び出しに置き換えることで、この最適化を実現します。

3.  **`runtime.eqstring`**:
    *   これはGoランタイム内部の関数で、2つの文字列が等しいかどうかを比較するために使用されます。Goの`==`演算子が文字列に対して使用される際に、コンパイラによってこのランタイム関数が呼び出されることがあります。

4.  **`runtime.slicebytetostringtmp`**:
    *   これはGoランタイムの内部関数であり、Goコンパイラによって特定の最適化されたシナリオで使用されます。この関数の主な目的は、`[]byte`スライスを`string`に変換する際に、新しいメモリを割り当てることなく、元の`[]byte`のバッキングメモリを直接参照する一時的な`string`を作成することです。
    *   この最適化は、コンパイラが以下の条件を保証できる場合に適用されます。
        *   変換後、元の`[]byte`が変更されないこと。
        *   結果として得られる`string`が、元の`[]byte`が変更される前に破棄されること。
    *   一般的なユースケースとしては、文字列キーのマップルックアップ (`m[string(k)]`) や文字列結合 (`"<"+string(b)+">"`) が挙げられます。このコミットにより、文字列比較 (`string(b)=="foo"`) もこの最適化の対象となりました。

5.  **Goコンパイラ内部のノードタイプ (`OARRAYBYTESTR`, `OARRAYBYTESTRTMP`, `OCMPSTR`)**:
    *   Goコンパイラ (`gc`) は、ソースコードを解析する際に、内部的な抽象構文木 (AST) や中間表現 (IR) を構築します。これらのツリーの各ノードは、特定の操作や式を表す「Opコード」を持っています。
    *   `O`プレフィックスは通常「Operation」を意味します。
    *   `OCMPSTR`: 文字列比較操作を表すノードタイプです。
    *   `OARRAYBYTESTR`: `[]byte`から`string`への変換操作を表すノードタイプです（例: `string(myBytes)`）。
    *   `OARRAYBYTESTRTMP`: `OARRAYBYTESTR`の「一時的 (Temporary)」バージョンです。コンパイラが、この変換によって生成される`string`が一時的なものであり、メモリ割り当てを回避できると判断した場合に、`OARRAYBYTESTR`ノードを`OARRAYBYTESTRTMP`に書き換えます。これは、`slicebytetostringtmp`ランタイム関数への呼び出しに変換されることを示唆します。

## 技術的詳細

このコミットの技術的詳細は、Goコンパイラ (`cmd/gc`) とGoランタイム (`src/runtime`) の連携によって、`[]byte`から`string`への変換が文字列比較のコンテキストで発生する際のメモリ割り当てを回避する仕組みにあります。

1.  **コンパイラによる変換の識別とマーキング**:
    *   `src/cmd/gc/order.c`内の`orderexpr`関数は、コンパイラのバックエンドに近い部分で、式の評価順序を決定し、最適化の機会を探します。
    *   このコミットでは、`OCMPSTR`（文字列比較）のケースが追加されました。文字列比較の左右のオペランドが評価された後、コンパイラはそれらのオペランドが`OARRAYBYTESTR`（`[]byte`から`string`への変換）であるかどうかをチェックします。
    *   もしオペランドが`OARRAYBYTESTR`であれば、そのノードの`op`フィールドを`OARRAYBYTESTRTMP`に書き換えます。この`TMP`サフィックスは、コンパイラに対して、この`[]byte`から`string`への変換が一時的なものであり、特別な最適化（具体的にはメモリ割り当てを伴わない`slicebytetostringtmp`の使用）を適用できることを示します。
    *   このマーキングは、文字列比較が後で文字列を記憶しない（永続的に保持しない）ため安全であるという前提に基づいています。

2.  **ランタイム関数`slicebytetostringtmp`の利用**:
    *   コンパイラが`OARRAYBYTESTRTMP`ノードを検出すると、通常の`[]byte`から`string`への変換（メモリ割り当てとコピーを伴う）の代わりに、ランタイム関数`runtime.slicebytetostringtmp`への呼び出しを生成します。
    *   `runtime.slicebytetostringtmp`は、与えられた`[]byte`スライスのバッキング配列を直接参照する`string`ヘッダを構築します。これにより、新しいメモリ割り当てとデータコピーのオーバーヘッドが完全に回避されます。
    *   この関数は、元の`[]byte`が変更されない、または結果の`string`がすぐに破棄されるという保証がある場合にのみ安全に使用できます。文字列比較のケースでは、この保証が成り立ちます。

3.  **テストによる検証**:
    *   `src/runtime/string_test.go`に追加された`TestCompareTempString`は、この最適化が正しく機能していることを検証します。
    *   `testing.AllocsPerRun`関数を使用して、`string(b) == s`のような文字列比較が実行される際に、メモリ割り当てが発生しない（0アロケーションである）ことを確認します。これにより、最適化が期待通りに動作していることが保証されます。

この一連の変更により、Goプログラムが`[]byte`を`string`に変換して文字列比較を行う際に、不要なメモリ割り当てが削減され、結果としてパフォーマンスが向上します。これは、Goのガベージコレクタの負荷を軽減し、特に高頻度で文字列比較が行われるようなアプリケーションにおいて、よりスムーズな実行を実現します。

## コアとなるコードの解説

### `src/cmd/gc/order.c` の変更

この変更は、Goコンパイラの`orderexpr`関数内で行われています。`orderexpr`は、コンパイラが抽象構文木 (AST) を走査し、各ノードの評価順序を決定し、最適化を適用する場所です。

*   **`case OCMPSTR:` の追加**:
    *   `OCMPSTR`は、Goコード内の文字列比較式（例: `a == b`）に対応するコンパイラ内部のノードタイプです。
    *   このケースが追加されたことで、コンパイラは文字列比較式を特別に処理するようになります。
*   **`orderexpr(&n->left, order);` と `orderexpr(&n->right, order);`**:
    *   文字列比較の左右のオペランド（`n->left`と`n->right`）を再帰的に評価します。これにより、それらのオペランドが完全に処理され、その内部構造が確定します。
*   **コメント `// Mark string(byteSlice) arguments to reuse byteSlice backing ...`**:
    *   このコメントは、なぜこの最適化が安全であるかを説明しています。文字列比較は、比較対象の文字列を後で再利用するために記憶しないため、一時的な`string`オブジェクトを使用しても問題がないことを示しています。
*   **`if(n->left->op == OARRAYBYTESTR)` と `n->left->op = OARRAYBYTESTRTMP;`**:
    *   もし文字列比較の左オペランドが`OARRAYBYTESTR`（`[]byte`から`string`への変換）である場合、そのノードのオペレーションタイプを`OARRAYBYTESTRTMP`に書き換えます。
    *   `OARRAYBYTESTRTMP`は、この変換が一時的なものであり、メモリ割り当てを伴わない`runtime.slicebytetostringtmp`関数を使用できることをコンパイラに伝えます。
*   **右オペランドに対する同様の処理**:
    *   右オペランドに対しても同様のチェックと書き換えが行われます。

この変更により、コンパイラは文字列比較のコンテキストで`string(byteSlice)`のような変換を見つけると、それを一時的な変換としてマークし、ランタイムがメモリ割り当てなしで処理できるように指示します。

### `src/runtime/string.go` の変更

このファイルでは、`slicebytetostringtmp`関数のコメントに一行追加されています。

*   **`// Third such case is string(b)=="foo" comparison where b is []byte.`**:
    *   これは、`slicebytetostringtmp`が使用される3番目の主要なケースとして、`[]byte`から`string`への変換が文字列比較の文脈で行われる場合が追加されたことを明示しています。
    *   このコメントの追加は、コードの動作には直接影響しませんが、この関数の意図と使用されるシナリオを明確にするための重要なドキュメントの更新です。

### `src/runtime/string_test.go` の変更

このファイルには、新しいテスト関数`TestCompareTempString`が追加されています。

*   **`func TestCompareTempString(t *testing.T) { ... }`**:
    *   このテストは、`[]byte`から`string`への変換を含む文字列比較が、メモリ割り当てなしで実行されることを検証するために設計されています。
*   **`s := "foo"` と `b := []byte(s)`**:
    *   テスト用の文字列`s`と、それに対応する`[]byte`スライス`b`を準備します。
*   **`n := testing.AllocsPerRun(1000, func() { ... })`**:
    *   `testing.AllocsPerRun`は、指定された関数が実行される間に発生する平均メモリ割り当て回数を測定するためのGoのテストユーティリティです。ここでは、1000回の実行における平均割り当て回数を測定しています。
    *   内部の無名関数では、`string(b) != s`と`string(b) == s`という二つの文字列比較が行われています。これは、比較が正しく行われることと、その過程でメモリ割り当てが発生しないことを確認するためです。
*   **`if n != 0 { t.Fatalf("want 0 allocs, got %v", n) }`**:
    *   テストの最終的なアサーションです。`AllocsPerRun`が返す割り当て回数`n`が0であることを期待しています。もし0でなければ、テストは失敗し、エラーメッセージが出力されます。

このテストの追加により、コンパイラとランタイムの最適化が期待通りに機能し、`[]byte`から`string`への一時的な変換が文字列比較においてメモリ割り当てを発生させないことが保証されます。

# [インデックス 21654] ファイルの概要

このコミットは、Goコンパイラのフロントエンドである `cmd/gc` を、アーキテクチャ固有のバックエンド（`5g`, `6g`, `8g`, `9g` など）から独立した真のライブラリとして再構築することを目的としています。これにより、コンパイラのモジュール性が向上し、将来的なGo言語でのコンパイラ書き換え（セルフホスティング）への移行が容易になります。

## コミット

Date:   Thu Jan 22 00:52:01 2015 -0500

    cmd/gc: make cmd/gc a real library

    cmd/gc contains symbol references into the back end dirs like 6g.
    It also contains a few files that include the back end header files and
    are compiled separately for each back end, despite being in cmd/gc.

    program written Go.

    call into cmd/gc after making the necessary references available.

## 元コミット内容

`cmd/gc` は、`6g` のようなバックエンドディレクトリへのシンボル参照を含んでいました。また、`cmd/gc` 内にありながら、バックエンドのヘッダーファイルを含み、各バックエンド用に個別にコンパイルされるファイルもいくつか存在しました。さらに、`cmd/gc` が `main` 関数を定義していたため、少なくとも1つの逆方向のシンボル参照が避けられない状態でした（そうでなければバックエンドコードに入ることができません）。

これらの実装は便宜的なものでしたが、特にGoで書かれたプログラムにとっては結合度が高すぎました。

このコミットは、`cmd/gc` を真のライブラリとすることで、バックエンドが `main` 関数を定義し、必要な参照を利用可能にした上で `cmd/gc` を呼び出すように変更します。`cmd/gc` が真のライブラリになることで、Go言語への移行が容易になります。

## 変更の背景

Goコンパイラは、当初C言語で書かれており、Plan9のCコンパイラから派生しました。しかし、Go言語の進化とともに、コンパイラ自体をGo言語で書き直す（セルフホスティング）という目標が掲げられました。この「CからGoへの移行」は、コンパイラの保守性、生産性、そしてGo言語の原則との整合性を高めるために不可欠でした。

このコミットが行われた2015年1月は、Go 1.4のリリース直後であり、Go 1.5でのセルフホスティングコンパイラの実現に向けた重要な準備段階でした。当時のGoコンパイラ（`gc`）は、フロントエンド（Goソースコードの解析、AST生成、型チェックなど）と、ターゲットアーキテクチャ固有のバックエンド（中間表現から機械語への変換、最適化など）が密接に結合していました。

具体的には、`cmd/gc` はコンパイラの共通部分を担っていましたが、実際には各アーキテクチャ（`5g` for ARM, `6g` for AMD64, `8g` for 386, `9g` for PowerPC）のバックエンドと強く依存していました。この依存関係は、`cmd/gc` がバックエンドのシンボルを直接参照したり、バックエンド固有のヘッダーファイルをインクルードしたり、さらには `main` 関数を定義してバックエンドコードへのエントリポイントとなっていた点に現れていました。

このような密結合は、コンパイラをGo言語で書き直す上で大きな障害となります。Go言語のモジュール性やパッケージ管理の恩恵を最大限に受けるためには、各コンポーネントが疎結合である必要があります。特に、`cmd/gc` が `main` 関数を持つことは、バックエンドが `cmd/gc` をライブラリとして利用するのではなく、`cmd/gc` がバックエンドを呼び出すという逆方向の依存関係を生み出し、柔軟性を損なっていました。

このコミットは、コンパイラのセルフホスティングという長期的な目標を見据え、`cmd/gc` を独立した再利用可能なライブラリとして切り出すことで、コンパイラ全体のアーキテクチャをよりクリーンでGoらしいものにするための重要な一歩でした。これにより、各バックエンドが `cmd/gc` ライブラリをインポートし、自身の `main` 関数から呼び出すという、より自然な依存関係が確立されます。

## 前提知識の解説

このコミットの理解には、以下のGoコンパイラの基本的なアーキテクチャと関連する概念の知識が役立ちます。

1.  **Goコンパイラの構造 (gc)**:
    *   **フロントエンド (Frontend)**: Goソースコードを解析し、抽象構文木 (AST) を生成し、型チェックを行う部分です。主に `cmd/gc` がこの役割を担っていました。
    *   **中間表現 (IR - Intermediate Representation)**: ASTから生成される、機械語に依存しない中間的なコード表現です。Goコンパイラでは、当初は独自のツリーベースのIRを使用していましたが、後にSSA (Static Single Assignment) 形式のIRに移行しました。
    *   **バックエンド (Backend)**: 中間表現を特定のターゲットアーキテクチャ（例: AMD64, ARM, 386, PowerPC）の機械語に変換し、最適化を行う部分です。Goコンパイラでは、`5g`, `6g`, `8g`, `9g` といったツールが各アーキテクチャのバックエンドを担当していました。
    *   **リンカ (Linker)**: コンパイルされたオブジェクトファイルを結合し、実行可能ファイルを生成します。

2.  **C言語におけるコンパイルとリンク**:
    *   C言語のプロジェクトでは、通常、複数のソースファイルが個別にコンパイルされ、オブジェクトファイル（`.o` や `.obj`）が生成されます。
    *   これらのオブジェクトファイルは、リンカによって結合され、最終的な実行可能ファイルやライブラリ（静的ライブラリ `.a` や動的ライブラリ `.so`/`.dll`）が作成されます。
    *   **シンボル参照**: あるオブジェクトファイルが別のオブジェクトファイルで定義された関数や変数を使用する場合、それはシンボル参照として解決されます。リンカがこれらの参照を解決し、最終的な実行可能ファイル内で正しいアドレスに結びつけます。
    *   **ヘッダーファイル**: C/C++では、関数や変数の宣言をヘッダーファイル（`.h`）に記述し、実装をソースファイル（`.c` や `.cpp`）に記述するのが一般的です。ヘッダーファイルをインクルードすることで、コンパイラは他のソースファイルで定義された要素の存在と型を知ることができます。

3.  **Goコンパイラのセルフホスティング (Self-hosting)**:
    *   コンパイラ自身が、そのコンパイラがコンパイルする言語で書かれている状態を指します。Goコンパイラは、Go 1.5で完全にセルフホスティングされました。
    *   セルフホスティングの利点は、コンパイラの開発にその言語のツールやエコシステムを直接利用できること、コンパイラ自体のバグ修正や機能追加が容易になること、そして言語の設計原則がコンパイラの実装にも反映されることです。
    *   C言語で書かれたコンパイラをGo言語で書き直す際には、段階的な移行が必要です。通常、既存のCコンパイラが「ブートストラップコンパイラ」として機能し、Goで書かれた新しいコンパイラをコンパイルします。

4.  **`main` 関数の役割**:
    *   C言語プログラムのエントリポイントです。プログラムの実行は `main` 関数から開始されます。
    *   このコミットでは、`cmd/gc` が `main` を持っていたことが問題視されています。これは、`cmd/gc` が独立したライブラリとして機能するのではなく、それ自体が実行可能なプログラムであり、バックエンドを「呼び出す」ような構造になっていたためです。理想的には、バックエンドが `main` を持ち、`cmd/gc` をライブラリとして「利用する」形が望ましいとされました。

これらの概念を理解することで、このコミットがGoコンパイラのアーキテクチャにおいてどのような課題を解決し、将来の発展にどのように貢献したかが明確になります。

## 技術的詳細

このコミットの核心は、Goコンパイラのフロントエンドである `cmd/gc` と、各アーキテクチャ固有のバックエンドとの間の結合度を劇的に低減し、`cmd/gc` を真のライブラリとして機能させることにあります。この変更は、主に以下の技術的アプローチによって実現されています。

1.  **`main` 関数の移動と `gcmain` の導入**:
    *   変更前: `cmd/gc` が `main` 関数を定義し、そこからバックエンド固有の処理を呼び出していました。これにより、`cmd/gc` がバックエンドに依存する形になっていました。
    *   変更後: 各バックエンド（`src/cmd/5g/galign.c`, `src/cmd/6g/galign.c`, `src/cmd/8g/galign.c`, `src/cmd/9g/galign.c` など）が自身の `main` 関数を定義するようになりました。
    *   これらの新しい `main` 関数は、`cmd/gc` の主要な処理を実行するために `gcmain(argc, argv)` という関数を呼び出します。`gcmain` は `src/cmd/gc/go.h` で宣言され、`src/cmd/gc/main.c` (コミットには含まれていないが、この変更の文脈で作成または変更されたと推測される) に実装されています。これにより、バックエンドがフロントエンドをライブラリとして利用するという、より論理的な依存関係が確立されました。

2.  **`Arch` 構造体の導入と関数ポインタによる抽象化**:
    *   このコミットの最も重要な変更点の一つは、`src/cmd/gc/go.h` に `Arch` 構造体が導入されたことです。
    *   `Arch` 構造体は、`thechar` (アーキテクチャ識別子), `thestring` (アーキテクチャ名), `thelinkarch` (リンカアーキテクチャ情報), `typedefs` (型定義) といったアーキテクチャ固有の定数やデータだけでなく、`cgen`, `bgen`, `gjmp`, `anyregalloc` など、バックエンド固有の動作をカプセル化する多数の**関数ポインタ**を含んでいます。
    *   変更前は、`cmd/gc` 内のコードがこれらのバックエンド固有の関数を直接呼び出したり、グローバル変数としてアクセスしたりしていました。
    *   変更後: `cmd/gc` 内の共通コードは、`arch.cgen(...)`, `arch.bgen(...)` のように、`Arch` 構造体を介してこれらの関数ポインタを呼び出すようになりました。
    *   各バックエンドの `main` 関数（`galign.c` 内）では、`gcmain` を呼び出す前に、自身のアーキテクチャに特化した関数や定数のアドレスを `arch` 構造体の対応するフィールドに設定します。これにより、`cmd/gc` は実行時にどのバックエンドの機能を使用すべきかを動的に決定できるようになり、コンパイル時にバックエンドとの直接的なシンボル結合が不要になりました。

3.  **ヘッダーファイルの整理と依存関係の解消**:
    *   `src/cmd/*/opt.h` や `src/cmd/*/gg.h` といったバックエンド固有のヘッダーファイルから、`ProgInfo` 構造体や `newproc`, `deferproc` などのグローバルな `Node*` 変数の宣言が削除されました。
    *   これらの共通定義は、`src/cmd/gc/go.h` に移動され、必要に応じて `Arch` 構造体の一部として再定義されました。
    *   これにより、`cmd/gc` 内のソースファイルがバックエンド固有のヘッダーファイルを直接インクルードする必要がなくなり、コンパイル時の依存関係が大幅に削減されました。

4.  **ビルドプロセスの変更 (`src/cmd/dist/build.go`)**:
    *   `src/cmd/dist/build.go` はGoのビルドシステムを定義するファイルです。このコミットでは、`cmd/5g`, `cmd/6g`, `cmd/8g`, `cmd/9g` の依存関係から、`../gc/cplx.c`, `../gc/pgen.c`, `../gc/plive.c`, `../gc/popt.c`, `../gc/popt.h` といった `cmd/gc` のCソースファイルやヘッダーファイルの直接的な参照が削除されました。
    *   代わりに、これらのバックエンドは `$GOROOT/pkg/obj/${GOHOSTOS}_$GOHOSTARCH/libgc.a` に依存するようになりました。これは、`cmd/gc` が独立した静的ライブラリ (`libgc.a`) としてビルドされ、各バックエンドがそのライブラリをリンクするという新しいビルドフローを明確に示しています。

これらの変更により、`cmd/gc` はバックエンドから完全に独立した共通のコンパイラフロントエンドライブラリとなり、各バックエンドは必要に応じてこのライブラリをインポートし、自身のアーキテクチャ固有の機能を提供するためのフック（`Arch` 構造体の関数ポインタ）を埋め込む形になりました。これは、GoコンパイラがC言語からGo言語へと移行する上で、コードベースのモジュール化とクリーンなアーキテクチャを確立するための極めて重要なステップでした。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下のファイル群に集中しています。

1.  **`src/cmd/gc/go.h`**:

    *   代わりに、これらのバックエンドは `$GOROOT/pkg/obj/${GOHOSTOS}_$GOHOSTARCH/libgc.a` に依存するようになります。

これらの変更は、Goコンパイラのビルドシステムと内部アーキテクチャの根本的な再編成を示しており、`cmd/gc` を独立したライブラリとして確立するための重要なステップです。

## コアとなるコードの解説

このコミットの核心は、`cmd/gc` を独立したライブラリとして機能させるための「インターフェース」の確立と、そのインターフェースを介したバックエンドとの連携です。

**1. `src/cmd/gc/go.h` における `Arch` 構造体の定義**

```c
// src/cmd/gc/go.h (抜粋)

typedef struct Arch Arch;

struct Arch
{
    int thechar;
    char *thestring;
    LinkArch *thelinkarch;
    Typedef *typedefs;
    Prog zprog;

    int ACALL;
    // ... (多数の定数) ...
    vlong MAXWIDTH;

    void (*afunclit)(Addr*, Node*);
    int (*anyregalloc)(void);
    void (*betypeinit)(void);
    void (*bgen)(Node*, int, int, Prog*);
    void (*cgen)(Node*, Node*);
    // ... (多数の関数ポインタ) ...
    Prog* (*unpatch)(Prog*);
};

EXTERN Arch arch; // グローバルな arch インスタンス
```

*   **`Arch` 構造体**: この構造体は、Goコンパイラのフロントエンド (`cmd/gc`) がバックエンド (`5g`, `6g` など) から提供されるべき、アーキテクチャ固有の機能や定数を集約したものです。
    *   `thechar`, `thestring`, `thelinkarch`, `typedefs`, `MAXWIDTH` などは、各アーキテクチャの特性を示す定数やデータ構造です。
    *   `afunclit`, `anyregalloc`, `bgen`, `cgen` などは、バックエンドが実装するべき、コード生成やレジスタ割り当て、分岐処理などの低レベルな操作を表す**関数ポインタ**です。
*   **`EXTERN Arch arch;`**: `arch` という名前のグローバル変数が宣言されています。この変数は、各バックエンドが起動時に自身のアーキテクチャに特化した実装で初期化する「共有インターフェース」として機能します。

**2. 各バックエンドの `galign.c` における `main` 関数の実装**

```c
// src/cmd/6g/galign.c (抜粋)

void
main(int argc, char **argv)
{
    arch.thechar = thechar;
    arch.thestring = thestring;
    arch.thelinkarch = thelinkarch;
    arch.typedefs = typedefs;
    arch.zprog = zprog;
    arch.ACALL = ACALL;
    // ... (他の定数や関数ポインタの初期化) ...
    arch.afunclit = afunclit;
    arch.anyregalloc = anyregalloc;
    arch.betypeinit = betypeinit;
    arch.bgen = bgen;
    arch.cgen = cgen;
    // ... (他の関数ポインタの初期化) ...

    gcmain(argc, argv); // cmd/gc の共通処理を呼び出す
}
```

*   **`main` 関数の移動**: 以前は `cmd/gc` が `main` を持っていたのに対し、このコミット以降は各バックエンド（例: `6g`）が自身の `main` 関数を持つようになりました。
*   **`arch` の初期化**: 各バックエンドの `main` 関数は、まず自身のアーキテクチャに固有の定数や、自身が実装する低レベルな関数へのポインタを、グローバルな `arch` 構造体の対応するフィールドに代入します。これにより、`arch` はそのバックエンドの「コンテキスト」で初期化されます。
*   **`gcmain` の呼び出し**: `arch` の初期化が完了した後、バックエンドの `main` 関数は `gcmain(argc, argv)` を呼び出します。`gcmain` は `cmd/gc` の主要なコンパイルロジックを含んでおり、このロジックは `arch` 構造体を介してバックエンド固有の機能にアクセスします。

**3. `cmd/gc` 内の共通コードの変更**

```c
// src/cmd/gc/gen.c (抜粋)

// 変更前:
// wasregalloc = anyregalloc();
// patch(p1, pc);
// bgen(n->ntest, 0, -n->likely, p2);
// cgen_asop(n);

// 変更後:
wasregalloc = arch.anyregalloc(); // arch 経由で呼び出し
// ...
arch.patch(p1, pc); // arch 経由で呼び出し
arch.bgen(n->ntest, 0, -n->likely, p2); // arch 経由で呼び出し
// ...
arch.cgen_asop(n); // arch 経由で呼び出し
```

*   `cmd/gc` 内のCソースファイル（`align.c`, `cplx.c`, `gen.c` など）は、以前直接呼び出していたバックエンド固有の関数やグローバル変数へのアクセスを、すべて `arch.` プレフィックスを付けて `arch` 構造体を介するように変更されました。
*   これにより、`cmd/gc` のコードは特定のバックエンドの実装に直接依存することなく、`arch` インターフェースを通じて抽象化された操作を実行できるようになります。

**この変更の意義**:

この設計パターンは、C言語における「仮想関数テーブル」や「依存性注入 (Dependency Injection)」に似ています。`cmd/gc` は、具体的なバックエンドの実装を知ることなく、`Arch` インターフェースが提供する機能セットにのみ依存します。各バックエンドは、起動時にこの `Arch` インターフェースを自身の具体的な実装で「満たす」ことで、`cmd/gc` の共通ロジックが自身のアーキテクチャ上で正しく動作するようにします。

この疎結合化は、GoコンパイラをC言語からGo言語へ移行させる上で極めて重要でした。なぜなら、共通のフロントエンドロジックをGoで書き直す際に、各バックエンドのC言語実装との依存関係を最小限に抑えることができたからです。最終的に、Go 1.5では、このモジュール化されたアーキテクチャの上に、Go言語で書かれた新しいバックエンドが構築され、コンパイラのセルフホスティングが実現されました。

# [インデックス 23895] ファイルの概要

このコミットは、Goランタイムにおけるメモリ割り当てとガベージコレクション（GC）の安全性に関する重要な修正を導入しています。特に、ARMやPowerPCのような弱順序メモリモデルを持つアーキテクチャにおいて、GCが未初期化メモリや古いヒープビットマップ情報を参照してしまう可能性を排除するための「公開バリア（publication barrier）」の導入が主な変更点です。

変更されたファイルは以下の通りです。

*   `src/runtime/asm_386.s`
*   `src/runtime/asm_amd64.s`
*   `src/runtime/asm_amd64p32.s`
*   `src/runtime/asm_arm.s`
*   `src/runtime/atomic_arm64.s`
*   `src/runtime/atomic_ppc64x.s`
*   `src/runtime/malloc.go`
*   `src/runtime/stubs.go`
*   `src/runtime/sys_darwin_arm.s`
*   `src/runtime/sys_freebsd_arm.s`
*   `src/runtime/sys_linux_arm.s`
*   `src/runtime/sys_nacl_arm.s`
*   `src/runtime/sys_netbsd_arm.s`
*   `src/runtime/sys_openbsd_arm.s`

## コミット

Goランタイムにおいて、弱順序アーキテクチャ（ARM, PowerPCなど）上でガベージコレクタが型安全なメモリを確実に認識できるようにするための修正。具体的には、`mallocgc`関数内で新しく割り当てられたオブジェクトがGCに公開される前に、そのメモリの初期化とヒープビットマップの設定が完了していることを保証する「公開バリア」を導入しました。これにより、GCが未初期化メモリや古いヒープビットマップを参照する可能性が排除されます。

## 元コミット内容

```
runtime: ensure GC sees type-safe memory on weak machines

Currently its possible for the garbage collector to observe
uninitialized memory or stale heap bitmap bits on weakly ordered
architectures such as ARM and PPC. On such architectures, the stores
that zero newly allocated memory and initialize its heap bitmap may
move after a store in user code that makes the allocated object
observable by the garbage collector.

To fix this, add a "publication barrier" (also known as an "export
barrier") before returning from mallocgc. This is a store/store
barrier that ensures any write done by user code that makes the
returned object observable to the garbage collector will be ordered
after the initialization performed by mallocgc. No barrier is
necessary on the reading side because of the data dependency between
loading the pointer and loading the contents of the object.

Fixes one of the issues raised in #9984.

Change-Id: Ia3d96ad9c5fc7f4d342f5e05ec0ceae700cd17c8
```

## 変更の背景

この変更の背景には、マルチコアプロセッサとメモリ階層の複雑さ、特に異なるアーキテクチャが採用するメモリモデルの違いがあります。Goのガベージコレクタは、ヒープ上のオブジェクトを正確に追跡し、不要になったメモリを解放する役割を担っています。このプロセスにおいて、GCはオブジェクトが指すメモリの内容や、そのオブジェクトがヒープ上でどのように表現されているか（ヒープビットマップ）を正確に把握する必要があります。

問題は、ARMやPowerPCのような「弱順序（weakly ordered）」メモリモデルを持つアーキテクチャで発生していました。これらのアーキテクチャでは、コンパイラやCPUがプログラムの実行順序を最適化のために変更することが許されています。特に、ストア（書き込み）操作の順序が入れ替わることがあります。

具体的には、Goの`mallocgc`関数が新しいオブジェクトのためにメモリを割り当てる際、以下のステップが実行されます。
1.  割り当てられたメモリ領域をゼロで初期化する。
2.  そのオブジェクトに対応するヒープビットマップを設定し、GCがオブジェクトの型情報やポインタの有無を正しく認識できるようにする。
3.  ユーザーコードに新しく割り当てられたオブジェクトへのポインタを返す（これによりオブジェクトが「公開」され、GCを含む他のゴルーチンから参照可能になる）。

弱順序アーキテクチャでは、上記1と2のストア操作が、3のオブジェクトを公開するストア操作よりも後に実行されてしまう可能性がありました。もしこのような順序の入れ替わりが発生すると、GCがオブジェクトへのポインタを読み取った際に、まだゼロ初期化されていないメモリや、古い（不正確な）ヒープビットマップ情報を見てしまうことになります。これは、GCの誤動作や、最悪の場合、プログラムのクラッシュにつながる可能性のある深刻なバグです。

この問題は、Go issue #9984で提起された複数の問題の一つとして認識され、このコミットはその解決策の一つとして導入されました。

## 前提知識の解説

### メモリモデル (Memory Model)

コンピュータシステムにおけるメモリモデルは、複数のプロセッサ（またはコア）が共有メモリにアクセスする際の、読み書き操作の順序と可視性を定義するルールセットです。

*   **強順序メモリモデル (Strongly Ordered Memory Model)**: x86やx64アーキテクチャがこれに該当します。一般的に、プロセッサはプログラムで指定された順序でメモリ操作を実行し、その順序が他のプロセッサからも観測されることを保証します。ストア操作の順序が入れ替わることはほとんどありません。
*   **弱順序メモリモデル (Weakly Ordered Memory Model)**: ARMやPowerPCなどのアーキテクチャがこれに該当します。これらのアーキテクチャでは、パフォーマンス向上のために、プロセッサやコンパイラがメモリ操作の順序を積極的に変更（再順序付け）することが許されています。特に、ストア操作が他のストア操作やロード操作に対して再順序付けされることがよくあります。これにより、あるプロセッサが行った書き込みが、別のプロセッサからすぐに観測されるとは限りません。

### メモリバリア (Memory Barrier / Memory Fence)

メモリバリアは、弱順序メモリモデルにおいて、メモリ操作の順序を強制するための特別な命令です。特定のメモリ操作がバリアを越えて再順序付けされるのを防ぎます。

*   **ストアバリア (Store Barrier / Store/Store Barrier)**: 複数のストア操作の順序を保証します。バリアより前のストア操作が、バリアより後のストア操作よりも先に完了することを保証します。このコミットで導入された「公開バリア」は、このストア・ストアバリアの一種です。
*   **ロードバリア (Load Barrier / Load/Load Barrier)**: 複数のロード操作の順序を保証します。
*   **フルバリア (Full Barrier)**: ロードとストアの両方の順序を保証します。

### ガベージコレクション (Garbage Collection, GC)

Go言語は自動メモリ管理（ガベージコレクション）を採用しています。GCは、プログラムが動的に割り当てたメモリのうち、もはや到達不可能になった（どの変数からも参照されなくなった）オブジェクトを自動的に識別し、そのメモリを解放する仕組みです。

*   **ヒープビットマップ (Heap Bitmap)**: GoのGCは、ヒープ上の各メモリワードがポインタであるか、非ポインタであるかを識別するためにヒープビットマップを使用します。これにより、GCはポインタをたどって到達可能なオブジェクトを正確にマークし、誤って非ポインタデータをポインタとして解釈することを防ぎます。
*   **GCスキャン**: GCは、ルート（グローバル変数、スタック、レジスタなど）から開始して、ポインタをたどりながらヒープ上の到達可能なオブジェクトをスキャンします。

### オブジェクトの公開 (Publication)

プログラミングにおいて「オブジェクトの公開」とは、新しく作成または初期化されたオブジェクトへの参照が、他のスレッドやゴルーチン、あるいはガベージコレクタなどの外部エンティティからアクセス可能になることを指します。このコミットの文脈では、`mallocgc`が新しく割り当てたメモリへのポインタを呼び出し元に返すことで、そのオブジェクトがGCに「公開」されることを意味します。

## 技術的詳細

このコミットの核心は、弱順序アーキテクチャにおけるメモリ割り当ての安全性を確保することです。

### `mallocgc`における問題の再確認

`mallocgc`関数は、新しいオブジェクトのためにメモリを割り当て、そのメモリをゼロ初期化し、対応するヒープビットマップを設定します。その後、この新しいオブジェクトへのポインタを呼び出し元に返します。

弱順序アーキテクチャでは、以下の3つの操作の順序が問題となります。
1.  メモリのゼロ初期化（ストア操作）
2.  ヒープビットマップの設定（ストア操作）
3.  オブジェクトへのポインタを返す（これによりオブジェクトが「公開」されるストア操作）

CPUやコンパイラの最適化により、1と2の操作が3の操作よりも後に実行される可能性があります。もしGCが3の操作によって公開されたポインタを読み取ったが、1や2の操作がまだ完了していない場合、GCは未初期化のデータや不正確なヒープビットマップを見てしまい、誤った判断を下すことになります。

### 「公開バリア (Publication Barrier)」の導入

この問題を解決するために、`mallocgc`関数内でオブジェクトが呼び出し元に返される直前に`publicationBarrier()`が導入されました。このバリアは「ストア・ストアバリア」として機能します。

*   **ストア・ストアバリアの機能**: `publicationBarrier()`より前のすべてのストア操作（メモリのゼロ初期化、ヒープビットマップの設定）が、`publicationBarrier()`より後のすべてのストア操作（オブジェクトの公開）よりも先に完了することを保証します。これにより、オブジェクトがGCに公開される時点では、そのメモリが完全に初期化され、ヒープビットマップも正しく設定されていることが保証されます。

### 読み込み側でバリアが不要な理由

コミットメッセージには「No barrier is necessary on the reading side because of the data dependency between loading the pointer and loading the contents of the object.」とあります。これは、ほとんどのアーキテクチャにおいて、データ依存性のあるロード操作の順序は保証されるためです。

具体的には、GCがオブジェクトへのポインタをロードし、そのポインタを使ってオブジェクトの内容をロードする場合、ポインタのロードと内容のロードの間にはデータ依存性があります。CPUは通常、このような依存性のある操作の順序を維持するため、別途ロードバリアを挿入する必要はありません。ポインタが有効であれば、そのポインタが指す内容も最新の状態であることが期待されます。

### 各アーキテクチャでの`publicationBarrier`の実装

`publicationBarrier`は、アーキテクチャごとに異なるアセンブリコードで実装されています。

*   **x86/x64 (386, amd64, amd64p32)**:
    *   `TEXT ·publicationBarrier(SB),NOSPLIT,$0-0`
    *   `RET`
    *   x86/x64アーキテクチャは強順序メモリモデルを持つため、ストア操作の再順序付けは基本的に発生しません。したがって、`publicationBarrier`は実質的に何もしない（コンパイルバリアとしてのみ機能する）`RET`命令として実装されています。
*   **ARMv7+ (`src/runtime/asm_arm.s`, `src/runtime/sys_darwin_arm.s`, `src/runtime/sys_freebsd_arm.s`, `src/runtime/sys_nacl_arm.s`, `src/runtime/sys_netbsd_arm.s`, `src/runtime/sys_openbsd_arm.s`)**:
    *   `TEXT runtime·armPublicationBarrier(SB),NOSPLIT,$-4-0`
    *   `WORD $0xf57ff05e // DMB ST`
    *   ARMv7以降では、`DMB ST` (Data Memory Barrier, Store) 命令がストア・ストアバリアとして使用されます。これは、それより前のすべてのストアが、それより後のすべてのストアよりも先に完了することを保証します。
*   **ARM64 (`src/runtime/atomic_arm64.s`)**:
    *   `TEXT ·publicationBarrier(SB),NOSPLIT,$-8-0`
    *   `DMB $0xe // DMB ST`
    *   ARM64でも同様に`DMB ST`命令が使用されます。`$0xe`は`ST`（Store）バリアを指定するオペランドです。
*   **PowerPC (`src/runtime/atomic_ppc64x.s`)**:
    *   `TEXT ·publicationBarrier(SB),NOSPLIT,$-8-0`
    *   `WORD $0x7c2004ac // LWSYNC`
    *   PowerPCでは`LWSYNC`命令が使用されます。これは、Power ISA v2.07で推奨される「export barrier」であり、ロード/ロード、ロード/ストア、ストア/ストアのバリアとして機能します。
*   **Linux ARM (`src/runtime/sys_linux_arm.s`)**:
    *   `TEXT publicationBarrier<>(SB),NOSPLIT,$0`
    *   `MOVW $0xffff0fa0, R15 // R15 is hardware PC.`
    *   `TEXT ·publicationBarrier(SB),NOSPLIT,$0`
    *   `BL publicationBarrier<>(SB)`
    *   `RET`
    *   Linux ARMでは、カーネルが提供するユーザーヘルパー関数`__kuser_memory_barrier`を呼び出すことでメモリバリアを実現しています。これは、ARMのバージョン（ARMv5はSMP非対応、ARMv6はコプロセッサレジスタへの書き込み、ARMv7はDMB命令）によってメモリバリアの実装が異なる複雑さをカーネルが吸収してくれるためです。

## コアとなるコードの変更箇所

### `src/runtime/malloc.go`

```go
func mallocgc(size uintptr, typ *_type, flags uint32) unsafe.Pointer {
	// ... (既存のメモリ割り当てと初期化ロジック) ...

	// Ensure that the stores above that initialize x to
	// type-safe memory and set the heap bits occur before
	// the caller can make x observable to the garbage
	// collector. Otherwise, on weakly ordered machines,
	// the garbage collector could follow a pointer to x,
	// but see uninitialized memory or stale heap bits.
	publicationBarrier()
	// ... (後続のロジック) ...
}
```

`mallocgc`関数内で、メモリの初期化とヒープビットマップの設定が完了した後、かつ割り当てられたオブジェクトが呼び出し元に返される（GCに公開される）直前に`publicationBarrier()`が呼び出されています。

### `src/runtime/stubs.go`

```go
// publicationBarrier performs a store/store barrier (a "publication"
// or "export" barrier). Some form of synchronization is required
// between initializing an object and making that object accessible to
// another processor. Without synchronization, the initialization
// writes and the "publication" write may be reordered, allowing the
// other processor to follow the pointer and observe an uninitialized
// object. In general, higher-level synchronization should be used,
// such as locking or an atomic pointer write. publicationBarrier is
// for when those aren't an option, such as in the implementation of
// the memory manager.
//
// There's no corresponding barrier for the read side because the read
// side naturally has a data dependency order. All architectures that
// Go supports or seems likely to ever support automatically enforce
// data dependency ordering.
func publicationBarrier()
```

`publicationBarrier`関数の宣言と、その目的、機能、および読み込み側でバリアが不要な理由に関する詳細なコメントが追加されています。これは、メモリマネージャの実装など、低レベルな同期が必要な場合に用いられるストア・ストアバリアであることが明記されています。

### 各アーキテクチャのアセンブリファイル

各アーキテクチャ固有のアセンブリファイル（例: `src/runtime/asm_arm.s`, `src/runtime/atomic_arm64.s`, `src/runtime/atomic_ppc64x.s`など）に、`publicationBarrier`関数の具体的な実装が追加されています。これらは、それぞれのアーキテクチャのメモリバリア命令（`DMB ST`, `LWSYNC`など）を利用して、ストア操作の順序を強制します。x86/x64では、メモリ順序が強いため、`RET`命令（実質的なno-op）として実装されています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`mallocgc`関数における`publicationBarrier()`の戦略的な配置と、そのアーキテクチャ固有の実装です。

1.  **`mallocgc`における`publicationBarrier()`の呼び出し**:
    `mallocgc`はGoランタイムのメモリ割り当ての根幹をなす関数です。この関数内で新しいオブジェクトのメモリが確保され、ゼロ初期化され、GCが使用するヒープビットマップが更新されます。これらの初期化処理は複数のストア操作を含みます。その後、この新しいオブジェクトへのポインタが呼び出し元に返され、オブジェクトが「公開」されます。
    `publicationBarrier()`は、これらの初期化ストア操作と、オブジェクトを公開するストア操作の間に挿入されます。これにより、弱順序アーキテクチャであっても、初期化が完全に完了してからオブジェクトが公開されることが保証されます。GCが公開されたポインタを読み取ったときには、常に完全に初期化された、型安全なメモリと正確なヒープビットマップを見ることになります。

2.  **`publicationBarrier`の抽象化とアーキテクチャ固有の実装**:
    `src/runtime/stubs.go`で`publicationBarrier()`が宣言されているのは、このバリアがGoのランタイムコード内で抽象的に使用されるためです。しかし、その具体的な実装は、各CPUアーキテクチャのメモリモデルと利用可能なメモリバリア命令に依存します。
    *   **x86/x64**: 強順序モデルのため、特別なハードウェア命令は不要です。コンパイラがストア操作の順序を入れ替えないようにする「コンパイルバリア」として機能するだけで十分であり、`RET`命令で実装されます。
    *   **ARM/ARM64**: 弱順序モデルのため、`DMB ST`（Data Memory Barrier, Store）命令が使用されます。これは、それ以前のストア操作がそれ以降のストア操作よりも先に完了することを保証するハードウェア命令です。
    *   **PowerPC**: 弱順序モデルのため、`LWSYNC`命令が使用されます。これは、PowerPCアーキテクチャにおけるストア・ストアバリアとして機能します。
    *   **Linux ARM**: Linuxカーネルが提供する`__kuser_memory_barrier`ヘルパー関数を利用します。これは、異なるARMバージョン（ARMv5, ARMv6, ARMv7など）間でのメモリバリア命令の複雑さを抽象化し、適切なバリアを適用する役割を担います。

この設計により、Goランタイムは異なるアーキテクチャのメモリモデルの特性を吸収し、一貫した安全なメモリ割り当て動作を保証しています。特に、GCの正確性と信頼性を高める上で不可欠な変更です。

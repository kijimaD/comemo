# [インデックス 23132] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）において、ライトバリアを有効にする際の「Stop-the-World (STW)」ポーズを排除し、「ragged barrier」と呼ばれるより効率的な同期メカニズムに置き換えるものです。これにより、GCのレイテンシが改善され、アプリケーションの実行中断時間が短縮されます。

## 変更の背景

Goのガベージコレクタは、アプリケーションの実行と並行して動作するコンカレントGCを採用しています。しかし、GCの特定のフェーズ、特にライトバリアを有効にする際には、すべてのGoroutine（Goにおける軽量スレッド）を一時停止させる「Stop-the-World (STW)」ポーズが必要とされていました。

ライトバリアは、GCがヒープ上のオブジェクトグラフを正確に追跡するために不可欠なメカニズムです。GCがオブジェクトをマークしている最中に、アプリケーション（ミューテータ）がポインタを書き換えると、GCがオブジェクトを見落とす可能性があります。ライトバリアは、このようなポインタの書き換えを検出し、GCが正しく動作するように介入します。

従来のGo GCでは、マークフェーズの開始時にライトバリアを有効にする際、すべてのGoroutineが新しいライトバリアのロジックを認識し、適用するまでSTWポーズを導入していました。これは、GCがオブジェクトの「黒化」（到達可能としてマークすること）を開始する前に、すべてのミューテータがライトバリアを有効にしていることを保証するためでした。しかし、このSTWポーズは、アプリケーションの応答性やスループットに悪影響を与える可能性があり、特に大規模なアプリケーションや低レイテンシが求められるシステムでは、このポーズ時間の短縮が重要な課題でした。

このコミットの目的は、このSTWポーズを排除し、より粒度の細かい同期メカニズムである「ragged barrier」を導入することで、GCのレイテンシをさらに削減し、Goアプリケーションの全体的なパフォーマンスを向上させることにあります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

### 1. ガベージコレクション (GC) の基本

ガベージコレクションは、プログラムが動的に確保したメモリ領域のうち、もはや使用されていない（到達不可能になった）ものを自動的に解放するプロセスです。Goはトレース型GCを採用しており、到達可能なオブジェクトを特定し、それ以外のオブジェクトをガベージとして扱います。

### 2. GoのコンカレントGCと三色マーキング

GoのGCは、ほとんどの作業をアプリケーションの実行と並行して行う「コンカレントGC」です。これにより、STWポーズの時間を最小限に抑えています。GoのGCは「三色マーキング」アルゴリズムをベースにしています。

*   **白 (White) オブジェクト**: GCによってまだ訪問されていない、または到達不可能と見なされているオブジェクト。最終的に解放される候補。
*   **灰 (Gray) オブジェクト**: GCによって訪問されたが、その参照先（子オブジェクト）がまだ訪問されていないオブジェクト。
*   **黒 (Black) オブジェクト**: GCによって訪問され、その参照先もすべて訪問されたオブジェクト。到達可能と確定されたオブジェクト。

GCのマークフェーズでは、ルートセット（グローバル変数、スタックなど）から開始し、到達可能なオブジェクトを白から灰へ、そして灰から黒へと色を塗っていきます。

### 3. Stop-the-World (STW) ポーズ

STWは、GCの特定の段階で、すべてのGoroutineの実行を一時的に停止させることです。これにより、GCはオブジェクトグラフが変化しない静止した状態で作業を行うことができます。GoのGCはSTWポーズを最小限に抑えるように設計されていますが、完全に排除することはできません。例えば、GCの初期ルートスキャンやマーク終了フェーズでは、短いSTWポーズが必要です。このコミットが対象としているのは、ライトバリア有効化時のSTWポーズです。

### 4. ライトバリア (Write Barrier)

コンカレントGCにおいて、ミューテータ（アプリケーションのGoroutine）がオブジェクトグラフを変更する際に、GCの正確性を保証するためのメカニズムです。三色マーキングGCでは、「白から黒へのポインタの変更」を防ぐ必要があります。これは、GCがまだ訪問していない白いオブジェクト（解放候補）が、すでに黒いオブジェクト（到達可能と確定されたオブジェクト）から参照されるようになることを意味します。もしこれが許されると、白いオブジェクトはGCによって誤って解放されてしまう可能性があります。

ライトバリアは、ポインタの書き込み操作をインターセプトし、GCの不変条件（例えば、「黒いオブジェクトは白いオブジェクトを参照してはならない」）が破られないようにします。Goのライトバリアは、ポインタが書き換えられる際に、古い参照先のオブジェクトや新しい参照先のオブジェクトを「灰」にマークすることで、GCがそれらを再スキャンできるようにします。

### 5. GoのP (Processor) とM (Machine)

Goランタイムは、GoroutineのスケジューリングにG-M-Pモデルを使用します。
*   **G (Goroutine)**: Goの軽量スレッド。
*   **M (Machine)**: OSスレッド。
*   **P (Processor)**: MがGを実行するために必要な論理プロセッサ。Pは実行可能なGのキューを持ち、MはPにアタッチされてGを実行します。Pの数は通常、CPUコア数に制限されます。

GCの同期メカニズムは、これらのPの状態に依存することがよくあります。

### 6. Mutator Assists と Background Mark Workers

*   **Mutator Assists**: GCのマークフェーズ中に、ミューテータ（アプリケーションのGoroutine）がメモリを割り当てようとした際に、GCの作業を「手伝う」メカニズムです。これにより、GCの進行が遅れることを防ぎます。
*   **Background Mark Workers**: GCのマークフェーズ中に、バックグラウンドでオブジェクトのマーキングを行うGoroutineです。

これらのワーカーやアシストが「黒化」を開始する前に、ライトバリアが正しく有効になっていることが重要です。

## 技術的詳細

このコミットの核心は、ライトバリアを有効にする際のSTWポーズを、「ragged barrier」と呼ばれるより緩やかな同期メカニズムに置き換えることです。

従来のSTWアプローチでは、GCがマークフェーズに入る際に、`stoptheworld()`を呼び出してすべてのGoroutineを停止させ、その間にライトバリアを有効にし、`starttheworld()`で再開していました。これはシンプルで確実な方法ですが、アプリケーションの実行が完全に停止するため、レイテンシのスパイクを引き起こします。

「ragged barrier」は、各P（論理プロセッサ）が個別にライトバリアが有効になったことを認識し、それに応じて動作することを保証するメカニズムです。これにより、すべてのPが同時に停止する必要がなくなります。

具体的な変更点は以下の通りです。

1.  **`gcBlackenEnabled` 変数の導入**:
    `src/runtime/runtime2.go` に `gcBlackenEnabled` という新しい `uint32` 型のグローバル変数が導入されました。この変数は、ミューテータアシストやバックグラウンドマークワーカーがオブジェクトの「黒化」を許可されているかどうかを示します。`1`であれば許可、`0`であれば不許可です。この変数は、`gcphase == _GCmark` の場合にのみ `1` に設定されるべきです。

2.  **`stoptheworld()` の削除と `forEachP` の利用**:
    `src/runtime/mgc.go` の `gc` 関数内で、マークフェーズ開始時の `stoptheworld()` と `starttheworld()` の呼び出しが削除されました。
    代わりに、`atomicstore(&gcphase, _GCmark)` でGCフェーズをマークフェーズに設定した後、`forEachP(func(*p) {})` が呼び出されます。
    `forEachP` は、現在アクティブなすべてのPをイテレートするGoランタイムの内部関数です。この関数が呼び出されると、各Pは自身の状態をチェックし、GCフェーズの変更を認識します。これにより、各Pは個別にライトバリアを有効にするための準備を行います。この「各Pが個別に認識する」という点が「ragged barrier」の肝です。すべてのPが同時に停止するのではなく、それぞれのPが次のGoroutineを実行する前に、GCフェーズの変更を検出し、ライトバリアを有効にします。

3.  **黒化の開始条件の変更**:
    `gcBgMarkPrepare()` は、`forEachP` の後に呼び出されます。これにより、すべてのPがマークフェーズのライトバリアを有効にした後で、ミューテータアシストとマークワーカーが安全にオブジェクトの黒化を開始できるようになります。
    `atomicstore(&gcBlackenEnabled, 1)` が呼び出され、黒化が許可されたことを示します。

4.  **黒化条件のチェックの追加**:
    `src/runtime/malloc.go` の `mallocgc` 関数や、`src/runtime/mgc.go` の `findRunnable` 関数、`src/runtime/proc1.go` のアイドル時間マーキングのロジックなど、GCの黒化に関連する処理を行う箇所で、`gcphase == _GCmark` のチェックが `gcBlackenEnabled != 0` のチェックに置き換えられました。これにより、黒化が許可されているかどうかをより正確に判断できるようになります。

5.  **マーク終了時の `gcBlackenEnabled` のリセット**:
    `gc` 関数内のマーク終了フェーズ (`_GCmarktermination`) の開始時に、`atomicstore(&gcBlackenEnabled, 0)` が呼び出され、黒化が不許可に設定されます。

この変更により、ライトバリアの有効化に伴うSTWポーズが不要になり、GCのレイテンシが大幅に削減されます。各Pが非同期的にライトバリアを有効にするため、全体としての同期コストが低減されます。

この部分が最も重要な変更点です。
*   `stoptheworld()` と `starttheworld()` の呼び出しが削除されました。これにより、GCマークフェーズ開始時のSTWポーズがなくなります。
*   `gcphase = _GCmark` の直接代入が `atomicstore(&gcphase, _GCmark)` に変更されました。これは、`gcphase` が複数のGoroutineからアクセスされる可能性があるため、アトミックな操作で安全に更新するためです。
*   `forEachP(func(*p) {})` が導入されました。これは「ragged barrier」の核心部分です。この関数は、現在アクティブなすべてのPをイテレートします。各Pは、このイテレーション中にGCフェーズの変更を認識し、自身のコンテキストでライトバリアを有効にするための必要な設定を行います。これにより、すべてのPが同時に停止することなく、非同期的にライトバリアが有効になることが保証されます。
*   `atomicstore(&gcBlackenEnabled, 1)` が呼び出され、`gcBlackenEnabled` が `1` に設定されます。これは、すべてのPがライトバリアを有効にした後で、ミューテータアシストやバックグラウンドマークワーカーがオブジェクトの黒化を安全に開始できるようになったことを示します。

```go
func gc(mode int) {
    // ... (中略) ...
    // World is stopped.
    // Start marktermination which includes enabling the write barrier.
    atomicstore(&gcBlackenEnabled, 0) // 黒化を不許可
    gcphase = _GCmarktermination
    // ... (中略) ...
}
```
GCのマーク終了フェーズ (`_GCmarktermination`) の開始時に、`atomicstore(&gcBlackenEnabled, 0)` が呼び出され、黒化が不許可に設定されます。これは、マークフェーズが終了し、黒化の必要がなくなったことを示します。

```go
func (c *gcControllerState) findRunnable(_p_ *p) *g {
    // if gcphase != _GCmark { // 変更前
    if gcBlackenEnabled == 0 { // 変更後
        throw("gcControllerState.findRunnable: blackening not enabled")
    }
    // ...
}

func gcBgMarkWorker(p *p) {
    // ...
    if gcBlackenEnabled == 0 {
        throw("gcBgMarkWorker: blackening not enabled")
    }
    // ...
}
```
`findRunnable` (バックグラウンドマークワーカーを見つける関数) や `gcBgMarkWorker` (バックグラウンドマークワーカーの本体) の中で、GCの黒化処理を開始する前に `gcBlackenEnabled != 0` のチェックが追加されました。これにより、黒化が許可されている場合にのみこれらの処理が実行されるようになります。

### `src/runtime/malloc.go`

```go
func mallocgc(size uintptr, typ *_type, flags uint32) unsafe.Pointer {
    // ...
    if shouldtriggergc() {
        startGC(gcBackgroundMode)
    // } else if gcphase == _GCmark { // 変更前
    } else if gcBlackenEnabled != 0 { // 変更後
        // Assist garbage collector.
        // ...
    }
    // ...
}
```
メモリ割り当て時にGCアシストを行う条件が、`gcphase == _GCmark` から `gcBlackenEnabled != 0` に変更されました。これは、GCアシストがオブジェクトの黒化を行うため、黒化が許可されている場合にのみアシストを行うべきであることを示しています。

### `src/runtime/proc1.go`

```go
func schedule() {
    // ...
    // if _p_ := _g_.m.p.ptr(); gcphase == _GCmark && _p_.gcBgMarkWorker != nil { // 変更前
    if _p_ := _g_.m.p.ptr(); gcBlackenEnabled != 0 && _p_.gcBgMarkWorker != nil { // 変更後
        // ... run idle-time marking ...
    }
    // ...
    // if gp == nil && gcphase == _GCmark { // 変更前
    if gp == nil && gcBlackenEnabled != 0 { // 変更後
        gp = gcController.findRunnable(_g_.m.p.ptr())
        // ...
    }
    // ...
}
```
アイドル時間マーキングや、GCワーカーの検索を行う条件も `gcphase == _GCmark` から `gcBlackenEnabled != 0` に変更されました。これにより、これらの処理が黒化が許可されている場合にのみ実行されるようになります。

これらの変更により、GoランタイムはGCマークフェーズにおけるライトバリアの有効化を、STWポーズなしで、より効率的に行うことができるようになりました。

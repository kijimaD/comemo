# [インデックス 24394] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における並行マークフェーズの動作を改善するものです。具体的には、マークフェーズの「マーク1」と「マーク2」の間にGCワーカーが不必要に起動される問題を解決し、パフォーマンスの向上と競合状態の解消を図ります。これにより、GCの効率が向上し、特定のベンチマーク（TestTraceStress）で大幅な実行時間とメモリ使用量の削減が達成されました。また、関連する既存のバグ（#11677と#11694）の修正に向けた前提条件となる変更でもあります。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行と並行して動作する並行GCを採用しています。この並行GCには「マークフェーズ」と呼ばれる段階があり、オブジェクトが到達可能かどうかをマークします。このマークフェーズはさらに「マーク1」と「マーク2」というサブフェーズに分かれています。

このコミット以前のGoランタイムでは、並行マークフェーズの開始時に「マーク1」と「マーク2」の両方の完了シグナルがクリアされていました。スケジューラは、これらのシグナルがクリアされていることを「バックグラウンドGCワーカーを起動すべき」という合図として解釈していました。

しかし、この挙動には以下の問題がありました。

1.  **不必要なワーカーの起動**: マーク1とマーク2の間の期間では、実際にはGCワーカーが実行すべき作業がないにもかかわらず、スケジューラは新しいバックグラウンドワーカーを繰り返し起動しようとしていました。これらのワーカーはすぐに「何もすることがない」と判断して終了するため、起動と終了のオーバーヘッドが無駄に発生していました。
2.  **パフォーマンスの低下とミューテーター作業の遅延**: 不必要なワーカーの起動は、システムリソースを消費し、本来アプリケーション（ミューテーター）が実行すべき作業を遅延させていました。
3.  **競合状態**: マーク1のために起動されたワーカーが誤ってマーク2の完了をシグナルしてしまう競合状態が発生し、マーク2が時期尚早に完了してしまう可能性がありました。
4.  **#11677への干渉**: この問題は、#11677（スキャンフェーズ中のアシストの早期開始）の修正を妨げていました。スキャンフェーズ中にバックグラウンドワーカーを有効にしたくないため、マークフェーズが始まるまでワーカーの起動を遅らせる必要がありました。
5.  **#11694への影響**: #11694（長いマーク終了ポーズ）の問題にも関連しており、このコミットによってマーク終了ポーズの発生頻度が大幅に減少することが実験で示されました（1000回中64回から2回へ）。
6.  **TestTraceStressベンチマークの非効率性**: 上記の問題により、`TestTraceStress`ベンチマークの実行時間と最終ヒープサイズが不必要に大きくなっていました。

これらの問題を解決し、GCの効率と安定性を向上させることが、このコミットの背景にあります。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクション（GC）の基本的な仕組みと、特に並行マークフェーズに関する知識が必要です。

### Goのガベージコレクション (GC)

GoのGCは、主に以下の特徴を持ちます。

*   **トレース型GC**: プログラムが参照しているオブジェクトを追跡し、参照されていないオブジェクトを「ガベージ（ゴミ）」として回収します。
*   **並行GC (Concurrent GC)**: アプリケーションの実行（ミューテーター）と並行してGC処理の一部を実行します。これにより、GCによるアプリケーションの一時停止（ポーズ）時間を短縮します。
*   **三色マーク＆スイープ (Tri-color Mark and Sweep)**: オブジェクトを白、灰、黒の3色で分類し、到達可能性を判断します。
    *   **白**: まだGCによって訪問されていない、または到達不可能と判断されたオブジェクト。
    *   **灰**: GCによって訪問されたが、その参照先がまだ訪問されていないオブジェクト。
    *   **黒**: GCによって訪問され、その参照先もすべて訪問されたオブジェクト。
*   **ストップ・ザ・ワールド (Stop-The-World, STW)**: GCの特定の短いフェーズでは、アプリケーションの実行を一時的に完全に停止させる必要があります。GoのGCはSTWの時間を最小限に抑えるように設計されています。

### 並行マークフェーズ

並行マークフェーズは、GCの主要な段階の一つで、アプリケーションの実行と並行してヒープ上の到達可能なオブジェクトをマークします。このフェーズはさらにいくつかのサブフェーズに分かれますが、このコミットでは特に「マーク1」と「マーク2」が重要です。

*   **マーク1 (bgMark1)**: GCの初期マークフェーズ。ルートオブジェクト（グローバル変数、スタック上の変数など）から到達可能なオブジェクトをマークし始めます。
*   **マーク2 (bgMark2)**: マーク1に続くマークフェーズ。ヒープ全体を走査し、到達可能なすべてのオブジェクトをマークします。

### GCワーカーとアシスト

GoのGCには、GC作業を実行するための2種類のゴルーチンがあります。

*   **バックグラウンドGCワーカー (Background GC Workers)**: スケジューラによって起動され、アプリケーションの実行とは独立してGC作業（主にマーク作業）を実行するゴルーチンです。これらは通常、システムにアイドル状態のP（プロセッサ）がある場合に利用されます。
*   **ミューテーターアシスト (Mutator Assists)**: アプリケーションのゴルーチン（ミューテーター）がヒープに新しいオブジェクトを割り当てようとした際に、GC作業が遅れている場合に、そのミューテーター自身がGC作業の一部を手伝うメカニズムです。これにより、GCの進行を強制し、GCが完了するまでミューテーターがオブジェクトを割り当てられない状況を防ぎます。

### `bgMarkSignal`

`bgMarkSignal`は、GCの特定のマークフェーズ（マーク1やマーク2）の完了を調整するために使用される構造体です。これは、そのフェーズが完了したかどうかを示すシグナルとして機能し、GCコーディネーターゴルーチンが特定のフェーズの完了を待機するために使用します。

### `gcControllerState.findRunnableGCWorker`

この関数は、Goスケジューラの一部であり、実行可能なGCワーカーゴルーチンを見つけて起動する役割を担います。スケジューラは、GCワーカーを起動すべきかどうかを判断するために、様々な条件（例えば、GCシグナルの状態）をチェックします。

### 関連するGoのIssue

*   **#11677**: スキャンフェーズ中にアシストを有効にすることに関する問題。このコミットは、スキャンフェーズ中にバックグラウンドワーカーが起動しないようにすることで、この問題の修正を可能にします。
*   **#11694**: GCのマーク終了フェーズにおける長いポーズに関する問題。このコミットは、不必要なワーカーの起動を減らすことで、このポーズの発生頻度を大幅に削減します。

## 技術的詳細

このコミットの核心は、GCの並行マークフェーズにおける`bgMark1`と`bgMark2`という2つの完了シグナルの初期状態と、それらのシグナルがスケジューラの動作に与える影響を根本的に変更することにあります。

### 変更前の問題点の詳細

以前の実装では、並行マークフェーズの開始時（`gcBgMarkPrepare`関数内）に`work.bgMark1.clear()`と`work.bgMark2.clear()`が呼び出されていました。`clear()`メソッドは、シグナルの`done`フィールドを0に設定します。スケジューラは、この`done`フィールドが0である（つまり、シグナルがクリアされている）ことを検知すると、「GCワーカーが実行すべき作業がある」と判断し、バックグラウンドGCワーカーを起動しようとします。

しかし、マーク1とマーク2の間の期間では、マーク1の作業は完了しているものの、マーク2の作業はまだ開始されていないため、GCワーカーが実行すべき実質的な作業はありません。このため、スケジューラはワーカーを起動し、ワーカーはすぐに「何もすることがない」と判断して終了するという無駄なループが発生していました。これはCPUサイクルを浪費し、アプリケーションのパフォーマンスを低下させていました。

さらに、マーク1のワーカーが誤ってマーク2の完了をシグナルしてしまう競合状態も存在しました。これは、`bgMarkSignal`の`done`フィールドが0である期間が長いため、複数のワーカーが同時に`complete()`を呼び出す可能性があり、意図しないフェーズ完了を引き起こすリスクがありました。

また、マーク2の待機に入る前にすべての作業が完了してしまい、完了をシグナルするワーカーが存在しない場合に、コーディネーターが無限に待機してしまう可能性がありました。これを回避するために、コーディネーター自身が作業の有無をチェックするという競合状態をはらんだロジックが存在していました。

### 新しいアプローチ

このコミットでは、これらの問題を解決するために以下の変更を導入しました。

1.  **シグナルの初期状態の変更**:
    *   `gcBgMarkPrepare()`関数内で、`work.bgMark1.clear()`と`work.bgMark2.clear()`の代わりに、`work.bgMark1.done = 1`と`work.bgMark2.done = 1`が設定されるようになりました。
    *   これにより、並行マークフェーズの開始時には、両方のシグナルが「完了済み」（`done = 1`）の状態になります。スケジューラは`done = 1`の状態を見て、バックグラウンドGCワーカーを起動しません。
    *   ただし、ミューテーターアシストは引き続き実行可能です。これは、アシストがGCの進行を強制するために重要であり、バックグラウンドワーカーとは異なるメカニズムで動作するためです。

2.  **フェーズ移行時のシグナルクリア**:
    *   `gc()`関数内で、マーク1フェーズに入る準備ができたときに`work.bgMark1.clear()`が呼び出され、その後`work.bgMark1.wait()`で完了を待機します。
    *   同様に、マーク2フェーズに入る準備ができたときに`work.bgMark2.clear()`が呼び出され、その後`work.bgMark2.wait()`で完了を待機します。
    *   この変更により、GCワーカーは必要なマークフェーズが実際に開始されるまで起動されなくなり、不必要な起動ループが解消されます。

3.  **`findRunnableGCWorker`における完了シグナルのロジック変更**:
    *   `gcControllerState.findRunnableGCWorker()`関数に新しいロジックが追加されました。
    *   このロジックは、`work.nwait == work.nproc`（すべてのPが待機状態であり、実行中のワーカーがないことを意味する）という条件が満たされた場合に、GC作業が完了したと判断し、`bgMark1.complete()`または`bgMark2.complete()`を呼び出して完了をシグナルします。
    *   これにより、マーク2の待機に入る前にすべての作業が完了してしまい、完了をシグナルするワーカーが存在しない場合でも、スケジューラ自身が完了をシグナルできるようになります。コーディネーターは無条件にマーク完了を待機できるようになり、競合状態をはらんだ作業チェックが不要になりました。

4.  **`bgMarkSignal.complete()`の戻り値変更**:
    *   `bgMarkSignal.complete()`関数が`bool`値を返すようになりました。この`bool`値は、その呼び出しがそのフェーズの最初の完了シグナルであったかどうかを示します。
    *   これにより、`findRunnableGCWorker`内で`complete()`が呼び出された際に、それが実際に新しい完了状態を引き起こしたかどうかを判断し、必要に応じて`resetspinning()`を呼び出すことができます。

これらの変更により、GCワーカーの起動がより正確に制御され、不必要なオーバーヘッドが削減され、GCの安定性とパフォーマンスが向上しました。特に、`TestTraceStress`ベンチマークでの大幅な改善は、この変更の有効性を示しています。

## コアとなるコードの解説

### `gcBgMarkPrepare` 関数での変更

```go
// Reset background mark completion points.
-	work.bgMark1.clear()
-	work.bgMark2.clear()
+	work.bgMark1.done = 1
+	work.bgMark2.done = 1
```
この変更が、このコミットの最も根本的な部分です。並行マークフェーズの準備段階である`gcBgMarkPrepare`において、`bgMark1`と`bgMark2`という2つのシグナルの`done`フィールドが直接`1`に設定されるようになりました。
以前は`clear()`メソッドが呼び出され、`done`フィールドが`0`に設定されていました。`done = 0`は「未完了」を意味し、スケジューラはこれをGCワーカーを起動する合図と解釈していました。
`done = 1`に初期設定することで、並行マークフェーズの開始時には両方のシグナルが「完了済み」の状態にあるとスケジューラに伝えられます。これにより、マーク1とマーク2の間にGCワーカーが不必要に起動されることがなくなります。ワーカーは、実際にそのフェーズが開始され、シグナルが`clear()`されるまで起動されません。

### `gc` 関数での変更

```go
// Wait for background mark completion.
+	work.bgMark1.clear()
	work.bgMark1.wait()

// ...

	gcBlackenPromptly = true
	// Wait for this more aggressive background mark to complete.
+	work.bgMark2.clear()
	work.bgMark2.wait()
```
`gc`関数はGCのメインコーディネーターゴルーチンが実行する関数です。ここでは、各マークフェーズに入る直前に、対応するシグナル（`bgMark1`または`bgMark2`）が`clear()`されるようになりました。
`clear()`が呼び出されることで、そのフェーズが「未完了」状態になり、スケジューラがGCワーカーを起動できるようになります。その後、`wait()`が呼び出され、そのフェーズの完了が待機されます。
この変更により、GCワーカーは必要なマークフェーズが実際に開始されるまで起動されなくなり、不必要な起動ループが解消されます。また、以前存在した、作業の有無をチェックしてマーク2の待機をスキップする競合状態をはらんだロジックが削除され、コーディネーターは常にマーク完了を待機するようになりました。

### `bgMarkSignal.complete` 関数の変更

```go
func (s *bgMarkSignal) complete() bool {
	if cas(&s.done, 0, 1) {
		// ... (既存のロジック) ...
		return true
	}
	return false
}
```
`bgMarkSignal.complete()`関数は、GCフェーズの完了をシグナルするために使用されます。この変更により、関数が`bool`値を返すようになりました。この`bool`値は、`cas(&s.done, 0, 1)`（Compare And Swap）操作が成功し、`s.done`が`0`から`1`に atomically に変更された場合（つまり、その呼び出しがそのフェーズの最初の完了シグナルであった場合）に`true`を返します。それ以外の場合は`false`を返します。
この戻り値は、`findRunnableGCWorker`関数内で、完了シグナルが実際に新しい状態を引き起こしたかどうかを判断するために使用されます。

### `gcControllerState.findRunnableGCWorker` 関数での変更

```go
if work.nwait == work.nproc {
	// There are also no workers, which
	// means we've reached a completion point.
	// There may not be any workers to
	// signal it, so signal it here.
	readied := false
	if gcBlackenPromptly {
		if work.bgMark1.done == 0 {
			throw("completing mark 2, but bgMark1.done == 0")
		}
		readied = work.bgMark2.complete()
	} else {
		readied = work.bgMark1.complete()
	}
	if readied {
		// complete just called ready,
		// but we're inside the
		// scheduler. Let it know that
		// that's okay.
		resetspinning()
	}
}
return nil
```
この新しいコードブロックは、`gcControllerState.findRunnableGCWorker`関数に追加されました。この関数は、スケジューラが実行可能なGCワーカーを見つけるために呼び出されます。
`work.nwait == work.nproc`という条件は、すべてのP（プロセッサ）がGC作業を待機しており、現在アクティブなGCワーカーがいないことを意味します。この状態は、GC作業が完了した可能性が高いことを示唆します。
この条件が満たされた場合、このブロックは`bgMark1.complete()`または`bgMark2.complete()`を呼び出して、GCフェーズの完了をシグナルします。これは、すべてのGC作業が完了したにもかかわらず、それをシグナルするワーカーが残っていない場合に特に重要です。
`bgMarkSignal.complete()`が`true`を返した場合（つまり、この呼び出しが最初の完了シグナルであった場合）、`resetspinning()`が呼び出されます。これは、スケジューラがGCワーカーを不必要にスピン（ループ）して待機するのを防ぐためのものです。
このロジックにより、GCコーディネーターは常にマーク完了を待機できるようになり、以前の競合状態をはらんだ作業チェックが不要になりました。

これらの変更の組み合わせにより、GoのGCはより効率的かつ安定して動作するようになり、特に並行マークフェーズにおける不必要なオーバーヘッドと競合状態が解消されました。

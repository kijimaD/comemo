# [インデックス 24502] ファイルの概要

このコミットは、Go言語のコマンドラインツール `go` における `go get` コマンドのバグ修正に関するものです。具体的には、`go get x/...` のようにワイルドカードを使用してパッケージを取得する際に、意図せず「internal」ディレクトリにマッチしてしまい、エラーが発生する問題を解決します。

## 変更の背景

このコミットは、GoのIssue #11960で報告された問題を解決するために導入されました。この問題は、`go get` コマンドがワイルドカード (`...`) を含むインポートパス（例: `go get example.com/repo/...`）を処理する際に、Goの「internal」パッケージの規約に違反して、内部ディレクトリにマッチしてしまうというものでした。

Go言語では、`internal` という名前のディレクトリとそのサブディレクトリ内のパッケージは、その親ディレクトリのツリー内にあるパッケージからのみインポートできるという特別なルールがあります。このルールは、ライブラリの内部実装を外部から隠蔽し、APIの安定性を保つために非常に重要です。

しかし、`go get x/...` が `internal` ディレクトリにマッチしてしまうと、`go get` はこれらの内部パッケージを外部からアクセス可能なものとして扱おうとし、結果としてビルドエラーや予期せぬ動作を引き起こしていました。このコミットは、`go get` が `internal` ディレクトリを適切に無視するように修正し、Goのパッケージ規約を遵守させることを目的としています。

## 前提知識の解説

### `go get` コマンド

`go get` は、Go言語のパッケージやモジュールをリモートリポジトリからダウンロードし、ローカルのGOPATHまたはGoモジュールキャッシュにインストールするためのコマンドです。依存関係の解決とダウンロードを自動的に行い、必要に応じてビルドも実行します。

### Goモジュールのインポートパスとワイルドカード (`...`)

Goのパッケージは、通常、`github.com/user/repo/package` のようなインポートパスで識別されます。ワイルドカード `...` は、特定のパス以下のすべてのサブパッケージを意味します。例えば、`github.com/user/repo/...` は、`github.com/user/repo` およびそのすべてのサブディレクトリ内のパッケージを指します。これは、複数の関連パッケージを一括で取得したり、テストを実行したりする際に便利です。

### Goにおける「internal」パッケージ

Go 1.4から導入された「internal」パッケージのルールは、パッケージの可視性を制御するためのものです。`internal` という名前のディレクトリの下にあるパッケージは、その `internal` ディレクトリの親ディレクトリ（またはその兄弟ディレクトリ）にあるパッケージからのみインポートできます。それ以外の外部のパッケージからはインポートできません。これにより、ライブラリ開発者は、外部に公開したくない実装の詳細を `internal` ディレクトリに配置し、意図しない依存関係の発生を防ぐことができます。

例:
```
myproject/
├── src/
│   ├── mylib/
│   │   ├── internal/
│   │   │   └── helper/  // mylib/internal/helper は mylib/ のパッケージからのみインポート可能
│   │   └── mylib.go
│   └── main/
│       └── main.go
```
この場合、`myproject/src/main` から `myproject/src/mylib/internal/helper` を直接インポートすることはできません。

### `importStack` の役割

`importStack` は、Goのパッケージローダーがパッケージの依存関係を追跡するために使用するデータ構造です。パッケージのインポートパスをスタックに積むことで、循環インポートの検出や、現在処理中のパッケージのコンテキストを維持します。`go get` のようなツールがパッケージを解決・ダウンロードする際には、このスタックが正しく管理されていることが重要です。

## 技術的詳細

このコミットの核心は、`go get` コマンドの内部ロジック、特に `src/cmd/go/get.go` 内の `download` 関数における `importStack` の不適切な操作を修正することにあります。

以前のコードでは、`download` 関数内でパッケージをロードする前に `stk.push(arg)` を呼び出し、ロード後に `stk.pop()` を呼び出すという処理が行われていました。しかし、`download` 関数が内部で呼び出す `load` 関数（これはさらに `loadPackage` または `loadImport` を呼び出す）自体が、既に引数 `arg` を `importStack` にプッシュするロジックを含んでいました。

この二重のプッシュ操作により、`importStack` は同じ引数を二重に持つことになり、スタックの状態が不正になっていました。特に、`go get x/...` のようなワイルドカードインポートパスが `internal` ディレクトリにマッチした場合、この不正なスタック状態が原因で、`internal` パッケージのインポートルールが正しく適用されず、エラーが発生していました。

コミットでは、`download` 関数内の冗長な `stk.push(arg)` と `stk.pop()` の呼び出しを削除しました。これにより、`importStack` は `load` 関数によってのみ適切に管理されるようになり、スタックの整合性が保たれます。結果として、`go get` は `internal` ディレクトリを正しく処理し、Goのパッケージ可視性ルールに準拠するようになりました。

また、この修正を検証するために、`src/cmd/go/go_test.go` に新しいテストケース `TestGoGetInternalWildcard` が追加されました。このテストは、`github.com/rsc/go-get-issue-11960/...` のようなワイルドカードパスを使用して `go get` を実行し、`internal` パッケージに関連するエラーが発生しないことを確認します。

## コアとなるコードの解説

### `src/cmd/go/get.go` の変更

`download` 関数内の `for _, arg := range args` ループ内で、以前は `stk.push(arg)` と `stk.pop()` が `load(arg, mode)` の呼び出しを挟む形で存在していました。

-   **削除された行**:
    ```go
    			stk.push(arg)
    			// ...
    			stk.pop()
    ```
-   **追加されたコメント**:
    ```go
    			// Note: load calls loadPackage or loadImport,
    			// which push arg onto stk already.
    			// Do not push here too, or else stk will say arg imports arg.
    ```

この変更により、`importStack` への `arg` のプッシュは `load` 関数内部でのみ行われるようになり、二重プッシュが解消されました。これにより、`importStack` の状態が常に正確に保たれ、`internal` パッケージの可視性ルールが `go get` コマンドによって正しく評価されるようになりました。結果として、`go get x/...` が `internal` ディレクトリにマッチしても、不正なインポートエラーが発生しなくなります。

### `src/cmd/go/go_test.go` の変更

-   `TestGoGetWorksWithVanityWildcards` テスト関数が `TestGoGetCustomDomainWildcard` にリネームされました。これは機能的な変更ではなく、テストの意図をより明確にするための命名規則の改善です。

-   **新しいテストケース `TestGoGetInternalWildcard` の追加**:
    ```go
    func TestGoGetInternalWildcard(t *testing.T) {
    	testenv.MustHaveExternalNetwork(t)

    	tg := testgo(t)
    	defer tg.cleanup()
    	tg.makeTempdir()
    	tg.setenv("GOPATH", tg.path("."))
    	// used to fail with errors about internal packages
    	tg.run("get", "github.com/rsc/go-get-issue-11960/...")
    }
    ```
    この新しいテストは、`go get github.com/rsc/go-get-issue-11960/...` を実行することで、`internal` パッケージを含むリポジトリに対してワイルドカード `go get` が正しく動作することを確認します。コメントにあるように、このテストは以前は `internal` パッケージに関するエラーで失敗していたケースを再現し、修正が正しく適用されたことを検証します。`testenv.MustHaveExternalNetwork(t)` は、このテストが外部ネットワークアクセスを必要とすることを示しています。

# [インデックス 23464] ファイルの概要

このコミットは、Goコンパイラ（`gc`）における構文エラーメッセージの生成方法を改善するものです。具体的には、`yacc`文法ファイル（`go.y`）にカスタムエラーメッセージを直接定義できる新しい構文 `%error { tokens } : message` を導入し、これまで別個のツールであった `yaccerrors.go` と `go.errors` ファイルを `cmd/yacc` ツールと `go.y` 文法ファイルに統合しました。これにより、より具体的で分かりやすいエラーメッセージを生成できるようになり、コンパイラの保守性も向上しています。

## 変更の背景

Goコンパイラは、コードの構文解析に`yacc`（またはそのGo実装である`goyacc`）を使用しています。従来の`yacc`ベースのパーサーでは、構文エラーが発生した場合に「syntax error」のような一般的なメッセージしか表示されないことが多く、開発者にとって問題の特定が困難でした。

このコミットの背景には、より具体的でユーザーフレンドリーなエラーメッセージを提供したいという要望がありました。以前は、`yaccerrors.go`という補助ツールと`go.errors`というファイルを使って、特定の構文パターンに対応するカスタムエラーメッセージを生成していましたが、これはツールチェーンを複雑にし、エラーメッセージの定義が文法定義から分離されているという問題がありました。

この変更は、内部的な課題トラッカーである `#9968` に対応するもので、`yacc`の文法定義ファイル（`.y`ファイル）内で直接カスタムエラーメッセージを指定できる新しいメカニズムを導入することで、これらの問題を解決しようとしています。

## 前提知識の解説

### Yacc (Yet Another Compiler Compiler) / Goyacc

`Yacc`は、コンパイラのパーサー（構文解析器）を生成するためのツールです。文法規則を記述したファイル（通常`.y`拡張子）を入力として受け取り、その文法に従って入力テキストを解析するC言語（またはGo言語の場合は`goyacc`によってGo言語）のコードを生成します。

*   **文法規則**: `yacc`ファイルは、BNF（バッカス・ナウア記法）に似た形式で文法規則を定義します。例えば、「式は項の後に演算子と項が続く」といった形です。
*   **トークン**: 字句解析器（lexer）によって生成される最小単位のシンボルです。`yacc`はこれらのトークンを組み合わせて文法規則に合致するかを判断します。
*   **パーサー**: トークンのストリームを読み込み、文法規則に従って構文木を構築します。構文エラーが発生した場合、パーサーは通常、エラーを報告し、可能であればエラー回復を試みます。

### 構文エラーとエラー回復

パーサーが入力ストリームで予期しないトークンに遭遇すると、構文エラーが発生します。伝統的な`yacc`では、`%error`トークンを文法規則に挿入することで、エラー発生時の挙動をカスタマイズできます。例えば、`statement: expression ';' | error ';' { /* エラー処理 */ };` のように記述することで、`expression`の後にセミコロンがない場合に`error`規則が適用され、特定のエラー処理を実行できます。

しかし、`yacc`のデフォルトのエラーメッセージはしばしば「syntax error」としか表示されず、どの部分で何が問題なのかを具体的に示しませんでした。

## 技術的詳細

このコミットの主要な技術的変更点は、`cmd/yacc`ツール自体に、`go.y`ファイル内でカスタムエラーメッセージを直接定義できる新しい構文 `%error { tokens } : message` を追加したことです。

### 新しい `%error` 構文

この新しい構文は、特定の構文パターン（`{ tokens }`で指定）が期待される場所でエラーが発生した場合に、指定された`message`を出力するように`yacc`パーサーに指示します。

例:
```yacc
%error loadsys package LIMPORT '(' LLITERAL import_package import_there ',':
	"unexpected comma during import block"
```
この行は、`loadsys package LIMPORT '(' LLITERAL import_package import_there` の後に `,` が来た場合に、「unexpected comma during import block」というカスタムエラーメッセージを出力するように定義しています。

### 統合と簡素化

以前は、`go.errors`ファイルにエラーパターンとメッセージのペアを記述し、`yaccerrors.go`ツールがこれを処理して、`y.go`ファイルに埋め込む`yymsg`というデータ構造を生成していました。

このコミットでは、以下の変更が行われました。
1.  `go.errors`ファイルが削除されました。カスタムエラーメッセージは直接 `go.y` に記述されるようになりました。
2.  `yaccerrors.go`ツールが削除されました。`cmd/yacc`が新しい`%error`構文を直接解釈し、必要なコードを生成するようになりました。
3.  `src/cmd/internal/gc/y.go`ファイルに、`yyErrorMessages`という新しいデータ構造が導入されました。これは、`go.y`で定義されたカスタムエラーメッセージを格納し、パーサーがエラー時に参照します。
4.  `src/cmd/internal/gc/subr.go`から、古い`yymsg`を参照するエラー処理ロジックが削除されました。

この統合により、エラーメッセージの定義が文法定義と密接に結びつき、コンパイラのビルドプロセスが簡素化され、エラーメッセージの管理が容易になりました。

## コアとなるコードの解説

この変更の核心は、`go.y`ファイルと`y.go`ファイルの連携にあります。

1.  **`go.y`でのエラーメッセージ定義**:
    `go.y`ファイルには、以下のような形式でカスタムエラーメッセージが直接記述されます。
    ```yacc
    %error loadsys package LIMPORT '(' LLITERAL import_package import_there ',':
    	"unexpected comma during import block"
    ```
    この行は、`cmd/yacc`ツールによって解析されます。`cmd/yacc`は、この規則がどのパーサーステートとどの予期しないトークン（`','`）に対応するかを特定し、それに関連付けられたメッセージを抽出します。

2.  **`cmd/yacc`によるコード生成**:
    `cmd/yacc`は、`go.y`を処理する際に、これらの`%error`定義を基に`src/cmd/internal/gc/y.go`内に`yyErrorMessages`というGoの構造体スライスを生成します。
    ```go
    var yyErrorMessages = [...]struct {
    	state int
    	token int
    	msg   string
    }{
    	{332, 76, "unexpected comma during import block"}, // 例
    	// ... 他のエラーメッセージ ...
    }
    ```
    ここで、`state`はエラーが発生したパーサーの状態番号、`token`は予期されなかったトークンの内部表現、`msg`はカスタムエラーメッセージです。

3.  **`yyErrorMessage`によるエラー報告**:
    `src/cmd/internal/gc/y.go`内の`yyErrorMessage`関数は、パーサーが構文エラーを検出した際に呼び出されます。この関数は、現在のパーサーステートと予期しないトークンを受け取り、`yyErrorMessages`スライスを検索します。
    ```go
    func yyErrorMessage(state, lookAhead int) string {
    	// ...
    	for _, e := range yyErrorMessages {
    		if e.state == state && e.token == lookAhead {
    			return "syntax error: " + e.msg
    		}
    	}
    	// ...
    	return "syntax error" // カスタムメッセージが見つからない場合
    }
    ```
    一致するエントリが見つかれば、そのカスタムメッセージが返され、そうでなければ一般的な「syntax error」メッセージが返されます。

このメカニズムにより、Goコンパイラは、より詳細で文脈に即した構文エラーメッセージを開発者に提供できるようになり、デバッグ体験が大幅に向上しました。

# [インデックス 26392] ファイルの概要

このコミットは、Go言語の`net/http`パッケージにおけるHTTP/2トランスポートが、リクエストの`Content-Length`ヘッダーを正しく送信するように改善するものです。特に、`Content-Length`が明示的に設定されていない場合やゼロとされている場合に、リクエストボディの実際の長さを適切に検出し、ヘッダーとして付与するロジックが追加されました。これにより、HTTP/2クライアントが送信するリクエストの互換性と堅牢性が向上します。

## 変更の背景

HTTP/1.1では、リクエストボディの長さを`Content-Length`ヘッダーで明示的に示すことが一般的であり、サーバーはこれを利用してリクエストボディの終端を判断します。HTTP/2では、ストリームベースのプロトコルであるため、理論的には`Content-Length`ヘッダーがなくてもボディの終端を判断できます（ストリームの終了によって示される）。しかし、多くのHTTPサーバーやプロキシは、後方互換性や処理の簡素化のために`Content-Length`ヘッダーの存在を期待しています。

Goの`net/http`パッケージのHTTP/2トランスポートは、以前は`http.Request.ContentLength`フィールドが明示的に設定されていない場合、またはゼロとされている場合に、実際のボディ長を適切に`Content-Length`ヘッダーとして送信しない可能性がありました。これにより、`Content-Length`ヘッダーを必須とするサーバーとの間で互換性の問題が発生することがありました。

このコミットは、`x/net/http2`ライブラリの更新を取り込むことで、この問題を解決し、HTTP/2リクエストにおいても`Content-Length`ヘッダーがより堅牢に扱われるようにすることを目的としています。特に、`http.Request.Body`が`io.Reader`インターフェースとして提供され、`ContentLength`が不明な場合に、ボディの内容を先読みして長さを判断するメカニズムが導入されました。

## 前提知識の解説

### HTTP/1.1とHTTP/2の比較

*   **HTTP/1.1**: リクエストごとにTCPコネクションを確立し、ヘッダーはテキスト形式で送信されます。`Content-Length`ヘッダーは、リクエストボディのバイト数を明示的に示し、サーバーがボディの終端を判断するために重要です。
*   **HTTP/2**: 単一のTCPコネクション上で複数のリクエストとレスポンスを多重化（ストリーム）して送受信します。ヘッダーはバイナリ形式で圧縮されて送信され、効率が向上しています。ボディの終端は、ストリームの終了を示すフラグ（`END_STREAM`）によっても判断できますが、`Content-Length`ヘッダーも引き続き使用されることがあります。

### Goの`net/http`パッケージ

Goの標準ライブラリである`net/http`は、HTTPクライアントとサーバーを構築するための機能を提供します。
*   **`http.Request`**: クライアントからサーバーへ、またはサーバーからクライアントへ送信されるHTTPリクエストを表す構造体です。`Body`フィールドは`io.ReadCloser`インターフェースであり、リクエストボディのデータを読み出すために使用されます。`ContentLength`フィールドは、リクエストボディのバイト数を示します。
*   **`http.Client`**: HTTPリクエストを送信し、HTTPレスポンスを受信するためのクライアントです。内部的に`http.Transport`を使用して実際のネットワーク通信を行います。
*   **`http.Transport`**: `http.Client`がネットワーク通信を行うためのインターフェースを実装します。HTTP/1.1とHTTP/2の両方をサポートし、コネクションの管理、リクエストの送信、レスポンスの受信などを担当します。

### `Content-Length`ヘッダー

HTTPメッセージのエンティティボディのオクテットサイズをバイト単位で示すヘッダーです。このヘッダーが存在することで、受信側はボディの読み込みをいつ停止すべきかを知ることができます。特に、ストリーミングではないリクエストにおいて、サーバーがリクエストボディを完全に受信したことを確認するために重要です。

### `io.Reader`と`io.ReadCloser`インターフェース

Goにおけるデータのストリーム処理の基本となるインターフェースです。
*   **`io.Reader`**: `Read(p []byte) (n int, err error)`メソッドを持ち、データをバイトスライス`p`に読み込みます。
*   **`io.ReadCloser`**: `io.Reader`に加えて`Close() error`メソッドを持ち、リソースの解放を可能にします。`http.Request.Body`はこのインターフェースを実装しています。

### `x/net/http2`

`golang.org/x/net/http2`は、Goの標準ライブラリにHTTP/2のサポートが統合される前に、実験的かつ先行して開発されていたHTTP/2実装です。標準ライブラリの`net/http`パッケージは、この`x/net/http2`のコードベースを基にHTTP/2サポートを実装しており、定期的に`x/net/http2`の更新を取り込んでいます。

## 技術的詳細

このコミットの主要な変更は、`src/net/http/h2_bundle.go`内の`http2ClientConn.RoundTrip`メソッドに集中しています。このメソッドは、HTTP/2クライアントコネクションを介してHTTPリクエストを送信する際の中心的なロジックを含んでいます。

### `http2ClientConn.RoundTrip`の変更点

1.  **`Content-Length`の決定ロジックの強化**:
    *   元のリクエストの`req.Body`と`req.ContentLength`が取得されます。
    *   `req.Body != nil`かつ`contentLen == 0`の場合（つまり、ボディは存在するが`Content-Length`がゼロとされているか、未設定の場合）、実際のボディ長を判断するための特殊な処理が導入されます。
    *   `io.ReadFull(body, buf[:])`を使用して、ボディの先頭1バイトを読み込もうとします。
        *   もしエラーが発生し、それが`io.EOF`でなければ、`contentLen`は`-1`（不明）とされ、ボディはエラーを返す`http2errorReader`でラップされます。
        *   もし1バイト読み込めた場合（`n == 1`）、ボディは空ではないため、`contentLen`は`-1`（不明）とされ、読み込んだ1バイトを元のボディの先頭に戻すために`io.MultiReader`が使用されます。これにより、後続のボディ読み込みが正しく行われます。
        *   もし1バイトも読み込めず、`io.EOF`が返された場合（`n == 0`）、ボディは実際に空であると判断され、`body`は`nil`に設定されます。この場合、`contentLen`は`0`のままです。
    *   このロジックにより、`Content-Length`が明示的に設定されていない場合でも、ボディが実際に空であるか、または内容を持つかを正確に判断し、適切な`Content-Length`を送信できるようになります。

2.  **`hasBody`変数の更新**:
    *   以前は`req.Body != nil`で判断されていた`hasBody`が、上記のロジックで更新された`body`変数に基づいて`body != nil`で判断されるようになりました。これにより、ボディが実際に空であると判断された場合に、不必要にボディ送信処理が実行されるのを防ぎます。

3.  **`encodeHeaders`への`contentLen`の伝播**:
    *   ヘッダーをエンコードする`cc.encodeHeaders`メソッドに、新たに決定された`contentLen`が引数として渡されるようになりました。

4.  **`writeRequestBody`の引数変更**:
    *   リクエストボディを書き込む`cs.writeRequestBody`メソッドのシグネチャが変更され、`body io.Reader`と`bodyCloser io.Closer`の2つの引数を受け取るようになりました。これは、`RoundTrip`内で`io.MultiReader`が作成された場合でも、元の`io.ReadCloser`を適切にクローズできるようにするためです。

### `encodeHeaders`関数の変更点

*   `cc.encodeHeaders`メソッドもシグネチャが変更され、`contentLength int64`引数を受け取るようになりました。
*   ヘッダーのエンコード処理中に、既存の`req.Header`から`"content-length"`ヘッダーを明示的にスキップするロジックが追加されました。これは、新しいロジックで計算された`Content-Length`を優先し、重複や不正確なヘッダーの送信を防ぐためです。
*   `contentLength >= 0`の場合にのみ、`"content-length"`ヘッダーが`strconv.FormatInt(contentLength, 10)`でフォーマットされ、エンコードされるヘッダーリストに追加されます。

### `http2errorReader`構造体の追加

*   `http2errorReader`という新しい型が追加されました。これは、`Read`メソッドが常に初期化時に与えられたエラーを返す`io.Reader`の実装です。これにより、ボディの読み込み中に発生したエラーを後続の処理に適切に伝播させることができます。

### テストケースの追加 (`src/net/http/clientserver_test.go`)

*   `TestH12_RequestContentLength_Known_NonZero`、`TestH12_RequestContentLength_Known_Zero`、`TestH12_RequestContentLength_Unknown`という新しいテスト関数が追加されました。
*   これらのテストは、`h12requestContentLength`というヘルパー関数を利用して、HTTP/1.1とHTTP/2の両方で、既知の非ゼロ長、既知のゼロ長、および不明な長さのリクエストボディに対する`Content-Length`ヘッダーの処理が正しく行われることを検証します。
*   サーバー側で受信した`Content-Length`ヘッダーの値を`Got-Length`レスポンスヘッダーに含め、クライアント側で期待値と比較することで検証を行います。

## コアとなるコードの解説

このコミットの核心は、`http2ClientConn.RoundTrip`メソッドにおける`Content-Length`の動的な検出と、それをHTTP/2ヘッダーとして適切に送信するメカニズムにあります。

`RoundTrip`メソッド内で、まずリクエストの`req.Body`と`req.ContentLength`が確認されます。もし`req.Body`が存在し、かつ`req.ContentLength`が`0`である場合、これはボディが本当に空なのか、それとも単に`ContentLength`が設定されていないだけなのかを判断する必要があります。

この判断のために、`io.ReadFull(body, buf[:])`が使用されます。これは、`body`から1バイトだけを読み込もうと試みる「先読み」操作です。
1.  **エラーが発生し、それが`io.EOF`ではない場合**: ボディの読み込み中に予期せぬエラーが発生したことを意味します。この場合、`contentLen`は`-1`（不明）とマークされ、元のボディは`http2errorReader`でラップされます。これにより、後続のボディ読み込み試行時にこのエラーが適切に伝播されます。
2.  **1バイト読み込めた場合**: ボディが空ではないことを意味します。この場合も`contentLen`は`-1`（不明）とマークされますが、先読みした1バイトを失わないように、`io.MultiReader`が使用されます。`io.MultiReader`は、先読みした1バイトを含む`bytes.NewReader(buf[:])`と元の`body`を結合し、新しい`body`として設定します。これにより、後続のボディ読み込みは先頭から正しく行われます。
3.  **1バイトも読み込めず、`io.EOF`が返された場合**: ボディが実際に空であることを意味します。この場合、`body`は`nil`に設定され、`contentLen`は`0`のままとなります。

このロジックにより、`Content-Length`が不明な場合でも、GoのHTTP/2トランスポートはリクエストボディの実際の状態を正確に把握し、適切な`Content-Length`ヘッダーを生成できるようになります。

次に、`encodeHeaders`メソッドでは、この決定された`contentLen`が引数として渡されます。ここで重要なのは、元の`req.Header`に`"content-length"`が存在しても、それを無視するロジックが追加されたことです。これは、`RoundTrip`で計算された`contentLen`が最も正確な情報であるため、それを優先し、重複や矛盾するヘッダーの送信を防ぐためです。最終的に、`contentLength >= 0`の場合にのみ、計算された`Content-Length`がHTTP/2ヘッダーとして追加されます。

`writeRequestBody`メソッドのシグネチャ変更は、`RoundTrip`で`io.MultiReader`が作成されたシナリオに対応するためのものです。`io.MultiReader`は元の`io.ReadCloser`をラップしているため、`io.MultiReader`をクローズしても元のリソースが適切に解放されない可能性があります。そこで、`body io.Reader`（実際に読み込むリーダー）と`bodyCloser io.Closer`（クローズすべき元のリーダー）を分離して渡すことで、`defer bodyCloser.Close()`によって確実に元のリソースが解放されるようにしています。

これらの変更により、GoのHTTP/2クライアントは、`Content-Length`ヘッダーの有無や値に関わらず、より堅牢かつ互換性の高いリクエストを送信できるようになりました。

# [インデックス 21822] ファイルの概要

このコミットは、Go言語のテスト実行メカニズムにおけるバグ修正と、それに伴うテストファイルの記述規則の明確化に関するものです。具体的には、Goのテストランナーがソースファイル内のビルド制約（build constraints）をどのように解釈するか、そのロジックを修正しています。

## 変更の背景

このコミットの背景には、Go言語のテストスイートにおける特定のテスト（`misc/cgo/{stdio,life}`など）が、`run.bash`スクリプトから実行された際に**サイレントにスキップされる**という問題がありました。

Goのテストシステムでは、テストファイルの冒頭に特別なコメント形式で「テストアクション」（例: `// run`）や「ビルド制約」（例: `// +build !nacl`）を記述することで、そのテストの実行方法や対象環境を制御します。

問題の根本原因は、テストランナーである`run.go`が、テストアクションとビルド制約の解釈において一貫性のないロジックを持っていたことにありました。`run.go`はテストアクションについてはファイルの最初の空行までしかチェックしないのに対し、ビルド制約についてはファイル全体をスキャンしていました。この不整合により、ビルド制約がファイルの後半に記述されている場合、テストランナーがそれを正しく認識できず、結果としてテストが意図せずスキップされてしまっていたのです。

このコミットは、この不整合を解消し、ビルド制約もテストアクションと同様にファイルの最初の空行まででチェックするように変更することで、テストのサイレントスキップを防ぎ、テストファイルの記述規則を明確化することを目的としています。

## 前提知識の解説

### Go言語のビルド制約 (Build Constraints)

Go言語には「ビルド制約」または「ビルドタグ (build tags)」と呼ばれる仕組みがあります。これは、特定のファイルが特定の環境（OS、アーキテクチャ、Goバージョンなど）でのみコンパイルされるように制御するためのディレクティブです。

ビルド制約は、Goソースファイルの先頭付近に`// +build tag`または`//go:build tag`（Go 1.17以降）という形式のコメントとして記述されます。複数のタグをスペースで区切って記述したり、カンマで区切ってOR条件を表したり、`!`を付けてNOT条件を表したりできます。

例:
*   `// +build linux darwin`：LinuxまたはmacOSでのみコンパイル
*   `// +build !windows`：Windows以外でのみコンパイル
*   `// +build debug`：`debug`タグが指定された場合のみコンパイル（`go build -tags debug`）

これらの制約は、Goコンパイラやツールチェーンがソースファイルを処理する際に参照され、条件に合致しないファイルはコンパイル対象から除外されます。

### Go言語のテストアクション (Test Actions)

Goのテストフレームワークには、`go test`コマンドで実行される通常のテスト関数（`TestXxx`）とは別に、Goリポジトリ内の`test`ディレクトリにあるファイル群で使われる独自のテスト実行メカニズムがあります。これらのファイルは、Go言語の機能やランタイムの挙動を検証するためのもので、ファイルの冒頭に特別なコメント形式で「テストアクション」を記述します。

例:
*   `// run`：このファイルをGoプログラムとして実行し、エラーがないことを確認する。
*   `// errorcheck`：このファイルをコンパイルし、特定のコンパイルエラーが発生することを確認する。
*   `// compile`：このファイルをコンパイルし、エラーがないことを確認する。

これらのテストアクションは、Goリポジトリのテストランナー（`test/run.go`）によって解釈され、テストの実行フローを制御します。

### `test/run.go`の役割

`test/run.go`は、Go言語の標準ライブラリやランタイムのテストを実行するためのカスタムテストランナーです。これは、一般的な`go test`コマンドとは異なり、Goリポジトリ内の特定のテストファイル群（主に`test`ディレクトリ以下）を処理するために設計されています。

`run.go`は、各テストファイルの冒頭を読み込み、そこに記述されたテストアクション（`// run`など）やビルド制約（`// +build`）を解析します。そして、それらの情報に基づいて、テストのコンパイル、実行、結果の検証を行います。

### 空行の重要性

Goのソースファイルにおける特別なコメント（ビルド制約やテストアクション）は、ファイルの冒頭、`package`宣言の前に記述されることが慣例です。そして、これらのコメントブロックと`package`宣言の間には、通常、空行が挿入されます。この空行は、Goツールが特別なコメントの範囲を識別するための区切りとして機能することがあります。

このコミットでは、`run.go`がビルド制約を解析する際に、この「最初の空行」を区切りとして認識するように変更することで、テストアクションの解析ロジックとの一貫性を保っています。

## 技術的詳細

このコミットの技術的な核心は、`test/run.go`内の`shouldTest`関数と、その呼び出し箇所におけるソースコードの処理範囲の変更にあります。

### `shouldTest`関数

`shouldTest`関数は、与えられたソースコード文字列と現在のOS/アーキテクチャに基づいて、そのファイルがテスト対象となるべきかどうかを判断する役割を担っています。この関数は、ソースコード内の`// +build`コメントを解析し、ビルド制約が満たされているかをチェックします。

変更前の`shouldTest`関数は、引数として渡された`src`文字列全体を対象にビルド制約を検索していました。これは、`src`がファイル全体のコンテンツである場合、ファイルのどこにビルド制約が書かれていてもそれを認識してしまうことを意味します。

### 変更点

1.  **`test/run.go`の変更**:
    *   変更前: `shouldTest`関数内で、`strings.Index(src, "\npackage")`を使って`package`宣言の位置を見つけ、その手前までを`src`として処理するロジックがありました。これは、ビルド制約が`package`宣言より前に来るべきという意図を反映したものですが、空行の扱いに問題がありました。
        ```go
        // shouldTest looks for build tags in a source file and returns
        // whether the file should be used according to the tags.
        func shouldTest(src string, goos, goarch string) (ok bool, whyNot string) {
        -	if idx := strings.Index(src, "\npackage"); idx >= 0 {
        -		src = src[:idx]
        -	}
        	for _, line := range strings.Split(src, "\n") {
        		// ... (build tag parsing logic) ...
        	}
        }
        ```
        このコミットでは、この`package`宣言までの切り詰めロジックが削除されています。
    *   変更後: `shouldTest`関数を呼び出す側（`test.run()`メソッド内）で、ソースコードの切り詰めが行われるようになりました。具体的には、テストファイルの冒頭にある「テストアクション」や「ビルド制約」が記述されているブロックの終端（最初の空行、または`package`宣言の直前）までを`shouldTest`に渡すように変更されました。
        ```go
        func (t *test) run() {
        	// ...
        	// pos は最初の空行、または package 宣言の直前の位置を示す
        	// ...
        -	if ok, why := shouldTest(t.src, goos, goarch); !ok {
        +	// Check for build constraints only upto the first blank line.
        +	if ok, why := shouldTest(t.src[:pos], goos, goarch); !ok {
        		t.action = "skip"
        		// ...
        	}
        }
        ```
        ここで`t.src[:pos]`は、テストファイルのコンテンツのうち、最初の空行までの部分を指します。これにより、`shouldTest`関数は、ビルド制約が記述されるべき「ヘッダー」部分のみを対象にチェックするようになります。

2.  **テストファイルの変更**:
    *   `test/gc2.go`と`test/nosplit.go`の2つのテストファイルで、`// run`と`// +build !nacl`の行順が入れ替えられました。
        変更前:
        ```go
        // run

        // +build !nacl
        ```
        変更後:
        ```go
        // +build !nacl
        // run
        ```
        この変更は、ビルド制約とテストアクションが同じブロック（最初の空行まで）に存在するという新しい規則に準拠させるためのものです。これにより、`run.go`が両方を正しく認識できるようになります。

### 影響

この変更により、`run.go`はビルド制約を解析する際に、テストアクションと同様にファイルの冒頭の「ヘッダーブロック」のみを考慮するようになります。これにより、ビルド制約がファイルの後半に誤って記述された場合でも、それが無視されることで、意図しないテストのスキップが防止されます。同時に、テストファイルの記述者に対して、ビルド制約とテストアクションはファイルの冒頭の同じブロック内に記述する必要があるという明確な規則が課せられることになります。

## コアとなるコードの解説

### `test/run.go`の変更点

1.  **`shouldTest`関数内の`package`宣言による切り詰めロジックの削除**:
    変更前の`shouldTest`関数には、`src`文字列から`package`宣言より前の部分を抽出するロジックがありました。これは、ビルド制約がファイルの冒頭に記述されるべきという意図を反映したものですが、このロジック自体が空行の扱いに関して不完全であったり、呼び出し元での制御と重複したりする可能性がありました。このコミットでは、この内部的な切り詰めロジックを削除し、`shouldTest`関数は渡された`src`文字列全体を素直に処理するように変更されました。これにより、`shouldTest`の役割が「与えられた文字列内のビルド制約をチェックする」という単一の責任に集中し、よりクリーンな設計になります。

2.  **`test.run()`メソッドにおける`shouldTest`の呼び出し箇所の変更**:
    これがこのコミットの最も重要な変更点です。
    *   変更前は、`shouldTest(t.src, goos, goarch)`のように、テストファイル全体のコンテンツ（`t.src`）を`shouldTest`に渡していました。
    *   変更後は、`shouldTest(t.src[:pos], goos, goarch)`のように、`t.src`の先頭から`pos`で示される位置までの部分文字列を渡すように変更されました。
        ここで`pos`は、`test.run()`メソッド内で既に計算されている、テストファイルの冒頭にある「テストアクション」や「ビルド制約」が記述されているブロックの終端（具体的には、最初の空行、または`package`宣言の直前）を指します。
        この変更により、`shouldTest`関数は、ビルド制約が記述されるべき「ヘッダー」部分のみを対象にチェックするようになります。これは、テストアクションがチェックされる範囲と完全に一致するため、ビルド制約とテストアクションの解析ロジックに一貫性がもたらされます。

    コメント`// Check for build constraints only upto the first blank line.`が追加され、この変更の意図が明確に示されています。

### テストファイルの変更点 (`test/gc2.go`, `test/nosplit.go`)

これらのファイルでは、`// run`と`// +build !nacl`のコメントの順序が入れ替えられました。
変更前:
```go
// run

// +build !nacl
```
変更後:
```go
// +build !nacl
// run
```
この変更は、`run.go`の新しい動作に合わせたものです。ビルド制約とテストアクションは、ファイルの冒頭の同じコメントブロック内に記述されるべきであり、そのブロックは最初の空行で区切られます。変更前の記述では、`// run`の後に空行があり、その後に`// +build !nacl`が続くため、`run.go`が`// +build !nacl`をビルド制約として認識しない可能性がありました。順序を入れ替えることで、両方のディレクティブが最初の空行より前に存在し、正しく解析されるようになります。

`run.go`は、各テストファイルの冒頭を読み込み、そこに記述されたテストアクション（`// run`など）やビルド制約（`// +build`）を解析します。そして、それらの情報に基づいて、テストのコンパイル、実行、結果の検証を行います。

### 空行の重要性

Goのソースファイルにおける特別なコメント（ビルド制約やテストアクション）は、ファイルの冒頭、`package`宣言の前に記述されることが慣例です。そして、これらのコメントブロックと`package`宣言の間には、通常、空行が挿入されます。この空行は、Goツールが特別なコメントの範囲を識別するための区切りとして機能することがあります。

このコミットでは、`run.go`がビルド制約を解析する際に、この「最初の空行」を区切りとして認識するように変更することで、テストアクションの解析ロジックとの一貫性を保っています。

## 技術的詳細

このコミットの技術的な核心は、`test/run.go`内の`shouldTest`関数と、その呼び出し箇所におけるソースコードの処理範囲の変更にあります。

### `shouldTest`関数

`shouldTest`関数は、与えられたソースコード文字列と現在のOS/アーキテクチャに基づいて、そのファイルがテスト対象となるべきかどうかを判断する役割を担っています。この関数は、ソースコード内の`// +build`コメントを解析し、ビルド制約が満たされているかをチェックします。

変更前の`shouldTest`関数は、引数として渡された`src`文字列全体を対象にビルド制約を検索していました。これは、`src`がファイル全体のコンテンツである場合、ファイルのどこにビルド制約が書かれていてもそれを認識してしまうことを意味します。

### 変更点

1.  **`test/run.go`の変更**:
    *   変更前: `shouldTest`関数内で、`strings.Index(src, "\npackage")`を使って`package`宣言の位置を見つけ、その手前までを`src`として処理するロジックがありました。これは、ビルド制約が`package`宣言より前に来るべきという意図を反映したものですが、空行の扱いに問題がありました。
        ```go
        // shouldTest looks for build tags in a source file and returns
        // whether the file should be used according to the tags.
        func shouldTest(src string, goos, goarch string) (ok bool, whyNot string) {
        -	if idx := strings.Index(src, "\npackage"); idx >= 0 {
        -		src = src[:idx]
        -	}
        	for _, line := range strings.Split(src, "\n") {
        		// ... (build tag parsing logic) ...
        	}
        }
        ```
        このコミットでは、この`package`宣言までの切り詰めロジックが削除されています。
    *   変更後: `shouldTest`関数を呼び出す側（`test.run()`メソッド内）で、ソースコードの切り詰めが行われるようになりました。具体的には、テストファイルの冒頭にある「テストアクション」や「ビルド制約」が記述されているブロックの終端（最初の空行、または`package`宣言の直前）までを`shouldTest`に渡すように変更されました。
        ```go
        func (t *test) run() {
        	// ...
        	// pos は最初の空行、または package 宣言の直前の位置を示す
        	// ...
        -	if ok, why := shouldTest(t.src, goos, goarch); !ok {
        +	// Check for build constraints only upto the first blank line.
        +	if ok, why := shouldTest(t.src[:pos], goos, goarch); !ok {
        		t.action = "skip"
        		// ...
        	}
        }
        ```
        ここで`t.src[:pos]`は、テストファイルのコンテンツのうち、最初の空行までの部分を指します。これにより、`shouldTest`関数は、ビルド制約が記述されるべき「ヘッダー」部分のみを対象にチェックするようになります。

2.  **テストファイルの変更**:
    *   `test/gc2.go`と`test/nosplit.go`の2つのテストファイルで、`// run`と`// +build !nacl`の行順が入れ替えられました。
        変更前:
        ```go
        // run

        // +build !nacl
        ```
        変更後:
        ```go
        // +build !nacl
        // run
        ```
        この変更は、ビルド制約とテストアクションが同じブロック（最初の空行まで）に存在するという新しい規則に準拠させるためのものです。これにより、`run.go`が両方を正しく認識できるようになります。

### 影響

この変更により、`run.go`はビルド制約を解析する際に、テストアクションと同様にファイルの冒頭の「ヘッダーブロック」のみを考慮するようになります。これにより、ビルド制約がファイルの後半に誤って記述された場合でも、それが無視されることで、意図しないテストのスキップが防止されます。同時に、テストファイルの記述者に対して、ビルド制約とテストアクションはファイルの冒頭の同じブロック内に記述する必要があるという明確な規則が課せられることになります。

## コアとなるコードの解説

### `test/run.go`の変更点

1.  **`shouldTest`関数内の`package`宣言による切り詰めロジックの削除**:
    変更前の`shouldTest`関数には、`src`文字列から`package`宣言より前の部分を抽出するロジックがありました。これは、ビルド制約がファイルの冒頭に記述されるべきという意図を反映したものですが、このロジック自体が空行の扱いに関して不完全であったり、呼び出し元での制御と重複したりする可能性がありました。このコミットでは、この内部的な切り詰めロジックを削除し、`shouldTest`関数は渡された`src`文字列全体を素直に処理するように変更されました。これにより、`shouldTest`の役割が「与えられた文字列内のビルド制約をチェックする」という単一の責任に集中し、よりクリーンな設計になります。

2.  **`test.run()`メソッドにおける`shouldTest`の呼び出し箇所の変更**:
    これがこのコミットの最も重要な変更点です。
    *   変更前は、`shouldTest(t.src, goos, goarch)`のように、テストファイル全体のコンテンツ（`t.src`）を`shouldTest`に渡していました。
    *   変更後は、`shouldTest(t.src[:pos], goos, goarch)`のように、`t.src`の先頭から`pos`で示される位置までの部分文字列を渡すように変更されました。
        ここで`pos`は、`test.run()`メソッド内で既に計算されている、テストファイルの冒頭にある「テストアクション」や「ビルド制約」が記述されているブロックの終端（具体的には、最初の空行、または`package`宣言の直前）を指します。
        この変更により、`shouldTest`関数は、ビルド制約が記述されるべき「ヘッダー」部分のみを対象にチェックするようになります。これは、テストアクションがチェックされる範囲と完全に一致するため、ビルド制約とテストアクションの解析ロジックに一貫性がもたらされます。

    コメント`// Check for build constraints only upto the first blank line.`が追加され、この変更の意図が明確に示されています。

### テストファイルの変更点 (`test/gc2.go`, `test/nosplit.go`)

これらのファイルでは、`// run`と`// +build !nacl`のコメントの順序が入れ替えられました。
変更前:
```go
// run

// +build !nacl
```
変更後:
```go
// +build !nacl
// run
```
この変更は、`run.go`の新しい動作に合わせたものです。ビルド制約とテストアクションは、ファイルの冒頭の同じコメントブロック内に記述されるべきであり、そのブロックは最初の空行で区切られます。変更前の記述では、`// run`の後に空行があり、その後に`// +build !nacl`が続くため、`run.go`が`// +build !nacl`をビルド制約として認識しない可能性がありました。順序を入れ替えることで、両方のディレクティブが最初の空行より前に存在し、正しく解析されるようになります。

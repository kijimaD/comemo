# [インデックス 25441] ファイルの概要

このコミットは、Go言語のツールチェイン（アセンブラ、リンカ）とランタイムが、PPC64アーキテクチャにおけるスレッドローカルストレージ（TLS）を処理する方法を変更するものです。具体的には、TLSアクセス時のオフセット計算の責任をGoランタイムのアセンブリコードからプラットフォームリンカに移行することで、外部リンカとの互換性を向上させています。

## 元コミット内容

PPC64アーキテクチャにおいて、Goのツールチェイン（`cmd/internal/obj`、`cmd/link`）とランタイムがTLSを処理する方法を、プラットフォームリンカの挙動に近づけるように変更します。

PPC64xでは、R13レジスタに保持されるスレッドポインタが、スレッドローカルストレージの開始位置から0x7000バイト先にオフセットされています（これはおそらく、16ビット符号付きディスプレイスメントでアクセスできるストレージ量を最大化するためと考えられます）。プラットフォームリンカにスレッドローカルストレージを示すために使用される再配置（relocation）は、このオフセットを考慮に入れています。そのため、外部リンカをサポートできるようにするには、Goランタイムのアセンブリではなく、リンカがこのオフセットを適用するように変更する必要があります。

## 変更の背景

Go言語は、そのビルドシステムとランタイムにおいて、特定のアーキテクチャやOSの特性に合わせた最適化や互換性対応を継続的に行っています。このコミットの背景には、PPC64xアーキテクチャにおけるスレッドローカルストレージ（TLS）の特殊な挙動と、Goのツールチェインが外部リンカと連携する際の課題がありました。

PPC64xアーキテクチャでは、スレッドローカルストレージのベースアドレスを指すスレッドポインタ（R13レジスタ）が、実際のTLS領域の開始位置から0x7000バイトずれた位置を指すという慣習があります。これは、命令セットの制約（例えば、16ビットの符号付きオフセットでアクセスできる範囲を広げるため）によるものと考えられます。

従来のGoのランタイムアセンブリコードでは、この0x7000バイトのオフセットを明示的に減算することで、TLS変数への正しいアクセスを実現していました。しかし、これはプラットフォームの標準的なリンカがTLS再配置を処理する方法とは異なっていました。標準的なリンカは、TLS関連の再配置タイプ（例: `R_PPC64_TLS_LE`）を処理する際に、この0x7000のオフセットを自動的に適用します。

Goのプログラムを外部リンカ（例えば、GCCリンカ）と連携させてビルドする場合、Goのランタイムアセンブリがオフセットを処理し、かつ外部リンカもオフセットを処理しようとすると、二重にオフセットが適用されてしまい、TLS変数へのアクセスが不正になる可能性がありました。この不整合は、特にCgoなどを用いてGoとC/C++コードを混在させる場合に問題となります。

このコミットは、この不整合を解消し、GoのツールチェインがPPC64xのTLSをプラットフォームリンカと同じように処理するように変更することで、外部リンカとの互換性を向上させることを目的としています。これにより、Goプログラムがより広範なビルド環境や既存のC/C++ライブラリとシームレスに連携できるようになります。

## 前提知識の解説

### スレッドローカルストレージ (TLS: Thread-Local Storage)

TLSは、マルチスレッドプログラミングにおいて、各スレッドがそれぞれ独立した変数を持つためのメカニズムです。グローバル変数や静的変数はプロセス内の全スレッドで共有されますが、TLS変数はスレッドごとに異なる値を保持できます。これにより、スレッドセーフなコードを記述しやすくなり、ロックなどの同期メカニズムを減らすことができます。

TLS変数は、通常、スレッドの開始時にOSやランタイムによって割り当てられ、スレッドの終了時に解放されます。アクセス方法はアーキテクチャやOSによって異なりますが、一般的にはスレッドポインタと呼ばれる特殊なレジスタを基準としたオフセットでアクセスされます。

### PPC64xアーキテクチャとR13レジスタ

PPC64x（PowerPC 64-bit）は、IBMが開発したRISCプロセッサアーキテクチャです。LinuxなどのOSでは、PPC64x用のELFv2 ABI（Application Binary Interface）が広く採用されています。

PPC64xのELFv2 ABIでは、R13レジスタがスレッドポインタとして予約されています。このR13レジスタは、TLS領域の特定のオフセットを指すように設定されます。コミットメッセージにあるように、PPC64xではR13がTLS領域の開始位置から0x7000バイト先に設定されるという特殊な慣習があります。これは、命令セットが提供する16ビット符号付きオフセットアドレッシングモードを最大限に活用し、より広い範囲のTLS変数に効率的にアクセスできるようにするための設計上の選択です。

### 再配置 (Relocation)

再配置とは、コンパイル時にアドレスが確定できないシンボル（変数や関数のアドレスなど）について、リンカが最終的な実行可能ファイルや共有ライブラリを生成する際に、正しいアドレスに修正する処理のことです。

オブジェクトファイルには、未解決のシンボル参照と、それらを解決するための再配置エントリが含まれています。各再配置エントリは、どのシンボルを参照しているか、どの種類の再配置を行うか（例: 絶対アドレス、相対アドレス、TLSオフセットなど）、そしてどこを修正するか（オフセット）といった情報を含んでいます。

### ELFv2 ABIにおけるTLSアクセスモデル

ELFv2 ABIでは、TLS変数へのアクセス方法としていくつかのモデルが定義されています。このコミットで言及されているのは「local exec」モデルに関連するものです。

-   **local exec (LE) モデル**: 実行可能ファイル内で定義され、かつ同じ実行可能ファイル内で参照されるTLS変数に適用されます。このモデルでは、TLS変数のアドレスはスレッドポインタからの固定オフセットとして解決されます。

PPC64xのELFv2 ABIの「3.7.2 TLS Runtime Handling」セクションには、R13レジスタがTLS領域の開始位置から0x7000バイトオフセットされていること、そしてリンカが`R_PPC64_TLS_LE`のような再配置タイプを処理する際にこのオフセットを考慮に入れることが明記されています。

### Goのツールチェイン

Go言語のビルドプロセスは、主に以下のコンポーネントで構成されます。

-   **アセンブラ (`cmd/internal/obj`)**: Goのアセンブリコード（`.s`ファイル）をオブジェクトファイルに変換します。この際、シンボル参照に対して再配置エントリを生成します。
-   **リンカ (`cmd/link`)**: オブジェクトファイルを結合し、未解決のシンボル参照を解決して実行可能ファイルや共有ライブラリを生成します。この過程で、再配置エントリに基づいてアドレスを修正します。
-   **ランタイム (`src/runtime`)**: Goプログラムの実行を管理するコードです。ガベージコレクション、スケジューラ、TLSアクセスなどの低レベルな処理を担当します。

## 技術的詳細

このコミットの技術的な核心は、PPC64xアーキテクチャにおけるTLS変数のアドレス計算ロジックを、GoのランタイムアセンブリからGoのリンカに移管することにあります。

### 新しい再配置タイプ `R_POWER_TLS_LE` の導入

Goの内部オブジェクトフォーマットにおいて、PPC64x向けの新しい再配置タイプ `R_POWER_TLS_LE` が導入されました。
-   `src/cmd/internal/obj/link.go`: `obj.R_POWER_TLS_LE` が定義されます。これは、TLS変数がスレッドポインタ（R13）からどれだけオフセットされているかを示すために使用されます。
-   `src/cmd/internal/obj/ppc64/a.out.go` および `src/cmd/internal/obj/ppc64/anames9.go`: アセンブラ内部で使用されるシンボルクラス `C_TLS_LE` が追加され、`R_POWER_TLS_LE` 再配置と関連付けられます。

### アセンブラの変更 (`src/cmd/internal/obj/ppc64/asm9.go`)

Goのアセンブラは、TLSシンボル（`obj.STLSBSS`型）を参照する命令に対して、新しい `R_POWER_TLS_LE` 再配置を生成するように変更されました。
具体的には、`aclass`関数がシンボルの型が `obj.STLSBSS` である場合に `C_TLS_LE` クラスを返すようになり、`asmout`関数が `C_TLS_LE` クラスのオペランドを持つ `AMOVD` 命令に対して `R_POWER_TLS_LE` タイプの再配置エントリを生成するようになりました。この再配置は、TLS変数のオフセットを命令の低位16ビットに挿入するために使用されます。

### リンカの変更 (`src/cmd/link/internal/ppc64/asm.go`)

Goのリンカは、`R_POWER_TLS_LE` タイプの再配置を処理するロジックが追加されました。
-   リンカは、`R_POWER_TLS_LE` 再配置を見つけると、参照されているTLSシンボルの値（`r.Sym.Value`）から0x7000バイトを減算します。
-   この結果得られたオフセット値（`v`）が16ビット符号付き整数に収まるかチェックし、範囲外であればエラーを報告します。
-   最終的に、このオフセット値の下位16ビットを、再配置対象の命令ワードに適用します。これにより、命令はR13レジスタを基準とした正しいオフセットでTLS変数にアクセスできるようになります。

### ランタイムアセンブリの変更 (`src/runtime/tls_ppc64x.s`)

Goのランタイムアセンブリコード（`runtime·save_g` および `runtime·load_g` 関数）から、TLSアクセス時に行っていた0x7000バイトのオフセット調整が削除されました。
-   変更前は、`ADD R13, R31` の後に `SUB $0x7000, R31` という命令があり、R13から0x7000を明示的に減算していました。
-   変更後は、この `SUB $0x7000, R31` 命令が削除され、リンカが再配置時にオフセットを適用することを前提とするようになりました。

### 影響

この変更により、GoのツールチェインはPPC64xのTLSアクセスを、プラットフォームのELFv2 ABI仕様に準拠した方法で処理するようになります。これにより、Goのオブジェクトファイルや実行可能ファイルが外部リンカによって処理される際に、TLS関連のシンボル解決が正しく行われ、外部リンカとの互換性が向上します。特に、Cgoを使用してGoとC/C++コードを連携させる場合に、TLS変数のアクセスに関する問題が解消されることが期待されます。

### `src/cmd/internal/obj/ppc64/asm9.go`
アセンブラがTLSシンボルに対して `R_POWER_TLS_LE` 再配置を生成するように変更。
- `aclass` 関数で `obj.STLSBSS` 型のシンボルに対して `C_TLS_LE` を返す。
- `asmout` 関数で `C_TLS_LE` クラスのオペランドを持つ `AMOVD` 命令に対して `R_POWER_TLS_LE` 再配置を生成するロジックを追加。
```go
 func aclass(ctxt *obj.Link, a *obj.Addr) int {
 	// ...
 	case obj.TYPE_MEM:
 		// ...
 		if a.Sym != nil { // use relocation
+			if a.Sym.Type == obj.STLSBSS {
+				return C_TLS_LE
+			}
 			return C_ADDR
 		}
 		return C_LEXT
 	// ...
 }

 func asmout(ctxt *obj.Link, p *obj.Prog, o *Optab, out []uint32) {
 	// ...
 	case 79: // AMOVD, C_TLS_LE, C_NONE, C_NONE, C_REG
 		if p.From.Offset != 0 {
 			ctxt.Diag("invalid offset against tls var %v", p)
 		}
 		o1 = AOP_IRR(OP_ADDI, uint32(p.To.Reg), REGZERO, 0)
 		rel := obj.Addrel(ctxt.Cursym)
 		rel.Off = int32(ctxt.Pc)
 		rel.Siz = 4
 		rel.Sym = p.From.Sym
 		rel.Type = obj.R_POWER_TLS_LE
 	// ...
 }
```

### `src/cmd/link/internal/ppc64/asm.go`
リンカが `R_POWER_TLS_LE` 再配置を処理するロジックを追加。
- TLSシンボルの値から0x7000を減算し、結果を命令ワードに適用。
```go
 func archreloc(r *ld.Reloc, s *ld.LSym, val *int64) int {
 	// ...
 	case obj.R_POWER_TLS_LE:
 		// The thread pointer points 0x7000 bytes after the start of the the
 		// thread local storage area as documented in section "3.7.2 TLS
 		// Runtime Handling" of "Power Architecture 64-Bit ELF V2 ABI
 		// Specification".
 		v := r.Sym.Value - 0x7000
 		if int64(int16(v)) != v {
 			ld.Diag("TLS offset out of range %d", v)
 		}
 		*val = (*val &^ 0xffff) | (v & 0xffff)
 		return 0
 	}
 	// ...
 }
```

## コアとなるコードの解説

このコミットの核となる変更は、PPC64xアーキテクチャにおけるTLS変数のアドレス計算の責任を、GoのランタイムアセンブリからGoのリンカに移すことです。

1.  **`src/cmd/internal/obj/link.go` での `R_POWER_TLS_LE` の定義**:
    これは、Goの内部リンカが認識する新しい再配置タイプです。`R_POWER_TLS_LE` は "Thread-Local Storage, Local Exec" の略で、TLS変数がスレッドポインタ（R13）からのオフセットとしてアクセスされる場合に用いられます。この再配置タイプが導入されたことで、リンカはTLSシンボルに対する特別な処理を行うべきであることを認識できるようになります。

2.  **`src/cmd/internal/obj/ppc64/asm9.go` でのアセンブラの変更**:
    Goのアセンブラは、Goのアセンブリコード（`.s`ファイル）をオブジェクトファイルに変換する際に、TLS変数への参照を検出すると、その参照に対して `R_POWER_TLS_LE` タイプの再配置エントリを生成するようになります。
    具体的には、`aclass` 関数が `obj.STLSBSS` (Thread-Local Storage BSS) 型のシンボルを `C_TLS_LE` という新しいクラスとして識別します。そして、`asmout` 関数内で、この `C_TLS_LE` クラスのオペランドを持つ `AMOVD` (Move Doubleword) 命令（PPC64xでレジスタに値をロードする命令）に対して、`R_POWER_TLS_LE` タイプの再配置が生成されます。この再配置は、命令の低位16ビットにTLS変数のオフセットを埋め込むことをリンカに指示します。

3.  **`src/cmd/link/internal/ppc64/asm.go` でのリンカの変更**:
    Goのリンカは、オブジェクトファイルを結合する際に、`R_POWER_TLS_LE` タイプの再配置エントリを処理します。
    リンカは、再配置対象のTLSシンボル（`r.Sym`）の `Value` (シンボルのアドレスまたはオフセット) から、PPC64xのABIで規定されている0x7000バイトのオフセットを減算します。この減算された値が、スレッドポインタ（R13）からの真のオフセットとなります。
    リンカは、このオフセット値が16ビット符号付き整数（PPC64xの命令で直接扱える範囲）に収まることを確認し、その値の下位16ビットを、再配置対象の命令ワードに書き込みます。これにより、実行時にR13レジスタを基準としてTLS変数にアクセスする命令が正しく構築されます。

4.  **`src/runtime/tls_ppc64x.s` でのランタイムアセンブリの変更**:
    Goのランタイムアセンブリコード（`runtime·save_g` と `runtime·load_g`）は、これまでTLS変数にアクセスする際に、R13レジスタに0x7000を足した後、明示的に0x7000を減算していました。これは、R13がTLS領域の開始位置から0x7000バイト先に設定されているというPPC64xの慣習に対応するためでした。
    しかし、リンカが `R_POWER_TLS_LE` 再配置を処理する際にこのオフセットを適用するようになったため、ランタイムアセンブリでのこの明示的な減算は不要になりました。このコミットでは、`SUB $0x7000, R31` 命令が削除され、ランタイムとリンカの間でオフセット計算の責任が明確に分離されました。

これらの変更により、GoのツールチェインはPPC64xのTLSアクセスを、プラットフォームのELFv2 ABI仕様に完全に準拠した方法で処理するようになります。これにより、Goのオブジェクトファイルが外部リンカによって処理される際にも、TLS関連のシンボル解決が正しく行われ、外部リンカとの互換性が大幅に向上します。

    cmd/internal/obj, cmd/link, runtime: handle TLS more like a platform linker on ppc64

    On ppc64x, the thread pointer, held in R13, points 0x7000 bytes past where
    thread-local storage begins (presumably to maximize the amount of storage that
    can be accessed with a 16-bit signed displacement). The relocations used to
    indicate thread-local storage to the platform linker account for this, so to be
    able to support external linking we need to change things so the linker applies
    this offset instead of the runtime assembly.

## 元コミット内容

PPC64アーキテクチャにおいて、Goのツールチェイン（`cmd/internal/obj`、`cmd/link`）とランタイムがTLSを処理する方法を、プラットフォームリンカの挙動に近づけるように変更します。

PPC64xでは、R13レジスタに保持されるスレッドポインタが、スレッドローカルストレージの開始位置から0x7000バイト先にオフセットされています（これはおそらく、16ビット符号付きディスプレイスメントでアクセスできるストレージ量を最大化するためと考えられます）。プラットフォームリンカにスレッドローカルストレージを示すために使用される再配置（relocation）は、このオフセットを考慮に入れています。そのため、外部リンカをサポートできるようにするには、Goランタイムのアセンブリではなく、リンカがこのオフセットを適用するように変更する必要があります。

## 変更の背景

Go言語は、そのビルドシステムとランタイムにおいて、特定のアーキテクチャやOSの特性に合わせた最適化や互換性対応を継続的に行っています。このコミットの背景には、PPC64xアーキテクチャにおけるスレッドローカルストレージ（TLS）の特殊な挙動と、Goのツールチェインが外部リンカと連携する際の課題がありました。

PPC64xアーキテクチャでは、スレッドローカルストレージのベースアドレスを指すスレッドポインタ（R13レジスタ）が、実際のTLS領域の開始位置から0x7000バイトずれた位置を指すという慣習があります。これは、命令セットの制約（例えば、16ビットの符号付きオフセットでアクセスできる範囲を広げるため）によるものと考えられます。

従来のGoのランタイムアセンブリコードでは、この0x7000バイトのオフセットを明示的に減算することで、TLS変数への正しいアクセスを実現していました。しかし、これはプラットフォームの標準的なリンカがTLS再配置を処理する方法とは異なっていました。標準的なリンカは、TLS関連の再配置タイプ（例: `R_PPC64_TLS_LE`）を処理する際に、この0x7000のオフセットを自動的に適用します。

Goのプログラムを外部リンカ（例えば、GCCリンカ）と連携させてビルドする場合、Goのランタイムアセンブリがオフセットを処理し、かつ外部リンカもオフセットを処理しようとすると、二重にオフセットが適用されてしまい、TLS変数へのアクセスが不正になる可能性がありました。この不整合は、特にCgoなどを用いてGoとC/C++コードを混在させる場合に問題となります。

このコミットは、この不整合を解消し、GoのツールチェインがPPC64xのTLSをプラットフォームリンカと同じように処理するように変更することで、外部リンカとの互換性を向上させることを目的としています。これにより、Goプログラムがより広範なビルド環境や既存のC/C++ライブラリとシームレスに連携できるようになります。

## 前提知識の解説

### スレッドローカルストレージ (TLS: Thread-Local Storage)

TLSは、マルチスレッドプログラミングにおいて、各スレッドがそれぞれ独立した変数を持つためのメカニズムです。グローバル変数や静的変数はプロセス内の全スレッドで共有されますが、TLS変数はスレッドごとに異なる値を保持できます。これにより、スレッドセーフなコードを記述しやすくなり、ロックなどの同期メカニズムを減らすことができます。

TLS変数は、通常、スレッドの開始時にOSやランタイムによって割り当てられ、スレッドの終了時に解放されます。アクセス方法はアーキテクチャやOSによって異なりますが、一般的にはスレッドポインタと呼ばれる特殊なレジスタを基準としたオフセットでアクセスされます。

### PPC64xアーキテクチャとR13レジスタ

PPC64x（PowerPC 64-bit）は、IBMが開発したRISCプロセッサアーキテクチャです。LinuxなどのOSでは、PPC64x用のELFv2 ABI（Application Binary Interface）が広く採用されています。

PPC64xのELFv2 ABIでは、R13レジスタがスレッドポインタとして予約されています。このR13レジスタは、TLS領域の特定のオフセットを指すように設定されます。コミットメッセージにあるように、PPC64xではR13がTLS領域の開始位置から0x7000バイト先に設定されるという特殊な慣習があります。これは、命令セットが提供する16ビット符号付きオフセットアドレッシングモードを最大限に活用し、より広い範囲のTLS変数に効率的にアクセスできるようにするための設計上の選択です。

### 再配置 (Relocation)

再配置とは、コンパイル時にアドレスが確定できないシンボル（変数や関数のアドレスなど）について、リンカが最終的な実行可能ファイルや共有ライブラリを生成する際に、正しいアドレスに修正する処理のことです。

オブジェクトファイルには、未解決のシンボル参照と、それらを解決するための再配置エントリが含まれています。各再配置エントリは、どのシンボルを参照しているか、どの種類の再配置を行うか（例: 絶対アドレス、相対アドレス、TLSオフセットなど）、そしてどこを修正するか（オフセット）といった情報を含んでいます。

### ELFv2 ABIにおけるTLSアクセスモデル

ELFv2 ABIでは、TLS変数へのアクセス方法としていくつかのモデルが定義されています。このコミットで言及されているのは「local exec」モデルに関連するものです。

-   **local exec (LE) モデル**: 実行可能ファイル内で定義され、かつ同じ実行可能ファイル内で参照されるTLS変数に適用されます。このモデルでは、TLS変数のアドレスはスレッドポインタからの固定オフセットとして解決されます。

PPC64xのELFv2 ABIの「3.7.2 TLS Runtime Handling」セクションには、R13レジスタがTLS領域の開始位置から0x7000バイトオフセットされていること、そしてリンカが`R_PPC64_TLS_LE`のような再配置タイプを処理する際にこのオフセットを考慮に入れることが明記されています。

### Goのツールチェイン

Go言語のビルドプロセスは、主に以下のコンポーネントで構成されます。

-   **アセンブラ (`cmd/internal/obj`)**: Goのアセンブリコード（`.s`ファイル）をオブジェクトファイルに変換します。この際、シンボル参照に対して再配置エントリを生成します。
-   **リンカ (`cmd/link`)**: オブジェクトファイルを結合し、未解決のシンボル参照を解決して実行可能ファイルや共有ライブラリを生成します。この過程で、再配置エントリに基づいてアドレスを修正します。
-   **ランタイム (`src/runtime`)**: Goプログラムの実行を管理するコードです。ガベージコレクション、スケジューラ、TLSアクセスなどの低レベルな処理を担当します。

## 技術的詳細

このコミットの技術的な核心は、PPC64xアーキテクチャにおけるTLS変数のアドレス計算ロジックを、GoのランタイムアセンブリからGoのリンカに移管することにあります。

### 新しい再配置タイプ `R_POWER_TLS_LE` の導入

Goの内部オブジェクトフォーマットにおいて、PPC64x向けの新しい再配置タイプ `R_POWER_TLS_LE` が導入されました。
-   `src/cmd/internal/obj/link.go`: `obj.R_POWER_TLS_LE` が定義されます。これは、TLS変数がスレッドポインタ（R13）からどれだけオフセットされているかを示すために使用されます。
-   `src/cmd/internal/obj/ppc64/a.out.go` および `src/cmd/internal/obj/ppc64/anames9.go`: アセンブラ内部で使用されるシンボルクラス `C_TLS_LE` が追加され、`R_POWER_TLS_LE` 再配置と関連付けられます。

### アセンブラの変更 (`src/cmd/internal/obj/ppc64/asm9.go`)

Goのアセンブラは、TLSシンボル（`obj.STLSBSS`型）を参照する命令に対して、新しい `R_POWER_TLS_LE` 再配置を生成するように変更されました。
具体的には、`aclass`関数がシンボルの型が `obj.STLSBSS` である場合に `C_TLS_LE` クラスを返すようになり、`asmout`関数が `C_TLS_LE` クラスのオペランドを持つ `AMOVD` 命令に対して `R_POWER_TLS_LE` タイプの再配置エントリを生成するようになりました。この再配置は、TLS変数のオフセットを命令の低位16ビットに挿入するために使用されます。

### リンカの変更 (`src/cmd/link/internal/ppc64/asm.go`)

Goのリンカは、`R_POWER_TLS_LE` タイプの再配置を処理するロジックが追加されました。
-   リンカは、`R_POWER_TLS_LE` 再配置を見つけると、参照されているTLSシンボルの値（`r.Sym.Value`）から0x7000バイトを減算します。
-   この結果得られたオフセット値（`v`）が16ビット符号付き整数に収まるかチェックし、範囲外であればエラーを報告します。
-   最終的に、このオフセット値の下位16ビットを、再配置対象の命令ワードに適用します。これにより、命令はR13レジスタを基準とした正しいオフセットでTLS変数にアクセスできるようになります。

### ランタイムアセンブリの変更 (`src/runtime/tls_ppc64x.s`)

Goのランタイムアセンブリコード（`runtime·save_g` および `runtime·load_g` 関数）から、TLSアクセス時に行っていた0x7000バイトのオフセット調整が削除されました。
-   変更前は、`ADD R13, R31` の後に `SUB $0x7000, R31` という命令があり、R13から0x7000を明示的に減算していました。
-   変更後は、この `SUB $0x7000, R31` 命令が削除され、リンカが再配置時にオフセットを適用することを前提とするようになりました。

### 影響

この変更により、GoのツールチェインはPPC64xのTLSアクセスを、プラットフォームのELFv2 ABI仕様に準拠した方法で処理するようになります。これにより、Goのオブジェクトファイルや実行可能ファイルが外部リンカによって処理される際に、TLS関連のシンボル解決が正しく行われ、外部リンカとの互換性が向上します。特に、Cgoを使用してGoとC/C++コードを連携させる場合に、TLS変数のアクセスに関する問題が解消されることが期待されます。

## コアとなるコードの変更箇所

### `src/cmd/internal/obj/link.go`
新しい再配置タイプ `R_POWER_TLS_LE` を定義に追加。
```go
 const (
 	// the thread local base and the thread local variable defined by the
 	// referenced (thread local) symbol from the GOT.
 	R_ARM64_TLS_IE
+
+	// PPC64.
+
+	// R_POWER_TLS_LE is used to implement the "local exec" model for tls
+	// access. It resolves to the offset of the thread-local symbol from the
+	// thread pointer (R13) and inserts this value into the low 16 bits of an
+	// instruction word.
+	R_POWER_TLS_LE
 )
```

### `src/cmd/internal/obj/ppc64/a.out.go` および `src/cmd/internal/obj/ppc64/anames9.go`
アセンブラ内部で使用されるシンボルクラス `C_TLS_LE` を追加。
```go
// a.out.go
 const (
 	C_ANY
 	C_GOK
 	C_ADDR
+	C_TLS_LE
 	C_TEXTSIZE

 	C_NCLASS /* must be the last */
 )

// anames9.go
 var cnames9 = []string{
 	"ANY",
 	"GOK",
 	"ADDR",
+	"TLS_LE",
 	"TEXTSIZE",
 	"NCLASS",
 }
```

### `src/cmd/internal/obj/ppc64/asm9.go`
アセンブラがTLSシンボルに対して `R_POWER_TLS_LE` 再配置を生成するように変更。
- `aclass` 関数で `obj.STLSBSS` 型のシンボルに対して `C_TLS_LE` を返す。
- `asmout` 関数で `C_TLS_LE` クラスのオペランドを持つ `AMOVD` 命令に対して `R_POWER_TLS_LE` 再配置を生成するロジックを追加。
```go
 func aclass(ctxt *obj.Link, a *obj.Addr) int {
 	// ...
 	case obj.TYPE_MEM:
 		// ...
 		if a.Sym != nil { // use relocation
+			if a.Sym.Type == obj.STLSBSS {
+				return C_TLS_LE
+			}
 			return C_ADDR
 		}
 		return C_LEXT
 	// ...
 }

 func asmout(ctxt *obj.Link, p *obj.Prog, o *Optab, out []uint32) {
 	// ...
 	case 79: // AMOVD, C_TLS_LE, C_NONE, C_NONE, C_REG
 		if p.From.Offset != 0 {
 			ctxt.Diag("invalid offset against tls var %v", p)
 		}
 		o1 = AOP_IRR(OP_ADDI, uint32(p.To.Reg), REGZERO, 0)
 		rel := obj.Addrel(ctxt.Cursym)
 		rel.Off = int32(ctxt.Pc)
 		rel.Siz = 4
 		rel.Sym = p.From.Sym
 		rel.Type = obj.R_POWER_TLS_LE
 	// ...
 }
```

### `src/cmd/link/internal/ppc64/asm.go`
リンカが `R_POWER_TLS_LE` 再配置を処理するロジックを追加。
- TLSシンボルの値から0x7000を減算し、結果を命令ワードに適用。
```go
 func archreloc(r *ld.Reloc, s *ld.LSym, val *int64) int {
 	// ...
 	case obj.R_POWER_TLS_LE:
 		// The thread pointer points 0x7000 bytes after the start of the the
 		// thread local storage area as documented in section "3.7.2 TLS
 		// Runtime Handling" of "Power Architecture 64-Bit ELF V2 ABI
 		// Specification".
 		v := r.Sym.Value - 0x7000
 		if int64(int16(v)) != v {
 			ld.Diag("TLS offset out of range %d", v)
 		}
 		*val = (*val &^ 0xffff) | (v & 0xffff)
 		return 0
 	}
 	// ...
 }
```

### `src/runtime/tls_ppc64x.s`
ランタイムアセンブリから0x7000バイトのオフセット調整を削除。
```asm
// 変更前 (runtime·save_g):
// 	MOVD	$runtime·tls_g(SB), R31
// 	ADD	R13, R31
// 	// The actual TLS base is 0x7000 below R13
// 	SUB	$0x7000, R31

// 変更後 (runtime·save_g):
	MOVD	runtime·tls_g(SB), R31
	ADD	R13, R31

// 変更前 (runtime·load_g):
// 	MOVD	$runtime·tls_g(SB), R31
// 	// R13 is the C ABI TLS base pointer + 0x7000
// 	ADD	R13, R31
// 	SUB	$0x7000, R31

// 変更後 (runtime·load_g):
	MOVD	runtime·tls_g(SB), R31
	ADD	R13, R31
```

## コアとなるコードの解説

このコミットの核となる変更は、PPC64xアーキテクチャにおけるTLS変数のアドレス計算の責任を、GoのランタイムアセンブリからGoのリンカに移すことです。

1.  **`src/cmd/internal/obj/link.go` での `R_POWER_TLS_LE` の定義**:
    これは、Goの内部リンカが認識する新しい再配置タイプです。`R_POWER_TLS_LE` は "Thread-Local Storage, Local Exec" の略で、TLS変数がスレッドポインタ（R13）からのオフセットとしてアクセスされる場合に用いられます。この再配置タイプが導入されたことで、リンカはTLSシンボルに対する特別な処理を行うべきであることを認識できるようになります。

2.  **`src/cmd/internal/obj/ppc64/asm9.go` でのアセンブラの変更**:
    Goのアセンブラは、Goのアセンブリコード（`.s`ファイル）をオブジェクトファイルに変換する際に、TLS変数への参照を検出すると、その参照に対して `R_POWER_TLS_LE` タイプの再配置エントリを生成するようになります。
    具体的には、`aclass` 関数が `obj.STLSBSS` (Thread-Local Storage BSS) 型のシンボルを `C_TLS_LE` という新しいクラスとして識別します。そして、`asmout` 関数内で、この `C_TLS_LE` クラスのオペランドを持つ `AMOVD` (Move Doubleword) 命令（PPC64xでレジスタに値をロードする命令）に対して、`R_POWER_TLS_LE` タイプの再配置が生成されます。この再配置は、命令の低位16ビットにTLS変数のオフセットを埋め込むことをリンカに指示します。

3.  **`src/cmd/link/internal/ppc64/asm.go` でのリンカの変更**:
    Goのリンカは、オブジェクトファイルを結合する際に、`R_POWER_TLS_LE` タイプの再配置エントリを処理します。
    リンカは、再配置対象のTLSシンボル（`r.Sym`）の `Value` (シンボルのアドレスまたはオフセット) から、PPC64xのABIで規定されている0x7000バイトのオフセットを減算します。この減算された値が、スレッドポインタ（R13）からの真のオフセットとなります。
    リンカは、このオフセット値が16ビット符号付き整数（PPC64xの命令で直接扱える範囲）に収まることを確認し、その値の下位16ビットを、再配置対象の命令ワードに書き込みます。これにより、実行時にR13レジスタを基準としてTLS変数にアクセスする命令が正しく構築されます。

4.  **`src/runtime/tls_ppc64x.s` でのランタイムアセンブリの変更**:
    Goのランタイムアセンブリコード（`runtime·save_g` と `runtime·load_g`）は、これまでTLS変数にアクセスする際に、R13レジスタに0x7000を足した後、明示的に0x7000を減算していました。これは、R13がTLS領域の開始位置から0x7000バイト先に設定されているというPPC64xの慣習に対応するためでした。
    しかし、リンカが `R_POWER_TLS_LE` 再配置を処理する際にこのオフセットを適用するようになったため、ランタイムアセンブリでのこの明示的な減算は不要になりました。このコミットでは、`SUB $0x7000, R31` 命令が削除され、ランタイムとリンカの間でオフセット計算の責任が明確に分離されました。

これらの変更により、GoのツールチェインはPPC64xのTLSアクセスを、プラットフォームのELFv2 ABI仕様に完全に準拠した方法で処理するようになります。これにより、Goのオブジェクトファイルが外部リンカによって処理される際にも、TLS関連のシンボル解決が正しく行われ、外部リンカとの互換性が大幅に向上します。

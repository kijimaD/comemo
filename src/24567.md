## 変更の背景

Go 1.5で導入されたベンダー実験（`GO15VENDOREXPERIMENT`）は、プロジェクトが自身の依存関係を`vendor`ディレクトリ内に管理できるようにする機能です。これにより、依存関係のバージョン管理が容易になり、ビルドの再現性が向上します。しかし、このベンダーメカニズムが導入された当初、`go`コマンドは`_test.go`ファイル（通常のパッケージコードとは別にコンパイルされるテストコード）内で宣言されたインポートパスの解決において、ベンダーディレクトリを適切に考慮しないという問題がありました。

具体的には、以下の問題が発生していました。

*   **Issue #11977**: 外部テスト（`_test`パッケージとして定義されるテスト）が、ベンダーされたパッケージ内の内部テストのエクスポートされたシンボルを参照できない、またはベンダーパスが正しく解決されないためにビルドに失敗する。
*   **Issue #11988**: `go test -i`コマンド（テストの依存関係をインストールする）が、`_test.go`ファイル内のベンダーインポートを正しく処理できず、テストのビルドが失敗する。

これらの問題は、`_test.go`ファイルが通常のパッケージコードとは異なる方法でインポートを解決する必要があるというGoの設計上の特性と、ベンダーメカニズムの初期実装との間の不整合に起因していました。このコミットは、これらの問題を解決し、`_test.go`ファイル内のベンダーインポートが期待通りに機能するようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoの概念について理解しておく必要があります。

1.  **Goのパッケージ管理と`GOPATH`**:
    *   Go 1.5以前は、すべてのGoプロジェクトは`GOPATH`という環境変数で指定されたワークスペース内で管理されていました。依存関係は`GOPATH/src`以下に配置され、`go get`コマンドで取得されました。
    *   `GOPATH`は、Goのソースコード、コンパイル済みパッケージ、実行可能バイナリを配置するための標準的なディレクトリ構造を定義していました。

2.  **ベンダー（Vendoring）メカニズム**:
    *   Go 1.5で実験的に導入され、Go 1.6でデフォルトで有効になった機能です。
    *   プロジェクトのルートディレクトリに`vendor`という名前のディレクトリを作成し、その中にプロジェクト固有の依存関係のコピーを配置します。
    *   `go`コマンドは、パッケージをインポートする際に、まず現在のパッケージの`vendor`ディレクトリ内を検索し、次に`GOPATH`を検索します。これにより、プロジェクトは自身の依存関係のバージョンを固定し、他のプロジェクトや`GOPATH`の変更に影響されずにビルドの再現性を確保できます。
    *   `vendor`ディレクトリ内のパッケージは、そのパッケージのインポートパスが`vendor/`プレフィックスなしで解決されるように、`go`コマンドによって内部的にパスが書き換えられます。

3.  **`_test.go`ファイルとテストの種類**:
    *   Goでは、テストコードは`_test.go`というサフィックスを持つファイルに記述されます。
    *   **内部テスト**: `package foo`のように、テスト対象のパッケージと同じパッケージ名で定義されるテストです。テスト対象パッケージの内部（エクスポートされていない）シンボルにアクセスできます。
    *   **外部テスト**: `package foo_test`のように、テスト対象のパッケージとは異なるパッケージ名で定義されるテストです。テスト対象パッケージのエクスポートされたシンボルのみにアクセスできます。これは、パッケージが外部からどのように見えるかをテストするのに役立ちます。
    *   `go`コマンドは、通常のパッケージコードと`_test.go`ファイルを別々にコンパイルし、リンクします。特に外部テストは、通常のパッケージとは完全に独立したバイナリとして扱われます。

4.  **`Package`構造体とインポートパス**:
    *   `cmd/go`内部では、Goのパッケージは`Package`構造体で表現されます。この構造体には、そのパッケージがインポートする他のパッケージのパスが格納されます。
    *   `pkg.Imports`: 通常のパッケージコードがインポートするパッケージのリスト。
    *   `pkg.TestImports`: 内部テスト（`_test.go`ファイルで`package foo`として定義されるもの）がインポートするパッケージのリスト。
    *   `pkg.XTestImports`: 外部テスト（`_test.go`ファイルで`package foo_test`として定義されるもの）がインポートするパッケージのリスト。

このコミットの核心は、`pkg.TestImports`と`pkg.XTestImports`に格納されているインポートパスが、ベンダーメカニズムによって正しく解決されるようにすることです。

## 技術的詳細

このコミットの主要な変更点は、`Package`構造体に`vendored`という新しいメソッドを導入し、`_test.go`ファイル内のインポートパスをベンダーパスに解決するロジックを集中させたことです。

以前は、`list.go`や`test.go`内で個別に`vendoredImportPath`関数を呼び出して`TestImports`や`XTestImports`のパスを解決しようとしていました。しかし、このアプローチでは、テストインポートが通常のインポートとは異なるライフサイクルで処理されるため、ベンダーパスの解決が不完全または不正確になるケースがありました。

新しい`Package.vendored`メソッドは、以下の役割を担います。

1.  **遅延解決**: `p.TestImports`や`p.XTestImports`は、パッケージの初期ロード時にはベンダー解決されません。これは、ファイルシステムへのアクセスを避け、また`go test`実行時に元のパスからエラーメッセージを生成できるようにするためです。`vendored`メソッドは、これらのインポートパスが必要になったときに初めてベンダー解決を行います。
2.  **一貫した解決**: `vendoredImportPath(p, path)`関数を使用して、与えられたパッケージ`p`のコンテキストでインポートパス`path`をベンダー解決します。これにより、`vendor`ディレクトリ内の正しいパッケージが参照されるようになります。
3.  **重複排除とソート**: 解決されたインポートパスのリストから重複を排除し、アルファベット順にソートして返します。
4.  **安全チェック**: `p.vendored(p.Imports)`が誤って呼び出されないようにパニックを発生させるチェックが含まれています。これは、`p.Imports`はパッケージの初期ロード時に既にベンダー解決されているため、二重に処理する必要がないことを示しています。

この`vendored`メソッドが導入されたことで、`list.go`や`test.go`のような`_test.go`ファイルのインポートパスを扱う箇所では、直接`vendoredImportPath`を呼び出す代わりに、`p.vendored(p.TestImports)`や`p.vendored(p.XTestImports)`を呼び出すように変更されました。これにより、ベンダーパス解決のロジックが一元化され、テストインポートの取り扱いがより堅牢になりました。

## コアとなるコードの解説

このコミットの核心は、`src/cmd/go/pkg.go`に追加された`Package.vendored`メソッドです。

```go
func (p *Package) vendored(imports []string) []string {
	// p.Importsが誤って渡されないようにするための安全チェック
	if len(imports) > 0 && len(p.Imports) > 0 && &imports[0] == &p.Imports[0] {
		panic("internal error: p.vendored(p.Imports) called")
	}
	
	seen := make(map[string]bool) // 重複排除のためのマップ
	var all []string             // 解決されたインポートパスを格納するスライス
	
	for _, path := range imports {
		// vendoredImportPath関数を使って、各インポートパスをベンダー解決
		path, _ = vendoredImportPath(p, path) 
		if !seen[path] { // 重複がなければ追加
			seen[path] = true
			all = append(all, path)
		}
	}
	sort.Strings(all) // 結果をソート
	return all
}
```

このメソッドは、`_test.go`ファイルから読み込まれた生のインポートパス（`p.TestImports`や`p.XTestImports`）を受け取り、それらを現在のパッケージ`p`のコンテキストでベンダー解決します。

*   `vendoredImportPath(p, path)`: この内部関数が、実際に`path`が`p`の`vendor`ディレクトリ内に存在するかどうかを判断し、存在する場合はベンダー解決されたパス（例: `example.com/foo/vendor/bar`ではなく`bar`）を返します。
*   遅延解決の理由: `_test.go`ファイル内のインポートは、通常のパッケージインポートとは異なり、パッケージの初期ロード時にすぐにベンダー解決されません。これは、`go test`コマンドがテストを実行する際に、元のインポートパスからより適切なエラーメッセージを生成できるという利点があるためです。また、不要なファイルシステムアクセスを避ける目的もあります。
*   `list.go`と`test.go`での利用: この`vendored`メソッドを呼び出すことで、`go list`コマンドはベンダー解決されたテストインポートパスを正確に表示し、`go test`コマンドはテストのビルド時にベンダーされた依存関係を正しくリンクできるようになります。

この変更により、Goのベンダーメカニズムが`_test.go`ファイルに対しても完全に機能するようになり、ベンダーを使用するプロジェクトでのテストの信頼性と再現性が向上しました。

## 元コミット内容

`cmd/go`: `foo_test.go`ファイル内のベンダーインポートの取り扱いを修正。

Issue #11977 と #11988 を修正。

## 変更の背景

Go 1.5で導入されたベンダー実験（`GO15VENDOREXPERIMENT`）は、プロジェクトが自身の依存関係を`vendor`ディレクトリ内に管理できるようにする機能です。これにより、依存関係のバージョン管理が容易になり、ビルドの再現性が向上します。しかし、このベンダーメカニズムが導入された当初、`go`コマンドは`_test.go`ファイル（通常のパッケージコードとは別にコンパイルされるテストコード）内で宣言されたインポートパスの解決において、ベンダーディレクトリを適切に考慮しないという問題がありました。

具体的には、以下の問題が発生していました。

*   **Issue #11977**: 外部テスト（`_test`パッケージとして定義されるテスト）が、ベンダーされたパッケージ内の内部テストのエクスポートされたシンボルを参照できない、またはベンダーパスが正しく解決されないためにビルドに失敗する。
*   **Issue #11988**: `go test -i`コマンド（テストの依存関係をインストールする）が、`_test.go`ファイル内のベンダーインポートを正しく処理できず、テストのビルドが失敗する。

これらの問題は、`_test.go`ファイルが通常のパッケージコードとは異なる方法でインポートを解決する必要があるというGoの設計上の特性と、ベンダーメカニズムの初期実装との間の不整合に起因していました。このコミットは、これらの問題を解決し、`_test.go`ファイル内のベンダーインポートが期待通りに機能するようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoの概念について理解しておく必要があります。

1.  **Goのパッケージ管理と`GOPATH`**:
    *   Go 1.5以前は、すべてのGoプロジェクトは`GOPATH`という環境変数で指定されたワークスペース内で管理されていました。依存関係は`GOPATH/src`以下に配置され、`go get`コマンドで取得されました。
    *   `GOPATH`は、Goのソースコード、コンパイル済みパッケージ、実行可能バイナリを配置するための標準的なディレクトリ構造を定義していました。

2.  **ベンダー（Vendoring）メカニズム**:
    *   Go 1.5で実験的に導入され、Go 1.6でデフォルトで有効になった機能です。
    *   プロジェクトのルートディレクトリに`vendor`という名前のディレクトリを作成し、その中にプロジェクト固有の依存関係のコピーを配置します。
    *   `go`コマンドは、パッケージをインポートする際に、まず現在のパッケージの`vendor`ディレクトリ内を検索し、次に`GOPATH`を検索します。これにより、プロジェクトは自身の依存関係のバージョンを固定し、他のプロジェクトや`GOPATH`の変更に影響されずにビルドの再現性を確保できます。
    *   `vendor`ディレクトリ内のパッケージは、そのパッケージのインポートパスが`vendor/`プレフィックスなしで解決されるように、`go`コマンドによって内部的にパスが書き換えられます。

3.  **`_test.go`ファイルとテストの種類**:
    *   Goでは、テストコードは`_test.go`というサフィックスを持つファイルに記述されます。
    *   **内部テスト**: `package foo`のように、テスト対象のパッケージと同じパッケージ名で定義されるテストです。テスト対象パッケージの内部（エクスポートされていない）シンボルにアクセスできます。
    *   **外部テスト**: `package foo_test`のように、テスト対象のパッケージとは異なるパッケージ名で定義されるテストです。テスト対象パッケージのエクスポートされたシンボルのみにアクセスできます。これは、パッケージが外部からどのように見えるかをテストするのに役立ちます。
    *   `go`コマンドは、通常のパッケージコードと`_test.go`ファイルを別々にコンパイルし、リンクします。特に外部テストは、通常のパッケージとは完全に独立したバイナリとして扱われます。

4.  **`Package`構造体とインポートパス**:
    *   `cmd/go`内部では、Goのパッケージは`Package`構造体で表現されます。この構造体には、そのパッケージがインポートする他のパッケージのパスが格納されます。
    *   `pkg.Imports`: 通常のパッケージコードがインポートするパッケージのリスト。
    *   `pkg.TestImports`: 内部テスト（`_test.go`ファイルで`package foo`として定義されるもの）がインポートするパッケージのリスト。
    *   `pkg.XTestImports`: 外部テスト（`_test.go`ファイルで`package foo_test`として定義されるもの）がインポートするパッケージのリスト。

このコミットの核心は、`pkg.TestImports`と`pkg.XTestImports`に格納されているインポートパスが、ベンダーメカニズムによって正しく解決されるようにすることです。

## 技術的詳細

このコミットの主要な変更点は、`Package`構造体に`vendored`という新しいメソッドを導入し、`_test.go`ファイル内のインポートパスをベンダーパスに解決するロジックを集中させたことです。

以前は、`list.go`や`test.go`内で個別に`vendoredImportPath`関数を呼び出して`TestImports`や`XTestImports`のパスを解決しようとしていました。しかし、このアプローチでは、テストインポートが通常のインポートとは異なるライフサイクルで処理されるため、ベンダーパスの解決が不完全または不正確になるケースがありました。

新しい`Package.vendored`メソッドは、以下の役割を担います。

1.  **遅延解決**: `p.TestImports`や`p.XTestImports`は、パッケージの初期ロード時にはベンダー解決されません。これは、ファイルシステムへのアクセスを避け、また`go test`実行時に元のパスからエラーメッセージを生成できるようにするためです。`vendored`メソッドは、これらのインポートパスが必要になったときに初めてベンダー解決を行います。
2.  **一貫した解決**: `vendoredImportPath(p, path)`関数を使用して、与えられたパッケージ`p`のコンテキストでインポートパス`path`をベンダー解決します。これにより、`vendor`ディレクトリ内の正しいパッケージが参照されるようになります。
3.  **重複排除とソート**: 解決されたインポートパスのリストから重複を排除し、アルファベット順にソートして返します。
4.  **安全チェック**: `p.vendored(p.Imports)`が誤って呼び出されないようにパニックを発生させるチェックが含まれています。これは、`p.Imports`はパッケージの初期ロード時に既にベンダー解決されているため、二重に処理する必要がないことを示しています。

この`vendored`メソッドが導入されたことで、`list.go`や`test.go`のような`_test.go`ファイルのインポートパスを扱う箇所では、直接`vendoredImportPath`を呼び出す代わりに、`p.vendored(p.TestImports)`や`p.vendored(p.XTestImports)`を呼び出すように変更されました。これにより、ベンダーパス解決のロジックが一元化され、テストインポートの取り扱いがより堅牢になりました。

## コアとなるコードの解説

このコミットの核心は、`src/cmd/go/pkg.go`に追加された`Package.vendored`メソッドです。

```go
func (p *Package) vendored(imports []string) []string {
	// p.Importsが誤って渡されないようにするための安全チェック
	if len(imports) > 0 && len(p.Imports) > 0 && &imports[0] == &p.Imports[0] {
		panic("internal error: p.vendored(p.Imports) called")
	}
	
	seen := make(map[string]bool) // 重複排除のためのマップ
	var all []string             // 解決されたインポートパスを格納するスライス
	
	for _, path := range imports {
		// vendoredImportPath関数を使って、各インポートパスをベンダー解決
		path, _ = vendoredImportPath(p, path) 
		if !seen[path] { // 重複がなければ追加
			seen[path] = true
			all = append(all, path)
		}
	}
	sort.Strings(all) // 結果をソート
	return all
}
```

このメソッドは、`_test.go`ファイルから読み込まれた生のインポートパス（`p.TestImports`や`p.XTestImports`）を受け取り、それらを現在のパッケージ`p`のコンテキストでベンダー解決します。

*   `vendoredImportPath(p, path)`: この内部関数が、実際に`path`が`p`の`vendor`ディレクトリ内に存在するかどうかを判断し、存在する場合はベンダー解決されたパス（例: `example.com/foo/vendor/bar`ではなく`bar`）を返します。
*   遅延解決の理由: `_test.go`ファイル内のインポートは、通常のパッケージインポートとは異なり、パッケージの初期ロード時にすぐにベンダー解決されません。これは、`go test`コマンドがテストを実行する際に、元のインポートパスからより適切なエラーメッセージを生成できるという利点があるためです。また、不要なファイルシステムアクセスを避ける目的もあります。
*   `list.go`と`test.go`での利用: この`vendored`メソッドを呼び出すことで、`go list`コマンドはベンダー解決されたテストインポートパスを正確に表示し、`go test`コマンドはテストのビルド時にベンダーされた依存関係を正しくリンクできるようになります。

この変更により、Goのベンダーメカニズムが`_test.go`ファイルに対しても完全に機能するようになり、ベンダーを使用するプロジェクトでのテストの信頼性と再現性が向上しました。

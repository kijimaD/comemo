# [インデックス 25688] ファイルの概要

## 変更の背景

この変更は、ARM64アーキテクチャにおけるシステムリンカの既知のバグに対応するために導入されました。具体的には、2015年5月以前のシステムリンカでは、`R_AARCH64_ADR_GOT_PAGE`リロケーションがローカルシンボルに対して適用された場合に不具合が発生するという問題がありました（Sourceware Bugzilla 18270）。

Go言語のリンカは、動的リンクをサポートするために、関数シンボルに対するリロケーションをローカルシンボルに対するものとして処理することがあります（`putelfsym`関数を参照）。しかし、このシステムリンカのバグにより、Goリンカが生成するコードが正しくリンクされない可能性がありました。

このコミットは、この特定のバグを回避するために、Goリンカが`R_ARM64_GOTPCREL`リロケーションを処理する方法を変更します。これにより、バグのあるシステムリンカでもGoプログラムが正しく動作するようにします。

## 前提知識の解説

### リンカとリロケーション

*   **リンカ**: コンパイラによって生成されたオブジェクトファイル（機械語コードとデータ）を結合し、実行可能ファイルや共有ライブラリを生成するプログラムです。リンカの主な役割の一つは、プログラム内のシンボル（変数や関数の名前）が参照するアドレスを解決することです。
*   **リロケーション**: プログラムがメモリ上のどこにロードされるかに関わらず、正しく実行できるように、コード内のアドレス参照を調整するプロセスです。特に共有ライブラリでは、ロードされるアドレスが実行時まで分からないため、リロケーションが不可欠です。リロケーションエントリは、リンカに対して、特定のアドレスをどのように修正すべきかを指示します。

### GOT (Global Offset Table)

*   **GOT (Global Offset Table)**: 共有ライブラリを使用する際に、外部シンボル（他の共有ライブラリや実行可能ファイルで定義されている関数や変数）へのアクセスを仲介するために使用されるデータ構造です。
*   **PIC (Position-Independent Code)**: 共有ライブラリは、メモリ上の任意のアドレスにロードされても正しく動作するように設計されている必要があります。これを実現するために、コードは絶対アドレスではなく、PC (Program Counter) 相対アドレスやGOTを介した間接参照を使用します。GOTは、外部シンボルの実際のアドレスを格納し、実行時にダイナミックリンカによって更新されます。これにより、コード自体を変更することなく、外部シンボルにアクセスできます。

### ARM64アーキテクチャの命令とアドレス指定

ARM64 (AArch64) アーキテクチャでは、命令が32ビット固定長であるため、単一の命令で64ビットのアドレスを直接エンコードすることはできません。そのため、64ビットアドレスをロードするには、通常、複数の命令シーケンスが使用されます。

*   **`ADRP` (Address Page Relative)**: この命令は、現在のPC (Program Counter) を基準として、4KBページのアドレスを計算し、レジスタにロードします。21ビットの符号付き即値を取り、これを12ビット左シフトしてPCに加算します。これにより、目的の4KBページのベースアドレスが得られます。
*   **`ADD` / `LDR` (Load Register)**: `ADRP`命令で得られたページベースアドレスに、そのページ内のオフセットを加算（`ADD`）したり、そのアドレスからデータをロード（`LDR`）したりすることで、完全な64ビットアドレスを構築します。

### ARM64リロケーションタイプ

ELF (Executable and Linkable Format) 形式では、特定のリロケーションタイプが定義されており、リンカはこれらに従ってアドレスを修正します。

*   **`R_AARCH64_ADR_GOT_PAGE`**: `ADRP`命令の即値フィールドを、ターゲットシンボルのGOTエントリを含む4KBページのベースアドレスに設定するようリンカに指示します。
*   **`R_AARCH64_LD64_GOT_LO12_NC` (および類似)**: `ADRP`に続く`LDR`または`ADD`命令の即値フィールドを、GOTエントリのページ内オフセット（下位12ビット）に設定するようリンカに指示します。これにより、`ADRP`と組み合わせてGOTエントリの完全な64ビットアドレスをロードできます。
*   **`R_ARM64_GOTPCREL`**: これは特定のリロケーションタイプというよりは、GOTへのPC相対アクセスを指す一般的な概念です。通常、`ADRP`と`LDR`の組み合わせによって実現されます。

## 技術的詳細

このコミットは、`src/cmd/link/internal/arm64/asm.go`ファイル内の`archreloc`関数を変更し、`obj.R_ARM64_GOTPCREL`リロケーションの処理に特別なロジックを追加します。

Goリンカは、動的リンクが有効な場合（`ld.DynlinkingGo()`）、関数シンボルに対する`R_ARM64_GOTPCREL`リロケーションを検出すると、システムリンカのバグを回避するためにその動作を変更します。

具体的には、以下の条件が満たされた場合にこのワークアラウンドが適用されます。

1.  リロケーションが関数シンボルに対して行われている（`r.Sym.Type == obj.STEXT`）。
2.  シンボルがローカルではない、かつ隠されていない（`!(r.Sym.Version != 0 || (r.Sym.Type&obj.SHIDDEN != 0) || r.Sym.Local)`）。これは、外部から参照される可能性のある関数シンボルを指します。
3.  動的リンクが有効である（`ld.DynlinkingGo()`）。

この条件が満たされた場合、Goリンカは以下の変換を行います。

*   **命令の変換**:
    *   元の命令シーケンスは、通常 `adrp; ld64` の形式で、`R_ARM64_GOTPCREL`リロケーションが`ld64`命令に適用されます。
    *   Goリンカは、`ld64`命令（`0xf9400000`で始まる命令）を`add`命令（`0x91000000`で始まる命令）に変換します。具体的には、`o2`（命令の下位32ビット）のビットマスク`0xffc00000`が`0xf9400000`でない場合、予期しない命令であるとして診断メッセージを出力します。その後、`o2`を`0x91000000 | (o2 & 0x000003ff)`に変換します。これは、`ld64`命令のオペコード部分を`add`命令のオペコードに置き換え、オフセット部分（下位10ビット）を保持する操作です。
*   **リロケーションタイプの変更**:
    *   リロケーションタイプを`obj.R_ARM64_GOTPCREL`から`obj.R_ADDRARM64`に変更します。`obj.R_ADDRARM64`は、絶対アドレスへのリロケーションを意味し、`adrp; add`シーケンスと組み合わせて使用されます。

この変換により、バグのあるシステムリンカが`R_AARCH64_ADR_GOT_PAGE`リロケーションをローカルシンボルに対して処理する際に発生する問題を回避し、代わりに`adrp; add`シーケンスと`R_ADDRARM64`リロケーションを使用することで、Goリンカが生成するバイナリが正しくリンクされるようになります。

また、`val`のビット操作は、64ビットの値を2つの32ビット値（`o1`, `o2`）に分割し、エンディアン（バイト順序）に応じて適切に処理するためのものです。これは、ARM64命令が32ビットであるため、64ビットのアドレスやオフセットを命令に埋め込む際に必要となる処理です。

## コアとなるコードの変更箇所

変更は`src/cmd/link/internal/arm64/asm.go`ファイルの`archreloc`関数内で行われています。

```diff
--- a/src/cmd/link/internal/arm64/asm.go
+++ b/src/cmd/link/internal/arm64/asm.go
@@ -241,8 +241,38 @@ func archreloc(r *ld.Reloc, s *ld.LSym, val *int64) int {
 		default:
 			return -1
 
-		case obj.R_ADDRARM64,
-			obj.R_ARM64_GOTPCREL:
+		case obj.R_ARM64_GOTPCREL:
+			var o1, o2 uint32
+			if ld.Ctxt.Arch.ByteOrder == binary.BigEndian {
+				o1 = uint32(*val >> 32)
+				o2 = uint32(*val)
+			} else {
+				o1 = uint32(*val)
+				o2 = uint32(*val >> 32)
+			}
+			// Any relocation against a function symbol is redirected to
+			// be against a local symbol instead (see putelfsym in
+			// symtab.go) but unfortunately the system linker was buggy
+			// when confronted with a R_AARCH64_ADR_GOT_PAGE relocation
+			// against a local symbol until May 2015
+			// (https://sourceware.org/bugzilla/show_bug.cgi?id=18270). So
+			// we convert the adrp; ld64 + R_ARM64_GOTPCREL into adrp;
+			// add + R_ADDRARM64.
+			if !(r.Sym.Version != 0 || (r.Sym.Type&obj.SHIDDEN != 0) || r.Sym.Local) && r.Sym.Type == obj.STEXT && ld.DynlinkingGo() {
+				if o2&0xffc00000 != 0xf9400000 {
+					ld.Ctxt.Diag("R_ARM64_GOTPCREL against unexpected instruction %x", o2)
+				}
+				o2 = 0x91000000 | (o2 & 0x000003ff)
+				r.Type = obj.R_ADDRARM64
+			}
+			if ld.Ctxt.Arch.ByteOrder == binary.BigEndian {
+				*val = int64(o1)<<32 | int64(o2)
+			} else {
+				*val = int64(o2)<<32 | int64(o1)
+			}
+			fallthrough
+
+		case obj.R_ADDRARM64:
 			r.Done = 0
 
 			// set up addend for eventual relocation via outer symbol.
```

## コアとなるコードの解説

*   **`case obj.R_ARM64_GOTPCREL:` ブロックの追加**:
    *   以前は`obj.R_ADDRARM64`と`obj.R_ARM64_GOTPCREL`が同じ`case`で処理されていましたが、このコミットで`obj.R_ARM64_GOTPCREL`が独立した`case`として追加されました。
    *   `var o1, o2 uint32`: 64ビットの`val`を2つの32ビット値に分割するための変数です。
    *   `if ld.Ctxt.Arch.ByteOrder == binary.BigEndian { ... } else { ... }`: システムのエンディアン（ビッグエンディアンまたはリトルエンディアン）に応じて、`val`の上位32ビットと下位32ビットを`o1`と`o2`に適切に割り当てます。
    *   **コメント**: システムリンカのバグ（Sourceware Bugzilla 18270）について説明し、`adrp; ld64 + R_ARM64_GOTPCREL`を`adrp; add + R_ADDRARM64`に変換する意図を述べています。
    *   `if !(r.Sym.Version != 0 || (r.Sym.Type&obj.SHIDDEN != 0) || r.Sym.Local) && r.Sym.Type == obj.STEXT && ld.DynlinkingGo() { ... }`:
        *   この条件は、リロケーションが外部から参照される可能性のある関数シンボル（`obj.STEXT`）に対して行われ、かつ動的リンクが有効な場合に真となります。
        *   `r.Sym.Version != 0 || (r.Sym.Type&obj.SHIDDEN != 0) || r.Sym.Local`: シンボルがバージョン付きであるか、隠されているか、ローカルであるかを確認します。`!`で否定されているため、これらのいずれでもない（つまり、外部から参照可能なグローバルシンボル）場合に処理が実行されます。
        *   `r.Sym.Type == obj.STEXT`: シンボルがテキストセクション（関数）であることを確認します。
        *   `ld.DynlinkingGo()`: Goの動的リンクが有効になっているかを確認します。
    *   `if o2&0xffc00000 != 0xf9400000 { ... }`:
        *   `o2`は命令の下位32ビットを表します。`0xf9400000`は`ld64`命令のオペコードの一部です。このチェックは、`R_ARM64_GOTPCREL`が予期される`ld64`命令に対して適用されているかを確認します。もし異なる命令であれば、診断メッセージを出力します。
    *   `o2 = 0x91000000 | (o2 & 0x000003ff)`:
        *   `0x91000000`は`add`命令のオペコードの一部です。
        *   `o2 & 0x000003ff`は、元の`ld64`命令の下位10ビット（オフセット部分）を抽出します。
        *   この行は、`ld64`命令のオペコードを`add`命令のオペコードに置き換え、元のオフセットを保持することで、命令を`ld64`から`add`に変換します。
    *   `r.Type = obj.R_ADDRARM64`: リロケーションタイプを`obj.R_ARM64_GOTPCREL`から`obj.R_ADDRARM64`に変更します。
    *   `if ld.Ctxt.Arch.ByteOrder == binary.BigEndian { ... } else { ... }`: 変更された`o1`と`o2`を再び64ビットの`*val`に結合します。
    *   `fallthrough`: このキーワードにより、処理は次の`case obj.R_ADDRARM64:`ブロックに続行されます。これは、`R_ARM64_GOTPCREL`が`R_ADDRARM64`に変換された後、`R_ADDRARM64`として通常のリロケーション処理を継続する必要があるためです。

*   **`case obj.R_ADDRARM64:` ブロック**:
    *   `r.Done = 0`: リロケーションがまだ完了していないことを示します。
    *   `// set up addend for eventual relocation via outer symbol.`: 外部シンボルを介した最終的なリロケーションのためのアデンド（加算値）を設定するコメントです。

この変更により、GoリンカはARM64アーキテクチャで動的リンクを使用する際に、特定のシステムリンカのバグを回避し、生成されるバイナリの互換性と信頼性を向上させています。

## 変更の背景

このコミットは、Go言語の`os/exec`パッケージにおける`Cmd.WaitContext`関数が、`context.Context`がキャンセルされた際にゴルーチンを適切に終了させない可能性があった問題を修正します。この問題は、Goの変数シャドーイングという言語機能の誤用によって引き起こされていました。

`os/exec`パッケージは外部コマンドを実行し、そのライフサイクルを管理するために使用されます。`Cmd.WaitContext()`は、子プロセスの終了を待機し、そのリソース（Unix系システムにおけるゾンビプロセスなど）を適切に解放するために不可欠なメソッドです。このメソッドが呼び出されない場合、子プロセスは「ゾンビ」となり、リソースが完全に解放されず、時間とともにリソース枯渇につながる可能性があります。

元のコードでは、`waitDone`というチャネルが二重に宣言され、内部スコープで新しいローカル変数としてシャドーイングされていました。これにより、`context.Context`のキャンセルを監視するゴルーチンが、外部スコープで宣言された本来の`waitDone`チャネルではなく、内部スコープの`waitDone`チャネルを操作していました。結果として、外部の`waitDone`チャネルは適切にシグナルを受け取ることができず、`WaitContext`関数が無限にブロックし、ゴルーチンリークを引き起こす可能性がありました。

この修正は、この変数シャドーイングの問題を解消し、`context.Context`のキャンセルが正しく処理され、ゴルーチンが適切に終了するようにすることで、リソースリークを防ぎます。

## 前提知識の解説

このコミットの理解には、以下のGo言語の概念と`os/exec`パッケージの動作に関する知識が不可欠です。

1.  **Goの`os/exec`パッケージ**:
    *   `os/exec`パッケージは、外部コマンドを実行するための機能を提供します。`exec.Command`関数でコマンドを構築し、`Start()`で実行を開始し、`Wait()`または`WaitContext()`でコマンドの完了を待機します。
    *   `Cmd.Wait()`: 外部コマンドの実行が完了するまでブロックし、その終了ステータスを返します。
    *   `Cmd.WaitContext(ctx context.Context)`: `Wait()`と同様ですが、`context.Context`を受け取ります。コンテキストがキャンセルされると、子プロセスにシグナルを送信して終了させようとします。ただし、コンテキストがキャンセルされた後も、子プロセスのリソースを完全に解放するためには`WaitContext()`の呼び出しが必要です。

2.  **`context.Context`**:
    *   `context.Context`は、API境界を越えてデッドライン、キャンセルシグナル、およびその他のリクエストスコープの値を伝播するためのGoの標準的なメカニズムです。
    *   `ctx.Done()`チャネルは、コンテキストがキャンセルされたり、デッドラインに達したりすると閉じられます。これにより、複数のゴルーチンが協調的に作業を停止できます。
    *   `context.WithCancel`や`context.WithTimeout`などで作成されたコンテキストには、対応する`cancel`関数があり、これを呼び出すことでコンテキストをキャンセルできます。通常、`defer cancel()`を使ってリソースを確実に解放します。

3.  **ゴルーチンリーク (Goroutine Leak)**:
    *   ゴルーチンリークは、開始されたゴルーチンが何らかの理由で終了せず、メモリやCPUリソースを消費し続ける状態を指します。これは、チャネルからの読み取りが永久にブロックされたり、無限ループに陥ったり、親ゴルーチンが子ゴルーチンの完了を待たずに終了したりする場合に発生します。
    *   リークしたゴルーチンは、プログラムのパフォーマンス低下やメモリ不足を引き起こす可能性があります。

4.  **変数シャドーイング (Variable Shadowing)**:
    *   変数シャドーイングは、内部スコープで外部スコープの変数と同じ名前の新しい変数を宣言する際に発生します。Goでは、`:=` (ショート変数宣言) 演算子が新しい変数を宣言するため、意図せずシャドーイングを引き起こすことがあります。
    *   例:
        ```go
        var x int = 10
        if true {
            x := 20 // ここで新しい 'x' が宣言され、外部の 'x' をシャドーイングする
            fmt.Println(x) // 20
        }
        fmt.Println(x) // 10
        ```
    *   シャドーイング自体は必ずしもバグではありませんが、特にクロージャや並行処理の文脈では、意図しない動作やバグ（今回のゴルーチンリークのように）につながる可能性があります。既存の変数に値を代入する場合は、`=`演算子を使用する必要があります。

## 技術的詳細

このコミットの核心は、`src/os/exec/exec.go`内の`Cmd.WaitContext`関数における`waitDone`チャネルの初期化方法の変更です。

元のコードは以下のようになっていました。

```go
func (c *Cmd) WaitContext(ctx context.Context) error {
    // ...
    var waitDone chan struct{} // (A) 外部スコープで waitDone を宣言
    if ctx != nil {
        waitDone := make(chan struct{}) // (B) 内部スコープで新しい waitDone を宣言し、外部の waitDone をシャドーイング
        go func() {
            select {
            case <-ctx.Done():
                // ...
            case <-waitDone: // (C) このゴルーチンは内部スコープの waitDone を待機
                // ...
            }
        }()
        // ...
    }
    // ...
    // 外部スコープの waitDone は make されていないため、nil のまま
    // ...
}
```

このコードの問題点は以下の通りです。

1.  **変数シャドーイング**: `(A)`で`waitDone`が`chan struct{}`型として宣言されますが、これは初期値が`nil`チャネルです。その後、`if ctx != nil`ブロック内で`(B)`の`waitDone := make(chan struct{})`が実行されます。Goの`:=`演算子は新しい変数を宣言するため、これは`if`ブロックのローカルスコープで新しい`waitDone`チャネルを作成し、外部スコープの`waitDone`をシャドーイングします。
2.  **ゴルーチンとチャネルの不整合**: `(C)`で起動されるゴルーチンは、`if`ブロック内で定義されているため、そのスコープ内の`waitDone`（つまり、`(B)`で`make`された新しいチャネル）をクロージャとしてキャプチャします。このゴルーチンは、この内部の`waitDone`チャネルが閉じられるのを待機します。
3.  **リークの原因**: しかし、`if`ブロックの外側、つまり`Cmd.WaitContext`関数の残りの部分では、依然として`(A)`で宣言された`nil`の`waitDone`チャネルを参照しています。この外部の`waitDone`チャネルは決して`make`されることも、閉じられることもありません。もし`WaitContext`関数が、この外部の`waitDone`チャネルを介してゴルーチンにシグナルを送ることを期待していた場合、そのシグナルは決して届かず、ゴルーチンは`<-waitDone`で永久にブロックされ、ゴルーチンリークを引き起こします。

修正後のコードは以下の通りです。

```go
func (c *Cmd) WaitContext(ctx context.Context) error {
    // ...
    var waitDone chan struct{} // (A) 外部スコープで waitDone を宣言
    if ctx != nil {
        waitDone = make(chan struct{}) // (B') 外部スコープの waitDone にチャネルを代入
        go func() {
            select {
            case <-ctx.Done():
                // ...
            case <-waitDone: // (C) このゴルーチンは外部スコープの waitDone を待機
                // ...
            }
        }()
        // ...
    }
    // ...
    // 外部スコープの waitDone は make されているため、適切に利用可能
    // ...
}
```

変更点`(B')`では、`waitDone := make(chan struct{})`が`waitDone = make(chan struct{})`に変更されています。これにより、`if`ブロック内で新しいローカル変数`waitDone`が宣言されるのではなく、`(A)`で宣言された**既存の外部スコープの`waitDone`変数に、新しく作成されたチャネルが代入されます**。

この修正により、`if`ブロック内で起動されるゴルーチンも、`Cmd.WaitContext`関数の残りの部分も、同じ`waitDone`チャネルを参照するようになります。これにより、`context.Context`のキャンセルやコマンドの完了に応じて、`waitDone`チャネルが適切に閉じられ、ゴルーチンがブロックされずに終了することが保証され、ゴルーチンリークが防止されます。

## コアとなるコードの解説

この一行の変更は、Go言語における変数宣言と代入のセマンティクス、特に`:=`と`=`の違いが、並行処理の文脈でいかに重要であるかを示しています。

*   **変更前 (`waitDone := make(chan struct{})`)**:
    *   `if ctx != nil`ブロック内で、`waitDone`という名前の**新しいローカル変数**が宣言され、`make(chan struct{})`によって初期化されます。
    *   この新しいローカル変数`waitDone`は、その外側（`Cmd.WaitContext`関数スコープ）で既に`var waitDone chan struct{}`として宣言されていた`waitDone`変数を**シャドーイング**します。
    *   `go func()`で起動されるゴルーチンは、この`if`ブロック内のローカルな`waitDone`チャネルをクロージャとしてキャプチャし、そのチャネルからのシグナルを待ちます。
    *   しかし、`if`ブロックの外側にある`Cmd.WaitContext`関数の残りのロジックは、依然としてシャドーイングされた**外部の`waitDone`変数**を参照します。この外部の`waitDone`は`nil`チャネルのままであり、決して`make`されることも、閉じられることもありません。
    *   結果として、ゴルーチンが待機しているチャネルと、関数が操作しようとしているチャネルが異なるため、ゴルーチンは外部からのシグナルを受け取ることができず、永久にブロックされ、ゴルーチンリークが発生します。

*   **変更後 (`waitDone = make(chan struct{})`)**:
    *   `if ctx != nil`ブロック内で、`waitDone`という名前の**新しい変数は宣言されません**。
    *   代わりに、`=`演算子によって、`Cmd.WaitContext`関数スコープの先頭で`var waitDone chan struct{}`として宣言されていた**既存の`waitDone`変数に、新しく作成されたチャネルが代入されます**。
    *   これにより、`if`ブロック内で起動されるゴルーチンも、`Cmd.WaitContext`関数の残りのロジックも、**同じ`waitDone`チャネル**を参照するようになります。
    *   `context.Context`がキャンセルされたり、外部コマンドが終了したりした際に、この共有された`waitDone`チャネルが適切に閉じられることで、ゴルーチンはブロックされずに終了し、ゴルーチンリークが防止されます。

この修正は、Goの`:=`演算子が常に新しい変数を宣言するという挙動を深く理解し、意図しないシャドーイングを避けることの重要性を示しています。特に、クロージャが外部変数をキャプチャするような並行処理のシナリオでは、この種のバグは発見が困難であり、システムのリソース枯渇につながる可能性があります。

# [インデックス 21805] ファイルの概要

このコミットは、Go言語のツールチェイン（コンパイラ、アセンブラ、リンカ）をC言語からGo言語自身で書き換えるという、Go 1.5リリースにおける画期的な取り組みの一環として、`master`ブランチの変更を`dev.cc`ブランチにマージしたものです。特に、リンカの一部である`liblink`の内部表現をシリアライズし、Go言語で書かれたルーチンがプログラムのレイアウトを処理できるようにするための基盤が導入されています。これにより、C言語からGo言語への段階的な移行がサポートされ、Goツールチェインの自己ホスト化と簡素化が推進されました。

## 元コミット内容

このコミットはマージコミットであり、`master`ブランチ（ハッシュ`b8fcae0`）の変更を`dev.cc`ブランチに取り込んでいます。コミットメッセージ自体は簡潔ですが、その背後にはGo 1.5の主要な変更点であるツールチェインのCからGoへの書き換えという大規模なプロジェクトが含まれています。

## 変更の背景

Go言語は当初、コンパイラやランタイムの一部にC言語を使用していました。これは、初期のGo開発を迅速に進める上で有効な手段でしたが、いくつかの課題も抱えていました。

1.  **Cコンパイラへの依存:** Goのビルドには、内部的にCコンパイラ（Plan 9 Cコンパイラをベースとしたもの）が必要でした。これにより、ツールチェインが複雑になり、クロスコンパイル環境のセットアップが難しくなることがありました。
2.  **スタック管理の複雑さ:** GoのランタイムがC言語で書かれている部分があるため、Goのゴルーチンスタック管理（特にスタックの動的な拡張）が複雑になることがありました。Cコードがゴルーチンのコールスタック上に存在する場合、より効率的な「コピーイングスタック」ではなく、古い「スプリットスタック」方式にフォールバックする必要があるケースがありました。
3.  **自己ホスト化の目標:** Go言語の究極的な目標の一つは、Go言語自身でGoコンパイラとランタイムを完全にビルドできる「自己ホスト化」を実現することでした。これにより、Goの移植性と保守性が向上します。

これらの課題を解決し、Go言語の成熟度を高めるため、Go 1.5リリースではツールチェイン全体をCからGoへ書き換えるという大規模なプロジェクトが実施されました。このコミットは、その移行プロセスの一部であり、特にリンカ（`liblink`）のGo言語化に向けた基盤整備を含んでいます。

## 前提知識の解説

### Goツールチェインの構成要素

*   **コンパイラ (gc):** Goソースコードをアセンブリコードに変換します。Go 1.5以前はC言語で書かれていました。
*   **アセンブラ (go tool asm):** アセンブリコードをオブジェクトファイルに変換します。
*   **リンカ (go tool link):** オブジェクトファイルを結合し、実行可能ファイルを生成します。Go 1.5以前は`liblink`というC言語ライブラリが中心でした。
*   **ランタイム:** ゴルーチン、スケジューラ、ガベージコレクションなど、Goプログラムの実行を管理する部分です。一部がC言語で書かれていました。

### Go 1.5におけるCからGoへの移行

Go 1.5の最大の変更点の一つは、Goツールチェイン（コンパイラ、アセンブラ、リンカ）とランタイムの大部分をC言語からGo言語に書き換えたことです。この移行は段階的に行われ、本コミットはその初期段階、特にリンカのGo言語化の準備として重要な役割を果たしています。

### リンカの役割と内部表現

リンカは、コンパイラやアセンブラによって生成された複数のオブジェクトファイル（機械語コードとデータを含む）を結合し、最終的な実行可能ファイルを生成します。この過程で、シンボル解決（関数や変数のアドレスを決定する）、再配置（アドレス依存のコードを修正する）、セクションの結合などを行います。

リンカは、プログラムの構造を内部的に表現するために、`Prog`（プログラム命令）、`LSym`（リンカシンボル）、`Addr`（アドレス）などのデータ構造を使用します。これらの構造体は、命令の種類、オペランド、シンボルへの参照、アドレス情報などを保持します。

## 技術的詳細

このマージコミットは、GoツールチェインのCからGoへの移行、特にリンカ（`liblink`）のGo言語化に向けた重要なステップです。

`src/liblink/objfilego.c`の追加は、リンカの内部表現をシリアライズし、Go言語で書かれた新しいリンカ部分がそのデータを読み取って処理できるようにするためのものです。このファイルは、C言語で書かれたリンカのデータ構造（`Link`コンテキスト、`Plist`、`LSym`、`Prog`、`Addr`、`Hist`など）をバイナリ形式で出力する関数群を提供します。これにより、C言語のリンカとGo言語のリンカが連携し、段階的にCコードをGoコードに置き換えることが可能になります。コメントにも明記されている通り、「このシリアライズ形式とコードは、CからGoへの段階的な移行をサポートし、不要になった時点で残りのCコードと共に削除される予定」でした。

`include/link.h`の変更は、リンカの内部データ構造である`Prog`構造体に対するものです。特に、`comefrom`、`pcrel`、`optab`、`back`、`ft`、`tt`、`isize`といったフィールドのコメントが、特定のアーキテクチャ（例: `6l, 8l`から`amd64, 386`へ）に限定されていたものが、より一般的な`liblink internal use`や、具体的なアーキテクチャ名（`amd64, 386`, `arm`, `ppc64`）に修正されています。また、`printed`という新しい`uchar`フィールドが追加されており、これは`objfilego.c`でリンカのデータ構造をシリアライズする際に、既に処理済みかどうかを追跡するために使用されます。これにより、無限ループを防ぎ、データ構造のグラフを正しくトラバースできます。

`src/cmd/go/build.go`の変更は、`go tool asm`コマンドの動作に関連しています。特に注目すべきは、`verifyAsm`という新しいロジックが追加されている点です。これは、通常のアセンブラ（`archChar + "a"`）と新しいアセンブラ（`new" + archChar + "a"`）の両方でアセンブリファイルを処理し、生成されたオブジェクトファイルがバイト単位で一致するかどうかを検証するものです。これは、新しいGo言語で書かれたアセンブラが、既存のC言語で書かれたアセンブラと完全に互換性があることを保証するためのテストメカニズムとして導入されました。この検証ステップは、ツールチェインのCからGoへの移行における品質保証の重要な部分です。

全体として、このコミットは、Go 1.5におけるツールチェインの自己ホスト化という大きな目標に向けた、リンカのGo言語化の基盤構築と、その品質を保証するための検証メカニズムの導入を意味します。

## コアとなるコードの変更箇所

このコミットはマージコミットであり、多数のファイルにわたる変更を含んでいます。特に重要な変更は以下のファイルに見られます。

1.  **`src/liblink/objfilego.c`**:
    *   このファイルが新規追加されています。
    *   リンカの内部データ構造をシリアライズするためのC言語関数群が含まれています。
    *   `writeobjgo1`と`writeobjgo2`関数が、リンカのコンテキスト、シンボル、プログラム命令、アドレスなどの情報をバイナリ形式で出力します。
    *   `printtype`, `printint`, `printstr`, `printptr`, `printsym`, `printprog`, `printaddr`, `printhist`といったヘルパー関数が定義され、各データ型のシリアライズを担当します。

2.  **`include/link.h`**:
    *   `Prog`構造体に`printed`フィールド（`uchar`型）が追加されました。
    *   `Prog`構造体内の既存フィールド（`comefrom`, `pcrel`, `optab`, `back`, `ft`, `tt`, `isize`）のコメントが更新され、より具体的なアーキテクチャや`liblink`内部使用を示すようになりました。
    *   `TYPE_BRANCH`, `TYPE_FCONST`, `TYPE_SCONST`, `TYPE_TEXTSIZE`といったマクロが導入され、`ctxt->arch->D_BRANCH`のようなアーキテクチャ依存の定数参照を置き換えています。これは、リンカのコードをより汎用的にし、Go言語への移行を容易にするための抽象化の一環です。

3.  **`src/cmd/go/build.go`**:
    *   `gcToolchain.asm`関数内に`verifyAsm`という新しいロジックが追加されました。
    *   このロジックは、通常のアセンブラ（`archChar + "a"`）と新しいアセンブラ（`new" + archChar + "a"`）の両方で生成されたオブジェクトファイルを比較し、バイト単位で一致するかどうかを検証します。
    *   不一致の場合にはエラーを報告します。

## コアとなるコードの解説

### `src/liblink/objfilego.c`

このファイルは、C言語で書かれたリンカの内部状態をGo言語で書かれたリンカの新しい部分に「引き渡す」ためのブリッジとして機能します。リンカのデータ構造は複雑なグラフ構造をしており、ポインタが多用されています。`objfilego.c`内の`printsym`, `printprog`, `printaddr`などの関数は、これらのポインタを数値としてシリアライズし、各データ構造のフィールドを特定の順序でバイナリストリームに書き出します。

例えば、`printsym`関数は`LSym`（リンカシンボル）構造体の各フィールド（名前、外部名、型、バージョン、値、サイズ、関連するポインタなど）を順次書き出します。特に重要なのは、ポインタフィールド（例: `s->hash`, `s->allsym`, `s->next`など）も数値として書き出される点です。これにより、Go言語側でこのバイナリデータを読み込み、対応するGoのデータ構造を再構築する際に、ポインタの参照関係を正しく再現できるようになります。

`printed`フィールドの導入は、グラフ構造のシリアライズにおいて非常に重要です。リンカのデータ構造は循環参照を含む可能性があるため、既にシリアライズ済みのノードを再度処理しないように`printed`フラグでマークすることで、無限ループを防ぎ、効率的なシリアライズを実現します。

### `include/link.h`の変更

`Prog`構造体への`printed`フィールドの追加は、`objfilego.c`でのシリアライズ処理をサポートするための直接的な変更です。これにより、リンカの命令リストをトラバースする際に、各命令が一度だけ処理されることが保証されます。

また、`TYPE_BRANCH`などのマクロによるアーキテクチャ依存の定数の抽象化は、リンカのコードベースをよりクリーンにし、将来的なGo言語への移行や、異なるアーキテクチャへの対応を容易にするための設計上の改善です。これは、C言語のコードをGo言語に移植する際に、アーキテクチャ固有のロジックをより適切に分離・管理するための準備とも言えます。

### `src/cmd/go/build.go`の`verifyAsm`ロジック

この変更は、GoツールチェインのCからGoへの移行における「信頼性」を確保するためのものです。新しいGo言語で書かれたアセンブラが、既存のC言語で書かれたアセンブラと完全に同じ出力を生成することを保証することは、移行の成功にとって不可欠です。

`verifyAsm`は、同じ入力アセンブリファイルに対して、両方のアセンブラを実行し、生成されたオブジェクトファイルのバイト列を比較します。もし両者の出力が一致しない場合、それは新しいアセンブラにバグがあるか、互換性の問題があることを意味し、ビルドプロセスが失敗します。この厳格な検証ステップにより、開発者は安心して新しいGo言語のアセンブラに移行でき、既存のGoプログラムの動作に影響がないことを確認できます。これは、大規模なリファクタリングや言語実装の変更において、後方互換性と安定性を維持するための優れたプラクティスです。

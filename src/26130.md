# [インデックス 26130] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) における、`go tool compile -pack` コマンドで生成されたアーカイブファイル (`.a`) が `package main` でない場合に、リンカがそれを正しく拒否しないというバグを修正するものです。同時に、Go 1.2以降機能していなかった古いエクスポートデータ解析コードを削除し、リンカのコードベースを簡素化しています。

## コミット

cmd/link: reject non-package main toplevel.a file, remove dead code

The test for non-package main top-level inputs is done while parsing
the export data. Issue #13468 happened because we were not parsing
the export data when using compiler-generated archives
(that is, when using go tool compile -pack).

Fix this by parsing the export data even for archives.

However, that turns up a different problem: the export data check
reports (one assumes spurious) skew errors now, because it has
not been run since Go 1.2.
(Go 1.3 was the first release to use go tool compile -pack.)

Since the code hasn't run since Go 1.2, it can't be that important.
Since it doesn't work today, just delete it.

Figuring out how to make this code work with Robert's export
format was one of the largest remaining TODOs for that format.
Now we don't have to.

Fixes #13468 and makes the world a better place.

## 変更の背景

このコミットは、主にGoリンカ (`cmd/link`) の二つの問題に対処しています。

1.  **Issue #13468の修正**: `go tool compile -pack` コマンドを使用してコンパイラが生成したアーカイブファイル (`.a`) をリンカが処理する際、そのアーカイブが `package main` でないにもかかわらず、リンカがエラーを発生させずにリンクを試みてしまう問題がありました。通常、実行可能ファイルを生成するためには、トップレベルのパッケージは `main` である必要があります。このチェックはエクスポートデータの解析中に行われるべきでしたが、`go tool compile -pack` で生成されたアーカイブの場合、エクスポートデータが適切に解析されていなかったため、このチェックが機能していませんでした。
2.  **デッドコードの削除とリンカの簡素化**: 上記の問題を修正するためにエクスポートデータを常に解析するように変更したところ、Go 1.2以降実行されていなかった古いエクスポートデータチェックコードが「skew errors」（データ形式の不一致によるエラー）を報告し始めました。このコードはGo 1.3で `go tool compile -pack` が導入されて以来、実質的に機能していなかったため、重要性が低いと判断されました。また、Robert Griesemer氏が導入した新しいエクスポートフォーマットに対応させるための大きなTODOリストの一つでもありました。この機能しない、かつ古いコードを削除することで、リンカのコードベースが簡素化され、将来的なメンテナンスコストが削減されました。

## 前提知識の解説

### Go言語のビルドプロセス
Go言語のプログラムは、通常 `go build` コマンドによってコンパイル・リンクされます。この裏側では、`go tool compile` と `go tool link` という低レベルなツールが使われています。
*   **`go tool compile`**: Goのソースコードをオブジェクトファイル (`.o`) やアーカイブファイル (`.a`) にコンパイルします。
    *   **`-pack` オプション**: このオプションを使用すると、コンパイラはコンパイル結果を直接アーカイブファイル (`.a`) にパックします。これは主にGoの標準ライブラリのビルドなどで使用されます。
*   **`go tool link`**: オブジェクトファイルやアーカイブファイルを結合し、実行可能ファイルを生成します。

### Goリンカ (`cmd/link`) の役割
Goリンカは、コンパイルされたGoのコード（オブジェクトファイルやアーカイブ）と、C言語で書かれたランタイムやライブラリ（Cgoを使用している場合）を結合し、最終的な実行可能ファイルを生成する役割を担います。この過程で、シンボルの解決、メモリレイアウトの決定、デバッグ情報の埋め込みなど、様々な処理を行います。

### Goのパッケージシステム
Go言語では、コードはパッケージに分割されます。
*   **`package main`**: 実行可能プログラムのエントリポイントとなるパッケージです。`main` 関数を含み、`go build` で実行可能ファイルが生成されます。
*   **その他のパッケージ**: ライブラリとして機能し、他のパッケージからインポートされて利用されます。これら単独では実行可能ファイルにはなりません。

リンカは、実行可能ファイルを生成する際に、トップレベルの入力が `package main` であることを確認する必要があります。

### エクスポートデータ (Export Data)
Goのコンパイラは、パッケージをコンパイルする際に、そのパッケージが外部に公開する型、変数、関数などの情報（エクスポートデータ）を生成します。このエクスポートデータは、そのパッケージをインポートする他のパッケージのコンパイル時に型チェックやシンボル解決のために利用されます。リンカも、パッケージ間の整合性を確認するためにこのエクスポートデータを利用することがあります。

### Go 1.2とGo 1.3の歴史的背景
*   **Go 1.2**: このコミットで削除されたエクスポートデータチェックコードが最後に機能していたバージョン。
*   **Go 1.3**: `go tool compile -pack` オプションが導入されたバージョン。この変更により、コンパイラが直接アーカイブを生成するようになり、リンカのエクスポートデータ解析パスに影響を与えました。また、Robert Griesemer氏によるエクスポートフォーマットの変更もこの時期に行われ、古い解析コードとの互換性が失われました。

## 技術的詳細

### `ldpkg` 関数の役割
`src/cmd/link/internal/ld/go.go` に存在する `ldpkg` 関数は、Goのパッケージデータ（主にアーカイブファイル内のエクスポートデータ）を読み込む主要な関数です。この関数は、パッケージ名、ファイル名、データの長さ、およびデータの種類を示す `whence` 引数（例: `Pkgdef` はパッケージ定義ファイル）を受け取ります。

### 削除されたエクスポートデータ解析コード
コミットメッセージが示唆するように、Go 1.2以降機能していなかったコードは、パッケージ間の型の一貫性をチェックするためのものでした。具体的には、以下の構造体と関数が削除されました。

*   **`type Import struct`**: インポートされたシンボルのプレフィックス（`type`, `var`, `func`, `const`）、名前、定義、ファイル名を保持する構造体。
*   **`var importmap = map[string]*Import{}`**: インポートされたシンボル情報を格納し、名前によるルックアップを可能にするマップ。
*   **`func lookupImport(name string) *Import`**: `importmap`からシンボル情報を検索または新規作成する関数。
*   **`func loadpkgdata(file string, pkg string, data string)`**: パッケージのエクスポートデータを解析し、`importmap`に格納する関数。この関数内で、異なるファイルからの同じシンボルの定義が衝突しないか、定義内容が一致するかといった一貫性チェックが行われていました。
*   **`func parsepkgdata(...)`**: `loadpkgdata`から呼び出され、エクスポートデータ文字列を解析して個々のシンボル情報（プレフィックス、名前、定義）を抽出する低レベルなパーサー。
*   **`func parsemethod(...)`**: `parsepkgdata`から呼び出され、型に付随するメソッド定義を解析する関数。

これらのコードは、Go 1.3で導入された `go tool compile -pack` と Robert Griesemer氏による新しいエクスポートフォーマットに対応できておらず、実質的にデッドコードとなっていました。リンカの進化に伴い、これらのチェックはより新しい、より堅牢なメカニズムに置き換えられたか、あるいはその重要性が低下したと考えられます。

### `ldpkg` 内の変更
`ldpkg` 関数内では、`__.PKGDEF` ファイル（Goのパッケージ定義を含むファイル）を処理する際に、エクスポートデータの読み込み長さを制限するロジックが追加されました。
```go
	// In a __.PKGDEF, we only care about the package name.
	// Don't read all the export data.
	if length > 1000 && whence == Pkgdef {
		length = 1000
	}
```
これは、`__.PKGDEF` からはパッケージ名のみが必要であり、完全なエクスポートデータを読み込む必要がないことを示唆しています。また、エクスポートデータの終端を示す `"\n$$\n"` が見つからない場合の処理も `Pkgdef` の場合に限り、データの最後までを終端と見なすように変更されました。

### `src/cmd/link/internal/ld/lib.go` の変更
`objfile` 関数内で `ldpkg` を呼び出す箇所で、`Debug['u'] != 0` という条件が削除されました。
変更前:
```go
	if Debug['u'] != 0 {
		ldpkg(f, pkg, atolwhex(arhdr.size), lib.File, Pkgdef)
	}
```
変更後:
```go
	ldpkg(f, pkg, atolwhex(arhdr.size), lib.File, Pkgdef)
```
これは、`ldpkg` の呼び出しがデバッグフラグに依存せず、常に実行されるようになったことを意味します。これにより、`go tool compile -pack` で生成されたアーカイブに対しても、`ldpkg` が常に呼び出され、その中でパッケージタイプチェック（`pkg == "main" && name != "main"` のチェック）が適切に行われるようになりました。

## コアとなるコードの変更箇所

### `src/cmd/link/internal/ld/go.go`
*   `import ("strconv")` の削除。
*   `type Import struct`, `var importmap`, `func lookupImport`, `func loadpkgdata`, `func parsepkgdata`, `func parsemethod` の定義と実装が全て削除されました。これは約200行以上のコードの削除に相当します。
*   `ldpkg` 関数内で、`__.PKGDEF` の場合にエクスポートデータの読み込み長さを制限するロジックが追加されました。
*   `ldpkg` 関数内で、`loadpkgdata` の呼び出しが削除されました。

### `src/cmd/link/internal/ld/lib.go`
*   `objfile` 関数内の `ldpkg` の呼び出しから、`if Debug['u'] != 0` という条件が削除され、`ldpkg` が常に実行されるようになりました。

### `test/linkmain.go` (新規追加)
```go
// +build ignore

// Copyright 2015 The Go Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

// For linkmain_run.go.

package notmain

func main() {
}
```
`package notmain` であるにもかかわらず `main` 関数を持つGoファイル。これは、リンカが `package main` でないアーカイブを正しく拒否するかどうかをテストするために使用されます。

### `test/linkmain_run.go` (新規追加)
```go
// +build !nacl
// run

// Copyright 2014 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

// Run the sinit test.

package main

import (
	"fmt"
	"os"
	"os/exec"
	"strings"
)

func cleanup() {
	os.Remove("linkmain.o")
	os.Remove("linkmain.a")
	os.Remove("linkmain1.o")
	os.Remove("linkmain1.a")
	os.Remove("linkmain.exe")
}

func run(cmdline string) {
	args := strings.Fields(cmdline)
	cmd := exec.Command(args[0], args[1:]...)
	out, err := cmd.CombinedOutput()
	if err != nil {
		fmt.Printf("$ %s\n", strings.Join(args, " "))
		fmt.Println(string(out))
		fmt.Println(err)
		cleanup()
		os.Exit(1)
	}
}

func runFail(args ...string) {
	cmd := exec.Command(args[0], args[1:]...)
	out, err := cmd.CombinedOutput()
	if err == nil {
		fmt.Printf("$ %s\n", strings.Join(args, " "))
		fmt.Println(string(out))
		fmt.Println("SHOULD HAVE FAILED!")
		cleanup()
		os.Exit(1)
	}
}

func main() {
	// helloworld.go is package main
	run("go tool compile -o linkmain.o helloworld.go")
	run("go tool compile -pack -o linkmain.a helloworld.go")
	run("go tool link -o linkmain.exe linkmain.o")
	run("go tool link -o linkmain.exe linkmain.a")

	// linkmain.go is not
	run("go tool compile -o linkmain.o linkmain.go")
	run("go tool compile -pack -o linkmain.a linkmain.go")
	runFail("go tool link -o linkmain.exe linkmain1.o")
	runFail("go tool link -o linkmain.exe linkmain1.a")
	cleanup()
}
```
リンカの挙動をテストするためのGoプログラム。
*   `run` 関数はコマンドを実行し、成功を期待します。
*   `runFail` 関数はコマンドを実行し、失敗を期待します。
*   `main` 関数では、まず `helloworld.go` (これは `package main` であると仮定) をコンパイル・リンクして成功することを確認します。
*   次に、新しく追加された `linkmain.go` (これは `package notmain` である) をコンパイルし、`go tool link` でリンクを試みます。この際、`runFail` を使用して、リンカが非 `package main` のアーカイブを拒否し、エラーを返すことを期待しています。

## コアとなるコードの解説

このコミットの核心は、Goリンカが `package main` でないトップレベルのアーカイブを正しく識別し、拒否する能力を回復させ、同時に不要になった古いコードを削除することにあります。

1.  **`src/cmd/link/internal/ld/lib.go` の変更**: `ldpkg` 関数の呼び出しが `Debug['u'] != 0` という条件から解放され、常に実行されるようになりました。これにより、`go tool compile -pack` で生成されたアーカイブを含むすべてのアーカイブに対して、`ldpkg` 内で行われるパッケージタイプチェックが確実に実行されるようになります。このチェックは `ldpkg` 内の以下の部分で行われます。
    ```go
    	if pkg == "main" && name != "main" {
    		Exitf("%s: not package main (package %s)", filename, name)
    	}
    ```
    この修正により、Issue #13468 で報告された問題が解決され、リンカは `package main` ではないアーカイブをトップレベルの入力として受け取った場合に、期待通りにエラーを発生させるようになります。

2.  **`src/cmd/link/internal/ld/go.go` からのコード削除**: `Import` 構造体、`importmap`、`loadpkgdata`、`parsepkgdata`、`parsemethod` といった一連のコードは、Go 1.2以降機能していなかったパッケージ間の型の一貫性チェックを目的としたものでした。Go 1.3で `go tool compile -pack` が導入され、Robert Griesemer氏によるエクスポートフォーマットが変更されたことで、これらの古い解析ロジックは新しいフォーマットに対応できなくなり、デッドコードと化していました。このコミットでは、これらの機能しないコードを完全に削除することで、リンカの複雑性を減らし、将来的なメンテナンスの負担を軽減しています。コミットメッセージにある「Figuring out how to make this code work with Robert's export format was one of the largest remaining TODOs for that format. Now we don't have to.」という記述は、この削除がコードベースの大きな改善であることを明確に示しています。

3.  **新しいテストファイルの追加**: `test/linkmain.go` と `test/linkmain_run.go` は、この修正が正しく機能することを検証するための重要なテストです。
    *   `test/linkmain.go` は意図的に `package notmain` としながら `main` 関数を持つファイルを作成し、リンカがこれを `package main` として扱わないことを確認するための入力となります。
    *   `test/linkmain_run.go` は、`go tool compile -pack` で生成された `package notmain` のアーカイブを `go tool link` が拒否することを確認するシナリオを自動化しています。これにより、リンカの挙動が期待通りであることを保証します。

これらの変更により、Goリンカはより堅牢になり、同時にコードベースが簡素化されました。

    multiple modules whose relative offset is determined at runtime.

    *rtype that references it and its typeOff value. We determine
    the module from the original pointer, and then use the typeOff from
    there to compute the final *rtype.

    type from an earlier module when resolving that offset. This means

    pointer dynamic relocations.

## 変更の背景

このコミットの主な背景には、Goプログラムにおける型情報のメモリ効率の改善と、特に共有ライブラリ（`buildmode=shared`）やプラグイン（将来の`buildmode=plugin`）の利用における課題がありました。

従来のGoバイナリでは、型情報は`*rtype`というポインタとして直接格納されていました。これは、単一の実行可能ファイル（`buildmode=exe`や`buildmode=pie`など）の場合には問題ありませんでしたが、複数のモジュールが動的にロードされるシナリオ（共有ライブラリやプラグイン）では、いくつかの問題を引き起こしました。

1.  **メモリ使用量の増大**: 各モジュールが独自の型情報を持つ場合、同じ型であっても異なるメモリ位置に存在し、それぞれが`*rtype`として表現されるため、メモリの重複が発生していました。これは特に大規模なアプリケーションや、多くのプラグインを使用するシステムで顕著な問題となります。
2.  **型の同一性問題**: 複数のモジュール間で同じ型が異なる`*rtype`ポインタとして表現されると、Goのランタイムや`reflect`パッケージが型の同一性を正しく判断できなくなる可能性がありました。Goでは型の等価性をポインタの等価性で判断する場面が多いため、これは重要な問題です。
3.  **動的リンキングの複雑化**: 共有ライブラリやプラグインでは、モジュールのロードアドレスが実行時に決定されます。`*rtype`のような絶対アドレスを持つポインタを直接使用すると、リンカが実行時にこれらのポインタを適切に再配置する必要があり、リンキングプロセスが複雑化します。

これらの問題を解決するため、型情報を絶対ポインタではなく、モジュール内の相対オフセットとして格納するアプローチが導入されました。これにより、メモリ使用量を削減し、動的にロードされるモジュール間での型の重複排除と同一性保証を可能にすることが目的です。

## 前提知識の解説

このコミットを理解するためには、以下のGoの内部構造と概念に関する知識が必要です。

*   **`*rtype`**: Goのランタイムが型情報を表現するために使用する内部構造体へのポインタです。`reflect`パッケージを通じてアクセスされる型情報は、この`*rtype`に基づいています。各Goの型（`int`, `string`, ユーザー定義の構造体など）は、ランタイム内で一意の`*rtype`インスタンスを持ちます。
*   **`moduledata`**: Goのバイナリは、実行時に`moduledata`という構造体を通じて自身のメタデータ（型情報、シンボルテーブル、初期化関数など）を管理します。`buildmode=shared`や`buildmode=plugin`の場合、複数の`moduledata`インスタンスが存在し、それぞれが異なるモジュールに対応します。
*   **`buildmode`**: Goコンパイラのビルドモードを指定するオプションです。
    *   `buildmode=exe`: 実行可能ファイルを生成します。
    *   `buildmode=pie` (Position-Independent Executable): アドレス空間配置のランダム化（ASLR）に対応した実行可能ファイルを生成します。
    *   `buildmode=c-archive`: C言語のアーカイブライブラリ（.aファイル）を生成し、C/C++プログラムからGoコードを呼び出せるようにします。
    *   `buildmode=c-shared`: C言語の共有ライブラリ（.soや.dylibファイル）を生成し、C/C++プログラムからGoコードを呼び出せるようにします。
    *   `buildmode=shared`: Goの共有ライブラリを生成します。これは、複数のGoプログラムが共通のGoランタイムとライブラリを共有するために使用されます。
    *   `buildmode=plugin`: Goのプラグインを生成します。これは、実行中のGoプログラムに動的にロードされるGoモジュールです。
*   **リフレクション (`reflect`パッケージ)**: 実行時にプログラムの型情報を検査・操作するための機能を提供します。`reflect`パッケージは内部的に`*rtype`を利用して型情報を扱います。
*   **リンカのリロケーション (Relocation)**: リンカがプログラムを結合する際に、シンボル参照（変数や関数のアドレス）を実際のメモリ位置に解決するプロセスです。動的リンキングでは、実行時にロードされるモジュールのベースアドレスが不明なため、リロケーション情報がバイナリに埋め込まれ、ロード時に解決されます。
*   **`uncommonType`**: Goの型情報（`_type`構造体）の一部で、型名やメソッド情報など、すべての型が持つわけではない「珍しい」情報が格納されます。メソッドを持つ型や名前を持つ型のみがこの`uncommonType`を持ちます。

## 技術的詳細

このコミットの核心は、`*rtype`ポインタを`typeOff`という32ビットオフセットに置き換えることです。同様に、関数ポインタも`textOff`というオフセットで表現されます。

1.  **`typeOff`と`textOff`の導入**:
    *   `typeOff`は、`moduledata`内の型情報セクションの先頭からの相対オフセットを表す`int32`型です。
    *   `textOff`は、`moduledata`内のコードセクションの先頭からの相対オフセットを表す`int32`型です。
    *   これにより、型情報や関数ポインタが絶対アドレスではなく、モジュール内の相対位置で表現されるようになります。

2.  **オフセットからポインタへの解決**:
    *   `(*_type).typeOff(off typeOff)`メソッドが導入され、`typeOff`から実際の`*rtype`ポインタを計算できるようになりました。
    *   同様に、`(*_type).textOff(off textOff)`メソッドが導入され、`textOff`から実際の関数ポインタを計算できるようになりました。
    *   この解決ロジックは、現在の`*rtype`がどの`moduledata`に属するかを判断し、そのモジュールのベースアドレスとオフセットを組み合わせて最終的なポインタを生成します。

3.  **`buildmode=shared`および`buildmode=plugin`のサポート**:
    *   これらのビルドモードでは、複数の`moduledata`が存在し、それぞれのロードアドレスが実行時に決定されます。
    *   `typeOff`を使用することで、各モジュールは自身の型情報をオフセットとして保持し、実行時に適切な`moduledata`のベースアドレスと結合してポインタを生成できます。
    *   **型の重複排除 (`typemap`)**: ランタイムは、`typelinksinit`関数で各モジュールの`typemap`を初期化します。これは、以前にロードされたモジュールに存在する同一の型を特定し、その既存の`*rtype`ポインタを再利用するためのマップです。これにより、複数のモジュール間で同じ型が重複してメモリ上に存在することを防ぎ、メモリ使用量を削減します。`typesEqual`関数が型の等価性を判断するために使用されます。
    *   リンカは、`R_METHOD`リロケーションを`R_METHODOFF`に変更し、メソッドポインタをオフセットとして扱うようにしました。これにより、リンカは動的にロードされるモジュール内のメソッドをより効率的に処理できます。

4.  **リフレクションによる実行時型生成の対応 (`reflectOffs`)**:
    *   `reflect`パッケージによって実行時に動的に生成される型（例: `reflect.StructOf`で作成される構造体型）は、ヒープ上に存在します。ヒープのアドレスは変動する可能性があり、32ビットオフセットで表現するのが困難です。
    *   このため、`reflectOffs`というグローバルマップが導入されました。実行時に生成された`*rtype`オブジェクトは、このマップに登録され、負のID（オフセットと衝突しないように）が割り当てられます。`typeOff`や`textOff`が負の値の場合、この`reflectOffs`マップを参照して実際のポインタが解決されます。これにより、ヒープ上の型も安定したIDで参照できるようになります。

5.  **メモリ使用量の削減**:
    *   コミットメッセージに記載されているように、この変更により、`cmd/go`や`jujud`といったGoバイナリのサイズが数KBから数MB削減されています。これは、`*rtype`ポインタが`typeOff`オフセットに置き換えられたことによる直接的な効果です。特に、`uncommonType`構造体から`[]method`スライスが削除され、`mcount`と`moff`という`uint16`のフィールドに置き換えられたことが大きな要因です。

## コアとなるコードの解説

### `src/reflect/type.go` と `src/runtime/type.go` の変更

最も重要な変更は、`method`構造体と`uncommonType`構造体の定義です。

**変更前 (`method`構造体):**
```go
type method struct {
	name name           // name of method
	mtyp *rtype         // method type (without receiver)
	ifn  unsafe.Pointer // fn used in interface call (one-word receiver)
	tfn  unsafe.Pointer // fn used for normal method call
}
```
`mtyp`は直接`*rtype`ポインタを保持し、`ifn`と`tfn`も`unsafe.Pointer`で関数への絶対アドレスを保持していました。

**変更後 (`method`構造体):**
```go
type method struct {
	name name    // name of method
	mtyp typeOff // method type (without receiver)
	ifn  textOff // fn used in interface call (one-word receiver)
	tfn  textOff // fn used for normal method call
}
```
`mtyp`は`typeOff`に、`ifn`と`tfn`は`textOff`に変わりました。これにより、メモリフットプリントが削減され、動的リンキングの柔軟性が向上します。

**変更前 (`uncommonType`構造体):**
```go
type uncommonType struct {
	pkgPath *string  // import path; nil for built-in types like int, string
	methods []method // methods associated with type
}
```
`methods`フィールドは`method`構造体のスライスを直接保持していました。

**変更後 (`uncommonType`構造体):**
```go
type uncommonType struct {
	pkgPath *string // import path; nil for built-in types like int, string
	mcount  uint16  // number of methods
	moff    uint16  // offset from this uncommontype to [mcount]method
}
```
`methods`スライスは削除され、代わりに`mcount`（メソッド数）と`moff`（`uncommonType`構造体の先頭からメソッド配列までのオフセット）が追加されました。これにより、`uncommonType`自体のサイズが固定され、メソッドデータは`uncommonType`の直後に配置されるか、`reflectOffs`を通じて参照されるようになります。

### `(*_type).typeOff` と `(*_type).textOff`

これらのメソッドは、`typeOff`または`textOff`を実際の`*rtype`または関数ポインタに解決する役割を担います。

```go
func (t *_type) typeOff(off typeOff) *_type {
	if off == 0 {
		return nil
	}
	base := uintptr(unsafe.Pointer(t))
	var md *moduledata
	// tがどのmoduledataに属するかを特定
	for next := &firstmoduledata; next != nil; next = next.next {
		if base >= next.types && base < next.etypes {
			md = next
			break
		}
	}
	if md == nil {
		// reflectによって実行時に生成された型の場合
		lock(&reflectOffs.lock)
		res := reflectOffs.m[int32(off)]
		unlock(&reflectOffs.lock)
		// ... エラーハンドリング ...
		return (*_type)(res)
	}
	// typemapに登録されているか確認（重複排除のため）
	if t := md.typemap[off]; t != nil {
		return t
	}
	// オフセットからポインタを計算
	res := md.types + uintptr(off)
	// ... 範囲チェック ...
	return (*_type)(unsafe.Pointer(res))
}
```
このロジックは、まず与えられた`_type`ポインタがどの`moduledata`に属するかを判断します。もし`moduledata`が見つからない場合（例えば、`reflect`パッケージによってヒープ上に動的に生成された型の場合）、`reflectOffs`マップから対応するポインタを検索します。`moduledata`が見つかった場合は、そのモジュールの`typemap`をチェックして、既に重複排除された型があればそれを返します。そうでなければ、`moduledata`の型セクションのベースアドレスにオフセットを加算して、最終的な`*rtype`ポインタを計算します。`textOff`の解決も同様のロジックで行われます。

### `typelinksinit()` と `typesEqual()`

`typelinksinit`関数は、Goプログラムの起動時に一度だけ実行され、特に`buildmode=shared`の場合に重要な役割を果たします。

```go
func typelinksinit() {
	// ...
	typehash := make(map[uint32][]*_type) // 型のハッシュ値に基づくマップ
	// ...
	for len(modules) > 0 {
		// 以前のモジュールから型を収集し、typehashに格納
		// ...
		// 現在のモジュールのtypelinksを走査
		md := modules[len(modules)-1]
		md.typemap = make(map[typeOff]*_type, len(md.typelinks))
		for _, tl := range md.typelinks {
			t := (*_type)(unsafe.Pointer(md.types + uintptr(tl)))
			for _, candidate := range typehash[t.hash] {
				if typesEqual(t, candidate) { // 型が等しいか比較
					t = candidate // 既存の型を再利用
					break
				}
			}
			md.typemap[typeOff(tl)] = t // 現在のモジュールのtypemapに登録
		}
		// ...
	}
}
```
この関数は、ロードされたすべての`moduledata`を走査し、`typemap`を構築します。`typemap`は、あるモジュール内の`typeOff`が、以前にロードされたモジュール内の既存の`*rtype`を指すようにマッピングすることで、型の重複を排除します。`typesEqual`関数は、2つの`*rtype`が論理的に同じ型であるかどうかを詳細に比較します。これにより、ポインタの等価性だけでは判断できない、複数のモジュールにまたがる型の同一性を保証します。

### `reflectOffs`

`reflectOffs`は、`reflect`パッケージによって実行時に動的に生成される型（例: `reflect.StructOf`で作成される型）を管理するためのマップです。これらの型はヒープ上に存在するため、固定のオフセットを持つことができません。

```go
var reflectOffs struct {
	lock mutex
	next int32 // 次に割り当てる負のID
	m    map[int32]unsafe.Pointer // IDからポインタへのマップ
	minv map[unsafe.Pointer]int32 // ポインタからIDへのマップ
}
```
`reflect.addReflectOff`関数が呼び出されると、動的に生成された`*rtype`や関数ポインタが`reflectOffs.m`に登録され、負のユニークなIDが割り当てられます。このIDが`typeOff`や`textOff`として使用され、ランタイムは負のオフセットを見たときに`reflectOffs`を参照して実際のポインタを解決します。

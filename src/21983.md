## 元コミット内容

このコミットは、Goのアセンブラ (`cmd/internal/asm`) におけるビルドエラーを修正するものです。具体的には、`amd64` (x86-64) アーキテクチャでの `SP` (スタックポインタ) レジスタの参照が正しく処理されていなかった問題に対処しています。

問題の根本原因は、ARMアーキテクチャでの作業中に、`SP` がx86アーキテクチャでは実際のハードウェアレジスタであるという事実が見落とされていたことにあります。そのため、`SP` レジスタを特別に検出して処理する必要がありました。

このコミットは一時的な修正であり、将来的にはより良い方法で解決される予定ですが、差し当たりのビルド問題を解決するための迅速な対応として適用されました。

## 変更の背景

Go言語のツールチェイン、特にアセンブラ (`cmd/internal/asm`) は、異なるCPUアーキテクチャ（例: x86、ARM）に対応するために、アーキテクチャ固有のレジスタ処理を抽象化しています。Goのアセンブラでは、`SP` (スタックポインタ) は、実際のハードウェアレジスタとしての `SP` と、Goのランタイムが管理する「擬似レジスタ」としての `SP` の二つの意味合いを持ちます。

擬似レジスタとしての `SP` は、関数内のローカル変数や引数へのアクセスに使用され、通常は `x-8(SP)` のようにオフセットを伴って参照されます。これは、Goのコンパイラとアセンブラがスタックフレームを管理するための抽象化された概念です。

一方、実際のハードウェアレジスタとしての `SP` は、CPUが直接使用する物理的なスタックポインタです。x86アーキテクチャでは `RSP` (64ビットの場合) がこれに該当し、ARMアーキテクチャでは `R13` がこれに該当します。

このコミットが行われた背景には、GoのツールチェインがARMアーキテクチャのサポートを強化する作業がありました。その過程で、ARMでは `SP` が物理レジスタとして扱われる一方で、x86アーキテクチャにおける `SP` の特殊な扱い（擬似レジスタと物理レジスタの両方の側面を持つこと）が見落とされていました。

結果として、`amd64` (x86-64) 環境でアセンブラが `SP` を参照する際に、それが物理レジスタであるにもかかわらず、擬似レジスタとして不適切に扱われるケースが発生し、ビルドエラーを引き起こしていました。このコミットは、そのビルドエラーを解消するための緊急的な修正として導入されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **Goのアセンブラ (`cmd/internal/asm`)**: Go言語のコンパイラツールチェインの一部であり、Goのアセンブリ言語で書かれたコードを機械語に変換する役割を担います。Goのアセンブリ言語は、一般的なアセンブリ言語とは異なり、Goランタイムの特性に合わせて設計されています。
*   **擬似レジスタ (Pseudo-registers)**: Goのアセンブラが提供する仮想的なレジスタです。これらは実際のCPUレジスタに直接対応するわけではなく、Goのランタイムがメモリやプログラムの制御フローを管理するための抽象化された概念です。主要な擬似レジスタには以下のものがあります。
    *   **FP (Frame Pointer)**: 関数の引数や戻り値にアクセスするために使用されます。
    *   **PC (Program Counter)**: ジャンプや分岐命令に使用されます。
    *   **SB (Static Base Pointer)**: グローバルなシンボル（関数やデータ）を参照するために使用されます。
    *   **SP (Stack Pointer)**: 関数内のローカル変数や、関数呼び出しのために準備される引数にアクセスするために使用されます。これはハードウェアのSPレジスタとは異なる仮想的なSPです。
*   **`SP` レジスタの二面性**:
    *   **擬似 `SP`**: Goのアセンブラがスタックフレーム内のローカル変数や引数を参照するために使用する仮想的なスタックポインタ。通常、`x-8(SP)` のようにオフセットを伴って使用されます。
    *   **ハードウェア `SP`**: CPUが実際に使用する物理的なスタックポインタ。x86アーキテクチャでは `RSP` (64ビット) や `ESP` (32ビット) がこれに該当します。Goのアセンブラでは、オフセットのみで `SP` を参照する場合（例: `-8(SP)`）にハードウェア `SP` を指すことがあります。
*   **`obj.Addr`**: `cmd/internal/obj` パッケージで定義されている構造体で、Goのコンパイラが機械語を生成する前に使用する、アセンブリライクな中間表現におけるオペランドやアドレスを表します。レジスタ、メモリ位置、定数、シンボルなど、様々な種類のアドレスをカプセル化します。
*   **`obj.NAME_AUTO`**: `cmd/internal/obj` パッケージの内部定数で、通常はスタック上に自動的に割り当てられる変数に関連付けられる、自動的に割り当てられた名前やシンボルを指します。
*   **`obj.TYPE_ADDR`**: `cmd/internal/obj` パッケージの内部定数で、`obj.Addr` 構造体内でアドレスのタイプを分類するために使用されます。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/asm/internal/asm/parse.go` 内の `symbolReference` および `setPseudoRegister` 関数における `SP` レジスタの処理の変更にあります。

元々の実装では、`symbolReference` 関数内で `(reg)` 形式のシンボル参照を処理する際に、`p.arch.Registers[reg]` を直接 `setPseudoRegister` に渡していました。ここで `reg` は文字列としてのレジスタ名（例: "SP"）です。

問題は、`p.arch.Registers[reg]` が返す値が、アーキテクチャによっては `SP` が物理レジスタとして定義されている場合と、擬似レジスタとして定義されている場合で異なる可能性がある点です。特に `amd64` の場合、`SP` は物理レジスタ `RSP` に対応しますが、アセンブラの内部処理では擬似レジスタとしての `SP` との区別が重要になります。

このコミットでは、以下の修正が加えられました。

1.  **`symbolReference` 関数内の `SP` の特別扱い**:
    `p.arch.Registers[reg]` でレジスタの数値表現 `r` を取得した後、もし `reg` が `"SP"` であれば、明示的に `r = arch.RSP` と設定しています。これは、`amd64` において `SP` が物理レジスタ `RSP` であることを保証し、`setPseudoRegister` 関数に常に物理レジスタとしての `SP` の値が渡されるようにするためです。
    コメント `// On some machines, SP is a real register, on some it's pseudo. Make sure // setPseudoRegister sees the pseudo always.` は、この変更の意図を明確に示しています。つまり、`setPseudoRegister` が擬似レジスタを扱う関数であるにもかかわらず、`SP` の場合は物理レジスタとしての `RSP` を渡すことで、その後の処理で `SP` が正しく識別されるようにしています。

2.  **`setPseudoRegister` 関数のシグネチャ変更**:
    `setPseudoRegister` 関数のシグネチャが `func (p *Parser) setPseudoRegister(addr *obj.Addr, reg int16, isStatic bool, prefix rune)` から `func (p *Parser) setPseudoRegister(addr *obj.Addr, name string, reg int16, isStatic bool, prefix rune)` に変更されました。これにより、レジスタの数値表現 (`reg`) に加えて、レジスタの文字列名 (`name`) も引数として受け取れるようになりました。

3.  **エラーメッセージの改善**:
    `setPseudoRegister` 関数内で、期待される擬似レジスタが見つからなかった場合のエラーメッセージが、数値表現 (`%d`) ではなく文字列名 (`%s`) を表示するように変更されました。これにより、デバッグ時の情報がより分かりやすくなります。

4.  **`registerIndirect` 関数での `name` の伝播**:
    `registerIndirect` 関数でも、レジスタの文字列名 `name` を取得し、それを新しい `setPseudoRegister` 関数に渡すように変更されました。

これらの変更により、Goのアセンブラは `amd64` 環境で `SP` レジスタを正しく識別し、擬似レジスタとしての `SP` と物理レジスタとしての `SP` の間の曖昧さを解消することで、ビルドエラーを修正しました。これは、Goのクロスコンパイルとマルチアーキテクチャサポートの複雑さを示す一例でもあります。

## コアとなるコードの解説

### `symbolReference` 関数の変更

```go
 	reg := p.get(scanner.Ident).String()
 	p.get(')')
-	p.setPseudoRegister(a, p.arch.Registers[reg], isStatic != 0, prefix)
+	// On some machines, SP is a real register, on some it's pseudo. Make sure
+	// setPseudoRegister sees the pseudo always.
+	// TODO: Set up a pseudo-register map analogous to the register map in arch?
+	r := p.arch.Registers[reg]
+	if reg == "SP" {
+		r = arch.RSP
+	}
+	p.setPseudoRegister(a, reg, r, isStatic != 0, prefix)
```

*   **変更前**: `p.arch.Registers[reg]` の結果を直接 `setPseudoRegister` に渡していました。これは、`reg` が "SP" の場合でも、アーキテクチャによっては擬似レジスタとしての `SP` の値が返される可能性がありました。
*   **変更後**:
    1.  `p.arch.Registers[reg]` の結果を `r` に格納します。
    2.  `reg` が `"SP"` であるかをチェックします。
    3.  もし `"SP"` であれば、`r` を明示的に `arch.RSP` に設定し直します。`arch.RSP` は `amd64` における物理的なスタックポインタレジスタ `RSP` を表す定数です。
    4.  `setPseudoRegister` を呼び出す際に、レジスタの文字列名 `reg` と、修正された数値表現 `r` の両方を渡すように変更されました。
*   **目的**: この変更により、`SP` が参照された際に、それが `amd64` 上の物理レジスタ `RSP` であることをアセンブラが正しく認識できるようになります。これにより、擬似レジスタと物理レジスタの間の混同が解消され、ビルドエラーが修正されます。

*   **エラーメッセージの改善**: `default` ケースでのエラーメッセージが `found %d` (数値) から `found %s` (文字列) に変更されました。これにより、エラー発生時にどのレジスタ名が問題を引き起こしたのかが直接的に表示され、デバッグが容易になります。

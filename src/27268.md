# [インデックス 27268] ファイルの概要

このコミットは、Go言語の標準ライブラリである `testing` パッケージにおける、テストおよびベンチマークの実行メカニズムの根本的な変更を導入するものです。特に、`t.Run` メソッドによるサブテストの導入に備え、並列テストの管理方法を大幅に再構築しています。これにより、各テストが自身の並列サブテストの開始と停止を管理する責任を持つようになり、テストの構造化と並列実行の柔軟性が向上しました。

## 変更の背景

このコミットの主な背景は、Go 1.7で導入される `*testing.T` および `*testing.B` の `Run` メソッドの準備です。`Run` メソッドは、テスト関数内でサブテストやサブベンチマークを定義できるようにする画期的な機能であり、これによりテストの構造化、共通のセットアップ/ティアダウン、および並列実行のよりきめ細やかな制御が可能になります。

この機能が導入される前は、各テストは独立したトップレベルの関数として定義され、並列テストの管理は `testing` パッケージの内部で一元的に行われていました。しかし、サブテストの概念を導入するためには、テストが階層構造を持つことを許容し、親テストが自身のサブテストのライフサイクル（特に並列実行）を管理できるようなメカニズムが必要でした。

このコミットは、そのための基盤を構築し、並列テストの管理ロジックを中央集権的なアプローチから、各テストが自身のサブテストの並列実行を調整する分散型のアプローチへと移行させています。これにより、`t.Run` が導入された際に、既存のテストセマンティクスと矛盾なく、かつ効率的に並列サブテストを実行できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の `testing` パッケージに関する知識が役立ちます。

*   **`go test` コマンド**: Go言語のテストを実行するためのコマンド。`-run` フラグで特定のテストを指定したり、`-parallel` フラグで並列実行数を制御したりできます。
*   **`*testing.T`**: テスト関数に渡される構造体で、テストの失敗 (`t.Fail()`, `t.Errorf()`)、スキップ (`t.Skip()`)、並列実行 (`t.Parallel()`) などの機能を提供します。
*   **`*testing.B`**: ベンチマーク関数に渡される構造体で、ベンチマークの実行回数 (`b.N`) やタイマーの制御 (`b.ResetTimer()`, `b.StartTimer()`, `b.StopTimer()`) などの機能を提供します。
*   **並列テスト (`t.Parallel()`)**: `t.Parallel()` を呼び出すことで、テストランナーは当該テストを他の並列テストと同時に実行できると判断します。これにより、テストスイート全体の実行時間を短縮できます。
*   **`tRunner`**: `testing` パッケージ内部でテスト関数を実行するゴルーチンを指します。各テストは通常、独自の `tRunner` ゴルーチンで実行されます。
*   **チャネル (Channels)**: Go言語におけるゴルーチン間の通信手段。このコミットでは、テストの完了シグナルや並列実行の同期にチャネルが多用されています。
*   **`sync.Mutex`**: 複数のゴルーチンから共有リソースへのアクセスを保護するための排他ロック。テストコンテキストの状態管理に使用されます。

## 技術的詳細

このコミットの技術的な核心は、並列テストの管理モデルの変更と、サブテストの階層構造をサポートするための `testing` パッケージ内部構造の再設計にあります。

1.  **並列テスト管理の分散化**:
    *   以前は、`RunTests` 関数が一元的に並列テストの数を管理し、`startParallel` チャネルを通じてテストの開始を調整していました。
    *   このコミットでは、`testContext` という新しい構造体が導入され、並列実行の管理ロジックがこのコンテキストに集約されます。各テストは、自身の `testContext` を通じて並列実行を調整するようになります。
    *   `testContext` は、現在実行中の並列テストの数 (`running`)、並列実行を待機しているテストの数 (`numWaiting`)、および最大並列数 (`maxParallel`) を管理します。
    *   `waitParallel()` メソッドは、テストが並列実行を開始する前に呼び出され、並列スロットが利用可能になるまで待機します。
    *   `release()` メソッドは、テストが完了した際に呼び出され、並列スロットを解放し、待機中のテストがあればそれを開始させます。

2.  **サブテストの階層構造の導入**:
    *   `common` 構造体に `parent *common` フィールドが追加され、テストが親テストを持つことができるようになりました。これにより、テストの階層構造が表現されます。
    *   `T.Fail()` メソッドは、自身の `failed` フラグを設定するだけでなく、親テストの `Fail()` メソッドも呼び出すようになり、サブテストの失敗が親テストに伝播するようになりました。
    *   `tRunner` 関数は、サブテストの実行ロジックを内包するようになり、親テストが自身のサブテストの完了を待機するメカニズムが導入されました。
    *   `T.Parallel()` メソッドは、自身を親テストの `sub` スライスに追加し、親テストがすべての並列サブテストの完了を待機できるようにします。

3.  **チャネルの型変更と役割の明確化**:
    *   `common` 構造体の `signal` チャネルの型が `chan interface{}` から `chan bool` に変更されました。これにより、シグナルの意味が「テスト完了」に特化され、より明確になりました。
    *   `barrier chan bool` が `common` 構造体に追加され、並列サブテストが親テストの完了を待機するための同期メカニズムとして機能します。

4.  **出力管理の改善**:
    *   `common` 構造体に `w io.Writer` が追加され、テストの出力先を柔軟に設定できるようになりました。
    *   `flushToParent` メソッドが導入され、サブテストの出力が適切に親テストの出力にマージされるようになりました。これにより、階層的なテスト出力が整理されます。

これらの変更により、`testing` パッケージは `t.Run` メソッドの導入に備え、より柔軟で強力なテスト実行フレームワークへと進化しました。

## コアとなるコードの解説

このコミットの核心は、`testing` パッケージが並列テストをどのように管理するかというパラダイムシフトにあります。

1.  **`common` 構造体の拡張**:
    *   `parent *common`: テストが階層構造を持つことを可能にし、サブテストが親テストに紐付けられるようにします。これにより、サブテストの失敗が親テストに伝播したり、親テストがサブテストの完了を待機したりするメカニズムが実現されます。
    *   `name string`: テストやベンチマークの名前を保持します。
    *   `w io.Writer`: テストの出力を柔軟にリダイレクトできるようにします。これにより、サブテストの出力を親テストの出力ストリームに統合することが容易になります。
    *   `barrier chan bool`: `t.Parallel()` を呼び出したサブテストが、親テストがすべての並列サブテストの準備が整うまで待機するための同期ポイントとして機能します。
    *   `signal chan bool`: テストが完了したことを通知するためのシンプルなブールチャネルです。以前の `interface{}` よりも意図が明確になりました。
    *   `sub []*T`: 親テストが実行するサブテストのキューを保持します。

2.  **`testContext` による並列実行の管理**:
    *   `testContext` は、`go test -parallel N` で指定される並列実行数 `N` に基づいて、同時に実行できるテストの数を制御します。
    *   `waitParallel()`: テストが並列実行を開始する前にこのメソッドを呼び出します。もし利用可能な並列スロットがあればすぐに実行を許可し、なければスロットが解放されるまで `startParallel` チャネルで待機します。
    *   `release()`: テストが完了した際にこのメソッドを呼び出し、並列スロットを解放します。待機中のテストがあれば、`startParallel` チャネルにシグナルを送信して実行を許可します。
    *   このメカニズムにより、並列テストの管理が `RunTests` 関数から `testContext` に移譲され、よりモジュール化された設計になっています。

3.  **`tRunner` の役割の強化**:
    *   `tRunner` は、単にテスト関数を実行するだけでなく、サブテストのライフサイクル管理の中心的な役割を担うようになりました。
    *   テスト関数が `t.Parallel()` を呼び出した場合、`tRunner` は `t.context.waitParallel()` を呼び出して並列スロットを確保し、親テストの `barrier` チャネルで待機します。
    *   テスト関数が `t.Run()` を呼び出してサブテストを生成した場合、`tRunner` はそれらのサブテストの完了を待機し、すべてのサブテストが終了した後に自身の `report()` を呼び出します。

これらの変更は、Goのテストフレームワークが、より複雑なテストシナリオ（特に並列サブテスト）を効率的かつ堅牢に処理できるようにするための重要な進化を示しています。

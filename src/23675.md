## 元コミット内容

このコミットは、GoコンパイラのARM64バックエンドにおける関数プロローグの生成ロジックを改善するものです。主な変更点は以下の2点です。

1.  **スタック拡張チェックの分岐予測最適化**: 静的分岐予測の挙動に合わせて、スタック拡張が必要なケース（稀なケース）がフォワードブランチ（順方向への分岐）となるように分岐条件を変更します。これにより、CPUの分岐予測ミスを減らし、パフォーマンスを向上させます。
2.  **デバッグ用命令の削除**: デバッグ目的でのみ使用されていた、フレームサイズを一時レジスタに保存する命令を削除します。これにより、生成されるコードがわずかに小さくなり、実行効率が向上します。

コミットメッセージには、`func f() { _ = [128]byte{} }`というシンプルな関数を例にとったアセンブリコードのBefore/Afterが示されており、変更によって生成されるコードがどのように変わるかが具体的に示されています。また、`sort`パッケージのベンチマーク結果も含まれており、一部のケースでパフォーマンスが改善していることが示されています。

## 変更の背景

Goランタイムでは、各Goルーチンが独自のスタックを持っています。関数呼び出しの際に、必要なスタック領域が現在のスタックに足りるかどうかをチェックし、足りない場合は`runtime.morestack`などの関数を呼び出してスタックを拡張するメカニズム（スタック分割、stack split）が組み込まれています。このチェックは関数のプロローグ（関数の冒頭部分）で行われます。

このコミットの背景には、CPUの**分岐予測器**の効率を最大化するという目的があります。

*   **静的分岐予測 (Static Branch Prediction)**: 現代のCPUは、プログラムの実行フローを高速化するために、次に実行される命令を予測する「分岐予測器」を持っています。静的分岐予測は、過去の実行履歴に依存せず、命令の構造（例えば、フォワードブランチは「取られない」、バックワードブランチは「取られる」と予測する）に基づいて予測を行います。
*   **スタック拡張の頻度**: Goプログラムにおいて、スタックが不足して`runtime.morestack`が呼び出されるケースは非常に稀です。ほとんどの関数呼び出しでは、既存のスタックで十分な領域が確保できます。

元のコードでは、スタックが足りている場合にフォワードブランチ（`b.hi`）が実行され、スタック拡張が必要な場合にフォワードブランチがスキップされて`morestack`への呼び出しが行われる構造になっていました。静的分岐予測器はフォワードブランチが取られないと予測するため、スタックが足りている（＝フォワードブランチが取られる）という一般的なケースで予測ミスが発生し、パイプラインストールによる性能低下を招く可能性がありました。

このコミットは、この分岐予測の非効率性を解消し、一般的なケース（スタック拡張が不要なケース）で分岐予測が成功するようにコードのフローを反転させることを目的としています。また、デバッグ目的の不要な命令を削除することで、コードのフットプリントを削減し、わずかながら実行効率を向上させることも意図されています。

## 前提知識の解説

### 1. ARM64アーキテクチャとアセンブリ

ARM64は、Apple SiliconやQualcomm Snapdragonなど、モバイルデバイスやサーバー、デスクトップPCで広く採用されている64ビットRISCプロセッサアーキテクチャです。

*   **レジスタ**:
    *   `x0` - `x30`: 汎用レジスタ。`x0` - `x7`は関数呼び出しの引数/戻り値、`x8`は間接結果レジスタ、`x9` - `x15`は呼び出し側保存レジスタ、`x16` - `x17`はプロシージャ内一時レジスタ、`x18`はプラットフォームレジスタ、`x19` - `x28`は呼び出し先保存レジスタ、`x29`はフレームポインタ（FP）、`x30`はリンクレジスタ（LR）。
    *   `sp`: スタックポインタ。現在のスタックの最上位アドレスを指します。
    *   `xzr`: ゼロレジスタ。常に0を保持し、書き込みは無視されます。
*   **命令**:
    *   `ldr Xd, [Xn, #offset]`: メモリからレジスタへロード。`Xn + offset`のアドレスからデータを`Xd`にロードします。
    *   `sub Xd, Xn, #imm`: 減算。`Xn - imm`の結果を`Xd`に格納します。
    *   `cmp Xn, Xm`: 比較。`Xn`と`Xm`を比較し、結果をステータスレジスタに設定します。
    *   `b.hi label`: 条件分岐。`HI` (Higher) 条件（符号なしで`Xn > Xm`）が真の場合に`label`へ分岐します。
    *   `b.ls label`: 条件分岐。`LS` (Lower or Same) 条件（符号なしで`Xn <= Xm`）が真の場合に`label`へ分岐します。
    *   `mov Xd, Xn`: レジスタ間移動。`Xn`の値を`Xd`にコピーします。
    *   `movz Xd, #imm`: ゼロ拡張付き移動。`imm`を`Xd`に格納し、上位ビットをゼロで埋めます。
    *   `bl label`: 分岐とリンク。`label`へ分岐し、次の命令のアドレスをリンクレジスタ`x30`に保存します（関数呼び出しに使用）。
    *   `b label`: 無条件分岐。`label`へ分岐します。
    *   `str Xd, [Xn, #offset]`: レジスタからメモリへストア。`Xd`のデータを`Xn + offset`のアドレスにストアします。
    *   `ret`: サブルーチンからのリターン。通常は`x30`（LR）に保存されたアドレスへ分岐します。

### 2. Goランタイムのスタック管理

Goは、Goroutineごとに可変サイズのスタックを使用します。関数呼び出しの際、Goコンパイラは各関数のプロローグにスタック拡張チェックのコードを挿入します。

*   **スタックポインタ (SP)**: 現在のスタックの最上位を指すレジスタ。Goでは`SP`レジスタが使用されます。
*   **スタックガード (Stack Guard)**: スタックの限界を示す値。Goランタイムは、スタックのオーバーフローを防ぐために、スタックポインタがこのガード値を下回っていないかをチェックします。
*   **`runtime.morestack`**: スタックが不足している場合に呼び出されるランタイム関数。新しい、より大きなスタックを割り当て、現在のスタックの内容を新しいスタックにコピーし、実行を継続します。`runtime.morestack_noctxt`は、コンテキスト情報なしで`morestack`を呼び出すバリアントです。

### 3. Goコンパイラのオブジェクトファイル生成 (`cmd/internal/obj`)

Goコンパイラは、ソースコードを中間表現に変換した後、各アーキテクチャ（amd64, arm64など）固有のオブジェクトファイル生成バックエンドに渡します。`cmd/internal/obj`パッケージは、このバックエンドの一部であり、アセンブリ命令を生成し、オブジェクトファイルに変換する役割を担います。

*   `obj.Prog`: アセンブリ命令を表す構造体。
*   `obj.Appendp(ctxt, p)`: 新しい命令を現在の命令リストに追加します。
*   `obj.TYPE_BRANCH`, `obj.TYPE_REG`, `obj.TYPE_CONST`: 命令のオペランドのタイプを示します。
*   `obj.Linklookup`: シンボル（関数名など）に対応するリンカオブジェクトを検索します。

## 技術的詳細

### 1. 分岐予測の最適化

元のコードでは、スタックチェックの分岐は以下のようになっていました。

```armasm
    cmp        x2, x1      // x2 (新しいSP) と x1 (スタックガード) を比較
    b.hi       0x...       // x2 > x1 (スタックが足りている) ならば、スタック拡張ロジックをスキップして関数本体へ
    // スタック拡張ロジック (morestack呼び出し)
```

ここで`b.hi`は「Higher」条件分岐であり、`x2 > x1`の場合に分岐します。静的分岐予測器はフォワードブランチ（順方向への分岐）を「取られない」と予測する傾向があります。しかし、スタックが足りている（`x2 > x1`が真）という一般的なケースでは、この`b.hi`分岐は「取られる」ため、予測ミスが発生しやすくなります。

変更後のコードでは、分岐条件が`b.ls`（Lower or Same）に変更されています。

```armasm
    cmp        x2, x1      // x2 (新しいSP) と x1 (スタックガード) を比較
    b.ls       0x...       // x2 <= x1 (スタックが足りない) ならば、スタック拡張ロジックへ
    // 関数本体へ進むロジック
```

`b.ls`は「Lower or Same」条件分岐であり、`x2 <= x1`の場合に分岐します。スタックが足りない（`x2 <= x1`が真）という稀なケースでこの分岐が「取られる」ことになります。一般的なケース（スタックが足りている）では`b.ls`分岐は「取られない」ため、静的分岐予測器の予測（フォワードブランチは取られない）と一致し、予測ミスが減少します。これにより、CPUパイプラインの効率が向上し、全体的なパフォーマンスが改善される可能性があります。

### 2. デバッグ用命令の削除

元のコードには、`framesize`（フレームサイズ）を一時レジスタ`REGTMP`（`x27`）に保存する命令が含まれていました。

```armasm
    movz       x27, #0x90  // framesize (0x90) を x27 に保存
```

コミットメッセージによると、これはデバッグ目的でのみ使用される命令であり、通常の実行には不要です。この命令を削除することで、生成されるコードのサイズがわずかに減少し、命令フェッチやキャッシュの効率が向上する可能性があります。

### 3. アセンブリコードの具体的な変更点

コミットメッセージに示されたアセンブリのBefore/Afterを詳細に見てみましょう。

主な変更点は以下の通りです。

*   `b.hi 0x4008268` が `b.ls 0x4004c28` に変更されました。これにより、スタックが足りている一般的なケースでは分岐が取られず、命令が順次実行されるようになります。
*   `movz x27, #0x90` 命令が削除されました。
*   `morestack`への呼び出しとそれに続く分岐命令が、`b.ls`のターゲットアドレス（`0x4004c28`）に移動しました。

この変更により、スタックチェックのロジックが「スタックが足りている場合はそのまま続行、足りない場合のみ分岐して`morestack`を呼び出す」という、分岐予測器にとってより効率的な形に再構築されました。

## コアとなるコードの解説

`stacksplit`関数は、Goコンパイラが各関数のプロローグに挿入するスタックチェックコードを生成する役割を担っています。

1.  **分岐命令の変更**:
    *   元のコードでは`ABHI` (Branch if Higher) 命令が生成され、スタックが足りている場合にスキップするロジックでした。
    *   変更後では`ABLS` (Branch if Lower or Same) 命令が生成され、スタックが足りない場合に`morestack`呼び出しへ分岐するロジックに変わりました。
    *   `bls := obj.Appendp(ctxt, p)`: 新しい分岐命令`bls`を生成します。
    *   `bls.As = ABLS`: 命令のタイプを`ABLS`に設定します。
    *   `bls.To.Type = obj.TYPE_BRANCH`: ターゲットが分岐であることを示します。

2.  **`morestack`呼び出しロジックの移動**:
    *   元のコードでは、`ABHI`の後に`morestack`呼び出しが続き、その後に無条件分岐で関数の先頭に戻るという流れでした。
    *   変更後では、`morestack`呼び出しとそれに続く無条件分岐の命令群が、`ABLS`命令のターゲットとして関数の最後尾近くに移動されました。
    *   `var last *obj.Prog; for last = ctxt.Cursym.Text; last.Link != nil; last = last.Link {}`: これは、現在の関数の命令リストの末尾を見つけるためのループです。`morestack`呼び出しのコードを関数の最後に配置するために使用されます。
    *   `movlr := obj.Appendp(ctxt, last)`: `LR`を`R3`に保存する命令を、命令リストの末尾に追加します。
    *   `bls.Pcond = movlr`: `ABLS`命令のターゲットを、この`movlr`命令に設定します。これにより、スタックが足りない場合に`morestack`呼び出しのシーケンスへジャンプします。
    *   `call := obj.Appendp(ctxt, debug)`: `runtime.morestack`を呼び出す`ABL`命令を生成します。
    *   `jmp := obj.Appendp(ctxt, call)`: `morestack`から戻った後、関数の先頭に戻るための無条件分岐`AB`命令を生成します。

3.  **デバッグ用命令の削除**:
    *   `if false { ... }`というブロックが追加され、その中にあったフレームサイズを一時レジスタ`REGTMP`に保存する命令が実質的に削除されました。`if false`はコンパイル時に常に偽と評価されるため、このブロック内のコードは生成されません。

これらの変更により、生成されるアセンブリコードのフローが最適化され、CPUの分岐予測器の効率が向上し、デバッグ目的の不要な命令が取り除かれました。

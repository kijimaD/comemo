# [インデックス 27768] ファイルの概要

このコミットは、Go言語のネットワークパッケージにおける`sendfile`システムコールのSolarisおよび一部のBSD系OSでの誤った動作を修正するものです。特に、部分的な書き込みが発生し、`EAGAIN`または`EINTR`エラーが返された際に、`sendfile`が返す値とオフセットポインタの更新の間に不整合が生じる問題に対処しています。この修正により、GoアプリケーションがSolaris上で`sendfile`を介してファイルを効率的かつ正確に転送できるようになります。

## 元コミット内容

このコミットは、Goの`net`パッケージにおける`sendfile`の実装がSmartOS/Solaris環境で正しく機能しない問題を修正します。具体的には、Solarisおよび一部のBSD系OSにおいて、`sendfile()`システムコールが部分的な書き込みを行った際に、`errno`が`EAGAIN`または`EINTR`に設定されて`-1`を返しても、オフセットポインタが更新されてしまうという挙動に対応しています。

修正内容は以下の通りです。
1.  `sendfile()`呼び出しの前後のオフセットポインタの差分に基づいて、実際に書き込まれたバイト数を計算します。
2.  もし実際に書き込まれたバイト数が0であり、かつ`errno`が`EAGAIN`または`EINTR`である場合、そのエラーは無視され、処理が続行されます。これにより、不正確なエラー処理や無限ループを防ぎます。
3.  関連するテストファイル`src/net/sendfile_test.go`が新規追加され、`sendfile`の動作が広範に検証されるようになりました。

この修正は、GoのIssue #13892を解決します。

## 変更の背景

Go言語の`net`パッケージは、`io.Copy`などの高レベルなI/O操作において、可能であればOSの`sendfile`システムコールを利用して「ゼロコピー」転送を実現しようとします。ゼロコピー転送は、データをカーネル空間内で直接ファイルディスクリプタからソケットディスクリプタへ転送することで、ユーザー空間へのデータコピーを省略し、CPUオーバーヘッドとメモリ帯域幅の使用を削減し、スループットを向上させる非常に効率的なメカニズムです。

しかし、SolarisやSmartOSといった一部のUNIX系OSでは、`sendfile()`システムコールの挙動に特有の癖がありました。具体的には、非ブロッキングI/Oやシグナル割り込みによって部分的な書き込みが発生し、`sendfile()`が`EAGAIN`（操作がブロックされる可能性がある）または`EINTR`（シグナルによって中断された）を`errno`に設定して`-1`（エラー）を返した場合でも、`sendfile()`に渡されたオフセットポインタ（`off_t *off`）が、実際に転送されたバイト数に応じて更新されてしまうという問題がありました。

Goの既存の`sendfile`ラッパーは、`sendfile()`が`-1`を返した場合には、何もバイトが書き込まれなかったと誤解釈し、エラーをそのまま伝播させるか、あるいはオフセットが不正確な状態で処理を続行してしまう可能性がありました。これにより、ファイル転送が途中で停止したり、データが破損したり、あるいは無限ループに陥るなどの問題が発生していました。この問題はGoのIssue #13892として報告され、Goのネットワークスタックの堅牢性を高めるために修正が必要とされました。

## 前提知識の解説

### `sendfile()`システムコール

`sendfile()`は、オペレーティングシステムが提供するシステムコールの一つで、ファイルディスクリプタから別のファイルディスクリプタへデータを直接転送するために使用されます。主な利点は「ゼロコピー」と呼ばれる最適化です。

*   **ゼロコピー (Zero-copy)**: 通常、ファイルからネットワークソケットへデータを送信する場合、データは以下の手順でコピーされます。
    1.  ファイルからカーネルバッファへ (DMA)
    2.  カーネルバッファからユーザーバッファへ (CPU)
    3.  ユーザーバッファからソケットバッファへ (CPU)
    4.  ソケットバッファからNICへ (DMA)
    `sendfile()`を使用すると、データはカーネルバッファから直接ソケットバッファへ転送され、ユーザーバッファへのコピーが省略されます（OSによってはさらに最適化され、カーネルバッファからNICへ直接転送されることもあります）。これにより、CPUの負荷が軽減され、メモリ帯域幅の使用量が減り、全体的なスループットが向上します。

*   **引数**: `sendfile()`の具体的なシグネチャはOSによって異なりますが、一般的には以下の情報を受け取ります。
    *   `out_fd`: 出力先のファイルディスクリプタ（通常はソケット）。
    *   `in_fd`: 入力元のファイルディスクリプタ（通常はファイル）。
    *   `offset`: 入力ファイルからの読み込み開始オフセット。OSによってはポインタで渡され、関数内で更新されることがあります。
    *   `count`: 転送するバイト数。

*   **戻り値とエラー**:
    *   成功した場合、転送されたバイト数を返します。
    *   エラーが発生した場合、`-1`を返し、`errno`変数にエラーコードを設定します。

### `errno`と`EAGAIN`/`EINTR`

`errno`は、システムコールやライブラリ関数がエラーを報告するために使用するグローバル変数（またはスレッドローカル変数）です。

*   **`EAGAIN` (または `EWOULDBLOCK`)**:
    *   「もう一度試してください」という意味のエラーです。
    *   主に非ブロッキングI/O操作で発生します。操作がすぐに完了できない（例えば、ソケットの送信バッファが満杯で、データを書き込むとブロックされる）場合に返されます。
    *   このエラーが返された場合、通常は後で操作を再試行する必要があります。

*   **`EINTR`**:
    *   「中断されたシステムコール」という意味のエラーです。
    *   システムコールが実行中にシグナルによって中断された場合に返されます。
    *   このエラーが返された場合、通常はシステムコールを再試行する必要があります。データ転送は行われていないか、部分的に行われた可能性がありますが、`sendfile`の戻り値は`-1`となります。

### Solaris/SmartOSの`sendfile()`の特殊性

多くのUNIX系OSでは、`sendfile()`が`-1`を返し`errno`が`EAGAIN`または`EINTR`の場合、オフセットポインタは更新されないか、または実際に転送されたバイト数のみを反映するように更新されます。しかし、Solarisおよび一部のBSD系OSでは、`sendfile()`が`-1`を返しても、オフセットポインタが**実際に転送されたバイト数に関わらず**、内部的に進んでしまうという挙動を示すことがありました。これは、`sendfile()`の戻り値とオフセットポインタの更新が独立して行われるためと考えられます。この不整合が、Goの`net`パッケージにおける問題の根本原因でした。

## 技術的詳細

このコミットの技術的詳細な修正は、`src/net/sendfile_solaris.go`ファイル内の`sendFile`関数に集中しています。

Goの`net`パッケージは、`io.Copy`のような高レベルなインターフェースを通じて、可能であればOS固有の`sendfile`実装を呼び出すことでパフォーマンスを最適化します。`netFD`はネットワークファイルディスクリプタを表し、`io.Reader`は読み込み元のデータソース（この場合はファイル）を表します。

修正前のコードでは、`syscall.Sendfile`の呼び出し結果を直接利用していました。

```go
n, err1 := syscall.Sendfile(dst, src, &pos1, n)
```

ここで、`dst`は宛先ソケットのファイルディスクリプタ、`src`はソースファイルのファイルディスクリプタ、`&pos1`は読み込み開始オフセットへのポインタ、`n`は転送を試みるバイト数です。

問題は、Solarisの`syscall.Sendfile`が`err1 == syscall.EAGAIN || err1 == syscall.EINTR`の場合に`-1`を返しても、`pos1`（オフセットポインタ）が内部的に更新されてしまうことにありました。Goのコードは通常、`-1`が返されたら何も書き込まれなかったと判断しますが、`pos1`が更新されていると、次回の`sendfile`呼び出しで誤ったオフセットから読み込みを開始してしまうか、あるいは書き込みバイト数の計算が狂ってしまいます。

このコミットでは、この挙動を以下のように修正しています。

1.  `syscall.Sendfile`呼び出し前に、現在のオフセット`pos`を`pos1`に保存します。
    ```go
    pos1 := pos
    n, err1 := syscall.Sendfile(dst, src, &pos1, n)
    ```
2.  `syscall.Sendfile`が`EAGAIN`または`EINTR`エラーを返した場合に、`pos1`と元の`pos`の差分を計算して、実際に書き込まれたバイト数`n`を再計算します。
    ```go
    if err1 == syscall.EAGAIN || err1 == syscall.EINTR {
        // partial write may have occurred
        if n = int(pos1 - pos); n == 0 {
            // nothing more to write
            err1 = nil
        }
    }
    ```
    *   `n = int(pos1 - pos)`: これが核心的な修正です。`syscall.Sendfile`がエラーを返しても`pos1`が更新されている場合、その差分が実際にカーネルによって処理されたバイト数と見なされます。
    *   `if n == 0`: もし`pos1`が更新されていなかった（つまり`pos1 - pos`が0）にもかかわらず`EAGAIN`または`EINTR`が返された場合、それは「何も書き込まれなかったが、再試行すべき」という状況です。この場合、`err1`を`nil`に設定してエラーを無視し、ループを続行させることで再試行を促します。これにより、Goの`sendfile`ラッパーは、`EAGAIN`や`EINTR`が返された際に、実際に書き込まれたバイト数に基づいて適切に処理を継続できるようになります。

この修正により、Solaris環境での`sendfile`の挙動がGoの期待するセマンティクスに合致し、堅牢なファイル転送が可能になります。

また、`src/net/sendfile_test.go`が新規追加され、`io.Copy`が`sendfile`を利用してファイルを転送するシナリオをテストしています。このテストは、大きなファイル（Mark Twainの「トム・ソーヤーの冒険」のテキストファイル）をTCP接続経由で送信し、受信側でSHA256ハッシュを検証することで、データが正確に転送されたことを確認します。これにより、将来的に同様の問題が再発するのを防ぐための安全網が提供されます。

```go

package net

import (
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"io"
	"os"
	"testing"
)

const (
	twain       = "../compress/testdata/Mark.Twain-Tom.Sawyer.txt"
	twainLen    = 387851
	twainSHA256 = "461eb7cb2d57d293fc680c836464c9125e4382be3596f7d415093ae9db8fcb0e"
)

func TestSendFile(t *testing.T) {
	ln, err := newLocalListener("tcp")
	if err != nil {
		t.Fatal(err)
	}
	defer ln.Close()

	errc := make(chan error, 1)
	go func(ln Listener) {
		// Wait for a connection.
		conn, err := ln.Accept()
		if err != nil {
			errc <- err
			close(errc)
			return
		}

		go func() {
			defer close(errc)
			defer conn.Close()

			f, err := os.Open(twain)
			if err != nil {
				errc <- err
				return
			}
			defer f.Close()

			// Return file data using io.Copy, which should use
			// sendFile if available.
			sbytes, err := io.Copy(conn, f)
			if err != nil {
				errc <- err
				return
			}

			if sbytes != twainLen {
				errc <- fmt.Errorf("sent %d bytes; expected %d", sbytes, twainLen)
				return
			}
		}()
	}(ln)

	// Connect to listener to retrieve file and verify digest matches
	// expected.
	c, err := Dial("tcp", ln.Addr().String())
	if err != nil {
		t.Fatal(err)
	}
	defer c.Close()

	h := sha256.New()
	rbytes, err := io.Copy(h, c)
	if err != nil {
		t.Error(err)
	}

	if rbytes != twainLen {
		t.Errorf("received %d bytes; expected %d", rbytes, twainLen)
	}

	if res := hex.EncodeToString(h.Sum(nil)); res != twainSHA256 {
		t.Error("retrieved data hash did not match")
	}

	for err := range errc {
		t.Error(err)
	}
}
```

## コアとなるコードの解説

### `src/net/sendfile_solaris.go`の変更点

1.  **Solaris `sendfile`の再有効化**:
    以前のコミットで、Issue #13892が解決されるまでSolarisの`sendfile`は無効化されていました（`return // Solaris sendfile is disabled...`の行）。このコミットでは、問題が理解され修正されたため、この無効化コメントが削除され、`sendfile`機能が再び有効になります。

2.  **オフセットポインタの差分計算とエラー処理の改善**:
    *   `pos1 := pos`: `syscall.Sendfile`を呼び出す直前の現在のファイルオフセット`pos`を`pos1`に保存します。
    *   `n, err1 := syscall.Sendfile(dst, src, &pos1, n)`: `syscall.Sendfile`を呼び出します。ここで`&pos1`は、`sendfile`が内部でオフセットを更新するために使用するポインタです。
    *   `if err1 == syscall.EAGAIN || err1 == syscall.EINTR`: `sendfile`が`EAGAIN`または`EINTR`エラーを返した場合の特殊な処理ブロックです。
        *   `if n = int(pos1 - pos); n == 0`: ここが最も重要な変更点です。`sendfile`がエラーを返したにもかかわらず、`pos1`が`pos`から進んでいた場合、その差分（`pos1 - pos`）が実際にカーネルによって処理されたバイト数と見なされます。この差分を`n`に代入し、実際に書き込まれたバイト数として扱います。もし`pos1`が全く進んでいなかった（`n`が0）場合、つまり何も書き込まれなかったがエラーが返された場合は、`err1 = nil`と設定してエラーを無視します。これにより、呼び出し元はエラーとして扱わず、再試行を促すことになります。
    *   `if n > 0`: 実際に`n`バイトが書き込まれた場合、`pos`と`written`カウンタを更新します。

この修正により、Solarisの`sendfile`が`EAGAIN`や`EINTR`を返してもオフセットポインタが更新されるという特殊な挙動を正しく解釈し、Goの`net`パッケージが堅牢に動作するようになります。

### `src/net/sendfile_test.go`の新規追加

このファイルは、`sendfile`機能の正確性を検証するための統合テストです。

1.  **テスト環境のセットアップ**:
    *   `newLocalListener("tcp")`でローカルのTCPリスナーを作成します。
    *   ゴルーチン内で`ln.Accept()`を呼び出し、クライアントからの接続を待ち受けます。

2.  **サーバー側の動作**:
    *   接続が確立されると、別のゴルーチンが起動し、`os.Open(twain)`で大きなテストファイル（「トム・ソーヤーの冒険」）を開きます。
    *   `io.Copy(conn, f)`を呼び出します。Goの`io.Copy`は、ソースが`*os.File`で宛先が`*net.TCPConn`の場合、内部的に`sendfile`のようなゼロコピーメカニズムを利用しようとします。
    *   `io.Copy`が返したバイト数`sbytes`が期待されるファイルサイズ`twainLen`と一致するかを検証します。

3.  **クライアント側の動作**:
    *   `Dial("tcp", ln.Addr().String())`でサーバーに接続します。
    *   `sha256.New()`でSHA256ハッシュ計算機を初期化します。
    *   `io.Copy(h, c)`を呼び出し、受信したデータをハッシュ計算機に書き込みながら読み込みます。
    *   受信したバイト数`rbytes`が期待されるファイルサイズ`twainLen`と一致するかを検証します。
    *   計算されたハッシュ値`hex.EncodeToString(h.Sum(nil))`が期待されるハッシュ値`twainSHA256`と一致するかを検証します。

このテストは、`sendfile`が正しく機能し、データが破損なく完全に転送されることをエンドツーエンドで確認します。特に、Solarisの`sendfile`の特殊な挙動が修正された後も、このテストがパスすることで機能の安定性が保証されます。

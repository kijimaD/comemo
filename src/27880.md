# [インデックス 27880] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) において、動的リンク時に `COPY` リロケーションの生成を抑制し、特にARMアーキテクチャにおいては `gold` リンカを使用するように変更を加えるものです。これにより、特定のセクション（`STYPE`など）が安定したオフセットに依存している場合に、`COPY` リロケーションによってシンボルが移動してしまう問題を回避します。

## 変更の背景

この変更の背景には、動的リンクにおける `COPY` リロケーションの挙動と、特にARMアーキテクチャにおけるGNUリンカ (`ld`) の特定のバグが存在します。

動的リンクでは、実行ファイルが共有ライブラリのシンボルを参照する際に、そのシンボルをどのように解決するかが重要になります。`COPY` リロケーションは、共有ライブラリで定義されたグローバルデータシンボルを実行ファイルの `.bss` セクションにコピーするメカニズムです。これにより、実行ファイルは共有ライブラリのデータとは独立した自身のコピーを持つことができ、実行ファイルがそのデータを変更しても共有ライブラリの元のデータには影響を与えません。

しかし、この `COPY` リロケーションはいくつかの問題を引き起こす可能性があります。特に、Go言語のランタイムのような低レベルなコードでは、特定のセクション（例えば `STYPE` と呼ばれるセクション）が、そのセクションの先頭からの安定したオフセットに依存している場合があります。`COPY` リロケーションが発生すると、リンカはシンボルを元の場所から `.bss` セクションに移動させるため、この安定したオフセットの前提が崩れてしまう可能性があります。これは、Goランタイムが内部的に使用するデータ構造やポインタの計算に影響を与え、予期せぬ動作やクラッシュにつながる恐れがあります。

さらに、ARMアーキテクチャのGNUリンカには、`-znocopyreloc` オプションが指定されていても `COPY` リロケーションを生成してしまうという既知のバグ（Bugzilla ID: 19962）が存在しました。このバグにより、Goのリンカが `COPY` リロケーションを抑制しようとしても、ARM環境では意図せず生成されてしまい、上記の問題が発生する可能性がありました。

このコミットは、これらの問題を解決するために、動的リンク時に `COPY` リロケーションを明示的に抑制し、特にARMアーキテクチャでは `gold` リンカを使用することで、GNUリンカのバグを回避することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

1.  **ELF (Executable and Linkable Format)**:
    Unix系システムで実行ファイル、オブジェクトファイル、共有ライブラリなどに使用される標準的なファイルフォーマットです。ELFファイルは、ヘッダ、プログラムヘッダ、セクションヘッダなどで構成され、コードやデータを構造化して格納します。

2.  **動的リンク (Dynamic Linking)**:
    プログラムの実行時に外部ライブラリ（共有ライブラリ、`.so`ファイル）をリンクするプロセスです。静的リンクとは異なり、ライブラリのコードは実行ファイルに完全に組み込まれず、実行時にロードされます。これにより、ディスクスペースの削減、メモリ使用量の効率化、ライブラリの独立した更新などの利点があります。動的リンカ（Linuxでは `ld.so` など）が、実行時にシンボル解決やリロケーションを行います。

3.  **リロケーション (Relocation)**:
    プログラム内のアドレス参照を、最終的なメモリ上のアドレスに調整するプロセスです。コンパイル時には、コードやデータが最終的にどこに配置されるか分からないため、仮のアドレスが使用されます。リンク時（静的リンク）や実行時（動的リンク）に、これらの仮のアドレスを実際のメモリ上のアドレスに修正するのがリロケーションです。

4.  **`COPY` リロケーション**:
    動的リンクにおける特定のリロケーションタイプの一つです。共有ライブラリで定義されたグローバルな初期化済みデータシンボルを、実行ファイルの `.bss` セクションにコピーするために使用されます。これにより、実行ファイルは共有ライブラリのデータとは独立した、書き込み可能な自身のコピーを持つことができます。実行ファイルがこのデータを変更しても、共有ライブラリの元のデータには影響しません。

5.  **`gold` リンカ**:
    GNU Binutilsプロジェクトの一部として開発された、高速なリンカです。従来のGNU `ld` リンカと比較して、大規模なプロジェクトでのリンク時間を大幅に短縮することを目的としています。また、`gold` リンカは `ld` とは異なる実装を持つため、特定のバグや挙動の違いが存在することがあります。

6.  **`-Wl` オプション**:
    GCCなどのコンパイラドライバで、リンカに直接オプションを渡すためのフラグです。例えば、`-Wl,-znow` はリンカに `-znow` オプションを渡すことを意味します。

7.  **`-znocopyreloc` リンカオプション**:
    リンカに対して、`COPY` リロケーションの生成を抑制するように指示するオプションです。これにより、共有ライブラリのグローバルデータシンボルが実行ファイルの `.bss` セクションにコピーされるのを防ぎます。

8.  **`STYPE` セクションと安定したオフセット**:
    `STYPE` は特定のELFセクションタイプを指すものではなく、Goランタイムが内部的に使用する特定のデータ構造やセクションを指している可能性があります。一般的に、低レベルなシステムプログラミングでは、特定のデータ構造がメモリ上の固定されたオフセットに配置されることを前提とする場合があります。このような「安定したオフセット」は、ポインタ演算やアセンブリコードでのアクセスにおいて非常に重要です。`COPY` リロケーションによってシンボルが移動すると、このオフセットの安定性が損なわれ、プログラムの誤動作につながる可能性があります。

## 技術的詳細

このコミットは、Go言語のリンカ (`src/cmd/link/internal/ld/lib.go`) の `hostlink` 関数に変更を加えています。`hostlink` 関数は、Goプログラムをホストシステムのリンカ（通常はGCCのラッパーを介して呼び出されるGNU `ld` または `gold`）を使ってリンクする際の処理を担っています。

変更点は以下の2つです。

1.  **`-Wl,-znocopyreloc` の追加**:
    `argv = append(argv, "-Wl,-znocopyreloc")` の行が追加されています。これは、ホストリンカに対して `COPY` リロケーションを生成しないように指示するオプションです。これにより、共有ライブラリのグローバルデータシンボルが実行ファイルの `.bss` セクションにコピーされるのを防ぎます。この抑制は、Goランタイムが安定したオフセットに依存するセクション（`STYPE`など）を持つ場合に、シンボルが予期せず移動するのを防ぐために重要です。

2.  **ARMアーキテクチャでの `gold` リンカの使用**:
    `if SysArch.Family == sys.ARM` の条件ブロックが追加されています。このブロック内では、`argv = append(argv, "-fuse-ld=gold")` の行が実行されます。これは、システムアーキテクチャがARMである場合に、明示的に `gold` リンカを使用するようにホストリンカに指示するものです。
    この変更は、GNUリンカがARMアーキテクチャにおいて、`-znocopyreloc` オプションが指定されていても `COPY` リロケーションを生成してしまうという既知のバグ（Bugzilla ID: 19962）を回避するために導入されました。`gold` リンカはこのバグの影響を受けないため、ARM環境でのリンクの信頼性を向上させます。

これらの変更により、Goプログラムが動的リンクされる際に、`COPY` リロケーションによる潜在的な問題が回避され、特にARMアーキテクチャでの安定性が向上します。

変更は `src/cmd/link/internal/ld/lib.go` ファイルの `hostlink` 関数内で行われています。

```diff
 		// times we cannot allow it to do so.

+		// can move symbols out of sections that rely on stable offsets

+			// even with -znocopyreloc set. Switch to gold.
+			// https://sourceware.org/bugzilla/show_bug.cgi?id=19962
+			argv = append(argv, "-fuse-ld=gold")
+		}
 	}

```

## コアとなるコードの解説

追加されたコードは、`hostlink` 関数内でリンカに渡す引数 (`argv`) を操作しています。

1.  `argv = append(argv, "-Wl,-znocopyreloc")`
    この行は、リンカに `-znocopyreloc` オプションを渡すためのものです。`-Wl,` プレフィックスは、コンパイラドライバがこのオプションをリンカに直接渡すことを示します。`-znocopyreloc` は、リンカが `COPY` リロケーションを生成するのを防ぎます。これは、Goランタイムが内部的に使用する特定のセクション（例えば `STYPE`）が、そのセクションの先頭からのオフセットに厳密に依存しているため、`COPY` リロケーションによってシンボルが移動すると問題が発生する可能性があるためです。

2.  `if SysArch.Family == sys.ARM { ... }`
    この条件文は、現在のシステムアーキテクチャがARMファミリーであるかどうかをチェックします。`SysArch.Family` は `go/build/sys` パッケージで定義されているアーキテクチャファミリーを表す定数です。

3.  `argv = append(argv, "-fuse-ld=gold")`
    `SysArch.Family` が `sys.ARM` である場合にのみ実行されるこの行は、リンカに `gold` リンカを使用するように指示します。`-fuse-ld=` オプションは、使用するリンカを指定するためのものです。
    この特定の変更は、GNUリンカがARMアーキテクチャにおいて、`-znocopyreloc` オプションが指定されていても `COPY` リロケーションを誤って生成してしまうというバグ（Bugzilla ID: 19962）を回避するために不可欠です。`gold` リンカは、このバグの影響を受けないため、ARM環境でのGoプログラムの動的リンクの信頼性を確保します。

これらの変更により、Goのビルドシステムは、動的リンク時に `COPY` リロケーションによる問題を回避し、特にARMアーキテクチャでのリンカの挙動をより堅牢に制御できるようになります。

# [インデックス 22522] ファイルの概要

このコミットは、Goコンパイラの内部における最適化に関するものです。具体的には、アセンブリ命令の情報を保持する`ProgInfo`構造体を、各命令を表す`Prog`構造体自身にキャッシュするように変更しています。これにより、命令の解析パス中に何度も`ProgInfo`をロードするオーバーヘッドを削減し、コンパイラのパフォーマンス向上を図っています。

## 変更の背景

Goコンパイラのバックエンドでは、コードの最適化を行う際に、各アセンブリ命令（`obj.Prog`）がどのような特性を持つか（例: どのレジスタを読み書きするか、ジャンプ命令か、関数呼び出し命令かなど）を頻繁に参照します。この命令の特性情報は`ProgInfo`構造体にカプセル化され、通常は`proginfo()`関数を呼び出すことで取得されていました。

しかし、コンパイラの解析パス（特にライブ変数解析や最適化パス）では、同じ命令に対して何度も`proginfo()`関数が呼び出され、そのたびに`ProgInfo`が計算・ロードされるという非効率な処理が行われていました。これは、特に大規模な関数や複雑な制御フローを持つコードにおいて、コンパイル時間の増加につながる可能性がありました。

このコミットの目的は、この冗長な`proginfo()`呼び出しを排除し、命令の`ProgInfo`を一度計算したら、それを`Prog`構造体自体にキャッシュすることで、コンパイラのパフォーマンスを向上させることにあります。これにより、命令の特性情報へのアクセスが高速化され、全体的なコンパイル時間の短縮が期待されます。コミットメッセージにある「previous CL more than compensates」という記述は、以前の変更で`Prog`構造体が大きくなったとしても、今回の最適化によるメリットがそれを上回ることを示唆しています。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラのバックエンドにおけるいくつかの基本的な概念を理解しておく必要があります。

*   **Goコンパイラ (`gc`)**: Go言語の公式コンパイラです。ソースコードを機械語に変換する過程で、様々な最適化を行います。このコミットで変更されているファイル群（`src/cmd/5g`, `src/cmd/6g`, `src/cmd/7g`, `src/cmd/8g`, `src/cmd/9g`など）は、それぞれ異なるアーキテクチャ（ARM、x86、ARM64、PPC64など）向けのコンパイラバックエンドの一部です。`src/cmd/internal/gc`は、これらのアーキテクチャ固有のバックエンドで共通して使用されるコードを含んでいます。
*   **`obj.Prog`**: Goコンパイラのバックエンドが使用する中間表現（IR）における「プログラム命令」の単位です。これは、特定のアセンブリ命令（例: `ADD`, `MOV`, `CALL`, `JMP`など）とそのオペランド（ソース、デスティネーションなど）を表します。コンパイラは、この`Prog`のリストを操作して最適化を行い、最終的に実行可能なバイナリを生成します。
*   **`gc.ProgInfo`**: 各`obj.Prog`（命令）に関する詳細なメタデータを提供する構造体です。この情報には、以下のようなフラグが含まれます。
    *   `Flags`: 命令のタイプ（例: `gc.Call`は関数呼び出し、`gc.Jump`はジャンプ命令、`gc.LeftRead`は左オペランドを読み取る、`gc.RightWrite`は右オペランドに書き込むなど）や、レジスタの使用状況（キャリーフラグへの影響など）を示します。
    *   `Reguse`: 命令が暗黙的に使用するレジスタのビットマスク。
    *   `Regset`: 命令が暗黙的に設定するレジスタのビットマスク。
    *   `Regindex`: アドレッシングモードによって使用されるレジスタのビットマスク。
    これらの情報は、ライブ変数解析（どの変数がどの時点で「生きている」か）、レジスタ割り当て、デッドコード削除などの最適化パスで非常に重要となります。
*   **`proginfo()` 関数**: 以前のバージョンでは、この関数が`obj.Prog`を受け取り、その命令に対応する`gc.ProgInfo`構造体を計算して返していました。この関数は、命令のオペコードやオペランドの種類に基づいて、適切な`ProgInfo`を決定します。
*   **最適化パス**: Goコンパイラには、生成されるコードの効率を高めるための様々な最適化パスがあります。
    *   **`plive.go` (ライブ変数解析)**: プログラムの各ポイントでどの変数が将来使用される可能性があるか（ライブであるか）を決定する解析です。これにより、不要な変数のメモリ割り当てを解放したり、デッドコードを削除したりできます。この解析では、各命令がレジスタやメモリをどのように使用・変更するかを知るために`ProgInfo`が頻繁に参照されます。
    *   **`popt.go` (ピーホール最適化)**: 小さな命令シーケンスをより効率的なシーケンスに置き換える最適化です。例えば、`MOV A, B; MOV B, C`を`MOV A, C`に置き換えるなどです。ここでも、命令の特性（読み書きするレジスタなど）を理解するために`ProgInfo`が使われます。
    *   **`Flowstart`**: 最適化パスの開始時に呼び出される関数で、プログラムの制御フローグラフ（CFG）を構築し、各命令の初期情報を設定します。

## 技術的詳細

このコミットの核心は、`ProgInfo`の取得方法を「オンデマンド計算」から「事前キャッシュ」へと変更した点にあります。

**変更前**:
各最適化パスのコード（例: `peep.go`, `plive.go`, `popt.go`）では、特定の`obj.Prog`の`ProgInfo`が必要になるたびに、以下のように`proginfo()`関数を呼び出していました。

```go
var info gc.ProgInfo
info = proginfo(p) // または Thearch.Proginfo(p)
// info を使用して処理を行う
```

このアプローチでは、同じ`Prog`に対して何度も`proginfo()`が呼び出されると、そのたびに同じ計算が繰り返され、パフォーマンスのボトルネックとなっていました。

**変更後**:
このコミットでは、`obj.Prog`構造体に直接`Info`というフィールドを追加し、そこに`ProgInfo`を格納するようにしました。

```go
type Prog struct {
    // ... 既存のフィールド ...
    Info ProgInfo // 新しく追加されたフィールド
    // ...
}
```

そして、`proginfo()`関数のシグネチャを変更し、`ProgInfo`を返すのではなく、引数として渡された`obj.Prog`の`Info`フィールドを直接更新するようにしました。

```go
// 変更前: func proginfo(p *obj.Prog) (info gc.ProgInfo)
// 変更後: func proginfo(p *obj.Prog)
func proginfo(p *obj.Prog) {
    info := &p.Info // p.Infoへのポインタを取得
    *info = progtable[p.As] // progtableから情報をコピーしてp.Infoを更新
    // ... その他の処理 ...
}
```

これにより、`Flowstart`関数や`plive.go`内の`newcfg`関数など、最適化パスの開始時や制御フローグラフ構築時に、各`Prog`に対して一度だけ`Thearch.Proginfo(p)`（アーキテクチャ固有の`proginfo`実装を呼び出す）を呼び出すことで、その`Prog`の`ProgInfo`が`p.Info`にキャッシュされます。

以降、その`Prog`の`ProgInfo`が必要になった場合は、`proginfo(p)`を呼び出す代わりに、直接`p.Info`を参照するようになります。

```go
// 変更前: info.Flags & gc.Call != 0
// 変更後: p.Info.Flags & gc.Call != 0
```

**メリット**:
*   **パフォーマンス向上**: `proginfo()`関数の冗長な呼び出しがなくなるため、コンパイル時間が短縮されます。特に、命令の特性情報を頻繁に参照する最適化パスにおいて効果が大きいです。
*   **コードの簡素化**: 各所で`proginfo()`を呼び出してローカル変数に`ProgInfo`を格納する必要がなくなり、コードがより直接的になります。

**トレードオフ**:
*   **メモリ使用量の増加**: 各`obj.Prog`構造体に`ProgInfo`が直接埋め込まれるため、プログラム全体の`Prog`オブジェクトの総数によっては、わずかにメモリ使用量が増加する可能性があります。しかし、コミットメッセージにあるように「previous CL more than compensates」とあり、以前の変更でメモリ使用量が削減されたため、全体としては問題ないと判断されています。

この変更は、Goコンパイラのバックエンドにおける命令処理の効率を根本的に改善するものであり、コンパイル時間の最適化に貢献します。

## コアとなるコードの解説

このコミットの主要な変更は、`ProgInfo`の情報を`obj.Prog`構造体自体に直接格納するようにしたことです。これにより、コンパイラの最適化パスで命令の特性情報を取得する際のオーバーヘッドが大幅に削減されます。

具体的には、以下の点が重要です。

1.  **`ProgInfo`の埋め込み**:
    以前は、`gc.ProgInfo`は独立した構造体であり、`proginfo()`関数がそのインスタンスを返していました。このコミットでは、`obj.Prog`構造体（各アーキテクチャの`src/cmd/*/prog.go`で定義されている）に`Info ProgInfo`というフィールドが追加されました。これにより、各命令オブジェクトが自身の特性情報を直接保持できるようになります。

2.  **`proginfo`関数の役割変更**:
    `proginfo`関数（各アーキテクチャの`src/cmd/*/prog.go`に実装されている）は、もはや`ProgInfo`を返しません。代わりに、引数として渡された`*obj.Prog`の`Info`フィールドを直接初期化するようになりました。
    例えば、`src/cmd/5g/prog.go`の`proginfo`関数では、以下のように変更されています。

    ```go
    // 変更前: func proginfo(p *obj.Prog) (info gc.ProgInfo)
    // 変更後: func proginfo(p *obj.Prog)
    func proginfo(p *obj.Prog) {
        info := &p.Info // p.Infoへのポインタを取得
        *info = progtable[p.As] // progtableから命令の基本情報をp.Infoにコピー
        // ... その後、命令のオペランドなどに基づいてinfoのフラグやレジスタ情報をさらに設定 ...
    }
    ```
    この変更により、`proginfo`は命令の特性情報を計算し、それを命令オブジェクト自身に「書き込む」役割を担うことになります。

3.  **`ProgInfo`の利用箇所の変更**:
    `peep.go`（ピーホール最適化）、`plive.go`（ライブ変数解析）、`popt.go`（一般的な最適化）など、コンパイラの様々な最適化パスで`ProgInfo`が利用されていました。これらのファイルでは、以前は`info := proginfo(p)`のようにローカル変数に`ProgInfo`を格納していましたが、このコミット以降は直接`p.Info`フィールドを参照するようになりました。

    例えば、`src/cmd/5g/peep.go`の`subprop`関数では、以下のような変更が見られます。

    ```go
    // 変更前:
    // var info gc.ProgInfo
    // info = proginfo(p)
    // if info.Flags&gc.Call != 0 { ... }

    // 変更後:
    // // var info gc.ProgInfo (削除)
    // // proginfo(p) // 必要に応じて、p.Infoがまだ設定されていない場合に呼び出す
    // if p.Info.Flags&gc.Call != 0 { ... }
    ```
    特に注目すべきは、`src/cmd/5g/peep.go`の`subprop`関数内で`proginfo(p)`が明示的に呼び出されている箇所です。これは、`p.Info`がまだ設定されていない可能性があるため、または特定の最適化の文脈で最新の`ProgInfo`が必要な場合に、その場で計算してキャッシュを更新していることを示唆しています。

4.  **初期化の集中化**:
    `src/cmd/internal/gc/plive.go`の`newcfg`関数や`src/cmd/internal/gc/popt.go`の`Flowstart`関数など、命令リストを走査する初期段階で、各`obj.Prog`に対して`Thearch.Proginfo(p)`が呼び出されるようになりました。これは、命令の特性情報を一度だけ計算し、それを`p.Info`にキャッシュする「集中管理」のポイントとなります。これにより、後続の最適化パスでは、計算済みの`p.Info`を直接参照できるため、効率が向上します。

この一連の変更により、Goコンパイラは命令の特性情報へのアクセスを最適化し、コンパイル時間の短縮に貢献しています。

The ProgInfo is loaded many times during each analysis pass.

## 変更の背景

Goコンパイラのバックエンドでは、コードの最適化を行う際に、各アセンブリ命令（`obj.Prog`）がどのような特性を持つか（例: どのレジスタを読み書きするか、ジャンプ命令か、関数呼び出し命令かなど）を頻繁に参照します。この命令の特性情報は`ProgInfo`構造体にカプセル化され、通常は`proginfo()`関数を呼び出すことで取得されていました。

しかし、コンパイラの解析パス（特にライブ変数解析や最適化パス）では、同じ命令に対して何度も`proginfo()`関数が呼び出され、そのたびに`ProgInfo`が計算・ロードされるという非効率な処理が行われていました。これは、特に大規模な関数や複雑な制御フローを持つコードにおいて、コンパイル時間の増加につながる可能性がありました。

このコミットの目的は、この冗長な`proginfo()`呼び出しを排除し、命令の`ProgInfo`を一度計算したら、それを`Prog`構造体自体にキャッシュすることで、コンパイラのパフォーマンスを向上させることにあります。これにより、命令の特性情報へのアクセスが高速化され、全体的なコンパイル時間の短縮が期待されます。コミットメッセージにある「previous CL more than compensates」という記述は、以前の変更で`Prog`構造体が大きくなったとしても、今回の最適化によるメリットがそれを上回ることを示唆しています。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラのバックエンドにおけるいくつかの基本的な概念を理解しておく必要があります。

*   **Goコンパイラ (`gc`)**: Go言語の公式コンパイラです。ソースコードを機械語に変換する過程で、様々な最適化を行います。このコミットで変更されているファイル群（`src/cmd/5g`, `src/cmd/6g`, `src/cmd/7g`, `src/cmd/8g`, `src/cmd/9g`など）は、それぞれ異なるアーキテクチャ（ARM、x86、ARM64、PPC64など）向けのコンパイラバックエンドの一部です。`src/cmd/internal/gc`は、これらのアーキテクチャ固有のバックエンドで共通して使用されるコードを含んでいます。
*   **`obj.Prog`**: Goコンパイラのバックエンドが使用する中間表現（IR）における「プログラム命令」の単位です。これは、特定のアセンブリ命令（例: `ADD`, `MOV`, `CALL`, `JMP`など）とそのオペランド（ソース、デスティネーションなど）を表します。コンパイラは、この`Prog`のリストを操作して最適化を行い、最終的に実行可能なバイナリを生成します。
*   **`gc.ProgInfo`**: 各`obj.Prog`（命令）に関する詳細なメタデータを提供する構造体です。この情報には、以下のようなフラグが含まれます。
    *   `Flags`: 命令のタイプ（例: `gc.Call`は関数呼び出し、`gc.Jump`はジャンプ命令、`gc.LeftRead`は左オペランドを読み取る、`gc.RightWrite`は右オペランドに書き込むなど）や、レジスタの使用状況（キャリーフラグへの影響など）を示します。
    *   `Reguse`: 命令が暗黙的に使用するレジスタのビットマスク。
    *   `Regset`: 命令が暗黙的に設定するレジスタのビットマスク。
    *   `Regindex`: アドレッシングモードによって使用されるレジスタのビットマスク。
    これらの情報は、ライブ変数解析（どの変数がどの時点で「生きている」か）、レジスタ割り当て、デッドコード削除などの最適化パスで非常に重要となります。
*   **`proginfo()` 関数**: 以前のバージョンでは、この関数が`obj.Prog`を受け取り、その命令に対応する`gc.ProgInfo`構造体を計算して返していました。この関数は、命令のオペコードやオペランドの種類に基づいて、適切な`ProgInfo`を決定します。
*   **最適化パス**: Goコンパイラには、生成されるコードの効率を高めるための様々な最適化パスがあります。
    *   **`plive.go` (ライブ変数解析)**: プログラムの各ポイントでどの変数が将来使用される可能性があるか（ライブであるか）を決定する解析です。これにより、不要な変数のメモリ割り当てを解放したり、デッドコードを削除したりできます。この解析では、各命令がレジスタやメモリをどのように使用・変更するかを知るために`ProgInfo`が頻繁に参照されます。
    *   **`popt.go` (ピーホール最適化)**: 小さな命令シーケンスをより効率的なシーケンスに置き換える最適化です。例えば、`MOV A, B; MOV B, C`を`MOV A, C`に置き換えるなどです。ここでも、命令の特性（読み書きするレジスタなど）を理解するために`ProgInfo`が使われます。
    *   **`Flowstart`**: 最適化パスの開始時に呼び出される関数で、プログラムの制御フローグラフ（CFG）を構築し、各命令の初期情報を設定します。

## 技術的詳細

このコミットの核心は、`ProgInfo`の取得方法を「オンデマンド計算」から「事前キャッシュ」へと変更した点にあります。

**変更前**:
各最適化パスのコード（例: `peep.go`, `plive.go`, `popt.go`）では、特定の`obj.Prog`の`ProgInfo`が必要になるたびに、以下のように`proginfo()`関数を呼び出していました。

```go
var info gc.ProgInfo
info = proginfo(p) // または Thearch.Proginfo(p)
// info を使用して処理を行う
```

このアプローチでは、同じ`Prog`に対して何度も`proginfo()`が呼び出されると、そのたびに同じ計算が繰り返され、パフォーマンスのボトルネックとなっていました。

**変更後**:
このコミットでは、`obj.Prog`構造体に直接`Info`というフィールドを追加し、そこに`ProgInfo`を格納するようにしました。

```go
type Prog struct {
    // ... 既存のフィールド ...
    Info ProgInfo // 新しく追加されたフィールド
    // ...
}
```

そして、`proginfo()`関数のシグネチャを変更し、`ProgInfo`を返すのではなく、引数として渡された`obj.Prog`の`Info`フィールドを直接更新するようにしました。

```go
// 変更前: func proginfo(p *obj.Prog) (info gc.ProgInfo)
// 変更後: func proginfo(p *obj.Prog)
func proginfo(p *obj.Prog) {
    info := &p.Info // p.Infoへのポインタを取得
    *info = progtable[p.As] // progtableから情報をコピーしてp.Infoを更新
    // ... その他の処理 ...
}
```

これにより、`Flowstart`関数や`plive.go`内の`newcfg`関数など、最適化パスの開始時や制御フローグラフ構築時に、各`Prog`に対して一度だけ`Thearch.Proginfo(p)`（アーキテクチャ固有の`proginfo`実装を呼び出す）を呼び出すことで、その`Prog`の`ProgInfo`が`p.Info`にキャッシュされます。

以降、その`Prog`の`ProgInfo`が必要になった場合は、`proginfo(p)`を呼び出す代わりに、直接`p.Info`を参照するようになります。

```go
// 変更前: info.Flags & gc.Call != 0
// 変更後: p.Info.Flags & gc.Call != 0
```

**メリット**:
*   **パフォーマンス向上**: `proginfo()`関数の冗長な呼び出しがなくなるため、コンパイル時間が短縮されます。特に、命令の特性情報を頻繁に参照する最適化パスにおいて効果が大きいです。
*   **コードの簡素化**: 各所で`proginfo()`を呼び出してローカル変数に`ProgInfo`を格納する必要がなくなり、コードがより直接的になります。

**トレードオフ**:
*   **メモリ使用量の増加**: 各`obj.Prog`構造体に`ProgInfo`が直接埋め込まれるため、プログラム全体の`Prog`オブジェクトの総数によっては、わずかにメモリ使用量が増加する可能性があります。しかし、コミットメッセージにあるように「previous CL more than compensates」とあり、以前の変更でメモリ使用量が削減されたため、全体としては問題ないと判断されています。

この変更は、Goコンパイラのバックエンドにおける命令処理の効率を根本的に改善するものであり、コンパイル時間の最適化に貢献します。

## コアとなるコードの解説

このコミットの主要な変更は、`ProgInfo`の情報を`obj.Prog`構造体自体に直接格納するようにしたことです。これにより、コンパイラの最適化パスで命令の特性情報を取得する際のオーバーヘッドが大幅に削減されます。

具体的には、以下の点が重要です。

1.  **`ProgInfo`の埋め込み**:
    以前は、`gc.ProgInfo`は独立した構造体であり、`proginfo()`関数がそのインスタンスを返していました。このコミットでは、`obj.Prog`構造体（各アーキテクチャの`src/cmd/*/prog.go`で定義されている）に`Info ProgInfo`というフィールドが追加されました。これにより、各命令オブジェクトが自身の特性情報を直接保持できるようになります。

2.  **`proginfo`関数の役割変更**:
    `proginfo`関数（各アーキテクチャの`src/cmd/*/prog.go`に実装されている）は、もはや`ProgInfo`を返しません。代わりに、引数として渡された`*obj.Prog`の`Info`フィールドを直接初期化するようになりました。
    例えば、`src/cmd/5g/prog.go`の`proginfo`関数では、以下のように変更されています。

    ```go
    // 変更前: func proginfo(p *obj.Prog) (info gc.ProgInfo)
    // 変更後: func proginfo(p *obj.Prog)
    func proginfo(p *obj.Prog) {
        info := &p.Info // p.Infoへのポインタを取得
        *info = progtable[p.As] // progtableから命令の基本情報をp.Infoにコピー
        // ... その後、命令のオペランドなどに基づいてinfoのフラグやレジスタ情報をさらに設定 ...
    }
    ```
    この変更により、`proginfo`は命令の特性情報を計算し、それを命令オブジェクト自身に「書き込む」役割を担うことになります。

3.  **`ProgInfo`の利用箇所の変更**:
    `peep.go`（ピーホール最適化）、`plive.go`（ライブ変数解析）、`popt.go`（一般的な最適化）など、コンパイラの様々な最適化パスで`ProgInfo`が利用されていました。これらのファイルでは、以前は`info := proginfo(p)`のようにローカル変数に`ProgInfo`を格納していましたが、このコミット以降は直接`p.Info`フィールドを参照するようになりました。

    例えば、`src/cmd/5g/peep.go`の`subprop`関数では、以下のような変更が見られます。

    ```go
    // 変更前:
    // var info gc.ProgInfo
    // info = proginfo(p)
    // if info.Flags&gc.Call != 0 { ... }

    // 変更後:
    // // var info gc.ProgInfo (削除)
    // // proginfo(p) // 必要に応じて、p.Infoがまだ設定されていない場合に呼び出す
    // if p.Info.Flags&gc.Call != 0 { ... }
    ```
    特に注目すべきは、`src/cmd/5g/peep.go`の`subprop`関数内で`proginfo(p)`が明示的に呼び出されている箇所です。これは、`p.Info`がまだ設定されていない可能性があるため、または特定の最適化の文脈で最新の`ProgInfo`が必要な場合に、その場で計算してキャッシュを更新していることを示唆しています。

4.  **初期化の集中化**:
    `src/cmd/internal/gc/plive.go`の`newcfg`関数や`src/cmd/internal/gc/popt.go`の`Flowstart`関数など、命令リストを走査する初期段階で、各`obj.Prog`に対して`Thearch.Proginfo(p)`が呼び出されるようになりました。これは、命令の特性情報を一度だけ計算し、それを`p.Info`にキャッシュする「集中管理」のポイントとなります。これにより、後続の最適化パスでは、計算済みの`p.Info`を直接参照できるため、効率が向上します。

この一連の変更により、Goコンパイラは命令の特性情報へのアクセスを最適化し、コンパイル時間の短縮に貢献しています。

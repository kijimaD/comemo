# [インデックス 20807] ファイルの概要

このコミットは、GoランタイムにおけるWindows環境での例外処理メカニズムの改善を目的としています。特に、GoプログラムがWindows上で予期せぬ例外（クラッシュなど）に遭遇した際の挙動をより堅牢にし、デバッグ時の挙動も考慮に入れています。以前の変更の取り消しを含みつつ、`SetUnhandledExceptionFilter`の利用方法の調整や、例外ハンドラ内で`EXCEPTION_BREAKPOINT`を受け取った際のクラッシュ挙動の導入が行われています。

## 元コミット内容

このコミットは、GoランタイムがWindows環境で発生するあらゆる例外を処理するための「2回目の試み」です。具体的には、以下の変更が含まれています。

*   以前のコミット `22318cd31d7d` の変更を取り消しています。
*   Windows-386アーキテクチャでは常に `SetUnhandledExceptionFilter` を使用するように変更しています。
*   例外ハンドラ内で `EXCEPTION_BREAKPOINT` を受け取った場合にクラッシュするようになります。

この変更は、Issue `#8006` を修正することを目的としています。

## 変更の背景

GoプログラムがWindows上で実行される際、メモリ違反、ゼロ除算、不正な命令などの様々なハードウェア例外やソフトウェア例外が発生する可能性があります。Windowsはこれらの例外を処理するための構造化例外処理 (SEH: Structured Exception Handling) やベクタ例外処理 (VEH: Vectored Exception Handling) といったメカニズムを提供しています。Goランタイムは、これらのOSレベルの例外を捕捉し、Goのパニック（panic）機構に変換することで、プログラムが予期せぬ終了をせずに回復したり、より制御された形で終了したりできるようにする必要があります。

このコミットの背景には、GoランタイムがWindows例外を適切に処理できていなかった、あるいは特定のシナリオ（特にデバッグ時や特定のアーキテクチャ）で問題が発生していたという課題があったと考えられます。コミットメッセージにある「second attempt」という記述や、特定のコミットの「undo」が含まれていることから、以前の例外処理の実装に問題があり、それを修正・改善するための再設計が行われたことが示唆されます。特に、デバッガが使用する`EXCEPTION_BREAKPOINT`の扱いを明確にすることで、デバッグ時の挙動を予測可能にし、Goプログラムの安定性を向上させる狙いがあります。

## 前提知識の解説

このコミットを理解するためには、以下のWindows例外処理に関する概念とGoランタイムの基本的な挙動について理解しておく必要があります。

1.  **Windows例外処理 (Structured Exception Handling - SEH)**:
    Windows OSが提供する例外処理の基本的なメカニズムです。C/C++の`__try`, `__except`, `__finally`ブロックなどを用いて、特定のコードブロック内で発生した例外を捕捉し、処理することができます。SEHはスレッドローカルであり、スタックフレームベースで動作します。

2.  **Vectored Exception Handling (VEH)**:
    Windows XPで導入された、SEHを拡張する例外処理メカニズムです。VEHはプロセスグローバルな例外ハンドラであり、`AddVectoredExceptionHandler`関数を使用して登録されます。VEHハンドラは、SEHハンドラよりも**先に**呼び出されるため、アプリケーション全体で例外を捕捉するのに適しています。Goランタイムのような低レベルのシステムがOSからの例外を捕捉する際に利用されます。

3.  **Vectored Continue Handling (VCH)**:
    VEHと密接に関連するメカニズムです。`AddVectoredContinueHandler`関数で登録され、例外ハンドラ（VEHまたはSEH）が例外を処理し、`EXCEPTION_CONTINUE_EXECUTION`を返して実行を再開しようとした場合に呼び出されます。これにより、プログラムが実行を再開する前に、実行コンテキストを変更する機会が提供されます。

4.  **`SetUnhandledExceptionFilter`**:
    この関数は、プロセス全体で、どの例外ハンドラにも捕捉されなかった例外（未処理例外）が発生した場合に呼び出される、トップレベルの例外フィルタ関数を設定します。これは、OSがデフォルトの未処理例外の挙動（クラッシュダイアログの表示やアプリケーションの終了など）を実行する前の「最後の砦」として機能します。デバッガがアタッチされている場合、このフィルタは呼び出されないことがあります。

5.  **`EXCEPTION_BREAKPOINT` (0x80000003)**:
    これは、ブレークポイントが検出されたことを示す特定の例外コードです。通常、デバッガがプログラムの実行を一時停止するために生成します。デバッガがアタッチされている場合、通常はこの例外を処理し、プログラムの実行を一時停止します。デバッガが存在しない場合や、デバッガがこの例外を処理しないことを選択した場合、この例外は他の例外処理メカニズム（SEHやVEH）によって処理される可能性があります。

6.  **Goランタイムのパニック (panic)**:
    Go言語におけるエラー処理メカニズムの一つで、プログラムの回復不可能なエラーを示すために使用されます。Goランタイムは、OSレベルの例外（例えば、アクセス違反）を捕捉し、それをGoのパニックに変換することで、Goプログラムが`recover`関数を使ってパニックから回復したり、適切なスタックトレースを出力して終了したりできるようにします。

## 技術的詳細

このコミットの技術的詳細は、GoランタイムがWindowsの例外処理メカニズムとどのように連携し、特定のシナリオでその挙動をどのように調整しているかにあります。

*   **VEHとVCHの利用**:
    Goランタイムは、`AddVectoredExceptionHandler`を使用して`runtime·exceptiontramp`をVEHとして登録しています。これにより、Goのコード内で発生した例外をOSレベルで最初に捕捉できるようになります。
    また、`AddVectoredContinueHandler`を使用して`runtime·firstcontinuetramp`と`runtime·lastcontinuetramp`をVCHとして登録しています。これは、例外処理後に実行を継続する際の挙動を制御するためです。特に、`firstcontinuetramp`は、`exceptionhandler`が例外を処理して実行継続を指示した場合に、WindowsがVCHのリストを検索するのを停止させる役割を担います。`lastcontinuetramp`は、Goランタイムが例外を処理できなかった場合に、クラッシュ情報を出力して終了する最終的なハンドラとして機能します。

*   **`SetUnhandledExceptionFilter`の利用**:
    Windows-386アーキテクチャの場合、または`AddVectoredContinueHandler`が利用できない場合（例えば、古いWindowsバージョン）、Goランタイムは`SetUnhandledExceptionFilter`を使用して`runtime·lastcontinuetramp`を未処理例外フィルタとして設定します。これは、VEH/VCHが利用できない、または機能しない場合のフォールバックメカニズムとして機能し、Goプログラムが未処理例外に遭遇した際に、少なくともGoランタイムが制御を奪い、クラッシュ情報を出力できるようにします。コミットメッセージにある「always use SetUnhandledExceptionFilter on windows-386」は、このフォールバックが386アーキテクチャで常に有効であることを強調しています。

*   **`EXCEPTION_BREAKPOINT`の扱い**:
    このコミットの重要な変更点の一つは、例外ハンドラ内で`EXCEPTION_BREAKPOINT`を受け取った場合にクラッシュする挙動を導入したことです。通常、`EXCEPTION_BREAKPOINT`はデバッガによって生成され、デバッガがこれを処理します。しかし、もしGoの例外ハンドラがこの例外を捕捉し、それを処理しようとした場合、それはデバッガの意図と異なる挙動を引き起こす可能性があります。この変更は、Goランタイムが`EXCEPTION_BREAKPOINT`を捕捉した場合、それをGoのパニックに変換するのではなく、意図的にクラッシュさせることで、デバッガがその例外を適切に処理できるようにし、デバッグ体験を改善することを目的としています。これにより、デバッガがブレークポイントで停止し、開発者がプログラムの状態を検査できるようになります。

*   **`runtime·sighandler`から`runtime·exceptionhandler`への分離**:
    以前は`runtime·sighandler`という単一の関数が例外処理を行っていましたが、このコミットでは`runtime·isgoexception`、`runtime·exceptionhandler`、`runtime·firstcontinuehandler`、`runtime·lastcontinuehandler`といった複数の関数に役割が分割されています。これにより、Goが処理すべき例外であるかどうかの判定（`isgoexception`）、Goのパニックに変換する処理（`exceptionhandler`）、そして実行継続時の挙動（`firstcontinuehandler`, `lastcontinuehandler`）がより明確に分離され、コードの可読性と保守性が向上しています。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は、以下のファイルに集中しています。

*   `src/runtime/defs_windows.go`, `src/runtime/defs_windows_386.h`, `src/runtime/defs_windows_amd64.h`:
    `EXCEPTION_BREAKPOINT`、`EXCEPTION_CONTINUE_EXECUTION`、`EXCEPTION_CONTINUE_SEARCH`といったWindows APIの定数が追加または更新されています。これらは例外処理の挙動を制御するためにGoランタイム内で使用されます。

*   `src/runtime/os_windows.c`:
    `SetUnhandledExceptionFilter`関数の動的インポートが追加され、`runtime·osinit`関数内でVEH/VCHの登録ロジックが変更されています。特に、`runtime·stdcall2(runtime·AddVectoredExceptionHandler, 1, (uintptr)runtime·sigtramp)`が`runtime·stdcall2(runtime·AddVectoredExceptionHandler, 1, (uintptr)runtime·exceptiontramp)`に変更され、`SetUnhandledExceptionFilter`や`AddVectoredContinueHandler`の呼び出しが追加されています。また、`runtime·issigpanic`関数に`EXCEPTION_BREAKPOINT`が追加され、Goのパニックを引き起こす例外として認識されるようになっています。

*   `src/runtime/os_windows_386.c`, `src/runtime/os_windows_amd64.c`:
    `runtime·sighandler`関数が`runtime·isgoexception`と`runtime·exceptionhandler`に分割されています。`runtime·isgoexception`はGoが処理すべき例外であるかを判定し、`runtime·exceptionhandler`はGoのパニックを生成するロジックを含みます。また、`runtime·lastcontinuehandler`が追加され、未処理例外の最終的な処理（クラッシュと終了）を担当します。

*   `src/runtime/sys_windows_386.s`, `src/runtime/sys_windows_amd64.s`:
    アセンブリコードの変更は、VEHハンドラである`runtime·sigtramp`が、実際の例外処理ロジックを呼び出す際に、どのハンドラを呼び出すかを動的に決定するように修正されています。具体的には、`runtime·exceptiontramp`、`runtime·firstcontinuetramp`、`runtime·lastcontinuetramp`といった新しいエントリポイントが追加され、それぞれが対応するC言語のハンドラ関数（`runtime·exceptionhandler`、`runtime·firstcontinuehandler`、`runtime·lastcontinuehandler`）を呼び出すように設定されています。これにより、例外処理のフローがより柔軟に制御できるようになっています。

*   `src/runtime/syscall_windows_test.go`:
    `TestRaiseException`と`TestZeroDivisionException`という新しいテストケースが追加されています。これらは、GoランタイムがWindows例外（カスタム例外とゼロ除算例外）を正しく捕捉し、Goのパニックに変換できることを検証するためのものです。

## コアとなるコードの解説

このコミットの核心は、GoランタイムがWindowsの例外をより細かく、かつ堅牢に処理するためのメカニズムを再構築した点にあります。

1.  **例外処理フローの再設計**:
    以前は単一の`runtime·sighandler`が多くの役割を担っていましたが、このコミットでは、例外のタイプと処理の段階に応じて複数のハンドラ関数に責任が分散されました。
    *   `runtime·exceptiontramp` (VEH): OSから最初に例外を受け取るアセンブリレベルのエントリポイント。
    *   `runtime·exceptionhandler` (C言語): `runtime·exceptiontramp`から呼び出され、Goのコード内で発生した例外をGoのパニックに変換する主要なロジックを含みます。
    *   `runtime·firstcontinuetramp` (VCH): `AddVectoredContinueHandler`で登録され、`exceptionhandler`が例外を処理して実行継続を指示した場合に、WindowsがVCHのリストを検索するのを停止させる役割を担います。
    *   `runtime·lastcontinuetramp` (VCH/UnhandledExceptionFilter): `AddVectoredContinueHandler`または`SetUnhandledExceptionFilter`で登録され、Goランタイムが処理できなかった例外の最終的なハンドラとして機能し、クラッシュ情報を出力してプログラムを終了させます。

2.  **`EXCEPTION_BREAKPOINT`の特別な扱い**:
    `src/runtime/os_windows.c`の`runtime·issigpanic`関数に`EXCEPTION_BREAKPOINT`が追加されたことで、この例外もGoのパニックを引き起こす可能性があると認識されます。しかし、コミットメッセージにある「crash when receive EXCEPTION_BREAKPOINT in exception handler」という指示は、デバッグ時の挙動を改善するためのものです。これは、`runtime·exceptionhandler`内で`EXCEPTION_BREAKPOINT`が検出された場合、Goのパニックに変換するのではなく、意図的にプログラムをクラッシュさせることで、デバッガがその例外を捕捉し、ブレークポイントとして機能するように促すことを意味します。これにより、開発者はデバッガを使ってGoプログラムの実行をより正確に制御できるようになります。

3.  **Windows-386アーキテクチャでの`SetUnhandledExceptionFilter`の強制**:
    `src/runtime/os_windows.c`の`runtime·osinit`関数内で、Windows-386アーキテクチャの場合、または`AddVectoredContinueHandler`が利用できない場合に、`SetUnhandledExceptionFilter`が常に使用されるように変更されています。これは、古いシステムや特定の環境での互換性と堅牢性を確保するための措置です。`SetUnhandledExceptionFilter`はデバッガがアタッチされていると呼び出されないという特性があるため、デバッグ時の挙動に影響を与える可能性がありますが、未処理例外の最終的な捕捉メカニズムとして重要です。

これらの変更により、GoランタイムはWindows環境での例外処理をより包括的かつ予測可能に行えるようになり、特にデバッグ時の挙動が改善され、Goプログラムの安定性が向上しています。

## 変更の背景

このコミットの主な目的は、`go build -n` コマンドの出力先を標準出力 (stdout) から標準エラー出力 (stderr) へと変更することです。

`go build -n` コマンドは、実際にビルドを実行せずに、ビルドプロセス中に実行されるであろうコマンド群を表示します。従来のUnix哲学では、プログラムの「通常の」出力はstdoutに、診断情報、警告、エラーメッセージなどの補助的な情報はstderrに出力されるべきだとされています。

`go build -n` の出力は、ビルドの「結果」ではなく、ビルドプロセスに関する「診断情報」と見なすことができます。そのため、この情報をstderrにリダイレクトすることで、以下のような利点があります。

1.  **出力の分離**: スクリプトなどで `go build` の実際の出力（例えば、生成されたバイナリのパスなど）をパースする場合、`-n` オプションによる診断情報が混ざることを防ぎます。これにより、スクリプトの堅牢性が向上します。
2.  **一貫性**: Goツールチェーン全体で、診断情報やデバッグ情報をstderrに出力するという慣習に合わせることで、ユーザー体験の一貫性が保たれます。
3.  **リダイレクトの容易さ**: ユーザーは `2>` を使って診断情報のみをファイルにリダイレクトしたり、`1>` を使って通常の出力のみをリダイレクトしたりすることが容易になります。

コミットメッセージにある `Fixes #12913` は、この変更がGoのIssueトラッカーで報告された特定の課題を解決するものであることを示しています。この課題は、おそらく `go build -n` の出力がstdoutに出力されることによる問題点や、stderrへのリダイレクトを求める要望であったと推測されます。

また、`-v` オプション（詳細出力）に関する変更も、この出力の一貫性を保つために行われています。

## 前提知識の解説

### 標準出力 (stdout) と標準エラー出力 (stderr)

Unix系オペレーティングシステムでは、プロセスはデフォルトで3つの標準I/Oストリームを持っています。

*   **標準入力 (stdin)**: プロセスへの入力データが供給されるストリーム。通常はキーボードに接続されています。
*   **標準出力 (stdout)**: プロセスが生成する通常の出力データが送られるストリーム。通常は画面に表示されます。
*   **標準エラー出力 (stderr)**: プロセスが生成するエラーメッセージや診断情報が送られるストリーム。通常は画面に表示されますが、stdoutとは独立しています。

これらのストリームは、シェルリダイレクション (`>`, `>>`, `2>`, `2>>`, `&>`, `|`) を使ってファイルに保存したり、別のコマンドにパイプで渡したりすることができます。

*   `command > file`: `command` のstdoutを `file` にリダイレクトします。
*   `command 2> file`: `command` のstderrを `file` にリダイレクトします。
*   `command &> file`: `command` のstdoutとstderrの両方を `file` にリダイレクトします。

### `go build -n` コマンド

`go build` コマンドはGoのソースコードをコンパイルして実行可能なバイナリを生成します。
`-n` オプションは "print the commands but do not run them" (コマンドを実行せずに表示する) を意味します。このオプションを使用すると、`go build` が内部的にどのようなシェルコマンド（コンパイラ呼び出し、リンカ呼び出しなど）を実行しようとしているかを確認できます。これはデバッグやビルドプロセスの理解に非常に役立ちます。

### `fmt.Printf` と `fmt.Fprintf`

Go言語の `fmt` パッケージは、フォーマットされたI/Oを提供します。

*   `fmt.Printf(format string, a ...interface{}) (n int, err error)`: フォーマットされた文字列を標準出力 (stdout) に出力します。
*   `fmt.Fprintf(w io.Writer, format string, a ...interface{}) (n int, err error)`: フォーマットされた文字列を指定された `io.Writer` インターフェースに書き込みます。`os.Stderr` は `io.Writer` インターフェースを実装しているため、`fmt.Fprintf(os.Stderr, ...)` を使うことで標準エラー出力に書き込むことができます。

### `builder.print` メソッド

`src/cmd/go/build.go` 内の `builder` 構造体には、おそらく `print` というメソッドが存在し、これはビルドプロセス中のメッセージ出力のために使われていると推測されます。このコミットでは、`fmt.Printf` や `fmt.Fprintf(os.Stderr, ...)` の直接的な呼び出しを `b.print` メソッドに置き換えることで、出力の制御を一元化し、柔軟性を持たせていると考えられます。`b.print` の内部実装が、最終的にstdoutまたはstderrのどちらに出力するかを決定するロジックを持っている可能性があります。

## 技術的詳細

このコミットは、`src/cmd/go/build.go` ファイル内の2つの出力箇所を変更しています。

変更前は、`go build -n` の出力の一部が `fmt.Printf` を通じて標準出力に直接書き込まれていました。また、`buildV` (おそらく `-v` オプションが有効な場合) の出力も `fmt.Fprintf(os.Stderr, ...)` を通じて標準エラー出力に直接書き込まれていました。

変更後は、これらの直接的な `fmt` パッケージの呼び出しが、`builder` 構造体の `b.print` メソッドの呼び出しに置き換えられています。

これにより、`builder` の `print` メソッドが、出力が標準出力に送られるべきか、標準エラー出力に送られるべきかを内部的に判断し、適切なストリームに書き込む責任を持つようになります。この抽象化により、将来的に出力の挙動を変更する際に、個々の `fmt.Printf` や `fmt.Fprintf` の呼び出しを修正する必要がなくなり、保守性が向上します。

特に、`go build -n` の出力がすべてstderrに送られるようにするため、以前 `fmt.Printf` で出力されていた部分も `b.print` を通じてstderrに送られるように変更されたと考えられます。

## コアとなるコードの解説

1.  **変更箇所1: `fmt.Printf` から `b.print` へ**
    ```diff
    -		fmt.Printf("\n#\n# %s\n#\n\n", a.p.ImportPath)
    +		b.print("\n#\n# " + a.p.ImportPath + "\\n#\\n\\n")
    ```
    この行は、ビルドの各パッケージの開始を示すバナー（`#` で囲まれたインポートパス）を出力する部分です。
    *   変更前は `fmt.Printf` を使用しており、このバナーは標準出力 (stdout) に出力されていました。
    *   変更後は `b.print` メソッドを使用するように変更されています。これにより、このバナーも `go build -n` の出力の一部として、`b.print` の内部ロジックに従って標準エラー出力 (stderr) に送られるようになります。文字列の結合方法も `fmt.Printf` のフォーマット文字列から単純な文字列結合 (`+`) に変更されていますが、これは `b.print` メソッドが可変引数を取らない（または異なる形式を期待する）ためか、あるいは単に文字列結合の方がこのケースではシンプルであると判断されたためと考えられます。

2.  **変更箇所2: `fmt.Fprintf(os.Stderr, ...)` から `b.print` へ**
    ```diff
    -		fmt.Fprintf(os.Stderr, "%s\\n", a.p.ImportPath)
    +		b.print(a.p.ImportPath + "\\n")
    ```
    この行は、`buildV` (おそらく `-v` オプションが有効な場合) の詳細出力の一部として、パッケージのインポートパスを出力する部分です。
    *   変更前は `fmt.Fprintf(os.Stderr, ...)` を使用しており、この出力は既に標準エラー出力 (stderr) に送られていました。
    *   変更後も `b.print` メソッドを使用するように変更されています。これは、`go build -n` の出力がすべてstderrに送られるという一貫性を保つため、および `builder` の出力ロジックを一元化するためです。この変更により、`-v` オプションによる詳細出力も `b.print` を通じて処理されることになり、出力の一貫性がさらに強化されます。

これらの変更により、`go build -n` の出力はすべて `b.print` メソッドを経由するようになり、その結果、標準エラー出力に統一して送られるようになりました。これにより、診断情報と通常のプログラム出力を明確に分離するというUnixの慣習に、Goのビルドツールがより厳密に準拠する形になりました。

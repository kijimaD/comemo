## 変更の背景

このコミットの背景には、`net/http`パッケージの`http.Request`構造体におけるプロトコルバージョン関連フィールド（`Proto`, `ProtoMajor`, `ProtoMinor`）のドキュメントが、特にクライアントリクエストの挙動に関して誤解を招く可能性があったという問題があります。

以前のコメントでは、「Client requests always use HTTP/1.1.」と記述されていましたが、これはHTTP/2.0の導入や、Goの`net/http`クライアントがサーバーのサポート状況に応じて自動的に最適なプロトコルバージョン（HTTP/1.1またはHTTP/2.0）を選択するようになった現状と一致しませんでした。

開発者がこれらのフィールドをクライアントリクエストのプロトコルバージョンを制御するために使用しようとすると、意図しない挙動や混乱を招く可能性がありました。このコミットは、ドキュメントを更新することで、これらのフィールドが主に**受信するサーバーリクエスト**のプロトコルバージョンを示すものであり、**クライアントリクエスト**においては標準のHTTPトランスポートが自動的にプロトコルバージョンを決定するという事実を明確にすることを目的としています。これにより、APIの意図がより正確に伝わり、開発者の誤解を防ぎます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の`net/http`パッケージとHTTPプロトコルに関する基本的な知識が必要です。

*   **Goの`net/http`パッケージ**: Go言語の標準ライブラリの一部であり、HTTPクライアントとサーバーを構築するための機能を提供します。WebアプリケーションやAPIサービスを開発する上で中心的な役割を果たします。
*   **`http.Request`構造体**: HTTPリクエストの情報をカプセル化するGoの構造体です。これには、リクエストメソッド（GET, POSTなど）、URL、ヘッダー、ボディ、そしてプロトコルバージョンなどの情報が含まれます。この構造体は、HTTPサーバーが受信したリクエストを表現するためにも、HTTPクライアントが送信するリクエストを構築するためにも使用されます。
*   **HTTPプロトコルバージョン**:
    *   **HTTP/1.1**: 広く普及しているHTTPプロトコルのバージョンです。TCPコネクションごとに1つのリクエスト/レスポンスを処理し、パイプライン処理をサポートしますが、ヘッドオブラインブロッキングの問題を抱えることがあります。
    *   **HTTP/2.0**: HTTP/1.1のパフォーマンス上の制約を克服するために設計された新しいバージョンです。単一のTCPコネクション上で複数のリクエスト/レスポンスを並行して処理する多重化、ヘッダー圧縮、サーバープッシュなどの機能を提供し、Webのパフォーマンスを大幅に向上させます。
*   **クライアントリクエストとサーバーリクエストにおけるプロトコルバージョンの扱い**:
    *   **サーバー側**: HTTPサーバーは、クライアントから受信したリクエストがどのHTTPプロトコルバージョン（例: HTTP/1.0, HTTP/1.1, HTTP/2.0）で送信されたかを正確に知る必要があります。`http.Request`構造体の`Proto`, `ProtoMajor`, `ProtoMinor`フィールドは、この情報を提供します。
    *   **クライアント側**: HTTPクライアントがリクエストを送信する際、通常、開発者はどのHTTPバージョンを使用するかを明示的に指定するよりも、基盤となるHTTPトランスポート層がサーバーのサポート状況やネットワーク条件に応じて最適なバージョンを自動的に選択することを期待します。Goの`net/http`クライアントのデフォルトのトランスポートは、この自動ネゴシエーションを行います。

このコミットは、特にクライアント側で`Proto`フィールドを直接設定しても、標準のHTTPトランスポートがその値を無視し、独自のロジックでプロトコルバージョンを決定するという重要な挙動を明確にしています。

## 技術的詳細

このコミットは、`net/http`パッケージの`http.Request`構造体内の`Proto`、`ProtoMajor`、`ProtoMinor`フィールドのドキュメンテーションを更新するものです。コードの動作自体を変更するものではなく、APIの利用方法に関する開発者の理解を深めることを目的とした純粋なドキュメントの改善です。

変更の核心は、これらのフィールドが「受信するサーバーリクエスト」に対しては権威ある情報源である一方で、「クライアントリクエスト」に対しては標準のHTTPトランスポートによって無視される、という区別を明確にすることにあります。

具体的には、以下の点が技術的に重要です。

1.  **サーバーリクエストのプロトコルバージョン**: HTTPサーバーがクライアントからリクエストを受信した場合、`Request.Proto`、`Request.ProtoMajor`、`Request.ProtoMinor`は、そのリクエストが実際にどのHTTPプロトコルバージョンで送信されたかを示します。これは、サーバーがリクエストを適切に処理し、レスポンスを生成するために不可欠な情報です。例えば、HTTP/1.0のリクエストにはKeep-Aliveヘッダーがないため、サーバーはコネクションを閉じるべきか判断できます。
2.  **クライアントリクエストでのフィールドの無視**: Goの`net/http`クライアント（特にデフォルトの`http.Transport`）は、リクエストを送信する際に、`http.Request`構造体の`Proto`、`ProtoMajor`、`ProtoMinor`フィールドの値を直接使用しません。代わりに、トランスポート層が以下のロジックに基づいてプロトコルバージョンを決定します。
    *   **HTTP/2.0のネゴシエーション**: サーバーがHTTP/2.0をサポートしている場合（ALPNネゴシエーションなどを通じて）、クライアントは自動的にHTTP/2.0で通信しようとします。
    *   **HTTP/1.1へのフォールバック**: サーバーがHTTP/2.0をサポートしていない場合、または何らかの理由でHTTP/2.0での通信が確立できない場合、クライアントはHTTP/1.1にフォールバックします。
    *   **デフォルトの挙動**: 開発者が`http.Client`や`http.Transport`を特別に設定しない限り、この自動ネゴシエーションが行われます。これにより、開発者はHTTPプロトコルの詳細を意識することなく、最適なパフォーマンスを得ることができます。
3.  **ドキュメントの重要性**: このドキュメントの更新は、APIの「契約」を明確にする上で非常に重要です。開発者が`http.Request`を構築して`http.Client.Do()`に渡す際に、`Proto`フィールドを設定してもそれが無視されることを明示することで、誤った期待やデバッグの困難さを回避できます。これは、APIの使いやすさと堅牢性を向上させるための重要なステップです。

この変更は、Goの`net/http`パッケージがHTTP/2.0をサポートするようになった後の、APIドキュメントの整合性を保つための調整と見なすことができます。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は、`http.Request`構造体の`Proto`、`ProtoMajor`、`ProtoMinor`フィールドに付随するコメントの修正です。

**変更前のコメント:**

```go
	// The protocol version for incoming requests.
	// Client requests always use HTTP/1.1.
	Proto      string // "HTTP/1.0"
	ProtoMajor int    // 1
	ProtoMinor int    // 0
```

*   `The protocol version for incoming requests.` (受信するリクエストのプロトコルバージョン。)
    *   これは曖昧で、クライアントが送信するリクエストにも適用されるかのように読める可能性がありました。
*   `Client requests always use HTTP/1.1.` (クライアントリクエストは常にHTTP/1.1を使用します。)
    *   これはHTTP/2.0の導入後、不正確な情報となりました。Goの`net/http`クライアントは、サーバーがサポートしていればHTTP/2.0を使用するようになりました。

**変更後のコメント:**

```go
	// The protocol version for incoming server requests.
	//
	// For client requests these fields are ignored. The HTTP
	// transport code uses either HTTP/1.1 or HTTP/2.0 by default,
	// depending on what the server supports.
	Proto      string // "HTTP/1.0"
	ProtoMajor int    // 1
	ProtoMinor int    // 0
```

*   `The protocol version for incoming server requests.` (受信するサーバーリクエストのプロトコルバージョン。)
    *   この変更により、これらのフィールドが主にサーバーが受信するリクエストに適用されることが明確になりました。これにより、クライアントが送信するリクエストの文脈での誤解が解消されます。
*   `For client requests these fields are ignored.` (クライアントリクエストの場合、これらのフィールドは無視されます。)
    *   これは非常に重要な追加情報です。開発者がクライアントリクエストオブジェクトを作成する際に`Proto`フィールドを設定しても、標準のHTTPトランスポートはその値を考慮しないことを明示しています。
*   `The HTTP transport code uses either HTTP/1.1 or HTTP/2.0 by default, depending on what the server supports.` (HTTPトランスポートコードは、サーバーがサポートするものに応じて、デフォルトでHTTP/1.1またはHTTP/2.0を使用します。)
    *   この文は、クライアントリクエストのプロトコルバージョンがどのように決定されるかを説明しています。つまり、開発者が手動で設定するのではなく、`net/http`の内部トランスポートがサーバーとのネゴシエーションに基づいて最適なプロトコルバージョンを自動的に選択するという挙動を明確にしています。

このコメントの更新は、Goの`net/http`パッケージのAPIの正確性と使いやすさを向上させる上で、非常に重要なドキュメンテーションの改善です。

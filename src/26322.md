# [インデックス 26322] ファイルの概要

このコミットは、Go言語の`crypto/cipher`パッケージにおけるGCM (Galois/Counter Mode) 暗号の実装に関するものです。特に、認証失敗時における出力バッファの挙動の不整合を解消し、セキュリティとプラットフォーム間の一貫性を向上させることを目的としています。AESNI (Advanced Encryption Standard New Instructions) を利用する最適化されたGCM実装と、汎用的なソフトウェアGCM実装との間で、認証失敗時に出力バッファが上書きされるかどうかの挙動が異なっていた問題を修正し、常にバッファをゼロクリアするように変更しています。

## 元コミット内容

```
crypto/cipher: always zero dst buffer on GCM authentication failure.

The AESNI GCM code decrypts and authenticates concurrently and so
overwrites the destination buffer even in the case of an authentication
failure.

This change updates the documentation to make that clear and also
mimics that behaviour in the generic code so that different platforms
act identically.

Fixes #13886
```

## 変更の背景

Go言語の`crypto/cipher`パッケージにおけるGCM (Galois/Counter Mode) の実装には、特定の条件下でセキュリティ上の潜在的な問題とプラットフォーム間の挙動の不整合が存在していました。

1.  **AESNI GCMの挙動**: IntelやAMDのCPUに搭載されているAESNI命令セットを利用するGCM実装では、復号処理と認証タグの計算が並行して行われるように最適化されています。この並行処理の性質上、認証タグの検証が完了する前に、暗号文が復号され、その結果が一時的に出力バッファ（`dst`）に書き込まれてしまうことがありました。もし認証タグの検証が最終的に失敗した場合でも、この出力バッファは既に上書きされた状態となっていました。

2.  **汎用GCMの挙動**: 一方、AESNIを利用しない汎用的な（ソフトウェアベースの）GCM実装では、通常、復号処理と認証処理がよりシーケンシャルに行われるため、認証失敗時には出力バッファが変更されない可能性がありました。

3.  **セキュリティ上の懸念**: 認証失敗時に出力バッファに平文の一部が残存する可能性があると、攻撃者が認証失敗の事実をトリガーとして、バッファに残された部分平文から情報を推測しようとする「サイドチャネル攻撃」や情報漏洩のリスクが生じます。特に、認証失敗の事実だけが攻撃者に伝わり、バッファの内容がクリアされない場合、これはセキュリティ上の脆弱性となり得ます。

4.  **一貫性の欠如**: 上記の挙動の差異は、異なるCPUアーキテクチャやGoのビルド設定によって、同じGCMの`Open`メソッドが異なる動作をするという、プラットフォーム間の一貫性の欠如を引き起こしていました。これは、開発者が予測不能なバグに遭遇したり、セキュリティ上の保証が曖昧になったりする原因となります。

このコミットは、これらの問題を解決するために導入されました。具体的には、認証失敗時には常に`dst`バッファをゼロクリアすることで、すべてのプラットフォームで一貫した安全な挙動を保証し、潜在的な情報漏洩のリスクを排除することを目的としています。また、この新しい挙動を`AEAD`インターフェースのドキュメントに明記することで、APIの利用者がこの仕様を正しく理解できるようにしています。

## 前提知識の解説

このコミットの理解を深めるために、以下の暗号技術に関する前提知識を解説します。

-   **GCM (Galois/Counter Mode)**:
    GCMは、現代の暗号システムで広く利用されている認証付き暗号 (Authenticated Encryption with Associated Data, AEAD) モードの一つです。これは、データの**機密性**（暗号化によって内容を隠す）、**完全性**（データが改ざんされていないことを保証する）、そして**認証**（データが正当な送信元から来たことを保証する）の3つのセキュリティ特性を同時に提供します。
    GCMは、ブロック暗号（例: AES）をカウンタモード (CTR) で動作させてデータを暗号化し、同時にGHASHと呼ばれるハッシュ関数を用いて認証タグを生成します。この認証タグは、暗号文と追加認証データ (AAD) の両方に対して計算され、復号時に検証されます。

-   **AEAD (Authenticated Encryption with Associated Data)**:
    AEADは、暗号化と認証を単一のアルゴリズムで提供する暗号化方式のカテゴリです。従来の「暗号化してから認証する (Encrypt-then-MAC)」や「認証してから暗号化する (MAC-then-Encrypt)」といった方式に比べて、より安全で実装が容易であるとされています。AEADは、暗号文だけでなく、ヘッダー情報など暗号化されないが認証が必要なデータ（Associated Data）も保護できる点が特徴です。GCMはAEADの代表的な実装の一つです。

-   **AESNI (Advanced Encryption Standard New Instructions)**:
    AESNIは、IntelおよびAMDの最新のCPUに搭載されている、AES暗号化・復号処理をハードウェアレベルで高速化するための命令セットです。これにより、ソフトウェアのみでAESを実装する場合に比べて、大幅なパフォーマンス向上を実現します。また、ハードウェア実装であるため、一部のサイドチャネル攻撃（例: タイミング攻撃）に対する耐性も向上します。GCMのような複雑なモードでは、AESNIを利用することで、復号と認証の計算をより効率的に、時には並行して実行することが可能になります。

-   **認証失敗時のセキュリティ**:
    暗号化されたデータを受信し、それを復号して認証を行う際、認証タグの検証が失敗した場合は、そのデータが通信中に改ざんされたか、あるいは不正な送信元から送られてきたことを意味します。このような場合、復号されたデータ（平文）をアプリケーションに渡すことは絶対に避けるべきです。
    さらに重要なのは、認証失敗時に、復号処理の途中で生成された平文の一部がメモリバッファに残存しないようにすることです。もし残存した場合、攻撃者は認証失敗という結果と、バッファに残された部分平文の情報を組み合わせて、元の平文に関する情報を推測する可能性があります。これは「サイドチャネル攻撃」の一種であり、暗号システムの安全性を損なう可能性があります。したがって、認証失敗時には、出力バッファの内容を完全にクリア（ゼロクリアなど）することが、セキュリティ上のベストプラクティスとされています。

## 技術的詳細

このコミットの技術的な核心は、GCMの認証失敗時における出力バッファの挙動を、プラットフォーム間で一貫させ、かつセキュリティを強化することにあります。

-   **AESNI GCMの並行処理とバッファ上書き**:
    AESNIを利用したGCMの実装では、CPUのハードウェア命令を活用して、暗号文の復号と認証タグの計算（GHASH）を可能な限り並行して実行します。この設計は高いスループットを実現しますが、認証タグの最終的な検証が完了する前に、復号されたデータが一時的に出力バッファ（`dst`）に書き込まれてしまうという副作用があります。もし認証タグの検証が失敗した場合、このバッファには、本来アプリケーションに渡されるべきではない「部分的に復号された、信頼できないデータ」が残ってしまいます。

-   **汎用GCM実装との挙動の不整合**:
    一方、ソフトウェアで実装された汎用GCMコードでは、通常、復号処理と認証タグの計算・検証はより段階的に行われます。多くの場合、認証タグの検証が成功するまで、復号されたデータを出力バッファに書き込まない、あるいは書き込んでもすぐに破棄するような設計が可能です。このため、汎用実装では認証失敗時に出力バッファが上書きされない、またはクリアされるという挙動になることがありました。
    このAESNIと汎用実装間の挙動の差異は、Goの`crypto/cipher`パッケージを利用するアプリケーションにとって、予期せぬ動作や潜在的なセキュリティリスクをもたらす可能性がありました。例えば、ある環境では認証失敗時にバッファがクリアされるが、別の環境（AESNIが有効な場合）ではクリアされず、部分平文が残存するといった状況です。

-   **ゼロクリアによるセキュリティと一貫性の確保**:
    このコミットは、この不整合を解消し、セキュリティを強化するために、以下の戦略を採用しています。
    1.  **AESNIの挙動を模倣**: 汎用GCM実装においても、AESNI GCMと同様に、認証タグの検証前に復号されたデータを出力バッファに書き込むようにします。これにより、両者の処理フローを近づけます。
    2.  **認証失敗時のゼロクリア**: 認証タグの検証が失敗した場合、出力バッファに書き込まれた内容を**必ずゼロクリア**します。これにより、認証失敗時にバッファに平文の一部が残存するリスクを完全に排除し、サイドチャネル攻撃の可能性を低減します。
    この変更により、GoのGCM実装は、どのプラットフォームで実行されても、認証失敗時には常に安全かつ一貫した挙動を示すようになります。

## コアとなるコードの解説

### `src/crypto/cipher/gcm.go` の変更点

-   **`AEAD`インターフェースの`Open`メソッドのドキュメント更新**:
    ```go
    // Even if the function fails, the contents of dst, up to its capacity,
    // may be overwritten.
    ```
    この新しいコメントは、`AEAD`インターフェースの`Open`メソッドがエラーを返した場合でも、`dst`バッファの内容がその容量の範囲内で上書きされる可能性があることを明確にしています。これは、特にAESNIのような並行処理を行う実装の挙動を反映しており、APIの利用者がこの挙動を前提としてコードを設計すべきであることを示唆しています。これにより、ユーザーは認証失敗時でも`dst`バッファの内容を信頼してはならないことを理解できます。

-   **`gcm.Open`メソッド内のロジック変更**:
    元のコードでは、`sliceForAppend`（`dst`バッファから出力スライスを準備するヘルパー関数）の呼び出しが認証タグの検証後に行われていました。しかし、このコミットでは、`sliceForAppend`の呼び出しが認証タグ検証の前に移動されました。
    ```go
    	ret, out := sliceForAppend(dst, len(ciphertext)) // 認証タグ検証の前に移動
    ```
    この変更により、認証タグの検証が失敗した場合でも、`out`バッファ（復号されたデータが一時的に格納される可能性のある領域）が既に準備されており、その内容にアクセスしてゼロクリアすることが可能になります。

    そして、認証タグの比較が失敗した場合の処理ブロックに、以下のゼロクリアロジックが追加されました。
    ```go
    	if subtle.ConstantTimeCompare(expectedTag[:], tag) != 1 {
    		// The AESNI code decrypts and authenticates concurrently, and
    		// so overwrites dst in the event of a tag mismatch. That
    		// behaviour is mimicked here in order to be consistent across
    		// platforms.
    		for i := range out {
    			out[i] = 0
    		}
    		return nil, errOpen
    	}
    ```
    -   `subtle.ConstantTimeCompare(expectedTag[:], tag) != 1`: これは、計算にかかる時間が入力データに依存しないように設計された比較関数です。これにより、タイミング攻撃を防ぎながら、計算された認証タグ (`expectedTag`) と受信した認証タグ (`tag`) を比較します。比較が一致しない場合（`!= 1`）、認証は失敗と判断されます。
    -   `for i := range out { out[i] = 0 }`: 認証が失敗した場合、`out`バッファのすべてのバイトが`0`に設定されます。このゼロクリアは、AESNI実装の挙動（認証失敗時でもバッファが上書きされる）を汎用実装で模倣し、プラットフォーム間の一貫性を保つためのものです。これにより、バッファに平文の一部が残存するリスクが排除されます。
    -   `return nil, errOpen`: ゼロクリア後、`nil`（復号されたデータなし）と`errOpen`（認証失敗エラー）を返して処理を終了します。

### `src/crypto/cipher/gcm_test.go` の変更点

-   **`TestTagFailureOverwrite` テストケースの追加**:
    この新しいテストケースは、認証失敗時に`dst`バッファが確実にゼロクリアされることを検証するために導入されました。
    -   テストでは、有効な鍵、Nonce、そして意図的に認証タグが不正になるように改ざんされた暗号文が用意されます。
    -   `dst`バッファは、初期値として`42`（`0x2a`）で埋め尽くされます。これは、ゼロクリアが正しく行われたかどうかを視覚的に確認しやすくするためです。
    -   `aesgcm.Open`が呼び出され、認証失敗が期待されます。
    -   テストは、`Open`がエラーを返し（`err == nil`でないこと）、かつ復号されたデータが返されないこと（`result == nil`であること）を確認します。
    -   最も重要な検証は、以下のループです。
        ```go
        	for i := range dst {
        		if dst[i] != 0 {
        			t.Fatal("Failed Open didn't zero dst buffer")
        		}
        	}
        ```
        このループは、`dst`バッファのすべての要素が`0`になっていることを確認します。もし一つでも`0`以外の値が残っていれば、テストは失敗し、「Failed Open didn't zero dst buffer」というエラーメッセージが出力されます。これにより、認証失敗時にバッファが確実にゼロクリアされるという新しい挙動が保証されます。

# [インデックス 24868] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおいて、ガベージコレクション (GC) のビットマップ生成を改善し、SSAコンパイルされたコードがGCと正しく連携できるようにするための重要な変更です。具体的には、スタック割り当てのメカニズムを見直し、スピル（レジスタからスタックへ退避される値）ごとに変数宣言を生成するように変更することで、既存のGCビットマップ生成ロジックをSSAコードに適用できるようにしました。これにより、スタックコピーが正しく機能し、GCが完全に動作するための基盤が強化されました。

## コミット

```
[dev.ssa] cmd/runtime: generate gc bitmaps for SSA-compiled code

This change is all about leveraging the gc bitmap generation
that is already done by the current compiler.  We rearrange how
stack allocation is done so that we generate a variable declaration
for each spill.  We also reorganize how args/locals are recorded
during SSA.  Then we can use the existing allocauto/defframe to
allocate the stack frame and liveness to make the gc bitmaps.

With this change, stack copying works correctly and we no longer
need hacks in runtime/stack*.go to make tests work.  GC is close
to working, it just needs write barriers.
```

## 変更の背景

Goコンパイラは、コードの最適化のためにSSA (Static Single Assignment) 形式への変換を進めていました。SSAは、各変数が一度だけ代入されるようにすることで、データフロー解析や最適化を容易にする強力な中間表現です。しかし、SSAコンパイルされたコードがGoランタイムのガベージコレクション (GC) と完全に連携するためには、いくつかの課題がありました。

特に、GCがスタック上のポインタを正確に識別するためには、「GCビットマップ」と呼ばれる情報が必要です。従来のコンパイラは、このGCビットマップを生成するメカニズムを持っていましたが、SSAコンパイルされたコードのスタックフレームの構造や変数管理の方法が異なっていたため、そのままでは適用できませんでした。

このコミットの主な背景は、SSAコンパイルされたコードでも既存のGCビットマップ生成ロジックを再利用できるようにすることです。これにより、GCがSSAコードのスタックを正確にスキャンし、ポインタを識別できるようになり、Goのメモリ管理の健全性と効率性を確保することが目的でした。具体的には、スタックに退避される値（スピル）の扱いを改善し、それらがGCビットマップ生成の対象となるようにすることが求められました。

この変更がなければ、SSAコンパイルされたコードではGCが正しく機能せず、メモリリークや誤ったメモリ解放といった問題が発生する可能性がありました。また、スタックコピー（Goのgoroutineスタックは動的にサイズ変更されるため、必要に応じてコピーされることがあります）も正しく動作しないという問題も抱えていました。コミットメッセージにある「runtime/stack*.goのハックが不要になる」という記述は、これらの問題を回避するために一時的に導入されていたコードが、この変更によって不要になることを示唆しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

### 1. Goのガベージコレクション (GC) とGCビットマップ

GoのGCは、並行（concurrent）かつ三色（tri-color）マーク＆スイープアルゴリズムを採用しています。これは、アプリケーションの実行と並行してGCが動作し、STW (Stop-The-World) ポーズを最小限に抑えることを目指しています。

*   **GCビットマップ**: GCがメモリ内のポインタを効率的に識別するために使用するデータ構造です。ヒープ上のオブジェクトやスタックフレーム内の変数について、どのメモリワードがポインタであり、どれが非ポインタデータであるかを示します。ビットマップの「1」はポインタを示し、「0」は非ポインタを示します。これにより、GCはポインタをたどって到達可能なオブジェクトを正確にマークできます。コンパイラは型情報に基づいてこのビットマップ生成に必要な情報をランタイムに提供します。

### 2. GoコンパイラのSSA (Static Single Assignment) 形式

*   **SSA**: プログラムの最適化を目的とした中間表現 (IR) の一種です。SSA形式では、各変数は一度だけ代入されます。これにより、データフロー解析が簡素化され、デッドコード削除、定数伝播、共通部分式除去などの多くの最適化が容易になります。Goコンパイラは、Go 1.7以降でSSAバックエンドを導入し、コード生成の品質と最適化能力を大幅に向上させました。

### 3. スタック割り当てとスピル (Spill)

*   **スタック割り当て**: 関数内のローカル変数や引数、戻り値などは、通常、関数のスタックフレームに割り当てられます。スタックはLIFO (Last-In, First-Out) 構造で、関数の呼び出しと終了に伴ってメモリが効率的に確保・解放されます。
*   **スピル (Spill)**: コンパイラのレジスタ割り当てフェーズにおいて、利用可能なCPUレジスタの数が不足した場合、一部の変数の値はレジスタからスタックメモリに一時的に退避されます。この操作を「スピル」と呼び、退避された値を「スピルされた値」と呼びます。スピルはメモリアクセスを伴うため、パフォーマンスに影響を与える可能性があります。

### 4. `allocauto`, `defframe`, `liveness`

これらはGoコンパイラのバックエンドにおけるスタックフレーム管理とGC連携に関連する概念です。

*   **`allocauto`**: コンパイラが自動的にローカル変数をスタックに割り当てるプロセスを指します。エスケープ解析によって、ヒープではなくスタックに割り当てられることが決定された変数が対象となります。
*   **`defframe`**: 関数のスタックフレームの定義と管理に関連します。Goランタイムは動的にサイズ変更可能なgoroutineスタックを管理しており、`defframe`はスタックフレームのプロローグ（関数開始時の処理）で、スタックフレームのセットアップや、GCがポインタを識別できるようにするための情報（GCビットマップ）の準備を行います。
*   **`liveness` (生存期間解析)**: コンパイラのデータフロー解析の一種で、プログラムの特定のポイントでどの変数が「生きている」（将来的にその値が使用される可能性がある）かを判断します。この情報は、レジスタ割り当ての最適化、スタックスロットの再利用、そしてGCがスタック上のどの場所をスキャンすべきかを決定するために不可欠です。`cmd/compile/internal/liveness`パッケージがこの解析を担当し、GCがスタック上のライブポインタを識別するためのランタイムデータ構造を生成します。

### 5. ライトバリア (Write Barrier)

*   **ライトバリア**: 並行GCにおいて、アプリケーションがポインタを書き換える際にGCの整合性を保つためにコンパイラが挿入する小さなコードスニペットです。GCがオブジェクトグラフを走査している最中にアプリケーションがポインタを変更すると、GCがライブオブジェクトを見落としたり、誤って収集したりする可能性があります。ライトバリアは、このような状況を防ぎ、三色不変条件（例えば、「黒いオブジェクトが白いオブジェクトを指してはならない」）を維持する役割を果たします。Go 1.8以降ではハイブリッドライトバリアが導入され、STWポーズのさらなる短縮に貢献しています。

## 技術的詳細

このコミットの核心は、SSAコンパイルされたコードのスタックフレーム管理とGCビットマップ生成の統合です。

1.  **スタック割り当ての再編成**:
    *   従来のコンパイラでは、スタック上のローカル変数やスピルされた値は、GCビットマップ生成のために特定の形式で管理されていました。SSAバックエンドでは、スピルが発生した際に、そのスピルされた値に対して明示的な変数宣言（`VarDef`）を生成するように変更されました。これにより、スピルされた値も通常のローカル変数と同様に扱われ、既存のGCビットマップ生成ロジックの対象となります。
    *   `src/cmd/compile/internal/gc/ssa.go` の `buildssa` 関数内で、`PAUTO` (自動変数) の処理が変更され、`decladdrs` マップへの追加方法が見直されています。以前は `Offset: -1` でオフセットが未定の `AutoSymbol` を作成していましたが、この変更により、`PAUTO` は使用されるたびにアドレスが再生成されるようになりました。これは、`VarDef` オペレーションが宣言よりも前に発生し、生存期間解析を混乱させるのを防ぐためです。

2.  **引数/ローカル変数の記録方法の変更**:
    *   SSA形式での引数 (`args`) とローカル変数 (`locals`) の記録方法も再編成されました。`ssa.ArgSymbol` と `ssa.AutoSymbol` 構造体が変更され、`Sym` (シンボル) ではなく `Node` (ASTノード) を直接参照するようになりました。これにより、コンパイラのフロントエンドが持つ豊富な型情報や変数情報をSSAバックエンドに直接渡すことが可能になり、GCビットマップ生成の精度が向上します。

3.  **既存のGCメカニズムの活用**:
    *   これらの変更により、SSAコンパイルされたコードでも、既存の `allocauto` (自動変数割り当て)、`defframe` (スタックフレーム定義)、`liveness` (生存期間解析) といったコンパイラおよびランタイムのメカニズムを再利用してGCビットマップを生成できるようになりました。
    *   `src/cmd/compile/internal/gc/ssa.go` の `genssa` 関数では、スタックフレームの割り当て (`allocauto`) とGCビットマップの生成 (`liveness`) が明示的に呼び出されるようになりました。これにより、SSAコードのスタックフレームに対してもGCビットマップが正確に生成され、GCがポインタを識別できるようになります。
    *   `ssa.OpVarDef` と `ssa.OpVarKill` という新しいSSAオペレーションが導入され、変数の生存期間をより正確に追跡できるようになりました。`VarDef` は変数が初期化される直前に、`VarKill` は変数がデッドになったときに挿入されます。これらは生存期間解析 (`liveness`) の精度を高め、GCビットマップの正確な生成に貢献します。

4.  **`runtime/stack*.go` のハックの削除**:
    *   この変更により、SSAコンパイルされたコードのスタックコピーが正しく動作するようになり、以前はテストを機能させるために必要だった `runtime/stack*.go` 内の特定の「ハック」が不要になりました。これは、SSAバックエンドがGCとより深く統合された結果です。

5.  **GCの進捗**:
    *   コミットメッセージは、「GCは動作に近づいており、あとはライトバリアが必要なだけだ」と述べています。これは、このコミットがGCの完全な機能に向けた重要な一歩であり、残る主要な課題がライトバリアの実装であることを示しています。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   `src/cmd/compile/internal/gc/ssa.go`: SSAバックエンドとコンパイラのフロントエンドの統合部分。`buildssa` 関数での `PAUTO` (自動変数) および `PPARAM`/`PPARAMOUT` (引数/戻り値) の処理、`genssa` 関数での `allocauto` と `liveness` の呼び出し、`ssa.OpVarDef` と `ssa.OpVarKill` の導入に関連する変更が含まれます。
*   `src/cmd/compile/internal/ssa/config.go`: SSAコンフィグレーションに `Frontend` インターフェースの `Auto` メソッドが追加され、SSAコンパイラがスピル用のスペースを割り当てるために `gc.Node` を要求できるようになりました。
*   `src/cmd/compile/internal/ssa/func.go`: `Func` 構造体から `FrameSize` フィールドが削除されています。これは、スタックフレームサイズの計算方法が変更されたことを示唆しています。
*   `src/cmd/compile/internal/ssa/gen/genericOps.go`: `VarDef` と `VarKill` という新しいジェネリックなSSAオペレーションが追加されています。
*   `src/cmd/compile/internal/ssa/location.go`: `LocalSlot` 構造体が `Idx` (オフセット) ではなく `N fmt.Stringer` (自動変数の `*gc.Node`) を持つように変更され、スタック上のローカル変数の表現がより抽象的になりました。
*   `src/cmd/compile/internal/ssa/stackalloc.go`: スタック割り当てロジックが大幅に変更されています。特に、`f.Config.fe.Auto(v.Type)` を呼び出して自動変数を割り当てることで、スピルされた値が `gc.Node` として扱われ、GCビットマップ生成の対象となるようにしています。以前のオフセット計算ロジックが削除されています。
*   `src/cmd/compile/internal/ssa/value.go`: `ArgSymbol` と `AutoSymbol` 構造体が `Sym` フィールドの代わりに `Node` フィールドを持つように変更され、より詳細なASTノード情報にアクセスできるようになりました。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更点

*   **`buildssa` 関数**:
    *   `PPARAM`, `PPARAMOUT` の `decladdrs` への追加で、`Aux` に `&ssa.ArgSymbol{Typ: n.Type, Node: n}` を使用するようになりました。以前は `Offset` を直接設定していました。
    *   `PAUTO` の処理が変更され、`decladdrs` に直接追加されなくなりました。代わりに、コメントで「使用されるたびに処理され、`Addr` が宣言より前に来るのを防ぐ」と説明されています。これは、`VarDef` オペレーションと連携して、変数の生存期間を正確に追跡するための変更です。
    *   `OVARKILL` (変数キル) ステートメントの処理が追加され、`ssa.OpVarKill` オペレーションが挿入されるようになりました。これは、変数がもはやライブではないことを記録し、生存期間解析に役立ちます。
    *   `assign` 関数内で、`ONAME` (名前付き変数) の割り当て時に `ssa.OpVarDef` オペレーションが挿入されるようになりました。これは、変数が定義されたことをGCに通知するために重要です。
    *   `addr` 関数で `PAUTO` の処理が変更され、`ssa.OpAddr` オペレーションを使用してアドレスが再生成されるようになりました。これは、`VarDef` オペレーションと `LEA` (アドレス計算) 命令の順序関係を正しく保つためです。

*   **`genssa` 関数**:
    *   スタックフレームのサイズ計算 (`f.FrameSize`) や引数サイズの初期化に関する古いコードが削除されました。
    *   `allocauto(ptxt)` と `liveness(Curfn, ptxt, gcargs, gclocals)` が明示的に呼び出されるようになりました。これにより、SSAコードに対しても既存のスタックフレーム割り当てとGCビットマップ生成ロジックが適用されます。
    *   `removevardef(ptxt)` が追加され、`VarDef`/`VarKill` オペレーションが命令ストリームから削除されるようになりました。これらはGCビットマップ生成のためのメタデータであり、最終的な機械語には不要なためです。

### `src/cmd/compile/internal/ssa/config.go` の変更点

*   `Frontend` インターフェースに `Auto(Type) fmt.Stringer` メソッドが追加されました。これは、SSAコンパイラがスピルされた値のために新しい自動変数 (`*gc.Node`) を要求するためのインターフェースです。

### `src/cmd/compile/internal/ssa/gen/genericOps.go` の変更点

*   `VarDef` と `VarKill` という新しいSSAオペレーションが定義されました。これらは、変数の定義と生存期間の終了をマークするために使用されます。

### `src/cmd/compile/internal/ssa/location.go` の変更点

*   `LocalSlot` 構造体の `Idx int64` フィールドが `N fmt.Stringer` に変更されました。これにより、スタック上のスロットが単なるオフセットではなく、対応する `*gc.Node` (自動変数) に関連付けられるようになりました。

### `src/cmd/compile/internal/ssa/stackalloc.go` の変更点

*   スタック割り当てのロジックが根本的に変更されました。以前は `FrameSize` を直接計算していましたが、新しいアプローチでは `f.Config.fe.Auto(v.Type)` を呼び出すことで、SSAバックエンドがコンパイラのフロントエンドに新しい自動変数 (`*gc.Node`) の作成を要求します。これにより、スピルされた値が `gc.Node` として登録され、既存の `allocauto`/`defframe`/`liveness` メカニズムを通じてGCビットマップ生成の対象となります。

### `src/cmd/compile/internal/ssa/value.go` の変更点

*   `ArgSymbol` と `AutoSymbol` 構造体から `Sym` フィールドが削除され、代わりに `Node fmt.Stringer` フィールドが追加されました。これにより、これらのシンボルが直接ASTノードを参照できるようになり、より豊富なコンテキスト情報が利用可能になります。

これらの変更は、SSAコンパイラが生成するコードがGoのGCとより密接に連携し、正確なメモリ管理と効率的なスタックコピーを可能にするための基盤を築きました。

## 変更の背景

Go言語の `net/http/httputil` パッケージが提供する `ReverseProxy` は、クライアントからのHTTPリクエストをバックエンドサーバーに転送し、その応答をクライアントに返すための重要なコンポーネントです。このコミット以前は、`ReverseProxy` がバックエンドサーバーに接続できない、またはバックエンドからの応答がないといったネットワークレベルのエラーに遭遇した場合、クライアントに対して `http.StatusInternalServerError` (HTTPステータスコード 500) を返していました。

しかし、HTTPステータスコードのセマンティクスを厳密に解釈すると、`500 Internal Server Error` はプロキシサーバー自身の内部的な問題を示すべきです。一方、プロキシがバックエンドサーバーと通信できない状況は、プロキシが「不正なゲートウェイ」として機能していることを意味し、`502 Bad Gateway` がより適切です。

このセマンティクスの不整合は、クライアント側でのエラーハンドリングや、監視システムがエラーの原因を特定する際に混乱を招く可能性がありました。例えば、500エラーが多発している場合、プロキシサーバー自体に問題があるのか、それともバックエンドサーバーに問題があるのかがすぐに判別できません。

この問題を解決し、より正確なHTTPステータスコードを返すことで、エラーの根本原因の特定を容易にし、システムの運用監視を改善するために、Issue #9864 が起票され、このコミットによって修正されました。

## 前提知識の解説

### リバースプロキシ (Reverse Proxy)

リバースプロキシは、クライアントからのリクエストを受け取り、それを一つ以上のバックエンドサーバー（オリジンサーバーとも呼ばれる）に転送し、バックエンドからのレスポンスをクライアントに返すサーバーです。クライアントはリバースプロキシと直接通信しているように見えますが、実際にはリバースプロキシがバックエンドサーバーとの間の仲介役を果たします。

リバースプロキシの主な用途には以下のようなものがあります。
- **ロードバランシング**: 複数のバックエンドサーバーにリクエストを分散させ、負荷を均等にする。
- **SSLターミネーション**: SSL/TLS暗号化の処理をプロキシで行い、バックエンドサーバーの負荷を軽減する。
- **キャッシュ**: 静的コンテンツをキャッシュし、バックエンドサーバーへのリクエスト数を減らす。
- **セキュリティ**: バックエンドサーバーを外部から直接アクセスできないように保護する。
- **URL書き換え**: クライアントに見せるURLと、バックエンドサーバーが処理するURLを変換する。

Go言語の `net/http/httputil.ReverseProxy` は、このようなリバースプロキシの機能を簡単に実装するための構造体とメソッドを提供します。

### HTTPステータスコード 500 (Internal Server Error)

`500 Internal Server Error` は、HTTP/1.1 のステータスコードで、サーバーがリクエストを処理する際に予期しない状況に遭遇し、その結果リクエストを完了できなかったことを示す汎用的なエラーレスポンスコードです。これは通常、サーバー自身の内部的な問題（例: アプリケーションのバグ、データベース接続エラー、設定ミスなど）を示唆します。クライアントは、このエラーが発生した場合、サーバー側の問題であると判断し、再試行しても解決しない可能性が高いと認識します。

### HTTPステータスコード 502 (Bad Gateway)

`502 Bad Gateway` は、HTTP/1.1 のステータスコードで、ゲートウェイまたはプロキシとして機能しているサーバーが、アップストリームサーバー（リクエストを処理しようとしてアクセスしたサーバー）から無効なレスポンスを受け取ったことを示すエラーレスポンスコードです。このコードは、プロキシ自体は正常に動作しているが、そのプロキシが通信しようとしたバックエンドサーバーに問題があるか、バックエンドからの応答がHTTPプロトコルに準拠していない場合に用いられます。具体的には、バックエンドサーバーがダウンしている、ネットワーク接続が切断された、バックエンドがタイムアウトした、または不正なHTTP応答を返したなどの状況で発生します。

500と502の重要な違いは、エラーの原因がプロキシ自身にあるのか（500）、それともプロキシが通信しようとしたバックエンドサーバーにあるのか（502）という点です。

## 技術的詳細

`net/http/httputil.ReverseProxy` の内部では、クライアントからのHTTPリクエストを受け取ると、それをバックエンドサーバーに転送するために `http.RoundTripper` インターフェースを実装した `Transport` を利用します。デフォルトでは `http.DefaultTransport` が使用されます。

`ReverseProxy` の `ServeHTTP` メソッドは、以下の主要なステップを実行します。
1.  クライアントからのリクエストを解析し、バックエンドサーバーに転送するための新しいリクエスト (`outreq`) を作成します。
2.  `p.Transport.RoundTrip(outreq)` を呼び出して、バックエンドサーバーへリクエストを送信し、応答を受け取ります。
3.  この `RoundTrip` の呼び出し中に、バックエンドサーバーへの接続が確立できない、DNS解決に失敗する、接続がタイムアウトする、またはバックエンドサーバーが応答を返さないといったネットワークレベルのエラーが発生した場合、`RoundTrip` はエラー (`err`) を返します。

このコミット以前は、`RoundTrip` がエラーを返した場合、`ReverseProxy` は `rw.WriteHeader(http.StatusInternalServerError)` を呼び出してクライアントに 500 エラーを返していました。

このコミットでは、このエラー処理ロジックが変更され、`RoundTrip` がエラーを返した場合には `rw.WriteHeader(http.StatusBadGateway)` を呼び出すように修正されました。これにより、プロキシがバックエンドサーバーと通信できなかったという具体的な状況を、より正確な 502 Bad Gateway ステータスコードでクライアントに伝えることができるようになりました。

テストコード (`reverseproxy_test.go`) では、この新しい動作を検証するために、以下のような工夫がされています。
-   `httptest.NewServer` を使用して、テスト用のバックエンドサーバーを模擬します。
-   この模擬バックエンドサーバーのハンドラ内で、特定のクエリパラメータ (`mode=hangup`) が指定された場合に、`http.Hijacker` インターフェースを利用してクライアントとの接続を強制的に切断します (`c.Close()`)。これにより、バックエンドサーバーが応答を返さない、または到達不能な状況をシミュレートします。
-   `ReverseProxy` を設定し、この模擬バックエンドサーバーをターゲットとします。
-   `frontend.URL + "/?mode=hangup"` へのリクエストを `http.DefaultClient` で実行し、その結果として返されるHTTPステータスコードが `http.StatusBadGateway` (502) であることをアサートします。
-   `proxyHandler.ErrorLog = log.New(ioutil.Discard, "", 0)` の行は、テスト中に `ReverseProxy` が出力する可能性のあるエラーログを `/dev/null` にリダイレクトし、テストの出力をクリーンに保つためのものです。

## コアとなるコードの解説

### `reverseproxy.go` の変更

この変更は、`ReverseProxy` の `ServeHTTP` メソッド内で、バックエンドへの `RoundTrip` がエラーを返した場合の処理を修正しています。
以前は、`transport.RoundTrip(outreq)` がエラーを返すと、プロキシは `http.StatusInternalServerError` (500) をクライアントに返していました。
このコミットにより、エラー発生時には `http.StatusBadGateway` (502) を返すように変更されました。
これにより、プロキシがバックエンドサーバーと通信できなかったという、より具体的で正確なエラーセマンティクスがクライアントに伝達されるようになります。これは、プロキシ自身の内部エラーではなく、プロキシがゲートウェイとして機能する際にアップストリームサーバーから無効な応答を受け取った、または応答がなかったことを明確に示します。

### `reverseproxy_test.go` の変更

`TestReverseProxy` 関数内に新しいテストケースが追加され、`ReverseProxy` の新しいエラーハンドリング動作を検証しています。
1.  **バックエンドの模擬**: `httptest.NewServer` で模擬バックエンドサーバーが作成されます。このサーバーのハンドラには、`mode=hangup` クエリパラメータが指定された場合に、`http.Hijacker` インターフェースを使用してクライアント接続を強制的に切断するロジックが追加されています。これは、バックエンドサーバーが応答しない、または到達不能な状況をシミュレートするための重要な部分です。
2.  **エラーログの抑制**: `proxyHandler.ErrorLog = log.New(ioutil.Discard, "", 0)` の行が追加されました。これは、テスト中に `ReverseProxy` がバックエンドとの通信エラー時に出力する可能性のあるエラーログを抑制し、テストの出力をクリーンに保つためのものです。`ioutil.Discard` は書き込みを破棄する `io.Writer` であり、ログがどこにも出力されないようにします。
3.  **テストリクエストの実行**: `frontend.URL + "/?mode=hangup"` へのHTTP GETリクエストが作成され、`http.DefaultClient.Do(getReq)` を使用して実行されます。このリクエストは、模擬バックエンドサーバーの「接続切断」ロジックをトリガーするように設計されています。
4.  **ステータスコードの検証**: リクエストの結果として返されるHTTPレスポンスのステータスコードが `http.StatusBadGateway` (502) であることをアサートしています。これにより、`ReverseProxy` がバックエンドとの通信エラー時に期待通りに 502 エラーを返していることが検証されます。

これらの変更により、`net/http/httputil.ReverseProxy` は、バックエンドサーバーとの通信エラーに対してより正確なHTTPステータスコードを返すようになり、システムの信頼性と診断性が向上しました。

## 変更の背景

このコミットの主な背景は、Go言語のARMアーキテクチャ向けビルドにおいて、Clangコンパイラを使用する際に発生していたコンパイルエラーを解決することです。具体的には、`src/runtime/cgo/gcc_arm.S`というアセンブリファイル内で使用されている`BLX`命令の扱いが問題となっていました。

元々、このアセンブリファイルでは、アセンブラに対してターゲットアーキテクチャを`armv5t`として指定するために`.arch armv5t`ディレクティブが使用されていました。これは、`BLX`命令がARMv5T以降のアーキテクチャで導入されたため、古いアセンブラがデフォルトで`BLX`を認識しない場合に明示的に指定する必要があったためです。

しかし、Clangのアセンブラ（LLVMのintegrated assembler）は、この`.arch`ディレクティブのサポートが不完全であったり、特定の状況下で正しく解釈できない問題がありました。その結果、`BLX`命令が「選択されたプロセッサがARMモードの`blx r0`をサポートしていません」といったエラーメッセージと共にコンパイルに失敗していました。

コミットメッセージによると、この問題に対する以前の試みとして、外部アセンブラに切り戻すというアプローチも検討されましたが、これはうまくいきませんでした。そこで、Minux氏が提案した、`.word`ディレクティブを使って`BLX`命令の機械語を直接埋め込むという、より堅牢な解決策が採用されることになりました。これにより、アセンブラの`.arch`ディレクティブの解釈に依存することなく、確実に正しい機械語が生成されるようになります。

この修正は、GoのARMビルドにおけるClangサポートを改善し、より広範な開発環境でのGoの利用を可能にすることを目的としています。

## 前提知識の解説

このコミットの変更内容を深く理解するためには、以下の技術的な前提知識が必要です。

### GoのCGO

CGOは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。Goはシステムプログラミング言語であり、OSのシステムコールや既存のCライブラリと連携する必要がある場面が多々あります。CGOは、このような異なる言語間のインターフェースを提供し、Goの柔軟性と拡張性を高めています。

CGOを使用すると、Goのソースファイル内にCのコードを直接記述したり、既存のCのヘッダファイルをインポートしてCの関数やデータ構造を利用したりできます。GoとCの間でデータをやり取りする際には、型変換やメモリ管理の考慮が必要になります。特に、異なるスタックやレジスタ規約を持つ環境間での関数呼び出し（クロスコール）は、アセンブリ言語レベルでの特別な処理が必要となる場合があります。このコミットで修正されている`crosscall_arm1`関数は、まさにCGOにおけるクロスコールの一部を担うアセンブリコードです。

### ARMアーキテクチャ

ARM（Advanced RISC Machine）は、モバイルデバイス、組み込みシステム、サーバーなど、幅広い分野で利用されているRISC（Reduced Instruction Set Computer）ベースのプロセッサアーキテクチャです。ARMプロセッサは、その電力効率の高さと性能のバランスから、特にスマートフォンやタブレットで広く採用されています。

ARMアーキテクチャには、いくつかの命令セットとモードがあります。
*   **ARMモード**: 32ビット幅の命令を使用するモードで、高い性能を発揮します。
*   **Thumbモード**: 16ビット幅の命令を使用するモードで、コードサイズを削減し、メモリ効率を高めます。一部のARMプロセッサでは、Thumb-2という16ビットと32ビット命令を混在できるモードもサポートされています。

プロセッサは、これらのモード間を切り替えることで、性能とコードサイズのバランスを取ることができます。

### BLX命令

`BLX`（Branch with Link and eXchange instruction set）命令は、ARMアーキテクチャにおける重要な分岐命令の一つです。その名の通り、以下の2つの主要な機能を持っています。

1.  **分岐（Branch）**: 指定されたアドレスにプログラムの実行フローをジャンプさせます。
2.  **リンク（Link）**: 分岐元の次の命令のアドレスをリンクレジスタ（`LR`、`R14`）に保存します。これにより、呼び出されたサブルーチンが処理を終えた後、`LR`レジスタの値を使って呼び出し元に戻ることができます。
3.  **命令セットの切り替え（eXchange instruction set）**: `BLX`命令の最も特徴的な機能は、ARMモードとThumbモードの間で命令セットを切り替えることができる点です。
    *   `BLX <label>`（即値オフセットによる分岐）の場合、常に命令セットが切り替わります。
    *   `BLX <Rm>`（レジスタによる分岐）の場合、分岐先のレジスタ`Rm`の最下位ビット（LSB）が0であればARMモードに、1であればThumbモードに切り替わります。

`BLX`命令は、ARMv5Tアーキテクチャで導入されました。そのため、それ以前のアーキテクチャをターゲットとするアセンブラでは、この命令が認識されない場合があります。

### .archディレクティブ

`.arch`ディレクティブは、アセンブラに対して、コンパイル対象のコードが特定のARMアーキテクチャバージョン向けであることを指示するために使用されます。例えば、`.arch armv5t`と記述することで、アセンブラはARMv5T以降の命令セット（`BLX`など）を認識し、それらの命令を正しくアセンブルできるようになります。

しかし、アセンブラの実装によっては、このディレクティブのサポートが不完全であったり、特定のコンテキストで期待通りに機能しないことがあります。特に、異なるコンパイラツールチェーン（例: GCCとClang）間でアセンブラの挙動に差異が生じることがあります。

### .wordディレクティブ

`.word`ディレクティブは、アセンブラに対して、指定された32ビット（4バイト）の値を直接、現在のメモリ位置に埋め込むように指示する擬似命令です。これは、アセンブラが命令を解釈して機械語に変換するのではなく、開発者が直接指定した機械語のバイト列をバイナリに挿入したい場合に非常に有用です。

例えば、`BLX r5`というアセンブリ命令は、特定の32ビットの機械語（このコミットでは`0xe12fff35`）に変換されます。通常のアセンブルではアセンブラがこの変換を行いますが、`.word 0xe12fff35`と記述することで、アセンブラの解釈を介さずに、直接この機械語をバイナリに埋め込むことができます。これにより、アセンブラのバージョンや設定に依存しない、より堅牢なコードを記述することが可能になります。

### ClangとGCC

ClangとGCCは、C、C++、Objective-Cなどの言語をコンパイルするための主要なコンパイラツールチェーンです。どちらもオープンソースであり、広く利用されています。

*   **GCC (GNU Compiler Collection)**: 長い歴史を持ち、非常に成熟したコンパイラです。多くの場合、デフォルトのアセンブラとしてGNU Binutilsの`as`を使用します。
*   **Clang**: LLVMプロジェクトの一部として開発されており、モジュール化された設計と高速なコンパイルが特徴です。Clangは通常、独自の統合アセンブラ（integrated assembler）を使用します。

このコミットの問題は、GCCのアセンブラでは問題なく処理されていた`.arch`ディレクティブと`BLX`命令の組み合わせが、Clangの統合アセンブラでは正しく機能しなかったことに起因します。これは、両者のアセンブラの実装や、ARMアーキテクチャの特定の命令セットに対するサポートのニュアンスの違いによるものです。

## 技術的詳細

このコミットの技術的な核心は、ClangコンパイラがARMアセンブリコード内の`BLX`命令を正しくアセンブルできない問題に対する解決策です。

### Clangの`.arch`サポートの問題

Goのランタイムコード、特にCGO関連のアセンブリファイル（`src/runtime/cgo/gcc_arm.S`）では、ARMv5T以降で導入された`BLX`命令を使用しています。この命令は、分岐と同時に命令セット（ARM/Thumb）を切り替える機能を持つため、CGOのような異なる実行コンテキスト間での呼び出しにおいて非常に重要です。

アセンブラに対して、`BLX`命令が利用可能なアーキテクチャバージョンであることを伝えるために、元のコードでは`.arch armv5t`というディレクティブが使用されていました。しかし、Clangの統合アセンブラは、この`.arch`ディレクティブの解釈に問題がありました。具体的には、Clangは`armv5t`という指定にもかかわらず、`BLX`命令を認識せず、「selected processor does not support ARM mode `blx r0`」のようなエラーを出力してコンパイルを中断していました。これは、Clangのアセンブラが、特定のARMモードでの`BLX`命令の利用を、指定された`.arch`設定にもかかわらず、サポートしていないと誤って判断していたためと考えられます。

### `.word`ディレクティブによる直接エンコード

この問題に対する解決策として、Minux氏が提案したのは、アセンブラに`BLX`命令を解釈させるのではなく、その機械語表現を直接`.word`ディレクティブで埋め込むというアプローチでした。

`BLX r5`というアセンブリ命令は、ARMの命令エンコーディング規則に従って、特定の32ビットの機械語に変換されます。このコミットでは、`BLX r5`が`0xe12fff35`に、`BLX r4`が`0xe12fff34`にそれぞれ対応します。

*   `0xe12fff35`: これはARM命令の32ビット表現です。
    *   上位4ビット `E` (1110) は条件コード（常に実行）を示します。
    *   残りのビットは、`BLX`命令の形式（レジスタ間接分岐）と、ターゲットレジスタ（`r5`）をエンコードしています。
*   `0xe12fff34`: 同様に、`BLX r4`の機械語表現です。ターゲットレジスタが`r4`である点が異なります。

これらの機械語を`.word`ディレクティブ（例: `.word 0xe12fff35`）で直接アセンブリファイルに記述することで、アセンブラはこれらの値を単なる32ビットデータとして扱い、そのままバイナリに埋め込みます。これにより、アセンブラが`BLX`命令の構文を解析したり、ターゲットアーキテクチャのサポート状況を確認したりするプロセスを完全にバイパスできます。結果として、Clangのアセンブラが`BLX`命令の解釈でエラーを出すことなく、期待通りの機械語が生成されるようになります。

### `crosscall_arm1`関数の役割

`crosscall_arm1`関数は、GoのCGOランタイムにおいて、CコードからGoコードへ、またはその逆の呼び出しを行う際のコンテキストスイッチを処理するアセンブリ関数です。この関数は、レジスタの保存・復元、スタックポインタの調整、そしてGoランタイムのスケジューラに関連する処理などを行います。

コミットメッセージに示されているGDBの出力からもわかるように、`crosscall_arm1`関数は、`push`でレジスタを保存し、`mov`で引数をレジスタに移動した後、`blx r5`（`setg_gcc`関数を呼び出し、Goのg（goroutine）ポインタを設定）と`blx r4`（実際のGo関数`fn`を呼び出し）を実行し、最後に`pop`でレジスタを復元して呼び出し元に戻ります。この一連の処理の中で、`BLX`命令は、CGOのクロスコールにおいて、異なる言語の関数を呼び出すための重要な役割を担っています。

### GDBによる確認

コミットメッセージには、GDB（GNU Debugger）を使って生成された機械語が期待通りであることを確認した旨が記載されています。これは、`.word`ディレクティブによって直接埋め込まれた機械語が、実際に`blx r5`や`blx r4`としてデバッグ情報に表示され、正しく実行されることを検証したことを意味します。この確認は、修正の有効性を裏付ける重要なステップです。

### 残された問題

このコミットはClangでのビルドエラーの一つを修正しましたが、コミットメッセージの最後には「There is another compilation failure that blocks building Go with clang on arm」とあり、別のコンパイルエラーがまだ残っていることが示されています。これは、`blx r0`に関するエラーで、このコミットでは対処されていません。この問題は、別途新しいIssueとして追跡されることになりました。これは、GoのARMビルドにおけるClangサポートが、このコミットだけでは完全に解決しない、より複雑な課題を抱えていることを示唆しています。

## コアとなるコードの解説

このコミットにおけるコアとなるコードの変更は、ClangコンパイラがARMアセンブリの`BLX`命令を正しく処理できない問題に対する直接的な回避策です。

### `.arch armv5t`の削除の理由

元のコードでは、`BLX`命令がARMv5T以降で導入されたため、アセンブラがこの命令を認識できるように`.arch armv5t`と明示的に指定していました。これは、古いアセンブラがデフォルトで古いARMアーキテクチャをターゲットとする場合に必要でした。

しかし、Clangのアセンブラは、この`.arch`ディレクティブを正しく解釈できない、あるいは特定のコンテキストで`BLX`命令のサポートを適切に有効にできないという問題がありました。このため、`.arch armv5t`が存在しても、Clangは`BLX`命令でエラーを発生させていました。

このコミットでは、この問題のある`.arch`ディレクティブを完全に削除することで、Clangのアセンブラがその解釈に失敗する可能性を排除しています。

### `blx`から`.word`への置き換えの理由と効果

`.arch`ディレクティブを削除しただけでは、アセンブラは`BLX`命令を認識できなくなるため、別の方法で`BLX`命令をバイナリに含める必要があります。ここで登場するのが`.word`ディレクティブです。

*   **`blx r5`の機械語 `0xe12fff35`**:
    この32ビットの16進数値は、ARMアーキテクチャにおける「レジスタ`r5`の内容をアドレスとして`BLX`命令を実行する」という操作に対応する機械語です。
*   **`blx r4`の機械語 `0xe12fff34`**:
    同様に、これは「レジスタ`r4`の内容をアドレスとして`BLX`命令を実行する」という操作に対応する機械語です。

`.word 0xe12fff35`と記述することで、アセンブラは`0xe12fff35`という値を、それが命令であるかどうかに関わらず、そのまま32ビットのデータとして出力バイナリに埋め込みます。これにより、アセンブラが`BLX`命令の構文を解析したり、ターゲットアーキテクチャのサポート状況を確認したりするプロセスを完全にバイパスできます。結果として、Clangのアセンブラが`BLX`命令の解釈でエラーを出すことなく、期待通りの機械語が生成されるようになります。

この変更は、アセンブラの特定の挙動に依存するのではなく、命令の最終的な機械語表現を直接指定することで、コンパイラツールチェーンの互換性の問題を回避する、非常に堅牢なアプローチと言えます。これは、Goのランタイムのような低レベルなコードにおいて、異なるコンパイラやアセンブラ環境での安定したビルドを保証するために有効な手段です。

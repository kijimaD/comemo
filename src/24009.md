# [インデックス 24009] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおける`nilcheckelim`（nilチェック除去）パスのパフォーマンス特性を明らかにするために、ベンチマークを追加するものです。特に、このパスが特定の条件下でO(n^2)の計算量を持つことを示し、さらに支配木（dominator tree）の構築も同様にO(n^2)である可能性を指摘しています。

`cmd/compile/ssa`パッケージに`nilcheckelim`のベンチマークを追加。これらのベンチマークは、`nilcheckelim`パスがおおよそO(n^2)の計算量を持つことを示しています。プロファイリングの結果、支配木の構築もO(n^2)であり、サイズ要因が支配的になる前は`nilcheckelim`よりもかなりコストが高いことが示唆されています。

## 変更の背景

Goコンパイラは、プログラムの最適化のためにSSA（Static Single Assignment）形式の中間表現を使用しています。`nilcheckelim`は、このSSA形式上で実行される最適化パスの一つで、冗長なnilポインタチェックを削除することを目的としています。例えば、あるポインタが既にnilでないことが証明されている場合、その後の同じポインタに対するnilチェックは不要になります。

このコミットが作成された背景には、`nilcheckelim`パスのパフォーマンス特性、特にその計算量に対する懸念があったと考えられます。コンパイラの最適化パスは、コンパイル時間に直接影響するため、その効率性は非常に重要です。特に、入力サイズ（ここではSSA形式のブロック数や値の数）に対して計算量が二次関数的に増加するO(n^2)のアルゴリズムは、大規模なプログラムのコンパイルにおいてボトルネックとなる可能性があります。

このコミットは、`nilcheckelim`パスが実際にO(n^2)の挙動を示すことをベンチマークによって定量的に確認し、その原因が`nilcheckelim`自身だけでなく、その前提となる支配木構築アルゴリズムにもあることを示唆しています。これにより、将来的なパフォーマンス改善のための具体的なターゲットが特定されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての基本的な知識が必要です。

1.  **GoコンパイラとSSA（Static Single Assignment）形式**:
    *   Goコンパイラは、ソースコードを直接機械語に変換するのではなく、複数の段階を経て処理します。その中間段階の一つで、プログラムはSSA形式という特殊な中間表現に変換されます。
    *   SSA形式では、各変数が一度だけ代入されるように変換されます。これにより、データフロー解析や最適化が容易になります。
    *   `cmd/compile/internal/ssa`パッケージは、このSSA形式を扱うGoコンパイラのバックエンド部分です。

2.  **nilポインタチェック**:
    *   Go言語では、nilポインタへのアクセスはランタイムパニックを引き起こします。これを防ぐため、コンパイラはポインタがnilでないことを保証できないアクセスに対して、自動的にnilチェックを挿入します。
    *   例えば、`x.Method()`のような呼び出しでは、`x`がnilでないことを確認するチェックが挿入されます。

3.  **nilcheckelim（nilチェック除去）最適化**:
    *   コンパイラの最適化パスの一つで、プログラムの実行フローを解析し、既にnilでないことが保証されているポインタに対する冗長なnilチェックを削除します。これにより、生成されるバイナリのサイズを削減し、実行時のオーバーヘッドを減らすことができます。

4.  **支配木（Dominator Tree）**:
    *   プログラムの制御フローグラフ（CFG）において、あるブロックAがブロックBの「支配者（dominator）」であるとは、AからBへのすべてのパスがAを通過する場合を言います。
    *   支配木は、各ブロックとその直接の支配者（immediate dominator）の関係を木構造で表現したものです。
    *   支配木は、多くのデータフロー解析や最適化アルゴリズム（例: 共通部分式除去、ループ不変コード移動、そしてnilチェック除去など）の基礎となります。nilチェック除去では、支配木を辿ることで、あるポインタが特定の時点でnilでないことが保証されているかどうかを判断します。

5.  **計算量（Big O表記）**:
    *   アルゴリズムの効率性を示す指標で、入力サイズ`n`が増加したときに、アルゴリズムの実行時間や使用メモリがどのように増加するかを表します。
    *   O(n^2)は、入力サイズ`n`に対して実行時間が二次関数的に増加することを示します。これは、`n`が大きくなると非常に効率が悪くなることを意味します。

## 技術的詳細

このコミットの核心は、`nilcheckelim`パスと支配木構築の計算量がO(n^2)であるという発見と、それを実証するためのベンチマークの追加です。

### `nilcheckelim`のO(n^2)特性

`nilcheckelim`パスは、`nilcheck.go`内の`nilcheckelim`関数で実装されています。この関数は、各ブロック内のnilチェックを走査し、そのチェックが冗長であるかどうかを判断するために、支配木を遡って既に同じポインタがnilでないことがチェックされているかどうかを確認します。

コミットメッセージと`nilcheck.go`に追加されたコメント`// TODO: This loop is O(n^2). See BenchmarkNilCheckDeep*.`が示すように、この支配木を遡るループがO(n^2)のボトルネックとなっています。具体的には、最悪のケース（例えば、線形に連なる多数のブロックがあり、各ブロックでnilチェックが行われるが、どれも除去できないようなシナリオ）では、各nilチェックに対して支配木を根まで辿る必要があり、これが全体の計算量を二次関数的に増加させます。

### 支配木構築のO(n^2)特性

`dom.go`内の`dominators`関数は、支配木を構築する役割を担っています。このコミットでは、`dominators`関数と、その中で使用される`intersect`関数に`// TODO: This loop is O(n^2). See BenchmarkNilCheckDeep*.`というコメントが追加されています。これは、支配木の構築アルゴリズム自体もO(n^2)の計算量を持つ可能性があることを示唆しています。

特に`intersect`関数は、2つのブロックの最も近い共通支配者を見つけるために使用されます。この関数も、最悪のケースでは支配木を根まで遡る必要があり、これがO(n^2)のボトルネックとなる可能性があります。

### `BenchmarkNilCheckDeep`ベンチマーク

`nilcheck_test.go`に新しく追加された`benchmarkNilCheckDeep`関数は、`nilcheckelim`パスの最悪ケースをシミュレートするために設計されています。このベンチマークは、以下のような特徴を持つSSA関数を生成します。

*   **線形なブロックチェーン**: `depth`パラメータで指定された数のブロックが線形に連結されます。
*   **除去不可能なnilチェック**: 各ブロックには、そのブロック内で初めて登場する新しいポインタに対するnilチェックが挿入されます。これにより、どのnilチェックも冗長ではなく、`nilcheckelim`パスによって除去されることはありません。
*   **支配木の深さ**: この構造は、支配木が非常に深くなることを意味し、`nilcheckelim`が支配木を遡る際のコストを最大化します。

ベンチマーク結果は、`depth`が1から10000に増加するにつれて、`ns/op`（操作あたりのナノ秒）が劇的に増加し、O(n^2)の挙動を明確に示しています。

```

BenchmarkNilCheckDeep10          1000000              2237 ns/op           4.47 MB/s
BenchmarkNilCheckDeep100           20000             60713 ns/op           1.65 MB/s
BenchmarkNilCheckDeep1000            200           7925198 ns/op           0.13 MB/s

`BenchmarkNilCheckDeep10000`では、1回の操作に1.2秒以上かかっており、`depth`が大きくなるとコンパイル時間が非常に長くなることがわかります。

```go
// TODO: Benchmarks. See BenchmarkNilCheckDeep* for an example.
func dominators(f *Func) []*Block {
    // ... 既存の支配木構築ロジック ...
}

// intersect finds the closest dominator of both b and c.
// It requires a postorder numbering of all the blocks.
func intersect(b, c *Block, postnum []int, idom []*Block) *Block {
    // TODO: This loop is O(n^2). See BenchmarkNilCheckDeep*.
    for b != c {
        if postnum[b.ID] < postnum[c.ID] {
            b = idom[b.ID]
        } else {
            c = idom[c.ID]
        }
    }
    return b
}
```
`dominators`関数は、関数の制御フローグラフから支配木を計算します。追加されたコメントは、この関数（および`intersect`関数）の計算量に問題がある可能性を指摘し、新しく追加されたベンチマークを参照することで、そのパフォーマンス特性を検証するよう促しています。`intersect`関数内の`for`ループは、最悪のケースで支配木の深さに比例して実行されるため、全体の支配木構築アルゴリズムがO(n^2)になる原因の一つと考えられます。

### `src/cmd/compile/internal/ssa/nilcheck.go`

```go
func nilcheckelim(f *Func) {
    // ...
    for _, b := range f.Blocks {
        for _, v := range b.Values {
            if v.Op != OpIsNonNil {
                continue
            }
            ptr := v.Args[0]
            // ...
            var elim bool
            // Walk up the dominator tree,
            // looking for identical nil checks.
            // TODO: This loop is O(n^2). See BenchmarkNilCheckDeep*.
            for c := idom[b.ID]; c != nil; c = idom[c.ID] {
                if checkedptr(c) == ptr {
                    elim = true
                    break
                }
            }
            // ...
        }
    }
}
```
`nilcheckelim`関数は、各ブロック内の`OpIsNonNil`操作（nilチェック）を走査します。そして、そのチェックが冗長かどうかを判断するために、現在のブロックの直接の支配者（`idom[b.ID]`）から支配木を遡っていきます。この`for c := idom[b.ID]; c != nil; c = idom[c.ID]`というループが、最悪のケースで支配木の深さに比例して実行されるため、`nilcheckelim`パス全体の計算量がO(n^2)になる原因と特定されています。追加されたコメントは、このボトルネックを明確に示しています。

```go
package ssa

import (
	"strconv"
	"testing"
)

func BenchmarkNilCheckDeep1(b *testing.B)     { benchmarkNilCheckDeep(b, 1) }
func BenchmarkNilCheckDeep10(b *testing.B)    { benchmarkNilCheckDeep(b, 10) }
func BenchmarkNilCheckDeep100(b *testing.B)   { benchmarkNilCheckDeep(b, 100) }
func BenchmarkNilCheckDeep1000(b *testing.B)  { benchmarkNilCheckDeep(b, 1000) }
func BenchmarkNilCheckDeep10000(b *testing.B) { benchmarkNilCheckDeep(b, 10000) }

// benchmarkNilCheckDeep is a stress test of nilcheckelim.
// It uses the worst possible input: A linear string of
// nil checks, none of which can be eliminated.
// Run with multiple depths to observe big-O behavior.
func benchmarkNilCheckDeep(b *testing.B, depth int) {
	ptrType := &TypeImpl{Size_: 8, Ptr: true, Name: "testptr"} // dummy for testing

	var blocs []bloc
	blocs = append(blocs,
		Bloc("entry",
			Valu("mem", OpArg, TypeMem, 0, ".mem"),
			Goto(blockn(0)),
		),
	)
	for i := 0; i < depth; i++ {
		blocs = append(blocs,
			Bloc(blockn(i),
				Valu(ptrn(i), OpGlobal, ptrType, 0, nil),
				Valu(booln(i), OpIsNonNil, TypeBool, 0, nil, ptrn(i)),
				If(booln(i), blockn(i+1), "exit"),
			),
		)
	}
	blocs = append(blocs,
		Bloc(blockn(depth), Goto("exit")),
		Bloc("exit", Exit("mem")),
	)

	c := NewConfig("amd64", DummyFrontend{b})
	fun := Fun(c, "entry", blocs...)

	CheckFunc(fun.f)
	b.SetBytes(int64(depth)) // helps for eyeballing linearity
	b.ResetTimer()

	for i := 0; i < b.N; i++ {
		nilcheckelim(fun.f)
	}
}

func blockn(n int) string { return "b" + strconv.Itoa(n) }
func ptrn(n int) string   { return "p" + strconv.Itoa(n) }
func booln(n int) string  { return "c" + strconv.Itoa(n) }
```
このファイルは、`nilcheckelim`のパフォーマンス問題を具体的に示すためのベンチマークを定義しています。`benchmarkNilCheckDeep`関数は、`depth`パラメータに基づいて、線形に連結されたブロックと、それぞれ異なるポインタに対するnilチェックを含むSSA関数を動的に生成します。この構造は、`nilcheckelim`が支配木を深く遡る必要がある最悪のシナリオを作り出します。

`b.SetBytes(int64(depth))`は、ベンチマーク結果の`MB/s`列に`depth`の値を表示させるためのもので、パフォーマンスの傾向を視覚的に把握しやすくします。`b.ResetTimer()`は、SSA関数の構築時間をベンチマーク測定から除外するために使用されます。

最終的に、`for i := 0; i < b.N; i++ { nilcheckelim(fun.f) }`のループ内で`nilcheckelim`関数が繰り返し実行され、その実行時間が測定されます。これにより、`depth`の増加に伴う`nilcheckelim`の計算量の増加が定量的に示されます。

このコミットを理解するためには、以下の概念についての基本的な知識が必要です。

1.  **GoコンパイラとSSA（Static Single Assignment）形式**:
    *   Goコンパイラは、ソースコードを直接機械語に変換するのではなく、複数の段階を経て処理します。その中間段階の一つで、プログラムはSSA形式という特殊な中間表現に変換されます。
    *   SSA形式では、各変数が一度だけ代入されるように変換されます。これにより、データフロー解析や最適化が容易になります。
    *   `cmd/compile/internal/ssa`パッケージは、このSSA形式を扱うGoコンパイラのバックエンド部分です。

2.  **nilポインタチェック**:
    *   Go言語では、nilポインタへのアクセスはランタイムパニックを引き起こします。これを防ぐため、コンパイラはポインタがnilでないことを保証できないアクセスに対して、自動的にnilチェックを挿入します。
    *   例えば、`x.Method()`のような呼び出しでは、`x`がnilでないことを確認するチェックが挿入されます。

3.  **nilcheckelim（nilチェック除去）最適化**:
    *   コンパイラの最適化パスの一つで、プログラムの実行フローを解析し、既にnilでないことが保証されているポインタに対する冗長なnilチェックを削除します。これにより、生成されるバイナリのサイズを削減し、実行時のオーバーヘッドを減らすことができます。

4.  **支配木（Dominator Tree）**:
    *   プログラムの制御フローグラフ（CFG）において、あるブロックAがブロックBの「支配者（dominator）」であるとは、AからBへのすべてのパスがAを通過する場合を言います。
    *   支配木は、各ブロックとその直接の支配者（immediate dominator）の関係を木構造で表現したものです。
    *   支配木は、多くのデータフロー解析や最適化アルゴリズム（例: 共通部分式除去、ループ不変コード移動、そしてnilチェック除去など）の基礎となります。nilチェック除去では、支配木を辿ることで、あるポインタが特定の時点でnilでないことが保証されているかどうかを判断します。

5.  **計算量（Big O表記）**:
    *   アルゴリズムの効率性を示す指標で、入力サイズ`n`が増加したときに、アルゴリズムの実行時間や使用メモリがどのように増加するかを表します。
    *   O(n^2)は、入力サイズ`n`に対して実行時間が二次関数的に増加することを示します。これは、`n`が大きくなると非常に効率が悪くなることを意味します。

## 技術的詳細

このコミットの核心は、`nilcheckelim`パスと支配木構築の計算量がO(n^2)であるという発見と、それを実証するためのベンチマークの追加です。

### `nilcheckelim`のO(n^2)特性

`nilcheckelim`パスは、`nilcheck.go`内の`nilcheckelim`関数で実装されています。この関数は、各ブロック内のnilチェックを走査し、そのチェックが冗長であるかどうかを判断するために、支配木を遡って既に同じポインタがnilでないことがチェックされているかどうかを確認します。

コミットメッセージと`nilcheck.go`に追加されたコメント`// TODO: This loop is O(n^2). See BenchmarkNilCheckDeep*.`が示すように、この支配木を遡るループがO(n^2)のボトルネックとなっています。具体的には、最悪のケース（例えば、線形に連なる多数のブロックがあり、各ブロックでnilチェックが行われるが、どれも除去できないようなシナリオ）では、各nilチェックに対して支配木を根まで辿る必要があり、これが全体の計算量を二次関数的に増加させます。

### 支配木構築のO(n^2)特性

`dom.go`内の`dominators`関数は、支配木を構築する役割を担っています。このコミットでは、`dominators`関数と、その中で使用される`intersect`関数に`// TODO: This loop is O(n^2). See BenchmarkNilCheckDeep*.`というコメントが追加されています。これは、支配木の構築アルゴリズム自体もO(n^2)の計算量を持つ可能性があることを示唆しています。

特に`intersect`関数は、2つのブロックの最も近い共通支配者を見つけるために使用されます。この関数も、最悪のケースでは支配木を根まで遡る必要があり、これがO(n^2)のボトルネックとなる可能性があります。

### `BenchmarkNilCheckDeep`ベンチマーク

`nilcheck_test.go`に新しく追加された`benchmarkNilCheckDeep`関数は、`nilcheckelim`パスの最悪ケースをシミュレートするために設計されています。このベンチマークは、以下のような特徴を持つSSA関数を生成します。

*   **線形なブロックチェーン**: `depth`パラメータで指定された数のブロックが線形に連結されます。
*   **除去不可能なnilチェック**: 各ブロックには、そのブロック内で初めて登場する新しいポインタに対するnilチェックが挿入されます。これにより、どのnilチェックも冗長ではなく、`nilcheckelim`パスによって除去されることはありません。
*   **支配木の深さ**: この構造は、支配木が非常に深くなることを意味し、`nilcheckelim`が支配木を遡る際のコストを最大化します。

ベンチマーク結果は、`depth`が1から10000に増加するにつれて、`ns/op`（操作あたりのナノ秒）が劇的に増加し、O(n^2)の挙動を明確に示しています。

```

BenchmarkNilCheckDeep10          1000000              2237 ns/op           4.47 MB/s

`BenchmarkNilCheckDeep10000`では、1回の操作に1.2秒以上かかっており、`depth`が大きくなるとコンパイル時間が非常に長くなることがわかります。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/dom.go`

```go
// TODO: Benchmarks. See BenchmarkNilCheckDeep* for an example.
func dominators(f *Func) []*Block {
    // ... 既存の支配木構築ロジック ...
}

// intersect finds the closest dominator of both b and c.
// It requires a postorder numbering of all the blocks.
func intersect(b, c *Block, postnum []int, idom []*Block) *Block {
    // TODO: This loop is O(n^2). See BenchmarkNilCheckDeep*.
    for b != c {
        if postnum[b.ID] < postnum[c.ID] {
            b = idom[b.ID]
        } else {
            c = idom[c.ID]
        }
    }
    return b
}
```
`dominators`関数は、関数の制御フローグラフから支配木を計算します。追加されたコメントは、この関数（および`intersect`関数）の計算量に問題がある可能性を指摘し、新しく追加されたベンチマークを参照することで、そのパフォーマンス特性を検証するよう促しています。`intersect`関数内の`for`ループは、最悪のケースで支配木の深さに比例して実行されるため、全体の支配木構築アルゴリズムがO(n^2)になる原因の一つと考えられます。

### `src/cmd/compile/internal/ssa/nilcheck.go`

```go
func nilcheckelim(f *Func) {
    // ...
    for _, b := range f.Blocks {
        for _, v := range b.Values {
            if v.Op != OpIsNonNil {
                continue
            }
            ptr := v.Args[0]
            // ...
            var elim bool
            // Walk up the dominator tree,
            // looking for identical nil checks.
            // TODO: This loop is O(n^2). See BenchmarkNilCheckDeep*.
            for c := idom[b.ID]; c != nil; c = idom[c.ID] {
                if checkedptr(c) == ptr {
                    elim = true
                    break
                }
            }
            // ...
        }
    }
}
```
`nilcheckelim`関数は、各ブロック内の`OpIsNonNil`操作（nilチェック）を走査します。そして、そのチェックが冗長かどうかを判断するために、現在のブロックの直接の支配者（`idom[b.ID]`）から支配木を遡っていきます。この`for c := idom[b.ID]; c != nil; c = idom[c.ID]`というループが、最悪のケースで支配木の深さに比例して実行されるため、`nilcheckelim`パス全体の計算量がO(n^2)になる原因と特定されています。追加されたコメントは、このボトルネックを明確に示しています。

### `src/cmd/compile/internal/ssa/nilcheck_test.go` (新規ファイル)

```go
package ssa

import (
	"strconv"
	"testing"
)

func BenchmarkNilCheckDeep1(b *testing.B)     { benchmarkNilCheckDeep(b, 1) }
func BenchmarkNilCheckDeep10(b *testing.B)    { benchmarkNilCheckDeep(b, 10) }
func BenchmarkNilCheckDeep100(b *testing.B)   { benchmarkNilCheckDeep(b, 100) }
func BenchmarkNilCheckDeep1000(b *testing.B)  { benchmarkNilCheckDeep(b, 1000) }
func BenchmarkNilCheckDeep10000(b *testing.B) { benchmarkNilCheckDeep(b, 10000) }

// benchmarkNilCheckDeep is a stress test of nilcheckelim.
// It uses the worst possible input: A linear string of
// nil checks, none of which can be eliminated.
// Run with multiple depths to observe big-O behavior.
func benchmarkNilCheckDeep(b *testing.B, depth int) {
	ptrType := &TypeImpl{Size_: 8, Ptr: true, Name: "testptr"} // dummy for testing

	var blocs []bloc
	blocs = append(blocs,
		Bloc("entry",
			Valu("mem", OpArg, TypeMem, 0, ".mem"),
			Goto(blockn(0)),
		),
	)
	for i := 0; i < depth; i++ {
		blocs = append(blocs,
			Bloc(blockn(i),
				Valu(ptrn(i), OpGlobal, ptrType, 0, nil),
				Valu(booln(i), OpIsNonNil, TypeBool, 0, nil, ptrn(i)),
				If(booln(i), blockn(i+1), "exit"),
			),
		)
	}
	blocs = append(blocs,
		Bloc(blockn(depth), Goto("exit")),
		Bloc("exit", Exit("mem")),
	)

	c := NewConfig("amd64", DummyFrontend{b})
	fun := Fun(c, "entry", blocs...)

	CheckFunc(fun.f)
	b.SetBytes(int64(depth)) // helps for eyeballing linearity
	b.ResetTimer()

	for i := 0; i < b.N; i++ {
		nilcheckelim(fun.f)
	}
}

func blockn(n int) string { return "b" + strconv.Itoa(n) }
func ptrn(n int) string   { return "p" + strconv.Itoa(n) }
func booln(n int) string  { return "c" + strconv.Itoa(n) }
```
このファイルは、`nilcheckelim`のパフォーマンス問題を具体的に示すためのベンチマークを定義しています。`benchmarkNilCheckDeep`関数は、`depth`パラメータに基づいて、線形に連結されたブロックと、それぞれ異なるポインタに対するnilチェックを含むSSA関数を動的に生成します。この構造は、`nilcheckelim`が支配木を深く遡る必要がある最悪のシナリオを作り出します。

`b.SetBytes(int64(depth))`は、ベンチマーク結果の`MB/s`列に`depth`の値を表示させるためのもので、パフォーマンスの傾向を視覚的に把握しやすくします。`b.ResetTimer()`は、SSA関数の構築時間をベンチマーク測定から除外するために使用されます。

最終的に、`for i := 0; i < b.N; i++ { nilcheckelim(fun.f) }`のループ内で`nilcheckelim`関数が繰り返し実行され、その実行時間が測定されます。これにより、`depth`の増加に伴う`nilcheckelim`の計算量の増加が定量的に示されます。

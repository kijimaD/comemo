# [インデックス 27145] ファイルの概要

このコミットは、Goコンパイラ (`cmd/compile`) の内部パッケージである `src/cmd/internal/obj` におけるデータ保存ロジックのクリーンアップを目的としています。具体的には、`savedata` 関数のシグネチャを簡素化し、使用されていない `Link` コンテキストフィールド `Enforce_data_order` を削除することで、コードの可読性と保守性を向上させています。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、様々な中間表現を扱います。このコミットは、コンパイルプロセスの後半、特にオブジェクトファイル（`.o` ファイル）の生成に関連する部分の改善です。

`savedata` 関数は、コンパイラが生成するデータセクション（初期化されたデータやBSSセクションなど）をオブジェクトファイルに書き込むための内部ヘルパー関数です。この関数は、特定のシンボル (`LSym`) に関連付けられたデータを処理します。

変更の背景には、以下の点が考えられます。

1.  **コードの簡素化と保守性向上**: 既存の `savedata` 関数のシグネチャが冗長であったり、渡される引数の一部が関数内で直接取得可能であったりした場合、それを簡素化することでコードが読みやすくなり、将来的な変更が容易になります。
2.  **未使用コードの削除**: `Link` 構造体内の `Enforce_data_order` フィールドが、もはやコンパイラのロジックで利用されていないことが判明したため、これを削除することでデッドコードを排除し、コンパイラのフットプリントをわずかに減らし、混乱の元をなくします。未使用のフィールドやコードは、誤解を招いたり、将来的に誤って再利用されたりするリスクがあるため、定期的にクリーンアップされます。
3.  **コンパイラの進化**: Goコンパイラは継続的に改善されており、時間の経過とともに内部構造やアルゴリズムが洗練されます。この種のクリーンアップは、より効率的で堅牢なコンパイラを構築するための継続的な取り組みの一環です。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの内部構造と、オブジェクトファイル生成の基本的な概念を理解する必要があります。

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードをコンパイルし、実行可能なバイナリやオブジェクトファイルを生成するツールです。
*   **`src/cmd/internal/obj` パッケージ**: Goコンパイラのバックエンドの一部であり、アセンブラやリンカが使用するオブジェクトファイル形式を扱うための低レベルなユーティリティを提供します。シンボル、プログラム命令 (`Prog`)、リンカコンテキスト (`Link`) などの概念が定義されています。
*   **`Link` 構造体**: コンパイルおよびリンクプロセス全体の状態を保持するコンテキスト構造体です。ターゲットアーキテクチャ情報、デバッグフラグ、パス情報、シンボルテーブルなど、多くのフィールドを含みます。
*   **`LSym` (Linker Symbol)**: リンカが扱うシンボルを表す構造体です。関数、グローバル変数、データセクションなど、プログラム内の名前付きエンティティに対応します。各 `LSym` は、そのシンボルに関連付けられたデータやコードを持つことができます。
*   **`Prog` 構造体**: アセンブリ命令を表す構造体です。Goコンパイラは、中間表現から最終的な機械語命令を生成する際に、この `Prog` 構造体のリストを操作します。`Prog` には、命令の種類、オペランド、関連するシンボルなどの情報が含まれます。
*   **`savedata` 関数**: `obj` パッケージ内で、特定のシンボル (`LSym`) に関連付けられたデータ（例えば、初期化されたグローバル変数の値など）を、オブジェクトファイルに書き込む準備をする役割を担います。これは、`Prog` 命令の一部としてデータが指定された場合に呼び出されます。
*   **`Enforce_data_order`**: `Link` 構造体にあったフィールドで、データが特定の順序で書き込まれることを強制するためのフラグであったと推測されます。このコミットで削除されたことから、この順序制約が不要になったか、別のメカニズムで処理されるようになったことを示唆しています。
*   **`toolstash -cmp`**: Goプロジェクトで変更をテストする際に使用されるツールです。コンパイラやツールの変更が、生成されるバイナリに意図しない影響を与えないことを確認するために、変更前と変更後で生成されるオブジェクトファイルやバイナリを比較します。これをパスするということは、この変更がコンパイラの出力に機能的な影響を与えていないことを意味します。

## 技術的詳細

このコミットの技術的詳細は、主に `savedata` 関数のインターフェース変更と、`Link` 構造体からのフィールド削除に集約されます。

1.  **`savedata` 関数のシグネチャ変更**:
    *   変更前: `func savedata(ctxt *Link, s *LSym, p *Prog, file string)`
    *   変更後: `func savedata(ctxt *Link, p *Prog)`
    *   この変更により、`s *LSym` と `file string` の2つの引数が削除されました。
    *   `s *LSym` は、関数内で `p.From.Sym` から直接取得されるようになりました。これは、`Prog` 構造体自体が、その命令が関連するシンボルへの参照 (`p.From.Sym`) を持っているため、引数として別途渡す必要がなくなったことを意味します。これにより、関数の呼び出し側が `LSym` を明示的に渡す手間が省け、インターフェースが簡潔になります。
    *   `file string` 引数は完全に削除されました。元のコードでは、エラーメッセージ (`log.Fatalf`) の一部として使用されていましたが、この情報が不要になったか、より適切な方法でエラーが報告されるようになったためと考えられます。新しいエラーメッセージは `log.Fatalf("savedata: bad off=%d siz=%d", off, siz)` となり、ファイル名に依存しない形になりました。

2.  **`Link` 構造体からの `Enforce_data_order` フィールドの削除**:
    *   `src/cmd/internal/obj/link.go` 内の `Link` 構造体から `Enforce_data_order int32` フィールドが削除されました。
    *   これに伴い、`src/cmd/internal/obj/data.go` 内の `savedata` 関数から、このフィールドを参照する以下のコードが削除されました。
        ```go
        if ctxt.Enforce_data_order != 0 && off < int32(len(s.P)) {
            ctxt.Diag("data out of order (already have %d)\n%v", len(s.P), p)
        }
        ```
    *   このフィールドと関連するチェックが削除されたことは、データセクションの順序付けに関する特定の制約が、もはやコンパイラの設計上不要になったか、あるいは別のより抽象的なレイヤーで処理されるようになったことを示唆しています。例えば、データが常に正しい順序で生成されることが保証されるようになった、あるいは順序の強制が不要なケースが増えた、などが考えられます。

3.  **呼び出し箇所の更新**:
    *   `src/cmd/internal/obj/objfile.go` 内の `flushplist` 関数で `savedata` を呼び出している箇所が、新しいシグネチャに合わせて `savedata(ctxt, p.From.Sym, p, "<input>")` から `savedata(ctxt, p)` に変更されました。これは、インターフェース変更に伴う必然的な修正です。

これらの変更は、コンパイラの内部コードをよりクリーンで効率的に保つための典型的なリファクタリングであり、機能的な変更ではなく、主に保守性とコード品質の向上を目的としています。

## コアとなるコードの解説

### `savedata` 関数の変更

*   **シグネチャの簡素化**:
    *   `func savedata(ctxt *Link, s *LSym, p *Prog, file string)` から `func savedata(ctxt *Link, p *Prog)` へと変更されました。
    *   これにより、`savedata` を呼び出す側は、`LSym` と `file` の情報を明示的に渡す必要がなくなりました。
*   **`LSym` の取得元変更**:
    *   変更前は引数 `s *LSym` として受け取っていましたが、変更後は関数内で `s := p.From.Sym` とすることで、`Prog` 構造体 `p` から関連するシンボル情報を直接取得しています。これは、`ADATA` 命令が常に特定のシンボルに関連付けられているという前提に基づいています。
*   **`file` 引数の削除とエラーメッセージの変更**:
    *   `file string` 引数が削除され、それに伴いエラーメッセージも `log.Fatalf("%s: mangled input file", file)` から `log.Fatalf("savedata: bad off=%d siz=%d", off, siz)` へと変更されました。これにより、エラーメッセージがより具体的になり、問題の原因特定に役立つ情報（オフセットとサイズ）を提供するようになりました。
*   **`Enforce_data_order` チェックの削除**:
    *   `ctxt.Enforce_data_order` フィールドを参照していた以下のコードブロックが削除されました。
        ```go
        if ctxt.Enforce_data_order != 0 && off < int32(len(s.P)) {
            ctxt.Diag("data out of order (already have %d)\n%v", len(s.P), p)
        }
        ```
    *   この削除は、データセクションの順序に関する特定の制約が、もはやコンパイラのロジックで必要とされていないことを明確に示しています。これにより、コンパイラの内部ロジックが簡素化され、不要なオーバーヘッドが削減されます。

### `Link` 構造体からの `Enforce_data_order` フィールドの削除

*   `Link` 構造体は、コンパイルおよびリンクプロセス全体の状態を管理するための中心的なコンテキストです。この構造体から `Enforce_data_order int32` フィールドが削除されたことは、このフィールドがコンパイラのどの部分でも使用されなくなったことを意味します。デッドコードの削除は、コードベースをクリーンに保ち、将来のメンテナンスを容易にする上で重要です。

### `flushplist` 関数内の `savedata` 呼び出しの更新

*   `src/cmd/internal/obj/objfile.go` の `flushplist` 関数は、プログラム命令のリスト (`Plist`) をフラッシュ（処理）する役割を担っています。
*   `ADATA` 命令（データセクションへの書き込みを指示する命令）を処理する際に `savedata` が呼び出されますが、その呼び出しが新しいシグネチャに合わせて `savedata(ctxt, p)` に変更されました。これは、`savedata` 関数のインターフェース変更に直接対応する修正であり、コンパイラの整合性を保つために必要です。

これらの変更は、Goコンパイラの内部構造をより効率的かつ保守しやすいものにするための、細部にわたる継続的な改善の一例です。

# [インデックス 28160] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) がPosition-Independent Executable (PIE) モードで実行可能ファイルをビルドする際に、ホストリンカに対して `-Wl,-z,relro` フラグを渡すように変更するものです。これにより、生成される実行可能ファイルのセキュリティが強化され、特に再配置情報を含むセクションが読み取り専用として保護されるようになります。

## 変更の背景

この変更は、GoでビルドされたPosition-Independent Executable (PIE) のセキュリティを強化することを目的としています。コミットメッセージに「Fixes #15485」とあることから、この変更は特定のセキュリティ問題またはセキュリティ強化の要望に対応するものであることがわかります。

PIEは、Address Space Layout Randomization (ASLR) と組み合わせて使用されることで、実行可能ファイルがメモリ上のランダムなアドレスにロードされることを可能にし、攻撃者が特定のコードやデータのメモリ上の位置を予測することを困難にします。しかし、PIEであっても、プログラムのロード時に行われる再配置（relocation）情報を含むセクション（特にGlobal Offset Table (GOT) など）が、実行時にも書き込み可能である場合、攻撃者はこれらのセクションを改ざんして悪意のあるコードを実行する「GOTハイジャック」などの攻撃を仕掛ける可能性があります。

このコミットは、ホストリンカに `-Wl,-z,relro` フラグを渡すことで、これらの再配置情報を含むセクションを読み取り専用 (Read-Only) に設定し、実行時における改ざんを防ぐことを目的としています。これにより、GoでビルドされたPIE実行可能ファイルの堅牢性が向上し、より安全なソフトウェアが提供されるようになります。

## 前提知識の解説

### Goリンカ (`cmd/link`)

`cmd/link` は、Go言語のツールチェーンの一部であり、Goプログラムのコンパイルプロセスにおいて重要な役割を果たすリンカです。Goのソースコードはまずコンパイラによってオブジェクトファイルに変換され、その後 `cmd/link` がこれらのオブジェクトファイルと必要なライブラリを結合して、最終的な実行可能ファイルや共有ライブラリを生成します。Goのリンカは、クロスコンパイルのサポートや、Goランタイムの特定の要件を満たすための独自の機能を持っています。

### Position-Independent Executable (PIE)

PIE (Position-Independent Executable) は、実行時にメモリ上の任意のアドレスにロードできる実行可能ファイル形式です。通常の実行可能ファイルは、特定の固定されたメモリ位置にロードされることを前提としていますが、PIEはコードが絶対アドレスではなく相対アドレスで記述されているため、どこにロードされても正しく実行できます。

PIEは、主にASLR (Address Space Layout Randomization) と組み合わせて使用されます。ASLRは、プログラムのコード、データ、ヒープ、スタックなどのメモリ領域をランダムなアドレスに配置するオペレーティングシステムのセキュリティ機能です。PIEとASLRを組み合わせることで、攻撃者がメモリ上の特定のコードやデータを正確に指し示すことを困難にし、バッファオーバーフローなどのメモリ関連の脆弱性を悪用した攻撃からの保護を強化します。

### `-Wl` オプション

`-Wl` は、GCCやClangなどのコンパイラドライバ（コンパイラ、アセンブラ、リンカなどを呼び出すプログラム）で使用されるオプションです。このオプションは、後続の引数をリンカに直接渡すことを指示します。例えば、`-Wl,option` と記述すると、`option` がリンカに渡されます。これにより、コンパイラドライバが通常は認識しないリンカ固有のオプションを指定することができます。

### RELRO (Relocation Read-Only)

RELRO (Relocation Read-Only) は、実行可能ファイルのセキュリティを強化するためのメカニズムの一つです。プログラムがロードされ、動的リンカによって再配置（relocation）が完了した後、特定のメモリセクションを読み取り専用に設定します。

特に重要なのは、Global Offset Table (GOT) と Procedure Linkage Table (PLT) の一部です。GOTは、共有ライブラリ内の関数へのポインタを格納するテーブルであり、PLTはGOTを介して共有ライブラリ関数を呼び出すためのコードです。攻撃者がGOTを書き換えることができれば、正当な関数呼び出しを悪意のあるコードにリダイレクトする「GOTハイジャック」などの攻撃が可能になります。

RELROには主に2つのレベルがあります。
1.  **Partial RELRO**: GOTの一部のみを読み取り専用にします。
2.  **Full RELRO** (`-z,relro`): GOT全体を読み取り専用にし、さらに動的セクション（`.dynamic`, `.got`, `.got.plt` など）を読み取り専用にします。これにより、起動時のオーバーヘッドはわずかに増加しますが、セキュリティは最大限に強化されます。

`-z,relro` フラグは、リンカに対してFull RELROを有効にするよう指示します。

### ASLR (Address Space Layout Randomization)

ASLR (Address Space Layout Randomization) は、オペレーティングシステムが、実行可能ファイルのコード、データ、ヒープ、スタックなどのメモリ領域をランダムなアドレスに配置するセキュリティ技術です。これにより、攻撃者が特定のメモリ位置を予測して攻撃を仕掛けることを困難にします。PIEはASLRを効果的に機能させるための前提条件となります。PIEがなければ、実行可能ファイルは常に同じベースアドレスにロードされるため、ASLRの効果が限定的になります。

## 技術的詳細

このコミットは、Goのリンカ (`src/cmd/link/internal/ld/lib.go` 内の `hostlink` 関数) が、`-buildmode=PIE` オプションでビルドされる際に、ホストリンカに渡す引数に `-Wl,-z,relro` を追加するように変更します。

以前のGoのビルドシステムでは、PIEモードでビルドする際には `-pie` フラグのみがホストリンカに渡されていました。これにより、実行可能ファイルは位置独立となり、ASLRの恩恵を受けることができましたが、RELROによる追加のセキュリティ強化は適用されていませんでした。つまり、再配置が完了した後もGOTなどの重要なセクションが書き込み可能なままである可能性があり、セキュリティ上のリスクが残されていました。

この変更により、`BuildmodePIE` のケースにおいて、`UseRelro()` 関数が `true` を返す場合（これは通常、デフォルトで有効になっています）、`-Wl,-z,relro` フラグがホストリンカのコマンドライン引数に追加されます。このフラグは、リンカに対してFull RELROを有効にするよう指示し、プログラムのロード時に再配置が完了した後、GOTなどの動的セクションを読み取り専用としてマークさせます。

結果として、GoでビルドされたPIE実行可能ファイルは、ASLRに加えてRELROによる保護も受けることになり、攻撃者がメモリ上の脆弱性を悪用して重要なデータ構造を改ざんする攻撃（例: GOTハイジャック）に対する耐性が大幅に向上します。これは、Goアプリケーションの全体的なセキュリティ体制を強化する重要な改善です。

## コアとなるコードの解説

変更は `src/cmd/link/internal/ld/lib.go` ファイル内の `hostlink()` 関数にあります。この関数は、Goのリンカが最終的な実行可能ファイルを生成するために、外部のホストリンカ（通常はシステムにインストールされているGCCやClangのリンカ）を呼び出す際に使用されるコマンドライン引数を構築する役割を担っています。

変更箇所は `switch HEADTYPE` 文の `case BuildmodePIE:` ブロック内です。

```go
case BuildmodePIE:
    if UseRelro() {
        argv = append(argv, "-Wl,-z,relro")
    }
    argv = append(argv, "-pie")
```

1.  **`case BuildmodePIE:`**: このブロックは、GoプログラムがPosition-Independent Executable (PIE) としてビルドされる場合に実行されます。PIEは、ASLRを最大限に活用するために必要です。
2.  **`if UseRelro() { ... }`**:
    *   `UseRelro()` は、RELRO (Relocation Read-Only) を有効にするべきかどうかを判断する内部関数です。この関数は、リンカがRELROをサポートしている環境であるか、またはRELROを無効にするような明示的な設定がない限り、通常は `true` を返します。
    *   `UseRelro()` が `true` を返す場合、以下の行が実行されます。
3.  **`argv = append(argv, "-Wl,-z,relro")`**:
    *   `argv` は、ホストリンカに渡されるコマンドライン引数のスライス（Goのスライスは動的配列のようなもの）です。
    *   この行は、引数リストに `"-Wl,-z,relro"` を追加します。
        *   `-Wl`: これはコンパイラドライバに対する指示で、後続の引数（この場合は `-z,relro`）をリンカに直接渡すことを意味します。
        *   `-z,relro`: これはリンカに対する指示で、Full RELROを有効にするよう指定します。これにより、実行可能ファイルの再配置情報を含むセクションが読み取り専用としてマークされ、セキュリティが強化されます。
4.  **`argv = append(argv, "-pie")`**:
    *   この行は、既存の `-pie` フラグも引き続き引数リストに追加します。これは、実行可能ファイルが位置独立であることを保証し、ASLRの恩恵を受けられるようにするために不可欠です。

この変更により、GoのPIEビルドはデフォルトでRELROによるセキュリティ強化が適用されるようになり、生成される実行可能ファイルは、メモリ改ざん攻撃に対してより堅牢になります。

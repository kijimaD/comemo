## 元コミット内容

このコミットが元に戻しているのは、CL 159990043（コミットハッシュ: 421fadcef39a）です。そのコミットの目的は「runtime: make pprof a little nicer」（pprofを少し改善する）というものでした。これはIssue 8942に関連しており、プロファイルがより有用になるように改善を試みたものです。具体的には、`runtime·sigprof`関数内で、`g0`（スケジューラが使用する特別なゴルーチン）から現在のゴルーチン（`mp->curg`）へのスタックトレースの切り替えを試み、より正確なプロファイル情報を取得しようとしていました。

## 変更の背景

元となるCL 159990043は、Goのプロファイリングツールである`pprof`の出力を改善することを目的としていました。しかし、この変更がWindows環境で予期せぬ問題を引き起こしたとDmitriy氏（おそらくDmitriy Vyukov氏）が指摘しました。ビルドシステム（build.golang.org）のログでは、この変更が適用される前に問題が発生していたようにも見えましたが、念のためこの変更を元に戻すことが決定されました。これは、特定のプラットフォーム（この場合はWindows）におけるランタイムの挙動の複雑さ、特にシグナルハンドリングやスタックトレースの取得メカニズムが、プラットフォーム間で異なることによって生じる互換性の問題を示唆しています。

## 前提知識の解説

### Go Runtime (Goランタイム)

Goランタイムは、Goプログラムの実行を管理するシステムです。これには、ガベージコレクション、スケジューラ（ゴルーチンの管理）、メモリ割り当て、プリミティブな同期メカニズムなどが含まれます。Goプログラムは、OSの機能に直接依存する部分を除き、ほとんどがGoランタイムによって抽象化されています。

### pprof

`pprof`は、Goプログラムのプロファイリングデータを視覚化するためのツールです。CPU使用率、メモリ割り当て、ブロックされたゴルーチン、ミューテックス競合など、様々な種類のプロファイル情報を収集し、グラフやテキスト形式で表示できます。開発者は`pprof`を使用して、プログラムのパフォーマンスボトルネックを特定し、最適化を行うことができます。`pprof`が収集するデータの一つに、プログラム実行中のスタックトレースがあります。

### `runtime·sigprof`

`runtime·sigprof`は、Goランタイム内でプロファイリングシグナル（通常は`SIGPROF`）を受信した際に呼び出される関数です。このシグナルは、OSによって定期的に（例えば、CPUプロファイリングのために100Hzで）プロセスに送信され、その時点でのプログラムの実行状態（特にスタックトレース）をサンプリングするために使用されます。この関数は、シグナルハンドラとして機能し、現在のプログラムカウンタ（`pc`）、スタックポインタ（`sp`）、リンクレジスタ（`lr`）などの情報を受け取り、それらを使ってスタックトレースを収集します。

### `runtime·gentraceback`

`runtime·gentraceback`は、与えられたプログラムカウンタ、スタックポインタ、リンクレジスタ、およびゴルーチン情報に基づいて、スタックトレースを生成するGoランタイムの内部関数です。プロファイリングやデバッグ、パニック発生時などに呼び出され、関数の呼び出し履歴を遡って記録します。

### `G` (Goroutine) と `M` (Machine)

Goのスケジューラは、`G`（Goroutine）、`M`（Machine）、`P`（Processor）という3つの主要な抽象化を使用します。
*   **`G` (Goroutine)**: Goにおける軽量な実行スレッドです。Goプログラムの並行処理の単位となります。
*   **`M` (Machine)**: OSのスレッド（カーネルスレッド）を表します。Goランタイムは、`M`をOSに作成させ、その上でGoコードを実行します。
*   **`P` (Processor)**: 論理的なプロセッサを表し、`G`を実行するためのコンテキストを提供します。`M`は`P`にアタッチされ、`P`が持つ実行可能な`G`のキューから`G`を取り出して実行します。

### `g0` と `curg`

*   **`g0`**: 各`M`（OSスレッド）には、特別なゴルーチンである`g0`が関連付けられています。`g0`は、Goランタイムの内部処理（スケジューリング、ガベージコレクション、スタックの拡張など）を実行するために使用されるスタックを持っています。通常のGoコードは`g0`のスタックでは実行されません。
*   **`curg`**: `M`が現在実行しているユーザーゴルーチン（`G`）を指します。`g0`はランタイムの内部処理用であり、ユーザーコードは`curg`が指すゴルーチンで実行されます。

プロファイリングシグナルが`M`に到達した際、その`M`が`g0`上でランタイムコードを実行しているのか、それともユーザーゴルーチン（`curg`）を実行しているのかによって、スタックトレースの取得方法が変わる可能性があります。特にWindowsのようなOSでは、シグナルハンドリングのコンテキストがLinuxなどと異なる場合があり、`g0`と`curg`の切り替えが複雑な問題を引き起こすことがあります。

## 技術的詳細

このコミットは、`src/runtime/proc.c`ファイル内の`runtime·sigprof`関数に対する変更を元に戻しています。元に戻された変更は、プロファイリングシグナルが`g0`（ランタイムの内部処理用ゴルーチン）上で捕捉された場合に、実際に実行されていたユーザーゴルーチン（`mp->curg`）のスタックトレースを取得しようとするロジックでした。

具体的には、以下のコードが削除されました。

```c
-	int32 n, off;
+	int32 n;
...
-	off = 0;
-	if(gp == mp->g0 && mp->curg != nil) {
-		stk[0] = (uintptr)pc;
-		off = 1;
-		gp = mp->curg;
-		pc = (uint8*)gp->sched.pc;
-		sp = (uint8*)gp->sched.sp;
-		lr = 0;
-		traceback = true;
-	}
...
-	n = runtime·gentraceback((uintptr)pc, (uintptr)sp, (uintptr)lr, gp, 0, stk+off, nelem(stk)-off, nil, nil, false);
+	n = runtime·gentraceback((uintptr)pc, (uintptr)sp, (uintptr)lr, gp, 0, stk, nelem(stk), nil, nil, false);
```

この変更の意図は、`g0`上でプロファイリングシグナルがトリガーされた場合でも、その`g0`がユーザーゴルーチン`mp->curg`のコンテキストでランタイム処理を行っていたのであれば、ユーザーゴルーチンのスタックトレースを記録することで、より意味のあるプロファイルデータを得ることにありました。`stk[0] = (uintptr)pc; off = 1;` の部分は、`g0`のスタックフレームの先頭に現在の`pc`を記録し、その後に`curg`のスタックトレースを続けることで、`g0`から`curg`への遷移をプロファイルに含めようとしていたと考えられます。

しかし、このロジックがWindows環境で問題を引き起こしました。Windowsにおけるシグナルハンドリングやスレッドコンテキストの切り替えの挙動が、他のUnix系OSと異なるため、`g0`と`curg`間のスタック切り替えやコンテキストの解釈が正しく行われなかった可能性があります。特に、`gp->sched.pc`や`gp->sched.sp`といったスケジューラが保持するゴルーチンのコンテキスト情報が、シグナル発生時の実際のCPUレジスタの状態と一致しない、あるいはWindowsの特定のAPI呼び出しと競合するといった問題が考えられます。結果として、不正なスタックトレースが生成されたり、ランタイムがクラッシュしたりする原因となったと推測されます。

このコミットでは、この複雑なロジックを削除し、`runtime·gentraceback`を常に`stk`の先頭から呼び出すように戻すことで、Windowsでの安定性を優先しました。これは、プロファイリングの「nicer」な側面よりも、ランタイムの堅牢性が重要であるという判断に基づいています。

## コアとなるコードの解説

変更は`src/runtime/proc.c`ファイルの`runtime·sigprof`関数に集中しています。

1.  **`off`変数の削除**:
    `- int32 n, off;` が `+ int32 n;` に変更されています。これは、スタックトレースのオフセットを管理するために導入された`off`変数が不要になったことを示しています。

2.  **`g0`から`curg`へのスタック切り替えロジックの削除**:
    以下のブロックが完全に削除されました。
    ```c
    -	off = 0;
    -	if(gp == mp->g0 && mp->curg != nil) {
    -		stk[0] = (uintptr)pc;
    -		off = 1;
    -		gp = mp->curg;
    -		pc = (uint8*)gp->sched.pc;
    -		sp = (uint8*)gp->sched.sp;
    -		lr = 0;
    -		traceback = true;
    -	}
    ```
    このコードは、プロファイリングシグナルが`g0`（ランタイム内部ゴルーチン）上で発生し、かつ`mp->curg`（現在のユーザーゴルーチン）が存在する場合に、`g0`のスタックの先頭に現在の`pc`を記録し、その後`curg`のコンテキスト（`gp->sched.pc`, `gp->sched.sp`）に切り替えてスタックトレースを生成しようとしていました。これにより、`g0`がユーザーゴルーチンのために行っていたランタイム処理もプロファイルに含めることを意図していました。このロジックがWindowsで問題を引き起こしたため、削除されました。

3.  **`runtime·gentraceback`の呼び出しの簡素化**:
    `- n = runtime·gentraceback((uintptr)pc, (uintptr)sp, (uintptr)lr, gp, 0, stk+off, nelem(stk)-off, nil, nil, false);`
    が
    `+ n = runtime·gentraceback((uintptr)pc, (uintptr)sp, (uintptr)lr, gp, 0, stk, nelem(stk), nil, nil, false);`
    に変更されました。
    `off`変数の削除に伴い、`runtime·gentraceback`関数への`stk`引数が`stk+off`から`stk`に、`nelem(stk)-off`から`nelem(stk)`にそれぞれ変更されました。これは、スタックトレースの開始位置をオフセットするロジックが不要になり、常にスタックバッファの先頭からトレースを開始するように戻されたことを意味します。

これらの変更は、`pprof`のプロファイル精度を向上させる試みを元に戻し、特にWindows環境でのGoランタイムの安定性を優先した結果です。

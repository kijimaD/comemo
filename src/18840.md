# [インデックス 18840] ファイルの概要

このコミットは、Goランタイムにおける`efence`（Electric Fence）デバッグモードのサポートを改善し、特に可変長スタック（growable stacks）に関連するバグを修正するものです。主な目的は、`shrinkstack`関数がヒープにメモリを返してしまうことで発生する`growslice`の誤動作と、それに続くGC（ガベージコレクタ）のクラッシュを防ぐことにあります。また、スタックセグメントに対しても`efence`を有効にすることで、メモリ安全性のデバッグ能力を向上させています。

## 変更の背景

このコミットの背景には、Goランタイムのデバッグモードである`efence`を有効にした際に発生する深刻なメモリ破損バグがありました。具体的には、以下の問題が指摘されています。

1.  **`shrinkstack`によるメモリのヒープへの返却**: Goのgoroutineスタックは動的に伸縮しますが、スタックが縮小される際に`shrinkstack`関数が使用されます。この関数が、本来スタックとして管理されるべきメモリ領域を誤って汎用ヒープに返却してしまうバグがありました。
2.  **`growslice`の誤動作**: `growslice`はGoのスライスが容量不足になった際に、新しいより大きなバッキング配列を割り当て、既存の要素をコピーする関数です。`efence`モードでは、メモリの初期化が厳密に行われますが、`shrinkstack`がヒープに返却したメモリが、後に`growslice`によって再利用される可能性がありました。この際、`growslice`が手動でブロックを初期化するにもかかわらず、`shrinkstack`が解放したメモリが部分的に初期化された状態で`growslice`から出てくることが問題でした。
3.  **GCのクラッシュ**: 部分的に初期化されたメモリブロックがスライスとして使用されると、その内容が不定となります。Goのガベージコレクタは、メモリ上のポインタを追跡して到達可能なオブジェクトを特定しますが、不定なメモリ内容（特に`Eface`/`Iface`のようなインターフェース型）をポインタとして誤って解釈し、存在しないメモリ領域にアクセスしようとすることでクラッシュを引き起こしていました。

これらの問題は、`efence`モードというデバッグ環境下で顕在化するものでしたが、Goランタイムのメモリ管理の健全性に関わる重要なバグであり、その修正が求められていました。また、スタックセグメントに対しても`efence`を有効にすることで、スタック関連のメモリ問題の検出能力を高めることも目的とされました。

## 前提知識の解説

### Goの可変長スタック (Growable Stacks)

Goのgoroutineは非常に軽量であり、数百万ものgoroutineを同時に実行できることが特徴です。これを可能にしているのが、動的にサイズが変化する「可変長スタック」です。

*   **初期サイズ**: 各goroutineは非常に小さなスタック（Go 1.4時点では通常2KB）で開始します。
*   **スタックの成長**: 関数呼び出しが深くなり、現在のスタック領域が不足すると、Goランタイムは自動的にスタックを拡張します。Go 1.3以降では「連続スタック」方式が採用されており、新しいより大きなメモリブロックを割り当て、古いスタックの内容を新しい場所にコピーすることでスタックを成長させます。これにより、以前の「セグメントスタック」方式で問題となっていた「ホットスプリット問題」（頻繁なスタックセグメントの分割と解放によるオーバーヘッド）が解消されました。
*   **スタックの縮小 (`shrinkstack`)**: goroutineのスタック使用量が大幅に減少した場合（例えば、関数呼び出しが戻り、スタックフレームが解放された後）、ランタイムはメモリを節約するためにスタックサイズを縮小することがあります。この処理は`shrinkstack`関数によって行われます。

### `efence` (Electric Fence) デバッグモード

`efence`は、Goランタイムのメモリデバッグモードの一つで、`GODEBUG=efence=1`を設定することで有効になります。これはC/C++のElectric Fenceデバッガに似た挙動をします。

*   **ページ単位の割り当て**: `efence`モードでは、各メモリ割り当てが個別のメモリページに配置されます。
*   **アドレスの再利用なし**: 一度割り当てられたメモリページは、解放されてもすぐに再利用されません。
*   **目的**: バッファオーバーフロー（割り当てられたブロックの範囲外へのアクセス）やuse-after-free（解放されたメモリへのアクセス）といったメモリエラーを検出するために設計されています。各オブジェクトを個別のページに分離することで、境界外へのアクセスは即座にセグメンテーション違反（SIGSEGV）を引き起こし、問題の特定を容易にします。
*   **性能への影響**: `efence`モードはメモリ消費とパフォーマンスに大きな影響を与えるため、本番環境での使用には適していません。デバッグ用途に特化しています。

### `growslice`関数

`growslice`は、Goのスライスに要素を追加する際に、現在の容量が不足した場合に呼び出されるランタイム関数です。

*   **再割り当て**: スライスの`append`操作で容量が足りなくなった場合、`growslice`は新しいより大きなバッキング配列を割り当てます。
*   **コピー**: 古いバッキング配列の要素を新しい配列にコピーします。
*   **成長戦略**: 新しい容量は、スライスのサイズに応じて異なる戦略で決定されます（例えば、小さいスライスでは容量を2倍にする、大きいスライスでは1.25倍にするなど）。

### Goのガベージコレクタ (GC) とスタックメモリ

GoのGCは主にヒープメモリを管理しますが、スタックメモリとも密接に連携します。

*   **ルートオブジェクト**: GCは、グローバル変数やアクティブなスタックフレーム（現在のコールスタック上のローカル変数）を「ルートオブジェクト」として認識します。
*   **スタックスキャン**: GCは、マークフェーズ中にgoroutineのスタックをスキャンし、ヒープ上のオブジェクトへのポインタを識別します。これにより、スタック上の変数によって参照されているヒープ割り当てデータが「生きている」とマークされ、回収されないようにします。
*   **スタックの動的管理**: GCは、スタックの成長と縮小のプロセスを認識し、必要に応じてスタックを再スキャンします。

### `SysAlloc`, `SysFree`, `SysFault`

これらはGoランタイムがOSと直接やり取りするための低レベルなメモリ管理関数です。

*   **`SysAlloc`**: OSから生のメモリを要求するために使用されます。ヒープやスタックなどの内部データ構造のために、大きな連続した仮想アドレス空間を確保します。Unix系システムでは`mmap`のようなシステムコールに相当します。
*   **`SysFree`**: 不要になったメモリをOSに解放するために使用されます。GoのGCはGoヒープ内のメモリを再利用しますが、`SysFree`はより大きなメモリチャンクをOSに返却します。`munmap`や`madvise`（`DONTNEED`フラグ付き）のようなシステムコールに相当します。
*   **`SysFault`**: 低レベルのランタイムエラー、特にセグメンテーション違反（SIGSEGV）や無効なメモリアクセスを示すものです。プログラムがアクセスを許可されていないメモリ位置にアクセスしようとしたり、許可されていない方法でアクセスしようとしたりした場合に発生します。通常、Goプログラム内では回復不能なエラーであり、プログラムのクラッシュにつながります。

### `StackFromSystem`

`StackFromSystem`はGoランタイム内部の変数で、GoランタイムがgoroutineスタックをGoヒープからではなく、直接システムメモリから割り当てるべきかどうかを示します。この変数が`0`の場合、システムメモリからの割り当てを意味します。これは低レベルな実装の詳細であり、ユーザーが直接設定するオプションではありません。

## 技術的詳細

このコミットは、`src/pkg/runtime/stack.c`ファイル内のメモリ割り当てと解放のロジックを変更することで、`efence`モードでの問題を解決しています。

問題の核心は、`shrinkstack`がスタックメモリを解放する際に、`efence`モードが有効な場合でも、そのメモリが通常のヒープに返却されてしまうことにありました。これにより、`growslice`がその部分的に初期化されたメモリを再利用し、GCがその内容を誤って解釈してクラッシュするという連鎖的な問題が発生していました。

コミットの変更点は、`efence`モードが有効な場合、スタックの割り当てと解放、特に`shrinkstack`による解放が、通常のヒープ管理ではなく、`SysAlloc`/`SysFree`/`SysFault`といったシステムレベルのメモリ管理関数を介して行われるようにすることです。

具体的には、以下の変更が行われています。

1.  **`runtime·stackalloc`の変更**:
    スタックを割り当てる`runtime·stackalloc`関数において、`StackFromSystem`だけでなく、`runtime·debug.efence`が真の場合も`runtime·SysAlloc`を使用してシステムから直接メモリを割り当てるように変更されました。これにより、`efence`モードではスタックメモリがヒープとは独立して管理されるようになります。

    変更前:
    ```c
    if(StackFromSystem)
        return runtime·SysAlloc(ROUND(n, PageSize), &mstats.stacks_sys);
    ```
    変更後:
    ```c
    if(runtime·debug.efence || StackFromSystem)
        return runtime·SysAlloc(ROUND(n, PageSize), &mstats.stacks_sys);
    ```

2.  **`runtime·stackfree`の変更**:
    スタックを解放する`runtime·stackfree`関数においても、同様に`efence`モードが有効な場合は`runtime·SysFault`または`runtime·SysFree`を使用してシステムレベルでメモリを処理するように変更されました。これにより、`efence`モードで解放されたスタックメモリが誤ってヒープに混入することを防ぎます。

    変更前:
    ```c
    if(StackFromSystem) {
        if(StackFaultOnFree)
            runtime·SysFault(v, n);
        else
            runtime·SysFree(v, n, &mstats.stacks_sys);
    ```
    変更後:
    ```c
    if(runtime·debug.efence || StackFromSystem) {
        if(runtime·debug.efence || StackFaultOnFree)
            runtime·SysFault(v, n);
        else
            runtime·SysFree(v, n, &mstats.stacks_sys);
    ```

3.  **`runtime·shrinkstack`の変更**:
    スタックを縮小する`runtime·shrinkstack`関数が最も重要な変更点です。以前は、スタックの下半分を解放する際に、`malloc`（Goランタイムのヒープアロケータ）を騙して2つの半分のサイズの割り当てとして扱わせ、`free()`を呼び出すことでメモリを解放していました。しかし、`efence`モードではこの方法が問題を引き起こしていました。

    このコミットでは、`efence`モードまたは`StackFromSystem`が有効な場合、`shrinkstack`は直接`runtime·SysFault`または`runtime·SysFree`を呼び出して、システムレベルでメモリを解放するように変更されました。これにより、`shrinkstack`が解放したメモリが通常のヒープに返却されることがなくなり、`growslice`が部分的に初期化されたメモリを再利用する問題が根本的に解決されます。

    変更前:
    ```c
    // Free bottom half of the stack.  First, we trick malloc into thinking
    // we allocated the stack as two separate half-size allocs.  Then the
    // free() call does the rest of the work for us.
    if(oldsize == PageSize) {
    ```
    変更後:
    ```c
    // Free bottom half of the stack.
    if(runtime·debug.efence || StackFromSystem) {
        if(runtime·debug.efence || StackFaultOnFree)
            runtime·SysFault(oldstk, newsize);
        else
            runtime·SysFree(oldstk, newsize, &mstats.stacks_sys);
        return;
    }
    // First, we trick malloc into thinking
    // we allocated the stack as two separate half-size allocs.  Then the
    // free() call does the rest of the work for us.
    if(oldsize == PageSize) {
    ```
    この変更により、`efence`モードではスタックメモリの解放がより厳密に制御され、ヒープメモリとの混同が避けられるようになりました。

## コアとなるコードの解説

このコミットは、`src/pkg/runtime/stack.c`ファイル内の3つの主要な関数に変更を加えています。これらの変更は、`efence`デバッグモードが有効な場合に、Goランタイムがスタックメモリをどのように割り当て、解放、および縮小するかを制御することを目的としています。

1.  **`runtime·stackalloc`関数 (`+`104行目)**:
    *   **変更前**: `if(StackFromSystem)`という条件のみで、スタックメモリをシステムから直接割り当てるかどうかを判断していました。`StackFromSystem`は、スタックがGoランタイムのヒープではなく、OSから直接割り当てられるべきであることを示す内部フラグです。
    *   **変更後**: `if(runtime·debug.efence || StackFromSystem)`に変更されました。これは、`efence`デバッグモードが有効な場合（`runtime·debug.efence`が真の場合）も、スタックメモリを`runtime·SysAlloc`を使ってシステムから直接割り当てるように指示します。これにより、`efence`モードでのスタック割り当てが、通常のヒープ管理から分離され、より厳密なメモリ境界チェックが可能になります。

2.  **`runtime·stackfree`関数 (`+`145行目)**:
    *   **変更前**: `if(StackFromSystem)`という条件で、スタックメモリをシステムに解放する際の挙動を制御していました。`StackFaultOnFree`が真であれば`runtime·SysFault`を呼び出し、そうでなければ`runtime·SysFree`を呼び出していました。
    *   **変更後**: `if(runtime·debug.efence || StackFromSystem)`に変更され、さらに内部の`if`条件も`if(runtime·debug.efence || StackFaultOnFree)`に変更されました。これは、`efence`モードが有効な場合、スタックメモリの解放時にも`runtime·SysFault`（メモリへの不正アクセスを意図的に引き起こすデバッグ機能）または`runtime·SysFree`（システムへのメモリ解放）を強制的に使用することを意味します。これにより、`efence`モードで解放されたスタックメモリが、Goランタイムのヒープに誤って混入することを防ぎ、メモリ破損のリスクを低減します。

3.  **`runtime·shrinkstack`関数 (`+`822行目から`+`829行目)**:
    *   **変更前**: スタックの下半分を解放する際に、コメントにあるように「`malloc`を騙して2つの半分のサイズの割り当てとして扱わせ、`free()`を呼び出す」という手法を用いていました。これは、Goランタイムのヒープアロケータの内部的な挙動を利用したものでした。
    *   **変更後**: `if(runtime·debug.efence || StackFromSystem)`という新しい条件ブロックが追加されました。このブロック内では、`efence`モードまたは`StackFromSystem`が有効な場合、スタックの下半分を解放する際に、直接`runtime·SysFault`または`runtime·SysFree`を呼び出します。そして、`return;`で関数を終了します。
        この変更の最も重要な点は、`efence`モードが有効な場合に、スタックの縮小時にヒープアロケータの内部的なトリックを使用するのではなく、OSレベルのメモリ解放メカニズムを強制的に使用することです。これにより、`shrinkstack`が解放したメモリが通常のヒープに返却されることがなくなり、`growslice`が部分的に初期化されたメモリを再利用してGCクラッシュを引き起こすという、コミットメッセージで述べられているバグが根本的に解決されます。
        元の「`malloc`を騙す」ロジックは、`efence`モードや`StackFromSystem`が有効でない場合にのみ実行されるようになりました。

これらの変更により、`efence`デバッグモードの堅牢性が大幅に向上し、Goランタイムのメモリ管理における潜在的なバグの検出と防止に貢献しています。

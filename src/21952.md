# [インデックス 21952] ファイルの概要

このコミットは、Go言語のARMアーキテクチャ向けアセンブリソースコードを、新しいアセンブラの要件に合わせてより規則的な形式に編集するものです。具体的には、擬似レジスタの明示的なハードウェアレジスタへの置き換え、定数定義方法の統一、およびレジスタ参照の正規化が含まれます。

        - mentioning SP or PC as a hardware register

                they're not, and it's confusing because the context should not affect
                which register you mean. Change the references to the hardware
                registers to be explicit: R13 for SP, R15 for PC.
        - constant creation using assignment
                The files say a=b when they could instead say #define a b.
                There is no reason to have both mechanisms.
        - R(0) to refer to R0.
                Some macros use this to a great extent. Again, it's easy just to
                use a #define to rename a register.

## 変更の背景

このコミットの主な背景は、Go言語のARMアセンブリコードが、当時導入されつつあった「新しいアセンブラ」の要件に準拠していなかった点にあります。Go言語のアセンブラは、Plan 9アセンブラをベースにしており、GNU ARMアセンブリとは異なる独自の構文と規約を持っています。

古いアセンブリコードには、新しいアセンブラがサポートしないいくつかの特性がありました。これらは主に以下の3点に集約されます。

1.  **SP (スタックポインタ) および PC (プログラムカウンタ) の参照方法の曖昧さ**: Goアセンブラでは、`SP`と`PC`は通常「擬似レジスタ」として扱われます。これらは仮想的なスタックポインタやプログラムカウンタを指し、フレームローカル変数や関数呼び出しの引数へのアクセスに使用されます。しかし、特定のコンテキストではこれらがハードウェアレジスタを指すことがあり、その区別が不明瞭でした。新しいアセンブラでは、この曖昧さを排除し、ハードウェアレジスタを明示的に参照するよう求められました。
2.  **定数定義の不統一**: アセンブリファイル内で定数を定義する際に、`a=b`のような代入形式と、`#define a b`のようなプリプロセッサディレクティブ形式が混在していました。新しいアセンブラは、定数定義のメカニズムを統一することを推奨し、`#define`の使用を標準としました。
3.  **`R(0)`形式のレジスタ参照**: 一部のマクロで`R(0)`のようにレジスタを参照する形式が使用されていました。これは、レジスタをリネームするために`#define`を使用する方が、より明確で一貫性のある方法であると判断されました。

これらの不規則な記述は、アセンブラの解析を複雑にし、将来的な最適化や機能拡張の妨げとなる可能性がありました。そのため、コードの規則性を高め、新しいアセンブラとの互換性を確保するために、これらの変更が実施されました。

## 前提知識の解説

このコミットを理解するためには、Go言語のアセンブラ、特にARMアーキテクチャにおけるレジスタの扱いや定数定義の慣習に関する以下の知識が不可欠です。

### Go言語のアセンブラ (Plan 9アセンブラ)

Go言語は、独自のツールチェーンを使用しており、アセンブラも一般的なGNUアセンブラとは異なります。GoのアセンブラはPlan 9オペレーティングシステムのアセンブラをベースにしており、以下のような特徴があります。

*   **独自の構文**: 命令のオペランドの順序（ソースが左、デスティネーションが右）や、レジスタの表記方法などが異なります。
*   **擬似レジスタ**: Goアセンブラには、実際のハードウェアレジスタとは異なる「擬似レジスタ」の概念があります。

### ARMアーキテクチャにおけるレジスタ

ARMアーキテクチャには、汎用レジスタ（R0-R12）、スタックポインタ（SP）、リンクレジスタ（LR）、プログラムカウンタ（PC）などがあります。

*   **R0-R12**: 汎用レジスタ。
*   **R13 (SP)**: ハードウェアスタックポインタ。
*   **R14 (LR)**: リンクレジスタ。関数呼び出し時に戻りアドレスを保持します。
*   **R15 (PC)**: プログラムカウンタ。次に実行される命令のアドレスを保持します。

### GoアセンブラにおけるSPとPCの扱い

Goアセンブラでは、`SP`と`PC`は特別な意味を持ちます。

*   **`SP` (擬似レジスタ)**: Goアセンブラの`SP`は、仮想的なスタックポインタを指します。これは、関数内のローカル変数や引数にアクセスするために使用され、通常は`SYMBOL+offset(SP)`（例: `x-8(SP)`）のように、シンボルとオフセットを組み合わせて参照されます。これは、実際のハードウェアスタックポインタとは異なる概念です。
*   **`PC` (擬似レジスタ)**: 同様に、Goアセンブラの`PC`は、ジャンプや分岐命令で使用される擬似レジスタです。
*   **ハードウェアSP (`R13`) とハードウェアPC (`R15`)**: 実際のARMハードウェアレジスタとしてのスタックポインタは`R13`、プログラムカウンタは`R15`です。Goアセンブラでは、`offset(SP)`のようにシンボルなしで`SP`を参照する場合、それはハードウェア`SP`（`R13`）を指すことがあります。この曖昧さが問題でした。

### `#define` と代入による定数定義

*   **`#define`**: C言語のプリプロセッサディレクティブと同様に、Goアセンブラでも`#define`が使用されます。これはコンパイル時にテキスト置換を行うもので、シンボリック定数やマクロを定義するために使われます。Goのビルドプロセスでは、Goソースコードで定義された構造体のフィールドオフセットやサイズなどの定数が、`go_asm.h`というヘッダファイルに`#define`として生成され、アセンブリファイルからインクルードされることがあります。
*   **代入 (`a=b`)**: アセンブリコード内で`a=b`のような形式で定数を定義する慣習も存在しましたが、これは`#define`とは異なるメカニズムであり、統一性がありませんでした。

### `R(0)`形式のレジスタ参照

一部の古いアセンブリコードでは、`R(0)`のように括弧を使ってレジスタを参照するマクロが使われていました。これは、レジスタに別名を付けるためのものでしたが、`#define`を使って直接レジスタに名前を付ける方が、より直接的で分かりやすいと判断されました。

## 技術的詳細

このコミットで行われた技術的な変更は、Go言語のARMアセンブリコードの可読性、保守性、そして新しいアセンブラとの互換性を向上させることを目的としています。

### 1. `SP`または`PC`の明示的なハードウェアレジスタ (`R13`, `R15`) への置き換え

*   **問題点**: 従来のGo ARMアセンブリでは、`SP`や`PC`という表記が、文脈によってGoアセンブラの擬似レジスタを指す場合と、実際のARMハードウェアレジスタ（`R13`や`R15`）を指す場合がありました。この曖昧さは、コードの解釈を困難にし、特に新しいアセンブラがより厳密な規則を導入する際に問題となりました。
*   **解決策**: ハードウェアレジスタを指す場合は、`R13`（スタックポインタ）と`R15`（プログラムカウンタ）を明示的に使用するように変更されました。これにより、コードの意図が明確になり、アセンブラが正しく解釈できるようになります。
*   **例**:
    *   `MOVW SP, gobuf_sp(R0)` は `MOVW R13, gobuf_sp(R0)` に変更されました。これは、`gobuf_sp`に保存されるのが実際のスタックポインタの値であるため、ハードウェアレジスタ`R13`を明示的に使用することで、その意図を明確にしています。
    *   `MOVW $0xffff0fc0, PC` は `MOVW $0xffff0fc0, R15` に変更されました。これは、`PC`がプログラムカウンタのハードウェアレジスタを指すため、`R15`を明示的に使用しています。

### 2. 定数定義の`a=b`から`#define a b`への統一

*   **問題点**: アセンブリファイル内で定数を定義する際に、`table = 0`のような代入形式と、`#define`プリプロセッサディレクティブが混在していました。これは、定数定義のメカニズムが複数存在し、一貫性がありませんでした。
*   **解決策**: すべての定数定義を`#define`形式に統一しました。`#define`はコンパイル時にテキスト置換を行うため、アセンブリコードの実行には影響を与えず、コードの可読性と保守性を向上させます。
*   **例**:
    *   `table = 0` は `#define Rtable R0` に変更されました。
    *   `data = 1` は `#define Rdata R1` に変更されました。
    *   これにより、定数に`R`プレフィックスを付けることで、それがレジスタの別名であることを示し、コードの意図をさらに明確にしています。

### 3. `R(0)`形式のレジスタ参照の廃止と`#define`によるレジスタリネーム

*   **問題点**: 一部のマクロやコードで`R(0)`のように括弧を使ってレジスタを参照する形式が使用されていました。これは、レジスタに別名を付けるためのものでしたが、`#define`を使用する方がより直接的で分かりやすい方法です。
*   **解決策**: `R(X)`形式の参照を廃止し、代わりに`#define`を使用してレジスタに直接別名を付けるように変更されました。これにより、マクロの内部で`R(X)`を介さずに、直接定義されたレジスタ名を使用できるようになります。
*   **例**:
    *   `ROUND1(a, b, c, d, index, shift, const)` マクロ内の `R(c)` は `Rc` に変更されました。
    *   これは、`#define Ra R2` のように、あらかじめレジスタに別名が定義されているため、マクロ内でその別名を直接使用できるようになったことを意味します。

これらの変更は、Go言語のARMアセンブリコードベース全体にわたって適用され、コードの均一性と新しいアセンブラとの互換性を大幅に向上させました。

## コアとなるコードの変更箇所

このコミットでは、複数のアセンブリファイルにわたって広範な変更が行われています。ここでは、主要な変更タイプを示すために、`src/crypto/md5/md5block_arm.s` と `src/runtime/asm_arm.s` から具体的な変更箇所を抜粋して解説します。

### `src/crypto/md5/md5block_arm.s` における定数定義とマクロの変更

**変更前:**
```assembly
// Register definitions
table = 0	// Pointer to MD5 constants table
data = 1	// Pointer to data to hash
a = 2		// MD5 accumulator
b = 3		// MD5 accumulator
c = 4		// MD5 accumulator
d = 5		// MD5 accumulator
c0 = 6		// MD5 constant
c1 = 7		// MD5 constant
c2 = 8		// MD5 constant
// r9, r10 are forbidden
// r11 is OK provided you check the assembler that no synthetic instructions use it
c3 = 11		// MD5 constant
t0 = 12		// temporary
t1 = 14		// temporary

// ... (中略) ...

#define ROUND1(a, b, c, d, index, shift, const) \\\
	EOR	R(c), R(d), R(t0)		; \\\
	AND	R(b), R(t0)			; \\\
	EOR	R(d), R(t0)			; \\\
	MOVW	(index<<2)(R(data)), R(t1)	; \\\
	ADD	R(t1), R(t0)			; \\\
	ADD	R(const), R(t0)			; \\\
	ADD	R(t0), R(a)			; \\\
	ADD	R(a)@>(32-shift), R(b), R(a)	;
```

**変更後:**
```assembly
// Register definitions
#define Rtable	R0	// Pointer to MD5 constants table
#define Rdata	R1	// Pointer to data to hash
#define Ra	R2	// MD5 accumulator
#define Rb	R3	// MD5 accumulator
#define Rc	R4	// MD5 accumulator
#define Rd	R5	// MD5 accumulator
#define Rc0	R6	// MD5 constant
#define Rc1	R7	// MD5 constant
#define Rc2	R8	// MD5 constant
// r9, r10 are forbidden
// r11 is OK provided you check the assembler that no synthetic instructions use it
#define Rc3	R11	// MD5 constant
#define Rt0	R12	// temporary
#define Rt1	R14	// temporary

// ... (中略) ...

#define ROUND1(a, b, c, d, index, shift, Rconst) \\\
	EOR	Rc, Rd, Rt0		; \\\
	AND	Rb, Rt0			; \\\
	EOR	Rd, Rt0			; \\\
	MOVW	(index<<2)(Rdata), Rt1	; \\\
	ADD	Rt1, Rt0			; \\\
	ADD	Rconst, Rt0			; \\\
	ADD	Rt0, Ra			; \\\
	ADD	Ra@>(32-shift), Rb, Ra	;
```

### `src/runtime/asm_arm.s` における`SP`の`R13`への変更

**変更前:**
```assembly
TEXT runtime·gosave(SB),NOSPLIT,$-4-4
	MOVW	0(FP), R0		// gobuf
	MOVW	SP, gobuf_sp(R0)
	MOVW	LR, gobuf_pc(R0)
	MOVW	g, gobuf_g(R0)
	MOVW	$0, R11
```

**変更後:**
```assembly
TEXT runtime·gosave(SB),NOSPLIT,$-4-4
	MOVW	0(FP), R0		// gobuf
	MOVW	R13, gobuf_sp(R0)
	MOVW	LR, gobuf_pc(R0)
	MOVW	g, gobuf_g(R0)
	MOVW	$0, R11
```

## コアとなるコードの解説

### `src/crypto/md5/md5block_arm.s` の変更

このファイルはMD5ハッシュアルゴリズムのARMアセンブリ実装です。

*   **定数定義の変更**:
    *   変更前は `table = 0` のように、レジスタに割り当てる定数を直接代入形式で定義していました。
    *   変更後は `#define Rtable R0` のように、`#define`プリプロセッサディレクティブを使用して、レジスタにシンボリックな別名（`Rtable`, `Rdata`など）を割り当てています。これにより、コード内で`R0`, `R1`といった具体的なレジスタ番号ではなく、`Rtable`, `Rdata`といった意味のある名前でレジスタを参照できるようになり、可読性が向上します。また、`R`プレフィックスを付けることで、それがレジスタの別名であることが一目で分かります。
*   **マクロ内のレジスタ参照の変更**:
    *   `ROUND1`マクロの定義において、変更前は `R(c)`, `R(d)`, `R(t0)` のように、`R()`という形式でレジスタを参照していました。
    *   変更後は `Rc`, `Rd`, `Rt0` のように、`#define`で定義されたシンボリックなレジスタ名を直接使用しています。これにより、マクロの内部がより簡潔になり、`R()`という余分な間接参照がなくなりました。これは、新しいアセンブラが`R()`形式をサポートしない、または推奨しないためです。

### `src/runtime/asm_arm.s` の変更

このファイルはGoランタイムのARMアセンブリコードで、コンテキストスイッチやスタック管理などの低レベルな処理を扱います。

*   **`SP`から`R13`への変更**:
    *   `runtime·gosave`関数は、現在のゴルーチンの状態（スタックポインタ、プログラムカウンタなど）を`gobuf`構造体に保存する役割を担っています。
    *   変更前は `MOVW SP, gobuf_sp(R0)` と記述されており、`SP`がスタックポインタの値を`gobuf_sp`に保存していました。
    *   変更後は `MOVW R13, gobuf_sp(R0)` となっています。これは、`SP`がGoアセンブラの擬似レジスタとして使われる場合と、ハードウェアレジスタを指す場合があるという曖昧さを解消するためです。`gobuf_sp`に保存されるのは実際のハードウェアスタックポインタの値であるため、ARMのハードウェアスタックポインタレジスタである`R13`を明示的に使用することで、コードの意図が明確になり、新しいアセンブラが正しく解釈できるようになります。同様の変更が、`runtime·gogo`、`runtime·mcall`、`runtime·morestack`などの関数でも行われています。

これらの変更は、Go言語のARMアセンブリコードベース全体にわたって一貫性を保ち、新しいアセンブラの導入に伴う互換性の問題を解決するために不可欠でした。

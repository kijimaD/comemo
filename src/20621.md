# [インデックス 20621] ファイルの概要

このコミットは、Goランタイムの様々なアセンブリファイルおよび一部のCファイルにおいて、グローバルデータ宣言に`NOPTR`（No Pointers）フラグを明示的に追加するものです。この変更は、Goのガベージコレクタ（GC）が、これらのデータがGoのヒープ上のポインタを含まないことを正確に認識するために不可欠です。これにより、GCの効率と正確性が向上し、特にLinuxビルドにおける`_vdso`（virtual Dynamic Shared Object）関連の問題や、クロスコンパイル時の安定性が改善されます。

## 変更の背景

Goのガベージコレクタは、メモリ内のポインタを正確に識別し、到達可能なオブジェクトを追跡することで、不要なメモリを解放します。しかし、アセンブリコードや特定のCコードで宣言されたグローバルデータの中には、Goのヒープ上のポインタを含まないものがあります。これらのデータがポインタを含むと誤ってGCに認識されると、GCが不必要にスキャンを行ったり、最悪の場合、誤ったメモリを解放してクラッシュを引き起こす可能性があります。

このコミットの主な目的は、Goランタイムが使用する特定のグローバル変数がポインタを含まないことをGCに明示的に伝えることです。特に、Linuxの`_vdso` (virtual Dynamic Shared Object) に関連するビルド問題が言及されており、これはGoがシステムコールを最適化するために利用するカーネル提供のメモリ領域です。この領域はGoのヒープとは独立しており、GCの対象外であるべきです。

また、この変更はクロスコンパイルの問題を解決すると述べられています。異なるアーキテクチャやOS向けにGoプログラムをビルドする際に、ポインタの扱いに関する不整合が問題を引き起こしていた可能性があります。`NOPTR`を明示することで、GCの挙動がより予測可能になり、様々な環境でのビルドの安定性が向上します。

## 前提知識の解説

*   **Goのガベージコレクタ (GC)**: Goはトレース型ガベージコレクタを採用しており、プログラムが使用しているメモリ（到達可能なオブジェクト）を識別し、それ以外のメモリを自動的に解放します。GCはメモリ内のポインタを辿ることで到達可能性を判断します。
*   **ポインタと非ポインタデータ**: GoのGCは、メモリ領域がポインタを含むかどうかを知る必要があります。ポインタを含む可能性のあるデータはGCによってスキャンされますが、ポインタを含まないデータ（例: 整数、浮動小数点数、文字列のバイト列など）はスキャンする必要がありません。
*   **`GLOBL` ディレクティブとアセンブリにおけるデータ宣言**: Goのアセンブリ言語（Plan 9アセンブラの派生）では、`GLOBL` ディレクティブはグローバルシンボルを宣言するために使用されます。これにより、そのシンボルがプログラムの他の部分から参照可能になります。通常、`GLOBL`で宣言されたデータは、GCの対象となりうるため、GCはそれをスキャンする可能性があります。
*   **`NOPTR` フラグ**: `NOPTR`は"No Pointers"の略で、Goのアセンブリ言語やCgoで使用されるフラグです。このフラグがデータシンボルに付与されると、そのメモリ領域にはGoのヒープ上のポインタが含まれていないことをGCに明示的に伝えます。これにより、GCはその領域をスキャンする必要がなくなり、GCの効率が向上し、誤ったスキャンによるバグを防ぎます。`RODATA` (Read-Only Data) としてマークされたデータは、暗黙的に`NOPTR`と見なされます。
*   **`_vdso` (virtual Dynamic Shared Object)**: Linuxカーネルが提供するメカニズムで、ユーザー空間のプロセスに特定のカーネル関数（例: `gettimeofday`, `clock_gettime`）を直接呼び出せるように、共有ライブラリをメモリにマッピングします。これにより、システムコールによるモード切り替えのオーバーヘッドを回避し、パフォーマンスを向上させます。`_vdso`はカーネルによって管理されるメモリ領域であり、GoのGCの対象外であるべきです。
*   **クロスコンパイル**: あるプラットフォーム（OS/アーキテクチャ）で、別のプラットフォーム向けの実行可能ファイルをビルドすることです。Goは強力なクロスコンパイル機能を持ちますが、OSやアーキテクチャ固有のアセンブリコードやCコードが絡む場合、ポインタのサイズやアライメント、GCの挙動の違いが問題を引き起こすことがあります。

## 技術的詳細

このコミットの核心は、Goランタイムの様々な部分で宣言されているグローバルデータに対して、`NOPTR`フラグを明示的に追加することです。これにより、Goのガベージコレクタは、これらのデータがポインタを含まないことを認識し、スキャン対象から除外します。

具体的には、以下の種類のデータに`NOPTR`が適用されています。
1.  **`src/runtime/mem_plan9.c`**: C言語で書かれたPlan 9向けのメモリ管理コードで、`bloc`という静的変数に`#pragma dataflag NOPTR`が追加されています。これは、この変数がGoのヒープポインタを含まないことをCコンパイラ経由でGoツールチェインに伝えます。
2.  **`src/runtime/rt0_linux_386.s` などの`rt0_*.s`ファイル**: これらのファイルは、Goプログラムのエントリポイント（ランタイムの初期化コード）を含むアセンブリファイルです。`runtime·_vdso`や`runtime·isplan9`といったグローバル変数に`NOPTR`が追加されています。これらはOS固有のフラグや`_vdso`のアドレスなど、Goのヒープポインタではない値を保持するため、GCのスキャン対象から外す必要があります。
3.  **`src/runtime/sys_*.s`ファイル**: 各OS/アーキテクチャ固有のシステムコールや低レベル処理を扱うアセンブリファイルです。`runtime·tlsoffset`や`runtime·cbctxts`といった変数に`NOPTR`が追加されています。これらもGoのヒープポインタを含まない、システムレベルのオフセットやコンテキスト情報などを保持します。
4.  **`src/sync/atomic/asm_arm.s` および `src/sync/atomic/asm_linux_arm.s`**: アトミック操作を実装するアセンブリファイルです。`ok64`や`armCAS64`といった変数に`NOPTR`が追加されています。これらはアトミック操作の内部状態やヘルパー変数であり、Goのヒープポインタを含まないため、GCの対象外とされます。

これらの変更により、GCはこれらのグローバルデータを誤ってスキャンすることがなくなり、GCのオーバーヘッドが削減され、特にクロスコンパイル環境でのビルドの安定性と正確性が向上します。`_vdso`のようなOS固有のメモリ領域はGoのGCとは無関係であるため、`NOPTR`を付与することで、GCがその領域を不必要に参照しようとすることを防ぎ、Linuxビルドの問題を解決します。

## コアとなるコードの変更箇所

このコミットでは、主にGoランタイムの初期化、OS固有の処理、アトミック操作に関連するアセンブリファイルと一部のCファイルにおいて、グローバルデータ宣言に`NOPTR`フラグが追加されています。

**例1: `src/runtime/mem_plan9.c`**
```diff
--- a/src/runtime/mem_plan9.c
+++ b/src/runtime/mem_plan9.c
@@ -10,6 +10,7 @@
 #include "textflag.h"

 extern byte runtime·end[];
+#pragma dataflag NOPTR
 static byte *bloc = { runtime·end };
 static Mutex memlock;
 ```
`bloc`変数の宣言に`#pragma dataflag NOPTR`が追加されています。

**例2: `src/runtime/rt0_linux_386.s`**
```diff
--- a/src/runtime/rt0_linux_386.s
+++ b/src/runtime/rt0_linux_386.s
@@ -21,5 +21,5 @@ TEXT _fallback_vdso(SB),NOSPLIT,$0
 	RET

 DATA	runtime·_vdso(SB)/4, $_fallback_vdso(SB)
-GLOBL	runtime·_vdso(SB), $4
+GLOBL	runtime·_vdso(SB), NOPTR, $4
 ```
`runtime·_vdso`の`GLOBL`宣言に`NOPTR`が追加されています。

**例3: `src/runtime/rt0_linux_arm.s`**
```diff
--- a/src/runtime/rt0_linux_arm.s
+++ b/src/runtime/rt0_linux_arm.s
@@ -77,7 +77,7 @@ DATA bad_abi_msg+0x18(SB)/8, $" run on "
 DATA bad_abi_msg+0x20(SB)/8, $"EABI ker"
 DATA bad_abi_msg+0x28(SB)/4, $"nels"
 DATA bad_abi_msg+0x2c(SB)/1, $0xa
-GLOBL bad_abi_msg(SB), $45
+GLOBL bad_abi_msg(SB), RODATA, $45
 ```
`bad_abi_msg`の`GLOBL`宣言に`RODATA`が追加されています。`RODATA`は暗黙的に`NOPTR`を意味します。

**例4: `src/runtime/rt0_plan9_386.s`**
```diff
--- a/src/runtime/rt0_plan9_386.s
+++ b/src/runtime/rt0_plan9_386.s
@@ -17,7 +17,7 @@ TEXT _rt0_386_plan9(SB),NOSPLIT,$12
 	CALL	runtime·rt0_go(SB)

 DATA  runtime·isplan9(SB)/4, $1
-GLOBL runtime·isplan9(SB), $4
-GLOBL _tos(SB), $4

+GLOBL runtime·isplan9(SB), NOPTR, $4
+GLOBL _tos(SB), NOPTR, $4
+GLOBL _privates(SB), NOPTR, $4
+GLOBL _nprivates(SB), NOPTR, $4
```
複数の`GLOBL`宣言に`NOPTR`が追加されています。

## コアとなるコードの解説

これらの変更は、Goのガベージコレクタが、これらのグローバル変数をポインタを含むものとして誤って解釈するのを防ぐことを目的としています。

*   `#pragma dataflag NOPTR` (Cファイル): Cコードで宣言された静的変数`bloc`は、Goのランタイムが使用するメモリブロックの開始点を示しています。この変数はGoのヒープ上のポインタを直接保持するわけではないため、GCがスキャンする必要はありません。このプラグマを追加することで、Cコンパイラが生成するシンボル情報に`NOPTR`属性が付与され、Goのツールチェインがそれを認識できるようになります。

*   `GLOBL ... NOPTR` (アセンブリファイル):
    *   `runtime·_vdso`: Linuxの`_vdso`は、カーネルが提供する関数へのエントリポイントを含むメモリ領域です。これはGoのヒープとは独立しており、GCが管理する対象ではありません。`NOPTR`を付与することで、GCがこのシンボルをポインタとして扱い、不必要なスキャンや誤った参照を行うことを防ぎます。これにより、Linuxビルドにおける`_vdso`関連の問題が解決されます。
    *   `runtime·isplan9`, `_tos`, `_privates`, `_nprivates` (Plan 9): これらはPlan 9 OS固有のランタイム情報やスレッドローカルストレージに関連する変数です。これらもGoのヒープポインタを含まないため、`NOPTR`が適切です。
    *   `runtime·tlsoffset` (DragonFly BSD, FreeBSD, NetBSD, OpenBSD): スレッドローカルストレージのオフセットを示す変数で、ポインタではありません。
    *   `runtime·cbctxts` (Windows): コールバックコンテキストに関連する変数で、ポインタではありません。
    *   `ok64`, `armCAS64` (アトミック操作): アトミック操作の内部で使用されるヘルパー変数で、Goのヒープポインタを含みません。

*   `GLOBL ... RODATA` (アセンブリファイル):
    *   `bad_abi_msg` (Linux ARM): エラーメッセージの文字列データです。文字列リテラルは読み取り専用データであり、Goのヒープポインタを含みません。`RODATA`は"Read-Only Data"を意味し、暗黙的に`NOPTR`の特性を持ちます。これにより、GCはこのメッセージデータをスキャンする必要がなくなります。

これらの変更は、Goのガベージコレクタの正確性と効率性を向上させ、特に低レベルのランタイムコードやOS固有のインターフェースにおいて、ポインタではないデータをGCが誤って処理することを防ぎます。結果として、様々なプラットフォームでのGoのビルド、特にクロスコンパイルの信頼性が高まります。

# [インデックス 24089] ファイルの概要

このコミットは、Go言語の標準ライブラリである `net/http` パッケージにおける、HTTPリクエストスマグリング防御策の一部を緩和するものです。具体的には、`Transfer-Encoding` ヘッダと不正な `Content-Length` ヘッダが同時に存在するHTTPリクエストに対して、以前は厳格にエラーとして処理していた動作を改め、`Content-Length` ヘッダを無視する（削除する）ように変更しています。これにより、実世界のHTTPリクエストで発生しうる、RFCの規定とは異なるが一般的なケースに対応し、過度な厳格さによるサービス停止を防ぐことを目的としています。

## 変更の背景

この変更の背景には、以前導入されたHTTPリクエストスマグリングに対する防御策が、実世界のHTTPトラフィックにおいて過度に厳格であったという問題があります。

具体的には、`https://golang.org/cl/11810` で導入された変更により、`Transfer-Encoding` ヘッダと `Content-Length` ヘッダが同時に存在するHTTPリクエスト（特に、`Content-Length` が不正な値である場合）を `400 Bad Request` エラーとして処理するようになりました。これは、HTTPリクエストスマグリング攻撃を防ぐためのセキュリティ強化策の一環でした。

しかし、この厳格な処理が、一部の正当な（しかしRFCに厳密には準拠していない）HTTPリクエストを誤ってエラーとして扱ってしまうことが判明しました。コミットメッセージによると、「実世界のHTTPリクエストの中には、`Transfer-Encoding` と共に不正な `Content-Length` を含むものがある」とのことです。このようなリクエストをエラーとして拒否することは、互換性の問題やサービス停止を引き起こす可能性がありました。

そのため、このコミットでは、過度に厳格であった防御策の一部を元に戻し、`Transfer-Encoding` が存在する場合は `Content-Length` を無視するという、以前の挙動に戻すことで、実世界の多様なHTTPトラフィックへの対応とセキュリティのバランスを取ることを目指しています。

## 前提知識の解説

### HTTP/1.1におけるメッセージボディの長さの決定

HTTP/1.1では、メッセージボディの長さを決定する方法が主に2つあります。

1.  **Content-Length ヘッダ**: メッセージボディのオクテット単位の長さを数値で示します。このヘッダが存在する場合、受信側はこの値に基づいてボディの読み込みを停止します。
2.  **Transfer-Encoding ヘッダ (特に `chunked`)**: メッセージボディがチャンク（塊）に分割されて送信されることを示します。各チャンクは自身の長さ情報を含み、ボディの終端は長さ0のチャンクで示されます。この方式は、メッセージボディの全長が事前に分からない場合に特に有用です。

RFC 7230 (HTTP/1.1 Message Syntax and Routing) のセクション 3.3.3 "Message Body Length" では、これらのヘッダが同時に存在する場合の優先順位について明確に規定されています。

> If a message is received with both a Transfer-Encoding and a Content-Length header field, the Transfer-Encoding overrides the Content-Length. Such a message might indicate an attempt to perform request smuggling (Section 9.5) or response splitting (Section 9.4) and ought to be handled as an error. A sender MUST remove the received Content-Length field prior to forwarding such a message downstream.

この規定は、「`Transfer-Encoding` と `Content-Length` が両方存在するメッセージを受信した場合、`Transfer-Encoding` が `Content-Length` を上書きする。このようなメッセージはリクエストスマグリングの試みを示す可能性があり、エラーとして処理されるべきである。送信者は、そのようなメッセージをダウンストリームに転送する前に、受信した `Content-Length` フィールドを削除しなければならない。」と述べています。

### HTTPリクエストスマグリング (HTTP Request Smuggling)

HTTPリクエストスマグリングは、HTTP/1.1プロトコルの曖昧さや、プロキシサーバーとバックエンドサーバー間でのメッセージボディ長の解釈の違いを悪用する攻撃手法です。攻撃者は、`Content-Length` と `Transfer-Encoding` ヘッダを巧妙に組み合わせることで、プロキシとバックエンドでリクエストの境界認識をずらし、バックエンドサーバーが攻撃者の意図しないリクエストを処理するように仕向けます。

**攻撃のメカニズムの例**:

1.  攻撃者は、`Content-Length` と `Transfer-Encoding: chunked` の両方を含むリクエストを送信します。
2.  フロントエンドのプロキシサーバーが `Content-Length` を優先してリクエストを解析し、バックエンドに転送します。
3.  バックエンドサーバーが `Transfer-Encoding: chunked` を優先してリクエストを解析します。
4.  この解釈のずれにより、プロキシが1つのリクエストとして認識したものが、バックエンドでは2つのリクエストとして認識され、2つ目のリクエストが攻撃者の意図した不正なリクエストとして処理される可能性があります。これにより、認証回避、情報漏洩、キャッシュ汚染などの様々な攻撃が可能になります。

この攻撃を防ぐためには、RFCの規定に従い、`Transfer-Encoding` と `Content-Length` が同時に存在するリクエストを厳格に処理することが重要です。しかし、このコミットの背景にあるように、実世界のシステムではRFCに厳密に準拠していないリクエストも存在するため、実装者はセキュリティと互換性の間でバランスを取る必要があります。

## 技術的詳細

このコミットは、`net/http` パッケージがHTTPリクエストのヘッダを解析する際の挙動を変更しています。特に、`Transfer-Encoding` ヘッダが存在する場合の `Content-Length` ヘッダの扱いに関するロジックが修正されました。

以前の `https://golang.org/cl/11810` での変更では、HTTPリクエスト（`isRequest` が `true` の場合）において `Transfer-Encoding` と `Content-Length` が同時に存在すると、`"http: invalid Content-Length with Transfer-Encoding"` というエラーを返していました。これはRFC 7230の「エラーとして処理されるべき」という推奨事項に厳密に従ったもので、リクエストスマグリング攻撃に対する強力な防御策でした。

しかし、このコミットでは、その厳格なエラー処理を緩和しています。新しい挙動では、`Transfer-Encoding` が存在する場合、`Content-Length` ヘッダが同時に存在してもエラーを返さず、単に `Content-Length` ヘッダを削除する（無視する）ように変更されました。これは、RFC 7230の「送信者は、そのようなメッセージをダウンストリームに転送する前に、受信した `Content-Length` フィールドを削除しなければならない」という部分に焦点を当て、エラーとして処理するのではなく、`Content-Length` を無効化することで、`Transfer-Encoding` のみを有効にするというアプローチを取っています。

この変更は、実世界のHTTPクライアントやプロキシがRFCに厳密に準拠しないリクエストを送信する可能性があるという現実を考慮したものです。例えば、一部のクライアントは、`chunked` 転送エンコーディングを使用しているにもかかわらず、互換性のためや誤って `Content-Length` ヘッダを含めてしまうことがあります。以前の厳格な実装では、これらのリクエストがすべて `400 Bad Request` として拒否され、正当な通信が妨げられる可能性がありました。

このコミットによる変更は、セキュリティ上のリスクを完全に無視するものではなく、`Transfer-Encoding` が優先されるというRFCの主要な原則は維持しつつ、過度なエラー処理を避けることで、より堅牢な互換性を提供することを目的としています。`Content-Length` を削除することで、バックエンドサーバーが誤って `Content-Length` を解釈し、リクエストスマグリングを引き起こす可能性を低減しています。

## コアとなるコードの解説

`src/net/http/transfer.go` の `fixTransferEncoding` 関数は、HTTPメッセージの `Transfer-Encoding` ヘッダを処理し、メッセージボディの読み込み方法を決定する上で重要な役割を担っています。この関数は、`Transfer-Encoding` ヘッダが存在する場合に、その値に基づいて適切な `transferReader` を設定し、同時に `Content-Length` ヘッダの扱いを調整します。

変更前のコードでは、`Transfer-Encoding` が存在し、かつ `Content-Length` も存在する場合、特にそれがHTTPリクエスト (`isRequest` が `true`) であれば、RFC 7230の「エラーとして処理されるべき」という推奨に従い、明示的にエラーを返していました。これは、リクエストスマグリング攻撃を防ぐための厳格なセキュリティ対策でした。

しかし、このコミットでは、そのエラーを返すロジックが削除されました。代わりに、`Transfer-Encoding` が存在する場合は、`Content-Length` ヘッダを無条件に削除する `delete(header, "Content-Length")` という処理が導入されました。この変更は、RFC 7230の別の部分、すなわち「送信者は、そのようなメッセージをダウンストリームに転送する前に、受信した `Content-Length` フィールドを削除しなければならない」という指示に焦点を当てたものです。

この新しい挙動により、`net/http` パッケージは、`Transfer-Encoding` と `Content-Length` が同時に存在するリクエストを受信した場合でも、エラーとして拒否するのではなく、`Content-Length` を無視して `Transfer-Encoding` に従ってメッセージボディを解析するようになります。これにより、RFCに厳密には準拠しないが実世界で発生しうるリクエストに対しても、互換性を保ちつつ、`Content-Length` の誤用によるスマグリング攻撃のリスクを軽減することができます。

`src/net/http/readrequest_test.go` に追加された新しいテストケースは、この変更された挙動を検証するためのものです。このテストは、`Transfer-Encoding: chunked` と不正な `Content-Length` を持つリクエストが、エラーにならずに正常に解析され、`Content-Length` が `-1` (無視されたことを示す) として処理されることを確認します。これにより、コードの変更が意図した通りに機能していることが保証されます。

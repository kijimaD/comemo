# [インデックス 26009] ファイルの概要

このコミットは、Goコンパイラにおける最適化に関するもので、特に「キャプチャレスなクロージャ」を定数として扱うことで、バイナリサイズと起動コストを削減することを目的としています。

## コミット

Author: Keith Randall <khr@golang.org>
Date:   Thu Dec 3 13:20:58 2015 -0800

    cmd/compile: captureless closures are constants
    
    In particular, we can initialize globals with them at link time instead
    of generating code for them in an init() function. Less code, less
    startup cost.
    
    But the real reason for this change is binary size. This change reduces
    the binary size of hello world by ~4%.
    
    The culprit is fmt.ssFree, a global variable which is a sync.Pool of
    scratch scan states. It is initalized with a captureless closure as the
    pool's New action. That action in turn references all the scanf code.
    
    If you never call any of the fmt.Scanf* routines, ssFree is never used.
    But before this change, ssFree is still referenced by fmt's init
    function. That keeps ssFree and all the code it references in the
    binary. With this change, ssFree is initialized at link time. As a
    result, fmt.init never mentions ssFree. If you don't call fmt.Scanf*,
    ssFree is unreferenced and it and the scanf code are not included.
    
    This change is an easy fix for what is generally a much harder problem,
    the unnecessary initializing of unused globals (and retention of code
    that they reference). Ideally we should have separate init code for
    each global and only include that code if the corresponding global is
    live. (We'd need to make sure that the initializing code has no side
    effects, except on the global being initialized.) That is a much harder
    change.

## 元コミット内容

Goコンパイラは、キャプチャ（外部変数の参照）を持たないクロージャを定数として扱うように変更されました。これにより、これらのクロージャで初期化されるグローバル変数を、`init()`関数内でコードを生成する代わりに、リンク時に初期化できるようになります。結果として、生成されるコード量が減り、プログラムの起動コストが削減されます。

この変更の主な動機はバイナリサイズの削減であり、特に「Hello World」プログラムのバイナリサイズを約4%削減する効果がありました。

この最適化の具体的な例として、`fmt.ssFree`というグローバル変数が挙げられます。これは`sync.Pool`型で、その`New`アクションはキャプチャレスなクロージャで初期化されていました。このクロージャは`scanf`関連のコード全体を参照していました。

以前のバージョンでは、`fmt.init`関数が`ssFree`を参照していたため、たとえ`fmt.Scanf`系のルーチンが全く呼び出されなくても、`ssFree`とその参照する`scanf`コードはバイナリに含まれていました。今回の変更により、`ssFree`がリンク時に初期化されるようになったため、`fmt.init`は`ssFree`を参照しなくなりました。その結果、`fmt.Scanf`系の関数が呼び出されない場合、`ssFree`はどこからも参照されなくなり、`ssFree`と`scanf`コードはバイナリから除外されるようになりました。

この変更は、未使用のグローバル変数の不要な初期化（およびそれらが参照するコードの保持）という、より広範で難しい問題に対する比較的簡単な解決策です。理想的には、各グローバル変数に対して個別の初期化コードを持ち、そのグローバル変数が実際に使用される場合にのみそのコードを含めるべきですが、これはより複雑な変更が必要となります。

## 変更の背景

Go言語のプログラムは、静的リンクされるため、生成されるバイナリサイズが比較的大きくなる傾向があります。特に、標準ライブラリの多くの機能がリンクされるため、シンプルな「Hello World」のようなプログラムでも、他の言語に比べてバイナリサイズが大きくなりがちです。

このコミットの背景には、Goプログラムのバイナリサイズを削減したいという強い要望がありました。特に、`fmt`パッケージのような広く使われるパッケージが、その中の特定の機能（例: `Scanf`）が使われていない場合でも、関連するコードをバイナリに含んでしまうことが問題視されていました。これは、`sync.Pool`の`New`フィールドに設定されたクロージャが、そのクロージャが参照するコード全体を「生きている」と見なさせてしまうためでした。

Goのグローバル変数は、通常、パッケージの`init()`関数が実行される前に初期化されます。しかし、`init()`関数内で複雑な初期化ロジックを持つグローバル変数が存在すると、そのグローバル変数が実際に使用されるかどうかに関わらず、`init()`関数が実行されることで関連コードがバイナリに残り続けてしまいます。

このコミットは、キャプチャレスなクロージャという特定のケースに焦点を当てることで、この問題を部分的に解決し、デッドコードエリミネーション（不要なコードの削除）をより効果的に機能させることを目指しました。

## 前提知識の解説

### 1. Go言語のクロージャ (Closures)
Go言語におけるクロージャは、関数リテラル（匿名関数）の一種で、それが定義された環境（外部スコープ）の変数を「キャプチャ」して記憶し、その変数にアクセスできる機能を持つものです。
*   **キャプチャするクロージャ**: 外部スコープの変数を参照し、その変数の値を変更することもできます。これらの変数は、クロージャが外部関数の実行後も存在し続ける場合、ヒープに割り当てられることがあります。
*   **キャプチャレスなクロージャ**: 外部スコープの変数を一切参照しないクロージャです。自身の引数とローカル変数のみで動作します。本質的には、名前のない通常の関数と同じように振る舞います。このコミットでは、この「キャプチャレスなクロージャ」が最適化の対象となります。

### 2. Go言語のグローバル変数と初期化 (Global Variables and Initialization)
Go言語では、パッケージレベルで宣言された変数はグローバル変数として扱われます。これらの変数の初期化は、プログラムの実行開始前に行われます。
*   **初期化順序**:
    1.  パッケージレベルの変数が初期化されます。明示的な初期値が指定されていない場合、ゼロ値（数値型なら0、文字列型なら""、ポインタやスライスならnilなど）で初期化されます。
    2.  各パッケージの`init()`関数が実行されます。`init()`関数は、パッケージの初期設定や複雑な初期化ロジックを実行するために使用されます。
    3.  `main()`関数が実行され、プログラムが開始されます。
*   **リンク時初期化**: コンパイル・リンクの段階で、変数の初期値がバイナリに直接埋め込まれる初期化方法です。これにより、実行時の初期化コードが不要になり、起動速度の向上やコードサイズの削減に繋がります。

### 3. `sync.Pool`
`sync.Pool`は、Go言語の標準ライブラリ`sync`パッケージが提供する、一時的なオブジェクトの再利用を目的とした型です。頻繁に生成・破棄されるオブジェクト（例: バイトスライス、バッファ）をプールしておき、必要に応じて再利用することで、メモリ割り当てのオーバーヘッドとガベージコレクション（GC）の負荷を軽減します。
*   **`New`フィールド**: `sync.Pool`の`New`フィールドは、プールが空のときに`Get()`メソッドが呼び出された際に、新しいオブジェクトを生成するために実行される関数です。この`New`フィールドには、通常、オブジェクトを生成するクロージャが設定されます。

### 4. デッドコードエリミネーション (Dead Code Elimination, DCE)
デッドコードエリミネーションは、コンパイラ最適化の一種で、プログラムの実行に影響を与えない（到達不能な、または結果が使用されない）コードをバイナリから削除するプロセスです。これにより、バイナリサイズが削減され、実行速度が向上する可能性があります。Goコンパイラもこの最適化を自動的に行いますが、コードの参照関係によっては、実際には使われていないコードでも「生きている」と判断されてしまうことがあります。

## 技術的詳細

このコミットの核心は、Goコンパイラがキャプチャレスなクロージャをより効率的に扱う方法を変更した点にあります。

以前のGoコンパイラでは、クロージャはキャプチャの有無にかかわらず、実行時に生成されるコードとして扱われ、その初期化は`init()`関数などの実行時ロジックに依存していました。特に、グローバル変数として宣言された`sync.Pool`の`New`フィールドにキャプチャレスなクロージャが割り当てられている場合、そのクロージャは`init()`関数内で初期化される必要がありました。

この初期化プロセスは、`init()`関数がそのクロージャ（およびそれが参照する可能性のあるコード）を「生きている」と見なす原因となっていました。結果として、たとえそのグローバル変数やクロージャがプログラムの実行中に一度も使用されなくても、関連するコードが最終的なバイナリに含まれてしまい、バイナリサイズの肥大化を招いていました。

今回の変更では、コンパイラがキャプチャレスなクロージャを「定数」として認識できるようになりました。これにより、これらのクロージャは実行時のコード生成や`init()`関数による初期化を必要とせず、リンク時に直接バイナリに埋め込むことが可能になります。

具体的には、`src/cmd/compile/internal/gc/sinit.go`内の`staticassign`関数が修正され、`OCLOSURE`（クロージャ）ノードが処理される際に、そのクロージャがキャプチャ変数を持たない（`r.Func.Cvars == nil`）場合、そのクロージャをリンク時に初期化可能なグローバルデータとして扱うようになりました。これにより、`init()`関数がこのグローバル変数を参照する必要がなくなり、デッドコードエリミネーションがより効果的に機能するようになります。

この最適化は、特に`fmt.ssFree`のようなケースで顕著な効果を発揮します。`fmt.ssFree`は`sync.Pool`であり、その`New`フィールドは`scanf`関連のコードを参照するキャプチャレスなクロージャでした。変更前は`fmt.init`が`ssFree`を参照していたため、`scanf`が使われなくてもコードが残りました。変更後は、`ssFree`がリンク時に初期化されるため、`fmt.init`は`ssFree`を参照せず、`scanf`が使われない場合は関連コードがバイナリから削除されるようになりました。

## コアとなるコードの変更箇所

このコミットでは、主に以下の2つのファイルが変更されています。

1.  **`src/cmd/compile/internal/gc/global_test.go`**:
    *   `TestScanfRemoval`という新しいテスト関数が追加されました。このテストは、`fmt.Scanf`系のルーチンを呼び出さない「Hello World」プログラムをビルドし、そのバイナリに`scanInt`のような`scanf`関連のシンボルが含まれていないことを確認します。これは、このコミットの目的であるバイナリサイズ削減、特に未使用の`scanf`コードの削除が正しく機能しているかを検証するためのものです。

2.  **`src/cmd/compile/internal/gc/sinit.go`**:
    *   `staticassign`関数が変更されました。この関数は、グローバル変数の初期化をリンク時に行えるかどうかを判断し、そのための処理を行うGoコンパイラの内部関数です。
    *   特に、`switch r.Op`文の中に`case OCLOSURE:`という新しいケースが追加されました。
    *   この新しいケースでは、クロージャノード`r`がキャプチャ変数を持たない（`r.Func.Cvars == nil`）場合に、そのクロージャをリンク時に初期化可能なグローバルデータとして扱うロジックが追加されています。具体的には、`gdata(&n, r.Func.Closure.Func.Nname, Widthptr)`を呼び出すことで、クロージャの関数ポインタをグローバルデータとして設定します。
    *   これにより、キャプチャレスなクロージャで初期化されるグローバル変数は、`init()`関数を介さずに直接リンク時に初期化されるようになります。
    *   また、既存の`switch`文から不要な`default`ケースやコメントが削除され、コードが整理されています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/sinit.go` の変更点

`sinit.go`ファイルは、Goコンパイラのバックエンドの一部であり、主に静的初期化（リンク時初期化）に関連する処理を担当しています。`staticassign`関数は、特定のノード（変数や式）が静的に（つまりリンク時に）初期化可能かどうかを判断し、そのための処理を行う重要な関数です。

変更前の`staticassign`関数は、`OCLOSURE`（クロージャ）ノードを静的初期化の対象として明示的に扱っていませんでした。そのため、クロージャで初期化されるグローバル変数は、たとえキャプチャレスであっても、実行時の`init()`関数を通じて初期化される必要がありました。

変更後のコードでは、`staticassign`関数内の`switch r.Op`文に`case OCLOSURE:`が追加されました。

```go
	case OCLOSURE:
		if r.Func.Cvars == nil {
			// Closures with no captured variables are globals,
			// so the assignment can be done at link time.
			n := *l
			gdata(&n, r.Func.Closure.Func.Nname, Widthptr)
			return true
		}
```

このコードブロックの解説は以下の通りです。

1.  **`case OCLOSURE:`**: 現在処理しているノード`r`がクロージャ（`OCLOSURE`）であることを示します。
2.  **`if r.Func.Cvars == nil`**: ここがこの変更の肝となる条件です。`r.Func.Cvars`は、クロージャがキャプチャしている変数（Captured Variables）のリストを保持しています。このリストが`nil`であるということは、そのクロージャが外部スコープの変数を一切キャプチャしていない、すなわち「キャプチャレスなクロージャ」であることを意味します。
3.  **`// Closures with no captured variables are globals, // so the assignment can be done at link time.`**: コメントが示す通り、キャプチャレスなクロージャは実質的にグローバルな関数ポインタとして扱えるため、その初期化をリンク時に行うことが可能になります。
4.  **`n := *l`**: 代入先のノード`l`（グローバル変数）のコピーを作成します。
5.  **`gdata(&n, r.Func.Closure.Func.Nname, Widthptr)`**: この関数呼び出しが、リンク時初期化の具体的な処理を行います。
    *   `gdata`は、指定されたノード`n`（グローバル変数）に対して、`r.Func.Closure.Func.Nname`（クロージャが表す関数の名前）が指すアドレスを、ポインタの幅（`Widthptr`）でグローバルデータとして設定するようコンパイラに指示します。
    *   これにより、コンパイラは、このグローバル変数が実行時に`init()`関数で初期化されるのではなく、リンク時に直接、キャプチャレスなクロージャのコードへのポインタで初期化されるようにバイナリを生成します。
6.  **`return true`**: この代入が静的に処理されたことを`staticassign`関数の呼び出し元に通知します。

この変更により、Goコンパイラはキャプチャレスなクロージャをより効率的に扱い、不要な実行時初期化コードの生成を回避できるようになりました。

### `src/cmd/compile/internal/gc/global_test.go` の追加点

このファイルは、Goコンパイラの内部テストの一部として追加されました。`TestScanfRemoval`関数は、このコミットによる最適化が意図通りに機能していることを検証するための統合テストです。

```go
func TestScanfRemoval(t *testing.T) {
	testenv.MustHaveGoBuild(t)

	// Make a directory to work in.
	dir, err := ioutil.TempDir("", "issue6853a-")
	// ... (エラーハンドリング) ...
	defer os.RemoveAll(dir)

	// Create source.
	src := path.Join(dir, "test.go")
	f, err := os.Create(src)
	// ... (エラーハンドリング) ...
	f.Write([]byte(`
package main
import "fmt"
func main() {
	fmt.Println("hello world")
}
`))
	f.Close()

	// Name of destination.
	dst := path.Join(dir, "test")

	// Compile source.
	cmd := exec.Command("go", "build", "-o", dst, src)
	// ... (ビルド実行とエラーハンドリング) ...

	// Check destination to see if scanf code was included.
	cmd = exec.Command("go", "tool", "nm", dst)
	// ... (nm実行とエラーハンドリング) ...
	if bytes.Index(out, []byte("scanInt")) != -1 {
		log.Fatalf("scanf code not removed from helloworld")
	}
}
```

このテストの主要なステップは以下の通りです。

1.  **一時ディレクトリの作成**: テスト用の作業ディレクトリを作成します。
2.  **ソースファイルの生成**: `package main`と`import "fmt"`、そして`fmt.Println("hello world")`のみを含むシンプルなGoプログラム（「Hello World」）を生成します。重要なのは、`fmt.Scanf`系の関数は一切呼び出していない点です。
3.  **プログラムのコンパイル**: `go build`コマンドを使用して、生成したソースファイルをコンパイルし、実行可能バイナリを作成します。
4.  **シンボルテーブルの確認**: `go tool nm`コマンドを使用して、生成されたバイナリのシンボルテーブルをダンプします。`nm`コマンドは、オブジェクトファイルや実行可能ファイル内のシンボル（関数名、変数名など）をリスト表示するツールです。
5.  **`scanInt`シンボルの存在チェック**: `nm`の出力結果に`scanInt`という文字列（`scanf`関連の内部関数名）が含まれていないことを確認します。もし含まれていれば、それは`scanf`コードが不要にもかかわらずバイナリに残ってしまっていることを意味し、テストは失敗します。

このテストは、このコミットによる最適化（未使用の`scanf`コードのデッドコードエリミネーション）が正しく機能していることを、具体的な「Hello World」の例で検証するものです。

# [インデックス 23063] ファイルの概要

このコミットは、Go言語の標準ライブラリである`net/http`パッケージにおける、稀に発生する`Transport`の`readLoop`ゴルーチンリークを修正するものです。特に、HTTPキープアライブ接続の管理におけるタイミングの問題に起因するリークを解決しています。

## 元コミット内容

```
net/http: fix rare Transport readLoop goroutine leak

There used to be a small window where if a server declared it would do
a keep-alive connection but then actually closed the connection before
the roundTrip goroutine scheduled after being sent a response from the
readLoop goroutine, then the readLoop goroutine would loop around and
block forever reading from a channel because the numExpectedResponses
accounting was done too late.

Fixes #10457
```

## 変更の背景

このコミットは、Goの`net/http`パッケージにおいて、HTTPクライアントがサーバーとの間でキープアライブ接続を使用する際に発生しうる、稀なゴルーチンリークの問題を解決するために導入されました。

問題の核心は、`Transport`内部の`readLoop`ゴルーチンと`roundTrip`ゴルーチンの間の同期と、`numExpectedResponses`というカウンタの更新タイミングにありました。

具体的には、以下のようなシナリオでリークが発生する可能性がありました。

1.  サーバーがキープアライブ接続を維持すると宣言する。
2.  `readLoop`ゴルーチンがサーバーからのレスポンスを読み取り、`roundTrip`ゴルーチンに送信する。
3.  しかし、`readLoop`がレスポンスを送信した後、`roundTrip`ゴルーチンがスケジューリングされて処理を開始するまでの「ごく短い時間窓」の間に、サーバーが実際に接続を閉じてしまう。
4.  この状況下で、`readLoop`ゴルーチンは`numExpectedResponses`カウンタのデクリメント（減少）が遅れるため、次のレスポンスを期待してチャネルからの読み取りを永久にブロックしてしまう。結果として、この`readLoop`ゴルーチンは終了せず、リークとしてシステムリソースを消費し続けることになります。

この問題は、GoのIssue #10457として報告されていました。

## 前提知識の解説

このコミットの理解には、以下のGo言語およびHTTPプロトコルに関する知識が役立ちます。

### Go言語のゴルーチンとチャネル

*   **ゴルーチン (Goroutine)**: Go言語における軽量な並行実行単位です。OSのスレッドよりもはるかに少ないメモリで作成でき、数万から数十万のゴルーチンを同時に実行することが可能です。GoランタイムがこれらのゴルーチンをOSスレッドにマッピングし、スケジューリングを行います。
*   **チャネル (Channel)**: ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは、ゴルーチン間の同期と通信を安全に行うための主要な手段であり、Goの並行プログラミングの根幹をなします。チャネルからの読み取りは、データが利用可能になるまでブロックされることがあります。

### `net/http`パッケージとHTTPクライアント

*   **`net/http`パッケージ**: Go言語でHTTPクライアントおよびサーバーを実装するための標準ライブラリです。
*   **`http.Client`**: HTTPリクエストを送信し、レスポンスを受信する高レベルなインターフェースを提供します。通常、アプリケーション全体で単一の`http.Client`インスタンスを再利用することが推奨されます。
*   **`http.Transport`**: `http.Client`の内部で使用され、実際のHTTPリクエストの送信、レスポンスの受信、接続の管理（TCP接続の確立、キープアライブ、プロキシなど）を担当します。`Transport`は、複数のリクエスト間でTCP接続を再利用することでパフォーマンスを向上させます。
*   **`persistConn`**: `http.Transport`の内部構造体で、単一の永続的な（キープアライブ）HTTP接続を表します。この構造体は、その接続上での読み書きを処理するための専用のゴルーチン（`readLoop`と`writeLoop`）を管理します。
*   **`readLoop`ゴルーチン**: `persistConn`の一部として起動され、基となるTCP接続からサーバーレスポンスを継続的に読み取る役割を担います。読み取ったレスポンスは、適切な`roundTrip`ゴルーチンにチャネルを通じて送信されます。
*   **`roundTrip`ゴルーチン**: `http.Client`がリクエストを送信する際に起動されるゴルーチンで、`Transport`を通じてリクエストを送信し、`readLoop`からレスポンスを受け取ります。

### HTTPキープアライブ (Keep-Alive)

*   HTTP/1.1の標準機能で、複数のHTTPリクエスト/レスポンスのペアを単一のTCP接続上で送受信することを可能にします。これにより、各リクエストごとに新しいTCP接続を確立するオーバーヘッドが削減され、パフォーマンスが向上します。
*   サーバーはレスポンスヘッダーに`Connection: keep-alive`を含めることで、接続を維持する意図を示します。クライアントも同様にリクエストヘッダーでキープアライブを要求します。

### ゴルーチンリーク (Goroutine Leak)

*   ゴルーチンが予期せず終了せず、システムリソース（メモリ、ファイルディスクリプタなど）を消費し続ける状態を指します。これは、チャネルからの読み取りが永久にブロックされたり、無限ループに陥ったりすることで発生することがあります。ゴルーチンリークは、アプリケーションのメモリ使用量が増加し続けたり、パフォーマンスが低下したりする原因となります。`net/http`クライアントにおける一般的なゴルーチンリークの原因は、`http.Response.Body`を適切に閉じないことですが、このコミットで修正されたのは、より内部的なタイミングの問題です。

## 技術的詳細

このゴルーチンリークは、`persistConn`の`readLoop`メソッドと、その接続を使用する`roundTrip`メソッド間の相互作用における、`numExpectedResponses`というカウンタの管理の不備に起因していました。

`numExpectedResponses`は、特定の`persistConn`上で現在処理中である、または処理が期待されているレスポンスの数を追跡するためのカウンタです。このカウンタは、`roundTrip`ゴルーチンがリクエストを送信する際にインクリメントされ、`readLoop`ゴルーチンがレスポンスを読み取り終えた後にデクリメントされることが期待されていました。

問題のシナリオは以下の通りです。

1.  `roundTrip`ゴルーチンがリクエストを送信し、`pc.numExpectedResponses`をインクリメントします。
2.  `readLoop`ゴルーチンがサーバーからのレスポンスを正常に読み取ります。
3.  `readLoop`はレスポンスを読み取った後、`roundTrip`ゴルーチンにそのレスポンスをチャネル経由で送信します。
4.  **ここが問題の核心です。** 以前のコードでは、`readLoop`が`pc.numExpectedResponses`をデクリメントする処理が、レスポンスを`roundTrip`に送信した後、かつ`roundTrip`がそのレスポンスを受け取って処理を開始する「前」に、サーバーが接続を閉じてしまうという非常に稀なタイミングで発生していました。
5.  サーバーが接続を閉じたため、`readLoop`は次の読み取り操作でEOF（End Of File）を受け取ります。
6.  `readLoop`はEOFを受け取ると、接続が閉じられたと判断し、`pc.numExpectedResponses`が0になるのを待って終了しようとします。
7.  しかし、`numExpectedResponses`のデクリメントが遅れたため、`readLoop`はまだ処理中のレスポンスがあると誤解し、チャネルからの読み取りを永久にブロックしてしまいます。これは、`readLoop`が`numExpectedResponses`が0になるまでループを継続し、次のレスポンスを待つためです。しかし、接続は既に閉じられているため、次のレスポンスは決して来ず、ゴルーチンはハングアップします。

このコミットは、`readLoop`ゴルーチンがレスポンスを`roundTrip`ゴルーチンに送信する**直前**に`pc.numExpectedResponses`をデクリメントするように変更することで、このタイミングの問題を解決しました。これにより、`readLoop`がレスポンスの処理を完了したと見なすタイミングと、`numExpectedResponses`の会計処理がより密接に同期されるようになり、サーバーが接続を早期に閉じた場合でも、`readLoop`が正しく終了できるようになりました。

## コアとなるコードの解説

### `src/net/http/transport.go` の変更

*   **移動された`pc.numExpectedResponses--`**:
    *   変更前は、`pc.numExpectedResponses--`の処理が`WaitResponse`ラベルの後にありました。これは、`readLoop`がレスポンスを`roundTrip`ゴルーチンに送信し、さらにその`roundTrip`ゴルーチンがレスポンスの処理を終える（またはエラーが発生する）まで、このカウンタがデクリメントされない可能性があったことを意味します。
    *   変更後は、`readLoop`内のレスポンス処理ロジックの**直後**、具体的には`pc.readLoop()`関数内の`if re.err != nil { ... }`ブロックの直前、かつ`pc.lk.Lock()`と`pc.lk.Unlock()`で保護されたセクションに移動されました。
    *   この移動により、`readLoop`がレスポンスの読み取りと送信を完了した時点で、`numExpectedResponses`が即座にデクリメントされるようになりました。これにより、サーバーが接続を早期に閉じた場合でも、`readLoop`が`numExpectedResponses`の誤った値によって永久にブロックされることがなくなります。`readLoop`は、自身の責任範囲である「レスポンスの読み取りと送信」が完了した時点で、期待されるレスポンスの数を減らすことができるため、より正確な状態管理が可能になります。

### `src/net/http/transport_test.go` の変更

*   **`TestTransportIssue10457`の追加**:
    *   このテストは、まさにコミットが修正しようとしている稀なゴルーチンリークのシナリオを再現するために追加されました。
    *   `httptest.NewServer`を使用してテスト用のHTTPサーバーをセットアップします。
    *   このテストサーバーは、リクエストを受け取ると、HTTP/1.1 200 OKレスポンス（ボディなし、キープアライブ）を送信した後、**すぐに接続を閉じます**。これは、サーバーがキープアライブを宣言しながらも、実際にはすぐに接続を切断するという、問題のトリガーとなる状況をシミュレートしています。
    *   クライアント側では、`http.Transport`と`http.Client`を使用してこのテストサーバーにリクエストを送信します。
    *   テストの重要な部分は、`defer afterTest(t)`です。`afterTest`は、テスト終了時に残存するゴルーチンがないかチェックするヘルパー関数であり、ゴルーチンリークを検出するために使用されます。
    *   このテストの目的は、サーバーが接続を早期に閉じた場合でも、`Transport`の`readLoop`ゴルーチンがリークせずに正常に終了することを確認することです。レスポンスヘッダーのチェックは、単にレスポンスが少なくとも受信されたことの健全性チェックであり、テストの主要な目的はゴルーチンリークがないことの検証です。

これらの変更により、`net/http`パッケージは、より堅牢になり、特定のタイミングの問題によるゴルーチンリークを防ぐことができるようになりました。

## 変更の背景

このコミットで説明が追加された「内部パッケージ」と「正規インポートパス」は、Go言語のパッケージ管理における長年の課題を解決するために導入されました。

### 内部パッケージの背景

Goのパッケージシステムは、コードをコンポーネントに分割し、明確な境界を持つプログラムを構築するのに優れています。しかし、アクセス制御の形式は「ローカル（非エクスポート）」と「グローバル（エクスポート）」の2種類しかありませんでした。これにより、大規模なライブラリやアプリケーションを複数のパッケージに分割する際に、意図せず内部APIが外部に公開されてしまうという問題が生じていました。

例えば、標準ライブラリ内でも、特定の機能が複数のパッケージで重複して実装されたり、本来内部利用を意図したパッケージが外部からインポートされてしまうといった状況がありました。これは、APIの安定性を損なう可能性があり、将来的なリファクタリングを困難にする要因となっていました。

「内部パッケージ」の導入は、このような問題を解決し、公開リポジトリの一部でありながら、そのプログラムの外部での使用を意図しないコードのコンポーネントを持つことを可能にすることを目的としています。これにより、開発者はよりクリーンなアーキテクチャを設計し、内部実装の詳細を外部から隠蔽できるようになりました。

### 正規インポートパスの背景

Goのパッケージは通常、`github.com/user/repo` のように、ホスティングサービスのドメイン名を含むインポートパスを持ちます。しかし、Goには「カスタム」または「Vanity」インポートパス（例: `rsc.io/pdf`）を提供する既存のメカニズムがありました。これは、開発者が自身のドメイン名を使用してパッケージを公開できる便利な機能です。

しかし、このVanityインポートパスを使用すると、一つのパッケージに対して複数の有効なインポートパス（例: `github.com/rsc/pdf` と `rsc.io/pdf`）が存在することになります。これは以下の問題を引き起こす可能性がありました。

*   **コードの重複と無駄**: 単一のプログラム内で、意図せず同じパッケージが異なるパスで二重にインポートされてしまうと、コンパイルされたバイナリのサイズが増加したり、予期せぬ挙動を引き起こす可能性がありました。
*   **更新の見落とし**: 使用しているパスが古くなっていることに気づかず、パッケージの更新を見落とす可能性がありました。
*   **クライアントの破損**: パッケージが別のホスティングサービスに移動された場合、古いパスを使用しているクライアントのコードが壊れてしまう可能性がありました。

「正規インポートパス」の導入は、これらの問題を解決し、パッケージのインポートパスを明確に一意にすることで、より堅牢で管理しやすいGoエコシステムを構築することを目的としています。

## 前提知識の解説

### Goのパッケージシステム

Go言語は、コードを整理し、再利用性を高めるためにパッケージシステムを採用しています。
*   **パッケージ**: Goのプログラムは、関連する機能を持つソースファイルの集まりであるパッケージによって構成されます。各Goファイルは `package <name>` 宣言で始まる必要があります。
*   **インポート**: 別のパッケージの機能を利用するには、`import "<path>"` ステートメントを使用してそのパッケージをインポートします。インポートパスは、通常、Goモジュールパスとリポジトリのディレクトリ構造に対応します。
*   **エクスポートと非エクスポート**: Goでは、識別子（変数、関数、型など）の最初の文字が大文字である場合、その識別子はエクスポートされ、パッケージの外部からアクセス可能です。小文字で始まる識別子は非エクスポートであり、パッケージ内部からのみアクセス可能です。

### Vanity Imports (カスタムインポートパス)

Go 1.4以前から存在していた機能で、Goパッケージのインポートパスを、実際のホスティングサービスのURL（例: `github.com/user/repo`）ではなく、開発者自身のドメイン名（例: `example.com/repo`）にマッピングする仕組みです。これは、`go get` コマンドがVanity URLにアクセスした際に、HTMLの `<meta>` タグに埋め込まれたリポジトリ情報（例: `go-import` メタタグ）を読み取り、実際のソースコードの場所を特定することで実現されます。これにより、パッケージのインポートパスをホスティングサービスから独立させ、よりブランド化された、安定したパスを提供できます。

### `go` コマンド

`go` コマンドは、Go言語のビルド、テスト、依存関係管理など、開発ワークフロー全体を管理するための主要なツールです。このコミットで説明されている「内部パッケージ」と「正規インポートパス」の機能は、この `go` コマンドによって強制されます。

## 技術的詳細

### 内部パッケージ (Internal Packages)

*   **目的**: パッケージの可視性を制限し、特定のサブツリー内でのみインポート可能にする。これにより、大規模なプロジェクトにおける内部APIの誤用を防ぎ、モジュール性を高める。
*   **仕組み**:
    *   パッケージを `internal` という名前のディレクトリ、または `internal` ディレクトリのサブディレクトリに配置します。
    *   例: `.../a/b/c/internal/d/e/f` のようなパスを持つパッケージは、`go` コマンドによって、その `internal` ディレクトリの親ディレクトリ（この例では `.../a/b/c`）をルートとするディレクトリツリー内のコードからのみインポートが許可されます。
    *   `.../a/b/g` や他のリポジトリ内のコードからはインポートできません。
*   **強制**: `go` コマンドがインポートパスに `internal` を含むパッケージを検出すると、インポート元のパッケージが `internal` ディレクトリの親をルートとするツリー内に存在するかどうかを検証します。この検証に失敗すると、コンパイルエラーが発生します。
*   **段階的導入**: Go 1.4では、Goのメインリポジトリに対してこのメカニズムが強制されました。Go 1.5以降では、任意のGoリポジトリに対して強制されるようになりました。
*   **設計ドキュメント**: 詳細なメカニズムは、`http://golang.org/s/go14internal` にて設計ドキュメントとして公開されています。

### 正規インポートパス (Canonical Import Paths)

*   **目的**: パッケージのインポートパスを一意に強制し、Vanityインポートパスと実際のホスティングパスの間の曖昧さを解消する。これにより、コードの重複、更新の見落とし、リポジトリ移動時のクライアント破損を防ぐ。
*   **仕組み**:
    *   Goソースファイルの `package` 宣言行に、特別なコメントを追加します。
    *   構文: `package <name> // import "<canonical-path>"`
    *   例: `package pdf // import "rsc.io/pdf"`
    *   このコメントは、そのパッケージの正規のインポートパスを `go` コマンドに伝えます。
*   **強制**: `go` コマンドは、パッケージがインポートされる際に、実際に使用されたインポートパスが、ソースファイルに指定された正規インポートパスと一致するかどうかを検証します。
    *   一致しない場合、`go` コマンドはインポート元のパッケージのコンパイルを拒否します。
*   **チェックのタイミング**: このチェックはビルド時に行われます。`go get` がこのチェックのために失敗した場合、誤ってインポートされたパッケージはローカルマシンにコピーされている可能性があるため、手動で削除する必要があります。
*   **設計ドキュメント**: 詳細なメカニズムは、`http://golang.org/s/go14customimport` にて設計ドキュメントとして公開されています。

## コアとなるコードの解説

このコミットは、Go 1.4のリリースノートに、Go言語のパッケージ管理における重要な改善点である「内部パッケージ」と「正規インポートパス」に関する公式な説明を追加するものです。

*   **内部パッケージの説明**:
    *   Goのパッケージシステムにおけるアクセス制御の限界（エクスポート/非エクスポートのみ）を指摘し、内部利用を意図したコードの隠蔽の必要性を強調しています。
    *   `internal` ディレクトリの命名規則と、`go` コマンドがどのようにインポートを制限するかを具体的に説明しています。これにより、開発者はプロジェクト内でより厳密なモジュール境界を定義できるようになります。
    *   Go 1.4ではGoメインリポジトリに限定されていた強制が、Go 1.5以降で一般のリポジトリにも拡大されることが明記されており、この機能の重要性と将来的な普及を示唆しています。
    *   関連する設計ドキュメントへのリンクが提供されており、より深い理解を促しています。

*   **正規インポートパスの説明**:
    *   `github.com` のようなホスティングサービスに依存するインポートパスと、Vanityインポートパスの共存が引き起こす問題（重複インポート、更新の見落とし、リポジトリ移動時の問題）を明確に提示しています。
    *   `package <name> // import "<canonical-path>"` というシンプルな構文で正規インポートパスを指定できることを示しています。
    *   `go` コマンドが正規インポートパスを強制し、非正規パスでのインポートを拒否することで、これらの問題を解決するメカニズムを説明しています。これにより、パッケージのインポートパスが一意に定まり、コードの堅牢性と保守性が向上します。
    *   チェックがビルド時に行われること、および `go get` が失敗した場合の対処法（手動削除）についても言及しており、ユーザーがこの新機能に遭遇した際の混乱を避けるための実用的な情報を提供しています。
    *   関連する設計ドキュメントへのリンクも提供されており、この機能の背景と詳細な設計思想を学ぶことができます。

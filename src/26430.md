# [インデックス 26430] ファイルの概要

## コミット

このコミットは、Goアセンブラ（`cmd/asm`）のテストスイートにおける「ゴールデンファイル」のメンテナンス方法を簡素化することを目的としています。具体的には、アセンブラの入力となるアセンブリ言語ファイル（`.s`ファイル）と、そのアセンブル結果の期待値が記述された出力ファイル（`.out`ファイル）が並行して存在していたテスト構造を改善します。変更後は、期待される出力との差異を元の`.s`ファイル内に直接アノテーションとして記述する方式に移行し、テストの可読性とメンテナンス性を向上させています。

この変更により、テストが引き続きパスするだけでなく、以前は2つのファイルに分散していたために見過ごされがちだった、アセンブラの出力やパースに関する多くのエラーが明確になりました。また、`cmd/internal/obj`内の診断に関するいくつかの問題も修正されています。これは、Go issue #13822 の解決に向けた一歩です。

## 変更の背景

Goのアセンブラ（`cmd/asm`）のテストでは、アセンブリ言語のソースファイル（例: `386.s`, `amd64.s`など）と、それらをアセンブルした結果の期待値が記述された対応する出力ファイル（例: `386.out`, `amd64.out`など）を比較する「ゴールデンファイルテスト」が用いられていました。この方式は、アセンブラの出力が意図した通りであることを確認するのに有効ですが、以下のような課題がありました。

1.  **メンテナンスの複雑さ:** ソースファイルと出力ファイルがほぼ同じ内容を持つにもかかわらず、2つの独立したファイルとして管理する必要がありました。ソースファイルに変更を加えるたびに、対応する出力ファイルも手動またはスクリプトで更新する必要があり、手間がかかりました。
2.  **差異の把握の困難さ:** 期待される出力と実際のアセンブラの出力との間にわずかな差異がある場合、2つのファイルを並べて比較する必要があり、どの部分が意図的な差異で、どの部分がバグによるものなのかを即座に把握するのが困難でした。特に、アセンブラの出力形式の変更があった場合、大量の`.out`ファイルを更新する必要が生じ、その変更が正しいかどうかを検証するのも一苦労でした。
3.  **隠れたバグ:** 2つのファイルに情報が分散していることで、アセンブラの出力やパースにおける微妙なエラーが見過ごされやすい状況でした。

これらの課題を解決し、テストのメンテナンスコストを削減し、同時にテストの診断能力を向上させるために、このコミットではテストの構造が根本的に見直されました。

## 前提知識の解説

### ゴールデンファイルテスト

ゴールデンファイルテスト（またはスナップショットテスト）は、プログラムの出力が時間の経過とともに変化しないことを保証するためのテスト手法です。テスト対象のプログラムを実行し、その出力を「ゴールデンファイル」（またはスナップショット）と呼ばれる事前に定義された期待値ファイルと比較します。出力がゴールデンファイルと一致しない場合、テストは失敗します。この手法は、コンパイラ、アセンブラ、コードジェネレータ、レンダリングエンジンなど、複雑な出力を生成するプログラムのテストで特に有用です。

### Goのアセンブラ (`cmd/asm`)

Go言語は、一部のパフォーマンスクリティカルな部分や、特定のハードウェア機能を利用するためにアセンブリ言語を使用します。`cmd/asm`は、Goツールチェーンの一部として提供されるアセンブラで、Goのランタイムや標準ライブラリの一部で使用されるPlan 9スタイルのアセンブリ言語をアセンブルします。このアセンブラは、一般的なアセンブラとは異なる独自の構文とセマンティクスを持っています。

### Plan 9アセンブリ

Goのアセンブラは、Bell LabsのPlan 9オペレーティングシステムで使用されていたアセンブラの構文に基づいています。これは、Intel構文やAT&T構文とは異なり、レジスタ名、オペランドの順序、アドレッシングモードの記述方法などに特徴があります。例えば、`MOVQ $1, AX` のように、ソースオペランドが先に、デスティネーションオペランドが後に来るのが一般的です。

### `cmd/internal/obj` パッケージ

`cmd/internal/obj`パッケージは、Goコンパイラおよびアセンブラのバックエンドで共通して使用されるオブジェクトファイル形式やアセンブリ命令の抽象化を定義しています。アセンブラがソースコードをパースして生成する中間表現（`obj.Prog`など）や、リンカが使用するシンボル情報などが含まれます。

## 技術的詳細

このコミットの核心は、ゴールデンファイルテストの運用方法の変更にあります。

**変更前:**
`testdata/arch.s` (アセンブリソース) と `testdata/arch.out` (期待されるアセンブル結果) の2つのファイルが存在しました。`endtoend_test.go`内のテストコードは、`arch.s`をアセンブルし、その結果を`arch.out`と比較していました。

**変更後:**
`testdata/arch.out`ファイルは削除されました。代わりに、`testdata/arch.s`ファイル内に、アセンブラの出力に関するアノテーションがコメント形式で直接記述されるようになりました。

例えば、元の`.s`ファイルに以下のような行があったとします。

```assembly
TEXT foo(SB), 0, $0
    ADD $1, R2, R3
```

これがアセンブルされると、特定の形式で出力されます。変更前は、この出力が`arch.out`に記述されていました。変更後は、`arch.s`ファイル内に以下のように記述されます。

```assembly
TEXT foo(SB), 7, $0 // TEXT foo(SB), 0, $0 (original line, now with frame size 7)
    ADD $1, R2, R3 // ADD $1, R2, R3 (expected output form)
```

ここで、`//`以降のコメントがアセンブラの期待される出力形式を示しています。`endtoend_test.go`内のテストロジックは、`arch.s`ファイルを読み込み、アセンブラを実行して実際の出力を生成します。その後、`arch.s`ファイル内のアノテーションをパースし、実際の出力とアノテーションで指定された期待値を比較します。

この方式の利点は以下の通りです。

*   **単一ソース:** アセンブリコードと期待される出力が同じファイル内に共存するため、関連する情報を一箇所で確認できます。
*   **差異の明確化:** アセンブリコードの行と、それに対応する期待される出力行が隣接しているため、どの入力がどの出力に対応するのか、そしてどのような差異が期待されているのかが一目で分かります。これにより、意図しない出力の変更や、アセンブラのバグの発見が容易になります。
*   **メンテナンスの簡素化:** アセンブリコードを変更した場合、対応するアノテーションも同じファイル内で更新するだけで済みます。
*   **診断の改善:** コミットメッセージにもあるように、この変更により、以前は2つのファイルに分かれていたために見過ごされがちだった、アセンブラの出力やパースに関する多くのエラーが明確になりました。

`endtoend_test.go`の変更は、この新しいテストロジックを実装しています。具体的には、`.out`ファイルを読み込む代わりに、`.s`ファイルを読み込み、コメント行を解析して期待される出力を抽出する処理が追加されています。また、アセンブラの出力形式の正規化（スペースの調整など）も行われ、比較の堅牢性が高められています。

`src/cmd/internal/obj`パッケージにおける診断問題の修正は、アセンブラがエラーメッセージを生成する際のコンテキスト（ファイル名や行番号）をより正確に提供するための改善と考えられます。例えば、`opbra`関数のエラーメッセージが、単なる文字列ではなく、`%v: .nil/.nil/.W on bra instruction`のように`p`（`obj.Prog`）オブジェクトを含めるように変更されており、これにより具体的なプログラム情報が診断メッセージに含まれるようになります。

## コアとなるコードの変更箇所

1.  **`src/cmd/asm/internal/asm/endtoend_test.go`**:
    *   `testEndToEnd`関数が大幅に書き換えられました。
    *   以前は`goarch+".out"`ファイルを読み込んで期待値と比較していましたが、このファイルは削除され、代わりに`goarch+".s"`ファイルを読み込み、その中のコメントから期待される出力を抽出するロジックが追加されました。
    *   アセンブラの出力と、`.s`ファイル内のアノテーションから抽出された期待値を比較する新しいアルゴリズムが実装されました。これには、出力の正規化（スペースの調整、相対アドレスの絶対アドレスへの変換など）が含まれます。
    *   `ctxt.Diag`が`log.Fatalf`から`t.Errorf`に変更され、テスト失敗時にテスト全体を終了させるのではなく、エラーとして報告するようになりました。

2.  **`src/cmd/asm/internal/asm/testdata/*.s` ファイル群**:
    *   `386.s`, `amd64.s`, `arm.s`, `arm64.s`, `mips64.s`, `ppc64.s`などのアセンブリソースファイルが変更されました。
    *   これらのファイルから対応する`.out`ファイルが削除されました。
    *   各アセンブリ命令の行に、アセンブラが生成する期待される出力形式を示すコメント（例: `// TEXT foo(SB), 0, $0`）が追加されました。これにより、アセンブリコードと期待される出力が同じファイル内で管理されるようになりました。
    *   一部の命令の`TEXT`ディレクティブのフレームサイズが`0`から`7`に変更されています（例: `TEXT foo(SB), 0, $0` -> `TEXT foo(SB), 7, $0`）。これは、アセンブラの内部的な変更や、より正確なフレームサイズ計算の反映である可能性があります。

3.  **`src/cmd/asm/internal/asm/testdata/*.out` ファイル群**:
    *   `386.out`, `amd64.out`, `arm.out`, `arm64.out`, `mips64.out`, `ppc64.out`など、すべてのアーキテクチャの`.out`ファイルが削除されました。

4.  **`src/cmd/internal/obj/arm/asm5.go`**:
    *   `opbra`関数が変更され、診断メッセージが`ctxt.Diag(".nil/.nil/.W on bra instruction")`から`ctxt.Diag("%v: .nil/.nil/.W on bra instruction", p)`のように、`obj.Prog`オブジェクト`p`を含むように改善されました。これにより、エラー発生時のコンテキスト情報がより詳細になります。

5.  **`src/cmd/asm/internal/arch/arm.go`**:
    *   `armJump`マップに`"BX": true`が追加されました。これはARMアーキテクチャにおける`BX`命令がジャンプ命令として認識されるようにするための修正です。

## コアとなるコードの解説

### `src/cmd/asm/internal/asm/endtoend_test.go` の変更

このファイルの`testEndToEnd`関数は、アセンブラのテストの中核をなします。主要な変更点は以下の通りです。

```go
// 変更前:
// expect, err := ioutil.ReadFile(output) // outputはgoarch+".out"
// if result != string(expect) { ... }

// 変更後:

// ...
// Reconstruct expected output by independently "parsing" the input.
data, err := ioutil.ReadFile(input) // inputはgoarch+".s"
// ...
lineno := 0
seq := 0
Diff:
for _, line := range strings.SplitAfter(string(data), "\n") {
    lineno++
    // ...
    // コメントから期待される出力形式を抽出
    parts := strings.Split(line, "//")
    printed := strings.TrimSpace(parts[0])
    if printed == "" || strings.HasSuffix(printed, ":") { // empty or label
        continue
    }
    seq++

    switch len(parts) {
    default:
        t.Errorf("%s:%d: unable to understand comments: %s", input, lineno, line)
    case 1:
        // no comment
    case 2:
        // one comment, printed form
        printed = strings.TrimSpace(parts[1])
    }

    // Canonicalize spacing in printed form.
    // ... (スペースの正規化ロジック)

    // Turn relative (PC) into absolute (PC) automatically,
    // so that most branch instructions don't need comments
    // giving the absolute form.
    // ... (相対アドレスを絶対アドレスに変換するロジック)

    want := fmt.Sprintf("%05d (%s:%d)\t%s", seq, input, lineno, printed)
    // 実際の出力 (output) と期待される出力 (want) を比較
    for len(output) > 0 && (output[0] < want || output[0] != want && len(output[0]) >= 5 && output[0][:5] == want[:5]) {
        // ... エラー報告ロジック
    }
    if len(output) > 0 && output[0] == want {
        output = output[1:]
    } else {
        t.Errorf("missing output: %q", want)
    }
}
// ... (残りの出力のチェック)
```

このコードは、`goarch+".s"`ファイルを1行ずつ読み込み、`//`で始まるコメントを解析して期待されるアセンブラの出力形式（`printed`変数に格納される）を抽出します。抽出された`printed`形式は、スペースの正規化や相対アドレスの絶対アドレスへの変換といった処理を経て、最終的な期待値`want`が構築されます。この`want`と、アセンブラが実際に生成した出力`output`の各行が比較され、一致しない場合はエラーが報告されます。

### `src/cmd/internal/obj/arm/asm5.go` の変更

`opbra`関数は、ARMアーキテクチャの分岐命令（`B`, `BL`, `BEQ`など）を処理する際に呼び出されます。変更前は、診断メッセージが汎用的な文字列でしたが、変更後は`p *obj.Prog`引数を受け取るようになり、エラーメッセージに具体的なプログラム情報を含めることができるようになりました。

```go
// 変更前:
// func opbra(ctxt *obj.Link, a int, sc int) uint32 {
//     if sc&(C_SBIT|C_PBIT|C_WBIT) != 0 {
//         ctxt.Diag(".nil/.nil/.W on bra instruction")
//     }
//     // ...
//     if sc != 0xe {
//         ctxt.Diag(".COND on bcond instruction")
//     }
// }

// 変更後:
func opbra(ctxt *obj.Link, p *obj.Prog, a int, sc int) uint32 {
    if sc&(C_SBIT|C_PBIT|C_WBIT) != 0 {
        ctxt.Diag("%v: .nil/.nil/.W on bra instruction", p) // p を含める
    }
    // ...
    if sc != 0xe {
        ctxt.Diag("%v: .COND on bcond instruction", p) // p を含める
    }
}
```

この変更により、アセンブラが不正な分岐命令を検出した場合、どのソースファイルのどの行で問題が発生したのかをより正確にユーザーに伝えることができるようになります。

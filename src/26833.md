## 元コミット内容

GoコンパイラのSSAバックエンドにおいて、オペコードに引数の最大長（`argLength`）を追加し、それをゼロコスト共通部分式除去（ZCSE: Zero Cost Common Subexpression Elimination）で利用するようにしました。この変更はコンパイル速度には影響しませんが、`checkFunc`におけるより厳密なチェックを可能にし、引数を取らないオペコードのリストを別途管理する必要をなくします。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現としてSSA（Static Single Assignment）形式を使用します。SSA形式では、各変数が一度だけ代入されるため、最適化が容易になります。このSSA形式のバックエンドでは、様々な操作が「オペコード」として表現され、それぞれが特定の数の引数を取ります。

以前のGoコンパイラでは、各オペコードが取る引数の数を明示的に管理する方法が不十分でした。特に、引数を取らないオペコード（ゼロ引数オペコード）のリストを別途手動で更新する必要があり、これはエラーの温床となる可能性がありました。また、コンパイラの内部整合性チェック（`checkFunc`）において、オペコードが期待される数の引数を実際に持っているかどうかの検証が、より堅牢であるべきという課題がありました。

このコミットは、これらの課題に対処するために、オペコードの定義に引数の最大長を直接組み込むことで、コンパイラの堅牢性と保守性を向上させることを目的としています。これにより、オペコードの引数に関する不整合を早期に検出し、コンパイラのバグを未然に防ぐことが期待されます。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化で広く用いられる中間表現です。この形式では、プログラム中の各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が単純化され、共通部分式除去（CSE）、定数伝播、デッドコード除去などの最適化が効率的に行えるようになります。Goコンパイラも、最適化パスでSSA形式を採用しています。

### 2. オペコード (Opcode)

オペコードは、コンパイラのSSA中間表現における基本的な操作単位です。例えば、`Add64`は64ビット整数の加算、`Load`はメモリからのロード、`Store`はメモリへのストアといった具体的な操作を表します。各オペコードは、その操作を実行するために特定の数の入力値（引数）を必要とします。

### 3. `checkFunc`

`checkFunc`は、GoコンパイラのSSAバックエンドにおける重要なデバッグおよび検証関数です。SSA形式の関数が生成された後、その構造が正しいか、各オペコードが適切な引数を持っているか、型が一致しているかなど、様々な整合性チェックを行います。これにより、コンパイラ自体のバグを早期に発見し、不正なコード生成を防ぎます。

### 4. ZCSE (Zero Cost Common Subexpression Elimination)

共通部分式除去（CSE）は、同じ計算が複数回行われている場合に、その計算結果を一度だけ求め、再利用することで冗長な計算を排除する最適化手法です。GoコンパイラのSSAバックエンドでは、特に「ゼロコスト」という言葉が使われることがありますが、これは特定の状況下でCSEが非常に効率的に行われることを指す場合があります。このコミットでは、`zcse`という名前で言及されており、オペコードの引数情報がこの最適化パスで利用されることが示唆されています。

### 5. `opData` と `opInfo` 構造体

GoコンパイラのSSAバックエンドでは、オペコードに関するメタデータが`opData`（ジェネレータ用）や`opInfo`（ランタイム用）といった構造体で管理されています。これらの構造体には、オペコードの名前、レジスタ割り当て情報、補助データ型などの情報が含まれています。このコミットでは、これらの構造体に`argLength`フィールドが追加されます。

## 技術的詳細

このコミットの主要な技術的変更点は、GoコンパイラのSSAバックエンドにおけるオペコードの定義に`argLength`という新しいフィールドを導入したことです。

1.  **`opData` および `opInfo` 構造体への `argLength` の追加**:
    *   `src/cmd/compile/internal/ssa/gen/main.go` にある `opData` 構造体（オペコード定義の生成に使用される）に `argLength int32` フィールドが追加されました。このフィールドは、オペコードが取る引数の数を表し、可変長引数の場合は `-1` が設定されます。
    *   `src/cmd/compile/internal/ssa/op.go` にある `opInfo` 構造体（コンパイラランタイムがオペコード情報を参照するために使用する）にも同様に `argLen int32` フィールドが追加されました。

2.  **オペコード定義への `argLength` の設定**:
    *   `src/cmd/compile/internal/ssa/gen/AMD64Ops.go` および `src/cmd/compile/internal/ssa/gen/genericOps.go` の両方で、各オペコードの定義に `argLength` フィールドが明示的に追加され、適切な引数の数が設定されました。例えば、`ADDSS`のような2項演算は `argLength: 2` となり、`MOVSSconst`のような定数生成オペコードは `argLength: 0` となります。可変長引数を取る `Phi` オペコードには `argLength: -1` が設定されています。

3.  **`checkFunc` での引数チェックの強化**:
    *   `src/cmd/compile/internal/ssa/check.go` の `checkFunc` 関数内で、各`Value`（SSA形式のオペコードインスタンス）が持つ引数の数が、そのオペコードの`opInfo`に定義されている`argLen`と一致するかどうかのチェックが追加されました。
    *   具体的には、`nArgs := opcodeTable[v.Op].argLen` でオペコードの期待される引数長を取得し、`if nArgs != -1 && int32(len(v.Args)) != nArgs` という条件で、可変長でないオペコードの引数数が一致しない場合に `f.Fatalf` でコンパイルエラーを発生させるようになりました。これにより、コンパイラ内部の不整合を早期に検出できるようになります。

4.  **`zcse` (Zero Cost Common Subexpression Elimination) での利用**:
    *   コミットメッセージには「use it in zcse」とありますが、提供された差分では `src/cmd/compile/internal/ssa/zcse.go` の具体的な変更は示されていません。しかし、`argLength`情報が利用可能になったことで、ZCSEパスでオペコードの引数数をより正確に把握し、最適化の判断に役立てることができるようになったと考えられます。例えば、引数数が異なるオペコードは共通部分式として扱わない、といった厳密な判断が可能になります。

5.  **`rulegen.go` の変更**:
    *   `src/cmd/compile/internal/ssa/gen/rulegen.go` では、オペコードの可変長引数に関する判定ロジックが `op.variableLength` から `op.argLength == -1` を参照するように変更されました。これは、可変長引数であるかどうかの情報を `argLength` フィールドに集約した結果です。

この変更により、GoコンパイラのSSAバックエンドは、オペコードの引数に関するより厳密な型チェックと整合性検証を行うことができるようになり、コンパイラの信頼性と保守性が向上しました。

## コアとなるコードの解説

このコミットの核心は、GoコンパイラのSSA中間表現におけるオペコードの厳密な引数管理を導入した点にあります。

1.  **`opInfo` と `opData` への `argLen` の追加**:
    *   `opInfo` はコンパイラが実行時に各オペコードの特性をルックアップするために使用する構造体です。ここに `argLen` を追加することで、各オペコードが期待する引数の数を直接、かつ一元的に定義できるようになりました。これにより、オペコードの定義と実際の使用の間で不整合が生じるリスクが低減されます。
    *   `opData` は、`opInfo` などのオペコード関連のデータを生成するためのメタデータ構造体です。`variableLength` ブール値から `argLength` 整数値への変更は、可変長引数を持つオペコード（例: `Phi`）と固定長引数を持つオペコードをより明確に区別し、引数の数を数値で直接表現できるようにしたものです。`-1` は可変長を意味します。

2.  **`checkFunc` での引数検証**:
    *   `checkFunc` はコンパイラの健全性を保つための重要なガードレールです。この変更により、SSA形式の各 `Value`（オペコードのインスタンス）が、そのオペコード定義で指定された `argLen` と同じ数の引数を持っているかを厳密にチェックするようになりました。
    *   `nArgs := opcodeTable[v.Op].argLen` で、現在のオペコード `v.Op` に対応する `opInfo` から期待される引数長 `nArgs` を取得します。
    *   `if nArgs != -1 && int32(len(v.Args)) != nArgs` の条件は、オペコードが可変長引数（`nArgs == -1`）でない場合に、実際に渡された引数の数 `len(v.Args)` が期待される数 `nArgs` と異なるかどうかをチェックします。
    *   もし不一致があれば、`f.Fatalf` を呼び出してコンパイルを中止し、詳細なエラーメッセージを出力します。これにより、コンパイラの開発者は、オペコードの定義ミスやSSA生成ロジックのバグを早期に特定し、修正することができます。これは、コンパイラの安定性と信頼性を高める上で非常に重要です。

3.  **`zcse` および `rulegen.go` への影響**:
    *   `zcse` での利用は、オペコードの引数数を正確に知ることで、共通部分式の識別をより正確に行えるようになることを意味します。例えば、引数数が異なる2つのオペコードは、たとえ名前が同じでも共通部分式ではないと判断できます。
    *   `rulegen.go` の変更は、オペコードの可変長引数特性を `variableLength` ブール値ではなく `argLength == -1` で判断するように統一したもので、コードの一貫性と保守性を向上させます。

全体として、このコミットはGoコンパイラの内部構造をより堅牢にし、将来的な開発や最適化の基盤を強化するものです。

## 元コミット内容

`runtime: avoid fault in heapBitsBulkBarrier`

このコミットは、`heapBitsBulkBarrier`関数内で発生する可能性のあるページフォルト（メモリ保護違反）を回避するための修正です。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行中に不要になったメモリを自動的に解放する重要な機能です。Go 1.5以降、GCは並行かつ低遅延で動作するように設計されており、そのために「ライトバリア（Write Barrier）」という技術が導入されています。ライトバリアは、ポインタの書き込み時にGCがオブジェクトのグラフを正確に追跡できるようにするためのフックです。

`heapBitsBulkBarrier`関数は、大量のヒープメモリをコピーまたは移動する際に、その範囲内のポインタに対してライトバリア処理を一括で適用するために使用されます。これは、例えばスライスやマップの拡張、チャネル操作などでメモリが再配置される際に必要となります。

この関数内で、現在のゴルーチン（`gp`）のスタック領域と、バリア処理の対象となるメモリ領域`p`が重なっているかどうかをチェックするロジックがありました。もし重なっている場合、`systemstack`を使ってシステムスタックに切り替えて処理を行うことで、スタックオーバーフローなどの問題を回避しようとしていました。

しかし、特定の状況下で`getg().m.curg`が`nil`を返す可能性があり、その結果`gp.stack.lo`や`gp.stack.hi`にアクセスしようとすると、`nil`ポインタデリファレンスによるページフォルトが発生する可能性がありました。これは、例えばゴルーチンがまだ完全に初期化されていない、あるいは既に終了処理中であるといったエッジケースで起こりえます。このような状況で`gp`が`nil`であるにもかかわらずスタック情報にアクセスしようとすると、プログラムがクラッシュしてしまいます。

このコミットは、この潜在的なクラッシュを防ぐために、`gp.stack.lo`や`gp.stack.hi`にアクセスする前に`gp`が`nil`でないことを確認するチェックを追加しています。

## 前提知識の解説

### Goのガベージコレクション (GC) とライトバリア

GoのGCは、三色マーク＆スイープアルゴリズムをベースにしています。オブジェクトは「白（未訪問）」「灰（訪問済みだが参照先未訪問）」「黒（訪問済みかつ参照先も訪問済み）」のいずれかの色でマークされます。

ライトバリアは、GCのマークフェーズ中にプログラムがポインタを書き換える際に、GCがオブジェクトグラフの整合性を保つためのメカニズムです。具体的には、あるオブジェクトから別のオブジェクトへのポインタが書き換えられるとき、GCがその変更を認識し、必要に応じてオブジェクトを「灰色」にマークし直すことで、GCが誤って到達可能なオブジェクトを回収してしまうことを防ぎます。

`heapBitsBulkBarrier`は、個々のポインタ書き込みではなく、メモリブロック全体に対してライトバリアを適用する際に使用されます。これは、大量のメモリ移動が発生する際に、個別のライトバリアを何度も実行するよりも効率的です。

### `getg().m.curg`

Goランタイム内部では、`getg()`は現在のゴルーチン（`g`構造体）へのポインタを返します。`g`構造体には、そのゴルーチンのスタック情報（`stack.lo`と`stack.hi`）などが含まれています。
`getg().m`は現在のM（Machine、OSスレッド）構造体へのポインタを返し、`getg().m.curg`はそのM上で現在実行中のゴルーチンへのポインタを返します。通常、`getg()`と`getg().m.curg`は同じゴルーチンを指しますが、ランタイムの特定のコンテキスト（例えば、システムスタック上での処理中など）では異なる場合があります。

### `systemstack`

`systemstack`は、Goランタイムが内部的に使用する特殊な関数です。通常のGoコードはゴルーチンのスタック上で実行されますが、`systemstack`を使用すると、現在のゴルーチンのスタックではなく、ランタイムが管理する固定サイズのシステムスタックに切り替えてコードを実行できます。これは、スタックオーバーフローの危険がある処理や、GCなどのランタイムのコア機能で、現在のゴルーチンのスタック状態に依存せずに安全に処理を実行したい場合に利用されます。

### ページフォルト

ページフォルトは、プログラムがアクセスしようとしたメモリページが物理メモリ上に存在しない、またはアクセス権がない場合に発生するハードウェア割り込みです。オペレーティングシステムは、この割り込みを処理して、必要なページをディスクからロードしたり、アクセス違反の場合はプログラムを終了させたりします。このコミットの文脈では、`nil`ポインタデリファレンスによって不正なメモリアドレスにアクセスしようとした結果としてページフォルトが発生し、プログラムがクラッシュする可能性を指しています。

## 技術的詳細

`heapBitsBulkBarrier`関数は、`p`で始まる`size`バイトのメモリ領域に対してライトバリア処理を行います。この処理中に、対象メモリ領域`p`が現在のゴルーチン`gp`のスタック領域と重なっているかどうかをチェックします。

元のコードは以下のようになっていました。

```go
		gp := getg().m.curg
		if gp.stack.lo <= p && p < gp.stack.hi {
			// Run on the system stack to give it more
			// stack space.
			systemstack(func() {
				// ...
			})
		}
```

ここで問題となるのは、`gp := getg().m.curg`が`nil`を返す可能性がある点です。`getg().m.curg`は、現在のM（OSスレッド）が実行しているゴルーチンを返しますが、ランタイムの非常に初期段階や、ゴルーチンの終了処理中など、特定の遷移状態では`curg`が`nil`である可能性があります。

もし`gp`が`nil`であるにもかかわらず、次の行で`gp.stack.lo`や`gp.stack.hi`にアクセスしようとすると、`nil`ポインタデリファレンスが発生します。これは不正なメモリアドレスへのアクセスとなり、オペレーティングシステムによってページフォルトが検出され、プログラムがクラッシュする原因となります。

このコミットでは、この問題を解決するために、`gp.stack.lo`や`gp.stack.hi`にアクセスする前に`gp`が`nil`でないことを明示的にチェックする条件を追加しました。

```go
		if gp != nil && gp.stack.lo <= p && p < gp.stack.hi {
```

この変更により、`gp`が`nil`の場合には`gp.stack.lo`へのアクセスが試みられる前に条件式全体が`false`と評価されるため、`nil`ポインタデリファレンスが回避され、プログラムの安定性が向上します。

- **変更前**: `if gp.stack.lo <= p && p < gp.stack.hi {`
  - `gp`が`nil`の場合、`gp.stack.lo`へのアクセスで`nil`ポインタデリファレンスが発生し、クラッシュする可能性がありました。

この修正は、Goランタイムの堅牢性を高め、特にエッジケースにおけるクラッシュを防ぐ上で重要です。

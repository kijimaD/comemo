## 元コミット内容

このコミットは、Go言語の `go/types` パッケージにおいて、`real(a)` および `imag(a)` ビルトイン関数が型なし引数（untyped arguments）を扱う際の不具合を修正します。この修正は、Issue #11947 に対応するものです。

## 変更の背景

Go言語では、数値リテラルなどの定数は、初期段階では特定の型を持たない「型なし定数（untyped constants）」として扱われます。これらの定数は、その値が使用される文脈（例えば、変数への代入や他の型付き値との演算）によって初めて具体的な型が決定されます。`real` および `imag` 関数は、複素数の実部と虚部を抽出するために使用されますが、これらの関数に型なしの引数が渡された場合、型チェッカーがその引数をどのように解釈し、どのような型を推論すべきかについて、以前のバージョンでは不正確な挙動を示すことがありました。

具体的には、型なしの数値リテラル（例: `10` や `2.7182818`）が `imag()` や `real()` に渡された場合、これらが複素数として適切に扱われず、型エラーとなるケースがありました。Goの仕様では、型なしの数値定数は必要に応じて複素数として解釈されるべきであり、`real` や `imag` 関数はそのような定数に対しても機能することが期待されます。このコミットは、この期待される挙動と実際の型チェッカーの挙動との間の乖離を解消するために導入されました。

## 前提知識の解説

### Goの型システムと型なし定数

Go言語の型システムは、静的型付けでありながらも、型推論の柔軟性を提供します。特に重要な概念が「型なし定数（untyped constants）」です。

*   **型なし定数**: `10`、`3.14`、`"hello"`、`1 + 2i` のようなリテラル値は、明示的に型が指定されない限り、最初は型なし定数として扱われます。これらは「理想的な値の空間」に存在し、任意の精度を持つことができます。
*   **デフォルト型**: 型なし定数が型付きの文脈で使用される際、明示的な型変換がない場合は、その定数にデフォルトの型が割り当てられます。
    *   整数定数: `int`
    *   浮動小数点定数: `float64`
    *   複素数定数: `complex128`
    *   真偽値定数: `bool`
    *   ルーン定数: `rune` (int32のエイリアス)
    *   文字列定数: `string`
*   **型なし式**: 定数だけでなく、`1 << s` のようなシフト演算子を含む式も、オペランドが型なしの場合、結果が型なしのままになることがあります。

この柔軟性により、開発者は異なる数値型間での演算をより自然に記述できますが、型チェッカーはこれらの型なし値を適切に「型付け」する複雑なロジックを必要とします。

### `real` と `imag` ビルトイン関数

Go言語には、複素数型 (`complex64`, `complex128`) の実部と虚部を抽出するためのビルトイン関数 `real` と `imag` が用意されています。

*   `real(c)`: 複素数 `c` の実部を返します。
*   `imag(c)`: 複素数 `c` の虚部を返します。

これらの関数は、引数として複素数型を期待しますが、型なしの複素数定数に対してもコンパイル時に動作し、結果として型なしの浮動小数点定数を返します。

### `go/types` パッケージ

`go/types` パッケージは、Goコンパイラの重要な部分であり、Goプログラムの静的型チェックとセマンティック分析を担当します。このパッケージは、ソースコードを解析し、各式の型を決定し、型エラーを検出します。Goの言語仕様に厳密に従い、型なし定数の型推論やビルトイン関数の引数チェックなど、Goプログラムの正しさを保証する上で中心的な役割を果たします。

## 技術的詳細

このコミットの主要な変更点は、`src/go/types/builtins.go` 内の `builtin` 関数における `_Imag` および `_Real` ケースの処理ロジックにあります。以前の実装では、`real` や `imag` に渡される引数が型なしの場合、その型推論とエラーチェックが不十分でした。

### 変更前の問題点

1.  **型なし数値リテラルの不適切な処理**: `imag(10)` や `real(2.718)` のようなコードは、Goの仕様上は有効であるべきですが、以前の型チェッカーでは「引数は複素数でなければならない」というエラーを発生させていました。これは、型なしの数値定数が複素数として適切に解釈されていなかったためです。
2.  **型なし非定数引数の処理**: シフト演算子などを含む型なしの非定数式が `real` や `imag` に渡された場合、その後の型チェックで適切なエラーを生成するための準備が不足していました。
3.  **エラーメッセージの曖昧さ**: 引数が複素数型でない場合のエラーメッセージが「`%s must be a complex number`」と一般的であり、より具体的な情報が不足していました。

### 変更後の改善点

このコミットでは、以下の改善が行われました。

1.  **型なし引数の明示的な処理**:
    *   `isUntyped(x.typ)` で引数が型なしであるかをチェックします。
    *   **型なし定数の場合 (`x.mode == constant_`)**:
        *   引数が数値型 (`isNumeric(x.typ)`) であれば、その型を `Typ[UntypedComplex]` に設定します。これにより、型なしの数値定数が `real` や `imag` の引数として渡された際に、型チェッカーがそれを型なし複素数として正しく解釈できるようになります。
    *   **型なし非定数の場合 (`else`)**:
        *   引数を `Typ[Complex128]` に変換します。これは、例えば `1 << s` のような型なしのシフト式が `real` や `imag` に渡された場合に、その式が複素数型に変換されることを試みるものです。シフト演算は複素数に対しては許可されていないため、この変換は通常、後続の型チェックでエラー（「シフト演算の左オペランドは整数型でなければならない」など）を引き起こします。これにより、より適切なエラーメッセージがユーザーに提供されます。
2.  **エラーメッセージの具体化**:
    *   引数が複素数型でない場合のエラーメッセージが「`argument has type %s, expected complex type`」に変更されました。これにより、エラーの原因がより明確になります。
3.  **結果の型推論の改善**:
    *   `real` や `imag` の結果の型を決定するロジックが、引数の型に基づいて `Float32`、`Float64`、または `UntypedFloat` を適切に選択するように修正されました。特に、型なし複素数 (`UntypedComplex`) からは型なし浮動小数点数 (`UntypedFloat`) が得られるように明示されています。

これらの変更により、`real` および `imag` 関数はGoの言語仕様に沿って、型なし引数をより堅牢かつ正確に処理できるようになりました。

## コアとなるコードの解説

`src/go/types/builtins.go` の変更は、`real` および `imag` 関数が型なし引数を処理する際のロバスト性を大幅に向上させています。

1.  **型なし引数の検出と初期処理**:
    ```go
    if isUntyped(x.typ) {
        if x.mode == constant_ {
            // an untyped constant number can alway be considered
            // as a complex constant
            if isNumeric(x.typ) {
                x.typ = Typ[UntypedComplex]
            }
        } else {
            // an untyped non-constant argument may appear if
            // it contains a (yet untyped non-constant) shift
            // epression: convert it to complex128 which will
            // result in an error (shift of complex value)
            check.convertUntyped(x, Typ[Complex128])
            // x should be invalid now, but be conservative and check
            if x.mode == invalid {
                return
            }
        }
    }
    ```
    このブロックは、引数 `x` が型なしである場合に実行されます。
    *   `x.mode == constant_` の場合、つまり引数が型なし定数である場合、それが数値型であれば `UntypedComplex` 型として扱われるように `x.typ` を設定します。これにより、`10` や `2.718` のようなリテラルが `real` や `imag` に渡された際に、型チェッカーがこれらを有効な複素数として認識できるようになります。
    *   `else` の場合、つまり引数が型なしの非定数式である場合、`check.convertUntyped(x, Typ[Complex128])` を呼び出して、引数を `complex128` 型に変換しようと試みます。これは、例えば `1 << s` のようなシフト式が型なしのまま `real` や `imag` に渡された場合に、Goの型規則（複素数に対するシフト演算は無効）に基づいて後続の型チェックでエラーを発生させるための戦略です。これにより、より意味のあるエラーメッセージが生成されます。

2.  **引数型の厳密なチェックとエラーメッセージの改善**:
    ```go
    if !isComplex(x.typ) {
        check.invalidArg(x.pos(), "argument has type %s, expected complex type", x.typ)
        return
    }
    ```
    型なし引数の処理後、または引数が最初から型付きであった場合、このコードは引数が実際に複素数型であるかをチェックします。以前の一般的なエラーメッセージ「`%s must be a complex number`」は、「`argument has type %s, expected complex type`」という、より具体的で診断に役立つメッセージに置き換えられました。これにより、開発者は引数の実際の型と期待される型を直接比較できます。

3.  **結果の型推論の正確化**:
    ```go
    var res BasicKind
    switch x.typ.Underlying().(*Basic).kind {
    case Complex64:
        res = Float32
    case Complex128:
        res = Float64
    case UntypedComplex:
        res = UntypedFloat
    default:
        unreachable()
    }
    resTyp := Typ[res]
    // ...
    x.typ = resTyp
    ```
    `real` や `imag` の結果の型を決定するロジックも改善されました。引数の基底型が `Complex64` なら結果は `Float32`、`Complex128` なら `Float64` となります。特に重要なのは、引数が `UntypedComplex` であった場合、結果の型が `UntypedFloat` となるように明示された点です。これにより、型なし複素数から抽出された実部や虚部も、その後の文脈で型が決定されるまで型なしの浮動小数点数として扱われるというGoの仕様が正確に反映されます。

これらの変更は、Goの型チェッカーが言語仕様に沿って、より正確かつユーザーフレンドリーな型推論とエラー報告を行うための重要な改善です。

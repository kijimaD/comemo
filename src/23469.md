## 元コミット内容

Goランタイムにおいて、32ビットシステム上での1ポインタ割り当てに関するヒープビットマップのテストと修正を行いました。

## 変更の背景

Goのガベージコレクタ（GC）は、ヒープ上のオブジェクトがポインタを含むかどうかを判断するためにヒープビットマップを使用します。このビットマップは、GCがヒープをスキャンする際に、どのメモリ領域がポインタであり、どのメモリ領域がポインタではない（スカラー値である）かを識別するために不可欠です。

以前のGoランタイムでは、32ビットシステムにおいて、単一のポインタを割り当てる際にヒープビットマップが正しく設定されないという問題がありました。具体的には、32ビットシステムではポインタのサイズが4バイトですが、最小の割り当て単位が8バイト（2ポインタ分）になることがありました。この場合、1つのポインタしか含まない8バイトのブロックに対して、ヒープビットマップが2つのポインタが存在すると誤ってマークしてしまう可能性がありました。これは、GCが誤ったメモリ領域をスキャンしたり、解放してはならないメモリを解放したりする原因となり、メモリ破損やクラッシュにつながる可能性があります。

このコミットは、この32ビットシステム特有のヒープビットマップの不正確さを修正し、同時にその挙動を検証するためのテストを追加することで、ランタイムの堅牢性を向上させることを目的としています。

## 前提知識の解説

*   **ガベージコレクタ (GC)**: Goのランタイムに組み込まれている自動メモリ管理システムです。不要になったメモリを自動的に解放し、メモリリークを防ぎます。GCはヒープ上のオブジェクトをスキャンし、到達可能なオブジェクトを特定します。
*   **ヒープビットマップ (Heap Bitmap)**: GoのGCがヒープを効率的にスキャンするために使用するデータ構造です。ヒープ上の各ワード（ポインタサイズに等しいメモリ単位）がポインタであるか、スカラー値であるかを示すビット情報が格納されています。これにより、GCはポインタをたどってオブジェクトグラフを構築し、到達可能なオブジェクトをマークします。
*   **ポインタサイズ (PtrSize)**: システムのアーキテクチャによって異なる、ポインタが占めるメモリのサイズです。64ビットシステムでは8バイト、32ビットシステムでは4バイトです。
*   **メモリ割り当て (Memory Allocation)**: プログラムが実行時にメモリを要求し、システムがその要求に応じてメモリ領域を確保するプロセスです。Goランタイムは、効率的なメモリ管理のために、特定のサイズのブロック単位でメモリを割り当てることがよくあります。
*   **`_type` 構造体**: Goの型システムにおける内部表現です。各型に関する情報（サイズ、アラインメント、ポインタ情報など）を含んでいます。GCはこの情報を使用して、オブジェクト内のどこにポインタがあるかを判断します。
*   **`heapBitsSetType` 関数**: Goランタイムの内部関数で、新しく割り当てられたヒープオブジェクトのヒープビットマップを設定する役割を担います。この関数は、オブジェクトの型情報に基づいて、どのワードがポインタであるかをビットマップにエンコードします。

## 技術的詳細

このコミットの核心は、32ビットシステムにおけるメモリ割り当ての特性とヒープビットマップの正確な設定の間の不整合を解消することにあります。

32ビットシステムでは `ptrSize` が4バイトです。しかし、Goランタイムのメモリ割り当て器は、効率のために最小の割り当て単位が `2*ptrSize` (8バイト) であることがあります。これは、アラインメント要件やキャッシュ効率の最適化のためです。

問題は、ユーザーが `new(Ptr)` のように単一のポインタ（4バイト）を割り当てた場合でも、ランタイムが実際には8バイトのメモリブロックを割り当てることがある点にありました。この8バイトブロックに対して、`heapBitsSetType` 関数がビットマップを設定する際に、オブジェクトの実際のサイズ (`dataSize`) ではなく、割り当てられたブロックのサイズ (`size`) に基づいて判断してしまうと、誤って2つのポインタが存在するとマークしてしまう可能性がありました。

このコミットでは、`src/runtime/mbitmap.go` の `heapBitsSetType` 関数に以下の修正が加えられました。

1.  **64ビットシステムでの単一ポインタ最適化の明確化**:
    `if size == ptrSize` の条件が `if ptrSize == 8 && size == ptrSize` に変更されました。これにより、`size == ptrSize` の最適化パスは64ビットシステム（`ptrSize == 8`）に限定されます。32ビットシステムでは、単一ポインタの割り当てでも `size` が `ptrSize` とは異なる（例えば `2*ptrSize`）可能性があるため、このパスを避ける必要があります。

2.  **32ビットシステムでの1ポインタ割り当ての特殊処理**:
    `if size == 2*ptrSize` のブロック内に、32ビットシステム (`ptrSize == 4`) かつ割り当てられたデータの実際のサイズが1ポインタ分 (`dataSize == ptrSize`) である場合の新しい条件が追加されました。
    ```go
    if ptrSize == 4 && dataSize == ptrSize {
        // 1 pointer.
        if gcphase == _GCoff {
            *h.bitp |= bitPointer << h.shift
        } else {
            atomicor8(h.bitp, bitPointer<<h.shift)
        }
    }
    ```
    このコードブロックは、32ビットシステムで8バイトのブロックが割り当てられたが、その中に実際には1つのポインタしか含まれていない場合に、ヒープビットマップを正しく1つのポインタとして設定します。これにより、GCが正確なポインタ情報を参照できるようになります。

`src/runtime/gcinfo_test.go` では、この修正を検証するために新しいテストケースが追加されました。
*   `Ptr` 型（単一ポインタを持つ構造体）が導入され、そのGC情報が `infoPtr` として定義されました。
*   `verifyGCInfo` 関数が、`bss`, `data`, `heap` 上の `Ptr` オブジェクトに対して呼び出され、GC情報が正しく設定されているかを確認します。
*   特に重要なのは `padDead` ヘルパー関数の導入です。これは、32ビットシステムで1ワードの割り当てが2ワードのブロックを使用する場合に、ヒープビットマップとテスト用の期待値の長さを合わせるために、追加のスカラーバイトでパディングを行う役割を果たします。これにより、テストが32ビットシステム特有の割り当て挙動を正しく考慮できるようになります。

`src/runtime/export_test.go` では、`PtrSize` 定数がエクスポートされ、テストコードからランタイムのポインタサイズにアクセスできるようになりました。これは、`gcinfo_test.go` の `padDead` 関数で `runtime.PtrSize` を使用するために必要です。

これらの変更により、32ビットシステム上でのGoプログラムのメモリ安全性とGCの正確性が向上しました。

### `src/runtime/mbitmap.go` の変更

`heapBitsSetType` 関数は、ヒープに割り当てられたオブジェクトのGCビットマップを設定する役割を担います。

*   **`if ptrSize == 8 && size == ptrSize`**:
    この変更は、以前の `if size == ptrSize` をより厳密にしました。64ビットシステム（`ptrSize == 8`）において、割り当てられたブロックのサイズがちょうど1ポインタ分である場合にのみ、この最適化パスが適用されることを保証します。32ビットシステムでは、1ポインタの割り当てでもより大きなブロックが使われる可能性があるため、このパスから除外されます。

*   **`if ptrSize == 4 && dataSize == ptrSize` ブロック**:
    これが32ビットシステムにおける主要な修正点です。
    `size == 2*ptrSize` の条件は、割り当てられたメモリブロックが2ポインタ分（32ビットシステムでは8バイト）であることを意味します。
    このブロック内で、さらに `ptrSize == 4` (32ビットシステムであること) かつ `dataSize == ptrSize` (実際に割り当てられたオブジェクトのサイズが1ポインタ分であること) という条件がチェックされます。
    この条件が真の場合、ランタイムは8バイトのブロックを割り当てたが、その中に含まれるポインタは1つだけであると判断します。
    `*h.bitp |= bitPointer << h.shift` または `atomicor8(h.bitp, bitPointer<<h.shift)` によって、ヒープビットマップの該当する位置に1つのポインタが存在することを示すビットが設定されます。これにより、GCは正確なポインタ情報を取得し、誤ったメモリ操作を防ぐことができます。

### `src/runtime/gcinfo_test.go` の変更

このファイルは、GCがオブジェクトのポインタ情報を正しく識別できることを検証するためのテストを含んでいます。

    `type Ptr struct { *byte }` という新しい構造体が定義されました。これは単一のポインタフィールドを持つシンプルな型です。
    `var infoPtr = []byte{typePointer}` は、`Ptr` 型のオブジェクトが1つのポインタを含むことを示す期待されるGC情報マスクです。

*   **`verifyGCInfo` の追加呼び出し**:
    `bss`, `data`, `heap` の各セクションに割り当てられた `Ptr` オブジェクトに対して `verifyGCInfo` が呼び出されます。これにより、これらのメモリ領域における単一ポインタのGC情報が正しく設定されているかが検証されます。

*   **`padDead` 関数**:
    このヘルパー関数は、32ビットシステム特有の割り当て挙動に対応するために導入されました。
    `if runtime.PtrSize == 4 && len(mask) == 1` の条件は、32ビットシステムで、かつ期待されるGC情報マスクが1つのポインタのみを示す場合（つまり、`Ptr` 型のような単一ポインタオブジェクトの場合）に適用されます。
    32ビットシステムでは、1ワード（4バイト）のオブジェクトが実際には2ワード（8バイト）のブロックに割り当てられることがあります。この場合、ヒープビットマップは8バイト全体をカバーするように設定されるため、テストの期待値もそれに合わせて調整する必要があります。
    `return []byte{mask[0], 0}` は、元の1ポインタのマスクに、追加のスカラーバイト（`0`）をパディングとして追加します。これにより、テストがランタイムの実際のヒープビットマップと正しく比較できるようになります。

*   **`const PtrSize = ptrSize`**:

*   **メモリ割り当て (Memory Allocation)**: プログラムが実行時にメモリを要求し、システムがその要求に応じてメモリ領域を確保するプロセスです。Goランタイムは、効率的なメモリ管理のために、特定のサイズのブロック単位でメモリを割り当てることがよくあります。
*   **`_type` 構造体**: Goの型システムにおける内部表現です。各型に関する情報（サイズ、アラインメント、ポインタ情報など）を含んでいます。GCはこの情報を使用して、オブジェクト内のどこにポインタがあるかを判断します。
*   **`heapBitsSetType` 関数**: Goランタイムの内部関数で、新しく割り当てられたヒープオブジェクトのヒープビットマップを設定する役割を担います。この関数は、オブジェクトの型情報に基づいて、どのワードがポインタであるかをビットマップにエンコードします。

## 技術的詳細

このコミットの核心は、32ビットシステムにおけるメモリ割り当ての特性とヒープビットマップの正確な設定の間の不整合を解消することにあります。

32ビットシステムでは `ptrSize` が4バイトです。しかし、Goランタイムのメモリ割り当て器は、効率のために最小の割り当て単位が `2*ptrSize` (8バイト) であることがあります。これは、アラインメント要件やキャッシュ効率の最適化のためです。

問題は、ユーザーが `new(Ptr)` のように単一のポインタ（4バイト）を割り当てた場合でも、ランタイムが実際には8バイトのメモリブロックを割り当てることがある点にありました。この8バイトブロックに対して、`heapBitsSetType` 関数がビットマップを設定する際に、オブジェクトの実際のサイズ (`dataSize`) ではなく、割り当てられたブロックのサイズ (`size`) に基づいて判断してしまうと、誤って2つのポインタが存在するとマークしてしまう可能性がありました。

このコミットでは、`src/runtime/mbitmap.go` の `heapBitsSetType` 関数に以下の修正が加えられました。

1.  **64ビットシステムでの単一ポインタ最適化の明確化**:
    `if size == ptrSize` の条件が `if ptrSize == 8 && size == ptrSize` に変更されました。これにより、`size == ptrSize` の最適化パスは64ビットシステム（`ptrSize == 8`）に限定されます。32ビットシステムでは、単一ポインタの割り当てでも `size` が `ptrSize` とは異なる（例えば `2*ptrSize`）可能性があるため、このパスを避ける必要があります。

2.  **32ビットシステムでの1ポインタ割り当ての特殊処理**:
    `if size == 2*ptrSize` のブロック内に、32ビットシステム (`ptrSize == 4`) かつ割り当てられたデータの実際のサイズが1ポインタ分 (`dataSize == ptrSize`) である場合の新しい条件が追加されました。
    ```go
    if ptrSize == 4 && dataSize == ptrSize {
        // 1 pointer.
        if gcphase == _GCoff {
            *h.bitp |= bitPointer << h.shift
        } else {
            atomicor8(h.bitp, bitPointer<<h.shift)
        }
    }
    ```
    このコードブロックは、32ビットシステムで8バイトのブロックが割り当てられたが、その中に実際には1つのポインタしか含まれていない場合に、ヒープビットマップを正しく1つのポインタとして設定します。これにより、GCが正確なポインタ情報を参照できるようになります。

`src/runtime/gcinfo_test.go` では、この修正を検証するために新しいテストケースが追加されました。
*   `Ptr` 型（単一ポインタを持つ構造体）が導入され、そのGC情報が `infoPtr` として定義されました。
*   `verifyGCInfo` 関数が、`bss`, `data`, `heap` 上の `Ptr` オブジェクトに対して呼び出され、GC情報が正しく設定されているかを確認します。
*   特に重要なのは `padDead` ヘルパー関数の導入です。これは、32ビットシステムで1ワードの割り当てが2ワードのブロックを使用する場合に、ヒープビットマップとテスト用の期待値の長さを合わせるために、追加のスカラーバイトでパディングを行う役割を果たします。これにより、テストが32ビットシステム特有の割り当て挙動を正しく考慮できるようになります。

`src/runtime/export_test.go` では、`PtrSize` 定数がエクスポートされ、テストコードからランタイムのポインタサイズにアクセスできるようになりました。これは、`gcinfo_test.go` の `padDead` 関数で `runtime.PtrSize` を使用するために必要です。

これらの変更により、32ビットシステム上でのGoプログラムのメモリ安全性とGCの正確性が向上しました。

## コアとなるコードの解説

### `src/runtime/mbitmap.go` の変更

`heapBitsSetType` 関数は、ヒープに割り当てられたオブジェクトのGCビットマップを設定する役割を担います。

*   **`if ptrSize == 8 && size == ptrSize`**:
    この変更は、以前の `if size == ptrSize` をより厳密にしました。64ビットシステム（`ptrSize == 8`）において、割り当てられたブロックのサイズがちょうど1ポインタ分である場合にのみ、この最適化パスが適用されることを保証します。32ビットシステムでは、1ポインタの割り当てでもより大きなブロックが使われる可能性があるため、このパスから除外されます。

*   **`if ptrSize == 4 && dataSize == ptrSize` ブロック**:
    これが32ビットシステムにおける主要な修正点です。
    `size == 2*ptrSize` の条件は、割り当てられたメモリブロックが2ポインタ分（32ビットシステムでは8バイト）であることを意味します。
    このブロック内で、さらに `ptrSize == 4` (32ビットシステムであること) かつ `dataSize == ptrSize` (実際に割り当てられたオブジェクトのサイズが1ポインタ分であること) という条件がチェックされます。
    この条件が真の場合、ランタイムは8バイトのブロックを割り当てたが、その中に含まれるポインタは1つだけであると判断します。
    `*h.bitp |= bitPointer << h.shift` または `atomicor8(h.bitp, bitPointer<<h.shift)` によって、ヒープビットマップの該当する位置に1つのポインタが存在することを示すビットが設定されます。これにより、GCは正確なポインタ情報を取得し、誤ったメモリ操作を防ぐことができます。

### `src/runtime/gcinfo_test.go` の変更

このファイルは、GCがオブジェクトのポインタ情報を正しく識別できることを検証するためのテストを含んでいます。

*   **`Ptr` 型と `infoPtr`**:
    `type Ptr struct { *byte }` という新しい構造体が定義されました。これは単一のポインタフィールドを持つシンプルな型です。
    `var infoPtr = []byte{typePointer}` は、`Ptr` 型のオブジェクトが1つのポインタを含むことを示す期待されるGC情報マスクです。

*   **`verifyGCInfo` の追加呼び出し**:
    `bss`, `data`, `heap` の各セクションに割り当てられた `Ptr` オブジェクトに対して `verifyGCInfo` が呼び出されます。これにより、これらのメモリ領域における単一ポインタのGC情報が正しく設定されているかが検証されます。

*   **`padDead` 関数**:
    このヘルパー関数は、32ビットシステム特有の割り当て挙動に対応するために導入されました。
    `if runtime.PtrSize == 4 && len(mask) == 1` の条件は、32ビットシステムで、かつ期待されるGC情報マスクが1つのポインタのみを示す場合（つまり、`Ptr` 型のような単一ポインタオブジェクトの場合）に適用されます。
    32ビットシステムでは、1ワード（4バイト）のオブジェクトが実際には2ワード（8バイト）のブロックに割り当てられることがあります。この場合、ヒープビットマップは8バイト全体をカバーするように設定されるため、テストの期待値もそれに合わせて調整する必要があります。
    `return []byte{mask[0], 0}` は、元の1ポインタのマスクに、追加のスカラーバイト（`0`）をパディングとして追加します。これにより、テストがランタイムの実際のヒープビットマップと正しく比較できるようになります。

### `src/runtime/export_test.go` の変更

*   **`const PtrSize = ptrSize`**:
    ランタイム内部の `ptrSize` 定数（ポインタのバイトサイズ）をテストコードからアクセスできるようにエクスポートしました。これにより、`gcinfo_test.go` の `padDead` 関数で `runtime.PtrSize` を使用して、現在のシステムが32ビットか64ビットかを判断できるようになりました。

これらの変更は、GoランタイムのGCが32ビットシステム上でもメモリ内のポインタを正確に識別し、メモリ安全性を維持するために不可欠です。

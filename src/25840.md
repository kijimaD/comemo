# [インデックス 25840] ファイルの概要

このコミットは、Go言語の正規表現エンジンにおける`LiteralPrefix`関数のバグ修正に関するものです。具体的には、`onepass`最適化パスを使用する正規表現において、リテラルプレフィックスの検出が不正確であった問題を解決します。

## 元コミット内容

このコミットは、Go言語の正規表現パッケージ（`regexp`）における`LiteralPrefix`関数の挙動を修正します。`onepass`最適化が適用される正規表現プログラムにおいて、正規表現の途中に「テキストの先頭に一致する空幅マッチ（`^`）」が存在する場合に、`LiteralPrefix`が誤って`complete=true`を返してしまうバグがありました。

この修正は、`complete`が`true`を返す条件を厳格化することで行われます。具体的には、リテラルプレフィックスの後に「テキストの末尾に一致する空幅マッチ（`$`）」が続き、その後に「マッチ成功状態」が続く場合にのみ`complete=true`を返すように変更されました。これにより、正規表現の途中に現れる`^`が誤って完全なプレフィックスと判断されることがなくなります。

この修正は、Issue #11175で報告された問題を解決します。

## 変更の背景

Goの正規表現エンジンは、パフォーマンス向上のために様々な最適化を適用します。その一つが「`onepass`」最適化です。これは、正規表現が決定性オートマトン（DFA）として効率的に実行できる場合に適用され、マッチング処理を高速化します。

`LiteralPrefix`関数は、正規表現がマッチングを開始する前に、パターンが持つ固定の先頭文字列（リテラルプレフィックス）を特定するために使用されます。例えば、正規表現が`"abc.*"`であれば、リテラルプレフィックスは`"abc"`です。このプレフィックスが特定できると、正規表現エンジンは文字列全体をスキャンする代わりに、まずこのプレフィックスを効率的に検索し、その位置から本格的な正規表現マッチングを開始できます。これにより、特に長い文字列に対して大きなパフォーマンス改善が期待できます。

`complete`というフラグは、このリテラルプレフィックスが正規表現全体をカバーしているかどうかを示します。例えば、`"abc"`という正規表現の場合、リテラルプレフィックスは`"abc"`であり、`complete`は`true`になります。しかし、`"abc.*"`の場合、リテラルプレフィックスは`"abc"`ですが、`complete`は`false`になります。

報告されたバグ（Issue #11175）は、`onepass`最適化が適用される特定の正規表現において、`LiteralPrefix`がこの`complete`フラグを誤って設定してしまうというものでした。具体的には、正規表現の途中に`^`（テキストの先頭）のような空幅アサーションがある場合に、それがリテラルプレフィックスの「完全性」を誤って示唆してしまうことが問題でした。これは、正規表現のセマンティクスと`LiteralPrefix`の目的（固定文字列による高速な事前フィルタリング）との間に不整合を生じさせ、予期せぬマッチング結果やパフォーマンス特性につながる可能性がありました。

このバグは、正規表現の正確性と信頼性を確保するために修正が必要でした。

## 前提知識の解説

### 正規表現 (Regular Expression)
正規表現は、文字列のパターンを記述するための強力なツールです。Go言語の`regexp`パッケージは、RE2という高速な正規表現エンジンに基づいています。

### 正規表現の構文要素
*   **リテラル文字列**: `abc` のように、そのままの文字列にマッチします。
*   **メタ文字**: 特殊な意味を持つ文字です。
    *   `^`: 行（またはテキスト）の先頭にマッチするアンカー（空幅アサーション）。
    *   `$`: 行（またはテキスト）の末尾にマッチするアンカー（空幅アサーション）。
    *   `.`: 任意の一文字にマッチします（改行を除く）。
    *   `*`: 直前の要素が0回以上繰り返されることにマッチします。
*   **空幅アサーション (Zero-width assertion)**: 文字を消費せずに、特定の位置条件にマッチするパターンです。`^`や`$`がこれに該当します。

### 正規表現エンジンと最適化
正規表現エンジンは、与えられたパターンを内部的に「プログラム」（オートマトン）に変換してマッチングを行います。
*   **NFA (Non-deterministic Finite Automaton)**: 非決定性有限オートマトン。多くの正規表現エンジンで使われる基本的なモデルですが、バックトラッキングが発生しやすく、最悪計算量が指数関数的になることがあります。
*   **DFA (Deterministic Finite Automaton)**: 決定性有限オートマトン。NFAよりも高速で、線形時間でマッチングが完了しますが、NFAで表現できる全てのパターンをDFAで直接表現できるわけではありません（特にバックリファレンスなど）。GoのRE2エンジンは、NFAをDFAに変換して実行することで高速化を図っています。

### `onepass`最適化
Goの`regexp`パッケージにおける`onepass`は、正規表現がDFAとして効率的に実行できる場合に適用される最適化パスです。これにより、マッチング処理が単一のパスで完了し、非常に高速になります。この最適化は、特にシンプルな正規表現や、先頭から順にマッチングを進められるパターンで効果を発揮します。

### `syntax.Prog`と`syntax.Inst`
Goの`regexp`パッケージ内部では、正規表現パターンは`syntax.Prog`という構造体で表現される「プログラム」にコンパイルされます。このプログラムは、`syntax.Inst`（Instruction、命令）のリストで構成されており、各命令は正規表現オートマトンの状態遷移やマッチング操作を表します。
*   `syntax.InstEmptyWidth`: 空幅アサーションを表す命令。
*   `syntax.EmptyBeginText`: `^`（テキストの先頭）に対応する空幅アサーションのフラグ。
*   `syntax.EmptyEndText`: `$`（テキストの末尾）に対応する空幅アサーションのフラグ。
*   `syntax.InstMatch`: マッチ成功状態を表す命令。

### `LiteralPrefix`関数
`LiteralPrefix`関数は、正規表現パターンから固定の先頭文字列（リテラルプレフィックス）を抽出し、そのプレフィックスが正規表現全体をカバーしているかどうかを示す`complete`フラグを返します。これは、マッチングの高速化のための重要なヒューリスティックです。

## 技術的詳細

このコミットの核心は、`src/regexp/onepass.go`内の`onePassPrefix`関数のロジック変更にあります。この関数は、`onepass`最適化が可能な正規表現プログラムに対して、リテラルプレフィックスを計算する役割を担っています。

変更前のコードでは、`onePassPrefix`関数は、リテラルプレフィックスを構築した後、現在の命令（`i`）が`syntax.InstEmptyWidth`であり、かつその空幅アサーションが`syntax.EmptyBeginText`（`^`）である場合に、`complete`を`true`と判断していました。

```go
// 変更前
return buf.String(), i.Op == syntax.InstEmptyWidth && (syntax.EmptyOp(i.Arg))&syntax.EmptyBeginText != 0, pc
```

このロジックの問題点は、正規表現の途中に`^`が現れた場合でも`complete=true`を返してしまう可能性があったことです。例えば、`"abc^def"`のようなパターンでは、`"abc"`がリテラルプレフィックスとして抽出されるべきですが、`^`が途中に存在するため、`complete`の判断が誤る可能性がありました。`^`はテキストの先頭にのみマッチするアサーションであり、正規表現の途中で現れることは、その正規表現が「固定のプレフィックスで完全にマッチする」ことを意味しません。

修正後のコードでは、`complete`が`true`となる条件がより厳格になりました。

```go
// 変更後
if i.Op == syntax.InstEmptyWidth &&
	syntax.EmptyOp(i.Arg)&syntax.EmptyEndText != 0 &&
	p.Inst[i.Out].Op == syntax.InstMatch {
	complete = true
}
return buf.String(), complete, pc
```

この新しいロジックは、以下の3つの条件がすべて満たされた場合にのみ`complete`を`true`に設定します。
1.  現在の命令`i`が`syntax.InstEmptyWidth`であること。
2.  その空幅アサーションが`syntax.EmptyEndText`（`$`、テキストの末尾）であること。
3.  `$`の直後の命令（`p.Inst[i.Out]`）が`syntax.InstMatch`（マッチ成功）であること。

これにより、リテラルプレフィックスが正規表現全体をカバーしていると判断されるのは、そのプレフィックスが文字列の末尾（`$`）に続き、かつその`$`が正規表現の最終的なマッチ成功状態に直接つながる場合のみとなります。これは、`"abc$"`のような正規表現が`"abc"`というリテラルプレフィックスを持ち、かつ`complete=true`となるべきケースを正確に捉えます。

この変更により、正規表現の途中に現れる`^`のような空幅アサーションが、`LiteralPrefix`の`complete`フラグに誤った影響を与えることがなくなりました。

## コアとなるコードの解説

`onePassPrefix`関数は、正規表現プログラム`p`からリテラルプレフィックスを抽出し、そのプレフィックス文字列、それが正規表現全体をカバーしているかを示す`complete`フラグ、そしてプレフィックスの終端に対応するプログラムカウンタ`pc`を返します。

変更のあった部分を詳しく見てみましょう。

```go
// 変更前:
// return buf.String(), i.Op == syntax.InstEmptyWidth && (syntax.EmptyOp(i.Arg))&syntax.EmptyBeginText != 0, pc

// 変更後:
if i.Op == syntax.InstEmptyWidth &&
	syntax.EmptyOp(i.Arg)&syntax.EmptyEndText != 0 &&
	p.Inst[i.Out].Op == syntax.InstMatch {
	complete = true
}
return buf.String(), complete, pc
```

1.  **`buf.String()`**: これは、正規表現の先頭から抽出されたリテラル文字列の部分です。例えば、`"abc.*"`であれば`"abc"`がこれに該当します。
2.  **`complete`フラグの計算（変更前）**:
    *   `i.Op == syntax.InstEmptyWidth`: 現在の命令が空幅アサーションであるか。
    *   `(syntax.EmptyOp(i.Arg))&syntax.EmptyBeginText != 0`: その空幅アサーションが`^`（テキストの先頭）であるか。
    *   これらの条件が満たされると、`complete`は`true`とされていました。これが問題でした。正規表現の途中に`^`があっても、それはリテラルプレフィックスが正規表現全体をカバーしていることを意味しないためです。

3.  **`complete`フラグの計算（変更後）**:
    *   `i.Op == syntax.InstEmptyWidth`: 現在の命令が空幅アサーションであるか。
    *   `syntax.EmptyOp(i.Arg)&syntax.EmptyEndText != 0`: その空幅アサーションが`$`（テキストの末尾）であるか。
    *   `p.Inst[i.Out].Op == syntax.InstMatch`: `$`の直後の命令がマッチ成功状態であるか。
    *   これらの3つの条件がすべて満たされた場合にのみ、`complete`が`true`に設定されます。これは、リテラルプレフィックスが正規表現全体をカバーし、かつその正規表現が文字列の末尾で終了する（例: `"abc$"`）という、`complete=true`が適切であるケースを正確に表現しています。

この修正により、`LiteralPrefix`関数は、正規表現のセマンティクスに合致した正確な`complete`フラグを返すようになり、`onepass`最適化の信頼性が向上しました。

# [インデックス 20045] ファイルの概要

このコミットは、Go言語のツールチェインの一部である`cmd/9a`アセンブラのソースコードファイル`src/cmd/9a/lex.c`に対する変更です。`cmd/9a`は、Plan 9アーキテクチャ（特にこの場合はpower64）向けのアセンブラであり、Goのビルドプロセスにおいてアセンブリ言語のソースファイルをオブジェクトファイルに変換する役割を担っています。

## 元コミット内容

このコミットは、`cmd/9a`アセンブラにおいて、コマンドライン引数の解析方法を新しいフラグパーサーを使用するように変更するものです。主な目的は、`go`コマンドが`-trimpath`のような複数文字のフラグを正しく解釈できるようにすることです。以前のパーサーでは、`-trimpath`が`-t`と`rimpath`に誤って解釈される可能性がありました。また、`cmd/6a`（x86アセンブラ）の`main`関数からコードをコピーすることで、他のアセンブラとのコードの統一性も図られています。

## 変更の背景

Go言語のツールチェインは、様々なアーキテクチャに対応するために、それぞれのアセンブラ（例: `6a` for x86, `8a` for ARM, `9a` for PowerPC/Power64）を持っています。これらのアセンブラは、歴史的にPlan 9のツールチェインから派生しており、独自のコマンドライン引数解析メカニズムを持っていました。

従来の引数解析は、`ARGBEGIN`/`ARGEND`というマクロを用いたシンプルなものでした。これは主に単一文字のオプション（例: `-o`）を処理するのに適していましたが、`-trimpath`のような複数文字のオプションや、より複雑なフラグの定義には不十分でした。

特に、Go 1.3で導入された`-trimpath`フラグは、ビルド時にソースファイルの絶対パス情報をバイナリから削除し、再現可能なビルドを可能にするための重要な機能です。しかし、従来のパーサーでは、`-trimpath`が`-t`オプションとそれに続く引数`rimpath`として誤って解釈される可能性があり、これは`go`コマンドの期待する動作と異なりました。

この問題を解決し、将来的なフラグの追加や変更に柔軟に対応できるようにするため、より堅牢で標準的なフラグ解析メカニズムへの移行が必要とされました。このコミットは、`cmd/6a`で既に採用されていた新しいフラグパーサーのロジックを`cmd/9a`に適用することで、この課題に対処しています。

## 前提知識の解説

1.  **Go言語のツールチェインとアセンブラ (`cmd/9a`)**:
    *   Go言語は、ソースコードをコンパイルして実行可能なバイナリを生成する際に、コンパイラ、リンカ、アセンブラなどのツールチェインを使用します。
    *   `cmd/9a`は、Goの標準ライブラリやユーザーコードに含まれるアセンブリ言語のソースファイル（`.s`拡張子）を、特定のアーキテクチャ（この場合はPowerPC/Power64）向けのオブジェクトファイルに変換するアセンブラです。
    *   Goのツールチェインのアセンブラは、Plan 9オペレーティングシステムのツールチェインから派生しており、その設計思想や一部のコードベースを共有しています。

2.  **コマンドライン引数解析のメカニズム**:
    *   **`ARGBEGIN`/`ARGEND`マクロ**: これはPlan 9のツールチェインで伝統的に使用されてきた、非常にシンプルなコマンドライン引数解析のためのマクロです。`ARGBEGIN`と`ARGEND`の間に`case`文を記述することで、`-c`のような単一文字オプションを処理します。しかし、`-longflag`のような複数文字のオプションや、`--flag=value`のような形式には直接対応していません。`-trimpath`のようなフラグが`-t`と`rimpath`に分割されてしまうのは、このマクロの単純な文字ベースの解析に起因します。
    *   **新しいフラグパーサー**: Go言語の標準ライブラリには`flag`パッケージがあり、より堅牢で柔軟なコマンドライン引数解析を提供します。このコミットで導入された「新しいフラグパーサー」は、`flag`パッケージの概念に似た、より構造化された内部実装を指していると考えられます。これは、オプション名全体を認識し、その値（存在する場合）を適切に抽出することができます。

3.  **`-trimpath`フラグ**:
    *   Go 1.3で導入されたビルドフラグの一つです。
    *   このフラグを使用すると、Goコンパイラは生成されるバイナリファイルに埋め込まれるソースファイルのパス情報を、ビルド時の絶対パスではなく、モジュールルートからの相対パス、または完全に削除された形式で記録します。
    *   これにより、異なる環境で同じソースコードからビルドされたバイナリが、パス情報に関して同一になる（再現可能なビルド）という利点があります。また、バイナリサイズをわずかに削減したり、デバッグ情報から機密性の高いパス情報を隠蔽したりする効果もあります。
    *   このフラグが正しく解析されないと、再現可能なビルドの恩恵を受けられなくなったり、ビルドプロセスが予期せぬエラーを起こしたりする可能性があります。

4.  **`GOARCH`環境変数**:
    *   Go言語のクロスコンパイルにおいて、ターゲットとするCPUアーキテクチャを指定するために使用される環境変数です。
    *   例えば、`GOARCH=amd64`はx86-64アーキテクチャを、`GOARCH=arm`はARMアーキテクチャを、`GOARCH=power64`はPowerPC 64-bitアーキテクチャをそれぞれ指定します。
    *   アセンブラは、この`GOARCH`の値に基づいて、適切なアーキテクチャ固有のコード生成ロジックを選択します。

## 技術的詳細

このコミットの核心は、`src/cmd/9a/lex.c`の`main`関数におけるコマンドライン引数解析ロジックの全面的な置き換えです。

**変更前（従来の`ARGBEGIN`/`ARGEND`ベースの解析）**:

```c
// 変更前のmain関数の一部
ARGBEGIN {
default:
    c = ARGC();
    if(c >= 0 && c < sizeof(debug))
        debug[c] = 1;
    break;

case 'o':
    outfile = ARGF();
    break;

case 'D':
    p = ARGF();
    if(p) {
        if (nDlist%8 == 0)
            Dlist = allocn(Dlist, nDlist*sizeof(char *), 
                8*sizeof(char *));
        Dlist[nDlist++] = p;
    }
    break;

case 'I':
    p = ARGF();
    setinclude(p);
    break;

case 'S':
    ctxt->debugasm++;
    break;
} ARGEND
```

このコードは、`ARGBEGIN`と`ARGEND`マクロに囲まれたブロック内で、`ARGC()`（現在のオプション文字を取得）、`ARGF()`（オプションの引数を取得）といったマクロを使って引数を処理していました。`default`ケースは、認識されない単一文字オプションを`debug`配列のインデックスとして扱うという、Plan 9ツールチェイン特有の挙動を示しています。

この方式の主な問題点は以下の通りです。
*   **複数文字オプションの不正確な解析**: `-trimpath`のようなオプションが来た場合、`ARGBEGIN`はまず`-t`を認識し、残りの`rimpath`を次の引数として扱ってしまう可能性があります。これにより、`-trimpath`が正しく一つのフラグとして認識されません。
*   **柔軟性の欠如**: 新しいフラグを追加する際に、`case`文を増やすだけであり、型チェックやデフォルト値、ヘルプメッセージの自動生成といった高度な機能は提供されません。
*   **エラーハンドリングの単純さ**: 不正な引数や不足している引数に対するエラー処理が手動で、かつ限定的です。

**変更後（新しいフラグパーサーの使用）**:

```c
// 変更後のmain関数の一部
flagfn1("D", "name[=value]: add #define", dodef);
flagfn1("I", "dir: add dir to include path", setinclude);
flagcount("S", "print assembly and machine code", &debug['S']);
flagcount("m", "debug preprocessor macros", &debug['m']);
flagstr("o", "file: set output file", &outfile);
flagstr("trimpath", "prefix: remove prefix from recorded source file paths", &ctxt->trimpath);

flagparse(&argc, &argv, usage);
ctxt->debugasm = debug['S']; // 'S'フラグの値を反映
```

新しいフラグパーサーは、以下のような関数群を提供します。
*   `flagfn1(name, usage, func)`: 特定のフラグ（例: `D`, `I`）が指定されたときに呼び出される関数`func`を登録します。`dodef`は`-D`オプションの引数を処理し、`setinclude`は`-I`オプションの引数を処理します。
*   `flagcount(name, usage, *int_var)`: 特定のフラグ（例: `S`, `m`）が指定されるたびに、指定された整数変数`*int_var`の値をインクリメントします。これにより、フラグの出現回数をカウントしたり、ブール値として扱ったりできます。
*   `flagstr(name, usage, *string_var)`: 文字列引数を取るフラグ（例: `o`, `trimpath`）を定義し、その値を指定された文字列変数`*string_var`に格納します。特に注目すべきは、`"trimpath"`という複数文字のフラグが直接サポートされている点です。

これらの関数でフラグを定義した後、`flagparse(&argc, &argv, usage)`を呼び出すことで、実際のコマンドライン引数解析が実行されます。`usage`関数は、解析エラーが発生した場合やヘルプが要求された場合に、使用方法のメッセージを表示するために使用されます。

この新しいアプローチにより、以下の利点が得られます。
*   **複数文字オプションの正確な解析**: `-trimpath`のようなフラグが正しく一つの単位として認識され、その値が`ctxt->trimpath`に適切に格納されます。
*   **構造化されたフラグ定義**: 各フラグの目的（usageメッセージ）、型、関連する変数やコールバック関数が明確に定義されます。
*   **堅牢なエラーハンドリング**: パーサーが不正な引数や形式を自動的に検出し、`usage`関数を呼び出すことで一貫したエラーメッセージを提供します。
*   **コードの再利用性**: `cmd/6a`から`main`関数をコピーしたという記述から、この新しいフラグパーサーのロジックがGoツールチェイン内の他のアセンブラやツールで共通化されていることが示唆されます。

また、`GOARCH`の処理も変更されています。
変更前:
```c
thestring = getgoarch();
if(strcmp(thestring, "power64le") == 0)
    ctxt = linknew(&linkpower64le);
else
    ctxt = linknew(&linkpower64);
```
変更後:
```c
thestring = "power64"; // thestringを固定値に
// ...
p = getgoarch();
if(strncmp(p, thestring, strlen(thestring)) != 0)
    sysfatal("cannot use %cc with GOARCH=%s", thechar, p);
if(strcmp(p, "power64le") == 0)
    thelinkarch = &linkpower64le;
// ...
ctxt = linknew(thelinkarch);
```
これは、`thestring`が常に`"power64"`であることを保証しつつ、`getgoarch()`で取得した実際の`GOARCH`値が`"power64"`で始まることを検証しています。これにより、`power64le`のような派生アーキテクチャも正しく扱いつつ、不正な`GOARCH`値に対するチェックが強化されています。

さらに、出力ファイル名の決定ロジックも変更され、より堅牢になっています。特に、`outfile`が指定されていない場合のデフォルトの出力ファイル名生成において、既存のファイル名から拡張子を適切に処理し、アセンブラの出力拡張子（`.9`など）を付与するロジックが改善されています。

## コアとなるコードの変更箇所

`src/cmd/9a/lex.c`ファイルの`main`関数内における、コマンドライン引数解析部分が大きく変更されています。

1.  **旧来の`ARGBEGIN`/`ARGEND`ブロックの削除**:
    約50行にわたる`ARGBEGIN { ... } ARGEND`のブロックが完全に削除されています。

2.  **新しいフラグ定義関数の追加**:
    削除されたブロックの代わりに、以下のフラグ定義関数が追加されています。
    *   `flagfn1("D", ..., dodef);`
    *   `flagfn1("I", ..., setinclude);`
    *   `flagcount("S", ..., &debug['S']);`
    *   `flagcount("m", ..., &debug['m']);`
    *   `flagstr("o", ..., &outfile);`
    *   `flagstr("trimpath", ..., &ctxt->trimpath);`

3.  **フラグ解析の実行**:
    `flagparse(&argc, &argv, usage);`の呼び出しが追加され、実際の引数解析がこの関数に委ねられています。

4.  **`GOARCH`環境変数の処理ロジックの変更**:
    `main`関数の冒頭で、`thestring`の初期化と`GOARCH`の検証ロジックが変更されています。

5.  **出力ファイル名生成ロジックの変更**:
    `assemble`関数内で、出力ファイル名（`ofile`）の生成と、デフォルトの出力ファイル名（`outfile`）の決定ロジックが変更されています。特に、`.s`拡張子の処理や、`thechar`（アセンブラの種類を示す文字、例: `9`）の付与方法が修正されています。

## コアとなるコードの解説

このコミットの最も重要な変更は、コマンドライン引数解析のパラダイムシフトです。

従来の`ARGBEGIN`/`ARGEND`は、C言語のマクロプリプロセッサを駆使した、非常に低レベルで手続き的な引数解析でした。これは、引数を文字単位で見て、特定の文字（例: `-o`の`o`）にマッチした場合に、その後の引数（`ARGF()`）を読み取るという単純なロジックでした。この方式では、`-trimpath`のような複数文字のフラグを一つの単位として認識することが困難であり、`-t`と`rimpath`に誤って分割される可能性がありました。これは、`go`コマンドが`-trimpath`を正しくアセンブラに渡すことを期待しているにもかかわらず、アセンブラ側で正しく解釈できないという問題を引き起こしていました。

新しいフラグパーサーは、より宣言的なアプローチを採用しています。`flagfn1`, `flagcount`, `flagstr`といった関数を呼び出すことで、各フラグの名前、期待される引数の型（文字列、カウント）、そしてそのフラグが解析されたときに実行されるべきアクション（コールバック関数や変数の更新）を明示的に定義します。

特に、`flagstr("trimpath", ..., &ctxt->trimpath);`の追加は、`-trimpath`という複数文字のフラグが、その名前全体で認識され、その値が`ctxt->trimpath`という変数に格納されることを保証します。これにより、従来のパーサーが抱えていた「`-t`と`rimpath`に誤解釈される」という問題が根本的に解決されます。

`flagparse(&argc, &argv, usage);`の呼び出しは、定義されたフラグに基づいて実際のコマンドライン引数を解析し、定義されていないフラグや不正な形式の引数があった場合には、`usage`関数を呼び出して適切なエラーメッセージを表示します。これにより、引数解析の堅牢性とユーザーフレンドリーさが向上します。

`GOARCH`の処理変更は、`cmd/9a`が`power64`アーキテクチャのアセンブラであることをより厳密に強制しつつ、`power64le`（little-endian）のような派生形も正しく扱えるようにするためのものです。これにより、アセンブラが意図しないアーキテクチャで実行されることを防ぎ、ビルドの信頼性を高めます。

全体として、このコミットは`cmd/9a`のコマンドライン引数解析を現代化し、Goツールチェイン全体の整合性と堅牢性を向上させるための重要なステップです。これにより、`-trimpath`のような新しいビルドフラグがGoツールチェイン全体で一貫して機能するようになります。

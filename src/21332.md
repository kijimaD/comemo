# [インデックス 21332] ファイルの概要

このコミットは、Goランタイムにおけるフォールバックハッシュ関数を改善することを目的としています。特に、AES命令を持たないx86アーキテクチャ、ARM、およびPowerPCアーキテクチャ向けに、より高速で高品質なハッシュ関数を導入しています。これにより、ハッシュテーブルのパフォーマンスと安定性が向上します。

## 元コミット内容

Goランタイムにおけるフォールバックハッシュ関数を改善する。これは、ARM、PowerPC、およびAES命令を持たないx86アーキテクチャ向けのものである。CityHashとxxHashのアイデアを組み合わせたものとなっている。

ARM上の古いフォールバックハッシュと比較して、小さなオブジェクトでは速度はほぼ変わらず、大きなオブジェクトでは最大50%高速化されている。さらに重要なのは、ハッシュ関数としての品質が大幅に向上し、ハッシュ衝突による予期せぬ動作のリスクが低減されたことである。

この変更はIssue #8737を修正する。

ベンチマーク結果は以下の通り：
- `BenchmarkHash5`: 173 ns/op -> 181 ns/op (+4.62%)
- `BenchmarkHash16`: 252 ns/op -> 212 ns/op (-15.87%)
- `BenchmarkHash64`: 575 ns/op -> 419 ns/op (-27.13%)
- `BenchmarkHash1024`: 7173 ns/op -> 3995 ns/op (-44.31%)
- `BenchmarkHash65536`: 516940 ns/op -> 313173 ns/op (-39.42%)
- `BenchmarkHashStringSpeed`: 300 ns/op -> 279 ns/op (-7.00%)
- `BenchmarkHashBytesSpeed`: 478 ns/op -> 424 ns/op (-11.30%)
- `BenchmarkHashInt32Speed`: 217 ns/op -> 207 ns/op (-4.61%)
- `BenchmarkHashInt64Speed`: 262 ns/op -> 231 ns/op (-11.83%)
- `BenchmarkHashStringArraySpeed`: 609 ns/op -> 631 ns/op (+3.61%)

## 変更の背景

Go言語のランタイムは、`map`などの組み込みデータ構造の効率的な動作をサポートするためにハッシュ関数を内部的に使用しています。特定のCPUアーキテクチャ（特にAES命令セットを持たないもの）では、ハッシュ計算のパフォーマンスがボトルネックとなる可能性がありました。既存のフォールバックハッシュ関数は、ハッシュ品質と速度の両面で改善の余地がありました。

このコミットは、以下の課題に対処するために行われました。
1.  **パフォーマンスの向上**: 特に大きなデータブロックに対するハッシュ計算の速度を向上させる。
2.  **ハッシュ品質の向上**: ハッシュ衝突の可能性を減らし、ハッシュテーブルの最悪ケースの動作を防ぐ。これにより、`map`のパフォーマンスがより予測可能で安定したものになります。
3.  **アーキテクチャ固有の最適化**: AES命令が利用できない環境（ARM, PowerPC, 一部のx86）において、より効率的なハッシュアルゴリズムを提供します。

Issue #8737は、ハッシュ関数の品質が不十分であることによるパフォーマンスの問題や、特定の入力パターンでハッシュ衝突が頻発する可能性を示唆していたと考えられます。

## 前提知識の解説

### ハッシュ関数

ハッシュ関数は、任意のサイズのデータを固定サイズのデータ（ハッシュ値またはハッシュコード）に変換する関数です。理想的なハッシュ関数は、異なる入力に対して異なるハッシュ値を生成し、ハッシュ値が均等に分布するように設計されます。Go言語の`map`（ハッシュマップ）のようなデータ構造では、キーをハッシュ値に変換して、そのハッシュ値に基づいてデータを格納・検索します。

### 非暗号学的ハッシュ関数

このコミットで言及されているCityHashやxxHashは、「非暗号学的ハッシュ関数」に分類されます。これらは、データの完全性やセキュリティを保証する暗号学的ハッシュ関数（例: SHA-256）とは異なり、主に高速なデータ検索や比較のために設計されています。そのため、衝突耐性よりも速度とハッシュ値の均等な分布が重視されます。

### CityHash

Googleが開発した非暗号学的ハッシュ関数ファミリーです。文字列やその他のデータ型を高速かつ効率的にハッシュするために設計されています。特に、64ビットレジスタや命令レベルの並列処理など、現代のCPUアーキテクチャに最適化されています。高速性と優れたハッシュ値の分布が特徴ですが、暗号学的に安全ではありません。

### xxHash

非常に高速な非暗号学的ハッシュアルゴリズムで、RAMの速度限界に近い、あるいはそれ以上の速度で動作するとされています。ハッシュテーブル、データフィンガープリンティング、ルックアップ操作など、生の処理性能が重要なシナリオ向けに設計されています。高い移植性を持ち、異なるプラットフォーム間で同じハッシュ値を生成します。SMHasherテストスイートをクリアする高いハッシュ品質も特徴です。

### Goランタイムのハッシュメカニズム

Go言語では、`map`のキーのハッシュ計算はランタイムによって行われます。Go 1.19以降では`maphash`パッケージを通じてAESベースのハッシュ関数が公開されていますが、このコミットが行われた2014年時点では、ランタイム内部でハッシュ関数が管理されていました。Goのハッシュ関数は、コンパイラによって生成される場合があり、利用可能なハードウェア命令（例: AES-NI）を最大限に活用するように最適化されます。AES命令が利用できない環境では、ソフトウェアによるフォールバックハッシュ関数が使用されます。

### アラインメントとアンアラインドアクセス

メモリのアラインメントとは、データが特定のメモリアドレス境界に配置されることを指します。例えば、4バイトの整数は4の倍数のアドレスに配置されるのが一般的です。CPUによっては、アラインされていないアドレスからのデータ読み書き（アンアラインドアクセス）が遅かったり、エラーになったりする場合があります。このコミットでは、`readUnaligned32`や`readUnaligned64`といった関数が導入されており、これはメモリからアラインメントを気にせずにデータを読み取るためのものです。これにより、ハッシュ計算の際にデータのコピーを減らし、パフォーマンスを向上させることができます。

## 技術的詳細

このコミットの主要な変更点は、Goランタイムの`memhash`関数、つまりメモリブロックのハッシュを計算するフォールバックアルゴリズムの置き換えです。

### 新しいハッシュアルゴリズムの設計思想

新しいハッシュアルゴリズムは、CityHashとxxHashのアイデアを組み合わせたものです。これらのハッシュ関数は、以下の特徴を持っています。
-   **高速な乗算とビット演算**: データの混合を効率的に行うために、特定の定数による乗算とビットシフト（特にローテートシフト）を多用します。
-   **パイプライン処理**: 複数のハッシュ状態変数（`v1`, `v2`, `v3`, `v4`など）を並行して更新することで、CPUのパイプラインを最大限に活用し、スループットを向上させます。
-   **データサイズに応じた処理**: 入力データのサイズ（例: 4バイト未満、4バイト、8バイト、16バイト、それ以上）に応じて、異なる処理パスを提供します。これにより、小さなデータではオーバーヘッドを最小限に抑え、大きなデータでは効率的なループ処理を行います。
-   **最終的なミキシング**: 複数のハッシュ状態変数を最終的に結合し、さらにビットシフトと乗算を適用して、ハッシュ値の均等な分布を保証します。

### アーキテクチャ固有の実装

このコミットでは、32ビットアーキテクチャ（`386`, `arm`）と64ビットアーキテクチャ（`amd64`, `amd64p32`, `ppc64`, `ppc64le`）向けに、それぞれ異なるハッシュ関数が導入されています。
-   `src/runtime/hash32.go`: 32ビットアーキテクチャ向けの`memhash`を実装しています。32ビットの定数`m1`から`m4`を使用し、`rotl_15`と`rotl_11`といった32ビットのローテートシフト関数を定義しています。
-   `src/runtime/hash64.go`: 64ビットアーキテクチャ向けの`memhash`を実装しています。64ビットの定数`m1`から`m4`を使用し、`rotl_31`と`rotl_27`といった64ビットのローテートシフト関数を定義しています。

これらのファイルは、ビルドタグ（`+build 386 arm`など）によって、特定のアーキテクチャでのみコンパイルされるようになっています。

### アンアラインド読み込みの導入

新しいハッシュ関数は、メモリからデータを読み込む際に、アラインメントを気にしない読み込み（アンアラインド読み込み）を利用しています。これは、データのコピーを避けて直接メモリからバイト列を読み込むことで、パフォーマンスを向上させるためです。
-   `src/runtime/unaligned1.go`: `386`, `amd64`, `amd64p32`といった、CPUがハードウェアレベルでアンアラインドアクセスを効率的に処理できるアーキテクチャ向けに、単純なポインタキャストによる`readUnaligned32`と`readUnaligned64`を実装しています。
-   `src/runtime/unaligned2.go`: `arm`, `ppc64`, `ppc64le`といった、アンアラインドアクセスが遅い、あるいはサポートされていないアーキテクチャ向けに、バイト単位で手動でデータを読み込み、結合する`readUnaligned32`と`readUnaligned64`を実装しています。これにより、これらのアーキテクチャでも安全かつ効率的にアンアラインドデータを処理できます。

### ベンチマーク結果の分析

コミットメッセージに含まれるベンチマーク結果は、新しいハッシュ関数の効果を明確に示しています。
-   `BenchmarkHash5` (5バイトのハッシュ): わずかに遅くなっています (+4.62%)。これは、新しいアルゴリズムが小さなデータに対しては、より複雑な初期化や最終処理のオーバーヘッドがあるためと考えられます。
-   `BenchmarkHash16`から`BenchmarkHash65536` (16バイトから65536バイトのハッシュ): データサイズが大きくなるにつれて、顕著な速度向上が見られます（-15.87%から-44.31%）。これは、新しいアルゴリズムが大きなデータブロックに対して、より効率的なループ処理と並列処理（複数のハッシュ状態変数）を行っているためです。
-   `BenchmarkHashStringSpeed`, `BenchmarkHashBytesSpeed`, `BenchmarkHashInt32Speed`, `BenchmarkHashInt64Speed`: これらのベンチマークも、全体的に速度が向上しています。
-   `BenchmarkHashStringArraySpeed`: わずかに遅くなっています (+3.61%)。これは、文字列配列のハッシュが、個々の文字列のハッシュと配列構造のハッシュの組み合わせであり、個々の文字列が小さい場合に`BenchmarkHash5`と同様のオーバーヘッドの影響を受ける可能性があるためと考えられます。

全体として、この変更は特に大きなデータに対するハッシュ計算のパフォーマンスを大幅に改善し、ハッシュ関数の品質も向上させています。

## コアとなるコードの解説

### `src/runtime/alg.go`の変更

以前の`memhash`関数は、単純なバイト単位のXORと乗算のループを使用していました。これは非常に基本的なハッシュ関数であり、ハッシュ衝突の可能性が高く、パフォーマンスも最適ではありませんでした。このコミットでは、この古い実装が削除され、アーキテクチャ固有の新しい`memhash`実装に置き換えられました。

`strhash`関数の変更は、文字列の内部表現からポインタと長さをより直接的に取得するように修正されたものです。これは、新しい`memhash`関数が`unsafe.Pointer`と`uintptr`のサイズを受け取るため、そのインターフェースに合わせるための調整です。

### `src/runtime/hash32.go`と`src/runtime/hash64.go`の新規実装

これらのファイルは、それぞれ32ビットと64ビットのアーキテクチャ向けに、CityHashとxxHashのアイデアを組み合わせた新しい`memhash`関数を提供します。

**共通の構造:**
どちらのファイルも、`memhash(p unsafe.Pointer, s, seed uintptr) uintptr`というシグネチャを持つ`memhash`関数を定義しています。
-   `p`: ハッシュするデータのポインタ。
-   `s`: ハッシュするデータのサイズ（バイト単位）。
-   `seed`: ハッシュの初期シード値。

関数内部では、入力データのサイズに応じて異なる処理パスが選択されます（`switch`文）。

-   **小さなデータ（`s < 4`, `s == 4`, `s <= 8`, `s <= 16`など）**:
    -   これらのケースでは、データサイズが小さいため、ループを使わずに直接データを読み込み、乗算とローテートシフトを適用してハッシュ値を計算します。
    -   `readUnaligned32`や`readUnaligned64`といった関数を使用して、メモリから直接データを読み込みます。

-   **大きなデータ（`default`ケース）**:
    -   データサイズが16バイト（32ビット版）または32バイト（64ビット版）を超える場合、ループ処理が開始されます。
    -   複数のハッシュ状態変数（`v1`, `v2`, `v3`, `v4`）が導入され、それぞれがデータの異なる部分を並行して処理します。これにより、CPUの並列処理能力を最大限に活用します。
    -   ループ内で、各状態変数はデータのチャンクを読み込み、乗算とローテートシフトを適用して更新されます。
    -   ループが終了した後、残りのデータ（テール）は小さなデータと同様の処理パスで処理されます（`goto tail`）。

-   **最終的なミキシング**:
    -   すべてのデータが処理された後、最終的なハッシュ値は、複数の状態変数を結合し、さらにビットシフトと乗算を適用する「ファイナライズ」ステップによって計算されます。このステップは、ハッシュ値の均等な分布を保証するために重要です。

**ローテートシフト関数:**
`rotl_XX`関数（例: `rotl_15`, `rotl_11`, `rotl_31`, `rotl_27`）は、ビットを循環的にシフトする操作を行います。これは、ハッシュ値の各ビットが入力データのすべてのビットに依存するように、データの混合を促進するためにハッシュ関数で一般的に使用されるテクニックです。コメントにあるように、コンパイラがこれらの操作をCPUのローテート命令に変換できるように、シフト量を定数として手動で指定しています。

### `src/runtime/unaligned1.go`と`src/runtime/unaligned2.go`の新規実装

これらのファイルは、異なるアーキテクチャでのアンアラインド読み込みの具体的な実装を提供します。

-   **`unaligned1.go` (Intel/AMD64系)**:
    -   `func readUnaligned32(p unsafe.Pointer) uint32 { return *(*uint32)(p) }`
    -   `func readUnaligned64(p unsafe.Pointer) uint64 { return *(*uint64)(p) }`
    -   これらのアーキテクチャでは、CPUがアンアラインドアクセスを効率的に処理できるため、`unsafe.Pointer`を直接`*uint32`や`*uint64`にキャストしてデリファレンスするだけで済みます。これは最も高速な方法です。

-   **`unaligned2.go` (ARM/PowerPC系)**:
    -   `func readUnaligned32(p unsafe.Pointer) uint32 { q := (*[4]byte)(p); return uint32(q[0]) + uint32(q[1])<<8 + uint32(q[2])<<16 + uint32(q[3])<<24 }`
    -   `func readUnaligned64(p unsafe.Pointer) uint64 { q := (*[8]byte)(p); return uint64(q[0]) + uint64(q[1])<<8 + ... + uint64(q[7])<<56 }`
    -   これらのアーキテクチャでは、アンアラインドアクセスがパフォーマンスに悪影響を与えたり、ハードウェアでサポートされていなかったりする場合があります。そのため、ポインタをバイト配列として扱い、各バイトを個別に読み込んでビットシフトで結合することで、手動でアンアラインド読み込みをシミュレートしています。これにより、安全かつ移植性の高い方法でアンアラインドデータを処理できます。

これらの変更により、Goランタイムは、AES命令が利用できない環境でも、より堅牢で高性能なハッシュ関数を利用できるようになり、`map`などのデータ構造の全体的なパフォーマンスと信頼性が向上しました。

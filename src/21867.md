# [インデックス 21867] ファイルの概要

このコミットは、Goランタイムにおけるスレッドローカルストレージ（TLS）の扱い、特に`runtime.tlsg`シンボルに関するリンカとアセンブリコードの挙動を修正するものです。`runtime.tlsg`への参照が、TLS再配置のプレースホルダーではなく、通常の変数として扱われるべき場合に、その型宣言が適切に行われるという前提に基づき、`liblink`（Goリンカの一部）でのチェックロジックが調整されました。これにより、アセンブリ時に`runtime.tlsg`の型がゼロである場合に、TLS再配置が正しく行われるようになります。また、`_cgo_init`の呼び出しと`setg_gcc`関数の定義が`src/runtime/asm_arm.s`から`src/runtime/tls_arm.s`へ移動され、TLS関連のコードがより一箇所に集約されました。

## 元コミット内容

`liblink, runtime: move all references to runtime.tlsg to tls_arm.s`

このコミットは、`runtime.tlsg`へのすべての参照を`tls_arm.s`に移動し、`liblink`における`runtime.tlsg`の型チェックを修正します。具体的には、`CL 2118`が`runtime.tlsg`への参照がTLS再配置のプレースホルダーではなく通常の変数である場合に、その型宣言が伴うという前提を導入したため、`liblink`は`STLSBSS`ではなく型が`0`であるかをチェックするように変更されます。これは、`cmd/ld`がアセンブリ時に実行されないため、`runtime.tlsg`がランタイムパッケージによって宣言されていない場合、その型が`0`になるためです。

## 変更の背景

Goランタイムは、内部的にスレッドローカルストレージ（TLS）を利用して、現在のゴルーチン（`g`オブジェクト）の状態を効率的に管理しています。特にCgo（GoとC言語の相互運用機能）を介してCコードと連携する際に、TLSは重要な役割を果たします。

このコミットの背景には、Goのリンカ（`cmd/ld`）とアセンブラ（`go tool asm`）の間の`runtime.tlsg`シンボルの型に関する不整合がありました。

1.  **`CL 2118`の前提**: コミットメッセージに記載されている`CL 2118`は、`runtime.tlsg`への参照が、TLS再配置のための特別なプレースホルダーではなく、通常の変数として扱われるべき場合には、その型が明示的に宣言されているべきであるという新しい前提を導入しました。
2.  **リンカとアセンブラの挙動の違い**:
    *   `cmd/ld`（リンカ）は、最終的なバイナリを生成する際にシンボルの型を初期化します。
    *   しかし、`go tool asm`（アセンブラ）がアセンブリコードを処理する時点では、`cmd/ld`はまだ実行されていません。
    *   このため、`runtime`パッケージによって`runtime.tlsg`が明示的に宣言されていない場合、アセンブリ時には`runtime.tlsg`の型が`0`（未定義またはデフォルト）として扱われていました。
3.  **`liblink`の誤ったチェック**: 以前の`liblink`（Goリンカの内部ライブラリ）では、`runtime.tlsg`がTLS再配置の対象であるかを判断するために、その型が`STLSBSS`（Static Thread-Local BSS、未初期化TLSデータセクションを示す型）であるかをチェックしていました。
4.  **問題点**: `CL 2118`の新しい前提とアセンブリ時の型の不整合により、`runtime.tlsg`が通常の変数として扱われるべき場合でも、アセンブリ時に型が`0`であるために`STLSBSS`と一致せず、TLS再配置が正しく行われない可能性がありました。

このコミットは、この不整合を解消し、`liblink`が`runtime.tlsg`の型が`0`である場合にTLS再配置を行うように修正することで、Goランタイムの堅牢性と正確性を向上させることを目的としています。また、TLS関連のアセンブリコードを`tls_arm.s`に集約することで、コードの保守性を高めています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要があります。

1.  **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステム。ゴルーチンのスケジューリング、メモリ管理（ガベージコレクション）、チャネル通信、システムコールなど、Go言語の並行性モデルと効率的な実行を支える基盤を提供します。
2.  **スレッドローカルストレージ (TLS: Thread-Local Storage)**: オペレーティングシステムが提供するメカニズムで、各スレッドが独自のデータインスタンスを持つことを可能にします。GoのゴルーチンはOSスレッドに直接マッピングされるわけではありませんが、Goランタイムは内部的にOSスレッドを使用し、特にCgoを介してCライブラリと連携する際にTLSを利用します。Goランタイムでは、現在のゴルーチン（`g`オブジェクト）へのポインタをTLSに格納し、高速にアクセスできるようにしています。
3.  **`runtime.tlsg`**: Goランタイム内部で使用されるシンボルで、TLSを介して現在のゴルーチン（`g`）とマシン（`m`）のポインタにアクセスするためのオフセットを表します。これはGo開発者が直接操作するAPIではなく、ランタイムの低レベルな実装詳細です。
4.  **再配置 (Relocation)**: リンカの主要な機能の一つで、コンパイルされたオブジェクトファイル内のシンボリック参照（変数や関数の名前）を、最終的な実行可能ファイル内の実際のメモリアドレスに解決するプロセスです。TLS再配置は、スレッドローカル変数へのアクセス方法を決定するために行われます。
5.  **`liblink`**: Goのリンカ（`cmd/ld`）の内部で使われるライブラリで、特に命令選択アルゴリズムなど、リンカのコア機能の一部を担っていました。Goのツールチェインの進化に伴い、その機能は現在`cmd/link`パッケージや`obj`パッケージに統合されていますが、このコミットが作成された時点ではまだ重要な役割を担っていました。
6.  **`cmd/ld` (Go Linker)**: Goのビルドプロセスにおける最終段階で、コンパイルされたGoパッケージやオブジェクトファイルを結合して単一の実行可能バイナリを生成するツールです。シンボルの解決、メモリレイアウトの決定、再配置の適用などを行います。
7.  **Goアセンブリ (Go Assembly)**: Go言語は、特定の低レベルな処理やパフォーマンスが要求される部分のために、独自の擬似アセンブリ言語を提供しています。これは、特定のCPUアーキテクチャに直接マッピングされるのではなく、Goツールチェインによって抽象化された命令セットです。これにより、Goは異なるアーキテクチャへの移植が容易になっています。`asm_arm.s`や`tls_arm.s`は、ARMアーキテクチャ向けのアセンブリコードファイルです。
8.  **`STLSBSS`**: Static Thread-Local BSSの略で、未初期化の静的スレッドローカルデータが格納されるメモリセグメントを指します。リンカがシンボルの型を識別するために使用する内部的な型の一つです。
9.  **`_cgo_init`**: Cgoを使用するGoプログラムにおいて、Cgoランタイムの初期化を行うための関数です。GoプログラムがCライブラリと連携する際に呼び出されます。
10. **`setg_gcc`**: Goランタイム内部で、現在のゴルーチン（`g`）ポインタを設定するための関数です。特に、Cgoを介してCコードからGoランタイムに制御が戻る際などに、正しいゴルーチンコンテキストを復元するために使用されることがあります。

## 技術的詳細

このコミットの技術的な核心は、Goリンカ（`liblink`）が`runtime.tlsg`シンボルをどのように解釈し、TLS再配置を適用するかというロジックの変更にあります。

Goランタイムは、各ゴルーチンが自身の`g`構造体（ゴルーチンの状態を保持するデータ構造）へのポインタを効率的に取得できるように、TLSを利用しています。ARMアーキテクチャでは、通常、特定のレジスタ（例えば`R9`）が現在の`g`ポインタを指すように設定されます。しかし、Cgoのような外部Cコードとの連携では、OSスレッドのTLSメカニズムを介して`g`ポインタを管理する必要が生じます。

以前の`liblink`では、`runtime.tlsg`シンボルがTLS再配置の対象であるかを判断するために、そのシンボルの型が`STLSBSS`であるかをチェックしていました。`STLSBSS`は、未初期化の静的スレッドローカルデータセクションを示す内部的な型です。このチェックは、`runtime.tlsg`がTLS再配置を必要とする特別なシンボルであることを識別するためのものでした。

しかし、`CL 2118`という先行する変更により、`runtime.tlsg`への参照が、TLS再配置のプレースホルダーではなく、通常の変数として扱われるべき場合には、その型がランタイムパッケージによって明示的に宣言されるという新しい前提が導入されました。この前提は、`runtime.tlsg`が通常の変数として扱われるべき場合と、TLS再配置の対象となる場合とを区別するためのものです。

問題は、`cmd/ld`（リンカ）がシンボルの型を初期化するのに対し、`go tool asm`（アセンブラ）がアセンブリコードを処理する時点では`cmd/ld`がまだ実行されていないため、`runtime`パッケージによって`runtime.tlsg`が明示的に宣言されていない場合、アセンブリ時には`runtime.tlsg`の型が`0`（未定義またはデフォルト）として扱われていた点です。

この不整合により、`liblink`が`STLSBSS`をチェックしても、アセンブリ時に型が`0`であるためにTLS再配置が正しく適用されない可能性がありました。

このコミットは、`liblink`のチェックロジックを修正し、`runtime.tlsg`の型が`0`である場合にTLS再配置を行うように変更しました。これは、`runtime.tlsg`がランタイムパッケージによって明示的に宣言されていない（つまり型が`0`である）場合、それはTLS再配置のプレースホルダーとして扱われるべきであるという新しい解釈に基づいています。これにより、リンカとアセンブラの間の挙動の不整合が解消され、TLS再配置が常に正しく行われるようになります。

さらに、このコミットは、`_cgo_init`の呼び出しと`setg_gcc`関数の定義を`src/runtime/asm_arm.s`から`src/runtime/tls_arm.s`へ移動しています。これは、TLS関連のコードを`tls_arm.s`という専用のファイルに集約することで、コードのモジュール性と保守性を向上させるためのリファクタリングです。`tls_arm.s`は、ARMアーキテクチャにおけるTLS関連の低レベルなアセンブリルーチンを格納するためのファイルとして機能します。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下の3つのファイルにわたります。

1.  **`src/liblink/asm5.c`**:
    *   `if(rel->sym == ctxt->tlsg && ctxt->tlsg->type == STLSBSS) {`
        を
        `if(rel->sym == ctxt->tlsg && ctxt->tlsg->type == 0) {`
        に変更。
        これにより、`liblink`が`runtime.tlsg`の型をチェックする際に、`STLSBSS`ではなく`0`であるかを判断するようになります。これは、アセンブリ時に`runtime.tlsg`の型が`0`である場合にTLS再配置を適用するための修正です。

2.  **`src/runtime/asm_arm.s`**:
    *   `_cgo_init`の呼び出しと関連するTLSベースポインタのロード、`setg_gcc`の呼び出しを含むブロックが削除されました。
    *   `TEXT setg_gcc<>(SB),NOSPLIT,$0` で始まる`setg_gcc`関数の定義が削除されました。
    *   代わりに、`BL runtime·_initcgo(SB)`という新しい関数呼び出しが追加されました。これは、削除された`_cgo_init`関連のロジックを`runtime·_initcgo`という新しい関数にカプセル化し、その関数が`tls_arm.s`で定義されることを示唆しています。

3.  **`src/runtime/tls_arm.s`**:
    *   `TEXT runtime·_initcgo(SB),NOSPLIT,$0` で始まる新しい関数が追加されました。この関数は、`src/runtime/asm_arm.s`から移動された`_cgo_init`の呼び出しと関連するTLSベースポインタのロードロジックを含んでいます。
    *   `TEXT setg_gcc<>(SB),NOSPLIT,$0` で始まる`setg_gcc`関数の定義が追加されました。これも`src/runtime/asm_arm.s`から移動されたものです。

## コアとなるコードの解説

### `src/liblink/asm5.c`の変更

```c
// 変更前
// Emit a TLS relocation instead of a standard one if it's
// typed STLSBSS.
if(rel->sym == ctxt->tlsg && ctxt->tlsg->type == STLSBSS) {

// 変更後
// Emit a TLS relocation instead of a standard one if its
// type is not explicitly set by runtime. This assumes that
// all references to runtime.tlsg should be accompanied with
// its type declaration if necessary.
if(rel->sym == ctxt->tlsg && ctxt->tlsg->type == 0) {
```

この変更は、Goリンカの内部ロジックにおける`runtime.tlsg`シンボルの扱い方を根本的に変えるものです。
*   **`rel->sym == ctxt->tlsg`**: これは、現在の再配置エントリが`runtime.tlsg`シンボルを参照していることを確認しています。
*   **`ctxt->tlsg->type == STLSBSS` (変更前)**: 以前は、`runtime.tlsg`の型が`STLSBSS`（Static Thread-Local BSS）である場合に、その参照をTLS再配置（`R_TLS`）として扱っていました。`STLSBSS`は、未初期化の静的スレッドローカルデータセクションを示すリンカ内部の型です。
*   **`ctxt->tlsg->type == 0` (変更後)**: 変更後は、`runtime.tlsg`の型が`0`である場合にTLS再配置を適用します。この`0`という型は、シンボルがランタイムパッケージによって明示的に型宣言されていないことを意味します。コミットメッセージにあるように、「`runtime.tlsg`がランタイムパッケージによって宣言されていない場合、その型はゼロになる」という前提に基づいています。これは、アセンブリ時にリンカがまだシンボルの型を初期化していない状況に対応するためのものです。

この修正により、`liblink`は、`runtime.tlsg`が明示的に型付けされていない（つまり、TLS再配置のプレースホルダーとして機能する）場合に、正しくTLS再配置を生成するようになります。

### `src/runtime/asm_arm.s`と`src/runtime/tls_arm.s`の変更

これらの変更は、ARMアーキテクチャにおけるGoランタイムの初期化とTLS関連のコードのリファクタリングです。

**`src/runtime/asm_arm.s` (変更前)**:
このファイルには、Goプログラムのエントリポイントである`runtime·rt0_go`関数が含まれていました。その中で、`_cgo_init`関数の存在チェックと呼び出し、そして`setg_gcc`関数の定義が行われていました。`_cgo_init`はCgoランタイムの初期化を行い、`setg_gcc`は現在のゴルーチン（`g`）ポインタを設定する低レベルな関数です。これらの処理はTLSと密接に関連しています。

**`src/runtime/asm_arm.s` (変更後)**:
`_cgo_init`の呼び出しと`setg_gcc`の定義が削除され、代わりに`BL runtime·_initcgo(SB)`というシンプルな呼び出しに置き換えられました。これにより、`asm_arm.s`はよりクリーンになり、初期化ロジックの詳細は別のファイルに委譲されます。

**`src/runtime/tls_arm.s` (新規追加/変更)**:
このファイルに、`runtime·_initcgo`関数と`setg_gcc`関数が新しく定義されました。
*   **`runtime·_initcgo`**: `asm_arm.s`から移動された`_cgo_init`の呼び出しロジックを含みます。これには、`_cgo_init`が存在するかどうかのチェック、TLSベースポインタのロード（`MRC 15, 0, R0, C13, C0, 3`はARMのCP15レジスタからTLSレジスタを読み込む命令）、そして`_cgo_init`の呼び出しが含まれます。
*   **`setg_gcc`**: `asm_arm.s`から移動された`MOVW R0, g`と`B runtime·save_g(SB)`というシンプルなロジックを含みます。これは、引数`R0`で渡されたゴルーチンポインタをグローバル変数`g`に設定し、`runtime·save_g`を呼び出してゴルーチンコンテキストを保存するものです。

これらの変更により、TLS関連の低レベルなアセンブリコードが`tls_arm.s`という専用のファイルに集約されました。これは、コードの整理とモジュール化を促進し、将来的なメンテナンスやARMアーキテクチャにおけるTLS関連の変更を容易にするためのものです。

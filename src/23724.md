# [インデックス 23724] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）の正確性に関する重要なバグを修正します。具体的には、`typedmemmove`のような特定のランタイム関数が、現在のスタックフレームより上位のフレームにポインタを書き込む際に、ライトバリアが適切に適用されないために発生する問題に対処しています。この問題により、GCが更新されたポインタを認識できず、誤ってオブジェクトを解放してしまう可能性がありました。修正は、`heapBitsBulkBarrier`関数内でスタック上の書き込みを検出し、関連するスタックバリアを解除することで、GCが影響を受けたフレームを再スキャンするように強制するというアプローチを取っています。

## コミット

Author: Austin Clements <austin@google.com>
Date:   Fri Jun 5 14:49:27 2015 -0400

    runtime: unwind stack barriers when writing above the current frame
    
    Stack barriers assume that writes through pointers to frames above the
    current frame will get write barriers, and hence these frames do not
    need to be re-scanned to pick up these changes. For normal writes,
    this is true. However, there are places in the runtime that use
    typedmemmove to potentially write through pointers to higher frames
    (such as mapassign1). Currently, typedmemmove does not execute write
    barriers if the destination is on the stack. If there's a stack
    barrier between the current frame and the frame being modified with
    typedmemmove, and the stack barrier is not otherwise hit, it's
    possible that the garbage collector will never see the updated pointer
    and incorrectly reclaim the object.
    
    Fix this by making heapBitsBulkBarrier (which lies behind typedmemmove
    and its variants) detect when the destination is in the stack and
    unwind stack barriers up to the point, forcing mark termination to
    later rescan the effected frame and collect these pointers.
    
    Fixes #11084. Might be related to #10240, #10541, #10941, #11023,
     #11027 and possibly others.

## 変更の背景

Goのガベージコレクタ（GC）は、プログラムの実行中に不要になったメモリを自動的に解放する役割を担っています。GCの正確性を保証するためには、プログラムがポインタを更新する際に、GCがその変更を確実に認識できるメカニズムが必要です。このメカニズムの一つが「ライトバリア（Write Barrier）」です。

通常、Goランタイムは、現在のスタックフレームより上位のフレームにあるポインタへの書き込みに対してライトバリアが適用されることを前提としています。これにより、GCはこれらのフレームを再スキャンすることなく、ポインタの変更を追跡できます。しかし、`typedmemmove`のような特定のランタイム内部関数（例えば`mapassign1`などで使用される）は、スタック上のメモリに書き込む際にライトバリアを実行しないという特性がありました。

この問題は、`typedmemmove`が現在のフレームよりも上位のスタックフレームにポインタを書き込み、かつその書き込みがスタックバリアを越える場合、深刻なバグを引き起こす可能性がありました。もし、このスタックバリアが他の方法で「ヒット」されなかった場合、GCは更新されたポインタを検知できず、そのポインタが指すオブジェクトを誤って到達不能と判断し、不正に解放してしまう恐れがありました。これは、プログラムのクラッシュやデータ破損につながる可能性のある、GCの正確性に関わる重大な問題です。

このコミットは、このGCの正確性に関するバグ（Issue #11084）を修正するために導入されました。

## 前提知識の解説

このコミットの理解には、以下のGoランタイムおよびGCに関する知識が不可欠です。

### 1. Goのガベージコレクション (GC) の基本

GoのGCは、並行マーク＆スイープ（concurrent mark-and-sweep）アルゴリズムをベースにしています。これは、プログラムの実行と並行してGCが動作し、アプリケーションの一時停止（STW: Stop The World）時間を最小限に抑えることを目指しています。GCの主要なフェーズは以下の通りです。

*   **マークフェーズ (Mark Phase)**: プログラムが使用している（到達可能な）オブジェクトを特定します。ルート（グローバル変数、スタック上の変数、レジスタなど）からポインタをたどって、到達可能なオブジェクトにマークを付けます。
*   **マークターミネーションフェーズ (Mark Termination Phase)**: マークフェーズの終了処理を行います。このフェーズでSTWが発生し、GCがマークフェーズ中に見逃した可能性のあるポインタの変更を処理します。
*   **スイープフェーズ (Sweep Phase)**: マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放し、再利用可能にします。

### 2. Write Barrier (ライトバリア)

ライトバリアは、GCがポインタの変更を追跡するためのメカニズムです。プログラムがヒープ上のポインタを更新する際に、GCはライトバリアを介してその変更を記録します。これにより、GCはマークフェーズ中にオブジェクトグラフが変化しても、正確に到達可能なオブジェクトを特定できます。GoのGCは、Dijkstraスタイルのライトバリアを使用しており、ポインタが更新される「前」の値を記録します。

### 3. Stack Barrier (スタックバリア)

スタックバリアは、GoのGCがスタックを効率的にスキャンするために導入された概念です。Goのスタックは動的に伸縮するため、GCがスタックをスキャンする際に、スタックの移動や拡張によってポインタが変更される可能性があります。スタックバリアは、特定の関数呼び出しの境界に設定され、GCがスタックをスキャンする際に、そのバリアを越えてポインタが変更されたかどうかを検出します。これにより、GCはスタックの変更を効率的に追跡し、必要に応じて再スキャンを行うことができます。

### 4. `typedmemmove` とその役割

`typedmemmove`は、Goランタイム内部で使用される関数で、型情報（ビットマップ）に基づいてメモリブロックをコピーします。これは、特にマップの割り当て（`mapassign1`）など、ポインタを含む可能性のある構造体を効率的に移動させるために使用されます。重要なのは、この関数が通常のポインタ書き込みとは異なり、スタック上のメモリへの書き込みに対してはライトバリアを直接実行しないという点です。

### 5. Goランタイムのスタック管理

Goのgoroutineは、比較的小さなスタック（通常は数KB）で開始し、必要に応じて自動的に拡張されます。スタックはヒープ上に割り当てられ、GCの対象となります。スタックフレームは、関数呼び出しごとに作成され、ローカル変数や引数、戻りアドレスなどが格納されます。

## 技術的詳細

このコミットの核心は、`typedmemmove`がスタック上の上位フレームにポインタを書き込む際にライトバリアが欠落するという問題に対処することです。

従来のGoランタイムでは、スタックバリアは、現在のフレームより上位のフレームへのポインタ書き込みがライトバリアによって捕捉されることを前提としていました。しかし、`typedmemmove`はスタックへの書き込み時にライトバリアを実行しないため、この前提が崩れていました。

この修正は、`heapBitsBulkBarrier`関数（`typedmemmove`などの背後にある低レベルのメモリ操作関数）に新しいロジックを追加することで実現されます。

1.  **スタック上の書き込みの検出**: `heapBitsBulkBarrier`は、書き込み先のアドレス`p`がヒープ上ではなく、現在のgoroutineのスタック範囲内にあるかどうかをチェックします。さらに、その書き込み先が現在のフレームよりも上位のフレームにある可能性があることを考慮します。
2.  **スタックバリアの解除 (Unwind)**: もし書き込み先がスタック上にあり、かつ現在のフレームよりも上位のフレームであると判断された場合、`heapBitsBulkBarrier`は`gcUnwindBarriers`関数を呼び出します。
3.  **`gcUnwindBarriers`の役割**: `gcUnwindBarriers`は、指定されたスタックポインタ`sp`（この場合は`p`が属するフレームのスタックポインタ）まで、既存のスタックバリアを「解除」します。ここでいう「解除」とは、単にバリアをスキップするのではなく、`gcRemoveStackBarrier`を呼び出して実際にスタックバリアの記録を削除し、それらのバリアが「ヒット済み」として扱われるようにすることです。
4.  **GCによる再スキャン**: スタックバリアが解除されると、GCのマークターミネーションフェーズにおいて、影響を受けたスタックフレームが再スキャンされることが保証されます。これにより、`typedmemmove`によって更新されたポインタがGCによって正しく検出され、オブジェクトが誤って解放されることを防ぎます。

このアプローチの利点は、`typedmemmove`自体に複雑なライトバリアロジックを追加する必要がないことです。代わりに、GCの既存のスタック管理メカニズムを利用して、問題のあるフレームを再スキャンさせることで、GCの正確性を維持しています。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/runtime/mbitmap.go`**:
    *   `heapBitsBulkBarrier`関数に、書き込み先がスタック上にある場合の新しいロジックが追加されました。
    *   `inheap(p)`のチェックが`writeBarrierEnabled`のチェックから分離され、スタック上のアドレス`p`に対する処理が追加されています。
    *   `gp.stack.lo <= p && p < gp.stack.hi`で、`p`が現在のgoroutineのスタック範囲内にあるかを確認します。
    *   スタック上にある場合、`systemstack(func() { gcUnwindBarriers(gp, p) })`を呼び出し、システムスタック上で`gcUnwindBarriers`を実行します。

2.  **`src/runtime/mgcmark.go`**:
    *   `gcSkipBarriers`関数が`gcUnwindBarriers`にリネームされ、その機能が拡張されました。
    *   `gcUnwindBarriers`は、単にバリアをスキップするだけでなく、`gcRemoveStackBarrier`を呼び出して実際にスタックバリアを削除するようになりました。
    *   `//go:nosplit`ディレクティブが追加され、関数実行中にスタックが移動しないことが保証されます。
    *   `gcRemoveStackBarrier`にも`//go:nosplit`ディレクティブが追加されました。

3.  **`src/runtime/panic1.go`**:
    *   `recovery`関数内で、`gcSkipBarriers(gp, sp)`の呼び出しが`gcUnwindBarriers(gp, sp)`に変更されました。これは、パニック/リカバリ時のスタックアンワインド処理においても、スタックバリアの適切な解除が必要であることを示しています。

## コアとなるコードの解説

### `src/runtime/mbitmap.go` の `heapBitsBulkBarrier` 関数

```go
func heapBitsBulkBarrier(p, size uintptr) {
	if (p|size)&(ptrSize-1) != 0 {
		throw("heapBitsBulkBarrier: unaligned arguments")
	}
	if !writeBarrierEnabled { // ライトバリアが無効な場合は何もしない
		return
	}
	if !inheap(p) { // 書き込み先pがヒープ上にない場合
		// If p is on the stack and in a higher frame than the
		// caller, we either need to execute write barriers on
		// it (which is what happens for normal stack writes
		// through pointers to higher frames), or we need to
		// force the mark termination stack scan to scan the
		// frame containing p.
		//
		// Executing write barriers on p is complicated in the
		// general case because we either need to unwind the
		// stack to get the stack map, or we need the type's
		// bitmap, which may be a GC program.
		//
		// Hence, we opt for forcing the re-scan to scan the
		// frame containing p, which we can do by simply
		// unwinding the stack barriers between the current SP
		// and p's frame.
		gp := getg().m.curg
		if gp.stack.lo <= p && p < gp.stack.hi { // pが現在のgoroutineのスタック範囲内にある場合
			// Run on the system stack to give it more
			// stack space.
			systemstack(func() {
				gcUnwindBarriers(gp, p) // システムスタック上でgcUnwindBarriersを呼び出す
			})
		}
		return // ヒープ外の書き込みはここで処理を終える
	}
	// ... (ヒープ上の書き込みに対する既存のライトバリアロジック)
}
```

この変更の肝は、`!inheap(p)`のブロック内に追加されたロジックです。`p`がヒープ上ではなく、かつ現在のgoroutineのスタック範囲内にある場合、`gcUnwindBarriers`が呼び出されます。これにより、`typedmemmove`のような関数がスタック上の上位フレームにポインタを書き込んだ際に、GCがその変更を確実に捕捉できるようになります。`systemstack`を使用しているのは、`gcUnwindBarriers`がスタック操作を行うため、十分なスタック空間を確保するためです。

### `src/runtime/mgcmark.go` の `gcUnwindBarriers` 関数

```go
// gcUnwindBarriers marks all stack barriers up the frame containing
// sp as hit and removes them. This is used during stack unwinding for
// panic/recover and by heapBitsBulkBarrier to force stack re-scanning
// when its destination is on the stack.
//
// This is nosplit to ensure gp's stack does not move.
//
//go:nosplit
func gcUnwindBarriers(gp *g, sp uintptr) {
	// On LR machines, if there is a stack barrier on the return
	// from the frame containing sp, this will mark it as hit even
	// though it isn't, but it's okay to be conservative.
	before := gp.stkbarPos
	for int(gp.stkbarPos) < len(gp.stkbar) && gp.stkbar[gp.stkbarPos].savedLRPtr < sp {
		gcRemoveStackBarrier(gp, gp.stkbar[gp.stkbarPos]) // スタックバリアを削除
		gp.stkbarPos++
	}
	if debugStackBarrier && gp.stkbarPos != before {
		// ... (デバッグ出力)
	}
}
```

`gcUnwindBarriers`は、以前の`gcSkipBarriers`から改名され、機能が強化されました。ループ内で、`sp`（スタックポインタ）よりも低いアドレスにあるスタックバリアを順に処理します。重要な変更は、`gcRemoveStackBarrier`が呼び出されるようになった点です。これにより、単にバリアをスキップするだけでなく、実際にバリアが削除され、GCがそのフレームを再スキャンする必要があることを示します。`//go:nosplit`ディレクティブは、この関数が実行中にスタックを拡張しないことを保証し、スタック操作の安全性を高めます。

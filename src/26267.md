# [インデックス 26267] ファイルの概要

## 変更の背景

この変更の背景には、GoランタイムがWindows上で `timeBeginPeriod(1)` 関数を呼び出すことによって引き起こされる潜在的な問題と、Goスケジューラの進化があります。

Go 1.5以前のGoランタイムは、Windows環境でより正確なタイマーイベントと効率的なスケジューリングを実現するために、起動時に `timeBeginPeriod(1)` を呼び出していました。この関数は、システム全体のタイマー解像度を最小値（通常1ミリ秒）に設定するもので、Goのランタイムがより短い間隔でゴルーチンをスケジューリングできるようになることを意図していました。

しかし、このアプローチにはいくつかの問題がありました。
1.  **システム全体への影響**: `timeBeginPeriod` はグローバルな設定であり、Goプログラムだけでなく、システム上で動作する他のすべてのアプリケーションのタイマー解像度にも影響を与えます。これにより、他のアプリケーションが予期せぬ挙動を示したり、電力消費が増加したりする可能性がありました。特に、バッテリー駆動のデバイスでは、タイマー解像度が高い状態が維持されることでバッテリー寿命が短くなるという問題が報告されていました。
2.  **問題の報告**: 一部のシステムでは、このグローバルなタイマー解像度の変更が原因で、オーディオの途切れやその他のパフォーマンス上の問題が発生することが報告されていました（Issue #13731）。
3.  **スケジューラの改善**: Goランタイムのスケジューラは継続的に改善されており、Go 1.6の時点では、`timeBeginPeriod(1)` を呼び出さなくても十分なパフォーマンスを発揮できるようになっていました。より洗練されたスケジューリングアルゴリズムと、Windowsの新しいAPIや最適化の活用により、Goは外部のグローバル設定に依存することなく、効率的に動作できるようになっていたのです。

これらの理由から、Go開発チームは `timeBeginPeriod(1)` の呼び出しを廃止することを決定し、その変更をユーザーに伝えるためにこのドキュメントの更新が行われました。

## 前提知識の解説

### Windowsのタイマー解像度 (`timeBeginPeriod`, `timeEndPeriod`)

Windowsオペレーティングシステムには、システムタイマーの解像度という概念があります。これは、システムがタイマーイベントを処理する最小の時間間隔を指します。デフォルトでは、この解像度は比較的粗く（例えば、10msから15.6msの範囲）、電力効率を優先しています。

*   **`timeBeginPeriod(UINT uPeriod)`**: このWindows API関数は、システム全体のタイマー解像度を `uPeriod` ミリ秒に設定するよう要求します。`uPeriod` に1を指定すると、タイマー解像度は1ミリ秒に設定され、システムはより頻繁にタイマーイベントをチェックするようになります。これは、高精度なタイミングを必要とするアプリケーション（例: ゲーム、マルチメディアアプリケーション）で利用されることがあります。
*   **`timeEndPeriod(UINT uPeriod)`**: `timeBeginPeriod` で設定したタイマー解像度を解放するために使用されます。`timeBeginPeriod` と `timeEndPeriod` はペアで呼び出すことが推奨されており、アプリケーションが終了する際にはタイマー解像度を元の状態に戻すべきです。

**問題点**: `timeBeginPeriod` はグローバルな設定であるため、あるアプリケーションがこれを呼び出すと、システム上の他のすべてのアプリケーションにも影響を与えます。これにより、意図しない副作用（電力消費の増加、他のアプリケーションのパフォーマンス低下など）が発生する可能性があります。

### Goランタイムのスケジューラ

Goランタイムには、ユーザーレベルの軽量スレッドである「ゴルーチン (goroutine)」を管理するための独自のスケジューラが組み込まれています。このスケジューラは、OSのスレッド上でゴルーチンを効率的に多重化し、並行処理を実現します。

Goスケジューラは、ゴルーチンがブロックされたり、実行可能になったりするイベントを監視し、適切なタイミングで別のゴルーチンにCPUを切り替えます。この切り替えの精度や頻度は、アプリケーションの応答性やスループットに大きく影響します。Windows環境では、OSのタイマー解像度がスケジューラの効率に影響を与える可能性があったため、Go 1.5以前では `timeBeginPeriod(1)` を利用してタイマー精度を向上させようとしていました。しかし、Goスケジューラの内部的な改善により、このようなOSレベルのタイマー設定に依存する必要がなくなりました。

## 技術的詳細

このコミット自体は、Goランタイムのコードを変更するものではなく、Go 1.6のリリースノートに新しい段落を追加するドキュメントの変更です。しかし、その背景にある技術的変更は重要です。

Go 1.5以前のGoランタイムは、Windowsの `runtime` パッケージ内で `timeBeginPeriod(1)` を呼び出していました。これは、Goのスケジューラがより短いタイムスライスでゴルーチンをプリエンプトし、より応答性の高いシステムを実現するための一時的な対策でした。Windowsのデフォルトのタイマー解像度がGoのスケジューラの要求する精度に満たない場合、ゴルーチンの切り替えが遅延し、結果としてアプリケーションのレイテンシが増加する可能性がありました。

Go 1.6では、スケジューラの内部的な改善により、この `timeBeginPeriod(1)` の呼び出しが不要になりました。具体的な改善点としては、以下のようなものが考えられます（ただし、このコミットの範囲外の変更です）：
*   **より効率的なポーリングメカニズム**: OSのタイマーに依存するのではなく、I/Oイベントやネットワークイベントなどの非同期イベントをより効率的にポーリングするメカニズムが導入された可能性があります。
*   **スピンロックの最適化**: スケジューラ内のロック機構や同期プリミティブが最適化され、短い待機時間でCPUを解放できるようになり、タイマー解像度の影響を受けにくくなった可能性があります。
*   **OSスケジューラとの協調**: WindowsのOSスケジューラとのより良い協調メカニズムが開発され、GoランタイムがOSに適切なヒントを与えることで、より効率的なスレッド管理が可能になった可能性があります。

`timeBeginPeriod(1)` の削除は、GoプログラムがWindowsシステムに与える影響を最小限に抑え、他のアプリケーションとの共存性を高めるための重要なステップです。これにより、Goプログラムはより「行儀の良い」市民となり、システム全体の安定性と電力効率に貢献します。

## コアとなるコードの解説

追加されたHTMLの段落は、Go 1.6におけるWindows環境での重要な変更点を簡潔かつ明確に説明しています。

*   **「On Windows, Go programs in Go 1.5 and earlier forced the global Windows timer resolution to 1ms at startup by calling `timeBeginPeriod(1)`」**:
    *   これは、Go 1.5以前のGoプログラムがWindows上でどのように動作していたかを説明しています。`timeBeginPeriod(1)` を呼び出すことで、システム全体のタイマー解像度を1ミリ秒に設定していたことを明記しています。これは、Goのスケジューラがより細かい粒度で動作するために必要だと考えられていたためです。
*   **「Go no longer needs this for good scheduler performance」**:
    *   Go 1.6以降では、Goランタイムのスケジューラが改善されたため、このグローバルなタイマー解像度の変更が不要になったことを示しています。これは、Goの内部的な最適化により、外部のOS設定に依存せずに高いパフォーマンスを維持できるようになったことを意味します。
*   **「and changing the global timer resolution caused problems on some systems, so the call has been removed.」**:
    *   `timeBeginPeriod(1)` の呼び出しが削除された理由を説明しています。グローバルなタイマー解像度の変更が一部のシステムで問題を引き起こしていたこと（例: バッテリー寿命の短縮、オーディオの途切れなど）が主な理由です。この変更は、Goプログラムの安定性とシステム全体との互換性を向上させるためのものです。

このドキュメントの追加は、ユーザーがGo 1.6にアップグレードする際に、Windows環境でのGoプログラムの挙動変更を理解し、潜在的な影響（良い意味での）を認識できるようにするための重要な情報提供です。

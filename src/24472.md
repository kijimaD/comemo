# [インデックス 24472] ファイルの概要

このコミットはGoコンパイラのSSA (Static Single Assignment) バックエンドにおけるシフト演算の取り扱いと、ビット単位NOT演算 (`OCOM`) の実装に関する重要な改善を含んでいます。特に、シフト演算のオペランドの型情報をより詳細にSSA形式にエンコードすることで、AMD64アーキテクチャでのコード生成の精度と効率を向上させています。また、符号付き右シフトの最適化と、定数畳み込みルールの拡張も行われています。

## 元コミット内容

GoコンパイラのSSAバックエンドにおいて、シフト演算の処理を修正し、シフト量のサイズもエンコードするように変更しました。これにより、符号付き右シフトのコード生成をCMOV命令からビット操作に切り替え、コードサイズを削減し、わずかながら高速化を実現しました。また、ビット単位NOT演算 (`OCOM`) の実装も追加しました。

## 変更の背景

GoコンパイラのSSAバックエンドは、より最適化された機械語コードを生成するために導入されました。このコミットが行われた時点では、SSAバックエンドはまだ開発途上であり、様々な演算のコード生成ルールが洗練されていました。

シフト演算は、特にシフト量がオペランドのビット幅を超える場合に、言語仕様に厳密に従った挙動を保証する必要があります。Go言語の仕様では、シフト量がオペランドのビット幅以上の場合、結果は0（左シフト、符号なし右シフト）または符号ビットの複製（符号付き右シフト）となります。従来のSSA形式では、シフト演算のオペランドの型情報が不十分であったため、これらのエッジケースを効率的かつ正確に処理するためのコード生成が複雑になる可能性がありました。

また、符号付き右シフトの最適化は、CMOV（条件付き移動）命令を使用する既存の実装が、特定のシナリオで最適なパフォーマンスを発揮しない可能性があったため検討されました。CMOVは分岐予測ミスを避けるために使用されますが、常に最速とは限りません。

さらに、ビット単位NOT演算 (`OCOM`) は基本的なビット操作であり、SSA形式で直接サポートすることで、コンパイラがより効率的なコードを生成できるようになります。

## 前提知識の解説

### 1. GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木 (AST) に変換した後、中間表現 (IR) を生成します。SSA (Static Single Assignment) 形式は、このIRの一種であり、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。SSAバックエンドは、このSSA形式のIRを基に、ターゲットアーキテクチャ（この場合はAMD64）の機械語コードを生成します。

### 2. シフト演算のGo言語仕様

Go言語では、シフト演算 `x << y` (左シフト) および `x >> y` (右シフト) の挙動は、シフト量 `y` がシフト対象 `x` のビット幅以上の場合に特殊なルールがあります。
*   **左シフト (`x << y`)**: `y` が `x` のビット幅以上の場合、結果は0になります。
*   **符号なし右シフト (`x >> y`)**: `y` が `x` のビット幅以上の場合、結果は0になります。
*   **符号付き右シフト (`x >> y`)**: `y` が `x` のビット幅以上の場合、結果は `x` の符号ビットで埋め尽くされます（負の数の場合は-1、正の数の場合は0）。

これらのルールは、C言語などの他の言語とは異なるため、コンパイラは正確なコードを生成する必要があります。

### 3. AMD64アーキテクチャにおけるシフト命令

AMD64 (x86-64) アーキテクチャには、論理シフト (`SHL`, `SHR`) と算術シフト (`SAR`) の命令があります。
*   `SHL` (Shift Left): 左シフト。最上位ビットはキャリーフラグに移動し、最下位ビットには0が挿入されます。
*   `SHR` (Shift Right): 論理右シフト。最下位ビットはキャリーフラグに移動し、最上位ビットには0が挿入されます。符号なし整数に使用されます。
*   `SAR` (Shift Arithmetic Right): 算術右シフト。最下位ビットはキャリーフラグに移動し、最上位ビットには符号ビットが複製されます。符号付き整数に使用されます。

これらの命令は、シフト量がレジスタ (`CL` レジスタ) に格納されている場合にのみ、可変シフトとして機能します。シフト量が即値の場合は、命令に直接埋め込まれます。

### 4. CMOV (Conditional Move) 命令

CMOV命令は、特定のCPUフラグの状態に基づいてレジスタ間でデータを条件付きで移動させる命令です。分岐命令 (`JMP`) と異なり、CPUのパイプラインをストールさせる可能性のある分岐予測ミスを避けるために使用されることがあります。しかし、CMOV命令自体が複数のマイクロオペレーションに分解される場合や、依存関係が複雑になる場合には、必ずしも高速とは限りません。

### 5. ビット操作 (Bit Twiddling)

ビット操作は、論理演算 (`AND`, `OR`, `XOR`, `NOT`) やシフト演算を組み合わせて、特定のビットパターンを生成したり、条件を判定したりするテクニックです。CMOV命令の代わりにビット操作を使用することで、命令数を減らしたり、CPUのパイプライン効率を向上させたりできる場合があります。

### 6. 定数畳み込み (Constant Folding)

定数畳み込みは、コンパイル時に定数オペランドを持つ演算の結果を計算し、その結果で元の演算を置き換える最適化手法です。例えば、`2 + 3` はコンパイル時に `5` に置き換えられます。これにより、実行時の計算が不要になり、パフォーマンスが向上します。

## 技術的詳細

### 1. シフト演算のSSAオペレーションの細分化

このコミットの最も重要な変更点の一つは、シフト演算のSSAオペレーションが、シフト対象の値のビット幅とシフト量のビット幅の両方をエンコードするように変更されたことです。
例えば、以前は `OpLsh64` のようにシフト対象のビット幅のみを表現していましたが、変更後は `OpLsh64x64` (64ビット値を64ビット量でシフト)、`OpLsh64x32` (64ビット値を32ビット量でシフト) のように、`Op<ValueBits>x<ShiftAmountBits>` の形式になりました。

これは `src/cmd/compile/internal/gc/ssa.go` の `shiftOpToSSA` マップと、`src/cmd/compile/internal/ssa/gen/genericOps.go` および `src/cmd/compile/internal/ssa/opGen.go` の新しいSSAオペレーション定義で確認できます。

この細分化の目的は、Go言語のシフト仕様（シフト量がビット幅以上の場合の挙動）を正確に、かつ効率的にAMD64の機械語にマッピングするためです。特に、シフト量がシフト対象のビット幅以上の場合、AMD64のネイティブなシフト命令はGoの仕様とは異なる結果を返すため、追加のマスク処理が必要になります。シフト量の型情報を持つことで、コンパイラはより適切なマスク処理を生成できるようになります。

### 2. 符号付き右シフトの最適化

以前の符号付き右シフト (`Rsh64`) は、シフト量が64以上の場合に結果を調整するために `CMOVQCC` (Conditional Move if Carry Clear) 命令を使用していました。これは、シフト量が64未満の場合は通常の `SARQ` (Arithmetic Right Shift Quadword) を実行し、64以上の場合は63にクランプしたシフト量で `SARQ` を実行するというロジックでした。

このコミットでは、`CMOV` を使用する代わりに「ビット操作」 (`bit twiddles`) を使用するように変更されました。具体的には、`AMD64.rules` で `Rsh64x64` のようなルールが以下のように変更されています。

```
(Rsh64x64 <t> x y) -> (SARQ <t> x (ORQ <y.Type> y (NOTQ <y.Type> (SBBQcarrymask <y.Type> (CMPQconst <TypeFlags> [64] y)))))
```

この新しいロジックは、シフト量 `y` が64以上の場合に、`y` を `-1` (全ビット1) に変更するような効果を持たせます。
*   `CMPQconst <TypeFlags> [64] y`: `y` と64を比較し、フラグを設定します。
*   `SBBQcarrymask <y.Type> (...)`: キャリーフラグがセットされている（`y >= 64`）場合、`-1` (全ビット1) を生成し、そうでなければ `0` を生成します。
*   `NOTQ <y.Type> (...)`: 上記の結果をビット反転します。`y >= 64` なら `0`、そうでなければ `-1` を生成します。
*   `ORQ <y.Type> y (...)`: `y` と上記のビット反転結果をORします。
    *   `y < 64` の場合: `y | (-1)` は `-1` になります。
    *   `y >= 64` の場合: `y | 0` は `y` になります。

しかし、このルールは `y >= 64` の場合に `y` を `-1` にするのではなく、`y` が64以上の場合に `y` を `y | (-1)` にすることで、結果的にシフト量が非常に大きな値（実質的に `-1`）になるように調整しています。AMD64の `SAR` 命令は、シフト量がオペランドのビット幅以上の場合、シフト量をビット幅-1として扱います。例えば、64ビット値の `SAR` でシフト量が64以上の場合、シフト量は63として扱われます。このため、`y` を `-1` にすることで、`SAR` 命令が期待通りの結果（符号ビットの複製）を生成するように誘導しています。

コミットメッセージでは「5命令ではなく4命令」とありますが、これは `CMOV` を使ったバージョンと新しいビット操作バージョンの比較であり、新しいバージョンが「より少ないバイト数でわずかに速い」とされています。これは、`CMOV` が複数のマイクロオペレーションに分解されることや、ビット操作がより効率的なCPUリソースを使用することに起因する可能性があります。

### 3. OCOM (ビット単位NOT) の実装

`OCOM` はGo言語の `^` 演算子に対応するビット単位NOT演算です。このコミットでは、`OCOM` がSSA形式でサポートされ、AMD64の `NOTQ`, `NOTL`, `NOTW`, `NOTB` 命令にマッピングされるようになりました。
*   `src/cmd/compile/internal/gc/ssa.go`: `opToSSA` マップに `OCOM` と対応するSSAオペレーション (`ssa.OpCom8`, `ssa.OpCom16` など) が追加されました。
*   `src/cmd/compile/internal/ssa/gen/AMD64.rules`: `(Com64 x) -> (NOTQ x)` のようなルールが追加され、`OCOM` がAMD64の `NOT` 命令に直接変換されるようになりました。
*   `src/cmd/compile/internal/ssa/gen/AMD64Ops.go` および `src/cmd/compile/internal/ssa/opGen.go`: `NOTQ`, `NOTL`, `NOTW`, `NOTB` のSSAオペレーションが定義されました。
*   `src/cmd/compile/internal/ssa/rewriteAMD64.go`: `Com16`, `Com32`, `Com64`, `Com8` のSSAオペレーションを `NOTW`, `NOTL`, `NOTQ`, `NOTB` に書き換えるルールが追加されました。

これにより、Goコードで `^x` のようなビット単位NOT演算が使用された場合、コンパイラは直接対応するAMD64の `NOT` 命令を生成できるようになり、効率が向上します。

### 4. 定数畳み込みルールの拡張

`src/cmd/compile/internal/ssa/rewriteAMD64.go` および `src/cmd/compile/internal/ssa/gen/AMD64.rules` では、`ADD`, `SUB`, `MUL`, `AND`, `OR`, `XOR`, `NOT` などの演算に対する定数畳み込みルールが大幅に拡張されました。
例えば、`ADDQconst [c] (MOVQconst [d])` (定数 `c` と定数 `d` の加算) は `MOVQconst [c+d]` (定数 `c+d` の移動) に置き換えられるようになりました。
これは、コンパイル時に計算可能な式を事前に評価することで、実行時のオーバーヘッドを削減し、生成されるコードをよりコンパクトにするための一般的な最適化です。

## コアとなるコードの変更箇所

### `src/cmd/compile/internal/gc/ssa.go`

*   `opToSSA` マップに `OCOM` 演算子とそれに対応するSSAオペレーション (`ssa.OpCom8` など) が追加されました。
*   `shiftOpToSSA` という新しいマップが導入され、シフト演算 (`OLSH`, `ORSH`) がシフト対象とシフト量の両方の型に基づいてSSAオペレーションにマッピングされるようになりました (例: `ssa.OpLsh8x8`, `ssa.OpRsh8Ux8`)。

*   `genValue` 関数から `ssa.OpAMD64CMOVQCC` の処理が削除されました。

## コアとなるコードの解説

このコミットの核心は、GoコンパイラのSSA中間表現におけるシフト演算の表現をより詳細にし、それに対応するAMD64機械語コード生成ルールを最適化することにあります。

1.  **シフト演算の型情報の強化**:
    `src/cmd/compile/internal/gc/ssa.go` の `ssaShiftOp` 関数と `shiftOpToSSA` マップは、シフト対象の値の型 (`etype1`) とシフト量の型 (`etype2`) の両方に基づいて、特定のSSAオペレーション (`ssa.OpLsh8x8` など) を選択します。これにより、コンパイラはシフト演算のセマンティクスをより正確に理解し、ターゲットアーキテクチャの特性（例えば、シフト量がレジスタのビット幅を超える場合の挙動）を考慮したコードを生成できます。

2.  **符号付き右シフトの最適化**:
    `src/cmd/compile/internal/ssa/gen/AMD64.rules` にある符号付き右シフトの新しいルールは、`SARQ` 命令と、シフト量 `y` を調整するためのビット操作を組み合わせています。
    `y` がシフト対象のビット幅（64ビット値の場合64）以上の場合、Goの仕様では結果は符号ビットの複製で埋め尽くされる必要があります。AMD64の `SAR` 命令は、シフト量がビット幅以上の場合、シフト量をビット幅-1として扱います。
    新しいビット操作 `(ORQ <y.Type> y (NOTQ <y.Type> (SBBQcarrymask <y.Type> (CMPQconst <TypeFlags> [64] y))))` は、`y` が64以上の場合に、`SARQ` 命令に渡されるシフト量を実質的に63（またはそれ以上の大きな値）に設定することで、`SARQ` が期待通りの結果（符号拡張）を生成するようにします。
    このアプローチは、`CMOV` 命令を使用するよりも、命令の依存関係が単純になり、CPUの実行ユニットをより効率的に利用できるため、パフォーマンスが向上する可能性があります。

3.  **ビット単位NOT (`OCOM`) の直接サポート**:
    `OCOM` 演算子がSSA形式で直接サポートされ、AMD64の `NOT` 命令にマッピングされることで、コンパイラは `^x` のようなGoのビット単位NOT演算に対して、より直接的で効率的な機械語コードを生成できるようになりました。これにより、中間的な変換ステップが減り、コードの品質が向上します。

4.  **定数畳み込みの強化**:
    `rewriteAMD64.go` に追加された多数の定数畳み込みルールは、コンパイル時に定数オペランドを持つ算術およびビット演算の結果を計算し、その結果で置き換えることで、実行時の計算を不要にします。これは、コンパイラの基本的な最適化の一つであり、生成されるコードの実行速度とサイズの両方に良い影響を与えます。

これらの変更は、GoコンパイラのSSAバックエンドがより成熟し、より最適化された機械語コードを生成するための重要なステップでした。特に、Go言語の厳密なシフト仕様を効率的に実装するための基盤を強化しています。

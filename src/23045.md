## 元コミット内容
```
runtime: finish sweeping before concurrent GC starts

Currently, the concurrent sweep follows a 1:1 rule: when allocation
needs a span, it sweeps a span (likewise, when a large allocation
needs N pages, it sweeps until it frees N pages). This rule worked
well for the STW collector (especially when GOGC==100) because it did
no more sweeping than necessary to keep the heap from growing, would
generally finish sweeping just before GC, and ensured good temporal
locality between sweeping a page and allocating from it.

It doesn't work well with concurrent GC. Since concurrent GC requires
starting GC earlier (sometimes much earlier), the sweep often won't be
done when GC starts. Unfortunately, the first thing GC has to do is
finish the sweep. In the mean time, the mutator can continue
allocating, pushing the heap size even closer to the goal size. This
worked okay with the 7/8ths trigger, but it gets into a vicious cycle
with the GC trigger controller: if the mutator is allocating quickly
and driving the trigger lower, more and more sweep work will be left
to GC; this both causes GC to take longer (allowing the mutator to
allocate more during GC) and delays the start of the concurrent mark
phase, which throws off the GC controller's statistics and generally
causes it to push the trigger even lower.

As an example of a particularly bad case, the garbage benchmark with
GOMAXPROCS=4 and -benchmem 512 (MB) spends the first 0.4-0.8 seconds
of each GC cycle sweeping, during which the heap grows by between
109MB and 252MB.

To fix this, this change replaces the 1:1 sweep rule with a
proportional sweep rule. At the end of GC, GC knows exactly how much
heap allocation will occur before the next concurrent GC as well as
how many span pages must be swept. This change computes this "sweep
ratio" and when the mallocgc asks for a span, the mcentral sweeps
enough spans to bring the swept span count into ratio with the
allocated byte count.

On the benchmark from above, this entirely eliminates sweeping at the
beginning of GC, which reduces the time between startGC readying the
GC goroutine and GC stopping the world for sweep termination to ~100µs
during which the heap grows at most 134KB.

## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）におけるスイープ（sweep）処理の効率を改善することを目的としています。特に、並行GC（concurrent GC）の導入によって顕在化した問題に対処しています。

従来のGoのGCでは、スイープ処理は「1:1ルール」に従っていました。これは、アロケータが新しいスパン（メモリのチャンク）を必要とするたびに、1つのスパンをスイープするというものでした。大きなアロケーションの場合も同様に、必要なページ数に応じてスイープが行われました。この1:1ルールは、ストップ・ザ・ワールド（STW）GCにおいてはうまく機能していました。STW GCでは、GCが開始される直前にスイープが完了し、ヒープの成長を抑制し、スイープされたページとそこからのアロケーションの間に良好な時間的局所性（temporal locality）を確保していました。

しかし、並行GCの導入により、この1:1ルールは問題を引き起こすようになりました。並行GCは、GCサイクルをより早期に（時にはかなり早期に）開始する必要があるため、GCが開始される時点でスイープが完了していないことが頻繁に発生しました。GCが最初にしなければならないことは、未完了のスイープを終了させることでした。この間、ミューテータ（ユーザープログラム）はアロケーションを継続し、ヒープサイズを目標サイズにさらに近づけてしまいます。

この問題は、GCトリガーコントローラとの間で「悪循環」を生み出しました。ミューテータが高速にアロケーションを行うと、GCトリガーがより低い値に設定され、結果としてGC開始時に未完了のスイープ作業が大量に残されることになります。これにより、GCの実行時間が長くなり（その間にもミューテータはさらにアロケーションを行う）、並行マークフェーズの開始が遅延します。これはGCコントローラの統計を狂わせ、さらにトリガーを低く設定させる原因となりました。

具体的な例として、`GOMAXPROCS=4`および`-benchmem 512 (MB)`を設定した`garbage`ベンチマークでは、各GCサイクルの最初の0.4〜0.8秒がスイープに費やされ、その間にヒープが109MBから252MBも成長するという深刻な問題が発生していました。このコミットは、この非効率性を解消し、GC開始前にスイープを完了させることで、GCのパフォーマンスとヒープ管理の安定性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションの基本的な仕組みと、特に「スイープ」フェーズに関する知識が必要です。

*   **ガベージコレクション (GC)**: Goのランタイムは、不要になったメモリを自動的に解放するガベージコレクタを備えています。これにより、開発者は手動でのメモリ管理から解放されます。GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにしています。
    *   **マーク (Mark)**: GCの最初のフェーズで、到達可能な（プログラムから参照されている）オブジェクトを特定し、マークします。
    *   **スイープ (Sweep)**: マークされなかった（到達不可能な）オブジェクトが占めていたメモリ領域を解放し、再利用可能にするフェーズです。

*   **ストップ・ザ・ワールド (STW) GC**: 従来のGC方式の一つで、GCが実行されている間、ユーザープログラム（ミューテータ）の実行を完全に停止させます。これにより、GCは一貫性のあるヒープの状態を安全に操作できますが、プログラムの応答性が一時的に低下するという問題があります。

*   **並行GC (Concurrent GC)**: Go 1.5で導入されたGC方式で、GCの大部分の処理（特にマークフェーズ）をユーザープログラムと並行して実行します。これにより、STWポーズの時間を大幅に短縮し、アプリケーションのレイテンシを改善します。しかし、並行して動作するため、GCがヒープの状態を変更している間にミューテータもヒープを変更する可能性があり、より複雑な同期と調整が必要になります。

*   **スパン (Span)**: Goのメモリ管理において、ヒープは「スパン」と呼ばれる連続したメモリページのチャンクに分割されます。各スパンは特定のサイズのオブジェクトを格納するために使用されます。

*   **`mheap`**: Goランタイムにおけるヒープ全体の管理構造体です。スパンのリストや、GCに関する統計情報などを保持します。

*   **`mcentral`**: 特定のサイズクラスのスパンを管理する構造体です。`mcache`（各P（プロセッサ）に紐づくローカルキャッシュ）にスパンを提供し、必要に応じて`mheap`から新しいスパンを取得します。

*   **スイープのタイミング**: スイープは、GCサイクルの一部として、またはアロケーション時にオンデマンドで行われることがあります。アロケーション時にスイープを行うことで、メモリが不足した際に即座に利用可能なスパンを確保できます。

*   **GCトリガーコントローラ**: GoのGCは、ヒープの成長に基づいて次のGCサイクルを開始するタイミングを決定します。このコントローラは、ヒープの使用状況やアロケーションレートに基づいて、GCの目標ヒープサイズ（`next_gc`）を動的に調整します。

このコミットは、並行GCの文脈で、スイープがGC開始時に完了していないことによるパフォーマンス上の問題を解決するために、「1:1ルール」から「比例スイープルール」への移行を提案しています。

## 技術的詳細

このコミットの核心は、従来の「1:1スイープルール」を「比例スイープルール」に置き換えることです。

**従来の1:1スイープルールとその問題点**:
前述の通り、従来のルールでは、アロケーションが必要なときにスパンをスイープしていました。これはSTW GCでは問題ありませんでしたが、並行GCではGCが早期に開始されるため、スイープが完了していない状態でGCが開始されることが頻繁にありました。GCが開始されると、まず未完了のスイープを完了させる必要があり、その間にもミューテータはアロケーションを継続し、ヒープサイズが目標に近づき、GCの効率を低下させるという悪循環に陥っていました。

**新しい比例スイープルール**:
この変更では、GCサイクルの終了時に、次の並行GCが開始されるまでにどれだけヒープアロケーションが発生するか、そしてどれだけのスパンページをスイープする必要があるかを正確に計算します。この情報に基づいて、「スイープ比率（sweep ratio）」が計算されます。

具体的には、`mheap_.sweepPagesPerByte`という新しいフィールドが導入され、これは「スイープすべきページ数 / 次のGCまでにアロケーションされると予想されるバイト数」という比率を表します。また、`mheap_.pagesSwept`は、現在のGCサイクルで既にスイープされたページ数を追跡します。

アロケーション（`mallocgc`がスパンを要求する際）が発生すると、`mcentral`は、このスイープ比率と現在のアロケーションバイト数に基づいて、スイープされたスパンの数がアロケーションされたバイト数と比例するように、十分なスパンをスイープします。これにより、GCが開始される前に、必要なスイープ作業の大部分が完了している状態を目指します。

**実装の詳細**:

1.  **`mheap`構造体の変更**:
    *   `pagesSwept` (uint64): 現在のGCサイクルで原子的に更新される、スイープされたページ数。
    *   `sweepPagesPerByte` (float64): 比例スイープ比率。ロックなしで読み取られ、ロックありで書き込まれます。

2.  **`mcentral_CacheSpan`の変更**:
    *   この関数は、`MCache`にスパンを割り当てる際に呼び出されます。
    *   ここで比例スイープ作業が実行されます。`memstats.heap_live`（現在のライブヒープサイズ）と`memstats.heap_marked`（マークされたヒープサイズ）の差分、および`mheap_.sweepPagesPerByte`を使用して、スイープすべきページ数を計算します。
    *   `gosweepone()`を呼び出すことで、スイープ作業を進めます。これにより、アロケーション中にバックグラウンドでスイープが進行し、GC開始時のスイープ作業を減らします。

3.  **`gcSweep`の変更**:
    *   GCのスイープフェーズの最後に、次のGCサイクルまでにスイープする必要があるページ数を計算し、比例スイープの統計を設定します。
    *   `pagesToSweep`を計算し、`heapDistance`（次のGCまでのヒープアロケーションの予測量）を考慮して、`mheap_.sweepPagesPerByte`を設定します。これにより、次のGCが開始されるまでに、必要なスイープが完了するように調整されます。
    *   `heapDistance`には、丸め誤差や並行スイープによる未スイープページを考慮して、少しマージンが追加されます。

4.  **`mSpan_Sweep`の変更**:
    *   スパンがスイープされるたびに、`mheap_.pagesSwept`を原子的に更新します。これにより、スイープの進行状況が正確に追跡されます。

この変更により、`garbage`ベンチマークのような負荷の高いシナリオでも、GC開始時のスイープ作業がほぼ完全に排除され、GCゴルーチンが準備されてからGCがSTWでスイープ終了を待つまでの時間が約100µsに短縮され、その間のヒープ成長も最大134KBに抑えられました。これは、並行GCの効率と安定性を大幅に向上させるものです。

## コアとなるコードの解説

### `src/runtime/mcentral.go`
#### `func mCentral_CacheSpan(c *mcentral) *mspan`
この関数は、`MCache`（各Pに紐づくローカルキャッシュ）がスパンを要求する際に呼び出されます。変更点として、この関数内で比例スイープ作業が実行されるようになりました。
```go
// Perform proportional sweep work. We don't directly reuse
// the spans we're sweeping here for this allocation because
// these can hold any size class. We'll sweep one more span
// below and use that because it will have the right size
// class and be hot in our cache.
pagesOwed := int64(mheap_.sweepPagesPerByte * float64(memstats.heap_live-memstats.heap_marked))
if pagesOwed-int64(mheap_.pagesSwept) > 1 {
    // Get the debt down to one page, which we're likely
    // to take care of below (if we don't, that's fine;
    // we'll pick up the slack later).
    for pagesOwed-int64(atomicload64(&mheap_.pagesSwept)) > 1 {
        if gosweepone() == ^uintptr(0) {
            mheap_.sweepPagesPerByte = 0
            break
        }
    }
}
```
ここで、`mheap_.sweepPagesPerByte`と現在のヒープの状態（`memstats.heap_live`と`memstats.heap_marked`の差）に基づいて、スイープすべきページ数（`pagesOwed`）を計算します。そして、`pagesOwed`が`mheap_.pagesSwept`（既にスイープされたページ数）よりも十分に大きい場合、`gosweepone()`を繰り返し呼び出してスイープ作業を進めます。これにより、アロケーションの合間にスイープが進行し、GC開始時の負担を軽減します。

### `src/runtime/mgc.go`
#### `func gc(mode int)`
この関数はGCのメインエントリポイントです。変更点として、GC開始時に残っているスイープ作業を完了させる部分のコメントが更新されました。
```go
// This shouldn't happen if we're being invoked in background
// mode since proportional sweep should have just finished
// sweeping everything, but rounding errors, etc, may leave a
// few spans unswept. In forced mode, this is necessary since
// GC can be forced at any point in the sweeping cycle.
for gosweepone() != ^uintptr(0) {
    sweep.nbgsweep++
}
```
これは、比例スイープが導入されたことで、バックグラウンドGCモードではほとんどのスイープが完了しているはずだが、丸め誤差などにより少数のスパンが未スイープのまま残る可能性があることを示しています。強制GCモードでは、スイープサイクル中の任意の時点でGCが強制される可能性があるため、この処理は引き続き必要です。

#### `func gcSweep(mode int)`
この関数はGCのスイープフェーズを管理します。比例スイープの統計を設定する重要なロジックが追加されました。
```go
// Account how much sweeping needs to be done before the next
// GC cycle and set up proportional sweep statistics.
var pagesToSweep uintptr
for _, s := range work.spans {
    if s.state == mSpanInUse {
        pagesToSweep += s.npages
    }
}
heapDistance := int64(memstats.next_gc) - int64(memstats.heap_live)
// Add a little margin so rounding errors and concurrent
// sweep are less likely to leave pages unswept when GC starts.
heapDistance -= 1024 * 1024
if heapDistance < _PageSize {
    // Avoid setting the sweep ratio extremely high
    heapDistance = _PageSize
}
lock(&mheap_.lock)
mheap_.sweepPagesPerByte = float64(pagesToSweep) / float64(heapDistance)
mheap_.pagesSwept = 0
unlock(&mheap_.lock)
```
GCの終了時に、次のGCサイクルまでにスイープする必要がある総ページ数（`pagesToSweep`）を計算します。また、現在のライブヒープサイズから次のGC目標サイズまでの距離（`heapDistance`）を計算し、これらを用いて`mheap_.sweepPagesPerByte`（スイープ比率）を設定します。これにより、次のGCが開始されるまでに、必要なスイープが完了するように、アロケーション時のスイープ作業が調整されます。

### `src/runtime/mgcsweep.go`
#### `func mSpan_Sweep(s *mspan, preserve bool) bool`
この関数は個々のスパンをスイープする際に呼び出されます。変更点として、スイープされたページ数を追跡するロジックが追加されました。
```go
xadd64(&mheap_.pagesSwept, int64(s.npages))
```
スパン`s`がスイープされるたびに、そのスパンが持つページ数（`s.npages`）を`mheap_.pagesSwept`に原子的に加算します。これにより、システム全体でどれだけのページがスイープされたかを正確に把握できます。

### `src/runtime/mheap.go`
#### `type mheap struct`
`mheap`構造体に、比例スイープをサポートするための新しいフィールドが追加されました。
```go
// Proportional sweep
pagesSwept        uint64  // pages swept this cycle; updated atomically
sweepPagesPerByte float64 // proportional sweep ratio; written with lock, read without
```
*   `pagesSwept`: 現在のGCサイクルでスイープされたページ数を記録します。`mSpan_Sweep`によって原子的に更新されます。
*   `sweepPagesPerByte`: 比例スイープの比率を保持します。`gcSweep`によって設定され、`mCentral_CacheSpan`などで読み取られます。

#### `func mHeap_Alloc_m(h *mheap, npage uintptr, sizeclass int32, large bool) *mspan`
この関数は、ヒープから新しいスパンを割り当てる際に呼び出されます。変更点として、スイープが完了していない場合に`mHeap_Reclaim`を呼び出す部分にコメントが追加されました。
```go
// TODO(austin): This tends to sweep a large number of
// spans in order to find a few completely free spans
// (for example, in the garbage benchmark, this sweeps
// ~30x the number of pages its trying to allocate).
// If GC kept a bit for whether there were any marks
// in a span, we could release these free spans
// at the end of GC and eliminate this entirely.

```
このコメントは、`mHeap_Reclaim`がまだ非効率である可能性を示唆しており、将来的な改善の余地があることを示しています。これは、比例スイープの導入後も、アロケーション時のスイープが完全に最適化されたわけではないことを示唆しています。

## 元コミット内容
```
runtime: finish sweeping before concurrent GC starts

Currently, the concurrent sweep follows a 1:1 rule: when allocation
needs a span, it sweeps a span (likewise, when a large allocation
needs N pages, it sweeps until it frees N pages). This rule worked
well for the STW collector (especially when GOGC==100) because it did
no more sweeping than necessary to keep the heap from growing, would
generally finish sweeping just before GC, and ensured good temporal
locality between sweeping a page and allocating from it.

It doesn't work well with concurrent GC. Since concurrent GC requires
starting GC earlier (sometimes much earlier), the sweep often won't be
done when GC starts. Unfortunately, the first thing GC has to do is
finish the sweep. In the mean time, the mutator can continue
allocating, pushing the heap size even closer to the goal size. This
worked okay with the 7/8ths trigger, but it gets into a vicious cycle
with the GC trigger controller: if the mutator is allocating quickly
and driving the trigger lower, more and more sweep work will be left
to GC; this both causes GC to take longer (allowing the mutator to
allocate more during GC) and delays the start of the concurrent mark
phase, which throws off the GC controller's statistics and generally
causes it to push the trigger even lower.

As an example of a particularly bad case, the garbage benchmark with
GOMAXPROCS=4 and -benchmem 512 (MB) spends the first 0.4-0.8 seconds
of each GC cycle sweeping, during which the heap grows by between
109MB and 252MB.

To fix this, this change replaces the 1:1 sweep rule with a
proportional sweep rule. At the end of GC, GC knows exactly how much
heap allocation will occur before the next concurrent GC as well as
how many span pages must be swept. This change computes this "sweep
ratio" and when the mallocgc asks for a span, the mcentral sweeps
enough spans to bring the swept span count into ratio with the
allocated byte count.

On the benchmark from above, this entirely eliminates sweeping at the
beginning of GC, which reduces the time between startGC readying the
GC goroutine and GC stopping the world for sweep termination to ~100µs
during which the heap grows at most 134KB.

```

## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）におけるスイープ（sweep）処理の効率を改善することを目的としています。特に、並行GC（concurrent GC）の導入によって顕在化した問題に対処しています。

従来のGoのGCでは、スイープ処理は「1:1ルール」に従っていました。これは、アロケータが新しいスパン（メモリのチャンク）を必要とするたびに、1つのスパンをスイープするというものでした。大きなアロケーションの場合も同様に、必要なページ数に応じてスイープが行われました。この1:1ルールは、ストップ・ザ・ワールド（STW）GCにおいてはうまく機能していました。STW GCでは、GCが開始される直前にスイープが完了し、ヒープの成長を抑制し、スイープされたページとそこからのアロケーションの間に良好な時間的局所性（temporal locality）を確保していました。

しかし、並行GCの導入により、この1:1ルールは問題を引き起こすようになりました。並行GCは、GCサイクルをより早期に（時にはかなり早期に）開始する必要があるため、GCが開始される時点でスイープが完了していないことが頻繁に発生しました。GCが最初にしなければならないことは、未完了のスイープを終了させることでした。この間、ミューテータ（ユーザープログラム）はアロケーションを継続し、ヒープサイズを目標サイズにさらに近づけてしまいます。

この問題は、GCトリガーコントローラとの間で「悪循環」を生み出しました。ミューテータが高速にアロケーションを行うと、GCトリガーがより低い値に設定され、結果としてGC開始時に未完了のスイープ作業が大量に残されることになります。これにより、GCの実行時間が長くなり（その間にもミューテータはさらにアロケーションを行う）、並行マークフェーズの開始が遅延します。これはGCコントローラの統計を狂わせ、さらにトリガーを低く設定させる原因となりました。

具体的な例として、`GOMAXPROCS=4`および`-benchmem 512 (MB)`を設定した`garbage`ベンチマークでは、各GCサイクルの最初の0.4〜0.8秒がスイープに費やされ、その間にヒープが109MBから252MBも成長するという深刻な問題が発生していました。このコミットは、この非効率性を解消し、GC開始前にスイープを完了させることで、GCのパフォーマンスとヒープ管理の安定性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションの基本的な仕組みと、特に「スイープ」フェーズに関する知識が必要です。

*   **ガベージコレクション (GC)**: Goのランタイムは、不要になったメモリを自動的に解放するガベージコレクタを備えています。これにより、開発者は手動でのメモリ管理から解放されます。GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにしています。
    *   **マーク (Mark)**: GCの最初のフェーズで、到達可能な（プログラムから参照されている）オブジェクトを特定し、マークします。
    *   **スイープ (Sweep)**: マークされなかった（到達不可能な）オブジェクトが占めていたメモリ領域を解放し、再利用可能にするフェーズです。

*   **ストップ・ザ・ワールド (STW) GC**: 従来のGC方式の一つで、GCが実行されている間、ユーザープログラム（ミューテータ）の実行を完全に停止させます。これにより、GCは一貫性のあるヒープの状態を安全に操作できますが、プログラムの応答性が一時的に低下するという問題があります。

*   **並行GC (Concurrent GC)**: Go 1.5で導入されたGC方式で、GCの大部分の処理（特にマークフェーズ）をユーザープログラムと並行して実行します。これにより、STWポーズの時間を大幅に短縮し、アプリケーションのレイテンシを改善します。しかし、並行して動作するため、GCがヒープの状態を変更している間にミューテータもヒープを変更する可能性があり、より複雑な同期と調整が必要になります。

*   **スパン (Span)**: Goのメモリ管理において、ヒープは「スパン」と呼ばれる連続したメモリページのチャンクに分割されます。各スパンは特定のサイズのオブジェクトを格納するために使用されます。

*   **`mheap`**: Goランタイムにおけるヒープ全体の管理構造体です。スパンのリストや、GCに関する統計情報などを保持します。

*   **`mcentral`**: 特定のサイズクラスのスパンを管理する構造体です。`mcache`（各P（プロセッサ）に紐づくローカルキャッシュ）にスパンを提供し、必要に応じて`mheap`から新しいスパンを取得します。

*   **スイープのタイミング**: スイープは、GCサイクルの一部として、またはアロケーション時にオンデマンドで行われることがあります。アロケーション時にスイープを行うことで、メモリが不足した際に即座に利用可能なスパンを確保できます。

*   **GCトリガーコントローラ**: GoのGCは、ヒープの成長に基づいて次のGCサイクルを開始するタイミングを決定します。このコントローラは、ヒープの使用状況やアロケーションレートに基づいて、GCの目標ヒープサイズ（`next_gc`）を動的に調整します。

このコミットは、並行GCの文脈で、スイープがGC開始時に完了していないことによるパフォーマンス上の問題を解決するために、「1:1ルール」から「比例スイープルール」への移行を提案しています。

## 技術的詳細

このコミットの核心は、従来の「1:1スイープルール」を「比例スイープルール」に置き換えることです。

**従来の1:1スイープルールとその問題点**:
前述の通り、従来のルールでは、アロケーションが必要なときにスパンをスイープしていました。これはSTW GCでは問題ありませんでしたが、並行GCではGCが早期に開始されるため、スイープが完了していない状態でGCが開始されることが頻繁にありました。GCが開始されると、まず未完了のスイープを完了させる必要があり、その間にもミューテータはアロケーションを継続し、ヒープサイズが目標に近づき、GCの効率を低下させるという悪循環に陥っていました。

**新しい比例スイープルール**:
この変更では、GCサイクルの終了時に、次の並行GCが開始されるまでにどれだけヒープアロケーションが発生するか、そしてどれだけのスパンページをスイープする必要があるかを正確に計算します。この情報に基づいて、「スイープ比率（sweep ratio）」が計算されます。

具体的には、`mheap_.sweepPagesPerByte`という新しいフィールドが導入され、これは「スイープすべきページ数 / 次のGCまでにアロケーションされると予想されるバイト数」という比率を表します。また、`mheap_.pagesSwept`は、現在のGCサイクルで既にスイープされたページ数を追跡します。

アロケーション（`mallocgc`がスパンを要求する際）が発生すると、`mcentral`は、このスイープ比率と現在のアロケーションバイト数に基づいて、スイープされたスパンの数がアロケーションされたバイト数と比例するように、十分なスパンをスイープします。これにより、GCが開始される前に、必要なスイープ作業の大部分が完了している状態を目指します。

**実装の詳細**:

1.  **`mheap`構造体の変更**:
    *   `pagesSwept` (uint64): 現在のGCサイクルで原子的に更新される、スイープされたページ数。
    *   `sweepPagesPerByte` (float64): 比例スイープ比率。ロックなしで読み取られ、ロックありで書き込まれます。

2.  **`mcentral_CacheSpan`の変更**:
    *   この関数は、`MCache`にスパンを割り当てる際に呼び出されます。
    *   ここで比例スイープ作業が実行されます。`memstats.heap_live`（現在のライブヒープサイズ）と`memstats.heap_marked`（マークされたヒープサイズ）の差分、および`mheap_.sweepPagesPerByte`を使用して、スイープすべきページ数を計算します。
    *   `gosweepone()`を呼び出すことで、スイープ作業を進めます。これにより、アロケーション中にバックグラウンドでスイープが進行し、GC開始時のスイープ作業を減らします。

3.  **`gcSweep`の変更**:
    *   GCのスイープフェーズの最後に、次のGCサイクルまでにスイープする必要があるページ数を計算し、比例スイープの統計を設定します。
    *   `pagesToSweep`を計算し、`heapDistance`（次のGCまでのヒープアロケーションの予測量）を考慮して、`mheap_.sweepPagesPerByte`を設定します。これにより、次のGCが開始されるまでに、必要なスイープが完了するように調整されます。
    *   `heapDistance`には、丸め誤差や並行スイープによる未スイープページを考慮して、少しマージンが追加されます。

4.  **`mSpan_Sweep`の変更**:
    *   スパンがスイープされるたびに、`mheap_.pagesSwept`を原子的に更新します。これにより、スイープの進行状況が正確に追跡されます。

この変更により、`garbage`ベンチマークのような負荷の高いシナリオでも、GC開始時のスイープ作業がほぼ完全に排除され、GCゴルーチンが準備されてからGCがSTWでスイープ終了を待つまでの時間が約100µsに短縮され、その間のヒープ成長も最大134KBに抑えられました。これは、並行GCの効率と安定性を大幅に向上させるものです。

## コアとなるコードの解説

### `src/runtime/mcentral.go`
#### `func mCentral_CacheSpan(c *mcentral) *mspan`
この関数は、`MCache`（各Pに紐づくローカルキャッシュ）がスパンを要求する際に呼び出されます。変更点として、この関数内で比例スイープ作業が実行されるようになりました。
```go
// Perform proportional sweep work. We don't directly reuse
// the spans we're sweeping here for this allocation because
// these can hold any size class. We'll sweep one more span
// below and use that because it will have the right size
// class and be hot in our cache.
pagesOwed := int64(mheap_.sweepPagesPerByte * float64(memstats.heap_live-memstats.heap_marked))
if pagesOwed-int64(mheap_.pagesSwept) > 1 {
    // Get the debt down to one page, which we're likely
    // to take care of below (if we don't, that's fine;
    // we'll pick up the slack later).
    for pagesOwed-int64(atomicload64(&mheap_.pagesSwept)) > 1 {
        if gosweepone() == ^uintptr(0) {
            mheap_.sweepPagesPerByte = 0
            break
        }
    }
}
```
ここで、`mheap_.sweepPagesPerByte`と現在のヒープの状態（`memstats.heap_live`と`memstats.heap_marked`の差）に基づいて、スイープすべきページ数（`pagesOwed`）を計算します。そして、`pagesOwed`が`mheap_.pagesSwept`（既にスイープされたページ数）よりも十分に大きい場合、`gosweepone()`を繰り返し呼び出してスイープ作業を進めます。これにより、アロケーションの合間にスイープが進行し、GC開始時の負担を軽減します。

### `src/runtime/mgc.go`
#### `func gc(mode int)`
この関数はGCのメインエントリポイントです。変更点として、GC開始時に残っているスイープ作業を完了させる部分のコメントが更新されました。
```go
// This shouldn't happen if we're being invoked in background
// mode since proportional sweep should have just finished
// sweeping everything, but rounding errors, etc, may leave a
// few spans unswept. In forced mode, this is necessary since
// GC can be forced at any point in the sweeping cycle.
for gosweepone() != ^uintptr(0) {
    sweep.nbgsweep++
}
```
これは、比例スイープが導入されたことで、バックグラウンドGCモードではほとんどのスイープが完了しているはずだが、丸め誤差などにより少数のスパンが未スイープのまま残る可能性があることを示しています。強制GCモードでは、スイープサイクル中の任意の時点でGCが強制される可能性があるため、この処理は引き続き必要です。

#### `func gcSweep(mode int)`
この関数はGCのスイープフェーズを管理します。比例スイープの統計を設定する重要なロジックが追加されました。
```go
// Account how much sweeping needs to be done before the next
// GC cycle and set up proportional sweep statistics.
var pagesToSweep uintptr
for _, s := range work.spans {
    if s.state == mSpanInUse {
        pagesToSweep += s.npages
    }
}
heapDistance := int64(memstats.next_gc) - int64(memstats.heap_live)
// Add a little margin so rounding errors and concurrent
// sweep are less likely to leave pages unswept when GC starts.
heapDistance -= 1024 * 1024
if heapDistance < _PageSize {
    // Avoid setting the sweep ratio extremely high
    heapDistance = _PageSize
}
lock(&mheap_.lock)
mheap_.sweepPagesPerByte = float64(pagesToSweep) / float64(heapDistance)
mheap_.pagesSwept = 0
unlock(&mheap_.lock)
```
GCの終了時に、次のGCサイクルまでにスイープする必要がある総ページ数（`pagesToSweep`）を計算します。また、現在のライブヒープサイズから次のGC目標サイズまでの距離（`heapDistance`）を計算し、これらを用いて`mheap_.sweepPagesPerByte`（スイープ比率）を設定します。これにより、次のGCが開始されるまでに、必要なスイープが完了するように、アロケーション時のスイープ作業が調整されます。

### `src/runtime/mgcsweep.go`
#### `func mSpan_Sweep(s *mspan, preserve bool) bool`
この関数は個々のスパンをスイープする際に呼び出されます。変更点として、スイープされたページ数を追跡するロジックが追加されました。
```go
xadd64(&mheap_.pagesSwept, int64(s.npages))
```
スパン`s`がスイープされるたびに、そのスパンが持つページ数（`s.npages`）を`mheap_.pagesSwept`に原子的に加算します。これにより、システム全体でどれだけのページがスイープされたかを正確に把握できます。

### `src/runtime/mheap.go`
#### `type mheap struct`
`mheap`構造体に、比例スイープをサポートするための新しいフィールドが追加されました。
```go
// Proportional sweep
pagesSwept        uint64  // pages swept this cycle; updated atomically
sweepPagesPerByte float64 // proportional sweep ratio; written with lock, read without
```
*   `pagesSwept`: 現在のGCサイクルでスイープされたページ数を記録します。`mSpan_Sweep`によって原子的に更新されます。
*   `sweepPagesPerByte`: 比例スイープの比率を保持します。`gcSweep`によって設定され、`mCentral_CacheSpan`などで読み取られます。

#### `func mHeap_Alloc_m(h *mheap, npage uintptr, sizeclass int32, large bool) *mspan`
この関数は、ヒープから新しいスパンを割り当てる際に呼び出されます。変更点として、スイープが完了していない場合に`mHeap_Reclaim`を呼び出す部分にコメントが追加されました。
```go
// TODO(austin): This tends to sweep a large number of
// spans in order to find a few completely free spans
// (for example, in the garbage benchmark, this sweeps
// ~30x the number of pages its trying to allocate).
// If GC kept a bit for whether there were any marks
// in a span, we could release these free spans
// at the end of GC and eliminate this entirely.
mHeap_Reclaim(h, npage)
```
このコメントは、`mHeap_Reclaim`がまだ非効率である可能性を示唆しており、将来的な改善の余地があることを示しています。これは、比例スイープの導入後も、アロケーション時のスイープが完全に最適化されたわけではないことを示唆しています。

# [インデックス 21509] ファイルの概要

このコミットは、Goコンパイラ (`cmd/gc`) におけるレース検出器の不具合を修正するものです。具体的には、`runtime.writebarrierfat` 関数が `typedmemmove` にリネームされた際に、レース検出器がその変更を追従できず、必要な計測（instrumentation）を挿入できなくなった問題に対処しています。

## コミット

`cmd/gc`: `writebarrierfat` が `typedmemmove` にリネームされた後の `racewalk` の修正

関数のリネームにより、レース検出器がその名前を探しても見つけられなくなり、必要な計測を挿入しなくなったため、レース検出器が壊れていました。

## 変更の背景

Goのランタイムには、並行処理におけるデータ競合（data race）を検出するためのレース検出器（Race Detector）が組み込まれています。このレース検出器は、プログラムの実行中にメモリへのアクセスを監視し、複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも一方が書き込み操作である場合に警告を発します。

レース検出器が正しく機能するためには、特定のランタイム関数、特にガベージコレクション（GC）のライトバリア（write barrier）に関連する関数呼び出しに対して、特別な計測（instrumentation）を挿入する必要があります。ライトバリアは、GCがオブジェクトの参照関係を正確に追跡するために、ポインタの書き込み時に実行されるコードです。

以前のコミットで、ランタイム関数 `runtime.writebarrierfat` が `runtime.typedmemmove` にリネームされました。`writebarrierfat` は、大きな構造体や配列のコピー時にライトバリアを適用するために使用されていました。このリネームは、関数の目的をより正確に反映するためのものでしたが、Goコンパイラ (`cmd/gc`) 内のレース検出器のロジックがこの名前変更を認識していませんでした。

具体的には、`cmd/gc/racewalk.c` 内のコードは、抽象構文木（AST）を走査し、`runtime.writebarrier` で始まる関数名や `runtime.writebarrierfat` という特定の関数名を探していました。名前が `typedmemmove` に変更されたことで、このロジックは該当する関数呼び出しを見つけられなくなり、結果として必要なレース検出器の計測が挿入されなくなりました。これにより、`typedmemmove` を介したメモリ操作におけるデータ競合が検出されなくなるという不具合が発生しました。

このコミットは、この不具合を修正し、レース検出器が `typedmemmove` 関数に対しても正しく計測を挿入できるようにすることを目的としています。

## 前提知識の解説

### Goのガベージコレクションとライトバリア

Goは、自動メモリ管理のためにガベージコレクション（GC）を使用します。GCは、プログラムがもはや到達できないメモリを自動的に解放します。GoのGCは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行してGCが動作します。

ライトバリアは、並行GCにおいて非常に重要なメカニズムです。プログラムがヒープ上のポインタを書き換える際に、GCがオブジェクトグラフの一貫性を保つために実行される小さなコードスニペットです。これにより、GCがオブジェクトをスキャンしている最中にポインタが変更されても、GCが誤って到達可能なオブジェクトを回収してしまうことを防ぎます。

### Goのレース検出器 (Race Detector)

Goのレース検出器は、並行プログラムにおけるデータ競合を特定するためのツールです。データ競合は、複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つが書き込み操作であり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に発生します。データ競合は、予測不能な動作やバグの原因となるため、Goのツールチェインはこれを検出する機能を提供しています。

レース検出器は、コンパイル時または実行時にコードに計測（instrumentation）を挿入することで機能します。この計測は、メモリへの読み書き操作を監視し、競合のパターンを検出します。ランタイムの内部関数、特にメモリ操作やGCに関連する関数は、レース検出器が正しく動作するために、特別な方法で計測される必要があります。

### `cmd/gc` (Goコンパイラ)

`cmd/gc` は、Go言語の公式コンパイラです。Goのソースコードをコンパイルして実行可能なバイナリを生成します。コンパイルプロセスには、字句解析、構文解析、抽象構文木（AST）の生成、型チェック、最適化、コード生成などが含まれます。レース検出器の計測の挿入も、このコンパイルプロセスの一部として行われます。

### 抽象構文木 (AST) と `racewalk.c`

コンパイラは、ソースコードを解析して抽象構文木（AST）を構築します。ASTは、プログラムの構造を木構造で表現したものです。コンパイラの様々なフェーズ（型チェック、最適化、コード生成など）は、このASTを走査（walk）して処理を行います。

`src/cmd/gc/racewalk.c` は、Goコンパイラの一部であり、レース検出器に関連するASTの走査ロジックを含んでいます。このファイルは、ASTを走査しながら、特定の関数呼び出し（特にライトバリア関連の関数）を識別し、レース検出器が必要とする追加のコード（計測）を挿入する役割を担っています。

### `Node` と `OCALLFUNC`

`Node` は、GoコンパイラがASTを表現するために使用するデータ構造です。ASTの各要素（変数宣言、関数呼び出し、演算子など）は `Node` として表現されます。
`OCALLFUNC` は、`Node` の種類（オペレーションコード）の一つで、関数呼び出しを表します。`racewalk.c` は、`OCALLFUNC` タイプのノードを処理する際に、それが特定のランタイム関数（例: `writebarrier` や `typedmemmove`）への呼び出しであるかどうかをチェックします。

### `sym` (Symbol)

コンパイラにおいて、`sym` (symbol) は、変数、関数、型などのプログラム要素の名前と、それに関連する情報（型、スコープ、メモリ位置など）を管理するためのデータ構造です。`n->left->sym` は、関数呼び出しノード `n` の左の子（通常は呼び出される関数を表す）のシンボルを参照します。`sym->pkg` はシンボルが属するパッケージを、`sym->name` はシンボル名をそれぞれ表します。

## 技術的詳細

Goのレース検出器は、コンパイル時に特定のランタイム関数呼び出しをフックすることで機能します。特に、メモリの書き込み操作を伴うランタイム関数（例: `memmove`, `memset` など、そしてライトバリア関連の関数）は、レース検出器が監視すべき重要なポイントです。

`src/cmd/gc/racewalk.c` 内の `racewalknode` 関数は、ASTを再帰的に走査します。`OCALLFUNC`（関数呼び出し）ノードに遭遇すると、呼び出される関数のシンボル名を確認します。

以前のコードでは、以下の条件でライトバリア関連の関数呼び出しを識別していました。
1.  関数が `runtime` パッケージに属していること (`n->left->sym->pkg == runtimepkg`)。
2.  関数名が `"writebarrier"` で始まること (`strncmp(n->left->sym->name, "writebarrier", 12) == 0`)。
3.  または、関数名が `"writebarrierfat"` と完全に一致すること (`strcmp(n->left->sym->name, "writebarrierfat") == 0`)。

`runtime.writebarrierfat` が `runtime.typedmemmove` にリネームされた後、上記の3番目の条件はもはや `typedmemmove` を捕捉できませんでした。また、`typedmemmove` は `"writebarrier"` で始まらないため、2番目の条件も満たしません。このため、`typedmemmove` への呼び出しはレース検出器によって計測されなくなり、`typedmemmove` を介したデータ競合が見過ごされる可能性がありました。

このコミットは、`racewalknode` 関数内の条件を更新し、`"typedmemmove"` という新しい関数名を明示的にチェックするように変更することで、この問題を解決します。これにより、`typedmemmove` が実行するメモリ操作もレース検出器の監視対象となり、データ競合の検出漏れがなくなります。

## コアとなるコードの解説

このコミットでは、`racewalknode` 関数内の2つの条件式が変更されています。

1.  **関数呼び出しの識別条件の変更**:
    変更前:
    ```c
    if(n->left->sym != S && n->left->sym->pkg == runtimepkg && strncmp(n->left->sym->name, "writebarrier", 12) == 0) {
    ```
    変更後:
    ```c
    if(n->left->sym != S && n->left->sym->pkg == runtimepkg && 
    (strncmp(n->left->sym->name, "writebarrier", 12) == 0 || strcmp(n->left->sym->name, "typedmemmove") == 0)) {
    ```
    この変更により、レース検出器が計測対象とする関数呼び出しの条件が拡張されました。以前は `"writebarrier"` で始まる関数名のみを対象としていましたが、変更後はそれに加えて `"typedmemmove"` という名前の関数も明示的に対象に含めるようになりました。これにより、`writebarrierfat` から `typedmemmove` へのリネーム後も、レース検出器がこの重要なメモリ操作関数を正しく識別し、必要な計測を挿入できるようになります。

2.  **引数特定ロジックの変更**:
    変更前:
    ```c
    if(strcmp(n->left->sym->name, "writebarrierfat") == 0) {
    ```
    変更後:
    ```c
    if(strcmp(n->left->sym->name, "typedmemmove") == 0) {
    ```
    この変更は、特定の関数（以前は `writebarrierfat`、現在は `typedmemmove`）の引数を特定するための内部ロジックを更新するものです。`writebarrierfat` と `typedmemmove` は、その引数の構造が他の一般的な `writebarrier` 関数とは異なるため、特別な処理が必要でした。関数名が `typedmemmove` に変更されたことに合わせて、この条件も更新されました。これにより、`typedmemmove` の呼び出しにおいて、レース検出器が監視すべき正しい引数（通常は書き込み先のポインタ）を正確に特定できるようになります。

これらの変更により、Goのレース検出器は、`runtime.typedmemmove` を介したメモリ操作におけるデータ競合を再び正確に検出できるようになり、Goプログラムの並行安全性とデバッグ能力が向上します。

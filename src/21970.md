## 変更の背景

この変更の主な背景には、Goランタイムのコードベースをより現代的で、安全で、Goらしい（idiomatic Go）ものにするという目的があります。

1.  **安全性と堅牢性の向上**: C言語スタイルの文字列操作（`strcmp`, `strncmp`など）は、ヌル終端文字に依存しており、バッファオーバーフローやヌル終端文字の欠如による未定義動作など、多くのセキュリティ脆弱性やバグの原因となる可能性があります。Goの文字列は長さ情報を持つため、これらの問題が発生しにくい設計になっています。Cスタイルの関数を削除し、Goネイティブの安全な文字列操作に置き換えることで、ランタイムの堅牢性が向上します。
2.  **Go言語のイディオムへの準拠**: Go言語は、文字列をバイトスライスとして扱い、その長さを内部で管理します。C言語のようなヌル終端文字列とは根本的に異なるアプローチを取っています。ランタイムコード内でCスタイルの文字列関数を使用することは、Goの設計思想から逸脱しており、コードの可読性や保守性を低下させる可能性があります。この変更は、ランタイムコードをGoの標準的なプラクティスに合わせるものです。
3.  **コードの一貫性と保守性の向上**: ランタイム内の文字列処理を一貫したGoのメカニズムに統一することで、開発者がコードを理解しやすくなり、将来的な変更やデバッグが容易になります。異なるスタイルの文字列処理が混在していると、混乱を招き、エラーの温床となる可能性があります。
4.  **Plan 9固有のコードの近代化**: このコミットの変更箇所は主にPlan 9オペレーティングシステム関連のコードに集中しています。Plan 9はGo言語の開発に影響を与えたOSであり、GoランタイムにはPlan 9固有の低レベルなコードが残っていることがあります。この変更は、そうしたレガシーなCスタイルのインターフェースをGoの現代的なアプローチに更新する一環と見られます。

これらの理由から、Cスタイルの文字列ヘルパーを削除し、Goのネイティブな文字列操作に移行することは、Goランタイムの品質と持続可能性を高める上で重要なステップでした。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **C言語の文字列とヌル終端**:
    *   C言語において、文字列は文字の配列であり、その終端は特別な文字であるヌル文字（`\0`、ASCII値0）によって示されます。
    *   文字列の長さを知るためには、配列の先頭からヌル文字までを走査する必要があります。
    *   `strcmp(s1, s2)`: 2つのヌル終端文字列`s1`と`s2`を比較します。辞書順で`s1`が`s2`より小さい場合は負の値、大きい場合は正の値、等しい場合は0を返します。
    *   `strncmp(s1, s2, n)`: 2つのヌル終端文字列`s1`と`s2`の最初の`n`文字（またはヌル文字が見つかるまで）を比較します。`strcmp`と同様に比較結果を返します。`n`で指定された文字数を超えて読み込むことがないため、バッファオーバーフローのリスクを軽減しますが、ヌル終端文字の扱いに注意が必要です。
    *   これらの関数は、ヌル文字を文字列の終端と見なすため、ヌル文字が途中に含まれるバイナリデータには適していません。また、プログラマが明示的にバッファサイズや長さを管理する必要があり、誤用するとセキュリティ上の問題（例: バッファオーバーフロー）を引き起こしやすいという欠点があります。

2.  **Go言語の文字列**:
    *   Go言語の文字列は、バイトの読み取り専用スライス（`[]byte`）として内部的に表現されます。
    *   C言語とは異なり、Goの文字列はヌル終端ではありません。代わりに、文字列の長さが内部的に管理されています。
    *   `len(s)`: Goの組み込み関数で、文字列`s`のバイト数を返します。これは定数時間で実行されます。
    *   `string`型は不変（immutable）であり、一度作成されると内容を変更できません。
    *   Goの文字列は、UTF-8エンコードされたテキストを扱うのに最適化されています。
    *   `hasprefix(s, prefix)`: Goの標準ライブラリ（`strings`パッケージ）にある関数で、文字列`s`が指定された`prefix`で始まるかどうかを効率的にチェックします。

3.  **Plan 9オペレーティングシステム**:
    *   Plan 9は、ベル研究所で開発された分散オペレーティングシステムです。Go言語の設計思想に大きな影響を与えました。
    *   Goランタイムには、Plan 9固有のシステムコールやシグナル処理に関するコードが含まれています。
    *   Plan 9のシステムインターフェースは、しばしばC言語の規約に従っており、文字列もヌル終端で渡されることがあります。そのため、GoランタイムがPlan 9と連携する際には、Cスタイルの文字列をGoの文字列に変換したり、その逆を行ったりする処理が必要になることがあります。

このコミットは、Plan 9のシグナルハンドリングコード内で、C言語から受け取ったヌル終端文字列をGoの文字列として安全に扱い、Goのネイティブな文字列操作に移行することで、コードの安全性を高め、Goのイディオムに準拠させるものです。

## 技術的詳細

このコミットの技術的な核心は、Goランタイム内のCスタイルの文字列比較関数（`strcmp`と`strncmp`）を削除し、Goのネイティブな文字列型と操作に置き換えることです。これにより、特にPlan 9向けのシグナルハンドリングコードが近代化され、より安全でGoらしいコードになります。

具体的な変更点は以下の通りです。

1.  **`src/runtime/string1.go`からの`strcmp`と`strncmp`の削除**:
    *   このファイルは、Goランタイム内部で使用される低レベルな文字列操作ヘルパーを含んでいました。
    *   `strcmp`と`strncmp`は、C言語の同名関数と同様に、`*byte`ポインタ（実質的にはCスタイルのヌル終端バイト配列）を受け取り、バイト単位で比較を行う実装でした。
    *   これらの関数は、Goの`string`型が持つ長さ情報や安全なインデックスアクセスといった利点を活用しておらず、手動でのポインタ操作や境界チェックが必要でした。
    *   このコミットにより、これらの関数は完全に削除され、GoランタイムがCスタイルの文字列比較に依存しなくなりました。

2.  **`src/runtime/signal_plan9.go`における`sigTabT.name`の型変更**:
    *   `sigTabT`構造体は、Plan 9のシグナルテーブルのエントリを定義しており、`name`フィールドはシグナルの名前を保持していました。
    *   変更前は`name []byte`（バイトスライス）でしたが、変更後は`name string`（Goの文字列型）になりました。
    *   これにより、`sigtable`配列内のすべてのシグナル名リテラルも`[]byte("...")`から標準のGo文字列リテラル`"..."`に更新されました。
    *   この型変更は、後続のコードでGoの組み込み文字列関数を使用するための前提となります。Goの`string`型は不変であり、長さ情報を持つため、より安全で効率的な操作が可能です。

3.  **`src/runtime/os3_plan9.go`における文字列処理の適応**:
    *   このファイルは、Plan 9におけるシグナルハンドリングの主要なロジックを含んでいます。
    *   **`note`のGo文字列への変換**: Plan 9カーネルから受け取るシグナル通知（`note`）は、Cスタイルのヌル終端バイト配列として`*byte`ポインタで渡されます。
        *   変更前は、この`note`の長さを`findnull(note)`で手動で計算していました。
        *   変更後は、`notestr := gostringnocopy(note)`という行が追加されました。`gostringnocopy`は、既存のバイト配列からGoの`string`を作成しますが、データをコピーしないため、オーバーヘッドを最小限に抑えつつ、Goの文字列として扱えるようになります。これにより、`note`の長さを`len(notestr)`で安全かつ効率的に取得できるようになりました。
    *   **シグナル名との比較ロジックの変更**:
        *   変更前は、`strncmp(note, &t.name[0], uintptr(n))`を使用して、受け取った`note`と`sigtable`内のシグナル名を比較していました。これはCスタイルの比較でした。
        *   変更後は、`hasprefix(notestr, t.name)`に置き換えられました。`hasprefix`はGoのイディオムに沿った文字列のプレフィックスチェックであり、`notestr`（Go文字列）と`t.name`（Go文字列）を直接比較します。これにより、手動での長さ管理やポインタ操作が不要になり、コードが簡潔かつ安全になりました。
    *   **`memmove`と`print`の引数変更**:
        *   `memmove`（メモリコピー）や`print`（デバッグ出力）の呼び出しにおいて、以前は`length`変数や`gostringnocopy(note)`の直接の結果が使われていましたが、これらも`len(notestr)`や`notestr`に置き換えられ、Goの文字列の長さ情報や文字列自体を直接利用するようになりました。

これらの変更により、GoランタイムはC言語の低レベルな文字列操作から脱却し、Go言語の持つ安全性と表現力を最大限に活用するようになりました。特に、ヌル終端文字列の扱いに起因する潜在的なバグやセキュリティリスクが軽減され、コードベース全体の一貫性が向上しています。

3.  **コードの一貫性と保守性の向上**: ランタイム内の文字列処理を一貫したGoのメカニズムに統一することで、開発者がコードを理解しやすくなり、将来的な変更やデバッグが容易になります。異なるスタイルの文字列処理が混在していると、混乱を招き、エラーの温床となる可能性があります。
4.  **Plan 9固有のコードの近代化**: このコミットの変更箇所は主にPlan 9オペレーティングシステム関連のコードに集中しています。Plan 9はGo言語の開発に影響を与えたOSであり、GoランタイムにはPlan 9固有の低レベルなコードが残っていることがあります。この変更は、そうしたレガシーなCスタイルのインターフェースをGoの現代的なアプローチに更新する一環と見られます。

これらの理由から、Cスタイルの文字列ヘルパーを削除し、Goのネイティブな文字列操作に移行することは、Goランタイムの品質と持続可能性を高める上で重要なステップでした。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **C言語の文字列とヌル終端**:
    *   C言語において、文字列は文字の配列であり、その終端は特別な文字であるヌル文字（`\0`、ASCII値0）によって示されます。
    *   文字列の長さを知るためには、配列の先頭からヌル文字までを走査する必要があります。
    *   `strcmp(s1, s2)`: 2つのヌル終端文字列`s1`と`s2`を比較します。辞書順で`s1`が`s2`より小さい場合は負の値、大きい場合は正の値、等しい場合は0を返します。
    *   `strncmp(s1, s2, n)`: 2つのヌル終端文字列`s1`と`s2`の最初の`n`文字（またはヌル文字が見つかるまで）を比較します。`strcmp`と同様に比較結果を返します。`n`で指定された文字数を超えて読み込むことがないため、バッファオーバーフローのリスクを軽減しますが、ヌル終端文字の扱いに注意が必要です。
    *   これらの関数は、ヌル文字を文字列の終端と見なすため、ヌル文字が途中に含まれるバイナリデータには適していません。また、プログラマが明示的にバッファサイズや長さを管理する必要があり、誤用するとセキュリティ上の問題（例: バッファオーバーフロー）を引き起こしやすいという欠点があります。

2.  **Go言語の文字列**:
    *   Go言語の文字列は、バイトの読み取り専用スライス（`[]byte`）として内部的に表現されます。
    *   C言語とは異なり、Goの文字列はヌル終端ではありません。代わりに、文字列の長さが内部的に管理されています。
    *   `len(s)`: Goの組み込み関数で、文字列`s`のバイト数を返します。これは定数時間で実行されます。
    *   `string`型は不変（immutable）であり、一度作成されると内容を変更できません。
    *   Goの文字列は、UTF-8エンコードされたテキストを扱うのに最適化されています。
    *   `hasprefix(s, prefix)`: Goの標準ライブラリ（`strings`パッケージ）にある関数で、文字列`s`が指定された`prefix`で始まるかどうかを効率的にチェックします。

3.  **Plan 9オペレーティングシステム**:
    *   Plan 9は、ベル研究所で開発された分散オペレーティングシステムです。Go言語の設計思想に大きな影響を与えました。
    *   Goランタイムには、Plan 9固有のシステムコールやシグナル処理に関するコードが含まれています。
    *   Plan 9のシステムインターフェースは、しばしばC言語の規約に従っており、文字列もヌル終端で渡されることがあります。そのため、GoランタイムがPlan 9と連携する際には、Cスタイルの文字列をGoの文字列に変換したり、その逆を行ったりする処理が必要になることがあります。

このコミットは、Plan 9のシグナルハンドリングコード内で、C言語から受け取ったヌル終端文字列をGoの文字列として安全に扱い、Goのネイティブな文字列操作に移行することで、コードの安全性を高め、Goのイディオムに準拠させるものです。

## 技術的詳細

このコミットの技術的な核心は、Goランタイム内のCスタイルの文字列比較関数（`strcmp`と`strncmp`）を削除し、Goのネイティブな文字列型と操作に置き換えることです。これにより、特にPlan 9向けのシグナルハンドリングコードが近代化され、より安全でGoらしいコードになります。

具体的な変更点は以下の通りです。

1.  **`src/runtime/string1.go`からの`strcmp`と`strncmp`の削除**:
    *   このファイルは、Goランタイム内部で使用される低レベルな文字列操作ヘルパーを含んでいました。
    *   `strcmp`と`strncmp`は、C言語の同名関数と同様に、`*byte`ポインタ（実質的にはCスタイルのヌル終端バイト配列）を受け取り、バイト単位で比較を行う実装でした。
    *   これらの関数は、Goの`string`型が持つ長さ情報や安全なインデックスアクセスといった利点を活用しておらず、手動でのポインタ操作や境界チェックが必要でした。
    *   このコミットにより、これらの関数は完全に削除され、GoランタイムがCスタイルの文字列比較に依存しなくなりました。

2.  **`src/runtime/signal_plan9.go`における`sigTabT.name`の型変更**:
    *   `sigTabT`構造体は、Plan 9のシグナルテーブルのエントリを定義しており、`name`フィールドはシグナルの名前を保持していました。
    *   変更前は`name []byte`（バイトスライス）でしたが、変更後は`name string`（Goの文字列型）になりました。
    *   これにより、`sigtable`配列内のすべてのシグナル名リテラルも`[]byte("...")`から標準のGo文字列リテラル`"..."`に更新されました。
    *   この型変更は、後続のコードでGoの組み込み文字列関数を使用するための前提となります。Goの`string`型は不変であり、長さ情報を持つため、より安全で効率的な操作が可能です。

3.  **`src/runtime/os3_plan9.go`における文字列処理の適応**:
    *   このファイルは、Plan 9におけるシグナルハンドリングの主要なロジックを含んでいます。
    *   **`note`のGo文字列への変換**: Plan 9カーネルから受け取るシグナル通知（`note`）は、Cスタイルのヌル終端バイト配列として`*byte`ポインタで渡されます。
        *   変更前は、この`note`の長さを`findnull(note)`で手動で計算していました。
        *   変更後は、`notestr := gostringnocopy(note)`という行が追加されました。`gostringnocopy`は、既存のバイト配列からGoの`string`を作成しますが、データをコピーしないため、オーバーヘッドを最小限に抑えつつ、Goの文字列として扱えるようになります。これにより、`note`の長さを`len(notestr)`で安全かつ効率的に取得できるようになりました。
    *   **シグナル名との比較ロジックの変更**:
        *   変更前は、`strncmp(note, &t.name[0], uintptr(n))`を使用して、受け取った`note`と`sigtable`内のシグナル名を比較していました。これはCスタイルの比較でした。
        *   変更後は、`hasprefix(notestr, t.name)`に置き換えられました。`hasprefix`はGoのイディオムに沿った文字列のプレフィックスチェックであり、`notestr`（Go文字列）と`t.name`（Go文字列）を直接比較します。これにより、手動での長さ管理やポインタ操作が不要になり、コードが簡潔かつ安全になりました。
    *   **`memmove`と`print`の引数変更**:
        *   `memmove`（メモリコピー）や`print`（デバッグ出力）の呼び出しにおいて、以前は`length`変数や`gostringnocopy(note)`の直接の結果が使われていましたが、これらも`len(notestr)`や`notestr`に置き換えられ、Goの文字列の長さ情報や文字列自体を直接利用するようになりました。

これらの変更により、GoランタイムはC言語の低レベルな文字列操作から脱却し、Go言語の持つ安全性と表現力を最大限に活用するようになりました。特に、ヌル終端文字列の扱いに起因する潜在的なバグやセキュリティリスクが軽減され、コードベース全体の一貫性が向上しています。

## コアとなるコードの解説

### `src/runtime/os3_plan9.go`

このファイルはPlan 9オペレーティングシステムにおけるシグナルハンドリングのロジックを実装しています。

```go
// func sighandler(_ureg *ureg, note *byte, gp *g) int {
// ...
// 	var length int // 削除
// ...
// 	c := &sigctxt{_ureg}
// 	notestr := gostringnocopy(note) // 追加: CスタイルのnoteをGo文字列に変換

// ...
// 	// Check that the note is no more than ERRMAX bytes (including
// 	// the trailing NUL). We should never receive a longer note.
// -	length = findnull(note) // 削除: ヌル終端を検索して長さを得る
// -	if length > _ERRMAX-1 { // 削除: lengthを使用
// +	if len(notestr) > _ERRMAX-1 { // 追加: Go文字列のlenを使用
// 		print("sighandler: note is longer than ERRMAX\n")
// 		goto Throw
// 	}

// ...
// 	flags = _SigNotify
// 	for sig, t = range sigtable {
// -		n := len(t.name) // 削除: バイトスライスの長さを取得
// -		if length < n { // 削除: lengthとnを比較
// -			continue
// -		}
// -		if strncmp(note, &t.name[0], uintptr(n)) == 0 { // 削除: Cスタイルのstrncmpを使用
// +		if hasprefix(notestr, t.name) { // 追加: Goのhasprefixを使用
// 			flags = t.flags
// 			break
// 		}
// ...

// 	// we can reliably access it from the panic routines.
// -		memmove(unsafe.Pointer(_g_.m.notesig), unsafe.Pointer(note), uintptr(length+1)) // 削除: lengthを使用
// +		memmove(unsafe.Pointer(_g_.m.notesig), unsafe.Pointer(note), uintptr(len(notestr)+1)) // 追加: len(notestr)を使用
// ...
// 	print(gostringnocopy(note), "\n") // 削除: gostringnocopyを再度呼び出し
// +	print(notestr, "\n") // 追加: 既に変換済みのnotestrを使用
// ...
```

*   **`notestr := gostringnocopy(note)`**: Plan 9カーネルから受け取る`note`は`*byte`型であり、Cスタイルのヌル終端文字列を指しています。`gostringnocopy`は、このCスタイルのバイト配列をGoの`string`型に変換します。この関数は、元のデータをコピーせずにGoの文字列ビューを作成するため、効率的です。これにより、以降の処理でGoの安全な文字列操作を利用できるようになります。
*   **`len(notestr)`**: 以前は`findnull(note)`でヌル終端を検索して長さを取得していましたが、`notestr`がGoの文字列になったことで、組み込みの`len`関数を使って効率的かつ安全に長さを取得できるようになりました。
*   **`hasprefix(notestr, t.name)`**: 最も重要な変更点です。以前はCスタイルの`strncmp`を使って`note`とシグナル名`t.name`を比較していました。`strncmp`はポインタと長さを引数にとり、手動での管理が必要でした。`hasprefix`はGoの標準的な文字列操作であり、2つのGo文字列を引数にとり、`notestr`が`t.name`で始まるかどうかをチェックします。これにより、コードがより簡潔で、Goのイディオムに沿ったものになり、潜在的なバッファオーバーフローのリスクもなくなります。
*   **`memmove`と`print`の引数**: `memmove`（メモリコピー）や`print`（デバッグ出力）の呼び出しも、`length`変数や`gostringnocopy(note)`の直接の結果ではなく、既にGo文字列として変換された`notestr`とその長さ`len(notestr)`を使用するように変更されました。これにより、コードの一貫性が保たれます。

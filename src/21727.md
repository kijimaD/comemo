## 変更の背景

Goランタイムのトレーサーは、プログラムの実行中に発生するイベント（ゴルーチンのスケジューリング、GC活動など）を記録し、そのパフォーマンス特性を分析するための詳細な情報を提供します。このトレーサーは、イベントのタイムスタンプを記録するためにシステムの高分解能タイマーを使用します。

しかし、Windowsオペレーティングシステムでは、デフォルトのタイマー分解能が比較的低い（一般的に15ミリ秒程度）という特性があります。これは、`nanotime()`のような高分解能タイマー関数を非常に短い間隔で呼び出した場合、連続する呼び出しで同じタイムスタンプが返される可能性があることを意味します。

Goのトレーサーが`StopTrace()`関数でトレースの終了時刻を記録する際、`trace.timeEnd`と`trace.timeStart`が同じ値になってしまうと、トレース期間がゼロと計算されたり、ティック頻度の計算が不正確になったりする問題が発生していました。これにより、Windows環境で生成されたトレースデータが信頼できないものとなり、パフォーマンス分析の妨げとなっていました。

このコミットは、このWindows特有のタイマー分解能の問題に対処し、トレーサーが正確な時間情報を取得できるようにすることで、Windows上でのトレース機能の信頼性と有用性を向上させることを目的としています。

## 前提知識の解説

1.  **Goランタイムトレーサー**:
    Goのランタイムトレーサーは、Goプログラムの実行中に発生する内部イベント（ゴルーチンの作成・終了、スケジューリング、GC、システムコールなど）を記録するツールです。これにより、開発者はプログラムの実行挙動を詳細に分析し、パフォーマンスのボトルネックや非効率な部分を特定できます。トレースデータは通常、`go tool trace`コマンドで可視化されます。

2.  **`cputicks()`と`nanotime()`**:
    *   `cputicks()`: CPUのティックカウント（CPUサイクル数に近い値）を返します。これは非常に高分解能な時間測定ですが、CPUの周波数に依存するため、絶対的な時間ではなく相対的な時間差の測定に適しています。
    *   `nanotime()`: ナノ秒単位のモノトニックな時間（単調増加する時間）を返します。これはシステム起動時からの経過時間であり、システム時刻の変更（NTP同期など）に影響されません。パフォーマンス測定やイベントの順序付けに広く使用されます。

3.  **Windowsのタイマー分解能**:
    Windowsのシステムタイマーは、デフォルトで約15.6ミリ秒（64分の1秒）の分解能を持っています。これは、システムがタイマー割り込みを発生させる頻度を示します。アプリケーションがこれよりも短い間隔で時間を要求しても、タイマーが更新されるまでは同じ値が返される可能性があります。高分解能タイマー（QueryPerformanceCounterなど）も存在しますが、その使用方法や精度はハードウェアやOSのバージョンに依存することがあります。この低い分解能は、特に短い期間のイベントを正確に測定する必要があるパフォーマンスプロファイリングツールにとって課題となります。

4.  **`osyield()`**:
    `osyield()`は、現在のゴルーチンを一時的に中断し、他のゴルーチンにCPUを譲るための関数です。これは、CPUを占有し続けることを避け、他の準備ができたゴルーチンが実行される機会を与えるために使用されます。このコミットの文脈では、タイマーが更新されるのを待つ間に、CPUを無駄に消費しないようにするために使用されます。

## 技術的詳細

このコミットの主要な変更は、`src/runtime/trace.go`の`StopTrace()`関数にあります。トレースの終了時刻を記録する際、`trace.ticksEnd`と`trace.timeEnd`をそれぞれ`cputicks()`と`nanotime()`で取得します。

Windows環境では、`nanotime()`が連続して呼び出された際に同じ値を返す可能性があるため、`trace.timeEnd`が`trace.timeStart`と同じ値になってしまう問題がありました。これは、トレース期間がゼロと計算され、その後のティック頻度（`traceEvFrequency`）の計算に悪影響を及ぼす可能性がありました。

この問題を解決するため、`StopTrace()`関数に`for`ループが導入されました。このループは、`trace.timeEnd`が`trace.timeStart`と異なる値になるまで、`cputicks()`と`nanotime()`の呼び出しを繰り返します。これにより、少なくとも1回のタイマーティックが発生し、`trace.timeEnd`が確実に更新された後にトレースの終了処理が続行されることが保証されます。ループ内では`osyield()`が呼び出され、CPUを他のゴルーチンに譲ることで、ビジーループによるCPUの無駄な消費を防いでいます。

また、`src/runtime/pprof/trace_parser_test.go`では、`traceEvFrequency`イベントの解析時に、`ticksPerSec`（1秒あたりのティック数）が0以下の場合にエラーを返すチェックが追加されました。これは、不正な頻度データがトレースファイルに含まれることを防ぎ、解析の堅牢性を高めます。

`src/runtime/pprof/trace_test.go`では、Windows環境でのトレーステストのスキップ条件が削除されました。これは、今回の修正によってWindowsでのトレース機能が安定したため、テストを有効にできるようになったことを示しています。同時に、ARMアーキテクチャでのトレーステストのスキップ条件が追加されており、これは別の未解決の問題（`http://golang.org/issue/9725`）を示唆しています。

## コアとなるコードの変更箇所

主要な変更は`src/runtime/trace.go`の`StopTrace()`関数にあります。

```diff
--- a/src/runtime/trace.go
+++ b/src/runtime/trace.go
@@ -208,8 +208,16 @@ func StopTrace() {
 		traceFullQueue(buf)
 	}

-	trace.ticksEnd = cputicks()
-	trace.timeEnd = nanotime()
+	for {
+		trace.ticksEnd = cputicks()
+		trace.timeEnd = nanotime()
+		// Windows time can tick only every 15ms, wait for at least one tick.
+		if trace.timeEnd != trace.timeStart {
+			break
+		}
+		osyield()
+	}
+
 	trace.enabled = false
 	trace.shutdown = true
 	trace.stackTab.dump()
```

## コアとなるコードの解説

上記のコードスニペットは、`StopTrace()`関数内でトレースの終了時刻を決定するロジックを示しています。

変更前は、`trace.ticksEnd`と`trace.timeEnd`が一度だけ`cputicks()`と`nanotime()`の呼び出しによって設定されていました。Windowsのタイマー分解能が低い場合、`nanotime()`が`trace.timeStart`と同じ値を返す可能性があり、その結果、トレース期間がゼロと見なされる問題がありました。

変更後では、`for`ループが導入されています。
1.  ループ内で`trace.ticksEnd`と`trace.timeEnd`が繰り返し更新されます。
2.  `if trace.timeEnd != trace.timeStart`という条件で、`trace.timeEnd`が`trace.timeStart`とは異なる値になったかどうかがチェックされます。これは、少なくとも1回のタイマーティックが発生し、時間が進んだことを意味します。
3.  条件が満たされれば`break`でループを抜けます。
4.  条件が満たされない（つまり、時間が進んでいない）場合、`osyield()`が呼び出されます。これにより、現在のゴルーチンはCPUを解放し、他のゴルーチンが実行される機会を与えます。これは、タイマーが更新されるのを待つ間、CPUをビジーループで消費し続けることを避けるための重要な最適化です。

このループにより、Windows環境においても、トレースの終了時刻が正確に記録され、トレースデータの信頼性が向上します。

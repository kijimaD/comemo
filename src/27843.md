# [インデックス 27843] ファイルの概要

このコミットは、Goコンパイラの共通部分式除去（Common Subexpression Elimination, CSE）における支配関係（dominance checking）の処理速度を向上させるものです。具体的には、等価な値のスライス処理において、要素を削除する代わりに`nil`を設定することでコピーを排除し、さらにエントリ番号によるソート順序を利用して早期にループを中断する最適化が施されています。これにより、特定のコードパターンにおけるコンパイル時間が大幅に短縮されました。

## 変更の背景

この変更の背景には、Goコンパイラの最適化フェーズの一つである共通部分式除去（CSE）のパフォーマンス問題がありました。特に、特定のコードパターン（Issue #15112で報告されたようなケース）において、CSEの支配関係チェックがボトルネックとなり、コンパイル時間が著しく長くなることが判明していました。

従来の支配関係チェックのアルゴリズムでは、等価な値のリストを処理する際に、支配された値をリストから削除するためにスライスのコピー操作が頻繁に発生していました。Goのスライスは動的配列であり、要素の削除は通常、後続の要素をシフトさせる（つまり、新しいスライスを作成してコピーする）ことで行われます。この操作は、リストが長くなるにつれてコストが増大し、コンパイル時間の増加に直結していました。

また、支配関係のチェック自体も、不必要な比較を多く含んでいました。支配関係はプログラムの制御フローグラフにおける重要な概念であり、あるブロックが別のブロックを支配するということは、後者のブロックに到達する全てのパスが前者のブロックを通過することを意味します。CSEでは、この支配関係を利用して、ある値が計算された後に、その値が有効なスコープ内で再利用できるかどうかを判断します。しかし、支配関係が成立しないことが一度判明した後も、不必要にチェックを続けることでオーバーヘッドが生じていました。

このコミットは、これらのパフォーマンスボトルネックを解消し、コンパイラの効率を向上させることを目的としています。

## 前提知識の解説

### 1. GoコンパイラとSSA (Static Single Assignment)

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現としてSSA（Static Single Assignment）形式を使用します。SSA形式では、各変数が一度だけ代入されるように変換され、データフロー解析や最適化が容易になります。CSEのような最適化は、このSSA形式のコードに対して行われます。

### 2. 共通部分式除去 (Common Subexpression Elimination, CSE)

CSEは、コンパイラの最適化手法の一つで、同じ値が複数回計算されている部分（共通部分式）を特定し、その計算を一度だけ行い、結果を再利用することで、実行時の計算量を削減します。例えば、`a = b * c + d; e = b * c + f;`というコードがあった場合、`b * c`は共通部分式であり、一度計算してその結果を`a`と`e`の両方に利用できます。

CSEを適用するためには、以下の条件を満たす必要があります。
*   共通部分式が同じ値を持つこと。
*   共通部分式が計算される間に、その部分式を構成する変数の値が変更されていないこと。
*   共通部分式が再利用される場所が、元の計算場所によって「支配」されていること。

### 3. 支配関係 (Dominance)

プログラムの制御フローグラフ（Control Flow Graph, CFG）において、ブロックAがブロックBを「支配する（dominates）」とは、ブロックBに到達する全てのパスがブロックAを通過する場合を指します。記号で`A dom B`と書かれます。
*   **厳密な支配 (Strict Dominance):** `A dom B` かつ `A != B` の場合。
*   **即時支配 (Immediate Dominance):** `A dom B` かつ `A != B` であり、`A`から`B`への厳密な支配パス上に他のブロックが存在しない場合。
*   **支配木 (Dominator Tree):** CFGの支配関係を木構造で表現したもので、各ノードは即時支配者によって親ノードと結ばれます。

CSEでは、ある値`v`が計算されたブロック`B_v`が、その値が再利用されるブロック`B_w`を支配している必要があります。`f.sdom.isAncestorEq(v.Block, w.Block)`というコードは、`v`が計算されたブロックが`w`が計算されたブロックを支配しているか、あるいは両者が同じブロックであるかをチェックしています。

### 4. Goのスライス操作のパフォーマンス

Goのスライスは、基盤となる配列への参照、長さ、容量を持つデータ構造です。スライスから要素を削除する際、例えば`s = append(s[:i], s[i+1:]...)`のような操作を行うと、`s[i+1:]`の部分が新しい配列にコピーされ、その結果新しいスライスが作成されます。このコピー操作は、スライスのサイズに比例してコストが増大するため、頻繁に行われるとパフォーマンスに大きな影響を与えます。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/ssa/cse.go`ファイル内の`cse`関数における、等価な値の処理ロジックを最適化しています。

### 1. スライス要素の削除方法の変更

変更前は、等価な値のリスト`e`から支配された値`w`を削除する際に、`copy(e[i:], e[i+1:])`と`e = e[:len(e)-1]`という操作を行っていました。これは、`e[i]`以降の要素を一つ前にシフトさせ、スライスの長さを短くする、典型的なスライスからの要素削除パターンです。しかし、この操作は内部的に配列のコピーを伴うため、パフォーマンス上のオーバーヘッドが大きくなります。

変更後では、削除対象の要素`w`を`e[j] = nil`と設定することで、スライスから論理的に削除しています。これにより、物理的な要素の移動や基盤配列のコピーが不要になり、処理が高速化されます。`nil`チェックを`if v == nil { continue }`や`if w == nil { continue }`として追加することで、`nil`になった要素はスキップされます。この手法は、スライス内の要素がポインタ型である場合に特に有効です。`*ssa.Value`はポインタ型であるため、この最適化が適用可能です。

### 2. 支配関係チェックの早期終了

変更前は、内側のループ`for i := 0; i < len(e);`において、`v`が`w`を支配しない場合でもループが継続され、不必要な支配関係チェックが行われる可能性がありました。

変更後では、`e`がエントリ番号（`sortbyentry`によってソートされている）でソートされているという特性を利用しています。エントリ番号は、ブロックが制御フローグラフ内で出現する順序を示すもので、支配関係と密接に関連しています。
`if f.sdom.isAncestorEq(v.Block, w.Block)`のチェックで`v`が`w`を支配しないことが判明した場合、`else { break }`によって内側のループを即座に終了します。これは、`e`がエントリ番号順にソートされているため、現在の`w`のブロックが`v`によって支配されていないならば、それ以降の`e`内のブロックも`v`によって支配されることはない、という論理に基づいています。この早期終了により、不必要な支配関係チェックの回数が大幅に削減され、特に支配関係が複雑な大規模な関数において効果を発揮します。

### 3. パフォーマンス改善の数値

コミットメッセージに記載されているように、Issue #15112で報告された特定のコードに対して、コンパイル時間が約52秒から約22秒へと、半分以下に短縮されています。これは、これらの最適化が非常に効果的であったことを示しています。

## コアとなるコードの解説

### 変更前 (`for len(e) > 1`)

*   `for len(e) > 1 { ... }`: `e`スライスに複数の要素がある限りループを続けます。
*   `v := e[0]`: スライスの最初の要素を`v`として取得します。これが現在の支配候補です。
*   `e = e[1:]`: `v`を処理した後、スライス`e`から最初の要素を削除します。この操作は、新しいスライスヘッダを作成し、基盤配列の残りの部分を参照させますが、実質的には`v`が「削除」されたかのように振る舞います。
*   `for i := 0; i < len(e); { ... }`: 残りの`e`の要素`w`に対してループします。
*   `w := e[i]`: 現在の要素`w`を取得します。
*   `if f.sdom.isAncestorEq(v.Block, w.Block) { ... }`: `v`のブロックが`w`のブロックを支配しているかチェックします。
*   `rewrite[w.ID] = v`: 支配関係が成立する場合、`w`を`v`で書き換えるようにマークします。
*   `copy(e[i:], e[i+1:])`: `w`が支配された場合、スライス`e`から`w`を削除するために、`i`番目以降の要素を一つ前にコピーします。
*   `e = e[:len(e)-1]`: スライスの長さを1つ減らします。
*   `else { i++ }`: 支配関係が成立しない場合、次の要素に進みます。

この変更前のコードでは、内側のループで`w`が支配されるたびに`copy`とスライス再構築が行われ、これがパフォーマンスボトルネックとなっていました。

### 変更後 (`for i := 0; i < len(e)-1; i++`)

*   `for i := 0; i < len(e)-1; i++ { ... }`: スライスのインデックス`i`を使ってループします。最後の要素は比較対象にならないため`len(e)-1`までです。
*   `v := e[i]`: 現在のインデックス`i`の要素を`v`として取得します。
*   `if v == nil { continue }`: `v`が既に`nil`に設定されている場合（以前のイテレーションで支配されたため）、この要素はスキップします。
*   `e[i] = nil`: `v`を処理した後、その位置の要素を`nil`に設定します。これにより、スライスから物理的に削除するコストの高い操作を回避します。
*   `for j := i + 1; j < len(e); j++ { ... }`: `v`の次の要素からスライスの最後までを`w`としてループします。
*   `w := e[j]`: 現在の要素`w`を取得します。
*   `if w == nil { continue }`: `w`が既に`nil`に設定されている場合、スキップします。
*   `if f.sdom.isAncestorEq(v.Block, w.Block) { ... }`: `v`のブロックが`w`のブロックを支配しているかチェックします。
*   `rewrite[w.ID] = v`: 支配関係が成立する場合、`w`を`v`で書き換えるようにマークします。
*   `e[j] = nil`: 支配された`w`の要素を`nil`に設定します。これにより、スライスからの物理的な削除を回避します。
*   `else { break }`: **重要な最適化点**。`v`が`w`を支配しない場合、`e`がエントリ番号順にソートされているため、それ以降の`e`内の要素も`v`によって支配されることはありません。したがって、内側のループを即座に終了します。これにより、不必要な支配関係チェックが大幅に削減されます。

この変更により、スライス要素の削除に伴うコピーオーバーヘッドが排除され、さらに支配関係チェックの効率が向上したことで、コンパイル時間が大幅に短縮されました。

# [インデックス 23074] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるヒープサイズの推定方法を改善し、GCトリガーと目標値の設定に到達可能なヒープの推定値を使用するように変更するものです。これにより、ミューテータ（アプリケーションコード）が大量の「浮動ゴミ」（floatLive）を生成するシナリオにおいて発生していた、ヒープサイズの過剰な増大とGCサイクルの長期化という悪循環を解消します。

    Currently, we set the heap goal for the next GC cycle using the size
    of the marked heap at the end of the current cycle. This can lead to a
    bad feedback loop if the mutator is rapidly allocating and releasing
    pointers that can significantly bloat heap size.
    
    If the GC were STW, the marked heap size would be exactly the
    reachable heap size (call it stwLive). However, in concurrent GC,
    marked=stwLive+floatLive, where floatLive is the amount of "floating
    garbage": objects that were reachable at some point during the cycle
    and were marked, but which are no longer reachable by the end of the
    cycle. If the GC cycle is short, then the mutator doesn't have much
    time to create floating garbage, so marked≈stwLive. However, if the GC
    cycle is long and the mutator is allocating and creating floating
    garbage very rapidly, then it's possible that marked≫stwLive. Since
    the runtime currently sets the heap goal based on marked, this will
    cause it to set a high heap goal. This means that 1) the next GC cycle
    will take longer because of the larger heap and 2) the assist ratio
    will be low because of the large distance between the trigger and the
    goal. The combination of these lets the mutator produce even more
    floating garbage in the next cycle, which further exacerbates the
    problem.
    
    For example, on the garbage benchmark with GOMAXPROCS=1, this causes
    the heap to grow to ~500MB and the garbage collector to retain upwards
    of ~300MB of heap, while the true reachable heap size is ~32MB. This,
    in turn, causes the GC cycle to take upwards of ~3 seconds.
    
    Fix this bad feedback loop by estimating the true reachable heap size
    (stwLive) and using this rather than the marked heap size
    (stwLive+floatLive) as the basis for the GC trigger and heap goal.
    This breaks the bad feedback loop and causes the mutator to assist
    more, which decreases the rate at which it can create floating
    garbage. On the same garbage benchmark, this reduces the maximum heap
    size to ~73MB, the retained heap to ~40MB, and the duration of the GC

## 元コミット内容

現在のGoランタイムでは、次回のGCサイクルのヒープ目標値（heap goal）を、現在のサイクル終了時点でのマーク済みヒープサイズ（marked heap size）に基づいて設定していました。しかし、ミューテータがポインタを高速に割り当て・解放し、ヒープサイズを大幅に肥大化させる場合、これは悪循環を引き起こす可能性がありました。

並行GCでは、`marked = stwLive + floatLive` の関係が成り立ちます。ここで `stwLive` はSTW（Stop-The-World）GCであった場合に到達可能であったヒープサイズ、`floatLive` は「浮動ゴミ」と呼ばれる、GCサイクル中に一時的に到達可能とマークされたものの、サイクル終了時には到達不可能になっているオブジェクトの量です。GCサイクルが短い場合、`marked` は `stwLive` に近い値になりますが、サイクルが長く、ミューテータが高速に浮動ゴミを生成する場合、`marked` は `stwLive` よりもはるかに大きくなる可能性があります。

ランタイムが `marked` に基づいてヒープ目標値を設定すると、高いヒープ目標値が設定されます。これは、1) ヒープが大きくなるため次回のGCサイクルが長くなる、2) トリガーと目標値の距離が大きくなるためアシスト比率が低くなる、という問題を引き起こします。これらの組み合わせにより、ミューテータは次回のサイクルでさらに多くの浮動ゴミを生成し、問題がさらに悪化します。

このコミットは、真の到達可能なヒープサイズ（`stwLive`）を推定し、これをGCトリガーとヒープ目標値の基礎として使用することで、この悪循環を修正します。これにより、ミューテータがより多くGCアシストを行うようになり、浮動ゴミの生成速度が低下します。

## 変更の背景

Goのガベージコレクション（GC）は、低レイテンシと高スループットを目指して設計されており、主に並行マーク＆スイープアルゴリズムを採用しています。GCの大部分はアプリケーションのゴルーチンと並行して実行されますが、短いSTW（Stop-The-World）ポーズも含まれます。

このコミットが修正しようとしている問題は、並行GCの特性に起因します。並行GCでは、GCがオブジェクトをマークしている最中にもアプリケーション（ミューテータ）は実行され、新しいオブジェクトを割り当てたり、既存のオブジェクトへの参照を変更したり、あるいはオブジェクトを到達不可能にしたりします。

従来のGo GCでは、次回のGCサイクルを開始するタイミングや、ヒープの目標サイズを決定する際に、前回のGCサイクル終了時に「マークされたヒープサイズ」（`memstats.heap_marked`）を基準にしていました。この `heap_marked` は、GCがマークフェーズ中に到達可能と判断したすべてのオブジェクトの合計サイズです。

しかし、この `heap_marked` には、GCサイクル中に一時的に到達可能とマークされたものの、GCサイクルが終了するまでにミューテータによって到達不可能になったオブジェクト、すなわち「浮動ゴミ」（`floatLive`）が含まれる可能性があります。特に、アプリケーションが非常に高速にオブジェクトを割り当て、すぐに解放するようなパターン（例えば、一時的なデータ構造を頻繁に作成・破棄するような処理）を実行する場合、この `floatLive` の量が無視できないほど大きくなることがあります。

`marked = stwLive + floatLive` の関係において、`stwLive` はGCが完全に停止した状態で実行された場合に到達可能と判断される真のライブオブジェクトのサイズです。`floatLive` が大きい場合、`heap_marked` は `stwLive` よりも大幅に大きくなります。

この `heap_marked` を基準に次回のGC目標を設定すると、GCは実際よりもはるかに大きなヒープサイズを許容してしまいます。その結果、以下の悪影響が生じます。

1.  **GCサイクルの長期化**: ヒープサイズが大きくなるため、次回のGCが処理すべきデータ量が増え、GCサイクル全体の実行時間が長くなります。
2.  **アシスト比率の低下**: GCトリガーと目標値の間の距離が大きくなるため、ミューテータがGCに協力する（GCアシスト）必要性が低くなります。これにより、ミューテータはGCの進行を妨げることなく、さらに多くの浮動ゴミを生成し続けることができます。
3.  **悪循環**: 上記の要因が組み合わさることで、ヒープの肥大化とGCサイクルの長期化がさらに加速され、アプリケーションのパフォーマンスが著しく低下する可能性があります。コミットメッセージの例では、真の到達可能ヒープサイズが約32MBであるにもかかわらず、ヒープが約500MBにまで膨れ上がり、GCサイクルが約3秒もかかるという極端なケースが示されています。

このコミットは、この悪循環を断ち切り、GCがより効率的に動作するように、ヒープ目標値の計算基準を `heap_marked` から「推定された到達可能ヒープサイズ」（`heap_reachable`）に変更することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションに関するいくつかの基本的な概念と、ヒープ管理に関連する統計値について理解しておく必要があります。

*   **ガベージコレクション (GC)**: プログラムが不要になったメモリを自動的に解放するプロセスです。GoのGCは、主に並行マーク＆スイープアルゴリズムを採用しています。
*   **並行GC**: GCの大部分のフェーズ（特にマーキングフェーズ）が、アプリケーションの実行（ミューテータ）と並行して動作します。これにより、アプリケーションの実行を長時間停止させることなくGCを実行できます。
*   **STW (Stop-The-World)**: GCの特定の短いフェーズで、すべてのアプリケーションゴルーチンが一時的に停止される期間です。GoのGCでは、マーク開始時とマーク終了時に短いSTWポーズがあります。
*   **ミューテータ (Mutator)**: アプリケーションのコード自体を指します。ミューテータはオブジェクトを割り当てたり、参照を変更したりします。
*   **`stwLive` (Stop-The-World Live)**: もしGCが完全にSTWで実行された場合に到達可能と判断される、真のライブオブジェクトのサイズを指します。これは、GCサイクル終了時点での純粋な到達可能ヒープサイズと考えることができます。
*   **`floatLive` (Floating Garbage)**: 「浮動ゴミ」と訳されます。並行GCの特性上、GCがオブジェクトをマークしている最中に、ミューテータによってそのオブジェクトへの参照が切断され、到達不可能になることがあります。しかし、GCは既にそのオブジェクトを到達可能とマークしてしまっているため、そのサイクルでは解放されません。このような、GCサイクル中に一時的に到達可能とマークされたが、サイクル終了時には到達不可能になっているオブジェクトの合計サイズが `floatLive` です。
    *   関係式: `marked = stwLive + floatLive`
*   **`memstats.heap_marked`**: 前回のGCサイクル終了時にマークされたヒープの合計サイズ。これには `stwLive` と `floatLive` の両方が含まれます。
*   **`memstats.heap_live`**: 現在のヒープ上のライブオブジェクトの合計サイズ。これはGCサイクル中に変動します。
*   **`memstats.heap_reachable`**: このコミットで導入される新しい統計値で、GCサイクル終了時点での到達可能なヒープサイズ（`stwLive` に近い値）の推定値です。
*   **`gcpercent` (GOGC)**: GCのトリガーを制御する重要なパラメータです。前回のGCでライブだったヒープサイズに対して、どれだけの新しいメモリが割り当てられたら次回のGCを開始するかをパーセンテージで指定します。デフォルトは100%です。例えば、ライブヒープが10MBで `gcpercent` が100%の場合、さらに10MBの新しいメモリが割り当てられるとGCがトリガーされます。環境変数 `GOGC` または `runtime/debug.SetGCPercent()` で設定できます。
*   **`triggerRatio`**: `gcpercent` に基づいて計算される比率で、ヒープがどれだけ成長したらGCをトリガーするかを示します。`triggerRatio = gcpercent / 100` とは異なります。Goの内部では `1 + triggerRatio` が `1 + gcpercent/100` に相当するような計算がされます。
*   **`heapGoal`**: 次回のGCサイクルが完了するまでにヒープが到達してもよい目標サイズです。このサイズを超えると、GCが開始されるか、ミューテータがGCアシストを開始します。
*   **`memstats.next_gc`**: 次回のGCがトリガーされるヒープの目標サイズ。`heapGoal` と概念的には同じです。`runtime.MemStats` 構造体に含まれます。

## 技術的詳細

このコミットの核心は、Goの並行GCにおける「浮動ゴミ」の問題に対処し、GCの効率と予測可能性を向上させることにあります。

**問題点（変更前）**:
従来のGo GCでは、次回のGCサイクルをいつ開始するか（`memstats.next_gc`）と、ヒープの目標サイズ（`gcController.heapGoal`）を決定する際に、前回のGCサイクル終了時点での「マーク済みヒープサイズ」（`memstats.heap_marked`）を基準にしていました。

`memstats.heap_marked` は、GCのマークフェーズ中に到達可能と判断されたオブジェクトの合計サイズです。しかし、並行GCの性質上、マークフェーズ中にミューテータがオブジェクトを割り当てたり、既存のオブジェクトへの参照を切断したりすることがあります。このため、`memstats.heap_marked` には、GCサイクル終了時には実際には到達不可能になっているオブジェクト（`floatLive`）が含まれる可能性があります。

`marked = stwLive + floatLive`

ここで、`stwLive` は真の到達可能ヒープサイズです。`floatLive` が大きい場合、`memstats.heap_marked` は `stwLive` よりも大幅に大きくなります。この過大評価された `memstats.heap_marked` を基に `next_gc` や `heapGoal` が設定されると、GCは実際よりもはるかに大きなヒープサイズを許容してしまいます。

結果として、以下のような悪循環が生じました。
1.  `heap_marked` が過大評価される。
2.  `next_gc` と `heapGoal` が過大に設定される。
3.  GCが開始されるまでのヒープの成長が許容される範囲が広がる。
4.  ミューテータがGCアシストを行う必要性が低下し、GCの進行を妨げることなく、さらに多くの浮動ゴミを生成し続ける。
5.  次回のGCサイクルが処理すべきヒープサイズがさらに増大し、GC時間が長くなる。
6.  GC時間が長くなることで、ミューテータが浮動ゴミを生成する時間も増え、問題がさらに悪化する。

コミットメッセージの例では、この問題が顕著に現れており、真の到達可能ヒープサイズが約32MBであるにもかかわらず、ヒープが約500MBにまで膨れ上がり、GCサイクルが約3秒もかかるという非効率な状態が発生していました。

**解決策（変更後）**:
このコミットは、この悪循環を断ち切るために、GCトリガーとヒープ目標値の基礎を `memstats.heap_marked` から「推定された到達可能ヒープサイズ」（`memstats.heap_reachable`）に変更します。

`memstats.heap_reachable` は、GCサイクル開始時点での真の到達可能ヒープサイズ（`stwLive`）を推定しようとするものです。この推定は、GCマークフェーズ中にマークされたバイト数（`work.bytesMarked`）から、マーク開始後にミューテータによって割り当てられたヒープ量（`memstats.heap_live - gcController.initialHeapLive`）を差し引くことで行われます。

`memstats.heap_reachable = work.bytesMarked - (memstats.heap_live - gcController.initialHeapLive)`

この計算は、`work.bytesMarked` がGCサイクル終了時のマーク済みヒープサイズであり、`(memstats.heap_live - gcController.initialHeapLive)` がGCサイクル中にミューテータが新たに割り当てたヒープサイズ（そしてその一部が浮動ゴミになる可能性のある部分）であるという近似に基づいています。これにより、`floatLive` の影響を排除し、より正確な `stwLive` の推定値を得ようとします。

`heap_reachable` を基準に `next_gc` と `heapGoal` を設定することで、以下の改善が期待されます。
1.  **より正確なヒープ目標**: `floatLive` の影響が排除されるため、`next_gc` と `heapGoal` が真の到達可能ヒープサイズにより近い値に設定されます。
2.  **GCアシストの促進**: ヒープ目標がより現実的な値になるため、ミューテータはより早い段階でGCアシストを行う必要が生じます。これにより、ミューテータが浮動ゴミを生成する速度が低下します。
3.  **ヒープ使用量の削減**: ヒープが過剰に肥大化するのを防ぎ、メモリフットプリントを削減します。
4.  **GC時間の短縮**: GCが処理すべきヒープサイズが適切になるため、GCサイクル全体の実行時間が短縮されます。

コミットメッセージの例では、この変更により、最大ヒープサイズが約73MBに、保持されるヒープが約40MBに、GCサイクル時間が約200msにまで大幅に改善されたことが示されています。これは、GCの効率とアプリケーションのパフォーマンスにとって非常に重要な改善です。

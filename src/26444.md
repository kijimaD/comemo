このコミットは、Goアセンブラ（`cmd/asm`）における2つの重要な改善を導入しています。一つは、不正なアセンブリ命令の構文 `foo(SB)(AX)` を、以前のように黙って `foo(SB)` として解釈するのではなく、明示的なエラーとして拒否するように変更した点です。もう一つは、アセンブラが不正な命令に対して複数のエラーメッセージを重複して出力していた問題を修正し、エラーメッセージが一度だけ表示されるようにした点です。これにより、アセンブラの診断機能が向上し、ユーザーはより正確で分かりやすいエラー報告を受け取れるようになります。

## 変更の背景

このコミットは、Goアセンブラ（`cmd/asm`）の2つの既存の問題に対処するために行われました。

1.  **不正なアセンブリ構文の黙示的な許容**: 以前のGoアセンブラは、`foo(SB)(AX)` のような不正なメモリアドレッシングモードを、`foo(SB)` と解釈し、` (AX)` 部分を黙って無視していました。`foo(SB)` はシンボル `foo` のアドレスを指し、`SB` (Static Base) は静的メモリ領域のベースレジスタです。` (AX)` はインデックスレジスタ `AX` を使ったオフセット指定を意味しますが、`foo(SB)` 自体が既にメモリ上のアドレスを指しているため、これらを組み合わせることは通常、x86アセンブリの文法として不正です。アセンブラがこれをエラーとして報告せず、誤った解釈をしていたため、開発者は意図しないコードを生成してしまう可能性がありました。この変更は、このような曖昧で不正な構文を明示的にエラーとして扱うことで、アセンブラの厳密性を高め、バグの早期発見に貢献します。

2.  **重複するエラーメッセージの出力**: アセンブラが不正な命令を検出した際、エラーメッセージが複数回（特に `span` イテレーションごとに）出力されるという問題がありました。これにより、エラーログが冗長になり、実際の問題の特定が困難になることがありました。この変更は、エラーメッセージが一度だけ出力されるように修正し、診断の明確性を向上させます。

これらの問題は、Goアセンブラのユーザーエクスペリエンスとコードの正確性に影響を与えていたため、修正が必要とされました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびアセンブラに関する知識が役立ちます。

*   **Goアセンブラ (`cmd/asm`)**: Go言語のツールチェーンの一部であり、Goプログラムから呼び出されるアセンブリコードを記述するために使用されます。GoのアセンブリはPlan 9アセンブラの構文に基づいており、一般的なx86アセンブリとは異なる独自の記法を持っています。
*   **シンボル (`SB`)**: Goアセンブラにおける `SB` (Static Base) は、静的メモリ領域のベースアドレスを示す擬似レジスタです。グローバル変数や関数などのシンボルは、`foo(SB)` のように `SB` を基準としたオフセットで参照されます。
*   **メモリアドレッシングモード (x86)**: x86アーキテクチャでは、メモリ上のデータにアクセスするための様々なアドレッシングモードがあります。
    *   **ベースレジスタ + オフセット**: `[base + offset]` の形式。例: `[RBP - 8]`
    *   **ベースレジスタ + インデックスレジスタ * スケール + オフセット**: `[base + index * scale + offset]` の形式。例: `[RBX + RSI * 4 + 0x10]`
    *   **シンボルアドレス**: `foo(SB)` のように、シンボルのアドレスを直接指定する形式。
    `foo(SB)(AX)` のような構文は、シンボルアドレス `foo(SB)` とインデックスレジスタ `AX` を組み合わせようとするもので、通常は有効なx86メモリアドレッシングモードではありません。`foo(SB)` 自体が既にメモリ上のアドレスを指しているため、その後にさらにインデックスレジスタを指定することは文法的に矛盾します。
*   **`obj.Link` コンテキスト**: Goのアセンブラおよびリンカの内部では、`obj.Link` 構造体がアセンブリ処理全体のコンテキストを管理します。これには、エラー報告のための `Diag` (または `DiagFunc`) や、シンボルリストなどが含まれます。
*   **`span` 関数**: アセンブラのバックエンド処理の一部で、命令のサイズを決定し、最終的なバイナリコードを生成する過程で呼び出されます。この処理は、命令のオペランドの複雑さや、ジャンプ命令のターゲットアドレスの距離などに応じて複数回繰り返されることがあります。

## 技術的詳細

このコミットは、主に `src/cmd/internal/obj/link.go` と `src/cmd/internal/obj/x86/asm6.go` の変更によって、上記の問題を解決しています。

### 1. `foo(SB)(AX)` の拒否

*   **`src/cmd/internal/obj/x86/asm6.go` の `oclass` 関数**:
    `oclass` 関数は、アセンブリ命令のオペランドのタイプを分類する役割を担っています。この関数内の `obj.TYPE_MEM` ケースに新しいロジックが追加されました。
    ```go
    case obj.TYPE_MEM:
    	if a.Name != obj.NAME_NONE {
    		if ctxt.Asmode == 64 && (a.Reg != REG_NONE || a.Index != REG_NONE || a.Scale != 0) {
    			return Yxxx
    		}
    	}
    	return Ym
    ```
    このコードは、オペランドがメモリタイプ (`obj.TYPE_MEM`) であり、かつシンボル名 (`a.Name != obj.NAME_NONE`) を持っている場合に、追加のチェックを行います。具体的には、64ビットモード (`ctxt.Asmode == 64`) で、かつレジスタ (`a.Reg`), インデックスレジスタ (`a.Index`), またはスケール (`a.Scale`) のいずれかが指定されている場合、そのオペランドを `Yxxx` (不正なオペランドタイプ) として分類します。
    これは、`foo(SB)(AX)` のような構文を捕捉するためのものです。`foo(SB)` は `a.Name != obj.NAME_NONE` に該当し、`(AX)` は `a.Index != REG_NONE` に該当します。以前は、この組み合わせが `Ym` (有効なメモリオペランド) として扱われていましたが、この変更により `Yxxx` となり、アセンブラがエラーを報告するようになります。

### 2. 重複エラーメッセージの修正

*   **`src/cmd/internal/obj/link.go` の `Link` 構造体と `Diag` メソッド**:
    `obj.Link` 構造体に `Errors int` フィールドが追加され、エラーの総数を追跡するようになりました。
    また、`Diag` フィールドが `DiagFunc` にリネームされ、`func (ctxt *Link) Diag` という新しいメソッドが追加されました。
    ```go
    type Link struct {
    	// ...
    	DiagFunc           func(string, ...interface{})
    	// ...
    	Errors             int
    }

    func (ctxt *Link) Diag(format string, args ...interface{}) {
    	ctxt.Errors++
    	ctxt.DiagFunc(format, args...)
    }
    ```
    これにより、アセンブラの様々な箇所でエラーが報告される際に、`ctxt.Diag` メソッドを呼び出すことで、`Errors` カウンタが自動的にインクリメントされるようになります。実際のメッセージ出力は `DiagFunc` に委譲されます。

*   **`src/cmd/internal/obj/x86/asm6.go` の `span6` 関数**:
    `span6` 関数は、アセンブリ命令のサイズを決定するためにループ内で複数回実行される可能性があります。以前は、このループ内でエラーが報告されるたびにメッセージが出力されていました。
    ```go
    func span6(ctxt *obj.Link, s *obj.LSym) {
    	// ...
    	errors := ctxt.Errors // ループ開始時のエラー数を記録
    	for {
    		loop = 0
    		// ... 命令の処理 ...
    		if loop == 0 {
    			break
    		}
    		if ctxt.Errors > errors { // ループ内で新しいエラーが報告された場合
    			return // span6関数を終了
    		}
    	}
    	// ...
    }
    ```
    この変更により、`span6` 関数のループの開始時に `ctxt.Errors` の現在の値が `errors` 変数に保存されます。ループの各イテレーションの終わりに、`ctxt.Errors` が `errors` よりも大きい場合（つまり、この `span6` の実行中に新しいエラーが報告された場合）、関数は直ちに `return` します。これにより、同じ命令に対するエラーメッセージが複数回出力されるのを防ぎ、エラー報告の重複が解消されます。

### テストの追加

*   **`src/cmd/asm/internal/asm/endtoend_test.go`**:
    `testErrors` という新しいテスト関数が追加されました。この関数は、アセンブリソースファイル内のコメント `// ERROR "..."` を解析し、アセンブラが実際に報告したエラーメッセージと比較することで、エラー報告が期待通りに行われるかを検証します。
    `src/cmd/asm/internal/asm/testdata/amd64error.s` という新しいテストファイルが追加され、`MOVL foo<>(SB)(AX), AX // ERROR "invalid instruction"` という不正な命令が含まれています。このテストは、アセンブラがこの命令に対して正しく「invalid instruction」エラーを報告することを確認します。

## コアとなるコードの解説

### `obj.Link` 構造体と `Diag` メソッド

`obj.Link` 構造体は、アセンブラとリンカの処理全体で共有されるコンテキストオブジェクトです。以前は、エラー報告のための関数ポインタ `Diag` を直接持っていました。このコミットでは、`Diag` を `DiagFunc` にリネームし、`Errors` という整数フィールドを追加しました。そして、`func (ctxt *Link) Diag` という新しいメソッドを導入しました。

この変更の意図は、エラー報告のメカニズムを改善することにあります。
1.  **エラー数の追跡**: `Errors` フィールドが追加されたことで、アセンブラは処理中に発生したエラーの総数を簡単に追跡できるようになりました。これは、後述する重複エラーメッセージの抑制に利用されます。
2.  **エラー報告の抽象化**: `ctxt.Diag` メソッドは、`ctxt.Errors` をインクリメントしてから、実際のメッセージ出力を行う `ctxt.DiagFunc` を呼び出します。これにより、エラー報告のロジック（エラー数のカウントとメッセージ出力）が分離され、よりクリーンな設計になります。`DiagFunc` は、テスト時にはエラーを `t.Errorf` に報告するように設定され、実際の実行時には `log.Printf` に報告するように設定されます。

### `span6` 関数における重複エラーの抑制

`span6` 関数は、x86アーキテクチャのアセンブリ命令の最終的なサイズを決定し、コードを生成する重要なフェーズです。この処理は、命令のオペランドやジャンプの距離などによって、複数回繰り返されることがあります。以前は、このループの各イテレーションで同じ不正な命令が検出されるたびにエラーメッセージが出力され、結果として重複したエラーメッセージがユーザーに表示されていました。

新しいコードでは、`span6` 関数の冒頭で `errors := ctxt.Errors` を実行し、現在のエラー数を記録します。ループの各イテレーションの終わりに `if ctxt.Errors > errors { return }` というチェックが追加されました。これは、現在の `span6` の実行中に `ctxt.Diag` メソッドが呼び出され、`ctxt.Errors` がインクリメントされた場合（つまり、新しいエラーが報告された場合）、直ちに `span6` 関数を終了することを意味します。これにより、同じ命令に対する後続の `span` イテレーションで再びエラーが報告されることがなくなり、エラーメッセージの重複が効果的に抑制されます。

### `oclass` 関数における不正構文 `foo(SB)(AX)` の拒否

`oclass` 関数は、アセンブリ命令のオペランドがどのタイプに属するかを分類する役割を担っています。Goアセンブラのx86バックエンド (`asm6.go`) において、`obj.TYPE_MEM` (メモリ参照) のオペランドを処理する部分に重要な変更が加えられました。

以前は、`foo(SB)(AX)` のような構文が与えられた場合、`foo(SB)` はシンボルアドレスとして認識され、`(AX)` はインデックスレジスタとして認識されます。しかし、`foo(SB)` 自体が既にメモリ上のアドレスを指しているため、その後にさらにインデックスレジスタを指定することは、x86アセンブリの標準的なメモリアドレッシングモードとしては不正です。アセンブラはこれを黙って `foo(SB)` として解釈し、`(AX)` を無視していました。

新しいコードでは、`obj.TYPE_MEM` のオペランドがシンボル名 (`a.Name != obj.NAME_NONE`) を持ち、かつ64ビットモード (`ctxt.Asmode == 64`) で、レジスタ (`a.Reg`)、インデックスレジスタ (`a.Index`)、またはスケール (`a.Scale`) のいずれかが指定されている場合に、そのオペランドを `Yxxx` として分類します。`Yxxx` は「不正なオペランドタイプ」を意味し、これによりアセンブラはエラーを報告するようになります。この変更により、アセンブラは不正な構文を早期に検出し、開発者に正確なフィードバックを提供するようになります。

## 変更の背景

このコミットは、Goアセンブラ（`cmd/asm`）の2つの既存の問題に対処するために行われました。

1.  **不正なアセンブリ構文の黙示的な許容**: 以前のGoアセンブラは、`foo(SB)(AX)` のような不正なメモリアドレッシングモードを、`foo(SB)` と解釈し、` (AX)` 部分を黙って無視していました。`foo(SB)` はシンボル `foo` のアドレスを指し、`SB` (Static Base) は静的メモリ領域のベースレジスタです。` (AX)` はインデックスレジスタ `AX` を使ったオフセット指定を意味しますが、`foo(SB)` 自体が既にメモリ上のアドレスを指しているため、これらを組み合わせることは通常、x86アセンブリの文法として不正です。アセンブラがこれをエラーとして報告せず、誤った解釈をしていたため、開発者は意図しないコードを生成してしまう可能性がありました。この変更は、このような曖昧で不正な構文を明示的にエラーとして扱うことで、アセンブラの厳密性を高め、バグの早期発見に貢献します。

2.  **重複するエラーメッセージの出力**: アセンブラが不正な命令を検出した際、エラーメッセージが複数回（特に `span` イテレーションごとに）出力されるという問題がありました。これにより、エラーログが冗長になり、実際の問題の特定が困難になることがありました。この変更は、エラーメッセージが一度だけ出力されるように修正し、診断の明確性を向上させます。

これらの問題は、Goアセンブラのユーザーエクスペリエンスとコードの正確性に影響を与えていたため、修正が必要とされました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびアセンブラに関する知識が役立ちます。

*   **Goアセンブラ (`cmd/asm`)**: Go言語のツールチェーンの一部であり、Goプログラムから呼び出されるアセンブリコードを記述するために使用されます。GoのアセンブリはPlan 9アセンブラの構文に基づいており、一般的なx86アセンブリとは異なる独自の記法を持っています。
*   **シンボル (`SB`)**: Goアセンブラにおける `SB` (Static Base) は、静的メモリ領域のベースアドレスを示す擬似レジスタです。グローバル変数や関数などのシンボルは、`foo(SB)` のように `SB` を基準としたオフセットで参照されます。
*   **メモリアドレッシングモード (x86)**: x86アーキテクチャでは、メモリ上のデータにアクセスするための様々なアドレッシングモードがあります。
    *   **ベースレジスタ + オフセット**: `[base + offset]` の形式。例: `[RBP - 8]`
    *   **ベースレジスタ + インデックスレジスタ * スケール + オフセット**: `[base + index * scale + offset]` の形式。例: `[RBX + RSI * 4 + 0x10]`
    *   **シンボルアドレス**: `foo(SB)` のように、シンボルのアドレスを直接指定する形式。
    `foo(SB)(AX)` のような構文は、シンボルアドレス `foo(SB)` とインデックスレジスタ `AX` を組み合わせようとするもので、通常は有効なx86メモリアドレッシングモードではありません。`foo(SB)` 自体が既にメモリ上のアドレスを指しているため、その後にさらにインデックスレジスタを指定することは文法的に矛盾します。
*   **`obj.Link` コンテキスト**: Goのアセンブラおよびリンカの内部では、`obj.Link` 構造体がアセンブリ処理全体のコンテキストを管理します。これには、エラー報告のための `Diag` (または `DiagFunc`) や、シンボルリストなどが含まれます。
*   **`span` 関数**: アセンブラのバックエンド処理の一部で、命令のサイズを決定し、最終的なバイナリコードを生成する過程で呼び出されます。この処理は、命令のオペランドの複雑さや、ジャンプ命令のターゲットアドレスの距離などに応じて複数回繰り返されることがあります。

### 1. `foo(SB)(AX)` の拒否

*   **`src/cmd/internal/obj/x86/asm6.go` の `oclass` 関数**:

### 2. 重複エラーメッセージの修正

*   **`src/cmd/internal/obj/link.go` の `Link` 構造体と `Diag` メソッド**:
    `obj.Link` 構造体に `Errors int` フィールドが追加され、エラーの総数を追跡するようになりました。
    また、`Diag` フィールドが `DiagFunc` にリネームされ、`func (ctxt *Link) Diag` という新しいメソッドが追加されました。
    ```go
    type Link struct {
    	// ...
    	DiagFunc           func(string, ...interface{})
    	// ...
    	Errors             int
    }

    func (ctxt *Link) Diag(format string, args ...interface{}) {
    	ctxt.Errors++
    	ctxt.DiagFunc(format, args...)
    }
    ```
    これにより、アセンブラの様々な箇所でエラーが報告される際に、`ctxt.Diag` メソッドを呼び出すことで、`Errors` カウンタが自動的にインクリメントされるようになります。実際のメッセージ出力は `DiagFunc` に委譲されます。

*   **`src/cmd/internal/obj/x86/asm6.go` の `span6` 関数**:
    `span6` 関数は、アセンブリ命令のサイズを決定するためにループ内で複数回実行される可能性があります。以前は、このループ内でエラーが報告されるたびにメッセージが出力されていました。
    ```go
    func span6(ctxt *obj.Link, s *obj.LSym) {
    	var loop int32
    	var m int
    	var p *obj.Prog
    	errors := ctxt.Errors // ループ開始時のエラー数を記録
    	for {
    		loop = 0
    		// ... 命令の処理 ...
    		if loop == 0 {
    			break
    		}
    		if ctxt.Errors > errors { // ループ内で新しいエラーが報告された場合
    			return // span6関数を終了
    		}
    	}
    	// ...
    }
    ```
    この変更により、`span6` 関数のループの開始時に `ctxt.Errors` の現在の値が `errors` 変数に保存されます。ループの各イテレーションの終わりに `if ctxt.Errors > errors { return }` というチェックが追加されました。これは、現在の `span6` の実行中に `ctxt.Diag` メソッドが呼び出され、`ctxt.Errors` がインクリメントされた場合（つまり、新しいエラーが報告された場合）、関数は直ちに `return` します。これにより、同じ命令に対するエラーメッセージが複数回出力されるのを防ぎ、エラー報告の重複が効果的に抑制されます。

### テストの追加

*   **`src/cmd/asm/internal/asm/endtoend_test.go`**:
    `testErrors` という新しいテスト関数が追加されました。この関数は、アセンブリソースファイル内のコメント `// ERROR "..."` を解析し、アセンブラが実際に報告したエラーメッセージと比較することで、エラー報告が期待通りに行われるかを検証します。

## コアとなるコードの解説

### `obj.Link` 構造体と `Diag` メソッド

`obj.Link` 構造体は、アセンブラとリンカの処理全体で共有されるコンテキストオブジェクトです。以前は、エラー報告のための関数ポインタ `Diag` を直接持っていました。このコミットでは、`Diag` を `DiagFunc` にリネームし、`Errors` という整数フィールドを追加しました。そして、`func (ctxt *Link) Diag` という新しいメソッドを導入しました。

この変更の意図は、エラー報告のメカニズムを改善することにあります。
1.  **エラー数の追跡**: `Errors` フィールドが追加されたことで、アセンブラは処理中に発生したエラーの総数を簡単に追跡できるようになりました。これは、後述する重複エラーメッセージの抑制に利用されます。
2.  **エラー報告の抽象化**: `ctxt.Diag` メソッドは、`ctxt.Errors` をインクリメントしてから、実際のメッセージ出力を行う `ctxt.DiagFunc` を呼び出します。これにより、エラー報告のロジック（エラー数のカウントとメッセージ出力）が分離され、よりクリーンな設計になります。`DiagFunc` は、テスト時にはエラーを `t.Errorf` に報告するように設定され、実際の実行時には `log.Printf` に報告するように設定されます。

### `span6` 関数における重複エラーの抑制

`span6` 関数は、x86アーキテクチャのアセンブリ命令の最終的なサイズを決定し、コードを生成する重要なフェーズです。この処理は、命令のオペランドやジャンプの距離などによって、複数回繰り返されることがあります。以前は、このループの各イテレーションで同じ不正な命令が検出されるたびにエラーメッセージが出力され、結果として重複したエラーメッセージがユーザーに表示されていました。

新しいコードでは、`span6` 関数の冒頭で `errors := ctxt.Errors` を実行し、現在のエラー数を記録します。ループの各イテレーションの終わりに `if ctxt.Errors > errors { return }` というチェックが追加されました。これは、現在の `span6` の実行中に `ctxt.Diag` メソッドが呼び出され、`ctxt.Errors` がインクリメントされた場合（つまり、新しいエラーが報告された場合）、直ちに `span6` 関数を終了することを意味します。これにより、同じ命令に対する後続の `span` イテレーションで再びエラーが報告されることがなくなり、エラーメッセージの重複が効果的に抑制されます。

### `oclass` 関数における不正構文 `foo(SB)(AX)` の拒否

`oclass` 関数は、アセンブリ命令のオペランドがどのタイプに属するかを分類する役割を担っています。Goアセンブラのx86バックエンド (`asm6.go`) において、`obj.TYPE_MEM` (メモリ参照) のオペランドを処理する部分に重要な変更が加えられました。

以前は、`foo(SB)(AX)` のような構文が与えられた場合、`foo(SB)` はシンボルアドレスとして認識され、`(AX)` はインデックスレジスタとして認識されます。しかし、`foo(SB)` 自体が既にメモリ上のアドレスを指しているため、その後にさらにインデックスレジスタを指定することは、x86アセンブリの標準的なメモリアドレッシングモードとしては不正です。アセンブラはこれを黙って `foo(SB)` として解釈し、`(AX)` を無視していました。

新しいコードでは、`obj.TYPE_MEM` のオペランドがシンボル名 (`a.Name != obj.NAME_NONE`) を持ち、かつ64ビットモード (`ctxt.Asmode == 64`) で、レジスタ (`a.Reg`)、インデックスレジスタ (`a.Index`)、またはスケール (`a.Scale`) のいずれかが指定されている場合に、そのオペランドを `Yxxx` として分類します。`Yxxx` は「不正なオペランドタイプ」を意味し、これによりアセンブラはエラーを報告するようになります。この変更により、アセンブラは不正な構文を早期に検出し、開発者に正確なフィードバックを提供するようになります。

# [インデックス 21092] ファイルの概要

このコミットは、Goコンパイラ（`6g`と`8g`）におけるレジスタ使用スキャンに関する不要かつ不正確なコードを削除するものです。具体的には、レジスタ割り当ての際に、考慮対象の領域を超えてレジスタの使用状況をスキャンしていた古いロジックが削除されました。これにより、特定のレジスタ（`AX`や`DX`）の割り当てが不必要に制限される問題が解決されています。

## コミット

```
commit c3dadb3d190973b888f5f83de3a3cccdbe7fc949
Author: Austin Clements <austin@google.com>
Date:   Thu Nov 13 13:34:20 2014 -0500

    [dev.power64] 6g,8g: remove unnecessary and incorrect reg use scanning
    
    Previously, the 6g and 8g registerizers scanned for used
    registers beyond the end of a region being considered for
    registerization.  This ancient artifact was copied from the C
    compilers, where it was probably necessary to track implicitly
    used registers.  In the Go compilers it's harmless (because it
    can only over-restrict the set of available registers), but no
    longer necessary because the Go compilers correctly track
    register use/set information.  The consequences of this extra
    scan were (at least) that 1) we would not consider allocating
    the AX register if there was a deferproc call in the future
    because deferproc uses AX as a return register, so we see the
    use of AX, but don't track that AX is set by the CALL, and 2)
    we could not consider allocating the DX register if there was
    a MUL in the future because MUL implicitly sets DX and (thanks
    to an abuse of copyu in this code) we would also consider DX
    used.
    
    This commit fixes these problems by nuking this code.
    
    LGTM=rsc
    R=rsc
    CC=golang-codereviews
    https://golang.org/cl/174110043
```

## 元コミット内容

このコミットは、Goコンパイラ（`6g`と`8g`）のレジスタ割り当てロジックから、不要かつ不正確なレジスタ使用スキャンコードを削除するものです。以前のバージョンでは、レジスタ割り当ての対象となる領域を超えて、将来的に使用される可能性のあるレジスタをスキャンしていました。このスキャンは、Cコンパイラから引き継がれた古い遺物であり、Goコンパイラではレジスタの使用/設定情報が正確に追跡されているため、もはや不要となっていました。

この余分なスキャンは、以下の2つの具体的な問題を引き起こしていました。

1.  `deferproc`呼び出しが将来的に存在する場合、`AX`レジスタの割り当てが考慮されなくなる問題。`deferproc`は`AX`を戻りレジスタとして使用するため、スキャンは`AX`の使用を検出しますが、`CALL`によって`AX`が設定されることを追跡していませんでした。
2.  `MUL`命令が将来的に存在する場合、`DX`レジスタの割り当てが考慮されなくなる問題。`MUL`は暗黙的に`DX`を設定し、さらにコード内の`copyu`の誤用により、`DX`が使用済みと見なされていました。

このコミットは、これらの問題を引き起こしていたコードを完全に削除することで解決しています。

## 変更の背景

この変更の背景には、Goコンパイラのレジスタ割り当て戦略の進化があります。初期のGoコンパイラは、Cコンパイラの設計思想やコードベースの一部を継承していました。C言語のような低レベル言語のコンパイラでは、レジスタの使用状況を正確に追跡することが難しく、特に暗黙的なレジスタの使用（例えば、特定の命令が副作用として特定のレジスタを変更する場合）を考慮するために、より広範なレジスタ使用スキャンが必要となることがありました。

しかし、Goコンパイラは時間の経過とともに成熟し、レジスタの使用および設定に関する情報をより正確かつ包括的に追跡できるようになりました。これにより、Cコンパイラから引き継がれた「レジスタ割り当て対象領域を超えたレジスタ使用スキャン」という古いメカニズムが、Goコンパイラの文脈では冗長かつ不正確なものとなっていました。

この冗長なスキャンは、コンパイラのレジスタ割り当て器（registerizer）が利用可能なレジスタを過度に制限する原因となっていました。特に、`deferproc`（Goの`defer`文の実装に関連する関数）や`MUL`（乗算命令）のような特定の操作が、実際には問題ないにもかかわらず、特定のレジスタ（`AX`や`DX`）の割り当てを妨げていました。これは、コンパイラがレジスタのライフタイムを正確に把握できていないことに起因していました。

このコミットは、このような非効率性とバグを解消し、Goコンパイラのレジスタ割り当てをより正確で効率的なものにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

### 1. コンパイラのレジスタ割り当て (Register Allocation)

レジスタ割り当ては、コンパイラの最適化フェーズの一つで、プログラムの変数や中間結果をCPUのレジスタに割り当てるプロセスです。レジスタはメモリよりもはるかに高速にアクセスできるため、効率的なレジスタ割り当てはプログラムの実行速度に大きく影響します。

レジスタ割り当ての主な目的は、メモリへのアクセスを最小限に抑え、レジスタの使用を最大化することです。これには、変数の「ライブネス」（変数がその時点で将来的に使用される可能性があるかどうか）を分析し、ライブな期間が重ならない変数に同じレジスタを割り当てるなどの技術が用いられます。

### 2. Goコンパイラ (`6g`, `8g`)

Go言語の初期のコンパイラは、ターゲットアーキテクチャに応じて異なる名前を持っていました。
*   `6g`: AMD64 (x86-64) アーキテクチャ向けのGoコンパイラ。
*   `8g`: x86 (32-bit) アーキテクチャ向けのGoコンパイラ。

これらのコンパイラは、Goのソースコードを機械語に変換する役割を担っていました。現在のGoツールチェーンでは、`go build`コマンドが内部的に適切なコンパイラを呼び出すため、ユーザーが直接これらの名前を意識することは少なくなっています。

### 3. `deferproc`

`deferproc`は、Go言語の`defer`文を実装するためにGoランタイムが使用する内部関数です。`defer`文は、関数がリターンする直前（またはパニックが発生した場合）に実行される関数呼び出しをスケジュールします。`deferproc`は、この遅延実行される関数呼び出しをスタックに記録する役割を担います。

`deferproc`のようなランタイム関数は、特定のレジスタを内部的に使用することがあります。このコミットの文脈では、`deferproc`が`AX`レジスタを戻りレジスタとして使用することが問題となっていました。

### 4. `MUL`命令と暗黙的なレジスタ使用

`MUL`は、x86アーキテクチャにおける乗算命令です。この命令の重要な特徴は、そのオペランドと結果の格納方法にあります。
*   32ビットの乗算（`MUL r/m32`）の場合、`EAX`レジスタの内容と指定されたオペランドを乗算し、結果の64ビット値を`EDX:EAX`（`EDX`が上位32ビット、`EAX`が下位32ビット）に格納します。
*   64ビットの乗算（`MUL r/m64`）の場合、`RAX`レジスタの内容と指定されたオペランドを乗算し、結果の128ビット値を`RDX:RAX`に格納します。

このように、`MUL`命令は明示的に`DX`（または`EDX`/`RDX`）レジスタを指定しなくても、その内容を暗黙的に変更します。コンパイラがこの暗黙的な使用を正確に追跡できない場合、`DX`レジスタが不必要に「使用中」と見なされ、他の目的での割り当てが妨げられる可能性があります。

### 5. `copyu`関数

コミットメッセージに「abuse of copyu」とある`copyu`関数は、コンパイラの内部でレジスタやメモリのアドレス情報をコピーまたは変換するために使用されるユーティリティ関数であると推測されます。この文脈では、`copyu`が`MUL`命令による`DX`の暗黙的な設定を誤って「使用」として解釈し、レジスタ割り当て器に誤った情報を提供していたことを示唆しています。

## 技術的詳細

このコミットが修正している問題は、コンパイラのレジスタ割り当て器が、プログラムの特定のポイントにおけるレジスタの「ライブネス」を誤って判断していたことに起因します。

レジスタ割り当て器は通常、プログラムを基本ブロック（分岐のない一連の命令）に分割し、各基本ブロックの入り口と出口でどのレジスタがライブであるかを分析します。この分析は、データフロー解析（data-flow analysis）と呼ばれる技術を用いて行われます。レジスタがライブであるとは、そのレジスタに格納された値が将来の命令で読み取られる可能性があることを意味します。

問題のコードは、レジスタ割り当ての対象となる「領域」（おそらくは基本ブロックや関数のサブグラフ）を超えて、将来の命令におけるレジスタの使用状況をスキャンしていました。これは、Cコンパイラでは暗黙的なレジスタ使用を捕捉するために必要だったかもしれませんが、Goコンパイラではレジスタの使用/設定情報がより正確に追跡されているため、この「余分なスキャン」は冗長でした。

この冗長なスキャンが引き起こした具体的な問題は以下の通りです。

1.  **`deferproc`と`AX`レジスタ**:
    *   `deferproc`は、Goランタイムの内部で`AX`レジスタを戻り値のレジスタとして使用します。
    *   問題のレジスタ使用スキャンは、`deferproc`呼び出しが将来的に存在する場合、`AX`レジスタが使用されることを検出します。
    *   しかし、このスキャンは`CALL`命令（`deferproc`を呼び出す命令）によって`AX`レジスタが「設定される」（つまり、新しい値が書き込まれる）ことを正確に追跡していませんでした。
    *   結果として、スキャンは`AX`が使用されることだけを見て、その後の`CALL`によって`AX`が上書きされることを考慮せず、`AX`レジスタが「ライブ」であると誤って判断し続けました。これにより、`AX`レジスタが不必要に割り当て不可能となり、コンパイラが他のレジスタを使用せざるを得なくなるか、あるいはスピル（レジスタの内容をメモリに退避させること）を引き起こしていました。

2.  **`MUL`命令と`DX`レジスタ**:
    *   `MUL`命令は、前述の通り、暗黙的に`DX`レジスタを結果の一部として設定します。
    *   問題のコードは、この`MUL`命令による`DX`の暗黙的な設定を、`copyu`関数の「誤用」を通じて「使用」として解釈していました。`copyu`は、レジスタのコピーや使用状況を分析する際に用いられる関数ですが、この文脈では`MUL`の副作用を誤ってレジスタの「使用」としてフラグ付けしていたと考えられます。
    *   これにより、`MUL`命令が将来的に存在する場合、`DX`レジスタが不必要に「ライブ」であると見なされ、割り当てが妨げられていました。

このコミットは、これらの誤ったレジスタ使用スキャンロジックを削除することで、レジスタ割り当て器がより正確なレジスタのライブネス情報を基に動作するように修正しています。これにより、コンパイラはより効率的にレジスタを割り当て、生成されるコードの品質を向上させることができます。

## コアとなるコードの変更箇所

このコミットでは、主に`src/cmd/6g/reg.c`と`src/cmd/8g/reg.c`の2つのファイルが変更されています。両ファイルで同様のコードが削除されています。

### `src/cmd/6g/reg.c` (同様の変更が `src/cmd/8g/reg.c` にも適用)

**削除された関数:**

*   `uint32 regset(Reg *r, uint32 bb)`:
    *   この関数は、指定されたレジスタセット`bb`のうち、プログラムの命令`r->f.prog`によって「設定される」（値が書き込まれる）レジスタを特定していました。`copyu`関数の戻り値`c == 3`が「設定」を意味していたようです。
*   `uint32 reguse(Reg *r, uint32 bb)`:
    *   この関数は、指定されたレジスタセット`bb`のうち、プログラムの命令`r->f.prog`によって「使用される」（値が読み取られる）レジスタを特定していました。`copyu`関数の戻り値`c == 1 || c == 2 || c == 4`が「使用」を意味していたようです。

**`paint2`関数内の変更:**

`paint2`関数は、レジスタ割り当てのライブネス分析の一部として使用される関数です。この関数内で、削除された`regset`と`reguse`関数を使用していた以下のループが削除されました。

```c
    bb = vreg;
    for(; r; r=(Reg*)r->f.s1) {
        x = r->regu & ~bb;
        if(x) {
            vreg |= reguse(r, x);
            bb |= regset(r, x);
        }
    }
```

このループは、現在のレジスタのライブネス情報（`vreg`）と、将来の命令（`r`が指す命令列）におけるレジスタの使用/設定情報を組み合わせて、`vreg`を更新していました。この「将来の命令におけるレジスタ使用スキャン」が、コミットメッセージで言及されている不要なロジックでした。

## コアとなるコードの解説

削除されたコードは、コンパイラのレジスタ割り当て器が、現在の命令のコンテキストを超えて、将来の命令におけるレジスタの使用状況を予測しようとする試みでした。

`regset`と`reguse`関数は、特定の命令（`r->f.prog`）が与えられたレジスタセット（`bb`）のどのレジスタを「設定」（書き込み）し、どのレジスタを「使用」（読み込み）するかを判断するために設計されていました。これらは`copyu`という内部関数に依存しており、`copyu`の戻り値によってレジスタの操作タイプ（使用、設定、両方など）を区別していました。

`paint2`関数内の削除されたループは、レジスタ割り当てのバックワードデータフロー分析の一部として機能していました。`r`は命令のリストを逆順に辿るポインタであり、`r->f.s1`は次の命令を指していました。このループは、現在の命令から遡って、将来の命令（つまり、現在の命令より後に実行される命令）がどのレジスタを使用または設定するかを分析し、その情報を`vreg`（ライブレジスタのビットマスク）に統合していました。

このロジックは、Cコンパイラのようにレジスタのライフタイム分析が不完全な場合に、暗黙的なレジスタ使用を捕捉するための「安全策」として機能した可能性があります。しかし、Goコンパイラでは、より洗練されたデータフロー分析によってレジスタのライブネスが正確に追跡されるようになったため、この追加のスキャンは冗長となり、むしろ`AX`や`DX`レジスタの割り当てを誤って制限する原因となっていました。

このコミットによるコードの削除は、Goコンパイラがレジスタ割り当てにおいて、より正確で局所的な情報に依存するようになったことを示しています。これにより、コンパイラの複雑性が軽減され、同時にレジスタ割り当ての効率と正確性が向上しました。

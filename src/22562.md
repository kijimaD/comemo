# [インデックス 22562] ファイルの概要

このコミットは、Go言語のツールチェイン、特にWindows/386アーキテクチャにおける外部リンキングのサポートを改善することを目的としています。具体的には、Goのリンカ (`cmd/internal/ld` および `cmd/8l`) が、外部リンカ (例: MinGWの`gcc`) を使用してWindowsの32ビット実行可能ファイル (PEフォーマット) を生成する際の、リロケーション処理とPEヘッダの生成ロジックを修正・強化しています。これにより、GoプログラムがCgoを介してCライブラリとリンクする場合や、システムDLLとリンクする場合の安定性と正確性が向上します。

## 変更の背景

Go言語は、通常、独自の内部リンカを使用して実行可能ファイルを生成します。しかし、C言語で書かれたライブラリ（Cgoを使用する場合）や、オペレーティングシステムが提供する特定のDLL（ダイナミックリンクライブラリ）とリンクする必要がある場合、Goの内部リンカだけでは対応できないことがあります。このようなシナリオでは、システムにインストールされている外部リンカ（Windowsでは通常、MinGWなどのGCCツールチェインに含まれる`ld`やMicrosoft Visual C++の`link.exe`）を使用する必要があります。これを「外部リンキング」と呼びます。

このコミットは、Windows/386（32ビットWindows）環境における外部リンキングの既存の問題（コミットメッセージで「#4069」と参照されている問題）を解決するために導入されました。具体的な問題の詳細はコミットメッセージからは不明ですが、一般的に外部リンキングの問題は、シンボルの解決、リロケーションの不正確さ、または生成される実行可能ファイルのPE（Portable Executable）フォーマットの不整合に起因することが多いです。このコミットは、これらの問題を解決し、Windows/386での外部リンキングの信頼性を向上させることを目的としています。

## 前提知識の解説

### Goのリンカ (`cmd/ld`, `cmd/8l`)

Go言語のビルドシステムは、コンパイラ (`cmd/compile`) とリンカ (`cmd/link`) を含んでいます。`cmd/link`は、Goのソースコードから生成されたオブジェクトファイル（`.o`ファイル）と、必要なライブラリを結合して最終的な実行可能ファイルを生成する役割を担います。
`cmd/8l`は、`cmd/link`の一部であり、特に386（Intel 32ビット）アーキテクチャ向けのリンカです。Goのリンカは、ほとんどの場合、完全に自己完結しており、外部ツールに依存しません。

### 外部リンキング (External Linking)

Goのビルドプロセスにおいて、`go build -ldflags="-linkmode=external"` のように指定することで、Goの内部リンカではなく、システムにインストールされている外部リンカを使用させることができます。
*   **メリット**:
    *   Cgoを介してC/C++ライブラリとリンクする際に必須となることが多い。
    *   特定のシステムライブラリ（例: GUIライブラリ、データベースドライバなど）との互換性を確保できる。
    *   外部リンカが提供する高度な最適化や機能を利用できる場合がある。
*   **デメリット**:
    *   ビルド環境に外部リンカ（例: MinGW、Visual Studio）がインストールされている必要がある。
    *   クロスコンパイルが複雑になる場合がある。
    *   ビルド時間が長くなる可能性がある。

### PE (Portable Executable) フォーマット

PEフォーマットは、Windowsオペレーティングシステムで使用される実行可能ファイル、オブジェクトコード、DLL、FON（フォント）ファイルのファイル形式です。PEファイルは、ヘッダ、セクション、インポート/エクスポートテーブル、リソース、リロケーション情報など、プログラムを実行するために必要なすべての情報を含んでいます。
*   **ヘッダ**: ファイルの種類、ターゲットアーキテクチャ、タイムスタンプなどの基本的な情報。
*   **セクション**: コード、初期化済みデータ、未初期化データ（BSS）、リソースなどの論理的なブロック。
*   **インポートテーブル**: 外部DLLからインポートされる関数に関する情報。
*   **リロケーションテーブル**: プログラムがメモリにロードされる際に、絶対アドレスを修正するために必要な情報。

### リロケーション (Relocation)

リロケーションとは、コンパイル時やリンク時に決定できないメモリアドレスを、プログラムが実際にメモリにロードされる際に修正するプロセスです。
*   **絶対リロケーション**: 特定のメモリアドレスへの参照を、ロード時のベースアドレスに基づいて調整します。
*   **相対リロケーション (PC-relative relocation)**: プログラムカウンタ（PC）からの相対オフセットに基づいてアドレスを計算します。
PEフォーマットでは、`IMAGE_REL_I386_DIR32`（32ビット絶対アドレス）や`IMAGE_REL_I386_REL32`（32ビット相対アドレス）などのリロケーションタイプが定義されています。外部リンキングでは、Goのコードと外部ライブラリのコードが異なるアドレス空間に配置される可能性があるため、正確なリロケーションが不可欠です。

### COFF (Common Object File Format)

COFFは、PEフォーマットの基盤となるオブジェクトファイルフォーマットです。PEファイルは、COFFの概念を拡張して実行可能ファイルとしています。COFFシンボルテーブルは、プログラム内のシンボル（関数、変数など）に関する情報（名前、アドレス、型など）を格納します。

## 技術的詳細

このコミットは、主に以下のファイルに影響を与え、Windows/386における外部リンキングの挙動を修正・改善しています。

1.  **`src/cmd/internal/ld/pe.go`**:
    *   PEヘッダの生成ロジックが、外部リンキング (`LinkExternal`) の場合に分岐するようになりました。特に、`.symtab` セクションの扱いが変更され、外部リンキング時にはGoの内部シンボルテーブルをPEファイルに含めないようにしています。これは、外部リンカが独自のシンボル解決を行うため、Goの内部シンボルテーブルがWindowsリンカを混乱させる可能性があったためと考えられます。
    *   `peemitreloc` 関数が追加され、外部リンキング時にPEフォーマットのリロケーションエントリを生成するようになりました。これは、Goのオブジェクトファイル (`go.o`) 内のシンボルに対するリロケーション情報を、外部リンカが理解できる形式でPEファイルに書き出すために重要です。
    *   `perelocsect` 関数が追加され、各セクション内のリロケーションを処理し、リロケーションエントリの数をカウントするようになりました。
    *   `addpesym` 関数が修正され、外部リンキング時に`SHOSTOBJ`（ホストオブジェクト、つまり外部リンカが扱うシンボル）や`cgoexport`されたシンボルに対して、シンボル名をアンダースコア (`_`) でプレフィックスするようになりました。これは、WindowsのリンカがC言語のシンボルにアンダースコアを付加する慣習に合わせるためです。
    *   `IMAGE_FILE_LINE_NUMS_STRIPPED` や `IMAGE_SCN_LNK_NRELOC_OVFL` といったPEフラグが追加・利用され、PEファイルの特性をより正確に表現できるようになりました。
    *   `.bss` セクション（未初期化データ）の扱いが外部リンキング時に変更され、`IMAGE_SCN_ALIGN_32BYTES` フラグが追加されています。

2.  **`src/cmd/8l/asm.go`**:
    *   `pereloc1` 関数が追加されました。この関数は、386アーキテクチャにおけるPEフォーマットのリロケーションエントリを生成する具体的なロジックを実装しています。`R_ADDR`（絶対アドレス）と `R_CALL`/`R_PCREL`（相対アドレス）のリロケーションタイプに対応し、それぞれ `IMAGE_REL_I386_DIR32` と `IMAGE_REL_I386_REL32` のPEリロケーションタイプにマッピングしています。
    *   `adddynrel` 関数内で、Windows環境でのリロケーション処理をスキップする条件が追加されました。これは、`pereloc1` でリロケーションが処理されるため、重複を避けるためです。

3.  **`src/cmd/8l/obj.go`**:
    *   `ld.Thearch.PEreloc1 = pereloc1` の行が追加され、386アーキテクチャのリンカ設定に `pereloc1` 関数が登録されました。これにより、PEフォーマットのリロケーション処理が386リンカで利用可能になります。
    *   `ld.Hwindows` が `archinit` 関数のブレーク条件に追加され、Windowsが特定のアーキテクチャ初期化パスに含まれるようになりました。

4.  **`src/cmd/internal/ld/data.go`**:
    *   `relocsym` 関数内で、`HEADTYPE == Hwindows` の場合にリロケーション処理をスキップする条件が追加されました。これは、外部リンキング時のリロケーションが `pe.go` で処理されるため、Goの内部リロケーション処理との競合を避けるためです。
    *   `dynrelocsym` 関数が `LinkExternal` モードの場合に動的リロケーションをスキップするように変更されました。

5.  **`src/cmd/internal/ld/lib.go`**:
    *   `Arch` 構造体に `PEreloc1` フィールドが追加され、アーキテクチャ固有のPEリロケーション関数を登録できるようになりました。
    *   `hostlink` 関数内で、Windows (`HEADTYPE == Hwindows`) の場合に、`headstring`（出力タイプ、例: `windowsgui` または `console`）に応じて外部リンカに `-mwindows` または `-mconsole` オプションを渡すようになりました。これにより、生成される実行可能ファイルがGUIアプリケーションかコンソールアプリケーションかを外部リンカに正しく伝えることができます。
    *   `peimporteddlls()` 関数が追加され、インポートされるDLLの名前から `-l` オプション（例: `-lkernel32`）を生成し、外部リンカに渡すようになりました。これにより、Goプログラムが依存するDLLを外部リンカが正しく解決できるようになります。
    *   `genasmsym` 関数内で、`SHOSTOBJ` シンボルがWindowsの場合に `U` タイプ（未定義シンボル）として出力されるようになりました。

6.  **`src/cmd/internal/ld/go.go`**:
    *   `cgo_export_static` のWindowsでの一時的なスキップロジックが削除されました。これは、このコミットによってWindowsでの外部リンキングが十分に安定したため、この一時的な回避策が不要になったことを示唆しています。

これらの変更は、GoのリンカがWindowsのPEフォーマットと外部リンカの挙動をより深く理解し、それらに適応するように再構築されたことを示しています。特に、リロケーション処理の分離と、外部リンカへの適切なオプションの引き渡しが、このコミットの核心です。

## コアとなるコードの変更箇所

### `src/cmd/8l/asm.go` における `pereloc1` 関数の追加

```go
func pereloc1(r *ld.Reloc, sectoff int64) bool {
	var v uint32

	rs := r.Xsym

	if rs.Dynid < 0 {
		ld.Diag("reloc %d to non-coff symbol %s type=%d", r.Type, rs.Name, rs.Type)
		return false
	}

	ld.Thearch.Lput(uint32(sectoff))
	ld.Thearch.Lput(uint32(rs.Dynid))

	switch r.Type {
	default:
		return false

	case ld.R_ADDR:
		v = ld.IMAGE_REL_I386_DIR32

	case ld.R_CALL,
		ld.R_PCREL:
		v = ld.IMAGE_REL_I386_REL32
	}

	ld.Thearch.Wput(uint16(v))

	return true
}
```

### `src/cmd/internal/ld/pe.go` における外部リンキング時のPEファイル生成ロジックの分岐

```go
// pewrite() 関数内の一部
if Linkmode == LinkExternal {
	// Add real symbol name
	for d := dr; d != nil; d = d.next {
		for m = d.ms; m != nil; m = m.next {
			m.s.Type = SDATA
			Symgrow(Ctxt, m.s, int64(Thearch.Ptrsize))
			dynName := m.s.Extname
			if m.argsize >= 0 {
				dynName += fmt.Sprintf("@%d", m.argsize)
			}
			dynSym := Linklookup(Ctxt, dynName, 0)
			dynSym.Reachable = true
			dynSym.Type = SHOSTOBJ
			r := Addrel(m.s)
			r.Sym = dynSym
			r.Off = 0
			r.Siz = uint8(Thearch.Ptrsize)
			r.Type = R_ADDR

			// pre-allocate symtab entries for those symbols
			dynSym.Dynid = int32(ncoffsym)
			ncoffsym++
		}
	}
} else {
	dynamic := Linklookup(Ctxt, ".windynamic", 0)
	dynamic.Reachable = true
	dynamic.Type = SWINDOWS
	for d := dr; d != nil; d = d.next {
		for m = d.ms; m != nil; m = m.next {
			m.s.Type = SWINDOWS | SSUB
			m.s.Sub = dynamic.Sub
			dynamic.Sub = m.s
			m.s.Value = dynamic.Size
			dynamic.Size += int64(Thearch.Ptrsize)
		}

		dynamic.Size += int64(Thearch.Ptrsize)
	}
}
```

## コアとなるコードの解説

### `pereloc1` 関数の追加 (`src/cmd/8l/asm.go`)

この関数は、WindowsのPEフォーマットにおけるリロケーションエントリを生成する中心的なロジックです。
*   `r *ld.Reloc`: 処理対象のリロケーション情報。
*   `sectoff int64`: リロケーションが適用されるセクション内のオフセット。
*   `rs := r.Xsym`: リロケーションのターゲットとなるシンボル。
*   `rs.Dynid`: COFFシンボルテーブルにおけるシンボルのインデックス。
*   関数は、リロケーションのオフセット (`sectoff`) とシンボルの `Dynid` をPEファイルに書き込みます。
*   `switch r.Type`: Goのリロケーションタイプ (`ld.R_ADDR`, `ld.R_CALL`, `ld.R_PCREL`) に応じて、対応するPEリロケーションタイプ (`IMAGE_REL_I386_DIR32`, `IMAGE_REL_I386_REL32`) を選択し、PEファイルに書き込みます。
    *   `IMAGE_REL_I386_DIR32`: 32ビット絶対アドレスのリロケーション。
    *   `IMAGE_REL_I386_REL32`: 32ビット相対アドレスのリロケーション。これは、関数呼び出し (`R_CALL`) やPC相対アドレス (`R_PCREL`) で使用されます。
この関数が追加されたことで、Goのリンカは、外部リンカが期待する正確なPEリロケーション情報を生成できるようになり、Windows/386での外部リンキングの正確性が大幅に向上しました。

### 外部リンキング時のPEファイル生成ロジックの分岐 (`src/cmd/internal/ld/pe.go`)

`pewrite` 関数内のこの変更は、Goの内部リンカを使用する場合と外部リンカを使用する場合で、PEファイルのインポートセクションの生成方法を大きく変えています。
*   `Linkmode == LinkExternal` の場合:
    *   Goは、インポートされるDLLの関数を、外部リンカが解決できるように`SHOSTOBJ`（ホストオブジェクト）タイプのシンボルとして扱います。
    *   これらのシンボルには、Windowsのリンカの慣習に合わせて、必要に応じて`@`と引数サイズが付加されたり、アンダースコアがプレフィックスされたりします。
    *   これらのシンボルは、COFFシンボルテーブルにエントリが事前に割り当てられ、外部リンカがこれらを解決できるようになります。
*   `LinkExternal` でない場合（Goの内部リンカを使用する場合）:
    *   Goは、`.windynamic` という内部セクションを作成し、インポートされるDLLの関数をこのセクション内のサブシンボルとして管理します。これは、Goの内部リンカが独自にインポート解決を行うためのメカニズムです。

この分岐により、Goのリンカは、外部リンカに処理を委ねる際に、PEフォーマットのインポート情報を外部リンカが理解できる形式で提供できるようになり、Goの内部リンカの挙動とは異なる、外部リンカに特化したPEファイル生成が可能になりました。

### `hostlink` 関数でのWindows固有リンカオプション追加 (`src/cmd/internal/ld/lib.go`)

`hostlink` 関数は、外部リンカを呼び出す際のコマンドライン引数を構築します。
*   **`-mwindows` / `-mconsole` オプション**:
    *   Windowsの実行可能ファイルは、GUIアプリケーション (`windowsgui`) とコンソールアプリケーション (`console`) の2種類があります。これらのオプションは、外部リンカに対して、生成する実行可能ファイルのタイプを明示的に指示します。これにより、Windowsがプログラムを実行する際に、適切なサブシステム（GUIまたはCUI）を割り当てることができます。
*   **`peimporteddlls()`**:
    *   この関数は、GoプログラムがインポートするDLL（例: `kernel32.dll`）のリストから、外部リンカに渡すための `-l` オプション（例: `-lkernel32`）を生成します。これにより、外部リンカは、Goプログラムが依存するDLLを正しく見つけてリンクすることができます。

これらの変更は、GoのリンカがWindowsの外部リンカと連携するために必要な、プラットフォーム固有のリンカオプションを適切に設定できるようにすることで、外部リンキングの成功率を高めています。

# [インデックス 28173] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおける共通部分式除去（Common Subexpression Elimination: CSE）の最適化に関する変更です。具体的には、メモリを生成する2つの操作（"memory-generating operations"）に対してCSEを適用しないように修正されています。これにより、コンパイラの最適化ロジックがより正確になり、不必要な処理を避けることができます。

## コミット

```
cmd/compile: never CSE two memories

It never makes sense to CSE two ops that generate memory.
We might as well start those ops off in their own partition.

Fixes #15520
```

## 変更の背景

この変更の背景には、GoコンパイラのSSAバックエンドにおけるCSEの挙動に関する問題がありました。CSEは、同じ計算を複数回行う代わりに、その計算結果を一度だけ生成して再利用することで、コードの効率を向上させる最適化手法です。しかし、メモリを生成する操作（例えば、`newobject`のようなヒープアロケーションを行う関数呼び出し）の場合、たとえ見た目が同じ操作であっても、それぞれが独立した新しいメモリ領域を指すため、それらを共通部分式として除去することは意味がありません。

元の実装では、`OpStaticCall`, `OpAMD64CALLstatic`, `OpARMCALLstatic` のような静的呼び出し操作において、`newobject` ランタイムコールを特別扱いし、CSEの対象から除外するロジックが存在しました。しかし、このアプローチは特定のランタイムコールに限定されており、より一般的な「メモリを生成する操作」全般をカバーしていませんでした。

コミットメッセージにある「It never makes sense to CSE two ops that generate memory. We might as well start those ops off in their own partition.」という記述は、メモリ生成操作は本質的に異なる結果（異なるメモリ位置）を生み出すため、それらを同一視してCSEすることは無意味であり、むしろ最適化の妨げになる可能性を示唆しています。したがって、これらの操作を最初から異なる「パーティション」（CSEの比較対象とならないグループ）に分類することで、コンパイラの効率と正確性を向上させることを目的としています。

この変更は、Issue #15520 を修正するものです。

## 前提知識の解説

### GoコンパイラとSSA (Static Single Assignment)

Goコンパイラは、ソースコードを機械語に変換する過程で、様々な最適化を行います。その中でも重要なフェーズの一つが、SSA（Static Single Assignment）形式への変換と、SSA上での最適化です。

*   **SSA形式**: プログラム中の各変数が一度だけ代入されるように変換された中間表現です。これにより、データフロー解析や最適化が容易になります。Goコンパイラでは、AST（Abstract Syntax Tree）からSSA形式に変換され、その上で多くの最適化パスが実行されます。
*   **SSAバックエンド**: GoコンパイラのSSA形式を扱う部分で、最適化と最終的な機械語生成を担当します。

### 共通部分式除去 (Common Subexpression Elimination: CSE)

CSEは、コンパイラの最適化手法の一つで、プログラム内で同じ値が計算される式が複数回出現する場合に、その計算を一度だけ行い、結果を再利用することで冗長な計算を排除します。

例:
```go
a = x + y
b = x + y
```
CSEを適用すると、`x + y` の計算は一度だけ行われ、その結果が `a` と `b` の両方に使用されます。

### メモリ操作とSSA

SSA形式では、プログラムの状態全体を表す特別な「メモリ」値（`memory` type）が存在します。これは、プログラムの実行順序や副作用を追跡するために使用されます。メモリを読み書きする操作（ロード、ストア、関数呼び出しなど）は、このメモリ値を入力として受け取り、新しいメモリ値を出力として生成します。

例えば、`*p = 10` のようなストア操作は、古いメモリ値と `p` および `10` を入力として受け取り、`p` の指すアドレスのメモリが変更された新しいメモリ値を出力します。

### `newobject` ランタイムコール

`newobject` はGoランタイム内部の関数で、新しいオブジェクトをヒープに割り当てるために使用されます。これはメモリを生成する操作の典型例であり、呼び出されるたびに新しい、独立したメモリ領域を返します。

## 技術的詳細

このコミットの技術的詳細を理解するためには、GoコンパイラのSSAバックエンドにおける値の比較とCSEのメカニズムを深く掘り下げる必要があります。

### `cmpVal` 関数と値の比較

`src/cmd/compile/internal/ssa/cse.go` にある `cmpVal` 関数は、2つのSSA値 `v` と `w` が等しいかどうかを比較し、CSEの対象となり得るかを判断する主要なロジックを含んでいます。この関数は、値のオペレーション（`v.Op`）、型（`v.Type`）、補助データ（`v.Aux`）、入力値などを再帰的に比較します。

CSEは、`v` と `w` が完全に同じ計算を表す場合にのみ適用されます。しかし、メモリを生成する操作の場合、たとえオペレーションや入力が同じに見えても、結果として得られるメモリの状態は常に異なります。例えば、2回の `newobject` 呼び出しは、それぞれ異なるヒープアドレスを返します。したがって、これらを共通部分式として除去することはできません。

### 変更前の挙動

変更前は、`cmpVal` 関数内で特定の静的呼び出し（`OpStaticCall`, `OpAMD64CALLstatic`, `OpARMCALLstatic`）に対して特別なチェックがありました。もし呼び出されるシンボルが `runtime.newobject` であれば、これらの値はCSEの対象から除外され、`v.ID < w.ID` に基づいて順序付けされていました。これは、`newobject` が常に新しいメモリを生成するという性質を考慮したものでした。

しかし、このアプローチには以下の問題がありました。
1.  **限定的な適用**: `newobject` 以外のメモリ生成操作には適用されませんでした。
2.  **特定のランタイムコールへの依存**: `runtime.newobject` という特定の関数名に依存しており、将来的に他のメモリ生成ランタイムコールが追加された場合、同様のロジックを追加する必要がありました。
3.  **SSAのメモリモデルとの整合性**: SSAのメモリモデルでは、メモリを生成する操作は常に新しいメモリ状態を生成すると考えるのが自然です。特定のランタイムコールに限定するのではなく、メモリ型を持つ値全般にこの原則を適用する方が、より堅牢で一貫性のあるアプローチです。

### 変更後の挙動

このコミットでは、`cmpVal` 関数内のロジックが簡素化され、より一般的なルールが導入されました。

```go
	if v.Type.IsMemory() {
		// We will never be able to CSE two values
		// that generate memory.
		return lt2Cmp(v.ID < w.ID)
	}
```

この変更により、`v` の型がメモリ型（`v.Type.IsMemory()` が `true` を返す）である場合、その値は無条件にCSEの対象から除外されるようになりました。具体的には、`v.ID < w.ID` に基づいて順序付けされ、`v` と `w` が等しいと判断されることはなくなります。これにより、メモリを生成するいかなる操作も、その種類に関わらずCSEの対象外となります。

この変更は、`src/cmd/compile/internal/gc/subr.go` から `IsRuntimeCall` メソッドが削除され、`src/cmd/compile/internal/ssa/config.go` から `GCSym` インターフェースが削除されたことと関連しています。これらの要素は、`newobject` の特別な扱いをサポートするために存在していましたが、新しい一般的なルールが導入されたことで不要になりました。

### 最適化への影響

この変更は、コンパイラの最適化パスにおいて、メモリ生成操作に関する不必要な比較や処理を削減します。これにより、CSEパスの効率が向上し、コンパイラの全体的なパフォーマンスにわずかながら貢献する可能性があります。また、メモリモデルに関するコンパイラの内部的な整合性が高まります。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/cmd/compile/internal/gc/subr.go`**:
    *   `(*Sym) IsRuntimeCall(name string) bool` メソッドが削除されました。このメソッドは、特定のシンボルが指定されたランタイムコールであるかをチェックするために使用されていました。

2.  **`src/cmd/compile/internal/ssa/config.go`**:
    *   `GCSym` インターフェースが削除されました。このインターフェースは、`gc.Sym` 型が `IsRuntimeCall` メソッドを実装していることをSSAバックエンドに伝えるために存在していました。

3.  **`src/cmd/compile/internal/ssa/cse.go`**:
    *   `cmpVal` 関数内のロジックが変更されました。
    *   変更前: `OpStaticCall`, `OpAMD64CALLstatic`, `OpARMCALLstatic` のケースで `runtime.newobject` を特別扱いするロジックがありました。
    *   変更後: `v.Type.IsMemory()` が `true` の場合、無条件にCSEの対象から除外するロジックが追加されました。これにより、以前の特定のランタイムコールをチェックするロジックは不要となり削除されました。

### `cmpVal` 関数と値の比較

`src/cmd/compile/internal/ssa/cse.go` にある `cmpVal` 関数は、2つのSSA値 `v` と `w` が等しいかどうかを比較し、CSEの対象となり得るかを判断する主要なロジックを含んでいます。この関数は、値のオペレーション（`v.Op`）、型（`v.Type`）、補助データ（`v.Aux`）、入力値などを再帰的に比較します。

CSEは、`v` と `w` が完全に同じ計算を表す場合にのみ適用されます。しかし、メモリを生成する操作の場合、たとえオペレーションや入力が同じに見えても、結果として得られるメモリの状態は常に異なります。例えば、2回の `newobject` 呼び出しは、それぞれ異なるヒープアドレスを返します。したがって、これらを共通部分式として除去することはできません。

### 変更前の挙動

変更前は、`cmpVal` 関数内で特定の静的呼び出し（`OpStaticCall`, `OpAMD64CALLstatic`, `OpARMCALLstatic`）に対して特別なチェックがありました。もし呼び出されるシンボルが `runtime.newobject` であれば、これらの値はCSEの対象から除外され、`v.ID < w.ID` に基づいて順序付けされていました。これは、`newobject` が常に新しいメモリを生成するという性質を考慮したものでした。

しかし、このアプローチには以下の問題がありました。
1.  **限定的な適用**: `newobject` 以外のメモリ生成操作には適用されませんでした。
2.  **特定のランタイムコールへの依存**: `runtime.newobject` という特定の関数名に依存しており、将来的に他のメモリ生成ランタイムコールが追加された場合、同様のロジックを追加する必要がありました。
3.  **SSAのメモリモデルとの整合性**: SSAのメモリモデルでは、メモリを生成する操作は常に新しいメモリ状態を生成すると考えるのが自然です。特定のランタイムコールに限定するのではなく、メモリ型を持つ値全般にこの原則を適用する方が、より堅牢で一貫性のあるアプローチです。

### 変更後の挙動

このコミットでは、`cmpVal` 関数内のロジックが簡素化され、より一般的なルールが導入されました。

```go
	if v.Type.IsMemory() {
		// We will never be able to CSE two values
		// that generate memory.
		return lt2Cmp(v.ID < w.ID)
	}
```

この変更により、`v` の型がメモリ型（`v.Type.IsMemory()` が `true` を返す）である場合、その値は無条件にCSEの対象から除外されるようになりました。具体的には、`v.ID < w.ID` に基づいて順序付けされ、`v` と `w` が等しいと判断されることはなくなります。これにより、メモリを生成するいかなる操作も、その種類に関わらずCSEの対象外となります。

この変更は、`src/cmd/compile/internal/gc/subr.go` から `IsRuntimeCall` メソッドが削除され、`src/cmd/compile/internal/ssa/config.go` から `GCSym` インターフェースが削除されたことと関連しています。これらの要素は、`newobject` の特別な扱いをサポートするために存在していましたが、新しい一般的なルールが導入されたことで不要になりました。

### 最適化への影響

この変更は、コンパイラの最適化パスにおいて、メモリ生成操作に関する不必要な比較や処理を削減します。これにより、CSEパスの効率が向上し、コンパイラの全体的なパフォーマンスにわずかながら貢献する可能性があります。また、メモリモデルに関するコンパイラの内部的な整合性が高まります。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/cmd/compile/internal/gc/subr.go`**:
    *   `(*Sym) IsRuntimeCall(name string) bool` メソッドが削除されました。このメソッドは、特定のシンボルが指定されたランタイムコールであるかをチェックするために使用されていました。

2.  **`src/cmd/compile/internal/ssa/config.go`**:
    *   `GCSym` インターフェースが削除されました。このインターフェースは、`gc.Sym` 型が `IsRuntimeCall` メソッドを実装していることをSSAバックエンドに伝えるために存在していました。

3.  **`src/cmd/compile/internal/ssa/cse.go`**:
    *   `cmpVal` 関数内のロジックが変更されました。
    *   変更前: `OpStaticCall`, `OpAMD64CALLstatic`, `OpARMCALLstatic` のケースで `runtime.newobject` を特別扱いするロジックがありました。
    *   変更後: `v.Type.IsMemory()` が `true` の場合、無条件にCSEの対象から除外するロジックが追加されました。これにより、以前の特定のランタイムコールをチェックするロジックは不要となり削除されました。

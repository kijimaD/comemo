# [インデックス 22291] ファイルの概要

## コミット

このコミットは、Goランタイムにおける`defer`（遅延実行）メカニズムで使用されるメモリプールの管理に関する改善です。特に、無制限に成長する可能性があったリストベースの`defer`プールに上限を設けることを目的としています。これにより、特定のシナリオ（ゴルーチンが`defer`を頻繁に割り当て、その後異なるP（プロセッサ）でブロック解除・スケジュールされる場合など）で発生しうるメモリ使用量の無限増大を防ぎます。

変更の核心は、中央の`defer`プールを導入し、既存のローカル（Pごとの）プールを固定サイズにすることです。ローカルプールは、中央プールへのアクセスを償却（アモルタイズ）するためのキャッシュとして機能します。また、`freedefer`関数がシステムスタック上で実行されるように変更され、`nosplit`スタック領域の消費を避けるようになっています。

## 元コミット内容

```
runtime: bound defer pools (try 2)

The unbounded list-based defer pool can grow infinitely.
This can happen if a goroutine routinely allocates a defer;
then blocks on one P; and then unblocked, scheduled and
frees the defer on another P.
The scenario was reported on golang-nuts list.

We've been here several times. Any unbounded local caches
are bad and grow to infinite size. This change introduces
central defer pool; local pools become fixed-size
with the only purpose of amortizing accesses to the
central pool.

Freedefer now executes on system stack to not consume
nosplit stack space.

## 変更の背景

この変更の背景には、Goランタイムにおける`defer`ステートメントのメモリ管理に関する既知の問題がありました。以前の設計では、`defer`構造体を再利用するためのプールがP（プロセッサ）ごとに存在し、これがリストベースで無制限に成長する可能性がありました。

具体的には、以下のようなシナリオで問題が発生していました。

1.  **無制限の成長**: あるゴルーチンが繰り返し`defer`を割り当てると、そのゴルーチンが実行されているPのローカル`defer`プールに、使用済みの`defer`構造体が蓄積されていきます。
2.  **P間の移動とメモリリーク**: そのゴルーチンが何らかの理由でブロックされ、その後別のPでスケジュールされて`defer`構造体を解放した場合、元のPのプールに蓄積された`defer`構造体は再利用されず、メモリが解放されないまま残ってしまう可能性がありました。これにより、システム全体のメモリ使用量が無限に増大するリスクがありました。
3.  **コミュニティからの報告**: この問題は、`golang-nuts`メーリングリストでも報告されており、実際の運用環境で顕在化していたことが示唆されています。

開発チームは、過去にも同様の「無制限に成長するローカルキャッシュ」の問題に直面しており、それらがシステム全体の安定性やメモリ効率に悪影響を与えることを認識していました。このコミットは、この根本的な問題を解決し、`defer`プールのメモリ使用量を予測可能で管理しやすいものにすることを目的としています。

また、`freedefer`関数が`nosplit`スタック領域を消費しないように、システムスタック上で実行されるように変更されたのは、スタックの成長に関する制約を回避し、より堅牢なランタイム動作を保証するためです。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念と一般的なプログラミングの知識が必要です。

1.  **`defer`ステートメント**:
    *   Go言語のキーワードで、関数がリターンする直前（パニックが発生した場合でも）に指定された関数呼び出しを遅延実行させるために使用されます。
    *   リソースの解放（ファイルクローズ、ロック解除など）やエラーハンドリングによく利用されます。
    *   `defer`が実行されると、その呼び出しに関する情報（関数ポインタ、引数など）が`_defer`構造体に格納され、現在のゴルーチンのスタックにリンクされたリストとして追加されます。

2.  **ゴルーチン (Goroutine)**:
    *   Goランタイムによって管理される軽量なスレッドです。数千、数万のゴルーチンを同時に実行することが可能です。
    *   各ゴルーチンは独自のスタックを持ちます。

3.  **P (Processor)**:
    *   Goスケジューラにおける論理プロセッサ（またはコンテキスト）。GoのM:Nスケジューリングモデルの一部です。
    *   M（OSスレッド）がG（ゴルーチン）を実行するために必要なリソース（ローカルキュー、キャッシュなど）を提供します。
    *   各Pは、実行可能なゴルーチンのローカルキューや、特定のオブジェクト（この場合は`_defer`構造体）のキャッシュプールなど、Mがゴルーチンを実行するために必要なコンテキストを保持します。
    *   ゴルーチンは、あるPで実行を開始し、ブロックされた後に別のPで再開されることがあります。

4.  **メモリプール/キャッシュ**:
    *   頻繁に割り当てと解放が行われるオブジェクトのために、あらかじめメモリを確保しておき、再利用することで、メモリ割り当て/解放のオーバーヘッドを削減する手法です。
    *   ローカルキャッシュ（Pごとのキャッシュ）は、特定のPが頻繁にアクセスするオブジェクトを高速に提供するために使用されます。
    *   中央プールは、複数のP間で共有される大規模なキャッシュです。

5.  **スタックと`nosplit`**:
    *   **スタック**: 関数呼び出しの際に、ローカル変数、引数、リターンアドレスなどが格納されるメモリ領域です。Goのゴルーチンスタックは、必要に応じて動的にサイズが変更されます（スタックの伸縮）。
    *   **システムスタック**: Goランタイム内部の低レベルな処理（スケジューラ、GCなど）が実行される際に使用される特別なスタックです。通常のゴルーチンスタックとは異なります。
    *   **`nosplit`**: Goコンパイラに対する指示で、特定の関数がスタックを分割（拡張）しないことを保証します。これは、スタックの拡張処理自体がスタックを必要とするため、デッドロックや無限ループを防ぐために、非常に低レベルなランタイム関数で使用されます。`nosplit`関数は、スタックのサイズが固定されているか、非常に小さいことを前提とします。`nosplit`関数内で大きなスタック領域を消費すると、スタックオーバーフローを引き起こす可能性があります。

これらの概念を理解することで、コミットが解決しようとしている問題と、その解決策の技術的な詳細がより明確になります。特に、Pごとのローカルキャッシュが無制限に成長する問題は、Goのスケジューリングモデルとメモリ管理の相互作用によって引き起こされる複雑な問題です。

## 技術的詳細

このコミットは、Goランタイムの`defer`プール管理を根本的に変更し、メモリ使用量の予測可能性と効率性を向上させています。主要な変更点は以下の通りです。

1.  **中央`defer`プールの導入**:
    *   これまでのPごとのローカル`defer`プールに加えて、`schedt`構造体（スケジューラのグローバル状態を保持）内に`deferlock`ミューテックスと`deferpool`配列が追加されました。
    *   この`sched.deferpool`が、異なるサイズの`_defer`構造体を格納する中央プールとして機能します。
    *   `clearpools`関数（GCサイクルなどで呼び出される）は、Pごとのローカルプールではなく、この中央`defer`プールをクリアするように変更されました。これにより、P間で移動した`defer`構造体が適切に解放されるようになります。

2.  **ローカル`defer`プールの固定サイズ化と役割の変更**:
    *   `p`構造体（Pごとの状態を保持）の`deferpool`フィールドが、これまでの`[5]*_defer`（リストのヘッドを保持）から`[5][]*_defer`（スライスベースの固定サイズ配列）に変更されました。
    *   さらに、`[5][32]*_defer`という`deferpoolbuf`が追加され、各ローカルプールが最大32個の`_defer`構造体を保持できるようになりました。これにより、ローカルプールは厳密にサイズが制限されたキャッシュとして機能します。
    *   ローカルプールの目的は、中央プールへの頻繁なアクセスを償却することに限定されます。つまり、Pはまず自身のローカルプールから`_defer`構造体を取得しようとし、なければ中央プールから補充します。

3.  **`newdefer`関数の変更**:
    *   `newdefer`は新しい`_defer`構造体を割り当てる関数です。
    *   変更後、`newdefer`はまず現在のPのローカル`deferpool`から利用可能な`_defer`構造体を探します。
    *   もしローカルプールが空で、かつ中央プールに利用可能な`_defer`構造体がある場合、中央プールからローカルプールに`_defer`構造体を補充します。この補充は、ローカルプールの容量の半分まで行われます。この操作は`sched.deferlock`ミューテックスによって保護されます。
    *   ローカルプールからも中央プールからも取得できない場合は、新しい`_defer`構造体がヒープに割り当てられます。

4.  **`freedefer`関数の変更**:
    *   `freedefer`は使用済みの`_defer`構造体をプールに戻す関数です。
    *   変更後、`freedefer`はまず現在のPのローカル`deferpool`に`_defer`構造体を戻そうとします。
    *   もしローカルプールがその容量（32個）に達した場合、ローカルプールの半分（16個）の`_defer`構造体を中央`defer`プールに転送します。この転送も`sched.deferlock`ミューテックスによって保護されます。
    *   これにより、ローカルプールが過度に成長することなく、使用済みの`_defer`構造体が中央プールを通じて他のPでも再利用される機会が生まれます。

5.  **`freedefer`のシステムスタック上での実行**:
    *   `deferreturn`関数内で`freedefer(d)`が呼び出される際、`systemstack(func() { freedefer(d) })`というラッパーが追加されました。
    *   これは、`freedefer`が`nosplit`関数ではないため、通常のゴルーチンスタック上で実行されると、スタックの伸縮処理（`morestack`など）が発生し、それが`defer`の解放処理中に問題を引き起こす可能性があったためです。
    *   `systemstack`上で実行することで、`freedefer`はランタイムの固定されたシステムスタック上で動作し、スタックの伸縮による潜在的な問題を回避し、`nosplit`スタック領域の消費を防ぎます。

これらの変更により、`defer`構造体の割り当てと解放がより効率的かつ安全になり、特にメモリ使用量の観点からランタイムの堅牢性が向上しました。Pごとのローカルキャッシュは高速アクセスを提供しつつ、中央プールが全体的なメモリ再利用を管理するというハイブリッドなアプローチが採用されています。

## コアとなるコードの解説

### `src/runtime/runtime2.go`

*   **`p` 構造体の変更**:
    *   `deferpool [5]*_defer` が `deferpool [5][]*_defer` に変更されました。これは、Pごとの`defer`プールが、これまでの単なるリストのヘッドを指すポインタの配列から、`_defer`構造体のスライス（動的配列）の配列になったことを意味します。
    *   `deferpoolbuf [5][32]*_defer` が追加されました。これは、各`deferpool`スライスの基盤となる固定サイズのバッファで、各サイズカテゴリの`defer`プールが最大32個の`_defer`構造体を保持できることを示しています。これにより、Pごとのローカルプールが厳密にサイズ制限されるようになりました。

*   **`schedt` 構造体の追加**:
    *   `deferlock mutex` と `deferpool [5]*_defer` が追加されました。これらは、Goランタイム全体で共有される中央`defer`プールとその保護のためのミューテックスです。`deferpool`は、異なるサイズの`_defer`構造体を格納するリストのヘッドの配列です。

### `src/runtime/panic.go`

*   **`newdefer` 関数**:
    *   新しい`_defer`構造体を割り当てる際に、まずPのローカル`deferpool`から取得を試みます。
    *   `if len(pp.deferpool[sc]) == 0 && sched.deferpool[sc] != nil` の条件は、ローカルプールが空で、かつ中央プールに利用可能な`defer`構造体がある場合に、中央プールからローカルプールへ`defer`構造体を補充するロジックです。
    *   `lock(&sched.deferlock)` と `unlock(&sched.deferlock)` で中央プールへのアクセスを保護しています。
    *   `for len(pp.deferpool[sc]) < cap(pp.deferpool[sc])/2 && sched.deferpool[sc] != nil` ループにより、中央プールからローカルプールの容量の半分まで`defer`構造体を補充します。これにより、ローカルプールが完全に空になるのを防ぎ、中央プールへの頻繁なロックを回避します。
    *   `d = pp.deferpool[sc][ln-1]` と `pp.deferpool[sc] = pp.deferpool[sc][:ln-1]` は、スライスから末尾の要素を取得し、スライスを短縮する一般的なGoのイディオムです。

*   **`freedefer` 関数**:

## 変更の背景

この変更の背景には、Goランタイムにおける`defer`ステートメントのメモリ管理に関する既知の問題がありました。以前の設計では、`defer`構造体を再利用するためのプールがP（プロセッサ）ごとに存在し、これがリストベースで無制限に成長する可能性がありました。

具体的には、以下のようなシナリオで問題が発生していました。

1.  **無制限の成長**: あるゴルーチンが繰り返し`defer`を割り当てると、そのゴルーチンが実行されているPのローカル`defer`プールに、使用済みの`defer`構造体が蓄積されていきます。
2.  **P間の移動とメモリリーク**: そのゴルーチンが何らかの理由でブロックされ、その後別のPでスケジュールされて`defer`構造体を解放した場合、元のPのプールに蓄積された`defer`構造体は再利用されず、メモリが解放されないまま残ってしまう可能性がありました。これにより、システム全体のメモリ使用量が無限に増大するリスクがありました。
3.  **コミュニティからの報告**: この問題は、`golang-nuts`メーリングリストでも報告されており、実際の運用環境で顕在化していたことが示唆されています。

開発チームは、過去にも同様の「無制限に成長するローカルキャッシュ」の問題に直面しており、それらがシステム全体の安定性やメモリ効率に悪影響を与えることを認識していました。このコミットは、この根本的な問題を解決し、`defer`プールのメモリ使用量を予測可能で管理しやすいものにすることを目的としています。

また、`freedefer`関数が`nosplit`スタック領域を消費しないように、システムスタック上で実行されるように変更されたのは、スタックの成長に関する制約を回避し、より堅牢なランタイム動作を保証するためです。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念と一般的なプログラミングの知識が必要です。

1.  **`defer`ステートメント**:
    *   Go言語のキーワードで、関数がリターンする直前（パニックが発生した場合でも）に指定された関数呼び出しを遅延実行させるために使用されます。
    *   リソースの解放（ファイルクローズ、ロック解除など）やエラーハンドリングによく利用されます。
    *   `defer`が実行されると、その呼び出しに関する情報（関数ポインタ、引数など）が`_defer`構造体に格納され、現在のゴルーチンのスタックにリンクされたリストとして追加されます。

2.  **ゴルーチン (Goroutine)**:
    *   Goランタイムによって管理される軽量なスレッドです。数千、数万のゴルーチンを同時に実行することが可能です。
    *   各ゴルーチンは独自のスタックを持ちます。

3.  **P (Processor)**:
    *   Goスケジューラにおける論理プロセッサ（またはコンテキスト）。GoのM:Nスケジューリングモデルの一部です。
    *   M（OSスレッド）がG（ゴルーチン）を実行するために必要なリソース（ローカルキュー、キャッシュなど）を提供します。
    *   各Pは、実行可能なゴルーチンのローカルキューや、特定のオブジェクト（この場合は`_defer`構造体）のキャッシュプールなど、Mがゴルーチンを実行するために必要なコンテキストを保持します。
    *   ゴルーチンは、あるPで実行を開始し、ブロックされた後に別のPで再開されることがあります。

4.  **メモリプール/キャッシュ**:
    *   頻繁に割り当てと解放が行われるオブジェクトのために、あらかじめメモリを確保しておき、再利用することで、メモリ割り当て/解放のオーバーヘッドを削減する手法です。
    *   ローカルキャッシュ（Pごとのキャッシュ）は、特定のPが頻繁にアクセスするオブジェクトを高速に提供するために使用されます。
    *   中央プールは、複数のP間で共有される大規模なキャッシュです。

5.  **スタックと`nosplit`**:
    *   **スタック**: 関数呼び出しの際に、ローカル変数、引数、リターンアドレスなどが格納されるメモリ領域です。Goのゴルーチンスタックは、必要に応じて動的にサイズが変更されます（スタックの伸縮）。
    *   **システムスタック**: Goランタイム内部の低レベルな処理（スケジューラ、GCなど）が実行される際に使用される特別なスタックです。通常のゴルーチンスタックとは異なります。
    *   **`nosplit`**: Goコンパイラに対する指示で、特定の関数がスタックを分割（拡張）しないことを保証します。これは、スタックの拡張処理自体がスタックを必要とするため、デッドロックや無限ループを防ぐために、非常に低レベルなランタイム関数で使用されます。`nosplit`関数は、スタックのサイズが固定されているか、非常に小さいことを前提とします。`nosplit`関数内で大きなスタック領域を消費すると、スタックオーバーフローを引き起こす可能性があります。

これらの概念を理解することで、コミットが解決しようとしている問題と、その解決策の技術的な詳細がより明確になります。特に、Pごとのローカルキャッシュが無制限に成長する問題は、Goのスケジューリングモデルとメモリ管理の相互作用によって引き起こされる複雑な問題です。

## 技術的詳細

このコミットは、Goランタイムの`defer`プール管理を根本的に変更し、メモリ使用量の予測可能性と効率性を向上させています。主要な変更点は以下の通りです。

1.  **中央`defer`プールの導入**:
    *   これまでのPごとのローカル`defer`プールに加えて、`schedt`構造体（スケジューラのグローバル状態を保持）内に`deferlock`ミューテックスと`deferpool`配列が追加されました。
    *   この`sched.deferpool`が、異なるサイズの`_defer`構造体を格納する中央プールとして機能します。
    *   `clearpools`関数（GCサイクルなどで呼び出される）は、Pごとのローカルプールではなく、この中央`defer`プールをクリアするように変更されました。これにより、P間で移動した`defer`構造体が適切に解放されるようになります。

2.  **ローカル`defer`プールの固定サイズ化と役割の変更**:
    *   `p`構造体（Pごとの状態を保持）の`deferpool`フィールドが、これまでの`[5]*_defer`（リストのヘッドを保持）から`[5][]*_defer`（スライスベースの固定サイズ配列）に変更されました。
    *   さらに、`[5][32]*_defer`という`deferpoolbuf`が追加され、各ローカルプールが最大32個の`_defer`構造体を保持できるようになりました。これにより、ローカルプールは厳密にサイズが制限されたキャッシュとして機能します。
    *   ローカルプールの目的は、中央プールへの頻繁なアクセスを償却することに限定されます。つまり、Pはまず自身のローカルプールから`_defer`構造体を取得しようとし、なければ中央プールから補充します。

3.  **`newdefer`関数の変更**:
    *   `newdefer`は新しい`_defer`構造体を割り当てる関数です。
    *   変更後、`newdefer`はまず現在のPのローカル`deferpool`から利用可能な`_defer`構造体を探します。
    *   もしローカルプールが空で、かつ中央プールに利用可能な`_defer`構造体がある場合、中央プールからローカルプールに`_defer`構造体を補充します。この補充は、ローカルプールの容量の半分まで行われます。この操作は`sched.deferlock`ミューテックスによって保護されます。
    *   ローカルプールからも中央プールからも取得できない場合は、新しい`_defer`構造体がヒープに割り当てられます。

4.  **`freedefer`関数の変更**:
    *   `freedefer`は使用済みの`_defer`構造体をプールに戻す関数です。
    *   変更後、`freedefer`はまず現在のPのローカル`deferpool`に`_defer`構造体を戻そうとします。
    *   もしローカルプールがその容量（32個）に達した場合、ローカルプールの半分（16個）の`_defer`構造体を中央`defer`プールに転送します。この転送も`sched.deferlock`ミューテックスによって保護されます。
    *   これにより、ローカルプールが過度に成長することなく、使用済みの`_defer`構造体が中央プールを通じて他のPでも再利用される機会が生まれます。

5.  **`freedefer`のシステムスタック上での実行**:
    *   `deferreturn`関数内で`freedefer(d)`が呼び出される際、`systemstack(func() { freedefer(d) })`というラッパーが追加されました。
    *   これは、`freedefer`が`nosplit`関数ではないため、通常のゴルーチンスタック上で実行されると、スタックの伸縮処理（`morestack`など）が発生し、それが`defer`の解放処理中に問題を引き起こす可能性があったためです。
    *   `systemstack`上で実行することで、`freedefer`はランタイムの固定されたシステムスタック上で動作し、スタックの伸縮による潜在的な問題を回避し、`nosplit`スタック領域の消費を防ぎます。

これらの変更により、`defer`構造体の割り当てと解放がより効率的かつ安全になり、特にメモリ使用量の観点からランタイムの堅牢性が向上しました。Pごとのローカルキャッシュは高速アクセスを提供しつつ、中央プールが全体的なメモリ再利用を管理するというハイブリッドなアプローチが採用されています。

## コアとなるコードの解説

### `src/runtime/runtime2.go`

*   **`p` 構造体の変更**:
    *   `deferpool [5]*_defer` が `deferpool [5][]*_defer` に変更されました。これは、Pごとの`defer`プールが、これまでの単なるリストのヘッドを指すポインタの配列から、`_defer`構造体のスライス（動的配列）の配列になったことを意味します。
    *   `deferpoolbuf [5][32]*_defer` が追加されました。これは、各`deferpool`スライスの基盤となる固定サイズのバッファで、各サイズカテゴリの`defer`プールが最大32個の`_defer`構造体を保持できることを示しています。これにより、Pごとのローカルプールが厳密にサイズ制限されるようになりました。

*   **`schedt` 構造体の追加**:
    *   `deferlock mutex` と `deferpool [5]*_defer` が追加されました。これらは、Goランタイム全体で共有される中央`defer`プールとその保護のためのミューテックスです。`deferpool`は、異なるサイズの`_defer`構造体を格納するリストのヘッドの配列です。

### `src/runtime/panic.go`

*   **`newdefer` 関数**:
    *   新しい`_defer`構造体を割り当てる際に、まずPのローカル`deferpool`から取得を試みます。
    *   `if len(pp.deferpool[sc]) == 0 && sched.deferpool[sc] != nil` の条件は、ローカルプールが空で、かつ中央プールに利用可能な`defer`構造体がある場合に、中央プールからローカルプールへ`defer`構造体を補充するロジックです。
    *   `lock(&sched.deferlock)` と `unlock(&sched.deferlock)` で中央プールへのアクセスを保護しています。
    *   `for len(pp.deferpool[sc]) < cap(pp.deferpool[sc])/2 && sched.deferpool[sc] != nil` ループにより、中央プールからローカルプールの容量の半分まで`defer`構造体を補充します。これにより、ローカルプールが完全に空になるのを防ぎ、中央プールへの頻繁なロックを回避します。
    *   `d = pp.deferpool[sc][ln-1]` と `pp.deferpool[sc] = pp.deferpool[sc][:ln-1]` は、スライスから末尾の要素を取得し、スライスを短縮する一般的なGoのイディオムです。

*   **`freedefer` 関数**:
    *   使用済みの`_defer`構造体をプールに戻す際に、まずPのローカル`deferpool`に戻します。
    *   `if len(pp.deferpool[sc]) == cap(pp.deferpool[sc])` の条件は、ローカルプールが満杯になった場合に、その半分を中央プールに転送するロジックです。
    *   `for len(pp.deferpool[sc]) > cap(pp.deferpool[sc])/2` ループにより、ローカルプールの半分を中央プールに転送します。これにより、ローカルプールが過度に大きくなるのを防ぎ、中央プールを通じて`_defer`構造体が再利用される機会を増やします。
    *   ここでも `lock(&sched.deferlock)` と `unlock(&sched.deferlock)` で中央プールへのアクセスを保護しています。
    *   `last.link = sched.deferpool[sc]` と `sched.deferpool[sc] = first` は、転送される`_defer`構造体のリストを中央プールのリストの先頭に連結する処理です。
    *   `//go:nosplit` コメントが削除されました。これは、`freedefer`がもはや`nosplit`関数ではないことを示唆しています。

*   **`deferreturn` 関数**:
    *   `freedefer(d)` の呼び出しが `systemstack(func() { freedefer(d) })` でラップされました。
    *   これは、`freedefer`が通常のゴルーチンスタックではなく、ランタイムのシステムスタック上で実行されるようにするためです。これにより、`freedefer`がスタックを拡張する必要がなくなり、`nosplit`スタック領域の消費を回避できます。

### `src/runtime/mgc.go`

*   **`clearpools` 関数**:
    *   Pごとの`deferpool`をクリアする古いロジックが削除されました。
    *   代わりに、新しく追加された中央`deferpool`をクリアするロジックが追加されました。これは、GCサイクルなどでメモリプールをリセットする際に、中央プールに蓄積された`_defer`構造体も適切に解放されるようにするためです。
    *   `lock(&sched.deferlock)` と `unlock(&sched.deferlock)` で中央プールへのアクセスを保護しています。

### `src/runtime/proc1.go`

*   **`procresize` 関数**:
    *   Pの初期化およびサイズ変更時に、Pの`deferpool`スライスが`deferpoolbuf`の先頭を指すように初期化されるロジックが追加されました。これにより、Pごとのローカルプールが正しく固定サイズのバッファを使用するようになります。

これらの変更は、Goランタイムのメモリ管理、特に`defer`構造体のライフサイクルと再利用のメカニズムを大幅に改善し、特定の条件下でのメモリリークや無限のメモリ成長の問題を解決しています。

# [インデックス 16486] ファイルの概要

このコミットは、GoプロジェクトのコードレビューツールにおけるMercurialのコミット処理に関する警告ロジックの変更を扱っています。具体的には、Mercurial Queues (MQ) 拡張機能とMercurial 2.1で導入された「Phases」機能、特に「secret」フェーズを併用する際に発生していた問題を解決し、開発者がより柔軟にコミットを管理できるようにすることを目的としています。

## コミット

このコミットは、Goプロジェクトのコードレビュープラグインが、`submit`コマンドを使用しない場合に新しいコミットの追加を無効にするという通常の動作を変更します。これにより、Mercurial Queues拡張機能とMercurial 2.1以降で利用可能な「secret」フェーズの概念を併用できるようになります。`mq.secret`オプションが`hgrc(5)`で設定されている場合、コードレビューツールは「secret」としてマークされたコミットに対して警告を発しなくなります。

## 変更の背景

Goプロジェクトでは、コードレビュープロセスを効率化するためにカスタムのコードレビューツール（Mercurialの拡張機能として実装されている）が使用されていました。このツールは、開発者が`hg commit`コマンドを直接使用して新しいコミットを追加するのではなく、`mail`、`upload`、または`submit`といった専用のコマンドを使用することを強制していました。これは、コミットがレビュープロセスを経ずに直接リポジトリにプッシュされるのを防ぐためのセキュリティおよび品質管理の仕組みでした。

しかし、この厳格なルールは、Mercurial Queues (MQ) 拡張機能を使用する開発者にとって問題を引き起こしました。MQは、コミットを一時的に変更したり、パッチとして管理したりするための強力なツールですが、そのワークフローではしばしば`hg commit`コマンドが内部的に使用されます。コードレビューツールが`hg commit`をブロックすると、MQの機能が制限され、開発者の生産性が低下する可能性がありました。

Mercurial 2.1で導入された「Phases」機能は、この問題に対する解決策を提供しました。特に「secret」フェーズは、コミットがローカルリポジトリにのみ存在し、上流のリポジトリにはプッシュされないことを保証します。これにより、開発者はMQを使用してローカルでコミットを自由に操作しつつ、誤って未レビューのコミットをプッシュしてしまうリスクを回避できるようになりました。

このコミットの目的は、コードレビューツールが「secret」フェーズのコミットを認識し、それらに対して不必要な警告を発しないようにすることで、MQとコードレビューツールの両方をシームレスに共存させることでした。

## 前提知識の解説

### Mercurial (Hg)

Mercurialは、分散型バージョン管理システム（DVCS）の一つです。Gitと同様に、各開発者がコードベースの完全な履歴を持つローカルリポジトリを保持し、変更を共有リポジトリと同期します。MercurialはPythonで書かれており、シンプルさと堅牢性で知られています。

### Mercurial Queues (MQ)

Mercurial Queues (MQ) は、Mercurialの強力な拡張機能であり、一連のパッチ（変更セット）を管理するために使用されます。MQを使用すると、開発者はコミットを一時的に適用したり、変更したり、並べ替えたり、削除したりすることができます。これは、複数の変更を同時に作業している場合や、コミットをレビューのために準備している場合に特に便利です。MQは、パッチをローカルリポジトリに適用し、それらを通常のコミットとして扱うことで機能します。

### Mercurial Phases

Mercurial 2.1で導入された「Phases」（フェーズ）は、コミットの「状態」を示すメタデータです。コミットは、そのライフサイクルに応じて異なるフェーズに属します。主なフェーズは以下の通りです。

*   **`draft` (ドラフト)**: ローカルで作成された新しいコミット。まだ公開されておらず、変更される可能性があります。
*   **`public` (公開)**: 他のリポジトリにプッシュされたコミット。通常、変更されるべきではありません。
*   **`secret` (秘密)**: ローカルにのみ存在し、決してプッシュされないことが保証されているコミット。MQで管理されるパッチや、一時的な作業コミットによく使用されます。

「secret」フェーズのコミットは、Mercurialが自動的にプッシュ対象から除外するため、開発者は安心してローカルで作業を進めることができます。

### `hgrc(5)` と `mq.secret` オプション

`hgrc`はMercurialの設定ファイルです。システム全体、ユーザーごと、またはリポジトリごとに設定をカスタマイズできます。`hgrc(5)`は、この設定ファイルのマニュアルページを指します。

`mq.secret`オプションは、Mercurial Queuesに関連する設定で、MQで作成されたパッチがデフォルトで「secret」フェーズとして扱われるかどうかを制御します。このオプションが有効になっている場合、MQによって適用されたコミットは自動的に「secret」フェーズになり、誤ってプッシュされることを防ぎます。

## 技術的詳細

このコミットの技術的な核心は、Goプロジェクトのコードレビューツール（`lib/codereview/codereview.py`）が、Mercurialのバージョンとコミットのフェーズをチェックするように変更された点にあります。

変更前は、`precommithook`というMercurialのフックが、`commit_okay`というフラグが`True`でない限り、常にコミットをブロックし、専用のコードレビューコマンドを使用するよう警告していました。この`commit_okay`フラグは、`mail`、`upload`、`submit`などのコマンドが実行された場合にのみ`True`に設定されます。

変更後、`precommithook`の冒頭に以下のロジックが追加されました。

1.  **Mercurialバージョンのチェック**: `hgversion >= "2.1"`という条件で、Mercurialのバージョンが2.1以上であるかを確認します。これは、「Phases」機能がMercurial 2.1で導入されたためです。
2.  **`mercurial.phases`モジュールのインポート**: Mercurial 2.1以上の場合にのみ、`mercurial.phases`モジュールをインポートします。これにより、古いMercurialバージョンでの互換性問題が回避されます。
3.  **`mq.secret`設定とコミットフェーズのチェック**:
    *   `repo.ui.config('phases', 'new-commit')`は、新しいコミットのデフォルトフェーズに関する設定を取得します。
    *   この設定が`phases.secret`（Mercurialの「secret」フェーズを表す定数）以上であるかをチェックします。これは、`hgrc`ファイルで`mq.secret`オプションが設定されている場合に該当します。
    *   もしこの条件が真であれば、つまり、新しいコミットが「secret」フェーズとして扱われるべきであると設定されている場合、`return False`を実行します。Mercurialのフックにおいて`False`を返すことは、フックが成功し、コミット処理を続行しても良いことを意味します。

この変更により、Mercurial 2.1以降を使用し、かつ`mq.secret`オプションを有効にしている開発者は、MQを使用して作成された「secret」コミットに対して、コードレビューツールからの警告を受けることなく、自由に作業を進めることができるようになりました。これにより、開発ワークフローの柔軟性が向上し、MQの利点を最大限に活用できるようになります。

また、このコミットでは、コードレビューツールが推奨するMercurialのバージョンも「2.0」から「2.1」に更新されています。これは、新しい「Phases」機能を利用するために必要な変更です。

## コアとなるコードの解説

変更は主に2つの部分に分かれます。

1.  **推奨Mercurialバージョンの更新**:
    ```diff
    -# We require Mercurial 1.9 and suggest Mercurial 2.0.
    +# We require Mercurial 1.9 and suggest Mercurial 2.1.
     # ...
     hg_required = "1.9"
    -hg_suggested = "2.0"
    +hg_suggested = "2.1"
    ```
    これは、コードレビューツールがMercurial 2.1で導入された新機能（Phases）を利用するため、開発者に対してMercurial 2.1の使用を推奨するようにメッセージを更新したものです。

2.  **`precommithook` の変更**:
    ```python
    def precommithook(ui, repo, **opts):
        if hgversion >= "2.1":
            from mercurial import phases
            if repo.ui.config('phases', 'new-commit') >= phases.secret:
                return False
        if commit_okay:
            return False  # False means okay.
        ui.write("\ncodereview extension enabled; use mail, upload, or submit instead of commit\n\n")
    ```
    *   `precommithook` は、Mercurialでコミットが作成される直前に実行されるフック関数です。
    *   `if hgversion >= "2.1":`：Mercurialのバージョンが2.1以上であるかを確認します。これは、`phases`モジュールがこのバージョンで導入されたためです。
    *   `from mercurial import phases`：Mercurialの`phases`モジュールをインポートします。これにより、`phases.secret`などの定数にアクセスできるようになります。
    *   `if repo.ui.config('phases', 'new-commit') >= phases.secret:`：
        *   `repo.ui.config('phases', 'new-commit')` は、Mercurialの設定ファイル（`hgrc`）から、新しいコミットのデフォルトのフェーズに関する設定を読み取ります。具体的には、`[phases]`セクションの`new-commit`オプションの値を取得します。
        *   この値が `phases.secret` 以上であるかをチェックします。これは、`mq.secret = True` のように設定されている場合に、MQで作成されたコミットが自動的に `secret` フェーズとして扱われることを意味します。
        *   もしこの条件が真であれば、つまり、新しいコミットが「secret」フェーズとして扱われるべきであると設定されている場合、`return False` を実行します。Mercurialのフックにおいて `False` を返すことは、フックが成功し、コミット処理を続行しても良いことを意味します。これにより、コードレビューツールは「secret」コミットに対して警告を発しなくなります。
    *   `if commit_okay:`：これは既存のロジックで、`mail`、`upload`、`submit`などの専用コマンドが使用された場合にコミットを許可します。
    *   `ui.write(...)`：上記の条件のいずれも満たされない場合（つまり、`submit`コマンドが使われず、かつコミットが`secret`フェーズでもない場合）、コードレビューツールは警告メッセージを出力し、コミットをブロックします。

この変更により、Mercurial QueuesとMercurial Phasesの「secret」機能がGoのコードレビューワークフローに統合され、開発者はより柔軟なコミット管理が可能になりました。

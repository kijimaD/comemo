# [インデックス 26548] ファイルの概要

このコミットは、Goコンパイラのx86アーキテクチャ向けバックエンドにおける、動的リンク時の命令生成に関するバグ修正です。具体的には、`LEAQ symbol+offset(SB), Reg`のような命令が動的リンク時に`MOVQ symbol@GOT(SB), Reg; ADDQ $offset, Reg`と誤って変換され、`ADDQ`命令がCPUのフラグレジスタを破壊してしまう問題を解決します。修正後は、`ADDQ`の代わりに`LEAQ offset(Reg), Reg`を使用することで、フラグの破壊を防ぎ、元の`LEAQ`命令のセマンティクスを維持します。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する際に、様々な最適化とアーキテクチャ固有の命令生成を行います。特に、Go 1.7で導入されたSSA (Static Single Assignment) バックエンドは、より効率的なコード生成を目指していました。このコミットは、そのSSAバックエンドの一部であるx86アセンブラのコード生成ロジックに関するものです。

問題は、`LEAQ symbol+offset(SB), Reg`のような命令が動的リンクを考慮して再書き込みされる際に発生しました。`LEAQ` (Load Effective Address) 命令は、オペランドのアドレスを計算してレジスタに格納しますが、CPUのフラグレジスタ（ゼロフラグ、キャリーフラグなど）を変更しないという特性があります。これは、アドレス計算と同時にフラグの状態を維持したい場合に重要です。

しかし、動的リンクが有効な場合、`symbol(SB)`のようなグローバルシンボルへの参照は、GOT (Global Offset Table) を介して解決される必要があります。そのため、コンパイラは`LEAQ symbol+offset(SB), Reg`を、まず`symbol`のアドレスをGOTからレジスタにロードし（`MOVQ symbol@GOT(SB), Reg`）、その後オフセットを加算する（`ADDQ $offset, Reg`）という2つの命令に変換していました。

ここで問題となるのが`ADDQ`命令です。`ADDQ`は加算結果に基づいてフラグレジスタを更新します。これは、元の`LEAQ`命令がフラグを破壊しないという特性と矛盾します。もし、`LEAQ`命令の直後にフラグの状態に依存する命令（例: 条件分岐）が続く場合、`ADDQ`によるフラグの破壊はプログラムの誤動作を引き起こす可能性がありました。

このコミットは、このフラグ破壊の問題を解決し、動的リンク時でも元の`LEAQ`命令のセマンティクス（フラグを破壊しない）を維持することを目的としています。

## 前提知識の解説

### 1. x86アセンブリ命令

*   **LEAQ (Load Effective Address)**:
    *   オペランドのアドレスを計算し、その結果をデスティネーションレジスタに格納する命令です。
    *   例: `LEAQ symbol+100(SB), AX` は、`symbol`のアドレスに100を加算した結果を`AX`レジスタに格納します。
    *   重要な特性として、**CPUのフラグレジスタ（ZF, CF, SF, OFなど）を一切変更しません**。これは、アドレス計算と同時にフラグの状態を維持したい場合に非常に有用です。
*   **ADDQ (Add Quadword)**:
    *   2つのオペランドを加算し、結果をデスティネーションに格納する命令です。
    *   例: `ADDQ $100, AX` は、`AX`レジスタの値に100を加算し、結果を`AX`に格納します。
    *   加算結果に基づいて**CPUのフラグレジスタを更新します**。例えば、結果がゼロになればゼロフラグ(ZF)がセットされ、オーバーフローが発生すればオーバーフローフラグ(OF)がセットされます。
*   **MOVQ (Move Quadword)**:
    *   ソースオペランドの値をデスティネーションオペランドに移動する命令です。
    *   例: `MOVQ symbol@GOT(SB), AX` は、`symbol`のアドレスをGOTから取得し、`AX`レジスタに格納します。
    *   通常、**CPUのフラグレジスタを変更しません**。

### 2. CPUフラグレジスタ

x86アーキテクチャのCPUには、演算結果の状態を示すためのフラグレジスタ（EFLAGS/RFLAGS）があります。主要なフラグには以下のようなものがあります。

*   **ZF (Zero Flag)**: 演算結果がゼロの場合にセットされます。
*   **CF (Carry Flag)**: 符号なし演算でキャリー（桁上がり）またはボロー（桁借り）が発生した場合にセットされます。
*   **SF (Sign Flag)**: 演算結果の最上位ビット（符号ビット）が1の場合にセットされます（結果が負の場合）。
*   **OF (Overflow Flag)**: 符号付き演算でオーバーフローが発生した場合にセットされます。

これらのフラグは、条件分岐命令（例: `JZ` (Jump if Zero), `JC` (Jump if Carry)）や、特定の演算（例: `ADC` (Add with Carry)）で使用され、プログラムの制御フローや多倍長演算に不可欠です。

### 3. 動的リンクとGOT (Global Offset Table)

*   **動的リンク**: プログラムの実行時に、必要なライブラリ（共有ライブラリ、DLLなど）をロードし、その中の関数やデータへの参照を解決する仕組みです。これにより、実行ファイルのサイズを小さくし、ライブラリの更新を容易にします。
*   **GOT (Global Offset Table)**: 動的リンクされたプログラムが、外部の共有ライブラリ内のグローバル変数や関数にアクセスするために使用するテーブルです。プログラムが外部シンボルを参照する際、直接そのアドレスにジャンプするのではなく、GOT内のエントリを介して間接的にアクセスします。リンカは、実行時にGOTのエントリを実際のメモリアドレスで埋めます。
*   **`symbol@GOT(SB)`**: Goのアセンブリ構文で、`symbol`のアドレスをGOTから取得することを示します。`SB` (Static Base) は、静的データセグメントのベースアドレスを示す擬似レジスタです。

### 4. GoコンパイラのSSAバックエンド

Go 1.7以降、コンパイラのコード生成バックエンドはSSA (Static Single Assignment) 形式をベースにしています。SSAは、各変数が一度だけ代入されるようにプログラムを表現する中間表現で、データフロー解析や最適化を容易にします。このSSAバックエンドは、プラットフォーム固有の命令に変換する際に、動的リンクなどの実行環境の特性を考慮した命令選択と再書き込みを行います。

## 技術的詳細

Goコンパイラのx86バックエンドでは、`obj6.go`ファイルがアセンブリ命令の再書き込みロジックの一部を担っています。特に、`rewriteToUseGot`関数は、動的リンクが必要な場合にシンボル参照をGOT経由に変換する処理を行います。

元の実装では、`LEAQ symbol+offset(SB), Reg`のような命令が以下のように変換されていました。

1.  `MOVQ symbol@GOT(SB), Reg`：`symbol`のGOTエントリからアドレスを`Reg`にロードします。
2.  `ADDQ $offset, Reg`：`Reg`にオフセット値を加算します。

この変換の問題点は、`ADDQ`命令がCPUのフラグレジスタを更新してしまうことです。`LEAQ`命令はフラグを破壊しないため、この変換は元の命令のセマンティクスを破壊していました。もし、この命令の直後にフラグの状態に依存する命令（例: `JCC` (Conditional Jump)）が続く場合、プログラムの動作が不正になる可能性がありました。

このコミットでは、`ADDQ $offset, Reg`の代わりに`LEAQ offset(Reg), Reg`を使用するように変更することで、この問題を解決しています。

*   `LEAQ offset(Reg), Reg`：`Reg`の値に`offset`を加算した結果を`Reg`に格納します。この命令は、`ADDQ`と同様に加算を行いますが、**CPUのフラグレジスタを更新しません**。

これにより、動的リンク時でも`LEAQ symbol+offset(SB), Reg`がフラグを破壊しないという元の特性が維持され、コンパイラが生成するコードの正確性が向上しました。

## コアとなるコードの解説

このコミットの核心は、`rewriteToUseGot`関数内で、オフセットを持つアドレス計算を動的リンク用に再書き込みする際の命令選択の変更です。

以前は、`LEAQ symbol+offset(SB), Reg`のような命令は、動的リンク時には以下のように展開されていました。

1.  `MOVQ symbol@GOT(SB), Reg`：`symbol`のGOTアドレスを`Reg`にロード。
2.  `ADDQ $offset, Reg`：`Reg`にオフセットを加算。

この`ADDQ`命令がフラグを破壊するという問題がありました。

修正後、この部分は以下のように展開されます。

1.  `MOVQ symbol@GOT(SB), Reg`：`symbol`のGOTアドレスを`Reg`にロード。
2.  `LEAQ offset(Reg), Reg`：`Reg`の値に`offset`を加算し、結果を`Reg`に格納。

`LEAQ offset(Reg), Reg`は、`Reg`に`offset`を加算するという点では`ADDQ $offset, Reg`と同じ効果を持ちますが、**フラグレジスタを更新しない**という決定的な違いがあります。これにより、元の`LEAQ`命令が持っていた「フラグを破壊しない」というセマンティクスが、動的リンク時にも正しく維持されるようになりました。

この変更は、Goコンパイラが生成するコードの正確性と堅牢性を向上させ、特にフラグの状態に依存する低レベルのコードや最適化において、予期せぬバグを防ぐ上で重要です。

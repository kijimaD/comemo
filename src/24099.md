# [インデックス 24099] ファイルの概要

このコミットは、Goランタイムにおけるシステムモニター（`sysmon`）によってトリガーされるガベージコレクション（GC）の動作を変更するものです。具体的には、これまでStop-The-World (STW) GCとして実行されていた`sysmon`トリガーGCを、並行（concurrent）GCに変更することで、アプリケーションの一時停止時間を削減し、全体的なパフォーマンスを向上させることを目的としています。

## コミット

`runtime: make sysmon-triggered GC concurrent`

## 変更の背景

Goランタイムには、`sysmon`（システムモニター）と呼ばれるバックグラウンドゴルーチンが存在します。この`sysmon`は、様々なランタイムのハウスキーピングタスクを実行しますが、その一つに、一定期間（このコミットの時点では2分間）GCが実行されていない場合に、強制的にGCをトリガーするという役割があります。これは、GCが全く実行されないことによるメモリ枯渇やパフォーマンス低下を防ぐための安全機構です。

しかし、この`sysmon`によってトリガーされるGCは、これまでStop-The-World (STW) GCとして実装されていました。STW GCは、GCの実行中に全てのアプリケーションゴルーチンを一時停止させるため、アプリケーションの応答性やレイテンシに悪影響を与える可能性があります。特に、GCが長時間実行されないようなワークロードでは、この強制GCが突然発生し、顕著な一時停止を引き起こすことが問題となっていました。

コミットメッセージにある「There is no reason for this to be STW, so make it concurrent.」という記述が示す通り、`sysmon`がトリガーするGCは、必ずしも即座にメモリを解放する必要があるわけではなく、むしろバックグラウンドでゆっくりと実行される並行GCの方が、アプリケーションへの影響を最小限に抑えられるという判断がなされました。この変更は、GoランタイムのGCメカニズム全体をより並行性の高いものへと進化させる一環として行われました。

この変更は、Issue #10261「runtime: sysmon-triggered GC should be concurrent」を解決するものです。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念について理解しておく必要があります。

### 1. Goのガベージコレクション (GC)

Goは自動メモリ管理を採用しており、不要になったメモリ領域を自動的に解放するガベージコレクタを備えています。GoのGCは、主に以下の2つのフェーズで構成されます。

*   **マークフェーズ (Mark Phase)**: どのオブジェクトがまだ使用されているか（到達可能か）を識別します。
*   **スイープフェーズ (Sweep Phase)**: マークされなかった（到達不可能な）オブジェクトが占めていたメモリを解放し、再利用可能にします。

GoのGCは、バージョン1.5以降、主に**並行GC (Concurrent GC)**として動作します。これは、GCの大部分の処理がアプリケーションゴルーチンと並行して実行されることを意味します。これにより、アプリケーションの一時停止時間（STW時間）が大幅に短縮され、レイテンシが改善されます。

### 2. Stop-The-World (STW) GC

STW GCは、GCの特定のフェーズ（特にマークフェーズの初期やスイープフェーズの完了時など）で、全てのアプリケーションゴルーチンを一時的に停止させるGCの方式です。これにより、GCがメモリの状態を安全にスキャンし、変更されることを防ぎます。STW時間は、GCの効率とアプリケーションの応答性のトレードオフにおいて重要な指標となります。Goの並行GCはSTW時間を最小限に抑えるように設計されていますが、完全にゼロにすることはできません。

### 3. `sysmon` (システムモニター) ゴルーチン

`sysmon`は、Goランタイム内で動作する特別なゴルーチンです。これは、以下のような様々なバックグラウンドタスクを定期的に実行します。

*   **ネットワークポーラーの呼び出し**: ネットワークI/Oの準備ができたことを確認します。
*   **タイマーのチェック**: `time.Sleep`や`time.After`などのタイマーが期限切れになっていないかを確認します。
*   **デッドロックの検出**: ゴルーチンがデッドロック状態に陥っていないかをチェックします。
*   **P (Processor) の解放**: 長時間実行されているM (Machine) がPを占有している場合に、Pを解放して他のMが利用できるようにします。
*   **強制GCのトリガー**: 一定期間GCが実行されていない場合に、GCを強制的に開始します。このコミットの焦点はこの機能です。

`sysmon`は、通常10ミリ秒ごとに起動し、これらのタスクを実行します。

### 4. GCモード (`gcForceMode`, `gcBackgroundMode`)

GoランタイムのGCは、いくつかの異なるモードで開始できます。

*   **`gcForceMode`**: 強制的にGCを実行するモードです。このコミット以前は、`sysmon`によってトリガーされるGCはこのモードで実行されており、STW GCとして動作していました。
*   **`gcBackgroundMode`**: バックグラウンドで並行GCとして実行するモードです。このモードでは、GCの大部分がアプリケーションゴルーチンと並行して動作し、STW時間を最小限に抑えます。

### 5. `atomicloaduint(&bggc.working)`

`atomicloaduint`は、Goの`sync/atomic`パッケージで提供される関数で、アトミックに符号なし整数値を読み込みます。これは、複数のゴルーチンが同時にアクセスする可能性のある共有変数に対して、競合状態を避けて安全に値を読み込むために使用されます。
`bggc.working`は、バックグラウンドGCが現在動作中であるかどうかを示すフラグであると推測されます。このフラグが0であれば、バックグラウンドGCは現在実行されていないことを意味します。

## 技術的詳細

このコミットの技術的な変更点は、主に以下の2つのファイルにおける2つの変更に集約されます。

### 1. `src/runtime/proc.go` の変更

`forcegchelper`関数は、GCを強制的に開始するためのヘルパー関数です。この関数内で、GCの開始モードが変更されました。

```diff
--- a/src/runtime/proc.go
+++ b/src/runtime/proc.go
@@ -154,7 +154,7 @@ func forcegchelper() {
 		if debug.gctrace > 0 {
 			println("GC forced")
 		}
-		startGC(gcForceMode)
+		startGC(gcBackgroundMode)
 	}
 }
```

*   **変更前**: `startGC(gcForceMode)`
*   **変更後**: `startGC(gcBackgroundMode)`

この変更により、`forcegchelper`が呼び出す`startGC`は、STW GCとして動作する`gcForceMode`ではなく、並行GCとして動作する`gcBackgroundMode`でGCを開始するようになりました。`sysmon`がGCをトリガーする際に`forcegchelper`を呼び出すため、この変更が`sysmon`トリガーGCの動作に直接影響を与えます。

### 2. `src/runtime/proc1.go` の変更

`sysmon`ゴルーチンのメインループ内で、GCを強制的にトリガーする条件が変更されました。

```diff
--- a/src/runtime/proc1.go
+++ b/src/runtime/proc1.go
@@ -3004,7 +3004,7 @@ func sysmon() {
 		}
 		// check if we need to force a GC
 		lastgc := int64(atomicload64(&memstats.last_gc))
-		if lastgc != 0 && unixnow-lastgc > forcegcperiod && atomicload(&forcegc.idle) != 0 {
+		if lastgc != 0 && unixnow-lastgc > forcegcperiod && atomicload(&forcegc.idle) != 0 && atomicloaduint(&bggc.working) == 0 {
 			lock(&forcegc.lock)
 			forcegc.idle = 0
 			forcegc.g.schedlink = 0
```

*   **変更前**: `if lastgc != 0 && unixnow-lastgc > forcegcperiod && atomicload(&forcegc.idle) != 0`
*   **変更後**: `if lastgc != 0 && unixnow-lastgc > forcegcperiod && atomicload(&forcegc.idle) != 0 && atomicloaduint(&bggc.working) == 0`

この変更では、`sysmon`がGCをトリガーする条件に、`atomicloaduint(&bggc.working) == 0`という新しい条件が追加されました。
これは、「バックグラウンドGCが現在実行中でない場合のみ、`sysmon`はGCをトリガーする」という条件を意味します。
この条件が追加された理由は、`sysmon`がトリガーするGCが並行GCになったため、既に別の並行GCが進行中である場合は、新たにGCをトリガーする必要がない、あるいは既存のGCと競合する可能性があるため、それを避けるためと考えられます。これにより、不必要なGCの重複実行を防ぎ、ランタイムの効率を向上させます。

## コアとなるコードの解説

### `startGC(gcBackgroundMode)` への変更

`src/runtime/proc.go` の `forcegchelper` 関数における `startGC` の呼び出しが、`gcForceMode` から `gcBackgroundMode` に変更されたことは、`sysmon` によってトリガーされるGCが、もはやアプリケーションゴルーチンを完全に停止させるSTW GCではなく、アプリケーションゴルーチンと並行して動作する並行GCとして実行されることを意味します。

*   **`gcForceMode`**: 以前は、このモードでGCが開始されると、ランタイムはGCの完了までアプリケーションゴルーチンを停止させることがありました。これは、緊急性の高いGCや、特定のデバッグシナリオで利用されることが想定されていました。
*   **`gcBackgroundMode`**: このモードは、GCの大部分の作業をバックグラウンドで実行し、アプリケーションゴルーチンの実行を可能な限り継続させます。これにより、GCによるアプリケーションの一時停止時間が大幅に短縮され、レイテンシが改善されます。

この変更は、GoランタイムのGC設計哲学である「低レイテンシ」をさらに推進するものです。`sysmon`による強制GCは、メモリ枯渇を防ぐための安全策であり、必ずしも即座に完了する必要がないため、並行GCとして実行することがより適切であると判断されました。

### `&& atomicloaduint(&bggc.working) == 0` の追加

`src/runtime/proc1.go` の `sysmon` 関数におけるGCトリガー条件に `&& atomicloaduint(&bggc.working) == 0` が追加されたことは、以下の意味を持ちます。

*   **`bggc.working`**: これは、バックグラウンドGCが現在アクティブに動作しているかどうかを示すフラグです。`atomicloaduint` を使用することで、複数のゴルーチンからのアクセスに対して安全にこのフラグの値を読み取ることができます。
*   **条件の目的**: この条件は、「もし既にバックグラウンドGCが進行中であれば、`sysmon`は新たなGCをトリガーしない」というロジックを追加します。

この追加は、`sysmon`トリガーGCが並行GCになったことと密接に関連しています。もし`sysmon`が新たな並行GCをトリガーしようとしたときに、既に別の並行GCが実行中であった場合、それは冗長であるか、あるいはGCの内部状態を複雑にする可能性があります。この条件により、`sysmon`は不必要なGCの重複実行を避け、GCスケジューリングの効率と安定性を向上させます。

全体として、これらの変更は、GoランタイムのGCメカニズムをより洗練させ、特に長期間GCが実行されない状況下でのアプリケーションのパフォーマンスと応答性を向上させることに貢献しています。

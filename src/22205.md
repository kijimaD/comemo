# [インデックス 22205] ファイルの概要

このコミットは、Goランタイムにおける`goexit1`からのトレースバックが正しく機能しない問題を修正するものです。特に、`amd64p32`アーキテクチャ上でトレーサーがクラッシュする原因となっていた、`runtime.getg`の呼び出し元PC（プログラムカウンタ）が予期せぬ値になる問題を解決します。具体的には、`goexit`関数にNOP（No Operation）命令を追加することで、トレースバックが`goexit`のコード範囲を正しく認識できるようにします。

## 変更の背景

このコミットの背景には、Goランタイムのトレーシング機能の進化があります。以前は`goexit1`関数からトレースバックが呼び出されることはありませんでしたが、新しいトレーサーが導入されたことで、`goexit1`の実行パス中にトレースバックが生成されるようになりました。

この変更により、`amd64p32`アーキテクチャ上でトレーサーがクラッシュするという問題が発生しました。クラッシュの原因は、`runtime.getg`関数が呼び出された際のプログラムカウンタ（PC）が、ランタイムが期待する値と異なっていたためです。具体的には、`goexit1`からのリターンPCが、`goexit`関数の直後（+0x6バイト）を指しており、これがトレースバック機構の誤動作を引き起こしていました。

この問題は、特に`amd64p32`のような特定のアーキテクチャで顕在化しました。これは、ポインタサイズの違いがスタックフレームのレイアウトやリターンアドレスの解釈に影響を与え、トレースバックの正確性を損なう可能性があったためと考えられます。このコミットは、このPCのずれを修正し、`goexit1`からのトレースバックが常に`goexit`関数の有効なコード範囲内を指すようにすることで、トレーサーの安定性を確保することを目的としています。

## 前提知識の解説

### Goroutine (ゴルーチン)
Go言語における軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行することも可能です。Goランタイムがゴルーチンのスケジューリングと管理を行います。

### `runtime.Goexit()`、`goexit`、`goexit1`
*   **`runtime.Goexit()`**: Go言語の標準ライブラリ`runtime`パッケージで提供される公開関数です。これを呼び出すと、現在のゴルーチンが終了します。`os.Exit()`とは異なり、プログラム全体ではなく、呼び出し元のゴルーチンのみを終了させ、他のゴルーチンは実行を継続します。`runtime.Goexit()`が呼び出されると、そのゴルーチン内で登録された`defer`関数がすべて実行されます。
*   **`goexit`**: `runtime.Goexit()`から内部的に呼び出されるランタイム関数です。アセンブリコードで実装されており、`goexit1`を呼び出す役割を担います。
*   **`goexit1`**: `goexit`から呼び出される、ゴルーチン終了処理の最終段階を担う内部ランタイム関数です。ゴルーチンのクリーンアップやリソース解放など、低レベルな処理を行います。

### トレースバック (Traceback / Stack Trace)
プログラムの実行中にエラーやパニックが発生した際に、その時点での関数の呼び出し履歴（コールスタック）を遡って表示する機能です。どの関数がどの関数を呼び出し、最終的に問題が発生した箇所に至ったかを示すため、デバッグにおいて非常に重要な情報となります。Goでは、パニック発生時や`SIGQUIT`シグナル受信時などにトレースバックが出力されます。

### プログラムカウンタ (PC: Program Counter)
CPUのレジスタの一つで、次に実行される命令のアドレスを保持しています。関数呼び出しやジャンプ命令によってその値が変化します。トレースバックを生成する際には、スタックに保存されたリターンアドレス（呼び出し元関数の次の命令のPC）を辿ることで、呼び出し履歴を再構築します。

### スタックフレーム
関数が呼び出されるたびに、その関数のローカル変数、引数、そして呼び出し元に戻るためのリターンアドレスなどがスタックメモリ上に確保される領域です。トレースバックは、これらのスタックフレームを順に辿ることで生成されます。

### NOP (No Operation) 命令
CPUが実行しても何も処理を行わない命令です。主に以下のような目的で使用されます。
*   **アライメント調整**: メモリ上のデータやコードの配置を特定のバイト境界に合わせるために使用されます。これにより、CPUのキャッシュ効率が向上したり、特定のハードウェア要件を満たしたりすることができます。
*   **命令の置き換え**: デバッグ目的で一時的に命令を無効化したり、将来の拡張のためにプレースホルダーとして使用したりすることがあります。
*   **タイミング調整**: 非常に短い遅延を挿入するために使用されることもあります。

このコミットでは、トレースバックのPCのずれを修正するために、コードの実行フローに影響を与えずに命令のアドレスを調整する目的で利用されています。

### `runtime.getg`
現在のゴルーチン（`g`構造体）へのポインタを取得するGoランタイムの内部関数です。`g`構造体には、ゴルーチンのスタック情報、状態、スケジューラ関連データなど、ゴルーチンに関するあらゆる情報が含まれています。トレースバックやプロファイリングなど、ゴルーチンの内部状態にアクセスする必要がある場面で利用されます。

### `amd64p32`
Go言語における`GOARCH`（Goアーキテクチャ）の一つです。これは、64ビットのx86（AMD64）命令セットを使用しますが、ポインタサイズが32ビットであるという特徴を持ちます。主にGoogle Native Client (NaCl) 環境で使用されていました。通常の`amd64`が64ビットポインタを使用するのに対し、`amd64p32`は32ビットポインタを使用するため、メモリレイアウトやアドレス計算において違いが生じ、これがトレースバックの挙動に影響を与える可能性がありました。

## 技術的詳細

この問題の核心は、`goexit`関数が`goexit1`関数を呼び出す際のリターンアドレスの扱いにありました。Goランタイムのトレースバック機構は、スタック上のリターンアドレスを読み取り、それを使って呼び出し元の関数を特定します。しかし、このコミット以前の`goexit`の実装では、`CALL runtime·goexit1(SB)`命令の直後に、トレースバックが期待するような「有効な」命令が存在しないか、あるいは命令の長さの都合でPCがずれていました。

コミットメッセージによると、「`goexit1`からのリターンPCが`goexit`の直後（+0x6）を指していた」とあります。これは、`goexit`関数が`goexit1`を呼び出した後、`goexit1`がリターンする際に、スタックに積まれたリターンアドレスが`goexit`関数の本来のコード範囲の終端、あるいはその直後を指してしまっていたことを意味します。

新しいトレーサーが`goexit1`の実行中にトレースバックを生成しようとした際、`runtime.getg`の呼び出し元PCがこの「ずれた」アドレスを指していたため、トレーサーは予期しないPC値に遭遇し、クラッシュしました。特に`amd64p32`で問題が顕在化したのは、32ビットポインタと64ビット命令セットの組み合わせが、スタックフレームの構造やPCの計算に微妙な差異をもたらし、このPCのずれが他のアーキテクチャよりも致命的な影響を与えたためと考えられます。

この問題を解決するために、コミットでは`goexit`関数内の`CALL runtime·goexit1(SB)`命令の直後に、アーキテクチャに応じたNOP命令を追加しています。

*   **x86 (386, amd64, amd64p32)**: `BYTE $0x90` (これはx86アーキテクチャにおける1バイトのNOP命令のオペコードです)
*   **ARM**: `MOVW R0, R0` (ARMアーキテクチャにおけるNOPに相当する命令)
*   **PPC64x**: `MOVD R0, R0` (PowerPCアーキテクチャにおけるNOPに相当する命令)

このNOP命令の追加により、`goexit1`がリターンする際のリターンアドレスが、`goexit`関数の有効なコード範囲内、具体的には追加されたNOP命令のアドレスを指すようになります。これにより、トレースバック機構がPCを辿る際に、常に`goexit`関数内の正当な命令アドレスを認識できるようになり、`runtime.getg`の呼び出し元PCが期待通りの値となることで、トレーサーのクラッシュが回避されました。

つまり、この修正は、コードの実行ロジック自体を変更するのではなく、アセンブリレベルでの命令配置を微調整することで、トレースバックのような低レベルなランタイム機能が正しく動作するための「足場」を確保するものです。

## コアとなるコードの変更箇所

このコミットでは、主にGoランタイムのアセンブリファイルが変更されています。

*   `src/runtime/asm_386.s`
*   `src/runtime/asm_amd64.s`
*   `src/runtime/asm_amd64p32.s`
*   `src/runtime/asm_arm.s`
*   `src/runtime/asm_ppc64x.s`

これらのファイルにおいて、`runtime·goexit`関数の定義内で`CALL runtime·goexit1(SB)`命令の直後にNOP命令が追加されています。

また、`src/runtime/proc1.go`ファイルからは、`goexit1`関数のコメントにあった`// Must be NOSPLIT because it is called from Go. (TODO - probably not anymore)`と`//go:nosplit`の行が削除されています。これは直接的なバグ修正とは異なりますが、`goexit1`の呼び出し規約に関する古いコメントの整理であり、このコミットの文脈で関連する変更として含まれています。

## コアとなるコードの解説

各アセンブリファイルにおける変更は、以下のパターンに従っています。

```assembly
TEXT runtime·goexit(SB),NOSPLIT,$0-0
 	BYTE	$0x90	// NOP
 	CALL	runtime·goexit1(SB)	// does not return
+	// traceback from goexit1 must hit code range of goexit
+	BYTE	$0x90	// NOP
```
（`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s` の例）

*   `TEXT runtime·goexit(SB),NOSPLIT,$0-0`: `runtime·goexit`関数の定義を開始します。`NOSPLIT`は、この関数がスタックを分割しないことを示します。
*   `BYTE $0x90 // NOP`: 既存のNOP命令です。これは以前から存在していた可能性があります。
*   `CALL runtime·goexit1(SB)`: `runtime·goexit1`関数を呼び出します。この関数はリターンしない（`does not return`）とコメントされていますが、トレースバックの文脈では、この呼び出しの「後」のアドレスが重要になります。
*   `// traceback from goexit1 must hit code range of goexit`: この行は、追加されたNOP命令の目的を明確に説明するコメントです。`goexit1`からのトレースバックが、`goexit`関数の有効なコード範囲内を指す必要があることを示しています。
*   `BYTE $0x90 // NOP`: **このコミットで追加された重要なNOP命令です。** この命令が追加されることで、`CALL`命令の直後に、トレースバックがリターンアドレスとして認識すべき有効な命令が存在するようになります。これにより、PCのずれが解消され、トレースバックが正しく機能するようになります。

他のアーキテクチャ（ARM, PPC64x）でも同様に、それぞれのアーキテクチャのNOPに相当する命令（`MOVW R0, R0`や`MOVD R0, R0`）が追加されています。これらの命令は、レジスタの値をそれ自身に移動させることで、実質的に何も操作を行わないNOPとして機能します。

`src/runtime/proc1.go`からのコメント削除は、`goexit1`が`NOSPLIT`である必要性に関する古い仮定が、ランタイムの変更により不要になったことを示唆しています。これは直接的なバグ修正ではありませんが、コードベースのクリーンアップと最新のランタイムの挙動への適合を反映しています。

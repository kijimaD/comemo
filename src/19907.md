## 変更の背景

このコミットの背景には、Goランタイムのメモリ管理における`MSpan`のライフサイクルと、`UncacheSpan`関数の役割の明確化があります。コミットメッセージにある「Full spans can't be passed to UncacheSpan since we get rid of free.」という記述が核心です。

Goのメモリ管理では、`MSpan`はメモリの連続したページ群を表し、オブジェクトの割り当てに使用されます。`MSpan`は`mcache`（プロセッサごとのキャッシュ）から`mcentral`（サイズクラスごとの集中リスト）へ、そして最終的には`mheap`（ヒープ全体）へと移動します。

`UncacheSpan`関数は、`mcache`から`mcentral`へ`MSpan`を返す際に呼び出されます。この関数が呼び出されるのは、通常、`MSpan`内のオブジェクトがすべて解放され、`MSpan`が空になった場合、または`mcache`がフラッシュされる場合です。

しかし、以前の実装では、`UncacheSpan`内で`s->ref == 0`（つまり、`MSpan`内の参照カウントが0、完全に空の状態）の場合に、`MCentral_ReturnToHeap`を呼び出して`MSpan`を直接ヒープに返すロジックが存在していました。コミットメッセージは、このロジックが「freeを削除したため、Full spanはUncacheSpanに渡せない」という前提と矛盾していることを示唆しています。

つまり、`UncacheSpan`が呼び出される時点で、`MSpan`は`mcache`から`mcentral`に戻される途中の状態であり、まだ完全にヒープに返されるべきではない、あるいはそのパスが適切ではないという認識があったと考えられます。このコミットは、この矛盾を解消し、コードパスを簡素化することで、メモリ管理のロジックをより堅牢で理解しやすいものにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理の基本的な概念を把握しておく必要があります。

1.  **ページ (Page)**: Goランタイムのメモリ管理における最小単位はページです。通常、8KBのサイズを持ちます。
2.  **MSpan (Memory Span)**: 連続した複数のページから構成されるメモリ領域の単位です。`MSpan`は特定のサイズクラス（後述）のオブジェクトを格納するために使用されます。`MSpan`は、その中に含まれるオブジェクトがすべて解放されると「空」になり、再利用可能になります。
3.  **サイズクラス (Size Class)**: Goは、異なるサイズのオブジェクトを効率的に管理するために、事前に定義された「サイズクラス」を使用します。例えば、8バイトのオブジェクト用、16バイトのオブジェクト用、といった具合に、様々なサイズのオブジェクトに対応する`MSpan`が存在します。
4.  **mcache (Memory Cache)**: 各論理プロセッサ（P）に紐付けられたローカルなメモリキャッシュです。ゴルーチン（G）がメモリを割り当てる際、まず自身のPに紐付けられた`mcache`から`MSpan`を取得しようとします。これにより、グローバルなロックを回避し、高速なアロケーションを実現します。`mcache`は、特定のサイズクラスの`MSpan`のリストを保持しています。
5.  **mcentral (Memory Central)**: 各サイズクラスごとに存在する中央のメモリリストです。`mcache`が`MSpan`を使い果たした場合、`mcentral`から新しい`MSpan`を取得します。また、`mcache`から空になった`MSpan`が返される場所でもあります。`mcentral`は、空の`MSpan`と、部分的に使用されている`MSpan`のリストを管理しています。
6.  **mheap (Memory Heap)**: GoランタイムがOSから取得したすべてのメモリを管理するグローバルなヒープです。`mcentral`が新しい`MSpan`を必要とする場合、`mheap`から取得します。また、`MSpan`が完全に解放され、OSに返却される準備ができた場合も、`mheap`に返されます。
7.  **UncacheSpan**: `mcache`から`mcentral`へ`MSpan`を返す際に呼び出される関数です。`MSpan`が`mcache`から取り除かれ、`mcentral`の管理下に戻される処理を行います。
8.  **ref (Reference Count)**: `MSpan`内の割り当て済みオブジェクトの数を追跡する参照カウントです。`ref`が0の場合、その`MSpan`内のすべてのオブジェクトが解放されたことを意味します。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムのメモリ管理における`MSpan`のライフサイクルと、`UncacheSpan`関数の役割の厳密化にあります。

変更の核心は、`runtime·MCentral_UncacheSpan`関数内のロジックの修正です。以前のバージョンでは、`UncacheSpan`が呼び出された際に、`MSpan`の参照カウント`s->ref`が0である（つまり、`MSpan`が完全に空である）場合、その`MSpan`を`MCentral_ReturnToHeap`関数を通じて直接`mheap`に返していました。

しかし、コミットメッセージが示唆するように、`UncacheSpan`の本来の目的は、`MSpan`を`mcache`から`mcentral`に戻すことであり、完全に空の`MSpan`が`UncacheSpan`に渡されるべきではない、という設計思想の変更があったと考えられます。`MSpan`が完全に空でヒープに返されるべき状態であれば、それは`MCentral_FreeSpan`のような別のパスで処理されるべきです。

このコミットでは、以下の変更が行われています。

1.  **`UncacheSpan`からの`MCentral_ReturnToHeap`呼び出しの削除**: `mcentral.c`の`runtime·MCentral_UncacheSpan`関数から、`s->ref == 0`の場合に`MCentral_ReturnToHeap`を呼び出すロジックが削除されました。
2.  **`UncacheSpan`におけるアサーションの追加**: 代わりに、`s->ref == 0`の場合には`runtime·throw("uncaching full span")`というパニックを発生させるアサーションが追加されました。これは、「完全に空の`MSpan`が`UncacheSpan`に渡されることは予期しない状態である」というランタイムの前提を強化するものです。
3.  **`MCentral_ReturnToHeap`関数の削除**: `mcentral.c`から`MCentral_ReturnToHeap`関数自体が削除されました。この関数は、`UncacheSpan`からのみ呼び出されていたため、その呼び出しが削除されたことで不要になりました。
4.  **`MCentral_FreeSpan`の簡素化**: `MCentral_FreeSpan`関数内で`MSpan`が完全に解放された際にヒープに返すロジックが、`MCentral_ReturnToHeap`の呼び出しから、直接`MSpanList_Remove`、`needzero`、`freelist`のクリア、ロック解除、`unmarkspan`、そして`MHeap_Free`の呼び出しへと変更されました。これは、`MCentral_ReturnToHeap`が削除されたことによる直接的な影響です。
5.  **`runtime·MGetSizeClassInfo`関数の削除とインライン化**: `malloc.h`から`runtime·MGetSizeClassInfo`関数の宣言が削除され、`mcentral.c`の`MCentral_Grow`関数内でそのロジックが直接インライン化されました。これは、小さなヘルパー関数を削除し、コードをより直接的にすることで、コンパイラの最適化を助け、コードの可読性を向上させる一般的な最適化手法です。

これらの変更により、`UncacheSpan`の役割が「`mcache`から`mcentral`へ`MSpan`を戻す」という一点に絞られ、`MSpan`が完全に空になった場合のヒープへの返却は、`MCentral_FreeSpan`などの別のパスで一貫して処理されるようになりました。これにより、メモリ管理のロジックがより明確になり、潜在的なバグのリスクが低減されます。

## コアとなるコードの解説

### `src/pkg/runtime/malloc.h` と `src/pkg/runtime/mcentral.c` からの `runtime·MGetSizeClassInfo` の削除とインライン化

*   **変更内容**: `malloc.h`から`runtime·MGetSizeClassInfo`関数の宣言が削除され、`mcentral.c`の`MCentral_Grow`関数内でこの関数が提供していたロジック（`sizeclass`から`size`, `npages`, `nobj`を取得する）が直接記述されるようになりました。
*   **解説**: `runtime·MGetSizeClassInfo`は、特定のサイズクラスに対応するメモリのサイズ、ページ数、オブジェクト数を返すヘルパー関数でした。この関数は非常にシンプルであり、その呼び出しオーバーヘッドを削減し、コンパイラによる最適化を促進するために、呼び出し元である`MCentral_Grow`関数内に直接そのロジックを埋め込む（インライン化する）ことが選択されました。これにより、コードの依存関係が減り、全体的な簡素化に貢献しています。

### `src/pkg/runtime/mcache.c` における `runtime·MCentral_UncacheSpan` 呼び出しの変更

*   **変更内容**: `runtime·MCache_Refill`関数内で、`MSpan`が`emptymspan`でない場合に`runtime·MCentral_UncacheSpan(&runtime·mheap.central[sizeclass], s);`という呼び出しが`s->incache = false;`に置き換えられました。
*   **解説**: 以前は、`mcache`が`MSpan`を使い果たし、新しい`MSpan`を`mcentral`から取得する前に、現在使用している`MSpan`を`mcentral`に「アンキャッシュ」する処理を行っていました。しかし、このコミットの目的は`UncacheSpan`の役割を厳密化することです。`mcache`から`mcentral`へ`MSpan`を返す際に、`MSpan`が`mcache`のキャッシュから外れることを示す`s->incache = false;`というフラグ設定のみで十分であると判断されました。これにより、`UncacheSpan`の呼び出しが不要になり、コードパスが簡素化されました。

### `src/pkg/runtime/mcentral.c` における `runtime·MCentral_UncacheSpan` の修正

*   **変更内容**:
    *   `s->ref == 0`の場合に`MCentral_ReturnToHeap(c, s);`を呼び出すロジックが削除されました。
    *   代わりに、`s->ref == 0`の場合に`runtime·throw("uncaching full span");`というパニックが追加されました。
*   **解説**: これがこのコミットの最も重要な変更点です。`UncacheSpan`の本来の意図は、`mcache`から`mcentral`へ`MSpan`を戻すことであり、その`MSpan`はまだ完全に空である（`s->ref == 0`）べきではありません。もし`MSpan`が完全に空であれば、それは`mcentral`から直接ヒープに返されるべきであり、`UncacheSpan`のパスを通るべきではありません。この変更は、`UncacheSpan`の契約を強化し、予期せぬ状態（完全に空の`MSpan`が`UncacheSpan`に渡されること）が発生した場合に早期に問題を検出するためのアサーションとして機能します。これにより、メモリ管理のロジックがより堅牢になります。

### `src/pkg/runtime/mcentral.c` における `MCentral_ReturnToHeap` の削除と `MCentral_FreeSpan` の修正

*   **変更内容**:
    *   `static void MCentral_ReturnToHeap(MCentral *c, MSpan *s);`の宣言と定義が`mcentral.c`から完全に削除されました。
    *   `runtime·MCentral_FreeSpan`関数内で、`MSpan`が完全に解放された際にヒープに返すロジックが、削除された`MCentral_ReturnToHeap`の呼び出しから、直接的な一連の操作（`runtime·MSpanList_Remove(s);`、`s->needzero = 1;`、`s->freelist = nil;`、`runtime·unlock(c);`、`runtime·unmarkspan(...)`、`runtime·MHeap_Free(...)`）に置き換えられました。
*   **解説**: `MCentral_ReturnToHeap`関数は、`UncacheSpan`からのみ呼び出されていました。`UncacheSpan`からの呼び出しが削除されたため、この関数自体が不要となり、削除されました。その結果、`MSpan`が完全に解放された場合にヒープに返す処理は、`MCentral_FreeSpan`内で直接行われるようになりました。これにより、コードの冗長性が排除され、メモリ解放のパスがより直接的で理解しやすくなりました。

これらの変更は全体として、Goランタイムのメモリ管理コードを簡素化し、各関数の役割を明確にし、予期せぬ状態に対する堅牢性を高めることを目的としています。

## 変更の背景

Goツールチェインは、ソースコードを最終的な実行可能ファイルに変換する一連のツール（コンパイラ、アセンブラ、リンカなど）で構成されています。このプロセスの中で、データ定義は様々な中間表現を経て処理されます。

以前は、アセンブラを含むツールチェインの一部で、データ定義を表現するために`ADATA Prog`という内部的な命令タイプが使用されていました。`Prog`はアセンブリ命令の抽象的な内部表現であり、`ADATA`はその`Prog`がデータ定義を表すことを示すタイプでした。

しかし、Goツールチェインの開発が進むにつれて、データ定義をより直接的かつ効率的に処理する方法が導入されてきました。具体的には、リンカシンボル（`LSym`）に直接データを書き込むAPIが整備され、中間的な`ADATA Prog`を介する必要がなくなりました。

このコミットの時点で、アセンブラが`ADATA Prog`を生成する唯一の場所となっていました。他のコンポーネントは既にこの古いメカニズムから移行していたため、アセンブラも同様に移行することで、ツールチェイン全体から`ADATA Prog`の概念を完全に排除し、関連する不要なコードを削除することが可能になりました。これにより、コードベースの簡素化、保守性の向上、そして潜在的なパフォーマンスの改善が期待されます。

## 前提知識の解説

このコミットを理解するためには、Goツールチェインの基本的な構造と、アセンブリ命令の内部表現に関する知識が必要です。

### Goツールチェインの概要

Go言語のソースコードは、以下の主要なステップを経て実行可能ファイルになります。

1.  **コンパイラ (`go tool compile`)**: Goのソースコード（`.go`ファイル）を、特定のマシンアーキテクチャに依存しない中間表現（SSA形式など）に変換し、最終的にはアセンブリコード（`.s`ファイル）またはオブジェクトファイル（`.o`ファイル）を生成します。
2.  **アセンブラ (`go tool asm`)**: Goのアセンブリコード（`.s`ファイル）を読み込み、マシンコードを含むオブジェクトファイル（`.o`ファイル）に変換します。Goのアセンブラは、一般的なアセンブラとは異なり、仮想レジスタや抽象的な命令セットを使用する特徴があります。
3.  **リンカ (`go tool link`)**: コンパイラやアセンブラが生成した複数のオブジェクトファイル（`.o`ファイル）を結合し、必要なGoランタイムライブラリを含めて、最終的な実行可能バイナリを生成します。シンボル解決や再配置（リロケーション）などの重要な処理を行います。

### `obj.Prog`と`obj.As`

Goツールチェインの内部では、アセンブリ命令は`obj.Prog`という構造体で表現されます。これは、アセンブリ命令のオペコード、オペランド、関連するメタデータなどをカプセル化したものです。

`obj.As`は、`obj.Prog`構造体の一部であり、その`Prog`がどのような種類のアセンブリ命令を表すかを示す列挙型（または定数）です。例えば、`obj.ATEXT`は関数コードの開始を、`obj.AGLOBL`はグローバルシンボルの定義を、そしてこのコミットで削除される`obj.ADATA`はデータ定義をそれぞれ表していました。

### `LSym` (Linker Symbol)

`LSym`は、リンカが扱うシンボル（関数、グローバル変数、データなど）の内部表現です。各`LSym`は、そのシンボルがメモリ上のどこに配置されるか、どのようなデータを持つか、どのような再配置情報が必要かといった詳細な情報を含んでいます。

Goツールチェインでは、データ定義は最終的に`LSym`に関連付けられたバイト列として表現されます。以前は`ADATA Prog`を生成し、その`Prog`をリンカが処理して`LSym`にデータを書き込むという間接的な方法が取られていましたが、このコミット以降はアセンブラが直接`LSym`のAPI（例: `WriteInt`, `WriteString`など）を呼び出してデータを書き込むようになります。

### データ定義の進化

Goツールチェインにおけるデータ定義の処理は、より直接的で効率的な方法へと進化してきました。初期の段階では、`ADATA Prog`のような中間表現がデータの種類（整数、浮動小数点数、文字列、アドレスなど）を抽象化し、リンカがそれを解釈して最終的なデータセクションに書き込む役割を担っていました。

しかし、このアプローチはオーバーヘッドを伴う可能性があり、また、アセンブラが直接シンボルにデータを書き込む方が、より柔軟で最適化されたコード生成を可能にするという判断がなされたと考えられます。このコミットは、その進化の最終段階の一つであり、`ADATA Prog`という中間層を完全に排除することで、ツールチェインの内部構造を簡素化しています。

## 技術的詳細

このコミットの技術的な詳細を掘り下げると、主に以下の点が挙げられます。

1.  **`ADATA Prog`生成の停止と直接書き込みへの移行**:
    *   `src/cmd/asm/internal/asm/asm.go`の`asmData`関数は、アセンブリコード中の`DATA`ディレクティブを処理する部分です。以前はここで`obj.ADATA`タイプの`obj.Prog`を生成し、それをリンカに渡していました。
    *   変更後は、`obj.ADATA` `Prog`を生成する代わりに、`valueAddr.Type`（データの種類、例: `obj.TYPE_CONST`, `obj.TYPE_FCONST`, `obj.TYPE_SCONST`, `obj.TYPE_ADDR`）に応じて、`nameAddr.Sym`（対象のシンボル）の適切な`WriteXxx`メソッド（`WriteInt`, `WriteFloat32`, `WriteFloat64`, `WriteString`, `WriteAddr`）を直接呼び出すようになりました。これにより、アセンブラが直接シンボルのデータ領域に値を書き込む形になります。

2.  **`savedata`関数の削除**:
    *   `src/cmd/internal/obj/data.go`にあった`savedata`関数は、`obj.ADATA` `Prog`を受け取り、その内容に基づいてシンボル（`LSym`）のデータ領域に値を書き込む役割を担っていました。
    *   アセンブラが直接`LSym`にデータを書き込むようになったため、この`savedata`関数は不要となり、完全に削除されました。これにより、約60行のコードが削除され、データ処理ロジックが簡素化されました。

3.  **`ADATA`参照の削除**:
    *   `obj.ADATA`がツールチェインの内部で特別な意味を持たなくなったため、その参照が様々なファイルから削除されています。
    *   `src/cmd/compile/internal/arm/peep.go`: ARMアーキテクチャのpeephole最適化器から`obj.ADATA`が削除されています。peephole最適化は命令列を局所的に最適化するものですが、データ定義である`ADATA`は最適化の対象外であるため、そのリストから削除されました。
    *   `src/cmd/compile/internal/gc/gsubr.go`と`src/cmd/compile/internal/gc/plive.go`: コンパイラの内部処理において、`obj.ADATA` `Prog`の特別な扱いが不要になったため、条件分岐から削除されています。
    *   `src/cmd/internal/obj/objfile.go`: `flushplist`関数内で`ADATA` `Prog`を処理するために`savedata`を呼び出していた部分が削除されました。
    *   `src/cmd/internal/obj/link.go`: `Prog`構造体のコメントから`ADATA`に関する記述が削除され、`ADATA`定数のコメントが「used only by the assembler for parsing」と変更されています。これは、`ADATA`がもはやリンカによって処理される命令タイプではなく、アセンブラの構文解析段階でのみ使用されることを示唆しています。
    *   `src/cmd/internal/obj/util.go`: `Prog`の文字列表現を生成する際に、`ADATA` `Prog`に対する特別なフォーマット処理が不要になったため、その条件が削除されています。
    *   `src/cmd/internal/obj/x86/asm6.go`: x86アセンブラの命令テーブルから`obj.ADATA`が削除されています。これは、`ADATA`がもはやアセンブラが生成する命令タイプではないことを反映しています。

これらの変更は、Goツールチェインの内部設計が成熟し、より直接的で効率的なデータ処理メカニズムへと移行したことを示しています。`ADATA Prog`という中間層を排除することで、コードの複雑性が減少し、将来的なメンテナンスや機能拡張が容易になります。

## コアとなるコードの変更箇所

このコミットにおける最もコアとなるコードの変更箇所は、以下の2つのファイルに集中しています。

1.  **`src/cmd/asm/internal/asm/asm.go` の `asmData` 関数**:
    `asmData`関数は、アセンブリソースコード内の`DATA`ディレクティブを処理する部分です。
    変更前:
    ```go
    	prog := &obj.Prog{
    		Ctxt:   p.ctxt,
    		As:     obj.ADATA,
    		Lineno: p.histLineNum,
    		From:   nameAddr,
    		From3: &obj.Addr{
    			Offset: int64(scale),
    		},
    		To: valueAddr,
    	}
    	p.append(prog, "", false)
    ```
    変更後:
    ```go
    	switch valueAddr.Type {
    	case obj.TYPE_CONST:
    		nameAddr.Sym.WriteInt(p.ctxt, nameAddr.Offset, int64(scale), valueAddr.Offset)
    	case obj.TYPE_FCONST:
    		switch scale {
    		case 4:
    			nameAddr.Sym.WriteFloat32(p.ctxt, nameAddr.Offset, float32(valueAddr.Val.(float64)))
    		case 8:
    			nameAddr.Sym.WriteFloat64(p.ctxt, nameAddr.Offset, valueAddr.Val.(float64))
    		default:
    			panic("bad float scale")
    		}
    	case obj.TYPE_SCONST:
    		nameAddr.Sym.WriteString(p.ctxt, nameAddr.Offset, int64(scale), valueAddr.Val.(string))
    	case obj.TYPE_ADDR:
    		nameAddr.Sym.WriteAddr(p.ctxt, nameAddr.Offset, int64(scale), valueAddr.Sym, valueAddr.Offset)
    	}
    ```
    この変更により、`obj.ADATA`タイプの`Prog`を生成して`p.append`で追加する代わりに、データの種類に応じて`nameAddr.Sym`（リンカシンボル）の適切な`WriteXxx`メソッドを直接呼び出すようになりました。

2.  **`src/cmd/internal/obj/data.go` から `savedata` 関数の削除**:
    `savedata`関数は、`obj.ADATA` `Prog`を処理し、シンボルにデータを書き込むための内部関数でした。
    変更前（関数全体が削除されています）:
    ```go
    func savedata(ctxt *Link, p *Prog) {
    	s := p.From.Sym
    	off := int32(p.From.Offset)
    	siz := int32(p.From3.Offset)
    	// ... (データ書き込みロジック) ...
    }
    ```
    この関数が完全に削除されたことで、`ADATA Prog`を処理するメカニズムがツールチェインから取り除かれました。

## コアとなるコードの解説

### `src/cmd/asm/internal/asm/asm.go` の `asmData` 関数

この変更は、アセンブラがデータ定義をどのように扱うかという根本的なアプローチを変更しています。

*   **変更前**: アセンブラは、`DATA`ディレクティブに遭遇すると、そのデータ定義を抽象的な`obj.ADATA` `Prog`オブジェクトとしてカプセル化していました。この`Prog`オブジェクトには、データのオフセット、サイズ、値などの情報が含まれていました。その後、この`Prog`はリンカに渡され、リンカが`savedata`関数などを通じて実際のシンボルデータ領域に値を書き込んでいました。これは、データ処理をリンカに委ねる間接的な方法でした。

*   **変更後**: アセンブラは、`DATA`ディレクティブを解析すると、そのデータの種類（定数、浮動小数点数、文字列、アドレス）を直接識別します。そして、対象となるリンカシンボル（`nameAddr.Sym`）に対して、その種類に応じた専用の書き込みメソッド（`WriteInt`, `WriteFloat32`, `WriteString`, `WriteAddr`など）を直接呼び出します。これにより、アセンブラ自身がシンボルのデータ領域に直接値を書き込む責任を持つようになりました。

この変更の利点は以下の通りです。
*   **簡素化**: `ADATA Prog`という中間表現とその処理ロジックが不要になり、ツールチェインのデータフローが簡素化されます。
*   **効率化**: 中間オブジェクトの生成と、それをリンカが再度解釈するオーバーヘッドがなくなります。アセンブラが直接書き込むことで、より効率的な処理が可能になります。
*   **責任の明確化**: データ定義の最終的な書き込みが、アセンブラの段階でより直接的に行われるようになり、各コンポーネントの責任が明確になります。

### `src/cmd/internal/obj/data.go` から `savedata` 関数の削除

`savedata`関数は、`obj.ADATA` `Prog`を処理するための中心的なロジックを含んでいました。この関数は、`ADATA Prog`からデータのオフセット、サイズ、値、型などの情報を抽出し、それに基づいてシンボルのバイト配列（`s.P`）に適切な形式でデータを書き込む役割を担っていました。また、アドレス再配置が必要な場合には`Addrel`を呼び出して再配置情報を追加していました。

`asmData`関数が`ADATA Prog`を生成しなくなったため、`savedata`関数を呼び出す必要がなくなり、この関数は完全に削除されました。これは、`ADATA Prog`という概念がGoツールチェインのデータ処理パイプラインから完全に排除されたことを象徴する変更です。この削除により、コードベースから約60行の古い、もはや使用されないロジックが取り除かれ、全体的なコードの軽量化と保守性の向上が実現されました。

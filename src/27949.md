# [インデックス 27949] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における「スキャン作業量 (scan work)」の計算方法を修正するものです。具体的には、GC中に「ブラック (black)」として割り当てられたオブジェクト（ブラックアロケーション）を、スキャン作業量に含めるように変更しています。これにより、GCの動作の一貫性が向上し、将来的にGoのGCが常にブラックアロケーションを行うようになる際の準備となります。

    runtime: count black allocations toward scan work
    
    Currently we count black allocations toward the scannable heap size,
    but not toward the scan work we've done so far. This is clearly
    inconsistent (we have, in effect, scanned these allocations and since
    they're already black, we're not going to scan them again). Worse, it
    means we don't count black allocations toward the scannable heap size
    as of the *next* GC because this is based on the amount of scan work
    we did in this cycle.
    
    Fix this by counting black allocations as scan work. Currently the GC
    spends very little time in allocate-black mode, so this probably
    hasn't been a problem, but this will become important when we switch
    to always allocating black.

## 元コミット内容

Goランタイムにおいて、ブラックとして割り当てられたオブジェクト（ブラックアロケーション）は、スキャン可能なヒープサイズには計上されるものの、これまでに実行されたスキャン作業量には計上されていませんでした。これは、これらのオブジェクトが実質的にスキャン済みであり、再度スキャンされることがないという事実と矛盾していました。さらに悪いことに、この不整合は、次回のGCにおけるスキャン可能なヒープサイズが、現在のGCサイクルで実行されたスキャン作業量に基づいて計算されるため、ブラックアロケーションが適切に考慮されないという問題を引き起こしていました。

このコミットは、ブラックアロケーションをスキャン作業量として計上することで、この問題を修正します。現状では、GCが「allocate-blackモード」で費やす時間は非常に短いため、この問題が顕在化することは少なかったと考えられます。しかし、将来的にGoのGCが常にブラックアロケーションを行うように変更される際には、この修正が非常に重要になります。

## 変更の背景

Goのガベージコレクションは、並行マーク＆スイープ方式を採用しており、その効率性を高めるために様々な最適化が施されています。このコミットの背景には、GCの「スキャン作業量」の正確な計測と、将来的なGC戦略の変更への準備があります。

GoのGCは、ヒープの成長率に基づいて次回のGCのタイミングを決定します。この決定には、前回のGCサイクルでどれだけの「スキャン作業」が行われたかが重要な指標となります。スキャン作業量が多いほど、GCはより多くのオブジェクトを処理したと見なされ、次回のGCまでの期間が調整されます。

しかし、これまでの実装では、GC中に新しく割り当てられたオブジェクトが「ブラック」としてマークされた場合（ブラックアロケーション）、そのオブジェクトは既にスキャン済みと見なされるにもかかわらず、スキャン作業量には加算されていませんでした。これは以下の問題を引き起こしていました。

1.  **不整合**: 既にスキャンされたオブジェクトがスキャン作業量に計上されないのは論理的に不整合です。
2.  **次回のGCへの影響**: スキャン作業量の不正確な計上は、次回のGCのトリガータイミングやヒープサイズの推定に影響を与え、GCの効率を低下させる可能性がありました。特に、次回のGCの目標ヒープサイズは、現在のGCサイクルでスキャンされたヒープサイズに基づいて決定されるため、ブラックアロケーションが考慮されないと、目標ヒープサイズが過小評価される恐れがありました。
3.  **将来のGC戦略**: GoのGCは、パフォーマンス向上のために「常にブラックアロケーションを行う」方向へと進化する計画がありました。この戦略が導入された場合、ブラックアロケーションがスキャン作業量に計上されないという現在の問題は、GCの動作全体に深刻な影響を及ぼすことになります。

このコミットは、これらの問題を解決し、GCの計測をより正確にすることで、現在のGCの安定性を向上させるとともに、将来のGC戦略変更への道を開くものです。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションの基本的な概念と、特に「三色マーキング (Tri-color marking)」アルゴリズムに関する知識が必要です。

### Goのガベージコレクション (GC)

GoのGCは、並行（concurrent）かつ低遅延（low-latency）なマーク＆スイープ方式を採用しています。これは、アプリケーションの実行と並行してGC処理の一部を進めることで、アプリケーションの一時停止時間（Stop-The-World, STW）を最小限に抑えることを目指しています。

GCの主要なフェーズは以下の通りです。

1.  **マークフェーズ (Mark Phase)**:
    *   **マーク開始 (Mark Start)**: 短いSTWが発生し、GCが開始されます。ルートオブジェクト（グローバル変数、スタック上の変数など）が特定され、GCワーカーが起動します。
    *   **並行マーク (Concurrent Mark)**: アプリケーションの実行と並行して、GCワーカーが到達可能なオブジェクトをマークしていきます。この際、三色マーキングアルゴリズムが使用されます。
    *   **マーク終了 (Mark Termination)**: 短いSTWが発生し、並行マーク中に発生した変更（ミューテータがオブジェクトグラフを変更したこと）を処理し、マークフェーズを完了します。

2.  **スイープフェーズ (Sweep Phase)**:
    *   **並行スイープ (Concurrent Sweep)**: マークされなかったオブジェクト（到達不可能と判断されたオブジェクト）が解放され、ヒープメモリが再利用可能になります。これはアプリケーションの実行と並行して行われます。

### 三色マーキング (Tri-color marking) アルゴリズム

三色マーキングは、並行GCで広く用いられるアルゴリズムです。オブジェクトは以下の3つの色のいずれかの状態を持ちます。

*   **白 (White)**: まだGCによって到達可能かどうかが確認されていないオブジェクト。GCサイクルの開始時には、すべてのオブジェクトが白です。最終的に白のままのオブジェクトは、到達不可能と判断され、スイープフェーズで回収されます。
*   **灰 (Gray)**: GCによって到達可能であるとマークされたが、そのオブジェクトが参照している他のオブジェクト（子オブジェクト）がまだスキャンされていない状態のオブジェクト。GCワーカーは灰色のオブジェクトをスキャンし、その子オブジェクトを灰色にマークし、自身を黒色に遷移させます。
*   **黒 (Black)**: GCによって到達可能であるとマークされ、かつそのオブジェクトが参照しているすべての子オブジェクトもスキャン済み（または灰色/黒色）である状態のオブジェクト。黒色のオブジェクトは、GCサイクル中に回収されることはありません。

### ブラックアロケーション (Black Allocations)

通常のGCサイクル中、新しいオブジェクトが割り当てられると、最初は「白」として扱われます。しかし、GoのGCには、特定の条件下で新しく割り当てられたオブジェクトを最初から「黒」としてマークする「allocate-blackモード」が存在します。

これは主に、GCのマークフェーズ中に新しいオブジェクトが作成された場合に、そのオブジェクトがGCによって見落とされないようにするための最適化です。もし新しいオブジェクトが白として割り当てられ、かつGCがそのオブジェクトに到達する前に、そのオブジェクトへの唯一の参照が失われた場合、そのオブジェクトは誤って回収されてしまう可能性があります（これは「Dijkstraの三色マーキングの不変条件」を破ることに繋がります）。

allocate-blackモードでは、新しく割り当てられたオブジェクトは即座に黒としてマークされます。これにより、そのオブジェクトは現在のGCサイクルでは回収されず、次回のGCサイクルで改めて評価されることになります。これは、GCの正確性を保証しつつ、ミューテータ（アプリケーションコード）がオブジェクトを自由に操作できるようにするための重要なメカニズムです。

### スキャン作業量 (Scan Work)

GoのGCは、ヒープの成長を監視し、次回のGCをいつトリガーするかを決定するために、様々なメトリクスを使用します。その一つが「スキャン作業量 (scan work)」です。

スキャン作業量とは、GCがオブジェクトグラフを辿り、ポインタをスキャンするために費やした作業の量をバイト単位で表したものです。これは、GCがどれだけのメモリを「検査」したかを示す指標であり、次回のGCの目標ヒープサイズを計算する際の重要な入力となります。具体的には、`gcControllerState.scanWork`というフィールドで管理されており、GCサイクル中に原子的に更新されます。

このコミット以前は、ブラックアロケーションされたオブジェクトは、そのオブジェクト自体がスキャン可能であるにもかかわらず、この`scanWork`には計上されていませんでした。

## 技術的詳細

このコミットの技術的な核心は、`gcmarknewobject_m`関数と、`mallocgc`関数における`scanSize`の計算および`gcw.scanWork`への加算です。

### `mallocgc`関数の変更

`mallocgc`関数は、Goプログラムがメモリを割り当てる際に呼び出される主要な関数です。この関数内で、新しく割り当てられるオブジェクトの「スキャンサイズ」が計算され、GCワーカーのローカルスキャン作業量に加算されるようになりました。

変更前は、`c.local_scan += typ.ptrdata`のように、オブジェクトのポインタデータサイズが直接`c.local_scan`に加算されていました。しかし、このコミットでは、`scanSize`という新しい変数が導入され、オブジェクトのポインタデータサイズ（または配列の場合の調整されたサイズ）が`scanSize`に格納されます。そして、この`scanSize`が`c.local_scan`に加算されます。

さらに重要な変更は、`gcmarknewobject_m`関数の呼び出しです。GCがマークフェーズ中であるか、`gcBlackenPromptly`が真である場合（つまり、オブジェクトを即座に黒くマークする必要がある場合）、`gcmarknewobject_m`が呼び出されます。変更前は`gcmarknewobject_m(uintptr(x), size)`のように`size`のみが渡されていましたが、変更後は`gcmarknewobject_m(uintptr(x), size, scanSize)`のように、計算された`scanSize`も引数として渡されるようになりました。

### `gcmarknewobject_m`関数の変更

`gcmarknewobject_m`関数は、新しく割り当てられたオブジェクトを黒くマークする役割を担います。この関数は、GCがマークフェーズ中であるか、`gcBlackenPromptly`フラグが設定されている場合に呼び出されます。

変更前は、この関数はオブジェクトのサイズ（`size`）のみを受け取っていました。変更後、`scanSize`という新しい引数を受け取るようになりました。

この関数内で、オブジェクトは`heapBitsForAddr(obj).setMarked()`によって黒くマークされ、`atomic.Xadd64(&work.bytesMarked, int64(size))`によってマークされたバイト数がグローバルな`bytesMarked`カウンタに加算されます。

このコミットの核心的な変更は、以下の行です。
`gcw := &getg().m.p.ptr().gcw`
`gcw.scanWork += int64(scanSize)`

ここで、現在のゴルーチン（`getg()`）が実行されているP（プロセッサ）に関連付けられたGCワーカー（`gcw`）を取得し、その`gcw.scanWork`に、新しく割り当てられたオブジェクトの`scanSize`を加算しています。これにより、ブラックアロケーションされたオブジェクトのスキャン作業量が、GCの全体的なスキャン作業量に正確に反映されるようになります。

### `gcControllerState`と`gcMark`の変更

`src/runtime/mgc.go`の`gcControllerState`構造体には、`scanWork`フィールドのコメントが更新され、このフィールドが「サイクル中に実行された合計スキャン作業量」だけでなく、「サイクル終了時点での、保持されているヒープのうちスキャン可能な量」も表すようになったことが明記されています。これは、ブラックアロケーションが`scanWork`に計上されるようになった結果、その意味合いが拡張されたことを示しています。

また、`gcMark`関数内のマーク終了処理において、各PのGCワーカー（`gcw`）が、マーク終了時に`scanWork`や`bytesMarked`に未フラッシュの統計情報を持っていないことを確認する`throw`（パニック）が追加されました。これは、GCワーカーがそのサイクルで完了した作業を適切に報告していることを保証するための健全性チェックです。

## コアとなるコードの解説

### `src/runtime/malloc.go`

*   `var scanSize uintptr` の追加: 新しく割り当てられるオブジェクトのスキャン対象となるサイズを保持するための変数が導入されました。
*   `scanSize` の計算: `typ.ptrdata`（ポインタを含むデータのサイズ）に基づいて`scanSize`が計算されます。配列の場合など、オブジェクトの実際のサイズとポインタデータのサイズが異なる場合があるため、より正確なスキャンサイズを決定しています。
*   `c.local_scan += scanSize`: 計算された`scanSize`が、現在のP（プロセッサ）に紐づくGCワーカーのローカルなスキャン作業量カウンタ`c.local_scan`に加算されます。これは、GCワーカーが実際にスキャンしたと見なされる作業量を反映します。
*   `gcmarknewobject_m` の呼び出し変更: `gcmarknewobject_m`関数が呼び出される際に、オブジェクトのベースアドレス（`uintptr(x)`）、合計サイズ（`size`）に加えて、新しく計算された`scanSize`も引数として渡されるようになりました。これにより、`gcmarknewobject_m`内でブラックアロケーションのスキャン作業量を正確に計上できるようになります。

### `src/runtime/mgc.go`

*   `gcControllerState.scanWork` のコメント更新: `scanWork`フィールドの役割が拡張され、単に「サイクル中に実行された合計スキャン作業量」だけでなく、「サイクル終了時点での、保持されているヒープのうちスキャン可能な量」も意味するようになったことが明記されました。これは、ブラックアロケーションが`scanWork`に計上されるようになったことによる、このメトリクスの意味合いの変化を反映しています。
*   `gcMark` 関数内の健全性チェックの追加: `gcMark`のマーク終了フェーズにおいて、各PのGCワーカー（`gcw`）が、`empty()`（キューが空であること）、`scanWork != 0`、`bytesMarked != 0` のいずれかの条件を満たさない場合に`throw`（パニック）するチェックが追加されました。これは、GCワーカーがそのサイクルで処理すべき作業をすべて完了し、統計情報が適切にフラッシュされていることを保証するためのものです。これにより、GCの状態の一貫性が保たれます。

### `src/runtime/mgcmark.go`

*   `gcmarknewobject_m` 関数のシグネチャ変更: `func gcmarknewobject_m(obj, size uintptr)` から `func gcmarknewobject_m(obj, size, scanSize uintptr)` へと変更され、`scanSize`引数が追加されました。
*   `gcw.scanWork += int64(scanSize)` の追加: この行がこのコミットの最も重要な変更点です。
    *   `getg().m.p.ptr().gcw`: 現在実行中のゴルーチン（`getg()`）から、そのゴルーチンが実行されているM（OSスレッド）、P（プロセッサ）、そしてPに紐づくGCワーカー（`gcw`）のポインタを取得しています。
    *   `gcw.scanWork += int64(scanSize)`: 取得したGCワーカーの`scanWork`カウンタに、新しく割り当てられたオブジェクトの`scanSize`を加算しています。これにより、ブラックアロケーションされたオブジェクトが、GCの全体的なスキャン作業量に適切に貢献するようになります。この加算は、オブジェクトが黒くマークされると同時に行われるため、GCの計測がより正確になります。

これらの変更により、GoのGCはブラックアロケーションをより正確に追跡し、次回のGCの計画をより効果的に立てることができるようになります。これは、特に将来的にGoのGCが常にブラックアロケーションを行うようになる場合に、GCのパフォーマンスと安定性を維持するために不可欠な修正です。

# [インデックス 27949] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における「スキャン作業量 (scan work)」の計算方法を修正するものです。具体的には、GC中に「ブラック (black)」として割り当てられたオブジェクト（ブラックアロケーション）を、スキャン作業量に含めるように変更しています。これにより、GCの動作の一貫性が向上し、将来的にGoのGCが常にブラックアロケーションを行うようになる際の準備となります。

## 元コミット内容

Goランタイムにおいて、ブラックとして割り当てられたオブジェクト（ブラックアロケーション）は、スキャン可能なヒープサイズには計上されるものの、これまでに実行されたスキャン作業量には計上されていませんでした。これは、これらのオブジェクトが実質的にスキャン済みであり、再度スキャンされることがないという事実と矛盾していました。さらに悪いことに、この不整合は、次回のGCにおけるスキャン可能なヒープサイズが、現在のGCサイクルで実行されたスキャン作業量に基づいて計算されるため、ブラックアロケーションが適切に考慮されないという問題を引き起こしていました。

このコミットは、ブラックアロケーションをスキャン作業量として計上することで、この問題を修正します。現状では、GCが「allocate-blackモード」で費やす時間は非常に短いため、この問題が顕在化することは少なかったと考えられます。しかし、将来的にGoのGCが常にブラックアロケーションを行うように変更される際には、この修正が非常に重要になります。

## 変更の背景

Goのガベージコレクションは、並行マーク＆スイープ方式を採用しており、その効率性を高めるために様々な最適化が施されています。このコミットの背景には、GCの「スキャン作業量」の正確な計測と、将来的なGC戦略の変更への準備があります。

GoのGCは、ヒープの成長率に基づいて次回のGCのタイミングを決定します。この決定には、前回のGCサイクルでどれだけの「スキャン作業」が行われたかが重要な指標となります。スキャン作業量が多いほど、GCはより多くのオブジェクトを処理したと見なされ、次回のGCまでの期間が調整されます。

しかし、これまでの実装では、GC中に新しく割り当てられたオブジェクトが「ブラック」としてマークされた場合（ブラックアロケーション）、そのオブジェクトは既にスキャン済みと見なされるにもかかわらず、スキャン作業量には加算されていませんでした。これは以下の問題を引き起こしていました。

1.  **不整合**: 既にスキャンされたオブジェクトがスキャン作業量に計上されないのは論理的に不整合です。
2.  **次回のGCへの影響**: スキャン作業量の不正確な計上は、次回のGCのトリガータイミングやヒープサイズの推定に影響を与え、GCの効率を低下させる可能性がありました。特に、次回のGCの目標ヒープサイズは、現在のGCサイクルでスキャンされたヒープサイズに基づいて決定されるため、ブラックアロケーションが考慮されないと、目標ヒープサイズが過小評価される恐れがありました。
3.  **将来のGC戦略**: GoのGCは、パフォーマンス向上のために「常にブラックアロケーションを行う」方向へと進化する計画がありました。この戦略が導入された場合、ブラックアロケーションがスキャン作業量に計上されないという現在の問題は、GCの動作全体に深刻な影響を及ぼすことになります。

このコミットは、これらの問題を解決し、GCの計測をより正確にすることで、現在のGCの安定性を向上させるとともに、将来のGC戦略変更への道を開くものです。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションの基本的な概念と、特に「三色マーキング (Tri-color marking)」アルゴリズムに関する知識が必要です。

### Goのガベージコレクション (GC)

GoのGCは、並行（concurrent）かつ低遅延（low-latency）なマーク＆スイープ方式を採用しています。これは、アプリケーションの実行と並行してGC処理の一部を進めることで、アプリケーションの一時停止時間（Stop-The-World, STW）を最小限に抑えることを目指しています。

GCの主要なフェーズは以下の通りです。

1.  **マークフェーズ (Mark Phase)**:
    *   **マーク開始 (Mark Start)**: 短いSTWが発生し、GCが開始されます。ルートオブジェクト（グローバル変数、スタック上の変数など）が特定され、GCワーカーが起動します。
    *   **並行マーク (Concurrent Mark)**: アプリケーションの実行と並行して、GCワーカーが到達可能なオブジェクトをマークしていきます。この際、三色マーキングアルゴリズムが使用されます。
    *   **マーク終了 (Mark Termination)**: 短いSTWが発生し、並行マーク中に発生した変更（ミューテータがオブジェクトグラフを変更したこと）を処理し、マークフェーズを完了します。

2.  **スイープフェーズ (Sweep Phase)**:
    *   **並行スイープ (Concurrent Sweep)**: マークされなかったオブジェクト（到達不可能と判断されたオブジェクト）が解放され、ヒープメモリが再利用可能になります。これはアプリケーションの実行と並行して行われます。

### 三色マーキング (Tri-color marking) アルゴリズム

三色マーキングは、並行GCで広く用いられるアルゴリズムです。オブジェクトは以下の3つの色のいずれかの状態を持ちます。

*   **白 (White)**: まだGCによって到達可能かどうかが確認されていないオブジェクト。GCサイクルの開始時には、すべてのオブジェクトが白です。最終的に白のままのオブジェクトは、到達不可能と判断され、スイープフェーズで回収されます。
*   **灰 (Gray)**: GCによって到達可能であるとマークされたが、そのオブジェクトが参照している他のオブジェクト（子オブジェクト）がまだスキャンされていない状態のオブジェクト。GCワーカーは灰色のオブジェクトをスキャンし、その子オブジェクトを灰色にマークし、自身を黒色に遷移させます。
*   **黒 (Black)**: GCによって到達可能であるとマークされ、かつそのオブジェクトが参照しているすべての子オブジェクトもスキャン済み（または灰色/黒色）である状態のオブジェクト。黒色のオブジェクトは、GCサイクル中に回収されることはありません。

### ブラックアロケーション (Black Allocations)

通常のGCサイクル中、新しいオブジェクトが割り当てられると、最初は「白」として扱われます。しかし、GoのGCには、特定の条件下で新しく割り当てられたオブジェクトを最初から「黒」としてマークする「allocate-blackモード」が存在します。

これは主に、GCのマークフェーズ中に新しいオブジェクトが作成された場合に、そのオブジェクトがGCによって見落とされないようにするための最適化です。もし新しいオブジェクトが白として割り当てられ、かつGCがそのオブジェクトに到達する前に、そのオブジェクトへの唯一の参照が失われた場合、そのオブジェクトは誤って回収されてしまう可能性があります（これは「Dijkstraの三色マーキングの不変条件」を破ることに繋がります）。

allocate-blackモードでは、新しく割り当てられたオブジェクトは即座に黒としてマークされます。これにより、そのオブジェクトは現在のGCサイクルでは回収されず、次回のGCサイクルで改めて評価されることになります。これは、GCの正確性を保証しつつ、ミューテータ（アプリケーションコード）がオブジェクトを自由に操作できるようにするための重要なメカニズムです。

### スキャン作業量 (Scan Work)

GoのGCは、ヒープの成長を監視し、次回のGCをいつトリガーするかを決定するために、様々なメトリクスを使用します。その一つが「スキャン作業量 (scan work)」です。

スキャン作業量とは、GCがオブジェクトグラフを辿り、ポインタをスキャンするために費やした作業の量をバイト単位で表したものです。これは、GCがどれだけのメモリを「検査」したかを示す指標であり、次回のGCの目標ヒープサイズを計算する際の重要な入力となります。具体的には、`gcControllerState.scanWork`というフィールドで管理されており、GCサイクル中に原子的に更新されます。

このコミット以前は、ブラックアロケーションされたオブジェクトは、そのオブジェクト自体がスキャン可能であるにもかかわらず、この`scanWork`には計上されていませんでした。

## 技術的詳細

このコミットの技術的な核心は、`gcmarknewobject_m`関数と、`mallocgc`関数における`scanSize`の計算および`gcw.scanWork`への加算です。

### `mallocgc`関数の変更

`mallocgc`関数は、Goプログラムがメモリを割り当てる際に呼び出される主要な関数です。この関数内で、新しく割り当てられるオブジェクトの「スキャンサイズ」が計算され、GCワーカーのローカルスキャン作業量に加算されるようになりました。

変更前は、`c.local_scan += typ.ptrdata`のように、オブジェクトのポインタデータサイズが直接`c.local_scan`に加算されていました。しかし、このコミットでは、`scanSize`という新しい変数が導入され、オブジェクトのポインタデータサイズ（または配列の場合の調整されたサイズ）が`scanSize`に格納されます。そして、この`scanSize`が`c.local_scan`に加算されます。

さらに重要な変更は、`gcmarknewobject_m`関数の呼び出しです。GCがマークフェーズ中であるか、`gcBlackenPromptly`が真である場合（つまり、オブジェクトを即座に黒くマークする必要がある場合）、`gcmarknewobject_m`が呼び出されます。変更前は`gcmarknewobject_m(uintptr(x), size)`のように`size`のみが渡されていましたが、変更後は`gcmarknewobject_m(uintptr(x), size, scanSize)`のように、計算された`scanSize`も引数として渡されるようになりました。

### `gcmarknewobject_m`関数の変更

`gcmarknewobject_m`関数は、新しく割り当てられたオブジェクトを黒くマークする役割を担います。この関数は、GCがマークフェーズ中であるか、`gcBlackenPromptly`フラグが設定されている場合に呼び出されます。

変更前は、この関数はオブジェクトのサイズ（`size`）のみを受け取っていました。変更後、`scanSize`という新しい引数を受け取るようになりました。

この関数内で、オブジェクトは`heapBitsForAddr(obj).setMarked()`によって黒くマークされ、`atomic.Xadd64(&work.bytesMarked, int64(size))`によってマークされたバイト数がグローバルな`bytesMarked`カウンタに加算されます。

このコミットの核心的な変更は、以下の行です。
`gcw := &getg().m.p.ptr().gcw`
`gcw.scanWork += int64(scanSize)`

ここで、現在のゴルーチン（`getg()`）が実行されているP（プロセッサ）に関連付けられたGCワーカー（`gcw`）を取得し、その`gcw.scanWork`に、新しく割り当てられたオブジェクトの`scanSize`を加算しています。これにより、ブラックアロケーションされたオブジェクトのスキャン作業量が、GCの全体的なスキャン作業量に正確に反映されるようになります。

### `gcControllerState`と`gcMark`の変更

`src/runtime/mgc.go`の`gcControllerState`構造体には、`scanWork`フィールドのコメントが更新され、このフィールドが「サイクル中に実行された合計スキャン作業量」だけでなく、「サイクル終了時点での、保持されているヒープのうちスキャン可能な量」も表すようになったことが明記されています。これは、ブラックアロケーションが`scanWork`に計上されるようになった結果、その意味合いが拡張されたことを示しています。

また、`gcMark`関数内のマーク終了処理において、各PのGCワーカー（`gcw`）が、マーク終了時に`scanWork`や`bytesMarked`に未フラッシュの統計情報を持っていないことを確認する`throw`（パニック）が追加されました。これは、GCワーカーがそのサイクルで完了した作業を適切に報告していることを保証するための健全性チェックです。

### `src/runtime/malloc.go`

*   `var scanSize uintptr` の追加: 新しく割り当てられるオブジェクトのスキャン対象となるサイズを保持するための変数が導入されました。
*   `scanSize` の計算: `typ.ptrdata`（ポインタを含むデータのサイズ）に基づいて`scanSize`が計算されます。配列の場合など、オブジェクトの実際のサイズとポインタデータのサイズが異なる場合があるため、より正確なスキャンサイズを決定しています。
*   `c.local_scan += scanSize`: 計算された`scanSize`が、現在のP（プロセッサ）に紐づくGCワーカーのローカルなスキャン作業量カウンタ`c.local_scan`に加算されます。これは、GCワーカーが実際にスキャンしたと見なされる作業量を反映します。
*   `gcmarknewobject_m` の呼び出し変更: `gcmarknewobject_m`関数が呼び出される際に、オブジェクトのベースアドレス（`uintptr(x)`）、合計サイズ（`size`）に加えて、新しく計算された`scanSize`も引数として渡されるようになりました。これにより、`gcmarknewobject_m`内でブラックアロケーションのスキャン作業量を正確に計上できるようになります。

### `src/runtime/mgc.go`

*   `gcControllerState.scanWork` のコメント更新: `scanWork`フィールドの役割が拡張され、単に「サイクル中に実行された合計スキャン作業量」だけでなく、「サイクル終了時点での、保持されているヒープのうちスキャン可能な量」も意味するようになったことが明記されました。これは、ブラックアロケーションが`scanWork`に計上されるようになったことによる、このメトリクスの意味合いの変化を反映しています。
*   `gcMark` 関数内の健全性チェックの追加: `gcMark`のマーク終了フェーズにおいて、各PのGCワーカー（`gcw`）が、`empty()`（キューが空であること）、`scanWork != 0`、`bytesMarked != 0` のいずれかの条件を満たさない場合に`throw`（パニック）するチェックが追加されました。これは、GCワーカーがそのサイクルで処理すべき作業をすべて完了し、統計情報が適切にフラッシュされていることを保証するためのものです。これにより、GCの状態の一貫性が保たれます。

### `src/runtime/mgcmark.go`

*   `gcmarknewobject_m` 関数のシグネチャ変更: `func gcmarknewobject_m(obj, size uintptr)` から `func gcmarknewobject_m(obj, size, scanSize uintptr)` へと変更され、`scanSize`引数が追加されました。
*   `gcw.scanWork += int64(scanSize)` の追加: この行がこのコミットの最も重要な変更点です。
    *   `getg().m.p.ptr().gcw`: 現在実行中のゴルーチン（`getg()`）から、そのゴルーチンが実行されているM（OSスレッド）、P（プロセッサ）、そしてPに紐づくGCワーカー（`gcw`）のポインタを取得しています。

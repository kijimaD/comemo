# [インデックス 24654] ファイルの概要

このコミットは、Go言語の`net`パッケージにおけるDNS逆引き（`LookupAddr`）の挙動を修正するものです。特に、Cgoを使用してDNS解決を行う際に、返されるDNS名が「ルート付きDNSパス」（末尾にドットが付く形式）になるように強制します。これにより、純粋なGo実装やGo 1.4以前の挙動との一貫性が保たれます。

## コミット

```
commit 18d27b2d754923854e05c3b37a2b799d9c063164
Author: Russ Cox <rsc@golang.org>
Date:   Tue Aug 18 22:19:58 2015 -0400

    net: force LookupAddr results to be rooted DNS paths when using cgo

    Go 1.4 and before have always returned DNS names with a trailing dot
    for reverse lookups, as they do for basically all other routines returning
    DNS names. Go 1.4 and before always implemented LookupAddr using
    pure Go (not C library calls).

    Go 1.5 added the ability to make a C library call to implement LookupAddr.
    Unfortunately the C library call returns a DNS name without a trailing dot
    (an unrooted name), meaning that if turn off cgo during make.bash then
    you still get the rooted name but with cgo on you get an unrooted name.
    The unrooted name is inconsistent with the pure Go implementation
    and with all previous Go releases, so change it to a rooted name.

    Fixes #12189.

    Reviewed-on: https://go-review.googlesource.com/13697
    Reviewed-by: Rob Pike <r@golang.org>
```

## 元コミット内容

Go 1.5で`net`パッケージの`LookupAddr`関数がCgo（Cライブラリ呼び出し）を使用して実装されるようになった際、Cライブラリが返すDNS名が末尾のドットを持たない「ルートなし名」となる問題が発生しました。これは、Go 1.4以前の純粋なGo実装や他のDNS関連ルーチンが常に末尾にドットを持つ「ルート付き名」を返していた挙動と矛盾していました。このコミットは、Cgoを使用した場合でも`LookupAddr`がルート付きDNS名を返すように修正し、一貫性を確保することを目的としています。

## 変更の背景

Go 1.5より前、Goの`net`パッケージはDNS逆引き（IPアドレスからホスト名への変換）を純粋なGoコードで実装していました。この実装では、`LookupAddr`を含むほとんどのDNS関連関数が、返されるDNS名の末尾に常にドット（`.`）を付けていました。これは、DNSの完全修飾ドメイン名（FQDN）がルートゾーン（`.`）で終わるという慣例に従ったものです。

しかし、Go 1.5で`LookupAddr`の実装にCgoが導入され、システムに存在するCライブラリ（例: `getnameinfo`）を利用できるようになりました。これにより、特定の環境下でのDNS解決のパフォーマンス向上や、より複雑なDNS設定への対応が期待されました。

問題は、Cライブラリが返すホスト名が、Goの純粋な実装とは異なり、末尾のドットを持たない形式であったことです。例えば、`google.com.`ではなく`google.com`が返されるといった状況です。この不一致は、GoアプリケーションがDNS名を処理する際に予期せぬ挙動を引き起こす可能性がありました。特に、DNS名を比較したり、特定の形式を期待する既存のコードにとっては互換性の問題となります。

このコミットは、この挙動の不一致を解消し、Cgoを使用した場合でもGoの従来の挙動（ルート付きDNS名を返す）を維持するために行われました。これは、Goの`net`パッケージ全体での一貫性を保ち、開発者がDNS名の形式について心配することなくコードを書けるようにするための重要な修正です。

## 前提知識の解説

### DNS (Domain Name System)

DNSは、インターネット上のコンピュータやサービスを識別するための階層的な分散型命名システムです。人間が覚えやすいドメイン名（例: `www.example.com`）を、コンピュータが理解できるIPアドレス（例: `192.0.2.1`）に変換する役割を担っています。

*   **正引き (Forward Lookup)**: ドメイン名からIPアドレスを検索すること。
*   **逆引き (Reverse Lookup)**: IPアドレスからドメイン名を検索すること。本コミットで扱われる`LookupAddr`は逆引きに該当します。

### 完全修飾ドメイン名 (FQDN: Fully Qualified Domain Name)

FQDNは、ホスト名とドメイン名を含む、インターネット上の特定のコンピュータまたはリソースの完全なドメイン名です。FQDNは常にルートドメイン（`.`）で終わると定義されています。例えば、`www.example.com.`はFQDNですが、`www.example.com`はFQDNではありません（ただし、多くのアプリケーションやユーザーは末尾のドットを省略して使用します）。DNSシステム内部では、この末尾のドットが重要であり、名前がルートゾーンからの絶対パスであることを示します。

### Cgo

Cgoは、GoプログラムからC言語のコードを呼び出すためのGoの機能です。これにより、Goの標準ライブラリでは提供されていないOS固有の機能や、既存のCライブラリをGoプログラムで利用できるようになります。`net`パッケージでは、DNS解決のためにシステムのCライブラリ（例: `libc`の`getaddrinfo`や`getnameinfo`）を利用するためにCgoが使用されることがあります。

### Goの`net`パッケージ

Goの標準ライブラリである`net`パッケージは、ネットワークI/Oのプリミティブを提供します。TCP/IP、UDP、ドメイン名解決（DNS）などの機能が含まれます。

*   `net.LookupAddr(addr string) ([]string, error)`: 指定されたIPアドレスの逆引きを行い、対応するホスト名のリストを返します。
*   `net.LookupCNAME(name string) (cname string, err error)`: 指定されたドメイン名のCNAME（Canonical Name）レコードを検索します。
*   `net.LookupMX(name string) ([]*MX, error)`: 指定されたドメイン名のMX（Mail Exchange）レコードを検索します。
*   `net.LookupNS(name string) ([]*NS, error)`: 指定されたドメイン名のNS（Name Server）レコードを検索します。
*   `net.LookupSRV(service, proto, name string) (cname string, addrs []*SRV, err error)`: 指定されたサービス、プロトコル、ドメイン名のSRV（Service）レコードを検索します。

これらの関数は、DNSクエリを実行し、その結果をGoのデータ構造にマッピングして返します。

## 技術的詳細

このコミットの核心は、`net`パッケージがDNS逆引きを行う際に、Cgoを使用するか純粋なGo実装を使用するかにかかわらず、一貫した結果（末尾にドットが付いたFQDN形式）を返すようにすることです。

Go 1.5で`LookupAddr`がCgo経由でCライブラリを呼び出すようになった際、Cライブラリの`getnameinfo`関数などが返すホスト名には、通常、末尾のドットが含まれていませんでした。これは、多くのOSのCライブラリが、ユーザーフレンドリーな表示のために末尾のドットを省略する傾向があるためです。しかし、Goの`net`パッケージは、DNSの仕様に厳密に従い、FQDNを返すことを意図していました。

この不一致を解消するため、`src/net/cgo_unix.go`内の`cgoLookupPTR`関数（Cgo経由で逆引きを行う内部関数）に修正が加えられました。具体的には、Cライブラリから取得したホスト名（バイトスライス`b`として表現される）の末尾がドットで終わっていない場合、明示的にドットを追加するロジックが挿入されました。

```go
 	// Add trailing dot to match pure Go reverse resolver
 	// and all other lookup routines. See golang.org/issue/12189.
 	if len(b) > 0 && b[len(b)-1] != '.' {
 		b = append(b, '.')
 	}
```
このコードスニペットは、取得したDNS名が空でなく、かつ最後の文字がドットでない場合に、バイトスライス`b`の末尾にドットを追加しています。これにより、Cgo経由で解決されたDNS名も、純粋なGo実装と同様にルート付きDNSパスとして返されるようになります。

また、この変更の検証のために、`src/net/lookup_test.go`に`TestLookupDots`という新しいテスト関数が追加されました。このテストは、`LookupAddr`だけでなく、`LookupCNAME`、`LookupMX`、`LookupNS`、`LookupSRV`といった他のDNS関連関数についても、返されるDNS名が末尾にドットを持っていることを確認します。これにより、`net`パッケージ全体でDNS名の形式の一貫性が保証されます。

テストの実行環境を制御するために、`src/net/unix_test.go`と新しく追加された`src/net/non_unix_test.go`には、`forceGoDNS`と`forceCgoDNS`というヘルパー関数が導入されました。これらは、テスト中にDNS解決を純粋なGo実装に強制したり、Cgo実装に強制したりするためのもので、異なるDNS解決メカニズム下での挙動を検証するために使用されます。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/net/cgo_unix.go`内の`cgoLookupPTR`関数に追加された以下の5行です。

```go
 	// Add trailing dot to match pure Go reverse resolver
 	// and all other lookup routines. See golang.org/issue/12189.
 	if len(b) > 0 && b[len(b)-1] != '.' {
 		b = append(b, '.')
 	}
```

1.  **`if len(b) > 0 && b[len(b)-1] != '.'`**:
    *   `len(b) > 0`: これは、Cライブラリから返されたDNS名（バイトスライス`b`）が空でないことを確認します。空の文字列に対して操作を行うとパニックが発生する可能性があるため、このチェックは重要です。
    *   `b[len(b)-1] != '.'`: これは、DNS名の最後の文字が既にドットでないことを確認します。もし既にドットが付いている場合、二重にドットを追加するのを防ぎます。
    *   この条件が両方とも真である場合、つまり、DNS名が空ではなく、かつ末尾にドットがない場合にのみ、次の行の処理が実行されます。

2.  **`b = append(b, '.')`**:
    *   `append`関数は、Goのスライスに要素を追加するために使用されます。ここでは、バイトスライス`b`の末尾にASCIIコードのドット（`.`）を追加しています。
    *   この操作により、Cgo経由で取得されたDNS名が、Goの純粋な実装やGo 1.4以前の挙動と一貫性のある「ルート付きDNSパス」形式になります。

このシンプルな追加により、`net`パッケージの`LookupAddr`関数は、Cgoを使用しているかどうかにかかわらず、常に末尾にドットを持つFQDN形式のホスト名を返すようになります。これにより、Goのネットワークスタック全体での一貫性が保たれ、開発者はDNS名の形式について一貫した期待を持つことができます。

テストコードの追加も重要です。`TestLookupDots`は、`LookupAddr`だけでなく、`LookupCNAME`、`LookupMX`、`LookupNS`、`LookupSRV`といった他のDNS関連関数も対象に、返されるDNS名が末尾にドットを持つことを確認します。これは、単一の関数だけでなく、`net`パッケージ全体でDNS名の形式に関する一貫性を保証するための包括的なアプローチを示しています。`forceGoDNS`と`forceCgoDNS`は、テストの信頼性を高めるために、特定のDNS解決メカニズムを強制するメカニズムを提供します。

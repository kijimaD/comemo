## 変更の背景

Goコンパイラは、プログラムの最適化のためにSSA（Static Single Assignment）形式の中間表現を使用します。SSA形式では、各変数が一度だけ代入されるため、データフロー解析や最適化が容易になります。多くの最適化パス（共通部分式除去、デッドコード除去、nilチェック除去など）は、プログラムの制御フローグラフ（Control Flow Graph: CFG）におけるドミネータ関係に依存します。

ドミネータツリーは、CFG内の各ブロックがどのブロックによって支配されているかを示すデータ構造です。このツリーは、特定の最適化を実行するために頻繁に計算されます。以前のGoコンパイラでは、各最適化パスが必要に応じてドミネータツリーを個別に計算していました。これは冗長であり、コンパイル時間の増加につながる可能性がありました。

このコミットの「前のCL」（Change List、つまり先行するコミット）では、複数の最適化パスで共有できる単一のドミネータツリーを計算する`domTree`パスが導入されました。これにより、ドミネータツリーの計算を一度だけ行い、その結果を複数のパスで再利用することで、コンパイル効率を向上させることを目的としていました。

しかし、その先行するCLにおいて、共通部分式除去（CSE）パスがこの共有ドミネータツリーを利用するように更新されていませんでした。このコミットは、その見落としを修正し、CSEパスも共有ドミネータツリー（具体的には`f.sdom`フィールド）を使用するように変更することで、コンパイラの整合性と効率性をさらに高めることを目的としています。

## 前提知識の解説

### 1. SSA (Static Single Assignment)

SSAは、コンパイラの中間表現（IR）の一種で、プログラム中の各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、最適化の機会が増えます。例えば、`x = a + b; y = x * 2; x = c + d; z = x / 2;`のようなコードは、SSA形式では`x1 = a + b; y = x1 * 2; x2 = c + d; z = x2 / 2;`のように変換され、各`x`の定義が明確になります。Goコンパイラでは、ソースコードが抽象構文木（AST）からSSA形式に変換され、様々な最適化が適用されます。

### 2. ドミネータツリー (Dominator Tree)

ドミネータツリーは、制御フローグラフ（CFG）の重要な特性を表現するデータ構造です。CFGにおいて、あるブロックAがブロックBを「支配する（dominate）」とは、CFGの開始ブロックからブロックBへのすべてのパスがブロックAを通過する場合を指します。ドミネータツリーでは、各ノード（CFGのブロック）の親ノードは、そのノードを直接支配するブロック（immediate dominator）になります。

ドミネータツリーは、以下のような最適化に不可欠です。
*   **共通部分式除去 (CSE)**: ある式が計算された後、その結果がまだ有効な範囲内で同じ式が再度計算される場合、最初の結果を再利用できます。ドミネータ関係は、式の値が変更されていないことを保証するために重要です。
*   **ループ不変コード移動 (Loop Invariant Code Motion)**: ループ内で常に同じ値を生成する計算をループの外に移動させ、冗長な計算を避けます。
*   **デッドコード除去 (Dead Code Elimination)**: 到達不能なコードや、その結果が使用されない計算を削除します。

### 3. 共通部分式除去 (Common Subexpression Elimination: CSE)

CSEは、コンパイラの最適化手法の一つで、同じ式が複数回計算され、かつその間にオペランドが変更されていない場合に、その式の計算を一度だけ行い、結果を再利用することで冗長な計算を排除します。

例:
```go
a = b * c + d
e = b * c + f
```
このコードでは、`b * c`という式が2回計算されています。CSEを適用すると、`b * c`の計算結果を一時変数に格納し、それを再利用することで、以下のように最適化できます。
```go
temp = b * c
a = temp + d
e = temp + f
```
CSEは、式の値が変更されていないことを保証するために、ドミネータツリーによって提供される情報（特に、ある式の計算結果が、その式が再利用される場所まで「生きている」かどうか）に依存します。

### 4. Goコンパイラの `ssa` パッケージ

`src/cmd/compile/internal/ssa`パッケージは、Goコンパイラのバックエンドの一部であり、GoプログラムのSSA中間表現を構築し、それに対して様々な最適化を適用する役割を担っています。このパッケージ内には、SSA形式の関数を表す`Func`構造体や、最適化パスを定義する`pass`構造体などが含まれています。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSA最適化パスの実行順序と、ドミネータツリーの利用方法の変更にあります。

以前の`cse`パスは、自身の内部でドミネータツリー（`idom`と`sdom`）を計算していました。これは、他のパスも同様にドミネータツリーを計算している場合、冗長な計算が発生することを意味します。

このコミットでは、以下の変更が行われました。

1.  **`domTree`パスの導入と順序変更**:
    `src/cmd/compile/internal/ssa/compile.go`内の`passes`配列は、SSA最適化パスの実行順序を定義しています。このコミットでは、`generic cse`パスの前に`generic domtree`パスが配置されるように変更されました。これにより、`domTree`パスが一度だけドミネータツリーを計算し、その結果を`Func`構造体（具体的には`f.sdom`フィールド）に格納するようになります。

2.  **`cse`パスからのドミネータツリー計算の削除**:
    `src/cmd/compile/internal/ssa/cse.go`内の`cse`関数から、ドミネータツリーを計算する以下の行が削除されました。
    ```go
    // Compute dominator tree
    idom := dominators(f)
    sdom := newSparseTree(f, idom)
    ```
    これにより、`cse`パスはドミネータツリーを自身で計算するのではなく、`domTree`パスによって既に計算され`f.sdom`に格納されている共有ドミネータツリーを利用するようになります。

3.  **共有ドミネータツリー (`f.sdom`) の利用**:
    `cse`関数内でドミネータ関係をチェックする箇所（`sdom.isAncestorEq`の呼び出し）が、`f.sdom.isAncestorEq`に変更されました。これは、`Func`構造体`f`に格納されている共有のスパースドミネータツリー（sparse dominator tree）を利用することを意味します。

4.  **パス間の依存関係の明示**:
    `src/cmd/compile/internal/ssa/compile.go`内の`passOrder`配列は、パス間の依存関係を定義しています。このコミットでは、`cse`パスが`domTree`パスに依存することを明示するために、以下の制約が追加されました。
    ```go
    {"generic domtree", "generic cse"},
    ```
    これにより、`generic cse`が実行される前に`generic domtree`が必ず実行されることが保証されます。

これらの変更により、ドミネータツリーの計算が一度だけ行われ、その結果が複数の最適化パス（CSE、nilチェック除去、証明、ループ境界チェック除去など）で効率的に再利用されるようになります。

### `src/cmd/compile/internal/ssa/compile.go` の変更

*   **パスの順序変更**: `passes`配列は、GoコンパイラのSSAバックエンドで実行される最適化パスのリストを定義しています。`{name: "generic domtree", fn: domTree}`が`{name: "generic cse", fn: cse}`の前に移動されたことで、`cse`パスが実行される前に必ず`domTree`パスが実行され、共有ドミネータツリーが構築されることが保証されます。

これらの変更は、GoコンパイラのSSAバックエンドにおける最適化パスのモジュール性と効率性を向上させるための重要なステップです。ドミネータツリーの計算を一元化し、複数のパスで共有することで、コンパイル時間の短縮とコードの保守性の向上が期待されます。

SSAは、コンパイラの中間表現（IR）の一種で、プログラム中の各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、最適化の機会が増えます。例えば、`x = a + b; y = x * 2; x = c + d; z = x / 2;`のようなコードは、SSA形式では`x1 = a + b; y = x1 * 2; x2 = c + d; z = x2 / 2;`のように変換され、各`x`の定義が明確になります。Goコンパイラでは、ソースコードが抽象構文木（AST）からSSA形式に変換され、様々な最適化が適用されます。

### 2. ドミネータツリー (Dominator Tree)

ドミネータツリーは、制御フローグラフ（CFG）の重要な特性を表現するデータ構造です。CFGにおいて、あるブロックAがブロックBを「支配する（dominate）」とは、CFGの開始ブロックからブロックBへのすべてのパスがブロックAを通過する場合を指します。ドミネータツリーでは、各ノード（CFGのブロック）の親ノードは、そのノードを直接支配するブロック（immediate dominator）になります。

ドミネータツリーは、以下のような最適化に不可欠です。
*   **共通部分式除去 (CSE)**: ある式が計算された後、その結果がまだ有効な範囲内で同じ式が再度計算される場合、最初の結果を再利用できます。ドミネータ関係は、式の値が変更されていないことを保証するために重要です。
*   **ループ不変コード移動 (Loop Invariant Code Motion)**: ループ内で常に同じ値を生成する計算をループの外に移動させ、冗長な計算を避けます。
*   **デッドコード除去 (Dead Code Elimination)**: 到達不能なコードや、その結果が使用されない計算を削除します。

### 3. 共通部分式除去 (Common Subexpression Elimination: CSE)

CSEは、コンパイラの最適化手法の一つで、同じ式が複数回計算され、かつその間にオペランドが変更されていない場合に、その式の計算を一度だけ行い、結果を再利用することで冗長な計算を排除します。

例:
```go
a = b * c + d
e = b * c + f
```
このコードでは、`b * c`という式が2回計算されています。CSEを適用すると、`b * c`の計算結果を一時変数に格納し、それを再利用することで、以下のように最適化できます。
```go
temp = b * c
a = temp + d
e = temp + f
```
CSEは、式の値が変更されていないことを保証するために、ドミネータツリーによって提供される情報（特に、ある式の計算結果が、その式が再利用される場所まで「生きている」かどうか）に依存します。

### 4. Goコンパイラの `ssa` パッケージ

`src/cmd/compile/internal/ssa`パッケージは、Goコンパイラのバックエンドの一部であり、GoプログラムのSSA中間表現を構築し、それに対して様々な最適化を適用する役割を担っています。このパッケージ内には、SSA形式の関数を表す`Func`構造体や、最適化パスを定義する`pass`構造体などが含まれています。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSA最適化パスの実行順序と、ドミネータツリーの利用方法の変更にあります。

以前の`cse`パスは、自身の内部でドミネータツリー（`idom`と`sdom`）を計算していました。これは、他のパスも同様にドミネータツリーを計算している場合、冗長な計算が発生することを意味します。

このコミットでは、以下の変更が行われました。

1.  **`domTree`パスの導入と順序変更**:
    `src/cmd/compile/internal/ssa/compile.go`内の`passes`配列は、SSA最適化パスの実行順序を定義しています。このコミットでは、`generic cse`パスの前に`generic domtree`パスが配置されるように変更されました。これにより、`domTree`パスが一度だけドミネータツリーを計算し、その結果を`Func`構造体（具体的には`f.sdom`フィールド）に格納するようになります。

2.  **`cse`パスからのドミネータツリー計算の削除**:
    `src/cmd/compile/internal/ssa/cse.go`内の`cse`関数から、ドミネータツリーを計算する以下の行が削除されました。
    ```go
    // Compute dominator tree
    idom := dominators(f)
    sdom := newSparseTree(f, idom)
    ```
    これにより、`cse`パスはドミネータツリーを自身で計算するのではなく、`domTree`パスによって既に計算され`f.sdom`に格納されている共有ドミネータツリーを利用するようになります。

3.  **共有ドミネータツリー (`f.sdom`) の利用**:
    `cse`関数内でドミネータ関係をチェックする箇所（`sdom.isAncestorEq`の呼び出し）が、`f.sdom.isAncestorEq`に変更されました。これは、`Func`構造体`f`に格納されている共有のスパースドミネータツリー（sparse dominator tree）を利用することを意味します。

4.  **パス間の依存関係の明示**:
    `src/cmd/compile/internal/ssa/compile.go`内の`passOrder`配列は、パス間の依存関係を定義しています。このコミットでは、`cse`パスが`domTree`パスに依存することを明示するために、以下の制約が追加されました。
    ```go
    {"generic domtree", "generic cse"},
    ```
    これにより、`generic cse`が実行される前に`generic domtree`が必ず実行されることが保証されます。

これらの変更により、ドミネータツリーの計算が一度だけ行われ、その結果が複数の最適化パス（CSE、nilチェック除去、証明、ループ境界チェック除去など）で効率的に再利用されるようになります。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/compile.go` の変更

*   **パスの順序変更**: `passes`配列は、GoコンパイラのSSAバックエンドで実行される最適化パスのリストを定義しています。`{name: "generic domtree", fn: domTree}`が`{name: "generic cse", fn: cse}`の前に移動されたことで、`cse`パスが実行される前に必ず`domTree`パスが実行され、共有ドミネータツリーが構築されることが保証されます。
*   **依存関係の追加**: `passOrder`配列は、特定のパスが他のパスの前に実行される必要があるという制約を定義します。`{"generic domtree", "generic cse"}`の追加は、`generic cse`パスが正しく機能するために`generic domtree`パスによって計算されたドミネータツリーが必要であることを明示しています。これは、コンパイラのパススケジューリングにおいて重要な情報となります。

### `src/cmd/compile/internal/ssa/cse.go` の変更

*   **ドミネータツリー計算の削除**: 以前の`cse`関数は、`idom := dominators(f)`と`sdom := newSparseTree(f, idom)`を呼び出して、自身のドミネータツリーを計算していました。このコミットではこれらの行が削除され、`cse`パスがドミネータツリーの計算責任を持たなくなりました。これにより、冗長な計算が排除されます。
*   **共有ドミネータツリーの利用**: `cse`関数内の`sdom.isAncestorEq`の呼び出しは、`f.sdom.isAncestorEq`に変更されました。`f`は現在のSSA関数を表す`Func`構造体であり、`f.sdom`は`domTree`パスによって計算され、`Func`構造体に格納された共有のスパースドミネータツリーです。この変更により、CSEは共有されたドミネータ情報を使用して、共通部分式の有効性を判断するようになります。

### `src/cmd/compile/internal/ssa/cse_test.go` の変更

*   **テストケースへの`domTree`呼び出しの追加**: `TestCSEAuxPartitionBug`というテスト関数に`domTree(fun.f)`が追加されました。これは、`cse(fun.f)`が呼び出される前に、テスト環境においても`domTree`パスが実行され、`fun.f`（テスト対象のSSA関数）の`sdom`フィールドが適切に初期化されていることを保証するためです。これにより、テストが実際のコンパイラの実行フローをより正確に模倣し、`cse`パスが共有ドミネータツリーを正しく利用していることを検証できます。

これらの変更は、GoコンパイラのSSAバックエンドにおける最適化パスのモジュール性と効率性を向上させるための重要なステップです。ドミネータツリーの計算を一元化し、複数のパスで共有することで、コンパイル時間の短縮とコードの保守性の向上が期待されます。

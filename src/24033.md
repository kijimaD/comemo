## 変更の背景

Goのビルドプロセスにおいて、`-ldflags="-X package.name=value"` というリンカフラグを使用することで、コンパイル時に特定の文字列変数の値を上書きすることができます。これは、ビルドバージョン情報や設定値などを埋め込む際によく利用される機能です。

しかし、この機能は本来文字列変数に対してのみ意図されていました。以前の実装では、`-X` フラグが文字列型ではない変数（例えば `bool` や `int`）に対して使用された場合でも、リンカはエラーを報告せず、予期せぬ動作やクラッシュを引き起こす可能性がありました。

このコミットは、この潜在的な問題を解決するために導入されました。コミットメッセージに記載されている `Fixes #9621` は、この問題がGoのイシュートラッカーで報告されたことを示唆していますが、現在のところ、この特定のイシュー番号に関する公開情報は確認できませんでした。しかし、変更内容から、リンカが誤った型の変数に`-X`フラグを適用しようとした際に、早期に問題を検出し、明確なエラーメッセージを開発者に提供することが目的であることが明らかです。

## 前提知識の解説

### Goリンカ (`cmd/link`)

Goリンカは、Goコンパイラによって生成されたオブジェクトファイル（`.o` ファイル）を結合し、実行可能なバイナリを生成するツールです。Goプログラムのビルドチェーンの最終段階を担います。リンカは、シンボル解決、メモリレイアウトの決定、デバッグ情報の埋め込みなど、様々な重要なタスクを実行します。

### `-X` リンカフラグ

`-X` フラグは、Goリンカに渡される `ldflags` の一部として使用され、コンパイル時にGoプログラム内のグローバル文字列変数の値を変更するために使われます。書式は `-X package.name=value` です。例えば、`go build -ldflags="-X main.Version=1.0.0"` とすると、`main` パッケージ内の `Version` という名前の文字列変数の値が `"1.0.0"` に設定されます。

### シンボル (`LSym`)

Goリンカの内部では、プログラム内のすべての変数、関数、型などが「シンボル」として表現されます。`LSym` はリンカがこれらのシンボルを管理するための内部データ構造です。各シンボルは名前、型、サイズ、アドレスなどの情報を持っています。

### シンボルの型 (`obj.STEXT`, `obj.SNOPTRDATA`)

`LSym` 構造体には、シンボルの種類を示す `Type` フィールドがあります。
*   `obj.STEXT`: これはコードセクション（実行可能な命令）を表すシンボルです。つまり、関数やメソッドの本体です。
*   `obj.SNOPTRDATA`: これはポインタを含まないデータセクションを表すシンボルです。文字列や数値などの静的データがこれに該当します。

### `Gotype`

`LSym` 構造体には `Gotype` フィールドがあり、これはGoの型システムにおけるシンボルの型情報を指します。`Gotype.Name` は、そのGoの型の名前（例: `"type.string"`, `"type.int"`, `"type.bool"`) を保持します。この情報は、リンカがシンボルの型を識別するために使用されます。

## 技術的詳細

この変更の核心は、`-X` フラグによって上書きされるシンボルが、実際に文字列型であるかどうかを検証するメカニズムを導入することです。以前は、`addstrdata` 関数が `-X` フラグで指定されたシンボルを処理していましたが、その際にシンボルの型を厳密にチェックしていませんでした。

このコミットでは、以下の新しいロジックが導入されました。

1.  **`strdata` スライスの導入**: `addstrdata` 関数が処理したすべての `-X` 指定シンボル (`*LSym`) を一時的に `strdata` というグローバルスライスに格納します。
2.  **`checkstrdata` 関数の追加**: リンカのメイン処理 (`Ldmain`) の後半で、`checkstrdata` 関数が呼び出されます。この関数は `strdata` スライスに格納された各シンボルを反復処理し、その型を検証します。
3.  **型チェックロジック**:
    *   シンボルの `Type` が `obj.STEXT` (つまり関数) である場合、`-X` フラグで関数を上書きしようとしているためエラーとします。
    *   シンボルの `Gotype` が存在し、かつその `Gotype.Name` が `"type.string"` ではない場合、`-X` フラグで文字列型ではない変数を上書きしようとしているためエラーとします。
4.  **エラー報告**: 上記のいずれかの条件に合致した場合、`Diag` 関数を使用して診断メッセージ（エラー）を生成し、リンカの実行を停止します。

この変更により、リンカはビルド時に早期に問題を検出し、開発者に明確なエラーメッセージを提供できるようになります。これにより、デバッグが容易になり、予期せぬランタイムエラーを防ぐことができます。

## コアとなるコードの解説

### `data.go` の `checkstrdata` 関数

```go
func checkstrdata() {
    for _, s := range strdata { // -Xで指定されたすべてのシンボルをループ
        if s.Type == obj.STEXT { // シンボルがテキストセクション（関数）の場合
            Diag("cannot use -X with text symbol %s", s.Name) // エラーを報告
        } else if s.Gotype != nil && s.Gotype.Name != "type.string" { // シンボルが文字列型ではない場合
            Diag("cannot use -X with non-string symbol %s", s.Name) // エラーを報告
        }
    }
}
```

この関数は、`-X` フラグによって上書き対象として指定されたすべてのシンボル (`strdata` スライスに格納されているもの) を検査します。

1.  `if s.Type == obj.STEXT`:
    *   これは、`-X` フラグが関数（コードセクション）を指している場合に真となります。`-X` はデータ変数の値を変更するためのものであり、関数のコードを変更するものではないため、これは不正な使用方法です。リンカは `cannot use -X with text symbol %s` というエラーメッセージを出力します。
2.  `else if s.Gotype != nil && s.Gotype.Name != "type.string"`:
    *   これは、シンボルがテキストセクションではないが、そのGoの型が文字列型 (`"type.string"`) ではない場合に真となります。例えば、`bool` 型や `int` 型の変数に `-X` で値を設定しようとした場合がこれに該当します。リンカは `cannot use -X with non-string symbol %s` というエラーメッセージを出力します。

これらのチェックにより、`-X` フラグの誤用が早期に検出され、ビルドプロセス中に開発者にフィードバックが提供されるようになります。

### `pobj.go` の `Ldmain` 関数への `checkstrdata` の追加

`Ldmain` はGoリンカのエントリポイントとなる主要な関数です。この関数内で `checkstrdata()` が呼び出されるタイミングは重要です。`checkgo()` の後、`deadcode()` や `callgraph()` の前に呼び出されることで、シンボル情報が完全に解決され、かつ不要なシンボルが削除される前に型チェックが実行されることが保証されます。これにより、リンカは正確な型情報に基づいて検証を行うことができます。

## 変更の背景

この変更は、`cl/11834` での議論やコメントに基づいて行われました。`src/internal/trace/parser.go` では、トレースイベントを時間順にソートする際に `sort.Stable` 関数が使用されています。しかし、なぜ通常の `sort.Sort` ではなく `sort.Stable` が選ばれているのかについての説明がコード中にありませんでした。

## 前提知識の解説

### Go言語のトレースツール (`internal/trace`)

Go言語には、プログラムの実行状況を詳細に記録・可視化するためのプロファイリングおよびトレースツールが組み込まれています。`go tool trace` コマンドを通じて利用でき、Goランタイムが生成するイベント（ガーベージコレクション、ゴルーチンライフサイクル、システムコールなど）を収集し、グラフィカルに表示します。
`src/internal/trace` パッケージは、このトレースデータの生成、収集、そして解析の中核を担う内部パッケージです。`parser.go` は、収集された生データを解析し、意味のあるイベントオブジェクトのリストに変換する部分です。

### 安定ソート (Stable Sort) と不安定ソート (Unstable Sort)

ソートアルゴリズムには、安定ソートと不安定ソートの2種類があります。

*   **安定ソート (Stable Sort)**: ソートキーが同じ要素の相対的な順序が、ソート後も保持されるソートアルゴリズムです。例えば、`[(A, 1), (B, 2), (C, 1)]` をキーでソートする場合、安定ソートでは `[(A, 1), (C, 1), (B, 2)]` のように、キーが `1` の `A` と `C` の元の順序が保たれます。
*   **不安定ソート (Unstable Sort)**: ソートキーが同じ要素の相対的な順序が、ソート後に保持される保証がないソートアルゴリズムです。上記の例では、`[(C, 1), (A, 1), (B, 2)]` のようになる可能性もあります。

Go言語の標準ライブラリ `sort` パッケージには、`sort.Sort` と `sort.Stable` の2つの主要なソート関数があります。
`sort.Sort` は一般的にクイックソートなどの不安定ソートアルゴリズムを使用し、高速ですが安定性は保証されません。
`sort.Stable` はマージソートなどの安定ソートアルゴリズムを使用し、`sort.Sort` よりもわずかに遅い場合がありますが、安定性が保証されます。

### CPUティックとリアルタイム

Goのトレースイベントは、CPUのタイムスタンプカウンター（TSC）などのハードウェアティックに基づいて記録されることがあります。これらのティックは非常に高精度ですが、直接的な時間単位ではありません。`parser.go` は、これらのCPUティックを実際の経過時間（ナノ秒など）に変換するために、`EvFrequency` イベントなどで記録された周波数情報を使用します。

## 技術的詳細

`src/internal/trace/parser.go` では、`parseEvents` 関数内で生イベントデータを `events` スライスに格納した後、`sort.Stable(eventList(events))` を呼び出してイベントを時間順にソートしています。

このコミットが追加したコメントは、なぜ `sort.Stable` がここで不可欠なのかを説明しています。
「Use stable sort because adjacent events in a batch can have the same timestamp (this was observed on some VMs).」

これは、以下の重要な技術的側面を指摘しています。

1.  **同一タイムスタンプのイベント**: トレースイベントは非常に短い時間間隔で発生するため、特に高負荷なシステムや、CPUティックの分解能が低い環境（一部の仮想マシンなど）では、複数のイベントが全く同じタイムスタンプを持つことがあります。
2.  **相対順序の重要性**: トレースイベントの解析において、同じタイムスタンプを持つイベント間の相対的な順序が意味を持つ場合があります。例えば、ある操作の開始イベントと終了イベントが同じタイムスタンプで記録された場合、開始イベントが終了イベントの前に来るべきという論理的な順序があります。不安定ソートを使用すると、これらのイベントの相対的な順序が入れ替わってしまう可能性があり、トレースの解釈を誤る原因となる可能性があります。
3.  **デバッグと可視化の正確性**: トレースツールは、プログラムの挙動を正確に可視化することが目的です。イベントの順序が不正確になると、タイムライン表示が混乱したり、因果関係が誤って解釈されたりする可能性があります。安定ソートは、このような問題を回避し、トレースデータの整合性を保つために不可欠です。

したがって、`sort.Stable` の使用は、トレースデータの正確な解析と表示を保証するための重要な設計上の決定であり、このコメントはその理由を明確にすることで、コードの堅牢性と理解度を高めています。

## コアとなるコードの解説

追加されたコメントは以下の通りです。

```go
	// Sort by time and translate cpu ticks to real time.
	// Use stable sort because adjacent events in a batch can have the same timestamp
	// (this was observed on some VMs).
	sort.Stable(eventList(events))
```

このコメントは、`parseEvents` 関数内でトレースイベントをソートする際に `sort.Stable` を使用する理由を明確にしています。

1.  `// Sort by time and translate cpu ticks to real time.`
    これは、続く処理がイベントを時間順にソートし、CPUティックを実際の時間に変換する目的であることを示しています。これは、トレースデータが時間軸に沿って意味を持つため、最も基本的な処理の一つです。

2.  `// Use stable sort because adjacent events in a batch can have the same timestamp`
    `sort.Stable` を使用する直接的な理由を述べています。複数のイベントが同じタイムスタンプを持つ可能性があるため、安定ソートが必要であると説明しています。これにより、同じタイムスタンプを持つイベント間の元の相対的な順序が保持されます。

3.  `// (this was observed on some VMs).`
    この要件が単なる理論上の懸念ではなく、実際に一部の仮想マシン環境で観測された具体的な問題に基づいていることを補足しています。これにより、この設計判断の根拠がより強固なものとなります。

このコメントは、コードの意図を明確にし、なぜ `sort.Stable` が `sort.Sort` よりも優先されるのかという疑問に答えることで、コードの可読性と保守性を向上させています。

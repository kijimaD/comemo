# [インデックス 2029] ファイルの概要

このコミットは、Go言語における配列からスライスへの変換規則の重要な変更と、`utf8.EncodeRuneToString`関数の削除を伴うものです。以前は配列をスライスに暗黙的に変換できましたが、この変更により明示的なアドレス演算子`&`の使用が必須となりました。これにより、Go言語の設計哲学である「明示性」がさらに強化されています。

## 変更の背景

このコミットの主な背景は、Go言語の設計哲学である「明示性 (explicitness)」をさらに推進することにあります。Go言語は、コードの読みやすさと予測可能性を重視しており、暗黙的な挙動を極力排除する傾向があります。

以前のGo言語では、配列をスライスに代入する際に、配列の先頭アドレスを暗黙的に取得し、それを基にスライスを作成する挙動がありました。具体的には、`var slice []byte; slice = arr;` のように書くと、コンパイラが内部的に `slice = &arr;` と解釈していました。この暗黙的なアドレス取得は、開発者にとって予期せぬ挙動や混乱を招く可能性がありました。例えば、配列が値型であるにもかかわらず、スライスへの代入が参照渡しのように振る舞うという誤解を生む可能性がありました。

この変更により、配列からスライスを作成する際には、明示的にアドレス演算子`&`を使用して配列のポインタを渡すことが必須となりました。これにより、コードの意図がより明確になり、配列が値型であり、スライスがその基盤となる配列への参照であることを開発者が意識しやすくなります。コミットメッセージにあるように、この変更によって残る暗黙的な`&`は、`.`演算子（構造体のフィールドアクセス）と`string(arr)`（バイト配列から文字列への変換）の場合のみとなり、言語全体の一貫性が向上しました。

また、`utf8.EncodeRuneToString`関数の削除と`string(rune)`への移行も、同様に言語の簡潔性と一貫性を追求したものです。`string()`変換は、Go言語において様々な型を文字列に変換するための汎用的なメカニズムであり、ルーン（Unicodeコードポイント）から文字列への変換もこのメカニズムに統合することで、APIの冗長性を排除し、より直感的な記述を可能にしています。

## 前提知識の解説

### Goにおける配列 (Arrays in Go)

Go言語における配列は、同じ型の要素を固定長で連続して格納するデータ構造です。配列の長さは型の一部であり、コンパイル時に決定されます。例えば、`var arr [10]byte`は10個の`byte`型要素を持つ配列を宣言します。配列は値型であり、代入や関数への引数として渡される際には、その内容全体がコピーされます。

```go
var arr [3]int = [3]int{1, 2, 3} // 長さ3のint型配列
var arr2 [3]int = arr             // arr2はarrのコピー
arr2[0] = 100                     // arr2を変更してもarrは変わらない
```

### Goにおけるスライス (Slices in Go)

Go言語におけるスライスは、配列の一部を参照する動的なデータ構造です。スライスは、基盤となる配列へのポインタ、長さ（`len`）、容量（`cap`）の3つの要素で構成されます。スライスは参照型のように振る舞い、スライスを介して基盤となる配列の要素を変更すると、その配列を参照する他のスライスからも変更が反映されます。

```go
var arr [5]int = [5]int{1, 2, 3, 4, 5}
slice := arr[1:4] // arrのインデックス1から3までを参照するスライス
// sliceは {2, 3, 4}
slice[0] = 99     // arrは {1, 99, 3, 4, 5} になる
```

### 配列からスライスへの変換 (Conversion from Array to Slice)

このコミット以前は、Go言語では配列を直接スライス型に代入することが可能でした。この際、コンパイラが暗黙的に配列の先頭アドレスを取得し、その配列全体を参照するスライスを作成していました。

**変更前:**
```go
var arr [10]byte
var slice []byte
slice = arr // 暗黙的に slice = &arr と解釈されていた
```

この挙動は、配列が値型であるというGoの原則と、スライスが参照型のように振る舞うという事実の間で、一部の混乱を招く可能性がありました。

**変更後:**
このコミットにより、配列からスライスを作成する際には、明示的にアドレス演算子`&`を使用して配列のポインタを渡す必要があります。

```go
var arr [10]byte
var slice []byte
slice = &arr // 明示的にアドレス演算子を使用
```
この変更により、配列のポインタがスライスの基盤となる配列へのポインタとして使用されることが明確になります。

### ポインタとアドレス演算子 `&` (Pointers and Address-of Operator `&`)

Go言語におけるポインタは、変数のメモリアドレスを格納する変数です。アドレス演算子`&`は、変数のメモリアドレスを取得するために使用されます。

```go
var x int = 10
var p *int = &x // pはxのメモリアドレスを指すポインタ
fmt.Println(*p) // *pはpが指す値（xの値）を取得する
```

このコミットでは、配列からスライスへの変換において、この`&`演算子を明示的に使用することが求められるようになりました。

### `string(rune)` と `utf8.EncodeRuneToString`

Go言語では、`rune`型はUnicodeコードポイントを表す整数型です。文字列はUTF-8でエンコードされたバイトのシーケンスです。

以前は、`rune`をUTF-8エンコードされた文字列に変換するために、`utf8.EncodeRuneToString(rune)`という関数が提供されていました。

**変更前:**
```go
import "utf8"
r := '世'
s := utf8.EncodeRuneToString(r) // "世"
```

このコミットにより、`string(rune)`という組み込みの型変換が導入され、`utf8.EncodeRuneToString`は削除されました。

**変更後:**
```go
r := '世'
s := string(r) // "世"
```
`string(rune)`は、単一のルーンをUTF-8エンコードされた文字列に変換する、より簡潔でGoらしい方法です。これは、Goの型変換メカニズムの一貫性を高めるものです。

## 技術的詳細

このコミットは、Go言語の型システムとメモリ管理に関する重要な変更を反映しています。

**配列からスライスへの変換の明示化:**
この変更の核心は、配列が値型であるというGoの原則をより厳密に適用することにあります。配列をスライスに変換する際に`&`を必須とすることで、開発者は「配列のコピー」ではなく「配列への参照（スライス）」を作成していることを明確に意識するようになります。これは、特に大規模なデータ構造を扱う際に、意図しないコピーによるパフォーマンスの低下や、参照の誤解によるバグを防ぐ上で重要です。

例えば、`func Read(p []byte) (n int, err os.Error)`のような関数に配列を渡す場合、以前は`f.Read(buf)`のように書けましたが、この変更後は`f.Read(&buf)`と書く必要があります。これは、`Read`関数がバイトスライスを受け取ることを期待しており、配列`buf`のデータが書き込まれるべきメモリ領域への参照が必要だからです。`&buf`とすることで、`buf`配列の先頭アドレスから始まるスライスが作成され、それが`Read`関数に渡されます。

**`utf8.EncodeRuneToString`の削除と`string(rune)`への移行:**
この変更は、Go言語の標準ライブラリの設計における「簡潔性」と「一貫性」を追求したものです。`string()`変換は、Goにおいて非常に強力で汎用的な型変換メカニズムです。整数型（`int`, `rune`など）から文字列への変換、バイトスライスから文字列への変換など、様々な用途で利用されます。`rune`から文字列への変換もこの汎用的なメカニズムに統合することで、特定の用途のために個別の関数（`utf8.EncodeRuneToString`）を用意する必要がなくなり、APIの表面積が削減されます。これにより、開発者はより少ないルールでGo言語を習得し、より直感的にコードを書くことができるようになります。

この変更は、Go言語がまだ初期段階にあった2009年に行われたものであり、言語設計の進化の過程で、より洗練された、一貫性のあるAPIとセマンティクスを追求する姿勢が伺えます。

## コアとなるコードの変更箇所

このコミットでは、主に以下の2種類の変更が行われています。

1.  **配列からスライスへの変換における`&`の追加**:
    *   `Read`関数など、バイトスライスを受け取る関数に配列を渡す際に、引数の前に`&`が追加されています。
    *   例: `f.Read(buf)` が `f.Read(&buf)` に変更。
    *   `sort`パッケージのテストコードなどでも、配列をソート関数に渡す際に`&`が追加されています。
    *   例: `sort.SortInts(data)` が `sort.SortInts(&data)` に変更。
    *   配列リテラルをスライスとして渡す際にも`&`が追加されています。
    *   例: `sum([3]int{1,2,3})` が `sum(&[3]int{1,2,3})` に変更。

2.  **`utf8.EncodeRuneToString`の削除と`string(rune)`への置き換え**:
    *   `src/lib/utf8.go` から `EncodeRuneToString` 関数が完全に削除されています。
    *   `src/lib/go/scanner.go` や `src/lib/utf8_test.go` など、この関数を使用していた箇所が `string(ch)` や `string(m.rune)` のように `string()` 変換に置き換えられています。

具体的なファイルと変更行数は以下の通りです（一部抜粋）：

*   `doc/progs/cat.go`: `f.Read(buf)` -> `f.Read(&buf)`
*   `doc/progs/sum.go`: `sum([3]int{1,2,3})` -> `sum(&[3]int{1,2,3})`
*   `src/lib/exec.go`: `os.ForkExec(..., fd)` -> `os.ForkExec(..., &fd)`
*   `src/lib/go/scanner.go`: `utf8.EncodeRuneToString(ch)` -> `string(ch)`
*   `src/lib/hash/md5.go`: `_Block(d, d.x)` -> `_Block(d, &d.x)`
*   `src/lib/io/pipe_test.go`: `var buf [64]byte;` -> `var buf = make([]byte, 64);` (これは配列からスライスへの変更とは直接関係ないが、スライスを明示的に作成する例)
*   `src/lib/net/fd.go`: `s.pr.Read(scratch)` -> `s.pr.Read(&scratch)`
*   `src/lib/sort_test.go`: `sort.SortInts(data)` -> `sort.SortInts(&data)`
*   `src/lib/tabwriter/tabwriter.go`: `b.write0(b.padbytes)` -> `b.write0(&b.padbytes)`
*   `src/lib/utf8.go`: `EncodeRuneToString` 関数が削除
*   `src/lib/utf8_test.go`: `TestEncodeRuneToString` テスト関数が削除され、関連する呼び出しが `string()` に変更

## コアとなるコードの解説

### 配列からスライスへの変換の変更例

`doc/progs/cat.go` の変更を見てみましょう。これはファイルを読み込むプログラムの例です。

**変更前:**
```go
// doc/progs/cat.go
func cat(f *file.File) {
    const NBUF = 512;
    var buf [NBUF]byte; // 配列を宣言
    for {
        switch nr, er := f.Read(buf); true { // 配列を直接Read関数に渡している
        // ...
        }
    }
}
```
`f.Read(buf)` の部分では、`buf`という配列が`Read`関数に渡されています。`Read`関数は通常、`[]byte`（バイトスライス）を受け取ります。変更前は、Goコンパイラがこの`buf`配列を暗黙的にスライスに変換していました。

**変更後:**
```go
// doc/progs/cat.go
func cat(f *file.File) {
    const NBUF = 512;
    var buf [NBUF]byte; // 配列を宣言
    for {
        switch nr, er := f.Read(&buf); true { // 配列のアドレスをRead関数に渡している
        // ...
        }
    }
}
```
変更後では、`f.Read(&buf)` となっています。ここで`&buf`は、`buf`配列の先頭アドレスを指すポインタを意味します。Go言語では、配列のポインタからスライスを作成することができます。この`&buf`によって、`buf`配列全体を参照するスライスが明示的に作成され、それが`Read`関数に渡されるようになりました。これにより、`Read`関数が`[]byte`を受け取るという期待と、`buf`が配列であるという事実の間のギャップが、`&`演算子によって明示的に埋められています。

同様に、`doc/progs/sum.go` では、配列リテラルを関数に渡す際の変更が見られます。

**変更前:**
```go
// doc/progs/sum.go
func main() {
    s := sum([3]int{1,2,3});  // 配列リテラルを直接sum関数に渡している
    fmt.Print(s, "\n");
}
```
`sum`関数がスライスを受け取る場合、ここでも暗黙的な変換が行われていました。

**変更後:**
```go
// doc/progs/sum.go
func main() {
    s := sum(&[3]int{1,2,3});  // 配列リテラルのアドレスをsum関数に渡している
    fmt.Print(s, "\n");
}
```
`&[3]int{1,2,3}`とすることで、この配列リテラルのアドレスが取得され、それを基にしたスライスが`sum`関数に渡されます。

### `utf8.EncodeRuneToString`の削除と`string(rune)`への移行例

`src/lib/go/scanner.go` の変更を見てみましょう。これはGoのソースコードをスキャンする部分です。

**変更前:**
```go
// src/lib/go/scanner.go
func charString(ch int) string {
    // ...
    default  : s = utf8.EncodeRuneToString(ch); // utf8パッケージの関数を使用
    // ...
}
```
ここでは、`ch`という`int`型のルーンを文字列に変換するために`utf8.EncodeRuneToString`が使われています。

**変更後:**
```go
// src/lib/go/scanner.go
func charString(ch int) string {
    // ...
    default  : s = string(ch); // 組み込みのstring()変換を使用
    // ...
}
```
変更後では、`string(ch)`という、より簡潔でGo言語の組み込み機能を利用した形に置き換えられています。これにより、`utf8`パッケージへの依存が減り、コードの可読性も向上しています。

また、`src/lib/utf8.go` からは `EncodeRuneToString` 関数自体が削除されています。

**変更前 (src/lib/utf8.goの一部):**
```go
// EncodeRuneToString returns the UTF-8 encoding of the rune.
func EncodeRuneToString(rune int) string {
    if rune < _Rune1Max {
        return string([1]byte{byte(rune)})
    }

    var buf [UTFMax]byte;
    size := EncodeRune(rune, buf);
    return string(buf[0:size]);
}
```

**変更後 (src/lib/utf8.go):**
この関数は完全に削除されています。

これらの変更は、Go言語が初期段階から、より一貫性があり、明示的で、簡潔な言語となるように進化してきた過程を示しています。

この変更により、配列からスライスを作成する際には、明示的にアドレス演算子`&`を使用して配列のポインタを渡すことが必須となりました。これにより、コードの意図がより明確になり、配列が値型であり、スライスがその基盤となる配列への参照であることを開発者が意識しやすくなります。コミットメッセージにあるように、この変更によって残る暗黙的な`&`は、`.`演算子（構造体のフィールドアクセス）と`string(arr)`（バイト配列から文字列への変換）の場合のみとなり、言語全体の一貫性が向上しました。

また、`utf8.EncodeRuneToString`関数の削除と`string(rune)`への移行も、同様に言語の簡潔性と一貫性を追求したものです。`string()`変換は、Go言語において様々な型を文字列に変換するための汎用的なメカニズムであり、ルーン（Unicodeコードポイント）から文字列への変換もこのメカニズムに統合することで、APIの冗長性を排除し、より直感的な記述を可能にしています。

## 前提知識の解説

### Goにおける配列 (Arrays in Go)

Go言語における配列は、同じ型の要素を固定長で連続して格納するデータ構造です。配列の長さは型の一部であり、コンパイル時に決定されます。例えば、`var arr [10]byte`は10個の`byte`型要素を持つ配列を宣言します。配列は値型であり、代入や関数への引数として渡される際には、その内容全体がコピーされます。

```go
var arr [3]int = [3]int{1, 2, 3} // 長さ3のint型配列
var arr2 [3]int = arr             // arr2はarrのコピー
arr2[0] = 100                     // arr2を変更してもarrは変わらない
```

### Goにおけるスライス (Slices in Go)

Go言語におけるスライスは、配列の一部を参照する動的なデータ構造です。スライスは、基盤となる配列へのポインタ、長さ（`len`）、容量（`cap`）の3つの要素で構成されます。スライスは参照型のように振る舞い、スライスを介して基盤となる配列の要素を変更すると、その配列を参照する他のスライスからも変更が反映されます。

```go
var arr [5]int = [5]int{1, 2, 3, 4, 5}
slice := arr[1:4] // arrのインデックス1から3までを参照するスライス
// sliceは {2, 3, 4}
slice[0] = 99     // arrは {1, 99, 3, 4, 5} になる
```

### 配列からスライスへの変換 (Conversion from Array to Slice)

このコミット以前は、Go言語では配列を直接スライス型に代入することが可能でした。この際、コンパイラが暗黙的に配列の先頭アドレスを取得し、その配列全体を参照するスライスを作成していました。

**変更前:**
```go
var arr [10]byte
var slice []byte
slice = arr // 暗黙的に slice = &arr と解釈されていた
```

この挙動は、配列が値型であるというGoの原則と、スライスが参照型のように振る舞うという事実の間で、一部の混乱を招く可能性がありました。

**変更後:**
このコミットにより、配列からスライスを作成する際には、明示的にアドレス演算子`&`を使用して配列のポインタを渡す必要があります。

```go
var arr [10]byte
var slice []byte
slice = &arr // 明示的にアドレス演算子を使用
```
この変更により、配列のポインタがスライスの基盤となる配列へのポインタとして使用されることが明確になります。

### ポインタとアドレス演算子 `&` (Pointers and Address-of Operator `&`)

Go言語におけるポインタは、変数のメモリアドレスを格納する変数です。アドレス演算子`&`は、変数のメモリアドレスを取得するために使用されます。

```go
var x int = 10
var p *int = &x // pはxのメモリアドレスを指すポインタ
fmt.Println(*p) // *pはpが指す値（xの値）を取得する
```

このコミットでは、配列からスライスへの変換において、この`&`演算子を明示的に使用することが求められるようになりました。

### `string(rune)` と `utf8.EncodeRuneToString`

Go言語では、`rune`型はUnicodeコードポイントを表す整数型です。文字列はUTF-8でエンコードされたバイトのシーケンスです。

以前は、`rune`をUTF-8エンコードされた文字列に変換するために、`utf8.EncodeRuneToString(rune)`という関数が提供されていました。

**変更前:**
```go
import "utf8"
r := '世'
s := utf8.EncodeRuneToString(r) // "世"
```

このコミットにより、`string(rune)`という組み込みの型変換が導入され、`utf8.EncodeRuneToString`は削除されました。

**変更後:**
```go
r := '世'
s := string(r) // "世"
```
`string(rune)`は、単一のルーンをUTF-8エンコードされた文字列に変換する、より簡潔でGoらしい方法です。これは、Goの型変換メカニズムの一貫性を高めるものです。

## 技術的詳細

このコミットは、Go言語の型システムとメモリ管理に関する重要な変更を反映しています。

**配列からスライスへの変換の明示化:**
この変更の核心は、配列が値型であるというGoの原則をより厳密に適用することにあります。配列をスライスに変換する際に`&`を必須とすることで、開発者は「配列のコピー」ではなく「配列への参照（スライス）」を作成していることを明確に意識するようになります。これは、特に大規模なデータ構造を扱う際に、意図しないコピーによるパフォーマンスの低下や、参照の誤解によるバグを防ぐ上で重要です。

例えば、`func Read(p []byte) (n int, err os.Error)`のような関数に配列を渡す場合、以前は`f.Read(buf)`のように書けましたが、この変更後は`f.Read(&buf)`と書く必要があります。これは、`Read`関数がバイトスライスを受け取ることを期待しており、配列`buf`のデータが書き込まれるべきメモリ領域への参照が必要だからです。`&buf`とすることで、`buf`配列の先頭アドレスから始まるスライスが作成され、それが`Read`関数に渡されます。

**`utf8.EncodeRuneToString`の削除と`string(rune)`への移行:**
この変更は、Go言語の標準ライブラリの設計における「簡潔性」と「一貫性」を追求したものです。`string()`変換は、Goにおいて非常に強力で汎用的な型変換メカニズムです。整数型（`int`, `rune`など）から文字列への変換、バイトスライスから文字列への変換など、様々な用途で利用されます。`rune`から文字列への変換もこの汎用的なメカニズムに統合することで、特定の用途のために個別の関数（`utf8.EncodeRuneToString`）を用意する必要がなくなり、APIの表面積が削減されます。これにより、開発者はより少ないルールでGo言語を習得し、より直感的にコードを書くことができるようになります。

この変更は、Go言語がまだ初期段階にあった2009年に行われたものであり、言語設計の進化の過程で、より洗練された、一貫性のあるAPIとセマンティクスを追求する姿勢が伺えます。

## コアとなるコードの変更箇所

このコミットでは、主に以下の2種類の変更が行われています。

1.  **配列からスライスへの変換における`&`の追加**:
    *   `Read`関数など、バイトスライスを受け取る関数に配列を渡す際に、引数の前に`&`が追加されています。
    *   例: `f.Read(buf)` が `f.Read(&buf)` に変更。
    *   `sort`パッケージのテストコードなどでも、配列をソート関数に渡す際に`&`が追加されています。
    *   例: `sort.SortInts(data)` が `sort.SortInts(&data)` に変更。
    *   配列リテラルをスライスとして渡す際にも`&`が追加されています。
    *   例: `sum([3]int{1,2,3})` が `sum(&[3]int{1,2,3})` に変更。

2.  **`utf8.EncodeRuneToString`の削除と`string(rune)`への置き換え**:
    *   `src/lib/utf8.go` から `EncodeRuneToString` 関数が完全に削除されています。
    *   `src/lib/go/scanner.go` や `src/lib/utf8_test.go` など、この関数を使用していた箇所が `string(ch)` や `string(m.rune)` のように `string()` 変換に置き換えられています。

具体的なファイルと変更行数は以下の通りです（一部抜粋）：

*   `doc/progs/cat.go`: `f.Read(buf)` -> `f.Read(&buf)`
*   `doc/progs/sum.go`: `sum([3]int{1,2,3})` -> `sum(&[3]int{1,2,3})`
*   `src/lib/exec.go`: `os.ForkExec(..., fd)` -> `os.ForkExec(..., &fd)`
*   `src/lib/go/scanner.go`: `utf8.EncodeRuneToString(ch)` -> `string(ch)`
*   `src/lib/hash/md5.go`: `_Block(d, d.x)` -> `_Block(d, &d.x)`
*   `src/lib/io/pipe_test.go`: `var buf [64]byte;` -> `var buf = make([]byte, 64);` (これは配列からスライスへの変更とは直接関係ないが、スライスを明示的に作成する例)
*   `src/lib/net/fd.go`: `s.pr.Read(scratch)` -> `s.pr.Read(&scratch)`
*   `src/lib/sort_test.go`: `sort.SortInts(data)` -> `sort.SortInts(&data)`
*   `src/lib/tabwriter/tabwriter.go`: `b.write0(b.padbytes)` -> `b.write0(&b.padbytes)`
*   `src/lib/utf8.go`: `EncodeRuneToString` 関数が削除
*   `src/lib/utf8_test.go`: `TestEncodeRuneToString` テスト関数が削除され、関連する呼び出しが `string()` に変更

## コアとなるコードの解説

### 配列からスライスへの変換の変更例

`doc/progs/cat.go` の変更を見てみましょう。これはファイルを読み込むプログラムの例です。

**変更前:**
```go
// doc/progs/cat.go
func cat(f *file.File) {
    const NBUF = 512;
    var buf [NBUF]byte; // 配列を宣言
    for {
        switch nr, er := f.Read(buf); true { // 配列を直接Read関数に渡している
        // ...
        }
    }
}
```
`f.Read(buf)` の部分では、`buf`という配列が`Read`関数に渡されています。`Read`関数は通常、`[]byte`（バイトスライス）を受け取ります。変更前は、Goコンパイラがこの`buf`配列を暗黙的にスライスに変換していました。

**変更後:**
```go
// doc/progs/cat.go
func cat(f *file.File) {
    const NBUF = 512;
    var buf [NBUF]byte; // 配列を宣言
    for {
        switch nr, er := f.Read(&buf); true { // 配列のアドレスをRead関数に渡している
        // ...
        }
    }
}
```
変更後では、`f.Read(&buf)` となっています。ここで`&buf`は、`buf`配列の先頭アドレスを指すポインタを意味します。Go言語では、配列のポインタからスライスを作成することができます。この`&buf`によって、`buf`配列全体を参照するスライスが明示的に作成され、それが`Read`関数に渡されるようになりました。これにより、`Read`関数が`[]byte`を受け取るという期待と、`buf`が配列であるという事実の間のギャップが、`&`演算子によって明示的に埋められています。

同様に、`doc/progs/sum.go` では、配列リテラルを関数に渡す際の変更が見られます。

**変更前:**
```go
// doc/progs/sum.go
func main() {
    s := sum([3]int{1,2,3});  // 配列リテラルを直接sum関数に渡している
    fmt.Print(s, "\n");
}
```
`sum`関数がスライスを受け取る場合、ここでも暗黙的な変換が行われていました。

**変更後:**
```go
// doc/progs/sum.go
func main() {
    s := sum(&[3]int{1,2,3});  // 配列リテラルのアドレスをsum関数に渡している
    fmt.Print(s, "\n");
}
```
`&[3]int{1,2,3}`とすることで、この配列リテラルのアドレスが取得され、それを基にしたスライスが`sum`関数に渡されます。

### `utf8.EncodeRuneToString`の削除と`string(rune)`への移行例

`src/lib/go/scanner.go` の変更を見てみましょう。これはGoのソースコードをスキャンする部分です。

**変更前:**
```go
// src/lib/go/scanner.go
func charString(ch int) string {
    // ...
    default  : s = utf8.EncodeRuneToString(ch); // utf8パッケージの関数を使用
    // ...
}
```
ここでは、`ch`という`int`型のルーンを文字列に変換するために`utf8.EncodeRuneToString`が使われています。

**変更後:**
```go
// src/lib/go/scanner.go
func charString(ch int) string {
    // ...
    default  : s = string(ch); // 組み込みのstring()変換を使用
    // ...
}
```
変更後では、`string(ch)`という、より簡潔でGo言語の組み込み機能を利用した形に置き換えられています。これにより、`utf8`パッケージへの依存が減り、コードの可読性も向上します。

また、`src/lib/utf8.go` からは `EncodeRuneToString` 関数自体が削除されています。

**変更前 (src/lib/utf8.goの一部):**
```go
// EncodeRuneToString returns the UTF-8 encoding of the rune.
func EncodeRuneToString(rune int) string {
    if rune < _Rune1Max {
        return string([1]byte{byte(rune)})
    }

    var buf [UTFMax]byte;
    size := EncodeRune(rune, buf);
    return string(buf[0:size]);
}
```

**変更後 (src/lib/utf8.go):**
この関数は完全に削除されています。

これらの変更は、Go言語が初期段階から、より一貫性があり、明示的で、簡潔な言語となるように進化してきた過程を示しています。

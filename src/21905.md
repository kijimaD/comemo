# [インデックス 21905] ファイルの概要

このコミットは、Go言語のツールチェインにおけるアセンブリリストの出力整形に関するバグ修正です。具体的には、ARMアーキテクチャ向けのアセンブリコードにおいて、`TYPE_REGREG`および`TYPE_REGREG2`という内部的なオペランド型が正しく表示されない問題を解決します。これにより、生成されるアセンブリリストの可読性が向上します。

## 元コミット内容

`[dev.cc] liblink, cmd/internal/obj: fix printing of TYPE_REGREG and TYPE_REGREG2`

このコミットは、`liblink`および`cmd/internal/obj`における`TYPE_REGREG`と`TYPE_REGREG2`の出力形式を修正します。

修正前は、例えば以下のような出力になっていました。

```
        0x0000 00000 (/tmp/x.s:2)       MULLU   R6,R3,(R7, R6)
```

コミットメッセージでは、`MULLU R6,R3,(R7, R6)`の`(R7, R6)`部分のスペースが少し奇妙であると指摘されていますが、これは別の変更リスト（CL）でC言語のコードがGoに移行した後に修正されるべき問題とされています。

## 変更の背景

Go言語のコンパイラやアセンブラは、Goのソースコードを機械語に変換する過程で、中間的なアセンブリコードを生成し、それを人間が読める形式でリスト出力する機能を持っています。このリスト出力は、デバッグやパフォーマンス分析において非常に重要です。

このコミット以前は、ARMアーキテクチャ向けのアセンブリリストにおいて、特定のオペランド型（`TYPE_REGREG`と`TYPE_REGREG2`）の表示が不適切でした。具体的には、レジスタの組み合わせやレジスタとオフセットの組み合わせを表す際に、期待される括弧やカンマが欠落したり、不適切なスペースが入ったりしていました。これにより、生成されるアセンブリリストの可読性が損なわれ、開発者がコードの動作を正確に理解する上で混乱を招く可能性がありました。

このコミットは、これらの内部的なオペランド型が、アセンブリリスト上で標準的かつ明確な形式で表示されるように修正することを目的としています。

## 前提知識の解説

### Goコンパイラとリンカ

Go言語のビルドプロセスは、主にコンパイラとリンカによって行われます。
*   **コンパイラ**: Goのソースコード（`.go`ファイル）を、特定のアーキテクチャ（例: ARM）向けのアセンブリコード（擬似アセンブリ）やオブジェクトファイルに変換します。
*   **リンカ**: コンパイラが生成したオブジェクトファイルやライブラリを結合し、最終的な実行可能バイナリを生成します。この過程で、アセンブリコードの命令選択やアドレス解決などが行われます。

### `liblink`

`liblink`は、Go 1.3リリース以前のGoツールチェインにおいて重要な役割を担っていた内部ライブラリです。その名の通り、Goリンカの機能の一部を担っており、主にオブジェクトファイルの生成や命令選択に関与していました。コンパイラやアセンブラは`liblink`を使用してオブジェクトファイルを書き出し、リンカはそれらのファイルを読み込んで最終的なバイナリを生成していました。しかし、Goのツールチェインの進化に伴い、`liblink`の機能は徐々に`cmd/internal/obj`などの他の部分に統合され、現在では直接的に参照されることは少なくなっています。このコミットが2015年のものであることから、当時のGoツールチェインがまだ`liblink`に依存していたことがわかります。

### `cmd/internal/obj`

`cmd/internal/obj`は、Goプロジェクト内のGoコンパイラのオブジェクトファイル生成に関連する内部パッケージです。このディレクトリには、Goコンパイラが低レベルな操作（アセンブリ、再配置など）を実行するために必要な型定義や関数が含まれています。パスに`internal`が含まれていることからもわかるように、このパッケージはGoツールチェインのプライベートなコンポーネントであり、Goモジュールツリー内の他のパッケージからのみインポート可能です。

### Goアセンブラのリスト形式

Goのアセンブラは、Plan 9アセンブラをベースにした独自の「擬似アセンブリ」言語を使用します。これは、特定のCPUアーキテクチャのネイティブなアセンブリ言語とは異なり、より抽象的な命令セットを持っています。リンカが最終的な機械語命令への変換（命令選択）を行います。
`go tool compile -S your_file.go`コマンドを使用すると、Goソースコードから生成された擬似アセンブリのリスト（アセンブリリスト）を確認できます。このリストは、GoコンパイラがどのようにGoコードを低レベルの操作に変換しているかを理解するのに役立ちます。

### ARMアーキテクチャとレジスタ

ARM（Advanced RISC Machine）は、モバイルデバイスや組み込みシステムで広く使用されているCPUアーキテクチャです。ARMプロセッサは、汎用レジスタ（R0-R15など）を使用してデータを操作します。アセンブリ言語では、これらのレジスタやメモリ上のアドレスをオペランドとして指定し、命令を実行します。

### `TYPE_REGREG`と`TYPE_REGREG2`

これらはGoアセンブラの内部表現におけるオペランドの型です。Goのアセンブラは、アセンブリ命令のオペランドを内部的に表現するために様々な型を使用します。
*   `TYPE_REGREG`: 2つのレジスタの組み合わせ、またはレジスタとオフセットの組み合わせを表すために使用されると推測されます。例えば、`MULLU R6,R3,(R7, R6)`のような命令における`(R7, R6)`の部分がこれに該当します。これは、メモリのアドレッシングモードや、特定の命令における複合オペランドを表す可能性があります。
*   `TYPE_REGREG2`: `TYPE_REGREG`と同様にレジスタの組み合わせを表しますが、その出力形式が異なります。例えば、`R7, R6`のように括弧なしでカンマ区切りで表示される形式を指すと考えられます。

これらの型はGoツールチェインの内部的なものであり、一般のGoプログラマが直接扱うことはほとんどありません。しかし、アセンブリリストの生成においては、これらの内部型を人間が読める文字列に変換する処理が不可欠です。

### `Dconv`関数

`Dconv`関数は、Goアセンブラの内部的なアドレス表現（`obj.Addr`構造体）を、人間が読める文字列形式に変換する役割を担っています。アセンブリリストを生成する際に、各命令のオペランドを整形するために呼び出されます。このコミットでは、この`Dconv`関数が`TYPE_REGREG`と`TYPE_REGREG2`を処理するロジックが修正されています。

## 技術的詳細

このコミットの技術的な核心は、Goツールチェインがアセンブリリストを生成する際に使用する`Dconv`関数における、`TYPE_REGREG`と`TYPE_REGREG2`という特定のオペランド型の文字列変換ロジックの修正です。

Goツールチェインは、Go言語で書かれた部分（`src/cmd/internal/obj/arm/list5.go`）と、C言語で書かれた部分（`src/liblink/list5.c`）が混在していました。これは、Goが初期段階でC言語のツールを多く利用していた名残です。そのため、同じ論理的な修正が、GoとCの両方のファイルに適用されています。

### `src/cmd/internal/obj/arm/list5.go`の修正

このファイルは、Go言語で書かれたARMアーキテクチャ向けのアセンブリリスト生成ロジックの一部です。`Dconv`関数は、`obj.Addr`型のオペランドを受け取り、それを文字列に変換します。

修正前は、`obj.TYPE_REGREG`と`obj.TYPE_REGREG2`のケースが明示的に処理されていませんでした。これにより、これらの型のオペランドが正しく整形されずに、アセンブリリストに表示されていました。

修正では、`switch`文に以下の新しい`case`が追加されました。

*   **`case obj.TYPE_REGREG:`**:
    ```go
    str = fmt.Sprintf("(%v, %v)", Rconv(int(a.Reg)), Rconv(int(a.Offset)))
    ```
    この行は、`TYPE_REGREG`型のオペランドを`(レジスタ, オフセット)`の形式で整形します。`Rconv`関数はレジスタ番号をその名前（例: R7, R6）に変換します。これにより、`MULLU R6,R3,(R7, R6)`のような出力が正しく生成されます。括弧で囲むことで、これが単一の複合オペランドであることを明確に示します。

*   **`case obj.TYPE_REGREG2:`**:
    ```go
    str = fmt.Sprintf("%v, %v", Rconv(int(a.Reg)), Rconv(int(a.Offset)))
    ```
    この行は、`TYPE_REGREG2`型のオペランドを`レジスタ, オフセット`の形式で整形します。`TYPE_REGREG`とは異なり、括弧は使用せず、カンマで区切ることで、別の種類のレジスタペアまたはレジスタとオフセットの組み合わせを表します。

### `src/liblink/list5.c`の修正

このファイルは、C言語で書かれた`liblink`の一部であり、ARMアーキテクチャ向けのアセンブリリスト生成ロジックを含んでいます。ここでも同様に、`Dconv`関数がオペランドの文字列変換を担当しています。

修正前は、`TYPE_REGREG`と`TYPE_REGREG2`のケースが明示的に処理されていませんでした。

修正では、`switch`文に以下の新しい`case`が追加されました。

*   **`case TYPE_REGREG:`**:
    ```c
    sprint(str, "(%R, %R)", a->reg, (int)a->offset);
    ```
    C言語の`sprint`関数と、Goの`Rconv`に相当する`%R`フォーマット指定子を使用して、`(レジスタ, オフセット)`の形式で文字列を生成します。

*   **`case TYPE_REGREG2:`**:
    ```c
    sprint(str, "%R, %R", a->reg, (int)a->offset);
    ```
    同様に、`%R, %R`の形式で文字列を生成します。

これらの修正により、Goツールチェインが生成するアセンブリリストにおいて、`TYPE_REGREG`と`TYPE_REGREG2`が意図した通りの、より明確で標準的な形式で表示されるようになりました。コミットメッセージにある「The space is a little odd but I'd rather fix the usual printing to add spaces than delete that one. But in a different CL, once C is gone.」というコメントは、当時のGoツールチェインがC言語のコードベースからGo言語への移行期にあり、C言語のコードが完全にGoに置き換われば、より根本的な整形の問題も解決できるという背景を示唆しています。

## コアとなるコードの解説

### `src/cmd/internal/obj/arm/list5.go`

```go
 	case obj.TYPE_SCONST:
 		str = fmt.Sprintf("$\"%q\"", a.U.Sval)
-		break // 削除された行
+
+	case obj.TYPE_REGREG:
+		str = fmt.Sprintf("(%v, %v)", Rconv(int(a.Reg)), Rconv(int(a.Offset)))
+
+	case obj.TYPE_REGREG2:
+		str = fmt.Sprintf("%v, %v", Rconv(int(a.Reg)), Rconv(int(a.Offset)))
```

*   `case obj.TYPE_SCONST:` の後にあった `break` が削除され、新しい `case` 文が追加されています。これは、Goの`switch`文がデフォルトで`fallthrough`しないため、`break`が不要になったためです。
*   `case obj.TYPE_REGREG:`: `fmt.Sprintf("(%v, %v)", Rconv(int(a.Reg)), Rconv(int(a.Offset)))`
    *   `fmt.Sprintf`はGoの文字列フォーマット関数です。
    *   `(%v, %v)`というフォーマット文字列は、括弧で囲まれた2つの値（レジスタとオフセット）をカンマで区切って出力することを指定します。
    *   `Rconv(int(a.Reg))`と`Rconv(int(a.Offset))`は、それぞれオペランドのレジスタとオフセットの値を、対応するレジスタ名（例: `R7`, `R6`）に変換します。これにより、例えば`(R7, R6)`のような出力が生成されます。
*   `case obj.TYPE_REGREG2:`: `str = fmt.Sprintf("%v, %v", Rconv(int(a.Reg)), Rconv(int(a.Offset)))`
    *   こちらも`fmt.Sprintf`を使用しますが、フォーマット文字列は`%v, %v`となっており、括弧がありません。
    *   これにより、例えば`R7, R6`のような出力が生成され、`TYPE_REGREG`とは異なる形式でレジスタペアが表現されます。

### `src/liblink/list5.c`

```c
 	case TYPE_SCONST:
 		sprint(str, "$\"%$\"", a->u.sval);
 		break;
+
+	case TYPE_REGREG:
+		sprint(str, "(%R, %R)", a->reg, (int)a->offset);
+		break;
+
+	case TYPE_REGREG2:
+		sprint(str, "%R, %R", a->reg, (int)a->offset);
+		break;
```

*   `case TYPE_REGREG:`: `sprint(str, "(%R, %R)", a->reg, (int)a->offset);`
    *   `sprint`はC言語の文字列フォーマット関数で、Goの`fmt.Sprintf`に相当します。
    *   `(%R, %R)`というフォーマット文字列は、Goの`Rconv`と同様に、レジスタ値をレジスタ名に変換する`%R`フォーマット指定子を使用しています。
    *   これにより、`(R7, R6)`のような出力が生成されます。
*   `case TYPE_REGREG2:`: `sprint(str, "%R, %R", a->reg, (int)a->offset);`
    *   こちらも`sprint`を使用し、`%R, %R`というフォーマット文字列で、括弧なしの`R7, R6`のような出力を生成します。

これらの変更により、Goのアセンブリリストにおける特定のオペランドの表示が標準化され、より正確で読みやすいものになりました。

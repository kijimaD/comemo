# [インデックス 21864] ファイルの概要

このコミットは、Go言語のアセンブラである `cmd/asm` の内部実装を、新しい `obj` パッケージのAPIと連携するように大幅に書き換えるものです。特に、アセンブラがオペランド（命令の引数）を解析し、機械語に変換する際の内部表現が変更され、よりシンプルで短くなっています。

## 元コミット内容

このコミットの元の内容は、Go言語のアセンブラ (`cmd/asm`) を、GoのオブジェクトファイルフォーマットとリンカのAPIを提供する `obj` パッケージの新しいインターフェースに合わせて書き直すというものです。

主な変更点は以下の通りです。

*   **内部 `Addr` 型の廃止**: 以前は `src/cmd/asm/internal/addr` パッケージで定義されていたアセンブラ独自の `Addr` 型が削除されました。
*   **`obj.Addr` への直接解析**: オペランドの解析結果が、直接 `obj` パッケージの `obj.Addr` 型に格納されるようになりました。これにより、中間的なデータ構造が不要になり、コードが簡素化されました。
*   **パーサーとコードジェネレータの書き換え**: 上記の変更に伴い、アセンブラのパーサー（構文解析器）とコードジェネレータ（機械語生成器）が大幅に書き直されました。これにより、コードベースがよりシンプルで短くなったと述べられています。
*   **レジスタペアに関する「ひどいハック」**: 一時的な解決策として、レジスタペア（例: x86/amd64アーキテクチャにおける `DX:AX` のような2つのレジスタを組み合わせた表現）を扱うために、`obj.Addr` の `Class` フィールドが流用されています。これはAPIで適切なフィールドが提供されていないための一時的な措置であり、将来的には改善が望まれています。
*   **出力ファイルの同一性**: 変更後も、旧アセンブラと同じ `.6` (386アーキテクチャ用) および `.8` (amd64アーキテクチャ用) ファイルが生成されることが確認されています。これは、アセンブラの出力結果の互換性が維持されていることを意味します。

## 変更の背景

この変更の背景には、Go言語のツールチェインにおける内部APIの進化があります。特に、オブジェクトファイルフォーマットとリンカの処理を抽象化する `obj` パッケージのAPIが更新されたことが挙げられます。

`cmd/asm` はGoプログラムのアセンブリコードを機械語に変換する重要なツールであり、その内部構造は `obj` パッケージと密接に連携しています。`obj` APIの変更に伴い、`cmd/asm` もその新しいAPIに適応する必要がありました。

以前の `cmd/asm` は、アセンブリ命令のオペランドを表現するために独自の `addr.Addr` 型を使用していました。しかし、`obj` パッケージが提供する `obj.Addr` 型がより汎用的に設計され、アセンブラのニーズを満たせるようになったため、重複する `addr.Addr` 型を廃止し、直接 `obj.Addr` を利用する方針が取られました。これにより、コードの複雑性を減らし、ツールチェイン全体の整合性を高めることが目的とされています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

### 1. Go言語のアセンブラ (`cmd/asm`)

Go言語は、Goで書かれたコードをコンパイルするだけでなく、アセンブリ言語で書かれたコードもサポートしています。`cmd/asm` は、Goのアセンブリ言語（Plan 9アセンブリに似た構文を持つ）を機械語に変換するためのツールです。Goのランタイムや標準ライブラリの一部は、パフォーマンスが重要な部分でアセンブリ言語で書かれています。

### 2. Goのオブジェクトファイルフォーマットとリンカ (`cmd/internal/obj` パッケージ)

Goのコンパイラ (`cmd/compile`) やアセンブラ (`cmd/asm`) が生成する中間ファイルは、Go独自のオブジェクトファイルフォーマットに従っています。`cmd/internal/obj` パッケージは、このオブジェクトファイルフォーマットを扱い、リンカが最終的な実行可能ファイルを生成するために必要な情報（シンボル、命令、データなど）を表現するためのAPIを提供します。

*   **`obj.Prog`**: プログラム中の単一の命令（または擬似命令）を表す構造体です。アセンブラが生成する機械語命令や、リンカが処理するデータ定義などがこれに該当します。
*   **`obj.Addr`**: `obj.Prog` のフィールドとして使用され、命令のオペランド（引数）のアドレスや値を表現する汎用的な構造体です。レジスタ、メモリのアドレス、即値定数、シンボルなどを表現できます。

### 3. アセンブリ言語のオペランド

アセンブリ言語の命令は、通常、操作コード（命令の種類）と1つ以上のオペランドで構成されます。オペランドは、命令が操作するデータやその場所を指定します。

例: `MOVQ AX, BX` (AXレジスタの内容をBXレジスタに移動)
*   `MOVQ`: 操作コード
*   `AX`: ソースオペランド（データの元）
*   `BX`: デスティネーションオペランド（データの送り先）

オペランドの種類には、レジスタ、即値（定数）、メモリ参照（シンボル、オフセット、インデックスレジスタなど）があります。

### 4. レジスタペア (Register Pairs)

一部のCPUアーキテクチャ（特にx86/amd64）では、特定の命令で複数のレジスタを組み合わせて1つのオペランドとして扱うことがあります。例えば、`DX:AX` は、`DX` レジスタと `AX` レジスタを連結して64ビットの値を表現する際に使用されることがあります。アセンブラはこのような特殊なオペランドの表現を適切に解析し、機械語に変換する必要があります。

### 5. Plan 9 アセンブリ構文

Goのアセンブリ言語は、Bell LabsのPlan 9オペレーティングシステムで使用されていたアセンブリ言語の構文に基づいています。これは一般的なAT&T構文やIntel構文とは異なる特徴を持っています。例えば、レジスタは `R0`, `R1` のように表記され、メモリ参照は `offset(register)` の形式を取ります。シンボルは `symbol(SB)` (Static Base) や `symbol(FP)` (Frame Pointer) のように、基準レジスタからのオフセットで表現されます。

## 技術的詳細

このコミットの技術的詳細を掘り下げると、`cmd/asm` の内部におけるデータフローと構造が大きく変化したことがわかります。

### 1. `addr.Addr` 型の削除と `obj.Addr` への統一

最も重要な変更は、`src/cmd/asm/internal/addr/addr.go` ファイルが削除され、それに伴い `addr.Addr` 型が廃止されたことです。以前は、アセンブラのパーサーがアセンブリコードのオペランドを解析する際に、この `addr.Addr` 型のインスタンスを生成し、その中にオペランドの種類（レジスタ、即値、シンボルなど）や関連する値（オフセット、レジスタ番号、シンボル名など）を格納していました。

このコミット以降、パーサーはオペランドを直接 `cmd/internal/obj` パッケージが提供する `obj.Addr` 型に解析するようになりました。`obj.Addr` は、リンカがオブジェクトファイルを処理する際に使用する汎用的なアドレス表現であり、アセンブラが独自の `Addr` 型を持つ必要がなくなりました。これにより、アセンブラとリンカの間のインターフェースが簡素化され、コードの重複が排除されました。

### 2. パーサー (`parse.go`) の変更

`src/cmd/asm/internal/asm/parse.go` は、アセンブリコードのテキストをトークン化し、それらを `obj.Addr` 構造体に変換する主要なロジックを含んでいます。

*   **`Parser.address` メソッドの変更**: 以前は `addr.Addr` を返していましたが、`obj.Addr` を返すように変更されました。
*   **`Parser.operand` メソッドの再実装**: このメソッドは、アセンブリ命令の個々のオペランドを解析し、対応する `obj.Addr` 構造体を構築する中心的な役割を担っています。
    *   レジスタ、即値、文字列定数、浮動小数点定数、シンボル参照など、様々な種類のオペランドの解析ロジックが `obj.Addr` のフィールド（`Type`, `Reg`, `Index`, `Offset`, `Sym`, `U.Dval`, `U.Sval` など）に直接マッピングされるようになりました。
    *   特に、シンボル参照（例: `main·main(SB)`）の解析において、`obj.Linklookup` を使用して `obj.Sym` を取得し、`obj.Addr` の `Sym` フィールドに設定するようになりました。また、`SB` (Static Base), `FP` (Frame Pointer), `SP` (Stack Pointer) といった擬似レジスタの扱いも `obj.Addr` の `Name` フィールド（`obj.NAME_EXTERN`, `obj.NAME_PARAM`, `obj.NAME_AUTO`）にマッピングされています。
*   **`Parser.register` および `Parser.symbolReference` の導入**: オペランド解析のロジックが、レジスタ単独の参照とシンボルを含む参照に分割され、それぞれ `register` と `symbolReference` というヘルパーメソッドで処理されるようになりました。これにより、コードの可読性と保守性が向上しています。

### 3. アセンブラ (`asm.go`) の変更

`src/cmd/asm/internal/asm/asm.go` は、解析された `obj.Prog` 構造体を受け取り、最終的な機械語命令を生成する役割を担っています。

*   **`Parser.addrToAddr` メソッドの削除**: 以前は `addr.Addr` から `obj.Addr` への変換を行っていましたが、パーサーが直接 `obj.Addr` を生成するようになったため、この変換メソッドは不要となり削除されました。
*   **擬似命令の処理の変更**: `TEXT`, `DATA`, `GLOBL`, `PCDATA`, `FUNCDATA` といった擬似命令の処理ロジックが、`obj.Addr` を直接操作するように変更されました。
    *   例えば、`TEXT` 命令では、関数のフレームサイズや引数サイズが `prog.To.Offset` や `prog.To.U.Argsize` に直接設定されるようになりました。以前はアーキテクチャごとに異なるエンコーディング（`D_CONST`, `D_CONST2` など）を使用していましたが、これが統一されました。
*   **命令アセンブルの変更**: `asmInstruction` や `asmJump` といった命令をアセンブルするメソッドも、引数として `[]obj.Addr` を受け取るように変更されました。これにより、オペランドの処理がより直接的になりました。
*   **レジスタペアの「ハック」**: コミットメッセージで言及されている「ひどいハック」は、`asmInstruction` メソッド内で確認できます。レジスタペア（例: `DX:AX`）がオペランドとして現れた場合、`obj.Addr` の `Class` フィールド（通常はオペランドのクラスを示す）を流用して2番目のレジスタの情報を格納しています。これは `obj.Addr` APIにレジスタペアを直接表現するフィールドがないための一時的な回避策です。

### 4. アーキテクチャ定義 (`arch.go`) の変更

`src/cmd/asm/internal/arch/arch.go` は、各CPUアーキテクチャ（386, Amd64など）固有のレジスタ名や命令名を定義しています。

*   `Arch` 構造体から `D_INDIR`, `D_CONST2`, `SP`, `NoAddr` といったフィールドが削除されました。これらは `obj` パッケージの新しいAPIで直接扱われるか、不要になったためです。
*   `Registers` マップの値の型が `int` から `int16` に変更されました。これは `obj.Addr` の `Reg` フィールドが `int16` 型であることに合わせたものです。
*   `Pseudos` マップが `Arch` 構造体の外に移動し、グローバル変数として定義されました。これは、擬似命令がアーキテクチャに依存しない共通の概念であるためです。

### 5. その他の変更

*   `src/cmd/asm/internal/lex/lex.go` の `HistLine` 関数が `int32` を返すように変更されました。これは `obj.Prog` の `Lineno` フィールドの型に合わせたものです。
*   `src/cmd/asm/internal/lex/stack.go` と `src/cmd/asm/main.go` からビルドタグ `// +build ignore` が削除されました。これは、これらのファイルがビルドプロセスに直接含まれるようになったことを示唆しています。

これらの変更により、`cmd/asm` は `obj` パッケージのAPIをより直接的に利用するようになり、アセンブラの内部構造がよりシンプルで、Goツールチェイン全体の設計思想に沿ったものになりました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

### 1. Go言語のアセンブラ (`cmd/asm`)

Go言語は、Goで書かれたコードをコンパイルするだけでなく、アセンブリ言語で書かれたコードもサポートしています。`cmd/asm` は、Goのアセンブリ言語（Plan 9アセンブリに似た構文を持つ）を機械語に変換するためのツールです。Goのランタイムや標準ライブラリの一部は、パフォーマンスが重要な部分でアセンブリ言語で書かれています。

### 2. Goのオブジェクトファイルフォーマットとリンカ (`cmd/internal/obj` パッケージ)

Goのコンパイラ (`cmd/compile`) やアセンブラ (`cmd/asm`) が生成する中間ファイルは、Go独自のオブジェクトファイルフォーマットに従っています。`cmd/internal/obj` パッケージは、このオブジェクトファイルフォーマットを扱い、リンカが最終的な実行可能ファイルを生成するために必要な情報（シンボル、命令、データなど）を表現するためのAPIを提供します。

*   **`obj.Prog`**: プログラム中の単一の命令（または擬似命令）を表す構造体です。アセンブラが生成する機械語命令や、リンカが処理するデータ定義などがこれに該当します。
*   **`obj.Addr`**: `obj.Prog` のフィールドとして使用され、命令のオペランド（引数）のアドレスや値を表現する汎用的な構造体です。レジスタ、メモリのアドレス、即値定数、シンボルなどを表現できます。

### 3. アセンブリ言語のオペランド

アセンブリ言語の命令は、通常、操作コード（命令の種類）と1つ以上のオペランドで構成されます。オペランドは、命令が操作するデータやその場所を指定します。

例: `MOVQ AX, BX` (AXレジスタの内容をBXレジスタに移動)
*   `MOVQ`: 操作コード
*   `AX`: ソースオペランド（データの元）
*   `BX`: デスティネーションオペランド（データの送り先）

オペランドの種類には、レジスタ、即値（定数）、メモリ参照（シンボル、オフセット、インデックスレジスタなど）があります。

### 4. レジスタペア (Register Pairs)

一部のCPUアーキテクチャ（特にx86/amd64）では、特定の命令で複数のレジスタを組み合わせて1つのオペランドとして扱うことがあります。例えば、`DX:AX` は、`DX` レジスタと `AX` レジスタを連結して64ビットの値を表現する際に使用されることがあります。アセンブラはこのような特殊なオペランドの表現を適切に解析し、機械語に変換する必要があります。

### 5. Plan 9 アセンブリ構文

Goのアセンブリ言語は、Bell LabsのPlan 9オペレーティングシステムで使用されていたアセンブリ言語の構文に基づいています。これは一般的なAT&T構文やIntel構文とは異なる特徴を持っています。例えば、レジスタは `R0`, `R1` のように表記され、メモリ参照は `offset(register)` の形式を取ります。シンボルは `symbol(SB)` (Static Base) や `symbol(FP)` (Frame Pointer) のように、基準レジスタからのオフセットで表現されます。

`src/cmd/asm/internal/asm/asm.go` は、解析された `obj.Prog` 構造体を受け取り、最終的な機械語命令を生成する役割を担っています。

*   **`Parser.addrToAddr` メソッドの削除**: 以前は `addr.Addr` から `obj.Addr` への変換を行っていましたが、パーサーが直接 `obj.Addr` を生成するようになったため、この変換メソッドは不要となり削除されました。
*   **擬似命令の処理の変更**: `TEXT`, `DATA`, `GLOBL`, `PCDATA`, `FUNCDATA` といった擬似命令の処理ロジックが、`obj.Addr` を直接操作するように変更されました。
    *   例えば、`TEXT` 命令では、関数のフレームサイズや引数サイズが `prog.To.Offset` や `prog.To.U.Argsize` に直接設定されるようになりました。以前はアーキテクチャごとに異なるエンコーディング（`D_CONST`, `D_CONST2` など）を使用していましたが、これが統一されました。
*   **命令アセンブルの変更**: `asmInstruction` や `asmJump` といった命令をアセンブルするメソッドも、引数として `[]obj.Addr` を受け取るように変更されました。これにより、オペランドの処理がより直接的になりました。
*   **レジスタペアの「ハック」**: コミットメッセージで言及されている「ひどいハック」は、`asmInstruction` メソッド内で確認できます。レジスタペア（例: `DX:AX`）がオペランドとして現れた場合、`obj.Addr` の `Class` フィールド（通常はオペランドのクラスを示す）を流用して2番目のレジスタの情報を格納しています。これは `obj.Addr` APIにレジスタペアを直接表現するフィールドがないための一時的な回避策です。

### 4. アーキテクチャ定義 (`arch.go`) の変更

`src/cmd/asm/internal/arch/arch.go` は、各CPUアーキテクチャ（386, Amd64など）固有のレジスタ名や命令名を定義しています。

*   `Arch` 構造体から `D_INDIR`, `D_CONST2`, `SP`, `NoAddr` といったフィールドが削除されました。これらは `obj` パッケージの新しいAPIで直接扱われるか、不要になったためです。
*   `Registers` マップの値の型が `int` から `int16` に変更されました。これは `obj.Addr` の `Reg` フィールドが `int16` 型であることに合わせたものです。
*   `Pseudos` マップが `Arch` 構造体の外に移動し、グローバル変数として定義されました。これは、擬似命令がアーキテクチャに依存しない共通の概念であるためです。

### 5. その他の変更

*   `src/cmd/asm/internal/lex/lex.go` の `HistLine` 関数が `int32` を返すように変更されました。これは `obj.Prog` の `Lineno` フィールドの型に合わせたものです。
*   `src/cmd/asm/internal/lex/stack.go` と `src/cmd/asm/main.go` からビルドタグ `// +build ignore` が削除されました。これは、これらのファイルがビルドプロセスに直接含まれるようになったことを示唆しています。

これらの変更により、`cmd/asm` は `obj` パッケージのAPIをより直接的に利用するようになり、アセンブラの内部構造がよりシンプルで、Goツールチェイン全体の設計思想に沿ったものになりました。

## コアとなるコードの解説

上記の `parse.go` の `operand` メソッドの変更は、アセンブラのオペランド解析の根本的なアプローチを示しています。

**変更前 (`addr.Addr` を使用):**
変更前の `operand` メソッドは、独自の `addr.Addr` 構造体のフィールド（`IsImmediateConstant`, `HasRegister`, `Symbol`, `Offset` など）をブール値や特定の型で設定することで、オペランドの特性を表現していました。例えば、`$` プレフィックスがあれば `IsImmediateConstant` を `true` に設定し、レジスタ名があれば `HasRegister` を `true` に設定していました。

**変更後 (`obj.Addr` を直接使用):**
変更後の `operand` メソッドは、`obj.Addr` 構造体の `Type`, `Reg`, `Index`, `Offset`, `Sym`, `Name`, `Class`, `U.Dval`, `U.Sval` といったフィールドを直接設定します。

*   **`prefix` 変数**: オペランドの先頭に `$` (即値) や `*` (間接参照) があるかどうかを識別するために導入されました。これにより、オペランドの種類を早期に判断し、適切な `obj.Addr.Type` を設定できます。
*   **`scanner.Ident` の処理**:
    *   識別子がレジスタ名である場合は、`register` ヘルパー関数を呼び出し、`obj.Addr.Type` を `obj.TYPE_REG` に、`obj.Addr.Reg` をレジスタ番号に設定します。レジスタペア (`R1:R2`) の場合は、一時的に `obj.Addr.Class` フィールドに2番目のレジスタを格納する「ハック」が行われます。
    *   識別子がシンボル名である場合は、`symbolReference` ヘルパー関数を呼び出し、`obj.Addr.Type` を `obj.TYPE_MEM` (または `obj.TYPE_ADDR`, `obj.TYPE_INDIR`) に、`obj.Addr.Sym` を `obj.Linklookup` で取得したシンボルに設定します。また、`SB`, `FP`, `SP` といった擬似レジスタからのオフセットも `obj.Addr.Name` フィールドに適切にマッピングされます。
*   **定数とメモリ参照の処理**:
    *   浮動小数点数、文字列、整数などの定数は、`$` プレフィックスの有無に応じて `obj.TYPE_FCONST`, `obj.TYPE_SCONST`, `obj.TYPE_CONST` にマッピングされ、それぞれの値が `obj.Addr.U.Dval` や `obj.Addr.U.Sval`, `obj.Addr.Offset` に格納されます。
    *   括弧 `()` を含むメモリ参照（例: `offset(reg)` や `(reg)(index*scale)`）も、`obj.Addr.Reg`, `obj.Addr.Index`, `obj.Addr.Scale` フィールドに適切に解析されます。

この変更により、アセンブラの内部表現が `obj` パッケージの標準的な表現に統一され、コードの複雑性が大幅に削減されました。また、`obj.Addr` が持つ豊富なフィールドを直接利用することで、より表現力豊かなオペランド解析が可能になっています。

# [インデックス 27533] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおいて、複合型（complex、string、slice、interface）の扱いを改善し、特にライブ変数解析とDWARFデバッグ情報の生成を最適化することを目的としています。以前は、これらの複合型が自動変数（AUTO）として扱われる際に、その内部構造が適切に名前付けされず、ライブ変数解析が困難でした。この変更により、複合型が個々の単一ワード変数に分割され、それぞれが独立して扱われることで、より正確なライブ変数解析と効率的なコード生成、そしてデバッグ情報の改善が実現されています。

    cmd/compile: better job of naming compound types
    
    Compound AUTO types weren't named previously. That was because live
    variable analysis (plive.go) doesn't handle spilling to compound types.
    It can't handle them because there is no valid place to put VARDEFs when
    regalloc is spilling compound types.
    
    compound types = multiword builtin types: complex, string, slice, and
    interface.
    
    Instead, we split named AUTOs into individual one-word variables. For
    example, a string s gets split into a byte ptr s.ptr and an integer
    s.len. Those two variables can be spilled to / restored from
    independently. As a result, live variable analysis can handle them
    because they are one-word objects.
    
    This CL will change how AUTOs are described in DWARF information.
    Consider the code:
    
    func f(s string, i int) int {
        x := s[i:i+5]
        g()
        return lookup(x)
    }
    
    The old compiler would spill x to two consecutive slots on the stack,
    both named x (at offsets 0 and 8). The new compiler spills the pointer
    of x to a slot named x.ptr. It doesn't spill x.len at all, as it is a
    constant (5) and can be rematerialized for the call to lookup.
    
    So compound objects may not be spilled in their entirety, and even if
    they are they won't necessarily be contiguous. Such is the price of
    optimization.
    
    Re-enable live variable analysis tests. One test remains disabled, it
    fails because of #14904.

## 変更の背景

GoコンパイラのSSAバックエンドでは、プログラムの最適化と効率的な機械語コード生成のために、ライブ変数解析（Live Variable Analysis）が重要な役割を果たします。しかし、`complex`、`string`、`slice`、`interface`といったGoの複合型は、複数の内部要素（例えば、stringはデータへのポインタと長さ）から構成されるため、従来のライブ変数解析ではその扱いが困難でした。

具体的には、コンパイラがこれらの複合型をスタックにスピル（レジスタからメモリへ退避）する際、複合型全体を一つのエンティティとして扱うと、その内部要素の個別のライフタイムを正確に追跡できませんでした。特に、デバッグ情報（DWARF）を生成する際に、複合型全体に一つの名前を割り当ててしまうと、デバッガがその内部構造を正確に表示できないという問題がありました。また、レジスタ割り当て（regalloc）が複合型をスピルする際に、VARDEF（変数定義）を配置する適切な場所がないため、ライブ変数解析が正しく機能しないという技術的な制約も存在しました。

この問題に対処するため、このコミットでは、複合型をその構成要素である単一ワードの変数に分割し、それぞれに独立した名前を付けることで、ライブ変数解析の精度を向上させ、より詳細なDWARFデバッグ情報を生成できるようにする変更が導入されました。これにより、コンパイラは複合型の一部のみをスピルしたり、再計算（rematerialize）したりするなどの最適化をより柔軟に行えるようになります。

## 前提知識の解説

### GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木（AST）に変換した後、中間表現としてSSA（Static Single Assignment）形式を使用します。SSA形式は、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。SSAバックエンドは、このSSA形式のコードを機械語コードに変換する役割を担います。

### ライブ変数解析 (Live Variable Analysis)

ライブ変数解析は、コンパイラのデータフロー解析の一種で、プログラムの特定の位置において、ある変数の値が将来的に使用される可能性があるかどうか（「ライブである」か「デッドである」か）を判断します。この情報は、レジスタ割り当て（ライブな変数をレジスタに保持し、デッドな変数のレジスタを再利用する）、デッドコード削除、およびガベージコレクションの精度向上などに利用されます。

### DWARFデバッグ情報

DWARF（Debugging With Attributed Record Formats）は、コンパイルされたプログラムのデバッグ情報を記述するための標準フォーマットです。デバッガはDWARF情報を使用して、ソースコードの行番号、変数名、型、スタック上の位置などを把握し、開発者がプログラムの実行状態を検査できるようにします。変数のライフタイムやメモリ上の配置に関する正確なDWARF情報は、デバッグ体験を大きく左右します。

### Goの複合型

Go言語には、複数の値を内部に持つ複合型がいくつか存在します。
-   **string**: 内部的には、文字列データへのポインタと文字列の長さ（`len`）の2つの要素で構成されます。
-   **slice**: 内部的には、基底配列へのポインタ、スライスの長さ（`len`）、容量（`cap`）の3つの要素で構成されます。
-   **interface**: 内部的には、型情報へのポインタ（`itab`または`type`）とデータへのポインタ（`data`）の2つの要素で構成されます。
-   **complex**: 内部的には、実部と虚部の2つの浮動小数点数で構成されます（`complex64`は`float32`を2つ、`complex128`は`float64`を2つ）。

これらの型は、Goのセマンティクス上は単一のエンティティとして扱われますが、コンパイラの内部処理ではその構成要素に分解されることがあります。

### AUTO変数とVARDEF

Goコンパイラにおいて、`AUTO`変数は通常、関数内で宣言されたローカル変数や一時変数（テンポラリ）を指します。`VARDEF`は、これらの変数がメモリ上に割り当てられる場所（通常はスタック）をコンパイラが認識するための擬似命令のようなものです。ライブ変数解析が正しく機能するためには、変数のライフタイム全体にわたってVARDEFが適切に配置されている必要があります。

### スピル (Spilling) と リマテリアライゼーション (Rematerialization)

-   **スピル**: レジスタ割り当ての過程で、利用可能なレジスタが不足した場合、コンパイラは一部の変数をレジスタからメモリ（通常はスタック）に退避させます。この操作をスピルと呼びます。
-   **リマテリアライゼーション**: ある値が定数であるか、または非常に安価に再計算できる場合、コンパイラはその値をメモリからロードする代わりに、必要に応じてその場で再計算することがあります。これをリマテリアライゼーションと呼び、メモリアクセスを減らすことでパフォーマンスを向上させます。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドが複合型を扱う方法を根本的に変更した点にあります。

1.  **複合型の分解と名前付け**:
    以前は、`PAUTO`クラスの複合型（string, slice, interface）は、ライブ変数解析の対象から除外されていました。これは、これらの型が複数ワードで構成されており、レジスタ割り当てが複合型全体をスピルする際に、VARDEFを適切に配置できないためでした。
    この変更では、`src/cmd/compile/internal/gc/ssa.go`に`SplitString`, `SplitInterface`, `SplitSlice`, `SplitComplex`といった新しい関数が導入されました。これらの関数は、複合型をその構成要素（例: stringのポインタと長さ）に分解し、それぞれに`.ptr`, `.len`, `.cap`, `.real`, `.imag`, `.itab`, `.data`といったサフィックスを付けて独立した`AUTO`変数として名前を付けます。
    例えば、`string s`は`s.ptr`と`s.len`という2つの独立した変数として扱われます。これにより、各構成要素は単一ワードのオブジェクトとしてライブ変数解析の対象となり、個別にスピルやリマテリアライゼーションの対象とすることができます。

2.  **SSAフロントエンドインターフェースの拡張**:
    `src/cmd/compile/internal/ssa/config.go`の`Frontend`インターフェースに、上記で述べた`SplitString`, `SplitInterface`, `SplitSlice`, `SplitComplex`メソッドが追加されました。これは、SSAバックエンドがこれらの複合型の分解ロジックをフロントエンド（`gc`パッケージ）に委譲し、抽象化された形で利用できるようにするためです。

3.  **SSA分解パスの更新**:
    `src/cmd/compile/internal/ssa/decompose.go`では、複合型を分解する際に、直接`LocalSlot`を作成する代わりに、`f.Config.fe.Split*`メソッドを呼び出すように変更されました。これにより、SSA中間表現の段階で、複合型がその構成要素に分解され、それぞれが独立した`LocalSlot`として扱われるようになります。

4.  **SSAリライトルールの変更**:
    -   `src/cmd/compile/internal/ssa/gen/dec.rules`には、複合型（complex, string, slice, interface）の`Load`および`Store`操作を分解するための新しいリライトルールが追加されました。これらのルールは、メモリからのロード時やメモリへのストア時に、複合型をその構成要素に分解または結合する方法を定義します。例えば、`Load`命令がstring型をロードする場合、それは`StringMake`オペレーションに変換され、stringのポインタと長さを個別にロードする形になります。
    -   `src/cmd/compile/internal/ssa/gen/generic.rules`からは、以前の複合型に関する`Load`および`Store`のリライトルールが削除されました。これは、これらのルールが`dec.rules`に移動され、より特化した分解パスで処理されるようになったためです。また、`ComplexImag`, `ComplexReal`, `IData`, `ITab`といった複合型の要素にアクセスするオペレーションのリライトルールも、`rewritedec.go`に移動されました。

5.  **SSAリライト関数の更新**:
    `src/cmd/compile/internal/ssa/rewritedec.go`には、`OpComplexImag`, `OpComplexReal`, `OpIData`, `OpITab`, `OpLoad`, `OpStore`といったオペレーションに対する新しい`rewriteValuedec_Op*`関数が追加されました。これらの関数は、`dec.rules`で定義されたリライトルールに対応し、SSA値の変換ロジックを実装します。これにより、複合型の要素へのアクセスや、複合型のロード/ストアが、その内部要素に対する操作に変換されます。

6.  **スタック割り当てロジックの調整**:
    `src/cmd/compile/internal/ssa/stackalloc.go`では、スタック割り当ての際に変数の干渉をチェックするロジックが微調整されました。`LocalSlot`オブジェクト全体ではなく、`name.N`（ノード）と`name.Off`（オフセット）を比較するように変更されたのは、複合型が分解され、その構成要素が異なるオフセットを持つ可能性があるため、より粒度の細かい比較が必要になったためと考えられます。

7.  **ライブ変数解析テストの追加**:
    `test/live_ssa.go`という新しいテストファイルが追加され、多数のライブ変数解析に関するテストケースが含まれています。これにより、複合型の分解と名前付けの変更が、ライブ変数解析の正確性にどのように影響するかを検証し、改善された動作を保証しています。特に、`ERROR`アノテーションは、特定の呼び出しサイトでどの変数がライブであるとコンパイラが判断するかを示しており、デバッグ情報の精度向上に直結します。

この一連の変更により、Goコンパイラは複合型をより細かく制御できるようになり、ライブ変数解析の精度向上、レジスタ割り当ての効率化、そしてデバッガがより詳細な変数情報を提供できるようなDWARFデバッグ情報の生成が可能になりました。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の `Split*` 関数群

これらの関数は、このコミットの最も重要な部分です。例えば、`SplitString`関数を見てみましょう。

```go
func (e *ssaExport) SplitString(name ssa.LocalSlot) (ssa.LocalSlot, ssa.LocalSlot) {
	n := name.N.(*Node)
	ptrType := Ptrto(Types[TUINT8]) // stringのデータポインタの型
	lenType := Types[TINT]          // stringの長さの型
	if n.Class == PAUTO && !n.Addrtaken {
		// このstringを2つの独立した変数に分割する
		p := e.namedAuto(n.Sym.Name+".ptr", ptrType) // ポインタ部分に ".ptr" サフィックスを付けて名前を付ける
		l := e.namedAuto(n.Sym.Name+".len", lenType) // 長さ部分に ".len" サフィックスを付けて名前を付ける
		return ssa.LocalSlot{p, ptrType, 0}, ssa.LocalSlot{l, lenType, 0}
	}
	// より大きな変数の2つの部分を返す (PAUTOでない場合やアドレスが取られている場合)
	return ssa.LocalSlot{n, ptrType, name.Off}, ssa.LocalSlot{n, lenType, name.Off + int64(Widthptr)}
}
```

この関数は、`name`で指定された`LocalSlot`（ローカル変数）がstring型である場合に呼び出されます。
-   もしその変数が`PAUTO`（自動変数）であり、かつアドレスが取られていない（`!n.Addrtaken`）場合、コンパイラはこれを最適化の対象と見なし、`n.Sym.Name + ".ptr"`と`n.Sym.Name + ".len"`という新しい名前を持つ2つの独立した`AUTO`変数を生成します。これにより、デバッガは`s.ptr`と`s.len`として個々の要素を認識できるようになります。
-   それ以外の場合（例えば、変数が明示的にアドレスが取られている場合など）、元の変数`n`のオフセットを基に、ポインタ部分と長さ部分の`LocalSlot`を返します。これは、変数がメモリ上に連続して配置されていることを前提としています。

同様のロジックが`SplitInterface`, `SplitSlice`, `SplitComplex`にも適用され、それぞれの複合型がその構成要素に分解されます。

### `src/cmd/compile/internal/ssa/gen/dec.rules` のリライトルール

`dec.rules`ファイルは、SSA中間表現の変換ルールを定義しています。このコミットで追加されたルールは、複合型の`Load`や`Store`操作を、その内部要素に対する操作に変換する方法を示しています。

例えば、string型の`Load`に関するルールは以下のようになります。

```
(Load <t> ptr mem) && t.IsString() ->
  (StringMake
    (Load <config.fe.TypeBytePtr()> ptr mem)
    (Load <config.fe.TypeInt()>\
      (OffPtr <config.fe.TypeInt().PtrTo()> [config.PtrSize] ptr)\
      mem))
```

このルールは、「string型`t`を`ptr`から`mem`を使ってロードする`Load`オペレーション」を、「`StringMake`オペレーション」に変換することを示しています。`StringMake`オペレーションは、stringのポインタ部分（`ptr`から直接ロード）と長さ部分（`ptr`から`config.PtrSize`オフセットした場所からロード）を個別にロードして構築されます。

これにより、コンパイラはstring全体を一度にロードするのではなく、その構成要素を個別にロードするようになり、より細かい粒度での最適化（例えば、長さだけが必要な場合はポインタをロードしないなど）が可能になります。

これらの変更は、GoコンパイラのSSAバックエンドが複合型をより効率的かつ正確に処理するための基盤を築き、結果として生成されるコードの品質とデバッグ体験の向上に貢献しています。

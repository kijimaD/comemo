# [インデックス 21853] ファイルの概要

このコミットは、Go言語のランタイムにおけるmacOS Yosemite (OS X 10.10) の`readdir`システムコールに関する特定のバグに対するワークアラウンドを元に戻すものです。具体的には、Yosemiteのベータ版で発生していた`getdirentries64`システムコールがディレクトリの終端で誤ってエラーを返す問題への対処を削除し、その修正がYosemiteの最終リリースで適用されたことを確認しています。また、正規のファイルをディレクトリとして読み込もうとした場合に適切に失敗することを確認するための新しいテストが追加されています。

## 元コミット内容

このコミットがrevertしている元のコミットは、`https://golang.org/cl/119530044` であり、その内容は以下の通りです。

OS X 10.10 Yosemiteのベータ版（ビルド14A299l）において、`getdirentries64`システムコールが特定の条件下で`EOF`（End Of File）ではなく`EINVAL`（Invalid argument）または`ENOENT`（No such file or directory）エラーを誤って返すバグが存在しました。この問題は、特に小さなディレクトリを読み取る際、または最初の`EOF`の後に連続して読み取りを行い、その間にファイルが削除された場合に発生しました。

このバグに対処するため、Goの`syscall`パッケージ内の`ReadDirent`関数において、`darwin`（macOS）環境に限り、`EINVAL`および`ENOENT`エラーを`EOF`として扱うというワークアラウンドが導入されました。これは、Goのテストスイート（`all.bash`）がYosemite上でパスするようにするための実用的な解決策でした。この変更は、Russ Cox (rsc) によって実装され、Appleへのバグ報告が困難であったため、一時的な措置として採用されました。

## 変更の背景

このコミットの背景には、macOS Yosemiteのベータ版（特にビルド14A299l）に存在した、`readdir`関連のシステムコール（`getdirentries64`）のバグがあります。このバグにより、Goプログラムがディレクトリの内容を正しく読み取れない、または予期せぬエラーを受け取る可能性がありました。

Goチームは、このOSのバグを回避するために、一時的なワークアラウンドを導入しました。具体的には、`syscall`パッケージ内で`EINVAL`や`ENOENT`といった特定のエラーを`EOF`として扱うことで、Goの`Readdir`関数が正常に動作するようにしていました。

しかし、Yosemiteの最終リリースにおいて、Appleはこのバグを修正しました。これにより、Goランタイムに組み込まれていたワークアラウンドは不要となり、むしろ本来のOSの挙動と異なる動作を引き起こす可能性が出てきました。このコミットは、その不要になったワークアラウンドを削除し、GoランタイムがOSの正しい挙動に依存するように戻すことを目的としています。

また、コミットメッセージには、`http://swtch.com/~rsc/readdirbug.c` というC言語のプログラムがYosemite上でパスすることを確認したと記載されており、これによりOSのバグが修正されたことが裏付けられています。さらに、正規のファイルをディレクトリとして開こうとした場合にエラーとなるべき挙動を検証するための新しいテストが追加され、将来的な回帰を防ぐための対策も講じられています。

## 前提知識の解説

### `readdir`とディレクトリの読み取り

`readdir`は、Unix系システムにおいてディレクトリの内容を読み取るための一般的な操作を指します。プログラムは、ディレクトリを開き、その中にあるファイルやサブディレクトリのエントリを一つずつ読み取っていきます。Go言語の`os`パッケージの`Readdir`や`Readdirnames`関数は、この`readdir`操作を抽象化したものです。

### `getdirentries`システムコール

`getdirentries`（またはmacOSにおける`getdirentries64`）は、Unix系システムでディレクトリの内容を直接読み取るための低レベルなシステムコールです。これは、指定されたファイルディスクリプタ（開かれたディレクトリに対応）から、ディレクトリのエントリ（ファイル名、inode番号など）をバッファに読み込みます。このシステムコールは、一度に複数のエントリを読み込むことができ、バッファが満たされるか、ディレクトリの終端に達するまで読み込みを続けます。

### `EOF` (End Of File)

`EOF`は、ファイルやストリームの終わりに達したことを示す状態です。ディレクトリの読み取りにおいては、すべてのエントリを読み終えて、これ以上読み取るべきエントリがない場合に`EOF`となります。通常、`getdirentries`のようなシステムコールは、`EOF`に達すると読み込んだバイト数として0を返します。

### `EINVAL` (Invalid argument)

`EINVAL`は、システムコールに渡された引数が無効であることを示すエラーコードです。ディレクトリの読み取りにおいて、このエラーが返されることは通常ありません。Yosemiteのバグでは、ディレクトリの終端に達したにもかかわらず、誤ってこのエラーが返されることがありました。

### `ENOENT` (No such file or directory)

`ENOENT`は、指定されたファイルやディレクトリが存在しないことを示すエラーコードです。これもまた、ディレクトリの読み取りにおいて、ディレクトリ自体は開かれているにもかかわらず、このエラーが返されることは通常ありません。Yosemiteのバグでは、`EINVAL`と同様に、誤ってこのエラーが返されることがありました。

### システムコールとOSのバグ

システムコールは、ユーザー空間のプログラムがカーネル空間の機能（ファイルI/O、メモリ管理など）を利用するためのインターフェースです。OSのバグは、これらのシステムコールの実装に問題がある場合に発生し、プログラムが予期しない動作をしたり、誤ったエラーを受け取ったりすることがあります。Goのような高レベル言語のランタイムは、これらのシステムコールを内部的に利用しているため、OSのバグが直接影響を及ぼすことがあります。

## 技術的詳細

このコミットは、macOS Yosemiteの`readdir`実装における特定のバグとそのGoランタイムでの対処、そしてその対処の削除という一連の経緯を反映しています。

**Yosemiteベータ版のバグ**:
macOS Yosemiteのベータ版（特にビルド14A299l）では、`getdirentries64`システムコールにバグがありました。このバグは、ディレクトリの終端に達した際に、本来であれば読み込んだバイト数として0（`EOF`を示す）を返すはずが、誤って`EINVAL`（Invalid argument）または`ENOENT`（No such file or directory）エラーを返すというものでした。
コミットメッセージに記載されているように、この問題は特に「単一の`getdirentries64`呼び出しで返されるような小さなディレクトリ」で発生し、さらに「EOFで2回目に読み取ろうとした場合」や「2回目の呼び出しの間にファイルが削除された場合」に顕著でした。これは、OSがディレクトリの状態を正しく管理できていない、または`getdirentries64`の内部ロジックに欠陥があったことを示唆しています。

**Goランタイムのワークアラウンド**:
Goランタイムは、このOSのバグを回避するために、`src/syscall/syscall_bsd.go`内の`ReadDirent`関数にワークアラウンドを導入していました。このワークアラウンドは、`runtime.GOOS == "darwin"`（macOS環境）の場合に、`Getdirentries`システムコールが`EINVAL`または`ENOENT`を返した場合でも、それを`nil`（エラーなし、つまり`EOF`として）として扱うというものでした。
この対処は、GoのテストスイートがYosemite上でパスするようにするための緊急措置であり、OSのバグが修正されるまでの間、Goプログラムがディレクトリ読み取りでクラッシュしたり、誤動作したりするのを防ぐ目的がありました。

**Yosemite最終リリースでのバグ修正とワークアラウンドの削除**:
Yosemiteの最終リリースにおいて、Appleはこの`readdir`のバグを修正しました。コミットメッセージでは、`http://swtch.com/~rsc/readdirbug.c`にあるC言語のテストプログラムがYosemite上でパスすることを確認したと述べており、これによりOS側の修正が確認されました。
OSのバグが修正されたため、Goランタイムに組み込まれていたワークアラウンドは不要となり、むしろGoがOSの正しい挙動を妨げる可能性がありました。そのため、このコミットでは、そのワークアラウンドコードを`src/syscall/syscall_bsd.go`から削除しています。

**新しいテストの追加**:
ワークアラウンドの削除と同時に、`src/os/os_test.go`に`TestReaddirOfFile`という新しいテストが追加されました。このテストの目的は、正規のファイル（ディレクトリではないファイル）に対して`Readdirnames`を呼び出した場合に、適切にエラーが返されることを検証することです。これは、将来的に同様の`readdir`関連のバグがGoランタイムに忍び込むのを防ぐための回帰テストとして機能します。

この一連の変更は、GoランタイムがOSの挙動に密接に依存していること、そしてOSのバグに対して一時的な対処を施しつつも、OS側の修正が確認され次第、その対処を速やかに削除して本来のクリーンな状態に戻すという、堅実な開発プラクティスを示しています。

## コアとなるコードの解説

### `src/os/os_test.go` の変更点

追加された `TestReaddirOfFile` 関数は、Goの `os` パッケージの堅牢性を高めるための重要なテストです。

1.  **一時ファイルの作成**:
    ```go
    f, err := ioutil.TempFile("", "_Go_ReaddirOfFile")
    if err != nil {
        t.Fatal(err)
    }
    defer Remove(f.Name())
    ```
    `ioutil.TempFile` を使用して一時ファイルを作成します。このファイルはテスト終了時に `defer Remove(f.Name())` によって確実に削除されます。

2.  **ファイルへの書き込みとクローズ**:
    ```go
    f.Write([]byte("foo"))
    f.Close()
    ```
    作成した一時ファイルに少量のデータ（"foo"）を書き込み、ファイルをクローズします。これにより、このファイルが通常のファイルであることが保証されます。

3.  **ファイルを `os.Open` で開く**:
    ```go
    reg, err := Open(f.Name())
    if err != nil {
        t.Fatal(err)
    }
    defer reg.Close()
    ```
    `os.Open` を使用して、先ほど作成したファイルを再度開きます。ここで得られる `reg` は `*os.File` 型であり、これはファイルとディレクトリの両方を扱うことができます。

4.  **`Readdirnames` の呼び出しとエラーチェック**:
    ```go
    names, err := reg.Readdirnames(-1)
    if err == nil {
        t.Error("Readdirnames succeeded; want non-nil error")
    }
    if len(names) > 0 {
        t.Errorf("unexpected dir names in regular file: %q", names)
    }
    ```
    ここがテストの核心です。`reg.Readdirnames(-1)` を呼び出します。`Readdirnames` は、ファイルディスクリプタが指すものがディレクトリである場合にその内容を読み取る関数です。しかし、ここでは通常のファイルを指しているため、この呼び出しはエラーを返す**べき**です。

    -   `if err == nil`: エラーが返されなかった場合、それは予期せぬ成功であり、テストは失敗します。
    -   `if len(names) > 0`: もし、通常のファイルからディレクトリ名が読み取られてしまった場合（これはありえない挙動）、それも予期せぬ結果であり、テストは失敗します。

このテストは、Goの `os` パッケージが、ディレクトリではないファイルに対して `Readdirnames` のようなディレクトリ操作関数が呼び出されたときに、適切にエラーを返すことを保証します。これは、OSの`readdir`関連のバグが修正されたことを確認し、将来的な回帰を防ぐための重要な安全策となります。

### `src/syscall/syscall_bsd.go` の変更点

`syscall_bsd.go` は、BSD系のOS（macOSを含む）におけるシステムコールをGoから呼び出すための低レベルな実装を含んでいます。このファイルから削除されたコードは、macOS Yosemiteの`readdir`バグに対する直接的なワークアラウンドでした。

**削除されたコードの概要**:

```go
	n, err = Getdirentries(fd, buf, base)

	// On OS X 10.10 Yosemite, if you have a directory that can be returned
	// in a single getdirentries64 call (for example, a directory with one file),
	// and you read from the directory at EOF twice, you get EOF both times:
	//	fd = open("dir")
	//	getdirentries64(fd) // returns data
	//	getdirentries64(fd) // returns 0 (EOF)
	//	getdirentries64(fd) // returns 0 (EOF)
	//
	// But if you remove the file in the middle between the two calls, the
	// second call returns an error instead.
	//	fd = open("dir")
	//	getdirentries64(fd) // returns data
	//	getdirentries64(fd) // returns 0 (EOF)
	//	remove("dir/file")
	//	getdirentries64(fd) // returns ENOENT/EINVAL
	//
	// Whether you get ENOENT or EINVAL depends on exactly what was
	// in the directory. It is deterministic, just data-dependent.
	//
	// This only happens in small directories. A directory containing more data
	// than fits in a 4k getdirentries64 call will return EOF correctly.
	// (It's not clear if the criteria is that the directory be split across multiple
	// getdirentries64 calls or that it be split across multiple file system blocks.)
	//
	// We could change package os to avoid the second read at EOF,
	// and maybe we should, but that's a bit involved.
	// For now, treat the EINVAL/ENOENT as EOF.
	if runtime.GOOS == "darwin" && (err == EINVAL || err == ENOENT) {
		err = nil
	}

	return
```

このコードブロックは、`Getdirentries`システムコールが返したエラーをチェックし、もしそれがmacOS (`runtime.GOOS == "darwin"`) であり、かつエラーが `EINVAL` または `ENOENT` であった場合に、エラーを `nil` に上書きしていました。これは、Yosemiteのバグによって誤って返されるこれらのエラーを、本来期待される`EOF`（エラーなし）として扱うためのロジックでした。

**削除の理由**:

Yosemiteの最終リリースでOS側のバグが修正されたため、このワークアラウンドは不要になりました。OSが正しく`EOF`を返すようになったため、Goランタイムがエラーを上書きする必要がなくなったのです。このコードを削除することで、GoはOSの本来の挙動に素直に従うようになり、将来的にOSの`readdir`実装がさらに改善された場合にも、Goランタイムがその恩恵を受けられるようになります。

この変更は、Goが低レベルなOSの挙動にどのように適応し、そしてOS側の修正に応じてどのように自身のコードベースをクリーンアップしていくかを示す良い例です。

## 元コミット内容

このコミットがrevertしている元のコミットは、`https://golang.org/cl/119530044` であり、その内容は以下の通りです。

OS X 10.10 Yosemiteのベータ版（ビルド14A299l）において、`getdirentries64`システムコールが特定の条件下で`EOF`（End Of File）ではなく`EINVAL`（Invalid argument）または`ENOENT`（No such file or directory）エラーを誤って返すバグが存在しました。この問題は、特に小さなディレクトリを読み取る際、または最初の`EOF`の後に連続して読み取りを行い、その間にファイルが削除された場合に発生しました。

このバグに対処するため、Goの`syscall`パッケージ内の`ReadDirent`関数において、`darwin`（macOS）環境に限り、`EINVAL`および`ENOENT`エラーを`EOF`として扱うというワークアラウンドが導入されました。これは、Goのテストスイート（`all.bash`）がYosemite上でパスするようにするための実用的な解決策でした。この変更は、Russ Cox (rsc) によって実装され、Appleへのバグ報告が困難であったため、一時的な措置として採用されました。

## 変更の背景

このコミットの背景には、macOS Yosemiteのベータ版（特にビルド14A299l）に存在した、`readdir`関連のシステムコール（`getdirentries64`）のバグがあります。このバグにより、Goプログラムがディレクトリの内容を正しく読み取れない、または予期せぬエラーを受け取る可能性がありました。

Goチームは、このOSのバグを回避するために、一時的なワークアラウンドを導入しました。具体的には、`syscall`パッケージ内で`EINVAL`や`ENOENT`といった特定のエラーを`EOF`として扱うことで、Goの`Readdir`関数が正常に動作するようにしていました。

しかし、Yosemiteの最終リリースにおいて、Appleはこのバグを修正しました。これにより、Goランタイムに組み込まれていたワークアラウンドは不要となり、むしろ本来のOSの挙動と異なる動作を引き起こす可能性が出てきました。このコミットは、その不要になったワークアラウンドを削除し、GoランタイムがOSの正しい挙動に依存するように戻すことを目的としています。

また、コミットメッセージには、`http://swtch.com/~rsc/readdirbug.c` というC言語のプログラムがYosemite上でパスすることを確認したと記載されており、これによりOSのバグが修正されたことが裏付けられています。さらに、正規のファイルをディレクトリとして開こうとした場合にエラーとなるべき挙動を検証するための新しいテストが追加され、将来的な回帰を防ぐための対策も講じられています。

## 前提知識の解説

### `readdir`とディレクトリの読み取り

`readdir`は、Unix系システムにおいてディレクトリの内容を読み取るための一般的な操作を指します。プログラムは、ディレクトリを開き、その中にあるファイルやサブディレクトリのエントリを一つずつ読み取っていきます。Go言語の`os`パッケージの`Readdir`や`Readdirnames`関数は、この`readdir`操作を抽象化したものです。

### `getdirentries`システムコール

`getdirentries`（またはmacOSにおける`getdirentries64`）は、Unix系システムでディレクトリの内容を直接読み取るための低レベルなシステムコールです。これは、指定されたファイルディスクリプタ（開かれたディレクトリに対応）から、ディレクトリのエントリ（ファイル名、inode番号など）をバッファに読み込みます。このシステムコールは、一度に複数のエントリを読み込むことができ、バッファが満たされるか、ディレクトリの終端に達するまで読み込みを続けます。

### `EOF` (End Of File)

`EOF`は、ファイルやストリームの終わりに達したことを示す状態です。ディレクトリの読み取りにおいては、すべてのエントリを読み終えて、これ以上読み取るべきエントリがない場合に`EOF`となります。通常、`getdirentries`のようなシステムコールは、`EOF`に達すると読み込んだバイト数として0を返します。

### `EINVAL` (Invalid argument)

`EINVAL`は、システムコールに渡された引数が無効であることを示すエラーコードです。ディレクトリの読み取りにおいて、このエラーが返されることは通常ありません。Yosemiteのバグでは、ディレクトリの終端に達したにもかかわらず、誤ってこのエラーが返されることがありました。

### `ENOENT` (No such file or directory)

`ENOENT`は、指定されたファイルやディレクトリが存在しないことを示すエラーコードです。これもまた、ディレクトリの読み取りにおいて、ディレクトリ自体は開かれているにもかかわらず、このエラーが返されることは通常ありません。Yosemiteのバグでは、`EINVAL`と同様に、誤ってこのエラーが返されることがありました。

### システムコールとOSのバグ

システムコールは、ユーザー空間のプログラムがカーネル空間の機能（ファイルI/O、メモリ管理など）を利用するためのインターフェースです。OSのバグは、これらのシステムコールの実装に問題がある場合に発生し、プログラムが予期しない動作をしたり、誤ったエラーを受け取ったりすることがあります。Goのような高レベル言語のランタイムは、これらのシステムコールを内部的に利用しているため、OSのバグが直接影響を及ぼすことがあります。

## 技術的詳細

このコミットは、macOS Yosemiteの`readdir`実装における特定のバグとそのGoランタイムでの対処、そしてその対処の削除という一連の経緯を反映しています。

**Yosemiteベータ版のバグ**:
macOS Yosemiteのベータ版（特にビルド14A299l）では、`getdirentries64`システムコールにバグがありました。このバグは、ディレクトリの終端に達した際に、本来であれば読み込んだバイト数として0（`EOF`を示す）を返すはずが、誤って`EINVAL`（Invalid argument）または`ENOENT`（No such file or directory）エラーを返すというものでした。
コミットメッセージに記載されているように、この問題は特に「単一の`getdirentries64`呼び出しで返されるような小さなディレクトリ」で発生し、さらに「EOFで2回目に読み取ろうとした場合」や「2回目の呼び出しの間にファイルが削除された場合」に顕著でした。これは、OSがディレクトリの状態を正しく管理できていない、または`getdirentries64`の内部ロジックに欠陥があったことを示唆しています。

**Goランタイムのワークアラウンド**:
Goランタイムは、このOSのバグを回避するために、`src/syscall/syscall_bsd.go`内の`ReadDirent`関数にワークアラウンドを導入していました。このワークアラウンドは、`runtime.GOOS == "darwin"`（macOS環境）の場合に、`Getdirentries`システムコールが`EINVAL`または`ENOENT`を返した場合でも、それを`nil`（エラーなし、つまり`EOF`として）として扱うというものでした。
この対処は、GoのテストスイートがYosemite上でパスするようにするための緊急措置であり、OSのバグが修正されるまでの間、Goプログラムがディレクトリ読み取りでクラッシュしたり、誤動作したりするのを防ぐ目的がありました。

**Yosemite最終リリースでのバグ修正とワークアラウンドの削除**:
Yosemiteの最終リリースにおいて、Appleはこの`readdir`のバグを修正しました。コミットメッセージでは、`http://swtch.com/~rsc/readdirbug.c`にあるC言語のテストプログラムがYosemite上でパスすることを確認したと述べており、これによりOS側の修正が確認されました。
OSのバグが修正されたため、Goランタイムに組み込まれていたワークアラウンドは不要となり、むしろGoがOSの正しい挙動を妨げる可能性がありました。そのため、このコミットでは、そのワークアラウンドコードを`src/syscall/syscall_bsd.go`から削除しています。

**新しいテストの追加**:
ワークアラウンドの削除と同時に、`src/os/os_test.go`に`TestReaddirOfFile`という新しいテストが追加されました。このテストの目的は、正規のファイル（ディレクトリではないファイル）に対して`Readdirnames`を呼び出した場合に、適切にエラーが返されることを検証することです。これは、将来的に同様の`readdir`関連のバグがGoランタイムに忍び込むのを防ぐための回帰テストとして機能します。

この一連の変更は、GoランタイムがOSの挙動に密接に依存していること、そしてOSのバグに対して一時的な対処を施しつつも、OS側の修正が確認され次第、その対処を速やかに削除して本来のクリーンな状態に戻すという、堅実な開発プラクティスを示しています。

## コアとなるコードの解説

### `src/os/os_test.go` の変更点

追加された `TestReaddirOfFile` 関数は、Goの `os` パッケージの堅牢性を高めるための重要なテストです。

1.  **一時ファイルの作成**:
    ```go
    f, err := ioutil.TempFile("", "_Go_ReaddirOfFile")
    if err != nil {
        t.Fatal(err)
    }
    defer Remove(f.Name())
    ```
    `ioutil.TempFile` を使用して一時ファイルを作成します。このファイルはテスト終了時に `defer Remove(f.Name())` によって確実に削除されます。

2.  **ファイルへの書き込みとクローズ**:
    ```go
    f.Write([]byte("foo"))
    f.Close()
    ```
    作成した一時ファイルに少量のデータ（"foo"）を書き込み、ファイルをクローズします。これにより、このファイルが通常のファイルであることが保証されます。

3.  **ファイルを `os.Open` で開く**:
    ```go
    reg, err := Open(f.Name())
    if err != nil {
        t.Fatal(err)
    }
    defer reg.Close()
    ```
    `os.Open` を使用して、先ほど作成したファイルを再度開きます。ここで得られる `reg` は `*os.File` 型であり、これはファイルとディレクトリの両方を扱うことができます。

4.  **`Readdirnames` の呼び出しとエラーチェック**:
    ```go
    names, err := reg.Readdirnames(-1)
    if err == nil {
        t.Error("Readdirnames succeeded; want non-nil error")
    }
    if len(names) > 0 {
        t.Errorf("unexpected dir names in regular file: %q", names)
    }
    ```
    ここがテストの核心です。`reg.Readdirnames(-1)` を呼び出します。`Readdirnames` は、ファイルディスクリプタが指すものがディレクトリである場合にその内容を読み取る関数です。しかし、ここでは通常のファイルを指しているため、この呼び出しはエラーを返す**べき**です。

    -   `if err == nil`: エラーが返されなかった場合、それは予期せぬ成功であり、テストは失敗します。
    -   `if len(names) > 0`: もし、通常のファイルからディレクトリ名が読み取られてしまった場合（これはありえない挙動）、それも予期せぬ結果であり、テストは失敗します。

このテストは、Goの `os` パッケージが、ディレクトリではないファイルに対して `Readdirnames` のようなディレクトリ操作関数が呼び出されたときに、適切にエラーを返すことを保証します。これは、OSの`readdir`関連のバグが修正されたことを確認し、将来的な回帰を防ぐための重要な安全策となります。

### `src/syscall/syscall_bsd.go` の変更点

`syscall_bsd.go` は、BSD系のOS（macOSを含む）におけるシステムコールをGoから呼び出すための低レベルな実装を含んでいます。このファイルから削除されたコードは、macOS Yosemiteの`readdir`バグに対する直接的なワークアラウンドでした。

**削除されたコードの概要**:

```go
	n, err = Getdirentries(fd, buf, base)

	// On OS X 10.10 Yosemite, if you have a directory that can be returned
	// in a single getdirentries64 call (for example, a directory with one file),
	// and you read from the directory at EOF twice, you get EOF both times:
	//	fd = open("dir")
	//	getdirentries64(fd) // returns data
	//	getdirentries64(fd) // returns 0 (EOF)
	//	getdirentries64(fd) // returns 0 (EOF)
	//
	// But if you remove the file in the middle between the two calls, the
	// second call returns an error instead.
	//	fd = open("dir")
	//	getdirentries64(fd) // returns data
	//	getdirentries64(fd) // returns 0 (EOF)
	//	remove("dir/file")
	//	getdirentries64(fd) // returns ENOENT/EINVAL
	//
	// Whether you get ENOENT or EINVAL depends on exactly what was
	// in the directory. It is deterministic, just data-dependent.
	//
	// This only happens in small directories. A directory containing more data
	// than fits in a 4k getdirentries64 call will return EOF correctly.
	// (It's not clear if the criteria is that the directory be split across multiple
	// getdirentries64 calls or that it be split across multiple file system blocks.)
	//
	// We could change package os to avoid the second read at EOF,
	// and maybe we should, but that's a bit involved.
	// For now, treat the EINVAL/ENOENT as EOF.
	if runtime.GOOS == "darwin" && (err == EINVAL || err == ENOENT) {
		err = nil
	}

	return
```

このコードブロックは、`Getdirentries`システムコールが返したエラーをチェックし、もしそれがmacOS (`runtime.GOOS == "darwin"`) であり、かつエラーが `EINVAL` または `ENOENT` であった場合に、エラーを `nil` に上書きしていました。これは、Yosemiteのバグによって誤って返されるこれらのエラーを、本来期待される`EOF`（エラーなし）として扱うためのロジックでした。

**削除の理由**:

Yosemiteの最終リリースでOS側のバグが修正されたため、このワークアラウンドは不要になりました。OSが正しく`EOF`を返すようになったため、Goランタイムがエラーを上書きする必要がなくなったのです。このコードを削除することで、GoはOSの本来の挙動に素直に従うようになり、将来的にOSの`readdir`実装がさらに改善された場合にも、Goランタイムがその恩恵を受けられるようになります。

この変更は、Goが低レベルなOSの挙動にどのように適応し、そしてOS側の修正に応じてどのように自身のコードベースをクリーンアップしていくかを示す良い例です。

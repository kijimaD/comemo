## 変更の背景
このコミットは、Go言語のパーサー（`go/parser`パッケージ）がメソッドレシーバに関する特定のチェックを構文解析時（parse-time）に行わないように変更することを目的としています。

コミットメッセージによると、この変更の主な理由は以下の通りです。
1.  **AST (抽象構文木) とプリンターの関心外**: 構文解析の出力であるASTや、ASTを元にコードを整形するプリンターは、メソッドレシーバのセマンティックな妥当性（例えば、レシーバが1つであるか、その型が識別子であるかなど）には関心がありません。これらは純粋に構文的な構造を表現するものです。
2.  **`go/types`によるより良いエラーメッセージの提供**: メソッドレシーバのセマンティックなチェックは、Goの型チェッカーである`go/types`パッケージの役割です。`go/types`は、コード全体の型情報やスコープ情報など、より豊富なコンテキストを持っており、これにより、パーサーが行うよりも正確で、かつユーザーにとって理解しやすいエラーメッセージを提供できます。

この変更は、Goのツールチェインにおける各コンポーネントの責任範囲をより明確にし、エラー報告の質を向上させることを意図しています。コミットメッセージには「Fixes #8493」とありますが、このIssueの詳細は現在のところ確認できませんでした。しかし、この変更が`go/types`パッケージのテスト更新を必要とすることが示されており、これは責任の移行が単なるコード削除ではなく、システム全体の整合性を考慮したものであることを示唆しています。

## 前提知識の解説

### Go言語のパーサー (`go/parser`)
`go/parser`パッケージは、Go言語のソースコードを解析し、抽象構文木（AST: Abstract Syntax Tree）を生成する役割を担います。パーサーは、ソースコードがGo言語の文法規則に準拠しているかをチェックし、その構造をASTというデータ構造で表現します。通常、パーサーは構文エラーを報告しますが、セマンティックな（意味的な）エラーのチェックは後続のフェーズに任せることが多いです。

### 抽象構文木 (AST - `go/ast`)
`go/ast`パッケージは、Go言語のソースコードの抽象構文木を表現するためのデータ構造を定義しています。ASTは、プログラムの構造を階層的に表現したもので、コンパイラや各種ツールがソースコードを理解し、操作するための基盤となります。例えば、関数宣言、変数宣言、式、ステートメントなどがASTのノードとして表現されます。

### 型チェッカー (`go/types`)
`go/types`パッケージは、Go言語のプログラムの型チェックとセマンティック解析を行う役割を担います。パーサーが生成したASTを受け取り、変数や関数の型が正しく使用されているか、未定義の識別子がないか、メソッド呼び出しが正しいかなど、プログラムの意味的な正当性を検証します。型チェッカーは、構文解析だけでは検出できない、より深いレベルのエラーを報告します。

### メソッドレシーバ
Go言語において、メソッドは特定の型に関連付けられた関数です。メソッドを定義する際には、そのメソッドがどの型に属するかを示す「レシーバ」を指定します。レシーバは、関数名の前に括弧で囲んで記述されます。
例: `func (r MyType) MyMethod() { ... }`
ここで `(r MyType)` がレシーバです。レシーバは値レシーバ（`MyType`）またはポインタレシーバ（`*MyType`）のいずれかになります。Goの仕様では、メソッドは常に1つのレシーバを持つ必要があります。

### Goのコンパイルプロセス
Go言語のコンパイルプロセスは、大まかに以下のフェーズに分けられます。
1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換します。
2.  **構文解析 (Parsing)**: トークンのストリームを解析し、プログラムの構文構造をASTとして構築します。このフェーズで`go/parser`が使用されます。
3.  **セマンティック解析/型チェック (Semantic Analysis/Type Checking)**: ASTを解析し、プログラムの意味的な正当性（型の一貫性、スコープ規則など）を検証します。このフェーズで`go/types`が使用されます。
4.  **中間コード生成 (Intermediate Code Generation)**: ASTから、より低レベルの中間表現を生成します。
5.  **最適化 (Optimization)**: 中間コードを最適化し、実行効率を向上させます。
6.  **コード生成 (Code Generation)**: 最終的な機械語コードを生成します。

このコミットは、構文解析フェーズとセマンティック解析/型チェックフェーズ間の責任分担を調整するものです。

## 技術的詳細
このコミットの技術的な核心は、Go言語のパーサーが「構文解析」というその本来の役割に徹し、セマンティックなチェックを「型チェック」のフェーズに完全に委ねるという設計思想の明確化にあります。

以前の`go/parser`は、メソッドレシーバの定義において、以下のセマンティックなチェックを構文解析時に行っていました。
*   **レシーバの数のチェック**: メソッドは厳密に1つのレシーバを持つ必要があるというGoの仕様に合致しているか。
*   **レシーバの型のチェック**: レシーバの基本型が識別子であるか（例: `(r MyType)` の `MyType` が識別子であるか）。

これらのチェックは、純粋な構文解析の範囲を超え、プログラムの意味的な妥当性に関わるものです。コミットメッセージが指摘するように、ASTやプリンターはこれらのセマンティックな詳細を必要としません。ASTは単に「ここにレシーバリストがあり、その中にフィールドが1つある」という構文構造を表現すれば十分です。

`go/types`パッケージは、AST全体と、インポートされたパッケージ、宣言された識別子、スコープ情報など、プログラムに関するより広範なコンテキストにアクセスできます。この豊富な情報に基づいて、`go/types`は以下のようなより洗練されたエラーメッセージを提供できます。
*   レシーバが複数ある場合、どのレシーバが問題なのかを具体的に指摘する。
*   レシーバの型が不正な場合、その型がなぜ不正なのか（例えば、未定義の型である、リテラルであるなど）を詳細に説明する。

パーサーからこれらのセマンティックチェックを取り除くことで、パーサーはよりシンプルになり、その役割が「有効なGoの構文をASTに変換する」ことに限定されます。これにより、Goのツールチェイン全体のモジュール性が向上し、各コンポーネントがそれぞれの専門分野に集中できるようになります。また、エラー報告のロジックが一箇所（`go/types`）に集約されるため、エラーメッセージの一貫性と品質が向上します。

この変更は、`go/types`パッケージがこれらのチェックを適切に処理できるように、そのテストを更新する必要があることを示唆しています。これは、単にコードを削除するだけでなく、責任の移行に伴うシステム全体の整合性を維持するための重要なステップです。

## コアとなるコードの解説

### 削除された `parseReceiver` 関数
削除された `parseReceiver` 関数は、メソッドレシーバの構文解析と、そのセマンティックな妥当性チェックの両方を行っていました。
*   `par := p.parseParameters(scope, false)`: まず、一般的なパラメータリストを解析する`parseParameters`を呼び出し、レシーバの構文構造を取得していました。
*   `if par.NumFields() != 1`: ここで、レシーバが厳密に1つであるかというセマンティックなチェックを行っていました。Goのメソッドは1つのレシーバしか持てないため、これに違反するとエラーを報告していました。
*   `base := unparen(deref(unparen(recv.Type)))` および `if _, isIdent := base.(*ast.Ident); !isIdent`: ここでは、レシーバの型が識別子であるかというセマンティックなチェックを行っていました。例えば、`(r int)` は有効ですが、`(r 123)` のようなリテラルは無効です。

これらのセマンティックなチェックが、パーサーの役割から外され、より適切な`go/types`パッケージに委譲されることになりました。

### `parseFuncDecl` 内の変更
`parseFuncDecl` 関数は、Goの関数宣言（通常の関数とメソッドの両方）を解析する役割を担っています。この関数内で、トークンが `token.LPAREN` (左括弧) である場合、それはメソッドレシーバの開始を示す可能性があるため、レシーバの解析を試みます。

変更前は `recv = p.parseReceiver(scope)` を呼び出していましたが、変更後は `recv = p.parseParameters(scope, false)` を直接呼び出すようになりました。
*   `parseParameters(scope, false)` は、一般的な関数パラメータリストを解析するために設計された関数です。この関数は、パラメータの構文構造をASTの`ast.FieldList`として返しますが、パラメータの数や型に関するセマンティックなチェックは行いません。
*   この変更により、`parseFuncDecl` はレシーバの「構文」を正しく解析し、ASTに組み込むことは引き続き行いますが、その「意味的な妥当性」の検証は行わなくなります。このセマンティックな検証は、後続の型チェックフェーズ（`go/types`）で行われることになります。

このコミットは、Goのコンパイラツールチェインの設計原則、特に各コンポーネントの責任範囲の明確化と、エラー報告の質の向上という観点から重要な変更と言えます。

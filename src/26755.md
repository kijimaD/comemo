## 変更の背景

このコミットは、GoコンパイラのSSAバックエンドにおけるコード生成の効率を向上させるためのものです。主な動機は以下の2点です。

1.  **`runtime.throw`の特殊な性質の活用**: `runtime.throw`関数は、Goランタイム内でパニックや致命的なエラーが発生した際に呼び出される関数であり、決して呼び出し元に戻りません。コンパイラがこの特性を認識することで、`runtime.throw`が呼び出された後のコードが到達不能であることを判断し、不要なコード生成を省略したり、より積極的な最適化を適用したりすることが可能になります。これは、`mapaccess1_faststr`のような特定のランタイム関数を調査している際に見つかった改善点とされています。
2.  **AMD64におけるLEA命令の最適化**: AMD64アーキテクチャには、"Load Effective Address" (LEA) という命令があります。この命令は、メモリのアドレス計算を行うだけでなく、汎用的な加算器としても非常に強力です。特に `x + y + c` のような複数の加算と定数オフセットを含む計算を、単一のLEA命令で効率的に実行できる場合があります。これにより、複数の`ADD`命令を使用するよりも少ない命令数で、より高速なコードを生成できます。

これらの改善は、Goプログラムの実行速度向上と、生成されるバイナリサイズの削減に寄与します。

## 前提知識の解説

### 1. GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現（IR: Intermediate Representation）を複数段階で利用します。SSA（Static Single Assignment）形式は、その中間表現の一つであり、最適化の主要なステージで用いられます。

*   **SSA形式**: 各変数が一度だけ代入されるようにする表現形式です。これにより、データフロー解析が容易になり、コンパイラはより効果的な最適化（例: 共通部分式の削除、デッドコードの削除、レジスタ割り当ての最適化など）を実行できます。
*   **バックエンド**: コンパイラの最終段階で、SSA形式のコードを特定のCPUアーキテクチャ（例: AMD64）の機械語に変換する部分を指します。この段階で、命令選択、レジスタ割り当て、スケジューリングなどの最適化が行われます。

### 2. AMD64アーキテクチャとLEA命令

*   **AMD64 (x86-64)**: 現代のほとんどのデスクトップおよびサーバーCPUで使用されている64ビット命令セットアーキテクチャです。
*   **LEA (Load Effective Address) 命令**:
    *   `LEA`命令は、メモリのアドレスを計算し、その結果をレジスタに格納します。しかし、実際にメモリからデータをロードするわけではありません。
    *   その強力なアドレス計算能力（`base + index * scale + displacement`）を利用して、汎用的な算術演算（特に加算と乗算）を効率的に実行できます。
    *   例えば、`LEA RAX, [RBX + RCX*1 + 8]` は `RAX = RBX + RCX + 8` と同等の計算を1命令で実行できます。これは、`ADD`命令を複数回使うよりも高速で、命令のエンコードサイズも小さくなる可能性があります。
    *   特に `x + y + c` の形式の計算は、LEA命令の `base + index * 1 + displacement` の形式に直接マッピングできるため、最適化の対象となります。

### 3. Goランタイム関数 `runtime.throw`, `gopanic`, `selectgo`

*   **`runtime.throw(string)`**: Goランタイム内で回復不能なエラーが発生した際に呼び出される関数です。この関数は決して呼び出し元に戻らず、プログラムを終了させます。コンパイラにとって、この関数が呼び出された後のコードは「到達不能（unreachable）」と見なすことができます。
*   **`gopanic(interface{})`**: Goの`panic`ステートメントが実行された際に、ランタイムが呼び出す関数です。これもまた、通常の制御フローでは呼び出し元に戻りません（ただし、`recover`によってパニックが捕捉された場合は別ですが、コンパイラの最適化の文脈では通常、到達不能と見なされます）。
*   **`selectgo()`**: `select`ステートメントのランタイム実装に関連する関数です。この関数も特定の条件下で呼び出し元に戻らない可能性があります。

コンパイラがこれらの関数の「決して戻らない」という特性を認識することで、その後のコードをデッドコードとして削除したり、コードパスの複雑さを軽減したりする最適化が可能になります。

## 技術的詳細

このコミットは、主に以下の2つの技術的改善に焦点を当てています。

### 1. `runtime.throw`の到達不能性に関する最適化

GoコンパイラのSSAバックエンドでは、関数呼び出しの後に制御フローが継続するかどうかを判断します。通常、関数呼び出しの後には次の命令が実行されますが、`runtime.throw`のような「決して戻らない」関数（noreturn function）の場合、その後のコードは実行されません。

このコミットでは、`src/cmd/compile/internal/gc/ssa.go`内の`stmt`関数において、`OCALLFUNC`（関数呼び出し）の処理に修正を加えています。具体的には、`runtime.throw`が呼び出された場合、その呼び出しを含むブロックを`ssa.BlockExit`としてマークするように変更されました。`ssa.BlockExit`は、そのブロックから制御フローが外に出ることを示し、コンパイラはこれを利用して、その後のコードが到達不能であることを認識し、不要なコード生成を抑制できます。

以前は`gopanic`と`selectgo`のみが同様に処理されていましたが、`runtime.throw`もこのリストに追加され、コンパイラがより正確な制御フロー情報を利用できるようになりました。特に、`compiling_runtime != 0`という条件が追加されており、これはランタイム自体をコンパイルしている場合にのみ`runtime.throw`の特殊な処理を適用することを示唆しています。これは、ユーザーコードから`runtime.throw`を直接呼び出すことは稀であり、ランタイム内部でのみその特性が重要になるためと考えられます。

### 2. AMD64における`x + y + c`形式のLEA命令への変換

この最適化は、`src/cmd/compile/internal/ssa/gen/AMD64.rules`と`src/cmd/compile/internal/ssa/rewriteAMD64.go`に実装されています。

*   **`AMD64.rules`**: これは、SSAオペレーションをAMD64の機械語命令に変換するためのルールを定義するファイルです。このコミットでは、`ADDQ`（64ビット加算）と`ADDQconst`（64ビット定数加算）の組み合わせを`LEAQ1`命令に変換する新しいルールが追加されています。
    *   具体的には、`(ADDQconst [c] (ADDQ x y))`、`(ADDQ (ADDQconst [c] x) y)`、`(ADDQ x (ADDQconst [c] y))` のようなパターンが、`(LEAQ1 [c] x y)` に変換されるようになります。
    *   `LEAQ1`は、`base + index * 1 + displacement` の形式でアドレスを計算するLEA命令のSSA内部表現です。これにより、`x + y + c` の計算が単一のLEA命令で表現され、より効率的なアセンブリコードが生成されます。

*   **`rewriteAMD64.go`**: このファイルには、`AMD64.rules`で定義されたルールに基づいて、SSAの値を書き換えるためのGoコードが自動生成されます。このコミットでは、`rewriteValueAMD64_OpAMD64ADDQ`および`rewriteValueAMD64_OpAMD64ADDQconst`関数に、上記のLEA変換ロジックが追加されています。
    *   これらの関数は、SSAの`ADDQ`や`ADDQconst`オペレーションを処理する際に、特定のパターン（`ADDQ (ADDQconst [c] x) y` や `ADDQ x (ADDQconst [c] y)` など）にマッチした場合、そのオペレーションを`LEAQ1`オペレーションに書き換える処理を実行します。
    *   これにより、コンパイラはSSAグラフ上でこれらの加算パターンを検出し、自動的にLEA命令に最適化されたコードを生成できるようになります。

これらの変更は、Goコンパイラが生成するAMD64アセンブリコードの品質を向上させ、特にアドレス計算や複数の加算を含む演算において、より効率的な命令シーケンスを利用できるようにします。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go`の変更

この変更は、Goコンパイラのフロントエンド（`gc`パッケージ）がSSA中間表現を生成する際に、特定のランタイム関数呼び出しの特性をSSAバックエンドに伝える方法を改善しています。

*   **変更前**: `gopanic`または`selectgo`が`Runtimepkg`（ランタイムパッケージ）内の関数として呼び出された場合、その呼び出しを含むブロックは`ssa.BlockExit`としてマークされていました。これは、これらの関数が呼び出し元に戻らないことをコンパイラに示し、その後のコードを到達不能として扱うためのものです。
*   **変更後**: `runtime.throw`関数もこのリストに追加されました。さらに、`compiling_runtime != 0`という条件が追加されています。これは、コンパイラがGoランタイム自体をコンパイルしている場合にのみ、`runtime.throw`を`ssa.BlockExit`として扱うことを意味します。ユーザーコードが`runtime.throw`を直接呼び出すことは通常なく、ランタイム内部でのみその「決して戻らない」という特性が重要になるため、この条件は適切なスコープを設定しています。
*   **効果**: この変更により、`runtime.throw`が呼び出された後のコードがデッドコードとしてより正確に認識され、不要なコード生成が削減される可能性があります。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules`の変更

このファイルは、SSAオペレーションをAMD64アセンブリ命令に変換するためのパターンマッチングルールを定義しています。

*   **追加されたルール**: `ADDQ`と`ADDQconst`の組み合わせを`LEAQ1`に変換する3つの新しいルールが追加されました。
    *   `(ADDQconst [c] (ADDQ x y)) -> (LEAQ1 [c] x y)`
    *   `(ADDQ (ADDQconst [c] x) y) -> (LEAQ1 [c] x y)`
    *   `(ADDQ x (ADDQconst [c] y)) -> (LEAQ1 [c] x y)`
*   **`LEAQ1`とは**: これはSSA内部でLEA命令を表すオペレーションの一つで、`base + index * 1 + displacement` の形式のアドレス計算に対応します。ここで`c`は定数オフセット（displacement）、`x`と`y`はレジスタ値（baseとindex）に対応します。
*   **効果**: これらのルールにより、コンパイラは`x + y + c`のような複数の加算と定数オフセットを含む計算パターンを検出し、それを単一のLEA命令に変換できるようになります。これにより、生成されるアセンブリコードの命令数が減り、実行効率が向上します。

### `src/cmd/compile/internal/ssa/rewriteAMD64.go`の変更

このファイルは、`AMD64.rules`で定義されたルールに基づいて自動生成されるコードを含んでいます。このコミットでは、`ADDQ`および`ADDQconst`オペレーションを処理するリライト関数に、LEA変換ロジックが手動で追加されています。

*   **追加されたリライトロジック**: `rewriteValueAMD64_OpAMD64ADDQ`関数と`rewriteValueAMD64_OpAMD64ADDQconst`関数内に、`ADDQ`と`ADDQconst`の組み合わせを`LEAQ1`に変換するための`for`ループと`if`条件が追加されています。
    *   これらのコードは、SSAグラフ内の`ADDQ`または`ADDQconst`オペレーションが特定のパターン（例: `(ADDQ (ADDQconst [c] x) y)`)にマッチするかどうかをチェックします。
    *   マッチした場合、元のオペレーションを`OpAMD64LEAQ1`にリセットし、定数`c`とオペランド`x`, `y`を新しい`LEAQ1`オペレーションの引数として設定します。
*   **効果**: このリライトロジックにより、SSAバックエンドは実行時にこれらの最適化パターンを検出し、より効率的なLEA命令に変換されたSSAオペレーションを生成します。最終的に、これはより最適化されたAMD64アセンブリコードの生成につながります。

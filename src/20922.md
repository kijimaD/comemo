## 変更の背景

このコミットは、Go 1.4のリリースに向けて、その変更点を公式ドキュメント `doc/go1.4.html` に反映させることを目的としています。特に、`go` コマンドに関連する多くの変更がこのドキュメントに追記されています。コミットメッセージにある「still need to do internal and import comments」という記述から、このコミットが `go` コマンドに関する変更点の大部分をカバーしているものの、まだ「internal」パッケージや「import comments」に関する記述が残っている途中段階の更新であることが示唆されます。

Go言語は、後方互換性を非常に重視していますが、新しい機能の追加や既存の挙動の改善に伴い、一部の仕様やツールの振る舞いが変更されることがあります。これらの変更は、ユーザーが新しいバージョンにスムーズに移行できるよう、詳細に文書化される必要があります。このコミットは、Go 1.4における重要な変更点、特に開発者が日常的に使用する `go` コマンドの挙動に関する情報を、公式リリースノートとして提供するための準備の一環として行われました。

具体的には、以下の主要な変更点がドキュメントに追加されています。

1.  **`unsafe` パッケージの互換性ガイドラインの明確化**: `unsafe` パッケージの使用がGoの型システムを迂回するものであるため、その互換性が保証されないことを明記。
2.  **`go generate` サブコマンドの導入**: ビルド前にソースコードを生成するツールを自動化するための新しいコマンドの追加。
3.  **ファイル名によるビルドタグの扱いの変更**: 特定のアーキテクチャやOSに特化したファイル名の命名規則に関する変更。
4.  **その他の `go` コマンドの変更**: `cgo` を使用しないCソースファイルのコンパイル拒否、`go test -o` フラグの追加、`go test` がすべての `_test.go` ファイルをコンパイルするようになる変更、`go build -a` フラグの挙動変更など。

これらの変更は、Go言語の進化と、より堅牢で使いやすい開発環境を提供するための継続的な取り組みを反映しています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語に関する前提知識が必要です。

*   **Go言語の互換性ガイドライン (Go compatibility guidelines)**: Go言語は、Go 1以降、後方互換性を非常に重視しており、既存のGo 1プログラムが新しいGoバージョンでも動作することを保証しています。しかし、一部の例外や特定の条件下では互換性が保証されない場合があります。
*   **`unsafe` パッケージ**: Go言語の `unsafe` パッケージは、Goの型システムを迂回し、ポインタ演算や任意の型へのキャストを可能にする機能を提供します。これにより、低レベルのメモリ操作やC言語との連携が可能になりますが、Goの安全な型システムを破るため、非常に注意して使用する必要があります。
*   **`go generate` コマンド**: Go 1.4で導入された新しいサブコマンドです。これは、コンパイル前にソースコードを生成するツール（例: `yacc`、`stringer` など）の実行を自動化するために使用されます。ソースファイル内の特定のコメント行 (`//go:generate`) を解析し、指定されたコマンドを実行します。
*   **ビルドタグ (Build Tags / Build Constraints)**: Go言語では、ソースファイルに特別なコメント (`// +build tag`) を記述することで、特定の条件（OS、アーキテクチャ、Goバージョンなど）に基づいてファイルのコンパイルを含めたり除外したりできます。これにより、プラットフォーム固有のコードや条件付きコンパイルを実現します。
*   **ファイル名によるビルドタグ**: ビルドタグの一種で、ファイル名自体に特定のサフィックス（例: `_windows.go`, `_amd64.go`）を付けることで、そのファイルが特定のOSやアーキテクチャでのみコンパイルされるように指定できます。
*   **`cgo`**: GoプログラムからC言語のコードを呼び出すためのメカニズムです。`cgo` を使用すると、GoとCの間の相互運用が可能になります。
*   **`go test` コマンド**: Go言語のテストフレームワークを実行するためのコマンドです。パッケージ内のテストファイル (`_test.go` で終わるファイル) をコンパイルし、テスト関数 (`TestXxx`) を実行します。
*   **`go build -a` フラグ**: `go build` コマンドのフラグで、すべての依存関係を強制的に再ビルドします。通常、キャッシュされたビルド結果がある場合でも、このフラグを使用すると最初からビルドが実行されます。

## 技術的詳細

このコミットによって `doc/go1.4.html` に追加された主要な技術的変更点は以下の通りです。

1.  **`unsafe` パッケージの互換性ガイドラインの明確化**:
    *   Go 1.4以前は、`unsafe` パッケージの使用がGoの互換性ガイドラインにどのように関連するかが明示されていませんでした。
    *   この変更により、`unsafe` パッケージはGoの型システムを破壊し、実装の詳細やデータの機械表現に依存するため、`unsafe` を使用するコードの互換性は保証されないことが明確に記述されました。
    *   これは技術的な変更ではなく、既存の挙動に関するドキュメントの明確化です。つまり、`unsafe` コードは常に互換性が保証されていなかったが、それが明示的に文書化されたということです。

2.  **`go generate` サブコマンドの導入**:
    *   Go 1.4で `go generate` という新しいサブコマンドが導入されました。
    *   このコマンドは、コンパイル前にソースコードを生成するツール（例: `yacc`、`stringer`）の実行を自動化することを目的としています。
    *   開発者はソースファイル内に `//go:generate command arguments` の形式でコメントを記述し、`go generate` を実行することで、これらのコマンドが自動的に実行され、必要なソースファイルが生成されます。
    *   これにより、コード生成プロセスが標準化され、ビルドシステムに統合しやすくなりました。

3.  **ファイル名によるビルドタグの扱いの変更**:
    *   Go 1.4以前は、`arm.go` のようにファイル名が直接アーキテクチャ名である場合もビルドタグとして扱われていました。
    *   しかし、これは新しいアーキテクチャが追加された際に、既存のソースコードが意図せずタグ付けされてしまう問題を引き起こす可能性がありました。
    *   Go 1.4からは、ファイル名によるビルドタグは、アンダースコア (`_`) が先行する場合にのみ有効となります（例: `gopher_arm.go`）。
    *   これにより、`windows.go` や `arm64.go` のようなファイルは、明示的なビルドタグ (`// +build windows`) を追加するか、`os_windows.go` や `support_arm64.go` のようにリネームする必要が生じました。これは後方互換性を破る変更点として明記されています。

4.  **その他の `go` コマンドの変更**:
    *   **`cgo` を使用しないCソースファイルのコンパイル拒否**: `cgo` が使用されていないパッケージでは、`go` コマンドはCソースファイル (`.c` ファイルなど) のコンパイルを拒否するようになりました。これは、将来的にCコンパイラ (`6c` など) がGoのインストールから削除される予定であるため、その準備として行われました。これにより、誤ったCソースの使用を防ぎます。
    *   **`go test -o` フラグの追加**: `go test` サブコマンドに、生成されるテストバイナリの名前を設定するための `-o` フラグが追加されました。これは他のサブコマンドの `-o` フラグと一貫性を持たせるための変更です。
    *   **`go test` がすべての `_test.go` ファイルをコンパイルするようになる変更**: 以前は、`_test.go` ファイル内に `Test` 関数が存在しない場合、`go test` はそのファイルを無視していました。Go 1.4からは、`Test` 関数がなくても、パッケージ内のすべての `*_test.go` ファイルがコンパイルおよびリンクされるようになりました。
    *   **`go build -a` フラグの挙動変更**: リリース版のGoインストールにおいて、`go build -a` フラグは標準ライブラリやコマンドを再ビルドしなくなりました。これは、インストールされているファイルを上書きするのを避けるためです。開発環境以外での使用における安全性を高めるための変更です。

これらの変更は、Go言語のツールチェインの成熟度を高め、より予測可能で堅牢な開発体験を提供することを目的としています。

## コアとなるコードの変更箇所

このコミットは `doc/go1.4.html` ファイルのみを変更しており、Go言語のランタイムやコンパイラの実際のコードを変更するものではありません。変更はHTMLドキュメントの特定のセクションに集中しています。

主な変更箇所は以下の通りです。

*   **`id="compatibility"` セクションの移動と内容の追加**:
    *   以前は `id="runtime"` の後にあった `id="compatibility"` セクションが、`id="impl"` (実装とツールに関する変更) の前に移動しました。
    *   `unsafe` パッケージに関する互換性ガイドラインの明確化についての記述が追加されました。

*   **`id="impl"` セクションの構造変更と内容の追加**:
    *   `id="impl"` の下に新しい `h3` タグが導入され、`id="runtime"` がそのサブセクションになりました。
    *   `id="gccgo"` セクションが移動し、`TODO gccgo news` が残されています。
    *   新しいセクションとして `id="internalpackages"` と `id="importcomments"` が追加されましたが、これらはまだ `TODO prose for these` となっており、具体的な内容は記述されていません。
    *   **`id="gogenerate"` セクションの追加**: `go generate` サブコマンドに関する詳細な説明が追加されました。
    *   **`id="filenames"` セクションの追加**: ファイル名によるビルドタグの扱いの変更に関する説明が追加されました。
    *   **`id="gocmd"` セクションの変更と内容の追加**: 以前は `Changes to the go command` だった見出しが `Other changes to the go command` に変更され、以下の `go` コマンドに関する変更点が箇条書きで詳細に記述されました。
        *   `cgo` を使用しないCソースファイルのコンパイル拒否。
        *   `go test -o` フラグの追加と `-file` フラグの削除。
        *   `go test` がすべての `_test.go` ファイルをコンパイルするようになる変更。
        *   `go build -a` フラグの挙動変更。

*   **既存の `TODO` コメントの削除**:
    *   以前のバージョンで存在した `TODO news about foobarblatz` や `TODO news about garbage collection`、`TODO news about stacks` といったプレースホルダーが削除され、具体的な内容に置き換えられています。
    *   ファイルの末尾にあった、以前のコミットで追加されたと思われる `cmd/go` 関連の変更点のリスト（例: `cmd/go: import comments (CL 124940043)`）が削除されています。これは、これらの内容がHTMLドキュメントの適切なセクションに詳細な説明として組み込まれたためと考えられます。

## コアとなるコードの解説

このコミットにおける「コアとなるコード」とは、`doc/go1.4.html` ファイル内のHTMLマークアップです。このHTMLの変更は、Go 1.4のリリースノートとして、ユーザーに以下の重要な情報を提供します。

1.  **`unsafe` パッケージの利用に関する注意喚起**:
    ```html
    <h2 id="compatibility">Changes to the compatibility guidelines</h2>
    <p>
    The <a href="/pkg/unsafe/"><code>unsafe</code></a> package allows one
    to defeat Go's type system by exploiting internal details of the implementation
    or machine representation of data.
    It was never explicitly specified what use of <code>unsafe</code> meant
    with respect to compatibility as specified in the
    <a href="go1compat.html">Go compatibilty guidelines</a>.
    The answer, of course, is that we can make no promise of compatibility
    for code that does unsafe things.
    </p>
    <p>
    We have clarified this situation in the documentation included in the release.
    The <a href="go1compat.html">Go compatibilty guidelines</a> and the
    docs for the <a href="/pkg/unsafe/"><code>unsafe</code></a> package
    are now explicit that unsafe code is not guaranteed to remain compatible.
    </p>
    <p>
    <em>Updating</em>: Nothing technical has changed; this is just a clarification
    of the documentation.
    </p>
    ```
    このセクションは、`unsafe` パッケージを使用するGoコードが、Goの将来のバージョンで互換性を維持することを保証できないことを明確に述べています。これは、`unsafe` がGoの内部実装に深く依存するためであり、Goの進化に伴い内部実装が変更される可能性があるためです。この記述は、開発者に対して `unsafe` の使用にはリスクが伴うことを強く警告しています。

2.  **`go generate` コマンドの紹介**:
    ```html
    <h3 id="gogenerate">The go generate subcommand</h3>
    <p>
    The <a href="/cmd/go/"><code>go</code></a> command has a new subcommand,
    <a href="/cmd/go/#hdr-Generate_Go_files_by_processing_source"><code>go generate</code></a>,
    to automate the running of tools to generate source code before compilation.
    For example, it can be used to run the <a href="http://en.wikipedia.org/wiki/Yacc"><code>yacc</code></a>
    compiler-compiler on a <code>.y</code> file to produce the Go source file implementing the grammar,
    or to automate the generation of <code>String</code> methods for typed constants using the new
    <a href="http://godoc.org/code.google.com/p/go.tools/cmd/stringer">stringer</a>
    tool in the <code>go.tools</code> repository.
    </p>
    <p>
    For more information, see the 
    <a href="http://golang.org/s/go1.4-generate">design document</a>.
    </p>
    ```
    このセクションは、Go 1.4で導入された `go generate` コマンドの目的と使用例を説明しています。これにより、開発者はコード生成プロセスをGoのビルドシステムに統合し、より効率的な開発ワークフローを構築できるようになります。`stringer` ツールのような具体的な例を挙げることで、その有用性を具体的に示しています。

3.  **ファイル名によるビルドタグの変更**:
    ```html
    <h3 id="filenames">Change to file name handling</h3>
    <p>
    Build constraints, also known as build tags, control compilation by including or excluding files
    (see the documentation <a href="/pkg/go/build/"><code>/go/build</code></a>).
    Compilation can also be controlled by the name of the file itself by "tagging" the file with
    a suffix (before the <code>.go</code> or <code>.s</code> extension) with an underscore
    and the name of the architecture or operating system.
    For instance, the file <code>gopher_arm.go</code> will only be compiled if the target
    processor is an ARM.
    </p>
    <p>
    Before Go 1.4, a file called just <code>arm.go</code> was similarly tagged, but this behavior
    can break sources when new architectures are added, causing files to suddenly become tagged.
    In 1.4, therefore, a file will be tagged in this manner only if the tag (architecture or operating
    system name) is preceded by an underscore.
    </p>
    <p>
    <em>Updating</em>: Packages that depend on the old behavior will no longer compile correctly.
    Files with names like <code>windows.go</code> or <code>arm64.go</code> should either
    have explicit build tags added to the source or be renamed to something like
    <code>os_windows.go</code> or <code>support_arm64.go</code>.
    </p>
    ```
    このセクションは、ファイル名によるビルドタグの挙動が変更されたことを説明し、既存のコードが影響を受ける可能性があることを警告しています。特に、`windows.go` のようなファイル名が、Go 1.4以降ではビルドタグとして認識されなくなるため、開発者はコードを修正する必要があることを明示しています。これは、将来的な互換性の問題を回避するための重要な変更です。

4.  **その他の `go` コマンドの変更点**:
    ```html
    <h3 id="gocmd">Other changes to the go command</h3>
    <ul>
    <li>
    Unless <a href="/cmd/cgo/"><code>cgo</code></a> is being used to build the package,
    the <code>go</code> command now refuses to compile C source files,
    since the relevant C compilers
    (<a href="/cmd/6c/"><code>6c</code></a> etc.)
    are intended to be removed from the installation in some future release.
    ...
    </li>
    <li>
    The <a href="/cmd/go/#hdr-Test_packages"><code>go</code> <code>test</code></a>
    subcommand has a new flag, <code>-o</code>, to set the name of the resulting binary,
    corresponding to the same flag in other subcommands.
    The non-functional <code>-file</code> flag has been removed.
    </li>
    <li>
    The <a href="/cmd/go/#hdr-Test_packages"><code>go</code> <code>test</code></a>
    will compile and link all <code>*_test.go</code> files in the package,
    even when there are no <code>Test</code> functions in them. 
    It previously ignored such files.
    </li>
    <li>
    The behavior of the
    <a href="/cmd/go/#hdr-Test_packages"><code>go</code> <code>build</code></a>'s
    <code>-a</code> flag has been changed for non-development installations.
    For installations running a released distribution, the <code>-a</code> flag will no longer
    rebuild the standard library and commands, to avoid overwriting the installation's files.
    </li>
    </ul>
    ```
    このリストは、`go` コマンドの様々な改善点と変更点をまとめています。特に、`cgo` を使用しないCソースファイルのコンパイル拒否は、Goのビルドシステムをよりクリーンに保ち、将来的なCコンパイラの削除に備えるための重要なステップです。`go test` の挙動変更は、テストの信頼性を高め、開発者が意図しないテストファイルの無視を防ぎます。`go build -a` の変更は、リリース版のGoインストールにおける安全性を向上させます。

これらのHTMLの変更は、Go 1.4のユーザーが新しい機能や変更された挙動を理解し、必要に応じて既存のコードを調整するための重要な情報源となります。

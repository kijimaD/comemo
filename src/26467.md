# [インデックス 26467] ファイルの概要

このコミットは、Goランタイムのプロファイリングテストの信頼性を向上させるための変更です。特に、CPUプロファイリングテストが、サンプル数が少ないために不安定になる問題を解決することを目的としています。テストハーネスを修正し、サンプル不足が原因と思われる失敗に対して、より長い期間でテストを再試行するメカニズムを導入しています。

## 元コミット内容

`runtime/pprof: retry failed tests with longer duration`

現在、プロファイリングテストはショートモードで約200ms実行されます。しかし、優れたプロファイリング機能を備えたプラットフォームであっても、これらのテストは本質的に不安定であり、特にビルダーのような負荷の高いシステムでは顕著です。

これを軽減するため、プロファイリングテストハーネスを修正し、サンプル数が不足している可能性を示す方法でテストが失敗した場合、より長い期間で再試行するようにします。

これには、プロファイルチェッカーを調整して、「致命的」エラーと「再試行可能」エラーを区別する必要があります。特に、ゼロサンプルでプロファイルを取得することを致命的なエラーとは見なさなくなりました（以前はパースエラーとして扱っていました）。これを、合計サンプル数が妥当であるかどうかをチェックする再試行可能なチェックに置き換えます。

Fixes #13943. Fixes #13871. Fixes #13223.

## 変更の背景

Go言語のCPUプロファイリングは、プログラムのパフォーマンス特性を理解し、最適化するために不可欠なツールです。`runtime/pprof`パッケージは、CPU使用率、メモリ割り当て、ゴルーチンスタックトレースなどのプロファイルデータを収集する機能を提供します。これらのプロファイリング機能の正確性と信頼性を保証するために、Goプロジェクトには一連のテストスイートが含まれています。

しかし、これらのプロファイリングテスト、特にCPUプロファイリングに関するものは、実行環境の負荷やタイミングの変動によって不安定になるという問題に直面していました。コミットメッセージによると、ショートモードで約200msという短い期間で実行されるテストでは、特にCI/CD環境（ビルダー）のような負荷の高いシステムで、十分なプロファイルサンプルが収集されないことが頻繁にありました。これにより、テストが本来検出したいバグとは関係なく、単にサンプル不足のために失敗するという「フレークネス（flakiness）」が発生していました。

このフレークネスは、開発者がテスト結果を信頼できなくし、実際のバグと一時的なテストの失敗を区別することを困難にします。結果として、開発プロセスが遅延し、CIシステムの効率が低下します。このコミットは、この根本的な問題に対処し、プロファイリングテストの信頼性を向上させることを目的としています。具体的には、以下のIssueがこのコミットによって修正されています。

*   **Issue #13943**: `runtime/pprof: TestCPUProfileMultithreaded fails on builders` - マルチスレッドCPUプロファイルテストがビルダーで失敗する問題。
*   **Issue #13871**: `runtime/pprof: TestCPUProfile fails on builders` - 基本的なCPUプロファイルテストがビルダーで失敗する問題。
*   **Issue #13223**: `runtime/pprof: TestCPUProfileMultithreaded fails on some systems` - 特定のシステムでマルチスレッドCPUプロファイルテストが失敗する問題。

これらのIssueはすべて、プロファイリングテストの不安定性、特にサンプル収集の不十分さに起因するものでした。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の概念について理解しておく必要があります。

### 1. CPUプロファイリングと`pprof`

*   **CPUプロファイリング**: プログラムがCPU時間をどのように消費しているかを測定する手法です。Goでは、`runtime/pprof`パッケージを通じてCPUプロファイリング機能が提供されます。これにより、どの関数が最も多くのCPU時間を使用しているかを特定し、パフォーマンスのボトルネックを見つけることができます。
*   **サンプリング**: CPUプロファイリングは通常、サンプリングベースで行われます。これは、一定の間隔（例: 100Hz、つまり1秒間に100回）でプログラムの実行状態（どの関数が実行されているか）を「スナップショット」として記録するものです。これらのスナップショット（サンプル）を多数集めることで、CPU時間の統計的な分布を推定します。
*   **`pprof`ツール**: Goのプロファイリングデータを視覚化・分析するためのツールです。`go tool pprof`コマンドで利用でき、テキスト、グラフ、Webインターフェースなど様々な形式でプロファイルを表示できます。

### 2. Goのテストフレームワーク

*   **`testing`パッケージ**: Goの標準テストフレームワークです。`go test`コマンドで実行され、`TestXxx`という名前の関数がテストとして認識されます。
*   **`t.Skipf` / `t.FailNow`**: `*testing.T`型のメソッドで、テストの動作を制御します。
    *   `t.Skipf`: テストをスキップします。特定の環境や条件でテストを実行しない場合に便利です。
    *   `t.FailNow`: 現在のテストを即座に失敗させ、そのテスト関数を終了します。
*   **`testing.Short()`**: `go test -short`フラグが指定されているかどうかを返します。これにより、開発者はテストの実行時間を短縮するために、一部のテストをスキップしたり、実行期間を短くしたりすることができます。

### 3. プロファイリングテストの課題

*   **フレークネス (Flakiness)**: テストが、コードの変更とは無関係に、実行ごとに成功したり失敗したりする現象です。プロファイリングテストでは、サンプリングの性質上、実行時のタイミングやシステム負荷によって収集されるサンプル数が変動しやすく、これがフレークネスの原因となることがあります。
*   **サンプル数**: プロファイリングの精度は、収集されるサンプル数に大きく依存します。サンプル数が少なすぎると、統計的な有意性が失われ、テストが誤って失敗する可能性があります。
*   **CI/CD環境**: 継続的インテグレーション/継続的デリバリー環境（例: Goのビルダー）では、複数のテストが並行して実行されたり、システムリソースが共有されたりするため、テストの実行環境が不安定になりやすく、プロファイリングテストのフレークネスが顕著になる傾向があります。

### 4. `time.Duration`

Goの`time`パッケージで定義されている型で、時間の長さを表します。ミリ秒（`time.Millisecond`）、秒（`time.Second`）などで指定できます。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、`src/runtime/pprof/pprof_test.go`ファイルに集中しています。

1.  **`cpuHogger`関数のシグネチャ変更**:
    *   `func cpuHogger(f func())` から `func cpuHogger(f func(), dur time.Duration)` へ変更。
    *   CPUを消費するループの条件が `time.Since(t0) < 250*time.Millisecond` から `time.Since(t0) < dur` へ変更。

2.  **`testCPUProfile`関数の大幅な変更**:
    *   `func testCPUProfile(t *testing.T, need []string, f func())` から `func testCPUProfile(t *testing.T, need []string, f func(dur time.Duration))` へ変更。
    *   テストの実行期間を制御する`duration`変数の導入。
    *   `maxDuration`定数（5秒）の導入。
    *   テストの再試行を実装するための`for duration <= maxDuration`ループの導入。
    *   プロファイル検証ロジックを`profileOk`関数に委譲。
    *   再試行時に`t.Logf("retrying with %s duration", duration)`でログを出力。
    *   最終的な失敗時に`t.FailNow()`を呼び出す。

3.  **`profileOk`ヘルパー関数の新規追加**:
    *   `func profileOk(t *testing.T, need []string, prof bytes.Buffer, duration time.Duration) (ok bool)` というシグネチャで新規追加。
    *   プロファイルデータのパースと検証ロジックをカプセル化。
    *   プロファイルが短すぎる場合のチェック条件を緩和 (`l < 5+2+3` から `l < 5+3`)。
    *   Windowsでのサンプル不足を`t.Log`で記録し、再試行を促す (`return false`)。
    *   収集されたサンプル数が理想的な値の1/4未満である場合に`ok = false`を設定し、再試行を促す。
    *   期待される関数にサンプルがない場合に`ok = false`を設定。

4.  **既存のテスト関数の呼び出し箇所の修正**:
    *   `TestCPUProfile`, `TestCPUProfileMultithreaded`, `TestMathBigDivide`, `TestStackBarrierProfiling`内で`testCPUProfile`を呼び出す際に、新しいシグネチャに合わせて`func(dur time.Duration)`を渡すように変更。

## コアとなるコードの解説

このコミットの核心は、プロファイリングテストの「フレークネス」を、より堅牢な再試行メカニズムと柔軟なプロファイル検証ロジックで解決することにあります。

### `cpuHogger`の変更

`cpuHogger`関数は、CPUプロファイリングの対象となる「作業」をシミュレートします。以前は固定の250ミリ秒で実行されていましたが、プロファイリングテストの不安定性の原因の一つが、この短い期間で十分なサンプルが収集されないことでした。`dur time.Duration`引数を導入することで、テストの実行時間を動的に調整できるようになり、特に再試行時にはより長い期間でCPUを消費させることが可能になりました。これにより、プロファイラがより多くのサンプルを収集する機会が増え、テストの信頼性が向上します。

### `testCPUProfile`の再試行ロジック

`testCPUProfile`関数は、プロファイリングテストの実行と検証のオーケストレーションを担当します。
最も重要な変更は、`for duration <= maxDuration`ループの導入です。

1.  **初期期間**: `testing.Short()`が`true`の場合は200ミリ秒、それ以外の場合は5秒という初期期間を設定します。これは、開発中の高速なフィードバックと、CI環境でのより堅牢なテストの両方に対応するためです。
2.  **プロファイルの実行と停止**: ループ内で`StartCPUProfile`と`StopCPUProfile`を呼び出し、`cpuHogger`を含むプロファイリング対象の関数`f`を実行します。
3.  **`profileOk`による検証**: 収集されたプロファイルデータは、新しく導入された`profileOk`関数に渡され、そのプロファイルが有効であるかどうかがチェックされます。
4.  **再試行の判断**: `profileOk`が`false`を返した場合、それはプロファイルが何らかの理由で不十分であったことを意味します。この場合、`duration`を倍にし、`maxDuration`（5秒）を超えない限り、テストは再試行されます。`t.Logf`で再試行のログが出力されるため、デバッグ時にも状況を把握しやすくなっています。
5.  **最終的な失敗**: `maxDuration`に達してもプロファイルが有効と判断されない場合、`t.FailNow()`が呼び出され、テストは最終的に失敗します。これにより、一時的なサンプル不足によるフレークネスは解消されつつも、実際のプロファイリングの問題は適切に検出されるようになります。

### `profileOk`による柔軟なプロファイル検証

`profileOk`関数は、プロファイルデータの「妥当性」を判断するための中心的なロジックを含んでいます。

*   **ゼロサンプルプロファイルの扱い**: 以前はゼロサンプルプロファイルはパースエラーとして扱われ、即座にテスト失敗につながる可能性がありました。しかし、システム負荷が高い場合など、短い期間ではゼロサンプルになることもあり得ます。この変更により、ゼロサンプル自体は致命的なエラーではなくなり、後続の「妥当なサンプル数」チェックに委ねられるようになりました。
*   **妥当なサンプル数のチェック**: `ideal := uintptr(duration * 100 / time.Second)`は、プロファイリング期間（`duration`）とサンプリングレート（GoのCPUプロファイラは通常100Hz）に基づいて、理想的なサンプル数を計算します。そして、実際に収集されたサンプル数（`samples`）がこの理想値の1/4未満である場合、またはゼロである場合に`ok = false`を返します。この閾値（1/4）は、ある程度の変動を許容しつつ、明らかにサンプルが不足している状況を検出するためのものです。
*   **Windowsでの特殊な扱い**: Windows環境ではタイマーの解像度が粗いため、サンプル数が少なくなる傾向があります。以前はこれを`t.Skip`で完全に回避していましたが、`profileOk`内では`t.Log`で警告を出しつつ`false`を返すことで、再試行メカニズムに組み込まれるようになりました。これにより、Windowsでも可能な限りテストを実行し、必要に応じて再試行することで、より多くの環境でテストの信頼性を向上させることができます。

これらの変更により、GoのCPUプロファイリングテストは、一時的な環境要因によるフレークネスに強くなり、より信頼性の高いテスト結果を提供するようになりました。

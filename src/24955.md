# [インデックス 24955] ファイルの概要

このコミットは、Go言語のビルドツールである `cmd/dist` における `GOARM` 環境変数の自動検出ロジックを改善するものです。特に、ARMアーキテクチャにおけるVFP (Vector Floating Point) サポートの検出方法が変更され、より堅牢なランタイム検出メカニズムが導入されました。これにより、特定のARMシステムで発生していた `GOARM` 検出の不具合が解消されています。

## 元コミット内容

このコミットは、`cmd/dist` ツールが `GOARM` 環境変数を自動検出する機能を再有効化し、その検出方法を改善するものです。具体的には、VFP (Vector Floating Point) サポートの有無をランタイムで検出するために、`cmd/dist` 自身を再実行するメカニズムが導入されました。これにより、以前の `/proc/cpuinfo` の解析に依存する方法から脱却し、より信頼性の高い検出が可能になります。

## 変更の背景

この変更は、GoのIssue #9732 と #12548 を解決するために行われました。

*   **Issue #9732: cmd/dist: GOARM detection is broken on some ARM systems**
    この問題は、一部のARMシステムで `cmd/dist` の `GOARM` 検出が正しく機能しないことを報告していました。特に、`/proc/cpuinfo` ファイルのフォーマットがシステムによって異なったり、必要な情報が欠落していたりする場合に、VFPサポートの誤検出や検出失敗が発生していました。これにより、GoプログラムがターゲットARMデバイスで正しく動作しない、または最適化された浮動小数点演算を利用できないといった問題が生じていました。

*   **Issue #12548: cmd/dist: GOARM detection fails on ARMv6 with VFPv2**
    この問題は、ARMv6アーキテクチャでVFPv2を搭載しているシステムにおいて、`GOARM` の検出が失敗することを具体的に指摘していました。`/proc/cpuinfo` の解析ロジックがVFPv2を正しく認識できず、結果として `GOARM=5` (VFPサポートなし) と誤って判断されることがありました。

これらの問題の根本原因は、`/proc/cpuinfo` の内容がLinuxカーネルのバージョンやディストリビューション、ハードウェアベンダーによって一貫性がなく、その解析に依存する検出方法が脆弱であったことにあります。より堅牢な検出方法が求められていました。

## 前提知識の解説

*   **GOARM環境変数**: Go言語のクロスコンパイルにおいて、ARMアーキテクチャの特定のサブアーキテクチャ（例: ARMv5, ARMv6, ARMv7）および浮動小数点ユニット（FPU）のサポートレベルを指定するために使用される環境変数です。
    *   `GOARM=5`: ARMv5TE、ソフトフロート（FPUなし、またはFPUがあっても使用しない）
    *   `GOARM=6`: ARMv6、VFPv1またはVFPv2（ハードフロート）
    *   `GOARM=7`: ARMv7、VFPv3またはVFPv4（ハードフロート）
    この値によって、コンパイラが生成するコードの命令セットやFPUの利用方法が決定されます。

*   **VFP (Vector Floating Point)**: ARMアーキテクチャ向けの浮動小数点演算ユニット（FPU）の拡張機能です。VFPは、単精度および倍精度の浮動小数点演算をハードウェアで高速に実行するために使用されます。VFPには複数のバージョン（VFPv1, VFPv2, VFPv3, VFPv4など）があり、それぞれサポートする命令セットや機能が異なります。

*   **`cmd/dist`**: Go言語のソースコードからGoツールチェイン（コンパイラ、リンカなど）をビルドするためのツールです。クロスコンパイル環境のセットアップや、ターゲットアーキテクチャの特性（この場合はGOARMの値）の自動検出など、ビルドプロセスの初期段階で重要な役割を果たします。

*   **`/proc/cpuinfo`**: Linuxシステムにおいて、CPUに関する詳細情報を提供する仮想ファイルです。CPUのモデル名、機能（features）、キャッシュサイズなどが含まれます。以前の `cmd/dist` は、このファイルの `Features` 行を解析してVFPサポートを判断していました。

*   **`SIGILL` (Illegal Instruction)**: プログラムが不正なCPU命令を実行しようとしたときにOSがプロセスに送信するシグナルです。このシグナルを受け取ると、通常、プログラムはクラッシュします。このコミットでは、この特性を利用してVFP命令のサポートを検出します。

*   **`re-exec` (再実行)**: プログラムが自分自身を再度実行することです。このコミットでは、`cmd/dist` がVFPサポートを検出するために、特定の引数 (`-check-goarm`) を付けて自分自身を子プロセスとして起動します。子プロセスはVFP命令の実行を試み、その結果（クラッシュするかどうか）を親プロセスが判断します。

## 技術的詳細

このコミットの主要な技術的変更点は、`GOARM` の自動検出方法を `/proc/cpuinfo` の解析から、**ランタイムでのVFP命令実行による検出**へと移行したことです。

1.  **`cmd/dist` の再実行メカニズム**:
    *   `src/cmd/dist/util.go` の `xgetgoarm()` 関数が変更されました。
    *   以前はLinuxシステムで `/proc/cpuinfo` を読み込み、`Features` 行を解析して `vfp` や `vfpv3` といったキーワードを探していました。
    *   新しい実装では、`os.Args[0]` (現在の実行可能ファイルのパス) と `-check-goarm` 引数を使って、`cmd/dist` 自身を子プロセスとして再実行します。
    *   親プロセスは子プロセスの標準出力 (`out`) をキャプチャし、その内容に "VFPv1 OK." や "VFPv3 OK." という文字列が含まれているかどうかをチェックします。

2.  **VFP命令の実行と `SIGILL` の利用**:
    *   `main()` 関数に、`-check-goarm` 引数が渡された場合に実行される新しいコードブロックが追加されました。
    *   このブロックでは、`useVFPv1()` と `useVFPv3()` という2つの関数が呼び出されます。
    *   これらの関数は、それぞれVFPv1とVFPv3の特定の命令を実行しようとします。
    *   もし実行中のARMプロセッサがそのVFP命令をサポートしていない場合、CPUは不正な命令として `SIGILL` シグナルを生成し、子プロセスはクラッシュします。
    *   子プロセスがクラッシュせずに `println("VFPv1 OK.")` や `println("VFPv3 OK.")` を出力できた場合、そのVFPバージョンがサポートされていると判断されます。

3.  **アセンブリコードによるVFP命令の実行**:
    *   `src/cmd/dist/vfp_arm.s` という新しいアセンブリファイルが追加されました。このファイルは `gc` (Goコンパイラ) と `arm` アーキテクチャ向けにビルドされます。
    *   `useVFPv1` 関数は `vmov.f64 d0, d0` というVFPv1でサポートされる命令を実行します。
    *   `useVFPv3` 関数は `vmov.f64 d0, #112` というVFPv3でサポートされる命令を実行します。この命令はVFPv1/v2ではサポートされていません。
    *   これらの命令は、レジスタ `d0` に値を移動する単純な操作ですが、その命令自体がCPUによってサポートされているかどうかが重要です。

4.  **クロスプラットフォーム対応**:
    *   `src/cmd/dist/vfp_default.s` という別の新しいアセンブリファイルが追加されました。これは `!arm` (非ARM) アーキテクチャ向けにビルドされます。
    *   このファイルでは `useVFPv1` と `useVFPv3` は単に `RET` (リターン) するだけの何もしない関数として定義されており、非ARMシステムでのコンパイルエラーを防ぎます。
    *   `src/cmd/dist/util_gccgo.go` では、`gccgo` コンパイラを使用する場合のために、これらの関数が空のGo関数として定義されています。これは `gccgo` がアセンブリコードの扱いが異なるためです。

このアプローチにより、`/proc/cpuinfo` のフォーマットの差異に悩まされることなく、実際のハードウェアがどのVFPバージョンをサポートしているかを確実に検出できるようになりました。

## コアとなるコードの解説

### `src/cmd/dist/util.go` の変更点

*   **`main()` 関数内の `-check-goarm` 処理**:
    `main` 関数に新しい条件分岐が追加されました。`cmd/dist` が `-check-goarm` というコマンドライン引数付きで実行された場合、`useVFPv1()` と `useVFPv3()` 関数を呼び出します。これらの関数はアセンブリで実装されており、VFP命令の実行を試みます。もし命令がサポートされていれば、それぞれ "VFPv1 OK." と "VFPv3 OK." を標準出力に出力し、正常終了します。サポートされていない命令を実行しようとすると、プロセスは `SIGILL` でクラッシュします。

*   **`xgetgoarm()` 関数の変更点**:
    `xgetgoarm()` 関数は、現在のシステムで最適な `GOARM` の値を決定する役割を担っています。
    *   以前の `/proc/cpuinfo` を解析するロジック（`cpuinfo := readfile("/proc/cpuinfo")` から始まる部分）が削除されました。
    *   代わりに、`run("", 0, os.Args[0], "-check-goarm")` を呼び出すことで、`cmd/dist` 自身を `-check-goarm` 引数付きで子プロセスとして実行します。
    *   子プロセスの標準出力 (`out`) を取得し、`strings.Contains` を使って "VFPv1 OK." と "VFPv3 OK." の文字列が含まれているかを確認します。
    *   両方がOKであれば `GOARM=7` (VFPv3サポート)、VFPv1のみOKであれば `GOARM=6` (VFPv1サポート)、どちらもOKでなければ `GOARM=5` (VFPサポートなし) を返します。

### `src/cmd/dist/util_gc.go` の変更点

*   `useVFPv1()` と `useVFPv3()` の関数宣言が追加されました。これらはGoのコードからは呼び出されますが、実際の実装はアセンブリ言語で行われます。Goコンパイラ (`gc`) がこれらの宣言を見て、対応するアセンブリ関数をリンクするようにします。

### `src/cmd/dist/vfp_arm.s` の新規追加

*   このファイルはARMアーキテクチャ向けのアセンブリコードを含みます。
*   `TEXT ·useVFPv1(SB),NOSPLIT,$0` と `TEXT ·useVFPv3(SB),NOSPLIT,$0` は、それぞれGoの `useVFPv1` と `useVFPv3` 関数に対応するアセンブリルーチンを定義しています。
*   `useVFPv1` では `WORD $0xeeb00b40` という命令が実行されます。これは `vmov.f64 d0, d0` というVFPv1で利用可能な命令の機械語表現です。
*   `useVFPv3` では `WORD $0xeeb70b00` という命令が実行されます。これは `vmov.f64 d0, #112` というVFPv3で導入された命令の機械語表現です。
*   これらの命令は、対応するVFPバージョンがサポートされていないCPUで実行されると `SIGILL` を発生させ、プロセスをクラッシュさせます。この挙動を利用して、VFPサポートの有無を検出します。

### `src/cmd/dist/vfp_default.s` の新規追加

*   このファイルは非ARMアーキテクチャ向けのアセンブリコードを含みます。
*   `useVFPv1` と `useVFPv3` は、単に `RET` (リターン) 命令を実行するだけの何もしない関数として定義されています。これにより、非ARMシステムでこれらの関数が呼び出されても安全に処理され、コンパイルエラーを防ぎます。

この一連の変更により、`cmd/dist` は `/proc/cpuinfo` の解析という不安定な方法に頼ることなく、実際のCPUのVFPサポートレベルを直接的かつ堅牢に検出できるようになりました。

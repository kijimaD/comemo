## 変更の背景

Go言語は伝統的に、すべての依存関係を単一のバイナリに含める静的リンクを主に行ってきました。これはデプロイの容易さという利点がある一方で、大規模なアプリケーションや多くのGoプログラムが共通のライブラリを使用する場合に、バイナリサイズが大きくなるという課題がありました。また、ビルド時間も長くなる傾向がありました。

このコミットは、Go 1.5で導入された共有ライブラリ機能の一部として、この課題を解決するために行われました。`-linkshared` フラグをリンカに追加することで、GoプログラムがGoでビルドされた共有ライブラリ（`go build -buildmode=shared` で作成されたもの）に動的にリンクできるようになります。これにより、複数のGoプログラムが同じ共有ライブラリを共有できるようになり、ディスク使用量の削減、メモリ使用量の効率化（共有ライブラリが一度ロードされれば複数のプロセスで共有されるため）、そして大規模プロジェクトにおけるビルド時間の短縮が期待されます。

## 前提知識の解説

### Goのビルドモード

Goにはいくつかのビルドモードがあります。
*   **`go build -buildmode=exe`**: デフォルトのビルドモードで、実行可能な単一のバイナリを生成します。すべての依存関係が静的にリンクされます。
*   **`go build -buildmode=shared`**: 複数のGoパッケージを一つの共有ライブラリ（例: `.so` ファイル）としてコンパイルします。この共有ライブラリは、他のGoプログラムから動的にリンクされることを意図しています。
*   **`go build -buildmode=c-shared`**: GoのパッケージをC言語から呼び出し可能な共有ライブラリとしてコンパイルします。これは、Goの機能をC、C++、Pythonなどの他の言語から利用したい場合に用いられます。

### リンカの役割

リンカ（この場合は `cmd/6l`）は、コンパイラによって生成されたオブジェクトファイルやライブラリを結合し、最終的な実行可能ファイルやライブラリを作成するツールです。リンカの主な役割は、未解決のシンボル（関数や変数の参照）を解決し、それらを適切なメモリ位置にマッピングすることです。

### 静的リンクと動的リンク

*   **静的リンク (Static Linking)**: プログラムが必要とするすべてのライブラリコードが、コンパイル時に最終的な実行可能ファイルにコピーされます。
    *   **利点**: 実行可能ファイルが自己完結型であり、デプロイが容易です。依存関係の問題（DLL Hellなど）が発生しにくいです。
    *   **欠点**: 実行可能ファイルのサイズが大きくなる傾向があります。複数のプログラムが同じライブラリを使用する場合でも、それぞれのバイナリにライブラリのコピーが含まれるため、ディスク容量やメモリの無駄が生じることがあります。ライブラリの更新があった場合、すべてのプログラムを再コンパイル・再デプロイする必要があります。
*   **動的リンク (Dynamic Linking)**: プログラムが必要とするライブラリコードは、実行時にロードされます。実行可能ファイルには、どのライブラリのどの関数を使用するかという情報（シンボル参照）のみが含まれます。
    *   **利点**: 実行可能ファイルのサイズが小さくなります。複数のプログラムが同じ共有ライブラリを使用する場合、ライブラリのコードはメモリ上で一度だけロードされ、共有されるため、メモリ効率が向上します。ライブラリの更新があった場合、プログラムを再コンパイルせずに、新しいライブラリに置き換えるだけで済みます（互換性がある場合）。
    *   **欠点**: デプロイ時に必要な共有ライブラリがシステムに存在することを確認する必要があります。バージョン管理が複雑になることがあります。

### シンボル解決

シンボル解決とは、リンカがプログラム内の関数や変数の名前（シンボル）を、それらが実際にメモリ上のどこに配置されるかというアドレスにマッピングするプロセスです。動的リンクの場合、一部のシンボル解決はプログラムの実行時に行われます。

### PLT (Procedure Linkage Table) / GOT (Global Offset Table)

動的リンクされたプログラムが共有ライブラリ内の関数を呼び出す際に使用されるメカニズムです。
*   **PLT**: 共有ライブラリ内の関数を呼び出すための小さなコードスタブのテーブルです。
*   **GOT**: 共有ライブラリ内のデータや関数の実際のアドレスを格納するテーブルです。

プログラムが共有ライブラリの関数を初めて呼び出す際、PLTのエントリがGOTを介してリンカに制御を渡し、リンカが実際の関数のアドレスを解決してGOTに書き込みます。2回目以降の呼び出しでは、PLTは直接GOTに格納されたアドレスを使用して関数を呼び出します。この「遅延解決」はパフォーマンスを向上させますが、特定の状況（例えば、Goランタイムの初期化時）では問題となることがあります。

## 技術的詳細

このコミットは、Goリンカに動的リンクのサポートを導入するために、以下の主要な変更と機能追加を行っています。

1.  **`-linkshared` フラグの導入**:
    *   `src/cmd/internal/ld/pobj.go` に `flag.BoolVar(&Linkshared, "linkshared", false, "link against installed Go shared libraries")` が追加され、リンカが `-linkshared` コマンドライン引数を受け入れるようになります。
    *   このフラグが設定されている場合、リンカはGo共有ライブラリに動的にリンクしようとします。
    *   `-linkshared` はELFシステム（Linuxなど）でのみ使用可能であり、それ以外のシステムではエラーとなります。

2.  **共有ライブラリの検索とロード**:
    *   `src/cmd/internal/ld/ld.go` の `addlib` 関数が変更され、ライブラリを検索する際に、通常のアーカイブファイル（`.a`）だけでなく、共有ライブラリの情報を記述した `.shlibname` ファイルも探すようになります。
    *   `.shlibname` ファイルが見つかった場合、そのファイルの内容（実際の共有ライブラリ名）を読み込み、`addlibpath` 関数に渡します。
    *   `src/cmd/internal/ld/lib.go` の `loadinternal` 関数も同様に、内部ライブラリをロードする際に `.shlibname` ファイルを考慮するよう変更されています。

3.  **`addlibpath` 関数の拡張**:
    *   `src/cmd/internal/ld/ld.go` の `addlibpath` 関数に `shlibnamefile` という新しい引数が追加されました。
    *   この引数が空でない場合、`ioutil.ReadFile` を使用して `.shlibname` ファイルの内容を読み込み、`Library` 構造体の新しい `Shlib` フィールドに格納します。この `Shlib` フィールドには、実際にリンクすべき共有ライブラリの名前が保持されます。

4.  **`ldshlibsyms` 関数の追加**:
    *   `src/cmd/internal/ld/lib.go` に `ldshlibsyms(shlib string)` という新しい関数が追加されました。
    *   この関数は、指定された共有ライブラリ（`shlib`）を開き、その動的シンボルテーブルを読み込みます。
    *   共有ライブラリから読み込んだシンボルは、リンカのシンボルテーブルに `SDYNIMPORT` タイプとして登録されます。これにより、リンカはこれらのシンボルが外部の共有ライブラリによって提供されることを認識します。
    *   重複するシンボルが見つかった場合、警告を発します。
    *   Goのランタイムが生成する特定の関数（型等価/ハッシュ関数など）が共有ライブラリによって上書きされる可能性があるため、`Textp`（テキストセクションのシンボルリスト）からこれらのシンボルを「アンステッチ」（リストから削除）するロジックが含まれています。これは、これらのシンボルに対してPCLN（PC-Line）テーブルエントリが生成されないようにするためです。

5.  **`DynlinkingGo` 関数の変更**:
    *   `src/cmd/internal/ld/lib.go` の `DynlinkingGo()` 関数が `Buildmode == BuildmodeShared || Linkshared` と変更されました。
    *   これは、`BuildmodeShared`（共有ライブラリ自体をビルドする場合）または `Linkshared`（共有ライブラリにリンクする実行ファイルをビルドする場合）のいずれかの状況で、Goコードが動的にリンクされることを示すようになります。

6.  **`hostlink` における `-znow` フラグの追加**:
    *   `src/cmd/internal/ld/lib.go` の `hostlink` 関数に、`Linkshared` かつ `Iself`（ELFシステムである）の場合に、外部リンカ（通常はGCC）に `-znow` フラグを渡すロジックが追加されました。
    *   `-znow` フラグは、PLT（Procedure Linkage Table）の遅延解決を無効にし、プログラム起動時にすべてのシンボル解決を強制的に行わせます。これは、Goランタイムが特定のタイミングで大量のスタックを使用する可能性があるため、PLTの遅延解決が予期せぬスタックオーバーフローを引き起こすのを防ぐための重要な変更です。

7.  **`deadcode` 関数での `main.init` と `main.main` のマーク**:
    *   `src/cmd/internal/ld/go.go` の `deadcode` 関数が変更され、`Linkshared` かつ `Buildmode == BuildmodeExe` の場合に、`main.main` と `main.init` シンボルが明示的にマークされるようになりました。
    *   `deadcode` 関数は、到達可能なコードをマークし、到達不可能なコードを削除する役割を担います。共有ライブラリにリンクする場合、これらのエントリポイントが適切に保持されるようにするために、明示的なマークが必要となります。

8.  **`STT_TLS` シンボルタイプに関する変更**:
    *   `src/cmd/internal/ld/symtab.go` で、`Ctxt.Tlsg`（スレッドローカルストレージのGoルーチン構造体）のシンボルタイプが `STT_TLS` として適切に扱われるようになりました。これは、共有ライブラリ環境でのTLS（Thread Local Storage）の正しい動作を保証するために重要です。

## コアとなるコードの解説

このコミットの核心は、GoリンカがGo共有ライブラリを認識し、それらに動的にリンクできるようにするメカニズムの導入です。

最も重要な追加は `ldshlibsyms` 関数です。この関数は、Go共有ライブラリのパスを受け取り、`debug/elf` パッケージを使用してそのELFヘッダと動的シンボルテーブルを解析します。共有ライブラリ内で定義されているすべてのエクスポートされたシンボル（関数や変数）を抽出し、それらをリンカの内部シンボルテーブルに `SDYNIMPORT`（動的インポート）として登録します。これにより、リンカは、これらのシンボルが現在のバイナリ内ではなく、外部の共有ライブラリによって提供されることを理解します。

`addlib` および `addlibpath` 関数の変更は、リンカがライブラリを検索する際に、従来のアーカイブファイル（`.a`）だけでなく、Go共有ライブラリのメタデータを含む `.shlibname` ファイルも考慮するように拡張されたことを示しています。`.shlibname` ファイルには、実際にロードすべき共有ライブラリのファイル名が記述されており、リンカはこの情報を使用して正しい共有ライブラリを見つけ出します。

また、`hostlink` 関数で外部リンカに渡される `-znow` フラグは、動的リンクにおける重要な最適化であるPLTの遅延解決を無効にします。Goランタイムは起動時に特定の初期化処理を行うため、このタイミングでシンボル解決が遅延されると、予期せぬスタック使用量の増加やクラッシュを引き起こす可能性があります。`-znow` を使用することで、すべてのシンボル解決がプログラム起動時に強制的に行われ、このような問題を回避します。

`deadcode` 関数における `main.main` と `main.init` の明示的なマークは、共有ライブラリにリンクされた実行ファイルの場合に、これらの重要なエントリポイントがリンカによって誤って削除されないようにするためのものです。

これらの変更により、Goリンカは、GoプログラムがGo共有ライブラリに動的にリンクするために必要なすべての情報を処理し、最終的な実行可能ファイルを正しく生成できるようになります。

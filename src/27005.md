## 元コミット内容

`cmd/compile: inline list storage stealing`

このコミットは、Goコンパイラにおいてリストのストレージを「盗む」処理をインライン化します。この処理はごく一部の場所でのみ必要であり、インライン化することで `NodeLists` からの移行を簡素化できます。`toolstash -cmp` テストをパスしています。

## 変更の背景

この変更の主な背景は、Goコンパイラ内部における抽象構文木（AST）の表現方法の進化にあります。以前のGoコンパイラでは、ASTノードのリストを `NodeList` という構造体で管理していました。しかし、より効率的で柔軟なAST表現への移行が進められており、`NodeList` から `Nodes` (または類似の新しいリスト表現) への置き換えが行われていました。

このコミットの目的は、その移行プロセスを簡素化することです。具体的には、`NodeList` が `OBLOCK` (ブロック文) のような特定のASTノードで、初期化文 (`Ninit`) を持たない場合に、その内部のリスト (`List`) のストレージを「盗んで」再利用する最適化ロジックが存在していました。これは、不要なメモリ割り当てを避け、パフォーマンスを向上させるためのテクニックです。

しかし、この「ストレージを盗む」ロジックが `syntax.go` 内の汎用的なリスト操作関数 (`list1`, `setNodeSeqNode`, `appendNodeSeqNode`) に組み込まれていると、`NodeList` からの移行を進める上で複雑さが増します。なぜなら、これらの汎用関数は `NodeList` 以外の新しいリスト表現でも使用される可能性があり、その際に `NodeList` 特有の最適化ロジックが邪魔になるからです。

そこで、このコミットでは、この特定の最適化ロジックを汎用関数から削除し、実際にその最適化が必要な `parser.go` 内の特定の箇所（`labeled_stmt`, `if_stmt`, `stmt_list`）に直接インライン化することで、`syntax.go` の汎用関数をクリーンアップし、`NodeList` からの移行をスムーズにすることを目指しています。

## 前提知識の解説

### Goコンパイラの構造

Goコンパイラ (`cmd/compile`) は、Go言語のソースコードを機械語に変換するツールです。その過程は大きく分けて以下のフェーズに分かれます。

1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換します。
2.  **構文解析 (Syntax Analysis)**: トークンのストリームを解析し、プログラムの構造を抽象構文木（AST）として構築します。このコミットが関連するのはこのフェーズです。
3.  **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、名前解決、定数畳み込みなどの意味的な検証と変換を行います。
4.  **中間表現 (IR) 生成**: ASTをコンパイラ内部の中間表現に変換します。
5.  **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用し、生成されるコードの効率を高めます。
6.  **コード生成 (Code Generation)**: 最適化された中間表現をターゲットアーキテクチャの機械語に変換します。

### 抽象構文木 (AST)

ASTは、ソースコードの構造を木構造で表現したものです。各ノードはプログラムの構成要素（変数宣言、関数呼び出し、制御構造など）を表します。Goコンパイラでは、`Node` 構造体がASTの基本的な要素を表します。

### `NodeList` と `Nodes` (または新しいリスト表現)

Goコンパイラの初期のバージョンでは、ASTノードのリストを `NodeList` というリンクリストのような構造で管理していました。しかし、リンクリストはキャッシュ効率が悪く、特定の操作でオーバーヘッドが生じる可能性があります。そのため、より効率的な配列ベースの `Nodes` (または類似の新しいリスト表現) への移行が進められていました。この移行は、コンパイラのパフォーマンス向上を目的としています。

### `OBLOCK` ノード

`OBLOCK` は、GoコンパイラのASTにおける「ブロック文」を表すノードです。例えば、`{ ... }` のように波括弧で囲まれたコードブロックや、`if` 文や `for` 文の本体などが `OBLOCK` ノードとして表現されます。`OBLOCK` ノードは、そのブロック内で宣言された初期化文 (`Ninit`) と、ブロック内のステートメントのリスト (`List`) を持ちます。

### ストレージの「盗み (Stealing)」とインライン化

「ストレージの盗み」とは、特定の条件（この場合は `OBLOCK` ノードが初期化文を持たない場合）を満たす `NodeList` の内部ストレージを、新しいリスト構造にコピーするのではなく、直接再利用する最適化手法です。これにより、メモリの再割り当てとコピーのコストを削減できます。

「インライン化」とは、ある関数やロジックを、それを呼び出す箇所に直接展開することです。これにより、関数呼び出しのオーバーヘッドをなくし、コンパイラがより広範な最適化を適用できるようになる可能性があります。このコミットでは、汎用的なリスト操作関数から特定の最適化ロジックを削除し、そのロジックが必要な特定の呼び出し元に直接記述することで、インライン化を実現しています。

## 技術的詳細

このコミットの技術的な核心は、GoコンパイラのAST操作におけるメモリ管理とコードの簡素化にあります。

### `NodeList` の内部構造と「盗み」のメカニズム

以前の `NodeList` は、おそらく以下のような構造を持っていました（簡略化）。

```go
type NodeList struct {
    N    *Node     // リストの最初のノード
    End  *NodeList // リストの最後の要素へのポインタ (リンクリストの末尾)
    // 他のフィールド
}
```

`OBLOCK` ノードが `Ninit` (初期化文) を持たない場合、その `List` フィールドは単なるステートメントのリストであり、特別な初期化処理は不要です。この場合、`NodeList` の内部で管理されている `Node` のシーケンスを、新しい `NodeList` や `Nodes` にコピーするのではなく、既存の `NodeList` の `List` フィールドを直接「盗んで」再利用することで、メモリ割り当てとコピーのオーバーヘッドを回避していました。

具体的には、`syntax.go` の `list1`、`setNodeSeqNode`、`appendNodeSeqNode` といった関数内で、入力された `Node` が `OBLOCK` で `Ninit` が空の場合、その `Node` の `List` フィールドを直接取り出し、元の `Node` の `List` フィールドを `nil` に設定（ポイズンポインタ化）して、取り出したリストを返す、という処理が行われていました。これにより、元の `Node` はもはやリストの所有者ではなくなり、そのストレージが「盗まれた」ことになります。

### 変更による影響

このコミットでは、上記の「ストレージを盗む」ロジックを `syntax.go` の汎用関数から削除し、`parser.go` 内の特定の箇所に移動しました。これにより、以下のメリットが生まれます。

1.  **`syntax.go` のクリーンアップ**: `syntax.go` 内のリスト操作関数は、`NodeList` 特有の最適化ロジックから解放され、より汎用的でシンプルな実装になります。これは、将来的に `NodeList` が完全に廃止された際に、これらの関数を容易に新しいリスト表現に対応させたり、削除したりすることを可能にします。
2.  **コードの意図の明確化**: 「ストレージを盗む」という特殊な最適化が、それが本当に必要な `parser.go` の特定のコンテキストでのみ行われるようになります。これにより、コードの意図がより明確になり、理解しやすくなります。
3.  **移行の簡素化**: `NodeList` から `Nodes` への移行作業において、`syntax.go` の汎用関数が `NodeList` の詳細に依存しなくなるため、移行作業がよりスムーズに進められます。

### `nodeSeqLen` 関数

`nodeSeqLen` は、`NodeList` または `Nodes` のようなノードシーケンスの長さを取得するユーティリティ関数です。このコミットでは、`s.Ninit` が空であるかどうかを判断するために使用されています。

### `concat` と `list` 関数

`concat` は2つのノードリストを連結する関数、`list` は既存のノードリストに新しいノードを追加する関数です。これらの関数は、ASTノードのリストを構築する際に使用されます。このコミットでは、`OBLOCK` のリストを「盗む」場合に `concat` を使用し、そうでない場合に `list` を使用することで、適切なリスト操作を行っています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/parser.go` の変更点

`parser.go` の各関数では、`Node` が `OBLOCK` オペレーションを持ち、かつ `Ninit` (初期化文) が空である場合に、特別な処理が追加されています。

*   **`labeled_stmt` 関数**:
    *   ラベル付きステートメントの解析中に、`ls` (ラベルの定義ノード) が `OBLOCK` で `Ninit` が空の場合、`concat(l, ls.List)` を使用して既存のリスト `l` に `ls` の内部リストを直接連結します。これにより、`ls` のストレージが再利用されます。
    *   それ以外の場合は、通常の `list(l, ls)` を使用して `ls` をリストに追加します。

*   **`if_stmt` 関数**:
    *   `if` ステートメントの `else` ブロックの解析中に、`compound_stmt(true)` が返す `cs` (複合ステートメント) が `OBLOCK` で `Ninit` が `nil` の場合、`setNodeSeq(&stmt.Rlist, cs.List)` を使用して `stmt.Rlist` に `cs` の内部リストを直接設定します。
    *   それ以外の場合は、`setNodeSeq(&stmt.Rlist, []*Node{cs})` を使用して `cs` を単一のノードとしてリストに追加します。

*   **`stmt_list` 関数**:
    *   ステートメントのリストを解析中に、`s` (現在のステートメントノード) が `OBLOCK` で `Ninit` が空の場合、`concat(l, s.List)` を使用して既存のリスト `l` に `s` の内部リストを直接連結します。
    *   それ以外の場合は、通常の `list(l, s)` を使用して `s` をリストに追加します。

これらの変更により、「ストレージを盗む」ロジックが、それが実際に必要とされる構文解析の特定のコンテキストに直接組み込まれました。

### `src/cmd/compile/internal/gc/syntax.go` の変更点

`syntax.go` からは、`NodeList` のストレージを「盗む」ための特殊なロジックが完全に削除されました。

*   **`list1` 関数**:
    *   以前は、入力 `n` が `OBLOCK` で `Ninit` が空の場合に `n.List` を取り出し、`n.List` を `nil` に設定してそのリストを返すロジックがありました。このロジックが削除されました。
    *   これにより、`list1` は常に新しい `NodeList` を作成し、入力 `n` をその最初の要素として設定する、よりシンプルな動作になります。

*   **`setNodeSeqNode` 関数**:
    *   この関数も同様に、入力 `n` が `OBLOCK` で `Ninit` が空の場合に `n.List` を「盗む」ロジックを含んでいましたが、これが削除されました。
    *   これにより、`setNodeSeqNode` は、`NodeList` ポインタの場合には `list1(n)` を呼び出すか、`[]*Node` スライスの場合には `n` を含む新しいスライスを作成する、より直接的な動作になります。

*   **`appendNodeSeqNode` 関数**:
    *   この関数からも、`OBLOCK` ノードのリストストレージを「盗む」ロジックが削除されました。
    *   これにより、`appendNodeSeqNode` は、`NodeList` ポインタの場合には `list(*a, n)` を呼び出すか、`[]*Node` スライスの場合には `n` を既存のスライスに追加する、より標準的な動作になります。

これらの削除により、`syntax.go` のリスト操作関数は `NodeList` の特定の最適化の詳細から切り離され、より汎用的な役割に特化するようになりました。これは、`NodeList` からの移行を容易にし、コンパイラコードベース全体の保守性を向上させます。

このコミットの目的は、その移行プロセスを簡素化することです。具体的には、`NodeList` が `OBLOCK` (ブロック文) のような特定のASTノードで、初期化文 (`Ninit`) を持たない場合に、その内部のリスト (`List`) のストレージを「盗んで」再利用する最適化ロジックが存在していました。これは、不要なメモリ割り当てを避け、パフォーマンスを向上させるためのテクニックです。

しかし、この「ストレージを盗む」ロジックが `syntax.go` 内の汎用的なリスト操作関数 (`list1`, `setNodeSeqNode`, `appendNodeSeqNode`) に組み込まれていると、`NodeList` からの移行を進める上で複雑さが増します。なぜなら、これらの汎用関数は `NodeList` 以外の新しいリスト表現でも使用される可能性があり、その際に `NodeList` 特有の最適化ロジックが邪魔になるからです。

そこで、このコミットでは、この特定の最適化ロジックを汎用関数から削除し、実際にその最適化が必要な `parser.go` 内の特定の箇所（`labeled_stmt`, `if_stmt`, `stmt_list`）に直接インライン化することで、`syntax.go` の汎用関数をクリーンアップし、`NodeList` からの移行をスムーズにすることを目指しています。

## 前提知識の解説

### Goコンパイラの構造

Goコンパイラ (`cmd/compile`) は、Go言語のソースコードを機械語に変換するツールです。その過程は大きく分けて以下のフェーズに分かれます。

1.  **字句解析 (Lexical Analysis)**: ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換します。
2.  **構文解析 (Syntax Analysis)**: トークンのストリームを解析し、プログラムの構造を抽象構文木（AST）として構築します。このコミットが関連するのはこのフェーズです。
3.  **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、名前解決、定数畳み込みなどの意味的な検証と変換を行います。
4.  **中間表現 (IR) 生成**: ASTをコンパイラ内部の中間表現に変換します。
5.  **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用し、生成されるコードの効率を高めます。
6.  **コード生成 (Code Generation)**: 最適化された中間表現をターゲットアーキテクチャの機械語に変換します。

### 抽象構文木 (AST)

ASTは、ソースコードの構造を木構造で表現したものです。各ノードはプログラムの構成要素（変数宣言、関数呼び出し、制御構造など）を表します。Goコンパイラでは、`Node` 構造体がASTの基本的な要素を表します。

### `NodeList` と `Nodes` (または新しいリスト表現)

Goコンパイラの初期のバージョンでは、ASTノードのリストを `NodeList` というリンクリストのような構造で管理していました。しかし、リンクリストはキャッシュ効率が悪く、特定の操作でオーバーヘッドが生じる可能性があります。そのため、より効率的な配列ベースの `Nodes` (または類似の新しいリスト表現) への移行が進められていました。この移行は、コンパイラのパフォーマンス向上を目的としています。

### `OBLOCK` ノード

`OBLOCK` は、GoコンパイラのASTにおける「ブロック文」を表すノードです。例えば、`{ ... }` のように波括弧で囲まれたコードブロックや、`if` 文や `for` 文の本体などが `OBLOCK` ノードとして表現されます。`OBLOCK` ノードは、そのブロック内で宣言された初期化文 (`Ninit`) と、ブロック内のステートメントのリスト (`List`) を持ちます。

### ストレージの「盗み (Stealing)」とインライン化

「ストレージの盗み」とは、特定の条件（この場合は `OBLOCK` ノードが初期化文を持たない場合）を満たす `NodeList` の内部ストレージを、新しいリスト構造にコピーするのではなく、直接再利用する最適化手法です。これにより、メモリの再割り当てとコピーのコストを削減できます。

「インライン化」とは、ある関数やロジックを、それを呼び出す箇所に直接展開することです。これにより、関数呼び出しのオーバーヘッドをなくし、コンパイラがより広範な最適化を適用できるようになる可能性があります。このコミットでは、汎用的なリスト操作関数から特定の最適化ロジックを削除し、そのロジックが必要な特定の呼び出し元に直接記述することで、インライン化を実現しています。

## 技術的詳細

このコミットの技術的な核心は、GoコンパイラのAST操作におけるメモリ管理とコードの簡素化にあります。

### `NodeList` の内部構造と「盗み」のメカニズム

以前の `NodeList` は、おそらく以下のような構造を持っていました（簡略化）。

```go
type NodeList struct {
    N    *Node     // リストの最初のノード
    End  *NodeList // リストの最後の要素へのポインタ (リンクリストの末尾)
    // 他のフィールド
}
```

`OBLOCK` ノードが `Ninit` (初期化文) を持たない場合、その `List` フィールドは単なるステートメントのリストであり、特別な初期化処理は不要です。この場合、`NodeList` の内部で管理されている `Node` のシーケンスを、新しい `NodeList` や `Nodes` にコピーするのではなく、既存の `NodeList` の `List` フィールドを直接「盗んで」再利用することで、メモリ割り当てとコピーのオーバーヘッドを回避していました。

具体的には、`syntax.go` の `list1`、`setNodeSeqNode`、`appendNodeSeqNode` といった関数内で、入力された `Node` が `OBLOCK` で `Ninit` が空の場合、その `Node` の `List` フィールドを直接取り出し、元の `Node` の `List` フィールドを `nil` に設定（ポイズンポインタ化）して、取り出したリストを返す、という処理が行われていました。これにより、元の `Node` はもはやリストの所有者ではなくなり、そのストレージが「盗まれた」ことになります。

### 変更による影響

このコミットでは、上記の「ストレージを盗む」ロジックを `syntax.go` の汎用関数から削除し、`parser.go` 内の特定の箇所に移動しました。これにより、以下のメリットが生まれます。

1.  **`syntax.go` のクリーンアップ**: `syntax.go` 内のリスト操作関数は、`NodeList` 特有の最適化ロジックから解放され、より汎用的でシンプルな実装になります。これは、将来的に `NodeList` が完全に廃止された際に、これらの関数を容易に新しいリスト表現に対応させたり、削除したりすることを可能にします。
2.  **コードの意図の明確化**: 「ストレージを盗む」という特殊な最適化が、それが本当に必要な `parser.go` の特定のコンテキストでのみ行われるようになります。これにより、コードの意図がより明確になり、理解しやすくなります。
3.  **移行の簡素化**: `NodeList` から `Nodes` への移行作業において、`syntax.go` の汎用関数が `NodeList` の詳細に依存しなくなるため、移行作業がよりスムーズに進められます。

### `nodeSeqLen` 関数

`nodeSeqLen` は、`NodeList` または `Nodes` のようなノードシーケンスの長さを取得するユーティリティ関数です。このコミットでは、`s.Ninit` が空であるかどうかを判断するために使用されています。

### `concat` と `list` 関数

`concat` は2つのノードリストを連結する関数、`list` は既存のノードリストに新しいノードを追加する関数です。これらの関数は、ASTノードのリストを構築する際に使用されます。このコミットでは、`OBLOCK` のリストを「盗む」場合に `concat` を使用し、そうでない場合に `list` を使用することで、適切なリスト操作を行っています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/parser.go` の変更点

`parser.go` の各関数では、`Node` が `OBLOCK` オペレーションを持ち、かつ `Ninit` (初期化文) が空である場合に、特別な処理が追加されています。

*   **`labeled_stmt` 関数**:
    *   ラベル付きステートメントの解析中に、`ls` (ラベルの定義ノード) が `OBLOCK` で `Ninit` が空の場合、`concat(l, ls.List)` を使用して既存のリスト `l` に `ls` の内部リストを直接連結します。これにより、`ls` のストレージが再利用されます。
    *   それ以外の場合は、通常の `list(l, ls)` を使用して `ls` をリストに追加します。

*   **`if_stmt` 関数**:
    *   `if` ステートメントの `else` ブロックの解析中に、`compound_stmt(true)` が返す `cs` (複合ステートメント) が `OBLOCK` で `Ninit` が `nil` の場合、`setNodeSeq(&stmt.Rlist, cs.List)` を使用して `stmt.Rlist` に `cs` の内部リストを直接設定します。
    *   それ以外の場合は、`setNodeSeq(&stmt.Rlist, []*Node{cs})` を使用して `cs` を単一のノードとしてリストに追加します。

*   **`stmt_list` 関数**:
    *   ステートメントのリストを解析中に、`s` (現在のステートメントノード) が `OBLOCK` で `Ninit` が空の場合、`concat(l, s.List)` を使用して既存のリスト `l` に `s` の内部リストを直接連結します。
    *   それ以外の場合は、通常の `list(l, s)` を使用して `s` をリストに追加します。

これらの変更により、「ストレージを盗む」ロジックが、それが実際に必要とされる構文解析の特定のコンテキストに直接組み込まれました。

### `src/cmd/compile/internal/gc/syntax.go` の変更点

`syntax.go` からは、`NodeList` のストレージを「盗む」ための特殊なロジックが完全に削除されました。

*   **`list1` 関数**:
    *   以前は、入力 `n` が `OBLOCK` で `Ninit` が空の場合に `n.List` を取り出し、`n.List` を `nil` に設定してそのリストを返すロジックがありました。このロジックが削除されました。
    *   これにより、`list1` は常に新しい `NodeList` を作成し、入力 `n` をその最初の要素として設定する、よりシンプルな動作になります。

*   **`setNodeSeqNode` 関数**:
    *   この関数も同様に、入力 `n` が `OBLOCK` で `Ninit` が空の場合に `n.List` を「盗む」ロジックを含んでいましたが、これが削除されました。
    *   これにより、`setNodeSeqNode` は、`NodeList` ポインタの場合には `list1(n)` を呼び出すか、`[]*Node` スライスの場合には `n` を含む新しいスライスを作成する、より直接的な動作になります。

*   **`appendNodeSeqNode` 関数**:
    *   この関数からも、`OBLOCK` ノードのリストストレージを「盗む」ロジックが削除されました。
    *   これにより、`appendNodeSeqNode` は、`NodeList` ポインタの場合には `list(*a, n)` を呼び出すか、`[]*Node` スライスの場合には `n` を既存のスライスに追加する、より標準的な動作になります。

これらの削除により、`syntax.go` のリスト操作関数は `NodeList` の特定の最適化の詳細から切り離され、より汎用的な役割に特化するようになりました。これは、`NodeList` からの移行を容易にし、コンパイラコードベース全体の保守性を向上させます。

# [インデックス 24426] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおいて、静的データ生成の仕組みを改善するものです。既存のバックエンドがコード生成中に静的データを直接出力し、AST (Abstract Syntax Tree) を変更するという挙動が、SSAの二段階ブートストラップ方式と相性が悪かった問題を解決するために導入されました。具体的には、静的データを副作用なしに問い合わせる機能を追加し、関数に必要な静的データを保存し、SSAコード生成時にそれらを出力するように変更しています。

## コミット

```
[dev.ssa] cmd/compile: implement static data generation

The existing backend recognizes special
assignment statements as being implementable
with static data rather than code.
Unfortunately, it assumes that it is in the middle
of codegen; it emits data and modifies the AST.

This does not play well with SSA's two-phase
bootstrapping approach, in which we attempt to
compile code but fall back to the existing backend
if something goes wrong.

To work around this:

* Add the ability to inquire about static data
without side-effects.
* Save the static data required for a function.
* Emit that static data during SSA codegen.

Reviewed-on: https://go-review.googlesource.com/12790
Reviewed-by: Keith Randall <khr@golang.org>
```

## 変更の背景

Goコンパイラは、パフォーマンス向上と最適化の機会を増やすために、従来のバックエンドからSSA (Static Single Assignment) ベースのバックエンドへの移行を進めていました。この移行期間中、コンパイラは「二段階ブートストラップ」というアプローチを採用していました。これは、まず新しいSSAバックエンドでコードのコンパイルを試み、何らかの問題が発生した場合には、安全のために既存の（古い）バックエンドにフォールバックするというものです。

しかし、既存のバックエンドにおける静的データ（コンパイル時に値が確定する定数や初期化された変数など）の生成方法が、このSSAの二段階ブートストラップと相性が悪いという問題がありました。既存のバックエンドは、特定の代入文を静的データとして実装できると認識すると、コード生成の途中で直接データをメモリに出力し、さらにAST (Abstract Syntax Tree) を変更していました。

この「コード生成の途中での副作用（データ出力とAST変更）」が問題でした。SSAバックエンドがコンパイルに失敗して古いバックエンドにフォールバックする場合、既にASTが変更されていたり、データが不適切に出力されていたりすると、コンパイルプロセス全体が不安定になる可能性がありました。SSAバックエンドは、コード生成の前に静的データを「問い合わせる」だけで、実際の出力は後で行う必要があったのです。

このコミットは、SSAバックエンドが静的データを安全に処理できるように、既存の静的データ生成ロジックを修正し、SSAの二段階ブートストラップモデルに適合させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。複数のステージを経てコンパイルを行います。
*   **SSA (Static Single Assignment) 形式**: コンパイラの最適化で広く用いられる中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。Goコンパイラは、より高度な最適化を実現するために、従来のASTベースのIRからSSA形式への移行を進めていました。
*   **静的データ (Static Data)**: プログラムの実行が開始される前に、コンパイル時にその内容が確定し、メモリ上に配置されるデータのことです。例えば、グローバル変数、定数、文字列リテラル、初期化された配列や構造体などがこれに該当します。これらは実行時にコードで初期化するのではなく、プログラムのバイナリイメージの一部として格納されます。
*   **コード生成 (Codegen)**: コンパイラの最終段階の一つで、中間表現（ASTやSSA）をターゲットとなるCPUアーキテクチャの機械語命令に変換するプロセスです。
*   **AST (Abstract Syntax Tree - 抽象構文木)**: ソースコードの構文構造を木構造で表現したものです。コンパイラの初期段階で生成され、その後の意味解析や最適化、コード生成の基盤となります。
*   **二段階ブートストラップ (Two-phase bootstrapping)**: GoコンパイラがSSAバックエンドへの移行期に採用していた戦略です。新しいSSAバックエンドがまだ完全に安定していない段階で、その機能を導入しつつも、問題が発生した場合には既存の安定したバックエンドに切り戻せるようにする仕組みです。これにより、新しいバックエンドの開発と導入を段階的に進めることができました。この方式では、SSAバックエンドがコードをコンパイルする前に、そのコードがSSAで処理可能かどうかを「試行」するようなフェーズが存在します。

## 技術的詳細

このコミットの技術的な核心は、既存の静的データ生成関数 `gen_as_init` の振る舞いを変更し、SSAバックエンドの要件に合わせる点にあります。

1.  **副作用のない静的データ問い合わせ機能の追加**:
    *   `gen_as_init` 関数に `reportOnly` という新しいブール型引数が追加されました。
    *   `reportOnly` が `true` の場合、`gen_as_init` は実際に静的データをメモリに出力したり、ASTを変更したりする副作用を起こさずに、単にその代入文が静的データとして処理可能かどうかを報告するだけになります。
    *   これにより、SSAバックエンドはコード生成の前に、どの代入が静的データとして扱えるかを安全に「試行」できるようになります。

2.  **関数に必要な静的データの保存**:
    *   `src/cmd/compile/internal/ssa/func.go` に定義されている `ssa.Func` 構造体に `StaticData interface{}` フィールドが追加されました。
    *   SSAバックエンドの `stmt` メソッド（`src/cmd/compile/internal/gc/ssa.go` 内）で、`gen_as_init(n, true)` を呼び出し、静的データとして処理可能な代入文 `n` を検出します。
    *   検出された `n` は、`ssa.Func` の `StaticData` フィールドに一時的に保存されます。この時点ではまだデータは出力されません。

3.  **SSAコード生成時の静的データ出力**:
    *   SSAバックエンドの `genssa` 関数（`src/cmd/compile/internal/gc/ssa.go` 内）のコード生成の最終段階で、`ssa.Func` に保存されていた `StaticData` をループ処理します。
    *   保存されていた各 `Node` に対して、再度 `gen_as_init(n, false)` を呼び出します。このとき `reportOnly` は `false` なので、実際に静的データがメモリに出力されます。
    *   これにより、静的データの生成がSSAコード生成の適切なタイミングで行われるようになり、二段階ブートストラップの整合性が保たれます。

この変更により、SSAバックエンドは、静的データとして扱える代入を事前に識別し、その情報を保持しておき、実際のコード生成フェーズでまとめて処理できるようになります。これにより、SSAバックエンドがコンパイルに失敗してフォールバックした場合でも、ASTやメモリの状態が不整合になることを防ぎ、コンパイラの堅牢性が向上します。

## コアとなるコードの変更箇所

このコミットでは、主に以下の4つのファイルが変更されています。

1.  **`src/cmd/compile/internal/gc/gen.go`**:
    *   `gen` 関数内の `OAS` (代入) ケースで呼び出される `gen_as_init` の呼び出しに、新しい引数 `false` が追加されました。これは、従来のバックエンドのコードパスでは、引き続き副作用を伴う静的データ生成を行うことを意味します。

2.  **`src/cmd/compile/internal/gc/sinit.go`**:
    *   `gen_as_init` 関数のシグネチャが `func gen_as_init(n *Node) bool` から `func gen_as_init(n *Node, reportOnly bool) bool` に変更されました。
    *   関数内部で、`reportOnly` フラグに基づいて、`gused(nil)`、`gdata`、`gdatacomplex`、`gdatastring` といった実際のデータ出力やAST変更を行う処理が条件付きで実行されるようになりました。`reportOnly` が `true` の場合はこれらの副作用が抑制されます。

3.  **`src/cmd/compile/internal/gc/ssa.go`**:
    *   `state` 構造体の `stmt` メソッド内の `OAS` (代入) および `OASWB` (ライトバリア付き代入) の処理に、静的データ生成のロジックが追加されました。
    *   `gen_as_init(n, true)` を呼び出して、副作用なしに静的データとして処理可能かを確認します。
    *   もし可能であれば、その `Node` を `s.f.StaticData` (SSA関数オブジェクトに紐付けられた静的データリスト) に追加し、現在の `stmt` の処理をスキップします。
    *   `genssa` 関数（SSAコード生成のメイン関数）の最後に、`f.StaticData` に保存されたすべての `Node` をループし、`gen_as_init(n, false)` を呼び出して実際の静的データを出力するロジックが追加されました。

4.  **`src/cmd/compile/internal/ssa/func.go`**:
    *   `Func` 構造体に `StaticData interface{}` フィールドが追加されました。これは、SSAバックエンドが処理する関数に関連する静的データを一時的に保存するためのものです。`interface{}` 型であるため、任意の型のデータを格納できますが、このコンテキストでは `[]*Node` のスライスが格納されます。

## コアとなるコードの解説

このコミットの核となる変更は、`gen_as_init` 関数の役割の分離と、`ssa.Func` 構造体への `StaticData` フィールドの追加、そして `ssa.go` におけるその利用方法です。

*   **`gen_as_init` の役割分離**:
    *   以前の `gen_as_init` は、静的データとして処理できる代入を見つけると、即座にそのデータをバイナリに出力し、必要に応じてASTを操作していました。これは「問い合わせ」と「実行」が一体化した関数でした。
    *   新しい `reportOnly` 引数により、この関数は「この代入は静的データとして扱えるか？」という問い合わせ（`reportOnly=true`）と、「この静的データを出力せよ」（`reportOnly=false`）という実行の2つのモードを持つようになりました。
    *   これにより、SSAバックエンドは、コード生成の初期段階で副作用なく静的データを識別し、後でまとめて出力するという、より柔軟な制御が可能になります。

*   **`ssa.Func.StaticData` の導入**:
    *   `ssa.Func` は、SSA形式で表現された単一のGo関数を表す構造体です。この構造体に `StaticData interface{}` フィールドが追加されたことで、各SSA関数は、自身に関連する静的データとして処理すべきASTノードのリストを保持できるようになりました。
    *   このリストは、SSAバックエンドがコードを生成する前に、どの静的データを処理する必要があるかを把握するための「TODOリスト」のような役割を果たします。

*   **`ssa.go` におけるフローの変更**:
    *   `ssa.go` の `stmt` メソッドは、GoのステートメントをSSA形式に変換する役割を担います。ここで代入文 (`OAS`, `OASWB`) が現れた際、まず `gen_as_init(n, true)` を呼び出して、その代入が静的データとして処理可能かを確認します。
    *   もし可能であれば、その代入ノード `n` は `s.f.StaticData` に追加され、`stmt` メソッドはそれ以上の処理を行わずにリターンします。これにより、SSAバックエンドは、静的データとして扱われるべき代入をSSAグラフに変換するのを避けます。
    *   その後、`genssa` メソッドの終盤で、`s.f.StaticData` に蓄積されたすべてのノードに対して `gen_as_init(n, false)` が呼び出されます。ここで初めて、実際の静的データがバイナリに出力されます。
    *   この二段階の処理により、SSAバックエンドは、静的データ生成のタイミングを完全に制御し、二段階ブートストラップの要件を満たすことができます。

この一連の変更は、GoコンパイラのSSAバックエンドが、より複雑な最適化やコード生成のシナリオを安全かつ効率的に処理するための重要なステップでした。

## 元コミット内容

`cmd/yacc: Prevent index out of range. Fixes #9099.`

このコミットは、`cmd/yacc`ツールが生成するコードにおいて発生しうるインデックス範囲外エラーを修正します。これはGoのIssue #9099で報告された問題に対応するものです。

## 変更の背景

`cmd/yacc`は、Go言語でパーサーを生成するためのツールであり、Unix系の`yacc`（Yet Another Compiler Compiler）に似た機能を提供します。このツールが生成するパーサーは、入力されたトークン列を解析し、文法規則に従って構文木を構築します。

報告された問題（Issue #9099）は、パーサーが文法規則を「還元（reduce）」する際に発生する可能性のある「インデックス範囲外（index out of range）」エラーでした。特に、文法規則の中に「イプシロン生成規則（epsilon production）」、すなわち空文字列を生成する規則が含まれる場合に、パーサーの内部スタック（`$$S`）へのアクセスが不正なインデックスで行われることが原因でした。

このエラーは、パーサーが還元操作を行う際に、スタック上の要素を参照するインデックスが、スタックの現在のサイズを超えてしまうことで発生します。結果として、パーサーがクラッシュしたり、予期せぬ動作を引き起こしたりする可能性がありました。このコミットは、このような状況を検出し、スタックを適切に拡張することで、エラーの発生を防ぐことを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

1.  **Yacc (Yet Another Compiler Compiler)**:
    Yaccは、文法定義から構文解析器（パーサー）のソースコードを自動生成するツールです。プログラミング言語のコンパイラやインタプリタのフロントエンド部分で広く利用されます。YaccはLALR(1)パーサーを生成し、これはシフト・還元（shift-reduce）という操作を繰り返しながら入力を解析します。

2.  **パーサー（構文解析器）**:
    プログラミング言語のソースコードやその他の形式言語の入力ストリームを読み込み、その構文が言語の文法規則に準拠しているかを検証し、通常は抽象構文木（AST）などの構造を生成するプログラムです。

3.  **シフト・還元解析（Shift-Reduce Parsing）**:
    Yaccが生成するパーサーの基本的な動作原理です。
    *   **シフト（Shift）**: 入力ストリームから次のトークンを読み込み、パーサースタックにプッシュします。
    *   **還元（Reduce）**: スタックのトップにある一連の記号が、ある文法規則の右辺と一致した場合、それらの記号をスタックからポップし、その規則の左辺の非終端記号をプッシュします。これにより、より高レベルの構文構造が形成されます。

4.  **パーサースタック**:
    シフト・還元解析において、パーサーは内部的にスタックを使用します。このスタックには、シフトされた終端記号（トークン）や、還元によって生成された非終端記号、そしてパーサーの状態が格納されます。還元操作では、このスタック上の記号を参照したり、操作したりします。

5.  **イプシロン生成規則（ε-production または Null Production）**:
    文法規則の一種で、非終端記号が空文字列（ε）に還元されることを許可する規則です。例えば、`OptionalPart -> Expression | ε` のような規則は、`OptionalPart`が`Expression`になるか、あるいは何も生成しない（空になる）ことを意味します。イプシロン生成規則は、文法の柔軟性を高めますが、パーサーのスタック操作を複雑にすることがあります。特に、空文字列を還元する際に、スタック上の要素のインデックス計算がずれる原因となることがあります。

6.  **インデックス範囲外エラー（Index Out of Range Error）**:
    配列やスライスなどのデータ構造にアクセスする際に、指定されたインデックスがそのデータ構造の有効な範囲外である場合に発生するエラーです。Go言語では、スライスへの不正なインデックスアクセスはパニック（panic）を引き起こし、プログラムを異常終了させます。

## 技術的詳細

このコミットの技術的な核心は、`cmd/yacc`が生成するGoコード（`yacc.go`）内の還元処理におけるスタック操作の安全性向上にあります。

`yacc`が生成するパーサーは、還元操作を行う際に、スタック上の`$$p`というインデックスを基準として、還元される規則の右辺の長さに基づいて`$$p`を調整します。その後、`$$p+1`などの相対インデックスを用いてスタック`$$S`から値を取り出し、`$$VAL`に代入します。

問題は、イプシロン生成規則が還元される場合、つまり規則の右辺が空である場合です。このとき、還元される要素がないため、`$$p`の調整が適切に行われないか、あるいは`$$p`が指す位置がスタックの末尾に近い場合、`$$p+1`のようなアクセスがスタック`$$S`の現在の長さを超えてしまう可能性がありました。コミットメッセージのコメント`Iff the reduced production is ε, $1 is possibly out of range.`がこの状況を明確に示しています。`$1`は還元される規則の最初の記号に対応するスタック上の値を示しますが、イプシロン生成規則の場合、実質的に`$1`が存在しないにもかかわらず、コードがその位置にアクセスしようとすることで問題が発生します。

この修正は、`$$VAL = $$S[$$p+1]`というアクセスが行われる直前に、`$$p+1`が`$$S`の現在の長さを超えていないかをチェックします。もし超えている場合、それはスタックが不足していることを意味するため、`$$S`スライスを現在の2倍のサイズに拡張し、既存の要素を新しいスライスにコピーします。これにより、`$$p+1`でのアクセスが常に有効な範囲内で行われることが保証され、インデックス範囲外エラーが回避されます。

このアプローチは、必要に応じてスタックを動的に拡張することで、パーサーの堅牢性を高めます。特に、イプシロン生成規則のような特殊なケースでのスタック管理の複雑さを吸収し、パーサーが予期せぬ入力や文法構造に対しても安定して動作するようにします。

## コアとなるコードの解説

追加されたコードブロックは以下の通りです。

```go
	// $$p is now the index of $0. Perform the default action. Iff the
	// reduced production is ε, $1 is possibly out of range.
	if $$p+1 >= len($$S) {
		nyys := make([]$$SymType, len($$S)*2)
		copy(nyys, $$S)
		$$S = nyys
	}
```

1.  **`// $$p is now the index of $0. Perform the default action. Iff the // reduced production is ε, $1 is possibly out of range.`**:
    このコメントは、修正の意図を明確に説明しています。`$$p`は還元操作後のスタックのベースインデックス（`$0`に対応する位置）を示します。問題は、還元される生成規則がイプシロン（ε、空文字列）である場合に、`$1`（還元される規則の最初の記号に対応するスタック上の値）へのアクセスがスタックの範囲外になる可能性があることです。これは、イプシロン生成規則がスタックから何も消費しないため、`$$p`がスタックの末尾に近い位置に留まり、`$$p+1`が有効なインデックスでなくなる場合に発生します。

2.  **`if $$p+1 >= len($$S)`**:
    この条件文は、`$$p+1`というインデックスが、現在のスタック`$$S`の長さを超えているかどうかをチェックします。もし`$$p+1`が`len($$S)`以上であれば、それは`$$S[$$p+1]`へのアクセスがインデックス範囲外エラーを引き起こすことを意味します。

3.  **`nyys := make([]$$SymType, len($$S)*2)`**:
    インデックス範囲外エラーの可能性がある場合、新しいスライス`nyys`を作成します。この新しいスライスの容量は、現在のスタック`$$S`の容量の2倍に設定されます。これにより、将来の操作のための十分なスペースが確保されます。`$$SymType`は、パーサースタックに格納される要素の型です。

4.  **`copy(nyys, $$S)`**:
    既存のスタック`$$S`のすべての要素を、新しく作成したより大きなスライス`nyys`にコピーします。これにより、既存のスタックの内容が保持されます。

5.  **`$$S = nyys`**:
    元のスタック変数`$$S`が、新しく拡張されたスライス`nyys`を指すように更新されます。この操作により、パーサーは拡張されたスタックで処理を続行できるようになり、`$$p+1`でのアクセスが安全に行えるようになります。

この修正は、Goの`slice`の動的な性質をうまく利用して、必要に応じてスタックの容量を増やすことで、パーサーの堅牢性を高めています。

このコミットは、Go言語のコマンドラインツール `go get` の動作に関するドキュメントを更新するものです。具体的には、`go get` が新しいパッケージをどこにダウンロードするか、そして `vendor` ディレクトリ内のコードを扱わないことを明確にしています。これは、`go get` の挙動に関するユーザーの混乱を解消し、ツールの透明性を高めることを目的としています。

## 変更の背景

このコミットは、Goのパッケージ管理とビルドシステムにおける `go get` コマンドの挙動に関するユーザーの理解を深めるために行われました。特に、以下の2点について明確化が求められていました。

1.  **`go get` がパッケージをダウンロードする場所の明確化**: ユーザーは `go get` を実行した際に、ダウンロードされたソースコードがファイルシステム上のどこに配置されるのかを正確に知る必要がありました。特に `GOPATH` が複数のエントリを持つ場合に、どのパスが使用されるのかという疑問がありました。
2.  **`vendor` ディレクトリとの相互作用の明確化**: Go 1.5で導入され、Go 1.6でデフォルトで有効になった `vendor` ディレクトリは、プロジェクト固有の依存関係を管理するための重要な機能です。しかし、`go get` が `vendor` ディレクトリ内のコードをどのように扱うのか（あるいは扱わないのか）について、公式ドキュメントでの明確な記述が不足していました。これにより、ユーザーは `go get` が `vendor` ディレクトリ内の依存関係を誤って更新したり、無視したりするのではないかという懸念を抱く可能性がありました。

これらの不明確な点を解消し、ユーザーが `go get` をより効果的に、かつ予測可能に利用できるようにするために、ドキュメントの更新が必要とされました。これは、Issue #12260 で報告された問題に対応するものです。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語の概念について知っておく必要があります。

*   **`go get` コマンド**:
    `go get` は、Go言語のパッケージとその依存関係をリモートリポジトリ（GitHubなど）からダウンロードし、ローカルの `GOPATH` にインストールするためのコマンドです。通常、ダウンロードされたパッケージは `GOPATH/src/<import-path>` に配置されます。また、`go get` はパッケージのビルドとインストールも行います。

*   **`GOPATH` 環境変数**:
    `GOPATH` は、Goのワークスペースのルートディレクトリを指定する環境変数です。Goのツールチェーンは、この `GOPATH` 内でソースコード、コンパイル済みパッケージ、実行可能バイナリを探します。`GOPATH` は複数のディレクトリパスをコロン（Unix/Linux/macOS）またはセミコロン（Windows）で区切って指定できます。例えば、`export GOPATH=/home/user/go:/usr/local/go_projects` のように設定できます。`go get` が新しいパッケージをダウンロードする際、`GOPATH` に複数のエントリがある場合は、最初のパスが使用されます。

*   **`vendor` ディレクトリ**:
    `vendor` ディレクトリは、Go 1.5で実験的に導入され、Go 1.6でデフォルトで有効になった依存関係管理のメカニズムです。プロジェクトのルートディレクトリ直下やサブディレクトリに `vendor` という名前のディレクトリを作成し、その中にプロジェクトが依存する外部パッケージのソースコードを配置します。これにより、プロジェクトはグローバルな `GOPATH` にインストールされたパッケージに依存するのではなく、自身の `vendor` ディレクトリ内のパッケージを使用するようになります。これは、依存関係のバージョン管理をプロジェクトごとに独立させ、再現可能なビルドを保証するために非常に重要です。`vendor` ディレクトリ内のパッケージは、Goのビルドプロセスにおいて、`GOPATH` よりも優先して解決されます。

## 技術的詳細

このコミットは、`go get` コマンドのヘルプドキュメントを更新することで、その動作をより明確にしています。変更は主に `src/cmd/go/alldocs.go` と `src/cmd/go/get.go` の2つのファイルに対して行われています。これらのファイルは、`go get` コマンドの内部的なヘルプメッセージや、`go help get` で表示されるドキュメントの生成元となります。

追加されたドキュメントのポイントは以下の2つです。

1.  **`GOPATH` への書き込み場所の明示**:
    `When checking out a new package, get creates the target directory GOPATH/src/<import-path>. If the GOPATH contains multiple entries, get uses the first one. See 'go help gopath'.`
    この記述により、`go get` が新しいパッケージをダウンロードする際に、`GOPATH` 環境変数で指定されたパスの `src/<import-path>` にディレクトリを作成し、そこにコードを配置することが明確にされました。特に、`GOPATH` が複数のパスを持つ場合、`go get` はリストの最初のパスを使用するという重要な情報が追加されています。これにより、ユーザーはどの `GOPATH` エントリが `go get` のターゲットとなるかを正確に理解できます。

2.  **`vendor` ディレクトリの無視の明示**:
    `Get never checks out or updates code stored in vendor directories.`
    この記述は、`go get` が `vendor` ディレクトリ内のコードに対して一切操作を行わないことを明確にしています。これは、`vendor` ディレクトリがプロジェクト固有の依存関係を管理するためのものであり、`go get` のようなグローバルなパッケージ取得ツールがこれを変更すべきではないという設計思想を反映しています。この明確化により、ユーザーは `go get` が `vendor` ディレクトリ内の依存関係を誤って上書きしたり、バージョンを更新したりする心配がないことを確信できます。これは、再現可能なビルドを維持する上で非常に重要な保証となります。

これらの変更は、`go get` のコード自体に機能的な変更を加えるものではなく、あくまでその挙動に関するドキュメントを改善するものです。しかし、これによりユーザーは `go get` の動作をより正確に理解し、予期せぬ挙動に遭遇する可能性を減らすことができます。

## コアとなるコードの解説

追加されたコードは、Goのソースコードではなく、`go get` コマンドのヘルプメッセージの一部となるプレーンテキストのドキュメント文字列です。

1.  `When checking out a new package, get creates the target directory GOPATH/src/<import-path>. If the GOPATH contains multiple entries, get uses the first one. See 'go help gopath'.`
    この文は、`go get` が新しいパッケージをダウンロードする際の具体的な保存場所を説明しています。`GOPATH` の最初のパスが使用されるという点は、複数の `GOPATH` エントリを持つユーザーにとって特に重要です。

2.  `Get never checks out or updates code stored in vendor directories.`
    この文は、`go get` が `vendor` ディレクトリ内のコードを意図的に無視するというポリシーを明確にしています。これは、`vendor` ディレクトリがプロジェクトのローカルな依存関係管理のために存在し、`go get` のようなグローバルなツールがこれを変更すべきではないというGoの設計原則を強調しています。

これらのドキュメントの追加は、`go get` コマンドの動作に関するユーザーの誤解を防ぎ、より予測可能な開発体験を提供することを目的としています。機能的な変更はありませんが、ユーザーエクスペリエンスとツールの理解度向上に大きく貢献します。

## 元コミット内容

このコミットは、以前にリバートされたCL #9345の再導入版であり、小さなバグ修正が加えられています。元のCL #9345の主な内容は以下の通りです。

*   **バッファ付きチャネルの再試行メカニズムの削除**: 以前はバッファ付きチャネルで再試行メカニズムが使用されていましたが、これを削除しました。
*   **完全なプロトコル完了**: 送信側が受信側を、またはその逆が相手をウェイクアップする際に、相手との完全なプロトコルを完了するように変更されました。これにより、ウェイクアップされた側がチャネルを再ロックする必要がなくなりました。
*   **データコピーの最適化**:
    *   待機中の受信側がいるチャネルへの送信の場合、データコピーの回数が2回（送信者 -> キュー、キュー -> 受信者）から1回（送信者 -> 受信者）に削減されました。
    *   待機中の送信側がいるチャネルからの受信の場合、データコピーは引き続き2回必要です。
*   **アルゴリズムの統一**: バッファ付きチャネルとバッファなしチャネルのアルゴリズムが大幅に統一され、全体的な実装が簡素化されました。

このコミットでは、上記のCL #9345の変更に加えて、`sendDirect`関数とその呼び出し箇所に特化したバグ修正が行われています。

## 変更の背景

この変更の背景には、Goランタイムにおけるチャネル操作の効率性と堅牢性の向上が挙げられます。特に、以下の2つの問題が主要な動機となっています。

1.  **チャネル操作の複雑性**: 以前のGoランタイムでは、バッファ付きチャネルとバッファなしチャネルの処理ロジックが異なり、特にバッファ付きチャネルには再試行メカニズムが存在していました。これにより、コードの複雑性が増し、デバッグやメンテナンスが困難になる可能性がありました。CL #9345は、これらのアルゴリズムを統一し、簡素化することを目指しました。
2.  **ゴルーチンスタックの動的な性質によるバグ**: Goのゴルーチンは、スタックを動的に伸縮させることでメモリ効率を高めています。しかし、この動的な性質が特定の条件下でバグを引き起こす可能性がありました。具体的には、チャネル送信操作中に、受信を待っているスリープ中のゴルーチンのスタックが縮小されると、送信側が保持していた受信側のスタック上のポインタが無効になり、データコピーが不正なメモリ領域に対して行われるという問題が発生しました（Issue #13169）。この問題は、CL #9345の導入によって顕在化したと考えられます。

このコミットは、CL #9345によるチャネル操作の簡素化というメリットを維持しつつ、スタック縮小によるポインタ無効化のバグを修正することで、Goランタイムの安定性と効率性を両立させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とメカニズムに関する知識が必要です。

1.  **Goチャネル (Channels)**:
    *   Goにおけるゴルーチン間の安全な通信手段。
    *   **バッファなしチャネル (Unbuffered Channels)**: 送信と受信が同時に行われるまでブロックします。データは直接送信者から受信者にコピーされます。
    *   **バッファ付きチャネル (Buffered Channels)**: 指定された数の要素を格納できるキューを持ちます。バッファが満杯でない限り送信はブロックせず、バッファが空でない限り受信はブロックしません。
    *   **内部構造 (`hchan`)**: チャネルはランタイム内部で`hchan`構造体として表現されます。これには、バッファのポインタ、要素サイズ、キューの現在の要素数 (`qcount`)、キューサイズ (`dataqsiz`)、送受信待ちのゴルーチンキュー (`sendq`, `recvq`) などが含まれます。
2.  **ゴルーチン (Goroutines)**:
    *   Goランタイムによって管理される軽量なスレッド。
    *   **スタック管理**: Goのゴルーチンは、非常に小さな初期スタック（通常2KB）で開始し、必要に応じて動的にスタックを拡張（成長）および縮小します。
        *   **スタック成長**: 関数呼び出しが現在のスタック容量を超える場合、ランタイムはより大きな新しいスタックを割り当て、古いスタックの内容を新しいスタックにコピーし、ポインタを更新します。
        *   **スタック縮小**: ガベージコレクション (GC) サイクル中に、スタックが大幅に未使用であると判断された場合、ランタイムはより小さなスタックに内容をコピーし、未使用のメモリを解放することがあります。
    *   **プリエンプション (Preemption)**: Goランタイムは、長時間実行されるゴルーチンが他のゴルーチンをブロックしないように、プリエンプション（横取り）メカニズムを持っています。これにより、ランタイムは実行中のゴルーチンを一時停止し、別のゴルーチンにCPUを割り当てることができます。プリエンプションポイントは、特定の関数呼び出しやループのバックエッジなどで発生する可能性があります。
3.  **`sudog` 構造体**:
    *   Goランタイム内部で使用される構造体で、チャネル操作でブロックされたゴルーチンを表します。
    *   `sudog`は、ブロックされたゴルーチン (`g`フィールド)、チャネル要素のポインタ (`elem`フィールド)、ウェイクアップ時に渡されるパラメータ (`param`フィールド) などの情報を含みます。
    *   チャネルの`sendq`や`recvq`は、この`sudog`のキューです。
4.  **`gopark` と `goready`**:
    *   `gopark`: 現在のゴルーチンをスリープさせ、スケジューラに制御を戻すランタイム関数。チャネル操作でブロックされる際に使用されます。
    *   `goready`: スリープ中のゴルーチンをウェイクアップし、実行可能キューに入れるランタイム関数。チャネル操作が完了した際に、相手のゴルーチンをウェイクアップするために使用されます。
5.  **`typedmemmove` と `memmove`**:
    *   Goランタイム内部のメモリコピー関数。`typedmemmove`は型情報に基づいてポインタのバリア（GC関連の処理）を考慮しますが、`memmove`は単純なバイトコピーです。
6.  **`raceenabled`, `racesync`, `raceacquire`, `racerelease`**:
    *   Goのデータ競合検出器 (Race Detector) に関連するランタイム関数。`raceenabled`がtrueの場合に有効になり、チャネル操作におけるメモリアクセスの同期を追跡します。

## 技術的詳細

このコミットの技術的詳細の核心は、チャネル操作におけるデータ転送のロジックの変更と、それに伴うゴルーチンスタックの動的な性質に起因するバグの修正です。

**CL #9345によるチャネル操作の簡素化と統一**:
以前のGoランタイムでは、バッファ付きチャネルの送信と受信は、バッファなしチャネルとは異なるロジックを持っていました。特に、バッファ付きチャネルでは、送信者がデータをバッファに書き込み、受信者がバッファから読み取るという2段階のコピーが行われ、さらに、相手のゴルーチンをウェイクアップした後に、ウェイクアップされたゴルーチンがチャネルロックを再取得して残りの処理を行うという「再試行メカニズム」が存在しました。

CL #9345は、このメカニズムを廃止し、送信者と受信者が直接連携してデータ転送を完了するモデルに移行しました。

*   **送信操作 (`chansend`)**:
    *   待機中の受信者 (`c.recvq`に`sudog`がある) がいる場合、送信者は直接その受信者のスタックまたはヒープ上の領域にデータをコピーします。これにより、バッファを介した中間コピーが不要になり、`sender -> queue -> receiver` の2回のコピーが `sender -> receiver` の1回に削減されます。
    *   バッファに空きがある場合、データはバッファに直接書き込まれます。
    *   待機中の受信者もバッファの空きもない場合、送信者は`c.sendq`に自身の`sudog`をエンキューしてスリープします。
*   **受信操作 (`chanrecv`)**:
    *   待機中の送信者 (`c.sendq`に`sudog`がある) がいる場合、受信者は直接その送信者からデータを受け取ります。バッファ付きチャネルの場合、これはバッファの先頭からデータを読み取り、送信者のデータをバッファの末尾に書き込むという操作になります（バッファが満杯の場合、同じスロットを指す）。
    *   バッファにデータがある場合、データはバッファから直接読み取られます。
    *   待機中の送信者もバッファのデータもない場合、受信者は`c.recvq`に自身の`sudog`をエンキューしてスリープします。

この変更により、バッファ付きチャネルとバッファなしチャネルのデータ転送ロジックが`send`および`recv`という共通のヘルパー関数に集約され、コードの重複が減り、全体的なチャネル実装が簡素化されました。

**Issue #13169のバグ修正**:
CL #9345の導入後、Issue #13169で報告されたバグは、`sendDirect`関数が関与するチャネル送信操作中に発生しました。

1.  **問題の発生箇所**: 送信側がスリープ中の受信側ゴルーチンにデータを送信しようとする際。
2.  **問題のシーケンス**:
    *   送信側は、受信側の`sudog`構造体からデータの書き込み先ポインタ（`sg.elem`）を読み取ります。
    *   次に、送信する値をそのポインタにコピーします。
    *   しかし、以前の変更では、この「ポインタの読み取り」と「値のコピー」の間にゴルーチンのサスペンションポイント（`sendDirect`の呼び出し）が存在していました。
3.  **スタック縮小の影響**: Goランタイムは、ゴルーチンのスタックを動的に縮小する可能性があります。もし、サスペンションポイントの間に受信側ゴルーチンのスタックが縮小された場合、ステップ1で読み取ったポインタは、ステップ2で実際にデータがコピーされる時点では無効なメモリ領域を指すことになります。これにより、データが誤った場所に書き込まれたり、メモリ破壊が発生したりする可能性がありました。
4.  **修正**: このコミットでは、`sendDirect`関数内で、`sg.elem`から宛先ポインタを読み取った後、そのポインタにデータをコピーするまでの間に、**いかなるプリエンプションポイントも発生させない**ように修正されました。これにより、ポインタが読み取られてから使用されるまでの間にスタックが縮小される可能性がなくなり、ポインタの有効性が保証されます。コミットメッセージには「I suspect the old code worked correctly basically by accident.（古いコードは基本的に偶然に正しく動作していたのだろう）」とあり、この問題が以前から潜在していた可能性を示唆しています。

この修正は、Goランタイムの低レベルなスタック管理とゴルーチン間のデータ転送の複雑な相互作用を考慮したものであり、Goの並行処理モデルの堅牢性を高める上で非常に重要です。

## コアとなるコードの解説

このコミットのコアとなるコード変更は、`src/runtime/chan.go`内の`sendDirect`関数と、`chansend`および`chanrecv`関数が`send`および`recv`という新しいヘルパー関数を使用するように変更された点です。

### `sendDirect` 関数の修正 (src/runtime/chan.go)

```go
func sendDirect(t *_type, sg *sudog, src unsafe.Pointer) {
	// Send on an unbuffered or empty-buffered channel is the only operation
	// in the entire runtime where one goroutine
	// writes to the stack of another goroutine. The GC assumes that
	// stack writes only happen when the goroutine is running and are
	// atomic. We must ensure that the write is atomic.
	// typedmemmove will call heapBitsBulkBarrier, but the target bytes
	// are not in the heap, so that will not help. We arrange to call
	// memmove and typeBitsBulkBarrier instead.

	// Once we read sg.elem out of sg, it will no longer
	// be updated if the destination's stack gets copied (shrunk).
	// So make sure that no preemption points can happen between read & use.
	dst := sg.elem
	memmove(dst, src, t.size)
	typeBitsBulkBarrier(t, uintptr(dst), t.size)
}
```

*   **`dst := sg.elem`**: ここで、受信側ゴルーチンの`sudog`構造体から、データが書き込まれるべき宛先メモリ領域のポインタ`sg.elem`を読み取ります。
*   **コメントの重要性**: 「`Once we read sg.elem out of sg, it will no longer be updated if the destination's stack gets copied (shrunk). So make sure that no preemption points can happen between read & use.`」というコメントが非常に重要です。これは、`sg.elem`を読み取った後、受信側ゴルーチンのスタックが縮小されても`sg.elem`自体は更新されないため、読み取った`dst`ポインタが古くなる可能性があることを示唆しています。このため、`dst`を読み取ってから実際に`memmove`でデータを使用するまでの間に、ゴルーチンのプリエンプション（一時停止）が発生しないようにすることが必須となります。
*   **`memmove(dst, src, t.size)`**: 送信元`src`から宛先`dst`へ、`t.size`バイトのデータをコピーします。これは型情報を考慮しない生のメモリコピーです。
*   **`typeBitsBulkBarrier(t, uintptr(dst), t.size)`**: GCのライトバリア（write barrier）処理を行います。`dst`がヒープ上のオブジェクトを指している場合、GCがオブジェクトの移動を追跡できるように、このバリアが必要です。ただし、このケースでは`dst`は別のゴルーチンのスタック上にある可能性が高いため、GCのヒープスキャンとは異なる考慮が必要です。

この修正の肝は、`dst := sg.elem`と`memmove`の間に、Goランタイムがゴルーチンを一時停止させる可能性のあるコード（例えば、別の関数呼び出し）を挟まないようにした点です。これにより、`dst`が読み取られた時点での有効性が、データコピーが完了するまで保証されます。

### `chansend` と `chanrecv` の変更 (src/runtime/chan.go)

`chansend`と`chanrecv`関数は、チャネルのタイプ（バッファなし/バッファ付き）や状態（空き/データあり/待機中のゴルーチンあり）に応じて複雑なロジックを持っていました。このコミットでは、これらの関数が`send`と`recv`という新しいヘルパー関数を呼び出すようにリファクタリングされました。

例えば、`chansend`の冒頭部分の変更は以下のようになります。

**変更前 (`chansend`の一部):**
```go
	if c.dataqsiz == 0 { // synchronous channel
		sg := c.recvq.dequeue()
		if sg != nil { // found a waiting receiver
			// ...
			syncsend(c, sg, ep) // ここでsyncsendが呼ばれる
			// ...
		}
		// ...
	}
	// asynchronous channel
	// ...
```

**変更後 (`chansend`の一部):**
```go
	if sg := c.recvq.dequeue(); sg != nil {
		// Found a waiting receiver. We pass the value we want to send
		// directly to the receiver, bypassing the channel buffer (if any).
		send(c, sg, ep, func() { unlock(&c.lock) }) // 新しいsendヘルパー関数が呼ばれる
		return true
	}
	if c.qcount < c.dataqsiz {
		// Space is available in the channel buffer.  Enqueue the element to send.
		// ...
	}
	// ...
```

この変更により、チャネルのロック管理やゴルーチンのウェイクアップ処理など、共通のロジックが`send`および`recv`関数にカプセル化され、`chansend`と`chanrecv`自体のコードが大幅に簡素化されました。これにより、コードの可読性と保守性が向上し、バッファ付き/バッファなしチャネル間のアルゴリズムの統一が実現されました。

## 変更の背景

この変更の背景には、Goランタイムにおけるチャネル操作の効率性と堅牢性の向上が挙げられます。特に、以下の2つの問題が主要な動機となっています。

1.  **チャネル操作の複雑性**: 以前のGoランタイムでは、バッファ付きチャネルとバッファなしチャネルの処理ロジックが異なり、特にバッファ付きチャネルには再試行メカニズムが存在していました。これにより、コードの複雑性が増し、デバッグやメンテナンスが困難になる可能性がありました。CL #9345は、これらのアルゴリズムを統一し、簡素化することを目指しました。
2.  **ゴルーチンスタックの動的な性質によるバグ**: Goのゴルーチンは、スタックを動的に伸縮させることでメモリ効率を高めています。しかし、この動的な性質が特定の条件下でバグを引き起こす可能性がありました。具体的には、チャネル送信操作中に、受信を待っているスリープ中のゴルーチンのスタックが縮小されると、送信側が保持していた受信側のスタック上のポインタが無効になり、データコピーが不正なメモリ領域に対して行われるという問題が発生しました（Issue #13169）。この問題は、CL #9345の導入によって顕在化したと考えられます。

このコミットは、CL #9345によるチャネル操作の簡素化というメリットを維持しつつ、スタック縮小によるポインタ無効化のバグを修正することで、Goランタイムの安定性と効率性を両立させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とメカニズムに関する知識が必要です。

1.  **Goチャネル (Channels)**:
    *   Goにおけるゴルーチン間の安全な通信手段。
    *   **バッファなしチャネル (Unbuffered Channels)**: 送信と受信が同時に行われるまでブロックします。データは直接送信者から受信者にコピーされます。
    *   **バッファ付きチャネル (Buffered Channels)**: 指定された数の要素を格納できるキューを持ちます。バッファが満杯でない限り送信はブロックせず、バッファが空でない限り受信はブロックしません。
    *   **内部構造 (`hchan`)**: チャネルはランタイム内部で`hchan`構造体として表現されます。これには、バッファのポインタ、要素サイズ、キューの現在の要素数 (`qcount`)、キューサイズ (`dataqsiz`)、送受信待ちのゴルーチンキュー (`sendq`, `recvq`) などが含まれます。
2.  **ゴルーチン (Goroutines)**:
    *   Goランタイムによって管理される軽量なスレッド。
    *   **スタック管理**: Goのゴルーチンは、非常に小さな初期スタック（通常2KB）で開始し、必要に応じて動的にスタックを拡張（成長）および縮小します。
        *   **スタック成長**: 関数呼び出しが現在のスタック容量を超える場合、ランタイムはより大きな新しいスタックを割り当て、古いスタックの内容を新しいスタックにコピーし、ポインタを更新します。
        *   **スタック縮小**: ガベージコレクション (GC) サイクル中に、スタックが大幅に未使用であると判断された場合、ランタイムはより小さなスタックに内容をコピーし、未使用のメモリを解放することがあります。
    *   **プリエンプション (Preemption)**: Goランタイムは、長時間実行されるゴルーチンが他のゴルーチンをブロックしないように、プリエンプション（横取り）メカニズムを持っています。これにより、ランタイムは実行中のゴルーチンを一時停止し、別のゴルーチンにCPUを割り当てることができます。プリエンプションポイントは、特定の関数呼び出しやループのバックエッジなどで発生する可能性があります。
3.  **`sudog` 構造体**:
    *   Goランタイム内部で使用される構造体で、チャネル操作でブロックされたゴルーチンを表します。
    *   `sudog`は、ブロックされたゴルーチン (`g`フィールド)、チャネル要素のポインタ (`elem`フィールド)、ウェイクアップ時に渡されるパラメータ (`param`フィールド) などの情報を含みます。
    *   チャネルの`sendq`や`recvq`は、この`sudog`のキューです。
4.  **`gopark` と `goready`**:
    *   `gopark`: 現在のゴルーチンをスリープさせ、スケジューラに制御を戻すランタイム関数。チャネル操作でブロックされる際に使用されます。
    *   `goready`: スリープ中のゴルーチンをウェイクアップし、実行可能キューに入れるランタイム関数。チャネル操作が完了した際に、相手のゴルーチンをウェイクアップするために使用されます。
5.  **`typedmemmove` と `memmove`**:
    *   Goランタイム内部のメモリコピー関数。`typedmemmove`は型情報に基づいてポインタのバリア（GC関連の処理）を考慮しますが、`memmove`は単純なバイトコピーです。
6.  **`raceenabled`, `racesync`, `raceacquire`, `racerelease`**:
    *   Goのデータ競合検出器 (Race Detector) に関連するランタイム関数。`raceenabled`がtrueの場合に有効になり、チャネル操作におけるメモリアクセスの同期を追跡します。

## 技術的詳細

このコミットの技術的詳細の核心は、チャネル操作におけるデータ転送のロジックの変更と、それに伴うゴルーチンスタックの動的な性質に起因するバグの修正です。

**CL #9345によるチャネル操作の簡素化と統一**:
以前のGoランタイムでは、バッファ付きチャネルの送信と受信は、バッファなしチャネルとは異なるロジックを持っていました。特に、バッファ付きチャネルでは、送信者がデータをバッファに書き込み、受信者がバッファから読み取るという2段階のコピーが行われ、さらに、相手のゴルーチンをウェイクアップした後に、ウェイクアップされたゴルーチンがチャネルロックを再取得して残りの処理を行うという「再試行メカニズム」が存在しました。

CL #9345は、このメカニズムを廃止し、送信者と受信者が直接連携してデータ転送を完了するモデルに移行しました。

*   **送信操作 (`chansend`)**:
    *   待機中の受信者 (`c.recvq`に`sudog`がある) がいる場合、送信者は直接その受信者のスタックまたはヒープ上の領域にデータをコピーします。これにより、バッファを介した中間コピーが不要になり、`sender -> queue -> receiver` の2回のコピーが `sender -> receiver` の1回に削減されます。
    *   バッファに空きがある場合、データはバッファに直接書き込まれます。
    *   待機中の受信者もバッファの空きもない場合、送信者は`c.sendq`に自身の`sudog`をエンキューしてスリープします。
*   **受信操作 (`chanrecv`)**:
    *   待機中の送信者 (`c.sendq`に`sudog`がある) がいる場合、受信者は直接その送信者からデータを受け取ります。バッファ付きチャネルの場合、これはバッファの先頭からデータを読み取り、送信者のデータをバッファの末尾に書き込むという操作になります（バッファが満杯の場合、同じスロットを指す）。
    *   バッファにデータがある場合、データはバッファから直接読み取られます。
    *   待機中の送信者もバッファのデータもない場合、受信者は`c.recvq`に自身の`sudog`をエンキューしてスリープします。

この変更により、バッファ付きチャネルとバッファなしチャネルのデータ転送ロジックが`send`および`recv`という共通のヘルパー関数に集約され、コードの重複が減り、全体的なチャネル実装が簡素化されました。

**Issue #13169のバグ修正**:
CL #9345の導入後、Issue #13169で報告されたバグは、`sendDirect`関数が関与するチャネル送信操作中に発生しました。

1.  **問題の発生箇所**: 送信側がスリープ中の受信側ゴルーチンにデータを送信しようとする際。
2.  **問題のシーケンス**:
    *   送信側は、受信側の`sudog`構造体からデータの書き込み先ポインタ（`sg.elem`）を読み取ります。
    *   次に、送信する値をそのポインタにコピーします。
    *   しかし、以前の変更では、この「ポインタの読み取り」と「値のコピー」の間にゴルーチンのサスペンションポイント（`sendDirect`の呼び出し）が存在していました。
3.  **スタック縮小の影響**: Goランタイムは、ゴルーチンのスタックを動的に縮小する可能性があります。もし、サスペンションポイントの間に受信側ゴルーチンのスタックが縮小された場合、ステップ1で読み取ったポインタは、ステップ2で実際にデータがコピーされる時点では無効なメモリ領域を指すことになります。これにより、データが誤った場所に書き込まれたり、メモリ破壊が発生したりする可能性がありました。
4.  **修正**: このコミットでは、`sendDirect`関数内で、`sg.elem`から宛先ポインタを読み取った後、そのポインタにデータをコピーするまでの間に、**いかなるプリエンプションポイントも発生させない**ように修正されました。これにより、ポインタが読み取られてから使用されるまでの間にスタックが縮小される可能性がなくなり、ポインタの有効性が保証されます。コミットメッセージには「I suspect the old code worked correctly basically by accident.（古いコードは基本的に偶然に正しく動作していたのだろう）」とあり、この問題が以前から潜在していた可能性を示唆しています。

この修正は、Goランタイムの低レベルなスタック管理とゴルーチン間のデータ転送の複雑な相互作用を考慮したものであり、Goの並行処理モデルの堅牢性を高める上で非常に重要です。

## コアとなるコードの解説

このコミットのコアとなるコード変更は、`src/runtime/chan.go`内の`sendDirect`関数と、`chansend`および`chanrecv`関数が`send`および`recv`という新しいヘルパー関数を使用するように変更された点です。

### `sendDirect` 関数の修正 (src/runtime/chan.go)

```go
func sendDirect(t *_type, sg *sudog, src unsafe.Pointer) {
	// Send on an unbuffered or empty-buffered channel is the only operation
	// in the entire runtime where one goroutine
	// writes to the stack of another goroutine. The GC assumes that
	// stack writes only happen when the goroutine is running and are
	// atomic. We must ensure that the write is atomic.
	// typedmemmove will call heapBitsBulkBarrier, but the target bytes
	// are not in the heap, so that will not help. We arrange to call
	// memmove and typeBitsBulkBarrier instead.

	// Once we read sg.elem out of sg, it will no longer
	// be updated if the destination's stack gets copied (shrunk).
	// So make sure that no preemption points can happen between read & use.
	dst := sg.elem
	memmove(dst, src, t.size)
	typeBitsBulkBarrier(t, uintptr(dst), t.size)
}
```

*   **`dst := sg.elem`**: ここで、受信側ゴルーチンの`sudog`構造体から、データが書き込まれるべき宛先メモリ領域のポインタ`sg.elem`を読み取ります。
*   **コメントの重要性**: 「`Once we read sg.elem out of sg, it will no longer be updated if the destination's stack gets copied (shrunk). So make sure that no preemption points can happen between read & use.`」というコメントが非常に重要です。これは、`sg.elem`を読み取った後、受信側ゴルーチンのスタックが縮小されても`sg.elem`自体は更新されないため、読み取った`dst`ポインタが古くなる可能性があることを示唆しています。このため、`dst`を読み取ってから実際に`memmove`でデータを使用するまでの間に、ゴルーチンのプリエンプション（一時停止）が発生しないようにすることが必須となります。
*   **`memmove(dst, src, t.size)`**: 送信元`src`から宛先`dst`へ、`t.size`バイトのデータをコピーします。これは型情報を考慮しない生のメモリコピーです。
*   **`typeBitsBulkBarrier(t, uintptr(dst), t.size)`**: GCのライトバリア（write barrier）処理を行います。`dst`がヒープ上のオブジェクトを指している場合、GCがオブジェクトの移動を追跡できるように、このバリアが必要です。ただし、このケースでは`dst`は別のゴルーチンのスタック上にある可能性が高いため、GCのヒープスキャンとは異なる考慮が必要です。

この修正の肝は、`dst := sg.elem`と`memmove`の間に、Goランタイムがゴルーチンを一時停止させる可能性のあるコード（例えば、別の関数呼び出し）を挟まないようにした点です。これにより、`dst`が読み取られた時点での有効性が、データコピーが完了するまで保証されます。

### `chansend` と `chanrecv` の変更 (src/runtime/chan.go)

`chansend`と`chanrecv`関数は、チャネルのタイプ（バッファなし/バッファ付き）や状態（空き/データあり/待機中のゴルーチンあり）に応じて複雑なロジックを持っていました。このコミットでは、これらの関数が`send`と`recv`という新しいヘルパー関数を呼び出すようにリファクタリングされました。

例えば、`chansend`の冒頭部分の変更は以下のようになります。

**変更前 (`chansend`の一部):**
```go
	if c.dataqsiz == 0 { // synchronous channel
		sg := c.recvq.dequeue()
		if sg != nil { // found a waiting receiver
			// ...
			syncsend(c, sg, ep) // ここでsyncsendが呼ばれる
			// ...
		}
		// ...
	}
	// asynchronous channel
	// ...
```

**変更後 (`chansend`の一部):**
```go
	if sg := c.recvq.dequeue(); sg != nil {
		// Found a waiting receiver. We pass the value we want to send
		// directly to the receiver, bypassing the channel buffer (if any).
		send(c, sg, ep, func() { unlock(&c.lock) }) // 新しいsendヘルパー関数が呼ばれる
		return true
	}
	if c.qcount < c.dataqsiz {
		// Space is available in the channel buffer.  Enqueue the element to send.
		// ...
	}
	// ...
```

この変更により、チャネルのロック管理やゴルーチンのウェイクアップ処理など、共通のロジックが`send`および`recv`関数にカプセル化され、`chansend`と`chanrecv`自体のコードが大幅に簡素化されました。これにより、コードの可読性と保守性が向上し、バッファ付き/バッファなしチャネル間のアルゴリズムの統一が実現されました。

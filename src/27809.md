# [インデックス 27809] ファイルの概要

このコミットは、Go言語の`syscall`パッケージにおける`epoll_event`構造体の定義が、`ppc64le`および`ppc64`アーキテクチャ向けに誤っていた問題を修正するものです。この修正により、`epoll_*`システムコールからの戻り値が正しく処理され、`fsnotify`やDockerのビルドにおける不具合が解消されます。具体的には、構造体に不足していたパディングフィールドが追加されました。

## 変更の背景

このコミットの背景には、Go言語の`syscall`パッケージが提供する`epoll_event`構造体の定義が、特定のアーキテクチャ（`ppc64le`および`ppc64`）においてLinuxカーネルの期待するレイアウトと異なっていたという問題があります。この不一致により、`epoll_wait`などの`epoll_*`システムコールがイベントを返した際に、Goプログラムが誤った情報を読み取ってしまう事態が発生していました。

具体的には、以下の問題が報告されていました。

*   **fsnotifyの不具合**: ファイルシステムイベントを監視する`fsnotify`パッケージが正しく機能しない。
*   **Dockerビルドの失敗**: アップストリームのDockerをビルドする際に問題が発生する。

これらの問題は、Goの`syscall`パッケージが`epoll_event`構造体のメモリレイアウトを、`ppc64le`/`ppc64`アーキテクチャにおけるLinuxカーネルのABI（Application Binary Interface）に合致させていなかったことに起因します。興味深いことに、`gccgo`（GCCベースのGoコンパイラ）ではこの構造体が正しく定義されていたため、Goの標準コンパイラ（gc）における特定の実装上の差異が問題を引き起こしていたことが示唆されます。

このコミットは、これらの不具合を解消し、`ppoll_*`システムコールが`ppc64le`/`ppc64`環境で期待通りに動作するようにするために行われました。

## 前提知識の解説

### epollとは

`epoll`はLinuxカーネルが提供するI/Oイベント通知メカニズムの一つで、多数のファイルディスクリプタ（ソケットやファイルなど）からのI/Oイベントを効率的に監視するために使用されます。特に、C10K問題（同時に1万以上のクライアント接続を処理する問題）のような高並行処理環境でその真価を発揮します。`select`や`poll`といった従来のメカニズムと比較して、監視対象のファイルディスクリプタ数が増えてもパフォーマンスが劣化しにくいという特徴があります。

`epoll`を使用する主なシステムコールは以下の通りです。
*   `epoll_create` / `epoll_create1`: `epoll`インスタンスを作成します。
*   `epoll_ctl`: `epoll`インスタンスにファイルディスクリプタを追加、変更、削除します。
*   `epoll_wait`: 監視対象のファイルディスクリプタで発生したイベントを待ち、取得します。

### epoll_event構造体

`epoll_event`構造体は、`epoll_ctl`でイベントを登録する際や、`epoll_wait`でイベントを受け取る際に使用されます。この構造体は、発生したイベントの種類（読み込み可能、書き込み可能など）と、そのイベントに関連付けられたユーザーデータを格納します。

一般的な`epoll_event`構造体はC言語で以下のように定義されます（Linuxカーネルのヘッダファイルより）：

```c
struct epoll_event {
    uint32_t events; /* Epoll events */
    epoll_data_t data; /* User data variable */
};

union epoll_data {
    void *ptr;
    int fd;
    uint32_t u32;
    uint64_t u64;
};
typedef union epoll_data epoll_data_t;
```

ここで重要なのは、`epoll_data_t`が共用体（union）である点です。共用体は、そのメンバーの中で最も大きいサイズのメモリを共有します。64ビットアーキテクチャでは、`void *ptr`や`uint64_t u64`が8バイトとなるため、`epoll_data_t`のサイズは8バイトとなり、8バイト境界にアラインされる必要があります。

### ppc64le / ppc64アーキテクチャとアラインメント

`ppc64le` (PowerPC 64-bit Little Endian) および `ppc64` (PowerPC 64-bit Big Endian) は、IBMが開発したPower ISAに基づく64ビットプロセッサアーキテクチャです。これらのアーキテクチャでは、メモリ上のデータ構造のアラインメント（配置）に関する特定の規則があります。

特に、64ビットシステムでは、8バイトのデータ型（例: `uint64_t`、ポインタ）は8バイト境界に配置されることが一般的です。構造体内のフィールドがこのアラインメント要件を満たさない場合、コンパイラやシステムコールは自動的にパディング（詰め物）を挿入して、次のフィールドが正しい境界に配置されるようにします。

`epoll_event`構造体の場合、`uint32_t events`（4バイト）の後に`epoll_data_t data`（8バイト）が続くため、`events`と`data`の間に4バイトのパディングが必要となります。これにより、`data`フィールドが8バイト境界に正しく配置されます。

### Goのsyscallパッケージ

Go言語の`syscall`パッケージは、オペレーティングシステムが提供するシステムコールをGoプログラムから呼び出すためのインターフェースを提供します。このパッケージは、OS固有のデータ構造（例: `epoll_event`）や定数をGoの型として定義し、Goプログラムが低レベルのOS機能とやり取りできるようにします。

`syscall`パッケージ内の構造体定義は、対応するC言語の構造体とメモリレイアウトが完全に一致している必要があります。もし一致しない場合、システムコールを呼び出した際にカーネルとGoプログラムの間でデータの解釈に齟齬が生じ、予期せぬ動作やエラーが発生します。

## 技術的詳細

このコミットの技術的な核心は、`ppc64le`および`ppc64`アーキテクチャにおける`epoll_event`構造体のメモリレイアウトの不一致にあります。

LinuxカーネルのABIでは、`epoll_event`構造体は以下のメモリレイアウトを持つことが期待されます。

1.  `events` (4バイト, `uint32_t`)
2.  **パディング** (4バイト) - `data`フィールドを8バイト境界にアラインするため
3.  `data` (8バイト, `epoll_data_t`共用体)

これにより、`epoll_event`構造体の合計サイズは16バイトになります。

しかし、Goの`syscall`パッケージ内の`EpollEvent`構造体は、`ppc64le`/`ppc64`向けにこの4バイトのパディングを考慮していませんでした。元の定義は以下のようでした。

```go
type EpollEvent struct {
	Events uint32
	Fd     int32 // これはepoll_data_tのfdメンバーに対応するが、直接定義されていた
	Pad    int32 // これは構造体全体のパディングではなく、Fdの後のパディングを意図していた可能性
}
```

この定義では、`Events` (4バイト) の直後に`Fd` (4バイト) が続き、その後に`Pad` (4バイト) が続くため、`epoll_data_t`に相当する部分が正しく8バイト境界に配置されず、カーネルが返す8バイトの`data`フィールドをGo側が誤って解釈していました。

このコミットでは、`src/syscall/types_linux.go`でC言語の構造体定義に`_padFd`を追加し、さらに`src/syscall/ztypes_linux_ppc64.go`と`src/syscall/ztypes_linux_ppc64le.go`でGoの`EpollEvent`構造体に`X_padFd`というフィールドを追加することで、このパディング問題を解決しています。これにより、Goの`EpollEvent`構造体のメモリレイアウトがLinuxカーネルのABIと完全に一致するようになり、システムコールからの戻り値が正しく解釈されるようになりました。

## コアとなるコードの解説

このコミットのコアとなる変更は、`EpollEvent`構造体への`X_padFd int32`フィールドの追加です。

元の`EpollEvent`構造体は、`Events uint32` (4バイト)、`Fd int32` (4バイト)、`Pad int32` (4バイト) のように定義されていました。しかし、`ppc64le`/`ppc64`アーキテクチャでは、`Events` (4バイト) の後に続く`epoll_data_t`共用体（Goの構造体では`Fd`と`Pad`で表現される部分）が8バイト境界にアラインされる必要があります。

このアラインメント要件を満たすために、`Events`フィールドの直後に4バイトのパディングが必要でした。`X_padFd int32`フィールドは、この不足していた4バイトのパディングを明示的に構造体に追加する役割を果たします。

変更後の`EpollEvent`構造体のメモリレイアウトは以下のようになります。

*   `Events uint32` (4バイト)
*   `X_padFd int32` (4バイト) - **これが追加されたパディング**
*   `Fd int32` (4バイト)
*   `Pad int32` (4バイト)

これにより、`Events`と`X_padFd`を合わせた8バイトの後に、`Fd`と`Pad`で構成される8バイトのデータが続く形となり、`epoll_data_t`に相当する部分が8バイト境界に正しく配置されるようになります。結果として、Goの`syscall`パッケージがLinuxカーネルと`epoll_event`構造体の情報を正しく交換できるようになり、`fsnotify`やDockerビルドの問題が解決されました。

`types_linux.go`への変更は、Goの`zerrors.go`や`ztypes.go`ファイルを生成するツールが、C言語のヘッダファイルからGoの型定義を生成する際に、このパディングの存在を認識させるためのものです。`__powerpc64__`プリプロセッサディレクティブは、PowerPC 64ビットアーキテクチャ向けにコンパイルされる場合にのみこのパディングが考慮されることを示しています。

# [インデックス 22704] ファイルの概要

このコミットは、Go言語のコンパイラ（`cmd/internal/gc`）において、`math.Sqrt`関数の呼び出しを、特定のアーキテクチャ（AMD64およびARM）で利用可能なハードウェアの平方根命令に置き換える最適化を導入するものです。これにより、`math.Sqrt`の計算がより効率的に行われるようになります。

## 元コミット内容

`cmd/internal/gc: math.Sqrt にハードウェア命令を使用 (amd64/arm)`

この変更は2011年9月に最初に試作されましたが、明らかなベンチマークループでは効果が見られなかったため破棄されました。
今回も明らかなベンチマークループでは効果が見られませんが、より複雑な、`Sqrt`呼び出しの周りで追加の計算を行うようなケースでは、呼び出しを行わない（ハードウェア命令に置き換える）ことで顕著な効果が見られました。

ベンチマーク結果:
- `BenchmarkSqrt`: 4.56 ns/op -> 4.57 ns/op (+0.22%)
- `BenchmarkSqrtIndirect`: 4.56 ns/op -> 4.56 ns/op (+0.00%)
- `BenchmarkSqrtGo`: 69.4 ns/op -> 69.4 ns/op (+0.00%)
- `BenchmarkSqrtPrime`: 4417 ns/op -> 3647 ns/op (-17.43%)

この変更は、ランタイム内の1行アセンブリルーチン（例: `getg`）への一部の呼び出しをハードウェア命令に展開するための準備段階です。

## 変更の背景

このコミットの主な背景は、`math.Sqrt`関数のパフォーマンス最適化です。Go言語の標準ライブラリである`math.Sqrt`は、浮動小数点数の平方根を計算する関数です。多くのCPUアーキテクチャには、この平方根計算を高速に行うための専用のハードウェア命令（例: x86の`SQRTSS`/`SQRTSD`、ARMの`FSQRTD`）が用意されています。

コミットメッセージによると、この最適化のアイデア自体は2011年9月には存在していましたが、当時のベンチマークでは目立った性能向上が見られなかったため、一度は採用が見送られました。これは、単純な`math.Sqrt`のループベンチマークでは、関数呼び出しのオーバーヘッドやその他の要因が支配的であり、ハードウェア命令への置き換えによる純粋な計算時間の短縮効果が隠れてしまっていたためと考えられます。

しかし、今回の再検討では、`BenchmarkSqrtPrime`という、`Sqrt`の呼び出しの周りに他の計算が混じる、より現実的なシナリオのベンチマークにおいて、17%以上の顕著な性能向上が確認されました。これは、`Sqrt`の計算がボトルネックとなるような、より複雑なアルゴリズムにおいて、ハードウェア命令の利用が大きなメリットをもたらすことを示しています。

この変更は、単なる`math.Sqrt`の最適化に留まらず、Goコンパイラが特定の標準ライブラリ関数呼び出しを、対応するハードウェア命令に直接展開する（インライン化する）ための「ウォーミングアップ」と位置づけられています。将来的には、ランタイム内の他のアセンブリルーチン（例えば、現在のゴルーチンを取得する`getg`のような、頻繁に呼び出されるが非常に短い処理）についても同様の最適化を適用する可能性が示唆されています。これにより、Goプログラム全体の実行効率が向上することが期待されます。

## 前提知識の解説

### Goコンパイラ (gc) とその役割

Go言語の公式コンパイラは、かつては各アーキテクチャ（例: `5g` for ARM, `6g` for AMD64）ごとに独立したバイナリとして存在していましたが、現在は`cmd/compile`という単一のバイナリに統合されています。しかし、このコミットが作成された2015年時点では、まだ`5g`や`6g`といった名称が使われていました。

コンパイラ（`gc`）は、Goのソースコードを機械語に変換するだけでなく、様々な最適化を行います。これには、関数のインライン化、デッドコードの削除、レジスタ割り当ての最適化などが含まれます。このコミットでは、`math.Sqrt`という特定の関数呼び出しを、コンパイル時にその関数の実装を呼び出すのではなく、直接CPUのハードウェア命令に置き換えるという最適化が行われています。

### アセンブリスタブとハードウェア命令

Goの標準ライブラリには、Go言語で書かれたコードだけでなく、パフォーマンスが重要な部分や、OSとのインターフェース部分などでアセンブリ言語で書かれたコード（アセンブリスタブ）が含まれることがあります。`math.Sqrt`も、多くのシステムではアセンブリで実装されたり、Goで書かれた汎用実装からアセンブリスタブを介して呼び出されたりします。

ハードウェア命令とは、CPUが直接実行できる低レベルな命令のことです。多くの現代のCPUには、浮動小数点演算（加算、減算、乗算、除算、平方根など）を高速に実行するための専用の命令セットが搭載されています。これらの命令は、ソフトウェアで同じ計算を行うよりもはるかに高速です。

### `math.Sqrt`関数

`math.Sqrt`は、`float64`型の引数を取り、その平方根を`float64`型で返すGoの標準関数です。通常、この関数は内部的にCPUの浮動小数点演算ユニット（FPU）を利用して計算を行います。

### Goにおけるベンチマーク (`go test -bench`)

Go言語には、標準でベンチマークテストを記述・実行する機能が組み込まれています。`go test -bench .`コマンドを実行すると、プロジェクト内のベンチマーク関数（`BenchmarkXxx`という命名規則に従う関数）が実行され、各操作にかかる時間（ns/op）、割り当てられたメモリ量（B/op）、割り当て回数（allocs/op）などが報告されます。このコミットのベンチマーク結果は、この機能を使って測定されたものです。

### `cmd/5g`, `cmd/6g`, `cmd/internal/gc`

*   `cmd/5g`: ARMアーキテクチャ向けのGoコンパイラ（歴史的な名称）。
*   `cmd/6g`: AMD64アーキテクチャ向けのGoコンパイラ（歴史的な名称）。
*   `cmd/internal/gc`: Goコンパイラの内部パッケージで、アーキテクチャに依存しない共通のコード生成ロジックや最適化パスが含まれています。このコミットでは、この共通部分に`OSQRT`という新しい中間表現のオペコードが追加され、各アーキテクチャ固有のバックエンドで対応するハードウェア命令に変換されるように変更されています。

### `obj.ProgInfo`とコンパイラ/アセンブラの概念

Goコンパイラのバックエンドは、最終的に`obj`パッケージで定義された`obj.Prog`構造体（プログラム命令を表す）のリストを生成します。`obj.ProgInfo`は、各命令に関する情報（例: オペランドの読み書きの特性、サイズなど）を定義する構造体です。コンパイラは、GoのAST（抽象構文木）を中間表現に変換し、最終的にターゲットアーキテクチャのアセンブリ命令に変換します。このプロセスにおいて、`optoas`のような関数が、Goの内部オペコードを特定のアセンブリ命令にマッピングする役割を担います。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラが`math.Sqrt`の呼び出しを検出し、それを直接ハードウェアの平方根命令に置き換えるように変更された点にあります。

1.  **新しい中間表現オペコード `OSQRT` の導入**:
    `src/cmd/internal/gc/syntax.go`において、新しいオペコード`OSQRT`が追加されました。これは、`math.Sqrt`関数呼び出しを表現するためのコンパイラ内部の記号です。
    ```diff
    --- a/src/cmd/internal/gc/syntax.go
    +++ b/src/cmd/internal/gc/syntax.go
    @@ -303,6 +303,7 @@ const (
     	ORROTC  // right rotate-carry: ARCR.
     	ORETJMP // return to other function
     	OPS     // compare parity set (for x86 NaN check)
    +	OSQRT   // sqrt(float64), on systems that have hw support
     
     	OEND
     )
    ```
    この`OSQRT`は、`float64`型の平方根計算で、ハードウェアサポートがあるシステムで使用されることを示しています。

2.  **`math.Sqrt`呼び出しの`OSQRT`への変換**:
    `src/cmd/internal/gc/walk.go`の`walkexpr`関数内で、`math.Sqrt`関数への直接呼び出しが検出された場合、そのASTノードのオペレーションが`OSQRT`に書き換えられます。これは、コンパイラの「ウォーク」フェーズ（ASTを走査し、最適化や変換を行うフェーズ）で行われます。
    ```diff
    --- a/src/cmd/internal/gc/walk.go
    +++ b/src/cmd/internal/gc/walk.go
    @@ -622,6 +622,16 @@ func walkexpr(np **Node, init **NodeList) {
     	\twalkexpr(&n.Left, init)
     	\twalkexprlist(n.List, init)
     
    +	\tif n.Left.Op == ONAME && n.Left.Sym.Name == "Sqrt" && n.Left.Sym.Pkg.Path == "math" {
    +	\t\tswitch Thearch.Thechar {
    +	\t\tcase '5', '6':
    +	\t\t\tn.Op = OSQRT
    +	\t\t\tn.Left = n.List.N
    +	\t\t\tn.List = nil
    +	\t\t\tgoto ret
    +	\t\t}
    +	\t}
    +
     	\tll := ascompatte(int(n.Op), n, n.Isddd, getinarg(t), n.List, 0, init)
     	\tn.List = reorder1(ll)
     	\tgoto ret
    ```
    ここで`Thearch.Thechar`が`'5'`（ARM）または`'6'`（AMD64）の場合にのみ変換が行われるため、この最適化はこれらのアーキテクチャに限定されます。

3.  **コード生成における`OSQRT`の処理**:
    *   **`src/cmd/internal/gc/cgen.go`**: `Cgen`関数は、ASTノードからコードを生成する役割を担います。`OSQRT`オペコードが検出された場合、`Thearch.Gins`を呼び出して、アーキテクチャ固有の平方根命令を生成するように変更されました。
        ```diff
        --- a/src/cmd/internal/gc/cgen.go
        +++ b/src/cmd/internal/gc/cgen.go
        @@ -409,6 +409,15 @@ func Cgen(n *Node, res *Node) {
         	\tcgen_norm(n, &n1, res)
         	\treturn
         
        +	case OSQRT:
        +	\tvar n1 Node
        +	\tRegalloc(&n1, nl.Type, res)
        +	\tCgen(n.Left, &n1)
        +	\tThearch.Gins(Thearch.Optoas(OSQRT, nl.Type), &n1, &n1)
        +	\tThearch.Gmove(&n1, res)
        +	\tRegfree(&n1)
        +	\treturn
        +
         	\t\t// symmetric binary
         	case OAND,
         	\t\tOOR,
        ```
        `Thearch.Optoas(OSQRT, nl.Type)`は、`OSQRT`オペコードと型（`float64`）に基づいて、対応するアセンブリ命令（例: `arm.ASQRTD`, `x86.ASQRTSD`）を返します。

    *   **`src/cmd/internal/gc/gen.go`**: `gen`関数は、特定のオペコードに対するコード生成の振る舞いを定義します。`OSQRT`の場合、左の子ノード（平方根を計算する対象の式）のコードを生成し、その結果を破棄するように変更されています。これは、`OSQRT`が単一の命令に展開されるため、別途結果を保持する必要がないことを示唆しています。
        ```diff
        --- a/src/cmd/internal/gc/gen.go
        +++ b/src/cmd/internal/gc/gen.go
        @@ -1002,6 +1002,9 @@ func gen(n *Node) {
         	case ORETURN, ORETJMP:
         	\tcgen_ret(n)
         
        +	case OSQRT:
        +	\tcgen_discard(n.Left)
        +
         	case OCHECKNIL:
         	\tCgen_checknil(n.Left)
         ```

4.  **アーキテクチャ固有のアセンブリ命令へのマッピング**:
    *   **ARM (`src/cmd/5g/gsubr.go`, `src/cmd/5g/prog.go`)**:
        `src/cmd/5g/gsubr.go`の`optoas`関数に、`OSQRT`と`TFLOAT64`の組み合わせが`arm.ASQRTD`（ARMの倍精度浮動小数点平方根命令）にマッピングされるように追加されました。
        `src/cmd/5g/prog.go`の`progtable`に`arm.ASQRTD`のエントリが追加され、その命令の特性（例: `gc.SizeD`で倍精度浮動小数点、`gc.LeftRead | RightRdwr`で左オペランドを読み込み、右オペランドを読み書きする）が定義されました。
    *   **AMD64 (`src/cmd/6g/gsubr.go`, `src/cmd/6g/prog.go`)**:
        `src/cmd/6g/gsubr.go`の`optoas`関数に、`OSQRT`と`TFLOAT64`の組み合わせが`x86.ASQRTSD`（x86の倍精度浮動小数点平方根命令）にマッピングされるように追加されました。
        `src/cmd/6g/prog.go`の`progtable`に`x86.ASQRTSD`のエントリが追加され、その命令の特性が定義されました。

5.  **ベンチマークの追加と修正**:
    `src/math/all_test.go`に、この最適化の効果を測定するための新しいベンチマークが追加されました。特に`BenchmarkSqrtPrime`は、`isPrime`関数内で`Sqrt`を繰り返し呼び出すことで、より現実的なシナリオをシミュレートし、最適化の恩恵を明確に示しています。
    ```go
    func isPrime(i int) bool {
    	// Yes, this is a dumb way to write this code,
    	// but calling Sqrt repeatedly in this way demonstrates
    	// the benefit of using a direct SQRT instruction on systems
    	// that have one, whereas the obvious loop seems not to
    	// demonstrate such a benefit.
    	for j := 2; float64(j) <= Sqrt(float64(i)); j++ {
    		if i%j == 0 {
    			return false
    		}
    	}
    	return true
    }

    func BenchmarkSqrtPrime(b *testing.B) {
    	any := false
    	for i := 0; i < b.N; i++ {
    		if isPrime(100003) {
    			any = true
    		}
    	}
    	if any {
    		Global = 1
    	}
    }
    ```
    このベンチマークは、`Sqrt`の呼び出しがループ内で頻繁に行われ、かつその結果が次の計算に利用されるような状況で、ハードウェア命令への置き換えが有効であることを示しています。

6.  **`src/math/sqrt.go`のコメント更新**:
    `src/math/sqrt.go`に、`Sqrt`が一部のシステムでアセンブリで実装されていること、およびコンパイラが直接ハードウェア命令に置き換える可能性があることについてのコメントが追加されました。
    ```go
    // Note: Sqrt is implemented in assembly on some systems.
    // Others have assembly stubs that jump to func sqrt below.
    // On systems where Sqrt is a single instruction, the compiler
    // may turn a direct call into a direct use of that instruction instead.
    ```

この一連の変更により、Goコンパイラは`math.Sqrt`の特定の呼び出しパターンを認識し、対応するCPUのハードウェア命令に直接変換することで、実行時のパフォーマンスを向上させます。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、主に以下のファイルに分散しています。

*   `src/cmd/internal/gc/syntax.go`: 新しい中間表現オペコード `OSQRT` の定義。
*   `src/cmd/internal/gc/walk.go`: `math.Sqrt` 関数呼び出しを `OSQRT` オペコードに変換するロジック。

## コアとなるコードの解説

*   **`src/cmd/internal/gc/syntax.go` (L293-304)**:
    `OSQRT`という新しい定数が追加され、コンパイラが`math.Sqrt`のようなハードウェアサポートを持つ平方根演算を内部的に表現するための識別子として機能します。これは、コンパイラのフロントエンドとバックエンドの間で、特定の最適化可能な操作を伝えるための「言語」の一部です。

*   **`src/cmd/internal/gc/walk.go` (L622-632)**:
    `walkexpr`関数は、Goのソースコードから生成された抽象構文木（AST）を走査し、様々な変換や最適化を適用します。この変更では、`math`パッケージの`Sqrt`関数への呼び出しが検出された場合、そのASTノードのオペレーションを`OSQRT`に書き換えます。この変換は、コンパイラがこの特定の関数呼び出しを、通常の関数呼び出しシーケンスではなく、特別なハードウェア命令として扱うべきであることを示す「フラグ」を設定する役割を果たします。`Thearch.Thechar`によるアーキテクチャチェック（`'5'`はARM、`'6'`はAMD64）により、この最適化がサポートされるアーキテクチャに限定されます。

*   **`src/cmd/internal/gc/cgen.go` (L409-418)**:
    `Cgen`関数は、ASTノードから最終的な機械語命令を生成する過程の一部です。`OSQRT`オペコードが渡された場合、`Regalloc`でレジスタを割り当て、入力値をレジスタにロードし、`Thearch.Gins(Thearch.Optoas(OSQRT, nl.Type), &n1, &n1)`を呼び出します。この`Gins`呼び出しが、実際にターゲットアーキテクチャの平方根命令（例: `ASQRTD`や`SQRTSD`）を生成する部分です。これにより、Goの関数呼び出しのオーバーヘッドなしに、CPUのネイティブな平方根計算能力が直接利用されます。

*   **`src/cmd/internal/gc/gen.go` (L1002-1005)**:
    `gen`関数は、特定のオペコードに対するコード生成の振る舞いを定義します。`OSQRT`の場合、`cgen_discard(n.Left)`が呼び出されます。これは、`OSQRT`が単一の命令に展開されるため、その入力値（`n.Left`）の計算結果を一時的に保持する必要がなく、単にその値を計算するだけでよいことを示しています。

*   **`src/cmd/5g/gsubr.go` (L1055-1057) および `src/cmd/6g/gsubr.go` (L1131-1133)**:
    これらのファイルは、それぞれARMとAMD64アーキテクチャ固有のコード生成ルーチンを含んでいます。`optoas`関数は、Goコンパイラの内部オペコード（`OSQRT`）を、対応するアセンブリ命令（ARMの`arm.ASQRTD`またはAMD64の`x86.ASQRTSD`）にマッピングします。これにより、コンパイラは抽象的な`OSQRT`を、実際のCPUが理解できる具体的な命令に変換できます。

## 前提知識の解説

### Goコンパイラ (gc) とその役割

Go言語の公式コンパイラは、かつては各アーキテクチャ（例: `5g` for ARM, `6g` for AMD64）ごとに独立したバイナリとして存在していましたが、現在は`cmd/compile`という単一のバイナリに統合されています。しかし、このコミットが作成された2015年時点では、まだ`5g`や`6g`といった名称が使われていました。

コンパイラ（`gc`）は、Goのソースコードを機械語に変換するだけでなく、様々な最適化を行います。これには、関数のインライン化、デッドコードの削除、レジスタ割り当ての最適化などが含まれます。このコミットでは、`math.Sqrt`という特定の関数呼び出しを、コンパイル時にその関数の実装を呼び出すのではなく、直接CPUのハードウェア命令に置き換えるという最適化が行われています。

### アセンブリスタブとハードウェア命令

Goの標準ライブラリには、Go言語で書かれたコードだけでなく、パフォーマンスが重要な部分や、OSとのインターフェース部分などでアセンブリ言語で書かれたコード（アセンブリスタブ）が含まれることがあります。`math.Sqrt`も、多くのシステムではアセンブリで実装されたり、Goで書かれた汎用実装からアセンブリスタブを介して呼び出されたりします。

ハードウェア命令とは、CPUが直接実行できる低レベルな命令のことです。多くの現代のCPUには、浮動小数点演算（加算、減算、乗算、除算、平方根など）を高速に実行するための専用の命令セットが搭載されています。これらの命令は、ソフトウェアで同じ計算を行うよりもはるかに高速です。

### `math.Sqrt`関数

`math.Sqrt`は、`float64`型の引数を取り、その平方根を`float64`型で返すGoの標準関数です。通常、この関数は内部的にCPUの浮動小数点演算ユニット（FPU）を利用して計算を行います。

### Goにおけるベンチマーク (`go test -bench`)

Go言語には、標準でベンチマークテストを記述・実行する機能が組み込まれています。`go test -bench .`コマンドを実行すると、プロジェクト内のベンチマーク関数（`BenchmarkXxx`という命名規則に従う関数）が実行され、各操作にかかる時間（ns/op）、割り当てられたメモリ量（B/op）、割り当て回数（allocs/op）などが報告されます。このコミットのベンチマーク結果は、この機能を使って測定されたものです。

### `cmd/5g`, `cmd/6g`, `cmd/internal/gc`

*   `cmd/5g`: ARMアーキテクチャ向けのGoコンパイラ（歴史的な名称）。
*   `cmd/6g`: AMD64アーキテクチャ向けのGoコンパイラ（歴史的な名称）。
*   `cmd/internal/gc`: Goコンパイラの内部パッケージで、アーキテクチャに依存しない共通のコード生成ロジックや最適化パスが含まれています。このコミットでは、この共通部分に`OSQRT`という新しい中間表現のオペコードが追加され、各アーキテクチャ固有のバックエンドで対応するハードウェア命令に変換されるように変更されています。

### `obj.ProgInfo`とコンパイラ/アセンブラの概念

Goコンパイラのバックエンドは、最終的に`obj`パッケージで定義された`obj.Prog`構造体（プログラム命令を表す）のリストを生成します。`obj.ProgInfo`は、各命令に関する情報（例: オペランドの読み書きの特性、サイズなど）を定義する構造体です。コンパイラは、GoのAST（抽象構文木）を中間表現に変換し、最終的にターゲットアーキテクチャのアセンブリ命令に変換します。このプロセスにおいて、`optoas`のような関数が、Goの内部オペコードを特定のアセンブリ命令にマッピングする役割を担います。

*   `src/cmd/5g/prog.go` および `src/cmd/6g/prog.go`: 各アーキテクチャのアセンブリ命令テーブルに `ASQRTD` および `ASQRTSD` の情報を追加する部分。

## コアとなるコードの解説

*   **`src/cmd/internal/gc/syntax.go` (L293-304)**:
    `OSQRT`という新しい定数が追加され、コンパイラが`math.Sqrt`のようなハードウェアサポートを持つ平方根演算を内部的に表現するための識別子として機能します。これは、コンパイラのフロントエンドとバックエンドの間で、特定の最適化可能な操作を伝えるための「言語」の一部です。

*   **`src/cmd/internal/gc/walk.go` (L622-632)**:
    `walkexpr`関数は、Goのソースコードから生成された抽象構文木（AST）を走査し、様々な変換や最適化を適用します。この変更では、`math`パッケージの`Sqrt`関数への呼び出しが検出された場合、そのASTノードのオペレーションを`OSQRT`に書き換えます。この変換は、コンパイラがこの特定の関数呼び出しを、通常の関数呼び出しシーケンスではなく、特別なハードウェア命令として扱うべきであることを示す「フラグ」を設定する役割を果たします。`Thearch.Thechar`によるアーキテクチャチェック（`'5'`はARM、`'6'`はAMD64）により、この最適化がサポートされるアーキテクチャに限定されます。

*   **`src/cmd/internal/gc/cgen.go` (L409-418)**:
    `Cgen`関数は、ASTノードから最終的な機械語命令を生成する過程の一部です。`OSQRT`オペコードが渡された場合、`Regalloc`でレジスタを割り当て、入力値をレジスタにロードし、`Thearch.Gins(Thearch.Optoas(OSQRT, nl.Type), &n1, &n1)`を呼び出します。この`Gins`呼び出しが、実際にターゲットアーキテクチャの平方根命令（例: `ASQRTD`や`SQRTSD`）を生成する部分です。これにより、Goの関数呼び出しのオーバーヘッドなしに、CPUのネイティブな平方根計算能力が直接利用されます。

*   **`src/cmd/internal/gc/gen.go` (L1002-1005)**:
    `gen`関数は、特定のオペコードに対するコード生成の振る舞いを定義します。`OSQRT`の場合、`cgen_discard(n.Left)`が呼び出されます。これは、`OSQRT`が単一の命令に展開されるため、その入力値（`n.Left`）の計算結果を一時的に保持する必要がなく、単にその値を計算するだけでよいことを示しています。

*   **`src/cmd/5g/gsubr.go` (L1055-1057) および `src/cmd/6g/gsubr.go` (L1131-1133)**:
    これらのファイルは、それぞれARMとAMD64アーキテクチャ固有のコード生成ルーチンを含んでいます。`optoas`関数は、Goコンパイラの内部オペコード（`OSQRT`）を、対応するアセンブリ命令（ARMの`arm.ASQRTD`またはAMD64の`x86.ASQRTSD`）にマッピングします。これにより、コンパイラは抽象的な`OSQRT`を、実際のCPUが理解できる具体的な命令に変換できます。

*   **`src/cmd/5g/peep.go` (L1101-1102)**:
    `copyu`関数は、コピー最適化に関連する部分です。`arm.ASQRTD`がこのリストに追加されたことで、平方根命令の結果がすぐに別のレジスタにコピーされるような冗長な操作が、コンパイラによって最適化されないように指示されます。これは、ハードウェア命令が直接結果を生成するため、中間的なコピーが不要であることを示唆している可能性があります。

*   **`src/cmd/5g/prog.go` (L70-80) および `src/cmd/6g/prog.go` (L204-205)**:
    これらのファイルは、各アーキテクチャのアセンブリ命令に関するメタデータ（例: オペランドのサイズ、読み書きの特性）を定義する`progtable`を含んでいます。`arm.ASQRTD`と`x86.ASQRTSD`のエントリが追加され、コンパイラがこれらの命令を正しく扱うために必要な情報が提供されます。

*   **`src/math/all_test.go` (L2977-3020)**:
    `BenchmarkSqrtPrime`は、この最適化の実際の効果を示すために非常に重要です。このベンチマークは、素数判定アルゴリズム内で`math.Sqrt`を繰り返し呼び出すことで、`Sqrt`がボトルネックとなるようなシナリオを意図的に作り出しています。この「非自明な」ベンチマークで性能が大幅に向上したことは、この最適化が現実世界のアプリケーションでメリットをもたらす可能性を示唆しています。

*   **`src/math/sqrt.go` (L91-96)**:
    このコメントは、`math.Sqrt`の実装がシステムによって異なること、特に一部のシステムではアセンブリで実装されていること、そしてコンパイラが直接ハードウェア命令に置き換える可能性があることを開発者に伝えています。これは、Goの移植性とパフォーマンスのバランスを示す良い例です。

これらの変更は、Goコンパイラが特定の数値計算を、より低レベルで効率的なハードウェア命令に「インライン化」する能力を獲得したことを意味します。これにより、Goプログラムは、特に数値計算が頻繁に行われるアプリケーションにおいて、より高いパフォーマンスを発揮できるようになります。

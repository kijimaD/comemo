## 変更の背景

Go言語の `crypto/cipher` パッケージには、バイト列のXOR演算を高速に行うための `fastXORBytes` という関数が存在します。この関数は、特定のCPUアーキテクチャがアンアラインドなメモリアクセス（メモリのアドレスがワードサイズ境界に揃っていないアクセス）を効率的に処理できる場合に、最適化されたパスを使用するように設計されています。

`s390x` はIBMのメインフレームで使用される64ビットアーキテクチャであり、その設計上、アンアラインドな64ビット値のロードおよびストアをハードウェアレベルで効率的にサポートしています。これまでのGoのランタイムでは、`s390x` がこの特性を持つことが `fastXORBytes` の `supportsUnaligned` フラグに反映されていませんでした。その結果、`s390x` 環境では、本来利用できるはずの高速なXOR演算パスが使われず、汎用的な（そして遅い）パスが選択されていました。

このコミットは、`s390x` アーキテクチャの能力をGoランタイムが正しく認識し、暗号処理のパフォーマンスを向上させることを目的としています。

## 前提知識の解説

### 1. XOR演算と暗号処理

XOR（排他的論理和）演算は、暗号化において非常に基本的な操作です。ストリーム暗号やブロック暗号のモード（例: CTRモード、OFBモード）では、平文や暗号文とキー（またはキーから派生したストリーム）との間でバイトごとのXOR演算が頻繁に行われます。この演算の速度は、暗号システムの全体的なパフォーマンスに直結します。

### 2. `crypto/cipher` パッケージ

Go言語の標準ライブラリ `crypto/cipher` パッケージは、共通鍵暗号のブロック暗号モードやストリーム暗号の実装を提供します。このパッケージ内の `xor.go` ファイルには、バイトスライス間でXOR演算を行うためのユーティリティ関数が含まれており、その中でも `fastXORBytes` はパフォーマンスが要求される場面で利用されます。

### 3. メモリのアラインメントとアンアラインメント

*   **メモリのアラインメント（Alignment）**: 多くのCPUアーキテクチャでは、データが特定のメモリアドレス境界に配置されている場合に、最も効率的にアクセスできます。例えば、32ビットの整数は4バイト境界に、64ビットの整数は8バイト境界に配置されていることが理想的です。このような配置を「アラインド（aligned）」と呼びます。
*   **アンアラインド（Unaligned）アクセス**: データがその自然な境界に揃っていないメモリアドレスからアクセスされることを指します。
    *   **パフォーマンスへの影響**: 多くのアーキテクチャでは、アンアラインドアクセスはアラインドアクセスよりも大幅に遅くなる可能性があります。これは、CPUが複数のメモリアクセスを実行してデータを再構築する必要があるためです。
    *   **ハードウェアサポート**: 一部のアーキテクチャ（例: x86, s390x）は、ハードウェアレベルでアンアラインドアクセスを効率的に処理できます。しかし、他のアーキテクチャ（例: ARMの古いバージョン）では、アンアラインドアクセスが例外（アラインメントフォルト）を発生させたり、非常に大きな性能ペナルティを伴ったりすることがあります。

### 4. `s390x` アーキテクチャ

`s390x` は、IBMのz/Architectureを実装した64ビットのメインフレームプロセッサアーキテクチャです。このアーキテクチャは、高い信頼性、可用性、保守性（RAS特性）と、大量のI/Oおよびトランザクション処理に特化しています。`s390x` は、その設計思想から、メモリ操作の柔軟性が高く、アンアラインドなメモリアクセスを効率的に処理できる特性を持っています。これは、様々なデータ形式やプロトコルを扱うメインフレーム環境において、ソフトウェアの複雑性を軽減し、パフォーマンスを維持するために重要です。

## 技術的詳細

`fastXORBytes` 関数は、内部的に `uintptr` 型（ポインタを保持できる整数型）のワードサイズでメモリを読み書きすることで、バイトごとのXORループよりも高速な処理を実現します。しかし、この最適化は、CPUがワードサイズのアンアラインドな読み書きを効率的にサポートしている場合にのみ安全かつ高速に機能します。

Goランタイムは、`runtime.GOARCH` という環境変数を通じて現在のCPUアーキテクチャを識別します。`xor.go` ファイル内の `supportsUnaligned` 定数は、この `runtime.GOARCH` の値に基づいて、どのアーキテクチャがアンアラインドアクセスをサポートしているかを判定します。

このコミット以前は、`supportsUnaligned` 定数は `386` (x86 32-bit), `amd64` (x86 64-bit), `ppc64` (PowerPC 64-bit big-endian), `ppc64le` (PowerPC 64-bit little-endian) のみをアンアラインドアクセス対応アーキテクチャとして認識していました。`s390x` はこのリストに含まれていなかったため、`s390x` 上でGoプログラムが実行される際には、`fastXORBytes` はその高速パスを利用せず、より安全だが低速なバイトごとのXORループにフォールバックしていました。

今回の変更により、`s390x` が `supportsUnaligned` リストに追加されたことで、`s390x` 環境でも `fastXORBytes` がアンアラインドなワードアクセスを利用した高速なXOR演算を実行できるようになり、暗号処理のパフォーマンスが向上します。

## コアとなるコードの解説

変更された行は `supportsUnaligned` という定数の定義です。

```go
const supportsUnaligned = runtime.GOARCH == "386" || runtime.GOARCH == "amd64" || runtime.GOARCH == "ppc64" || runtime.GOARCH == "ppc64le" || runtime.GOARCH == "s390x"
```

この定数はブール値であり、現在の実行環境のCPUアーキテクチャ (`runtime.GOARCH`) が、アンアラインドなメモリ読み書きを効率的にサポートしているかどうかを示します。

*   `runtime.GOARCH == "386"`: Intel/AMD x86 32ビットアーキテクチャ
*   `runtime.GOARCH == "amd64"`: Intel/AMD x86 64ビットアーキテクチャ
*   `runtime.GOARCH == "ppc64"`: PowerPC 64ビット (ビッグエンディアン)
*   `runtime.GOARCH == "ppc64le"`: PowerPC 64ビット (リトルエンディアン)
*   `runtime.GOARCH == "s390x"`: IBM z/Architecture 64ビット

この変更により、`s390x` アーキテクチャでGoプログラムが実行される際、`supportsUnaligned` が `true` と評価されるようになります。その結果、`fastXORBytes` 関数は、アンアラインドアクセスを前提とした高速なワード単位のXOR演算パスを選択し、暗号処理の性能が向上します。これは、`s390x` のハードウェア特性をGoランタイムが最大限に活用するための重要な最適化です。

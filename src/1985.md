# [インデックス 1985] ファイルの概要

このコミットは、Go言語のランタイムにおける文字列の内部表現を根本的に変更するものです。具体的には、文字列がポインタと長さを直接含む構造体として表現されるようになり、これによりメモリ管理の柔軟性と効率が向上しました。また、コンパイラ内部での文字列リテラルの扱いとランタイムでの文字列の扱いが明確に分離されました。

## 変更の背景

このコミットが行われた2009年4月は、Go言語がまだ初期開発段階にあった時期です。Go言語の設計目標の一つに、効率的なメモリ管理と高速な実行性能がありました。初期の文字列表現は、おそらくC言語のNULL終端文字列や、固定サイズのバッファを内包する構造体のようなものであったと推測されます。しかし、このような表現では、文字列の連結、スライス、部分文字列の抽出といった操作において、非効率なメモリコピーが発生したり、柔軟性に欠けたりする問題がありました。

この変更の主な背景は以下の点にあると考えられます。

1.  **効率性の向上**: 文字列データを指すポインタと長さを直接持つ構造体に変更することで、文字列のコピーを最小限に抑え、データへの参照渡しを効率的に行えるようになります。特に、文字列のスライス操作では、新しい文字列データを作成する代わりに、既存のデータへのポインタと新しい長さを設定するだけで済むようになります。
2.  **スライスとの一貫性**: Go言語のスライス（`[]byte`など）は、内部的にポインタ、長さ、容量の3つの要素で構成されています。文字列をポインタと長さで表現することで、スライスとの類似性が高まり、ランタイムでの処理を共通化しやすくなります。これにより、コードの複雑さを減らし、最適化の機会を増やすことができます。
3.  **メモリ管理の改善**: 文字列データ自体をヒープ上に確保し、文字列構造体からそのデータを指すようにすることで、ガベージコレクションの効率が向上し、メモリフラグメンテーションを抑制できる可能性があります。
4.  **コンパイラとランタイムの分離**: コンパイラが扱う文字列リテラル（`Strlit`）と、ランタイムが扱う文字列（`String`）の型を明確に分離することで、それぞれの役割に応じた最適化や表現が可能になります。コンパイラは文字列リテラルを効率的に管理し、ランタイムは実行時の文字列操作に特化できます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の基本的な概念と、当時のC言語ベースのコンパイラ・ランタイムの知識が必要です。

### 1. Go言語の文字列 (変更前)

このコミット以前のGo言語の文字列の正確な内部表現は、コミットログからは直接読み取れませんが、変更内容から推測できます。
変更前の`src/runtime/runtime.h`の`String`構造体は、`byte str[1]`というフィールドを持っていました。これは、C言語で可変長配列を構造体の最後に配置する慣用的な手法（flexible array memberの古い形式）に似ています。この場合、`String`構造体自体が文字列データを保持するか、あるいは`str`が文字列データの開始位置を示すポインタとして扱われていた可能性があります。しかし、`len`フィールドが`String`構造体の外に定義されていたり、`string`型が`*string`（ポインタ）として扱われていたことから、文字列データは`String`構造体とは別に確保され、`string`型は`String`構造体へのポインタとして扱われていた可能性が高いです。そして、その`String`構造体の中に、文字列の長さと、文字列データへのポインタ（またはインラインの短い文字列データ）が含まれていたと推測されます。

### 2. Go言語のスライス

Go言語のスライスは、配列の一部を参照するための軽量なデータ構造です。スライスは以下の3つの要素で構成されます。

*   **ポインタ (Pointer)**: スライスが参照する基底配列の先頭要素へのポインタ。
*   **長さ (Length)**: スライスに含まれる要素の数。
*   **容量 (Capacity)**: スライスの基底配列の先頭から、基底配列の末尾までの要素の数。

スライスは値渡しされますが、内部のポインタが同じ基底配列を指すため、スライスを介して基底配列の要素を変更すると、その変更は他のスライスからも見えます。

### 3. 値渡しとポインタ渡し

*   **値渡し (Pass by Value)**: 関数の引数として渡される変数の値がコピーされます。関数内で引数の値を変更しても、呼び出し元の変数は影響を受けません。Go言語では、プリミティブ型（int, boolなど）や構造体はデフォルトで値渡しされます。
*   **ポインタ渡し (Pass by Pointer)**: 関数の引数として変数のメモリアドレス（ポインタ）が渡されます。関数内でポインタが指す先の値を変更すると、呼び出し元の変数も影響を受けます。

このコミットでは、Goの`string`型がポインタ型から構造体型（値型）に変更され、関数呼び出しの際に値渡しされるようになります。しかし、その構造体内部には文字列データへのポインタが含まれるため、実質的には文字列データ自体はコピーされず、効率的な参照が可能になります。

### 4. コンパイラの役割

Go言語のコンパイラ（この場合は`6g`や`gc`）は、ソースコードを機械語に変換するだけでなく、型チェック、最適化、ランタイムとの連携など、多くの役割を担っています。文字列リテラルはコンパイル時に処理され、通常は実行可能ファイルのデータセクションに格納されます。

## 技術的詳細

このコミットの核心は、Go言語の文字列の内部表現を、従来のポインタベースの表現から、ポインタと長さを直接含む構造体ベースの表現へと変更した点にあります。

### 1. `String`構造体の再定義

最も重要な変更は、`src/runtime/runtime.h`における`String`構造体の定義です。

**変更前:**
```c
struct String
{
    int32   len;
    byte    str[1]; // Flexible array member (or similar concept)
};
typedef struct String *string; // string is a pointer to String
```
この定義では、`string`型は`String`構造体へのポインタでした。`str[1]`は、文字列データが`String`構造体の直後に続くことを示す慣用的な方法です。

**変更後:**
```c
struct String
{
    byte*   str; // Pointer to the actual string data
    int32   len; // Length of the string
};
typedef struct String String; // string is now the String struct itself (value type)
```
この変更により、`string`型は`String`構造体そのもの（値型）になりました。`str`フィールドは、文字列データが格納されているメモリ上の場所を指すポインタとなり、`len`フィールドはその文字列の長さを保持します。これにより、文字列データ自体は`String`構造体の外部に存在し、`String`構造体はデータへの「ビュー」を提供する形になります。

### 2. `Strlit`型の導入と役割分担

`src/cmd/gc/go.h`では、コンパイラ内部で文字列リテラルを扱うための新しい型`Strlit`が導入されました。

```c
typedef struct Strlit Strlit;
struct Strlit
{
    int32   len;
    char    s[3]; // variable (flexible array member)
};
```
これは、コンパイラがソースコード中の文字列リテラルを解析し、内部的に表現するための型です。`s[3]`は、コンパイラが文字列リテラルを処理する際に、そのデータをインラインで保持するためのバッファとして機能します。この`Strlit`型は、ランタイムの`String`型とは異なる目的で使用され、コンパイラとランタイムの間で文字列の表現が分離されたことを示しています。コンパイラは`Strlit`を使って文字列リテラルを管理し、最終的にランタイムの`String`形式に変換して実行可能ファイルに埋め込みます。

### 3. `OLEN`操作の変更

`src/cmd/6g/cgen.c`では、`len()`組み込み関数の処理が変更されました。

**変更前:**
```c
case OLEN:
    if(istype(nl->type, TSTRING) || istype(nl->type, TMAP)) {
        // both string and map have len in the first 32-bit word.
        // ...
    }
    if(isslice(nl->type)) {
        // ...
    }
```
**変更後:**
```c
case OLEN:
    if(istype(nl->type, TMAP)) {
        // map hsd len in the first 32-bit word.
        // ...
    }
    if(istype(nl->type, TSTRING) || isslice(nl->type)) {
        // both slice and string have len in the first 32-bit word.
        // a zero pointer means zero length
        // ...
    }
```
この変更は、`string`型が`slice`型と同様に、先頭の32ビットワードに長さを保持するようになったことを明確に示しています。これは、`String`構造体の`len`フィールドが、その構造体の先頭から特定のオフセットに配置されることを意味します。これにより、`len()`関数は文字列とスライスの両方に対して共通のロジックで長さを取得できるようになり、コードの簡素化と一貫性が図られます。

### 4. `sizeof_String`の導入

`src/cmd/gc/align.c`では、`sizeof_String`という新しい定数が導入され、`TSTRING`（文字列型）のサイズ計算に使用されるようになりました。

```c
case TSTRING:
    w = sizeof_String;
    break;
// ...
// string is same as slice wo the cap
sizeof_String = rnd(Array_nel+types[TUINT32]->width, maxround);
```
`sizeof_String`は、スライスの長さフィールド（`Array_nel`）とそれに続く`uint32`の幅を考慮して計算されます。これは、文字列がスライスと同様に、ポインタと長さの2つの要素で構成されることを裏付けています（スライスはさらに容量も持つ）。これにより、文字列のメモリレイアウトがスライスと非常に似たものになり、ランタイムでの処理の共通化がさらに進みます。

### 5. 関数シグネチャの変更と値渡し

`src/runtime`ディレクトリ内の多くのファイル（`runtime.c`, `print.c`, `iface.c`, `amd64/traceback.c`, `string.c`など）で、`string`型の引数や戻り値の型が`string`（ポインタ）から`String`（構造体）に変更されました。

### 6. `emptystring`の変更

`src/runtime/string.c`では、空文字列`emptystring`の定義が変更されました。

**変更前:**
```c
static  int32   empty       = 0;
string  emptystring = (string)&empty;
```
**変更後:**
```c
String  emptystring;
```
変更前は、`emptystring`が`int32`型の変数`empty`のアドレスを指すポインタとして定義されていました。これは、空文字列の長さが0であることを示すためのハックのようなものです。変更後は、`emptystring`が`String`構造体そのものとして定義され、その`str`フィールドはNULLポインタ、`len`フィールドは0に初期化されることになります。これにより、空文字列の表現がより自然で、新しい`String`構造体のセマンティクスに合致するようになりました。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は以下のファイルに集中しています。

1.  **`src/cmd/gc/go.h`**:
    *   `String`型が`Strlit`型にリネームされ、コンパイラ内部の文字列リテラル表現として明確化。

# [インデックス 22222] ファイルの概要

このコミットは、GoランタイムがPlan 9オペレーティングシステム上で乱数を生成する際に、`/dev/random`デバイスの使用を停止し、代わりに内部の擬似乱数生成メカニズムである`extendRandom`に完全に依存するように変更するものです。これにより、`/dev/random`の遅延やブロッキングによるパフォーマンス低下を防ぎます。

## 元コミット内容

Plan 9環境において、Goランタイムが乱数生成のために`/dev/random`を使用しないように変更します。これは、`/dev/random`が遅く、ブロッキングする可能性があるためです。ハッシュ値の分布をわずかに改善するためだけにGoプログラムの速度を著しく低下させたくないため、NaClと同様に、擬似乱数生成に`extendRandom`のみを使用するようにします。

## 変更の背景

この変更の主な背景は、Plan 9オペレーティングシステムにおける`/dev/random`デバイスの特性にあります。`/dev/random`は、システムのエントロピー（予測不可能性）源から真の乱数を生成しようとします。これには、キーボード入力、マウスの動き、ディスクI/O、システム割り込みなどの環境ノイズが利用されます。しかし、真の乱数を生成するためには十分なエントロピーが必要であり、エントロピーが不足すると`/dev/random`は新しいエントロピーが収集されるまで読み取りをブロックします。

Goランタイムは、ハッシュ値の生成など、様々な内部処理で乱数を使用します。これらの処理において、`/dev/random`からの読み取りがブロックされると、Goプログラム全体のパフォーマンスが著しく低下する可能性があります。コミットメッセージにあるように、「ハッシュ値の分布をわずかに改善するためだけにGoプログラムの速度を著しく低下させたくない」という明確な意図があります。

この問題に対処するため、GoランタイムはPlan 9上での乱数生成戦略を変更し、より高速で非ブロッキングな擬似乱数生成メカニズムに依存することになりました。

## 前提知識の解説

### `/dev/random`と`/dev/urandom`

Unix系システム（Plan 9も含む）には、乱数を提供する特別なデバイスファイルとして`/dev/random`と`/dev/urandom`が存在します。

*   **`/dev/random`**: システムのエントロピープールから真の乱数を生成します。エントロピーが不足すると、新しいエントロピーが収集されるまで読み取りをブロックします。これにより、生成される乱数の品質は非常に高いですが、パフォーマンスが低下したり、アプリケーションがハングアップしたりする可能性があります。暗号鍵の生成など、非常に高いセキュリティが要求される場面で使用されます。
*   **`/dev/urandom`**: エントロピープールからシードされた擬似乱数生成器（CSPRNG: Cryptographically Secure Pseudo-Random Number Generator）から乱数を生成します。エントロピーが不足してもブロックせず、既存のエントロピーから擬似乱数を生成し続けます。これにより、高速に乱数を供給できますが、エントロピーが枯渇した場合、理論的には予測可能になるリスクがあります（ただし、現代のCSPRNGは非常に強力であり、実用上は安全とされています）。

### 擬似乱数生成器 (PRNG) と暗号論的擬似乱数生成器 (CSPRNG)

*   **擬似乱数生成器 (PRNG)**: 決定論的なアルゴリズムに基づいて乱数のように見える数列を生成します。初期シード値が同じであれば、常に同じ数列が生成されます。一般的なシミュレーションやゲームなどで使用されます。
*   **暗号論的擬似乱数生成器 (CSPRNG)**: PRNGの一種ですが、暗号学的な要件を満たすように設計されています。生成される数列が統計的にランダムであるだけでなく、将来の数列を予測することが計算上困難であるという特性を持ちます。少量の真の乱数（エントロピー）でシードされることで、大量の高品質な擬似乱数を高速に生成できます。

### Plan 9における乱数生成

Plan 9では、`/dev/random`が真の乱数を提供しますが、その生成は遅く、ブロッキングする可能性があります。一般的な用途では、`genrandom`という関数が推奨されます。`genrandom`は、`/dev/random`から少量の真の乱数でシードされたCSPRNG（X9.17アルゴリズム）を使用し、高速に擬似乱数を生成します。

### `extendRandom` (Goランタイム内部)

Goランタイムにおける`extendRandom`は、内部で使用される擬似乱数生成メカニズムの一部であると考えられます。コミットメッセージから、これはGoが独自に管理する擬似乱数生成器であり、外部の`/dev/random`に依存せずに乱数を生成する能力を持っていることが示唆されます。この関数は、おそらく既存の乱数バイト列を拡張したり、新しい擬似乱数バイトを生成したりするために使用されます。

### NaCl (Networking and Cryptography library)

NaClは、高速で安全な暗号プリミティブを提供するライブラリです。コミットメッセージでNaClが参照されているのは、NaClが乱数生成において、真の乱数源に過度に依存せず、効率的なCSPRNGを内部で利用する設計思想を持っていることへの言及であると考えられます。つまり、Goランタイムも同様に、パフォーマンスを重視し、内部のCSPRNG（`extendRandom`）を優先するという方針を示唆しています。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムがPlan 9上で乱数を取得する際の戦略を根本的に変更した点にあります。

変更前は、`getRandomData`関数内で`/dev/random`デバイスを開き、そこから乱数バイトを読み取っていました。この操作は、前述の通り、Plan 9の`/dev/random`がエントロピー不足時にブロッキングする特性を持つため、Goプログラムの実行を停止させる可能性がありました。特に、ハッシュ値の生成など、頻繁に乱数を必要とする処理において、このブロッキングは深刻なパフォーマンス問題を引き起こします。

変更後は、`/dev/random`への依存を完全に排除しました。具体的には、`random_dev`変数の削除、`/dev/random`を開く`open`システムコール、そこから読み取る`read`システムコール、そしてファイルを閉じる`close`システムコールの呼び出しが削除されました。

代わりに、`getRandomData`関数は`extendRandom(r, 0)`を呼び出すだけになりました。ここで注目すべきは、`extendRandom`の第二引数が`0`になっている点です。変更前は、`/dev/random`から実際に読み取ったバイト数`n`を渡していました。これは、`extendRandom`が読み取った真の乱数バイトを内部の擬似乱数生成器の状態に混ぜ込む（シードする、またはエントロピーを供給する）役割を担っていたことを示唆します。しかし、変更後は`0`を渡すことで、外部からのエントロピー供給なしに、`extendRandom`が純粋に内部の擬似乱数生成ロジックに基づいて乱数を生成するようになったことを意味します。

この変更は、ハッシュ値の生成に必要な乱数の品質が、真の乱数である必要はなく、十分にランダムに見える擬似乱数で事足りるという判断に基づいています。ハッシュ値の衝突耐性には乱数性が重要ですが、それが真の乱数であることよりも、高速かつ安定して乱数を供給できることの方が、Goプログラム全体の応答性にとっては重要であるというトレードオフがなされています。

これにより、GoプログラムはPlan 9環境下で、乱数生成のために外部デバイスのブロッキングに悩まされることなく、安定したパフォーマンスで動作するようになります。

## コアとなるコードの解説

変更は`src/runtime/os1_plan9.go`ファイル内の`getRandomData`関数に集中しています。

1.  **`random_dev`変数の削除**:
    変更前: `var random_dev = []byte("/dev/random\x00")`
    変更後: 削除
    これは、`/dev/random`デバイスへのパスを保持していた変数が不要になったため削除されました。

2.  **`/dev/random`からの読み取りロジックの削除**:
    変更前:
    ```go
    	fd := open(&random_dev[0], 0 /* O_RDONLY */, 0)
    	n := read(fd, unsafe.Pointer(&r[0]), int32(len(r)))
    	close(fd)
    ```
    変更後: 削除
    この部分は、Plan 9のシステムコールである`open`で`/dev/random`を開き、`read`で乱数を読み取り、`close`で閉じる一連の処理を行っていました。この処理が、`/dev/random`のブロッキング問題の根源であったため、完全に削除されました。

3.  **`extendRandom`の呼び出し変更**:
    変更前: `extendRandom(r, int(n))`
    変更後: `extendRandom(r, 0)`
    `extendRandom`関数は、Goランタイム内部の擬似乱数生成器に関連する関数です。変更前は、`/dev/random`から実際に読み取ったバイト数`n`を第二引数に渡していました。これは、読み取った真の乱数バイトを擬似乱数生成器のシードやエントロピーとして利用していたことを示唆します。
    変更後は、第二引数に`0`を渡しています。これは、外部からのエントロピー供給なしに、`extendRandom`が純粋に内部の擬似乱数生成ロジックに基づいて乱数を生成するようになったことを意味します。つまり、`getRandomData`はもはや真の乱数源に依存せず、完全に擬似乱数でデータを埋める役割を担うようになりました。

この変更により、GoランタイムはPlan 9環境において、乱数生成のパフォーマンスと安定性を向上させ、`/dev/random`のブロッキングによる影響を受けなくなりました。

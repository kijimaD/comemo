## 前提知識の解説

### Goの並行処理とGoroutine、Channel

Go言語は、並行処理を言語レベルでサポートしており、その中心となるのが「Goroutine」と「Channel」です。

*   **Goroutine**: Goランタイムによって管理される軽量なスレッドです。数千、数万といった多数のGoroutineを同時に実行しても、OSのスレッドに比べてオーバーヘッドが非常に小さいのが特徴です。`go` キーワードを使って関数呼び出しの前に記述することで、新しいGoroutineを起動できます。
*   **Channel**: Goroutine間で値を安全に送受信するための通信メカニズムです。チャネルは型付けされており、特定の型の値のみを送受信できます。チャネルは、Goroutine間の同期と通信をシンプルかつ安全に行うためのGoの哲学「Do not communicate by sharing memory; instead, share memory by communicating.（メモリを共有して通信するのではなく、通信によってメモリを共有せよ）」を体現しています。

### Channelの操作

チャネルには主に以下の操作があります。

*   **`make(chan Type, [capacity])`**: 新しいチャネルを作成します。`Type` はチャネルが送受信する値の型です。`capacity` はオプションで、バッファのサイズを指定します。`capacity` が0の場合、チャネルはアンバッファード（同期）チャネルとなり、送信と受信が同時に行われるまでブロックします。`capacity` が0より大きい場合、チャネルはバッファード（非同期）チャネルとなり、バッファが満杯になるまで送信はブロックせず、バッファが空になるまで受信はブロックしません。
*   **`ch <- value`**: `value` をチャネル `ch` に送信します。
*   **`value := <-ch`**: チャネル `ch` から値を受信し、`value` に代入します。
*   **`value, ok := <-ch`**: チャネル `ch` から値を受信し、`value` に代入します。`ok` はブール値で、チャネルが閉じられる前に値が受信された場合は `true`、チャネルが閉じられた後に値が受信された（その場合 `value` はゼロ値になる）場合は `false` となります。この `ok` イディオムは、チャネルが閉じられたことを検出するために非常に重要です。
*   **`close(ch)`**: チャネル `ch` を閉じます。閉じられたチャネルへの送信は `panic` を引き起こします。閉じられたチャネルからの受信は、バッファにまだ値が残っていればその値を返し、バッファが空になった後はそのチャネルの要素型のゼロ値を返し、`ok` は `false` となります。

### `select` ステートメント

`select` ステートメントは、複数のチャネル操作を同時に待機し、準備ができた最初の操作を実行するために使用されます。これは、Unixの `select` システムコールに似ています。

*   `select` は、複数の `case` 文を持ち、それぞれの `case` はチャネルの送受信操作を含みます。
*   複数の `case` が同時に準備できた場合、`select` はランダムに1つを選択して実行します。
*   どの `case` も準備できていない場合、`select` はブロックします。
*   **`default` ケース**: `select` ステートメントに `default` ケースが含まれている場合、どのチャネル操作も準備できていないときに `default` ケースが即座に実行されます。これにより、`select` はブロックせずに非ブロッキングなチャネル操作を行うことができます。

### `panic`

Goにおける `panic` は、プログラムの実行を停止させるランタイムエラーの一種です。通常、回復不可能なエラーやプログラマの論理的な誤りを示すために使用されます。`panic` が発生すると、現在のGoroutineの実行が停止し、遅延関数（`defer`）が実行され、コールスタックを遡って `panic` が伝播します。`recover` 関数を使って `panic` から回復することも可能ですが、通常はプログラムを終了させるために使用されます。

## 技術的詳細

このテストケース `issue8347.go` は、バッファ付きチャネル `c` を使用し、`select` ステートメントの `default` ケースとチャネルのクローズ処理がどのように相互作用するかを検証しています。

テストの核心は、`for` ループ内で `select` ステートメントを繰り返し実行し、チャネル `c` が閉じられる前と後で `ok` 変数の値が期待通りに振る舞うことを確認することです。

1.  **チャネルの初期化**: `c := make(chan bool, 1)` で、容量1のバッファ付きブールチャネルを作成します。
2.  **ループ処理**: `for i := 0; i < 12; i++` のループが12回実行されます。
3.  **`select` ステートメント**:
    *   `case _, ok = <-c:`: チャネル `c` から値を受信しようとします。受信が成功した場合、`ok` は `true` になります。チャネルが閉じられていてバッファが空の場合、`ok` は `false` になります。
    *   `default:`: `case` が準備できていない場合、即座にこのブロックが実行されます。
4.  **`ok` の検証（チャネルクローズ前）**:
    *   `if i < 10 && !ok { panic("BUG") }`: ループの最初の10回（`i` が0から9まで）は、チャネル `c` は開いています。この期間に `ok` が `false` になることは、チャネルが閉じられたことを意味するため、バグとみなされます。`select` ステートメントに `default` ケースがあるため、チャネルに値がない場合でもブロックせず、`default` ケースが実行されます。このとき、`ok` の値は `case` 節が実行されていないため変更されません。しかし、`case` 節が実行された場合（例えば、別のGoroutineがチャネルに値を送信した場合）、`ok` は `true` になるはずです。このテストでは、チャネルに値が送信されることはないので、`case` 節は実行されず、`ok` の値は初期値の `true` のままか、あるいは以前のイテレーションで `case` 節が実行された場合の値が保持されます。この `if` 文は、`case` 節が実行されたにもかかわらず `ok` が `false` になるという、チャネルが閉じられていないにもかかわらず閉じられたと誤認するバグを検出することを意図しています。
5.  **チャネルのクローズ**:
    *   `if i >= 10 && ok { close(c) }`: ループの10回目（`i = 10`）で、チャネル `c` が閉じられます。この条件 `ok` は、チャネルが閉じられる直前の `ok` の状態をチェックしています。もし `ok` が `false` であれば、チャネルは既に閉じられているか、何らかの異常が発生していることになります。
6.  **`ok` の検証（チャネルクローズ後）**:
    *   `if i < 10 && !ok { panic("BUG") }` の後に、同じ条件 `if i < 10 && !ok { panic("BUG") }` が再度チェックされています。これは、`select` ステートメントの直後だけでなく、ループの各イテレーションの終わりにも `ok` の状態を再確認することで、より堅牢なテストを実現しています。
    *   チャネルが閉じられた後（`i >= 10`）、`case _, ok = <-c:` が実行されると、チャネル `c` のバッファが空であれば `ok` は `false` になることが期待されます。このテストは、この `ok` の値が正しく `false` になることを検証しています。もし `ok` が `true` のままであれば、それはバグを示します。

このテストは、`select` ステートメントが `default` ケースを持つ場合に、閉じられたチャネルからの受信が正しく `ok=false` を返すことを保証するためのものです。特に、チャネルが閉じられた後に `select` が `default` ケースにフォールバックする際に、`ok` の状態が誤って保持されるようなエッジケースを捉えることを目的としています。

// run

// Copyright 2014 The Go Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style

package main

func main() {
	c := make(chan bool, 1)
	ok := true
	for i := 0; i < 12; i++ {
		select {
		case _, ok = <-c:
			if i < 10 && !ok {
				panic("BUG")
			}
		default:
		}
		if i < 10 && !ok {
			panic("BUG")
		}
		if i >= 10 && ok {
			close(c)
		}
	}
}
```

*   `func main() { ... }`: プログラムのエントリポイントです。
*   `c := make(chan bool, 1)`: 容量1のバッファ付きブールチャネル `c` を作成します。バッファ付きチャネルであるため、送信操作はバッファが満杯になるまでブロックせず、受信操作はバッファが空になるまでブロックしません。
*   `ok := true`: ブール変数 `ok` を `true` で初期化します。この変数は、チャネルからの受信操作の結果（チャネルが閉じられているかどうか）を保持するために使用されます。
*   `for i := 0; i < 12; i++ { ... }`: 12回繰り返されるループです。このループ内でチャネルの操作と検証が行われます。
*   `select { ... }`: 複数のチャネル操作を待機するための `select` ステートメントです。
    *   `case _, ok = <-c:`: この `case` は、チャネル `c` から値を受信しようとします。
        *   `_`: 受信した値は使用しないため、ブランク識別子で破棄しています。
        *   `ok = <-c`: チャネルからの受信操作の結果、`ok` 変数にチャネルが閉じられているかどうかの情報が代入されます。チャネルが閉じられていない場合は `true`、閉じられている場合は `false` となります。
        *   `if i < 10 && !ok { panic("BUG") }`: この条件は、チャネルが閉じられる前（`i` が10未満）に `ok` が `false` になるのはバグであると主張しています。`select` に `default` ケースがあるため、チャネルに値がない場合でもブロックせず、`default` ケースが実行されます。このとき、`ok` の値は `case` 節が実行されていないため変更されません。しかし、もし `case` 節が実行されたにもかかわらず `ok` が `false` になるような状況があれば、それはバグです。
    *   `default:`: `case` 節がすぐに実行できない場合（このテストではチャネルに値が送信されないため、常にそうなる）、`default` 節が実行されます。これにより、`select` ステートメントはブロックしません。
*   `if i < 10 && !ok { panic("BUG") }`: `select` ステートメントの直後に、同じ条件が再度チェックされています。これは、`select` の実行後も `ok` の状態が期待通りであることを確認するための追加の検証です。
*   `if i >= 10 && ok { close(c) }`:
    *   `i >= 10`: ループが10回目以降（`i` が10または11）になったときにこのブロックが実行されます。
    *   `ok`: この条件は、チャネルを閉じる直前の `ok` の値が `true` であることを確認しています。もし `ok` が `false` であれば、チャネルは既に閉じられているか、何らかの異常が発生していることになります。
    *   `close(c)`: チャネル `c` を閉じます。チャネルが閉じられた後、それ以降の受信操作は、バッファが空になった時点でゼロ値と `ok=false` を返します。

このテストの目的は、チャネルが閉じられた後、特に `select` ステートメントに `default` ケースがある場合に、`ok` 変数が正しく `false` を返すことを保証することです。もし `ok` が `true` のままであれば、それはバグであり、`panic("BUG")` が呼び出されてテストが失敗します。

### `select` ステートメント

`select` ステートメントは、複数のチャネル操作を同時に待機し、準備ができた最初の操作を実行するために使用されます。これは、Unixの `select` システムコールに似ています。

*   `select` は、複数の `case` 文を持ち、それぞれの `case` はチャネルの送受信操作を含みます。
*   複数の `case` が同時に準備できた場合、`select` はランダムに1つを選択して実行します。
*   どの `case` も準備できていない場合、`select` はブロックします。
*   **`default` ケース**: `select` ステートメントに `default` ケースが含まれている場合、どのチャネル操作も準備できていないときに `default` ケースが即座に実行されます。これにより、`select` はブロックせずに非ブロッキングなチャネル操作を行うことができます。

### `panic`

Goにおける `panic` は、プログラムの実行を停止させるランタイムエラーの一種です。通常、回復不可能なエラーやプログラマの論理的な誤りを示すために使用されます。`panic` が発生すると、現在のGoroutineの実行が停止し、遅延関数（`defer`）が実行され、コールスタックを遡って `panic` が伝播します。`recover` 関数を使って `panic` から回復することも可能ですが、通常はプログラムを終了させるために使用されます。

## 技術的詳細

このテストケース `issue8347.go` は、バッファ付きチャネル `c` を使用し、`select` ステートメントの `default` ケースとチャネルのクローズ処理がどのように相互作用するかを検証しています。

テストの核心は、`for` ループ内で `select` ステートメントを繰り返し実行し、チャネル `c` が閉じられる前と後で `ok` 変数の値が期待通りに振る舞うことを確認することです。

1.  **チャネルの初期化**: `c := make(chan bool, 1)` で、容量1のバッファ付きブールチャネルを作成します。
2.  **ループ処理**: `for i := 0; i < 12; i++` のループが12回実行されます。
3.  **`select` ステートメント**:
    *   `case _, ok = <-c:`: チャネル `c` から値を受信しようとします。受信が成功した場合、`ok` は `true` になります。チャネルが閉じられていてバッファが空の場合、`ok` は `false` になります。
    *   `default:`: `case` が準備できていない場合、即座にこのブロックが実行されます。
4.  **`ok` の検証（チャネルクローズ前）**:
    *   `if i < 10 && !ok { panic("BUG") }`: ループの最初の10回（`i` が0から9まで）は、チャネル `c` は開いています。この期間に `ok` が `false` になることは、チャネルが閉じられたことを意味するため、バグとみなされます。`select` ステートメントに `default` ケースがあるため、チャネルに値がない場合でもブロックせず、`default` ケースが実行されます。このとき、`ok` の値は `case` 節が実行されていないため変更されません。しかし、`case` 節が実行された場合（例えば、別のGoroutineがチャネルに値を送信した場合）、`ok` は `true` になるはずです。この `if` 文は、`case` 節が実行されたにもかかわらず `ok` が `false` になるという、チャネルが閉じられていないにもかかわらず閉じられたと誤認するバグを検出することを意図しています。
5.  **チャネルのクローズ**:
    *   `if i >= 10 && ok { close(c) }`: ループの10回目（`i = 10`）で、チャネル `c` が閉じられます。この条件 `ok` は、チャネルが閉じられる直前の `ok` の状態をチェックしています。もし `ok` が `false` であれば、チャネルは既に閉じられているか、何らかの異常が発生していることになります。
6.  **`ok` の検証（チャネルクローズ後）**:
    *   `if i < 10 && !ok { panic("BUG") }` の後に、同じ条件 `if i < 10 && !ok { panic("BUG") }` が再度チェックされています。これは、`select` ステートメントの直後だけでなく、ループの各イテレーションの終わりにも `ok` の状態を再確認することで、より堅牢なテストを実現しています。
    *   チャネルが閉じられた後（`i >= 10`）、`case _, ok = <-c:` が実行されると、チャネル `c` のバッファが空であれば `ok` は `false` になることが期待されます。このテストは、この `ok` の値が正しく `false` になることを検証しています。もし `ok` が `true` のままであれば、それはバグを示します。

このテストは、`select` ステートメントが `default` ケースを持つ場合に、閉じられたチャネルからの受信が正しく `ok=false` を返すことを保証するためのものです。特に、チャネルが閉じられた後に `select` が `default` ケースにフォールバックする際に、`ok` の状態が誤って保持されるようなエッジケースを捉えることを目的としています。

## コアとなるコードの変更箇所

`test/fixedbugs/issue8347.go` が新規追加されています。

```go
// run

// Copyright 2014 The Go Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package main

func main() {
	c := make(chan bool, 1)
	ok := true
	for i := 0; i < 12; i++ {
		select {
		case _, ok = <-c:
			if i < 10 && !ok {
				panic("BUG")
			}
		default:
		}
		if i < 10 && !ok {
			panic("BUG")
		}
		if i >= 10 && ok {
			close(c)
		}
	}
}
```

## コアとなるコードの解説

このテストコードは、Goのチャネルと `select` ステートメントの特定の挙動を検証するために設計されています。

*   `// run`: このコメントは、Goのテストフレームワークに対して、このファイルが実行可能なテストであることを示します。
*   `// Copyright 2014 The Go Authors. ...`: 標準的なGoの著作権表示とライセンス情報です。
*   `package main`: このファイルが実行可能なプログラムであることを示します。
*   `func main() { ... }`: プログラムのエントリポイントです。
*   `c := make(chan bool, 1)`: 容量1のバッファ付きブールチャネル `c` を作成します。バッファ付きチャネルであるため、送信操作はバッファが満杯になるまでブロックせず、受信操作はバッファが空になるまでブロックしません。
*   `ok := true`: ブール変数 `ok` を `true` で初期化します。この変数は、チャネルからの受信操作の結果（チャネルが閉じられているかどうか）を保持するために使用されます。
*   `for i := 0; i < 12; i++ { ... }`: 12回繰り返されるループです。このループ内でチャネルの操作と検証が行われます。
*   `select { ... }`: 複数のチャネル操作を待機するための `select` ステートメントです。
    *   `case _, ok = <-c:`: この `case` は、チャネル `c` から値を受信しようとします。
        *   `_`: 受信した値は使用しないため、ブランク識別子で破棄しています。
        *   `ok = <-c`: チャネルからの受信操作の結果、`ok` 変数にチャネルが閉じられているかどうかの情報が代入されます。チャネルが閉じられていない場合は `true`、閉じられている場合は `false` となります。
        *   `if i < 10 && !ok { panic("BUG") }`: この条件は、チャネルが閉じられる前（`i` が10未満）に `ok` が `false` になるのはバグであると主張しています。`select` に `default` ケースがあるため、チャネルに値がない場合でもブロックせず、`default` ケースが実行されます。このとき、`ok` の値は `case` 節が実行されていないため変更されません。しかし、もし `case` 節が実行されたにもかかわらず `ok` が `false` になるような状況があれば、それはバグです。
    *   `default:`: `case` 節がすぐに実行できない場合（このテストではチャネルに値が送信されないため、常にそうなる）、`default` 節が実行されます。これにより、`select` ステートメントはブロックしません。
*   `if i < 10 && !ok { panic("BUG") }`: `select` ステートメントの直後に、同じ条件が再度チェックされています。これは、`select` の実行後も `ok` の状態が期待通りであることを確認するための追加の検証です。
*   `if i >= 10 && ok { close(c) }`:
    *   `i >= 10`: ループが10回目以降（`i` が10または11）になったときにこのブロックが実行されます。
    *   `ok`: この条件は、チャネルを閉じる直前の `ok` の値が `true` であることを確認しています。もし `ok` が `false` であれば、チャネルは既に閉じられているか、何らかの異常が発生していることになります。
    *   `close(c)`: チャネル `c` を閉じます。チャネルが閉じられた後、それ以降の受信操作は、バッファが空になった時点でゼロ値と `ok=false` を返します。

このテストの目的は、チャネルが閉じられた後、特に `select` ステートメントに `default` ケースがある場合に、`ok` 変数が正しく `false` を返すことを保証することです。もし `ok` が `true` のままであれば、それはバグであり、`panic("BUG")` が呼び出されてテストが失敗します。

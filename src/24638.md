# [インデックス 24638] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおけるレジスタ割り当てメカニズムを根本的に変更するものです。具体的には、従来の「基本ブロックごとのローカルなレジスタ割り当て」から、「関数全体を対象とするグローバルなレジスタ割り当て」へと移行しています。これにより、より効率的なコード生成とパフォーマンスの向上が期待されます。

## 変更の背景

Goコンパイラは、プログラムのソースコードを機械語に変換する過程で、様々な最適化を行います。その中でも、レジスタ割り当ては非常に重要なステップの一つです。レジスタはCPU内部にある高速な記憶領域であり、データへのアクセス速度を大幅に向上させます。コンパイラは、プログラム内で使用される変数を、メモリではなく可能な限りレジスタに割り当てることで、実行速度を向上させようとします。

このコミット以前のGoコンパイラのSSAバックエンドでは、レジスタ割り当てが「基本ブロック（Basic Block）」という、分岐やジャンプを含まない連続した命令の塊ごとにローカルに行われていました。このローカルなアプローチは実装が比較的容易である反面、基本ブロックをまたがる変数の寿命（live range）を考慮できないため、最適なレジスタ利用が難しいという欠点がありました。例えば、ある基本ブロックでレジスタに割り当てられた変数が、次の基本ブロックでも使用される場合、ローカルな割り当てではその変数を一度メモリに退避させ、再度レジスタにロードし直すといった無駄な処理が発生する可能性がありました。

この非効率性を解消し、生成される機械語コードの品質を向上させるために、関数全体を対象とする「グローバルなレジスタ割り当て」の導入が決定されました。グローバルなレジスタ割り当ては、関数内のすべての基本ブロックを横断して変数の寿命を分析し、より広範な視点から最適なレジスタの利用計画を立てることができます。

## 前提知識の解説

### 1. コンパイラの最適化とSSA (Static Single Assignment)

コンパイラは、ソースコードをより効率的な機械語に変換するために様々な最適化を行います。SSA形式は、コンパイラ最適化の中間表現（IR: Intermediate Representation）の一つで、各変数が一度だけ代入されるという特性を持ちます。これにより、データの流れが明確になり、デッドコード削除、共通部分式除去、レジスタ割り当てなどの最適化が容易になります。GoコンパイラのバックエンドもSSA形式を採用しています。

### 2. レジスタ割り当て (Register Allocation)

レジスタ割り当ては、コンパイラの最も重要な最適化の一つです。プログラムの実行中に頻繁にアクセスされる変数を、CPUの高速なレジスタに割り当てることで、メモリへのアクセス回数を減らし、プログラムの実行速度を向上させます。レジスタの数は限られているため、どの変数をどのレジスタに、いつまで割り当てるかを決定することは複雑な問題です。

*   **ローカルレジスタ割り当て (Local Register Allocation)**:
    *   個々の基本ブロック（Basic Block）内でのみレジスタ割り当てを行います。
    *   実装が比較的簡単ですが、基本ブロック間の変数の受け渡しでレジスタの再利用が難しく、メモリへの退避（spill）や再ロード（reload）が頻繁に発生する可能性があります。
    *   コードの品質はグローバル割り当てに劣ります。

*   **グローバルレジスタ割り当て (Global Register Allocation)**:
    *   関数全体を対象としてレジスタ割り当てを行います。
    *   変数の「寿命」（live range、変数が定義されてから最後に使用されるまでの期間）を分析し、複数の基本ブロックをまたがってレジスタを効率的に利用します。
    *   通常、グラフ彩色アルゴリズム（Graph Coloring Algorithm）などの複雑なアルゴリズムが用いられます。変数の寿命をノード、寿命が重なる変数をエッジとする干渉グラフ（interference graph）を構築し、グラフの彩色問題としてレジスタ割り当てを解決します。
    *   より高品質なコードを生成し、実行速度を向上させますが、実装は複雑です。

### 3. レジスタのクロバリング (Register Clobbering)

一部のCPU命令（特にシステムコールや特定の算術命令、関数呼び出しなど）は、明示的に指定されていないレジスタの内容を暗黙的に変更（破壊）することがあります。これを「レジスタのクロバリング」と呼びます。コンパイラは、このようなクロバリングを正確に把握し、破壊される可能性のあるレジスタに重要な値が格納されていないことを保証するか、事前にメモリに退避させる必要があります。このコミットでは、命令によるレジスタのクロバリングが適切に処理されるようになったと述べられています。

    *   従来のローカルな割り当てでは、基本ブロックの境界でレジスタの内容をメモリに退避させる必要がありましたが、グローバル割り当てでは、変数の寿命が続く限り同じレジスタを使い続けることが可能になり、無駄なロード/ストア命令が削減されます。

2.  **レジスタクロバリングの適切なハンドリング**:

    *   `src/cmd/compile/internal/ssa/gen/AMD64Ops.go` や `src/cmd/compile/internal/ssa/opGen.go` の変更を見ると、各オペレーション（命令）がどのレジスタをクロバリングするかを示す `clobbers` フィールドが `regInfo` 構造体に追加され、多くの命令定義に `flags` レジスタのクロバリング情報が追加されています。また、`CALLstatic` や `CALLclosure` のような関数呼び出し命令には、`callerSave` レジスタ（呼び出し元が保存すべきレジスタ）がクロバリングされるという情報が追加されています。これにより、コンパイラはクロバリングされるレジスタに重要な値がある場合、事前にメモリに退避させるなどの適切な処理を行うことができます。

3.  **入力レジスタの割り当て順序の最適化**:
    *   `src/cmd/compile/internal/ssa/gen/main.go` の変更では、`genOp` 関数内で命令の入力レジスタを割り当てる際に、制約の多い（使用可能なレジスタが少ない）入力から順に割り当てるロジックが追加されています。これは、`inputInfo` 構造体と `byKey` ソートインターフェースの導入によって実現されており、より効率的なレジスタ割り当てを可能にします。

4.  **デッドコード削除の制約**:
    *   `src/cmd/compile/internal/ssa/deadcode.go` には、レジスタ割り当て後にデッドコード削除を実行することを禁止するチェックが追加されています。これは、レジスタ割り当てがまだ完全に合法なSSA形式を生成していないため、デッドコード削除によって必要なムーブ命令が削除されてしまう可能性があるためです。このコメントは、レジスタ割り当ての導入がまだ初期段階であり、今後の改善の余地があることを示唆しています。

5.  **テストケースの追加**:
    *   `src/cmd/compile/internal/gc/testdata/regalloc_ssa.go` という新しいテストファイルが追加され、`phiOverwrite_ssa` や `phiOverwriteBig_ssa` といった関数が導入されています。これらは、SSA形式におけるPhi関数（複数の制御フローパスから来る値をマージする）のレジスタ割り当てが正しく機能するかを検証するためのものです。特に `phiOverwriteBig_ssa` は多数の変数を扱うことで、レジスタ割り当ての複雑なシナリオをテストしています。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/op.go` の変更

```go
type regInfo struct {
	inputs   []inputInfo // ordered in register allocation order
	clobbers regMask
	outputs  []regMask // NOTE: values can only have 1 output for now.
}

type inputInfo struct {
	idx  int     // index in Args array
	regs regMask // allowed input registers
}
```
`regInfo` 構造体に `clobbers` フィールドが追加され、命令が破壊するレジスタのマスクを保持するようになりました。また、`inputs` フィールドの型が `[]regMask` から `[]inputInfo` に変更されています。`inputInfo` は、入力引数の元のインデックス (`idx`) と、その引数に割り当て可能なレジスタのマスク (`regs`) を保持します。これにより、レジスタ割り当て時に、どの入力がどのレジスタを要求し、どのレジスタが破壊されるかを正確に追跡できるようになります。`inputs` が「レジスタ割り当て順に並べられる」というコメントも重要で、これは `gen/main.go` で実装されたソートロジックと関連しています。

### `src/cmd/compile/internal/ssa/gen/AMD64Ops.go` の変更

```go
	var (
		// ...
		flags      = buildReg("FLAGS")
		callerSave = gp | fp | flags // 呼び出し元が保存すべきレジスタの集合
	)

	// ...

	{name: "CALLstatic", reg: regInfo{clobbers: callerSave}}, // 関数呼び出しはcallerSaveレジスタを破壊する
	{name: "CALLclosure", reg: regInfo{[]regMask{gpsp, buildReg("DX"), 0}, callerSave, nil}}, // 同上
```
`callerSave` という新しいレジスタマスクが定義され、汎用レジスタ (`gp`)、浮動小数点レジスタ (`fp`)、およびフラグレジスタ (`flags`) の組み合わせとしています。これは、関数呼び出し規約において、呼び出された関数がこれらのレジスタを自由に使用できる（呼び出し元は必要であれば事前に保存する必要がある）ことを示しています。`CALLstatic` や `CALLclosure` といった関数呼び出し命令の `regInfo` に `clobbers: callerSave` が設定されたことで、コンパイラは関数呼び出しの前後でこれらのレジスタの内容が変更される可能性があることを認識し、適切なコード（例えば、重要な値がこれらのレジスタにある場合はメモリに退避させる命令）を生成できるようになります。

### `src/cmd/compile/internal/ssa/gen/main.go` の変更

```go
			// Compute input allocation order.  We allocate from the
			// most to the least constrained input.  This order guarantees
			// that we will always be able to find a register.
			var s []intPair
			for i, r := range v.reg.inputs { // v.reg.inputsはまだregMaskのスライス
				if r != 0 {
					s = append(s, intPair{countRegs(r), i})
				}
			}
			if len(s) > 0 {
				sort.Sort(byKey(s)) // 制約の多い順にソート
				fmt.Fprintln(w, "inputs: []inputInfo{")
				for _, p := range s {
					r := v.reg.inputs[p.val] // ソートされた順序で元のregMaskを取得
					fmt.Fprintf(w, "{%d,%d},%s\\n", p.val, r, a.regMaskComment(r))
				}
				fmt.Fprintln(w, "},\")
			}
```
このコードは、命令の入力レジスタを割り当てる際の順序を決定しています。`countRegs` 関数で各入力レジスタマスクに含まれるレジスタの数を数え、その数が少ない（つまり制約が多い）入力から順に割り当てるようにソートしています。これは、レジスタ割り当てのヒューリスティックとして知られており、制約の多い入力を先に処理することで、後続の割り当てが失敗する可能性を減らし、より良い割り当て結果を得やすくします。`inputInfo` 構造体は、このソートされた順序と元の引数インデックスを保持するために使用されます。

### `src/cmd/compile/internal/ssa/deadcode.go` の変更

```go
func deadcode(f *Func) {
	// deadcode after regalloc is forbidden for now.  Regalloc
	// doesn't quite generate legal SSA which will lead to some
	// required moves being eliminated.  See the comment at the
	// top of regalloc.go for details.
	if f.RegAlloc != nil {
		f.Fatalf("deadcode after regalloc")
	}
	// ...
}
```
このコードは、レジスタ割り当て (`f.RegAlloc != nil`) が行われた後にデッドコード削除を実行しようとすると、コンパイラがパニックを起こして終了するようにしています。これは、新しいグローバルレジスタ割り当てがまだSSAの厳密なルールを完全に満たしていないため、デッドコード削除が誤って必要な `move` 命令を削除してしまう可能性があるという一時的な制約です。このコメントは、この機能がまだ開発中であり、将来的に改善されるべき点があることを示しています。

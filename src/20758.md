# [インデックス 20758] ファイルの概要

このコミットは、Goランタイムにおいて、ガベージコレクション (GC) アリーナ内の無効なポインタを検出した場合にクラッシュするメカニズムを導入します。これは、リリースフリーズ期間中に潜在的なバグを発見しやすくすることを目的としています。

runtime: crash if we see an invalid pointer into GC arena
    
This will help find bugs during the release freeze.
It's not clear it should be kept for the release itself.
That's issue 8861.

The most likely thing that would trigger this is stale
pointers that previously were ignored or caused memory
leaks. These were allowed due to the use of conservative

The small number check reinforces what the stack copier

which is to say if the binary is using SWIG to allocate untyped
Go memory. In that case, there are invalid pointers and there's

## 変更の背景

このコミットの主な背景には、Goランタイムのガベージコレクション (GC) の進化があります。以前のGoのGCは「保守的 (conservative)」な部分があり、メモリ内の値がポインタであるかどうかを厳密に判断せず、ポインタのように見える値もポインタとして扱うことがありました。これにより、実際にはポインタではない値がGCによって追跡され、メモリリークを引き起こしたり、無効なメモリ領域を指す「古いポインタ (stale pointers)」が無視されたりする可能性がありました。

しかし、このコミットが作成された時点では、GoのGCはより「正確 (precise)」なものへと移行していました。正確なGCでは、どの値が実際にポインタであるかをランタイムが正確に識別できるため、古いポインタや無効なポインタが存在することは、ランタイムのバグを示す深刻な問題となります。

この変更は、特にリリースフリーズ期間中に、このような新しい種類のバグを早期に発見し、修正することを目的としています。無効なポインタを検出した場合に即座にクラッシュさせることで、問題の根本原因を特定しやすくし、より堅牢なランタイムを構築するためのデバッグを促進します。

また、CGO（GoとC言語の相互運用機能）を使用している場合に、`_cgo_allocate`がバイナリにリンクされていると、SWIGなどを介して型付けされていないGoメモリが割り当てられることがあり、この場合には無効なポインタが存在しうるため、このチェックを無効にする例外処理も導入されています。これは、CGOの特定のユースケースにおける現実的な制約に対応するためのものです。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

*   **ガベージコレクション (GC)**: プログラムが動的に確保したメモリ領域のうち、もはや使用されなくなったものを自動的に解放する仕組みです。GoのGCは、メモリリークを防ぎ、開発者が手動でメモリ管理を行う負担を軽減します。
    *   **保守的GC (Conservative GC)**: メモリ内の値がポインタであるかどうかを厳密に判断せず、ポインタのように見える値（例えば、ヒープ内の有効なオブジェクトを指す可能性のある整数値）もポインタとして扱うGCです。これにより、誤ってポインタでないものをポインタとして扱い、メモリを解放しない（リークする）可能性がありますが、実装は比較的容易です。
    *   **正確なGC (Precise GC)**: メモリ内のどの値が実際にポインタであるかを正確に識別し、それらのみを追跡するGCです。これにより、メモリリークのリスクが低減し、より効率的なメモリ管理が可能になりますが、ランタイムが型情報を正確に把握している必要があります。Goは、このコミットの時期には正確なGCへと移行していました。
*   **GCアリーナ (GC Arena)**: Goランタイムがヒープメモリを管理するために使用する、連続したメモリ領域の集合です。GCは、このアリーナ内のオブジェクトをスキャンし、到達可能なオブジェクトをマークします。
*   **ポインタ (Pointer)**: メモリ上の特定のアドレスを指し示す変数です。Goでは、ポインタは型安全ですが、`unsafe.Pointer`を使用すると型安全性をバイパスできます。
*   **CGO**: GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのメカニズムです。CGOを使用すると、Goの型システムが認識しない方法でメモリが割り当てられたり、ポインタが扱われたりする可能性があります。特に、SWIGのようなツールは、CGOを介してGoのメモリを型付けされていない形で操作することがあります。
*   **スタックコピア (Stack Copier)**: Goのランタイムは、ゴルーチンのスタックを必要に応じて拡大・縮小するために、スタックの内容を新しいメモリ領域にコピーすることがあります。この際、スタック上の値がポインタなのか、それとも単なる整数値なのかを正確に区別する必要があります。誤って整数値をポインタとして解釈すると、無効なメモリ参照を引き起こす可能性があります。
*   **`mspan`**: Goのメモリ管理において、ヒープメモリは`mspan`と呼ばれる連続したページ（通常は8KB）のチャンクに分割されます。各`mspan`は、特定のサイズのオブジェクトを格納するために使用されたり、スタックとして使用されたりします。`mspan`には`state`（状態）があり、`MSpanInUse`はヒープオブジェクトが割り当てられていることを示し、`MSpanStack`はスタックとして使用されていることを示します。

## 技術的詳細

このコミットは、Goランタイムのガベージコレクタがヒープをスキャンする際に、無効なポインタを検出するための新しいチェックを導入します。主な変更は`src/runtime/mgc0.c`ファイルに集中しています。

1.  **無効なポインタの検出ロジック**:
    *   `scanblock`関数内で、GCがポインタをスキャンする際に、そのポインタがGCアリーナ（ヒープ）の有効な範囲内を指しているか、そしてそれが有効な`mspan`（メモリブロック）内にあるかを検証します。
    *   具体的には、ポインタ`obj`が`arena_start`と`arena_used`の範囲内にあるかを確認します。
    *   さらに、`obj`が指すアドレスに対応する`mspan`が存在し、その`mspan`が`MSpanInUse`状態であるかを確認します。`MSpanStack`状態の`mspan`を指すポインタは、スタックポインタであるため無視されます。
    *   ポインタが`PhysPageSize`（通常4KB）よりも小さいアドレスを指している場合も無効と判断されます。これは、NULLポインタや非常に小さい不正なアドレスを検出するためです。

2.  **エラー報告とクラッシュ**:
    *   無効なポインタが検出された場合、`runtime·printf`を使用して詳細なエラーメッセージを出力し、`runtime·throw`を呼び出してランタイムをクラッシュさせます。これにより、デバッガがアタッチされている場合に、問題発生箇所でプログラムの実行を停止させ、原因を調査しやすくします。
    *   エラーメッセージには、無効なポインタが見つかった元の場所（`b+i`）、無効なポインタの値（`obj`）、および関連する`mspan`の情報（`start`, `limit`, `state`）が含まれます。

3.  **`_cgo_allocate`の例外処理**:
    *   `have_cgo_allocate()`という新しい関数が導入され、バイナリに`_cgo_allocate_internal`シンボルがリンクされているかどうかをチェックします。このシンボルは、CGOがGoのメモリを型付けされていない形で割り当てる場合（例: SWIGを使用する場合）に存在します。
    *   `_cgo_allocate`がリンクされている場合、GCは`[]unsafe.Pointer`として割り当てられたメモリを保守的にスキャンする必要があるため、無効なポインタのチェックは無効化されます。これは、CGOがGoの型システムをバイパスしてメモリを操作するため、ランタイムがそのメモリの内容を正確に把握できないという現実的な制約に対応するためです。

4.  **`badblock`配列とGCの再実行**:
    *   `badblock`という静的配列と`nbadblock`カウンタが導入されました。これは、無効なポインタが検出された際に、そのポインタがどこから来たのか（ルートからのパス）を追跡するためのデバッグメカニズムです。
    *   `runtime·gc_m`関数（GCのメインエントリポイント）内で、`nbadblock > 0`の場合、GCを繰り返し実行します。これは、無効なポインタが見つかった場合に、そのポインタを指している別のポインタを特定し、最終的にルート（スタックやグローバル変数など）まで遡って、無効なポインタがどのようにして生成されたかを特定するのに役立ちます。

5.  **デバッグフラグ `DebugPtrs`**:
    *   `DebugPtrs`というコンパイル時フラグが追加されました。これを1に設定すると、GCがポインタをスキャンする際に、すべてのポインタロードのトレースが出力されるようになります。これは、デバッグ時にポインタの挙動を詳細に追跡するのに非常に有用です。

このコミットは、GoのGCが保守的GCから正確なGCへと移行する過程で、ランタイムの堅牢性を高め、メモリ関連のバグを早期に発見するための重要なステップです。

## コアとなるコードの変更箇所

主な変更は `src/runtime/mgc0.c` にあります。

1.  **`have_cgo_allocate` 関数の追加**:
    ```c
    // Is _cgo_allocate linked into the binary?
    static bool
    have_cgo_allocate(void)
    {
    	extern	byte	go·weak·runtime·_cgo_allocate_internal[1];
    	return go·weak·runtime·_cgo_allocate_internal != nil;
    }
    ```

2.  **`scanblock` 関数内のポインタ検証ロジックの追加と変更**:
    `markobj` ラベルの直後から `badobj` ラベルにかけてのブロックが大幅に変更・追加されています。
    ```c
    		markobj:
    			// At this point we have extracted the next potential pointer.
    			// Check if it points into heap.
    			if(obj == nil)
    				continue;
    			if((uintptr)obj < PhysPageSize) {
    				s = nil;
    				goto badobj;
    			}
    			if(obj < arena_start || obj >= arena_used)
    				continue;
    			// Mark the object.
    			obj = (byte*)((uintptr)obj & ~(PtrSize-1));
    			off = (uintptr*)obj - (uintptr*)arena_start;
    			bitp = arena_start - off/wordsPerBitmapByte - 1;
    			shift = (off % wordsPerBitmapByte) * gcBits;
    			bits = (*bitp >> shift) & ((1<<gcBits)-1);
    			if(bits == BitsDead) {
    				// obj is not a live object.
    				// Check if it is a stack pointer.
    				k = (uintptr)obj >> PageShift;
    				x = k;
    				x -= (uintptr)arena_start>>PageShift;
    				s = runtime·mheap.spans[x];
    				if(s == nil || k < s->start || obj >= s->limit || s->state != MSpanInUse) {
    					// Stack pointers lie within the arena bounds but are not part of the GC heap.
    					// Ignore them.
    					if(s != nil && s->state == MSpanStack)
    						continue;
    				
    				badobj:
    					// If cgo_allocate is linked into the binary, it can allocate
    					// memory as []unsafe.Pointer that may not contain actual
    					// pointers and must be scanned conservatively.
    					// In this case alone, allow the bad pointer.
    					if(have_cgo_allocate() && ptrmask == nil)
    						continue;

    					// Anything else indicates a bug somewhere.
    					// If we're in the middle of chasing down a different bad pointer,
    					// don't confuse the trace by printing about this one.
    					if(nbadblock > 0)
    						continue;

    					runtime·printf("runtime: garbage collector found invalid heap pointer *(%p+%p)=%p", b, i, obj);
    					if(s == nil)
    						runtime·printf(" s=nil\\n");
    					else
    						runtime·printf(" span=%p-%p-%p state=%d\\n", (uintptr)s->start<<PageShift, s->limit, (uintptr)(s->start+s->npages)<<PageShift, s->state);
    					if(ptrmask != nil)
    						runtime·throw("bad pointer");
    					// Add to badblock list, which will cause the garbage collection
    					// to keep repeating until it has traced the chain of pointers
    					// leading to obj all the way back to a root.
    					if(nbadblock == 0)
    						badblock[nbadblock++] = (uintptr)b;
    					continue;
    				}
    				p = (byte*)((uintptr)s->start<<PageShift);
    				if(s->sizeclass != 0) {
    					size = s->elemsize;
    					off = (uintptr)(obj - p);
    					obj = p + off - off%size;
    				} else {
    					// Large object.
    					obj = p;
    				}
    				goto markobj;
    			}
    ```

3.  **`runtime·gc_m` 関数内の `badblock` 処理**:
    ```c
    	if(nbadblock > 0) {
    		// Work out path from root to bad block.
    		for(;;) {
    			gc(&a);
    			if(nbadblock >= nelem(badblock))
    				runtime·throw("cannot find path to bad pointer");
    		}
    	}
    ```

## コアとなるコードの解説

### `have_cgo_allocate` 関数

この関数は、GoバイナリがCGOを介してメモリを割り当てるための内部関数である`_cgo_allocate_internal`にリンクされているかどうかをチェックします。`extern byte go·weak·runtime·_cgo_allocate_internal[1];`は、このシンボルが外部で定義されていることを宣言しています。`go·weak·`プレフィックスは、これが弱いシンボルであることを示唆しており、リンクされていない場合でもエラーにならないことを意味します。この関数が`true`を返す場合、CGOが使用されており、特定のメモリ領域が無効なポインタを含む可能性があるため、厳密なポインタチェックをスキップするべきだと判断されます。

### `scanblock` 関数内のポインタ検証ロジック

`scanblock`関数は、GCがメモリブロックをスキャンしてポインタを見つける主要な場所です。

*   **`markobj` ラベル**: ここに到達すると、`obj`はGCがスキャン対象として見つけた潜在的なポインタです。
*   **`if(obj == nil) continue;`**: NULLポインタは有効なヒープオブジェクトを指さないため、スキップします。
*   **`if((uintptr)obj < PhysPageSize) { s = nil; goto badobj; }`**: ポインタが物理ページサイズ（通常4KB）よりも小さいアドレスを指している場合、それは通常、無効なポインタ（例えば、NULLに近いアドレス）であるため、`badobj`処理にジャンプします。
*   **`if(obj < arena_start || obj >= arena_used) continue;`**: ポインタがGCアリーナの有効な範囲外を指している場合、それはヒープオブジェクトではないため、スキップします。
*   **`obj = (byte*)((uintptr)obj & ~(PtrSize-1));`**: ポインタを`PtrSize`（ポインタのサイズ、通常は4バイトまたは8バイト）の倍数にアラインします。これは、オブジェクトの先頭を正確に指すようにするためです。
*   **`if(bits == BitsDead)`**: GCビットマップで`obj`が指すオブジェクトが「死んでいる」（到達不可能）とマークされている場合、さらに詳細なチェックを行います。
*   **`if(s == nil || k < s->start || obj >= s->limit || s->state != MSpanInUse)`**: `obj`が指すアドレスに対応する`mspan`が存在しない、または`mspan`の範囲外を指している、または`mspan`が`MSpanInUse`状態ではない場合、無効なポインタの可能性があります。
    *   **`if(s != nil && s->state == MSpanStack) continue;`**: ただし、`mspan`が`MSpanStack`状態である場合、それはスタックポインタであるため、ヒープオブジェクトではないので無視します。スタックポインタはGCヒープの一部ではありませんが、アリーナの範囲内に存在することがあります。
*   **`badobj` ラベル**: ここに到達した場合、無効なポインタが検出されたことを意味します。
    *   **`if(have_cgo_allocate() && ptrmask == nil) continue;`**: `_cgo_allocate`がリンクされており、かつ`ptrmask`がNULL（GCビットマップを使用している場合）であれば、この無効なポインタは許容されるため、スキップします。これは、CGOが型付けされていないメモリを割り当てる場合に発生する可能性があります。
    *   **`if(nbadblock > 0) continue;`**: 既に別の無効なポインタを追跡中の場合、現在のトレースを混乱させないために、この無効なポインタに関するエラーメッセージの出力はスキップします。
    *   **`runtime·printf(...)`**: 無効なポインタの詳細な情報を出力します。
    *   **`if(ptrmask != nil) runtime·throw("bad pointer");`**: `ptrmask`がNULLでない場合（つまり、GCビットマップではなく、明示的なポインタマスクが与えられている場合）、これはより深刻なエラーであるため、即座に`runtime·throw`でクラッシュさせます。
    *   **`if(nbadblock == 0) badblock[nbadblock++] = (uintptr)b;`**: `badblock`配列に、無効なポインタが見つかった元のメモリブロックのアドレスを記録します。これは、後でルートからのパスを追跡するために使用されます。

### `runtime·gc_m` 関数内の `badblock` 処理

`runtime·gc_m`は、GCの実行を調整する高レベルの関数です。

*   **`if(nbadblock > 0)`**: GCの実行後、`badblock`配列に無効なポインタが記録されている場合、つまり無効なポインタが検出された場合、このブロックに入ります。
*   **`for(;;) { gc(&a); ... }`**: 無限ループに入り、GCを繰り返し実行します。これは、`badblock`配列に記録された無効なポインタへのルートを特定するためのデバッグメカニズムです。GCが再実行されるたびに、`scanblock`内の`badblock`追跡ロジックが、無効なポインタを指している可能性のある新しいポインタを特定しようとします。
*   **`if(nbadblock >= nelem(badblock)) runtime·throw("cannot find path to bad pointer");`**: `badblock`配列が満杯になってもルートが見つからない場合、パスを特定できないと判断し、クラッシュさせます。

これらの変更により、Goランタイムはメモリの整合性をより厳密にチェックし、潜在的なメモリ破損やバグを早期に発見できるようになります。

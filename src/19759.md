## 変更の背景

このコミットの主な目的は、Goランタイムにおける`select`ステートメントのベンチマークの質を向上させることです。既存のベンチマークでは、特定のシナリオ、特に同期チャネル（バッファなしチャネル）における`select`のパフォーマンス特性が十分に捉えられていませんでした。また、`BenchmarkSelectNonblock`では、`GOMAXPROCS`が1より大きい場合に、より現実的で興味深い競合条件をシミュレートするために、チャネルを共有するように変更する必要がありました。

Goの`select`ステートメントは、複数のチャネル操作を同時に待機し、準備ができた最初の操作を実行するための強力なプリミティブです。そのパフォーマンスは、並行プログラムの効率に直接影響します。そのため、ランタイム開発者は、`select`のボトルネックを特定し、最適化するために、堅牢で代表的なベンチマークを必要としていました。このコミットは、そのベンチマークスイートの網羅性と精度を高めることを目指しています。

## 前提知識の解説

### Goのチャネル (Channels)
Goのチャネルは、ゴルーチン間で値を送受信するための通信メカニズムです。チャネルには以下の2種類があります。
*   **同期チャネル (Synchronous Channels / Unbuffered Channels)**: `make(chan int)`のようにバッファサイズを指定せずに作成されます。送信操作は受信操作が完了するまでブロックし、受信操作は送信操作が完了するまでブロックします。これにより、ゴルーチン間の同期が保証されます。
*   **非同期チャネル (Asynchronous Channels / Buffered Channels)**: `make(chan int, N)`のようにバッファサイズ`N`を指定して作成されます。バッファが満杯でない限り、送信操作はブロックせず、バッファが空でない限り、受信操作はブロックしません。

### `select`ステートメント
`select`ステートメントは、複数のチャネル操作（送信または受信）を同時に待機するために使用されます。`select`は、準備ができた最初のチャネル操作を実行します。複数の操作が準備できている場合、`select`はランダムに1つを選択します。`default`ケースを持つこともでき、その場合、どのチャネル操作も準備できていないときに`default`ケースが実行され、`select`はブロックしません。

### Goのベンチマーク
Goには、標準ライブラリにベンチマークテストを記述するための`testing`パッケージが用意されています。
*   **`testing.B`**: ベンチマーク関数に渡される型で、ベンチマークの実行回数や時間などを制御するためのメソッドを提供します。
*   **`b.N`**: ベンチマーク関数が実行されるループの回数を示します。
*   **`b.RunParallel(func(pb *testing.PB))`**: 並列ベンチマークを実行するためのメソッドです。複数のゴルーチンが同時にベンチマークコードを実行し、並行処理のパフォーマンスを測定できます。`pb.Next()`が`true`を返す間、ベンチマークコードを繰り返し実行します。
*   **`GOMAXPROCS`**: Goランタイムが同時に実行できるOSスレッドの最大数を制御する環境変数です。`GOMAXPROCS=1`の場合、Goランタイムは1つのOSスレッドしか使用しないため、真の並行性は発生せず、並行処理はゴルーチンのスケジューリングによってシミュレートされます。`GOMAXPROCS > 1`の場合、複数のOSスレッドが使用され、真の並行処理が測定されます。

### 競合 (Contention)
並行プログラミングにおいて、複数のゴルーチンが同時に同じリソース（この場合はチャネル）にアクセスしようとするときに発生する状況を指します。競合が高いほど、同期メカニズム（チャネル、ミューテックスなど）のオーバーヘッドが顕著になり、パフォーマンスに影響を与える可能性があります。

## 技術的詳細

このコミットは、`src/pkg/runtime/chan_test.go`内の既存のベンチマークを改善し、新しいベンチマークを追加することで、`select`ステートメントのパフォーマンス測定をより包括的にしています。

1.  **`BenchmarkSelectSyncContended`の追加**:
    *   これは、バッファなし（同期）チャネルに対する`select`操作の競合を測定するために新しく追加されたベンチマークです。
    *   `myc1`, `myc2`, `myc3`という3つの同期チャネルを使用します。
    *   `b.RunParallel`内で、1つのゴルーチンがこれらのチャネルにデータを送信し続け、ベンチマークを実行するゴルーチンが`select`を使ってこれらのチャネルからデータを受信します。
    *   同期チャネルは、送信と受信が同時に行われるまでブロックするため、高い競合条件下での`select`の動作を正確に評価できます。

2.  **`BenchmarkSelectNonblock`のチャネル共有化**:
    *   以前の`BenchmarkSelectNonblock`では、`b.RunParallel`内の各ゴルーチンが独自のチャネルセット（`myc1`, `myc2`, `myc3`, `myc4`）を作成していました。これは、`GOMAXPROCS > 1`の場合でも、各ゴルーチンが独立して動作するため、真の競合を測定できませんでした。
    *   この変更により、`myc1`, `myc2`, `myc3`, `myc4`チャネルが`b.RunParallel`の外で作成され、すべての並列実行ゴルーチンで共有されるようになりました。
    *   これにより、`GOMAXPROCS > 1`の環境でベンチマークを実行すると、複数のゴルーチンが同じチャネルに対して`select`操作を試みるため、より現実的な競合シナリオがシミュレートされ、`select`の並行パフォーマンスがより正確に測定できるようになります。`GOMAXPROCS=1`の場合は、以前と同様に動作します。

3.  **`BenchmarkSelectContended`のリネーム**:
    *   既存の`BenchmarkSelectContended`は、バッファ付きチャネルを使用していたため、その実態をより正確に反映するために`BenchmarkSelectAsyncContended`にリネームされました。これにより、同期チャネルのベンチマークと非同期チャネルのベンチマークが明確に区別されます。

これらの変更により、Goランタイムの`select`ベンチマークスイートは、同期チャネルと非同期チャネルの両方における競合条件下のパフォーマンスをより詳細に分析できるようになり、ランタイムの最適化に役立つ貴重なデータを提供します。

## コアとなるコードの解説

### `BenchmarkSelectSyncContended`の追加

```go
+func BenchmarkSelectSyncContended(b *testing.B) {
+	myc1 := make(chan int)
+	myc2 := make(chan int)
+	myc3 := make(chan int)
+	done := make(chan int)
+	b.RunParallel(func(pb *testing.PB) {
+		go func() {
+			for {
+				select {
+				case myc1 <- 0:
+				case myc2 <- 0:
+				case myc3 <- 0:
+				case <-done:
+					return
+				}
+			}
+		}()
+		for pb.Next() {
+			select {
+			case <-myc1:
+			case <-myc2:
+			case <-myc3:
+			}
+		}
+	})
+	close(done)
+}
```
この新しいベンチマーク関数は、同期チャネル（バッファなしチャネル）における`select`の競合パフォーマンスを測定します。
*   `myc1`, `myc2`, `myc3`は、すべてバッファサイズ0のチャネルとして作成されます。
*   `b.RunParallel`内で、匿名ゴルーチンがこれらのチャネルにデータを送信し続けます。同期チャネルであるため、送信は対応する受信が完了するまでブロックします。
*   `pb.Next()`ループ内で、ベンチマークを実行するゴルーチンが`select`を使ってこれらのチャネルからデータを受信します。
*   これにより、送信側と受信側のゴルーチンが同期チャネルを介して頻繁に同期を試みるため、高い競合状態が生まれ、`select`が同期チャネルを処理する際のオーバーヘッドが正確に測定されます。
*   `done`チャネルは、送信側ゴルーチンがベンチマーク終了時に適切に終了できるようにするためのものです。

### `BenchmarkSelectContended`から`BenchmarkSelectAsyncContended`へのリネーム

```diff

+func BenchmarkSelectAsyncContended(b *testing.B) {
```
これは単なる関数名のリネームです。元の`BenchmarkSelectContended`はバッファ付きチャネルを使用していたため、その性質をより明確にするために`BenchmarkSelectAsyncContended`という名前に変更されました。これにより、同期チャネルのベンチマーク（`BenchmarkSelectSyncContended`）と区別がつきやすくなります。

この変更は、`BenchmarkSelectNonblock`のベンチマークの精度を大幅に向上させます。
*   変更前は、`b.RunParallel`のクロージャ内で`myc1`, `myc2`, `myc3`, `myc4`チャネルが作成されていました。これは、並列実行される各ゴルーチンが**それぞれ独自のチャネルセット**を持っていたことを意味します。
*   そのため、`GOMAXPROCS > 1`であっても、各ゴルーチンは他のゴルーチンとチャネルを共有せず、真の競合は発生しませんでした。これは、`select`の非ブロック動作をテストする上では問題ありませんでしたが、複数のゴルーチンが同じチャネルにアクセスするシナリオでのパフォーマンスを測定するには不十分でした。
*   変更後は、これらのチャネルが`b.RunParallel`の**外側**で作成され、すべての並列実行ゴルーチンで**共有**されるようになりました。
*   これにより、複数のゴルーチンが同時に同じチャネルに対して`select`操作を試みるため、`GOMAXPROCS > 1`の環境では、より現実的な競合状態がシミュレートされます。これは、`select`が非ブロックモードで複数のチャネルをポーリングする際の並行パフォーマンスを評価するために重要です。

これらの変更は、Goランタイムの`select`実装のパフォーマンス特性をより深く理解し、将来的な最適化のための基盤を築く上で不可欠です。

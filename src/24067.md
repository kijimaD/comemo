# [インデックス 24067] ファイルの概要

このコミットは、Go言語の `mime/multipart` パッケージにおけるバグを修正するものです。具体的には、マルチパートボディのコンテンツ内に、実際の境界文字列のプレフィックス（接頭辞）が含まれている場合に、パーサーがそれを誤って境界として認識してしまう問題を解決します。これにより、不正なデータ解析やデータの欠落を防ぎ、マルチパートメッセージの堅牢な処理を保証します。

## 変更の背景

`mime/multipart` パッケージは、HTTPリクエストやメールなどで使用されるマルチパートメッセージを解析するためのGo言語の標準ライブラリです。マルチパートメッセージは、複数の異なるデータ部分（パート）を一つのメッセージに結合するために使用され、各パートは特定の「境界文字列（boundary string）」によって区切られます。

このコミットが修正する問題は、Issue #10616として報告されたもので、マルチパートボディのデータ自体が、本来の境界文字列のプレフィックス（例えば、境界が `--boundary` であるときに、ボディ内に `--bound` という文字列が含まれる場合）を含んでいると、`mime/multipart` パーサーがこれを誤って境界の開始と認識してしまう可能性がありました。

このような誤認識が発生すると、パーサーは現在のパートがそこで終了したと判断し、本来のデータの一部を切り捨てたり、後続のパートを正しく解析できなかったりするバグを引き起こします。特に、ネストされたマルチパートメッセージ（マルチパートのパートの中にさらにマルチパートメッセージが含まれる場合）で、内部の境界が外部の境界のプレフィックスになっているような複雑なシナリオで問題が顕在化しました。この修正は、このようなエッジケースにおいても `mime/multipart` パーサーが正確に動作することを保証するために導入されました。

## 前提知識の解説

### MIME (Multipurpose Internet Mail Extensions)

MIMEは、電子メールがASCIIテキスト以外のコンテンツ（画像、音声、動画、アプリケーションデータなど）を扱えるようにするために開発された標準です。HTTPプロトコルでも広く利用されており、Webサーバーとクライアント間で様々な種類のデータを交換する際に、データの種類（Content-Type）やエンコーディング方法などを指定するために使われます。

### マルチパートメッセージ

MIMEの重要な機能の一つに、複数の異なるデータタイプを一つのメッセージに結合する「マルチパートメッセージ」があります。これは、例えばメールでテキストと添付ファイルを同時に送る場合や、HTTPでフォームデータとファイルを同時にアップロードする際（`multipart/form-data`）などに利用されます。

マルチパートメッセージは、`Content-Type` ヘッダーで `multipart/mixed` や `multipart/form-data` などのメディアタイプを指定し、さらに `boundary` パラメータで各パートを区切るための文字列（境界文字列）を定義します。

### 境界文字列 (Boundary String)

マルチパートメッセージにおいて、各パートの開始と終了を示すために使用される特殊な文字列です。境界文字列は、メッセージボディ内で一意である必要があり、通常はランダムな文字列が生成されます。

境界文字列のフォーマットには以下のルールがあります：
- 各パートの開始を示す境界は、`--` の後に境界文字列が続き、その後に改行（`CRLF`）が続きます。例: `--myboundary\r\n`
- メッセージ全体の終了を示す境界は、`--` の後に境界文字列が続き、さらに `--` が続き、その後に改行（`CRLF`）が続きます。例: `--myboundary--\r\n`
- 境界文字列の直前には、常に改行（`CRLF`）が必要です。

### `mime/multipart` パッケージ

Go言語の標準ライブラリである `mime/multipart` パッケージは、これらのマルチパートメッセージの生成と解析を扱うための機能を提供します。`multipart.Reader` は、入力ストリームからマルチパートメッセージを読み込み、各パートを `multipart.Part` として提供します。`partReader` は、個々のパートのボディを読み込むための内部的なリーダーです。

### `mr.nlDashBoundary`

`mr.nlDashBoundary` は、`multipart.Reader` 内部で管理されるバイトスライスで、`\r\n--` の後に実際の境界文字列が続く形式（例: `\r\n--myboundary`）を持っています。これは、新しいパートの開始やメッセージの終了を示す境界を効率的に検索するために使用されます。

## 技術的詳細

### 以前のバグのメカニズム

このコミット以前の `mime/multipart` パッケージの `partReader.Read` メソッドでは、次の境界を探すために `bytes.Index(peek, p.mr.nlDashBoundary)` を使用していました。ここで `peek` は、入力ストリームから先読みされた（まだ消費されていない）データを含むバッファです。

この `bytes.Index` 関数は、`peek` バッファ内で `p.mr.nlDashBoundary` のバイト列が最初に出現するインデックスを返します。問題は、`bytes.Index` が単にバイト列の一致を検索するだけであり、それが「有効な境界」であるかどうかの文脈を考慮しない点にありました。

例えば、境界文字列が `----=_NextPart_XYZ` であったとします。もしパートのコンテンツ内に `----=_NextPart_ABC` のような文字列が含まれていた場合、`bytes.Index` は `----=_NextPart_` の部分を `p.mr.nlDashBoundary` のプレフィックスとして誤って認識し、そのインデックスを返してしまう可能性がありました。これにより、パーサーは本来のパートの途中で誤ってパートの終了を検出し、残りのデータを読み飛ばしたり、不正なデータとして扱ったりしていました。

特に、ネストされたマルチパートメッセージで、内部の境界が外部の境界のプレフィックスになっている場合にこの問題が発生しやすかったのです。

### 修正の概要

このコミットでは、この問題を解決するために、`partReader.Read` メソッドにおける境界の検出ロジックが強化されました。具体的には、単なるバイト列の一致だけでなく、その一致が「有効な境界」であるかどうかを厳密に検証する新しいヘルパー関数 `peekBufferSeparatorIndex` が導入されました。

`peekBufferSeparatorIndex` は、`p.mr.nlDashBoundary` が見つかった場合でも、その後に続く文字が境界の終了を示す `\r\n` または ` --` であることを確認します。これにより、コンテンツ内の偶然の一致を本物の境界と誤認することを防ぎます。

## コアとなるコードの解説

### `partReader.Read` の変更

`partReader.Read` メソッド内の境界検出ロジックが以下のように変更されました。

```go
-	if idx := bytes.Index(peek, p.mr.nlDashBoundary); idx != -1 {
+	if idx, isEnd := p.mr.peekBufferSeparatorIndex(peek); idx != -1 {
 		nCopy = idx
-		foundBoundary = true
+		foundBoundary = isEnd
+		if !isEnd && nCopy == 0 {
+			nCopy = 1 // make some progress.
+		}
 	}
```

- 以前は `bytes.Index` を直接使用して `p.mr.nlDashBoundary` を検索し、見つかれば `foundBoundary = true` としていました。
- 修正後は、新しく導入された `p.mr.peekBufferSeparatorIndex(peek)` 関数を呼び出し、その戻り値 `idx` と `isEnd` を使用します。
- `isEnd` は、見つかった `idx` が単なるプレフィックスではなく、実際に有効な境界の開始であるかどうかを示します。
- `foundBoundary` は `isEnd` の値に設定され、真の境界のみが認識されるようになります。
- `if !isEnd && nCopy == 0 { nCopy = 1 }` の行は、重要な進捗保証のメカニズムです。もし `peekBufferSeparatorIndex` が境界のプレフィックスを見つけたものの、それが有効な境界ではない（`isEnd` が `false`）場合、そしてまだ何もコピーされていない（`nCopy == 0`）場合、少なくとも1バイトを消費して進捗を確保します。これにより、無限ループに陥ることを防ぎます。

### `peekBufferSeparatorIndex` 関数の導入

この新しい関数は、`peek` バッファ内で `mr.nlDashBoundary` を検索し、それが有効な境界であるかどうかを厳密に判断します。

```go
func (mr *Reader) peekBufferSeparatorIndex(peek []byte) (idx int, isEnd bool) {
	idx = bytes.Index(peek, mr.nlDashBoundary)
	if idx == -1 {
		return // 境界が見つからなければ、そのまま終了
	}
	// 境界文字列の直後からチェックを開始
	peek = peek[idx+len(mr.nlDashBoundary):]

	// 終端境界 (epilogue) のチェック: "--" が続く場合
	if len(peek) > 1 && peek[0] == '-' && peek[1] == '-' {
		return idx, true // 有効な終端境界
	}

	// 境界の後に続く空白文字 (LWSP-char: Space / HTAB) をスキップ
	peek = skipLWSPChar(peek)

	// 境界の後に完全な改行がない場合、それは有効な境界ではない
	// (例: ボディの途中に境界のプレフィックスがあるが、改行で終わっていない)
	if bytes.IndexByte(peek, '\n') == -1 {
		return -1, false // 有効な境界ではない
	}

	// 境界の後に '\n' または '\r\n' が続く場合、それは有効な境界
	if len(peek) > 0 && peek[0] == '\n' {
		return idx, true
	}
	if len(peek) > 1 && peek[0] == '\r' && peek[1] == '\n' {
		return idx, true
	}

	return idx, false // それ以外の場合は有効な境界ではない
}
```

この関数は以下のロジックで動作します：
1.  まず `bytes.Index` を使って `mr.nlDashBoundary` の最初の出現位置 `idx` を探します。見つからなければ `-1, false` を返します。
2.  `idx` が見つかった場合、`peek` スライスを境界文字列の直後から開始するように調整します。
3.  **終端境界のチェック**: 境界文字列の直後に `--` が続く場合（例: `--myboundary--`）、それはメッセージ全体の終端を示す有効な境界 (`isEnd = true`) と判断されます。
4.  **空白文字のスキップ**: `skipLWSPChar` を呼び出して、境界の後に続く可能性のある空白文字（スペースやタブ）をスキップします。RFC 822では、境界の後にLWSP-charが続くことが許容されています。
5.  **改行のチェック**: スキップ後、残りの `peek` バッファに改行文字 `\n` が含まれているかを `bytes.IndexByte(peek, '\n') == -1` で確認します。もし改行が見つからない場合、それは有効な境界ではありません（境界は常に改行で終わるため）。この場合、`-1, false` を返します。これは、境界のプレフィックスがボディの途中に現れたが、その後に改行が続かないケースを検出します。
6.  **有効な改行シーケンスのチェック**: 最後に、境界の直後に `\n` または `\r\n` が続くことを確認します。これらが存在すれば、それは有効なパートの区切り (`isEnd = true`) と判断されます。
7.  上記いずれの条件にも合致しない場合、`idx, false` を返します。これは、境界文字列自体は見つかったものの、その後のシーケンスが有効な境界の形式を満たしていないことを意味します。

この `peekBufferSeparatorIndex` 関数により、`mime/multipart` パーサーは、ボディコンテンツ内の偶然の一致ではなく、RFCの仕様に厳密に準拠した真の境界のみを認識できるようになり、解析の堅牢性が大幅に向上しました。

# [インデックス 2218] ファイルの概要

このコミットは、Go言語の `os` パッケージにおけるファイル情報取得関数 `Stat` の挙動を改善し、取得した `Dir` 構造体（ファイルやディレクトリのメタデータを表す）に、シンボリックリンクを辿った結果であるかどうかを示す情報を追加するものです。これにより、ユーザーは `Stat` が返した情報が、元のパスがシンボリックリンクであった場合に、そのリンク自体のものではなく、リンクが指し示す実体の情報であるかをプログラム的に判断できるようになります。

## 変更の背景

Go言語の `os` パッケージにおける `Stat` 関数は、指定されたパスのファイル情報を取得する際に、そのパスがシンボリックリンクであった場合、デフォルトでそのリンクが指し示す実体の情報を返します。これは多くのユースケースで望ましい挙動ですが、時には `Stat` がシンボリックリンクを辿った結果として情報を取得したのかどうかを知る必要がある場合があります。

例えば、ファイルシステムを走査するツールや、バックアップシステム、あるいはセキュリティ関連のアプリケーションなどでは、シンボリックリンクの存在とその解決の有無が重要な意味を持つことがあります。従来の `Stat` 関数では、返された `Dir` 構造体だけでは、それがシンボリックリンクを辿った結果得られた情報なのか、それとも直接ファイルやディレクトリの情報を取得したものなのかを区別できませんでした。

このコミットは、この情報不足を解消するために、`Dir` 構造体に `FollowedSymlink` という新しいフィールドを追加し、`Stat` 関数がシンボリックリンクを辿った場合にこのフィールドを `true` に設定するように変更することで、より詳細なファイルシステム情報の取得を可能にしています。これにより、開発者は `Stat` の結果をより正確に解釈し、シンボリックリンクの挙動に基づいたロジックを実装できるようになります。

## 前提知識の解説

### 1. シンボリックリンク (Symbolic Link / Symlink)

シンボリックリンク（またはソフトリンク）は、Unix系オペレーティングシステムにおける特殊なファイルの一種で、他のファイルやディレクトリへの参照（ポインタ）として機能します。Windowsにおける「ショートカット」に似ていますが、より低レベルでOSに統合されています。

- **機能**: シンボリックリンクは、それ自体がデータを含まず、単に別のファイルやディレクトリのパスを指し示します。
- **用途**:
    - 頻繁にアクセスされるファイルを、より短いパスや異なるディレクトリからアクセスできるようにする。
    - ライブラリのバージョン管理（例: `libfoo.so` が `libfoo.so.1.2.3` を指す）。
    - 設定ファイルやログファイルを特定の場所に集約する。
    - 異なるファイルシステム上のリソースを参照する。
- **挙動**: シンボリックリンクを操作するほとんどのファイルシステム操作（読み込み、書き込み、実行など）は、リンクが指し示す実体に対して行われます。しかし、リンク自体を操作する特別なコマンド（例: `rm` でリンクを削除する、`ls -l` でリンクの情報を表示する）も存在します。

### 2. `stat` と `lstat` システムコール

Unix系OSには、ファイルやディレクトリのメタデータ（サイズ、パーミッション、所有者、最終更新日時など）を取得するためのシステムコールが提供されています。その中でも `stat` と `lstat` はシンボリックリンクの扱いで重要な違いがあります。

-   **`stat(2)` システムコール**:
    -   指定されたパスがシンボリックリンクである場合、**そのリンクが指し示す実体**のメタデータを取得します。つまり、シンボリックリンクを自動的に「辿って」実体の情報を返します。
    -   Go言語の `os.Stat` 関数は、この `stat(2)` システムコールの挙動を模倣しています。

-   **`lstat(2)` システムコール**:
    -   指定されたパスがシンボリックリンクである場合、**そのシンボリックリンク自体**のメタデータを取得します。リンクが指し示す実体は辿りません。
    -   Go言語の `os.Lstat` 関数は、この `lstat(2)` システムコールの挙動を模倣しています。

このコミットの変更は、`os.Stat` 関数が内部で `lstat` と `stat` の両方を利用し、シンボリックリンクを辿ったかどうかを判断するロジックを追加することで、この `stat` と `lstat` の違いをユーザーに透過的に伝えることを目的としています。

### 3. Go言語の `os` パッケージ

`os` パッケージは、Go言語におけるオペレーティングシステムとのインタフェースを提供する標準ライブラリです。ファイルシステム操作（ファイルの読み書き、ディレクトリの作成、ファイル情報の取得など）、プロセス管理、環境変数へのアクセスなど、OSレベルの機能を提供します。

-   **`os.File`**: ファイルディスクリプタをラップした構造体で、ファイル操作のメソッドを提供します。
-   **`os.Dir`**: ファイルやディレクトリのメタデータ（ファイル情報）を保持する構造体です。`os.Stat` や `os.Lstat` 関数がこの構造体のポインタを返します。

### 4. `Dir` 構造体

`os` パッケージの `Dir` 構造体は、ファイルやディレクトリに関する様々なメタデータを格納するために使用されます。このコミット以前は、以下のようなフィールドを持っていました（一部抜粋）：

```go
type Dir struct {
    Dev     uint64; // device number of filesystem
    Ino     uint64; // inode number
    Nlink   uint64; // number of hard links
    Mode    int;    // file mode bits
    Uid     uint32; // owner uid
    Gid     uint32; // group gid
    Rdev    uint64; // device numbers (for devices)
    Size    int64;  // file size in bytes
    Blksize int64;  // blocksize for filesystem I/O
    Blocks  int64;  // number of blocks allocated
    Atime   int64;  // access time; seconds since epoch.
    Mtime   int64;  // modified time; seconds since epoch.
    Ctime   int64;  // status change time; seconds since epoch.
    Name    string; // name of file as presented to Open.
}
```

このコミットでは、この `Dir` 構造体に `FollowedSymlink bool` という新しいフィールドが追加され、`Stat` 関数がシンボリックリンクを辿った場合にこのフィールドが `true` に設定されるようになります。

## 技術的詳細

このコミットの主要な技術的変更点は、`os.Stat` 関数の内部ロジックと `os.Dir` 構造体の拡張にあります。

1.  **`os.Dir` 構造体の拡張**:
    `src/lib/os/types.go` にて、`Dir` 構造体に `FollowedSymlink bool` という新しいフィールドが追加されました。このフィールドは、`Stat` 関数がシンボリックリンクを辿ってファイル情報を取得した場合に `true` となります。

    ```go
    type Dir struct {
        // ... 既存のフィールド ...
        Name            string; // name of file as presented to Open.
        FollowedSymlink bool;   // followed a symlink to get this information
    }
    ```

2.  **`os.Stat` 関数のロジック変更 (`src/lib/os/file.go`)**:
    従来の `os.Stat` は、直接 `syscall.Stat` を呼び出してファイル情報を取得していました。しかし、この変更により、`os.Stat` は以下のようなロジックで動作するようになります。

    -   まず、`syscall.Lstat(name, &lstat)` を呼び出し、指定された `name` のパスがシンボリックリンクであるかどうかに関わらず、そのパス自体の情報を `lstat` に取得します。
    -   `lstat` の結果、`name` がシンボリックリンク (`syscall.S_IFLNK`) であった場合、さらに `syscall.Stat(name, &stat)` を呼び出し、シンボリックリンクが指し示す実体の情報を `stat` に取得します。
    -   `dirFromStat` ヘルパー関数に、`lstat` と `stat` の両方の情報が渡されるようになります。

    この二段階の `stat` 呼び出しにより、`os.Stat` は元のパスがシンボリックリンクであったか（`lstat` の情報）、そして実際にシンボリックリンクを辿って実体の情報を取得したか（`stat` の情報）を判断できるようになります。

3.  **`dirFromStat` ヘルパー関数の変更 (`src/lib/os/stat_amd64_darwin.go`, `src/lib/os/stat_amd64_linux.go` など)**:
    `dirFromStat` 関数は、`syscall.Stat_t` 構造体から `os.Dir` 構造体を構築する内部ヘルパー関数です。この関数は、各OS固有のファイル情報取得実装（例: `stat_amd64_darwin.go` や `stat_amd64_linux.go`）に存在します。

    変更後、`dirFromStat` は `lstat` と `stat` の2つの `syscall.Stat_t` ポインタを受け取るようになりました。そして、`lstat` がシンボリックリンクを示し（`isSymlink(lstat)` が `true`）、かつ `stat` がシンボリックリンクを示さない（`isSymlink(stat)` が `false`、つまり実体を辿った）場合に、`dir.FollowedSymlink` を `true` に設定します。

    ```go
    func dirFromStat(name string, dir *Dir, lstat, stat *syscall.Stat_t) *Dir {
        // ... 既存のフィールド設定ロジック ...
        if isSymlink(lstat) && !isSymlink(stat) {
            dir.FollowedSymlink = true;
        }
        return dir;
    }
    ```
    また、`isSymlink` というヘルパー関数が追加され、`syscall.Stat_t` の `Mode` フィールドからシンボリックリンクであるかを判定するロジックがカプセル化されました。

4.  **テストケースの追加 (`src/lib/os/os_test.go`)**:
    `TestSymLink` 関数に、`Stat` がシンボリックリンクを辿った際に `FollowedSymlink` が正しく設定されることを検証するテストが追加されました。これにより、新しい機能が意図通りに動作することが保証されます。

これらの変更により、Goの `os.Stat` 関数は、ファイルシステム操作においてより詳細な情報を提供できるようになり、シンボリックリンクの挙動を考慮した堅牢なアプリケーション開発が可能になります。

## コアとなるコードの解説

### `src/lib/os/types.go` の変更

`Dir` 構造体に `FollowedSymlink bool` フィールドが追加されました。これは、`os.Stat` 関数がシンボリックリンクを辿ってファイル情報を取得した場合に `true` となるフラグです。この追加により、`Stat` の呼び出し元は、返された `Dir` 情報がシンボリックリンクの実体のものであるか、あるいは直接指定されたファイルのものであるかを区別できるようになります。

### `src/lib/os/file.go` の変更

1.  **`Stat` 関数のシグネチャとコメントの変更**:
    -   関数のコメントが更新され、`Stat` がシンボリックリンクを辿った場合の `Dir.FollowedSymlink` の挙動が明記されました。
    -   `Stat` が有効なシンボリックリンク名を指定された場合、返される `Dir` はリンクが指し示すファイルのものであり、`dir.FollowedSymlink` は `true` に設定されます。
    -   無効なシンボリックリンク名を指定された場合、返される `Dir` はリンク自体のものであり、`dir.FollowedSymlink` は `false` に設定されます。

2.  **`Stat` 関数の内部ロジック**:
    -   変更前は `syscall.Stat(name, stat)` を直接呼び出していました。
    -   変更後は、まず `syscall.Lstat(name, &lstat)` を呼び出し、`name` がシンボリックリンクであるかどうかにかかわらず、そのパス自体の情報を `lstat` に取得します。
    -   もし `lstat` の結果、`name` がシンボリックリンク (`syscall.S_IFLNK`) であった場合、さらに `syscall.Stat(name, &stat)` を呼び出し、シンボリックリンクが指し示す実体の情報を `stat` に取得します。
    -   `statp` というポインタが導入され、デフォルトでは `lstat` を指しますが、シンボリックリンクを辿って実体の情報が取得できた場合は `stat` を指すようになります。
    -   最終的に `dirFromStat(name, new(Dir), &lstat, statp)` が呼び出されます。ここで `lstat` と `statp` の両方が渡されることで、`dirFromStat` は元のパスがシンボリックリンクであったか、そして実際にシンボリックリンクを辿ったかを判断できるようになります。

3.  **`File.Stat()` と `Lstat()` の変更**:
    -   これらの関数も `dirFromStat` の呼び出しにおいて、`lstat` と `stat` の両方を渡すように変更されました。ただし、`File.Stat()` は既に開かれているファイルディスクリプタに対する `fstat` の結果であり、シンボリックリンクを辿ることはないため、`&stat, &stat` のように同じ `stat` 情報を2回渡しています。
    -   `Lstat()` も同様にシンボリックリンクを辿らないため、`&stat, &stat` を渡しています。これにより、`dirFromStat` 内で `FollowedSymlink` が `true` になることはありません。

### `src/lib/os/stat_amd64_darwin.go` (および `stat_amd64_linux.go`) の変更

1.  **`isSymlink` ヘルパー関数の追加**:
    -   `syscall.Stat_t` 構造体の `Mode` フィールドと `syscall.S_IFMT` および `syscall.S_IFLNK` を用いて、ファイルがシンボリックリンクであるかを判定するシンプルなヘルパー関数 `isSymlink` が追加されました。これにより、コードの可読性が向上します。

2.  **`dirFromStat` 関数のシグネチャとロジックの変更**:
    -   `dirFromStat` 関数は、これまでの `(name string, dir *Dir, stat *syscall.Stat_t)` から `(name string, dir *Dir, lstat, stat *syscall.Stat_t)` へとシグネチャが変更されました。これにより、元のパスの `lstat` 情報と、実際に取得された `stat` 情報の両方を受け取れるようになりました。
    -   新しいロジックとして、`if isSymlink(lstat) && !isSymlink(stat)` という条件が追加されました。これは、「元のパス (`lstat`) がシンボリックリンクであり、かつ、最終的に取得された情報 (`stat`) がシンボリックリンクではない（つまり、シンボリックリンクを辿って実体の情報を取得した）」場合に `dir.FollowedSymlink` を `true` に設定するという意味です。

これらの変更により、Goの `os.Stat` 関数は、シンボリックリンクの解決に関するより詳細なコンテキストをユーザーに提供できるようになり、ファイルシステム操作の透明性と制御性が向上しました。

# [インデックス 25692] ファイルの概要

このコミットは、Goランタイムのメモリ管理における重要なバグ修正に関するものです。具体的には、32ビット環境でのメモリ確保時に、`sysReserve`関数が予期せぬアドレスを返す可能性があり、それがヒープの内部状態を破損させ、最終的にクラッシュを引き起こす問題に対処しています。

## コミット

```
commit 0de59c27ebda76d3e5121888acca304e49009266
Author: Austin Clements <austin@google.com>
Date:   Sun Nov 15 23:13:16 2015 -0500

    runtime: handle sysReserve returning a pointer below the arena
    
    In mheap.sysAlloc, if an allocation at arena_used would exceed
    arena_end (but wouldn't yet push us past arena_start+_MaxArean32), it
    trie to extend the arena reservation by another 256 MB. It extends the
    arena by calling sysReserve, which, on 32-bit, calls mmap without
    MAP_FIXED, which means the address is just a hint and the kernel can
    put the mapping wherever it wants. In particular, mmap may choose an
    address below arena_start (the kernel also chose arena_start, so there
    could be lots of space below it). Currently, we don't detect this case
    and, if it happens, mheap.sysAlloc will corrupt arena_end and
    arena_used then return the low pointer to mheap.grow, which will crash
    when it attempts to index in to h_spans with an underflowed index.
    
    Fix this by checking not only that that p+p_size isn't too high, but
    that p isn't too low.
    
    Fixes #13143.
```

## 元コミット内容

`runtime: handle sysReserve returning a pointer below the arena`

このコミットは、`sysReserve`関数がアリーナ（Goランタイムが管理するメモリ領域）の下限よりも低いアドレスを返すケースを処理するように、Goランタイムを変更します。

## 変更の背景

Goランタイムは、プログラムが使用するメモリを効率的に管理するために、独自のヒープ（`mheap`）を実装しています。このヒープは、`arena`と呼ばれる大きなメモリ領域をOSから確保し、その中を細かく分割してオブジェクトに割り当てます。

`mheap.sysAlloc`関数は、必要に応じてこのアリーナ領域を拡張する役割を担っています。アリーナの現在の使用済み領域（`arena_used`）がアリーナの終端（`arena_end`）を超えそうになった場合、`sysAlloc`は`sysReserve`を呼び出して、さらに256MBのメモリ領域をOSに要求し、アリーナを拡張しようとします。

問題は、特に32ビットシステムにおいて発生しました。`sysReserve`は内部的にOSの`mmap`システムコールを使用しますが、32ビット環境では`MAP_FIXED`フラグなしで`mmap`を呼び出すことがあります。`MAP_FIXED`フラグがない場合、`mmap`に渡されるアドレスは単なる「ヒント」として扱われ、カーネルは指定されたアドレスではなく、利用可能な任意のアドレスにメモリをマッピングする可能性があります。

この「任意のアドレス」が、既存のアリーナの開始アドレス（`arena_start`）よりも低いアドレスになることがありました。カーネルは`arena_start`自体も選択しているため、その下にも十分な空きスペースが存在する可能性があったためです。

しかし、Goランタイムの`mheap.sysAlloc`は、この`sysReserve`が`arena_start`よりも低いアドレスを返すケースを想定していませんでした。その結果、`sysAlloc`は不正な低いポインタを受け取ると、`arena_end`と`arena_used`といったヒープの内部状態を誤って更新してしまい、最終的に`mheap.grow`関数が`h_spans`配列に不正な（アンダーフローした）インデックスでアクセスしようとした際にクラッシュを引き起こしていました。

このバグはIssue #13143として報告されていました。

## 前提知識の解説

*   **Goランタイムのメモリ管理**: Goは独自のガベージコレクタとメモリマネージャを持っています。これはOSから大きなメモリブロック（アリーナ）を確保し、それを細かく管理することで、効率的なメモリ割り当てと解放を実現しています。
*   **`mheap`**: Goランタイムにおけるグローバルなヒープ構造体です。アリーナの管理、スパン（メモリブロックの単位）の割り当てなどを担当します。
*   **`arena`**: GoランタイムがOSから確保する連続した仮想メモリ領域です。`arena_start`、`arena_end`、`arena_used`などのフィールドで管理されます。
*   **`sysAlloc`**: `mheap`がOSから新しいメモリ領域を確保する際に呼び出す関数です。
*   **`sysReserve`**: `sysAlloc`から呼び出され、OSに対して仮想メモリ領域の予約を要求する関数です。
*   **`mmap`**: Unix系OSにおけるシステムコールで、ファイルやデバイスをメモリにマッピングしたり、匿名メモリ領域を確保したりするために使用されます。
*   **`MAP_FIXED`フラグ**: `mmap`システムコールに渡されるフラグの一つです。このフラグが指定されると、`mmap`は指定されたアドレスに正確にメモリをマッピングしようとします。指定されたアドレスが利用できない場合、`mmap`は失敗します。このフラグがない場合、指定されたアドレスは単なるヒントとして扱われ、カーネルは別のアドレスを選択する可能性があります。
*   **32ビットシステム**: 32ビットのアドレス空間を持つシステムです。仮想メモリのアドレス範囲が4GBに制限されるため、メモリ管理において特定の問題が発生しやすいことがあります。特に、連続した大きなメモリ領域を確保する際に、アドレス空間の断片化が問題となることがあります。
*   **`h_spans`**: `mheap`構造体の一部で、メモリのスパン（連続したページ群）を管理するための配列です。スパンは、Goのオブジェクトが割り当てられる基本的なメモリ単位です。

## 技術的詳細

この問題の核心は、`sysReserve`（そしてその内部の`mmap`）が、要求されたアドレスの「ヒント」を無視して、`arena_start`よりも低いアドレスを返す可能性があるという点にありました。

Goランタイムは、アリーナを拡張する際に、既存の`arena_end`から新しい領域を確保しようとします。しかし、`mmap`が`arena_start`よりも低いアドレス`p`を返した場合、`p`は既存のアリーナの範囲外となります。

元のコードでは、`sysAlloc`は新しい領域`p`が`h.arena_end`に隣接しているかどうか、または`p+p_size`が`_MaxArena32`（32ビットシステムにおけるアリーナの最大サイズ）を超えていないか、というチェックは行っていましたが、`p`自体が`arena_start`よりも低いかどうかというチェックが欠けていました。

このチェックの欠如により、`p`が`arena_start`よりも低い場合でも、`sysAlloc`はそれを有効な拡張と見なし、`h.arena_end = p + p_size`のように`arena_end`を更新してしまいました。これにより、`arena_end`が`arena_start`よりも低い値になる可能性があり、ヒープの内部状態が矛盾した状態に陥りました。

結果として、`mheap.grow`関数が、この破損した`arena_end`や`arena_used`に基づいて`h_spans`配列のインデックスを計算しようとすると、インデックスがアンダーフロー（非常に大きな負の値になるなど）し、配列の範囲外アクセスが発生してプログラムがクラッシュしていました。

## コアとなるコードの変更箇所

変更は`src/runtime/malloc.go`ファイル内の`mheap.sysAlloc`関数にあります。

```diff
--- a/src/runtime/malloc.go
+++ b/src/runtime/malloc.go
@@ -404,7 +404,7 @@ func (h *mheap) sysAlloc(n uintptr) unsafe.Pointer {
 		if p == h.arena_end {
 			h.arena_end = new_end
 			h.arena_reserved = reserved
-		} else if p+p_size <= h.arena_start+_MaxArena32 {
+		} else if h.arena_start <= p && p+p_size <= h.arena_start+_MaxArena32 {
 			// Keep everything page-aligned.
 			// Our pages are bigger than hardware pages.
 			h.arena_end = p + p_size
```

## コアとなるコードの解説

変更された行は以下の部分です。

**変更前:**
```go
} else if p+p_size <= h.arena_start+_MaxArena32 {
```

**変更後:**
```go
} else if h.arena_start <= p && p+p_size <= h.arena_start+_MaxArena32 {
```

この変更は、`else if`条件に`h.arena_start <= p`という新しいチェックを追加しています。

*   `p`は`sysReserve`によって返された新しいメモリ領域の開始アドレスです。
*   `p_size`はその領域のサイズです。
*   `h.arena_start`は既存のアリーナの開始アドレスです。
*   `_MaxArena32`は32ビットシステムにおけるアリーナの最大サイズです。

変更前のコードでは、新しい領域`p`が既存のアリーナの最大範囲（`h.arena_start+_MaxArena32`）を超えていないことだけを確認していました。しかし、これでは`p`が`h.arena_start`よりも低いアドレスである可能性を見落としていました。

変更後のコードでは、`h.arena_start <= p`という条件が追加されたことで、新しい領域`p`が既存のアリーナの開始アドレス`h.arena_start`以上であることを厳密にチェックするようになりました。これにより、`sysReserve`が`arena_start`よりも低いアドレスを返した場合でも、その領域をアリーナの有効な拡張として誤って受け入れることがなくなります。

この修正により、`arena_end`や`arena_used`が不正な値で更新されることがなくなり、`mheap.grow`でのクラッシュが防止されます。これは、Goランタイムのメモリ管理の堅牢性を高めるための重要な修正です。

# [インデックス 21059] ファイルの概要

このコミットは、Goランタイムパッケージ内のC言語ヘッダーファイルをGo言語のソースファイルに変換することを目的としています。これにより、GoランタイムのCコードへの依存を減らし、Go言語の自己完結性を高める重要な一歩となります。

## 変更の背景

このコミットは、GoランタイムからCコードを排除するという大規模な取り組みの一環です。コミットメッセージに記載されている `golang.org/s/dev.cc` は、このプロジェクトの概要を示すドキュメントへのショートリンクです。

この変更の主な動機は以下の通りです。

1.  **ビルドプロセスの簡素化**: Cコードへの依存を減らすことで、Goプログラムのビルドに必要なツールチェインが簡素化され、クロスコンパイルが容易になります。
2.  **移植性の向上**: 特定のCコンパイラやCライブラリへの依存を減らすことで、Goランタイムがより多くのプラットフォームに移植しやすくなります。
3.  **Goネイティブな最適化の促進**: CコードがGoコードに変換されることで、Goコンパイラやランタイムがより深いレベルで最適化を行えるようになり、パフォーマンスの向上が期待されます。
4.  **開発の効率化**: Go言語でランタイムの大部分を記述することで、Go開発者にとってランタイムの理解、デバッグ、および貢献が容易になります。

Goプロジェクトは、Go 1.5以降、Cランタイムへの依存を減らす努力を続けており、例えばDNS解決などの機能においてもCへの依存を排除してきました。このコミットは、その初期段階における重要なステップの一つです。

## 前提知識の解説

### Goランタイム

Goランタイムは、Goプログラムの実行を管理する低レベルなコンポーネントの集合体です。これには、ゴルーチン（軽量スレッド）のスケジューリング、ガベージコレクション（メモリ管理）、チャネル（ゴルーチン間の通信）、メモリ割り当て、システムコールインターフェースなどが含まれます。Goプログラムは、コンパイル時にこのランタイムとリンクされ、自己完結型のバイナリを生成します。

### C言語のヘッダーファイル (.h)

C言語において、ヘッダーファイル（通常 `.h` 拡張子を持つ）は、関数、マクロ、構造体、型定義などの宣言を含みます。これらは、異なるソースファイル間で共有されるインターフェースを定義するために使用されます。コンパイル時には、`#include` ディレクティブによってヘッダーファイルの内容がソースファイルに展開されます。

### GoとCの相互運用性 (cgo)

Go言語は、`cgo`というメカニズムを通じてC言語のコードと相互運用することができます。これにより、GoプログラムからC関数を呼び出したり、Cライブラリを利用したりすることが可能です。しかし、`cgo`を使用すると、ビルドプロセスが複雑になり、GoのガベージコレクタがC言語で割り当てられたメモリを直接管理できないなどの課題が生じます。GoランタイムのCコード排除は、このような`cgo`の複雑性を減らすことを目指しています。

### Goの型システムとunsafeパッケージ

Goは静的型付け言語であり、厳格な型システムを持っています。これにより、コンパイル時に多くのエラーを捕捉し、コードの安全性を高めます。しかし、ランタイムのような低レベルなプログラミングでは、メモリの直接操作や型変換が必要になる場合があります。Goの標準ライブラリである`unsafe`パッケージは、このような低レベルな操作を可能にする機能（例: `unsafe.Pointer`による任意の型へのポインタ変換）を提供しますが、その使用は慎重に行う必要があります。

### CL (Change List)

Goコミュニティでは、コード変更の単位を「Change List (CL)」と呼びます。これは、Gitのコミットに似ていますが、通常はより大きな論理的な変更のまとまりを指し、レビュープロセスを経てGoのリポジトリにマージされます。コミットメッセージの `https://golang.org/cl/167550043` は、この変更に対応するGoのコードレビューシステム（Gerrit）上のCLへのリンクです。

## 技術的詳細

このコミットの核心は、Goランタイムの内部構造を定義していたCヘッダーファイル（`.h`）を、Go言語のソースファイル（`.go`）に変換することです。この変換は、自動化ツールによって大部分が行われ、その後、コンパイルと実行を可能にするために必要な手動での調整が加えられました。

具体的な変換のパターンは以下の通りです。

*   **Cの構造体 (`struct`) からGoの構造体 (`type struct`) への変換**:
    C言語のヘッダーファイルで定義されていたランタイムの主要なデータ構造（例: `Hchan`, `G`, `M`, `P`など）は、Go言語の`struct`として再定義されました。この際、Cのポインタ型はGoのポインタ型（例: `*byte`, `*g`）に、Cのプリミティブ型はGoの対応する型（例: `uintgo` -> `uint`, `int32` -> `int32`）に変換されています。
    Goの`unsafe`パッケージは、Cの構造体におけるメモリレイアウトの整合性を保ちつつ、Goの型システム内で低レベルなポインタ操作を可能にするために使用されています。例えば、`unsafe.Pointer`は、任意の型へのポインタとして機能し、型安全性を一時的にバイパスしてメモリを直接操作することを可能にします。

*   **Cのマクロ (`#define`) からGoの定数 (`const`) への変換**:
    Cヘッダーファイルで定義されていた定数やマクロ（例: `MAXALIGN`, `CaseRecv`など）は、Goの`const`宣言に変換されました。Goの`iota`キーワードは、連続する定数に自動的に値を割り当てるために活用されています。

*   **Cの型エイリアス (`typedef`) からGoの型エイリアス (`type`) への変換**:
    Cの`typedef`による型エイリアスは、Goの`type`キーワードを用いた型定義に置き換えられました。

*   **ファイル分割と命名規則**:
    元のCヘッダーファイルは、その内容に応じて複数のGoファイルに分割されています。例えば、`chan.h`は`chan1.go`に、`runtime.h`は`runtime2.go`に、`type.h`は`type.go`に変換されています。これは、Goのパッケージ構造とファイル分割の慣習に従ったものです。`chan1.go`や`runtime2.go`のような命名は、既存のGoファイルとの衝突を避けるため、または段階的な移行を示すために使用されることがあります。

*   **`funcdata.h`と`typekind.h`の変更**:
    これらのファイルは完全に削除されたわけではなく、一部が変更されています。`funcdata.h`は、Goバイナリ内のPCDATA（PC-data）およびFUNCDATA（関数データ）命令のIDを定義しており、アセンブリソースによってインクルードされるため、`#define`を使用し続ける必要があります。変更は、PCDATA_ArgSizeの削除とPCDATA_StackMapIndexのインデックス変更など、Goランタイムの内部的なデータ構造の進化を反映しています。`typekind.h`も同様に、Goの型システムにおける内部的な型表現に関連する定数を定義しており、Goコードへの移行に伴い、一部の定数定義が`typekind1.go`に移動しています。

## コアとなるコードの変更箇所

このコミットでは、主に以下のCヘッダーファイルが削除され、対応するGoファイルが追加または変更されています。

1.  **`src/runtime/chan.h` の削除と `src/runtime/chan1.go` の追加**:
    *   `chan.h`で定義されていた`WaitQ`、`Hchan`、`Scase`、`Select`といったチャネル関連の構造体が、`chan1.go`でGoの`struct`として再定義されました。
    *   Cのマクロ`chanbuf`は、Goのコメントとして残され、その機能はGoのポインタ演算と`unsafe`パッケージを使って実現されます。
    *   `CaseRecv`などの定数は、`_CaseRecv`のようにGoの`const`として定義されました。

    **`src/runtime/chan.h` (削除されるCコードの例)**:
    ```c
    typedef struct WaitQ WaitQ;
    typedef struct Select Select;
    typedef struct Scase Scase;

    struct Hchan
    {
        uintgo  qcount;         // total data in the q
        uintgo  dataqsiz;       // size of the circular q
        byte*   buf;
        uint16  elemsize;
        uint32  closed;
        Type*   elemtype;       // element type
        uintgo  sendx;          // send index
        uintgo  recvx;          // receive index
        WaitQ   recvq;          // list of recv waiters
        WaitQ   sendq;          // list of send waiters
        Mutex   lock;
    };
    ```

    **`src/runtime/chan1.go` (追加されるGoコードの例)**:
    ```go
    type waitq struct {
        first *sudog
        last  *sudog
    }

    type hchan struct {
        qcount   uint // total data in the q
        dataqsiz uint // size of the circular q
        buf      *byte
        elemsize uint16
        closed   uint32
        elemtype *_type // element type
        sendx    uint   // send index
        recvx    uint   // receive index
        recvq    waitq  // list of recv waiters
        sendq    waitq  // list of send waiters
        lock     mutex
    }
    ```

2.  **`src/runtime/runtime.h` の削除と `src/runtime/runtime2.go` の追加**:
    *   Goランタイムの最も基本的な構造体である`G`（ゴルーチン）、`M`（OSスレッド）、`P`（プロセッサ）、`SchedT`（スケジューラの状態）などが、`runtime.h`から`runtime2.go`に移行されました。
    *   Cのプリミティブ型（`int8`, `uintptr`など）や、`Gidle`, `Grunnable`などのGステータス定数もGoの対応する型や定数に変換されました。

    **`src/runtime/runtime.h` (削除されるCコードの例)**:
    ```c
    typedef signed char     int8;
    typedef unsigned char   uint8;
    // ...
    typedef struct  G       G;
    typedef struct  M       M;
    typedef struct  P       P;
    typedef struct  SchedT  SchedT;

    enum
    {
        // G status
        Gidle,
        Grunnable,
        // ...
    };

    struct G
    {
        Stack   stack;
        uintptr stackguard0;
        // ...
    };
    ```

    **`src/runtime/runtime2.go` (追加されるGoコードの例)**:
    ```go
    package runtime

    import "unsafe"

    const (
        // G status
        _Gidle            = iota // 0
        _Grunnable               // 1 runnable and on a run queue
        // ...
    )

    type g struct {
        stack       stack   // offset known to runtime/cgo
        stackguard0 uintptr // offset known to liblink
        // ...
    }
    ```

3.  **`src/runtime/type.h` の削除と `src/runtime/type.go` の追加**:
    *   Goの型システムに関連する`Type`構造体や`Itab`（インターフェーステーブル）などが、`type.h`から`type.go`に変換されました。

    **`src/runtime/type.h` (削除されるCコードの例)**:
    ```c
    typedef struct  Type        Type;
    typedef struct  Itab        Itab;

    struct  Itab
    {
        InterfaceType*  inter;
        Type*           type;
        // ...
    };
    ```

    **`src/runtime/type.go` (追加されるGoコードの例)**:
    ```go
    package runtime

    import "unsafe"

    type _type struct {
        size       uintptr
        hash       uint32
        // ...
    }

    type itab struct {
        inter  *interfacetype
        _type  *_type
        // ...
    }
    ```

4.  **`src/runtime/funcdata.h` と `src/runtime/typekind.h` の変更**:
    *   これらのファイルは完全に削除されたわけではなく、Goコードへの移行に伴い、一部の定義が変更または移動されました。
    *   `funcdata.h`では、PCDATA_ArgSizeが削除され、PCDATA_StackMapIndexのインデックスが変更されています。これは、Goの関数データ表現の内部的な変更を反映しています。
    *   `typekind.h`は、Goの型システムにおける内部的な型表現に関連する定数を定義しており、一部の定数定義が`typekind1.go`に移動しています。

## コアとなるコードの解説

これらの変更は、GoランタイムのCコード依存を大幅に削減し、Go言語の自己完結性を高める上で極めて重要です。

*   **Go言語によるランタイムの統一**: ランタイムの主要なデータ構造がGo言語で定義されることで、Goコンパイラとランタイムの間のインターフェースがより明確になり、Go言語のツールチェイン全体での一貫性が向上します。
*   **ガベージコレクションの効率化**: Goのガベージコレクタは、Goの型システムと密接に連携しています。ランタイムの内部構造がGoで定義されることで、ガベージコレクタがこれらの構造体をより効率的にスキャンし、メモリ管理を最適化できるようになります。特に、CのポインタとGoのポインタの間の変換に伴う複雑さが軽減されます。
*   **デバッグと保守の容易性**: Go開発者にとって、Go言語で書かれたランタイムコードは、C言語で書かれたコードよりも理解しやすく、デバッグや保守が容易になります。これにより、ランタイムの改善や新機能の追加が加速される可能性があります。
*   **ビルドシステムの簡素化**: Cコンパイラや関連するビルドツールへの依存が減ることで、Goのビルドシステムがよりシンプルになり、異なる環境でのGoのデプロイが容易になります。

このコミットは、GoランタイムがC言語の遺産から脱却し、より純粋なGo言語のシステムへと進化していく過程における、重要なマイルストーンの一つと言えます。

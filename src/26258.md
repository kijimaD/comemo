# [インデックス 26258] ファイルの概要

このコミットは、Go言語の `archive/zip` パッケージにおけるZIP64アーカイブの読み書きに関する複数のバグを修正します。具体的には、ZIP64拡張フィールドのパースロジックを改善し、不正な形式のExtraフィールドに対する耐性を高め、非圧縮データサイズが `0xFFFFFFFF` のエッジケースを正しく処理するようにします。これにより、より広範なZIPファイルの互換性が向上します。

## 変更の背景

このコミットは、主に以下の3つの問題に対処するために行われました。

1.  **Issue #13367: ZIP64拡張フィールドの誤ったパース**
    一部のZIP作成ツールは、ZIP64拡張情報Extraフィールドに不正なサイズ値を設定することがありました。Goの `archive/zip` パッケージは、以前はこの不正なサイズ値に基づいて64ビットフィールド（`UncompressedSize64`、`CompressedSize64`、`headerOffset`）をすべて読み込もうとし、結果として `ErrFormat` エラーを引き起こしていました。ZIP仕様では、これらの64ビットフィールドは、対応する32ビットフィールド（`CompressedSize`、`UncompressedSize`、ローカルヘッダーオフセット）が `0xFFFFFFFF` に設定されている場合にのみ存在すると規定されています。このコミットは、この仕様に準拠し、必要な場合にのみ64ビット値を読み込むように修正しました。

2.  **Issue #13166: 予期せぬExtraフィールドに対する厳格すぎる処理**
    `archive/zip` パッケージは、Extraフィールドの内容に対して厳格すぎる傾向がありました。これにより、ZIP仕様に完全に準拠していないが、他の一般的なZIPツール（`zip` や `unzip` など）では問題なく処理されるようなZIPファイルが、Goではエラーとなるケースがありました。このコミットは、64ビットのサイズやオフセット情報が必要ない限り、予期せぬExtraフィールドの内容をより寛容に扱うように変更し、互換性を向上させました。

3.  **非圧縮データサイズ `0xFFFFFFFF` のエッジケース**
    ZIPフォーマットでは、32ビットフィールドで表現できる最大値である `0xFFFFFFFF` は、その値が実際には64ビット値であることを示す「マジックマーカー」として使用されます。Go 1.5以前のバージョンでは、非圧縮データサイズが `0xFFFFFFFF` の場合、これを32ビット値として扱い、ZIP64ヘッダーを使用せずに不正なZIPファイルを書き出す可能性がありました。このコミットは、このエッジケースを正しく処理し、`0xFFFFFFFF` が検出された場合には必ずZIP64ヘッダーを使用するように修正しました。

これらの問題は、Goの `archive/zip` パッケージが生成または読み込むZIPファイルの互換性に影響を与え、特に大容量ファイルや、標準からわずかに逸脱したツールで作成されたZIPファイルを扱う際に問題となっていました。

## 前提知識の解説

### ZIPファイルフォーマットの基本

ZIPファイルは、複数のファイルやディレクトリを1つのアーカイブにまとめるための一般的なファイルフォーマットです。各ファイルは「エントリ」として格納され、それぞれにファイル名、圧縮・非圧縮サイズ、CRC32チェックサム、変更日時などのメタデータが含まれます。

### Extraフィールド

ZIPファイルフォーマットには、「Extraフィールド」と呼ばれる拡張可能な領域があります。これは、標準のファイルヘッダーに含まれない追加のメタデータ（例: UNIXのパーミッション、NTFSのタイムスタンプ、UTF-8ファイル名など）を格納するために使用されます。Extraフィールドは、特定の「タグ」（2バイト）と「サイズ」（2バイト）のペアで構成され、その後にデータが続きます。

### ZIP64フォーマット

オリジナルのZIPフォーマットは、ファイルサイズやアーカイブ全体のサイズ、エントリ数、オフセットなどに32ビットの制限がありました（約4GBまで）。この制限を超えるファイルを扱うために導入されたのが「ZIP64」フォーマットです。
ZIP64では、これらの制限を超える値を格納するために、Extraフィールド内にZIP64拡張情報ブロック（タグ `0x0001`）が追加されます。このブロックには、64ビットの非圧縮サイズ、圧縮サイズ、ローカルヘッダーオフセットなどが格納されます。

**`0xFFFFFFFF` のマジックマーカー**: ZIP64の重要な側面は、32ビットフィールドが `0xFFFFFFFF` (または `0xFFFF` for 16-bit fields) に設定されている場合、それは実際の値ではなく、対応する64ビット値がZIP64拡張フィールドに存在することを示す「マジックマーカー」として機能するという点です。つまり、32ビットフィールドがこの値の場合、ZIPリーダーはZIP64 Extraフィールドを調べて真のサイズやオフセットを取得する必要があります。

### Goの `archive/zip` パッケージ

Go標準ライブラリの `archive/zip` パッケージは、ZIPファイルの読み書き機能を提供します。このパッケージは、ZIPファイルフォーマットの仕様に準拠し、ZIP64を含む様々なZIPアーカイブを扱うことができます。

## 技術的詳細

このコミットは、`src/archive/zip/reader.go`、`src/archive/zip/struct.go`、`src/archive/zip/writer.go`、および `src/archive/zip/zip_test.go` の4つのファイルにわたって変更を加えています。

### `src/archive/zip/reader.go` の変更

`readDirectoryHeader` 関数は、中央ディレクトリヘッダーを読み込み、`File` 構造体に情報を格納する役割を担います。この関数における主な変更点は以下の通りです。

1.  **ZIP64拡張フィールドの条件付きパース**:
    以前は、Extraフィールドに `zip64ExtraId` (0x0001) が見つかると、無条件にその内容をパースしようとしていました。しかし、Issue #13367で指摘されたように、一部のツールは不正なZIP64 Extraフィールドを書き込むため、これが `ErrFormat` の原因となっていました。
    新しいコードでは、まず3つのブールフラグ `needUSize`、`needCSize`、`needHeaderOffset` を導入します。これらは、それぞれ `f.UncompressedSize`、`f.CompressedSize`、`f.headerOffset` が32ビットの最大値 `^uint32(0)` (すなわち `0xFFFFFFFF`) に設定されているかどうかをチェックします。これらのフラグが `true` の場合のみ、対応する64ビット値がZIP64 Extraフィールドから読み取られるべきであることを示します。
    `zip64ExtraId` がExtraフィールド内で見つかった場合、これらの `need` フラグが `true` の場合にのみ、対応する64ビット値を読み込みます。読み込みが完了したら、対応する `need` フラグを `false` に設定します。これにより、必要な情報のみを読み込み、不正なExtraフィールドによるエラーを回避します。

2.  **Extraフィールドのパースの堅牢化**:
    Extraフィールドのパースループ内で、`if int(size) > len(b)` の条件が `return ErrFormat` から `break` に変更されました。これは、Extraフィールド内の個々のブロックのサイズが残りのデータ長を超えている場合、以前は即座にエラーを返していましたが、今後はそのブロックのパースを中断し、残りのExtraフィールドのパースを試みることを意味します。これにより、Issue #13166で指摘されたような、予期せぬまたは不正なExtraフィールドに対する耐性が向上します。

3.  **パース後の厳格なチェック**:
    Extraフィールドのパースが完了した後、`if needUSize || needCSize || needHeaderOffset` というチェックが追加されました。これは、もし `0xFFFFFFFF` が設定されていたにもかかわらず、対応する64ビット値がExtraフィールドから見つからなかった場合（つまり、`need` フラグのいずれかが `true` のままの場合）、`ErrFormat` を返すことを意味します。これにより、必要な情報が欠落している場合には適切にエラーを報告しつつ、不要な情報に対する寛容性を保ちます。

### `src/archive/zip/struct.go` の変更

`FileHeader` 構造体の `isZip64()` メソッドが変更されました。
`return fh.CompressedSize64 > uint32max || fh.UncompressedSize64 > uint32max`
から
`return fh.CompressedSize64 >= uint32max || fh.UncompressedSize64 >= uint32max`
に変更されています。
これは、圧縮サイズまたは非圧縮サイズが `uint32max` (0xFFFFFFFF) と**等しい**場合にもZIP64として扱うべきであることを明確にしています。前述の通り、`0xFFFFFFFF` はZIP64を必要とするマジックマーカーであるため、この変更は正しい挙動を保証します。

### `src/archive/zip/writer.go` の変更

`Writer` 構造体の `Close()` メソッド内で、中央ディレクトリヘッダーを書き込む際の条件が変更されました。
`if h.isZip64() || h.offset > uint32max`
から
`if h.isZip64() || h.offset >= uint32max`
に変更されています。
これも `struct.go` と同様に、オフセットが `uint32max` と**等しい**場合にもZIP64ヘッダーが必要であることを保証するための変更です。

### `src/archive/zip/zip_test.go` の変更

テストファイルには、これらの修正を検証するための重要な変更が加えられました。

1.  **`TestZip64EdgeCase` の追加**:
    この新しいテストは、非圧縮サイズが `1<<32 - 1` (すなわち `0xFFFFFFFF`) のファイルを特別にテストします。これは、Go 1.5以前のバージョンがこのエッジケースを誤って処理し、不正なZIPファイルを書き出していた問題を修正するためのものです。このテストは、`0xFFFFFFFF` が32ビットフィールドに収まる値であっても、ZIP64ヘッダーが正しく使用されることを確認します。

2.  **`testZip64` 関数の改善**:
    `testZip64` 関数は、指定されたサイズのファイルをZIPアーカイブに書き込み、その後読み込んで検証するヘルパー関数です。
    *   `size` 引数に基づいて、`chunkSize` で割り切れない端数（`frag`）も正しく書き込まれるように修正されました。
    *   検証部分で、`f0.UncompressedSize` の比較が `size == 1<<32` から `size+int64(len("END\\n")) >= 1<<32-1` に変更され、`uint32max` との比較が `Errorf` メッセージで16進数 (`%#x`) を使用するように改善されました。これにより、`0xFFFFFFFF` のエッジケースがより正確に検証されます。

3.  **Extraフィールドパースのテスト改善**:
    *   `TestHeaderInvalidTagAndSize` と `TestHeaderTooShort` は、以前は `testInvalidHeader` を呼び出してエラーを期待していましたが、`testValidHeader` を呼び出すように変更されました。これは、Extraフィールドのパースがより寛容になったため、これらのケースでもエラーではなく、有効なヘッダーとして扱われるべきであることを反映しています。
    *   `TestHeaderIgnoredSize` が追加されました。これは、不正なサイズを持つZIP64 Extraフィールドが、必要な情報が32ビットフィールドに存在しない限り、無視されることを検証します。

## コアとなるコードの変更箇所

*   `src/archive/zip/reader.go`: ZIP64 Extraフィールドのパースロジックと、Extraフィールド全体の堅牢性を向上。
*   `src/archive/zip/struct.go`: `isZip64()` メソッドの比較演算子を修正。
*   `src/archive/zip/writer.go`: 中央ディレクトリヘッダー書き込み時の条件を修正。
*   `src/archive/zip/zip_test.go`: ZIP64のエッジケースとExtraフィールドのパースに関するテストを追加・修正。

## コアとなるコードの解説

### `src/archive/zip/reader.go` の変更点詳細

```go
 // ... (前略) ...

 	needUSize := f.UncompressedSize == ^uint32(0)
 	needCSize := f.CompressedSize == ^uint32(0)
 	needHeaderOffset := f.headerOffset == int64(^uint32(0))

 	if len(f.Extra) > 0 {
 		// Best effort to find what we need.
 		// Other zip authors might not even follow the basic format,
 		// and we'll just ignore the Extra content in that case.
 		b := readBuf(f.Extra)
 		for len(b) >= 4 { // need at least tag and size
 			tag := b.uint16()
 			size := b.uint16()
 			if int(size) > len(b) {
-				return ErrFormat // 以前はここでエラーを返していた
+				break // 残りのExtraフィールドのパースを中断し、エラーを回避
 			}
 			if tag == zip64ExtraId {
 				// update directory values from the zip64 extra block.
 				// They should only be consulted if the sizes read earlier
 				// are maxed out.
 				// See golang.org/issue/13367.
 				eb := readBuf(b[:size])

 				if needUSize {
 					needUSize = false
 					if len(eb) < 8 {
 						return ErrFormat
 					}
 					f.UncompressedSize64 = eb.uint64()
 				}
 				if needCSize {
 					needCSize = false
 					if len(eb) < 8 {
 						return ErrFormat
 					}
 					f.CompressedSize64 = eb.uint64()
 				}
 				if needHeaderOffset {
 					needHeaderOffset = false
 					if len(eb) < 8 {
 						return ErrFormat
 					}
 					f.headerOffset = int64(eb.uint64())
 				}
 				break // ZIP64 Extraフィールドが見つかったら、それ以上探す必要はない
 			}
 			b = b[size:]
 		}
-		// ... (以前のExtraフィールドのゼロパディングチェックは削除) ...
 	}

 	if needUSize || needCSize || needHeaderOffset {
 		return ErrFormat // 必要な64ビット情報が見つからなかった場合はエラー
 	}

 	return nil
 }
```

このコードスニペットは、`readDirectoryHeader` 関数におけるZIP64 Extraフィールドの処理の核心を示しています。

*   `needUSize`, `needCSize`, `needHeaderOffset` の各フラグは、32ビットのサイズ/オフセットフィールドが `0xFFFFFFFF` であるかどうかを追跡します。これが `true` の場合、対応する64ビット値がZIP64 Extraフィールドから読み取られる必要があります。
*   Extraフィールドをループで処理する際、`if int(size) > len(b)` の条件で `break` を使用することで、不正なExtraフィールドブロックが検出されても、残りのExtraフィールドのパースを試み、全体のエラーを回避します。これはIssue #13166への対応です。
*   `tag == zip64ExtraId` のブロック内では、`needUSize` などのフラグが `true` の場合にのみ、対応する64ビット値を読み込みます。これにより、Issue #13367で指摘された、不要なZIP64 Extraフィールドのパースによるエラーを防ぎます。
*   ループの最後に `if needUSize || needCSize || needHeaderOffset` のチェックを追加することで、`0xFFFFFFFF` が設定されているにもかかわらず、対応する64ビット値がZIP64 Extraフィールドから見つからなかった場合にのみ `ErrFormat` を返します。これにより、必要な情報が欠落している場合にのみエラーを報告し、それ以外の場合は寛容なパースを維持します。

### `src/archive/zip/struct.go` と `src/archive/zip/writer.go` の変更点詳細

`isZip64()` メソッドと `Writer.Close()` メソッドにおける `uint32max` との比較が `>` から `>=` に変更されたことは、`0xFFFFFFFF` という値自体がZIP64フォーマットを必要とするマジックマーカーであるというZIP仕様の厳密な解釈に基づいています。これにより、サイズがちょうど `0xFFFFFFFF` のファイルが正しくZIP64として扱われ、互換性のあるZIPファイルが生成されるようになります。

# [インデックス 21342] ファイルの概要

このコミットは、Goランタイムにおけるスタックフレームの管理方法に重要な変更を加えています。特に、`go`ステートメントや`defer`ステートメントに関連するプロシージャ（`goproc`および`deferproc`）の呼び出しにおいて、スタックフレームのサイズを固定化し、スタックポインタ（SP）の操作を簡素化することを目的としています。これにより、デファースタックのウォーク処理や、将来的なスタックウォークコードの簡素化への道を開いています。

## 元コミット内容

Goランタイムにおいて、`goproc`（新しいゴルーチンを開始する際に呼び出される）および`deferproc`（`defer`ステートメントを処理する際に呼び出される）への呼び出しは、以前は引数のサイズと呼び出す関数という2つの追加引数をスタックにプッシュ・ポップしていました。このコミットでは、これらの引数に対して`outargs`セクションにスペースを事前に割り当てることで、スタックポインタ（SP）を動的に変更する必要がなくなりました。

また、`defer`は、関連するスタックフレームを識別するために、引数ポインタ（AP）ではなくスタックポインタ（SP）を使用するように変更されました。これにより、スタックフレームのサイズが固定化され、将来的に`funcspdelta`やスタックウォークコードの簡素化に繋がる可能性が示唆されています。

## 変更の背景

Goランタイムでは、効率的なメモリ管理とスタックの利用が非常に重要です。特に、ゴルーチンの生成や`defer`関数の実行は頻繁に行われる操作であり、これらのオーバーヘッドを最小限に抑えることが求められます。

従来の`goproc`/`deferproc`の呼び出しでは、引数のサイズと関数ポインタをスタックに動的にプッシュ・ポップしていました。この動的なスタック操作は、スタックフレームのサイズを可変にし、スタックウォーク（デバッガやプロファイラがスタックトレースを生成するためにスタックを辿る処理）を複雑にする要因となっていました。スタックウォークの正確性と効率性は、デバッグやプロファイリングのパフォーマンスに直結するため、この複雑さを解消することが望まれました。

このコミットの主な目的は、以下の課題を解決することにあります。

1.  **スタックフレームサイズの固定化**: `goproc`/`deferproc`呼び出しにおけるスタック操作を簡素化し、スタックフレームのサイズを予測可能にすることで、スタックウォークのロジックを単純化します。
2.  **スタックポインタの安定化**: 動的なプッシュ・ポップを排除することで、スタックポインタ（SP）がより安定し、デファースタックの管理やスタックトレースの生成が容易になります。
3.  **デファースタックの識別精度の向上**: `defer`が関連するスタックフレームを識別する際に、引数ポインタ（AP）ではなくスタックポインタ（SP）を使用することで、より堅牢な関連付けが可能になります。これは、スタックが成長・縮小する際にAPが変動する可能性があるのに対し、SPはフレームの基点としてより安定しているためです。

これらの変更は、Goランタイムの堅牢性とパフォーマンスを向上させ、将来的な最適化やデバッグツールの開発を容易にするための基盤となります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびコンパイラの基本的な概念を理解しておく必要があります。

*   **スタックフレーム (Stack Frame)**: 関数が呼び出されるたびに、その関数のローカル変数、引数、戻りアドレスなどを格納するためにスタック上に確保されるメモリ領域です。
*   **スタックポインタ (Stack Pointer, SP)**: 現在のスタックの最上位（または最下位、アーキテクチャによる）を指すレジスタです。関数呼び出しやローカル変数の確保によって値が変化します。
*   **引数ポインタ (Argument Pointer, AP)**: 関数の引数が格納されているスタック上の位置を指すポインタです。Goの特定のコンテキストでは、引数領域の開始位置を指すために使用されることがあります。
*   **`goproc`**: Goランタイム内部で、新しいゴルーチンを起動する際に呼び出される関数です。新しいゴルーチンのスタックをセットアップし、実行を開始します。
*   **`deferproc`**: Goランタイム内部で、`defer`ステートメントが実行される際に呼び出される関数です。`defer`された関数とその引数をデファースタックに登録します。
*   **`_defer`構造体**: `defer`された関数の情報（関数ポインタ、引数サイズ、関連するスタックフレームのポインタなど）を保持するランタイム内部のデータ構造です。
*   **`funcval`**: Goの関数を表すランタイム内部の構造体で、関数コードへのポインタなどを含みます。
*   **`setmaxarg`**: コンパイラが関数の引数領域の最大サイズを計算・設定する関数です。
*   **`adjustargs`**: `go`や`defer`呼び出しの引数位置を調整するコンパイラ内部の関数です。
*   **`ggen.c` (5g, 6g, 8g, 9g)**: Goコンパイラのバックエンドコードの一部で、それぞれ異なるCPUアーキテクチャ（5g: ARM, 6g: x86-64, 8g: x86-32, 9g: PowerPC）向けのアセンブリコード生成を担当します。これらのファイルは、関数呼び出し規約やスタックフレームのレイアウトに密接に関連しています。
*   **`src/runtime/panic.go`, `src/runtime/panic1.go`**: `panic`や`defer`、`recover`といった例外処理に関連するGoランタイムのコードが含まれています。
*   **`src/runtime/traceback.go`**: スタックトレースの生成（スタックウォーク）に関連するGoランタイムのコードが含まれています。

## 技術的詳細

このコミットの核心は、`goproc`および`deferproc`への呼び出し規約を変更し、スタックフレームのレイアウトを固定化することにあります。

**変更前**:
`goproc`や`deferproc`を呼び出す際、呼び出し元は引数として「引数のサイズ」と「呼び出す関数（`funcval`）」をスタックにプッシュしていました。これらの引数は、通常の関数引数とは別に、動的にスタックに積まれていました。これにより、スタックポインタ（SP）が一時的に変動し、スタックフレームのサイズが可変になっていました。また、`_defer`構造体は、関連するスタックフレームを`argp`（引数ポインタ）で識別していました。

**変更後**:
1.  **`outargs`セクションへの事前割り当て**: `goproc`および`deferproc`に渡される「引数のサイズ」と「呼び出す関数」の2つの追加引数は、もはや動的にスタックにプッシュされません。代わりに、これらの引数分のスペースが、呼び出し元の関数の`outargs`セクション（呼び出す関数の引数を格納する領域）に事前に割り当てられるようになりました。これにより、`goproc`/`deferproc`呼び出し時にSPを動的に変更する必要がなくなり、スタックフレームのサイズが固定化されます。
    *   コンパイラのバックエンド（`src/cmd/*/ggen.c`）で、`setmaxarg`関数に`extra`引数が追加され、`goproc`や`deferproc`呼び出しの場合に`2 * widthptr`（ポインタサイズの2倍、つまり引数サイズと関数ポインタの分）の追加スペースを考慮するようになりました。
    *   `adjustargs`関数が`src/cmd/gc/walk.c`に追加され、`go`および`defer`ノードの引数位置を`2 * widthptr`分調整するようになりました。これは、これらの追加引数分のスペースが`outargs`セクションに確保されることを反映しています。
2.  **`_defer`構造体の変更**: `_defer`構造体の`argp`フィールドが`sp`フィールドに変更されました。これは、`defer`が関連するスタックフレームを識別するために、引数ポインタ（`argp`）ではなく、より安定したスタックポインタ（`sp`、つまり`deferproc`が呼び出された時点のSP）を使用するようになったことを意味します。
    *   `src/runtime/runtime2.go`で`_defer`構造体が変更されました。
    *   `src/runtime/panic.go`、`src/runtime/panic1.go`、`src/runtime/heapdump.go`、`src/runtime/stack1.go`、`src/runtime/traceback.go`など、`_defer`構造体を参照する多くのランタイムファイルで、`d.argp`が`d.sp`に置き換えられました。
3.  **スタックウォークの簡素化**: `src/runtime/traceback.go`におけるスタックウォークのロジックが簡素化されました。特に、`newprocPC`や`deferprocPC`に関連する特別なSP調整ロジックが削除され、`wasnewproc`フラグも不要になりました。これは、スタックフレームが固定サイズになったことと、`defer`がSPでフレームを識別するようになったことによる直接的な恩恵です。

これらの変更により、Goランタイムはより予測可能で効率的なスタック管理を実現し、デバッグやプロファイリングの精度向上に貢献します。

    *   `_defer`構造体の`argp`フィールドへの参照が`sp`フィールドへの参照に更新されました。

## コアとなるコードの解説

このコミットの最も重要な変更は、`goproc`と`deferproc`への呼び出しにおける引数の渡し方と、`_defer`構造体におけるスタックフレームの識別の方法です。

**コンパイラ側 (`src/cmd/*/ggen.c` と `src/cmd/gc/walk.c`)**:

以前は、`go`や`defer`の呼び出しは、通常の関数呼び出しとは異なり、引数サイズと関数ポインタをスタックに動的にプッシュしていました。例えば、`src/cmd/5g/ggen.c`の`ginscall`関数では、以下のようなコードがありました（削除された部分を抜粋）：

```c
// 以前のコード (削除された部分)
// 引数サイズをプッシュ
p = gins(AMOVW, &con, &r);
p = gins(AMOVW, &r, N);
p->to.type = D_OREG;
p->to.reg = REGSP;
p->to.offset = 4; // SP+4に引数サイズを格納

// 関数ポインタをプッシュ
p = gins(AMOVW, &r, N);
p->to.type = D_OREG;
p->to.reg = REGSP;
p->to.offset = 8; // SP+8に関数ポインタを格納
```

このコミットでは、これらの動的なプッシュ操作が削除され、代わりに`setmaxarg`関数に`extra`引数を追加し、`adjustargs`関数で引数位置を調整することで、これらの引数分のスペースを`outargs`セクションに事前に確保するようにしました。これにより、`goproc`/`deferproc`が呼び出される際には、これらの引数が既にスタック上の固定位置に存在するため、SPを動的に操作する必要がなくなります。

例えば、`src/cmd/5g/ggen.c`の変更では、`ginscall`内で`setmaxarg(f->type, extra)`が呼び出され、`extra`が`2 * widthptr`（引数サイズと関数ポインタの合計サイズ）に設定されます。そして、引数サイズと関数ポインタは、SPからのオフセットで直接書き込まれるようになります。

```c
// 新しいコード (src/cmd/5g/ggen.c)
// 引数サイズを0(SP)に格納 (またはSPからのオフセット)
nodconst(&con, types[TINT32], argsize(f->type));
gins(AMOVW, &con, &r);
p = gins(AMOVW, &r, N);
p->to.type = D_OREG;
p->to.reg = REGSP;
p->to.offset = 4; // SP+4に引数サイズを格納 (例: 32bitアーキテクチャ)

// FuncVal* をwidthptr(SP)に格納
memset(&n1, 0, sizeof n1);
n1.op = OADDR;
n1.left = f;
gins(AMOVW, &n1, &r);
p = gins(AMOVW, &r, N);
p->to.type = D_OREG;
p->to.reg = REGSP;
p->to.offset = 8; // SP+8に関数ポインタを格納 (例: 32bitアーキテクチャ)
```
この変更により、`goproc`/`deferproc`が呼び出される時点では、これらの引数は既にスタック上の固定位置に存在するため、SPを動的に操作する必要がなくなります。

**ランタイム側 (`src/runtime/panic.go` と `src/runtime/runtime2.go`)**:

`_defer`構造体の変更は、`defer`がどのスタックフレームに関連付けられているかを識別する方法に直接影響します。

以前の`_defer`構造体:
```go
type _defer struct {
    // ...
    argp    uintptr // where args were copied from
    // ...
}
```

新しい`_defer`構造体:
```go
type _defer struct {
    // ...
    sp      uintptr // sp at time of defer
    // ...
}
```

この変更により、`deferproc`や`deferreturn`、`gopanic`などの関数では、`d.argp`の代わりに`d.sp`を使用して、デファースタック上のエントリがどのスタックフレームに対応するかを判断するようになりました。`argp`は引数領域の開始を指すため、スタックの変動によって相対的な位置が変わる可能性がありましたが、`sp`は`deferproc`が呼び出された時点のスタックポインタの値を直接保持するため、より安定したフレーム識別子となります。

例えば、`src/runtime/panic.go`の`deferproc`関数では、`argp`の計算が削除され、代わりに`sp := getcallersp(unsafe.Pointer(&siz))`によって現在のSPを取得し、これを`d.sp`に格納するようになりました。

```go
// src/runtime/panic.go の deferproc 関数 (変更後)
// sp := getcallersp(unsafe.Pointer(&siz))
// d.sp = sp
```

これらの変更は、Goランタイムのスタック管理をより堅牢にし、スタックウォークの正確性を向上させるための重要なステップです。

# [インデックス 20661] ファイルの概要

このコミットは、Go言語の`math`パッケージ内の`Sincos`関数のAMD64アセンブリ実装におけるバグを修正するものです。具体的には、浮動小数点演算モード、特に「非正規化数をゼロとして扱う（denormals are zero）」モードが有効な環境下で、`Sincos`関数が誤った結果を返す問題を解決します。元のコードが条件分岐を避けるために巧妙な浮動小数点比較（`CMPSD`命令）を使用していたことが原因で、意図せず非正規化数を生成し、その処理が環境に依存してしまったため、これを浮動小数点モードに依存しない整数演算に置き換えることで堅牢性を高めています。

## コミット

```
math: avoid assumption of denormalized math mode in Sincos

The extra-clever code in Sincos is trying to do

        if v&2 == 0 {
                mask = 0xffffffffffffffff
        } else {
                mask = 0
        }

It does this by turning v&2 into a float64 X0 and then using

        MOVSD $0.0, X3
        CMPSD X0, X3, 0

That CMPSD is defined to behave like:

        if X0 == X3 {
                X3 = 0xffffffffffffffff
        } else {
                X3 = 0
        }

which gives the desired mask in X3. The goal in using the
CMPSD was to avoid a conditional branch.

This code fails when called from a PortAudio callback.
In particular, the failure behavior is exactly as if the
CMPSD always chose the 'true' execution.

Notice that the comparison X0 == X3 is comparing as
floating point values the 64-bit pattern v&2 and the actual
floating point value zero. The only possible values for v&2
are 0x0000000000000000 (floating point zero)
and 0x0000000000000002 (floating point 1e-323, a denormal).
If they are both comparing equal to zero, I conclude that
in a PortAudio callback (whatever that means), the processor
is running in "denormals are zero" mode.

I confirmed this by placing the processor into that mode
and running the test case in the bug; it produces the
incorrect output reported in the bug.

In general, if a Go program changes the floating point math
modes to something other than what Go expects, the math
library is not going to work exactly as intended, so we might
be justified in not fixing this at all.

However, it seems reasonable that the client code might
have expected "denormals are zero" mode to only affect
actual processing of denormals. This code has produced
what is in effect a gratuitous denormal by being extra clever.
There is nothing about the computation being requested
that fundamentally requires a denormal.

It is also easy to do this computation in integer math instead:

        mask = ((v&2)>>1)-1

Do that.

For the record, the other math tests that fail if you put the
processor in "denormals are zero" mode are the tests for
Frexp, Ilogb, Ldexp, Logb, Log2, and FloatMinMax, but all
fail processing denormal inputs. Sincos was the only function
for which that mode causes incorrect behavior on non-denormal inputs.

The existing tests check that the new assembly is correct.
There is no test for behavior in "denormals are zero" mode,
because I don't want to add assembly to change that.

Fixes #8623.

LGTM=josharian
R=golang-codereviews, josharian
CC=golang-codereviews, iant, r
https://golang.org/cl/151750043
```

## 変更の背景

このコミットは、Go言語の`math`パッケージに含まれる`Sincos`関数のAMD64アセンブリ実装における、浮動小数点演算の予期せぬ振る舞いを修正するために行われました。

問題の根源は、`Sincos`関数内で特定のマスク値を生成するために、条件分岐を避ける目的で「巧妙な」浮動小数点比較（`CMPSD`命令）が使用されていたことにあります。この比較は、整数値`v&2`を浮動小数点数に変換し、それを`0.0`と比較するというものでした。

ここで問題となるのは、`v&2`の結果が`2`である場合、これを64ビット浮動小数点数（`float64`）に変換すると、非常に小さい非正規化数（約`1e-323`）となる点です。多くのCPUには、パフォーマンス向上のために「非正規化数をゼロとして扱う（denormals are zero, DAZ）」というモードが存在します。このモードが有効な環境（例えば、PortAudioのようなリアルタイムオーディオ処理のコールバック内）では、`1e-323`のような非正規化数が強制的に`0`として扱われてしまいます。

その結果、`CMPSD`命令による比較（`1e-323`と`0.0`の比較）が、DAZモード下では常に「等しい」と評価され、意図しないマスク値（常に`0xffffffffffffffff`）が生成されていました。これにより、`Sincos`関数は誤った計算結果を返し、バグとして報告されました（Go issue #8623）。

この変更の目的は、このような特定の浮動小数点演算モードに依存しない、より堅牢なマスク生成ロジックを導入することです。元のコードは、計算の本質的な要件として非正規化数を必要としていなかったため、浮動小数点演算を介さずに整数演算で同じマスクを生成するように修正されました。

## 前提知識の解説

### 浮動小数点数とIEEE 754標準

コンピュータにおける浮動小数点数は、実数を近似的に表現するための形式です。ほとんどのシステムでは、IEEE 754標準に従って表現されます。この標準では、数を符号部、指数部、仮数部（または有効数字部）に分けて表現します。

*   **正規化数 (Normalized Numbers)**: 通常の浮動小数点数で、仮数部の最上位ビットが常に1であると暗黙的に仮定されます。これにより、表現できる精度が最大化されます。
*   **非正規化数 (Denormalized Numbers / Subnormal Numbers)**: ゼロに非常に近い値を表現するために使用される特殊な浮動小数点数です。指数部が最小値を取り、仮数部の最上位ビットが0である点が正規化数と異なります。これにより、ゼロの周りのギャップを埋め、アンダーフロー（表現可能な最小値よりも小さい値になること）が発生しても、より小さな値を表現できるようになります。しかし、非正規化数の演算は、ハードウェアによっては正規化数よりも大幅に遅くなることがあります。

### 「非正規化数をゼロとして扱う (Denormals Are Zero, DAZ)」モード

DAZモードは、CPUの浮動小数点演算ユニット（FPU）が持つ設定の一つです。このモードが有効な場合、FPUは非正規化数を入力として受け取った際に、それを強制的にゼロとして扱います。また、演算結果が非正規化数になる場合も、それをゼロに切り詰めます。

DAZモードの主な目的は、非正規化数の処理に伴う性能低下を回避することです。非正規化数の処理は、FPUのパイプラインを停止させたり、特別なマイクロコードを実行したりする必要があるため、パフォーマンスに悪影響を与えることがあります。DAZモードは、このような性能ペナルティを回避し、浮動小数点演算のスループットを向上させますが、その代償として、ゼロに近い値の精度が失われる可能性があります。

### `CMPSD` 命令 (Compare Scalar Double-Precision Floating-Point Value)

`CMPSD`は、x86-64アーキテクチャのSSE（Streaming SIMD Extensions）命令セットに含まれる命令で、2つの64ビット倍精度浮動小数点数（`double`型）を比較するために使用されます。

この命令は、比較結果をブール値（真/偽）として返すのではなく、比較結果に基づいて64ビットのマスク値を生成します。具体的には、比較が真であれば宛先レジスタの対応する部分を全て1（`0xffffffffffffffff`）で埋め、偽であれば全て0（`0x0000000000000000`）で埋めます。この特性は、条件分岐を避けたい場合に、マスク値を用いたビット演算で条件付き処理を実装するのに利用されることがあります。

### PortAudio コールバック

PortAudioは、クロスプラットフォームのオーディオI/Oライブラリです。PortAudioのストリーム処理では、`PaStreamCallback`というコールバック関数が使用されます。このコールバック関数は、リアルタイムでオーディオデータを処理するために、非常に厳格な制約の下で実行されます。

*   **リアルタイムコンテキスト**: コールバックは、通常、OSのリアルタイムスレッドや高優先度スレッドで実行されます。
*   **厳格な制約**: コールバック内では、メモリ割り当て/解放（`malloc`/`free`）、ファイルI/O、コンソール出力（`printf`）、ほとんどのOSサービス呼び出し、GUI操作など、時間が予測できない、またはブロックする可能性のある操作は厳しく禁止されています。
*   **浮動小数点演算モード**: 一部のオーディオアプリケーションやライブラリは、パフォーマンス上の理由から、FPUの浮動小数点演算モード（例: DAZモード）を変更することがあります。このような環境でGoの数学関数が呼び出されると、Goが想定していない浮動小数点モードで動作することになり、予期せぬ結果を招く可能性があります。

### Goの`math`パッケージとアセンブリ言語

Go言語の標準ライブラリである`math`パッケージは、三角関数、指数関数、対数関数など、基本的な数学関数を提供します。これらの関数の一部、特にパフォーマンスが重要となる部分は、Go言語自体ではなく、プラットフォーム固有のアセンブリ言語で実装されています（例: `src/math/sincos_amd64.s`）。これは、特定のCPU命令セットの最適化を利用して、最高の性能と精度を達成するためです。

## 技術的詳細

このコミットで修正された問題は、`Sincos`関数のアセンブリ実装が、特定のマスク値を生成する際に、浮動小数点演算の副作用に依存していたことに起因します。

元のコードは、`v&2`という整数演算の結果（`0`または`2`）を基に、`mask`を`0xffffffffffffffff`または`0`に設定しようとしていました。これを実現するために、以下のようなアセンブリ命令が使われていました。

1.  `v&2`の結果を`DX`レジスタに格納。
2.  `DX`レジスタの値を浮動小数点レジスタ`X0`に移動（`MOVQ DX, X0`）。この際、整数値`2`は64ビット浮動小数点数`1e-323`（非正規化数）として表現されます。整数値`0`は浮動小数点数`0.0`として表現されます。
3.  浮動小数点レジスタ`X3`に`0.0`をロード（`MOVSD $0.0, X3`）。
4.  `X0`と`X3`を`CMPSD X0, X3, 0`命令で比較。この命令は、`X0 == X3`が真であれば`X3`を`0xffffffffffffffff`に、偽であれば`0`に設定します。

問題は、CPUが「非正規化数をゼロとして扱う（DAZ）」モードで動作している場合に発生しました。このモードでは、`X0`に格納された非正規化数`1e-323`が`0.0`として扱われます。その結果、`CMPSD`命令は常に`X0 == X3`（つまり`0.0 == 0.0`）が真であると判断し、`X3`（マスク）が常に`0xffffffffffffffff`に設定されてしまいました。これは、`v&2`が`0`の場合にマスクが`0`になるという本来の意図に反するものでした。

この問題を解決するため、コミットではマスク生成ロジックを浮動小数点演算から純粋な整数演算に置き換えました。新しいロジックは以下の通りです。

`mask = ((v&2)>>1)-1`

この整数演算は、`v&2`が`0`の場合と`2`の場合で、それぞれ以下のように機能します。

*   `v&2`が`0`の場合:
    *   `((0)>>1)-1`
    *   `(0)-1`
    *   結果: `-1` (64ビット整数では`0xffffffffffffffff`)
*   `v&2`が`2`の場合:
    *   `((2)>>1)-1`
    *   `(1)-1`
    *   結果: `0`

このように、整数演算を用いることで、CPUの浮動小数点モードに依存することなく、常に意図したマスク値（`0xffffffffffffffff`または`0`）を正確に生成できるようになりました。これにより、PortAudioコールバックのような、浮動小数点モードが変更される可能性のある環境でも`Sincos`関数が正しく動作することが保証されます。

## コアとなるコードの解説

変更されたアセンブリコードは、`Sincos`関数内で`sin`と`cos`の値を入れ替えるべきかどうかを決定するためのマスクを生成する部分です。

**変更前のアセンブリコード:**

```assembly
	MOVQ    $1, DX
	ADDQ    BX, DX
	MOVQ    $2, AX
	ANDQ    AX, DX    // DX = (BX + 1) & 2
	MOVQ    DX, X0    // DX (integer) to X0 (float64)
	MOVSD   $0.0, X3  // X3 = 0.0
	CMPSD   X0, X3, 0 // Compare X0 and X3 for equality, result mask in X3
```

1.  `MOVQ $1, DX`: `DX`レジスタに整数値`1`をロードします。
2.  `ADDQ BX, DX`: `BX`レジスタの値（おそらく`q`という変数）を`DX`に加算します。これで`DX`は`q + 1`になります。
3.  `MOVQ $2, AX`: `AX`レジスタに整数値`2`をロードします。
4.  `ANDQ AX, DX`: `DX`と`AX`のビットAND演算を行い、結果を`DX`に格納します。これにより`DX`は`(q + 1) & 2`となります。この結果は`0`または`2`のいずれかです。
5.  `MOVQ DX, X0`: `DX`レジスタの整数値を浮動小数点レジスタ`X0`に移動します。ここで、整数値`2`が浮動小数点数`1e-323`（非正規化数）に変換されることが問題でした。
6.  `MOVSD $0.0, X3`: 浮動小数点レジスタ`X3`に`0.0`をロードします。
7.  `CMPSD X0, X3, 0`: `X0`と`X3`を比較します（比較タイプ`0`は等価比較）。比較結果に基づいて、`X3`に`0xffffffffffffffff`（真の場合）または`0x0000000000000000`（偽の場合）のマスクが生成されます。

**変更後のアセンブリコード:**

```assembly
	MOVQ    $1, DX
	ADDQ    BX, DX
	ANDQ    $2, DX    // DX = (BX + 1) & 2
	SHRQ    $1, DX    // DX = ((BX + 1) & 2) >> 1
	SUBQ	$1, DX    // DX = (((BX + 1) & 2) >> 1) - 1
	MOVQ    DX, X3    // DX (integer) to X3 (float64, but now it's a mask)
```

1.  `MOVQ $1, DX`: `DX`レジスタに整数値`1`をロードします。
2.  `ADDQ BX, DX`: `BX`レジスタの値（`q`）を`DX`に加算します。これで`DX`は`q + 1`になります。
3.  `ANDQ $2, DX`: `DX`と即値`2`のビットAND演算を行い、結果を`DX`に格納します。これにより`DX`は`(q + 1) & 2`となります。この結果は`0`または`2`のいずれかです。
4.  `SHRQ $1, DX`: `DX`の値を右に1ビットシフトします。
    *   `DX`が`0`の場合: `0 >> 1`は`0`。
    *   `DX`が`2`の場合: `2 >> 1`は`1`。
    これで`DX`は`0`または`1`のいずれかになります。
5.  `SUBQ $1, DX`: `DX`から即値`1`を減算します。
    *   `DX`が`0`の場合: `0 - 1`は`-1`（64ビット整数では`0xffffffffffffffff`）。
    *   `DX`が`1`の場合: `1 - 1`は`0`。
    これで`DX`は`0xffffffffffffffff`または`0`のいずれかになります。これは、浮動小数点比較で生成しようとしていたマスク値と全く同じです。
6.  `MOVQ DX, X3`: `DX`レジスタの整数値を浮動小数点レジスタ`X3`に移動します。この`X3`が、後続の`ANDPD`命令などでマスクとして使用されます。

この変更により、浮動小数点演算や`CMPSD`命令が完全に排除され、マスク生成が純粋な整数演算で行われるようになりました。これにより、CPUの浮動小数点モード（特にDAZモード）の影響を受けることなく、常に正しいマスク値が生成されることが保証されます。

## 変更の背景

このコミットは、主にGoの`net/http`パッケージにおけるリクエストキャンセル処理の堅牢性を向上させることを目的としています。

1.  **`Request.Cancel`チャネルによるミッドボディキャンセルテストの追加**:
    Go 1.7で`context.Context`が導入される以前は、`http.Request`構造体の`Cancel`フィールドに`chan struct{}`を設定することで、クライアント側からリクエストをキャンセルするメカニズムが提供されていました。しかし、レスポンスボディの読み取り中にこのチャネルをクローズした場合に、HTTPクライアントがそのキャンセルを適切に検知し、ボディの読み取りを中断してエラーを返すかどうかが不明確でした。Issue #13159は、このシナリオにおける挙動の不備や未定義な状態を指摘していたと考えられます。このコミットでは、この重要なユースケース（レスポンスボディの途中でのキャンセル）がHTTP/1.1とHTTP/2の両方で正しく機能することを保証するためのテストが追加されました。これにより、不要なリソース消費を防ぎ、クライアントアプリケーションがより予測可能な挙動を示すようになります。

2.  **バンドルされたHTTP/2パッケージの更新**:
    Goの`net/http`パッケージは、HTTP/2プロトコルを内部的にサポートするために、HTTP/2のコードをバンドルしています。このコミットでは、`https://golang.org/cl/17757`で提供されたHTTP/2に関する修正がこのバンドルコードに組み込まれました。この修正は、おそらく上記の`Request.Cancel`によるミッドボディキャンセルをHTTP/2ストリームで適切に処理するためのもので、HTTP/2のストリームベースの性質とキャンセルの同期を改善することを目的としています。

これらの変更により、GoのHTTPクライアントは、特にネットワークの不安定な状況やタイムアウトが発生しやすい環境において、より信頼性の高いリクエストキャンセル処理を提供できるようになりました。

## 前提知識の解説

### Goの`net/http`パッケージ
Go言語の標準ライブラリである`net/http`パッケージは、HTTPクライアントとサーバーの実装を提供します。ウェブアプリケーションの構築やHTTPリクエストの送信に広く利用されます。

### `http.Request.Cancel` (チャネルベースのキャンセル)
Go 1.7で`context.Context`が導入される以前、`http.Request`には`Cancel chan struct{}`というフィールドがありました。このチャネルをクローズすることで、進行中のHTTPリクエストをキャンセルするシグナルを送ることができました。クライアントは、このチャネルがクローズされたことを検知すると、リクエストの送信やレスポンスの受信を中断し、エラーを返すことが期待されていました。このコミットは、この古いキャンセルメカニズムがレスポンスボディの読み取り中にどのように機能するかを扱っています。

### HTTP/1.1とHTTP/2
-   **HTTP/1.1**: 広く普及しているHTTPプロトコルのバージョン。リクエストとレスポンスは通常、1つのTCP接続上で順番に処理されます（パイプライン化はありますが、ヘッドオブラインブロッキングの問題があります）。
-   **HTTP/2**: HTTP/1.1のパフォーマンス上の制約を克服するために設計された新しいプロトコル。単一のTCP接続上で複数のリクエストとレスポンスを同時に多重化（multiplexing）できる「ストリーム」の概念を導入しています。これにより、ヘッドオブラインブロッキングが解消され、より効率的な通信が可能になります。

### `io.Reader`と`io.Writer`
GoにおけるI/O操作の基本的なインターフェースです。
-   `io.Reader`: `Read(p []byte) (n int, err error)`メソッドを持ち、データソースからバイトを読み取ります。
-   `io.Writer`: `Write(p []byte) (n int, err error)`メソッドを持ち、データシンクにバイトを書き込みます。
HTTPレスポンスボディは`io.Reader`として提供され、クライアントはこれを通じてレスポンスデータを読み取ります。

### `sync.Cond`
Goの`sync`パッケージに含まれる条件変数です。`sync.Mutex`と組み合わせて使用され、特定の条件が満たされるまでゴルーチンを待機させたり、条件が満たされたときに待機中のゴルーチンに通知したりするために使われます。`c.L`フィールドは`sync.Locker`インターフェース（通常は`*sync.Mutex`）を指します。

### `chan struct{}`
Goでイベント通知や同期によく使われる、要素を持たないチャネルです。要素がないためメモリを消費せず、チャネルのクローズによって複数の受信ゴルーチンに同時に通知できる特性があります。

## 技術的詳細

このコミットの技術的詳細は、`Request.Cancel`チャネルによるミッドボディキャンセルをHTTP/1.1とHTTP/2の両方で確実に機能させるための変更に集約されます。

### `clientserver_test.go`におけるテストの追加
`testCancelRequestMidBody`関数は、以下の手順でミッドボディキャンセルをテストします。
1.  **サーバーのセットアップ**: サーバーは、まず"Hello"という文字列を書き込み、`Flush()`を呼び出してクライアントに送信します。その後、`unblock`チャネルからの信号を待ちます。
2.  **クライアントのリクエスト**: クライアントはサーバーにGETリクエストを送信します。このリクエストには、キャンセル用の`cancel`チャネルが設定されています。
3.  **部分的なボディ読み取りとキャンセル**: クライアントはサーバーから"Hello"を受け取った後、`cancel`チャネルをクローズしてリクエストをキャンセルします。
4.  **キャンセル後のボディ読み取り**: クライアントは残りのレスポンスボディを読み取ろうとしますが、この時点でキャンセルが有効になっているため、`ExportErrRequestCanceled`エラーが返されることを期待します。また、読み取られたボディが"Hello"のみであることを確認します。
このテストは、HTTP/1.1 (`h1Mode`) とHTTP/2 (`h2Mode`) の両方で実行され、プロトコルに依存しない一貫したキャンセル挙動を保証します。

### `h2_bundle.go`におけるHTTP/2のキャンセル処理の強化
HTTP/2はストリームベースのプロトコルであるため、キャンセル処理はHTTP/1.1とは異なるアプローチが必要です。このコミットでは、HTTP/2の内部実装に以下の変更が加えられました。

1.  **`http2pipe`構造体の拡張**:
    -   `donec chan struct{}`フィールドが追加されました。これは、`http2pipe`がエラーでクローズされたときに通知するためのチャネルです。
    -   `CloseWithError(err error)`メソッドが、`p.err`が`nil`でない場合に`donec`チャネルをクローズするように変更されました。これにより、パイプのクローズイベントを待機しているゴルーチンに通知されます。
    -   `Done() <-chan struct{}`メソッドが追加されました。このメソッドは`donec`チャネルを返します。これにより、他のゴルーチンが`http2pipe`のクローズを非同期に待機できるようになります。

2.  **`http2clientStream`におけるキャンセル監視**:
    -   `awaitRequestCancel(cancel <-chan struct{})`メソッドが追加されました。このメソッドは新しいゴルーチンで実行されることを想定しており、以下のいずれかのイベントを待ちます。
        -   `cancel`チャネル（`http.Request.Cancel`から渡される）がクローズされる。
        -   `cs.bufPipe.Done()`チャネル（`http2pipe`がクローズされたときに通知される）がクローズされる。
    -   いずれかのイベントが発生した場合、`cs.bufPipe.CloseWithError(http2errRequestCanceled)`を呼び出し、内部のパイプをキャンセルエラーでクローズします。

3.  **`http2clientConn.RoundTrip`におけるキャンセル統合**:
    -   `RoundTrip`メソッド内で、リクエストのヘッダーが送信された後、`req.Cancel`チャネルがクローズされた場合に、`cs.abortRequestBodyWrite()`を呼び出し、`http2errRequestCanceled`を返してリクエストを即座にキャンセルするロジックが追加されました。これは、リクエストボディの送信中にキャンセルが発生した場合の処理です。
    -   レスポンスヘッダーが受信され、`res.Body`が`http2transportResponseBody`として設定された後、`go cs.awaitRequestCancel(cs.req.Cancel)`が起動されます。これにより、レスポンスボディの読み取り中に`Request.Cancel`がクローズされた場合でも、`http2clientStream`がそれを検知し、`http2pipe`をキャンセルエラーでクローズできるようになります。

4.  **`http2errRequestCanceled`の定義**:
    `net/http`パッケージの内部エラー`errRequestCanceled`がエクスポートされていないため、HTTP/2バンドル内で同等のエラー`http2errRequestCanceled`が定義されました。これにより、HTTP/1.1とHTTP/2のキャンセルエラーが`reflect.DeepEqual`で比較可能になり、テストの一貫性が保たれます。

これらの変更により、`Request.Cancel`チャネルがクローズされた際に、HTTP/2の内部ストリームとパイプが適切にクリーンアップされ、クライアントが期待通りにキャンセルエラーを受け取ることが保証されます。

### `src/net/http/clientserver_test.go`
```go
// Tests that closing the Request.Cancel channel also while still
// reading the response body. Issue 13159.
func TestCancelRequestMidBody_h1(t *testing.T) { testCancelRequestMidBody(t, h1Mode) }
func TestCancelRequestMidBody_h2(t *testing.T) { testCancelRequestMidBody(t, h2Mode) }
func testCancelRequestMidBody(t *testing.T, h2 bool) {
	defer afterTest(t)
	unblock := make(chan bool)
	didFlush := make(chan bool, 1)
	cst := newClientServerTest(t, h2, HandlerFunc(func(w ResponseWriter, r *Request) {
		io.WriteString(w, "Hello")
		w.(Flusher).Flush()
		didFlush <- true
		<-unblock
		io.WriteString(w, ", world.")
		<-unblock
	}))
	defer cst.close()
	defer close(unblock)

	req, _ := NewRequest("GET", cst.ts.URL, nil)
	cancel := make(chan struct{})
	req.Cancel = cancel

	res, err := cst.c.Do(req)
	if err != nil {
		t.Fatal(err)
	}
	defer res.Body.Close()
	<-didFlush
	close(cancel)

	slurp, err := ioutil.ReadAll(res.Body)
	if string(slurp) != "Hello" {
		t.Errorf("Read %q; want Hello", slurp)
	}
	if !reflect.DeepEqual(err, ExportErrRequestCanceled) {
		t.Errorf("ReadAll error = %v; want %v", err, ExportErrRequestCanceled)
	}
}
```

### `src/net/http/h2_bundle.go`

#### `http2pipe`構造体と関連メソッドの変更
```go
type http2pipe struct {
	mu    sync.Mutex
	c     sync.Cond // c.L must point to
	b     http2pipeBuffer
	err   error         // read error once empty. non-nil means closed.
	donec chan struct{} // closed on error
}

func (p *http2pipe) CloseWithError(err error) {
	p.mu.Lock()
	defer p.mu.Unlock()
	defer p.c.Signal()
	if p.err == nil {
		p.err = err
		if p.donec != nil {
			close(p.donec)
		}
	}
}

// Done returns a channel which is closed if and when this pipe is closed
// with CloseWithError.
func (p *http2pipe) Done() <-chan struct{} {
	p.mu.Lock()
	defer p.mu.Unlock()
	if p.donec == nil {
		p.donec = make(chan struct{})
		if p.err != nil {
			close(p.donec)
		}
	}
	return p.donec
}
```

// awaitRequestCancel runs in its own goroutine and waits for the user's
func (cs *http2clientStream) awaitRequestCancel(cancel <-chan struct{}) {
	if cancel == nil {
		return
	}
	select {
	case <-cancel:
		cs.bufPipe.CloseWithError(http2errRequestCanceled)
	case <-cs.bufPipe.Done():
	}
}

## コアとなるコードの解説

### `testCancelRequestMidBody`関数
このテスト関数は、`Request.Cancel`チャネルがレスポンスボディの読み取り中にクローズされたときに、クライアントが正しくキャンセルエラーを受け取ることを検証します。
-   サーバーは意図的にレスポンスボディを2つの部分に分けて送信し、その間に`unblock`チャネルで一時停止します。
-   クライアントは最初の部分（"Hello"）を読み取った後、`req.Cancel`チャネルをクローズします。
-   その後、クライアントが残りのボディを読み取ろうとすると、`ioutil.ReadAll`は`ExportErrRequestCanceled`エラーを返し、読み取られたデータが"Hello"のみであることを確認します。
このテストは、HTTP/1.1とHTTP/2の両方で実行され、プロトコルに依存しないキャンセル処理の正確性を保証します。

### `http2pipe`の変更
-   `donec chan struct{}`の追加は、`http2pipe`がクローズされたというイベントを、`sync.Cond`による待機/通知メカニズムとは独立して、チャネルを通じて通知するためのものです。これにより、複数のゴルーチンがパイプの終了を効率的に待機できるようになります。
-   `CloseWithError`が`donec`をクローズするようになったことで、パイプがエラー状態になったときに、`Done()`チャネルを介して待機しているすべてのリスナーに即座に通知が伝播されます。
-   `Done()`メソッドは、`donec`チャネルを遅延初期化し、既にエラーが発生している場合は即座にクローズして返します。これにより、パイプの状態に関わらず、常に有効な通知チャネルが提供されます。

### `http2clientStream.awaitRequestCancel`
このゴルーチンは、HTTP/2ストリームごとに起動され、ユーザーが設定した`Request.Cancel`チャネル、または内部の`http2pipe`がクローズされるのを監視します。
-   `select`ステートメントを使用することで、どちらかのチャネルが先にクローズされた場合に処理が実行されます。
-   `Request.Cancel`がクローズされた場合、`cs.bufPipe.CloseWithError(http2errRequestCanceled)`を呼び出し、レスポンスボディの読み取りに使用されている内部パイプをキャンセルエラーで強制的にクローズします。これにより、クライアントがボディを読み取ろうとした際にキャンセルエラーが返されるようになります。
-   `cs.bufPipe.Done()`がクローズされた場合は、既にパイプが終了しているため、特別な処理は不要です。

### `http2clientConn.RoundTrip`におけるキャンセル処理
-   リクエストボディの送信中に`req.Cancel`がクローズされた場合、`cs.abortRequestBodyWrite()`を呼び出してボディの送信を中断し、`http2errRequestCanceled`を返します。これは、リクエストの初期段階でのキャンセルを処理します。
-   レスポンスヘッダーを受信し、レスポンスボディの読み取りが開始される準備ができた後、`go cs.awaitRequestCancel(cs.req.Cancel)`が起動されます。これにより、レスポンスボディの読み取り中に`Request.Cancel`がクローズされた場合でも、`awaitRequestCancel`ゴルーチンがそれを検知し、ボディの読み取りを停止させることができます。

これらの変更は、`Request.Cancel`チャネルがクローズされたときに、HTTP/2のストリームと関連するリソースが適切にクリーンアップされ、クライアントに一貫したキャンセルエラーが返されることを保証します。

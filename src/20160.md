# [インデックス 20160] ファイルの概要

このコミットは、Go言語の標準ライブラリである`time`パッケージ内のテストコードの修正に関するものです。具体的には、タイムゾーンの略語に関する古い仮定が、IANAタイムゾーンデータベースの更新によって無効になったため、テストが失敗するようになった問題に対処しています。`ParseInLocation`関数が、異なるタイムゾーンであっても同じ略語を持つ日付を正しく解析できることを確認するためのテストロジックが更新されました。

## コミット

```
time: removed from tests now obsolete assumption about Australian tz abbreviations

Australian timezones abbreviation for standard and daylight saving time were recently
changed from EST for both to AEST and AEDT in the icann tz database (see changelog
on www.iana.org/time-zones).

A test in the time package was written to check that the ParseInLocation function
understand that Feb EST and Aug EST are different time zones, even though they are
both called EST. This is no longer the case, and the Date function now returns
AEST or AEDT for australian tz on every Linux system with an up to date tz database
(and this makes the test fail).

Since I wasn't able to find another country that 1) uses daylight saving and 2) has
the same abbreviation for both on tzdata, I changed the test to make sure that
ParseInLocation does not get confused when it parses, in different locations, two
dates with the same abbreviation (this was suggested in the mailing list).

Fixes #8547.

LGTM=bradfitz
R=golang-codereviews, bradfitz
CC=golang-codereviews
https://golang.org/cl/130920043
```

## 変更の背景

このコミットの背景には、タイムゾーン情報の国際的な標準であるIANAタイムゾーンデータベース（tzdata）の更新があります。以前、オーストラリアのタイムゾーン（特にシドニー）では、標準時と夏時間の両方で「EST」という略語が使用されていました。Go言語の`time`パッケージには、`ParseInLocation`関数が、同じ略語（例: EST）であっても、それが属するロケーション（タイムゾーン）と日付によって異なるタイムゾーンを正しく識別できることを検証するテストが存在しました。

しかし、最近のtzdataの更新により、オーストラリアのタイムゾーン略語が変更されました。具体的には、標準時は「AEST」（Australian Eastern Standard Time）、夏時間は「AEDT」（Australian Eastern Daylight Time）と区別されるようになりました。この変更により、Goの`Date`関数が最新のtzdataを持つLinuxシステム上でオーストラリアのタイムゾーンに対して「AEST」または「AEDT」を返すようになり、既存のテストが期待する「EST」という略語の曖昧性が失われ、テストが失敗するようになりました。

この問題に対処するため、テストの目的（`ParseInLocation`が略語の曖昧性を正しく処理できること）を維持しつつ、最新のtzdataに適合するようにテストケースを変更する必要が生じました。

## 前提知識の解説

### Go言語の`time`パッケージ

Go言語の`time`パッケージは、時刻の表現、操作、フォーマット、およびタイムゾーンの処理を提供します。

*   **`time.Time`**: 特定の時点を表す構造体です。
*   **`time.Location`**: タイムゾーン情報を表す構造体です。`LoadLocation`関数を使って、IANAタイムゾーン名（例: "America/New_York", "Asia/Tokyo"）から`Location`オブジェクトをロードします。
*   **`time.ParseInLocation(layout, value, loc *Location) (Time, error)`**: 指定されたレイアウトと文字列から`Time`オブジェクトを解析します。この関数は、`loc`で指定されたタイムゾーンのコンテキストで解析を行います。特に、タイムゾーンの略語が与えられた場合に、その略語がどのタイムゾーンを指すのかを`loc`の情報に基づいて解決しようとします。
*   **`time.Date(year, month, day, hour, min, sec, nsec int, loc *Location) Time`**: 指定された年、月、日、時、分、秒、ナノ秒、および`Location`に基づいて`Time`オブジェクトを作成します。
*   **`Time.Zone() (name string, offset int)`**: `Time`オブジェクトが表す時刻のタイムゾーン名とUTCからのオフセット（秒単位）を返します。

### IANAタイムゾーンデータベース (tzdata)

IANAタイムゾーンデータベース（通称「tzdata」または「zoneinfo」）は、世界のタイムゾーンと夏時間（DST）の規則に関する情報を集めた公開データベースです。このデータベースは、オペレーティングシステムや多くのプログラミング言語（Goを含む）でタイムゾーン情報を処理するための基盤として広く利用されています。

tzdataは定期的に更新され、各国のタイムゾーン規則の変更（例: 夏時間の開始・終了日の変更、新しいタイムゾーンの導入、既存のタイムゾーンの廃止、略語の変更など）が反映されます。このコミットで問題となったオーストラリアのタイムゾーン略語の変更も、tzdataの更新によってもたらされたものです。

### タイムゾーン略語の曖昧性

タイムゾーンの略語（例: EST, CST, AST）は、しばしば曖昧性を含みます。同じ略語が異なるタイムゾーンを指すことがあったり、同じタイムゾーン内でも標準時と夏時間で同じ略語が使われることがありました。

*   **異なるタイムゾーンで同じ略語**: 例えば、「AST」は「Arabia Standard Time」（UTC+3）と「Atlantic Standard Time」（UTC-4）の両方を指すことがあります。
*   **同じタイムゾーン内で標準時と夏時間で同じ略語**: かつてのオーストラリアの「EST」のように、Eastern Standard Time（標準時）とEastern Summer Time（夏時間）の両方が「EST」と略されるケースがありました。

`ParseInLocation`のような関数は、このような曖昧性を、与えられた`Location`情報と日付のコンテキスト（夏時間期間かどうかなど）に基づいて解決しようとします。この解決が正しく行われることが、正確な時刻処理には不可欠です。

## 技術的詳細

このコミットの技術的な核心は、`ParseInLocation`関数がタイムゾーン略語の曖昧性を正しく解決できることを保証するテストのロバスト性を高めることです。

元のテスト`TestParseInSydney`は、オーストラリア/シドニーのタイムゾーンにおいて、2月の「EST」（夏時間）と8月の「EST」（標準時）が、同じ略語「EST」を使用しながらも異なるUTCオフセットを持つことを利用して、`ParseInLocation`がこれらを区別できることを検証していました。2月のESTはUTC+11、8月のESTはUTC+10でした。

しかし、IANA tzdataの更新により、オーストラリアのタイムゾーン略語がより明確に区別されるようになりました。
*   オーストラリア東部標準時 (AEST): UTC+10
*   オーストラリア東部夏時間 (AEDT): UTC+11

この変更により、シドニーでは2月には「AEDT」、8月には「AEST」が使われるようになり、もはや「EST」という略語の曖昧性が存在しなくなりました。その結果、元のテストは、最新のtzdataを持つシステムでは「EST」を認識できなくなり、失敗するようになりました。

新しいテスト`TestParseInLocation`では、この問題を解決するために、異なるタイムゾーンでありながら同じ略語「AST」を使用する2つのタイムゾーンを選定しました。
1.  **`Asia/Baghdad`**: イラクのバグダッド。標準時で「AST」（Arabia Standard Time, UTC+3）を使用します。
2.  **`America/Blanc-Sablon`**: カナダのブラン・サブロン。夏時間を使用しない地域で、「AST」（Atlantic Standard Time, UTC-4）を使用します。

この2つのタイムゾーンは、どちらも「AST」という略語を使用しますが、UTCからのオフセットが大きく異なります（+3時間と-4時間）。新しいテストは、`ParseInLocation`が、これらの異なる`Location`オブジェクトと「AST」という略語が与えられたときに、それぞれの正しいタイムゾーンとオフセットを識別できることを検証します。これにより、タイムゾーン略語の曖昧性に対する`ParseInLocation`の堅牢性を、より普遍的なケースで確認できるようになりました。

## コアとなるコードの解説

新しい`TestParseInLocation`関数は、`ParseInLocation`がタイムゾーン略語の曖昧性を正しく解決できることを、以下の2つのケースで検証します。

1.  **`Asia/Baghdad` (バグダッド) のケース**:
    *   `LoadLocation("Asia/Baghdad")`でバグダッドのタイムゾーン情報をロードします。
    *   `ParseInLocation("Jan 02 2006 MST", "Feb 01 2013 AST", baghdad)`を呼び出し、バグダッドのコンテキストで「Feb 01 2013 AST」を解析します。ここで「AST」は「Arabia Standard Time」を指し、UTC+3のオフセットを持ちます。
    *   `Date(2013, February, 1, 00, 00, 00, 0, baghdad)`で期待される`time.Time`オブジェクトを作成し、解析結果と比較します。
    *   `t1.Zone()`で取得したオフセットが`3*60*60`（3時間）であることを検証します。

2.  **`America/Blanc-Sablon` (ブラン・サブロン) のケース**:
    *   `LoadLocation("America/Blanc-Sablon")`でブラン・サブロンのタイムゾーン情報をロードします。この地域は夏時間を使用しません。
    *   `ParseInLocation("Jan 02 2006 MST", "Feb 01 2013 AST", blancSablon)`を呼び出し、ブラン・サブロンのコンテキストで「Feb 01 2013 AST」を解析します。ここで「AST」は「Atlantic Standard Time」を指し、UTC-4のオフセットを持ちます。
    *   `Date(2013, February, 1, 00, 00, 00, 0, blancSablon)`で期待される`time.Time`オブジェクトを作成し、解析結果と比較します。
    *   `t1.Zone()`で取得したオフセットが`-4*60*60`（-4時間）であることを検証します。

このテストは、`ParseInLocation`が、同じタイムゾーン略語「AST」が与えられた場合でも、それがどの`Location`オブジェクト（タイムゾーン）に属するかによって、異なるUTCオフセットを正しく導き出せることを確認しています。これにより、IANAタイムゾーンデータベースの将来の変更に対しても、より堅牢なテストが提供されることになります。

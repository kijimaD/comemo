## 変更の背景

Go言語では、コードの可読性を高めるためにコメントが重要な役割を果たします。特に、構造体のフィールドや変数宣言の行末に記述されるコメント（trailing comments）は、その要素の目的や制約を簡潔に説明するためによく用いられます。しかし、このコミット以前のGoのASTでは、このような行コメントが構造的に捕捉されず、単なるフリーコメントとして扱われるか、あるいは完全に無視される可能性がありました。

この状況では、`go/ast`パッケージを利用するツール（例えば、コードフォーマッター、ドキュメンテーションジェネレーター、静的解析ツールなど）が、コードの意味を完全に理解したり、コメントを保持したままコードを正確に再構築したりすることが困難でした。例えば、構造体のフィールド定義の横に書かれたコメントは、そのフィールドに密接に関連する情報であるにもかかわらず、AST上ではその関連性が失われてしまうため、ツールがそのコメントを適切に扱えませんでした。

このコミットは、このような問題を解決するために、ASTにフィールドや宣言に付随する行コメントを明示的に保持する構造を追加し、パーサーがそれらを正確に識別してASTに組み込むように拡張することを目的としています。これにより、Goのコードベースを扱うツールがより堅牢になり、開発体験が向上することが期待されます。

また、パーサー内部の識別子命名規則をGoの標準的な慣習であるキャメルケースに統一するクリーンアップも行われています。これは、コードベース全体の整合性を高め、将来的なメンテナンス性を向上させるための一般的な改善です。

## 前提知識の解説

### 抽象構文木 (Abstract Syntax Tree, AST)

ASTは、プログラミング言語のソースコードの抽象的な構文構造を木構造で表現したものです。コンパイラやインタープリタがソースコードを解析する際の中間表現として広く利用されます。Go言語では、標準ライブラリの`go/ast`パッケージがこのASTの定義と操作を提供します。ASTの各ノードは、変数宣言、関数定義、式、文などの言語要素に対応し、ソースコードの構造を忠実に反映します。

### Go言語の`go/ast`パッケージ

`go/ast`パッケージは、GoプログラムのASTを表現するためのデータ構造を定義しています。例えば、`ast.Field`は構造体のフィールドや関数のパラメータを表し、`ast.GenDecl`は`import`, `const`, `var`, `type`などの一般的な宣言を表します。これらの構造体には、ソースコード上の位置情報（`token.Pos`）や、関連するドキュメンテーションコメント（`ast.CommentGroup`）などを保持するフィールドが含まれています。

### Go言語の`go/parser`パッケージ

`go/parser`パッケージは、Goのソースコードを解析し、`go/ast`パッケージで定義されたASTを構築する機能を提供します。このパッケージは、字句解析（lexing）と構文解析（parsing）のプロセスを通じて、ソースコードのテキスト表現を構造化されたASTに変換します。パーサーは、トークンストリームを読み込み、言語の文法規則に従ってASTノードを生成します。

### Go言語のコメントの種類

Go言語には主に以下のコメント形式があります。

*   **行コメント (`//`)**: 行の終わりまで続くコメント。
*   **ブロックコメント (`/* ... */`)**: `/*`と`*/`で囲まれた複数行にわたるコメント。

さらに、コメントの配置によって以下のように分類されることがあります。

*   **ドキュメンテーションコメント**: 宣言の直前に記述され、その宣言のドキュメントとして機能するコメント。通常、`go/doc`ツールによって抽出されます。
*   **フリーコメント**: コードの特定の要素に直接関連付けられていない、独立したコメント。
*   **トレーリングコメント (Trailing Comments)**: コードの行末に記述され、その行のコード要素（例: 構造体フィールド、変数宣言）に直接付随するコメント。

このコミットは、特に「トレーリングコメント」をASTに適切に組み込むことに焦点を当てています。

### Goの命名規則 (`_`-style vs `camelCase`)

Go言語の公式スタイルガイドでは、識別子には`camelCase`（キャメルケース）を使用することが推奨されています。これは、複数の単語を連結する際に、最初の単語の最初の文字を小文字にし、それ以降の単語の最初の文字を大文字にする形式です（例: `myVariable`, `parseFieldDecl`）。一方、`_`-style（アンダースコアスタイル、例: `my_variable`, `parse_field_decl`）は、C言語など他の言語でよく見られますが、Goでは推奨されません。このコミットのクリーンアップ部分は、パーサーコード内の`_`-styleの識別子を`camelCase`に修正し、Goの慣習に合わせるものです。

## 技術的詳細

このコミットの主要な技術的変更は、`go/ast`パッケージのデータ構造の拡張と、`go/parser`パッケージにおけるコメント処理ロジックの根本的な見直しです。

### `go/ast`パッケージの変更

`ast.go`では、以下の主要なASTノード構造体に`Comment *Comment`フィールドが追加されました。

*   `Field` (構造体フィールド、関数パラメータ、メソッドレシーバなど)
*   `ImportSpec` (import宣言)
*   `ValueSpec` (const/var宣言)
*   `TypeSpec` (type宣言)

これらの新しいフィールドは、それぞれの宣言やフィールドの行末に記述された単一行コメントを保持するために使用されます。`*Comment`型は、`go/ast`パッケージで定義されているコメントノードへのポインタであり、コメントのテキスト内容やソースコード上の位置情報を含みます。これにより、トレーリングコメントがASTの一部として明示的に表現され、そのコメントがどのコード要素に付随しているかが構造的に明確になります。

### `go/parser`パッケージの変更

`parser.go`では、コメントの収集とASTノノードへの関連付けのロジックが大幅に改修されました。

1.  **パーサーの状態変更**:
    *   `parser`構造体に`lastComment int`フィールドが追加されました。これは、最後に解析されたトレーリングコメントのインデックスを`comments`ベクター（収集されたコメントのリスト）内に保持するためのものです。
    *   `last_doc interval`が`lastDoc interval`にリネームされ、`_`-styleから`camelCase`への命名規則の変更が適用されました。
    *   `opt_semi`が`optSemi`に、`expr_lev`が`exprLev`に、`ellipsis_ok`が`ellipsisOk`に、`is_ident`が`isIdent`に、`is_call`が`isCall`に、`is_expr`が`isExpr`に、`prev_lev`が`prevLev`に、`is_as`が`isAssign`に、`is_unary`が`isUnary`に、`is_ptr`が`isPtr`に、`label_ok`が`labelOk`に、`is_ellipsis`が`isEllipsis`にそれぞれ変更されました。これは、Goの命名規則に準拠するためのクリーンアップです。

2.  **コメント消費ロジックの改善**:
    *   `collectComment()`関数が`consumeComment()`にリネームされ、コメントを消費してパーサーのコメントリストに追加する役割を担います。
    *   `consumeCommentGroup()`という新しい関数が導入されました。これは、連続するコメント群（コメントブロックやドキュメンテーションコメントなど）をまとめて消費し、そのコメント群が`comments`ベクター内で占める範囲（`interval`）を返します。空行や非コメントトークンによってコメント群は区切られます。

3.  **`next()`関数の再設計**:
    *   `next()`関数は、次の非コメントトークンに進むだけでなく、その過程で遭遇したコメントを適切に分類し、`lastComment`や`lastDoc`に設定する役割を担うようになりました。
    *   具体的には、現在のトークンと同じ行にあるコメントはトレーリングコメントとして扱われ、`lastComment`にそのインデックスが保存されます。
    *   連続するコメント群で、かつ次のトークンがそのコメント群の直後の行に続く場合、そのコメント群はドキュメンテーションコメントとして`lastDoc`に保存されます。

4.  **コメント取得関数の追加**:
    *   `getComment() *ast.Comment`という新しい関数が追加されました。これは、`lastComment`に保存されたトレーリングコメントを取得し、`comments`ベクターからそのコメントを削除（nilに設定）します。これにより、トレーリングコメントは一度だけ取得され、適切なASTノードに割り当てられます。
    *   `getDoc() ast.Comments`関数も改修され、`lastDoc`に保存されたドキュメンテーションコメント群を取得し、同様に`comments`ベクターから削除します。

5.  **ASTノードへのコメント割り当て**:
    *   `parseFieldDecl()`、`parseImportSpec()`、`parseConstSpec()`、`parseTypeSpec()`、`parseVarSpec()`などの宣言を解析する関数内で、`p.getComment()`が呼び出され、解析されたASTノードの新しい`Comment`フィールドにトレーリングコメントが割り当てられるようになりました。
    *   これにより、例えば構造体のフィールドを解析した後、そのフィールドの行末にコメントがあれば、それが`ast.Field`構造体の`Comment`フィールドに格納されます。

これらの変更により、Goパーサーはソースコード内のコメントをより詳細に、かつ構造的に理解できるようになり、ASTがコードのセマンティクスをより豊かに表現できるようになりました。

## コアとなるコードの解説

### `src/pkg/go/ast/ast.go` の変更点

*   **`Field`構造体への`Comment`フィールド追加**:
    ```go
    type (
        Field struct {
            Doc Comments;  // associated documentation; or nil
            Names []*Ident;  // field/method/parameter names; nil if anonymous field
            Type Expr;  // field/method/parameter type
            Tag []*StringLit;  // field tag; or nil
            Comment *Comment;  // trailing comment on same line; or nil // ★追加
        };
    )
    ```
    この変更により、構造体のフィールド、関数のパラメータ、メソッドのレシーバなどの宣言の行末に記述されたコメントを、`Field`ノードが直接保持できるようになりました。例えば、`Name string // ユーザー名` のようなコードがあった場合、`// ユーザー名` の部分がこの`Comment`フィールドに格納されます。

*   **`ImportSpec`, `ValueSpec`, `TypeSpec`構造体への`Comment`フィールド追加**:
    同様に、`import`宣言、`const`/`var`宣言、`type`宣言を表す各構造体にも`Comment *Comment`フィールドが追加されました。これにより、これらの宣言の行末コメントもASTに構造的に組み込まれるようになりました。

    ```go
    // ImportSpec
    type (

    // ValueSpec (const/var)
    type (

    };
    ```
    `lastComment`は、直前に解析された行コメントがトレーリングコメントである場合に、そのコメントが`comments`ベクター内のどこにあるかを記録します。`lastDoc`は、ドキュメンテーションコメント群の範囲を記録します。その他のフィールドは、Goの命名規則に合わせて`_`-styleから`camelCase`にリネームされました。

*   **`consumeComment()`関数のリネームと役割**:
    `collectComment()`が`consumeComment()`にリネームされました。この関数は、現在のトークンがコメントである場合にそれを消費し、パーサーの内部コメントリスト（`p.comments`）に追加します。そして、そのコメントが終了する行番号を返します。

*   **`consumeCommentGroup()`関数の追加**:
    ```go
    func (p *parser) consumeCommentGroup() interval {
        beg := p.comments.Len();
        endline := p.pos.Line;
        for p.tok == token.COMMENT && endline+1 >= p.pos.Line {
            endline = p.consumeComment();
        }
        end := p.comments.Len();
        return interval{beg, end};
    }
    ```
    この関数は、連続するコメントトークンをグループとして消費します。コメントが連続している限り（かつ空行で区切られていない限り）、`consumeComment()`を呼び出してコメントを収集し続けます。これにより、複数の行コメントやブロックコメントが連続している場合でも、それらを一つの論理的なコメントグループとして扱えるようになります。

*   **`next()`関数のロジック変更**:
    ```go
    func (p *parser) next() {
        p.lastComment = -1; // 初期化
        p.lastDoc = empty;  // 初期化

        line := p.pos.Line;
        p.next0(); // 次のトークンに進む

        if p.tok == token.COMMENT {
            // 現在のトークンがコメントの場合
            if p.pos.Line == line {
                // 前のトークンと同じ行にあるコメントはトレーリングコメントの可能性がある
                p.consumeComment();
                if p.pos.Line != line {
                    // 次のトークンが異なる行にある場合、このコメントはトレーリングコメント
                    p.lastComment = p.comments.Len() - 1;
                }
            }

            // 後続のコメントを消費
            group := empty;
            for p.tok == token.COMMENT {
                group = p.consumeCommentGroup();
            }

            if group.end > 0 && p.comments.At(group.end - 1).(*ast.Comment).EndLine + 1 == p.pos.Line {
                // コメントグループがあり、次のトークンがその直後の行に続く場合、ドキュメンテーションコメントとして扱う
                p.lastDoc = group;
            }
        }
    }
    ```
    `next()`関数は、パーサーの最も重要な変更点の一つです。この関数は、次のトークンを読み込む際に、コメントの処理と分類を行います。
    1.  まず、`lastComment`と`lastDoc`をリセットします。
    2.  `p.next0()`を呼び出して、物理的に次のトークンを読み込みます。
    3.  もし読み込んだトークンがコメントであれば、そのコメントがトレーリングコメントなのか、ドキュメンテーションコメントなのかを判断します。
        *   現在のトークンが前のトークンと同じ行にあり、かつそのコメントを消費した後に次のトークンが異なる行に移動した場合、そのコメントはトレーリングコメントと見なされ、`lastComment`に記録されます。
        *   連続するコメント群（`consumeCommentGroup()`で収集）があり、そのコメント群の最終行の直後に次のトークンが続く場合、そのコメント群はドキュメンテーションコメントと見なされ、`lastDoc`に記録されます。

*   **`getComment()`関数の追加**:
    ```go
    func (p *parser) getComment() *ast.Comment {
        i := p.lastComment;
        if i < 0 {
            return nil; // トレーリングコメントがない
        }
        c := p.comments.At(i).(*ast.Comment);
        p.comments.Set(i, nil);  // 取得したコメントはリストからクリア
        p.lastComment = -1;      // リセット
        return c;
    }
    ```
    この関数は、`next()`で設定された`lastComment`からトレーリングコメントを取得します。コメントを取得した後、そのコメントはパーサーの内部リストから`nil`に設定され、`lastComment`もリセットされます。これにより、コメントが重複して処理されるのを防ぎます。

*   **`getDoc()`関数のロジック変更**:
    `getDoc()`関数は、`next()`で設定された`lastDoc`からドキュメンテーションコメント群を取得するように変更されました。取得後、コメント群は内部リストからクリアされます。

*   **ASTノード構築時のコメント割り当て**:
    `parseFieldDecl()`、`parseImportSpec()`、`parseConstSpec()`、`parseTypeSpec()`、`parseVarSpec()`などの関数内で、宣言やフィールドの解析が完了した後、`p.getComment()`を呼び出してトレーリングコメントを取得し、対応するASTノードの`Comment`フィールドに割り当てます。

    例えば、`parseFieldDecl()`では、フィールドの解析後に以下の行が追加されました。
    ```go
    // ...
    f := p.parseFieldDecl();
    list.Push(f);
    if p.tok == token.SEMICOLON {
        p.next();
        f.Comment = p.getComment(); // ★追加
    } else {
        f.Comment = p.getComment(); // ★追加
        break;
    }
    // ...
    ```
    これにより、パーサーがフィールド宣言の行末コメントを認識し、それをASTノードに正確に結びつけることができるようになりました。

これらの変更は、GoのASTがソースコードのより豊かな情報を保持できるようにし、Goのツールエコシステムがより高度なコード理解と操作を行えるようにするための重要な基盤を築きました。

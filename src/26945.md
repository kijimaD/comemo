# [インデックス 26945] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）が生成する文字列データからNUL終端子（null terminator）を削除し、それに伴いリンカ（`cmd/link`）での文字列データの読み取り方法を更新するものです。この変更は、特に`godoc`ツールのバイナリサイズを約37KB削減することを目的としており、Goバイナリの全体的なサイズ削減を目指すIssue #6853の一環として実施されました。

## 変更の背景

Go言語のバイナリサイズは、静的リンクやランタイム情報の埋め込みなどにより、比較的大型になる傾向があります。この問題はGoコミュニティで長らく議論されており、Issue #6853として追跡されています。バイナリサイズの削減は、特にリソースが限られた環境や、デプロイメントの効率性を高める上で重要です。

このコミットは、Goコンパイラが生成する文字列データに不要なNUL終端子が付加されていたという特定の問題に対処します。C言語では文字列の終端を示すためにNUL終端子（`\0`）が必須ですが、Go言語の文字列は長さ情報を持つ構造体であり、NUL終端子を必要としません。しかし、Goの内部処理の一部で、C言語との互換性や過去の慣習から、文字列データにNUL終端子が付加されている箇所がありました。

`godoc`ツールは、Goのソースコードからドキュメントを生成するツールであり、多くの文字列リテラルを含んでいます。これらの文字列リテラルがそれぞれNUL終端子を持つことで、`godoc`のバイナリサイズが不必要に増加していました。このコミットは、この冗長なNUL終端子を削除することで、`godoc`のバイナリサイズを約37KB削減し、Issue #6853の目標達成に貢献します。

## 前提知識の解説

### Go言語における文字列の内部表現

Go言語の文字列は、単なるバイト列ではなく、`struct StringHeader`として定義される構造体です。これは、文字列のバイト列へのポインタと、そのバイト列の長さ（バイト数）の2つのフィールドから構成されます。

```go
type StringHeader struct {
    Data uintptr // 文字列のバイト列へのポインタ
    Len  int     // 文字列の長さ（バイト数）
}
```

この設計により、Goの文字列はNUL終端子を必要とせず、任意のバイト列（NULバイトを含む）を格納できます。また、文字列の長さをO(1)で取得できるため、効率的な処理が可能です。

### C言語スタイルの文字列（NUL終端文字列）

C言語では、文字列は文字の配列として表現され、その終端は必ずNUL文字（`\0`、ASCII値0）で示されます。これはNUL終端文字列（null-terminated string）と呼ばれ、文字列の長さを知るためにはNUL文字までバイトを走査する必要があります。Go言語の文字列とは根本的に異なる表現方法です。

### Goコンパイラ (`cmd/compile`) とリンカ (`cmd/link`)

*   **`cmd/compile`**: Goのソースコードを中間表現（アセンブリコードやオブジェクトファイル）に変換するコンパイラです。このプロセスで、ソースコード中の文字列リテラルがバイナリデータとしてどのように表現されるかが決定されます。
*   **`cmd/link`**: コンパイラによって生成されたオブジェクトファイルやライブラリを結合し、実行可能なバイナリファイルを生成するリンカです。リンカは、コンパイラが生成したシンボル情報やデータセクションを解釈し、最終的なバイナリを構築します。

### `godoc`ツールの役割

`godoc`は、Goのソースコードからドキュメントを抽出し、表示するためのツールです。Goの標準ライブラリやユーザーが作成したパッケージのドキュメントを閲覧する際に利用されます。`godoc`自体もGoで書かれたプログラムであり、そのバイナリサイズはGoのツールチェイン全体の効率性を示す指標の一つとなります。

### シンボルテーブルとデータセクション

コンパイラとリンカは、プログラム内の変数、関数、文字列リテラルなどの情報をシンボルとして管理します。これらのシンボルに関連付けられたデータ（例えば文字列リテラルの実際のバイト列）は、バイナリファイルのデータセクションに格納されます。

## 技術的詳細

このコミットの技術的な核心は、Goの文字列データがC言語スタイルのNUL終端子を必要としないという事実に基づき、コンパイラとリンカの両方でその処理を最適化することにあります。

### `cmd/compile` 側でのNUL終端子の削除

変更前、`src/cmd/compile/internal/gc/obj.go` 内の `stringsym` 関数は、文字列データをバイナリに書き込む際に、明示的にNUL終端子を追加していました。

```go
// 変更前:
off = duint8(symdata, off, 0) // terminating NUL for runtime
```

この行は、文字列のバイト列の直後に1バイトのNUL文字（`0`）を書き込んでいました。これは、Goランタイムが文字列をC言語スタイルの文字列として扱う必要があった、あるいはそのように誤解されていた可能性を示唆しています。しかし、Goの文字列は長さ情報を持つため、このNUL終端子は冗長であり、バイナリサイズを不必要に増加させていました。

このコミットでは、上記の行が削除されました。これにより、コンパイラは文字列データにNUL終端子を付加しなくなります。

### `cmd/link` 側での文字列データ読み取り方法の変更

コンパイラがNUL終端子を生成しなくなったため、リンカは文字列データを読み取る際に、NUL終端子に依存する従来のC言語スタイルの読み取り方法から、Goの文字列の内部表現に合わせた方法に切り替える必要があります。

変更前、`src/cmd/link/internal/ld/decodesym.go` 内の `decodetype_structfieldname` 関数は、`cstring` 関数を使用して文字列を読み取っていました。`cstring` 関数は、ポインタが指すアドレスからNUL終端子が見つかるまでバイトを読み取る、C言語スタイルの文字列読み取り関数です。

```go
// 変更前:
return cstring(r.Sym.P[r.Add:])
```

このコミットでは、この行が以下のように変更されました。

```go
// 変更後:
strlen := int64(decode_inuxi(s.P[Thearch.Ptrsize:], Thearch.Intsize))
return string(r.Sym.P[r.Add : r.Add+strlen])
```

この変更は、以下のステップで文字列を読み取ります。

1.  **`strlen := int64(decode_inuxi(s.P[Thearch.Ptrsize:], Thearch.Intsize))`**:
    *   `s.P` はシンボルのデータへのポインタです。
    *   `Thearch.Ptrsize` はポインタのサイズ（例: 64ビットシステムでは8バイト）を示します。Goの文字列はポインタと長さのペアなので、`Thearch.Ptrsize` のオフセットには文字列の長さ情報が格納されていると推測されます。
    *   `decode_inuxi` は、指定されたバイト列から指定されたサイズの符号なし整数をデコードする関数です。ここでは、文字列の長さ情報をデコードしています。
    *   デコードされた長さは `strlen` 変数に格納されます。
2.  **`return string(r.Sym.P[r.Add : r.Add+strlen])`**:
    *   `r.Sym.P[r.Add:]` は、文字列データの開始アドレスを示します。
    *   `r.Add : r.Add+strlen` は、開始アドレスから `strlen` バイト分のスライスを作成します。
    *   このバイトスライスをGoの `string` 型に変換して返します。

この新しい方法では、NUL終端子に依存せず、Goの文字列が持つ長さ情報に基づいて正確に文字列データを読み取ることができます。

### メモリレイアウトとパフォーマンスへの影響

この変更は、バイナリサイズを削減するだけでなく、Goの文字列の内部表現とリンカの処理をより整合性の取れたものにします。NUL終端子を削除することで、データセクションのフットプリントが減少し、結果としてバイナリのロード時間やメモリ使用量にわずかながらも良い影響を与える可能性があります。パフォーマンスへの直接的な大きな影響は期待されませんが、全体的な効率性の向上に寄与します。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/obj.go` の変更

-   **削除された行**: `off = duint8(symdata, off, 0) // terminating NUL for runtime`
    -   この行は、コンパイラが文字列データをオブジェクトファイルに書き込む際に、その末尾にNULバイト（`0`）を追加していました。コメントにある「runtimeのためのNUL終端子」という記述は、GoランタイムがC言語スタイルの文字列を期待していたか、あるいはそのように扱われていたことを示唆しています。
    -   Goの文字列は長さ情報を持つため、このNUL終端子は不要であり、この行の削除によってバイナリサイズが削減されます。

### `src/cmd/link/internal/ld/decodesym.go` の変更

-   **変更前の行**: `return cstring(r.Sym.P[r.Add:])`
    -   リンカは、シンボルデータ（`r.Sym.P`）内の特定のアドレス（`r.Add`）から始まるバイト列を、`cstring`関数を使ってC言語スタイルのNUL終端文字列として読み取っていました。
-   **変更後の行**:
    ```go
    strlen := int64(decode_inuxi(s.P[Thearch.Ptrsize:], Thearch.Intsize))
    return string(r.Sym.P[r.Add : r.Add+strlen])
    ```
    -   この変更は、リンカが文字列データを読み取る方法を、NUL終端に依存しないGoの文字列の内部表現に合わせるものです。
    -   `decode_inuxi(s.P[Thearch.Ptrsize:], Thearch.Intsize)`: シンボルデータ `s.P` の `Thearch.Ptrsize` オフセットから、`Thearch.Intsize` バイト分のデータを符号なし整数としてデコードし、文字列の長さ `strlen` を取得します。これは、Goの文字列構造体における `Len` フィールドに対応するデータです。
    -   `string(r.Sym.P[r.Add : r.Add+strlen])`: シンボルデータ `r.Sym.P` の `r.Add` から始まるアドレスから、取得した `strlen` バイト分のデータをスライスとして抽出し、それをGoの `string` 型に変換して返します。これにより、正確な長さの文字列データがNUL終端子なしで読み取られます。

これらの変更により、コンパイラとリンカの間で文字列データの扱いが一貫し、Goの文字列の特性を最大限に活かした効率的なバイナリ生成が可能になります。

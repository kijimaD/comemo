# [インデックス 21795] ファイルの概要

このコミットは、Go言語のツールチェインにおけるリンカ（`liblink`）の内部表現に関する重要な変更を導入しています。具体的には、アドレスを表す際にこれまで一部で誤用されていた `TYPE_CONST` を廃止し、よりセマンティクス的に正確な `TYPE_ADDR` の使用を強制するものです。これにより、コードの明確性が向上し、将来的な最適化やアーキテクチャ固有の挙動の管理が容易になります。

## コミット

このコミットは、Go言語のリンカである`liblink`において、アドレス表現の型を`TYPE_CONST`から`TYPE_ADDR`に統一することを目的としています。`liblink/pass.c`に`Addr`のチェック機能が追加され、すべての`Prog`入力に対して`TYPE_ADDR`の使用が必須となります。これに伴い、既存のコンパイラ（`5a`, `5g`, `6a`, `8a`, `9a`, `9g`）およびアセンブラが、新しい型要件を満たすように更新されました。

## 変更の背景

Go言語のコンパイラとリンカは、プログラムの命令やデータのアドレスを内部的に表現するために、`Addr`という構造体を使用しています。この`Addr`構造体には、そのアドレスがどのような種類のものかを示す`type`フィールドが含まれています。

これまでの実装では、特にARMやPPC64といった一部のアーキテクチャにおいて、メモリ参照の実効アドレス（effective address）や、オフセットのみを持つアドレス（例: `$<±integer value>`) を表現する際に、セマンティクス的に不適切な `TYPE_CONST` が使用されていました。`TYPE_CONST`は本来、純粋な定数値を表すためのものであり、メモリ上の位置やシンボルに関連するアドレスを表すには適していません。

この曖昧な型使用は、以下のような問題を引き起こす可能性がありました。

1.  **セマンティクスの不明瞭さ**: `TYPE_CONST`が定数とアドレスの両方を意味するため、コードの可読性や理解を妨げていました。
2.  **バグの温床**: 型の意図が不明確なため、誤ったアドレス計算や最適化が行われるリスクがありました。
3.  **将来的な拡張性の阻害**: 新しいアーキテクチャのサポートや、より高度なリンカ最適化を導入する際に、既存の曖昧な型定義が足かせとなる可能性がありました。

このコミットは、これらの問題を解決し、アドレス表現のセマンティクスを明確にするために、`TYPE_ADDR`をアドレス専用の型として厳密に適用することを目的としています。これにより、リンカの内部処理がより堅牢になり、将来的な開発が容易になります。

## 前提知識の解説

このコミットを理解するためには、Go言語のコンパイラとリンカの基本的な構造、特にアセンブラとリンカがどのように命令やアドレスを表現しているかについての知識が必要です。

*   **Goツールチェイン**: Go言語のソースコードを最終的な実行可能ファイルに変換する一連のツール群を指します。これには、コンパイラ（`5g`, `6g`, `8g`, `9g`など、各アーキテクチャに対応）、アセンブラ（`5a`, `6a`, `8a`, `9a`など）、リンカ（`liblink`）などが含まれます。
*   **`liblink`**: Go言語のリンカの中核部分を担うライブラリです。コンパイラやアセンブラによって生成されたオブジェクトファイルを結合し、実行可能ファイルを生成します。
*   **`Prog` (Program Instruction)**: Goリンカの内部で命令を表す基本的な単位です。各`Prog`は、アセンブリ命令、オペランド、およびその他のメタデータを含みます。
*   **`Addr` (Address Structure)**: `Prog`構造体の一部として、命令のオペランド（ソースやデスティネーション）が参照するアドレスを表現するために使用される構造体です。`Addr`構造体には、アドレスの種類を示す`type`フィールド、オフセットを示す`offset`フィールド、レジスタを示す`reg`フィールド、シンボルを示す`sym`フィールドなどがあります。
*   **`TYPE_CONST`**: `Addr`構造体の`type`フィールドで使われる定数の一つで、純粋な定数値を表すために設計されています。しかし、これまでは一部のアーキテクチャでメモリ参照のアドレスとしても誤用されていました。
*   **`TYPE_ADDR`**: `Addr`構造体の`type`フィールドで使われる定数の一つで、メモリ上の実効アドレスやシンボルに関連するアドレスを明示的に表すために設計されています。このコミットにより、アドレス表現の標準的な型としてその使用が厳密化されます。
*   **`y.tab.c` / `a.y`**: Goのアセンブラ（例: `5a`, `6a`, `8a`, `9a`）のパーサを生成するためのYacc/Bisonのソースファイルです。`a.y`は文法定義、`y.tab.c`はそれから生成されるC言語のコードです。これらのファイルは、アセンブリコードがどのように解析され、内部の`Prog`および`Addr`構造体に変換されるかを定義しています。
*   **`cgen.c` / `ggen.c` / `gobj.c` / `gsubr.c` / `peep.c` / `prog.c` / `reg.c`**: これらはGoコンパイラ（例: `5g`, `6g`, `8g`, `9g`）のバックエンドを構成するC言語のソースファイルです。それぞれコード生成、オブジェクト生成、サブルーチン、ピーフホール最適化、プログラム情報の管理、レジスタ割り当てなど、コンパイルプロセスの異なる側面を扱っています。これらのファイル内で`Addr`構造体が操作され、`TYPE_CONST`や`TYPE_ADDR`が使用される箇所が今回の変更の対象となります。

## 技術的詳細

このコミットの核心は、Goリンカの内部でアドレスを表現する際の型システムを厳密化することにあります。これまで、`include/link.h`のコメントにも示されているように、ARM (`5a`, `5g`) や PPC64 (`9a`, `9g`) などの一部のアーキテクチャでは、メモリ参照の実効アドレス（`$<mem>`）やオフセット値（`$<±integer value>`）を表現する際に、本来定数を意味する`TYPE_CONST`が使用されていました。これは、アドレスが本質的にメモリ上の位置を指すものであるにもかかわらず、その値が定数であるという側面だけを捉えて`TYPE_CONST`を割り当てていたためです。

このコミットでは、この曖昧さを解消し、アドレスは常に`TYPE_ADDR`で表現されるべきであるという原則を導入します。

具体的な変更点は以下の通りです。

1.  **`liblink/pass.c`における`Addr`チェックの追加**:
    `liblink/pass.c`は、リンカが`Prog`命令を処理する際のパスの一つです。このファイルに、入力されるすべての`Prog`命令の`Addr`オペランドに対して、`TYPE_ADDR`が適切に使用されているかを検証する新しいチェックが追加されました。これにより、リンカの早期段階で型の一貫性が強制され、不正なアドレス表現が検出されるようになります。

2.  **コンパイラとアセンブラの更新**:
    `5a`, `5g`, `6a`, `8a`, `9a`, `9g`といった各アーキテクチャのアセンブラとコンパイラが、`TYPE_CONST`を`TYPE_ADDR`に置き換えるように修正されました。
    *   **アセンブラ (`a.y`, `y.tab.c`)**: アセンブリコードを解析し、`Prog`構造体を生成する段階で、アドレスを表現する際に`TYPE_CONST`ではなく`TYPE_ADDR`を割り当てるように変更されました。例えば、`$oreg`（レジスタオフセット付きのアドレス）のような表現が`TYPE_ADDR`として扱われるようになります。
    *   **コンパイラ (`cgen.c`, `ggen.c`, `gobj.c`, `gsubr.c`, `peep.c`, `prog.c`, `reg.c`)**: Goソースコードからアセンブリ命令を生成する際に、アドレスを扱う箇所で`TYPE_CONST`の使用を`TYPE_ADDR`に切り替えました。これには、データ文字列のアドレス、関数リテラルのアドレス、スタックフレームの調整、シンボルポインタの生成など、多岐にわたる変更が含まれます。

3.  **`include/link.h`のコメント更新**:
    `link.h`内の`Addr`構造体に関するコメントが更新され、`$<mem>`や`$<±integer value>`といったアドレス表現が`TYPE_ADDR`を使用することが明記されました。これにより、リンカの内部型に関するドキュメントが最新の状態に保たれ、開発者にとっての明確性が向上します。

この変更は、単なる型名の置き換え以上の意味を持ちます。`TYPE_ADDR`をアドレス専用とすることで、リンカはアドレスと定数を明確に区別できるようになります。これにより、アドレスに対する特定の最適化（例: アドレスの再配置、ベースレジスタの割り当て）をより安全かつ効果的に適用できるようになり、リンカの堅牢性と性能の向上が期待されます。また、将来的にGoが新しいアーキテクチャをサポートする際や、リンカの機能が拡張される際にも、この明確な型定義が基盤となります。

## コアとなるコードの解説

上記の変更箇所は、Go言語のコンパイラとリンカがどのようにアドレスを内部的に表現し、処理するかという、その根幹に関わる部分です。

*   **`include/link.h`のコメント変更**:
    これは直接的なコードの動作変更ではありませんが、Goツールチェインの設計思想とドキュメントの整合性を保つ上で非常に重要です。以前のコメントは、ARMやPPC64で`TYPE_CONST`がアドレスとして使われているという「現状」を記述していました。このコミットでは、その「現状」が「誤り」であり、`TYPE_ADDR`が正しいセマンティクスを持つ型であるという「あるべき姿」を明示しています。これにより、将来のGo開発者がリンカの内部を理解する際の混乱を防ぎ、正しい型使用を促します。

*   **`src/liblink/pass.c`の`checkaddr`関数**:
    この関数は、リンカがオブジェクトファイルを読み込み、`Prog`命令のリストを構築する初期段階で呼び出されます。`checkaddr`は、各`Prog`命令の`from`、`to`、`from3`オペランド（これらはすべて`Addr`型）を検査します。
    *   `if (a->type == TYPE_CONST)`ブロックでは、`TYPE_CONST`がアドレスとして（シンボルやレジスタ、名前が関連付けられている場合）使用されていないかをチェックします。もしそのような誤用が見つかれば、`diag`関数を通じて診断メッセージ（エラーまたは警告）を出力します。これは、コンパイラやアセンブラがまだ古い`TYPE_CONST`のセマンティクスでコードを生成している場合に、その問題を早期に発見するためのガードレールとして機能します。
    *   `if (a->type == TYPE_ADDR)`ブロックでは、逆に`TYPE_ADDR`が純粋な定数（シンボル、レジスタ、名前が関連付けられていない場合）として使用されていないかをチェックします。`TYPE_ADDR`はアドレスを指すべきであり、単なる数値定数ではないためです。
    *   これらのチェックは、リンカが処理を進める前に、入力される`Prog`命令の`Addr`構造体が期待されるセマンティクスに沿っていることを保証します。これにより、リンカの後の段階での予期せぬ動作やバグを防ぎます。

*   **アセンブラ (`a.y`, `y.tab.c`) の変更**:
    アセンブラは、人間が書いたアセンブリコードを機械が理解できる`Prog`命令に変換する役割を担います。`a.y`の変更は、アセンブリ言語の構文解析ルールを変更し、例えば`$oreg`のような「レジスタオフセット付きの即値」が、これからは`TYPE_ADDR`として解釈されるようにします。これは、アセンブラが生成する`Prog`命令の`Addr`構造体の`type`フィールドに、正しいセマンティクスを持つ`TYPE_ADDR`が設定されることを意味します。`y.tab.c`は`a.y`から自動生成されるファイルであり、`a.y`の変更が反映されます。

*   **コンパイラ (`cgen.c`など) の変更**:
    コンパイラはGoのソースコードを中間表現（最終的にはアセンブリ命令）に変換します。`cgen.c`のようなファイルは、この変換プロセスで`Prog`命令を生成する部分です。例えば、データセクションに文字列リテラルを配置する際に、その文字列のアドレスを表現する`Addr`構造体の`type`フィールドが`TYPE_CONST`から`TYPE_ADDR`に変更されます。これは、文字列リテラルがメモリ上の特定のアドレスに配置される「データ」であり、そのアドレスは「定数」ではなく「メモリ上の位置」を指すものであるという、より正確なセマンティクスを反映しています。

これらの変更は、Goツールチェインの内部でアドレスと定数の区別を明確にし、型安全性を向上させるためのものです。これにより、リンカはより正確な情報に基づいて最適化を行い、異なるアーキテクチャ間での一貫性を保ちやすくなります。また、将来的なツールチェインの進化においても、この明確な型システムが強固な基盤となります。

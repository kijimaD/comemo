## 変更の背景

このコミットは、Goコンパイラのエスケープ解析における特定のバグを修正するために行われました。具体的には、以前の変更（CL 21202）によって導入された不具合が原因で、可変長引数（varargs）を持つ関数が関数の戻り値（`PPARAMOUT`）のエスケープ解析を正しく行わないケースが発生していました。この問題は、GoのIssue #15013として報告されており、コンパイラのクラッシュを引き起こす可能性がありました。

エスケープ解析は、変数がスタックに割り当てられるべきか、それともヒープに割り当てられるべきかを決定する重要な最適化プロセスです。この解析が誤ると、プログラムのパフォーマンス低下や、最悪の場合、コンパイラのクラッシュや不正なコード生成につながる可能性があります。このコミットは、`esccall`関数が可変長引数を持つ関数呼び出しの後に`PPARAMOUT`をスキップしないようにすることで、このバグを修正し、コンパイラの堅牢性を向上させることを目的としています。

## 前提知識の解説

### Goコンパイラ

Goコンパイラは、Go言語で書かれたソースコードを機械語に変換するプログラムです。最適化フェーズを含み、生成されるバイナリのパフォーマンスを向上させるための様々な分析を行います。

### エスケープ解析 (Escape Analysis)

エスケープ解析は、Goコンパイラの重要な最適化の一つです。これは、プログラム内の変数がその変数が宣言されたスコープの外側（例えば、関数から戻り値として返される、グローバル変数に代入されるなど）から参照され続ける可能性があるかどうかを判断するプロセスです。

*   **スタック割り当て**: 変数がスコープ外から参照されない（エスケープしない）と判断された場合、その変数はスタックに割り当てられます。スタック割り当ては非常に高速で、ガベージコレクションの対象とならないため、パフォーマンス上の利点があります。
*   **ヒープ割り当て**: 変数がスコープ外から参照される可能性がある（エスケープする）と判断された場合、その変数はヒープに割り当てられます。ヒープ割り当てされたオブジェクトはガベージコレクタによって管理されるため、オーバーヘッドが発生します。

エスケープ解析の目的は、可能な限り多くの変数をスタックに割り当てることで、ガベージコレクションの負荷を減らし、プログラムの実行速度を向上させることです。

### `esccall`関数

`src/cmd/compile/internal/gc/esc.go`ファイルに存在する`esccall`関数は、Goコンパイラのエスケープ解析フェーズの一部です。この関数は、関数呼び出し（`OCALLFUNC`などのオペレーション）の引数と戻り値がどのようにエスケープするかを分析する役割を担っています。関数呼び出しのコンテキストで、引数が呼び出し元からエスケープするか、または戻り値が呼び出し元にエスケープするかなどを判断します。

### `PPARAM`と`PPARAMOUT`

Goコンパイラの内部では、関数のパラメータと戻り値は特定のノードタイプで表現されます。

*   **`PPARAM`**: 関数の入力パラメータ（引数）を表します。
*   **`PPARAMOUT`**: 関数の出力パラメータ（戻り値）を表します。Goでは、戻り値も内部的にはパラメータとして扱われ、エスケープ解析の対象となります。

### 可変長引数 (Varargs)

Goの可変長引数は、関数が任意の数の引数を受け入れることを可能にする機能です（例: `func foo(a ...int)`）。関数内部では、可変長引数はその型のスライスとして扱われます。エスケープ解析においては、このスライス自体やその要素がどのようにエスケープするかが重要な考慮事項となります。

### CL (Change List)

Goプロジェクトでは、コードの変更は「Change List (CL)」という単位で管理されます。これは、Gitのコミットに相当する概念で、コードレビューシステム（Gerrit）を通じて提案、レビュー、承認されます。

## 技術的詳細

このコミットが修正するバグは、`esccall`関数が可変長引数を持つ関数呼び出しのエスケープ解析を行う際に、`PPARAMOUT`（戻り値）の解析を誤ってスキップしてしまうというものでした。

具体的な問題点は、`esccall`関数内のループ処理にありました。関数の宣言リスト（`fn.Name.Defn.Func.Dcl`）をイテレートして`PPARAM`（入力パラメータ）と`PPARAMOUT`（出力パラメータ）を処理する際、可変長引数（`...`引数）の処理が特定の条件で`break DclLoop`によって早期に終了してしまうロジックになっていました。これにより、可変長引数の後に続く`PPARAMOUT`が適切にエスケープ解析されず、結果としてコンパイラのクラッシュ（Issue #15013）を引き起こしていました。

このコミットでは、以下の主要な変更によってこの問題を解決しています。

1.  **`DclLoop`ラベルの削除**: ループを早期に中断させるための`DclLoop`ラベルが削除されました。これにより、ループが`PPARAMOUT`を含むすべての宣言を確実に処理できるようになります。
2.  **可変長引数処理の改善**: 可変長引数（`...`引数）が処理される部分のロジックが変更されました。以前は`break DclLoop`でループを抜けていましたが、修正後は可変長引数の要素を個別に「追跡されない」（untracked）ものとして`escassignSinkNilWhy`で処理し、`lls = nil`を設定した上で`continue`でループの次のイテレーションに進むように変更されました。これにより、可変長引数の処理が完了した後も、ループが継続して`PPARAMOUT`の処理に到達できるようになります。
3.  **不要な可変長引数処理の削除**: ループの後に存在していた、可変長引数を「追跡されない」ものとして処理する冗長なコードブロックが削除されました。これは、ループ内で既に適切に処理されるようになったためです。

これらの変更により、`esccall`関数は可変長引数を持つ関数呼び出しにおいても、すべての入力パラメータと出力パラメータに対して正確なエスケープ解析を実行できるようになり、コンパイラの安定性と正確性が向上しました。

追加されたテストケース`test/fixedbugs/issue15013.go`は、`F1`という可変長引数を持つ関数と、それを呼び出す`F2`という関数を定義しています。これらの関数が再帰的なグループにある状況を模倣することで、以前のバグが再現されることを確認し、修正が正しく適用されたことを検証します。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/esc.go` の変更点

1.  **`DclLoop:` ラベルの削除**:
    変更前: `DclLoop:`
    変更後: (削除)
    このラベルは、ループを特定の条件で中断するために使用されていました。このラベルを削除することで、ループが`fn.Name.Defn.Func.Dcl`内のすべての要素（`PPARAM`と`PPARAMOUT`）を確実にイテレートできるようになります。これにより、可変長引数の処理後に`PPARAMOUT`の解析がスキップされることを防ぎます。

2.  **`continue DclLoop` の `continue` への変更**:
    変更前: `continue DclLoop`
    変更後: `continue`
    `DclLoop`ラベルが削除されたため、`continue`文も通常のループの次のイテレーションに進む動作に変更されました。これにより、特定の条件（レシーバの処理後や`lls`が空の場合）で現在のイテレーションをスキップしつつも、ループ自体は継続して次の宣言の処理に進むことができます。

3.  **可変長引数処理ロジックの変更**:
    最も重要な変更は、`if src != lls[0]` のブロック内です。
    変更前は、この条件が真の場合（つまり、`...`引数が通常の引数とは異なる方法で処理される場合）、`break DclLoop`によってループが完全に中断されていました。これは、可変長引数の後に続く`PPARAMOUT`の解析が実行されない原因となっていました。

    変更後:
    ```go
    					// "..." arguments are untracked
    					for _, n2 := range lls {
    						if Debug['m'] > 3 {
    							fmt.Printf("%v::esccall:: ... <- %v, untracked\\n", linestr(lineno), Nconv(n2, FmtShort))
    						}
    						escassignSinkNilWhy(e, src, n2, "... arg to recursive call")
    					}
    					// No more PPARAM processing, but keep
    					// going for PPARAMOUT.
    					lls = nil
    					continue
    ```
    *   `for _, n2 := range lls { ... }`: 可変長引数（`lls`スライス）の各要素を個別にループ処理し、`escassignSinkNilWhy`関数を使って「追跡されない」（untracked）ものとしてエスケープ解析のコンテキストに登録しています。これは、可変長引数の要素がどのようにエスケープするかを正確にモデル化するために重要です。
    *   `lls = nil`: 可変長引数の処理が完了したことを示し、これ以上`lls`が通常のパラメータとして扱われないようにします。
    *   `continue`: ここで`continue`を使用することで、現在のイテレーションは終了しますが、外側の`for`ループは継続します。これにより、可変長引数の処理が完了した後も、`fn.Name.Defn.Func.Dcl`リストの残りの要素（特に`PPARAMOUT`）の処理に進むことができるようになります。

4.  **冗長な可変長引数処理の削除**:
    変更前は、`for _, n2 := range lls { ... }`というブロックがメインのループの外側にも存在していました。これは、可変長引数が処理されなかった場合に備えていたものと考えられますが、上記の変更によりループ内で適切に処理されるようになったため、この冗長なブロックは削除されました。

これらの変更により、`esccall`関数は可変長引数を持つ関数呼び出しにおいても、すべてのパラメータと戻り値に対して正確なエスケープ解析を実行できるようになり、コンパイラのクラッシュを防ぎます。

### `test/fixedbugs/issue15013.go` の解説

このテストファイルは、修正されたバグを再現するための最小限のコードを提供します。

*   **`F1`関数**:
    ```go
    func F1(p *int, a ...*int) (int, *int) {
    	if p == nil {
    		return F2(), a[0]
    	}
    	return 0, a[0]
    }
    ```
    `F1`はポインタ`p`と可変長引数`a`（`...*int`）を受け取り、`int`と`*int`を返します。`p`が`nil`の場合、`F2()`を呼び出し、その戻り値と`a[0]`を返します。この`a[0]`が、エスケープ解析の誤りにつながる可能性のあるポイントです。

*   **`F2`関数**:
    ```go
    func F2() int {
    	var i0, i1 int
    	a, _ := F1(&i0, &i1)
    	return a
    }
    ```
    `F2`は`i0`と`i1`という2つの`int`型変数を宣言し、それらのアドレスを`F1`に渡して呼び出します。`F1`の戻り値の一部を受け取り、それを返します。

このテストケースの肝は、`F1`が可変長引数を受け取り、その要素（`a[0]`）を戻り値として返す可能性がある点、そして`F1`と`F2`が相互に呼び出し合う（または同じ再帰グループに属する）構造になっている点です。以前のバグでは、`F1`の可変長引数`a`が処理された後、`F1`の戻り値（`PPARAMOUT`）のエスケープ解析がスキップされ、`a[0]`が不適切にスタックに割り当てられると判断される可能性がありました。しかし、`a[0]`は`F2`に返されるため、実際にはヒープにエスケープする必要があります。この不一致がコンパイラのクラッシュを引き起こしていました。このテストは、修正が適用されたコンパイラでこのコードが正常にコンパイルされることを確認します。

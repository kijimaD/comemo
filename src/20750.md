## 元コミット内容

このコミット自体はドキュメントの変更のみですが、その元となった変更は `go/build` パッケージにおけるファイル名に基づくビルド制約の挙動変更です。具体的には、`android.go` のような `GOOS.go` 形式のファイルが、暗黙的にそのOS専用のファイルとして扱われないようにする変更が、`golang.org/cl/147690043` で行われました。このコミットは、その変更に伴うドキュメントの更新が「忘れられていた」ために追加されました。

## 変更の背景

Go言語のビルドシステムには、特定のファイルが特定のオペレーティングシステム (GOOS) やアーキテクチャ (GOARCH) 向けにのみコンパイルされるようにするための「ビルド制約 (build constraints)」という仕組みがあります。これには、ソースファイルの先頭に `// +build tag` のようなコメントを記述する方法と、ファイル名に特定のサフィックスを付けることで暗黙的に制約を適用する方法がありました。

以前は、`windows.go` や `linux.go` のように、ファイル名が `GOOS.go` の形式である場合、そのファイルは暗黙的にそのOS向けのビルド制約を持つと解釈されていました。しかし、この挙動は意図しない副作用を生む可能性がありました。例えば、単に `android.go` という名前のファイルが、Android OS専用のコードとして扱われてしまうといったケースです。

`golang.org/cl/147690043` で、この暗黙的なビルド制約の解釈が変更され、`GOOS.go` 形式のファイルはもはや暗黙的なビルド制約を持たないようになりました。この変更により、開発者はより明示的にビルド制約を記述する必要があり、意図しないファイルのマッチングを防ぐことができます。

本コミットは、この重要な挙動変更が `src/go/build/doc.go` のドキュメントに反映されていなかったため、その修正を行うものです。Issue #8838 は、このドキュメントの不整合や、関連するビルド制約の挙動に関する問題提起であったと推測されます。

## 前提知識の解説

### Go言語のビルドシステムとビルド制約

Go言語のビルドシステムは、ソースコードをコンパイルして実行可能なバイナリを生成するプロセスを管理します。このシステムは、クロスコンパイルを容易にするために設計されており、`GOOS` (ターゲットOS) や `GOARCH` (ターゲットアーキテクチャ) といった環境変数を使用して、異なるプラットフォーム向けのビルドをサポートします。

**ビルド制約 (Build Constraints / Build Tags)**:
Goのビルド制約は、特定のソースファイルが特定の条件が満たされた場合にのみビルドに含まれるようにするためのメカニズムです。これにより、プラットフォーム固有のコードや、開発環境と本番環境で異なるコードを容易に管理できます。

ビルド制約の指定方法には主に2つあります。

1.  **明示的なビルドタグ**: ソースファイルの先頭に `// +build tag` の形式でコメントを記述する方法です。例えば、`// +build linux` と書かれたファイルはLinux環境でのみビルドに含まれます。複数のタグを組み合わせることも可能です（例: `// +build linux,amd64`）。
2.  **暗黙的なビルド制約 (ファイル名に基づく)**: 特定のファイル名パターンを持つファイルは、Goツールチェーンによって自動的にビルド制約が適用されます。主なパターンは以下の通りです。
    *   `*_GOOS.go`: 例: `foo_windows.go` はWindowsでのみビルド。
    *   `*_GOARCH.go`: 例: `foo_amd64.go` はAMD64アーキテクチャでのみビルド。
    *   `*_GOOS_GOARCH.go`: 例: `foo_windows_amd64.go` はWindowsかつAMD64でのみビルド。

このコミットが修正しているのは、かつて存在した `GOOS.go` (例: `windows.go`) という形式のファイル名が暗黙的なビルド制約を持つというルールに関するドキュメントです。

### `GOOS` と `GOARCH`

*   **`GOOS`**: Goプログラムをビルドするターゲットのオペレーティングシステムを指定します。例: `linux`, `windows`, `darwin` (macOS), `android` など。
*   **`GOARCH`**: Goプログラムをビルドするターゲットのプロセッサアーキテクチャを指定します。例: `amd64`, `arm`, `arm64`, `386` など。

これらの環境変数を設定することで、Goコンパイラは指定されたプラットフォーム向けのバイナリを生成します。

## 技術的詳細

このコミットの技術的詳細は、Goのビルドシステムがソースファイルをどのように解釈し、ビルドに含めるかを定義する `go/build` パッケージの内部ロジックと、そのドキュメントの整合性に関わっています。

元の `src/go/build/doc.go` の記述では、ファイル名が `GOOS.go` (例: `windows.go`) や `GOARCH.go` (例: `amd64.go`) の形式である場合、そのファイルが暗黙的に対応するOSやアーキテクチャのビルド制約を持つと説明されていました。しかし、`golang.org/cl/147690043` でこの挙動が変更されました。

`golang.org/cl/147690043` の変更は、`go/build` パッケージがファイル名を解析する際のロジックを修正し、`GOOS.go` や `GOARCH.go` のようなファイル名が、もはや暗黙的なビルド制約として扱われないようにしました。この変更の意図は、ファイル名が偶然OS名やアーキテクチャ名と一致した場合に、意図せずビルドから除外されたり、特定のプラットフォームに限定されたりするのを防ぐためと考えられます。例えば、`android.go` というファイルが、Android OS向けのコードではなく、単に「Androidに関する何か」を扱う汎用的なコードであった場合、以前のルールではAndroid環境でしかビルドされませんでした。この変更により、そのようなファイルは明示的なビルドタグがない限り、すべてのプラットフォームでビルドされるようになります。

本コミットは、この重要な挙動変更が `src/go/build/doc.go` のドキュメントに反映されていなかったという「忘れられた」点を修正するものです。ドキュメントから `GOOS` および `GOARCH` のリテラル形式（例: `windows.go`）が暗黙的なビルド制約を持つという記述を削除することで、実際のGoツールチェーンの挙動とドキュメントの整合性を保っています。

これにより、開発者はファイル名に `_` (アンダースコア) を含む `*_GOOS.go` や `*_GOARCH.go` の形式を使用するか、明示的なビルドタグ `// +build` を使用して、プラットフォーム固有のコードを管理する必要があることが明確になります。

## コアとなるコードの解説

変更箇所は `src/go/build/doc.go` の108行目から117行目にかけてのコメントブロックです。

削除された行:
```
// (example: source_windows_amd64.go) or the literals:
//	GOOS
// 	GOARCH
// (example: windows.go) where GOOS and GOARCH represent any known operating
// system and architecture values respectively, then the file is considered to
// have an implicit build constraint requiring those terms.
```

変更後の行:
```
// (example: source_windows_amd64.go) where GOOS and GOARCH represent
// any known operating system and architecture values respectively, then
// the file is considered to have an implicit build constraint requiring
// those terms.
```

この変更により、`GOOS` や `GOARCH` のリテラル（例: `windows.go`）が暗黙的なビルド制約を持つという記述がドキュメントから削除されました。これは、`golang.org/cl/147690043` で行われた実際のビルドシステムの挙動変更に合わせて、ドキュメントを正確にするための修正です。

具体的には、以前は `windows.go` というファイル名が `// +build windows` と同等に扱われると説明されていましたが、このコミットによってその説明が削除され、もはやその挙動は期待されないことが明確になりました。これにより、Goのビルド制約に関するドキュメントが、現在のGoツールチェーンの動作と一致するようになりました。

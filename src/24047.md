# [インデックス 24047] ファイルの概要

このコミットは、Go言語の`net/textproto`パッケージにおけるHTTPヘッダーキーの正規化ロジックのセキュリティ脆弱性を修正するものです。具体的には、ヘッダーキー内のスペースをハイフンとして扱う以前の挙動が、HTTPリクエストスマグリング攻撃の潜在的な原因となるため、この挙動を廃止し、無効なヘッダーキーは正規化せずにそのまま返すように変更されました。

## 変更の背景

この変更の背景には、HTTPヘッダーの処理におけるセキュリティ上の懸念、特にHTTPリクエストスマグリング攻撃への対策があります。

元々、Goの`net/textproto`パッケージの`CanonicalMIMEHeaderKey`関数は、HTTPヘッダーキーを正規化する際に、スペース文字をハイフンに変換する挙動を持っていました。この挙動は、2012年2月に特定のウェブカメラから返される不正なレスポンスヘッダー（例: `Content Length`）に対応するために導入されたものでした。これにより、`Content Length`のような非標準的なヘッダーキーも`Content-Length`として正しく解釈され、アプリケーションが機能するように意図されていました。

しかし、この「スペースをハイフンに変換する」という挙動は、HTTPリクエストスマグリングという深刻なセキュリティ問題を引き起こす可能性が指摘されました。攻撃者は、この挙動を利用して、フロントエンドプロキシとバックエンドサーバー間でのHTTPリクエストの解釈の不一致を引き起こし、悪意のあるリクエストを隠蔽したり、認証を回避したり、キャッシュポイズニングを行ったりすることが可能になります。

例えば、`Content Length`というヘッダーがプロキシとバックエンドで異なる解釈をされた場合、プロキシはこれを正規のヘッダーとして扱い、バックエンドはこれを`Content-Length`として正規化して処理することで、リクエストボディの長さの認識にずれが生じ、後続のリクエストが前のリクエストのボディの一部として扱われる可能性があります。

この問題は、HTTP/1.1のメッセージ構文を定義するRFC 7230に準拠していないヘッダーキーの処理に起因します。RFC 7230では、ヘッダーフィールド名に使用できる文字（`tchar`）が厳密に定義されており、スペースは含まれていません。

このコミットは、Régis Leroy氏からの報告を受け、HTTPリクエストスマグリングに対する全体的なHTTP強化の一環として、この潜在的なセキュリティ問題を解消するために行われました。

## 前提知識の解説

### HTTPヘッダーの正規化 (Canonicalization)

HTTPヘッダーの正規化とは、HTTPヘッダーフィールド名（キー）を標準的な形式に変換するプロセスです。HTTPプロトコルでは、ヘッダーフィールド名は大文字・小文字を区別しないとされています（例: `Content-Length`、`content-length`、`CONTENT-LENGTH`はすべて同じヘッダーを指す）。しかし、プログラムでヘッダーを扱う際には、一貫した形式に揃えることで、マップやハッシュテーブルでの検索を容易にし、開発者が異なる大文字・小文字の表記を気にすることなくヘッダーにアクセスできるようにします。

Go言語の`net/http`パッケージや`net/textproto`パッケージでは、慣習的にヘッダーキーを「最初の文字とハイフンの後の文字を大文字にし、それ以外を小文字にする」という形式に正規化します。例えば、`accept-encoding`は`Accept-Encoding`に、`user-agent`は`User-Agent`に正規化されます。

### HTTPリクエストスマグリング (HTTP Request Smuggling)

HTTPリクエストスマグリングは、HTTPプロキシサーバーとバックエンドサーバーが、同じHTTPリクエストを異なる方法で解釈する脆弱性を悪用する攻撃手法です。この解釈の不一致は、主に`Content-Length`ヘッダーと`Transfer-Encoding`ヘッダーの処理方法の違いによって引き起こされます。

攻撃者は、プロキシがリクエストの終わりを認識する方法と、バックエンドサーバーがリクエストの終わりを認識する方法の間に不一致を作り出すことで、悪意のあるリクエストを正規のリクエストの「後ろ」に隠して送信します。これにより、バックエンドサーバーは、プロキシが意図しなかったリクエストを処理してしまう可能性があります。

この攻撃は、以下のような影響を及ぼす可能性があります。

*   **認証回避**: 認証されていないリクエストを、認証されたリクエストの一部としてバックエンドに送信し、認証を回避する。
*   **キャッシュポイズニング**: 悪意のあるコンテンツをキャッシュに保存させ、他のユーザーに配信する。
*   **Webアプリケーションファイアウォール (WAF) の回避**: WAFが検出できない形で攻撃ペイロードを送信する。

このコミットで修正された問題は、`Content-Length`ヘッダーの解釈の不一致に関連しています。もし`Content Length`（スペースを含む）のようなヘッダーが、プロキシでは無効なヘッダーとして無視されるか、あるいは異なる方法で処理される一方で、Goのバックエンドサーバーでは`Content-Length`として正規化されて処理された場合、リクエストボディの長さの認識にずれが生じ、スマグリング攻撃の足がかりとなる可能性があります。

### RFC 7230

RFC 7230は、HTTP/1.1のメッセージ構文とルーティングを定義する主要な仕様の一つです。このRFCでは、HTTPヘッダーフィールド名（キー）に使用できる文字セットが厳密に定義されています。

RFC 7230のセクション3.2.6「Field Value Components」では、`token`という概念が定義されており、ヘッダーフィールド名はこの`token`である必要があります。`token`は`tchar`（token character）の1つ以上のシーケンスとして定義されます。

`tchar`は以下の文字のいずれかです。
`tchar = "!" / "#" / "$" / "%" / "&" / "'" / "*" / "+" / "-" / "." / "^" / "_" / "`" / "|" / "~" / DIGIT / ALPHA`

ここで重要なのは、**スペース文字 (` `) は`tchar`に含まれていない**という点です。したがって、`Content Length`のようにスペースを含むヘッダーフィールド名は、RFC 7230の仕様に準拠していません。Goの`net/textproto`が以前行っていた「スペースをハイフンに変換する」という挙動は、このRFCの規定から逸脱しており、それがセキュリティ上の問題を引き起こす原因となっていました。

## 技術的詳細

このコミットの技術的な核心は、`net/textproto`パッケージの`CanonicalMIMEHeaderKey`関数が、RFC 7230に準拠しないヘッダーキー（特にスペースを含むもの）を正規化しないように変更された点にあります。

以前の`CanonicalMIMEHeaderKey`関数は、ヘッダーキー文字列をバイトスライスに変換し、そのバイトスライスを操作する内部関数`canonicalMIMEHeaderKey`を呼び出していました。この`canonicalMIMEHeaderKey`関数内には、`if c == ' ' { c = '-' }`というロジックがあり、これがスペース文字をハイフンに変換していました。この挙動は、前述の通り、特定のウェブカメラからの不正なヘッダーに対応するためのものでしたが、HTTPリクエストスマグリングの脆弱性を生み出す原因となっていました。

このコミットでは、以下の主要な変更が導入されました。

1.  **`validHeaderFieldByte`関数の導入**:
    新しいヘルパー関数`validHeaderFieldByte(b byte) bool`が追加されました。この関数は、与えられたバイト`b`がHTTPヘッダーフィールドキーとして有効な文字であるかどうかを判定します。RFC 7230の`tchar`定義を厳密に適用するのではなく、Goの既存の実装や歴史的な互換性を考慮し、以下の文字を有効としています。
    *   大文字アルファベット (`A` - `Z`)
    *   小文字アルファベット (`a` - `z`)
    *   数字 (`0` - `9`)
    *   ハイフン (`-`)
    コメントには「これは実際にはRFC 7230よりも厳格である」と記載されており、将来的に拡張される可能性も示唆されていますが、現時点ではスペースやその他の特殊文字は無効と判断されます。

2.  **`CanonicalMIMEHeaderKey`の変更**:
    `CanonicalMIMEHeaderKey`関数は、まず入力文字列`s`の各バイトが`validHeaderFieldByte`によって有効であるかをチェックするようになりました。もし1つでも無効なバイト（スペースを含む）が見つかった場合、関数は正規化を行わず、元の文字列`s`をそのまま返します。これにより、不正なヘッダーキーが意図せず正規化されることを防ぎます。

3.  **`canonicalMIMEHeaderKey`の変更**:
    内部関数`canonicalMIMEHeaderKey`も変更されました。この関数は、バイトスライス`a`を受け取りますが、まず`a`内のすべてのバイトが`validHeaderFieldByte`によって有効であるかをチェックします。もし無効なバイトが含まれている場合、この関数も正規化を行わず、元のバイトスライス`a`の文字列コピーをそのまま返します。
    そして、最も重要な変更点として、この関数から`if c == ' ' { c = '-' }`というスペースをハイフンに変換するロジックが完全に削除されました。これにより、スペースを含むヘッダーキーが正規化の過程で変更されることはなくなりました。

4.  **`net/http/header.go`のドキュメント更新**:
    `net/http/header.go`の`CanonicalHeaderKey`関数のドキュメントが更新され、「もし`s`がスペースや無効なヘッダーフィールドバイトを含む場合、変更されずに返される」という旨が追記されました。これは、`CanonicalHeaderKey`が`textproto.CanonicalMIMEHeaderKey`を呼び出すため、その挙動の変更を反映したものです。

これらの変更により、GoのHTTPサーバーは、RFC 7230に準拠しないヘッダーキーを正規化しようとせず、そのままの形で扱うようになります。これにより、プロキシとバックエンドサーバー間でのヘッダー解釈の不一致が減少し、HTTPリクエストスマグリング攻撃のリスクが低減されます。

## コアとなるコードの解説

### `src/net/textproto/reader.go` の変更

1.  **`validHeaderFieldByte` 関数の追加**:
    この新しい関数は、HTTPヘッダーフィールドキーの各バイトが有効な文字であるかをチェックします。有効な文字は、英大文字、英小文字、数字、およびハイフンのみです。これにより、RFC 7230で定義されている`tchar`のサブセットがGoの実装で有効とみなされます。特に、スペース文字はここで無効と判断されます。

2.  **`CanonicalMIMEHeaderKey` の変更**:
    この関数は、ヘッダーキーの正規化を行う主要なエントリポイントです。変更後、まず入力文字列`s`をループし、各文字が`validHeaderFieldByte`によって有効であるかをチェックします。もし1つでも無効な文字（例: スペース）が見つかった場合、この関数は正規化を中断し、元の文字列`s`をそのまま返します。これにより、不正な形式のヘッダーキーが正規化によって変更されることがなくなります。

3.  **`canonicalMIMEHeaderKey` の変更**:
    この内部関数は、バイトスライスを直接操作して正規化を行います。変更後、この関数もまず入力バイトスライス`a`をループし、各バイトが`validHeaderFieldByte`によって有効であるかをチェックします。もし無効なバイトが見つかった場合、この関数も正規化を中断し、元のバイトスライス`a`の文字列コピーを返します。
    最も重要な変更は、以前存在した`if c == ' ' { c = '-' }`というロジックが削除されたことです。これにより、スペースがハイフンに変換される挙動が完全に排除されました。

### `src/net/http/header.go` の変更

`CanonicalHeaderKey`関数のコメントが更新されました。この関数は`textproto.CanonicalMIMEHeaderKey`を呼び出すため、その下層の変更を反映し、「もし`s`がスペースや無効なヘッダーフィールドバイトを含む場合、変更されずに返される」という新しい挙動が明記されました。これは、APIの利用者に対して、ヘッダーキーの正規化が常に発生するわけではないことを明確に伝えるための重要なドキュメント変更です。

### `src/net/textproto/reader_test.go` の変更

テストケースが更新され、新しい挙動が正しく反映されていることを確認しています。
*   以前は`{"C Ontent-Transfer-Encoding", "C-Ontent-Transfer-Encoding"}`のようにスペースがハイフンに変換されることを期待していましたが、変更後は`{"C Ontent-Transfer-Encoding", "C Ontent-Transfer-Encoding"}`のように元の文字列がそのまま返されることを期待するようになりました。
*   同様に、`{"foo bar", "Foo-Bar"}`が`{"foo bar", "foo bar"}`に変更されました。
*   `ReadMIMEHeaderNonCompliant`テストでは、`Audio Mode`というヘッダーキーがそのまま保持されることを確認するようになりました。

これらの変更により、GoのHTTPスタックは、HTTPヘッダーキーの処理においてRFC 7230に厳密に準拠し、潜在的なHTTPリクエストスマグリング攻撃のリスクを軽減します。

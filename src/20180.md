## 元コミット内容

このコミットが元に戻している変更（CL 130240043 / b09f70c301a5）は、Goコンパイラ (`cmd/gc`) において、インターフェースの内部表現を変更することを目的としていました。具体的には、「データワードにポインタのみを格納する」という方針を導入しようとしていました。この変更は、Go 1.4サイクルの終了まで、これに依存する他の変更を行わないという注意書きとともに提案されていました。また、Go issue #8405 を修正する意図があったようです。

## 変更の背景

元々の変更（CL 130240043）は、Goのインターフェースの内部表現をよりシンプルかつ効率的にすることを目的としていた可能性があります。インターフェースのデータワードが常にポインタを保持するようにすることで、コンパイラやランタイムがインターフェース値を扱う際のロジックを簡素化し、パフォーマンスの向上やコードの保守性の改善を図ろうとしたと考えられます。

しかし、この変更は意図しない副作用を引き起こしました。コミットメッセージによると、「`divmod.go` をすべてのARMプラットフォームで壊した」とのことです。これは、インターフェースの内部表現の変更が、特定のアーキテクチャ（ARM）における数値演算（特に除算と剰余）のコード生成やランタイムの動作に悪影響を与えたことを示唆しています。安定性と互換性を維持するため、問題を引き起こした変更を元に戻すことが決定されました。

## 前提知識の解説

### Goのインターフェースの内部表現

Go言語のインターフェースは、その柔軟性と強力な抽象化能力の基盤となっています。内部的には、Goのインターフェース値は通常、2つのワード（ポインタ）で構成される構造体として表現されます。

1.  **型情報 (Type Word / Itab Pointer)**: 最初のワードは、インターフェース値が保持する具体的な型（コンクリート型）に関する情報へのポインタです。このポインタは「itab」（interface table）と呼ばれる構造体を指します。itabには、そのコンクリート型が実装するインターフェースのメソッドセットへのポインタや、型のサイズ、アライメントなどのメタデータが含まれています。これにより、ランタイムはインターフェースを介してメソッド呼び出しを行う際に、正しい具体的なメソッドをディスパッチできます。

2.  **データ情報 (Data Word / Value Pointer)**: 2番目のワードは、インターフェース値が保持する実際のデータへのポインタです。
    *   もしインターフェースに格納される値が既にポインタ型（例: `*MyStruct`）である場合、このデータワードはそのポインタを直接格納します。
    *   もしインターフェースに格納される値が値型（例: `int`, `string`, `struct`）である場合、その値のコピーがヒープ上に割り当てられ、このデータワードはそのヒープ上のコピーへのポインタを格納します。
    *   したがって、Goのインターフェースのデータワードは、常に何らかのポインタを保持するように設計されています。元々の変更は、この「常にポインタを保持する」という性質をより厳密に、あるいは特定の最適化のために強制しようとした可能性があります。

### `divmod.go` と数値演算

`divmod.go` というファイル名から、このファイルが除算（`div`）と剰余（`mod`）に関する操作、あるいはそれらを含む数値演算のテストや実装に関連していると推測されます。Go言語では、整数型に対する除算と剰余演算は、CPUのアーキテクチャに依存する低レベルな命令にコンパイルされることが多く、特にエッジケース（例: ゼロ除算、最小負の整数を-1で割る場合など）では、アーキテクチャ固有の振る舞いや最適化が関わってきます。

### `cmd/gc` (Goコンパイラ)

`cmd/gc` は、Go言語の公式コンパイラです。Goのソースコードを機械語に変換する役割を担っており、型チェック、最適化、コード生成など、コンパイルプロセスの主要な部分を実行します。インターフェースの内部表現のような低レベルな実装の変更は、このコンパイラのコード生成ロジックに直接影響を与えます。

## 技術的詳細

このコミットは、`src/cmd/gc/subr.c` ファイル内の `isdirectiface` 関数に関連する `IfacePointerOnly` という定数の値を `1` から `0` に戻しています。

```c
enum {
    IfacePointerOnly = 0, // 変更後
};
```

### `IfacePointerOnly` フラグの役割

元の変更では `IfacePointerOnly = 1` と設定されていました。これは、コンパイラがインターフェースのデータワードにポインタのみを格納するという新しい規則を適用するためのフラグであったと推測されます。このフラグが `1` の場合、コンパイラはインターフェース値のデータワードが常に有効なポインタを指すように、より厳密なチェックや異なるコード生成戦略を採用した可能性があります。

### ARMプラットフォームでの問題発生の推測

`IfacePointerOnly = 1` の変更がARMプラットフォームで `divmod.go` を壊した原因として、いくつかの可能性が考えられます。

1.  **アライメントとメモリレイアウト**: ARMアーキテクチャは、特定のデータ型に対するメモリのアライメント要件が厳格な場合があります。インターフェースのデータワードがポインタのみを格納するという変更が、コンパイラが生成するコードのメモリレイアウトやアライメントに影響を与え、ARMの特定の命令セットやハードウェアの期待と合致しなくなった可能性があります。これにより、数値データが正しく読み書きされず、`divmod`のような演算で誤った結果が生じたと考えられます。

2.  **ポインタの扱いと最適化**: インターフェースのデータワードが常にポインタであるという前提が、コンパイラのポインタ解析や最適化に影響を与えた可能性があります。例えば、コンパイラが特定の数値型をインターフェースとして扱う際に、ポインタを介したアクセスが非効率になったり、あるいはポインタのデリファレンスに関するバグが導入されたりしたかもしれません。ARMプロセッサは、特定のデータアクセスパターンに対して異なるパフォーマンス特性を持つことがあり、この変更がその特性と衝突した可能性があります。

3.  **ガベージコレクション (GC) との相互作用**: インターフェースの内部表現の変更は、ガベージコレクタがメモリをスキャンし、到達可能なオブジェクトを識別する方法にも影響を与える可能性があります。もしデータワードがポインタであるという新しい規則が、GCのポインタスキャンロジックとARM固有のメモリ管理との間で不整合を引き起こした場合、GCが誤ってメモリを解放したり、重要なデータ構造を破損させたりする可能性も考えられます。これにより、`divmod`のような基本的な演算が不安定になったのかもしれません。

4.  **特定の数値型とインターフェースの変換**: `divmod.go`が壊れたという事実は、特に整数型や浮動小数点型がインターフェースに変換され、その後元の型に戻されて演算されるようなシナリオで問題が発生した可能性を示唆しています。例えば、`int`型の値を`interface{}`として渡し、その後`int`型に型アサーションして除算を行うようなコードパスで、データワードのポインタ表現の変更が原因で、値の取得に失敗したり、不正な値が読み込まれたりしたのかもしれません。

これらの推測は、インターフェースの内部表現という低レベルな変更が、特定のアーキテクチャでどのように予期せぬバグを引き起こしうるかを示しています。

## コアとなるコードの解説

変更されたコードは、`src/cmd/gc/subr.c` 内の `isdirectiface` 関数の一部です。この関数は、Goコンパイラがインターフェースの型情報を処理する際に使用されるユーティリティ関数であると推測されます。

変更内容は、`IfacePointerOnly` という列挙型定数の値を `1` から `0` に戻すことです。

-   `IfacePointerOnly = 1` (変更前): これは、インターフェースのデータワードがポインタのみを保持するという新しいセマンティクスを有効にするためのフラグでした。このフラグが `1` の場合、コンパイラはインターフェースのデータワードの扱いに関して、より厳格なルールや異なるコード生成パスを採用していたと考えられます。
-   `IfacePointerOnly = 0` (変更後): この値を `0` に戻すことで、以前のインターフェースデータワードのセマンティクス（ポインタまたはポインタサイズ以下の非ポインタ値を保持できる）に戻されます。これにより、ARMプラットフォームで発生していた `divmod.go` の問題が解消されることになります。

`if(IfacePointerOnly)` という条件文があることから、このフラグがコンパイラの動作を条件分岐させるために使用されていたことがわかります。フラグを `0` に戻すことで、この条件分岐内の新しいロジックが実行されなくなり、安定した以前の動作が維持されます。

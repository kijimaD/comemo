# [インデックス 25507] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）メカニズムにおける重要な変更の第一歩を示しています。具体的には、これまで集中管理されていたGCコーディネーターの役割を分散型ステートマシンへと移行させるための初期段階として、GCが「オフ」状態（`_GCoff`）から「マーク」状態（`_GCmark`）または「マーク終了」状態（`_GCmarktermination`）へ遷移するトリガーを内部APIとして導入しています。これにより、GCの開始ロジックがより柔軟かつ堅牢になることを目指しています。

## 変更の背景

Goのガベージコレクション（GC）は、そのパフォーマンス特性と並行処理モデルにおいて重要な役割を果たします。従来のGo GCは、GCサイクルの開始と進行を集中型のGCコーディネーターが管理していました。しかし、この集中型アプローチは、特に複数のゴルーチンが同時にGC開始条件を検知した場合に、競合状態や非効率性を引き起こす可能性がありました。

このコミットの主な背景は、GCコーディネーターの集中管理を分散型ステートマシンへと段階的に移行させることにあります。これにより、GCの開始と状態遷移のロジックをより堅牢にし、並行処理環境下でのGCの振る舞いを改善することが目的です。

具体的には、以下の問題意識がありました。

1.  **GC開始の競合**: 複数のゴルーチンが同時にヒープサイズがGCトリガー条件を満たしたことを検知し、それぞれがGCを開始しようと試みる可能性がありました。集中型コーディネーターでは、これを適切に調整する必要があり、複雑さが増していました。
2.  **デバッグモードのバグ**: `gcstoptheworld` デバッグモードにおいて、ヒープトリガーが一度発生しただけで、複数のStop-The-World (STW) GCが連続してトリガーされてしまうというマイナーなバグが存在しました。これは、GC開始ロジックの調整不足に起因していました。
3.  **将来的な拡張性**: 分散型アプローチは、GCの各フェーズの管理をよりモジュール化し、将来的なGCアルゴリズムの改善や並行性の向上に対する拡張性を提供します。

このコミットは、これらの課題に対処するため、GCの「オフ」状態から「マーク」状態への最初の遷移を分散化するための基盤を構築します。これは、Issue #11970 で追跡されていた改善の一部です。

## 前提知識の解説

このコミットの変更を理解するためには、Goランタイムのガベージコレクションに関するいくつかの基本的な概念を理解しておく必要があります。

### Goのガベージコレクション (GC)

GoのGCは、主に**三色マーク＆スイープ**アルゴリズムをベースにした**コンカレントGC**です。これは、プログラムの実行と並行してGCの一部を実行することで、アプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑えることを目指しています。

*   **三色マーク**: オブジェクトを「白（未訪問）」「灰（訪問済みだが参照先未訪問）」「黒（訪問済みかつ参照先も訪問済み）」の3色に分類し、到達可能なオブジェクトをマークします。
*   **スイープ**: マークされなかった（白のままの）オブジェクトを解放します。

### GCフェーズ

GoのGCサイクルは、いくつかのフェーズに分かれています。このコミットで言及されている主要なフェーズは以下の通りです。

*   `_GCoff`: GCが現在実行されていない状態。アプリケーションは自由にメモリを割り当てることができます。
*   `_GCmark`: マークフェーズ。到達可能なオブジェクトを識別します。このフェーズは主にコンカレントに実行されますが、一部STWを伴う場合があります。
*   `_GCmarktermination`: マークフェーズの終了処理。通常、短いSTWを伴い、マークフェーズの最終的なクリーンアップと次のフェーズへの移行準備を行います。

### STW (Stop-The-World)

STWは、GCの特定の段階で、すべてのアプリケーションゴルーチンの実行を一時的に停止させる期間を指します。GoのコンカレントGCはSTW時間を最小限に抑えるように設計されていますが、GCの正確性を保証するためには、一部のクリティカルな操作（例えば、マークフェーズの開始や終了、スイープの開始など）でSTWが必要となります。STW中はアプリケーションの実行が完全に停止するため、その時間は短ければ短いほどアプリケーションのレイテンシに良い影響を与えます。

### GCコーディネーター

従来のGoランタイムでは、GCサイクルの開始、フェーズ遷移、および全体的な進行を管理する集中型のロジック（GCコーディネーター）が存在しました。これは、GCの各ステップを順序立てて実行し、必要に応じてSTWをトリガーする役割を担っていました。このコミットは、この集中型コーディネーターの役割を分散化する第一歩です。

### `semacquire`/`semrelease`

これらはGoランタイム内部で使用されるセマフォ操作です。
*   `semacquire(s, block)`: セマフォ `s` を取得しようとします。`block` が `true` の場合、セマフォが利用可能になるまでブロックします。
*   `semrelease(s)`: セマフォ `s` を解放します。
これらは、複数のゴルーチン間で共有リソースへのアクセスを同期したり、特定のイベントの発生を待機したりするために使用されます。このコミットでは、GC状態遷移の排他制御のために導入されています。

### `memstats.heap_live`, `memstats.next_gc`

これらはGoランタイムのメモリ統計に関連する変数です。
*   `memstats.heap_live`: 現在ヒープ上に存在するライブオブジェクト（GCによって回収されていない、アプリケーションから到達可能なオブジェクト）の合計サイズを示します。
*   `memstats.next_gc`: 次のGCサイクルがトリガーされるべきヒープの目標サイズを示します。
通常、`memstats.heap_live` が `memstats.next_gc` を超えたときにGCがトリガーされます。

## 技術的詳細

このコミットの技術的な核心は、GCの「オフ」状態から「マーク」状態への遷移を、集中型コーディネーターから分散型ステートマシンへと移行させるための基盤を構築することにあります。

### 分散型GC状態遷移の導入

*   **`work.startSema` の導入**: GC状態遷移の排他制御のために、`work` 構造体に `startSema` という `uint32` 型のセマフォが導入されました。これは、複数のゴルーチンが同時にGC開始条件を検知した場合でも、実際にGCを開始する（状態遷移を実行する）のは1つのゴルーチンのみであることを保証するための「トランジションロック」として機能します。
    *   `semacquire(&work.startSema, false)` でセマフォを取得し、`semrelease(&work.startSema)` で解放します。これにより、GC開始処理がアトミックに実行されるようになります。

### GC開始条件の再定義

*   **`shouldtriggergc()` の削除と `gcShouldStart()` の導入**: 従来の `shouldtriggergc()` 関数は削除され、代わりに `gcShouldStart()` という新しい関数が導入されました。
    *   `gcShouldStart(forceTrigger bool)` は、GCが `_GCoff` フェーズにあり、かつ `forceTrigger` が `true` であるか、または `memstats.heap_live` が `memstats.next_gc` 以上である場合に `true` を返します。また、GCが有効 (`memstats.enablegc`) であり、パニック状態ではなく (`panicking == 0`)、`gcpercent` が負でないことも条件に含まれます。
    *   この新しい関数は、GC開始の条件をより明確にし、状態遷移のロジックに組み込むことを可能にします。

### 新しいGC開始API `gcStart()`

*   **`startGC()` から `gcStart()` への移行**: 従来のGC開始関数 `startGC()` は、`startGCCoordinator()` という内部関数にリネームされ、その役割が限定されました。新たに `gcStart()` 関数が導入され、これがGCの「オフ」から「マーク」または「マーク終了」への遷移をトリトリガーする主要なAPIとなります。
    *   `gcStart()` は、`malloc` のようなメモリ割り当てパスから呼び出されることを想定しており、ロックを保持している状態やプリエンプト不可な状況ではGCを開始しないようにガードが設けられています。
    *   `gcStart()` 内では、`work.startSema` を使用してトランジションロックを取得し、GC開始条件を再確認します。これにより、複数のゴルーチンが同時にGC開始を試みても、実際にGCを開始するのは1つだけになります。
    *   デバッグモード (`debug.gcstoptheworld`) の処理も `gcStart()` 内に移動され、複数のSTW GCがトリガーされるバグが修正されています。

### 段階的な移行

*   このコミットは、分散型GCへの「始まり」であり、まだGCサイクルの実際の実行は `startGCCoordinator()` を通じて従来のGCコーディネーターに委ねられています。
*   コミットメッセージにもあるように、今後はスイープ終了やGC初期化のロジックをGCコーディネーターから切り離し、`gcStart()` のような遷移関数へと移動させていく計画です。

### `gcstoptheworld` デバッグモードのバグ修正

*   従来の `startGC` 関数では、`gcstoptheworld` デバッグモードが有効な場合、複数のゴルーチンが同時にヒープトリガーを検知すると、複数のSTW GCが連続して実行される可能性がありました。
*   新しい `gcStart` 関数では、トランジションロック (`work.startSema`) の下でGC開始条件を再確認し、デバッグモードのアップグレードをその後に実行することで、この問題が修正されています。これにより、複数のゴルーチンがトリガーを検知しても、実際にSTW GCを開始するのは一度だけになります。

```go
// 変更前
-	if shouldhelpgc && shouldtriggergc() {
-		startGC(gcBackgroundMode, false)
// 変更後
+	if shouldhelpgc && gcShouldStart(false) {
+		gcStart(gcBackgroundMode, false)
```
`mallocgc` はメモリ割り当てを行う主要な関数です。ここでGC開始の条件チェックと開始処理が行われます。変更前は `shouldtriggergc()` でGCトリガー条件を判断し、`startGC()` でGCを開始していました。変更後は、新しいAPIである `gcShouldStart(false)` で条件を判断し、`gcStart(gcBackgroundMode, false)` でGCを開始するように変更されています。これにより、GC開始ロジックが新しい分散型フレームワークに統合されました。

### `src/runtime/mgc.go` の変更

#### `gcinit()` の変更

```go
// 変更前
// (変更なし)
// 変更後
	memstats.next_gc = heapminimum
	work.startSema = 1
```
`gcinit()` はGCシステムが初期化される際に呼び出されます。ここで `work.startSema` が `1` に初期化されています。これは、GCが「オフ」状態から「マーク」状態への遷移を制御するセマフォであり、初期状態では取得可能（つまり、最初のGC開始が可能）であることを示しています。

#### `shouldtriggergc()` の削除

```go
// 変更前
// func shouldtriggergc() bool {
// 	return memstats.heap_live >= memstats.next_gc && atomicloaduint(&bggc.working) == 0
// }
// 変更後
// (関数全体が削除)
```
従来のGCトリガー条件を判断する `shouldtriggergc()` 関数は削除されました。そのロジックは、より汎用的な `gcShouldStart()` 関数に置き換えられています。

#### `work` 構造体への `startSema` 追加

```go
// 変更前
// var work struct { ... }
// 変更後
var work struct {
	// ... 既存フィールド ...

	// Each type of GC state transition is protected by a lock.
	// Since multiple threads can simultaneously detect the state
	// transition condition, any thread that detects a transition
	// condition must acquire the appropriate transition lock,
	// re-check the transition condition and return if it no
	// longer holds or perform the transition if it does.
	// Likewise, any transition must invalidate the transition
	// condition before releasing the lock. This ensures that each
	// transition is performed by exactly one thread and threads
	// that need the transition to happen block until it has
	// happened.
	//
	// startSema protects the transition from "off" to mark or
	// mark termination.
	startSema uint32

	// ... 既存フィールド ...
}
```
`work` 構造体はGCの作業状態を管理します。ここに `startSema` という `uint32` 型のフィールドが追加されました。このセマフォは、`_GCoff` から `_GCmark` または `_GCmarktermination` への状態遷移を保護するためのトランジションロックとして機能します。これにより、複数のゴルーチンが同時にGC開始を試みても、実際に遷移を実行するのは1つだけであることが保証されます。

#### `GC()` の変更

```go
// 変更前
-	startGC(gcForceBlockMode, false)
// 変更後
+	gcStart(gcForceBlockMode, false)
```
`GC()` は、ユーザーが明示的にGCを要求する際に呼び出される関数です。ここでも、GC開始の呼び出しが `startGC()` から新しい `gcStart()` に変更されています。`gcForceBlockMode` は、GCを強制的にSTWモードで実行することを意味します。

#### `startGC()` の `startGCCoordinator()` へのリネームと変更

```go
// 変更前
// func startGC(mode gcMode, forceTrigger bool) { ... }
// 変更後
// func startGCCoordinator(mode gcMode) { ... }
```
従来の `startGC()` 関数は `startGCCoordinator()` にリネームされ、その役割が変更されました。この関数は、GCコーディネーターゴルーチンを開始し、準備する役割を担います。コミットメッセージにあるように、これは一時的な関数であり、分散型ステートマシンへの移行が完了すれば削除される予定です。この関数は、GCサイクルの実際の実行をまだ集中型コーディネーターに委ねている部分です。

#### `gcShouldStart()` の新規導入

```go
func gcShouldStart(forceTrigger bool) bool {
	return gcphase == _GCoff && (forceTrigger || memstats.heap_live >= memstats.next_gc) && memstats.enablegc && panicking == 0 && gcpercent >= 0
}
```
この新しい関数は、GCが `_GCoff` フェーズにあり、かつGCを開始すべき条件が満たされているかを判断します。
*   `gcphase == _GCoff`: 現在GCが実行されていない状態であること。
*   `(forceTrigger || memstats.heap_live >= memstats.next_gc)`: 強制トリガーであるか、またはライブヒープサイズが次のGC目標サイズを超えていること。
*   `memstats.enablegc`: GCが有効であること。
*   `panicking == 0`: パニック状態ではないこと。
*   `gcpercent >= 0`: GCの割合が有効な値であること。
これらの条件がすべて満たされた場合に `true` を返します。

#### `gcStart()` の新規導入

```go
func gcStart(mode gcMode, forceTrigger bool) {
	// ... ロック保持チェック ...

	useStartSema := mode == gcBackgroundMode
	if useStartSema {
		semacquire(&work.startSema, false)
		// Re-check transition condition under transition lock.
		if !gcShouldStart(forceTrigger) {
			semrelease(&work.startSema)
			return
		}
	}

	// ... gcstoptheworld デバッグモードの処理 ...

	// TODO: Move sweep termination and initialization from the
	// coordinator to here.
	startGCCoordinator(mode)

	if useStartSema {
		semrelease(&work.startSema)
	}
}
```
`gcStart()` は、GCを `_GCoff` から `_GCmark` または `_GCmarktermination` へと遷移させる新しい主要な関数です。
1.  **ロック保持チェック**: `malloc` から呼び出される可能性があるため、現在のゴルーチンがシステムスタック上にあるか、ロックを保持しているか、プリエンプト不可な状態であるかをチェックし、安全でない場合はGC開始をスキップします。
2.  **トランジションロック**: `mode` が `gcBackgroundMode` の場合（つまり、バックグラウンドGCの場合）、`work.startSema` を `semacquire` で取得します。これにより、GC開始処理が排他的に実行されることが保証されます。
3.  **条件の再チェック**: トランジションロックを取得した後、`gcShouldStart()` を再度呼び出してGC開始条件を再チェックします。これは、ロックを取得するまでの間に他のゴルーチンがGCを開始してしまった可能性を考慮するためです。条件が満たされなければ、セマフォを解放して関数を終了します。
4.  **デバッグモードの処理**: `gcstoptheworld` デバッグモードが有効な場合、GCモードを `gcForceMode` または `gcForceBlockMode` にアップグレードします。これにより、デバッグモードでの複数GCトリガーのバグが修正されます。
5.  **コーディネーターの呼び出し**: 現在のところ、実際のGCサイクル実行は `startGCCoordinator(mode)` を呼び出すことで、従来のGCコーディネーターに委ねられています。将来的に、スイープ終了やGC初期化のロジックがこの関数内に移動される予定です。
6.  **セマフォ解放**: トランジションロックを取得していた場合、`semrelease(&work.startSema)` でセマフォを解放します。

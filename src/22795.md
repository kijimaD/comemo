## 変更の背景

Go言語の初期の設計では、生成されるバイナリは静的にリンクされ、すべての依存関係（Goランタイム、標準ライブラリ、サードパーティライブラリなど）が単一の実行ファイルにまとめられていました。これにより、デプロイが容易になるという利点がありましたが、一方で、複数のGoプログラムが同じシステム上で動作する場合、それぞれのバイナリがGoランタイムや共通のライブラリのコピーを持つため、ディスクスペースの消費が増大するという問題がありました。

このコミットは、この問題を解決するための一歩として、GoプログラムがGoの共有ライブラリを動的にリンクできるようにする `-buildmode=shared` オプションのサポートを導入しました。これにより、Goの標準ライブラリなどを共有ライブラリとしてビルドし、複数のGo実行ファイルがそれを共有することで、個々のバイナリサイズを削減し、システムリソースの効率的な利用を目指しました。

ただし、この `-buildmode=shared` は、後にGoモジュールの導入などにより複雑性が増し、Go 1.17以降では事実上非推奨または機能しない状態となっています。このコミットは、その初期の取り組みの一環として位置づけられます。

## 前提知識の解説

### Goリンカ (ld)

Goのビルドプロセスにおいて、`ld` (linker) は、コンパイルされたオブジェクトファイル（`.o` ファイル）やアーカイブファイル（`.a` ファイル）を結合し、最終的な実行可能ファイルやライブラリを生成する役割を担います。シンボル解決、リロケーション、デッドコード排除など、バイナリ生成における重要な処理を行います。

### ビルドモード (buildmode)

Goコンパイラ (`go build`) は、`-buildmode` オプションを通じて、出力されるバイナリの形式を制御します。主なビルドモードは以下の通りです。

*   **`exe` (Executable)**: デフォルトのモードで、単一の実行可能バイナリを生成します。すべての依存関係が静的にリンクされます。
*   **`c-shared` (C Shared Library)**: GoコードをC言語から呼び出し可能な共有ライブラリ（例: `.so`, `.dll`, `.dylib`）としてビルドします。Goの関数をCのABI（Application Binary Interface）に準拠させてエクスポートし、他の言語のアプリケーションから利用できるようにします。
*   **`shared` (Go Shared Library)**: このコミットでサポートが追加されたモードです。Goのパッケージを、他のGoプログラムが動的にリンクできる共有ライブラリとしてビルドします。主な目的は、Goの標準ライブラリなどを共有化し、Goバイナリのサイズを削減することです。
*   **`plugin` (Go Plugin)**: Goプログラムが実行時に動的にロードできるプラグインをビルドします。これは、アプリケーションの機能を拡張するために使用されます。

このコミットは、特に `shared` モードに焦点を当てています。

### シンボル解決とリロケーション

プログラムが複数のオブジェクトファイルやライブラリから構成される場合、それぞれのファイルは他のファイルで定義された関数や変数（シンボル）を参照します。リンカの主要な役割の一つは、これらの参照を解決し、各シンボルがメモリ上のどこに配置されるかを決定することです。このプロセスを「シンボル解決」と呼びます。

「リロケーション」は、シンボル解決の結果に基づいて、コード内のアドレス参照を修正するプロセスです。共有ライブラリでは、ロードされるメモリ上のアドレスが実行時まで確定しないため、位置独立コード (PIC: Position-Independent Code) が生成され、GOT (Global Offset Table) や PLT (Procedure Linkage Table) といったメカニズムを用いて、実行時に正しいアドレスに解決されるようにします。

### デッドコード排除 (Dead Code Elimination)

リンカは、最終的なバイナリに含まれる必要のないコードやデータを特定し、それらを削除する最適化を行います。これをデッドコード排除と呼びます。通常、リンカはプログラムのエントリポイント（例: `main` 関数）から到達可能なコードのみをバイナリに含めます。しかし、共有ライブラリをビルドする際には、将来的に他のプログラムから呼び出される可能性のあるシンボルは、たとえ現在のビルドで直接参照されていなくても、デッドコードとして排除されないようにする必要があります。

### Goのランタイムと標準ライブラリ

Goプログラムは、ガベージコレクション、スケジューラ、I/O処理などを提供するGoランタイムに大きく依存しています。また、`fmt`, `net/http` などの標準ライブラリは、ほとんどのGoアプリケーションで共通して使用されます。`-buildmode=shared` は、これらの共通コンポーネントを共有ライブラリとして提供し、複数のGoバイナリが同じコピーを利用できるようにすることで、メモリフットプリントとディスク使用量を削減することを目指しました。

## 技術的詳細

このコミットは、Goリンカの内部 (`src/cmd/internal/ld`) に多岐にわたる変更を加えて、`-buildmode=shared` のサポートを実現しています。

### `DynlinkingGo()` 関数の導入

`src/cmd/internal/ld/lib.go` に `DynlinkingGo()` という新しいヘルパー関数が導入されました。この関数は、現在のビルドモードが `BuildmodeShared` であるかどうかを判定します。

```go
// DynlinkingGo returns whether we are producing Go code that can live
// in separate shared libraries linked together at runtime.
func DynlinkingGo() bool {
	// TODO(mwhudson): This is a bit silly for now, but it will need to have
	// "|| Linkshared" appended when a subsequent change adds that flag.
	return Buildmode == BuildmodeShared
}
```

この関数は、共有ライブラリをビルドしているか、または共有ライブラリにリンクしているGoプログラムをビルドしているかを判断するための統一された方法を提供し、リンカの様々な箇所で条件分岐の基準として使用されます。

### リロケーション処理の変更

*   **`src/cmd/6l/asm.go`**: x86-64アーキテクチャにおける `R_CALL` リロケーションの処理が変更されました。`DynlinkingGo()` が真の場合、`R_X86_64_GOTPCREL` ではなく `R_X86_64_PLT32` を使用するように変更されています。これは、共有ライブラリからの関数呼び出しが PLT (Procedure Linkage Table) を介して行われる必要があるためです。
*   **`src/cmd/internal/ld/data.go`**: `relocsym` 関数において、シンボルが未定義の場合の処理が変更されました。`BuildmodeShared` の場合、`main.main` や `main.init` といったシンボルが未定義であってもエラーとせず、`SDYNIMPORT` (動的インポートシンボル) としてマークされるようになりました。これは、共有ライブラリとしてビルドされるGoランタイムには `main` 関数が含まれないためです。また、`SDYNIMPORT` シンボルのリロケーション処理も `DynlinkingGo()` の結果に基づいて調整されています。
*   **`.init_array` セクションの追加**: `dodata()` 関数と `doelf()` 関数において、`BuildmodeCShared` または `DynlinkingGo()` の場合に `.init_array` セクションが追加されるようになりました。このセクションは、共有ライブラリがロードされた際に実行される初期化ルーチンへのポインタを格納するために使用されます。

### リンカモードの調整

*   **`src/cmd/6l/obj.go`**: `archinit` 関数において、`BuildmodeCShared` または `DynlinkingGo()` の場合にリンカモードが `LinkExternal` に設定されるようになりました。`LinkExternal` は、Goリンカが外部リンカ（通常はGCC）を呼び出して最終的なバイナリを生成することを意味します。これは、共有ライブラリの生成には外部リンカの機能が必要となるためです。

### デッドコード排除の挙動変更

*   **`src/cmd/internal/ld/go.go`**: `deadcode()` 関数において、`BuildmodeShared` の場合にデッドコード排除のロジックが大きく変更されました。通常、リンカはエントリポイントから到達可能なシンボルのみをマークしますが、`BuildmodeShared` の場合は、すべてのシンボルが到達可能 (`Reachable = true`) とマークされるようになりました。これは、共有ライブラリとしてビルドされるコードは、将来的に他のGoプログラムから呼び出される可能性があるため、たとえ現在のビルドで直接参照されていなくても、デッドコードとして削除されるべきではないからです。

### シンボルテーブルの扱い

*   **`src/cmd/internal/ld/symtab.go`**:
    *   Goの内部シンボル名に含まれる `·` (ミドルドット) を `.` に書き換える処理が、`DynlinkingGo()` が偽の場合にのみ行われるようになりました。これは、動的リンクを行う場合、共有ライブラリのシンボルテーブルから読み取られるシンボル名が正確に一致する必要があるためです。
    *   `putelfsym` 関数において、ELFシンボルのバインディング (`STB_GLOBAL` または `STB_LOCAL`) を決定する際に、新しく導入された `LSym.Local` フィールドが考慮されるようになりました。また、`DynlinkingGo()` が偽の場合にのみ、外部リンカモードでのGoシンボルのバインディングが `STB_LOCAL` に設定されるようになりました。これは、動的リンク時にはすべてのグローバルシンボルが必要となるためです。
    *   `runtime.typelink`, `go.string.*`, `go.func.*`, `runtime.symtab`, `runtime.moduledata` などの特定のランタイムシンボルに対して `Local = true` が設定されるようになりました。これは、これらのシンボルが共有ライブラリの内部でのみ使用され、外部にエクスポートされるべきではないことを示します。

### `BuildmodeShared` の追加と処理

*   **`src/cmd/internal/ld/lib.go`**: `BuildMode` 列挙型に `BuildmodeShared` が追加されました。また、`Set` メソッドと `String` メソッドが更新され、`shared` ビルドモードのパースと文字列変換をサポートするようになりました。現時点では、`shared` モードは `linux/amd64` のみに限定されています。
*   **`libinit()` 関数**: `BuildmodeShared` の場合、`INITENTRY` (初期化エントリポイント) が設定されないようになりました。これは、共有ライブラリには独立したエントリポイントが必要ないためです。
*   **`hostlink()` 関数**: `BuildmodeShared` の場合、外部リンカに `-Wl,-Bsymbolic-functions` と `-shared` フラグが渡されるようになりました。`-Bsymbolic-functions` は、関数参照をシンボリックに解決し、PLTを介した間接呼び出しを避けることでパフォーマンスを向上させる可能性があります。`-shared` は、共有ライブラリを生成するための標準的なリンカフラグです。

### コマンドライン引数の処理

*   **`src/cmd/internal/ld/pobj.go`**: `Ldmain` 関数において、`BuildmodeShared` の場合にコマンドライン引数の処理が変更されました。`buildmode=shared` では、複数のパッケージパスを `pkgpath=file` の形式で指定できるようになり、これにより複数のGoパッケージを一つの共有ライブラリにまとめることが可能になります。

### `LSym.Local` フィールドの追加

*   **`src/cmd/internal/ld/link.go`**: `LSym` 構造体（リンカが扱うシンボルを表す構造体）に `Local` というブール型のフィールドが追加されました。このフィールドは、シンボルがローカル（バイナリ内部でのみ使用される）であるか、それともグローバル（外部から参照可能）であるかを示すために使用されます。このフラグは、シンボルテーブルの生成やリロケーション処理において、シンボルの可視性を制御するために利用されます。

## コアとなるコードの解説

### `DynlinkingGo()` 関数の定義 (`src/cmd/internal/ld/lib.go`)

この関数は、Goリンカの様々な場所で、現在のビルドがGoの共有ライブラリを生成しているか、またはGoの共有ライブラリにリンクしているかを判断するための中心的な役割を果たします。`BuildmodeShared` が設定されている場合に `true` を返します。これにより、リンカは共有ライブラリ特有の挙動（例: シンボル解決、デッドコード排除、リロケーション）を条件付きで適用できるようになります。

### `BuildmodeShared` の追加 (`src/cmd/internal/ld/lib.go`)

`BuildMode` 列挙型に `BuildmodeShared` が追加され、Goリンカがこの新しいビルドモードを認識できるようになりました。`Set` メソッドでは、コマンドラインで `-buildmode=shared` が指定された場合に `BuildmodeShared` を設定し、現時点では `linux/amd64` のみに限定されていることが示されています。`String` メソッドは、このモードの文字列表現を提供します。これにより、Goのビルドシステムは、Goの共有ライブラリを生成するための新しいターゲットをサポートする基盤を得ました。

### `deadcode()` 関数内の `BuildmodeShared` 条件分岐 (`src/cmd/internal/ld/go.go`)

`deadcode()` 関数は、リンカが不要なコードを削除するデッドコード排除のロジックを実装しています。通常モードでは、エントリポイントから到達可能なシンボルのみが保持されます。しかし、`BuildmodeShared` の場合、このコミットはすべてのシンボルを `Reachable = true` とマークするように変更しました。これは、共有ライブラリとしてビルドされるコードは、将来的に他のGoプログラムから動的に呼び出される可能性があるため、たとえ現在のビルドで直接参照されていなくても、デッドコードとして削除されるべきではないという設計思想に基づいています。これにより、共有ライブラリが完全な機能を提供できるようになります。

### `relocsym()` 関数内の `BuildmodeShared` 条件分岐 (`src/cmd/internal/ld/data.go`)

`relocsym()` 関数は、シンボルのリロケーション（アドレス解決）を行う際に、未定義のシンボルを処理します。通常、未定義のシンボルはエラーとなりますが、`BuildmodeShared` の場合、`main.main` や `main.init` といった特定のシンボルが未定義であってもエラーとせず、`SDYNIMPORT` (動的インポートシンボル) として扱われるようになりました。これは、Goの共有ライブラリには独立した `main` 関数が含まれないため、これらのシンボルが未定義であることは正常な状態であるためです。また、`DynlinkingGo()` の結果に基づいて、動的インポートシンボルのリロケーション処理が調整され、共有ライブラリからの参照が正しく解決されるようにしています。

### `putelfsym()` 関数内の `DynlinkingGo()` 条件分岐と `x.Local` の利用 (`src/cmd/internal/ld/symtab.go`)

`putelfsym()` 関数は、ELFバイナリのシンボルテーブルにシンボルを書き込む際に、そのシンボルのバインディング（グローバルかローカルか）を決定します。このコミットでは、`LSym` 構造体に新しく追加された `Local` フィールドが `true` の場合、または `DynlinkingGo()` が真の場合に、シンボルが `STB_LOCAL` としてマークされるようになりました。これにより、共有ライブラリの内部シンボルが外部にエクスポートされるのを防ぎつつ、動的リンクに必要なグローバルシンボルは適切にエクスポートされるように制御しています。また、Goの内部シンボル名に含まれる `·` を `.` に書き換える処理も、`DynlinkingGo()` が偽の場合にのみ行われるようになり、動的リンク時のシンボル名の一致要件に対応しています。

## 変更の背景

Go言語は、その高い並行処理性能とシンプルな構文により、サーバーサイドアプリケーション、クラウドネイティブな開発、CLIツールなど、幅広い分野で人気を集めています。しかし、特定のアーキテクチャでGoプログラムをネイティブに実行するためには、そのアーキテクチャに特化したランタイムサポートが不可欠です。

ARM64（AArch64）アーキテクチャは、モバイルデバイス市場で支配的な地位を確立しているだけでなく、近年ではサーバー、組み込みシステム、高性能コンピューティング（HPC）の分野でも急速に普及しています。特に、AWS GravitonプロセッサのようなクラウドインフラストラクチャにおけるARM64の採用は、その性能と電力効率の高さから注目されています。

このような背景から、GoプログラムがARM64ベースのシステムで効率的に動作できるようにすることは、Go言語のエコシステムを拡大し、より多様なプラットフォームでの利用を可能にする上で極めて重要でした。このコミットは、GoランタイムがARM64アーキテクチャの特性を最大限に活用し、最適なパフォーマンスを発揮するための基盤を築くものです。

## 前提知識の解説

### ARM64アーキテクチャの基本

ARM64（AArch64）は、ARMv8-Aアーキテクチャで導入された64ビット命令セットアーキテクチャです。従来の32ビットARM（AArch32）とは異なる新しい命令セットとレジスタセットを持ちます。

*   **レジスタ**:
    *   汎用レジスタ: X0-X30（64ビット）、W0-W30（Xレジスタの下位32ビット）。X30はリンクレジスタ（LR）として使用されます。
    *   スタックポインタ: SP（64ビット）。
    *   プログラムカウンタ: PC（64ビット）。
    *   ゼロレジスタ: XZR/WZR（常に0）。
    *   浮動小数点/SIMDレジスタ: V0-V31（128ビット）。
*   **命令セット**: 固定長32ビット命令。ロード/ストア命令、データ処理命令、分岐命令などが含まれます。
*   **呼び出し規約（ABI）**: Linux/ARM64の標準ABI（Procedure Call Standard for the ARM 64-bit Architecture）に従います。関数呼び出しでは、最初の8つの引数はX0-X7レジスタで渡され、それ以降はスタックで渡されます。戻り値はX0/X1レジスタで返されます。
*   **メモリモデル**: 厳密なメモリ順序付けを保証するためのバリア命令（DMB, DSB, ISB）が提供されます。アトミック操作には、ロード・エクスクルーシブ（LDXR）とストア・エクスクルーシブ（STXR）命令のペアが使用されます。
*   **ページサイズ**: 一般的に4KBページが使用されますが、より大きなページサイズ（例: 64KB）もサポートされます。

### Goランタイムの基本

Goランタイムは、Goプログラムの実行を管理する重要なコンポーネントです。これには、スケジューラ、メモリマネージャ（ガベージコレクタを含む）、スタック管理、アトミック操作、シグナルハンドリングなどが含まれます。

*   **Goroutine**: Goの軽量な並行処理単位。数千から数百万のGoroutineを同時に実行できます。各Goroutineは独自のスタックを持ちます。
*   **M/P/Gモデル**: Goスケジューラの中心的な概念。
    *   **M (Machine)**: OSスレッドを表します。
    *   **P (Processor)**: 論理プロセッサを表し、Goコードを実行するためのコンテキストを提供します。MとGoroutineを関連付けます。
    *   **G (Goroutine)**: Goroutine自体。
*   **スタック管理**: GoのGoroutineスタックは、必要に応じて動的に伸縮します。スタックの拡張（`morestack`）や縮小はランタイムによって自動的に行われます。
*   **ガベージコレクション（GC）**: Goはトレース型GCを採用しており、不要になったメモリを自動的に解放します。GCはランタイムの一部として動作し、メモリの割り当てと解放を管理します。
*   **アトミック操作**: 複数のGoroutineから共有データに安全にアクセスするための低レベルなプリミティブ（例: Compare-And-Swap (CAS), Add, Exchangeなど）。
*   **シグナルハンドリング**: OSからのシグナル（例: SIGSEGV, SIGINT）を捕捉し、適切に処理するためのメカニズム。クラッシュレポートの生成や、プログラムの正常終了などに利用されます。
*   **システムコール**: GoプログラムがOSの機能（ファイルI/O、ネットワーク通信、メモリ管理など）を利用するためのインターフェース。

### クロスコンパイルとビルドタグ

Goは強力なクロスコンパイル機能を内蔵しており、あるOS/アーキテクチャ上で別のOS/アーキテクチャ向けのバイナリを簡単にビルドできます。この機能は、`GOOS`と`GOARCH`環境変数を設定することで利用されます。

*   `GOOS`: ターゲットOS（例: `linux`, `windows`, `darwin`）。
*   `GOARCH`: ターゲットアーキテクチャ（例: `amd64`, `arm`, `arm64`）。

Goのソースコードでは、`+build`ディレクティブ（ビルドタグ）を使用して、特定のOSやアーキテクチャに固有のコードを条件付きでコンパイルに含めることができます。例えば、`// +build linux,arm64`という行があるファイルは、Linux/ARM64環境でのみコンパイルされます。

## 技術的詳細

このコミットは、GoランタイムがARM64アーキテクチャ上で正しく機能するために必要な、多岐にわたる変更を導入しています。主な変更点は以下の通りです。

1.  **アセンブリコードの実装 (`src/runtime/*.s`)**:
    *   `src/runtime/asm_arm64.s`: Goプログラムのエントリポイント (`runtime·rt0_go`)、Goroutineのコンテキストスイッチ (`runtime·gosave`, `runtime·gogo`)、スタック拡張 (`runtime·morestack`)、システムコール呼び出し、リフレクション呼び出しなど、Goランタイムの根幹をなす低レベルなアセンブリルーチンがARM64用に実装されています。これらはARM64のレジスタ、命令セット、ABIに厳密に従って記述されています。
    *   `src/runtime/atomic_arm64.s`: `xadd`, `xchg`, `cas`などのアトミック操作がARM64のロード・エクスクルーシブ/ストア・エクスクルーシブ命令（LDXR/STXR）を使用して実装されています。これにより、複数のCPUコアからの共有データへの安全かつ効率的なアクセスが保証されます。
    *   `src/runtime/memclr_arm64.s`, `src/runtime/memmove_arm64.s`: メモリのクリアと移動のための最適化されたアセンブリルーチンが提供されます。これらは大量のメモリ操作を高速に行うために重要です。
    *   `src/runtime/rt0_linux_arm64.s`: Linux/ARM64システムにおけるプログラムの初期エントリポイント (`_rt0_arm64_linux`) と、Goランタイムの初期化ルーチン (`runtime·rt0_go`) へのジャンプが定義されています。
    *   `src/runtime/sys_linux_arm64.s`: LinuxシステムコールをARM64上で実行するためのラッパー関数が実装されています。これにより、GoランタイムがOSの機能（メモリ確保、シグナル設定など）を呼び出すことができます。

2.  **アーキテクチャ固有のGoコード (`src/runtime/*.go`)**:
    *   `src/runtime/arch1_arm64.go`, `src/runtime/arch_arm64.go`: ARM64アーキテクチャ固有の定数（例: キャッシュラインサイズ、ポインタサイズ）や型定義（例: `uintreg`）が定義されています。
    *   `src/runtime/defs_linux_arm64.go`: Linux/ARM64システムコールで使用される定数（エラーコード、メモリ保護フラグ、シグナル番号など）や、OS固有の構造体（`timespec`, `sigactiont`, `sigcontext`, `ucontext`など）がGoの型として定義されています。これらはC言語のヘッダファイルからGoに変換されたものです。
    *   `src/runtime/lfstack_linux_arm64.go`: ロックフリースタックの実装に関連する、ポインタとカウンタをパック/アンパックする関数がARM64向けに調整されています。
    *   `src/runtime/os_linux_arm64.go`: Linux/ARM64固有のOS関連のランタイム関数（例: `cputicks`の実装）が含まれています。
    *   `src/runtime/signal_arm64.go`, `src/runtime/signal_linux_arm64.go`: シグナルハンドリングのロジックがARM64向けに実装されています。これには、レジスタのダンプ、シグナルコンテキストの解析、パニック時のスタックフレーム操作などが含まれます。特に、`sigctxt`構造体を通じて、シグナル発生時のCPUレジスタの状態にアクセスできるようになっています。
    *   `src/runtime/zgoarch_arm64.go`: ビルドシステムがARM64アーキテクチャを認識するためのファイルです。

3.  **既存ファイルへの変更**:
    *   `src/runtime/cputicks.go`: ARM64では`cputicks()`が`nanotime()`と`randomNumber`を組み合わせて実装されるため、既存のビルドタグからARM64が除外されています。
    *   `src/runtime/debug/stubs.s`: デバッグ用のスタブにARM64のジャンプ命令が追加されています。
    *   `src/runtime/gcinfo_test.go`, `src/runtime/hash64.go`, `src/runtime/noasm.go`, `src/runtime/panic1.go`: これらのファイルでは、ビルドタグや条件付きコンパイルのロジックに`arm64`が追加され、ARM64環境でも適切にコンパイルされるように変更されています。
    *   `src/runtime/malloc.go`: メモリ割り当ての初期化ルーチンにおいて、ARM64固有の仮想メモリレイアウト（特に3レベル変換バッファを使用する際のユーザーアドレス空間の制限）に対応するための調整が行われています。具体的には、`arenaSize`の計算と`sysReserve`の呼び出しにおけるアドレス範囲の指定がARM64向けに分岐されています。
    *   `src/runtime/mgcmark.go`: ガベージコレクタのスタックフレームスキャンにおいて、ARM64のスタックアライメント（`spAlign`）を考慮するように変更されています。
    *   `src/runtime/proc1.go`: 新しいGoroutineのスタックフレームを準備する際に、ARM64のリンクレジスタ（LR）の扱いを考慮した調整が行われています。

これらの変更は、GoランタイムがARM64プロセッサの特性を理解し、その上でGoの並行処理モデル、メモリ管理、エラーハンドリングなどの機能を効率的かつ正確に実行するための基盤を構築しています。特に、アセンブリ言語での実装は、OSとのインターフェースやパフォーマンスが重要な部分において、アーキテクチャ固有の最適化を可能にしています。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は、主に以下のファイル群に集約されます。

1.  **`src/runtime/asm_arm64.s`**: Goランタイムの低レベルなアセンブリルーチン（Goroutineのスケジューリング、スタック管理、関数呼び出し規約の処理など）のARM64実装。特に`runtime·rt0_go`（プログラムエントリ）、`runtime·gosave`/`runtime·gogo`（コンテキストスイッチ）、`runtime·morestack`（スタック拡張）などが重要です。
2.  **`src/runtime/atomic_arm64.s`**: ARM64アーキテクチャにおけるアトミック操作（CAS, XADD, XCHGなど）のアセンブリ実装。並行処理におけるデータ競合を防ぐために不可欠です。
3.  **`src/runtime/defs_linux_arm64.go`**: Linux/ARM64固有のOS定数や構造体定義。システムコールやシグナルハンドリングのGo側からのインターフェースを提供します。
4.  **`src/runtime/malloc.go`**: メモリ割り当ての初期化ロジックにおけるARM64固有の仮想メモリレイアウト調整。
5.  **`src/runtime/signal_arm64.go` および `src/runtime/signal_linux_arm64.go`**: ARM64環境でのシグナルハンドリングのGoおよびアセンブリ実装。クラッシュ時のレジスタダンプやパニック処理に影響します。
6.  **`src/runtime/sys_linux_arm64.s`**: LinuxシステムコールをARM64上で実行するためのアセンブリラッパー。

## コアとなるコードの解説

### `src/runtime/asm_arm64.s` - `runtime·rt0_go` (プログラムエントリ)

```armasm
TEXT runtime·rt0_go(SB),NOSPLIT,$0
    // SP = stack; R0 = argc; R1 = argv

    // initialize essential registers
    BL  runtime·reginit(SB)

    SUB $32, RSP
    MOVW    R0, 8(RSP) // argc
    MOVD    R1, 16(RSP) // argv

    // create istack out of the given (operating system) stack.
    // _cgo_init may update stackguard.
    MOVD    $runtime·g0(SB), g
    MOVD RSP, R7
    MOVD    $(-64*1024)(R7), R0
    MOVD    R0, g_stackguard0(g)
    MOVD    R0, g_stackguard1(g)
    MOVD    R0, (g_stack+stack_lo)(g)
    MOVD    R7, (g_stack+stack_hi)(g)
    // ... (cgo_init, stackguard update, m0 setup) ...

    BL  runtime·args(SB)
    BL  runtime·osinit(SB)
    BL  runtime·schedinit(SB)

    // create a new goroutine to start program
    MOVD    $runtime·main·f(SB), R0      // entry
    MOVD    RSP, R7
    MOVD.W  $0, -8(R7)
    MOVD.W  R0, -8(R7)
    MOVD.W  $0, -8(R7)
    MOVD.W  $0, -8(R7)
    MOVD    R7, RSP
    BL  runtime·newproc(SB)
    ADD $32, RSP

    // start this M
    BL  runtime·mstart(SB)
    // ... (trap for unreached code) ...
```

`runtime·rt0_go`は、GoプログラムがOSによって起動された際に最初に実行されるアセンブリコードです。
1.  **レジスタ初期化**: `runtime·reginit`を呼び出し、浮動小数点レジスタなどを初期化します。
2.  **引数処理**: `argc`と`argv`（コマンドライン引数の数とポインタ）をスタックに保存します。
3.  **g0 Goroutineのセットアップ**: OSから与えられたスタックを基に、特別なGoroutineである`g0`（スケジューラが使用するGoroutine）のスタック（`stack_lo`, `stack_hi`）とスタックガード（`stackguard0`, `stackguard1`）を設定します。`g0`はGoランタイムの初期化やシステムコール実行時に使用されます。
4.  **ランタイム初期化**: `runtime·args`（引数処理）、`runtime·osinit`（OS固有の初期化）、`runtime·schedinit`（スケジューラ初期化）を順に呼び出します。
5.  **`main` Goroutineの作成**: ユーザーの`main`関数を実行するための新しいGoroutineを作成し、`runtime·newproc`を呼び出してスケジューラに登録します。
6.  **Mの開始**: `runtime·mstart`を呼び出し、現在のOSスレッド（M）でGoroutineの実行を開始します。

このルーチンは、GoプログラムがOSから制御を受け取り、Goランタイムの環境を構築し、最終的にユーザーのGoコードを実行するまでの橋渡しをします。

### `src/runtime/atomic_arm64.s` - `runtime·cas64` (Compare-And-Swap)

```armasm
TEXT runtime·cas64(SB), NOSPLIT, $0-25
    MOVD    ptr+0(FP), R0   // ptr (uint64* val)
    MOVD    old+8(FP), R1   // old (uint64 old)
    MOVD    new+16(FP), R2  // new (uint64 new)
again:
    LDAXR   (R0), R3        // Load-Acquire Exclusive (load *ptr into R3)
    CMP R1, R3              // Compare R1 (old) with R3 (*ptr)
    BNE ok                  // If not equal, jump to ok (CAS fails)
    STLXR   R2, (R0), R3    // Store-Release Exclusive (try to store R2 (new) into *ptr)
    CBNZ    R3, again       // If R3 is non-zero, store failed (contention), retry
ok:
    CSET    EQ, R0          // Set R0 to 1 if comparison was equal (CAS succeeded), else 0
    MOVB    R0, ret+24(FP)  // Store result (bool)
    RET
```

`runtime·cas64`は、64ビット値に対するアトミックなCompare-And-Swap操作を実装しています。
*   `LDAXR (R0), R3`: メモリ位置`R0`から値を排他的にロードし、`R3`に格納します。これは、このメモリ位置に対する排他的なアクセスを開始します。
*   `CMP R1, R3`: ロードした値`R3`が期待される古い値`R1`と等しいか比較します。
*   `BNE ok`: 等しくない場合、CASは失敗し、`ok`ラベルにジャンプします。
*   `STLXR R2, (R0), R3`: 等しい場合、新しい値`R2`をメモリ位置`R0`に排他的にストアしようとします。ストアが成功すると`R3`は0になり、失敗すると非ゼロになります（他のCPUが排他的アクセスを破った場合など）。
*   `CBNZ R3, again`: ストアが失敗した場合（`R3`が非ゼロ）、`again`ラベルに戻り、操作を再試行します。
*   `CSET EQ, R0`: 最終的な比較結果（`CMP R1, R3`）が等しかった場合（CASが成功した場合）、`R0`に1を設定し、そうでなければ0を設定します。
*   `MOVB R0, ret+24(FP)`: 結果を呼び出し元に返します。

このアトミック操作は、ロックフリーデータ構造や並行アルゴリズムにおいて、複数のGoroutineが共有データに安全にアクセスするために不可欠です。

### `src/runtime/malloc.go` - メモリ割り当ての調整

```go
// src/runtime/malloc.go (抜粋)
func mallocinit() {
    // ...
    // If this fails we fall back to the 32 bit memory mechanism
    //
    // However, on arm64, we ignore all this advice above and slam the
    // allocation at 0x40 << 32 because when using 4k pages with 3-level
    // translation buffers, the user address space is limited to 39 bits
    arenaSize := round(_MaxMem, _PageSize)
    bitmapSize = arenaSize / (ptrSize * 8 / 4)
    spansSize = arenaSize / _PageSize * ptrSize
    spansSize = round(spansSize, _PageSize)
    for i := 0; i <= 0x7f; i++ {
        if GOARCH == "arm64" {
            p = uintptr(i)<<40 | uintptrMask&(0x0040<<32)
        } else {
            p = uintptr(i)<<40 | uintptrMask&(0x00c0<<32)
        }
        pSize = bitmapSize + spansSize + arenaSize + _PageSize
        p = uintptr(sysReserve(unsafe.Pointer(p), pSize, &reserved))
        if p != 0 {
            // ...
        }
    }
    // ...
}
```

`mallocinit`関数は、Goランタイムのメモリヒープ（アリーナ）を初期化する際に呼び出されます。このコードスニペットは、仮想メモリ空間におけるアリーナのベースアドレスを決定する部分です。

*   **ARM64固有の考慮事項**: コメントにあるように、ARM64アーキテクチャでは、特に4KBページと3レベル変換バッファを使用する場合、ユーザーアドレス空間が39ビットに制限されることがあります。これは、仮想アドレス空間の利用可能な範囲が他のアーキテクチャ（例: AMD64の48ビット）よりも狭いことを意味します。
*   **アドレスの調整**: `p = uintptr(i)<<40 | uintptrMask&(0x0040<<32)`の行は、このARM64の制約に対応するために、アリーナの開始アドレスを`0x40 << 32`（つまり`0x4000000000`）付近に配置しようとします。これは、Goランタイムが仮想メモリを効率的に管理し、アドレス空間の衝突を避けるための戦略です。
*   **`sysReserve`**: `sysReserve`はOSのシステムコール（Linuxでは`mmap`など）を呼び出して、指定されたアドレス範囲で仮想メモリを予約します。この予約された領域がGoのヒープとして使用されます。

この変更は、GoランタイムがARM64システム上で安定して動作し、メモリを効率的に利用するために不可欠な、アーキテクチャ固有のメモリ管理の調整を示しています。

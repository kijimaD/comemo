## 変更の背景

GoコンパイラのSSA（Static Single Assignment）バックエンドでは、コードの最適化段階で`OpCopy`というコピー命令が生成されることがあります。これらのコピー命令は、レジスタ割り当ての都合や、他の最適化パスの中間結果として一時的に導入されるもので、最終的には除去されるべき「冗長な」命令です。

従来のコピー除去（copy elimination）処理では、`OpCopy`命令が連鎖している場合（例: `x = y`, `y = z`, `z = w`）、各コピー命令の引数を解決するために、その都度チェーンを辿る必要がありました。この「チェーンを辿る」操作が、チェーンの長さnに対してO(n)のコストがかかり、それが各コピー命令に対して行われるため、全体としてO(n^2)の計算量になっていました。

特に、非常に長いコピーチェーンが存在するような稀なケースでは、このO(n^2)の挙動がコンパイル時間を著しく悪化させる原因となっていました。コミットメッセージに示されているベンチマーク結果は、この問題の深刻さを明確に示しています。例えば、`BenchmarkCopyElim100000`では、旧バージョンで31秒以上かかっていた処理が、新バージョンでは約0.1秒にまで短縮されており、99.67%もの改善が達成されています。この劇的な改善は、コンパイラの性能ボトルネックの一つを解消し、大規模なコードベースのコンパイル時間を短縮する上で非常に重要です。

このコミットは、このO(n^2)の問題を解決し、コピーチェーンの長さに線形（O(n)）またはほぼ線形に近い時間でコピー除去を完了できるように、アルゴリズムを再編成することを目的としています。

## 前提知識の解説

### GoコンパイラとSSA (Static Single Assignment)

Goコンパイラは、ソースコードを機械語に変換する過程で、複数のステージを経由します。その中でも重要なのが、中間表現（IR: Intermediate Representation）としてSSA（Static Single Assignment）形式を使用するバックエンドです。

*   **SSA形式**: プログラム中の各変数に一度だけ値を割り当てる（代入する）という特性を持つ中間表現です。これにより、データフロー解析や最適化が容易になります。例えば、`x = a + b; x = c + d;`のようなコードは、SSAでは`x1 = a + b; x2 = c + d;`のように、異なる代入ごとに新しい変数（バージョン）が導入されます。
*   **最適化**: SSA形式のコードに対して、デッドコード除去、共通部分式除去、コピー伝播、レジスタ割り当てなど、様々な最適化が適用されます。これにより、生成される機械語コードの効率が向上します。

### OpCopy (コピー命令)

SSA形式の最適化パスにおいて、`OpCopy`は「ある値が別の値のコピーである」ことを示す特殊な命令です。これは以下のような状況で発生します。

*   **レジスタ割り当ての都合**: 物理レジスタの制約により、あるレジスタの内容を別のレジスタにコピーする必要がある場合。
*   **最適化の中間段階**: ある最適化が適用された結果、一時的に冗長なコピーが生成されることがあります。例えば、`x = y`という代入があった場合、`y`が使われている箇所を直接`x`に置き換える「コピー伝播」が行われるまで、`x`は`y`のコピーとして扱われます。
*   **Phi関数**: 制御フローグラフの複数のパスが合流する点で、異なるバージョンの同じ変数を統合するために使用される仮想的な関数ですが、これも最終的にはコピー命令に変換されることがあります。

`OpCopy`命令自体は計算を行わず、単に値を転送するだけなので、可能な限り除去されるべきです。

### コピー伝播 (Copy Propagation) / コピー除去 (Copy Elimination)

*   **コピー伝播**: `x = y`というコピー命令がある場合、その後のコードで`y`が使用されている箇所を、可能であれば`x`に置き換える最適化です。これにより、`y`のロードや計算が不要になる場合があります。
*   **コピー除去**: コピー伝播の結果、または他の最適化の結果として、もはや不要になった`OpCopy`命令そのものを削除する最適化です。このコミットが対象としているのは、このコピー除去の効率化です。

### O(n^2)問題

*   **計算量**: アルゴリズムの効率性を示す指標で、入力サイズ`n`に対する処理時間の増加率を表します。
*   **O(n^2)**: 入力サイズ`n`が2倍になると、処理時間が4倍になる（`n`の2乗に比例する）ことを意味します。`n`が大きくなると、処理時間は非常に急激に増加します。
*   **問題点**: コピーチェーンの長さ`n`に対して、各コピーを解決するためにチェーンを辿る操作が`n`回行われると、合計で`n * n = n^2`回の操作が必要になります。`n`が100,000のような大きな値になると、`100,000^2 = 10,000,000,000`（100億）回の操作が必要となり、これがコンパイル時間のボトルネックとなります。

### タートルのアルゴリズム (Floyd's Cycle-Finding Algorithm)

このアルゴリズムは、連結リストやグラフなどのデータ構造におけるサイクル（循環参照）を検出するために使用されます。通称「ウサギとカメのアルゴリズム」とも呼ばれます。

*   **原理**: 2つのポインタ（「速いポインタ」と「遅いポインタ」）を使用します。速いポインタは一度に2ステップ進み、遅いポインタは一度に1ステップ進みます。もしデータ構造にサイクルが存在する場合、速いポインタは必ず遅いポインタに追いつき、両者が同じノードを指すことになります。
*   **応用**: このコミットの`copySource`関数では、コピー命令が無限ループ（`x = x`のような直接的なものや、`x = y, y = x`のような間接的なもの）を形成している可能性を検出するために、このアルゴリズムの変形が使用されています。これにより、不正なSSA形式の入力や、最適化パスのバグによって発生しうる無限ループからコンパイラがハングアップするのを防ぎます。

## 技術的詳細

このコミットの核心は、SSA値のコピーチェーンを解決する際に発生していたO(n^2)の計算量を、パス圧縮（path compression）の概念を導入することで改善した点にあります。

### 既存の`copyelim`の課題

変更前の`copyelimValue`関数や`rewrite.go`内のコピー解決ロジックでは、`v.Args[0]`を繰り返し辿ることでコピーチェーンの最終的なソース値を見つけていました。

```go
// 変更前のcopyelimValueの抜粋
for i, a := range v.Args {
    if a.Op != OpCopy {
        continue
    }
    // ... サイクル検出ロジック ...
    for a.Op == OpCopy {
        a = a.Args[0]
        // ... サイクル検出ロジック ...
    }
    v.SetArg(i, a) // ここで最終的なソースに置き換え
    changed = true
}
```

このコードでは、`v.SetArg(i, a)`で`v`の引数を最終的なソース`a`に置き換えますが、これは`v`の引数一つに対してのみ行われます。もし`v`の引数`a`が`copy1 -> copy2 -> ... -> copyN -> source`という長いチェーンの途中にあった場合、`a`を解決するたびに`N`ステップを辿る必要がありました。そして、もし別の値が`copy1`や`copy2`を参照していた場合、それらもまた独立してチェーンを辿ることになり、全体として非効率なO(n^2)の挙動を引き起こしていました。

### 新しい`copySource`関数の導入とパス圧縮

このコミットでは、`copySource(v *Value)`という新しいヘルパー関数が導入されました。この関数は、与えられた`OpCopy`値`v`の最終的な非コピーソースを効率的に見つけ出し、さらにその過程で「パス圧縮」を行います。

1.  **最終ソースの特定**: `copySource`は、`v`から始まり、`v.Args[0]`を繰り返し辿ることで、`OpCopy`ではない最終的なソース値`w`を見つけます。
2.  **サイクル検出**: この探索中に、タートルのアルゴリズム（`slow`と`advance`ポインタ）を使用して、コピーチェーン内に無限ループ（循環参照）がないかをチェックします。もしサイクルが検出された場合、そのサイクル内の値を`OpUnknown`にリセットしてループを中断し、コンパイラのハングアップを防ぎます。
3.  **パス圧縮**: 最終的なソース`w`が見つかった後、`copySource`は元の`v`から`w`に至るまでのパス上のすべての`OpCopy`値の引数を、直接`w`を指すように更新します。

```go
// copySource returns the (non-copy) op which is the
// ultimate source of v.  v must be a copy op.
func copySource(v *Value) *Value {
    w := v.Args[0]

    // This loop is just:
    // for w.Op == OpCopy {
    //     w = w.Args[0]
    // }
    // but we take some extra care to make sure we
    // don't get stuck in an infinite loop.
    // Infinite copy loops may happen in unreachable code.
    // (TODO: or can they?  Needs a test.)
    slow := w
    var advance bool
    for w.Op == OpCopy {
        w = w.Args[0]
        if w == slow { // サイクル検出
            w.reset(OpUnknown) // サイクルを壊す
            break
        }
        if advance {
            slow = slow.Args[0]
        }
        advance = !advance
    }

    // The answer is w.  Update all the copies we saw
    // to point directly to w.  Doing this update makes
    // sure that we don't end up doing O(n^2) work
    // for a chain of n copies.
    for v != w { // パス圧縮
        x := v.Args[0]
        v.SetArg(0, w) // vの引数を直接最終ソースwに設定
        v = x          // 次のコピーに進む
    }
    return w
}
```

このパス圧縮により、一度`copySource`が呼び出されてコピーチェーンが解決されると、そのチェーン上のすべてのコピー命令は直接最終ソースを指すようになります。これにより、次に同じチェーン上のコピー命令が解決される際には、O(1)の時間で最終ソースに到達できるようになり、全体としての計算量が大幅に削減されます。これは、Union-Findデータ構造におけるパス圧縮と非常に似たアプローチです。

### `copyelimValue`と`rewrite.go`での`copySource`の利用

*   **`copyelimValue`**: 各SSA値`v`の引数`a`が`OpCopy`である場合、`copySource(a)`を呼び出して最終ソースを取得し、`v.SetArg(i, copySource(a))`で引数を直接そのソースに置き換えます。これにより、`copyelimValue`自体がO(n^2)になるのを防ぎます。
*   **`rewrite.go`**: コンパイラの書き換えパス（rewrite pass）でも同様にコピーチェーンの解決が必要な箇所がありましたが、ここでも重複していたコピー解決ロジックが削除され、新しく導入された`copySource`関数が利用されるようになりました。これにより、コードの重複が排除され、一貫性が保たれます。

### ベンチマーク結果が示す性能改善の理由

ベンチマーク結果は、`n`が大きくなるにつれて性能改善の度合いが劇的に増加していることを示しています。

*   `BenchmarkCopyElim1` (n=1): ほぼ変化なし。単一のコピーではO(n^2)の問題は顕在化しないため。
*   `BenchmarkCopyElim1000` (n=1000): 82.85%改善。
*   `BenchmarkCopyElim100000` (n=100000): 99.67%改善。

これは、パス圧縮によって、コピーチェーンの解決がO(n^2)からほぼO(n)に近づいたことを明確に裏付けています。`n`が大きくなるほど、O(n^2)とO(n)の差は指数関数的に開くため、このような劇的な改善が見られます。

## コアとなるコードの解説

### `copySource`関数の詳細

`copySource`関数は、このコミットの性能改善の鍵となる部分です。

```go
func copySource(v *Value) *Value {
    w := v.Args[0] // 最初のコピーの引数をwとする

    // タートルのアルゴリズムによるサイクル検出
    slow := w
    var advance bool
    for w.Op == OpCopy { // wがコピーである限りループ
        w = w.Args[0] // wは1ステップ進む
        if w == slow { // wがslowに追いついたらサイクル検出
            w.reset(OpUnknown) // サイクルを壊す（OpUnknownに設定）
            break
        }
        if advance { // advanceがtrueの場合のみslowも1ステップ進む
            slow = slow.Args[0]
        }
        advance = !advance // advanceを反転させ、slowが2ステップごとに進むようにする
    }

    // パス圧縮
    // vが最終ソースwと異なる限りループ
    for v != w {
        x := v.Args[0]     // vの現在の引数を一時的に保存
        v.SetArg(0, w)     // vの引数を直接最終ソースwに設定（パス圧縮）
        v = x              // vを元の引数xに進める
    }
    return w // 最終ソースwを返す
}
```

1.  **初期化**: `w`は最初のコピーの引数で初期化されます。`slow`も`w`で初期化され、`advance`は`false`です。
2.  **サイクル検出ループ**:
    *   `w.Op == OpCopy`である限り、`w`は`w.Args[0]`に進みます。
    *   `w == slow`になった場合、サイクルが検出されたことを意味します。この場合、`w.reset(OpUnknown)`を呼び出して、サイクル内の値を`OpUnknown`に設定し、コンパイラが無限ループに陥るのを防ぎます。その後、ループを`break`します。
    *   `advance`フラグは、`slow`ポインタが`w`の半分の速度で進むように制御します。`advance`が`true`のときだけ`slow`が進み、その後`advance`が反転します。これにより、`w`が2ステップ進む間に`slow`が1ステップ進むことになります。
3.  **パス圧縮ループ**:
    *   サイクル検出ループが終了した後、`w`はコピーチェーンの最終的な非コピーソースを指しています。
    *   `for v != w`ループは、元の`v`から最終ソース`w`までのパス上のすべてのコピー命令を処理します。
    *   `x := v.Args[0]`で、現在の`v`の元の引数を一時的に保存します。
    *   `v.SetArg(0, w)`で、現在の`v`の引数を直接最終ソース`w`に設定します。これがパス圧縮の核心です。
    *   `v = x`で、`v`を元の引数（つまり、チェーンの次のコピー）に進めます。
    *   このループが終了すると、元の`v`から`w`に至るまでのすべてのコピー命令が直接`w`を指すようになり、将来の参照がO(1)で解決できるようになります。

### `copyelim`関数の変更点

`copyelim`関数は、SSAグラフ全体を走査し、`OpCopy`命令を排除します。

```go
func copyelim(f *Func) {
    // すべての値を変更し、OpCopyの引数を含むいかなる引数もコピーではないようにする。
    for _, b := range f.Blocks {
        for _, v := range b.Values {
            copyelimValue(v) // 各値の引数を処理
        }
    }

    // ブロックの制御値を更新する。
    for _, b := range f.Blocks {
        if v := b.Control; v != nil && v.Op == OpCopy {
            b.SetControl(v.Args[0]) // 制御値がコピーなら、その引数に直接置き換える
        }
    }

    // 名前付き変数を更新する。
    for _, name := range f.Names {
        values := f.NamedValues[name]
        for i, v := range values {
            if v.Op == OpCopy {
                values[i] = v.Args[0] // 名前付き変数がコピーなら、その引数に直接置き換える
            }
        }
    }
}
```

*   `copyelimValue(v)`の呼び出しにより、各SSA値の引数に含まれるコピーチェーンが`copySource`によって効率的に解決されます。
*   ブロックの制御値（`b.Control`）や名前付き変数（`f.NamedValues`）も、直接`OpCopy`を参照している場合は、その引数（つまり、`copySource`によって解決された最終ソース）に置き換えられます。

これらの変更により、GoコンパイラのSSAバックエンドにおけるコピー除去処理が、大規模なコピーチェーンに対しても非常に効率的に動作するようになりました。

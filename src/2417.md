具体的な変更内容は、コンパイラのバックエンドにおけるコード生成戦略の改善に焦点を当てています。特に、複雑な式のアドレス計算やレジスタ割り当て、特定の演算（バイト乗算など）の効率的な処理方法に関する調整が行われています。これは、生成される機械語コードの効率性や正確性を向上させるための継続的な取り組みの一環です。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの初期のバックエンド構造と、一般的なコンパイラ最適化の概念に関する知識が必要です。

1.  **Goコンパイラ `8g`**:
    Go言語の初期のコンパイラは、ターゲットアーキテクチャごとに異なる名前を持っていました。`8g`はx86-64アーキテクチャ（64ビットIntel/AMDプロセッサ）向けのコンパイラを指します。これらのコンパイラは、Plan 9 Cコンパイラの設計思想を継承しており、非常にシンプルで高速なコンパイルを特徴としていました。

2.  **コンパイラのフェーズ**:
    一般的なコンパイラは、ソースコードを機械語に変換する過程で複数のフェーズを経ます。
    *   **フロントエンド**: 字句解析、構文解析、意味解析を行い、抽象構文木（AST）を生成します。
    *   **中間コード生成**: ASTから、プラットフォームに依存しない中間表現（IR）を生成します。
    *   **バックエンド**: IRをターゲットアーキテクチャの機械語に変換します。このフェーズには、最適化、レジスタ割り当て、コード生成が含まれます。
    このコミットは主にバックエンド、特にコード生成とレジスタ割り当てのフェーズに関わります。

3.  **`cgen`, `agen`, `ggen`, `gsubr`**:
    これらは`8g`コンパイラのバックエンドにおける主要なモジュール（ファイル）です。
    *   `cgen.c`: "Code Generation" の略で、主に式の評価やステートメントの実行に対応する機械語コードを生成します。
    *   `agen.c`: "Address Generation" の略で、変数や配列要素などのメモリアドレスを計算し、そのアドレスをレジスタにロードするコードを生成します。
    *   `ggen.c`: "General Generation" の略で、特定の種類のコード生成（例: シフト演算、乗算など）やヘルパー関数を提供します。
    *   `gsubr.c`: "General Subroutines" の略で、レジスタ割り当てや型変換など、コード生成全体で利用されるユーティリティ関数やサブルーチンを含みます。

4.  **Ullman Number (ウルマン数)**:
    コンパイラ最適化において、式の評価順序を決定するために使用されるヒューリスティックな値です。各ノード（演算子やオペランド）にウルマン数を割り当て、その値に基づいてレジスタの使用効率を最大化するように評価順序を決定します。`UINF` (Ullman Infinity) は、非常に複雑な式や、レジスタに保持するのが難しい式を示すために使われることがあります。`nl->ullman >= UINF`のような条件は、そのオペランドがレジスタに保持するのが難しい、あるいは多くのレジスタを必要とすることを示唆しています。

5.  **レジスタ割り当て**:
    CPUのレジスタは高速ですが数が限られています。コンパイラは、プログラムの実行中にどの値をどのレジスタに格納するかを決定する「レジスタ割り当て」を行います。効率的なレジスタ割り当ては、メモリへのアクセスを減らし、プログラムの実行速度を向上させます。`regalloc`や`regfree`といった関数は、レジスタの確保と解放を管理します。

6.  **浮動小数点演算**:
    x86アーキテクチャでは、浮動小数点演算は専用の浮動小数点ユニット（FPU）またはSSE/AVX命令セットによって処理されます。FPUは通常、スタックベースのレジスタ（ST(0)からST(7)）を使用し、SSE/AVXはXMMレジスタを使用します。このコミットの時期（2009年）では、FPUスタックレジスタ（`D_F0`から`D_F7`）がまだ主要な浮動小数点レジスタとして扱われていた可能性があります。

## 技術的詳細

このコミットは、`8g`コンパイラのコード生成ロジックにおけるいくつかの重要な調整を含んでいます。

1.  **バイナリ演算の評価順序の変更 (`cgen.c`)**:
    `cgen`関数内で、二項演算（例: `+`, `*`）の両方のオペランドが複雑（`ullman >= UINF`）である場合、以前は右オペランドを先に評価して一時変数に格納していましたが、このコミットでは左オペランドを先に評価するように変更されました。これは、特定のケースでレジスタの使用効率を改善したり、コード生成の安定性を高めたりするためのヒューリスティックな調整と考えられます。

2.  **バイト乗算の最適化 (`cgen.c`, `ggen.c`)**:
    `cgen`関数に`cgen_bmul`という新しいヘルパー関数への呼び出しが追加されました。これは、バイト（8ビット）値の乗算を効率的に処理するためのものです。`ggen.c`に実装された`cgen_bmul`は、8ビットのオペランドを16ビットのレジスタに拡張（符号拡張またはゼロ拡張）し、16ビットの乗算を実行してから、結果を元のバイトサイズに切り詰めるという戦略を取ります。これは、x86アーキテクチャにおいて8ビット直接乗算命令が限られているか、あるいは16ビット乗算の方が効率的である場合に有効な最適化です。

3.  **インデックス計算の型統一 (`cgen.c`)**:
    `agen`関数内の`OINDEX`（配列インデックスアクセス）の処理において、一時変数の型が`nr->type`から`types[TINT32]`に統一されました。これは、インデックス計算を常に32ビット整数で行うことで、コンパイラの内部処理を簡素化し、潜在的な型ミスマッチやプラットフォーム間の差異によるバグを防ぐことを目的としている可能性があります。特に64ビット環境で32ビットインデックスを使用することは、アドレス計算のオーバーフローに注意が必要ですが、当時のGoの設計では一般的なアプローチでした。

4.  **レジスタ割り当ての簡素化と厳格化 (`gsubr.c`)**:
    *   **整数レジスタ**: `regalloc`関数において、`TINT8`, `TUINT8`などの小さな整数型に対する特別なレジスタ範囲（`D_AL`から`D_BH`）の考慮が削除され、すべての整数型が`D_AX`から`D_DI`までの汎用レジスタプールを使用するように統一されました。これは、レジスタ割り当てロジックを簡素化し、より一貫性のあるアプローチを取るための変更です。
    *   **浮動小数点レジスタ**: `ginit`と`gclean`から浮動小数点レジスタ（`D_F0`から`D_F7`）の初期化とクリーンアップのロジックが削除されました。また、`regalloc`では浮動小数点型に対して常に`D_F0`を割り当てるように変更されました。これは、浮動小数点演算が主にFPUスタックのトップ（ST(0)）を使用するモデルに依存しているか、あるいはより高度な浮動小数点レジスタ割り当てが後のフェーズや別のモジュールで処理されることを示唆しています。
    *   `gmove`関数では、浮動小数点レジスタからメモリへの移動時に、ソースレジスタが`D_F0`でない場合に`fatal`エラーを発生させるチェックが追加されました。これは、浮動小数点値がメモリに書き込まれる前に`D_F0`に移動されるべきという厳格なルールを強制するものです。

5.  **浮動小数点型変換の改善 (`gsubr.c`)**:
    `gmove`関数における`TFLOAT32`と`TFLOAT64`間の型変換ロジックがより詳細になりました。`AFMOVDP`（float to double）や`AFMOVFP`（double to float）といった特定のFPU命令が明示的に使用され、レジスタ間の変換や一時変数の使用が考慮されています。これにより、浮動小数点型の精度変換がより正確かつ効率的に行われるようになります。

## コアとなるコードの変更箇所

### `src/cmd/8g/cgen.c`
- `cgen`関数内のバイナリ演算（`OADD`, `OMUL`など）で、両オペランドが複雑な場合の評価順序を左オペランド優先に変更。
- `OADD`, `OMUL`に対して、`AIMULB`が返された場合に`cgen_bmul`を呼び出すロジックを追加。
- `agen`関数内の`OREGISTER`ノードが`addable`な場合に`fatal`エラーを追加。
- `agen`関数内の`OINDEX`処理で、一時変数の型を`types[TINT32]`に統一。

### `src/cmd/8g/ggen.c`
- `cgen_bmul`関数を新規実装。バイト乗算を16ビットレジスタに拡張して処理する。

### `src/cmd/8g/gsubr.c`
- `ginit`と`gclean`から浮動小数点レジスタの初期化/クリーンアップロジックを削除。
- `regalloc`関数で、整数レジスタの割り当て範囲を`D_AX`から`D_DI`に統一。
- `regalloc`関数で、浮動小数点型に対して常に`D_F0`を割り当てるように変更。
- `gmove`関数で、浮動小数点レジスタからメモリへの移動時に`D_F0`以外のレジスタを禁止するチェックを追加。
- `gmove`関数で、`TFLOAT32`と`TFLOAT64`間の型変換ロジックを`AFMOVDP`, `AFMOVFP`命令を用いて詳細化。

### `cgen.c`におけるバイナリ演算の評価順序変更

```c
// 変更前
// tempalloc(&n1, nr->type);
// cgen(nr, &n1);
// n2 = *n;
// n2.right = &n1;
// cgen(&n2, res);

// 変更後

```
この変更は、二項演算のコード生成において、両方のオペランドが複雑な場合に、左オペランドを先に評価して一時変数に格納するように修正しています。これは、コンパイラが生成するコードの効率性や、レジスタの利用状況を改善するためのヒューリスティックな調整です。特定のCPUアーキテクチャや命令セットの特性に合わせて、より良いコードを生成するための試みと考えられます。

### `ggen.c`における`cgen_bmul`の実装

```c
void
cgen_bmul(int op, Node *nl, Node *nr, Node *res)
{
	Node n1b, n2b, n1w, n2w;
	Type *t;
	int a;

	// オペランドの複雑度に応じて評価順序を決定し、バイトレジスタにロード
	if(nl->ullman >= nr->ullman) {
		regalloc(&n1b, nl->type, res);
		cgen(nl, &n1b);
		regalloc(&n2b, nr->type, N);
		cgen(nr, &n2b);
	} else {
		regalloc(&n2b, nr->type, N);
		cgen(nr, &n2b);
		regalloc(&n1b, nl->type, res);
		cgen(nl, &n1b);
	}

	// バイトレジスタからショート（16ビット）レジスタにコピー（拡張）
	t = types[TUINT16];
	if(issigned[nl->type->etype])
		t = types[TINT16];

	regalloc(&n2w, t, &n2b);
	cgen(&n2b, &n2w);

	regalloc(&n1w, t, &n1b);
	cgen(&n1b, &n1w);

	// 16ビット乗算命令を生成
	a = optoas(op, t);
	gins(a, &n2w, &n1w); // n1w = n1w * n2w

	// 結果を元のバイトレジスタに戻し、最終結果にコピー
	cgen(&n1w, &n1b);
	cgen(&n1b, res);

	// レジスタを解放
	regfree(&n1w);
	regfree(&n2w);
	regfree(&n1b);
	regfree(&n2b);
}
```
この関数は、8ビット整数（バイト）の乗算を処理するために導入されました。x86アーキテクチャでは、8ビットの乗算命令は結果が16ビットになるため、直接8ビットレジスタで完結する乗算は効率的ではありません。この`cgen_bmul`は、オペランドを一時的に16ビットレジスタに拡張し（符号付きの場合は符号拡張、符号なしの場合はゼロ拡張）、16ビットの乗算命令を実行します。その後、結果を再び8ビットレジスタに格納し、最終的な結果として返します。これにより、バイト乗算がより正確かつ効率的に処理されるようになります。

    一般的なコンパイラは、ソースコードを機械語に変換する過程で複数のフェーズを経ます。
    *   **フロントエンド**: 字句解析、構文解析、意味解析を行い、抽象構文木（AST）を生成します。
    *   **中間コード生成**: ASTから、プラットフォームに依存しない中間表現（IR）を生成します。
    *   **バックエンド**: IRをターゲットアーキテクチャの機械語に変換します。このフェーズには、最適化、レジスタ割り当て、コード生成が含まれます。
    このコミットは主にバックエンド、特にコード生成とレジスタ割り当てのフェーズに関わります。

3.  **`cgen`, `agen`, `ggen`, `gsubr`**:
    これらは`8g`コンパイラのバックエンドにおける主要なモジュール（ファイル）です。
    *   `cgen.c`: "Code Generation" の略で、主に式の評価やステートメントの実行に対応する機械語コードを生成します。
    *   `agen.c`: "Address Generation" の略で、変数や配列要素などのメモリアドレスを計算し、そのアドレスをレジスタにロードするコードを生成します。
    *   `ggen.c`: "General Generation" の略で、特定の種類のコード生成（例: シフト演算、乗算など）やヘルパー関数を提供します。
    *   `gsubr.c`: "General Subroutines" の略で、レジスタ割り当てや型変換など、コード生成全体で利用されるユーティリティ関数やサブルーチンを含みます。

4.  **Ullman Number (ウルマン数)**:
    コンパイラ最適化において、式の評価順序を決定するために使用されるヒューリスティックな値です。各ノード（演算子やオペランド）にウルマン数を割り当て、その値に基づいてレジスタの使用効率を最大化するように評価順序を決定します。`UINF` (Ullman Infinity) は、非常に複雑な式や、レジスタに保持するのが難しい式を示すために使われることがあります。`nl->ullman >= UINF`のような条件は、そのオペランドがレジスタに保持するのが難しい、あるいは多くのレジスタを必要とすることを示唆しています。

5.  **レジスタ割り当て**:
    CPUのレジスタは高速ですが数が限られています。コンパイラは、プログラムの実行中にどの値をどのレジスタに格納するかを決定する「レジスタ割り当て」を行います。効率的なレジスタ割り当ては、メモリへのアクセスを減らし、プログラムの実行速度を向上させます。`regalloc`や`regfree`といった関数は、レジスタの確保と解放を管理します。

6.  **浮動小数点演算**:
    x86アーキテクチャでは、浮動小数点演算は専用の浮動小数点ユニット（FPU）またはSSE/AVX命令セットによって処理されます。FPUは通常、スタックベースのレジスタ（ST(0)からST(7)）を使用し、SSE/AVXはXMMレジスタを使用します。このコミットの時期（2009年）では、FPUスタックレジスタ（`D_F0`から`D_F7`）がまだ主要な浮動小数点レジスタとして扱われていた可能性があります。

## 技術的詳細

このコミットは、`8g`コンパイラのコード生成ロジックにおけるいくつかの重要な調整を含んでいます。

1.  **バイナリ演算の評価順序の変更 (`cgen.c`)**:
    `cgen`関数内で、二項演算（例: `+`, `*`）の両方のオペランドが複雑（`ullman >= UINF`）である場合、以前は右オペランドを先に評価して一時変数に格納していましたが、このコミットでは左オペランドを先に評価するように変更されました。これは、特定のケースでレジスタの使用効率を改善したり、コード生成の安定性を高めたりするためのヒューリスティックな調整と考えられます。

2.  **バイト乗算の最適化 (`cgen.c`, `ggen.c`)**:
    `cgen`関数に`cgen_bmul`という新しいヘルパー関数への呼び出しが追加されました。これは、バイト（8ビット）値の乗算を効率的に処理するためのものです。`ggen.c`に実装された`cgen_bmul`は、8ビットのオペランドを16ビットのレジスタに拡張（符号拡張またはゼロ拡張）し、16ビットの乗算を実行してから、結果を元のバイトサイズに切り詰めるという戦略を取ります。これは、x86アーキテクチャにおいて8ビット直接乗算命令が限られているか、あるいは16ビット乗算の方が効率的である場合に有効な最適化です。

3.  **インデックス計算の型統一 (`cgen.c`)**:
    `agen`関数内の`OINDEX`（配列インデックスアクセス）の処理において、一時変数の型が`nr->type`から`types[TINT32]`に統一されました。これは、インデックス計算を常に32ビット整数で行うことで、コンパイラの内部処理を簡素化し、潜在的な型ミスマッチやプラットフォーム間の差異によるバグを防ぐことを目的としている可能性があります。特に64ビット環境で32ビットインデックスを使用することは、アドレス計算のオーバーフローに注意が必要ですが、当時のGoの設計では一般的なアプローチでした。

4.  **レジスタ割り当ての簡素化と厳格化 (`gsubr.c`)**:
    *   **整数レジスタ**: `regalloc`関数において、`TINT8`, `TUINT8`などの小さな整数型に対する特別なレジスタ範囲（`D_AL`から`D_BH`）の考慮が削除され、すべての整数型が`D_AX`から`D_DI`までの汎用レジスタプールを使用するように統一されました。これは、レジスタ割り当ての複雑さを軽減し、より一貫性のあるアプローチを取るための変更です。
    *   **浮動小数点レジスタ**: `ginit`と`gclean`から浮動小数点レジスタ（`D_F0`から`D_F7`）の初期化とクリーンアップのロジックが削除されました。また、`regalloc`では浮動小数点型に対して常に`D_F0`を割り当てるように変更されました。これは、浮動小数点演算が主にFPUスタックのトップ（ST(0)）を使用するモデルに依存しているか、あるいはより高度な浮動小数点レジスタ割り当てが後のフェーズや別のモジュールで処理されることを示唆しています。
    *   `gmove`関数では、浮動小数点レジスタからメモリへの移動時に、ソースレジスタが`D_F0`でない場合に`fatal`エラーを発生させるチェックが追加されました。これは、浮動小数点値がメモリに書き込まれる前に`D_F0`に移動されるべきという厳格なルールを強制するものです。

5.  **浮動小数点型変換の改善 (`gsubr.c`)**:
    `gmove`関数における`TFLOAT32`と`TFLOAT64`間の型変換ロジックがより詳細になりました。`AFMOVDP`（float to double）や`AFMOVFP`（double to float）といった特定のFPU命令が明示的に使用され、レジスタ間の変換や一時変数の使用が考慮されています。これにより、浮動小数点型の精度変換がより正確かつ効率的に行われるようになります。

## コアとなるコードの変更箇所

### `src/cmd/8g/cgen.c`
- `cgen`関数内のバイナリ演算（`OADD`, `OMUL`など）で、両オペランドが複雑な場合の評価順序を左オペランド優先に変更。
- `OADD`, `OMUL`に対して、`AIMULB`が返された場合に`cgen_bmul`を呼び出すロジックを追加。
- `agen`関数内の`OREGISTER`ノードが`addable`な場合に`fatal`エラーを追加。
- `agen`関数内の`OINDEX`処理で、一時変数の型を`types[TINT32]`に統一。

### `src/cmd/8g/ggen.c`
- `cgen_bmul`関数を新規実装。バイト乗算を16ビットレジスタに拡張して処理する。

### `src/cmd/8g/gsubr.c`
- `ginit`と`gclean`から浮動小数点レジスタの初期化/クリーンアップロジックを削除。
- `regalloc`関数で、整数レジスタの割り当て範囲を`D_AX`から`D_DI`に統一。
- `regalloc`関数で、浮動小数点型に対して常に`D_F0`を割り当てるように変更。
- `gmove`関数で、浮動小数点レジスタからメモリへの移動時に`D_F0`以外のレジスタを禁止するチェックを追加。
- `gmove`関数で、`TFLOAT32`と`TFLOAT64`間の型変換ロジックを`AFMOVDP`, `AFMOVFP`命令を用いて詳細化。

## コアとなるコードの解説

### `cgen.c`におけるバイナリ演算の評価順序変更

```c
// 変更前
// tempalloc(&n1, nr->type);
// cgen(nr, &n1);
// n2 = *n;
// n2.right = &n1;
// cgen(&n2, res);

// 変更後
tempalloc(&n1, nl->type); // 左オペランドの型で一時変数を確保
cgen(nl, &n1);           // 左オペランドを先に評価
n2 = *n;
n2.left = &n1;           // 評価済みの左オペランドをノードに設定
cgen(&n2, res);
```
この変更は、二項演算のコード生成において、両方のオペランドが複雑な場合に、左オペランドを先に評価して一時変数に格納するように修正しています。これは、コンパイラが生成するコードの効率性や、レジスタの利用状況を改善するためのヒューリスティックな調整です。特定のCPUアーキテクチャや命令セットの特性に合わせて、より良いコードを生成するための試みと考えられます。

### `ggen.c`における`cgen_bmul`の実装

```c
void
cgen_bmul(int op, Node *nl, Node *nr, Node *res)
{
	Node n1b, n2b, n1w, n2w;
	Type *t;
	int a;

	// オペランドの複雑度に応じて評価順序を決定し、バイトレジスタにロード
	if(nl->ullman >= nr->ullman) {
		regalloc(&n1b, nl->type, res);
		cgen(nl, &n1b);
		regalloc(&n2b, nr->type, N);
		cgen(nr, &n2b);
	} else {
		regalloc(&n2b, nr->type, N);
		cgen(nr, &n2b);
		regalloc(&n1b, nl->type, res);
		cgen(nl, &n1b);
	}

	// バイトレジスタからショート（16ビット）レジスタにコピー（拡張）
	t = types[TUINT16];
	if(issigned[nl->type->etype])
		t = types[TINT16];

	regalloc(&n2w, t, &n2b);
	cgen(&n2b, &n2w);

	regalloc(&n1w, t, &n1b);
	cgen(&n1b, &n1w);

	// 16ビット乗算命令を生成
	a = optoas(op, t);
	gins(a, &n2w, &n1w); // n1w = n1w * n2w

	// 結果を元のバイトレジスタに戻し、最終結果にコピー
	cgen(&n1w, &n1b);
	cgen(&n1b, res);

	// レジスタを解放
	regfree(&n1w);
	regfree(&n2w);
	regfree(&n1b);
	regfree(&n2b);
}
```
この関数は、8ビット整数（バイト）の乗算を処理するために導入されました。x86アーキテクチャでは、8ビットの乗算命令は結果が16ビットになるため、直接8ビットレジスタで完結する乗算は効率的ではありません。この`cgen_bmul`は、オペランドを一時的に16ビットレジスタに拡張し（符号付きの場合は符号拡張、符号なしの場合はゼロ拡張）、16ビットの乗算命令を実行します。その後、結果を再び8ビットレジスタに格納し、最終的な結果として返します。これにより、バイト乗算がより正確かつ効率的に処理されるようになります。

### `gsubr.c`におけるレジスタ割り当ての変更

```c
// 変更前 (TINT8/TUINT8 の部分)
// 		min = D_AL;
// 		max = D_BH;
// 		goto try;

// 変更後 (すべての整数型で共通)
// 		if(o != N && o->op == OREGISTER) {
// 			i = o->val.u.reg;
// 			if(i >= D_AX && i <= D_DI) // 汎用レジスタ範囲
// 				goto out;
// 		}
// 		for(i=D_AX; i<=D_DI; i++) // 汎用レジスタを探索
// 			if(reg[i] == 0)
// 				goto out;
```
`regalloc`関数における整数レジスタの割り当てロジックが簡素化されました。以前は8ビット整数型に対して特定のレジスタ範囲（`D_AL`から`D_BH`）を考慮していましたが、この変更により、すべての整数型（8ビット、16ビット、32ビット、ポインタ、ブール）が`D_AX`から`D_DI`までの汎用レジスタプールから割り当てられるようになりました。これは、レジスタ割り当ての複雑さを軽減し、コンパイラの保守性を向上させるための変更です。

```c
// 変更前 (浮動小数点レジスタの割り当て)
// 		if(o != N && o->op == OREGISTER) {
// 			i = o->val.u.reg;
// 			if(i >= D_F0 && i <= D_F7)
// 				goto out;
// 		}
// 		for(i=D_F0; i<=D_F7; i++)
// 			if(reg[i] == 0)
// 				goto out;
// 		yyerror("out of floating registers");
// 		goto err;

// 変更後
		i = D_F0; // 常にD_F0を割り当てる
		goto out;
```
浮動小数点レジスタの割り当てロジックも大幅に簡素化されました。以前は`D_F0`から`D_F7`までのFPUスタックレジスタを探索して空いているものを割り当てていましたが、この変更により、常に`D_F0`（FPUスタックのトップ）を割り当てるようになりました。これは、FPUスタックの特性（常にST(0)が現在の演算対象となる）を考慮したもので、コンパイラがFPUスタックを明示的に管理するのではなく、`D_F0`を主要な作業レジスタとして扱う方針に転換したことを示唆しています。

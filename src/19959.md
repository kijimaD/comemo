## 変更の背景

このコミットの背景には、Go言語のツールチェインにおけるアセンブラの近代化と、特定のアーキテクチャ（この場合はPower64）に対するサポートの強化があります。従来のGoアセンブラは、Plan 9のツールチェインに由来する独自のリンキングメカニズムを持っていました。しかし、Go言語の進化と多様なアーキテクチャへの対応を進める中で、より汎用的で再利用可能なリンキングライブラリ (`liblink`) を導入する必要性が生じました。

`liblink` への移行は、以下のような利点をもたらします。

*   **コードの再利用性向上**: リンキングに関する共通のロジックを `liblink` に集約することで、各アーキテクチャのアセンブラが個別にリンキング処理を実装する必要がなくなり、コードの重複が削減されます。
*   **メンテナンス性の向上**: リンキングロジックの変更やバグ修正が `liblink` 側で一元的に行えるようになり、メンテナンスが容易になります。
*   **新機能の追加の容易化**: 新しいリンキング機能や最適化を導入する際に、`liblink` を更新するだけで済むため、各アセンブラへの影響を最小限に抑えられます。
*   **Power64アーキテクチャのサポート強化**: Power64アーキテクチャ特有の新しい命令や機能に対応するため、アセンブラのパーサーとコード生成部分に修正が必要でした。`liblink` への移行と合わせて、これらの命令が適切に処理されるようにアセンブラが更新されています。

特に、`y.tab.c` の大幅な変更（3794行の追加）は、アセンブラの文法解析部分が `bison` などのパーサー生成ツールによって再生成されたことを示唆しており、これは `liblink` への統合や新しい命令の追加に伴う文法定義の変更が原因と考えられます。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

### 1. Go言語のツールチェイン

Go言語のプログラムは、`go build` コマンドによってコンパイルされます。このプロセスには、コンパイラ (`gc` など)、アセンブラ (`5a`, `6a`, `8a`, `9a` など)、リンカ (`5l`, `6l`, `8l`, `9l` など) といった複数のツールが含まれます。各アーキテクチャ（例: `amd64`, `arm`, `ppc64`）には、それぞれ対応するアセンブラとリンカが存在します。

*   **アセンブラ (`cmd/9a`)**: アセンブリ言語で書かれたソースコード（`.s` ファイル）を、機械語のオブジェクトファイル（`.o` ファイル）に変換するツールです。このコミットで変更されている `cmd/9a` は、Power64アーキテクチャ向けのアセンブラです。
*   **リンカ (`cmd/9l`)**: 複数のオブジェクトファイルやライブラリを結合し、実行可能なバイナリファイルを生成するツールです。

### 2. Plan 9のツールチェイン

Go言語のツールチェインは、Bell LabsのPlan 9オペレーティングシステムのツールチェインに強く影響を受けています。特に、アセンブラやリンカの命名規則（例: `8a` for `amd64`, `9a` for `power64`）や、一部の内部設計はPlan 9のものを踏襲しています。

### 3. `liblink`

`liblink` は、Go言語のツールチェイン内でリンキング処理を抽象化し、共通化するためのライブラリです。従来の各アセンブラが独自に持っていたリンキング関連のロジックを `liblink` に集約することで、コードの重複を排除し、メンテナンス性と拡張性を向上させることを目的としています。`liblink` は、シンボル解決、再配置、セクション管理など、リンカが実行する主要なタスクをカプセル化します。

### 4. `bison` (GNU Bison)

`bison` は、文法定義ファイル（通常は `.y` または `.yy` 拡張子）から、C言語のパーサー（構文解析器）を生成するツールです。アセンブラのような言語処理ツールでは、入力されたアセンブリコードの文法を解析するためにパーサーが必要となります。`y.tab.c` や `y.tab.h` といったファイルは、`bison` によって生成されたパーサーのソースコードです。このコミットでこれらのファイルが大幅に更新されているのは、アセンブラの文法定義（`a.y`）が変更されたためと考えられます。

### 5. Power64アーキテクチャ

Power64は、IBMが開発したPowerアーキテクチャの64ビット版です。サーバーや高性能計算（HPC）システムで広く使用されています。Go言語がPower64をサポートするためには、その命令セットアーキテクチャ（ISA）に合わせたアセンブラとリンカが必要となります。このコミットは、Power64固有の命令のサポートを追加することで、このアーキテクチャ上でのGoプログラムの実行を可能にしています。

### 6. `PCDATA` と `FUNCDATA`

Goランタイムでは、ガベージコレクションやスタックトレースなどのランタイム機能のために、生成された機械語コードに関するメタデータが必要となります。`PCDATA` (PC Data) と `FUNCDATA` (Function Data) は、このメタデータをコードに埋め込むためのディレクティブです。

*   **`PCDATA`**: プログラムカウンタ (PC) に関連付けられたデータで、主にガベージコレクションのためのスタックマップ情報などをエンコードします。
*   **`FUNCDATA`**: 関数に関連付けられたデータで、関数のプロローグ/エピローグ情報、フレームサイズ、引数のサイズなど、関数固有のメタデータをエンコードします。

これらのディレクティブは、アセンブリコード内で使用され、Goランタイムが実行時に必要な情報を効率的に取得できるようにします。

## 技術的詳細

このコミットの技術的詳細は、主に以下の2つの側面に集約されます。

1.  **`liblink` への移行**:
    *   `src/cmd/9a/a.h` および `src/cmd/9a/lex.c` から、従来のPlan 9由来のリンキング関連のヘッダ (`u.h`, `libc.h`, `9.out.h`) の一部が削除され、代わりに `link.h` がインクルードされています。これは、リンキングの責務が `liblink` に移譲されたことを明確に示しています。
    *   `lex.c` の `main` 関数内で、`linknew` 関数が呼び出され、`linkpower64le` または `linkpower64` というアーキテクチャ固有のリンカコンテキストが初期化されています。これにより、`cmd/9a` は `liblink` を通じてリンキング処理を行うようになります。
    *   `outcode` および `outgcode` 関数（アセンブリ命令をオブジェクトコードに変換する役割）のシグネチャが変更され、`Gen` 型の引数が `Addr` 型に変更されています。これは、`liblink` が提供するアドレス表現 (`Addr`) に統一されたことを意味します。
    *   従来の `zname`, `zaddr`, `outsim`, `outhist` といった、オブジェクトファイルの生成やシンボル管理、履歴情報の出力に関する関数が `lex.c` から削除され、その機能が `liblink` 内部で処理されるようになりました。代わりに `writeobj(ctxt, &obuf)` が呼び出され、`liblink` がオブジェクトファイルの書き出しを行います。

2.  **Power64固有の追加命令とメタデータディレクティブのサポート**:
    *   `src/cmd/9a/a.y` (Bisonの文法定義ファイル) に、`LPCDAT` (PCDATA) と `LFUNCDAT` (FUNCDATA) という新しいトークンが追加されています。これにより、アセンブラはGoランタイムが必要とする `PCDATA` および `FUNCDATA` ディレクティブを解析できるようになります。
    *   `a.y` の `inst` ルールに、`PCDATA` と `FUNCDATA` を処理するための新しいプロダクションが追加されています。これにより、アセンブラはこれらのディレクティブを認識し、対応する `outcode` 呼び出しを生成します。
        *   `LPCDAT imm ',' imm`: `PCDATA` ディレクティブを処理します。2つの整数定数を引数にとります。
        *   `LFUNCDAT imm ',' addr`: `FUNCDATA` ディレクティブを処理します。インデックスとシンボル参照を引数にとります。
    *   `src/cmd/9a/lex.c` の `itab` 配列（アセンブリ命令の定義）に、`PCDATA` と `FUNCDATA` のエントリが追加されています。
    *   `src/cmd/9a/a.h` から `Gen` 構造体が削除され、`Addr` 構造体が使用されるようになっています。`Addr` 構造体は `liblink` で定義されており、アドレス指定モードやオペランドの情報をより汎用的に表現します。
    *   `src/cmd/9a/doc.go` が新規追加され、`9a` アセンブラがPower64アーキテクチャをターゲットとしていること、およびGoのアセンブリに関するドキュメントへのリンクが記載されています。これは、このアセンブラの役割を明確にするためのドキュメントの追加です。
    *   `src/cmd/9a/Makefile` に `y.tab.h` の生成ルールが追加されています。これは `a.y` の変更に伴い、パーサーのヘッダファイルが再生成されることを示しています。

これらの変更により、`cmd/9a` は `liblink` のフレームワークに統合され、Goランタイムの要件を満たす `PCDATA` および `FUNCDATA` ディレクティブを処理できるようになりました。これは、Power64アーキテクチャ上でのGoプログラムのコンパイルと実行をより堅牢にするための重要なステップです。

## コアとなるコードの解説

### `liblink` への移行

最も重要な変更は、アセンブラが `liblink` を利用するようになった点です。

*   **`a.h` の変更**:
    ```c
    -#include <u.h>
    -#include <libc.h>
     #include <bio.h>
    -#include "../9c/9.out.h"
    +#include <link.h>
    +#include "../9l/9.out.h" // Still includes 9.out.h for constants, but not for core linking logic
    ```
    `link.h` の導入は、リンキング処理が `liblink` に委譲されたことを示します。

*   **`lex.c` の `main` 関数**:
    ```c
    	thestring = getgoarch();
    	if(strcmp(thestring, "power64le") == 0)
    		ctxt = linknew(&linkpower64le);
    	else
    		ctxt = linknew(&linkpower64);
    	ctxt->diag = yyerror;
    	ctxt->bso = &bstdout;
    	Binit(&bstdout, 1, OWRITE);
    	listinit9();
    	fmtinstall('L', Lconv);
    	ensuresymb(NSYMB);
    ```
    ここで `liblink` のコンテキスト (`ctxt`) が初期化され、アーキテクチャ固有のリンカ (`linkpower64le` または `linkpower64`) が設定されます。これにより、アセンブラは `liblink` の機能を通じてオブジェクトコードを生成するようになります。

*   **`outcode` / `outgcode` 関数の再実装**:
    従来の `outcode` と `outgcode` は、直接オブジェクトファイルにバイトを書き込むような低レベルな処理を行っていましたが、このコミットで `liblink` の `Prog` 構造体と `Plist` (Program List) を利用するように変更されました。
    ```c
    void
    outcode(int a, Addr *g1, int reg, Addr *g2)
    {
    	Prog *p;
    	Plist *pl;

    	if(pass == 1)
    		goto out;

    	// ... (operand handling) ...

    	p = ctxt->arch->prg(); // Get a new program instruction from liblink context
    	p->as = a;             // Opcode
    	p->lineno = lineno;
    	if(nosched)
    		p->mark |= NOSCHED;
    	p->from = *g1;         // Source operand
    	p->reg = reg;          // Register
    	p->to = *g2;           // Destination operand
    	p->pc = pc;            // Program counter

    	if(lastpc == nil) {
    		pl = linknewplist(ctxt); // Start a new program list
    		pl->firstpc = p;
    	} else
    		lastpc->link = p; // Link to the previous instruction
    	lastpc = p;
    out:
    	if(a != AGLOBL && a != ADATA)
    		pc++;
    }
    ```
    この変更は、アセンブラが直接オブジェクトコードを生成するのではなく、`liblink` が提供する抽象化された命令 (`Prog`) を構築し、それをリンカに渡すという、より高レベルなアプローチに移行したことを示しています。これにより、リンカ側で命令の最適化や再配置をより柔軟に行えるようになります。

### `PCDATA` と `FUNCDATA` のサポート

Goランタイムのガベージコレクションやスタックトレースに必要なメタデータを埋め込むためのディレクティブが追加されました。

*   **`a.y` でのトークンとルールの追加**:
    ```yacc
    %token	<lval>	LPCDAT LFUNCDAT ...

    ...

    /*
     * PCDATA
     */
    |\tLPCDAT imm ',' imm
    	{
    		if($2.type != D_CONST || $4.type != D_CONST)
    			yyerror("arguments to PCDATA must be integer constants");
    		outcode($1, &$2, NREG, &$4);
    	}
    /*
     * FUNCDATA
     */
    |\tLFUNCDAT imm ',' addr
    	{
    		if($2.type != D_CONST)
    			yyerror("index for FUNCDATA must be integer constant");
    		if($4.type != D_EXTERN && $4.type != D_STATIC && $4.type != D_OREG)
    			yyerror("value for FUNCDATA must be symbol reference");
     		outcode($1, &$2, NREG, &$4);
    	}
    ```
    これにより、アセンブラは `PCDATA` と `FUNCDATA` という新しいアセンブリディレクティブを認識し、それらを `outcode` 関数を通じて `liblink` の `Prog` 構造体として表現できるようになります。これらのディレクティブは、Goバイナリにランタイムメタデータを埋め込むために不可欠です。

### `LTEXT` ルールの変更

`LTEXT` (関数定義) のルールも変更され、関数の引数サイズに関する情報 (`ArgsSizeUnknown`) が `liblink` の `Prog` 構造体に渡されるようになりました。これは、Goの関数呼び出し規約とガベージコレクションの正確性を保証するために重要な情報です。

```yacc
|\tLTEXT name ',' con ',' imm
	{
		$6.offset &= 0xffffffffull;
		$6.offset |= (vlong)ArgsSizeUnknown << 32;
		outcode($1, &$2, $4, &$6);
	}
|\tLTEXT name ',' con ',' imm '-' con
	{
		$6.offset &= 0xffffffffull;
		$6.offset |= ($8 & 0xffffffffull) << 32;
		outcode($1, &$2, $4, &$6);
	}
```
この変更は、Goの関数がスタックフレームをどのように使用するかに関するメタデータを、アセンブラがリンカに正確に伝えることを可能にします。

これらの変更は、Goのツールチェインがよりモジュール化され、Power64のような特定のアーキテクチャに対するサポートがより洗練されたことを示しています。

## 変更の背景

このコミットは、Goコンパイラおよびランタイムが、Power64アーキテクチャのような64ビットレジスタを持つシステムを適切にサポートするために行われました。これまでのGoがサポートしていたアーキテクチャ（x86、ARMなど）は、最大で32個のレジスタしか持っていませんでした。そのため、Goコンパイラのレジスタ割り当てやガベージコレクション（GC）のレジスタスキャンにおいて、レジスタの状態をビットマスクとして表現する際に、`uint32`型の配列である`Bits`構造体の最初の要素（`Bits.b[0]`）を直接レジスタマスクとして利用することが可能でした。

しかし、Power64アーキテクチャは64個の汎用レジスタを持つため、32ビット幅の`uint32`では、単一の要素で全てのレジスタの状態を表現することができません。この制約により、Power64上で効率的かつ正確なレジスタ管理を行うことが困難でした。このコミットの目的は、`Bits`構造体の基盤となるデータ型を`uint32`から`uint64`に変更することで、Power64のような64ビットレジスタを持つアーキテクチャでも、`Bits.b[0]`を64ビット幅のレジスタマスクとして引き続き利用できるようにし、レジスタ管理ロジックの整合性と効率性を維持することにあります。

## 前提知識の解説

### Goコンパイラのバックエンド (`src/cmd/5g`, `src/cmd/6g`, `src/cmd/8g`)

Goコンパイラは、異なるCPUアーキテクチャ向けにコードを生成するための複数のバックエンドを持っています。
*   `src/cmd/5g`: ARMアーキテクチャ (arm) 向けのコンパイラ。
*   `src/cmd/6g`: x86-64アーキテクチャ (amd64) 向けのコンパイラ。
*   `src/cmd/8g`: x86アーキテクチャ (386) 向けのコンパイラ。
これらのバックエンドは、それぞれのアセンブリコード生成やレジスタ割り当てのロジックを含んでおり、共通のデータ構造やユーティリティ（例えば、`Bits`構造体）を`src/cmd/gc`ディレクトリ内のコードと共有しています。

### CPUレジスタとレジスタ割り当て

CPUレジスタは、プロセッサがデータを一時的に格納するために使用する高速な記憶領域です。プログラムの実行速度は、データがメモリとレジスタ間でどれだけ効率的に移動されるかに大きく依存します。コンパイラは、プログラムの変数を可能な限りレジスタに割り当てる「レジスタ割り当て」という最適化を行います。これにより、メモリへのアクセスを減らし、実行速度を向上させます。アーキテクチャによって利用可能なレジスタの数や種類は異なります。

### ビットマスク

ビットマスクは、ビット演算（AND, OR, XOR, NOTなど）を使用して、特定のビットの状態を操作したり、複数のブール値をコンパクトに表現したりするための技術です。例えば、32個のレジスタの状態（使用中か否か）を表現する場合、32ビットの整数（`uint32`）の各ビットを対応するレジスタの状態にマッピングすることで、効率的に管理できます。

### `uint32` と `uint64`

*   `uint32`: 32ビット（4バイト）の符号なし整数型。0から約42億までの値を表現できます。
*   `uint64`: 64ビット（8バイト）の符号なし整数型。0から約1.8 x 10^19までの値を表現できます。
このコミットの文脈では、これらの型がビットマスクの「幅」を決定します。`uint32`は32個のビットを、`uint64`は64個のビットを表現できます。

### GoのGC (Garbage Collector) とレジスタスキャン

Goのガベージコレクタ（GC）は、プログラムが不要になったメモリを自動的に解放する役割を担っています。GCは、到達可能性（reachability）に基づいてオブジェクトが「生きている」か「死んでいる」かを判断します。このプロセスの一環として、GCは実行中のゴルーチン（Goの軽量スレッド）のスタックやCPUレジスタをスキャンし、そこに格納されているポインタを識別して、それらが指すオブジェクトを「生きている」とマークします。レジスタに格納されている値がポインタであるか非ポインタであるかを正確に識別することは、GCの正確性と安全性のために不可欠です。

## 技術的詳細

このコミットの核心は、Goコンパイラとランタイムが内部的に使用する`Bits`構造体の定義変更と、それに伴うビット操作ロジックの更新です。

1.  **`Bits`構造体の変更**:
    以前の`Bits`構造体は、`uint32`型の配列`b`を持っていました。
    ```c
    // src/cmd/gc/go.h (変更前)
    typedef struct Bits Bits;
    struct Bits
    {
        uint32 b[BITS];
    };
    ```
    このコミットにより、`b`配列の型が`uint64`に変更されました。
    ```c
    // src/cmd/gc/go.h (変更後)
    typedef struct Bits Bits;
    struct Bits
    {
        uint64 b[BITS];
    };
    ```
    これにより、`Bits`構造体の各要素が64ビット幅のビットマスクを保持できるようになり、Power64のような64レジスタを持つアーキテクチャでも、`b[0]`だけで全てのレジスタの状態を表現できるようになりました。

2.  **`BITS`定数の変更**:
    `src/cmd/gc/go.h`で定義されている`BITS`定数は、`Bits`構造体内の`b`配列の要素数を決定します。この定数は、`NVAR`（変数の総数、またはビットマスクで表現できる最大ビット数）を基に計算されます。
    変更前: `#define BITS 5`
    変更後: `#define BITS 3`
    同時に、`NVAR`の計算式も変更されました。
    変更前: `#define NVAR (BITS*sizeof(uint32)*8)`
    変更後: `#define NVAR (BITS*sizeof(uint64)*8)`
    `sizeof(uint32)*8`は`32`、`sizeof(uint64)*8`は`64`です。
    変更前: `NVAR = 5 * 32 = 160`
    変更後: `NVAR = 3 * 64 = 192`
    この変更により、`Bits`構造体全体のビット表現能力は160ビットから192ビットに増加し、より多くの変数をビットマスクで管理できるようになりました。同時に、各要素の幅が広がったため、配列の要素数は減りました。

3.  **ビット操作関数の更新**:
    `src/cmd/gc/bits.c`では、`Bits`構造体に対するビット操作を行うヘルパー関数が定義されています。これらの関数は、`uint32`を前提としたビットシフトやマスク操作を行っていましたが、`uint64`への変更に伴い、対応する調整が行われました。
    *   `bnum(Bits a)`: ビットがセットされている最初の位置を返す関数。内部の計算が`32*i + bitno(b)`から`64*i + bitno(b)`に変更されました。
    *   `blsh(uint n)`: 指定された位置`n`に1ビットをセットした`Bits`構造体を返す関数。`n/32`と`n%32`の計算が`n/64`と`n%64`に変更され、`1L`が`1LL`（long long literal）に変更されました。
    *   `bitno(uint64 b)`: 最下位ビットがセットされている位置を返す関数。ループの範囲が`i<32`から`i<64`に変更され、`1L`が`1LL`に変更されました。
    *   新しいヘルパー関数 `btest`, `biset`, `biclr` の導入:
        以前は`a.b[n/32] & (1L << (n%32))`のような直接的なビット操作が行われていましたが、`uint64`への変更とコードの可読性・保守性向上のため、これらの操作をカプセル化する関数が導入されました。
        *   `btest(Bits *a, uint n)`: 指定されたビット`n`がセットされているかテストします。
        *   `biset(Bits *a, uint n)`: 指定されたビット`n`をセットします。
        *   `biclr(Bits *a, uint n)`: 指定されたビット`n`をクリアします。

4.  **関数シグネチャの変更**:
    `src/cmd/{5g,6g,8g}/opt.h`および`src/cmd/{5g,6g,8g}/reg.c`内の複数の関数で、`uint32`や`int32`で表現されていたビットマスクやレジスタ関連の引数・戻り値の型が`uint64`や`uint32`に変更されました。
    *   `LOAD`, `STORE`関数の戻り値が`uint32`から`uint64`に変更。
    *   `paint3`関数の引数`rb`の型が`int32`から`uint32`に変更。
    *   `RtoB`, `FtoB`関数の戻り値が`int32`から`uint32`に変更。
    *   `BtoR`, `BtoF`関数の引数が`int32`から`uint32`に変更。
    これらの変更は、`Bits`構造体の基盤となる型が変更されたことに伴い、関連するビットマスクやレジスタ表現を扱う関数も新しい型定義に合わせるために必要でした。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/cmd/gc/go.h`における`Bits`構造体の定義変更です。

```c
// src/cmd/gc/go.h
#define BITS    3 // 以前は 5
#define NVAR    (BITS*sizeof(uint64)*8) // 以前は BITS*sizeof(uint32)*8

typedef struct Bits Bits;
struct Bits
{
    uint64  b[BITS]; // 以前は uint32 b[BITS];
};
```

この変更により、`Bits`構造体は、各要素が64ビット幅のビットマスクを保持できるようになりました。これにより、Power64のような64個のレジスタを持つアーキテクチャでも、`b[0]`だけで全てのレジスタの状態を効率的に表現できるようになります。

また、`src/cmd/gc/bits.c`で導入された新しいヘルパー関数`btest`, `biset`, `biclr`は、`Bits`構造体に対するビット操作を抽象化し、コードの可読性と保守性を向上させます。

```c
// src/cmd/gc/bits.c
int
btest(Bits *a, uint n)
{
    return (a->b[n/64] & (1LL << (n%64))) != 0;
}

void
biset(Bits *a, uint n)
{
    a->b[n/64] |= 1LL << (n%64);
}

void
biclr(Bits *a, uint n)
{
    a->b[n/64] &= ~(1LL << (n%64));
}
```
これらの関数は、ビットインデックス`n`を64で割った商を配列のインデックスとし、剰余をビットシフト量として使用することで、`uint64`配列内の任意のビットを効率的に操作します。これにより、各アーキテクチャのレジスタ数に応じた柔軟なビットマスク管理が可能になります。

コンパイラのバックエンド（`5g`, `6g`, `8g`）の`reg.c`ファイルでは、以前は直接行われていた`bit.b[i/32] &= ~(1L<<(i%32));`のようなビット操作が、これらの新しいヘルパー関数（例: `biclr(&bit, i);`）に置き換えられています。これにより、コードの重複が減り、将来的な変更に対する堅牢性が高まります。

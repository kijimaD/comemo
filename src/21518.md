## 変更の背景

このコミットは、Go言語の `crypto/x509` パッケージにおける、証明書失効リスト（CRL: Certificate Revocation List）のバージョン番号に関する誤りを修正するものです。具体的には、RFC 5280（X.509 Public Key Infrastructure Certificate and Certificate Revocation List (CRL) Profile）の規定に準拠していなかった点が問題でした。

RFC 5280のセクション5.1では、CRLのバージョンフィールドについて以下のように規定しています。
「このオプションフィールドは、エンコードされたCRLのバージョンを記述する。このプロファイルで要求されるように、拡張が使用される場合、このフィールドは存在しなければならず、バージョン2（整数値は1）を指定しなければならない。」

つまり、X.509 v2 CRLでは、バージョンフィールドのASN.1エンコーディングにおける整数値は `1` でなければならないにもかかわらず、Goの `crypto/x509` パッケージでは誤って `2` を設定していました。この不正確なバージョン番号は、他のシステムがGoで生成されたCRLを正しく解釈できない可能性を引き起こすため、修正が必要でした。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

### X.509

X.509は、公開鍵証明書の標準フォーマットを定義するITU-T（国際電気通信連合電気通信標準化部門）の勧告です。PKI（公開鍵基盤）の重要な要素であり、デジタル証明書を通じてエンティティ（ユーザー、サーバーなど）の公開鍵の真正性を検証するために使用されます。X.509証明書は、公開鍵、所有者の識別情報、発行者の識別情報、有効期間、発行者のデジタル署名などを含みます。

### 証明書失効リスト (CRL: Certificate Revocation List)

CRLは、認証局（CA: Certificate Authority）によって発行される、失効したデジタル証明書のリストです。証明書は、有効期限が切れる前に、秘密鍵の漏洩、所有者の情報の変更、CAの運用停止などの理由で失効することがあります。CRLは、これらの失効した証明書を公開し、利用者が証明書の有効性を確認する際に参照できるようにします。CRLは定期的に発行され、通常はCAのウェブサイトやLDAPディレクトリなどで公開されます。

### RFC 5280

RFC 5280は、「Internet X.509 Public Key Infrastructure Certificate and Certificate Revocation List (CRL) Profile」というタイトルのIETF（インターネット技術タスクフォース）の標準文書です。これは、X.509証明書とCRLのインターネットでの使用方法に関する詳細なプロファイル（仕様）を定義しています。PKIの実装において、相互運用性とセキュリティを確保するための重要なガイドラインとなります。

### ASN.1 (Abstract Syntax Notation One)

ASN.1は、データ構造を記述するための標準的な記法です。通信プロトコルやデータストレージにおいて、異なるシステム間でデータを交換する際に、データの表現方法を抽象的に定義するために使用されます。X.509証明書やCRLもASN.1で定義された構造に従ってエンコードされます。ASN.1で定義されたデータは、BER（Basic Encoding Rules）やDER（Distinguished Encoding Rules）などのエンコーディングルールに従ってバイト列に変換されます。

### X.509 CRLのバージョンフィールド

X.509 CRLにはバージョンフィールドが存在します。
- **Version 1 CRL**: 拡張機能を持たない基本的なCRL。バージョンフィールドは存在しないか、存在しても値は `0` と解釈されます。
- **Version 2 CRL**: 拡張機能を持つCRL。RFC 5280で定義されており、このバージョンではバージョンフィールドが必須となり、そのASN.1整数値は `1` でなければなりません。これは、ASN.1の慣習で、バージョン番号 `N` は通常 `N-1` の整数値で表現されるためです。つまり、バージョン2は整数値 `1` に対応します。

## 技術的詳細

このコミットの技術的な核心は、X.509 CRLのバージョンフィールドのASN.1エンコーディングにおける整数値の誤りです。

RFC 5280の規定によれば、X.509 v2 CRLを使用する場合、`TBSCertificateList` 構造体内の `version` フィールドは必須であり、その値は `1`（これはバージョン2を意味する）でなければなりません。しかし、Goの `crypto/x509` パッケージでは、このフィールドのデフォルト値が `2` に設定されていました。

具体的には、以下の2箇所で修正が行われました。

1.  **`src/crypto/x509/pkix/pkix.go` 内の `TBSCertificateList` 構造体定義**:
    この構造体は、CRLの署名対象部分（To Be Signed Certificate List）を定義しており、その中に `Version` フィールドが含まれています。ASN.1タグ `asn1:"optional,default:2"` は、このフィールドがオプションであり、デフォルト値がASN.1整数値 `2` であることを示していました。これを `asn1:"optional,default:1"` に変更することで、RFC 5280の要件に合致させました。

2.  **`src/crypto/x509/x509.go` 内の `Certificate.CreateCRL` 関数**:
    この関数は、GoでCRLを生成する際に使用されます。`TBSCertificateList` 構造体を初期化する際に、`Version` フィールドに直接 `2` を設定していました。これを `1` に変更することで、生成されるCRLがRFC 5280に準拠するようにしました。

この修正により、Go言語で生成されるCRLが、他のPKIシステムとの相互運用性において問題を起こす可能性が低減されました。

## コアとなるコードの解説

### `src/crypto/x509/pkix/pkix.go`

`TBSCertificateList` 構造体は、X.509 CRLの主要な部分を定義しています。この構造体は、CRLのバージョン、署名アルゴリズム、発行者、発行日時、次回更新日時、失効した証明書のリストなどを含みます。

変更された行:
`Version int `asn1:"optional,default:2"`
から
`Version int `asn1:"optional,default:1"`

これは、Goの `asn1` パッケージが構造体タグを通じてASN.1エンコーディングの挙動を制御する方法を示しています。`default:2` は、このフィールドが省略された場合にASN.1エンコーディングで整数値 `2` が使用されることを意味していました。RFC 5280の規定に従い、バージョン2のCRLでは整数値 `1` を使用する必要があるため、`default:1` に修正されました。

### `src/crypto/x509/x509.go`

`Certificate.CreateCRL` 関数は、`Certificate` オブジェクト（通常はCA証明書）を使用して新しいCRLを作成するためのメソッドです。この関数内で、`pkix.TBSCertificateList` 構造体のインスタンスが作成され、CRLの各フィールドが設定されます。

変更された行:
`tbsCertList.Version: 2,`
から
`tbsCertList.Version: 1,`

この変更は、`CreateCRL` 関数がCRLを生成する際に、`TBSCertificateList` の `Version` フィールドに直接 `1` を設定するようにします。これにより、明示的にバージョン2のCRL（ASN.1整数値 `1`）が生成されるようになり、`pkix.go` の構造体定義におけるデフォルト値の変更と合わせて、RFC 5280への完全な準拠が実現されます。

## 変更の背景

このコミットの主な背景は、Goの `net/http` パッケージにおけるHTTP/2クライアント接続の管理方法を改善することにあります。以前の実装では、HTTP/2トランスポート (`http2Transport`) が直接接続プールを管理しており、そのロジックが `http2Transport` の内部に密結合していました。

このような密結合は、以下のような問題を引き起こす可能性があります。

1.  **拡張性の欠如**: カスタムの接続プール戦略を実装したり、異なる接続管理ポリシーを試したりすることが困難でした。
2.  **テストの複雑さ**: 接続管理ロジックがトランスポートと一体化しているため、単体テストが複雑になりがちでした。
3.  **コードの保守性**: 接続管理のロジックが肥大化し、`http2Transport` のコードベースが読みにくく、変更しにくい状態になる可能性がありました。

これらの問題を解決するため、接続プール機能を独立した抽象化として切り出すことが決定されました。これにより、接続管理の責任が `http2Transport` から分離され、よりクリーンで、テストしやすく、拡張性の高い設計が実現されます。特に、`DefaultTransport` との連携において、HTTP/1.1とHTTP/2の接続管理をより柔軟に統合するための基盤となります。

## 前提知識の解説

### HTTP/2 (Hypertext Transfer Protocol Version 2)

HTTP/2は、HTTP/1.1のセマンティクスを維持しつつ、パフォーマンスを大幅に向上させるために設計されたプロトコルです。主な特徴は以下の通りです。

*   **多重化 (Multiplexing)**: 複数のリクエストとレスポンスを単一のTCP接続上で同時に送受信できます。これにより、HTTP/1.1で発生していたヘッドオブラインブロッキング問題が緩和されます。
*   **ヘッダー圧縮 (Header Compression)**: HPACKという圧縮形式を使用して、HTTPヘッダーのサイズを削減します。
*   **サーバープッシュ (Server Push)**: クライアントがリクエストする前に、サーバーがリソースをプッシュして送信できます。
*   **ストリーム (Streams)**: 各リクエスト/レスポンスの交換は「ストリーム」として扱われ、それぞれが独立した双方向のバイトフローを持ちます。
*   **フロー制御 (Flow Control)**: 送信者が受信者のバッファを溢れさせないように、データ送信量を制御するメカニズムです。

### 接続プール (Connection Pooling)

接続プールは、データベース接続やネットワーク接続など、確立にコストがかかるリソースを再利用するためのソフトウェア設計パターンです。HTTP/2においては、単一のTCP接続で複数のリクエストを処理できるため、接続の確立と切断のオーバーヘッドを削減し、パフォーマンスを向上させるために接続プールが非常に重要です。

接続プールは通常、以下の機能を提供します。

*   **接続の取得**: プールから利用可能な接続を取得します。利用可能な接続がない場合は、新しい接続を確立するか、待機します。
*   **接続の解放**: 使用済みの接続をプールに戻し、再利用できるようにします。
*   **接続の管理**: アイドル状態の接続のクローズ、デッドな接続の検出と削除など、プールの健全性を維持します。

### Go言語の `net/http` パッケージ

Goの `net/http` パッケージは、HTTPクライアントとサーバーを実装するための標準ライブラリです。

*   **`http.Client`**: HTTPリクエストを送信するためのクライアントです。
*   **`http.Transport`**: `http.Client` の内部で使用され、実際のネットワーク接続の確立、接続の再利用、プロキシ設定、TLS設定などを担当します。HTTP/1.1とHTTP/2の両方をサポートします。
*   **`http.RoundTripper`**: `Transport` インターフェースを定義しており、`RoundTrip` メソッドを持つ任意の型が `http.Client` の `Transport` として機能できます。

HTTP/2のサポートは、`net/http` パッケージの内部で `h2_bundle.go` というファイルにバンドルされており、これは `golang.org/x/net/http2` パッケージのコードをコピーしたものです。

## 技術的詳細

このコミットの核心は、HTTP/2クライアント接続の管理ロジックを `http2Transport` から分離し、`http2ClientConnPool` インターフェースとそのデフォルト実装である `http2clientConnPool` に移譲した点にあります。

### `http2ClientConnPool` インターフェースの導入

```go
// ClientConnPool manages a pool of HTTP/2 client connections.
type http2ClientConnPool interface {
	GetClientConn(req *Request, addr string) (*http2ClientConn, error)
	MarkDead(*http2ClientConn)
}
```
この新しいインターフェースは、HTTP/2クライアント接続プールが提供すべき最小限の機能セットを定義しています。
*   `GetClientConn(req *Request, addr string) (*http2ClientConn, error)`: 指定されたアドレス (`addr`) に対して、新しいリクエストを処理できるHTTP/2クライアント接続 (`http2ClientConn`) をプールから取得します。
*   `MarkDead(*http2ClientConn)`: 指定されたクライアント接続がデッドになったことをプールに通知し、プールから削除するなどの適切な処理を行います。

### `http2clientConnPool` 構造体と実装

`http2clientConnPool` は `http2ClientConnPool` インターフェースのデフォルト実装です。

```go
type http2clientConnPool struct {
	t  *http2Transport
	mu sync.Mutex // TODO: switch to RWMutex
	// TODO: add support for sharing conns based on cert names
	// (e.g. share conn for googleapis.com and appspot.com)
	conns map[string][]*http2ClientConn // key is host:port
	keys  map[*http2ClientConn][]string
}
```
*   `t *http2Transport`: このプールが属する `http2Transport` への参照です。接続のダイヤルなどに使用されます。
*   `mu sync.Mutex`: 接続マップ (`conns` と `keys`) へのアクセスを保護するためのミューテックスです。コメントには `RWMutex` への切り替えが検討されていることが示唆されています。
*   `conns map[string][]*http2ClientConn`: `host:port` をキーとして、そのアドレスに接続されている `http2ClientConn` のスライスを保持します。
*   `keys map[*http2ClientConn][]string`: `http2ClientConn` をキーとして、その接続がどの `host:port` キーでプールに登録されているかを追跡します。これは、一つの接続が複数のエイリアス（例: `example.com:443` と `www.example.com:443`）で共有される可能性がある場合に、`MarkDead` 処理を効率的に行うために使用されます。

`http2clientConnPool` は `GetClientConn`, `addConn`, `MarkDead`, `closeIdleConnections` などのメソッドを実装し、実際の接続管理ロジックをカプセル化します。

### `http2Transport` の変更

`http2Transport` は、接続プールを直接管理する代わりに、`http2ClientConnPool` インターフェースを介して接続プールと対話するようになりました。

```go
type http2Transport struct {
	// ...
	// ConnPool optionally specifies an alternate connection pool to use.
	// If nil, the default is used.
	ConnPool http2ClientConnPool

	connPoolOnce  sync.Once
	connPoolOrDef http2ClientConnPool // non-nil version of ConnPool
}

func (t *http2Transport) connPool() http2ClientConnPool {
	t.connPoolOnce.Do(t.initConnPool)
	return t.connPoolOrDef
}

func (t *http2Transport) initConnPool() {
	if t.ConnPool != nil {
		t.connPoolOrDef = t.ConnPool
	} else {
		t.connPoolOrDef = &http2clientConnPool{t: t}
	}
}
```
*   `ConnPool http2ClientConnPool`: ユーザーがカスタムの接続プール実装を提供できるようにするためのフィールドです。`nil` の場合はデフォルトの `http2clientConnPool` が使用されます。
*   `connPoolOnce` と `connPoolOrDef`: `connPool()` メソッドを通じて、接続プールが一度だけ初期化されることを保証します。

`http2Transport.RoundTrip` メソッドは、接続を取得する際に `t.connPool().GetClientConn(req, addr)` を呼び出すようになり、接続管理の責任が `http2Transport` から `http2ClientConnPool` に移譲されたことを示しています。

### `http2clientConn` から `http2ClientConn` へのリネーム

`http2clientConn` 構造体の名前が `http2ClientConn` に変更されました。これは、Goの慣例に従い、エクスポートされる型名は大文字で始まるべきであるという原則に合わせたものと考えられます。これにより、この型がパッケージ外部からも参照可能になったことを示唆しています。

### `net/http/transport.go` における統合

`net/http/transport.go` では、`DefaultTransport` がHTTP/2をサポートするためのロジックが更新されました。

```go
var (
	// h2ConnPool is the connection pool for HTTP/2 connections.
	h2ConnPool = &http2clientConnPool{}
	// h2Transport is the HTTP/2 version of DefaultTransport.
	h2Transport = &http2Transport{ConnPool: noDialClientConnPool{h2ConnPool}}
)

func init() {
	h2ConnPool.t = h2Transport // avoid decalaration loop
}

// noDialClientConnPool is an implementation of http2.ClientConnPool
// which never dials.  We let the HTTP/1.1 client dial and use its TLS
// connection instead.
type noDialClientConnPool struct{ *http2clientConnPool }

func (p noDialClientConnPool) GetClientConn(req *Request, addr string) (*http2ClientConn, error) {
	const doDial = false
	return p.getClientConn(req, addr, doDial)
}
```
*   `h2ConnPool`: `DefaultTransport` が使用するグローバルな `http2clientConnPool` インスタンスです。
*   `h2Transport`: `DefaultTransport` が使用するグローバルな `http2Transport` インスタンスです。ここで注目すべきは、`ConnPool` フィールドに `noDialClientConnPool` が設定されている点です。
*   `noDialClientConnPool`: これは `http2clientConnPool` をラップする型で、`GetClientConn` メソッドが新しい接続をダイヤルしないようにオーバーライドされています (`dialOnMiss` を `false` に設定)。これは、`DefaultTransport` がHTTP/1.1のメカニズムでTLS接続を確立し、その既存のTLS接続をHTTP/2にアップグレードするシナリオに対応するためです。つまり、HTTP/1.1のトランスポートがTLSハンドシェイクを行い、その結果得られた `*tls.Conn` をHTTP/2トランスポートに渡すことで、HTTP/2接続が確立されます。この場合、HTTP/2トランスポート自身が新しいTCP/TLS接続をダイヤルする必要はありません。

この変更により、`DefaultTransport` はHTTP/1.1とHTTP/2の接続管理をよりシームレスに統合できるようになり、既存のTLS接続をHTTP/2接続プールに効率的に追加できるようになります。

## コアとなるコードの変更箇所

### `src/net/http/h2_bundle.go`

*   `http2ClientConnPool` インターフェースの新規追加。
*   `http2clientConnPool` 構造体と、その `GetClientConn`, `addConn`, `MarkDead`, `closeIdleConnections` メソッドの新規追加。
*   `http2Transport` 構造体から `connMu`, `conns` フィールドが削除され、代わりに `ConnPool`, `connPoolOnce`, `connPoolOrDef` フィールドが追加。
*   `http2Transport.connPool()` および `http2Transport.initConnPool()` メソッドの新規追加。
*   `http2clientConn` 構造体が `http2ClientConn` にリネームされ、いくつかのメソッド名も `CanTakeNewRequest`, `RoundTrip` などに大文字で始まるように変更。
*   `http2Transport.RoundTrip` メソッド内で、接続取得ロジックが `t.getClientConn` から `t.connPool().GetClientConn` に変更。
*   `http2Transport.CloseIdleConnections` メソッドが、新しい接続プールインターフェースを使用するように変更。
*   `http2Transport.removeClientConn`, `http2Transport.AddIdleConn`, `http2Transport.addConn`, `http2Transport.getClientConn` メソッドが削除。これらの機能は `http2clientConnPool` に移譲された。
*   `http2Transport.dialClientConn` メソッドが簡素化され、`http2Transport.NewClientConn` を呼び出すように変更。
*   `http2clientConn.readLoop` 内で、接続がデッドになった際の処理が `cc.t.removeClientConn(cc)` から `cc.t.connPool().MarkDead(cc)` に変更。

### `src/net/http/transport.go`

*   `h2ConnPool` (グローバルな `http2clientConnPool` インスタンス) と `h2Transport` (グローバルな `http2Transport` インスタンス) が新規追加。
*   `noDialClientConnPool` 構造体と、その `GetClientConn` メソッドが新規追加。
*   `init()` 関数内で、`DefaultTransport` の `RegisterProtocol` および `TLSNextProto` の設定が、新しい `h2Transport` と `h2ConnPool` を使用するように変更。特に、`TLSNextProto` のハンドラ内で `h2Transport.NewClientConn` を呼び出し、`h2ConnPool.addConn` を使って接続をプールに追加するロジックが導入された。

## コアとなるコードの解説

### `http2ClientConnPool` インターフェース

このインターフェースは、HTTP/2接続プールの契約を定義します。これにより、`http2Transport` は具体的な接続プール実装に依存することなく、接続プールと対話できるようになります。これは、依存性逆転の原則 (Dependency Inversion Principle) の良い例であり、コードのモジュール性とテスト容易性を向上させます。

### `http2clientConnPool` 構造体

この構造体は、`http2ClientConnPool` インターフェースのデフォルト実装であり、実際の接続管理ロジックを担います。
*   `GetClientConn`: プール内の既存の接続を検索し、利用可能なものがあればそれを返します。利用可能な接続がない場合、`dialOnMiss` が `true` であれば `http2Transport.dialClientConn` を呼び出して新しい接続を確立し、それをプールに追加してから返します。
*   `MarkDead`: 指定された接続をプールから削除します。これは、接続がエラーで終了したり、GOAWAYフレームを受信したりした場合に呼び出されます。
*   `addConn`: 新しい接続をプールに追加します。
*   `closeIdleConnections`: プール内のすべての接続を反復処理し、アイドル状態の接続をクローズします。

### `http2Transport` と `ConnPool` フィールド

`http2Transport` に `ConnPool` フィールドが追加されたことで、ユーザーは独自の接続プール実装を注入できるようになりました。これにより、例えば、特定の負荷分散戦略を持つ接続プールや、接続のライフサイクルをより細かく制御する接続プールなどを簡単に試すことが可能になります。`connPoolOnce` と `connPoolOrDef` は、遅延初期化とシングルトンパターンを組み合わせたもので、接続プールが初めて必要になったときに一度だけ初期化されることを保証します。

### `noDialClientConnPool`

この特殊な接続プール実装は、`net/http` パッケージの `DefaultTransport` がHTTP/2をサポートする際に重要な役割を果たします。`DefaultTransport` は、まずHTTP/1.1のメカニズムでTLS接続を確立しようとします。このTLSハンドシェイク中に、ALPN (Application-Layer Protocol Negotiation) を使用してHTTP/2がネゴシエートされることがあります。HTTP/2がネゴシエートされた場合、既存のTLS接続をHTTP/2接続として再利用する必要があります。

`noDialClientConnPool` は、`GetClientConn` が新しい接続をダイヤルしないようにすることで、このシナリオをサポートします。代わりに、`DefaultTransport` の `TLSNextProto` ハンドラが、既存のTLS接続から `http2ClientConn` を作成し、それを `h2ConnPool` に直接追加します。これにより、HTTP/1.1とHTTP/2の接続管理がスムーズに連携し、不要な接続の再確立を防ぎます。

## 元コミット内容

このコミットは、GoランタイムのWindows固有のメモリ管理コードにおいて、`SysUsed`関数が抱えていた問題を修正します。具体的には、`SysUnused`関数に以前適用された修正と同様のロジックを`SysUsed`にも適用することで、この問題を解決しています。この変更は、GoのIssue #8038を修正するものです。

## 変更の背景

Goランタイムは、プログラムが必要とするメモリをオペレーティングシステムから取得し、管理します。Windows環境では、`VirtualAlloc`というシステムコールを使用して仮想メモリを予約（reserve）し、その後必要に応じてコミット（commit）します。コミットされたメモリは、実際に物理メモリやページファイルにマッピングされ、プログラムが使用できるようになります。

このコミットが修正する問題は、`runtime.SysUsed`関数が、指定されたサイズのメモリ領域を一度にコミットしようとした際に、そのコミットが失敗する可能性があるという点にありました。特に、非常に大きなメモリ領域をコミットしようとした場合や、システムのリソースが逼迫している状況では、`VirtualAlloc`が一度に全量をコミットできないことがあります。

元の実装では、`VirtualAlloc`が失敗した場合、即座にパニック（`runtime·throw`）を引き起こしていました。しかし、これは必ずしも致命的なエラーではなく、より小さなチャンクに分割してコミットを再試行することで、問題を回避できる可能性があります。この挙動は、以前`SysUnused`関数で同様の問題が発見され、修正された経緯があります。`SysUsed`も同様の脆弱性を持っていたため、同じ修正が適用されることになりました。

Issue #8038の具体的な内容は、このコミットメッセージとCL（Change List）から直接確認することはできませんでしたが、コミットメッセージに「Same fix as for SysUnused. Fixes #8038.」とあることから、`SysUnused`で発生した問題と同様の、`VirtualAlloc`のコミット失敗時の挙動に関する問題であったと推測されます。

## 前提知識の解説

### 1. 仮想メモリと物理メモリ

*   **仮想メモリ (Virtual Memory)**: オペレーティングシステムが提供する抽象化されたメモリ空間です。各プロセスは、物理メモリの実際の配置に関わらず、連続した仮想アドレス空間を持っているかのように見えます。これにより、プログラムは物理メモリの制約から解放され、より大きなメモリ空間を扱えるようになります。
*   **物理メモリ (Physical Memory)**: コンピュータに実際に搭載されているRAM（Random Access Memory）のことです。仮想メモリのアドレスは、MMU（Memory Management Unit）によって物理メモリのアドレスに変換されます。

### 2. Windowsのメモリ管理API (`VirtualAlloc`)

Windowsでは、プロセスがメモリを管理するためにWin32 APIの`VirtualAlloc`関数を使用します。この関数は、仮想アドレス空間の領域を予約、コミット、または解放するために使われます。

`VirtualAlloc`の主要な引数とフラグ:

*   `lpAddress`: 予約またはコミットする領域の開始アドレス。`NULL`を指定すると、システムが適切なアドレスを決定します。
*   `dwSize`: 領域のサイズ（バイト単位）。
*   `flAllocationType`: 割り当ての種類を指定するフラグ。
    *   `MEM_RESERVE`: 仮想アドレス空間の領域を予約しますが、物理ストレージは割り当てません。
    *   `MEM_COMMIT`: 予約された領域に物理ストレージ（RAMまたはページファイル）を割り当てます。
    *   `MEM_COMMIT | MEM_RESERVE`: 領域を予約し、同時にコミットします。
*   `flProtect`: 領域のメモリ保護を指定するフラグ。
    *   `PAGE_READWRITE`: 領域への読み取りおよび書き込みアクセスを許可します。

Goランタイムは、まず`MEM_RESERVE`で大きな仮想アドレス空間を確保し、その後、実際にメモリが必要になったときに`MEM_COMMIT`を使ってその一部をコミットするという戦略をとることが一般的です。

### 3. Goランタイムのメモリ管理 (`SysUsed`, `SysUnused`)

Goランタイムは、独自のメモリマネージャ（ガベージコレクタを含む）を持っています。OSから取得したメモリを細かく管理し、Goプログラムのヒープ、スタック、ゴルーチンなどに割り当てます。

*   **`runtime.SysUsed`**: GoランタイムがOSから取得した仮想メモリ領域のうち、実際に使用するためにコミットする（物理ストレージを割り当てる）際に内部的に呼び出される関数です。
*   **`runtime.SysUnused`**: GoランタイムがOSから取得した仮想メモリ領域のうち、もはや使用しないと判断した領域をOSに返却する（デコミットする）際に内部的に呼び出される関数です。

これらの関数は、Goの`runtime.MemStats`構造体で報告される`Sys`（OSから取得した総仮想メモリ）や`HeapReleased`（OSに返却されたヒープメモリ）といった統計値の背後にある、低レベルのOSとのインタラクションを担っています。

## 技術的詳細

このコミットの技術的詳細は、`runtime.SysUsed`関数における`VirtualAlloc`の呼び出しが失敗した場合のフォールバックメカニズムの導入にあります。

元のコードでは、`runtime·VirtualAlloc`（Goランタイムがラップした`VirtualAlloc`）の呼び出しが`v`（要求されたアドレス）を返さなかった場合、つまりコミットに失敗した場合、即座に`runtime·throw("runtime: failed to commit pages")`が実行され、プログラムが異常終了していました。

しかし、Windowsの`VirtualAlloc`は、要求された全量を一度にコミットできない場合でも、部分的にコミットできる可能性があります。また、システムのリソース状況によっては、大きなブロックのコミットは失敗しても、より小さなブロックに分割すれば成功する場合があります。

この修正は、`SysUnused`関数に以前適用されたロジックを`SysUsed`に持ち込むことで、この問題を解決します。そのロジックは以下の通りです。

1.  **ループによる再試行**: `while(n > 0)`ループを導入し、要求されたサイズ`n`がゼロになるまでコミット処理を繰り返します。
2.  **サイズを半分に**: `small = n`で現在のコミット試行サイズを初期化します。`runtime·VirtualAlloc`が失敗した場合、`small = (small / 2) & ~(4096-1)`という計算で`small`のサイズを半分にし、かつ4096バイト（Windowsのページサイズ）の倍数に切り捨てます。これにより、より小さなチャンクでのコミットを試みます。
3.  **最小サイズチェック**: `small < 4096`となった場合、つまりコミット試行サイズが最小単位（ページサイズ）よりも小さくなった場合は、これ以上分割してもコミットできないと判断し、`runtime·throw("runtime: failed to decommit pages")`（コミットの文脈だが、エラーメッセージは`SysUnused`から流用されている）でパニックを引き起こします。
4.  **成功時の処理**: `runtime·VirtualAlloc`が成功した場合、`v`ポインタを`small`だけ進め、`n`から`small`を減算します。これにより、コミットが成功した部分をスキップし、残りの部分のコミットを次のループで試行します。

このアプローチにより、Goランタイムは、一度に大きなメモリ領域をコミットできない場合でも、より小さなチャンクに分割してコミットを試みることができ、Windows環境でのメモリ割り当ての堅牢性が向上します。

## コアとなるコードの解説

追加されたコードブロックは、`runtime·SysUsed`関数内で、`runtime·VirtualAlloc`による初期のコミット試行が失敗した場合のフォールバックロジックを実装しています。

1.  `uintptr small;`
    *   コミットを試みる現在のチャンクサイズを保持するための変数`small`を宣言しています。

2.  `r = runtime·stdcall4(runtime·VirtualAlloc, (uintptr)v, n, MEM_COMMIT, PAGE_READWRITE);`
    *   これは既存のコードで、指定されたアドレス`v`からサイズ`n`のメモリ領域を`MEM_COMMIT`フラグ（コミット）と`PAGE_READWRITE`保護でコミットしようとします。
    *   `runtime·stdcall4`は、GoランタイムがWindows APIを呼び出すためのラッパー関数です。

3.  `if(r != v)`
    *   `VirtualAlloc`が成功した場合、要求されたアドレス`v`を返します。`r != v`は、コミットが失敗したことを意味します。
    *   **この`if`ブロックは、コミットが失敗した場合に即座にパニックを引き起こす元のロジックです。しかし、追加されたコードは、この`if`ブロックの後に続くため、この`if`文の条件が満たされた場合（つまり、最初のコミット試行が失敗した場合）に、新しいフォールバックロジックが実行されることになります。**

4.  `// Commit failed. See SysUnused.`
    *   コメントで、この後のコードがコミット失敗時の処理であり、`SysUnused`関数での修正と同様であることを示しています。

5.  `while(n > 0) { ... }`
    *   この外側の`while`ループは、まだコミットされていないメモリ領域`n`が残っている限り、処理を続行します。

6.  `small = n;`
    *   内側のループに入る前に、現在の残りのサイズ`n`を`small`にコピーします。これは、最初に残りの全量をコミットしようと試みるためです。

7.  `while(small >= 4096 && runtime·stdcall4(runtime·VirtualAlloc, (uintptr)v, small, MEM_COMMIT, PAGE_READWRITE) == nil)`
    *   この内側の`while`ループは、`small`がWindowsのページサイズ（4096バイト）以上であり、かつ`VirtualAlloc`によるコミットが失敗した場合に実行されます。
    *   `runtime·VirtualAlloc(...) == nil`は、`VirtualAlloc`が失敗したことを示します。
    *   **このループの目的は、コミットが失敗した場合に、試行するサイズ`small`を徐々に小さくしていくことです。**

8.  `small = (small / 2) & ~(4096-1);`
    *   `VirtualAlloc`が失敗した場合、`small`を半分にします。
    *   `& ~(4096-1)`は、`small`を4096の倍数に切り捨てるためのビット演算です。Windowsのメモリ管理はページ単位で行われるため、コミットサイズはページサイズの倍数である必要があります。

9.  `if(small < 4096)`
    *   内側のループが終了し、`small`が4096バイト未満になった場合、これ以上サイズを小さくしてもコミットできないと判断します。
    *   `runtime·throw("runtime: failed to decommit pages");`でパニックを引き起こします。エラーメッセージは`SysUnused`から流用されていますが、文脈的には「コミットに失敗した」ことを意味します。

10. `v = (byte*)v + small;`
    *   `VirtualAlloc`が`small`サイズの領域のコミットに成功した場合、ポインタ`v`を`small`バイト分進めます。これにより、次にコミットを試みる領域の開始アドレスが更新されます。

11. `n -= small;`
    *   コミットが成功した`small`サイズ分を、残りのコミットすべきサイズ`n`から減算します。

この修正により、Goランタイムは、Windows上でのメモリコミットの失敗に対してより堅牢になり、部分的なコミットの可能性を考慮して処理を継続できるようになりました。

3.  **最小サイズチェック**: `small < 4096`となった場合、つまりコミット試行サイズが最小単位（ページサイズ）よりも小さくなった場合は、これ以上分割してもコミットできないと判断し、`runtime·throw("runtime: failed to decommit pages")`（コミットの文脈だが、エラーメッセージは`SysUnused`から流用されている）でパニックを引き起こします。
4.  **成功時の処理**: `runtime·VirtualAlloc`が成功した場合、`v`ポインタを`small`だけ進め、`n`から`small`を減算します。これにより、コミットが成功した部分をスキップし、残りの部分のコミットを次のループで試行します。

このアプローチにより、Goランタイムは、一度に大きなメモリ領域をコミットできない場合でも、より小さなチャンクに分割してコミットを試みることができ、Windows環境でのメモリ割り当ての堅牢性が向上します。

## コアとなるコードの解説

追加されたコードブロックは、`runtime·SysUsed`関数内で、`runtime·VirtualAlloc`による初期のコミット試行が失敗した場合のフォールバックロジックを実装しています。

1.  `uintptr small;`
    *   コミットを試みる現在のチャンクサイズを保持するための変数`small`を宣言しています。

2.  `r = runtime·stdcall4(runtime·VirtualAlloc, (uintptr)v, n, MEM_COMMIT, PAGE_READWRITE);`
    *   これは既存のコードで、指定されたアドレス`v`からサイズ`n`のメモリ領域を`MEM_COMMIT`フラグ（コミット）と`PAGE_READWRITE`保護でコミットしようとします。
    *   `runtime·stdcall4`は、GoランタイムがWindows APIを呼び出すためのラッパー関数です。

3.  `if(r != v)`
    *   `VirtualAlloc`が成功した場合、要求されたアドレス`v`を返します。`r != v`は、コミットが失敗したことを意味します。
    *   **この`if`ブロックは、コミットが失敗した場合に即座にパニックを引き起こす元のロジックです。しかし、追加されたコードは、この`if`ブロックの後に続くため、この`if`文の条件が満たされた場合（つまり、最初のコミット試行が失敗した場合）に、新しいフォールバックロジックが実行されることになります。**

4.  `// Commit failed. See SysUnused.`
    *   コメントで、この後のコードがコミット失敗時の処理であり、`SysUnused`関数での修正と同様であることを示しています。

5.  `while(n > 0) { ... }`
    *   この外側の`while`ループは、まだコミットされていないメモリ領域`n`が残っている限り、処理を続行します。

6.  `small = n;`
    *   内側のループに入る前に、現在の残りのサイズ`n`を`small`にコピーします。これは、最初に残りの全量をコミットしようと試みるためです。

7.  `while(small >= 4096 && runtime·stdcall4(runtime·VirtualAlloc, (uintptr)v, small, MEM_COMMIT, PAGE_READWRITE) == nil)`
    *   この内側の`while`ループは、`small`がWindowsのページサイズ（4096バイト）以上であり、かつ`VirtualAlloc`によるコミットが失敗した場合に実行されます。
    *   `runtime·VirtualAlloc(...) == nil`は、`VirtualAlloc`が失敗したことを示します。
    *   **このループの目的は、コミットが失敗した場合に、試行するサイズ`small`を徐々に小さくしていくことです。**

8.  `small = (small / 2) & ~(4096-1);`
    *   `VirtualAlloc`が失敗した場合、`small`を半分にします。
    *   `& ~(4096-1)`は、`small`を4096の倍数に切り捨てるためのビット演算です。Windowsのメモリ管理はページ単位で行われるため、コミットサイズはページサイズの倍数である必要があります。

9.  `if(small < 4096)`
    *   内側のループが終了し、`small`が4096バイト未満になった場合、これ以上サイズを小さくしてもコミットできないと判断します。
    *   `runtime·throw("runtime: failed to decommit pages");`でパニックを引き起こします。エラーメッセージは`SysUnused`から流用されていますが、文脈的には「コミットに失敗した」ことを意味します。

10. `v = (byte*)v + small;`
    *   `VirtualAlloc`が`small`サイズの領域のコミットに成功した場合、ポインタ`v`を`small`バイト分進めます。これにより、次にコミットを試みる領域の開始アドレスが更新されます。

11. `n -= small;`
    *   コミットが成功した`small`サイズ分を、残りのコミットすべきサイズ`n`から減算します。

この修正により、Goランタイムは、Windows上でのメモリコミットの失敗に対してより堅牢になり、部分的なコミットの可能性を考慮して処理を継続できるようになりました。

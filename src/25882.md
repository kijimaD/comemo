# [インデックス 25882] ファイルの概要

このコミットは、Goの`net/http`パッケージにおいて、再利用されたHTTPコネクションがサーバーによって閉じられようとしている際に発生する可能性のあるリクエスト失敗を、冪等なリクエストに限り自動的に再試行するメカニズムを導入するものです。これにより、HTTPクライアントの堅牢性が向上し、特定のネットワーク条件下での信頼性が高まります。

## 元コミット内容

Goの`net/http`パッケージにおいて、再利用されたHTTPコネクションがサーバーによって閉じられようとしている際に発生する可能性のあるリクエスト失敗を、冪等なHTTPリクエストに限り自動的に再試行する機能を追加します。

具体的には、以下の問題に対処します。
サーバーがコネクションを閉じている最中に、クライアントがそのコネクションを再利用しようとすると、リクエストの一部または全部を正常に書き込めたとしても、ソケットからの読み取り（または書き込み完了）時にコネクションエラー（EOFなど）が発生することがあります。これは`Transport`の`RoundTrip`メソッドからEOFとして返されます。この問題はGoのIssue #4677で議論されていました。

この変更は、Chromiumのガイドラインに倣い、以下の条件を満たす場合にのみ冪等なリクエストを再試行します。
1.  コネクションが以前に正常に使用されたことがある（再利用されたコネクションである）。
2.  レスポンスのヘッダーデータがまだ受信されていない。

また、この変更の一環として、これまでインラインで定義されていた`errMissingHost`エラーが、エクスポートされない変数として定義されました。`errMissingHost`は、`Request`の`Write()`メソッドから返される唯一のネットワークエラーではないエラーです。

さらに、この変更は`TestLinuxSendfile`テストに影響を与えました。このテストは、今回の変更が再試行を意図するシナリオを意図的に引き起こすものでしたが、テストサーバーが再試行前にテストリスナーでのコネクション受け入れを停止するため、テストがタイムアウトする可能性がありました。この問題を解決するため、テストは非冪等なテストタイプ（POST）を使用するように変更されました。

## 変更の背景

このコミットの主な背景には、HTTP/1.1の持続的接続（Keep-Alive）の利用における信頼性の課題があります。HTTP/1.1では、複数のリクエスト/レスポンスサイクルで同じTCPコネクションを再利用することで、コネクション確立のオーバーヘッドを削減し、パフォーマンスを向上させます。しかし、この再利用のメカニズムには潜在的な問題が伴います。

サーバーがアイドル状態のコネクションをタイムアウトで閉じたり、何らかの理由で能動的にコネクションを閉じたりする際に、クライアントがそのコネクションを再利用しようとすると、競合状態が発生する可能性があります。クライアントがリクエストを送信し始めた直後、または送信中にサーバーがコネクションを閉じると、クライアントはリクエストを完全に送信できたとしても、レスポンスを読み取る際に予期せぬエラー（例えばEOFや"connection reset by peer"）を受け取ることがあります。

特に、Goの`net/http`パッケージの`Transport`層では、このような「死んだ再利用コネクション」にリクエストを送信してしまい、`RoundTrip`がEOFエラーを返すという問題がGo Issue #4677で報告されていました。この問題は、ユーザー体験の低下やアプリケーションの不安定性につながるため、対処が必要でした。

このコミットは、このような状況下で、特に副作用のない「冪等な」リクエスト（GET, HEADなど）であれば、安全に別の新しいコネクションで再試行することで、クライアント側の堅牢性を高めることを目的としています。これにより、ユーザーは一時的なネットワークの問題やサーバー側のコネクション管理の挙動に起因するエラーに遭遇する機会が減り、よりスムーズな通信が期待できるようになります。

## 前提知識の解説

### HTTP/1.1 持続的接続 (Keep-Alive)

HTTP/1.1では、`Connection: keep-alive`ヘッダーを使用することで、単一のTCPコネクション上で複数のHTTPリクエストとレスポンスを交換できます。これにより、新しいTCPコネクションを確立する際のハンドシェイク（SYN, SYN-ACK, ACK）やTLSハンドシェイクのオーバーヘッドを削減し、Webページのロード時間やAPI通信の効率を向上させます。クライアントとサーバーは、それぞれアイドルタイムアウトを設定し、一定時間データが流れなければコネクションを閉じることができます。

### HTTPメソッドの冪等性 (Idempotency)

HTTPメソッドの冪等性とは、同じリクエストを複数回実行しても、サーバー側の状態が初回実行時と同じ結果になる特性を指します。

*   **冪等なメソッド**:
    *   **GET**: リソースの取得。何度実行してもリソースの状態は変わらない。
    *   **HEAD**: GETと同様だが、レスポンスボディを含まない。
    *   **OPTIONS**: リソースがサポートする通信オプションの取得。
    *   **TRACE**: リクエストパスの診断。
    *   **PUT**: リソースの作成または更新。同じ内容で複数回実行しても、リソースは同じ状態になる。
    *   **DELETE**: リソースの削除。初回で削除され、それ以降はリソースが存在しない状態が続く。
*   **非冪等なメソッド**:
    *   **POST**: リソースの作成やデータの送信。複数回実行すると、通常は複数のリソースが作成されたり、データが複数回処理されたりするなど、サーバーの状態が変化する可能性がある。

このコミットでは、冪等なリクエストのみを再試行の対象とすることで、サーバーに意図しない副作用（例: 注文の重複作成）が発生するのを防ぎます。

### Goの`net/http`パッケージの`Transport`と`RoundTrip`

Goの`net/http`パッケージは、HTTPクライアントとサーバーの実装を提供します。
*   `http.Client`: HTTPリクエストを送信するための高レベルなインターフェース。
*   `http.Transport`: `http.Client`の内部で実際にHTTPリクエストを送信し、レスポンスを受信する低レベルな実装。コネクションのプール、プロキシの処理、TLSハンドシェイクなどを担当します。
*   `RoundTrip(req *Request) (*Response, error)`: `http.Transport`の主要なメソッドで、単一のHTTPリクエストを送信し、そのレスポンスを受け取ります。このメソッドが、コネクションの再利用やエラーハンドリングのロジックを内包しています。

### `persistConn`構造体

`net/http`パッケージ内部で使用される`persistConn`は、単一の持続的HTTPコネクション（TCP接続）を抽象化する構造体です。この構造体は、コネクションの読み書きバッファ、状態（アイドル、使用中、破損など）、そしてコネクションが再利用されたかどうかなどの情報を管理します。

### EOFエラー

EOF (End Of File) は、通常、ファイルやストリームの終端に達したことを示すエラーです。ネットワークプログラミングにおいては、TCPコネクションの相手側がコネクションを正常にシャットダウンした際に、読み取り操作でEOFが返されることがあります。しかし、予期せぬタイミングでEOFが返される場合、それは相手側が突然コネクションを切断した（例えば、サーバーがリクエストの処理中にクラッシュした、またはアイドルタイムアウトでコネクションを閉じた直後にクライアントが書き込みを試みた）ことを意味する場合があります。

## 技術的詳細

このコミットは、`net/http`パッケージの`Transport`層に、再利用されたコネクションでの一時的なエラーに対する自動再試行ロジックを導入します。

1.  **`RoundTrip`メソッドの変更**:
    *   `Transport.RoundTrip`メソッドは、リクエストを送信する前に無限ループ`for {}`で囲まれるようになりました。これにより、特定の条件でエラーが発生した場合にリクエストを再試行できるようになります。
    *   リクエストごとに`transportRequest`が新しく作成されるようになり、再試行のたびにリクエストの状態がクリーンに保たれます。
    *   `t.getConn(req, cm)`でコネクションを取得し、`pconn.roundTrip(treq)`で実際のリクエスト送信とレスポンス受信を行います。

2.  **`checkTransportResend`関数の導入**:
    *   `RoundTrip`内でエラーが発生した場合、新しく導入された`checkTransportResend`関数が呼び出されます。この関数は、エラーが再試行可能かどうかを判断します。
    *   `checkTransportResend`は、`beforeRespHeaderError`というカスタムエラー型をチェックします。これは、レスポンスヘッダーが受信される前にI/Oエラーが発生したことを示すマーカーエラーです。
    *   再試行の条件は以下の通りです。
        *   エラーが`errMissingHost`ではないこと。
        *   `pconn.isReused()`が`true`であること（コネクションが再利用されたものであること）。
        *   `req.isReplayable()`が`true`であること（リクエストが冪等であること）。
    *   これらの条件がすべて満たされた場合、`checkTransportResend`は`nil`を返します。`nil`が返された場合、`RoundTrip`のループは次のイテレーションに進み、リクエストは新しいコネクションで再試行されます。
    *   それ以外の場合、`checkTransportResend`は元のエラー（または`beforeRespHeaderError`からアンラップされたエラー）を返し、`RoundTrip`はエラーを呼び出し元に伝播します。

3.  **`beforeRespHeaderError`カスタムエラー型**:
    *   この新しいエラー型は、レスポンスヘッダーがクライアントに到達する前にコネクションエラーが発生したことを示すために導入されました。これにより、リクエストがサーバーに到達し、処理が開始された可能性が低い状況でのみ再試行を行うという、より安全な判断が可能になります。
    *   `persistConn.roundTrip`や`persistConn.readLoop`内で、レスポンスヘッダー受信前のI/Oエラーをこの型でラップして返します。

4.  **`Request.isReplayable()`メソッドの追加**:
    *   `Request`構造体に`isReplayable()`メソッドが追加されました。これは、リクエストが冪等であるかどうかを判断します。
    *   具体的には、リクエストボディが`nil`であり、かつメソッドが`GET`, `HEAD`, `OPTIONS`, `TRACE`のいずれかである場合に`true`を返します。これにより、副作用のあるリクエスト（例: POST）が誤って再試行されることを防ぎます。

5.  **`persistConn.markReused()`と`reused`フィールド**:
    *   `persistConn`構造体に`reused`というブール型フィールドが追加されました。これは、このコネクションが以前に正常なリクエスト/レスポンスサイクルで使用され、再利用されているかどうかを示します。
    *   `Transport.putIdleConn`（アイドルコネクションプールにコネクションを戻す際）で`pconn.markReused()`が呼び出され、`reused`フィールドが`true`に設定されます。これにより、初めて使用されるコネクションでは再試行が行われないようになります。

6.  **`errMissingHost`の定義変更**:
    *   `Request.Write`メソッド内でインラインで定義されていた`"http: Request.Write on Request with no Host or URL set"`というエラー文字列が、`var errMissingHost = errors.New(...)`として`request.go`内で定義され、再利用されるようになりました。これにより、エラーメッセージの一貫性が保たれ、テストなどでの比較が容易になります。

7.  **テストの変更 (`TestLinuxSendfile`)**:
    *   `TestLinuxSendfile`は、再試行シナリオを意図的に引き起こすテストでしたが、新しい再試行ロジックとテストサーバーの挙動が競合し、タイムアウトする問題が発生しました。
    *   このテストは、`Get`リクエストの代わりに`Post`リクエストを使用するように変更されました。`Post`は非冪等なリクエストであるため、新しい再試行ロジックの対象外となり、テストが正常に完了するようになります。

これらの変更により、GoのHTTPクライアントは、サーバーがコネクションを閉じるタイミングとクライアントがそのコネクションを再利用しようとするタイミングが重なった場合に発生する一時的なネットワークエラーに対して、より回復力を持つようになりました。

## コアとなるコードの解説

### `src/net/http/transport.go` の `RoundTrip` メソッド

```go
func (t *Transport) RoundTrip(req *Request) (*Response, error) {
	// ... (URLチェックなど)

	for { // 再試行のためのループ
		treq := &transportRequest{Request: req} // リクエストごとに新しいtransportRequestを作成
		cm, err := t.connectMethodForRequest(treq)
		if err != nil {
			req.closeBody()
			return nil, err
		}

		pconn, err := t.getConn(req, cm) // コネクションを取得 (キャッシュまたは新規)
		if err != nil {
			t.setReqCanceler(req, nil)
			req.closeBody()
			return nil, err
		}

		var resp *Response
		if pconn.alt != nil {
			// HTTP/2 path.
			resp, err = pconn.alt.RoundTrip(req)
		} else {
			resp, err = pconn.roundTrip(treq) // HTTP/1.x リクエストの実行
		}
		if err == nil {
			return resp, nil // 成功したらレスポンスを返す
		}
		if err := checkTransportResend(err, req, pconn); err != nil { // エラーが発生した場合、再試行可能かチェック
			return nil, err // 再試行不可ならエラーを返す
		}
		if retried != nil { // テスト用のフック
			retried()
		}
		// 再試行可能であれば、ループの次のイテレーションでリクエストを再送信
	}
}
```
`RoundTrip`メソッドは、リクエストの送信とレスポンスの受信を行う`net/http`クライアントの中心的なロジックです。このコミットでは、このメソッドが`for {}`ループで囲まれ、エラー発生時に`checkTransportResend`関数が`nil`を返した場合にリクエストを再試行するようになりました。これにより、一時的なコネクションエラーに対して自動的に回復する能力が追加されます。

### `src/net/http/transport.go` の `checkTransportResend` 関数

```go
func checkTransportResend(err error, req *Request, pconn *persistConn) error {
	brhErr, ok := err.(beforeRespHeaderError) // beforeRespHeaderErrorかチェック
	if !ok {
		return err // beforeRespHeaderErrorでなければ再試行しない
	}
	err = brhErr.error // カスタムエラーから元のエラーをアンラップ
	if err != errMissingHost && pconn.isReused() && req.isReplayable() {
		// サーバーが閉じているコネクションを再利用しようとした場合
		// リクエストを書き込んだが、レスポンスヘッダー受信前にコネクションエラーが発生した場合
		// (errMissingHostではない、再利用されたコネクション、冪等なリクエスト)
		// これらの条件を満たせば再試行する (nilを返す)
		return nil
	}
	return err // 上記条件を満たさなければエラーを返す
}
```
この関数は、`RoundTrip`で発生したエラーが、新しいコネクションでリクエストを再送信するべき状況であるかを判断します。重要なのは、エラーが`beforeRespHeaderError`でラップされていること（レスポンスヘッダー受信前のエラーであること）、コネクションが再利用されたものであること、そしてリクエストが冪等であることの3点です。これらの条件が揃った場合にのみ`nil`を返し、`RoundTrip`ループが再試行に進むことを許可します。

### `src/net/http/request.go` の `isReplayable` メソッド

```go
func (r *Request) isReplayable() bool {
	return r.Body == nil && // リクエストボディがないこと
		(r.Method == "GET" ||
			r.Method == "HEAD" ||
			r.Method == "OPTIONS" ||
			r.Method == "TRACE") // 冪等なメソッドであること
}
```
このメソッドは、リクエストが安全に再試行できる（冪等である）かどうかを判断します。リクエストボディがないことと、HTTPメソッドが`GET`, `HEAD`, `OPTIONS`, `TRACE`のいずれかであることを条件としています。これにより、POSTなどの非冪等なリクエストが意図せず複数回実行されることを防ぎ、サーバー側の状態の一貫性を保ちます。

### `src/net/http/transport.go` の `persistConn` 構造体と `markReused` メソッド

```go
type persistConn struct {
	// ...
	reused               bool // whether conn has had successful request/response and is being reused.
	// ...
}

// markReused marks this connection as having been successfully used for a
// request and response.
func (pc *persistConn) markReused() {
	pc.lk.Lock()
	pc.reused = true
	pc.lk.Unlock()
}
```
`persistConn`に`reused`フィールドが追加され、コネクションが一度でも正常にリクエスト/レスポンスサイクルで使用された場合に`true`に設定されます。`checkTransportResend`はこの`reused`フィールドをチェックし、初めて使用されるコネクションでの再試行を防ぎます。これは、新しいコネクションでの最初の試行が失敗した場合、それは再利用コネクションの問題ではなく、より根本的なネットワークの問題である可能性が高いため、再試行しても無駄であるという判断に基づいています。

### `src/net/http/transport.go` の `beforeRespHeaderError` 型

```go
// beforeRespHeaderError is used to indicate when an IO error has occurred before
// any header data was received.
type beforeRespHeaderError struct {
	error
}
```
このカスタムエラー型は、レスポンスヘッダーがクライアントに到達する前にI/Oエラーが発生したことを示すために導入されました。このエラーでラップされた場合のみ再試行の対象となるため、サーバーがリクエストを処理し始めた後に発生したエラー（例えば、サーバー内部エラーでレスポンスボディの送信中にエラーになった場合など）は再試行されません。これにより、サーバーに二重のリクエスト処理を強制するリスクを最小限に抑えます。

## 元コミット内容

Goの`net/http`パッケージにおいて、再利用されたHTTPコネクションがサーバーによって閉じられようとしている際に発生する可能性のあるリクエスト失敗を、冪等なHTTPリクエストに限り自動的に再試行する機能を追加します。

具体的には、以下の問題に対処します。
サーバーがコネクションを閉じている最中に、クライアントがそのコネクションを再利用しようとすると、リクエストの一部または全部を正常に書き込めたとしても、ソケットからの読み取り（または書き込み完了）時にコネクションエラー（EOFなど）が発生することがあります。これは`Transport`の`RoundTrip`メソッドからEOFとして返されます。この問題はGoのIssue #4677で議論されていました。

この変更は、Chromiumのガイドラインに倣い、以下の条件を満たす場合にのみ冪等なリクエストを再試行します。
1.  コネクションが以前に正常に使用されたことがある（再利用されたコネクションである）。
2.  レスポンスのヘッダーデータがまだ受信されていない。

また、この変更の一環として、これまでインラインで定義されていた`errMissingHost`エラーが、エクスポートされない変数として定義されました。`errMissingHost`は、`Request`の`Write()`メソッドから返される唯一のネットワークエラーではないエラーです。

さらに、この変更は`TestLinuxSendfile`テストに影響を与えました。このテストは、今回の変更が再試行を意図するシナリオを意図的に引き起こすものでしたが、テストサーバーが再試行前にテストリスナーでのコネクション受け入れを停止するため、テストがタイムアウトする可能性がありました。この問題を解決するため、テストは非冪等なテストタイプ（POST）を使用するように変更されました。

## 変更の背景

このコミットの主な背景には、HTTP/1.1の持続的接続（Keep-Alive）の利用における信頼性の課題があります。HTTP/1.1では、複数のリクエスト/レスポンスサイクルで同じTCPコネクションを再利用することで、コネクション確立のオーバーヘッドを削減し、パフォーマンスを向上させます。しかし、この再利用のメカニズムには潜在的な問題が伴います。

サーバーがアイドル状態のコネクションをタイムアウトで閉じたり、何らかの理由で能動的にコネクションを閉じたりする際に、クライアントがそのコネクションを再利用しようとすると、競合状態が発生する可能性があります。クライアントがリクエストを送信し始めた直後、または送信中にサーバーがコネクションを閉じると、クライアントはリクエストを完全に送信できたとしても、レスポンスを読み取る際に予期せぬエラー（例えばEOFや"connection reset by peer"）を受け取ることがあります。

特に、Goの`net/http`パッケージの`Transport`層では、このような「死んだ再利用コネクション」にリクエストを送信してしまい、`RoundTrip`がEOFエラーを返すという問題がGo Issue #4677で報告されていました。この問題は、ユーザー体験の低下やアプリケーションの不安定性につながるため、対処が必要でした。

このコミットは、このような状況下で、特に副作用のない「冪等な」リクエスト（GET, HEADなど）であれば、安全に別の新しいコネクションで再試行することで、クライアント側の堅牢性を高めることを目的としています。これにより、ユーザーは一時的なネットワークの問題やサーバー側のコネクション管理の挙動に起因するエラーに遭遇する機会が減り、よりスムーズな通信が期待できるようになります。

## 前提知識の解説

### HTTP/1.1 持続的接続 (Keep-Alive)

HTTP/1.1では、`Connection: keep-alive`ヘッダーを使用することで、単一のTCPコネクション上で複数のHTTPリクエストとレスポンスを交換できます。これにより、新しいTCPコネクションを確立する際のハンドシェイク（SYN, SYN-ACK, ACK）やTLSハンドシェイクのオーバーヘッドを削減し、Webページのロード時間やAPI通信の効率を向上させます。クライアントとサーバーは、それぞれアイドルタイムアウトを設定し、一定時間データが流れなければコネクションを閉じることができます。

### HTTPメソッドの冪等性 (Idempotency)

HTTPメソッドの冪等性とは、同じリクエストを複数回実行しても、サーバー側の状態が初回実行時と同じ結果になる特性を指します。

*   **冪等なメソッド**:
    *   **GET**: リソースの取得。何度実行してもリソースの状態は変わらない。
    *   **HEAD**: GETと同様だが、レスポンスボディを含まない。
    *   **OPTIONS**: リソースがサポートする通信オプションの取得。
    *   **TRACE**: リクエストパスの診断。
    *   **PUT**: リソースの作成または更新。同じ内容で複数回実行しても、リソースは同じ状態になる。
    *   **DELETE**: リソースの削除。初回で削除され、それ以降はリソースが存在しない状態が続く。
*   **非冪等なメソッド**:
    *   **POST**: リソースの作成やデータの送信。複数回実行すると、通常は複数のリソースが作成されたり、データが複数回処理されたりするなど、サーバーの状態が変化する可能性がある。

このコミットでは、冪等なリクエストのみを再試行の対象とすることで、サーバーに意図しない副作用（例: 注文の重複作成）が発生するのを防ぎます。

### Goの`net/http`パッケージの`Transport`と`RoundTrip`

Goの`net/http`パッケージは、HTTPクライアントとサーバーの実装を提供します。
*   `http.Client`: HTTPリクエストを送信するための高レベルなインターフェース。
*   `http.Transport`: `http.Client`の内部で実際にHTTPリクエストを送信し、レスポンスを受信する低レベルな実装。コネクションのプール、プロキシの処理、TLSハンドシェイクなどを担当します。
*   `RoundTrip(req *Request) (*Response, error)`: `http.Transport`の主要なメソッドで、単一のHTTPリクエストを送信し、そのレスポンスを受け取ります。このメソッドが、コネクションの再利用やエラーハンドリングのロジックを内包しています。

### `persistConn`構造体

`net/http`パッケージ内部で使用される`persistConn`は、単一の持続的HTTPコネクション（TCP接続）を抽象化する構造体です。この構造体は、コネクションの読み書きバッファ、状態（アイドル、使用中、破損など）、そしてコネクションが再利用されたかどうかなどの情報を管理します。

### EOFエラー

EOF (End Of File) は、通常、ファイルやストリームの終端に達したことを示すエラーです。ネットワークプログラミングにおいては、TCPコネクションの相手側がコネクションを正常にシャットダウンした際に、読み取り操作でEOFが返されることがあります。しかし、予期せぬタイミングでEOFが返される場合、それは相手側が突然コネクションを切断した（例えば、サーバーがリクエストの処理中にクラッシュした、またはアイドルタイムアウトでコネクションを閉じた直後にクライアントが書き込みを試みた）ことを意味する場合があります。

## 技術的詳細

このコミットは、`net/http`パッケージの`Transport`層に、再利用されたコネクションでの一時的なエラーに対する自動再試行ロジックを導入します。

1.  **`RoundTrip`メソッドの変更**:
    *   `Transport.RoundTrip`メソッドは、リクエストを送信する前に無限ループ`for {}`で囲まれるようになりました。これにより、特定の条件でエラーが発生した場合にリクエストを再試行できるようになります。
    *   リクエストごとに`transportRequest`が新しく作成されるようになり、再試行のたびにリクエストの状態がクリーンに保たれます。
    *   `t.getConn(req, cm)`でコネクションを取得し、`pconn.roundTrip(treq)`で実際のリクエスト送信とレスポンス受信を行います。

2.  **`checkTransportResend`関数の導入**:
    *   `RoundTrip`内でエラーが発生した場合、新しく導入された`checkTransportResend`関数が呼び出されます。この関数は、エラーが再試行可能かどうかを判断します。
    *   `checkTransportResend`は、`beforeRespHeaderError`というカスタムエラー型をチェックします。これは、レスポンスヘッダーが受信される前にI/Oエラーが発生したことを示すマーカーエラーです。
    *   再試行の条件は以下の通りです。
        *   エラーが`errMissingHost`ではないこと。
        *   `pconn.isReused()`が`true`であること（コネクションが再利用されたものであること）。
        *   `req.isReplayable()`が`true`であること（リクエストが冪等であること）。
    *   これらの条件がすべて満たされた場合、`checkTransportResend`は`nil`を返します。`nil`が返された場合、`RoundTrip`のループは次のイテレーションに進み、リクエストは新しいコネクションで再試行されます。
    *   それ以外の場合、`checkTransportResend`は元のエラー（または`beforeRespHeaderError`からアンラップされたエラー）を返し、`RoundTrip`はエラーを呼び出し元に伝播します。

3.  **`beforeRespHeaderError`カスタムエラー型**:
    *   この新しいエラー型は、レスポンスヘッダーがクライアントに到達する前にコネクションエラーが発生したことを示すために導入されました。これにより、リクエストがサーバーに到達し、処理が開始された可能性が低い状況でのみ再試行を行うという、より安全な判断が可能になります。
    *   `persistConn.roundTrip`や`persistConn.readLoop`内で、レスポンスヘッダー受信前のI/Oエラーをこの型でラップして返します。

4.  **`Request.isReplayable()`メソッドの追加**:
    *   `Request`構造体に`isReplayable()`メソッドが追加されました。これは、リクエストが冪等であるかどうかを判断します。
    *   具体的には、リクエストボディが`nil`であり、かつメソッドが`GET`, `HEAD`, `OPTIONS`, `TRACE`のいずれかである場合に`true`を返します。これにより、副作用のあるリクエスト（例: POST）が誤って複数回実行されることを防ぎます。

5.  **`persistConn.markReused()`と`reused`フィールド**:
    *   `persistConn`構造体に`reused`というブール型フィールドが追加されました。これは、このコネクションが以前に正常なリクエスト/レスポンスサイクルで使用され、再利用されているかどうかを示します。
    *   `Transport.putIdleConn`（アイドルコネクションプールにコネクションを戻す際）で`pconn.markReused()`が呼び出され、`reused`フィールドが`true`に設定されます。これにより、初めて使用されるコネクションでは再試行が行われないようになります。

6.  **`errMissingHost`の定義変更**:
    *   `Request.Write`メソッド内でインラインで定義されていた`"http: Request.Write on Request with no Host or URL set"`というエラー文字列が、`var errMissingHost = errors.New(...)`として`request.go`内で定義され、再利用されるようになりました。これにより、エラーメッセージの一貫性が保たれ、テストなどでの比較が容易になります。

7.  **テストの変更 (`TestLinuxSendfile`)**:
    *   `TestLinuxSendfile`は、再試行シナリオを意図的に引き起こすテストでしたが、新しい再試行ロジックとテストサーバーの挙動が競合し、タイムアウトする問題が発生しました。
    *   このテストは、`Get`リクエストの代わりに`Post`リクエストを使用するように変更されました。`Post`は非冪等なリクエストであるため、新しい再試行ロジックの対象外となり、テストが正常に完了するようになります。

これらの変更により、GoのHTTPクライアントは、サーバーがコネクションを閉じるタイミングとクライアントがそのコネクションを再利用しようとするタイミングが重なった場合に発生する一時的なネットワークエラーに対して、より回復力を持つようになりました。

### `src/net/http/transport.go` の `RoundTrip` メソッド

```go
func (t *Transport) RoundTrip(req *Request) (*Response, error) {
	// ... (URLチェックなど)

	for { // 再試行のためのループ
		treq := &transportRequest{Request: req} // リクエストごとに新しいtransportRequestを作成
		cm, err := t.connectMethodForRequest(treq)
		if err != nil {
			req.closeBody()
			return nil, err
		}

		pconn, err := t.getConn(req, cm) // コネクションを取得 (キャッシュまたは新規)
		if err != nil {
			t.setReqCanceler(req, nil)
			req.closeBody()
			return nil, err
		}

		var resp *Response
		if pconn.alt != nil {
			// HTTP/2 path.
			resp, err = pconn.alt.RoundTrip(req)
		} else {
			resp, err = pconn.roundTrip(treq) // HTTP/1.x リクエストの実行
		}
		if err == nil {
			return resp, nil // 成功したらレスポンスを返す
		}
		if err := checkTransportResend(err, req, pconn); err != nil { // エラーが発生した場合、再試行可能かチェック
			return nil, err // 再試行不可ならエラーを返す
		}
		if retried != nil { // テスト用のフック
			retried()
		}
		// 再試行可能であれば、ループの次のイテレーションでリクエストを再送信
	}
}
```
`RoundTrip`メソッドは、リクエストの送信とレスポンスの受信を行う`net/http`クライアントの中心的なロジックです。このコミットでは、このメソッドが`for {}`ループで囲まれ、エラー発生時に`checkTransportResend`関数が`nil`を返した場合にリクエストを再試行するようになりました。これにより、一時的なコネクションエラーに対して自動的に回復する能力が追加されます。

### `src/net/http/transport.go` の `checkTransportResend` 関数

```go
func checkTransportResend(err error, req *Request, pconn *persistConn) error {
	brhErr, ok := err.(beforeRespHeaderError) // beforeRespHeaderErrorかチェック
	if !ok {
		return err // beforeRespHeaderErrorでなければ再試行しない
	}
	err = brhErr.error // カスタムエラーから元のエラーをアンラップ
	if err != errMissingHost && pconn.isReused() && req.isReplayable() {
		// サーバーが閉じているコネクションを再利用しようとした場合
		// リクエストを書き込んだが、レスポンスヘッダー受信前にコネクションエラーが発生した場合
		// (errMissingHostではない、再利用されたコネクション、冪等なリクエスト)
		// これらの条件を満たせば再試行する (nilを返す)
		return nil
	}
	return err // 上記条件を満たさなければエラーを返す
}
```
この関数は、`RoundTrip`で発生したエラーが、新しいコネクションでリクエストを再送信するべき状況であるかを判断します。重要なのは、エラーが`beforeRespHeaderError`でラップされていること（レスポンスヘッダー受信前のエラーであること）、コネクションが再利用されたものであること、そしてリクエストが冪等であることの3点です。これらの条件が揃った場合にのみ`nil`を返し、`RoundTrip`ループが再試行に進むことを許可します。

### `src/net/http/request.go` の `isReplayable` メソッド

```go
func (r *Request) isReplayable() bool {
	return r.Body == nil && // リクエストボディがないこと
		(r.Method == "GET" ||
			r.Method == "HEAD" ||
			r.Method == "OPTIONS" ||
			r.Method == "TRACE") // 冪等なメソッドであること
}
```
このメソッドは、リクエストが安全に再試行できる（冪等である）かどうかを判断します。リクエストボディがないことと、HTTPメソッドが`GET`, `HEAD`, `OPTIONS`, `TRACE`のいずれかであることを条件としています。これにより、POSTなどの非冪等なリクエストが意図せず複数回実行されることを防ぎ、サーバー側の状態の一貫性を保ちます。

### `src/net/http/transport.go` の `persistConn` 構造体と `markReused` メソッド

```go
type persistConn struct {
	// ...
	reused               bool // whether conn has had successful request/response and is being reused.
	// ...
}

// markReused marks this connection as having been successfully used for a
// request and response.
func (pc *persistConn) markReused() {
	pc.lk.Lock()
	pc.reused = true
	pc.lk.Unlock()
}
```
`persistConn`に`reused`フィールドが追加され、コネクションが一度でも正常にリクエスト/レスポンスサイクルで使用された場合に`true`に設定されます。`checkTransportResend`はこの`reused`フィールドをチェックし、初めて使用されるコネクションでの再試行を防ぎます。これは、新しいコネクションでの最初の試行が失敗した場合、それは再利用コネクションの問題ではなく、より根本的なネットワークの問題である可能性が高いため、再試行しても無駄であるという判断に基づいています。

### `src/net/http/transport.go` の `beforeRespHeaderError` 型

```go
// beforeRespHeaderError is used to indicate when an IO error has occurred before
// any header data was received.
type beforeRespHeaderError struct {
	error
}
```
このカスタムエラー型は、レスポンスヘッダーがクライアントに到達する前にI/Oエラーが発生したことを示すために導入されました。このエラーでラップされた場合のみ再試行の対象となるため、サーバーがリクエストを処理し始めた後に発生したエラー（例えば、サーバー内部エラーでレスポンスボディの送信中にエラーになった場合など）は再試行されません。これにより、サーバーに二重のリクエスト処理を強制するリスクを最小限に抑えます。

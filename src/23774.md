# [インデックス 23774] ファイルの概要

このコミットは、Go言語の `fmt` パッケージにおけるスキャン関数、特に `Scanf` ファミリーの改行文字の扱いに関するバグを修正し、ドキュメントとの整合性を確保するものです。具体的には、`Scanf` がフォーマット文字列内の改行と入力中の改行を正しく一致させるように動作を改善しています。

## 元コミット内容

`fmt: require newlines to match when scanning with a format`

このコミットは、`fmt` パッケージのスキャン関数において、フォーマット文字列を使用する際に改行文字が正しく一致することを要求するように修正します。

ドキュメントには、改行の振る舞いについて以下のように記述されています。

*   `Scan` など: 改行はスペースとして扱われる。
*   `Scanln` など: 改行はスキャンを終了させる。
*   `Scanf` など: 入力とフォーマット内の改行は一致しなければならない。

しかし、特に `Scanf` において、コードがこの振る舞いをすべての場合で実装していませんでした。このコミットは、以下の変更によってこの振る舞いを修正します。

*   `ss.Advance` におけるスペースと改行の処理を修正。コードは長くなりましたが、期待通りに動作するようになりました。
*   `newScanState` における現在の `ss` の再利用を削除。これは再帰的な `Scan` などの呼び出しでのみ使用され、フラグが誤っている可能性があったため、必要ありませんでした。毎回新しいものを割り当てる方がシンプルで、より正確である可能性が高いです。

Issue #10862 を修正します。

## 変更の背景

Go言語の `fmt` パッケージは、C言語の `printf`/`scanf` に似た書式付き入出力機能を提供します。しかし、C言語の `scanf` とは異なり、Goの `fmt.Scanf` はフォーマット文字列内の改行文字に対して特定の振る舞いを要求するようにドキュメントで規定されていました。具体的には、`Scanf` はフォーマット文字列に改行が含まれている場合、入力ストリームにも対応する改行が存在することを期待していました。

しかし、実際のGoの `fmt` パッケージの実装では、このドキュメントに記載された `Scanf` の改行マッチングルールが常に適用されていませんでした。例えば、`Scanf("%d\n%d", &a, &b)` というフォーマット文字列に対して、入力が `1 2` (改行ではなくスペース) であった場合でも、期待に反してスキャンが成功してしまうことがありました。これは、ユーザーがドキュメントを読んで期待する動作と、実際のプログラムの動作との間に不一致を生じさせ、混乱やバグの原因となっていました。

この不一致は、GoのIssueトラッカーで #10862 として報告されました。このコミットは、この報告された問題を解決し、`fmt` パッケージのドキュメントと実装の整合性を回復することを目的としています。これにより、開発者は `fmt.Scanf` の改行処理について、ドキュメント通りの予測可能な動作を期待できるようになります。

## 前提知識の解説

このコミットを理解するためには、Go言語の `fmt` パッケージにおけるスキャン関数の基本的な動作と、C言語の `scanf` との比較、そして文字エンコーディングに関する知識が役立ちます。

### Go言語の `fmt` パッケージのスキャン関数

Goの `fmt` パッケージには、様々な形式で入力から値を読み取るための関数群があります。これらは主に以下の3つのカテゴリに分けられます。

1.  **`Scan`, `Fscan`, `Sscan`**:
    *   これらはスペース区切りの値を読み取ります。
    *   **改行文字 (`\n`) は通常のスペースとして扱われます。** 複数のスペースやタブ、改行は単一のスペースとして扱われ、トークンの区切りとして機能します。
    *   例: `Sscan("1\n2", &a, &b)` は `a=1, b=2` とスキャンします。

2.  **`Scanln`, `Fscanln`, `Sscanln`**:
    *   これらは行末までスキャンし、**改行文字 (`\n`) またはEOF (End Of File) でスキャンを終了します。**
    *   スキャンされた項目は改行またはEOFで終わる必要があります。
    *   例: `Sscanln("1 2\n", &a, &b)` は `a=1, b=2` とスキャンしますが、`Sscanln("1\n2", &a, &b)` は `a=1` までしかスキャンせず、エラーを返すか、`b` には何も割り当てられません（または部分的なスキャンとして扱われます）。

3.  **`Scanf`, `Fscanf`, `Sscanf`**:
    *   これらはフォーマット文字列に基づいて値を読み取ります。C言語の `scanf` に最も似ています。
    *   **フォーマット文字列内の改行は、入力中の改行と一致する必要があります。**
    *   フォーマット文字列内の非空のスペース文字の連続（改行を除く）は、入力中の単一のスペースに相当します。
    *   **C言語の `scanf` との重要な違い**: C言語の `scanf` は、フォーマット文字列内の改行を単なるスペースとして扱いますが、Goの `Scanf` は改行のマッチングを要求します。
    *   例: `Sscanf("1\n2", "%d\n%d", &a, &b)` は `a=1, b=2` とスキャンします。しかし、`Sscanf("1 2", "%d\n%d", &a, &b)` はフォーマットと入力の改行が一致しないため、エラーとなるか、部分的なスキャンで終了します。

### `ScanState` インターフェースと `ss` 構造体

`fmt` パッケージの内部では、スキャン処理の状態を管理するために `ScanState` インターフェースとそれを実装する `ss` (scan state) 構造体が使用されます。
`ss` 構造体は、入力ストリームからの読み取り、スペースのスキップ、トークンの抽出などの低レベルな操作をカプセル化します。
このコミットでは、`ss.Advance` メソッドが特に重要です。これは、フォーマット文字列と入力ストリームを比較し、一致する部分を進める役割を担います。

### UnicodeとUTF-8

Go言語はUnicodeをネイティブにサポートしており、文字列はUTF-8でエンコードされます。`fmt` パッケージのスキャン関数も、ルーン（Unicodeコードポイント）単位で文字を処理します。`utf8.DecodeRuneInString` のような関数が使用され、マルチバイト文字も正しく扱われます。

### `sync.Pool`

`sync.Pool` は、Goの標準ライブラリで提供される、一時的なオブジェクトを再利用するためのメカニズムです。オブジェクトの割り当てとガベージコレクションのオーバーヘッドを削減し、パフォーマンスを向上させるために使用されます。このコミットでは、`newScanState` 関数で `ss` オブジェクトの再利用に関するロジックが変更されています。

## 技術的詳細

このコミットの技術的な核心は、`fmt` パッケージが `Scanf` ファミリーの関数における改行文字の処理を、ドキュメントに記載された厳密なマッチングルールに準拠させるように変更した点にあります。

### 1. `src/fmt/doc.go` の更新

最も直接的な変更は、`fmt` パッケージのドキュメント (`doc.go`) の更新です。これにより、各スキャン関数の改行処理に関する振る舞いが明確に記述され、以前の曖昧さや誤解の余地が排除されました。

*   `Scan`, `Fscan`, `Sscan` は「入力中の改行をスペースとして扱う」と明記。
*   `Scanln`, `Fscanln`, `Sscanln` は「改行でスキャンを停止し、項目が改行またはEOFで終わることを要求する」と明記。
*   `Scanf`, `Fscanf`, `Sscanf` は「（スペースをスキップした後）フォーマット中の改行が入力中の改行と一致することを要求し、その逆も同様である」と明記。さらに、「この振る舞いはC言語の対応するルーチンとは異なり、Cでは改行を一様にスペースとして扱う」という重要な注意書きが追加されました。

このドキュメントの更新は、コードの変更が意図する新しい（または修正された）振る舞いをユーザーに正確に伝える上で不可欠です。

### 2. `src/fmt/scan.go` の変更

#### `newScanState` 関数の変更

以前の `newScanState` 関数には、入力リーダー `r` が既に `*ss` 型である場合に、既存の `ss` オブジェクトを再利用するロジックが含まれていました。これは、再帰的なスキャン呼び出し（例えば、カスタムスキャナーが内部で別のスキャン関数を呼び出す場合）でパフォーマンスを最適化しようとする試みでした。

しかし、コミットメッセージが指摘するように、この再利用ロジックは「フラグが誤っている可能性が高い」という問題がありました。`ss` オブジェクトには `nlIsSpace` や `nlIsEnd` といった、現在のスキャン操作の改行処理モードを決定するフラグが含まれています。再帰呼び出しでこれらのフラグが正しくリセットまたは設定されない場合、予期しない改行処理のバグを引き起こす可能性がありました。

このコミットでは、この再利用ロジックが完全に削除されました。代わりに、`newScanState` は常に `sync.Pool` から新しい `ss` オブジェクトを取得するか、新しく割り当てて初期化するように変更されました。これにより、コードはよりシンプルになり、フラグの誤った状態によるバグのリスクが排除されました。パフォーマンスへの影響は、`sync.Pool` を使用しているため最小限に抑えられます。

#### `ss.advance` 関数の改行処理の修正

このコミットの最も複雑で重要な変更は、`ss.advance` メソッド内のロジックです。このメソッドは、`Scanf` がフォーマット文字列と入力ストリームを文字ごとに比較し、一致するかどうかを判断する中心的な部分です。

以前の実装では、フォーマット文字列内のスペース（改行を含む）と入力中のスペースの扱いが曖昧で、特に改行のマッチングが不十分でした。修正後の `advance` メソッドは、以下のロジックで改行を厳密に処理します。

1.  **フォーマット中のスペースのスキップと改行の検出**:
    *   `advance` はまず、フォーマット文字列中のスペース文字（`isSpace(fmtc)`）をスキップします。
    *   この際、フォーマット中に改行 (`\n`) があったかどうかを `wasNewline` フラグで記録します。
    *   複数の改行がフォーマット中に連続している場合、最初の改行のみを考慮し、それ以上はスキップを停止します（`if wasNewline { break }`）。これは、フォーマット中の複数の改行が入力中の単一の改行に対応することを意味する可能性があります。

2.  **入力中のスペースと改行のマッチング**:
    *   フォーマット中にスペース（または改行）があった場合 (`sawSpace` が true)、入力ストリームにも対応するスペースが存在することを期待します。
    *   入力から文字 (`inputc`) を読み取ります。
    *   **EOFの処理**: 入力がEOFに達した場合、スキャンを停止します。
    *   **入力中の非スペース文字**: 入力中の文字がスペースでない場合 (`!isSpace(inputc)`)、フォーマット中のスペースと一致しないためエラーとなります。
    *   **入力中のスペースのスキップ**: 入力中のスペース文字をスキップしますが、**改行 (`\n`) に到達したらスキップを停止します** (`for inputc != '\n' && isSpace(inputc)`）。
    *   **改行のマッチングロジック**:
        *   入力中に改行 (`inputc == '\n'`) が見つかった場合:
            *   もしフォーマット中に改行がなかった場合 (`!wasNewline`)、これは「入力中の改行がフォーマットと一致しない」というエラーになります。
            *   入力中の改行が見つかったら、それ以上読み進めずにスキャンを停止します。
        *   入力中に改行が見つからなかったが、フォーマット中に改行があった場合 (`wasNewline` が true で、最終的に `inputc` が改行でなかった場合):
            *   これは「フォーマット中の改行が入力と一致しない」というエラーになります。
    *   `s.UnreadRune()` を使用して、スキップ中に読みすぎた文字を戻すことで、次のスキャンが正しい位置から開始されるようにします。

この詳細なロジックにより、`Scanf` はフォーマット文字列と入力ストリームの改行文字を厳密に比較し、ドキュメントに記載された「改行は一致しなければならない」という要件を満たすようになりました。

### 3. `src/fmt/scan_test.go` の追加

新しいテストケースは、修正された改行処理の振る舞いを検証するために不可欠です。

*   `TestScanNewlinesAreSpaces`: `Sscan` が改行をスペースとして正しく扱うことを確認します。
*   `TestScanlnNewlinesTerminate`: `Sscanln` が改行でスキャンを正しく終了することを確認します。
*   `TestScanfNewlineMatchFormat`: これは最も重要なテストスイートで、`Sscanf` がフォーマットと入力の改行を厳密にマッチングさせることを検証します。
    *   フォーマットと入力の両方に改行がある場合 (`"1\n2"`, `"%d\n%d"`) は成功。
    *   入力に改行があるがフォーマットにない場合 (`"1\n2"`, `"%d %d"`) は部分的なスキャンまたはエラー。
    *   フォーマットに改行があるが入力にない場合 (`"1 2"`, `"%d\n%d"`) も部分的なスキャンまたはエラー。
    *   スペースと改行の組み合わせ (`"1 \n2"`, `"%d \n%d"`) も正しく処理されることを確認。

これらのテストは、修正が意図した通りに機能し、以前のバグが再発しないことを保証します。

## コアとなるコードの解説

### `src/fmt/scan.go` の `ss.advance` 関数における変更点

`ss.advance` 関数は、`Scanf` の動作を決定する上で最も重要な部分です。この関数は、フォーマット文字列の次の部分と入力ストリームの次の部分が一致するかどうかを判断し、一致すれば入力とフォーマットの両方を進めます。

変更前のコードでは、フォーマット文字列中のスペース（改行を含む）と入力中のスペースの扱いが単純化されすぎており、`Scanf` のドキュメントが要求する厳密な改行マッチングが実現できていませんでした。

変更後のコードでは、以下のロジックが導入されました。

```go
// advance determines whether the next characters in the input match
// those of the format. It returns the number of bytes (sic) consumed
// in the format. All runs of space characters in either input or
// format behave as a single space. Newlines are special, though:
// newlines in the format must match those in the input and vice versa.
// This routine also handles the %% case. If the return value is zero,
// either format starts with a % (with no following %) or the input
// is empty. If it is negative, the input did not match the string.
func (s *ss) advance(format string) (i int) {
	for i < len(format) {
		fmtc, w := utf8.DecodeRuneInString(format[i:])
		if fmtc == '%' {
			// ... (%% の処理は省略)
		}
		sawSpace := false
		wasNewline := false // フォーマット中に改行があったかを記録
		// Skip spaces in format but absorb at most one newline.
		for isSpace(fmtc) && i < len(format) {
			if fmtc == '\n' {
				if wasNewline { // 既に改行があった場合、ここで停止
					break
				}
				wasNewline = true // 改行を検出
			}
			sawSpace = true
			i += w
			fmtc, w = utf8.DecodeRuneInString(format[i:])
		}
		if sawSpace {
			// フォーマット中にスペースがあった場合、入力にもスペースがあるべき
			inputc := s.getRune()
			if inputc == eof {
				return // EOFなら終了
			}
			if !isSpace(inputc) {
				// フォーマットにスペースがあるが入力にない場合、エラー
				s.errorString("expected space in input to match format")
			}
			// Skip spaces but stop at newline.
			for inputc != '\n' && isSpace(inputc) { // 入力中のスペースをスキップするが、改行で停止
				inputc = s.getRune()
			}
			if inputc == '\n' {
				if !wasNewline {
					// 入力に改行があるがフォーマットにない場合、エラー
					s.errorString("newline in input does not match format")
				}
				// 改行に到達した場合、それ以上読み進めずに終了
				return
			}
			s.UnreadRune() // 読みすぎた文字を戻す
			if wasNewline {
				// フォーマットに改行があるが入力にない場合、エラー
				s.errorString("newline in format does not match input")
			}
			continue
		}
		// ... (非スペース文字のマッチングロジックは省略)
	}
	return
}
```

この変更のポイントは以下の通りです。

*   **`wasNewline` フラグの導入**: フォーマット文字列を解析する際に、改行文字 (`\n`) が出現したかどうかを `wasNewline` ブール値で追跡します。これにより、フォーマット中の改行の存在を明確に識別できます。
*   **フォーマット中の改行の吸収**: `for isSpace(fmtc) && i < len(format)` ループ内で、フォーマット中のスペースをスキップする際に、改行が一度検出されたらそれ以上はスキップを停止します (`if wasNewline { break }`)。これは、フォーマット中の複数の改行が入力中の単一の改行に対応する可能性を考慮しているためです。
*   **入力中のスペースのスキップと改行の検出**: `inputc := s.getRune()` で入力から文字を読み取り、それがスペースである限りスキップします。しかし、このスキップは改行文字 (`\n`) に到達すると停止します (`for inputc != '\n' && isSpace(inputc)`)。これにより、入力中の改行が特別な意味を持つことが保証されます。
*   **厳密な改行マッチング**:
    *   入力中に改行が見つかった (`inputc == '\n'`) が、フォーマット中に改行がなかった (`!wasNewline`) 場合、`"newline in input does not match format"` というエラーを発生させます。
    *   フォーマット中に改行があった (`wasNewline`) が、入力中に改行が見つからなかった場合、`"newline in format does not match input"` というエラーを発生させます。
*   **`s.UnreadRune()` の使用**: 入力中のスペースをスキップする際に、改行で停止するために読みすぎた文字を `s.UnreadRune()` で戻すことで、次のスキャンが正しい位置から開始されるようにします。

これらの変更により、`ss.advance` は `Scanf` のドキュメントに記載された改行マッチングルールを正確に強制するようになり、以前のバグが修正されました。

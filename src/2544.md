## 変更の背景

Go言語は、その文法の一部として「セミコロン自動挿入（Automatic Semicolon Insertion: ASI）」というメカニズムを持っています。これは、特定の状況下で改行の後に自動的にセミコロンを挿入することで、開発者が明示的にセミコロンを記述する手間を省き、コードの可読性を高めることを目的としています。しかし、このASIには厳密なルールがあり、すべての改行箇所でセミコロンが挿入されるわけではありません。

このコミットが行われた2009年当時、Go言語の初期コンパイラである`6g`（Go 1.5で`gc`に統合される前のコンパイラ）は、Go言語の仕様で許可されていないにもかかわらず、修飾識別子（例: `os.Error`）の後に続く改行でセミコロンの省略を誤って許可していました。これは、Go言語の仕様との不一致であり、コンパイラのバグと見なされました。

このバグにより、仕様に準拠しないコードが`6g`ではコンパイルできてしまうという問題が発生していました。言語の安定性と予測可能性を保証するためには、コンパイラが言語仕様に厳密に従うことが不可欠です。そのため、この誤った挙動を検出し、将来的に修正するためのテストケースが追加されることになりました。

## 前提知識の解説

### Go言語のセミコロン自動挿入 (Automatic Semicolon Insertion: ASI)

Go言語の文法は、C言語系の言語とは異なり、ほとんどの文の終わりに明示的なセミコロンを必要としません。これは、コンパイラが特定のルールに基づいて改行の後に自動的にセミコロンを挿入するためです。このルールは以下の通りです。

1.  識別子（変数名、関数名など）、整数・浮動小数点・文字列リテラル、`break`、`continue`、`fallthrough`、`return`、`++`、`--`、`)`、`]`、`}`のトークンの直後に改行がある場合、その改行の前にセミコロンが挿入されます。
2.  ただし、改行が文を継続するような状況（例: 演算子が改行の直前にある場合）ではセミコロンは挿入されません。

このASIの目的は、コードの記述を簡潔にし、特定のコーディングスタイルを強制することにあります。しかし、そのルールは厳密であり、開発者がASIの挙動を誤解すると、意図しないコンパイルエラーや、逆にコンパイルが通ってしまうバグにつながることがあります。

### 修飾識別子 (Qualified Identifiers)

Go言語において、修飾識別子とは、パッケージ名とそれに続くドット（`.`）、そしてエクスポートされた識別子（変数、関数、型など）を組み合わせたものです。例えば、`os.Error`は`os`パッケージ内の`Error`という識別子を指します。これは、他の言語における名前空間の概念に似ており、異なるパッケージ間で名前の衝突を避けるために使用されます。

このコミットの文脈では、`os.Error`のような修飾識別子の直後に改行が来た場合に、`6g`コンパイラがセミコロンを自動挿入すべきでない場所で挿入してしまっていた、あるいは、本来セミコロンが必要な場所で省略を許可してしまっていた、という問題が指摘されています。

### `6g` コンパイラ

`6g`は、Go言語の初期の開発段階で使用されていたコンパイラの一つです。Go言語は当初、複数のアーキテクチャ（`6`はx86-64、`8`はx86-32、`5`はARMを指す）向けに異なるコンパイラを持っていました。`6g`はx86-64アーキテクチャ向けのGoコンパイラでした。Go 1.5以降、これらのコンパイラは`gc`という単一のコンパイラに統合され、よりモダンな実装に置き換えられました。このコミットは、Go言語の初期の歴史的背景を反映しています。

### Go言語の仕様 (Go Language Specification)

Go言語の挙動を定義する公式文書です。コンパイラやツールは、この仕様に厳密に従って実装される必要があります。このコミットは、`6g`コンパイラがこの仕様の一部（セミコロン自動挿入のルール）に準拠していなかったことを示しています。

## 技術的詳細

このコミットが修正しようとしている問題は、Go言語のセミコロン自動挿入のルールに関する`6g`コンパイラの誤った解釈にあります。Goの仕様では、セミコロンが自動挿入されるのは、特定のトークン（識別子、リテラル、`break`、`continue`、`fallthrough`、`return`、`++`、`--`、`)`、`]`、`}`）の直後に改行がある場合です。

問題のコードは、`var e os.Error` のような修飾識別子の宣言の後に改行が続くケースです。この場合、`os.Error`は識別子であるため、その直後の改行でセミコロンが自動挿入されるのが正しい挙動です。しかし、コミットメッセージによると、`6g`は「修飾識別子の後にセミコロンの省略を許可していた」とあります。これは、`var e os.Error` の後に改行があっても、`6g`がその改行を文の終わりと認識せず、セミコロンを挿入しなかったか、あるいは、本来セミコロンが必要な文脈でその省略を許容してしまっていたことを意味します。

具体的には、`if e == nil {` の行が `var e os.Error` の直後に続く場合、`var e os.Error` の行の終わりにセミコロンが自動挿入されるべきです。もし挿入されなければ、`var e os.Error if e == nil {` のように解釈され、構文エラーとなります。しかし、`6g`はこれをエラーとせず、コンパイルを許可していたようです。

このコミットで追加されたテストケースは、この誤った挙動を意図的に引き起こし、コンパイラがエラーを報告することを期待しています。これにより、コンパイラがGo言語の仕様に厳密に準拠しているかを確認できます。

## コアとなるコードの解説

### `test/bugs/bug166.go` の解説

このファイルは、`6g`コンパイラのセミコロン自動挿入に関するバグをテストするために特別に作成されたGoプログラムです。

*   `// errchk $G $D/$F.go`: これはGoのテストフレームワークで使用される特別なコメントです。`errchk`は、指定されたコマンド（ここでは`$G $D/$F.go`、つまり`6g`コンパイラでこのファイルをコンパイルするコマンド）がエラーを発生させることを期待していることを示します。もしエラーが発生しなければ、テストは失敗します。
*   `package main` と `import "os"`: 標準的なGoプログラムの構造です。`os`パッケージは、`os.Error`型を使用するためにインポートされています。
*   `func fn() { ... }`: テスト対象のコードを含む関数です。
*   `var e os.Error`: ここがテストの核心です。`os.Error`はGoの組み込みエラーインターフェース（Go 1.13で`error`インターフェースに置き換えられましたが、当時は`os.Error`が使われていました）の修飾識別子です。この行の後に改行が続きます。
*   `if e == nil { // ERROR "syntax error|expected ';'" }`: この`if`文は、`var e os.Error`の直後にセミコロンが自動挿入されない場合に構文エラーとなることを期待しています。`// ERROR "syntax error|expected ';'" `というコメントは、この行で`syntax error`または`expected ';'`というエラーメッセージがコンパイラから出力されることを期待していることを示します。

このテストの意図は、`var e os.Error`の行の終わりにセミコロンが自動挿入されるべきであり、もし挿入されなければ、次の`if`文と結合されて不正な構文となるため、コンパイラがエラーを報告するはずだ、というものです。`6g`がこのエラーを報告しなかったため、このテストが追加されました。

### `test/golden.out` の解説

`test/golden.out`ファイルは、Goコンパイラのテストスイートにおいて、特定のテストケースが生成するコンパイラ出力（エラーメッセージなど）の「期待される」内容を記録するために使用されます。コンパイラのテストが実行される際、各テストケースの出力は`golden.out`に記録された内容と比較されます。もし出力が一致しなければ、テストは失敗します。

このコミットでは、`test/golden.out`に以下の行が追加されています。

```
=========== bugs/bug166.go
BUG: errchk: command succeeded unexpectedly:  6g bugs/bug166.go
```

これは、`test/bugs/bug166.go`のテストが、`6g bugs/bug166.go`というコマンドが「予期せず成功した」（つまり、エラーを報告しなかった）ことを`BUG`として記録していることを意味します。これは、このコミットが導入された時点ではまだ`6g`のバグが修正されておらず、テストがそのバグを検出した状態であることを示しています。このテストが追加された後、`6g`コンパイラが修正されれば、この`golden.out`のエントリは削除されるか、期待されるエラーメッセージに更新されることになります。

# [インデックス 24920] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile/internal/gc`）におけるマップリテラルのキー重複排除処理に関するバグ修正です。特に、定数式評価器が特定の「奇妙な」マップリテラルキーに対して失敗する問題に対処し、コンパイラのクラッシュを防ぐための暫定的な修正を導入しています。

## コミット

Author: Keith Randall <khr@golang.org>
Date:   Tue Sep 8 13:41:51 2015 -0700

    cmd/compile/internal/gc: handle weird map literals in key dedup
    
    We compute whether two keys k1 and k2 in a map literal are duplicates by
    constructing the expression OEQ(k1, k2) and calling the constant
    expression evaluator on that expression, then extracting the boolean
    result.
    
    Unfortunately, the constant expression evaluator can fail for various
    reasons.  I'm not really sure why it is dying in the case of 12536, but
    to be safe we should use the result only if we get a constant back (if
    we get a constant back, it must be boolean).  This probably isn't a
    permanent fix, but it should be good enough for 1.5.2.
    
    A permanent fix would be to ensure that the constant expression
    evaluator can always work for map literal keys, and if not the compiler
    should generate an error saying that the key isn't a constant (or isn't
    comparable to some specific other key).
    
    This patch has the effect of allowing the map literal to compile when
    constant eval of the OEQ fails.  If the keys are really equal (which the
    map impl will notice at runtime), one will overwrite the other in the
    resulting map.  Not great, but better than a compiler crash.

## 元コミット内容

Goコンパイラは、マップリテラル内の2つのキー `k1` と `k2` が重複しているかどうかを判断するために、`OEQ(k1, k2)` という式を構築し、その式に対して定数式評価器を呼び出し、ブール結果を抽出します。

しかし、定数式評価器は様々な理由で失敗することがあります。このコミットが対処する問題（Issue 12536）では、評価器が特定のケースで異常終了していました。この修正は、定数式評価器が定数値を返した場合にのみその結果を使用するように変更することで、安全性を確保します。返される値が定数であれば、それは必ずブール値であるはずです。これは恒久的な解決策ではありませんが、Go 1.5.2のリリースには十分な対応とされています。

恒久的な解決策としては、定数式評価器がマップリテラルキーに対して常に機能することを保証するか、それが不可能な場合はコンパイラが「キーが定数ではない」または「特定の他のキーと比較できない」といったエラーを生成すべきです。

このパッチは、`OEQ`の定数評価が失敗した場合でもマップリテラルがコンパイルされるようにします。もしキーが実際に等しい場合（これはランタイムのマップ実装が検出します）、結果のマップでは一方が他方を上書きすることになります。これは理想的ではありませんが、コンパイラのクラッシュよりはましな状況です。

このコミットは Issue 12536 を修正します。

## 変更の背景

Go言語では、マップリテラルを記述する際に、同じキーが複数回指定された場合、コンパイラはそれを検出して警告したり、場合によってはエラーとしたりすることがあります。この重複キーの検出は、コンパイル時に行われる最適化の一環であり、プログラマが意図しないキーの重複を防ぐ目的があります。

このコミット以前のGoコンパイラでは、マップリテラルのキーが重複しているかをチェックするために、内部的に `OEQ` (Operator for Equality、等価演算子) を用いた比較式を生成し、それを定数式評価器 (`evconst`) で評価していました。しかし、特定の「奇妙な」マップリテラルキーの組み合わせにおいて、この定数式評価器が予期せず失敗し、結果としてコンパイラがクラッシュするという問題が発生していました (Issue 12536)。

コンパイラのクラッシュは、開発者にとって非常に深刻な問題であり、開発体験を著しく損ないます。そのため、このクラッシュを回避するための緊急の修正が必要とされました。このコミットは、その緊急対応として、定数式評価器が失敗した場合でもコンパイラがクラッシュしないように、フォールバックメカニズムを導入することを目的としています。

## 前提知識の解説

### Go言語のマップリテラル (Map Literals in Go)

Go言語のマップリテラルは、`map[KeyType]ValueType{key1: value1, key2: value2, ...}` の形式でマップを初期化するための構文です。例えば、`m := map[string]int{"a": 1, "b": 2}` のように使用します。コンパイラは、このリテラルを解析する際に、キーが重複していないかなどの基本的な検証を行います。

### コンパイル時の定数評価 (Constant Expression Evaluation during Compilation)

Goコンパイラは、プログラムの実行前に可能な限り多くの計算をコンパイル時に行おうとします。これを定数評価と呼びます。例えば、`const x = 1 + 2` のような式は、コンパイル時に `x = 3` と評価され、実行時にはすでに計算された値が使用されます。これにより、実行時のパフォーマンスが向上します。マップリテラルのキー重複チェックも、この定数評価の仕組みを利用して行われていました。

### Goコンパイラの内部構造 (`cmd/compile/internal/gc`)

`cmd/compile/internal/gc` は、Go言語の公式コンパイラのバックエンド部分を指します。`gc` は "Go Compiler" の略です。このディレクトリには、字句解析、構文解析、型チェック、中間表現の生成、最適化、コード生成など、コンパイルプロセスの主要な段階を処理するコードが含まれています。`typecheck.go` ファイルは、型チェックフェーズを担当し、式の型が正しいか、変数や関数の使用法が適切かなどを検証します。

### `OEQ` (Operator for Equality)

`OEQ` は、Goコンパイラの内部で等価比較演算子 (`==`) を表すノードタイプです。コンパイラは、ソースコード中の `k1 == k2` のような比較を、内部的な抽象構文木 (AST) 上で `OEQ(k1, k2)` のようなノードとして表現します。

### `OLITERAL` (Node type for literals)

`OLITERAL` は、Goコンパイラの内部でリテラル値（定数）を表すノードタイプです。数値リテラル、文字列リテラル、ブールリテラルなどがこれに該当します。定数式評価器が式を評価し、その結果が定数である場合、その結果は `OLITERAL` ノードとして表現されます。

## 技術的詳細

このコミットの核心は、マップリテラルのキー重複チェックにおける定数式評価器の信頼性の問題に対処することです。

従来のGoコンパイラでは、マップリテラル `map[K]V{k1: v1, k2: v2}` において、`k1` と `k2` が重複しているかを判断するために、以下の手順を踏んでいました。

1.  `k1` と `k2` の等価性をチェックする式、例えば `OEQ(k1, k2)` を内部的に構築します。
2.  この `OEQ` 式を `evconst` 関数（定数式評価器）に渡して評価させます。
3.  `evconst` が返す結果がブール値の定数であれば、その値（`true` または `false`）に基づいてキーが重複しているかを判断します。

しかし、Issue 12536で報告されたように、特定の複雑な、あるいは「奇妙な」マップリテラルキーの場合、`evconst` がこの `OEQ` 式を正しく評価できず、コンパイラがクラッシュしていました。コミットメッセージでは、具体的な失敗原因は不明とされていますが、評価器が予期しない状態に陥っていたと考えられます。

このコミットによる修正は、この問題に対する暫定的な回避策です。変更点を見ると、`evconst(&cmp)` の呼び出し後、その結果を `obj.Bool2int(cmp.Val().U.(bool))` でブール値に変換する前に、`if cmp.Op == OLITERAL` という条件を追加しています。

これは、`evconst` が評価を試みた結果、`cmp` ノードのオペレーション (`cmp.Op`) が `OLITERAL` である場合にのみ、その評価結果（定数ブール値）を信頼して使用するという意味です。もし `cmp.Op` が `OLITERAL` でない場合、それは `evconst` が定数評価に失敗したことを意味します。この場合、以前はクラッシュにつながっていた処理をスキップし、`b` の値（重複フラグ）は初期値の `0` (false) のままとなります。

この修正のトレードオフは、定数評価が失敗した場合、コンパイラはキーが重複していないと「仮定」してコンパイルを続行することです。もし実際にはキーが重複していたとしても、コンパイルは成功します。その場合、ランタイムのマップ実装が重複キーを検出し、後から挿入された値が前の値を上書きするというGo言語のマップの通常の動作に従います。これはコンパイラのクラッシュよりははるかに良い結果ですが、コンパイル時に重複キーを検出して警告するという本来の目的は達成されません。

コミットメッセージにもあるように、これはGo 1.5.2向けの「恒久的な修正ではない」と明記されています。理想的な恒久的な修正は、定数式評価器がマップリテラルキーに対して常に正しく機能するようにするか、あるいは定数評価が不可能なキーに対してはコンパイラが明確なエラーメッセージを出すようにすることです。

## コアとなるコードの解説

変更されたコードブロックは、マップリテラルのキー重複をチェックするロジックの一部です。

1.  `evconst(&cmp)`: ここで、`cmp` ノード（`OEQ` 式を表す）に対して定数式評価器が呼び出されます。この関数は、可能であれば式を定数に評価し、その結果を `cmp` ノードに格納します。
2.  `if cmp.Op == OLITERAL`: この新しい条件文が追加されました。`cmp.Op` は、`cmp` ノードの現在のオペレーション（種類）を示します。
    *   もし `evconst` が成功し、`cmp` ノードが定数ブール値に評価された場合、`cmp.Op` は `OLITERAL` となります。この場合、条件は `true` となり、ブロック内のコードが実行されます。
    *   もし `evconst` が何らかの理由で失敗し、`cmp` ノードが定数に評価されなかった場合、`cmp.Op` は `OLITERAL` 以外の値（例えば、元の `OEQ` のまま）を保持します。この場合、条件は `false` となり、ブロック内のコードはスキップされます。
3.  `b = uint32(obj.Bool2int(cmp.Val().U.(bool)))`: この行は、`cmp` ノードが `OLITERAL` である場合にのみ実行されます。`cmp.Val().U.(bool)` は、定数評価されたブール値を取得し、`obj.Bool2int` はそれを `0` または `1` の `uint32` に変換します。この `b` の値が、キーが重複しているかどうかのフラグとして使用されます。

この変更により、定数式評価器が失敗した場合でも、`b` の値は変更されず（初期値の `0` のまま）、コンパイラはクラッシュすることなく処理を続行できます。これは、定数評価が失敗したケースではキーが重複していないと見なす（または、少なくともコンパイル時に重複を検出できない）という挙動になります。

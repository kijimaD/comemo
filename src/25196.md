# [インデックス 25196] ファイルの概要

このコミットは、Goランタイムにおける`duffcopy`の挙動を修正するものです。具体的には、Plan 9オペレーティングシステム上で`duffcopy`が`MOVUPS`命令を使用することで発生していたビルドエラーを解決するため、Plan 9環境では`duffcopy`の使用を無効化します。

## 変更の背景

この変更の背景には、Goランタイムのパフォーマンス最適化と、特定のオペレーティングシステム（Plan 9）のアーキテクチャ上の制約との間の衝突があります。

以前の変更（CL 14836）では、`amd64`アーキテクチャにおける`duffcopy`の実装が改善されました。この最適化では、従来の`MOVQ`（Move Quadword）命令の代わりに`MOVUPS`（Move Unaligned Packed Single-precision Floating-point）命令が使用されるようになりました。`MOVUPS`はSSE（Streaming SIMD Extensions）命令セットの一部であり、一度に複数のデータ要素を効率的に移動できるため、メモリコピーのパフォーマンス向上に寄与します。

しかし、この`MOVUPS`命令の使用が、`plan9/amd64`環境でのビルドを破壊するという問題を引き起こしました。Plan 9オペレーティングシステムは、その「ノートハンドラ」（Unixにおけるシグナルハンドラに相当）内で浮動小数点演算を許可しないという厳格なポリシーを持っています。`MOVUPS`命令は、たとえ汎用データ転送のために使用されたとしても、Plan 9のカーネルからは浮動小数点演算として認識され、ノートハンドラのコンテキストで実行されると問題が発生しました。

このビルドの破損を修正するため、このコミットではPlan 9環境において`duffcopy`の使用を無効化し、代わりに安全な代替手段にフォールバックさせることで、Plan 9上でのGoのビルドを再び可能にしました。

## 前提知識の解説

### `duffcopy`

`duffcopy`は、Goランタイム内で使用される、メモリブロックを高速にコピーするためのアセンブリルーチンです。これは「Duff's Device」というテクニックに由来しており、ループのオーバーヘッドを削減するためにループアンローリング（ループを展開して、ループ制御の命令を減らすこと）を多用します。これにより、特に大きなメモリブロックのコピーにおいて高いパフォーマンスを発揮します。Goコンパイラは、大きな構造体やスライスのコピーなど、特定のメモリ操作で`duffcopy`を生成して利用します。

### `MOVQ` vs `MOVUPS`

*   **`MOVQ` (Move Quadword)**: x86-64アーキテクチャにおける基本的なデータ転送命令の一つで、64ビット（8バイト）のデータをレジスタ間、またはレジスタとメモリ間で移動させます。汎用的なデータ移動に使用されます。
*   **`MOVUPS` (Move Unaligned Packed Single-precision Floating-point)**: SSE命令セットの一部であり、128ビット（16バイト）のデータを一度に移動させることができます。名前の通り、本来はパックされた単精度浮動小数点数（4つの32ビット浮動小数点数）を扱うための命令ですが、汎用的な16バイトのデータ移動にも利用できます。特に「Unaligned（アラインされていない）」という特性が重要で、メモリ上の任意のアドレスからデータを読み書きできるため、メモリのアラインメントを気にせずに高速なコピーが可能です。

### Plan 9とノートハンドラ

*   **Plan 9**: ベル研究所で開発された分散オペレーティングシステムです。Unixとは異なる独自の設計思想を持ち、すべてのリソースをファイルとして扱うなど、クリーンで一貫性のあるアーキテクチャが特徴です。
*   **ノートハンドラ (Note Handler)**: Plan 9における非同期イベント処理メカニズムで、Unixのシグナルハンドラに似ています。しかし、Plan 9のノートハンドラは、カーネルの安定性と予測可能性を保つために、実行できる操作に厳しい制約があります。特に、ノートハンドラ内で浮動小数点演算を行うことは、CPUの浮動小数点レジスタの状態管理が複雑になるため、許可されていません。

### CL 14836とIssue #12829

*   **CL 14836**: このコミットメッセージで言及されている以前の変更リスト（Change List）です。`amd64`の`duffcopy`実装で`MOVQ`を`MOVUPS`に置き換えた変更を指します。残念ながら、公開されている情報源からはこの特定のCLの詳細を特定できませんでした。
*   **Issue #12829**: このコミットが修正したとされる問題のトラッカー番号です。同様に、Goの公式イシュートラッカーでこの番号の具体的な問題を見つけることはできませんでした。これは、イシュートラッカーの変更、または内部的な問題番号である可能性が考えられます。しかし、コミットメッセージから、この問題が`plan9/amd64`でのビルド失敗に関連していることは明らかです。

## 技術的詳細

このコミットの技術的な核心は、Plan 9のカーネルが`MOVUPS`命令を浮動小数点演算として扱い、ノートハンドラ内でその使用を禁止している点にあります。Goランタイムの`duffcopy`が`MOVUPS`を使用するように変更された結果、Plan 9上でGoプログラムがビルドされる際に、この制約に抵触し、ビルドが失敗するようになりました。

具体的には、`src/cmd/compile/internal/amd64/cgen.go`ファイル内の`blockcopy`関数（メモリコピーを処理する関数）において、特定の条件で`duffcopy`またはそれに類する最適化されたコピーメカニズムが選択されます。以前の実装では、コピーサイズ`q`が128バイトを超える場合、または`gc.Nacl`（Google Native Client）環境で`q`が4バイト以上の場合に、より効率的なコピーパス（おそらく`MOVUPS`を含む`duffcopy`の利用）が選択されていました。

このコミットは、この条件に`(obj.Getgoos() == "plan9" && q >= 4)`という新たな条件を追加します。これにより、オペレーティングシステムがPlan 9であり、かつコピーサイズ`q`が4バイト以上の場合には、`duffcopy`（`MOVUPS`を使用するパス）が意図的に回避されるようになります。代わりに、より汎用的で安全な`REP MOVSQ`命令（繰り返し文字列移動命令）などを用いたコピーメカニズムにフォールバックすることで、Plan 9のノートハンドラの制約に違反することなく、ビルドが成功するようになります。

この変更は、パフォーマンス最適化とOS固有の制約とのバランスを取るための典型的な例であり、クロスプラットフォーム開発における低レベルなアセンブリ最適化の難しさを示しています。

## コアとなるコードの解説

変更された行は、メモリコピーの最適化パスを選択するための条件式です。

元のコード:
`if q > 128 || (gc.Nacl && q >= 4) {`

変更後のコード:
`if q > 128 || (gc.Nacl && q >= 4) || (obj.Getgoos() == "plan9" && q >= 4) {`

この`if`文は、コピーするバイト数`q`に基づいて、どのようなコピー戦略を採用するかを決定します。

*   `q > 128`: コピーサイズが128バイトを超える場合。これは通常、`REP MOVSQ`のような繰り返し命令を用いた効率的なコピーパスを選択するための条件です。
*   `(gc.Nacl && q >= 4)`: Google Native Client (NaCl) 環境で、コピーサイズが4バイト以上の場合。NaClも特定の制約を持つ環境であり、この条件で特別なコピーパスが選択されていました。
*   `(obj.Getgoos() == "plan9" && q >= 4)`: **このコミットで追加された条件です。** オペレーティングシステムがPlan 9であり、かつコピーサイズが4バイト以上の場合に、このブロック内のコードが実行されます。

このブロック内のコードは、`gconreg(movptr, q, x86.REG_CX)`、`gins(x86.AREP, nil, nil)`、`gins(x86.AMOVSQ, nil, nil)`といったアセンブリ命令を生成しています。これは、`REP MOVSQ`命令を使用して`q`バイトのメモリをコピーする一般的な方法です。

コミットメッセージによると、`duffcopy`の`amd64`実装が`MOVUPS`を使用するように変更されたことが問題でした。この`if`文の変更は、Plan 9環境で`q >= 4`の場合に、`MOVUPS`を使用する`duffcopy`のパスを回避し、代わりに`REP MOVSQ`のような安全な代替手段にフォールバックさせることを目的としています。これにより、Plan 9のノートハンドラの制約に違反することなく、ビルドが成功するようになります。

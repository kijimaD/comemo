# [インデックス 25663] ファイルの概要

このコミットは、Goの`net/http`パッケージにおいて、HTTPリクエストのメソッド文字列がRFCに準拠しているかを検証する機能を追加します。具体的には、`http.NewRequest`関数と`http.Transport.RoundTrip`メソッドに、無効なHTTPメソッドが使用された場合にエラーを返すバリデーションロジックが導入されました。これにより、不正なHTTPメソッドがシステム内で処理されることを防ぎ、HTTPプロトコルの厳密な解釈とセキュリティの向上に貢献します。

## 元コミット内容

`net/http`: `NewRequest`と`Transport.RoundTrip`で有効なメソッドを要求する

Issue #12078を修正。

## 変更の背景

この変更は、Goの`net/http`パッケージがHTTPメソッド文字列の検証を適切に行っていなかったという問題（Issue #12078）に対応するために導入されました。以前のバージョンでは、`http.NewRequest`関数に`"GET "`のように末尾にスペースを含むような不正なHTTPメソッド文字列を渡しても、エラーを発生させずにリクエストオブジェクトが作成されてしまうことがありました。

このような不正なメソッド文字列が作成されると、以下のような問題が発生する可能性がありました。

1.  **サーバー間の挙動の不一致**: 一部のHTTPサーバーはこのような不正なメソッドを許容して正常に処理する一方で、他のサーバーは「Bad Request」として拒否するなど、サーバー実装によって挙動が異なりました。これにより、クライアント側で予期せぬ動作やデバッグの困難さが発生していました。
2.  **プロトコル違反**: HTTPプロトコル（RFC 7230など）では、HTTPメソッドは特定の形式（トークン）に従う必要があります。この検証が欠けていると、Goの`net/http`パッケージがプロトコル仕様に厳密に準拠していないことになります。
3.  **潜在的なセキュリティリスク**: 不正な形式のメソッド文字列が処理されることで、HTTPパーサーの脆弱性を突かれたり、意図しないリクエストルーティングが発生したりするなどの潜在的なセキュリティリスクが生じる可能性がありました。

このコミットは、これらの問題を解決し、`net/http`パッケージがより堅牢でプロトコルに準拠した動作をするようにするために行われました。

## 前提知識の解説

### HTTPメソッドとRFC 7230 (またはRFC 2616)

HTTPメソッド（例: GET, POST, PUT, DELETE）は、クライアントがサーバーに対してどのようなアクションを要求するかを示すものです。HTTPプロトコルでは、これらのメソッドは特定の構文規則に従う必要があります。

RFC 7230 (Hypertext Transfer Protocol (HTTP/1.1): Message Syntax and Routing) のセクション 3.1.1 "Request-Line" およびセクション 3.2.6 "Token" では、HTTPメソッドが「トークン (token)」として定義されています。

*   **Method = token**: HTTPメソッドはトークンである。
*   **token = 1\*<any CHAR except CTLs or separators>**: トークンは、制御文字 (CTLs) およびセパレータ以外の任意の文字が1文字以上連続したものである。

ここでいう「制御文字 (CTLs)」とはASCIIコードの0-31（およびDELの127）を指し、「セパレータ (separators)」とは以下の文字を指します:
`(` `)` `<` `>` `@` `,` `;` `:` `\` `"` `/` `[` `]` `?` `=` `{` `}` ` ` (スペース) `\t` (水平タブ)

つまり、HTTPメソッドは、スペースやタブ、括弧などの特殊文字を含んではならない、という厳格なルールがあります。

### Goの`net/http`パッケージ

Goの標準ライブラリである`net/http`パッケージは、HTTPクライアントとサーバーの実装を提供します。

*   **`http.NewRequest(method, urlStr string, body io.Reader) (*Request, error)`**:
    この関数は、指定されたメソッド、URL、およびオプションのボディを持つ新しい`http.Request`オブジェクトを作成します。クライアントがサーバーに送信するリクエストを構築する際に使用されます。
*   **`http.Transport`と`RoundTrip(*Request) (*Response, error)`**:
    `http.Transport`は、HTTPリクエストの実際の送信（ネットワーク接続の確立、リクエストの書き込み、レスポンスの読み取りなど）を処理する構造体です。`RoundTrip`メソッドは、単一のHTTPトランザクションを実行し、リクエストを送信してレスポンスを受け取ります。`http.Client`は内部的に`http.Transport`を使用してリクエストを送信します。

### `io.Reader`と`io.Closer`

*   **`io.Reader`**: データを読み出すためのインターフェース。`Read(p []byte) (n int, err error)`メソッドを持ちます。HTTPリクエストのボディなど、ストリーム形式のデータを扱う際によく使用されます。
*   **`io.Closer`**: リソースを閉じるためのインターフェース。`Close() error`メソッドを持ちます。ファイルやネットワーク接続など、使用後に解放する必要があるリソースに対して実装されます。`http.Request`のボディが`io.Closer`も実装している場合、リクエスト処理後に自動的に閉じられることがあります。

## 技術的詳細

このコミットの主要な技術的変更点は、HTTPメソッド文字列の有効性をチェックする`validMethod`関数の導入と、その関数を`http.NewRequest`および`http.Transport.RoundTrip`に組み込んだことです。

### `validMethod`関数の実装

`validMethod`関数は、与えられた`method`文字列がHTTPプロトコルのトークン規則に準拠しているかをチェックします。

```go
func validMethod(method string) bool {
	/*
	     Method         = "OPTIONS"                ; Section 9.2
	                    | "GET"                    ; Section 9.3
	                    | "HEAD"                   ; Section 9.4
	                    | "POST"                   ; Section 9.5
	                    | "PUT"                    ; Section 9.6
	                    | "DELETE"                 ; Section 9.7
	                    | "TRACE"                  ; Section 9.8
	                    | "CONNECT"                ; Section 9.9
	                    | extension-method
	   extension-method = token
	     token          = 1*<any CHAR except CTLs or separators>
	*/
	return len(method) > 0 && strings.IndexFunc(method, isNotToken) == -1
}
```

*   `len(method) > 0`: メソッド文字列が空でないことを確認します。HTTPメソッドは1文字以上である必要があります。
*   `strings.IndexFunc(method, isNotToken) == -1`:
    *   `strings.IndexFunc`は、指定された文字列`method`内で、`isNotToken`関数が`true`を返す最初の文字のインデックスを返します。そのような文字が見つからない場合は`-1`を返します。
    *   `isNotToken`関数（コミットの差分には直接含まれていませんが、`net/http`パッケージの他の場所で定義されているか、この文脈で暗黙的に参照されていると推測されます）は、文字がHTTPトークンの一部として無効である場合に`true`を返すはずです。つまり、制御文字やセパレータ文字であれば`true`を返します。
    *   したがって、`strings.IndexFunc(method, isNotToken) == -1`は、「メソッド文字列内に無効な文字が一切含まれていない」ことを意味します。

このロジックにより、メソッド文字列がRFCで定義されたトークンの規則に厳密に従っているかどうかが検証されます。

### `NewRequest`への組み込み

`http.NewRequest`関数は、リクエストオブジェクトを作成する初期段階でメソッドの検証を行います。

```go
func NewRequest(method, urlStr string, body io.Reader) (*Request, error) {
	if !validMethod(method) {
		return nil, fmt.Errorf("net/http: invalid method %q", method)
	}
	// ... 既存の処理 ...
}
```

`validMethod(method)`が`false`を返した場合（つまり、メソッドが無効な場合）、`fmt.Errorf`を使用してエラーを返し、リクエストオブジェクトの作成を中止します。これにより、不正なメソッドを持つリクエストがシステム内でこれ以上処理されることを防ぎます。

### `Transport.RoundTrip`への組み込み

`http.Transport.RoundTrip`メソッドは、実際にリクエストを送信する直前にもメソッドの検証を行います。

```go
func (t *Transport) RoundTrip(req *Request) (*Response, error) {
	// ... 既存の処理 ...
	if !validMethod(req.Method) {
		return nil, fmt.Errorf("net/http: invalid method %q", req.Method)
	}
	// ... 既存の処理 ...
}
```

この二重のチェックは重要です。`NewRequest`で検証が行われるにもかかわらず、`RoundTrip`でも再度検証を行うのは、`Request`オブジェクトが作成された後に`req.Method`フィールドが外部から変更される可能性があるためです。例えば、`NewRequest`で有効なメソッドを持つリクエストを作成した後、ユーザーコードが`req.Method = "bad method"`のように変更してしまうケースが考えられます。`RoundTrip`での再検証は、このような変更があった場合でも、不正なメソッドがネットワークに送信されるのを防ぐための最後の防衛線となります。

## コアとなるコードの解説

### `validMethod`関数

```go
func validMethod(method string) bool {
	// ... (RFCのコメント) ...
	return len(method) > 0 && strings.IndexFunc(method, isNotToken) == -1
}
```

この関数は、HTTPメソッド文字列のバリデーションの中核を担います。
`strings.IndexFunc`は、`method`文字列を走査し、各文字に対して`isNotToken`関数を適用します。`isNotToken`は、その文字がHTTPトークンとして許可されない文字（制御文字やセパレータ）である場合に`true`を返します。
もし`strings.IndexFunc`が`-1`を返した場合、それは`method`文字列内に無効な文字が一つも含まれていないことを意味し、`validMethod`は`true`を返します。
また、`len(method) > 0`のチェックにより、空文字列が有効なメソッドとして扱われることを防ぎます。

### `NewRequest`関数での利用

```go
func NewRequest(method, urlStr string, body io.Reader) (*Request, error) {
	if !validMethod(method) {
		return nil, fmt.Errorf("net/http: invalid method %q", method)
	}
	// ...
}
```

`NewRequest`は、リクエストオブジェクトが生成される最初の段階でメソッドの有効性をチェックします。これにより、アプリケーションコードが不正なメソッドを持つリクエストオブジェクトを誤って作成してしまうことを防ぎます。エラーが発生した場合は、`*Request`は`nil`となり、エラー情報が返されます。

### `Transport.RoundTrip`メソッドでの利用

```go
func (t *Transport) RoundTrip(req *Request) (*Response, error) {
	// ...
	if !validMethod(req.Method) {
		return nil, fmt.Errorf("net/http: invalid method %q", req.Method)
	}
	// ...
}
```

`RoundTrip`は、リクエストが実際にネットワークに送信される直前にメソッドの有効性を再チェックします。これは、`NewRequest`でリクエストが作成された後、アプリケーションコードによって`req.Method`フィールドが変更される可能性があるためです。この二重チェックにより、GoのHTTPクライアントが常にRFCに準拠した有効なHTTPメソッドを送信することが保証されます。

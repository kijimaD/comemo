## 変更の背景

このコミットは、Goコンパイラ（`cmd/9g`）がPowerPC 64-bitアーキテクチャ向けに浮動小数点数の比較を行う際に、NaN（Not a Number）値が絡む場合に誤った結果を生成するバグを修正することを目的としています。特に、`x <= y` (less than or equal) や `x >= y` (greater than or equal) のような比較において、オペランドのいずれか、または両方がNaNである場合に、IEEE 754浮動小数点標準の規定に反する動作をしていました。

浮動小数点数の比較は、整数とは異なり、NaNという特殊な値の存在により複雑になります。IEEE 754標準では、NaNとの比較は常に「順序なし（unordered）」とされ、いかなる比較演算子（`<`, `<=`, `>`, `>=`, `==`, `!=`）を用いても、NaNが関与する比較は常に偽（false）を返します（ただし、`NaN != NaN` は真を返します）。

従来のコードでは、`x <= y` のような比較を単一のアセンブラ命令にマッピングしていた可能性があります。しかし、NaNの特性を考慮すると、これは問題を引き起こします。例えば、`NaN <= 5` はIEEE 754では偽となるべきですが、通常の比較命令では異なる結果になる可能性がありました。このバグは、`test/floatcmp.go` のテストが失敗することで顕在化したようです。

## 前提知識の解説

### 浮動小数点数 (Floating-Point Numbers)

浮動小数点数は、実数を近似的に表現するためのコンピュータの数値表現形式です。Go言語を含む多くのプログラミング言語では、IEEE 754標準に準拠した浮動小数点数が使用されます。この標準は、数値の表現方法（符号、指数部、仮数部）だけでなく、特殊な値（ゼロ、無限大、NaN）や演算の振る舞いも定義しています。

### NaN (Not a Number)

NaNは「Not a Number」の略で、浮動小数点演算の結果が未定義または表現不能な場合に生成される特殊な値です。例えば、`0/0`、`無限大 - 無限大`、負の数の平方根などがNaNを生成します。NaNの最も重要な特性は、**いかなる値（NaN自身を含む）と比較しても、常に「順序なし」と判断され、結果が偽（false）になる**という点です。

*   `NaN < X` は `false`
*   `NaN <= X` は `false`
*   `NaN > X` は `false`
*   `NaN >= X` は `false`
*   `NaN == X` は `false`
*   `NaN == NaN` も `false` (これは特に重要で、NaNが自分自身とも等しくないという特性を示します)
*   `NaN != X` は `true` (NaNが関与する唯一の比較で真になる可能性があるのは `!=` です)
*   `NaN != NaN` は `true`

この特性のため、浮動小数点数の比較、特に等価性を含む比較（`<=`, `>=`）は、NaNの存在を考慮して慎重に実装する必要があります。

### Goコンパイラ (cmd/9g)

`cmd/9g` は、Go言語の初期のコンパイラツールチェーンの一部であり、GoのソースコードをPlan 9アセンブラの形式に変換する役割を担っていました。Goのコンパイラは、フロントエンド（構文解析、型チェックなど）とバックエンド（コード生成）に分かれており、`9g` はバックエンドの一部として、特定のCPUアーキテクチャ向けのアセンブラコードを生成していました。このコミットは、PowerPC 64-bit (dev.power64) という特定のアーキテクチャ向けのコード生成ロジックに焦点を当てています。

### PowerPC 64-bit (power64)

PowerPCはIBMが開発したRISCプロセッサアーキテクチャです。`power64` はその64ビット版を指します。Goコンパイラは様々なアーキテクチャをサポートしており、それぞれのアーキテクチャ向けに最適化されたコードを生成するためのバックエンドを持っています。このコミットは、`power64` アーキテクチャにおける浮動小数点比較のコード生成に関する問題に対処しています。

## 技術的詳細

このコミットの核心は、浮動小数点数の比較、特に「より小さいか等しい (`OLE`)」と「より大きいか等しい (`OGE`)」の演算を、NaNのセマンティクスに適合するように修正することです。

IEEE 754標準では、`x <= y` は `x < y || x == y` とは厳密には等価ではありません。なぜなら、NaNが関与する場合、`x < y` も `x == y` も両方とも偽になるため、その論理和も偽になります。しかし、NaNが関与しない通常の数値の場合、この論理は成り立ちます。

従来の `cmd/9g` のコード生成では、`OLE` や `OGE` のような比較を単一のアセンブラ命令にマッピングしようとしていた可能性があります。しかし、このアプローチではNaNの特殊な振る舞いを正しく扱えません。

このコミットでは、`cgen.c` 内の `bgen` 関数が変更されています。`bgen` 関数は、Goの抽象構文木（AST）ノードを受け取り、それに対応するアセンブラコードを生成する役割を担っています。特に、条件分岐（`if`文など）の条件式を評価し、その結果に基づいてジャンプ命令を生成します。

変更のポイントは、浮動小数点数の比較（`isfloat[nr->type->etype]`）で、かつ比較演算子が `OLE` または `OGE` の場合です。この場合、従来の単一命令での比較ではなく、**「より小さい（またはより大きい）」と「等しい」の2つの比較に分解してコードを生成する**ように修正されました。

具体的には、`x <= y` を `(x < y) || (x == y)` のように展開します。
*   まず、`x < y` (または `x > y` for `OGE`) の比較を行い、その結果に基づいて条件分岐命令を生成します。
*   次に、`x == y` の比較を行い、その結果に基づいてさらに条件分岐命令を生成します。

これにより、例えば `NaN <= 5` の場合、`NaN < 5` は偽となり、`NaN == 5` も偽となるため、最終的に `false` という正しい結果が得られます。これは、NaNが関与する比較では、いかなる順序関係も成立しないというIEEE 754の原則に厳密に従った実装となります。

`optoas` 関数は、Goの内部的な演算子コード（`OCMP`, `OLT`, `OGT`, `OEQ` など）を、ターゲットアーキテクチャ（PowerPC 64-bit）のアセンブラ命令に変換します。`gbranch` 関数は、指定された条件に基づいて分岐命令を生成し、`patch` 関数は、生成された分岐命令のジャンプ先アドレスを後から修正するために使用されます。

## コアとなるコードの解説

変更の中心は、`bgen` 関数内の浮動小数点比較を処理する部分です。

1.  **変更前のコメントアウトされたコード**:
    以前のコードには、`// TODO(minux): determine the reason for failed test/floatcmp.go.` というコメントがあり、浮動小数点比較の特殊なハンドリングが必要である可能性が示唆されていました。これは、この問題が以前から認識されていたことを示しています。

2.  **新しい条件分岐 `if(isfloat[nr->type->etype] && (n->op == OLE || n->op == OGE))`**:
    この行が、NaNの正しい比較ロジックを適用するための新しいエントリポイントです。
    *   `isfloat[nr->type->etype]` は、現在処理しているノード `nr` の型が浮動小数点型であるかどうかをチェックします。
    *   `n->op == OLE || n->op == OGE` は、現在の比較演算子が「より小さいか等しい (`OLE`)」または「より大きいか等しい (`OGE`)」であるかどうかをチェックします。
    この条件が真の場合、NaNの特殊な振る舞いを考慮したコード生成パスに入ります。

3.  **`switch(n->op)` ブロック**:
    *   `OLE` の場合、比較演算子 `a` を `OLT` (より小さい) に設定します。
    *   `OGE` の場合、比較演算子 `a` を `OGT` (より大きい) に設定します。
    これは、`x <= y` を `x < y || x == y` に分解する最初のステップです。

4.  **`patch(gbranch(optoas(a, nr->type), nr->type, likely), to);`**:
    この行は、分解された比較の「より小さい」または「より大きい」部分に対応するアセンブラ分岐命令を生成します。
    *   `optoas(a, nr->type)` は、`OLT` または `OGT` に対応するアセンブラ命令コードを取得します。
    *   `gbranch(...)` は、その命令コードに基づいて条件分岐命令を生成します。
    *   `patch(...)` は、この分岐命令のジャンプ先を `to` に設定します。これは、条件が真であった場合にジャンプするターゲットです。

5.  **`patch(gbranch(optoas(OEQ, nr->type), nr->type, likely), to);`**:
    この行が、NaNの比較を正しく扱うための重要な追加です。これは、分解された比較の「等しい」部分 (`x == y`) に対応するアセンブラ分岐命令を生成します。
    *   `optoas(OEQ, nr->type)` は、`OEQ` (等しい) に対応するアセンブラ命令コードを取得します。
    *   これにより、`x <= y` が `(x < y) || (x == y)` として評価されるようになります。
    NaNが関与する場合、`x < y` も `x == y` も偽となるため、両方の分岐が実行されず、最終的に `false` という結果が得られます。通常の数値の場合、どちらかの条件が真であれば、`to` へジャンプします。

6.  **`else` ブロック**:
    浮動小数点数ではない場合、または浮動小数点数であっても `OLE` や `OGE` 以外の比較（例: `OEQ`, `ONE`, `OLT`, `OGT`）の場合は、従来の単一命令での比較ロジックが適用されます。これは、これらの比較演算子ではNaNの特殊なハンドリングが不要であるか、既に別の方法で処理されているためです。

この変更により、GoコンパイラはPowerPC 64-bitアーキテクチャにおいて、IEEE 754標準に準拠したNaNを含む浮動小数点比較を正しく処理できるようになりました。

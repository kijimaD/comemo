# [インデックス 13820] ファイルの概要

このコミットは、Go言語のリンカ（`ld`）に`.gcdata`および`.gcbss`セクションを追加し、ガベージコレクション（GC）に必要な型情報をこれらのセクションに格納するように変更するものです。これにより、Goランタイムが正確なGCを実行するために必要なポインタ情報を効率的に取得できるようになります。

## コミット

リンカに`.gcdata`および`.gcbss`セクションを追加。

## 変更の背景

Go言語のガベージコレクションは、ヒープ上のオブジェクトがポインタを含むかどうか、そしてそのポインタがどこを指しているかを正確に知る必要があります。これは、到達可能なオブジェクトを特定し、不要なオブジェクトを解放するために不可欠です。以前のGoのバージョンでは、この型情報は異なる方法で管理されていましたが、より効率的で正確なGCを実現するために、リンカが生成するバイナリに直接GCに必要なメタデータを含める必要が生じました。

このコミットの主な目的は、Goランタイムが実行時にデータセクション（`.data`）とBSSセクション（`.bss`）内のポインタを正確に識別できるように、リンカがこれらのセクションに関するGCメタデータを生成することです。具体的には、`.gcdata`セクションには初期化されたデータセクション（`.data`）内のポインタに関する情報が、`.gcbss`セクションにはゼロ初期化されたデータセクション（`.bss`）内のポインタに関する情報が格納されます。これにより、GCはこれらのセクションをスキャンする際に、どのメモリ領域がポインタを含み、どのメモリ領域がポインタを含まないかを迅速に判断できるようになります。

また、この変更は、Goの型システムとランタイムの連携を強化し、より堅牢なガベージコレクションメカニズムを構築するための一環でもあります。

## 前提知識の解説

### 1. Go言語のガベージコレクション (GC)

GoのGCは、主にトレース型GCの一種である「マーク＆スイープ」アルゴリズムをベースにしています。GCは、プログラムが使用しているメモリ（ヒープ）を定期的にスキャンし、どのオブジェクトがまだプログラムによって参照されているか（到達可能か）を特定します。到達不可能なオブジェクトは「ガベージ」と見なされ、メモリが解放されます。

正確なGCのためには、GCがメモリ内のどの部分がポインタであり、どの部分がポインタでないかを識別できる必要があります。もしGCが非ポインタデータをポインタとして誤って解釈したり、その逆を行ったりすると、プログラムのクラッシュやメモリリークにつながる可能性があります。

### 2. リンカ (`ld`) とELFセクション

Goのツールチェインにおけるリンカ（`ld`）は、コンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリを生成する役割を担います。リンカは、コード、データ、シンボルテーブルなどの情報を整理し、最終的な実行ファイルの構造を決定します。

ELF (Executable and Linkable Format) は、Unix系システムで広く使用されている実行ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFファイルは複数の「セクション」に分割されており、それぞれが特定の種類のデータを格納します。

*   **`.text`セクション**: 実行可能な機械語コードを格納します。
*   **`.rodata`セクション**: 読み取り専用のデータを格納します（例: 文字列リテラル、定数）。
*   **`.data`セクション**: 初期化されたグローバル変数や静的変数を格納します。プログラムの開始時に値が設定されます。
*   **`.bss`セクション**: 初期化されていないグローバル変数や静的変数を格納します。プログラムの開始時にゼロで初期化されます。
*   **`.gosymtab`**: Goのシンボルテーブル。
*   **`.gopclntab`**: GoのPC-Lineテーブル。スタックトレースやプロファイリングに使用されます。

このコミットでは、新たに`.gcdata`と`.gcbss`というセクションが追加されます。

### 3. `Sym` (シンボル) 構造体

Goリンカの内部では、プログラム内のすべてのエンティティ（関数、変数、型など）が「シンボル」（`Sym`構造体）として表現されます。各シンボルは、その名前、アドレス、サイズ、型、およびその他の属性を持ちます。リンカはこれらのシンボルを操作して、最終的なバイナリを構築します。

### 4. `PtrSize`

`PtrSize`は、システムにおけるポインタのサイズ（バイト単位）を表します。32ビットシステムでは4バイト、64ビットシステムでは8バイトです。Goのランタイムは、このサイズに基づいてメモリを操作します。

### 5. `KindNoPointers` と型情報

Goの型システムは、各型がポインタを含むかどうか、そしてポインタを含む場合にそのポインタがメモリ内のどこに位置するかを追跡します。`KindNoPointers`は、特定の型がポインタを一切含まないことを示すフラグです。GCは、この情報を使用して、ポインタを含まないメモリ領域をスキャンしないことで効率を向上させます。

### 6. `CommonSize`

`CommonSize`は、Goの型情報構造体（`_type`）における共通部分のサイズを表します。Goのすべての型は、`_type`構造体の共通フィールドを持ち、その後に特定の型に応じたフィールドが続きます。`CommonSize`は、これらの共通フィールドの合計サイズを指します。

### 7. `Reloc` (リロケーション)

リロケーションは、リンカがオブジェクトファイルを結合する際に、シンボル参照を実際のメモリアドレスに解決するプロセスです。オブジェクトファイル内のコードやデータは、他のセクションや外部シンボルへの参照を相対アドレスやプレースホルダーとして持っています。リンカはこれらの参照を、最終的な実行ファイル内の絶対アドレスに「リロケート」（再配置）します。`Reloc`構造体は、このリロケーション情報を保持します。

### 8. `inuxi` デコード

`inuxi`は、Goリンカ内でバイトオーダー（エンディアン）を考慮して数値をデコードするためのユーティリティ関数群を指します。異なるアーキテクチャではバイトの並び順が異なるため、リンカはこれを適切に処理する必要があります。`decode_inuxi`関数は、指定されたバイト列から、指定されたサイズ（2, 4, 8バイト）の整数値をデコードします。

## 技術的詳細

このコミットは、Goリンカのデータ処理とセクション管理に大きな変更を加えています。

### 1. 新しいセクションの導入

*   **`.gcdata`**: 初期化されたデータセクション（`.data`）内のポインタに関するGCメタデータを格納します。
*   **`.gcbss`**: ゼロ初期化されたデータセクション（`.bss`）内のポインタに関するGCメタデータを格納します。

これらのセクションは、`src/cmd/ld/data.c`の`dodata`関数内で`addsection`によって追加され、`src/cmd/5l/asm.c`, `src/cmd/6l/asm.c`, `src/cmd/8l/asm.c`といった各アーキテクチャのアセンブラファイルでも、ELFセクション名として追加されています。

### 2. `decodesym.c`の追加と型情報のデコード

`src/cmd/ld/decodesym.c`という新しいファイルが追加されました。このファイルは、Goのランタイム型情報（`type.*`シンボル）をリンカが解釈するためのユーティリティ関数群を提供します。

*   `decode_reloc`、`decode_reloc_sym`: シンボル内のリロケーション情報をデコードし、関連するシンボルを取得します。
*   `decode_inuxi`: バイトオーダーを考慮して数値をデコードします。
*   `decodetype_kind`, `decodetype_size`, `decodetype_gc`: Goの型構造体から、その種類（`kind`）、サイズ、およびGCデータへのポインタをデコードします。
*   `decodetype_arrayelem`, `decodetype_ptrelem`, `decodetype_mapkey`, `decodetype_mapvalue`, `decodetype_chanelem`: 配列、ポインタ、マップ、チャネルなどの複合型の要素型をデコードします。
*   `decodetype_funcdotdotdot`, `decodetype_funcincount`, `decodetype_funcoutcount`, `decodetype_funcintype`, `decodetype_funcouttype`: 関数型の引数と戻り値の情報をデコードします。
*   `decodetype_structfieldcount`, `decodetype_structfieldname`, `decodetype_structfieldtype`, `decodetype_structfieldoffs`: 構造体型のフィールド情報をデコードします。
*   `decodetype_ifacemethodcount`: インターフェース型のメソッド数をデコードします。

これらの関数は、リンカがGoの型情報を理解し、それに基づいてGCメタデータを生成するために不可欠です。

### 3. `dodata`関数の変更

`src/cmd/ld/data.c`の`dodata`関数は、リンカがデータセクションを処理する主要な場所です。このコミットでは、`dodata`関数が大幅に改修され、以下の処理が追加されました。

*   **GCシンボルの定義**: `gcdata1`と`gcbss1`というGC関連のシンボルが定義され、それぞれ`SGCDATA`と`SGCBSS`タイプが割り当てられます。
*   **セクションの再編成**: 以前は`.rodata`、`.gosymtab`、`.gopclntab`が`segtext`（コードセグメント）の一部として処理されていましたが、この変更により、`.gcdata`と`.gcbss`も`segtext`に配置されるようになりました。
*   **GCメタデータの生成**: `gcaddsym`関数が導入され、`.data`および`.bss`セクション内の各シンボルについて、その型情報に基づいてGCメタデータ（ポインタのオフセットなど）を`gcdata1`または`gcbss1`シンボルに追加します。このメタデータは、`GC_CALL`や`GC_APTR`といったGC命令としてエンコードされます。
*   **セクションサイズの更新**: `gcdata1`と`gcbss1`シンボルの先頭に、対応するセクションの実際のサイズが書き込まれます。これは、ランタイムがセクションの終わりを識別するために使用されます。

### 4. `address`関数の変更

`src/cmd/ld/data.c`の`address`関数は、リンカが各セクションとシンボルに最終的なアドレスを割り当てる場所です。このコミットでは、`.gcdata`と`.gcbss`セクションが追加されたことに伴い、これらのセクションのアドレスも適切に定義されるようになりました。また、`xdefine`マクロを使用して、これらのセクションの開始アドレスと終了アドレスがシンボルとしてエクスポートされます（例: `gcdata`, `egcdata`）。

### 5. `lib.h`の変更

`src/cmd/ld/lib.h`には、リンカの内部で使用される型定義、列挙型、関数プロトタイプが含まれています。このコミットでは、新しいシンボルタイプ`SGCDATA`と`SGCBSS`が`enum`に追加され、`decodesym.c`で定義された型デコード関数のプロトタイプが追加されました。また、`adduintxx`関数のシグネチャが変更され、`setuintxx`という新しい関数が導入されました。これは、既存のシンボル内の特定オフセットに値を設定するためのものです。

### 6. `symtab.c`の変更

`src/cmd/ld/symtab.c`の`symtab`関数は、リンカがシンボルテーブルを生成する場所です。このコミットでは、`.gcdata`と`.gcbss`セクションの開始アドレスと終了アドレスを示すシンボル（`gcdata`, `egcdata`, `gcbss`, `egcbss`）が、初期値0で定義されるようになりました。これらの値は、後で`address`関数によって実際の値に更新されます。

## コアとなるコードの解説

### `src/cmd/ld/data.c`における変更

`dodata`関数は、GoバイナリのデータセクションとBSSセクションを構築する中心的な役割を担います。このコミットでは、GCに必要なポインタ情報を効率的に管理するために、この関数が大きく変更されました。

```c
// dodata関数内
// define garbage collection symbols
gcdata1 = lookup("gcdata1", 0);
gcdata1->type = SGCDATA;
gcdata1->reachable = 1;
gcbss1 = lookup("gcbss1", 0);
gcbss1->type = SGCBSS;
gcbss1->reachable = 1;

// size of .data and .bss section. the zero value is later replaced by the actual size of the section.
adduintxx(gcdata1, 0, PtrSize);
adduintxx(gcbss1, 0, PtrSize);
```
ここでは、`gcdata1`と`gcbss1`という2つの新しいシンボルが作成されます。これらはそれぞれ`.gcdata`と`.gcbss`セクションに対応し、GCメタデータを格納するためのコンテナとして機能します。初期値として、それぞれのセクションのサイズを格納するためのプレースホルダー（0）が追加されます。この値は、セクションの構築が完了した後に実際のサイズで上書きされます。

```c
// dodata関数内 (データセクション処理の一部)
for(; s != nil && s->type < SBSS; s = s->next) {
    s->type = SDATA;
    t = alignsymsize(s->size);
    datsize = aligndatsize(datsize, s);
    s->value = datsize;
    gcaddsym(gcdata1, s, datsize - sect->vaddr);  // gc
    datsize += t;
}
sect->len = datsize - sect->vaddr;
datsize = rnd(datsize, PtrSize);

adduintxx(gcdata1, GC_END, PtrSize);
setuintxx(gcdata1, 0, sect->len, PtrSize);
```
この部分は、`.data`セクション内のシンボルを処理し、同時にGCメタデータを生成するロジックを示しています。`gcaddsym`関数が各シンボルに対して呼び出され、そのシンボルがポインタを含むかどうか、そしてポインタのオフセットなどの情報が`gcdata1`シンボルに追加されます。セクションの処理が完了すると、`GC_END`マーカーが追加され、セクションの実際のサイズが`gcdata1`シンボルの先頭に書き込まれます。同様のロジックが`.bss`セクションに対しても`gcbss1`シンボルを使用して適用されます。

### `src/cmd/ld/decodesym.c`における変更

この新規ファイルは、Goの型情報をリンカが理解するための重要な役割を担います。

```c
// src/cmd/ld/decodesym.c
// Type.commonType.kind
uint8
decodetype_kind(Sym *s)
{
    return s->p[3*PtrSize + 7] & ~KindNoPointers;
}

// Type.commonType.size
vlong
decodetype_size(Sym *s)
{
    return decode_inuxi(s->p + 2*PtrSize, PtrSize);
}

// Type.ArrayType.elem and Type.SliceType.Elem
Sym*
decodetype_arrayelem(Sym *s)
{
    return decode_reloc_sym(s, CommonSize);
}
```
これらの関数は、Goのランタイム型情報がメモリ内でどのようにレイアウトされているかを知っている必要があります。例えば、`decodetype_kind`は、`Sym`構造体のデータ（`s->p`）から特定のオフセットにあるバイトを読み取り、型の種類（`kind`）を抽出します。`KindNoPointers`フラグをマスクすることで、ポインタの有無に関する情報も取得します。`decodetype_size`は、型のサイズをデコードし、`decodetype_arrayelem`は配列やスライスの要素型へのリロケーションを解決して、そのシンボルを返します。

これらの関数は、`gcaddsym`関数がGCメタデータを生成する際に、各シンボルの型を正確に解析するために使用されます。

### `src/cmd/ld/lib.h`における変更

```c
// src/cmd/ld/lib.h
enum {
    // ...
    SRODATA,
    SGCDATA, // New
    SGCBSS,  // New
    SSYMTAB,
    SPCLNTAB,
    // ...
};

// ...
void    setuint8(Sym*, vlong, uint8);
void    setuint16(Sym*, vlong, uint16);
void    setuint32(Sym*, vlong, uint32);
void    setuint64(Sym*, vlong, uint64);

// ...
uint8   decodetype_kind(Sym*);
vlong   decodetype_size(Sym*);
Sym*    decodetype_gc(Sym*);
// ... (decodesym.cで定義された他の関数のプロトタイプ)
```
`enum`に`SGCDATA`と`SGCBSS`が追加されたことで、リンカはこれらの新しいセクションタイプを認識し、適切に処理できるようになります。`setuintxx`関数は、既存のシンボルデータ内の特定オフセットに値を書き込むための新しいユーティリティです。これは、特にセクションのサイズを後から更新する際に使用されます。また、`decodesym.c`で定義されたすべての型デコード関数のプロトタイプが追加され、リンカの他の部分からこれらの関数を呼び出せるようになりました。

これらの変更は、Goのガベージコレクションがより効率的かつ正確に動作するために不可欠な基盤を構築しています。リンカが型情報を深く理解し、それに基づいて実行ファイルにGCメタデータを含めることで、Goランタイムはメモリ管理を最適化できます。

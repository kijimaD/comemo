# [インデックス 23273] ファイルの概要

このコミットは、GoランタイムにおけるARMアーキテクチャでのソフトウェア浮動小数点数（FP）演算のエミュレーションに関するバグ修正です。具体的には、`SQRT`命令のエミュレーション時に、`sqrt`関数自体が浮動小数点演算を使用することで、ユーザーのソフトウェアFPレジスタが破壊される問題を解決します。

変更されたファイルは以下の通りです。

*   `src/runtime/export_test.go`: `runtime.Sqrt`関数をテスト可能にするためのエクスポートが追加されました。
*   `src/runtime/softfloat_arm.go`: ARMの`SQRT`命令エミュレーションロジックが修正され、`sqrt`関数への引数と戻り値の型が`float64`から`uint64`（ビット表現）に変更されました。
*   `src/runtime/sqrt.go`: `sqrt`関数が、浮動小数点演算を一切使用せず、純粋な整数演算（ビット操作）のみで平方根を計算するように大幅に修正されました。これにより、エミュレーション中のレジスタ破壊が防止されます。
*   `src/runtime/sqrt_test.go`: `sqrt.go`の変更を検証するための新しいテストファイルが追加されました。`math`パッケージの`Sqrt`テストをコピーし、`runtime.Sqrt`の整数演算実装をテストします。

## 変更の背景

この変更の背景には、ARMアーキテクチャにおける浮動小数点演算の特殊な扱いと、Goランタイムがそれをどのようにエミュレートしているかという問題があります。

一部のARMプロセッサ、特に古いものや組み込みシステム向けのものは、ハードウェアによる浮動小数点演算ユニット（FPU）を持たないか、またはFPUの機能が限定的である場合があります。このような環境では、浮動小数点演算はソフトウェアによってエミュレートされる必要があります。Goランタイムは、このような環境でもGoプログラムが正しく動作するように、必要な浮動小数点演算をソフトウェアで実装しています。

問題は、ARMの`FSQRT`（浮動小数点平方根）命令をソフトウェアでエミュレートする際に発生しました。このエミュレーション処理の中で、平方根を計算する`sqrt`関数が、内部でさらに浮動小数点演算を使用していたのです。これにより、エミュレーション中にユーザープログラムが使用しているソフトウェア浮動小数点レジスタの内容が意図せず上書き（clobber）されてしまう可能性がありました。これは、プログラムの誤動作やクラッシュにつながる深刻なバグです。

コミットメッセージによると、`sqrt`関数が浮動小数点命令を使用していたのは、主にゼロ、NaN（非数）、無限大などの特殊なケース（コーナーケース）をテストするためでした。これらのチェックを純粋な整数演算（ビット操作）に置き換えることで、`sqrt`関数がエミュレーション中にユーザーのレジスタを破壊するリスクを排除することが目的とされました。

## 前提知識の解説

### ARMアーキテクチャと浮動小数点演算

ARMアーキテクチャは、その多様性から、FPUの有無や性能がプロセッサによって大きく異なります。
*   **ハードウェア浮動小数点（Hardware FP）**: FPUが搭載されている場合、浮動小数点演算は非常に高速に実行されます。レジスタは通常、専用の浮動小数点レジスタセットを使用します。
*   **ソフトウェア浮動小数点（Software FP）**: FPUがないか、特定の命令をサポートしない場合、コンパイラやランタイムは浮動小数点演算を整数演算のシーケンスに変換して実行します。この際、通常の整数レジスタを浮動小数点数のビットパターンとして一時的に使用することがあります。この「ソフトウェアFPレジスタ」が、今回の問題の焦点です。

Goランタイムは、ビルドターゲットに応じて、ハードウェアFPUを利用するか、ソフトウェアエミュレーションを行うかを決定します。

### Goランタイムにおける浮動小数点エミュレーション

Goはクロスプラットフォーム言語であり、様々なアーキテクチャで動作します。ARMのような環境でFPUが利用できない場合、Goランタイムは`_sfloat`のような内部関数群を用いて浮動小数点演算をソフトウェアでエミュレートします。このエミュレーションは、ユーザープログラムからは透過的に行われますが、内部的には複雑なビット操作と整数演算の組み合わせで実現されています。

### IEEE 754 浮動小数点標準

浮動小数点数は、IEEE 754標準によって定義されています。この標準は、浮動小数点数の表現形式（符号ビット、指数部、仮数部）と、それらの演算規則を定めています。
*   **NaN (Not a Number)**: 不正な演算結果（例: 0/0, 無限大 - 無限大）を表します。ビットパターンでは、指数部が全て1で、仮数部が0以外の場合にNaNとなります。
*   **Inf (Infinity)**: オーバーフローなどによって発生する無限大を表します。ビットパターンでは、指数部が全て1で、仮数部が全て0の場合に無限大となります。符号ビットで正の無限大と負の無限大が区別されます。
*   **符号ビット**: 数値の正負を表します。
*   **指数部**: 数値の桁の大きさを表します。
*   **仮数部**: 数値の有効数字を表します。

`float64`は64ビットの浮動小数点数で、これらの要素が特定のビット位置に格納されています。

### `float64bits` と `float64frombits`

Goの`math`パッケージには、`Float64bits(f float64) uint64`と`Float64frombits(b uint64) float64`という関数があります。これらは、`float64`型の浮動小数点数と、そのIEEE 754ビット表現である`uint64`型との間で相互変換を行うためのものです。
今回のコミットでは、`runtime`パッケージ内で同様の機能が`unsafe`パッケージを使って直接実装されていましたが、変更後は`sqrt`関数が`uint64`を直接受け取るように変更されたため、これらの変換は`softfloat_arm.go`側で行われるようになりました。これにより、`sqrt`関数内部では浮動小数点型を扱わないという原則が徹底されます。

## 技術的詳細

### `src/runtime/softfloat_arm.go` での `SQRT` 命令エミュレーション

`src/runtime/softfloat_arm.go`は、ARMプロセッサがハードウェアFPUを持たない場合に、浮動小数点命令をソフトウェアでエミュレートするロジックを含んでいます。`case 0xeeb10bc0: // D[regd] = sqrt D[regm]` の部分が、`FSQRT`命令のエミュレーションを担当しています。

変更前は、このエミュレーションコードは以下のようになっていました。
```go
uval = float64bits(sqrt(float64frombits(fgetd(regm))))
fputd(regd, uval)
```
ここで、`fgetd(regm)`はソフトウェアFPレジスタから`uint64`のビットパターンを取得し、`float64frombits`で`float64`に変換して`sqrt`関数に渡していました。`sqrt`関数は`float64`を処理し、結果を`float64`で返し、それを`float64bits`で`uint64`に変換して`fputd(regd, uval)`でソフトウェアFPレジスタに書き戻していました。

この問題は、`sqrt`関数が`float64`型の引数を受け取り、内部で浮動小数点演算を行っていたため、その過程でユーザーのソフトウェアFPレジスタを破壊する可能性があったことです。

変更後は、以下のようになりました。
```go
fputd(regd, sqrt(fgetd(regm)))
```
この変更により、`sqrt`関数は`uint64`型のビットパターンを直接受け取り、`uint64`型のビットパターンを直接返すようになりました。これにより、`sqrt`関数内部では`float64`型を一切扱わず、純粋な整数演算のみで処理が完結するため、ソフトウェアFPレジスタの破壊が回避されます。

### `src/runtime/sqrt.go` の変更

`src/runtime/sqrt.go`は、`math`パッケージの`sqrt.go`のコピーであり、ARMのソフトウェア浮動小数点エミュレーションで使用される平方根計算ロジックを提供していました。

**変更前**:
`sqrt`関数は`float64`型の引数`x`を受け取り、`float64`を返していました。
```go
func float64bits(f float64) uint64     { return *(*uint64)(unsafe.Pointer(&f)) }
func float64frombits(b uint64) float64 { return *(*float64)(unsafe.Pointer(&b)) }

func sqrt(x float64) float64 {
    // special cases
    switch {
    case x == 0 || x != x || x > maxFloat64:
        return x
    case x < 0:
        return nan()
    }
    ix := float64bits(x)
    // ... (rest of the sqrt logic)
    return float64frombits(ix)
}
```
このコードでは、`float64bits`と`float64frombits`を使って`float64`と`uint64`の変換を行っていましたが、`sqrt`関数のシグネチャ自体が`float64`であったため、コンパイラが内部で浮動小数点演算を生成する可能性がありました。特に、`x == 0 || x != x || x > maxFloat64`のような比較演算は、浮動小数点演算として処理される可能性があり、これが問題の原因となっていました。

**変更後**:
`sqrt`関数は`uint64`型の引数`ix`を受け取り、`uint64`を返すように変更されました。
```go
// Modified to not use any floating point arithmetic so
// that we don't clobber any floating-point registers
// while emulating the sqrt instruction.

// ...

// isnanu returns whether ix represents a NaN floating point number.
func isnanu(ix uint64) bool {
    exp := (ix >> float64Shift) & float64Mask
    sig := ix << (64 - float64Shift) >> (64 - float64Shift)
    return exp == float64Mask && sig != 0
}

func sqrt(ix uint64) uint64 {
    // special cases
    switch {
    case ix == 0 || ix == 1<<63: // x == 0 (positive or negative zero)
        return ix
    case isnanu(ix): // x != x (NaN)
        return ix
    case ix&(1<<63) != 0: // x < 0 (negative number)
        return float64NaN
    case ix == float64Inf: // x > MaxFloat (positive infinity)
        return ix
    }
    // ... (rest of the sqrt logic, now operating on uint64)
    return ix
}
```
この変更の核心は、`sqrt`関数が浮動小数点数をそのビット表現である`uint64`としてのみ扱い、すべての計算と条件分岐をビット操作と整数比較で行うようにした点です。
*   `float64bits`と`float64frombits`は削除されました。
*   特殊ケースのチェック（ゼロ、NaN、負の数、無限大）も、`uint64`のビットパターンを直接検査することで行われます。例えば、`isnanu`関数は、`uint64`のビットパターンから指数部と仮数部を抽出し、NaNの条件（指数部が全て1かつ仮数部が0以外）を純粋な整数演算で判定します。
*   負の数のチェック`ix&(1<<63) != 0`は、最上位ビット（符号ビット）が1であるかを検査することで行われます。
*   無限大のチェック`ix == float64Inf`も、定義された無限大のビットパターンと比較することで行われます。

これにより、`sqrt`関数はコンパイラが浮動小数点命令を生成する余地をなくし、完全に整数演算のみで動作するようになりました。

### `//go:nosfloat` コメントの提案

コミットメッセージでは、「`//go:nosfloat` を追加して、コンパイラにこれを強制させるべきか？」という提案がされています。これは、特定の関数が浮動小数点演算を使用しないことをコンパイラに指示するようなディレクティブ（プラグマ）のアイデアです。もしこのようなディレクティブがあれば、コンパイラは浮動小数点命令が誤って生成されていないかをチェックし、開発者が意図しない浮動小数点演算の混入を防ぐことができます。このコミット時点では提案に留まっていますが、将来的にGoコンパイラに同様の機能が追加される可能性を示唆しています。

## コアとなるコードの解説

`src/runtime/sqrt.go`の変更がこのコミットの核心です。

1.  **`unsafe`パッケージと変換関数の削除**:
    以前は`unsafe.Pointer`を使って`float64`と`uint64`の間でビットパターンを直接やり取りしていましたが、`sqrt`関数が`uint64`を直接扱うようになったため、これらの低レベルな変換は不要になりました。これにより、コードの意図がより明確になり、潜在的な`unsafe`の使用による問題も回避されます。

2.  **`float64NaN`と`float64Inf`定数の導入**:
    IEEE 754標準で定義されているNaNと無限大のビットパターンを`uint64`として直接定数化しました。これにより、特殊ケースの処理でこれらの値を返す際に、浮動小数点演算を介さずに直接ビットパターンを返すことができます。

3.  **`isnanu`関数の導入**:
    ```go
    func isnanu(ix uint64) bool {
        exp := (ix >> float64Shift) & float64Mask
        sig := ix << (64 - float64Shift) >> (64 - float64Shift)
        return exp == float64Mask && sig != 0
    }
    ```
    この関数は、与えられた`uint64`のビットパターン`ix`がNaNを表しているかどうかを判定します。
    *   `float64Shift`は仮数部のビット数と符号ビットを除いた指数部の開始位置を示します。
    *   `float64Mask`は指数部のビットマスクです。
    *   `exp`は`ix`から指数部を抽出します。
    *   `sig`は`ix`から仮数部を抽出します。
    *   IEEE 754では、指数部が全て1（`float64Mask`の値）で、かつ仮数部が0以外の場合にNaNと判定されます。このロジックは純粋なビットシフトとビットマスク、整数比較のみで構成されており、浮動小数点演算は一切使用していません。

4.  **`sqrt`関数のシグネチャと特殊ケース処理の変更**:
    ```go
    func sqrt(ix uint64) uint64 {
        // special cases
        switch {
        case ix == 0 || ix == 1<<63: // x == 0 (positive or negative zero)
            return ix
        case isnanu(ix): // x != x (NaN)
            return ix
        case ix&(1<<63) != 0: // x < 0 (negative number)
            return float64NaN
        case ix == float64Inf: // x > MaxFloat (positive infinity)
            return ix
        }
        // ... (rest of the sqrt logic)
        return ix
    }
    ```
    *   引数と戻り値が`uint64`になったことで、関数全体がビットパターンレベルで動作することが保証されます。
    *   `ix == 0 || ix == 1<<63`: 正のゼロ（全てのビットが0）または負のゼロ（符号ビットのみ1）の場合をチェックします。これらの場合、平方根は元の値と同じです。
    *   `isnanu(ix)`: 上記で定義された`isnanu`関数を使ってNaNを判定します。NaNの平方根はNaNです。
    *   `ix&(1<<63) != 0`: `1<<63`は`uint64`の最上位ビット（符号ビット）が1であるビットパターンです。この条件は、入力が負の数であるかをチェックします。負の数の平方根はNaNであるため、`float64NaN`を返します。
    *   `ix == float64Inf`: 入力が正の無限大であるかをチェックします。正の無限大の平方根は正の無限大です。

これらの変更により、`sqrt`関数は完全に浮動小数点演算から切り離され、`uint64`のビットパターンに対する純粋な整数演算として機能するようになりました。これにより、ARMのソフトウェア浮動小数点エミュレーション中にユーザーのFPレジスタが破壊される問題が根本的に解決されました。

# [インデックス 26578] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおける最適化ルール、特に汎用的な書き換えルールセットに、さらなる簡素化と正規化のロジックを追加するものです。これにより、コンパイラが生成する中間コードの品質が向上し、結果として実行効率の高いバイナリが生成されることが期待されます。

## 元コミット内容

このコミットは、GoコンパイラのSSAバックエンドにおいて、より多くの簡素化と正規化のルールを追加します。これらのルールは、ランダムに生成されたコードを検査する過程で発見された最適化の機会に基づいています。具体的には、`generic.rules`ファイルに新しい書き換えルールが追加され、それに対応するGoコードが`rewritegeneric.go`に自動生成されています。

## 変更の背景

Goコンパイラは、プログラムのソースコードを機械語に変換する過程で、中間表現（IR: Intermediate Representation）を使用します。Go 1.7から導入されたSSA (Static Single Assignment) 形式は、このIRの一種であり、より高度な最適化を可能にします。SSA形式では、各変数が一度だけ代入されるという特性を持つため、データフロー解析や最適化が容易になります。

このコミットの背景には、SSAバックエンドの成熟と、さらなる最適化の追求があります。コンパイラの最適化フェーズでは、コードのパターンを認識し、より効率的な等価なコードに置き換える「書き換えルール（rewrite rules）」が多数適用されます。これらのルールは、定数伝播、共通部分式除去、不要なコードの削除など、様々な最適化を実現します。

コミットメッセージにある「Found by inspecting random generated code.」という記述は、コンパイラが生成するSSAコードを分析し、まだ最適化されていない、あるいはより効率的に表現できるパターンを発見したことを示唆しています。このようなパターンを特定し、それらを簡素化または正規化する新しいルールを追加することで、コンパイラの最適化能力を継続的に向上させることが目的です。特に、定数を含む演算の正規化や、自明な演算の除去は、コードの冗長性を減らし、後続の最適化フェーズでの処理を容易にします。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

### 1. GoコンパイラとSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを抽象構文木 (AST) に変換し、その後、中間表現であるSSA形式に変換します。SSA形式は、各変数がプログラム内で一度だけ定義されるという特性を持つ中間表現です。これにより、データフロー解析が単純化され、以下のような高度な最適化が容易になります。
*   **定数伝播 (Constant Propagation)**: 定数値を伝播させ、定数式を事前に計算する。
*   **共通部分式除去 (Common Subexpression Elimination, CSE)**: 同じ計算が複数回行われている場合、一度だけ計算して結果を再利用する。
*   **デッドコード除去 (Dead Code Elimination, DCE)**: 決して実行されない、またはその結果が使用されないコードを削除する。

### 2. SSA書き換えルール (Rewrite Rules)

GoコンパイラのSSAバックエンドでは、`src/cmd/compile/internal/ssa/gen/generic.rules`のような`.rules`ファイルに定義された書き換えルールに基づいて、SSA形式のコードを最適化します。これらのルールは、特定のSSA操作のパターンを検出し、より効率的な別のSSA操作のパターンに変換します。

例えば、`(Add64 (Const64 [0]) x) -> x` というルールは、「64ビットの定数0と変数xの加算は、変数xそのものに置き換えられる」という最適化を示します。これは、加算の単位元（identity element）の特性を利用した簡素化です。

`.rules`ファイルは、Goのテンプレートエンジンに似た構文で記述されており、`go generate`コマンドによって`rewritegeneric.go`のようなGoのソースコードに変換されます。この生成されたGoコードが、実際にコンパイラ内でSSA値を書き換えるロジックを実装しています。

### 3. 演算の正規化 (Canonicalization)

正規化とは、複数の等価な表現を持つ式を、常に一貫した「標準形」に変換するプロセスです。例えば、加算や乗算のような交換法則が成り立つ（可換な）演算では、`A + B` と `B + A` は数学的に同じですが、コンパイラにとっては異なるパターンとして認識される可能性があります。

正規化ルールは、このような可換演算において、例えば定数を常に左オペランドに配置する（例: `x + Const` を `Const + x` に変換する）といった規則を設けることで、コンパイラがより少ないルールでより多くの最適化パターンを認識できるようにします。これにより、ルールの記述が簡素化され、最適化の網羅性が向上します。

### 4. `Value`と`Op`

GoコンパイラのSSA形式では、プログラム内の各計算結果が`Value`オブジェクトとして表現されます。各`Value`は、その操作の種類（`Op`）、型、引数（他の`Value`オブジェクト）、および補助情報（定数値など）を持ちます。書き換えルールは、これらの`Value`オブジェクトのパターンをマッチングし、新しい`Value`オブジェクトのグラフに変換することで最適化を行います。

## 技術的詳細

このコミットは、主に`src/cmd/compile/internal/ssa/gen/generic.rules`ファイルに新しい書き換えルールを追加することで、GoコンパイラのSSA最適化パスを強化しています。これらのルールは、特定の演算パターンをより効率的な形式に変換することを目的としています。

追加された主要なルールは以下のカテゴリに分類できます。

### 1. 可換演算の正規化 (Canonicalization of Commutative Operations)

既存の`Eq` (等価比較) や `Add` (加算) 演算と同様に、`Mul` (乗算)、`And` (ビット論理積)、`Or` (ビット論理和)、`Xor` (ビット排他的論理和) といった可換演算に対しても、定数オペランドを常に左側に配置する正規化ルールが追加されました。

**例:**
*   `(Mul64 x (Const64 <t> [c])) && x.Op != OpConst64 -> (Mul64 (Const64 <t> [c]) x)`
    *   これは、「64ビットの乗算で、右オペランドが定数であり、左オペランドが定数でない場合、定数を左オペランドに移動する」というルールです。
    *   同様のルールが`Mul32`, `Mul16`, `Mul8`, `And64`から`And8`, `Or64`から`Or8`, `Xor64`から`Xor8`に対して追加されています。

この正規化により、コンパイラは定数を含む可換演算を常に一貫した形式で扱うことができ、後続の最適化ルールがより少ないパターンで効果的に適用できるようになります。

### 2. シフト演算の簡素化 (Simplification of Shift Operations)

定数0をシフトする操作や、非常に大きなシフト量を持つ操作に対する簡素化ルールが追加されました。

**例:**
*   `(Lsh64x64 (Const64 [0]) _) -> (Const64 [0])`
    *   「64ビットの定数0を任意の量だけ左シフトする操作は、常に定数0になる」というルールです。
    *   同様のルールが、`Lsh` (左シフト) および `Rsh` (右シフト) の様々なビット幅 (`64x64`, `64x32`, `64x16`, `64x8`) と符号付き/符号なしバージョン (`Rsh64Ux64`など) に対して追加されています。

*   `(Lsh64x64 _ (Const64 [c])) && uint64(c) >= 64 -> (Const64 [0])`
    *   「64ビット値を64ビット以上左シフトする操作は、常に定数0になる」というルールです。これは、64ビットレジスタの範囲を超えるシフトは結果を0にするというハードウェアの特性に基づいています。
    *   同様に、符号なし右シフト (`Rsh64Ux64`) に対しても、64ビット以上シフトすると0になるルールが追加されています。

### 3. ビット演算と算術演算の恒等式・吸収律 (Identity and Absorption Laws for Bitwise and Arithmetic Operations)

ビット演算 (`And`, `Or`, `Xor`) および算術演算 (`Add`, `Mul`) における、定数0や定数-1（全ビットが1）との自明な操作に対する簡素化ルールが多数追加されました。

**例:**
*   `(Or64 (Const64 [0]) x) -> x`
    *   「64ビット値と定数0のビット論理和は、その64ビット値自身になる」という恒等律です。
    *   同様のルールが`Or32`, `Or16`, `Or8`, `Add64`から`Add8`, `Xor64`から`Xor8`に対して追加されています。

*   `(Or64 (Const64 [-1]) _) -> (Const64 [-1])`
    *   「64ビット値と定数-1（全ビット1）のビット論理和は、常に定数-1になる」という吸収律です。
    *   同様のルールが`Or32`, `Or16`, `Or8`に対して追加されています。

*   `(And64 (Const64 [-1]) x) -> x`
    *   「64ビット値と定数-1のビット論理積は、その64ビット値自身になる」という恒等律です。
    *   同様のルールが`And32`, `And16`, `And8`に対して追加されています。

*   `(And64 (Const64 [0]) _) -> (Const64 [0])`
    *   「64ビット値と定数0のビット論理積は、常に定数0になる」という吸収律です。
    *   同様のルールが`And32`, `And16`, `And8`, `Mul64`から`Mul8`に対して追加されています。

### 4. 減算の否定の簡素化 (Simplification of Negation of Subtraction)

減算の否定をより単純な減算に変換するルールが追加されました。

**例:**
*   `(Neg8 (Sub8 x y)) -> (Sub8 y x)`
    *   「8ビット値の `-(x - y)` は `y - x` に等しい」というルールです。
    *   同様のルールが`Neg16`, `Neg32`, `Neg64`に対して追加されています。

これらのルールは、コンパイラが生成するSSAコードをよりコンパクトで効率的な形式に変換し、後続のコード生成フェーズでの処理を簡素化し、最終的なバイナリの性能向上に貢献します。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下の2つのファイルに集中しています。

1.  **`src/cmd/compile/internal/ssa/gen/generic.rules`**:
    *   このファイルは、GoコンパイラのSSAバックエンドで使用される汎用的な書き換えルールを定義しています。
    *   変更点としては、可換演算（`Mul`, `And`, `Or`, `Xor`）における定数オペランドの正規化ルール、定数0のシフト演算の簡素化ルール、ビット演算および算術演算における恒等式・吸収律に基づく簡素化ルール、そして減算の否定の簡素化ルールが追加されています。
    *   具体的には、約20行の新しいルールが追加され、既存のコメントが修正されています。

2.  **`src/cmd/compile/internal/ssa/rewritegeneric.go`**:
    *   このファイルは、`generic.rules`ファイルから`go generate`コマンドによって自動生成されるGoのソースコードです。
    *   `generic.rules`に追加された新しい書き換えルールに対応するため、このファイルには大幅な変更が加えられています。具体的には、1064行の追加と29行の削除があり、これは新しい最適化ロジックを実装する多数の`rewriteValuegeneric_Op*`関数内の`match`および`result`ブロックの追加を意味します。
    *   例えば、`rewriteValuegeneric_OpAdd16`関数には`(Add16 (Const16 [0]) x)`を`x`に書き換える新しいロジックが追加されています。同様に、`rewriteValuegeneric_OpAnd16`関数には、定数オペランドの正規化や、`(And16 (Const16 [-1]) x)`を`x`に、`(And16 (Const16 [0]) _)`を`(Const16 [0])`に書き換えるロジックが追加されています。
    *   これらの変更は、`generic.rules`で定義された抽象的なルールを、Goコンパイラが実際に実行できる具体的なコードに変換した結果です。

## コアとなるコードの解説

`generic.rules`ファイルは、GoコンパイラのSSA最適化の「設計図」のようなものです。このファイルに記述された各行は、特定のSSA操作のパターン（`match`）と、それを置き換えるべきより効率的なパターン（`result`）を定義しています。

例えば、`generic.rules`に追加された以下の行を見てみましょう。

```
(Mul64 x (Const64 <t> [c])) && x.Op != OpConst64 -> (Mul64 (Const64 <t> [c]) x)
```

このルールは次のように解釈されます。
*   `Mul64`: 64ビットの乗算操作。
*   `x`: 任意のSSA値（左オペランド）。
*   `(Const64 <t> [c])`: 型`t`と定数値`c`を持つ64ビットの定数（右オペランド）。
*   `&& x.Op != OpConst64`: 条件として、左オペランド`x`が定数ではないこと。
*   `->`: このパターンがマッチした場合、以下のパターンに書き換える。
*   `(Mul64 (Const64 <t> [c]) x)`: 定数を左オペランドに、非定数を右オペランドに配置した64ビットの乗算操作。

このルールが`go generate`によって処理されると、`rewritegeneric.go`ファイル内の`rewriteValuegeneric_OpMul64`関数に、このルールを実装するGoコードが生成されます。生成されるコードは、SSA値`v`が`OpMul64`である場合に、その引数を検査し、条件が満たされれば`v`を新しい構造にリセットして引数を再配置するロジックを含みます。

```go
// rewriteValuegeneric_OpMul64
// ...
// match: (Mul64 x (Const64 <t> [c]))
// cond: x.Op != OpConst64
// result: (Mul64 (Const64 <t> [c]) x)
for {
	x := v.Args[0]
	if v.Args[1].Op != OpConst64 {
		break
	}
	t := v.Args[1].Type
	c := v.Args[1].AuxInt
	if !(x.Op != OpConst64) {
		break
	}
	v.reset(OpMul64)
	v0 := b.NewValue0(v.Line, OpConst64, t) // 新しい定数Valueを作成
	v0.AuxInt = c
	v.AddArg(v0) // 定数を左オペランドに追加
	v.AddArg(x)  // 非定数を右オペランドに追加
	return true
}
// ...
```

このように、`.rules`ファイルは高レベルな最適化パターンを記述し、`rewritegeneric.go`はそれをコンパイラが実行可能な低レベルなGoコードに変換する役割を担っています。このコミットは、これらのルールセットを拡張することで、Goコンパイラの最適化能力を向上させています。

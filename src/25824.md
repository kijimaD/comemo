# [インデックス 25824] ファイルの概要

このコミットは、Goランタイムのシグナルハンドラにおいて、ライトバリアが再帰的に無効化されるように修正するものです。具体的には、`//go:nowritebarrier` ディレクティブを `//go:nowritebarrierrec` に変更することで、シグナルハンドラ関数だけでなく、その関数が呼び出す全ての関数に対してもライトバリアの挿入を禁止します。これは、シグナルハンドラがStop-The-World (STW) フェーズ中に実行される可能性があり、その際にライトバリアが動作するとランタイムの整合性を損なう恐れがあるためです。

## 変更の背景

Goランタイムのガベージコレクション (GC) は、プログラムの実行中に不要になったメモリを自動的に解放する重要な機能です。このGCプロセスの一部として、Stop-The-World (STW) フェーズが存在します。STWフェーズ中、Goプログラムの全てのゴルーチンは一時的に停止され、GCが安全にメモリの状態を検査・変更できるようになります。

シグナルハンドラは、オペレーティングシステムからのシグナル（例えば、セグメンテーション違反やタイマー割り込みなど）を受け取った際に非同期に実行される特殊な関数です。これらのシグナルハンドラは、GoランタイムのSTWフェーズ中であっても、予期せぬタイミングで実行される可能性があります。

GoのGCは、ポインタの書き込みを監視するために「ライトバリア (Write Barrier)」というメカニズムを使用します。ライトバリアは、ヒープ上のポインタが変更される際に特定のコードを実行し、GCがオブジェクトグラフの整合性を維持できるようにします。しかし、STWフェーズ中にライトバリアが実行されると、GCの内部状態が不安定になったり、デッドロックが発生したりする可能性があります。これは、STW中はGCがメモリの状態を固定しているため、ライトバリアによる変更が許されないためです。

以前は `//go:nowritebarrier` ディレクティブが使用されていましたが、これは `sighandler` 関数自体にのみライトバリアの挿入を禁止するものでした。しかし、`sighandler` 関数が内部で他の関数を呼び出す場合、その呼び出された関数にはライトバリアが挿入されてしまう可能性がありました。STW中に `sighandler` が実行され、その中でライトバリアを持つ関数が呼び出されると、上述のランタイムの整合性問題が発生する恐れがありました。

このコミットは、この潜在的な問題を解決するために、`sighandler` およびその呼び出しチェーン全体でライトバリアを確実に無効化する `//go:nowritebarrierrec` ディレクティブを導入しました。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、並行・世代別・三色マーキング方式を採用しています。主なフェーズは以下の通りです。

1.  **マークフェーズ (Mark Phase)**: ルート（スタック、グローバル変数など）から到達可能なオブジェクトをマークします。GoのGCは並行マークを採用しており、ほとんどの作業はアプリケーションのゴルーチンと並行して実行されます。
2.  **マーク終了フェーズ (Mark Termination Phase)**: 短いSTWフェーズ。並行マーク中に発生した変更を処理し、マークフェーズを完了させます。
3.  **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不能なオブジェクト）を解放し、メモリを再利用可能にします。これも並行して行われます。

### ライトバリア (Write Barrier)

ライトバリアは、GCが正しく動作するために、ポインタの書き込み操作を監視・介入するメカニズムです。GoのGCは三色マーキングアルゴリズムを使用しており、オブジェクトを白、灰色、黒のいずれかの色で分類します。

*   **白**: まだGCによって到達可能かチェックされていないオブジェクト。または到達不能と判断されたオブジェクト。
*   **灰色**: 到達可能とマークされたが、その子オブジェクトがまだチェックされていないオブジェクト。
*   **黒**: 到達可能とマークされ、その全ての子オブジェクトもチェック済みのオブジェクト。

ライトバリアは、黒のオブジェクトから白のオブジェクトへのポインタの書き込み（変更）が発生した場合に発動し、白のオブジェクトを灰色にマークし直すことで、GCが誤って生きているオブジェクトを回収してしまうことを防ぎます（Dijkstraの三色マーキングアルゴリズムにおける「強力な三色不変条件」を維持するため）。

### Stop-The-World (STW)

STWは、ガベージコレクタが正確なメモリ状態を確保するために、アプリケーションの全てのゴルーチンを一時的に停止させる期間を指します。GoのGCはSTWの時間を最小限に抑えるように設計されていますが、マーク終了フェーズなど、一部のクリティカルな処理ではSTWが不可欠です。STW中は、GCがメモリの状態を自由に操作できるため、アプリケーションのゴルーチンによるメモリの変更は厳しく制限されます。

### シグナルハンドラ (Signal Handler)

シグナルハンドラは、OSがプロセスに送信するシグナル（例: `SIGSEGV` (セグメンテーション違反)、`SIGINT` (割り込み)、`SIGTERM` (終了要求) など）を処理するために登録される関数です。シグナルは非同期に発生し、プログラムの任意の時点で実行中のコードを中断してシグナルハンドラを呼び出すことができます。シグナルハンドラ内では、実行コンテキストが非常に限定されており、通常のアプリケーションコードと同じように振る舞うことはできません。特に、メモリ割り当てやロックの取得など、ランタイムの複雑な機能を使用することは危険とされています。

### `//go:nowritebarrier` と `//go:nowritebarrierrec`

これらはGoコンパイラに対するディレクティブ（指示）です。

*   **`//go:nowritebarrier`**: このディレクティブが付与された関数に対して、コンパイラはライトバリアのコードを挿入しません。つまり、その関数内でポインタの書き込みが行われても、GCのライトバリア処理は実行されません。
*   **`//go:nowritebarrierrec`**: このディレクティブは `//go:nowritebarrier` の再帰版です。このディレクティブが付与された関数だけでなく、その関数が直接的または間接的に呼び出す全ての関数に対しても、ライトバリアの挿入を禁止します。これは、特定のコードパス全体でライトバリアを確実に無効化したい場合に非常に重要です。

## 技術的詳細

Goランタイムのシグナルハンドラ (`sighandler`) は、非常に特殊な環境で実行されます。特に重要なのは、STWフェーズ中に実行される可能性があるという点です。STW中は、GoのGCがメモリの状態を固定し、オブジェクトグラフの整合性を確保しようとします。この期間中に、もしシグナルハンドラ内でライトバリアが実行されてしまうと、以下のような深刻な問題が発生する可能性があります。

1.  **GCの整合性破壊**: ライトバリアはGCの内部状態（例えば、オブジェクトの色付け）を変更する可能性があります。STW中にGCがその内部状態を固定しているにもかかわらず、ライトバリアがそれを変更しようとすると、GCのアルゴリズムが破壊され、メモリリークやクラッシュにつながる可能性があります。
2.  **デッドロック**: ライトバリアの処理は、GCが使用する内部ロックを必要とすることがあります。STW中はGC自身がこれらのロックを保持している可能性があり、シグナルハンドラ内のライトバリアが同じロックを取得しようとすると、デッドロックが発生し、プログラムがハングアップする可能性があります。
3.  **未定義の動作**: シグナルハンドラは非同期に、かつ非常に限定されたスタック空間で実行されるため、通常のGoコードが期待するランタイムのサービス（スケジューラ、メモリ割り当てなど）が利用できない場合があります。ライトバリアがこれらのサービスに依存している場合、未定義の動作を引き起こす可能性があります。

以前の `//go:nowritebarrier` ディレクティブは、`sighandler` 関数自体にはライトバリアを挿入しないようにしていました。しかし、`sighandler` の実装は複雑であり、内部で他のヘルパー関数を呼び出すことが一般的です。これらのヘルパー関数には `//go:nowritebarrier` ディレクティブが適用されないため、それらの関数内でポインタの書き込みが発生した場合、ライトバリアが挿入されてしまいます。

このコミットは、この問題を認識し、`//go:nowritebarrierrec` ディレクティブを導入することで解決しました。`//go:nowritebarrierrec` は、`sighandler` 関数とその関数が呼び出す全ての関数（再帰的に）に対してライトバリアの挿入を禁止します。これにより、STW中に `sighandler` が実行されたとしても、その実行パス全体でライトバリアが確実に無効化され、GCの整合性破壊やデッドロックといった問題が回避されるようになります。

この変更は、Goランタイムの堅牢性と安定性を向上させる上で非常に重要です。特に、予期せぬシグナルがGCのクリティカルなフェーズ中に発生した場合でも、ランタイムが安全に動作することを保証します。

## コアとなるコードの解説

変更の核心は、`sighandler` 関数の定義の直前にあるコンパイラディレクティブです。

```go
// May run during STW, so write barriers are not allowed.
//
//go:nowritebarrierrec
func sighandler(...) {
    // ...
}
```

この `//go:nowritebarrierrec` ディレクティブは、Goコンパイラに対して以下の指示を与えます。

1.  `sighandler` 関数自体の中で行われるポインタの書き込み操作に対して、ライトバリアのコードを挿入しない。
2.  さらに、`sighandler` 関数が内部で呼び出す**全ての関数**（直接的、間接的を問わず）に対しても、その関数内で発生するポインタの書き込み操作にライトバリアのコードを挿入しない。

これにより、`sighandler` がSTW中に実行されたとしても、その実行パス上のどのコードにおいてもライトバリアがトリガーされることがなくなります。これは、GCの整合性を保護し、ランタイムの安定性を確保するために不可欠な変更です。

*   **`//go:nowritebarrierrec`**: このディレクティブは `//go:nowritebarrier` の再帰版です。このディレクティブが付与された関数だけでなく、その関数が直接的または間接的に呼び出す全ての関数に対しても、ライトバリアの挿入を禁止します。これは、特定のコードパス全体でライトバリアを確実に無効化したい場合に非常に重要です。

## 技術的詳細

Goランタイムのシグナルハンドラ (`sighandler`) は、非常に特殊な環境で実行されます。特に重要なのは、STWフェーズ中に実行される可能性があるという点です。STW中は、GoのGCがメモリの状態を固定し、オブジェクトグラフの整合性を確保しようとします。この期間中に、もしシグナルハンドラ内でライトバリアが実行されてしまうと、以下のような深刻な問題が発生する可能性があります。

1.  **GCの整合性破壊**: ライトバリアはGCの内部状態（例えば、オブジェクトの色付け）を変更する可能性があります。STW中にGCがその内部状態を固定しているにもかかわらず、ライトバリアがそれを変更しようとすると、GCのアルゴリズムが破壊され、メモリリークやクラッシュにつながる可能性があります。
2.  **デッドロック**: ライトバリアの処理は、GCが使用する内部ロックを必要とすることがあります。STW中はGC自身がこれらのロックを保持している可能性があり、シグナルハンドラ内のライトバリアが同じロックを取得しようとすると、デッドロックが発生し、プログラムがハングアップする可能性があります。
3.  **未定義の動作**: シグナルハンドラは非同期に、かつ非常に限定されたスタック空間で実行されるため、通常のGoコードが期待するランタイムのサービス（スケジューラ、メモリ割り当てなど）が利用できない場合があります。ライトバリアがこれらのサービスに依存している場合、未定義の動作を引き起こす可能性があります。

以前の `//go:nowritebarrier` ディレクティブは、`sighandler` 関数自体にはライトバリアを挿入しないようにしていました。しかし、`sighandler` の実装は複雑であり、内部で他のヘルパー関数を呼び出すことが一般的です。これらのヘルパー関数には `//go:nowritebarrier` ディレクティブが適用されないため、それらの関数内でポインタの書き込みが発生した場合、ライトバリアが挿入されてしまいます。

このコミットは、この問題を認識し、`//go:nowritebarrierrec` ディレクティブを導入することで解決しました。`//go:nowritebarrierrec` は、`sighandler` 関数とその関数が呼び出す全ての関数（再帰的に）に対してライトバリアの挿入を禁止します。これにより、STW中に `sighandler` が実行されたとしても、その実行パス全体でライトバリアが確実に無効化され、GCの整合性破壊やデッドロックといった問題が回避されるようになります。

この変更は、Goランタイムの堅牢性と安定性を向上させる上で非常に重要です。特に、予期せぬシグナルがGCのクリティカルなフェーズ中に発生した場合でも、ランタイムが安全に動作することを保証します。

## コアとなるコードの解説

変更の核心は、`sighandler` 関数の定義の直前にあるコンパイラディレクティブです。

```go
// May run during STW, so write barriers are not allowed.
//
//go:nowritebarrierrec
func sighandler(...) {
    // ...
}
```

この `//go:nowritebarrierrec` ディレクティブは、Goコンパイラに対して以下の指示を与えます。

1.  `sighandler` 関数自体の中で行われるポインタの書き込み操作に対して、ライトバリアのコードを挿入しない。
2.  さらに、`sighandler` 関数が内部で呼び出す**全ての関数**（直接的、間接的を問わず）に対しても、その関数内で発生するポインタの書き込み操作にライトバリアのコードを挿入しない。

これにより、`sighandler` がSTW中に実行されたとしても、その実行パス上のどのコードにおいてもライトバリアがトリガーされることがなくなります。これは、GCの整合性を保護し、ランタイムの安定性を確保するために不可欠な変更です。

# [インデックス 2405] ファイルの概要

このコミットは、Goコンパイラの初期バージョンである`8c`（32-bit x86アーキテクチャ向け）におけるコード生成の修正に関するものです。具体的には、定数による除算の最適化に関連するバグを修正するため、`log2`関数の使用を、非2のべき乗に対して-1を返すカスタム関数`xlog2`に置き換えています。これにより、コンパイラが`/10`のような除算を誤って`/8`のようなビットシフト最適化に変換してしまう問題を解決しています。

## コミット

Goコンパイラ`8c`のコードジェネレータにおいて、定数除算の最適化ロジックで使用される対数計算関数を、標準の`log2`から、非2のべき乗に対しては負の値を返す`xlog2`に変更しました。この変更は、コンパイラが非2のべき乗の定数除算（例: `/10`）を誤って2のべき乗による除算（例: `/8`）として最適化してしまうバグを修正することを目的としています。

```

8c was rewriting /10 into /8.

```

## 変更の背景

このコミットの背景には、Goコンパイラ`8c`におけるコード生成の最適化、特に定数による除算の処理に関する問題がありました。

コンパイラは、プログラムの実行速度を向上させるために様々な最適化を行います。定数による除算は、CPUの除算命令が比較的遅いため、しばしばビットシフトや乗算といったより高速な命令に置き換えられます。この最適化は、除数が2のべき乗である場合に特に効果的です（例: `x / 8`は`x >> 3`に変換できる）。

しかし、このコミットメッセージによると、`8c`コンパイラは非2のべき乗の除数（例: `10`）に対しても、誤って2のべき乗による除算（例: `8`）として最適化を適用しようとしていたようです。具体的には、「`8c` was rewriting `/10` into `/8`」と記述されており、これは`x / 10`というコードが、誤って`x / 8`（またはそれに相当するビットシフト操作）としてコンパイルされてしまうバグを示唆しています。

この誤った最適化は、プログラムの計算結果に誤りを生じさせる重大なバグです。この問題を解決するためには、除数が本当に2のべき乗であるかを正確に判断し、そうでない場合にはビットシフト最適化を適用しないようにする必要がありました。

Plan 9のCコンパイラ（`cc`）環境では、`log2`という名前の関数が、非2のべき乗に対して特定の値を返すカスタムな振る舞いをしていた可能性があります。しかし、Goコンパイラ`8c`のコンテキストでは、この`log2`が標準ライブラリの`log2`と衝突するか、あるいは期待する振る舞いをしないため、明示的に「非2のべき乗に対して-1を返す」という特性を持つ`xlog2`という関数を使用するように変更されました。これにより、除数が2のべき乗であるかどうかの判定を正確に行い、誤った最適化を防ぐことが目的です。

## 前提知識の解説

1.  **Goコンパイラ `8c`**:
    初期のGo言語には、ターゲットアーキテクチャごとに異なるコンパイラが存在しました。`8c`は、Intel 386 (32-bit x86) アーキテクチャ向けのGoコンパイラを指します。同様に、`6c`はx64向け、`5c`はARM向けでした。これらは、Go言語の生みの親の一人であるKen Thompsonが開発したPlan 9のCコンパイラをベースにしていました。これらのコンパイラは、Goのソースコードを直接機械語に変換する役割を担っていました。

2.  **`cgen.c`**:
    `cgen.c`は「Code Generator」の略であり、コンパイラのバックエンド部分、特に中間表現からターゲットアーキテクチャの機械語（またはアセンブリコード）を生成する役割を担うファイルです。このファイルには、様々な命令の生成ロジックや最適化ルーチンが含まれています。

3.  **`log2` 関数と2のべき乗判定**:
    *   **`log2(x)`**: 数学における底が2の対数関数です。例えば、`log2(8) = 3`、`log2(16) = 4`です。プログラミングにおいては、`x`が2のべき乗である場合、`log2(x)`は整数値を返します。
    *   **2のべき乗判定とビットシフト最適化**: コンピュータの演算において、整数を2のべき乗で除算することは、右ビットシフト操作（`>>`）に置き換えることができます。例えば、`x / 8`は`x >> 3`と同じ意味です（ただし、負の数の扱いには注意が必要）。ビットシフトはCPUにとって非常に高速な操作であるため、コンパイラは除数が2のべき乗である場合にこの最適化を積極的に適用します。
    *   **非2のべき乗の除算最適化**: 除数が2のべき乗でない場合（例: `x / 10`）、単純なビットシフトには置き換えられません。しかし、現代のコンパイラは、このような場合でも「マジックナンバー乗算とビットシフト」というテクニックを用いて、遅い除算命令を回避し、より高速な乗算とビットシフトの組み合わせに変換することがあります。このテクニックは、`x / D`を`(x * M) >> S`のような形に変換するもので、`M`は「マジックナンバー」、`S`はシフト量です。

4.  **Plan 9 Cコンパイラの特性**:
    Plan 9のCコンパイラは、標準Cとは異なる独自の拡張や振る舞いを持つことがありました。このコミットメッセージにある「on plan 9 cc calls it log2, but that conflicts here」という記述は、Plan 9のCコンパイラが提供する`log2`関数が、Goコンパイラ`8c`のビルド環境において、標準Cライブラリの`log2`と名前が衝突するか、あるいはGoコンパイラが期待する特定のセマンティクス（非2のべき乗に対する特別な戻り値）を持っていなかったことを示唆しています。

## 技術的詳細

このコミットの核心は、定数除算の最適化における除数の「2のべき乗」判定の正確性を確保することにあります。

コンパイラが`x / C`のような除算式を処理する際、`C`が2のべき乗であれば、`x >> log2(C)`のようなビットシフト操作に変換できます。この変換は非常に効率的です。しかし、`C`が2のべき乗でない場合（例: `C=10`）、この単純なビットシフト最適化を適用すると、結果が誤りになります。

元のコードでは、おそらく標準の`log2`関数、またはそれに準ずる関数を使用して、定数`c`の対数を計算し、その結果が負でなければ（つまり、`c`が正の数であれば）、何らかの最適化パスに進んでいたと考えられます。

コミットメッセージにある「the difference is that xlog2 returns -1 on non powers of 2」という記述は、`xlog2`が以下のような振る舞いをすることを示しています。

*   `c`が2のべき乗の場合（例: 1, 2, 4, 8, ...）：`log2(c)`の値を返す（例: `xlog2(8)`は`3`を返す）。
*   `c`が2のべき乗ではない場合（例: 3, 5, 6, 7, 9, 10, ...）：`-1`を返す。

この`xlog2`の特性を利用することで、`cgen.c`内の最適化ロジックは、`v = xlog2(c)`の結果が`-1`であるかどうかをチェックするだけで、`c`が2のべき乗であるか否かを確実に判断できるようになります。

```c
// 変更前 (推測)
v = log2(c); // cが非2のべき乗でも、正の値を返す可能性がある

// 変更後
v = xlog2(c); // cが非2のべき乗なら -1 を返す
if (v < 0) {
    // c は2のべき乗ではないので、ビットシフト最適化は適用しない
    break; // または別の非ビットシフト最適化パスへ
}
// c は2のべき乗なので、ビットシフト最適化を適用する
```

この変更により、`c`が`10`のような非2のべき乗である場合でも、`xlog2(10)`は`-1`を返し、`v < 0`の条件が真となるため、誤って`/10`が`/8`に変換されるようなビットシフト最適化が回避されるようになります。これは、コンパイラの正確性を保証し、生成されるコードの信頼性を高める上で非常に重要な修正です。

## コアとなるコードの変更箇所

変更は `src/cmd/8c/cgen.c` ファイルの2箇所で行われています。

```diff
--- a/src/cmd/8c/cgen.c
+++ b/src/cmd/8c/cgen.c
@@ -346,7 +346,7 @@ cgen(Node *n, Node *nn)
 			c = r->vconst;
 			if(c < 0)
 				c = -c;
-			v = log2(c);
+			v = xlog2(c);
 			if(v < 0)
 				break;
 			/* fall thru */
@@ -609,7 +609,7 @@ cgen(Node *n, Node *nn)
 			c = r->vconst;
 			if(c < 0)
 				c = -c;
-			v = log2(c);
+			v = xlog2(c);
 			if(v < 0)
 				break;
 			/* fall thru */
```

## コアとなるコードの解説

上記のコードスニペットは、`cgen.c`内の`cgen`関数の一部を示しています。`cgen`関数は、Go言語の抽象構文木（AST）のノードを受け取り、それに対応する機械語コードを生成する役割を担っています。

変更箇所は、定数`c`の値を処理する部分です。

1.  `c = r->vconst;`
    これは、現在のノード`r`が表す定数値を`c`に代入しています。`r->vconst`は、コンパイル時に既知の定数値を保持するフィールドです。

2.  `if(c < 0) c = -c;`
    定数`c`が負の場合、その絶対値を取っています。対数関数は通常、正の数に対して定義されるため、この処理は適切です。

3.  `v = log2(c);` (変更前) -> `v = xlog2(c);` (変更後)
    ここが主要な変更点です。
    *   変更前は、`log2(c)`という関数が呼び出されていました。これが標準Cライブラリの`log2`であった場合、`c`が非2のべき乗であっても浮動小数点数値を返すか、あるいはPlan 9のCコンパイラが提供する`log2`が、Goコンパイラが期待する「非2のべき乗なら-1」というセマンティクスを持っていなかった可能性があります。
    *   変更後は、`xlog2(c)`という関数が呼び出されています。コミットメッセージによると、この`xlog2`は「非2のべき乗に対して-1を返す」という特別な振る舞いをします。

4.  `if(v < 0) break;`
    `xlog2(c)`の戻り値`v`が負であるかどうかのチェックです。
    *   `xlog2(c)`が`-1`を返した場合（つまり、`c`が2のべき乗ではない場合）、この条件が真となり、`break`文が実行されます。これにより、現在の最適化パス（おそらくビットシフト最適化）から抜け出し、誤った最適化が適用されるのを防ぎます。
    *   `xlog2(c)`が正の値を返した場合（つまり、`c`が2のべき乗である場合）、この条件は偽となり、コードは次の行に進みます。`/* fall thru */`というコメントから、この後でビットシフトによる最適化が適用されることが示唆されます。

この修正により、コンパイラは定数除算の最適化を行う際に、除数が本当に2のべき乗であるかを正確に判断できるようになり、`/10`が`/8`に誤変換されるようなバグが解消されました。

# [インデックス 21348] ファイルの概要

このコミットは、Goランタイムにおける`thunk.s`ファイルの削除と、それに伴う内部関数の公開メカニズムの変更に関するものです。これまで`thunk.s`を通じて間接的に公開されていたランタイム関数が、`//go:linkname`ディレクティブを用いたGoソースコード内での直接的なリンク、またはアセンブリコード内での直接的な名前参照に置き換えられました。特に`reflect.call`のような、依然としてジャンプが必要なケースについては、そのジャンプが関連するアセンブリ実装の近くに配置されるようになりました。

## 元コミット内容

Goランタイムから`thunk.s`ファイルを削除します。

Goファイル内では`//go:linkname`を使用し、`.s`ファイル内では名前を直接使用するように置き換えます。
唯一、本当にジャンプが必要なのは`reflect.call`だけであり、そのジャンプは`runtime.reflectcall`のアセンブリ実装の隣に配置されるようになりました。

## 変更の背景

Goのランタイムは、言語のコア機能（スケジューリング、メモリ管理、ガベージコレクションなど）を実装しており、これらの機能の一部は、`reflect`パッケージや`sync`パッケージなど、他の標準ライブラリパッケージからアクセスされる必要があります。

以前は、これらのランタイムの内部関数を外部パッケージに公開するために、`thunk.s`というアセンブリファイルが使用されていました。このファイルは、外部から呼び出される関数へのジャンプ命令（thunk）を多数含んでいました。しかし、このアプローチにはいくつかの課題がありました。

1.  **間接性の増加**: `thunk.s`を介した呼び出しは、余分なジャンプ命令を挟むため、わずかながらオーバーヘッドが発生します。
2.  **ビルドプロセスの複雑化**: `thunk.s`は、ランタイムの内部関数と外部パッケージの間の接着剤として機能していましたが、これはビルドシステムにとって追加の考慮事項となります。
3.  **コードの可読性と保守性**: 多数のシンプルなジャンプ命令が並ぶ`thunk.s`は、その目的は明確であるものの、Goのコードベース全体から見ると、より直接的な方法が望ましいと判断された可能性があります。

このコミットの背景には、Goの内部リンケージメカニズムを合理化し、より直接的で効率的な方法でランタイム関数を公開するという目的があります。特に、`//go:linkname`というコンパイラディレクティブの導入と成熟により、アセンブリによるthunkの必要性が薄れました。

## 前提知識の解説

### Goアセンブリ (`.s`ファイル)

Go言語は、そのランタイムの大部分がGoで書かれていますが、パフォーマンスが非常に重要であったり、OSやハードウェアとの低レベルなインタラクションが必要な部分（例: goroutineのスケジューリング、システムコール、一部のプリミティブ操作）では、アセンブリ言語が使用されます。Goのアセンブリは、Plan 9アセンブラの構文に基づいています。`.s`ファイルは、これらのアセンブリコードを記述するために使用されます。

### `//go:linkname` ディレクティブ

`//go:linkname`は、Goコンパイラに対する特殊なディレクティブ（指示子）です。これは、Goのパッケージシステムにおける通常の可視性ルール（エクスポートされていない関数や変数はパッケージ外からアクセスできない）をバイパスするために使用されます。具体的には、あるパッケージの関数や変数を、別のパッケージの関数や変数としてリンクすることを可能にします。

構文は以下のようになります。
`//go:linkname localname importpath.name`

*   `localname`: 現在のファイル内で定義されている関数または変数の名前。
*   `importpath.name`: リンクしたい外部パッケージの関数または変数の完全修飾名（例: `runtime.nanotime`）。

このディレクティブは、主にGoの標準ライブラリ、特に`runtime`パッケージと他のパッケージ（`reflect`, `sync`, `net`など）の間で、内部的な関数やデータ構造にアクセスするために使われます。これにより、Goのコードだけで低レベルな操作を記述できるようになり、アセンブリコードの量を減らすことができます。

### Thunk (サンク)

プログラミングにおける「thunk」とは、主に以下のような目的で使用される小さなコード片です。

1.  **遅延評価 (Lazy Evaluation)**: 計算を必要になるまで遅延させるために、計算自体をカプセル化した関数やクロージャ。
2.  **アダプタ/プロキシ**: ある関数呼び出しを別の関数呼び出しに変換したり、追加の処理（ロギング、エラーハンドリングなど）を挟んだりするための仲介役。
3.  **ジャンプテーブル**: 特にアセンブリ言語において、あるアドレスから別のアドレスへ制御を移すためのシンプルなジャンプ命令。Goの`thunk.s`はこの3番目の意味合いで使われていました。

Goのランタイムにおける`thunk.s`は、Goの内部関数（例えば`runtime`パッケージ内の関数）を、`reflect`や`sync`などの他のパッケージから呼び出せるようにするためのジャンプテーブルとして機能していました。外部パッケージがランタイム関数を呼び出そうとすると、まず`thunk.s`内の対応するエントリにジャンプし、そこから実際のランタイム関数へとさらにジャンプするという二段階の呼び出しが行われていました。

### `reflect`パッケージ

`reflect`パッケージは、Goプログラムが実行時に自身の構造を検査し、操作するための機能を提供します。これにより、型情報（構造体のフィールド、メソッドなど）の取得、インターフェース値の操作、関数の動的な呼び出しなどが可能になります。`reflect.call`は、このパッケージの主要な機能の一つで、実行時に任意の関数を動的に呼び出すために使用されます。この機能は、コンパイル時に呼び出し先が確定しないため、ランタイムとの密接な連携が必要となります。

## 技術的詳細

このコミットの核心は、Goランタイムが他のパッケージに内部関数を公開する方法を、間接的なアセンブリthunkから、より直接的な`//go:linkname`ディレクティブとアセンブリ内の直接参照へと移行した点にあります。

**変更前のアプローチ (`thunk.s`の使用)**:
Goのランタイムには、`runtime.nanotime`、`runtime.asyncsemacquire`、`runtime.netpollOpen`など、他の標準ライブラリパッケージ（`time`、`sync`、`net`など）からアクセスする必要がある多くの内部関数がありました。Goの通常の可視性ルールでは、これらの関数はエクスポートされていないため、直接呼び出すことはできません。

そこで、`src/runtime/thunk.s`というアセンブリファイルが導入されました。このファイルには、各内部ランタイム関数に対応する「thunk」が定義されていました。thunkは、単に目的のランタイム関数へのジャンプ命令を含む小さなアセンブリコード片です。例えば、`time.runtimeNano`が`runtime.nanotime`を呼び出す場合、実際には`thunk.s`内の`TEXT time·runtimeNano(SB)`にジャンプし、そこから`JMP runtime·nanotime(SB)`によって`runtime.nanotime`へと制御が移されていました。

この方法は機能しましたが、以下のような欠点がありました。
*   **余分な間接性**: 呼び出しごとに1回の余分なジャンプが発生します。
*   **アセンブリコードの増加**: 多数のthunkが`thunk.s`に記述されるため、アセンブリコードの量が増えます。
*   **保守性の問題**: 新しいランタイム関数を公開するたびに、`thunk.s`に新しいエントリを追加する必要がありました。

**変更後のアプローチ (`//go:linkname`と直接参照)**:
このコミットでは、`thunk.s`を完全に削除し、その役割を以下の2つの方法で置き換えました。

1.  **Goファイル内での`//go:linkname`の使用**:
    Goのソースファイル内で、他のパッケージからアクセスしたいランタイム関数（またはそのラッパー関数）の定義に`//go:linkname`ディレクティブを追加します。これにより、コンパイラは、その関数が指定された外部パッケージの関数としてリンクされるべきであることを認識します。
    例えば、`src/runtime/chan.go`では、`reflect.makechan`が`runtime.makechan`を呼び出すために、以下のように変更されました。

    ```go
    //go:linkname reflect_makechan reflect.makechan
    func reflect_makechan(t *chantype, size int64) *hchan {
        return makechan(t, size)
    }
    ```
    `reflect.makechan`という名前で外部に公開される関数が、実際には`runtime`パッケージ内の`makechan`を呼び出す`reflect_makechan`という内部関数にリンクされます。これにより、アセンブリthunkを介さずに、Goコンパイラとリンカが直接リンクを解決できるようになります。

2.  **アセンブリファイル内での直接参照**:
    Goのアセンブリファイル（`.s`ファイル）内では、`//go:linkname`のようなディレクティブは必要ありません。アセンブリコードは、シンボル名を直接参照して関数を呼び出すことができます。このコミットでは、`thunk.s`が削除された後、アセンブリコード内で直接ランタイム関数名が使用されるようになりました。

    **`reflect.call`の特殊なケース**:
    コミットメッセージにもあるように、`reflect.call`は唯一「本当にジャンプが必要」なケースとして言及されています。これは、`reflect.call`がGoの関数呼び出し規約とは異なる方法で引数を渡し、動的な関数呼び出しを行うため、特別なアセンブリコードによる処理が必要だからです。
    変更前は、`thunk.s`に`reflect·call`のエントリがあり、それが`runtime·reflectcall`にジャンプしていました。変更後は、このジャンプ命令が各アーキテクチャのアセンブリファイル（例: `src/runtime/asm_amd64.s`）内の`runtime·reflectcall`の実装のすぐ隣に移動されました。

    ```assembly
    TEXT reflect·call(SB), NOSPLIT, $0-0
    	JMP	·reflectcall(SB)
    ```
    これにより、`reflect.call`の呼び出しパスは依然としてジャンプを含みますが、そのジャンプはより局所化され、`thunk.s`という中央集権的なジャンプテーブルの必要性がなくなりました。

**メリット**:
*   **間接性の削減**: ほとんどのケースで余分なジャンプが不要になり、わずかながらパフォーマンスが向上する可能性があります。
*   **ビルドプロセスの簡素化**: `thunk.s`という特殊なアセンブリファイルの管理が不要になります。
*   **コードの明確化**: `//go:linkname`ディレクティブは、Goのソースコード内でどの関数が外部に公開されているかを明示的に示します。
*   **アセンブリコードの削減**: `thunk.s`が削除されたことで、Goのコードベース全体のアセンブリコードの量が減少します。

## コアとなるコードの解説

このコミットの主要な変更は、Goの内部リンケージメカニズムの近代化です。

*   **`thunk.s`の削除**:
    これは、Goのビルドプロセスから不要な間接レイヤーとアセンブリコードを排除するという明確な意図を示しています。`thunk.s`は、Goの初期のバージョンで、ランタイムの内部関数を他のパッケージに公開するための暫定的な解決策として機能していました。`//go:linkname`ディレクティブがGoコンパイラに組み込まれ、その機能が成熟したことで、このファイルは冗長になりました。

*   **`//go:linkname`の広範な導入**:
    `src/runtime`ディレクトリ内の多数のGoファイルに`//go:linkname`ディレクティブが追加されたことは、これがGoの内部関数公開の標準的な方法になったことを意味します。これにより、GoのコードベースはよりGoらしくなり、アセンブリコードの量を減らし、コンパイラとリンカが直接リンクを解決できるようになります。これは、Goのツールチェーンの進化と、より洗練された内部リンケージ機能の実現を反映しています。

    例えば、`reflect.makechan`が`runtime.makechan`を呼び出す場合、以前は`reflect.makechan`が`thunk.s`内の`reflect·makechan`にジャンプし、それがさらに`runtime·makechan`にジャンプしていました。この変更後は、`reflect.makechan`は`//go:linkname`によって直接`runtime`パッケージ内の`makechan`にリンクされるため、中間のアセンブリジャンプが不要になります。

*   **`reflect.call`の特殊な扱い**:
    `reflect.call`は、Goの関数呼び出し規約とは異なる低レベルな操作を必要とするため、依然としてアセンブリによるジャンプが必要です。しかし、このジャンプはもはや`thunk.s`のような中央集権的なファイルにはなく、`runtime.reflectcall`の実装のすぐ隣に配置されます。これは、必要なアセンブリコードをその機能が最も関連する場所に局所化するという設計原則に従っています。これにより、コードの関連性が高まり、保守性が向上します。

*   **`bytes.Compare`の変更**:
    `runtime·cmpbytes`が`bytes·Compare`に名称変更されたことは、`bytes`パッケージの`Compare`関数が、ランタイムの内部比較ルーチンに直接リンクされるようになったことを示唆しています。これもまた、`//go:linkname`の活用により、標準ライブラリの関数がランタイムの最適化された内部実装を直接利用できるようになる例です。

全体として、このコミットはGoランタイムの内部構造を簡素化し、より効率的で保守しやすいリンケージメカニズムへと移行する重要なステップです。

Goランタイムから`thunk.s`ファイルを削除します。

Goファイル内では`//go:linkname`を使用し、`.s`ファイル内では名前を直接使用するように置き換えます。
唯一、本当にジャンプが必要なのは`reflect.call`だけであり、そのジャンプは`runtime.reflectcall`のアセンブリ実装の隣に配置されるようになりました。

## 変更の背景

Goのランタイムは、言語のコア機能（スケジューリング、メモリ管理、ガベージコレクションなど）を実装しており、これらの機能の一部は、`reflect`パッケージや`sync`パッケージなど、他の標準ライブラリパッケージからアクセスされる必要があります。

以前は、これらのランタイムの内部関数を外部パッケージに公開するために、`thunk.s`というアセンブリファイルが使用されていました。このファイルは、外部から呼び出される関数へのジャンプ命令（thunk）を多数含んでいました。しかし、このアプローチにはいくつかの課題がありました。

1.  **間接性の増加**: `thunk.s`を介した呼び出しは、余分なジャンプ命令を挟むため、わずかながらオーバーヘッドが発生します。
2.  **ビルドプロセスの複雑化**: `thunk.s`は、ランタイムの内部関数と外部パッケージの間の接着剤として機能していましたが、これはビルドシステムにとって追加の考慮事項となります。
3.  **コードの可読性と保守性**: 多数のシンプルなジャンプ命令が並ぶ`thunk.s`は、その目的は明確であるものの、Goのコードベース全体から見ると、より直接的な方法が望ましいと判断された可能性があります。

このコミットの背景には、Goの内部リンケージメカニズムを合理化し、より直接的で効率的な方法でランタイム関数を公開するという目的があります。特に、`//go:linkname`というコンパイラディレクティブの導入と成熟により、アセンブリによるthunkの必要性が薄れました。

## 前提知識の解説

### Goアセンブリ (`.s`ファイル)

Go言語は、そのランタイムの大部分がGoで書かれていますが、パフォーマンスが非常に重要であったり、OSやハードウェアとの低レベルなインタラクションが必要な部分（例: goroutineのスケジューリング、システムコール、一部のプリミティブ操作）では、アセンブリ言語が使用されます。Goのアセンブリは、Plan 9アセンブラの構文に基づいています。`.s`ファイルは、これらのアセンブリコードを記述するために使用されます。

### `//go:linkname` ディレクティブ

`//go:linkname`は、Goコンパイラに対する特殊なディレクティブ（指示子）です。これは、Goのパッケージシステムにおける通常の可視性ルール（エクスポートされていない関数や変数はパッケージ外からアクセスできない）をバイパスするために使用されます。具体的には、あるパッケージの関数や変数を、別のパッケージの関数や変数としてリンクすることを可能にします。

構文は以下のようになります。
`//go:linkname localname importpath.name`

*   `localname`: 現在のファイル内で定義されている関数または変数の名前。
*   `importpath.name`: リンクしたい外部パッケージの関数または変数の完全修飾名（例: `runtime.nanotime`）。

このディレクティブは、主にGoの標準ライブラリ、特に`runtime`パッケージと他のパッケージ（`reflect`, `sync`, `net`など）の間で、内部的な関数やデータ構造にアクセスするために使われます。これにより、Goのコードだけで低レベルな操作を記述できるようになり、アセンブリコードの量を減らすことができます。

### Thunk (サンク)

プログラミングにおける「thunk」とは、主に以下のような目的で使用される小さなコード片です。

1.  **遅延評価 (Lazy Evaluation)**: 計算を必要になるまで遅延させるために、計算自体をカプセル化した関数やクロージャ。
2.  **アダプタ/プロキシ**: ある関数呼び出しを別の関数呼び出しに変換したり、追加の処理（ロギング、エラーハンドリングなど）を挟んだりするための仲介役。
3.  **ジャンプテーブル**: 特にアセンブリ言語において、あるアドレスから別のアドレスへ制御を移すためのシンプルなジャンプ命令。Goの`thunk.s`はこの3番目の意味合いで使われていました。

Goのランタイムにおける`thunk.s`は、Goの内部関数（例えば`runtime`パッケージ内の関数）を、`reflect`や`sync`などの他のパッケージから呼び出せるようにするためのジャンプテーブルとして機能していました。外部パッケージがランタイム関数を呼び出そうとすると、まず`thunk.s`内の対応するエントリにジャンプし、そこから実際のランタイム関数へとさらにジャンプするという二段階の呼び出しが行われていました。

### `reflect`パッケージ

`reflect`パッケージは、Goプログラムが実行時に自身の構造を検査し、操作するための機能を提供します。これにより、型情報（構造体のフィールド、メソッドなど）の取得、インターフェース値の操作、関数の動的な呼び出しなどが可能になります。`reflect.call`は、このパッケージの主要な機能の一つで、実行時に任意の関数を動的に呼び出すために使用されます。この機能は、コンパイル時に呼び出し先が確定しないため、ランタイムとの密接な連携が必要となります。

## 技術的詳細

このコミットの核心は、Goランタイムが他のパッケージに内部関数を公開する方法を、間接的なアセンブリthunkから、より直接的な`//go:linkname`ディレクティブとアセンブリ内の直接参照へと移行した点にあります。

**変更前のアプローチ (`thunk.s`の使用)**:
Goのランタイムには、`runtime.nanotime`、`runtime.asyncsemacquire`、`runtime.netpollOpen`など、他の標準ライブラリパッケージ（`time`、`sync`、`net`など）からアクセスする必要がある多くの内部関数がありました。Goの通常の可視性ルールでは、これらの関数はエクスポートされていないため、直接呼び出すことはできません。

そこで、`src/runtime/thunk.s`というアセンブリファイルが導入されました。このファイルには、各内部ランタイム関数に対応する「thunk」が定義されていました。thunkは、単に目的のランタイム関数へのジャンプ命令を含む小さなアセンブリコード片です。例えば、`time.runtimeNano`が`runtime.nanotime`を呼び出す場合、実際には`thunk.s`内の`TEXT time·runtimeNano(SB)`にジャンプし、そこから`JMP runtime·nanotime(SB)`によって`runtime.nanotime`へと制御が移されていました。

この方法は機能しましたが、以下のような欠点がありました。
*   **余分な間接性**: 呼び出しごとに1回の余分なジャンプが発生します。
*   **アセンブリコードの増加**: 多数のthunkが`thunk.s`に記述されるため、アセンブリコードの量が増えます。
*   **保守性の問題**: 新しいランタイム関数を公開するたびに、`thunk.s`に新しいエントリを追加する必要がありました。

**変更後のアプローチ (`//go:linkname`と直接参照)**:
このコミットでは、`thunk.s`を完全に削除し、その役割を以下の2つの方法で置き換えました。

1.  **Goファイル内での`//go:linkname`の使用**:
    Goのソースファイル内で、他のパッケージからアクセスしたいランタイム関数（またはそのラッパー関数）の定義に`//go:linkname`ディレクティブを追加します。これにより、コンパイラは、その関数が指定された外部パッケージの関数としてリンクされるべきであることを認識します。
    例えば、`src/runtime/chan.go`では、`reflect.makechan`が`runtime.makechan`を呼び出すために、以下のように変更されました。

    ```go
    //go:linkname reflect_makechan reflect.makechan
    func reflect_makechan(t *chantype, size int64) *hchan {
        return makechan(t, size)
    }
    ```
    `reflect.makechan`という名前で外部に公開される関数が、実際には`runtime`パッケージ内の`makechan`を呼び出す`reflect_makechan`という内部関数にリンクされます。これにより、アセンブリthunkを介さずに、Goコンパイラとリンカが直接リンクを解決できるようになります。

2.  **アセンブリファイル内での直接参照**:
    Goのアセンブリファイル（`.s`ファイル）内では、`//go:linkname`のようなディレクティブは必要ありません。アセンブリコードは、シンボル名を直接参照して関数を呼び出すことができます。このコミットでは、`thunk.s`が削除された後、アセンブリコード内で直接ランタイム関数名が使用されるようになりました。

    **`reflect.call`の特殊なケース**:
    コミットメッセージにもあるように、`reflect.call`は唯一「本当にジャンプが必要」なケースとして言及されています。これは、`reflect.call`がGoの関数呼び出し規約とは異なる方法で引数を渡し、動的な関数呼び出しを行うため、特別なアセンブリコードによる処理が必要だからです。
    変更前は、`thunk.s`に`reflect·call`のエントリがあり、それが`runtime·reflectcall`にジャンプしていました。変更後は、このジャンプ命令が各アーキテクチャのアセンブリファイル（例: `src/runtime/asm_amd64.s`）内の`runtime·reflectcall`の実装のすぐ隣に移動されました。

    ```assembly
    TEXT reflect·call(SB), NOSPLIT, $0-0
    	JMP	·reflectcall(SB)
    ```
    これにより、`reflect.call`の呼び出しパスは依然としてジャンプを含みますが、そのジャンプはより局所化され、`thunk.s`という中央集権的なジャンプテーブルの必要性がなくなりました。

**メリット**:
*   **間接性の削減**: ほとんどのケースで余分なジャンプが不要になり、わずかながらパフォーマンスが向上する可能性があります。
*   **ビルドプロセスの簡素化**: `thunk.s`という特殊なアセンブリファイルの管理が不要になります。
*   **コードの明確化**: `//go:linkname`ディレクティブは、Goのソースコード内でどの関数が外部に公開されているかを明示的に示します。
*   **アセンブリコードの削減**: `thunk.s`が削除されたことで、Goのコードベース全体のアセンブリコードの量が減少します。

## コアとなるコードの解説

このコミットの主要な変更は、Goの内部リンケージメカニズムの近代化です。

*   **`thunk.s`の削除**:
    これは、Goのビルドプロセスから不要な間接レイヤーとアセンブリコードを排除するという明確な意図を示しています。`thunk.s`は、Goの初期のバージョンで、ランタイムの内部関数を他のパッケージに公開するための暫定的な解決策として機能していました。`//go:linkname`ディレクティブがGoコンパイラに組み込まれ、その機能が成熟したことで、このファイルは冗長になりました。

*   **`//go:linkname`の広範な導入**:
    `src/runtime`ディレクトリ内の多数のGoファイルに`//go:linkname`ディレクティブが追加されたことは、これがGoの内部関数公開の標準的な方法になったことを意味します。これにより、GoのコードベースはよりGoらしくなり、アセンブリコードの量を減らし、コンパイラとリンカが直接リンクを解決できるようになります。これは、Goのツールチェーンの進化と、より洗練された内部リンケージ機能の実現を反映しています。

    例えば、`reflect.makechan`が`runtime.makechan`を呼び出す場合、以前は`reflect.makechan`が`thunk.s`内の`reflect·makechan`にジャンプし、それがさらに`runtime·makechan`にジャンプしていました。この変更後は、`reflect.makechan`は`//go:linkname`によって直接`runtime`パッケージ内の`makechan`にリンクされるため、中間のアセンブリジャンプが不要になります。

*   **`reflect.call`の特殊な扱い**:
    `reflect.call`は、Goの関数呼び出し規約とは異なる低レベルな操作を必要とするため、依然としてアセンブリによるジャンプが必要です。しかし、このジャンプはもはや`thunk.s`のような中央集権的なファイルにはなく、`runtime.reflectcall`の実装のすぐ隣に配置されます。これは、必要なアセンブリコードをその機能が最も関連する場所に局所化するという設計原則に従っています。これにより、コードの関連性が高まり、保守性が向上します。

*   **`bytes.Compare`の変更**:
    `runtime·cmpbytes`が`bytes·Compare`に名称変更されたことは、`bytes`パッケージの`Compare`関数が、ランタイムの内部比較ルーチンに直接リンクされるようになったことを示唆しています。これもまた、`//go:linkname`の活用により、標準ライブラリの関数がランタイムの最適化された内部実装を直接利用できるようになる例です。

全体として、このコミットはGoランタイムの内部構造を簡素化し、より効率的で保守しやすいリンケージメカニズムへと移行する重要なステップです。

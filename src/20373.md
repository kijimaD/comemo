このコミットは、GoランタイムにおけるGoコードからCコードへの関数呼び出しのメカニズムを改善することを目的としています。具体的には、GoルーチンがOSスレッド（M）上で特定の操作を実行する必要がある場合や、スタック管理の最適化のために、`onM`呼び出しや`#pragma textflag NOSPLIT`ディレクティブを導入・活用しています。これにより、GoランタイムのC部分を削減し、Goコードでの実装を増やすことで、保守性とパフォーマンスの向上を図っています。

## 変更の背景

Goランタイムは、パフォーマンスと低レベルなシステム操作のためにC言語で書かれた部分と、Go言語で書かれた部分が混在しています。Goルーチンは軽量なスレッドであり、OSスレッド（M）上で実行されますが、GoルーチンがCコードを呼び出す際には、GoのスタックとCのスタックの間で切り替えが発生したり、特定の操作がOSスレッドのコンテキストで実行される必要があるなど、複雑な相互作用が生じます。

このコミットの背景には、GoランタイムのCコード部分を減らし、より多くのロジックをGo言語で記述することで、ランタイムの保守性を向上させ、潜在的なバグを減らすという目標があります。特に、GoからCへの関数呼び出しは、スタック管理やスケジューリングの観点から注意が必要であり、このコミットはこれらの呼び出しをより安全かつ効率的に行うためのリファクタリングを行っています。

具体的には、以下の課題に対処しています。
*   **GoとCのスタック切り替えの複雑性**: Goルーチンは可変長のスタックを持ち、必要に応じてスタックを拡張します。しかし、C関数を呼び出す際には、固定サイズのCスタックに切り替える必要があります。この切り替えはオーバーヘッドを伴い、また、スタックの境界を越えるような操作は未定義の動作を引き起こす可能性があります。
*   **OSスレッド（M）のコンテキストの必要性**: 一部のランタイム操作（例：システムコール、プロファイリング、メモリ管理の低レベルな部分）は、特定のOSスレッドのコンテキストで実行される必要があります。Goルーチンは任意のM上で実行され得るため、これらの操作を安全に実行するためのメカニズムが必要です。
*   **Cコードの保守性**: CコードはGoコードに比べて型安全性やメモリ安全性の面で課題があり、バグの温床となる可能性があります。CコードをGoに移行することで、Goの型システムやガベージコレクションの恩恵を受け、コードの品質を向上させることができます。

このコミットは、これらの課題に対し、`onM`呼び出しと`#pragma textflag NOSPLIT`という2つの主要なアプローチで対処しています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の概念を理解しておく必要があります。

### Goランタイムのスケジューラ (GMPモデル)

Goランタイムは、G-M-Pモデルと呼ばれるスケジューラを採用しています。
*   **G (Goroutine)**: Go言語の軽量な実行単位です。GoルーチンはGoランタイムによって管理され、OSスレッドよりもはるかに軽量です。
*   **M (Machine/OS Thread)**: OSスレッドを表します。GoルーチンはM上で実行されます。MはOSによってスケジューリングされます。
*   **P (Processor)**: 論理プロセッサを表します。PはMに割り当てられ、Goルーチンを実行するためのコンテキストを提供します。PはGoルーチンをキューに入れ、MがPからGoルーチンを取得して実行します。

### スタック管理とスタック分割 (Stack Splitting)

Goルーチンは、必要に応じて動的にサイズが変更される可変長のスタックを使用します。Goコンパイラは、関数呼び出しの前にスタックの残りの容量をチェックし、必要であればスタックを拡張するコード（スタック分割チェック）を挿入します。これにより、Goルーチンは小さなスタックで開始し、必要に応じて成長できるため、メモリ効率が向上します。

### `onM` 関数

`onM`はGoランタイムの内部関数で、現在のGoルーチンが実行されているM（OSスレッド）上で、指定された関数を実行するために使用されます。これは、GoルーチンがOSスレッドのコンテキストで特定の操作を実行する必要がある場合に特に重要です。例えば、システムコールや、OSスレッドに固有の状態にアクセスする必要がある操作などがこれに該当します。`onM`は、Goルーチンが一時的にMに「固定」され、そのM上で指定された関数が実行されることを保証します。

### `#pragma textflag NOSPLIT`

これはGoコンパイラに対するディレクティブ（指示子）です。通常、Goコンパイラは関数呼び出しの前にスタック分割チェックを挿入しますが、`#pragma textflag NOSPLIT`が指定された関数には、このスタック分割チェックが挿入されません。これは、以下のような場合に利用されます。
*   **低レベルなランタイム関数**: Goランタイムの非常に低レベルな部分で、スタック分割チェックがオーバーヘッドになったり、スタックの整合性を損なう可能性がある場合。
*   **Cコードとの境界**: Cコードから呼び出されるGo関数や、Cコードに非常に近いGo関数で、スタックの切り替えが頻繁に発生する場合。スタック分割チェックが不要または不適切であると判断される場合に用いられます。

### GoとCの相互運用性

GoはC言語の関数を直接呼び出すことができます（cgo）。しかし、GoとCの間でデータをやり取りしたり、スタックを切り替えたりする際には、特定のルールとオーバーヘッドが発生します。Goランタイムの内部では、Cで書かれた部分とGoで書かれた部分が密接に連携しており、その間の呼び出しは最適化の対象となります。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムにおけるGoとCの間の関数呼び出しのパターンを体系的にリファクタリングした点にあります。

1.  **CからGoへの移行**:
    *   `src/pkg/runtime/malloc.c` にあった `persistentalloc` 関数が `src/pkg/runtime/malloc.go` に移行されました。`persistentalloc` は、Goランタイムの内部で永続的なデータ（型情報、デバッグ情報など）を割り当てるために使用される関数です。この関数をCからGoに移行することで、Goのメモリ管理の恩恵を受け、コードの保守性が向上します。
    *   `src/pkg/runtime/runtime.c` にあった `tickspersecond` 関数が `src/pkg/runtime/runtime.go` に移行されました。これは、CPUのティック数を秒単位で計算する関数で、プロファイリングなどに使用されます。
    *   `os_nacl.c`, `os_windows.c`, `signal_unix.c` にあった `os·sigpipe` 関数がそれぞれのGoファイル (`os_nacl.go`, `os_windows.go`, `signal_unix.go`) に移行されました。これは、SIGPIPEシグナル（クローズされたパイプへの書き込み時に発生）の処理に関するものです。

2.  **`onM` の活用**:
    *   GoルーチンがOSスレッド（M）のコンテキストで実行する必要がある操作（例：システムコール、プロファイリングの開始/停止、GCの停止/再開）に対して、`onM` 関数が積極的に導入されました。
    *   例えば、`setcpuprofilerate`, `GOMAXPROCS` (内部の `gomaxprocsfunc`), `stoptheworld`, `starttheworld`, `freemcache`, `setprofilebucket`, `semacreate`, `semasleep`, `syscall·runtime_BeforeFork`, `syscall·runtime_AfterFork` といった関数が、直接C関数を呼び出すのではなく、`_m` サフィックスを持つGo関数を定義し、それを `onM` 経由で呼び出すように変更されました。
    *   `onM` を使用することで、Goルーチンは一時的に現在のMに固定され、そのM上で安全に低レベルな操作を実行できます。これにより、Goルーチンが別のMに移動したり、スタックが切り替わったりする際に発生する可能性のある問題を回避できます。
    *   `g.m.scalararg` や `g.m.ptrarg` を使用して、`onM` 呼び出しを介して引数を渡すメカニズムが導入されています。これは、Goルーチン（G）が現在実行されているM（`g.m`）のフィールドを介して、`onM` で実行される関数にデータを渡すためのものです。

3.  **`#pragma textflag NOSPLIT` の適用**:
    *   非常にシンプルで低レベルな関数、またはスタック分割チェックが不要な関数に対して、`#pragma textflag NOSPLIT` が適用されました。これにより、これらの関数にはスタック分割チェックのコードが挿入されず、オーバーヘッドが削減されます。
    *   `runtime·semawakeup`, `runtime·semacreate` (内部の `semacreate`), `runtime·semasleep` (内部の `semasleep`), `runtime·mach_semrelease`, `runtime·gotraceback`, `runtime·gcount`, `os·sigpipe` (アセンブリのthunk) などに適用されています。
    *   特に、`runtime·mach_semrelease` のような関数は、シグナルハンドラなど、スタックの状況が予測しにくいコンテキストから呼び出される可能性があるため、`NOSPLIT` は重要です。

これらの変更により、GoランタイムはGoとCの間の境界をより明確にし、Goコードの比率を高め、低レベルな操作をより安全かつ効率的に実行できるようになりました。

// Wrapper around sysAlloc that can allocate small chunks.
// There is no associated free operation.
// Intended for things like function/type/debug-related persistent data.
// If align is 0, uses default align (currently 8).
func persistentalloc(size, align uintptr, stat *uint64) unsafe.Pointer {
	const (
		chunk    = 256 << 10
		maxBlock = 64 << 10 // VM reservation granularity is 64K on windows
	)

	if align != 0 {
		if align&(align-1) != 0 {
			gothrow("persistentalloc: align is not a power of 2")
		}
		if align > _PageSize {
			gothrow("persistentalloc: align is too large")
		}
	} else {
		align = 8
	}

	if size >= maxBlock {
		return sysAlloc(size, stat)
	}

	lock(&persistent.lock)
	persistent.pos = roundup(persistent.pos, align)
	if uintptr(persistent.pos)+size > uintptr(persistent.end) {
		persistent.pos = sysAlloc(chunk, &memstats.other_sys)
		if persistent.pos == nil {
			unlock(&persistent.lock)
			gothrow("runtime: cannot allocate memory")
		}
		persistent.end = add(persistent.pos, chunk)
	}
	p := persistent.pos
	persistent.pos = add(persistent.pos, size)
	unlock(&persistent.lock)

	if stat != &memstats.other_sys {
		xadd64(stat, int64(size))
		xadd64(&memstats.other_sys, -int64(size))
	}
	return p
}
```
`persistentalloc` は、Goランタイムが内部的に使用する、解放されない永続的なメモリ領域を割り当てるための関数です。この関数がCからGoに完全に移行されたことは、GoランタイムのC依存性を減らし、Goのメモリ管理の原則に沿った実装を増やすという方向性を示しています。Goで実装することで、Goの型システムやツールチェインの恩恵を受けることができます。

## 変更の背景

Goランタイムは、パフォーマンスと低レベルなシステム操作のためにC言語で書かれた部分と、Go言語で書かれた部分が混在しています。Goルーチンは軽量なスレッドであり、OSスレッド（M）上で実行されますが、GoルーチンがCコードを呼び出す際には、GoのスタックとCのスタックの間で切り替えが発生したり、特定の操作がOSスレッドのコンテキストで実行される必要があるなど、複雑な相互作用が生じます。

このコミットの背景には、GoランタイムのCコード部分を減らし、より多くのロジックをGo言語で記述することで、ランタイムの保守性を向上させ、潜在的なバグを減らすという目標があります。特に、GoからCへの関数呼び出しは、スタック管理やスケジューリングの観点から注意が必要であり、このコミットはこれらの呼び出しをより安全かつ効率的に行うためのリファクタリングを行っています。

具体的には、以下の課題に対処しています。
*   **GoとCのスタック切り替えの複雑性**: Goルーチンは可変長のスタックを持ち、必要に応じてスタックを拡張します。しかし、C関数を呼び出す際には、固定サイズのCスタックに切り替える必要があります。この切り替えはオーバーヘッドを伴い、また、スタックの境界を越えるような操作は未定義の動作を引き起こす可能性があります。
*   **OSスレッド（M）のコンテキストの必要性**: 一部のランタイム操作（例：システムコール、プロファイリング、メモリ管理の低レベルな部分）は、特定のOSスレッドのコンテキストで実行される必要があります。Goルーチンは任意のM上で実行され得るため、これらの操作を安全に実行するためのメカニズムが必要です。
*   **Cコードの保守性**: CコードはGoコードに比べて型安全性やメモリ安全性の面で課題があり、バグの温床となる可能性があります。CコードをGoに移行することで、Goの型システムやガベージコレクションの恩恵を受け、コードの品質を向上させることができます。

このコミットは、これらの課題に対し、`onM`呼び出しと`#pragma textflag NOSPLIT`という2つの主要なアプローチで対処しています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の概念を理解しておく必要があります。

### Goランタイムのスケジューラ (GMPモデル)

Goランタイムは、G-M-Pモデルと呼ばれるスケジューラを採用しています。
*   **G (Goroutine)**: Go言語の軽量な実行単位です。GoルーチンはGoランタイムによって管理され、OSスレッドよりもはるかに軽量です。
*   **M (Machine/OS Thread)**: OSスレッドを表します。GoルーチンはM上で実行されます。MはOSによってスケジューリングされます。
*   **P (Processor)**: 論理プロセッサを表します。PはMに割り当てられ、Goルーチンを実行するためのコンテキストを提供します。PはGoルーチンをキューに入れ、MがPからGoルーチンを取得して実行します。

### スタック管理とスタック分割 (Stack Splitting)

Goルーチンは、必要に応じて動的にサイズが変更される可変長のスタックを使用します。Goコンパイラは、関数呼び出しの前にスタックの残りの容量をチェックし、必要であればスタックを拡張するコード（スタック分割チェック）を挿入します。これにより、Goルーチンは小さなスタックで開始し、必要に応じて成長できるため、メモリ効率が向上します。

### `onM` 関数

`onM`はGoランタイムの内部関数で、現在のGoルーチンが実行されているM（OSスレッド）上で、指定された関数を実行するために使用されます。これは、GoルーチンがOSスレッドのコンテキストで特定の操作を実行する必要がある場合に特に重要です。例えば、システムコールや、OSスレッドに固有の状態にアクセスする必要がある操作などがこれに該当します。`onM`は、Goルーチンが一時的にMに「固定」され、そのM上で指定された関数が実行されることを保証します。

### `#pragma textflag NOSPLIT`

これはGoコンパイラに対するディレクティブ（指示子）です。通常、Goコンパイラは関数呼び出しの前にスタック分割チェックを挿入しますが、`#pragma textflag NOSPLIT`が指定された関数には、このスタック分割チェックが挿入されません。これは、以下のような場合に利用されます。
*   **低レベルなランタイム関数**: Goランタイムの非常に低レベルな部分で、スタック分割チェックがオーバーヘッドになったり、スタックの整合性を損なう可能性がある場合。
*   **Cコードとの境界**: Cコードから呼び出されるGo関数や、Cコードに非常に近いGo関数で、スタックの切り替えが頻繁に発生する場合。スタック分割チェックが不要または不適切であると判断される場合に用いられます。

### GoとCの相互運用性

GoはC言語の関数を直接呼び出すことができます（cgo）。しかし、GoとCの間でデータをやり取りしたり、スタックを切り替えたりする際には、特定のルールとオーバーヘッドが発生します。Goランタイムの内部では、Cで書かれた部分とGoで書かれた部分が密接に連携しており、その間の呼び出しは最適化の対象となります。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムにおけるGoとCの間の関数呼び出しのパターンを体系的にリファクタリングした点にあります。

1.  **CからGoへの移行**:
    *   `src/pkg/runtime/malloc.c` にあった `persistentalloc` 関数が `src/pkg/runtime/malloc.go` に移行されました。`persistentalloc` は、Goランタイムの内部で永続的なデータ（型情報、デバッグ情報など）を割り当てるために使用される関数です。この関数をCからGoに移行することで、Goのメモリ管理の恩恵を受け、コードの保守性が向上します。
    *   `src/pkg/runtime/runtime.c` にあった `tickspersecond` 関数が `src/pkg/runtime/runtime.go` に移行されました。これは、CPUのティック数を秒単位で計算する関数で、プロファイリングなどに使用されます。
    *   `os_nacl.c`, `os_windows.c`, `signal_unix.c` にあった `os·sigpipe` 関数がそれぞれのGoファイル (`os_nacl.go`, `os_windows.go`, `signal_unix.go`) に移行されました。これは、SIGPIPEシグナル（クローズされたパイプへの書き込み時に発生）の処理に関するものです。

2.  **`onM` の活用**:
    *   GoルーチンがOSスレッド（M）のコンテキストで実行する必要がある操作（例：システムコール、プロファイリングの開始/停止、GCの停止/再開）に対して、`onM` 関数が積極的に導入されました。
    *   例えば、`setcpuprofilerate`, `GOMAXPROCS` (内部の `gomaxprocsfunc`), `stoptheworld`, `starttheworld`, `freemcache`, `setprofilebucket`, `semacreate`, `semasleep`, `syscall·runtime_BeforeFork`, `syscall·runtime_AfterFork` といった関数が、直接C関数を呼び出すのではなく、`_m` サフィックスを持つGo関数を定義し、それを `onM` 経由で呼び出すように変更されました。
    *   `onM` を使用することで、Goルーチンは一時的に現在のMに固定され、そのM上で安全に低レベルな操作を実行できます。これにより、Goルーチンが別のMに移動したり、スタックが切り替わったりする際に発生する可能性のある問題を回避できます。
    *   `g.m.scalararg` や `g.m.ptrarg` を使用して、`onM` 呼び出しを介して引数を渡すメカニズムが導入されています。これは、Goルーチン（G）が現在実行されているM（`g.m`）のフィールドを介して、`onM` で実行される関数にデータを渡すためのものです。

3.  **`#pragma textflag NOSPLIT` の適用**:
    *   非常にシンプルで低レベルな関数、またはスタック分割チェックが不要な関数に対して、`#pragma textflag NOSPLIT` が適用されました。これにより、これらの関数にはスタック分割チェックのコードが挿入されず、オーバーヘッドが削減されます。
    *   `runtime·semawakeup`, `runtime·semacreate` (内部の `semacreate`), `runtime·semasleep` (内部の `semasleep`), `runtime·mach_semrelease`, `runtime·gotraceback`, `runtime·gcount`, `os·sigpipe` (アセンブリのthunk) などに適用されています。
    *   特に、`runtime·mach_semrelease` のような関数は、シグナルハンドラなど、スタックの状況が予測しにくいコンテキストから呼び出される可能性があるため、`NOSPLIT` は重要です。

これらの変更により、GoランタイムはGoとCの間の境界をより明確にし、Goコードの比率を高め、低レベルな操作をより安全かつ効率的に実行できるようになりました。

### `persistentalloc` のCからGoへの移行

**変更前 (`src/pkg/runtime/malloc.c`)**:
```c

**変更後 (`src/pkg/runtime/malloc.go`)**:
```go
// Wrapper around sysAlloc that can allocate small chunks.
// There is no associated free operation.
// Intended for things like function/type/debug-related persistent data.
// If align is 0, uses default align (currently 8).
func persistentalloc(size, align uintptr, stat *uint64) unsafe.Pointer {
	const (
		chunk    = 256 << 10
		maxBlock = 64 << 10 // VM reservation granularity is 64K on windows
	)

	if align != 0 {
		if align&(align-1) != 0 {
			gothrow("persistentalloc: align is not a power of 2")
		}
		if align > _PageSize {
			gothrow("persistentalloc: align is too large")
		}
	} else {
		align = 8
	}

	if size >= maxBlock {
		return sysAlloc(size, stat)
	}

	lock(&persistent.lock)
	persistent.pos = roundup(persistent.pos, align)
	if uintptr(persistent.pos)+size > uintptr(persistent.end) {
		persistent.pos = sysAlloc(chunk, &memstats.other_sys)
		if persistent.pos == nil {
			unlock(&persistent.lock)
			gothrow("runtime: cannot allocate memory")
		}
		persistent.end = add(persistent.pos, chunk)
	}
	p := persistent.pos
	persistent.pos = add(persistent.pos, size)
	unlock(&persistent.lock)

	if stat != &memstats.other_sys {
		xadd64(stat, int64(size))
		xadd64(&memstats.other_sys, -int64(size))
	}
	return p
}
```
`persistentalloc` は、Goランタイムが内部的に使用する、解放されない永続的なメモリ領域を割り当てるための関数です。この関数がCからGoに完全に移行されたことは、GoランタイムのC依存性を減らし、Goのメモリ管理の原則に沿った実装を増やすという方向性を示しています。Goで実装することで、Goの型システムやツールチェインの恩恵を受けることができます。

### `onM` の導入例 (`setcpuprofilerate`)

**変更前 (`src/pkg/runtime/cpuprof.go`)**:
```go
func setcpuprofilerate(int32) // proc.c
```
この行は、`setcpuprofilerate` が `proc.c` で定義されたC関数であることを示しています。

**変更後 (`src/pkg/runtime/cpuprof.go`)**:
```go
func setcpuprofilerate_m() // proc.c

func setcpuprofilerate(hz int32) {
	g := getg()
	g.m.scalararg[0] = uintptr(hz)
	onM(setcpuprofilerate_m)
}
```
`setcpuprofilerate` は、直接C関数を呼び出す代わりに、`setcpuprofilerate_m` というGo関数を定義し、それを `onM` 経由で呼び出すようになりました。`hz` 引数は、現在のGoルーチン（`g`）が実行されているM（`g.m`）の `scalararg` フィールドを介して `setcpuprofilerate_m` に渡されます。これにより、CPUプロファイリングレートの設定というOSスレッドに依存する操作が、安全にMのコンテキストで実行されることが保証されます。

**変更後 (`src/pkg/runtime/debug.go`)**:

### `#pragma textflag NOSPLIT` の適用例 (`runtime·semacreate`)

**変更前 (`src/pkg/runtime/os_darwin.c`)**:

**変更後 (`src/pkg/runtime/os_darwin.c`)**:

	g->m->scalararg[0] = runtime·mach_semcreate();

runtime·semacreate(void)

	uintptr x;
	void (*fn)(void);
	
	fn = semacreate;
	runtime·onM(&fn);
	x = g->m->scalararg[0];
	g->m->scalararg[0] = 0;
	return x;

`runtime·semacreate` は、セマフォを作成する関数です。この関数自体には `NOSPLIT` が適用され、内部で `semacreate` というGo関数を `onM` 経由で呼び出しています。`NOSPLIT` は、この関数がスタック分割チェックなしで実行されることを保証し、低レベルなOS操作の効率性を高めます。

これらの変更は、GoランタイムがGoとCの間の境界をより厳密に管理し、GoルーチンとOSスレッドの間の相互作用をより安全かつ効率的に行うための重要なステップです。

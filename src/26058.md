# [インデックス 26058] ファイルの概要

このコミットは、Goコンパイラの内部処理、特に`cmd/compile`パッケージ内の`walk.go`ファイルにおける変更に関するものです。`walk.go`は、Goプログラムの抽象構文木（AST）を走査し、様々な変換や最適化を行うコンパイラの重要なフェーズの一部です。この変更は、マルチバリュー関数呼び出しの戻り値の処理に関連するデッドコードを削除し、代わりに内部的な整合性チェックのためのアサートを追加するものです。

## 元コミット内容

`cmd/compile: change dead code into assert`

このコミットは、Goコンパイラの`cmd/compile`パッケージにおいて、デッドコードをアサート（プログラムの前提条件が満たされていることを確認するチェック）に置き換えるものです。

## 変更の背景

この変更の背景には、以前のコミットで解決されたGoのIssue #13587があります。Issue #13587の修正後、コミットの作者は、`walk.go`内の「OAS2FUNC in disguise」と呼ばれるコードブロックが、ライトバリア（ガベージコレクションのためにポインタの書き込みを追跡するメカニズム）を必要とする可能性があると考えました。しかし、テストを行った結果、`return f()`のようなマルチバリュー関数呼び出しのケースは既に正しく処理されていることが判明しました。

さらに調査を進めたところ、この特定のコードブロックは実際にはデッドコードであることが明らかになりました。これは、`orderstmt`というコンパイラフェーズが、マルチバリュー関数`f()`が呼び出される`return f()`のようなステートメントを、`t1, t2, ..., tN := f(); return t1, t2, ..., tN`という形式に既に変換しているためです。つまり、`walk.go`内の当該ブロックが処理を行う前に、`orderstmt`が既に必要な変換を完了させていたため、そのブロックは実行されることがありませんでした。

この発見に基づき、デッドコードを削除し、代わりに`orderstmt`が期待通りに動作していることを確認するためのアサートを追加することで、コードの健全性を高め、将来的なバグの混入を防ぐことを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造と概念に関する知識が必要です。

1.  **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。複数のフェーズ（字句解析、構文解析、型チェック、AST変換、最適化、コード生成など）を経てコンパイルを行います。
2.  **抽象構文木 (AST)**: ソースコードの構造を木構造で表現したものです。コンパイラの各フェーズはこのASTを操作して、プログラムの意味を解析し、変換していきます。
3.  **`walk.go`と`walkstmt`関数**: `cmd/compile/internal/gc`パッケージに存在する`walk.go`ファイルは、ASTを走査（"walk"）し、様々な変換を行う役割を担っています。`walkstmt`関数は、ステートメント（文）レベルでのASTノードの走査と変換を担当します。このフェーズでは、高レベルなGoの構文を、より低レベルなコンパイラ内部表現に変換する作業が行われます。
4.  **`orderstmt`フェーズ**: `walk`フェーズの前に実行されるコンパイラフェーズの一つです。このフェーズの主な役割は、ステートメントの評価順序を決定し、複雑な式を複数の単純なステートメントに分解することです。特に、マルチバリュー関数呼び出し（複数の戻り値を返す関数）が`return`ステートメント内で使用される場合、`orderstmt`はこれを一時変数への代入と、その一時変数を使用した`return`ステートメントのシーケンスに変換します。例えば、`return f()`（`f`が複数の値を返す場合）は、`t1, t2 := f(); return t1, t2`のように変換されます。
5.  **`OAS2FUNC`ノード**: Goコンパイラ内部で、マルチバリュー関数呼び出しの結果を複数の変数に代入する操作を表すASTノードです。`orderstmt`フェーズによって生成されることがあります。
6.  **ライトバリア (Write Barriers)**: ガベージコレクタ（GC）が正確に動作するために必要なメカニズムです。GoのGCは並行（concurrent）かつ低遅延（low-latency）で動作するため、GCがオブジェクトを移動している最中にプログラムがポインタを書き換える可能性があります。ライトバリアは、このようなポインタの書き込み操作をGCに通知し、GCがオブジェクトグラフの一貫性を維持できるようにします。特に、ポインタを含む構造体や配列がヒープに書き込まれる際に重要になります。
7.  **`Fatalf`**: Goコンパイラ内部で使用されるパニック関数の一つで、回復不能な内部エラーが発生した場合にプログラムを終了させます。これは、コンパイラの前提条件が満たされていないことを示すために使用されます。

## 技術的詳細

このコミットの核心は、Goコンパイラの`walk`フェーズにおける`return`ステートメントの処理の最適化と堅牢化にあります。

変更前のコードには、`OAS2FUNC in disguise`とコメントされたブロックがありました。このブロックは、`return f()`のような形式で、`f()`が複数の値を返す場合に、単一の式が実際には複数の戻り値を伴う関数呼び出しである状況を特別に処理しようとしていました。具体的には、`n.List`（`return`ステートメントの引数リスト）の要素数が1で、`rl`（関数の戻り値の型リスト）の要素数が1より大きい場合に、`f`が関数呼び出しであることを確認し、`n.List`を`f`の呼び出しと、その戻り値を`rl`の型に合わせて変換する`ascompatet`の結果と連結していました。これは、`return f()`を`return t1, t2, ...`のような形式に変換する意図があったと考えられます。

しかし、コミットメッセージが説明するように、`walk`フェーズの前に実行される`orderstmt`フェーズが既にこの変換を処理していました。`orderstmt`は、`return f()`（`f`がマルチバリュー関数）を、`t1, t2, ..., tN := f(); return t1, t2, ..., tN`という中間的なステートメントに変換します。この変換が行われると、`walkstmt`が`return`ステートメントを処理する時点では、`n.List`は既に複数の要素（`t1, t2, ..., tN`）を持つことになり、変更前の`OAS2FUNC in disguise`ブロックの条件（`count(n.List) == 1`）は満たされなくなります。したがって、このブロックは決して実行されないデッドコードとなっていました。

このデッドコードを削除し、代わりに新しいアサートが追加されました。このアサートは、`return`ステートメントの引数リスト`n.List`の要素数と、関数の戻り値の型リスト`rl`の要素数が一致することを検証します。もし一致しない場合、それは`orderstmt`がマルチバリュー関数呼び出しを期待通りに`OAS2FUNC`ノード（またはそれに相当する複数の代入ステートメント）に変換しなかったことを意味し、コンパイラの内部的な不整合を示します。このような状況はコンパイラのバグであるため、`Fatalf`を呼び出してプログラムを終了させます。

この変更により、コンパイラのコードベースはよりクリーンになり、デッドコードが削除されました。また、`orderstmt`フェーズの動作に対する暗黙の前提が明示的なアサートとしてコードに組み込まれたことで、将来的に`orderstmt`の動作が変更された際に、このアサートが早期に問題を検出するセーフティネットとしての役割を果たすことになります。

## コアとなるコードの解説

削除されたコードブロックは、`return f()`のような形式で、`f()`が複数の値を返す場合に、`walkstmt`がその変換を試みるものでした。しかし、`orderstmt`フェーズが既にこの変換を完了させているため、このブロックは不要でした。

新しく追加されたアサートは、`walkstmt`が`return`ステートメントを処理する際に、`return`される引数の数と、関数が期待する戻り値の数が一致していることを確認します。

```go
if got, want := count(n.List), count(rl); got != want {
    // order should have rewritten multi-value function calls
    // with explicit OAS2FUNC nodes.
    Fatalf("expected %v return arguments, have %v", want, got)
}
```

*   `n.List`: 現在処理中の`return`ステートメントの引数リスト（ASTノードのリスト）。
*   `rl`: 現在の関数が返す戻り値の型リスト。
*   `count(list)`: リストの要素数を返すヘルパー関数。

このアサートは、「`orderstmt`はマルチバリュー関数呼び出しを明示的な`OAS2FUNC`ノード（または同等の複数の代入）で書き換えているはずだ」というコンパイラの内部的な不変条件を強制します。もし`got`と`want`が一致しない場合、それは`orderstmt`がその役割を正しく果たさなかったことを意味し、コンパイラの内部エラーとして`Fatalf`が呼び出されます。これにより、コンパイラの整合性が保たれ、予期せぬ動作やバグが早期に検出されるようになります。

# [インデックス 25706] ファイルの概要

このコミットは、Goランタイムのメモリ管理において、32ビットシステムでのアリーナ（メモリ領域）の拡張時に発生しうる整数オーバーフローの問題に対する堅牢性を向上させるものです。具体的には、`arena_end + size` の計算がオーバーフローする可能性を明示的にチェックすることで、不正なメモリ割り当て要求がシステムコールに渡されることを防ぎ、より安全で予測可能なメモリ管理を実現します。

## コミット

```
runtime: check for updated arena_end overflow

Currently, if an allocation is large enough that arena_end + size
overflows (which is not hard to do on 32-bit), we go ahead and call
sysReserve with the impossible base and length and depend on this to
either directly fail because the kernel can't possibly fulfill the
requested mapping (causing mheap.sysAssoc to return nil) or to succeed
with a mapping at some other address which will then be rejected as
outside the arena.

In order to make this less subtle, less dependent on the kernel
getting all of this right, and to eliminate the hopeless system call,
add an explicit overflow check.

Updates #13143. This real issue has been fixed by 0de59c2, but this is
a belt-and-suspenders improvement on top of that. It was uncovered by
my symbolic modeling of that bug.
```

## 変更の背景

このコミットは、Goランタイムのメモリ管理における潜在的な脆弱性に対処するために導入されました。特に32ビットシステムにおいて、メモリ領域（アリーナ）の拡張を試みる際に、`arena_end`（現在のアリーナの終端アドレス）に要求されたサイズ `p_size` を加算した結果が整数オーバーフローを起こす可能性がありました。

元の実装では、このオーバーフローが発生した場合、`sysReserve`というシステムコールが不可能（存在しない）なアドレスと長さを指定して呼び出されていました。この状況では、以下のいずれかの結果に依存していました。
1.  カーネルが要求されたマッピングを物理的に満たせないため、`sysReserve`が直接失敗し、`mheap.sysAlloc`が`nil`を返す。
2.  カーネルが別の有効なアドレスにマッピングを成功させるが、そのアドレスが既存のアリーナの範囲外であるため、後で拒否される。

この挙動は、カーネルの動作に過度に依存しており、微妙で予測が難しいものでした。また、最終的に失敗する可能性が高い「絶望的な」システムコールを無駄に発行することにもなります。

このコミットは、Issue #13143に関連しています。Issue #13143の根本的な問題は、コミット `0de59c2` によって既に修正されています。`0de59c2`では、`mheap.sysAlloc`が`sysReserve`によって返されたアドレスが`arena_start`よりも低い場合に、アリーナポインタが破損するのを防ぐためのチェックが追加されました。具体的には、32ビットシステムで`sysReserve`が`MAP_FIXED`なしで`mmap`を使用し、既存の`arena_start`より低いアドレスを返す可能性があり、これが`arena_end`と`arena_used`の不正な更新を引き起こし、最終的にクラッシュにつながる問題でした。

今回のコミット `f9357cdec1235168590283abe027e501633755a5` は、`0de59c2`による修正の上に、さらに「念には念を入れた（belt-and-suspenders）」改善として位置づけられています。これは、`arena_end + p_size`の計算における明示的なオーバーフローチェックを追加することで、メモリ割り当ての堅牢性をさらに高めることを目的としています。この改善は、元のバグのシンボリックモデリングの過程で発見されたものです。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

*   **Goランタイムのメモリ管理**: Goランタイムは独自のメモリ管理システム（ヒープアリーナ）を持っています。これはOSから大きなメモリブロックを予約し、その中でGoのオブジェクトを効率的に割り当て・解放します。
*   **アリーナ (Arena)**: Goランタイムが管理する連続した仮想メモリ領域のことです。`arena_start`はその開始アドレス、`arena_end`はその終端アドレスを示します。
*   **`mheap`**: Goランタイムのヒープマネージャを表す構造体です。メモリの割り当て、解放、アリーナの管理などを行います。
*   **`sysAlloc`**: `mheap`のメソッドの一つで、OSから新しいメモリ領域をシステムコール（`sysReserve`など）を使って予約・コミットする役割を担います。
*   **`sysReserve`**: OSの機能（Linuxでは`mmap`など）を呼び出して、仮想メモリ空間を予約する（ただし、物理メモリはまだ割り当てない）ためのGoランタイムの抽象化された関数です。
*   **32ビットシステムのアドレス空間**: 32ビットシステムでは、仮想アドレス空間が最大4GBに制限されます。これにより、`uintptr`などのポインタ型やサイズを表す型が32ビット幅となり、大きな数値を扱う際に比較的容易に整数オーバーフローが発生する可能性があります。
*   **整数オーバーフロー**: 符号なし整数型で表現できる最大値を超えた場合に、値がゼロに戻ったり、予期しない小さな値になったりする現象です。例えば、32ビットの`uintptr`で`0xFFFFFFFF`に`1`を加算すると`0x00000000`になります。メモリ管理において、アドレス計算でオーバーフローが発生すると、全く異なる、不正なメモリ領域を指すことになり、セキュリティ脆弱性やクラッシュの原因となります。
*   **`uintptr`**: Go言語におけるポインタを保持できる整数型です。そのサイズはシステムのアドレス空間のサイズ（32ビットまたは64ビット）に依存します。

## 技術的詳細

このコミットの技術的な核心は、32ビットシステムにおける`uintptr`型の整数オーバーフローの危険性に対処することです。

`mheap.sysAlloc`関数内で、新しいメモリ領域を予約する際に、現在のアリーナの終端`h.arena_end`に要求されるサイズ`p_size`を加算して、新しいアリーナの終端`new_end`を計算します。
`new_end := h.arena_end + p_size`

32ビットシステムでは、`h.arena_end`と`p_size`がそれぞれ大きな値を取る場合、この加算が32ビットの最大値を超えてしまい、`new_end`が実際よりも小さな値（オーバーフローした結果）になる可能性があります。

元のコードでは、この`new_end`を使って`if new_end <= h.arena_start+_MaxArena32`という条件で、新しいアリーナの終端が許容範囲内にあるかをチェックしていました。しかし、`new_end`がオーバーフローしている場合、このチェックは誤った結果を導き出す可能性があります。例えば、`h.arena_end`が`0xFFFFFFF0`で`p_size`が`0x20`の場合、`new_end`はオーバーフローして`0x00000010`のような小さな値になります。この小さな`new_end`は`h.arena_start`よりも小さくなるため、条件式が真となり、不正な`new_end`が`sysReserve`に渡されてしまうことになります。

このコミットは、このオーバーフローの可能性を明示的に考慮したチェックを追加します。新しい条件式は以下のようになります。
`if h.arena_end <= new_end && new_end <= h.arena_start+_MaxArena32`

この変更により、以下の2つの条件が満たされる必要があります。
1.  `h.arena_end <= new_end`: これは、`new_end`が`h.arena_end`よりも小さくなっていないか（つまり、オーバーフローしていないか）をチェックします。もしオーバーフローしていれば、`new_end`は`h.arena_end`よりも小さな値になるため、この条件は偽となり、不正な`new_end`が使用されるのを防ぎます。
2.  `new_end <= h.arena_start+_MaxArena32`: これは、オーバーフローが発生していない`new_end`が、アリーナの最大許容範囲内にあるかをチェックします。

この二重チェックにより、`new_end`の計算がオーバーフローした場合でも、その不正な値が後続の処理（特に`sysReserve`の呼び出し）に渡される前に検出され、適切なエラー処理（`mheap.sysAlloc`が`nil`を返す）が行われるようになります。これにより、カーネルの挙動に依存することなく、Goランタイム自身がメモリ割り当ての健全性を保証できるようになります。

## コアとなるコードの解説

変更された行は、`mheap.sysAlloc`関数内で新しいアリーナの終端を計算し、その有効性をチェックする部分です。

1.  **`new_end := h.arena_end + p_size // Careful: can overflow`**:
    この行は、新しいアリーナの終端アドレス`new_end`を計算しています。`h.arena_end`は現在のアリーナの終端、`p_size`は新しく予約しようとしているメモリのサイズです。コメント`// Careful: can overflow`が追加され、この加算がオーバーフローする可能性があることを明示的に警告しています。これは、特に32ビットシステムで`uintptr`が32ビット幅である場合に重要です。

2.  **`if h.arena_end <= new_end && new_end <= h.arena_start+_MaxArena32 {`**:
    この`if`文の条件式が変更の核心です。
    *   **`h.arena_end <= new_end`**: この部分が追加されたオーバーフローチェックです。もし`h.arena_end + p_size`の計算がオーバーフローした場合、`new_end`は`h.arena_end`よりも小さな値になります（例: `0xFFFFFFF0 + 0x20`が`0x00000010`になる）。この条件は、`new_end`が`h.arena_end`よりも小さくなっていないこと、つまりオーバーフローが発生していないことを確認します。もしオーバーフローしていれば、この条件は偽となり、`if`ブロック内のコードは実行されません。
    *   **`new_end <= h.arena_start+_MaxArena32`**: これは元の条件式であり、オーバーフローが発生していないと仮定した場合に、計算された`new_end`がアリーナの最大許容範囲（`h.arena_start`から`_MaxArena32`の範囲）を超えていないかをチェックします。

この二つの条件を`&&`（論理AND）で結合することで、`new_end`がオーバーフローしておらず、かつ、有効なアリーナ範囲内にある場合にのみ、`if`ブロック内のメモリ予約処理が続行されるようになります。これにより、不正なアドレス計算が原因でシステムコールが失敗したり、ランタイムが不安定になったりするリスクが大幅に低減されます。

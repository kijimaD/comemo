# [インデックス 27039] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおける最適化ルールに関する変更です。具体的には、`AND`演算と定数を用いたビットマスク操作をシフト演算の組み合わせに書き換える最適化において、その適用条件を調整しています。32ビットオペランドに対する特定の最適化ルールが削除され、64ビットオペランドに対するルールには新たな条件が追加されました。これにより、特定のケースでのパフォーマンス低下を防ぎ、他の重要な最適化（境界チェック除去など）との競合を回避することを目的としています。

## コミット

`cmd/compile`: 小さな定数に対する`&-to-<<>>`最適化をガードする

定数Kが1バイト引数に収まるような`AND-K`をシフトペアに変換することは、おそらく最適化にはならず、また、`(<< (AND K))` [小さなKの場合] のような他の発火させたいパターンや、マスクされたインデックスに対する境界チェック除去とも干渉する。

Intelアーキテクチャでは、32ビット符号付き即値でさえシフトペアよりも優れていることが判明した。ツールバイナリのサイズ削減は、8ビット即値のみの場合の0.07%に対し、0.09%である。

RLHが新しい/次期GCに取り組んでいる際にこれを発見した。

## 変更の背景

この変更の背景には、GoコンパイラのSSAバックエンドにおける最適化のトレードオフと、特定のアーキテクチャ（特にIntel）での命令コストに関する深い理解があります。

元々、Goコンパイラは、`x & K` のようなビットマスク操作を、特定の定数 `K` の場合に `(x << shift1) >> shift2` のようなシフト演算の組み合わせに書き換える最適化を行っていました。これは、一部のCPUアーキテクチャや特定の状況下で、`AND`命令よりもシフト命令のペアの方が高速に実行できる可能性があるためです。

しかし、このコミットでは、以下の問題点が指摘されています。

1.  **小さな定数に対する非効率性**: 定数 `K` が小さい場合（特に1バイト引数に収まるような場合）、`AND`命令は非常に効率的です。これを2つのシフト命令に分解することは、命令数が増え、レジスタの使用が増えるなど、かえってパフォーマンスを低下させる可能性がありました。コミットメッセージでは「おそらく最適化にはならない」と述べられています。
2.  **他の最適化との干渉**: この`&-to-<<>>`最適化が、コンパイラが発火させたい他の重要な最適化パターンと干渉することが判明しました。具体的には、`(<< (AND K))` のようなパターン（小さなKの場合）や、配列アクセスにおけるマスクされたインデックスに対する境界チェック除去（Bounds Check Elimination, BCE）が挙げられています。BCEは、配列アクセスが常に有効な範囲内で行われることをコンパイラが証明できる場合に、実行時の境界チェックを省略することでパフォーマンスを向上させる重要な最適化です。`AND`操作がシフトに書き換えられることで、コンパイラがインデックスの範囲を正確に推論できなくなり、BCEが適用されなくなる可能性がありました。
3.  **Intelアーキテクチャでの検証**: コミットメッセージによると、Intelアーキテクチャでは、32ビットの符号付き即値（immediate value）を用いた`AND`命令が、シフトペアよりも高速であることが確認されました。これは、Intel CPUが即値オペランドを効率的に処理できるためと考えられます。ツールバイナリのサイズ削減効果も、8ビット即値のみの場合の0.07%に対して、シフト最適化を適用しない方が0.09%とわずかに改善されることが示されており、この最適化が逆効果であったことを裏付けています。

これらの理由から、コンパイラはより賢く最適化を適用する必要があるという結論に至り、小さな定数に対する`&-to-<<>>`最適化を抑制する変更が導入されました。

## 前提知識の解説

### GoコンパイラのSSA形式

Goコンパイラは、ソースコードを中間表現（IR）に変換する際に、SSA（Static Single Assignment）形式を採用しています。SSA形式では、各変数が一度だけ代入されるという特性を持ち、これによりデータフロー解析や最適化が容易になります。Goコンパイラのバックエンドは、このSSA形式のIRに対して様々な最適化パスを適用し、最終的に機械語コードを生成します。

### `cmd/compile` の役割

`cmd/compile` はGo言語の公式コンパイラです。Goのソースコードを解析し、抽象構文木（AST）を構築し、SSA形式に変換し、最適化を行い、最終的に実行可能なバイナリを生成する一連のプロセスを担います。このコミットで変更されているファイルは、SSAバックエンドにおける最適化ルールを定義する部分に属します。

### ビット演算子 `AND` とシフト演算子 `<<`, `>>`

*   **`AND` (`&`)**: ビットごとの論理積を計算します。特定のビットをマスク（抽出またはクリア）する際によく使用されます。例えば、`x & 0xFF` は `x` の下位8ビットを抽出します。
*   **左シフト (`<<`)**: ビットを左に移動させます。左に1ビットシフトするごとに値は2倍になります。
*   **右シフト (`>>`)**: ビットを右に移動させます。符号なし右シフト (`>>>` に相当するもの、Goでは単に `>>` が論理右シフトとして機能することが多い) は、左から0を埋めます。符号付き右シフトは、左から符号ビットを埋めます。Goの整数型に対する `>>` は、符号なし整数では論理右シフト、符号付き整数では算術右シフトとして機能します。

### `nlz`, `nto`, `nlo`, `ntz` の概念

これらは、数値のビットパターンに関する情報を取得する関数です。GoコンパイラのSSAバックエンドの最適化ルールで、定数のビットパターンを分析するために使用されます。

*   **`nlz(x)` (Number of Leading Zeros)**: `x` の最上位ビットから見て、最初に1が現れるまでの0の数。例えば、32ビット整数 `00000000_00000000_00000000_00001011` (11) の `nlz` は28です。
*   **`nto(x)` (Number of Trailing Ones)**: `x` の最下位ビットから見て、最初に0が現れるまでの1の数。例えば、`...0111` の `nto` は3です。
*   **`nlo(x)` (Number of Leading Ones)**: `x` の最上位ビットから見て、最初に0が現れるまでの1の数。例えば、`11110...` の `nlo` は4です。
*   **`ntz(x)` (Number of Trailing Zeros)**: `x` の最下位ビットから見て、最初に1が現れるまでの0の数。例えば、`...1000` の `ntz` は3です。

これらの関数は、定数 `K` が特定のビットマスクパターン（例えば、連続する1のブロックや、特定のビット範囲のみがセットされているなど）を持っているかどうかを効率的に判断するために使われます。

### コンパイラの最適化におけるコストモデル

コンパイラは、コードを最適化する際に、様々な要因を考慮して「コストモデル」に基づいた判断を行います。これには以下のような要素が含まれます。

*   **命令数**: 実行される機械語命令の数。少ない方が一般的に良い。
*   **命令の種類**: 各命令の実行サイクル数。例えば、`AND`は通常1サイクルで実行されますが、シフト命令のペアは2サイクルかかる可能性があります。
*   **レジスタ使用量**: 命令が使用するレジスタの数。レジスタが不足すると、メモリへのスピル/フィルが発生し、パフォーマンスが低下します。
*   **パイプライン**: CPUの命令パイプラインにおけるハザード（依存関係による停止）の可能性。
*   **キャッシュ**: メモリアクセスがキャッシュヒットするかどうか。
*   **コードサイズ**: 生成される機械語コードのサイズ。小さい方がキャッシュ効率が良い場合があります。

このコミットでは、特に命令の種類と命令数、そして他の最適化との干渉が考慮されています。

### 境界チェック除去 (Bounds Check Elimination, BCE)

Go言語はメモリ安全性を重視しており、配列やスライスへのアクセス時には常にインデックスが有効な範囲内にあるかどうかの境界チェックが行われます。しかし、コンパイラが静的にインデックスが常に有効であることを証明できる場合、この実行時チェックを省略することができます。これが境界チェック除去です。

例えば、`for i := 0; i < len(s); i++ { s[i] = ... }` のようなループでは、コンパイラは `s[i]` へのアクセスが常に有効であることを推論できるため、境界チェックを省略できます。

`x & K` のようなマスク操作がシフトペアに書き換えられると、コンパイラがインデックスの範囲を正確に分析することが難しくなり、結果としてBCEが適用されなくなる可能性があります。BCEは非常に効果的な最適化であるため、これと干渉するような最適化は慎重に適用する必要があります。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおける`AND`演算の最適化ルール、特に定数との`AND`をシフト演算の組み合わせに変換するルールを修正しています。

### `AND`をシフトに変換する最適化の原理

特定の定数 `K` との `AND` 演算 `x & K` は、`K` のビットパターンが連続する1のブロックである場合、シフト演算の組み合わせで表現できます。

例えば、`x & 0x00FF0000` (32ビット整数で、ビット16から23までが1) のようなマスクは、以下のように表現できます。

1.  `x` を右に16ビットシフトして、目的のビットブロックを最下位に移動させる: `x >> 16`
2.  結果を左に16ビットシフトして、元の位置に戻す: `(x >> 16) << 16`

これは、`K` が `(1 << N) - (1 << M)` の形式で表現できる場合（つまり、連続する1のブロックである場合）に有効です。

この最適化は、`nlz(y) + nto(y) == 64` または `nlo(y) + ntz(y) == 64` という条件で識別されます。

*   `nlz(y) + nto(y) == 64`: これは、64ビット整数 `y` が、最上位ビットから連続する0のブロックがあり、その後に連続する1のブロックが続き、残りがすべて0であるパターン（例: `00...011...100...0`）であることを意味します。この場合、`y` は `(1 << N) - 1` の形式のマスクをシフトした形になります。
*   `nlo(y) + ntz(y) == 64`: これは、64ビット整数 `y` が、最上位ビットから連続する1のブロックがあり、その後に連続する0のブロックが続き、残りがすべて1であるパターン（例: `11...100...011...1`）であることを意味します。

これらの条件が満たされる場合、`AND`演算は2つのシフト演算に書き換えられます。

### 変更点と理由

1.  **32ビットオペランドに対するルールの削除**:
    `src/cmd/compile/internal/ssa/rewritegeneric.go` から、`OpAnd32` に対する2つの書き換えルールが完全に削除されました。
    これらのルールは、32ビット定数 `y` との `AND` 演算をシフトペアに変換するものでした。
    コミットメッセージによると、Intelアーキテクチャでは32ビットの即値`AND`がシフトペアよりも高速であり、この最適化は逆効果であったため削除されました。また、他の最適化との干渉も理由として挙げられています。

2.  **64ビットオペランドに対するルールの条件追加**:
    `src/cmd/compile/internal/ssa/gen/generic.rules` および `src/cmd/compile/internal/ssa/rewritegeneric.go` の `OpAnd64` に対する書き換えルールに、新たな条件が追加されました。
    *   `nlz(y) + nto(y) == 64` のルールに `&& nto(y) >= 32` が追加。
    *   `nlo(y) + ntz(y) == 64` のルールに `&& ntz(y) >= 32` が追加。

    この追加条件 `nto(y) >= 32` および `ntz(y) >= 32` は、定数 `y` のビットマスクが少なくとも32ビット幅の連続する1または0のブロックを持つ場合にのみ、シフト最適化を適用することを意味します。
    これは、マスクが「十分に大きい」場合にのみシフト最適化が有益であるという判断に基づいています。マスクが小さい場合（例えば、下位8ビットのみをマスクする `0xFF` のような場合）、`AND`命令の方が効率的であるため、この最適化を抑制します。特に、32ビット幅未満のマスクは、32ビット即値`AND`の方が優れているというIntelアーキテクチャでの知見が反映されています。

この変更により、コンパイラはより選択的に`&-to-<<>>`最適化を適用し、パフォーマンスの向上ではなく低下を招くケースや、他の重要な最適化を妨げるケースを回避できるようになります。

## コアとなるコードの解説

### `generic.rules` の構文

`generic.rules` ファイルは、GoコンパイラのSSAバックエンドが使用するパターンマッチングと書き換えルールを定義するためのDSL（Domain Specific Language）です。

*   `match: (Op <type> args...)` : マッチさせたいSSAオペレーションのパターンを定義します。
    *   `Op`: オペレーションの種類（例: `And32`, `And64`, `Const32`, `Lsh64x64` など）。
    *   `<type>`: オペレーションの結果の型。
    *   `args...`: オペレーションの引数。
    *   `[y]`: 定数値を表す。
    *   `x`: 変数を表す。
*   `cond: condition` : パターンがマッチした場合に、さらに適用される条件式です。Goの式で記述されます。
    *   `nlz(y)`, `nto(y)`, `nlo(y)`, `ntz(y)`: 前述のビットパターン分析関数。
*   `result: (Op <type> args...)` : 条件が満たされた場合に、元のオペレーションが書き換えられる新しいSSAオペレーションのパターンを定義します。

### 変更されたルールの意味

#### 削除された32ビットルール

削除されたルールは、以下のようなパターンをシフトペアに変換していました。

```
(And32 <t> (Const32 [y]) x) && nlz(int64(int32(y))) + nto(int64(int32(y))) == 64 -> (Rsh32Ux32 (Lsh32x64 <t> x (Const32 <t> [nlz(int64(int32(y)))-32])) (Const32 <t> [nlz(int64(int32(y)))-32]))
(And32 <t> (Const32 [y]) x) && nlo(int64(int32(y))) + ntz(int64(int32(y))) == 64 -> (Lsh32x32 (Rsh32Ux32 <t> x (Const32 <t> [ntz(int64(int32(y)))])) (Const32 <t> [ntz(int64(int32(y)))]))
```

これらのルールは、32ビットの定数 `y` との `AND` 演算を、`nlz` や `nto`、`nlo`、`ntz` の結果に基づいて2つのシフト演算に書き換えるものでした。しかし、コミットメッセージで述べられているように、32ビットオペランド、特に小さな定数に対しては、この最適化はパフォーマンス上の利点がないか、むしろ悪影響を及ぼすことが判明したため、完全に削除されました。

#### 変更された64ビットルール

変更された64ビットルールは以下のようになります。

**元のルール:**
`(And64 <t> (Const64 [y]) x) && nlz(y) + nto(y) == 64 -> (Rsh64Ux64 (Lsh64x64 <t> x (Const64 <t> [nlz(y)])) (Const64 <t> [nlz(y)]))`

**変更後のルール:**
`(And64 <t> (Const64 [y]) x) && nlz(y) + nto(y) == 64 && nto(y) >= 32 -> (Rsh64Ux64 (Lsh64x64 <t> x (Const64 <t> [nlz(y)])) (Const64 <t> [nlz(y)]))`

そして、もう一つのルールも同様に：

**元のルール:**
`(And64 <t> (Const64 [y]) x) && nlo(y) + ntz(y) == 64 -> (Lsh64x64 (Rsh64Ux64 <t> x (Const64 <t> [ntz(y)])) (Const64 <t> [ntz(y)]))`

**変更後のルール:**
`(And64 <t> (Const64 [y]) x) && nlo(y) + ntz(y) == 64 && ntz(y) >= 32 -> (Lsh64x64 (Rsh64Ux64 <t> x (Const64 <t> [ntz(y)])) (Const64 <t> [ntz(y)]))`

追加された条件 `nto(y) >= 32` および `ntz(y) >= 32` は、定数 `y` が表すビットマスクが、少なくとも32ビット幅の連続する1または0のブロックを持つ場合にのみ、このシフト最適化を適用することを強制します。

*   `nlz(y) + nto(y) == 64` は、`y` が `0...01...10...0` の形式であることを意味します。`nto(y)` は末尾の1の数です。`nto(y) >= 32` は、この連続する1のブロックが少なくとも32ビット幅であることを要求します。
*   `nlo(y) + ntz(y) == 64` は、`y` が `1...10...01...1` の形式であることを意味します。`ntz(y)` は末尾の0の数です。`ntz(y) >= 32` は、この連続する0のブロックが少なくとも32ビット幅であることを要求します。

この条件により、マスクが小さい（32ビット未満）場合には、`AND`演算がシフトペアに書き換えられることを防ぎます。これは、小さなマスクの場合には`AND`命令の方が効率的であるという知見に基づいています。特に、32ビットの即値`AND`がシフトペアよりも優れているというIntelアーキテクチャでの発見が、この条件の導入を後押ししています。

### `rewritegeneric.go` の役割

`rewritegeneric.go` は、`generic.rules` ファイルを元に `go generate` コマンドによって自動生成されるGoのソースコードです。このファイルには、`rewriteValuegeneric_OpAnd32` や `rewriteValuegeneric_OpAnd64` のような関数が含まれており、SSA形式の各オペレーションに対して、定義されたルールに基づいて書き換え処理を実行します。

このコミットでは、`generic.rules` の変更が `rewritegeneric.go` に反映され、32ビットの`AND`最適化ロジックが削除され、64ビットの`AND`最適化ロジックの条件が更新されています。これにより、コンパイラの実行時にこれらの新しいルールが適用されるようになります。

## 変更の背景

この変更の背景には、Goプロジェクトの開発ワークフローにおけるMercurial (hg) の利用と、新しい開発ブランチを作成する際の効率化があります。

Goプロジェクトでは、コードの変更は「変更リスト (Change List, CL)」として提出され、レビューを経てリポジトリにコミットされます。このプロセスには、Mercurialのコマンドと、それを補助するカスタムスクリプト（`codereview.py`など）が使用されていました。

従来のワークフローでは、新しい開発ブランチ（例えば、Goの次のメジャーバージョンに向けたブランチ）を作成し、そのブランチに最初のコミットを行う際に、`hg submit` コマンドが新しいヘッド（ブランチ）の作成を検出し、エラーとして処理してしまう可能性がありました。これは、通常、開発者が古いリビジョンに基づいて作業しており、リポジトリが最新の状態でない場合に発生する「新しいヘッドの作成」とは異なる状況です。

コミットメッセージにある「This means I won't have to edit the plugin when I create the next dev branch.」という記述から、新しい開発ブランチを作成するたびに、この`codereview.py`スクリプトを手動で修正する必要があったことが示唆されます。この手動での修正作業をなくし、新しいブランチの作成をよりスムーズに行えるようにするために、この変更が導入されました。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

### Mercurial (hg)

Mercurialは、Gitと同様の分散型バージョン管理システム (DVCS) です。主な概念は以下の通りです。

*   **リポジトリ**: プロジェクトの全履歴とファイルが保存されている場所。
*   **コミット**: リポジトリへの変更の記録。各コミットは一意のハッシュで識別されます。
*   **ヘッド (Heads)**: ブランチの先端にあるコミット。複数のヘッドが存在する場合、それは複数の開発ライン（ブランチ）が存在することを示します。
*   **ブランチ (Branches)**: 開発の分岐。Mercurialには名前付きブランチと匿名ブランチの概念があります。この文脈では、新しい開発ラインを指すことが多いです。
*   **`hg submit`**: GoプロジェクトでカスタムされたMercurialコマンドで、変更リストをレビューシステムに提出し、承認後にリポジトリにコミットする役割を担います。
*   **`hg push`**: ローカルリポジトリの変更をリモートリポジトリに送信するコマンド。新しいヘッドをリモートにプッシュしようとすると、通常は警告またはエラーが発生し、ユーザーにマージを促します。これは、意図しない分岐を防ぐための安全機構です。

### Goプロジェクトのコードレビューシステム

Goプロジェクトでは、Gerritベースのコードレビューシステムが使用されています。開発者は変更をMercurialリポジトリにコミットする前に、Gerritを通じてレビューを受けます。`codereview.py`のようなスクリプトは、このレビュープロセスとMercurial操作を統合し、開発者がスムーズに作業できるようにするためのツールです。

### `codereview.py`

`codereview.py`は、GoプロジェクトのMercurialベースのコードレビューワークフローをサポートするPythonスクリプトです。`hg submit`コマンドの内部で呼び出され、変更リストの準備、レビューシステムとの連携、そして最終的なリポジトリへのコミットとプッシュを処理します。このスクリプトは、リポジトリの状態（例えば、新しいヘッドが作成されたかどうか）をチェックし、必要に応じて警告やエラーを出すことで、リポジトリの整合性を保つ役割も果たします。

## 技術的詳細

このコミットは、`lib/codereview/codereview.py` ファイル内の `submit` 関数におけるMercurialのプッシュ操作のロジックを変更しています。具体的には、コミットメッセージ（変更リストの記述）に特定の文字列が含まれている場合に、新しいブランチの作成を許可するように動作を調整しています。

変更点は2箇所です。

1.  **新しいヘッドの検出ロジックの変更**:
    変更前:
    ```python
    if old_heads != new_heads and not (old_heads == 0 and new_heads == 1):
    ```
    変更後:
    ```python
    if cl.desc.find("create new branch") < 0 and old_heads != new_heads and not (old_heads == 0 and new_heads == 1):
    ```
    この変更は、`hg submit` が新しいヘッド（ブランチ）の作成を検出した際に、それがエラーであると判断する条件を緩和しています。具体的には、変更リスト (`cl.desc`) の記述に `"create new branch"` という文字列が含まれていない場合にのみ、新しいヘッドの作成を問題視するようになりました。
    *   `old_heads` と `new_heads` は、プッシュ操作の前後でのリポジトリのヘッドの数を表します。
    *   `old_heads == 0 and new_heads == 1` は、空のリポジトリに最初のコミットを行うケースを特別に扱っています。
    *   `cl.desc.find("create new branch") < 0` は、変更リストの記述に `"create new branch"` という文字列が見つからない場合に `True` となります。つまり、この文字列が見つかった場合は、この条件全体が `False` となり、`need_sync()`（同期を促すエラー）が呼び出されなくなります。

2.  **`hg_push` 関数の呼び出しの変更**:
    変更前:
    ```python
    if hg_push(ui, repo):
    ```
    変更後:
    ```python
    if hg_push(ui, repo, new_branch=cl.desc.find("create new branch")>=0):
    ```
    この変更は、`hg_push` 関数に `new_branch` という新しい引数を渡すようにしています。この引数は、変更リストの記述に `"create new branch"` という文字列が含まれている場合に `True` となります (`cl.desc.find("create new branch") >= 0` は、文字列が見つかった場合に `True` を返します)。
    `hg_push` 関数は、この `new_branch` 引数を受け取ることで、新しいブランチの作成を意図したプッシュであることを認識し、それに応じた内部処理（例えば、Mercurialのプッシュコマンドに適切なオプションを渡すなど）を行うことができるようになります。これにより、通常はエラーとなる新しいヘッドのプッシュが、特定の条件下で許可されるようになります。

これらの変更により、開発者が新しい開発ブランチを作成する際に、変更リストの記述に特定のフレーズを含めることで、`hg submit` がその操作を正しく認識し、エラーを発生させることなく新しいブランチへのコミットとプッシュを完了できるようになります。これにより、手動でのスクリプト修正が不要になり、ワークフローが簡素化されます。

## コアとなるコードの解説

このコミットのコアとなる変更は、`codereview.py` の `submit` 関数内の2行です。

1.  **`if cl.desc.find("create new branch") < 0 and old_heads != new_heads and not (old_heads == 0 and new_heads == 1):`**
    *   この行は、`hg submit` がリモートリポジトリにプッシュする前に、ローカルリポジトリのヘッドの状態をチェックする部分です。
    *   `old_heads` はプッシュ前のヘッドの数、`new_heads` はプッシュ後のヘッドの数を表します。
    *   `old_heads != new_heads` は、ヘッドの数に変化があったことを意味します。通常、これは新しいヘッドが作成されたことを示し、リポジトリが最新の状態でない場合に発生します。
    *   `not (old_heads == 0 and new_heads == 1)` は、空のリポジトリに最初のコミットを行う特殊なケースを除外しています。
    *   追加された `cl.desc.find("create new branch") < 0` という条件が重要です。`cl.desc` は現在の変更リストの記述（コミットメッセージ）です。`find("create new branch")` は、この記述内に文字列 `"create new branch"` が存在するかどうかをチェックします。存在しない場合、`find` メソッドは `-1` を返します。
    *   したがって、この条件全体は「変更リストの記述に `"create new branch"` が含まれておらず、かつ新しいヘッドが作成された（ただし、最初のコミットではない）」場合に `True` となります。この条件が `True` の場合、`need_sync()` が呼び出され、ユーザーにリポジトリの同期を促すエラーが発生します。
    *   この変更により、コミットメッセージに `"create new branch"` が含まれていれば、新しいヘッドが作成されても `need_sync()` が呼び出されなくなり、エラーが回避されます。

2.  **`if hg_push(ui, repo, new_branch=cl.desc.find("create new branch")>=0):`**
    *   この行は、実際にMercurialのリモートリポジトリへのプッシュ操作を行う `hg_push` 関数を呼び出している部分です。
    *   `new_branch=cl.desc.find("create new branch")>=0` という新しい引数が追加されています。
    *   `cl.desc.find("create new branch")>=0` は、変更リストの記述に `"create new branch"` という文字列が含まれている場合に `True` を返します（文字列が見つかると、その開始インデックスが返され、それは0以上の値になります）。含まれていない場合は `False` を返します。
    *   この `new_branch` 引数は、`hg_push` 関数に対して、今回のプッシュが新しいブランチの作成を意図したものであるかどうかを伝えます。`hg_push` 関数は、この情報に基づいて、Mercurialのプッシュコマンドに適切なオプション（例えば、新しいブランチの作成を許可するオプション）を内部的に渡すことができます。
    *   これにより、通常は新しいヘッドのプッシュを拒否するMercurialの動作が、この特定のケースでは許可されるようになります。

これらの変更は連携して機能し、コミットメッセージに特定のキーワードを含めることで、Goプロジェクトのコードレビューツールが新しい開発ブランチの作成とコミットをスムーズに処理できるようにしています。

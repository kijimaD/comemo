# [インデックス 23961] ファイルの概要

## 元コミット内容

`4g/5g/6g/8g/9g`へのいくつかの古い参照を修正しました。

## 変更の背景

Go言語の初期のバージョンでは、異なるCPUアーキテクチャ（例：`amd64`, `386`, `arm`）ごとに専用のコンパイラが提供されていました。これらはそれぞれ`6g`（amd64用）、`8g`（386用）、`5g`（ARM用）といった名前で呼ばれていました。これらのコンパイラは、Goの標準コンパイラツールチェインの一部であり、`gc`（Go Compiler）スイートとして総称されていました。

しかし、Goツールチェインの進化に伴い、これらのアーキテクチャ固有のコンパイラは、単一の統合されたコンパイラである`cmd/compile`に統合されました。この変更は、ツールチェインの管理を簡素化し、ユーザーが特定のアーキテクチャを意識することなく`go build`や`go tool compile`といったコマンドを使用できるようにすることを目的としていました。

このコミットは、コードベース全体に残っていた古いコンパイラ名への参照を、新しい統一された名称（`gc`または`cmd/compile`）に更新することで、この移行を反映し、ドキュメントや内部コメントの正確性を保つために行われました。

## 前提知識の解説

*   **Goツールチェイン**: Go言語のプログラムを開発、ビルド、実行するために必要な一連のツール群です。これにはコンパイラ、リンカ、アセンブラ、デバッガなどが含まれます。
*   **`gc` (Go Compiler)**: Go言語の公式コンパイラスイートの総称です。歴史的には、このスイート内に`6g`, `8g`, `5g`などのアーキテクチャ固有のコンパイラが存在しました。
*   **`4g`, `5g`, `6g`, `8g`, `9g`**: Go言語の初期に存在した、特定のCPUアーキテクチャ向けのコンパイラコマンドです。
    *   `4g`: SPARCアーキテクチャ向け（現在は非推奨または統合）
    *   `5g`: ARMアーキテクチャ向け
    *   `6g`: AMD64（x86-64）アーキテクチャ向け
    *   `8g`: 386（x86）アーキテクチャ向け
    *   `9g`: Plan 9アーキテクチャ向け（現在は非推奨または統合）
    これらのコンパイラは、それぞれのアセンブラ（例：`6a`）、リンカ（例：`6l`）と組み合わせて使用されていました。
*   **`cmd/compile`**: 現在のGoツールチェインにおける主要なコンパイラコマンドです。これは、以前の`4g/5g/6g/8g/9g`の機能を統合し、`go build`コマンドの内部で呼び出される実体となっています。ユーザーは通常、直接`cmd/compile`を呼び出すことはなく、`go build`や`go run`などの高レベルなコマンドを使用します。
*   **`go tool`**: `go`コマンドのサブコマンドで、Goツールチェインに含まれる低レベルなツール（例：`compile`, `asm`, `link`）を直接実行するために使用されます。例えば、`go tool compile`はコンパイラを直接呼び出します。
*   **Cgo**: GoプログラムからC言語のコードを呼び出すためのメカニズムです。Cgoを使用する際には、GoコンパイラとCコンパイラ（通常はGCC）の間でデータ構造や呼び出し規約の整合性を取る必要があります。

## 技術的詳細

このコミットの技術的な詳細は、主にGoツールチェインの内部的な整合性を保つことにあります。古いコンパイラ名がコードベースに残っていると、以下のような問題が生じる可能性があります。

1.  **ドキュメントの誤解**: ユーザーが古いドキュメントを参照した際に、現在存在しないコンパイラ名に遭遇し、混乱を招く可能性があります。
2.  **コードの誤解**: 開発者が内部コードを読んだ際に、古いコンパイラ名が使われていると、現在のツールチェインの構造を誤解する可能性があります。
3.  **メンテナンスの複雑化**: 将来的にツールチェインがさらに進化する際に、古い参照が残っていると、変更の影響範囲を特定しにくくなる可能性があります。

このコミットでは、これらの問題を解決するために、ドキュメント、Cgo関連のコード、ランタイム、テストコードなど、Goリポジトリ内の広範なファイルで古いコンパイラ名への参照を検索し、`gc`または`cmd/compile`といった現在の名称に置き換えています。

特にCgo関連のファイルでは、GoコンパイラとCコンパイラ（GCC）の間での構造体のアライメントや引数フレームのレイアウトに関する記述があり、ここでのコンパイラ名の変更は、どのGoコンパイラの規約に合わせるべきかを示す重要な情報となります。例えば、`src/cmd/cgo/out.go`では、`6g`の引数フレームに一致するGCC構造体を構築する、という記述が`gc`の引数フレームに一致する、という記述に更新されています。これは、Goコンパイラの内部的なABI（Application Binary Interface）が、アーキテクチャ固有のコンパイラから統合された`gc`コンパイラへと引き継がれていることを示唆しています。

また、`src/runtime/compiler.go`では、`Compiler`定数の説明が「`5g/6g/8g`コンパイラスイート」から「`cmd/compile`としても知られる」に変更されており、`gc`が`cmd/compile`の別名または実体であることを明確にしています。

## コアとなるコードの解説

このコミットの核心は、Goツールチェインの進化に伴う名称変更をコードベース全体に反映させることです。

例えば、`doc/asm.html`では、Goのアセンブリ言語に関するドキュメントで、以前は「`gc`スイートのGoコンパイラ（`6g`, `8g`など）」と説明されていた箇所が、単に「`gc` Goコンパイラ」と簡潔に記述されるようになっています。これは、ユーザーが特定のアーキテクチャ固有のコンパイラ名を意識する必要がなくなったことを示しています。また、アセンブリコードの生成例も`go tool 6g -S x.go`から`go tool compile -S x.go`に変更されており、現在のコマンドラインインターフェースに即した形になっています。

Cgo関連のファイルでは、GoとCの間のインターフェースを定義する際に、GoコンパイラのABI（Application Binary Interface）に合わせる必要があるため、どのGoコンパイラを指しているかを明確にすることが重要です。古い`6g`などの名前が使われていると、将来的にABIが変更された際に混乱を招く可能性があります。`gc`という統一された名称にすることで、Goコンパイラの現在のABIを指すことが明確になります。

ランタイムのアセンブリコード（例：`src/runtime/cgo/asm_arm.s`）では、Cgoのクロス呼び出し（crosscall）の際に、Goランタイムのスタックフレームやレジスタの規約に関するコメントが更新されています。ここでも、`5c/5g world`といった古い表現が`gc world`に置き換えられ、Goコンパイラの内部的な動作に関する記述が最新の状態に保たれています。

`src/runtime/compiler.go`の`Compiler`定数の変更は、Goプログラムが自身をビルドしたコンパイラの名前を識別するためのものです。この定数の説明を更新することで、`gc`が`cmd/compile`という具体的なコマンドを指すようになったことを明確にしています。

テストファイルにおける変更は、主にテストのコメントや、特定のコンパイラの挙動（例：最適化、エラーメッセージの形式）に関する記述を更新するものです。これにより、テストコードが現在のGoコンパイラの挙動を正確に反映するようになります。

全体として、このコミットはGo言語のツールチェインが成熟し、より統一されたインターフェースと内部構造を持つようになったことを示す重要なクリーンアップ作業と言えます。

## コアとなるコードの解説

このコミットの核心は、Goツールチェインの進化に伴う名称変更をコードベース全体に反映させることです。

例えば、`doc/asm.html`では、Goのアセンブリ言語に関するドキュメントで、以前は「`gc`スイートのGoコンパイラ（`6g`, `8g`など）」と説明されていた箇所が、単に「`gc` Goコンパイラ」と簡潔に記述されるようになっています。これは、ユーザーが特定のアーキテクチャ固有のコンパイラ名を意識する必要がなくなったことを示しています。また、アセンブリコードの生成例も`go tool 6g -S x.go`から`go tool compile -S x.go`に変更されており、現在のコマンドラインインターフェースに即した形になっています。

Cgo関連のファイルでは、GoとCの間のインターフェースを定義する際に、GoコンパイラのABI（Application Binary Interface）に合わせる必要があるため、どのGoコンパイラを指しているかを明確にすることが重要です。古い`6g`などの名前が使われていると、将来的にABIが変更された際に混乱を招く可能性があります。`gc`という統一された名称にすることで、Goコンパイラの現在のABIを指すことが明確になります。

ランタイムのアセンブリコード（例：`src/runtime/cgo/asm_arm.s`）では、Cgoのクロス呼び出し（crosscall）の際に、Goランタイムのスタックフレームやレジスタの規約に関するコメントが更新されています。ここでも、`5c/5g world`といった古い表現が`gc world`に置き換えられ、Goコンパイラの内部的な動作に関する記述が最新の状態に保たれています。

`src/runtime/compiler.go`の`Compiler`定数の変更は、Goプログラムが自身をビルドしたコンパイラの名前を識別するためのものです。この定数の説明を更新することで、`gc`が`cmd/compile`という具体的なコマンドを指すようになったことを明確にしています。

テストファイルにおける変更は、主にテストのコメントや、特定のコンパイラの挙動（例：最適化、エラーメッセージの形式）に関する記述を更新するものです。これにより、テストコードが現在のGoコンパイラの挙動を正確に反映するようになります。

全体として、このコミットはGo言語のツールチェインが成熟し、より統一されたインターフェースと内部構造を持つようになったことを示す重要なクリーンアップ作業と言えます。

# [インデックス 24498] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおけるAMD64アーキテクチャ向けの`NEG`（符号反転）および`NOT`（ビット反転）命令の処理方法を修正するものです。特に、これらの操作が「非インプレース」で行われる場合に、正しくレジスタを扱うように変更されています。この修正は、`crypto/subtle`パッケージのテストが失敗する問題を解決するために導入されました。

## 変更の背景

このコミットの主な背景は、`crypto/subtle`パッケージのテストが失敗していたことです。`crypto/subtle`パッケージは、サイドチャネル攻撃（特にタイミング攻撃）を防ぐために、実行時間が入力値に依存しない「定数時間」で動作する関数を提供します。

GoコンパイラのSSA（Static Single Assignment）最適化バックエンドは、プログラムのパフォーマンスを向上させるために様々な変換を行います。しかし、これらの最適化が、意図せず定数時間の保証を破るようなコードを生成してしまうことがあります。具体的には、`NEG`（符号反転）や`NOT`（ビット反転）のような単項演算が、コンパイラによって「インプレース」（オペランドと同じレジスタに結果を書き込む）であると誤って仮定されていた可能性があります。

もし、SSAがこれらの操作を常にインプレースであると仮定し、実際には結果が別のレジスタに書き込まれるべきであったり、元のオペランドが後続の処理で必要とされたりする場合、以下の問題が発生する可能性があります。

1.  **データの破損**: オペランドが上書きされ、後でその元の値が必要な場合に誤った値が使用される。
2.  **タイミング攻撃への脆弱性**: レジスタの再利用やメモリ操作のパターンが入力データに依存して変化することで、定数時間の保証が破られ、タイミング攻撃の可能性が生じる。`crypto/subtle`のテスト失敗は、まさにこの種の脆弱性を示唆しています。

このコミットは、SSAバックエンドが`NEG`と`NOT`操作をより正確に扱い、特に結果がオペランドとは異なるレジスタに格納される「非インプレース」のシナリオを適切に処理することで、これらの問題を解決し、`crypto/subtle`の定数時間特性を維持することを目的としています。

## 前提知識の解説

### 1. GoコンパイラとSSA (Static Single Assignment)

Goコンパイラは、ソースコードを機械語に変換する過程で、複数のステージを経由します。その中でも、SSA（Static Single Assignment）形式は、中間表現（IR）の一つとして非常に重要です。

*   **SSA形式**: プログラム中の各変数が一度だけ代入されるようにする表現形式です。例えば、`x = a + b; x = x * c;`というコードは、SSA形式では`x1 = a + b; x2 = x1 * c;`のように変換されます。これにより、データフロー解析や最適化が大幅に簡素化され、より強力な最適化（例: 共通部分式の削除、デッドコードの削除、レジスタ割り当ての改善など）が可能になります。
*   **SSAバックエンド**: Goコンパイラでは、SSA形式に変換されたコードを基に、特定のアーキテクチャ（例: AMD64）向けの機械語を生成する部分をSSAバックエンドと呼びます。このステージでは、SSAの各操作（`ssa.Value`）が、対応するアセンブリ命令（`obj.Prog`）にマッピングされます。

### 2. `NEG`と`NOT`命令

これらは、多くのプロセッサアーキテクチャに存在する基本的な単項演算命令です。

*   **`NEG` (Negate)**: オペランドの符号を反転させます。例えば、5を-5に、-10を10にします。2の補数表現では、ビット反転（NOT）して1を加えることで実現されます。
*   **`NOT` (Bitwise NOT)**: オペランドの各ビットを反転させます（0を1に、1を0に）。

これらの命令は、通常、レジスタ内の値を操作します。

### 3. インプレース (In-place) と非インプレース (Non-in-place) 操作

*   **インプレース操作**: 演算の結果が、元のオペランドが格納されていたメモリ位置やレジスタに直接書き込まれる操作です。これにより、追加のメモリやレジスタを必要とせず、効率的です。
*   **非インプレース操作**: 演算の結果が、元のオペランドとは異なるメモリ位置やレジスタに書き込まれる操作です。元のオペランドの値を保持する必要がある場合や、アーキテクチャの制約上、結果を別の場所に格納する必要がある場合に用いられます。SSA形式では、各変数が一度しか代入されないため、論理的にはすべての操作が非インプレースであると考えることができますが、物理的なレジスタ割り当ての段階でインプレース操作に最適化されることもあります。

### 4. `crypto/subtle`パッケージとタイミング攻撃

*   **`crypto/subtle`パッケージ**: Go言語の標準ライブラリの一部で、暗号操作においてサイドチャネル攻撃、特にタイミング攻撃を防ぐためのユーティリティ関数を提供します。
*   **タイミング攻撃**: プログラムの実行時間が入出力データに依存する場合に発生する可能性のあるサイドチャネル攻撃の一種です。例えば、秘密鍵の特定のビットが0か1かによって比較処理のループ回数がわずかに異なる場合、その時間差を測定することで秘密鍵を推測される可能性があります。
*   **定数時間 (Constant-time) 実行**: 入力データの内容に関わらず、常に同じ時間で実行されることを保証するプログラミング手法です。暗号アルゴリズムの実装において、タイミング攻撃を防ぐために極めて重要です。コンパイラの最適化がこの定数時間特性を破らないようにすることは、暗号ライブラリのセキュリティにとって不可欠です。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドがAMD64アーキテクチャ向けに`NEG`および`NOT`命令を生成する際のロジックを修正しています。

以前の実装では、`ssa.OpAMD64NEGQ`などの`NEG`および`NOT`系のSSA操作に対して、生成されるアセンブリ命令の`To.Reg`フィールド（結果を格納するレジスタ）が、常にオペランドのレジスタ（`v.Args[0]`）と同じであると仮定していました。これは、これらの操作が常にインプレースで行われるという前提に基づいています。

しかし、SSA形式では、各`ssa.Value`は一意の結果を表し、その結果が格納されるべきレジスタ（`regnum(v)`）は、必ずしもオペランドのレジスタ（`regnum(v.Args[0])`）と同じであるとは限りません。レジスタ割り当ての段階で、コンパイラは最適なレジスタ使用を決定するため、オペランドと結果に異なるレジスタを割り当てる可能性があります。

この「非インプレース」のシナリオが正しく処理されないと、以下のような問題が生じます。

1.  **誤ったコード生成**: オペランドと結果のレジスタが異なるにもかかわらず、コンパイラがインプレース操作を想定してコードを生成すると、結果が意図しないレジスタに書き込まれたり、元のオペランドが不適切に上書きされたりする可能性があります。
2.  **`crypto/subtle`テストの失敗**: `crypto/subtle`パッケージは、定数時間実行を厳密に要求します。もしコンパイラが、入力値に依存してレジスタの割り当てや操作の順序を変えるような最適化を行ったり、あるいは非インプレース操作をインプレースとして扱うことで、レジスタの競合や不必要なデータ移動を引き起こしたりすると、それが実行時間のわずかな変動につながり、タイミング攻撃の脆弱性を生み出す可能性があります。テストの失敗は、このような問題が実際に発生していたことを示しています。

このコミットは、この問題を解決するために、`NEG`および`NOT`操作のコード生成において、オペランドレジスタと結果レジスタが異なる場合に明示的なレジスタ間移動命令（`MOV`）を挿入するように変更しました。これにより、SSAのセマンティクスとレジスタ割り当ての決定が尊重され、操作が常に正しいレジスタに対して行われるようになります。

## コアとなるコードの解説

修正されたコードブロックは、以下のステップで`NEG`または`NOT`操作を処理します。

1.  **オペランドレジスタと結果レジスタの取得**:
    *   `x := regnum(v.Args[0])`: `v.Args[0]`は操作の入力（オペランド）となるSSA値です。`regnum(v.Args[0])`は、そのオペランドが格納されている物理レジスタの番号を取得します。
    *   `r := regnum(v)`: `v`は現在のSSA操作（`NEG`または`NOT`）の結果となるSSA値です。`regnum(v)`は、この結果が格納されるべき物理レジスタの番号を取得します。

2.  **非インプレース操作の検出とレジスタ移動**:
    *   `if x != r { ... }`: ここが変更の核心です。もしオペランドレジスタ`x`と結果レジスタ`r`が異なる場合、つまり操作が非インプレースで行われる必要がある場合、以下の処理が実行されます。
        *   `p := Prog(regMoveAMD64(v.Type.Size()))`: オペランドのサイズ（バイト数）に応じたAMD64のレジスタ移動命令（`MOV`）を生成します。例えば、`NEGQ`であれば8バイト（Qword）の移動命令が生成されます。
        *   `p.From.Type = obj.TYPE_REG; p.From.Reg = x`: 移動元をオペランドレジスタ`x`に設定します。
        *   `p.To.Type = obj.TYPE_REG; p.To.Reg = r`: 移動先を結果レジスタ`r`に設定します。
        *   この`MOV`命令により、オペランドの値が`x`から`r`にコピーされます。

3.  **実際の`NEG`/`NOT`命令の生成**:
    *   `p := Prog(v.Op.Asm())`: 現在のSSA操作（例: `ssa.OpAMD64NEGQ`）に対応するAMD64アセンブリ命令（例: `ANEGQ`）を生成します。
    *   `p.To.Type = obj.TYPE_REG`: 命令のターゲットがレジスタであることを指定します。
    *   `p.To.Reg = r`: **ここが以前のコードからの変更点です。** 以前は`regnum(v.Args[0])`（オペランドレジスタ）が使われていましたが、この修正により`r`（結果レジスタ）が明示的に指定されるようになりました。これにより、`NEG`または`NOT`操作は、オペランドがコピーされた後の正しい結果レジスタ`r`に対して実行されます。

この変更により、コンパイラは`NEG`や`NOT`操作がインプレースであるか非インプレースであるかに関わらず、常にSSAのセマンティクスに従って正しいレジスタに結果を書き込むようになります。特に、`crypto/subtle`のような定数時間実行を要求するコードにおいて、レジスタの不適切な使用によるタイミングの変動を防ぎ、セキュリティを向上させます。

## 変更の背景

Go言語の初期のコンパイラである`cmd/9g`（x86アーキテクチャ向け）は、小さなメモリコピー操作（例えば、構造体のコピーや短いスライスのコピーなど）に対して、効率の悪いアセンブリコードを生成していました。具体的には、コピー元とコピー先のメモリアドレスを計算する際に、不必要な`ADD`命令を繰り返し挿入していました。これにより、生成されるコードは命令数が多くなり、CPUのパイプライン処理を阻害する可能性がありました。

このコミットは、この非効率性を認識し、将来的なコンパイラの最適化作業の指針として、コード内にTODOコメントとして問題を明記することを目的としています。これは、すぐに問題を解決するのではなく、その存在を記録し、後の改善サイクルで対処するためのステップです。

## 前提知識の解説

### Goコンパイラの歴史と`cmd/9g`

Go言語の初期のツールチェインでは、異なるアーキテクチャ向けに個別のコンパイラが提供されていました。
- `5g`: ARM (32-bit)
- `6g`: x86-64 (64-bit)
- `8g`: MIPS
- `9g`: x86 (32-bit)

これらのコンパイラは、Go 1.5以降、単一の`gc`（Go compiler）として統合され、`go tool compile`コマンドを通じて利用されるようになりました。したがって、`cmd/9g`は現在では直接使われることはありませんが、Goコンパイラの進化の過程における重要な一部でした。このコミットは、その歴史的なコンテキストにおける最適化の課題を示しています。

### コード生成 (Code Generation)

コンパイラの主要なフェーズの一つに「コード生成」があります。これは、コンパイラがソースコードを解析し、中間表現（IR: Intermediate Representation）に変換した後、その中間表現をターゲットとなるCPUアーキテクチャの機械語（アセンブリコード）に変換するプロセスです。コード生成の品質は、最終的な実行ファイルのパフォーマンスに直結します。効率的なコード生成は、命令数を減らし、CPUのキャッシュ利用率を高め、パイプライン処理を最適化することを目指します。

### `cgen.c`

`cgen.c`は、Goコンパイラのコード生成部分を担っていたC言語のソースファイルです。Goコンパイラの初期バージョンでは、その一部がC言語で書かれていました。このファイルには、Goのプログラム構造を特定のアセンブリ命令に変換するためのロジックが含まれていました。

### メモリコピーの最適化

メモリコピーは、プログラム内で頻繁に行われる操作であり、その効率は全体のパフォーマンスに大きな影響を与えます。コンパイラは、メモリコピーを最適化するために様々な技術を使用します。
- **特殊命令の利用**: x86アーキテクチャには、`REP MOVSB`のような、大量のデータを効率的にコピーするための専用命令があります。
- **ループアンローリング**: 小さな固定サイズのコピーの場合、ループのオーバーヘッドを避けるために、コンパイラはループをアンロール（展開）し、複数の独立したコピー命令に変換することがあります。
- **アドレス計算の最適化**: メモリアドレスの計算は、アセンブリ命令の効率に大きく影響します。レジスタの利用、オフセットの直接指定、ベースレジスタとインデックスレジスタの組み合わせなど、様々なアドレッシングモードを適切に選択することで、命令数を減らし、実行速度を向上させることができます。

### パイプライン処理 (Pipelining)

現代のCPUは、命令をパイプライン処理することで高い性能を実現しています。これは、複数の命令を同時に異なるステージ（フェッチ、デコード、実行など）で処理する技術です。しかし、ある命令の実行結果が次の命令の入力となるような「依存関係」が多いコードは、パイプラインのストール（停止）を引き起こし、CPUの効率を低下させます。このコミットで言及されている「pipeline-able code」とは、依存関係が少なく、CPUがスムーズに命令をパイプライン処理できるようなコードを指します。

## 技術的詳細

このコミットが指摘している技術的な問題は、`cmd/9g`コンパイラが小さなメモリコピーを行う際に、以下のような非効率なアセンブリパターンを生成していたことです。

```assembly
ADD $-8,R8   ; コピー元アドレスを更新
ADD $-8,R7   ; コピー先アドレスを更新
n*(MOVDU 8(R8),R9; MOVDU R9,8(R7);) ; データをコピー
```

ここで、`R8`と`R7`はそれぞれコピー元とコピー先のベースアドレスを保持するレジスタです。`MOVDU`はデータ転送命令です。このコードは、ループ内で毎回`ADD`命令を使ってアドレスを更新し、その更新されたアドレスからオフセット`8`を使ってデータをロード/ストアしています。

コミットのTODOコメントが示唆している最適化は、この`ADD`命令を排除し、オフセットを直接指定することで、より短く、パイプライン処理に適したコードを生成することです。

例えば、以下のようなイメージです（具体的なアセンブリはアーキテクチャやコンパイラの最適化レベルに依存します）。

```assembly
; ループ内で直接オフセットを指定するか、
; ループの前にオフセットを計算してレジスタに保持する
MOVDU (R8 + offset1), R9
MOVDU R9, (R7 + offset1)
MOVDU (R8 + offset2), R9
MOVDU R9, (R7 + offset2)
; ...
```

このようにすることで、各コピー操作が独立した命令として扱われやすくなり、CPUのパイプラインがストールする可能性が低減します。`ADD`命令は、その結果が次の`MOVDU`命令のアドレス計算に依存するため、パイプラインの依存関係を生み出します。この依存関係を解消することで、CPUはより多くの命令を並行して実行できるようになり、全体的なパフォーマンスが向上します。

## コアとなるコードの解説

追加されたTODOコメントは、`cmd/9g`コンパイラのコード生成ロジックにおける具体的な改善点を明確に示しています。

コメントの内容は以下の通りです。
`// TODO(austin): Instead of generating ADD $-8,R8; ADD $-8,R7; n*(MOVDU 8(R8),R9; MOVDU R9,8(R7);) just // generate the offsets directly and eliminate the // ADDs. That will produce shorter, more // pipeline-able code.`

これは、現在の実装が「`ADD $-8,R8; ADD $-8,R7;` の後に `n` 回の `MOVDU 8(R8),R9; MOVDU R9,8(R7);`」というパターンを生成していることを指摘しています。そして、その代わりに「オフセットを直接生成し、`ADD`命令を排除する」べきだと提案しています。これにより、「より短く、よりパイプライン処理に適したコード」が生成されると述べています。

このTODOコメントは、コンパイラの開発者が将来的にこの部分のコード生成ロジックを見直す際の具体的な指針となります。これは、Goコンパイラが継続的にパフォーマンス最適化に取り組んでいる証拠でもあります。

# [インデックス 20405] ファイルの概要

このコミットは、Goランタイムにおけるパニック処理の重要な変更を導入しています。具体的には、パニック発生時にスタックを処理するために使用されていた`newstackcall`という内部関数を廃止し、代わりに`reflect.call`を使用するように変更しています。この変更の主な目的は、`newstackcall`が新しいスタックセグメントを作成するという特性が、パニック時のスタック処理において望ましくない挙動を引き起こす可能性があったため、その問題を解決することにあります。`reflect.call`への移行により、より柔軟で堅牢なパニック処理が実現され、特にスタックのコピーやガベージコレクションにおけるポインタの正確な追跡が改善されています。

## 変更の背景

この変更の背景には、Goランタイムのスタック管理とパニック処理における特定の課題がありました。

1.  **`newstackcall`の問題点**: `newstackcall`は、Goのスタック成長メカニズムの一部として、新しいスタックセグメントを割り当て、古いスタックの内容をコピーするために使用されていました。しかし、パニック発生時、特に`defer`関数が実行される際に`newstackcall`を使用すると、新しいスタックセグメントが作成されることで、スタックの巻き戻し（unwinding）や`recover`処理が複雑になる、あるいは意図しない挙動を引き起こす可能性がありました。コミットメッセージにある「newstackcall creates a new stack segment, and we want to be able to throw away all that code.」という記述は、`newstackcall`が生成する余分なコードや、そのスタックセグメント作成の副作用がパニック処理の効率性や正確性を妨げていたことを示唆しています。パニック処理では、現在のスタックフレームを正確に把握し、`defer`関数を順次実行しながらスタックを巻き戻す必要がありますが、`newstackcall`によるスタックセグメントの動的な変更がこのプロセスを困難にしていたと考えられます。

2.  **`reflect.call`の活用**: `reflect.call`は、Goの`reflect`パッケージが提供する機能で、動的に関数を呼び出すための汎用的なメカニズムです。このコミットでは、パニック時の`defer`関数の呼び出しに`reflect.call`を適用することで、`newstackcall`が抱えていた問題を回避しようとしています。`reflect.call`は、既存のスタック上で関数を呼び出すことができ、`newstackcall`のように新しいスタックセグメントを強制的に作成するわけではないため、パニック処理におけるスタックの連続性を保ちやすくなります。これにより、スタックの巻き戻しがより予測可能になり、`recover`の動作も安定します。

3.  **スタックポインタの正確な追跡**: Goのガベージコレクタ（GC）は、スタック上のポインタを正確に識別する必要があります。`newstackcall`が新しいスタックセグメントを作成するたびに、ポインタの再配置や追跡が複雑になる可能性がありました。`reflect.call`を使用することで、スタックの構造がより安定し、GCがポインタを正確に追跡するための情報（`FUNCDATA_ArgsPointerMaps`や`FUNCDATA_LocalsPointerMaps`など）をより確実に利用できるようになります。

4.  **関連するバグの修正**: `test/fixedbugs/issue4388.go`や`test/fixedbugs/issue5856.go`の変更は、このコミットがスタックフレームのカウントや`runtime.Caller`の挙動に影響を与えることを示しています。これは、パニック処理におけるスタックの構造変更が、デバッグ情報やスタックトレースの正確性に影響を及ぼす可能性があるため、それらの整合性を保つための調整が必要であったことを示唆しています。特に`issue7695_test.go`のコメント「This test depends on running C code on Go stacks. Not allowed anymore.」は、CGOとGoスタック間の相互作用における問題が、`newstackcall`の挙動と関連していた可能性を示唆しており、この変更がその問題解決の一環であったことを示しています。

これらの背景から、このコミットはGoランタイムのパニック処理をより堅牢で効率的にし、スタック管理の複雑さを軽減することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とメカニズムに関する知識が必要です。

1.  **Goroutineとスタック**:
    *   **Goroutine**: Goにおける軽量な実行単位です。OSのスレッドよりもはるかに軽量で、数百万のGoroutineを同時に実行できます。
    *   **スタック**: 各Goroutineは独自の実行スタックを持っています。関数呼び出しの引数、ローカル変数、戻りアドレスなどがスタックに積まれます。
    *   **スタック成長 (Stack Growth)**: Goのスタックは動的にサイズが変更されます。関数呼び出しによってスタックが不足しそうになると、ランタイムは自動的にスタックを拡張します。Go 1.4以降では「連続スタック（contiguous stack）」が採用されており、スタックが不足すると、より大きな新しいメモリ領域が割り当てられ、古いスタックの内容が新しい領域にコピーされます。このプロセスは透過的に行われます。

2.  **パニック (Panic) とリカバリ (Recover)**:
    *   **Panic**: Goにおける回復不能なエラー（例: `nil`ポインタのデリファレンス、配列の範囲外アクセス、明示的な`panic()`関数の呼び出し）が発生した際に使用されるメカニズムです。パニックが発生すると、通常のプログラム実行フローは停止し、スタックの巻き戻し（stack unwinding）が開始されます。
    *   **Defer**: `defer`文は、それを囲む関数がリターンする直前（正常終了かパニックによる終了かに関わらず）に実行される関数をスケジュールします。パニック時には、スタックが巻き戻される過程で、各関数の`defer`関数が逆順に実行されます。
    *   **Recover**: `recover()`は、`defer`関数内で呼び出された場合にのみ意味を持つ組み込み関数です。`recover()`がパニック中に呼び出されると、パニックを捕捉し、スタックの巻き戻しを停止させ、パニックの原因となった値を返します。これにより、プログラムはパニックから回復し、通常の実行を再開できます。`recover()`がパニック中でないときに呼び出されると、`nil`を返します。

3.  **`reflect`パッケージと`reflect.Call`**:
    *   **`reflect`パッケージ**: Goの`reflect`パッケージは、実行時にプログラムの構造（型、値、関数など）を検査・操作するための機能を提供します。これにより、ジェネリックなプログラミングや、動的な関数呼び出しなどが可能になります。
    *   **`reflect.Call`**: `reflect.Value`型が持つメソッドで、`reflect.Value`が表す関数を動的に呼び出すために使用されます。引数も`reflect.Value`のスライスとして渡されます。この機能は、コンパイル時に呼び出す関数が特定できない場合（例: プラグインシステム、RPCフレームワーク）に特に有用です。

4.  **Goランタイムの内部構造**:
    *   **アセンブリコード**: Goランタイムの多くの部分は、パフォーマンス最適化のためにアセンブリ言語で記述されています。特にスタック管理、Goroutineのスケジューリング、GC関連の処理など、低レベルな操作はアセンブリコードで行われます。
    *   **`m`と`g`構造体**: Goランタイムは、OSスレッドを表す`m`（machine）と、Goroutineを表す`g`（goroutine）という主要な構造体を持っています。`g`は自身のスタック情報やスケジューリング関連の情報を保持します。
    *   **`_panic`構造体**: パニックに関する情報を保持するランタイム内部の構造体です。パニックの原因となった値、`defer`関数へのリンク、回復状態などが含まれます。
    *   **`FUNCDATA_ArgsPointerMaps`と`FUNCDATA_LocalsPointerMaps`**: これらはGoのコンパイラとランタイムが使用する内部的なメタデータです。ガベージコレクタがスタック上のポインタを正確に識別するために、関数の引数（`ArgsPointerMaps`）とローカル変数（`LocalsPointerMaps`）のどこにポインタが存在するかを示す情報を提供します。これにより、GCは不要なメモリを解放する際に、誤って参照されているオブジェクトを回収してしまうことを防ぎます。

5.  **`newstackcall` (旧メカニズム)**: このコミットで置き換えられる古いメカニズムです。パニック時に`defer`関数を呼び出すために使用されていましたが、新しいスタックセグメントを作成するという特性が、パニック処理の複雑さを増していました。

これらの概念を理解することで、このコミットがGoランタイムの安定性、効率性、そしてデバッグのしやすさをどのように向上させているかを深く把握できます。

## 技術的詳細

このコミットの技術的詳細は、主に`newstackcall`の廃止と`reflect.call`への移行、それに伴うランタイムのスタック管理、パニック処理、およびガベージコレクション関連の変更に集約されます。

1.  **`newstackcall`の廃止**:
    *   `src/pkg/runtime/asm_386.s`, `src/pkg/runtime/asm_amd64.s`, `src/pkg/runtime/asm_amd64p32.s`, `src/pkg/runtime/asm_arm.s`といった各アーキテクチャのアセンブリファイルから、`runtime·newstackcall`の定義が完全に削除されています。これは、この関数がGoランタイムのパニック処理パスから完全に排除されたことを意味します。
    *   `src/pkg/runtime/stubs.go`からも`newstackcall`の宣言が削除されています。
    *   `src/pkg/runtime/cgocall.go`の`cgocallbackg1`関数や`src/pkg/runtime/malloc.go`の`runfinq`関数、`src/pkg/runtime/panic.go`の`Goexit`関数など、以前`newstackcall`を呼び出していた箇所が`reflectcall`に置き換えられています。

2.  **`reflect.call`の拡張と利用**:
    *   `src/pkg/reflect/value.go`の`call`関数（Go言語側の`reflect.call`の実装）のシグネチャが変更され、`panicpos unsafe.Pointer`という新しい引数が追加されています。これは、パニック処理中に`reflect.call`が呼び出された際に、パニック関連の情報を渡すためのものです。
    *   `src/pkg/runtime/stubs.go`の`reflectcall`の宣言も、この新しい引数`p *_panic`を含むように更新されています。
    *   `src/pkg/runtime/panic1.go`の`gopanic`関数内で、`newstackcall`の代わりに`reflectcall`が使用されるようになっています。特に、`defer`関数の実行時に`reflectcall`が呼び出され、その際に現在の`_panic`構造体へのポインタが渡されるようになっています。これにより、`reflect.call`の実行中にパニックが発生した場合でも、`recover`が正しく機能するためのコンテキストが提供されます。
    *   アセンブリコード（`asm_*.s`ファイル）内の`reflect·call`および`CALLFN`マクロが変更され、新しい`panic`引数を処理するように修正されています。具体的には、`panic_argp`フィールド（`_panic`構造体に追加された新しいフィールド）が設定され、`reflect.call`が実行される関数の引数ポインタを指すようになります。これにより、`recover`がスタックを巻き戻す際に、どのスタックフレームがパニックの起点であるかを正確に特定できるようになります。

3.  **`_panic`構造体の変更**:
    *   `src/pkg/runtime/runtime.h`において、`_panic`構造体に`uintptr argp`と`uint32 outerwrap`という新しいフィールドが追加されています。
        *   `argp`: `defer`呼び出しの引数へのポインタを格納します。これは`recover`がパニックを捕捉した際に、どのスタックフレームがパニックの起点であるかを特定するために使用されます。
        *   `outerwrap`: 外部の`gp->panicwrap`の値を保存します。`panicwrap`は、スタックの調整に関連する値で、`recover`が正しく機能するために必要です。
    *   `Stktop`構造体から`bool panic`フィールドが削除されています。これは、パニックの状態を管理する方法が変更されたことを示唆しています。

4.  **スタック管理とGCの連携**:
    *   `src/pkg/runtime/stack.c`の`adjustpanics`関数が変更され、`_panic`構造体の`argp`フィールドもスタックの調整（コピーなど）に伴って更新されるようになっています。これは、スタックが移動した場合でも、`recover`が正しい引数ポインタを指し続けることを保証するために重要です。
    *   `src/pkg/runtime/stack.c`の`runtime·newstack`関数から、`newstackcall`に関連するロジック（`newstackcall`フラグのチェックや、`Stktop`の`panic`フィールドの設定など）が削除されています。これにより、スタック成長のプロセスが簡素化され、パニック処理との結合が緩やかになります。
    *   `FUNCDATA_ArgsPointerMaps`と`FUNCDATA_LocalsPointerMaps`に関連するアセンブリコードの変更は、`reflect.call`が呼び出す関数の引数とローカル変数のポインタ情報をGCに正確に伝えるためのものです。これにより、パニック処理中にスタックが操作されても、GCがメモリを安全に管理できるようになります。

5.  **テストケースの調整**:
    *   `test/fixedbugs/issue4388.go`と`test/fixedbugs/issue5856.go`のテストケースが更新され、`checkLine`や`runtime.Caller`の引数が変更されています。これは、ランタイムのスタックフレームの構造やカウント方法が変更されたことに対応するための調整です。特に`issue4388.go`のコメントは、内部ランタイムフレームの数が変更されたことを明示しています。
    *   `misc/cgo/test/issue7695_test.go`に`// +build ignore`と`// This test depends on running C code on Go stacks. Not allowed anymore.`というコメントが追加されています。これは、CGOとGoスタック間の特定の相互作用が、この変更によってもはやサポートされないか、異なる方法で処理されるようになったことを示唆しています。

これらの変更は、Goランタイムのパニック処理をより統一的で、`reflect`メカニズムと統合されたものにすることで、スタック管理の複雑さを軽減し、将来的な改善のための基盤を築いています。特に、`newstackcall`が引き起こしていたスタックセグメントの動的な作成という副作用を排除することで、パニック時のスタックの連続性と`recover`の信頼性が向上しています。

## コアとなるコードの解説

上記のコアとなる変更箇所について、その技術的な意味合いを詳しく解説します。

1.  **`src/pkg/runtime/panic1.go`における`gopanic`の変更**:
    *   **変更前**: `newstackcall(d.fn, unsafe.Pointer(&d.args), uint32(d.siz))`
    *   **変更後**: `reflectcall(unsafe.Pointer(d.fn), unsafe.Pointer(&d.args), uint32(d.siz), uint32(d.siz), (*_panic)(noescape(unsafe.Pointer(&p))))`
    *   この変更は、パニック時に`defer`関数を呼び出すメカニズムの根本的な変更です。以前は`newstackcall`が使用されていましたが、これは新しいスタックセグメントを作成する可能性があり、パニック処理の複雑さを増していました。
    *   `reflectcall`は、`reflect`パッケージの内部的な関数呼び出しメカニズムであり、より汎用的な関数呼び出しを可能にします。新しい引数`(*_panic)(noescape(unsafe.Pointer(&p)))`は、現在のパニックに関する情報（`_panic`構造体へのポインタ）を`reflectcall`に渡すことを意味します。これにより、`reflectcall`の実行中に`recover`が呼び出された場合、`recover`は正しいパニックコンテキストにアクセスできるようになります。
    *   `gp.panicwrap`と`p.outerwrap`の操作は、スタックの調整（特に`recover`がスタックを巻き戻す際）において、スタックフレームのオフセットを正確に計算するために使用されます。これは、`recover`がパニックの起点となったスタックフレームを正確に特定し、その時点から実行を再開するために不可欠です。

2.  **`src/pkg/runtime/runtime.h`における`_panic`構造体の変更**:
    *   **追加フィールド**:
        *   `uintptr argp;`: このフィールドは、`defer`関数が呼び出された際の引数ポインタを格納します。`recover`がパニックを捕捉した際、この`argp`を使用して、パニックの起点となったスタックフレームの引数領域を特定します。これにより、`recover`はパニックの原因となった値を正確に取得できます。
        *   `uint32 outerwrap;`: `gp->panicwrap`の以前の値を保存します。`panicwrap`は、スタックフレームのサイズ調整に関連する値で、特に`recover`がスタックを巻き戻す際に、スタックポインタを正しく調整するために使用されます。このフィールドにより、ネストされたパニックや`recover`のシナリオでも、スタックの整合性が保たれます。
    *   **削除フィールド**:
        *   `bool panic;` (from `Stktop`): 以前は`Stktop`構造体（スタックフレームのトップを表す）に`panic`フラグがありましたが、これが削除されました。これは、パニックの状態管理が`_panic`構造体と`gp->panicwrap`を通じてより集中的に行われるようになったことを示唆しています。

3.  **`src/pkg/reflect/value.go`における`call`関数のシグネチャ変更**:
    *   `func call(fn, arg unsafe.Pointer, n uint32, retoffset uint32)` から `func call(fn, arg unsafe.Pointer, n uint32, retoffset uint32, panicpos unsafe.Pointer)` への変更は、`reflect.call`がパニック処理のコンテキストで呼び出される際に、パニック関連の情報を直接受け取れるようにするためのものです。`panicpos`は、`_panic`構造体へのポインタとして使用され、`reflect.call`の内部で`panic_argp`の設定などに利用されます。

4.  **アセンブリコード（`asm_*.s`）の変更**:
    *   **`newstackcall`の削除**: 各アーキテクチャのアセンブリファイルから`runtime·newstackcall`のコードが完全に削除されたことは、この関数がGoランタイムから完全に排除されたことを意味します。これにより、`newstackcall`が引き起こしていたスタックセグメントの動的な作成という副作用がなくなります。
    *   **`reflect·call`と`CALLFN`マクロの変更**:
        *   これらのアセンブリコードは、`reflect.call`が受け取る新しい`panic`引数を処理するように修正されています。
        *   特に重要なのは、`panic_argp`フィールドの設定とクリアです。`CALLFN`マクロ内で、`panic`引数が`nil`でない場合、現在のスタックポインタに基づいて`panic_argp`が設定されます。これは、`reflect.call`が実行する関数の引数領域を`_panic`構造体に記録することで、`recover`がその情報を利用してパニックの起点に戻れるようにするためです。関数呼び出しが完了すると、`panic_argp`はクリアされます。
        *   `gcargs_reflectcall<>`の変更は、`reflect.call`の引数が増えたことに伴い、ガベージコレクタがスタック上のポインタを正確に識別するためのメタデータが更新されたことを示しています。これにより、`reflect.call`を通じて呼び出される関数が、GCによって正しく処理されることが保証されます。

5.  **`src/pkg/runtime/stack.c`における`adjustpanics`と`runtime·newstack`の変更**:
    *   **`adjustpanics`**: この関数は、スタックがコピーされたり移動したりする際に、`_panic`構造体内のポインタ（特に`argp`）を新しいスタック上の正しい位置に調整します。これにより、スタックが移動しても`recover`が機能し続けることが保証されます。
    *   **`runtime·newstack`**: スタック成長の主要な関数です。ここから`newstackcall`に関連するロジックが削除されたことで、スタック成長のプロセスが簡素化され、パニック処理との結合が緩やかになりました。`StackCopyAlways`の導入は、スタックコピーが常に可能であることを前提とする新しいスタック管理モデルへの移行を示唆しています。

これらの変更は、Goランタイムのパニック処理をより堅牢で、`reflect`メカニズムと統合されたものにすることで、スタック管理の複雑さを軽減し、将来的な改善のための基盤を築いています。特に、`newstackcall`が引き起こしていたスタックセグメントの動的な作成という副作用を排除することで、パニック時のスタックの連続性と`recover`の信頼性が向上しています。

# [インデックス 21311] ファイルの概要

このコミットは、GoランタイムにおけるPlan 9オペレーティングシステム向けの`brk_`システムコールのシグネチャの修正に関するものです。特に、`uintptr`型が原因で発生していたメモリ割り当ての失敗検出の問題を解決し、Plan 9/amd64ビルドの安定性を向上させています。

## 変更の背景

このコミットは、GoランタイムがPlan 9オペレーティングシステム上で動作する際に発生していた、メモリ割り当てに関するバグを修正するために導入されました。具体的には、`brk_`システムコールの戻り値の型が`uintptr`として定義されていたことが問題でした。

Plan 9の`brk`システムコールは、メモリ割り当てに失敗した場合に`-1`を返します。しかし、Goの`uintptr`型は符号なし整数型であるため、`-1`という負の値を正しく表現できません。`uintptr`として`-1`を受け取ると、それは非常に大きな正の数として解釈されてしまいます。

この誤った解釈により、`mem_plan9.go`内の`sbrk()`関数で、`brk_`からの戻り値が負であるかどうかのチェック（` < 0`）が常に失敗していました。結果として、メモリ割り当てが実際に失敗していても、ランタイムはその失敗を検知できず、不正なメモリ領域を使用しようとしてクラッシュする可能性がありました。

コミットメッセージによると、この問題は特にPlan 9/amd64環境で顕著でした。`mallocinit()`関数が起動時に136GBという非常に大きなメモリを割り当てようとした際に、この失敗検出の不備が露呈し、ビルドが失敗していました。一方で、Plan 9/386環境では、偶然にもこのような大規模な割り当て失敗が発生しなかったため、問題が表面化していませんでした。

この修正は、`brk_`の戻り値の型を`int32`に変更することで、システムコールが返す`-1`というエラー値を正しく解釈できるようにし、ランタイムがメモリ割り当ての失敗を適切に処理できるようにすることを目的としています。

## 前提知識の解説

### 1. `brk`システムコールとメモリ管理

`brk`（または`sbrk`）は、Unix系システムやそれに類するOS（Plan 9も含む）で利用されるシステムコールの一つで、プロセスのデータセグメントの境界（プログラムブレーク）を調整するために使用されます。データセグメントは、プログラムのグローバル変数や静的変数が格納される領域であり、通常、ヒープ領域の開始点でもあります。

*   **`brk(addr)`**: プログラムブレークを`addr`に設定します。成功すると`0`を返し、失敗すると`-1`を返します。
*   **`sbrk(increment)`**: プログラムブレークを`increment`バイトだけ増減させます。成功すると新しいプログラムブレークの開始アドレスを返し、失敗すると`(void*)-1`を返します。

Goランタイムは、独自のメモリ管理メカニズム（Goのヒープ）を持っていますが、その基盤となるメモリ領域をOSから取得するために、このようなシステムコールを利用します。`brk_`は、GoランタイムがPlan 9上で`brk`システムコールを呼び出すためのラッパー関数と考えられます。

### 2. `uintptr`型と`int32`型

Go言語には、ポインタと整数型の間で変換を行うための特殊な型がいくつか存在します。

*   **`uintptr`**: 符号なし整数型で、ポインタを保持するのに十分な大きさがあります。これは、ポインタを整数として扱う必要がある場合（例えば、システムコールにアドレスを渡す場合や、アラインメントの計算など）に用いられます。しかし、`uintptr`は「符号なし」であるため、負の値を表現できません。負の値を`uintptr`にキャストすると、その値は非常に大きな正の数として解釈されます（例: `-1`は`0xFFFFFFFF`または`0xFFFFFFFFFFFFFFFF`など、そのシステムのポインタサイズに応じた最大値として扱われる）。
*   **`int32`**: 32ビット符号付き整数型です。正の値だけでなく、負の値も表現できます。システムコールがエラーを示すために`-1`のような負の値を返す場合、この型で受け取ることで正しくエラーを検出できます。

このコミットの核心は、`brk_`システムコールがエラー時に返す`-1`という値を、`uintptr`ではなく`int32`で受け取ることで、そのエラーを正しく識別できるようにすることにあります。

### 3. Plan 9オペレーティングシステム

Plan 9 from Bell Labsは、Unixの後継として設計された分散オペレーティングシステムです。Unixの哲学をさらに推し進め、すべてのリソースをファイルとして表現し、それらをネットワーク越しに透過的にアクセスできるような設計思想を持っています。Go言語の開発者の一部はPlan 9の開発にも携わっており、Go言語の設計思想にもPlan 9の影響が見られます。

Plan 9は、その独特な設計と高い一貫性から、研究や特定のニッチな分野で利用されていますが、一般的なOSとしては普及していません。しかし、Go言語が様々なプラットフォームをサポートする上で、Plan 9もそのターゲットの一つとなっています。

### 4. Goランタイムのメモリ初期化 (`mallocinit()`)

Goプログラムが起動する際、Goランタイムは自身のメモリ管理システムを初期化します。これには、OSから初期のメモリ領域を確保する作業が含まれます。`mallocinit()`のような関数は、この初期メモリ確保のプロセスを担当します。このプロセス中にOSからのメモリ確保が失敗すると、プログラムは正常に起動できません。

コミットメッセージにある「attempt to allocate 136GB in mallocinit()」は、Goランタイムが起動時に大量のメモリを確保しようとしたことを示唆しており、この初期割り当ての失敗がPlan 9/amd64でのビルド失敗の直接的な原因でした。

## 技術的詳細

このコミットの技術的な問題は、GoランタイムがPlan 9上でメモリを管理する際に、OSの`brk`システムコールからのエラー応答を正しく処理できていなかった点に集約されます。

Plan 9の`brk`システムコールは、メモリ割り当てに失敗した場合、慣例的に`-1`を返します。Goランタイムの`src/runtime/os_plan9.go`ファイルには、このシステムコールをGoから呼び出すためのラッパー関数`brk_`が定義されていました。

修正前の`brk_`関数のシグネチャは以下のようになっていました。

```go
func brk_(addr unsafe.Pointer) uintptr
```

ここで問題となるのが、戻り値の型が`uintptr`であることです。`uintptr`は符号なし整数型であるため、`brk`システムコールが返す`-1`という負の値は、`uintptr`に変換されると、そのシステムのポインタサイズに応じた最大値（例: 64ビットシステムでは`0xFFFFFFFFFFFFFFFF`）として解釈されてしまいます。

この`brk_`の戻り値は、`mem_plan9.go`内の`sbrk()`関数（またはそれに相当するメモリ割り当て関数）で利用されていました。`sbrk()`のような関数では、通常、システムコールが成功したかどうかを判断するために、戻り値が負であるかどうかのチェック（例: `if result < 0 { /* エラー処理 */ }`）を行います。

しかし、`brk_`が`uintptr`を返すと、`-1`が非常に大きな正の数として解釈されるため、`result < 0`という条件は決して真になりません。つまり、`brk`システムコールが実際に失敗して`-1`を返していたとしても、Goランタイムはそれを成功と誤認し、エラー処理ロジックが実行されませんでした。

この問題は、特にPlan 9/amd64環境で顕在化しました。`mallocinit()`（Goランタイムのメモリ初期化ルーチン）が起動時に136GBという非常に大きなメモリ領域を確保しようとした際、この割り当てがOSによって拒否され、`brk`システムコールは`-1`を返しました。しかし、Goランタイムはこれをエラーとして認識せず、存在しないメモリ領域を操作しようとしたため、クラッシュや予期せぬ動作を引き起こし、結果としてPlan 9/amd64ビルドが失敗していました。

一方、Plan 9/386環境では、`mallocinit()`が要求するメモリ量が偶然にもOSが許容する範囲内であったか、あるいは他の要因により、このような大規模な割り当て失敗が発生しなかったため、同じバグが存在していても問題が表面化していませんでした。

このコミットは、`brk_`関数の戻り値の型を`int32`に変更することで、この根本的な問題を解決しています。`int32`は符号付き整数型であるため、システムコールが返す`-1`を正しく負の値として解釈できます。これにより、`sbrk()`関数内のエラーチェックが正しく機能し、メモリ割り当ての失敗を適切に検出し、それに応じたエラー処理を行うことが可能になります。

## コアとなるコードの解説

変更された行は、GoランタイムがPlan 9の`brk`システムコールを呼び出すためのGo側の関数シグネチャを定義しています。

修正前:
```go
func brk_(addr unsafe.Pointer) uintptr
```
この定義では、`brk_`関数は`unsafe.Pointer`型のアドレスを受け取り、`uintptr`型の値を返すと宣言されています。前述の通り、`uintptr`は符号なし整数であるため、システムコールが返すエラー値`-1`を正しく表現できませんでした。

修正後:
```go
func brk_(addr unsafe.Pointer) int32
```
この修正により、`brk_`関数の戻り値の型が`int32`に変更されました。`int32`は32ビットの符号付き整数型であり、`-1`のような負の値を正確に表現できます。これにより、`brk`システムコールがメモリ割り当てに失敗して`-1`を返した場合、Goランタイムはその値を正しく負の数として認識し、適切なエラー処理ロジック（例えば、`mem_plan9.go`内の`sbrk()`関数での` < 0`チェック）がトリガーされるようになります。

この小さな型変更が、Plan 9/amd64環境でのGoランタイムのメモリ初期化時のクラッシュを防ぎ、ビルドを成功させるための重要な鍵となりました。これは、システムコールインターフェースとGoの型システム間の整合性を確保することの重要性を示す良い例です。

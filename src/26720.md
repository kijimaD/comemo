# [インデックス 26720] ファイルの概要

このコミットは、GoランタイムがLinux/386アーキテクチャ上でシステムコールを呼び出す方法を根本的に変更するものです。具体的には、これまで一部の環境で利用されていた`vsyscall`メカニズム（`%gs:0x10`経由）の使用を廃止し、代わりに伝統的な`int $0x80`命令を常に使用するように統一しています。この変更は、`bionic`（Androidで使用されるCライブラリ）や`musl`（軽量なCライブラリ）といった、`%gs:0x10`に`vsyscall`ヘルパーを提供しない環境との互換性問題を解決することを目的としています。また、ベンチマークにより`int $0x80`が既存の`vsyscall`呼び出しと同程度の速度であることが確認されたため、パフォーマンスを大きく損なうことなく互換性を向上させることが可能になりました。これにより、vDSO（Virtual Dynamic Shared Object）に関連するコードも削除され、ランタイムの複雑性が軽減されています。

## 変更の背景

Goランタイムは、Linux/386アーキテクチャ上でシステムコールを実行する際に、パフォーマンス最適化のために`vsyscall`メカニズムを利用していました。特に、`glibc`を使用する標準的なLinuxシステムでは、`__kernel_vsyscall`エントリポイントが`%gs`レジスタのオフセット`0x10`に格納されており、Goランタイムはこのエントリポイントを`CALL 0x10(GS)`命令で呼び出すことで、高速なシステムコールを実現していました。

しかし、このアプローチには互換性の問題がありました。Androidで使用されるC標準ライブラリである`bionic`や、軽量なC標準ライブラリである`musl`は、`glibc`とは異なり、`%gs:0x10`に`vsyscall`ヘルパーを提供していませんでした。このため、Goプログラムがこれらのライブラリを使用する環境で実行されると、システムコール呼び出しが失敗するか、予期せぬ動作を引き起こす可能性がありました。

この問題を解決するため、Goチームはシステムコール呼び出しメカニズムの見直しを行いました。ベンチマークの結果、伝統的な`int $0x80`命令によるシステムコール呼び出しが、Linux/386環境において`%gs:0x10`経由の`vsyscall`呼び出しとほぼ同等の速度であることが判明しました（ただし、AMD Opteronプロセッサでは例外があることが示唆されています）。この性能特性により、互換性の問題を解決するために`int $0x80`に切り替えることが、パフォーマンスの大きな犠牲なしに可能であると判断されました。

この変更により、Goランタイムは異なるC標準ライブラリ環境（特に`bionic`や`musl`）においても、Linux/386上で一貫してシステムコールを実行できるようになり、互換性が大幅に向上しました。また、`vsyscall`に依存しなくなったことで、vDSOに関連する複雑なコード（vDSOアドレスの追跡やシグナルハンドラでの特殊なアンワインド処理など）を削除することができ、ランタイムのコードベースが簡素化されました。この変更は、Go Issue #14476で報告された問題の解決策として実施されました。

## 前提知識の解説

### システムコール (System Call)
システムコールは、ユーザー空間で実行されるプログラムが、オペレーティングシステム（カーネル）が提供するサービス（ファイルI/O、メモリ管理、プロセス制御、ネットワーク通信など）を利用するためのインターフェースです。プログラムが直接ハードウェアにアクセスすることはセキュリティ上、安定性上の問題があるため、カーネルが仲介役となり、安全な方法でサービスを提供します。システムコールを呼び出す際には、ユーザーモードからカーネルモードへのコンテキストスイッチが発生し、これには一定のオーバーヘッドが伴います。

### `int 0x80`
`int 0x80`は、32-bit x86 (i386) アーキテクチャにおける伝統的なシステムコール呼び出しメカニズムです。これはソフトウェア割り込みの一種で、CPUが`int 0x80`命令を実行すると、割り込みディスクリプタテーブル（IDT: Interrupt Descriptor Table）を参照して対応する割り込みハンドラ（この場合はシステムコールハンドラ）に制御を移します。このプロセスには、ユーザーモードからカーネルモードへの切り替え、レジスタの状態保存、IDTルックアップなどのオーバーヘッドが含まれます。システムコール番号は`EAX`レジスタに、引数は`EBX`, `ECX`, `EDX`, `ESI`, `EDI`などのレジスタに格納されて渡されます。

### `vsyscall` (Virtual System Call) と vDSO (Virtual Dynamic Shared Object)
`vsyscall`は、Linuxカーネルが導入した、頻繁に呼び出される特定のシステムコール（例: `gettimeofday()`）のパフォーマンスを向上させるためのメカニズムです。`int 0x80`のような完全なコンテキストスイッチのオーバーヘッドを避けることを目的としています。
`vDSO`は、この`vsyscall`メカニズムを実装するために使用される技術です。vDSOは、カーネルによって各プロセスのアドレス空間にマッピングされる小さな共有ライブラリ（例: `linux-gate.so.1`）です。このライブラリには、最適化されたシステムコールの実装が含まれており、ユーザー空間から直接呼び出すことができます。vDSO内の関数は、`sysenter`や`syscall`といった、`int 0x80`よりも高速なプロセッサ固有の命令を利用してシステムコールを実行します。これにより、コンテキストスイッチのオーバーヘッドが削減され、システムコールが高速化されます。

### `%gs:0x10`
`%gs:0x10`は、`glibc`を使用する一部のLinuxシステムにおいて、`__kernel_vsyscall`エントリポイントのアドレスが格納されるメモリ位置を指します。`GS`レジスタはセグメントレジスタの一つで、特定のメモリセグメントのベースアドレスを指すために使用されます。`0x10`はそのセグメント内でのオフセットです。このメカニズムは、位置独立コード（PIC: Position-Independent Code）から`vsyscall`ヘルパーに高速にアクセスできるようにするために利用されていました。`CALL 0x10(GS)`のような命令で直接呼び出すことが可能でした。

### `bionic`
`bionic`は、GoogleがAndroidプラットフォーム向けに開発したC標準ライブラリです。`glibc`（GNU C Library）とは異なり、メモリと処理能力が限られたモバイルデバイス向けに、より軽量で効率的であることを目指して設計されています。`bionic`は、`glibc`が提供するすべての機能を提供するわけではなく、またシステムコール呼び出しのメカニズムも`glibc`とは異なる場合があります。特に、`%gs:0x10`に`vsyscall`ヘルパーを提供しない点が、Goランタイムの互換性問題の原因となっていました。

### `musl`
`musl`は、軽量で高速、かつシンプルさを特徴とするC標準ライブラリです。LinuxシステムコールAPI上に直接構築されており、組み込みシステム、コンテナ環境、静的リンクされたバイナリなどに適しています。`glibc`や`bionic`と同様に、`musl`も独自のシステムコール呼び出しメカニズムを持っていますが、`bionic`と同様に`%gs:0x10`に`vsyscall`ヘルパーを提供しないため、Goランタイムの互換性問題を引き起こしていました。

### Linux/386
`Linux/386`は、32-bit x86 (Intel 80386以降) アーキテクチャ上で動作するLinuxシステムを指します。このアーキテクチャは、現代の64-bitシステムとは異なるレジスタセット、メモリ管理、システムコールインターフェースを持っています。Goランタイムは、異なるアーキテクチャごとに最適化されたコードパスを持っており、このコミットは特に`Linux/386`環境におけるシステムコール処理に焦点を当てています。

## 技術的詳細

このコミットの技術的詳細は、GoランタイムがLinux/386環境でのシステムコール呼び出しを、特定のC標準ライブラリ（`glibc`）に依存しない、より普遍的な方法に切り替えることにあります。

### 1. システムコール呼び出しメカニズムの統一

以前のGoランタイムでは、システムコールを呼び出す際に、コンパイル時のターゲットOS（`GOOS_android`かどうか）に基づいて異なるアセンブリコードを使用していました。
*   `GOOS_android`の場合: `INT $0x80`を使用。
*   それ以外の場合（主に`glibc`環境）: `CALL 0x10(GS)`を使用。これは`glibc`が`%gs:0x10`に`__kernel_vsyscall`エントリポイントを配置していることに依存していました。

このコミットでは、`src/runtime/sys_linux_386.s`と`src/syscall/asm_linux_386.s`内の`INVOKE_SYSCALL`マクロの定義が変更され、常に`INT $0x80`を使用するように統一されました。

```assembly
// 変更前 (例: src/runtime/sys_linux_386.s)
-#ifdef GOOS_android
-#define INVOKE_SYSCALL	INT	$0x80
-#else
-#define INVOKE_SYSCALL	CALL	0x10(GS)
-#endif

// 変更後
// #define INVOKE_SYSCALL	CALL	0x10(GS) // non-portable
#define INVOKE_SYSCALL	INT	$0x80
```
この変更により、`bionic`や`musl`のように`%gs:0x10`に`vsyscall`ヘルパーを提供しない環境でも、Goランタイムがシステムコールを正しく実行できるようになります。

### 2. vDSO関連コードの削除

`vsyscall`メカニズムへの依存を排除した結果、vDSOに関連するいくつかのコードが不要になりました。

*   **`src/runtime/os_linux_386.go`**:
    *   `_vdso`変数の定義が削除されました。この変数はvDSOのアドレスを格納するために使用されていましたが、vDSOを直接利用しなくなったため不要になりました。
    *   `sysargs`関数内で、`auxv` (Auxiliary Vector) から`_AT_SYSINFO`エントリを読み取り、vDSOのアドレスを`_vdso`に割り当てる処理が削除されました。

*   **`src/runtime/rt0_linux_386.s`**:
    *   `_fallback_vdso`関数が削除されました。この関数は、vDSOが利用できない場合に`int $0x80`を呼び出すフォールバックメカニズムを提供していましたが、常に`int $0x80`を使用するようになったため、このフォールバックは不要になりました。
    *   `runtime·_vdso`変数の定義と、`_fallback_vdso`のアドレスで初期化する処理も削除されました。

*   **`src/runtime/signal_386.go`**:
    *   シグナルハンドラ内で、vsyscall領域で発生したシグナルのスタックトレースを正確にアンワインドするための特殊なロジックが削除されました。以前は、vsyscallルーチンがスタックに保存する値の数を推測し、プログラムカウンタ（PC）とスタックポインタ（SP）を調整していましたが、vsyscallを使用しなくなったため、この複雑な処理は不要になりました。これにより、`tracebacktrap`関数に直接現在のPCとSPが渡されるようになり、コードが簡素化されました。

### 3. `setldt`における`__kernel_vsyscall`エントリポイントの格納処理の削除

`src/runtime/sys_linux_386.s`の`runtime·setldt`関数内には、`glibc`の動的リンカの挙動を模倣し、`__kernel_vsyscall`エントリポイントを`0x10(GS)`に格納する処理がありました。これは、静的リンクされたバイナリでも`CALL 0x10(GS)`を使用できるようにするためのものでしたが、Goランタイムがこのエントリポイントを使用しなくなったため、この格納処理も削除されました。

### 4. パフォーマンスに関する考慮

コミットメッセージに明記されているように、`int $0x80`が`CALL 0x10(GS)`とほぼ同等の速度であることがベンチマークで確認されています。これは、互換性の向上とコードの簡素化を、パフォーマンスの大きな低下なしに実現できるという重要な根拠となりました。現代のLinuxカーネルとCPUは、`int $0x80`のオーバーヘッドを最小限に抑えるための最適化を施している可能性があり、特に32-bit x86環境ではその影響が小さいと考えられます。

これらの変更により、GoランタイムはLinux/386環境において、より堅牢で互換性の高いシステムコール呼び出しメカニズムを獲得し、同時にコードベースの複雑性を軽減することに成功しました。

# [インデックス 23882] ファイルの概要

このコミットは、Go言語の`compress/lzw`パッケージにおいて、LZW圧縮器が`litWidth`（リテラルコードのビット幅）で表現できないバイト値を書き込もうとした際に、それを拒否する機能を追加するものです。これにより、不正な入力データによる圧縮エラーや予期せぬ動作を防ぎ、堅牢性を向上させています。

## 変更の背景

LZW (Lempel-Ziv-Welch) 圧縮アルゴリズムでは、`litWidth`というパラメータが初期辞書のリテラルコードのビット幅を定義します。例えば、`litWidth`が8の場合、0から255までの256個のバイト値がリテラルコードとして扱われます。しかし、`litWidth`が8未満に設定された場合（例えば、`litWidth=2`であれば、リテラルコードは0から3までしか表現できません）、入力データに`litWidth`で表現できないバイト値（例えば、`litWidth=2`の時に値4以上のバイト）が含まれていると、圧縮処理が正しく行われない可能性がありました。

このコミット以前の`compress/lzw`パッケージの`writer`は、このような不正な入力バイト値に対する検証を行っていませんでした。その結果、圧縮器が予期せぬ動作をしたり、不正な圧縮データが生成されたりする可能性がありました。この問題はGoのIssue #11142として報告され、このコミットはその問題を解決するために導入されました。具体的には、`litWidth`で表現可能な最大値を超える入力バイトを検出した場合に、明示的にエラーを返すように変更されました。

## 前提知識の解説

### LZW圧縮

LZW (Lempel-Ziv-Welch) 圧縮は、可逆データ圧縮アルゴリズムの一種です。これは、データ内の繰り返しパターンをより短いコードに置き換えることで機能します。LZWは、GIF画像フォーマットやPDFファイルなどで広く利用されています。

アルゴリズムの基本的な考え方は以下の通りです。
1.  **初期辞書**: 既知のシンボル（通常は単一のバイト値）で初期化された辞書から始まります。
2.  **辞書の拡張**: 入力データを読み込みながら、既知のシーケンス（文字列）を辞書に追加していきます。
3.  **コードの出力**: 最長一致するシーケンスを辞書から見つけ、そのシーケンスに対応するコードを出力します。
4.  **動的な学習**: 圧縮器と展開器は、同じロジックで辞書を動的に構築するため、辞書自体を送信する必要がありません。

### `litWidth` (リテラルコードのビット幅)

`litWidth`は、LZW圧縮において非常に重要なパラメータです。これは、初期辞書に格納される「リテラルコード」のビット幅を定義します。
*   **リテラルコード**: LZW辞書の基本となるコードで、通常は単一の入力シンボル（バイト）に対応します。
*   **`litWidth`の役割**: `litWidth`が`N`ビットの場合、初期辞書には`2^N`個のリテラルコードが予約されます。例えば、`litWidth=8`であれば、`2^8 = 256`個のコードが0から255までのバイト値に割り当てられます。これは、一般的なバイトストリームを扱う場合に最もよく使われる設定です。
*   **入力バイトとの関係**: `litWidth`が8未満に設定された場合、入力バイトの値は`litWidth`で表現可能な範囲に収まっている必要があります。例えば、`litWidth=2`の場合、リテラルコードは00, 01, 10, 11の4つ（値0, 1, 2, 3）しか表現できません。もし入力データに値4以上のバイトが含まれていると、それは`litWidth=2`の初期辞書では直接表現できない「不正な」バイトとなります。

### Goの`compress/lzw`パッケージ

Go言語の標準ライブラリに含まれる`compress/lzw`パッケージは、LZW圧縮フォーマットを実装しています。
*   `lzw.NewWriter(w io.Writer, order lzw.Order, litWidth int)`: LZW圧縮を行う`io.WriteCloser`を返します。`litWidth`パラメータは、前述のリテラルコードのビット幅を指定します。
*   `lzw.NewReader(r io.Reader, order lzw.Order, litWidth int)`: LZW展開を行う`io.ReadCloser`を返します。圧縮時と展開時で`litWidth`が一致している必要があります。

このパッケージは、LZW圧縮の一般的な用途（GIFなど）に対応していますが、TIFFファイルフォーマットで使われるLZWとは互換性がありません。

## 技術的詳細

このコミットの主要な変更は、`src/compress/lzw/writer.go`の`encoder`構造体の`Write`メソッドに、入力バイトの検証ロジックを追加したことです。

1.  **`maxLit`の計算**:
    ```go
    if maxLit := uint8(1<<e.litWidth - 1); maxLit != 0xff {
    ```
    `e.litWidth`は`encoder`が使用するリテラルコードのビット幅です。`1 << e.litWidth`は`2^litWidth`を計算し、そこから1を引くことで、`litWidth`で表現できる最大のリテラル値（例: `litWidth=2`なら`1<<2 - 1 = 3`）を求めます。この値は`uint8`にキャストされ、`maxLit`として保持されます。
    `maxLit != 0xff`という条件は、`litWidth`が8未満の場合にのみ以下の検証ループを実行するための最適化です。`litWidth=8`の場合、`maxLit`は`0xff`（255）となり、すべての`uint8`値が表現可能であるため、検証は不要です。

2.  **入力バイトの検証ループ**:
    ```go
    for _, x := range p {
        if x > maxLit {
            e.err = errors.New("lzw: input byte too large for the litWidth")
            return 0, e.err
        }
    }
    ```
    入力バイトスライス`p`の各バイト`x`に対して、`x`が`maxLit`よりも大きいかどうかをチェックします。もし大きい場合、そのバイトは現在の`litWidth`では表現できないため、エラーメッセージ「`lzw: input byte too large for the litWidth`」を含む`errors.New`を生成し、`e.err`に設定して即座にエラーを返します。これにより、不正なデータが圧縮処理に進むのを防ぎます。

3.  **`litMask`の削除**:
    ```diff
    -	litMask := uint32(1<<e.litWidth - 1)
    ...
    -		code, p = uint32(p[0])&litMask, p[1:]
    ...
    -		literal := uint32(x) & litMask
    ```
    以前のコードでは、入力バイトをリテラルコードとして扱う際に、`litMask`を使って`litWidth`の範囲に収まるようにビットマスクしていました。しかし、今回の変更で入力バイトが事前に`litWidth`の範囲内であることが保証されるようになったため、このビットマスク処理は不要となり、削除されました。これにより、コードが簡潔になり、わずかながらパフォーマンスも向上します。

4.  **テストケースの追加**:
    `src/compress/lzw/writer_test.go`に`TestSmallLitWidth`という新しいテスト関数が追加されました。このテストは、`litWidth`が小さい場合（例: `litWidth=2`）に、`litWidth`で表現可能なバイト値（例: `0x03`）は正常に書き込めるが、表現不可能なバイト値（例: `0x04`）はエラーを返すことを検証します。これにより、新しい検証ロジックが正しく機能することを確認しています。

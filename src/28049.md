# [インデックス 28049] ファイルの概要

このコミットは、Go言語のツールチェインにおいて、`darwin/arm`アーキテクチャ向けの`c-archive`ビルドモードで生成されるコードから絶対アドレス指定を排除し、Position-Independent Code (PIC) を生成できるようにする変更を導入しています。これにより、システムリンカが生成されたアーカイブを使用してPosition-Independent Executable (PIE) をリンクすることが可能になります。具体的には、GoリンカのARMアーキテクチャ向けMach-Oファイル生成ロジックと、Cgoランタイムの初期化処理が修正されています。

## 変更の背景

このコミットの主な背景は、`darwin/arm` (主にiOSデバイスなどのARMベースのAppleプラットフォーム) 向けにGoコードをC言語のアーカイブ (`.a`ファイル) としてビルドする際に、Position-Independent Code (PIC) を生成できるようにすることです。これにより、生成されたアーカイブをシステムリンカがPosition-Independent Executable (PIE) としてリンクできるようになります。

以前は、`darwin/arm`向けの`c-archive`ビルドでは絶対アドレスが使用されており、これがPIC/PIEの生成を妨げていました。PIC/PIEは、特にセキュリティの観点から重要です。Address Space Layout Randomization (ASLR) と組み合わせて使用することで、実行可能ファイルのメモリレイアウトをランダム化し、バッファオーバーフローなどの攻撃を困難にします。

この変更により、Goの`c-archive`がPICとしてビルドされることがデフォルトとなり、Goコードを含むアプリケーションがより安全なPIEとしてビルドされる道が開かれました。コミットメッセージにある`Fixes #12896`は、この問題に関連するGoのイシュートラッカーの項目を示唆していますが、現在の検索では直接的な情報は見つかりませんでした。しかし、このコミットが特定のビルドシナリオにおける制約を解消し、現代的なセキュリティ要件に対応するための改善であることは明らかです。

## 前提知識の解説

### 1. Position-Independent Code (PIC) と Position-Independent Executable (PIE)

*   **Position-Independent Code (PIC)**: メモリ上のどの位置にロードされても正しく実行できるコードです。これは、絶対メモリアドレスではなく、プログラムカウンタ (PC) からの相対アドレス指定や、Global Offset Table (GOT) および Procedure Linkage Table (PLT) を介した間接参照を使用することで実現されます。PICは主に共有ライブラリ (`.so`や`.dylib`) で使用され、複数のプロセスが同じライブラリを異なるメモリアドレスにロードして共有することを可能にします。
*   **Position-Independent Executable (PIE)**: PICで構築された実行可能ファイルです。PIEは、実行時にランダムなメモリアドレスにロードされるため、Address Space Layout Randomization (ASLR) と組み合わせて使用することで、セキュリティを大幅に向上させます。攻撃者が特定のコードやデータのメモリアドレスを予測することを困難にし、エクスプロイトの成功率を低下させます。

### 2. `c-archive`ビルドモード

Go言語の`go build -buildmode=c-archive`コマンドは、GoパッケージをC言語の静的ライブラリ (`.a`ファイル) とCヘッダファイルにコンパイルします。このアーカイブは、C/C++/Objective-Cアプリケーションにリンクして、Goコードをそのアプリケーションの一部として利用できるようにするために使用されます。

### 3. `darwin/arm`

AppleのmacOS/iOSプラットフォームで動作するARMアーキテクチャを指します。特にiOSデバイスはARMベースであり、セキュリティ上の理由からPIEが強く推奨され、多くの場合必須とされています。

### 4. Mach-O (Mach Object)

macOS、iOS、watchOS、tvOSなどのAppleのオペレーティングシステムで使用される実行可能ファイル、オブジェクトコード、共有ライブラリ、動的ロード可能コード、およびコアダンプのファイル形式です。Mach-Oファイルは、セクション、セグメント、リロケーションエントリなどを含みます。

### 5. リロケーション (Relocation)

リンカがプログラム内のシンボル参照 (変数や関数のアドレスなど) を、最終的なメモリアドレスに解決するプロセスです。PIC/PIEでは、実行時にアドレスが決定されるため、特殊なリロケーションタイプが使用されます。

### 6. Mach-O ARMリロケーションタイプ

*   **`MACHO_ARM_RELOC_SECTDIFF` (または `GENERIC_RELOC_SECTDIFF`)**: 2つのシンボルのアドレス間の差分を解決するために使用されるリロケーションタイプです。例えば、「シンボル1 - シンボル2 + 定数」のような式を解決します。
*   **`MACHO_ARM_RELOC_PAIR` (または `GENERIC_RELOC_PAIR`)**: `MACHO_ARM_RELOC_SECTDIFF`の直後に続くリロケーションタイプです。`SECTDIFF`リロケーションが開始した計算を完了するために必要な追加情報 (例えば、シンボル2のアドレスや関連するオフセット) を提供します。これらはペアで使用され、相対オフセットを正確に解決するために不可欠です。

### 7. `obj.R_PCREL`

Goリンカ内部で使用されるリロケーションタイプの一つで、PC (プログラムカウンタ) 相対リロケーションを示します。これは、命令のアドレスからの相対オフセットとしてアドレスを解決するために使用されます。

### 8. `obj.SHOSTOBJ`

Goリンカ内部で、外部のホストオブジェクト (Go以外の言語で書かれたオブジェクトファイル) からのシンボルを示すために使用されるシンボルタイプです。

## 技術的詳細

このコミットは、`darwin/arm`向けの`c-archive`ビルドでPIC/PIEを可能にするために、Goツールチェインの複数のコンポーネントにわたる協調的な変更を導入しています。

1.  **`go build`コマンドの変更 (`src/cmd/go/build.go`)**:
    `darwin/arm`ターゲットで`c-archive`ビルドモードが指定された場合、リンカに`-shared`フラグを渡すように変更されました。このフラグは、リンカに対して共有ライブラリまたはPIC互換のコードを生成するよう指示するもので、Goの`c-archive`がPICとしてビルドされるための重要なステップです。

2.  **ARMリンカのリロケーション処理の強化 (`src/cmd/link/internal/arm/asm.go`)**:
    `R_PCREL`タイプのリロケーション、特に外部シンボルへのPC相対参照を処理するために、Mach-Oの「scattered relocation」メカニズムが導入されました。
    *   `obj.R_PCREL`タイプのリロケーションが発生し、かつそれが外部シンボル (`rs.Type == obj.SHOSTOBJ`) でない場合、Goリンカは単一のリロケーションエントリではなく、`MACHO_ARM_RELOC_SECTDIFF`と`MACHO_ARM_RELOC_PAIR`の2つの「scattered relocation」エントリを生成します。
    *   `MACHO_ARM_RELOC_SECTDIFF`は、シンボルと命令のセクションアドレスの差分を解決するための情報を持ちます。
    *   `MACHO_ARM_RELOC_PAIR`は、`SECTDIFF`リロケーションを補完し、最終的な相対アドレスを正確に計算するために必要な追加情報を提供します。
    *   これにより、リンカは実行時にアドレスを解決できるような、位置独立なコードを生成できるようになります。

3.  **リンカのデータ処理の調整 (`src/cmd/link/internal/ld/data.go`)**:
    `relocsym`関数内で、ARMアーキテクチャ向けのリロケーションオフセット計算が調整されました。これは、`machoreloc1`で導入された新しいリロケーション処理と整合性を保つための変更であり、PC相対リロケーションが正しく処理されるようにします。

4.  **Mach-O構造体の拡張とセクション配置の調整 (`src/cmd/link/internal/ld/macho.go`)**:
    *   `MACHO_ARM_RELOC_PAIR`と`MACHO_ARM_RELOC_SECTDIFF`という新しいMach-O ARMリロケーションタイプが定数として定義されました。
    *   `machoshbits`関数において、非実行可能セクションを`__DATA`セグメントに移動する条件が拡張されました。以前は`arm64`および`amd64`の`c-shared`/`c-archive`ビルドモードに限定されていましたが、この変更により`arm`アーキテクチャの`c-shared`/`c-archive`ビルドモードも含まれるようになりました。これは、Darwinの外部リンカが`__TEXT`セグメント内の絶対リロケーションについて警告を発するため、非実行可能データが`__TEXT`に配置されるのを避けるための措置です。これにより、PIC/PIEの要件を満たしやすくなります。

5.  **Cgoランタイムの修正 (`src/runtime/cgo/signal_darwin_armx.go`)**:
    `x_cgo_panicmem`という外部シンボルの初期化方法が変更されました。以前は直接`funcPC(panicmem)`の結果を代入していましたが、これをポインタ (`_cgo_panicmem`) を介して間接的に代入するように修正されました。
    *   `var _cgo_panicmem = &x_cgo_panicmem`：`x_cgo_panicmem`のアドレスを指すポインタを導入。
    *   `*_cgo_panicmem = funcPC(panicmem)`：ポインタを介して値を代入。
    この変更は、`__TEXT`セクション内の外部シンボルのリロケーションを回避し、リンカがPICを生成する際の制約を緩和することを目的としています。

これらの変更が連携することで、`darwin/arm`向けのGo `c-archive`がPICとして生成され、最終的にPIEとしてリンクされることが可能になります。

## コアとなるコードの解説

このコミットの核となる変更は、Goリンカが`darwin/arm`向けの`c-archive`をビルドする際に、絶対アドレスではなく位置独立な参照を生成するようにすることです。

1.  **`src/cmd/link/internal/arm/asm.go`における「scattered relocation」の導入**:
    Goリンカは、`R_PCREL`タイプのリロケーション (PC相対参照) を処理する際に、Mach-O形式の`MACHO_ARM_RELOC_SECTDIFF`と`MACHO_ARM_RELOC_PAIR`という2つの特殊なリロケーションエントリを生成するようになりました。これは「scattered relocation」と呼ばれるメカニズムで、シンボルと命令のセクションアドレスの差分を表現し、実行時にアドレスを解決できるようにします。これにより、コードがメモリ上のどの位置にロードされても正しく機能するようになります。

2.  **`src/runtime/cgo/signal_darwin_armx.go`におけるポインタによる間接参照**:
    `x_cgo_panicmem`というCgoランタイムの外部シンボルへの参照が、直接代入からポインタを介した間接代入に変更されました。これは、`__TEXT`セクション (通常は実行可能コードが配置される) 内で外部シンボルへの絶対リロケーションが発生するのを避けるためのものです。絶対リロケーションはPICの原則に反するため、この変更によりリンカがより容易にPICを生成できるようになります。具体的には、`x_cgo_panicmem`のアドレスを指すポインタ`_cgo_panicmem`を導入し、そのポインタを介して`panicmem`関数のアドレスを代入することで、リンカが`__TEXT`セクション内の絶対アドレス参照を回避できるようになります。

これらの変更により、Goの`c-archive`が`darwin/arm`上でPICとして機能し、最終的にPIEとしてリンクされるアプリケーションの一部として利用できるようになるという、重要なセキュリティと互換性の向上が実現されています。

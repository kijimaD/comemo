# [インデックス 25457] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるルートスキャン処理の並列化と効率化に関するものです。具体的には、これまでGCコーディネーターが単一スレッドで実行していたルートスキャンを、GCワーカーに分散させて並行処理させるように変更しています。これにより、GCの停止時間（STW）をさらに短縮し、GCのCPU利用率目標（25%）への適合性を高め、全体的なGC性能を向上させることを目的としています。

## 元コミット内容

このコミットは、Goランタイムのガベージコレクション（GC）において、これまでGCコーディネーターが単独で実行していたルートスキャン処理を、GCワーカーに分散させて並行処理させるように変更するものです。

現在の実装では、並行マークフェーズに入る前に、GCコーディネーターがすべてのルートスキャンを完了させていました。このスキャンは逐次的に行われるため、スキャンフェーズが長引き、マークフェーズの開始が遅れ、GCのCPU利用率目標である25%に適合しないという問題がありました。また、ルートスキャンをマークフェーズの開始前に完全に完了させる必要はなく（実際にはスキャンフェーズ中にGCアシストが発生することは既に許容されていました）、これはルートスキャンとマークフェーズ間の不要な障壁となっていました。

この変更により、ルートスキャン作業はGCコーディネーターからGCワーカーに移管されます。コーディネーターはスキャン状態を設定し、適切な数のルートスキャンジョブをキューに入れるだけになります。GCワーカーは、ヒープスキャンジョブを処理する前に、これらのルートスキャンジョブを処理します。

この変更によって、ルートスキャンプロセスが並列化され、GCの25% CPU利用率目標に適合するようになります。また、ルートスキャンが独立したフェーズとして実質的に排除され、システムがルートスキャンからヒープマークへスムーズに移行できるようになります。さらに、GCコーディネーターの非STW（Stop-The-World）時の主要な責任が一つ減るため、分散型ステートマシンへの移行が容易になります。最後に、GCサイクルの開始時にアシストを満たすのに役立つ、アシスト内でのルートスキャン実行の基盤を築きます。

実装は概ね単純ですが、一つ注意すべき点として、プリエンプションデッドロックの問題があります。これは、2つの非プリエンプティブなゴルーチンが互いのスタックをスキャンしようとしてプリエンプトし合う状況です。このコンテキストでは、2つのバックグラウンドワーカーが互いをスキャンしようとする場合にのみ発生します。これを回避するために、並行フェーズ中はバックグラウンドワーカーのスタックをスキャンしないようにします。これは、マーク終了フェーズでそれらをスキャンするため安全であり、バックグラウンドワーカーのスタックは非常に小さく、新しいポインタを含まないはずであるため問題ありません。

この変更では、マーク終了フェーズ中のルートマーキングも、並行マークと同じ`gcDrain`ベースのコードパスを使用するように切り替わります。STWルートマーキングは既に並列化されており、ルートマーキングタスクがなくなるとすぐにヒープマーキングに切り替わっていたため、パフォーマンスへの影響は無視できるはずです。しかし、これによりコードが簡素化され、これらのコードパスが統合されます。

go1ベンチマークへの影響はごくわずかです。`XBenchGarbage`ベンチマークではわずかに遅くなりますが、これはGCがわずかに頻繁に実行されるようになったためと考えられます。

## 変更の背景

Goのガベージコレクション（GC）は、アプリケーションの実行を一時停止するStop-The-World（STW）時間を最小限に抑えることを目標に進化してきました。このコミットが行われた時点のGo GCは、並行マーク＆スイープ方式を採用しており、ほとんどのGC作業をアプリケーションの実行と並行して行います。

しかし、このコミット以前のGo GCでは、並行マークフェーズの開始前に「ルートスキャン」という重要なステップがGCコーディネーター（通常は単一のM/P）によって逐次的に実行されていました。ルートスキャンとは、GCの起点となるオブジェクト（グローバル変数、スタック上の変数、レジスタなど）を特定し、それらから到達可能なオブジェクトをマークするプロセスの初期段階です。

この逐次的なルートスキャンには以下の問題がありました。

1.  **STW時間の延長**: ルートスキャンが完了するまで並行マークフェーズを開始できないため、この逐次処理がボトルネックとなり、GCのSTW時間を不必要に延長させていました。
2.  **CPU利用率目標からの逸脱**: Go GCは、GC作業に利用するCPU時間を全体の25%に抑えるという目標（"25% CPU goal"）を持っています。しかし、逐次的なルートスキャンは、この目標に沿ってCPUリソースを調整することが難しく、一時的にCPUを過剰に消費する可能性がありました。
3.  **マークフェーズの遅延**: ルートスキャンが完了するまでヒープのマークを開始できないため、GC全体のサイクルが長くなり、メモリの再利用が遅れる可能性がありました。
4.  **コーディネーターの負担**: GCコーディネーターに非STW時の大きな責任が集中しており、将来的なGCアーキテクチャの分散化を妨げる要因となっていました。

これらの問題を解決し、GCの効率と並行性をさらに向上させるために、ルートスキャン処理をGCワーカーに分散させ、並行して実行することが提案されました。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションの基本的な仕組みと関連する概念を理解しておく必要があります。

### Goのガベージコレクション (GC)

GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにした並行GCです。これは、オブジェクトを白、灰、黒の3色に分類してマークし、不要なオブジェクトを特定して回収するプロセスです。

*   **白**: まだGCによって到達可能かどうかが確認されていないオブジェクト。最終的に白のまま残ったオブジェクトは回収される。
*   **灰**: 到達可能であることが確認されたが、そのオブジェクトが参照する他のオブジェクトがまだスキャンされていないオブジェクト。
*   **黒**: 到達可能であることが確認され、そのオブジェクトが参照するすべてのオブジェクトもスキャン済みであるオブジェクト。

Go GCの主要なフェーズは以下の通りです。

1.  **Sweep Termination (STW)**: 前回のGCサイクルで回収されなかったメモリ領域のスイープを完了させます。
2.  **Mark (Concurrent)**:
    *   **Root Scan**: GCの起点となるオブジェクト（ルート）を特定し、それらを灰色のキューに入れます。
    *   **Concurrent Mark**: GCワーカーが灰色のオブジェクトをキューから取り出し、参照しているオブジェクトを灰色にマークし、自身を黒にマークしてキューに戻します。このフェーズはアプリケーションの実行と並行して行われます。
    *   **Write Barrier**: このフェーズ中にアプリケーションがポインタを書き換える（新しいオブジェクトを作成したり、既存のオブジェクトの参照を変更したりする）場合、GCの正確性を保つために「ライトバリア」が作動し、変更をGCに通知します。
3.  **Mark Termination (STW)**: 短いSTWフェーズで、並行マーク中に発生した変更を処理し、GCの状態を最終調整します。
4.  **Sweep (Concurrent)**: 黒色にマークされなかった（白色の）オブジェクトが占めていたメモリ領域を解放し、再利用可能にします。このフェーズもアプリケーションの実行と並行して行われます。

### GCコーディネーターとGCワーカー

*   **GCコーディネーター**: GCサイクルの開始や終了、フェーズ間の移行など、GC全体の流れを管理する役割を担います。このコミット以前は、ルートスキャンもコーディネーターの主要なタスクでした。
*   **GCワーカー**: 並行マークフェーズ中に、ヒープ上のオブジェクトをスキャンし、到達可能なオブジェクトをマークする実際の作業を行うゴルーチンです。複数のワーカーが並行して動作します。

### ルートスキャン

プログラムの実行中に到達可能なすべてのオブジェクトは、最終的に「ルート」と呼ばれるオブジェクトから参照されています。ルートには以下のようなものがあります。

*   **グローバル変数**: プログラム全体からアクセス可能な変数。
*   **スタック上の変数**: 実行中のゴルーチンのスタックフレームに存在するローカル変数や引数。
*   **レジスタ**: CPUのレジスタに保持されているポインタ。

ルートスキャンは、これらのルートを特定し、そこから参照されているオブジェクトをGCのマークプロセスに投入する最初のステップです。

### 25% CPU目標

Go GCは、GC作業に費やすCPU時間を、アプリケーション全体のCPU時間の約25%に抑えることを目標としています。これは、GCがアプリケーションのパフォーマンスに与える影響を最小限に抑えるための重要な指標です。この目標を達成するためには、GC作業を並行化し、アプリケーションの実行とGC作業が適切にインターリーブされるようにスケジューリングする必要があります。

### プリエンプション (Preemption)

Goランタイムは、実行中のゴルーチンを一時停止させ、別のゴルーチンにCPUを割り当てる「プリエンプション」の仕組みを持っています。これにより、協調的なスケジューリングだけでなく、強制的なスケジューリングも可能になり、長時間実行されるゴルーチンが他のゴルーチンの実行を妨げることを防ぎます。GCのスタックスキャンでは、ゴルーチンのスタックを安全にスキャンするために、そのゴルーチンを一時停止させる必要があります。

### ライトバリア (Write Barrier)

並行GCでは、GCがオブジェクトをスキャンしている最中に、アプリケーションがポインタを書き換える可能性があります。この変更によってGCがオブジェクトを見落とすことを防ぐために、Go GCは「ライトバリア」という仕組みを使用します。ライトバリアは、ポインタの書き込み操作をインターセプトし、GCが必要な情報を記録できるようにします。Goのライトバリアは、通常、新しいポインタが作成されたり、既存のポインタが変更されたりしたときに、そのオブジェクトを灰色にマークするなどの処理を行います。

### `gcDrain`

`gcDrain`は、Go GCの内部関数で、GCワーカーがワークキューからGC作業（オブジェクトのスキャンやマーク）を取り出して処理するための汎用的なメカニズムです。ヒープ上のオブジェクトをスキャンするだけでなく、このコミットで示されているように、ルートスキャンジョブの処理にも利用されます。

## 技術的詳細

このコミットの技術的な核心は、Go GCのルートスキャンフェーズを、GCコーディネーターによる逐次処理から、GCワーカーによる並行処理へと移行させた点にあります。

### GCフェーズの変更

以前は、GCフェーズに`_GCscan`という独立したフェーズが存在し、ここでルートスキャンが行われていました。このコミットにより、`_GCscan`フェーズは廃止され、ルートスキャンは`_GCmark`フェーズの一部として、ヒープマークと並行してGCワーカーによって処理されるようになりました。

*   `_GCscan`フェーズの削除: `src/runtime/mgc.go`の`setGCPhase`関数から`_GCscan`が削除され、`writeBarrierEnabled`の条件からも外されました。
*   `_GCmark`フェーズの拡張: `_GCmark`フェーズが「GC marking roots and workbufs」と定義され、ルートスキャンとヒープマークの両方をカバーするようになりました。

### ルートスキャン作業の分散

1.  **ジョブキューの導入**: `work`構造体に`markrootNext`と`markrootJobs`というフィールドが追加されました。
    *   `markrootJobs`: 処理すべきルートスキャンジョブの総数。
    *   `markrootNext`: 次に処理すべきルートスキャンジョブのインデックス。
    これらのフィールドは、ルートスキャン作業を小さなジョブに分割し、GCワーカーがこれらを並行して取得・処理できるようにするために使用されます。

2.  **`gcMarkRootPrepare`の役割変更**:
    *   以前は、`gcMarkRootPrepare`はルートスキャンに必要な状態を初期化し、ルートの総数を返していました。
    *   変更後、`gcMarkRootPrepare`はルートスキャンジョブをキューに入れ（`work.markrootJobs`を設定）、`work.markrootNext`を0に初期化する役割を担うようになりました。これにより、ルートスキャンジョブがGCワーカーによって消費される準備が整います。

3.  **`gcDrain`によるルートスキャン**:

### プリエンプションデッドロックの回避

## 元コミット内容

このコミットは、Goランタイムのガベージコレクション（GC）において、これまでGCコーディネーターが単独で実行していたルートスキャン処理を、GCワーカーに分散させて並行処理させるように変更するものです。

現在の実装では、並行マークフェーズに入る前に、GCコーディネーターがすべてのルートスキャンを完了させていました。このスキャンは逐次的に行われるため、スキャンフェーズが長引き、マークフェーズの開始が遅れ、GCのCPU利用率目標である25%に適合しないという問題がありました。また、ルートスキャンをマークフェーズの開始前に完全に完了させる必要はなく（実際にはスキャンフェーズ中にGCアシストが発生することは既に許容されていました）、これはルートスキャンとマークフェーズ間の不要な障壁となっていました。

この変更により、ルートスキャン作業はGCコーディネーターからGCワーカーに移管されます。コーディネーターはスキャン状態を設定し、適切な数のルートスキャンジョブをキューに入れるだけになります。GCワーカーは、ヒープスキャンジョブを処理する前に、これらのルートスキャンジョブを処理します。

この変更によって、ルートスキャンプロセスが並列化され、GCの25% CPU利用率目標に適合するようになります。また、ルートスキャンが独立したフェーズとして実質的に排除され、システムがルートスキャンからヒープマークへスムーズに移行できるようになります。さらに、GCコーディネーターの非STW（Stop-The-World）時の主要な責任が一つ減るため、分散型ステートマシンへの移行が容易になります。最後に、GCサイクルの開始時にアシストを満たすのに役立つ、アシスト内でのルートスキャン実行の基盤を築きます。

実装は概ね単純ですが、一つ注意すべき点として、プリエンプションデッドロックの問題があります。これは、2つの非プリエンプティブなゴルーチンが互いのスタックをスキャンしようとしてプリエンプトし合う状況です。このコンテキストでは、2つのバックグラウンドワーカーが互いをスキャンしようとする場合にのみ発生します。これを回避するために、並行フェーズ中はバックグラウンドワーカーのスタックをスキャンしないようにします。これは、マーク終了フェーズでそれらをスキャンするため安全であり、バックグラウンドワーカーのスタックは非常に小さく、新しいポインタを含まないはずであるため問題ありません。

この変更では、マーク終了フェーズ中のルートマーキングも、並行マークと同じ`gcDrain`ベースのコードパスを使用するように切り替わります。STWルートマーキングは既に並列化されており、ルートマーキングタスクがなくなるとすぐにヒープマーキングに切り替わっていたため、パフォーマンスへの影響は無視できるはずです。しかし、これによりコードが簡素化され、これらのコードパスが統合されます。

go1ベンチマークへの影響はごくわずかです。`XBenchGarbage`ベンチマークではわずかに遅くなりますが、これはGCがわずかに頻繁に実行されるようになったためと考えられます。

## 変更の背景

Goのガベージコレクション（GC）は、アプリケーションの実行を一時停止するStop-The-World（STW）時間を最小限に抑えることを目標に進化してきました。このコミットが行われた時点のGo GCは、並行マーク＆スイープ方式を採用しており、ほとんどのGC作業をアプリケーションの実行と並行して行います。

しかし、このコミット以前のGo GCでは、並行マークフェーズの開始前に「ルートスキャン」という重要なステップがGCコーディネーター（通常は単一のM/P）によって逐次的に実行されていました。ルートスキャンとは、GCの起点となるオブジェクト（グローバル変数、スタック上の変数、レジスタなど）を特定し、それらから到達可能なオブジェクトをマークするプロセスの初期段階です。

この逐次的なルートスキャンには以下の問題がありました。

1.  **STW時間の延長**: ルートスキャンが完了するまで並行マークフェーズを開始できないため、この逐次処理がボトルネックとなり、GCのSTW時間を不必要に延長させていました。
2.  **CPU利用率目標からの逸脱**: Go GCは、GC作業に利用するCPU時間を全体の25%に抑えるという目標（"25% CPU goal"）を持っています。しかし、逐次的なルートスキャンは、この目標に沿ってCPUリソースを調整することが難しく、一時的にCPUを過剰に消費する可能性がありました。
3.  **マークフェーズの遅延**: ルートスキャンが完了するまでヒープのマークを開始できないため、GC全体のサイクルが長くなり、メモリの再利用が遅れる可能性がありました。
4.  **コーディネーターの負担**: GCコーディネーターに非STW時の大きな責任が集中しており、将来的なGCアーキテクチャの分散化を妨げる要因となっていました。

これらの問題を解決し、GCの効率と並行性をさらに向上させるために、ルートスキャン処理をGCワーカーに分散させ、並行して実行することが提案されました。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションの基本的な仕組みと関連する概念を理解しておく必要があります。

### Goのガベージコレクション (GC)

GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにした並行GCです。これは、オブジェクトを白、灰、黒の3色に分類してマークし、不要なオブジェクトを特定して回収するプロセスです。

*   **白**: まだGCによって到達可能かどうかが確認されていないオブジェクト。最終的に白のまま残ったオブジェクトは回収される。
*   **灰**: 到達可能であることが確認されたが、そのオブジェクトが参照する他のオブジェクトがまだスキャンされていないオブジェクト。
*   **黒**: 到達可能であることが確認され、そのオブジェクトが参照するすべてのオブジェクトもスキャン済みであるオブジェクト。

Go GCの主要なフェーズは以下の通りです。

1.  **Sweep Termination (STW)**: 前回のGCサイクルで回収されなかったメモリ領域のスイープを完了させます。
2.  **Mark (Concurrent)**:
    *   **Root Scan**: GCの起点となるオブジェクト（ルート）を特定し、それらを灰色のキューに入れます。
    *   **Concurrent Mark**: GCワーカーが灰色のオブジェクトをキューから取り出し、参照しているオブジェクトを灰色にマークし、自身を黒にマークしてキューに戻します。このフェーズはアプリケーションの実行と並行して行われます。
    *   **Write Barrier**: このフェーズ中にアプリケーションがポインタを書き換える（新しいオブジェクトを作成したり、既存のオブジェクトの参照を変更したりする）場合、GCの正確性を保つために「ライトバリア」が作動し、変更をGCに通知します。
3.  **Mark Termination (STW)**: 短いSTWフェーズで、並行マーク中に発生した変更を処理し、GCの状態を最終調整します。
4.  **Sweep (Concurrent)**: 黒色にマークされなかった（白色の）オブジェクトが占めていたメモリ領域を解放し、再利用可能にします。このフェーズもアプリケーションの実行と並行して行われます。

### GCコーディネーターとGCワーカー

*   **GCコーディネーター**: GCサイクルの開始や終了、フェーズ間の移行など、GC全体の流れを管理する役割を担います。このコミット以前は、ルートスキャンもコーディネーターの主要なタスクでした。
*   **GCワーカー**: 並行マークフェーズ中に、ヒープ上のオブジェクトをスキャンし、到達可能なオブジェクトをマークする実際の作業を行うゴルーチンです。複数のワーカーが並行して動作します。

### ルートスキャン

プログラムの実行中に到達可能なすべてのオブジェクトは、最終的に「ルート」と呼ばれるオブジェクトから参照されています。ルートには以下のようなものがあります。

*   **グローバル変数**: プログラム全体からアクセス可能な変数。
*   **スタック上の変数**: 実行中のゴルーチンのスタックフレームに存在するローカル変数や引数。
*   **レジスタ**: CPUのレジスタに保持されているポインタ。

ルートスキャンは、これらのルートを特定し、そこから参照されているオブジェクトをGCのマークプロセスに投入する最初のステップです。

### 25% CPU目標

Go GCは、GC作業に費やすCPU時間を、アプリケーション全体のCPU時間の約25%に抑えることを目標としています。これは、GCがアプリケーションのパフォーマンスに与える影響を最小限に抑えるための重要な指標です。この目標を達成するためには、GC作業を並行化し、アプリケーションの実行とGC作業が適切にインターリーブされるようにスケジューリングする必要があります。

### プリエンプション (Preemption)

Goランタイムは、実行中のゴルーチンを一時停止させ、別のゴルーチンにCPUを割り当てる「プリエンプション」の仕組みを持っています。これにより、協調的なスケジューリングだけでなく、強制的なスケジューリングも可能になり、長時間実行されるゴルーチンが他のゴルーチンの実行を妨げることを防ぎます。GCのスタックスキャンでは、ゴルーチンのスタックを安全にスキャンするために、そのゴルーチンを一時停止させる必要があります。

### ライトバリア (Write Barrier)

並行GCでは、GCがオブジェクトをスキャンしている最中に、アプリケーションがポインタを書き換える可能性があります。この変更によってGCがオブジェクトを見落とすことを防ぐために、Go GCは「ライトバリア」という仕組みを使用します。ライトバリアは、ポインタの書き込み操作をインターセプトし、GCが必要な情報を記録できるようにします。Goのライトバリアは、通常、新しいポインタが作成されたり、既存のポインタが変更されたりしたときに、そのオブジェクトを灰色にマークするなどの処理を行います。

### `gcDrain`

`gcDrain`は、Go GCの内部関数で、GCワーカーがワークキューからGC作業（オブジェクトのスキャンやマーク）を取り出して処理するための汎用的なメカニズムです。ヒープ上のオブジェクトをスキャンするだけでなく、このコミットで示されているように、ルートスキャンジョブの処理にも利用されます。

## 技術的詳細

このコミットの技術的な核心は、Go GCのルートスキャンフェーズを、GCコーディネーターによる逐次処理から、GCワーカーによる並行処理へと移行させた点にあります。

### GCフェーズの変更

以前は、GCフェーズに`_GCscan`という独立したフェーズが存在し、ここでルートスキャンが行われていました。このコミットにより、`_GCscan`フェーズは廃止され、ルートスキャンは`_GCmark`フェーズの一部として、ヒープマークと並行してGCワーカーによって処理されるようになりました。

*   `_GCscan`フェーズの削除: `src/runtime/mgc.go`の`setGCPhase`関数から`_GCscan`が削除され、`writeBarrierEnabled`の条件からも外されました。
*   `_GCmark`フェーズの拡張: `_GCmark`フェーズが「GC marking roots and workbufs」と定義され、ルートスキャンとヒープマークの両方をカバーするようになりました。

### ルートスキャン作業の分散

1.  **ジョブキューの導入**: `work`構造体に`markrootNext`と`markrootJobs`というフィールドが追加されました。
    *   `markrootJobs`: 処理すべきルートスキャンジョブの総数。
    *   `markrootNext`: 次に処理すべきルートスキャンジョブのインデックス。
    これらのフィールドは、ルートスキャン作業を小さなジョブに分割し、GCワーカーがこれらを並行して取得・処理できるようにするために使用されます。

2.  **`gcMarkRootPrepare`の役割変更**:
    *   以前は、`gcMarkRootPrepare`はルートスキャンに必要な状態を初期化し、ルートの総数を返していました。
    *   変更後、`gcMarkRootPrepare`はルートスキャンジョブをキューに入れ（`work.markrootJobs`を設定）、`work.markrootNext`を0に初期化する役割を担うようになりました。これにより、ルートスキャンジョブがGCワーカーによって消費される準備が整います。

3.  **`gcDrain`によるルートスキャン**:
    *   GCワーカーがGC作業を処理する汎用メカニズムである`gcDrain`関数が拡張され、ヒープスキャンジョブを処理する前に、`work.markrootNext`と`work.markrootJobs`を使ってルートスキャンジョブを処理するようになりました。
    *   具体的には、`gcDrain`内で`xadd(&work.markrootNext, +1) - 1`を使ってアトミックにジョブインデックスを取得し、`markroot(nil, job)`を呼び出して個々のルートスキャンジョブを実行します。

### プリエンプションデッドロックの回避

この変更の最も複雑な側面の1つは、プリエンプションデッドロックの可能性への対処です。

*   **問題**: 2つの非プリエンプティブなゴルーチン（特にGCバックグラウンドワーカー）が互いのスタックをスキャンしようとすると、デッドロックが発生する可能性があります。スタックをスキャンするためには、対象のゴルーチンを一時停止させる必要がありますが、もし両方が同時に相手を一時停止させようとすると、どちらも進めなくなります。
*   **解決策**: 並行フェーズ中（`gcphase != _GCmarktermination`）は、GCバックグラウンドワーカー（`gp.startpc == gcBgMarkWorkerPC`）のスタックをスキャンしないようにします。
    *   これは安全です。なぜなら、GCバックグラウンドワーカーのスタックは非常に小さく、新しいポインタを含まないはずであり、最終的にマーク終了フェーズでスキャンされるためです。
    *   `markroot`関数内のスタックスキャンロジックにこの条件が追加されました。

### マーク終了フェーズの統合

マーク終了フェーズにおけるルートマーキングも、並行マークと同じ`gcDrain`ベースのコードパスを使用するように変更されました。

*   以前は、マーク終了フェーズのルートマーキングは`parforsetup`と`parfordo`という並列処理フレームワークを使用していました。
*   変更後、`gchelper`関数内で`gcphase == _GCmarktermination`の場合に`gcDrain`を呼び出すことで、ルートスキャンとヒープマークの両方を処理するようになりました。
*   これにより、コードの重複が減り、GCの異なるフェーズでのマーク処理が統一され、保守性が向上します。

### パフォーマンスへの影響

コミットメッセージに記載されているベンチマーク結果は、この変更がGo 1ベンチマークに与える影響がごくわずかであることを示しています。

*   `XBenchGarbage`ベンチマークではわずかなパフォーマンス低下が見られますが、これはGCがより頻繁に実行されるようになったためと推測されています。
*   他の多くのベンチマークでは、パフォーマンスに統計的に有意な変化は見られません。
*   `JSONDecode`ベンチマークではわずかながらパフォーマンスが低下しています。

全体として、この変更はGCの内部構造を改善し、将来的な拡張性（特に分散型ステートマシンへの移行やアシストでのルートスキャン）のための基盤を築くものであり、直接的な大幅なパフォーマンス向上よりも、GCの安定性、並行性、および設計のクリーンアップに重点を置いています。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更点

```go
// 旧: _GCscan                   // GC collecting roots into workbufs, write barrier ENABLED
// 新: _GCmark                   // GC marking roots and workbufs, write barrier ENABLED
```
`_GCscan`フェーズが削除され、`_GCmark`フェーズがルートとワークバッファの両方をマークする役割を担うようになりました。これにより、ルートスキャンが独立したフェーズではなく、並行マークフェーズの一部として扱われることが明確になります。

```go
// 旧: writeBarrierEnabled = gcphase == _GCmark || gcphase == _GCmarktermination || gcphase == _GCscan
// 新: writeBarrierEnabled = gcphase == _GCmark || gcphase == _GCmarktermination
```
ライトバリアが有効になる条件から`_GCscan`が削除されました。これは、ルートスキャンが`_GCmark`フェーズに統合されたため、`_GCscan`という独立したフェーズでライトバリアを有効にする必要がなくなったことを意味します。

```go
	pad0  [_CacheLineSize]uint8 // prevents false-sharing between full/empty and nproc/nwait

	markrootNext uint32 // next markroot job
	markrootJobs uint32 // number of markroot jobs

	nproc   uint32
	tstart  int64
	nwait   uint32
	// ...
}
```
`work`構造体に`markrootNext`と`markrootJobs`が追加されました。これらは、ルートスキャン作業を並列化するためのジョブキューの管理に使用されます。`markrootJobs`は処理すべきルートスキャンジョブの総数を保持し、`markrootNext`は次に処理すべきジョブのインデックスを追跡します。

GCサイクルの開始時に、`_GCscan`フェーズへの移行が削除され、直接`_GCmark`フェーズに移行するようになりました。また、GCコーディネーターによる逐次ルートスキャンを実行していた`gcscan_m()`の呼び出しが削除されました。これにより、ルートスキャンが並行マークフェーズの一部としてGCワーカーに分散されることが示されます。

```go

// 新: (削除)
```
`gcscan_m`関数が完全に削除されました。これは、GCコーディネーターが単独でルートスキャンを実行するメカニズムが廃止されたことを明確に示しています。

```go
// markroot scans the i'th root.
//
// Preemption must be disabled (because this uses a gcWork).
//
//go:nowritebarrier
func markroot(desc *parfor, i uint32) {
	// ...
	case i >= work.fixedRootCount+work.nDataRoots+work.nBSSRoots+work.nSpanRoots && i < work.fixedRootCount+work.nDataRoots+work.nBSSRoots+work.nSpanRoots+work.nStackRoots:
		// Stack roots
		gp := allg[i-(work.fixedRootCount+work.nDataRoots+work.nBSSRoots+work.nSpanRoots)]
		if gp == nil || gp.gcscandone {
			break
		}

		if gcphase != _GCmarktermination && gp.startpc == gcBgMarkWorkerPC {
			// GC background workers may be
			// non-preemptible, so we may deadlock if we
			// try to scan them during a concurrent phase.
			// They also have tiny stacks, so just ignore
			// them until mark termination.
			gp.gcscandone = true
			break
		}
		// ...
}
```
`markroot`関数内のスタックスキャンロジックに、プリエンプションデッドロックを回避するための重要な変更が加えられました。`gcphase != _GCmarktermination`（つまり並行フェーズ中）かつ、対象のゴルーチンがGCバックグラウンドワーカー（`gp.startpc == gcBgMarkWorkerPC`）である場合、そのスタックはスキャンされずにスキップされます。これは、バックグラウンドワーカーが非プリエンプティブである可能性があり、互いにスキャンしようとするとデッドロックが発生する可能性があるためです。これらのスタックは小さく、新しいポインタを含まないため、マーク終了フェーズでスキャンしても問題ないと判断されています。

```go
// gcDrain scans roots and objects in work buffers, blackening grey
// objects until all roots and work buffers have been drained.
// ...
func gcDrain(gcw *gcWork, flags gcDrainFlags) {
	// ...
	// Drain root marking jobs.
	if work.markrootNext < work.markrootJobs {
		for blocking || !gp.preempt {
			job := xadd(&work.markrootNext, +1) - 1
			if job >= work.markrootJobs {
				break
			}
			// TODO: Pass in gcw.
			markroot(nil, job)
		}
	}

	// Drain heap marking jobs.
	initScanWork := gcw.scanWork
	// ...
}
```
`gcDrain`関数が拡張され、ヒープスキャンジョブを処理する前にルートスキャンジョブを処理するようになりました。`work.markrootNext`と`work.markrootJobs`を使用して、利用可能なルートスキャンジョブをアトミックに取得し、`markroot`関数を呼び出して実行します。これにより、GCワーカーがルートスキャンとヒープスキャンの両方を並行して処理できるようになります。

### `src/runtime/mgcwork.go` の変更点

```go
// 旧: if work.nwait == work.nproc {
// 新: if work.nwait == work.nproc && work.markrootNext >= work.markrootJobs {
// ...
```
`getfull`関数内の条件が変更されました。GCワーカーが待機状態に入る（つまり、利用可能な作業がないと判断する）のは、すべてのプロセッサが待機しており（`work.nwait == work.nproc`）、かつ、すべてのルートスキャンジョブが完了している場合（`work.markrootNext >= work.markrootJobs`）のみとなりました。これにより、ルートスキャンジョブが残っている限り、ワーカーは待機状態に入らずに作業を続けることができます。

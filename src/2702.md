## 変更の背景

このコミットは、Go言語がまだ開発の初期段階にあった2009年に行われました。`net/rpc`パッケージは、Goプログラム間でリモートプロシージャコールを行うための標準的なメカニズムとして設計されており、その基盤となる堅牢性と信頼性は非常に重要でした。

当時の`net/rpc`実装は、エラー発生時（特にネットワーク接続の切断や不正なデータ受信時）に`panic`を引き起こす可能性があり、サーバープロセス全体がクラッシュする原因となっていました。また、クライアント側でも接続が予期せず終了した場合の適切なハンドリングが不足していました。

このコミットの主な背景は以下の点に集約されます。

1.  **堅牢性の向上**: ネットワーク通信は本質的に不安定であり、接続の切断、データの破損、不正なリクエストなど、様々なエラーが発生し得ます。これらのエラーが発生した際に、RPCシステム全体が停止するのではなく、個々の接続やリクエストの失敗として適切に処理されるようにする必要がありました。特に、`panic`を避けてエラーを`os.Error`として返す、またはログに記録して接続をクローズする、といったより穏やかなエラーハンドリングが求められました。
2.  **テストカバレッジの拡充**: 堅牢なシステムを構築するためには、様々なエッジケースやエラーシナリオをカバーする包括的なテストが不可欠です。未知のサービス/メソッド呼び出しや不正な引数型など、予期せぬ入力に対するRPCシステムの挙動を検証するテストが不足していました。
3.  **APIの明確化と改善**: クライアント側の非同期RPC呼び出しメソッドの名称が`Start`から`Go`に変更され、よりGoらしい慣用的な命名に統一されました。また、サーバー側での接続受け入れと処理の分離により、APIの役割が明確化されました。
4.  **デバッグの容易性**: `gob`デコーダーのエラーメッセージをより詳細にすることで、型不一致の問題が発生した際に、開発者が原因を特定しやすくなりました。

これらの改善は、GoのRPCパッケージが実用的なネットワーク通信ライブラリとして成熟していく上で不可欠なステップでした。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語の基本的な概念とパッケージに関する知識が必要です。

1.  **GoのRPC (Remote Procedure Call)**:
    *   Goの`net/rpc`パッケージは、異なるアドレス空間（通常は異なるプロセスや異なるマシン）にあるプログラム間で関数やメソッドを呼び出すためのメカニズムを提供します。
    *   クライアントはリモートのメソッドをローカルのメソッドであるかのように呼び出し、サーバーはその呼び出しを受け取って処理し、結果をクライアントに返します。
    *   `net/rpc`は、ネットワーク越しにGoの構造体やプリミティブ型をやり取りするために、デフォルトで`encoding/gob`パッケージを使用します。

2.  **Goの`encoding/gob`パッケージ**:
    *   `gob`は、Goのデータ構造をシリアライズ（バイト列に変換）およびデシリアライズ（バイト列からデータ構造に復元）するためのGo固有のバイナリエンコーディング形式です。
    *   `gob`は「自己記述型」であり、データストリーム内に型情報を含みます。これにより、エンコーダーとデコーダー間で厳密に同じ型定義がなくても、互換性のある型であればデコードが可能です（ただし、このコミットでは型不一致を厳しくチェックする方向で改善されています）。
    *   Goの`reflect`パッケージを内部的に利用して、任意のGoの型を効率的にエンコード・デコードします。

3.  **`io.ReadWriteCloser`インターフェース**:
    *   Goの標準ライブラリで定義されているインターフェースで、`io.Reader`、`io.Writer`、`io.Closer`の3つのインターフェースを組み合わせたものです。
    *   `Read(p []byte) (n int, err error)`: データを読み込む機能。
    *   `Write(p []byte) (n int, err error)`: データを書き込む機能。
    *   `Close() error`: リソースをクローズする機能。
    *   ネットワーク接続（`net.Conn`など）やファイルなど、読み書きとクローズが可能なリソースを抽象化するために広く使用されます。`net/rpc`では、クライアントとサーバー間の通信チャネルとしてこのインターフェースを利用します。

4.  **`sync.Mutex`**:
    *   Goの`sync`パッケージが提供する相互排他ロック（ミューテックス）です。
    *   複数のゴルーチンが共有リソース（例: マップ、スライス、構造体のフィールド）に同時にアクセスする際に、データ競合を防ぎ、安全なアクセスを保証するために使用されます。
    *   `Lock()`メソッドでロックを取得し、`Unlock()`メソッドでロックを解放します。

5.  **`reflect`パッケージ**:
    *   Goの`reflect`パッケージは、プログラムの実行時に変数や型の情報を検査・操作するための機能を提供します。
    *   `net/rpc`サーバーでは、クライアントから呼び出されたメソッド名に基づいて、サーバーに登録されているサービスオブジェクトの対応するメソッドを動的に探し、引数をデコードしてメソッドを呼び出し、結果をエンコードするために`reflect`パッケージが extensively 使用されます。
    *   `reflect.Value`や`reflect.Type`といった型を通じて、実行時の型情報にアクセスします。

6.  **`os.Error`**:
    *   Goの初期バージョン（Go 1.1以前）では、エラーは`os.Error`インターフェースとして表現されていました。これは現在の`error`インターフェースの前身です。
    *   `os.ErrorString`は、文字列から`os.Error`を生成するためのヘルパー関数でした。

7.  **`panic`と`log.Stderr`**:
    *   `panic`は、Goにおける回復不能なエラーを示すメカニズムです。`panic`が発生すると、現在のゴルーチンは実行を停止し、遅延関数が実行された後、コールスタックを遡り、最終的にプログラム全体がクラッシュする可能性があります（`recover`で捕捉されない限り）。
    *   `log.Stderr`は、標準エラー出力にログメッセージを書き込むための関数です。`panic`とは異なり、プログラムの実行を中断せず、エラー情報を記録する目的で使用されます。このコミットでは、`panic`を`log.Stderr`に置き換えることで、サーバーの堅牢性を高めています。

## 技術的詳細

このコミットは、GoのRPCクライアントとサーバーの堅牢性を大幅に向上させ、エラーハンドリングを改善し、テストカバレッジを拡充しています。

### 1. `gob`デコーダーのエラーメッセージ改善 (`src/pkg/gob/decoder.go`)

-   **変更点**: 型不一致エラーが発生した際のエラーメッセージがより詳細になりました。
-   **詳細**: 以前は単に `"gob decode: incorrect type for wire value"` と表示されていましたが、変更後は `want [期待される型名]; received [受け取った型名]` という形式で、期待される型と実際に受け取った型が明示されるようになりました。
-   **効果**: これにより、デバッグ時に型不一致の原因を特定するのが格段に容易になります。

### 2. RPCクライアントの堅牢性向上 (`src/pkg/rpc/client.go`)

-   **`Client`構造体への`closed`フィールド追加**:
    -   `closed bool;` フィールドが追加され、クライアント接続が閉じられた状態を追跡できるようになりました。
    -   これにより、閉じられたクライアントに対してRPC呼び出しを行おうとした際に、早期にエラーを返すことが可能になります。
-   **`serve`ゴルーチンのエラーハンドリング強化**:
    -   クライアントの`serve`メソッドは、サーバーからの応答を非同期にデコードし続けるゴルーチンです。
    -   以前はデコードエラーが発生すると`panicln`を呼び出していましたが、変更後は`client.dec.Decode(response)`が`os.EOF`を返した場合にループを`break`し、接続が正常に終了したことを示します。
    -   その他のデコードエラーが発生した場合も`break`し、`log.Stderr`にエラーを記録するようになりました。これにより、クライアントプロセス全体がクラッシュするのを防ぎ、個々の接続の問題として処理されます。
    -   ループ終了後、`client.closed = true`を設定し、クライアントが閉じられた状態であることをマークします。
    -   `log.Stderr("client protocol error:", err)`: 接続が終了した理由をログに記録します。
-   **`Start`メソッドから`Go`メソッドへのリネームと改善**:
    -   非同期RPC呼び出しを行うメソッド名が`Start`から`Go`に変更されました。これはGo言語の慣用的な命名規則に合わせたものです。
    -   `Go`メソッド内で`client.closed`をチェックし、クライアントが既に閉じられている場合は`os.EOF`エラーを設定して即座に`Call`構造体を返すようになりました。これにより、無効なクライアントに対する呼び出しが無駄な処理を行うことを防ぎます。
-   **`Call`メソッドの改善**:
    -   `Call`メソッドは`Go`メソッドを利用するように変更され、`client.closed`のチェックも追加されました。これにより、同期的なRPC呼び出しも閉じられたクライアントに対しては早期にエラーを返すようになります。

### 3. RPCサーバーの堅牢性向上と接続管理 (`src/pkg/rpc/server.go`)

-   **`InvalidRequest`構造体の導入**:
    -   `type InvalidRequest struct { marker int }` と `var invalidRequest = InvalidRequest{1}` が追加されました。これは、不正なリクエストに対する応答のプレースホルダーとして使用されます。
-   **`sendResponse`ヘルパー関数の導入**:
    -   `func (s *service) sendResponse(sending *sync.Mutex, req *Request, reply interface{}, enc *gob.Encoder, errmsg string)` が追加されました。
    -   この関数は、RPC応答のヘッダーとペイロードをエンコードしてクライアントに送信するロジックを一元化します。エラーメッセージ (`errmsg`) を引数として受け取ることで、エラー応答の送信が容易になりました。
    -   これにより、サーバーコード内の応答送信ロジックの重複が削減され、保守性が向上します。
-   **`call`メソッドのリファクタリング**:
    -   `call`メソッドは、実際のサービスメソッド呼び出しを行い、その結果を`sendResponse`関数を使ってクライアントに返します。エラー処理が`sendResponse`に委譲される形になりました。
-   **`serve`ゴルーチンのエラーハンドリング強化**:
    -   サーバーの`serve`メソッドは、単一のクライアント接続からのリクエストを処理し続けるゴルーチンです。
    -   以前はデコードエラー、不正なサービス/メソッド名、サービス/メソッドが見つからない、引数のデコードエラーなど、様々なエラーケースで`panicln`を呼び出していましたが、これらはすべて`log.Stderr`へのエラー記録と`break`によるループ終了に置き換えられました。
    -   特に、サービスやメソッドが見つからない場合、または引数のデコードに失敗した場合、`service.sendResponse`を使用してクライアントにエラー応答を送信し、その後接続をクローズします。これにより、不正なリクエストがサーバー全体を停止させることを防ぎ、個々のクライアント接続の問題として適切に処理されます。
    -   ループ終了後、`conn.Close()`が呼び出され、接続が確実に閉じられるようになりました。
-   **`Serve`から`ServeConn`へのリネームと`Accept`関数の追加**:
    -   以前の`Serve`関数は、単一の`io.ReadWriteCloser`（つまり単一の接続）を処理する役割を持っていましたが、その役割をより明確にするために`ServeConn`にリネームされました。
    -   新しく`func (server *Server) Accept(lis net.Listener)`関数が追加されました。この関数は`net.Listener`から新しい接続を`Accept`し続け、各接続に対して`server.ServeConn(conn)`を新しいゴルーチンで起動します。
    -   **効果**: これにより、RPCサーバーは複数のクライアント接続を同時に、かつ非同期に処理できるようになり、スケーラビリティと応答性が向上しました。`log.Exit`が使用されていますが、これは当時のGoのエラーハンドリングの慣習の一部であり、後のバージョンでより洗練されたエラー処理パターンに進化していきます。

### 4. テストの拡充 (`src/pkg/rpc/server_test.go`)

-   **`startServer`の`once.Do`化**:
    -   `startServer`関数が`once.Do(startServer)`で呼び出されるようになりました。これにより、テストスイート全体でRPCサーバーが一度だけ起動されることが保証され、テストのセットアップが効率化されます。
-   **新しいテストケースの追加**:
    -   `TestCheckUnknownService`: 存在しないサービスを呼び出した場合に、RPCクライアントが適切にエラーを返すことを検証します。
    -   `TestCheckUnknownMethod`: 存在するサービス内の存在しないメソッドを呼び出した場合に、RPCクライアントが適切にエラーを返すことを検証します。
    -   `TestCheckBadType`: サービスメソッドの引数として不正な型を渡した場合に、RPCクライアントが適切にエラーを返すことを検証します。
-   **効果**: これらの新しいテストは、RPCサーバーのエラーハンドリングロジックが様々な不正な入力に対して正しく機能することを保証し、システムの堅牢性をさらに高めます。

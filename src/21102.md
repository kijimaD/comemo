## 元コミット内容

このコミットは、`default`ブランチ（Goのメイン開発ライン）の変更を`dev.garbage`という特定の開発ブランチにマージしたものです。コミットメッセージには「This is the revision that dev.cc is branched from.」とあり、`dev.cc`という別の開発ブランチの基点となるリビジョンであることを示唆しています。これは、Goのガベージコレクタの進化における重要なマージポイントであったことを意味します。

## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）メカニズムの進化と密接に関連しています。特に、オブジェクト内のポインタを正確に識別するための型情報の管理方法に大きな変更が加えられています。

GoのGCは「正確なGC（Precise GC）」であり、メモリ内のどの値がポインタであるかを正確に識別する必要があります。これにより、GCは誤って非ポインタデータをポインタとして解釈したり、生きているポインタを解放したりするのを防ぎます。この正確性を実現するために、Goランタイムは各型について、そのインスタンス内にポインタがどこに存在するかを示す「ポインタマスク」を保持しています。

このコミットでは、特に`_type`構造体内のGC関連情報（`typ.gc`フィールド）の解釈方法が変更され、より複雑なポインタレイアウトを持つ型（GCプログラムを持つ型）に対応するための`loadPtrMask`関数が導入されています。また、`misc/pprof`ディレクトリが大幅に削除され、`src/cmd/internal/objfile`に新しいファイルが追加されていることから、プロファイリングツールとオブジェクトファイル解析の内部構造が再編成されたことが伺えます。これは、Goのツールチェインが進化し、より堅牢な内部ライブラリ構造へと移行していることを示しています。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、並行（concurrent）かつ正確な（precise）マーク＆スイープ方式を採用しています。
- **並行性**: GCの大部分の処理は、アプリケーションの実行と並行して行われます。これにより、アプリケーションの停止時間（Stop-the-World: STW）を最小限に抑え、レイテンシを低減します。
- **正確性**: GCは、メモリ内のどの値がポインタであるかを正確に識別できます。これにより、誤ったメモリ解放やメモリリークを防ぎます。この正確性を実現するために、各型にはポインタのレイアウト情報が関連付けられています。

### `_type` 構造体

Goランタイム内部では、すべての型は`_type`構造体によって表現されます。この構造体には、型のサイズ、アラインメント、ハッシュ値、そしてGCに関連する情報などが含まれています。特に、`typ.gc`フィールドは、その型が持つポインタのレイアウト情報へのポインタを保持しています。

### ポインタマスク

ポインタマスクは、GoのGCがオブジェクト内のポインタを識別するために使用するビットマップのようなものです。オブジェクトのメモリレイアウトに対応するビット列で、各ビットはメモリワード（通常は8バイト）がポインタであるか非ポインタデータであるかを示します。GCは、このマスクを参照して、オブジェクト内のどのフィールドをスキャンして他の生きているオブジェクトを見つけるべきかを判断します。

### GCプログラム (`kindGCProg`)

一部の複雑な型（例えば、可変長配列やインターフェースなど）では、単純なビットマップではポインタのレイアウトを表現しきれない場合があります。このような場合、Goランタイムは「GCプログラム」と呼ばれるより複雑な記述を使用します。`_type`構造体の`kind`フィールドに`kindGCProg`フラグが設定されている場合、その型はGCプログラムを使用してポインタレイアウトを記述していることを示します。このGCプログラムは、GCがオブジェクトをスキャンする際に実行される一連の命令として機能します。

### `kindNoPointers` フラグ

`_type`構造体の`kind`フィールドに`kindNoPointers`フラグが設定されている場合、その型はポインタを一切含まないことを示します（例: `int`, `float64`, `string`など）。このような型はGCによるスキャンが不要であるため、GCの効率化に貢献します。

### `unsafe.Pointer`

`unsafe.Pointer`は、Goの型システムをバイパスして任意の型へのポインタとして扱える特殊なポインタ型です。Goランタイムの内部実装や、C言語との相互運用など、低レベルな操作が必要な場合に使用されます。ただし、その名の通り「unsafe」であり、誤用するとメモリ安全性やGCの正確性を損なう可能性があります。

### `atomicloadp`

`atomicloadp`は、アトミックなロード操作を行うGoランタイム内部の関数です。複数のゴルーチンが同時にアクセスする可能性のあるメモリ位置から値を読み出す際に、競合状態を防ぎ、常に最新の値を読み出すことを保証します。

### `onM`, `acquirem`, `releasem`

これらはGoランタイムのスケジューラに関連する内部関数です。
- `acquirem()`: 現在のゴルーチンがM（マシン、OSスレッド）を取得します。
- `onM(fn)`: 指定された関数`fn`を、現在のM上で実行します。これは、特定のOSスレッドのコンテキストで実行する必要がある操作（例: シグナルハンドリング、Cgoコールバックなど）に使用されます。
- `releasem(mp)`: 取得したMを解放します。

### `pprof` と `objfile`

- **`pprof`**: Goのプロファイリングツールです。CPU使用率、メモリ割り当て、ゴルーチンスタックトレースなどを収集し、プログラムのパフォーマンスボトルネックを特定するのに役立ちます。
- **`objfile`**: Goのオブジェクトファイル（実行可能ファイルやライブラリ）の解析に関連する内部パッケージです。シンボル情報、セクション情報、デバッグ情報などを読み取るために使用されます。このコミットでは、`misc/pprof`から`src/cmd/internal/objfile`へのコードの移動と再編成が行われています。

## 技術的詳細

このコミットの主要な技術的変更は、Goランタイムがオブジェクトのポインタレイアウト情報をどのように取得し、利用するかという点にあります。特に、`src/runtime/malloc.go`に追加された`loadPtrMask`関数は、このメカニズムの中心です。

### `loadPtrMask` 関数の役割

`loadPtrMask`関数は、与えられた型`_type`から、その型のインスタンス内のポインタのレイアウトを示すポインタマスク（またはGCプログラム）をロードする役割を担います。この関数は、GCがオブジェクトをスキャンする際に、どの部分がポインタであるかを正確に判断するために使用されます。

### GCプログラムの「アンロール」

`loadPtrMask`関数内で特に注目すべきは、`typ.kind&kindGCProg != 0`の条件分岐です。これは、型がGCプログラムを持っている場合に実行されるロジックです。GCプログラムは、通常、コンパクトな形式で格納されていますが、GCが効率的にスキャンできるように、より展開された（アンロールされた）形式に変換されることがあります。

このコミットでは、GCプログラムがまだアンロールされていない場合（`*(*uint8)(unsafe.Pointer(&maskword)) == 0`でチェック）、`onM(unrollgcprog_m)`を呼び出してGCプログラムをアンロールする処理が行われます。`unrollgcprog_m`は、GCプログラムを展開し、より直接的にポインタマスクとして利用できる形式に変換するランタイム内部の関数です。このアンロール処理は、特定のM（OSスレッド）上で実行される必要があります。これは、GCプログラムの展開が、メモリの割り当てや特定のCPUレジスタの状態に依存する可能性があるためです。

アンロールされたポインタマスクは、`typ.gc[0]`が指すメモリ領域に格納され、`loadPtrMask`関数はその領域へのポインタを返します。これにより、GCは効率的にポインタ情報を取得し、オブジェクトをスキャンできます。

### `newobject` 関数の変更

`newobject`関数は、新しいオブジェクトをヒープに割り当てるGoランタイムの内部関数です。このコミットでは、`flags`変数の型が`int`から`uint32`に変更されています。これは、`flags`がビットフラグとして使用され、より多くのフラグを表現できるようにするため、または特定のビット演算のコンテキストで`uint32`がより適切であるためと考えられます。

また、`typ.kind&kindNoPointers != 0`のチェックにより、ポインタを含まない型（`kindNoPointers`）の場合に`flagNoScan`フラグが設定されます。これにより、GCはこのようなオブジェクトをスキャンする必要がないことを認識し、GCのオーバーヘッドを削減します。

### `pprof` と `objfile` の再編成

`misc/pprof`ディレクトリの削除と`src/cmd/internal/objfile`へのファイルの追加は、Goのプロファイリングツールとオブジェクトファイル解析の内部構造がよりモジュール化され、再利用可能なライブラリとして整理されたことを示しています。これにより、Goのツールチェイン全体の保守性と拡張性が向上します。

## コアとなるコードの解説

### `loadPtrMask` 関数

この関数は、与えられた型`typ`のポインタマスクをロードします。

1.  `var ptrmask *uint8`: ポインタマスクへのポインタを宣言します。
2.  `nptr := (uintptr(typ.size) + ptrSize - 1) / ptrSize`: 型のサイズをポインタサイズで割ることで、その型が占めるメモリワードの数を計算します。これは、ポインタマスクの長さを決定するために使用されます。
3.  `if typ.kind&kindGCProg != 0`: 型がGCプログラムを持っているかどうかをチェックします。
    *   `masksize := nptr`: マスクの初期サイズを`nptr`に設定します。
    *   `if masksize%2 != 0 { masksize *= 2 }`: マスクサイズが奇数の場合、2倍にします。これは、GCプログラムのアンロール処理に関連するアラインメントまたは効率の要件である可能性があります。
    *   `masksize = masksize * pointersPerByte / 8`: マスクサイズをバイト単位に変換します。`pointersPerByte`は、1バイトあたりのポインタの数を示します（おそらく4ビット/ワードなので、1バイトあたり2ワード）。
    *   `masksize++`: アンロールフラグ用のバイトを追加します。
    *   `if masksize > maxGCMask && typ.gc[1] != 0 { gothrow("maxGCMask too small for now") }`: `maxGCMask`を超えるサイズのマスクの場合にエラーをスローします。これは、現在のGC実装の制限を示唆しています。
    *   `ptrmask = (*uint8)(unsafe.Pointer(uintptr(typ.gc[0])))`: `typ.gc[0]`はGCプログラムの開始アドレスを指します。これを`*uint8`にキャストして`ptrmask`に代入します。
    *   `maskword := uintptr(atomicloadp(unsafe.Pointer(ptrmask)))`: `ptrmask`が指すアドレスからアトミックに1ワードを読み込みます。これは、GCプログラムが既にアンロールされているかどうかのフラグをチェックするためです。
    *   `if *(*uint8)(unsafe.Pointer(&maskword)) == 0`: 読み込んだワードの最初のバイトが0の場合、GCプログラムはまだアンロールされていないと判断します。
        *   `mp := acquirem()`: 現在のM（OSスレッド）を取得します。
        *   `mp.ptrarg[0] = unsafe.Pointer(typ)`: アンロール処理に必要な型情報をMの引数に設定します。
        *   `onM(unrollgcprog_m)`: `unrollgcprog_m`関数を現在のM上で実行します。この関数がGCプログラムをアンロールします。
        *   `releasem(mp)`: Mを解放します。
    *   `ptrmask = (*uint8)(add(unsafe.Pointer(ptrmask), 1))`: アンロールフラグバイトをスキップするために、`ptrmask`を1バイト進めます。
4.  `else { ptrmask = (*uint8)(unsafe.Pointer(typ.gc[0])) }`: 型がGCプログラムを持たない場合（つまり、単純なポインタマスクである場合）、`typ.gc[0]`が直接ポインタマスクを指します。
5.  `return (*[1 << 30]byte)(unsafe.Pointer(ptrmask))[:(nptr+1)/2]`: `ptrmask`を`[]uint8`スライスに変換して返します。`[1 << 30]byte`は非常に大きな配列へのポインタとして扱われ、スライス表記で実際の長さに制限されます。`(nptr+1)/2`は、ポインタマスクのバイト数を計算しています（おそらく2ワードあたり1バイト）。

### `newobject` 関数

この関数は、新しいオブジェクトをヒープに割り当てます。

1.  `flags := uint32(0)`: `flags`変数の型が`uint32`に変更されました。
2.  `if typ.kind&kindNoPointers != 0 { flags |= flagNoScan }`: もし型がポインタを含まない場合（`kindNoPointers`フラグがセットされている場合）、`flagNoScan`フラグを`flags`に設定します。これにより、GCはこのオブジェクトをスキャンする必要がないと判断し、GCのオーバーヘッドを削減します。

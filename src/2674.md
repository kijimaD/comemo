## 変更の背景

この変更は、GoランタイムのARMアセンブリコードにおけるタイプミスを修正することを目的としています。アセンブリコードは、Goプログラムの低レベルな動作、特にゴルーチンのスケジューリングやコンテキストスイッチといったOSやハードウェアと密接に関わる部分を担っています。このような低レベルなコードにおけるタイプミスは、プログラムのクラッシュ、不正な動作、またはセキュリティ上の脆弱性につながる可能性があるため、非常に重要です。

この特定のケースでは、ゴルーチンの状態を保存する際に、ポインタのサイズに合わないデータ転送命令が使用されていました。Goランタイムは、ゴルーチンの実行コンテキスト（プログラムカウンタ、スタックポインタ、レジスタ値など）を `gobuf` と呼ばれる構造体に保存し、必要に応じて復元することでゴルーチンの切り替えを実現します。この保存処理において、ポインタのサイズと一致しない命令を使用すると、データが正しく保存されず、結果としてゴルーチンの復元に失敗したり、メモリ破壊を引き起こしたりする可能性があります。このコミットは、このような潜在的な問題を未然に防ぐための修正です。

## 前提知識の解説

### ARMアーキテクチャ

ARM (Advanced RISC Machine) は、モバイルデバイスや組み込みシステムで広く使用されているRISC (Reduced Instruction Set Computer) ベースのプロセッサアーキテクチャです。低消費電力と高性能を両立させる設計が特徴で、スマートフォン、タブレット、IoTデバイス、最近ではサーバーやデスクトップPCにも採用されています。Go言語は、ARMを含む多くのアーキテクチャをサポートしており、それぞれのアーキテクチャに最適化されたランタイムコードを持っています。

### アセンブリ言語 (ARM Assembly)

アセンブリ言語は、特定のコンピュータアーキテクチャの機械語と1対1に対応する低レベルプログラミング言語です。CPUが直接実行できる命令を人間が理解しやすいニーモニック（例: `MOV`, `ADD`, `BL`）で記述します。Goランタイムでは、C言語やGo言語では記述できない、非常に低レベルな操作（例: レジスタの直接操作、コンテキストスイッチ、メモリバリア、特定のシステムコール）を行うためにアセンブリ言語が使用されます。ARMアセンブリは、ARMプロセッサのレジスタセットと命令セットに特化しています。

### Goランタイム

Goランタイムは、Goプログラムの実行を管理する一連のライブラリとコードの集合体です。主な役割は以下の通りです。

*   **ゴルーチン (Goroutine) スケジューリング**: 多数の軽量スレッドであるゴルーチンを効率的に管理し、CPUコアに割り当てて実行します。
*   **メモリ管理 (Garbage Collection)**: 不要になったメモリを自動的に解放するガベージコレクタを提供します。
*   **スタック管理**: ゴルーチンのスタックを動的に拡張・縮小します。
*   **チャネル (Channel)**: ゴルーチン間の安全な通信メカニズムを提供します。
*   **システムコール**: OSの機能を利用するためのインターフェースを提供します。

Goランタイムの一部は、パフォーマンスや特定のハードウェア操作のためにアセンブリ言語で書かれています。

### `asm.s` ファイル

Goのソースコードにおける `asm.s` ファイルは、特定アーキテクチャ向けのアセンブリ言語で書かれたコードを格納するファイルです。Goのビルドシステムは、これらのファイルをアセンブルしてオブジェクトファイルに変換し、最終的な実行可能ファイルにリンクします。`src/pkg/runtime/arm/asm.s` は、ARMアーキテクチャ上でGoランタイムが動作するために必要な低レベルなアセンブリルーチンを含んでいます。これには、ゴルーチンの初期化、コンテキストの保存と復元、スタックの切り替え、特定の最適化された操作などが含まれます。

### `MOVW` と `MOVQ` 命令

ARMアセンブリには、データをレジスタ間やレジスタとメモリ間で転送するための様々な命令があります。

*   **`MOVW` (Move Word)**: 32ビットのデータを転送する命令です。ARMアーキテクチャにおいて、「ワード」は通常32ビットを指します。Goがサポートしていた当時のARMv5/ARMv6/ARMv7アーキテクチャでは、ポインタやレジスタの幅は32ビットが一般的でした。
*   **`MOVQ` (Move Quadword)**: 64ビットのデータを転送する命令です。これは、ARMv8-A (AArch64) アーキテクチャで導入された64ビットレジスタや、特定のデータ型（例: `int64`）を扱う際に使用されます。当時の32ビットARMアーキテクチャでは、`MOVQ`という直接的な命令は存在せず、64ビット値を扱う場合は2つの32ビットレジスタに分割して処理するか、特定の拡張命令（例: VFP/NEONのレジスタ）を使用する必要がありました。このコミットの文脈では、32ビットアーキテクチャで32ビットポインタを扱う際に `MOVQ` を使用することは不適切です。

### `gobuf` 構造体

`gobuf` はGoランタイム内部で使用される構造体で、ゴルーチンの実行コンテキストを保存するために使われます。この構造体には、ゴルーチンの再開に必要な情報、例えばプログラムカウンタ (PC)、スタックポインタ (SP)、そして現在のゴルーチンへのポインタ `g` などが含まれます。

```go
// runtime/runtime2.go (概念的な表現)
type gobuf struct {
    sp   uintptr // stack pointer
    pc   uintptr // program counter
    g    *g      // current goroutine
    // ... other fields
}
```
アセンブリコードでは、これらのフィールドに直接アクセスして値を保存・復元します。

### `reflect·call` 関数

`reflect·call` は、Goの `reflect` パッケージが内部的に使用する関数で、リフレクション機能を通じて任意の関数を呼び出す際に利用されます。リフレクションは、プログラムの実行中に型情報を調べたり、メソッドを呼び出したりする機能です。`reflect·call` は、特に異なるスタックフレームやコンテキストで関数を呼び出す必要がある場合に、アセンブリコードで実装された低レベルなスタック操作やレジスタ操作を伴います。この関数内でゴルーチンのコンテキストを `gobuf` に保存する処理が行われます。

## 技術的詳細

このコミットの技術的な核心は、32ビットARMアーキテクチャ上で32ビットポインタである `g` (現在のゴルーチンへのポインタ) を `gobuf` 構造体のフィールドに保存する際に、誤って64ビットデータ転送命令である `MOVQ` を使用していた点にあります。

当時のGoランタイムがターゲットとしていたARMアーキテクチャ（主にARMv5, ARMv6, ARMv7）は、基本的に32ビットのレジスタとアドレス空間を持っていました。したがって、ポインタのサイズも32ビットです。

`MOVQ g, (m_morebuf+gobuf_g)(m)` という命令は、`g` レジスタ（または `g` の値を保持するレジスタ）の内容を、`m` レジスタが指す `m_morebuf` のオフセット `gobuf_g` にあるメモリ位置に64ビット幅で転送しようとします。しかし、`g` は32ビットポインタであり、`gobuf_g` フィールドも32ビットポインタを格納するように設計されています。

この誤った `MOVQ` 命令が実行された場合、以下の問題が発生する可能性があります。

1.  **データ破壊**: 32ビットのポインタ `g` の値が、メモリ上の64ビット領域に書き込まれることになります。これにより、`gobuf_g` フィールドの隣接するメモリ領域が意図せず上書きされる可能性があります。これは、`gobuf` 構造体の他のフィールドや、その隣接メモリにある他のデータ構造を破壊し、予測不能な動作やクラッシュを引き起こす可能性があります。
2.  **不正な値の保存**: 32ビットの `g` の値が64ビットとして解釈されて保存される場合、上位32ビットがゼロ埋めされるか、あるいは未定義の値になる可能性があります。これにより、後で `gobuf` から `g` を復元しようとした際に、不正なポインタ値が読み込まれ、プログラムがクラッシュする原因となります。
3.  **アセンブラエラー**: 厳密なアセンブラによっては、32ビットアーキテクチャで `MOVQ` 命令がサポートされていない場合、アセンブル時にエラーとなる可能性もあります。しかし、このケースではアセンブルは通っていたものの、実行時に問題を引き起こす可能性があったと考えられます。

修正後の `MOVW g, (m_morebuf+gobuf_g)(m)` は、`g` の32ビット値を `gobuf_g` フィールドに32ビット幅で正しく転送します。これにより、メモリ破壊や不正な値の保存といった問題が解消され、ゴルーチンのコンテキスト保存・復元が正確に行われるようになります。

`reflect·call` は、Goの `reflect` パッケージが内部的に使用する関数で、リフレクション機能を通じて任意の関数を呼び出す際に利用されます。リフレクションは、プログラムの実行中に型情報を調べたり、メソッドを呼び出したりする機能です。`reflect·call` は、特に異なるスタックフレームやコンテキストで関数を呼び出す必要がある場合に、アセンブリコードで実装された低レベルなスタック操作やレジスタ操作を伴います。この関数内でゴルーチンのコンテキストを `gobuf` に保存する処理が行われます。

## 技術的詳細

このコミットの技術的な核心は、32ビットARMアーキテクチャ上で32ビットポインタである `g` (現在のゴルーチンへのポインタ) を `gobuf` 構造体のフィールドに保存する際に、誤って64ビットデータ転送命令である `MOVQ` を使用していた点にあります。

当時のGoランタイムがターゲットとしていたARMアーキテクチャ（主にARMv5, ARMv6, ARMv7）は、基本的に32ビットのレジスタとアドレス空間を持っていました。したがって、ポインタのサイズも32ビットです。

`MOVQ g, (m_morebuf+gobuf_g)(m)` という命令は、`g` レジスタ（または `g` の値を保持するレジスタ）の内容を、`m` レジスタが指す `m_morebuf` のオフセット `gobuf_g` にあるメモリ位置に64ビット幅で転送しようとします。しかし、`g` は32ビットポインタであり、`gobuf_g` フィールドも32ビットポインタを格納するように設計されています。

この誤った `MOVQ` 命令が実行された場合、以下の問題が発生する可能性があります。

1.  **データ破壊**: 32ビットのポインタ `g` の値が、メモリ上の64ビット領域に書き込まれることになります。これにより、`gobuf_g` フィールドの隣接するメモリ領域が意図せず上書きされる可能性があります。これは、`gobuf` 構造体の他のフィールドや、その隣接メモリにある他のデータ構造を破壊し、予測不能な動作やクラッシュを引き起こす可能性があります。
2.  **不正な値の保存**: 32ビットの `g` の値が64ビットとして解釈されて保存される場合、上位32ビットがゼロ埋めされるか、あるいは未定義の値になる可能性があります。これにより、後で `gobuf` から `g` を復元しようとした際に、不正なポインタ値が読み込まれ、プログラムがクラッシュする原因となります。
3.  **アセンブラエラー**: 厳密なアセンブラによっては、32ビットアーキテクチャで `MOVQ` 命令がサポートされていない場合、アセンブル時にエラーとなる可能性もあります。しかし、このケースではアセンブルは通っていたものの、実行時に問題を引き起こす可能性があったと考えられます。

修正後の `MOVW g, (m_morebuf+gobuf_g)(m)` は、`g` の32ビット値を `gobuf_g` フィールドに32ビット幅で正しく転送します。これにより、メモリ破壊や不正な値の保存といった問題が解消され、ゴルーチンのコンテキスト保存・復元が正確に行われるようになります。

## コアとなるコードの解説

変更は `src/pkg/runtime/arm/asm.s` ファイルの `reflect·call` 関数内にあります。

*   **`- MOVQ g, (m_morebuf+gobuf_g)(m)`**: 変更前の行です。ここで `MOVQ` 命令が使用されており、`g` (現在のゴルーチンへのポインタ) の値を `m_morebuf` が指すメモリ領域内の `gobuf_g` オフセットに64ビット幅で転送しようとしていました。前述の通り、32ビットARMアーキテクチャにおいて32ビットポインタを64ビットで転送しようとすることは誤りです。
*   **`+ MOVW g, (m_morebuf+gobuf_g)(m)`**: 変更後の行です。`MOVQ` が `MOVW` に修正されています。`MOVW` は32ビットのデータを転送する命令であり、32ビットポインタである `g` の値を `gobuf_g` フィールドに正しく32ビット幅で保存します。これにより、メモリの整合性が保たれ、ゴルーチンのコンテキストが正確に保存されるようになります。

この修正は、`reflect·call` 関数がリフレクションを通じて関数を呼び出す際に、現在のゴルーチンの状態を一時的に保存する処理の一部です。この保存処理が正しく行われることで、関数呼び出し後のゴルーチンの復元が問題なく行われることが保証されます。

## 前提知識の解説

### ロックフリーデータ構造とロックフリースタック

ロックフリーデータ構造は、複数のスレッドが同時にアクセスしても、ミューテックスなどのロックを使用せずに正しく動作するように設計されたデータ構造です。これにより、ロックの取得・解放によるオーバーヘッドやデッドロックのリスクを排除し、高い並行性とスループットを実現します。

ロックフリースタックは、その名の通り、ロックを使用せずにプッシュ（要素の追加）とポップ（要素の削除）操作を並行して実行できるスタックです。Goランタイムでは、ゴルーチンのスケジューリングやメモリ管理など、パフォーマンスが要求される多くの場面でロックフリーデータ構造が利用されています。

ロックフリーデータ構造の実現には、通常、アトミック操作（不可分操作）が用いられます。Go言語では、`sync/atomic` パッケージがこれらの操作を提供しますが、ランタイム内部ではより低レベルなアトミック操作が直接使用されます。特に、Compare-And-Swap (CAS) は、ロックフリーアルゴリズムの基盤となる重要なアトミック操作です。CASは、「メモリ位置の現在の値が期待値と一致する場合にのみ、そのメモリ位置の値を新しい値に更新する」という操作を不可分に実行します。

### ABA問題

ABA問題は、ロックフリーデータ構造、特にCAS操作を使用するデータ構造で発生する可能性のある、古典的かつ深刻な問題です。

**問題のシナリオ:**

1.  スレッドAが共有メモリ位置から値 `A` を読み取ります。
2.  スレッドAがプリエンプト（一時停止）されます。
3.  その間に、別のスレッドBが同じメモリ位置の値を `A` から `B` に変更し、その後再び `A` に戻します。
4.  スレッドAが再開し、再度同じメモリ位置の値を読み取ると、依然として `A` が見えます。
5.  スレッドAは、値が変更されていないと誤って判断し、CAS操作を成功させます。しかし、実際には値は一度変更され、元に戻されただけであり、その間にデータ構造の論理的な状態が変化している可能性があります。

**ロックフリースタックにおけるABA問題の例:**

ロックフリースタックの `head` ポインタをCASで更新するシナリオを考えます。

1.  スレッドAがスタックから要素をポップしようとし、現在の `head` がノード `N1` を指していることを読み取ります。
2.  スレッドAがプリエンプトされます。
3.  スレッドBが実行され、`N1` をポップします。その後、別のノード `N2` をプッシュします。このとき、メモリ再利用により、`N2` が `N1` と同じメモリアドレスに割り当てられる可能性があります。
4.  スレッドAが再開し、`head` がまだ `N1` を指していると（アドレス的には）判断し、CAS操作を成功させます。しかし、スレッドAが操作しようとしているのは、実際には `N1` とは異なる `N2` であり、これによりスタックが破損する可能性があります。

### ABA問題の解決策としてのタグ付きポインタ（バージョンカウンタ）

ABA問題を解決するための一般的な手法の一つに、「タグ付きポインタ」または「バージョンカウンタ」の使用があります。これは、ポインタ（または値）だけでなく、そのポインタが指すデータ構造のバージョン番号や変更回数を示すカウンタも一緒にCAS操作の対象とすることで、論理的な変更を検出できるようにするものです。

例えば、`head` ポインタと `version` カウンタを組み合わせた64ビット値を使用します。`head` が変更されるたびに `version` をインクリメントします。CAS操作は、`head` と `version` の両方が期待値と一致する場合にのみ成功します。これにより、値が `A` -> `B` -> `A` と変化しても、バージョンカウンタは `V1` -> `V2` -> `V3` と変化するため、2回目の `A` は `A, V3` となり、最初の `A, V1` とは異なるため、CASは失敗し、ABA問題を回避できます。

このコミットで言及されている `pushcnt` フィールドは、まさにこのようなバージョンカウンタとして機能していた可能性が高いです。

## 技術的詳細

このコミットは、`src/runtime/lfstack.c` と `src/runtime/runtime.h` の2つのファイルを変更しています。主な変更点は、`LFNode` 構造体における `next` フィールドの型と、`lfstackpush` および `lfstackpop` 関数における `pushcnt` フィールドの扱い方です。

元々の実装では、`LFNode` 構造体の `next` フィールドは `LFNode*` 型であり、ポインタと `pushcnt` (バージョンカウンタ) を組み合わせて64ビット値として `head` に格納していました。`pushcnt` は、ABA問題を緩和するために使用されていたと考えられます。`head` の下位ビットにポインタを、上位ビットに `pushcnt` を格納するようなエンコーディングが行われていました。

しかし、コミットメッセージにあるように、「`pushcnt` フィールドに競合状態がある」という疑いがあり、これが未診断のバッファ破損の原因となっていた可能性があります。これは、`pushcnt` の更新や読み取りがアトミックに行われていなかったか、あるいは複数のスレッドが同時に `pushcnt` を操作する際に予期せぬ副作用が生じていたことを示唆しています。

このコミットでは、この複雑な `pushcnt` の扱いを簡素化しています。具体的には：

1.  `src/runtime/runtime.h` において、`LFNode` 構造体の `next` フィールドの型が `LFNode*` から `uint64` に変更されています。これは、`next` フィールド自体がポインタとカウンタを組み合わせた64ビット値として扱われるようになったことを意味します。
2.  `src/runtime/lfstack.c` において、`lfstackpush` 関数では、新しいノードの `next` フィールドに `old` (現在の `head` の値、ポインタとカウンタを含む) を直接代入するよう変更されています。これにより、`node->pushcnt` を使って `new` の上位ビットを構築するロジックが削除されています。
3.  `lfstackpop` 関数では、`node->next` から `node2` を取得する際に `runtime·atomicloadp` を使用していた箇所が、`runtime·atomicload64(&node->next)` を使用して `next` (64ビット値) を直接読み取るように変更されています。また、`node2` の `pushcnt` を使って `new` を構築するロジックも削除され、`head` のCAS操作では `old` と `next` (読み取った64ビット値) を直接比較・更新するようになっています。

これらの変更は、`pushcnt` を `LFNode` の `next` フィールドの一部としてエンコードするのではなく、`next` フィールド自体を64ビットの「タグ付きポインタ」として扱うように変更したことを示唆しています。つまり、`next` フィールドの64ビット値の中に、ポインタとバージョンカウンタの両方が含まれるようになったと考えられます。これにより、`pushcnt` を個別のフィールドとして操作する際の競合状態のリスクが低減され、バッファ破損問題が解決されたと推測されます。

### `src/runtime/runtime.h` の変更

*   **`struct LFNode` の `next` フィールドの型変更**:
    *   変更前: `LFNode *next;` (ポインタ型)
    *   変更後: `uint64 next;` (64ビット符号なし整数型)
    この変更は、`LFNode` の `next` フィールドが、単なる次のノードへのポインタではなく、ポインタとバージョンカウンタ（またはタグ）を組み合わせた64ビットの「タグ付きポインタ」として扱われるようになったことを明確に示しています。これにより、`next` フィールド自体がABA問題対策のための情報を保持するようになります。

### `src/runtime/lfstack.c` の変更

#### `runtime·lfstackpush` 関数

*   **`node->next` への代入の変更**:
    *   変更前: `node->next = (LFNode*)(uintptr)(old&PTR_MASK);`
        *   これは、`head` の古い値 `old` からポインタ部分 (`PTR_MASK` でマスク) を抽出し、それを `LFNode*` にキャストして `node->next` に代入していました。
    *   変更後: `node->next = old;`
        *   新しいノードの `next` フィールドに、現在の `head` の値 `old` (ポインタとカウンタを含む64ビット値) を直接代入しています。これにより、`node->pushcnt` を使って `new` の上位ビットを構築する複雑なロジックが不要になりました。これは、`LFNode` の `next` フィールドがすでに64ビットのタグ付きポインタとして定義されているため、`old` の値をそのまま保持できるようになったことを意味します。

#### `runtime·lfstackpop` 関数

*   **変数宣言の変更**:
    *   変更前: `LFNode *node, *node2; uint64 old, new;`
    *   変更後: `LFNode *node; uint64 old, next;`
        *   `node2` と `new` 変数が削除され、代わりに `next` 変数が導入されています。これは、`node2` (次のノードのポインタ) を明示的に計算し、それと `node2->pushcnt` を組み合わせて `new` を構築するロジックが不要になったためです。
*   **`node->next` の読み取りと `new` の構築ロジックの削除**:
    *   変更前:
        ```c
        node2 = runtime·atomicloadp(&node->next);
        new = 0;
        if(node2 != nil)
            new = (uint64)(uintptr)node2|(((uint64)node2->pushcnt&CNT_MASK)<<PTR_BITS);
        ```
        *   ここでは、`node->next` から次のノードのポインタ `node2` を読み取り、その `node2` の `pushcnt` を使って新しい `head` の値 `new` を構築していました。この複雑な処理が削除されています。
    *   変更後: `next = runtime·atomicload64(&node->next);`
        *   `node->next` (64ビットのタグ付きポインタ) をアトミックに直接読み取り、`next` 変数に格納しています。
*   **CAS操作の変更**:
    *   変更前: `if(runtime·cas64(head, old, new))`
    *   変更後: `if(runtime·cas64(head, old, next))`
        *   `head` のCAS操作において、期待値 `old` と比較する新しい値として、以前計算していた `new` ではなく、`node->next` から直接読み取った `next` (64ビットのタグ付きポインタ) を使用しています。

これらの変更は、`pushcnt` を `LFNode` の `next` フィールドに統合し、`next` フィールド自体がポインタとバージョンカウンタの両方を保持する64ビット値として機能するようにしたことを示しています。これにより、`pushcnt` を個別に操作する際の複雑さや競合状態のリスクが排除され、コードが簡素化されるとともに、バッファ破損問題が解決されたと考えられます。

### ABA問題の解決策としてのタグ付きポインタ（バージョンカウンタ）

ABA問題を解決するための一般的な手法の一つに、「タグ付きポインタ」または「バージョンカウンタ」の使用があります。これは、ポインタ（または値）だけでなく、そのポインタが指すデータ構造のバージョン番号や変更回数を示すカウンタも一緒にCAS操作の対象とすることで、論理的な変更を検出できるようにするものです。

例えば、`head` ポインタと `version` カウンタを組み合わせた64ビット値を使用します。`head` が変更されるたびに `version` をインクリメントします。CAS操作は、`head` と `version` の両方が期待値と一致する場合にのみ成功します。これにより、値が `A` -> `B` -> `A` と変化しても、バージョンカウンタは `V1` -> `V2` -> `V3` と変化するため、2回目の `A` は `A, V3` となり、最初の `A, V1` とは異なるため、CASは失敗し、ABA問題を回避できます。

このコミットで言及されている `pushcnt` フィールドは、まさにこのようなバージョンカウンタとして機能していた可能性が高いです。

## 技術的詳細

このコミットは、`src/runtime/lfstack.c` と `src/runtime/runtime.h` の2つのファイルを変更しています。主な変更点は、`LFNode` 構造体における `next` フィールドの型と、`lfstackpush` および `lfstackpop` 関数における `pushcnt` フィールドの扱い方です。

元々の実装では、`LFNode` 構造体の `next` フィールドは `LFNode*` 型であり、ポインタと `pushcnt` (バージョンカウンタ) を組み合わせて64ビット値として `head` に格納していました。`pushcnt` は、ABA問題を緩和するために使用されていたと考えられます。`head` の下位ビットにポインタを、上位ビットに `pushcnt` を格納するようなエンコーディングが行われていました。

しかし、コミットメッセージにあるように、「`pushcnt` フィールドに競合状態がある」という疑いがあり、これが未診断のバッファ破損の原因となっていた可能性があります。これは、`pushcnt` の更新や読み取りがアトミックに行われていなかったか、あるいは複数のスレッドが同時に `pushcnt` を操作する際に予期せぬ副作用が生じていたことを示唆しています。

このコミットでは、この複雑な `pushcnt` の扱いを簡素化しています。具体的には：

1.  `src/runtime/runtime.h` において、`LFNode` 構造体の `next` フィールドの型が `LFNode*` から `uint64` に変更されています。これは、`next` フィールド自体がポインタとカウンタを組み合わせた64ビット値として扱われるようになったことを意味します。
2.  `src/runtime/lfstack.c` において、`lfstackpush` 関数では、新しいノードの `next` フィールドに `old` (現在の `head` の値、ポインタとカウンタを含む) を直接代入するよう変更されています。これにより、`node->pushcnt` を使って `new` の上位ビットを構築するロジックが削除されています。
3.  `lfstackpop` 関数では、`node->next` から `node2` を取得する際に `runtime·atomicloadp` を使用していた箇所が、`runtime·atomicload64(&node->next)` を使用して `next` (64ビット値) を直接読み取るように変更されています。また、`node2` の `pushcnt` を使って `new` を構築するロジックも削除され、`head` のCAS操作では `old` と `next` (読み取った64ビット値) を直接比較・更新するようになっています。

これらの変更は、`pushcnt` を `LFNode` の `next` フィールドの一部としてエンコードするのではなく、`next` フィールド自体を64ビットの「タグ付きポインタ」として扱うように変更したことを示唆しています。つまり、`next` フィールドの64ビット値の中に、ポインタとバージョンカウンタの両方が含まれるようになったと考えられます。これにより、`pushcnt` を個別のフィールドとして操作する際の競合状態のリスクが低減され、バッファ破損問題が解決されたと推測されます。

## コアとなるコードの解説

### `src/runtime/runtime.h` の変更

*   **`struct LFNode` の `next` フィールドの型変更**:
    *   変更前: `LFNode *next;` (ポインタ型)
    *   変更後: `uint64 next;` (64ビット符号なし整数型)
    この変更は、`LFNode` の `next` フィールドが、単なる次のノードへのポインタではなく、ポインタとバージョンカウンタ（またはタグ）を組み合わせた64ビットの「タグ付きポインタ」として扱われるようになったことを明確に示しています。これにより、`next` フィールド自体がABA問題対策のための情報を保持するようになります。

### `src/runtime/lfstack.c` の変更

#### `runtime·lfstackpush` 関数

*   **`node->next` への代入の変更**:
    *   変更前: `node->next = (LFNode*)(uintptr)(old&PTR_MASK);`
        *   これは、`head` の古い値 `old` からポインタ部分 (`PTR_MASK` でマスク) を抽出し、それを `LFNode*` にキャストして `node->next` に代入していました。
    *   変更後: `node->next = old;`
        *   新しいノードの `next` フィールドに、現在の `head` の値 `old` (ポインタとカウンタを含む64ビット値) を直接代入しています。これにより、`node->pushcnt` を使って `new` の上位ビットを構築する複雑なロジックが不要になりました。これは、`LFNode` の `next` フィールドがすでに64ビットのタグ付きポインタとして定義されているため、`old` の値をそのまま保持できるようになったことを意味します。

#### `runtime·lfstackpop` 関数

*   **変数宣言の変更**:
    *   変更前: `LFNode *node, *node2; uint64 old, new;`
    *   変更後: `LFNode *node; uint64 old, next;`
        *   `node2` と `new` 変数が削除され、代わりに `next` 変数が導入されています。これは、`node2` (次のノードのポインタ) を明示的に計算し、それと `node2->pushcnt` を組み合わせて `new` を構築するロジックが不要になったためです。
*   **`node->next` の読み取りと `new` の構築ロジックの削除**:
    *   変更前:
        ```c
        node2 = runtime·atomicloadp(&node->next);
        new = 0;
        if(node2 != nil)
            new = (uint64)(uintptr)node2|(((uint64)node2->pushcnt&CNT_MASK)<<PTR_BITS);
        ```
        *   ここでは、`node->next` から次のノードのポインタ `node2` を読み取り、その `node2` の `pushcnt` を使って新しい `head` の値 `new` を構築していました。この複雑な処理が削除されています。
    *   変更後: `next = runtime·atomicload64(&node->next);`
        *   `node->next` (64ビットのタグ付きポインタ) をアトミックに直接読み取り、`next` 変数に格納しています。
*   **CAS操作の変更**:
    *   変更前: `if(runtime·cas64(head, old, new))`
    *   変更後: `if(runtime·cas64(head, old, next))`
        *   `head` のCAS操作において、期待値 `old` と比較する新しい値として、以前計算していた `new` ではなく、`node->next` から直接読み取った `next` (64ビットのタグ付きポインタ) を使用しています。

これらの変更は、`pushcnt` を `LFNode` の `next` フィールドに統合し、`next` フィールド自体がポインタとバージョンカウンタの両方を保持する64ビット値として機能するようにしたことを示しています。これにより、`pushcnt` を個別に操作する際の複雑さや競合状態のリスクが排除され、バッファ破損問題が解決されたと考えられます。

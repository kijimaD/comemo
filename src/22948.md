# [インデックス 22948] ファイルの概要

このコミットは、Goコンパイラの`cmd/7g`（ARM64アーキテクチャ向け）におけるpeephole最適化に関するものです。具体的には、即値（immediate value）をレジスタにロードし、そのレジスタを使って加算または減算を行う一連の命令シーケンスを、より効率的な単一の命令に変換することで、生成されるコードのサイズを削減します。この最適化により、`godoc`ツールにおいて66KBのサイズ削減が実現されました。

## 元コミット内容

このコミットの目的は、Goコンパイラの`cmd/7g`において、即値をレジスタにロードし、そのレジスタを後続の`ADD`または`SUB`命令で使用する際の冗長なロード命令を削除することです。

具体的には、以下の命令シーケンスを最適化します。

```assembly
        MOV $imm, Rt
        ADD Rt, Rs, Rd
```

これを、以下のように単一の命令に変換します。

```assembly
        ADD $imm, Rs, Rd
```

この最適化により、`godoc`ツールで66KBのサイズ削減が達成されました。

## 変更の背景

コンパイラが生成するアセンブリコードには、時に冗長な命令シーケンスが含まれることがあります。特に、定数（即値）を一時的にレジスタにロードし、そのレジスタを別の演算のオペランドとして使用するパターンは、多くの場合、より直接的な命令で表現できます。

このコミットの背景には、ARM64アーキテクチャにおける即値のエンコーディング特性と、コンパイラが生成するコードの効率性向上の追求があります。ARM64の`ADD`や`SUB`命令は、特定の範囲の即値を直接オペランドとして受け取ることができます。この特性を活かすことで、中間的な`MOV`命令を省略し、命令数を削減することが可能になります。

コードサイズの削減は、特に組み込みシステムやリソースが限られた環境において重要です。また、命令数の削減は、CPUの命令フェッチやデコードのオーバーヘッドを減らし、実行速度の向上にも寄与します。`godoc`のようなツールで66KBのサイズ削減ができたことは、この最適化が実用的な効果をもたらすことを示しています。`godoc`のサイズが小さくなることで、ツールの起動時間やメモリ使用量が改善され、開発者の体験が向上します。

## 前提知識の解説

### Goコンパイラと`cmd/7g`

Go言語のコンパイラは、ソースコードを機械語に変換する役割を担います。Goの初期のコンパイラ群は、ターゲットアーキテクチャごとに`6g` (amd64), `8g` (386), `5g` (ARM) のように命名されていました。`cmd/7g`は、Plan 9オペレーティングシステム上の386アーキテクチャ向けのGoコンパイラの一部でした。現在では、`go build`コマンドがこれらのコンパイラを抽象化し、自動的に適切なコンパイラを選択して実行します。このコミットが作成された2015年時点では、`7g`はまだ現役のコンポーネントでした。

### Peephole最適化

Peephole最適化は、コンパイラ最適化の一種で、生成された機械語コードの小さな「窓（peephole）」、つまり数命令のシーケンスを検査し、より効率的な命令シーケンスに置き換える手法です。これは、コンパイラのコード生成フェーズの後に適用されることが多く、プログラムの動作を変えることなく、コードのパフォーマンス向上、メモリフットプリントの削減、コードサイズの縮小を目指します。

一般的なPeephole最適化の例としては、以下のようなものがあります。
*   **冗長なロード/ストアの削除**: 不要なデータ転送の除去。
*   **定数畳み込み (Constant Folding)**: コンパイル時に定数式を評価する。
*   **強度削減 (Strength Reduction)**: 計算コストの高い操作（例：乗算）をより安価な操作（例：ビットシフトや加算）に置き換える。
*   **無効なシーケンスの削除**: 実行されない、またはプログラムの動作に影響を与えないコードの削除。
*   **操作の結合**: 複数の命令を単一の等価な命令に置き換える。

このコミットで行われている最適化は、「操作の結合」と「冗長なロードの削除」に該当します。

### ARM64アーキテクチャと即値

ARM64（AArch64）は、64ビットのARMプロセッサアーキテクチャです。ARM64の命令セットは、固定長の32ビット命令であり、命令内に直接埋め込むことができる即値（immediate value）のサイズには制限があります。

*   **`MOV`命令と即値**: `MOV`命令は、即値をレジスタにロードするために使用されます。大きな即値をロードする場合、`MOVZ`（Move with Zero）や`MOVK`（Move with Keep）などの命令を複数組み合わせて、段階的にレジスタに値を構築することがあります。
*   **`ADD`/`SUB`命令と即値**: `ADD`や`SUB`命令は、特定の範囲の即値を直接オペランドとして受け取ることができます。例えば、12ビットの符号なし即値を0または12ビット左シフトして使用できる形式などがあります。

コンパイラは、これらの即値のエンコーディング規則を理解し、最も効率的な命令シーケンスを選択する必要があります。

### Goのアセンブリと`obj`パッケージ

Go言語は、独自のアセンブリ構文を持っています。これは、標準的なGNUアセンブリとは異なります。Goのアセンブリでは、`AMOVD`、`AADD`、`ASUB`といった命令が使用されます。

*   **`arm64.AMOVD`**: ARM64アーキテクチャにおける「Move Doubleword」命令に相当します。64ビット値をレジスタ間で移動したり、即値をレジスタにロードしたりする際に使用されます。
*   **`arm64.AADD`**: ARM64アーキテクチャにおける加算命令です。
*   **`arm64.ASUB`**: ARM64アーキテクチャにおける減算命令です。

`obj`パッケージ（具体的には`cmd/internal/obj`）は、Goツールチェーン内部で使用されるパッケージで、アセンブリやオブジェクトファイルの生成において、異なるアーキテクチャ間で共通の型や定数を定義しています。

*   **`obj.TYPE_REG`**: オペランドがCPUレジスタであることを示す型です。
*   **`obj.TYPE_CONST`**: オペランドが定数（即値）であることを示す型です。

### `godoc`

`godoc`は、Go言語のソースコードからドキュメントを生成・表示するためのツールです。Goの標準ライブラリやGoプロジェクトのドキュメントは、このツールによって生成されます。`godoc`のサイズが削減されることは、ツールの起動速度やメモリ使用量の改善に繋がり、開発体験の向上に貢献します。

## 技術的詳細

このコミットは、`src/cmd/7g/peep.go`ファイルに新しいpeephole最適化ルールを追加します。このファイルは、`7g`コンパイラのバックエンドにおける最適化パスの一部です。

追加された最適化は、以下のパターンを検出します。

1.  `AMOVD $c, R'`：即値`$c`をレジスタ`R'`にロードする命令。ここで`$c`は定数であり、特定の範囲（0から4095まで）に収まっている必要があります。これは、ARM64の`ADD`や`SUB`命令が直接扱える即値の範囲に合致するかどうかをチェックするためです。
2.  `ADD R', Rs, Rd` または `SUB R', Rs, Rd`：前の命令でロードされたレジスタ`R'`をオペランドとして使用する加算または減算命令。

この2つの命令が連続しており、かつ`R'`が後続の命令で他に利用されていない（つまり、`R'`が一時的なレジスタとしてのみ使用されている）場合、最適化が適用されます。

最適化のプロセスは以下の通りです。

1.  `AMOVD $c, R'` 命令の`From`オペランド（即値`$c`）を、`ADD`または`SUB`命令の`From`オペランドに直接コピーします。これにより、`ADD`または`SUB`命令が即値を直接オペランドとして使用する形になります。
2.  元の`AMOVD $c, R'` 命令を削除します（`excise(r)`）。

この変更により、中間的なレジスタロードが不要になり、命令数が1つ削減されます。これは、生成されるバイナリのサイズを小さくし、実行効率を向上させます。

コード内のコメント`// TODO(aram): also logical after we have bimm.`は、将来的にビットフィールド即値（bimm）を扱う論理演算（AND, OR, XORなど）にも同様の最適化を適用できる可能性を示唆しています。

## コアとなるコードの変更箇所

変更は`src/cmd/7g/peep.go`ファイルに追加された以下のコードブロックです。

```go
	// MOVD $c, R'; ADD R', R (R' unused) -> ADD $c, R
	for r := (*gc.Flow)(g.Start); r != nil; r = r.Link {
		p := r.Prog
		switch p.As {
		default:
			continue

		case arm64.AMOVD:
			if p.To.Type != obj.TYPE_REG {
				continue
			}
			if p.From.Type != obj.TYPE_CONST {
				continue
			}
			if p.From.Offset < 0 || 4096 <= p.From.Offset { // Check if immediate is within 0-4095 range
				continue
			}
		}
		r1 := r.Link
		if r1 == nil {
			continue
		}
		p1 := r1.Prog
		if p1.As != arm64.AADD && p1.As != arm64.ASUB { // TODO(aram): also logical after we have bimm.
			continue
		}
		if p1.From.Type != obj.TYPE_REG || p1.From.Reg != p.To.Reg { // Check if ADD/SUB uses the same register R'
			continue
		}
		if p1.To.Type != obj.TYPE_REG { // Ensure destination is a register
			continue
		}
		if gc.Debug['P'] != 0 {
			fmt.Printf("encoding $%d directly into %v in:\n%v\n%v\n", p.From.Offset, obj.Aconv(int(p1.As)), p, p1)
		}
		p1.From.Type = obj.TYPE_CONST // Change ADD/SUB's source to be a constant
		p1.From = p.From             // Copy the immediate value
		excise(r)                    // Remove the original MOVD instruction
	}
```

## コアとなるコードの解説

このコードブロックは、`peep.go`内の最適化ループに追加されています。`gc.Flow`は命令のフローグラフを表し、`r`はその中の現在の命令ノードを指します。

1.  **`for r := (*gc.Flow)(g.Start); r != nil; r = r.Link`**:
    *   命令のフローグラフを先頭から順に走査します。`r`は現在の命令ノード、`r.Link`は次の命令ノードを指します。

2.  **`p := r.Prog`**:
    *   現在の命令ノード`r`から、実際の命令（`obj.Prog`型）を取得します。

3.  **`switch p.As`**:
    *   現在の命令のオペレーションコード（`p.As`）をチェックします。
    *   **`case arm64.AMOVD`**: 命令が`AMOVD`である場合に処理を進めます。それ以外の場合は`continue`で次の命令に移ります。

4.  **`if p.To.Type != obj.TYPE_REG || p.From.Type != obj.TYPE_CONST`**:
    *   `AMOVD`命令の宛先（`p.To`）がレジスタ型（`obj.TYPE_REG`）であり、ソース（`p.From`）が定数型（`obj.TYPE_CONST`）であることを確認します。これらが満たされない場合、最適化の対象外として`continue`します。

5.  **`if p.From.Offset < 0 || 4096 <= p.From.Offset`**:
    *   `AMOVD`命令の即値（`p.From.Offset`）が、ARM64の`ADD`/`SUB`命令が直接扱える即値の範囲（0から4095）に収まっているかを確認します。この範囲外の場合、最適化は適用できません。

6.  **`r1 := r.Link; if r1 == nil { continue }`**:
    *   現在の`AMOVD`命令の次の命令ノード`r1`を取得します。次の命令が存在しない場合は`continue`します。

7.  **`p1 := r1.Prog`**:
    *   次の命令ノード`r1`から、実際の命令`p1`を取得します。

8.  **`if p1.As != arm64.AADD && p1.As != arm64.ASUB { continue }`**:
    *   次の命令`p1`が`AADD`または`ASUB`であることを確認します。これらが満たされない場合、最適化の対象外として`continue`します。

9.  **`if p1.From.Type != obj.TYPE_REG || p1.From.Reg != p.To.Reg`**:
    *   `AADD`または`ASUB`命令のソースオペランド（`p1.From`）がレジスタ型であり、かつそのレジスタが前の`AMOVD`命令の宛先レジスタ（`p.To.Reg`）と一致することを確認します。これにより、`AMOVD`でロードされた値が`AADD`/`ASUB`で使われていることを保証します。

10. **`if p1.To.Type != obj.TYPE_REG { continue }`**:
    *   `AADD`または`ASUB`命令の宛先（`p1.To`）がレジスタ型であることを確認します。

11. **`if gc.Debug['P'] != 0 { ... }`**:
    *   デバッグフラグ`P`が設定されている場合、最適化が適用されることを示すデバッグメッセージを出力します。

12. **`p1.From.Type = obj.TYPE_CONST`**:
    *   `AADD`または`ASUB`命令のソースオペランドの型を、レジスタ型から定数型（`obj.TYPE_CONST`）に変更します。

13. **`p1.From = p.From`**:
    *   `AMOVD`命令のソースオペランド（即値）を、`AADD`または`ASUB`命令のソースオペランドにコピーします。これにより、`AADD`/`ASUB`が即値を直接使用する形になります。

14. **`excise(r)`**:
    *   元の`AMOVD`命令ノード`r`を命令フローグラフから削除します。これにより、冗長な命令が取り除かれます。

この一連の処理により、`MOV $imm, Rt; ADD Rt, Rs, Rd`という2つの命令が、`ADD $imm, Rs, Rd`という1つの命令に効率的に変換されます。

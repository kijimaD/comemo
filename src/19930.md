# [インデックス 19930] ファイルの概要

このコミットは、Go言語のランタイムにおけるハッシュアルゴリズム、特に浮動小数点数（`float32`と`float64`）のハッシュ処理に関する改善です。変更が加えられた`src/pkg/runtime/alg.go`ファイルは、Goランタイムが内部的に使用する様々なデータ型に対するハッシュ関数を定義しています。これらのハッシュ関数は、`map`型のようなハッシュテーブルを基盤とするデータ構造のキーとして値を使用する際に不可欠です。

## コミット

このコミットは、浮動小数点数入力に対するハッシュアルゴリズムを改善することを目的としています。具体的には、浮動小数点数の「ワード（word）」ではなく「バイト（bytes）」に基づいてハッシュを計算することで、すべてのビットをより効果的に利用し、浮動小数点数をキーとする`map`のパフォーマンスを線形（O(1)に近い）に保つことを可能にしました。

## 元コミット内容

```
runtime: use better hash for floating point inputs

Hashing on the bytes instead of the words does
a (much) better job of using all the bits, so that
maps of floats have linear performance.
```

## 変更の背景

Go言語の`map`型はハッシュテーブルとして実装されており、キーのハッシュ値に基づいて要素の格納場所を決定します。ハッシュ関数の品質は、`map`のパフォーマンスに直接影響します。ハッシュ関数がキーを均等に分布させない場合、ハッシュ衝突が頻繁に発生し、`map`の操作（挿入、検索、削除）の平均計算量がO(1)から最悪の場合O(N)に劣化する可能性があります。

このコミット以前は、Goランタイムの浮動小数点数に対するハッシュ関数が最適ではありませんでした。特に`float64`のような大きな浮動小数点数では、そのビットパターンを適切にハッシュ値に変換できていなかった可能性があります。これにより、浮動小数点数をキーとして使用する`map`において、ハッシュ衝突が多発し、期待される線形性能（O(1)）が得られず、性能が著しく低下する問題が発生していました。この変更は、この性能問題を解決し、浮動小数点数をキーとする`map`が効率的に機能するようにするために導入されました。

## 前提知識の解説

### Goの`map`の仕組み

Goの`map`は、キーと値のペアを格納する組み込みのデータ構造であり、内部的にはハッシュテーブル（またはハッシュマップ）として実装されています。`map`のキーはハッシュ可能である必要があり、Goランタイムは各キー型に対して適切なハッシュ関数を提供します。キーが`map`に挿入される際、そのキーのハッシュ値が計算され、そのハッシュ値に基づいてデータが格納される「バケット」が決定されます。検索や削除の際も同様にハッシュ値が計算され、対応するバケットにアクセスすることで効率的な操作が可能になります。

### ハッシュ関数の重要性

ハッシュ関数は、任意のサイズの入力データ（キー）を固定サイズの出力（ハッシュ値）に変換する関数です。良いハッシュ関数は以下の特性を持つべきです。
*   **決定論的**: 同じ入力に対しては常に同じハッシュ値を返す。
*   **均一な分布**: 異なる入力に対しては、ハッシュ値が可能な限り均等に分布する。これにより、ハッシュ衝突（異なる入力が同じハッシュ値を生成すること）が最小限に抑えられます。
*   **高速な計算**: ハッシュ値の計算が迅速に行われる。

ハッシュ衝突が頻繁に発生すると、ハッシュテーブルのパフォーマンスは低下します。これは、衝突したキーを同じバケット内で線形探索する必要があるためです。

### 浮動小数点数の表現（IEEE 754）

Goの`float32`と`float64`は、IEEE 754標準に準拠した浮動小数点数です。この標準は、浮動小数点数のビット表現（符号部、指数部、仮数部）を定義しています。
*   **NaN (Not a Number)**: 不定な結果（例: 0/0、無限大-無限大）を表す特殊な値です。IEEE 754では、`NaN != NaN`という特性を持ちます。つまり、どんな`NaN`もそれ自身と等しくありません。
*   **+0と-0**: ゼロは正のゼロと負のゼロの2つの表現を持つことができます。これらはビット表現は異なりますが、比較上は`+0 == -0`が`true`となります。

これらの特殊な値の特性は、ハッシュ関数を設計する上で考慮される必要があります。特に`NaN`は、その比較特性から、マップのキーとして使用する際に特別な扱いが必要です。Goのマップは、`NaN`をキーとして使用した場合、それぞれの`NaN`を異なるキーとして扱います。また、ハッシュ衝突攻撃を防ぐために、`NaN`のハッシュ値はランダム化されます。

### `unsafe.Pointer`と型変換

`unsafe.Pointer`は、Goにおいて任意の型のポインタを保持できる特殊なポインタ型です。これはC言語の`void*`に似ており、型安全性をバイパスして低レベルなメモリ操作を可能にします。このコミットでは、浮動小数点数のメモリ上のバイト列に直接アクセスするために`unsafe.Pointer`が使用されています。

### `uintptr`

`uintptr`は、ポインタを保持するのに十分な大きさの符号なし整数型です。これは、ポインタを整数として扱うことを可能にし、ポインタ演算や、ポインタと整数の間の変換を可能にします。

### `memhash`

`memhash`は、Goランタイム内部で使用される汎用的なメモリハッシュ関数です。これは、指定されたメモリ領域のバイト列全体を効率的にハッシュ計算するために設計されています。この関数は、入力データのすべてのビットをハッシュ計算に利用するため、より均一なハッシュ分布を生成する傾向があります。

## 技術的詳細

### 旧実装の問題点

このコミット以前の`f32hash`（`float32`用ハッシュ関数）と`f64hash`（`float64`用ハッシュ関数）は、浮動小数点数の値を直接`uint32`や`uintptr`にキャストしてハッシュ計算を行っていました。

*   **`f32hash`の旧実装**:
    ```go
    return c1 * (c0 ^ h ^ uintptr(*(*uint32)(unsafe.Pointer(a))))
    ```
    `float32`の値を`uint32`にキャストし、その`uint32`の値を`uintptr`に変換してハッシュ計算に利用していました。これは、`float32`の4バイトのビットパターンを直接ハッシュに利用しているように見えますが、`uintptr`への変換がプラットフォームのワードサイズに依存するため、意図しないビットの切り捨てや拡張が発生する可能性がありました。

*   **`f64hash`の旧実装**:
    ```go
    case ptrSize == 4:
        x := (*[2]uintptr)(unsafe.Pointer(a))
        return c1 * (c0 ^ h ^ (x[1] * c1) ^ x[0])
    default:
        return c1 * (c0 ^ h ^ *(*uintptr)(unsafe.Pointer(a)))
    ```
    `float64`は8バイトのデータですが、`ptrSize == 4`（32ビットシステム）の場合、`float64`を2つの`uintptr`（それぞれ4バイト）に分割してハッシュ計算を行っていました。この方法では、`float64`の8バイトすべてのビットがハッシュ計算に均等に寄与しない可能性があり、特にビットの並び順や結合方法によっては、ハッシュ衝突が増加する原因となっていました。`ptrSize != 4`（64ビットシステム）の場合でも、`float64`の8バイトを1つの`uintptr`として扱っていましたが、これも`memhash`のようなバイト単位のハッシュ関数に比べると、ビットの利用効率が劣る可能性がありました。

これらの旧実装では、浮動小数点数のビットパターン全体がハッシュ関数に適切に伝わらず、結果としてハッシュ値の分布が悪くなり、`map`のパフォーマンスが低下していました。

### 新実装の改善点

このコミットでは、`f32hash`と`f64hash`の両方で、Goランタイムの汎用メモリハッシュ関数である`memhash`を使用するように変更されました。

*   **`f32hash`の新実装**:
    ```go
    return memhash(unsafe.Pointer(a), 4, h)
    ```
    `float32`のポインタ`a`とサイズ`4`バイト、そして既存のハッシュ値`h`を`memhash`に渡します。これにより、`float32`の4バイトのビットパターン全体が`memhash`によってハッシュ計算に利用されるようになります。

*   **`f64hash`の新実装**:
    ```go
    return memhash(unsafe.Pointer(a), 8, h)
    ```
    `float64`のポインタ`a`とサイズ`8`バイト、そして既存のハッシュ値`h`を`memhash`に渡します。これにより、`float64`の8バイトのビットパターン全体が`memhash`によってハッシュ計算に利用されるようになります。

`memhash`は、指定されたメモリ領域のバイト列を効率的にハッシュ化するように設計されており、入力データのすべてのビットをハッシュ計算に利用します。これにより、浮動小数点数のビットパターンがより均一にハッシュ値に変換されるようになり、ハッシュ衝突が大幅に減少します。結果として、浮動小数点数をキーとする`map`の操作が、期待される線形性能（O(1)）に近づくことが期待されます。

### NaNと±0の扱い

このコミットの変更は、`NaN`と`±0`の特別な扱いには影響を与えません。
*   **NaNの扱い**: `f != f`という条件で`NaN`を検出しています。`NaN`はそれ自身と等しくないという特性を利用し、`fastrand2()`（高速な擬似乱数生成器）を使ってランダムなハッシュ値を生成しています。これにより、異なる`NaN`値が同じハッシュ値を持つことを防ぎ、マップの動作を予測可能に保ちつつ、ハッシュ衝突攻撃に対する耐性も高めています。
*   **+0と-0の扱い**: `f64hash`では、`f == 0`の場合に特別なハッシュ値を返しています。これは、`+0`と`-0`がビット表現は異なるものの、比較上は等しいというGoのセマンティクスに合わせて、これらが同じハッシュ値を持つようにするためです。

これらの特別なケースは、`memhash`への変更とは独立して、引き続き適切に処理されます。

## コアとなるコードの解説

このコミットの核心は、浮動小数点数のハッシュ計算に`memhash`関数を導入した点です。

*   **`f32hash`の変更**:
    旧コードでは、`float32`の値を`uint32`にキャストし、その`uint32`を`uintptr`に変換してハッシュ計算を行っていました。これは、`float32`の4バイトのビットパターンを直接ハッシュに利用しようとする意図があったものの、`uintptr`への変換がプラットフォームのワードサイズに依存するため、ビットの利用効率が最適ではありませんでした。
    新コードでは、`memhash(unsafe.Pointer(a), 4, h)`とすることで、`float32`が占めるメモリ上の4バイトのデータ全体を、汎用的なメモリハッシュ関数である`memhash`に渡しています。これにより、`float32`のすべてのビットがハッシュ計算に均等に寄与し、より高品質なハッシュ値が生成されるようになります。

*   **`f64hash`の変更**:
    旧コードでは、`float64`の値をシステムが32ビットか64ビットかによって異なる方法でハッシュしていました。32ビットシステムでは`float64`を2つの`uintptr`に分割してハッシュしていましたが、これは`float64`の8バイトすべてのビットを効率的に利用できていませんでした。64ビットシステムでは1つの`uintptr`として扱っていましたが、これも`memhash`に比べると劣っていました。
    新コードでは、`memhash(unsafe.Pointer(a), 8, h)`とすることで、`float64`が占めるメモリ上の8バイトのデータ全体を`memhash`に渡しています。これにより、`float64`のすべてのビットがハッシュ計算に利用され、ハッシュ値の分布が大幅に改善されます。

`memhash`は、バイト単位でデータを処理し、より複雑なハッシュアルゴリズムを適用することで、入力データのすべてのビットを考慮に入れたハッシュ値を生成します。この変更により、浮動小数点数のビットパターンがより均一にハッシュ空間にマッピングされるようになり、結果として`map`におけるハッシュ衝突が減少し、パフォーマンスが向上します。特に、浮動小数点数をキーとして多数の要素を扱う`map`において、その効果は顕著に現れます。

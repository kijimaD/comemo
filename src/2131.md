# [インデックス 2131] ファイルの概要

このコミットは、Goランタイムにおけるスタック管理、特に`morestack`ルーチンの呼び出しメカニズムに関するさらなる調整（"more morestack fiddling"）を目的としています。Goの初期のスタック管理モデル（セグメントスタック）において、関数呼び出し時のスタック拡張処理をより効率的かつ柔軟に行うための改善が含まれています。リンカ（`6l`および`ld`）とランタイムのアセンブリコード（`asm.s`）の両方に変更が加えられ、特定のスタックオフセットに対する最適化された`morestack`トランポリンの導入と、それらをリンカが適切に処理するためのロジックが追加されています。

## 変更の背景

Go言語の初期バージョンでは、ゴルーチン（goroutine）のスタックは「セグメントスタック」モデルで管理されていました。これは、各ゴルーチンに小さな初期スタックセグメントが割り当てられ、必要に応じて新しいスタックセグメントが動的に割り当てられ、既存のセグメントにリンクされるという仕組みです。関数が呼び出される際、Goコンパイラは関数のプロローグにスタックチェックコードを挿入します。このチェックにより、現在のスタックセグメントが不足していると判断された場合、`morestack`というランタイム関数が呼び出され、スタックの拡張処理が行われます。

このコミットが行われた2009年当時、Goのランタイムとコンパイラはまだ初期開発段階にあり、パフォーマンスと効率の最適化が継続的に行われていました。`morestack`の呼び出しは、スタックが不足するたびに発生するため、そのオーバーヘッドを最小限に抑えることが重要でした。

このコミットの背景には、特定のスタックオフセット（例えば、引数やローカル変数のサイズ）を持つ関数呼び出しに対して、より効率的な`morestack`処理を提供しようとする意図があります。従来の`morestack00`, `morestack01`, `morestack10`, `morestack11`といった汎用的なトランポリンに加えて、特定の小さなスタックオフセット（8バイト刻みで48バイトまで）に対応する専用の`morestack`トランポリンを導入することで、スタック拡張時の処理パスを短縮し、パフォーマンスを向上させることが狙いです。これは、リンカがコードを生成する際に、より具体的な`morestack`ルーチンを選択できるようにするための「fiddling」（微調整）の一環です。

## 前提知識の解説

### Goのスタック管理（セグメントスタックモデル）

Goの初期バージョン（Go 1.3以前）で採用されていたスタック管理モデルです。
1.  **初期割り当て**: 各ゴルーチンは、最初に小さなスタックセグメント（例: 4KB）を受け取ります。
2.  **スタックチェック**: 関数が呼び出される際、その関数のプロローグでスタックポインタが現在のスタックセグメントの境界を超えていないかチェックされます。
3.  **`morestack`の呼び出し**: スタックが不足している場合、`runtime.morestack`関数が呼び出されます。
4.  **セグメントの追加**: `morestack`は新しい、より大きなスタックセグメントを割り当て、それを既存のスタックセグメントのチェーンに接続します。これにより、スタックは論理的に拡張されます。
5.  **ホットスプリット問題**: このモデルの欠点として、「ホットスプリット問題」がありました。これは、ループ内で頻繁にスタックの拡張と縮小が繰り返されると、スタックセグメントの頻繁な割り当てと解放が発生し、パフォーマンスが低下するという問題です。この問題は、Go 1.3以降の「連続スタック（スタックコピー）」モデルへの移行の主な理由となりました。

### `6l` (Goリンカ)

`6l`は、Goの初期のツールチェーンにおけるAMD64アーキテクチャ向けのリンカです。Goのビルドプロセスにおいて、コンパイルされたオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリを生成する役割を担います。特に、このコミットに関連する`pass.c`ファイルは、リンカの主要なパスの一つであり、スタックフレームのオフセット計算（`dostkoff`関数）や、`morestack`呼び出しの挿入といった重要な処理を行います。リンカは、コンパイラが生成したコードに、ランタイムのスタックチェックと拡張のための呼び出しを適切に埋め込む責任があります。

### `ld` (Goリンカの共通部分)

`ld`は、Goのリンカの共通部分を指します。アーキテクチャ固有のリンカ（例: `6l`）が共通のリンカフレームワークを利用する形です。`ld/go.c`ファイルは、リンカの共通処理、特にデッドコード削除（`deadcode`関数）に関連する部分を含んでいます。デッドコード削除は、最終的なバイナリサイズを削減するために、到達不可能なコードや未使用のシンボルを特定し、それらをバイナリから除外するプロセスです。`morestack`関連のシンボルは、ランタイムの重要な部分であるため、デッドコードとして削除されないように明示的にマークされる必要があります。

### `asm.s` (アセンブリコード)

`asm.s`ファイルは、Goランタイムの低レベルなアセンブリコードを含んでいます。Goランタイムは、ガベージコレクション、スケジューリング、スタック管理など、Goプログラムの実行を支える重要な機能を提供します。`morestack`のようなスタック管理ルーチンは、通常、パフォーマンスが非常に重要であるため、アセンブリ言語で実装されます。これにより、CPUのレジスタやスタックポインタを直接操作し、最大限の効率を引き出すことができます。このコミットでは、新しい`morestack`トランポリンがこのファイルに追加されています。

## 技術的詳細

このコミットは、Goのスタック拡張メカニズムである`morestack`の呼び出しを最適化するために、リンカとランタイムのアセンブリコードに協調的な変更を加えています。

### `src/cmd/6l/pass.c` の変更

*   **`morename`配列の導入**:
    ```c
    static char*
    morename[] =
    {
    	"sys·morestack00",
    	"sys·morestack10",
    	"sys·morestack01",
    	"sys·morestack11",

    	"sys·morestack8",
    	"sys·morestack16",
    	"sys·morestack24",
    	"sys·morestack32",
    	"sys·morestack40",
    	"sys·morestack48",
    };
    Prog*	pmorestack[nelem(morename)];
    Sym*	symmorestack[nelem(morename)];
    ```
    以前は個別の変数で管理されていた`morestack`のバリアント（`morestack00`, `morestack01`, `morestack10`, `morestack11`）に加えて、新しい`morestack8`から`morestack48`までのバリアントが`morename`配列として一元的に定義されました。これにより、リンカがこれらのシンボルを検索し、対応する`Prog`（プログラム命令）と`Sym`（シンボル）へのポインタを`pmorestack`と`symmorestack`配列に格納する処理が汎用化されました。

*   **`dostkoff`関数の変更**:
    `dostkoff`関数は、リンカがスタックフレームのオフセットを計算し、必要に応じて`morestack`呼び出しを挿入する主要な場所です。
    *   **`morestack`シンボルの検索ロジックの汎用化**:
        ```c
        // 変更前
        // pmorestack00 = P; ...
        // symmorestack00 = lookup("sys·morestack00", 0); ...

        // 変更後
        for(i=0; i<nelem(morename); i++) {
        	symmorestack[i] = lookup(morename[i], 0);
        	pmorestack[i] = P;
        }
        // ...
        for(p = firstp; p != P; p = p->link) {
        	if(p->as == ATEXT) {
        		for(i=0; i<nelem(morename); i++) {
        			if(p->from.sym == symmorestack[i]) {
        				pmorestack[i] = p;
        				break;
        			}
        		}
        	}
        }
        ```
        `morename`配列を使用することで、すべての`morestack`バリアントのシンボル検索と`Prog`ポインタの割り当てがループ処理で行われるようになり、コードの重複が削減され、拡張性が向上しました。

    *   **`morestack`呼び出しの挿入ロジックの改善**:
        リンカは、関数のスタックフレームサイズ（`autoffset`）と引数サイズ（`textarg`）に基づいて、適切な`morestack`トランポリンを呼び出すコードを挿入します。
        ```c

        // if(moreconst1 == 0 && moreconst2 == 0) { p->pcond = pmorestack00; ... }
        // else if(moreconst1 != 0 && moreconst2 == 0) { p->pcond = pmorestack10; ... }
        // else if(moreconst1 == 0 && moreconst2 != 0) { p->pcond = pmorestack01; ... }
        // else { p->pcond = pmorestack11; ... }

        // 変更後: 新しいmorestackバリアントの追加
        // ...
        if(moreconst1 == 0 && moreconst2 == 0) {
        	p->as = ACALL;
        	p->to.type = D_BRANCH;
        	p->pcond = pmorestack[0]; // sys·morestack00
        	p->to.sym = symmorestack[0];
        } else if(moreconst1 != 0 && moreconst2 == 0) {
        	p->as = ACALL;
        	p->to.type = D_BRANCH;
        	p->pcond = pmorestack[1]; // sys·morestack10
        	p->to.sym = symmorestack[1];
        } else if(moreconst1 == 0 && moreconst2 <= 48 && moreconst2%8 == 0) { // 新しい条件
        	i = moreconst2/8 + 3; // morestack8, morestack16, ... morestack48 に対応
        	p->as = ACALL;
        	p->to.type = D_BRANCH;
        	p->pcond = pmorestack[i];
        	p->to.sym = symmorestack[i];
        } else if(moreconst1 == 0 && moreconst2 != 0) {
        	// ... (AMOVL命令でmoreconst2をセット)
        	p->as = ACALL;
        	p->to.type = D_BRANCH;
        	p->pcond = pmorestack[2]; // sys·morestack01
        	p->to.sym = symmorestack[2];
        } else {
        	// ... (AMOVQ命令でmoreconst1とmoreconst2をセット)
        	p->as = ACALL;
        	p->to.type = D_BRANCH;
        	p->pcond = pmorestack[3]; // sys·morestack11
        	p->to.sym = symmorestack[3];

        ```
        最も重要な変更は、`moreconst1 == 0 && moreconst2 <= 48 && moreconst2%8 == 0`という新しい条件が追加されたことです。これは、スタックフレームのオフセット（`moreconst2`）が0でなく、かつ8の倍数で48以下の場合に、新しく導入された`sys·morestack8`から`sys·morestack48`までの特定のトランポリンを呼び出すようにリンカに指示します。これにより、これらの特定のケースで、より直接的な`morestack`呼び出しが可能になり、汎用的な`morestack01`（`moreconst1 == 0 && moreconst2 != 0`の場合）で必要だった追加の`MOV`命令を省略できる可能性があります。

### `src/cmd/ld/go.c` の変更

*   **`morename`配列の拡張と`deadcode`関数でのマーク**:
    ```c
    static char*
    morename[] =
    {
    	"sys·morestack",
    	"sys·morestackx", // 新しく追加

    	"sys·morestack00",
    	"sys·morestack10",
    	"sys·morestack01",
    	"sys·morestack11",

    	"sys·morestack8",
    	"sys·morestack16",
    	"sys·morestack24",
    	"sys·morestack32",
    	"sys·morestack40",
    	"sys·morestack48",
    };
    // ...
    void
    deadcode(void)
    {
    	// ...
    	// 変更前: mark(lookup("sys·morestack", 0));
    	// 変更後:
    ```

    `sys·morestackx`が`morename`配列に追加され、`deadcode`関数内でこの配列のすべてのシンボルが`mark`されるようになりました。これにより、リンカがデッドコード削除を行う際に、これらの`morestack`関連ルーチンが誤って削除されるのを防ぎ、最終的なバイナリに確実に含まれるようにします。

### `src/runtime/amd64/asm.s` の変更

*   **`sys·morestackx`の導入**:
    ```assembly
    TEXT	sys·morestackx(SB),7,$0
    	POPQ	AX
    	SHLQ	$35, AX
    	MOVQ	AX, 8(R14)
    	MOVQ	$sys·morestack(SB), AX
    	JMP	AX
    ```
    `sys·morestackx`は、新しい共通の`morestack`エントリポイントとして導入されました。これは、スタックから値をポップし（おそらくスタックオフセットに関連する情報）、それを`AX`レジスタで操作した後、`R14`レジスタ（GoのM構造体へのポインタ）のオフセット8に格納し、最終的に汎用的な`sys·morestack`ルーチンにジャンプします。これは、特定のスタックオフセットを持つ`morestack`トランポリンが、共通の処理を共有するためのハブとして機能します。

*   **`sys·morestack8`から`sys·morestack48`までの導入**:
    ```assembly
    // subcases of morestack01
    // with const of 8,16,...48
    TEXT	sys·morestack8(SB),7,$0
    	PUSHQ	$1
    	MOVQ	$sys·morestackx(SB), AX
    	JMP	AX

    TEXT	sys·morestack16(SB),7,$0
    	PUSHQ	$2
    	MOVQ	$sys·morestackx(SB), AX
    	JMP	AX
    // ... (morestack24, morestack32, morestack40, morestack48も同様)
    ```
    これらの新しいアセンブリルーチンは、特定のスタックオフセット（8, 16, ..., 48バイト）に対応する`morestack`トランポリンです。それぞれが、対応するオフセット値（8バイトの場合は1、16バイトの場合は2など）をスタックにプッシュした後、`sys·morestackx`にジャンプします。これにより、リンカがこれらの特定のトランポリンを呼び出すことで、スタックオフセットの計算と設定をより効率的に行い、`morestack`呼び出しのオーバーヘッドを削減することが可能になります。

これらの変更は、Goの初期のスタック管理モデルにおいて、スタック拡張のパフォーマンスを微調整し、特定の一般的なケースでの効率を向上させるための重要なステップでした。

## コアとなるコードの解説

### `src/cmd/6l/pass.c`

*   **`morename`配列の定義**:
    この配列は、Goランタイムが提供する様々な`morestack`トランポリンの名前を文字列として保持しています。これには、従来の4つのバリアント（`sys·morestack00`など）と、新しく追加された6つのバリアント（`sys·morestack8`から`sys·morestack48`）が含まれます。`pmorestack`と`symmorestack`は、これらの名前からリンカが解決した`Prog`（プログラム命令）と`Sym`（シンボル）へのポインタを格納するための配列です。これにより、リンカはこれらの`morestack`ルーチンを効率的に参照できます。

*   **`dostkoff`関数内のループによるシンボル解決**:
    ```c
    for(i=0; i<nelem(morename); i++) {
    	symmorestack[i] = lookup(morename[i], 0);
    	pmorestack[i] = P;
    }
    // ...
    for(p = firstp; p != P; p = p->link) {
    	if(p->as == ATEXT) {
    		for(i=0; i<nelem(morename); i++) {
    			if(p->from.sym == symmorestack[i]) {
    				pmorestack[i] = p;
    				break;
    			}
    		}
    	}
    }
    ```
    このコードは、`morename`配列に定義されたすべての`morestack`シンボルをリンカのシンボルテーブルから検索し、対応する`Sym`ポインタを`symmorestack`配列に格納します。その後、リンカが処理するすべてのテキストセクション（関数）を走査し、もしそのテキストセクションが`morestack`シンボルの一つに対応していれば、その`Prog`ポインタを`pmorestack`配列に格納します。これにより、リンカは後でこれらの`morestack`ルーチンへのジャンプ命令を生成する際に、正しいターゲットアドレスを参照できるようになります。

*   **`dostkoff`関数内の`morestack`呼び出し挿入ロジック**:
    ```c
    if(moreconst1 == 0 && moreconst2 <= 48 && moreconst2%8 == 0) {
    	i = moreconst2/8 + 3; // morestack8, morestack16, ... morestack48 に対応
    	p->as = ACALL;
    	p->to.type = D_BRANCH;
    	p->pcond = pmorestack[i];
    	p->to.sym = symmorestack[i];
    }
    ```
    この部分が、新しい最適化された`morestack`トランポリンを呼び出すための主要なロジックです。
    *   `moreconst1 == 0`: これは、スタックフレームのサイズに関連する定数の一つが0であることを意味します。
    *   `moreconst2 <= 48 && moreconst2%8 == 0`: これは、引数サイズに関連する定数（`moreconst2`）が48バイト以下で、かつ8の倍数である場合に真となります。
    *   これらの条件が満たされた場合、`i`は`moreconst2`の値に基づいて計算され、`pmorestack[i]`と`symmorestack[i]`を通じて、対応する`sys·morestack8`から`sys·morestack48`までのいずれかのトランポリンが呼び出されます。例えば、`moreconst2`が8の場合、`i`は`8/8 + 3 = 4`となり、`pmorestack[4]`（`sys·morestack8`に対応）が呼び出されます。
    *   `ACALL`命令は、指定されたシンボルへの関数呼び出しを生成します。これにより、リンカは特定のスタックオフセットに特化した`morestack`ルーチンを直接呼び出すことができ、汎用的な`morestack01`を呼び出す場合に必要だった追加のレジスタ操作を省略できる可能性があります。

### `src/cmd/ld/go.c`

*   **`deadcode`関数での`morename`配列の利用**:
    ```c
    for(i=0; i<nelem(morename); i++)
    	mark(lookup(morename[i], 0));
    ```
    `deadcode`関数は、最終的なバイナリから不要なコードを削除する役割を担います。この変更により、`morename`配列にリストされているすべての`morestack`関連シンボルが明示的に「生きているコード」としてマークされます。これにより、リンカはこれらの重要なランタイムルーチンをデッドコードとして誤って削除することなく、最終的な実行可能ファイルに含めることが保証されます。

### `src/runtime/amd64/asm.s`

*   **`sys·morestackx`ルーチン**:
    ```assembly
    TEXT	sys·morestackx(SB),7,$0
    	POPQ	AX
    	SHLQ	$35, AX
    	MOVQ	AX, 8(R14)
    	MOVQ	$sys·morestack(SB), AX
    	JMP	AX
    ```
    このアセンブリルーチンは、新しい`morestack`トランポリン（`sys·morestack8`など）から呼び出される共通の処理部分です。
    *   `POPQ AX`: スタックから8バイトの値をポップし、`AX`レジスタに格納します。これは、呼び出し元の`morestackN`ルーチンがスタックにプッシュしたオフセット値（1, 2, ... 6）であると推測されます。
    *   `SHLQ $35, AX`: `AX`レジスタの値を左に35ビットシフトします。この操作の具体的な目的は、Goの内部的なスタックフレーム構造や、`morestack`ルーチンが期待する引数のエンコーディングに関連している可能性があります。
    *   `MOVQ AX, 8(R14)`: `AX`レジスタの値を、`R14`レジスタが指すアドレス（GoのM構造体へのポインタ）からオフセット8の位置に格納します。これは、スタック拡張に必要な情報をM構造体の一部に設定していると考えられます。
    *   `MOVQ $sys·morestack(SB), AX`: 汎用的な`sys·morestack`ルーチンのアドレスを`AX`レジスタにロードします。
    *   `JMP AX`: `AX`レジスタに格納されたアドレス（`sys·morestack`）にジャンプし、実際のスタック拡張処理を実行します。

*   **`sys·morestack8`から`sys·morestack48`ルーチン**:
    ```assembly
    TEXT	sys·morestack8(SB),7,$0
    	PUSHQ	$1
    	MOVQ	$sys·morestackx(SB), AX
    	JMP	AX
    ```
    これらのルーチンは、リンカによって特定のスタックオフセットを持つ関数呼び出しから直接呼び出されます。
    *   `PUSHQ $1` (for `sys·morestack8`): スタックに定数`1`をプッシュします。この値は、`sys·morestackx`ルーチンで`POPQ AX`によって取得され、スタックオフセットの計算に使用されます。`sys·morestack16`では`$2`、`sys·morestack24`では`$3`といったように、対応するオフセット値の倍数がプッシュされます。
    *   `MOVQ $sys·morestackx(SB), AX`: `sys·morestackx`ルーチンのアドレスを`AX`レジスタにロードします。
    *   `JMP AX`: `sys·morestackx`ルーチンにジャンプし、共通のスタック拡張前処理を実行させます。

これらのアセンブリルーチンは、リンカが生成するコードと連携して、特定のスタックオフセットを持つ関数呼び出しに対して、より効率的な`morestack`パスを提供します。これにより、スタック拡張時のオーバーヘッドが削減され、Goプログラムの全体的なパフォーマンスが向上することが期待されます。

# [インデックス 22539] ファイルの概要

このコミットは、Go言語の仕様において、複合リテラル（composite literal）の型省略規則を拡張するものです。具体的には、マップリテラルのキーに対しても型省略を適用できるように変更されました。これにより、コードの記述がより簡潔になり、可読性が向上します。

## 元コミット内容

このコミットは、Go言語の仕様書 `doc/go_spec.html` を更新し、複合リテラルにおける型省略の規則を拡張するものです。

元々の仕様では、配列、スライス、またはマップの要素（値）がそれ自体複合リテラルである場合、外側の複合リテラルの要素型と同一であれば、その要素の型を省略できるとされていました。しかし、この規則がマップリテラルのキーには適用されていませんでした。

このコミットは、その見落としを修正し、マップリテラルのキーに対しても同様の型省略規則を適用できるように一般化します。これにより、マップのキーが複合リテラルである場合でも、その型を省略して記述できるようになります。

この変更は完全に後方互換性があり、言語の動作に影響を与えるものではありません。また、この変更は以前から議論されており、関連するIssue #8589 を修正するものです。

## 変更の背景

Go言語の複合リテラルは、構造体、配列、スライス、マップなどの複合型を初期化するための強力な構文です。コードの簡潔さを保つため、Go言語では特定の状況下で型を省略できる「型省略（type omission）」または「型省略（type elision）」の規則が導入されています。

以前のGo言語の仕様では、配列、スライス、およびマップの「値」に対して、要素が複合リテラルであり、かつ外側の複合リテラルの要素型と同一である場合に型を省略することが許可されていました。例えば、`[]Point{{1, 2}, {3, 4}}` のように、`Point` 型のスライスを初期化する際に、各要素の `Point{}` を省略することができました。

しかし、マップリテラルの「キー」が複合リテラルである場合には、この型省略規則が適用されていませんでした。これは一貫性に欠け、マップのキーに複合リテラルを使用する際に冗長な記述を強いることになっていました。

このコミットは、この不整合を解消し、マップリテラルのキーに対しても型省略を可能にすることで、言語仕様の一貫性を高め、開発者がより簡潔なコードを書けるようにすることを目的としています。コミットメッセージにある「Fixes #8589」は、この問題がGoのIssueトラッカーで報告され、修正が求められていたことを示唆しています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念を理解しておく必要があります。

1.  **複合リテラル (Composite Literals)**:
    Go言語において、構造体、配列、スライス、マップといった複合型の値を生成するための構文です。`Type{element1, element2, ...}` の形式で記述されます。
    *   **構造体リテラル**: `Person{Name: "Alice", Age: 30}`
    *   **配列リテラル**: `[3]int{1, 2, 3}`
    *   **スライスリテラル**: `[]string{"apple", "banana"}`
    *   **マップリテラル**: `map[string]int{"one": 1, "two": 2}`

2.  **型省略 (Type Omission / Type Elision)**:
    Go言語のコンパイラが文脈から型を推論できる場合に、明示的な型指定を省略できる機能です。これにより、コードがより簡潔になります。
    例えば、`var p Point = Point{X: 1, Y: 2}` は `p := Point{X: 1, Y: 2}` と書くことができます。
    複合リテラル内では、配列やスライスの要素、およびマップの「値」が、外側の複合リテラルの要素型と同一である場合に、その要素の型を省略できます。
    例: `[]Point{{1, 2}, {3, 4}}` は `[]Point{Point{1, 2}, Point{3, 4}}` と同じ意味です。ここで、内側の `Point{}` が省略されています。

3.  **Go言語仕様 (Go Language Specification)**:
    Go言語の構文とセマンティクスを定義する公式文書です。このコミットは、この仕様書の一部である `doc/go_spec.html` を直接変更しています。言語の挙動に関する最終的な権威であり、コンパイラの実装はこの仕様に従います。

## 技術的詳細

このコミットの技術的な核心は、Go言語仕様の「Composite literals」セクションにおける `Key` の定義と、型省略規則の記述の変更にあります。

以前の仕様では、複合リテラルの `Key` は `FieldName` または `ElementIndex` に限定されていました。これは、構造体のフィールド名や配列/スライスのインデックスを指します。しかし、マップリテラルのキーは `Expression` であり、その `Expression` が複合リテラルである場合、型省略の恩恵を受けられませんでした。

このコミットでは、`Key` の定義を以下のように変更しています。

変更前:
```
Key           = FieldName | ElementIndex .
```

変更後:
```
Key           = FieldName | Expression | LiteralValue .
```

`Key` の定義に `Expression` と `LiteralValue` が追加されたことで、マップリテラルのキーとして複合リテラルを直接記述できるようになり、さらにその複合リテラルの型を省略する余地が生まれました。

また、型省略に関する記述も以下のように変更されています。

変更前:
「Within a composite literal of array, slice, or map type `T`, elements that are themselves composite literals may elide the respective literal type if it is identical to the element type of `T`.」
（配列、スライス、またはマップ型 `T` の複合リテラル内で、それ自体が複合リテラルである要素は、`T` の要素型と同一であれば、それぞれのリテラル型を省略できる。）

変更後:
「Within a composite literal of array, slice, or map type `T`, elements or map keys that are themselves composite literals may elide the respective literal type if it is identical to the element or key type of `T`.」
（配列、スライス、またはマップ型 `T` の複合リテラル内で、それ自体が複合リテラルである要素またはマップキーは、`T` の要素またはキー型と同一であれば、それぞれのリテラル型を省略できる。）

この変更により、「elements or map keys」という文言が追加され、マップのキーに対しても型省略が明示的に許可されるようになりました。これにより、例えば `map[Point]string{{0, 0}: "orig"}` のような記述が可能になります。ここで `Point{0, 0}` の `Point` が省略されています。

この変更は、Goコンパイラがマップのキーの型を、マップ自体の型定義から推論できるようになったことを意味します。これにより、開発者はより自然で簡潔な構文でマップを初期化できるようになります。

## コアとなるコードの変更箇所

このコミットによるコアとなるコードの変更は、Go言語の公式仕様書である `doc/go_spec.html` ファイルに集中しています。

具体的には、以下の箇所が変更されています。

1.  **`Key` 構文定義の変更**:
    `LiteralType` の構文定義において、`Key` の定義が拡張されました。
    `- Key           = FieldName | ElementIndex .`
    `+ Key           = FieldName | Expression | LiteralValue .`

2.  **型省略規則の説明文の変更**:
    複合リテラルにおける型省略の規則を説明する段落が修正され、マップのキーも対象となることが明記されました。
    `- elements that are themselves composite literals may elide the respective`
    `- literal type if it is identical to the element type of <code>T</code>.`
    `+ elements or map keys that are themselves composite literals may elide the respective`
    `+ literal type if it is identical to the element or key type of <code>T</code>.`

3.  **例の追加**:
    型省略の新しい規則を示すために、マップのキーにおける型省略の例が追加されました。
    `+ map[string]Point{"orig": {0, 0}}    // same as map[string]Point{"orig": Point{0, 0}}`
    `+`
    `+ map[Point]string{{0, 0}: "orig"}    // same as map[Point]string{Point{0, 0}: "orig"}`

4.  **仕様書のバージョン日付の更新**:
    仕様書のバージョン日付が「December 26, 2014」から「March 20, 2015」に更新されました。

これらの変更は、Go言語のコンパイラやランタイムの動作そのものを直接変更するものではなく、Go言語の「文法」と「セマンティクス」を定義する仕様書を更新するものです。コンパイラは、この新しい仕様に従ってコードを解析し、型推論を行うようになります。

## コアとなるコードの解説

変更された `doc/go_spec.html` の内容は、Go言語の構文規則とセマンティクスをHTML形式で記述したものです。

1.  **`Key` 構文定義の拡張**:
    `Key = FieldName | Expression | LiteralValue .`
    この変更は、複合リテラル内でキーとして使用できる要素の範囲を広げます。
    *   `FieldName`: 構造体のフィールド名（例: `Name: "Alice"`）
    *   `Expression`: 任意の式。これには、以前からマップのキーとして許可されていた変数や関数呼び出しなどが含まれます。
    *   `LiteralValue`: 複合リテラル自体。この追加が、マップのキーとして複合リテラルを直接記述し、さらにその型を省略できるようにする鍵となります。

2.  **型省略規則の説明文の変更**:
    「elements or map keys that are themselves composite literals may elide the respective literal type if it is identical to the element or key type of `T`.」
    この文言の変更は、型省略の適用範囲を明確に拡張しています。以前は「elements」（要素、主に値）に限定されていたものが、「elements or map keys」（要素またはマップキー）に拡大されました。これにより、マップのキーが複合リテラルである場合でも、その型がマップのキー型と一致していれば、型を省略して記述することが正式に許可されます。

3.  **追加された例**:
    *   `map[string]Point{"orig": {0, 0}}`
        この例は、マップの値における型省略を示しています。`Point{0, 0}` の `Point` が省略されています。これは以前から可能でしたが、新しい規則の文脈で再確認されています。
    *   `map[Point]string{{0, 0}: "orig"}}`
        この例が、このコミットの核心を示すものです。`map[Point]string` というマップ型において、キーが `Point` 型の複合リテラル `Point{0, 0}` です。このコミットにより、キーの `Point{}` を省略して `{{0, 0}: "orig"}` と記述することが可能になりました。これは、マップのキーが複合リテラルであり、その型がマップのキー型と同一である場合に、型を省略できるという新しい規則を具体的に示しています。

これらの変更は、Go言語の構文解析器と型チェッカーが、マップリテラルのキーに対してもより高度な型推論を行うことを可能にし、開発者にとってより柔軟で簡潔なコーディングスタイルを提供します。

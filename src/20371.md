# [インデックス 20371] ファイルの概要

このコミットは、Goランタイムにおける`asmcgocall`および`asmcgocall_errno`というアセンブリ関数のリファクタリングと修正に関するものです。これらの関数は、GoコードからCコード（Cgo）を呼び出す際の重要なブリッジとして機能します。

## コミット

```
commit cb767247caeaedd0ed438adba8e27c3334be783e
Author: Russ Cox <rsc@golang.org>
Date:   Thu Sep 4 00:01:55 2014 -0400

    runtime: refactor/fix asmcgocall/asmcgocall_errno

    Instead of making asmcgocall call asmcgocall_errno,
    make both load args into registers and call a shared
    assembly function.

    On amd64, this costs 1 word in the asmcgocall_errno path
    but saves 3 words in the asmcgocall path, and the latter
    is what happens on critical nosplit paths on Windows.

    On arm, this fixes build failures: asmcgocall was writing
    the arguments for asmcgocall_errno into the wrong
    place on the stack. Passing them in registers avoids the
    decision entirely.

    On 386, this isn't really needed, since the nosplit paths
    have twice as many words to work with, but do it for consistency.

    Update #8635
    Fixes arm build (except GOARM=5).

    TBR=iant
    CC=golang-codereviews
    https://golang.org/cl/134390043
```

## 元コミット内容

Goランタイムの`asmcgocall`と`asmcgocall_errno`関数をリファクタリングし、修正します。
以前は`asmcgocall`が`asmcgocall_errno`を呼び出す構造でしたが、この変更により、両方の関数が引数をレジスタにロードし、共通のアセンブリ関数を呼び出すようにします。

この変更は、各アーキテクチャに以下の影響を与えます。
*   **amd64**: `asmcgocall_errno`パスでは1ワードのコストが増加しますが、`asmcgocall`パスでは3ワードを節約できます。後者はWindows上の重要な`nosplit`パスで発生するため、全体としてパフォーマンスが向上します。
*   **arm**: `asmcgocall`が`asmcgocall_errno`の引数をスタック上の誤った場所に書き込んでいたビルドエラーを修正します。引数をレジスタで渡すことで、この問題を完全に回避します。
*   **386**: `nosplit`パスが2倍のワードを扱えるため、この変更は厳密には必要ありませんが、一貫性のために適用されます。

このコミットは、内部トラッキングID #8635を更新し、ARMビルドの不具合（GOARM=5を除く）を修正します。

## 変更の背景

このコミットの背景には、GoランタイムがCgo（C言語との相互運用）を行う際のアセンブリレベルでの効率性と正確性の課題がありました。特に、異なるアーキテクチャ（amd64, arm, 386）間での挙動の差異や、スタック管理の複雑さが問題となっていました。

1.  **パフォーマンスの最適化**: `asmcgocall`はGoからCを呼び出す際の重要なパスであり、特にWindows上の`nosplit`パスのようなクリティカルなセクションでのパフォーマンスは重要です。既存の実装では、不要なスタック操作やレジスタの使用によりオーバーヘッドが生じていた可能性があります。
2.  **ARMアーキテクチャでのビルド問題**: ARMアーキテクチャでは、`asmcgocall`が`asmcgocall_errno`に引数を渡す際に、スタック上の誤った位置に書き込むという深刻なバグがありました。これは、アセンブリコードにおけるスタックフレームの管理や呼び出し規約の誤解、またはアーキテクチャ固有の特性への対応不足が原因と考えられます。この問題はビルドの失敗に直結するため、早急な修正が必要でした。
3.  **コードの一貫性と保守性**: 複数のアーキテクチャで類似の機能を持つアセンブリコードが存在する場合、共通のロジックを抽出して共有することで、コードの重複を減らし、保守性を向上させることができます。これにより、将来的な変更やデバッグが容易になります。
4.  **`nosplit`関数の重要性**: `nosplit`関数は、スタックの拡張（スプリット）を行わない特殊な関数であり、Goランタイムの低レベルな部分や、Cgoコールバックのように厳密なタイミングとスタック管理が求められる場所で利用されます。これらのパスでの効率性と信頼性は、ランタイム全体の安定性に直結します。

これらの課題に対処するため、引数渡しをレジスタベースに統一し、共通のアセンブリ関数を導入することで、パフォーマンスの向上、バグの修正、そしてコードベースの一貫性確保を目指しました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとアセンブリに関する前提知識が必要です。

1.  **Cgo (C Foreign Function Interface)**:
    *   GoプログラムからC言語の関数を呼び出したり、C言語からGoの関数を呼び出したりするためのメカニズムです。
    *   GoとCでは、メモリ管理、スタックの構造、呼び出し規約などが大きく異なるため、Cgoはこれらの間の橋渡しをします。
    *   Cgo呼び出しには、Goランタイムが関与し、スタックの切り替えやスケジューラの調整など、複雑な処理が行われます。

2.  **Goランタイムのアセンブリコード**:
    *   Go言語の多くの部分はGoで書かれていますが、スケジューラ、ガベージコレクタの低レベルな部分、システムコール、Cgoインターフェースなど、OSやハードウェアと直接対話する部分はアセンブリ言語で書かれています。
    *   アセンブリコードは、特定のCPUアーキテクチャ（例: amd64, arm, 386）に特化しており、レジスタの使用、スタックフレームの管理、命令セットなどが直接記述されます。

3.  **`asmcgocall`と`asmcgocall_errno`**:
    *   `runtime.cgocall`がGoからC関数を呼び出す際に、最終的にアセンブリレベルで実行をCの世界に引き渡すのが`asmcgocall`です。
    *   `asmcgocall`の主な役割は、現在のGoルーチンのスタックから、Cコードの実行に適した特別なスタック（通常はOSスレッドのスタック、`m->g0`スタック）に切り替えることです。
    *   `asmcgocall_errno`は、C関数やシステムコールがエラーを返した場合に、そのエラー番号（`errno`）をGoランタイムに伝達するためのアセンブリ関数であると推測されます。システムコールは通常、成功/失敗を返し、失敗時には`errno`というグローバル変数にエラーコードを設定します。

4.  **Goの呼び出し規約 (Calling Conventions)**:
    *   関数が呼び出される際に、引数がどのように渡され、戻り値がどのように返され、レジスタがどのように使用されるかを定義するルールです。
    *   Goには主に2つのABI（Application Binary Interface）があります。
        *   **ABI0**: ユーザーが書くアセンブリコードや、Goの初期の内部関数で使われていたスタックベースの呼び出し規約です。引数と戻り値はスタックメモリを介して渡されます。
        *   **ABIInternal**: Goの内部関数で使われる、より最適化された呼び出し規約で、レジスタとスタックを組み合わせて引数を渡します。パフォーマンス向上のために進化しています。
    *   このコミットは、引数渡しをレジスタベースにすることで、ABIInternalの考え方に近づけ、効率化を図っています。

5.  **`//go:nosplit` ディレクティブ**:
    *   Goコンパイラに対する特殊な指示で、その関数がスタックオーバーフローチェックを行わないようにします。
    *   通常のGo関数は、スタックが足りなくなった場合に自動的にスタックを拡張（スプリット）しますが、`nosplit`関数はこれをスキップします。
    *   これは、ランタイムの非常に低レベルな部分や、割り込みハンドラ、Cgoコールバックなど、スタック拡張がデッドロックを引き起こしたり、タイミングに影響を与えたりする可能性があるクリティカルなパスで使用されます。
    *   `nosplit`関数は、十分なスタック空間があることを前提としているため、誤って使用するとスタックオーバーフローによるクラッシュを引き起こす可能性があります。

6.  **レジスタとスタック**:
    *   **レジスタ**: CPU内部にある高速な記憶領域で、計算やデータ転送に一時的に使用されます。レジスタを介したデータ渡しは、スタックを介した渡しよりも高速です。
    *   **スタック**: プログラムの実行中に一時的なデータを格納するために使用されるメモリ領域です。関数呼び出しの引数、ローカル変数、戻りアドレスなどがスタックに積まれます。スタック操作はレジスタ操作よりもオーバーヘッドがあります。

これらの概念を理解することで、コミットがなぜ行われたのか、そしてそれがGoランタイムの動作にどのように影響するかを深く把握できます。

## 技術的詳細

このコミットの技術的詳細な変更点は、`asmcgocall`と`asmcgocall_errno`というGoランタイムのアセンブリ関数における引数渡しと制御フローの根本的な見直しにあります。

**変更前（既存の構造）**:
変更前は、`runtime.asmcgocall`が引数をスタックにプッシュし、その後`runtime.asmcgocall_errno`を呼び出すという、関数呼び出しの連鎖がありました。`asmcgocall_errno`が実際のCgo呼び出しのロジックを含んでいたと考えられます。

```
// 変更前の概念図
runtime.asmcgocall:
  - 引数 (fn, arg) をスタックにプッシュ
  - runtime.asmcgocall_errno を CALL
  - RET

runtime.asmcgocall_errno:
  - スタックから引数をロード
  - Cgo呼び出しの実際のロジック
  - 戻り値をスタックに格納
  - RET
```

この構造にはいくつかの問題がありました。

1.  **スタック操作のオーバーヘッド**: `asmcgocall`が引数をスタックにプッシュし、`asmcgocall_errno`がそれをスタックから読み出すという二重のスタック操作が発生していました。これは特に頻繁に呼び出されるパスや、`nosplit`のようなパフォーマンスが重要なパスで不要なオーバーヘッドとなります。
2.  **ARMでのスタックアライメント/引数渡し問題**: ARMアーキテクチャでは、`asmcgocall`が`asmcgocall_errno`に引数を渡す際に、スタック上の誤った位置に書き込むという具体的なバグがありました。これは、ARMの呼び出し規約やスタックアライメントの要件と、既存のアセンブリコードの実装が合致していなかったためと考えられます。結果として、不正な引数で`asmcgocall_errno`が実行され、ビルドエラーやランタイムエラーを引き起こしていました。
3.  **コードの重複と保守性**: `asmcgocall`と`asmcgocall_errno`がそれぞれ異なる引数渡しロジックを持ち、共通のCgo呼び出しロジックを共有していない場合、コードの重複が生じ、保守が困難になります。

**変更後（新しい構造）**:
このコミットでは、これらの問題を解決するために、`asmcgocall`と`asmcgocall_errno`の両方が引数（`fn`と`arg`）を直接レジスタにロードし、その後、新しく導入された共通のアセンブリ関数`asmcgocall<>`（Goのアセンブリではジェネリックな関数名を示す慣例）を呼び出すように変更されました。

```
// 変更後の概念図
runtime.asmcgocall:
  - fn を AX (または R1) にロード
  - arg を BX (または R0) にロード
  - asmcgocall<> を CALL
  - RET

runtime.asmcgocall_errno:
  - fn を AX (または R1) にロード
  - arg を BX (または R0) にロード
  - asmcgocall<> を CALL
  - AX (戻り値) を ret+オフセット(FP) に格納 (errnoパスのみ)
  - RET

asmcgocall<>: // 共通のロジック
  - fn は AX (または R1)、arg は BX (または R0) にあることを前提
  - Cgo呼び出しの実際のロジック
  - 戻り値を AX (または R0) に格納
  - RET
```

**アーキテクチャごとの影響**:

*   **amd64**:
    *   `runtime.asmcgocall`は、`fn`を`AX`に、`arg`を`BX`にロードし、`asmcgocall<>`を呼び出します。これにより、以前のスタックへのプッシュと`asmcgocall_errno`への呼び出しが不要になり、3ワードのスタック操作が節約されます。これは特にWindowsの`nosplit`パスのようなクリティカルな場所でパフォーマンス上のメリットがあります。
    *   `runtime.asmcgocall_errno`は、同様に`fn`を`AX`に、`arg`を`BX`にロードし、`asmcgocall<>`を呼び出します。その後、`asmcgocall<>`からの戻り値（`errno`）を`AX`から`ret+16(FP)`（フレームポインタからのオフセット）に格納します。このパスでは、以前のスタック操作が減るものの、戻り値の格納のために1ワードのコストが増加します。しかし、全体としては`asmcgocall`パスの改善が大きいため、正当化されます。
*   **arm**:
    *   `runtime.asmcgocall`は、`fn`を`R1`に、`arg`を`R0`にロードし、`asmcgocall<>`を呼び出します。これにより、以前のスタックへの書き込みが不要になり、スタック上の誤った場所への引数書き込みというビルドエラーが根本的に修正されます。引数をレジスタで渡すことで、スタックの管理に関する複雑な問題を回避できます。
    *   `runtime.asmcgocall_errno`も同様に`fn`を`R1`に、`arg`を`R0`にロードし、`asmcgocall<>`を呼び出します。その後、`asmcgocall<>`からの戻り値（`errno`）を`R0`から`ret+8(FP)`に格納します。
*   **386**:
    *   `runtime.asmcgocall`は、`fn`を`AX`に、`arg`を`BX`にロードし、`asmcgocall<>`を呼び出します。
    *   `runtime.asmcgocall_errno`も同様に`fn`を`AX`に、`arg`を`BX`にロードし、`asmcgocall<>`を呼び出します。その後、`asmcgocall<>`からの戻り値（`errno`）を`AX`から`ret+8(FP)`に格納します。
    *   386アーキテクチャでは、`nosplit`パスがより多くのスタック空間を利用できるため、この変更はパフォーマンス上の大きなメリットをもたらしませんが、他のアーキテクチャとの一貫性を保つために適用されました。

**共通のアセンブリ関数 `asmcgocall<>` の導入**:
このコミットの核心は、`asmcgocall<>`という新しい共通のアセンブリ関数の導入です。この関数は、`fn`と`arg`が特定のレジスタ（amd64では`AX`と`BX`、armでは`R1`と`R0`）にロードされていることを前提とし、Cgo呼び出しの実際のロジックを実行します。これにより、コードの重複が排除され、保守性が向上します。

**`misc/cgo/test/callback.go` の変更**:
テストファイル`callback.go`では、スタックトレースの検証ロジックが更新されています。`asmcgocall`が直接呼び出されるようになったため、スタックトレースに`asmcgocall`が含まれることを期待するように変更されています。また、スタックフレームの検証ロジックもより堅牢になるように修正されています。

このリファクタリングは、GoランタイムのCgoインターフェースの効率性、正確性、および保守性を向上させるための重要なステップです。特に、ARMアーキテクチャでのビルド問題を解決し、amd64でのパフォーマンスを最適化する効果があります。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下の3つのアセンブリファイルに集中しています。

1.  `src/pkg/runtime/asm_386.s`
2.  `src/pkg/runtime/asm_amd64.s`
3.  `src/pkg/runtime/asm_arm.s`

これらのファイルでは、`runtime·asmcgocall`と`runtime·asmcgocall_errno`の定義が変更され、新たに`asmcgocall<>`という共通のアセンブリ関数が追加されています。

具体的な変更点としては、各アーキテクチャの`runtime·asmcgocall`と`runtime·asmcgocall_errno`から、引数をスタックにプッシュする命令や、`runtime·asmcgocall_errno`を呼び出す命令が削除され、代わりに引数をレジスタにロードし、新しく追加された`asmcgocall<>`を呼び出す命令が追加されています。

また、`misc/cgo/test/callback.go`では、テストの期待値が変更され、スタックトレースに`asmcgocall`が含まれることを検証するようになっています。

## コアとなるコードの解説

各アセンブリファイルにおける変更の具体的な解説です。

### `src/pkg/runtime/asm_386.s`

**変更前**:
```assembly
TEXT runtime·asmcgocall(SB),NOSPLIT,$12-8
	MOVL	fn+0(FP), AX
	MOVL	arg+4(FP), BX
	MOVL	AX, 0(SP) // fnをスタックにプッシュ
	MOVL	BX, 4(SP) // argをスタックにプッシュ
	CALL	runtime·asmcgocall_errno(SB) // asmcgocall_errnoを呼び出し
	RET

TEXT runtime·asmcgocall_errno(SB),NOSPLIT,$0-12
	MOVL	fn+0(FP), AX
	MOVL	arg+4(FP), BX
	// ... 実際のCgo呼び出しロジック ...
	MOVL	AX, ret+8(FP) // 戻り値をスタックに格納
	RET
```

**変更後**:
```assembly
TEXT runtime·asmcgocall(SB),NOSPLIT,$0-8 // スタックフレームサイズが$12から$0に減少
	MOVL	fn+0(FP), AX
	MOVL	arg+4(FP), BX
	CALL	asmcgocall<>(SB) // 共通のasmcgocall<>を呼び出し
	RET

TEXT runtime·asmcgocall_errno(SB),NOSPLIT,$0-12
	MOVL	fn+0(FP), AX
	MOVL	arg+4(FP), BX
	CALL	asmcgocall<>(SB) // 共通のasmcgocall<>を呼び出し
	MOVL	AX, ret+8(FP) // asmcgocall<>からの戻り値(AX)をretに格納
	RET

TEXT asmcgocall<>(SB),NOSPLIT,$0-12 // 新しく追加された共通関数
	// fn in AX, arg in BX
	MOVL	SP, DX
	// ... 実際のCgo呼び出しロジック ...
	// 戻り値はAXに設定される
	RET
```
*   `runtime·asmcgocall`は、引数をスタックにプッシュする代わりに、直接レジスタ`AX`と`BX`にロードし、`asmcgocall<>`を呼び出すようになりました。これにより、スタックフレームサイズが`$12`から`$0`に削減され、不要なスタック操作がなくなりました。
*   `runtime·asmcgocall_errno`も同様に、引数をレジスタにロードし、`asmcgocall<>`を呼び出します。`asmcgocall<>`からの戻り値（`AX`レジスタに格納されている）を`ret+8(FP)`に格納する処理は残っています。
*   `asmcgocall<>`は、`fn`が`AX`に、`arg`が`BX`にあることを前提として、実際のCgo呼び出しロジックを実行します。

### `src/pkg/runtime/asm_amd64.s`

**変更前**:
```assembly
TEXT runtime·asmcgocall(SB),NOSPLIT,$24-16

	MOVQ	arg+8(FP), BX

	MOVQ	BX, 8(SP) // argをスタックにプッシュ

TEXT runtime·asmcgocall_errno(SB),NOSPLIT,$0-20

	MOVQ	arg+8(FP), BX
	// ... 実際のCgo呼び出しロジック ...
	MOVL	AX, ret+16(FP) // 戻り値をスタックに格納
	RET
```

**変更後**:
```assembly
TEXT runtime·asmcgocall(SB),NOSPLIT,$0-16 // スタックフレームサイズが$24から$0に減少
	MOVQ	fn+0(FP), AX
	MOVQ	arg+8(FP), BX

	RET
```

### `src/pkg/runtime/asm_arm.s`

**変更前**:
```assembly
TEXT	runtime·asmcgocall(SB),NOSPLIT,$12-8
	MOVW	fn+0(FP), R1
	MOVW	arg+4(FP), R2 // argをR2にロード
	MOVW	R1, 0(R13) // R1 (fn)をスタックにプッシュ
	MOVW	R2, 4(R13) // R2 (arg)をスタックにプッシュ
	BL	runtime·asmcgocall_errno(SB) // asmcgocall_errnoを呼び出し
	RET

TEXT runtime·asmcgocall_errno(SB),NOSPLIT,$0-12
	MOVW	fn+0(FP), R1
	MOVW	arg+4(FP), R0
	// ... 実際のCgo呼び出しロジック ...
	MOVW	R0, ret+8(FP) // 戻り値をスタックに格納
	RET
```

**変更後**:
```assembly
TEXT	runtime·asmcgocall(SB),NOSPLIT,$0-8 // スタックフレームサイズが$12から$0に減少
	MOVW	fn+0(FP), R1
	MOVW	arg+4(FP), R0 // argをR0にロード (呼び出し規約に合わせる)
	BL	asmcgocall<>(SB) // 共通のasmcgocall<>を呼び出し
	RET

TEXT runtime·asmcgocall_errno(SB),NOSPLIT,$0-12
	MOVW	fn+0(FP), R1
	MOVW	arg+4(FP), R0
	BL	asmcgocall<>(SB) // 共通のasmcgocall<>を呼び出し
	MOVW	R0, ret+8(FP) // asmcgocall<>からの戻り値(R0)をretに格納
	RET

TEXT asmcgocall<>(SB),NOSPLIT,$0-0 // 新しく追加された共通関数
	// fn in R1, arg in R0.
	MOVW	R13, R2
	// ... 実際のCgo呼び出しロジック ...
	// 戻り値はR0に設定される
	RET
```
*   ARM版では、`runtime·asmcgocall`が`fn`を`R1`に、`arg`を`R0`にロードし、`asmcgocall<>`を呼び出すようになりました。これにより、以前のスタックへの誤った書き込みが修正され、ビルドエラーが解消されます。ARMの呼び出し規約では、最初の引数が`R0`、2番目が`R1`に渡されることが一般的であり、この変更はそれに合わせています。
*   `runtime·asmcgocall_errno`も同様にレジスタ渡しで`asmcgocall<>`を呼び出し、戻り値を`ret+8(FP)`に格納します。
*   `asmcgocall<>`は、`fn`が`R1`に、`arg`が`R0`にあることを前提としています。

### `misc/cgo/test/callback.go`

このGoテストファイルでは、`testCallbackCallers`関数内の期待されるスタックトレースのリストに`"asmcgocall"`が追加されました。これは、`asmcgocall`が直接呼び出されるようになったため、スタックトレースにその名前が現れることをテストで確認するためです。また、スタックフレームの検証ロジックもより堅牢になるように修正されています。

これらの変更により、GoランタイムのCgo呼び出しメカニズムは、より効率的で、アーキテクチャ間で一貫性があり、特にARMでの安定性が向上しました。

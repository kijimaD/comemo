## 変更の背景

Go言語において、`<-`演算子は二つの異なる文脈で使用されます。一つはチャネルからの値の受信操作（例: `v := <-ch`）、もう一つは受信専用チャネル型の宣言（例: `func(<-chan int)`）です。この二つの用途は構文上、特に`<-x`のような形式で曖昧さを生じさせることがありました。

具体的には、`<-`の後に続く`x`が単なる変数や式である場合は受信操作と解釈されますが、`x`が`chan T`のようなチャネル型である場合は、`<-chan T`全体として受信専用チャネル型と解釈されるべきです。しかし、パーサーが`<-`を読み込んだ時点では、その後に続く要素が何であるか（単なる式か、それともチャネル型の一部か）を完全に判断できない場合があります。

この曖昧さが原因で、Goコンパイラのパーサーは特定の複雑なケース（特にネストされたチャネル型や型変換が絡む場合）で誤った構文解析を行ったり、不正確なエラーメッセージを報告したりする可能性がありました。コミットメッセージにある`Fixes #13273`は、この問題が具体的なバグとして報告されていたことを示唆しています。このコミットは、この構文解析の曖昧さを解消し、より堅牢なパーシングロジックと、より分かりやすいエラーメッセージを提供することを目的としています。

## 前提知識の解説

### Go言語のチャネルと`<-`演算子

Go言語のチャネルは、ゴルーチン間で値を送受信するための強力な同期プリミティブです。`<-`演算子はチャネル操作において中心的な役割を果たします。

1.  **受信操作**: `value := <-channel` の形式で、チャネルから値を受信します。
2.  **チャネル型宣言**:
    *   `chan int`: 送受信可能な`int`型のチャネル。
    *   `<-chan int`: 受信専用の`int`型のチャネル。このチャネルからは値を受信することしかできません。
    *   `chan<- int`: 送信専用の`int`型のチャネル。このチャネルには値を送信することしかできません。

このコミットで問題となっているのは、`<-`が単項演算子として機能する受信操作と、型の一部として機能する受信専用チャネル型の区別です。

### Goコンパイラのパーサー

Goコンパイラは、ソースコードを読み込み、その構文構造を解析して抽象構文木（AST: Abstract Syntax Tree）を構築します。このプロセスは「パース（構文解析）」と呼ばれ、コンパイラのフロントエンドの重要な部分です。パーサーは、トークン（字句解析器によって生成された最小単位のコード要素）のストリームを受け取り、Go言語の文法規則に従ってそれらを構造化します。

### 抽象構文木（AST）

ASTは、ソースコードの抽象的な構文構造を木構造で表現したものです。各ノードはソースコードの構成要素（式、文、宣言など）を表し、その子ノードはさらに詳細な構成要素を表します。コンパイラはASTを基に、型チェック、最適化、コード生成などの後続の処理を行います。

### `uexpr` (unary expression) 関数

Goコンパイラのパーサーでは、`uexpr`（unary expression、単項式）のような関数が、単項演算子（例: `+`, `-`, `!`, `^`, `*`, `&`, `<-`）を含む式を解析する役割を担います。これらの関数は、演算子の優先順位や結合規則に従って、正しいASTノードを構築する必要があります。

## 技術的詳細

このコミットの主要な技術的課題は、`<-`トークンが検出されたときに、それが「チャネル受信操作」なのか、それとも「受信専用チャネル型」の開始なのかを正確に判断することでした。

以前のパーサーは、`<-`の直後に`chan`キーワードが続くかどうかで判断しようとしていた可能性があります。しかし、`<-chan int(nil)`のような式では、`<-`の後に`chan`が続きますが、全体としては`int`型のチャネルを`nil`に型変換する式であり、`<-chan int`は型として機能します。一方で、`<-ch`のような単純な受信操作では、`ch`がチャネル型であれば受信操作となります。さらに複雑なケースとして、`<-chan (<-chan int)`のようにネストされたチャネル型も存在します。

このコミットでは、`parser.go`の`uexpr`関数内の`LCOMM`（`<-`トークン）の処理ロジックが大幅に修正されました。

1.  **先行解析**: `<-`トークンを検出した後、パーサーはまず`p.uexpr()`を再帰的に呼び出し、`<-`の後に続く式`x`を解析します。この時点では、`<-`が受信操作なのか型の一部なのかは確定しません。
2.  **結果に基づく判断**: `x`の解析結果（ASTノード`x`）が得られた後、パーサーは`x.Op`（ノードの操作タイプ）をチェックします。
    *   もし`x.Op == OTCHAN`（`x`がチャネル型を表すノード）であれば、`<-`は受信専用チャネル型の方向指定子として解釈されるべきです。この場合、パーサーは`x`のチャネル方向（`Etype`フィールド）を`Crecv`（受信専用）に設定し直します。
    *   `<-<-chan E`のような不正な構文（二重の受信方向指定子）を検出するために、`x`が既に受信専用チャネル型である場合はエラーを報告します。
    *   `<-chan<-E`のような不正な構文（チャネル要素がチャネルでないのに送信方向指定子がある）も検出します。
    *   もし`x`がチャネル型でなければ、`<-`は受信操作として解釈され、`ORECV`（受信操作）ノードが構築されます。

このアプローチにより、パーサーは`<-`の後の文脈全体を考慮して、その意味を正確に判断できるようになりました。

### エラーメッセージの改善

*   `parser.want`関数では、期待されるトークンが何であったかをエラーメッセージに含めるように変更され、より具体的なエラー情報が提供されるようになりました。
*   `parser.syntax_error_at`関数が導入されました。これは、特定の行番号で構文エラーを報告するためのものです。これにより、エラーが発生した正確な位置（例えば、ラベル付きステートメントのコロンの行など）でエラーを報告できるようになり、デバッグが容易になります。以前は`lexlineno`を一時的に変更してエラーを報告していましたが、この新しい関数により、よりクリーンで堅牢な方法で実現されます。

## コアとなるコードの解説

### `parser.go` の変更点

1.  **`want` 関数の改善**:
    *   以前は`p.syntax_error("")`と呼び出され、一般的な「syntax error: unexpected %s」というメッセージしか表示されませんでした。
    *   変更後、`p.syntax_error("expecting " + tokstring(tok))`と呼び出されるようになり、期待していたトークンが何であったかを具体的に示すエラーメッセージが出力されるようになりました。これにより、開発者はエラーの原因をより迅速に特定できます。

2.  **`syntax_error_at` 関数の導入**:
    *   この新しい関数は、指定された行番号`lineno`で構文エラーを報告するために導入されました。
    *   `defer`文を使って元の`lexlineno`（字句解析器の現在の行番号）を復元しつつ、一時的に`lexlineno`を`lineno`に設定して`p.syntax_error`を呼び出します。
    *   これにより、エラーが発生した実際のコード行（例えば、ラベルのコロンの行）でエラーを報告できるようになり、エラーメッセージの正確性が向上しました。

3.  **`labeled_stmt` 関数の変更**:
    *   ラベル付きステートメントでステートメントが欠落している場合のエラー報告が、新しく導入された`p.syntax_error_at`を使用するように変更されました。これにより、エラーがラベルのコロンの行で正確に報告されるようになりました。

4.  **`uexpr` 関数の `LCOMM` (<-) 処理の変更**:
    *   これがこのコミットの最も重要な変更点です。
    *   **先行解析**: `<-`トークンを読み込んだ後、すぐに`p.uexpr()`を呼び出して、`<-`の後に続く式`x`を解析します。この段階では、`<-`が受信操作なのか型の一部なのかはまだ確定していません。
    *   **チャネル型の場合の再関連付け**:
        *   `x.Op == OTCHAN`（`x`がチャネル型を表すASTノード）の場合、`<-`は受信専用チャネル型の方向指定子として解釈されます。
        *   `dir := EType(Csend)`で初期化された`dir`変数と、`t := x`で初期化された`t`変数を使って、`x`が表すチャネル型のネストを遡ります。
        *   ループ`for ; t.Op == OTCHAN && dir == Csend; t = t.Left`は、チャネル型のネストを深く掘り下げ、既に受信専用（`Crecv`）の方向指定子があるチャネル型がないかを確認します。
        *   `if dir == Crecv`のチェックは、`<-<-chan E`のような不正な構文（二重の受信方向指定子）を検出します。これはGoの文法で許可されていません。エラーメッセージは「unexpected <-, expecting chan」となります。
        *   `t.Etype = Crecv`により、現在のチャネル型の方向を`Crecv`（受信専用）に設定し直します。これにより、`<-`がチャネル型の一部として正しく解釈されます。
        *   ループ終了後、`if dir == Csend`のチェックは、`<-chan<-E`のような不正な構文（チャネル要素`E`がチャネルではないのに送信方向指定子`<-`がある）を検出します。エラーメッセージは「unexpected %v, expecting chan」となります。
        *   最終的に、`x`（再関連付けされたチャネル型）が返されます。
    *   **受信操作の場合**:
        *   `x.Op != OTCHAN`（`x`がチャネル型ではない）の場合、`<-`は受信操作として解釈されます。
        *   `Nod(ORECV, x, nil)`を呼び出して、`ORECV`（受信操作）を表すASTノードを構築し、`x`をそのオペランドとして設定します。

この新しいロジックにより、パーサーは`<-`の後の文脈を完全に解析した上で、その意味を正確に判断できるようになり、以前の曖昧さに起因するバグが修正されました。

### `test/fixedbugs/issue13273.go` の追加

このテストファイルは、`<-x`形式の単項式が正しく解析されることを検証するために追加されました。特に、以下のケースを網羅しています。

*   `<-chan int((chan int)(nil))`: 型変換を含む複雑なチャネル型。
*   `<-chan int(nil)`: 単純な受信専用チャネル型。
*   `<-chan chan int(nil)`: ネストされたチャネル型。
*   `<-chan<-chan int(nil)`: 送信方向指定子を含むネストされたチャネル型。
*   `<-chan (<-chan int)(nil)`: 括弧で囲まれた受信専用チャネル型。
*   `type _ <-<-chan int`: 不正な二重の受信方向指定子を持つチャネル型宣言。
*   `<-<-chan int`: 不正な二重の受信方向指定子を持つ式。
*   `type _ <-chan<-int`: 不正なチャネル要素を持つチャネル型宣言。
*   `<-chan<-int`: 不正なチャネル要素を持つ式。

これらのテストケースは、新しいパーシングロジックが様々な有効な構文を正しく解析し、同時に不正な構文に対しては適切なエラーメッセージを報告することを確認します。特に、`ERROR`コメントが付いている行は、コンパイラが期待するエラーメッセージを示しており、パーサーの修正が意図通りに機能していることを検証します。

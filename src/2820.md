# [インデックス 2820] ファイルの概要

このコミットは、Go言語の評価器（`usr/austin/eval` ディレクトリ配下）におけるスコープとフレームの管理メカニズムを根本的に再設計するものです。主な目的は、関数呼び出し時のフレーム構造を「フラット化」し、変数スロットの再利用を促進することで、実行効率の向上とコードの簡素化を図ることにあります。特に、ブロックの出入りに伴うコード実行のオーバーヘッドを排除し、ブロック境界を越えるジャンプを可能にすることで、より柔軟な制御フローを実現しています。

## 変更の背景

Go言語の初期の評価器（`eval`パッケージ）では、変数のスコープと実行時のフレーム（スタックフレーム）の管理が、ツリー構造を持つ`Frame`オブジェクトによって行われていたと考えられます。この設計では、ネストされたブロック（`if`文、`for`ループなど）に入るたびに新しい`Frame`が生成され、そこから抜けるたびに破棄されるという、比較的コストの高い処理が行われていた可能性があります。

元コミット内容から推測される問題点は以下の通りです。

1.  **ブロック出入りのオーバーヘッド**: 各ブロックの出入りがコード実行を伴うため、パフォーマンスのボトルネックとなっていた。
2.  **フレーム構造の複雑さ**: `Frame`がツリー構造を持つことで、変数のルックアップや管理が複雑になりがちだった。
3.  **変数スロットの非効率な利用**: 変数スロットがブロックごとに独立して割り当てられ、非効率なメモリ利用につながっていた可能性がある。
4.  **ブロック境界を越えるジャンプの困難さ**: `goto`文や`break`/`continue`文がブロック境界を越える際に、フレームの管理が複雑になるため、実装が困難であったか、非効率であった。
5.  **`Scope`と`Frame`の役割の曖昧さ**: `Scope`（コンパイル時の概念）と`Frame`（実行時の概念）が密接に結合しており、それぞれの役割が明確でなかった。特に、クロージャなどで外部スコープの変数（out vars）にアクセスする際に、特別な追跡が必要だった。

これらの問題を解決し、評価器の効率性、柔軟性、および保守性を向上させるために、このコミットでは`Frame`構造のフラット化と`Scope`の役割の明確化が図られました。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

*   **Go言語の評価器/コンパイラ**: Go言語のコードを実行可能形式に変換したり、直接解釈・実行したりするシステム。このコミットは、特にGo言語の初期の実験的な評価器（`usr/austin/eval`）の内部実装に関するものです。
*   **抽象構文木 (AST: Abstract Syntax Tree)**: ソースコードの構文構造を木構造で表現したもの。コンパイラや評価器はASTを解析してコードの意味を理解します。
*   **スコープ (Scope)**: プログラム内で変数が参照可能な範囲を定義するコンパイル時の概念。Go言語では、パッケージスコープ、ファイルスコープ、関数スコープ、ブロックスコープなどがあります。スコープは通常、ネストされた構造を持ちます。
*   **フレーム (Frame) またはスタックフレーム**: 関数が呼び出されるたびに、その関数のローカル変数、引数、戻りアドレスなどを格納するためにランタイムスタック上に割り当てられるメモリ領域。実行時に生成され、関数が終了すると破棄されます。
*   **変数スロット**: フレーム内で個々の変数が割り当てられるメモリ上の位置。
*   **非オーバーラップ変数 (Non-overlapping variables)**: 同じスコープ内で異なる生存期間を持つ変数が、実行時に同じメモリ位置（スロット）を再利用できるような最適化。これにより、メモリ使用量を削減できます。
*   **アウト変数 (Out variables)**: クロージャ（関数リテラル）が、それを定義した外側の関数のローカル変数にアクセスする際に、その外側の変数を指す概念。これらの変数は、外側の関数が終了してもクロージャが生きている限り存続する必要があります。
*   **コンパイル時と実行時**:
    *   **コンパイル時**: ソースコードが機械語や中間コードに変換される段階。この段階で型チェック、構文解析、最適化などが行われます。
    *   **実行時**: コンパイルされたプログラムが実際に実行される段階。

## 技術的詳細

このコミットの核となる技術的変更は、`Scope`と`Frame`の役割の分離と、`block`という新しい概念の導入によるフレーム構造のフラット化です。

1.  **`block`構造体の導入**:
    *   以前は`Scope`がコンパイル時と実行時の両方の側面（変数の定義とフレームの構造）を担っていましたが、このコミットでは`block`という新しい構造体が導入されました。
    *   `block`は、名前が複数回定義されない定義ブロックを表し、`outer`（外側のブロック）、`inner`（内側のブロック）、`scope`（このブロックを含む`Scope`）、`defs`（このブロックで定義された変数、定数、型）、`offset`（このブロックで定義された最初の変数のインデックス）、`numVars`（このブロックで定義された変数の数）を持ちます。
    *   これにより、ブロックスコープの管理が`block`構造体に集約され、`Scope`はより高レベルな概念として扱われるようになります。

2.  **`Scope`構造体の再定義**:
    *   新しい`Scope`構造体は、`*block`（スコープのルートブロック）と`maxVars`（このスコープで必要とされる最大の変数数）のみを持つようになりました。
    *   コミットメッセージにあるように、「`Scope`は排他的にコンパイル時オブジェクト」となり、実行時のフレーム構造からは切り離されました。これにより、`Scope`は変数の可視性や型チェックといったコンパイル時の情報のみを管理するようになります。

3.  **`Frame`構造体のフラット化**:
    *   以前の`Frame`は`Scope *Scope`フィールドを持っていましたが、これが削除されました。
    *   新しい`Frame`は`Outer *Frame`（外側のフレームへのポインタ）と`Vars []Value`（変数の値を格納するスライス）のみを持ちます。
    *   これにより、`Frame`は特定の`Scope`に直接関連付けられるのではなく、単に変数値を保持する実行時データ構造として機能します。
    *   「各関数呼び出しは単一のフレームを生成する」という記述は、関数全体で一つの`Frame`が使われ、その中の変数スロットがブロック間で再利用されることを意味します。

4.  **変数スロットの再利用と初期化タイミングの変更**:
    *   `block`構造体の`offset`と`numVars`フィールド、そして`Scope`構造体の`maxVars`フィールドが、非オーバーラップ変数のスロット再利用を可能にします。
    *   具体的には、異なるブロックで定義された変数が、その生存期間が重ならない場合、同じフレーム内の変数スロットを共有できるようになります。これにより、メモリ使用量が最適化されます。
    *   「フレームスロットの初期化は、フレーム作成時ではなく、定義時に行われる」ようになりました。これは、変数が定義されるコンパイル時に、その変数が使用するスロットが決定され、必要に応じてゼロ値で初期化されることを意味します。これにより、実行時のフレーム作成時のオーバーヘッドが削減されます。

5.  **ブロック出入りの効率化とジャンプの実現**:
    *   `block`の導入と`Frame`のフラット化により、ブロックの出入りがコード実行を伴わなくなりました。これは、以前のように新しい`Frame`を生成したり、既存の`Frame`を操作したりするランタイム処理が不要になったためです。
    *   結果として、「ブロック境界を越えるジャンプが可能になる」というメリットが生まれます。これは、`goto`文や`break`/`continue`文が、フレーム構造の複雑さに煩わされることなく、より直接的にターゲットに到達できるようになったことを示唆しています。

6.  **アウト変数のアクセス簡素化**:
    *   `Scope`が純粋なコンパイル時オブジェクトになったことで、「アウト変数へのアクセスに、関数アクティベーションフレームを特別に追跡する必要がなくなる」という利点が得られました。
    *   これは、クロージャが外部変数をキャプチャする際の実装が簡素化されたことを意味します。おそらく、コンパイル時にアウト変数のフレーム内のオフセットが解決され、実行時にはそのオフセットを使って直接アクセスできるようになります。

## コアとなるコードの変更箇所

主に `usr/austin/eval/decls.go` と `usr/austin/eval/scope.go` に大きな変更が見られます。

### `usr/austin/eval/decls.go`

*   **`type block struct` の新規導入**:
    ```go
    type block struct {
    	outer *block;
    	inner *block;
    	scope *Scope;
    	defs map[string] Def;
    	offset int;
    	numVars int;
    }
    ```
    この構造体が、ブロックスコープの具体的な定義と変数管理の責務を担います。`offset`と`numVars`は変数スロットの再利用に不可欠です。

*   **`type Scope struct` の変更**:
    ```go
    type Scope struct {
    	*block; // ルートブロックへのポインタ
    	maxVars int; // このスコープで必要な最大変数スロット数
    }
    ```
    `Scope`はもはや`outer *Scope`を持たず、`block`を埋め込み、`maxVars`を持つようになりました。これにより、`Scope`はコンパイル時の変数スロット割り当ての全体像を把握する役割に特化します。

*   **`type Frame struct` の変更**:
    ```go
    type Frame struct {
    	Outer *Frame;
    	Vars []Value;
    }
    ```
    `Scope *Scope`フィールドが削除され、`Frame`は純粋に実行時の変数値を保持する構造となりました。

*   **`func (f *Frame) Get(level int, index int) Value` の変更**:
    以前は`Get(s *Scope, index int)`でしたが、`level`引数を受け取るようになりました。これは、変数をルックアップする際に、`Scope`オブジェクトを比較するのではなく、外側のフレームを何段階遡るか（`level`）を指定する方式に変わったことを示します。

*   **`func (f *Frame) child(numVars int) *Frame` の新規導入**:
    `Scope.NewFrame`の代わりに、既存の`Frame`から子フレームを作成するヘルパー関数として導入されました。`numVars`は、この子フレームが必要とする変数スロットの総数を指定します。

### `usr/austin/eval/scope.go`

*   **`block`構造体へのメソッドの追加**:
    *   `enterChild() *block`: 現在のブロックの子ブロックを作成し、現在のブロックの`inner`フィールドに設定します。
    *   `exit()`: 現在のブロックを終了し、親ブロックの`inner`フィールドを`nil`に設定します。
    *   `ChildScope() *Scope`: 子ブロックから新しい`Scope`を作成します。
    *   `DefineVar(name string, t Type) *Variable`: ブロック内で変数を定義します。`DefineTemp`を呼び出して変数スロットを割り当て、`defs`マップに登録します。
    *   `DefineTemp(t Type) *Variable`: 一時変数を定義し、変数スロットを割り当てます。`offset`と`numVars`を使ってスロットインデックスを計算し、`scope.maxVars`を更新します。
    *   `Lookup(name string) (level int, def Def)`: ブロックチェーンを遡って変数をルックアップし、見つかった場合はその変数と、何段階外側のブロックで見つかったかを示す`level`を返します。

*   **`Scope`関連メソッドの変更**:
    *   `Scope.Fork()`が削除され、`block.ChildScope()`がその役割を担うようになりました。
    *   `Scope.DefineVar`などのメソッドは、`block`の対応するメソッドに処理を委譲するか、`block`の新しい構造に合わせて変更されました。
    *   `Scope.NewFrame`は、`outer.child(s.maxVars)`を呼び出すことで、フレームの作成を簡素化しています。

### その他のファイル (`compiler.go`, `expr.go`, `func.go`, `stmt.go`, `type.go`, `typec.go`)

これらのファイルでは、`Scope`オブジェクトを直接参照していた箇所が、新しく導入された`block`オブジェクトを参照するように変更されています。例えば、`compileFunc`、`compileExpr`、`compileType`などの関数シグネチャが`scope *Scope`から`b *block`に変更されています。また、`exprCompiler`や`blockCompiler`などの構造体も、`scope *Scope`フィールドが`block *block`フィールドに置き換えられています。

特に`func.go`では、`vm`構造体から`activation *Frame`フィールドが削除され、`evalFunc`構造体も`sc *Scope`と`fr *Frame`の代わりに`outer *Frame`と`frameSize int`を持つようになりました。これは、関数呼び出し時のフレーム管理が大幅に簡素化されたことを明確に示しています。

## コアとなるコードの解説

このコミットの核心は、Go言語の評価器が変数のスコープと実行時のスタックフレームをどのように管理するかという、根本的なモデルの変更にあります。

1.  **コンパイル時と実行時の責務の分離**:
    *   以前は`Scope`がコンパイル時の変数の可視性ルールと、実行時のフレーム構造の両方を暗黙的に管理していました。
    *   この変更により、`Scope`は純粋にコンパイル時の概念となり、変数の定義、型チェック、名前解決といった静的な側面を担当します。
    *   新しく導入された`block`構造体は、ブロックスコープ内の変数の定義と、それらが実行時にフレーム内のどこに配置されるか（`offset`と`numVars`）を管理します。
    *   `Frame`は純粋に実行時のデータ構造となり、変数の値を保持する配列（`Vars []Value`）と、外側のフレームへのポインタ（`Outer *Frame`）のみを持ちます。これにより、`Frame`は特定の`Scope`に依存せず、より汎用的なメモリ領域として機能します。

2.  **フラットなフレーム構造と変数スロットの再利用**:
    *   各関数呼び出しは、その関数内で必要となるすべてのローカル変数と引数を格納できる、単一の「フラットな」`Frame`を生成します。
    *   この`Frame`内の変数スロットは、`block`構造体の`offset`と`numVars`によって管理されます。コンパイル時に、異なるブロックスコープ内で定義された変数であっても、その生存期間が重ならない場合は、同じフレーム内の物理的なメモリ位置（スロット）を再利用するように割り当てられます。
    *   例えば、`if`ブロック内の変数と`else`ブロック内の変数は、同時に存在しないため、同じスロットを共有できます。これにより、実行時のメモリフットプリントが削減されます。

3.  **効率的なブロック出入りとジャンプ**:
    *   以前のツリー状の`Frame`構造では、ブロックに入るたびに新しい`Frame`を生成し、出るたびに破棄する必要があり、これがオーバーヘッドとなっていました。
    *   新しいモデルでは、関数全体で単一の`Frame`を使用し、変数の可視性は`block`チェーンと`Frame.Get(level, index)`によるルックアップで解決されます。
    *   これにより、ブロックの出入りは`block.enterChild()`と`block.exit()`といったコンパイル時の概念的な操作に限定され、実行時のフレーム操作は不要になります。
    *   この効率化は、`goto`文や`break`/`continue`文がブロック境界を越えても、複雑なフレーム操作なしに直接ターゲットにジャンプできることを意味し、より柔軟で効率的な制御フローの実装を可能にします。

4.  **変数初期化の最適化**:
    *   変数スロットの初期化が「フレーム作成時」から「定義時」に移動したことで、実行時のオーバーヘッドがさらに削減されます。
    *   変数が定義されるコンパイル時に、その変数が使用するスロットが決定され、必要に応じてゼロ値で初期化されるコードが生成されます。これにより、関数が呼び出されフレームが作成される際には、すでに必要なスロットが準備されている状態となります。

これらの変更は、Go言語の評価器のパフォーマンスを向上させ、より複雑な言語機能（特に制御フローやクロージャ）を効率的にサポートするための重要な基盤を築いたと言えます。

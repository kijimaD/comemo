# [インデックス 19825] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージにおける `ServeContent` 関数が、HTTPの `If-Range` ヘッダーにおいて `ETag` だけでなく、日付（`Last-Modified` タイムスタンプ）も適切にサポートするように拡張するものです。これにより、クライアントが `If-Range` ヘッダーに日付を指定した場合でも、サーバーが条件付きリクエストを正しく処理し、部分コンテンツの提供（レンジリクエスト）または完全なコンテンツの提供を決定できるようになります。

## 変更の背景

HTTP/1.1 の仕様（RFC 2616、後にRFC 7233で更新）では、`If-Range` ヘッダーは、クライアントがリソースの部分的なコピーを既に持っている場合に、そのコピーがまだ有効であるかどうかをサーバーに確認するために使用されます。このヘッダーは `Range` ヘッダーと組み合わせて使用され、クライアントがリソースの残りの部分を要求する際に、条件付きでリクエストを行います。

`If-Range` ヘッダーの値としては、`ETag`（エンティティタグ）または `Last-Modified` 日付のいずれかを指定できます。サーバーは、`If-Range` ヘッダーの値が現在のリソースの `ETag` または `Last-Modified` 日付と一致する場合にのみ、`Range` ヘッダーを処理し、部分コンテンツ（`206 Partial Content`）を返します。一致しない場合、サーバーは `Range` ヘッダーを無視し、リソース全体の最新バージョン（`200 OK`）を返します。

Goの `net/http` パッケージの `ServeContent` 関数は、ファイルやその他のコンテンツをHTTPレスポンスとして提供するために使用されます。この関数は、`Range` リクエストや条件付きリクエスト（`If-Modified-Since`, `If-None-Match` など）を自動的に処理するように設計されています。しかし、このコミット以前の `ServeContent` の実装では、`If-Range` ヘッダーの値として `ETag` のみを考慮しており、`Last-Modified` 日付が指定された場合には適切に処理されませんでした。

この不整合は、GoのIssue #8367として報告されました。このコミットは、この問題を修正し、`ServeContent` が `If-Range` ヘッダーに指定された日付も正しく解釈し、HTTP仕様に完全に準拠するようにすることで、より堅牢な部分コンテンツ提供機能を提供することを目的としています。これにより、クライアントは `ETag` または `Last-Modified` のどちらを使用しても、中断されたダウンロードの再開などをより信頼性高く行えるようになります。

## 前提知識の解説

### HTTP `If-Range` ヘッダー

`If-Range` ヘッダーは、HTTPの条件付きリクエストヘッダーの一つで、主に中断されたダウンロードの再開や、キャッシュされた部分コンテンツの検証に使用されます。このヘッダーは常に `Range` ヘッダーと組み合わせて使用されます。

*   **目的**: クライアントがリソースの部分的なコピーを保持している場合、そのコピーがサーバー上の最新のリソースと一致しているかを確認します。
*   **動作**:
    1.  クライアントは `Range` ヘッダー（例: `bytes=500-999`）と `If-Range` ヘッダーを同時に送信します。
    2.  `If-Range` ヘッダーの値には、クライアントが持っているリソースの `ETag` または `Last-Modified` 日付のいずれかが含まれます。
    3.  サーバーは、`If-Range` の値が現在のリソースの `ETag` または `Last-Modified` 日付と**一致する場合**、`Range` ヘッダーを処理し、`206 Partial Content` ステータスで要求されたバイト範囲のみを返します。これは、クライアントの持っている部分コピーがまだ有効であることを意味します。
    4.  サーバーは、`If-Range` の値が現在のリソースの `ETag` または `Last-Modified` 日付と**一致しない場合**（つまり、リソースが変更されている場合）、`Range` ヘッダーを**無視**します。代わりに、`200 OK` ステータスでリソース全体の最新バージョンを返します。これは、クライアントの部分コピーが無効になっているため、全体を再ダウンロードする必要があることを意味します。

### HTTP `ETag` と `Last-Modified`

これらはHTTPにおけるコンテンツの「バリデーター（検証子）」として機能し、リソースが変更されたかどうかを判断するために使用されます。

*   **`ETag` (Entity Tag)**: リソースの特定のバージョンを一意に識別する不透明な文字列です。リソースの内容が少しでも変更されると、`ETag` も変更されます。強力な `ETag` と弱い `ETag` がありますが、`If-Range` では強力な `ETag` が要求されます。
*   **`Last-Modified`**: リソースが最後に変更された日時を示す日付スタンプです。

### Go `net/http` パッケージ

Go言語の標準ライブラリ `net/http` は、HTTPクライアントとサーバーの実装を提供します。
*   **`http.ServeContent`**: この関数は、`io.ReadSeeker` インターフェースを実装する任意のコンテンツ（ファイル、メモリ上のデータなど）をHTTPレスポンスとして提供するために使用されます。`Range` リクエスト、条件付きリクエスト、MIMEタイプ検出、`Last-Modified` ヘッダーや `ETag` ヘッダーの設定など、HTTPサーバーがコンテンツを提供するために必要な多くの一般的なタスクを自動的に処理します。

## 技術的詳細

このコミットの主要な変更は、`net/http/fs.go` ファイル内の `checkETag` 関数に集中しています。この関数は、HTTPリクエストの `If-None-Match` および `If-Range` ヘッダーを検証する役割を担っています。

変更前は、`checkETag` 関数は `If-Range` ヘッダーの値が `ETag` と一致するかどうかのみをチェックしていました。もし一致しない場合、無条件に `rangeReq` を空文字列に設定し、結果としてサーバーは部分コンテンツではなく完全なコンテンツを返すようにしていました。これは、`If-Range` ヘッダーが `Last-Modified` 日付を含む可能性があるというHTTP仕様の側面を無視していました。

このコミットでは、以下の点が変更されました。

1.  **`checkETag` 関数のシグネチャ変更**:
    `func checkETag(w ResponseWriter, r *Request) (rangeReq string, done bool)`
    から
    `func checkETag(w ResponseWriter, r *Request, modtime time.Time) (rangeReq string, done bool)`
    へと変更されました。これにより、`ServeContent` 関数からコンテンツの最終更新時刻 (`modtime`) が `checkETag` に渡されるようになりました。

2.  **`If-Range` ヘッダーの処理ロジックの拡張**:
    `checkETag` 関数内で、`If-Range` ヘッダーの値が `ETag` と一致しない場合に、それが日付として解釈可能かどうかを試みる新しいロジックが追加されました。
    *   まず、`If-Range` の値が `ETag` と異なる場合に、`modtime.IsZero()` で `modtime` が有効な値であるかを確認します。`modtime` がゼロ値でない（つまり、有効な最終更新時刻が利用可能である）場合、`If-Range` の値を `ParseTime` 関数（`net/http` パッケージ内でHTTP日付文字列を `time.Time` に変換する関数）を使って日付としてパースを試みます。
    *   パースが成功し、かつパースされた日付のUnixタイムスタンプが `modtime` のUnixタイムスタンプと一致する場合（秒単位での比較）、`timeMatches` フラグが `true` に設定されます。これは、`If-Range` ヘッダーが日付として有効であり、かつリソースの最終更新時刻と一致することを示します。
    *   `ETag` とも `Last-Modified` 日付とも一致しない場合にのみ、`rangeReq` が空文字列に設定され、部分コンテンツの提供が無効化されます。

3.  **テストケースの追加**:
    `src/pkg/net/http/fs_test.go` に、`If-Range` ヘッダーに `Last-Modified` 日付が指定された場合の新しいテストケースが追加されました。これにより、この新しいロジックが期待通りに動作することが検証されます。特に、ナノ秒単位の精度を持つ `modtime` が与えられた場合でも、`If-Range` ヘッダーの日付が秒単位で一致すれば部分コンテンツが提供されることがテストされています。

この変更により、`ServeContent` はHTTP仕様に完全に準拠し、`If-Range` ヘッダーの柔軟な使用を可能にしました。

## コアとなるコードの解説

このコミットの核心は、`net/http/fs.go` 内の `checkETag` 関数が `If-Range` ヘッダーの処理を改善した点にあります。

変更前は、`checkETag` は `If-Range` ヘッダーの値が `ETag` と一致しない場合、無条件に `rangeReq` を空にしていました。これは、`If-Range` が `Last-Modified` 日付も取り得るというHTTP仕様の重要な側面を見落としていました。

変更後の `checkETag` 関数は、`modtime time.Time` という新しい引数を受け取るようになりました。これは、提供されるコンテンツの最終更新時刻を表します。

新しいロジックは以下の通りです。

1.  `If-Range` ヘッダーの値 (`ir`) が存在し、かつそれが現在の `ETag` と一致しない場合、追加のチェックが行われます。
2.  `modtime.IsZero()` をチェックし、有効な最終更新時刻が利用可能であるかを確認します。これは、`modtime` が設定されていない場合に不必要な日付パースを避けるためです。
3.  `modtime` が有効な場合、`ParseTime(ir)` を使用して `If-Range` の値を日付としてパースを試みます。`ParseTime` は、HTTP日付フォーマットの文字列を `time.Time` オブジェクトに変換するヘルパー関数です。
4.  パースが成功し、かつパースされた日付のUnixタイムスタンプ (`t.Unix()`) が、コンテンツの最終更新時刻のUnixタイムスタンプ (`modtime.Unix()`) と一致する場合、`timeMatches` が `true` に設定されます。ここで重要なのは、比較が秒単位で行われることです。これは、HTTP日付の精度が通常秒単位であるためです。
5.  最終的に、`ETag` とも `Last-Modified` 日付（`timeMatches`）とも一致しない場合にのみ、`rangeReq = ""` が実行されます。これにより、サーバーは `Range` ヘッダーを無視し、リソース全体の最新バージョンを返すことになります。

この変更により、`ServeContent` は `If-Range` ヘッダーに `ETag` または `Last-Modified` 日付のどちらが指定されても、HTTP仕様に従って正しく動作するようになりました。

`fs_test.go` に追加されたテストケースは、この新しい動作を検証します。特に、`range_with_modtime` と `range_with_modtime_nanos` のテストは、`If-Range` ヘッダーに日付が指定された場合に、部分コンテンツが正しく提供されることを確認しています。`range_with_modtime_nanos` は、`modtime` がナノ秒単位の精度を持っていても、HTTP日付の秒単位の比較が正しく機能することを示しています。

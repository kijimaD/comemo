Issue #13383 を修正します。

## 変更の背景

Webアプリケーションやサービスにおいて、クライアントに提供するコンテンツのMIMEタイプを正確に識別することは非常に重要です。特に、ユーザーがアップロードしたファイルや、サーバーが動的に生成するコンテンツの場合、ファイル拡張子だけではMIMEタイプを確実に判断できないことがあります。このような状況で、HTTPレスポンスヘッダーの `Content-Type` を正しく設定するためには、ファイルの内容を検査（スニッフィング）してMIMEタイプを推測するメカニズムが必要となります。

このコミットの背景には、Go言語の標準ライブラリである `net/http` パッケージが提供するMIMEタイプスニッフィング機能が、特定のオーディオおよびビデオフォーマットに対して不十分であったという課題がありました。具体的には、AIFF、Basic Audio、MIDI、MPEG Audio、AVIといった一般的なメディアフォーマットの検出がサポートされていませんでした。これにより、これらのファイルを扱うWebアプリケーションがGoで構築された場合、誤った `Content-Type` が設定されたり、MIMEタイプが不明とされたりする可能性がありました。

また、MIMEタイプスニッフィングの国際標準であるWHATWG MIME Sniffing Standardに完全に準拠するためには、既存のパターンマッチングアルゴリズムに修正が必要でした。特に、パターンとマスクのバイト長が一致するという重要な制約が実装されていなかったため、仕様との乖離が生じていました。

これらの問題を解決し、`net/http` パッケージの堅牢性と標準準拠性を高めることが、このコミットの主な動機となっています。

## 前提知識の解説

### MIMEタイプ (Multipurpose Internet Mail Extensions)

MIMEタイプは、インターネット上でやり取りされるデータの種類を識別するための標準的な方法です。HTTP通信では、サーバーがクライアントにファイルを送信する際に `Content-Type` ヘッダーにMIMEタイプを含めることで、クライアント（ブラウザなど）はそのデータがどのような種類であるかを理解し、適切に処理できます。例えば、`text/html` はHTMLドキュメント、`image/jpeg` はJPEG画像を示します。

### MIMEタイプスニッフィング (MIME Type Sniffing)

MIMEタイプスニッフィングとは、ファイルの内容（特に先頭のバイト列）を検査して、そのMIMEタイプを推測するプロセスです。ファイル拡張子に依存せず、データ自体の「マジックナンバー」や特定のパターンに基づいてタイプを識別するため、拡張子が欠落している場合や誤っている場合でも、より正確なMIMEタイプを判断できます。これは、Webブラウザがダウンロードしたコンテンツをどのように扱うべきかを決定する際や、サーバーがアップロードされたファイルのタイプを検証する際などに利用されます。

### WHATWG MIME Sniffing Standard

WHATWG (Web Hypertext Application Technology Working Group) は、Web技術の標準化を行う団体であり、MIMEタイプスニッフィングに関する詳細な仕様を策定しています。この仕様は、ブラウザやサーバーがMIMEタイプを安全かつ一貫性のある方法で推測するためのアルゴリズムを定義しています。この標準に従うことで、異なるシステム間でのMIMEタイプ解釈の互換性が保証され、セキュリティ上の問題（例：悪意のあるファイルが誤ったMIMEタイプで実行される）を防ぐことができます。

このコミットで参照されている主要なセクションは以下の通りです。

*   **Matching an audio or video type pattern**: オーディオ/ビデオタイプを識別するための具体的なバイトパターンとロジックを定義しています。
*   **Matching a MIME type pattern**: 一般的なMIMEタイプパターンマッチングアルゴリズムを定義しており、特に「パターン内のバイト数とマスク内のバイト数が一致しなければならない」という条項4が重要です。

### マジックナンバーとバイトパターン

多くのファイルフォーマットは、ファイルの先頭にそのフォーマットを識別するための特定のバイト列を持っています。これを「マジックナンバー」と呼びます。例えば、JPEGファイルは `FF D8 FF E0` で始まることが多く、PNGファイルは `89 50 4E 47 0D 0A 1A 0A` で始まります。MIMEタイプスニッフィングは、これらのマジックナンバーやより複雑なバイトパターンをデータと比較することで、ファイルタイプを特定します。

### `sniffSig` インターフェースと `maskedSig` 構造体

Goの `net/http` パッケージでは、MIMEタイプスニッフィングのために `sniffSig` というインターフェースが定義されており、様々なシグネチャ（パターン）がこのインターフェースを実装しています。
`maskedSig` は、特定のバイトパターンとマスク（どのバイトを比較対象とするかを指定する）を使用してMIMEタイプを検出するための構造体です。マスクは、パターンの一部が可変である場合（例：ファイルサイズが記述される部分など）に、比較対象から除外するバイトを指定するために使用されます。マスクのバイトが `0x00` の場合、対応するデータのバイトは比較されません。`0xFF` の場合、対応するデータのバイトはパターンと完全に一致する必要があります。

## 技術的詳細

このコミットは、`net/http` パッケージの `sniff.go` ファイルにMIMEタイプスニッフィングのロジックを追加・修正しています。

1.  **新しいオーディオ/ビデオフォーマットのサポート**:
    *   `audio/aiff`: AIFF (Audio Interchange File Format) は、Appleによって開発されたオーディオファイルフォーマットです。`FORM` チャンクと `AIFF` フォームタイプを持つRIFF (Resource Interchange File Format) 構造に基づいています。
    *   `audio/basic`: Sun Microsystemsによって開発されたオーディオフォーマットで、通常は `.snd` 拡張子を持ちます。ファイルの先頭に特定のヘッダー情報が含まれます。
    *   `audio/midi`: MIDI (Musical Instrument Digital Interface) は、電子楽器間の通信プロトコルおよびファイルフォーマットです。ファイルの先頭に `MThd` (MIDI Header) チャンクを持ちます。
    *   `audio/mpeg`: MPEG (Moving Picture Experts Group) オーディオ、特にMP3 (MPEG-1 Audio Layer III) を指します。ファイルの先頭に `ID3` タグ（メタデータ）が存在することが一般的です。
    *   `video/avi`: AVI (Audio Video Interleave) は、Microsoftによって開発されたマルチメディアコンテナフォーマットです。RIFF構造に基づき、ファイルの先頭に `RIFF` チャンクと `AVI ` フォームタイプを持ちます。

    これらのフォーマットに対応するため、`sniffSignatures` スライスに新しい `maskedSig` エントリが追加されています。各エントリは、特定のバイトパターン (`pat`) と、そのパターンをデータと比較する際にどのバイトを考慮するかを示すマスク (`mask`) を定義しています。

2.  **`application/ogg` シグネチャの更新**:
    既存の `application/ogg` のシグネチャが `exactSig` から `maskedSig` に変更され、より厳密なパターンマッチングが行われるようになりました。Oggコンテナフォーマットは、`OggS` というマジックナンバーで始まります。

3.  **パターンマッチングアルゴリズムの修正**:
    `maskedSig` の `match` メソッドに重要な変更が加えられました。WHATWG MIME Sniffing Standardの「Matching a MIME type pattern」セクションの条項4に従い、`len(m.pat) != len(m.mask)` の場合に空文字列を返す（つまりマッチしないと判断する）ロジックが追加されました。これは、パターンとマスクの長さが一致しない場合、そのシグネチャは無効であるという仕様の厳密な解釈を反映しています。これにより、MIMEタイプスニッフィングの堅牢性と標準準拠性が向上します。

    この変更は、`maskedSig` の定義において、`pat` と `mask` が常に同じ長さを持つべきであるという前提を強制するものです。もし異なる長さで定義されたシグネチャがあった場合、以前は予期せぬ動作をする可能性がありましたが、この修正により明確にマッチしないと判断されるようになります。

## コアとなるコードの解説

### `src/net/http/sniff.go` の変更点

*   **`sniffSignatures` スライスの拡張**:
    `sniffSignatures` は、MIMEタイプスニッフィングに使用されるすべてのシグネチャを保持するスライスです。このコミットでは、`audio/aiff`, `audio/basic`, `audio/midi`, `audio/mpeg`, `video/avi` の各MIMEタイプに対応する `maskedSig` インスタンスが追加されました。これらの `maskedSig` は、それぞれのフォーマットのマジックナンバーや特定のヘッダーパターンを `pat` フィールドに、そして比較対象とするバイトを示す `mask` フィールドに定義しています。
    例えば、`audio/aiff` のシグネチャは `FORM` と `AIFF` という文字列を特定のオフセットで探し、その間のバイトは `\x00` マスクで無視されます。これは、RIFFベースのファイルフォーマットでファイルサイズが可変であるため、その部分をマスクで無視する必要があるためです。
    `application/ogg` のシグネチャは、以前の `exactSig` から `maskedSig` に変更されました。これにより、より柔軟なパターンマッチングが可能になり、Oggフォーマットのバリエーションに対応しやすくなります。

*   **`maskedSig.match` メソッドの修正**:
    このメソッドは、与えられたバイトデータが `maskedSig` のパターンに一致するかどうかを判断します。追加された `if len(m.pat) != len(m.mask)` のチェックは、WHATWG MIME Sniffing Standardの条項4を直接実装したものです。この条項は、「パターン内のバイト数とマスク内のバイト数が一致しなければならない」と規定しています。このチェックが追加されたことで、もし誤って `pat` と `mask` の長さが異なる `maskedSig` が定義された場合でも、それがMIMEタイプスニッフィングのロジックに混乱をもたらすことなく、単にマッチしないと判断されるようになります。これにより、スニッフィングアルゴリズムの堅牢性と仕様への準拠が強化されます。

### `src/net/http/sniff_test.go` の変更点

*   **新しいテストケースの追加**:
    `sniffTests` スライスに、新たに追加されたオーディオ/ビデオMIMEタイプ（MIDI、MP3、WAV、AIFF、OGG、AVI）の検出を検証するためのテストケースが多数追加されました。これらのテストケースは、各フォーマットの実際のバイト列のサンプルと、期待されるMIMEタイプを定義しています。これにより、変更が正しく機能し、新しいMIMEタイプが正確に識別されることが保証されます。既存のWAVとMP4のテストケースも、新しいオーディオ/ビデオタイプと並べて整理されています。

これらの変更により、Goの `net/http` パッケージは、より広範なメディアフォーマットを正確に識別できるようになり、Web標準への準拠も強化されました。

# [インデックス 21918] ファイルの概要

このコミットは、Goコンパイラ（`cmd/6g`および`cmd/8g`）におけるメモリコピー操作の効率化に関するものです。特に、2ワードまたは3ワードといった短いサイズのメモリコピーにおいて、既存の`MOVSQ`/`MOVSL`命令に依存するのではなく、明示的な`MOVQ`/`MOVL`命令とアドレスオフセットのインクリメントを組み合わせることで、パフォーマンスを大幅に向上させています。これは、Go標準ライブラリのコンパイル時にこれらの短いコピー操作が頻繁に発生することに着目した最適化です。

## 変更の背景

この変更の背景には、Goコンパイラが標準ライブラリをコンパイルする際のパフォーマンスボトルネックがありました。コミットメッセージによると、`sgen`関数への呼び出しの大部分（`cmd/6g`では85%、`cmd/8g`では70%）が、正確に2ワードまたは3ワードのデータコピーに関するものでした。

既存の`sgen`の実装では、これらの短いコピーに対しても汎用的なメカニズム（特にDuff's Deviceを利用した`duffcopy`や、x86の文字列操作命令`MOVSQ`/`MOVSL`）が使用されていました。しかし、これらの汎用的なアプローチは、非常に短いコピーにおいてはオーバーヘッドが大きくなることが判明しました。

具体的には、`MOVSQ`や`MOVSL`のような命令は、ソースとデスティネーションのポインタ（`SI`と`DI`レジスタ）を自動的にインクリメントする副作用を持ちますが、この副作用が不要な場合や、命令のセットアップコストがコピーサイズに対して相対的に大きい場合に非効率的になります。

この非効率性を解消し、コンパイル時間を短縮するために、2ワードまたは3ワードのコピーに特化した最適化が導入されました。ベンチマーク結果が示すように、この変更により、`BenchmarkCopyFat16`（16バイト、2ワード）で74.77%減、`BenchmarkCopyFat24`（24バイト、3ワード）で82.63%減といった劇的な改善が達成されています。

## 前提知識の解説

### Goコンパイラ (`cmd/6g`, `cmd/8g`, `cmd/5g`, `cmd/9g`)

Go言語の初期のコンパイラは、ターゲットアーキテクチャごとに異なる名前を持っていました。
*   `cmd/6g`: AMD64 (x86-64) アーキテクチャ向けのGoコンパイラ。
*   `cmd/8g`: 386 (x86) アーキテクチャ向けのGoコンパイラ。
*   `cmd/5g`: ARMアーキテクチャ向けのGoコンパイラ。
*   `cmd/9g`: PowerPCアーキテクチャ向けのGoコンパイラ。

このコミットは`6g`と`8g`に特化しており、`5g`と`9g`には関係ないと明記されています。これは、最適化の対象となる命令がx86/x86-64アーキテクチャに固有のものであるためです。

### `sgen`関数

`sgen`は"structure generation"または"sequence generation"の略で、Goコンパイラのバックエンドにおいて、構造体や配列などのメモリブロックをコピーするためのアセンブリコードを生成する役割を担う関数です。これは、変数間の代入や関数呼び出し時の引数・戻り値の受け渡しなど、様々な場面で利用されます。

### Duff's Device (`duffcopy`)

Duff's Deviceは、C言語で書かれた効率的なループアンローリングのテクニックです。Goのランタイムでは、大きなメモリブロックのコピーを最適化するために、このDuff's Deviceの原理を応用した`duffcopy`というアセンブリルーチンが使用されています。これは、ループのオーバーヘッドを減らし、キャッシュ効率を向上させることで、高速なメモリコピーを実現します。`sgen`関数内で、特定のサイズ以上のコピーに対して`duffcopy`が呼び出されることがあります。

### x86アセンブリ命令

*   **`MOVSQ` (Move String Quadword)**: x86-64アーキテクチャの命令で、`RSI`（Source Index）レジスタが指すメモリ位置から8バイト（Quadword）のデータを`RDI`（Destination Index）レジスタが指すメモリ位置にコピーします。コピー後、`RSI`と`RDI`は自動的に8バイト分インクリメント（またはデクリメント、`DF`フラグによる）されます。これは、連続したメモリブロックを効率的にコピーするために設計されています。
*   **`MOVSL` (Move String Long)**: 386アーキテクチャの命令で、`ESI`（Source Index）レジスタが指すメモリ位置から4バイト（Longword）のデータを`EDI`（Destination Index）レジスタが指すメモリ位置にコピーします。`ESI`と`EDI`は自動的に4バイト分インクリメント（またはデクリメント）されます。
*   **`MOVQ` (Move Quadword)**: x86-64アーキテクチャの汎用データ転送命令で、8バイトのデータをレジスタ間、またはレジスタとメモリ間でコピーします。`MOVSQ`と異なり、ポインタの自動インクリメントは行いません。
*   **`MOVL` (Move Long)**: 386アーキテクチャの汎用データ転送命令で、4バイトのデータをレジスタ間、またはレジスタとメモリ間でコピーします。`MOVSL`と異なり、ポインタの自動インクリメントは行いません。

### x86レジスタ

*   **`SI` (Source Index) / `RSI`**: ソースオペランドのオフセットを保持するために使用されるレジスタ。文字列操作命令でソースアドレスを指すのに使われます。
*   **`DI` (Destination Index) / `RDI`**: デスティネーションオペランドのオフセットを保持するために使用されるレジスタ。文字列操作命令でデスティネーションアドレスを指すのに使われます。
*   **`CX` (Count Register) / `RCX`**: ループカウンタとしてよく使用される汎用レジスタ。このコミットでは、一時的なデータ転送の中間レジスタとして利用されています。

### Native Client (NaCl)

Google Native Client (NaCl) は、ウェブブラウザ内でネイティブコードを安全に実行するための技術です。GoコンパイラはNaClをターゲットとすることもできましたが、この最適化はNaCl環境では適用されません。これは、NaClのサンドボックス環境が特定の命令の使用を制限したり、パフォーマンス特性が異なるためと考えられます。

## 技術的詳細

このコミットの核心は、短いメモリコピー（2ワードまたは3ワード）の処理方法を変更することにあります。従来の`sgen`関数では、これらの短いコピーに対しても、`MOVSQ`（6gの場合）や`MOVSL`（8gの場合）といった文字列操作命令を使用していました。これらの命令は、`SI`/`DI`レジスタを自動的に更新する機能を持っています。

しかし、コピーするデータが非常に少ない場合、`MOVSQ`/`MOVSL`命令のセットアップコストや、レジスタの自動更新という「副作用」が、純粋なデータ転送の効率を低下させる要因となっていました。特に、`SI`や`DI`レジスタの値を明示的に管理する必要がない場合、自動更新はむしろオーバーヘッドになり得ます。

新しいアプローチでは、この自動更新の副作用を回避し、より直接的なデータ転送を行います。具体的には、以下の手順でコピーを実行します。

1.  ソースアドレスから一時レジスタ（`CX`/`RCX`）にデータを`MOVQ`/`MOVL`命令でコピーします。
2.  一時レジスタからデスティネーションアドレスにデータを`MOVQ`/`MOVL`命令でコピーします。
3.  ソースとデスティネーションのオフセットを、コピーしたワードサイズ分（6gでは8バイト、8gでは4バイト）明示的にインクリメントします。
4.  これをコピーすべきワード数だけ繰り返します。

この方法により、`MOVSQ`/`MOVSL`命令の持つ余分なロジックや、レジスタの自動更新に伴う潜在的なパイプラインストールなどを回避し、よりシンプルな一連の`MOV`命令としてコードを生成できます。結果として、CPUの実行効率が向上し、特に頻繁に発生する短いコピーのパフォーマンスが大幅に改善されます。

コミットメッセージのベンチマーク結果は、この最適化が非常に効果的であることを明確に示しています。例えば、`BenchmarkCopyFat16`（16バイト、2ワード）では、旧バージョンと比較して実行時間が約75%短縮されています。

## コアとなるコードの解説

追加されたコードブロックは、`sgen`関数内の既存の`duffcopy`呼び出しロジックの直後に挿入されています。

```c
} else if(!nacl && c == 0) {
    // We don't need the MOVSQ side-effect of updating SI and DI,
    // and issuing a sequence of MOVQs directly is faster.
    nodsi.op = OINDREG; // 6g
    noddi.op = OINDREG; // 6g
    // or
    nodreg(&cx, types[TINT32], REG_CX); // 8g: CXレジスタを32ビット整数型として設定
    src.op = OINDREG; // 8g
    dst.op = OINDREG; // 8g

    while(q > 0) {
        gmove(&nodsi, &cx); // 6g: MOVQ x+(SI),CX (ソースからCXへ8バイトコピー)
        gmove(&cx, &noddi); // 6g: MOVQ CX,x+(DI) (CXからデスティネーションへ8バイトコピー)
        // or
        gmove(&src, &cx); // 8g: MOVL x+(SI),CX (ソースからCXへ4バイトコピー)
        gmove(&cx, &dst); // 8g: MOVL CX,x+(DI) (CXからデスティネーションへ4バイトコピー)

        nodsi.xoffset += 8; // 6g: ソースオフセットを8バイト進める
        noddi.xoffset += 8; // 6g: デスティネーションオフセットを8バイト進める
        // or
        src.xoffset += 4; // 8g: ソースオフセットを4バイト進める
        dst.xoffset += 4; // 8g: デスティネーションオフセットを4バイト進める
        q--; // 残りのワード数を減らす
    }
}
```

この新しいブロックは、以下の条件が満たされた場合に実行されます。
*   `!nacl`: Native Client環境ではない場合。
*   `c == 0`: これは、コピーするワード数が2または3の場合に該当する条件です。`sgen`関数内のロジックで、`c`はコピーサイズに関連する内部変数であり、`c == 0`が短いコピーサイズ（特に2ワードや3ワード）を示す特殊なケースとして扱われています。

このブロックの内部では、以下の処理が行われます。

1.  **レジスタとノードの準備**:
    *   `nodsi.op = OINDREG;` / `noddi.op = OINDREG;` (6g): ソースとデスティネーションのノードを、レジスタ間接アドレッシング（`SI`と`DI`レジスタをベースとしたオフセットアクセス）を使用するように設定します。
    *   `nodreg(&cx, types[TINT32], REG_CX);` (8g): 386アーキテクチャでは、一時レジスタとして`CX`を使用するために、そのノードを初期化します。
    *   `src.op = OINDREG;` / `dst.op = OINDREG;` (8g): 同様に、ソースとデスティネーションのノードをレジスタ間接アドレッシングを使用するように設定します。

2.  **ループによる明示的なコピー**:
    *   `while(q > 0)`: コピーすべきワード数（`q`）が0になるまでループを繰り返します。`q`はコピーするワード数を示します。
    *   `gmove(&nodsi, &cx);` / `gmove(&src, &cx);`: ソースメモリ位置から`CX`レジスタへデータを移動するアセンブリ命令（`MOVQ`または`MOVL`）を生成します。
    *   `gmove(&cx, &noddi);` / `gmove(&cx, &dst);`: `CX`レジスタからデスティネーションメモリ位置へデータを移動するアセンブリ命令（`MOVQ`または`MOVL`）を生成します。
    *   `nodsi.xoffset += 8;` / `noddi.xoffset += 8;` (6g): ソースとデスティネーションのオフセットを8バイト（1ワード）分進めます。
    *   `src.xoffset += 4;` / `dst.xoffset += 4;` (8g): ソースとデスティネーションのオフセットを4バイト（1ワード）分進めます。
    *   `q--;`: コピーしたワード数をカウントダウンします。

このコードは、`MOVSQ`/`MOVSL`命令の自動インクリメント機能に頼る代わりに、`MOVQ`/`MOVL`命令と明示的なオフセットの加算を組み合わせることで、より細かく制御された、かつ短いコピーに最適化されたアセンブリコードを生成します。これにより、コンパイラが生成するコードの効率が向上し、結果としてGoプログラムのコンパイル時間が短縮されます。

## 変更の背景

この変更の背景には、Goコンパイラが標準ライブラリをコンパイルする際のパフォーマンスボトルネックがありました。コミットメッセージによると、`sgen`関数への呼び出しの大部分（`cmd/6g`では85%、`cmd/8g`では70%）が、正確に2ワードまたは3ワードのデータコピーに関するものでした。

既存の`sgen`の実装では、これらの短いコピーに対しても汎用的なメカニズム（特にDuff's Deviceを利用した`duffcopy`や、x86の文字列操作命令`MOVSQ`/`MOVSL`）が使用されていました。しかし、これらの汎用的なアプローチは、非常に短いコピーにおいてはオーバーヘッドが大きくなることが判明しました。

具体的には、`MOVSQ`や`MOVSL`のような命令は、ソースとデスティネーションのポインタ（`SI`と`DI`レジスタ）を自動的にインクリメントする副作用を持ちますが、この副作用が不要な場合や、命令のセットアップコストがコピーサイズに対して相対的に大きい場合に非効率的になります。

この非効率性を解消し、コンパイル時間を短縮するために、2ワードまたは3ワードのコピーに特化した最適化が導入されました。ベンチマーク結果が示すように、この変更により、`BenchmarkCopyFat16`（16バイト、2ワード）で74.77%減、`BenchmarkCopyFat24`（24バイト、3ワード）で82.63%減といった劇的な改善が達成されています。

## 前提知識の解説

### Goコンパイラ (`cmd/6g`, `cmd/8g`, `cmd/5g`, `cmd/9g`)

Go言語の初期のコンパイラは、ターゲットアーキテクチャごとに異なる名前を持っていました。
*   `cmd/6g`: AMD64 (x86-64) アーキテクチャ向けのGoコンパイラ。
*   `cmd/8g`: 386 (x86) アーキテクチャ向けのGoコンパイラ。
*   `cmd/5g`: ARMアーキテクチャ向けのGoコンパイラ。
*   `cmd/9g`: PowerPCアーキテクチャ向けのGoコンパイラ。

このコミットは`6g`と`8g`に特化しており、`5g`と`9g`には関係ないと明記されています。これは、最適化の対象となる命令がx86/x86-64アーキテクチャに固有のものであるためです。

### `sgen`関数

`sgen`は"structure generation"または"sequence generation"の略で、Goコンパイラのバックエンドにおいて、構造体や配列などのメモリブロックをコピーするためのアセンブリコードを生成する役割を担う関数です。これは、変数間の代入や関数呼び出し時の引数・戻り値の受け渡しなど、様々な場面で利用されます。

### Duff's Device (`duffcopy`)

Duff's Deviceは、C言語で書かれた効率的なループアンローリングのテクニックです。Goのランタイムでは、大きなメモリブロックのコピーを最適化するために、このDuff's Deviceの原理を応用した`duffcopy`というアセンブリルーチンが使用されています。これは、ループのオーバーヘッドを減らし、キャッシュ効率を向上させることで、高速なメモリコピーを実現します。`sgen`関数内で、特定のサイズ以上のコピーに対して`duffcopy`が呼び出されることがあります。

### x86アセンブリ命令

*   **`MOVSQ` (Move String Quadword)**: x86-64アーキテクチャの命令で、`RSI`（Source Index）レジスタが指すメモリ位置から8バイト（Quadword）のデータを`RDI`（Destination Index）レジスタが指すメモリ位置にコピーします。コピー後、`RSI`と`RDI`は自動的に8バイト分インクリメント（またはデクリメント、`DF`フラグによる）されます。これは、連続したメモリブロックを効率的にコピーするために設計されています。
*   **`MOVSL` (Move String Long)**: 386アーキテクチャの命令で、`ESI`（Source Index）レジスタが指すメモリ位置から4バイト（Longword）のデータを`EDI`（Destination Index）レジスタが指すメモリ位置にコピーします。`ESI`と`EDI`は自動的に4バイト分インクリメント（またはデクリメント）されます。
*   **`MOVQ` (Move Quadword)**: x86-64アーキテクチャの汎用データ転送命令で、8バイトのデータをレジスタ間、またはレジスタとメモリ間でコピーします。`MOVSQ`と異なり、ポインタの自動インクリメントは行いません。
*   **`MOVL` (Move Long)**: 386アーキテクチャの汎用データ転送命令で、4バイトのデータをレジスタ間、またはレジスタとメモリ間でコピーします。`MOVSL`と異なり、ポインタの自動インクリメントは行いません。

### x86レジスタ

*   **`SI` (Source Index) / `RSI`**: ソースオペランドのオフセットを保持するために使用されるレジスタ。文字列操作命令でソースアドレスを指すのに使われます。
*   **`DI` (Destination Index) / `RDI`**: デスティネーションオペランドのオフセットを保持するために使用されるレジスタ。文字列操作命令でデスティネーションアドレスを指すのに使われます。
*   **`CX` (Count Register) / `RCX`**: ループカウンタとしてよく使用される汎用レジスタ。このコミットでは、一時的なデータ転送の中間レジスタとして利用されています。

### Native Client (NaCl)

Google Native Client (NaCl) は、ウェブブラウザ内でネイティブコードを安全に実行するための技術です。GoコンパイラはNaClをターゲットとすることもできましたが、この最適化はNaCl環境では適用されません。これは、NaClのサンドボックス環境が特定の命令の使用を制限したり、パフォーマンス特性が異なるためと考えられます。

## 技術的詳細

このコミットの核心は、短いメモリコピー（2ワードまたは3ワード）の処理方法を変更することにあります。従来の`sgen`関数では、これらの短いコピーに対しても、`MOVSQ`（6gの場合）や`MOVSL`（8gの場合）といった文字列操作命令を使用していました。これらの命令は、`SI`/`DI`レジスタを自動的に更新する機能を持っています。

しかし、コピーするデータが非常に少ない場合、`MOVSQ`/`MOVSL`命令のセットアップコストや、レジスタの自動更新という「副作用」が、純粋なデータ転送の効率を低下させる要因となっていました。特に、`SI`や`DI`レジスタの値を明示的に管理する必要がない場合、自動更新はむしろオーバーヘッドになり得ます。

新しいアプローチでは、この自動更新の副作用を回避し、より直接的なデータ転送を行います。具体的には、以下の手順でコピーを実行します。

1.  ソースアドレスから一時レジスタ（`CX`/`RCX`）にデータを`MOVQ`/`MOVL`命令でコピーします。
2.  一時レジスタからデスティネーションアドレスにデータを`MOVQ`/`MOVL`命令でコピーします。
3.  ソースとデスティネーションのオフセットを、コピーしたワードサイズ分（6gでは8バイト、8gでは4バイト）明示的にインクリメントします。
4.  これをコピーすべきワード数だけ繰り返します。

この方法により、`MOVSQ`/`MOVSL`命令の持つ余分なロジックや、レジスタの自動更新に伴う潜在的なパイプラインストールなどを回避し、よりシンプルな一連の`MOV`命令としてコードを生成できます。結果として、CPUの実行効率が向上し、特に頻繁に発生する短いコピーのパフォーマンスが大幅に改善されます。

コミットメッセージのベンチマーク結果は、この最適化が非常に効果的であることを明確に示しています。例えば、`BenchmarkCopyFat16`（16バイト、2ワード）では、旧バージョンと比較して実行時間が約75%短縮されています。

## コアとなるコードの解説

追加されたコードブロックは、`sgen`関数内の既存の`duffcopy`呼び出しロジックの直後に挿入されています。

```c
} else if(!nacl && c == 0) {
    // We don't need the MOVSQ side-effect of updating SI and DI,
    // and issuing a sequence of MOVQs directly is faster.
    nodsi.op = OINDREG; // 6g
    noddi.op = OINDREG; // 6g
    // or
    nodreg(&cx, types[TINT32], REG_CX); // 8g: CXレジスタを32ビット整数型として設定
    src.op = OINDREG; // 8g
    dst.op = OINDREG; // 8g

    while(q > 0) {
        gmove(&nodsi, &cx); // 6g: MOVQ x+(SI),CX (ソースからCXへ8バイトコピー)
        gmove(&cx, &noddi); // 6g: MOVQ CX,x+(DI) (CXからデスティネーションへ8バイトコピー)
        // or
        gmove(&src, &cx); // 8g: MOVL x+(SI),CX (ソースからCXへ4バイトコピー)
        gmove(&cx, &dst); // 8g: MOVL CX,x+(DI) (CXからデスティネーションへ4バイトコピー)

        nodsi.xoffset += 8; // 6g: ソースオフセットを8バイト進める
        noddi.xoffset += 8; // 6g: デスティネーションオフセットを8バイト進める
        // or
        src.xoffset += 4; // 8g: ソースオフセットを4バイト進める
        dst.xoffset += 4; // 8g: デスティネーションオフセットを4バイト進める
        q--; // 残りのワード数を減らす
    }
}
```

この新しいブロックは、以下の条件が満たされた場合に実行されます。
*   `!nacl`: Native Client環境ではない場合。
*   `c == 0`: これは、コピーするワード数が2または3の場合に該当する条件です。`sgen`関数内のロジックで、`c`はコピーサイズに関連する内部変数であり、`c == 0`が短いコピーサイズ（特に2ワードや3ワード）を示す特殊なケースとして扱われています。

このブロックの内部では、以下の処理が行われます。

1.  **レジスタとノードの準備**:
    *   `nodsi.op = OINDREG;` / `noddi.op = OINDREG;` (6g): ソースとデスティネーションのノードを、レジスタ間接アドレッシング（`SI`と`DI`レジスタをベースとしたオフセットアクセス）を使用するように設定します。
    *   `nodreg(&cx, types[TINT32], REG_CX);` (8g): 386アーキテクチャでは、一時レジスタとして`CX`を使用するために、そのノードを初期化します。
    *   `src.op = OINDREG;` / `dst.op = OINDREG;` (8g): 同様に、ソースとデスティネーションのノードをレジスタ間接アドレッシングを使用するように設定します。

2.  **ループによる明示的なコピー**:
    *   `while(q > 0)`: コピーすべきワード数（`q`）が0になるまでループを繰り返します。`q`はコピーするワード数を示します。
    *   `gmove(&nodsi, &cx);` / `gmove(&src, &cx);`: ソースメモリ位置から`CX`レジスタへデータを移動するアセンブリ命令（`MOVQ`または`MOVL`）を生成します。
    *   `gmove(&cx, &noddi);` / `gmove(&cx, &dst);`: `CX`レジスタからデスティネーションメモリ位置へデータを移動するアセンブリ命令（`MOVQ`または`MOVL`）を生成します。
    *   `nodsi.xoffset += 8;` / `noddi.xoffset += 8;` (6g): ソースとデスティネーションのオフセットを8バイト（1ワード）分進めます。
    *   `src.xoffset += 4;` / `dst.xoffset += 4;` (8g): ソースとデスティネーションのオフセットを4バイト（1ワード）分進めます。
    *   `q--;`: コピーしたワード数をカウントダウンします。

このコードは、`MOVSQ`/`MOVSL`命令の自動インクリメント機能に頼る代わりに、`MOVQ`/`MOVL`命令と明示的なオフセットの加算を組み合わせることで、より細かく制御された、かつ短いコピーに最適化されたアセンブリコードを生成します。これにより、コンパイラが生成するコードの効率が向上し、結果としてGoプログラムのコンパイル時間が短縮されます。

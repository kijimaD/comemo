# [インデックス 27517] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/mail` パッケージにおける `ParseAddress` 関数の挙動を修正するものです。具体的には、`ParseAddress` 関数が単一のメールアドレスのみを解析することを保証し、入力文字列に複数のメールアドレスが含まれていた場合にエラーを返すように変更されました。これにより、開発者が意図しない形で複数のアドレスが処理されることを防ぎ、より堅牢なメールアドレス解析が可能になります。

## 元コミット内容

`net/mail: throw error when multiple addresses are given to ParseAddress`

このコミットは、`net/mail` パッケージの `ParseAddress` 関数が、入力に複数のメールアドレスが含まれている場合にエラーを発生させるように修正します。これは、Issue #14610 で報告された問題に対応するものです。

## 変更の背景

`net/mail` パッケージの `ParseAddress` 関数は、その名前が示す通り、単一のメールアドレスを解析することを目的としています。しかし、このコミット以前のバージョンでは、入力文字列に「`a@gmail.com b@gmail.com`」のように複数のメールアドレスが含まれていた場合でも、エラーを発生させずに最初のメールアドレス（この例では `a@gmail.com`）だけを解析し、残りの部分を黙って無視していました。

この挙動は、開発者が `ParseAddress` を使用する際に予期せぬ結果を招く可能性がありました。例えば、ユーザー入力の検証や、メールヘッダーの解析において、単一のアドレスが期待される場面で複数のアドレスが渡された場合、残りのアドレスが処理されずに見過ごされてしまうというバグにつながる恐れがありました。

Issue #14610 はこの問題を指摘し、`ParseAddress` がその意図通りに単一のアドレスのみを厳密に解析し、複数のアドレスが検出された場合には明確なエラーを返すようにすることを求めました。この変更は、APIのセマンティクスを明確にし、開発者がより安全に `net/mail` パッケージを利用できるようにすることを目的としています。

## 前提知識の解説

### RFC 5322 (Internet Message Format)

RFC 5322 は、インターネットメッセージ（主に電子メール）の標準フォーマットを定義する仕様です。メールアドレスの構造、ヘッダーフィールドの書式、メッセージ本文の構成など、電子メールの送受信に関する基本的なルールを定めています。`net/mail` パッケージは、このRFC 5322 に準拠したメールアドレスの解析やメッセージの処理を提供します。

### `net/mail` パッケージ

Go言語の標準ライブラリである `net/mail` パッケージは、RFC 5322 に基づいて電子メールメッセージを解析するための機能を提供します。主な機能には、メールアドレスの解析 (`ParseAddress`, `ParseAddressList`)、メッセージヘッダーの解析 (`ReadMessage`) などがあります。

*   **`ParseAddress(address string) (*Address, error)`**: 単一のメールアドレス文字列を解析し、`*mail.Address` 構造体を返します。
*   **`ParseAddressList(list string) ([]*Address, error)`**: 複数のメールアドレスがカンマで区切られた文字列を解析し、`[]*mail.Address` のスライスを返します。

このコミットの焦点は `ParseAddress` 関数であり、その厳密な単一アドレス解析の保証にあります。

### Go言語のエラーハンドリング

Go言語では、エラーは関数の戻り値として明示的に扱われます。慣例として、関数は通常の結果とエラーの2つの値を返します。エラーが発生した場合、エラー値は `nil` 以外となり、呼び出し元はそのエラーを適切に処理する必要があります。このコミットでは、`ParseAddress` が複数のアドレスを検出した場合に `error` を返すように変更することで、このGo言語のエラーハンドリングの原則に則っています。

## 技術的詳細

このコミットの技術的な核心は、`ParseAddress` および `AddressParser.Parse` 関数が、内部的に新しいヘルパー関数 `parseSingleAddress` を呼び出すように変更された点です。

1.  **`parseSingleAddress` 関数の導入**:
    `addrParser` 構造体に `parseSingleAddress()` という新しいメソッドが追加されました。このメソッドは以下のロジックで動作します。
    *   まず、既存の `p.parseAddress()` メソッドを呼び出して、入力文字列から単一のメールアドレスを解析します。
    *   解析が成功した後、`p.skipSpace()` を呼び出して、解析済みのメールアドレスの後に続く空白文字をスキップします。
    *   最後に、`p.empty()` をチェックします。`p.empty()` は、`addrParser` が処理すべき残りの文字列がまだ存在するかどうかを判断するメソッドです。もし `p.empty()` が `false` であれば、それは単一のアドレスの後にまだ解析されていない文字列が残っていることを意味します。この場合、`fmt.Errorf("mail: expected single address, got %q", p.s)` というエラーを返します。ここで `%q` は、残りの未解析文字列を表示し、エラーの原因を明確にします。

2.  **`ParseAddress` および `AddressParser.Parse` の変更**:
    *   `func ParseAddress(address string) (*Address, error)`: 以前は `return (&addrParser{s: address}).parseAddress()` を直接呼び出していましたが、変更後は `return (&addrParser{s: address}).parseSingleAddress()` を呼び出すようになりました。
    *   `func (p *AddressParser) Parse(address string) (*Address, error)`: 同様に、以前は `return (&addrParser{s: address, dec: p.WordDecoder}).parseAddress()` を直接呼び出していましたが、変更後は `return (&addrParser{s: address, dec: p.WordDecoder}).parseSingleAddress()` を呼び出すようになりました。

これらの変更により、`ParseAddress` と `AddressParser.Parse` は、内部で `parseSingleAddress` の厳密なチェックロジックを利用するようになり、単一アドレスの解析という契約を強制するようになりました。

3.  **テストケースの追加とリファクタリング**:
    `src/net/mail/message_test.go` には、この新しい挙動を検証するためのテストケースが追加されました。
    *   既存のエラーテスト (`TestAddressParsingError`, `TestAddressParsingErrorUnquotedNonASCII`) が、テーブル駆動テストの形式にリファクタリングされました。これにより、複数のエラーシナリオを簡潔に記述できるようになりました。
    *   特に重要なのは、`{"a@gmail.com b@gmail.com", "expected single address"}` という新しいテストケースが追加されたことです。このテストは、入力文字列に「`a@gmail.com b@gmail.com`」のように複数のアドレスが含まれている場合に、`ParseAddress` が「`expected single address`」というエラーメッセージを含むエラーを返すことを検証します。

## コアとなるコードの解説

### `src/net/mail/message.go` の変更点

1.  **`ParseAddress` 関数の委譲**:
    `ParseAddress` 関数は、以前は `addrParser` の `parseAddress` メソッドを直接呼び出していましたが、この変更により新しく追加された `parseSingleAddress` メソッドを呼び出すように変更されました。これにより、`ParseAddress` の呼び出しは、単一アドレスの厳密なチェックロジックを通過するようになります。

2.  **`AddressParser.Parse` 関数の委譲**:
    同様に、`AddressParser` 型の `Parse` メソッドも、`parseSingleAddress` メソッドを呼び出すように変更されました。`AddressParser` は、`WordDecoder` を使用してエンコードされた単語をデコードする機能を持つため、この変更は `AddressParser` を介した単一アドレス解析にも厳密なチェックを適用します。

3.  **`parseSingleAddress` メソッドの追加**:
    このメソッドは、このコミットの主要なロジックを実装しています。
    *   `addr, err := p.parseAddress()`: まず、既存の `parseAddress` メソッドを呼び出して、入力文字列の先頭から有効なメールアドレスを解析しようとします。
    *   `if err != nil { return nil, err }`: `parseAddress` がエラーを返した場合（例: 不正なフォーマットのアドレス）、そのエラーをそのまま呼び出し元に伝播します。
    *   `p.skipSpace()`: アドレスの解析が成功した後、残りの文字列の先頭にある空白文字をスキップします。これは、アドレスの後に続く可能性のあるスペースを無視するためです。
    *   `if !p.empty() { ... }`: ここが最も重要な部分です。`p.empty()` は、`addrParser` が処理すべき文字列が残っているかどうかをチェックします。もし `p.empty()` が `false` であれば、それは `parseAddress` が単一のアドレスを解析した後にも、まだ入力文字列に何らかのデータが残っていることを意味します。これは `ParseAddress` が単一のアドレスのみを期待しているという前提に反するため、エラーと判断されます。
    *   `return nil, fmt.Errorf("mail: expected single address, got %q", p.s)`: 複数のアドレスが検出された場合、具体的なエラーメッセージと共にエラーを返します。`%q` フォーマット指定子により、残りの未解析文字列がエラーメッセージに含まれるため、デバッグが容易になります。

### `src/net/mail/message_test.go` の変更点

1.  **テーブル駆動テストへのリファクタリング**:
    以前は個別のテスト関数として存在していた `TestAddressParsingError` と `TestAddressParsingErrorUnquotedNonASCII` が、`mustErrTestCases` という構造体のスライスを用いたテーブル駆動テストに統合されました。これにより、テストコードの重複が減り、新しいテストケースの追加が容易になります。

2.  **複数アドレスエラーのテストケース追加**:
    `mustErrTestCases` に `{"a@gmail.com b@gmail.com", "expected single address"}` という新しいテストケースが追加されました。このテストケースは、`ParseAddress` に複数のメールアドレスを含む文字列が渡されたときに、期待されるエラーメッセージ「`expected single address`」が返されることを検証します。これにより、このコミットで導入された新しいエラー挙動が正しく機能していることが保証されます。

これらの変更により、`net/mail.ParseAddress` は、その名前と意図に合致する、より厳密で予測可能な挙動を提供するようになりました。

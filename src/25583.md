# [インデックス 25583] ファイルの概要

このコミットは、Goリンカーにおける`filetab`スライスのサイズ計算に関するバグ修正です。具体的には、リンカーが`filetab`スライスに書き込むエントリの数が、実際には`Nhistfile`（ファイルシンボルの数）に加えて1つのオフセットを含むため、`Nhistfile + 1`であるべきところを`Nhistfile`として計算していた問題を修正しています。この修正により、特に共有ライブラリを使用する際に発生しやすかった、`filetab`スライスのサイズ不足による潜在的なランタイムエラーが解消されます。

## 元コミット内容

Goリンカー: `filetab`スライスのサイズを修正

リンカーは`filetab`スライスにファイルシンボルの数（`Nhistfile`）を書き込み、その後`Nhistfile`個のオフセットを書き込みます。これは、スライスが`Nhistfile`個のエントリだけでなく、`Nhistfile + 1`個のエントリを含むことを意味します。

このバグは少なくともGo 1.4から存在していたと思われますが、共有ライブラリと、関数が数個しかない小さなバイナリを使用すると、より簡単にトリガーされます。`go install -buildmode=shared std && go run -linkshared test/fixedbugs/issue4388.go`を試してみてください。

## 変更の背景

このコミットは、Goリンカーが生成するバイナリの内部データ構造である`moduledata`内の`filetab`スライスのサイズ計算に関する長年のバグを修正するために導入されました。

Goのランタイムは、実行中のプログラムに関する様々なメタデータを`moduledata`という構造体に格納しています。この`moduledata`には、スタックトレースの生成、デバッグ情報の提供、ガベージコレクションの補助などに不可欠な情報が含まれています。その中の一つに`pclntab`（Program Counter Line Table）があり、これはプログラムカウンタ（PC）とソースコードのファイル名および行番号をマッピングするためのテーブルです。`pclntab`はさらに、コンパイルされたソースファイルに関する情報を保持する`filetab`を参照します。

コミットメッセージによると、このバグはGo 1.4以降存在しており、特に共有ライブラリ（`-buildmode=shared`）を使用してビルドされたGoプログラムで顕在化しやすかったとされています。共有ライブラリは、複数のプログラムでコードを共有することでバイナリサイズを削減し、起動時間を短縮するなどの利点がありますが、その複雑さゆえにリンカーの内部処理に影響を与えることがあります。

問題の核心は、リンカーが`filetab`スライスを構築する際に、ファイルシンボルの数（`Nhistfile`）だけを考慮し、その後に続くオフセットの分（つまり、`Nhistfile`個のオフセット）を考慮していなかった点にあります。結果として、`filetab`スライスは必要な`Nhistfile + 1`個のエントリではなく、`Nhistfile`個のエントリしか確保されず、スライスがオーバーフローする可能性がありました。このようなサイズ不一致は、ランタイムが`filetab`にアクセスしようとした際に、不正なメモリ領域を読み込んだり、クラッシュを引き起こしたりする原因となります。

特に、関数が少ない小さなバイナリと共有ライブラリの組み合わせでこの問題が顕著になったのは、`filetab`のサイズが小さく、わずかなオフセットの追加でもすぐに容量を超過してしまったためと考えられます。この修正は、Goプログラムの安定性と、特に共有ライブラリを利用する際の信頼性を向上させるために重要でした。

## 前提知識の解説

このコミットを理解するためには、以下のGoの内部構造とリンカーの動作に関する知識が必要です。

1.  **Goのリンカー (`cmd/link`)**:
    Goのビルドプロセスにおいて、リンカーはコンパイルされたオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリまたはライブラリを生成する役割を担います。この過程で、リンカーはプログラムのコード、データ、およびランタイムが必要とする様々なメタデータ（例: `moduledata`, `pclntab`）を配置します。

2.  **`moduledata`構造体**:
    `moduledata`はGoランタイムの内部データ構造であり、ロードされたGoモジュールに関する包括的なメタデータを含んでいます。これには、モジュールのコードセクションとデータセクションへのポインタ、ガベージコレクタがポインタを識別するために必要な情報（`gcdatamask`, `gcbssmask`）、および`pclntab`などの他のランタイムテーブルへの参照が含まれます。Goランタイムは、現在アクティブなすべてのモジュールを追跡するために、`*moduledata`のスライスを管理しています。

3.  **`pclntab` (Program Counter Line Table)**:
    `pclntab`は、Goバイナリに埋め込まれた重要なメタデータテーブルです。その主な機能は、プログラムカウンタ（PC、実行命令のメモリアドレス）を対応するソースコードのファイル名と行番号にマッピングすることです。これは、パニック時の正確なスタックトレース生成、デバッグツールやプロファイリングツールが人間が読める形式で実行コンテキストを提供するために不可欠です。`pclntab`には、バイナリ内で定義されているすべての関数のエントリポイントと名前をリストする関数シンボルテーブルも含まれています。

4.  **`filetab`**:
    `filetab`は`pclntab`構造体と密接に関連するコンポーネントです。これは、Goバイナリにコンパイルされたソースファイルに関する情報を格納します。`pclntab`は、PCをソースコードの場所にマッピングする際に、この`filetab`を使用してファイル名を解決し、ファイルパスと行番号を含む詳細なスタックトレースを可能にします。Goリンカーのソースコードでは、`pclntab`構造体内に`filetab loader.Sym`フィールドと`nfiles uint32`フィールドがあり、`runtime.filetab`内のファイル名の数を追跡しています。

5.  **Goのスライス (slice)**:
    Goにおけるスライスは、基になる配列への動的なビューを提供する、サイズ変更可能なデータ構造です。内部的には、スライスは基になる配列へのポインタ、現在の長さ、および容量（再割り当てなしで保持できる最大要素数）の3つのフィールドを持つ構造体です。Goランタイムはスライスのメモリを管理し、スライスが現在の容量を超えて成長した場合に、より大きな基になる配列を割り当てて要素をコピーします。このコミットでは、`filetab`がGoのスライスとして扱われ、その長さと容量の計算が問題となっていました。

6.  **`Nhistfile`**:
    コミットメッセージから推測されるように、`Nhistfile`は「ファイルシンボルの数」を意味します。これは、リンカーが処理するソースファイルの履歴、またはデバッグ情報に関連するファイルの数を表す内部的なカウンタであると考えられます。`filetab`スライスには、これらのファイルシンボルに対応するオフセットが格納されるため、`Nhistfile`がその要素数を決定する上で重要な役割を果たします。

## 技術的詳細

このバグは、Goリンカーの`symtab.go`ファイル内の`symtab()`関数に存在していました。この関数は、Goバイナリのシンボルテーブルとランタイムメタデータ（`moduledata`を含む）を構築する責任を負っています。

問題の箇所は、`moduledata`構造体内に`filetab`スライスに関する情報を書き込む部分でした。`moduledata`は、`pclntab`のオフセット、`pclntab`内の関数の数、そして`filetab`スライスの情報など、様々なランタイムメタデータを格納します。

具体的には、リンカーは`filetab`スライスのサイズを`Ctxt.Nhistfile`（ファイルシンボルの数）として計算し、その値を`moduledata`に2回書き込んでいました。しかし、`filetab`スライスは、`Nhistfile`個のファイルシンボルに対応するオフセットに加えて、スライスの開始オフセットを示すための追加のエントリ（通常は最初の要素）を必要とします。したがって、`filetab`スライスの真のサイズは`Nhistfile + 1`であるべきでした。

このサイズ不一致により、リンカーが`filetab`スライスを構築する際に、必要なメモリよりも少ない領域しか確保されませんでした。結果として、ランタイムが`filetab`スライスにアクセスしようとした際に、確保された境界を超えて読み書きしようとし、メモリ破損やプログラムのクラッシュを引き起こす可能性がありました。

コミットメッセージで言及されているように、この問題は特に共有ライブラリを使用する場合に顕著でした。共有ライブラリは、通常の静的リンクされたバイナリとは異なるメモリレイアウトやシンボル解決のメカニズムを持つため、リンカーの内部処理におけるわずかな不正確さが、より深刻な問題として表面化しやすかったと考えられます。また、関数が少ない小さなバイナリでは、`Nhistfile`の値が小さいため、`Nhistfile`と`Nhistfile + 1`の差が相対的に大きく、スライスのサイズ不足がすぐに問題を引き起こす可能性がありました。

修正は非常にシンプルで、`adduint`関数を呼び出して`filetab`スライスのサイズを`moduledata`に書き込む際に、`Ctxt.Nhistfile`の代わりに`Ctxt.Nhistfile + 1`を使用するように変更されました。これにより、`filetab`スライスが常に正しいサイズで確保され、ランタイムが安全にアクセスできるようになります。

## コアとなるコードの変更箇所

変更は`src/cmd/link/internal/ld/symtab.go`ファイルにあります。

```diff
--- a/src/cmd/link/internal/ld/symtab.go
+++ b/src/cmd/link/internal/ld/symtab.go
@@ -498,8 +498,8 @@ func symtab() {
 	adduint(Ctxt, moduledata, uint64(pclntabNfunc+1))
 	// The filetab slice
 	Addaddrplus(Ctxt, moduledata, Linklookup(Ctxt, "runtime.pclntab", 0), int64(pclntabFiletabOffset))
-	adduint(Ctxt, moduledata, uint64(Ctxt.Nhistfile))
-	adduint(Ctxt, moduledata, uint64(Ctxt.Nhistfile))
+	adduint(Ctxt, moduledata, uint64(Ctxt.Nhistfile)+1)
+	adduint(Ctxt, moduledata, uint64(Ctxt.Nhistfile)+1)
 	// findfunctab
 	Addaddr(Ctxt, moduledata, Linklookup(Ctxt, "runtime.findfunctab", 0))
 	// minpc, maxpc
```

## コアとなるコードの解説

変更されたコードは、`symtab()`関数内で`moduledata`構造体に`filetab`スライスに関する情報を書き込む部分です。

*   `adduint(Ctxt, moduledata, uint64(Ctxt.Nhistfile))`
    この行は、`filetab`スライスのサイズとして`Ctxt.Nhistfile`の値を`moduledata`に書き込んでいました。この値は、ファイルシンボルの数を表します。

*   `adduint(Ctxt, moduledata, uint64(Ctxt.Nhistfile)+1)`
    修正後のこの行では、`Ctxt.Nhistfile`に`1`が加算されています。これは、`filetab`スライスが`Nhistfile`個のオフセットに加えて、スライスの開始を示すための追加のエントリを必要とするためです。この変更により、`filetab`スライスが常に正しいサイズで初期化されるようになり、ランタイムが安全にアクセスできるようになります。

`adduint`関数は、指定されたコンテキスト（`Ctxt`）とデータ構造（`moduledata`）に符号なし整数（`uint64`）を書き込むリンカーの内部ヘルパー関数です。この関数が2回呼び出されているのは、`filetab`スライスの長さと容量（または関連する2つの値）を`moduledata`に書き込むためと考えられます。どちらの呼び出しも同じ値で修正されていることから、両方の値が`Nhistfile + 1`であるべきだったことが示唆されます。

この修正は、Goのリンカーが生成するバイナリの内部構造の整合性を保ち、特に共有ライブラリを使用する際のランタイムの安定性を向上させる上で非常に重要です。

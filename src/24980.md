# [インデックス 24980] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) 変換フェーズにおける文字列インデックス処理のバグを修正するものです。具体的には、文字列の要素アクセス `s[i]` がSSA形式に変換される際に、誤ったコードが生成される可能性があった問題を解決しています。

## コミット

GoコンパイラのSSAバックエンドにおいて、文字列のインデックスアクセス `s[i]` の処理が修正されました。以前の実装では、文字列のインデックスアクセスが配列のインデックスアクセスと同様に `OpArrayIndex` オペレーションとして扱われていましたが、これは文字列の特性（バイト列としてのアクセス）を正確に反映していませんでした。このコミットにより、文字列のインデックスアクセスは、文字列のポインタとインデックスを計算し、そのアドレスからバイトをロードする一連のSSAオペレーションに置き換えられ、より正確かつ効率的なコード生成が可能になりました。また、境界チェックのロジックも文字列アクセスに合わせて調整されています。

## 変更の背景

Go言語において、文字列は不変なバイトのスライスとして扱われます。`s[i]` のようなインデックスアクセスは、文字列 `s` の `i` 番目のバイトを返します。Goコンパイラは、ソースコードを中間表現（IR）に変換し、最終的に機械語にコンパイルします。この中間表現の一つにSSA (Static Single Assignment) 形式があります。

以前のGoコンパイラのSSAバックエンドでは、文字列のインデックスアクセス `s[i]` を処理する際に、一般的な配列やスライスのインデックスアクセスと同じ `ssa.OpArrayIndex` オペレーションを使用していたと考えられます。しかし、文字列はバイトのスライスであるため、その要素アクセスは `uint8` 型の値をロードする操作として扱われるべきです。`OpArrayIndex` は通常、要素の型サイズを考慮してアドレスを計算しますが、文字列の場合は常に1バイト単位でのアクセスとなります。この不一致が、特に最適化の段階で問題を引き起こしたり、誤ったコードが生成されたりする可能性がありました。

このコミットの背景には、SSA形式での文字列インデックス処理の正確性を向上させ、より効率的でバグのないコード生成を実現するという目的があります。特に、境界チェックのロジックも文字列の長さに合わせて適切に適用されるように修正する必要がありました。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) 形式

SSA (Static Single Assignment) は、コンパイラ最適化において広く用いられる中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。Goコンパイラは、Go 1.7以降でSSAバックエンドを導入し、より高度な最適化と堅牢なコード生成を実現しています。

SSA形式への変換は、コンパイルパイプラインの重要なステップであり、抽象構文木（AST）からSSAグラフを構築し、そのグラフに対して様々な最適化（共通部分式除去、定数畳み込み、デッドコード除去など）を適用した後、最終的に機械語に変換されます。

### Goにおける文字列の内部表現とインデックスアクセス

Goの文字列は、内部的には読み取り専用のバイトスライスとして実装されています。具体的には、ポインタと長さのペアで構成されます。

```go
type StringHeader struct {
    Data uintptr // 文字列データの先頭へのポインタ
    Len  int     // 文字列の長さ（バイト数）
}
```

`s[i]` のようなインデックスアクセスは、文字列 `s` の `i` 番目のバイト（`byte` 型、つまり `uint8`）を返します。この操作は、文字列のデータポインタにインデックス `i` を加算したアドレスから1バイトを読み出すことに相当します。インデックス `i` が文字列の長さ `Len` 以上である場合、ランタイムパニックが発生します。

### 境界チェック (Bounds Check)

配列、スライス、および文字列へのインデックスアクセスを行う際には、インデックスが有効な範囲内にあるかを確認する「境界チェック」が必要です。Goランタイムは、不正なメモリアクセスを防ぐために、このチェックを自動的に行います。インデックスが範囲外の場合、`panic: runtime error: index out of range` が発生します。

コンパイラは、可能な限り境界チェックを省略（elimination）しようとします。例えば、ループ内でインデックスが常に有効な範囲内であることが静的に証明できる場合、そのループ内の境界チェックはコンパイル時に削除され、実行時のオーバーヘッドが削減されます。

## 技術的詳細

このコミットの技術的詳細は、GoコンパイラのSSAバックエンドが文字列のインデックスアクセス `s[i]` をどのように処理するかを変更した点にあります。

以前の実装では、`ssa.OpArrayIndex` オペレーションが文字列と配列/スライスの両方に使用されていました。`OpArrayIndex` は、ベースアドレスとインデックスを受け取り、要素のサイズを考慮してオフセットを計算し、そのアドレスを生成します。しかし、文字列の要素は常に1バイト（`uint8`）であるため、要素サイズを考慮した計算は不要であり、むしろ `OpArrayIndex` のセマンティクスとは少し異なります。

新しい実装では、文字列のインデックスアクセスに対して以下のSSAオペレーションのシーケンスを生成するように変更されました。

1.  **`ssa.OpStringLen`**: 文字列 `a` の長さを取得します。これは境界チェックのために使用されます。
2.  **`s.boundsCheck(i, len)`**: インデックス `i` が文字列の長さ `len` の範囲内にあるかをチェックします。`n.Bounded` が `true` の場合（コンパイラが既に境界チェックが不要と判断した場合）、このチェックはスキップされます。
3.  **`ssa.OpStringPtr`**: 文字列 `a` のデータポインタ（`uint8` へのポインタ）を取得します。
4.  **`ssa.OpAddPtr`**: `OpStringPtr` で得られたポインタにインデックス `i` を加算し、目的のバイトのアドレスを計算します。この際、ポインタの型は `Ptrto(Types[TUINT8])` となり、1バイト単位での加算が保証されます。
5.  **`ssa.OpLoad`**: `OpAddPtr` で計算されたアドレスから1バイト（`Types[TUINT8]`）をロードします。

この変更により、文字列のインデックスアクセスが、その内部表現とセマンティクスに合致したSSAオペレーションのシーケンスとして表現されるようになりました。これにより、コンパイラは文字列アクセスに対してより正確な最適化を適用できるようになり、潜在的なバグが修正され、生成される機械語コードの品質が向上します。

一方、配列やスライスのインデックスアクセスについては、引き続き `ssa.OpArrayIndex` が使用されます。これは、配列やスライスでは要素の型サイズが1バイトとは限らず、`OpArrayIndex` がその型サイズを考慮したアドレス計算を行うため、適切なオペレーションであるためです。

## コアとなるコードの解説

変更の中心は、`ssa.go` 内の `OINDEX` (インデックスアクセス) を処理する部分です。

**変更前:**

文字列 (`n.Left.Type.IsString()`) とそれ以外の型（配列など）で、`elemtype` と `len` の取得方法が異なっていましたが、最終的にはどちらも `s.newValue2(ssa.OpArrayIndex, elemtype, a, i)` を呼び出していました。

*   文字列の場合:
    *   `len = s.newValue1(ssa.OpStringLen, Types[TINT], a)` で文字列の長さを取得。
    *   `elemtype = Types[TUINT8]` で要素型を `uint8` に設定。
    *   `s.boundsCheck(i, len)` で境界チェック。
    *   `s.newValue2(ssa.OpArrayIndex, elemtype, a, i)` で `OpArrayIndex` を生成。

このアプローチの問題点は、`OpArrayIndex` が汎用的なインデックスアクセスオペレーションであり、要素の型サイズを考慮してアドレスを計算する点です。文字列の要素は常に1バイトであるにもかかわらず、`OpArrayIndex` を使用すると、そのセマンティクスが曖昧になり、コンパイラの最適化器が文字列アクセスの特性を十分に活用できない可能性がありました。

**変更後:**

文字列 (`n.Left.Type.IsString()`) の場合と、それ以外の型の場合で、SSAオペレーションの生成パスが完全に分離されました。

1.  **文字列の場合 (`n.Left.Type.IsString()` が `true` の場合):**
    *   `if !n.Bounded { ... }`: コンパイラがインデックスが既に境界内にあると判断していない場合のみ、境界チェックを生成します。
        *   `len := s.newValue1(ssa.OpStringLen, Types[TINT], a)`: 文字列 `a` の長さを取得する `OpStringLen` オペレーションを生成します。
        *   `s.boundsCheck(i, len)`: 取得した長さ `len` を使って、インデックス `i` の境界チェックを生成します。
    *   `ptrtyp := Ptrto(Types[TUINT8])`: `uint8` へのポインタ型を定義します。これは文字列の要素型です。
    *   `ptr := s.newValue1(ssa.OpStringPtr, ptrtyp, a)`: 文字列 `a` の内部データへのポインタを取得する `OpStringPtr` オペレーションを生成します。このポインタは `uint8` 型の要素を指します。
    *   `ptr = s.newValue2(ssa.OpAddPtr, ptrtyp, ptr, i)`: `OpStringPtr` で得られたポインタ `ptr` にインデックス `i` を加算し、目的のバイトのアドレスを計算する `OpAddPtr` オペレーションを生成します。`ptrtyp` を指定することで、ポインタ演算が1バイト単位で行われることを保証します。
    *   `return s.newValue2(ssa.OpLoad, Types[TUINT8], ptr, s.mem())`: 計算されたアドレス `ptr` から1バイト（`Types[TUINT8]`）をロードする `OpLoad` オペレーションを生成し、その結果を返します。

    このシーケンスは、Goの文字列インデックスアクセスのセマンティクス（文字列のデータポインタにインデックスをオフセットとして加算し、そのアドレスからバイトを読み出す）をSSA形式で正確に表現しています。

2.  **それ以外の型（配列やスライス）の場合 (`else` ブロック):**
    *   `if !n.Bounded { ... }`: こちらも同様に、コンパイラが境界チェックが不要と判断していない場合のみ、境界チェックを生成します。
        *   `len := s.constInt(Types[TINT], n.Left.Type.Bound)`: 配列の固定長やスライスの容量など、左辺の型から長さを取得します。
        *   `s.boundsCheck(i, len)`: 取得した長さ `len` を使って、インデックス `i` の境界チェックを生成します。
    *   `return s.newValue2(ssa.OpArrayIndex, n.Left.Type.Type, a, i)`: 汎用的な `OpArrayIndex` オペレーションを生成します。この場合、`n.Left.Type.Type` が要素の型となり、`OpArrayIndex` はその型サイズを考慮してアドレスを計算します。

この変更により、文字列のインデックスアクセスは、より低レベルで具体的なSSAオペレーションの組み合わせとして表現されるようになり、コンパイラが文字列の特性をより深く理解し、より適切な最適化を適用できるようになりました。これにより、生成されるコードの正確性と効率が向上します。

テストファイル `string_ssa.go` に追加された `testStringElem_ssa` と `testStringElemConst_ssa` 関数は、この修正が正しく機能することを確認するためのものです。これらは、文字列のインデックスアクセスが様々なケース（変数、定数文字列）で期待通りのバイト値を返すことを検証します。

## 変更の背景

Goランタイムの`internal/atomic`パッケージは、マルチコア環境での並行処理において、メモリの一貫性を保証するためのアトミック操作を提供します。これらの操作は、コンパイラの最適化によってメモリアクセス順序が変更されると、データ競合や予期せぬ動作を引き起こす可能性があるため、非常に慎重に扱われる必要があります。

以前のGoのバージョンでは、特定のアトミック関数がコンパイラによってインライン化されるのを防ぐために、`nop()`というダミーのアセンブリ命令呼び出しが使用されていました。インライン化とは、関数呼び出しのオーバーヘッドを削減するために、コンパイラが関数本体を呼び出し箇所に直接展開する最適化手法です。通常はパフォーマンス向上に寄与しますが、アトミック操作のようなメモリ順序に厳密な保証が必要なコードでは、インライン化によってコンパイラがメモリバリアや順序付けに関する仮定を破る可能性がありました。`nop()`呼び出しは、コンパイラがその関数をインライン化しないようにするための「ハック」として機能していました。これは、コンパイラが`nop()`呼び出しのセマンティクスを完全に理解せず、インライン化の判断を複雑にするためです。

しかし、この`nop()`によるインライン化抑制は、意図が不明瞭であり、将来のコンパイラの進化によってはその効果が保証されない可能性がありました。より明確で、コンパイラに直接意図を伝える方法が求められていました。

このコミットは、Go 1.6のリリースに向けて、この非推奨の`nop()`ハックを、Goコンパイラが公式にサポートする`//go:noinline`ディレクティブに置き換えることで、この問題を解決します。これにより、コードの意図が明確になり、将来にわたってインライン化抑制が保証されるようになります。

## 前提知識の解説

### Goランタイム

Goランタイムは、Goプログラムの実行を管理するシステムです。ガベージコレクション、ゴルーチン（軽量スレッド）のスケジューリング、チャネルによる通信、メモリ管理など、Go言語の並行処理モデルとメモリ安全性を支える重要なコンポーネントです。アトミック操作は、このランタイムの低レベルな部分で、並行処理のプリミティブを実装するために不可欠です。

### アトミック操作

アトミック操作とは、複数のCPUコアやスレッドから同時にアクセスされた場合でも、その操作全体が不可分（atomic）であることを保証する操作です。つまり、操作の途中で他の操作が割り込むことがなく、常に一貫性のある結果が得られます。Go言語では、`sync/atomic`パッケージを通じてユーザーレベルのアトミック操作が提供されますが、ランタイム内部ではより低レベルなアトミックプリミティブが使用されます。これらは通常、CPUの特定の命令（例: `XADD`, `CMPXCHG`）を利用して実装されます。

### メモリ順序付け (Memory Ordering)

現代のCPUは、パフォーマンス向上のために命令の実行順序を入れ替えたり（アウトオブオーダー実行）、メモリへの書き込みをバッファリングしたりします。これは通常問題ありませんが、複数のCPUコアが共有メモリにアクセスする並行プログラムでは、予期せぬ結果を引き起こす可能性があります。メモリ順序付けは、これらの最適化によってメモリ操作の可視性がどのように変化するかを定義する概念です。アトミック操作は、特定のメモリバリア（memory barrier）やフェンス（fence）命令を暗黙的に含み、コンパイラやCPUがメモリ操作の順序を勝手に変更しないように保証します。

### コンパイラのインライン化 (Compiler Inlining)

インライン化は、関数呼び出しのオーバーヘッド（スタックフレームの作成、レジスタの保存/復元など）を削減するために、コンパイラが呼び出される関数のコードを呼び出し元に直接コピーする最適化手法です。これにより、プログラムの実行速度が向上することが期待されます。しかし、アトミック操作のように厳密なメモリ順序付けが必要な関数がインライン化されると、コンパイラがその関数の内部構造を「見て」、メモリバリアの意図を誤解したり、最適化によって重要な順序保証を破ったりするリスクがあります。

### `//go:noinline` ディレクティブ

`//go:noinline`は、Goコンパイラに対するディレクティブ（指示子）の一つです。このディレクティブが関数宣言の直前に記述されている場合、コンパイラはその関数をインライン化しないように指示されます。これにより、開発者は特定の関数がインライン化されることによる潜在的な問題を回避し、メモリ順序付けなどの低レベルな保証を維持することができます。

### `//go:nosplit` ディレクティブ

`//go:nosplit`もGoコンパイラディレクティブの一つで、関数がスタックを分割しないことを保証します。Goのゴルーチンは小さなスタックで開始し、必要に応じてスタックを拡張（分割）しますが、ランタイムの非常に低レベルな部分では、スタック分割が許されない場合があります（例: スケジューラがロックを保持している間など）。アトミック操作はしばしばこのような制約の下で実行されるため、`//go:nosplit`が併用されることがあります。

## 技術的詳細

このコミットの核心は、Goランタイムのアトミック操作を実装する`runtime/internal/atomic`パッケージにおけるインライン化抑制のメカニズムの変更です。

以前は、`Load`, `Loadp`, `Load64`といったアトミックな読み込み操作を行う関数内で、`nop()`という関数が呼び出されていました。この`nop()`関数は、`src/runtime/internal/atomic/stubs.go`で宣言されており、その実体はアセンブリコードで単なる`NOP`（No Operation）命令を実行するものでした。この`nop()`呼び出しの目的は、コンパイラがこれらのアトミック関数をインライン化するのを防ぐことでした。コンパイラは、関数呼び出しが存在すると、その関数をインライン化するかどうかを判断する際に、より慎重になる傾向があります。特に、`nop()`のような外部（アセンブリ）関数への呼び出しは、コンパイラがその内部動作を完全に解析できないため、インライン化を避ける強力なシグナルとして機能していました。

しかし、この方法は間接的であり、コンパイラの最適化ロジックの変更によって、将来的にその効果が失われる可能性がありました。また、コードを読んだ際に`nop()`呼び出しの真の意図（インライン化抑制）がすぐに理解しにくいという問題もありました。

このコミットでは、この間接的な方法を廃止し、Goコンパイラが提供する公式のディレクティブである`//go:noinline`を使用するように変更しました。`//go:noinline`ディレクティブは、コンパイラに対して「この関数はインライン化してはならない」という明確な指示を与えます。これにより、以下の利点が得られます。

1.  **意図の明確化**: コードを読んだ人が、なぜこの関数がインライン化されないのかをすぐに理解できます。
2.  **堅牢性の向上**: コンパイラの内部実装に依存する「ハック」ではなく、公式のディレクティブを使用することで、将来のコンパイラのバージョンアップに対してもインライン化抑制の保証がより堅牢になります。
3.  **コードのクリーンアップ**: 不要な`nop()`関数とその宣言を削除できるため、コードベースがシンプルになります。

この変更は、特に`atomic_386.go`（32ビットx86アーキテクチャ向け）と`atomic_amd64x.go`（64ビットx86アーキテクチャ向け）のファイルに影響を与えています。これらのファイルは、それぞれのアーキテクチャに特化したアトミック操作の実装を含んでいます。

## コアとなるコードの変更箇所

変更は主に以下の3つのファイルで行われています。

1.  `src/runtime/internal/atomic/atomic_386.go`
2.  `src/runtime/internal/atomic/atomic_amd64x.go`
3.  `src/runtime/internal/atomic/stubs.go`

### `src/runtime/internal/atomic/atomic_386.go` および `src/runtime/internal/atomic/atomic_amd64x.go`

これらのファイルでは、`Load`、`Loadp`、`Load64`（`amd64x`のみ）といったアトミックな読み込み関数から、`nop()`の呼び出しが削除され、代わりに`//go:noinline`ディレクティブが追加されています。

**変更前:**

```go
// The calls to nop are to keep these functions from being inlined.
// If they are inlined we have no guarantee that later rewrites of the
// code by optimizers will preserve the relative order of memory accesses.

//go:nosplit
func Load(ptr *uint32) uint32 {
	nop() // この行が削除される
	return *ptr
}
```

**変更後:**

```go
//go:nosplit
//go:noinline // この行が追加される
func Load(ptr *uint32) uint32 {
	return *ptr
}
```

同様の変更が`Loadp`関数、および`atomic_amd64x.go`の`Load64`関数にも適用されています。

### `src/runtime/internal/atomic/stubs.go`

このファイルからは、`nop()`関数の宣言が完全に削除されています。

**変更前:**

```go
func Casp1(ptr *unsafe.Pointer, old, new unsafe.Pointer) bool

func nop() // call to prevent inlining of function body // この行が削除される

//go:noescape
func Casuintptr(ptr *uintptr, old, new uintptr) bool
```

**変更後:**

```go
func Casp1(ptr *unsafe.Pointer, old, new unsafe.Pointer) bool

//go:noescape
func Casuintptr(ptr *uintptr, old, new uintptr) bool
```

## コアとなるコードの解説

このコミットによるコードの変更は、Goランタイムのアトミック操作の信頼性と保守性を向上させる上で重要です。

`Load`, `Loadp`, `Load64`のようなアトミックな読み込み関数は、共有メモリ上の値を安全に読み取るために使用されます。これらの関数がインライン化されると、コンパイラは関数呼び出しの境界を越えて最適化を行うことが可能になります。特に、メモリ操作の順序に関する保証が重要なアトミック操作においては、コンパイラがメモリバリアを移動させたり、読み込み操作の順序を入れ替えたりする可能性があり、これがデータ競合や不正確な結果につながる恐れがあります。

`nop()`呼び出しを削除し、`//go:noinline`ディレクティブを追加することで、コンパイラはこれらの関数をインライン化しないことが保証されます。これにより、これらのアトミック関数が常に独立した関数呼び出しとして扱われ、その内部で実装されているメモリ順序付けの保証がコンパイラの最適化によって損なわれることがなくなります。

`stubs.go`から`nop()`関数の宣言が削除されたことは、この「ハック」が完全に廃止され、コードベースからその痕跡が消えたことを意味します。これは、Goコンパイラが`//go:noinline`というより洗練されたメカニズムを提供できるようになったことの証でもあります。

この変更は、Goの並行処理モデルの基盤を支えるアトミック操作の堅牢性を高め、Goプログラムがマルチコア環境でより予測可能かつ安全に動作することを保証します。

## 技術的詳細

このコミットの核心は、Goランタイムのアトミック操作を実装する`runtime/internal/atomic`パッケージにおけるインライン化抑制のメカニズムの変更です。

以前は、`Load`, `Loadp`, `Load64`といったアトミックな読み込み操作を行う関数内で、`nop()`という関数が呼び出されていました。この`nop()`関数は、`src/runtime/internal/atomic/stubs.go`で宣言されており、その実体はアセンブリコードで単なる`NOP`（No Operation）命令を実行するものでした。この`nop()`呼び出しの目的は、コンパイラがこれらのアトミック関数をインライン化するのを防ぐことでした。コンパイラは、関数呼び出しが存在すると、その関数をインライン化するかどうかを判断する際に、より慎重になる傾向があります。特に、`nop()`のような外部（アセンブリ）関数への呼び出しは、コンパイラがその内部動作を完全に解析できないため、インライン化を避ける強力なシグナルとして機能していました。

しかし、この方法は間接的であり、コンパイラの最適化ロジックの変更によって、将来的にその効果が失われる可能性がありました。また、コードを読んだ際に`nop()`呼び出しの真の意図（インライン化抑制）がすぐに理解しにくいという問題もありました。

このコミットでは、この間接的な方法を廃止し、Goコンパイラが提供する公式のディレクティブである`//go:noinline`を使用するように変更しました。`//go:noinline`ディレクティブは、コンパイラに対して「この関数はインライン化してはならない」という明確な指示を与えます。これにより、以下の利点が得られます。

1.  **意図の明確化**: コードを読んだ人が、なぜこの関数がインライン化されないのかをすぐに理解できます。
2.  **堅牢性の向上**: コンパイラの内部実装に依存する「ハック」ではなく、公式のディレクティブを使用することで、将来のコンパイラのバージョンアップに対してもインライン化抑制の保証がより堅牢になります。
3.  **コードのクリーンアップ**: 不要な`nop()`関数とその宣言を削除できるため、コードベースがシンプルになります。

この変更は、特に`atomic_386.go`（32ビットx86アーキテクチャ向け）と`atomic_amd64x.go`（64ビットx86アーキテクチャ向け）のファイルに影響を与えています。これらのファイルは、それぞれのアーキテクチャに特化したアトミック操作の実装を含んでいます。

## コアとなるコードの変更箇所

変更は主に以下の3つのファイルで行われています。

1.  `src/runtime/internal/atomic/atomic_386.go`
2.  `src/runtime/internal/atomic/atomic_amd64x.go`
3.  `src/runtime/internal/atomic/stubs.go`

### `src/runtime/internal/atomic/atomic_386.go` および `src/runtime/internal/atomic/atomic_amd64x.go`

これらのファイルでは、`Load`、`Loadp`、`Load64`（`amd64x`のみ）といったアトミックな読み込み関数から、`nop()`の呼び出しが削除され、代わりに`//go:noinline`ディレクティブが追加されています。

**変更前:**

```go
// The calls to nop are to keep these functions from being inlined.
// If they are inlined we have no guarantee that later rewrites of the
// code by optimizers will preserve the relative order of memory accesses.

//go:nosplit
func Load(ptr *uint32) uint32 {
	nop() // この行が削除される
	return *ptr
}
```

**変更後:**

```go
//go:nosplit
//go:noinline // この行が追加される
func Load(ptr *uint32) uint32 {
	return *ptr
}
```

同様の変更が`Loadp`関数、および`atomic_amd64x.go`の`Load64`関数にも適用されています。

### `src/runtime/internal/atomic/stubs.go`

このファイルからは、`nop()`関数の宣言が完全に削除されています。

**変更前:**

```go
func Casp1(ptr *unsafe.Pointer, old, new unsafe.Pointer) bool

func nop() // call to prevent inlining of function body // この行が削除される

//go:noescape
func Casuintptr(ptr *uintptr, old, new uintptr) bool
```

**変更後:**

```go
func Casp1(ptr *unsafe.Pointer, old, new unsafe.Pointer) bool

//go:noescape
func Casuintptr(ptr *uintptr, old, new uintptr) bool
```

## コアとなるコードの解説

このコミットによるコードの変更は、Goランタイムのアトミック操作の信頼性と保守性を向上させる上で重要です。

`Load`, `Loadp`, `Load64`のようなアトミックな読み込み関数は、共有メモリ上の値を安全に読み取るために使用されます。これらの関数がインライン化されると、コンパイラは関数呼び出しの境界を越えて最適化を行うことが可能になります。特に、メモリ操作の順序に関する保証が重要なアトミック操作においては、コンパイラがメモリバリアを移動させたり、読み込み操作の順序を入れ替えたりする可能性があり、これがデータ競合や不正確な結果につながる恐れがあります。

`nop()`呼び出しを削除し、`//go:noinline`ディレクティブを追加することで、コンパイラはこれらの関数をインライン化しないことが保証されます。これにより、これらのアトミック関数が常に独立した関数呼び出しとして扱われ、その内部で実装されているメモリ順序付けの保証がコンパイラの最適化によって損なわれることがなくなります。

`stubs.go`から`nop()`関数の宣言が削除されたことは、この「ハック」が完全に廃止され、コードベースからその痕跡が消えたことを意味します。これは、Goコンパイラが`//go:noinline`というより洗練されたメカニズムを提供できるようになったことの証でもあります。

この変更は、Goの並行処理モデルの基盤を支えるアトミック操作の堅牢性を高め、Goプログラムがマルチコア環境でより予測可能かつ安全に動作することを保証します。

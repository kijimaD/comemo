# [インデックス 27188] ファイルの概要

このコミットは、Go言語のコンパイラ (`cmd/compile`) とリンカ (`cmd/link`)、およびリフレクションパッケージ (`reflect`、`runtime`) における、メソッドの型情報管理の最適化に関するものです。具体的には、`reflect.Method` 構造体内で保持されていた、レシーバを含むメソッドの型情報 (`typ` フィールド) をコンパイル時に生成するのではなく、実行時に `reflect.FuncOf` を用いて動的に構築するように変更しています。これにより、バイナリサイズの大幅な削減を実現しています。

## 変更の背景

Go言語のメソッドは、その型情報において2つのバリアントを持ちます。一つはレシーバを含まない関数型（`func(args...) returns...`）、もう一つはレシーバを最初の引数として含む関数型（`func(receiverType, args...) returns...`）です。

これまでの実装では、これら両方の型情報がコンパイル時に生成され、`reflect.Method` 構造体内に格納されていました。しかし、コミットメッセージによると、レシーバを含まない関数型は動的なインターフェースチェックの一部として利用される一方で、レシーバを含む関数型は `reflect.Method` 構造体の `Type` フィールドとして返されるのみで、他の場所では直接利用されていませんでした。

この冗長な型情報をコンパイル時に生成し、バイナリに含めることは、特に多数のメソッドを持つ型が存在する場合に、不必要なバイナリサイズの増大を招いていました。このコミットは、この冗長性を排除し、バイナリサイズを削減することを目的としています。特に、`cmd/go` で480KB (4.4%)、`jujud` で5.6MB (7.8%) という大幅なサイズ削減が報告されており、その効果は顕著です。

この変更は、GoのIssue #6853に関連しています。

## 前提知識の解説

### Go言語のリフレクション (`reflect` パッケージ)

Go言語の `reflect` パッケージは、実行時にプログラムの構造を検査・操作するための機能を提供します。これにより、型情報、フィールド、メソッドなどを動的に取得・操作することが可能になります。

*   **`reflect.Type`**: Goの型を表すインターフェースです。`reflect.TypeOf(v)` で任意の変数の `reflect.Type` を取得できます。
*   **`reflect.Value`**: Goの値を表す構造体です。`reflect.ValueOf(v)` で任意の変数の `reflect.Value` を取得できます。
*   **`reflect.Method` 構造体**: 特定の型に紐付けられたメソッドの情報を保持する構造体です。メソッド名、パッケージパス、型情報、関数ポインタなどが含まれます。
    *   変更前は、この構造体内に `mtyp` (レシーバなしのメソッド型) と `typ` (レシーバありのメソッド型) の両方が格納されていました。
*   **`reflect.FuncOf` 関数**: 実行時に動的に関数型 (`reflect.Type`) を構築するための関数です。引数として入力パラメータの型スライス、出力パラメータの型スライス、および可変長引数であるかどうかのフラグを受け取ります。

    ```go
    func FuncOf(in, out []Type, variadic bool) Type
    ```

    この関数は、コンパイル時には未知の関数シグネチャを持つ型を、実行時に定義する必要がある場合に非常に有用です。

### Go言語のコンパイラ (`cmd/compile`) とリンカ (`cmd/link`)

*   **`cmd/compile`**: Goのソースコードをオブジェクトファイルにコンパイルするツールです。型情報やメソッド情報などもこの段階で中間表現として生成されます。
*   **`cmd/link`**: コンパイラによって生成されたオブジェクトファイルを結合し、実行可能なバイナリを生成するツールです。この過程で、リフレクションに必要な型情報などもバイナリに埋め込まれます。

### メソッドの型バリアント

Goのメソッド `func (recv T) MyMethod(args...) returns...` は、リフレクションの文脈で2つの異なる型として扱われることがあります。

1.  **レシーバを含まない関数型 (`mtyp`)**: `func(args...) returns...` の形式。これは主にインターフェースの動的ディスパッチ（メソッドセットの比較など）で使用されます。
2.  **レシーバを最初の引数とする関数型 (`typ`)**: `func(recv T, args...) returns...` の形式。これは `reflect.Method.Type` フィールドとして公開され、メソッドを `reflect.Value` として呼び出す際に、レシーバを通常の引数として渡すために使用されます。

このコミットのポイントは、2番目の型が `reflect.Method` 以外で直接利用されることが少ないため、コンパイル時に静的に生成してバイナリに含めるのは非効率である、という洞察に基づいています。

## 技術的詳細

このコミットの核となる技術的変更は、`reflect.Method` 構造体からレシーバを含むメソッドの型情報 (`typ` フィールド) を削除し、その情報を必要とする `reflect.Type.Method` メソッド内で、`reflect.FuncOf` を使用して動的に再構築する点にあります。

1.  **`reflect.method` 構造体の簡素化**:
    *   `src/reflect/type.go` および `src/runtime/type.go` にある内部的な `method` 構造体から `typ *rtype` フィールドが削除されました。これにより、各メソッドエントリが占めるメモリ量がポインタ1つ分削減されます。
2.  **コンパイラとリンカの変更**:
    *   `src/cmd/compile/internal/gc/reflect.go` では、コンパイル時に `typ` フィールドに対応する型情報を生成・出力する処理が削除されました。
    *   `src/cmd/link/internal/ld/deadcode.go` では、`methodref` 構造体内のリロケーションの数が4つから3つに減らされ、`typ` フィールドに関連するリロケーションの処理が削除されました。また、`markMethodType` 関数も削除され、`mtyp` のみをマークするように変更されました。
    *   `src/cmd/link/internal/ld/decodesym.go` では、`sizeofMethod` の計算が `6 * Thearch.Ptrsize` から `5 * Thearch.Ptrsize` に変更され、`reflect.method` 構造体のサイズが小さくなったことを反映しています。
3.  **`reflect.Type.Method` での動的生成**:
    *   `src/reflect/type.go` の `(t *rtype) Method(i int)` 関数が変更されました。この関数は、`reflect.Method` 構造体を構築して返しますが、その際に `m.Type` フィールド（レシーバを含むメソッドの型）を動的に生成します。
    *   具体的には、まず `p.mtyp` (レシーバを含まないメソッド型) から入力引数と出力引数を取得します。
    *   次に、入力引数のスライスにレシーバの型 (`t`) を先頭に追加します。
    *   最後に、これらの引数と出力引数、および可変長引数フラグを `reflect.FuncOf` に渡して、レシーバを含む新しい関数型を生成し、それを `m.Type` に設定します。

このアプローチにより、バイナリにはレシーバを含まないメソッド型 (`mtyp`) のみが静的に格納され、レシーバを含むメソッド型 (`typ`) は必要になった場合にのみ実行時に生成されるため、バイナリサイズが削減されます。リフレクションによるメソッド情報の取得は比較的稀な操作であるため、この動的な生成によるオーバーヘッドは全体的なパフォーマンスに大きな影響を与えないと判断されたと考えられます。

## コアとなるコードの解説

### `reflect.method` 構造体からの `typ` フィールドの削除

`src/reflect/type.go` と `src/runtime/type.go` の両方で、`method` 構造体から `typ *rtype` フィールドが削除されています。これは、レシーバを含むメソッドの型情報を静的に保持する必要がなくなったことを直接的に示しています。この変更により、Goバイナリ内の各メソッドエントリのサイズが削減され、結果として全体のバイナリサイズが小さくなります。

### `(t *rtype) Method(i int)` 関数の変更

この関数は、特定の型 `t` の `i` 番目のメソッドに関する `reflect.Method` 構造体を返します。変更の核心は、`m.Type` フィールドの値を設定する方法にあります。

変更前は、`p.typ` という既存のフィールドから直接 `mt` (メソッド型) を取得していました。これは、コンパイル時に既にレシーバを含むメソッド型が生成され、`method` 構造体に格納されていたことを意味します。

変更後は、以下の手順で `m.Type` が動的に生成されます。

1.  `ft := (*funcType)(unsafe.Pointer(p.mtyp))`
    *   `p.mtyp` はレシーバを含まないメソッドの型情報です。これを `funcType` にキャストして、その入力引数と出力引数を取得できるようにします。
2.  `in := make([]Type, 0, 1+len(ft.in()))`
    *   新しい入力引数スライス `in` を作成します。容量は、元の入力引数にレシーバの型を追加する分を考慮して `1 + len(ft.in())` とします。
3.  `in = append(in, t)`
    *   レシーバの型 `t` を `in` スライスの先頭に追加します。これにより、レシーバが最初の引数として扱われるようになります。
4.  `for _, arg := range ft.in() { in = append(in, arg) }`
    *   元のメソッドの入力引数を `in` スライスに追加します。
5.  `out := make([]Type, 0, len(ft.out()))`
    *   出力引数スライス `out` を作成し、元のメソッドの出力引数をコピーします。
6.  `mt := FuncOf(in, out, p.mtyp.IsVariadic())`
    *   `reflect.FuncOf` を呼び出し、新しく構築した入力引数スライス `in`、出力引数スライス `out`、および元のメソッドの可変長引数フラグ (`p.mtyp.IsVariadic()`) を渡して、レシーバを含む新しい関数型 `mt` を動的に生成します。
7.  `m.Type = mt`
    *   生成された `mt` を `reflect.Method` 構造体の `Type` フィールドに設定します。

この動的な生成により、コンパイル時に不要な型情報をバイナリに含める必要がなくなり、バイナリサイズの削減に貢献します。リフレクションによるメソッド情報の取得は、Goプログラムの実行パスにおいて頻繁に発生する操作ではないため、この実行時生成によるパフォーマンスオーバーヘッドは許容範囲内と判断されたと考えられます。

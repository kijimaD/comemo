# [インデックス 21094] ファイルの概要

このコミットは、GoコンパイラのPowerPC 64-bitアーキテクチャ向けバックエンドである`9g`に、レジスタ最適化（`regopt`）のサポートを追加するものです。変更は主に以下の2つのファイルにわたります。

- `src/cmd/9g/opt.h`: レジスタ最適化に関連するデータ構造（`Reg`、`Rgn`、`ProgInfo`）と関数プロトタイプが定義されています。これらの構造体は、プログラムの命令、レジスタの使用状況、レジスタ割り当ての領域を追跡するために使用されます。
- `src/cmd/9g/reg.c`: `regopt`関数の主要な実装と、レジスタ割り当てプロセスをサポートする多数のヘルパー関数が含まれています。このファイルには、レジスタ割り当てロジックの追加に伴う大幅なコードの追加が見られます。

## コミット

このコミットは、`9g`コンパイラにレジスタ化（registerization）のサポートを実装します。これは、他のGoコンパイラが既に持っている機能と同等のもので、変数を効率的にCPUレジスタに割り当てることで、メモリアクセスを最小限に抑え、プログラムの実行性能を向上させることを目的としています。

## 変更の背景

コンパイラにおけるレジスタ最適化は、生成される機械語コードの性能を決定する上で非常に重要なステップです。CPUのレジスタはメモリよりもはるかに高速にアクセスできるため、頻繁に使用される変数をレジスタに割り当てることで、プログラムの実行速度を大幅に向上させることができます。

このコミットが導入される以前の`9g`（PowerPC 64-bit向けGoコンパイラ）は、他のアーキテクチャ向けのGoコンパイラが既に持っていたレジスタ最適化の機能が不足していました。この機能の欠如は、PowerPC 64-bitアーキテクチャ上で実行されるGoプログラムの性能に影響を与えていた可能性があります。

したがって、この変更の背景には、`9g`コンパイラの性能を向上させ、他のGoコンパイラとの機能的な均一性を図るという目的があります。これにより、PowerPC 64-bit環境でのGoプログラムの実行効率が改善され、より広範なGoエコシステムとの互換性が高まります。

## 前提知識の解説

### 1. コンパイラのバックエンドと最適化

コンパイラは通常、フロントエンド、中間コード生成、バックエンドの3つの主要なフェーズに分けられます。
- **フロントエンド**: ソースコードを解析し、抽象構文木（AST）を生成します。
- **中間コード生成**: ASTを、特定のアーキテクチャに依存しない中間表現（IR）に変換します。
- **バックエンド**: 中間表現をターゲットアーキテクチャの機械語コードに変換します。このフェーズで、コードの最適化（レジスタ割り当て、命令スケジューリングなど）が行われます。

レジスタ最適化は、バックエンドの重要な部分であり、プログラムの実行速度に直接影響します。

### 2. レジスタ割り当て (Register Allocation)

レジスタ割り当ては、コンパイラ最適化の主要なタスクの一つで、プログラムの変数（または中間表現の仮想レジスタ）を、CPUの物理レジスタに割り当てるプロセスです。目標は、メモリへのアクセス（スピル）を最小限に抑えつつ、利用可能なレジスタを最大限に活用することです。

一般的なレジスタ割り当ての手法には、以下のようなものがあります。
- **グラフ彩色 (Graph Coloring)**: 変数の生存期間（ライブネス）に基づいて干渉グラフを構築し、そのグラフを彩色することでレジスタを割り当てます。干渉グラフでは、ノードが変数、エッジが同時に生存する変数（互いに干渉する変数）を表します。グラフの彩色数は、必要なレジスタの数を意味します。
- **リニアスキャン (Linear Scan)**: 変数の生存区間を線形に走査し、レジスタを割り当てます。これは、グラフ彩色よりも高速ですが、生成されるコードの品質は劣る場合があります。

このコミットで実装されている`regopt`は、グラフ彩色に似たアプローチ（領域の特定、コスト計算、レジスタの選択）を採用しているように見えます。

### 3. 制御フローグラフ (Control Flow Graph, CFG)

制御フローグラフは、プログラムの実行パスを抽象的に表現したものです。ノードは基本ブロック（分岐やジャンプを含まない連続した命令のシーケンス）を表し、エッジは基本ブロック間の制御フローの遷移を表します。レジスタ割り当てや他の最適化の多くは、このCFG上で実行されます。

### 4. ライブ変数解析 (Live Variable Analysis)

ライブ変数解析は、データフロー解析の一種で、プログラムの各点において、どの変数が「ライブ」（将来的に使用される可能性がある）であるかを特定します。レジスタ割り当てでは、ライブな変数のみがレジスタに割り当てられる候補となります。変数がライブでなくなった場合、そのレジスタは解放され、他の変数に再利用できます。

### 5. Plan 9 Assembler (`9g`, `9l`, `9c`)

Goコンパイラは、初期にはPlan 9のツールチェイン（`8g`, `6g`, `5g`など）をベースにしていました。`9g`はPowerPC 64-bitアーキテクチャ向けのGoコンパイラ（`g`はGoの略）を指します。これらのツールは、Go言語のソースコードをアセンブリコードに変換し、最終的に実行可能なバイナリを生成します。

### 6. `Prog`構造体

Goコンパイラのバックエンドでは、`Prog`構造体がアセンブリ命令を表します。これは、命令の種類（`as`）、オペランド（`from`, `to`, `reg`, `from3`）、リンク（`link`）などの情報を含みます。

## 技術的詳細

このコミットで導入された`regopt`関数は、Goコンパイラのバックエンドにおけるレジスタ割り当ての主要なロジックをカプセル化しています。これは、複数のパスにわたる複雑なプロセスであり、制御フローグラフの構築から始まり、ライブ変数解析、レジスタ割り当てのコスト計算、最終的なコードの書き換えまでを含みます。

`regopt`の処理は、以下の主要なパスに分けられます。

### パス1: 補助データ構造の構築と変数使用状況の特定

- `regopt`関数の冒頭で、`first`フラグがセットされていれば、`fmtinstall('Q', Qconv)`が呼び出され、デバッグ出力のためのフォーマットが設定されます。
- `mergetemp(firstp)`が呼び出され、一時変数のマージが行われます（コミットの差分には含まれていませんが、既存の関数として呼び出されています）。
- `NREGVAR`（64個のレジスタ変数、32個の汎用レジスタと32個の浮動小数点レジスタ）が定義され、レジスタの擬似変数が初期化されます。これにより、物理レジスタも変数として扱われ、レジスタ割り当ての対象となります。
- 固定機能を持つレジスタ（例: `REGSP`、`REGG`、特定の浮動小数点定数レジスタ）は、`regbits`マスクによってレジスタ割り当てから除外されます。
- `flowstart(firstp, sizeof(Reg))`を呼び出して、制御フローグラフ（CFG）を構築し、各プログラム命令に対応する`Reg`構造体を初期化します。`Reg`構造体は、命令によって書き込まれる変数（`set`）、読み込まれる変数（`use1`, `use2`）、およびライブネス情報（`refbehind`, `refahead`, `calbehind`, `calahead`など）をビットマップで追跡します。
- 各命令について`proginfo`を呼び出し、命令のフラグ（`LeftAddr`, `LeftRead`, `RightWrite`など）と暗黙的なレジスタ使用状況（`reguse`, `regset`, `regindex`）を取得します。
- `mkvar`関数を使用して、命令のオペランド（`from`, `to`）に対応する変数をビットマップに変換し、`Reg`構造体の`use1`, `use2`, `set`フィールドを更新します。
- アドレスが取られた変数（`addr`フラグがセットされた変数）は、`setaddrs`によってレジスタ割り当ての対象から除外されます。これは、ポインタを介したアクセスや、ガベージコレクタのライブネス解析との整合性を保つために重要です。

### パス2: ループ構造の特定

- `flowrpo(g)`を呼び出して、CFG上で逆ポストオーダー（Reverse Postorder, RPO）順序を計算します。これは、ループ検出やデータフロー解析の効率化に役立ちます。

### パス2.5: "fat vardef"の伝播

- `AVARDEF`命令（変数の定義）と`AVARKILL`命令（変数の破棄）を処理し、`walkvardef`関数を使って、`VARDEF`以降の`CALL`命令までアクティブな変数を`r->act`ビットマップに記録します。これは、初期化された変数が`CALL`をまたいでライブであることを保証し、ガベージコレクション時の整合性を保つために使用されます。

### パス3: 使用状況の伝播（後方データフロー解析）

- `prop`関数が呼び出され、ライブ変数解析を実行します。これは、CFGを後方（逆方向）に走査し、各命令の`refahead`（命令より後方でライブな変数）と`calahead`（`CALL`命令をまたいでライブな変数）ビットマップを伝播させます。
- `ABL`（関数呼び出し）命令では、`externs`（外部変数）、`ivar`（入力パラメータ）、`r1->act`（最近定義された変数）が`cal`（`calahead`）にマージされます。これは、関数呼び出しをまたいでライブな変数を正確に追跡するために重要です。
- `ARET`（関数リターン）命令では、`externs`と`ovar`（出力パラメータ）が`cal`に設定されます。
- `ref`と`cal`ビットマップは、命令の`set`、`use1`、`use2`ビットマップに基づいて更新されます。
- このパスは、`change`フラグがセットされなくなるまで繰り返され、不動点に達するまで伝播が行われます。

### パス4: レジスタ/変数同期の伝播（前方データフロー解析）

- `synch`関数が呼び出され、CFGを前方（順方向）に走査し、レジスタと変数の同期情報を`regdiff`ビットマップに伝播させます。これは、レジスタとメモリ上の値がいつ同期している必要があるかを特定するのに役立ちます。

### パス4.5: レジスタ擬似変数の`regu`への移動

- `Reg`構造体の`regu`フィールドに、レジスタ擬似変数のビットマップを移動します。これにより、他の`Bits`フィールドからレジスタ関連のビットがクリアされ、変数とレジスタの区別が明確になります。

### パス5: 領域の分離とコスト計算

- `paint1`関数が呼び出され、レジスタ割り当ての「領域」（`Rgn`）を特定し、各領域のコストを計算します。
- 領域は、特定の変数がレジスタに割り当てられる可能性のあるコードの連続した部分を表します。
- `change`変数は、領域のコスト（レジスタ割り当てによって節約できるメモリアクセスの量）を累積するために使用されます。`CREF`（参照コスト）と`CLOAD`（ロード/ストアコスト）が考慮されます。
- `nregion`は、特定された領域の数を追跡します。
- 最後に、`qsort`関数を使用して、`Rgn`構造体の配列をコストの降順でソートします。これにより、最も利益の大きいレジスタ割り当てから優先的に処理できるようになります。

### パス6: 使用レジスタの決定とコードの書き換え

- ソートされた`Rgn`配列を走査し、各領域に対してレジスタ割り当てを実行します。
- `paint2`関数が呼び出され、特定の領域内で既にどのレジスタが使用されているかを`usedreg`ビットマップで決定します。これにより、割り当て可能なレジスタの候補が絞られます。
- `allreg`関数が呼び出され、`usedreg`ビットマップと領域のコストに基づいて、実際に割り当てるレジスタ（`rgp->regno`）を選択します。
- `paint3`関数が呼び出され、選択されたレジスタを使用して、元のコードを書き換えます。
    - 変数がレジスタにロードされる必要がある場合（`LOAD`マクロと`regdiff`ビットマップで判断）、`addmove`関数が呼び出され、メモリからレジスタへの`MOV`命令が挿入されます（スピル）。
    - 命令のオペランド（`from`, `to`）がレジスタに割り当てられた変数を使用している場合、`addreg`関数が呼び出され、オペランドのタイプが`D_REG`または`D_FREG`に変更され、割り当てられたレジスタ番号が設定されます。
    - 変数がメモリにストアされる必要がある場合（`STORE`マクロと`regdiff`ビットマップで判断）、`addmove`関数が呼び出され、レジスタからメモリへの`MOV`命令が挿入されます（リロード）。
- `ostats`構造体は、`ncvtreg`（レジスタ変換数）、`nspill`（スピル数）、`ndelmov`（削除されたMOV命令数）、`nvar`（最適化された変数数）などの統計情報を収集します。

### パス7: ピーフホール最適化とNOPの除去

- `peep(firstp)`関数が呼び出され、ピーフホール最適化が実行されます。これは、隣接する少数の命令パターンをより効率的な命令シーケンスに置き換えるローカルな最適化です。
- 最後に、生成されたコードから不要な`ANOP`（No Operation）命令が除去されます。
- `ostats`に収集された統計情報がデバッグ出力として表示されます。

この一連のパスにより、コンパイラは変数を効率的にレジスタに割り当て、生成される機械語コードの性能を向上させます。

## コアとなるコードの解説

### `struct Reg` (`opt.h`)

```c
struct	Reg
{
	Flow	f;

	Bits	set;  	// regopt variables written by this instruction.
	Bits	use1; 	// regopt variables read by prog->from.
	Bits	use2; 	// regopt variables read by prog->to.

	// refahead/refbehind are the regopt variables whose current
	// value may be used in the following/preceding instructions
	// up to a CALL (or the value is clobbered).
	Bits	refbehind;
	Bits	refahead;
	// calahead/calbehind are similar, but for variables in
	// instructions that are reachable after hitting at least one
	// CALL.
	Bits	calbehind;
	Bits	calahead;
	Bits	regdiff;
	Bits	act;

	uint64	regu;		// register used bitmap
};
```
- `Flow f`: 制御フローグラフのノード情報（前任者、後任者、ループ情報など）を保持します。
- `set`, `use1`, `use2`: この命令によって書き込まれる（`set`）または読み込まれる（`use1`は`from`オペランド、`use2`は`to`オペランド）レジスタ最適化対象の変数をビットマップで表します。
- `refbehind`, `refahead`: `CALL`命令に到達するまで、この命令の前後でライブな変数を追跡します。
- `calbehind`, `calahead`: `CALL`命令を少なくとも1つ通過した後に、この命令の前後でライブな変数を追跡します。これは、関数呼び出しをまたぐライブネス解析に重要です。
- `regdiff`: レジスタとメモリ間の値の差異を追跡します。
- `act`: 変数のアクティブな期間を追跡します。
- `regu`: この命令で実際に使用されるレジスタのビットマップ。

### `struct Rgn` (`opt.h`)

```c
struct	Rgn
{
	Reg*	enter;
	int	varno;
	int	cost;
	int	regno;
};
```
- `enter`: この領域の開始命令に対応する`Reg`構造体へのポインタ。
- `varno`: この領域が対象とする変数の番号。
- `cost`: この領域でレジスタを割り当てることによって得られるコスト（性能向上）。
- `regno`: この領域に割り当てられた物理レジスタの番号。

### `regopt(Prog *firstp)` (`reg.c`)

この関数は、レジスタ最適化のメインエントリポイントであり、前述の7つのパスを順に実行します。

### `prop(Reg *r, Bits ref, Bits cal)` (`reg.c`)

```c
void
prop(Reg *r, Bits ref, Bits cal)
{
	// ... (省略) ...
	for(r1 = r; r1 != R; r1 = (Reg*)r1->f.p1) { // 後方走査
		// ... (refahead, calahead の伝播) ...
		switch(r1->f.prog->as) {
		case ABL: // 関数呼び出し
			// ... (cal に externs, ivar, r1->act をマージ) ...
			// ... (cal に Go 変数全体をマージ) ...
			break;
		case ATEXT: // 関数の開始
			// ... (ref, cal をクリア) ...
			break;

		}
		// ... (ref, cal を set, use1, use2 に基づいて更新) ...
	}

```
`prop`関数は、ライブ変数解析の核心部分です。制御フローグラフを後方（逆方向）に走査し、変数のライブネス情報を伝播させます。
- `ref`は`CALL`命令をまたがないライブネス、`cal`は`CALL`命令をまたぐライブネスを追跡します。
- `ABL`（関数呼び出し）命令では、呼び出しをまたいでライブであると見なされる変数（外部変数、入力パラメータ、最近定義された変数）が`cal`ビットマップに追加されます。また、Goの複合型（スライス、文字列、インターフェース）の場合、ガベージコレクタのライブネス解析との整合性を保つため、その変数を構成する全てのワードがライブであるとマークされます。
- `ATEXT`（関数の開始）では、ライブネス情報がリセットされます。
- `ARET`（関数リターン）では、外部変数と出力パラメータがライブであるとマークされます。
- 各命令では、その命令が変数を読み込む（`use1`, `use2`）か書き込む（`set`）かに応じて、ライブネス情報が更新されます。

### `RtoB(int r)` / `BtoR(uint64 b)` (`reg.c`)

```c
uint64
RtoB(int r)
{
	if(r > D_R0 && r <= D_R0+31)
		return 1ULL << (r - D_R0);
	return 0;
}

int
BtoR(uint64 b)
{
	b &= 0xffffffffull;
	if(b == 0)
		return 0;
	return bitno(b) + D_R0;
}
```
これらの関数は、レジスタ番号とビットマップ表現の間で変換を行います。
- `RtoB`は、汎用レジスタ番号を対応するビットマスクに変換します。
- `BtoR`は、ビットマスクから汎用レジスタ番号を抽出します。`bitno`は、ビットマスク内でセットされている最も低いビットのインデックスを返します。

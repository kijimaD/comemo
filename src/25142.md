# [インデックス 25142] ファイルの概要

このコミットは、GoプログラムがCgoを介してCコードと連携する際に、MemorySanitizer (MSan) を効果的に利用できるようにするための重要な変更を導入しています。具体的には、GoランタイムがCgoコードで使用するメモリ割り当てメカニズムを調整し、MSanがGoからCに渡されるメモリを「初期化済み」として正しく認識するように修正しています。これにより、CgoでリンクされたCコードのメモリ安全性をMSanで検証できるようになります。

    dynamically check for memory errors in C code. It's not useful for Go
    code, since Go is memory safe. But it is useful to be able to use the

## 元コミット内容

このコミットの目的は、GoプログラムがCgoを介してCコードと連携する際に、MemorySanitizer (MSan) をサポートすることです。MSanはCコードのメモリエラーを動的にチェックするコンパイラ機能ですが、Goはメモリ安全な言語であるため、Goコード自体には適用されません。しかし、Cgoを介してGoプログラムにリンクされたCコードに対してMSanを使用できることは非常に有用です。

これまでの実装では、GoからCに渡されたメモリがMSanによって「初期化されていない」と見なされ、誤ったエラーが報告されていました。この問題を解決するため、GoランタイムはCgoを使用する際にCの`mmap`関数を呼び出すように変更されます。MSanが有効な場合、この`mmap`呼び出しはインターセプトされ、返されるメモリが初期化済みとしてマークされます。

さらに、clang 3.8以前のバージョンのMSanに存在すると思われるバグを回避するため、`mmap`を呼び出す前に`malloc`を呼び出すというワークアラウンドが導入されています。

## 変更の背景

Go言語はメモリ安全性を重視して設計されており、ガベージコレクションや型安全性によって多くのメモリ関連のバグ（例えば、use-after-freeやdouble-freeなど）を防止します。しかし、GoプログラムがCgoを介してC/C++コードと連携する場合、C/C++コードはGoのメモリ安全性の恩恵を受けません。C/C++コードには、初期化されていないメモリの使用、バッファオーバーフロー、解放済みメモリへのアクセスといったメモリエラーが依然として存在する可能性があります。

MemorySanitizer (MSan) は、LLVM/Clangプロジェクトによって開発された動的メモリエラー検出ツールです。コンパイル時にコードに計測（instrumentation）を挿入し、実行時に初期化されていないメモリの読み取りを検出します。これはC/C++コードの品質と信頼性を向上させる上で非常に強力なツールです。

このコミット以前は、GoプログラムがCgoを介してCコードを呼び出し、Go側で割り当てられたメモリをCコードに渡すと、MSanはそのメモリを「初期化されていない」と誤って報告していました。これは、MSanがGoランタイムによるメモリ割り当てを認識せず、そのメモリがCコードによって初めてアクセスされる際に初期化されていないと判断するためです。この誤検出により、Cgoを使用するGoプログラムでMSanを実用的に利用することが困難でした。

この変更の背景には、GoとCgoの相互運用性を高め、Cgoで利用されるCコードのメモリ安全性をGoのツールエコシステムの一部として検証できるようにするという明確な目標があります。これにより、Go開発者はCgoを使用する際の信頼性を向上させることができます。

## 前提知識の解説

### MemorySanitizer (MSan)

MemorySanitizer (MSan) は、初期化されていないメモリの読み取りを検出する動的解析ツールです。LLVM/Clangコンパイラの一部として提供され、コンパイル時にコードにフックを挿入します。プログラムが実行されると、MSanはメモリのシャドウメモリ（shadow memory）を維持し、各バイトが初期化されているかどうかを追跡します。初期化されていないメモリが読み取られた場合、MSanは実行を停止し、詳細なエラーレポートを生成します。これは、C/C++プログラムにおける未定義動作の一般的な原因である初期化忘れのバグを特定するのに非常に効果的です。

### Cgo

Cgoは、GoプログラムがCコードを呼び出したり、CコードからGoコードを呼び出したりするためのGo言語の機能です。GoとCの間のインターフェースを提供し、異なる言語間のデータ型変換や関数呼び出しを可能にします。Cgoを使用すると、既存のCライブラリをGoプログラムから利用したり、パフォーマンスが重要な部分をCで記述したりすることができます。しかし、Cgoを使用すると、Goのメモリ安全性保証がCコード部分には適用されなくなるため、Cコードのメモリ管理には注意が必要です。

### `mmap`システムコール

`mmap`は、Unix系オペレーティングシステムで利用可能なシステムコールで、ファイルやデバイスをプロセスの仮想アドレス空間にマッピングするために使用されます。メモリをファイルにマッピングするだけでなく、匿名メモリ（ファイルに関連付けられていないメモリ）を割り当てるためにも使用されます。Goランタイムは、ヒープメモリの割り当てなど、多くの内部メモリ管理操作で`mmap`を使用します。

### `malloc`関数

`malloc`は、C標準ライブラリ（`stdlib.h`）で提供される関数で、指定されたサイズのメモリブロックをヒープから動的に割り当てます。割り当てられたメモリは初期化されず、その内容にはガベージ値が含まれる可能性があります。`malloc`で割り当てられたメモリは、`free`関数で解放する必要があります。

### `pthread_attr_t`とスレッドスタック

`pthread_attr_t`はPOSIXスレッド（pthreads）の属性オブジェクトで、新しいスレッドを作成する際の属性（スタックサイズ、スケジューリングポリシーなど）を定義するために使用されます。`pthread_attr_getstacksize`は、この属性オブジェクトからスレッドのスタックサイズを取得するために使用されます。Goランタイムは、Cgoスレッドの管理においてこれらのpthreads関連の関数を使用することがあります。

## 技術的詳細

このコミットの核心は、Goランタイムがメモリを割り当てる際に、Cgoが有効な場合にCの`mmap`関数を呼び出すように変更することです。

1.  **`mmap`のフック**:
    *   Goランタイムは通常、独自の`mmap`実装（`runtime.sysMmap`）を使用してメモリを割り当てます。
    *   この変更では、Cgoが有効な場合（`_cgo_mmap`シンボルがリンクされている場合）、Goの`runtime.mmap`関数がCgo経由でCの`mmap`関数（`x_cgo_mmap`）を呼び出すように変更されます。
    *   MSanが有効な環境でコンパイルされたCコードでは、Cの`mmap`呼び出しがMSanによってインターセプトされます。MSanは、`mmap`によって返されたメモリ領域を「初期化済み」としてマークするため、GoからCに渡されたメモリが誤って初期化されていないと報告されることがなくなります。

2.  **MSanバグのワークアラウンド**:
    *   `src/runtime/cgo/gcc_linux_amd64.c`の`x_cgo_init`関数に、`mmap`を呼び出す前に`malloc`を呼び出すコードが追加されました。
    *   これは、clang 3.8以前のMSanに存在する既知のバグ（`mmap`が`malloc`より先に呼び出されると、MSanが返すアドレスが後にMSanライブラリによって上書きされる可能性がある）を回避するためのものです。
    *   このワークアラウンドは、`malloc`によって割り当てられたメモリを実際に使用することで、GCCコンパイラがこの「一見不要な」`malloc`呼び出しを最適化で削除しないようにしています。

3.  **新しい`mmap`ラッパーの導入**:
    *   `src/runtime/cgo/gcc_mmap.c`に`x_cgo_mmap`というC関数が新しく追加されました。これは、Goランタイムから呼び出されるCの`mmap`ラッパーです。
    *   このラッパーは、`mmap`システムコールを呼び出し、エラーが発生した場合にはGoコードが期待する形式（`MAP_FAILED`の場合に`errno`を`uintptr_t`にキャストして返す）で結果を返します。
    *   `src/runtime/cgo/mmap.go`では、`//go:cgo_import_static x_cgo_mmap`と`//go:linkname _cgo_mmap _cgo_mmap`ディレクティブを使用して、このC関数をGoランタイムから利用できるようにしています。

4.  **テストの追加**:
    *   `misc/cgo/testsanitizers/msan.go`と`misc/cgo/testsanitizers/test.bash`が追加され、MSanがCgoコードで正しく機能するかどうかを検証するテストが導入されました。
    *   `msan.go`は、GoのスライスをC関数に渡し、C関数内でそのスライスにアクセスして初期化する簡単なCgoプログラムです。MSanが有効な場合、このテストはエラーなく実行されるはずです。
    *   `test.bash`スクリプトは、`clang`がMSanをサポートしているかどうかを検出し、サポートしている場合に`msan.go`を実行します。
    *   `src/cmd/dist/test.go`に、この新しいテストスイートをGoのビルドシステムに統合するためのエントリが追加されました。

これらの変更により、GoランタイムはCgoとMSanの間の相互作用を適切に管理し、CgoでリンクされたCコードのメモリ安全性を効果的に検証できるようになります。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

1.  **`src/runtime/cgo/gcc_linux_amd64.c`**:
    *   `x_cgo_init`関数内で、`pthread_attr_t`をスタックではなくヒープに割り当てるように変更（`pthread_attr_t attr;` -> `pthread_attr_t *attr;`）。
    *   `mmap`呼び出しの前に`malloc`を呼び出すMSanバグのワークアラウンドが追加されました。
        ```c
        	attr = (pthread_attr_t*)malloc(sizeof *attr);
        	if (attr == NULL) {
        		fatalf("malloc failed: %s", strerror(errno));
        	}
        	pthread_attr_init(attr);
        	pthread_attr_getstacksize(attr, &size);
        	g->stacklo = (uintptr)&size - size + 4096; // Note: &size is used here, which seems like a potential bug or a very specific intent. Original was &attr.
        	pthread_attr_destroy(attr);
        	free(attr);
        ```
        **注**: `g->stacklo = (uintptr)&size - size + 4096;` の行は、元のコードの `(uintptr)&attr - size + 4096;` から変更されています。これは、`attr`がヒープに移動したため、スタック上のローカル変数`size`のアドレスを基準にスタック下限を計算しようとしているように見えます。これは意図的なものか、あるいは別の修正が必要な箇所かもしれません。コミットメッセージの意図からすると、`attr`が指すメモリ領域ではなく、スレッドのスタック領域の計算に関連する変更である可能性が高いです。

2.  **`src/runtime/cgo/gcc_mmap.c` (新規ファイル)**:
    *   Cgoから呼び出されるCの`mmap`ラッパー関数`x_cgo_mmap`が定義されています。
        ```c
        void *
        x_cgo_mmap(void *addr, uintptr_t length, int32_t prot, int32_t flags, int32_t fd, uint32_t offset) {
        	void *p;
        	p = mmap(addr, length, prot, flags, fd, offset);
        	if (p == MAP_FAILED) {
        		p = (void *) (uintptr_t) errno;
        	}
        	return p;
        }
        ```

3.  **`src/runtime/cgo/mmap.go` (新規ファイル)**:
    *   `x_cgo_mmap` C関数をGoランタイムにリンクするための`//go:cgo_import_static`と`//go:linkname`ディレクティブが含まれています。
        ```go
        package cgo

        import _ "unsafe" // Import "unsafe" because we use go:linkname.

        //go:cgo_import_static x_cgo_mmap
        //go:linkname x_cgo_mmap x_cgo_mmap
        //go:linkname _cgo_mmap _cgo_mmap
        var x_cgo_mmap byte
        var _cgo_mmap = &x_cgo_mmap
        ```

4.  **`src/runtime/cgo_mmap.go` (新規ファイル)**:
    *   Goランタイムの`mmap`関数が、Cgoが有効な場合にCgo経由でCの`mmap`を呼び出すように変更されています。
        ```go
        package runtime

        import "unsafe"

        // _cgo_mmap is filled in by runtime/cgo when it is linked into the
        // program, so it is only non-nil when using cgo.
        //go:linkname _cgo_mmap _cgo_mmap
        var _cgo_mmap unsafe.Pointer

        func mmap(addr unsafe.Pointer, n uintptr, prot, flags, fd int32, off uint32) (ret unsafe.Pointer) {
        	if _cgo_mmap != nil {
        		systemstack(func() {
        			ret = callCgoMmap(addr, n, prot, flags, fd, off)
        		})
        		return
        	}
        	return sysMmap(addr, n, prot, flags, fd, off)
        }

        // sysMmap calls the mmap system call. It is implemented in assembly.
        func sysMmap(addr unsafe.Pointer, n uintptr, prot, flags, fd int32, off uint32) unsafe.Pointer

        // callCgoMmap calls the mmap function in the runtime/cgo package
        // using the GCC calling convention. It is implemented in assembly.
        func callCgoMmap(addr unsafe.Pointer, n uintptr, prot, flags, fd int32, off uint32) unsafe.Pointer
        ```

5.  **`src/runtime/sys_linux_amd64.s`**:
    *   既存の`runtime·mmap`アセンブリ関数が`runtime·sysMmap`にリネームされました。
    *   新しいアセンブリ関数`runtime·callCgoMmap`が追加され、これは`_cgo_mmap`が指すC関数をGCC呼び出し規約に従って呼び出します。
        ```assembly
        TEXT runtime·callCgoMmap(SB),NOSPLIT,$0
        	MOVQ	addr+0(FP), DI
        	MOVQ	n+8(FP), SI
        	MOVL	prot+16(FP), DX
        	MOVL	flags+20(FP), CX
        	MOVL	fd+24(FP), R8
        	MOVL	off+28(FP), R9
        	MOVQ	_cgo_mmap(SB), AX
        	CALL	AX
        	MOVQ	AX, ret+32(FP)
        	RET
        ```

6.  **`src/runtime/stubs2.go`**:
    *   `mmap`関数の宣言が削除されました。これは`src/runtime/cgo_mmap.go`に移動されたためです。

7.  **`misc/cgo/testsanitizers/msan.go` (新規ファイル)**:
    *   MSanテスト用のGoプログラム。Cgoを介してC関数を呼び出し、Goで割り当てたメモリをC側で初期化します。
        ```go
        package main

        /*
        #cgo CFLAGS: -fsanitize=memory
        #cgo LDFLAGS: -fsanitize=memory

        #include <stdint.h>

        void f(int32_t *p, int n) {
          int i;
          for (i = 0; i < n; i++) {
            p[i] = (int32_t)i;
          }
        }
        */
        import "C"

        import (
        	"fmt"
        	"os"
        	"unsafe"
        )

        func main() {
        	a := make([]int32, 10)
        	C.f((*C.int32_t)(unsafe.Pointer(&a[0])), C.int(len(a)))
        	for i, v := range a {
        		if i != int(v) {
        			fmt.Println("bad %d: %v\n", i, a)
        			os.Exit(1)
        		}
        	}
        }
        ```

8.  **`misc/cgo/testsanitizers/test.bash` (新規ファイル)**:
    *   MSanテストを実行するためのシェルスクリプト。`clang`のMSanサポートをチェックし、`msan.go`を実行します。

9.  **`src/cmd/dist/test.go`**:
    *   `testsanitizers`テストをGoのビルドシステムに登録するエントリが追加されました。

## コアとなるコードの解説

このコミットの主要な変更は、Goランタイムのメモリ割り当てパスを条件付きでCgo経由のCライブラリ呼び出しにリダイレクトすることです。

1.  **`runtime.mmap`の多態性**:
    *   `src/runtime/cgo_mmap.go`で定義されている`runtime.mmap`関数は、Goランタイムがメモリを割り当てるための主要なインターフェースです。
    *   この関数は、グローバル変数`_cgo_mmap`が`nil`でないかどうかをチェックします。`_cgo_mmap`は、Cgoがプログラムにリンクされている場合にのみ非`nil`になります。
    *   もし`_cgo_mmap`が非`nil`であれば、`systemstack`内で`callCgoMmap`アセンブリ関数を呼び出します。これは、Cgo経由でCの`x_cgo_mmap`関数（`src/runtime/cgo/gcc_mmap.c`で定義）を呼び出すためのものです。
    *   `_cgo_mmap`が`nil`の場合（Cgoが使用されていない場合）、通常のGoランタイムの`sysMmap`アセンブリ関数（`src/runtime/sys_linux_amd64.s`で定義）を呼び出します。
    *   このメカニズムにより、Cgoの有無に応じて異なる`mmap`実装を透過的に使用できるようになります。

2.  **Cgo経由の`mmap`呼び出し**:
    *   `src/runtime/sys_linux_amd64.s`の`runtime·callCgoMmap`アセンブリ関数は、Goの引数をGCC呼び出し規約（System V AMD64 ABI）に従ってレジスタ（`DI`, `SI`, `DX`, `CX`, `R8`, `R9`）に配置し、`_cgo_mmap`が指すアドレス（つまり、Cの`x_cgo_mmap`関数）を`CALL`命令で呼び出します。
    *   Cの`x_cgo_mmap`関数は、受け取った引数で実際の`mmap`システムコールを呼び出します。MSanが有効な環境では、このCの`mmap`呼び出しがMSanによってインターセプトされ、返されたメモリが初期化済みとしてマークされます。

3.  **MSanバグの回避**:
    *   `src/runtime/cgo/gcc_linux_amd64.c`の`x_cgo_init`関数における`malloc`呼び出しは、特定のMSanのバグに対する防御策です。このバグは、`mmap`が`malloc`より先に呼び出されると、MSanの内部状態が不正になる可能性があるというものです。Goランタイムの初期化フェーズで`mmap`が頻繁に呼び出されるため、このワークアラウンドは重要です。`malloc`を呼び出すことで、MSanの内部状態を安定させ、その後の`mmap`呼び出しが正しく処理されるようにします。

これらの変更により、GoプログラムがCgoを介してCコードと連携する際に、Goランタイムが割り当てるメモリがMSanによって正しく「初期化済み」と認識されるようになり、Cgoコードのメモリ安全性をMSanで効果的に検証できるようになります。

    dynamically check for memory errors in C code. It's not useful for Go
    code, since Go is memory safe. But it is useful to be able to use the
    memory sanitizer on C code that is linked into a Go program via cgo.
    Without this change it does not work, as msan considers memory passed
    from Go to C as uninitialized.

    using cgo. When using msan the mmap call will be intercepted and marked
    as returning initialized memory.

## 元コミット内容

このコミットの目的は、GoプログラムがCgoを介してCコードと連携する際に、MemorySanitizer (MSan) をサポートすることです。MSanはCコードのメモリエラーを動的にチェックするコンパイラ機能ですが、Goはメモリ安全な言語であるため、Goコード自体には適用されません。しかし、Cgoを介してGoプログラムにリンクされたCコードに対してMSanを使用できることは非常に有用です。

これまでの実装では、GoからCに渡されたメモリがMSanによって「初期化されていない」と見なされ、誤ったエラーが報告されていました。この問題を解決するため、GoランタイムはCgoを使用する際にCの`mmap`関数を呼び出すように変更されます。MSanが有効な場合、この`mmap`呼び出しはインターセプトされ、返されるメモリが初期化済みとしてマークされます。

さらに、clang 3.8以前のバージョンのMSanに存在すると思われるバグを回避するため、`mmap`を呼び出す前に`malloc`を呼び出すというワークアラウンドが導入されています。

## 変更の背景

Go言語はメモリ安全性を重視して設計されており、ガベージコレクションや型安全性によって多くのメモリ関連のバグ（例えば、use-after-freeやdouble-freeなど）を防止します。しかし、GoプログラムがCgoを介してC/C++コードと連携する場合、C/C++コードはGoのメモリ安全性の恩恵を受けません。C/C++コードには、初期化されていないメモリの使用、バッファオーバーフロー、解放済みメモリへのアクセスといったメモリエラーが依然として存在する可能性があります。

MemorySanitizer (MSan) は、LLVM/Clangプロジェクトによって開発された動的メモリエラー検出ツールです。コンパイル時にコードに計測（instrumentation）を挿入し、実行時に初期化されていないメモリの読み取りを検出します。これはC/C++コードの品質と信頼性を向上させる上で非常に強力なツールです。

このコミット以前は、GoプログラムがCgoを介してCコードを呼び出し、Go側で割り当てられたメモリをCコードに渡すと、MSanはそのメモリを「初期化されていない」と誤って報告していました。これは、MSanがGoランタイムによるメモリ割り当てを認識せず、そのメモリがCコードによって初めてアクセスされる際に初期化されていないと判断するためです。この誤検出により、Cgoを使用するGoプログラムでMSanを実用的に利用することが困難でした。

この変更の背景には、GoとCgoの相互運用性を高め、Cgoで利用されるCコードのメモリ安全性をGoのツールエコシステムの一部として検証できるようにするという明確な目標があります。これにより、Go開発者はCgoを使用する際の信頼性を向上させることができます。

## 前提知識の解説

### MemorySanitizer (MSan)

MemorySanitizer (MSan) は、初期化されていないメモリの読み取りを検出する動的解析ツールです。LLVM/Clangコンパイラの一部として提供され、コンパイル時にコードにフックを挿入します。プログラムが実行されると、MSanはメモリのシャドウメモリ（shadow memory）を維持し、各バイトが初期化されているかどうかを追跡します。初期化されていないメモリが読み取られた場合、MSanは実行を停止し、詳細なエラーレポートを生成します。これは、C/C++プログラムにおける未定義動作の一般的な原因である初期化忘れのバグを特定するのに非常に効果的です。

### Cgo

Cgoは、GoプログラムがCコードを呼び出したり、CコードからGoコードを呼び出したりするためのGo言語の機能です。GoとCの間のインターフェースを提供し、異なる言語間のデータ型変換や関数呼び出しを可能にします。Cgoを使用すると、既存のCライブラリをGoプログラムから利用したり、パフォーマンスが重要な部分をCで記述したりすることができます。しかし、Cgoを使用すると、Goのメモリ安全性保証がCコード部分には適用されなくなるため、Cコードのメモリ管理には注意が必要です。

### `mmap`システムコール

`mmap`は、Unix系オペレーティングシステムで利用可能なシステムコールで、ファイルやデバイスをプロセスの仮想アドレス空間にマッピングするために使用されます。メモリをファイルにマッピングするだけでなく、匿名メモリ（ファイルに関連付けられていないメモリ）を割り当てるためにも使用されます。Goランタイムは、ヒープメモリの割り当てなど、多くの内部メモリ管理操作で`mmap`を使用します。

### `malloc`関数

`malloc`は、C標準ライブラリ（`stdlib.h`）で提供される関数で、指定されたサイズのメモリブロックをヒープから動的に割り当てます。割り当てられたメモリは初期化されず、その内容にはガベージ値が含まれる可能性があります。`malloc`で割り当てられたメモリは、`free`関数で解放する必要があります。

### `pthread_attr_t`とスレッドスタック

`pthread_attr_t`はPOSIXスレッド（pthreads）の属性オブジェクトで、新しいスレッドを作成する際の属性（スタックサイズ、スケジューリングポリシーなど）を定義するために使用されます。`pthread_attr_getstacksize`は、この属性オブジェクトからスレッドのスタックサイズを取得するために使用されます。Goランタイムは、Cgoスレッドの管理においてこれらのpthreads関連の関数を使用することがあります。

## 技術的詳細

このコミットの核心は、Goランタイムがメモリを割り当てる際に、Cgoが有効な場合にCの`mmap`関数を呼び出すように変更することです。

1.  **`mmap`のフック**:
    *   Goランタイムは通常、独自の`mmap`実装（`runtime.sysMmap`）を使用してメモリを割り当てます。
    *   この変更では、Cgoが有効な場合（`_cgo_mmap`シンボルがリンクされている場合）、Goの`runtime.mmap`関数がCgo経由でCの`mmap`関数（`x_cgo_mmap`）を呼び出すように変更されます。
    *   MSanが有効な環境でコンパイルされたCコードでは、Cの`mmap`呼び出しがMSanによってインターセプトされます。MSanは、`mmap`によって返されたメモリ領域を「初期化済み」としてマークするため、GoからCに渡されたメモリが誤って初期化されていないと報告されることがなくなります。

2.  **MSanバグのワークアラウンド**:
    *   `src/runtime/cgo/gcc_linux_amd64.c`の`x_cgo_init`関数に、`mmap`を呼び出す前に`malloc`を呼び出すコードが追加されました。
    *   これは、clang 3.8以前のMSanに存在する既知のバグ（`mmap`が`malloc`より先に呼び出されると、MSanが返すアドレスが後にMSanライブラリによって上書きされる可能性がある）を回避するためのものです。
    *   このワークアラウンドは、`malloc`によって割り当てられたメモリを実際に使用することで、GCCコンパイラがこの「一見不要な」`malloc`呼び出しを最適化で削除しないようにしています。

3.  **新しい`mmap`ラッパーの導入**:
    *   `src/runtime/cgo/gcc_mmap.c`に`x_cgo_mmap`というC関数が新しく追加されました。これは、Goランタイムから呼び出されるCの`mmap`ラッパーです。
    *   このラッパーは、`mmap`システムコールを呼び出し、エラーが発生した場合にはGoコードが期待する形式（`MAP_FAILED`の場合に`errno`を`uintptr_t`にキャストして返す）で結果を返します。
    *   `src/runtime/cgo/mmap.go`では、`//go:cgo_import_static x_cgo_mmap`と`//go:linkname _cgo_mmap _cgo_mmap`ディレクティブを使用して、このC関数をGoランタイムから利用できるようにしています。

4.  **テストの追加**:
    *   `misc/cgo/testsanitizers/msan.go`と`misc/cgo/testsanitizers/test.bash`が追加され、MSanがCgoコードで正しく機能するかどうかを検証するテストが導入されました。
    *   `msan.go`は、GoのスライスをC関数に渡し、C関数内でそのスライスにアクセスして初期化する簡単なCgoプログラムです。MSanが有効な場合、このテストはエラーなく実行されるはずです。
    *   `test.bash`スクリプトは、`clang`がMSanをサポートしているかどうかを検出し、サポートしている場合に`msan.go`を実行します。
    *   `src/cmd/dist/test.go`に、この新しいテストスイートをGoのビルドシステムに統合するためのエントリが追加されました。

これらの変更により、GoランタイムはCgoとMSanの間の相互作用を適切に管理し、CgoでリンクされたCコードのメモリ安全性を効果的に検証できるようになります。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

1.  **`src/runtime/cgo/gcc_linux_amd64.c`**:
    *   `x_cgo_init`関数内で、`pthread_attr_t`をスタックではなくヒープに割り当てるように変更（`pthread_attr_t attr;` -> `pthread_attr_t *attr;`）。
    *   `mmap`呼び出しの前に`malloc`を呼び出すMSanバグのワークアラウンドが追加されました。
        ```c
        	attr = (pthread_attr_t*)malloc(sizeof *attr);
        	if (attr == NULL) {
        		fatalf("malloc failed: %s", strerror(errno));
        	}
        	pthread_attr_init(attr);
        	pthread_attr_getstacksize(attr, &size);
        	g->stacklo = (uintptr)&size - size + 4096; // Note: &size is used here, which seems like a potential bug or a very specific intent. Original was &attr.
        	pthread_attr_destroy(attr);
        	free(attr);
        ```
        **注**: `g->stacklo = (uintptr)&size - size + 4096;` の行は、元のコードの `(uintptr)&attr - size + 4096;` から変更されています。これは、`attr`がヒープに移動したため、スタック上のローカル変数`size`のアドレスを基準にスタック下限を計算しようとしているように見えます。これは意図的なものか、あるいは別の修正が必要な箇所かもしれません。コミットメッセージの意図からすると、`attr`が指すメモリ領域ではなく、スレッドのスタック領域の計算に関連する変更である可能性が高いです。

2.  **`src/runtime/cgo/gcc_mmap.c` (新規ファイル)**:
    *   Cgoから呼び出されるCの`mmap`ラッパー関数`x_cgo_mmap`が定義されています。
        ```c
        void *
        x_cgo_mmap(void *addr, uintptr_t length, int32_t prot, int32_t flags, int32_t fd, uint32_t offset) {
        	void *p;
        	p = mmap(addr, length, prot, flags, fd, offset);
        	if (p == MAP_FAILED) {
        		p = (void *) (uintptr_t) errno;
        	}
        	return p;
        }
        ```

3.  **`src/runtime/cgo/mmap.go` (新規ファイル)**:
    *   `x_cgo_mmap` C関数をGoランタイムにリンクするための`//go:cgo_import_static`と`//go:linkname`ディレクティブが含まれています。
        ```go
        package cgo

        import _ "unsafe" // Import "unsafe" because we use go:linkname.

        //go:cgo_import_static x_cgo_mmap
        //go:linkname x_cgo_mmap x_cgo_mmap
        //go:linkname _cgo_mmap _cgo_mmap
        var x_cgo_mmap byte
        var _cgo_mmap = &x_cgo_mmap
        ```

4.  **`src/runtime/cgo_mmap.go` (新規ファイル)**:
    *   Goランタイムの`mmap`関数が、Cgoが有効な場合にCgo経由でCの`mmap`を呼び出すように変更されています。
        ```go
        package runtime

        import "unsafe"

        // _cgo_mmap is filled in by runtime/cgo when it is linked into the
        // program, so it is only non-nil when using cgo.
        //go:linkname _cgo_mmap _cgo_mmap
        var _cgo_mmap unsafe.Pointer

        func mmap(addr unsafe.Pointer, n uintptr, prot, flags, fd int32, off uint32) (ret unsafe.Pointer) {
        	if _cgo_mmap != nil {
        		systemstack(func() {
        			ret = callCgoMmap(addr, n, prot, flags, fd, off)
        		})
        		return
        	}
        	return sysMmap(addr, n, prot, flags, fd, off)
        }

        // sysMmap calls the mmap system call. It is implemented in assembly.
        func sysMmap(addr unsafe.Pointer, n uintptr, prot, flags, fd int32, off uint32) unsafe.Pointer

        // callCgoMmap calls the mmap function in the runtime/cgo package
        // using the GCC calling convention. It is implemented in assembly.
        func callCgoMmap(addr unsafe.Pointer, n uintptr, prot, flags, fd int32, off uint32) unsafe.Pointer
        ```

5.  **`src/runtime/sys_linux_amd64.s`**:
    *   既存の`runtime·mmap`アセンブリ関数が`runtime·sysMmap`にリネームされました。
    *   新しいアセンブリ関数`runtime·callCgoMmap`が追加され、これは`_cgo_mmap`が指すC関数をGCC呼び出し規約に従って呼び出します。
        ```assembly
        TEXT runtime·callCgoMmap(SB),NOSPLIT,$0
        	MOVQ	addr+0(FP), DI
        	MOVQ	n+8(FP), SI
        	MOVL	prot+16(FP), DX
        	MOVL	flags+20(FP), CX
        	MOVL	fd+24(FP), R8
        	MOVL	off+28(FP), R9
        	MOVQ	_cgo_mmap(SB), AX
        	CALL	AX
        	MOVQ	AX, ret+32(FP)
        	RET
        ```

6.  **`src/runtime/stubs2.go`**:
    *   `mmap`関数の宣言が削除されました。これは`src/runtime/cgo_mmap.go`に移動されたためです。

7.  **`misc/cgo/testsanitizers/msan.go` (新規ファイル)**:
    *   MSanテスト用のGoプログラム。Cgoを介してC関数を呼び出し、Goで割り当てたメモリをC側で初期化します。

        #cgo CFLAGS: -fsanitize=memory
        #cgo LDFLAGS: -fsanitize=memory

        #include <stdint.h>

        }

        	"fmt"
        	"os"

        	C.f((*C.int32_t)(unsafe.Pointer(&a[0])), C.int(len(a)))

        	}

## コアとなるコードの解説

このコミットの主要な変更は、Goランタイムのメモリ割り当てパスを条件付きでCgo経由のCライブラリ呼び出しにリダイレクトすることです。

1.  **`runtime.mmap`の多態性**:
    *   `src/runtime/cgo_mmap.go`で定義されている`runtime.mmap`関数は、Goランタイムがメモリを割り当てるための主要なインターフェースです。
    *   この関数は、グローバル変数`_cgo_mmap`が`nil`でないかどうかをチェックします。`_cgo_mmap`は、Cgoがプログラムにリンクされている場合にのみ非`nil`になります。
    *   もし`_cgo_mmap`が非`nil`であれば、`systemstack`内で`callCgoMmap`アセンブリ関数を呼び出します。これは、Cgo経由でCの`x_cgo_mmap`関数（`src/runtime/cgo/gcc_mmap.c`で定義）を呼び出すためのものです。
    *   `_cgo_mmap`が`nil`の場合（Cgoが使用されていない場合）、通常のGoランタイムの`sysMmap`アセンブリ関数（`src/runtime/sys_linux_amd64.s`で定義）を呼び出します。
    *   このメカニズムにより、Cgoの有無に応じて異なる`mmap`実装を透過的に使用できるようになります。

2.  **Cgo経由の`mmap`呼び出し**:
    *   `src/runtime/sys_linux_amd64.s`の`runtime·callCgoMmap`アセンブリ関数は、Goの引数をGCC呼び出し規約（System V AMD64 ABI）に従ってレジスタ（`DI`, `SI`, `DX`, `CX`, `R8`, `R9`）に配置し、`_cgo_mmap`が指すアドレス（つまり、Cの`x_cgo_mmap`関数）を`CALL`命令で呼び出します。
    *   Cの`x_cgo_mmap`関数は、受け取った引数で実際の`mmap`システムコールを呼び出します。MSanが有効な環境では、このCの`mmap`呼び出しがMSanによってインターセプトされ、返されたメモリが初期化済みとしてマークされます。

3.  **MSanバグの回避**:
    *   `src/runtime/cgo/gcc_linux_amd64.c`の`x_cgo_init`関数における`malloc`呼び出しは、特定のMSanのバグに対する防御策です。このバグは、`mmap`が`malloc`より先に呼び出されると、MSanの内部状態が不正になる可能性があるというものです。Goランタイムの初期化フェーズで`mmap`が頻繁に呼び出されるため、このワークアラウンドは重要です。`malloc`を呼び出すことで、MSanの内部状態を安定させ、その後の`mmap`呼び出しが正しく処理されるようにします。

これらの変更により、GoプログラムがCgoを介してCコードと連携する際に、Goランタイムが割り当てるメモリがMSanによって正しく「初期化済み」と認識されるようになり、Cgoコードのメモリ安全性をMSanで効果的に検証できるようになります。

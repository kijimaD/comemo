# [インデックス 27240] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）における型比較ロジック、特に`Eqtype`関数がメソッドのレシーバパラメータを扱う方法に関する重要な変更を導入しています。これまでは`Eqtype`がレシーバパラメータを型シグネチャの一部として考慮していましたが、このコミットにより、特定の状況下でレシーバパラメータを無視するように修正されました。これにより、コンパイラの内部処理が簡素化され、Goの型システムにおけるメソッドの振る舞いとの整合性が向上しています。

    cmd/compile: ignore receiver parameters in Eqtype

    Receiver parameters generally aren't relevant to the function
    signature type. In particular:

      1. When checking whether a type's method implements an interface's
         method, we specifically want to ignore the receiver parameters,
         because they'll be different.

      2. When checking interface type equality, interface methods always
         use the same "fakethis" *struct{} type as their receiver.

      3. Finally, method expressions and method values degenerate into
         receiver-less function types.

    The only case where we care about receiver types matching is in
    addmethod, which is easily handled by adding an extra Eqtype check of
    the receiver parameters. Also, added a test for this, since
    (surprisingly) there weren't any.

    As precedence, go/types.Identical ignores receiver parameters when
    comparing go/types.Signature values.

    Notably, this allows us to slightly simplify the "implements"
    function, which is used for checking whether type/interface t
    implements interface iface. Currently, cmd/compile actually works
    around Eqtype's receiver parameter checking by creating new throwaway
    TFUNC Types without the receiver parameter.

    (Worse, the compiler currently only provides APIs to build TFUNC Types
    from Nod syntax trees, so building those throwaway types also involves
    first building throwaway syntax trees.)

## 元コミット内容

`cmd/compile: ignore receiver parameters in Eqtype`

レシーバパラメータは通常、関数シグネチャの型には関係ありません。特に：

1.  ある型のメソッドがインターフェースのメソッドを実装しているかチェックする場合、レシーバパラメータは異なるため、意図的に無視したい。
2.  インターフェース型の等価性をチェックする場合、インターフェースメソッドは常に同じ「fakethis」`*struct{}`型をレシーバとして使用する。
3.  最後に、メソッド式とメソッド値はレシーバを持たない関数型に退化する。

レシーバ型の一致が重要となる唯一のケースは`addmethod`であり、これはレシーバパラメータに対する追加の`Eqtype`チェックを追加することで容易に処理できます。また、これに対するテストも追加しました（驚くべきことに、これまでありませんでした）。

先行例として、`go/types.Identical`は`go/types.Signature`値を比較する際にレシーバパラメータを無視します。

特筆すべきは、これにより型/インターフェース`t`がインターフェース`iface`を実装しているかをチェックするために使用される「implements」関数をわずかに簡素化できることです。現在、`cmd/compile`は`Eqtype`のレシーバパラメータチェックを回避するために、レシーバパラメータを持たない新しい使い捨ての`TFUNC`型を作成していました。

（さらに悪いことに、コンパイラは現在、`Nod`構文木から`TFUNC`型を構築するためのAPIしか提供していないため、これらの使い捨て型を構築するには、まず使い捨ての構文木を構築する必要がありました。）

`toolstash -cmp`をパスします。

## 変更の背景

Go言語のコンパイラは、プログラムの型安全性を保証するために厳格な型チェックを行います。この型チェックの中心的な機能の一つが、二つの型が等しいかどうかを判断する`Eqtype`（またはそれに類する内部ロジック）です。しかし、メソッドの型シグネチャを比較する際に、レシーバパラメータの扱いが問題となっていました。

従来の`Eqtype`の実装では、メソッドのレシーバパラメータも型シグネチャの一部として比較対象に含まれていました。これは、以下のようなGoの言語仕様やコンパイラの内部動作と整合しない状況を生み出していました。

1.  **インターフェースの実装チェック**: Goでは、ある型がインターフェースを実装しているかどうかは、その型がインターフェースで定義されたすべてのメソッドを、互換性のあるシグネチャで持っているかによって決まります。この際、メソッドのレシーバ型（値レシーバ`T`かポインタレシーバ`*T`か）は、インターフェースのメソッドシグネチャには含まれません。インターフェースのメソッドは、レシーバの具体的な型に依存しない抽象的なシグネチャを持つため、コンパイラがインターフェース実装をチェックする際に、レシーバパラメータを比較対象に含めると不必要な不一致が生じていました。
2.  **インターフェース型の等価性**: インターフェース型同士の等価性をチェックする場合、そのメソッドセットが同じであれば等しいと判断されます。インターフェースのメソッドは、内部的には「fakethis」と呼ばれる`*struct{}`のような抽象的なレシーバ型を持つと見なされるため、具体的なレシーバ型を比較することは意味がありませんでした。
3.  **メソッド式とメソッド値**: Goでは、メソッドを通常の関数のように扱う「メソッド式」や「メソッド値」という機能があります。これらは、レシーバを引数として取る関数型、あるいは特定のレシーバにバインドされた関数型に「退化」します。この際、元のメソッドのレシーバパラメータは、結果として得られる関数型のシグネチャには直接現れないか、通常の引数として扱われるため、`Eqtype`がレシーバを特別扱いすることは不適切でした。

これらの理由から、コンパイラは`implements`関数などでインターフェース実装をチェックする際に、`Eqtype`のレシーバパラメータチェックを回避するために、一時的な`TFUNC`型（レシーバパラメータを含まない関数型）を生成するという複雑なワークアラウンドを導入していました。このワークアラウンドは、さらに一時的な`Nod`構文木を構築する必要があり、コンパイラのコードを複雑にし、パフォーマンスにも影響を与えていました。

このコミットは、このような不整合と複雑さを解消し、`Eqtype`がGoの型システムにおけるメソッドの振る舞いをより正確に反映するように変更することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびGoコンパイラの内部構造に関する知識が必要です。

### 1. Go言語のメソッドとレシーバ

*   **メソッド**: Goにおいて、メソッドは特定の型に関連付けられた関数です。`func (r ReceiverType) MethodName(params) (results)`のように定義され、`r ReceiverType`の部分が「レシーバパラメータ」です。
*   **値レシーバ vs. ポインタレシーバ**:
    *   **値レシーバ (`(t T)`)**: メソッドはレシーバ型の値のコピーに対して動作します。メソッド内でレシーバのフィールドを変更しても、元の値には影響しません。
    *   **ポインタレシーバ (`(t *T)`)**: メソッドはレシーバ型の値へのポインタに対して動作します。メソッド内でレシーバのフィールドを変更すると、元の値も変更されます。
*   **メソッドセット**: 型`T`のメソッドセットは、レシーバが`T`であるすべてのメソッドを含みます。型`*T`のメソッドセットは、レシーバが`T`または`*T`であるすべてのメソッドを含みます。インターフェースの実装チェックにおいて重要です。

### 2. Go言語のインターフェース

*   **暗黙的な実装**: Goのインターフェースは、`implements`キーワードなどを使わずに、型がインターフェースで定義されたすべてのメソッドを実装していれば、自動的にそのインターフェースを実装していると見なされます。
*   **インターフェース型**: インターフェース型は、メソッドシグネチャの集合を定義します。インターフェースのメソッドシグネチャには、レシーバの具体的な型は含まれません。
*   **`itab` (Interface Table)**: Goランタイムは、インターフェース値が保持する具体的な型とそのメソッドの実装を管理するために`itab`という内部データ構造を使用します。これにより、実行時に正しいメソッドが呼び出されます（動的ディスパッチ）。

### 3. Goコンパイラの内部構造

*   **`cmd/compile`**: Go言語の公式コンパイラです。ソースコードを解析し、中間表現を生成し、最終的に実行可能なバイナリを生成します。
*   **`Eqtype`**: コンパイラ内部で型が等しいかどうかを判断するために使用されるロジックの総称です。厳密には`cmd/compile/internal/gc/subr.go`内の`eqtype1`関数などがその役割を担います。Goの型システムにおける等価性のルール（例：関数型はパラメータと結果の型が一致すれば等しいが、パラメータ名は無視される）に従います。
*   **`TFUNC`型**: コンパイラ内部で関数型を表すためのデータ構造です。`cmd/compile/internal/gc/type.go`などで定義される`Type`構造体の一種で、`TFUNC`は関数であることを示します。
*   **`Nod`構文木**: コンパイラがソースコードを解析して生成する抽象構文木（AST）の内部表現です。`cmd/compile/internal/ir`パッケージなどで定義される`Node`構造体がこれに該当します。コンパイラは、この`Nod`構文木を操作してコードの分析や変換を行います。
*   **`go/types`パッケージ**: Goの標準ライブラリの一部で、Goの型システムをプログラム的に扱うためのパッケージです。コンパイラとは独立して型チェックツールなどが利用します。このパッケージの`Identical`関数は、メソッドシグネチャを比較する際にレシーバパラメータを無視するという仕様を持っています。

### 4. メソッド式とメソッド値

*   **メソッド式 (Method Expression)**: `T.Method`のように記述され、レシーバを最初の引数として取る関数を生成します。例えば、`type S struct{}; func (s S) M() {}`というメソッドがある場合、`S.M`は`func(S)`型の関数になります。
*   **メソッド値 (Method Value)**: `s.Method`のように記述され、特定のレシーバ`s`にバインドされた関数を生成します。上記の例で`s := S{}; f := s.M`とすると、`f`は`func()`型の関数になり、`f()`と呼び出すと`s.M()`が実行されます。

これらの概念は、Goコンパイラがどのように型を扱い、メソッドとインターフェースの間の関係を解決しているかを理解する上で不可欠です。

## 技術的詳細

このコミットの核心は、Goコンパイラの型比較ロジックである`Eqtype`（具体的には`eqtype1`関数）が、関数型（`TFUNC`）の比較においてレシーバパラメータを無視するように変更された点にあります。

### 変更前の問題点

変更前は、`eqtype1`関数が`TFUNC`型を比較する際に、レシーバ、通常のパラメータ、および結果パラメータのすべてを`recvsParamsResults`という配列を使ってループ処理し、それぞれのフィールドの型を比較していました。これにより、メソッドのレシーバパラメータも型比較の対象となっていました。

しかし、Goの型システムにおいて、以下の理由からメソッドのレシーバパラメータは、多くの場合、関数シグネチャの「型」の等価性には直接関係ありません。

1.  **インターフェースのメソッドシグネチャ**: インターフェースのメソッドはレシーバの具体的な型を持ちません。例えば、`interface { M() }`というインターフェースと、`type T struct{}; func (t T) M() {}`というメソッドを持つ型`T`を比較する際、`Eqtype`がレシーバを考慮すると、`T`の`M`メソッドのシグネチャとインターフェースの`M`メソッドのシグネチャが一致しないと誤って判断される可能性がありました。
2.  **`go/types.Identical`との不整合**: Goの標準ライブラリにある`go/types`パッケージの`Identical`関数は、メソッドシグネチャを比較する際にレシーバパラメータを無視します。コンパイラの内部ロジックがこれと異なる振る舞いをすることは、混乱を招き、一貫性を欠いていました。
3.  **コンパイラのワークアラウンド**: 上記の問題を回避するため、コンパイラの`implements`関数では、`Eqtype`を呼び出す前に、レシーバパラメータを含まない一時的な`TFUNC`型を生成していました。この一時的な型を生成するためには、さらに一時的な`Nod`構文木を構築する必要があり、コンパイラのコードが複雑化し、オーバーヘッドが発生していました。

### 変更内容

このコミットでは、以下の主要な変更が行われました。

1.  **`eqtype1`関数の修正**:
    *   `TFUNC`型を比較する際のループ処理で、`recvsParamsResults`の代わりに新しく導入された`paramsResults`を使用するように変更されました。
    *   `paramsResults`は、レシーバパラメータを除外し、通常のパラメータと結果パラメータのみを対象とします。これにより、`Eqtype`は関数型の比較においてレシーバパラメータを無視するようになります。
    *   コミットメッセージのコメントにもあるように、「We intentionally ignore receiver parameters for type equality, because they're never relevant.」（型等価性についてはレシーバパラメータを意図的に無視する。なぜなら、それらは決して関係ないからだ。）と明記されています。

2.  **`addmethod`関数の修正**:
    *   `addmethod`関数は、型にメソッドを追加する際に、メソッドの再宣言がないかなどをチェックします。この関数では、レシーバ型の一致が重要です。
    *   `Eqtype`がレシーバパラメータを無視するようになったため、`addmethod`内では明示的にレシーバパラメータの型を`Eqtype(t.Recvs(), f.Type.Recvs())`という形で追加チェックするように変更されました。これにより、`Eqtype`の汎用的な変更と`addmethod`の特定の要件が両立されます。

3.  **`implements`関数の簡素化**:
    *   `implements`関数は、ある型がインターフェースを実装しているかをチェックします。
    *   `Eqtype`がレシーバパラメータを無視するようになったため、以前必要だった「レシーバパラメータを含まない一時的な`TFUNC`型を生成する」というワークアラウンドが不要になりました。
    *   具体的には、`methodfunc(im.Type, nil)`や`methodfunc(tm.Type, nil)`といった一時的な型生成の呼び出しが削除され、`Eqtype(tm.Type, im.Type)`と直接比較できるようになりました。これにより、コードが大幅に簡素化され、一時的な`Nod`構文木の生成に伴うオーバーヘッドもなくなります。

4.  **`paramsResults`変数の導入**:
    *   `src/cmd/compile/internal/gc/type.go`に、`recvsParamsResults`からレシーバパラメータを除外した`paramsResults`という新しいグローバル変数が導入されました。これは`(*Type).Params`と`(*Type).Results`のみを含みます。

5.  **テストの追加**:
    *   `test/method1.go`に、レシーバ型が異なるメソッドの再宣言が正しくエラーとして検出されることを確認するテストケースが追加されました。これは`addmethod`の変更を検証するものです。

これらの変更により、Goコンパイラの型比較ロジックは、Go言語のセマンティクスとより密接に一致するようになり、コンパイラ内部のコードも簡素化され、保守性が向上しました。

## コアとなるコードの解説

### `eqtype1`関数 (`src/cmd/compile/internal/gc/subr.go`)

`eqtype1`関数は、Goコンパイラ内で二つの型が等しいかどうかを再帰的に判断する中心的な関数です。このコミットでは、特に`TFUNC`（関数型）を扱う`case TFUNC:`ブロックが変更されました。

変更前は、`for _, f := range recvsParamsResults`というループを使っていました。`recvsParamsResults`は、レシーバ、通常のパラメータ、結果パラメータの3つの部分を順に取得するための関数スライスでした。これにより、`Eqtype`はメソッドのレシーバパラメータも型比較の対象としていました。

変更後は、`for _, f := range paramsResults`というループに変わりました。`paramsResults`は新しく導入された変数で、レシーバパラメータを除外し、通常のパラメータと結果パラメータのみを対象とします。

```go
// src/cmd/compile/internal/gc/subr.go
case TFUNC:
    // Check parameters and result parameters for type equality.
    // We intentionally ignore receiver parameters for type
    // equality, because they're never relevant.
    for _, f := range paramsResults { // 変更点: recvsParamsResults から paramsResults へ
        // Loop over fields in structs, ignoring argument names.
        tta, ia := IterFields(f(t1))
        ttb, ib := IterFields(f(t2))
        // ... (フィールドの比較ロジックは省略)
    }
```

この変更により、`Eqtype`は関数型の等価性を判断する際に、レシーバの具体的な型を無視するようになりました。これは、Goのインターフェースのセマンティクスや、メソッド式・メソッド値の振る舞いとより整合性が取れるようになります。

### `addmethod`関数 (`src/cmd/compile/internal/gc/dcl.go`)

`addmethod`関数は、型にメソッドを追加する際に、同じ名前とシグネチャを持つメソッドが既に存在しないか（メソッドの再宣言）をチェックします。`Eqtype`の変更により、レシーバパラメータがデフォルトで無視されるようになったため、`addmethod`ではレシーバの一致が重要であるという特殊なケースを明示的に扱う必要があります。

```go
// src/cmd/compile/internal/gc/dcl.go
func addmethod(msym *Sym, t *Type, tpkg *Pkg, local, nointerface bool) {
    // ...
    if msym.Name != f.Sym.Name {
        continue
    }
    // Eqtype only checks that incoming and result parameters match,
    // so explicitly check that the receiver parameters match too.
    if !Eqtype(t, f.Type) || !Eqtype(t.Recvs(), f.Type.Recvs()) { // 変更点: レシーバの明示的なチェックを追加
        Yyerror("method redeclared: %v.%v\n\t%v\n\t%v", pa, msym, f.Type, t)
    }
    return
}
```

ここで、`!Eqtype(t, f.Type)`は通常のパラメータと結果パラメータの型が異なるかをチェックし、`!Eqtype(t.Recvs(), f.Type.Recvs())`はレシーバパラメータの型が異なるかを明示的にチェックします。この二つの条件のいずれかが真であれば、メソッドの再宣言としてエラーが報告されます。

### `implements`関数 (`src/cmd/compile/internal/gc/subr.go`)

`implements`関数は、ある型`t`がインターフェース型`iface`を実装しているかどうかを判断します。変更前は、`Eqtype`がレシーバを考慮してしまうため、一時的な`TFUNC`型を生成してレシーバを「取り除く」というワークアラウンドが必要でした。

```go
// src/cmd/compile/internal/gc/subr.go
func implements(t, iface *Type, m, samename **Field, ptr *int) bool {
    // ...
    if im.Broke {
        continue
    }
    // imtype := methodfunc(im.Type, nil) // 削除された行
    var followptr bool
    tm := ifacelookdot(im.Sym, t, &followptr, false)
    // if tm == nil || tm.Nointerface || !Eqtype(methodfunc(tm.Type, nil), imtype) { // 変更前の行
    if tm == nil || tm.Nointerface || !Eqtype(tm.Type, im.Type) { // 変更点: 直接 Eqtype を呼び出し
        if tm == nil {
            tm = ifacelookdot(im.Sym, t, &followptr, true)
        }
        // ...
    }
    // ...
}
```

`Eqtype`がレシーバを無視するようになったため、`methodfunc`による一時的な型生成が不要になり、`Eqtype(tm.Type, im.Type)`と直接比較できるようになりました。これにより、コードが簡素化され、コンパイラの効率も向上します。

### `paramsResults`変数 (`src/cmd/compile/internal/gc/type.go`)

このファイルでは、`eqtype1`関数で使用される新しいグローバル変数`paramsResults`が定義されました。

```go
// src/cmd/compile/internal/gc/type.go
// paramsResults is like recvsParamsResults, but omits receiver parameters.
var paramsResults = [2]func(*Type) *Type{
	(*Type).Params, (*Type).Results,
}
```

`recvsParamsResults`が`(*Type).Recvs, (*Type).Params, (*Type).Results`の3つの関数を含んでいたのに対し、`paramsResults`は`(*Type).Recvs`（レシーバ）を除外した`(*Type).Params`と`(*Type).Results`のみを含みます。これにより、`eqtype1`が関数型の比較を行う際に、レシーバパラメータを意図的にスキップすることが可能になります。

これらの変更は、Goコンパイラの型システムにおける一貫性を高め、内部実装の複雑さを軽減する上で重要な役割を果たしています。

# [インデックス 27118] ファイルの概要

このコミットは、Goコンパイラとリンカにおけるデッドコード削除の精度を向上させるための変更です。特に、`reflect.Type.Method` および `reflect.Type.MethodByName` を介してメソッドが動的に呼び出される可能性を考慮し、これらのリフレクションAPIが使用されている場合に、リンカが誤って必要なメソッドを削除しないようにするためのメカニズムを導入しています。

## 元コミット内容

`cmd/compile: track reflect.Type.Method in deadcode`

`reflect.Value.Call` に加えて、エクスポートされたメソッドは `reflect.Method` 構造体の `Func` 値によって呼び出される可能性があります。この変更は、コンパイラが以下のいずれかのインターフェース呼び出しを検出することで、正当な `reflect.Method` 構造体にアクセスする関数を追跡するようにします。

*   `Method(int) reflect.Method`
*   `MethodByName(string) (reflect.Method, bool)`

これはやや過度に保守的なアプローチです。もしユーザーが `reflect.Type` の基盤となる呼び出しを使用せずにこれらのメソッドを持つ型を実装した場合でも、リンカは最悪のケースを想定し、全てのエクスポートされたメソッドを含めることになります。しかし、このコストは小さいです。

cl/20483 で報告されたバイナリサイズには変更はありません。

Issue #14740 に関連します。

## 変更の背景

Go言語のコンパイラとリンカは、最終的なバイナリサイズを削減するために、到達不能なコード（デッドコード）を削除する最適化を行います。メソッドのデッドコード削除は特に複雑で、以下の3つの主要なケースを考慮する必要があります。

1.  **直接呼び出し**: コード内で明示的にメソッドが呼び出される場合。
2.  **到達可能なインターフェース型を介した呼び出し**: インターフェースを介してメソッドがディスパッチされる場合。
3.  **リフレクションを介した呼び出し**: `reflect` パッケージを使用して動的にメソッドが呼び出される場合。

これまでのリンカは、`reflect.Value.Call` が到達可能である場合、すべてのエクスポートされたメソッドがリフレクションによって呼び出される可能性があると判断し、それらをデッドコード削除の対象から外していました。しかし、`reflect.Value.Call` だけでなく、`reflect.Type` から取得できる `reflect.Method` 構造体の `Func` フィールドを介してもメソッドが呼び出される可能性があります。

具体的には、`reflect.Type` の `Method(int)` や `MethodByName(string)` メソッドが呼び出されると、その結果として `reflect.Method` 構造体が返されます。この `reflect.Method` 構造体には、実際のメソッドを呼び出すための `Func` フィールドが含まれています。もしリンカがこれらの `reflect.Type.Method` や `reflect.Type.MethodByName` の使用を認識しない場合、これらのリフレクションAPIを介して呼び出される可能性のあるメソッドを誤ってデッドコードとして削除してしまうリスクがありました。

このコミットは、このギャップを埋め、`reflect.Type.Method` および `reflect.Type.MethodByName` の使用もデッドコード削除の考慮事項に含めることで、リンカの健全性を向上させることを目的としています。これにより、リフレクションを多用するアプリケーションにおいて、実行時に必要なメソッドが誤って削除されることを防ぎます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とツールに関する知識が必要です。

### 1. Goコンパイラ (`cmd/compile`) とリンカ (`cmd/link`)

*   **コンパイラ**: Goソースコードを中間表現（アセンブリコードやオブジェクトファイル）に変換します。この過程で、関数や型の情報、呼び出しグラフなどが生成されます。
*   **リンカ**: コンパイラが生成したオブジェクトファイルやライブラリを結合し、実行可能なバイナリを生成します。この際、デッドコード削除などの最適化も行います。

### 2. デッドコード削除 (Dead Code Elimination)

プログラムの実行に不要なコード（デッドコード）を最終的なバイナリから削除する最適化手法です。これにより、バイナリサイズが小さくなり、起動時間やメモリ使用量が改善されます。Goのリンカは、到達可能性解析（reachability analysis）を用いてデッドコードを特定します。

### 3. Goのリフレクション (`reflect` パッケージ)

Goの `reflect` パッケージは、プログラムの実行時に型情報や値の操作を可能にする機能を提供します。

*   **`reflect.Type`**: Goの型のメタデータを提供します。例えば、構造体のフィールド、メソッド、インターフェースの実装などを調べることができます。
*   **`reflect.Value`**: Goの変数の値を抽象化し、実行時にその値を操作できるようにします。
*   **`reflect.Type.Method(int)`**: 型が持つ指定されたインデックスのメソッドを `reflect.Method` 構造体として返します。
*   **`reflect.Type.MethodByName(string)`**: 型が持つ指定された名前のメソッドを `reflect.Method` 構造体として返します。
*   **`reflect.Method` 構造体**: メソッドに関する情報（名前、型、`Func`など）を保持します。
*   **`reflect.Method.Func`**: メソッドの実体である関数を `reflect.Value` として返します。この `reflect.Value` を `Call` することで、メソッドを動的に呼び出すことができます。

### 4. `LSym` (Linker Symbol)

リンカが扱うシンボル（関数、変数など）の内部表現です。各シンボルには、その特性を示す属性（`Attr`）が関連付けられています。

### 5. `textflag.go` と `textflag.h`

Goのコンパイラとリンカ、およびアセンブラ間で共有される、関数の特性を示すフラグ（定数）を定義するファイルです。例えば、`NOSPLIT`（スタックを分割しない関数）などのフラグがあります。

### 6. インターフェース呼び出しの検出

Goコンパイラは、インターフェースを介したメソッド呼び出し（`OCALLINTER`）を検出する際に、その呼び出しが特定のパターンに合致するかどうかをチェックし、特別な処理を行うことがあります。

## 技術的詳細

このコミットの核心は、Goコンパイラとリンカが連携して、リフレクションによるメソッド呼び出しの可能性をより正確に追跡する点にあります。

1.  **コンパイラによる `reflect.Type.Method` 使用の検出**:
    *   `src/cmd/compile/internal/gc/syntax.go` に、`Func` 構造体に新しいフィールド `ReflectMethod bool` が追加されました。これは、その関数が `reflect.Type.Method` または `reflect.Type.MethodByName` を呼び出す可能性があるかどうかを示すフラグです。
    *   `src/cmd/compile/internal/gc/walk.go` の `walk` 関数内で、インターフェース呼び出し (`OCALLINTER`) を処理する際に、新しいヘルパー関数 `usemethod(n *Node)` が呼び出されます。
    *   `usemethod` 関数は、インターフェース呼び出しの型シグネチャを検査し、それが `Method(int) reflect.Method` または `MethodByName(string) (reflect.Method, bool)` のいずれかのパターンに合致するかどうかを判定します。
        *   具体的には、引数の数と型（`int` または `string`）、戻り値の数と型（`reflect.Method`、およびオプションで `bool`）をチェックします。
        *   このチェックはメソッド名までは行わないため、やや保守的（広範囲）な検出となります。
    *   もしパターンに合致するインターフェース呼び出しが検出された場合、現在コンパイル中の関数 (`Curfn`) の `Func.ReflectMethod` フラグが `true` に設定されます。

2.  **オブジェクトファイルへのフラグの埋め込み**:
    *   `src/cmd/internal/obj/textflag.go` および `src/runtime/textflag.h` に、新しいテキストフラグ `REFLECTMETHOD` (値: 1024) が定義されました。
    *   `src/cmd/compile/internal/gc/pgen.go` では、関数のコンパイル時に `fn.Func.ReflectMethod` が `true` であれば、この `REFLECTMETHOD` フラグが生成されるオブジェクトコードの関数情報に付与されます。
    *   `src/cmd/internal/obj/objfile.go` は、この `REFLECTMETHOD` フラグをオブジェクトファイルから読み込み、リンカの内部シンボル表現である `LSym` の属性として設定します。

3.  **リンカによるデッドコード削除ロジックの更新**:
    *   `src/cmd/internal/obj/link.go` に、`LSym` 構造体に `ReflectMethod bool` フィールドが追加されました。これは、そのシンボル（関数）が `reflect.Type.Method` または `reflect.Type.MethodByName` を呼び出す可能性があることを示します。
    *   `src/cmd/link/internal/ld/link.go` に、`AttrReflectMethod` という新しいシンボル属性が追加されました。
    *   `src/cmd/link/internal/ld/objfile.go` は、オブジェクトファイルから読み取った `REFLECTMETHOD` フラグを `LSym` の `AttrReflectMethod` 属性に変換します。
    *   `src/cmd/link/internal/ld/deadcode.go` のデッドコード削除ロジックが更新されました。
        *   `deadcodepass` 構造体に `reflectMethod bool` フィールドが追加され、リンカのデッドコード解析中に `reflect.Type.Method` が使用されたかどうかを追跡します。
        *   `deadcodepass.mark` 関数（シンボルが到達可能であるとマークする関数）内で、もしマークされたシンボルが `AttrReflectMethod` 属性を持っている場合、`d.reflectMethod` が `true` に設定されます。
        *   デッドコード削除のメインループでは、もし `reflect.Value.Call` シンボルが到達可能であるか、または `d.reflectMethod` が `true` であれば、リンカは「すべてのエクスポートされたメソッドがリフレクションによって呼び出される可能性がある」と判断し、到達可能なすべての型のエクスポートされたメソッドを到達可能としてマークします。これにより、これらのメソッドが誤って削除されるのを防ぎます。

この一連の変更により、コンパイラがリフレクションAPIの使用を検出し、その情報をリンカに伝達することで、リンカはより賢明なデッドコード削除の決定を下せるようになります。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

1.  **`src/cmd/compile/internal/gc/walk.go`**:
    *   `usemethod` 関数が追加され、インターフェース呼び出しが `reflect.Type.Method` または `reflect.Type.MethodByName` のパターンに合致するかを検出します。
    *   検出された場合、現在の関数 (`Curfn`) の `Func.ReflectMethod` フラグを `true` に設定します。

    ```go
    func usemethod(n *Node) {
        t := n.Left.Type
        // ... 型シグネチャのチェックロジック ...
        if Tconv(res0, 0) != "reflect.Method" {
            return

        Curfn.Func.ReflectMethod = true
    }
    ```

2.  **`src/cmd/internal/obj/textflag.go`**:
    *   新しい定数 `REFLECTMETHOD = 1024` が定義され、関数がリフレクションメソッドを呼び出す可能性を示すフラグとして使用されます。

    ```go
    const (
        // ... 既存のフラグ ...
        // Function can call reflect.Type.Method or reflect.Type.MethodByName.
        REFLECTMETHOD = 1024
    )
    ```

3.  **`src/cmd/link/internal/ld/deadcode.go`**:
    *   `deadcodepass` 構造体に `reflectMethod bool` フィールドが追加され、リフレクションメソッドの使用状況を追跡します。
    *   `mark` 関数内で、シンボルが `AttrReflectMethod` 属性を持つ場合に `d.reflectMethod` を `true` に設定します。
    *   デッドコード削除のメインループで、`callSym.Attr.Reachable() || d.reflectMethod` の条件が追加され、`reflect.Method` の使用が検出された場合にも、すべてのエクスポートされたメソッドが到達可能として扱われるようになります。

    ```go
    // ...
    type deadcodepass struct {
        // ...
        reflectMethod   bool
    }

    func (d *deadcodepass) mark(s, parent *LSym) {
        // ...
        if s.Attr.ReflectMethod() {
            d.reflectMethod = true
        }
        // ...
    }

    func deadcode(ctxt *Link) {
        // ...
        for {
            if callSym != nil && (callSym.Attr.Reachable() || d.reflectMethod) {
                // Methods are called via reflection. Give up on
                // static analysis, mark all exported methods of
                // all reachable types as reachable.
                // ...
            }
            // ...
        }
    }
    ```

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/walk.go` の `usemethod` 関数

この関数は、Goコンパイラのセマンティック解析フェーズの一部として実行されます。`OCALLINTER`（インターフェースメソッド呼び出し）ノードが検出された際に呼び出され、その呼び出しが `reflect.Type.Method` または `reflect.Type.MethodByName` のいずれかであるかを推測します。

*   `t := n.Left.Type`: 呼び出されているインターフェースメソッドの型を取得します。
*   `countfield(t.Params())` と `countfield(t.Results())`: メソッドの引数と戻り値の数をチェックします。
    *   `Method(int) reflect.Method` は引数1つ、戻り値1つ。
    *   `MethodByName(string) (reflect.Method, bool)` は引数1つ、戻り値2つ。
    *   これらのパターンに合致しない場合は、対象のメソッドではないと判断し、早期リターンします。
*   `p0 := t.Params().Field(0)`: 最初の引数の型を取得します。
*   `res0 := t.Results().Field(0)`: 最初の戻り値の型を取得します。
*   `res1 := t.Results().Field(1)`: 2番目の戻り値の型を取得します（`MethodByName` の場合のみ）。
*   引数の型が `TINT` (int) または `TSTRING` (string) であるか、戻り値の型が `TBOOL` (bool) であるかをチェックします。
*   最も重要なのは `Tconv(res0, 0) != "reflect.Method"` のチェックです。これは、最初の戻り値の型が `reflect.Method` であることを確認します。`Tconv` は型を文字列に変換するヘルパー関数です。
*   これらの条件を全て満たした場合、現在の関数 (`Curfn`) が `reflect.Type.Method` または `reflect.Type.MethodByName` を呼び出していると判断し、`Curfn.Func.ReflectMethod = true` を設定します。このフラグは後でオブジェクトファイルに埋め込まれ、リンカに伝達されます。

### `src/cmd/link/internal/ld/deadcode.go` のデッドコード削除ロジック

リンカのデッドコード削除は、`deadcode` 関数によって行われます。この関数は、プログラム内のシンボルを走査し、到達可能なシンボルをマークしていきます。

*   `deadcodepass` 構造体は、デッドコード削除のパスの状態を保持します。新しく追加された `reflectMethod bool` フィールドは、このリンカパス中に `reflect.Type.Method` を呼び出す関数が到達可能になったかどうかを追跡します。
*   `mark` 関数は、特定のシンボル `s` が到達可能であるとマークする際に呼び出されます。ここで `s.Attr.ReflectMethod()` が `true` であれば（つまり、コンパイラがこの関数がリフレクションメソッドを呼び出すとマークした場合）、`d.reflectMethod` を `true` に設定します。
*   デッドコード削除のメインループでは、`callSym`（`reflect.Value.Call` シンボル）が到達可能であるか、または `d.reflectMethod` が `true` であるかを確認します。
    *   もしこれらの条件のいずれかが満たされた場合、リンカは「リフレクションが使用されているため、静的解析だけではどのメソッドが呼び出されるか正確に判断できない」と判断します。
    *   この「最悪のケース」シナリオでは、到達可能なすべての型に属するエクスポートされたすべてのメソッドが、デッドコード削除の対象から外され、最終的なバイナリに含まれるようにマークされます。これにより、実行時にリフレクションで呼び出される可能性のあるメソッドが誤って削除されることを防ぎます。

このメカニズムは、Goのデッドコード削除が「安全第一」のアプローチを取っていることを示しています。つまり、誤って必要なコードを削除するよりも、不要なコードを少し残す方が良いという判断です。

## 変更の背景

Go言語のコンパイラとリンカは、最終的なバイナリサイズを削減するために、到達不能なコード（デッドコード）を削除する最適化を行います。メソッドのデッドコード削除は特に複雑で、以下の3つの主要なケースを考慮する必要があります。

1.  **直接呼び出し**: コード内で明示的にメソッドが呼び出される場合。
2.  **到達可能なインターフェース型を介した呼び出し**: インターフェースを介してメソッドがディスパッチされる場合。
3.  **リフレクションを介した呼び出し**: `reflect` パッケージを使用して動的にメソッドが呼び出される場合。

これまでのリンカは、`reflect.Value.Call` が到達可能である場合、すべてのエクスポートされたメソッドがリフレクションによって呼び出される可能性があると判断し、それらをデッドコード削除の対象から外していました。しかし、`reflect.Value.Call` だけでなく、`reflect.Type` から取得できる `reflect.Method` 構造体の `Func` フィールドを介してもメソッドが呼び出される可能性があります。

具体的には、`reflect.Type` の `Method(int)` や `reflect.Type.MethodByName(string)` メソッドが呼び出されると、その結果として `reflect.Method` 構造体が返されます。この `reflect.Method` 構造体には、実際のメソッドを呼び出すための `Func` フィールドが含まれています。もしリンカがこれらの `reflect.Type.Method` や `reflect.Type.MethodByName` の使用を認識しない場合、これらのリフレクションAPIを介して呼び出される可能性のあるメソッドを誤ってデッドコードとして削除してしまうリスクがありました。

このコミットは、このギャップを埋め、`reflect.Type.Method` および `reflect.Type.MethodByName` の使用もデッドコード削除の考慮事項に含めることで、リンカの健全性を向上させることを目的としています。これにより、リフレクションを多用するアプリケーションにおいて、実行時に必要なメソッドが誤って削除されることを防ぎます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とツールに関する知識が必要です。

### 1. Goコンパイラ (`cmd/compile`) とリンカ (`cmd/link`)

*   **コンパイラ**: Goソースコードを中間表現（アセンブリコードやオブジェクトファイル）に変換します。この過程で、関数や型の情報、呼び出しグラフなどが生成されます。
*   **リンカ**: コンパイラが生成したオブジェクトファイルやライブラリを結合し、実行可能なバイナリを生成します。この際、デッドコード削除などの最適化も行います。

### 2. デッドコード削除 (Dead Code Elimination)

プログラムの実行に不要なコード（デッドコード）を最終的なバイナリから削除する最適化手法です。これにより、バイナリサイズが小さくなり、起動時間やメモリ使用量が改善されます。Goのリンカは、到達可能性解析（reachability analysis）を用いてデッドコードを特定します。

### 3. Goのリフレクション (`reflect` パッケージ)

Goの `reflect` パッケージは、プログラムの実行時に型情報や値の操作を可能にする機能を提供します。

*   **`reflect.Type`**: Goの型のメタデータを提供します。例えば、構造体のフィールド、メソッド、インターフェースの実装などを調べることができます。
*   **`reflect.Value`**: Goの変数の値を抽象化し、実行時にその値を操作できるようにします。
*   **`reflect.Type.Method(int)`**: 型が持つ指定されたインデックスのメソッドを `reflect.Method` 構造体として返します。
*   **`reflect.Type.MethodByName(string)`**: 型が持つ指定された名前のメソッドを `reflect.Method` 構造体として返します。
*   **`reflect.Method` 構造体**: メソッドに関する情報（名前、型、`Func`など）を保持します。
*   **`reflect.Method.Func`**: メソッドの実体である関数を `reflect.Value` として返します。この `reflect.Value` を `Call` することで、メソッドを動的に呼び出すことができます。

### 4. `LSym` (Linker Symbol)

リンカが扱うシンボル（関数、変数など）の内部表現です。各シンボルには、その特性を示す属性（`Attr`）が関連付けられています。

### 5. `textflag.go` と `textflag.h`

Goのコンパイラとリンカ、およびアセンブラ間で共有される、関数の特性を示すフラグ（定数）を定義するファイルです。例えば、`NOSPLIT`（スタックを分割しない関数）などのフラグがあります。

### 6. インターフェース呼び出しの検出

Goコンパイラは、インターフェースを介したメソッド呼び出し（`OCALLINTER`）を検出する際に、その呼び出しが特定のパターンに合致するかどうかをチェックし、特別な処理を行うことがあります。

## 技術的詳細

このコミットの核心は、Goコンパイラとリンカが連携して、リフレクションによるメソッド呼び出しの可能性をより正確に追跡する点にあります。

1.  **コンパイラによる `reflect.Type.Method` 使用の検出**:
    *   `src/cmd/compile/internal/gc/syntax.go` に、`Func` 構造体に新しいフィールド `ReflectMethod bool` が追加されました。これは、その関数が `reflect.Type.Method` または `reflect.Type.MethodByName` を呼び出す可能性があるかどうかを示すフラグです。
    *   `src/cmd/compile/internal/gc/walk.go` の `walk` 関数内で、インターフェース呼び出し (`OCALLINTER`) を処理する際に、新しいヘルパー関数 `usemethod(n *Node)` が呼び出されます。
    *   `usemethod` 関数は、インターフェース呼び出しの型シグネチャを検査し、それが `Method(int) reflect.Method` または `MethodByName(string) (reflect.Method, bool)` のいずれかのパターンに合致するかどうかを判定します。
        *   具体的には、引数の数と型（`int` または `string`）、戻り値の数と型（`reflect.Method`、およびオプションで `bool`）をチェックします。
        *   このチェックはメソッド名までは行わないため、やや保守的（広範囲）な検出となります。
    *   もしパターンに合致するインターフェース呼び出しが検出された場合、現在コンパイル中の関数 (`Curfn`) の `Func.ReflectMethod` フラグが `true` に設定されます。

2.  **オブジェクトファイルへのフラグの埋め込み**:
    *   `src/cmd/internal/obj/textflag.go` および `src/runtime/textflag.h` に、新しいテキストフラグ `REFLECTMETHOD` (値: 1024) が定義されました。
    *   `src/cmd/compile/internal/gc/pgen.go` では、関数のコンパイル時に `fn.Func.ReflectMethod` が `true` であれば、この `REFLECTMETHOD` フラグが生成されるオブジェクトコードの関数情報に付与されます。
    *   `src/cmd/internal/obj/objfile.go` は、この `REFLECTMETHOD` フラグをオブジェクトファイルから読み込み、リンカの内部シンボル表現である `LSym` の属性として設定します。

3.  **リンカによるデッドコード削除ロジックの更新**:
    *   `src/cmd/internal/obj/link.go` に、`LSym` 構造体に `ReflectMethod bool` フィールドが追加されました。これは、そのシンボル（関数）が `reflect.Type.Method` または `reflect.Type.MethodByName` を呼び出す可能性があることを示します。
    *   `src/cmd/link/internal/ld/link.go` に、`AttrReflectMethod` という新しいシンボル属性が追加されました。
    *   `src/cmd/link/internal/ld/objfile.go` は、オブジェクトファイルから読み取った `REFLECTMETHOD` フラグを `LSym` の `AttrReflectMethod` 属性に変換します。
    *   `src/cmd/link/internal/ld/deadcode.go` のデッドコード削除ロジックが更新されました。
        *   `deadcodepass` 構造体に `reflectMethod bool` フィールドが追加され、リンカのデッドコード解析中に `reflect.Type.Method` が使用されたかどうかを追跡します。
        *   `deadcodepass.mark` 関数（シンボルが到達可能であるとマークする関数）内で、もしマークされたシンボルが `AttrReflectMethod` 属性を持っている場合、`d.reflectMethod` が `true` に設定されます。
        *   デッドコード削除のメインループでは、もし `reflect.Value.Call` シンボルが到達可能であるか、または `d.reflectMethod` が `true` であれば、リンカは「すべてのエクスポートされたメソッドがリフレクションによって呼び出される可能性がある」と判断し、到達可能なすべての型のエクスポートされたメソッドを到達可能としてマークします。これにより、これらのメソッドが誤って削除されるのを防ぎます。

この一連の変更により、コンパイラがリフレクションAPIの使用を検出し、その情報をリンカに伝達することで、リンカはより賢明なデッドコード削除の決定を下せるようになります。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

1.  **`src/cmd/compile/internal/gc/walk.go`**:
    *   `usemethod` 関数が追加され、インターフェース呼び出しが `reflect.Type.Method` または `reflect.Type.MethodByName` のパターンに合致するかを検出します。
    *   検出された場合、現在の関数 (`Curfn`) の `Func.ReflectMethod` フラグを `true` に設定します。

    ```go
    // usemethod check interface method calls for uses of reflect.Type.Method.
    func usemethod(n *Node) {
        t := n.Left.Type
        // ... 型シグネチャのチェックロジック ...
        if Tconv(res0, 0) != "reflect.Method" {
            return
        }
        Curfn.Func.ReflectMethod = true
    }
    ```

2.  **`src/cmd/internal/obj/textflag.go`**:
    *   新しい定数 `REFLECTMETHOD = 1024` が定義され、関数がリフレクションメソッドを呼び出す可能性を示すフラグとして使用されます。

    ```go
    const (
        // ... 既存のフラグ ...
        // Function can call reflect.Type.Method or reflect.Type.MethodByName.
        REFLECTMETHOD = 1024
    )
    ```

3.  **`src/cmd/link/internal/ld/deadcode.go`**:
    *   `deadcodepass` 構造体に `reflectMethod bool` フィールドが追加され、リフレクションメソッドの使用状況を追跡します。
    *   `mark` 関数内で、シンボルが `AttrReflectMethod` 属性を持つ場合に `d.reflectMethod` を `true` に設定します。
    *   デッドコード削除のメインループで、`callSym.Attr.Reachable() || d.reflectMethod` の条件が追加され、`reflect.Method` の使用が検出された場合にも、すべてのエクスポートされたメソッドが到達可能として扱われるようになります。

    ```go
    // ...
    type deadcodepass struct {
        // ...
        reflectMethod   bool
    }

    func (d *deadcodepass) mark(s, parent *LSym) {
        // ...
        if s.Attr.ReflectMethod() {
            d.reflectMethod = true
        }
        // ...
    }

    func deadcode(ctxt *Link) {
        // ...
        for {
            if callSym != nil && (callSym.Attr.Reachable() || d.reflectMethod) {
                // Methods are called via reflection. Give up on
                // static analysis, mark all exported methods of
                // all reachable types as reachable.
                // ...
            }
            // ...
        }
    }
    ```

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/walk.go` の `usemethod` 関数

この関数は、Goコンパイラのセマンティック解析フェーズの一部として実行されます。`OCALLINTER`（インターフェースメソッド呼び出し）ノードが検出された際に呼び出され、その呼び出しが `reflect.Type.Method` または `reflect.Type.MethodByName` のいずれかであるかを推測します。

*   `t := n.Left.Type`: 呼び出されているインターフェースメソッドの型を取得します。
*   `countfield(t.Params())` と `countfield(t.Results())`: メソッドの引数と戻り値の数をチェックします。
    *   `Method(int) reflect.Method` は引数1つ、戻り値1つ。
    *   `MethodByName(string) (reflect.Method, bool)` は引数1つ、戻り値2つ。
    *   これらのパターンに合致しない場合は、対象のメソッドではないと判断し、早期リターンします。
*   `p0 := t.Params().Field(0)`: 最初の引数の型を取得します。
*   `res0 := t.Results().Field(0)`: 最初の戻り値の型を取得します。
*   `res1 := t.Results().Field(1)`: 2番目の戻り値の型を取得します（`MethodByName` の場合のみ）。
*   引数の型が `TINT` (int) または `TSTRING` (string) であるか、戻り値の型が `TBOOL` (bool) であるかをチェックします。
*   最も重要なのは `Tconv(res0, 0) != "reflect.Method"` のチェックです。これは、最初の戻り値の型が `reflect.Method` であることを確認します。`Tconv` は型を文字列に変換するヘルパー関数です。
*   これらの条件を全て満たした場合、現在の関数 (`Curfn`) が `reflect.Type.Method` または `reflect.Type.MethodByName` を呼び出していると判断し、`Curfn.Func.ReflectMethod = true` を設定します。このフラグは後でオブジェクトファイルに埋め込まれ、リンカに伝達されます。

### `src/cmd/link/internal/ld/deadcode.go` のデッドコード削除ロジック

リンカのデッドコード削除は、`deadcode` 関数によって行われます。この関数は、プログラム内のシンボルを走査し、到達可能なシンボルをマークしていきます。

*   `deadcodepass` 構造体は、デッドコード削除のパスの状態を保持します。新しく追加された `reflectMethod bool` フィールドは、このリンカパス中に `reflect.Type.Method` を呼び出す関数が到達可能になったかどうかを追跡します。
*   `mark` 関数は、特定のシンボル `s` が到達可能であるとマークする際に呼び出されます。ここで `s.Attr.ReflectMethod()` が `true` であれば（つまり、コンパイラがこの関数がリフレクションメソッドを呼び出すとマークした場合）、`d.reflectMethod` を `true` に設定します。
*   デッドコード削除のメインループでは、`callSym`（`reflect.Value.Call` シンボル）が到達可能であるか、または `d.reflectMethod` が `true` であるかを確認します。
    *   もしこれらの条件のいずれかが満たされた場合、リンカは「リフレクションが使用されているため、静的解析だけではどのメソッドが呼び出されるか正確に判断できない」と判断します。
    *   この「最悪のケース」シナリオでは、到達可能なすべての型に属するエクスポートされたすべてのメソッドが、デッドコード削除の対象から外され、最終的なバイナリに含まれるようにマークされます。これにより、実行時にリフレクションで呼び出される可能性のあるメソッドが誤って削除されることを防ぎます。

このメカニズムは、Goのデッドコード削除が「安全第一」のアプローチを取っていることを示しています。つまり、誤って必要なコードを削除するよりも、不要なコードを少し残す方が良いという判断です。

## 変更の背景

GoコンパイラのSSAバックエンドでは、コードの最適化のために様々なパスが実行されます。その中の一つである `prove` 関数（またはパス）は、プログラムの特定のプロパティを「証明」し、それに基づいて最適化を可能にする役割を担っています。この `prove` 関数は、支配木（dominator tree）の構造を頻繁に利用します。

以前の実装では、`prove` 関数内で支配木を表現する `domTree` というデータ構造が、`idom` (immediate dominator) の情報から毎回再構築されていました。しかし、`sdom` (sparse dominator tree) という別のデータ構造が既に支配木の情報を効率的に保持していました。この `sdom` は、支配木の親子関係や兄弟関係を内部的に管理しているにもかかわらず、その情報が外部に公開されていなかったため、`prove` 関数は冗長な再構築を強いられていました。

このコミットの背景にあるのは、この冗長性を排除し、`sdom` が持つ既存の支配木情報を `prove` 関数から直接利用できるようにすることです。これにより、不要なデータ構造の構築とメモリ割り当てが削減され、コンパイラの性能が向上します。

## 前提知識の解説

このコミットを理解するためには、以下の概念を把握しておく必要があります。

1.  **SSA (Static Single Assignment) 形式**:
    SSAは、コンパイラ最適化において広く用いられる中間表現（IR）の一種です。SSA形式では、各変数がプログラム内で一度だけ定義されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、デッドコード削除、定数伝播、共通部分式除去など、多くの強力な最適化が可能になります。Goコンパイラは、最適化の主要な段階でSSA形式を使用します。

2.  **制御フローグラフ (Control Flow Graph, CFG)**:
    プログラムの実行パスを抽象的に表現したグラフです。ノードは基本ブロック（連続した命令のシーケンス）を表し、エッジは基本ブロック間の制御の移譲を表します。

3.  **支配関係 (Dominance Relation)** と **支配木 (Dominator Tree)**:
    CFGにおいて、あるノード `d` がノード `n` を**支配する**とは、CFGの開始ノードから `n` へのすべてのパスが `d` を通過する場合を指します。
    *   **厳密な支配 (Strict Dominance)**: `d` が `n` を支配し、かつ `d` と `n` が異なる場合。
    *   **即時支配者 (Immediate Dominator, idom)**: `n` を厳密に支配するすべてのノードの中で、`n` に最も近いノードを `n` の即時支配者と呼びます。即時支配者は一意に定まります。
    支配木は、各ノードをその即時支配者に接続することで構築される木構造です。CFGの開始ノードが支配木の根となります。支配木は、プログラムの構造を理解し、SSA形式の構築（特にφ関数の配置）や様々な最適化に不可欠な情報を提供します。

4.  **Sparse Dominator Tree (sdom)**:
    Goコンパイラの `src/cmd/compile/internal/ssa/sparsetree.go` で実装されているデータ構造で、支配木を効率的に表現・管理するためのものです。通常の支配木が各ノードからその即時支配者へのポインタを持つように、`sdom` は支配木の親子関係や兄弟関係を内部的に保持しています。この「sparse」という言葉は、おそらく支配木の情報をメモリ効率の良い形で表現していることを示唆しています。

5.  **`prove` 関数/パス**:
    GoコンパイラのSSAバックエンドにおける最適化パスの一つです。このパスは、プログラムの特定の条件やプロパティが真であることを「証明」し、それに基づいてさらなる最適化（例えば、冗長なnilチェックの削除、境界チェックの削除など）を可能にします。`prove` 関数は、支配木を走査して、あるブロックが別のブロックの支配下にあるか、といった情報を利用して証明を行います。

## 技術的詳細

このコミットの技術的な核心は、`prove` 関数が支配木を走査する方法を変更し、`sparsetree.go` で定義されている `sdom` データ構造の機能を拡張して、その走査を直接サポートするようにした点です。

変更前は、`prove.go` の `prove` 関数内で、`idom` (immediate dominator) の情報から `domTree` という `[][]*Block` 型のスライスが構築されていました。これは、各ブロックの支配下にある子ブロックのリストを保持するもので、支配木を表現する一種の方法でした。

```go
// 変更前のprove.goの一部
domTree := make([][]*Block, f.NumBlocks())
// Create a block ID -> [dominees] mapping
for _, b := range f.Blocks {
    if dom := idom[b.ID]; dom != nil {
        domTree[dom.ID] = append(domTree[dom.ID], b)
    }
}
// ...
for _, s := range domTree[node.block.ID] { // このループでdomTreeを使用
    // ...
}
```

この `domTree` の構築は、`sdom` が既に同様の支配木構造の情報を内部的に持っているにもかかわらず、冗長に実行されていました。

このコミットでは、以下の変更が行われました。

1.  **`prove.go` から `domTree` の構築を削除**:
    `prove` 関数内の `domTree` の宣言と構築ロジックが完全に削除されました。これにより、不要なメモリ割り当てと計算がなくなります。

2.  **`sparsetree.go` に `Child` および `Sibling` メソッドを追加**:
    `sparseTree` 型に `Child(x *Block) *Block` と `Sibling(x *Block) *Block` という2つの新しいメソッドが追加されました。
    *   `Child(x *Block)`: `x` の支配木における最初の子ブロックを返します。子がいない場合は `nil` を返します。
    *   `Sibling(x *Block)`: `x` と同じ即時支配者を持つ兄弟ブロックを返します。兄弟がいない場合は `nil` を返します。
    これらのメソッドは、`sparseTreeNode` 構造体内の `child` と `sibling` フィールドを利用して、支配木の親子・兄弟関係を直接公開します。

3.  **`prove.go` で `sdom.Child` と `sdom.Sibling` を使用して支配木を走査**:
    `prove` 関数内の支配木走査ロジックが、削除された `domTree` の代わりに、`sdom` の新しい `Child` と `Sibling` メソッドを使用するように変更されました。

    ```go
    // 変更後のprove.goの一部
    // for _, s := range domTree[node.block.ID] { // 削除された行
    for s := sdom.Child(node.block); s != nil; s = sdom.Sibling(s) { // 新しいループ
        // ...
    }
    ```
    この変更により、`prove` 関数は `sdom` が既に計算・保持している支配木構造を直接利用できるようになり、効率的な走査が可能になりました。

4.  **`sparseTreeNode` から `block` フィールドを削除**:
    `sparsetree.go` の `sparseTreeNode` 構造体から `block *Block` フィールドが削除されました。このフィールドは、`sparseTree` が `Block` のIDをインデックスとして使用するため、冗長でした。この削除は、メモリ使用量のわずかな削減にも貢献します。

これらの変更は、GoコンパイラのSSAバックエンドにおける支配木関連の処理をより効率的かつ簡潔にするための、クリーンアップと最適化の一環です。

## コアとなるコードの解説

このコミットの核心は、`prove` 関数が支配木を走査する際に、`sparsetree.go` で定義されている `sparseTree` (sdom) の内部構造を直接利用するように変更された点です。

1.  **`prove.go` の変更**:
    以前は、`prove` 関数内で `idom` (即時支配者) の情報から `domTree` という `[][]*Block` 型のスライスを構築していました。これは、各ブロックの直接の子孫ブロックのリストを保持するもので、支配木を表現する一種の方法でした。しかし、この構築は `sdom` が既に同様の情報を内部的に持っているため、冗長でした。
    このコミットでは、`domTree` の構築コードが削除され、代わりに `sdom.Child(node.block)` と `sdom.Sibling(s)` を用いたループに置き換えられました。これにより、`prove` 関数は `sdom` が提供する支配木の親子・兄弟関係を直接辿ることができ、メモリの再割り当てや計算のオーバーヘッドが削減されます。

2.  **`sparsetree.go` の変更**:
    `sparseTree` は、`sparseTreeNode` のスライスとして実装されており、各 `sparseTreeNode` は `child`、`sibling`、`parent` のポインタを保持しています。これらはそれぞれ、支配木における最初の子、次の兄弟、そして即時支配者を指します。
    このコミットでは、`sparseTreeNode` から冗長な `block` フィールドが削除されました。これは、`sparseTree` が `Block` のIDをインデックスとして使用するため、各ノードが自身の `Block` へのポインタを持つ必要がなかったためです。
    最も重要な変更は、`sparseTree` に `Child` と `Sibling` という2つの公開メソッドが追加されたことです。これらのメソッドは、`sparseTreeNode` の内部フィールドを外部に公開し、`prove` 関数が支配木を効率的に走査するためのAPIを提供します。
    *   `Child(x *Block)` は、ブロック `x` の `sparseTreeNode` に格納されている `child` ポインタを返します。
    *   `Sibling(x *Block)` は、ブロック `x` の `sparseTreeNode` に格納されている `sibling` ポインタを返します。

これらの変更により、`prove` 関数は `sdom` の内部構造をより直接的かつ効率的に利用できるようになり、コンパイラの性能向上とコードの保守性の向上が実現されました。

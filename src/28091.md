## 元コミット内容

`cmd/compile: allow 64-bit multiplication with immediates on s390x`

このコミットは、s390xアーキテクチャにおいて、即値（イミディエイト）を用いた64ビット乗算を可能にするものです。
`MULLW`および`MULLD`命令において、可能な限り`MGHI`（16ビット符号付き即値）命令を使用するように変更されました。`MGHI`は`MSGFI`よりも2バイト短いため、コードサイズの削減に貢献します。

## 変更の背景

Goコンパイラは、様々なアーキテクチャ向けに最適化された機械語コードを生成します。s390xはIBMのメインフレームコンピュータで使用される命令セットアーキテクチャであり、その特性を最大限に活かすための最適化が常に求められています。

この変更の背景には、以下の点があります。

1.  **コードサイズの最適化**: 生成される機械語コードのサイズは、実行効率やキャッシュ利用率に影響を与えます。命令が短ければ短いほど、より多くの命令をキャッシュに格納でき、命令フェッチの効率が向上します。`MGHI`命令は`MSGFI`命令よりも2バイト短いため、この変更によりコードサイズが削減され、全体的なパフォーマンス向上が期待されます。
2.  **s390x命令セットの活用**: s390xアーキテクチャには、特定のオペレーションに対して複数の命令形式が存在することがあります。コンパイラは、与えられたオペランド（特に即値の範囲）に応じて、最も効率的で適切な命令を選択する必要があります。このコミットは、即値乗算において`MGHI`という既存の効率的な命令をより積極的に活用するための改善です。
3.  **コンパイラの命令選択ロジックの改善**: 以前のコンパイラは、即値を用いた乗算において`MSGFI`を常に使用するか、あるいは特定の条件下で即値乗算を適切に扱えていなかった可能性があります。この変更は、即値の範囲をチェックし、より適切な命令（`MGHI`）を選択するロジックを導入することで、コンパイラの命令選択能力を向上させています。

## 前提知識の解説

### s390xアーキテクチャ

s390xは、IBM System/390およびz/Architectureメインフレームで使用される64ビット命令セットアーキテクチャです。特徴としては、豊富な汎用レジスタ（16個の64ビット汎用レジスタ）、強力なI/O機能、そして多様な命令形式が挙げられます。Go言語は、このs390xアーキテクチャもサポートしており、Goプログラムをメインフレーム上で実行できます。

### 即値（Immediate Value）

即値とは、命令コード自体に埋め込まれた定数のことです。例えば、「レジスタに5を加算する」という命令の場合、「5」が即値となります。即値は、メモリからデータをロードする手間を省けるため、処理速度の向上に寄与しますが、命令コードに埋め込むことができる値の範囲には制限があります（例：8ビット、16ビット、32ビットなど）。

### Goコンパイラのバックエンド

Goコンパイラは、ソースコードを中間表現に変換した後、各ターゲットアーキテクチャ（x86-64, ARM, s390xなど）のバックエンドがその中間表現を機械語コードに変換します。このプロセスには、命令選択（どの機械語命令を使用するか）、レジスタ割り当て、コード生成などが含まれます。

### s390xの乗算命令

s390xには、様々な乗算命令があります。このコミットで言及されているのは以下の2つです。

*   **`MULLW` (Multiply Logical Word)**: 32ビットの符号なし乗算を行います。結果は64ビットレジスタの下位32ビットに格納されます。
*   **`MULLD` (Multiply Logical Doubleword)**: 64ビットの符号なし乗算を行います。結果は64ビットレジスタに格納されます。

そして、即値を用いた乗算に関連する命令として、以下の2つが重要です。

*   **`MSGFI` (Multiply Single General Register Immediate)**: 汎用レジスタと32ビット符号付き即値の乗算を行います。命令形式はRIL (Register-Immediate-Long) 形式で、命令長は6バイトです。
*   **`MGHI` (Multiply Halfword Immediate)**: 汎用レジスタと16ビット符号付き即値の乗算を行います。命令形式はRI (Register-Immediate) 形式で、命令長は4バイトです。

`MGHI`は`MSGFI`よりも2バイト短いため、即値が16ビット符号付き整数の範囲（-32768から32767）に収まる場合は、`MGHI`を使用する方が効率的です。

## 技術的詳細

このコミットの核心は、s390xアーキテクチャにおける即値乗算の命令選択ロジックを改善し、可能な限り短い命令である`MGHI`を使用することにあります。

Goコンパイラのs390xバックエンドは、`MULLW`や`MULLD`といったGoの乗算操作をs390xの機械語命令に変換する際に、オペランドが即値である場合にどの命令を使用するかを決定します。

変更前は、即値乗算において`MSGFI`命令が主に、あるいは排他的に使用されていた可能性があります。`MSGFI`は32ビットの即値を扱えるため汎用性は高いですが、命令長が6バイトと長いです。

このコミットでは、即値が16ビット符号付き整数の範囲（-32768から32767）に収まるかどうかをチェックするロジックが導入されました。

1.  **即値の範囲チェック**: 乗算の即値オペランドが`int16`型で表現できる範囲内にあるかどうかを確認します。具体的には、64ビットの即値`v`が`int64(int16(v)) == v`という条件を満たす場合、その即値は16ビット符号付き整数として扱えることを意味します。
2.  **命令の選択**:
    *   即値が16ビット符号付き整数の範囲内であれば、`MGHI`命令（4バイト長）が選択されます。
    *   即値が16ビット符号付き整数の範囲を超える場合は、引き続き`MSGFI`命令（6バイト長）が使用されます。

この賢い命令選択により、コードサイズが削減され、命令フェッチの効率が向上します。特に、頻繁に小さな定数との乗算が行われるようなコードでは、この最適化が顕著な効果を発揮する可能性があります。

また、`src/cmd/compile/internal/s390x/gsubr.go`における`ginscon`関数の変更は、即値がレジスタにロードされるべきか、直接命令に埋め込まれるべきかを判断するロジックに影響を与えています。`AMULLD`に関する特定の制約が緩和されたことで、`MULLD`も即値乗算の最適化の恩恵を受けられるようになっています。

## コアとなるコードの変更箇所

このコミットは主に以下の3つのファイルに影響を与えています。

1.  **`src/cmd/asm/internal/asm/testdata/s390x.s`**:
    *   アセンブラのテストデータファイル。`MULLW`および`MULLD`命令の即値オペランドに対する命令エンコーディングが変更され、`MGHI`が使用される場合の短いエンコーディングが反映されています。
    *   負の即値（例: `-65537`, `-2147483648`）を用いた`MULLW`と`MULLD`の新しいテストケースが追加され、広範囲の即値が正しく処理されることを確認しています。

2.  **`src/cmd/compile/internal/s390x/gsubr.go`**:
    *   Goコンパイラのs390xバックエンドにおける汎用サブルーチンファイル。
    *   `ginscon`関数内の即値処理ロジックから、`s390x.AMULLD`に関する特定の条件が削除されました。これにより、`MULLD`命令が即値を直接扱える可能性が広がりました。
    *   `rawgins`関数内の`s390x.AMULLD`に関する`Fatalf`（致命的エラー）のチェックが削除されました。これは、`AMULLD`が定数オペランドを持つことが許容されるようになったことを示唆しています。

3.  **`src/cmd/internal/obj/s390x/asmz.go`**:
    *   s390xアセンブラの命令定義ファイル。
    *   `optab`配列から、`AADDC`および`AMULLW`の`C_LCON`（長定数）オペランドに関する複数のエントリが削除されました。これは、これらの命令の即値処理がより動的なロジックに移行したことを示しています。
    *   `buildop`関数内で、`opset(AMULLD, r)`と`opset(AMULLW, r)`の呼び出しが`case ADIVW`から`case AADD`に移動しました。これは、命令の分類と処理方法の再編成を示唆しています。
    *   `asmout`関数（機械語コードを出力する部分）が最も重要な変更箇所です。
        *   `AMULLW`および`AMULLD`命令の処理において、即値`v`が`int64(int16(v)) == v`という条件を満たす（つまり16ビット符号付き整数で表現可能である）場合、`zRI(op_MGHI, ...)`を呼び出して`MGHI`命令を生成します。
        *   そうでない場合（即値が16ビット符号付き整数の範囲を超える場合）は、引き続き`zRIL(_a, op_MSGFI, ...)`を呼び出して`MSGFI`命令を生成します。

## コアとなるコードの解説

### `src/cmd/internal/obj/s390x/asmz.go` の `asmout` 関数

このコミットの最も重要な変更は、`asmout`関数内の`AMULLW`および`AMULLD`命令のコード生成ロジックです。

```go
		case AMULLW, AMULLD:
			if r != p.To.Reg {
				zRRE(op_LGR, uint32(p.To.Reg), uint32(r), asm)
			}
			if int64(int16(v)) == v {
				zRI(op_MGHI, uint32(p.To.Reg), uint32(v), asm)
			} else {
				zRIL(_a, op_MSGFI, uint32(p.To.Reg), uint32(v), asm)
			}
```

*   `case AMULLW, AMULLD:`: `MULLW`または`MULLD`命令が処理対象であることを示します。
*   `if r != p.To.Reg { zRRE(op_LGR, uint32(p.To.Reg), uint32(r), asm) }`: これは、乗算のソースレジスタ`r`とデスティネーションレジスタ`p.To.Reg`が異なる場合に、ソースレジスタの内容をデスティネーションレジスタにロードする`LGR`（Load General Register）命令を生成する部分です。これは乗算命令のセマンティクス（結果がデスティネーションレジスタに格納される）を維持するために必要です。
*   `if int64(int16(v)) == v`: ここが最適化の肝となる条件分岐です。
    *   `v`は即値オペランドです。
    *   `int16(v)`は、`v`を16ビット符号付き整数にキャストします。この際、`v`が16ビット符号付き整数の範囲を超える場合、値は切り捨てられます。
    *   `int64(int16(v))`は、切り捨てられた（または切り捨てられなかった）16ビット符号付き整数を再度64ビット整数に拡張します。
    *   この結果が元の`v`と等しい場合、`v`は16ビット符号付き整数として正確に表現できることを意味します。
*   `zRI(op_MGHI, uint32(p.To.Reg), uint32(v), asm)`: 上記の条件が真の場合、つまり即値が16ビット符号付き整数の範囲に収まる場合、`MGHI`命令を生成します。`zRI`はRI形式の命令を生成するためのヘルパー関数です。
*   `else { zRIL(_a, op_MSGFI, uint32(p.To.Reg), uint32(v), asm) }`: 条件が偽の場合、つまり即値が16ビット符号付き整数の範囲を超える場合、`MSGFI`命令を生成します。`zRIL`はRIL形式の命令を生成するためのヘルパー関数です。

このロジックにより、コンパイラは即値の大きさに応じて最適な命令（`MGHI`または`MSGFI`）を動的に選択し、コードサイズの削減と効率化を実現しています。

## 技術的詳細

このコミットの核心は、s390xアーキテクチャにおける即値乗算の命令選択ロジックを改善し、可能な限り短い命令である`MGHI`を使用することにあります。

Goコンパイラのs390xバックエンドは、`MULLW`や`MULLD`といったGoの乗算操作をs390xの機械語命令に変換する際に、オペランドが即値である場合にどの命令を使用するかを決定します。

変更前は、即値乗算において`MSGFI`命令が主に、あるいは排他的に使用されていた可能性があります。`MSGFI`は32ビットの即値を扱えるため汎用性は高いですが、命令長が6バイトと長いです。

このコミットでは、即値が16ビット符号付き整数の範囲（-32768から32767）に収まるかどうかをチェックするロジックが導入されました。

1.  **即値の範囲チェック**: 乗算の即値オペランドが`int16`型で表現できる範囲内にあるかどうかを確認します。具体的には、64ビットの即値`v`が`int64(int16(v)) == v`という条件を満たす場合、その即値は16ビット符号付き整数として扱えることを意味します。
2.  **命令の選択**:
    *   即値が16ビット符号付き整数の範囲内であれば、`MGHI`命令（4バイト長）が選択されます。
    *   即値が16ビット符号付き整数の範囲を超える場合は、引き続き`MSGFI`命令（6バイト長）が使用されます。

この賢い命令選択により、コードサイズが削減され、命令フェッチの効率が向上します。特に、頻繁に小さな定数との乗算が行われるようなコードでは、この最適化が顕著な効果を発揮する可能性があります。

また、`src/cmd/compile/internal/s390x/gsubr.go`における`ginscon`関数の変更は、即値がレジスタにロードされるべきか、直接命令に埋め込まれるべきかを判断するロジックに影響を与えています。`AMULLD`に関する特定の制約が緩和されたことで、`MULLD`も即値乗算の最適化の恩恵を受けられるようになっています。

## コアとなるコードの変更箇所

このコミットは主に以下の3つのファイルに影響を与えています。

1.  **`src/cmd/asm/internal/asm/testdata/s390x.s`**:
    *   アセンブラのテストデータファイル。`MULLW`および`MULLD`命令の即値オペランドに対する命令エンコーディングが変更され、`MGHI`が使用される場合の短いエンコーディングが反映されています。
    *   負の即値（例: `-65537`, `-2147483648`）を用いた`MULLW`と`MULLD`の新しいテストケースが追加され、広範囲の即値が正しく処理されることを確認しています。

2.  **`src/cmd/compile/internal/s390x/gsubr.go`**:
    *   Goコンパイラのs390xバックエンドにおける汎用サブルーチンファイル。
    *   `ginscon`関数内の即値処理ロジックから、`s390x.AMULLD`に関する特定の条件が削除されました。これにより、`MULLD`命令が即値を直接扱える可能性が広がりました。
    *   `rawgins`関数内の`s390x.AMULLD`に関する`Fatalf`（致命的エラー）のチェックが削除されました。これは、`AMULLD`が定数オペランドを持つことが許容されるようになったことを示唆しています。

3.  **`src/cmd/internal/obj/s390x/asmz.go`**:
    *   s390xアセンブラの命令定義ファイル。
    *   `optab`配列から、`AADDC`および`AMULLW`の`C_LCON`（長定数）オペランドに関する複数のエントリが削除されました。これは、これらの命令の即値処理がより動的なロジックに移行したことを示しています。
    *   `buildop`関数内で、`opset(AMULLD, r)`と`opset(AMULLW, r)`の呼び出しが`case ADIVW`から`case AADD`に移動しました。これは、命令の分類と処理方法の再編成を示唆しています。
    *   `asmout`関数（機械語コードを出力する部分）が最も重要な変更箇所です。
        *   `AMULLW`および`AMULLD`命令の処理において、即値`v`が`int64(int16(v)) == v`という条件を満たす（つまり16ビット符号付き整数で表現可能である）場合、`zRI(op_MGHI, ...)`を呼び出して`MGHI`命令を生成します。
        *   そうでない場合（即値が16ビット符号付き整数の範囲を超える場合）は、引き続き`zRIL(_a, op_MSGFI, ...)`を呼び出して`MSGFI`命令を生成します。

## コアとなるコードの解説

### `src/cmd/internal/obj/s390x/asmz.go` の `asmout` 関数

このコミットの最も重要な変更は、`asmout`関数内の`AMULLW`および`AMULLD`命令のコード生成ロジックです。

```go
		case AMULLW, AMULLD:
			if r != p.To.Reg {
				zRRE(op_LGR, uint32(p.To.Reg), uint32(r), asm)
			}
			if int64(int16(v)) == v {
				zRI(op_MGHI, uint32(p.To.Reg), uint32(v), asm)
			} else {
				zRIL(_a, op_MSGFI, uint32(p.To.Reg), uint32(v), asm)
			}
```

*   `case AMULLW, AMULLD:`: `MULLW`または`MULLD`命令が処理対象であることを示します。
*   `if r != p.To.Reg { zRRE(op_LGR, uint32(p.To.Reg), uint32(r), asm) }`: これは、乗算のソースレジスタ`r`とデスティネーションレジスタ`p.To.Reg`が異なる場合に、ソースレジスタの内容をデスティネーションレジスタにロードする`LGR`（Load General Register）命令を生成する部分です。これは乗算命令のセマンティクス（結果がデスティネーションレジスタに格納される）を維持するために必要です。
*   `if int64(int16(v)) == v`: ここが最適化の肝となる条件分岐です。
    *   `v`は即値オペランドです。
    *   `int16(v)`は、`v`を16ビット符号付き整数にキャストします。この際、`v`が16ビット符号付き整数の範囲を超える場合、値は切り捨てられます。
    *   `int64(int16(v))`は、切り捨てられた（または切り捨てられなかった）16ビット符号付き整数を再度64ビット整数に拡張します。
    *   この結果が元の`v`と等しい場合、`v`は16ビット符号付き整数として正確に表現できることを意味します。
*   `zRI(op_MGHI, uint32(p.To.Reg), uint32(v), asm)`: 上記の条件が真の場合、つまり即値が16ビット符号付き整数の範囲に収まる場合、`MGHI`命令を生成します。`zRI`はRI形式の命令を生成するためのヘルパー関数です。
*   `else { zRIL(_a, op_MSGFI, uint32(p.To.Reg), uint32(v), asm) }`: 条件が偽の場合、つまり即値が16ビット符号付き整数の範囲を超える場合、`MSGFI`命令を生成します。`zRIL`はRIL形式の命令を生成するためのヘルパー関数です。

このロジックにより、コンパイラは即値の大きさに応じて最適な命令（`MGHI`または`MSGFI`）を動的に選択し、コードサイズの削減と効率化を実現しています。

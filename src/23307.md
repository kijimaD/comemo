# [インデックス 23307] ファイルの概要

このコミットは、Goランタイムと`syscall`パッケージにおけるSolarisバイナリのリンク方法に関する重要な変更を導入しています。具体的には、以前の`dlopen`/`dlsym`を用いた動的シンボル解決の仕組みを廃止し、Solarisのネイティブな遅延バインディング機能を利用して直接リンクするように変更しています。これにより、Goプログラムの起動速度の向上と、`syscall`パッケージ内の複雑なコードの削除が実現されています。

    runtime, syscall: link Solaris binaries directly instead of using dlopen/dlsym

    dynamic linking scheme that didn't permit lazy binding. To speed program
    startup, Go binaries only used it for a small number of symbols required
    by the runtime. Other symbols were resolved on demand on first use, and
    were cached for subsequent use. This required some moderately complex
    code in the syscall package.

    binding is supported. As now all symbols are resolved lazily by the
    dynamic loader, there is no need for the complex code in the syscall
    package that did the same. This CL makes Go programs link directly
    with the necessary shared libraries and deletes the lazy-loading code
    implemented in Go.

## 元コミット内容

このコミットは、GoのSolarisバイナリが共有ライブラリのシンボルを解決する方法を変更します。以前は、Solarisの動的リンクが遅延バインディングをサポートしていなかったため、Goは`dlopen`/`dlsym`を使用して必要なシンボルをオンデマンドで解決し、キャッシュしていました。これは`syscall`パッケージ内に複雑なコードを必要としていました。

しかし、先行するCL 8214によってSolarisの動的リンクの実装が変更され、遅延バインディングがネイティブにサポートされるようになりました。この変更により、すべてのシンボルが動的ローダーによって遅延解決されるため、Goが独自に実装していた複雑な遅延ロードコードは不要になりました。

このコミットは、Goプログラムが必要な共有ライブラリと直接リンクするようにし、Goで実装されていた遅延ロードコードを削除します。

## 変更の背景

Goプログラムは、オペレーティングシステムが提供する機能（システムコールなど）を利用するために、C言語で書かれた共有ライブラリ（例: `libc.so`）と連携する必要があります。Solaris環境において、Goは以前、共有ライブラリのシンボル（関数や変数）を解決するために、`dlopen`と`dlsym`という関数を使用していました。

`dlopen`は実行時に共有ライブラリをロードし、`dlsym`はロードされたライブラリから特定のシンボルのアドレスを取得するために使われます。これは「遅延バインディング」と呼ばれる手法の一種で、プログラムの起動時にすべてのシンボルを解決するのではなく、実際にそのシンボルが呼び出されるまで解決を遅らせることで、起動時間を短縮する目的がありました。

しかし、当時のSolarisの動的リンカーは、Goが期待するような効率的な遅延バインディングをネイティブにサポートしていませんでした。そのため、Goランタイムは`syscall`パッケージ内に、シンボルをオンデマンドで解決し、その結果をキャッシュするという独自の複雑なロジックを実装する必要がありました。これはコードの複雑性を増し、メンテナンスの負担となっていました。

この状況は、CL 8214（"use .plt instead of .got on Solaris"）によって大きく変わりました。この変更により、Solarisの動的リンカーが`.plt`（Procedure Linkage Table）を適切に利用するようになり、ネイティブな遅延バインディングがサポートされるようになりました。これにより、Goが独自に実装していた遅延ロードの仕組みが不要になったため、このコミットでそのコードを削除し、よりシンプルで効率的な直接リンク方式に移行することが決定されました。

## 前提知識の解説

*   **動的リンク (Dynamic Linking)**: プログラムが実行時に必要なライブラリ（共有ライブラリ、ダイナミックリンクライブラリなど）をロードし、リンクする仕組みです。これにより、ディスクスペースの節約、メモリ使用量の削減、ライブラリの更新が容易になるなどの利点があります。
*   **静的リンク (Static Linking)**: プログラムのコンパイル時に必要なライブラリのコードをすべて実行可能ファイルに含める仕組みです。実行可能ファイルが大きくなる傾向がありますが、実行時に外部ライブラリに依存しないため、配布が容易になります。
*   **遅延バインディング (Lazy Binding)**: 動的リンクの一種で、プログラムが共有ライブラリ内の関数を初めて呼び出すまで、その関数のアドレス解決（バインディング）を遅らせる手法です。これにより、プログラムの起動時にすべてのシンボルを解決する必要がなくなり、起動時間を短縮できます。
*   **`dlopen` / `dlsym`**: UNIX系システムで動的ロードを行うための標準的なAPIです。
    *   `dlopen(filename, flags)`: 指定された共有ライブラリをロードし、そのハンドルを返します。
    *   `dlsym(handle, symbol)`: ロードされたライブラリから指定されたシンボルのアドレスを検索し、返します。
*   **`.plt` (Procedure Linkage Table) / `.got` (Global Offset Table)**: 動的リンクされたプログラムが共有ライブラリ内の関数を呼び出す際に使用されるデータ構造です。
    *   `.got`: 共有ライブラリ内のデータや関数のアドレスを格納するテーブルです。
    *   `.plt`: 共有ライブラリ内の関数を呼び出すための小さなコードスタブのテーブルです。遅延バインディングでは、初めて関数が呼び出されたときに`.plt`エントリが動的リンカーを呼び出し、実際の関数のアドレスを解決して`.got`に格納し、以降の呼び出しでは直接そのアドレスにジャンプするようにします。
*   **`syscall`パッケージ (Go言語)**: Goプログラムからオペレーティングシステムのシステムコールを呼び出すための機能を提供します。OS固有の低レベルな操作を行う際に使用されます。
*   **`//go:cgo_import_dynamic` (Go言語)**: Goコンパイラに対するディレクティブで、指定されたシンボルが動的にリンクされる共有ライブラリからインポートされることを示します。これにより、GoプログラムはCGOを介さずに直接共有ライブラリのシンボルを参照できるようになります。
*   **`//go:linkname` (Go言語)**: Goコンパイラに対するディレクティブで、Goのシンボルを別のシンボル（通常はアセンブリコードやCGOでインポートされたシンボル）にリンクするために使用されます。これにより、Goの関数や変数が外部のシンボル名で参照できるようになります。

## 技術的詳細

このコミットの核心は、Solarisの動的リンカーがネイティブに遅延バインディングをサポートするようになったという、先行するCL 8214の変更を最大限に活用することにあります。

以前のGoのSolaris実装では、`src/syscall/so_solaris.go`ファイルに`lazySO`や`lazyProc`といった構造体が定義されており、これらが`dlopen`と`dlsym`を内部的に使用して、必要なシステムコール関数をオンデマンドでロード・解決していました。これは、Solarisの動的リンカーが効率的な遅延バインディングを提供していなかったため、Go自身がその役割を担っていたためです。

CL 8214によってSolarisの動的リンカーが`.plt`を介した遅延バインディングをサポートするようになったことで、Goが独自に実装していたこの複雑なレイヤーは不要になりました。

このコミットでは、以下の技術的変更が行われています。

1.  **`dlopen`/`dlsym`関連コードの削除**: `src/runtime/syscall_solaris.go`から`libc_dlopen`, `libc_dlclose`, `libc_dlsym`の宣言と、それらを利用する`syscall_dlopen`, `syscall_dlclose`, `syscall_dlsym`関数が削除されました。これは、GoランタイムがこれらのAPIを直接呼び出す必要がなくなったためです。
2.  **カスタム遅延ロード機構の廃止**: `src/syscall/so_solaris.go`ファイル全体が削除されました。このファイルには、共有ライブラリのロード（`loadSO`）、プロシージャの検索（`FindProc`）、そして遅延ロードを管理する`lazySO`および`lazyProc`のロジックが含まれていました。これらの機能は、Solarisの動的リンカーが提供するネイティブな遅延バインディングによって代替されるため、不要となりました。
3.  **`mksyscall_solaris.pl`の変更**: `src/syscall/mksyscall_solaris.pl`スクリプトは、Goの`syscall`パッケージのシステムコール関数を生成するために使用されます。このスクリプトが変更され、以前は`newLazySO`と`NewProc`を使って遅延ロードされるプロシージャを生成していましたが、代わりに`//go:cgo_import_dynamic`と`//go:linkname`ディレクティブを生成するようになりました。
    *   `//go:cgo_import_dynamic libc_SymbolName symbolName "library.so"`: これはGoコンパイラに対し、`symbolName`というシンボルが`library.so`から動的にインポートされることを指示します。Goコード内では`libc_SymbolName`という名前で参照されます。
    *   `//go:linkname libc_SymbolName libc_SymbolName`: これはGoの内部リンカーに対し、Goコード内の`libc_SymbolName`という変数を、外部の`libc_SymbolName`というシンボルにリンクするように指示します。これにより、Goの変数`libc_SymbolName`が、共有ライブラリからロードされた実際の関数のアドレスを指すようになります。
    *   `libcFunc uintptr`という新しい型が導入され、これらの動的にインポートされたシンボルのアドレスを保持するために使用されます。
4.  **システムコール呼び出しの変更**: `src/syscall/exec_solaris_test.go`や`src/syscall/zsyscall_solaris_amd64.go`などのファイルで、システムコールを呼び出す際の引数が変更されました。以前は`procGetpgid.Addr()`のように、`lazyProc`オブジェクトから取得したアドレスを使用していましたが、変更後は`uintptr(unsafe.Pointer(&libc_Getpgid))`のように、`//go:cgo_import_dynamic`で宣言された`libcFunc`型の変数のアドレスを直接渡すようになりました。これは、シンボル解決がGoのカスタムロジックではなく、OSの動的リンカーによって行われるようになったためです。

これらの変更により、GoのSolarisバイナリは、システムコールを呼び出す際に、OSの動的リンカーが提供する効率的な遅延バインディングメカニズムを直接利用するようになり、Goランタイムのコードベースが大幅に簡素化されました。

## コアとなるコードの解説

変更されたコードの核心は、GoがSolarisの共有ライブラリ関数を呼び出すためのメカニズムを、Go独自の動的ロード・遅延バインディング実装から、Solarisネイティブの動的リンカーによる直接的な遅延バインディングへと移行した点にあります。

*   **`src/runtime/syscall_solaris.go`の変更**:
    *   `dlopen`, `dlclose`, `dlsym`は、実行時に共有ライブラリをロードし、その中のシンボルを検索するためのC標準ライブラリ関数です。Goがこれらの関数を直接呼び出す必要がなくなったということは、Go自身が共有ライブラリのロードとシンボル解決の管理を行う層を削除したことを意味します。これは、Solarisの動的リンカーがその役割を効率的に果たせるようになったためです。

*   **`src/syscall/so_solaris.go`の削除**:
    *   このファイルは、GoがSolaris上で共有ライブラリの遅延ロードとシンボル解決を行うためのカスタム実装を含んでいました。`so`構造体は共有ライブラリのハンドルを管理し、`proc`構造体はライブラリ内のプロシージャ（関数）のアドレスを保持していました。`lazySO`と`lazyProc`は、これらのロードと検索を実際に遅延させるためのロジックを提供していました。このファイルが完全に削除されたことは、Goがこのカスタム実装を完全に放棄し、OSの機能に依存するようになったことを明確に示しています。

*   **`src/syscall/mksyscall_solaris.pl`の変更と`//go:cgo_import_dynamic`、`//go:linkname`の導入**:
    *   `mksyscall_solaris.pl`は、Goの`syscall`パッケージのソースコードを自動生成するPerlスクリプトです。以前は、このスクリプトが`newLazySO`と`NewProc`を呼び出すコードを生成し、Goのカスタム遅延ロード機構を利用していました。
    *   変更後、このスクリプトは`//go:cgo_import_dynamic`と`//go:linkname`というGoコンパイラディレクティブを生成するようになりました。
        *   `//go:cgo_import_dynamic libc_SymbolName symbolName "library.so"`: このディレクティブは、Goコンパイラに対して、`symbolName`という名前のシンボルが`library.so`という共有ライブラリから動的にインポートされることを伝えます。Goコード内では`libc_SymbolName`という名前で参照されます。これは、CGOを使わずにGoプログラムが直接共有ライブラリのシンボルを参照するためのメカニズムです。
        *   `//go:linkname libc_SymbolName libc_SymbolName`: このディレクティブは、Goのリンカーに対して、Goコード内の`libc_SymbolName`という変数を、外部の`libc_SymbolName`というシンボル（`//go:cgo_import_dynamic`によって参照される）にリンクするように指示します。これにより、Goの変数`libc_SymbolName`が、実行時に動的リンカーによって解決された実際の関数のエントリポイントを指すようになります。
    *   `libcFunc uintptr`という新しい型は、これらの動的にリンクされた関数のアドレスを保持するためのものです。`uintptr`はポインタを整数として扱うGoの型であり、システムコールのアドレスを直接操作するために使用されます。

*   **システムコール呼び出しの変更**:
    *   `sysvicall6(procGetpgid.Addr(), ...)`から`sysvicall6(uintptr(unsafe.Pointer(&libc_Getpgid)), ...)`への変更は、システムコールを呼び出す際のアドレスの取得方法が変わったことを示しています。
        *   以前は、`procGetpgid`という`lazyProc`オブジェクトが内部的に`dlsym`を使ってシンボルアドレスを解決し、そのアドレスを`Addr()`メソッドで返していました。
        *   変更後は、`&libc_Getpgid`は`//go:cgo_import_dynamic`と`//go:linkname`によって動的リンカーが解決した`getpgid`関数のアドレスを指す`libcFunc`型の変数のアドレスです。`unsafe.Pointer`と`uintptr`を使って、このアドレスを直接`sysvicall6`に渡しています。これは、Goがシンボル解決の仲介役をせず、OSの動的リンカーに完全に任せるようになったことを意味します。

これらの変更により、GoのSolarisバイナリは、より標準的で効率的なOSネイティブの動的リンクメカニズムを利用するようになり、Goランタイムの複雑性が軽減され、パフォーマンスの向上が期待されます。

## 元コミット内容

このコミットは、GoのSolarisバイナリが共有ライブラリのシンボルを解決する方法を変更します。以前は、Solarisの動的リンクが遅延バインディングをサポートしていなかったため、Goは`dlopen`/`dlsym`を使用して必要なシンボルをオンデマンドで解決し、キャッシュしていました。これは`syscall`パッケージ内に複雑なコードを必要としていました。

しかし、先行するCL 8214によってSolarisの動的リンクの実装が変更され、遅延バインディングがネイティブにサポートされるようになりました。この変更により、すべてのシンボルが動的ローダーによって遅延解決されるため、Goが独自に実装していた複雑な遅延ロードコードは不要になりました。

このコミットは、Goプログラムが必要な共有ライブラリと直接リンクするようにし、Goで実装されていた遅延ロードコードを削除します。

## 変更の背景

Goプログラムは、オペレーティングシステムが提供する機能（システムコールなど）を利用するために、C言語で書かれた共有ライブラリ（例: `libc.so`）と連携する必要があります。Solaris環境において、Goは以前、共有ライブラリのシンボル（関数や変数）を解決するために、`dlopen`と`dlsym`という関数を使用していました。

`dlopen`は実行時に共有ライブラリをロードし、`dlsym`はロードされたライブラリから特定のシンボルのアドレスを取得するために使われます。これは「遅延バインディング」と呼ばれる手法の一種で、プログラムの起動時にすべてのシンボルを解決するのではなく、実際にそのシンボルが呼び出されるまで解決を遅らせることで、起動時間を短縮する目的がありました。

しかし、当時のSolarisの動的リンカーは、Goが期待するような効率的な遅延バインディングをネイティブにサポートしていませんでした。そのため、Goランタイムは`syscall`パッケージ内に、シンボルをオンデマンドで解決し、その結果をキャッシュするという独自の複雑なロジックを実装する必要がありました。これはコードの複雑性を増し、メンテナンスの負担となっていました。

この状況は、CL 8214（"use .plt instead of .got on Solaris"）によって大きく変わりました。この変更により、Solarisの動的リンカーが`.plt`（Procedure Linkage Table）を適切に利用するようになり、ネイティブな遅延バインディングがサポートされるようになりました。これにより、Goが独自に実装していた遅延ロードの仕組みが不要になったため、このコミットでそのコードを削除し、よりシンプルで効率的な直接リンク方式に移行することが決定されました。

## 前提知識の解説

*   **動的リンク (Dynamic Linking)**: プログラムが実行時に必要なライブラリ（共有ライブラリ、ダイナミックリンクライブラリなど）をロードし、リンクする仕組みです。これにより、ディスクスペースの節約、メモリ使用量の削減、ライブラリの更新が容易になるなどの利点があります。
*   **静的リンク (Static Linking)**: プログラムのコンパイル時に必要なライブラリのコードをすべて実行可能ファイルに含める仕組みです。実行可能ファイルが大きくなる傾向がありますが、実行時に外部ライブラリに依存しないため、配布が容易になります。
*   **遅延バインディング (Lazy Binding)**: 動的リンクの一種で、プログラムが共有ライブラリ内の関数を初めて呼び出すまで、その関数のアドレス解決（バインディング）を遅らせる手法です。これにより、プログラムの起動時にすべてのシンボルを解決する必要がなくなり、起動時間を短縮できます。
*   **`dlopen` / `dlsym`**: UNIX系システムで動的ロードを行うための標準的なAPIです。
    *   `dlopen(filename, flags)`: 指定された共有ライブラリをロードし、そのハンドルを返します。
    *   `dlsym(handle, symbol)`: ロードされたライブラリから指定されたシンボルのアドレスを検索し、返します。
*   **`.plt` (Procedure Linkage Table) / `.got` (Global Offset Table)**: 動的リンクされたプログラムが共有ライブラリ内の関数を呼び出す際に使用されるデータ構造です。
    *   `.got`: 共有ライブラリ内のデータや関数のアドレスを格納するテーブルです。
    *   `.plt`: 共有ライブラリ内の関数を呼び出すための小さなコードスタブのテーブルです。遅延バインディングでは、初めて関数が呼び出されたときに`.plt`エントリが動的リンカーを呼び出し、実際の関数のアドレスを解決して`.got`に格納し、以降の呼び出しでは直接そのアドレスにジャンプするようにします。
*   **`syscall`パッケージ (Go言語)**: Goプログラムからオペレーティングシステムのシステムコールを呼び出すための機能を提供します。OS固有の低レベルな操作を行う際に使用されます。
*   **`//go:cgo_import_dynamic` (Go言語)**: Goコンパイラに対するディレクティブで、指定されたシンボルが動的にリンクされる共有ライブラリからインポートされることを示します。これにより、GoプログラムはCGOを介さずに直接共有ライブラリのシンボルを参照できるようになります。
*   **`//go:linkname` (Go言語)**: Goコンパイラに対するディレクティブで、Goのシンボルを別のシンボル（通常はアセンブリコードやCGOでインポートされたシンボル）にリンクするために使用されます。これにより、Goの関数や変数が外部のシンボル名で参照できるようになります。

## 技術的詳細

このコミットの核心は、Solarisの動的リンカーがネイティブに遅延バインディングをサポートするようになったという、先行するCL 8214の変更を最大限に活用することにあります。

以前のGoのSolaris実装では、`src/syscall/so_solaris.go`ファイルに`lazySO`や`lazyProc`といった構造体が定義されており、これらが`dlopen`と`dlsym`を内部的に使用して、必要なシステムコール関数をオンデマンドでロード・解決していました。これは、Solarisの動的リンカーが効率的な遅延バインディングを提供していなかったため、Go自身がその役割を担っていたためです。

CL 8214によってSolarisの動的リンカーが`.plt`を介した遅延バインディングをサポートするようになったことで、Goが独自に実装していたこの複雑なレイヤーは不要になりました。

このコミットでは、以下の技術的変更が行われています。

1.  **`dlopen`/`dlsym`関連コードの削除**: `src/runtime/syscall_solaris.go`から`libc_dlopen`, `libc_dlclose`, `libc_dlsym`の宣言と、それらを利用する`syscall_dlopen`, `syscall_dlclose`, `syscall_dlsym`関数が削除されました。これは、GoランタイムがこれらのAPIを直接呼び出す必要がなくなったためです。
2.  **カスタム遅延ロード機構の廃止**: `src/syscall/so_solaris.go`ファイル全体が削除されました。このファイルには、共有ライブラリのロード（`loadSO`）、プロシージャの検索（`FindProc`）、そして遅延ロードを管理する`lazySO`および`lazyProc`のロジックが含まれていました。これらの機能は、Solarisの動的リンカーが提供するネイティブな遅延バインディングによって代替されるため、不要となりました。
3.  **`mksyscall_solaris.pl`の変更**: `src/syscall/mksyscall_solaris.pl`スクリプトは、Goの`syscall`パッケージのシステムコール関数を生成するために使用されます。このスクリプトが変更され、以前は`newLazySO`と`NewProc`を使って遅延ロードされるプロシージャを生成していましたが、代わりに`//go:cgo_import_dynamic`と`//go:linkname`ディレクティブを生成するようになりました。
    *   `//go:cgo_import_dynamic libc_SymbolName symbolName "library.so"`: これはGoコンパイラに対し、`symbolName`というシンボルが`library.so`から動的にインポートされることを指示します。Goコード内では`libc_SymbolName`という名前で参照されます。これは、CGOを使わずにGoプログラムが直接共有ライブラリのシンボルを参照するためのメカニズムです。
    *   `//go:linkname libc_SymbolName libc_SymbolName`: これはGoの内部リンカーに対し、Goコード内の`libc_SymbolName`という変数を、外部の`libc_SymbolName`というシンボルにリンクするように指示します。これにより、Goの変数`libc_SymbolName`が、共有ライブラリからロードされた実際の関数のアドレスを指すようになります。
    *   `libcFunc uintptr`という新しい型が導入され、これらの動的にインポートされたシンボルのアドレスを保持するために使用されます。
4.  **システムコール呼び出しの変更**: `src/syscall/exec_solaris_test.go`や`src/syscall/zsyscall_solaris_amd64.go`などのファイルで、システムコールを呼び出す際の引数が変更されました。以前は`procGetpgid.Addr()`のように、`lazyProc`オブジェクトから取得したアドレスを使用していましたが、変更後は`uintptr(unsafe.Pointer(&libc_Getpgid))`のように、`//go:cgo_import_dynamic`で宣言された`libcFunc`型の変数のアドレスを直接渡すようになりました。これは、シンボル解決がGoのカスタムロジックではなく、OSの動的リンカーによって行われるようになったためです。

これらの変更により、GoのSolarisバイナリは、システムコールを呼び出す際に、OSの動的リンカーが提供する効率的な遅延バインディングメカニズムを直接利用するようになり、Goランタイムのコードベースが大幅に簡素化されました。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

1.  **`src/runtime/syscall_solaris.go`**:
    *   `libc_dlopen`, `libc_dlclose`, `libc_dlsym`の変数宣言が削除されました。
    *   `syscall_dlopen`, `syscall_dlclose`, `syscall_dlsym`関数が削除されました。
2.  **`src/syscall/exec_solaris_test.go`**:
    *   `modlibc.NewProc("getpgid")`や`modlibc.NewProc("getpgrp")`といった`lazySO`と`lazyProc`を使用するコードが削除されました。
    *   代わりに`libc_Getpgid`, `libc_Getpgrp libcFunc`という変数が宣言され、`//go:cgo_import_dynamic`と`//go:linkname`ディレクティブが追加されました。
    *   システムコール呼び出しが`sysvicall6(procGetpgid.Addr(), ...)`から`sysvicall6(uintptr(unsafe.Pointer(&libc_Getpgid)), ...)`に変更されました。
3.  **`src/syscall/mksyscall_solaris.pl`**:
    *   `$mods`と`$modnames`変数が削除され、`$dynimports`と`$linknames`変数が追加されました。
    *   `newLazySO`や`NewProc`を生成するロジックが削除され、`//go:cgo_import_dynamic`と`//go:linkname`ディレクティブを生成するロジックに置き換えられました。
    *   生成されるシステムコール呼び出しの引数が、`$sysvarname.Addr()`から`uintptr(unsafe.Pointer(&$sysvarname))`に変更されました。
    *   `libcFunc uintptr`型の宣言が生成されるようになりました。
4.  **`src/syscall/so_solaris.go`**:
    *   このファイル全体が削除されました。
5.  **`src/syscall/syscall_solaris.go`**:
    *   `procfcntl.Addr()`, `procread.Addr()`, `procwrite.Addr()`といった`lazyProc`のアドレスを使用する箇所が、`uintptr(unsafe.Pointer(&libc_fcntl))`, `uintptr(unsafe.Pointer(&libc_read))`, `uintptr(unsafe.Pointer(&libc_write))`のように直接リンクされたシンボルのアドレスを使用するように変更されました。
6.  **`src/syscall/zsyscall_solaris_amd64.go`**:
    *   大量の`procSymbolName = modlibrary.NewProc("symbolname")`形式の宣言が削除されました。
    *   代わりに、多数の`//go:cgo_import_dynamic`と`//go:linkname`ディレクティブが追加され、対応する`libc_SymbolName libcFunc`変数が宣言されました。
    *   システムコール呼び出しが、`procSymbolName.Addr()`から`uintptr(unsafe.Pointer(&libc_SymbolName))`に変更されました。

## コアとなるコードの解説

変更されたコードの核心は、GoがSolarisの共有ライブラリ関数を呼び出すためのメカニズムを、Go独自の動的ロード・遅延バインディング実装から、Solarisネイティブの動的リンカーによる直接的な遅延バインディングへと移行した点にあります。

*   **`src/runtime/syscall_solaris.go`の変更**:
    *   `dlopen`, `dlclose`, `dlsym`は、実行時に共有ライブラリをロードし、その中のシンボルを検索するためのC標準ライブラリ関数です。Goがこれらの関数を直接呼び出す必要がなくなったということは、Go自身が共有ライブラリのロードとシンボル解決の管理を行う層を削除したことを意味します。これは、Solarisの動的リンカーがその役割を効率的に果たせるようになったためです。

*   **`src/syscall/so_solaris.go`の削除**:
    *   このファイルは、GoがSolaris上で共有ライブラリの遅延ロードとシンボル解決を行うためのカスタム実装を含んでいました。`so`構造体は共有ライブラリのハンドルを管理し、`proc`構造体はライブラリ内のプロシージャ（関数）のアドレスを保持していました。`lazySO`と`lazyProc`は、これらのロードと検索を実際に遅延させるためのロジックを提供していました。このファイルが完全に削除されたことは、Goがこのカスタム実装を完全に放棄し、OSの機能に依存するようになったことを明確に示しています。

*   **`src/syscall/mksyscall_solaris.pl`の変更と`//go:cgo_import_dynamic`、`//go:linkname`の導入**:
    *   `mksyscall_solaris.pl`は、Goの`syscall`パッケージのソースコードを自動生成するPerlスクリプトです。以前は、このスクリプトが`newLazySO`と`NewProc`を呼び出すコードを生成し、Goのカスタム遅延ロード機構を利用していました。
    *   変更後、このスクリプトは`//go:cgo_import_dynamic`と`//go:linkname`というGoコンパイラディレクティブを生成するようになりました。
        *   `//go:cgo_import_dynamic libc_SymbolName symbolName "library.so"`: このディレクティブは、Goコンパイラに対して、`symbolName`という名前のシンボルが`library.so`という共有ライブラリから動的にインポートされることを伝えます。Goコード内では`libc_SymbolName`という名前で参照されます。これは、CGOを使わずにGoプログラムが直接共有ライブラリのシンボルを参照するためのメカニズムです。
        *   `//go:linkname libc_SymbolName libc_SymbolName`: このディレクティブは、Goのリンカーに対して、Goコード内の`libc_SymbolName`という変数を、外部の`libc_SymbolName`というシンボル（`//go:cgo_import_dynamic`によって参照される）にリンクするように指示します。これにより、Goの変数`libc_SymbolName`が、実行時に動的リンカーによって解決された実際の関数のエントリポイントを指すようになります。
    *   `libcFunc uintptr`という新しい型は、これらの動的にリンクされた関数のアドレスを保持するためのものです。`uintptr`はポインタを整数として扱うGoの型であり、システムコールのアドレスを直接操作するために使用されます。

*   **システムコール呼び出しの変更**:
    *   `sysvicall6(procGetpgid.Addr(), ...)`から`sysvicall6(uintptr(unsafe.Pointer(&libc_Getpgid)), ...)`への変更は、システムコールを呼び出す際のアドレスの取得方法が変わったことを示しています。
        *   以前は、`procGetpgid`という`lazyProc`オブジェクトが内部的に`dlsym`を使ってシンボルアドレスを解決し、そのアドレスを`Addr()`メソッドで返していました。
        *   変更後は、`&libc_Getpgid`は`//go:cgo_import_dynamic`と`//go:linkname`によって動的リンカーが解決した`getpgid`関数のアドレスを指す`libcFunc`型の変数のアドレスです。`unsafe.Pointer`と`uintptr`を使って、このアドレスを直接`sysvicall6`に渡しています。これは、Goがシンボル解決の仲介役をせず、OSの動的リンカーに完全に任せるようになったことを意味します。

これらの変更により、GoのSolarisバイナリは、より標準的で効率的なOSネイティブの動的リンクメカニズムを利用するようになり、Goランタイムの複雑性が軽減され、パフォーマンスの向上が期待されます。

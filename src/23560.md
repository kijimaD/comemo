# [インデックス 23560] ファイルの概要

このコミットは、Goリンカの`amd64`アーキテクチャ固有のコードにおいて、`-buildmode=c-archive`が指定された場合に、リンキングモードを強制的に外部リンキング (`ld.LinkExternal`) に設定する変更を導入しています。これにより、`c-archive`ビルドモードが`c-shared`ビルドモードと同様に外部リンキングを必要とすることが明示され、GoとC/C++の相互運用性におけるリンキングの挙動が統一されます。

## 元コミット内容

このコードは、いずれ`cmd/link/internal/ld`に移動すべきだが、少なくとも現時点では`c-shared`と同様に`c-archive`を扱う。

## 変更の背景

Go言語は、C言語との相互運用性（cgo）を強力にサポートしており、GoコードをCのライブラリとしてビルドする機能を提供しています。これには主に二つのビルドモードがあります。

1.  **`-buildmode=c-shared`**: GoコードをCの共有ライブラリ（.so, .dylib, .dllなど）としてビルドします。
2.  **`-buildmode=c-archive`**: GoコードをCの静的ライブラリ（.aなど）としてビルドします。

これらのビルドモードで生成されたライブラリは、C/C++のプロジェクトにリンクされ、Cの関数としてGoの機能を利用できるようにします。このような外部のC/C++ツールチェーンと連携する場合、Goリンカは通常とは異なるリンキング戦略を採用する必要があります。

以前は、`c-shared`ビルドモードと動的リンクされたGoコード (`ld.DynlinkingGo()`) の場合にのみ、Goリンカは外部リンキングモード (`ld.LinkExternal`) を強制していました。しかし、`c-archive`ビルドモードもまた、最終的には外部のC/C++リンカによって処理される静的ライブラリを生成するため、同様に外部リンキングの挙動が必要となります。

このコミットの背景には、`c-archive`ビルドモードが`c-shared`と同様に外部リンキングを必要とするという認識があり、リンカの挙動をより正確に、かつ一貫性のあるものにする目的があります。これにより、`c-archive`でビルドされたGoライブラリが、外部のC/C++プロジェクトに正しくリンクされ、期待通りに動作することが保証されます。

コミットメッセージにある「At some point this code should probably move to cmd/link/internal/ld」という記述は、このリンキングモードの決定ロジックが、特定のアーキテクチャ（`amd64`）に限定されるべきではなく、より汎用的なリンカのコアロジック (`cmd/link/internal/ld`) に配置されるべきであるという将来的なリファクタリングの意図を示唆しています。

## 前提知識の解説

### Goのビルドモード (`-buildmode`)

Goコンパイラ (`go build`) は、`-buildmode`フラグを通じて様々な種類の実行可能ファイルやライブラリを生成できます。

*   **`exe` (デフォルト)**: 実行可能なバイナリを生成します。
*   **`archive`**: Goパッケージをアーカイブファイル（.a）としてコンパイルしますが、これはGoのツールチェーン内で使用されることを意図しています。
*   **`c-archive`**: GoパッケージをCの静的ライブラリ（.a）としてコンパイルします。C/C++プロジェクトにリンクしてGoの関数を呼び出すことができます。
*   **`c-shared`**: GoパッケージをCの共有ライブラリ（.so, .dylib, .dll）としてコンパイルします。C/C++プロジェクトから動的にロードしてGoの関数を呼び出すことができます。
*   **`shared`**: 複数のGoプログラムで共有されるGo共有ライブラリをコンパイルします。
*   **`plugin`**: Goプラグインをコンパイルします。

### Goリンカ (`cmd/link`)

`cmd/link`はGoツールチェーンの一部であり、コンパイルされたGoオブジェクトファイル（.o）と、必要に応じてCオブジェクトファイルやシステムライブラリを結合して、最終的な実行可能ファイルやライブラリを生成する役割を担います。リンカは、プログラム内のシンボル（関数や変数など）の参照を解決し、それらをメモリ上の正しいアドレスにマッピングします。

### 内部リンキング (Internal Linking) と外部リンキング (External Linking)

Goリンカには、主に二つのリンキングモードがあります。

1.  **内部リンキング (`ld.LinkInternal`)**: Goリンカが、Goコードによって生成されたすべてのオブジェクトファイルと、Goランタイムに必要なすべてのシンボル解決を自身で行うモードです。このモードでは、Goリンカは完全に自己完結しており、外部のC/C++リンカの助けを借りずに最終バイナリを生成します。Goの標準的なビルド（`go build`で実行可能ファイルを生成する場合など）では、通常このモードが使用されます。
2.  **外部リンキング (`ld.LinkExternal`)**: Goリンカが、Goコードをオブジェクトファイルにコンパイルし、そのオブジェクトファイルを外部のC/C++リンカ（例: `gcc`や`clang`）に渡して最終的なリンク処理を行わせるモードです。このモードでは、GoリンカはGo固有の処理を行い、その後、外部リンカがGoのオブジェクトファイルとC/C++のオブジェクトファイル、システムライブラリなどを結合して最終的な成果物（実行可能ファイル、共有ライブラリ、静的ライブラリなど）を生成します。`cgo`を使用する場合や、`c-shared`、`c-archive`のようなCとの相互運用を目的としたビルドモードでは、この外部リンキングが強制されることがよくあります。これは、GoとC/C++のシンボル解決規則やランタイムの初期化プロセスが異なるため、外部リンカに最終的な調整を委ねる必要があるためです。

### `ld.Linkmode` と `ld.LinkExternal`/`ld.LinkInternal`

`ld.Linkmode`は、Goリンカが現在どのリンキングモードで動作しているかを示す内部変数です。`ld.LinkExternal`と`ld.LinkInternal`は、それぞれ外部リンキングモードと内部リンキングモードを表す定数です。リンカのコード内でこれらの値が設定され、それに基づいてリンキングの挙動が決定されます。

## 技術的詳細

このコミットの技術的詳細を理解するためには、GoのリンカがどのようにCとの相互運用を処理するか、特にシンボル解決とランタイムの初期化に焦点を当てる必要があります。

Goの`c-archive`および`c-shared`ビルドモードは、Goの関数をCのABI（Application Binary Interface）に準拠した形でエクスポートし、C/C++コードから呼び出せるようにします。このプロセスには、Goランタイムの初期化、Goスケジューラの起動、Goのガベージコレクタの管理などが含まれます。

### 外部リンキングが強制される理由

1.  **シンボル解決の複雑さ**: GoとC/C++は異なるシンボル命名規則やリンキング規則を持つことがあります。特に、Goのランタイムは多くの内部シンボルを持ち、これらが外部のC/C++リンカと衝突しないように、あるいは正しく解決されるように調整が必要です。外部リンキングモードでは、GoリンカはGo固有のシンボルを適切にマークし、外部リンカがそれらを正しく処理できるようにします。
2.  **ランタイムの初期化**: `c-archive`や`c-shared`でビルドされたGoライブラリがC/C++プログラムにロードされる際、Goランタイムは適切に初期化される必要があります。これには、`runtime.init`関数の呼び出しや、Goスケジューラの起動などが含まれます。外部リンキングでは、Goリンカはこれらの初期化ルーチンを外部リンカが呼び出せるような形式でエクスポートします。
3.  **Cgoとの連携**: `cgo`を使用してCコードをGoに組み込んでいる場合、GoリンカはCコンパイラによって生成されたオブジェクトファイルとGoのオブジェクトファイルを結合する必要があります。最終的なリンクは、通常、`gcc`のような外部リンカによって行われ、Goのオブジェクトファイル、Cのオブジェクトファイル、および必要なシステムライブラリがすべて結合されます。`c-archive`の場合、GoリンカはGoのオブジェクトファイルをアーカイブファイルにまとめ、そのアーカイブファイルが後で外部リンカによってC/C++プログラムにリンクされます。この際、Goのランタイムが外部リンカによって正しく扱われるように、外部リンキングモードが不可欠です。
4.  **プラットフォーム固有のリンキング要件**: オペレーティングシステムやアーキテクチャによっては、静的ライブラリや共有ライブラリのリンキングに特定の要件があります。外部リンキングモードは、Goリンカがこれらのプラットフォーム固有の要件に準拠したオブジェクトファイルを生成するのに役立ちます。

このコミットは、`ld.BuildmodeCArchive`が`ld.BuildmodeCShared`と同様に、Goリンカが外部リンキングモードで動作する必要があることを認識し、そのロジックを`src/cmd/link/internal/amd64/obj.go`内の条件式に追加することで、この要件を強制しています。これにより、`amd64`アーキテクチャ上で`c-archive`ビルドモードを使用する際のリンキングの堅牢性が向上します。

## コアとなるコードの変更箇所

変更は`src/cmd/link/internal/amd64/obj.go`ファイル内の`archinit`関数にあります。

```diff

+++ b/src/cmd/link/internal/amd64/obj.go
```

## コアとなるコードの解説

変更前のコードは以下の通りでした。

```go
	if ld.Buildmode == ld.BuildmodeCShared || ld.DynlinkingGo() {
		ld.Linkmode = ld.LinkExternal
	}
```

この条件式は、「ビルドモードが`c-shared`である場合、またはGoが動的にリンクされている場合」に、リンキングモードを`ld.LinkExternal`（外部リンキング）に設定していました。

変更後のコードは以下の通りです。

```go
	if ld.Buildmode == ld.BuildmodeCArchive || ld.Buildmode == ld.BuildmodeCShared || ld.DynlinkingGo() {
		ld.Linkmode = ld.LinkExternal
	}
```

この変更により、条件式に`ld.Buildmode == ld.BuildmodeCArchive`が追加されました。これは、「ビルドモードが`c-archive`である場合、またはビルドモードが`c-shared`である場合、またはGoが動的にリンクされている場合」に、リンキングモードを`ld.LinkExternal`に設定することを意味します。

この変更の目的は、`c-archive`ビルドモードでGoコードを静的ライブラリとしてビルドする際にも、`c-shared`と同様に外部リンキングを強制することです。これにより、`c-archive`で生成されたGoライブラリが、外部のC/C++リンカによって正しく処理され、Goランタイムの初期化やシンボル解決が適切に行われるようになります。

`archinit`関数は、リンカの初期化フェーズで呼び出され、アーキテクチャ固有の設定を行います。この中でリンキングモードを設定することは、リンカ全体の挙動に影響を与える重要なステップです。このコミットは、`amd64`アーキテクチャにおける`c-archive`のリンキング挙動を修正し、GoとC/C++の相互運用性における一貫性と正確性を向上させています。

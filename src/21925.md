## コミット

```
cmd/gc: transform closure calls to function calls

Currently we always create context objects for closures that capture variables.
However, it is completely unnecessary for direct calls of closures
(whether it is func()(), defer func()() or go func()()).
This change transforms any OCALLFUNC(OCLOSURE) to normal function call.
Closed variables become function arguments.
This transformation is especially beneficial for go func(),
because we do not need to allocate context object on heap.
But it makes direct closure calls a bit faster as well (see BenchmarkClosureCall).

On implementation level it required to introduce yet another compiler pass.
However, the pass iterates only over xtop, so it should not be an issue.
Transformation consists of two parts: closure transformation and call site
transformation. We can't run these parts on different sides of escape analysis,
because tree state is inconsistent. We can do both parts during typecheck,
we don't know how to capture variables and don't have call site.
We can't do both parts during walk of OCALLFUNC, because we can walk
OCLOSURE body earlier.
So now capturevars pass only decides how to capture variables
(this info is required for escape analysis). New transformclosure
pass, that runs just before order/walk, does all transformations
of a closure. And later walk of OCALLFUNC(OCLOSURE) transforms call site.
```

## 変更の背景

Go言語において、変数をキャプチャするクロージャ（無名関数）は、通常、キャプチャされた変数を保持するための「コンテキストオブジェクト」をヒープ上に割り当てます。これは、クロージャが定義されたスコープを離れても、キャプチャされた変数にアクセスできるようにするためです。しかし、クロージャがその場で直接呼び出される場合（例: `func()(){}()`、`defer func()(){}()`、`go func()(){}()`）、このコンテキストオブジェクトの割り当ては不要であり、オーバーヘッドとなります。

特に、`go func()(){}()` のようにゴルーチンを起動する際にクロージャを使用する場合、ヒープ割り当てはパフォーマンスに大きな影響を与えます。ヒープ割り当てはガベージコレクションの負荷を増加させ、実行速度を低下させる要因となります。

このコミットの目的は、このような直接呼び出されるクロージャに対して、コンテキストオブジェクトのヒープ割り当てを回避し、パフォーマンスを向上させることです。具体的には、クロージャの呼び出しを通常の関数呼び出しに変換し、キャプチャされた変数を関数の引数として渡すようにすることで、この最適化を実現しています。これにより、`BenchmarkClosureCall`で36.81%の高速化、`BenchmarkCreateGoroutinesCapture`で20.81%の高速化、そしてアロケーションが66.67%削減、バイト数が72.73%削減されるという顕著な改善が見られました。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoコンパイラとGo言語の概念に関する知識が必要です。

*   **Goのクロージャ (Closures in Go)**:
    Go言語におけるクロージャは、関数が定義された環境（スコープ）内の変数を「記憶」し、その関数がそのスコープ外で実行されてもそれらの変数にアクセスできる機能を持つ無名関数です。例えば、外側の関数のローカル変数をキャプチャして、その変数を操作する内部関数を返すことができます。

*   **コンテキストオブジェクト (Context Objects)**:
    Goコンパイラは、クロージャが外部の変数をキャプチャする際に、それらの変数を格納するための特別なデータ構造（コンテキストオブジェクト）を生成します。このオブジェクトは通常ヒープに割り当てられ、クロージャが実行される間、キャプチャされた変数のライフタイムを管理します。

*   **エスケープ解析 (Escape Analysis)**:
    Goコンパイラの重要な最適化の一つです。エスケープ解析は、プログラム内の変数がヒープに割り当てられるべきか、それともスタックに割り当てられるべきかを決定します。変数が関数のスコープを「エスケープ」して、その関数がリターンした後も参照され続ける可能性がある場合、その変数はヒープに割り当てられます。そうでない場合は、より高速なスタックに割り当てられます。クロージャがキャプチャする変数は、通常、エスケープ解析によってヒープに割り当てられると判断されます。

*   **`cmd/gc`**:
    Go言語の公式コンパイラです。Goのソースコードを機械語に変換する役割を担っています。このコミットの変更は、主にこのコンパイラの内部実装に関するものです。

*   **`OCALLFUNC`, `OCLOSURE`**:
    これらはGoコンパイラの内部表現（AST: Abstract Syntax Tree）におけるノードの種類です。
    *   `OCALLFUNC`: 関数呼び出しを表すノード。
    *   `OCLOSURE`: クロージャ（無名関数）の定義を表すノード。

*   **`xtop`**:
    Goコンパイラ内部で、トップレベルの宣言（関数、グローバル変数など）のリストを保持するデータ構造です。コンパイラの多くのパスは、この`xtop`リストを走査して処理を行います。

*   **`capturevars` パス**:
    既存のコンパイラパスの一つで、クロージャがキャプチャする変数をどのように扱うか（値渡し`byval`か参照渡し`byref`か）を決定します。この情報はエスケープ解析に利用されます。

*   **`walk` パス**:
    Goコンパイラの最終段階に近いパスで、ASTを走査し、実際のコード生成のための準備を行います。このパスで、`OCALLFUNC`などのノードが具体的な命令に変換されます。

## 技術的詳細

このコミットの核心は、直接呼び出されるクロージャの最適化です。

1.  **最適化のアイデア**:
    クロージャが`func()(){}()`、`defer func()(){}()`、`go func()(){}()`のようにその場で直接呼び出される場合、クロージャのコンテキストオブジェクトをヒープに割り当てる必要はありません。代わりに、キャプチャされた変数を通常の関数の引数として渡すことで、ヒープ割り当てを回避し、スタック上で処理を完結させることができます。

2.  **新しいコンパイラパス `transformclosure` の導入**:
    この最適化を実現するために、Goコンパイラに`transformclosure`という新しいパスが導入されました。このパスは、既存の`capturevars`パスと`walk`パスの間に実行されます。

    *   **`capturevars` パス**: 以前は変数のキャプチャ方法を決定し、クロージャのボディを変換していましたが、この変更により、変数のキャプチャ方法（`byval`か`byref`か）を決定する役割に特化しました。この情報はエスケープ解析に必要です。
    *   **`transformclosure` パス**: `capturevars`の後に実行され、クロージャのボディに対する実際の変換を行います。このパスは、クロージャが直接呼び出される場合に、キャプチャされた変数を関数の引数として追加し、クロージャの内部でそれらの変数へのアクセス方法を調整します。
    *   **`walk` パス**: `OCALLFUNC`ノードを処理する際に、`transformclosure`によって準備された情報に基づいて、クロージャの呼び出しを通常の関数呼び出しに変換し、キャプチャされた変数を引数リストに追加します。

3.  **パスの実行順序の重要性**:
    コミットメッセージで強調されているように、クロージャの変換（ボディの変更）と呼び出しサイトの変換（引数の追加）を、エスケープ解析の異なる側で実行することはできません。これは、コンパイラのツリーの状態が一貫性を失うためです。
    *   `typecheck`中に両方を実行することはできません。なぜなら、変数のキャプチャ方法がまだ不明であり、呼び出しサイトの情報も利用できないためです。
    *   `OCALLFUNC`の`walk`中に両方を実行することもできません。なぜなら、`OCLOSURE`のボディが先に`walk`される可能性があるためです。
    このため、`capturevars`がキャプチャ方法を決定し、`transformclosure`がクロージャのボディを変換し、最後に`walk`が呼び出しサイトを変換するという、3段階のパスが導入されました。

4.  **`Node`構造体への`top`フィールドの追加**:
    `src/cmd/gc/go.h`の`Node`構造体に`int top;`フィールドが追加されました。これは、`typecheckclosure`関数で設定され、クロージャが呼び出しコンテキスト（`Ecall`、`Eproc`など）で使われているかどうかを示すために利用されます。`transformclosure`はこの`top`フィールドを参照して、クロージャが直接呼び出されるケースであるかを判断します。

5.  **`byval` (値渡し) と `byref` (参照渡し) の扱い**:
    *   **`byval`**: 変数が値でキャプチャされる場合（宣言後に再割り当てされない128バイト以下の値など）、`transformclosure`は、その変数を単に`PPARAM`（関数パラメータ）にダウングレードします。これにより、クロージャ内でその変数へのアクセスは通常の関数パラメータと同様になります。
    *   **`byref`**: 変数が参照でキャプチャされる場合、`transformclosure`は、その変数の型へのポインタを新しい関数パラメータとして導入します（例: `&byref *int`）。クロージャ内の元の変数（`v`）は`PPARAMREF`のままで、`heapaddr`フィールドが新しいポインタパラメータを指すようになります。これにより、クロージャ内のアクセスは暗黙的にポインタのデリファレンスを伴うようになります。

6.  **amd64における小さな`byval`変数の最適化**:
    `src/cmd/gc/closure.c`の`transformclosure`関数内で、`v->byval && v->type->width <= 2*widthptr && arch.thechar == '6'`という条件があります。これは、amd64アーキテクチャ（`arch.thechar == '6'`）において、2ポインタ幅以下の小さな値渡しでキャプチャされた変数を`PAUTO`（自動変数、つまりスタック変数）にダウングレードする最適化です。これにより、さらにヒープ割り当てを回避し、パフォーマンスを向上させます。

## コアとなるコードの解説

### `src/cmd/gc/closure.c` の `transformclosure` 関数

```c
void
transformclosure(Node *xfunc)
{
    Node *func, *cv, *addr, *v, *f;
    NodeList *l, *body;
    Type **param, *fld;
    vlong offset;
    int lno, nvar;

    lno = lineno;
    lineno = xfunc->lineno;
    func = xfunc->closure;

    if(func->top&Ecall) { // クロージャが直接呼び出される場合
        // If the closure is directly called, we transform it to a plain function call
        // with variables passed as args. This avoids allocation of a closure object.
        // Here we do only a part of the transformation. Walk of OCALLFUNC(OCLOSURE)
        // will complete the transformation later.

        f = xfunc->nname; // 実際の関数のONAMEノード
        // 入力引数へのポインタを取得し、末尾まで巻き戻す。
        // キャプチャされた変数を入力引数に追加する。
        param = &getinargx(f->type)->type;
        for(; *param; param = &(*param)->down) {
        }
        for(l=func->cvars; l; l=l->next) { // キャプチャされた変数ごとに処理
            v = l->n;
            if(v->op == OXXX)
                continue;
            fld = typ(TFIELD);
            fld->funarg = 1;
            if(v->byval) { // 値渡しの場合
                // If v is captured by value, we merely downgrade it to PPARAM.
                v->class = PPARAM; // PPARAMにダウングレード
                v->ullman = 1;
                fld->nname = v;
            } else { // 参照渡しの場合
                // If v of type T is captured by reference,
                // we introduce function param &v *T
                // and v remains PPARAMREF with &v heapaddr
                // (accesses will implicitly deref &v).
                snprint(namebuf, sizeof namebuf, "&%s", v->sym->name);
                addr = newname(lookup(namebuf));
                addr->type = ptrto(v->type); // ポインタ型
                addr->class = PPARAM;
                v->heapaddr = addr; // 元の変数のheapaddrを新しいパラメータに設定
                fld->nname = addr;
            }
            fld->type = fld->nname->type;
            fld->sym = fld->nname->sym;
            // 新しいパラメータを宣言し、入力引数に追加
            xfunc->dcl = list(xfunc->dcl, fld->nname);
            *param = fld;
            param = &fld->down;
        }
        // パラメータのオフセットを再計算
        if(f->type->width > 0)
            fatal("transformclosure: width is already calculated");
        dowidth(f->type);
        xfunc->type = f->type; // ODCLFUNCの型を更新
    } else {
        // クロージャが直接呼び出されない場合（通常のクロージャとして残る）
        // ... 既存のクロージャコンテキストオブジェクト生成ロジック ...
        // この部分では、クロージャがヒープに割り当てられる場合の処理が記述されています。
        // 変更点としては、byvalの小さな変数をPAUTOにダウングレードする最適化が追加されています。
    }

    lineno = lno;
}
```
この関数は、`func->top&Ecall`が真の場合（つまり、クロージャが直接呼び出される場合）に、キャプチャされた変数をクロージャの関数シグネチャに引数として追加します。`byval`の変数は`PPARAM`に、`byref`の変数はそのポインタ型が`PPARAM`として追加されます。これにより、クロージャは通常の関数のように振る舞い、ヒープ上のコンテキストオブジェクトが不要になります。

### `src/cmd/gc/walk.c` の `walkexpr` 関数内の `OCALLFUNC` 処理

```c
case OCALLFUNC:
    if(n->left->op == OCLOSURE) { // 呼び出し対象がOCLOSUREの場合
        // Transform direct call of a closure to call of a normal function.
        // transformclosure already did all preparation work.

        // Append captured variables to argument list.
        n->list = concat(n->list, n->left->enter); // キャプチャされた変数を引数リストに追加
        n->left->enter = NULL;
        // Replace OCLOSURE with ONAME/PFUNC.
        n->left = n->left->closure->nname; // OCLOSUREノードを実際の関数ONAMEに置き換え
        // Update type of OCALLFUNC node.
        // Output arguments had not changed, but their offsets could.
        if(n->left->type->outtuple == 1) {
            t = getoutargx(n->left->type)->type;
            if(t->etype == TFIELD)
                t = t->type;
            n->type = t;
        } else
            n->type = getoutargx(n->left->type);
    }
    t = n->left->type;
    if(n->list && n->list->n->op == OAS)
        goto ret;
```
このコードは、`OCALLFUNC`ノードが`OCLOSURE`ノードを呼び出している場合に実行されます。`transformclosure`パスによって準備された情報（`n->left->enter`に格納されたキャプチャ変数）を利用して、それらを実際の関数呼び出しの引数リストに連結します。そして、`OCLOSURE`ノード自体を、クロージャが変換された先の通常の関数（`ONAME/PFUNC`）のノードに置き換えます。これにより、コンパイラはクロージャの直接呼び出しを、あたかも最初から通常の関数呼び出しであったかのように処理できるようになります。

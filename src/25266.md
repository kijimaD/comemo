# [インデックス 25266] ファイルの概要

このコミットは、Go言語の `database/sql` パッケージにおける接続プールのデッドロック問題を解決し、接続管理ロジックの一貫性を向上させるものです。特に、データベースへの接続試行が失敗した場合に発生する可能性のあるデッドロックを回避し、`db.numOpen` の追跡方法を統一することで、コードの理解と保守を容易にしています。

## 元コミット内容

`database/sql: avoid deadlock waiting for connections`

以前は、`db.maxOpen > 0` の設定で、`db.maxOpen` を超える数の接続試行が同時に失敗した場合にデッドロックが発生する可能性がありました。`DB.conn` および `DB.openNewConnection` は、接続試行が失敗した後に `DB.connectionOpener` ゴルーチンをトリガーしませんでした。この見落としにより、ゴルーチンが `DB.connectionOpener` を永久に待ち続ける可能性がありました。

さらに、接続プールの状態を追跡するロジックが一貫していませんでした。`db.numOpen` は楽観的にインクリメントされることもあれば、そうでないこともありました。この変更により、ロジックが統一され、`db.pendingOpens` 変数が削除され、ロジックの理解と保守が容易になりました。

Issue #10886 を修正します。

## 変更の背景

Goの `database/sql` パッケージは、データベース接続を管理するための汎用インターフェースを提供します。このパッケージは、接続プールを内部的に管理し、アプリケーションが効率的にデータベースリソースを利用できるようにします。しかし、接続プールの実装には複雑な状態管理が伴い、特に並行処理環境下ではデッドロックやリソースリークといった問題が発生しやすくなります。

このコミットの背景には、`db.maxOpen` (同時に開かれる最大接続数) の設定が有効な場合に、複数の接続試行が同時に失敗すると、システムがデッドロックに陥るという具体的な問題がありました。これは、接続を待っているゴルーチンが、新しい接続を開く責任を持つ `connectionOpener` ゴルーチンが起動されないために、永久にブロックされてしまうという状況です。

また、接続プールの状態を管理する `db.numOpen` (現在開かれている、または開かれようとしている接続の総数) と `db.pendingOpens` (現在開かれようとしている接続の数) のロジックが複雑で一貫性がなく、バグの温床となっていました。このコミットは、これらの問題を解決し、`database/sql` パッケージの堅牢性と信頼性を向上させることを目的としています。

## 前提知識の解説

### Goの `database/sql` パッケージと接続プール

`database/sql` パッケージは、GoアプリケーションからSQLデータベースにアクセスするための標準ライブラリです。このパッケージは、特定のデータベースドライバに依存しない汎用的なインターフェースを提供し、接続の確立、クエリの実行、トランザクション管理などを行います。

重要な機能の一つが**接続プール**です。データベース接続の確立はコストの高い操作であるため、`database/sql` は一度確立した接続を再利用するために接続プールを維持します。これにより、アプリケーションのパフォーマンスが向上し、データベースへの負荷が軽減されます。

*   **`DB.SetMaxOpenConns(n int)`**: 同時に開かれるデータベース接続の最大数を設定します。`n` が0の場合、接続数に制限はありません。
*   **`DB.SetMaxIdleConns(n int)`**: アイドル状態の接続プールに保持される接続の最大数を設定します。
*   **`db.numOpen`**: `DB` 構造体の内部フィールドで、現在開かれている、または開かれようとしている接続の総数を追跡します。
*   **`db.pendingOpens`**: (このコミットで削除される) 以前は、現在開かれようとしている接続の数を追跡するために使用されていました。
*   **`connectionOpener` ゴルーチン**: `database/sql` パッケージの内部で動作するゴルーチンで、新しいデータベース接続を開く責任を負います。接続要求があった際に、このゴルーチンが起動され、実際にデータベースへの接続を試みます。
*   **`connRequests`**: 接続を待っているゴルーチンからのリクエストを保持するチャネルのリスト。

### デッドロック

デッドロックとは、複数のプロセス（またはゴルーチン）が互いに相手が保持しているリソースの解放を待ち、結果としてどのプロセスも処理を進められなくなる状態を指します。このコミットで修正されたデッドロックは、特に接続プールの管理において、接続を待つゴルーチンと新しい接続を開くゴルーチンの間で発生していました。接続試行の失敗が `connectionOpener` の起動を妨げると、接続を待つゴルーチンは永遠にブロックされ、システム全体が停止する可能性があります。

## 技術的詳細

このコミットの主要な技術的変更点は以下の通りです。

1.  **`db.pendingOpens` の削除と `db.numOpen` の一元化**:
    以前は、`db.numOpen` と `db.pendingOpens` の2つの変数が接続の状態を追跡していました。`db.numOpen` は開いている接続の総数を、`db.pendingOpens` は現在開かれようとしている接続の数を表していました。この二重管理はロジックを複雑にし、一貫性のない更新を引き起こしていました。
    このコミットでは `db.pendingOpens` を削除し、`db.numOpen` が「開かれている接続」と「開かれようとしている接続」の両方を楽観的に追跡するように変更されました。これにより、接続プールの状態管理が簡素化され、一貫性が保たれます。

2.  **接続試行失敗時の `connectionOpener` のトリガー**:
    デッドロックの根本原因は、`openNewConnection` 関数内で接続試行が失敗した場合に、`connectionOpener` ゴルーチンが新しい接続を開くように通知されないことでした。
    変更後、`openNewConnection` で接続が失敗した場合、`db.numOpen` をデクリメントし、`db.maybeOpenNewConnections()` を呼び出すことで、`connectionOpener` ゴルーチンが再度起動され、接続要求を処理できるようになります。これにより、接続を待っているゴルーチンが永久にブロックされることがなくなります。

3.  **`maybeOpenNewConnections` のロジック改善**:
    `maybeOpenNewConnections` 関数は、接続要求の数と `db.maxOpen` の制限に基づいて、新しい接続を開く必要があるかどうかを判断します。
    変更前は `db.pendingOpens` を考慮していましたが、削除されたため、`numRequests` の計算が `len(db.connRequests)` のみとなり、`numCanOpen` の計算も `db.numOpen` のみを使用するように簡素化されました。これにより、接続プールの状態に応じた正確な接続要求の処理が可能になります。

4.  **`db.conn` での `db.numOpen` の楽観的インクリメントの修正**:
    `db.conn` 関数内で接続取得に失敗した場合、以前は `db.numOpen--` を実行していましたが、このコミットでは `db.maybeOpenNewConnections()` を呼び出すことで、接続プールの状態を適切に更新し、必要に応じて新しい接続のオープンを促すようになりました。

5.  **テストケースの追加**:
    `TestPendingConnsAfterErr` という新しいテストケースが追加され、このデッドロック問題が修正されたことを検証しています。このテストは、`db.maxOpen` を設定し、それ以上の数の接続試行を同時に開始し、意図的に接続を失敗させることで、すべての接続要求がデッドロックなしでエラーを返すことを確認します。

## コアとなるコードの解説

### `src/database/sql/sql.go` の変更点

1.  **`DB` 構造体**:
    *   `pendingOpens int` フィールドが削除されました。
    *   `numOpen int` のコメントが `// number of opened and pending open connections` に変更され、このフィールドが「開かれている接続」と「開かれようとしている接続」の両方を追跡するようになったことを明確に示しています。

2.  **`maybeOpenNewConnections()` 関数**:
    *   `numRequests := len(db.connRequests) - db.pendingOpens` が `numRequests := len(db.connRequests)` に変更されました。`pendingOpens` が削除されたため、接続要求の数は単に `connRequests` の長さで判断されます。
    *   `numCanOpen := db.maxOpen - (db.numOpen + db.pendingOpens)` が `numCanOpen := db.maxOpen - db.numOpen` に変更されました。これにより、開くことができる接続の数が `db.maxOpen` と現在の `db.numOpen` の差で正確に計算されます。
    *   `db.pendingOpens++` が `db.numOpen++ // optimistically` に変更されました。新しい接続を開くことを決定した時点で、`db.numOpen` を楽観的にインクリメントすることで、接続プールの状態をより正確に反映させます。

3.  **`openNewConnection()` 関数**:
    *   関数の冒頭に新しいコメントが追加され、`maybeOpenNewConnections` が既に `db.numOpen++` を実行しているため、この関数は接続が失敗またはクローズされた場合に `db.numOpen--` を実行する必要があることを説明しています。
    *   接続オープン (`db.driver.Open(db.dsn)`) が成功し、その後すぐにクローズされる場合 (`err == nil` のブロック内) に `db.numOpen--` が追加されました。
    *   接続オープンが失敗した場合 (`err != nil` のブロック内) に `db.numOpen--` が追加されました。これは、楽観的にインクリメントされた `db.numOpen` を元に戻すためです。
    *   接続オープンが失敗した場合 (`err != nil` のブロック内) に `db.maybeOpenNewConnections()` が呼び出されるようになりました。これがデッドロックを回避する重要な変更点です。接続試行が失敗しても、`connectionOpener` ゴルーチンが新しい接続を開くように促され、接続を待っている他のゴルーチンがブロックされ続けるのを防ぎます。
    *   `db.putConnDBLocked(dc, err)` が成功した場合、以前は `db.numOpen++` を行っていましたが、これは削除されました。`maybeOpenNewConnections` で既に楽観的にインクリメントされているため、ここでは不要です。
    *   `db.putConnDBLocked(dc, err)` が失敗した場合 (`else` ブロック内) に `db.numOpen--` が追加されました。これは、楽観的にインクリメントされた `db.numOpen` を元に戻すためです。

4.  **`db.conn()` 関数**:
    *   `ret := <-req` の部分が `ret, ok := <-req` に変更され、チャネルがクローズされた場合の処理 (`if !ok { return nil, errDBClosed }`) が追加されました。これにより、DBがクローズされた際の挙動がより堅牢になります。
    *   接続取得に失敗した場合 (`if err != nil` のブロック内) に `db.maybeOpenNewConnections()` が呼び出されるようになりました。これも `openNewConnection` と同様に、接続失敗時に `connectionOpener` をトリガーし、デッドロックを防ぐための重要な変更です。

### `src/database/sql/fakedb_test.go` の変更点

*   `hookOpenErr` というグローバル変数と `setHookOpenErr` 関数が追加されました。これにより、テスト中に `driver.Open` メソッドの動作をフックし、意図的に接続失敗をシミュレートできるようになります。これは、デッドロックのシナリオを再現し、修正が正しく機能するかを検証するために不可欠です。

### `src/database/sql/sql_test.go` の変更点

*   **`TestPendingConnsAfterErr`**:
    *   この新しいテストは、`db.maxOpen` を2に設定し、それよりも多い `tryOpen` (例えば6) の接続試行を同時に開始します。
    *   `setHookOpenErr` を使用して、すべての接続試行が `errOffline` というエラーで失敗するように設定します。
    *   `unblock` チャネルを使って、すべてのゴルーチンが接続オープンを試みるまでブロックし、その後一斉に接続失敗を発生させます。
    *   最終的に、すべての接続試行がデッドロックすることなく、期待されるエラー (`errOffline`) を返すことを検証します。これにより、以前のデッドロック問題が解決されたことが確認されます。

これらの変更により、`database/sql` パッケージは、接続試行が失敗した場合でも、接続プールが適切に状態を更新し、デッドロックに陥ることなく、新しい接続要求を処理できるようになりました。`db.numOpen` の一元化と `db.pendingOpens` の削除は、コードの可読性と保守性を大幅に向上させています。

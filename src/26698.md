# [インデックス 26698] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおいて、定数値をアセンブリ命令に変換する際のバグを修正します。具体的には、8ビット、16ビット、32ビットの定数を使用する際に、`AuxInt`フィールドの上位ビットが未定義であるために、`x86.oclass`が定数のサイズを誤認識し、不正な命令が生成される問題を解決します。この修正は、`ssa.Value`構造体に`AuxInt2Int64()`という新しいヘルパーメソッドを導入し、オペレーションの型に基づいて`AuxInt`を適切に切り詰める（truncate）ことで、この問題を回避します。

## 元コミット内容

このコミットの目的は、GoコンパイラのSSAバックエンドにおいて、8ビット、16ビット、32ビットの定数を使用する際に発生する問題を修正することです。これらの定数の`AuxInt`フィールドの上位ビットが未定義であるため、`x86.oclass`が定数の実際のサイズを誤って解釈し、結果として不正なアセンブリ命令が生成される可能性がありました。この問題は、Issue #14389として報告されていました。

## 変更の背景

Goコンパイラは、ソースコードをSSA形式の中間表現に変換し、その後、ターゲットアーキテクチャ（この場合はx86）のアセンブリコードに変換します。この変換プロセスにおいて、定数値をアセンブリ命令のオペランドとして使用する際、その定数のビット幅（8ビット、16ビット、32ビット、64ビット）を正確に扱う必要があります。

問題は、`ssa.Value`構造体の`AuxInt`フィールドが`int64`型であるにもかかわらず、8ビット、16ビット、32ビットの定数を格納する際に、その上位ビットが適切にクリアされず、未定義のデータが残ってしまうことにありました。例えば、`int8`の定数`5`を`AuxInt`に格納した場合、`AuxInt`は`...00000101`となりますが、`int32`の定数`5`も同じく`...00000101`となります。しかし、`int8`の定数`-1`は`...11111111`となりますが、`int32`の定数`-1`も`...11111111`となります。問題は、`int8`の定数`128`（`0x80`）を`AuxInt`に格納した場合、`int64`としては`0x80`ですが、`int8`としてはオーバーフローし、`int32`としては`0x80`です。もし`AuxInt`が`int8`として扱われるべき定数を含んでいるにもかかわらず、上位ビットがクリアされていないと、`x86.oclass`のようなアセンブリコード生成ロジックが、その定数を誤ったビット幅（例えば、`int64`として）で解釈してしまう可能性がありました。

`x86.oclass`は、x86アーキテクチャのアセンブリ命令のオペランドのクラス（種類やサイズ）を識別するために使用されるコンポーネントです。定数のサイズを誤認識すると、例えば8ビットの定数として扱われるべき値が32ビットの定数として扱われ、結果として間違ったアセンブリ命令（例: `ADDL`の代わりに`ADDQ`）が生成されたり、命令のエンコーディングが不正になったりする可能性がありました。

このコミットは、`AuxInt`から定数を取り出す際に、その定数が本来持つべきビット幅に合わせて上位ビットを切り詰めることで、この問題を解決しようとしています。これにより、`x86.oclass`が常に正しいサイズの定数を認識できるようになります。

## 前提知識の解説

### GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを複数の段階を経て機械語に変換します。その中でも重要なのが、SSA (Static Single Assignment) 形式の中間表現です。SSAは、各変数が一度だけ代入されるという特性を持つ中間表現で、データフロー解析や最適化を容易にします。

GoコンパイラのSSAバックエンドは、SSA形式のコードをターゲットアーキテクチャ（例: x86-64）の低レベルな命令（アセンブリ命令）に変換する役割を担います。このプロセスには、レジスタ割り当て、命令スケジューリング、そして定数やメモリ参照の処理などが含まれます。

### `ssa.Value`と`AuxInt`

GoコンパイラのSSA中間表現において、`ssa.Value`は計算の単一の結果を表す基本的な単位です。各`ssa.Value`は、そのオペレーション（例: `ADD`, `LOAD`, `CONST`など）と、そのオペレーションに必要な引数（他の`ssa.Value`）を持ちます。

`AuxInt`は、`ssa.Value`構造体に含まれるフィールドの一つで、特定のオペレーションに付随する追加の整数定数情報を格納するために使用されます。例えば、`ADDQconst`（定数を加算する命令）のようなオペレーションでは、加算される定数値が`AuxInt`に格納されます。`LOAD`命令では、メモリオフセットが`AuxInt`に格納されることがあります。`AuxInt`は`int64`型として定義されていますが、実際に格納される定数の論理的なサイズは、そのオペレーションの種類によって8ビット、16ビット、32ビット、または64ビットと異なります。

### x86アセンブリにおける定数とビット幅

x86アーキテクチャでは、命令のオペランドとして使用される定数には、そのサイズに応じたエンコーディングがあります。例えば、8ビットの定数は`imm8`、16ビットは`imm16`、32ビットは`imm32`、64ビットは`imm64`として扱われます。コンパイラがアセンブリコードを生成する際、これらの定数を正しく識別し、適切な命令形式とエンコーディングを選択する必要があります。

`x86.oclass`のようなコンポーネントは、この識別プロセスにおいて、定数の値に基づいてその最適なサイズを決定しようとします。例えば、値が`-128`から`127`の範囲にあれば8ビット定数として、`-32768`から`32767`の範囲にあれば16ビット定数として、といった具合です。しかし、`AuxInt`の上位ビットが未定義であると、この識別が誤り、例えば8ビットで十分な定数を32ビット定数として扱ってしまい、結果として不正な命令や非効率なコードが生成される原因となります。

### 符号拡張 (Sign Extension) と切り詰め (Truncation)

*   **符号拡張**: 小さいビット幅の符号付き整数を、より大きいビット幅の符号付き整数に変換する際に、元の値の符号を保持するために上位ビットを符号ビットで埋める処理です。例えば、8ビットの`-1` (バイナリで`11111111`) を16ビットに符号拡張すると、`1111111111111111`となります。
*   **切り詰め (Truncation)**: 大きいビット幅の整数を、より小さいビット幅の整数に変換する際に、上位ビットを単純に破棄する処理です。例えば、`int64`の`0xFFFFFFFF00000005`を`int32`に切り詰めると、`0x00000005`となります。

このコミットでは、`AuxInt`が`int64`であるにもかかわらず、オペレーションによっては8ビット、16ビット、32ビットの定数として扱われる必要があるため、適切な切り詰めを行うことが重要になります。

## 技術的詳細

このコミットの核心は、`src/cmd/compile/internal/ssa/value.go`に`AuxInt2Int64()`という新しいメソッドを導入し、`src/cmd/compile/internal/gc/ssa.go`内の`genValue`関数で`v.AuxInt`を直接参照していた箇所を`v.AuxInt2Int64()`の呼び出しに置き換えた点です。

### `AuxInt2Int64()`の役割

`AuxInt2Int64()`メソッドは、`ssa.Value`が保持する`AuxInt`フィールドの値を、そのオペレーションが期待する実際のビット幅に合わせて適切に変換（切り詰めまたは符号拡張）して`int64`として返すことを目的としています。

```go
// AuxInt2Int64 is used to sign extend the lower bits of AuxInt according to
// the size of AuxInt specified in the opcode table.
func (v *Value) AuxInt2Int64() int64 {
	switch opcodeTable[v.Op].auxType {
	case auxInt64:
		return v.AuxInt
	case auxInt32:
		return int64(int32(v.AuxInt))
	case auxInt16:
		return int64(int16(v.AuxInt))
	case auxInt8:
		return int64(int8(v.AuxInt))
	default:
		v.Fatalf("op %s doesn't have an aux int field", v.Op)
		return -1
	}
}
```

このメソッドは、`opcodeTable[v.Op].auxType`という情報に基づいて、`v.AuxInt`をどのように解釈すべきかを判断します。

*   `auxInt64`: オペレーションが64ビットの定数を期待している場合、`v.AuxInt`の値をそのまま`int64`として返します。
*   `auxInt32`: オペレーションが32ビットの定数を期待している場合、`v.AuxInt`をまず`int32`にキャストし、その後`int64`にキャストします。`int32(v.AuxInt)`のキャストにより、`v.AuxInt`の上位32ビットが切り捨てられ、下位32ビットのみが保持されます。その後、`int64()`へのキャストで、その32ビット値が符号拡張されて`int64`になります。これにより、32ビットの定数として正しい値が`int64`として表現されます。
*   `auxInt16`: 同様に、16ビットの定数を期待している場合は、`int16(v.AuxInt)`で切り詰めと符号拡張が行われます。
*   `auxInt8`: 同様に、8ビットの定数を期待している場合は、`int8(v.AuxInt)`で切り詰めと符号拡張が行われます。

このメカニズムにより、`genValue`関数がアセンブリ命令を生成する際に、常にオペレーションが期待する正確なビット幅の定数値を受け取ることが保証されます。これにより、`x86.oclass`が定数のサイズを誤認識する問題が解消されます。

### `genValue`関数における変更

`src/cmd/compile/internal/gc/ssa.go`の`genValue`関数は、SSA形式の`ssa.Value`オブジェクトを受け取り、対応するアセンブリ命令（`obj.Prog`）を生成する役割を担っています。この関数内で、定数オペランドとして`v.AuxInt`を直接使用していた箇所が、すべて`v.AuxInt2Int64()`の呼び出しに置き換えられました。

例えば、以下のような変更が行われています。

```diff
- if v.AuxInt == 1 {
+ if v.AuxInt2Int64() == 1 {
```

```diff
- p.From.Offset = v.AuxInt
+ p.From.Offset = v.AuxInt2Int64()
```

これらの変更により、`genValue`関数は、`AuxInt`の生の値ではなく、オペレーションの型に基づいて適切に処理された定数値を使用するようになります。

### テストケースの追加

`src/cmd/compile/internal/gc/testdata/arith_ssa.go`には、`testLargeConst()`という新しいテスト関数が追加されました。このテストは、32ビットを超える定数が`ADDL`命令に渡された場合に発生していた不正な命令エラーを再現し、修正が正しく機能することを確認します。

`invalidAdd_ssa`, `invalidSub_ssa`, `invalidMul_ssa`といった関数が追加され、`0x0fffFFFF`という定数を複数回加算・減算・乗算することで、`AuxInt`がオーバーフローし、上位ビットが未定義になる状況を意図的に作り出しています。`testLargeConst`は、これらの関数が期待通りの結果を返すことを検証し、コンパイラが定数を正しく処理していることを確認します。

## コアとなるコードの解説

このコミットの主要な変更は、`ssa.Value`の`AuxInt`フィールドが保持する定数値を、その定数が実際に使用されるオペレーションのビット幅に合わせて正確に解釈するための`AuxInt2Int64()`ヘルパーメソッドの導入と、そのメソッドを`genValue`関数内で適用した点にあります。

以前は、`AuxInt`が`int64`型であるため、8ビット、16ビット、32ビットの定数を格納する際に、その上位ビットが未定義のまま残ることがありました。例えば、`int8`の定数`5`を`AuxInt`に格納した場合、`AuxInt`は`0x0000000000000005`となります。しかし、もし`AuxInt`が`int8`の範囲を超える値（例えば`0x105`）を保持していた場合、`int8`として解釈されるべき場所で`AuxInt`を直接使用すると、上位ビットの`0x1`が無視され、`0x05`として扱われる可能性があります。逆に、`int8`の定数`-1`は`0xFF`ですが、`int64`としては`0xFFFFFFFFFFFFFFFF`となります。もし`AuxInt`が`int8`の定数`-1`を保持しているにもかかわらず、`int32`の定数として扱われるべき場所で`AuxInt`を直接使用すると、`int32`の`-1`として正しく解釈されるかもしれませんが、これは偶然に過ぎません。

この問題は、特に`x86.oclass`のようなアセンブリコード生成ロジックが、定数の値に基づいてその最適なビット幅を決定しようとする際に顕在化します。`AuxInt`の上位ビットが未定義であると、`x86.oclass`は定数を誤ったビット幅で解釈し、結果として不正なアセンブリ命令を生成してしまう可能性がありました。

`AuxInt2Int64()`メソッドは、この問題を解決するために、オペレーションの`auxType`（`auxInt8`, `auxInt16`, `auxInt32`, `auxInt64`）に基づいて、`AuxInt`の値を適切なビット幅に切り詰め、その後`int64`に符号拡張して返します。

*   `int64(int32(v.AuxInt))`: `v.AuxInt`をまず`int32`にキャストすることで、上位32ビットが破棄され、下位32ビットのみが残ります。その後、`int64`にキャストすることで、その32ビット値が符号拡張されて`int64`として表現されます。これにより、32ビットの定数として正しい値が保証されます。
*   `int64(int16(v.AuxInt))`: 同様に、`int16`にキャストすることで、上位48ビットが破棄され、下位16ビットが残り、その後`int64`に符号拡張されます。
*   `int64(int8(v.AuxInt))`: 同様に、`int8`にキャストすることで、上位56ビットが破棄され、下位8ビットが残り、その後`int64`に符号拡張されます。

この変更により、`genValue`関数は、アセンブリ命令を生成する際に、常にオペレーションが期待する正確なビット幅の定数値を受け取ることが保証されます。これにより、`x86.oclass`が定数のサイズを誤認識する問題が解消され、コンパイラがより堅牢で正確なアセンブリコードを生成できるようになります。

追加されたテストケース`testLargeConst`は、この修正が正しく機能することを検証します。特に、`uint32`の定数`0x0fffFFFF`を繰り返し加算・減算・乗算することで、`AuxInt`が32ビットの範囲を超え、上位ビットが未定義になる状況をシミュレートしています。このテストが成功することで、`AuxInt2Int64()`による適切な切り詰めと符号拡張が、このようなエッジケースでも正しく機能していることが確認されます。

## 元コミット内容

このコミットの目的は、GoコンパイラのSSAバックエンドにおいて、8ビット、16ビット、32ビットの定数を使用する際に発生する問題を修正することです。これらの定数の`AuxInt`フィールドの上位ビットが未定義であるため、`x86.oclass`が定数の実際のサイズを誤って解釈し、結果として不正なアセンブリ命令が生成される可能性がありました。この問題は、Issue #14389として報告されていました。

## 変更の背景

Goコンパイラは、ソースコードをSSA形式の中間表現に変換し、その後、ターゲットアーキテクチャ（この場合はx86）のアセンブリコードに変換します。この変換プロセスにおいて、定数値をアセンブリ命令のオペランドとして使用する際、その定数のビット幅（8ビット、16ビット、32ビット、64ビット）を正確に扱う必要があります。

問題は、`ssa.Value`構造体の`AuxInt`フィールドが`int64`型であるにもかかわらず、8ビット、16ビット、32ビットの定数を格納する際に、その上位ビットが適切にクリアされず、未定義のデータが残ってしまうことにありました。例えば、`int8`の定数`5`を`AuxInt`に格納した場合、`AuxInt`は`...00000101`となりますが、`int32`の定数`5`も同じく`...00000101`となります。問題は、`int8`の定数`128`（`0x80`）を`AuxInt`に格納した場合、`int64`としては`0x80`ですが、`int8`としてはオーバーフローし、`int32`としては`0x80`です。もし`AuxInt`が`int8`として扱われるべき定数を含んでいるにもかかわらず、上位ビットがクリアされていないと、`x86.oclass`のようなアセンブリコード生成ロジックが、その定数を誤ったビット幅（例えば、`int64`として）で解釈してしまう可能性がありました。

`x86.oclass`は、x86アーキテクチャのアセンブリ命令のオペランドのクラス（種類やサイズ）を識別するために使用されるコンポーネントです。定数のサイズを誤認識すると、例えば8ビットの定数として扱われるべき値が32ビットの定数として扱われ、結果として間違ったアセンブリ命令（例: `ADDL`の代わりに`ADDQ`）が生成されたり、命令のエンコーディングが不正になったりする可能性がありました。

このコミットは、`AuxInt`から定数を取り出す際に、その定数が本来持つべきビット幅に合わせて上位ビットを切り詰めることで、この問題を解決しようとしています。これにより、`x86.oclass`が常に正しいサイズの定数を認識できるようになります。

## 前提知識の解説

### GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを複数の段階を経て機械語に変換します。その中でも重要なのが、SSA (Static Single Assignment) 形式の中間表現です。SSAは、各変数が一度だけ代入されるという特性を持つ中間表現で、データフロー解析や最適化を容易にします。

GoコンパイラのSSAバックエンドは、SSA形式のコードをターゲットアーキテクチャ（例: x86-64）の低レベルな命令（アセンブリ命令）に変換する役割を担います。このプロセスには、レジスタ割り当て、命令スケジューリング、そして定数やメモリ参照の処理などが含まれます。

### `ssa.Value`と`AuxInt`

GoコンパイラのSSA中間表現において、`ssa.Value`は計算の単一の結果を表す基本的な単位です。各`ssa.Value`は、そのオペレーション（例: `ADD`, `LOAD`, `CONST`など）と、そのオペレーションに必要な引数（他の`ssa.Value`）を持ちます。

`AuxInt`は、`ssa.Value`構造体に含まれるフィールドの一つで、特定のオペレーションに付随する追加の整数定数情報を格納するために使用されます。例えば、`ADDQconst`（定数を加算する命令）のようなオペレーションでは、加算される定数値が`AuxInt`に格納されます。`LOAD`命令では、メモリオフセットが`AuxInt`に格納されることがあります。`AuxInt`は`int64`型として定義されていますが、実際に格納される定数の論理的なサイズは、そのオペレーションの種類によって8ビット、16ビット、32ビット、または64ビットと異なります。

### x86アセンブリにおける定数とビット幅

x86アーキテクチャでは、命令のオペランドとして使用される定数には、そのサイズに応じたエンコーディングがあります。例えば、8ビットの定数は`imm8`、16ビットは`imm16`、32ビットは`imm32`、64ビットは`imm64`として扱われます。コンパイラがアセンブリコードを生成する際、これらの定数を正しく識別し、適切な命令形式とエンコーディングを選択する必要があります。

`x86.oclass`のようなコンポーネントは、この識別プロセスにおいて、定数の値に基づいてその最適なサイズを決定しようとします。例えば、値が`-128`から`127`の範囲にあれば8ビット定数として、`-32768`から`32767`の範囲にあれば16ビット定数として、といった具合です。しかし、`AuxInt`の上位ビットが未定義であると、この識別が誤り、例えば8ビットで十分な定数を32ビット定数として扱ってしまい、結果として不正な命令や非効率なコードが生成される原因となります。

### 符号拡張 (Sign Extension) と切り詰め (Truncation)

*   **符号拡張**: 小さいビット幅の符号付き整数を、より大きいビット幅の符号付き整数に変換する際に、元の値の符号を保持するために上位ビットを符号ビットで埋める処理です。例えば、8ビットの`-1` (バイナリで`11111111`) を16ビットに符号拡張すると、`1111111111111111`となります。
*   **切り詰め (Truncation)**: 大きいビット幅の整数を、より小さいビット幅の整数に変換する際に、上位ビットを単純に破棄する処理です。例えば、`int64`の`0xFFFFFFFF00000005`を`int32`に切り詰めると、`0x00000005`となります。

このコミットでは、`AuxInt`が`int64`であるにもかかわらず、オペレーションによっては8ビット、16ビット、32ビットの定数として扱われる必要があるため、適切な切り詰めを行うことが重要になります。

## 技術的詳細

### `AuxInt2Int64()`の役割

`AuxInt2Int64()`メソッドは、`ssa.Value`が保持する`AuxInt`フィールドの値を、そのオペレーションが期待する実際のビット幅に合わせて適切に変換（切り詰めまたは符号拡張）して`int64`として返すことを目的としています。

```go
// AuxInt2Int64 is used to sign extend the lower bits of AuxInt according to
// the size of AuxInt specified in the opcode table.
func (v *Value) AuxInt2Int64() int64 {
	switch opcodeTable[v.Op].auxType {
	case auxInt64:
		return v.AuxInt
	case auxInt32:
		return int64(int32(v.AuxInt))
	case auxInt16:
		return int64(int16(v.AuxInt))
	case auxInt8:
		return int64(int8(v.AuxInt))
	default:
		v.Fatalf("op %s doesn't have an aux int field", v.Op)
		return -1
	}
}
```

このメソッドは、`opcodeTable[v.Op].auxType`という情報に基づいて、`v.AuxInt`をどのように解釈すべきかを判断します。

*   `auxInt64`: オペレーションが64ビットの定数を期待している場合、`v.AuxInt`の値をそのまま`int64`として返します。
*   `auxInt32`: オペレーションが32ビットの定数を期待している場合、`v.AuxInt`をまず`int32`にキャストし、その後`int64`にキャストします。`int32(v.AuxInt)`のキャストにより、`v.AuxInt`の上位32ビットが切り捨てられ、下位32ビットのみが保持されます。その後、`int64()`へのキャストで、その32ビット値が符号拡張されて`int64`になります。これにより、32ビットの定数として正しい値が`int64`として表現されます。
*   `auxInt16`: 同様に、16ビットの定数を期待している場合は、`int16(v.AuxInt)`で切り詰めと符号拡張が行われます。
*   `auxInt8`: 同様に、8ビットの定数を期待している場合は、`int8(v.AuxInt)`で切り詰めと符号拡張が行われます。

このメカニズムにより、`genValue`関数がアセンブリ命令を生成する際に、常にオペレーションが期待する正確なビット幅の定数値を受け取ることが保証されます。これにより、`x86.oclass`が定数のサイズを誤認識する問題が解消されます。

## コアとなるコードの解説

このコミットの主要な変更は、`ssa.Value`の`AuxInt`フィールドが保持する定数値を、その定数が実際に使用されるオペレーションのビット幅に合わせて正確に解釈するための`AuxInt2Int64()`ヘルパーメソッドの導入と、そのメソッドを`genValue`関数内で適用した点にあります。

以前は、`AuxInt`が`int64`型であるため、8ビット、16ビット、32ビットの定数を格納する際に、その上位ビットが未定義のまま残ることがありました。例えば、`int8`の定数`5`を`AuxInt`に格納した場合、`AuxInt`は`0x0000000000000005`となります。しかし、もし`AuxInt`が`int8`の範囲を超える値（例えば`0x105`）を保持していた場合、`int8`として解釈されるべき場所で`AuxInt`を直接使用すると、上位ビットの`0x1`が無視され、`0x05`として扱われる可能性があります。逆に、`int8`の定数`-1`は`0xFF`ですが、`int64`としては`0xFFFFFFFFFFFFFFFF`となります。もし`AuxInt`が`int8`の定数`-1`を保持しているにもかかわらず、`int32`の定数として扱われるべき場所で`AuxInt`を直接使用すると、`int32`の`-1`として正しく解釈されるかもしれませんが、これは偶然に過ぎません。

この問題は、特に`x86.oclass`のようなアセンブリコード生成ロジックが、定数の値に基づいてその最適なビット幅を決定しようとする際に顕在化します。`AuxInt`の上位ビットが未定義であると、`x86.oclass`は定数を誤ったビット幅で解釈し、結果として不正なアセンブリ命令を生成してしまう可能性がありました。

`AuxInt2Int64()`メソッドは、この問題を解決するために、オペレーションの`auxType`（`auxInt8`, `auxInt16`, `auxInt32`, `auxInt64`）に基づいて、`AuxInt`の値を適切なビット幅に切り詰め、その後`int64`に符号拡張して返します。

*   `int64(int32(v.AuxInt))`: `v.AuxInt`をまず`int32`にキャストすることで、上位32ビットが破棄され、下位32ビットのみが残ります。その後、`int64`にキャストすることで、その32ビット値が符号拡張されて`int64`として表現されます。これにより、32ビットの定数として正しい値が保証されます。
*   `int64(int16(v.AuxInt))`: 同様に、`int16`にキャストすることで、上位48ビットが破棄され、下位16ビットが残り、その後`int64`に符号拡張されます。
*   `int64(int8(v.AuxInt))`: 同様に、`int8`にキャストすることで、上位56ビットが破棄され、下位8ビットが残り、その後`int64`に符号拡張されます。

この変更により、`genValue`関数は、アセンブリ命令を生成する際に、常にオペレーションが期待する正確なビット幅の定数値を受け取ることが保証されます。これにより、`x86.oclass`が定数のサイズを誤認識する問題が解消され、コンパイラがより堅牢で正確なアセンブリコードを生成できるようになります。

追加されたテストケース`testLargeConst`は、この修正が正しく機能することを検証します。特に、`uint32`の定数`0x0fffFFFF`を繰り返し加算・減算・乗算することで、`AuxInt`が32ビットの範囲を超え、上位ビットが未定義になる状況をシミュレートしています。このテストが成功することで、`AuxInt2Int64()`による適切な切り詰めと符号拡張が、このようなエッジケースでも正しく機能していることが確認されます。

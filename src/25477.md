## 元コミット内容

このコミットは、Goコンパイラが `if` や `for` ステートメント内の `&&` (ANDAND) および `||` (OROR) 演算子を処理する方法を改善します。

以前のコードでは、`if a && b { target }` のようなステートメントに対して、以下のようなコードを生成していました。

```
v = a
if a {
   v = b
}
if v { goto target }
```

これは、一時変数 `v` を割り当て、`a` の評価結果を `v` に格納し、`a` が真の場合にのみ `b` を評価してその結果を `v` に格納し、最終的に `v` の値に基づいて `target` へジャンプするというものでした。このアプローチでは、2つの結合点（`if a` の後と `if v` の後）が存在しました。

新しいコードでは、同じステートメントに対して以下のようなコードを生成します。

```
if a {
  if b { goto target }
}
```

この新しいアプローチでは、一時変数を必要とせず、`a` が真の場合にのみ `b` を評価し、両方が真であれば `target` へジャンプします。これにより、結合点が1つに減少し、より効率的なコードが生成されます。

ただし、この改善は `if` または `for` ステートメントの直接の子孫ではない `ANDAND` および `OROR` 演算子には適用されず、それらのケースでは古いコード生成ロジックが引き続き使用されます。

## 変更の背景

コンパイラ最適化の主要な目標の一つは、生成される機械語コードの効率を最大化することです。特に、条件分岐はプログラムの実行フローを大きく左右するため、その生成方法はパフォーマンスに直結します。

Goコンパイラは、コードをSSA (Static Single Assignment) 形式に変換し、その上で様々な最適化を適用します。論理AND (`&&`) や論理OR (`||`) のような短絡評価（short-circuit evaluation）を行う演算子は、その性質上、条件分岐を伴います。

以前の実装では、`if a && b` のような短絡評価を伴う条件式をSSA形式に変換する際に、一時変数を導入し、複数の結合点を持つ複雑な制御フローグラフを生成していました。これは、コンパイラが条件式を評価し、その結果を一時的に保持する必要があるためです。しかし、このような一時変数や余分な結合点は、その後の最適化パスにおいてオーバーヘッドとなり、最終的な機械語コードの効率を低下させる可能性がありました。

このコミットの背景には、GoコンパイラのSSAバックエンドが成熟するにつれて、より洗練された制御フローの最適化が可能になったことがあります。特に、`if` や `for` のような制御構造の条件式は、プログラムの実行頻度が高いため、これらの部分のコード生成を最適化することは、全体的なパフォーマンス向上に大きく貢献します。一時変数を排除し、結合点を減らすことで、データフロー解析が単純化され、レジスタ割り当てが改善され、結果としてより高速でコンパクトなコードが生成されることが期待されます。

## 前提知識の解説

### 1. Goコンパイラの構造とSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを機械語に変換する過程で、複数のフェーズを経ます。主要なフェーズの一つが、中間表現 (IR: Intermediate Representation) への変換と最適化です。Go 1.7以降、コンパイラのバックエンドはSSA形式をベースとした新しいものに移行しました。

*   **SSA形式**: Static Single Assignment (静的単一割り当て) 形式は、コンパイラ最適化のために設計された中間表現の一種です。SSA形式では、各変数が一度だけ割り当てられることが保証されます。これにより、データフロー解析が大幅に簡素化され、デッドコード削除、共通部分式除去、定数伝播などの強力な最適化を適用しやすくなります。
*   **`cmd/compile/internal/gc`**: これはGoコンパイラの主要な部分であり、Go言語のフロントエンド（構文解析、型チェックなど）と、SSA形式への変換およびバックエンド（コード生成）の間の橋渡しをします。このコミットで変更されている `ssa.go` ファイルは、AST (Abstract Syntax Tree) からSSA形式への変換ロジックを担う部分です。

### 2. 論理AND (`&&`) と論理OR (`||`) の短絡評価 (Short-Circuit Evaluation)

Go言語を含む多くのプログラミング言語では、論理AND (`&&`) と論理OR (`||`) 演算子に対して短絡評価が適用されます。

*   **`A && B`**: `A` が `false` と評価された場合、式全体の評価結果はすでに `false` であることが確定するため、`B` は評価されません。
*   **`A || B`**: `A` が `true` と評価された場合、式全体の評価結果はすでに `true` であることが確定するため、`B` は評価されません。

この短絡評価は、プログラマが意図的に副作用のある式を安全に記述したり、パフォーマンスを向上させたりするために利用されます（例: `if ptr != nil && ptr.field > 0`）。コンパイラは、この短絡評価のセマンティクスを正確に反映したコードを生成する必要があります。

### 3. 制御フローグラフ (Control Flow Graph, CFG) と結合点 (Join Point)

*   **制御フローグラフ**: プログラムの実行可能なすべてのパスを抽象的に表現したグラフです。ノードは基本的なブロック（連続した命令のシーケンス）を表し、エッジはブロック間の可能な遷移を表します。
*   **結合点**: 複数の異なる実行パスが合流する点（ブロック）を指します。結合点が多いほど、コンパイラはデータフローを追跡し、最適化を適用するのが難しくなる傾向があります。特にSSA形式では、結合点において φ関数 (phi function) を導入して、異なるパスから来る同じ論理変数の値を統合する必要があります。φ関数は、コンパイル時のオーバーヘッドを伴うため、結合点を減らすことは最適化に繋がります。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおける条件分岐の生成ロジック、特に `if` および `for` ステートメント内の複合条件式 (`&&` や `||`) の扱いを改善することにあります。

### 従来のコード生成の問題点

コミットメッセージに示されているように、`if a && b { target }` のようなケースでは、従来のコードは以下のようなSSAブロックと値の生成を行っていました（概念的な表現）：

1.  `a` を評価し、その結果を一時変数 `v` に格納。
2.  `a` が真の場合にのみ `b` を評価し、その結果を `v` に格納（つまり、`v` の再割り当て）。
3.  最終的な `v` の値に基づいて `target` へ分岐。

このプロセスは、以下の点で非効率でした。

*   **一時変数の導入**: `v` という一時変数が導入され、その値が条件付きで更新されます。SSA形式では、これは `v` の複数のバージョン（`v1`, `v2` など）と、それらを結合するφ関数の導入を意味します。
*   **複数の結合点**: `if a` の条件分岐の後と、`if v` の条件分岐の後の2箇所で実行パスが合流する可能性がありました。これにより、制御フローグラフが複雑になり、φ関数の数が増加し、コンパイラのデータフロー解析やレジスタ割り当てが難しくなります。

### 新しい `condBranch` 関数による改善

このコミットでは、`state` 構造体に `condBranch` という新しいメソッドが導入されています。この関数は、与えられた条件式 `cond` を評価し、その結果に基づいて `yes` ブロックまたは `no` ブロックへ分岐する処理を抽象化します。

`condBranch` の重要な点は、`cond` が `OANDAND` (&&) または `OOROR` (||) である場合に、再帰的に自身を呼び出すことで、短絡評価のロジックを直接SSAの制御フローにマッピングする点です。

#### `OANDAND` (&&) の処理 (`condBranch(cond.Left, mid, no, ...)` と `condBranch(cond.Right, yes, no, ...)`):

`if a && b { target }` のようなケースを考えます。`condBranch(a && b, yesBlock, noBlock, ...)` が呼び出された場合：

1.  まず `a` を評価する条件分岐 `condBranch(a, midBlock, noBlock, ...)` を生成します。
    *   `a` が `false` ならば、直接 `noBlock` へ分岐します（短絡評価）。
    *   `a` が `true` ならば、`midBlock` へ進みます。
2.  `midBlock` に到達した場合、次に `b` を評価する条件分岐 `condBranch(b, yesBlock, noBlock, ...)` を生成します。
    *   `b` が `true` ならば、`yesBlock` へ分岐します。
    *   `b` が `false` ならば、`noBlock` へ分岐します。

この構造は、コミットメッセージで示された `if a { if b { goto target } }` と全く同じ制御フローをSSA形式で表現します。

*   **一時変数の排除**: `a` や `b` の評価結果を保持するための一時変数は不要になります。条件式の評価結果は、直接制御フローの遷移に利用されます。
*   **結合点の削減**: `a` が `false` のパスと `b` が `false` のパスは、最終的に `noBlock` で合流します。`a` と `b` が両方 `true` のパスは `yesBlock` へ向かいます。これにより、従来の2つの結合点ではなく、実質的に1つの主要な結合点（`noBlock`）に集約されます。

#### `OOROR` (||) の処理も同様に最適化されます。

`if a || b { target }` のようなケースでは：

1.  まず `a` を評価する条件分岐 `condBranch(a, yesBlock, midBlock, ...)` を生成します。
    *   `a` が `true` ならば、直接 `yesBlock` へ分岐します（短絡評価）。
    *   `a` が `false` ならば、`midBlock` へ進みます。
2.  `midBlock` に到達した場合、次に `b` を評価する条件分岐 `condBranch(b, yesBlock, noBlock, ...)` を生成します。
    *   `b` が `true` ならば、`yesBlock` へ分岐します。
    *   `b` が `false` ならば、`noBlock` へ分岐します。

### `likely` ヒントの伝播

`condBranch` 関数は `likely` という引数も受け取ります。これは、分岐がどちらのパスに進む可能性が高いかを示すヒント（-1: unlikely, 0: unknown, +1: likely）であり、コンパイラがより効率的な機械語命令（例: プロセッサの分岐予測を助ける命令）を生成するために利用されます。`OANDAND` や `OOROR` の再帰呼び出しでは、この `likely` ヒントが適切に伝播または調整されるロジックも含まれています。

### 適用範囲の限定

コミットメッセージにあるように、この最適化は `if` または `for` ステートメントの直接の子孫である `ANDAND` および `OROR` 演算子に限定されます。これは、これらの制御構造の条件式が、最も頻繁に実行され、最適化の効果が大きいと判断されたためと考えられます。他のコンテキスト（例: 変数への代入 `x = a && b`）では、一時変数を使った従来のコード生成が引き続き行われます。これは、コンパイラの複雑性を管理し、最も影響の大きい部分から最適化を進める一般的なアプローチです。

## コアとなるコードの変更箇所

変更は `src/cmd/compile/internal/gc/ssa.go` ファイルに集中しています。

1.  **`stmt(n *Node)` メソッド内の `OIF` および `OFOR` ケースの変更**:
    *   `OIF` (ifステートメント) の処理において、条件式 `n.Left` の評価と分岐ロジックが、新しく導入された `s.condBranch` 関数を呼び出すように変更されています。これにより、従来のSSAブロックと値の直接的な生成ロジックが削除され、より抽象化された `condBranch` に委譲されます。
    *   `OFOR` (forステートメント) の処理においても、ループ条件の評価と分岐ロジックが `s.condBranch` を使用するように変更されています。特に、無限ループ (`for {}`) のケースも考慮されています。

2.  **新しい `condBranch` 関数の追加**:
    *   `func (s *state) condBranch(cond *Node, yes, no *ssa.Block, likely int8)` という新しいメソッドが `state` 構造体に追加されました。
    *   この関数は、`cond` が `OANDAND` または `OOROR` である場合に、再帰的に自身を呼び出して短絡評価の制御フローを構築します。
    *   それ以外の条件式の場合（単純な比較など）、`s.expr(cond)` でSSA値を生成し、その値に基づいて `ssa.BlockIf` タイプのブロックを作成し、`yes` および `no` ブロックへのエッジを追加します。

#### 新しい `condBranch` 関数

```go
// condBranch evaluates the boolean expression cond and branches to yes
// if cond is true and no if cond is false.
// This function is intended to handle && and || better than just calling
// s.expr(cond) and branching on the result.
func (s *state) condBranch(cond *Node, yes, no *ssa.Block, likely int8) {
	if cond.Op == OANDAND {
		mid := s.f.NewBlock(ssa.BlockPlain)
		s.stmtList(cond.Ninit)
		s.condBranch(cond.Left, mid, no, max8(likely, 0))
		s.startBlock(mid)
		s.condBranch(cond.Right, yes, no, likely)
		return
		// Note: if likely==1, then both recursive calls pass 1.
		// If likely==-1, then we don't have enough information to decide
		// whether the first branch is likely or not.  So we pass 0 for
		// the likeliness of the first branch.
		// TODO: have the frontend give us branch prediction hints for
		// OANDAND and OOROR nodes (if it ever has such info).
	}
	if cond.Op == OOROR {
		mid := s.f.NewBlock(ssa.BlockPlain)
		s.stmtList(cond.Ninit)
		s.condBranch(cond.Left, yes, mid, min8(likely, 0))
		s.startBlock(mid)
		s.condBranch(cond.Right, yes, no, likely)
		return
		// Note: if likely==-1, then both recursive calls pass -1.
		// If likely==1, then we don't have enough info to decide
		// the likelihood of the first branch.
	}
	c := s.expr(cond)
	b := s.endBlock()
	b.Kind = ssa.BlockIf
	b.Control = c
	b.Likely = ssa.BranchPrediction(likely) // gc and ssa both use -1/0/+1 for likeliness
	b.AddEdgeTo(yes)
	b.AddEdgeTo(no)
}
```

*   **`cond.Op == OANDAND` の処理**:
    *   `mid := s.f.NewBlock(ssa.BlockPlain)`: `a && b` の `a` が真だった場合に `b` を評価するために一時的に経由する中間ブロック `mid` を作成します。
    *   `s.stmtList(cond.Ninit)`: 条件式に付随する初期化ステートメント（例: `if x := f(); x > 0 && x < 10` の `x := f()`）を処理します。
    *   `s.condBranch(cond.Left, mid, no, max8(likely, 0))`: 左オペランド `cond.Left` (`a`) を評価します。
        *   `a` が真なら `mid` ブロックへ。
        *   `a` が偽なら `no` ブロックへ（短絡評価）。
        *   `likely` ヒントは、`max8(likely, 0)` で調整されます。これは、`likely` が負の値（unlikely）であっても、最初の分岐は少なくとも不明（0）として扱うことを意味します。
    *   `s.startBlock(mid)`: `mid` ブロックを開始します。
    *   `s.condBranch(cond.Right, yes, no, likely)`: 右オペランド `cond.Right` (`b`) を評価します。
        *   `b` が真なら `yes` ブロックへ。
        *   `b` が偽なら `no` ブロックへ。
        *   `likely` ヒントはそのまま伝播されます。
    *   この再帰的な構造により、`if a { if b { goto target } }` と同等の効率的な制御フローがSSA形式で構築されます。

*   **`cond.Op == OOROR` の処理**:
    *   `OANDAND` と同様に、中間ブロック `mid` を使用して再帰的に処理されます。
    *   `s.condBranch(cond.Left, yes, mid, min8(likely, 0))`: 左オペランド `cond.Left` (`a`) を評価します。
        *   `a` が真なら `yes` ブロックへ（短絡評価）。
        *   `a` が偽なら `mid` ブロックへ。
        *   `likely` ヒントは `min8(likely, 0)` で調整されます。これは、`likely` が正の値（likely）であっても、最初の分岐は少なくとも不明（0）として扱うことを意味します。
    *   `s.startBlock(mid)`: `mid` ブロックを開始します。
    *   `s.condBranch(cond.Right, yes, no, likely)`: 右オペランド `cond.Right` (`b`) を評価します。
        *   `b` が真なら `yes` ブロックへ。
        *   `b` が偽なら `no` ブロックへ。
        *   `likely` ヒントはそのまま伝播されます。

*   **その他の条件式**:
    *   `c := s.expr(cond)`: `&&` や `||` ではない単純な条件式（例: `x > 0`）の場合、`s.expr` を呼び出してその条件式に対応するSSA値 `c` を生成します。
    *   `b := s.endBlock()`: 現在のブロックを終了します。
    *   `b.Kind = ssa.BlockIf`: 新しいブロックのタイプを条件分岐ブロック (`BlockIf`) に設定します。
    *   `b.Control = c`: 生成されたSSA値 `c` をこのブロックの制御値として設定します。
    *   `b.Likely = ssa.BranchPrediction(likely)`: 分岐予測ヒントを設定します。
    *   `b.AddEdgeTo(yes)` と `b.AddEdgeTo(no)`: `yes` ブロックと `no` ブロックへのエッジを追加し、制御フローを確立します。

この `condBranch` 関数は、短絡評価のセマンティクスをSSAの制御フローグラフに直接、かつ効率的にマッピングするための中心的な役割を担っています。これにより、一時変数の割り当てや余分なφ関数の生成が回避され、より最適化された機械語コードの生成が可能になります。

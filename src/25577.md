## 変更の背景

Goのガベージコレクタ（GC）は、プログラムの実行中に不要になったメモリを自動的に解放する役割を担っています。GCが正しく動作するためには、プログラムがポインタを書き換える際に、GCがその変更を追跡できるように特別な処理を挿入する必要があります。これが「ライトバリア（write barrier）」です。ライトバリアは、GCがオブジェクトグラフを正確にスキャンし、到達可能なオブジェクトを特定するために不可欠ですが、その実行にはオーバーヘッドが伴います。

このコミットの背景には、Goランタイムのトレーシング機能（特にスタックトレースの記録）において、`traceStack`構造体へのポインタの書き込みがライトバリアをトリガーし、GCのパフォーマンスに影響を与えていたという問題があります。トレーシング機能はデバッグやプロファイリングに利用されますが、そのオーバーヘッドは可能な限り小さく保つ必要があります。

先行するコミットでも同様の最適化が行われており、このコミットはその流れを汲むものです。特定のデータ構造がGCによって管理される必要がない、あるいはGCの介入がパフォーマンス上のボトルネックとなる場合に、ライトバリアを回避する手法が検討されました。

## 前提知識の解説

### ガベージコレクタ (GC) とライトバリア (Write Barrier)

GoのGCは、並行（concurrent）かつ低遅延（low-latency）なマーク＆スイープ方式を採用しています。GCサイクル中、プログラムは実行を継続できますが、GCがオブジェクトグラフを正確に追跡するためには、プログラムがポインタを書き換える際にGCに通知する必要があります。この通知メカニズムがライトバリアです。

ライトバリアは、ポインタの書き込み操作（例: `obj.field = newPtr`）が発生した際に、GCがその変更を認識し、必要に応じて古いポインタが指していたオブジェクトをマークしたり、新しいポインタが指すオブジェクトをマークしたりする処理を挿入します。これにより、GCは常に正確なオブジェクトグラフを把握し、誤って使用中のメモリを解放してしまうことを防ぎます。

しかし、ライトバリアは追加の処理であるため、プログラムの実行速度を低下させる可能性があります。特に、頻繁にポインタが書き換えられるようなホットパスでは、ライトバリアのオーバーヘッドが顕著になることがあります。

### `uintptr` と `unsafe.Pointer`

Goには、メモリを直接操作するための`unsafe`パッケージが提供されています。このパッケージには、以下の2つの重要な型が含まれています。

*   **`uintptr`**: 符号なし整数型で、ポインタのビットパターンを保持するのに十分な大きさがあります。`uintptr`は整数であり、GCは`uintptr`型の値がメモリ上のオブジェクトを指しているとは認識しません。したがって、`uintptr`に変換されたポインタはGCの追跡対象外となります。
*   **`unsafe.Pointer`**: 任意の型のポインタと、`uintptr`の間で相互変換が可能な特殊なポインタ型です。`unsafe.Pointer`は、Goの型システムをバイパスして、異なる型のポインタ間で変換を行うことを可能にします。これは非常に強力ですが、誤用するとメモリ安全性の問題を引き起こす可能性があるため、「unsafe」と名付けられています。

このコミットでは、`*traceStack`（GCの追跡対象）を`traceStackPtr`（実体は`uintptr`、GCの追跡対象外）に変換することで、ライトバリアの発生を回避しています。必要に応じて`traceStackPtr`を`*traceStack`に戻す際には`unsafe.Pointer`を介して行われます。

### Issue #10600

Go issue #10600は、「runtime: write barriers on trace.go are too expensive」というタイトルで、`trace.go`におけるライトバリアのコストが高いことを指摘しています。特に、`traceStackTable`が`*traceStack`の配列を保持しているため、この配列への書き込みがライトバリアをトリガーし、GCのオーバーヘッドを増加させていました。このコミットは、このパフォーマンス問題を解決するための直接的な対応策です。

## 技術的詳細

このコミットの核心は、`traceStack`構造体へのポインタをGCの追跡対象から外すことで、ライトバリアの発生を抑制することです。

1.  **`traceStackPtr`型の導入**:
    `type traceStackPtr uintptr`
    新しい型`traceStackPtr`が導入され、その基盤となる型は`uintptr`です。これにより、`traceStackPtr`型の変数は、Goの型システム上は単なる整数として扱われ、GCはこれをポインタとして認識しません。

2.  **`traceStackPtr.ptr()`メソッド**:
    `func (tp traceStackPtr) ptr() *traceStack { return (*traceStack)(unsafe.Pointer(tp)) }`
    `traceStackPtr`型には、自身を`*traceStack`型に変換するための`ptr()`メソッドが追加されました。この変換は`unsafe.Pointer`を介して行われます。これにより、`traceStackPtr`に格納されたアドレスを、必要に応じて実際の`traceStack`構造体へのポインタとして利用できるようになります。

3.  **`traceStackTable`の変更**:
    `traceStackTable`構造体の`tab`フィールドの型が`[1 << 13]*traceStack`から`[1 << 13]traceStackPtr`に変更されました。
    これにより、`traceStackTable`が保持するスタックへの参照は、GCの追跡対象となるポインタではなく、単なる`uintptr`の配列となります。この配列への書き込みはライトバリアをトリガーしなくなります。

4.  **`traceStack`の変更**:
    `traceStack`構造体の`link`フィールドの型が`*traceStack`から`traceStackPtr`に変更されました。
    `traceStack`はリンクリストを形成しており、次の`traceStack`へのポインタを`link`フィールドに保持しています。この変更により、リンクリストの接続もGCの追跡対象外となり、ライトバリアが不要になります。

5.  **ポインタ参照の更新**:
    `traceStackTable`の`find`メソッドと`dump`メソッド内で、`stk.link`による次の要素へのアクセスが`stk.link.ptr()`に変更されました。これは、`link`が`traceStackPtr`型になったため、実際の`*traceStack`ポインタとして利用する際に`ptr()`メソッドを呼び出す必要があるためです。

この変更により、`traceStackTable`や`traceStack`のリンクリストを操作する際のポインタ書き込みがライトバリアの対象外となり、GCのオーバーヘッドが削減されます。これは、トレーシングデータがGCによって直接管理される必要がない（トレーシングデータは一時的なものであり、GCのマークフェーズ中に参照される必要がない）という特性を活かした最適化です。

## コアとなるコードの解説

1.  **`traceStackTable`構造体の変更**:
    `tab [1 << 13]*traceStack` が `tab [1 << 13]traceStackPtr` に変更されました。
    これは、`traceStackTable`がハッシュテーブルとして`traceStack`を管理する際に、直接ポインタを保持するのではなく、`uintptr`としてアドレスを保持するように変更されたことを意味します。これにより、`tab`配列への要素の追加や更新時にライトバリアが不要になります。

2.  **`traceStack`構造体の変更**:
    `link *traceStack` が `link traceStackPtr` に変更されました。
    `traceStack`はハッシュ衝突を解決するためにリンクリストを形成しています。この`link`フィールドも同様に、直接ポインタを保持するのではなく、`uintptr`としてアドレスを保持するように変更されました。これにより、リンクリストの要素をたどる際のポインタ書き換え（理論上は発生しないが、構造体の初期化など）や、GCがこのリンクリストをスキャンする際のオーバーヘッドが軽減されます。

3.  **`traceStackPtr`型の定義と`ptr()`メソッド**:
    `type traceStackPtr uintptr`
    `func (tp traceStackPtr) ptr() *traceStack { return (*traceStack)(unsafe.Pointer(tp)) }`
    この新しい型とメソッドが、ライトバリア回避の鍵となります。`traceStackPtr`は`uintptr`のエイリアスであり、GCからは単なる数値として扱われます。しかし、`ptr()`メソッドを使うことで、この数値を`unsafe.Pointer`を介して元の`*traceStack`ポインタに安全に（ただし開発者の責任において）変換できます。これにより、GCの追跡を回避しつつ、必要に応じて実際のメモリ上のオブジェクトにアクセスすることが可能になります。

4.  **`find`メソッド内のループ条件の変更**:
    `for stk := tab.tab[part]; stk != nil; stk = stk.link {`
    が
    `for stk := tab.tab[part].ptr(); stk != nil; stk = stk.link.ptr() {`
    に変更されました。
    `tab.tab[part]`は`traceStackPtr`型を返すため、`.ptr()`を呼び出して`*traceStack`に変換してから`stk`に代入しています。また、リンクリストをたどる際も、`stk.link`が`traceStackPtr`型であるため、`stk.link.ptr()`を呼び出して次の`*traceStack`ポインタを取得しています。

5.  **`dump`メソッド内のループ条件の変更**:
    `for _, stk := range tab.tab { for ; stk != nil; stk = stk.link {`
    が
    `for _, stk := range tab.tab { stk := stk.ptr(); for ; stk != nil; stk = stk.link.ptr() {`
    に変更されました。
    `tab.tab`から取得した`stk`は`traceStackPtr`型であるため、ループに入る前に`stk := stk.ptr()`で`*traceStack`に変換しています。その後のリンクリストの走査も`stk.link.ptr()`を使用しています。

これらの変更により、`traceStack`に関連するポインタ操作がGCのライトバリアの対象外となり、トレーシング機能のパフォーマンスが向上します。これは、GoランタイムがGCのオーバーヘッドを最小限に抑えるために、`unsafe`パッケージを慎重に利用している一例です。

    `traceStackTable`の`find`メソッドと`dump`メソッド内で、`stk.link`による次の要素へのアクセスが`stk.link.ptr()`に変更されました。これは、`link`が`traceStackPtr`型になったため、実際の`*traceStack`ポインタとして利用する際に`ptr()`メソッドを呼び出す必要があるためです。

これらの変更により、`traceStack`に関連するポインタ操作がGCのライトバリアの対象外となり、トレーシング機能のパフォーマンスが向上します。これは、GoランタイムがGCのオーバーヘッドを最小限に抑えるために、`unsafe`パッケージを慎重に利用している一例です。

## コアとなるコードの解説

1.  **`traceStackTable`構造体の変更**:
    `tab [1 << 13]*traceStack` が `tab [1 << 13]traceStackPtr` に変更されました。
    これは、`traceStackTable`がハッシュテーブルとして`traceStack`を管理する際に、直接ポインタを保持するのではなく、`uintptr`としてアドレスを保持するように変更されたことを意味します。これにより、`tab`配列への要素の追加や更新時にライトバリアが不要になります。

2.  **`traceStack`構造体の変更**:
    `link *traceStack` が `link traceStackPtr` に変更されました。
    `traceStack`はハッシュ衝突を解決するためにリンクリストを形成しています。この`link`フィールドも同様に、直接ポインタを保持するのではなく、`uintptr`としてアドレスを保持するように変更されました。これにより、リンクリストの接続もGCの追跡対象外となり、ライトバリアが不要になります。

3.  **`traceStackPtr`型の定義と`ptr()`メソッド**:
    `type traceStackPtr uintptr`
    `func (tp traceStackPtr) ptr() *traceStack { return (*traceStack)(unsafe.Pointer(tp)) }`
    この新しい型とメソッドが、ライトバリア回避の鍵となります。`traceStackPtr`は`uintptr`のエイリアスであり、GCからは単なる数値として扱われます。しかし、`ptr()`メソッドを使うことで、この数値を`unsafe.Pointer`を介して元の`*traceStack`ポインタに安全に（ただし開発者の責任において）変換できます。これにより、GCの追跡を回避しつつ、必要に応じて実際のメモリ上のオブジェクトにアクセスすることが可能になります。

4.  **`find`メソッド内のループ条件の変更**:
    `for stk := tab.tab[part]; stk != nil; stk = stk.link {`
    が
    `for stk := tab.tab[part].ptr(); stk != nil; stk = stk.link.ptr() {`
    に変更されました。
    `tab.tab[part]`は`traceStackPtr`型を返すため、`.ptr()`を呼び出して`*traceStack`に変換してから`stk`に代入しています。また、リンクリストをたどる際も、`stk.link`が`traceStackPtr`型であるため、`stk.link.ptr()`を呼び出して次の`*traceStack`ポインタを取得しています。

5.  **`dump`メソッド内のループ条件の変更**:
    `for _, stk := range tab.tab { for ; stk != nil; stk = stk.link {`
    が
    `for _, stk := range tab.tab { stk := stk.ptr(); for ; stk != nil; stk = stk.link.ptr() {`
    に変更されました。
    `tab.tab`から取得した`stk`は`traceStackPtr`型であるため、ループに入る前に`stk := stk.ptr()`で`*traceStack`に変換しています。その後のリンクリストの走査も`stk.link.ptr()`を使用しています。

これらの変更により、`traceStack`に関連するポインタ操作がGCのライトバリアの対象外となり、トレーシング機能のパフォーマンスが向上します。これは、GoランタイムがGCのオーバーヘッドを最小限に抑えるために、`unsafe`パッケージを慎重に利用している一例です。

# [インデックス 26447] ファイルの概要

このコミットは、Go言語の `net/http` パッケージにおけるチャンクエンコーディングの処理を強化し、HTTPチャンクサイズの最大長をチェックする機能を追加します。具体的には、チャンクサイズを解析する `parseHexUint` 関数において、16進数で表現されたチャンクサイズの文字列が `uint64` の最大値を超える長さ（16桁以上）である場合にエラーを返すように変更されました。これにより、悪意のある、または不正な形式のチャンクサイズが指定された場合に発生しうる潜在的なサービス拒否（DoS）攻撃やリソース枯渇を防ぐことを目的としています。

## 変更の背景

この変更は、HTTP/1.1のチャンク転送エンコーディングにおいて、チャンクサイズを示す16進数文字列の長さに上限を設けることで、潜在的な脆弱性やリソース枯渇の問題を未然に防ぐために導入されました。コミットメッセージにある「Thanks to Régis Leroy for noticing.」という記述から、外部からの指摘によってこの問題が認識されたことが伺えます。

HTTPチャンクエンコーディングでは、各チャンクの前にそのチャンクのデータ長を16進数で示す行が挿入されます。この16進数文字列が非常に長い場合、例えば数千文字にも及ぶような不正な入力があった場合、サーバーはその文字列を解析するために不必要なCPU時間やメモリを消費する可能性があります。`uint64` 型で表現できる最大の16進数（`FFFFFFFFFFFFFFFF`）は16桁であるため、これを超える長さの文字列は、たとえそれが有効な数値として解釈できたとしても、HTTPプロトコルの意図する範囲を超えた異常な入力と見なすことができます。

このコミットは、このような異常な入力に対する堅牢性を高め、サービス拒否攻撃のリスクを低減するための予防的な措置として実施されました。

## 前提知識の解説

### HTTP Chunked Transfer Encoding

HTTP/1.1では、メッセージボディの長さを事前に知ることができない場合に「チャンク転送エンコーディング (Chunked Transfer Encoding)」を使用できます。これは、特に動的に生成されるコンテンツや、大きなファイルをストリーミングする際に有用です。

チャンク転送エンコーディングの仕組みは以下の通りです。

1.  **チャンクサイズ**: 各データチャンクの前に、そのチャンクのデータ長を16進数で示す行が挿入されます。この行の末尾にはCRLF（`\\r\\n`）が付きます。
2.  **チャンクデータ**: チャンクサイズに続く行には、実際のデータが含まれます。この行の末尾にもCRLFが付きます。
3.  **最終チャンク**: 全てのデータが送信された後、`0` とCRLFのみからなる最終チャンクが送信されます。
4.  **トレーラー**: 最終チャンクの後には、オプションでHTTPヘッダー（トレーラーヘッダー）が続くことがあります。
5.  **終端**: 最後に空行（CRLFのみ）が送信され、メッセージボディの終端を示します。

例:
```
4\r\n
Wiki\r\n
6\r\n
pedia \r\n
E\r\n
in\r\n
\r\n
chunks.\r\n
0\r\n
\r\n
```

### 16進数 (Hexadecimal)

16進数は、基数16の数値表現システムです。0から9までの数字と、AからFまでのアルファベット（A=10, B=11, ..., F=15）を使用して数値を表します。コンピュータシステムでは、バイナリデータをより簡潔に表現するためによく使用されます。

HTTPチャンクエンコーディングでは、チャンクサイズが16進数で指定されます。例えば、`A` は10バイト、`10` は16バイトを意味します。

### サービス拒否 (Denial of Service, DoS) 攻撃

DoS攻撃は、標的となるコンピュータシステムやネットワークサービスを過負荷状態に陥らせ、正当なユーザーからのアクセスを妨害することを目的としたサイバー攻撃です。リソース枯渇（CPU、メモリ、ネットワーク帯域幅など）は、DoS攻撃の一般的な手法の一つです。

このコミットの文脈では、非常に長い16進数文字列をチャンクサイズとして送信することで、サーバーがその解析に過剰なリソースを消費させられ、結果として正当なリクエストを処理できなくなる可能性が懸念されました。

## 技術的詳細

このコミットの核心は、`src/net/http/internal/chunked.go` 内の `parseHexUint` 関数に、チャンクサイズの16進数文字列の長さを制限するチェックを追加したことです。

`parseHexUint` 関数は、バイトスライスとして与えられた16進数文字列を `uint64` 型の数値に変換する役割を担っています。`uint64` は64ビットの符号なし整数であり、その最大値は `2^64 - 1` です。この値を16進数で表現すると `FFFFFFFFFFFFFFFF` となり、これは16桁の16進数に相当します。

変更前の `parseHexUint` 関数は、入力されたバイトスライス `v` の長さに制限を設けていませんでした。ループ内で `n <<= 4` というビットシフト操作を繰り返すことで、入力文字列の各16進数文字を順に処理し、最終的な `uint64` 値を構築します。もし入力文字列が16桁を超えていた場合、`uint64` のオーバーフローが発生する可能性がありました。Go言語では整数オーバーフローはパニックを引き起こすことはなく、ラップアラウンド（最大値を超えると0に戻る）しますが、これは予期せぬ動作やセキュリティ上の問題につながる可能性があります。また、単に非常に長い文字列を解析するだけでも、CPU時間を消費し、リソース枯渇の要因となりえます。

追加されたコードは以下の通りです。

```go
	for i, b := range v {
		// ... (既存のswitch文) ...
		if i == 16 {
			return 0, errors.New("http chunk length too large")
		}
		n <<= 4
		n |= uint64(b)
	}
```

ここで `i` はループのインデックスであり、`v` のバイトスライス内の現在の文字の位置を示します。`i == 16` という条件は、17番目の16進数文字（インデックスが0から始まるため）を処理しようとしていることを意味します。つまり、チャンクサイズの文字列が16桁を超えた場合に、`"http chunk length too large"` というエラーを返して処理を中断します。これにより、`uint64` の表現可能な範囲を超える長さのチャンクサイズが指定された場合に、早期にエラーを検出し、不正な入力を拒否することができます。

この変更は、HTTPチャンクエンコーディングの堅牢性を高め、悪意のある入力に対する耐性を向上させる重要なセキュリティ強化です。

## コアとなるコードの解説

### `src/net/http/internal/chunked.go` の変更

`parseHexUint` 関数は、チャンクサイズを表す16進数文字列を `uint64` に変換するロジックを含んでいます。

1.  **ループ変数の変更**:
    変更前: `for _, b := range v`
    変更後: `for i, b := range v`
    これにより、ループ内で現在の文字のインデックス `i` を利用できるようになりました。

2.  **長さチェックの追加**:
    `if i == 16 { return 0, errors.New("http chunk length too large") }`
    この行が追加された最も重要な変更点です。`i` が `16` になったということは、既に16文字（インデックス0から15まで）の16進数文字を処理し終え、17文字目を処理しようとしていることを意味します。`uint64` は16桁の16進数で表現できるため、17桁目以降の文字は不正な入力と見なされ、`"http chunk length too large"` というエラーを返して処理を中断します。このチェックは、`n <<= 4` の前に配置されているため、オーバーフローが発生する前に不正な入力を検出できます。

3.  **ビットシフト操作の移動**:
    変更前は `n <<= 4` がループの最初にありましたが、変更後は `if i == 16` チェックの後に移動しました。これにより、17文字目の処理に入る前に長さチェックが実行されることが保証されます。

これらの変更により、`parseHexUint` は、HTTPチャンクサイズとして許容される最大長（`uint64` で表現可能な16進数16桁）を超える入力に対して、明確なエラーを返すようになりました。

### `src/net/http/internal/chunked_test.go` の変更

テストファイルでは、`TestParseHexUint` 関数が大幅に改修され、新しいエラーケースを網羅するようになりました。

1.  **`testCase` 構造体の導入**:
    `in` (入力文字列), `want` (期待される `uint64` 値), `wantErr` (期待されるエラー文字列) を持つ `testCase` 構造体が定義され、テストケースの管理が容易になりました。

2.  **新しいテストケースの追加**:
    *   `{"x", 0, "invalid byte in chunk length"}`: 不正な16進数文字を含むケース。
    *   `{"00000000000000000", 0, "http chunk length too large"}`: 17桁の16進数文字列で、新しい長さチェックがトリガーされるケース。
    *   `{"10000000000000000", 0, "http chunk length too large"}`: 同様に17桁のケース。
    *   `{"00000000000000001", 0, "http chunk length too large"}`: 同様に17桁のケース。
    これらのテストケースは、`parseHexUint` に追加された長さチェックが正しく機能することを確認します。

3.  **テストループの改善**:
    従来のテストは `for i := uint64(0); i <= 1234; i++` のように単純なループで正常系をテストしていましたが、新しいテストでは `testCase` スライスに正常系と異常系の両方のケースを追加し、統一されたループで全てのテストを実行するように変更されました。これにより、テストの網羅性と保守性が向上しています。

これらのテストの追加により、`parseHexUint` 関数が期待通りに動作し、特に不正な長さのチャンクサイズに対して適切にエラーを返すことが保証されます。

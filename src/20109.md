## 元コミット内容

`runtime: mark with non-atomic operations when GOMAXPROCS=1`

このコミットは、`GOMAXPROCS=1`の場合に、GCのマーキング処理を非アトミック操作で行うように変更します。これは、アトミック操作を使用した場合に`GOMAXPROCS=1`の環境でGCポーズ時間が3-5%増加するというパフォーマンスビルダの報告に対応するものです。

## 変更の背景

Goのガベージコレクションは、並行性を考慮して設計されています。複数のプロセッサ（P）が同時にGCのマーキング作業を行う場合、共有されるメモリ上のマークビットを安全に更新するためにアトミック操作（Compare-And-Swap: CASなど）が使用されます。アトミック操作は、複数のゴルーチンやOSスレッドが同時に同じメモリ位置にアクセスしても、データの整合性を保つための重要なメカニズムです。

しかし、`GOMAXPROCS=1`という設定は、Goランタイムが利用できるOSスレッド（M）と論理プロセッサ（P）の数を1に制限することを意味します。この場合、GCのマーキングフェーズにおいても、実質的に単一のPが作業を行うことになります。このような単一スレッド環境では、複数のPによる競合状態が発生しないため、アトミック操作によるオーバーヘッドが不要になります。

コミットメッセージに記載されているように、Goのパフォーマンスビルダ（`goperfd.appspot.com`）のデータが、`GOMAXPROCS=1`の環境でアトミック操作を用いたマーキングがGCポーズ時間を3-5%増加させていることを示していました。これは、不要な同期オーバーヘッドがパフォーマンスに悪影響を与えていることを示唆しています。この問題を解決し、`GOMAXPROCS=1`環境でのGC性能を向上させることが、この変更の背景にあります。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goのガベージコレクションは、主に「マーク＆スイープ」アルゴリズムをベースにしています。これは、到達可能なオブジェクトをマークし、マークされていない（到達不可能な）オブジェクトを解放するプロセスです。GoのGCは、アプリケーションの実行と並行して動作する「並行GC」であり、アプリケーションの実行を完全に停止させる「ポーズ」時間を最小限に抑えるように設計されています。

GCの主要なフェーズは以下の通りです。
1.  **マークフェーズ (Mark Phase)**: ルート（グローバル変数、スタック上のポインタなど）から到達可能なすべてのオブジェクトを特定し、マークします。このフェーズは、Go 1.5以降、ほとんどが並行して実行されますが、一部の重要な処理ではSTW (Stop-The-World) ポーズが発生します。
2.  **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（ガベージ）をメモリから解放し、再利用可能な状態にします。

### GCのマークビットとアトミック操作

Goランタイムは、ヒープ上の各オブジェクトが「マークされているか」を示すためのビット（マークビット）を管理しています。GCのマークフェーズでは、このマークビットを「マーク済み」に設定します。

複数のPが同時にマーク作業を行う場合、同じオブジェクトのマークビットに同時にアクセスし、更新しようとする可能性があります。このような競合状態を防ぎ、データの整合性を保証するために、アトミック操作が使用されます。アトミック操作は、その操作が不可分であることを保証し、他の操作と同時に実行されても、その操作全体が完了するか、全く実行されないかのどちらかであることを保証します。代表的なアトミック操作には、Compare-And-Swap (CAS) があります。

### GOMAXPROCS

`GOMAXPROCS`は、Goランタイムが同時に実行できるOSスレッドの最大数を制御する環境変数です。これは、Goのスケジューラが利用できる論理プロセッサ（P）の数を決定します。

*   `GOMAXPROCS`が設定されていない場合、Goはデフォルトで利用可能なCPUコア数に設定されます。
*   `GOMAXPROCS=1`に設定すると、Goランタイムは同時に1つのOSスレッドしか実行しないように制限されます。これは、シングルスレッドアプリケーションのように動作することを意味し、並行処理のオーバーヘッドを排除したい場合や、デバッグ目的で使用されることがあります。

### パフォーマンスビルダ (Perf Builders)

Goプロジェクトでは、継続的なパフォーマンス監視のために「パフォーマンスビルダ」と呼ばれるシステムが運用されています。これは、Goのソースコードへのコミットごとに、様々なベンチマークを実行し、そのパフォーマンスの変化を追跡するものです。`goperfd.appspot.com`はその結果を可視化するウェブサイトであり、特定のコミットがパフォーマンスに与える影響（例えば、GCポーズ時間の増減）を詳細に分析することができます。

## 技術的詳細

このコミットの核心は、`src/pkg/runtime/mgc0.c`ファイル内の`scanblock`関数における変更です。`scanblock`関数は、GCのマークフェーズ中にメモリブロックをスキャンし、到達可能なオブジェクトをマークする役割を担っています。

元のコードでは、マークビットを設定する際に、特定の条件を満たさない場合にアトミック操作（CASループ）にフォールバックしていました。この条件は、`bits8`と`bitMask`、`gcBits`、`bitBoundary`を用いた複雑なビット演算によって表現されており、特定のビットパターンが既に設定されているかどうかを確認していました。これは、複数のPが同時にマーク作業を行う際に、既にマークされている可能性のあるオブジェクトに対して不要なCAS操作を避けるための最適化と考えられます。

変更後のコードでは、この条件に加えて、`work.nproc == 1`という条件が追加されています。`work.nproc`は、Goランタイムが現在利用している論理プロセッサ（P）の数を表します。

変更前:
```c
if((bits8&(bitMask|(bitMask<<gcBits))) != (bitBoundary|(bitBoundary<<gcBits)))
    ((uint8*)bitp)[shift/8] = bits8 | (bitMarked<<(shift&7));
else {
    for(;;) {
        // CAS loop for marking
    }
}
```

変更後:
```c
if((bits8&(bitMask|(bitMask<<gcBits))) != (bitBoundary|(bitBoundary<<gcBits)) ||
    work.nproc == 1) // <-- 追加された条件
    ((uint8*)bitp)[shift/8] = bits8 | (bitMarked<<(shift&7));
else {
    for(;;) {
        // CAS loop for marking
    }
}
```

この変更により、以下のロジックが適用されます。

*   **`work.nproc == 1`の場合**: `GOMAXPROCS=1`が設定されている場合、`work.nproc`は1になります。この場合、`if`文の条件が`true`になるため、常に非アトミックな代入操作 `((uint8*)bitp)[shift/8] = bits8 | (bitMarked<<(shift&7));` が実行されます。これにより、CASループ（アトミック操作）へのフォールバックが完全に回避されます。
*   **`work.nproc > 1`の場合**: 従来のロジックが維持されます。つまり、`bits8`のビットパターンが特定の条件を満たさない場合にのみ非アトミック操作が実行され、それ以外の場合はCASループ（アトミック操作）にフォールバックします。

この最適化は、`GOMAXPROCS=1`の環境では並行性が存在しないため、アトミック操作による同期オーバーヘッドが完全に不要になるという事実に基づいています。アトミック操作は、通常のメモリ操作よりもCPUサイクルを多く消費する傾向があるため、これを回避することでGCのポーズ時間を短縮し、全体的なアプリケーションのパフォーマンスを向上させることができます。

## コアとなるコードの解説

変更された行は、GCのマークビットを設定する際の条件分岐を修正しています。

元のコードの条件式:
`if((bits8&(bitMask|(bitMask<<gcBits))) != (bitBoundary|(bitBoundary<<gcBits)))`

この条件は、`bits8`（現在のマークビットの状態）が、`bitMask`、`gcBits`、`bitBoundary`といった定数とビット演算を組み合わせた特定のパターンと一致しない場合に`true`となります。これは、対象のメモリ領域がまだマークされていない、あるいは特定のマーク状態にないことを確認するためのものです。この条件が`true`の場合、非アトミックな代入操作でマークビットを設定します。`false`の場合、つまり特定のパターンに一致する場合は、CAS（Compare-And-Swap）ループを使用してアトミックにマークビットを設定しようとします。これは、複数のPが同時に同じビットをマークしようとする競合状態を安全に解決するためです。

追加された条件:
`|| work.nproc == 1`

この`||`（論理OR）演算子によって、元の条件に加えて`work.nproc == 1`という条件が追加されました。
`work.nproc`は、Goランタイムが現在利用している論理プロセッサ（P）の数を表すグローバル変数です。

この変更の意図は以下の通りです。

*   **`GOMAXPROCS=1`の場合**: `work.nproc`が1であるため、`if`文の条件全体が常に`true`になります（`A || true`は常に`true`）。これにより、`scanblock`関数は常に非アトミックな代入操作 `((uint8*)bitp)[shift/8] = bits8 | (bitMarked<<(shift&7));` を実行し、CASループ（アトミック操作）を完全にスキップします。単一のPしか存在しないため、競合状態が発生せず、アトミック操作のオーバーヘッドが不要になるため、これは安全かつ効率的な最適化です。
*   **`GOMAXPROCS > 1`の場合**: `work.nproc`は1ではないため、`|| work.nproc == 1`の部分は`false`になります。この場合、`if`文の条件は元の条件 `(bits8&(bitMask|(bitMask<<gcBits))) != (bitBoundary|(bitBoundary<<gcBits))` の結果に依存します。つまり、複数のPが存在する環境では、引き続き競合状態を考慮した従来のロジック（必要に応じてアトミック操作を使用）が適用されます。

この変更により、`GOMAXPROCS=1`の環境下でのGCマーキング処理における不要なアトミック操作のオーバーヘッドが排除され、GCポーズ時間の短縮に貢献します。

# [インデックス 27884] ファイルの概要

このコミットは、Go言語のリンカー（`cmd/link`）における特定のアーキテクチャ（`arm64`）での動的リンク時の問題を解決するためのものです。具体的には、GNUリンカーが`-znocopyreloc`フラグが指定された際に`COPY`リロケーションの生成を拒否し、エラーとなる問題を回避するため、`gold`リンカーを使用するように変更しています。

## 元コミット内容

`cmd/link: use gold when dynamic linking on arm64`

GNUリンカーは、`arm64`上で動的リンクを行う際に`-znocopyreloc`フラグが指定されていると、`COPY`リロケーションの生成を拒否し、エラーを発生させます。`gold`リンカーはこの状況で正しく機能するため、`arm64`での動的リンク時に`gold`リンカーを使用するように切り替えます。これにより、`linux/arm64`ビルドの問題が修正されます。

## 変更の背景

Go言語は通常、静的リンクをデフォルトとしていますが、`cgo`を使用する場合や`buildmode=c-shared`で共有ライブラリをビルドする場合には動的リンクが必要となります。動的リンクでは、実行時に共有ライブラリのシンボルを解決するためのメカニズムが重要になります。

このコミットの背景には、`arm64`アーキテクチャにおけるGNUリンカー（`ld`）の特定の挙動があります。動的リンクにおいて、共有ライブラリ内のグローバルデータシンボルを実行可能ファイルが参照し、かつそのデータを変更する可能性がある場合、リンカーは通常「`COPY`リロケーション」と呼ばれるメカニズムを使用します。これは、共有ライブラリのデータを実行可能ファイルの`.bss`セクションにコピーし、実行可能ファイルが自身のプライベートな書き込み可能なコピーを持つようにするものです。

しかし、`-znocopyreloc`というリンカーフラグは、この`COPY`リロケーションの生成を明示的に禁止します。このフラグは、主にPosition-Independent Executable (PIE) のような、より厳密なメモリレイアウトと動的リンク動作を求めるシナリオで利用されます。

問題は、`arm64`アーキテクチャにおいて、GNUリンカーが`-znocopyreloc`フラグの指示に厳密に従い、`COPY`リロケーションが必要な状況でそれを生成する代わりに、エラーを発生させてビルドを失敗させていた点にあります。これは、リンカーが代替手段を見つけられなかったためです。一方、`gold`リンカーはこの状況でも適切に処理を行い、ビルドを成功させることができました。

このため、`linux/arm64`環境でのGoプログラムのビルド、特に動的リンクを伴う場合に問題が発生していました。このコミットは、このビルドエラーを解決し、`arm64`上でのGoの動的リンクの信頼性を向上させることを目的としています。

## 前提知識の解説

### 1. リンカー (Linker)

リンカーは、コンパイラによって生成されたオブジェクトファイル（機械語コードとデータを含む）と、必要なライブラリを結合して、実行可能ファイルや共有ライブラリを生成するプログラムです。このプロセスには、シンボル解決（異なるオブジェクトファイル間で参照される関数や変数のアドレスを決定する）と、リロケーション（コードやデータ内のアドレス参照を実際のメモリ位置に調整する）が含まれます。

### 2. GNUリンカー (GNU ld) と Goldリンカー

*   **GNU ld (GNU Binutils ld)**: 伝統的なUnix系システムのリンカーであり、非常に広範なオブジェクトファイルフォーマットとアーキテクチャをサポートしています。BFD (Binary File Descriptor) ライブラリを使用しており、柔軟なリンカースクリプトによる詳細な制御が可能です。
*   **Goldリンカー (GNU gold)**: Googleによって開発された比較的新しいリンカーで、特に大規模なC++プロジェクトでのリンク速度向上とメモリ使用量の削減を目的としています。BFDライブラリを使用せず、ELFフォーマットに特化してゼロからC++で記述されています。一般的に`GNU ld`よりも高速ですが、サポートするフォーマットはELFに限定されます。

### 3. 動的リンク (Dynamic Linking) と 静的リンク (Static Linking)

*   **静的リンク**: 必要なライブラリのコードがすべて実行可能ファイルに直接組み込まれます。これにより、実行可能ファイルは自己完結型となり、他のライブラリに依存しません。Go言語のデフォルトのビルドモードです。
*   **動的リンク**: 実行可能ファイルは、必要なライブラリのコードを直接含まず、実行時にオペレーティングシステムが共有ライブラリ（`.so`ファイルなど）をロードしてリンクします。これにより、ディスクスペースの節約や、ライブラリの更新が容易になるという利点があります。`cgo`を使用するGoプログラムや、`buildmode=c-shared`でビルドされたGoの共有ライブラリで利用されます。

### 4. リロケーション (Relocation)

リロケーションとは、プログラム内のアドレス参照を、プログラムがメモリにロードされる実際の場所に合わせて調整するプロセスです。動的リンクでは、共有ライブラリがロードされるアドレスが実行時まで分からないため、特に重要になります。

### 5. `COPY`リロケーション

`COPY`リロケーションは、動的リンクにおいて、共有ライブラリ内のグローバルデータシンボルを実行可能ファイルが参照し、かつそのデータを変更する可能性がある場合に用いられるメカニズムです。
1.  リンカーは、実行可能ファイルの`.bss`セクションに、共有ライブラリのグローバルデータシンボルと同じサイズの領域を割り当てます。
2.  実行可能ファイル内のそのシンボルへの参照は、この`.bss`セクション内の新しい領域を指すように変更されます。
3.  プログラムのロード時（実行時）、動的リンカーは共有ライブラリから元のグローバルデータの値を、実行可能ファイルの`.bss`セクションにコピーします。
これにより、実行可能ファイルは共有ライブラリのデータとは独立した、自身の書き込み可能なコピーを持つことができます。

### 6. `-znocopyreloc`リンカーフラグ

このフラグは、リンカーに対して`COPY`リロケーションを生成しないように指示します。このフラグが使用される主な理由は以下の通りです。
*   **Position-Independent Code (PIC) / Position-Independent Executable (PIE)**: 現代のシステムでは、セキュリティ上の理由からPIEが推奨されます。PIEでは、コードがロードされるアドレスに依存しないように設計されており、`COPY`リロケーションはPIEの原則と相容れない場合があります。`COPY`リロケーションは、実行可能ファイル内の固定アドレスにデータを配置するため、PIEのランダム化されたアドレス空間レイアウト（ASLR）と衝突する可能性があります。
*   **メモリ効率**: `COPY`リロケーションは、共有ライブラリのデータが二重にメモリに存在することになるため、メモリ使用効率が低下する可能性があります。

### 7. `arm64`アーキテクチャ

`arm64`は、ARMv8-Aアーキテクチャに基づく64ビットの命令セットアーキテクチャです。スマートフォン、タブレット、サーバー、組み込みシステムなど、幅広いデバイスで利用されています。Go言語も`arm64`を主要なターゲットアーキテクチャの一つとしてサポートしています。

## 技術的詳細

このコミットの核心は、Goのリンカー（`cmd/link`）が外部リンカーを呼び出す際の挙動の変更にあります。Goは、`cgo`を使用する場合など、Cライブラリとの連携が必要な場合に、システムにインストールされている外部リンカー（通常はGNU `ld`）を利用します。

変更前のコードでは、`SysArch.Family == sys.ARM`という条件で、ARMアーキテクチャの場合にのみ`-fuse-ld=gold`フラグを追加し、`gold`リンカーを使用するようにしていました。これは、ARMアーキテクチャのGNUリンカーが`-znocopyreloc`フラグが設定されていても`COPY`リロケーションを生成してしまうという既知の問題（[https://sourceware.org/bugzilla/show_bug.cgi?id=19962](https://sourceware.org/bugzilla/show_bug.cgi?id=19962)）があったためです。

このコミットでは、この条件を`SysArch.InFamily(sys.ARM, sys.ARM64)`に拡張しています。これは、`arm64`アーキテクチャもこの問題の影響を受けることを意味します。ただし、`arm64`の場合のGNUリンカーの挙動はARMとは異なり、`COPY`リロケーションを生成する代わりに、それを拒否してエラーを発生させていました。どちらの挙動もビルドの失敗につながるため、`arm64`においても`gold`リンカーを使用するように統一することで問題を解決しています。

`gold`リンカーは、`COPY`リロケーションを必要としない代替のシンボル解決メカニズム（例えば、Global Offset Table (GOT) を介した間接参照）を適切に処理できるため、この問題の解決策として採用されました。

`misc/cgo/testshared/shared_test.go`の変更は、リンカーの挙動変更とは直接関係ありませんが、テストコードの堅牢性を向上させるためのものです。`log.Fatal`はテストを即座に終了させてしまうため、`t.Fatalf`に変更することで、`testing`パッケージのフレームワーク内でテスト失敗を適切に報告し、他のテストの実行を妨げないようにしています。また、`dynStrings`関数に`*testing.T`を渡すことで、テストヘルパー関数がテストコンテキストにアクセスできるようになり、より詳細なエラーメッセージやテスト固有の機能を利用できるようになります。

## コアとなるコードの解説

### `src/cmd/link/internal/ld/lib.go` の変更

このファイルはGoのリンカーの内部ロジックを扱っています。`hostlink()`関数は、Goのビルドプロセスが外部のシステムリンカーを呼び出す部分です。

*   **変更前**:
    ```go
    if SysArch.Family == sys.ARM {
        // The GNU linker will generate COPY relocations on ARM
        // even with -znocopyreloc set. Switch to gold.
        argv = append(argv, "-fuse-ld=gold")
    }
    ```
    ここでは、システムアーキテクチャが`ARM`ファミリーである場合にのみ、`gold`リンカーを使用するように指定していました。コメントには、GNUリンカーが`-znocopyreloc`が設定されていても`COPY`リロケーションを生成してしまう問題が記載されています。

*   **変更後**:
    ```go
    if SysArch.InFamily(sys.ARM, sys.ARM64) {
        // On ARM, the GNU linker will generate COPY relocations
        // even with -znocopyreloc set.
        // https://sourceware.org/bugzilla/show_bug.cgi?id=19962
        //
        // On ARM64, the GNU linker will fail instead of
        // generating COPY relocations.
        //
        // In both cases, switch to gold.
        argv = append(argv, "-fuse-ld=gold")
    }
    ```
    条件が`SysArch.InFamily(sys.ARM, sys.ARM64)`に変更されました。これは、`sys.ARM`と`sys.ARM64`の両方のアーキテクチャファミリーに対して、`gold`リンカーを使用することを意味します。
    コメントも更新され、`arm64`におけるGNUリンカーの挙動が明記されています。「`On ARM64, the GNU linker will fail instead of generating COPY relocations.`」（`arm64`では、GNUリンカーは`COPY`リロケーションを生成する代わりに失敗する）とあり、`arm64`でも`gold`リンカーへの切り替えが必要であることが強調されています。
    `argv = append(argv, "-fuse-ld=gold")`は、リンカーに`gold`を使用するよう指示するフラグです。

### `misc/cgo/testshared/shared_test.go` の変更

このファイルは`cgo`で共有ライブラリをテストするための補助関数を含んでいます。

*   `dynStrings`関数のシグネチャが`func dynStrings(path string, flag elf.DynTag) []string`から`func dynStrings(t *testing.T, path string, flag elf.DynTag) []string`に変更されました。これにより、`*testing.T`型の引数が追加され、この関数がテストヘルパーとして機能するようになりました。
*   エラーハンドリングが`log.Fatal`から`t.Fatalf`に変更されました。
    *   `log.Fatal`はプログラム全体を終了させてしまうため、テスト中にエラーが発生した場合、残りのテストが実行されなくなります。
    *   `t.Fatalf`は、現在のテスト関数を失敗としてマークし、そのテスト関数の実行を停止しますが、他のテスト関数は引き続き実行されます。これにより、テストスイート全体の実行がより堅牢になります。
*   `AssertIsLinkedToRegexp`と`AssertHasRPath`関数も、`dynStrings`関数の変更に合わせて、`*testing.T`引数を渡すように修正されています。

これらのテスト関連の変更は、リンカーの挙動変更とは直接的な機能変更ではありませんが、リンカーの変更がテスト環境に与える影響を考慮し、テストの信頼性と診断能力を高めるための改善と見なせます。

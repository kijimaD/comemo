# [インデックス 24379] ファイルの概要

このコミットは、Go言語のコマンドラインツール `go get` における、カスタムインポートパス（通称「Vanity URL」）のワイルドカード処理に関するバグを修正するものです。具体的には、`go get rsc.io/pdf/...` のような形式でワイルドカードを含むカスタムインポートパスを使用した場合に発生する問題を解決します。

## 元コミット内容

このコミットは、`src/cmd/go/get.go` ファイル内の `download` 関数に対する変更です。主な変更点は、インポートスタック (`stk`) の操作方法、特に `push` と `pop` の呼び出し位置の調整です。

具体的には、以下の変更が行われました。

1.  `load` 関数内で `loadPackage` および `loadImport` を呼び出す際に、引数として `arg` ではなく `path` を使用するように修正されました。
2.  `download` 関数の冒頭にあった `stk.push(arg)` と `defer stk.pop()` のペアが削除され、代わりに「ここでは `stk.push(arg)` と `defer stk.pop()` を行わないこと。以下の `push/pop` は、場合によっては更新された `arg` の値を使用する」というコメントが追加されました。
3.  `downloadPackage` の呼び出し前後に `stk.push(arg)` と `stk.pop()` が追加されました。
4.  ワイルドカードが展開された後の各パッケージの `load` 呼び出し前後に `stk.push(arg)` と `stk.pop()` が追加されました。

## 変更の背景

このコミットは、GoのIssue #11806 に対応するものです。このIssueでは、カスタムインポートパス（Vanity URL）でワイルドカード (`...`) を使用した場合に `go get` が正しく動作しないという問題が報告されていました。

カスタムインポートパスは、`go get` がパッケージをダウンロードする際に、実際のバージョン管理システム（Git, Mercurialなど）のリポジトリURLを隠蔽し、よりユーザーフレンドリーなパス（例: `rsc.io/pdf`）を提供するための仕組みです。通常、`go get` は指定されたインポートパスに対応するHTMLページをフェッチし、そのページ内の `<meta name="go-import" ...>` タグから実際のソースリポジトリの情報を取得します。

ワイルドカード (`...`) は、指定されたパス以下のすべてのサブパッケージを対象とすることを示します。例えば、`go get rsc.io/pdf/...` は `rsc.io/pdf` およびその下のすべてのサブパッケージをダウンロードしようとします。

このバグは、`download` 関数内でインポートスタック (`stk`) の管理が不適切だったために発生しました。特に、ワイルドカードが展開され、`arg` の値が変化する可能性があるにもかかわらず、関数の冒頭で `defer stk.pop()` を使用していたことが問題でした。これにより、スタックが不整合な状態になり、`go get` が正しいパッケージをダウンロードできなかったり、エラーが発生したりしていました。

コミットメッセージには「`TestGoGetWorksWithVanityWildcards` を修正するが、このテストはネットワークを使用するため、ビルダでは実行されない」とあり、この種のバグがCI/CDパイプラインで捕捉されにくい性質を持っていたことが示唆されています。

## 前提知識の解説

### `go get` コマンド

`go get` はGo言語のパッケージ管理ツールであり、指定されたインポートパスに対応するGoパッケージのソースコードをダウンロードし、インストールするために使用されます。通常、`go get` は以下の手順で動作します。

1.  **インポートパスの解析**: `go get` に渡されたインポートパス（例: `github.com/user/repo`）を解析します。
2.  **リポジトリの特定**: 標準的なリポジトリ（GitHub, Bitbucketなど）であれば、そのパスから直接リポジトリURLを特定します。カスタムインポートパスの場合は、HTTP(S)リクエストを送信して `<meta name="go-import" ...>` タグを解析し、実際のソースリポジトリのURLとバージョン管理システム（VCS）の種類（git, hgなど）を取得します。
3.  **リポジトリのクローン/フェッチ**: 特定されたリポジトリを `$GOPATH/src` または `$GOMODCACHE` にクローンまたはフェッチします。
4.  **パッケージのビルドとインストール**: ダウンロードしたソースコードをビルドし、実行可能ファイルやライブラリをインストールします。

### カスタムインポートパス (Vanity URL)

Goのカスタムインポートパスは、開発者が自身のドメイン名を使ってGoパッケージのインポートパスを定義できる機能です。これにより、実際のコードがホストされている場所（例: `github.com/user/repo`）を隠蔽し、より短く覚えやすい、またはブランドに合わせたインポートパス（例: `example.com/mypackage`）を提供できます。

これは、ウェブサーバーが特定のパス（例: `example.com/mypackage?go-get=1`）へのリクエストに対して、以下のような `<meta>` タグを含むHTMLを返すことで実現されます。

```html
<meta name="go-import" content="example.com/mypackage git https://github.com/user/repo">
```

`go get` はこのタグを読み取り、`https://github.com/user/repo` からGitリポジトリをクローンします。

### ワイルドカード (`...`)

Goのツールチェーンでは、インポートパスの末尾に `...` を付けることで、そのパス以下のすべてのサブパッケージを対象とすることができます。例えば、`go get example.com/mypackage/...` は `example.com/mypackage` とそのすべてのサブディレクトリにあるパッケージをダウンロード・インストールしようとします。

### インポートスタック (`importStack`)

`go get` のようなツールがパッケージの依存関係を解決し、ダウンロードする際には、現在処理中のパッケージのインポートパスの履歴を追跡する必要があります。これは、循環依存の検出や、エラーメッセージの生成（どのパッケージがどのパッケージをインポートしているかを示すため）に役立ちます。この履歴を管理するために使用されるのが「インポートスタック」です。

スタックはLIFO（Last-In, First-Out）のデータ構造であり、`push` 操作で要素を追加し、`pop` 操作で最新の要素を削除します。

## 技術的詳細

このコミットの核心は、`src/cmd/go/get.go` 内の `download` 関数におけるインポートスタック (`stk`) の管理方法の改善です。

元のコードでは、`download` 関数の冒頭で `stk.push(arg)` を行い、`defer stk.pop()` を使って関数の終了時にスタックから要素を削除していました。`defer` は関数がリターンする直前に実行されるため、一見すると適切に見えます。

しかし、`download` 関数はワイルドカードを含む `arg` を受け取ることがあります。ワイルドカードが展開されると、元の `arg` は複数の具体的なパッケージパスに分解され、それぞれのパスに対してダウンロード処理が続行されます。このとき、`arg` の値は関数内で変化する可能性があります。

問題は以下のシナリオで発生しました。

1.  `download("rsc.io/pdf/...", ...)` が呼び出される。
2.  関数の冒頭で `stk.push("rsc.io/pdf/...")` が実行され、`defer stk.pop()` がスケジュールされる。
3.  関数内でワイルドカードが展開され、例えば `arg` が `rsc.io/pdf/v1` と `rsc.io/pdf/v2` に更新される。
4.  これらの新しい `arg` の値に対して、さらにダウンロード処理が続行される。この際、`stk` にはまだ古いワイルドカードパスが残っている。
5.  `downloadPackage` や `load` のような操作が実行される際に、`stk` の内容が期待されるものと異なっているため、エラーメッセージが不正確になったり、内部的な状態が壊れたりする可能性がありました。特に、ワイルドカード展開後に個々のパッケージを処理する際に、スタックにワイルドカードパスが残ったままだと、その後の `push`/`pop` 操作が不整合を引き起こす原因となります。

この修正では、`defer stk.pop()` を削除し、`stk.push(arg)` と `stk.pop()` のペアを、`arg` の値が具体的なパッケージパスとして使用される直前と直後に移動させました。これにより、スタックは常に現在処理中の正確なパッケージパスを反映するようになります。

*   `downloadPackage(p)` の呼び出し前後に `stk.push(arg)` と `stk.pop()` を配置することで、パッケージのダウンロード処理中にのみそのパッケージパスがスタックに存在するようにします。
*   ワイルドカード展開後、`args` スライス内の各具体的なパッケージパスに対してループ処理を行う際も、それぞれの `arg` に対して `stk.push(arg)` と `stk.pop()` を行うことで、個々のパッケージの処理がスタック上で正しく表現されるようにします。

この変更により、インポートスタックの整合性が保たれ、ワイルドカードを含むカスタムインポートパスが `go get` で正しく処理されるようになりました。

## コアとなるコードの解説

変更の中心は、`download` 関数内での `stk` (importStack) の `push` および `pop` 操作のタイミングです。

1.  **`load` 関数の引数修正**:
    ```diff
    -			return loadPackage(arg, stk)
    +			return loadPackage(path, stk)
    // ...
    -		return loadImport(arg, parent.Dir, nil, stk, nil)
    +		return loadImport(path, parent.Dir, nil, stk, nil)
    ```
    これは、`load` 関数が受け取る引数 `path` を、内部の `loadPackage` や `loadImport` にそのまま渡すように修正したものです。元のコードでは、`download` 関数の外側のスコープの `arg` を参照していましたが、`load` 関数内で `path` という引数を受け取っているため、その `path` を使用するのがより自然で正確です。これは、今回のワイルドカードの問題とは直接関係ない、コードの整合性を高めるための修正と考えられます。

2.  **`defer stk.pop()` の削除とコメント追加**:
    ```diff
    -	stk.push(arg)
    -	defer stk.pop()
    +	// Note: Do not stk.push(arg) and defer stk.pop() here.
    +	// The push/pop below are using updated values of arg in some cases.
    ```
    これが最も重要な変更点です。以前は、`download` 関数が呼び出された直後に `arg` をスタックに `push` し、`defer` を使って関数終了時に `pop` していました。しかし、前述の通り、`arg` はワイルドカード展開によって関数内で変化する可能性があります。`defer` は `arg` の初期値でクロージャをキャプチャするため、`arg` が更新されても `pop` されるのは初期値に対応する要素ではありません。また、`arg` が変化した後に `push` される新しい要素と、`defer` で `pop` される要素の間に不整合が生じます。このコメントは、この問題の認識と、よりきめ細やかなスタック操作が必要であることを明確に示しています。

3.  **`downloadPackage` 呼び出し前後の `stk` 操作**:
    ```diff
    +		stk.push(arg)
     		err := downloadPackage(p)
     		if err != nil {
     			errorf("%s", &PackageError{ImportStack: stk.copy(), Err: err.Error()})
    +			stk.pop()
     			return
     		}
    // ...
    +		stk.pop()
    ```
    `downloadPackage` は実際にパッケージをダウンロードする処理です。この処理が実行される間だけ、現在の `arg`（ダウンロード対象のパッケージパス）がスタックに積まれるように変更されました。これにより、エラー発生時や正常終了時に、スタックが常に正しい状態に保たれます。特に、エラー発生時に `stk.pop()` が追加されたことで、スタックが不整合な状態で関数を抜けることを防いでいます。

4.  **ワイルドカード展開後の各パッケージ処理における `stk` 操作**:
    ```diff
    +		for _, arg := range args {
    +			stk.push(arg)
     			p := load(arg)
    +			stk.pop()
     			if p.Error != nil {
     				errorf("%s", p.Error)
     				continue
    ```
    ワイルドカード (`...`) が含まれていた場合、`args` スライスには展開された複数の具体的なパッケージパスが含まれます。このループでは、それぞれの具体的な `arg` に対して `load` 関数が呼び出されます。この修正により、各具体的なパッケージパスが `load` される直前にスタックに `push` され、処理が完了した直後に `pop` されるようになりました。これにより、スタックは常に現在処理中の単一のパッケージパスを正確に反映し、ワイルドカード展開による複数のパッケージ処理が正しく追跡されるようになります。

これらの変更により、`download` 関数は `arg` の値が変化する可能性のある状況でも、インポートスタックの整合性を正確に維持できるようになり、カスタムインポートパスのワイルドカード処理が正しく機能するようになりました。

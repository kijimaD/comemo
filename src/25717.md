# [インデックス 25717] ファイルの概要

このコミットは、GoランタイムがAndroid/386アーキテクチャ上でシステムコールを呼び出す方法を変更するものです。具体的には、`glibc`の動的リンカに特有の`VDSO`（Virtual Dynamic Shared Object）ヘルパーへの`CALL *runtime_vdso(SB)`による呼び出しから、`bionic`（AndroidのCライブラリ）が使用する`int $0x80`ソフトウェア割り込みによるシステムコール呼び出しに切り替えることで、Android環境での互換性とテキスト再配置の問題を解決しています。

## 変更の背景

この変更は、GoのAndroid/386環境におけるシステムコール呼び出しの不具合を修正するために導入されました。以前のコミット `golang.org/cl/16796` は、システムコールを呼び出す際に`glibc`（GNU C Library）の動的リンカに特有の振る舞いを前提としていました。具体的には、`__kernel_vsyscall`という`VDSO`ヘルパーが`0x10(GS)`という特定のメモリ位置に配置されていることを利用して、`CALL 0x10(GS)`という命令でシステムコールを呼び出していました。

しかし、Android環境では`glibc`ではなく`bionic`という独自のCライブラリと動的リンカが使用されています。`bionic`の動的リンカは、`glibc`のように`__kernel_vsyscall`ヘルパーを`0x10(GS)`に保存しないため、この呼び出し方法がAndroid/386では機能しませんでした。

さらに重要な問題として、`CALL *runtime_vdso(SB)`という形式の呼び出しは「テキスト再配置（text relocations）」を必要としました。テキスト再配置は、実行時にコードセクション（テキストセクション）を書き換える必要があり、これはセキュリティ上のリスク（ASLRなどの緩和策を無効にする可能性）やパフォーマンスのオーバーヘッドを引き起こす可能性があります。GoはAndroid上でテキスト再配置を排除することを目指しており、この古いシステムコール呼び出し方法はその目標と矛盾していました。

これらの理由から、Android/386では`bionic`が内部的にシステムコールを呼び出す際に使用している`int $0x80`ソフトウェア割り込みに切り替える必要がありました。これにより、Android環境でのシステムコール呼び出しの互換性を確保し、テキスト再配置の問題を回避することが可能になります。

## 前提知識の解説

### システムコール (Syscall)

システムコールは、ユーザー空間のプログラムがオペレーティングシステム（OS）のカーネル空間の機能（ファイルI/O、メモリ管理、プロセス制御など）にアクセスするためのメカニズムです。セキュリティと安定性のために、ユーザープログラムはカーネルに直接アクセスすることはできず、システムコールという定義されたインターフェースを通じてのみカーネルサービスを要求できます。

x86アーキテクチャでは、システムコールを呼び出す一般的な方法がいくつかあります。
*   **`int $0x80`**: ソフトウェア割り込みを利用する方法。レジスタにシステムコール番号と引数を設定し、`int $0x80`命令を実行することでカーネルに制御を移します。これは古いLinuxカーネルや、互換性が必要な環境でよく使われます。
*   **`sysenter`/`sysexit` (x86)** または **`syscall`/`sysret` (x86-64)**: より高速なシステムコール呼び出しメカニズム。割り込みではなく、専用の命令を使ってカーネルに直接ジャンプします。
*   **VDSO (Virtual Dynamic Shared Object)**: 後述。

### VDSO (Virtual Dynamic Shared Object)

VDSOは、Linuxカーネルがユーザー空間の各プロセスのアドレス空間にマッピングする小さな共有ライブラリです。これには、`gettimeofday`や`getcpu`など、頻繁に呼び出されるがカーネルモードへの完全な切り替えを必要としないシステムコールの一部が実装されています。VDSOを使用することで、システムコール呼び出しのオーバーヘッドを削減し、パフォーマンスを向上させることができます。

VDSO内の関数は、通常、`sysenter`/`syscall`命令を使用してカーネルにアクセスしますが、一部の古いシステムや特定の構成では`int $0x80`を使用することもあります。`glibc`のような標準Cライブラリは、VDSOの存在を検出し、利用可能な場合はそれを通じてシステムコールを呼び出すように最適化されています。

### `glibc` と `bionic` (AndroidのCライブラリ)

*   **`glibc` (GNU C Library)**: ほとんどのLinuxディストリビューションで標準的に使用されているCライブラリです。非常に機能が豊富で、POSIX標準に準拠しています。`glibc`の動的リンカは、`__kernel_vsyscall`のようなVDSOヘルパーを特定のメモリ位置（例: `0x10(GS)`）に配置する慣習があります。
*   **`bionic`**: Androidオペレーティングシステムで使用されるCライブラリです。`glibc`よりも軽量で、組み込みシステムやリソースが限られた環境向けに最適化されています。`bionic`の動的リンカは、`glibc`とは異なる方法でVDSOを扱います。特に、`__kernel_vsyscall`ヘルパーを`0x10(GS)`に保存するような慣習はありません。そのため、`bionic`環境では、システムコールを呼び出すために`int $0x80`のような直接的な方法がよく用いられます。

### `int $0x80` (ソフトウェア割り込みによるシステムコール呼び出し)

`int $0x80`は、x86アーキテクチャにおけるソフトウェア割り込み命令の一つで、Linuxカーネルでシステムコールを呼び出すために使用されます。この命令が実行されると、CPUは割り込みベクタテーブルを参照し、0x80番の割り込みハンドラ（通常はカーネルのシステムコールエントリポイント）に制御を移します。システムコール番号は`EAX`レジスタに、引数は`EBX`, `ECX`, `EDX`, `ESI`, `EDI`などのレジスタに格納されてカーネルに渡されます。

### テキスト再配置 (Text Relocations)

テキスト再配置とは、プログラムの実行時に、読み取り専用であるべきコードセクション（テキストセクション）内の命令を書き換える必要があるリンカの処理を指します。これは通常、位置独立コード（PIC: Position-Independent Code）ではないコードが、共有ライブラリや動的にロードされるモジュール内で絶対アドレスを参照する場合に発生します。

テキスト再配置はいくつかの問題を引き起こします。
1.  **セキュリティ**: コードセクションが書き込み可能になるため、攻撃者がコードを改ざんする機会が増え、ASLR（Address Space Layout Randomization）などのセキュリティ機構の効果が低下する可能性があります。
2.  **パフォーマンス**: 実行時にリンカがコードを書き換える必要があるため、プログラムの起動時間が長くなったり、メモリ使用量が増えたりする可能性があります。
3.  **メモリ共有**: コードセクションが書き換えられると、そのコードは複数のプロセス間で共有できなくなり、メモリ効率が低下します。

現代のシステムでは、セキュリティとパフォーマンスの観点からテキスト再配置を避けることが強く推奨されており、多くのプラットフォーム（特にAndroid）ではテキスト再配置を含むバイナリのロードを制限または禁止しています。

### `CALL *runtime_vdso(SB)` (GoにおけるVDSO呼び出しの慣習)

Goのランタイムでは、システムコールを効率的に呼び出すために、アセンブリコード内でVDSOを利用する慣習がありました。`CALL *runtime_vdso(SB)`は、`runtime_vdso`というシンボルが指すアドレス（通常はVDSO内のシステムコールエントリポイント）を間接的に呼び出すことを意味します。`SB`はStatic Baseレジスタを指し、Goのアセンブリではグローバルシンボルへの参照に使われます。

このコミットの変更前は、`glibc`の振る舞いを前提として、`runtime_vdso`が`0x10(GS)`（GSセグメントレジスタを基準としたオフセット10番地）に配置された`__kernel_vsyscall`ヘルパーを指すように設定されていました。しかし、前述の通り、この前提がAndroid/386では崩れていました。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムと`syscall`パッケージにおけるシステムコール呼び出しメカニズムを、ターゲットOS（特にAndroid）に応じて動的に切り替える点にあります。

変更は主に`src/runtime/sys_linux_386.s`と`src/syscall/asm_linux_386.s`の2つのアセンブリファイルで行われています。

1.  **`INVOKE_SYSCALL` マクロの導入**:
    システムコールを呼び出すための新しいマクロ`INVOKE_SYSCALL`が定義されました。このマクロは、コンパイル時の`GOOS_android`プリプロセッサマクロの有無によって異なる命令に展開されます。
    *   `#ifdef GOOS_android`: Android向けにコンパイルされる場合、`INVOKE_SYSCALL`は`INT $0x80`に展開されます。これは、Androidの`bionic`ライブラリがシステムコールを呼び出す標準的な方法です。
    *   `#else`: Android以外のLinuxシステム向けにコンパイルされる場合、`INVOKE_SYSCALL`は`CALL 0x10(GS)`に展開されます。これは、`glibc`の動的リンカが`__kernel_vsyscall`ヘルパーを`0x10(GS)`に配置する慣習を利用した、従来のVDSO経由のシステムコール呼び出し方法です。

2.  **既存のシステムコール呼び出しの置換**:
    `src/runtime/sys_linux_386.s`内の`runtime·exit`, `runtime·open`, `runtime·write`など、多数のシステムコール呼び出し箇所で、従来の`CALL 0x10(GS)`が新しく定義された`INVOKE_SYSCALL`マクロに置き換えられました。
    同様に、`src/syscall/asm_linux_386.s`内の`·Syscall`, `·Syscall6`, `·RawSyscall`などの関数で、`CALL *runtime·_vdso(SB)`が`INVOKE_SYSCALL`に置き換えられました。

3.  **`runtime·setldt`のコメント修正と条件付きコンパイルの調整**:
    `src/runtime/sys_linux_386.s`内の`runtime·setldt`関数は、`0x10(GS)`にVDSOエントリポイントを格納する処理を行っていました。この処理は`glibc`の振る舞いを模倣するためのものでしたが、Androidでは不要になるため、`#ifdef GOOS_android`ブロックの外に移動され、コメントも`glibc`の動的リンカの振る舞いをコピーしていることを明確にするように修正されました。これにより、Android向けビルドではこのVDSOエントリポイントの設定がスキップされ、無関係な処理が実行されなくなります。

この変更により、GoはAndroid/386環境で`int $0x80`を使用することで、`bionic`のリンカの振る舞いに依存せず、テキスト再配置を回避しながらシステムコールを正しく呼び出すことができるようになりました。他のLinux環境では引き続きVDSOを利用した高速なシステムコール呼び出しが維持されます。

## コアとなるコードの解説

### `INVOKE_SYSCALL` マクロ

このコミットの最も重要な変更は、`INVOKE_SYSCALL`というアセンブリマクロの導入です。

```assembly
#ifdef GOOS_android
#define INVOKE_SYSCALL	INT	$0x80
#else
#define INVOKE_SYSCALL	CALL	0x10(GS)
#endif
```

*   **`#ifdef GOOS_android`**: これはプリプロセッサディレクティブで、`GOOS_android`というマクロが定義されている場合（つまり、Android向けにGoがコンパイルされている場合）に続くコードが有効になります。
*   **`#define INVOKE_SYSCALL INT $0x80`**: Android向けの場合、`INVOKE_SYSCALL`マクロは`INT $0x80`という命令に展開されます。これは、x86アーキテクチャでソフトウェア割り込みを介してシステムコールを呼び出すための標準的な方法です。Androidの`bionic`ライブラリはこの方法を使用しており、Goもこれに倣うことで互換性を確保します。
*   **`#else`**: `GOOS_android`が定義されていない場合（つまり、通常のLinuxシステム向けの場合）に続くコードが有効になります。
*   **`#define INVOKE_SYSCALL CALL 0x10(GS)`**: Android以外のLinux向けの場合、`INVOKE_SYSCALL`マクロは`CALL 0x10(GS)`という命令に展開されます。これは、`GS`セグメントレジスタを基準としたオフセット`0x10`番地にあるアドレスを呼び出す命令です。`glibc`の動的リンカは、この場所にVDSOの`__kernel_vsyscall`エントリポイントを配置する慣習があるため、Goはこれを利用して高速なシステムコール呼び出しを実現していました。

このマクロを使用することで、Goのランタイムと`syscall`パッケージ内のすべてのシステムコール呼び出し箇所は、コンパイルターゲットに応じて適切なシステムコールメカニズムを自動的に選択するようになります。これにより、コードの重複を避けつつ、プラットフォーム固有の要件に対応しています。

### `runtime·setldt` の変更

`runtime·setldt`関数は、Goランタイムが独自のLDT（Local Descriptor Table）を設定する際に、`0x10(GS)`にVDSOエントリポイントを格納する処理を含んでいました。

これらの変更により、GoはAndroid/386環境でシステムコールを正しく、かつテキスト再配置なしで実行できるようになり、GoのAndroidサポートの安定性とセキュリティが向上しました。

# [インデックス 22267] ファイルの概要

このコミットは、Goランタイムにおけるファイル操作（`open`, `close`, `read`, `write`）のシステムコールがエラー時に`-1`を返すように修正するものです。特に、様々なアーキテクチャ（Darwin, DragonFly, FreeBSD, Linux, NetBSD, OpenBSD）の32ビットおよび64ビット版アセンブリコードに、システムコールが失敗した場合に`-1`を返すロジックが追加されています。また、WindowsおよびNaCl環境におけるこれらの関数のスタブも更新され、テストコードも追加されています。

## 元コミット内容

Goランタイムの`open`, `close`, `read`, `write`関数が、エラー発生時に`-1`を返すように更新されました。このエラー検出ロジックは、`syscall`パッケージからコピーされたもので、`errno`（エラー番号）はランタイムでは使用されないため破棄されます。この変更は、`Fixes #10052`に関連しています。

## 変更の背景

このコミットの主な目的は、Goランタイムが直接呼び出すシステムコール（`open`, `close`, `read`, `write`）において、エラー発生時の戻り値の挙動を標準化し、信頼性を向上させることです。特に、システムコールが失敗した場合に、明確に`-1`を返すようにすることで、呼び出し元がエラーを適切に検出できるようになります。

コミットメッセージには`Fixes #10052`と記載されていますが、公開されているGoのIssueトラッカーではこの番号のIssueは直接見つかりませんでした。これは、内部的なトラッキング番号であるか、非常に古いIssueである可能性が考えられます。しかし、この変更が特定の不具合（例えば、システムコールがエラーを返してもランタイムがそれを正しく認識しない、あるいは予期せぬ値を返す）を修正するために行われたことは明らかです。

Goのランタイムは、OSとの低レベルなインタラクションを担当しており、ファイル操作のような基本的な機能はシステムコールを介して行われます。これらのシステムコールがエラーを適切に報告しない場合、ランタイムやその上で動作するGoプログラムが不安定になったり、予期せぬ動作を引き起こしたりする可能性があります。このコミットは、このような低レベルなエラーハンドリングの堅牢性を高めることを目的としています。

## 前提知識の解説

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するGo言語の一部です。これには、ガベージコレクタ、スケジューラ（ゴルーチンの管理）、メモリ割り当て、システムコールインターフェースなどが含まれます。GoプログラムがOSと対話する際、多くの場合、ランタイムが仲介役となります。このコミットで変更されている`open`, `close`, `read`, `write`関数は、Goランタイムが内部的に使用する低レベルなファイルI/O操作であり、Goの標準ライブラリ（例: `os`パッケージ）がこれらのランタイム関数を介してOSの機能を利用します。

### システムコール (System Call)

システムコールは、ユーザー空間で実行されているプログラムが、OSのカーネル空間で提供されるサービス（ファイルI/O、メモリ管理、プロセス制御など）を利用するためのインターフェースです。プログラムがファイルを開いたり、読み書きしたり、閉じたりする際には、対応するシステムコールをOSに発行します。

システムコールは通常、アセンブリ言語で実装されたラッパー関数を介して呼び出されます。これは、システムコールが特定のCPU命令（例: `INT 0x80`、`SYSCALL`、`SWI`）を使用してカーネルモードに切り替わる必要があるためです。システムコールが成功した場合、通常は非負の値（例: 読み書きされたバイト数、ファイルディスクリプタ）を返しますが、失敗した場合は負の値（例: `-1`）を返し、エラーの詳細を示すエラー番号（`errno`）を特定のレジスタやメモリ位置に設定するのが一般的です。

### ファイルディスクリプタ (File Descriptor)

ファイルディスクリプタは、Unix系OSにおいて、開かれたファイルやI/Oリソース（ソケット、パイプなど）を識別するためにOSがプロセスに割り当てる非負の整数です。`open`システムコールはファイルディスクリプタを返し、`read`, `write`, `close`などのシステムコールはこのファイルディスクリプタを使用して特定のI/Oリソースを操作します。エラーが発生した場合、ファイルディスクリプタとして`-1`が返されることが一般的です。

### アセンブリ言語 (Assembly Language)

アセンブリ言語は、CPUが直接実行できる機械語と1対1に対応する低レベルなプログラミング言語です。OSのカーネルやデバイスドライバ、そしてGoランタイムのような低レベルな部分では、パフォーマンスの最適化やハードウェアへの直接アクセス、システムコールの呼び出しのためにアセンブリ言語が使用されることがあります。

このコミットで変更されている`.s`ファイルは、Goのアセンブリ言語ファイルです。Goのアセンブリは、一般的なアセンブリ言語とは異なる独自の構文を持っていますが、基本的な概念（レジスタ、命令、ジャンプなど）は共通しています。

*   **レジスタ**: CPU内部の高速な記憶領域。`AX`, `R0`, `DI`, `SI`, `DX`などはレジスタ名です。システムコールの引数や戻り値はこれらのレジスタを介してやり取りされます。
*   **命令**:
    *   `MOVL`, `MOVW`, `MOVD`, `CMPL`, `CMPQ`, `CMP`: データをレジスタやメモリ間で移動させたり、値を比較したりする命令。
    *   `INT 0x80`: x86アーキテクチャにおけるソフトウェア割り込み命令。LinuxやFreeBSDなどの32ビットシステムでシステムコールを呼び出す際に使用されます。
    *   `SYSCALL`: x86-64アーキテクチャやPPC64xなどにおける高速なシステムコール命令。
    *   `SWI`: ARMアーキテクチャにおけるソフトウェア割り込み命令。
    *   `JAE` (Jump if Above or Equal): 比較結果が「以上」の場合にジャンプする命令。符号なし数に対する比較。
    *   `JCC` (Jump if Carry Clear): キャリーフラグがクリア（0）の場合にジャンプする命令。多くのシステムコールでは、成功時にキャリーフラグがクリアされ、失敗時にセットされます。
    *   `JLS` (Jump if Less or Same): 比較結果が「以下」の場合にジャンプする命令。符号なし数に対する比較。
    *   `BVC` (Branch if Overflow Clear): オーバーフローフラグがクリアの場合に分岐する命令。
    *   `MOVW.CS` (Move Word if Carry Set): キャリーフラグがセットされている場合にワードを移動する命令。
    *   `MOVW.HI` (Move Word if Higher): 比較結果が「より大きい」場合にワードを移動する命令。
*   **`errno`**: Unix系OSでシステムコールが失敗した際に、エラーの種類を示す整数値が格納されるグローバル変数（またはスレッドローカル変数）。Goランタイムはこの`errno`を直接使用しないため、このコミットでは破棄されています。

## 技術的詳細

このコミットの核心は、GoランタイムがOSのシステムコールを呼び出した際に、そのシステムコールの戻り値をチェックし、エラーを示す値（通常は負の値）が返された場合に、Goランタイムの関数も一貫して`-1`を返すようにすることです。

多くのUnix系システムコールでは、成功時には非負の値を返し、失敗時には`-1`を返して、`errno`変数にエラーコードを設定します。Goランタイムは、この`-1`という慣習に従うことで、低レベルなファイルI/O操作の信頼性を向上させています。

具体的な変更は、各アーキテクチャ（386, amd64, arm, ppc64x）とOS（Darwin, DragonFly, FreeBSD, Linux, NetBSD, OpenBSD）に対応するアセンブリファイル（`sys_*.s`）に集中しています。これらのファイルでは、`open`, `close`, `read`, `write`システムコールを呼び出した直後に、戻り値（通常は`AX`レジスタや`R0`レジスタに格納される）をチェックするロジックが追加されています。

例えば、x86系のアーキテクチャでは、システムコールが成功するとキャリーフラグがクリアされる（`JCC`）か、戻り値が特定の閾値（例: `0xfffff001`、これは`-4095`に相当し、一般的なエラーコードの範囲外）より大きいかどうかをチェックする（`CMPL`/`CMPQ`と`JLS`）ことでエラーを検出します。エラーが検出された場合、戻り値レジスタに明示的に`-1`（`0xffffffff`または`0xffffffffffffffff`）をセットしています。

ARMアーキテクチャでは、`SWI`命令の後に`MOVW.CS`や`MOVW.HI`といった条件付き移動命令を使用して、キャリーフラグや比較結果に基づいて`-1`をセットしています。

Windows環境では、`os_windows.go`に`open`, `close`, `read`のスタブが追加されており、これらは`throw("unimplemented")`を呼び出し、`-1`を返します。これは、WindowsのファイルI/OがUnix系とは異なるAPIを使用するため、Goランタイムが直接これらのシステムコールを呼び出すことは稀であり、テスト目的のスタブとして機能していることを示唆しています。

`runtime_test.go`には`TestBadOpen`という新しいテスト関数が追加されており、これは存在しないファイルを開こうとしたり、無効なファイルディスクリプタに対して`read`, `write`, `close`を呼び出したりした場合に、期待通り`-1`が返されることを検証しています。これにより、変更が正しく機能していることが保証されます。

コミットメッセージにある「Error detection code copied from syscall, where presumably we actually do it right.」という記述は、Goの`syscall`パッケージが既に同様のエラー検出ロジックを実装しており、その実績のあるコードをランタイムの低レベルな部分にも適用したことを示しています。ただし、ランタイムでは`errno`を必要としないため、その部分は破棄されています。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は、以下のファイル群にわたっています。

1.  **`src/runtime/export_test.go`**:
    *   テストのために、ランタイムの内部関数である`open`, `close`, `read`, `write`をエクスポートする`var Open = open`のような行が追加されました。

2.  **`src/runtime/os_nacl.go`**:
    *   `open`, `close`, `read`関数のスタブが追加されました。これらはテストが正しくリンクされるためのもので、実際に呼び出されることは想定されていません。

3.  **`src/runtime/os_windows.go`**:
    *   `open`, `close`, `read`関数のスタブが追加されました。これらの関数は`throw("unimplemented")`を呼び出し、`-1`を返します。Windows固有のファイルI/Oは異なるAPIを使用するため、これらのスタブは主にテスト目的です。

4.  **`src/runtime/runtime_test.go`**:
    *   `TestBadOpen`という新しいテスト関数が追加されました。このテストは、`open`が失敗した場合に`-1`を返すこと、および無効なファイルディスクリプタに対して`read`, `write`, `close`を呼び出した場合に`-1`を返すことを検証します。

5.  **`src/runtime/sys_*.s` (多数のファイル)**:
    *   各OSとアーキテクチャ（例: `sys_darwin_386.s`, `sys_linux_amd64.s`, `sys_freebsd_arm.s`など）に対応するアセンブリファイルにおいて、`open`, `close`, `read`, `write`システムコールの呼び出し後に、エラー検出と`-1`を返すロジックが追加されました。

    *   **x86/x86-64系 (例: `sys_darwin_386.s`, `sys_linux_amd64.s`)**:
        *   システムコール呼び出し後、`JAE` (Jump if Above or Equal) や `JCC` (Jump if Carry Clear) 命令を使用して、システムコールが成功したかどうかをチェックします。
        *   失敗した場合（キャリーフラグがセットされている、または戻り値がエラーを示す範囲にある場合）、`MOVL $-1, AX` (または `MOVL $-1, R0`など、対応するレジスタ) 命令で明示的に`-1`を戻り値レジスタに設定します。
        *   Linuxのx86/x86-64では、`CMPL AX, $0xfffff001` や `CMPQ AX, $0xfffffffffffff001` といった比較を行い、戻り値がエラー範囲にあるかをチェックしています。

    *   **ARM系 (例: `sys_darwin_arm.s`, `sys_linux_arm.s`)**:
        *   システムコール呼び出し後、`MOVW.CS $-1, R0` (Move Word if Carry Set) や `MOVW.HI $-1, R0` (Move Word if Higher) といった条件付き移動命令を使用して、エラー時に`-1`を戻り値レジスタ`R0`に設定します。

    *   **PPC64x系 (例: `sys_linux_ppc64x.s`)**:
        *   システムコール呼び出し後、`BVC` (Branch if Overflow Clear) 命令を使用して、エラー時に`-1`を戻り値レジスタ`R3`に設定します。

## コアとなるコードの解説

ここでは、アセンブリコードの変更に焦点を当てて解説します。

**変更前（概念）:**

```assembly
TEXT runtime·open(SB),NOSPLIT,$0
    // ... システムコール引数の設定 ...
    SYSCALL // または INT $0x80, SWI $0 など
    // AX (または R0など) にシステムコールの戻り値が格納される
    MOVL AX, ret+12(FP) // 戻り値をGoの戻り値として設定
    RET
```

変更前は、システムコールが返した値をそのままGoの関数（`runtime·open`など）の戻り値としていました。しかし、システムコールがエラーを返した場合、その値が必ずしもGoランタイムが期待する`-1`であるとは限りませんでした。また、エラーを示すフラグ（キャリーフラグなど）がセットされていても、それをチェックして`-1`に変換するロジックがありませんでした。

**変更後（概念、x86/x86-64の例）:**

```assembly
TEXT runtime·open(SB),NOSPLIT,$0
    // ... システムコール引数の設定 ...
    SYSCALL // または INT $0x80
    JCC 2(PC) // キャリーフラグがクリア（成功）なら次の命令をスキップ
    MOVL $-1, AX // 失敗ならAXに-1を設定
    MOVL AX, ret+16(FP) // AXの値をGoの戻り値として設定
    RET
```

この変更のポイントは、システムコール呼び出し直後にエラーチェックのロジックが追加されたことです。

*   **`SYSCALL` (または `INT $0x80`, `SWI $0`など)**: OSのカーネルに処理を移し、システムコールを実行します。システムコールの結果は、通常、特定のレジスタ（x86/x86-64では`AX`、ARMでは`R0`など）に格納されます。成功時には非負の値、失敗時には負の値（またはエラーを示すフラグ）が設定されます。

*   **`JCC 2(PC)` (Jump if Carry Clear)**: これはx86/x86-64アーキテクチャにおける条件付きジャンプ命令です。多くのシステムコールでは、成功時にCPUのキャリーフラグ（CF）がクリア（0）になり、失敗時にセット（1）になります。
    *   `JCC`はキャリーフラグがクリアの場合にジャンプします。`2(PC)`は「プログラムカウンタの現在値から2バイト先にジャンプする」という意味で、これは次の`MOVL $-1, AX`命令をスキップすることを意味します。
    *   つまり、システムコールが成功した場合、`JCC`命令によってエラー処理の行がスキップされ、元の戻り値がそのままGoの戻り値として使用されます。
    *   システムコールが失敗した場合（キャリーフラグがセットされている場合）、`JCC`はジャンプせず、次の`MOVL $-1, AX`命令が実行されます。

*   **`MOVL $-1, AX`**: この命令は、レジスタ`AX`に即値`-1`を移動させます。システムコールが失敗した場合に、Goランタイムの関数が常に`-1`を返すようにするためのものです。`-1`は、ファイルディスクリプタや読み書きされたバイト数として無効な値であり、エラーを示す標準的な慣習です。

*   **`CMPL AX, $0xfffff001` / `JLS 2(PC)` (Linux x86/x86-64の例)**:
    Linuxでは、システムコールがエラーを返すと、`AX`レジスタに`-4095`から`-1`までの範囲の負の値が設定されることがあります（これは`errno`の値に対応します）。`0xfffff001`は符号なしの表現で`-4095`に相当します。
    *   `CMPL AX, $0xfffff001`: `AX`レジスタの値と`0xfffff001`を比較します。
    *   `JLS 2(PC)`: `AX`が`0xfffff001`以下（つまり、エラーを示す負の値）の場合にジャンプします。この場合も、ジャンプしない（成功）場合はそのまま進み、ジャンプする（失敗）場合は`MOVL $-1, AX`が実行されます。

*   **`MOVW.CS $-1, R0` (ARMの例)**:
    ARMアーキテクチャでは、`SWI`（ソフトウェア割り込み）命令でシステムコールを呼び出します。システムコールが失敗すると、キャリーフラグがセットされることがあります。
    *   `MOVW.CS $-1, R0`: これは条件付き実行命令です。キャリーフラグ（CS: Carry Set）がセットされている場合にのみ、`-1`をレジスタ`R0`（戻り値レジスタ）に移動させます。これにより、エラー時にのみ`-1`が設定されます。

これらの変更により、Goランタイムの低レベルなファイルI/O関数は、OSのシステムコールがエラーを返した場合に、プラットフォームやアーキテクチャに関わらず一貫して`-1`を返すようになり、Goランタイム内部でのエラーハンドリングがより予測可能で堅牢になりました。

## 元コミット内容

Goランタイムの`open`, `close`, `read`, `write`関数が、エラー発生時に`-1`を返すように更新されました。このエラー検出ロジックは、`syscall`パッケージからコピーされたもので、`errno`（エラー番号）はランタイムでは使用されないため破棄されます。この変更は、`Fixes #10052`に関連しています。

## 変更の背景

このコミットの主な目的は、Goランタイムが直接呼び出すシステムコール（`open`, `close`, `read`, `write`）において、エラー発生時の戻り値の挙動を標準化し、信頼性を向上させることです。特に、システムコールが失敗した場合に、明確に`-1`を返すようにすることで、呼び出し元がエラーを適切に検出できるようになります。

コミットメッセージには`Fixes #10052`と記載されていますが、公開されているGoのIssueトラッカーではこの番号のIssueは直接見つかりませんでした。これは、内部的なトラッキング番号であるか、非常に古いIssueである可能性が考えられます。しかし、この変更が特定の不具合（例えば、システムコールがエラーを返してもランタイムがそれを正しく認識しない、あるいは予期せぬ値を返す）を修正するために行われたことは明らかです。

Goのランタイムは、OSとの低レベルなインタラクションを担当しており、ファイル操作のような基本的な機能はシステムコールを介して行われます。これらのシステムコールがエラーを適切に報告しない場合、ランタイムやその上で動作するGoプログラムが不安定になったり、予期せぬ動作を引き起こしたりする可能性があります。このコミットは、このような低レベルなエラーハンドリングの堅牢性を高めることを目的としています。

## 前提知識の解説

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するGo言語の一部です。これには、ガベージコレクタ、スケジューラ（ゴルーチンの管理）、メモリ割り当て、システムコールインターフェースなどが含まれます。GoプログラムがOSと対話する際、多くの場合、ランタイムが仲介役となります。このコミットで変更されている`open`, `close`, `read`, `write`関数は、Goランタイムが内部的に使用する低レベルなファイルI/O操作であり、Goの標準ライブラリ（例: `os`パッケージ）がこれらのランタイム関数を介してOSの機能を利用します。

### システムコール (System Call)

システムコールは、ユーザー空間で実行されているプログラムが、OSのカーネル空間で提供されるサービス（ファイルI/O、メモリ管理、プロセス制御など）を利用するためのインターフェースです。プログラムがファイルを開いたり、読み書きしたり、閉じたりする際には、対応するシステムコールをOSに発行します。

システムコールは通常、アセンブリ言語で実装されたラッパー関数を介して呼び出されます。これは、システムコールが特定のCPU命令（例: `INT 0x80`、`SYSCALL`、`SWI`）を使用してカーネルモードに切り替わる必要があるためです。システムコールが成功した場合、通常は非負の値（例: 読み書きされたバイト数、ファイルディスクリプタ）を返しますが、失敗した場合は負の値（例: `-1`）を返し、エラーの詳細を示すエラー番号（`errno`）を特定のレジスタやメモリ位置に設定するのが一般的です。

### ファイルディスクリプタ (File Descriptor)

ファイルディスクリプタは、Unix系OSにおいて、開かれたファイルやI/Oリソース（ソケット、パイプなど）を識別するためにOSがプロセスに割り当てる非負の整数です。`open`システムコールはファイルディスクリプタを返し、`read`, `write`, `close`などのシステムコールはこのファイルディスクリプタを使用して特定のI/Oリソースを操作します。エラーが発生した場合、ファイルディスクリプタとして`-1`が返されることが一般的です。

### アセンブリ言語 (Assembly Language)

アセンブリ言語は、CPUが直接実行できる機械語と1対1に対応する低レベルなプログラミング言語です。OSのカーネルやデバイスドライバ、そしてGoランタイムのような低レベルな部分では、パフォーマンスの最適化やハードウェアへの直接アクセス、システムコールの呼び出しのためにアセンブリ言語が使用されることがあります。

このコミットで変更されている`.s`ファイルは、Goのアセンブリ言語ファイルです。Goのアセンブリは、一般的なアセンブリ言語とは異なる独自の構文を持っていますが、基本的な概念（レジスタ、命令、ジャンプなど）は共通しています。

*   **レジスタ**: CPU内部の高速な記憶領域。`AX`, `R0`, `DI`, `SI`, `DX`などはレジスタ名です。システムコールの引数や戻り値はこれらのレジスタを介してやり取りされます。
*   **命令**:
    *   `MOVL`, `MOVW`, `MOVD`, `CMPL`, `CMPQ`, `CMP`: データをレジスタやメモリ間で移動させたり、値を比較したりする命令。
    *   `INT 0x80`: x86アーキテクチャにおけるソフトウェア割り込み命令。LinuxやFreeBSDなどの32ビットシステムでシステムコールを呼び出す際に使用されます。
    *   `SYSCALL`: x86-64アーキテクチャやPPC64xなどにおける高速なシステムコール命令。
    *   `SWI`: ARMアーキテクチャにおけるソフトウェア割り込み命令。
    *   `JAE` (Jump if Above or Equal): 比較結果が「以上」の場合にジャンプする命令。符号なし数に対する比較。
    *   `JCC` (Jump if Carry Clear): キャリーフラグがクリア（0）の場合にジャンプする命令。多くのシステムコールでは、成功時にキャリーフラグがクリアされ、失敗時にセットされます。
    *   `JLS` (Jump if Less or Same): 比較結果が「以下」の場合にジャンプする命令。符号なし数に対する比較。
    *   `BVC` (Branch if Overflow Clear): オーバーフローフラグがクリアの場合に分岐する命令。
    *   `MOVW.CS` (Move Word if Carry Set): キャリーフラグがセットされている場合にワードを移動する命令。
    *   `MOVW.HI` (Move Word if Higher): 比較結果が「より大きい」場合にワードを移動する命令。
*   **`errno`**: Unix系OSでシステムコールが失敗した際に、エラーの種類を示す整数値が格納されるグローバル変数（またはスレッドローカル変数）。Goランタイムはこの`errno`を直接使用しないため、このコミットでは破棄されています。

## 技術的詳細

このコミットの核心は、GoランタイムがOSのシステムコールを呼び出した際に、そのシステムコールの戻り値をチェックし、エラーを示す値（通常は負の値）が返された場合に、Goランタイムの関数も一貫して`-1`を返すようにすることです。

多くのUnix系システムコールでは、成功時には非負の値を返し、失敗時には`-1`を返して、`errno`変数にエラーコードを設定します。Goランタイムは、この`-1`という慣習に従うことで、低レベルなファイルI/O操作の信頼性を向上させています。

具体的な変更は、各アーキテクチャ（386, amd64, arm, ppc64x）とOS（Darwin, DragonFly, FreeBSD, Linux, NetBSD, OpenBSD）に対応するアセンブリファイル（`sys_*.s`）に集中しています。これらのファイルでは、`open`, `close`, `read`, `write`システムコールを呼び出した直後に、戻り値（通常は`AX`レジスタや`R0`レジスタに格納される）をチェックするロジックが追加されています。

例えば、x86系のアーキテクチャでは、システムコールが成功するとキャリーフラグがクリアされる（`JCC`）か、戻り値が特定の閾値（例: `0xfffff001`、これは`-4095`に相当し、一般的なエラーコードの範囲外）より大きいかどうかをチェックする（`CMPL`/`CMPQ`と`JLS`）ことでエラーを検出します。エラーが検出された場合、戻り値レジスタに明示的に`-1`（`0xffffffff`または`0xffffffffffffffff`）をセットしています。

ARMアーキテクチャでは、`SWI`命令の後に`MOVW.CS`や`MOVW.HI`といった条件付き移動命令を使用して、キャリーフラグや比較結果に基づいて`-1`をセットしています。

Windows環境では、`os_windows.go`に`open`, `close`, `read`のスタブが追加されており、これらは`throw("unimplemented")`を呼び出し、`-1`を返します。これは、WindowsのファイルI/OがUnix系とは異なるAPIを使用するため、Goランタイムが直接これらのシステムコールを呼び出すことは稀であり、テスト目的のスタブとして機能していることを示唆しています。

`runtime_test.go`には`TestBadOpen`という新しいテスト関数が追加されており、これは存在しないファイルを開こうとしたり、無効なファイルディスクリプタに対して`read`, `write`, `close`を呼び出したりした場合に、期待通り`-1`が返されることを検証しています。これにより、変更が正しく機能していることが保証されます。

コミットメッセージにある「Error detection code copied from syscall, where presumably we actually do it right.」という記述は、Goの`syscall`パッケージが既に同様のエラー検出ロジックを実装しており、その実績のあるコードをランタイムの低レベルな部分にも適用したことを示しています。ただし、ランタイムでは`errno`を必要としないため、その部分は破棄されています。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は、以下のファイル群にわたっています。

1.  **`src/runtime/export_test.go`**:
    *   テストのために、ランタイムの内部関数である`open`, `close`, `read`, `write`をエクスポートする`var Open = open`のような行が追加されました。

2.  **`src/runtime/os_nacl.go`**:
    *   `open`, `close`, `read`関数のスタブが追加されました。これらはテストが正しくリンクされるためのもので、実際に呼び出されることは想定されていません。

3.  **`src/runtime/os_windows.go`**:
    *   `open`, `close`, `read`関数のスタブが追加されました。これらの関数は`throw("unimplemented")`を呼び出し、`-1`を返します。Windows固有のファイルI/Oは異なるAPIを使用するため、これらのスタブは主にテスト目的です。

4.  **`src/runtime/runtime_test.go`**:
    *   `TestBadOpen`という新しいテスト関数が追加されました。このテストは、`open`が失敗した場合に`-1`を返すこと、および無効なファイルディスクリプタに対して`read`, `write`, `close`を呼び出した場合に`-1`を返すことを検証します。

5.  **`src/runtime/sys_*.s` (多数のファイル)**:
    *   各OSとアーキテクチャ（例: `sys_darwin_386.s`, `sys_linux_amd64.s`, `sys_freebsd_arm.s`など）に対応するアセンブリファイルにおいて、`open`, `close`, `read`, `write`システムコールの呼び出し後に、エラー検出と`-1`を返すロジックが追加されました。

    *   **x86/x86-64系 (例: `sys_darwin_386.s`, `sys_linux_amd64.s`)**:
        *   システムコール呼び出し後、`JAE` (Jump if Above or Equal) や `JCC` (Jump if Carry Clear) 命令を使用して、システムコールが成功したかどうかをチェックします。
        *   失敗した場合（キャリーフラグがセットされている、または戻り値がエラーを示す範囲にある場合）、`MOVL $-1, AX` (または `MOVL $-1, R0`など、対応するレジスタ) 命令で明示的に`-1`を戻り値レジスタに設定します。
        *   Linuxのx86/x86-64では、`CMPL AX, $0xfffff001` や `CMPQ AX, $0xfffffffffffff001` といった比較を行い、戻り値がエラー範囲にあるかをチェックしています。

    *   **ARM系 (例: `sys_darwin_arm.s`, `sys_linux_arm.s`)**:
        *   システムコール呼び出し後、`MOVW.CS $-1, R0` (Move Word if Carry Set) や `MOVW.HI $-1, R0` (Move Word if Higher) といった条件付き移動命令を使用して、エラー時に`-1`を戻り値レジスタ`R0`に設定します。

    *   **PPC64x系 (例: `sys_linux_ppc64x.s`)**:
        *   システムコール呼び出し後、`BVC` (Branch if Overflow Clear) 命令を使用して、エラー時に`-1`を戻り値レジスタ`R3`に設定します。

## コアとなるコードの解説

ここでは、アセンブリコードの変更に焦点を当てて解説します。

**変更前（概念）:**

```assembly
TEXT runtime·open(SB),NOSPLIT,$0
    // ... システムコール引数の設定 ...
    SYSCALL // または INT $0x80, SWI $0 など
    // AX (または R0など) にシステムコールの戻り値が格納される
    MOVL AX, ret+12(FP) // 戻り値をGoの戻り値として設定
    RET
```

変更前は、システムコールが返した値をそのままGoの関数（`runtime·open`など）の戻り値としていました。しかし、システムコールがエラーを返した場合、その値が必ずしもGoランタイムが期待する`-1`であるとは限りませんでした。また、エラーを示すフラグ（キャリーフラグなど）がセットされていても、それをチェックして`-1`に変換するロジックがありませんでした。

**変更後（概念、x86/x86-64の例）:**

```assembly
TEXT runtime·open(SB),NOSPLIT,$0
    // ... システムコール引数の設定 ...
    SYSCALL // または INT $0x80
    JCC 2(PC) // キャリーフラグがクリア（成功）なら次の命令をスキップ
    MOVL $-1, AX // 失敗ならAXに-1を設定
    MOVL AX, ret+16(FP) // AXの値をGoの戻り値として設定
    RET
```

この変更のポイントは、システムコール呼び出し直後にエラーチェックのロジックが追加されたことです。

*   **`SYSCALL` (または `INT $0x80`, `SWI $0`など)**: OSのカーネルに処理を移し、システムコールを実行します。システムコールの結果は、通常、特定のレジスタ（x86/x86-64では`AX`、ARMでは`R0`など）に格納されます。成功時には非負の値、失敗時には負の値（またはエラーを示すフラグ）が設定されます。

*   **`JCC 2(PC)` (Jump if Carry Clear)**: これはx86/x86-64アーキテクチャにおける条件付きジャンプ命令です。多くのシステムコールでは、成功時にCPUのキャリーフラグ（CF）がクリア（0）になり、失敗時にセット（1）になります。
    *   `JCC`はキャリーフラグがクリアの場合にジャンプします。`2(PC)`は「プログラムカウンタの現在値から2バイト先にジャンプする」という意味で、これは次の`MOVL $-1, AX`命令をスキップすることを意味します。
    *   つまり、システムコールが成功した場合、`JCC`命令によってエラー処理の行がスキップされ、元の戻り値がそのままGoの戻り値として使用されます。
    *   システムコールが失敗した場合（キャリーフラグがセットされている場合）、`JCC`はジャンプせず、次の`MOVL $-1, AX`命令が実行されます。

*   **`MOVL $-1, AX`**: この命令は、レジスタ`AX`に即値`-1`を移動させます。システムコールが失敗した場合に、Goランタイムの関数が常に`-1`を返すようにするためのものです。`-1`は、ファイルディスクリプタや読み書きされたバイト数として無効な値であり、エラーを示す標準的な慣習です。

*   **`CMPL AX, $0xfffff001` / `JLS 2(PC)` (Linux x86/x86-64の例)**:
    Linuxでは、システムコールがエラーを返すと、`AX`レジスタに`-4095`から`-1`までの範囲の負の値が設定されることがあります（これは`errno`の値に対応します）。`0xfffff001`は符号なしの表現で`-4095`に相当します。
    *   `CMPL AX, $0xfffff001`: `AX`レジスタの値と`0xfffff001`を比較します。
    *   `JLS 2(PC)`: `AX`が`0xfffff001`以下（つまり、エラーを示す負の値）の場合にジャンプします。この場合も、ジャンプしない（成功）場合はそのまま進み、ジャンプする（失敗）場合は`MOVL $-1, AX`が実行されます。

*   **`MOVW.CS $-1, R0` (ARMの例)**:
    ARMアーキテクチャでは、`SWI`（ソフトウェア割り込み）命令でシステムコールを呼び出します。システムコールが失敗すると、キャリーフラグがセットされることがあります。
    *   `MOVW.CS $-1, R0`: これは条件付き実行命令です。キャリーフラグ（CS: Carry Set）がセットされている場合にのみ、`-1`をレジスタ`R0`（戻り値レジスタ）に移動させます。これにより、エラー時にのみ`-1`が設定されます。

これらの変更により、Goランタイムの低レベルなファイルI/O関数は、OSのシステムコールがエラーを返した場合に、プラットフォームやアーキテクチャに関わらず一貫して`-1`を返すようになり、Goランタイム内部でのエラーハンドリングがより予測可能で堅牢になりました。

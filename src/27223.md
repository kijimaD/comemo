## 変更の背景

Goランタイムの`shrinkstack`関数は、Goroutineのスタックが過剰に大きくなった場合にそのサイズを縮小する役割を担っています。しかし、この機能はこれまでSTW（Stop The World）フェーズ中、つまり全てのGoroutineが一時停止している間にのみ安全に実行可能でした。その理由は、`shrinkstack`がチャネルに関連するスタックポインタや送受信スロットを調整・移動する際に、チャネルコードとの同期を取っていなかったためです。

STWはガベージコレクション（GC）の重要なフェーズですが、その間はアプリケーションの実行が完全に停止するため、レイテンシの原因となります。GoランタイムはSTWの時間を最小限に抑える努力を続けており、`shrinkstack`のような処理をSTW外で安全に実行できるようにすることは、GCの効率化と全体的なアプリケーションパフォーマンスの向上に不可欠でした。

このコミットは、Issue #12967で報告された問題に対応し、`shrinkstack`がSTWなしで並行的に安全に動作できるようにすることで、Goランタイムのより効率的な運用を目指しています。

## 前提知識の解説

### Goランタイムのスタック管理

GoのGoroutineは、非常に軽量な実行単位であり、それぞれが独自のスタックを持っています。Goランタイムは、必要に応じてスタックを動的に拡大（stack growth）および縮小（stack shrinking）させることで、メモリ効率を最適化しています。

*   **スタックの拡大**: Goroutineが関数呼び出しを深く行うなどしてスタック領域が不足しそうになると、ランタイムはより大きな新しいスタックを割り当て、古いスタックの内容を新しいスタックにコピーします。
*   **スタックの縮小**: Goroutineがスタックをあまり使用しなくなった場合（例えば、深い関数呼び出しから戻った後）、ランタイムはスタックを縮小してメモリを解放します。この`shrinkstack`処理が本コミットの主題です。

スタックの拡大・縮小時には、スタック上に存在するポインタ（ローカル変数、引数、戻り値など）が新しいスタックアドレスを指すように調整される必要があります。

### GoのGoroutine

GoroutineはGoの並行処理の根幹をなすもので、OSのスレッドよりもはるかに軽量です。数百万のGoroutineを同時に実行することも可能です。GoroutineはGoランタイムによってスケジューリングされ、複数のOSスレッド上で多重化されて実行されます。

### Goのチャネルと`sudog`構造体

チャネルは、Goroutine間で値を安全に送受信するためのGoの主要な同期プリミティブです。チャネル操作（送信または受信）がブロックされる場合（例: バッファなしチャネルへの送信、空のチャネルからの受信）、Goroutineは一時停止し、`sudog`（"semaphore user goroutine" の略）という内部ランタイム構造体が使用されます。

*   **`sudog`**: `sudog`は、チャネルなどの同期プリミティブで待機しているGoroutineを表します。チャネルの内部には、送信待ちのGoroutineキュー（`sendq`）と受信待ちのGoroutineキュー（`recvq`）があり、これらのキューは`sudog`のリストとして管理されます。`sudog`には、待機しているGoroutineへのポインタや、チャネル操作に関連するスタック上のスロット（送受信される値が一時的に格納される場所）へのポインタが含まれることがあります。

### STW (Stop The World)

STWは、ガベージコレクション（GC）の特定のフェーズで、Goランタイムが全てのGoroutineの実行を一時的に停止させる期間を指します。これにより、GCはメモリの状態が変化しないことを保証し、安全にオブジェクトをスキャンしたり移動したりできます。STWはGCの正確性を保証するために不可欠ですが、アプリケーションの応答性を低下させるため、GoランタイムはSTWの時間を短縮するよう継続的に最適化されています。

### アトミック操作 (Atomic Operations)

アトミック操作は、複数のCPUコアやGoroutineから同時にアクセスされても、その操作全体が不可分（atomic）に実行されることを保証する低レベルの操作です。これにより、競合状態（race condition）を防ぎ、ロックを使用せずに共有データへの安全なアクセスを実現できます。Goでは`sync/atomic`パッケージを通じてアトミック操作が提供されており、本コミットでは`atomic.Casp1`（`CompareAndSwapPointer`に相当）が使用されています。これは、ポインタの値をアトミックに比較し、一致した場合にのみ新しい値に交換する操作です。

### ポインタ調整 (Pointer Adjustment)

スタックが移動する際、古いスタック上のアドレスを指していたポインタは、新しいスタック上の対応するアドレスを指すように更新される必要があります。このプロセスをポインタ調整と呼びます。Goランタイムは、GC情報（スタックマップ）を利用して、スタック上のどの位置にポインタが存在するかを識別し、それらを正確に調整します。

## 技術的詳細

このコミットの核心は、`shrinkstack`がSTWなしで安全に実行できるようにすることです。これまでの`shrinkstack`は、チャネルの送受信スロットや`sudog`が指すスタック上の領域を、チャネルコードとの同期なしに移動させていました。これは、Goroutineがチャネル操作でブロックされている間にスタックが縮小されると、チャネルコードが古い（無効な）スタックアドレスを参照したり、スタック上のデータが破壊されたりする可能性があったため、STW中のみ安全でした。

変更は主に以下の2つのメカニズムによって並行安全性を実現しています。

1.  **チャネルロックによる同期**:
    *   スタックを縮小するGoroutine（`gp`）がブロックしている可能性のある全てのチャネル（`gp.waiting`リストにある`sudog`が指すチャネル）に対して、`shrinkstack`はチャネルのロックを取得します。
    *   このロックは、`sudog`の調整と、送受信スロットを含む可能性のあるスタック領域のコピー中に保持されます。これにより、チャネル操作とスタック縮小処理の間で競合が発生するのを防ぎます。
    *   コミットメッセージでは、より粒度の細かい同期（例: `sudog`ごとに同期）も検討されたが、チャネルロックを使用することでチャネルコードに追加のロックが不要になり、またロック保持時間が非常に短い（スタック縮小時間全体に比べて）ため、このアプローチが採用されたと説明されています。

2.  **アトミックCASによるポインタ調整**:
    *   スタックフレーム内でチャネルの送受信スロットを含む可能性のあるポインタを調整する際、`atomic.Casp1`（CompareAndSwapPointer）が使用されます。
    *   これは、受信スロット内のポインタを調整する処理と、並行して実行される送信操作がその受信スロットに書き込む処理との間の競合を防ぐためです。`atomic.Casp1`を使用することで、ポインタが期待される古い値を保持している場合にのみ新しい値に更新され、そうでなければ再試行されるため、データの一貫性が保たれます。

これらの変更を実装するために、以下の具体的なコード変更が行われました。

*   **`adjustinfo`構造体への`sghi`フィールドの追加**:
    *   `adjustinfo`はスタック調整に関する情報（古いスタック、新しいスタック、ポインタの移動量など）を保持する構造体です。
    *   `sghi` (sudog highest) は、現在のGoroutineのスタック上で`sudog.elem`または`sudog.selectdone`が指す最も高いアドレス（スタックの底に近いアドレス）を記録します。この情報は、チャネルの送受信スロットを含む可能性のあるスタック領域を特定するために使用されます。

*   **`findsghi`関数の導入**:
    *   この関数は、与えられたGoroutine（`gp`）が待機している`sudog`リストを走査し、その`sudog`が指すスタック上の領域のうち、最も高いアドレス（`sghi`）を特定します。

*   **`syncadjustsudogs`関数の導入**:
    *   この関数は、`gp`の`sudog`を調整し、それらが参照するスタックの一部をコピーする際に、並行するチャネル操作と同期を取ります。
    *   具体的には、`gp`が待機している全てのチャネルのロックを取得し、`adjustsudogs`を呼び出して`sudog`内のポインタを調整します。
    *   その後、`sghi`で特定されたスタック領域を`memmove`で新しいスタック位置にコピーし、最後にチャネルのロックを解放します。

*   **`copystack`関数のシグネチャ変更と内部ロジックの修正**:
    *   `copystack`関数は、Goroutineのスタックを新しいサイズのスタックにコピーする主要な関数です。
    *   シグネチャに`sync bool`引数が追加されました。`sync`が`true`の場合（スタック拡大時など、自己トリガーされるスタックコピーで、他のGoroutineがスタックに書き込む可能性がない場合）、従来の`adjustsudogs`が直接呼び出されます。
    *   `sync`が`false`の場合（スタック縮小時など、並行チャネル操作から保護する必要がある場合）、`findsghi`と`syncadjustsudogs`が呼び出され、並行安全な方法で`sudog`の調整とスタック領域のコピーが行われます。

*   **`adjustpointers`関数でのアトミックCASの導入**:
    *   スタック上のポインタを調整する`adjustpointers`関数内で、`useCAS`フラグが導入されました。
    *   `useCAS`は、現在のスタックフレームが`sghi`（チャネルの送受信スロットを含む可能性のある領域）よりも低いアドレスにある場合に`true`になります。
    *   `useCAS`が`true`の場合、ポインタの調整は`atomic.Casp1`を使用して行われます。これにより、ポインタの読み取りと書き込みがアトミックに実行され、並行するチャネル操作との競合が回避されます。

これらの変更により、`shrinkstack`はSTWなしで実行できるようになったため、Goランタイムはより柔軟かつ効率的にメモリを管理できるようになります。

## コアとなるコードの変更箇所

### `src/runtime/chan_test.go`

`TestSelectStackAdjust`という新しいテストケースが追加されました。このテストは、チャネルの受信スロットに含まれるローカルスタックポインタが、スタック縮小によって正しく調整されることを検証します。Goroutineを起動し、意図的にスタックを成長させた後、`select`文でチャネル受信を待機させます。その間にGCを強制的に実行し、スタック縮小をトリガーします。最終的に、受信スロット内のポインタが正しく調整されているかを確認します。

```go
// Test that channel receive slots that contain local stack
// pointers are adjusted correctly by stack shrinking.
func TestSelectStackAdjust(t *testing.T) {
	c := make(chan *int)
	d := make(chan *int)
	ready := make(chan bool)
	go func() {
		// Temporarily grow the stack to 10K.
		stackGrowthRecursive((10 << 10) / (128 * 8))

		// We're ready to trigger GC and stack shrink.
		ready <- true

		val := 42
		var cx *int
		cx = &val
		// Receive from d. cx won't be affected.
		select {
		case cx = <-c:
		case <-d:
		}

		// Check that pointer in cx was adjusted correctly.
		if cx != &val {
			t.Error("cx no longer points to val")
		} else if val != 42 {
			t.Error("val changed")
		} else {
			*cx = 43
			if val != 43 {
				t.Error("changing *cx failed to change val")
			}
		}
		ready <- true
	}()

	// Let the goroutine get into the select.
	<-ready
	time.Sleep(10 * time.Millisecond)

	// Force concurrent GC a few times.
	var before, after runtime.MemStats
	runtime.ReadMemStats(&before)
	for i := 0; i < 100; i++ {
		selectSink = new([1 << 20]byte)
		runtime.ReadMemStats(&after)
		if after.NumGC-before.NumGC >= 2 {
			goto done
		}
	}
	t.Fatal("failed to trigger concurrent GC")
done:
	selectSink = nil

	// Wake select.
	d <- nil
	<-ready
}
```

### `src/runtime/stack.go`

このファイルには、`shrinkstack`の並行安全性を実現するための最も重要な変更が含まれています。

1.  **`adjustinfo`構造体への`sghi`フィールドの追加**:
    `adjustinfo`はスタック調整のコンテキストを保持します。`sghi`は、スタック上の`sudog.elem`または`sudog.selectdone`が指す最も高いアドレス（スタックの底に近い）を記録するために使用されます。

    ```go
    type adjustinfo struct {
    	old   stack
    	delta uintptr // ptr distance from old to new stack (newbase - oldbase)
    	cache pcvalueCache

    	// sghi is the highest sudog.elem on the stack.
    	sghi uintptr
    }
    ```

2.  **`adjustpointers`関数でのアトミックCASの導入**:
    この関数はスタック上のポインタを調整します。チャネルの受信スロットを含む可能性のあるスタック領域（`useCAS`が`true`の場合）では、`atomic.Casp1`を使用してポインタの調整が行われます。これにより、並行する送信操作との競合を防ぎます。

    ```go
    func adjustpointers(scanp unsafe.Pointer, cbv *bitvector, adjinfo *adjustinfo, f *_func) {
    	// ...
    	useCAS := uintptr(scanp) < adjinfo.sghi // sghiより低いアドレスならCASを使用
    	for i := uintptr(0); i < num; i++ {
    		if ptrbit(&bv, i) == 1 {
    			pp := (*uintptr)(add(scanp, i*sys.PtrSize))
    		retry: // CASが失敗した場合に再試行
    			p := *pp
    			// ... (ポインタが有効かどうかのチェック)
    			if p >= adjinfo.old.lo && p < adjinfo.old.hi {
    				// ...
    				if useCAS {
    					ppu := (*unsafe.Pointer)(unsafe.Pointer(pp))
    					if !atomic.Casp1(ppu, unsafe.Pointer(p), unsafe.Pointer(p+delta)) {
    						goto retry // CAS失敗、再試行
    					}
    				} else {
    					*pp = p + delta // 通常のポインタ調整
    				}
    			}
    		}
    	}
    }
    ```

3.  **`findsghi`関数の追加**:
    Goroutineが待機している`sudog`リストを走査し、スタック上の`sudog.elem`または`sudog.selectdone`が指す最も高いアドレスを返します。

    ```go
    func findsghi(gp *g, stk stack) uintptr {
    	var sghi uintptr
    	for sg := gp.waiting; sg != nil; sg = sg.waitlink {
    		p := uintptr(sg.elem) + uintptr(sg.c.elemsize)
    		if stk.lo <= p && p < stk.hi && p > sghi {
    			sghi = p
    		}
    		p = uintptr(unsafe.Pointer(sg.selectdone)) + unsafe.Sizeof(sg.selectdone)
    		if stk.lo <= p && p < stk.hi && p > sghi {
    			sghi = p
    		}
    	}
    	return sghi
    }
    ```

4.  **`syncadjustsudogs`関数の追加**:
    `sudog`の調整と、それらが参照するスタック領域のコピーを、チャネルロックを使用して並行安全に行います。

    ```go
    func syncadjustsudogs(gp *g, used uintptr, adjinfo *adjustinfo) uintptr {
    	if gp.waiting == nil {
    		return 0
    	}

    	// Lock channels to prevent concurrent send/receive.
    	for sg := gp.waiting; sg != nil; sg = sg.waitlink {
    		lock(&sg.c.lock)
    	}

    	// Adjust sudogs.
    	adjustsudogs(gp, adjinfo)

    	// Copy the part of the stack the sudogs point in to
    	// while holding the lock to prevent races on
    	// send/receive slots.
    	var sgsize uintptr
    	if adjinfo.sghi != 0 {
    		oldBot := adjinfo.old.hi - used
    		newBot := oldBot + adjinfo.delta
    		sgsize = adjinfo.sghi - oldBot
    		memmove(unsafe.Pointer(newBot), unsafe.Pointer(oldBot), sgsize)
    	}

    	// Unlock channels.
    	for sg := gp.waiting; sg != nil; sg = sg.waitlink {
    		unlock(&sg.c.lock)
    	}

    	return sgsize
    }
    ```

5.  **`copystack`関数の修正**:
    `copystack`のシグネチャに`sync bool`引数が追加され、スタックコピーのモードが切り替えられます。`sync`が`false`の場合（`shrinkstack`からの呼び出し）、`findsghi`と`syncadjustsudogs`が使用され、並行安全な処理が実行されます。

    ```go
    func copystack(gp *g, newsize uintptr, sync bool) {
    	// ...
    	if sync {
    		adjustsudogs(gp, &adjinfo)
    	} else {
    		// sudogs can point in to the stack. During concurrent
    		// shrinking, these areas may be written to. Find the
    		// highest such pointer so we can handle everything
    		// there and below carefully.
    		adjinfo.sghi = findsghi(gp, old)

    		// Synchronize with channel ops and copy the part of
    		// the stack they may interact with.
    		ncopy -= syncadjustsudogs(gp, used, &adjinfo)
    	}

    	// Copy the stack (or the rest of it) to the new location
    	memmove(unsafe.Pointer(new.hi-ncopy), unsafe.Pointer(old.hi-ncopy), ncopy)
    	// ...
    }
    ```

6.  **`newstack`と`shrinkstack`からの`copystack`呼び出しの変更**:
    `newstack`（スタック拡大）からは`copystack(gp, uintptr(newsize), true)`が、`shrinkstack`（スタック縮小）からは`copystack(gp, newsize, false)`が呼び出されるようになりました。これにより、それぞれのシナリオに応じた適切な並行安全処理が適用されます。

## コアとなるコードの解説

このコミットの主要な目的は、`shrinkstack`関数がSTWなしで安全に実行できるようにすることです。これを実現するために、スタック上のポインタ、特にチャネルに関連するポインタの調整方法が根本的に変更されました。

### `adjustpointers`におけるアトミックCAS

`adjustpointers`関数は、スタックが移動した際に、古いスタック上のポインタを新しいスタック上の対応する位置に更新する役割を担います。このコミットでは、この関数に`useCAS`というフラグが導入されました。

```go
useCAS := uintptr(scanp) < adjinfo.sghi
```

この行は、現在スキャンしているスタック領域（`scanp`）が、`adjinfo.sghi`（`sudog`が指すスタック上の最も高いアドレス）よりも低いアドレスにあるかどうかをチェックします。もしそうであれば、その領域にはチャネルの送受信スロットが含まれている可能性があり、並行するチャネル操作によってデータが書き込まれる競合状態が発生するリスクがあります。

このような競合を防ぐために、ポインタの調整には`atomic.Casp1`（CompareAndSwapPointer）が使用されます。

```go
if useCAS {
    ppu := (*unsafe.Pointer)(unsafe.Pointer(pp))
    if !atomic.Casp1(ppu, unsafe.Pointer(p), unsafe.Pointer(p+delta)) {
        goto retry
    }
} else {
    *pp = p + delta
}
```

*   `atomic.Casp1(ppu, unsafe.Pointer(p), unsafe.Pointer(p+delta))`は、`pp`が指すポインタの値が`p`（古い値）と等しい場合にのみ、その値を`p+delta`（新しい値）にアトミックに更新します。
*   もし`p`の値が`atomic.Casp1`の実行中に他のGoroutineによって変更されていた場合（例えば、並行する送信操作が受信スロットに値を書き込んだ場合）、`atomic.Casp1`は`false`を返します。この場合、`goto retry`によって処理が再試行され、最新のポインタ値に基づいて再度調整が試みられます。
*   `useCAS`が`false`の場合、つまりチャネルの送受信スロットを含まない安全な領域では、通常のポインタ代入`*pp = p + delta`が使用されます。

このアトミックCASの導入により、`shrinkstack`が実行されている最中でも、チャネル操作がスタック上の送受信スロットに安全にアクセスできるようになり、データ破壊のリスクが排除されます。

### `findsghi`と`syncadjustsudogs`によるチャネル同期

`shrinkstack`がSTWなしで実行される場合、Goroutineがチャネルでブロックされている間にそのスタックが縮小される可能性があります。このとき、`sudog`構造体はスタック上の領域を指しているため、スタックの移動に伴って`sudog`内のポインタも更新される必要があります。同時に、`sudog`が指すスタック領域自体も、並行するチャネル操作によって読み書きされる可能性があるため、保護が必要です。

`findsghi`関数は、`gp`が待機している`sudog`リストを走査し、`sudog.elem`（送受信される値が格納されるスロット）や`sudog.selectdone`（`select`文の完了フラグ）が指すスタック上の最も高いアドレス（スタックの底に近いアドレス）を特定します。この`sghi`は、チャネル関連のデータが存在するスタック領域の境界を示します。

`syncadjustsudogs`関数は、この`sghi`情報とチャネルロックを組み合わせて、並行安全な`sudog`調整とスタックコピーを実行します。

1.  **チャネルロックの取得**: `gp`が待機している全てのチャネルのロックを、`for sg := gp.waiting; sg != nil; sg = sg.waitlink { lock(&sg.c.lock) }`によって取得します。これにより、このGoroutineに関連するチャネル操作が一時的に停止し、スタック上のデータへの競合アクセスが防止されます。
2.  **`sudog`の調整**: `adjustsudogs(gp, adjinfo)`を呼び出し、`sudog`内のポインタを新しいスタックアドレスに更新します。
3.  **スタック領域のコピー**: `adjinfo.sghi != 0`の場合、`sghi`で特定されたスタック領域（チャネルの送受信スロットなど）を、`memmove`を使って古いスタックから新しいスタックへコピーします。このコピーはチャネルロックが保持されている間に行われるため、データの一貫性が保証されます。
4.  **チャネルロックの解放**: 処理が完了した後、取得した全てのチャネルロックを解放します。

この一連の処理により、`shrinkstack`はSTWなしで実行されても、チャネル操作との間でデータ競合を起こすことなく、`sudog`と関連するスタック領域を安全に移動・調整できるようになります。

## 変更の背景

Goランタイムの`shrinkstack`関数は、Goroutineのスタックが過剰に大きくなった場合にそのサイズを縮小し、メモリを効率的に利用するための重要な機能です。しかし、この機能はこれまでSTW（Stop The World）フェーズ中、つまり全てのGoroutineが一時停止している間にのみ安全に実行可能でした。その主な理由は、`shrinkstack`がチャネルに関連するスタックポインタや送受信スロットを調整・移動する際に、チャネルコードとの同期が取れていなかったためです。

STWはガベージコレクション（GC）の重要なフェーズであり、その間はアプリケーションの実行が完全に停止するため、レイテンシの原因となります。GoランタイムはSTWの時間を最小限に抑える努力を継続しており、`shrinkstack`のような処理をSTW外で安全に実行できるようにすることは、GCの効率化と全体的なアプリケーションパフォーマンスの向上に不可欠でした。

このコミットは、Issue #12967で報告された問題に対応し、`shrinkstack`がSTWなしで並行的に安全に動作できるようにすることで、Goランタイムのより効率的な運用を目指しています。これにより、GCのSTW時間がさらに短縮され、アプリケーションの応答性が向上することが期待されます。

## 前提知識の解説

### Goランタイムのスタック管理

GoのGoroutineは、非常に軽量な実行単位であり、それぞれが独自のスタックを持っています。Goランタイムは、必要に応じてスタックを動的に拡大（stack growth）および縮小（stack shrinking）させることで、メモリ効率を最適化しています。

*   **スタックの拡大**: Goroutineが関数呼び出しを深く行うなどしてスタック領域が不足しそうになると、ランタイムはより大きな新しいスタックを割り当て、古いスタックの内容を新しいスタックにコピーします。
*   **スタックの縮小**: Goroutineがスタックをあまり使用しなくなった場合（例えば、深い関数呼び出しから戻った後）、ランタイムはスタックを縮小してメモリを解放します。この`shrinkstack`処理が本コミットの主題です。

スタックの拡大・縮小時には、スタック上に存在するポインタ（ローカル変数、引数、戻り値など）が新しいスタックアドレスを指すように調整される必要があります。このポインタ調整は、Goの正確なGCにとって極めて重要です。

### GoのGoroutine

GoroutineはGoの並行処理の根幹をなすもので、OSのスレッドよりもはるかに軽量です。数百万のGoroutineを同時に実行することも可能です。GoroutineはGoランタイムによってスケジューリングされ、複数のOSスレッド上で多重化されて実行されます。これにより、高い並行性を低オーバーヘッドで実現しています。

### Goのチャネルと`sudog`構造体

チャネルは、Goroutine間で値を安全に送受信するためのGoの主要な同期プリミティブです。チャネル操作（送信または受信）がブロックされる場合（例: バッファなしチャネルへの送信、空のチャネルからの受信）、Goroutineは一時停止し、`sudog`（"semaphore user goroutine" の略）という内部ランタイム構造体が使用されます。

*   **`sudog`**: `sudog`は、チャネルなどの同期プリミティブで待機しているGoroutineを表します。チャネルの内部には、送信待ちのGoroutineキュー（`sendq`）と受信待ちのGoroutineキュー（`recvq`）があり、これらのキューは`sudog`のリストとして管理されます。`sudog`には、待機しているGoroutineへのポインタや、チャネル操作に関連するスタック上のスロット（送受信される値が一時的に格納される場所）へのポインタが含まれることがあります。これらのスタック上のスロットは、スタックが移動する際に正しく調整される必要があります。

### STW (Stop The World)

STWは、ガベージコレクション（GC）の特定のフェーズで、Goランタイムが全てのGoroutineの実行を一時的に停止させる期間を指します。これにより、GCはメモリの状態が変化しないことを保証し、安全にオブジェクトをスキャンしたり移動したりできます。STWはGCの正確性を保証するために不可欠ですが、アプリケーションの応答性を低下させるため、GoランタイムはSTWの時間を短縮するよう継続的に最適化されています。このコミットは、STWの外部で`shrinkstack`を安全に実行可能にすることで、STW時間のさらなる短縮に貢献します。

### アトミック操作 (Atomic Operations)

アトミック操作は、複数のCPUコアやGoroutineから同時にアクセスされても、その操作全体が不可分（atomic）に実行されることを保証する低レベルの操作です。これにより、競合状態（race condition）を防ぎ、ロックを使用せずに共有データへの安全なアクセスを実現できます。Goでは`sync/atomic`パッケージを通じてアトミック操作が提供されており、本コミットでは`atomic.Casp1`（`CompareAndSwapPointer`に相当）が使用されています。これは、ポインタの値をアトミックに比較し、一致した場合にのみ新しい値に交換する操作です。この操作は、並行アクセス下でのポインタの安全な更新に不可欠です。

### ポインタ調整 (Pointer Adjustment)

スタックが移動する際、古いスタック上のアドレスを指していたポインタは、新しいスタック上の対応するアドレスを指すように更新される必要があります。このプロセスをポインタ調整と呼びます。Goランタイムは、GC情報（スタックマップ）を利用して、スタック上のどの位置にポインタが存在するかを識別し、それらを正確に調整します。この調整が不正確だと、プログラムが不正なメモリを参照し、クラッシュやデータ破損を引き起こす可能性があります。

## 技術的詳細

このコミットの核心は、`shrinkstack`がSTWなしで安全に実行できるようにすることです。これまでの`shrinkstack`は、チャネルの送受信スロットや`sudog`が指すスタック上の領域を、チャネルコードとの同期なしに移動させていました。これは、Goroutineがチャネル操作でブロックされている間にスタックが縮小されると、チャネルコードが古い（無効な）スタックアドレスを参照したり、スタック上のデータが破壊されたりする可能性があったため、STW中のみ安全でした。

変更は主に以下の2つのメカニズムによって並行安全性を実現しています。

1.  **チャネルロックによる同期**:
    *   スタックを縮小するGoroutine（`gp`）がブロックしている可能性のある全てのチャネル（`gp.waiting`リストにある`sudog`が指すチャネル）に対して、`shrinkstack`はチャネルのロックを取得します。
    *   このロックは、`sudog`の調整と、送受信スロットを含む可能性のあるスタック領域のコピー中に保持されます。これにより、チャネル操作とスタック縮小処理の間で競合が発生するのを防ぎます。
    *   コミットメッセージでは、より粒度の細かい同期（例: `sudog`ごとに同期）も検討されたが、チャネルロックを使用することでチャネルコードに追加のロックが不要になり、またロック保持時間が非常に短い（スタック縮小時間全体に比べて）ため、このアプローチが採用されたと説明されています。この設計判断は、実装の複雑さを抑えつつ、十分なパフォーマンスを確保するためのものです。

2.  **アトミックCASによるポインタ調整**:
    *   スタックフレーム内でチャネルの送受信スロットを含む可能性のあるポインタを調整する際、`atomic.Casp1`（CompareAndSwapPointer）が使用されます。
    *   これは、受信スロット内のポインタを調整する処理と、並行して実行される送信操作がその受信スロットに書き込む処理との間の競合を防ぐためです。`atomic.Casp1`を使用することで、ポインタが期待される古い値を保持している場合にのみ新しい値に更新され、そうでなければ再試行されるため、データの一貫性が保たれます。これにより、ロックを使用せずに特定のメモリ位置を安全に更新することが可能になります。

これらの変更を実装するために、以下の具体的なコード変更が行われました。

*   **`adjustinfo`構造体への`sghi`フィールドの追加**:
    *   `adjustinfo`はスタック調整に関する情報（古いスタック、新しいスタック、ポインタの移動量など）を保持する構造体です。
    *   `sghi` (sudog highest) は、現在のGoroutineのスタック上で`sudog.elem`または`sudog.selectdone`が指す最も高いアドレス（スタックの底に近いアドレス）を記録します。この情報は、チャネルの送受信スロットを含む可能性のあるスタック領域を特定するために使用されます。この領域は、並行アクセスに対して特別な注意が必要なため、`sghi`はその境界を定義します。

*   **`findsghi`関数の導入**:
    *   この関数は、与えられたGoroutine（`gp`）が待機している`sudog`リストを走査し、その`sudog`が指すスタック上の領域のうち、最も高いアドレス（`sghi`）を特定します。これは、`sudog`がスタック上のどこにデータを保持しているかを正確に把握するために必要です。

*   **`syncadjustsudogs`関数の導入**:
    *   この関数は、`gp`の`sudog`を調整し、それらが参照するスタックの一部をコピーする際に、並行するチャネル操作と同期を取ります。
    *   具体的には、`gp`が待機している全てのチャネルのロックを取得し、`adjustsudogs`を呼び出して`sudog`内のポインタを調整します。
    *   その後、`sghi`で特定されたスタック領域を`memmove`で新しいスタック位置にコピーし、最後にチャネルのロックを解放します。このプロセス全体がチャネルロックによって保護されるため、`sudog`関連のデータが安全に移動されます。

*   **`copystack`関数のシグネチャ変更と内部ロジックの修正**:
    *   `copystack`関数は、Goroutineのスタックを新しいサイズのスタックにコピーする主要な関数です。
    *   シグネチャに`sync bool`引数が追加されました。`sync`が`true`の場合（スタック拡大時など、自己トリガーされるスタックコピーで、他のGoroutineがスタックに書き込む可能性がない場合）、従来の`adjustsudogs`が直接呼び出されます。
    *   `sync`が`false`の場合（`shrinkstack`からの呼び出しなど、並行チャネル操作から保護する必要がある場合）、`findsghi`と`syncadjustsudogs`が呼び出され、並行安全な方法で`sudog`の調整とスタック領域のコピーが行われます。この分岐により、スタックコピーのコンテキストに応じて最適な同期戦略が適用されます。

*   **`adjustpointers`関数でのアトミックCASの導入**:
    *   スタック上のポインタを調整する`adjustpointers`関数内で、`useCAS`フラグが導入されました。
    *   `useCAS`は、現在のスタックフレームが`sghi`（チャネルの送受信スロットを含む可能性のある領域）よりも低いアドレスにある場合に`true`になります。
    *   `useCAS`が`true`の場合、ポインタの調整は`atomic.Casp1`を使用して行われます。これにより、ポインタの読み取りと書き込みがアトミックに実行され、並行するチャネル操作との競合が回避されます。

これらの変更により、`shrinkstack`はSTWなしで実行できるようになったため、Goランタイムはより柔軟かつ効率的にメモリを管理できるようになります。これは、Goアプリケーションの全体的なパフォーマンスと応答性の向上に寄与します。

### `src/runtime/chan_test.go`

`TestSelectStackAdjust`という新しいテストケースが追加されました。このテストは、チャネルの受信スロットに含まれるローカルスタックポインタが、スタック縮小によって正しく調整されることを検証します。Goroutineを起動し、意図的にスタックを成長させた後、`select`文でチャネル受信を待機させます。その間にGCを強制的に実行し、スタック縮小をトリガーします。最終的に、受信スロット内のポインタが正しく調整されているかを確認することで、このコミットで導入された変更の正当性を保証します。

```go
// Test that channel receive slots that contain local stack
// pointers are adjusted correctly by stack shrinking.
func TestSelectStackAdjust(t *testing.T) {
	c := make(chan *int)
	d := make(chan *int)
	ready := make(chan bool)
	go func() {
		// Temporarily grow the stack to 10K.
		stackGrowthRecursive((10 << 10) / (128 * 8))

		// We're ready to trigger GC and stack shrink.
		ready <- true

		val := 42
		var cx *int
		cx = &val
		// Receive from d. cx won't be affected.
		select {
		case cx = <-c:
		case <-d:
		}

		// Check that pointer in cx was adjusted correctly.
		if cx != &val {
			t.Error("cx no longer points to val")
		} else if val != 42 {
			t.Error("val changed")
		} else {
			*cx = 43
			if val != 43 {
				t.Error("changing *cx failed to change val")
			}
		}
		ready <- true
	}()

	// Let the goroutine get into the select.
	<-ready
	time.Sleep(10 * time.Millisecond)

	// Force concurrent GC a few times.
	var before, after runtime.MemStats
	runtime.ReadMemStats(&before)
	for i := 0; i < 100; i++ {
		selectSink = new([1 << 20]byte)
		runtime.ReadMemStats(&after)
		if after.NumGC-before.NumGC >= 2 {
			goto done
		}
	}
	t.Fatal("failed to trigger concurrent GC")
done:
	selectSink = nil

	// Wake select.
	d <- nil
	<-ready
}
```

### `src/runtime/stack.go`

このファイルには、`shrinkstack`の並行安全性を実現するための最も重要な変更が含まれています。

1.  **`adjustinfo`構造体への`sghi`フィールドの追加**:
    `adjustinfo`はスタック調整のコンテキストを保持します。`sghi`は、スタック上の`sudog.elem`または`sudog.selectdone`が指す最も高いアドレス（スタックの底に近い）を記録するために使用されます。この情報は、チャネルの送受信スロットを含む可能性のあるスタック領域を特定し、その領域に対して特別な同期処理を適用するために不可欠です。

    ```go
    type adjustinfo struct {
    	old   stack
    	delta uintptr // ptr distance from old to new stack (newbase - oldbase)
    	cache pcvalueCache

    	// sghi is the highest sudog.elem on the stack.
    	sghi uintptr
    }
    ```

2.  **`adjustpointers`関数でのアトミックCASの導入**:
    この関数はスタック上のポインタを調整します。チャネルの受信スロットを含む可能性のあるスタック領域（`useCAS`が`true`の場合）では、`atomic.Casp1`を使用してポインタの調整が行われます。これにより、並行する送信操作との競合を防ぎます。

    ```go
    func adjustpointers(scanp unsafe.Pointer, cbv *bitvector, adjinfo *adjustinfo, f *_func) {
    	// ...
    	// If this frame might contain channel receive slots, use CAS
    	// to adjust pointers. If the slot hasn't been received into
    	// yet, it may contain stack pointers and a concurrent send
    	// could race with adjusting those pointers. (The sent value
    	// itself can never contain stack pointers.)
    	useCAS := uintptr(scanp) < adjinfo.sghi // sghiより低いアドレスならCASを使用
    	for i := uintptr(0); i < num; i++ {
    		if ptrbit(&bv, i) == 1 {
    			pp := (*uintptr)(add(scanp, i*sys.PtrSize))
    		retry: // CASが失敗した場合に再試行
    			p := *pp
    			// ... (ポインタが有効かどうかのチェック)
    			if p >= adjinfo.old.lo && p < adjinfo.old.hi {
    				// ...
    				if useCAS {
    					ppu := (*unsafe.Pointer)(unsafe.Pointer(pp))
    					if !atomic.Casp1(ppu, unsafe.Pointer(p), unsafe.Pointer(p+delta)) {
    						goto retry // CAS失敗、再試行
    					}
    				} else {
    					*pp = p + delta // 通常のポインタ調整
    				}
    			}
    		}
    	}
    }
    ```

3.  **`findsghi`関数の追加**:
    Goroutineが待機している`sudog`リストを走査し、スタック上の`sudog.elem`または`sudog.selectdone`が指す最も高いアドレスを返します。この関数は、`syncadjustsudogs`が保護すべきスタック領域を正確に特定するために使用されます。

    ```go
    func findsghi(gp *g, stk stack) uintptr {
    	var sghi uintptr
    	for sg := gp.waiting; sg != nil; sg = sg.waitlink {
    		p := uintptr(sg.elem) + uintptr(sg.c.elemsize)
    		if stk.lo <= p && p < stk.hi && p > sghi {
    			sghi = p
    		}
    		p = uintptr(unsafe.Pointer(sg.selectdone)) + unsafe.Sizeof(sg.selectdone)
    		if stk.lo <= p && p < stk.hi && p > sghi {
    			sghi = p
    		}
    	}
    	return sghi
    }
    ```

4.  **`syncadjustsudogs`関数の追加**:
    `sudog`の調整と、それらが参照するスタック領域のコピーを、チャネルロックを使用して並行安全に行います。

    ```go
    // syncadjustsudogs adjusts gp's sudogs and copies the part of gp's
    // stack they refer to while synchronizing with concurrent channel
    // operations. It returns the number of bytes of stack copied.
    func syncadjustsudogs(gp *g, used uintptr, adjinfo *adjustinfo) uintptr {
    	if gp.waiting == nil {
    		return 0
    	}

    	// Lock channels to prevent concurrent send/receive.
    	// It's important that we *only* do this for async
    	// copystack; otherwise, gp may be in the middle of
    	// putting itself on wait queues and this would
    	// self-deadlock.
    	for sg := gp.waiting; sg != nil; sg = sg.waitlink {
    		lock(&sg.c.lock)
    	}

    	// Adjust sudogs.
    	adjustsudogs(gp, adjinfo)

    	// Copy the part of the stack the sudogs point in to
    	// while holding the lock to prevent races on
    	// send/receive slots.
    	var sgsize uintptr
    	if adjinfo.sghi != 0 {
    		oldBot := adjinfo.old.hi - used
    		newBot := oldBot + adjinfo.delta
    		sgsize = adjinfo.sghi - oldBot
    		memmove(unsafe.Pointer(newBot), unsafe.Pointer(oldBot), sgsize)
    	}

    	// Unlock channels.
    	for sg := gp.waiting; sg != nil; sg = sg.waitlink {
    		unlock(&sg.c.lock)
    	}

    	return sgsize
    }
    ```

5.  **`copystack`関数の修正**:
    `copystack`のシグネチャに`sync bool`引数が追加され、スタックコピーのモードが切り替えられます。`sync`が`false`の場合（`shrinkstack`からの呼び出し）、`findsghi`と`syncadjustsudogs`が使用され、並行安全な処理が実行されます。

    ```go
    // Copies gp's stack to a new stack of a different size.
    // Caller must have changed gp status to Gcopystack.
    //
    // If sync is true, this is a self-triggered stack growth and, in
    // particular, no other G may be writing to gp's stack (e.g., via a
    // channel operation). If sync is false, copystack protects against
    // concurrent channel operations.
    func copystack(gp *g, newsize uintptr, sync bool) {
    	if gp.syscallsp != 0 {
    		throw("stack growth not allowed in system call")
    	}
    	// ...
    	adjinfo.old = old
    	adjinfo.delta = new.hi - old.hi

    	// Adjust sudogs, synchronizing with channel ops if necessary.
    	ncopy := used
    	if sync {
    		adjustsudogs(gp, &adjinfo)
    	} else {
    		// sudogs can point in to the stack. During concurrent
    		// shrinking, these areas may be written to. Find the
    		// highest such pointer so we can handle everything
    		// there and below carefully. (This shouldn't be far
    		// from the bottom of the stack, so there's little
    		// cost in handling everything below it carefully.)
    		adjinfo.sghi = findsghi(gp, old)

    		// Synchronize with channel ops and copy the part of
    		// the stack they may interact with.
    		ncopy -= syncadjustsudogs(gp, used, &adjinfo)
    	}

    	// Copy the stack (or the rest of it) to the new location
    	memmove(unsafe.Pointer(new.hi-ncopy), unsafe.Pointer(old.hi-ncopy), ncopy)

    	// Disallow sigprof scans of this stack and block if there's
    	// one in progress.
    	gcLockStackBarriers(gp)

    	// Adjust remaining structures that have pointers into stacks.
    	// We have to do most of these before we traceback the new
    	// stack because gentraceback uses them.
    	adjustctxt(gp, &adjinfo)
    	adjustdefers(gp, &adjinfo)
    	adjustpanics(gp, &adjinfo)
    	// adjustsudogs(gp, &adjinfo) // Moved into syncadjustsudogs or conditional
    	adjuststkbar(gp, &adjinfo)
    	if adjinfo.sghi != 0 {
    		adjinfo.sghi += adjinfo.delta
    	}

    	// copy old stack barriers to new stack barrier array
    	newstkbar = newstkbar[:len(gp.stkbar)]
    	// ...
    }
    ```

6.  **`newstack`と`shrinkstack`からの`copystack`呼び出しの変更**:
    `newstack`（スタック拡大）からは`copystack(gp, uintptr(newsize), true)`が、`shrinkstack`（スタック縮小）からは`copystack(gp, newsize, false)`が呼び出されるようになりました。これにより、それぞれのシナリオに応じた適切な並行安全処理が適用され、スタック拡大時はオーバーヘッドを最小限に抑え、スタック縮小時は並行安全性を確保します。

## コアとなるコードの解説

このコミットの主要な目的は、`shrinkstack`関数がSTWなしで安全に実行できるようにすることです。これを実現するために、スタック上のポインタ、特にチャネルに関連するポインタの調整方法が根本的に変更されました。

### `adjustpointers`におけるアトミックCAS

`adjustpointers`関数は、スタックが移動した際に、古いスタック上のポインタを新しいスタック上の対応する位置に更新する役割を担います。このコミットでは、この関数に`useCAS`というフラグが導入されました。

```go
useCAS := uintptr(scanp) < adjinfo.sghi
```

この行は、現在スキャンしているスタック領域（`scanp`）が、`adjinfo.sghi`（`sudog`が指すスタック上の最も高いアドレス）よりも低いアドレスにあるかどうかをチェックします。もしそうであれば、その領域にはチャネルの送受信スロットが含まれている可能性があり、並行するチャネル操作によってデータが書き込まれる競合状態が発生するリスクがあります。

このような競合を防ぐために、ポインタの調整には`atomic.Casp1`（CompareAndSwapPointer）が使用されます。

```go
if useCAS {
    ppu := (*unsafe.Pointer)(unsafe.Pointer(pp))
    if !atomic.Casp1(ppu, unsafe.Pointer(p), unsafe.Pointer(p+delta)) {
        goto retry
    }
} else {
    *pp = p + delta
}
```

*   `atomic.Casp1(ppu, unsafe.Pointer(p), unsafe.Pointer(p+delta))`は、`pp`が指すポインタの値が`p`（古い値）と等しい場合にのみ、その値を`p+delta`（新しい値）にアトミックに更新します。
*   もし`p`の値が`atomic.Casp1`の実行中に他のGoroutineによって変更されていた場合（例えば、並行する送信操作が受信スロットに値を書き込んだ場合）、`atomic.Casp1`は`false`を返します。この場合、`goto retry`によって処理が再試行され、最新のポインタ値に基づいて再度調整が試みられます。
*   `useCAS`が`false`の場合、つまりチャネルの送受信スロットを含まない安全な領域では、通常のポインタ代入`*pp = p + delta`が使用されます。

このアトミックCASの導入により、`shrinkstack`が実行されている最中でも、チャネル操作がスタック上の送受信スロットに安全にアクセスできるようになり、データ破壊のリスクが排除されます。これは、ロックによる排他制御よりも粒度が細かく、パフォーマンスへの影響を最小限に抑えることができます。

### `findsghi`と`syncadjustsudogs`によるチャネル同期

`shrinkstack`がSTWなしで実行される場合、Goroutineがチャネルでブロックされている間にそのスタックが縮小される可能性があります。このとき、`sudog`構造体はスタック上の領域を指しているため、スタックの移動に伴って`sudog`内のポインタも更新される必要があります。同時に、`sudog`が指すスタック領域自体も、並行するチャネル操作によって読み書きされる可能性があるため、保護が必要です。

`findsghi`関数は、`gp`が待機している`sudog`リストを走査し、`sudog.elem`（送受信される値が格納されるスロット）や`sudog.selectdone`（`select`文の完了フラグ）が指すスタック上の最も高いアドレス（スタックの底に近いアドレス）を特定します。この`sghi`は、チャネル関連のデータが存在するスタック領域の境界を示します。

`syncadjustsudogs`関数は、この`sghi`情報とチャネルロックを組み合わせて、並行安全な`sudog`調整とスタックコピーを実行します。

1.  **チャネルロックの取得**: `gp`が待機している全てのチャネルのロックを、`for sg := gp.waiting; sg != nil; sg = sg.waitlink { lock(&sg.c.lock) }`によって取得します。これにより、このGoroutineに関連するチャネル操作が一時的に停止し、スタック上のデータへの競合アクセスが防止されます。
2.  **`sudog`の調整**: `adjustsudogs(gp, adjinfo)`を呼び出し、`sudog`内のポインタを新しいスタックアドレスに更新します。この調整は、チャネルロックが保持されている間に行われるため、安全です。
3.  **スタック領域のコピー**: `adjinfo.sghi != 0`の場合、`sghi`で特定されたスタック領域（チャネルの送受信スロットなど）を、`memmove`を使って古いスタックから新しいスタックへコピーします。このコピーもチャネルロックが保持されている間に行われるため、データの一貫性が保証されます。
4.  **チャネルロックの解放**: 処理が完了した後、取得した全てのチャネルロックを解放します。

この一連の処理により、`shrinkstack`はSTWなしで実行されても、チャネル操作との間でデータ競合を起こすことなく、`sudog`と関連するスタック領域を安全に移動・調整できるようになります。これにより、Goランタイムはより効率的にメモリを管理し、GCのSTW時間を短縮することが可能になります。

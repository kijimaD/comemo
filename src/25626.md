# [インデックス 25626] ファイルの概要

`src/cmd/go/vcs.go` は、Go言語のコマンドラインツール `go` が、バージョン管理システム (VCS) と連携して動作するためのロジックを定義しているファイルです。特に、Gitリポジトリのクローン、更新、タグ付けといった操作に関連するコマンドの構築と実行を担当しています。このファイルは、`go get` コマンドが外部のGoパッケージを取得する際に、どのようにGitリポジトリを扱うかを制御する中心的な役割を担っています。

## コミット

このコミット `b619d5573e4ed02780018cad845a941f2a1c374e` は、以前に導入された「`cmd/go: use shallow clones for new git checkouts`」というコミット `bc1f9d20b40998b87c9a5f56f2b22595de65c2d4` を元に戻す（リバートする）ものです。これにより、`go get` コマンドがGitリポジトリをクローンする際の挙動が、シャロークローンを使用しない以前の状態に戻されました。

## 元コミット内容

リバートされたコミット `bc1f9d20b40998b87c9a5f56f2b22595de65c2d4` は、`go get` コマンドがGitリポジトリを新しくチェックアウトする際に、デフォルトでシャロークローン（`--depth=1` オプション付きの `git clone`）を使用するように変更しました。この変更の意図は、リポジトリの全履歴をダウンロードする代わりに最新のコミットのみを取得することで、ネットワーク帯域とディスク容量を節約し、`go get` の実行速度を向上させることにありました。

## 変更の背景

シャロークローンの導入はパフォーマンス向上を目的としていましたが、以下の2つの主要な問題を引き起こしたため、このコミットで元に戻されることになりました。

1.  **サーバー互換性の問題**: 一部のGitサーバーは、シャロークローンリクエストを適切に処理できない場合がありました。これにより、`go get` が特定の環境やリポジトリで失敗する原因となりました。
2.  **`go get -u` の不具合**: 既にシャローではない（通常の）クローンで取得されたリポジトリに対して `go get -u`（更新コマンド）を実行した場合に、正しく動作しないという問題が発生しました。シャロークローンとフルクローンの間でGitの内部状態に差異があるため、更新処理が複雑になり、予期せぬエラーや不整合が生じました。

これらの問題は、GoのIssueトラッカーで #13213 と #13206 として報告されており、このリバートコミットによってこれらの問題が修正されました。

## 前提知識の解説

*   **`go get` コマンド**: Go言語の公式ツールチェーンの一部であり、指定されたGoパッケージとその依存関係をダウンロードし、インストールするために使用されます。通常、ソースコードは `$GOPATH/src` ディレクトリに配置されます。
*   **Git シャロークローン (`--depth=1`)**: `git clone --depth=1 <repository> <directory>` コマンドは、指定されたリポジトリの全履歴ではなく、最新のコミット（または指定された深さのコミット）のみをクローンします。これにより、ダウンロードサイズが大幅に削減され、クローン時間が短縮されます。しかし、完全な履歴情報が失われるため、過去のコミットへのアクセスやブランチの切り替えなど、一部のGit操作に制約が生じます。
*   **`git pull --ff-only`**: `git pull` はリモートリポジトリから変更を取得し、現在のブランチに統合するコマンドです。`--ff-only` オプションは、ファストフォワードマージ（現在のブランチがリモートブランチの直接の祖先である場合に行われる、履歴を直線的に進めるマージ）のみを許可します。もし履歴が分岐している場合（つまり、ローカルでコミットがあり、リモートにも新しいコミットがある場合）、このコマンドは失敗し、マージコミットの作成を強制しません。
*   **`git submodule update --init --recursive`**: Gitサブモジュールは、別のGitリポジトリを親リポジトリのサブディレクトリとして埋め込む機能です。このコマンドは、サブモジュールを初期化（`--init`）し、そのサブモジュール内のサブモジュールも再帰的に（`--recursive`）更新します。

## 技術的詳細

シャロークローンを `go get` に導入した際の技術的な問題点は以下の通りです。

*   **Gitプロトコルの多様性**: Gitサーバーの実装は多岐にわたり、すべてのサーバーがシャロークローンリクエストを同じように、あるいは全くサポートしているわけではありませんでした。特に、古いGitサーバーや、特定のプロキシ設定、あるいは非標準的なGitホスティングサービスでは、`--depth` オプション付きの `clone` コマンドが失敗するケースが報告されました。これは、`go get` がGoエコシステム全体のパッケージを確実に取得できるという基本的な期待に反するものでした。
*   **`go get -u` の複雑性**: `go get -u` は、既にローカルに存在するパッケージを最新の状態に更新するために使用されます。シャロークローンで取得されたリポジトリは、完全な履歴を持たないため、通常の `git pull` 操作が期待通りに機能しないことがありました。例えば、シャロークローンされたリポジトリに対して `git pull` を実行すると、完全な履歴がないためにマージ戦略が複雑になったり、エラーが発生したりする可能性がありました。特に、`--depth=1` でクローンされたリポジトリを `git pull` で更新しようとすると、Gitは完全な履歴を必要とする操作を実行しようとして失敗することがあります。このため、`go get -u` が既存のシャローではないリポジトリとシャローリポジトリの両方で一貫して動作するようにすることは、実装上の大きな課題となりました。
*   **開発者のワークフローへの影響**: `go get` は単にパッケージを取得するだけでなく、開発者がそのパッケージのソースコードをローカルで参照したり、デバッグしたり、場合によっては変更を加えたりすることも想定されます。シャロークローンでは履歴が限定されるため、過去のコミットの調査や、特定のブランチへの切り替えといった開発者の一般的なGitワークフローが妨げられる可能性がありました。`go get` の目的はシンプルにパッケージを取得することですが、その結果として生成されるローカルリポジトリが開発者の期待するGitリポジトリとしての完全性を持たないことは、ユーザーエクスペリエンスの低下につながりました。

これらの問題は、シャロークローンによるパフォーマンス上の利点よりも、機能的な安定性と互換性の問題が上回ると判断され、元の挙動に戻す決定がなされました。

## コアとなるコードの解説

変更は `vcsGit` 構造体内の `createCmd` と `downloadCmd` の定義に集中しています。

*   **`createCmd` の変更**:
    *   変更前: `[]string{"clone --depth=1 {repo} {dir}", ...}`
    *   変更後: `[]string{"clone {repo} {dir}", ...}`
    *   この変更により、新しいGitリポジトリを `go get` でクローンする際に、`--depth=1` オプションが削除されました。結果として、シャロークローンではなく、リポジトリの完全な履歴を含むフルクローンが行われるようになりました。これにより、サーバー互換性の問題が解消され、ローカルに完全なGitリポジトリが作成されるため、開発者のGit操作の自由度も確保されます。

*   **`downloadCmd` の変更**:
    *   変更前: `[]string{"pull --depth=1 --ff-only", ...}`
    *   変更後: `[]string{"pull --ff-only", ...}`
    *   この変更により、既存のGitリポジトリを `go get -u` で更新する際に、`pull` コマンドから `--depth=1` オプションが削除されました。シャロークローンされたリポジトリに対する `pull --depth=1` は、完全な履歴がないために問題を引き起こす可能性がありましたが、このオプションの削除により、通常の `git pull --ff-only` が実行されるようになりました。これにより、`go get -u` がシャローではないリポジトリと一貫して動作し、更新時の不具合が解消されました。

これらの変更は、シャロークローンによるパフォーマンス上のわずかな利点よりも、`go get` コマンドの堅牢性、互換性、および開発者のワークフローとの整合性を優先するというGoプロジェクトの判断を反映しています。

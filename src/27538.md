# [インデックス 27538] ファイルの概要

このコミットは、Goの`net/http`パッケージにおいて、クライアント側（`http.Transport`）がサーバーから受信するレスポンスヘッダーの最大サイズを制限する機能を追加します。これにより、悪意のあるサーバーからの巨大なヘッダーによるリソース枯渇攻撃（DoS攻撃）を防ぎ、システムの堅牢性を向上させます。

## コミット

このコミットは、`net/http`パッケージの`Transport`に、サーバーからのレスポンスヘッダーの読み取りバイト数に制限を設ける変更を導入します。デフォルトの制限はHTTP/2と同様に10MBですが、新しく追加された`http.Transport.MaxResponseHeaderBytes`フィールドを通じて設定可能です。この変更は、Issue #9115を解決します。

## 変更の背景

この変更が導入される前は、Goの`net/http.Transport`は、サーバーから受信するレスポンスヘッダーのサイズを制限するメカニズムを持っていませんでした。この制限がないことは、潜在的な脆弱性につながる可能性がありました。悪意のある、または誤って設定されたサーバーが、非常に大きなHTTPレスポンスヘッダーを送信した場合、クライアント側のメモリを過剰に消費させ、リソース枯渇やサービス拒否（DoS）攻撃を引き起こす可能性があります。

Issue #9115は、おそらくこのような問題、つまり巨大なレスポンスヘッダーによって引き起こされるクライアント側の脆弱性やリソース消費の問題を報告していたと考えられます。このコミットは、GoのHTTPクライアントが、HTTP/2プロトコルが持つ`MaxHeaderListSize`のようなヘッダーサイズ制限の概念を取り入れることで、より堅牢で安全な動作を保証することを目的としています。これにより、クライアントは予期せぬ大量のデータから保護され、安定した動作を維持できるようになります。

## 前提知識の解説

### `net/http.Transport`

Go言語の`net/http`パッケージにおける`Transport`は、HTTPクライアントがネットワーク接続を確立し、リクエストを送信し、レスポンスを受信する際の低レベルな詳細を管理する構造体です。これには、TCP接続の確立、TLSハンドシェイク、HTTPリクエストのワイヤフォーマットへの変換、レスポンスの解析、そしてコネクションプーリング（接続の再利用）などが含まれます。通常、`http.Client`は内部的に`Transport`を利用して実際のネットワーク通信を行います。

### HTTPヘッダー

HTTP（Hypertext Transfer Protocol）通信において、ヘッダーはリクエストまたはレスポンスの本体（ボディ）に関するメタデータを提供するキーと値のペアの集合です。例えば、`Content-Type`はボディのメディアタイプを示し、`Authorization`は認証情報を含み、`Cache-Control`はキャッシュの動作を指示します。ヘッダーは通信の挙動を制御し、クライアントとサーバー間で重要な情報を交換するために不可欠です。

### HTTP/2 `MaxHeaderListSize`

HTTP/2プロトコルでは、`SETTINGS_MAX_HEADER_LIST_SIZE`という設定パラメータが定義されています。これは、通信の相手方（クライアントまたはサーバー）が、受信するヘッダーリストの最大サイズ（オクテット単位）をアドバイザリとして通知するものです。このサイズは、非圧縮のヘッダーフィールド名と値の合計長に、各ヘッダーフィールドごとに32オクテットのオーバーヘッドを加算して計算されます。この設定の主な目的は、巨大なヘッダーブロックによるリソース枯渇攻撃（DoS攻撃）を防ぐことです。この制限を超過するヘッダーリストを受信した場合、受信側はストリームを閉じるなどの対応を取ることができます。

### リソース枯渇攻撃 (Resource Exhaustion Attack) / サービス拒否攻撃 (Denial of Service - DoS)

リソース枯渇攻撃とは、攻撃者がシステムのメモリ、CPU、ネットワーク帯域幅などのリソースを過剰に消費させることで、正当なユーザーがサービスを利用できなくする攻撃手法です。HTTP通信の文脈では、非常に大きなHTTPヘッダーを送信することで、クライアントやサーバーがそのヘッダーを処理するために大量のメモリを割り当てざるを得なくなり、結果としてシステムが応答不能になる可能性があります。このコミットは、クライアント側がこのような攻撃から自身を保護するための防御策を導入しています。

## 技術的詳細

このコミットは、`net/http`パッケージの`Transport`に`MaxResponseHeaderBytes`という新しいフィールドを導入することで、レスポンスヘッダーの最大サイズ制限を実装しています。

1.  **`MaxResponseHeaderBytes`フィールドの導入**:
    *   `http.Transport`構造体に`MaxResponseHeaderBytes int64`フィールドが追加されました。
    *   このフィールドがゼロの場合、デフォルトの制限（10MB）が使用されます。
    *   ゼロ以外の値が設定された場合、その値がレスポンスヘッダーの最大許容バイト数として機能します。

2.  **デフォルト値とHTTP/2との連携**:
    *   `MaxResponseHeaderBytes`が明示的に設定されていない場合、デフォルトで10MB（`10 << 20`バイト）の制限が適用されます。これは、HTTP/2プロトコルにおけるヘッダーリストの一般的な制限値と一致させることで、一貫性と堅牢性を高めています。
    *   `Transport`がHTTP/2をサポートするように設定されている場合（`onceSetNextProtoDefaults`関数内）、`MaxResponseHeaderBytes`の値は`http2.Transport`の`MaxHeaderListSize`に自動的に反映されます。これにより、HTTP/1とHTTP/2の両方で同様のヘッダーサイズ制限が適用されるようになります。

3.  **`persistConn`における読み取り制限の実装**:
    *   `persistConn`構造体（`Transport`が管理する永続的な接続を表す）に`readLimit int64`フィールドが追加されました。このフィールドは、現在の接続で読み取りが許可されている残りのバイト数を追跡します。
    *   `persistConn`は`io.Reader`インターフェースを実装するようになり、その`Read`メソッド内で`readLimit`をチェックし、制限を超えないようにバイト数を調整します。
    *   `readLoop`内で、レスポンスヘッダーを読み取る前に`readLimit`が`MaxResponseHeaderBytes`（またはデフォルトの10MB）で初期化されます。ヘッダーの読み取りが完了すると、ボディの読み取りには制限をかけないように`readLimit`は`maxInt64`（実質的に無限）にリセットされます。
    *   もしヘッダーの読み取り中に`readLimit`がゼロ以下になった場合、`"net/http: server response headers exceeded %d bytes; aborted"`というエラーが返され、接続が中断されます。

4.  **`maxInt64`定数の導入**:
    *   `src/net/http/http.go`に`const maxInt64 = 1<<63 - 1`が追加されました。これは`int64`の最大値を表し、実質的に「無限」の読み取り制限として使用されます。これにより、ボディの読み取り時にはヘッダーサイズ制限が適用されないようにします。

これらの変更により、GoのHTTPクライアントは、サーバーからのレスポンスヘッダーのサイズを効果的に制御し、潜在的なリソース枯渇攻撃から自身を保護できるようになりました。

3.  **`src/net/http/transport.go`**:
    *   `Transport`構造体に`MaxResponseHeaderBytes int64`フィールドが追加されました。

    *   `noteEOFReader`というヘルパー型が削除され、その機能が`persistConn`の`Read`メソッドに統合されました。
    *   `dialConn`関数内で、`bufio.NewReader`の引数が`noteEOFReader`から`pconn`自体に変更されました。

## コアとなるコードの解説

このコミットの核心は、`http.Transport`がサーバーからのレスポンスヘッダーを読み取る際に、そのサイズを動的に制限するメカニズムを導入した点にあります。

### `maxInt64` 定数

`src/net/http/http.go`で定義された`const maxInt64 = 1<<63 - 1`は、Goの`int64`型が表現できる最大値です。この値は、読み取り制限を実質的に無効にする、つまり「無限」の制限として機能させるために使用されます。例えば、レスポンスボディの読み取り時には、ヘッダーサイズ制限を適用する必要がないため、`readLimit`が`maxInt64`に設定されます。

### `persistConn` の `Read` メソッド

最も重要な変更の一つは、`src/net/http/transport.go`内の`persistConn`構造体が`io.Reader`インターフェースを実装し、その`Read`メソッドがオーバーライドされたことです。

```go
func (pc *persistConn) Read(p []byte) (n int, err error) {
    if pc.readLimit <= 0 {
        return 0, fmt.Errorf("read limit of %d bytes exhausted", pc.maxHeaderResponseSize())
    }
    if int64(len(p)) > pc.readLimit {
        p = p[:pc.readLimit]
    }
    n, err = pc.conn.Read(p)
    if err == io.EOF {
        pc.sawEOF = true
    }
    pc.readLimit -= int64(n)
    return
}
```

この`Read`メソッドは、基となる`net.Conn`の`Read`を呼び出す前に、`pc.readLimit`（現在の読み取り許容残量）をチェックします。
*   `pc.readLimit <= 0`の場合、読み取り制限を超過したと判断し、エラーを返します。
*   読み取ろうとしているバイト数（`len(p)`）が`pc.readLimit`を超える場合、`p`スライスを`pc.readLimit`のサイズに切り詰めて、制限を超えないようにします。
*   実際に読み取ったバイト数`n`だけ`pc.readLimit`をデクリメントします。

これにより、`bufio.Reader`が`persistConn`を介してデータを読み取る際、ヘッダーのバイト数が`MaxResponseHeaderBytes`で設定された制限を超えないように強制されます。

### `readLoop` 内での `readLimit` の管理

`persistConn`の`readLoop()`ゴルーチンは、接続からのデータの読み取りを管理します。このループ内で、`readLimit`は以下のように管理されます。

```go
// ...
for alive {
    pc.readLimit = pc.maxHeaderResponseSize() // ヘッダー読み取り前に制限を設定
    _, err := pc.br.Peek(1) // ヘッダーの開始を待つ
    // ...
    if err != nil {
        if pc.readLimit <= 0 {
            err = fmt.Errorf("net/http: server response headers exceeded %d bytes; aborted", pc.maxHeaderResponseSize())
        }
        // ...
        return
    }
    pc.readLimit = maxInt64 // ヘッダー読み取り後、ボディには制限をかけない
    // ...
}
```

*   **ヘッダー読み取り前の初期化**: 各レスポンスのヘッダーを読み取る直前に、`pc.readLimit`は`pc.maxHeaderResponseSize()`（`MaxResponseHeaderBytes`またはデフォルトの10MB）で初期化されます。これにより、`bufio.Reader`がヘッダーを読み取る際に、この制限が適用されます。
*   **制限超過時のエラー**: `Peek(1)`やその後のヘッダー解析中にエラーが発生し、かつ`pc.readLimit <= 0`である場合、明示的に「サーバーレスポンスヘッダーが制限を超過した」というエラーメッセージが生成されます。
*   **ボディ読み取り時のリセット**: ヘッダーの読み取りが成功し、レスポンスボディの読み取りに移る前に、`pc.readLimit`は`maxInt64`にリセットされます。これは、レスポンスボディのサイズには通常、クライアント側で明示的な制限を設けないためです。

### `noteEOFReader` の削除

以前は、`persistConn`の`sawEOF`フラグを管理するために`noteEOFReader`というヘルパー型が使用されていましたが、このコミットで削除されました。代わりに、`persistConn`自体が`io.Reader`を実装し、その`Read`メソッド内で`io.EOF`を検出して`pc.sawEOF`を更新するように変更されました。これにより、コードが簡素化され、`sawEOF`の管理が`persistConn`内に統合されました。

これらの変更により、GoのHTTPクライアントは、巨大なレスポンスヘッダーに対する防御機構を獲得し、より堅牢なネットワーク通信を実現しています。

# [インデックス 28114] ファイルの概要

このコミットは、Go言語の `compress/flate` パッケージにおける「Best Speed」圧縮レベルの実装を、GoogleのSnappy圧縮ライブラリにインスパイアされたLZ77スタイルのエンコーダに置き換えるものです。これにより、圧縮速度が大幅に向上する一方で、出力サイズは若干増加するというトレードオフがあります。この変更は、特に速度を重視するアプリケーションにおいて、Goの標準ライブラリの圧縮性能を向上させることを目的としています。

## 変更の背景

Go言語の `compress/flate` パッケージは、DEFLATE圧縮アルゴリズムを実装しており、様々な圧縮レベルを提供しています。その中でも「Best Speed」レベルは、圧縮率よりも速度を優先する設定です。しかし、既存の「Best Speed」の実装は、特に高速な圧縮が求められるシナリオにおいて、その性能が最適ではないという課題がありました。

このコミットの背景には、Go 1.7の機能フリーズが迫る中で、Goの標準ライブラリにおける圧縮性能を向上させたいという強い要望がありました。特に、Googleが開発したSnappy圧縮ライブラリは、非常に高速な圧縮と合理的な圧縮率で知られており、そのLZ77スタイルのエンコーダは、速度を重視する圧縮アルゴリズムの優れた例とされていました。

コミットメッセージに示されているベンチマーク結果は、この変更の動機を明確に裏付けています。例えば、`EncodeDigitsSpeed1e6-8` のベンチマークでは、旧バージョンが32.1MB/sであったのに対し、新バージョンでは82.1MB/sと、約156%もの速度向上が見られます。他のベンチマークでも50%から130%以上の速度向上が報告されており、この変更がGoの圧縮性能に与える影響の大きさが伺えます。

一方で、この速度向上は出力サイズの増加と引き換えに達成されています。コミットメッセージの「Output size is larger」のセクションでは、様々なファイルで圧縮後のサイズが旧バージョンよりも大きくなっていることが示されています。これは、Snappyのような高速圧縮アルゴリズムが、より複雑なマッチング戦略やハフマン符号化の最適化を犠牲にして速度を優先する一般的なトレードオフです。

この変更は、Klaus Post氏による先行の変更提案 (cl/21021) に基づいていますが、その提案がコードレビューで停滞していたため、Go 1.7のリリースサイクルに合わせてNigel Tao氏が独立した変更として導入しました。これは、高速圧縮の必要性が非常に高かったことを示唆しています。

## 前提知識の解説

### DEFLATEアルゴリズム

DEFLATEは、可逆データ圧縮アルゴリズムであり、主にLZ77アルゴリズムとハフマン符号化の2つの段階を組み合わせています。

1.  **LZ77 (Lempel-Ziv 1977) アルゴリズム**:
    *   これは辞書ベースの圧縮アルゴリズムです。入力データストリーム内で繰り返されるバイトシーケンス（パターン）を検出し、それらを「長さ」と「距離」（または「オフセット」）のペアに置き換えます。
    *   「距離」は、現在の位置からどれだけ前に同じパターンが出現したかを示し、「長さ」はそのパターンの長さを表します。
    *   例えば、「ABCABCABC」というデータがあった場合、最初の「ABC」をリテラルとして出力し、次の「ABC」を「距離=3, 長さ=3」のような形で参照に置き換えることで圧縮します。
    *   LZ77は、特に繰り返しパターンが多いデータ（テキストファイルなど）で高い圧縮率を発揮します。

2.  **ハフマン符号化 (Huffman Coding)**:
    *   これはエントロピー符号化の一種で、データ内の各シンボル（バイトやLZ77の出力トークンなど）の出現頻度に基づいて、可変長のビット列を割り当てます。
    *   出現頻度の高いシンボルには短いビット列を、出現頻度の低いシンボルには長いビット列を割り当てることで、全体のデータサイズを削減します。
    *   DEFLATEでは、LZ77の出力（リテラルバイト、長さ/距離ペア）をさらにハフマン符号化することで、より高い圧縮率を実現します。

Goの `compress/flate` パッケージは、このDEFLATEアルゴリズムを実装しており、`flate.NewWriter` 関数で圧縮レベルを指定できます。

### Goの `compress/flate` パッケージと圧縮レベル

`compress/flate` パッケージは、Goにおける標準的なDEFLATE圧縮のインターフェースを提供します。`NewWriter` 関数に渡す圧縮レベルは、圧縮率と速度のトレードオフを制御します。

*   **`flate.NoCompression` (レベル0)**: 圧縮を行わず、データをそのまま出力します。
*   **`flate.BestSpeed` (レベル1)**: 圧縮速度を最優先します。このコミットで変更された対象です。通常、圧縮率は低くなります。
*   **`flate.DefaultCompression` (レベル-1)**: デフォルトの圧縮レベルで、速度と圧縮率のバランスが取れています（通常はレベル6に相当）。
*   **`flate.BestCompression` (レベル9)**: 最高の圧縮率を目指します。圧縮には最も時間がかかります。
*   **`flate.HuffmanOnly` (レベル-2)**: LZ77マッチングを行わず、ハフマン符号化のみを行います。これは、既にLZスタイルの圧縮が施されたデータに対して、さらにエントロピー符号化を適用する場合などに有用です。

### Snappy圧縮ライブラリ

Snappyは、Googleが開発した高速なデータ圧縮ライブラリです。その主な特徴は以下の通りです。

*   **速度優先**: Snappyは、最高の圧縮率を目指すのではなく、非常に高速な圧縮と解凍を目標としています。これは、CPUサイクルを節約し、I/O帯域幅を効率的に利用するために設計されています。
*   **LZ77スタイル**: Snappyも内部的にはLZ77に似たアルゴリズムを使用し、繰り返しパターンを検出して参照に置き換えます。しかし、DEFLATEのようにハフマン符号化を組み合わせることはせず、よりシンプルな符号化スキームを採用しています。
*   **用途**: 大量のデータを高速に転送または保存する必要があるが、最高の圧縮率が必須ではないシナリオ（例: データベースの内部圧縮、ログファイルの圧縮、ネットワーク通信）で広く利用されています。

このコミットは、`compress/flate` の `BestSpeed` 実装に、Snappyの「速度優先」という哲学と、その効率的なLZ77スタイルのエンコーダのアイデアを取り入れたものです。

## 技術的詳細

このコミットの核心は、`compress/flate` パッケージの `BestSpeed` 圧縮レベルの内部実装を、`github.com/golang/snappy` の `encodeBlock` 関数に触発された新しいアルゴリズムに置き換えたことです。これにより、Goの標準ライブラリにおける高速圧縮の性能が劇的に向上しました。

### 新しい「Best Speed」エンコーダの設計思想

新しいエンコーダは、Snappyと同様に、以下の原則に基づいています。

1.  **速度最優先**: 圧縮率を犠牲にしてでも、エンコード速度を最大化します。
2.  **LZ77ベース**: 入力データ内の繰り返しパターンを検出するために、ハッシュテーブルを用いたLZ77スタイルのマッチング戦略を採用します。
3.  **シンプルな出力形式**: DEFLATEの完全なハフマン符号化を適用するのではなく、よりシンプルなトークン（リテラルバイト、長さ/距離ペア）の表現を使用し、必要に応じてハフマン符号化を適用するハイブリッドなアプローチを取ります。

### 性能と出力サイズのトレードオフ

コミットメッセージに示されているベンチマーク結果は、このトレードオフを明確に示しています。

*   **速度向上**: 多くのテストケースで、エンコード速度が50%から150%以上向上しています。これは、特に大量のデータを高速に圧縮する必要があるアプリケーションにとって非常に大きなメリットです。
*   **出力サイズ増加**: 速度向上の代償として、圧縮後の出力サイズは旧バージョンと比較して平均的に5%から30%程度増加しています。これは、より積極的なマッチング戦略や、ハフマン符号化の最適化を一部緩和した結果と考えられます。

### Snappyの `encodeBlock` との比較

コミットメッセージには、新しい `encodeBestSpeed` 関数とSnappyの `encodeBlock` 関数の差分が詳細に記載されています。この差分は、Goの `compress/flate` の文脈にSnappyのロジックを適応させるための変更点を示しています。

主な変更点としては、以下の点が挙げられます。

*   **関数シグネチャの変更**: `encodeBlock(dst, src []byte) (d int)` から `encodeBestSpeed(dst []token, src []byte) []token` へと変更されています。これは、`flate` パッケージが内部的に `token` 型のスライスを使用して圧縮データを表現するためです。
*   **最小非リテラルブロックサイズのチェック**: `encodeBestSpeed` では、`minNonLiteralBlockSize` よりも入力サイズが小さい場合にリテラルとして処理する早期リターンが追加されています。これは、Snappyでは呼び出し元がこのケースを処理するため、`flate` 側で追加されたものです。
*   **`maxOffset` の考慮**: DEFLATEの仕様では、参照できるオフセット（距離）に `maxOffset` という制限があります。Snappyのオリジナル実装にはないこのチェックが、`if s-candidate < maxOffset && load32(src, s) == load32(src, candidate)` のように追加されています。これにより、DEFLATEの制約内で有効なマッチのみが考慮されます。
*   **マッチ長拡張の最適化**: マッチ長を延長するループにおいて、`s1 := base + maxMatchLength` と `if s1 > len(src) { s1 = len(src) }` のような境界チェックが追加され、`len(src)` ではなく `s1` を上限としてループすることで、より効率的かつ安全にマッチ長を拡張しています。
*   **トークン生成**: Snappyの `emitCopy` に相当する処理が、`flate` の `matchToken` を使用するように変更されています。`dst = append(dst, matchToken(uint32(s-base-3), uint32(base-candidate-minOffsetSize)))` のように、`token` スライスに直接追加する形式になっています。
*   **ハッシュ計算の最適化**: `load64` を使用して一度に8バイトを読み込み、シフト演算で複数のハッシュ値を計算する最適化が導入されています。これにより、複数の `load32` 呼び出しよりも高速になります。
*   **ヒューリスティックなマッチスキップ**: Snappyから採用された重要な最適化の一つです。これは、32バイトをスキャンしてもマッチが見つからない場合、次のスキャンでスキップするバイト数を増やす（例えば、2バイトおき、3バイトおきにスキャンする）という戦略です。これにより、非圧縮データ（JPEGなど）に対しては、マッチを探す無駄な処理を減らし、大幅な性能向上を実現します。マッチが見つかれば、すぐに全バイトをスキャンするモードに戻ります。

### `deflatefast.go` の導入

このコミットでは、新しい `encodeBestSpeed` 関数とそのヘルパー関数（`load32`, `load64`, `hash`, `emitLiteral`）を格納するために、`src/compress/flate/deflatefast.go` という新しいファイルが導入されました。これにより、高速圧縮ロジックが既存の `deflate.go` から分離され、コードのモジュール性が向上しています。

## コアとなるコードの解説

`src/compress/flate/deflatefast.go` に追加された `encodeBestSpeed` 関数が、このコミットの最も重要な部分です。この関数は、入力バイトスライス `src` を受け取り、圧縮されたトークンのスライス `dst` を返します。

### `encodeBestSpeed` 関数の主要なロジック

1.  **初期チェック**:
    *   `if len(src) < minNonLiteralBlockSize`: 入力サイズが非常に小さい場合、圧縮せずにリテラルとしてそのまま出力します。これはSnappyにはない、`flate` 固有の早期リターンです。

2.  **ハッシュテーブルの初期化**:
    *   `var table [maxTableSize]uint16`: マッチを高速に検索するためのハッシュテーブルを宣言します。テーブルサイズは入力サイズに応じて `1<<8` から `1<<14` の間で動的に決定されます。
    *   `shift := uint32(32 - 8)`: ハッシュ関数で使用するシフト値を計算します。

3.  **メインループ**:
    *   `sLimit := len(src) - inputMargin`: マッチ検索を停止する境界を設定します。`inputMargin` は、`emitLiteral` の高速パスを可能にするためのマージンです。
    *   `nextEmit := 0`: 次にリテラルとして出力すべきデータの開始位置を追跡します。
    *   `s := 1`, `nextHash := hash(load32(src, s), shift)`: 最初のマッチ検索を開始する位置とハッシュ値を初期化します。

4.  **ヒューリスティックなマッチスキップ**:
    *   `skip := 32`: この変数は、マッチが見つからない場合にスキャンをスキップするバイト数を制御します。
    *   `bytesBetweenHashLookups := skip >> 5`: 32バイトごとにスキップ量を増やします。これにより、非圧縮データに対する無駄なマッチ検索を減らし、性能を向上させます。
    *   `candidate = int(table[nextHash&tableMask])`: 現在のハッシュ値に対応する以前のマッチ候補をハッシュテーブルから取得します。
    *   `table[nextHash&tableMask] = uint16(s)`: 現在の位置 `s` をハッシュテーブルに記録します。
    *   `if s-candidate < maxOffset && load32(src, s) == load32(src, candidate)`: 4バイトのマッチが見つかったかどうかをチェックします。`maxOffset` のチェックはDEFLATEの制約を考慮したものです。

5.  **リテラルの出力**:
    *   `dst = emitLiteral(dst, src[nextEmit:s])`: マッチが見つかるまでの間のデータ（リテラル）をトークンとして出力します。

6.  **マッチの出力と延長**:
    *   `base := s`: マッチの開始位置を記録します。
    *   マッチ長を延長するループ: `for i := candidate + 4; s < s1 && src[i] == src[s]; i, s = i+1, s+1`
        *   `s1 := base + maxMatchLength`: マッチ長を延長する最大長を制限します。
        *   `src[i] == src[s]` でバイトを比較し、マッチが続く限り `s` をインクリメントしてマッチ長を延長します。
    *   `dst = append(dst, matchToken(uint32(s-base-3), uint32(base-candidate-minOffsetSize)))`: 延長されたマッチに基づいて、長さと距離を含む `matchToken` を生成し、`dst` スライスに追加します。

7.  **次のマッチ検索の準備**:
    *   `x := load64(src, s-1)`: `s-1` から8バイトを読み込みます。
    *   `prevHash := hash(uint32(x>>0), shift)`, `currHash := hash(uint32(x>>8), shift)`: 読み込んだ8バイトから複数のハッシュ値を効率的に計算します。
    *   ハッシュテーブルを更新し、次のマッチ候補を検索します。

8.  **残りのデータの処理**:
    *   `emitRemainder`: メインループが終了した後、まだ処理されていない残りのデータがあれば、それをリテラルとして出力します。

この `encodeBestSpeed` 関数は、Snappyの高速なマッチング戦略をGoの `compress/flate` パッケージのフレームワークに適合させることで、大幅な速度向上を実現しています。特に、ハッシュテーブルの効率的な利用、ヒューリスティックなスキップ、そしてDEFLATEの制約（`maxOffset`）への対応が特徴です。

# [インデックス 21838] ファイルの概要

このコミットは、Goランタイムにおける文字列比較関数 `eqstring` のパフォーマンスを向上させるものです。具体的には、文字列の長さチェックがコンパイラによって事前に行われるようになったため、`eqstring` 関数内の冗長な長さチェックを削除し、実行時のオーバーヘッドを削減しています。

## 元コミット内容

Goランタイムの文字列比較関数 `eqstring` から、文字列の長さチェックを削除することで、その実行速度を向上させます。この変更は、コンパイラが `eqstring` を呼び出す前に既に文字列の長さが等しいことを保証するため、`eqstring` 内での長さチェックが冗長になるという前提に基づいています。ベンチマーク結果は、`6g` および `5g` コンパイラにおいて、文字列比較のパフォーマンスが改善されたことを示しています。

## 変更の背景

Go言語において、文字列の比較は頻繁に行われる操作です。`==` 演算子を用いた文字列の等価比較は、内部的にランタイムの `eqstring` 関数（またはそれに相当する低レベルな処理）によって行われます。

従来の `eqstring` の実装では、文字列の内容を比較する前に、まず両方の文字列の長さが等しいかどうかを確認していました。しかし、Goコンパイラは、`==` 演算子による文字列比較を処理する際に、`eqstring` を呼び出す前に既に文字列の長さが等しいことを確認する最適化を行うことが可能です。

このコミットの背景にあるのは、このコンパイラ側の最適化を活用し、ランタイム側の `eqstring` 関数から冗長な長さチェックを排除することで、文字列比較全体のパフォーマンスをさらに向上させるという目的です。これにより、CPUサイクルが無駄なく利用され、特に頻繁な文字列比較が行われるアプリケーションにおいて、わずかながらも全体的な実行速度の改善が期待されます。ベンチマーク結果が示すように、この変更は実際にパフォーマンスの向上をもたらしています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびシステムプログラミングに関する前提知識が必要です。

1.  **Go言語における文字列の表現**:
    *   Go言語の文字列は、内部的には「ポインタ」と「長さ（バイト数）」のペアとして表現されます。ポインタは文字列のバイト列が格納されているメモリ上のアドレスを指し、長さはそのバイト列のサイズを示します。
    *   Goの文字列はイミュータブル（不変）です。一度作成された文字列の内容は変更できません。

2.  **Go言語における文字列の比較 (`==` 演算子)**:
    *   Goで `s1 == s2` のように文字列を比較する場合、まず両者の長さが比較されます。長さが異なる場合、文字列は等しくないと判断され、即座に `false` が返されます。
    *   長さが等しい場合、次に文字列の内容（バイト列）がバイトごとに比較されます。この内容比較は、ランタイムの低レベルな関数（本コミットで言及されている `eqstring` など）によって行われます。

3.  **Goコンパイラ (`gc`)**:
    *   `gc` はGo言語の公式コンパイラです。Goのソースコードを機械語に変換する役割を担います。
    *   コンパイラは、コードの最適化も行います。例えば、本コミットのように、特定のランタイム関数を呼び出す前に、その関数が内部で重複して行うであろうチェックを事前に行うことで、ランタイム関数の処理を簡略化し、全体的なパフォーマンスを向上させることができます。

4.  **Goランタイム (`runtime`)**:
    *   Goランタイムは、Goプログラムの実行をサポートする低レベルなコードの集合体です。ガベージコレクション、スケジューリング、プリミティブな操作（文字列操作、メモリ管理など）といった機能を提供します。
    *   `eqstring` のような関数は、Go言語の組み込み操作を効率的に実行するために、ランタイムの一部としてアセンブリ言語で実装されることがあります。

5.  **アセンブリ言語**:
    *   アセンブリ言語は、特定のCPUアーキテクチャ（例: x86, ARM）の命令セットに直接対応する低レベルなプログラミング言語です。
    *   Goランタイムのパフォーマンスが重要な部分は、C言語やGo言語ではなく、アセンブリ言語で書かれることがあります。これにより、CPUの機能を最大限に活用し、極めて高速な実行を実現できます。本コミットでは、`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `asm_arm.s` といったファイルがこれに該当します。

6.  **ベンチマークの読み方**:
    *   `ns/op` (nanoseconds per operation): 1回の操作にかかる平均ナノ秒数を示します。この値が小さいほど高速です。
    *   `delta`: 変更前と変更後のパフォーマンスの差をパーセンテージで示します。負の値はパフォーマンスが向上したことを意味します。
    *   `BenchmarkCompareStringEqual`: 異なる内容だが長さが等しい文字列を比較するベンチマーク。
    *   `BenchmarkCompareStringIdentical`: 同じ内容で、かつメモリ上の同じオブジェクトを指す文字列を比較するベンチマーク。後者は通常、ポインタ比較だけで済むため非常に高速です。
    *   `6g` と `5g`: これらは古いGoコンパイラの名称です。`6g` はamd64アーキテクチャ向け、`5g` はarmアーキテクチャ向けのコンパイラを指していました。現在では `go build` コマンドがこれらを抽象化しています。

## 技術的詳細

このコミットの核心は、GoコンパイラとGoランタイムの間の責任分担の最適化にあります。

1.  **`eqstring` 関数の役割**:
    `eqstring` は、Go言語の文字列比較 `s1 == s2` において、両者の長さが既に等しいと判断された後に、実際のバイト列の内容比較を行うためのランタイム関数です。この関数は、パフォーマンスが非常に重要であるため、各CPUアーキテクチャ向けにアセンブリ言語で実装されています。

2.  **従来の `eqstring` の実装**:
    このコミット以前の `eqstring` は、呼び出された際に、引数として渡された2つの文字列の長さが本当に等しいかどうかのチェックを内部で再度行っていました。これは、コンパイラが常に長さチェックを事前に行うとは限らない、あるいはランタイム関数が単独で完全なロジックを持つべきだという設計思想に基づいていた可能性があります。

3.  **コンパイラによる事前長さチェックの導入**:
    このコミットでは、Goコンパイラ (`src/cmd/gc/walk.c`) が、文字列の等価比較 (`OEQ`) を処理する際に、`eqstring` を呼び出す前に明示的に `len(left) == len(right)` のチェックを行うように変更されました。このチェックが `true` の場合にのみ `eqstring` が呼び出されるようになります。
    具体的には、`walkexpr` 関数内で `n->etype == OEQ` (等価比較) の場合、`len(left) == len(right)` の条件と、`eqstring` の結果を `&&` (論理AND) で結合するコードが生成されるようになります。これにより、`eqstring` が呼び出される時点では、常に文字列の長さが等しいことが保証されます。

4.  **`eqstring` からの冗長な長さチェックの削除**:
    コンパイラが長さの等価性を保証するようになったため、`eqstring` 関数自体が内部で行っていた長さチェックは冗長になります。このコミットでは、`src/runtime/asm_386.s`, `src/runtime/asm_amd64.s`, `src/runtime/asm_amd64p32.s`, `src/runtime/asm_arm.s` の各アセンブリファイルから、以下の命令が削除されました。
    *   文字列の長さをレジスタにロードする命令 (`MOVL/MOVQ/MOVW s1len...`)
    *   両者の長さを比較する命令 (`CMPL/CMPQ/CMP R0, R1`)
    *   長さが異なる場合にジャンプする条件分岐命令 (`JNE/JMP/RET.NE different/noteq`)
    これらの命令の削除により、`eqstring` の実行パスが短縮され、CPUサイクルが節約されます。

5.  **パフォーマンスへの影響**:
    ベンチマーク結果は、この変更が実際にパフォーマンス向上に寄与したことを明確に示しています。
    *   `6g` (amd64) では、`BenchmarkCompareStringEqual` で約12.66%、`BenchmarkCompareStringIdentical` で約9.52%の高速化。
    *   `5g` (arm) では、`BenchmarkCompareStringEqual` で約2.52%、`BenchmarkCompareStringIdentical` で約11.12%の高速化。
    特に `BenchmarkCompareStringIdentical` の改善が大きいのは、`eqstring` が呼び出されるケース（ポインタが異なるが内容が同じ場合）において、冗長な長さチェックがなくなることの恩恵が大きいことを示唆しています。

この変更は、Goのコンパイラとランタイムが密接に連携し、低レベルな最適化を通じて言語全体のパフォーマンスを継続的に改善している典型的な例と言えます。

## コアとなるコードの変更箇所

このコミットでは、主に以下の5つのファイルが変更されています。

1.  `src/cmd/gc/walk.c`: Goコンパイラのコード生成フェーズの一部。文字列比較の最適化ロジックが追加されました。
2.  `src/runtime/asm_386.s`: 32ビットx86アーキテクチャ向けGoランタイムのアセンブリコード。`eqstring` から長さチェックが削除されました。
3.  `src/runtime/asm_amd64.s`: 64ビットx86 (AMD64) アーキテクチャ向けGoランタイムのアセンブリコード。`eqstring` から長さチェックが削除されました。
4.  `src/runtime/asm_amd64p32.s`: AMD64アーキテクチャ上で32ビットポインタを使用するモード向けGoランタイムのアセンブリコード。`eqstring` から長さチェックが削除されました。
5.  `src/runtime/asm_arm.s`: ARMアーキテクチャ向けGoランタイムのアセンブリコード。`eqstring` から長さチェックが削除されました。

## コアとなるコードの解説

### `src/cmd/gc/walk.c` の変更

このファイルでは、Goコンパイラが抽象構文木 (AST) を走査し、コードを生成する `walkexpr` 関数が変更されています。

```c
@@ -1273,6 +1273,7 @@ walkexpr(Node **np, NodeList **init)
 			conv(n->right, types[TSTRING]));
 
 			// quick check of len before full compare for == or !=
+			// eqstring assumes that the lengths are equal
 			if(n->etype == OEQ) {
 				// len(left) == len(right) && eqstring(left, right)
 				r = nod(OANDAND, nod(OEQ, nod(OLEN, n->left, N), nod(OLEN, n->right, N)), r);
```

*   `if(n->etype == OEQ)`: これは、現在のノード `n` が文字列の等価比較 (`==`) を表す場合に実行されるブロックです。
*   `// eqstring assumes that the lengths are equal`: 新しく追加されたコメントで、`eqstring` が呼び出される際には既に長さが等しいという前提が確立されたことを示しています。
*   `r = nod(OANDAND, nod(OEQ, nod(OLEN, n->left, N), nod(OLEN, n->right, N)), r);`: この行が最も重要な変更です。
    *   `nod(OLEN, n->left, N)`: 左辺の文字列の長さを取得するノードを生成します。
    *   `nod(OLEN, n->right, N)`: 右辺の文字列の長さを取得するノードを生成します。
    *   `nod(OEQ, ..., ...)`: これら2つの長さが等しいかどうかを比較するノード (`len(left) == len(right)`) を生成します。
    *   `nod(OANDAND, ..., r)`: 上記の長さ比較の結果と、元の `eqstring` の呼び出しを含む比較結果 (`r`) を論理AND (`&&`) で結合します。
    これにより、コンパイラは `eqstring` を呼び出す前に、必ず文字列の長さが等しいことを確認するコードを生成するようになります。長さが異なる場合は、`eqstring` は呼び出されずに `false` が返されます。

### `src/runtime/asm_386.s`, `src/runtime/asm_amd64.s`, `src/runtime/asm_amd64p32.s`, `src/runtime/asm_arm.s` の変更

これらのファイルは、各アーキテクチャ向けに `runtime·eqstring` 関数がアセンブリ言語で実装されている部分です。変更のパターンはどのアーキテクチャでも同様で、冗長になった長さチェックの命令が削除されています。

**例: `src/runtime/asm_386.s` の変更**

```asm
@@ -1298,26 +1298,22 @@ eq:
 	RET
 
 // eqstring tests whether two strings are equal.
+// The compiler guarantees that strings passed
+// to eqstring have equal length.
 // See runtime_test.go:eqstring_generic for
 // equivalent Go code.
 TEXT runtime·eqstring(SB),NOSPLIT,$0-17
-\tMOVL\ts1len+4(FP), AX
-\tMOVL\ts2len+12(FP), BX
-\tCMPL\tAX, BX
-\tJNE\tdifferent
 \tMOVL\ts1str+0(FP), SI
 \tMOVL\ts2str+8(FP), DI
 \tCMPL\tSI, DI
 \tJEQ\tsame
+\tMOVL\ts1len+4(FP), BX
 \tCALL\truntime·memeqbody(SB)
 \tMOVB\tAX, v+16(FP)\n \tRET
 same:
 	MOVB\t$1, v+16(FP)
 	RET
-different:
-\tMOVB\t$0, v+16(FP)
-\tRET
```

*   削除された行:
    *   `MOVL s1len+4(FP), AX`: 最初の文字列の長さを `AX` レジスタにロード。
    *   `MOVL s2len+12(FP), BX`: 2番目の文字列の長さを `BX` レジスタにロード。
    *   `CMPL AX, BX`: 両者の長さを比較。
    *   `JNE different`: 長さが異なる場合、`different` ラベルにジャンプ（そこで `0` を返して終了）。
    *   `different:` ラベルとその後の `MOVB $0, v+16(FP)` および `RET`。
*   追加された行:
    *   `// The compiler guarantees that strings passed // to eqstring have equal length.`: 新しいコメントで、コンパイラが長さを保証するという前提を明記。
    *   `MOVL s1len+4(FP), BX`: `runtime·memeqbody` を呼び出す前に、文字列の長さを `BX` レジスタにロードする行が残されています。これは `memeqbody` が文字列の長さを必要とするためです。しかし、このロードは比較のためではなく、`memeqbody` への引数として使用されます。

他のアーキテクチャのアセンブリファイルでも同様に、文字列の長さを比較し、異なる場合に早期終了するロジックが削除されています。これにより、`eqstring` は常に長さが等しい文字列を受け取ることを前提とし、直接内容比較のロジックに進むことができるようになり、実行効率が向上します。

## 元コミット内容

`archive/tar: terminate when reading malformed sparse files`

このコミットは、不正な形式のスパースファイルを読み込む際に処理を終了させるように変更します。
Issue #10968 を修正します。

## 変更の背景

Goの `archive/tar` パッケージは、TARアーカイブの読み書きをサポートしています。TARアーカイブは、複数のファイルを一つのファイルにまとめるための一般的な形式です。このパッケージは、特に大きなファイルでディスクスペースを節約するために使用される「スパースファイル」の処理もサポートしています。

スパースファイルは、ファイル内の連続するゼロバイトのブロック（「ホール」と呼ばれる）を実際にディスクに書き込まずに、その存在だけを記録することで、効率的なストレージを実現します。TARアーカイブでは、これらのホールの位置とサイズをメタデータとして記録し、読み取り時に適切に処理する必要があります。

しかし、このコミット以前の `archive/tar` パッケージの実装では、スパースファイルのメタデータ（特にオフセット情報）が不正な形式であった場合、`sparseFileReader` の `readHole` メソッドが無限ループに陥り、結果としてプログラムがハングアップする可能性がありました。具体的には、スパースファイルのオフセットがファイルの総サイズを超えているような不正なデータが与えられた場合に、この問題が発生しました。

Issue #10968 はこの問題を報告しており、このコミットはその修正を目的としています。修正の目的は、不正なスパースファイルデータに遭遇した際に、ハングアップするのではなく、明確なエラー（`io.ErrUnexpectedEOF`）を返して処理を終了させることです。

## 前提知識の解説

### TARフォーマットとスパースファイル

TAR (Tape ARchive) は、複数のファイルを単一のアーカイブファイルにまとめるためのファイルフォーマットです。各ファイルはヘッダとそれに続くデータブロックで構成されます。ヘッダにはファイル名、サイズ、パーミッションなどのメタデータが含まれます。

**スパースファイル (Sparse Files)** は、ファイル内に大量の連続するゼロバイトの領域（「ホール」または「スパース領域」と呼ばれる）がある場合に、その領域を実際にディスク上に割り当てずに、メタデータとして記録する特殊なファイルです。これにより、ディスクスペースを大幅に節約できます。例えば、巨大なデータベースファイルや仮想ディスクイメージなどで利用されます。TARフォーマットは、POSIX.1-2001標準でスパースファイルの表現をサポートしており、ヘッダ内にスパース領域のオフセットとサイズを記述する情報を含めることができます。

### Goの `archive/tar` パッケージ

Go言語の標準ライブラリ `archive/tar` パッケージは、TARアーカイブの作成と展開をプログラム的に行うための機能を提供します。`tar.Reader` はTARアーカイブを読み取るための構造体で、`Next()` メソッドで次のエントリ（ファイルまたはディレクトリ）のヘッダを読み込み、`Read()` メソッドでそのエントリのデータを読み取ります。

スパースファイルの場合、`tar.Reader` は内部的に `sparseFileReader` という特殊なリーダーを使用して、ホールのスキップとデータブロックの読み取りを適切に処理します。

### `io.Reader` インターフェースとエラーハンドリング

Go言語では、データの読み取りは `io.Reader` インターフェースを通じて抽象化されています。`Read(p []byte) (n int, err error)` メソッドを持ち、`p` に最大 `len(p)` バイトのデータを読み込み、読み込んだバイト数 `n` とエラー `err` を返します。

*   `io.EOF`: 読み取りストリームの終端に達したことを示すエラーです。これは正常な終了条件として扱われます。
*   `io.ErrUnexpectedEOF`: 予期せぬ形で読み取りストリームの終端に達したことを示すエラーです。例えば、期待されるデータ量に満たない状態でストリームが終了した場合などに使用されます。このエラーは、通常、データが破損しているか、プロトコル違反が発生したことを示唆します。

このコミットでは、不正なスパースファイルデータが `io.ErrUnexpectedEOF` として扱われることで、プログラムがハングアップせずに異常終了するようになります。

## 技術的詳細

このコミットの修正は、`src/archive/tar/reader.go` 内の `sparseFileReader` 構造体の `Read` メソッドに集中しています。

`sparseFileReader` は、スパースファイルのデータを効率的に読み取るための内部的なリーダーです。このリーダーは、スパースファイルの構造を記述する `sp` (sparse entries) スライスと、現在までに読み込んだバイト数を追跡する `tot` フィールド、現在の読み取り位置 `pos` を持っています。

`Read` メソッドのロジックは、以下のようになっています。

1.  **スパースエントリの処理**: `sfr.sp` には、スパースファイルのデータブロック（非ホール部分）のオフセットとサイズが格納されています。`Read` メソッドは、これらのエントリを順に処理し、現在の読み取り位置 `sfr.pos` が次のデータブロックの開始オフセット `sfr.sp[0].offset` に達するまで、ホール（ゼロバイト）を生成するか、実際のデータを読み込みます。
2.  **ホールの読み取り**: `sfr.pos < sfr.sp[0].offset` の場合、現在の位置はホール内にあります。`readHole` メソッドが呼び出され、指定されたバイト数までゼロバイトを生成して返します。
3.  **データの読み取り**: `sfr.pos >= sfr.sp[0].offset` の場合、現在の位置はデータブロック内にあります。`sfr.r.Read()` を呼び出して基になるリーダーから実際のデータを読み込みます。

**問題点**:
コミット前のコードでは、`sfr.sp[0].offset` が `sfr.tot` (これまでに読み込んだ総バイト数) よりも大きい、つまり、ファイル全体のサイズを超えたオフセットがスパースエントリとして指定されているような不正なケースが考慮されていませんでした。このような状況では、`sfr.pos` が `sfr.sp[0].offset` に到達することがなく、`readHole` メソッドが無限にゼロバイトを生成しようとするか、あるいは `sfr.sp` が空になるまでループし続ける可能性がありました。特に、`readHole` が `sfr.sp[0].offset` に到達するまでゼロを埋め続けるロジックにおいて、`sfr.sp[0].offset` がファイルの論理的な終端を超えていると、`readHole` が永遠にそのオフセットに到達しようとし、結果としてハングアップを引き起こしていました。

**修正**:
追加されたコード `if sfr.tot < sfr.sp[0].offset` は、この不正な状態を検出します。`sfr.tot` はこれまでに `sparseFileReader` が読み込んだ（またはスキップした）総バイト数であり、`sfr.sp[0].offset` は次に処理すべきスパースエントリの開始オフセットです。もし `sfr.tot` が `sfr.sp[0].offset` よりも小さい場合、これは `sparseFileReader` がまだ `sfr.sp[0].offset` に到達していないことを意味します。しかし、もし `sfr.sp[0].offset` がファイルの論理的な終端を超えているような不正な値であれば、`sfr.tot` が `sfr.sp[0].offset` に到達することは決してありません。

このチェックが追加されたことで、もし `sfr.tot` が `sfr.sp[0].offset` よりも小さいにもかかわらず、`sfr.sp` が空でない（つまり、まだ処理すべきスパースエントリがある）という状況になった場合、それは不正なスパースデータであることを示します。この場合、`io.ErrUnexpectedEOF` を返すことで、ハングアップを防ぎ、エラーとして処理を終了させます。

### `src/archive/tar/reader.go` の変更

追加された3行のコードは、`sparseFileReader.Read` メソッドの冒頭近くに挿入されています。

	if sfr.tot < sfr.sp[0].offset {

	}
```

このコードブロックは、以下の条件をチェックします。

*   `sfr.tot`: `sparseFileReader` がこれまでに処理した（読み込んだかスキップした）総バイト数。これはファイルの論理的なサイズを表します。

通常、`sfr.tot` は `sfr.sp[0].offset` と等しいか、それよりも大きくなるはずです（つまり、既にそのオフセットを通過しているか、まさにそのオフセットにいる）。しかし、もし `sfr.tot` が `sfr.sp[0].offset` よりも**小さい**場合、これは不正な状態を示します。具体的には、`sfr.sp[0].offset` がファイルの論理的な終端を超えているか、またはスパースエントリの順序が不正である可能性が高いです。このような状況では、`sparseFileReader` は `sfr.sp[0].offset` に到達しようとして無限ループに陥る可能性があったため、ここで `io.ErrUnexpectedEOF` を返して処理を中断します。これにより、不正な入力データに対する堅牢性が向上し、ハングアップが防止されます。

`TestIssue10968` という新しいテスト関数が追加されました。

1.  `os.Open("testdata/issue10968.tar")`: 不正なスパースファイルデータを含む特別に作成されたTARファイルを開きます。
2.  `r := NewReader(f)`: そのファイルから `tar.Reader` を作成します。
3.  `r.Next()`: TARアーカイブの最初の（そして唯一の）エントリのヘッダを読み込みます。この時点で、`sparseFileReader` が初期化され、不正なスパースオフセット情報がロードされます。
4.  `io.Copy(ioutil.Discard, r)`: エントリのデータを読み飛ばします。この `io.Copy` の呼び出し中に、`sparseFileReader.Read` メソッドが繰り返し呼び出され、上記の不正なオフセット条件がトリガーされます。
5.  `if err != io.ErrUnexpectedEOF`: 期待される動作は、`io.ErrUnexpectedEOF` エラーが返されることです。もしこのエラーが返されなければ、テストは失敗し、問題が修正されていないことを示します。

`sparseFileReader` は、スパースファイルのデータを効率的に読み取るための内部的なリーダーです。このリーダーは、スパースファイルの構造を記述する `sp` (sparse entries) スライスと、現在までに読み込んだバイト数を追跡する `tot` フィールド、現在の読み取り位置 `pos` を持っています。

`Read` メソッドのロジックは、以下のようになっています。

1.  **スパースエントリの処理**: `sfr.sp` には、スパースファイルのデータブロック（非ホール部分）のオフセットとサイズが格納されています。`Read` メソッドは、これらのエントリを順に処理し、現在の読み取り位置 `sfr.pos` が次のデータブロックの開始オフセット `sfr.sp[0].offset` に達するまで、ホール（ゼロバイト）を生成するか、実際のデータを読み込みます。
2.  **ホールの読み取り**: `sfr.pos < sfr.sp[0].offset` の場合、現在の位置はホール内にあります。`readHole` メソッドが呼び出され、指定されたバイト数までゼロバイトを生成して返します。
3.  **データの読み取り**: `sfr.pos >= sfr.sp[0].offset` の場合、現在の位置はデータブロック内にあります。`sfr.r.Read()` を呼び出して基になるリーダーから実際のデータを読み込みます。

**問題点**:
コミット前のコードでは、`sfr.sp[0].offset` が `sfr.tot` (これまでに読み込んだ総バイト数) よりも大きい、つまり、ファイル全体のサイズを超えたオフセットがスパースエントリとして指定されているような不正なケースが考慮されていませんでした。このような状況では、`sfr.pos` が `sfr.sp[0].offset` に到達することがなく、`readHole` メソッドが無限にゼロバイトを生成しようとするか、あるいは `sfr.sp` が空になるまでループし続ける可能性がありました。特に、`readHole` が `sfr.sp[0].offset` に到達するまでゼロを埋め続けるロジックにおいて、`sfr.sp[0].offset` がファイルの論理的な終端を超えていると、`readHole` が永遠にそのオフセットに到達しようとし、結果としてハングアップを引き起こしていました。

**修正**:
追加されたコード `if sfr.tot < sfr.sp[0].offset` は、この不正な状態を検出します。`sfr.tot` はこれまでに `sparseFileReader` が読み込んだ（またはスキップした）総バイト数であり、`sfr.sp[0].offset` は次に処理すべきスパースエントリの開始オフセットです。もし `sfr.tot` が `sfr.sp[0].offset` よりも小さい場合、これは `sparseFileReader` がまだ `sfr.sp[0].offset` に到達していないことを意味します。しかし、もし `sfr.sp[0].offset` がファイルの論理的な終端を超えているような不正な値であれば、`sfr.tot` が `sfr.sp[0].offset` に到達することは決してありません。

このチェックが追加されたことで、もし `sfr.tot` が `sfr.sp[0].offset` よりも小さいにもかかわらず、`sfr.sp` が空でない（つまり、まだ処理すべきスパースエントリがある）という状況になった場合、それは不正なスパースデータであることを示します。この場合、`io.ErrUnexpectedEOF` を返すことで、ハングアップを防ぎ、エラーとして処理を終了させます。

## コアとなるコードの解説

### `src/archive/tar/reader.go` の変更

追加された3行のコードは、`sparseFileReader.Read` メソッドの冒頭近くに挿入されています。

```go
	if sfr.tot < sfr.sp[0].offset {
		return 0, io.ErrUnexpectedEOF
	}
```

このコードブロックは、以下の条件をチェックします。

*   `sfr.tot`: `sparseFileReader` がこれまでに処理した（読み込んだかスキップした）総バイト数。これはファイルの論理的なサイズを表します。
*   `sfr.sp[0].offset`: 次に処理すべきスパースエントリ（データブロック）の開始オフセット。

通常、`sfr.tot` は `sfr.sp[0].offset` と等しいか、それよりも大きくなるはずです（つまり、既にそのオフセットを通過しているか、まさにそのオフセットにいる）。しかし、もし `sfr.tot` が `sfr.sp[0].offset` よりも**小さい**場合、これは不正な状態を示します。具体的には、`sfr.sp[0].offset` がファイルの論理的な終端を超えているか、またはスパースエントリの順序が不正である可能性が高いです。このような状況では、`sparseFileReader` は `sfr.sp[0].offset` に到達しようとして無限ループに陥る可能性があったため、ここで `io.ErrUnexpectedEOF` を返して処理を中断します。これにより、不正な入力データに対する堅牢性が向上し、ハングアップが防止されます。

### `src/archive/tar/reader_test.go` の変更

`TestIssue10968` という新しいテスト関数が追加されました。

1.  `os.Open("testdata/issue10968.tar")`: 不正なスパースファイルデータを含む特別に作成されたTARファイルを開きます。
2.  `r := NewReader(f)`: そのファイルから `tar.Reader` を作成します。
3.  `r.Next()`: TARアーカイブの最初の（そして唯一の）エントリのヘッダを読み込みます。この時点で、`sparseFileReader` が初期化され、不正なスパースオフセット情報がロードされます。
4.  `io.Copy(ioutil.Discard, r)`: エントリのデータを読み飛ばします。この `io.Copy` の呼び出し中に、`sparseFileReader.Read` メソッドが繰り返し呼び出され、上記の不正なオフセット条件がトリガーされます。
5.  `if err != io.ErrUnexpectedEOF`: 期待される動作は、`io.ErrUnexpectedEOF` エラーが返されることです。もしこのエラーが返されなければ、テストは失敗し、問題が修正されていないことを示します。

このテストケースは、以前ハングアップを引き起こしていた特定の不正な入力シナリオを再現し、修正が正しく機能することを確認します。

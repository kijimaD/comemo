# [インデックス 25739] ファイルの概要

このコミットは、Goコンパイラおよびリンカにおける386アーキテクチャでの動的リンク（`-dynlink`オプション使用時）のサポートを改善するものです。具体的には、グローバルデータへのアクセスをGOT（Global Offset Table）経由で行うためのメカニズムを有効にします。これにより、386環境での動的リンクされたGoプログラムが、共有ライブラリ内のグローバル変数や関数に正しくアクセスできるようになります。

## 変更の背景

この変更の背景には、Goプログラムを動的リンク（`-dynlink`オプション）でビルドする際の、特に32ビットx86（386）アーキテクチャにおけるグローバルデータアクセスに関する課題がありました。

動的リンクされたプログラムでは、実行時に共有ライブラリがメモリ上のどこにロードされるか分からないため、コンパイル時に絶対アドレスを決定できません。この問題を解決するために、GOT（Global Offset Table）とPLT（Procedure Linkage Table）というメカニズムが使用されます。

64ビットアーキテクチャ（AMD64など）では、PC相対アドレッシング（プログラムカウンタからの相対オフセットでアドレスを指定する方式）が広くサポートされており、GOTへのアクセスも比較的容易です。しかし、32ビットx86アーキテクチャでは、PC相対アドレッシングの制約が大きく、特にGOTへのアクセスには特別な考慮が必要です。

以前のGoリンカは、386環境での動的リンク時にグローバルデータへのアクセスをGOT経由で行うための適切な処理が不足していました。これにより、動的リンクされたGoプログラムが共有ライブラリ内のグローバル変数や関数にアクセスしようとすると、実行時エラーや不正な動作を引き起こす可能性がありました。

このコミットは、386アーキテクチャにおいて、リンカが`R_GOTPCREL`という再配置タイプを適切に処理し、グローバルデータへのアクセスをGOT経由で行うように修正することで、この問題を解決することを目的としています。これにより、386環境でもGoプログラムがより堅牢に動的リンクできるようになります。

## 前提知識の解説

### 1. 動的リンクと静的リンク

*   **静的リンク**: プログラムが必要とする全てのコード（ライブラリ含む）をコンパイル時に一つの実行ファイルに結合する方式。実行ファイルは自己完結型で、他のライブラリに依存しない。
*   **動的リンク**: プログラムが必要とする共有ライブラリを、実行時にOSがメモリにロードし、プログラムと結合する方式。実行ファイルのサイズが小さくなり、複数のプログラムで同じライブラリを共有できるためメモリ効率が良い。しかし、ライブラリのバージョン管理やロード時のオーバーヘッドが発生する。

### 2. GOT (Global Offset Table) と PLT (Procedure Linkage Table)

動的リンクされたプログラムが共有ライブラリ内のデータや関数にアクセスするために使用される重要なメカニズムです。

*   **GOT (Global Offset Table)**:
    *   共有ライブラリ内のグローバル変数や、他の共有ライブラリ内のグローバル変数への絶対アドレスを格納するテーブルです。
    *   プログラムが起動される際、動的リンカがGOTエントリを実際のメモリ上のアドレスで埋めます。
    *   プログラムは、直接グローバル変数のアドレスを参照するのではなく、GOTを介して間接的に参照します。
*   **PLT (Procedure Linkage Table)**:
    *   共有ライブラリ内の関数や、他の共有ライブラリ内の関数を呼び出すために使用されるテーブルです。
    *   関数が初めて呼び出される際に、PLTエントリが動的リンカを呼び出し、実際の関数のアドレスを解決してGOTに格納します。2回目以降の呼び出しでは、PLTはGOTに格納されたアドレスを直接使用して関数を呼び出します。

### 3. PC相対アドレッシング (PC-relative Addressing)

*   命令のアドレスを、プログラムカウンタ（PC）の現在値からの相対オフセットで指定するアドレッシングモードです。
*   位置独立コード（PIC: Position-Independent Code）を生成するために不可欠です。PICは、メモリ上のどこにロードされても正しく実行できるコードであり、共有ライブラリで広く使用されます。
*   64ビットアーキテクチャでは、PC相対アドレッシングの範囲が広いため、GOTへのアクセスもPC相対で容易に行えます。
*   32ビットx86アーキテクチャでは、PC相対アドレッシングの範囲が限られている（通常±2GB程度）ため、GOTへのアクセスには工夫が必要です。特に、GOTのアドレス自体をPC相対で取得し、そのGOTを基準にグローバルデータのアドレスを計算する手法が一般的です。

### 4. 再配置 (Relocation)

*   コンパイル時に決定できなかったアドレス（例えば、共有ライブラリ内のグローバル変数のアドレス）を、リンク時またはロード時に解決するプロセスです。
*   リンカは、オブジェクトファイル内の再配置エントリ（Relocation Entry）を読み取り、シンボル（変数名や関数名）を実際のメモリ上のアドレスに置き換えます。
*   `R_GOTPCREL`は、GOTのアドレスをPC相対で取得するための再配置タイプの一つです。

### 5. 386 (IA-32) と AMD64 (x86-64) の違い

*   **386 (IA-32)**: 32ビットアーキテクチャ。レジスタが少なく（汎用レジスタ8個）、PC相対アドレッシングの制約が大きい。GOTへのアクセスには、`CALL`命令を利用してリターンアドレスをスタックにプッシュし、それをPCとして利用するなどのテクニックが使われることがあります。
*   **AMD64 (x86-64)**: 64ビットアーキテクチャ。レジスタが多く（汎用レジスタ16個）、PC相対アドレッシングの範囲が広い。GOTへのアクセスは、`LEA`命令などを使ってPC相対でGOTのアドレスをレジスタにロードし、それを使って間接的にアクセスするのが一般的です。

## 技術的詳細

このコミットは、Goのツールチェイン（アセンブラ、リンカ）が386アーキテクチャで動的リンクを行う際に、グローバルデータへのアクセスをGOT経由で正しく処理するための変更を導入しています。

主要な変更点は以下の通りです。

1.  **`R_GOTPCREL`再配置タイプの導入と処理**:
    *   `src/cmd/internal/obj/x86/asm6.go`において、386環境での`R_GOTPCREL`再配置タイプが`R_PCREL`と同様の仮定（PC相対オフセットの計算）に基づいて処理されるように修正されました。これは、GOTのアドレスをPC相対で計算する際に必要なオフセット調整を意味します。
    *   `src/cmd/link/internal/x86/asm.go`では、ELF形式の再配置処理において`R_GOTPCREL`が`R_386_GOTPC`として扱われるように明示的に定義されました。これは、リンカがこの再配置タイプを認識し、GOTへのPC相対参照を生成するために必要な情報です。

2.  **`rewriteToUseGot`関数の拡張**:
    *   `src/cmd/internal/obj/x86/obj6.go`内の`rewriteToUseGot`関数は、アセンブラが生成した命令をGOT経由のアクセスに書き換える役割を担っています。
    *   この関数は、386とAMD64の両方に対応できるよう、命令の種類（`MOVQ` vs `MOVL`、`ADDQ` vs `ADDL`、`LEAQ` vs `LEAL`）と一時レジスタ（`REG_R15` vs `REG_CX`）を動的に選択するように変更されました。
    *   特に386の場合、`LEAL sym, Rx`のような命令が`MOVL $sym, Rx`に変換され、さらに`MOVL sym@GOT, Rx`に書き換えられるロジックが追加されました。これは、386では直接的なPC相対`LEA`がGOTアクセスに使いにくいため、一度絶対アドレスとして扱い、その後GOT経由のアクセスに変換するアプローチを取っていることを示唆しています。
    *   複雑な宛先（レジスタではないメモリ位置など）を持つ命令（例: `PUSHL $sym`）に対しても、一時レジスタ（`CX`）を介してGOTからアドレスをロードし、そのレジスタを使って最終的な操作を行うように修正されました。

3.  **`CALL`命令の特殊処理 (386)**:
    *   386環境での`CALL`命令に対して特別な処理が追加されました。動的リンクされたプログラムでは、ほぼ全ての`CALL`がPLT（Procedure Linkage Table）への呼び出しになる可能性があるため、GOTポインタが`BX`レジスタにロードされていることを保証する必要があります。
    *   このため、`CALL`命令の前に`LEAL _GLOBAL_OFFSET_TABLE_, BX`という命令を挿入し、`BX`レジスタにGOTのアドレスをロードするように変更されました。これにより、PLTエントリがGOTを正しく参照できるようになります。

これらの変更により、Goのリンカは386アーキテクチャで動的リンクされたバイナリを生成する際に、グローバルデータへのアクセスをGOT経由で適切に解決できるようになり、実行時の互換性と安定性が向上します。

```go
 		} else {
```
*   `elfreloc1`関数に`obj.R_GOTPCREL`ケースが追加されました。これにより、リンカは`R_GOTPCREL`再配置をELFの`R_386_GOTPC`として処理し、必要に応じて`R_386_GOT32`再配置も生成するようになります。これは、386環境でGOTへのPC相対参照を正しく解決するために不可欠です。
*   `obj.R_CALL`の処理が`R_GOTPCREL`から分離され、動的インポートされたシンボルに対しては`R_386_PLT32`を、それ以外に対しては`R_386_PC32`を使用するように明示的に定義されました。

## コアとなるコードの解説

### `src/cmd/internal/obj/x86/asm6.go` の変更

`asm6.go`はGoのアセンブラの一部で、命令のエンコードと再配置エントリの生成を担当します。
追加されたコードブロックは、`R_GOTPCREL`再配置タイプが386アーキテクチャで使用される場合の特別な処理を定義しています。

```go
		if r.Type == obj.R_GOTPCREL && p.Mode == 32 {
			// On 386, R_GOTPCREL makes the same assumptions as R_PCREL.
			r.Add += int64(r.Off) - p.Pc + int64(r.Siz)
		}
```
*   `r.Type == obj.R_GOTPCREL && p.Mode == 32`: 現在の再配置タイプが`R_GOTPCREL`であり、かつターゲットアーキテクチャが32ビットモード（386）である場合にこのロジックが適用されます。
*   `r.Add += int64(r.Off) - p.Pc + int64(r.Siz)`: これはPC相対アドレッシングにおけるオフセット計算の典型的なパターンです。
    *   `r.Off`: 再配置が適用される命令内のオフセット。
    *   `p.Pc`: 現在のプログラムカウンタ（命令のアドレス）。
    *   `r.Siz`: 再配置フィールドのサイズ（通常は4バイト）。
    *   この計算は、再配置対象のアドレスがPCからの相対位置として正しく解決されるように、追加のオフセットを調整します。386では`R_GOTPCREL`が`R_PCREL`と同様に扱われるというコメントは、GOTへの参照もPC相対で計算されることを示唆しています。

### `src/cmd/internal/obj/x86/obj6.go` の変更

`obj6.go`は、Goのアセンブラが生成した命令（`obj.Prog`）を操作し、リンカが処理しやすい形に変換する役割を担っています。特に`rewriteToUseGot`関数は、動的リンク時にグローバルデータへのアクセスをGOT経由に書き換える中心的なロジックを含んでいます。

```go
	var add, lea, mov, reg int16
	if p.Mode == 64 {
		add = AADDQ
		lea = ALEAQ
		mov = AMOVQ
		reg = REG_R15
	} else {
		add = AADDL
		lea = ALEAL
		mov = AMOVL
		reg = REG_CX
	}
```
*   このブロックは、現在のプログラムのモード（32ビットまたは64ビット）に応じて、使用するアセンブリ命令（`ADD`, `LEA`, `MOV`）と一時レジスタを決定します。
    *   64ビットモードでは、`ADDQ`, `LEAQ`, `MOVQ`命令と`R15`レジスタを使用します。
    *   32ビットモードでは、`ADDL`, `LEAL`, `MOVL`命令と`CX`レジスタを使用します。これにより、コードが両方のアーキテクチャで汎用的に機能するようになります。

`ADUFFCOPY`/`ADUFFZERO`命令の変換ロジックの変更は、上記で定義された汎用命令とレジスタを使用するように更新されています。

```go
	if p.As == lea && p.From.Type == obj.TYPE_MEM && p.From.Name == obj.NAME_EXTERN && !p.From.Sym.Local {
		// $LEA sym, Rx becomes $MOV $sym, Rx which will be rewritten below
		p.As = mov
		p.From.Type = obj.TYPE_ADDR
	}
```
*   `LEA sym, Rx`のような命令（シンボル`sym`のアドレスをレジスタ`Rx`にロードする）が、まず`MOV $sym, Rx`（シンボル`sym`の絶対アドレスをレジスタ`Rx`にロードする）に変換されます。これは、386では直接的なPC相対`LEA`がGOTアクセスに使いにくいため、一度絶対アドレスとして扱い、その後GOT経由のアクセスに変換する準備段階です。

```go
	if p.From.Type == obj.TYPE_ADDR && p.From.Name == obj.NAME_EXTERN && !p.From.Sym.Local {
		// ...
		cmplxdest := false
		pAs := p.As
		var dest obj.Addr
		if p.To.Type != obj.TYPE_REG || pAs != mov {
			if p.Mode == 64 {
				ctxt.Diag("do not know how to handle LEA-type insn to non-register in %v with -dynlink", p)
			}
			cmplxdest = true
			dest = p.To
			p.As = mov
			p.To.Type = obj.TYPE_REG
			p.To.Reg = REG_CX
			p.To.Sym = nil
			p.To.Name = obj.NAME_NONE
		}
		// ... (GOT参照への変換ロジック)
		if cmplxdest {
			q = obj.Appendp(ctxt, q)
			q.As = pAs
			q.To = dest
			q.From.Type = obj.TYPE_REG
			q.From.Reg = REG_CX
		}
	}
```
*   `MOV $sym, Rx`のような命令を`MOV sym@GOT, Rx`に変換するロジックです。
*   `cmplxdest`フラグは、命令の宛先がレジスタではない場合（例: `PUSHL $sym`のようにスタックにプッシュする場合）に設定されます。
*   386モードで複雑な宛先を持つ場合、まず`MOV sym@GOT, CX`のようにGOTからアドレスを一時レジスタ`CX`にロードし、その後、元の命令（`PUSHL`など）を`PUSHL CX`のように書き換えて、`CX`レジスタの内容（GOTから取得したアドレス）を使用するようにします。これにより、間接的なアドレス指定が可能になります。

`ACALL`命令の特殊処理は、386環境での動的リンクの重要な側面を扱っています。

```go
	if p.As == obj.ACALL {
		// When dynlinking on 386, almost any call might end up being a call
		// to a PLT, so make sure the GOT pointer is loaded into BX.
		// ...
		p1 := obj.Appendp(ctxt, p)
		p2 := obj.Appendp(ctxt, p1)

		p1.As = ALEAL
		p1.From.Type = obj.TYPE_MEM
		p1.From.Name = obj.NAME_STATIC
		p1.From.Sym = obj.Linklookup(ctxt, "_GLOBAL_OFFSET_TABLE_", 0)
		p1.To.Type = obj.TYPE_REG
		p1.To.Reg = REG_BX

		p2.As = p.As
		// ... (元のCALL命令の情報をp2にコピー)
		p2.To.Type = obj.TYPE_MEM // checkaddrの警告を避けるため
		p2.RegTo2 = 1 // progeditで再処理されないようにフラグを設定

		obj.Nopout(p) // 元の命令をNOPで埋める
		return
	}
```
*   386モードで`ACALL`命令が見つかった場合、その前にGOTのアドレスを`BX`レジスタにロードする命令を挿入します。
*   `LEAL _GLOBAL_OFFSET_TABLE_, BX`: `_GLOBAL_OFFSET_TABLE_`というシンボル（GOTの先頭アドレス）を`BX`レジスタにロードします。これは、多くのシステムV ABI（Application Binary Interface）において、PLTがGOTを参照する際に`BX`レジスタにGOTのアドレスが期待されるためです。
*   元の`CALL`命令は`p2`にコピーされ、`p`は`obj.Nopout(p)`によってNOP命令で埋められます。これにより、命令が正しく再配置され、GOTポインタが`BX`に設定された状態で関数が呼び出されることが保証されます。

### `src/cmd/link/internal/x86/asm.go` の変更

`asm.go`はGoのリンカの一部で、ELF形式のオブジェクトファイルや実行ファイルを生成する際の再配置処理を担当します。

```go
	case obj.R_GOTPCREL:
		if r.Siz == 4 {
			ld.Thearch.Lput(ld.R_386_GOTPC)
			if r.Xsym.Name != "_GLOBAL_OFFSET_TABLE_" {
				ld.Thearch.Lput(uint32(sectoff))
				ld.Thearch.Lput(ld.R_386_GOT32 | uint32(elfsym)<<8)
			}
		} else {
			return -1
		}
```
*   `obj.R_GOTPCREL`再配置タイプが処理されるようになりました。
*   `ld.Thearch.Lput(ld.R_386_GOTPC)`: これは、ELFの`R_386_GOTPC`再配置エントリを生成します。`R_386_GOTPC`は、GOTのアドレスをPC相対で計算するために使用されます。
*   `if r.Xsym.Name != "_GLOBAL_OFFSET_TABLE_"`: もし参照しているシンボルがGOT自体ではない場合、追加で`R_386_GOT32`再配置を生成します。`R_386_GOT32`は、GOT内の特定のエントリへの32ビットオフセットを解決するために使用されます。これにより、リンカはGOT内の正しいエントリを指すようにアドレスを調整できます。

```go
	case obj.R_CALL:
		if r.Siz == 4 {
			if r.Xsym.Type == obj.SDYNIMPORT {
				ld.Thearch.Lput(ld.R_386_PLT32 | uint32(elfsym)<<8)
			} else {
				ld.Thearch.Lput(ld.R_386_PC32 | uint32(elfsym)<<8)
			}
		} else {
			return -1
		}
```
*   `obj.R_CALL`の処理が`R_GOTPCREL`から分離され、より明確になりました。
*   `r.Xsym.Type == obj.SDYNIMPORT`: 呼び出し対象のシンボルが動的にインポートされたものである場合（つまり、共有ライブラリ内の関数である場合）、`R_386_PLT32`再配置を生成します。これは、PLTを介して関数を呼び出すことを意味します。
*   それ以外の場合（静的にリンクされた関数など）は、通常のPC相対呼び出しである`R_386_PC32`再配置を生成します。

これらの変更により、Goのリンカは386アーキテクチャで動的リンクされたバイナリを生成する際に、グローバルデータへのアクセスと関数呼び出しをGOT/PLT経由で適切に解決できるようになり、実行時の互換性と安定性が向上します。

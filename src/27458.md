# [インデックス 27458] ファイルの概要

このコミットは、Goリンカがコンパイラによって生成されたすべてのインターフェーステーブル（`itab`）のリンクシンボル（`itablink`）を収集し、それらを`moduledata`構造体内のスライスとして格納するように変更します。これにより、Goランタイムが実行時にモジュール内のすべての`itab`に効率的にアクセスできるようになります。この変更は、既存の`typelink`シンボルの収集ロジックを参考にしています。

## コミット

```
cmd/link: collect itablinks as a slice in moduledata

See #14874

This change tells the linker to collect all the itablink symbols and
collect them so that moduledata can have a slice of all compiler
generated itabs.

The logic is shamelessly adapted from what is done with typelink symbols.
```

## 変更の背景

Go言語では、インターフェースは非常に強力な機能であり、ポリモーフィズムを実現するために利用されます。インターフェースの動的なディスパッチは、実行時に具体的な型がどのインターフェースメソッドを実装しているかを解決する必要があります。この解決には`itab`（インターフェーステーブル）というランタイムデータ構造が用いられます。

以前のGoのバージョンでは、`itab`の管理方法に改善の余地がありました。特に、リンカがコンパイラによって生成されたすべての`itab`シンボルを効率的に収集し、ランタイムがそれらにアクセスできるような一元的なメカニズムが不足していた可能性があります。これにより、`itab`の探索や管理が非効率になる可能性がありました。

このコミットの背景には、`typelink`（型情報へのリンク）と同様の課題があったと考えられます。`typelink`もまた、ランタイムが型情報にアクセスするための重要なメカボルズムであり、リンカがこれらを効率的に収集する仕組みが既に存在していました。このコミットは、`itablink`に対しても同様の最適化を適用することで、`itab`の管理を改善し、ランタイムの効率性を向上させることを目的としています。具体的には、`moduledata`というモジュールごとのメタデータ構造に`itablinks`のスライスを追加することで、すべての`itab`へのポインタを一箇所に集約し、ランタイムからのアクセスを容易にしています。

## 前提知識の解説

### Goのインターフェースと`itab` (Interface Table)

Goのインターフェースは、メソッドのシグネチャの集合を定義します。具体的な型がそのインターフェースのすべてのメソッドを実装している場合、その型はそのインターフェースを満たします。インターフェース変数は、内部的に2つのポインタで構成されます。1つは具体的な型のデータへのポインタ、もう1つは`itab`へのポインタです。

`itab`は、Goランタイムがインターフェースの動的ディスパッチを行うために使用する重要なデータ構造です。`itab`は以下の情報を含みます。
*   **インターフェース型**: その`itab`が対応するインターフェースの型情報。
*   **具体的な型**: その`itab`が対応する具体的な型の型情報。
*   **メソッドテーブル**: 具体的な型がインターフェースのメソッドを実装する際の、実際の関数ポインタのリスト。これにより、インターフェースメソッドが呼び出されたときに、正しい具体的な型のメソッドが実行されます。

`itab`は、具体的な型とインターフェース型のペアごとに生成されるか、既存のものが再利用されます。

### `moduledata`構造体

`moduledata`は、Goの実行可能ファイルまたは動的にロードされるプラグイン（モジュール）に関するメタデータを格納するランタイム内部の構造体です。Goランタイムは、この`moduledata`を使用して、モジュール内の型情報、関数情報、シンボル情報などを解決します。
`moduledata`には、コードセクション、データセクション、BSSセクションへのポインタ、関数テーブル、そして型情報へのリンクなどが含まれます。このコミット以前から、`typelinks`という型情報へのポインタのスライスが含まれていました。

### Goリンカの役割

Goリンカ（`cmd/link`）は、コンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能ファイルやライブラリを生成するツールです。リンカは、シンボル解決、メモリレイアウトの決定、リロケーションの適用など、多くの重要なタスクを実行します。Goのリンカは、Goランタイムが実行時に必要とするメタデータ（例: `moduledata`）を構築する役割も担っています。

### `typelink`シンボル

`typelink`シンボルは、Goランタイムが型情報にアクセスするためにリンカが生成する特殊なシンボルです。`moduledata`には`typelinks`というスライスがあり、これを通じてランタイムはモジュール内のすべての型情報に効率的にアクセスできます。このコミットは、`itablink`に対しても同様のメカニズムを導入します。

## 技術的詳細

このコミットの核心は、Goリンカが`itablink`シンボルを`moduledata`構造体内のスライスとして一元的に収集・管理するように変更することです。これにより、ランタイムはモジュール内のすべてのコンパイラ生成`itab`に効率的にアクセスできるようになります。

具体的な技術的変更点は以下の通りです。

1.  **新しいシンボル種別 `SITABLINK` の導入**:
    *   `src/cmd/internal/goobj/read.go` および `src/cmd/internal/obj/link.go` で、`SITABLINK`という新しいシンボル種別が定義されました。これは、`itab`へのリンクを表すシンボルを識別するために使用されます。
    *   `src/cmd/internal/objfile/goobj.go` では、`SITABLINK`シンボルが読み取り専用データ（`'R'`）として分類されるように更新されました。

2.  **`moduledata`構造体への`itablinks`スライスの追加**:
    *   `src/runtime/symtab.go` の`moduledata`構造体に、`itablinks []*itab`という新しいフィールドが追加されました。これは、収集されたすべての`itab`へのポインタを格納するためのスライスです。

3.  **リンカによる`itablink`シンボルの収集とセクションへの配置**:
    *   `src/cmd/link/internal/ld/symtab.go` では、リンカが`go.itablink.`というプレフィックスを持つシンボルを`SITABLINK`型として識別し、`symitablink`という特別なシンボルに紐付けるロジックが追加されました。また、`moduledata`に`itablinks`スライスの開始アドレスと要素数を記録する処理が追加されています。
    *   `src/cmd/link/internal/ld/data.go` では、`typelink`セクションと同様に、`.itablink`という新しい読み取り専用データセクションが追加され、`SITABLINK`型のシンボルがこのセクションに配置されるようになりました。`runtime.itablink`と`runtime.eitablink`というシンボルが定義され、それぞれ`itablinks`スライスの開始アドレスと終了アドレスを示します。

4.  **デッドコード削除ロジックの更新**:
    *   `src/cmd/link/internal/ld/deadcode.go` では、デッドコード削除の際に`go.itablink.`シンボルも考慮されるようになりました。`typelink`と同様に、`itablink`が指すシンボルが到達可能であれば、その`itablink`も保持されるようになります。これは、共有ライブラリ（`BuildmodeShared`）の場合には常に`itablink`が保持されるという既存の`typelink`のロジックに倣っています。

5.  **ELFセクション情報の更新**:
    *   `src/cmd/link/internal/ld/elf.go` では、ELF形式の出力において、`.itablink`セクションに関する情報（セクション名、リロケーション情報など）が追加されました。

6.  **アセンブリシンボル生成の更新**:
    *   `src/cmd/link/internal/ld/lib.go` の`genasmsym`関数において、`SITABLINK`型のシンボルもアセンブリシンボルとして適切に処理されるように更新されました。

これらの変更により、Goのリンカは`itab`に関するメタデータをより構造化された形で管理できるようになり、ランタイムがインターフェースの動的ディスパッチをより効率的に実行するための基盤が強化されました。特に、`typelink`の既存の成功したパターンを`itablink`に適用することで、一貫性のあるアプローチが採用されています。

## コアとなるコードの変更箇所

このコミットで変更された主要なファイルと、それぞれの変更の概要は以下の通りです。

*   **`src/cmd/internal/goobj/read.go`**:

    *   リンカ内部で使用される`SITABLINK`定数が追加され、`itablink`シンボルがリンカのシンボル種別として定義されました。
*   **`src/cmd/internal/objfile/goobj.go`**:
    *   `itablink`シンボルが読み取り専用データ（`'R'`）として分類されるように、シンボルコードの割り当てロジックが更新されました。
*   **`src/cmd/link/internal/ld/data.go`**:
    *   `itablink`シンボルを収集し、`.itablink`という新しい読み取り専用データセクションに配置するロジックが追加されました。
    *   `runtime.itablink`と`runtime.eitablink`というランタイムシンボルが定義され、`itablinks`スライスの開始と終了アドレスを示します。
*   **`src/cmd/link/internal/ld/deadcode.go`**:
    *   デッドコード削除の際に、`go.itablink.`プレフィックスを持つシンボルも到達可能性の判定対象となるようにロジックが拡張されました。
*   **`src/cmd/link/internal/ld/elf.go`**:
    *   ELF形式の出力において、`.itablink`セクション名および関連するリロケーションセクション名が追加されました。
*   **`src/cmd/link/internal/ld/lib.go`**:
    *   `genasmsym`関数が`SITABLINK`型のシンボルを適切に処理するように更新されました。
*   **`src/cmd/link/internal/ld/symtab.go`**:
    *   `runtime.itablink`と`runtime.eitablink`シンボルが初期化され、`go.itablink.`プレフィックスを持つシンボルが`SITABLINK`型として分類されるようになりました。
    *   `moduledata`構造体への`itablinks`スライスの開始アドレスと要素数の情報が追加されました。
*   **`src/runtime/symtab.go`**:
    *   `moduledata`構造体に`itablinks []*itab`フィールドが追加され、`itab`へのポインタのスライスを保持できるようになりました。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/runtime/symtab.go`における`moduledata`構造体への`itablinks`フィールドの追加と、`src/cmd/link/internal/ld/data.go`および`src/cmd/link/internal/ld/symtab.go`におけるリンカの処理ロジックの変更です。

### `src/runtime/symtab.go` の変更

```go
type moduledata struct {
	// ... 既存のフィールド ...
	end, gcdata, gcbss    uintptr

	typelinks []*_type
	itablinks []*itab // <-- 追加されたフィールド

	modulename   string
	modulehashes []modulehash
	// ... その他のフィールド ...
}
```
`moduledata`構造体に`itablinks []*itab`というスライスが追加されました。これは、このモジュール内でコンパイラによって生成されたすべての`itab`へのポインタを格納するためのものです。ランタイムはこのスライスを通じて、必要な`itab`を効率的に検索・利用できるようになります。

### `src/cmd/link/internal/ld/data.go` の変更

```go
func dodata() {
	// ... 既存の処理 ...

	/* itablink */ // <-- itablinkセクションの処理が追加
	sect = addsection(segro, relro_prefix+".itablink", relro_perms)

	sect.Align = maxalign(s, obj.SITABLINK)
	datsize = Rnd(datsize, int64(sect.Align))
	sect.Vaddr = uint64(datsize)
	Linklookup(Ctxt, "runtime.itablink", 0).Sect = sect
	Linklookup(Ctxt, "runtime.eitablink", 0).Sect = sect
	for ; s != nil && s.Type == obj.SITABLINK; s = s.Next {
		datsize = aligndatsize(datsize, s)
		s.Sect = sect
		s.Type = obj.SRODATA
		s.Value = int64(uint64(datsize) - sect.Vaddr)
		growdatsize(&datsize, s)
	}

	sect.Length = uint64(datsize) - sect.Vaddr

	// ... 既存の処理 ...
}
```
この部分では、リンカが`.itablink`という新しい読み取り専用データセクションを作成し、そこに`SITABLINK`型のシンボルを配置しています。`runtime.itablink`と`runtime.eitablink`は、このセクションの開始アドレスと終了アドレスを示すシンボルとして定義され、ランタイムが`itablinks`スライスをメモリ上で見つけるための目印となります。

### `src/cmd/link/internal/ld/symtab.go` の変更

```go
func symtab() {
	// ... 既存の処理 ...

	xdefine("runtime.itablink", obj.SRODATA, 0) // <-- runtime.itablinkシンボルの定義
	xdefine("runtime.eitablink", obj.SRODATA, 0) // <-- runtime.eitablinkシンボルの定義

	// ... 既存の処理 ...

	symitablink := Linklookup(Ctxt, "runtime.itablink", 0) // <-- symitablinkシンボルのルックアップ
	symitablink.Type = obj.SITABLINK // <-- 型をSITABLINKに設定

	// ... 既存の処理 ...

	nitablinks := 0 // <-- itablinkの数をカウントする変数を追加

	// ... 既存のシンボル処理ループ内 ...
	if strings.HasPrefix(s.Name, "go.itablink.") { // <-- go.itablink.プレフィックスを持つシンボルを処理
		nitablinks++
		s.Type = obj.SITABLINK
		s.Attr |= AttrHidden
		s.Outer = symitablink
	}
	// ... 既存の処理 ...

	// The itablinks slice // <-- moduledataにitablinksスライスの情報を追加
	Addaddr(Ctxt, moduledata, Linklookup(Ctxt, "runtime.itablink", 0))
	adduint(Ctxt, moduledata, uint64(nitablinks))
	adduint(Ctxt, moduledata, uint64(nitablinks))

	// ... 既存の処理 ...
}
```
このコードは、リンカが`runtime.itablink`と`runtime.eitablink`シンボルを定義し、`go.itablink.`というプレフィックスを持つすべてのシンボルを`SITABLINK`型として分類する役割を担っています。最も重要なのは、`moduledata`構造体に対して、`itablinks`スライスの開始アドレス（`runtime.itablink`）と、スライスの要素数（`nitablinks`）を書き込んでいる点です。これにより、ランタイムは`moduledata`から直接`itablinks`スライスにアクセスできるようになります。

これらの変更により、Goのリンカとランタイムは`itab`情報をより体系的に管理し、インターフェースの動的ディスパッチの効率性を向上させることが可能になりました。

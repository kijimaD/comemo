## 変更の背景

Goのガベージコレクションは、アプリケーションの実行と並行して動作する「並行GC」を採用しています。この並行GCでは、アプリケーションがメモリを割り当て続ける一方で、GCもヒープのスキャンを進めます。この際、GCがメモリをスキャンする速度がアプリケーションのメモリ割り当て速度に追いつかないと、ヒープサイズが際限なく増加し、最終的にはメモリ不足に陥る可能性があります。

この問題を解決するために導入されているのが「GCアシスト（GC Assist）」というメカニズムです。GCアシストは、アプリケーションのゴルーチンがメモリを割り当てようとした際に、GCが遅れている場合に、そのゴルーチン自身にGC作業の一部を行わせることで、GCの進行を助けるものです。

このコミットの背景にあるのは、GCアシストの比率（どれくらいのGC作業をアプリケーションに負担させるか）を計算する際に考慮すべき重要な側面、すなわち「GCサイクル中にヒープサイズが変動する」という点です。特に、GCが進行している間にもアプリケーションは新しいオブジェクトを生成し続けるため、GCがスキャンすべきメモリの総量（スキャン可能なヒープサイズ）は増加する可能性があります。

もしGCアシスト比率がGCサイクル開始時のヒープサイズに基づいて一度だけ計算され、その後更新されない場合、ヒープサイズが増加すると、計算されたアシスト比率ではGC作業が不足し、GCが完了するまでに時間がかかったり、ヒープが過度に膨張したりするリスクがあります。このコミットは、この動的なヒープサイズの増加に対応するため、アシスト比率を継続的に見直す（revise）必要性をコードコメントとして明示し、その理由を説明することを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC) の基本

GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにした並行・世代別・非圧縮のGCです。
- **三色マーク**: オブジェクトを「白（未訪問）」「灰（訪問済みだが参照先未訪問）」「黒（訪問済みで参照先も訪問済み）」の3色に分類し、到達可能なオブジェクトをマークします。
- **並行GC**: アプリケーションの実行と並行してマークフェーズの大部分を実行します。これにより、アプリケーションの一時停止時間（Stop The World: STW）を最小限に抑えます。
- **GCアシスト**: 並行GC中にアプリケーションがメモリを割り当てすぎると、GCの進行が追いつかなくなることがあります。このとき、メモリを割り当てようとするアプリケーションのゴルーチン自身がGC作業の一部を手伝うことで、GCの進行を加速させます。

### GCアシスト (GC Assist) とは何か

GCアシストは、Goの並行GCにおいて、ミューテータ（アプリケーションのゴルーチン）がGCの進行を助けるメカニズムです。ミューテータがメモリを割り当てようとした際に、GCが目標達成に遅れていると判断されると、ミューテータは一定量のGC作業（ヒープのスキャンなど）を実行してから自身のメモリ割り当てを続行します。これにより、GCの遅延を解消し、ヒープの過度な膨張を防ぎます。アシストの量は「アシスト比率」に基づいて計算されます。

### STW (Stop The World)

STWは、ガベージコレクタがヒープの一貫性を確保するために、アプリケーションのすべてのゴルーチンを一時的に停止させる期間を指します。GoのGCはSTW時間を極力短くするように設計されており、ほとんどのGC作業は並行して行われますが、GCの開始時や終了時など、ごく短いSTWフェーズが存在します。

### `memstats.heap_scan` と `mheap_.lock` の役割

- `memstats.heap_scan`: Goランタイムが管理するメモリ統計情報の一部で、GCがスキャンしたヒープの総量（バイト単位）を追跡します。これはGCの進行状況を測る重要な指標です。
- `mheap_.lock`: Goランタイムのヒープ管理構造体 `mheap` を保護するためのミューテックスです。ヒープの割り当てや解放、GC関連の統計情報の更新など、ヒープの状態を変更する操作を行う際にはこのロックが取得されます。コミットメッセージにある「whenever memstats.heap_scan is updated (with mheap_.lock held)」という記述は、`heap_scan` の更新がこのロックの下で行われることを示唆しています。

### スキャン可能なヒープサイズ (scannable heap size)

スキャン可能なヒープサイズとは、ガベージコレクタが到達可能性を判断するためにスキャンする必要があるヒープ上のメモリ領域の総量です。これは、ポインタを含む可能性のあるオブジェクトが配置されているメモリ領域を指します。GoのGCは、ポインタを含まない（スキャン不要な）オブジェクトと、ポインタを含む（スキャン必要な）オブジェクトを区別して管理します。GCアシスト比率の計算において、このスキャン可能なヒープサイズは、GCが完了すべき作業量の見積もりの基礎となります。

## 技術的詳細

このコミットは、`src/runtime/mgc.go` 内の `gcControllerState` 構造体の `revise` メソッドにおけるコメントを修正・追加しています。`revise` メソッドは、GCアシスト比率などのGCパラメータを再計算（見直し）する役割を担っています。

変更前のコメントでは、`revise` 関数が「現在のヒープにおける可能なスキャン作業の厳密な上限」を計算すると説明されていました。しかし、この説明だけでは、なぜGCサイクル中にこの `revise` 関数を継続的に呼び出す必要があるのかが不明瞭でした。

追加されたコメントは、この疑問に答えるものです。
「GCサイクル中にスキャン可能なヒープサイズが増加する可能性が高い」という重要な事実を指摘しています。アプリケーションが実行中に新しいオブジェクトを割り当て続けるため、GCがスキャンすべきメモリの総量はGCの開始時点よりも増えることがあります。

もしGCアシスト比率がGCサイクル開始時のスキャン可能なヒープサイズに基づいて一度だけ計算された場合、その後のヒープサイズの増加に対応できません。結果として、GCアシストが提供するスキャン作業量が不足し、GCの完了が遅れたり、ヒープが過度に膨張したりする可能性があります。

したがって、`revise` メソッドをGCサイクル中に継続的に呼び出し、最新のスキャン可能なヒープサイズに基づいてアシスト比率を見直すことが不可欠であると説明されています。これにより、GCはアプリケーションのメモリ割り当てのペースに合わせて動的に調整され、ヒープサイズの制御とGCの効率的な完了が保証されます。

この変更は、コードの動作自体を変更するものではなく、その動作の背後にある重要な理由と設計思想を明確にすることで、将来のメンテナやGoランタイムの学習者にとっての理解を深めることを目的としています。

## コアとなるコードの解説

変更は `src/runtime/mgc.go` ファイル内の `revise` 関数にあります。この関数は `gcControllerState` の一部であり、ガベージコレクションの制御パラメータ、特にGCアシスト比率を再計算するために使用されます。

元のコメントは以下の通りでした。
```go
// Compute the expected scan work. This is a strict upper
// bound on the possible scan work in the current heap.
```
これは、「期待されるスキャン作業量を計算する。これは現在のヒープにおける可能なスキャン作業の厳密な上限である」と述べていました。

変更後、以下のコメントが追加されました。
```go
// Compute the expected scan work.
//
// Note that the scannable heap size is likely to increase
// during the GC cycle. This is why it's important to revise
// the assist ratio throughout the cycle: if the scannable
// heap size increases, the assist ratio based on the initial
// scannable heap size may target too little scan work.
//
// This particular estimate is a strict upper bound on the
// possible scan work in the current heap.
```

この追加されたコメントのポイントは以下の通りです。

1.  **スキャン可能なヒープサイズの増加の指摘**: 「GCサイクル中にスキャン可能なヒープサイズが増加する可能性が高い」という重要な事実を明記しています。これは、アプリケーションがGCと並行して動作し、新しいオブジェクトを割り当て続けるためです。
2.  **継続的なアシスト比率見直しの必要性**: 上記の理由から、「サイクル全体を通してアシスト比率を見直すことが重要である」と説明しています。もし初期のスキャン可能なヒープサイズに基づいてアシスト比率が計算されたままだと、ヒープサイズが増加した場合にGC作業が不足し、GCの効率が低下する可能性があるためです。
3.  **見積もりの性質の再確認**: 以前のコメントにあった「この特定の見積もりは、現在のヒープにおける可能なスキャン作業の厳密な上限である」という記述は、新しい文脈の中で再度強調されています。これは、計算されるスキャン作業量が常に十分な量を見積もっていることを示唆していますが、それでもヒープの動的な変化に対応するためには継続的な見直しが必要であるという点を補強しています。

この変更は、コードの機能的な動作には影響を与えませんが、GoのGCアシストメカニズムの設計意図と、なぜ `revise` 関数がGCサイクル中に複数回呼び出される必要があるのかという理由を、より明確に文書化しています。これにより、Goランタイムの内部動作を理解しようとする開発者にとって、非常に価値のある情報が提供されます。

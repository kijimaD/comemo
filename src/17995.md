# [インデックス 17995] ファイルの概要

このコミットは、Go言語のコンパイラ（`cmd/gc`）とCコンパイラ（`cmd/cc`）、およびアセンブラ（`cmd/5a`, `cmd/6a`, `cmd/8a`）に対する調整を含んでいます。主な目的は、`liblink`（Goリンカのライブラリ）の変更に対応し、ツールチェーン全体の連携を改善することです。具体的には、出力処理の統一、アセンブラ出力の調整、リンカへの情報伝達の強化、ジャンプターゲットの保持、Go型情報の直接的な関連付け、そして`runtime.zerovalue`の定義方法の最適化が行われています。

## 元コミット内容

`cmd/cc, cmd/gc: update compilers, assemblers for liblink changes`

このコミットは、`liblink`の変更に対応するために、コンパイラとアセンブラを更新するものです。

主な変更点は以下の通りです。
- 全てのツールにバッファリングされた標準出力を追加し、リンカコンテキストに提供します。
- アセンブラによって書き込まれる`.6`ファイル（オブジェクトファイル）において、`!`の前の余分な改行を削除し、Cコンパイラの出力と一致させます。
- `linkouthist`と`linkwritefuncs`の代わりに`linkwriteobj`を使用します。
- アセンブラとCコンパイラにおいて、`liblink`で使用するために`Prog`構造体にプログラムカウンタ（`pc`）を明示的に記録します。
- Cコンパイラにおいて、ジャンプターゲットのリンクを保持します。
- Goコンパイラ（`gsubr.c`）において、命令ストリームから再導出するのではなく、対応する`LSym*`に`gotype`を直接アタッチします。
- Goコンパイラにおいて、各コンパイルから`runtime.zerovalue`の定義を1つだけ出力します。

この変更は全体的に小さな調整で構成されています。主要な作業は`CL 39680043`で行われ、これらは相互に依存しています。

## 変更の背景

このコミットの背景には、Go言語のツールチェーン、特にコンパイラ、アセンブラ、リンカ間の連携強化と効率化があります。Goのビルドプロセスでは、ソースコードがコンパイラによって中間表現に変換され、アセンブラによってアセンブリコードが生成され、最終的にリンカによって実行可能ファイルが生成されます。この一連のプロセスにおいて、各ツールが生成するオブジェクトファイルのフォーマットや、リンカに渡される情報の構造が重要になります。

コミットメッセージにある「`liblink` changes」は、Goのリンカライブラリである`liblink`に大きな変更があったことを示唆しています。この`liblink`の変更は、おそらくリンカの内部構造、オブジェクトファイルの処理方法、またはシンボル解決のメカニズムに影響を与えたと考えられます。本コミットは、その`liblink`の変更に追従し、コンパイラとアセンブラが新しい`liblink`の要件に適合するように調整を行うものです。

特に、`linkouthist`と`linkwritefuncs`から`linkwriteobj`への移行は、オブジェクトファイルの書き出し方法が根本的に変更されたことを示しています。これは、リンカがオブジェクトファイルから情報を読み取る方法にも影響を与えるため、コンパイラとアセンブラ側での出力フォーマットの調整が必要となります。

また、`runtime.zerovalue`の定義を各コンパイルから1つだけ出力するように変更する点は、リンカが重複するシンボル定義を効率的に処理できるようにするための最適化であると考えられます。これにより、最終的なバイナリサイズが削減されたり、リンカの処理速度が向上したりする可能性があります。

全体として、このコミットはGoツールチェーンの内部的な整合性を保ち、ビルドプロセスの堅牢性と効率性を向上させるための重要な調整であると言えます。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての基本的な知識が必要です。

1.  **Go言語のツールチェーン**:
    *   **コンパイラ (`cmd/gc`, `cmd/cc`)**: Goソースコードを中間表現やアセンブリコードに変換します。`cmd/gc`はGo言語のコンパイラ、`cmd/cc`はC言語のコンパイラです。Goのランタイムや一部の標準ライブラリはC言語で書かれているため、`cmd/cc`もGoのビルドプロセスの一部として使用されます。
    *   **アセンブラ (`cmd/5a`, `cmd/6a`, `cmd/8a`)**: 各アーキテクチャ（`5a`はARM、`6a`はAMD64、`8a`はx86）のアセンブリコードをオブジェクトファイルに変換します。
    *   **リンカ (`liblink`)**: オブジェクトファイルやライブラリを結合し、実行可能なバイナリを生成します。シンボル解決、アドレスの再配置などを行います。`liblink`はGoのリンカのコアライブラリです。

2.  **オブジェクトファイル**: コンパイラやアセンブラによって生成される中間ファイルで、機械語コード、データ、シンボル情報などが含まれます。Goのオブジェクトファイルは、特定の内部フォーマットを持っています。

3.  **`Prog`構造体**: Goのコンパイラやアセンブラの内部で、単一の機械語命令や擬似命令（ディレクティブ）を表すために使用されるデータ構造です。この構造体には、命令の種類、オペランド、そして命令が配置されるプログラムカウンタ（`pc`）などの情報が含まれます。

4.  **`LSym` (Linker Symbol)**: リンカが扱うシンボル（関数名、変数名など）を表すデータ構造です。`gotype`はGoの型情報を指し、リンカが型情報に基づいて特定の処理を行う際に利用されます。

5.  **`runtime.zerovalue`**: Goのランタイムが内部的に使用する、ゼロ値を持つメモリ領域を表すシンボルです。Goでは、変数が初期化されない場合、その型のゼロ値が自動的に割り当てられます。この`runtime.zerovalue`は、そのようなゼロ値の割り当てを効率的に行うために利用されることがあります。

6.  **バッファリングされた標準出力**: プログラムが標準出力に直接書き込むのではなく、一度メモリ上のバッファにデータを蓄え、バッファがいっぱいになったり、特定の条件が満たされたりしたときにまとめて出力する方式です。これにより、I/O操作の回数を減らし、パフォーマンスを向上させることができます。

7.  **`CL` (Change List)**: Goプロジェクトで変更を管理するために使用されるGerritの用語です。Gerritはコードレビューシステムであり、各変更は`CL`として扱われます。

## 技術的詳細

このコミットは、Goのビルドツールチェーンにおける複数のコンポーネント間の連携を最適化するための技術的な調整を含んでいます。

1.  **バッファリングされた標準出力の導入**:
    *   `src/cmd/*/lex.c` (アセンブラのメインファイル) および `src/cmd/cc/lex.c`, `src/cmd/gc/lex.c` (C/Goコンパイラのメインファイル) に `Biobuf bstdout;` が追加され、`Binit(&bstdout, 1, OWRITE);` で初期化されています。
    *   これにより、コンパイラやアセンブラが標準出力に直接書き込むのではなく、`bstdout`というバッファを介して書き込むようになります。これは、I/O操作のオーバーヘッドを削減し、ビルドプロセスのパフォーマンスを向上させるための一般的な最適化手法です。
    *   `ctxt->bso = &bstdout;` のように、リンカコンテキスト (`Link* ctxt`) にこのバッファが渡されることで、リンカも同じバッファを利用して出力を行うことが可能になり、出力の一貫性が保たれます。

2.  **アセンブラ出力の調整**:
    *   `src/cmd/*/lex.c` の `assemble` 関数内で、オブジェクトファイルのヘッダ部分の出力が `Bprint(&obuf, "\\n!\\n");` から `Bprint(&obuf, "!\\n");` に変更されています。
    *   これは、アセンブラが生成するオブジェクトファイル（`.6`ファイルなど）のフォーマットをCコンパイラの出力と一致させるための調整です。余分な改行を削除することで、リンカがオブジェクトファイルをよりスムーズに処理できるようになります。

3.  **`linkwriteobj`への移行**:
    *   `src/cmd/*/lex.c` および `src/cmd/*/swt.c` (C/Goコンパイラおよびアセンブラのスイッチ文処理ファイル) において、オブジェクトファイルの書き出し処理が `linkouthist(ctxt, &obuf);` と `linkwritefuncs(ctxt, &obuf);` の組み合わせから `linkwriteobj(ctxt, &obuf);` へと変更されています。
    *   これは、`liblink`のAPIが変更され、オブジェクトファイルのヘッダ情報 (`outhist`) と関数情報 (`writefuncs`) を個別に書き出すのではなく、`linkwriteobj`という単一の関数でまとめて書き出すようになったことを示しています。これにより、リンカとのインターフェースが簡素化され、より効率的なオブジェクトファイルの生成が可能になります。
    *   これに伴い、`src/liblink/list5.c`, `src/liblink/list6.c`, `src/liblink/list8.c` という新しいファイルが追加されています。これらのファイルは、各アーキテクチャ（ARM, AMD64, x86）向けのオブジェクトファイルの内容をリスト表示するためのユーティリティ関数を含んでおり、`linkwriteobj`が内部的に利用する可能性のある、オブジェクトファイルフォーマットの詳細を定義していると考えられます。

4.  **`Prog`構造体への`pc`の明示的な記録**:
    *   `src/cmd/*/lex.c` の `outcode` 関数や `src/cmd/6c/txt.c`, `src/cmd/8c/txt.c` の `nextpc` 関数において、`Prog`構造体に `p->pc = pc;` という行が追加されています。
    *   これは、各命令が生成される際に、その命令が配置されるプログラムカウンタ（`pc`）の値を`Prog`構造体内に明示的に記録するようにしたものです。これにより、リンカ（`liblink`）が命令のアドレス情報をより正確に、かつ直接的に利用できるようになります。特に、ジャンプ命令のターゲット解決や、デバッグ情報の生成において、この`pc`情報が重要になります。

5.  **Cコンパイラにおけるジャンプターゲットリンクの保持**:
    *   `src/cmd/5c/reg.c`, `src/cmd/6c/reg.c`, `src/cmd/8c/reg.c` の `brk` 関数や `fixjmp` 関数において、ジャンプ命令のターゲットアドレスを解決する際に、`p->to.u.branch = r->s2->prog;` という行が追加されています。
    *   これは、ジャンプ命令のターゲットが別の`Prog`構造体である場合に、そのターゲット`Prog`への直接的なポインタを`p->to.u.branch`に保存するようにしたものです。これにより、リンカがジャンプ命令の解決をより効率的に行えるようになり、リンカの処理速度や正確性が向上します。

6.  **Goコンパイラにおける`gotype`の直接的な関連付け**:
    *   `src/cmd/5g/gsubr.c`, `src/cmd/6g/gsubr.c`, `src/cmd/8g/gsubr.c` の `ggloblnod` 関数において、`p->from.gotype = linksym(ngotype(nam));` が `p->from.sym->gotype = linksym(ngotype(nam));` に変更されています。
    *   これは、Goの型情報 (`gotype`) を、命令ストリームから再導出するのではなく、対応するリンカシンボル (`LSym*`) に直接アタッチするようにしたものです。これにより、型情報の処理がより直接的かつ効率的になり、コンパイル時のオーバーヘッドが削減される可能性があります。

7.  **`runtime.zerovalue`の定義の最適化**:
    *   `src/cmd/gc/obj.c` の `dumpobj` 関数において、`runtime.zerovalue`の定義が `ggloblsym(zero, zerosize, 1, 1);` のように、`zerosize`という変数を用いて行われるようになりました。
    *   また、`src/cmd/gc/reflect.c` から `ggloblsym(zero, 0, 1, 1);` の呼び出しが削除され、`src/cmd/gc/walk.c` では `zerosize` の最大値を追跡するロジックが追加されています。
    *   これは、`runtime.zerovalue`の定義が各コンパイルユニットで重複して行われるのを防ぎ、リンカが最終的なバイナリに`runtime.zerovalue`の定義を1つだけ含めるようにするための最適化です。`zerosize`は、プログラム内で必要とされるゼロ値の最大サイズを追跡し、そのサイズで`runtime.zerovalue`を一度だけ定義することで、バイナリサイズを削減し、リンカの処理を効率化します。

これらの変更は、Goのビルドツールチェーンの内部的な整合性を高め、パフォーマンスと正確性を向上させるための、細部にわたる重要な調整です。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下のファイル群に分散しています。

1.  **`src/cmd/*/lex.c` (アセンブラのメインファイル)**:
    *   `Biobuf bstdout;` の追加と初期化。
    *   `ctxt->bso = &bstdout;` によるリンカコンテキストへのバッファの提供。
    *   オブジェクトファイルヘッダの出力 (`Bprint(&obuf, "!\\n");`) の変更。
    *   `linkouthist`と`linkwritefuncs`から`linkwriteobj`への変更。
    *   `Prog`構造体への`pc`の記録 (`p->pc = pc;`)。

2.  **`src/cmd/*/list.c` (アセンブラ/コンパイラのリスト出力関連ファイル)**:
    *   `listinit`関数から、`fmtinstall`の多くの呼び出しが削除され、代わりに`listinit5()`, `listinit6()`, `listinit8()`といったアーキテクチャ固有の初期化関数が呼び出されるようになっています。これは、`liblink`に移動したリスト出力機能への委譲を示唆しています。

3.  **`src/cmd/*/reg.c` (Cコンパイラのレジスタ割り当て/ジャンプ解決関連ファイル)**:
    *   ジャンプターゲットのリンクを保持するロジックの追加 (`p->to.u.branch = r->s2->prog;`)。

4.  **`src/cmd/*/swt.c` (Cコンパイラ/アセンブラのスイッチ文処理関連ファイル)**:
    *   `linkouthist`と`linkwritefuncs`から`linkwriteobj`への変更。

5.  **`src/cmd/*/gsubr.c` (Goコンパイラのグローバルシンボル処理関連ファイル)**:
    *   `gotype`の関連付け方法の変更 (`p->from.sym->gotype = linksym(ngotype(nam));`)。

6.  **`src/cmd/gc/obj.c` (Goコンパイラのオブジェクトファイル出力関連ファイル)**:
    *   `linkouthist`と`linkwritefuncs`の呼び出しが削除され、`linkwriteobj`が追加。
    *   `runtime.zerovalue`の定義ロジックの変更。

7.  **`src/cmd/gc/walk.c` (GoコンパイラのASTウォーク関連ファイル)**:
    *   `zerosize`の最大値を追跡するロジックの追加。

8.  **`src/liblink/list5.c`, `src/liblink/list6.c`, `src/liblink/list8.c` (新規追加ファイル)**:
    *   各アーキテクチャ向けのリスト出力ユーティリティ関数を定義。これらは、以前は各コンパイラ/アセンブラの`list.c`にあった機能が`liblink`に集約されたことを示しています。

これらの変更は、Goのビルドツールチェーンの各段階で、リンカとのインターフェースや内部データ構造の扱いがどのように調整されたかを示しています。

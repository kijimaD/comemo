## 元コミット内容

このコミットが元に戻したコミット (`42fcc6fea03673eeed1447eaab78a7df9385246e`) は、Goコンパイラの内部 (`cmd/internal/gc`) において、アロケーションを発生させずに文字列を連結するための `internConcat` 関数を追加することを目的としていた。これは、コンパイラ内部での頻繁な文字列操作におけるメモリ割り当てを削減し、パフォーマンスを向上させるための最適化であったと考えられる。

## 変更の背景

パフォーマンス最適化のための `internConcat` 関数の導入は、意図された効果を発揮しなかったか、あるいは予期せぬ問題を引き起こした可能性が高い。一般的に、このような最適化のrevertは以下のいずれかの理由によるものが多い。

1.  **パフォーマンスの回帰 (Performance Regressions)**: `internConcat` が特定のシナリオでパフォーマンスを向上させたとしても、他のより一般的なシナリオでオーバーヘッドを発生させ、全体的なパフォーマンスを低下させた可能性がある。例えば、インターニングのための文字列プールの管理や既存文字列の検索にかかるコストが、アロケーション削減のメリットを上回った場合など。
2.  **メモリ使用量の増加 (Increased Memory Usage)**: 文字列のインターニングは、重複する文字列のメモリ使用量を削減する一方で、インターニングされた文字列を保持するためのプール自体が肥大化し、全体的なメモリ使用量を増加させる可能性がある。特に、インターニングされた文字列が適切に解放されない場合、メモリリークに繋がることも考えられる。
3.  **予期せぬバグや複雑性の導入 (Unexpected Bugs or Increased Complexity)**: コンパイラの低レベルな部分に新たな最適化を導入することは、デバッグが困難な微妙なバグや競合状態を引き起こす可能性がある。また、コードベースの複雑性を増し、将来のメンテナンスを困難にする場合もある。
4.  **限定的な実世界での効果 (Limited Real-World Benefit)**: ベンチマーク上では効果が見られたとしても、実際のGoアプリケーションのコンパイル時間や実行時パフォーマンスにおいて、期待されるほどの改善が見られなかった可能性がある。

このrevertは、`internConcat` がもたらすメリットが、上記のようなデメリットによって相殺された、あるいは上回られたと判断された結果であると推測される。

## 前提知識の解説

### Goコンパイラ (`cmd/internal/gc`)
Go言語の公式コンパイラは、`gc` (Go Compiler) と呼ばれる。`cmd/internal/gc` は、そのコンパイラの内部実装の一部であり、字句解析、構文解析、型チェック、コード生成など、コンパイルプロセスの様々な段階を担っている。このディレクトリ内のコードは、Go言語のプログラムを機械語に変換する上で非常に重要な役割を果たす。

### 文字列のインターニング (String Interning)
文字列のインターニングとは、プログラム内で同じ内容を持つ文字列が複数存在する場合に、それらをメモリ上で一意のオブジェクトとして管理する最適化手法である。これにより、同じ文字列が何度もメモリに割り当てられることを防ぎ、メモリ使用量を削減し、文字列の比較を高速化できる（ポインタ比較で済むため）。Go言語では、コンパイル時にリテラル文字列に対してインターニングが行われることがあるが、動的に生成される文字列に対しては、通常、明示的なインターニング機構は提供されていない。`internConcat` は、コンパイラ内部で動的に生成される文字列に対して、このインターニングの概念を適用しようとした試みであった。

### Goにおける文字列の不変性と連結
Go言語の文字列は不変 (immutable) である。これは、一度作成された文字列の内容は変更できないことを意味する。文字列を連結する (`+` 演算子など) と、既存の文字列を変更するのではなく、新しい文字列がメモリに割り当てられ、その中に連結された内容がコピーされる。このため、ループ内で頻繁に文字列連結を行うと、多くの新しい文字列が生成され、ガベージコレクションの負荷が増大し、パフォーマンスが低下する可能性がある。`strings.Builder` のような型は、この問題を効率的に解決するために提供されている。

### `testing.AllocsPerRun`
Goの標準ライブラリ `testing` パッケージに含まれる `AllocsPerRun` 関数は、指定された関数が実行される際に発生するメモリ割り当ての回数を測定するために使用される。これは、コードのパフォーマンス最適化、特にメモリ割り当ての削減を目指す際に非常に有用なツールである。`internConcat` のテスト (`lex_test.go`) では、この関数を使って `internConcat` が本当にアロケーションフリーであるかを検証しようとしていた。

### Goの型アサーションと型変換、および関連するランタイム関数
Go言語では、インターフェース型から具体的な型へ、あるいはあるインターフェース型から別のインターフェース型へ値を変換する際に「型アサーション」や「型変換」が用いられる。これらの操作は、コンパイル時に型が確定できない場合があるため、実行時にGoランタイムの特定の関数が呼び出されることがある。例えば、`i.(T)` のような型アサーションは、内部的に `assertI2T` や `assertE2I` といったランタイム関数を呼び出すことがある。これらのランタイム関数の名前は、変換元の型と変換先の型を示す文字列 (`I` for interface, `E` for empty interface, `T` for concrete type) を連結して動的に構築されることがあり、`internConcat` はその文字列構築に使用されていた。

## 技術的詳細

元々追加された `internConcat` 関数は、`src/cmd/internal/gc/lex.go` に定義されていた。この関数は可変長引数 `ss ...string` を受け取り、内部で `bufsiz` (128バイト) の固定サイズのバイトスライスを初期容量として作成し、そこに引数として渡された文字列を順に `append` していた。最終的に、このバイトスライスを `internString` 関数に渡して文字列としてインターニングし、結果を返していた。この `bufsiz` を定数にすることで、`make([]byte, 0, bufsiz)` の呼び出しがヒープアロケーションを発生させないように意図されていた。

このコミットでは、以下の変更が行われた。

1.  **`src/cmd/internal/gc/lex.go` から `internConcat` 関数の削除**:
    `internConcat` 関数自体が完全に削除された。これにより、コンパイラ内部でのアロケーションフリーな文字列連結の試みが取り消された。

2.  **`src/cmd/internal/gc/lex_test.go` の削除**:
    `internConcat` のアロケーションフリー特性を検証するためのテストファイル `lex_test.go` が削除された。このテストは `testing.AllocsPerRun` を使用して、`internConcat` がヒープアロケーションを発生させないことを確認していた。

3.  **`src/cmd/internal/gc/subr.go` の変更**:
    `Type.IET()` メソッドが `type2IET(t *Type)` 関数にリファクタリングされた。これは `internConcat` の削除とは直接関係ないが、`walk.go` での `IET()` の呼び出し方が変更されたことに伴う調整である。

4.  **`src/cmd/internal/gc/walk.go` の変更**:
    `walk.go` は、GoのAST (Abstract Syntax Tree) を走査し、コード変換や最適化を行うコンパイラの重要な部分である。このファイルでは、型アサーション (`assert*`) や型変換 (`conv*`) のランタイム関数名を構築する際に `internConcat` が使用されていた箇所が、通常の文字列連結 (`+` 演算子) に置き換えられた。

    *   `internConcat("assert", r.Left.Type.IET(), "2", r.Type.IET())`
        が
        `"assert" + type2IET(r.Left.Type) + "2" + type2IET(r.Type)`
        に変更された。
    *   `fromKind := from.Type.IET()` と `toKind := t.IET()` が
        `fromKind := type2IET(from.Type)` と `toKind := type2IET(t)`
        に変更された。
    *   `internConcat("assert", fromKind, "2", toKind, "2")`
        が
        `"assert" + fromKind + "2" + toKind + "2"`
        に変更された。
    *   `internConcat("conv", n.Left.Type.IET(), "2", n.Type.IET())`
        が
        `"conv" + type2IET(n.Left.Type) + "2" + type2IET(n.Type)`
        に変更された。

これらの変更は、`internConcat` の削除に伴い、その機能に依存していた部分を元の、あるいはよりシンプルな文字列連結方法に戻すことを目的としている。

## コアとなるコードの解説

*   **`src/cmd/internal/gc/lex.go`**:
    *   `internConcat` 関数が削除された。この関数は、複数の文字列を連結し、その結果をインターニングすることで、メモリ割り当てを削減しようと試みていた。この削除は、この最適化が期待通りの効果を発揮しなかったか、あるいは問題を引き起こしたことを示唆している。

*   **`src/cmd/internal/gc/lex_test.go`**:
    *   `TestInternConcat` を含むテストファイル全体が削除された。このテストは `testing.AllocsPerRun` を使用して `internConcat` がアロケーションフリーであることを検証していたため、関数が削除されたことに伴い、テストも不要となった。

*   **`src/cmd/internal/gc/subr.go`**:
    *   `Type` 型のメソッドであった `IET()` が、`type2IET(t *Type)` という独立した関数に変更された。これは、`walk.go` での呼び出し元の変更に合わせて行われたリファクタリングであり、機能的な変更ではない。`IET` は "Interface", "Empty interface", "Type" の略で、型アサーションや型変換のランタイム関数名を構築する際に、型の種類を示すために使われる文字列を返す。

*   **`src/cmd/internal/gc/walk.go`**:
    *   このファイルでは、型アサーション (`assert*`) や型変換 (`conv*`) のランタイム関数名を動的に構築する際に `internConcat` を使用していた箇所が、Goの通常の文字列連結演算子 (`+`) に置き換えられた。
    *   例えば、`internConcat("assert", r.Left.Type.IET(), "2", r.Type.IET())` は、`"assert" + type2IET(r.Left.Type) + "2" + type2IET(r.Type)` となった。
    *   これは、`internConcat` が削除されたため、その代替として最も直接的でシンプルな文字列連結方法に戻したことを意味する。この変更により、これらの文字列連結操作で再びメモリ割り当てが発生する可能性があるが、`internConcat` の導入による問題が解消されることを優先したと考えられる。

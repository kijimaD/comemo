このコミットは、Goコンパイラのx86アーキテクチャ向けバックエンドにおける関数プロローグの生成ロジックを改善し、静的分岐予測の効率を高めることを目的としています。具体的には、スタックの拡張が必要ない場合のコードパスを「予測されるパス」として扱うように分岐命令の順序を変更することで、全体的なパフォーマンスの向上を図っています。

## 変更の背景

このコミットの背景には、現代のCPUが持つ「静的分岐予測 (Static Branch Prediction)」という最適化技術があります。CPUはプログラムの実行中に次にどの命令が実行されるかを予測し、パイプラインを効率的に埋めることでパフォーマンスを向上させます。特に条件分岐（`if`文など）においては、どちらのパスが実行されるかを予測し、予測が当たれば高速に処理を進められますが、外れるとパイプラインのフラッシュ（予測ミスのペナルティ）が発生し、性能が低下します。

静的分岐予測の一般的なヒューリスティックの一つに、「前方分岐は取られない (forward branches aren't taken)」というものがあります。これは、コード中でジャンプ先が現在の命令アドレスよりも大きい（つまり、コードのより後方にある）分岐命令は、通常は実行されないと予測される傾向があるという経験則に基づいています。

Go言語のランタイムでは、各関数のプロローグ（関数が呼び出された直後の初期処理）で、必要なスタック領域が現在利用可能かどうかをチェックします。もしスタックが足りない場合は、`runtime.morestack`関数を呼び出してスタックを拡張します。しかし、ほとんどの関数呼び出しではスタックの拡張は不要であり、`morestack`が呼び出されることは稀です。

変更前のコードでは、スタックチェックの結果、スタックが足りている場合に「前方分岐」で通常の関数本体の処理にジャンプし、足りない場合に「後方分岐」またはフォールスルーで`morestack`を呼び出すような構造になっていました。この構造は、CPUの「前方分岐は取られない」という静的予測と逆の動作をするため、スタックが足りている（＝分岐が取られる）という頻繁に発生するケースで予測ミスを誘発し、パフォーマンスの低下を招く可能性がありました。

このコミットは、この問題を解決するために、スタックが足りている場合のパスをフォールスルー（分岐しない）とし、スタックが足りない場合にのみ前方分岐で`morestack`を呼び出すようにアセンブリコードの生成順序と分岐命令を変更しました。これにより、「スタックが足りない（＝分岐が取られる）」という稀なケースが前方分岐となり、CPUの静的分岐予測のヒューリスティックと一致するようになり、予測ミスが減少し、全体的なパフォーマンスが向上することが期待されます。

## 前提知識の解説

### 1. Go言語のスタック管理と `morestack`

Go言語は、実行時に動的にサイズが変化する「可変長スタック（contiguous stack）」を採用しています。これは、C言語のような固定サイズのスタックとは異なり、関数呼び出し時に必要なスタック領域が不足した場合、ランタイムが自動的にスタックを拡張（または新しいより大きなスタックにコピー）する仕組みです。

このスタック拡張のメカニズムの中心となるのが `runtime.morestack` (または `runtime.morestack_noctxt`, `runtime.morestackc`) 関数です。Goの関数が呼び出される際、その関数のプロローグで、必要なスタックフレームサイズが現在のスタックの残量を超えていないかチェックされます。もし不足している場合、`morestack`関数が呼び出され、スタックの拡張処理が行われます。スタックが拡張された後、元の関数は最初から再実行されます。

### 2. CPUの静的分岐予測 (Static Branch Prediction)

現代の高性能CPUは、命令パイプラインを最大限に活用するために、次に実行される命令を事前に予測してフェッチ・デコードします。条件分岐命令（`if`文、`for`ループなど）に遭遇した場合、CPUはどちらの分岐パスが実行されるかを予測する必要があります。この予測が成功すれば、パイプラインは途切れることなく命令を処理し続けられますが、予測が外れると、誤ってフェッチ・デコードされた命令を破棄し、正しいパスの命令を最初からフェッチし直す必要があり、これが大きな性能ペナルティ（「分岐予測ミス」）となります。

分岐予測には大きく分けて「動的予測」と「静的予測」があります。
*   **動的予測**: 過去の分岐履歴に基づいて予測を行います。実行時に学習し、適応します。
*   **静的予測**: コードの構造や分岐命令の種類に基づいて、コンパイル時またはハードウェア設計時に決められたルールに従って予測を行います。動的予測器がまだ学習していない初期段階や、予測履歴が利用できない場合に用いられます。

このコミットで言及されている「前方分岐は取られない (forward branches aren't taken)」は、静的予測の一般的なヒューリスティックの一つです。これは、プログラムの制御フローが通常は順方向に進むという経験則に基づいています。例えば、エラー処理や稀なケースへのジャンプは、コードの後方に配置され、通常は実行されないと予測されることが多いです。

### 3. x86アセンブリの基本命令

*   **`CMPQ` (Compare Quadword)**: 2つの64ビット値を比較し、フラグレジスタ（ZF, CF, SF, OFなど）を設定します。
*   **`SP` (Stack Pointer)**: スタックの現在のトップを指すレジスタ。
*   **`GS` (Segment Register)**: Goランタイムでは、`GS`レジスタが現在のgoroutineの`g`構造体へのポインタを指すように設定されています。`GS:0x8a0`のような表記は、`g`構造体内の特定のオフセットにある値（この場合はスタックの境界情報）にアクセスしていることを示します。
*   **`JA` (Jump if Above)**: 比較結果が「より大きい」場合にジャンプします（符号なし比較）。
*   **`JBE` (Jump if Below or Equal)**: 比較結果が「より小さいか等しい」場合にジャンプします（符号なし比較）。
*   **`SUBQ` (Subtract Quadword)**: 64ビット値を減算します。スタックフレームを確保するために`SP`から値を引く際に使用されます。
*   **`ADDQ` (Add Quadword)**: 64ビット値を加算します。スタックフレームを解放するために`SP`に値を加える際に使用されます。
*   **`CALL` (Call)**: サブルーチンを呼び出します。リターンアドレスをスタックにプッシュし、指定されたアドレスにジャンプします。
*   **`JMP` (Jump)**: 無条件に指定されたアドレスにジャンプします。
*   **`RET` (Return)**: サブルーチンから戻ります。スタックからリターンアドレスをポップし、そのアドレスにジャンプします。

### 4. Goコンパイラのバックエンドと `obj.Prog`

Goコンパイラは、ソースコードを中間表現に変換した後、各アーキテクチャ（x86, ARMなど）固有のバックエンドでアセンブリコードを生成します。`cmd/internal/obj/x86`パッケージは、x86アーキテクチャ向けのアセンブリコード生成を担当する部分です。

`obj.Prog`は、Goコンパイラのバックエンドでアセンブリ命令を表現するためのデータ構造です。各`obj.Prog`インスタンスは、アセンブリ命令の種類 (`As`フィールド)、オペランド (`From`, `To`フィールド)、および命令間のリンクリスト (`Link`, `Pcond`フィールド) などの情報を含みます。コンパイラはこれらの`obj.Prog`オブジェクトを操作して、最終的なアセンブリコードを構築します。

*   `p.As`: 命令のオペコード（例: `ACMPQ`, `AJHI`, `ACALL`）。
*   `p.To.Type`: オペランドのタイプ（例: `obj.TYPE_BRANCH`で分岐先を示す）。
*   `p.To.Sym`: 呼び出し先やジャンプ先のシンボル（関数名など）。
*   `p.Link`: 次の命令へのポインタ。
*   `p.Pcond`: 条件分岐命令の場合、分岐が成功した場合のジャンプ先命令へのポインタ。

## 技術的詳細

このコミットの核心は、Go関数のプロローグにおけるスタックチェックのアセンブリコードのフローを変更し、CPUの静的分岐予測を最適化することです。

### 変更前のアセンブリコードのフロー

```
        CMPQ 0x10(CX), SP  // スタックポインタSPとスタック境界を比較
        JA 0x2016          // SPが境界より大きい（スタックが足りている）場合、0x2016へジャンプ
        CALL runtime.morestack_noctxt(SB) // スタックが足りない場合、morestackを呼び出す
        JMP main.f(SB)     // morestackから戻ったら関数の先頭に戻って再チェック
0x2016: SUBQ $0x80, SP     // スタックが足りている場合、スタックフレームを確保
        ... (関数本体の処理)
```
変更前は、`CMPQ`命令の後に`JA 0x2016`という条件分岐命令があります。`JA`は"Jump if Above"（より大きい場合にジャンプ）を意味します。
*   **スタックが足りている場合**: `SP`がスタック境界より大きいので、`JA`命令が**取られ**、`0x2016`（スタックフレーム確保の開始点）へジャンプします。この`JA`は前方分岐（`0x200d`から`0x2016`へ）であり、CPUの静的予測「前方分岐は取られない」に反するため、予測ミスが発生する可能性がありました。
*   **スタックが足りない場合**: `JA`命令は**取られず**、フォールスルーして`CALL runtime.morestack_noctxt`が実行されます。これは稀なケースであり、予測ミスは発生しにくいですが、頻繁に発生する「スタックが足りている」ケースでの予測ミスが問題でした。

### 変更後のアセンブリコードのフロー

```
        CMPQ 0x10(CX), SP  // スタックポインタSPとスタック境界を比較
        JBE 0x2029         // SPが境界以下（スタックが足りない）場合、0x2029へジャンプ
        SUBQ $0x80, SP     // スタックが足りている場合、スタックフレームを確保
        ... (関数本体の処理)
        RET                // 関数終了
0x2029: CALL runtime.morestack_noctxt(SB) // スタックが足りない場合、morestackを呼び出す
        JMP main.f(SB)     // morestackから戻ったら関数の先頭に戻って再チェック
```
変更後では、`CMPQ`命令の後に`JBE 0x2029`という条件分岐命令があります。`JBE`は"Jump if Below or Equal"（より小さいか等しい場合にジャンプ）を意味します。
*   **スタックが足りている場合**: `SP`がスタック境界より大きいので、`JBE`命令は**取られず**、フォールスルーして`SUBQ $0x80, SP`（スタックフレーム確保）が実行されます。これは最も頻繁に発生するパスであり、分岐命令が取られないため、CPUの静的予測「前方分岐は取られない」と一致し、予測ミスが回避されます。
*   **スタックが足りない場合**: `SP`がスタック境界以下なので、`JBE`命令が**取られ**、`0x2029`（`CALL runtime.morestack_noctxt`の開始点）へジャンプします。この`JBE`は前方分岐（`0x200d`から`0x2029`へ）であり、CPUの静的予測「前方分岐は取られない」と一致します。スタックが足りないケースは稀であるため、この分岐が取られることは少なく、予測ミスも稀になります。

このように、分岐命令の種類とコードの配置を入れ替えることで、最も頻繁に実行される「スタックが足りている」パスが分岐予測ミスを起こさないように最適化されています。

### `obj.Prog`リンクリスト操作の変更

`stacksplit`関数は、`obj.Prog`構造体のリンクリストを操作してアセンブリ命令を生成します。変更前は、`stacksplit`関数は`jmpok`という`**obj.Prog`型の引数を受け取り、スタックチェックが成功した場合にジャンプすべき命令へのポインタを`q`という`obj.Prog`に設定していました。

変更後は、`jmpok`引数が削除され、`stacksplit`関数内で直接`JLS` (Jump if Less or Equal, `JBE`に相当) 命令を生成し、その`Pcond`フィールド（条件分岐のジャンプ先）を`morestack`呼び出しの命令に設定しています。これにより、`stacksplit`関数がより自己完結的にスタックチェックの制御フローを構築できるようになりました。

具体的には、`obj.Appendp`を使って命令をリンクリストに追加し、`jls.Pcond = call`のように、条件分岐命令のジャンプ先を`morestack`を呼び出す`CALL`命令に設定しています。また、`jmp`命令のジャンプ先を関数の先頭（`ctxt.Cursym.Text.Link`）に設定することで、`morestack`から戻った後に再度スタックチェックから処理を再開するようにしています。

## コアとなるコードの解説

`stacksplit`関数は、Goコンパイラのx86バックエンドにおいて、関数のプロローグにスタックチェックのコードを挿入する役割を担っています。このコミットによる変更は、この`stacksplit`関数が生成するアセンブリ命令の構造を根本的に見直したものです。

変更前は、`stacksplit`はスタックチェックが成功した場合のジャンプ先を`jmpok`引数を通じて呼び出し元に伝えていました。しかし、変更後は`jmpok`引数を廃止し、`stacksplit`関数内でスタックチェックの分岐ロジック全体を完結させるようにしました。

新しい`stacksplit`関数は以下の手順で命令を生成します。

1.  **`jls`命令の生成**:
    `jls := obj.Appendp(ctxt, p)` で新しい`obj.Prog` (`jls`) を作成し、`jls.As = AJLS` と設定します。これは`JBE`命令に相当し、「スタックポインタが境界以下（スタックが足りない）であればジャンプする」という条件分岐を表現します。この命令は、スタックチェックの比較命令の直後に配置されます。

2.  **`morestack`呼び出しと`JMP`命令の生成**:
    `morestack`呼び出し (`CALL runtime.morestack_noctxt`など) と、その後の関数先頭への無条件ジャンプ (`JMP main.f(SB)`) は、関数のアセンブリコードの**末尾**に追加されます。これは、`for last = ctxt.Cursym.Text; last.Link != nil; last = last.Link {}` ループで現在の関数の最後の命令 (`last`) を見つけ、その後に `call` と `jmp` 命令を `obj.Appendp` で追加することで実現されます。
    `morestack`関数の選択 (`runtime.morestack`, `runtime.morestackc`, `runtime.morestack_noctxt`) は、関数のプロパティ (`Cfunc`, `NEEDCTXT`) に応じて行われます。
    `jmp.Pcond = ctxt.Cursym.Text.Link` は、`morestack`から戻った後に、関数の最初のアセンブリ命令（スタックチェックの比較命令）にジャンプして、スタックチェックを再実行することを意味します。

3.  **分岐先のリンク**:
    `jls.Pcond = call` という行が重要です。これは、`JLS`命令が条件を満たした場合（スタックが足りない場合）に、先ほど関数の末尾に追加した`morestack`を呼び出す`call`命令にジャンプするように設定します。

この変更により、スタックが足りている（一般的な）ケースでは`JLS`命令が取られず、そのままフォールスルーしてスタックフレームの確保と関数本体の実行に進みます。スタックが足りない（稀な）ケースでのみ`JLS`命令が取られ、関数の末尾に配置された`morestack`呼び出しにジャンプします。この構造は、CPUの静的分岐予測のヒューリスティックと一致し、予測ミスを最小限に抑えることで、Goプログラムのパフォーマンス向上に貢献します。

## 変更の背景

このコミットの背景には、現代のCPUが持つ「静的分岐予測 (Static Branch Prediction)」という最適化技術があります。CPUはプログラムの実行中に次にどの命令が実行されるかを予測し、パイプラインを効率的に埋めることでパフォーマンスを向上させます。特に条件分岐（`if`文など）においては、どちらのパスが実行されるかを予測し、予測が当たれば高速に処理を進められますが、外れるとパイプラインのフラッシュ（予測ミスのペナルティ）が発生し、性能が低下します。

静的分岐予測の一般的なヒューリスティックの一つに、「前方分岐は取られない (forward branches aren't taken)」というものがあります。これは、コード中でジャンプ先が現在の命令アドレスよりも大きい（つまり、コードのより後方にある）分岐命令は、通常は実行されないと予測される傾向があるという経験則に基づいています。

Go言語のランタイムでは、各関数のプロローグ（関数が呼び出された直後の初期処理）で、必要なスタック領域が現在利用可能かどうかをチェックします。もしスタックが足りない場合は、`runtime.morestack`関数を呼び出してスタックを拡張します。しかし、ほとんどの関数呼び出しではスタックの拡張は不要であり、`morestack`が呼び出されることは稀です。

変更前のコードでは、スタックチェックの結果、スタックが足りている場合に「前方分岐」で通常の関数本体の処理にジャンプし、足りない場合に「後方分岐」またはフォールスルーで`morestack`を呼び出すような構造になっていました。この構造は、CPUの「前方分岐は取られない」という静的予測と逆の動作をするため、スタックが足りている（＝分岐が取られる）という頻繁に発生するケースで予測ミスを誘発し、パフォーマンスの低下を招く可能性がありました。

このコミットは、この問題を解決するために、スタックが足りている場合のパスをフォールスルー（分岐しない）とし、スタックが足りない場合にのみ前方分岐で`morestack`を呼び出すようにアセンブリコードの生成順序と分岐命令を変更しました。これにより、「スタックが足りない（＝分岐が取られる）」という稀なケースが前方分岐となり、CPUの静的分岐予測のヒューリスティックと一致するようになり、予測ミスが減少し、全体的なパフォーマンスが向上することが期待されます。

## 前提知識の解説

### 1. Go言語のスタック管理と `morestack`

Go言語は、実行時に動的にサイズが変化する「可変長スタック（contiguous stack）」を採用しています。これは、C言語のような固定サイズのスタックとは異なり、関数呼び出し時に必要なスタック領域が不足した場合、ランタイムが自動的にスタックを拡張（または新しいより大きなスタックにコピー）する仕組みです。

このスタック拡張のメカニズムの中心となるのが `runtime.morestack` (または `runtime.morestack_noctxt`, `runtime.morestackc`) 関数です。Goの関数が呼び出される際、その関数のプロローグで、必要なスタックフレームサイズが現在のスタックの残量を超えていないかチェックされます。もし不足している場合、`morestack`関数が呼び出され、スタックの拡張処理が行われます。スタックが拡張された後、元の関数は最初から再実行されます。

### 2. CPUの静的分岐予測 (Static Branch Prediction)

現代の高性能CPUは、命令パイプラインを最大限に活用するために、次に実行される命令を事前に予測してフェッチ・デコードします。条件分岐命令（`if`文、`for`ループなど）に遭遇した場合、CPUはどちらの分岐パスが実行されるかを予測する必要があります。この予測が成功すれば、パイプラインは途切れることなく命令を処理し続けられますが、予測が外れると、誤ってフェッチ・デコードされた命令を破棄し、正しいパスの命令を最初からフェッチし直す必要があり、これが大きな性能ペナルティ（「分岐予測ミス」）となります。

分岐予測には大きく分けて「動的予測」と「静的予測」があります。
*   **動的予測**: 過去の分岐履歴に基づいて予測を行います。実行時に学習し、適応します。
*   **静的予測**: コードの構造や分岐命令の種類に基づいて、コンパイル時またはハードウェア設計時に決められたルールに従って予測を行います。動的予測器がまだ学習していない初期段階や、予測履歴が利用できない場合に用いられます。

このコミットで言及されている「前方分岐は取られない (forward branches aren't taken)」は、静的予測の一般的なヒューリスティックの一つです。これは、プログラムの制御フローが通常は順方向に進むという経験則に基づいています。例えば、エラー処理や稀なケースへのジャンプは、コードの後方に配置され、通常は実行されないと予測されることが多いです。

### 3. x86アセンブリの基本命令

*   **`CMPQ` (Compare Quadword)**: 2つの64ビット値を比較し、フラグレジスタ（ZF, CF, SF, OFなど）を設定します。
*   **`SP` (Stack Pointer)**: スタックの現在のトップを指すレジスタ。
*   **`GS` (Segment Register)**: Goランタイムでは、`GS`レジスタが現在のgoroutineの`g`構造体へのポインタを指すように設定されています。`GS:0x8a0`のような表記は、`g`構造体内の特定のオフセットにある値（この場合はスタックの境界情報）にアクセスしていることを示します。
*   **`JA` (Jump if Above)**: 比較結果が「より大きい」場合にジャンプします（符号なし比較）。
*   **`JBE` (Jump if Below or Equal)**: 比較結果が「より小さいか等しい」場合にジャンプします（符号なし比較）。
*   **`SUBQ` (Subtract Quadword)**: 64ビット値を減算します。スタックフレームを確保するために`SP`から値を引く際に使用されます。
*   **`ADDQ` (Add Quadword)**: 64ビット値を加算します。スタックフレームを解放するために`SP`に値を加える際に使用されます。
*   **`CALL` (Call)**: サブルーチンを呼び出します。リターンアドレスをスタックにプッシュし、指定されたアドレスにジャンプします。
*   **`JMP` (Jump)**: 無条件に指定されたアドレスにジャンプします。
*   **`RET` (Return)**: サブルーチンから戻ります。スタックからリターンアドレスをポップし、そのアドレスにジャンプします。

### 4. Goコンパイラのバックエンドと `obj.Prog`

Goコンパイラは、ソースコードを中間表現に変換した後、各アーキテクチャ（x86, ARMなど）固有のバックエンドでアセンブリコードを生成します。`cmd/internal/obj/x86`パッケージは、x86アーキテクチャ向けのアセンブリコード生成を担当する部分です。

`obj.Prog`は、Goコンパイラのバックエンドでアセンブリ命令を表現するためのデータ構造です。各`obj.Prog`インスタンスは、アセンブリ命令の種類 (`As`フィールド)、オペランド (`From`, `To`フィールド)、および命令間のリンクリスト (`Link`, `Pcond`フィールド) などの情報を含みます。コンパイラはこれらの`obj.Prog`オブジェクトを操作して、最終的なアセンブリコードを構築します。

*   `p.As`: 命令のオペコード（例: `ACMPQ`, `AJHI`, `ACALL`）。
*   `p.To.Type`: オペランドのタイプ（例: `obj.TYPE_BRANCH`で分岐先を示す）。
*   `p.To.Sym`: 呼び出し先やジャンプ先のシンボル（関数名など）。
*   `p.Link`: 次の命令へのポインタ。
*   `p.Pcond`: 条件分岐命令の場合、分岐が成功した場合のジャンプ先命令へのポインタ。

## 技術的詳細

このコミットの核心は、Go関数のプロローグにおけるスタックチェックのアセンブリコードのフローを変更し、CPUの静的分岐予測を最適化することです。

### 変更前のアセンブリコードのフロー

```
        CMPQ 0x10(CX), SP  // スタックポインタSPとスタック境界を比較
        JA 0x2016          // SPが境界より大きい（スタックが足りている）場合、0x2016へジャンプ
        CALL runtime.morestack_noctxt(SB) // スタックが足りない場合、morestackを呼び出す
        JMP main.f(SB)     // morestackから戻ったら関数の先頭に戻って再チェック
0x2016: SUBQ $0x80, SP     // スタックが足りている場合、スタックフレームを確保
        ... (関数本体の処理)
```
変更前は、`CMPQ`命令の後に`JA 0x2016`という条件分岐命令があります。`JA`は"Jump if Above"（より大きい場合にジャンプ）を意味します。
*   **スタックが足りている場合**: `SP`がスタック境界より大きいので、`JA`命令が**取られ**、`0x2016`（スタックフレーム確保の開始点）へジャンプします。この`JA`は前方分岐（`0x200d`から`0x2016`へ）であり、CPUの静的予測「前方分岐は取られない」に反するため、予測ミスが発生する可能性がありました。
*   **スタックが足りない場合**: `JA`命令は**取られず**、フォールスルーして`CALL runtime.morestack_noctxt`が実行されます。これは稀なケースであり、予測ミスは発生しにくいですが、頻繁に発生する「スタックが足りている」ケースでの予測ミスが問題でした。

### 変更後のアセンブリコードのフロー

```
        CMPQ 0x10(CX), SP  // スタックポインタSPとスタック境界を比較
        JBE 0x2029         // SPが境界以下（スタックが足りない）場合、0x2029へジャンプ
        SUBQ $0x80, SP     // スタックが足りている場合、スタックフレームを確保
        ... (関数本体の処理)
        RET                // 関数終了
0x2029: CALL runtime.morestack_noctxt(SB) // スタックが足りない場合、morestackを呼び出す
        JMP main.f(SB)     // morestackから戻ったら関数の先頭に戻って再チェック
```
変更後では、`CMPQ`命令の後に`JBE 0x2029`という条件分岐命令があります。`JBE`は"Jump if Below or Equal"（より小さいか等しい場合にジャンプ）を意味します。
*   **スタックが足りている場合**: `SP`がスタック境界より大きいので、`JBE`命令は**取られず**、フォールスルーして`SUBQ $0x80, SP`（スタックフレーム確保）が実行されます。これは最も頻繁に発生するパスであり、分岐命令が取られないため、CPUの静的予測「前方分岐は取られない」と一致し、予測ミスが回避されます。
*   **スタックが足りない場合**: `SP`がスタック境界以下なので、`JBE`命令が**取られ**、`0x2029`（`CALL runtime.morestack_noctxt`の開始点）へジャンプします。この`JBE`は前方分岐（`0x200d`から`0x2029`へ）であり、CPUの静的予測「前方分岐は取られない」と一致します。スタックが足りないケースは稀であるため、この分岐が取られることは少なく、予測ミスも稀になります。

このように、分岐命令の種類とコードの配置を入れ替えることで、最も頻繁に実行される「スタックが足りている」パスが分岐予測ミスを起こさないように最適化されています。

### `obj.Prog`リンクリスト操作の変更

`stacksplit`関数は、`obj.Prog`構造体のリンクリストを操作してアセンブリ命令を生成します。変更前は、`stacksplit`関数は`jmpok`という`**obj.Prog`型の引数を受け取り、スタックチェックが成功した場合にジャンプすべき命令へのポインタを`q`という`obj.Prog`に設定していました。

変更後は、`jmpok`引数が削除され、`stacksplit`関数内で直接`JLS` (Jump if Less or Equal, `JBE`に相当) 命令を生成し、その`Pcond`フィールド（条件分岐のジャンプ先）を`morestack`呼び出しの命令に設定しています。これにより、`stacksplit`関数がより自己完結的にスタックチェックの制御フローを構築できるようになりました。

具体的には、`obj.Appendp`を使って命令をリンクリストに追加し、`jls.Pcond = call`のように、条件分岐命令のジャンプ先を`morestack`を呼び出す`CALL`命令に設定しています。また、`jmp`命令のジャンプ先を関数の先頭（`ctxt.Cursym.Text.Link`）に設定することで、`morestack`から戻った後に再度スタックチェックから処理を再開するようにしています。

## コアとなるコードの解説

`stacksplit`関数は、Goコンパイラのx86バックエンドにおいて、関数のプロローグにスタックチェックのコードを挿入する役割を担っています。このコミットによる変更は、この`stacksplit`関数が生成するアセンブリ命令の構造を根本的に見直したものです。

変更前は、`stacksplit`はスタックチェックが成功した場合のジャンプ先を`jmpok`引数を通じて呼び出し元に伝えていました。しかし、変更後は`jmpok`引数を廃止し、`stacksplit`関数内でスタックチェックの分岐ロジック全体を完結させるようにしました。

新しい`stacksplit`関数は以下の手順で命令を生成します。

1.  **`jls`命令の生成**:
    `jls := obj.Appendp(ctxt, p)` で新しい`obj.Prog` (`jls`) を作成し、`jls.As = AJLS` と設定します。これは`JBE`命令に相当し、「スタックポインタが境界以下（スタックが足りない）であればジャンプする」という条件分岐を表現します。この命令は、スタックチェックの比較命令の直後に配置されます。

2.  **`morestack`呼び出しと`JMP`命令の生成**:
    `morestack`呼び出し (`CALL runtime.morestack_noctxt`など) と、その後の関数先頭への無条件ジャンプ (`JMP main.f(SB)`) は、関数のアセンブリコードの**末尾**に追加されます。これは、`for last = ctxt.Cursym.Text; last.Link != nil; last = last.Link {}` ループで現在の関数の最後の命令 (`last`) を見つけ、その後に `call` と `jmp` 命令を `obj.Appendp` で追加することで実現されます。
    `morestack`関数の選択 (`runtime.morestack`, `runtime.morestackc`, `runtime.morestack_noctxt`) は、関数のプロパティ (`Cfunc`, `NEEDCTXT`) に応じて行われます。
    `jmp.Pcond = ctxt.Cursym.Text.Link` は、`morestack`から戻った後に、関数の最初のアセンブリ命令（スタックチェックの比較命令）にジャンプして、スタックチェックを再実行することを意味します。

3.  **分岐先のリンク**:
    `jls.Pcond = call` という行が重要です。これは、`JLS`命令が条件を満たした場合（スタックが足りない場合）に、先ほど関数の末尾に追加した`morestack`を呼び出す`call`命令にジャンプするように設定します。

この変更により、スタックが足りている（一般的な）ケースでは`JLS`命令が取られず、そのままフォールスルーしてスタックフレームの確保と関数本体の実行に進みます。スタックが足りない（稀な）ケースでのみ`JLS`命令が取られ、関数の末尾に配置された`morestack`呼び出しにジャンプします。この構造は、CPUの静的分岐予測のヒューリスティックと一致し、予測ミスを最小限に抑えることで、Goプログラムのパフォーマンス向上に貢献します。

# [インデックス 23939] ファイルの概要

このコミットは、Go言語のコードフォーマッタである `go/format` における、`//line` ディレクティブを含む部分的なGoコードのフォーマットに関するコーナーケースのバグを修正します。具体的には、ステートメントリストをフォーマットする際に、`//line` コメントが正しく処理されず、最終的な出力が崩れる問題を解決しています。

## 元コミット内容

Go言語のコードフォーマッタ `go/format` は、ステートメントのリストのような部分的なGoコードに対しても適用できます。この際、パーサーが正しく処理できるように、これらのステートメントは一時的に関数定義でラップされ、フォーマット後に元の形に戻されます。

しかし、ステートメント内に `//line` アノテーションが含まれている場合、問題が発生することがありました。これは、プリンタが最終的な `}` の前にすべてのコメントをフラッシュしないために起こります。例えば、`"\ta()\n//line :1"` をフォーマットすると、誤って `"\ta() }\n\n//line"` のような出力になっていました。

このコミットでは、`}` の前にコメントが確実にフラッシュされるように、コードのラッピング/アンラッピング処理が調整されています。

この変更は Issue #11276 を修正します。

## 変更の背景

`go/format` (gofmt) は、Go言語のコードを標準的なスタイルに自動的にフォーマットするツールです。このツールは、完全なGoプログラムだけでなく、Goのステートメントのリストのような部分的なコードスニペットもフォーマットできる柔軟性を持っています。部分的なコードをフォーマットするために、`go/format` は内部的にそのコードを有効なGoプログラムのコンテキスト（例えば、`package p; func _() { ... }` のような関数ボディ）に一時的にラップしてからパースし、抽象構文木 (AST) を構築します。その後、ASTを再構築してフォーマットされたコードを生成し、最後にラッピングを解除して元の部分的なコードを返します。

このプロセスにおいて、`//line` ディレクティブ（または `//line` アノテーション）が問題を引き起こしていました。`//line` ディレクティブは、コンパイラやツールに対して、その後のコードの行番号やファイル名を変更するように指示する特殊なコメントです。これは、コード生成ツールが生成したコードのデバッグ情報を元のソースコードにマッピングする際によく使用されます。

問題は、`go/format` が部分的なコードをラップする際に、`//line` ディレクティブを含むコメントが、一時的に追加された関数定義の閉じ括弧 `}` の直前で適切に「フラッシュ」されないことにありました。Goのパーサーやプリンタは、コメントを特定のトークンやノードに関連付けて処理しますが、この特定のコーナーケースでは、`}` の直前のコメントが正しく出力ストリームに書き出されず、`}` がコメントの前に来てしまったり、コメントが意図しない位置に移動したりする結果となりました。これにより、フォーマットされたコードが構文的に不正になったり、意図しない出力になったりするバグが発生していました。

このコミットは、この `//line` ディレクティブと部分的なコードのラッピングが絡む特定のバグを修正することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびツールに関する知識が必要です。

1.  **`go/format` (gofmt)**:
    *   Go言語の公式なコードフォーマッタです。Goのソースコードを解析し、標準的なスタイルガイドに従って自動的に整形します。
    *   内部的には、ソースコードをパースして抽象構文木 (AST) を構築し、そのASTを再構築してフォーマットされたコードを生成します。
    *   部分的なGoコード（例: ステートメントのリスト、式）もフォーマットできます。この場合、`go/format` は内部的にそのコードを有効なGoプログラムのコンテキスト（例: `package p; func _() { ... }`）にラップしてから処理します。

2.  **`//line` ディレクティブ**:
    *   Go言語における特殊なコメント形式で、コンパイラやデバッグツールに対して、その後のコードのファイル名と行番号の情報を変更するように指示します。
    *   書式は `//line filename:line` または `//line :line` です。
    *   主に、`yacc` や `protobuf` のようなツールによって生成されたGoコードで、生成元となる元のソースファイルの行番号をデバッグ情報として保持するために使用されます。これにより、生成されたコードでエラーが発生した場合でも、元のソースファイルの正確な位置を報告できます。

3.  **Goパーサーとプリンタのコメント処理**:
    *   Goのパーサー (`go/parser`) は、ソースコードを解析する際にコメントも読み込み、ASTの一部として保持します。
    *   Goのプリンタ (`go/printer`) は、ASTをソースコードに変換する際に、ASTに付随するコメントを適切な位置に出力します。
    *   コメントの「フラッシュ」とは、プリンタがバッファリングしているコメントを、現在の出力位置に書き出す処理を指します。特定の構文要素（例: 閉じ括弧 `}`）の直前でコメントが適切にフラッシュされないと、コメントが意図しない位置に移動したり、失われたりする可能性があります。

4.  **抽象構文木 (AST)**:
    *   ソースコードの構造を木構造で表現したものです。Goのコンパイラやツールは、ソースコードを直接操作するのではなく、ASTを操作することで、解析、変換、最適化、コード生成などを行います。

これらの知識が、`go/format` がどのように動作し、`//line` ディレクティブがどのように処理され、そしてなぜこのバグが発生したのかを理解する上で不可欠です。

## 技術的詳細

このコミットの技術的詳細は、`go/format` が部分的なGoコードを処理する際の内部メカニズムと、`//line` ディレクティブの特殊な振る舞いに焦点を当てています。

`go/format` の `Parse` 関数は、与えられたソースコードが完全なGoファイルではない場合（例えば、ステートメントのリストや式の場合）、それをパース可能な形式に変換するために、一時的にGoの関数ボディでラップします。具体的には、元のソースコード `src` を `package p; func _() {` と `}` で囲みます。

変更前のコードでは、このラッピングは以下のようになっていました。
`fsrc := append(append([]byte("package p; func _() {"), src...), '\n', '}')`
これは、元のコードの後に改行 `\n` と閉じ括弧 `}` を追加していました。

問題は、`src` の末尾に `//line` ディレクティブのようなコメントがある場合、`go/printer` が `}` の直前でこれらのコメントを適切にフラッシュしないことがあった点です。これにより、`}` がコメントの前に出力されてしまい、フォーマットが崩れる結果となりました。例えば、`a()\n//line :1` という入力に対して、`a() }\n\n//line` のような不正な出力が生成されていました。これは、プリンタが `}` の直前の改行をコメントをフラッシュする十分な「区切り」と認識しなかったためと考えられます。

この問題を解決するために、コミットではラッピングのロジックが変更されました。

1.  **ラッピングの変更**:
    `fsrc := append(append([]byte("package p; func _() {"), src...), '\n', '\n', '}')`
    元のコードの後に、**2つの改行 `\n`, `\n`** と閉じ括弧 `}` を追加するように変更されました。この追加された余分な改行は、`go/printer` に対して、`}` の前にコメントをフラッシュするための明確な区切りを提供します。これにより、`//line` ディレクティブを含むコメントが `}` の前に正しく出力されるようになります。

2.  **アンラッピングの変更**:
    ラッピングの変更に伴い、フォーマット後に元のコードを抽出するアンラッピングのロジックも調整されました。
    変更前は、`src = src[:len(src)-(indent+len("\n}"))]` のように、追加された改行と `}`、そしてインデントを考慮して末尾を切り取っていました。
    変更後は、`src = src[:len(src)-len("}\n")]` となりました。これは、末尾から `}\n` だけを削除することを意味します。ラッピング時に追加された余分な改行 `\n` は、`bytes.TrimSpace(src)` によって後でトリムされるため、明示的に削除する必要がなくなりました。この変更により、アンラッピング処理が新しいラッピング構造と整合性が取れるようになりました。

これらの変更により、`go/format` は `//line` ディレクティブを含む部分的なGoコードを正しくフォーマットできるようになり、Issue #11276 で報告されたバグが修正されました。

## コアとなるコードの解説

`src/internal/format/format.go` の `Parse` 関数における変更は、`go/format` が部分的なGoコードを処理する際の内部的な挙動を根本的に改善しています。

1.  **ラッピング時の改行追加の意図**:
    最も重要な変更は、部分的なコードを関数ボディでラップする際に、閉じ括弧 `}` の直前に `\n` を1つ追加する代わりに、`\n\n` (2つの改行) を追加するようになった点です。
    `fsrc := append(append([]byte("package p; func _() {"), src...), '\n', '\n', '}')`
    この変更の目的は、`go/printer` がコメントをフラッシュするメカニズムに影響を与えることです。Goのプリンタは、特定の構文要素（この場合は `}`）の直前にコメントを出力する際に、その直前の空白や改行のパターンを考慮します。`//line` ディレクティブのような特殊なコメントは、通常のコメントとは異なる処理パスを持つことがあり、特に `}` のような「終端」を示すトークンの直前では、プリンタがコメントを適切に「フラッシュ」する機会を失うことがありました。
    2つの改行を追加することで、プリンタは `}` の前に十分な空白（改行）のコンテキストを得て、バッファリングされているコメント（特に `//line` ディレクティブ）を `}` の前に確実に書き出すことができるようになります。これにより、`}` がコメントの前に誤って出力される問題が解消されます。

2.  **アンラッピング時の変更の意図**:
    ラッピングの変更に伴い、フォーマットされたコードから元の部分的なコードを抽出するアンラッピングのロジックも調整されました。
    `src = src[:len(src)-len("}\n")]`
    以前は、`len(src)-(indent+len("\n}"))` を使って、追加されたインデントと `\n}` を削除していました。新しいラッピングでは `\n\n}` が追加されるため、このロジックも変更が必要です。
    しかし、このコミットでは、末尾から `}\n` だけを削除するように簡略化されています。これは、ラッピング時に追加された余分な `\n` は、最終的に `bytes.TrimSpace(src)` が呼び出される際に自動的にトリムされるため、明示的に削除する必要がないと判断されたためです。この変更により、アンラッピングのコードがよりシンプルになり、かつ新しいラッピング構造と正しく連携するようになりました。

`src/go/format/format_test.go` に追加されたテストケースは、これらの変更が意図した通りに機能することを検証します。特に、`//line` ディレクティブが様々な位置や形式で存在する場合に、`go/format` が正しくフォーマットされた出力を生成することを確認します。これらのテストは、この特定のコーナーケースが将来的に再発しないためのセーフティネットとして機能します。

    *   書式は `//line filename:line` または `//line :line` です。
    *   主に、`yacc` や `protobuf` のようなツールによって生成されたGoコードで、生成元となる元のソースファイルの行番号をデバッグ情報として保持するために使用されます。これにより、生成されたコードでエラーが発生した場合でも、元のソースファイルの正確な位置を報告できます。

3.  **Goパーサーとプリンタのコメント処理**:
    *   Goのパーサー (`go/parser`) は、ソースコードを解析する際にコメントも読み込み、ASTの一部として保持します。
    *   Goのプリンタ (`go/printer`) は、ASTをソースコードに変換する際に、ASTに付随するコメントを適切な位置に出力します。
    *   コメントの「フラッシュ」とは、プリンタがバッファリングしているコメントを、現在の出力位置に書き出す処理を指します。特定の構文要素（例: 閉じ括弧 `}`）の直前でコメントが適切にフラッシュされないと、コメントが意図しない位置に移動したり、失われたりする可能性があります。

4.  **抽象構文木 (AST)**:
    *   ソースコードの構造を木構造で表現したものです。Goのコンパイラやツールは、ソースコードを直接操作するのではなく、ASTを操作することで、解析、変換、最適化、コード生成などを行います。

これらの知識が、`go/format` がどのように動作し、`//line` ディレクティブがどのように処理され、そしてなぜこのバグが発生したのかを理解する上で不可欠です。

## 技術的詳細

このコミットの技術的詳細は、`go/format` が部分的なGoコードを処理する際の内部メカニズムと、`//line` ディレクティブの特殊な振る舞いに焦点を当てています。

`go/format` の `Parse` 関数は、与えられたソースコードが完全なGoファイルではない場合（例えば、ステートメントのリストや式の場合）、それをパース可能な形式に変換するために、一時的にGoの関数ボディでラップします。具体的には、元のソースコード `src` を `package p; func _() {` と `}` で囲みます。

変更前のコードでは、このラッピングは以下のようになっていました。
`fsrc := append(append([]byte("package p; func _() {"), src...), '\n', '}')`
これは、元のコードの後に改行 `\n` と閉じ括弧 `}` を追加していました。

問題は、`src` の末尾に `//line` ディレクティブのようなコメントがある場合、`go/printer` が `}` の直前でこれらのコメントを適切にフラッシュしないことがあった点です。これにより、`}` がコメントの前に出力されてしまい、フォーマットが崩れる結果となりました。例えば、`a()\n//line :1` という入力に対して、`a() }\n\n//line` のような不正な出力が生成されていました。これは、プリンタが `}` の直前の改行をコメントをフラッシュする十分な「区切り」と認識しなかったためと考えられます。

この問題を解決するために、コミットではラッピングのロジックが変更されました。

1.  **ラッピングの変更**:
    `fsrc := append(append([]byte("package p; func _() {"), src...), '\n', '\n', '}')`
    元のコードの後に、**2つの改行 `\n`, `\n`** と閉じ括弧 `}` を追加するように変更されました。この追加された余分な改行は、`go/printer` に対して、`}` の前にコメントをフラッシュするための明確な区切りを提供します。これにより、`//line` ディレクティブを含むコメントが `}` の前に正しく出力されるようになります。

2.  **アンラッピングの変更**:
    ラッピングの変更に伴い、フォーマット後に元のコードを抽出するアンラッピングのロジックも調整されました。
    変更前は、`src = src[:len(src)-(indent+len("\n}"))]` のように、追加された改行と `}`、そしてインデントを考慮して末尾を切り取っていました。
    変更後は、`src = src[:len(src)-len("}\n")]` となりました。これは、末尾から `}\n` だけを削除することを意味します。ラッピング時に追加された余分な改行 `\n` は、`bytes.TrimSpace(src)` によって後でトリムされるため、明示的に削除する必要がなくなりました。この変更により、アンラッピング処理が新しいラッピング構造と整合性が取れるようになりました。

これらの変更により、`go/format` は `//line` ディレクティブを含む部分的なGoコードを正しくフォーマットできるようになり、Issue #11276 で報告されたバグが修正されました。

## コアとなるコードの解説

`src/internal/format/format.go` の `Parse` 関数における変更は、`go/format` が部分的なGoコードを処理する際の内部的な挙動を根本的に改善しています。

1.  **ラッピング時の改行追加の意図**:
    最も重要な変更は、部分的なコードを関数ボディでラップする際に、閉じ括弧 `}` の直前に `\n` を1つ追加する代わりに、`\n\n` (2つの改行) を追加するようになった点です。
    `fsrc := append(append([]byte("package p; func _() {"), src...), '\n', '\n', '}')`
    この変更の目的は、`go/printer` がコメントをフラッシュするメカニズムに影響を与えることです。Goのプリンタは、特定の構文要素（この場合は `}`）の直前にコメントを出力する際に、その直前の空白や改行のパターンを考慮します。`//line` ディレクティブのような特殊なコメントは、通常のコメントとは異なる処理パスを持つことがあり、特に `}` のような「終端」を示すトークンの直前では、プリンタがコメントを適切に「フラッシュ」する機会を失うことがありました。
    2つの改行を追加することで、プリンタは `}` の前に十分な空白（改行）のコンテキストを得て、バッファリングされているコメント（特に `//line` ディレクティブ）を `}` の前に確実に書き出すことができるようになります。これにより、`}` がコメントの前に誤って出力される問題が解消されます。

2.  **アンラッピング時の変更の意図**:
    ラッピングの変更に伴い、フォーマットされたコードから元の部分的なコードを抽出するアンラッピングのロジックも調整されました。
    `src = src[:len(src)-len("}\n")]`
    以前は、`len(src)-(indent+len("\n}"))` を使って、追加されたインデントと `\n}` を削除していました。新しいラッピングでは `\n\n}` が追加されるため、このロジックも変更が必要です。
    しかし、このコミットでは、末尾から `}\n` だけを削除するように簡略化されています。これは、ラッピング時に追加された余分な `\n` は、最終的に `bytes.TrimSpace(src)` が呼び出される際に自動的にトリムされるため、明示的に削除する必要がないと判断されたためです。この変更により、アンラッピングのコードがよりシンプルになり、かつ新しいラッピング構造と正しく連携するようになりました。

`src/go/format/format_test.go` に追加されたテストケースは、これらの変更が意図した通りに機能することを検証します。特に、`//line` ディレクティブが様々な位置や形式で存在する場合に、`go/format` が正しくフォーマットされた出力を生成することを確認します。これらのテストは、この特定のコーナーケースが将来的に再発しないためのセーフティネットとして機能します。

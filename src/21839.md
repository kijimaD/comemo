# [インデックス 21839] ファイルの概要

このコミットは、Goランタイムにおける文字列比較関数 `eqstring` のパフォーマンス改善を目的としています。具体的には、PowerPC 64-bit (ppc64x) アーキテクチャ向けのアセンブリコードが変更され、文字列の長さチェックが不要になったことと、ポインタの等価性チェックが追加されたことにより、文字列比較の効率が向上しています。

## 変更の背景

Go言語のランタイムには、文字列の等価性を比較するための `eqstring` という内部関数が存在します。この関数は、Goプログラム内で `==` 演算子を使って文字列を比較する際に、コンパイラによって呼び出されることがあります。

従来の `eqstring` の実装では、比較対象の2つの文字列の長さが等しいかどうかを最初にチェックしていました。これは、長さが異なる文字列は決して等しくないという自明な事実に基づいています。しかし、このコミットの背景には、Goコンパイラが `eqstring` を呼び出す前に、すでに比較対象の文字列の長さが等しいことを保証するようになったという重要な変更があります。

コンパイラがこの保証を行うようになったため、`eqstring` 関数内で再度長さチェックを行うことは冗長であり、オーバーヘッドとなっていました。この冗長なチェックを削除することで、`eqstring` の実行速度を向上させることが可能になります。

また、文字列比較の一般的な最適化として、比較対象の文字列がメモリ上で同じアドレスを指している場合（つまり、同じ文字列インスタンスである場合）、その時点で等しいと判断できるというものがあります。このポインタ等価性チェックを追加することで、特に同じ文字列リテラルや、コピーされずに渡された文字列の比較において、早期に結果を確定し、バイトごとの比較処理をスキップできるため、さらなるパフォーマンス向上が期待されます。

このコミットは、特に `ppc64x` (PowerPC 64-bit) アーキテクチャ向けのアセンブリコードに焦点を当てています。他のアーキテクチャに対する同様の最適化は、別のコミットで既に行われているか、あるいは後続のコミットで実施される予定であることが示唆されています。これは、Goランタイムの最適化がアーキテクチャ固有のアセンブリコードレベルで行われることが多く、各アーキテクチャで個別に調整が必要となるためです。

## 前提知識の解説

### Go言語の文字列 (string)

Go言語の文字列は、不変なバイトのスライスとして内部的に表現されます。Goの文字列は、`string` ヘッダと呼ばれる構造体で管理されており、通常、以下の2つのフィールドを持ちます。

1.  **データポインタ**: 文字列の実際のバイトデータが格納されているメモリ上のアドレスを指すポインタ。
2.  **長さ**: 文字列のバイト長。

Goにおいて文字列を比較する際、`s1 == s2` のように `==` 演算子を使用すると、コンパイラは通常、ランタイムの `eqstring` 関数を呼び出します。この関数は、2つの文字列のバイトデータを比較して、それらが完全に一致するかどうかを判断します。

### Goランタイムとアセンブリ

Goランタイムは、ガベージコレクション、スケジューラ、プリミティブな操作（文字列操作、マップ操作など）といった、Goプログラムの実行を支える低レベルな機能を提供します。これらの機能の一部は、パフォーマンスが非常に重要であるため、Go言語自体ではなく、特定のアセンブリ言語で実装されています。

アセンブリ言語は、CPUが直接実行できる機械語命令に非常に近い低レベルなプログラミング言語です。特定のCPUアーキテクチャ（例: x86-64, ARM64, PowerPC）に特化しており、レジスタの直接操作やメモリへの低レベルなアクセスが可能です。これにより、Goコンパイラやランタイム開発者は、Go言語では不可能なレベルでの最適化（例: 特定のCPU命令の利用、キャッシュ効率の最大化）を行うことができます。

このコミットで変更されている `src/runtime/asm_ppc64x.s` は、PowerPC 64-bitアーキテクチャ向けのアセンブリコードファイルです。`.s` 拡張子は、通常、アセンブリソースファイルを示します。

### PowerPC 64-bit (ppc64x) アーキテクチャ

PowerPCは、IBMが開発したRISC (Reduced Instruction Set Computer) アーキテクチャです。ppc64xは、64ビット版のPowerPCアーキテクチャを指し、サーバー、組み込みシステム、スーパーコンピュータなどで使用されています。Goランタイムは、様々なアーキテクチャをサポートしており、それぞれのアーキテクチャに最適化されたアセンブリコードを持つことがあります。

### レジスタとアセンブリ命令 (PowerPCの例)

PowerPCのアセンブリでは、汎用レジスタ (R0-R31) がデータ操作に使用されます。

*   `MOVD`: データをレジスタ間またはレジスタとメモリ間で移動する命令。
*   `CMP`: 2つのオペランドを比較する命令。結果は条件レジスタに設定され、その後の分岐命令に影響します。
*   `BNE`: "Branch if Not Equal" の略。比較結果が等しくない場合に指定されたラベルに分岐します。
*   `BEQ`: "Branch if Equal" の略。比較結果が等しい場合に指定されたラベルに分岐します。
*   `RETURN`: 関数から戻る命令。
*   `MOVBZU`: "Move Byte Zero-extended Unsigned" の略。メモリから1バイトを読み込み、ゼロ拡張してレジスタに格納します。

アセンブリコードでは、関数引数はスタックまたはレジスタを通じて渡され、戻り値も同様にレジスタまたはスタックを通じて返されます。`s1len+8(FP)` のような表記は、フレームポインタ (FP) からのオフセットでスタック上の引数にアクセスしていることを示します。

## 技術的詳細

このコミットの技術的な核心は、`eqstring` 関数における文字列比較ロジックの最適化です。

### 1. 長さチェックの削除

元の `eqstring` のアセンブリコードには、以下のような長さチェックのシーケンスがありました。

```assembly
	MOVD	s1len+8(FP), R4  // s1の長さをR4にロード
	MOVD	s2len+24(FP), R5 // s2の長さをR5にロード
	CMP	R4, R5           // R4とR5を比較
	BNE	noteq            // 等しくなければnot_equalラベルに分岐
```

このコードは、2つの文字列 `s1` と `s2` の長さを取得し、それらが異なる場合は即座に `noteq` ラベル（文字列が等しくないことを示す処理）に分岐していました。

このコミットでは、この部分が完全に削除されています。これは、Goコンパイラが `eqstring` を呼び出す時点で、比較対象の文字列の長さが常に等しいことを保証するようになったためです。この保証により、ランタイムレベルでの長さチェックは不要となり、命令数を削減し、実行パスを短縮することでパフォーマンスが向上します。

### 2. ポインタ等価性チェックの追加

長さチェックの削除に加えて、新しい最適化としてポインタ等価性チェックが追加されました。

```assembly
	MOVD	s1str+0(FP), R3  // s1のデータポインタをR3にロード
	MOVD	s2str+16(FP), R4 // s2のデータポインタをR4にロード
	MOVD	$1, R5           // R5に1をセット (trueを表す)
	MOVB	R5, ret+32(FP)   // 戻り値retにtrueをセット
	CMP	R3, R4           // R3とR4を比較 (ポインタが等しいか)
	BNE	2(PC)            // 等しくなければ次の命令をスキップしてバイト比較へ
	RETURN                   // ポインタが等しければここで関数を終了 (trueを返す)
```

このシーケンスでは、まず `s1` と `s2` のデータポインタ（文字列の実際のバイトデータが始まるアドレス）をそれぞれ `R3` と `R4` にロードします。次に、これらのポインタが等しいかどうかを `CMP R3, R4` で比較します。

*   もしポインタが等しければ（つまり、`s1` と `s2` がメモリ上の同じ文字列インスタンスを指していれば）、その時点で文字列は等しいと判断できます。この場合、`RETURN` 命令が実行され、関数は `true` を返して終了します。これにより、その後のバイトごとの比較処理が完全にスキップされます。
*   もしポインタが等しくなければ、`BNE 2(PC)` 命令によって次の `RETURN` 命令がスキップされ、通常のバイトごとの比較ループに進みます。

このポインタ等価性チェックは、特に文字列リテラルや、関数間でコピーされずに渡される文字列など、同じメモリ領域を共有する文字列の比較において非常に効果的です。

### 3. バイト比較ループの変更

長さチェックが削除されたことで、`noteq` ラベルへの分岐も不要になりました。これにより、アセンブリコードのフローがより直線的になり、可読性も向上しています。

変更後のバイト比較ループは、ポインタが異なる場合にのみ実行されます。ループは文字列の各バイトを順に比較し、不一致が見つかった場合は `false` を返し、最後まで一致した場合は `true` を返します。

## コアとなるコードの解説

### 変更前 (`-` で示される行)

*   `MOVD s1len+8(FP), R4` と `MOVD s2len+24(FP), R5`: 最初の文字列 `s1` と2番目の文字列 `s2` の長さをそれぞれレジスタ `R4` と `R5` にロードしています。
*   `CMP R4, R5`: ロードした2つの長さを比較します。
*   `BNE noteq`: 長さが等しくない場合 (`BNE` - Branch if Not Equal)、`noteq` ラベルに分岐します。`noteq` ラベルでは、戻り値 `ret` に `false` (0) を設定して関数を終了します。

### 変更後 (`+` で示される行)

*   長さチェック (`MOVD s1len...`, `CMP R4, R5`, `BNE noteq`) の行が完全に削除されています。これは、コンパイラが `eqstring` を呼び出す時点で長さが等しいことを保証するためです。
*   `MOVD s1str+0(FP), R3` と `MOVD s2str+16(FP), R4`: 変更前と同じく、文字列のデータポインタをそれぞれ `R3` と `R4` にロードします。
*   `MOVD $1, R5` と `MOVB R5, ret+32(FP)`: 戻り値 `ret` を `true` (1) に初期設定します。これは、ポインタが等しい場合にすぐに `true` を返すための準備です。
*   `CMP R3, R4`: ロードした2つのデータポインタを比較します。
*   `BNE 2(PC)`: ポインタが等しくない場合 (`BNE`)、現在のプログラムカウンタ (PC) から2バイト先に分岐します。これにより、次の `RETURN` 命令がスキップされ、バイトごとの比較ループに進みます。
*   `RETURN`: ポインタが等しい場合、この命令が実行され、関数は `true` を返して終了します。
*   `MOVD s1len+8(FP), R5`: この行は、変更前は `s2len` をロードしていましたが、変更後は `s1len` をロードしています。これは、バイト比較ループの終了条件 (`CMP R3, R8`) で使用される `R8` の計算 (`ADD R3, R5, R8`) に必要な文字列の長さ (`s1len`) を `R5` にロードするためです。ポインタが等しくない場合にのみこのパスが実行されるため、長さは等しいというコンパイラの保証がここでも活かされています。
*   `BNE 4(PC)` が `BNE 2(PC)` に変更されています。これは、アセンブリ命令のサイズやジャンプ先の調整によるものです。
*   `noteq:` ラベルとその関連コードが削除されています。これは、長さチェックがなくなったため、長さが異なることによる早期終了パスが不要になったためです。不一致が見つかった場合は、直接 `MOVB R0, ret+32(FP)` (戻り値に `false` をセット) を実行して `RETURN` します。

この変更により、`eqstring` は、まずポインタが等しいかをチェックし、等しければ即座に `true` を返します。ポインタが異なる場合は、文字列の長さが等しいことが保証されているため、直接バイトごとの比較に進みます。これにより、文字列比較の最も一般的なケース（同じ文字列インスタンスの比較）と、長さが異なることが事前に分かっているケース（コンパイラが処理）の両方で効率が向上します。

### Goランタイムとアセンブリ

Goランタイムは、ガベージコレクション、スケジューラ、プリミティブな操作（文字列操作、マップ操作など）といった、Goプログラムの実行を支える低レベルな機能を提供します。これらの機能の一部は、パフォーマンスが非常に重要であるため、Go言語自体ではなく、特定のアセンブリ言語で実装されています。

アセンブリ言語は、CPUが直接実行できる機械語命令に非常に近い低レベルなプログラミング言語です。特定のCPUアーキテクチャ（例: x86-64, ARM64, PowerPC）に特化しており、レジスタの直接操作やメモリへの低レベルなアクセスが可能です。これにより、Goコンパイラやランタイム開発者は、Go言語では不可能なレベルでの最適化（例: 特定のCPU命令の利用、キャッシュ効率の最大化）を行うことができます。

このコミットで変更されている `src/runtime/asm_ppc64x.s` は、PowerPC 64-bitアーキテクチャ向けのアセンブリコードファイルです。`.s` 拡張子は、通常、アセンブリソースファイルを示します。

### PowerPC 64-bit (ppc64x) アーキテクチャ

PowerPCは、IBMが開発したRISC (Reduced Instruction Set Computer) アーキテクチャです。ppc64xは、64ビット版のPowerPCアーキテクチャを指し、サーバー、組み込みシステム、スーパーコンピュータなどで使用されています。Goランタイムは、様々なアーキテクチャをサポートしており、それぞれのアーキテクチャに最適化されたアセンブリコードを持つことがあります。

### レジスタとアセンブリ命令 (PowerPCの例)

PowerPCのアセンブリでは、汎用レジスタ (R0-R31) がデータ操作に使用されます。

*   `MOVD`: データをレジスタ間またはレジスタとメモリ間で移動する命令。
*   `CMP`: 2つのオペランドを比較する命令。結果は条件レジスタに設定され、その後の分岐命令に影響します。
*   `BNE`: "Branch if Not Equal" の略。比較結果が等しくない場合に指定されたラベルに分岐します。
*   `BEQ`: "Branch if Equal" の略。比較結果が等しい場合に指定されたラベルに分岐します。
*   `RETURN`: 関数から戻る命令。
*   `MOVBZU`: "Move Byte Zero-extended Unsigned" の略。メモリから1バイトを読み込み、ゼロ拡張してレジスタに格納します。

アセンブリコードでは、関数引数はスタックまたはレジスタを通じて渡され、戻り値も同様にレジスタまたはスタックを通じて返されます。`s1len+8(FP)` のような表記は、フレームポインタ (FP) からのオフセットでスタック上の引数にアクセスしていることを示します。

## 技術的詳細

このコミットの技術的な核心は、`eqstring` 関数における文字列比較ロジックの最適化です。

### 1. 長さチェックの削除

元の `eqstring` のアセンブリコードには、以下のような長さチェックのシーケンスがありました。

```assembly
	MOVD	s1len+8(FP), R4  // s1の長さをR4にロード
	MOVD	s2len+24(FP), R5 // s2の長さをR5にロード
	CMP	R4, R5           // R4とR5を比較
	BNE	noteq            // 等しくなければnot_equalラベルに分岐
```

このコードは、2つの文字列 `s1` と `s2` の長さを取得し、それらが異なる場合は即座に `noteq` ラベル（文字列が等しくないことを示す処理）に分岐していました。

このコミットでは、この部分が完全に削除されています。これは、Goコンパイラが `eqstring` を呼び出す時点で、比較対象の文字列の長さが常に等しいことを保証するようになったためです。この保証により、ランタイムレベルでの長さチェックは不要となり、命令数を削減し、実行パスを短縮することでパフォーマンスが向上します。

### 2. ポインタ等価性チェックの追加

長さチェックの削除に加えて、新しい最適化としてポインタ等価性チェックが追加されました。

```assembly
	MOVD	s1str+0(FP), R3  // s1のデータポインタをR3にロード
	MOVD	s2str+16(FP), R4 // s2のデータポインタをR4にロード
	MOVD	$1, R5           // R5に1をセット (trueを表す)
	MOVB	R5, ret+32(FP)   // 戻り値retにtrueをセット
	CMP	R3, R4           // R3とR4を比較 (ポインタが等しいか)
	BNE	2(PC)            // 等しくなければ次の命令をスキップしてバイト比較へ
	RETURN                   // ポインタが等しければここで関数を終了 (trueを返す)
```

このシーケンスでは、まず `s1` と `s2` のデータポインタ（文字列の実際のバイトデータが始まるアドレス）をそれぞれ `R3` と `R4` にロードします。次に、これらのポインタが等しいかどうかを `CMP R3, R4` で比較します。

*   もしポインタが等しければ（つまり、`s1` と `s2` がメモリ上の同じ文字列インスタンスを指していれば）、その時点で文字列は等しいと判断できます。この場合、`RETURN` 命令が実行され、関数は `true` を返して終了します。これにより、その後のバイトごとの比較処理が完全にスキップされます。
*   もしポインタが等しくなければ、`BNE 2(PC)` 命令によって次の `RETURN` 命令がスキップされ、通常のバイトごとの比較ループに進みます。

このポインタ等価性チェックは、特に文字列リテラルや、関数間でコピーされずに渡される文字列など、同じメモリ領域を共有する文字列の比較において非常に効果的です。

### 3. バイト比較ループの変更

長さチェックが削除されたことで、`noteq` ラベルへの分岐も不要になりました。これにより、アセンブリコードのフローがより直線的になり、可読性も向上しています。

変更後のバイト比較ループは、ポインタが異なる場合にのみ実行されます。ループは文字列の各バイトを順に比較し、不一致が見つかった場合は `false` を返し、最後まで一致した場合は `true` を返します。

## コアとなるコードの解説

### 変更前 (`-` で示される行)

*   `MOVD s1len+8(FP), R4` と `MOVD s2len+24(FP), R5`: 最初の文字列 `s1` と2番目の文字列 `s2` の長さをそれぞれレジスタ `R4` と `R5` にロードしています。
*   `CMP R4, R5`: ロードした2つの長さを比較します。
*   `BNE noteq`: 長さが等しくない場合 (`BNE` - Branch if Not Equal)、`noteq` ラベルに分岐します。`noteq` ラベルでは、戻り値 `ret` に `false` (0) を設定して関数を終了します。

### 変更後 (`+` で示される行)

*   長さチェック (`MOVD s1len...`, `CMP R4, R5`, `BNE noteq`) の行が完全に削除されています。これは、コンパイラが `eqstring` を呼び出す時点で長さが等しいことを保証するためです。
*   `MOVD s1str+0(FP), R3` と `MOVD s2str+16(FP), R4`: 変更前と同じく、文字列のデータポインタをそれぞれ `R3` と `R4` にロードします。
*   `MOVD $1, R5` と `MOVB R5, ret+32(FP)`: 戻り値 `ret` を `true` (1) に初期設定します。これは、ポインタが等しい場合にすぐに `true` を返すための準備です。
*   `CMP R3, R4`: ロードした2つのデータポインタを比較します。
*   `BNE 2(PC)`: ポインタが等しくない場合 (`BNE`)、現在のプログラムカウンタ (PC) から2バイト先に分岐します。これにより、次の `RETURN` 命令がスキップされ、バイトごとの比較ループに進みます。
*   `RETURN`: ポインタが等しい場合、この命令が実行され、関数は `true` を返して終了します。
*   `MOVD s1len+8(FP), R5`: この行は、変更前は `s2len` をロードしていましたが、変更後は `s1len` をロードしています。これは、バイト比較ループの終了条件 (`CMP R3, R8`) で使用される `R8` の計算 (`ADD R3, R5, R8`) に必要な文字列の長さ (`s1len`) を `R5` にロードするためです。ポインタが等しくない場合にのみこのパスが実行されるため、長さは等しいというコンパイラの保証がここでも活かされています。
*   `BNE 4(PC)` が `BNE 2(PC)` に変更されています。これは、アセンブリ命令のサイズやジャンプ先の調整によるものです。
*   `noteq:` ラベルとその関連コードが削除されています。これは、長さチェックがなくなったため、長さが異なることによる早期終了パスが不要になったためです。不一致が見つかった場合は、直接 `MOVB R0, ret+32(FP)` (戻り値に `false` をセット) を実行して `RETURN` します。

この変更により、`eqstring` は、まずポインタが等しいかをチェックし、等しければ即座に `true` を返します。ポインタが異なる場合は、文字列の長さが等しいことが保証されているため、直接バイトごとの比較に進みます。これにより、文字列比較の最も一般的なケース（同じ文字列インスタンスの比較）と、長さが異なることが事前に分かっているケース（コンパイラが処理）の両方で効率が向上します。

## 変更の背景

このコミットの主な目的は、`net/http` パッケージのテスト中に発生する可能性のあるデータ競合を修正することです。コミットメッセージには「I can't reproduce the race, but this should fix it.」とあり、これは特定の条件下でしか発生しない、再現が困難な競合状態であったことを示唆しています。このような競合は、並行処理が絡むシステムではデバッグが非常に難しく、テストの信頼性を損なう原因となります。

具体的には、`Transport` のコネクション管理、特に「socket late binding」（ソケットの後期バインディング）と呼ばれるメカニズムに関連する問題が背景にあります。これは、HTTPリクエストが発行された後も、基盤となるTCPコネクションの確立が非同期的に進行し、リクエストが完了した後もコネクションがまだ確立中である可能性があるという状況を指します。テストコードでは、`sync.WaitGroup` を使用して、すべてのリクエストと関連するダイヤル（コネクション確立）処理が完了するのを待っていましたが、この「後期バインディング」の性質により、テストが `WaitGroup` の `Done()` を呼び出す前に、ダイヤル処理が完了してしまう可能性があり、これが競合状態を引き起こしていました。

この問題は、Go issue #8483 で報告されており、このコミットはその問題を解決するために行われました。

## 前提知識の解説

### データ競合 (Data Race)

データ競合とは、複数のゴルーチン（またはスレッド）が同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に発生するプログラミング上のバグです。データ競合が発生すると、プログラムの動作が予測不能になり、クラッシュ、不正な結果、セキュリティ脆弱性など、様々な問題を引き起こす可能性があります。Go言語では、`go run -race` コマンドを使用することで、データ競合を検出することができます。

### Goの `net/http` パッケージ

`net/http` パッケージは、Go言語でHTTPクライアントおよびサーバーを実装するための標準ライブラリです。
*   **`http.Client`**: HTTPリクエストを送信するためのクライアント。
*   **`http.Transport`**: `http.Client` の基盤となるインターフェースで、実際のHTTPリクエストの送信、コネクションの確立、コネクションプーリング、TLSハンドシェイクなどを担当します。`Transport` は、複数のリクエスト間でTCPコネクションを再利用することで、パフォーマンスを向上させます。

### `sync.WaitGroup`

`sync.WaitGroup` は、Go言語の標準ライブラリ `sync` パッケージで提供される同期プリミティブです。複数のゴルーチンが特定のタスクを完了するまで、メインゴルーチンが待機するために使用されます。
*   `Add(delta int)`: カウンタに `delta` を加算します。
*   `Done()`: カウンタを1減算します。
*   `Wait()`: カウンタがゼロになるまでブロックします。

### ゴルーチン (Goroutine)

ゴルーチンは、Go言語における軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行することも可能です。`go` キーワードを使って関数呼び出しの前に記述することで、その関数を新しいゴルーチンとして実行できます。ゴルーチン間の通信にはチャネルが推奨されます。

### チャネル (Channel)

チャネルは、ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは、Goの並行処理モデルの中心的な概念であり、データ競合を避けるための安全な通信手段を提供します。チャネルへの送信と受信は、デフォルトでブロックされます。

### `defer` ステートメント

`defer` ステートメントは、そのステートメントを含む関数がリターンする直前に、指定された関数呼び出しを遅延実行させるために使用されます。これは、リソースの解放（ファイルのクローズ、ロックの解除など）を確実に行うためによく使われます。

### `export_test.go` ファイル

Go言語では、パッケージの内部関数や変数は通常、外部からアクセスできません。しかし、テスト目的でこれらの内部要素にアクセスしたい場合があります。`_test.go` で終わるファイルはテストファイルとして扱われますが、`export_test.go` という名前のファイルは、パッケージの内部要素をテストのために外部に公開するために使用される慣習的なファイルです。このファイルで宣言された変数や関数は、同じパッケージのテストファイルからアクセスできるようになります。

## 技術的詳細

このコミットは、`net/http` パッケージの `Transport` におけるコネクション確立の非同期性によって引き起こされるテストのデータ競合を解決するために、新しいテストフックを導入し、コネクション処理のロジックを調整しています。

1.  **テストフックの導入**:
    `src/pkg/net/http/export_test.go` と `src/pkg/net/http/transport.go` に、`prePendingDial` と `postPendingDial` という2つの関数型のグローバル変数（テスト目的で公開）が導入されました。これらは、`Transport` が保留中のダイヤル（コネクション確立）を処理する前後に呼び出されるフックです。
    *   `prePendingDial`: 保留中のダイヤル処理が開始される直前に呼び出されます。
    *   `postPendingDial`: 保留中のダイヤル処理が完了した直後に呼び出されます。

2.  **`handlePendingDial` の変更**:
    `src/pkg/net/http/transport.go` 内の `handlePendingDial` 関数は、`dialc` チャネルからダイヤル結果を受け取り、コネクションをアイドルプールに戻す役割を担っています。以前は、この関数自体が `go handlePendingDial()` としてゴルーチンで実行されることがありました。
    変更後、`handlePendingDial` の内部で、`dialc` からの読み取りと `t.putIdleConn` の呼び出しが新しいゴルーチン `go func() { ... }()` の中にラップされました。これにより、`handlePendingDial` 自体はすぐにリターンし、`prePendingDial` と `postPendingDial` の呼び出しが、`dialc` からの読み取りがブロックされることによる遅延の影響を受けなくなります。

    特に重要なのは、`prePendingDial()` が呼び出された後、すぐに新しいゴルーチンが起動され、そのゴルーチン内で `dialc` からの読み取りと `postPendingDial()` の呼び出しが行われる点です。これにより、`prePendingDial` と `postPendingDial` の呼び出しが、`dialc` の準備状況に依存せず、より予測可能なタイミングで実行されるようになります。

3.  **テストコードの修正**:
    `src/pkg/net/http/transport_test.go` の `TestTransportConcurrency` テストでは、`sync.WaitGroup` を使用して、すべてのHTTPリクエストとそれに関連するコネクションダイヤルが完了するのを待っていました。
    以前は、`Transport` の `Dial` フィールドをオーバーライドして、ダイヤルが開始されるたびに `wg.Add(1)` を呼び出し、ダイヤルが完了したときに `wg.Done()` を呼び出していました。
    変更後、このカスタム `Dial` 関数は削除され、代わりに新しく導入された `SetPendingDialHooks` 関数が使用されます。
    `SetPendingDialHooks(func() { wg.Add(1) }, wg.Done)` を呼び出すことで、保留中のダイヤル処理が開始されるたびに `wg.Add(1)` が呼び出され、完了するたびに `wg.Done()` が呼び出されるようになります。これにより、テストの `WaitGroup` が、コネクションの「後期バインディング」によって発生する非同期的なダイヤル処理も正確にカウントし、テストがすべての関連するゴルーチンの完了を待つことができるようになり、データ競合が解消されます。`defer SetPendingDialHooks(nil, nil)` は、テスト終了時にフックをリセットするために使用されます。

この一連の変更により、テストが `Transport` の内部的な非同期処理（特にコネクションの確立）をより正確に追跡できるようになり、再現困難なデータ競合が解消されました。

## コアとなるコードの解説

### `src/pkg/net/http/export_test.go` の変更

*   `var DefaultUserAgent = defaultUserAgent` の下に、`SetPendingDialHooks` という新しい関数が追加されました。
*   `SetPendingDialHooks` は、`before` と `after` という2つの関数を引数にとります。これらの関数は、`net/http` パッケージ内部で定義されている `prePendingDial` と `postPendingDial` というグローバル変数にそれぞれ代入されます。
*   この関数は、テストコードが `Transport` の内部的なコネクション処理のライフサイクルにフックを仕掛けることを可能にします。これにより、テストはコネクションの確立が開始されたときと完了したときに通知を受け取ることができます。

### `src/pkg/net/http/transport.go` の変更

*   `var prePendingDial, postPendingDial func()`: テストフックとして使用される2つの関数型変数が宣言されました。これらはパッケージプライベートですが、`export_test.go` を介してテストから設定できます。
*   `handlePendingDial` 関数の変更:
    *   以前は `if v := <-dialc; v.err == nil { t.putIdleConn(v.pc) }` という形で `dialc` チャネルからの読み取りとアイドルコネクションへの追加を直接行っていました。
    *   変更後、このロジックは新しいゴルーチン `go func() { ... }()` の中にラップされました。
    *   この新しいゴルーチンの外側で、`if prePendingDial != nil { prePendingDial() }` が呼び出されます。これにより、保留中のダイヤル処理が開始される直前に `prePendingDial` フックが実行されます。
    *   新しいゴルーチンの中で、`dialc` からの読み取りと `t.putIdleConn` が行われた後、`if postPendingDial != nil { postPendingDial() }` が呼び出されます。これにより、ダイヤル処理が完了した後に `postPendingDial` フックが実行されます。
    *   この変更の重要な点は、`handlePendingDial` 関数自体が `dialc` からの読み取りでブロックされなくなったことです。代わりに、読み取りと後処理は別のゴルーチンで行われるため、`handlePendingDial` はすぐにリターンし、呼び出し元（`getConn`）のロジックがスムーズに進行します。これにより、テストフックのタイミングがより正確になり、競合状態が回避されます。
*   `getConn` 関数内の `go handlePendingDial()` の削除:
    *   以前は、`getConn` 関数内でコネクションがすぐに利用可能になった場合や、リクエストがキャンセルされた場合に、`go handlePendingDial()` を呼び出して、保留中のダイヤル処理を別のゴルーチンで実行していました。
    *   変更後、`go` キーワードが削除され、`handlePendingDial()` が直接呼び出されるようになりました。これは、`handlePendingDial` の内部ロジックがすでに新しいゴルーチンでラップされているため、二重にゴルーチンを起動する必要がなくなったためです。これにより、ロジックが簡素化され、意図しない競合がさらに減少します。

### `src/pkg/net/http/transport_test.go` の変更

*   `TestTransportConcurrency` テスト内の `Transport` の `Dial` フィールドのカスタム実装が削除されました。
*   代わりに、`SetPendingDialHooks(func() { wg.Add(1) }, wg.Done)` が呼び出されます。これにより、`prePendingDial` フックが `wg.Add(1)` に、`postPendingDial` フックが `wg.Done` に設定されます。
*   `defer SetPendingDialHooks(nil, nil)` が追加され、テストの終了時にフックがリセットされるようにしています。これは、他のテストに影響を与えないようにするためのクリーンアップ処理です。
*   この変更により、`sync.WaitGroup` は、HTTPリクエストの完了だけでなく、`Transport` の内部で非同期的に行われるコネクションのダイヤル処理の開始と完了も正確に追跡できるようになります。これにより、「socket late binding」によって発生する可能性のあるデータ競合が解消され、テストの信頼性が向上します。

*   **`http.Transport`**: `http.Client` の基盤となるインターフェースで、実際のHTTPリクエストの送信、コネクションの確立、コネクションプーリング、TLSハンドシェイクなどを担当します。`Transport` は、複数のリクエスト間でTCPコネクションを再利用することで、パフォーマンスを向上させます。

### `sync.WaitGroup`

`sync.WaitGroup` は、Go言語の標準ライブラリ `sync` パッケージで提供される同期プリミティブです。複数のゴルーチンが特定のタスクを完了するまで、メインゴルーチンが待機するために使用されます。
*   `Add(delta int)`: カウンタに `delta` を加算します。
*   `Done()`: カウンタを1減算します。
*   `Wait()`: カウンタがゼロになるまでブロックします。

### ゴルーチン (Goroutine)

ゴルーチンは、Go言語における軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行することも可能です。`go` キーワードを使って関数呼び出しの前に記述することで、その関数を新しいゴルーチンとして実行できます。ゴルーチン間の通信にはチャネルが推奨されます。

### チャネル (Channel)

チャネルは、ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは、Goの並行処理モデルの中心的な概念であり、データ競合を避けるための安全な通信手段を提供します。チャネルへの送信と受信は、デフォルトでブロックされます。

### `defer` ステートメント

`defer` ステートメントは、そのステートメントを含む関数がリターンする直前に、指定された関数呼び出しを遅延実行させるために使用されます。これは、リソースの解放（ファイルのクローズ、ロックの解除など）を確実に行うためによく使われます。

### `export_test.go` ファイル

Go言語では、パッケージの内部関数や変数は通常、外部からアクセスできません。しかし、テスト目的でこれらの内部要素にアクセスしたい場合があります。`_test.go` で終わるファイルはテストファイルとして扱われますが、`export_test.go` という名前のファイルは、パッケージの内部要素をテストのために外部に公開するために使用される慣習的なファイルです。このファイルで宣言された変数や関数は、同じパッケージのテストファイルからアクセスできるようになります。

## 技術的詳細

このコミットは、`net/http` パッケージの `Transport` におけるコネクション確立の非同期性によって引き起こされるテストのデータ競合を解決するために、新しいテストフックを導入し、コネクション処理のロジックを調整しています。

1.  **テストフックの導入**:
    `src/pkg/net/http/export_test.go` と `src/pkg/net/http/transport.go` に、`prePendingDial` と `postPendingDial` という2つの関数型のグローバル変数（テスト目的で公開）が導入されました。これらは、`Transport` が保留中のダイヤル（コネクション確立）を処理する前後に呼び出されるフックです。
    *   `prePendingDial`: 保留中のダイヤル処理が開始される直前に呼び出されます。
    *   `postPendingDial`: 保留中のダイヤル処理が完了した直後に呼び出されます。

2.  **`handlePendingDial` の変更**:
    `src/pkg/net/http/transport.go` 内の `handlePendingDial` 関数は、`dialc` チャネルからダイヤル結果を受け取り、コネクションをアイドルプールに戻す役割を担っています。以前は、この関数自体が `go handlePendingDial()` としてゴルーチンで実行されることがありました。
    変更後、`handlePendingDial` の内部で、`dialc` からの読み取りと `t.putIdleConn` の呼び出しが新しいゴルーチン `go func() { ... }()` の中にラップされました。これにより、`handlePendingDial` 自体はすぐにリターンし、`prePendingDial` と `postPendingDial` の呼び出しが、`dialc` からの読み取りがブロックされることによる遅延の影響を受けなくなります。

    特に重要なのは、`prePendingDial()` が呼び出された後、すぐに新しいゴルーチンが起動され、そのゴルーチン内で `dialc` からの読み取りと `postPendingDial()` の呼び出しが行われる点です。これにより、`prePendingDial` と `postPendingDial` の呼び出しが、`dialc` の準備状況に依存せず、より予測可能なタイミングで実行されるようになります。

3.  **テストコードの修正**:
    `src/pkg/net/http/transport_test.go` の `TestTransportConcurrency` テストでは、`sync.WaitGroup` を使用して、すべてのHTTPリクエストとそれに関連するコネクションダイヤルが完了するのを待っていました。
    以前は、`Transport` の `Dial` フィールドをオーバーライドして、ダイヤルが開始されるたびに `wg.Add(1)` を呼び出し、ダイヤルが完了したときに `wg.Done()` を呼び出していました。
    変更後、このカスタム `Dial` 関数は削除され、代わりに新しく導入された `SetPendingDialHooks` 関数が使用されます。
    `SetPendingDialHooks(func() { wg.Add(1) }, wg.Done)` を呼び出すことで、保留中のダイヤル処理が開始されるたびに `wg.Add(1)` が呼び出され、完了するたびに `wg.Done()` が呼び出されるようになります。これにより、テストの `WaitGroup` が、コネクションの「後期バインディング」によって発生する非同期的なダイヤル処理も正確にカウントし、テストがすべての関連するゴルーチンの完了を待つことができるようになり、データ競合が解消されます。`defer SetPendingDialHooks(nil, nil)` は、テスト終了時にフックをリセットするために使用されます。

この一連の変更により、テストが `Transport` の内部的な非同期処理（特にコネクションの確立）をより正確に追跡できるようになり、再現困難なデータ競合が解消されました。

## コアとなるコードの解説

### `src/pkg/net/http/export_test.go` の変更

*   `var DefaultUserAgent = defaultUserAgent` の下に、`SetPendingDialHooks` という新しい関数が追加されました。
*   `SetPendingDialHooks` は、`before` と `after` という2つの関数を引数にとります。これらの関数は、`net/http` パッケージ内部で定義されている `prePendingDial` と `postPendingDial` というグローバル変数にそれぞれ代入されます。
*   この関数は、テストコードが `Transport` の内部的なコネクション処理のライフサイクルにフックを仕掛けることを可能にします。これにより、テストはコネクションの確立が開始されたときと完了したときに通知を受け取ることができます。

### `src/pkg/net/http/transport.go` の変更

*   `var prePendingDial, postPendingDial func()`: テストフックとして使用される2つの関数型変数が宣言されました。これらはパッケージプライベートですが、`export_test.go` を介してテストから設定できます。
*   `handlePendingDial` 関数の変更:
    *   以前は `if v := <-dialc; v.err == nil { t.putIdleConn(v.pc) }` という形で `dialc` チャネルからの読み取りとアイドルコネクションへの追加を直接行っていました。
    *   変更後、このロジックは新しいゴルーチン `go func() { ... }()` の中にラップされました。
    *   この新しいゴルーチンの外側で、`if prePendingDial != nil { prePendingDial() }` が呼び出されます。これにより、保留中のダイヤル処理が開始される直前に `prePendingDial` フックが実行されます。
    *   新しいゴルーチンの中で、`dialc` からの読み取りと `t.putIdleConn` が行われた後、`if postPendingDial != nil { postPendingDial() }` が呼び出されます。これにより、ダイヤル処理が完了した後に `postPendingDial` フックが実行されます。
    *   この変更の重要な点は、`handlePendingDial` 関数自体が `dialc` からの読み取りでブロックされなくなったことです。代わりに、読み取りと後処理は別のゴルーチンで行われるため、`handlePendingDial` はすぐにリターンし、呼び出し元（`getConn`）のロジックがスムーズに進行します。これにより、テストフックのタイミングがより正確になり、競合状態が回避されます。
*   `getConn` 関数内の `go handlePendingDial()` の削除:
    *   以前は、`getConn` 関数内でコネクションがすぐに利用可能になった場合や、リクエストがキャンセルされた場合に、`go handlePendingDial()` を呼び出して、保留中のダイヤル処理を別のゴルーチンで実行していました。
    *   変更後、`go` キーワードが削除され、`handlePendingDial()` が直接呼び出されるようになりました。これは、`handlePendingDial` の内部ロジックがすでに新しいゴルーチンでラップされているため、二重にゴルーチンを起動する必要がなくなったためです。これにより、ロジックが簡素化され、意図しない競合がさらに減少します。

### `src/pkg/net/http/transport_test.go` の変更

*   `TestTransportConcurrency` テスト内の `Transport` の `Dial` フィールドのカスタム実装が削除されました。
*   代わりに、`SetPendingDialHooks(func() { wg.Add(1) }, wg.Done)` が呼び出されます。これにより、`prePendingDial` フックが `wg.Add(1)` に、`postPendingDial` フックが `wg.Done` に設定されます。
*   `defer SetPendingDialHooks(nil, nil)` が追加され、テストの終了時にフックがリセットされるようにしています。これは、他のテストに影響を与えないようにするためのクリーンアップ処理です。
*   この変更により、`sync.WaitGroup` は、HTTPリクエストの完了だけでなく、`Transport` の内部で非同期的に行われるコネクションのダイヤル処理の開始と完了も正確に追跡できるようになります。これにより、「socket late binding」によって発生する可能性のあるデータ競合が解消され、テストの信頼性が向上します。

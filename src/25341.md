## 変更の背景

Goのガベージコレクションは、そのパフォーマンス特性において重要な要素です。初期のGoのGCは、Stop-The-World (STW) フェーズが長く、アプリケーションのレイテンシに影響を与えることがありました。Go 1.5では、GCのアーキテクチャが大きく変更され、並行GCが導入されました。これにより、STWの時間を大幅に短縮し、ほとんどのGC作業をアプリケーションの実行と並行して行うようになりました。

このコミットは、Go 1.5の並行GCへの移行に伴うコードベースのクリーンアップの一環として行われたと考えられます。`_GCstw`という定数は、おそらく以前のGC実装におけるStop-The-Worldフェーズを表すために存在していましたが、新しい並行GCの設計では直接使用されなくなったため、未使用のコードとして削除されました。これは、コードの可読性を向上させ、将来的な混乱を防ぐための典型的なリファクタリング作業です。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goのガベージコレクタは、メモリ管理を自動化し、開発者が手動でメモリを解放する手間を省きます。Go 1.5以降、GoのGCは「三色マーク＆スイープ」アルゴリズムをベースとした並行・世代別・非圧縮のGCを採用しています。

主要なGCフェーズは以下の通りです。

*   **_GCoff**: GCが実行されていない状態。バックグラウンドでスイープが行われ、ライトバリアは無効。
*   **_GCscan**: GCがルート（スタック、グローバル変数など）をスキャンし、到達可能なオブジェクトを特定するための作業バッファに格納するフェーズ。このフェーズではライトバリアが有効になります。
*   **_GCmark**: 作業バッファからオブジェクトをマークしていくフェーズ。このフェーズもライトバリアが有効です。アプリケーションの実行と並行して行われます。
*   **_GCmarktermination**: マークフェーズの終了処理。アプリケーションのP (Processor) がGCを手伝い、ライトバリアが有効なまま、マーク処理を完了させます。このフェーズは短いSTWフェーズを含むことがあります。
*   **_GCsweep**: マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放するフェーズ。これはアプリケーションの実行と並行して、または必要に応じて行われます。

### Stop-The-World (STW)

Stop-The-World (STW) は、ガベージコレクションの特定のフェーズ中に、アプリケーションの全てのゴルーチン（スレッド）の実行を一時停止させる期間を指します。STW中はアプリケーションの処理が完全に停止するため、その時間が長いとアプリケーションの応答性やスループットに悪影響を与えます。Go 1.5以降のGCの主要な目標の一つは、このSTW時間を可能な限り短縮することでした。

### ライトバリア (Write Barrier)

ライトバリアは、GCが実行されている間に、アプリケーションがオブジェクトグラフを変更する（ポインタを書き換える）際に、GCの正確性を保つために挿入されるコードです。Goの並行GCでは、マークフェーズ中にアプリケーションが実行され続けるため、オブジェクトの参照関係が変化する可能性があります。ライトバリアは、このような変更をGCが追跡し、誤って生きているオブジェクトを回収しないようにするために不可欠です。

## 技術的詳細

このコミットは、`src/runtime/mgc.go`ファイル内の`gcphase`定数定義から`_GCstw`を削除しています。

元のコードでは、以下のように定義されていました。

```go
const (
	_GCoff             = iota // GC not running; sweeping in background, write barrier disabled
	_GCstw                    // unused state
	_GCscan                   // GC collecting roots into workbufs, write barrier ENABLED
	_GCmark                   // GC marking from workbufs, write barrier ENABLED
	_GCmarktermination        // GC mark termination: allocate black, P's help GC, write barrier ENABLED
	// ...
)
```

変更後：

```go
const (
	_GCoff             = iota // GC not running; sweeping in background, write barrier disabled
	_GCscan                   // GC collecting roots into workbufs, write barrier ENABLED
	_GCmark                   // GC marking from workbufs, write barrier ENABLED
	_GCmarktermination        // GC mark termination: allocate black, P's help GC, write barrier ENABLED
	// ...
)
```

`_GCstw`がコメントで「unused state」と明記されていることから、この定数はGo 1.5の並行GCの設計において、もはやアクティブなGCフェーズとして使用されていなかったことがわかります。

Go 1.5のGCは、STWフェーズを完全に排除したわけではありませんが、その期間を非常に短くし、GCの大部分を並行して実行するように設計されています。例えば、マークフェーズの開始時や終了時に短いSTWフェーズが存在しますが、これらは`_GCscan`や`_GCmarktermination`といった既存のフェーズの一部として管理されており、独立した`_GCstw`という状態は不要になったと考えられます。

この変更は、Goランタイムのコードベースをよりクリーンで、現在のGC実装を正確に反映したものにするためのものです。未使用の定数を削除することで、開発者がコードを理解する際の認知負荷を軽減し、将来的なメンテナンスを容易にします。

## コアとなるコードの解説

`const (...)`ブロックは、Goにおける列挙型（enum）のような定数グループを定義するために使用されます。`iota`は、このブロック内で連続する整数値を自動的に生成する特殊な識別子です。

元のコードでは、`_GCoff`が`0`、`_GCstw`が`1`、`_GCscan`が`2`といった具合に値が割り当てられていました。`_GCstw`が削除されたことで、`_GCscan`が`1`、`_GCmark`が`2`というように、以降の定数の値が一つずつシフトします。

この変更は、単に未使用の定数を削除するだけでなく、GoのGC状態遷移ロジックにおいて、`_GCstw`という状態がもはや存在しないことを明確に示しています。これは、Go 1.5の並行GCが、以前のGC実装とは異なる状態モデルで動作していることの証拠です。

GoのGCは、これらの定数を使って現在のGCフェーズを追跡し、それに応じてランタイムの動作（例えば、ライトバリアの有効/無効、スケジューリングの調整など）を調整します。`_GCstw`の削除は、GCの状態機械からこの特定の状態が取り除かれたことを意味し、GCの全体的な設計がより洗練され、効率的になったことを示唆しています。

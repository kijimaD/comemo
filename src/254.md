## 変更の背景

このコミットは、「map index of index bug」という特定のバグを修正するために行われました。これは、マップのインデックス操作、特にインデックス自体が別のマップのルックアップ結果であるようなネストされたケース（例: `m[m2[key]]`）において、コンパイラが誤ったコードを生成する可能性があったことを示唆しています。

コンパイラのウォークフェーズでは、ASTノードを処理する際に、そのノードがどのようなコンテキストで評価されるべきかを指定する「トップ (top)」引数を使用します。このバグは、マップの左辺（マップ自体を表す式）を処理する際に、汎用的な `top` コンテキストを使用していたことが原因で発生したと考えられます。これにより、コンパイラがマップ式を正しく値として評価せず、結果として不正なコードが生成される可能性がありました。

## 前提知識の解説

*   **Goコンパイラ (gc)**: Go言語の公式コンパイラであり、Goプログラムを機械語に変換する役割を担っています。`gc` は、複数のフェーズ（字句解析、構文解析、型チェック、最適化、コード生成など）を経てコンパイルを行います。
*   **抽象構文木 (AST: Abstract Syntax Tree)**: ソースコードの構文構造を抽象的に表現した木構造のデータ構造です。コンパイラはASTを操作することで、プログラムの意味を理解し、変換を行います。
*   **`walk.c` とウォークフェーズ**: `gc` コンパイラにおけるウォークフェーズは、ASTを深さ優先で走査し、各ノードに対して意味論的な処理を適用する段階です。これには、型チェック、定数畳み込み、式の簡略化、変数のエスケープ解析などが含まれます。このフェーズは、コード生成の前の最終的なASTの準備を行います。
*   **`walktype` 関数**: `walk.c` 内に存在する関数で、特定のASTノードとその子ノードの型を解決し、必要に応じて型変換やエラーチェックを行う役割を担います。この関数は、ノードが評価されるべきコンテキストを示す `top` 引数を取ります。
*   **`top` 引数**: `walktype` 関数に渡される整数値で、ASTノードが評価されるべきコンテキスト（目的）を示します。例えば、ノードがステートメントの一部であるか、式の結果として値が必要か、アドレスが必要かなどを指定します。
    *   **`Etop`**: 汎用的なトップレベルのコンテキスト。ノードがステートメントとして評価される場合などに使用されます。
    *   **`Erv` (Expression Result Value)**: 式が評価され、その結果として値が期待されるコンテキスト。例えば、代入の右辺や関数の引数など、値が必要な場所で使われます。
*   **マップのインデックス操作**: Go言語における `map[key]` の形式で、マップからキーに対応する値を取得する操作です。この操作の左辺（`map`）は常に値として評価される必要があります。

## 技術的詳細

このバグは、マップのインデックス操作 `n->left[n->right]` のような構造において、`n->left`（マップ自体を表す式）を処理する際に、誤ったコンテキスト `top` が `walktype` 関数に渡されていたことに起因します。

本来、マップのインデックス操作の左辺は、そのマップオブジェクト自体を値として評価する必要があります。しかし、`walktype(n->left, top)` のように汎用的な `top` コンテキストが使用されていた場合、コンパイラは `n->left` を値としてではなく、より広範な（場合によっては副作用を伴う可能性のある）コンテキストで処理してしまう可能性がありました。これにより、特にネストされたマップアクセス（例: `m[m2[key]]`）のような複雑なケースで、コンパイラがマップ式を正しく評価できず、ランタイムエラーや不正なコード生成につながる「map index of index bug」が発生していました。

修正は、`n->left` を処理する際のコンテキストを `top` から `Erv` に変更することです。`Erv` は「Expression Result Value」の略であり、式が評価され、その結果として値が期待されることを明示的にコンパイラに伝えます。これにより、`n->left` が常にマップオブジェクトの値として正しく評価されるようになり、バグが解消されました。

## コアとなるコードの解説

変更は `src/cmd/gc/walk.c` の `loop` ラベル内の部分で行われています。

元のコード:
`walktype(n->left, top);`

変更後のコード:
`walktype(n->left, Erv);`

この変更は、ASTノード `n` がマップのインデックス操作を表す場合に適用されます。
*   `n->left`: マップのインデックス操作の左辺、つまりマップオブジェクト自体を表すASTノード。
*   `n->right`: マップのインデックス操作の右辺、つまりキーを表すASTノード。

変更前は、`n->left`（マップ式）が `walktype` 関数によって、現在のコンテキスト `top` を使って処理されていました。しかし、マップのインデックス操作においては、マップ式は常にその値（マップオブジェクト）として評価される必要があります。`top` が `Etop` のような汎用的なコンテキストであった場合、コンパイラは `n->left` を値としてではなく、より広い意味で処理してしまう可能性がありました。

変更後は、`n->left` が `Erv` コンテキストで処理されるようになりました。`Erv` は「Expression Result Value」を意味し、コンパイラに対して `n->left` が評価されて値を生み出す式として扱われるべきであることを明確に指示します。これにより、マップ式が常に値として正しく評価され、その後のインデックス操作が期待通りに機能するようになります。`n->right`（キー）も同様に `Erv` で処理されており、キーも値として評価される必要があるため、これは一貫した正しいアプローチです。

この修正により、マップのインデックス操作、特にネストされたインデックス操作における型解決とコード生成の正確性が向上し、特定のバグが解消されました。

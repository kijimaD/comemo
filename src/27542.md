## 変更の背景

Goの `net/http` パッケージの `Client` は、HTTPリクエストを送信し、リダイレクトを自動的に処理する機能を提供します。このリダイレクト処理において、開発者がカスタムのリダイレクトポリシーを定義するために `Client.CheckRedirect` フィールドを使用できます。しかし、`CheckRedirect` 関数がエラーを返した場合、`Client.Do` メソッドは `*http.Response` オブジェクトとエラーの両方を返すことがありました。この状況下で、返された `*http.Response` の `Body` がどのような状態にあるのか（クローズされているのか、それともユーザーがクローズする必要があるのか）が明確に文書化されていませんでした。

この不明確さは、Issue #8633 および #9134 で報告され、開発者が `Response.Body` のリークやリソースの不適切な管理を引き起こす可能性がありました。特に、`Response.Body` を適切にクローズしないと、基盤となるTCP接続が再利用されず、パフォーマンスの低下や接続枯渇につながる可能性があります。

このコミットは、このドキュメントの不足を解消し、コードをクリーンアップすることで、`CheckRedirect` エラー発生時の `Response.Body` の状態を明確にし、開発者がより安全かつ効率的に `net/http` クライアントを使用できるようにすることを目的としています。

## 前提知識の解説

### Goの `net/http` パッケージ

Go言語の `net/http` パッケージは、HTTPクライアントとサーバーを実装するための強力な機能を提供します。
*   **`http.Client`**: HTTPリクエストを送信し、レスポンスを受信するクライアントを表します。リダイレクト、クッキー、認証などのポリシーを設定できます。
*   **`http.Request`**: HTTPリクエストを表す構造体です。
*   **`http.Response`**: HTTPレスポンスを表す構造体です。
    *   **`Response.Body`**: レスポンスのボディ（通常は `io.ReadCloser` インターフェースを実装）を含みます。このボディは、読み取り後に必ずクローズする必要があります。クローズしないと、TCP接続が再利用されず、リソースリークの原因となることがあります。
*   **`Client.Do(req *Request) (*Response, error)`**: 指定されたリクエストを送信し、レスポンスを返します。
*   **`Client.CheckRedirect`**: `func(req *Request, via []*Request) error` 型の関数フィールドです。リダイレクトが発生するたびに呼び出され、次のリクエスト (`req`) とこれまでのリダイレクト履歴 (`via`) を受け取ります。この関数がエラーを返すと、クライアントはリダイレクトを停止します。
*   **`url.Error`**: `net/url` パッケージで定義されているエラー型で、URL操作中に発生したエラーをラップするために使用されます。操作の種類 (`Op`)、URL (`URL`)、および元のエラー (`Err`) を含みます。

### HTTPリダイレクト

HTTPリダイレクトは、サーバーがクライアントに別のURLにリクエストを再送信するように指示するメカニズムです。一般的なステータスコードには `301 Moved Permanently`、`302 Found`、`303 See Other`、`307 Temporary Redirect`、`308 Permanent Redirect` などがあります。`net/http` クライアントは、デフォルトでこれらのリダイレクトを自動的にフォローします。

### `Response.Body` のクローズの重要性

Goの `net/http` クライアントでは、`http.Response` が返された場合、その `Body` フィールドは `io.ReadCloser` 型であり、読み取りが完了したら必ず `Close()` メソッドを呼び出す必要があります。これは、基盤となるTCP接続を解放し、再利用可能にするために不可欠です。`Body` をクローズしないと、接続がアイドル状態のままになり、最終的には接続プールが枯渇し、新しい接続の確立に時間がかかったり、リソースが不足したりする可能性があります。

## 技術的詳細

このコミットの主要な変更点は、`net/http` クライアントのリダイレクト処理ロジック (`doFollowingRedirects` メソッド) の再構築と、関連するドキュメントの改善です。

1.  **`Client.Do` メソッドのドキュメント更新**:
    *   `Client.Do` のドキュメントに、エラーが発生した場合でも `Response.Body` が非nilである可能性があること、そして `CheckRedirect` が失敗した場合に返される `Response.Body` は既にクローズされていることが明記されました。
    *   これにより、開発者は `CheckRedirect` エラー発生時に `Response.Body` を明示的にクローズする必要がないことを理解できます。

2.  **`Client.CheckRedirect` フィールドのドキュメント更新**:
    *   `CheckRedirect` のドキュメントにも、この関数がエラーを返した場合、`Client` の `Get` メソッドは以前の `Response` と `CheckRedirect` のエラーを返す際に、`Response.Body` が既にクローズされていることが追記されました。

3.  **`doFollowingRedirects` メソッドのロジック改善**:
    *   リダイレクト処理のループがより明確に再構築されました。特に、リダイレクトごとに新しい `http.Request` オブジェクトがどのように作成され、ヘッダー（`Referer` など）がどのように設定されるかが整理されました。
    *   `checkRedirect` というヘルパー関数が導入され、ユーザー定義の `CheckRedirect` またはデフォルトのリダイレクトチェッカーを呼び出すロジックがカプセル化されました。これにより、コードの可読性と保守性が向上しています。
    *   リダイレクトが成功し、次のリクエストに進む前に、現在のレスポンスの `Body` が確実にクローズされるようになりました。これは、`io.CopyN(ioutil.Discard, resp.Body, maxBodySlurpSize)` を使用してボディを読み捨て、その後 `resp.Body.Close()` を呼び出すことで実現されています。これにより、小さなボディを持つレスポンスの場合、基盤となるTCP接続が再利用されやすくなります。
    *   エラー処理が改善され、`url.Error` を生成するための `uerr` ヘルパー関数が導入されました。これにより、エラーメッセージが一貫性のある形式で提供されます。
    *   Go 1 との互換性のための特別なケース（`CheckRedirect` が失敗した場合にレスポンスとエラーの両方を返す）が維持され、コメントでその理由（Issue #3795）が明記されています。これは、既存のGo 1アプリケーションが予期しない動作変更に遭遇しないようにするための重要な考慮事項です。

これらの変更により、`net/http` クライアントのリダイレクト処理はより堅牢になり、`Response.Body` のライフサイクル管理に関する混乱が解消されました。

## コアとなるコードの解説

### `Client` 構造体と `Client.Do` メソッドのドキュメント更新

これらのドキュメントの変更は、`net/http` クライアントのユーザーにとって最も直接的な影響を与えます。以前は、`CheckRedirect` がエラーを返した場合に `Response.Body` がクローズされているかどうかが不明確でした。このコミットにより、`CheckRedirect` がエラーを返して `Client.Do` が `*Response` とエラーの両方を返す場合でも、`Response.Body` は既にクローズされていることが明示されました。これにより、開発者は `defer resp.Body.Close()` のようなコードを記述する際に、この特定のケースを考慮する必要がなくなります。

### `doFollowingRedirects` メソッドの再構築

この関数は、リダイレクトチェーンを処理する中心的なロジックを含んでいます。

*   **エラーハンドリングの統一 (`uerr` 関数)**:
    ```go
    uerr := func(err error) error {
        req.closeBody()
        method := valueOrDefault(reqs[0].Method, "GET")
        var urlStr string
        if resp != nil {
            urlStr = resp.Request.URL.String()
        } else {
            urlStr = req.URL.String()
        }
        return &url.Error{
            Op:  method[:1] + strings.ToLower(method[1:]),
            URL: urlStr,
            Err: err,
        }
    }
    ```
    このクロージャは、リダイレクト処理中に発生したエラーを `url.Error` 型でラップし、一貫したエラー表現を提供します。また、エラー発生時に現在のリクエストボディをクローズする役割も担っています。

*   **リダイレクトループの改善**:
    以前のコードは、リダイレクトのたびに新しいリクエストオブジェクトを作成し、そのURLとヘッダーを更新するロジックがやや複雑でした。新しいコードでは、`reqs` スライス（以前の `via`）に各リクエストを追加していくことで、リダイレクト履歴をより明確に管理しています。
    特に、`loc := resp.Header.Get("Location")` でリダイレクト先のURLを取得し、それを基に新しい `Request` オブジェクトを構築するプロセスが整理されました。

*   **`checkRedirect` ヘルパー関数**:
    ```go
    func (c *Client) checkRedirect(req *Request, via []*Request) error {
        fn := c.CheckRedirect
        if fn == nil {
            fn = defaultCheckRedirect
        }
        return fn(req, via)
    }
    ```
    この関数は、`Client.CheckRedirect` が設定されている場合はそれを使用し、設定されていない場合はデフォルトのリダイレクトチェッカー (`defaultCheckRedirect`) を使用するロジックを抽象化します。これにより、`doFollowingRedirects` 内のコードが簡潔になります。

*   **`Response.Body` の確実なクローズ**:
    リダイレクトが検出され、次のリクエストに進む前に、現在のレスポンスボディが確実にクローズされるようになりました。
    ```go
    if resp.ContentLength == -1 || resp.ContentLength <= maxBodySlurpSize {
        io.CopyN(ioutil.Discard, resp.Body, maxBodySlurpSize)
    }
    resp.Body.Close()
    ```
    `io.CopyN(ioutil.Discard, resp.Body, maxBodySlurpSize)` は、ボディが小さい場合にその内容を読み捨ててからクローズすることで、基盤となるTCP接続が「クリーン」な状態で再利用される可能性を高めます。これは、HTTPのKeep-Alive機能の効率的な利用に寄与します。

*   **Go 1 互換性 (`Issue #3795`)**:
    ```go
    // Special case for Go 1 compatibility: return both the response
    // and an error if the CheckRedirect function failed.
    // See https://golang.org/issue/3795
    // The resp.Body has already been closed.
    ue := uerr(err)
    ue.(*url.Error).URL = loc
    return resp, ue
    ```
    この部分は、`CheckRedirect` がエラーを返した場合に、`*http.Response` とエラーの両方を返すというGo 1の特定の動作を維持するためのものです。これは、既存のコードベースとの互換性を保つために重要であり、このコミットの目的である `Response.Body` のクローズ状態の明確化と矛盾しないように、`resp.Body` が既にクローズされていることが明記されています。

これらの変更は、`net/http` クライアントの堅牢性と使いやすさを向上させ、特にリダイレクト処理とリソース管理に関する潜在的な問題を解消するものです。

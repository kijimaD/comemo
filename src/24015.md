# [インデックス 24015] ファイルの概要

このコミットは、Goランタイムにおけるスタックバリアのクリアに関するバグ修正です。具体的には、ゴルーチンが`_FixedStack`サイズのスタックを使用している場合に、`runtime.Goexit`を通じて終了すると、スタックバリアが適切にクリアされずに再利用され、その後にガベージコレクタがパニックを引き起こす可能性があった問題に対処しています。

## コミット

```
commit 840965f8d7ccad5ac1782e208865e8120f5c080a
Author: Austin Clements <austin@google.com>
Date:   Wed Jun 24 17:13:24 2015 -0400

    runtime: always clear stack barriers on G exit
    
    Currently the runtime fails to clear a G's stack barriers in gfput if
    the G's stack allocation is _FixedStack bytes. This causes the runtime
    to panic if the following sequence of events happens:
    
    1) The runtime installs stack barriers on a G.
    
    2) The G exits by calling runtime.Goexit. Since this does not
       necessarily return through the stack barriers installed on the G,
       there may still be untriggered stack barriers left on the G's stack
       in recorded in g.stkbar.
    
    3) The runtime calls gfput to add the exiting G to the free pool. If
       the G's stack allocation is _FixedStack bytes, we fail to clear
       g.stkbar.
    
    4) A new G starts and allocates the G that was just added to the free
       pool.
    
    5) The new G begins to execute and overwrites the stack slots that had
       stack barriers in them.
    
    6) The garbage collector enters mark termination, attempts to remove
       stack barriers from the new G, and finds that they've been
       overwritten.
    
    Fix this by clearing the stack barriers in gfput in the case where it
    reuses the stack.
    
    Fixes #11256.

## 元コミット内容

Goランタイムにおいて、ゴルーチンが終了する際に常にスタックバリアをクリアするように変更します。

現在のランタイムでは、`gfput`関数内でゴルーチンのスタック割り当てが`_FixedStack`バイトである場合、そのゴルーチンのスタックバリアをクリアすることに失敗していました。これにより、以下のイベントシーケンスが発生した場合にランタイムがパニックを引き起こす可能性がありました。

1.  ランタイムがゴルーチンにスタックバリアをインストールする。
2.  ゴルーチンが`runtime.Goexit`を呼び出して終了する。この際、ゴルーチンにインストールされたスタックバリアを介して必ずしも戻るわけではないため、`g.stkbar`に未トリガーのスタックバリアが残る可能性がある。
3.  ランタイムが`gfput`を呼び出し、終了するゴルーチンをフリープールに追加する。このとき、ゴルーチンのスタック割り当てが`_FixedStack`バイトである場合、`g.stkbar`のクリアに失敗する。
4.  新しいゴルーチンが開始され、フリープールに追加されたばかりのゴルーチンを割り当てる。
5.  新しいゴルーチンが実行を開始し、以前スタックバリアがあったスタックのスロットを上書きする。
6.  ガベージコレクタがマーク終了フェーズに入り、新しいゴルーチンからスタックバリアを削除しようとするが、それらが上書きされていることを検出し、パニックを引き起こす。

この問題は、スタックを再利用する場合（`_FixedStack`の場合）にも`gfput`内でスタックバリアをクリアすることで修正されます。

Fixes #11256.

## 変更の背景

この変更は、Goランタイムのガベージコレクタ（GC）とゴルーチンのスタック管理における特定の競合状態によって引き起こされる潜在的なパニックを解決するために導入されました。GoのGCは、スタック上のオブジェクトを正確にマークするために「スタックバリア」というメカニズムを使用します。しかし、ゴルーチンが`runtime.Goexit`という特殊な方法で終了し、かつそのスタックサイズが初期の固定サイズ（`_FixedStack`）であった場合に、このスタックバリアが適切にクリーンアップされないというバグが存在しました。

具体的には、`runtime.Goexit`は通常の関数リターンとは異なり、スタックの巻き戻し（unwinding）を伴わないため、スタックバリアが「トリガーされない」まま残ることがありました。その後、このゴルーチンがフリープールに戻され、別の新しいゴルーチンに再利用されると、古いスタックバリアが残ったままのスタックが新しいゴルーチンによって上書きされる可能性がありました。最終的にGCがマーク終了フェーズでこれらの古い、上書きされたスタックバリアを処理しようとすると、整合性チェックに失敗し、ランタイムパニックが発生するという深刻な問題でした。

このバグは、Goの安定性と信頼性に直接影響を与えるため、修正が不可欠でした。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念について理解しておく必要があります。

*   **ゴルーチン (Goroutine, G):** Go言語における軽量な実行スレッドです。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行できます。Goランタイムがスケジューリングとスタック管理を行います。
*   **スタック (Stack):** 各ゴルーチンは独自の実行スタックを持っています。Goのスタックは動的に伸縮可能であり、必要に応じて自動的に拡張されます。
*   **`_FixedStack`:** ゴルーチンが最初に割り当てられるスタックの最小サイズです。Goランタイムは、新しいゴルーチンを作成する際に、まずこの固定サイズのスタックを割り当てます。このサイズを超えるスタックが必要になった場合、より大きなスタックが割り当てられ、既存のスタックの内容がコピーされます。
*   **スタックバリア (Stack Barriers):** Goの並行ガベージコレクタがスタック上のポインタを正確にスキャンするために使用するメカニズムです。スタックバリアは、スタックの特定の場所に配置される特別な値やマーカーとして機能します。GCがスタックをスキャンする際、これらのバリアを検出してスタックの構造やポインタの有効性を判断します。スタックが拡張されたり、GCがスタックをスキャンする必要がある場合にインストールされます。
*   **`runtime.Goexit()`:** 現在実行中のゴルーチンを終了させるためのGoランタイム関数です。通常の関数からのリターンとは異なり、`Goexit`は呼び出し元の関数に戻らず、現在のゴルーチンを直接終了させます。この特性が、スタックバリアのクリーンアップ問題を引き起こす一因となりました。通常の関数リターンでは、スタックが巻き戻される過程でスタックバリアが適切に処理されることが期待されますが、`Goexit`ではそれが保証されません。
*   **`gfput` 関数:** Goランタイム内部の関数で、終了したゴルーチンをフリープール（再利用可能なゴルーチンのリスト）に戻す役割を担います。ゴルーチンを再利用することで、新しいゴルーチンをゼロから割り当てるオーバーヘッドを削減し、パフォーマンスを向上させます。
*   **ガベージコレクタ (GC) のマーク終了フェーズ (Mark Termination):** GoのGCは、マーク＆スイープ方式を採用しています。マークフェーズでは、到達可能なオブジェクトをマークし、マーク終了フェーズでは、マークフェーズの完了を待ち、次のスイープフェーズの準備をします。このフェーズ中に、GCはスタックバリアの状態をチェックし、必要に応じて削除しようとします。

## 技術的詳細

このバグは、Goランタイムのゴルーチン管理とガベージコレクションの相互作用における微妙な競合状態に起因していました。

1.  **スタックバリアのインストール**: GoのGCは、スタック上のポインタを正確に追跡するためにスタックバリアを使用します。特定の条件下（例えば、GCがスタックをスキャンする必要がある場合や、スタックが拡張される可能性がある場合）で、ランタイムはゴルーチンのスタックにこれらのバリアをインストールします。これらのバリアは`g.stkbar`というフィールドに記録されます。
2.  **`runtime.Goexit`による終了**: 問題の核心は、ゴルーチンが`runtime.Goexit()`を呼び出して終了する点にありました。通常の関数リターンでは、スタックが順序立てて巻き戻され、その過程でスタックバリアも適切に処理（トリガーまたはクリア）されます。しかし、`runtime.Goexit()`はスタックの巻き戻しを行わないため、`g.stkbar`に記録されたスタックバリアが未処理のまま残る可能性がありました。
3.  **`gfput`での不完全なクリーンアップ**: ゴルーチンが終了すると、`gfput`関数が呼び出され、そのゴルーチンをフリープールに戻します。ここで、`gfput`はゴルーチンのスタックが`_FixedStack`サイズを超えて拡張されていた場合、そのスタックを解放し、`g.stkbar`もクリアしていました。しかし、ゴルーチンのスタックが`_FixedStack`サイズ内に収まっていた場合、スタック自体は解放されず、将来のゴルーチンに再利用されることになります。このシナリオでは、`g.stkbar`がクリアされないという問題がありました。
4.  **スタックの再利用と上書き**: フリープールに戻されたゴルーチン（と、それに付随するスタック）が、新しいゴルーチンに再割り当てされると、新しいゴルーチンは古いスタックバリアが残ったままのスタックを使用することになります。新しいゴルーチンが実行を開始すると、以前スタックバリアが配置されていたメモリ領域を上書きしてしまう可能性があります。
5.  **GCパニック**: その後、ガベージコレクタがマーク終了フェーズに入り、この新しいゴルーチンのスタックバリアを処理しようとします。しかし、スタックバリアが上書きされているため、GCは期待する値を見つけることができず、スタックの整合性チェックに失敗し、ランタイムパニックを引き起こしていました。

この修正は、`gfput`関数において、スタックが`_FixedStack`サイズで再利用される場合でも、`g.stkbar`を明示的にクリアすることで、この競合状態を解消します。これにより、古いスタックバリアが新しいゴルーチンに引き継がれて上書きされることがなくなり、GCのパニックが防止されます。

// run

// Copyright 2015 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

// Test that stack barriers are reset when a goroutine exits without
// returning.

package main

import (
	"runtime"
	"sync/atomic"
	"time"
)

func main() {
	// Let the garbage collector run concurrently.
	runtime.GOMAXPROCS(2)

	var x [100][]byte

	for i := range x {
		var done int32

		go func() {
			// Use enough stack to get stack barriers, but
			// not so much that we go over _FixedStack.
			// There's a very narrow window here on most
			// OSs, so we basically can't do anything (not
			// even a time.Sleep or a channel).
			var buf [1024]byte
			buf[0]++
			for atomic.LoadInt32(&done) == 0 {
				runtime.Gosched()
			}
			atomic.StoreInt32(&done, 0)
			// Exit without unwinding stack barriers.
			runtime.Goexit()
		}()

		// Generate some garbage.
		x[i] = make([]byte, 1024*1024)

		// Give GC some time to install stack barriers in the G.
		time.Sleep(50 * time.Microsecond)
		atomic.StoreInt32(&done, 1)
		for atomic.LoadInt32(&done) == 1 {
			runtime.Gosched()
		}
	}
}
```

## コアとなるコードの解説

### `src/runtime/proc1.go` の変更

`gfput`関数は、ゴルーチンが終了した際にそのゴルーチン構造体（`gp`）をフリープールに戻す役割を担います。この関数内には、ゴルーチンのスタックが解放されるべきかどうかを判断する条件分岐がありました。

変更前のコードでは、ゴルーチンのスタックが`_FixedStack`サイズを超えて拡張されていた場合（つまり、`stackfree`が呼び出されるパス）、`gp.stkbar = nil`と`gp.stkbarPos = 0`が実行され、スタックバリア情報がクリアされていました。しかし、スタックが`_FixedStack`サイズ内に収まっており、スタック自体が解放されずに再利用される場合（`else`パス）、`gp.stkbar`はクリアされませんでした。

このコミットでは、この`else`ブロックに以下の行が追加されました。

```go
		// Reset stack barriers.
		gp.stkbar = gp.stkbar[:0]
		gp.stkbarPos = 0
```

*   `gp.stkbar = gp.stkbar[:0]`：これはスライス`gp.stkbar`を長さ0にリセットする操作です。これにより、スライスが保持していた以前のスタックバリアのエントリが効果的にクリアされます。基盤となる配列はまだ存在しますが、スライスは空であると見なされ、新しいバリアが追加される準備が整います。
*   `gp.stkbarPos = 0`：`stkbarPos`は、スタックバリアがインストールされる次の位置を示すインデックスです。これを0にリセットすることで、新しいゴルーチンがこのスタックを再利用する際に、スタックバリアの記録が最初から始まることを保証します。

この変更により、ゴルーチンのスタックが`_FixedStack`サイズで再利用される場合でも、古いスタックバリア情報が確実にクリアされるようになり、GCパニックの原因が取り除かれました。

### `test/fixedbugs/issue11256.go` の解説

このテストは、修正されたバグを再現し、修正が正しく機能することを確認するために作成されました。

1.  **`runtime.GOMAXPROCS(2)`**: ガベージコレクタが並行して動作するように設定し、GCがスタックバリアをインストールする機会を増やします。
2.  **`var x [100][]byte`**: 100個のゴルーチンと、GCをトリガーするための大きなバイトスライスを生成する準備をします。
3.  **ゴルーチンの生成**:
    *   `var buf [1024]byte`：このバッファは、ゴルーチンが`_FixedStack`サイズを超えない範囲で、スタックバリアがインストールされるのに十分なスタックを使用するように意図されています。コメントにもあるように、`_FixedStack`を超えない範囲でスタックバリアを誘発する「非常に狭いウィンドウ」を狙っています。
    *   `for atomic.LoadInt32(&done) == 0 { runtime.Gosched() }`：メインゴルーチンからのシグナルを待機します。
    *   `runtime.Goexit()`：これがバグ再現の鍵です。通常の関数リターンではなく`Goexit`を使用することで、スタックバリアが適切にクリーンアップされないシナリオをシミュレートします。
4.  **メインゴルーチンの動作**:
    *   `x[i] = make([]byte, 1024*1024)`：大量のメモリを割り当てることで、ガベージコレクタの実行を促します。
    *   `time.Sleep(50 * time.Microsecond)`：GCがスタックバリアをインストールするのに十分な時間を与えます。
    *   `atomic.StoreInt32(&done, 1)`：子ゴルーチンに終了を指示します。
    *   `for atomic.LoadInt32(&done) == 1 { runtime.Gosched() }`：子ゴルーチンが終了するのを待ちます。

このテストは、複数のゴルーチンが`_FixedStack`内で`Goexit`を呼び出して終了し、そのスタックが再利用されるという、バグが発生する可能性のある特定のシーケンスを意図的に作り出すことで、修正が有効であることを検証します。

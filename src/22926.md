# [インデックス 22926] ファイルの概要

このコミットは、Goのビルドシステムにおいて、パッケージのインストール先ディレクトリ（`$GOPATH/pkg/linux_amd64`のようなアーキテクチャ依存のパス）を`go/build.Package`構造体に`PkgTargetRoot`フィールドとして追加し、その計算ロジックを一元化するものです。これにより、`cmd/go`ツール内で重複していた同様のパス計算を排除し、特に`-buildmode=shared`のような新しいビルドモードへの対応を容易にしています。

## 元コミット内容

`cmd/go`および`go/build`パッケージに`build.Package.PkgTargetRoot`を追加します。

これは`$GOPATH/pkg/linux_amd64`のようなパスを指します。`cmd/go`は既にこのパスを不格好に計算していましたが、`-buildmode=shared`のために別の計算を追加する必要がありました。

## 変更の背景

Goのビルドシステムでは、コンパイルされたパッケージ（`.a`ファイルなど）は通常、`$GOPATH/pkg`以下の特定のディレクトリに保存されます。このディレクトリは、オペレーティングシステム（`GOOS`）とアーキテクチャ（`GOARCH`）、そして場合によってはインストールサフィックス（`InstallSuffix`）によって決定されます。例えば、Linux AMD64環境では`$GOPATH/pkg/linux_amd64`となります。

このコミット以前は、`cmd/go`ツール内でこのアーキテクチャ依存のパッケージルートパスを計算するロジックが複数箇所に散在していました。コミットメッセージにある「grotty calculation（不格好な計算）」とは、この重複した、あるいは最適化されていない計算処理を指しています。

`-buildmode=shared`のような新しいビルドモードが導入される際、同様のパス計算がさらに必要となることが予想されました。このような状況で、同じロジックを何度も記述することは、コードの重複、保守性の低下、そして将来的な変更の困難さにつながります。

このコミットの目的は、このアーキテクチャ依存のパッケージルートパスの計算を`go/build`パッケージ内の`Package`構造体に一元化し、`PkgTargetRoot`という新しいフィールドとして提供することです。これにより、`cmd/go`のようなツールは、このパスを再計算する代わりに、`Package`構造体から直接取得できるようになり、コードの簡素化と保守性の向上が図られます。

## 前提知識の解説

### Goのワークスペースと`GOPATH`

Goのプロジェクトは、通常「ワークスペース」と呼ばれる特定のディレクトリ構造で管理されます。このワークスペースのルートは環境変数`GOPATH`で指定されます。`GOPATH`は、Goのソースコード、コンパイル済みパッケージ、および実行可能バイナリが配置される場所を定義します。

`GOPATH`の典型的な構造は以下の通りです。
- `src/`: ソースコードが配置されます。各リポジトリやパッケージはここに独自のディレクトリを持ちます。
- `pkg/`: コンパイルされたパッケージアーカイブ（`.a`ファイルなど）が配置されます。このディレクトリはさらに`GOOS_GOARCH`（例: `linux_amd64`）のようなサブディレクトリに分かれ、異なるOS/アーキテクチャ向けのパッケージが区別されます。
- `bin/`: `go install`コマンドでインストールされた実行可能バイナリが配置されます。

### `go/build`パッケージ

`go/build`パッケージは、Goのソースコードパッケージに関する情報（インポートパス、依存関係、ファイルリストなど）を解析するための標準ライブラリです。`go build`や`go install`といったコマンドラインツールは、このパッケージを利用してGoのソースツリーを理解し、ビルドプロセスを実行します。

`build.Package`構造体は、単一のGoパッケージに関する詳細な情報（例: `ImportPath`, `Dir`, `GoFiles`, `PkgRoot`など）を保持します。このコミットでは、この構造体に`PkgTargetRoot`が追加されます。

### Goのコンパイラ: `gc`と`gccgo`

Goには主に2つの公式コンパイラがあります。
- **`gc`**: Goチームが開発している標準のGoコンパイラです。Goのリリースに同梱されており、ほとんどのGo開発者が日常的に使用しています。高速なコンパイルとGoランタイムとの密接な統合が特徴です。
- **`gccgo`**: GCC（GNU Compiler Collection）のフロントエンドとして実装されたGoコンパイラです。`gc`とは異なるコード生成バックエンドを使用しており、C/C++コードとの連携や、特定のアーキテクチャでの最適化など、GCCの豊富な機能を活用できる場合があります。

これらのコンパイラは、コンパイル済みパッケージの保存パスの命名規則にわずかな違いがあります。例えば、`gccgo`は`pkg/gccgo_GOOS_GOARCH`のようなパスを使用することがあります。

### `InstallSuffix`

`InstallSuffix`は、`go build`や`go install`コマンドでパッケージをインストールする際に、生成されるパッケージパスに付加されるサフィックスです。これは、異なるビルド設定（例: Cgoの有無、特定のビルドタグ）でコンパイルされた同じパッケージが、互いに衝突しないようにするために使用されます。例えば、`go install -tags=foo`でビルドした場合、`pkg/linux_amd64_foo`のようなディレクトリにインストールされることがあります。

### `-buildmode=shared`

Go 1.5で導入されたビルドモードの一つで、Goパッケージを共有ライブラリ（`.so`や`.dll`など）としてビルドすることを可能にします。これにより、複数のGoプログラムが同じ共有ライブラリをリンクしたり、C/C++プログラムからGoの機能を呼び出したりすることが容易になります。共有ライブラリのビルドは、通常のパッケージビルドとは異なるパスや依存関係の管理を必要とすることがあります。

## 技術的詳細

このコミットの核心は、Goのビルドシステムにおけるアーキテクチャ依存のパッケージインストールルートパスの計算ロジックを`go/build`パッケージに集約し、`build.Package`構造体の新しいフィールド`PkgTargetRoot`として公開することです。

以前は、`cmd/go`のようなツールが、`$GOPATH/pkg/GOOS_GOARCH`（または`gccgo`の場合は`$GOPATH/pkg/gccgo_GOOS_GOARCH`、`InstallSuffix`がある場合はそれも含む）のようなパスを、必要に応じてその場で計算していました。この計算は、`GOOS`、`GOARCH`、使用しているコンパイラ（`gc`か`gccgo`か）、そして`InstallSuffix`の有無によって分岐する複雑なものでした。

新しい`PkgTargetRoot`フィールドは、`go/build.Context.Import`メソッド内で、パッケージのインポート時に一度だけ正確に計算され、`Package`構造体に格納されます。これにより、この情報が必要な他の場所（例: `cmd/go`の`builder.includeArgs`関数）では、複雑なパス計算ロジックを繰り返す必要がなくなり、`a1.p.build.PkgTargetRoot`のようにシンプルに参照できるようになります。

具体的には、`go/build/build.go`の`Context.Import`メソッド内で、コンパイラの種類（`gc`または`gccgo`）と`InstallSuffix`に基づいて`pkgtargetroot`という一時変数が計算されます。
- `gccgo`の場合: `pkg/gccgo_` + `GOOS` + `_` + `GOARCH`
- `gc`の場合: `pkg/` + `GOOS` + `_` + `GOARCH` + `InstallSuffix`（存在する場合）

この計算された`pkgtargetroot`は、最終的に`Package`構造体の`PkgTargetRoot`フィールドに`ctxt.joinPath(p.Root, pkgtargetroot)`として設定されます。ここで`p.Root`は、パッケージが存在するGoツリーのルート（通常は`GOPATH`のエントリの一つ）です。

この変更により、ビルドシステム全体の整合性が向上し、将来的に新しいビルドモードやコンパイラが追加された場合でも、パス計算ロジックの変更が`go/build`パッケージ内の単一の場所で管理されるようになります。

## コアとなるコードの解説

### `src/cmd/go/build.go` の変更点

`cmd/go/build.go`の`builder.includeArgs`関数は、ビルド時にコンパイラに渡すインクルードパスを決定する役割を担っています。変更前は、この関数内で`buildToolchain`の種類（`gccgo`かそれ以外か）や`InstallSuffix`の有無に応じて、`$GOPATH/pkg/GOOS_GOARCH`のようなパスを動的に構築していました。これは、`go/build`パッケージが既に持っているべき情報であり、`cmd/go`側で重複して計算する必要のないものでした。

変更後は、`a1.p.build.PkgTargetRoot`という形で、`go/build`パッケージの`Package`構造体から直接このパスを取得するようになりました。これにより、`cmd/go`のコードはより簡潔になり、パス計算のロジックが`go/build`パッケージに一元化されたことで、保守性が向上しました。

### `src/go/build/build.go` の変更点

このファイルは、Goのビルドシステムの中核をなす`go/build`パッケージの一部です。

1.  **`Package`構造体への`PkgTargetRoot`フィールドの追加**:
    `type Package struct { ... PkgTargetRoot string ... }`
    この新しいフィールドは、コンパイル済みパッケージがインストールされるアーキテクチャ依存のルートディレクトリ（例: `$GOPATH/pkg/linux_amd64`）を保持します。これにより、この情報が必要な他のコンポーネントが、`Package`オブジェクトから直接このパスを取得できるようになります。

2.  **`Context.Import`関数内での`PkgTargetRoot`の計算と設定**:
    `Context.Import`関数は、Goのソースコードを解析し、そのパッケージに関する詳細な情報を`Package`構造体として返す主要な関数です。
    変更前は、パッケージアーカイブファイル（`.a`ファイル）のパスである`pkga`を構築する際に、`GOOS`、`GOARCH`、コンパイラ、`InstallSuffix`といった情報に基づいてパスが動的に生成されていました。このコミットでは、そのパス生成ロジックの一部を抽出し、`pkgtargetroot`という一時変数に割り当てています。

    - `case "gccgo":` ブロックでは、`pkgtargetroot`が`"pkg/gccgo_" + ctxt.GOOS + "_" + ctxt.GOARCH`として設定されます。これは`gccgo`コンパイラが使用するパッケージルートの命名規則です。
    - `case "gc":` ブロックでは、`pkgtargetroot`が`"pkg/" + ctxt.GOOS + "_" + ctxt.GOARCH + suffix`として設定されます。これは標準の`gc`コンパイラが使用する命名規則で、`InstallSuffix`も考慮されます。

    この`pkgtargetroot`は、その後`pkga`の構築にも再利用されます。
    そして最も重要なのは、`if pkga != ""`のブロック内で、`p.PkgTargetRoot = ctxt.joinPath(p.Root, pkgtargetroot)`という行が追加されたことです。これにより、計算されたアーキテクチャ依存のパッケージルートパスが、`Package`構造体の`PkgTargetRoot`フィールドに正式に格納されるようになりました。`ctxt.joinPath`は、プラットフォームに応じたパス結合を行うヘルパー関数です。

この一連の変更により、Goのビルドシステムは、パッケージのインストールパスに関する情報をより構造化された形で管理できるようになり、コードの重複を減らし、将来的な拡張性を高めています。

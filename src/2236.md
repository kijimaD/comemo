## 変更の背景

このコミットには、主に2つの目的があります。

1.  **空間効率の改善**: 擬似乱数生成器が使用する内部状態（`rng_cooked`配列）の初期化方法を見直し、メモリ空間の利用効率を向上させることを目指しています。初期のGo言語では、ランタイムのフットプリントとパフォーマンスが非常に重視されており、このような最適化は頻繁に行われていました。
2.  **シード処理のバグ修正**: 擬似乱数生成器のシード（乱数の初期値）設定にバグが存在していました。具体的には、異なるシード値を与えても、生成される乱数の上位11ビットが常に同じ値になってしまうという問題です。これは、乱数の品質、特にその予測不可能性と均一性に深刻な影響を与えます。乱数の上位ビットが固定されると、生成される乱数列の多様性が失われ、統計的なテストに失敗したり、セキュリティ上の脆弱性につながる可能性があります。このバグを修正し、シード値が乱数生成の初期状態全体に適切に反映されるようにすることが喫緊の課題でした。

## 前提知識の解説

### 擬似乱数生成器 (PRNG)

擬似乱数生成器（Pseudo-Random Number Generator, PRNG）は、決定論的なアルゴリズムを用いて、統計的にはランダムに見える数列を生成するプログラムです。真の乱数とは異なり、PRNGは初期値（シード）が同じであれば常に同じ数列を生成します。この特性は、再現性が必要なシミュレーションやテストなどで有用ですが、予測不可能性が求められる暗号技術などでは、高品質なPRNGや真の乱数生成器（TRNG）が不可欠です。

### 線形合同法 (Linear Congruential Generator, LCG)

このコミットで変更されている乱数生成器は、線形合同法（LCG）に基づいています。LCGは、以下の漸化式で定義されます。

`X_{n+1} = (aX_n + c) mod m`

ここで、
*   `X_n` は現在の乱数
*   `X_{n+1}` は次の乱数
*   `a` は乗数（multiplier）
*   `c` は増分（increment）
*   `m` は法（modulus）

LCGは実装が単純で高速ですが、周期性があり、適切なパラメータを選ばないと生成される乱数の品質が低いという欠点があります。`src/lib/rand/rand.go` の `seedrand` 関数は、`x[n+1] = 48271 * x[n] mod (2**31 - 1)` という形式で、増分 `c` がゼロの特殊なLCG（乗算合同法）を使用しています。

### シード (Seed)

シードは、PRNGの初期状態を決定する数値です。異なるシード値を与えることで、異なる乱数列を生成できます。シードが固定されていると、PRNGは常に同じ乱数列を生成するため、予測可能な動作をします。乱数の予測不可能性を高めるためには、システム時刻やプロセスIDなど、外部の不確定な要素からシードを生成することが一般的です。

### ビット演算と乱数の品質

コンピュータにおける乱数生成では、しばしばビット演算が用いられます。特に、乱数の分布や周期性を改善するために、ビットシフト（`<<`, `>>`）やビットごとの論理演算（`^` XOR, `&` AND, `|` OR）が活用されます。
このコミットで修正された「上位11ビットが変化しない」という問題は、シード値が乱数生成器の内部状態全体に均等に影響を与えていないことを示唆しています。特に、乱数の最上位ビットが固定されると、生成される数値の範囲が実質的に狭まり、均一な分布が得られなくなります。これは、乱数の統計的特性を損ない、その用途によっては深刻な問題を引き起こす可能性があります。

### 空間効率と初期化

プログラムの初期化時に大きなデータ構造をメモリに配置する方法は、そのプログラムのメモリフットプリントに影響を与えます。特に組み込みシステムやリソースが限られた環境では、メモリ使用量を最小限に抑えることが重要です。
Go言語では、グローバル変数やパッケージレベルの変数は、プログラムの起動時に初期化されます。大きな配列をコード内で明示的に初期化する（`var rng_cooked [...]int64 = [...]int64 { ... }` のように）ことで、コンパイル時にそのデータがバイナリに埋め込まれ、実行時にはデータセグメントに配置されます。これに対し、`init()` 関数内でループなどを使って動的に配列を埋める場合、初期化ロジック自体がコードとして存在し、実行時にCPUサイクルを消費してメモリを書き込む必要があります。このコミットでは、`rng_cooked` 配列の初期値を直接コードに埋め込むことで、`init()` 関数からその初期化ロジックを削除し、実行時の初期化コストと、場合によってはコードサイズを削減しています。

## 技術的詳細

このコミットの技術的な変更点は以下の通りです。

1.  **`rng_cooked` 配列の初期化方法の変更**:
    *   変更前は、`rng_cooked` 配列は `var` 宣言のみで、その内容は `init()` 関数内でループと `seedrand` 関数を使って動的に計算・設定されていました。
    *   変更後は、`rng_cooked` 配列が宣言時に直接、膨大な数の`int64`リテラル値で初期化されるようになりました。これらの値は、コメントによると「780e10回のイテレーション後のrngの状態」を表しており、事前に計算された「調理済み（cooked）」の乱数シークエンスの一部であると考えられます。
    *   この変更により、`init()` 関数から `rng_cooked` の初期化ロジックが完全に削除され、`init()` 関数は `Seed(1)` を呼び出すだけになりました。これにより、プログラムの起動時の初期化処理が簡素化され、実行時のメモリ書き込み処理が不要になるため、空間効率と起動速度の改善に寄与します。

2.  **`_M` 定数の定義変更**:
    *   `_M` 定数が `2147483647` から `(1<<31)-1` に変更されました。これは数値としては同じ `2^31 - 1` を表しますが、ビット演算を用いた表現に変わりました。これは、コードの意図をより明確にするため、または将来的なビット幅の変更に対する柔軟性を持たせるための変更である可能性があります。`2^31 - 1` は、31ビットの符号なし整数の最大値であり、多くのLCGで法として使用される素数です。

3.  **`Seed` 関数におけるビットシフト量の修正**:
    *   `Seed` 関数内で、`u` 変数に `x` の値をビットシフトして代入する箇所が2箇所変更されました。
        *   `u = int64(x) << 20;` が `u = int64(x) << 40;` に変更。
        *   `u ^= int64(x) << 10;` が `u ^= int64(x) << 20;` に変更。
    *   この変更は、シード処理のバグ修正の核心部分です。元のシフト量（20と10）では、シード値 `x` の情報が `u` の上位ビットに十分に伝播せず、結果として生成される乱数の上位11ビットがシードに依存せず固定されてしまう問題が発生していました。シフト量を大きくする（40と20）ことで、シード値 `x` の情報が `u` のより上位のビットにまで広範囲に影響を与えるようになり、乱数の初期状態がシードによってより多様に変化するようになりました。これにより、異なるシードが与えられた際に、生成される乱数の上位ビットも適切に変化するようになり、乱数の品質が向上しました。

4.  **`Perm` 関数における要素スワップの変更**:
    *   `Perm` 関数内で配列 `m` の要素をスワップする際に、一時変数 `t` を使用していた `t = m[i]; m[i] = m[j]; m[j] = t;` という記述が、Go言語の多重代入（tuple assignment）機能を用いた `m[i],m[j] = m[j],m[i];` に変更されました。
    *   これは機能的な変更ではなく、Go言語のイディオムに合わせたコードの簡潔化と可読性の向上を目的としたリファクタリングです。

## コアとなるコードの解説

### `rng_cooked` 配列の初期化変更

`rng_cooked` は、擬似乱数生成器の内部状態の一部として使用される、事前に計算された乱数の「調理済み」シーケンスを保持する配列です。以前は、この配列はプログラム起動時に `init()` 関数内で `seedrand` 関数を繰り返し呼び出すことで動的に生成されていました。

```go
// 変更前 (概念)
var rng_cooked [_LEN]int64;
func init() {
    // ...
    for i := 0; i < _LEN; i++ {
        x = seedrand(x);
        // ... u を計算し、rng_cooked[i] に代入
    }
}
```

このコミットでは、`rng_cooked` 配列の初期値が、Goの配列リテラル構文を使って直接ソースコードに埋め込まれる形に変更されました。

```go
// 変更後
var (
    // ...
    rng_cooked  [_LEN]int64 = [...]int64 {
     5041579894721019882,  4646389086726545243,  // ...
    }
)
```

この変更の主な利点は、**空間効率の向上**です。`init()` 関数内で動的に初期化する場合、初期化ロジック自体がコードとして存在し、実行時にCPUサイクルを消費してメモリを書き込む必要があります。一方、配列リテラルとして直接初期値を埋め込むことで、コンパイル時にそのデータがバイナリのデータセグメントに配置され、実行時には単にそのメモリ領域が読み込まれるだけになります。これにより、実行時の初期化オーバーヘッドが削減され、特にプログラムの起動が高速化されます。また、コードサイズとデータサイズのバランスが最適化され、全体的なメモリフットプリントの削減に寄与する可能性があります。

### `Seed` 関数におけるビットシフト量の修正

`Seed` 関数は、擬似乱数生成器のシードを設定する役割を担っています。この関数内で、入力されたシード値 `x` を基に、内部状態を更新するための `u` という中間値を生成する際にビットシフト演算が使用されていました。

```go
// 変更前
u = int64(x) << 20;
// ...
u ^= int64(x) << 10;
```

この元の実装では、シード値 `x` の情報が `u` の上位ビットに十分に伝播しないという問題がありました。その結果、異なるシードを与えても、生成される乱数の上位11ビットが常に同じ値になってしまうというバグが発生していました。これは、乱数の均一な分布を損ない、予測可能性を高めてしまうため、乱数の品質にとって致命的です。

このコミットでは、このビットシフト量が以下のように変更されました。

```go
// 変更後
u = int64(x) << 40;
// ...
u ^= int64(x) << 20;
```

ビットシフト量を `<< 20` から `<< 40` へ、`<< 10` から `<< 20` へと増やすことで、シード値 `x` の情報が `u` のより広範囲のビットに、特に上位ビットにまで影響を与えるようになりました。これにより、シード値のわずかな変化が `u` の全体的なビットパターンに大きく影響し、結果として乱数生成器の内部状態がより多様に初期化されるようになります。この修正により、「上位11ビットが変化しない」というシード処理のバグが解消され、生成される乱数の品質と予測不可能性が大幅に向上しました。

### `Perm` 関数における要素スワップの変更

`Perm` 関数は、与えられた整数範囲 `[0, n)` の擬似乱数順列を生成します。この関数内で配列の要素をスワップする際に、Go言語の多重代入構文が導入されました。

```go
// 変更前
t := m[i];
m[i] = m[j];
m[j] = t;
```

```go
// 変更後
m[i],m[j] = m[j],m[i];
```

これは機能的な変更ではなく、Go言語の**イディオム**に合わせたコードの簡潔化と可読性の向上を目的としたリファクタリングです。Go言語では、複数の値を同時に代入できる多重代入がサポートされており、これを利用することで一時変数を使用せずに2つの変数の値を効率的に交換できます。これにより、コードがより簡潔になり、Go言語の慣習に沿った記述になります。

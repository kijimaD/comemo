## 変更の背景

Go言語は、様々なアーキテクチャとオペレーティングシステムをサポートすることを目指しています。このコミットが行われた2014年頃は、GoがPowerPC 64-bitアーキテクチャへの対応を強化していた時期にあたります。特に、IBMのPower Systemsのようなエンタープライズ環境でGoを利用するニーズが高まっていたと考えられます。

リンカー (`cmd/ld`) は、コンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリを生成する重要なツールです。新しいアーキテクチャをサポートするためには、リンカーがそのアーキテクチャ固有のバイナリフォーマット（ELF、Mach-Oなど）、リロケーション（再配置）の種類、シンボルテーブルの構造などを正しく理解し、処理できる必要があります。

このコミットは、PowerPC 64-bitアーキテクチャ（Goのビルドシステムでは通常 `ppc64` または `ppc64le` と呼ばれ、内部的には `thechar == '9'` で識別される）のサポートをリンカーに完全に統合するための、一連の変更の一部です。これにより、GoプログラムがPowerPC 64-bitシステム上でネイティブにコンパイル・実行できるようになります。

## 前提知識の解説

### Goリンカー (`cmd/ld`)

Goリンカーは、Goコンパイラ (`cmd/compile`) が生成したオブジェクトファイル（Goでは通常 `.o` 拡張子を持つ）を結合し、最終的な実行可能ファイルや共有ライブラリを生成するツールです。Plan 9リンカーをベースにGo用に改良されており、クロスコンパイルにも対応しています。リンカーは、シンボルの解決、アドレスの再配置、セクションの配置、デバッグ情報の生成など、バイナリ生成における多くの複雑なタスクを担います。

### PowerPC 64-bit (power64)

PowerPCはIBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャです。PowerPC 64-bitは、64ビットのアドレス空間とレジスタを持つPowerPCプロセッサのバリアントを指します。Go言語では、`GOARCH=ppc64` または `GOARCH=ppc64le` (little-endian) としてサポートされます。このコミットでは、Goの内部でPowerPC 64-bitを識別するために `thechar == '9'` という表記が用いられています。

### ELF (Executable and Linkable Format)

ELFは、Unix系システムで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、そして様々なセクション（コード、データ、シンボルテーブル、リロケーション情報など）で構成されます。リンカーはELFフォーマットの仕様に従ってバイナリを生成します。

### DWARF (Debugging With Attributed Record Formats)

DWARFは、ソースレベルデバッガがプログラムの実行をデバッグするために必要な情報（変数名、型、行番号、スタックフレーム情報など）をバイナリファイルに格納するための標準フォーマットです。リンカーは、コンパイラが生成したDWARF情報を結合し、最終的な実行可能ファイルに含めます。

### Mach-O

Mach-Oは、macOS（旧OS X）およびiOSで使用される実行可能ファイル、オブジェクトファイル、共有ライブラリのフォーマットです。ELFと同様に、プログラムの構造とメタデータを定義します。

### リロケーション (Relocation)

リロケーションとは、プログラムがメモリにロードされる際に、シンボル（関数や変数など）のアドレスを解決し、コード内の参照を修正するプロセスです。リンカーは、オブジェクトファイルに含まれるリロケーションエントリを読み取り、最終的な実行可能ファイル内で正しいアドレスに修正します。

-   **`R_CALL`**: 一般的な関数呼び出しのリロケーション。
-   **`R_CALLARM`**: ARMアーキテクチャ固有の関数呼び出しのリロケーション。
-   **`R_CALLPOWER`**: PowerPCアーキテクチャ固有の関数呼び出しのリロケーション。このコミットで追加された、PowerPCの呼び出し規約や命令セットに合わせたリロケーションタイプです。

### `thechar`

Goのビルドシステム内部では、ターゲットアーキテクチャを識別するために単一の文字が使われることがあります。
-   `'5'` はARM (arm)
-   `'6'` はx86-64 (amd64)
-   `'8'` はx86 (386)
-   `'9'` はPowerPC 64-bit (ppc64)

このコミットでは、既存の `amd64` (`'6'`) 向けの処理に `power64` (`'9'`) を追加するパターンが多く見られます。これは、両者が64ビットアーキテクチャであり、多くのリンキング処理で共通のロジックを共有できるためです。

## 技術的詳細

このコミットは、GoリンカーがPowerPC 64-bitアーキテクチャを適切に処理できるようにするための多岐にわたる変更を含んでいます。主な変更点は以下の通りです。

### `src/cmd/ld/data.c`

-   `blk` 関数内のシンボル処理ロジックが微調整されています。`ctxt->cursym = sym;` の位置が変更され、`if(sym->value+sym->size >= eaddr)` という条件が追加されています。これは、シンボルの値とサイズがアドレス範囲を超えないようにするためのフェーズエラーチェックの改善であり、特定のアーキテクチャに限定されないリンカーの堅牢性向上に寄与します。

### `src/cmd/ld/doc.go`

-   リンカーのドキュメントが更新され、PowerPC 64-bit (`.9` ファイル) のサポートが明記されました。
    -   オブジェクトファイルの種類に `.9 files` が追加。
    -   出力バイナリ名に `9.out` が追加。
    -   `go tool` の使用例に `9l` が追加。

### `src/cmd/ld/dwarf.c`

-   DWARFデバッグ情報のリロケーション処理において、`thechar == '6'` (amd64) と同様に `thechar == '9'` (power64) も64ビットアーキテクチャとして扱われるようになりました。これにより、`.rela.debug_info` などのリロケーションセクションがpower64向けにも正しく生成されます。

### `src/cmd/ld/elf.c`

-   ELFバイナリ生成の核心部分で、`thechar == '9'` が `thechar == '6'` と同等に扱われるようになりました。
    -   `elfinit()`: ELFヘッダの初期化で、`'9'` も64ビットELF (`elf64 = 1`) として扱われます。
    -   `elfdynhash()`: ダイナミックセクションのハッシュテーブル生成で、`'9'` も `.rela.plt` を使用する64ビットリロケーションとして扱われます。
    -   `elfshreloc()`: セクションのリロケーション処理で、`'9'` も `.rela` プレフィックスと `SHT_RELA` タイプを使用する64ビットリロケーションとして扱われます。
    -   `doelf()`: ELFバイナリ全体の生成ロジックで、様々なセクション（`.rela.text`, `.rela.init_array`, `.dynsym`, `.rela` など）の処理が `'9'` にも適用されるようになりました。特に、シンボルサイズ (`ELF64SYMSIZE`) やリロケーションエントリサイズ (`ELF64RELASIZE`) が64ビットとして設定されます。
    -   `asmbelf()`: ELFヘッダの `e_machine` フィールドに `EM_PPC64` が設定されるようになりました。これは、バイナリがPowerPC 64-bitプロセッサ向けであることを示します。
    -   `elfobj`: ELFヘッダの `EI_DATA` フィールドが、アーキテクチャのエンディアン (`ctxt->arch->endian`) に応じて `ELFDATA2MSB` (ビッグエンディアン) または `ELFDATA2LSB` (リトルエンディアン) に設定されるようになりました。PowerPCはビッグエンディアンとリトルエンディアンの両方をサポートするため、これは重要な変更です。

### `src/cmd/ld/ldelf.c`

-   ELFオブジェクトファイルのロードと検証において、`thechar == '9'` の場合、オブジェクトの機械タイプが `ElfMachPower64` であり、クラスが `ElfClass64` であることを確認するチェックが追加されました。これにより、リンカーがPowerPC 64-bitのオブジェクトファイルを正しく識別し、処理できるようになります。

### `src/cmd/ld/lib.c`

-   `hostlink()`: ホストリンカー（システムリンカー）を呼び出す際に、`thechar == '9'` の場合も `-m64` オプションが渡されるようになりました。これは、64ビットバイナリを生成するためにシステムリンカーに指示するものです。
-   `stkcheck()` および `callgraph()`: スタックチェックとコールグラフ生成のロジックに、新しいリロケーションタイプ `R_CALLPOWER` が追加されました。これにより、PowerPC固有の関数呼び出しも正しく解析され、スタックフレームのサイズ計算やコールグラフの構築に反映されます。

### `src/cmd/ld/lib.h`

-   `MAXIO` という列挙型が削除されました。これは、おそらく不要になった定数のクリーンアップか、別の方法で管理されるようになったためと考えられます。直接的なPowerPCサポートとは関係ない、一般的なコードの整理です。

### `src/cmd/ld/macho.c`

-   Mach-Oバイナリ生成の初期化において、`thechar == '9'` の場合も `macho64 = 1` が設定されるようになりました。これにより、PowerPC 64-bit向けのMach-Oバイナリが64ビットフォーマットで生成されるようになります。

### `src/cmd/ld/symtab.c`

-   シンボルテーブルエントリの書き込み (`putelfsyment`) において、`thechar == '9'` の場合も `thechar == '6'` と同様に64ビットのシンボルエントリフォーマットが使用されるようになりました。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、Goリンカーの様々な部分で `thechar == '9'` (PowerPC 64-bit) のサポートを `thechar == '6'` (x86-64) と並行して追加している点です。特に、ELFバイナリの生成ロジック (`src/cmd/ld/elf.c`) と、リロケーション処理 (`src/cmd/ld/lib.c` の `R_CALLPOWER` の追加) が重要です。

例えば、`src/cmd/ld/elf.c` の `elfinit` 関数では、以下のように `case '9':` が追加されています。

```diff
--- a/src/cmd/ld/elf.c
+++ b/src/cmd/ld/elf.c
@@ -45,6 +45,7 @@ elfinit(void)
 	switch(thechar) {
 	// 64-bit architectures
 	case '6':
+	case '9':
 		elf64 = 1;
 		hdr.phoff = ELF64HDRSIZE;	/* Must be be ELF64HDRSIZE: first PHdr must follow ELF header */
 		hdr.shoff = ELF64HDRSIZE;	/* Will move as we add PHeaders */
```

また、`src/cmd/ld/lib.c` では、PowerPC固有の呼び出しリロケーション `R_CALLPOWER` が導入され、コールグラフの解析に組み込まれています。

```diff
--- a/src/cmd/ld/lib.c
+++ b/src/cmd/ld/lib.c
@@ -1146,6 +1147,7 @@ stkcheck(Chain *up, int depth)
 			switch(r->type) {
 			case R_CALL:
 			case R_CALLARM:
+			case R_CALLPOWER:
 				// Direct call.
 				ch.limit = limit - pcsp.value - callsize();
 				ch.sym = r->sym;
@@ -1525,7 +1527,7 @@ callgraph(void)
 		r = &s->r[i];
 		if(r->sym == nil)
 			continue;
-		if((r->type == R_CALL || r->type == R_CALLARM) && r->sym->type == STEXT)
+		if((r->type == R_CALL || r->type == R_CALLARM || r->type == R_CALLPOWER) && r->sym->type == STEXT)
 			Bprint(&bso, "%s calls %s\n", s->name, r->sym->name);
 	}
```

## コアとなるコードの解説

これらの変更は、GoリンカーがPowerPC 64-bitアーキテクチャのバイナリを正しく生成するために不可欠です。

-   **`elfinit` における `'9'` の追加**: これは、リンカーがPowerPC 64-bitを64ビットアーキテクチャとして認識し、ELFヘッダやプログラムヘッダのサイズ、オフセットを64ビットの仕様に合わせて初期化することを示します。これにより、生成されるELFバイナリがPowerPC 64-bitシステムで正しくロード・実行されるための基盤が作られます。

-   **`R_CALLPOWER` の導入と利用**: PowerPCアーキテクチャは、他のアーキテクチャ（x86-64やARM）とは異なる関数呼び出し規約や命令セットを持つ場合があります。`R_CALLPOWER` という新しいリロケーションタイプを導入することで、リンカーはPowerPC固有の関数呼び出し命令を正確に再配置できるようになります。また、このリロケーションタイプをスタックチェックやコールグラフ生成のロジックに組み込むことで、GoランタイムがPowerPC上で正しく動作し、デバッグ情報が正確に生成されることが保証されます。これは、Goのガベージコレクションやスケジューラが正確なスタック情報を必要とするため、非常に重要です。

全体として、これらの変更は、GoがPowerPC 64-bitアーキテクチャ上で完全に機能するための、リンカーレベルでの基盤的なサポートを確立するものです。

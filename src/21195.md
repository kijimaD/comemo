# [インデックス 21195] ファイルの概要

このコミットは、Go言語のリンカである`liblink`における最適化のバグを修正するものです。具体的には、`liblink`がジャンプ命令を最適化する際に、シンボルへのジャンプを適切に処理できず、結果として不正なジャンプ先を生成してしまう問題に対処しています。この修正により、リンカの正確性が向上し、生成されるバイナリの信頼性が確保されます。

## コミット

```
commit e04c8b063fd7d7aaded8e1ff549dbb520038c61e
Author: Austin Clements <austin@google.com>
Date:   Fri Dec 5 09:24:01 2014 -0500

    [dev.cc] liblink: don't patch jumps to jumps to symbols
    
    When liblink sees something like
    
           JMP x
           ...
        x: JMP y
    
    it rewrites the first jump to jump directly to y.  This is
    fine if y is a resolved label.  However, it *also* does this
    if y is a function symbol, but fails to carry over the
    relocation that would later patch in that symbol's value.  As
    a result, the original jump becomes either a self-jump (if
    relative) or a jump to PC 0 (if absolute).
    
    Fix this by disabling this optimization if the jump being
    patched in is a jump to a symbol.
    
    LGTM=minux
    R=rsc, minux
    CC=golang-codereviews
    https://golang.org/cl/185890044
```

## 元コミット内容

このコミットは、`liblink`がジャンプ命令の連鎖を最適化する際の不具合を修正します。`liblink`は、`JMP x`の後に`x: JMP y`のようなパターンを見つけると、最初の`JMP x`を直接`JMP y`に書き換える最適化を行います。この最適化は、`y`が既に解決されたラベルである場合には問題ありません。しかし、`y`が関数シンボルである場合にもこの最適化が適用されてしまい、そのシンボルの値を後でパッチするための再配置情報が引き継がれませんでした。その結果、元のジャンプ命令は、相対ジャンプであれば自分自身へのジャンプに、絶対ジャンプであればアドレス0へのジャンプになってしまうというバグが発生していました。この修正は、パッチされるジャンプがシンボルへのジャンプである場合に、この最適化を無効にすることで問題を解決します。

## 変更の背景

Go言語のコンパイラとリンカは、生成されるバイナリのサイズと実行速度を最適化するために様々な処理を行います。その一つに、ジャンプ命令の連鎖を短縮する最適化があります。例えば、ある場所から別の場所へジャンプし、その別の場所からさらに別の場所へジャンプする場合、リンカは最初のジャンプを最終的なジャンプ先へ直接向かうように書き換えることで、中間的なジャンプを省略し、実行効率を向上させようとします。

しかし、この最適化がシンボルへのジャンプに対して適用される際に問題が発生しました。シンボル（特に外部関数シンボル）は、リンク時にその最終的なアドレスが決定されるため、再配置（relocation）というプロセスが必要です。再配置とは、コンパイル時には不明なアドレスを、リンク時に実際のメモリ上のアドレスに置き換える処理のことです。

このコミットで修正されたバグは、`liblink`がジャンプ命令の連鎖を最適化する際に、シンボルへのジャンプが含まれている場合でも、そのシンボルに対する再配置情報を適切に引き継がなかったことに起因します。結果として、最適化されたジャンプ命令は、本来ジャンプすべきシンボルのアドレスではなく、無効なアドレス（例えば、相対ジャンプの場合は自分自身のアドレス、絶対ジャンプの場合はアドレス0）を指してしまい、プログラムのクラッシュや予期せぬ動作を引き起こしていました。この問題は、特に動的リンクや共有ライブラリを使用する際に顕在化する可能性がありました。

## 前提知識の解説

### リンカ (Linker)

リンカは、コンパイラによって生成された複数のオブジェクトファイル（機械語コードとデータを含むファイル）とライブラリを結合し、実行可能なプログラムや共有ライブラリを生成するソフトウェアです。リンカの主な役割は以下の通りです。

*   **シンボル解決 (Symbol Resolution)**: オブジェクトファイル内で参照されている関数や変数の名前（シンボル）を、他のオブジェクトファイルやライブラリで定義されている実際のメモリアドレスに解決します。
*   **再配置 (Relocation)**: コンパイル時にはアドレスが確定していないコードやデータ（例えば、外部関数へのジャンプ命令やグローバル変数の参照）について、リンク時に実際のメモリアドレスに基づいてオフセットを調整します。
*   **コード結合 (Code Merging)**: 複数のオブジェクトファイルのコードセクションとデータセクションを結合し、単一の実行可能ファイルを生成します。

### ジャンプ命令 (JMP Instruction)

アセンブリ言語における`JMP`命令は、プログラムの実行フローを現在の位置から指定された別のアドレスに無条件に転送する命令です。CPUは`JMP`命令が実行されると、プログラムカウンタ（PC）の値をジャンプ先のアドレスに更新し、そこから命令の実行を再開します。

ジャンプ命令には、相対ジャンプと絶対ジャンプがあります。

*   **相対ジャンプ**: 現在のプログラムカウンタからのオフセットでジャンプ先を指定します。例えば、「現在の位置から100バイト先にジャンプ」といった形式です。
*   **絶対ジャンプ**: メモリ上の特定のアドレスを直接指定してジャンプします。例えば、「アドレス0x12345678にジャンプ」といった形式です。

### シンボル (Symbol)

プログラミングにおいて、シンボルとは、関数名、変数名、ラベルなど、プログラム内の特定のエンティティを識別するための名前です。コンパイラはソースコードを機械語に変換する際に、これらのシンボルを生成し、オブジェクトファイル内にシンボルテーブルとして記録します。リンカは、このシンボルテーブルを参照して、未解決のシンボル参照を解決し、実際のメモリアドレスにマッピングします。

### 再配置 (Relocation)

再配置は、リンカの重要な機能の一つです。コンパイラは、ソースコードをオブジェクトファイルに変換する際、外部の関数や変数への参照のアドレスを確定できません。これらの参照は、プレースホルダー（仮のアドレスやオフセット）としてマークされます。リンカは、すべてのオブジェクトファイルとライブラリを結合する際に、これらのプレースホルダーを実際のメモリアドレスに置き換えることで、プログラムが正しく実行されるようにします。

例えば、`JMP external_function`という命令がある場合、コンパイル時には`external_function`のアドレスは不明です。リンカが`external_function`がライブラリ内の特定のアドレスにあることを解決すると、そのアドレス情報を使って`JMP`命令のオペランドを更新します。この更新プロセスが再配置です。

### `liblink`

`liblink`は、Go言語のツールチェインの一部であり、Goプログラムをリンクする役割を担うライブラリです。Goのコンパイラは、Goのソースコードを中間的なアセンブリコード（Plan 9アセンブリ）に変換し、その後、`liblink`がこのアセンブリコードを最終的な実行可能バイナリにリンクします。`liblink`は、Goランタイムの特定の最適化や、Goの並行処理モデルをサポートするための特殊なリンキング処理を行います。

## 技術的詳細

このバグは、`liblink`がジャンプ命令の連鎖を最適化する際に、再配置の必要性を適切に認識できなかったことにあります。

具体的なシナリオは以下の通りです。

1.  **元のコードパターン**:
    ```
    JMP x
    ...
    x: JMP y
    ```
    ここで、`JMP x`はプログラムのある地点からのジャンプ命令、`x`は中間的なラベル、`JMP y`は`x`からさらに`y`へのジャンプ命令です。

2.  **`liblink`の最適化**:
    `liblink`は、このようなジャンプの連鎖を見つけると、最初の`JMP x`を直接`JMP y`に書き換える最適化を行います。これにより、中間的な`x`へのジャンプが不要になり、実行パスが短縮されます。

3.  **問題の発生**:
    この最適化は、`y`がプログラム内の固定されたアドレスを持つ「解決済みのラベル」である場合には問題ありませんでした。しかし、`y`がまだアドレスが確定していない「関数シンボル」（例えば、別のオブジェクトファイルや共有ライブラリで定義されている関数）である場合に問題が発生しました。

    `liblink`は、`JMP x`を`JMP y`に書き換える際に、`y`がシンボルである場合に必要となる「再配置情報」を新しい`JMP y`命令に引き継ぎませんでした。再配置情報が欠落しているため、リンカの最終段階で`y`の実際のアドレスが決定されても、この最適化された`JMP y`命令のオペランドは更新されません。

4.  **結果**:
    再配置が行われないため、最適化された`JMP y`命令は、`y`の正しいアドレスを指すことができませんでした。
    *   **相対ジャンプの場合**: `JMP y`が相対ジャンプとして解釈されると、オペランドが0のままになるため、自分自身への無限ループジャンプ（`JMP .`）になってしまいます。
    *   **絶対ジャンプの場合**: `JMP y`が絶対ジャンプとして解釈されると、オペランドが0のままになるため、アドレス0へのジャンプになってしまいます。これは通常、プログラムのクラッシュ（セグメンテーション違反など）を引き起こします。

このコミットは、この問題を解決するために、最適化の適用条件に「パッチされるジャンプ先がシンボルではないこと」という条件を追加しました。これにより、シンボルへのジャンプを含む連鎖ジャンプは最適化の対象外となり、再配置が正しく行われるようになります。

## コアとなるコードの変更箇所

変更は`src/liblink/pass.c`ファイルにあります。

```diff
--- a/src/liblink/pass.c
+++ b/src/liblink/pass.c
@@ -41,7 +41,7 @@ brchain(Link *ctxt, Prog *p)
  	int i;
  
  	for(i=0; i<20; i++) {
- 		if(p == nil || p->as != ctxt->arch->AJMP)
+ 		if(p == nil || p->as != ctxt->arch->AJMP || p->pcond == nil)
  			return p;
  		p = p->pcond;
  	}
@@ -56,7 +56,7 @@ brloop(Link *ctxt, Prog *p)
  
  	c = 0;
  	for(q = p; q != nil; q = q->pcond) {
- 		if(q->as != ctxt->arch->AJMP)
+ 		if(q->as != ctxt->arch->AJMP || q->pcond == nil)
  			break;
  		c++;
  		if(c >= 5000)
```

この変更では、`brchain`関数と`brloop`関数の両方に、ジャンプ命令の条件として`p->pcond == nil`または`q->pcond == nil`というチェックが追加されています。

## コアとなるコードの解説

`src/liblink/pass.c`は、`liblink`の最適化パスの一部を実装しているファイルです。このファイルには、ジャンプ命令の連鎖を検出して最適化するロジックが含まれています。

*   **`brchain(Link *ctxt, Prog *p)`関数**:
    この関数は、与えられた`Prog`（プログラム命令を表す構造体）`p`から始まるジャンプ命令の連鎖を辿ります。ループ内で最大20個のジャンプ命令を辿り、その連鎖の終端にある命令を返そうとします。
    変更前は、`p == nil`（命令が存在しない）または`p->as != ctxt->arch->AJMP`（命令がアーキテクチャ固有のジャンプ命令ではない）の場合に連鎖の終端と判断していました。
    **変更点**: `p->pcond == nil`という条件が追加されました。`p->pcond`は、ジャンプ命令のターゲットとなる次の命令を指します。`p->pcond == nil`は、ジャンプ命令が次の命令へのポインタを持っていない、つまり、それがシンボルへのジャンプである可能性を示唆しています。シンボルへのジャンプは、リンカが最終的なアドレスを解決するまで`pcond`が設定されない場合があります。この条件を追加することで、シンボルへのジャンプを含む連鎖は、この最適化の対象から外れるようになります。

*   **`brloop(Link *ctxt, Prog *p)`関数**:
    この関数も同様に、ジャンプ命令のループや連鎖を検出するために使用されます。`q`は現在の命令を指し、`q->pcond`は次の命令を指します。
    **変更点**: `q->pcond == nil`という条件が追加されました。これも`brchain`関数と同様に、ジャンプ命令がシンボルへのジャンプである場合に、その連鎖の検出を中断し、最適化を適用しないようにするためのものです。

これらの変更により、`liblink`は、ジャンプ命令の連鎖を最適化する際に、その連鎖の途中に未解決のシンボルへのジャンプが含まれている場合、その最適化をスキップするようになります。これにより、シンボルに対する再配置情報が失われることなく、リンカが正しく動作するようになります。結果として、生成されるGoバイナリの安定性と正確性が向上します。

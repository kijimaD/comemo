## 変更の背景

このコミットは、Goコンパイラが複合リテラルを静的に初期化できるかどうかを判断する `isStaticCompositeLiteral` 関数におけるバグを修正するために行われました。以前の `isStaticCompositeLiteral` は、特定のネストされた複合リテラル、特に `[1]struct{ b []byte }{b: []byte{1}}` のような形式のリテラルに対して誤った結果を返していました。

問題は、外側の要素が配列であるにもかかわらず、`isStaticCompositeLiteral` が再帰的に呼び出された際に、内部の要素が再び配列であるかどうかのチェックを適切に行っていなかった点にありました。これにより、コンパイラは静的に初期化できないはずのリテラルを静的に初期化可能と誤って判断し、潜在的に不正なコード生成やランタイムエラーを引き起こす可能性がありました。

この修正の目的は、`isStaticCompositeLiteral` の内部ロジックを複雑にすることなく、あらゆる `Node` を受け入れて正しい静的複合リテラル判定を行うように改善することです。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Goコンパイラは、Go言語のソースコードを機械語に変換するツールです。`cmd/compile` はGoツールチェーンの一部であり、Goプログラムのビルドプロセスにおいて中心的な役割を担います。コンパイラは、ソースコードを抽象構文木 (AST: Abstract Syntax Tree) に変換し、様々な最適化やコード生成を行います。

### 複合リテラル (Composite Literals)

Go言語における複合リテラルは、構造体、配列、スライス、マップなどの複合型を初期化するための構文です。例えば、`[]int{1, 2, 3}` はスライスリテラル、`struct{x int}{x: 10}` は構造体リテラルです。

### 静的初期化 (Static Initialization)

静的初期化とは、プログラムの実行開始前に、コンパイル時に変数の値を決定し、その値をプログラムのデータセクションに配置することです。これにより、実行時の初期化コストを削減し、パフォーマンスを向上させることができます。Goコンパイラは、特定の条件を満たす複合リテラルを静的に初期化しようとします。

### `isStaticCompositeLiteral` 関数

`isStaticCompositeLiteral` 関数は、Goコンパイラの内部関数であり、与えられた複合リテラルが静的に初期化可能であるかどうかを判定します。静的に初期化可能であるためには、そのリテラルが完全にコンパイル時定数で構成されている必要があります。例えば、スライスは実行時にメモリ割り当てが必要なため、通常は静的に初期化できません。

### ASTノードの種類

Goコンパイラは、ソースコードをASTに変換する際に、様々な種類のノードを使用します。このコミットに関連する主なノードは以下の通りです。

*   **`OARRAYLIT`**: 配列リテラルを表すASTノード。例: `[3]int{1, 2, 3}`
*   **`OSTRUCTLIT`**: 構造体リテラルを表すASTノード。例: `MyStruct{Field: value}`
*   **`OLITERAL`**: 数値、文字列、真偽値などの基本的なリテラル値を表すASTノード。

## 技術的詳細

### 以前の `isStaticCompositeLiteral` の問題点

このコミットが修正するバグは、`isStaticCompositeLiteral` 関数がネストされた複合リテラルを処理する際のロジックの欠陥にありました。具体的には、以下のようなリテラルが問題を引き起こしました。

```go
[1]struct{ b []byte }{b: []byte{1}}
```

このリテラルは、外側が配列リテラル (`OARRAYLIT`) であり、その要素として構造体リテラル (`OSTRUCTLIT`) が含まれています。さらに、その構造体リテラルのフィールド `b` はスライスリテラル (`[]byte{1}`) です。スライスは実行時にメモリ割り当てが必要なため、静的に初期化することはできません。したがって、この全体のリテラルは静的に初期化不可能であると正しく判定されるべきです。

しかし、以前の `isStaticCompositeLiteral` の実装では、以下のような問題がありました。

1.  **初期のチェックの限定**: `isStaticCompositeLiteral` は、当初 `n must be a struct or array literal` というコメントがあったように、引数 `n` が構造体リテラルまたは配列リテラルであることを前提としていました。
2.  **再帰時のチェックの不足**: 関数が再帰的に呼び出される際、例えば `value := r.Right` の `value` が再び複合リテラルである場合、その `value` が配列リテラルであるかどうかのチェックが不十分でした。特に、`value.Op` が `OARRAYLIT` であったとしても、それがスライス型であるかどうかの判定が、再帰の深さによっては適切に行われない可能性がありました。
    以前のコードでは、`value.Op` が `OSTRUCTLIT` または `OARRAYLIT` の場合にのみ `isStaticCompositeLiteral(value)` を再帰的に呼び出し、それ以外の場合は `OLITERAL` であることを期待していました。このロジックでは、`OARRAYLIT` の内部でスライスが検出された場合に、そのスライスが静的ではないことを適切に伝播できませんでした。

結果として、`[1]struct{ b []byte }{b: []byte{1}}` のようなリテラルにおいて、外側の配列リテラルは `isStaticCompositeLiteral` の最初の呼び出しで処理されます。その後、内部の構造体リテラル、そしてスライスリテラルへと再帰的に処理が進みます。この再帰の過程で、スライスリテラルが静的ではないという情報が適切に上位に伝わらず、最終的に全体のリテラルが静的に初期化可能であると誤って判断されてしまうバグがありました。

### 修正アプローチ

このコミットでは、`isStaticCompositeLiteral` の内部ロジックを大幅に簡素化し、より堅牢な判定を行うように変更されました。主な変更点は以下の通りです。

1.  **引数の汎用化**: `isStaticCompositeLiteral` が `any Node` を受け入れるように変更されました。これにより、関数が呼び出された時点で、そのノードの `Op` (操作コード) に基づいて適切な初期チェックを行うことができるようになりました。
2.  **初期 `switch` ステートメントの導入**: 関数の冒頭に `switch n.Op` ステートメントが追加されました。
    *   `OARRAYLIT` の場合、その型がスライス (`n.Type.IsSlice()`) であれば、静的に初期化不可能であるため `false` を返します。配列型であれば処理を続行します。
    *   `OSTRUCTLIT` の場合、処理を続行します。
    *   `OLITERAL` の場合、それは静的リテラルであるため `true` を返します。
    *   上記以外の場合 (`default`) は、静的に初期化不可能であるため `false` を返します。
3.  **再帰ロジックの簡素化**: 以前のコードにあった `switch value.Op` ブロックが削除され、代わりに `if !isStaticCompositeLiteral(value) { return false }` という単一の再帰呼び出しに置き換えられました。これにより、ネストされた要素が静的であるかどうかの判定が、新しい初期 `switch` ステートメントによって一貫して処理されるようになり、ロジックが大幅に簡素化されました。

この修正により、`isStaticCompositeLiteral` は、複合リテラルのどのレベルにおいても、スライスのような静的に初期化できない要素を正確に検出し、適切な `false` を返すことができるようになりました。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/sinit.go` の変更

*   **`isStaticCompositeLiteral` 関数のシグネチャと初期チェックの変更**:
    *   以前のコメント `// n must be a struct or array literal.` が削除され、関数がより汎用的な `Node` を受け入れるようになったことを示唆しています。
    *   関数の冒頭に新しい `switch n.Op` ブロックが追加されました。
        *   `OARRAYLIT` の場合、`n.Type.IsSlice()` でスライス型であるかをチェックします。スライスであれば `false` を返し、静的に初期化できないことを明示します。配列型であれば、後続の要素チェックに進みます。
        *   `OSTRUCTLIT` の場合、構造体の要素チェックに進みます。
        *   `OLITERAL` の場合、これは基本的なリテラルであり静的であるため `true` を返します。
        *   `default` ケースでは、上記以外のノードタイプは静的複合リテラルではないため `false` を返します。
*   **再帰ロジックの簡素化**:
    *   以前の `switch value.Op` ブロックが削除されました。このブロックは、`value` が `OSTRUCTLIT` または `OARRAYLIT` の場合にのみ再帰呼び出しを行い、それ以外の場合は `OLITERAL` であることを期待していました。
    *   新しいコードでは、`if !isStaticCompositeLiteral(value) { return false }` という単一の再帰呼び出しに置き換えられています。これにより、`value` がどのような `Node` であっても、関数の冒頭で追加された新しい `switch n.Op` ロジックによって適切に静的判定が行われるようになります。この変更により、ロジックがよりクリーンになり、ネストされた複合リテラルの静的判定がより正確になりました。
*   **`anylit` 関数の `Fatalf` メッセージの改善**:
    *   `anylit` 関数内の `Fatalf` メッセージが、`op=%v node=%v` を含むように変更され、デバッグ情報が豊富になりました。これは直接的なバグ修正ではありませんが、コンパイラ内部エラー発生時の診断を容易にします。

### `src/cmd/compile/internal/gc/walk.go` の変更

*   **`OARRAYLIT`, `OMAPLIT`, `OSTRUCTLIT`, `OPTRLIT` ケースの条件式の簡素化**:
    *   以前のコードでは、`isStaticCompositeLiteral(n)` を呼び出す前に、`n.Op == OSTRUCTLIT || (n.Op == OARRAYLIT && !n.Type.IsSlice())` という複雑な条件式で `n` が構造体リテラルまたは非スライス配列リテラルであることを確認していました。
    *   このコミットでは、この条件式が `isStaticCompositeLiteral(n)` の単一の呼び出しに置き換えられました。これは、`isStaticCompositeLiteral` 関数自体が、その冒頭の `switch n.Op` ブロックによって、これらのチェックを内部で適切に行うようになったためです。これにより、`walk.go` のコードが簡素化され、ロジックの重複が排除されました。

これらの変更により、Goコンパイラは複合リテラルの静的初期化をより正確に判断できるようになり、特にネストされた複合リテラルにおける潜在的なバグが解消されました。

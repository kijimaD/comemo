# [インデックス 20318] ファイルの概要

このコミットは、Go言語のランタイムプロファイリングツールである`pprof`のCPUプロファイリングテストの堅牢性を向上させるための変更です。特に、Goの競合検出器（race detector）が有効な環境下でのテストの不安定性を解消することを目的としています。

## 変更の背景

このコミットの主な背景は、Goの競合検出器（race detector）が有効な状態でCPUプロファイリングテストを実行した際に発生していたテストの不安定性です。特に、FreeBSD環境でのビルドボット（`freebsd race builder`）がこのテストで頻繁に失敗していました。

CPUプロファイリングは、プログラムがCPU時間をどこで消費しているかを特定するために使用されます。しかし、競合検出器が有効な場合、検出器自体が多くのCPU時間を消費し、その活動がプロファイルサンプルに記録されてしまいます。これにより、本来プロファイルしたいアプリケーションコードではなく、競合検出器のランタイムコードに多くのサンプルが偏ってしまい、テストが期待する結果（特定の関数にCPU時間が集中していること）を検出できなくなっていました。

この問題に対処するため、プロファイリングの対象となる「CPUを大量に消費する（CPU hogging）」コードを、競合検出器の影響を受けにくいように変更し、テストの堅牢性を高める必要がありました。

## 前提知識の解説

### Goのプロファイリング（pprof）

Goには、プログラムのパフォーマンス特性を分析するための組み込みプロファイリングツールキット`pprof`が用意されています。これには、CPUプロファイル、メモリプロファイル、ゴルーチンプロファイル、ブロックプロファイル、ミューテックスプロファイルなどがあります。

*   **CPUプロファイル**: プログラムがCPU時間をどこで消費しているかをサンプリングによって記録します。デフォルトでは100Hz（1秒間に100回）でサンプリングが行われ、各サンプリング時に実行されていた関数のコールスタックが記録されます。これにより、どの関数が最もCPUを消費しているかを特定できます。

### Goの競合検出器（Race Detector）

Goの競合検出器は、複数のゴルーチンが共有メモリに同時にアクセスし、少なくとも1つのアクセスが書き込みである場合に発生するデータ競合（data race）を検出するためのツールです。データ競合は、プログラムの予測不能な動作やバグの原因となることが多く、検出が困難な場合があります。

*   **動作原理**: 競合検出器は、プログラムの実行中にメモリアクセスを監視し、競合のパターンを検出します。これを実現するために、検出器は追加のインストゥルメンテーション（計測コード）をプログラムに挿入し、実行時にメモリアクセスの履歴を追跡します。
*   **パフォーマンスへの影響**: 競合検出器は、プログラムの実行速度を大幅に低下させ（通常、数倍から数十倍）、メモリ使用量も増加させます。これは、検出器が多くの追加処理を行うためです。
*   **プロファイルへの影響**: 競合検出器が有効な場合、その内部処理（メモリアクセスの追跡、ロックの取得など）がCPU時間を消費します。この消費されたCPU時間は、CPUプロファイルに「競合ランタイム（race runtime）」として現れる可能性があります。もしプロファイル対象のコードが非常に短時間で実行される場合や、競合検出器のオーバーヘッドが大きい場合、プロファイルサンプルの大部分が競合ランタイムに偏ってしまい、本来のアプリケーションコードのプロファイルが困難になることがあります。

### `crc32.ChecksumIEEE`

`hash/crc32`パッケージは、CRC-32チェックサムを計算するためのGoの標準ライブラリです。`crc32.ChecksumIEEE`関数は、指定されたバイトスライスに対してIEEEポリノミアルを使用したCRC-32チェックサムを計算します。この関数は、データ処理においてCPUを比較的消費する操作であり、プロファイリングテストの対象として適切でした。しかし、この関数が内部でメモリを読み込むため、競合検出器が有効な場合にその監視対象となり、競合ランタイムにサンプルが偏る原因となっていました。

## 技術的詳細

このコミットの技術的な核心は、CPUプロファイリングテストの対象となる「CPUを消費する処理」を、競合検出器の影響を最小限に抑えるように再設計した点にあります。

元のテストでは、`crc32.ChecksumIEEE`関数を使用してCPU負荷を生成していました。この関数はバイトスライス（`buf`）を読み込むため、競合検出器が有効な場合、そのメモリ読み込み操作が検出器の監視対象となり、検出器の内部処理（競合ランタイム）に多くのCPUサンプルが記録されていました。結果として、プロファイルデータが`crc32.ChecksumIEEE`ではなく、競合検出器のコードに偏ってしまい、テストが意図した結果（`crc32.ChecksumIEEE`がプロファイルに現れること）を検証できなくなっていました。

新しいアプローチでは、以下の変更が導入されました。

1.  **カスタムのCPU消費関数（`cpuHog1`, `cpuHog2`）の導入**:
    *   これらの関数は、ループ内で単純な整数演算（`foo *= foo`や`foo *= foo + 1`など）を実行することでCPU時間を消費します。
    *   重要なのは、これらの関数が**ループ内で他の関数を呼び出したり、ヒープやグローバル変数にアクセスしたりしない**ように設計されている点です。これにより、競合検出器が有効な場合でも、その監視対象となるメモリ操作が最小限に抑えられ、プロファイルサンプルが競合ランタイムに偏ることを防ぎます。
    *   `salt1`と`salt2`というグローバル変数が導入されていますが、これらはループの開始時に一度読み込まれ、ループの終了時に一度書き込まれるだけで、ホットパス（ループ内）での頻繁なアクセスは避けています。これは、コンパイラによる最適化（ループの削除など）を防ぎ、実際にCPU時間を消費させるための工夫でもあります。

2.  **`cpuHogger`ヘルパー関数の導入**:
    *   この関数は、引数として渡されたCPU消費関数（`cpuHog1`や`cpuHog2`）を、プロファイルに必要な十分な時間（少なくとも250ミリ秒、または500回のイテレーション）実行することを保証します。
    *   これにより、プロファイルサンプリングの粒度（100Hz）に対して十分なCPU時間が確保され、テストが安定して期待するサンプルを捕捉できるようになります。

これらの変更により、CPUプロファイリングテストは、競合検出器のオーバーヘッドに左右されずに、純粋なCPU消費ロジックを正確にプロファイルできるようになり、テストの堅牢性が大幅に向上しました。

## コアとなるコードの解説

1.  **`hash/crc32`パッケージの削除**:
    *   `crc32.ChecksumIEEE`関数が使用されなくなったため、関連する`hash/crc32`パッケージのインポートが削除されました。

2.  **`cpuHogger`関数の追加**:
    *   この関数は、引数として渡された関数`f`を繰り返し実行し、CPUプロファイルが十分にサンプリングされるようにします。
    *   `t0 := time.Now()`と`time.Since(t0) < 250*time.Millisecond`により、少なくとも250ミリ秒間は処理が実行されることを保証します。
    *   `i < 500`という条件は、非常に高速なマシンでも最低限のイテレーションが実行されることを保証し、特にマルチスレッドテストで単一スレッドがスケジュールされる時間が短い場合にテストが失敗するのを防ぎます。

3.  **`salt1`, `salt2`グローバル変数の追加**:
    *   これらの変数は、`cpuHog1`と`cpuHog2`関数内で使用されるローカル変数の初期値として機能します。
    *   コンパイラがループを完全に最適化して削除してしまうのを防ぐために、ループの外部で値を保持し、ループの最後に更新する目的で導入されています。

4.  **`cpuHog1`, `cpuHog2`関数の追加**:
    *   これらは、CPUを意図的に消費させるための新しい関数です。
    *   コメントにあるように、「ループ内で他の関数を呼び出したり、ヒープ/グローバルにアクセスしたりしてはならない」という制約があります。これは、競合検出器が有効な場合に、プロファイルサンプルが競合ランタイムに偏るのを防ぐためです。
    *   内部では、単純な整数演算（`foo *= foo`や`foo *= foo + 1`、`foo *= foo + 2`）を10万回繰り返すことでCPU時間を消費します。これにより、純粋な計算処理がプロファイルの対象となります。

5.  **`TestCPUProfile`関数の変更**:
    *   以前は`crc32.ChecksumIEEE(buf)`を直接呼び出していましたが、新しい`cpuHogger(cpuHog1)`に置き換えられました。
    *   `buf`の作成も不要になりました。
    *   これにより、テストは競合検出器の影響を受けにくい、より制御されたCPU負荷をプロファイルできるようになります。

6.  **`TestCPUProfileMultithreaded`関数の変更**:
    *   このマルチスレッドテストでも同様に、`crc32.Update`と`crc32.ChecksumIEEE`の代わりに、`cpuHogger(cpuHog1)`と`cpuHogger(cpuHog2)`が使用されるようになりました。
    *   これにより、複数のゴルーチンがそれぞれ異なるCPU消費関数を実行し、それらがプロファイルに適切に現れることを検証できるようになります。

7.  **`testCPUProfile`関数のコメント変更**:
    *   プロファイルの内容をチェックするコメントが、`ChecksumIEEE`を含むことを確認する内容から、`need`（期待される関数名のリスト）を含むことを確認する内容に変更されました。これは、プロファイル対象の関数が動的に変更されたことに対応するものです。

これらの変更により、GoのCPUプロファイリングテストは、競合検出器が有効な環境下でも安定して動作し、プロファイリング機能の正確な検証が可能になりました。

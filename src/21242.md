## 変更の背景

このコミットは、Goランタイムにおけるスタック管理メカニズムの根本的な変更を反映したものです。Goは当初、ゴルーチン（goroutine）のスタックに「セグメントスタック（segmented stacks）」という方式を採用していました。これは、ゴルーチンが小さなスタックセグメントで開始し、必要に応じて新しいセグメントを割り当てて既存のスタックにリンクすることで、スタックを動的に拡張する仕組みでした。

しかし、このセグメントスタック方式には「ホットスプリット問題（hot split problem）」というパフォーマンス上の課題がありました。これは、関数がループ内で繰り返しスタックを使い切り、新しいセグメントの割り当てと解放が頻繁に発生することで、オーバーヘッドが大きくなる問題です。特に、スタックの分割と結合が頻繁に行われるような、再帰が深い処理や、スタック使用量が境界付近で変動するようなシナリオで顕著でした。

この問題を解決するため、Go 1.3（そしてGo 1.4で完全に実装）では、スタック管理モデルが「動的に成長するスタック（dynamically growing stacks）」、または「スタックコピー（stack copying）」方式へと移行しました。この新しいモデルでは、スタックが不足しそうになると、より大きな連続したメモリブロックを割り当て、古いスタックの内容を新しいブロックに丸ごとコピーします。これにより、スタックは常に連続したメモリ領域に存在し、セグメント間のジャンプや頻繁なセグメントの割り当て・解放が不要になりました。

`doc/play/peano.go` は、Peano数（再帰的な定義を持つ）を扱うGoのサンプルプログラムであり、大量の再帰計算を行うことで知られています。元々このプログラムは、セグメントスタックの「強力さ」を示すために使われていましたが、ランタイムのスタック管理が変更されたことで、そのコメントが実情に合わなくなりました。このコミットは、その「古くなった」コメントを、新しいスタック管理モデル（動的に成長するスタック）の「有効性」を示すものへと修正するために行われました。

## 前提知識の解説

### 関数呼び出しスタック (Call Stack)

プログラムが関数を呼び出す際、その関数のローカル変数、引数、戻りアドレスなどの情報がメモリ上の「スタック」と呼ばれる領域に積まれます。関数が終了すると、その情報はスタックから取り除かれます。スタックはLIFO（Last-In, First-Out）構造で、メモリは通常、連続した領域として確保されます。再帰的な関数呼び出しが多い場合、スタックは深く成長します。

### Goのセグメントスタック (Segmented Stacks)

Go 1.2以前のバージョンで採用されていたスタック管理方式です。

*   **仕組み**: ゴルーチンは最初、非常に小さなスタック（例: 4KB）で開始します。このスタックが不足しそうになると、Goランタイムは新しいスタックセグメントを割り当て、既存のスタックの末尾にリンクします。これにより、スタックは複数の非連続なメモリセグメントにまたがって存在することが可能でした。
*   **利点**: ゴルーチンが非常に軽量に開始できるため、数百万ものゴルーチンを生成してもメモリ消費を抑えられると考えられていました。
*   **課題（ホットスプリット問題）**:
    *   **パフォーマンスオーバーヘッド**: スタックセグメントの割り当て、解放、そしてセグメント間のポインタの更新にはコストがかかります。特に、スタック使用量が頻繁に増減する（スタックが「ホット」に分割・結合される）場合、このオーバーヘッドが顕著になり、パフォーマンスが低下しました。
    *   **キャッシュ効率の低下**: スタックが非連続なメモリ領域に分散するため、CPUキャッシュの効率が低下する可能性がありました。
    *   **デバッグの複雑さ**: スタックトレースの解析などが複雑になる場合がありました。

### Goの動的に成長するスタック (Dynamically Growing Stacks / Stack Copying)

Go 1.3以降で採用されている現在のスタック管理方式です。

*   **仕組み**: ゴルーチンは小さなスタック（Go 1.4以降は2KB）で開始します。スタックが不足しそうになると、Goランタイムは現在のスタックサイズの約2倍の、より大きな**連続した**メモリブロックを新しく割り当てます。そして、古いスタックの内容全体をこの新しいブロックにコピーします。関数が終了してスタックが縮小しても、メモリは解放されず、将来の呼び出しのために保持されます。
*   **利点**:
    *   **ホットスプリット問題の解消**: スタックが常に連続したメモリ領域に存在するため、セグメントの分割・結合によるオーバーヘッドがなくなりました。
    *   **パフォーマンス向上**: スタック操作が高速化され、特に再帰が深い処理やスタック使用量が変動する処理でのパフォーマンスが向上しました。
    *   **キャッシュ効率の向上**: 連続したメモリ領域であるため、CPUキャッシュの効率が向上します。
    *   **実装の簡素化**: スタック管理のロジックが簡素化されました。
*   **欠点**: スタックコピーの際に一時的にメモリ使用量が増加する可能性がありますが、これは通常、パフォーマンス上の利点によって相殺されます。

## 技術的詳細

このコミット自体はコードの動作を変更するものではなく、Goランタイムの進化に伴うドキュメントの整合性を保つためのものです。しかし、その背景にあるスタック管理の変更は、Goのパフォーマンスと設計思想において非常に重要な意味を持ちます。

セグメントスタックから動的に成長するスタックへの移行は、Goの設計者たちが、理論的なメモリ効率よりも実際の実行パフォーマンスを重視した結果です。セグメントスタックは、ゴルーチンを非常に安価に開始できるという魅力がありましたが、前述のホットスプリット問題が、特に高負荷なアプリケーションにおいて深刻なパフォーマンスボトルネックとなることが判明しました。

新しいスタックコピー方式では、スタックが不足した際にスタック全体をコピーするという、一見するとコストの高い操作が行われます。しかし、このコピー操作は比較的稀にしか発生せず、一度コピーされれば、その後の関数呼び出しは連続したメモリ領域上で行われるため、非常に高速です。また、スタックが縮小してもメモリを解放しないことで、将来のスタック拡張時に再割り当てやコピーの必要性を減らし、全体的なパフォーマンスを向上させています。

`peano.go` のような再帰的な計算を行うプログラムは、スタックの深さが動的に大きく変動する典型的な例です。セグメントスタックの時代には、この種のプログラムがセグメントスタックの「柔軟性」を示す良い例とされていました。しかし、スタックコピー方式に移行した現在では、このプログラムは新しいスタック管理モデルの「効率性」や「堅牢性」を示す例として位置づけられるべきである、という認識がこのコメント修正の動機となっています。

## コアとなるコードの解説

この変更は、`doc/play/peano.go` ファイル内のコメントを修正するものです。

*   **変更前**:
    ```go
    // This program demonstrates the power of Go's
    // segmented stacks when doing massively
    // recursive computations.
    ```
    このコメントは、Goがセグメントスタックを使用していた時代の記述であり、Peano数の計算のような大量の再帰を行う際に、セグメントスタックがいかに強力であるかを示していると説明していました。

*   **変更後**:
    ```go
    // This program demonstrates the effectiveness
    // of the Go runtime's dynamically growing
    // stacks for heavily recursive computations.
    ```
    この新しいコメントは、Goランタイムが現在採用している「動的に成長するスタック」が、大量の再帰計算においていかに効果的であるかを示していると説明しています。これは、Goのスタック管理モデルがセグメントスタックからスタックコピー方式へと変更されたことを反映した、ドキュメントの整合性を保つための修正です。コードの動作自体には影響を与えませんが、Goの進化を正確に伝える上で重要な変更です。

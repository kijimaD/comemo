# [インデックス 25488] ファイルの概要

このコミットは、Goコンパイラに新しいアノテーション `go:nowritebarrierrec` を導入し、指定された関数とその関数が再帰的に呼び出す全ての関数においてライトバリアの使用を禁止する機能を追加します。これにより、Goランタイムのガベージコレクション（GC）における特定の低レベルなコードパスで、ライトバリアが意図せず挿入されることをより厳密に防止できるようになります。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行中にメモリ管理を行う重要なコンポーネントです。特に、並行GC（concurrent GC）では、GCが実行されている間もアプリケーションが動作し続けるため、GCの正確性を保証するために「ライトバリア（write barrier）」というメカニズムが使用されます。ライトバリアは、ポインタの書き込み操作をインターセプトし、GCがオブジェクトグラフを正確に追跡できるように補助する役割を担います。

しかし、GCの内部、特にライトバリア自体を実装するような非常に低レベルなコードでは、ライトバリアが挿入されると無限ループやデッドロック、あるいはパフォーマンスの著しい低下を引き起こす可能性があります。このため、Goコンパイラには `//go:nowritebarrier` というアノテーションが存在し、特定の関数内でのライトバリアの生成を禁止していました。

この既存の `go:nowritebarrier` アノテーションには課題がありました。それは、アノテーションが付与された関数自体はライトバリアを含まないものの、その関数が呼び出す別の関数がライトバリアを含んでいる場合、そのライトバリアは検出されず、問題を引き起こす可能性があった点です。コミットメッセージにもあるように、多くの `go:nowritebarrier` 関数がライトバリアを持つ関数を呼び出しており、これまでは「保守的」なアノテーションとして許容されていましたが、より厳密な制御が必要とされました。

このコミットは、このような背景から、関数とその再帰的な呼び出しパス全体でライトバリアを禁止する `go:nowritebarrierrec` という新しいアノテーションを導入することで、GCの低レベルコードの安全性を高めることを目的としています。

## 前提知識の解説

### ガベージコレクション (GC) とライトバリア

Goのガベージコレクションは、主に「三色マーク＆スイープ（Tri-color mark-and-sweep）」アルゴリズムをベースにしています。このアルゴリズムでは、オブジェクトを白、灰、黒の3色で分類し、到達可能なオブジェクトをマークし、到達不能なオブジェクトを解放します。

並行GCでは、GCがマークフェーズを実行している間も、アプリケーションのゴルーチンがオブジェクトグラフを変更する可能性があります。この変更によって、GCが誤って到達可能なオブジェクトを解放したり、到達不能なオブジェクトを保持し続けたりする「ポインタの消失（pointer loss）」や「ポインタの再出現（pointer reappearance）」といった問題が発生する可能性があります。

これを防ぐために導入されるのが「ライトバリア」です。ライトバリアは、プログラムがヒープ上のポインタを書き換える際に実行される小さなコードスニペットです。具体的には、あるオブジェクトAのフィールドに別のオブジェクトBへのポインタを書き込む際、GCがその変更を認識できるように、ライトバリアが介入して必要な処理（例えば、Bを灰色にマークするなど）を行います。これにより、GCは常に正確なオブジェクトグラフを把握し、安全にメモリを管理できます。

### `//go:nowritebarrier` アノテーション

`//go:nowritebarrier` は、Goコンパイラに対するディレクティブ（指示）であり、このアノテーションが付与された関数内ではライトバリアのコード生成を禁止します。これは、GCの内部実装など、ライトバリアが挿入されると問題が発生する可能性のある特定の低レベル関数で使用されます。コンパイラは、このアノテーションが付与された関数内でポインタの書き込み操作がライトバリアをトリガーする場合、コンパイルエラーを発生させます。

### Goコンパイラの構造とアノテーション処理

Goコンパイラ（`cmd/compile`）は、Goソースコードを解析し、抽象構文木（AST）を構築し、型チェック、最適化、そして最終的に機械語コードを生成します。アノテーション（`//go:` ディレクティブ）は、ソースコードのコメントとして記述されますが、コンパイラの字句解析（lexical analysis）フェーズで特別に処理され、ASTの対応する関数ノードにフラグとして記録されます。

例えば、`Func`構造体（`src/cmd/compile/internal/gc/syntax.go`）には、`Nowritebarrier`のようなブール値のフィールドがあり、これがアノテーションの有無を保持します。コンパイラのコード生成フェーズでは、これらのフラグを参照して、特定の最適化を適用したり、コード生成の制約を課したりします。

## 技術的詳細

このコミットで導入された `go:nowritebarrierrec` は、既存の `go:nowritebarrier` を拡張し、再帰的にライトバリアの禁止を適用する強力なメカニズムです。

### `go:nowritebarrierrec` の機能

`go:nowritebarrierrec` アノテーションが関数 `F` に付与されると、以下の条件が満たされた場合にコンパイルエラーが発生します。
1.  関数 `F` 自体がライトバリアを含む場合。
2.  関数 `F` が呼び出す関数 `G` がライトバリアを含む場合。
3.  関数 `F` が呼び出す関数 `G` がさらに別の関数 `H` を呼び出し、`H` がライトバリアを含む場合。
    ...といった形で、`F` から到達可能な全ての呼び出しパス上の関数が対象となります。

エラーメッセージは、アノテーションが付与された関数からライトバリアを含む関数までの最短の呼び出しスタックを示し、関数名と呼び出し元の行番号を含みます。これにより、開発者は問題の根源を迅速に特定できます。

### 実装の概要

この機能は、主にGoコンパイラの `src/cmd/compile/internal/gc/dcl.go` に追加された `nowritebarrierrecChecker` という構造体と、それに関連するロジックによって実現されています。

1.  **`Func` 構造体の拡張**: `src/cmd/compile/internal/gc/syntax.go` の `Func` 構造体に `Nowritebarrierrec` (bool) と `WBLineno` (int32) フィールドが追加されました。
    *   `Nowritebarrierrec`: その関数に `go:nowritebarrierrec` アノテーションが付与されているかを示します。
    *   `WBLineno`: その関数内で最初に検出されたライトバリアの行番号を記録します。ライトバリアがない場合は0です。

2.  **アノテーションのパース**: `src/cmd/compile/internal/gc/lex.go` で `//go:nowritebarrierrec` ディレクティブが認識され、`nowritebarrierrec` フラグがセットされます。このアノテーションはランタイムコード内でのみ許可されます。また、`go:nowritebarrierrec` は `go:nowritebarrier` を含意するため、`nowritebarrier` フラグも同時にセットされます。

3.  **ライトバリアの検出と記録**: `src/cmd/compile/internal/gc/cgen.go` の `cgen_wbptr` および `cgen_wbfat` 関数（ライトバリアを生成する箇所）が変更され、現在の関数 (`Curfn`) にライトバリアがある場合、その行番号を `Curfn.Func.WBLineno` に記録するようになりました。

4.  **再帰的なチェックロジック (`nowritebarrierrecChecker`)**:
    *   `nowritebarrierrecChecker` 構造体は、`curfn` (現在処理中の関数)、`stable` (反復処理が安定したか)、`best` (各関数からライトバリアまでの最短パス情報) を保持します。
    *   `checknowritebarrierrec()` 関数が、コンパイルの最終段階で呼び出されます。
    *   **ボトムアップ走査**: `visitBottomUp` ヘルパー関数を使用して、関数の呼び出しグラフをボトムアップ（葉の関数から根の関数へ）で走査します。
    *   **ライトバリアの深さ伝播**:
        *   まず、`WBLineno != 0` の関数（自身がライトバリアを含む関数）は、ライトバリアまでの深さ `0` として `c.best` マップに記録されます。
        *   次に、`list` 内の関数を繰り返し処理し、各関数 `n` について、その関数が呼び出す他の関数 `fn` を調べます。
        *   もし `fn` がライトバリアを含む（またはライトバリアを含む関数を呼び出す）場合、`n` から `fn` への呼び出しパスを考慮して、`n` からライトバリアまでの最短深さを更新します。この処理は、`c.stable` フラグが `true` になるまで（つまり、深さ情報が収束するまで）繰り返されます。これは、呼び出しグラフにサイクル（再帰呼び出し）がある場合でも正確な最短パスを見つけるためです。
    *   **エラーチェック**: 最後に、`Nowritebarrierrec` フラグが `true` の関数 `n` について、`c.best[n]` にライトバリア情報が存在するかどうかを確認します。もし存在すれば、`n` からライトバリアまでの呼び出しスタックを逆順に構築し、詳細なエラーメッセージを `yyerrorl` で出力します。

### `gcmarkwb_m` への適用

この新しいアノテーションのデモンストレーションとして、`src/runtime/mbarrier.go` 内の `gcmarkwb_m` 関数に `//go:nowritebarrierrec` が適用されました。`gcmarkwb_m` は、GCのマークフェーズ中にポインタの書き込みを処理する、まさにライトバリア自体を実装する関数です。この関数とその呼び出しパスでライトバリアが挿入されることは絶対に避けなければならないため、`go:nowritebarrierrec` の適用は非常に理にかなっています。

## コアとなるコードの解説

このコミットの核心は、`src/cmd/compile/internal/gc/dcl.go` に追加された `nowritebarrierrecChecker` とその関連メソッド群です。

### `nowritebarrierrecChecker` 構造体

```go
type nowritebarrierrecChecker struct {
	curfn  *Node
	stable bool

	// best maps from the ODCLFUNC of each visited function that
	// recursively invokes a write barrier to the called function
	// on the shortest path to a write barrier.
	best map[*Node]nowritebarrierrecCall
}

type nowritebarrierrecCall struct {
	target *Node
	depth  int
	lineno int32
}
```
-   `best`: `map[*Node]nowritebarrierrecCall` は、各関数ノード（`ODCLFUNC`）から、再帰的に呼び出されるライトバリアまでの最短パス情報 (`nowritebarrierrecCall`) を格納します。`nowritebarrierrecCall` は、ライトバリアを含む関数への最短パス上の次の呼び出し先 (`target`)、そのパスの深さ (`depth`)、および呼び出し元の行番号 (`lineno`) を保持します。

### `checknowritebarrierrec()` 関数

```go
func checknowritebarrierrec() {
	c := nowritebarrierrecChecker{
		best: make(map[*Node]nowritebarrierrecCall),
	}
	visitBottomUp(xtop, func(list []*Node, recursive bool) {
		// Functions with write barriers have depth 0.
		for _, n := range list {
			if n.Func.WBLineno != 0 {
				c.best[n] = nowritebarrierrecCall{target: nil, depth: 0, lineno: n.Func.WBLineno}
			}
		}

		// Propagate write barrier depth up from callees.
		// ... (詳細な伝播ロジック) ...

		// Check nowritebarrierrec functions.
		for _, n := range list {
			if !n.Func.Nowritebarrierrec {
				continue
			}
			call, hasWB := c.best[n]
			if !hasWB {
				continue
			}

			// Build the error message in reverse.
			err := ""
			for call.target != nil {
				err = fmt.Sprintf("\n\t%v: called by %v%s", Ctxt.Line(int(call.lineno)), n.Func.Nname, err)
				n = call.target
				call = c.best[n]
			}
			err = fmt.Sprintf("write barrier prohibited by caller; %v%s", n.Func.Nname, err)
			yyerrorl(int(n.Func.WBLineno), err)
		}
	})
}
```
-   この関数は、コンパイルの最終段階で呼び出され、`go:nowritebarrierrec` アノテーションの違反をチェックします。
-   `visitBottomUp` を使用して、関数の呼び出しグラフをボトムアップで走査します。これにより、葉の関数から順にライトバリアの情報を伝播させることができます。
-   **深さ0の初期化**: まず、自身がライトバリアを含む関数 (`n.Func.WBLineno != 0`) を見つけ、それらを `best` マップに深さ `0` として記録します。`target` は `nil` で、`lineno` はそのライトバリアの行番号です。
-   **深さの伝播**: `list` 内の関数を複数回反復処理し、`visitcodelist` を使って各関数のボディを走査します。`visitcall` メソッドが呼び出しを見つけるたびに、呼び出し元関数 (`c.curfn`) から呼び出し先関数 (`defn`) へのパスを考慮して、`c.best[c.curfn]` の深さ情報を更新します。この伝播は、`stable` フラグが `true` になるまで（つまり、全ての深さ情報が収束するまで）繰り返されます。これは、呼び出しグラフに再帰が含まれる場合でも最短パスを正確に計算するために必要です。
-   **エラー報告**: 最後に、`Nowritebarrierrec` が設定されている関数 `n` について、`c.best[n]` に情報が存在する場合（つまり、再帰的にライトバリアが検出された場合）、`best` マップに記録された情報を使って、最短の呼び出しスタックを逆順に構築し、詳細なエラーメッセージを生成して報告します。

### `visitcodelist`, `visitcode`, `visitcall` メソッド

これらのメソッドは、関数のASTを走査し、関数呼び出しを検出するために使用されます。
-   `visitcodelist` は `NodeList` (ステートメントのリスト) を走査します。
-   `visitcode` は単一の `Node` (ASTノード) を走査します。
-   `visitcall` は `OCALLFUNC` (通常の関数呼び出し) または `OCALLMETH` (メソッド呼び出し) ノードを処理します。
    -   呼び出し先関数 (`fn`) を特定し、その関数が `c.best` マップに存在するかどうかを確認します。
    -   もし存在し、かつ現在の呼び出しパスが `c.curfn` からライトバリアまでのより短いパスを提供する場合は、`c.best[c.curfn]` を更新し、`c.stable` を `false` に設定して、深さ伝播の反復を継続させます。

この複雑なグラフ走査と深さ伝播のロジックにより、Goコンパイラは `go:nowritebarrierrec` アノテーションの制約を、関数呼び出しグラフ全体にわたって厳密に強制できるようになります。

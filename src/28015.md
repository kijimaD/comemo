## 元コミット内容

このコミットは、Go言語の`strings.Index`関数において、AMD64アーキテクチャ上でSSE4.2命令セットの`PCMPESTRI`命令を利用するように変更するものです。これにより、特定の文字列検索シナリオでのパフォーマンス向上が期待されます。コミットメッセージには、ベンチマーク結果も含まれており、特に`IndexHard1-4`と`IndexHard2-4`のケースで大幅な速度向上が示されています。

## 変更の背景

Go言語の標準ライブラリである`strings.Index`関数は、ある文字列（`s`）の中に別の文字列（`sep`）が最初に現れるインデックスを検索する機能を提供します。この関数は、多くのアプリケーションで頻繁に使用されるため、そのパフォーマンスはGoプログラム全体の実行速度に大きな影響を与えます。

従来の`strings.Index`の実装は、汎用的なCPU命令を使用していましたが、現代のCPUには特定のタスク（例えば文字列操作）を高速化するための特殊な命令セットが搭載されています。IntelのSSE4.2（Streaming SIMD Extensions 4.2）はその一つであり、特に文字列/テキスト処理に特化した命令を含んでいます。

このコミットの背景には、`strings.Index`のパフォーマンスを向上させることで、Goプログラム全体の効率を高めるという目的があります。特に、`PCMPESTRI`命令は、短い文字列の検索において非常に効率的であることが知られており、これを活用することで、Goの文字列処理性能をさらに引き上げることが狙いです。

## 前提知識の解説

### 1. `strings.Index`関数

Go言語の`strings`パッケージに含まれる`Index(s, sep string) int`関数は、文字列`s`内で`sep`が最初に現れる位置のインデックスを返します。`sep`が見つからない場合は-1を返します。

### 2. SIMD (Single Instruction, Multiple Data)

SIMDは、単一の命令で複数のデータ要素に対して同じ操作を同時に実行できるCPUの機能です。これにより、データ並列性の高い処理（例えば、画像処理、音声処理、科学技術計算、そして文字列処理）を大幅に高速化できます。IntelのSSE（Streaming SIMD Extensions）は、x86アーキテクチャにおけるSIMD命令セットのファミリーです。

### 3. SSE4.2命令セット

SSE4.2は、Intel Core i7（Nehalemマイクロアーキテクチャ）以降のプロセッサで導入されたSIMD命令セットの拡張です。この拡張には、特にXML処理や文字列処理に役立つ新しい命令が含まれています。

### 4. `PCMPESTRI`命令

`PCMPESTRI` (Packed Compare Explicit Length Strings, Return Index) は、SSE4.2命令セットの一部であり、2つの文字列（またはバイト列）を比較し、その結果に基づいてインデックスを返す強力な命令です。この命令は、最大16バイトの文字列を一度に処理でき、様々な比較モード（等価性、部分文字列、範囲など）と出力形式をサポートします。

`PCMPESTRI`の主な特徴は以下の通りです。
*   **明示的な長さ指定**: 比較する文字列の長さをレジスタで指定できます。
*   **バイト/ワード比較**: バイト単位またはワード単位での比較が可能です。
*   **比較モード**: 等価性、符号付き/符号なしの範囲比較、部分文字列検索など、複数の比較モードがあります。
*   **出力形式**: 比較結果として、一致したバイトのインデックス、マスク、またはフラグを返します。
*   **高速な文字列検索**: 特に短い文字列の検索において、ループと条件分岐を多用する従来のソフトウェア実装よりもはるかに高速に動作します。

### 5. Goのアセンブリ言語 (`.s`ファイル)

Go言語のランタイムや一部の標準ライブラリは、パフォーマンスが非常に重要な部分において、Goのアセンブリ言語（Plan 9アセンブラの構文に似ています）で記述されています。これは、特定のCPU命令を直接利用したり、レジスタの割り当てを細かく制御したりすることで、C言語やGo言語で書かれたコードよりもさらに最適化されたコードを生成するためです。`src/runtime/asm_amd64.s`のようなファイルは、AMD64アーキテクチャ向けのアセンブリコードを含んでいます。

### 6. Goのコンパイラとアセンブラの内部構造

Goのツールチェーンでは、`src/cmd/internal/obj/x86/`ディレクトリ内のファイルが、x86アーキテクチャ向けのアセンブラとオブジェクトファイル生成に関連する定義を含んでいます。
*   `a.out.go`: オブジェクトファイルのフォーマットや命令コードに関する定数を定義します。
*   `anames.go`: アセンブリ命令の名前とそれに対応する内部表現をマッピングします。
*   `asm6.go`: アセンブラの命令テーブル（`optab`）を定義し、各命令のオペランド形式やエンコーディング情報を含みます。新しい命令を追加する際には、これらのファイルにその命令を認識させるためのエントリを追加する必要があります。

## 技術的詳細

このコミットの核となる技術的詳細は、`strings.Index`関数における文字列検索ロジックを、SSE4.2の`PCMPESTRI`命令を利用するように変更した点にあります。

### `PCMPESTRI`命令の活用

`PCMPESTRI`命令は、最大16バイトのデータ（XMMレジスタに格納）とメモリ上の16バイトのデータを比較し、一致するバイトのインデックスを返すことができます。この命令は、特に短い`sep`文字列（検索対象のパターン）を長い`s`文字列（検索されるテキスト）から探す場合に非常に有効です。

変更されたアセンブリコードでは、以下のロジックが導入されています。

1.  **CPU機能の検出**: `PCMPESTRI`命令はSSE4.2の一部であるため、まず現在のCPUがSSE4.2をサポートしているかを確認します。これは`runtime·cpuid_ecx(SB)`を読み取り、特定のビット（`0x100000`、これはSSE4.2のフラグに対応）をチェックすることで行われます。サポートされていない場合は、従来の検索ロジック（`no_sse42`ラベルにジャンプ）にフォールバックします。
2.  **条件付き`PCMPESTRI`使用**: `PCMPESTRI`は常に高速であるとは限りません。特に`sep`文字列が非常に短い場合や、`s`文字列が非常に短い場合は、オーバーヘッドが大きくなる可能性があります。コミットメッセージのベンチマーク結果から、`sep`の長さが12バイト以上の場合に`PCMPESTRI`が有効であると判断されています（`CMPQ AX, $12`）。この閾値は実験的に決定されたもので、NehalemとHaswellの両方で同様の性能特性を示すとコメントされています。
3.  **検索ロジック**:
    *   `sep`文字列（最大16バイト）をXMMレジスタ（`X1`）にロードします。
    *   `s`文字列を16バイトずつXMMレジスタ（`X2`）にロードし、`PCMPESTRI`命令を使って`X1`と`X2`を比較します。
    *   `PCMPESTRI`は、比較結果として一致したバイトのインデックスを`CX`レジスタに格納します。
    *   `0x0c`というイミディエイト値は、`PCMPESTRI`の動作モードを指定します。この値は、符号なしバイト比較、等価性チェック、結果のマスクなし、最初のマッチングバイトのインデックスを返すことを意味します。
    *   `CX`レジスタの値と、`sep`の長さに基づいて計算されたオフセット（`R9`）を比較し、完全な一致または部分的な一致を検出します。
    *   一致が見つかった場合、そのインデックスを計算して返します。
    *   一致が見つからない場合、`s`文字列の次の16バイトブロックに進み、検索を続行します。
4.  **アセンブラの更新**: Goのアセンブラが`PCMPESTRI`命令を正しく解釈し、オブジェクトコードに変換できるように、`src/cmd/internal/obj/x86/a.out.go`、`src/cmd/internal/obj/x86/anames.go`、`src/cmd/internal/obj/x86/asm6.go`の各ファイルに`APCMPESTRI`という新しい命令エントリが追加されています。

### パフォーマンスの向上

コミットメッセージに示されているベンチマーク結果は、この最適化の有効性を明確に示しています。
*   `Index-4`: 21.1ns ± 0% -> 21.1ns ± 0% (変化なし) - これは、おそらく`PCMPESTRI`が適用されない短い文字列や単純なケースです。
*   `IndexHard1-4`: 395µs ± 0% -> 105µs ± 0% (-73.53%) - 大幅な改善。
*   `IndexHard2-4`: 300µs ± 0% -> 147µs ± 0% (-51.11%) - 大幅な改善。
*   `IndexHard3-4`: 665µs ± 0% -> 665µs ± 0% (変化なし) - このケースでは改善が見られなかったか、`PCMPESTRI`が適用されなかった可能性があります。

これらの結果から、`PCMPESTRI`は特定の「ハードな」文字列検索シナリオ（例えば、長い文字列内で比較的短いパターンを検索する場合など）において、顕著なパフォーマンス向上をもたらすことがわかります。

## コアとなるコードの解説

### `src/runtime/asm_amd64.s` の変更点

このファイルは、`strings.Index`関数のAMD64向けアセンブリ実装を含んでいます。変更の核心は、`PCMPESTRI`命令の導入と、それを使用するための条件分岐ロジックです。

```asm
// ... (既存のコード) ...

TEXT strings·indexShortStr(SB),NOSPLIT,$0-40
	MOVQ s+0(FP), DI       // 検索対象文字列sのポインタをDIにロード
	// We want len in DX and AX, because PCMPESTRI implicitly consumes them
	MOVQ s_len+8(FP), DX   // sの長さをDXにロード
	MOVQ c+16(FP), BP      // 検索パターンcのポインタをBPにロード
	MOVQ c_len+24(FP), AX  // cの長さをAXにロード
	CMPQ AX, DX            // cの長さ > sの長さ なら失敗
	JA fail

	CMPQ DX, $16           // sの長さが16バイト以上ならsse42パスを検討
	JAE sse42
no_sse42:
	// ... (SSE4.2が利用できない、または非効率な場合の従来の検索ロジック) ...

sse42:
	MOVL runtime·cpuid_ecx(SB), CX // CPUIDからECXレジスタを取得
	ANDL $0x100000, CX             // SSE4.2 (bit 20)が有効かチェック
	JZ no_sse42                    // 無効ならno_sse42にジャンプ

	CMPQ AX, $12                   // 検索パターンcの長さが12バイト以上かチェック
	// PCMPESTRI is slower than normal compare,
	// so using it makes sense only if we advance 4+ bytes per compare
	// This value was determined experimentally and is the ~same
	// on Nehalem (first with SSE42) and Haswell.
	JAE _9_or_more                 // 12バイト以上なら、従来の_9_or_moreパスにジャンプ（コメントと矛盾？）
	                               // ここはJAE sse42_optimized_path のようなものになるはずだが、
	                               // 実際には_9_or_moreにジャンプしている。
	                               // これは、PCMPESTRIが常に高速とは限らず、特定の長さのパターンでは
	                               // 従来の最適化されたパスの方が良い場合があることを示唆している。
	                               // あるいは、このコメントは一般的なPCMPESTRIの特性を述べており、
	                               // 実際のコードでは別の閾値やロジックが適用されている可能性もある。
	                               // 実際のコードでは、AX (c_len) が12未満の場合にPCMPESTRIを使用するパスに進む。
	                               // コメントの意図は「PCMPESTRIは通常の比較より遅い場合があるので、
	                               // 4バイト以上進む場合にのみ意味がある」という一般的な注意喚起で、
	                               // 実際の分岐ロジックはAX < 12の場合にPCMPESTRIを使うように見える。
	                               // これは、短いパターン（12バイト未満）に対してPCMPESTRIが特に有効であることを示唆している。

	LEAQ 16(BP), SI                // 検索パターンcの終端+16バイトのポインタをSIにロード
	TESTW $0xff0, SI               // SIの下位バイトをテスト (アライメントチェック？)
	JEQ no_sse42                   // 特定の条件でno_sse42にジャンプ

	MOVOU (BP), X1                 // 検索パターンcをXMMレジスタX1にロード
	LEAQ -15(DI)(DX*1), SI         // 検索対象sの終端-15バイトのポインタをSIにロード (ループの境界)
	MOVQ $16, R9                   // R9 = 16
	SUBQ AX, R9                    // R9 = 16 - len(sep) (各イテレーションで進むバイト数)

loop_sse42:
	// 0x0c means: unsigned byte compare (bits 0,1 are 00)
	// for equality (bits 2,3 are 11)
	// result is not masked or inverted (bits 4,5 are 00)
	// and corresponds to first matching byte (bit 6 is 0)
	PCMPESTRI $0x0c, (DI), X1      // DIが指すメモリとX1を比較し、結果をCXに格納
	                               // $0x0cは、符号なしバイト比較、等価性、結果はインデックス、最初のマッチを返すモード
	// CX == 16 means no match,
	// CX > R9 means partial match at the end of the string,
	// otherwise sep is at offset CX from X1 start
	CMPQ CX, R9                    // CXとR9を比較
	JBE sse42_success              // CX <= R9 なら成功 (一致が見つかった)
	ADDQ R9, DI                    // DIをR9だけ進める
	CMPQ DI, SI                    // DIがSIを超えたかチェック
	JB loop_sse42                  // 超えていなければループを続行

	PCMPESTRI $0x0c, -1(SI), X1    // ループの最後の部分で再度比較
	CMPQ CX, R9
	JA fail                        // CX > R9 なら失敗
	LEAQ -1(SI), DI                // DIを調整
sse42_success:
	ADDQ CX, DI                    // DIにCXを加算して最終的なインデックスを計算
success:
	SUBQ s+0(FP), DI               // sの開始アドレスからのオフセットを計算
	MOVQ DI, ret+32(FP)            // 結果をretに格納
	RET
```

このアセンブリコードは、`strings.Index`のパフォーマンスクリティカルな部分を、SSE4.2の`PCMPESTRI`命令を使って最適化しています。特に、短い検索パターンに対して、従来のバイト単位の比較ループよりもはるかに高速に動作することが期待されます。

### `src/cmd/internal/obj/x86/a.out.go`, `anames.go`, `asm6.go` の変更点

これらのファイルは、Goのアセンブラが`PCMPESTRI`命令を認識し、正しく処理できるようにするための定義を追加しています。

*   `a.out.go`では、`APCMPESTRI`という定数が追加され、アセンブラ内部でこの命令を識別するためのIDとして機能します。
*   `anames.go`では、`Anames`配列に文字列`"PCMPESTRI"`が追加され、アセンブリソースコード中の`PCMPESTRI`というテキストを、`a.out.go`で定義された内部IDにマッピングします。
*   `asm6.go`では、`optab`という命令ディスパッチテーブルに`APCMPESTRI`のエントリが追加されます。このエントリは、`PCMPESTRI`命令がどのようなオペランドを取り、どのように機械語にエンコードされるかをアセンブラに指示します。具体的には、`yxshuf`というオペランド形式と、`0x3a, 0x61, 0`というバイト列がエンコーディング情報として指定されています。これらは、`PCMPESTRI`命令のopcodeとModR/M、SIBバイトなどの情報に対応します。

これらの変更により、Goのツールチェーン全体が`PCMPESTRI`命令をサポートし、`src/runtime/asm_amd64.s`で記述された最適化されたコードを正しくコンパイルできるようになります。

## 元コミット内容

このコミットは、Go言語の`strings.Index`関数において、AMD64アーキテクチャ上でSSE4.2命令セットの`PCMPESTRI`命令を利用するように変更するものです。これにより、特定の文字列検索シナリオでのパフォーマンス向上が期待されます。コミットメッセージには、ベンチマーク結果も含まれており、特に`IndexHard1-4`と`IndexHard2-4`のケースで大幅な速度向上が示されています。

## 変更の背景

Go言語の標準ライブラリである`strings.Index`関数は、ある文字列（`s`）の中に別の文字列（`sep`）が最初に現れるインデックスを検索する機能を提供します。この関数は、多くのアプリケーションで頻繁に使用されるため、そのパフォーマンスはGoプログラム全体の実行速度に大きな影響を与えます。

従来の`strings.Index`の実装は、汎用的なCPU命令を使用していましたが、現代のCPUには特定のタスク（例えば文字列操作）を高速化するための特殊な命令セットが搭載されています。IntelのSSE4.2（Streaming SIMD Extensions 4.2）はその一つであり、特に文字列/テキスト処理に特化した命令を含んでいます。

このコミットの背景には、`strings.Index`のパフォーマンスを向上させることで、Goプログラム全体の効率を高めるという目的があります。特に、`PCMPESTRI`命令は、短い文字列の検索において非常に効率的であることが知られており、これを活用することで、Goの文字列処理性能をさらに引き上げることが狙いです。

## 前提知識の解説

### 1. `strings.Index`関数

Go言語の`strings`パッケージに含まれる`Index(s, sep string) int`関数は、文字列`s`内で`sep`が最初に現れる位置のインデックスを返します。`sep`が見つからない場合は-1を返します。

### 2. SIMD (Single Instruction, Multiple Data)

SIMDは、単一の命令で複数のデータ要素に対して同じ操作を同時に実行できるCPUの機能です。これにより、データ並列性の高い処理（例えば、画像処理、音声処理、科学技術計算、そして文字列処理）を大幅に高速化できます。IntelのSSE（Streaming SIMD Extensions）は、x86アーキテクチャにおけるSIMD命令セットのファミリーです。

### 3. SSE4.2命令セット

SSE4.2は、Intel Core i7（Nehalemマイクロアーキテクチャ）以降のプロセッサで導入されたSIMD命令セットの拡張です。この拡張には、特にXML処理や文字列処理に役立つ新しい命令が含まれています。

### 4. `PCMPESTRI`命令

`PCMPESTRI` (Packed Compare Explicit Length Strings, Return Index) は、SSE4.2命令セットの一部であり、2つの文字列（またはバイト列）を比較し、その結果に基づいてインデックスを返す強力な命令です。この命令は、最大16バイトの文字列を一度に処理でき、様々な比較モード（等価性、部分文字列、範囲など）と出力形式をサポートします。

`PCMPESTRI`の主な特徴は以下の通りです。
*   **明示的な長さ指定**: 比較する文字列の長さをレジスタで指定できます。
*   **バイト/ワード比較**: バイト単位またはワード単位での比較が可能です。
*   **比較モード**: 等価性、符号付き/符号なしの範囲比較、部分文字列検索など、複数の比較モードがあります。
*   **出力形式**: 比較結果として、一致したバイトのインデックス、マスク、またはフラグを返します。
*   **高速な文字列検索**: 特に短い文字列の検索において、ループと条件分岐を多用する従来のソフトウェア実装よりもはるかに高速に動作します。

### 5. Goのアセンブリ言語 (`.s`ファイル)

Go言語のランタイムや一部の標準ライブラリは、パフォーマンスが非常に重要な部分において、Goのアセンブリ言語（Plan 9アセンブラの構文に似ています）で記述されています。これは、特定のCPU命令を直接利用したり、レジスタの割り当てを細かく制御したりすることで、C言語やGo言語で書かれたコードよりもさらに最適化されたコードを生成するためです。`src/runtime/asm_amd64.s`のようなファイルは、AMD64アーキテクチャ向けのアセンブリコードを含んでいます。

### 6. Goのコンパイラとアセンブラの内部構造

Goのツールチェーンでは、`src/cmd/internal/obj/x86/`ディレクトリ内のファイルが、x86アーキテクチャ向けのアセンブラとオブジェクトファイル生成に関連する定義を含んでいます。
*   `a.out.go`: オブジェクトファイルのフォーマットや命令コードに関する定数を定義します。
*   `anames.go`: アセンブリ命令の名前とそれに対応する内部表現をマッピングします。
*   `asm6.go`: アセンブラの命令テーブル（`optab`）を定義し、各命令のオペランド形式やエンコーディング情報を含みます。新しい命令を追加する際には、これらのファイルにその命令を認識させるためのエントリを追加する必要があります。

## 技術的詳細

このコミットの核となる技術的詳細は、`strings.Index`関数における文字列検索ロジックを、SSE4.2の`PCMPESTRI`命令を利用するように変更した点にあります。

### `PCMPESTRI`命令の活用

`PCMPESTRI`命令は、最大16バイトのデータ（XMMレジスタに格納）とメモリ上の16バイトのデータを比較し、一致するバイトのインデックスを返すことができます。この命令は、特に短い`sep`文字列（検索対象のパターン）を長い`s`文字列（検索されるテキスト）から探す場合に非常に有効です。

変更されたアセンブリコードでは、以下のロジックが導入されています。

1.  **CPU機能の検出**: `PCMPESTRI`命令はSSE4.2の一部であるため、まず現在のCPUがSSE4.2をサポートしているかを確認します。これは`runtime·cpuid_ecx(SB)`を読み取り、特定のビット（`0x100000`、これはSSE4.2のフラグに対応）をチェックすることで行われます。サポートされていない場合は、従来の検索ロジック（`no_sse42`ラベルにジャンプ）にフォールバックします。
2.  **条件付き`PCMPESTRI`使用**: `PCMPESTRI`は常に高速であるとは限りません。特に`sep`文字列が非常に短い場合や、`s`文字列が非常に短い場合は、オーバーヘッドが大きくなる可能性があります。コミットメッセージのベンチマーク結果から、`sep`の長さが12バイト以上の場合に`PCMPESTRI`が有効であると判断されています（`CMPQ AX, $12`）。この閾値は実験的に決定されたもので、NehalemとHaswellの両方で同様の性能特性を示すとコメントされています。
3.  **検索ロジック**:
    *   `sep`文字列（最大16バイト）をXMMレジスタ（`X1`）にロードします。
    *   `s`文字列を16バイトずつXMMレジスタ（`X2`）にロードし、`PCMPESTRI`命令を使って`X1`と`X2`を比較します。
    *   `PCMPESTRI`は、比較結果として一致したバイトのインデックスを`CX`レジスタに格納します。
    *   `0x0c`というイミディエイト値は、`PCMPESTRI`の動作モードを指定します。この値は、符号なしバイト比較、等価性チェック、結果のマスクなし、最初のマッチングバイトのインデックスを返すことを意味します。
    *   `CX`レジスタの値と、`sep`の長さに基づいて計算されたオフセット（`R9`）を比較し、完全な一致または部分的な一致を検出します。
    *   一致が見つかった場合、そのインデックスを計算して返します。
    *   一致が見つからない場合、`s`文字列の次の16バイトブロックに進み、検索を続行します。
4.  **アセンブラの更新**: Goのアセンブラが`PCMPESTRI`命令を正しく解釈し、オブジェクトコードに変換できるように、`src/cmd/internal/obj/x86/a.out.go`、`src/cmd/internal/obj/x86/anames.go`、`src/cmd/internal/obj/x86/asm6.go`の各ファイルに`APCMPESTRI`という新しい命令エントリが追加されています。

### パフォーマンスの向上

コミットメッセージに示されているベンチマーク結果は、この最適化の有効性を明確に示しています。
*   `Index-4`: 21.1ns ± 0% -> 21.1ns ± 0% (変化なし) - これは、おそらく`PCMPESTRI`が適用されない短い文字列や単純なケースです。
*   `IndexHard1-4`: 395µs ± 0% -> 105µs ± 0% (-73.53%) - 大幅な改善。
*   `IndexHard2-4`: 300µs ± 0% -> 147µs ± 0% (-51.11%) - 大幅な改善。
*   `IndexHard3-4`: 665µs ± 0% -> 665µs ± 0% (変化なし) - このケースでは改善が見られなかったか、`PCMPESTRI`が適用されなかった可能性があります。

これらの結果から、`PCMPESTRI`は特定の「ハードな」文字列検索シナリオ（例えば、長い文字列内で比較的短いパターンを検索する場合など）において、顕著なパフォーマンス向上をもたらすことがわかります。

## コアとなるコードの解説

### `src/runtime/asm_amd64.s` の変更点

このファイルは、`strings.Index`関数のAMD64向けアセンブリ実装を含んでいます。変更の核心は、`PCMPESTRI`命令の導入と、それを使用するための条件分岐ロジックです。

```asm
// ... (既存のコード) ...

TEXT strings·indexShortStr(SB),NOSPLIT,$0-40
	MOVQ s+0(FP), DI       // 検索対象文字列sのポインタをDIにロード
	// We want len in DX and AX, because PCMPESTRI implicitly consumes them
	MOVQ s_len+8(FP), DX   // sの長さをDXにロード
	MOVQ c+16(FP), BP      // 検索パターンcのポインタをBPにロード
	MOVQ c_len+24(FP), AX  // cの長さをAXにロード
	CMPQ AX, DX            // cの長さ > sの長さ なら失敗
	JA fail

	CMPQ DX, $16           // sの長さが16バイト以上ならsse42パスを検討
	JAE sse42
no_sse42:
	// ... (SSE4.2が利用できない、または非効率な場合の従来の検索ロジック) ...

sse42:
	MOVL runtime·cpuid_ecx(SB), CX // CPUIDからECXレジスタを取得
	ANDL $0x100000, CX             // SSE4.2 (bit 20)が有効かチェック
	JZ no_sse42                    // 無効ならno_sse42にジャンプ

	CMPQ AX, $12                   // 検索パターンcの長さが12バイト以上かチェック
	// PCMPESTRI is slower than normal compare,
	// so using it makes sense only if we advance 4+ bytes per compare
	// This value was determined experimentally and is the ~same
	// on Nehalem (first with SSE42) and Haswell.
	JAE _9_or_more                 // 12バイト以上なら、従来の_9_or_moreパスにジャンプ（コメントと矛盾？）
	                               // ここはJAE sse42_optimized_path のようなものになるはずだが、
	                               // 実際には_9_or_moreにジャンプしている。
	                               // これは、PCMPESTRIが常に高速とは限らず、特定の長さのパターンでは
	                               // 従来の最適化されたパスの方が良い場合があることを示唆している。
	                               // あるいは、このコメントは一般的なPCMPESTRIの特性を述べており、
	                               // 実際のコードでは別の閾値やロジックが適用されている可能性もある。
	                               // 実際のコードでは、AX (c_len) が12未満の場合にPCMPESTRIを使用するパスに進む。
	                               // コメントの意図は「PCMPESTRIは通常の比較より遅い場合があるので、
	                               // 4バイト以上進む場合にのみ意味がある」という一般的な注意喚起で、
	                               // 実際の分岐ロジックはAX < 12の場合にPCMPESTRIを使うように見える。
	                               // これは、短いパターン（12バイト未満）に対してPCMPESTRIが特に有効であることを示唆している。

	LEAQ 16(BP), SI                // 検索パターンcの終端+16バイトのポインタをSIにロード
	TESTW $0xff0, SI               // SIの下位バイトをテスト (アライメントチェック？)
	JEQ no_sse42                   // 特定の条件でno_sse42にジャンプ

	MOVOU (BP), X1                 // 検索パターンcをXMMレジスタX1にロード
	LEAQ -15(DI)(DX*1), SI         // 検索対象sの終端-15バイトのポインタをSIにロード (ループの境界)
	MOVQ $16, R9                   // R9 = 16
	SUBQ AX, R9                    // R9 = 16 - len(sep) (各イテレーションで進むバイト数)

loop_sse42:
	// 0x0c means: unsigned byte compare (bits 0,1 are 00)
	// for equality (bits 2,3 are 11)
	// result is not masked or inverted (bits 4,5 are 00)
	// and corresponds to first matching byte (bit 6 is 0)
	PCMPESTRI $0x0c, (DI), X1      // DIが指すメモリとX1を比較し、結果をCXに格納
	                               // $0x0cは、符号なしバイト比較、等価性、結果はインデックス、最初のマッチを返すモード
	// CX == 16 means no match,
	// CX > R9 means partial match at the end of the string,
	// otherwise sep is at offset CX from X1 start
	CMPQ CX, R9                    // CXとR9を比較
	JBE sse42_success              // CX <= R9 なら成功 (一致が見つかった)
	ADDQ R9, DI                    // DIをR9だけ進める
	CMPQ DI, SI                    // DIがSIを超えたかチェック
	JB loop_sse42                  // 超えていなければループを続行

	PCMPESTRI $0x0c, -1(SI), X1    // ループの最後の部分で再度比較
	CMPQ CX, R9
	JA fail                        // CX > R9 なら失敗
	LEAQ -1(SI), DI                // DIを調整
sse42_success:
	ADDQ CX, DI                    // DIにCXを加算して最終的なインデックスを計算
success:
	SUBQ s+0(FP), DI               // sの開始アドレスからのオフセットを計算
	MOVQ DI, ret+32(FP)            // 結果をretに格納
	RET
```

このアセンブリコードは、`strings.Index`のパフォーマンスクリティカルな部分を、SSE4.2の`PCMPESTRI`命令を使って最適化しています。特に、短い検索パターンに対して、従来のバイト単位の比較ループよりもはるかに高速に動作することが期待されます。

### `src/cmd/internal/obj/x86/a.out.go`, `anames.go`, `asm6.go` の変更点

これらのファイルは、Goのアセンブラが`PCMPESTRI`命令を認識し、正しく処理できるようにするための定義を追加しています。

*   `a.out.go`では、`APCMPESTRI`という定数が追加され、アセンブラ内部でこの命令を識別するためのIDとして機能します。
*   `anames.go`では、`Anames`配列に文字列`"PCMPESTRI"`が追加され、アセンブリ命令名と内部表現のマッピングが更新されます。
*   `asm6.go`では、`optab`という命令ディスパッチテーブルに`APCMPESTRI`のエントリが追加されます。このエントリは、`PCMPESTRI`命令がどのようなオペランドを取り、どのように機械語にエンコードされるかをアセンブラに指示します。具体的には、`yxshuf`というオペランド形式と、`0x3a, 0x61, 0`というバイト列がエンコーディング情報として指定されています。これらは、`PCMPESTRI`命令のopcodeとModR/M、SIBバイトなどの情報に対応します。

これらの変更により、Goのツールチェーン全体が`PCMPESTRI`命令をサポートし、`src/runtime/asm_amd64.s`で記述された最適化されたコードを正しくコンパイルできるようになります。

# [インデックス 25510] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）メカニズムにおけるアイドルマークワーカーの挙動を修正するものです。具体的には、GCのマークフェーズ間でアイドルマークワーカーが不適切に起動するのを防ぎ、GCの整合性とデッドロックの可能性を排除することを目的としています。

## コミット

```
commit 20f276e237c4b312d4b62a1a83db84ce64229752
Author: Austin Clements <austin@google.com>
Date:   Tue Nov 3 19:47:07 2015 -0500

    runtime: don't start idle mark workers when barriers are cleared

    Currently, we don't start dedicated or fractional mark workers unless
    the mark 1 or mark 2 barriers have been cleared. One intended
    consequence of this is that no background workers run between the
    forEachP that disposes all gcWork caches and the beginning of mark 2.

    However, we (unintentionally) did not apply this restriction to idle
    mark workers. As a result, these can start in the interim between mark
    1 completion and mark 2 starting. This explains why it was necessary
    to reset the root marking jobs using carefully ordered atomic writes
    when setting up mark 2. It also means that, even though we definitely
    enqueue work before starting mark 2, it may be drained by the time we
    reset the mark 2 barrier. If this happens, currently the only thing
    preventing the runtime from deadlocking is that the scheduler itself
    also checks for mark completion and will signal mark 2 completion.
    Were it not for the odd behavior of idle workers, this check in the
    scheduler would not be necessary.

    Clean all of this up and prepare to remove this check in the scheduler
    by applying the same restriction to starting idle mark workers.
```

## 元コミット内容

Goランタイムにおいて、GCのマークフェーズ（mark 1またはmark 2）のバリアがクリアされるまで、専用または部分的なマークワーカーは起動しない。これにより、`forEachP`がすべての`gcWork`キャッシュを破棄してからmark 2が開始されるまでの間に、バックグラウンドワーカーが実行されないことが意図されていた。

しかし、この制限がアイドルマークワーカーには適用されていなかったため、mark 1の完了からmark 2の開始までの間にアイドルマークワーカーが起動してしまう可能性があった。この挙動が、mark 2のセットアップ時にルートマーキングジョブを慎重に順序付けられたアトミックな書き込みでリセットする必要があった理由を説明していた。また、mark 2開始前に確実に作業がキューに入れられていても、mark 2バリアがリセットされるまでにその作業が処理されてしまう可能性があった。このような状況では、ランタイムがデッドロックするのを防ぐ唯一の手段は、スケジューラ自体がマーク完了をチェックし、mark 2完了を通知することであった。アイドルワーカーのこの奇妙な挙動がなければ、スケジューラでのこのチェックは不要であった。

このコミットは、アイドルマークワーカーにも同様の制限を適用することで、これらの問題を整理し、スケジューラでの不要なチェックを削除する準備をするものである。

## 変更の背景

Goのガベージコレクションは、並行マーク＆スイープ方式を採用しており、アプリケーションの実行と並行してGC作業を進めることで、ストップ・ザ・ワールド（STW）時間を最小限に抑えています。このプロセスには、オブジェクトの到達可能性をマークする「マークフェーズ」が含まれます。マークフェーズは通常、複数のサブフェーズに分かれており、それぞれが特定の「バリア」によって区切られています。これらのバリアは、GCの進行中にアプリケーションがオブジェクトグラフを変更するのを制御し、GCの正確性を保証するために重要です。

コミットメッセージが示唆するように、GoのGCには「mark 1」と「mark 2」というフェーズが存在します。これらのフェーズの間には、特定のGCワーカーが活動すべきではない期間があります。これは、GCの内部状態が一時的に不安定になるため、あるいは特定の作業が完了するまで次の作業を開始すべきではないためです。

しかし、既存の実装では、専用（dedicated）ワーカーや部分（fractional）ワーカーにはこの制限が適用されていたものの、「アイドルマークワーカー」には適用されていませんでした。アイドルマークワーカーとは、アプリケーションのP（プロセッサ、Goスケジューラの実行コンテキスト）が他に実行すべきゴルーチンがない場合に、GC作業を補助するために起動されるワーカーです。このワーカーが意図しないタイミングで起動してしまうと、以下のような問題が発生する可能性がありました。

1.  **GC状態の不整合**: mark 1完了後からmark 2開始までの間に、GCの内部状態が完全にmark 2の準備ができていないにもかかわらず、アイドルワーカーがGC作業を開始してしまう。
2.  **作業の早期消費**: mark 2開始前にキューに入れられた作業が、アイドルワーカーによって早期に処理されてしまい、mark 2が開始された時点で作業が残っていない、あるいは期待される状態ではない。
3.  **デッドロックの可能性**: 最悪の場合、GCの進行が停止し、ランタイムがデッドロックする可能性があった。これを回避するために、スケジューラがGCの完了を別途チェックするという、本来不要な安全策が講じられていた。

このコミットは、これらの問題を解決し、GCのロジックをより堅牢で理解しやすいものにするために行われました。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションとスケジューラに関するいくつかの概念を理解しておく必要があります。

### Goのガベージコレクション (GC)

GoのGCは、主に以下のフェーズで構成される並行マーク＆スイープコレクタです。

*   **マークフェーズ (Mark Phase)**:
    *   **Mark 1**: ライブオブジェクト（到達可能なオブジェクト）を特定し、マークを開始するフェーズ。
    *   **Mark 2**: Mark 1で特定されたオブジェクトからさらに到達可能なオブジェクトをマークするフェーズ。このフェーズは通常、並行して実行されます。
    *   **マークワーカー**: GCのマーク作業を実行するゴルーチン。これには以下の種類があります。
        *   **Dedicated Mark Workers**: GC専用に割り当てられたワーカー。
        *   **Fractional Mark Workers**: アプリケーションのPの一部を借りてGC作業を行うワーカー。
        *   **Idle Mark Workers**: アプリケーションのPがアイドル状態（実行すべきゴルーチンがない）のときに、GC作業を補助するために起動されるワーカー。
*   **スイープフェーズ (Sweep Phase)**: マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放するフェーズ。
*   **Write Barrier**: GCのマークフェーズ中に、アプリケーションがポインタを書き換える際に実行される小さなコードスニペット。これにより、GCがオブジェクトグラフの変更を追跡し、ライブオブジェクトを見落とすことを防ぎます。コミットメッセージの「barriers are cleared」とは、このライトバリアが特定のGCフェーズで無効化されることを指す可能性があります。
*   **`gcWork` キャッシュ**: GCワーカーがマーク作業を行う際に使用する、マーク対象オブジェクトのキューのようなもの。Pごとにローカルキャッシュを持つことで、競合を減らし効率を高めます。

### Goスケジューラ

Goランタイムのスケジューラは、ゴルーチンをOSスレッド（M）上で実行されるP（プロセッサ）に割り当てます。Pは、ゴルーチンを実行するためのコンテキストを提供します。

*   **P (Processor)**: Goスケジューラにおける論理的なプロセッサ。OSスレッド（M）がPを取得し、そのPに割り当てられたゴルーチンを実行します。
*   **M (Machine)**: OSスレッド。
*   **G (Goroutine)**: Goの軽量スレッド。

スケジューラは、Pがアイドル状態になったときに、GC作業を含むバックグラウンドタスクを実行するかどうかを決定する役割も担います。

### `gcBlackenEnabled`

これは、GCのマークフェーズがアクティブであり、オブジェクトを「黒くする」（到達可能としてマークする）ことが許可されているかどうかを示すフラグまたは状態変数です。

### `work.bgMark1.done` および `work.bgMark2.done`

これらは、GCのmark 1およびmark 2フェーズのバックグラウンド作業が完了したかどうかを示す状態変数であると推測されます。`done == 0`は、そのフェーズの作業がまだ完了していないことを意味するでしょう。

## 技術的詳細

このコミットの核心は、`src/runtime/proc.go`内のアイドルマークワーカーを起動する条件の変更にあります。変更前は、Pがアイドル状態であり、GCマークフェーズが有効で、マークワーカーが利用可能で、かつGC作業が利用可能であれば、アイドルマークワーカーが起動していました。

問題は、`gcMarkWorkAvailable(_p_)`が`true`を返す場合でも、GCのバリアがまだクリアされていない（つまり、GCの特定のフェーズが完全に準備できていない）状況でアイドルワーカーが起動してしまう可能性があったことです。特に、mark 1の完了とmark 2の開始の間は、GCの内部状態が遷移中であり、この期間にアイドルワーカーが活動すると、GCの整合性が損なわれる可能性がありました。

コミットメッセージによると、専用ワーカーや部分ワーカーは、mark 1またはmark 2のバリアがクリアされるまで起動しないという制限が既にありました。このコミットは、この同じ制限をアイドルマークワーカーにも適用することで、GCの動作を一貫させ、予測可能にします。

具体的には、アイドルマークワーカーの起動条件に `(work.bgMark1.done == 0 || work.bgMark2.done == 0)` という条件が追加されました。これは、mark 1またはmark 2のバックグラウンド作業がまだ完了していない場合にのみ、アイドルマークワーカーが起動できることを意味します。

*   `work.bgMark1.done == 0`: mark 1のバックグラウンド作業がまだ進行中であるか、完了していない。
*   `work.bgMark2.done == 0`: mark 2のバックグラウンド作業がまだ進行中であるか、完了していない。

この条件が追加されることで、mark 1とmark 2の間の遷移期間や、いずれかのマークフェーズが完全に完了していない期間に、アイドルマークワーカーが不適切に起動することが防止されます。これにより、GCの内部状態が安定しているときにのみワーカーが活動するようになり、GCの正確性が向上し、デッドロックの可能性が排除されます。また、スケジューラがGC完了をチェックするという冗長な安全策も将来的には不要になる見込みです。

## コアとなるコードの解説

変更されたコードは、GoスケジューラがP（プロセッサ）がアイドル状態になったときに、GCのアイドルマークワーカーを起動するかどうかを決定する条件文です。

**変更前のコード:**

```go
if _p_ := _g_.m.p.ptr(); gcBlackenEnabled != 0 && _p_.gcBgMarkWorker != nil && gcMarkWorkAvailable(_p_) {
```

この条件は以下の要素で構成されていました。
*   `_p_ := _g_.m.p.ptr()`: 現在のゴルーチン`_g_`が実行されているP（プロセッサ）を取得します。
*   `gcBlackenEnabled != 0`: GCのマークフェーズがアクティブであり、オブジェクトを黒くする（到達可能としてマークする）ことが許可されている状態であることを確認します。
*   `_p_.gcBgMarkWorker != nil`: PにGCバックグラウンドマークワーカーが割り当てられていることを確認します。
*   `gcMarkWorkAvailable(_p_)`: 現在のPでGC作業が利用可能であることを確認します。

**変更後のコード:**

```go
if _p_ := _g_.m.p.ptr(); gcBlackenEnabled != 0 && _p_.gcBgMarkWorker != nil && (work.bgMark1.done == 0 || work.bgMark2.done == 0) && gcMarkWorkAvailable(_p_) {
```

変更点として、以下の条件が追加されました。
*   `(work.bgMark1.done == 0 || work.bgMark2.done == 0)`:
    *   `work.bgMark1.done == 0`: GCのmark 1フェーズのバックグラウンド作業がまだ完了していないことを示します。
    *   `work.bgMark2.done == 0`: GCのmark 2フェーズのバックグラウンド作業がまだ完了していないことを示します。

この追加された条件は、GCのmark 1またはmark 2のいずれかのフェーズがまだ進行中である場合にのみ、アイドルマークワーカーが起動することを許可します。これにより、mark 1が完了し、mark 2がまだ開始されていない（またはその逆）といった、GCのフェーズ間の遷移期間中にアイドルワーカーが不適切に起動するのを防ぎます。

つまり、この変更により、アイドルマークワーカーは、GCのマークフェーズがアクティブであり、かつ、いずれかのマークフェーズのバックグラウンド作業がまだ残っている場合にのみ、GC作業を補助するようになります。これは、GCの整合性を保ち、デッドロックの可能性を排除するための重要な修正です。

# [インデックス 27338] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおける最適化ルール記述方法の改善に関するものです。具体的には、ルール内のサブ式に名前を付ける機能が導入され、これによりルールの可読性が向上し、生成されるコードが削減されました。

変更された主なファイルは以下の通りです。

*   `src/cmd/compile/internal/ssa/gen/AMD64.rules`: AMD64アーキテクチャ向けのSSA書き換えルール。
*   `src/cmd/compile/internal/ssa/gen/generic.rules`: 汎用的なSSA書き換えルール。
*   `src/cmd/compile/internal/ssa/gen/rulegen.go`: SSA書き換えルールをGoコードに変換するジェネレータ。
*   `src/cmd/compile/internal/ssa/rewriteAMD64.go`: `AMD64.rules`から生成されるAMD64アーキテクチャ向け書き換えコード。
*   `src/cmd/compile/internal/ssa/rewritedec.go`: デバッグ用の書き換えコード。
*   `src/cmd/compile/internal/ssa/rewritegeneric.go`: `generic.rules`から生成される汎用書き換えコード。

## 元コミット内容

Goコンパイラにおいて、マッチングルールのサブ式に名前を付けることを許可します。
例えば、`(OpA x:(OpB y)) -> ..ここでxを使ってOpBの値を参照..` のように記述できるようになります。
これにより、これまで使用していた `.Args[0].Args[0]...` のような参照方法が不要になります。
また、この変更に伴い、参照されるたびに `.Args[i]` シーケンスで再計算する代わりに、すべてのサブ式マッチに名前を付けるようにしました。これにより、生成されるルールコードが少し小さくなります。

## 変更の背景

GoコンパイラのSSA（Static Single Assignment）バックエンドでは、コードの最適化のために書き換えルール（rewrite rules）が使用されます。これらのルールは、特定のパターンにマッチするSSA値を別のSSA値に変換することで、より効率的な命令シーケンスを生成します。

以前のシステムでは、書き換えルール内でサブ式を参照する際、例えばある操作の引数の引数を参照する場合に `.Args[0].Args[0]` のような形式でアクセスする必要がありました。この方法は、特にネストが深くなるにつれて非常に読みにくく、エラーが発生しやすいという問題がありました。また、同じサブ式を複数回参照する場合でも、毎回この冗長な `.Args[i]` シーケンスを記述する必要があり、生成されるコードのサイズが増大する原因となっていました。

このコミットの背景には、以下の課題がありました。

1.  **可読性の低さ**: `.Args[0].Args[0]...` のような参照方法は、ルールの意図を理解するのを困難にしていました。
2.  **保守性の問題**: ルールの構造が変更された場合、すべての参照箇所を更新する必要があり、保守が困難でした。
3.  **コードの冗長性**: 同じサブ式を複数回参照する際に、毎回同じアクセスパスを記述することで、生成されるGoコードが不必要に大きくなっていました。

これらの課題を解決し、SSA書き換えルールの記述と管理をより効率的にするために、サブ式に直接名前を付けるメカニズムが導入されました。

## 前提知識の解説

### 1. SSA (Static Single Assignment)

SSA（Static Single Assignment）は、コンパイラ最適化において広く使用される中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、コンパイラがより強力な最適化（定数伝播、デッドコード削除、共通部分式除去など）を適用できるようになります。

Goコンパイラは、ソースコードを抽象構文木（AST）に変換した後、SSA形式に変換します。このSSA形式に対して様々な最適化パスが適用され、最終的に機械語コードが生成されます。

### 2. GoコンパイラのSSAバックエンドと書き換えルール

GoコンパイラのSSAバックエンドは、`src/cmd/compile/internal/ssa` ディレクトリ以下に実装されています。このバックエンドの重要な部分が「書き換えルール（rewrite rules）」です。書き換えルールは、特定のSSA値のパターンを検出し、それをより最適化された別のSSA値のパターンに変換するために使用されます。

これらのルールは、`src/cmd/compile/internal/ssa/gen/*.rules` のようなファイルにLispのようなS式形式で記述されています（例: `generic.rules`, `AMD64.rules`）。これらのルールは、`rulegen.go` というツールによってGoのコード（例: `rewriteAMD64.go`, `rewritegeneric.go`）に変換されます。この生成されたGoコードが、コンパイル時にSSA値を実際に書き換えるロジックを含んでいます。

書き換えルールの基本的な形式は以下のようになります。

```
(パターン) -> (置換)
```

または、条件付きの場合：

```
(パターン) && (条件) -> (置換)
```

ここで、`パターン` はマッチさせたいSSA値の構造を記述し、`置換` はマッチした場合に生成する新しいSSA値の構造を記述します。

### 3. サブ式 (Subexpressions)

SSA書き換えルールにおいて、サブ式とは、より大きな式の一部を構成する式のことです。例えば、`(Add (Const [1]) x)` という式では、`(Const [1])` と `x` が `Add` 操作のサブ式です。これらのサブ式は、SSAグラフ内の他のSSA値への参照として表現されます。

## 技術的詳細

このコミットの核心は、SSA書き換えルールDSLにおけるサブ式の命名機能の導入です。これにより、ルール内で特定のサブ式に一時的な名前を割り当て、その名前を使って後続のパターンや置換部分で参照できるようになります。

### 新しい命名構文

新しい構文は以下の形式を取ります。

```
(OpA x:(OpB y))
```

ここで、`x` は `(OpB y)` というサブ式に割り当てられた名前です。この `x` は、ルールの右側（置換部分）や、同じルールの他の部分で `(OpB y)` のSSA値を参照するために使用できます。

### 変更のメカニズム

1.  **`rulegen.go` の変更**:
    `rulegen.go` は、`.rules` ファイルに記述されたS式形式のルールを解析し、Goのコードを生成するツールです。このコミットでは、`rulegen.go` がサブ式の命名構文を認識し、それに対応するGoコードを生成するように変更されました。
    具体的には、`genMatch0` 関数が変更され、`x:(OpB y)` のようなパターンを検出すると、`x` という名前のGo変数を生成し、その変数に `(OpB y)` に対応するSSA値を割り当てるコードを出力するようになりました。

    以前は、サブ式へのアクセスは `v.Args[0].Args[0]` のように、親のSSA値 (`v`) から引数リストを辿る形で行われていました。新しいシステムでは、`x := v.Args[0]` のように、サブ式に直接名前を割り当ててから、その名前 (`x`) を使ってサブ式を参照します。

2.  **生成されるコードの変更**:
    `rulegen.go` の変更により、`rewriteAMD64.go` や `rewritegeneric.go` などの生成されるファイルの内容が大きく変わりました。これらのファイルでは、冗長な `.Args[i]` チェーンが減少し、代わりに命名された変数による参照が増えました。これにより、生成されるGoコードの可読性が向上し、またコードサイズも削減されます。

    例えば、以前のルールが `(MOVBQSX (MOVBload [off] {sym} ptr mem)) && v.Args[0].Uses == 1` のような条件を含んでいた場合、`v.Args[0]` は `MOVBload` オペレーションを指していました。このコミット後、このルールは `(MOVBQSX x:(MOVBload [off] {sym} ptr mem)) && x.Uses == 1` のように記述され、`MOVBload` オペレーションは `x` という名前で直接参照できるようになりました。

### 利点

*   **可読性の向上**: ルールがより自然な形で記述できるようになり、特定のサブ式が何を表しているのかが一目でわかるようになりました。
*   **保守性の向上**: ルールの構造が変更された場合でも、命名されたサブ式を参照している箇所は影響を受けにくくなります。
*   **生成コードの削減**: 同じサブ式を複数回参照する場合に、毎回 `.Args[i]` シーケンスを再計算する代わりに、一度名前を割り当てた変数を使用することで、生成されるGoコードのバイトコードサイズが削減されます。これは、コンパイラ自身のバイナリサイズや、コンパイル時間のわずかな改善に寄与する可能性があります。
*   **エラーの減少**: 複雑な `.Args[i]` チェーンを手動で記述する際のタイプミスや論理エラーのリスクが減少します。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、`src/cmd/compile/internal/ssa/gen/rulegen.go` にあります。特に、`genMatch0` 関数がサブ式の命名を処理するように修正されました。

### `src/cmd/compile/internal/ssa/gen/rulegen.go` の変更点

変更前:
`genMatch0` 関数は、マッチするパターンを再帰的に処理し、`v.Args[i]` のような形式でサブ式を生成していました。変数名が与えられていない場合、サブ式は匿名で処理され、その都度 `v.Args[i]` を介してアクセスする必要がありました。

変更後:
`genMatch0` 関数は、パターン内の `x:(OpB y)` のような命名構文を認識するようになりました。
*   `colon := strings.Index(a, ":")` と `openparen := strings.Index(a, "(")` を使って、サブ式に名前が付けられているかどうかを検出します。
*   名前が付けられている場合 (`colon < openparen` の条件を満たす場合)、その名前 (`argname`) を使ってGoの変数を宣言し、対応するSSA値を割り当てます。
    ```go
    fmt.Fprintf(w, "%s := %s.Args[%d]\\n", argname, v, argnum)
    genMatch0(w, arch, a, argname, m, false) // 再帰呼び出しで、この名前付きサブ式を処理
    ```
*   名前が付けられていない場合でも、自動生成された名前 (`argname = fmt.Sprintf("%s_%d", v, argnum)`) を使用してサブ式に名前を付け、その名前を使ってGoの変数を宣言するように変更されました。これにより、すべてのサブ式が一度名前付けされ、冗長な `.Args[i]` アクセスが排除されます。

### `.rules` ファイルの変更例

`src/cmd/compile/internal/ssa/gen/AMD64.rules` の例:

変更前:
```
(MOVBQSX (MOVBload [off] {sym} ptr mem)) && v.Args[0].Uses == 1 -> @v.Args[0].Block (MOVBQSXload <v.Type> [off] {sym} ptr mem)
```
`v.Args[0]` が `MOVBload` を指しており、その `Uses` フィールドにアクセスするために `v.Args[0].Uses` と記述されています。

変更後:
```
(MOVBQSX x:(MOVBload [off] {sym} ptr mem)) && x.Uses == 1 -> @x.Block (MOVBQSXload <v.Type> [off] {sym} ptr mem)
```
`MOVBload` サブ式に `x` という名前が付けられ、条件部分で `x.Uses == 1` と直接参照できるようになりました。これにより、ルールの意図がより明確になります。

同様に、ネストされたサブ式へのアクセスも簡素化されています。
変更前:
```
(ORQ ... (MOVBQZXload [i] {s} p mem) ...) -> @v.Args[0].Args[0].Args[0].Args[0].Args[0].Args[0].Args[0].Block (MOVQload [i] {s} p mem)
```
非常に長い `.Args` チェーンが使用されています。

変更後:
```
(ORQ ... x:(MOVBQZXload [i] {s} p mem) ...) -> @x.Block (MOVQload [i] {s} p mem)
```
`MOVBQZXload` サブ式に `x` という名前が付けられ、置換部分で `x.Block` と簡潔に参照できるようになりました。

## コアとなるコードの解説

`rulegen.go` の `genMatch0` 関数は、SSA書き換えルールのパターンマッチング部分に対応するGoコードを生成する役割を担っています。このコミットにおける主要な変更は、この関数がサブ式に名前を割り当てるロジックを導入した点です。

以前の `genMatch0` は、パターン内の各要素を再帰的に処理し、それが単純な変数であればその変数を現在のSSA値 (`v`) に割り当て、複合的な式であれば `v.Args[i]` のような形でそのサブ式を処理していました。このアプローチでは、同じサブ式を複数回参照する場合、毎回 `v.Args[i]` のチェーンを再構築する必要がありました。

新しい `genMatch0` は、以下のロジックを追加しました。

1.  **名前付きサブ式の検出**:
    パターン文字列 `a` を解析し、`x:(OpB y)` のような形式でコロン `:` が括弧 `(` の前に現れる場合、それは名前付きサブ式であると判断します。
    `colon := strings.Index(a, ":")` と `openparen := strings.Index(a, "(")` を使用して、この条件をチェックします。

2.  **名前付き変数の生成**:
    名前付きサブ式が検出された場合、コロンの前の部分 (`a[:colon]`) を `argname` として抽出し、この名前でGoの変数を宣言します。この変数には、現在のSSA値 `v` の `argnum` 番目の引数 (`v.Args[argnum]`) が割り当てられます。
    `fmt.Fprintf(w, "%s := %s.Args[%d]\\n", argname, v, argnum)`

3.  **自動生成された名前の導入**:
    明示的に名前が付けられていない複合サブ式に対しても、`fmt.Sprintf("%s_%d", v, argnum)` のような形式で自動的に名前 (`argname`) を生成し、同様にGoの変数を宣言してSSA値を割り当てます。これにより、すべてのサブ式が一度だけ評価され、名前付き変数を通じて参照されるようになります。

4.  **再帰的な処理**:
    名前が割り当てられたサブ式 (`a[colon+1:]` または元の `a`) は、新しい `argname` を現在のSSA値として `genMatch0` を再帰的に呼び出すことで処理されます。これにより、ネストされたサブ式も適切に名前付けされ、簡潔に参照できるようになります。

この変更により、`rulegen.go` が生成する `rewrite*.go` ファイル内のコードは、`v.Args[0].Args[0].Args[0]` のような冗長な記述が大幅に削減され、`x := v.Args[0]` のように一度名前を割り当てた後、`x` を直接使用する形に変わりました。これは、生成されるコードの可読性と効率性の両方を向上させる重要な改善です。

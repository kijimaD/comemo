# [インデックス 2233] ファイルの概要

このコミットは、Goコンパイラのバックエンドとフロントエンドにわたる複数のファイルに影響を与えています。

-   `src/cmd/6g/cgen.c`: AMD64アーキテクチャ向けのコード生成における共通部分を扱うファイルです。主に、ノードからコードを生成する際の初期化処理の条件が変更されています。
-   `src/cmd/6g/gen.c`: AMD64アーキテクチャ向けのコード生成の汎用的な部分を扱うファイルです。静的アドレスの解決や、DATAステートメントとして初期化を生成するロジックが追加・拡張されています。
-   `src/cmd/gc/dcl.c`: Goコンパイラのフロントエンドにおける宣言処理を扱うファイルです。特に、静的初期化のためのAST（抽象構文木）変換ロジックが大幅に追加されています。自動変数から静的変数への書き換えを行い、DATAステートメントでの初期化を可能にするための準備を行います。
-   `src/cmd/gc/gen.c`: Goコンパイラのフロントエンドにおける汎用的なコード生成処理を扱うファイルです。アサインメント（代入）のコード生成において、静的初期化のパスが追加されています。
-   `src/cmd/gc/walk.c`: GoコンパイラのフロントエンドにおけるASTのウォーク（走査）処理を扱うファイルです。複合リテラル（struct, array, map）の処理が変更され、特にstructとarrayの静的初期化のパスが調整されています。

## 変更の背景

このコミットの主な背景は、Goプログラムにおける静的初期化の効率化です。Goコンパイラは、変数の初期化を通常、実行時の代入ステートメントとして生成します。しかし、静的に決定できる値（特にグローバル変数やパッケージレベルの変数）については、コンパイル時にデータセクションに直接値を埋め込む「DATAステートメント」として初期化する方が、実行時のオーバーヘッドを削減し、生成されるバイナリの効率を向上させることができます。

このコミット以前は、構造体（struct）や配列（array）の静的初期化も実行時の代入として処理されていたと考えられます。この変更により、コンパイラはこれらの複合型の静的初期化をDATAステートメントとして扱うようになり、パフォーマンスの向上やバイナリサイズの削減が期待されます。コミットメッセージにある「slices and maps are yet to do」という記述から、この最適化が段階的に導入されており、このコミットではstructとarrayに焦点が当てられていることがわかります。

これは、Goコンパイラの初期段階における重要な最適化の一つであり、生成されるコードの品質と実行効率を高めるための継続的な取り組みの一環です。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラおよびプログラミング言語の基本的な概念を理解しておく必要があります。

### Goコンパイラ (gc, 6g, 8g, 5g)

Goコンパイラは、初期には`gc`（Go Compiler）という名前で知られていました。これは、Go言語のソースコードを機械語に変換するツールチェーンの総称です。Goコンパイラは、複数のステージとコンポーネントから構成されています。

-   **`gc` (Go Compiler)**: これはGoコンパイラ全体のフロントエンドを指すことが多く、ソースコードの解析、AST（抽象構文木）の構築、型チェック、最適化、中間コード生成などを行います。
-   **`6g`, `8g`, `5g`**: これらは特定のアーキテクチャ向けのバックエンドコンパイラを指します。
    -   `6g`: AMD64（x86-64）アーキテクチャ向けのコンパイラ。
    -   `8g`: ARMアーキテクチャ向けのコンパイラ。
    -   `5g`: PowerPCアーキテクチャ向けのコンパイラ。
    このコミットでは、`src/cmd/6g/`以下のファイルが変更されていることから、AMD64アーキテクチャ向けのコード生成に特化した変更が含まれていることがわかります。

### 静的初期化 (Static Initialization)

静的初期化とは、プログラムの実行開始前に、コンパイル時またはリンク時に変数を初期値で設定することです。グローバル変数や静的変数（Goではパッケージレベルの変数）は、通常、静的初期化の対象となります。
静的初期化されたデータは、プログラムのデータセクションに格納され、プログラムがロードされる際にメモリに配置されます。これにより、実行時に初期化のためのコードを実行する必要がなくなり、起動時間の短縮や効率化が図れます。

### DATAステートメント

DATAステートメントは、アセンブリ言語や一部のコンパイラが生成する中間表現において、データセクションに直接値を埋め込むための命令や概念を指します。例えば、アセンブリ言語では`.data`セクションに`.word`や`.byte`のようなディレクティブを使って値を定義します。コンパイラは、静的初期化された変数を、実行時の代入命令ではなく、このようなDATAステートメントとして出力することで、より効率的なバイナリを生成します。

### Goの型システム (structs, arrays, slices, maps)

-   **Structs (構造体)**: 異なる型のフィールドをまとめた複合型です。C言語の構造体やJava/C#のクラスに似ています。
-   **Arrays (配列)**: 同じ型の要素を固定長で並べたシーケンスです。Goの配列は値型であり、サイズが型の一部となります。
-   **Slices (スライス)**: 配列の上に構築された動的なビューです。長さと容量を持ち、基になる配列の一部を参照します。スライスは参照型です。
-   **Maps (マップ)**: キーと値のペアを格納するハッシュテーブルです。マップは参照型です。

このコミットでは、structとarrayの静的初期化がDATAステートメントの対象となり、sliceとmapはまだ対象外であることが明記されています。これは、sliceとmapが参照型であり、その初期化がヒープアロケーションやランタイム関数呼び出しを伴うため、単純なDATAステートメントでの初期化が難しいことに起因します。

### AST (Abstract Syntax Tree)

ASTは、ソースコードの構造を木構造で表現したものです。コンパイラはソースコードを解析し、ASTを構築します。その後の型チェック、最適化、コード生成などのフェーズは、このASTを走査（ウォーク）したり、変換したりすることで行われます。

### Goコンパイラのファイル群の役割

-   **`src/cmd/gc/dcl.c`**: Declaration（宣言）処理を担当します。変数の宣言、型の定義、関数のシグネチャなどを処理し、ASTに反映させます。このファイルは、初期化式のASTを変換する重要な役割を担っています。
-   **`src/cmd/gc/walk.c`**: ASTのWalk（走査）処理を担当します。ASTを巡回し、各ノードに対して型チェック、最適化、中間コードへの変換などを行います。複合リテラルの処理もここで行われます。
-   **`src/cmd/6g/gen.c` / `src/cmd/gc/gen.c`**: Code Generation（コード生成）を担当します。ASTから最終的な機械語に近い中間表現（またはアセンブリコード）を生成します。`gc/gen.c`はより汎用的なコード生成、`6g/gen.c`はAMD64アーキテクチャに特化したコード生成を行います。
-   **`src/cmd/6g/cgen.c`**: Common Code Generation（共通コード生成）を担当します。特定のアーキテクチャ（この場合はAMD64）向けのコード生成において、共通して利用されるユーティリティ関数やロジックが含まれます。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラがどのようにして構造体と配列の静的初期化を、実行時の代入ではなく、コンパイル時のDATAステートメントとして処理するように変更されたかという点にあります。

### 静的初期化の識別と変換

1.  **`initflag`の導入**:
    `src/cmd/6g/cgen.c`の変更で`initflag`というグローバル変数が導入されています。`gen_as_init`関数の呼び出しに`initflag`のチェックが追加されており、これにより静的初期化のコンテキストでのみ特定のコードパスが有効になるように制御されています。これは、コンパイラが静的初期化のフェーズにあるかどうかを示すフラグと考えられます。

2.  **静的アドレスの解決 (`stataddr`関数)**:
    `src/cmd/6g/gen.c`に新しく追加された`stataddr`関数は、与えられたASTノードが静的にアドレス指定可能な変数（グローバル変数やパッケージレベルの変数）を参照しているかどうかを判断し、そのアドレス情報を抽出します。
    -   `ONAME`（変数名）の場合、そのノードが`PEXTERN`（外部リンケージを持つ、つまり静的変数）であれば静的アドレスとみなします。
    -   `ODOT`（構造体フィールドへのアクセス）や`OINDEX`（配列要素へのアクセス）の場合、再帰的に左辺（ベースとなる変数）が静的アドレスであるかをチェックし、オフセットを計算して最終的な静的アドレスを特定します。
    -   `getlit`関数は、配列のインデックスがリテラル定数であるかをチェックするために使用されます。

3.  **DATAステートメントの生成 (`gen_as_init`関数)**:
    `src/cmd/6g/gen.c`の`gen_as_init`関数が大幅に拡張されています。この関数は、与えられたノードがDATAステートメントとして初期化可能であるかを判断し、可能であれば`gins(ADATA, ...)`を呼び出してDATAステートメントを生成します。
    -   `initflag`が設定されていること、および初期化対象が静的アドレスであること（`stataddr`でチェック）が前提となります。
    -   初期化される値がリテラル（`OLITERAL`）である場合に、その型（`TBOOL`, `TINT`, `TFLOAT`など）に応じてDATAステートメントを生成します。これにより、数値や真偽値などの基本型のリテラル値が直接データセクションに埋め込まれるようになります。

### AST変換による静的初期化の準備

`src/cmd/gc/dcl.c`における変更が、このコミットの最も複雑で重要な部分です。ここでは、自動変数（ローカル変数）の初期化式を、静的初期化に適した形に変換するロジックが実装されています。

-   **`initlin`関数**:
    ASTを走査し、初期化に関連する代入（`OAS`）や関数呼び出し（`OCALL`、特に`mapassign1`のようなランタイム関数）のノードを収集します。これらのノードは、後で静的初期化の対象となる自動変数を参照している可能性があります。`xxx`というグローバルなリストにこれらのノードを追加していきます。

-   **`inittmp`, `sametmp`, `indsametmp`関数**:
    これらは、一時変数（`!tmpname`というシンボル名を持つ自動変数）を識別し、それらが同じ一時変数を参照しているかどうかを比較するためのヘルパー関数です。静的初期化の最適化では、コンパイラが生成した一時変数を、最終的な静的変数に置き換える必要があります。

-   **`initsub`関数**:
    `initlin`で収集されたノードリスト（`xxx`）を走査し、特定の一時変数（`nam`）への参照を、新しいノード（`n`、これは最終的な静的変数への参照になる）に置き換えます。
    -   代入（`OAS`）の左辺が一時変数であれば、それを新しいノードに置き換えます。
    -   構造体フィールドアクセス（`ODOT`）や配列要素アクセス（`OINDEX`）のベースが一時変数であれば、同様に置き換えます。
    -   `OCALL`（特に`mapassign1`）の場合、その引数リスト内の一時変数への参照も置き換えます。
    -   置き換えが成功した場合、元の代入ノードは`OEMPTY`（空のステートメント）に変換され、最終的なコード生成から除外されます。

-   **`initfix`関数**:
    `fninit`（関数の初期化処理）から呼び出される主要な関数です。
    1.  `initlin`を呼び出して、初期化に関連するノードを`xxx`リストに収集します。
    2.  `xxx`リストを逆順にします（`rev(xxx)`）。これは、依存関係のある初期化が正しい順序で処理されるようにするためと考えられます。
    3.  `xxx`リストを走査し、`OAS`ノードで右辺が一時変数であるものを見つけます。
    4.  そのような代入が見つかった場合、`initsub`を呼び出して、その一時変数へのすべての参照を代入の左辺（これは最終的に静的変数になる）に置き換えます。
    5.  置き換えが成功した場合、元の代入ノードは`OEMPTY`に設定されます。
    このプロセスにより、自動変数として一時的に初期化されていた複合リテラルが、最終的に静的変数への直接的な初期化として扱われるようにASTが変換されます。

### 複合リテラルの処理変更

`src/cmd/gc/walk.c`では、複合リテラル（`OCOMPOS`）の処理が変更されています。
-   以前は、`&Point(1, 2)`のような複合リテラルがヒープアロケーションと代入として処理されていました。
-   このコミットでは、`OCOMPOS`ノードが静的初期化の対象となる場合、`initfix`によってASTが変換され、`new`呼び出しとそれに続く代入が、最終的にDATAステートメントとして処理されるようにパスが調整されます。
-   `arraylit`関数も変更され、配列リテラルの初期化が`walktype(a, Etop)`を通じて`addtop`リストに追加されるようになりました。これにより、初期化の代入がトップレベルのステートメントとして扱われ、`initfix`による変換の対象となります。

これらの変更により、コンパイラは構造体や配列の複合リテラルが静的変数に割り当てられる際に、その初期化を効率的なDATAステートメントとして出力できるようになります。

## コアとなるコードの解説

このコミットの核となるのは、Goコンパイラが静的初期化を処理する方法を根本的に変更した点です。

1.  **`initflag`による静的初期化パスの制御**:
    `src/cmd/6g/cgen.c`の変更は、`gen_as_init`関数が静的初期化のコンテキストでのみ実行されるようにするためのガードです。これにより、通常の実行時初期化と静的初期化のロジックが混在することを防ぎ、コンパイラの動作を明確に分離します。

2.  **`stataddr`と`gen_as_init`によるDATAステートメント生成**:
    `src/cmd/6g/gen.c`に追加された`stataddr`関数は、コンパイラがASTを走査する際に、どの変数が静的にアドレス指定可能であるかを効率的に判断できるようにします。これは、グローバル変数やパッケージレベルの変数、およびそれらの構造体フィールドや配列要素へのアクセスを識別するために重要です。
    拡張された`gen_as_init`関数は、`stataddr`によって静的アドレスと識別された変数へのリテラル値の代入を検出し、それをアセンブリの`ADATA`命令（DATAステートメント）として直接出力します。これにより、実行時に代入命令を実行する代わりに、プログラムのロード時にデータがメモリに配置されるようになります。これは、特に大きな構造体や配列の初期化において、起動時間の短縮とコードサイズの削減に貢献します。

3.  **`dcl.c`におけるAST変換の複雑なロジック**:
    `src/cmd/gc/dcl.c`に追加された`initlin`, `inittmp`, `sametmp`, `indsametmp`, `initsub`, `initfix`の各関数は、このコミットの最も技術的に複雑な部分です。
    -   Goの複合リテラル（例: `Point{1, 2}`）は、コンパイラによって一時変数への一連の代入として内部的に表現されることがあります。
    -   `initfix`は、これらの「一時変数への代入」を検出し、その一時変数へのすべての参照を、最終的に静的初期化されるべき変数への参照に「書き換え」ます。
    -   例えば、`var p = Point{1, 2}`というコードがあった場合、コンパイラは内部的に`tmp := new(Point); tmp.x = 1; tmp.y = 2; p = *tmp`のような中間コードを生成するかもしれません。`initfix`は、この`tmp`への参照を`p`への参照に置き換え、`p.x = 1; p.y = 2`のような形に変換します。
    -   さらに、この変換が成功した場合、元の代入ノードは`OEMPTY`（空のステートメント）にマークされ、通常のコード生成パスからは除外されます。これにより、`gen_as_init`がこれらの初期化をDATAステートメントとして処理できるようになります。
    この変換は、コンパイラが生成する中間コードの構造に深く依存しており、コミットメッセージにある「it is extremely fragile knowing exactly how the code from (struct|array|map)lit will look」というコメントがその複雑さを示唆しています。

4.  **`walk.c`における複合リテラル処理の調整**:
    `src/cmd/gc/walk.c`の変更は、複合リテラルがAST上でどのように表現され、処理されるかを調整します。特に、`&Point(1, 2)`のようなポインタへの複合リテラル初期化が、ヒープアロケーションと代入の組み合わせから、静的初期化のパスに適切に誘導されるように変更されています。`walktype(a, Etop)`の追加は、初期化の代入がトップレベルのステートメントとして扱われ、`initfix`による変換の対象となるようにするための重要なステップです。

これらの変更が連携することで、Goコンパイラは構造体と配列の静的初期化を、より効率的なDATAステートメントとして生成できるようになり、Goプログラムの実行効率が向上します。

## 変更の背景

このコミットの主な背景は、Goプログラムにおける静的初期化の効率化です。Goコンパイラは、変数の初期化を通常、実行時の代入ステートメントとして生成します。しかし、静的に決定できる値（特にグローバル変数やパッケージレベルの変数）については、コンパイル時にデータセクションに直接値を埋め込む「DATAステートメント」として初期化する方が、実行時のオーバーヘッドを削減し、生成されるバイナリの効率を向上させることができます。

これは、Goコンパイラの初期段階における重要な最適化の一つであり、生成されるコードの品質と実行効率を高めるための継続的な取り組みの一環です。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラおよびプログラミング言語の基本的な概念を理解しておく必要があります。

### Goコンパイラ (gc, 6g, 8g, 5g)

Goコンパイラは、初期には`gc`（Go Compiler）という名前で知られていました。これは、Go言語のソースコードを機械語に変換するツールチェーンの総称です。Goコンパイラは、複数のステージとコンポーネントから構成されています。

-   **`gc` (Go Compiler)**: これはGoコンパイラ全体のフロントエンドを指すことが多く、ソースコードの解析、AST（抽象構文木）の構築、型チェック、最適化、中間コード生成などを行います。
-   **`6g`, `8g`, `5g`**: これらは特定のアーキテクチャ向けのバックエンドコンパイラを指します。
    -   `6g`: AMD64（x86-64）アーキテクチャ向けのコンパイラ。
    -   `8g`: ARMアーキテクチャ向けのコンパイラ。
    -   `5g`: PowerPCアーキテクチャ向けのコンパイラ。
    このコミットでは、`src/cmd/6g/`以下のファイルが変更されていることから、AMD64アーキテクチャ向けのコード生成に特化した変更が含まれていることがわかります。

### 静的初期化 (Static Initialization)

静的初期化とは、プログラムの実行開始前に、コンパイル時またはリンク時に変数を初期値で設定することです。グローバル変数や静的変数（Goではパッケージレベルの変数）は、通常、静的初期化の対象となります。
静的初期化されたデータは、プログラムのデータセクションに格納され、プログラムがロードされる際にメモリに配置されます。これにより、実行時に初期化のためのコードを実行する必要がなくなり、起動時間の短縮や効率化が図れます。

### DATAステートメント

DATAステートメントは、アセンブリ言語や一部のコンパイラが生成する中間表現において、データセクションに直接値を埋め込むための命令や概念を指します。例えば、アセンブリ言語では`.data`セクションに`.word`や`.byte`のようなディレクティブを使って値を定義します。コンパイラは、静的初期化された変数を、実行時の代入命令ではなく、このようなDATAステートメントとして出力することで、より効率的なバイナリを生成します。

### Goの型システム (structs, arrays, slices, maps)

-   **Structs (構造体)**: 異なる型のフィールドをまとめた複合型です。C言語の構造体やJava/C#のクラスに似ています。
-   **Arrays (配列)**: 同じ型の要素を固定長で並べたシーケンスです。Goの配列は値型であり、サイズが型の一部となります。
-   **Slices (スライス)**: 配列の上に構築された動的なビューです。長さと容量を持ち、基になる配列の一部を参照します。スライスは参照型です。
-   **Maps (マップ)**: キーと値のペアを格納するハッシュテーブルです。マップは参照型です。

このコミットでは、structとarrayの静的初期化がDATAステートメントの対象となり、sliceとmapはまだ対象外であることが明記されています。これは、sliceとmapが参照型であり、その初期化がヒープアロケーションやランタイム関数呼び出しを伴うため、単純なDATAステートメントでの初期化が難しいことに起因します。

### AST (Abstract Syntax Tree)

ASTは、ソースコードの構造を木構造で表現したものです。コンパイラはソースコードを解析し、ASTを構築します。その後の型チェック、最適化、コード生成などのフェーズは、このASTを走査（ウォーク）したり、変換したりすることで行われます。

### Goコンパイラのファイル群の役割

-   **`src/cmd/gc/dcl.c`**: Declaration（宣言）処理を担当します。変数の宣言、型の定義、関数のシグネチャなどを処理し、ASTに反映させます。このファイルは、初期化式のASTを変換する重要な役割を担っています。
-   **`src/cmd/gc/walk.c`**: ASTのWalk（走査）処理を担当します。ASTを巡回し、各ノードに対して型チェック、最適化、中間コードへの変換などを行います。複合リテラルの処理もここで行われます。
-   **`src/cmd/6g/gen.c` / `src/cmd/gc/gen.c`**: Code Generation（コード生成）を担当します。ASTから最終的な機械語に近い中間表現（またはアセンブリコード）を生成します。`gc/gen.c`はより汎用的なコード生成、`6g/gen.c`はAMD64アーキテクチャに特化したコード生成を行います。
-   **`src/cmd/6g/cgen.c`**: Common Code Generation（共通コード生成）を担当します。特定のアーキテクチャ（この場合はAMD64）向けのコード生成において、共通して利用されるユーティリティ関数やロジックが含まれます。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラがどのようにして構造体と配列の静的初期化を、実行時の代入ではなく、コンパイル時のDATAステートメントとして処理するように変更されたかという点にあります。

### 静的初期化の識別と変換

1.  **`initflag`の導入**:
    `src/cmd/6g/cgen.c`の変更で`initflag`というグローバル変数が導入されています。`gen_as_init`関数の呼び出しに`initflag`のチェックが追加されており、これにより静的初期化のコンテキストでのみ特定のコードパスが有効になるように制御されています。これは、コンパイラが静的初期化のフェーズにあるかどうかを示すフラグと考えられます。

2.  **静的アドレスの解決 (`stataddr`関数)**:
    `src/cmd/6g/gen.c`に新しく追加された`stataddr`関数は、与えられたASTノードが静的にアドレス指定可能な変数（グローバル変数やパッケージレベルの変数）を参照しているかどうかを判断し、そのアドレス情報を抽出します。
    -   `ONAME`（変数名）の場合、そのノードが`PEXTERN`（外部リンケージを持つ、つまり静的変数）であれば静的アドレスとみなします。
    -   `ODOT`（構造体フィールドへのアクセス）や`OINDEX`（配列要素へのアクセス）の場合、再帰的に左辺（ベースとなる変数）が静的アドレスであるかをチェックし、オフセットを計算して最終的な静的アドレスを特定します。
    -   `getlit`関数は、配列のインデックスがリテラル定数であるかをチェックするために使用されます。

3.  **DATAステートメントの生成 (`gen_as_init`関数)**:
    `src/cmd/6g/gen.c`の`gen_as_init`関数が大幅に拡張されています。この関数は、与えられたノードがDATAステートメントとして初期化可能であるかを判断し、可能であれば`gins(ADATA, ...)`を呼び出してDATAステートメントを生成します。
    -   `initflag`が設定されていること、および初期化対象が静的アドレスであること（`stataddr`でチェック）が前提となります。
    -   初期化される値がリテラル（`OLITERAL`）である場合に、その型（`TBOOL`, `TINT`, `TFLOAT`など）に応じてDATAステートメントを生成します。これにより、数値や真偽値などの基本型のリテラル値が直接データセクションに埋め込まれるようになります。

### AST変換による静的初期化の準備

`src/cmd/gc/dcl.c`における変更が、このコミットの最も複雑で重要な部分です。ここでは、自動変数（ローカル変数）の初期化式を、静的初期化に適した形に変換するロジックが実装されています。

-   **`initlin`関数**:
    ASTを走査し、初期化に関連する代入（`OAS`）や関数呼び出し（`OCALL`、特に`mapassign1`のようなランタイム関数）のノードを収集します。これらのノードは、後で静的初期化の対象となる自動変数を参照している可能性があります。`xxx`というグローバルなリストにこれらのノードを追加していきます。

-   **`inittmp`, `sametmp`, `indsametmp`関数**:
    これらは、一時変数（`!tmpname`というシンボル名を持つ自動変数）を識別し、それらが同じ一時変数を参照しているかどうかを比較するためのヘルパー関数です。静的初期化の最適化では、コンパイラが生成した一時変数を、最終的な静的変数に置き換える必要があります。

-   **`initsub`関数**:
    `initlin`で収集されたノードリスト（`xxx`）を走査し、特定の一時変数（`nam`）への参照を、新しいノード（`n`、これは最終的な静的変数への参照になる）に置き換えます。
    -   代入（`OAS`）の左辺が一時変数であれば、それを新しいノードに置き換えます。
    -   構造体フィールドアクセス（`ODOT`）や配列要素アクセス（`OINDEX`）のベースが一時変数であれば、同様に置き換えます。
    -   `OCALL`（特に`mapassign1`）の場合、その引数リスト内の一時変数への参照も置き換えます。
    -   置き換えが成功した場合、元の代入ノードは`OEMPTY`（空のステートメント）に変換され、最終的なコード生成から除外されます。

-   **`initfix`関数**:
    `fninit`（関数の初期化処理）から呼び出される主要な関数です。
    1.  `initlin`を呼び出して、初期化に関連するノードを`xxx`リストに収集します。
    2.  `xxx`リストを逆順にします（`rev(xxx)`）。これは、依存関係のある初期化が正しい順序で処理されるようにするためと考えられます。
    3.  `xxx`リストを走査し、`OAS`ノードで右辺が一時変数であるものを見つけます。
    4.  そのような代入が見つかった場合、`initsub`を呼び出して、その一時変数へのすべての参照を代入の左辺（これは最終的に静的変数になる）に置き換えます。
    5.  置き換えが成功した場合、元の代入ノードは`OEMPTY`に設定されます。
    このプロセスにより、自動変数として一時的に初期化されていた複合リテラルが、最終的に静的変数への直接的な初期化として扱われるようにASTが変換されます。

### 複合リテラルの処理変更

`src/cmd/gc/walk.c`では、複合リテラル（`OCOMPOS`）の処理が変更されています。
-   以前は、`&Point(1, 2)`のような複合リテラルがヒープアロケーションと代入として処理されていました。
-   このコミットでは、`OCOMPOS`ノードが静的初期化の対象となる場合、`initfix`によってASTが変換され、`new`呼び出しとそれに続く代入が、最終的にDATAステートメントとして処理されるようにパスが調整されます。
-   `arraylit`関数も変更され、配列リテラルの初期化が`walktype(a, Etop)`を通じて`addtop`リストに追加されるようになりました。これにより、初期化の代入がトップレベルのステートメントとして扱われ、`initfix`による変換の対象となります。

これらの変更により、コンパイラは構造体や配列の複合リテラルが静的変数に割り当てられる際に、その初期化を効率的なDATAステートメントとして出力できるようになります。

## コアとなるコードの解説

このコミットの核となるのは、Goコンパイラが静的初期化を処理する方法を根本的に変更した点です。

1.  **`initflag`による静的初期化パスの制御**:
    `src/cmd/6g/cgen.c`の変更は、`gen_as_init`関数が静的初期化のコンテキストでのみ実行されるようにするためのガードです。これにより、通常の実行時初期化と静的初期化のロジックが混在することを防ぎ、コンパイラの動作を明確に分離します。

2.  **`stataddr`と`gen_as_init`によるDATAステートメント生成**:
    `src/cmd/6g/gen.c`に追加された`stataddr`関数は、コンパイラがASTを走査する際に、どの変数が静的にアドレス指定可能であるかを効率的に判断できるようにします。これは、グローバル変数やパッケージレベルの変数、およびそれらの構造体フィールドや配列要素へのアクセスを識別するために重要です。
    拡張された`gen_as_init`関数は、`stataddr`によって静的アドレスと識別された変数へのリテラル値の代入を検出し、それをアセンブリの`ADATA`命令（DATAステートメント）として直接出力します。これにより、実行時に代入命令を実行する代わりに、プログラムのロード時にデータがメモリに配置されるようになります。これは、特に大きな構造体や配列の初期化において、起動時間の短縮とコードサイズの削減に貢献します。

3.  **`dcl.c`におけるAST変換の複雑なロジック**:
    `src/cmd/gc/dcl.c`に追加された`initlin`, `inittmp`, `sametmp`, `indsametmp`, `initsub`, `initfix`の各関数は、このコミットの最も技術的に複雑な部分です。
    -   Goの複合リテラル（例: `Point{1, 2}`）は、コンパイラによって一時変数への一連の代入として内部的に表現されることがあります。
    -   `initfix`は、これらの「一時変数への代入」を検出し、その一時変数へのすべての参照を、最終的に静的初期化されるべき変数への参照に「書き換え」ます。
    -   例えば、`var p = Point{1, 2}`というコードがあった場合、コンパイラは内部的に`tmp := new(Point); tmp.x = 1; tmp.y = 2; p = *tmp`のような中間コードを生成するかもしれません。`initfix`は、この`tmp`への参照を`p`への参照に置き換え、`p.x = 1; p.y = 2`のような形に変換します。
    -   さらに、この変換が成功した場合、元の代入ノードは`OEMPTY`（空のステートメント）にマークされ、通常のコード生成パスからは除外されます。これにより、`gen_as_init`がこれらの初期化をDATAステートメントとして処理できるようになります。
    この変換は、コンパイラが生成する中間コードの構造に深く依存しており、コミットメッセージにある「it is extremely fragile knowing exactly how the code from (struct|array|map)lit will look」というコメントがその複雑さを示唆しています。

4.  **`walk.c`における複合リテラル処理の調整**:
    `src/cmd/gc/walk.c`の変更は、複合リテラルがAST上でどのように表現され、処理されるかを調整します。特に、`&Point(1, 2)`のようなポインタへの複合リテラル初期化が、ヒープアロケーションと代入の組み合わせから、静的初期化のパスに適切に誘導されるように変更されています。`walktype(a, Etop)`の追加は、初期化の代入がトップレベルのステートメントとして扱われ、`initfix`による変換の対象となるための重要なステップです。

これらの変更が連携することで、Goコンパイラは構造体と配列の静的初期化を、より効率的なDATAステートメントとして生成できるようになり、Goプログラムの実行効率が向上します。

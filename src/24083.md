## 変更の背景

Goコンパイラは、コードの最適化のためにSSA (Static Single Assignment) 形式の中間表現を使用しています。SSA形式では、プログラムの制御フローグラフ (CFG) 上で各変数が一度だけ代入されるように変換されます。このCFG上で、あるブロックが別のブロックの「ドミネーター」であるかどうかを判断することは、多くの最適化（例えば、共通部分式の削除、ループ不変コードの移動など）の基礎となります。

このコミットの主な背景は以下の2点です。

1.  **ドミネーター計算の正確性の保証**: ドミネーター計算はコンパイラの重要な部分であり、その正確性は生成されるコードの正しさに直結します。そのため、様々な制御フローパターンに対応する堅牢なテストケースが必要でした。
2.  **ドミネーター計算の性能改善**: 大規模なプログラムや複雑な制御フローを持つ関数では、ドミネーター計算がコンパイル時間のボトルネックになる可能性があります。特に、ドミネーターツリーの構築において頻繁に呼び出される`intersect()`のような操作の効率が重要です。このコミットでは、メモリ割り当ての最適化を通じてこの性能を改善することを目指しました。

コミットメッセージに記載されているベンチマーク結果は、特に大規模なグラフにおいて顕著な性能向上が見られることを示しており、この変更がコンパイラの全体的な効率に貢献することを示唆しています。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの中間表現（IR）の一種で、各変数がプログラム内で一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、多くの最適化が容易になります。

-   **利点**:
    *   データフロー解析の精度向上。
    *   共通部分式の削除、デッドコード削除、レジスタ割り当てなどの最適化が容易になる。
-   **制御フローグラフ (CFG)**: プログラムの実行パスをノード（基本ブロック）とエッジ（制御フロー）で表現したグラフ。SSA形式はCFG上で定義されます。

### 2. ドミネーター (Dominator) とドミネーターツリー

制御フローグラフ (CFG) において、あるブロック `A` がブロック `B` の**ドミネーター**であるとは、`entry` ブロックから `B` へのすべてのパスが `A` を通過する場合を言います。つまり、`B` が実行される前に必ず `A` が実行されるということです。

-   **Immediate Dominator (直接ドミネーター)**: `B` をドミネートするブロック `A` の中で、`B` に最も近い（`A` と `B` の間に他のドミネーターが存在しない）ブロックを `B` の直接ドミネーターと呼びます。
-   **ドミネーターツリー**: 各ブロックとその直接ドミネーターの関係をツリー構造で表現したものです。`entry` ブロックがツリーの根となります。ドミネーターツリーは、ループ検出、到達可能性解析、最適化のスコープ決定など、多くのコンパイラ最適化で利用されます。
-   **`intersect()` 操作**: ドミネーターツリーの構築アルゴリズム（例えば、Lengauer-TarjanアルゴリズムやCooper-Harvey-Kennedyアルゴリズムなど）では、複数のパスが合流する地点でドミネーターの共通部分（intersection）を効率的に計算する必要があります。この操作の性能が全体のドミネーター計算のボトルネックになることがあります。

### 3. Goコンパイラの構造 (`cmd/compile/internal/ssa`)

Goコンパイラは、ソースコードを抽象構文木 (AST) にパースした後、中間表現に変換し、様々な最適化を適用してから最終的な機械語を生成します。`cmd/compile/internal/ssa` パッケージは、この中間表現としてSSA形式を扱い、SSAベースの最適化を行う部分です。

-   `Block`: SSA形式における基本ブロックを表します。命令のシーケンスと、後続のブロックへの制御フロー情報を含みます。
-   `Func`: Goの関数を表し、その関数内のすべての`Block`を含みます。
-   `dominators(f *Func)`: 特定の関数`f`のドミネーター情報を計算する関数です。

### 4. Goのベンチマーク (`testing` パッケージ)

Go言語には、標準ライブラリの`testing`パッケージにベンチマーク機能が組み込まれています。

-   `func BenchmarkXxx(b *testing.B)`: ベンチマーク関数は`Benchmark`で始まり、`*testing.B`型の引数を取ります。
-   `b.ResetTimer()`: ベンチマーク対象のコードの実行時間を計測する前にタイマーをリセットします。
-   `b.N`: ベンチマーク関数は`b.N`回実行され、`b.N`はベンチマークの実行時間に応じて自動的に調整されます。
-   `b.SetBytes(int64(size))`: 処理されたバイト数を設定することで、`ns/op`だけでなく`MB/s`などの指標も表示できます。

### 2. `blockPool`によるメモリ割り当ての最適化 (`func.go`)

最も重要な性能改善は、`src/cmd/compile/internal/ssa/func.go`における`blockPool`の導入と`NewBlock`関数の変更です。

-   **問題点**: 以前の`NewBlock`関数は、`Block`構造体をヒープ上に個別に割り当てていました。`Block`が多数生成される大規模な関数では、これによりメモリの断片化が発生し、特にドミネーター計算の`intersect()`関数のように、ブロックリストを頻繁に走査する操作でキャッシュミスが増加し、性能が低下する可能性がありました。
-   **解決策**: `blockPool`は、`Block`構造体を`blockSize`（このコミットでは100）単位で連続したメモリブロックとして事前に割り当てて保持します。`NewBlock`が呼び出されると、このプールから`Block`を一つ取得して再利用します。
    *   `blockPool`構造体:
        ```go
        type blockPool struct {
            blocks []Block
            mu     sync.Mutex
        }
        ```
        `blocks`スライスが連続した`Block`のチャンクを保持し、`mu`は並行アクセス時の安全性を保証するためのミューテックスです。
    *   `newBlock()`メソッド:
        ```go
        func (bp *blockPool) newBlock() *Block {
            bp.mu.Lock()
            defer bp.mu.Unlock()

            if len(bp.blocks) <= 0 {
                bp.blocks = make([]Block, blockSize, blockSize)
            }

            res := &bp.blocks[0]
            bp.blocks = bp.blocks[1:]
            return res
        }
        ```
        このメソッドは、プールが空の場合に新しい`blockSize`分の`Block`を割り当て、プールの先頭から`Block`を一つ取り出して返します。これにより、`Block`がヒープ上に散らばることなく、連続したメモリ領域に配置される可能性が高まります。
-   **性能への影響**: `Block`が連続したメモリに配置されることで、CPUのキャッシュ効率が向上します。`intersect()`関数がブロックリストを走査する際に、必要なデータがキャッシュラインにヒットしやすくなり、メモリアクセスのレイテンシが大幅に削減されます。コミットメッセージのベンチマーク結果が示すように、これにより特に大規模なグラフでのドミネーター計算の性能が30-40%改善されました。

// genLinear creates an array of blocks that succeed one another
// b_n -> [b_n+1].
func genLinear(size int) []bloc {
	var blocs []bloc
	blocs = append(blocs,
		Bloc("entry",
			Valu("mem", OpArg, TypeMem, 0, ".mem"),
			Goto(blockn(0)),
		),
	)
	for i := 0; i < size; i++ {
		blocs = append(blocs, Bloc(blockn(i),
			Goto(blockn(i+1))))
	}

	blocs = append(blocs,
		Bloc(blockn(size), Goto("exit")),
		Bloc("exit", Exit("mem")),
	)

	return blocs
}

// genLinear creates an array of blocks that alternate between
// b_n -> [b_n+1], b_n -> [b_n+1, b_n-1] , b_n -> [b_n+1, b_n+2]
func genFwdBack(size int) []bloc {
	var blocs []bloc
	blocs = append(blocs,
		Bloc("entry",
			Valu("mem", OpArg, TypeMem, 0, ".mem"),
			Valu("p", OpConst, TypeBool, 0, true),
			Goto(blockn(0)),
		),
	)
	for i := 0; i < size; i++ {
		switch i % 2 {
		case 0:

		case 1:
			blocs = append(blocs, Bloc(blockn(i),
				If("p", blockn(i+1), blockn(i-1))))
		}
	}

		Bloc(blockn(size), Goto("exit")),
		Bloc("exit", Exit("mem")),
	)

	return blocs
}

// genManyPred creates an array of blocks where 1/3rd have a sucessor of the
// first block, 1/3rd the last block, and the remaining third are plain.
func genManyPred(size int) []bloc {
	var blocs []bloc
	blocs = append(blocs,
		Bloc("entry",
			Valu("mem", OpArg, TypeMem, 0, ".mem"),
			Valu("p", OpConst, TypeBool, 0, true),
			Goto(blockn(0)),
		),
	)

	// We want predecessor lists to be long, so 2/3rds of the blocks have a
	// sucessor of the first or last block.
	for i := 0; i < size; i++ {
		switch i % 3 {
		case 0:
			blocs = append(blocs, Bloc(blockn(i),
				Valu("a", OpConst, TypeBool, 0, true),
				Goto(blockn(i+1))))
		case 1:
			blocs = append(blocs, Bloc(blockn(i),
				Valu("a", OpConst, TypeBool, 0, true),
				If("p", blockn(i+1), blockn(0))))
		case 2:
			blocs = append(blocs, Bloc(blockn(i),
				Valu("a", OpConst, TypeBool, 0, true),
				If("p", blockn(i+1), blockn(size))))
		}
	}

	blocs = append(blocs,
		Bloc(blockn(size), Goto("exit")),
		Bloc("exit", Exit("mem")),
	)

	return blocs
}

func verifyDominators(t *testing.T, f fun, doms map[string]string) {
	blockNames := map[*Block]string{}
	for n, b := range f.blocks {
		blockNames[b] = n
	}

	calcDom := dominators(f.f)

	for n, d := range doms {
		nblk, ok := f.blocks[n]
		if !ok {
			t.Errorf("invalid block name %s", n)
		}
		dblk, ok := f.blocks[d]
		if !ok {
			t.Errorf("invalid block name %s", d)
		}

		domNode := calcDom[nblk.ID]
		switch {
		case calcDom[nblk.ID] == dblk:
			calcDom[nblk.ID] = nil
			continue
		case calcDom[nblk.ID] != dblk:
			t.Errorf("expected %s as dominator of %s, found %s", d, n, blockNames[domNode])
		default:
			t.Fatal("unexpected dominator condition")
		}
	}

	for id, d := range calcDom {
		// If nil, we've already verified it
		if d == nil {
			continue
		}
		for _, b := range f.blocks {
			if int(b.ID) == id {
				t.Errorf("unexpected dominator of %s for %s", blockNames[d], blockNames[b])
			}
		}
	}

}

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの中間表現（IR）の一種で、各変数がプログラム内で一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、多くの最適化が容易になります。

-   **利点**:
    *   データフロー解析の精度向上。
    *   共通部分式の削除、デッドコード削除、レジスタ割り当てなどの最適化が容易になる。
-   **制御フローグラフ (CFG)**: プログラムの実行パスをノード（基本ブロック）とエッジ（制御フロー）で表現したグラフ。SSA形式はCFG上で定義されます。

### 2. ドミネーター (Dominator) とドミネーターツリー

制御フローグラフ (CFG) において、あるブロック `A` がブロック `B` の**ドミネーター**であるとは、`entry` ブロックから `B` へのすべてのパスが `A` を通過する場合を言います。つまり、`B` が実行される前に必ず `A` が実行されるということです。

-   **Immediate Dominator (直接ドミネーター)**: `B` をドミネートするブロック `A` の中で、`B` に最も近い（`A` と `B` の間に他のドミネーターが存在しない）ブロックを `B` の直接ドミネーターと呼びます。
-   **ドミネーターツリー**: 各ブロックとその直接ドミネーターの関係をツリー構造で表現したものです。`entry` ブロックがツリーの根となります。ドミネーターツリーは、ループ検出、到達可能性解析、最適化のスコープ決定など、多くのコンパイラ最適化で利用されます。
-   **`intersect()` 操作**: ドミネーターツリーの構築アルゴリズム（例えば、Lengauer-TarjanアルゴリズムやCooper-Harvey-Kennedyアルゴリズムなど）では、複数のパスが合流する地点でドミネーターの共通部分（intersection）を効率的に計算する必要があります。この操作の性能が全体のドミネーター計算のボトルネックになることがあります。

### 3. Goコンパイラの構造 (`cmd/compile/internal/ssa`)

Goコンパイラは、ソースコードを抽象構文木 (AST) にパースした後、中間表現に変換し、様々な最適化を適用してから最終的な機械語を生成します。`cmd/compile/internal/ssa` パッケージは、この中間表現としてSSA形式を扱い、SSAベースの最適化を行う部分です。

-   `Block`: SSA形式における基本ブロックを表します。命令のシーケンスと、後続のブロックへの制御フロー情報を含みます。
-   `Func`: Goの関数を表し、その関数内のすべての`Block`を含みます。
-   `dominators(f *Func)`: 特定の関数`f`のドミネーター情報を計算する関数です。

### 4. Goのベンチマーク (`testing` パッケージ)

Go言語には、標準ライブラリの`testing`パッケージにベンチマーク機能が組み込まれています。

-   `func BenchmarkXxx(b *testing.B)`: ベンチマーク関数は`Benchmark`で始まり、`*testing.B`型の引数を取ります。
-   `b.ResetTimer()`: ベンチマーク対象のコードの実行時間を計測する前にタイマーをリセットします。
-   `b.N`: ベンチマーク関数は`b.N`回実行され、`b.N`はベンチマークの実行時間に応じて自動的に調整されます。

### 2. `blockPool`によるメモリ割り当ての最適化 (`func.go`)

最も重要な性能改善は、`src/cmd/compile/internal/ssa/func.go`における`blockPool`の導入と`NewBlock`関数の変更です。

-   **問題点**: 以前の`NewBlock`関数は、`Block`構造体をヒープ上に個別に割り当てていました。`Block`が多数生成される大規模な関数では、これによりメモリの断片化が発生し、特にドミネーター計算の`intersect()`関数のように、ブロックリストを頻繁に走査する操作でキャッシュミスが増加し、性能が低下する可能性がありました。
-   **解決策**: `blockPool`は、`Block`構造体を`blockSize`（このコミットでは100）単位で連続したメモリブロックとして事前に割り当てて保持します。`NewBlock`が呼び出されると、このプールから`Block`を一つ取得して再利用します。
    *   `blockPool`構造体:
        ```go
        type blockPool struct {
            blocks []Block
            mu     sync.Mutex
        }
        ```
        `blocks`スライスが連続した`Block`のチャンクを保持し、`mu`は並行アクセス時の安全性を保証するためのミューテックスです。
    *   `newBlock()`メソッド:
        ```go
        func (bp *blockPool) newBlock() *Block {
            bp.mu.Lock()
            defer bp.mu.Unlock()

            if len(bp.blocks) <= 0 {
                bp.blocks = make([]Block, blockSize, blockSize)
            }

            res := &bp.blocks[0]
            bp.blocks = bp.blocks[1:]
            return res
        }
        ```
        このメソッドは、プールが空の場合に新しい`blockSize`分の`Block`を割り当て、プールの先頭から`Block`を一つ取り出して返します。これにより、`Block`がヒープ上に散らばることなく、連続したメモリ領域に配置される可能性が高まります。
-   **性能への影響**: `Block`が連続したメモリに配置されることで、CPUのキャッシュ効率が向上します。`intersect()`関数がブロックリストを走査する際に、必要なデータがキャッシュラインにヒットしやすくなり、メモリアクセスのレイテンシが大幅に削減されます。コミットメッセージのベンチマーク結果が示すように、これにより特に大規模なグラフでのドミネーター計算の性能が30-40%改善されました。

		),

	for i := 0; i < size; i++ {
		switch i % 2 {
		case 0:
			blocs = append(blocs, Bloc(blockn(i),
				If("p", blockn(i+1), blockn(i+2))))
		case 1:
			blocs = append(blocs, Bloc(blockn(i),
				If("p", blockn(i+1), blockn(i-1))))
		}
	}

	blocs = append(blocs,
		Bloc(blockn(size), Goto("exit")),
		Bloc("exit", Exit("mem")),
	)

	return blocs
}

// genManyPred creates an array of blocks where 1/3rd have a sucessor of the
// first block, 1/3rd the last block, and the remaining third are plain.
func genManyPred(size int) []bloc {
	var blocs []bloc
	blocs = append(blocs,
		Bloc("entry",
			Valu("mem", OpArg, TypeMem, 0, ".mem"),
			Valu("p", OpConst, TypeBool, 0, true),
			Goto(blockn(0)),
		),
	)

	// We want predecessor lists to be long, so 2/3rds of the blocks have a
	// sucessor of the first or last block.
	for i := 0; i < size; i++ {
		switch i % 3 {
		case 0:
			blocs = append(blocs, Bloc(blockn(i),
				Valu("a", OpConst, TypeBool, 0, true),
				Goto(blockn(i+1))))
		case 1:
			blocs = append(blocs, Bloc(blockn(i),
				Valu("a", OpConst, TypeBool, 0, true),
				If("p", blockn(i+1), blockn(0))))
		case 2:
			blocs = append(blocs, Bloc(blockn(i),
				Valu("a", OpConst, TypeBool, 0, true),
				If("p", blockn(i+1), blockn(size))))
		}
	}

	blocs = append(blocs,
		Bloc(blockn(size), Goto("exit")),
		Bloc("exit", Exit("mem")),
	)

	return blocs
}

func verifyDominators(t *testing.T, f fun, doms map[string]string) {
	blockNames := map[*Block]string{}
	for n, b := range f.blocks {
		blockNames[b] = n
	}

	calcDom := dominators(f.f)

	for n, d := range doms {
		nblk, ok := f.blocks[n]
		if !ok {
			t.Errorf("invalid block name %s", n)
		}
		dblk, ok := f.blocks[d]
		if !ok {
			t.Errorf("invalid block name %s", d)
		}

		domNode := calcDom[nblk.ID]
		switch {
		case calcDom[nblk.ID] == dblk:
			calcDom[nblk.ID] = nil
			continue
		case calcDom[nblk.ID] != dblk:
			t.Errorf("expected %s as dominator of %s, found %s", d, n, blockNames[domNode])
		default:
			t.Fatal("unexpected dominator condition")
		}
	}

	for id, d := range calcDom {
		// If nil, we've already verified it
		if d == nil {
			continue
		}
		for _, b := range f.blocks {
			if int(b.ID) == id {
				t.Errorf("unexpected dominator of %s for %s", blockNames[d], blockNames[b])
			}
		}
	}

}

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/dom.go`

このファイルでは、`dominators`関数のコメントが削除されただけです。これは、以前のコミットで「ベンチマークを追加する必要がある」という趣旨のTODOコメントがありましたが、このコミットで実際にベンチマークが追加されたため、そのTODOが完了したことを示しています。機能的な変更はありません。

### `src/cmd/compile/internal/ssa/dom_test.go`

このファイルは新規追加され、ドミネーター計算の正確性と性能を検証するためのテストとベンチマークが定義されています。

-   **`benchmarkDominators`関数**:
    *   `b *testing.B`, `size int`, `bg blockGen` を引数にとります。
    *   `bg(size)` を呼び出して、指定された`size`の制御フローグラフを生成します。`blockGen`は、`genLinear`、`genFwdBack`などのグラフ生成関数への型エイリアスです。
    *   `b.ResetTimer()` でタイマーをリセットし、`dominators(fun.f)` の呼び出し時間を計測します。
    *   `b.SetBytes(int64(size))` は、処理されたブロックの数に基づいてベンチマーク結果を正規化するために使用されます。
-   **`verifyDominators`関数**:
    *   テストケースで使用されるヘルパー関数で、計算されたドミネーターが期待されるドミネーターと一致するかを検証します。
    *   `calcDom := dominators(f.f)` で実際のドミネーターを計算し、`doms`マップで与えられた期待値と比較します。
-   **`TestDominators*`関数**:
    *   `TestDominatorsSimple`, `TestDominatorsMultPredFwd`, `TestDominatorsMultPredRev`, `TestDominatorsMultPred` は、それぞれ異なる制御フローパターンを持つ小さなグラフに対して、`dominators`関数が正しい結果を返すことを確認する機能テストです。

### `src/cmd/compile/internal/ssa/func.go`

このファイルでは、`Block`構造体の割り当て方法が大きく変更されています。

-   **`blockPool`構造体と`bp`変数**:
    *   `blockPool`は、`Block`構造体のスライスとミューテックス`mu`を保持します。
    *   `var bp blockPool` でグローバルな`blockPool`インスタンスが宣言されています。これは、複数の関数が同時に`Block`を割り当てる可能性があるため、スレッドセーフティを確保するためにミューテックスが必要です。
-   **`newBlock()`メソッド**:
    *   `bp.mu.Lock()` と `defer bp.mu.Unlock()` により、このメソッドはスレッドセーフに動作します。
    *   `if len(bp.blocks) <= 0` の条件で、プールが空になった場合に`blockSize`（100）個の新しい`Block`をまとめて`make`で割り当てます。これにより、`Block`が連続したメモリ領域に確保されます。
    *   `res := &bp.blocks[0]` でプールの先頭の`Block`へのポインタを取得し、`bp.blocks = bp.blocks[1:]` でその`Block`をプールから取り除きます。
    *   この方法により、個々の`Block`の割り当てがヒープ上に散らばることなく、大きなチャンクとして割り当てられ、キャッシュ効率が向上します。
-   **`NewBlock`関数の変更**:
    *   以前は`b := &Block{...}`のように直接`Block`をヒープに割り当てていましたが、変更後は`b := bp.newBlock()`を呼び出して`blockPool`から`Block`を取得するように変わりました。
    *   取得した`Block`のフィールド（`ID`, `Kind`, `Func`）を設定し、`f.Blocks`スライスに追加します。

この変更により、`Block`オブジェクトがメモリ上でより密に配置されるようになり、ドミネーター計算のような`Block`リストを頻繁に走査するアルゴリズムにおいて、CPUキャッシュのヒット率が向上し、結果として実行速度が大幅に改善されました。

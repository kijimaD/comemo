## 元コミット内容

このコミットは、GoコンパイラのSSA (Static Single Assignment) 開発ブランチにおける変更です。具体的には、`cmd/compile`パッケージ内で、レジスタの値をスタックに保存したり、スタックからロードしたりする際に、スタックスロットの実際のデータ幅（サイズ）を考慮するように修正しています。この修正以前は、コンパイラが自身のスタックを破壊してしまう問題があり、その結果`crypto/sha256`パッケージのテストが失敗していました。

## 変更の背景

Goコンパイラは、プログラムをより効率的な中間表現に変換するためにSSA形式を使用します。SSA形式では、各変数が一度だけ代入されるため、最適化が容易になります。コンパイルプロセスの後半では、SSA形式のコードはターゲットアーキテクチャの機械語に変換され、この過程でレジスタ割り当てが行われます。

レジスタ割り当ての際、一時的にレジスタに保持できない値や、関数呼び出しを跨いで保持する必要がある値は、スタック上の「スピル（spill）スロット」と呼ばれる領域に保存されます。このコミット以前のGoコンパイラでは、レジスタの値をスタックに保存（`StoreReg8`）したり、スタックからロード（`LoadReg8`）したりする際に、常に8バイトのデータとして扱っていました。これは、x86-64アーキテクチャにおける一般的なレジスタ幅である64ビット（8バイト）を前提としたものでした。

しかし、Go言語には`int8`, `int16`, `int32`などの異なるサイズの整数型や、`bool`型など、8バイトよりも小さいデータ型が存在します。これらの小さなデータ型の値をレジスタからスタックに保存する際にも一律に8バイトの命令（`AMOVQ`）を使用すると、本来その値が占めるべきスタック領域を超えて、隣接するスタック上のデータまで上書きしてしまう（「スタック破壊」）問題が発生しました。

このスタック破壊は、特にメモリの厳密な管理が必要な`crypto/sha256`のようなパッケージで顕在化し、テストの失敗という形で報告されました。このコミットは、この問題を解決し、コンパイラが生成するコードの正確性と堅牢性を向上させることを目的としています。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSAは、コンパイラの中間表現（IR）の一種で、各変数がプログラム内で一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が非常に容易になります。Goコンパイラは、Goソースコードを抽象構文木（AST）に変換した後、SSA形式に変換し、様々な最適化を適用します。

### 2. Goコンパイラの構造 (`cmd/compile`)

`cmd/compile`はGo言語の公式コンパイラです。その内部は複数のステージに分かれており、主要なステージには以下が含まれます。
*   **フロントエンド**: ソースコードの字句解析、構文解析、抽象構文木（AST）の構築。
*   **ミドルエンド**: 型チェック、ASTの最適化、SSA形式への変換。
*   **バックエンド**: SSA形式の最適化、レジスタ割り当て、機械語コードの生成。

このコミットは、主にバックエンドのレジスタ割り当てと機械語コード生成のフェーズに関連しています。

### 3. レジスタ割り当て (Register Allocation)

CPUのレジスタは非常に高速な記憶領域ですが、その数は限られています。レジスタ割り当ては、プログラムの実行中にどの値をどのレジスタに保持するかを決定するプロセスです。レジスタが不足した場合、一部の値はメモリ（特にスタック）に一時的に保存されます。このメモリへの保存を「スピル（spill）」、メモリからの読み出しを「フィル（fill）」と呼びます。

### 4. スタックフレーム (Stack Frame)

関数が呼び出されると、その関数専用のスタックフレームがスタック上に作成されます。スタックフレームには、関数のローカル変数、引数、戻りアドレス、そしてレジスタスピル用の領域などが含まれます。

### 5. x86-64アセンブリ命令とデータサイズ

x86-64アーキテクチャでは、データをメモリとレジスタ間で移動させるための`MOV`命令が、扱うデータサイズに応じて複数存在します。
*   `MOVQ`: Quadword (8バイト) の移動。64ビットレジスタ全体を扱う場合に使用。
*   `MOVL`: Longword (4バイト) の移動。32ビットレジスタまたはメモリの4バイトを扱う場合に使用。
*   `MOVW`: Word (2バイト) の移動。16ビットレジスタまたはメモリの2バイトを扱う場合に使用。
*   `MOVB`: Byte (1バイト) の移動。8ビットレジスタまたはメモリの1バイトを扱う場合に使用。

これらの命令は、データのサイズに合わせて適切に使い分ける必要があります。誤ったサイズの命令を使用すると、意図しないメモリ領域を読み書きしてしまい、プログラムの誤動作やクラッシュにつながります。

## 技術的詳細

このコミットの核心は、レジスタのスピル/フィル操作において、固定の8バイト移動（`AMOVQ`）ではなく、対象となる値の実際のデータ型サイズに応じた`MOV`命令を使用するように変更した点です。

以前は、`ssa.OpLoadReg8`と`ssa.OpStoreReg8`というSSA操作が定義されており、これらは名前が示す通り、常に8バイトのデータを扱うことを前提としていました。`src/cmd/compile/internal/gc/ssa.go`内の`genValue`関数は、これらのSSA操作をx86-64アセンブリ命令に変換する役割を担っていましたが、ここでも常に`x86.AMOVQ`（8バイト移動）が使用されていました。

この変更では、以下のステップが取られました。

1.  **汎用的なSSA操作への変更**: `ssa.OpLoadReg8`と`ssa.OpStoreReg8`を、サイズ情報を含まない汎用的な`ssa.OpLoadReg`と`ssa.OpStoreReg`にリネームしました。これにより、SSA操作自体が特定のサイズに縛られなくなります。
2.  **`movSize`関数の導入**: `src/cmd/compile/internal/gc/ssa.go`に`movSize`という新しいヘルパー関数が導入されました。この関数は、与えられたデータ幅（バイト数）に基づいて、対応するx86アセンブリの`MOV`命令（`x86.AMOVB`, `x86.AMOVW`, `x86.AMOVL`, `x86.AMOVQ`）を返します。
3.  **`genValue`関数の修正**: `genValue`関数内で`ssa.OpLoadReg`および`ssa.OpStoreReg`を処理する際に、対象となる`ssa.Value`の型情報からサイズを取得し、そのサイズを`movSize`関数に渡して適切な`MOV`命令を取得するように変更されました。具体的には、`v.Type.Size()`を呼び出して値のサイズを取得しています。

この修正により、例えば`int16`型の値をスタックに保存する際には`MOVW`命令が、`int32`型であれば`MOVL`命令が生成されるようになり、スタック破壊の問題が解消されました。

### `genValue` 関数の変更

`genValue`関数は、SSAの`Value`オブジェクトを受け取り、それに対応するアセンブリ命令を生成します。このコミットでは、`ssa.OpLoadReg8`と`ssa.OpStoreReg8`のケースが`ssa.OpLoadReg`と`ssa.OpStoreReg`に変更されました。

変更前:
```go
	case ssa.OpLoadReg8:
		// ...
		p := Prog(x86.AMOVQ) // 常に8バイト移動
		// ...
	case ssa.OpStoreReg8:
		// ...
		p := Prog(x86.AMOVQ) // 常に8バイト移動
		// ...
```

変更後:
```go
	case ssa.OpLoadReg:
		// ...
		p := Prog(movSize(v.Type.Size())) // 値のサイズに応じてMOV命令を選択
		// ...
	case ssa.OpStoreReg:
		// ...
		p := Prog(movSize(v.Type.Size())) // 値のサイズに応じてMOV命令を選択
		// ...
```

ここで重要なのは、`Prog(movSize(v.Type.Size()))`という部分です。`v.Type.Size()`は、現在処理しているSSA値`v`のデータ型が占めるバイト数を返します。このサイズ情報が新しく導入された`movSize`関数に渡され、適切な`MOV`命令（`AMOVB`, `AMOVW`, `AMOVL`, `AMOVQ`のいずれか）が選択されるようになりました。これにより、スタックへの読み書きが、対象のデータ型に正確なサイズで行われるようになります。

### `movSize` 関数の追加

`movSize`関数は、与えられた`width`（バイト数）に基づいて、対応するx86アセンブリの`MOV`命令のオペコードを返します。

```go
func movSize(width int64) (asm int) {
	switch width {
	case 1:
		asm = x86.AMOVB // 1バイト (Byte)
	case 2:
		asm = x86.AMOVW // 2バイト (Word)
	case 4:
		asm = x86.AMOVL // 4バイト (Longword)
	case 8:
		asm = x86.AMOVQ // 8バイト (Quadword)
	default:
		panic(fmt.Errorf("bad movSize %d", width)) // 未対応のサイズはパニック
	}
	return asm
}
```

この関数は、`width`が1, 2, 4, 8のいずれかである場合に、それぞれ`AMOVB`, `AMOVW`, `AMOVL`, `AMOVQ`を返します。これにより、コンパイラはGoの異なるサイズのデータ型（例: `byte`, `int16`, `int32`, `int64`）に対応する正確なアセンブリ命令を生成できるようになりました。もし未対応のサイズが渡された場合は、コンパイラのバグとしてパニックを発生させます。

*   `MOVB`: Byte (1バイト) の移動。8ビットレジスタまたはメモリの1バイトを扱う場合に使用。

これらの命令は、データのサイズに合わせて適切に使い分ける必要があります。誤ったサイズの命令を使用すると、意図しないメモリ領域を読み書きしてしまい、プログラムの誤動作やクラッシュにつながります。

## 技術的詳細

このコミットの核心は、レジスタのスピル/フィル操作において、固定の8バイト移動（`AMOVQ`）ではなく、対象となる値の実際のデータ型サイズに応じた`MOV`命令を使用するように変更した点です。

以前は、`ssa.OpLoadReg8`と`ssa.OpStoreReg8`というSSA操作が定義されており、これらは名前が示す通り、常に8バイトのデータを扱うことを前提としていました。`src/cmd/compile/internal/gc/ssa.go`内の`genValue`関数は、これらのSSA操作をx86-64アセンブリ命令に変換する役割を担っていましたが、ここでも常に`x86.AMOVQ`（8バイト移動）が使用されていました。

この変更では、以下のステップが取られました。

1.  **汎用的なSSA操作への変更**: `ssa.OpLoadReg8`と`ssa.OpStoreReg8`を、サイズ情報を含まない汎用的な`ssa.OpLoadReg`と`ssa.OpStoreReg`にリネームしました。これにより、SSA操作自体が特定のサイズに縛られなくなります。
2.  **`movSize`関数の導入**: `src/cmd/compile/internal/gc/ssa.go`に`movSize`という新しいヘルパー関数が導入されました。この関数は、与えられたデータ幅（バイト数）に基づいて、対応するx86アセンブリの`MOV`命令（`x86.AMOVB`, `x86.AMOVW`, `x86.AMOVL`, `x86.AMOVQ`）を返します。
3.  **`genValue`関数の修正**: `genValue`関数内で`ssa.OpLoadReg`および`ssa.OpStoreReg`を処理する際に、対象となる`ssa.Value`の型情報からサイズを取得し、そのサイズを`movSize`関数に渡して適切な`MOV`命令を取得するように変更されました。具体的には、`v.Type.Size()`を呼び出して値のサイズを取得しています。

この修正により、例えば`int16`型の値をスタックに保存する際には`MOVW`命令が、`int32`型であれば`MOVL`命令が生成されるようになり、スタック破壊の問題が解消されました。

## コアとなるコードの解説

### `genValue` 関数の変更

`genValue`関数は、SSAの`Value`オブジェクトを受け取り、それに対応するアセンブリ命令を生成します。このコミットでは、`ssa.OpLoadReg8`と`ssa.OpStoreReg8`のケースが`ssa.OpLoadReg`と`ssa.OpStoreReg`に変更されました。

変更前:
```go
	case ssa.OpLoadReg8:
		// ...
		p := Prog(x86.AMOVQ) // 常に8バイト移動
		// ...
	case ssa.OpStoreReg8:
		// ...
		p := Prog(x86.AMOVQ) // 常に8バイト移動
		// ...
```

変更後:
```go
	case ssa.OpLoadReg:
		// ...
		p := Prog(movSize(v.Type.Size())) // 値のサイズに応じてMOV命令を選択
		// ...
	case ssa.OpStoreReg:
		// ...
		p := Prog(movSize(v.Type.Size())) // 値のサイズに応じてMOV命令を選択
		// ...
```

ここで重要なのは、`Prog(movSize(v.Type.Size()))`という部分です。`v.Type.Size()`は、現在処理しているSSA値`v`のデータ型が占めるバイト数を返します。このサイズ情報が新しく導入された`movSize`関数に渡され、適切な`MOV`命令（`AMOVB`, `AMOVW`, `AMOVL`, `AMOVQ`のいずれか）が選択されるようになりました。これにより、スタックへの読み書きが、対象のデータ型に正確なサイズで行われるようになります。

### `movSize` 関数の追加

`movSize`関数は、与えられた`width`（バイト数）に基づいて、対応するx86アセンブリの`MOV`命令のオペコードを返します。

```go
func movSize(width int64) (asm int) {
	switch width {
	case 1:
		asm = x86.AMOVB // 1バイト (Byte)
	case 2:
		asm = x86.AMOVW // 2バイト (Word)
	case 4:
		asm = x86.AMOVL // 4バイト (Longword)
	case 8:
		asm = x86.AMOVQ // 8バイト (Quadword)
	default:
		panic(fmt.Errorf("bad movSize %d", width)) // 未対応のサイズはパニック
	}
	return asm
}
```

この関数は、`width`が1, 2, 4, 8のいずれかである場合に、それぞれ`AMOVB`, `AMOVW`, `AMOVL`, `AMOVQ`を返します。これにより、コンパイラはGoの異なるサイズのデータ型（例: `byte`, `int16`, `int32`, `int64`）に対応する正確なアセンブリ命令を生成できるようになりました。もし未対応のサイズが渡された場合は、コンパイラのバグとしてパニックを発生させます。

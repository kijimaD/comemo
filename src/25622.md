# [インデックス 25622] ファイルの概要

このコミットは、Goランタイムにおけるシステム、アーキテクチャ、および設定に特化した定数を、新しく導入された内部パッケージ `runtime/internal/sys` へと分離する大規模なリファクタリングです。これにより、ランタイムコードのモジュール性が向上し、異なるプラットフォームやアーキテクチャ間での定数の管理がより体系的になります。

## 元コミット内容

Goランタイムのシステム固有の定数を `sys` パッケージに分離する。

`runtime/internal/sys` は、システム、アーキテクチャ、および設定に特化した定数を保持する。

Issue #11647 を更新。

## 変更の背景

Go言語のランタイムは、様々なオペレーティングシステム（OS）やCPUアーキテクチャをサポートしています。これに伴い、ポインタのサイズ（`ptrSize`）、キャッシュラインサイズ（`_CacheLineSize`）、物理ページサイズ（`_PhysPageSize`）、エンディアン（`_BigEndian`）など、OSやアーキテクチャに依存する多くの定数が存在します。

以前は、これらの定数が`runtime`パッケージ内の複数のファイルに散在しており、特に`runtime/arch_*.go`や`runtime/zgoos_*.go`といったファイルで定義されていました。このアプローチは、以下のような問題を引き起こしていました。

1.  **コードの重複と保守性の低下**: 各アーキテクチャやOSごとに同じような定数定義が繰り返され、変更が必要になった場合に複数のファイルを修正する必要がありました。
2.  **依存関係の複雑化**: `runtime`パッケージ内の様々なコンポーネントがこれらの定数に直接依存しており、定数の定義場所が不明瞭になることがありました。
3.  **明確な責任範囲の欠如**: システム固有の定数が`runtime`パッケージの広範な部分に混在しているため、どの定数がどのレイヤーに属するのかが分かりにくくなっていました。

このコミットは、これらの問題を解決するために、システム固有の定数を一元的に管理する`runtime/internal/sys`という新しい内部パッケージを導入することを目的としています。これにより、ランタイムコードの構造が整理され、保守性と拡張性が向上します。Issue #11647は、このリファクタリングの必要性を示唆していたと考えられます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびシステムプログラミングに関する知識が役立ちます。

1.  **Goランタイム**: Goプログラムの実行を管理する低レベルのコンポーネント群です。ガベージコレクション、スケジューリング、メモリ管理、システムコールなどが含まれます。ランタイムはGo言語で書かれていますが、一部アセンブリ言語も使用されます。
2.  **クロスコンパイルとビルドタグ**: Goは異なるOSやアーキテクチャ向けに簡単にコンパイルできるクロスコンパイル機能を強力にサポートしています。`// +build`ディレクティブ（現在は`//go:build`）は、特定のOSやアーキテクチャでのみコンパイルされるファイルを指定するために使用されます。例えば、`// +build linux,amd64`はLinux AMD64環境でのみ有効なコードを示します。
3.  **内部パッケージ (`internal`)**: Goのパッケージシステムでは、`internal`ディレクトリ内のパッケージは、その親ディレクトリのパッケージからのみインポート可能です。`runtime/internal/sys`の場合、`runtime`パッケージ内からのみ`sys`パッケージをインポートできます。これにより、内部実装の詳細が外部に漏れるのを防ぎ、APIの安定性を保ちます。
4.  **システム固有の定数**:
    *   **`ptrSize`**: ポインタのサイズ（バイト単位）。32ビットシステムでは4バイト、64ビットシステムでは8バイトです。
    *   **`_CacheLineSize`**: CPUのキャッシュラインのサイズ。メモリのアクセスパターンを最適化するために重要です。
    *   **`_PhysPageSize`**: オペレーティングシステムが管理する物理メモリページのサイズ。メモリ管理やアロケータの設計に影響します。
    *   **`_BigEndian`**: バイトオーダー（エンディアン）を示すフラグ。ビッグエンディアンの場合は1、リトルエンディアンの場合は0です。
    *   **`GOOS` / `GOARCH`**: GoのビルドターゲットとなるOSとアーキテクチャを示す環境変数、およびそれに対応するランタイム定数。
5.  **`unsafe.Pointer`**: Goの型安全性をバイパスして、任意の型へのポインタとして扱える特殊な型です。低レベルのメモリ操作や、C言語との相互運用などで使用されます。ランタイムコードでは頻繁に利用されます。
6.  **`go generate`**: Goのツールチェーンの一部で、ソースコードを生成するためのコマンドを実行するために使用されます。このコミットでは、`gengoos.go`スクリプトが`go generate`によって実行され、OSやアーキテクチャ固有の定数ファイル（`zgoos_*.go`, `zgoarch_*.go`）を生成しています。

## 技術的詳細

このコミットの核となる技術的変更は、GoランタイムがOSやアーキテクチャに依存する定数をどのように管理するかという点にあります。

1.  **`runtime/internal/sys` パッケージの導入**:
    *   `src/runtime/internal/sys`という新しいディレクトリが作成され、この中に`sys.go`、`stubs.go`、`gengoos.go`、そして各アーキテクチャ・OSごとのファイルが配置されます。
    *   `sys.go`は`sys`パッケージのルートとなり、`go:generate`ディレクティブを含んでいます。これは`gengoos.go`を実行して、OSやアーキテクチャ固有の定数ファイルを生成する役割を担います。
    *   `stubs.go`には、`PtrSize`、`RegSize`、`SpAlign`といった基本的なシステム定数が定義されています。これらの定数は、`unsafe.Sizeof`を使ってコンパイル時に決定される値を持つように工夫されています。
2.  **アーキテクチャ・OS固有の定数の移動**:
    *   以前`src/runtime/arch_*.go`（例: `arch_386.go`, `arch_amd64.go`）に直接定義されていた`thechar`, `_BigEndian`, `_CacheLineSize`, `_PhysPageSize`などの定数が、対応する`src/runtime/internal/sys/arch_*.go`ファイルに移動されました。
    *   同様に、`src/runtime/zgoos_*.go`（例: `zgoos_linux.go`）や`src/runtime/zgoarch_*.go`に定義されていた`theGoos`, `theGoarch`などの定数も、`src/runtime/internal/sys/zgoos_*.go`や`src/runtime/internal/sys/zgoarch_*.go`に移動されました。
    *   これらのファイルは`gengoos.go`スクリプトによって自動生成されるため、定数の命名規則も`goos_linux`から`GoosLinux`のように変更され、よりGoの命名規約に沿うようになりました。
3.  **`runtime`パッケージ内の参照の更新**:
    *   `runtime`パッケージ内の様々なファイル（`alg.go`, `cgocall.go`, `export_test.go`, `extern.go`, `hashmap.go`, `heapdump.go`, `iface.go`, `malloc.go`, `mbarrier.go`, `mbitmap.go`など）で、以前は`runtime`パッケージ内で直接定義されていたり、グローバルにアクセス可能だったシステム定数への参照が、`runtime/internal/sys`パッケージからのインポートと、`sys.PtrSize`、`sys.TheGoos`などの形式でのアクセスに更新されました。
    *   これにより、`runtime`パッケージの各ファイルは、システム固有の定数が必要な場合にのみ`runtime/internal/sys`をインポートするようになり、依存関係が明確化されました。
4.  **ビルドシステムの変更**:
    *   `src/cmd/dist/build.go`や`src/cmd/dist/deps.go`といったビルド関連のファイルも、`runtime/internal/sys`パッケージの導入に合わせて依存関係が更新されています。特に`mkzversion`関数は、`zversion.go`を`runtime`パッケージではなく`sys`パッケージ向けに生成するように変更されました。

このリファクタリングは、Goランタイムの内部構造をより整理し、将来的なメンテナンスや新しいプラットフォームへの対応を容易にすることを目的としています。`internal`パッケージを使用することで、これらの低レベルな定数がランタイムの他の部分から適切にカプセル化され、意図しない外部からの利用を防ぐことができます。

## コアとなるコードの解説

このコミットの核心は、Goランタイムがプラットフォーム固有の定数をどのように扱うかを根本的に変更した点にあります。

以前は、`runtime`パッケージの様々なファイル（例: `arch_amd64.go`, `zgoos_linux.go`）に、そのプラットフォームに特化した定数が直接定義されていました。例えば、`ptrSize`（ポインタのサイズ）や`_PhysPageSize`（物理ページサイズ）などがこれに該当します。これらの定数は、ランタイムのメモリ管理、スケジューリング、CGO（C言語との相互運用）など、多くの低レベルな処理で利用されていました。

このアプローチの問題点は、定数が散在しているため、一貫性の維持が難しく、新しいプラットフォームのサポートを追加する際に多くのファイルを変更する必要があることでした。また、`runtime`パッケージの他の部分がこれらの定数に直接依存することで、コードの結合度が高まっていました。

このコミットでは、`runtime/internal/sys`という新しい内部パッケージを導入することで、これらの問題を解決しています。

1.  **一元化された定数管理**:
    *   `runtime/internal/sys`パッケージは、システム、アーキテクチャ、および設定に特化したすべての定数を集約する場所として機能します。
    *   `src/runtime/internal/sys/stubs.go`では、`PtrSize`のような基本的な定数が定義されています。`PtrSize`の定義`4 << (^uintptr(0) >> 63)`は、`uintptr`のビット数に基づいてポインタサイズをコンパイル時に決定する巧妙な方法です。64ビットシステムでは`^uintptr(0) >> 63`が1となり`4 << 1 = 8`、32ビットシステムでは`^uintptr(0) >> 63`が0となり`4 << 0 = 4`となります。
    *   各アーキテクチャ（例: `arch_amd64.go`）やOS（例: `zgoos_linux.go`）固有の定数も、対応する`sys`パッケージ内のファイルに移動されました。これにより、特定のプラットフォームの定数を変更する際には、`sys`パッケージ内の関連ファイルのみを修正すればよくなります。

2.  **`go generate`による自動生成**:
    *   `src/runtime/internal/sys/sys.go`に含まれる`//go:generate go run gengoos.go`ディレクティブは、`gengoos.go`スクリプトを実行して、`zgoos_*.go`や`zgoarch_*.go`といったファイルを自動生成します。これらのファイルには、現在のビルドターゲットのOSやアーキテクチャを示す定数（例: `GoosLinux = 1`, `GoarchAmd64 = 1`）が含まれます。これにより、手動での定数管理の手間が省かれ、エラーのリスクが低減されます。

3.  **依存関係の明確化**:
    *   `runtime`パッケージ内の他のファイルは、システム固有の定数が必要な場合、`import "runtime/internal/sys"`を宣言し、`sys.PtrSize`のように明示的に`sys`パッケージから定数を参照するようになりました。これにより、どの定数がシステム固有のものであるかがコード上で明確になり、`runtime`パッケージの各コンポーネントの責任範囲がより明確になります。

この変更は、Goランタイムの内部構造をよりクリーンでモジュール化されたものにし、長期的な保守性と拡張性を高める上で非常に重要なステップです。

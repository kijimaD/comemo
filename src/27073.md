# [インデックス 27073] ファイルの概要

## コミット

このコミットは、Goコンパイラの内部コードにおける関数型のレシーバ（メソッドの対象となる型）を扱うための命名規則の変更と、それに伴うコードベース全体の修正を目的としています。具体的には、`Recv` という名前の関数が複数のレシーバ（Go言語の仕様上、メソッドのレシーバは常に一つですが、コンパイラ内部ではリストとして扱われることがあります）を指すために使われていたのを `Recvs` に変更し、`Recv0` という名前の関数が単一のレシーバを指すために使われていたのを `Recv` に変更しています。これにより、命名の意図がより明確になり、コードの可読性と保守性が向上します。

## 変更の背景

この変更の背景には、Goコンパイラ（`cmd/compile`）の内部で関数型（`Type` 構造体）のレシーバ情報を扱う際の命名の曖昧さがありました。Go言語のメソッドは常に単一のレシーバを持ちますが、コンパイラの内部実装では、レシーバも関数パラメータや戻り値と同様に「フィールドのリスト」として表現されることがあります。

変更前は、以下の2つの関数が存在していました。
*   `Recv()`: レシーバの「リスト」全体（通常は1つの要素を持つリスト）を返す。
*   `Recv0()`: レシーバのリストの「最初の要素」、つまり実際の単一のレシーバ型を返す。

この命名は直感的ではなく、`Recv` が単数形であるにもかかわらずリストを返し、`Recv0` がリストの要素を返すという点で混乱を招く可能性がありました。特に、`Recv` という名前が単一のレシーバを意味すると誤解されやすかったと考えられます。

`src/cmd/compile/internal/gc/type.go` 内には、この状況を改善するための `TODO` コメントが存在していました。

```go
// TODO(mdempsky): Rename Recv to Recvs, so Recv0 can become just Recv.
```

このコミットは、この `TODO` コメントに沿って命名規則を修正し、より意味が明確で一貫性のあるAPIを提供することを目的としています。これにより、コンパイラのコードベースの可読性と保守性が向上します。

## 前提知識の解説

### Go言語のメソッドとレシーバ

Go言語では、構造体や任意の型にメソッドを定義できます。メソッドは、特別な引数である「レシーバ」を持つ関数です。レシーバは、メソッドがどの型の値に対して呼び出されるかを指定します。

例:
```go
type MyStruct struct {
    Value int
}

// 値レシーバのメソッド
func (s MyStruct) GetValue() int {
    return s.Value
}

// ポインタレシーバのメソッド
func (s *MyStruct) SetValue(newValue int) {
    s.Value = newValue
}
```

コンパイラ内部では、このレシーバも関数シグネチャの一部として扱われます。

### Goコンパイラの内部構造 (`cmd/compile`)

`cmd/compile` はGo言語の公式コンパイラであり、Goのソースコードを機械語に変換する役割を担っています。コンパイラは複数のステージ（字句解析、構文解析、型チェック、中間表現生成、最適化、コード生成など）を経て処理を進めます。

このコミットが関連するのは、主に「型チェック」と「中間表現生成」のステージで使われる型システムの部分です。コンパイラは、Goプログラム内のすべての型（プリミティブ型、構造体、インターフェース、関数など）を内部的なデータ構造で表現します。

### `Type` 構造体とフィールド

Goコンパイラの `src/cmd/compile/internal/gc/type.go` に定義されている `Type` 構造体は、Go言語の型情報を表現するための中心的なデータ構造です。この構造体は、型の種類（`Etype`）、サイズ、アライメント、そして複合型（構造体、関数など）の場合はその構成要素に関する情報（フィールド、パラメータ、戻り値など）を保持します。

関数型の場合、`Type` 構造体はレシーバ、パラメータ、戻り値の情報を内部的に「フィールドのリスト」として保持します。これらのリストは、`Type` 構造体内のポインタ (`t.Type`, `t.Type.Down`, `t.Type.Down.Down` など) を介して連結された `Field` 構造体のチェーンとして表現されることが多いです。

*   `t.Type`: 関数型の場合、レシーバのリストを指すポインタ。
*   `t.Type.Down`: 関数型の場合、パラメータのリストを指すポインタ。
*   `t.Type.Down.Down`: 関数型の場合、戻り値のリストを指すポインタ。

`Field` 構造体は、個々のパラメータやレシーバの型、名前などの情報を持ちます。

### `Recv`, `Recv0`, `Recvs` の概念（変更前）

変更前のコンパイラコードでは、`Type` 構造体には以下のようなメソッドがありました。

*   `func (t *Type) Recv() *Type`: 関数型のレシーバを表す `Type` 構造体のリスト（実際には単一のレシーバを含む `Type` 構造体へのポインタ）を返していました。この `Type` 構造体自体が、レシーバのフィールドリストのヘッドでした。
*   `func (t *Type) Recv0() *Type`: `t.Recv().Field(0)` と同等で、レシーバリストの最初のフィールド（つまり実際のレシーバ型）を返していました。

この命名は、`Recv` が単数形であるにもかかわらず「レシーバのリスト」を指し、`Recv0` がそのリストの「最初の要素」を指すという点で、直感的ではありませんでした。

## 技術的詳細

このコミットの主要な技術的変更は、Goコンパイラの内部APIにおける関数型レシーバのアクセサメソッドの命名規則の変更です。

### 命名規則の改善

*   **`Recv` から `Recvs` への変更**: 以前 `Recv` と呼ばれていたメソッドは、実際にはレシーバの「リスト」を表す `Type` 構造体を返していました。Go言語のメソッドは常に単一のレシーバを持つため、このリストは通常1つの要素しか持ちませんが、コンパイラ内部の汎用的なフィールドリスト処理のメカニズムに沿っていました。この曖昧さを解消するため、`Recv` は `Recvs` (複数形) にリネームされました。これにより、このメソッドがレシーバの「集合」または「リスト」を扱うことを明確に示します。
*   **`Recv0` から `Recv` への変更**: 以前 `Recv0` と呼ばれていたメソッドは、レシーバのリストの最初の要素、つまり実際の単一のレシーバ型を返していました。`Recv` が `Recvs` にリネームされたことで、`Recv0` は単一のレシーバを指す `Recv` (単数形) にリネームされることが適切になりました。これにより、`Recv` は直感的に単一のレシーバ型を指すようになります。

### `Type` 構造体のメソッドの変更

`src/cmd/compile/internal/gc/type.go` において、`Type` 構造体のレシーバ関連のアクセサメソッドが以下のように変更されました。

**変更前:**
```go
func (t *Type) RecvP() **Type { /* ... */ }
func (t *Type) Recv() *Type    { return *t.RecvP() }
func (t *Type) Recv0() *Type { return t.Recv().Field(0) }
```

**変更後:**
```go
func (t *Type) RecvsP() **Type { /* ... */ } // RecvP -> RecvsP
func (t *Type) Recvs() *Type   { return *t.RecvsP() } // Recv -> Recvs
func (t *Type) Recv() *Type { return t.Recvs().Field(0) } // Recv0 -> Recv
```

この変更により、`RecvsP()` はレシーバのリストへのポインタを返し、`Recvs()` はそのリストのヘッドとなる `Type` 構造体を返します。そして、`Recv()` は `Recvs()` が返すリストの最初のフィールド（実際のレシーバ型）を返すようになりました。これは、Go言語のメソッドが単一のレシーバを持つというセマンティクスと、コンパイラ内部のリスト表現との間の橋渡しを、より明確な命名で行うものです。

### `recvParamsResults` から `recvsParamsResults` への変更

関数型のレシーバ、パラメータ、戻り値のリストをイテレートするために使用されるグローバル変数 `recvParamsResults` も、新しい命名規則に合わせて `recvsParamsResults` に変更されました。

**変更前:**
```go
var recvParamsResults = [3]func(*Type) *Type{
    (*Type).Recv, (*Type).Params, (*Type).Results,
}
```

**変更後:**
```go
var recvsParamsResults = [3]func(*Type) *Type{
    (*Type).Recvs, (*Type).Params, (*Type).Results,
}
```

この配列は、`Type` 構造体からレシーバ、パラメータ、戻り値の各リストを取得するための関数ポインタを保持しており、コンパイラの様々な場所で関数シグネチャの各部分を汎用的に処理するために利用されます。命名変更は、この配列が `Recvs` メソッドを使用するように更新されたことを反映しています。

### 影響範囲

この変更は、`src/cmd/compile/internal/gc` ディレクトリ以下の多数のファイルにわたっています。これは、`Recv` および `Recv0` メソッドがコンパイラの型システムにおいて広範に使用されていたことを示しています。具体的には、型のアライメント計算、バイナリ出力、宣言処理、エスケープ解析、エクスポート処理、フォーマット、インライン化、字句解析、ポインタ生成、ライブネス解析、リフレクション情報の生成、サブルーチン処理、型チェック、ウォーク処理など、コンパイラのほぼすべての主要なステージに影響を与えています。

この広範な変更は、単なる名前の変更であっても、コンパイラの内部APIの一貫性と明確性を高める上で重要であることを示しています。

## コアとなるコードの解説

`src/cmd/compile/internal/gc/type.go` の変更は、Goコンパイラの型システムにおけるレシーバの表現とアクセス方法を根本的に明確化するものです。

1.  **`RecvP()` から `RecvsP()` への変更**:
    *   `RecvP()` は以前、レシーバのリストのヘッドを指すポインタへのポインタを返していました。この名前は単数形であるため、リストを指すには不適切でした。
    *   `RecvsP()` に変更されたことで、この関数がレシーバの「集合」（複数形）を指すポインタを返すことが明確になりました。`t.Type` フィールドは、関数型の場合、レシーバのフィールドリストのヘッドを保持しています。

2.  **`Recv()` から `Recvs()` への変更**:
    *   以前の `Recv()` は `*t.RecvP()` と定義されており、レシーバのフィールドリストのヘッドとなる `Type` 構造体を返していました。これも単数形でありながらリストを指すため、混乱を招いていました。
    *   `Recvs()` に変更されたことで、この関数がレシーバの「集合」を表す `Type` 構造体を返すことが明確になりました。

3.  **`Recv0()` から `Recv()` への変更**:
    *   以前の `Recv0()` は `t.Recv().Field(0)` と定義されており、レシーバのフィールドリストの最初の要素、つまり実際の単一のレシーバ型を返していました。`Recv0` という名前は、リストの0番目の要素を指すことを示唆していましたが、より直感的な単一レシーバのアクセサとしては冗長でした。
    *   `Recv()` に変更されたことで、この関数がGo言語のセマンティクスにおける「単一のレシーバ型」を直接返すことが明確になりました。これは、`t.Recvs().Field(0)` を呼び出すことで実現されます。`Field(0)` は、`Type` 構造体が保持するフィールドリストの最初の要素を取得するメソッドです。

    *   この配列は、関数型のレシーバ、パラメータ、戻り値の各リストにアクセスするための関数を格納していました。以前は `(*Type).Recv` を使用していましたが、`Recv` が `Recvs` にリネームされたため、この配列も `(*Type).Recvs` を使用するように更新されました。これにより、コンパイラの内部で関数シグネチャの各部分をイテレートする際の整合性が保たれます。

これらの変更は、コンパイラの内部APIのセマンティクスをより正確に反映させ、将来的な開発者がコードを理解しやすくするための重要なリファクタリングです。特に、Go言語のメソッドが単一のレシーバを持つという特性と、コンパイラ内部でそれをリストとして表現する実装の詳細との間のギャップを、より明確な命名で埋めることに成功しています。

コンパイラ内部では、このレシーバも関数シグネチャの一部として扱われます。

### Goコンパイラの内部構造 (`cmd/compile`)

`cmd/compile` はGo言語の公式コンパイラであり、Goのソースコードを機械語に変換する役割を担っています。コンパイラは複数のステージ（字句解析、構文解析、型チェック、中間表現生成、最適化、コード生成など）を経て処理を進めます。

このコミットが関連するのは、主に「型チェック」と「中間表現生成」のステージで使われる型システムの部分です。コンパイラは、Goプログラム内のすべての型（プリミティブ型、構造体、インターフェース、関数など）を内部的なデータ構造で表現します。

### `Type` 構造体とフィールド

Goコンパイラの `src/cmd/compile/internal/gc/type.go` に定義されている `Type` 構造体は、Go言語の型情報を表現するための中心的なデータ構造です。この構造体は、型の種類（`Etype`）、サイズ、アライメント、そして複合型（構造体、関数など）の場合はその構成要素に関する情報（フィールド、パラメータ、戻り値など）を保持します。

関数型の場合、`Type` 構造体はレシーバ、パラメータ、戻り値の情報を内部的に「フィールドのリスト」として保持します。これらのリストは、`Type` 構造体内のポインタ (`t.Type`, `t.Type.Down`, `t.Type.Down.Down` など) を介して連結された `Field` 構造体のチェーンとして表現されることが多いです。

*   `t.Type`: 関数型の場合、レシーバのリストを指すポインタ。
*   `t.Type.Down`: 関数型の場合、パラメータのリストを指すポインタ。
*   `t.Type.Down.Down`: 関数型の場合、戻り値のリストを指すポインタ。

`Field` 構造体は、個々のパラメータやレシーバの型、名前などの情報を持ちます。

### `Recv`, `Recv0`, `Recvs` の概念（変更前）

変更前のコンパイラコードでは、`Type` 構造体には以下のようなメソッドがありました。

*   `func (t *Type) Recv() *Type`: 関数型のレシーバを表す `Type` 構造体のリスト（実際には単一のレシーバを含む `Type` 構造体へのポインタ）を返していました。この `Type` 構造体自体が、レシーバのフィールドリストのヘッドでした。
*   `func (t *Type) Recv0() *Type`: `t.Recv().Field(0)` と同等で、レシーバリストの最初のフィールド（つまり実際の単一のレシーバ型）を返していました。

この命名は、`Recv` が単数形であるにもかかわらず「レシーバのリスト」を指し、`Recv0` がリストの要素を指すという点で、直感的ではありませんでした。

## 技術的詳細

このコミットの主要な技術的変更は、Goコンパイラの内部APIにおける関数型レシーバのアクセサメソッドの命名規則の変更です。

### 命名規則の改善

*   **`Recv` から `Recvs` への変更**: 以前 `Recv` と呼ばれていたメソッドは、実際にはレシーバの「リスト」を表す `Type` 構造体を返していました。Go言語のメソッドは常に単一のレシーバを持つため、このリストは通常1つの要素しか持ちませんが、コンパイラ内部の汎用的なフィールドリスト処理のメカニズムに沿っていました。この曖昧さを解消するため、`Recv` は `Recvs` (複数形) にリネームされました。これにより、このメソッドがレシーバの「集合」または「リスト」を扱うことを明確に示します。
*   **`Recv0` から `Recv` への変更**: 以前 `Recv0` と呼ばれていたメソッドは、レシーバのリストの最初の要素、つまり実際の単一のレシーバ型を返していました。`Recv` が `Recvs` にリネームされたことで、`Recv0` は単一のレシーバを指す `Recv` (単数形) にリネームされることが適切になりました。これにより、`Recv` は直感的に単一のレシーバ型を指すようになります。

### `Type` 構造体のメソッドの変更

`src/cmd/compile/internal/gc/type.go` において、`Type` 構造体のレシーバ関連のアクセサメソッドが以下のように変更されました。

**変更前:**
```go
func (t *Type) RecvP() **Type { /* ... */ }
func (t *Type) Recv() *Type    { return *t.RecvP() }
func (t *Type) Recv0() *Type { return t.Recv().Field(0) }
```

**変更後:**
```go
func (t *Type) RecvsP() **Type { /* ... */ } // RecvP -> RecvsP
func (t *Type) Recvs() *Type   { return *t.RecvsP() } // Recv -> Recvs
func (t *Type) Recv() *Type { return t.Recvs().Field(0) } // Recv0 -> Recv
```

この変更により、`RecvsP()` はレシーバのリストへのポインタを返し、`Recvs()` はそのリストのヘッドとなる `Type` 構造体を返します。そして、`Recv()` は `Recvs()` が返すリストの最初のフィールド（実際のレシーバ型）を返すようになりました。これは、Go言語のメソッドが単一のレシーバを持つというセマンティクスと、コンパイラ内部のリスト表現との間の橋渡しを、より明確な命名で行うものです。

### `recvParamsResults` から `recvsParamsResults` への変更

関数型のレシーバ、パラメータ、戻り値のリストをイテレートするために使用されるグローバル変数 `recvParamsResults` も、新しい命名規則に合わせて `recvsParamsResults` に変更されました。

**変更前:**
```go
var recvParamsResults = [3]func(*Type) *Type{
    (*Type).Recv, (*Type).Params, (*Type).Results,
}
```

**変更後:**
```go
var recvsParamsResults = [3]func(*Type) *Type{
    (*Type).Recvs, (*Type).Params, (*Type).Results,
}
```

この配列は、`Type` 構造体からレシーバ、パラメータ、戻り値の各リストを取得するための関数ポインタを保持しており、コンパイラの様々な場所で関数シグネチャの各部分を汎用的に処理するために利用されます。命名変更は、この配列が `Recvs` メソッドを使用するように更新されたことを反映しています。

### 影響範囲

この変更は、`src/cmd/compile/internal/gc` ディレクトリ以下の多数のファイルにわたっています。これは、`Recv` および `Recv0` メソッドがコンパイラの型システムにおいて広範に使用されていたことを示しています。具体的には、型のアライメント計算、バイナリ出力、宣言処理、エスケープ解析、エクスポート処理、フォーマット、インライン化、字句解析、ポインタ生成、ライブネス解析、リフレクション情報の生成、サブルーチン処理、型チェック、ウォーク処理など、コンパイラのほぼすべての主要なステージに影響を与えています。

この広範な変更は、単なる名前の変更であっても、コンパイラの内部APIの一貫性と明確性を高める上で重要であることを示しています。

## コアとなるコードの解説

`src/cmd/compile/internal/gc/type.go` の変更は、Goコンパイラの型システムにおけるレシーバの表現とアクセス方法を根本的に明確化するものです。

1.  **`RecvP()` から `RecvsP()` への変更**:
    *   `RecvP()` は以前、レシーバのリストのヘッドを指すポインタへのポインタを返していました。この名前は単数形であるため、リストを指すには不適切でした。
    *   `RecvsP()` に変更されたことで、この関数がレシーバの「集合」（複数形）を指すポインタを返すことが明確になりました。`t.Type` フィールドは、関数型の場合、レシーバのフィールドリストのヘッドを保持しています。

2.  **`Recv()` から `Recvs()` への変更**:
    *   以前の `Recv()` は `*t.RecvP()` と定義されており、レシーバのフィールドリストのヘッドとなる `Type` 構造体を返していました。これも単数形でありながらリストを指すため、混乱を招いていました。
    *   `Recvs()` に変更されたことで、この関数がレシーバの「集合」を表す `Type` 構造体を返すことが明確になりました。

3.  **`Recv0()` から `Recv()` への変更**:
    *   以前の `Recv0()` は `t.Recv().Field(0)` と定義されており、レシーバのフィールドリストの最初の要素、つまり実際の単一のレシーバ型を返していました。`Recv0` という名前は、リストの0番目の要素を指すことを示唆していましたが、より直感的な単一レシーバのアクセサとしては冗長でした。
    *   `Recv()` に変更されたことで、この関数がGo言語のセマンティクスにおける「単一のレシーバ型」を直接返すことが明確になりました。これは、`t.Recvs().Field(0)` を呼び出すことで実現されます。`Field(0)` は、`Type` 構造体が保持するフィールドリストの最初の要素を取得するメソッドです。

4.  **`recvParamsResults` から `recvsParamsResults` への変更**:
    *   この配列は、関数型のレシーバ、パラメータ、戻り値の各リストにアクセスするための関数を格納していました。以前は `(*Type).Recv` を使用していましたが、`Recv` が `Recvs` にリネームされたため、この配列も `(*Type).Recvs` を使用するように更新されました。これにより、コンパイラの内部で関数シグネチャの各部分をイテレートする際の整合性が保たれます。

これらの変更は、コンパイラの内部APIのセマンティクスをより正確に反映させ、将来的な開発者がコードを理解しやすくするための重要なリファクタリングです。特に、Go言語のメソッドが単一のレシーバを持つという特性と、コンパイラ内部でそれをリストとして表現する実装の詳細との間のギャップを、より明確な命名で埋めることに成功しています。

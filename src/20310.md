# [インデックス 20310] ファイルの概要

このコミットは、Goランタイムにおける`nosplit`領域のサイズを160バイトから192バイトに増加させるものです。これは主にWindows/amd64ビルドの問題を修正するために行われました。`nosplit`領域は、スタックチェックをスキップする関数（`nosplit`関数）が使用できるスタック領域の最大サイズを定義します。この変更は、`stackSmall`定数の値を96から64に減らすことで実現され、これにより`StackGuard - StackSmall`で計算される`nosplit`領域が拡張されます。

## 変更の背景

このコミットの主な背景は、GoランタイムがWindows/amd64環境でビルドされる際に発生していた問題の修正です。Goのランタイムには、スタックの成長をチェックする「スタックチェック」をスキップする特別な関数（`nosplit`関数）が存在します。これらの関数は、スタックの最下部に確保された特定の領域（`nosplit`領域）内で実行されることが保証されており、その領域を超えてスタックを使用することはできません。

以前のコミット（CL 131450043）で、この`nosplit`領域は128バイトから160バイトに拡張されていました。しかし、Windows/amd64環境では、特定のランタイム関数がこの160バイトの制限を超えてスタックを使用しようとし、ビルドエラーやランタイムエラーを引き起こしていました。このコミットは、この問題を解決するために`nosplit`領域をさらに192バイトに拡張する必要があるという認識に基づいて行われました。

コミットメッセージには、この領域の拡大に対する懸念への言及もあります。Goはかつて「セグメントスタック」という方式を採用しており、スタックが不足すると新しいスタックセグメントを割り当てていました。この方式では、各スタックセグメントの最下部に一定量のスペースが無駄になっていました。しかし、このコミットが作成された時点では、Goは「連続スタック」方式に移行しており、各ゴルーチンは単一の連続したスタックセグメントを持つようになりました。この新しい方式では、`nosplit`領域の「無駄」はゴルーチンごとに一度しか発生しないため、たとえこの領域をさらに拡大したとしても、全体としては以前のセグメントスタック方式よりもスタック使用量の節約になるという見解が示されています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **Goのスタック管理 (連続スタック vs. 分割スタック)**:
    *   **分割スタック (Segmented Stacks)**: Goの初期バージョンで採用されていたスタック管理方式です。ゴルーチンのスタックが不足すると、新しいより大きなスタックセグメントが割り当てられ、古いセグメントとリンクされます。これにより、スタックが動的に成長できますが、スタックの成長や縮小に伴うオーバーヘッド、およびスタックセグメント間のポインタ更新の複雑さがありました。また、各セグメントの最下部には、スタックチェックやセグメント切り替えのためのオーバーヘッド領域が存在しました。
    *   **連続スタック (Contiguous Stacks)**: 現在のGoで採用されているスタック管理方式です。各ゴルーチンは、単一の連続したスタック領域を持ちます。スタックが不足しそうになると、より大きな新しいスタック領域が割り当てられ、古いスタックの内容が新しい領域にコピーされます。これにより、スタックの操作が単純化され、キャッシュ効率が向上しますが、スタックコピーのオーバーヘッドが発生する可能性があります。この方式では、スタックの最下部に確保される`nosplit`領域は、ゴルーチンごとに一度だけ存在します。

2.  **`nosplit` 関数とその制約**:
    *   Goのコンパイラとリンカは、特定の関数がスタックチェックを行わないようにマークすることができます。これらの関数は「`nosplit`関数」と呼ばれます。
    *   `nosplit`関数は、非常に短い処理を行うランタイム内部のクリティカルなパス（例: スタックの切り替え、スケジューラ関連の処理、メモリ割り当ての初期段階など）で使用されます。これらの関数内でスタックチェックを行うと、無限ループやデッドロックなどの問題を引き起こす可能性があるため、スタックチェックが意図的にスキップされます。
    *   `nosplit`関数は、スタックチェックをスキップするため、自身が使用するスタック領域が、スタックの最下部に確保された「`nosplit`領域」内に収まることを厳密に保証する必要があります。リンカは、`nosplit`関数の呼び出しグラフを解析し、そのスタック使用量がこの制限を超えないことを検証します。もし超える可能性がある場合、リンカはエラーを報告します。

3.  **スタックガードとスタックスモール (`StackGuard`, `StackSmall`)**:
    *   Goのスタックは、スタックポインタ（SP）が特定の「スタックガード」値に近づくと、スタックオーバーフローを防ぐためにスタックチェックがトリガーされるように設計されています。
    *   `StackGuard`は、スタックの最下部（アドレスが最も低い側）にある特定のオフセットを示す定数です。
    *   `StackSmall`は、スタックチェックがトリガーされる前に、SPが`StackGuard`からどれだけ下（アドレスが高い側）に移動できるかを示す定数です。
    *   `StackGuard - StackSmall`で計算される領域が、`nosplit`関数がスタックチェックなしで使用できる「`nosplit`領域」のサイズとなります。SPが`StackGuard - StackSmall`よりも下に行くと、スタックチェックがトリガーされます。しかし、`nosplit`関数はスタックチェックをスキップするため、この領域内で処理を完結させる必要があります。

4.  **`morestack` とスタックチェック**:
    *   Goの関数呼び出しのプロローグには、通常、スタックポインタが`StackGuard`に近づいていないかをチェックするコードが含まれています。
    *   もしスタックが不足していると判断された場合、`morestack`というランタイム関数が呼び出されます。`morestack`は、新しいスタック領域の割り当てや、既存のスタックの拡張（連続スタックの場合、コピー）を行い、呼び出し元関数に制御を戻します。

## 技術的詳細

このコミットの技術的な核心は、`src/pkg/runtime/stack.go`、`src/pkg/runtime/stack.h`、`src/pkg/runtime/stack_test.go`の3つのファイルで定義されている`stackSmall`定数の値を変更することにあります。

*   **`stackSmall` の変更**:
    *   以前の`stackSmall`の値は`96`でした。
    *   このコミットにより、`stackSmall`の値は`64`に変更されました。

*   **`nosplit`領域の計算**:
    *   `nosplit`領域のサイズは、`StackGuard - StackSmall`で計算されます。
    *   `src/pkg/runtime/stack_test.go`を見ると、`StackGuard`は`256`と定義されています。
    *   変更前: `256 (StackGuard) - 96 (StackSmall) = 160`バイト
    *   変更後: `256 (StackGuard) - 64 (StackSmall) = 192`バイト
    *   このように、`stackSmall`の値を減らすことで、`nosplit`領域のサイズが160バイトから192バイトに拡張されています。

*   **Windows/amd64での問題**:
    *   コミットメッセージによると、この変更は特にWindows/amd64環境で必要とされました。これは、特定のランタイム関数（おそらく`morestack`や`deferproc`など、スタックの最下部で動作するクリティカルな関数）が、以前の160バイトの`nosplit`領域では収まらないほどのスタックフレームを必要としていたためと考えられます。リンカが`nosplit`関数のスタック使用量を検証する際に、この制限を超えていると判断し、ビルドエラーが発生していた可能性があります。

*   **`test/nosplit.go` の変更**:
    *   このテストファイルは、`nosplit`関数のスタック使用量を検証するためのものです。
    *   以前のコメント`// CL 131450043 raised the limit from 128 to 160.`が、`// The limit was originally 128 but is now 192.`に変更されています。これは、`nosplit`領域の現在のサイズが192バイトであることを反映しています。
    *   テストケースの調整部分で、`size += 32`が`size += 192 - 128`に変更されています。これは、テストが`nosplit`領域のサイズ変更に適切に対応し、新しい制限（192バイト）を考慮してスタックフレームサイズを調整していることを示しています。`192 - 128 = 64`なので、以前の32バイトの調整から64バイトの調整に変わっています。これは、テストが`nosplit`領域の増加分を正しく考慮していることを示しています。

この変更により、Windows/amd64環境でのランタイムの安定性が向上し、`nosplit`関数が安全に実行できる十分なスタック領域が確保されるようになりました。

## コアとなるコードの解説

このコミットの核となる変更は、`stackSmall`定数の値を`96`から`64`に減らしたことです。

*   **`stackSmall` の役割**: `stackSmall`は、スタックチェックがトリガーされる前に、スタックポインタ（SP）がスタックガード（`StackGuard`）からどれだけ下（アドレスが高い方向）に移動できるかを定義します。この値が小さいほど、`StackGuard - StackSmall`で計算される`nosplit`領域は大きくなります。
*   **`nosplit`領域の拡張**: `StackGuard`が`256`であるため、`stackSmall`を`96`から`64`に減らすことで、`nosplit`領域は`256 - 96 = 160`バイトから`256 - 64 = 192`バイトに拡張されます。これにより、`nosplit`関数がより多くのスタック領域を使用できるようになり、特にWindows/amd64環境で発生していたスタック使用量に関する問題を解決します。
*   **テストコードの調整**: `test/nosplit.go`の変更は、この`nosplit`領域の拡張をテストが正しく認識していることを示しています。テストは、`nosplit`関数のスタック使用量が新しい192バイトの制限内に収まることを検証するために、スタックフレームのサイズ調整ロジックを更新しています。具体的には、以前のコミットで128バイトから160バイトに増加した際に32バイトの調整を行っていた部分が、128バイトから192バイトへの増加に対応するために`192 - 128 = 64`バイトの調整を行うように変更されています。

この変更は、Goランタイムの安定性と移植性を向上させる上で重要な役割を果たしています。

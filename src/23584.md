### 構造体の埋め込み (Embedding)

Go言語の構造体の埋め込みは、ある構造体の中に別の構造体をフィールド名なしで宣言することで実現されます。これにより、埋め込まれた構造体のフィールドやメソッドが、外側の構造体のフィールドやメソッドであるかのように直接アクセスできるようになります。

例:
```go
type Inner struct {
    FieldA int
}

type Outer struct {
    Inner // 埋め込み
    FieldB string
}

func main() {
    o := Outer{Inner: Inner{FieldA: 10}, FieldB: "hello"}
    fmt.Println(o.FieldA) // 直接アクセス可能
}
```

## コアとなるコードの解説

`Node` 構造体内の `*Param` から `Param *Param` への変更は、Go言語の構造体における「埋め込み」と「フィールドとしてのポインタ」の違いを明確に示しています。

1.  **`*Param` (埋め込み)**:
    *   `Node` 構造体は `Param` 構造体のすべてのフィールドを直接「継承」します。
    *   `Node` のインスタンスは、`Param` のフィールドを直接含みます。例えば、`Param` に `Ntype` というフィールドがあれば、`n.Ntype` のようにアクセスできます。
    *   `Node` のサイズは、`Node` 自身のフィールドと `Param` のフィールドの合計サイズになります。`Param` が常に必要でない場合でも、その分のメモリが確保されます。

2.  **`Param *Param` (フィールドとしてのポインタ)**:
    *   `Node` 構造体は `Param` 型のポインタをフィールドとして持ちます。
    *   `Node` のインスタンスは、`Param` 構造体へのポインタ（通常は8バイト）のみを直接含みます。
    *   `Param` 構造体のフィールドにアクセスするには、`n.Param.Ntype` のように、明示的に `Param` フィールドを介する必要があります。
    *   `Param` 構造体は、必要に応じて別途ヒープに割り当てられ、そのアドレスが `n.Param` に格納されます。これにより、`Param` が不要な `Node` インスタンスでは `n.Param` が `nil` となり、`Param` 構造体分のメモリは消費されません。これは、コンパイラのメモリ使用量を最適化する上で非常に有効です。

この変更は、コンパイラの内部データ構造の設計原則における重要な進化を示しています。特に、`Node` のような頻繁に使用される基本構造体では、メモリ効率とコードの整理が極めて重要です。`Param` フィールドを非埋め込みにすることで、これらの目標が達成されています。

*   **`eg`**: `eg` は `gofmt -r` のようなコード変換をより高度に、かつ安全に行うためのツールです。GoのASTを操作し、より複雑なリファクタリングパターンを適用できます。このコミットでは、`Node` 構造体の変更に伴い、そのフィールドへのアクセスパターン (`n.Ntype` から `n.Param.Ntype` など) を自動的に書き換えるために使用されました。

### `toolstash -cmp`

`toolstash -cmp` は、Goコンパイラの開発において、コンパイラ自体への変更が生成されるバイナリコードに機能的な影響を与えないことを検証するためのツールです。具体的には、変更前のコンパイラと変更後のコンパイラで同じソースコードをコンパイルし、生成されたオブジェクトファイルやバイナリを比較します。もし両者が完全に一致すれば、機能的な変更がないことが保証されます。このコミットが `toolstash -cmp` をパスしたということは、今回のリファクタリングがコンパイラの出力に影響を与えない、純粋な内部構造の変更であることを意味します。

## 技術的詳細

このコミットの核心は、`src/cmd/compile/internal/gc/syntax.go` に定義されている `Node` 構造体の定義変更です。

変更前:
```go
type Node struct {
    // ... 既存のフィールド ...
    *Param // Param 構造体が埋め込まれている
    // ... その他のフィールド ...
}
```

変更後:
```go
type Node struct {
    // ... 既存のフィールド ...
    Param *Param // Param 構造体へのポインタとして宣言
    // ... その他のフィールド ...
}
```

この変更により、`Node` 構造体内の `Param` フィールドへのアクセス方法が `n.Field` から `n.Param.Field` へと変わりました。例えば、`n.Ntype` は `n.Param.Ntype` に、`n.Closure` は `n.Param.Closure` に変更されています。

**この変更の技術的な意味合いは以下の通りです。**

1.  **メモリ効率の向上**: `Param` 構造体が埋め込まれている場合、`Node` 構造体のすべてのインスタンスは `Param` 構造体のすべてのフィールドを直接含みます。しかし、`Param` がポインタ (`*Param`) になると、`Node` 構造体自体はポインタのサイズ（通常は8バイト）しか持ちません。`Param` 構造体が必要な場合にのみヒープに割り当てられ、そのポインタが `Node.Param` に格納されます。これにより、`Param` フィールドが常に必要ではない `Node` インスタンスのメモリフットプリントを削減できます。これは、コンパイラが処理するASTノードの数が非常に多いことを考えると、全体的なメモリ使用量の削減に大きく貢献する可能性があります。
2.  **コードの整理とカプセル化**: `Param` 構造体は、特定の種類のノード（例えば、関数や変数宣言など）に関連するパラメータ固有の情報を保持していると考えられます。これを独立した構造体としてポインタ経由で参照することで、`Node` 構造体自体の責務をより明確にし、関連するデータを `Param` の中にカプセル化できます。これにより、コードの可読性と保守性が向上します。
3.  **広範囲な変更の必要性**: `Node` 構造体はコンパイラ全体で広く使用されているため、この変更は `src/cmd/compile/internal/gc` 以下の多数のファイルに影響を与えています。コミットの差分を見ると、`align.go`, `closure.go`, `dcl.go`, `esc.go`, `export.go`, `fmt.go`, `gen.go`, `go.y`, `init.go`, `lex.go`, `sinit.go`, `subr.go`, `swt.go`, `syntax.go`, `typecheck.go`, `walk.go`, `y.go` など、17ものファイルが変更されています。これは、`Node` 構造体のフィールドアクセスがコンパイラの様々なステージで頻繁に行われていることを示しています。
4.  **自動化されたリファクタリング**: このような広範囲にわたる変更を手動で行うのはエラーが発生しやすく、非常に時間がかかります。`eg` と `gofmt -r` を使用して自動的に変更が適用されたことは、Go開発チームがコード品質と開発効率を両立させるための優れたプラクティスを持っていることを示しています。

## コアとなるコードの解説

`Node` 構造体内の `*Param` から `Param *Param` への変更は、Go言語の構造体における「埋め込み」と「フィールドとしてのポインタ」の違いを明確に示しています。

1.  **`*Param` (埋め込み)**:
    *   `Node` 構造体は `Param` 構造体のすべてのフィールドを直接「継承」します。
    *   `Node` のインスタンスは、`Param` のフィールドを直接含みます。例えば、`Param` に `Ntype` というフィールドがあれば、`n.Ntype` のようにアクセスできます。
    *   `Node` のサイズは、`Node` 自身のフィールドと `Param` のフィールドの合計サイズになります。`Param` が常に必要でない場合でも、その分のメモリが確保されます。

2.  **`Param *Param` (フィールドとしてのポインタ)**:
    *   `Node` 構造体は `Param` 型のポインタをフィールドとして持ちます。
    *   `Node` のインスタンスは、`Param` 構造体へのポインタ（通常は8バイト）のみを直接含みます。
    *   `Param` 構造体のフィールドにアクセスするには、`n.Param.Ntype` のように、明示的に `Param` フィールドを介する必要があります。
    *   `Param` 構造体は、必要に応じて別途ヒープに割り当てられ、そのアドレスが `n.Param` に格納されます。これにより、`Param` が不要な `Node` インスタンスでは `n.Param` が `nil` となり、`Param` 構造体分のメモリは消費されません。これは、コンパイラのメモリ使用量を最適化する上で非常に有効です。

この変更は、コンパイラの内部データ構造の設計原則における重要な進化を示しています。特に、`Node` のような頻繁に使用される基本構造体では、メモリ効率とコードの整理が極めて重要です。`Param` フィールドを非埋め込みにすることで、これらの目標が達成されています。

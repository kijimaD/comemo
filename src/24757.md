# [インデックス 24757] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおいて、複素数型（`complex64`および`complex128`）の基本的なサポートを追加するものです。具体的には、複素数定数、PHI関数（条件分岐による値の結合）、およびメモリからのロード/ストア操作における複素数の「構成 (compose)」と「分解 (decompose)」メカニズムを導入しています。これにより、複素数がSSA形式で適切に表現され、最適化パスで処理されるための基盤が構築されます。

## 元コミット内容

GoコンパイラのSSAバックエンドに、複素数型（`complex64`, `complex128`）の構成（compose）と分解（decompose）機能を追加します。この機能は、複素数定数、PHI関数、およびメモリ操作（ロード/ストア）を対象としています。複素数に対する算術演算のサポートは、このコミットの後の作業として残されています。

## 変更の背景

Goコンパイラは、コードの最適化と効率的な機械語生成のために、ソースコードを中間表現であるSSA形式に変換します。以前は、複素数型がSSA形式で直接的に扱われるための適切なメカニズムが不足していました。複素数は実部と虚部という2つの浮動小数点数から構成されるため、SSAでこれらを効率的に表現し、操作するためには特別な処理が必要です。

このコミットは、複素数型をSSA形式で「構成」（実部と虚部から複素数を生成）し、「分解」（複素数から実部と虚部を抽出）する基本的な操作を導入することで、このギャップを埋めることを目的としています。これにより、コンパイラは複素数を含むプログラムをSSA形式に変換し、その後の最適化パスで処理できるようになります。特に、条件分岐によって異なる複素数値が結合されるPHI関数や、メモリとの間で複素数をやり取りする際の正確な処理が不可欠でした。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化で広く用いられる中間表現です。SSAの主要な特性は、「各変数が一度だけ代入される」という点です。これにより、データフロー解析が大幅に簡素化され、より強力な最適化が可能になります。

*   **PHI関数**: SSA形式では、複数の制御フローパスが合流する地点（例: `if-else`文の終わり、ループの合流点）で、異なるパスから来る同じ変数に対する複数の定義を結合するためにPHI関数（Φ関数）が導入されます。PHI関数は、どのパスから来たかによって適切な値を選択します。

### 2. Goコンパイラの構造

Goコンパイラ（`cmd/compile`）は、複数のステージを経てソースコードを機械語に変換します。

*   **フロントエンド**: ソースコードの字句解析、構文解析、型チェック、抽象構文木（AST）の構築を行います。
*   **ミドルエンド (SSAジェネレータ)**: ASTをSSA形式に変換します。このステージで、Goの型システムとSSAの操作が橋渡しされます。
*   **バックエンド**: SSA形式をターゲットアーキテクチャの機械語に変換し、レジスタ割り当てや命令スケジューリングなどの最適化を行います。

### 3. 複素数型 (`complex64`, `complex128`)

Go言語には、`complex64`（`float32`の実部と虚部）と`complex128`（`float64`の実部と虚部）の2種類の複素数型があります。これらは内部的には2つの浮動小数点数として扱われます。例えば、`complex64`はメモリ上で2つの`float32`が連続して配置される形で表現されます。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドが複素数型をどのように扱うかを定義した点にあります。

1.  **新しいSSAオペレーションの導入**:
    *   `OpComplexMake`: 2つの浮動小数点数（実部と虚部）から複素数値を構成します。
    *   `OpComplexReal`: 複素数値から実部を抽出します。
    *   `OpComplexImag`: 複素数値から虚部を抽出します。
    これらのオペレーションは、SSA形式で複素数を抽象的に操作するためのプリミティブとなります。

2.  **複素数定数の処理**:
    `src/cmd/compile/internal/gc/ssa.go`の`expr`関数において、`CTCPLX`（コンパイラ内部の複素数定数）が検出された場合、`OpComplexMake`オペレーションを使用してSSA値に変換されます。これにより、`1 + 2i`のようなリテラル複素数がSSAグラフ内で適切に表現されます。

3.  **ゼロ値の生成**:
    `src/cmd/compile/internal/gc/ssa.go`の`zeroVal`関数に、複素数型のゼロ値（`0 + 0i`）を生成するロジックが追加されました。これも`OpComplexMake`と浮動小数点数のゼロ定数を用いて実現されます。

4.  **PHI関数の分解 (`decomposeComplexPhi`)**:
    `src/cmd/compile/internal/ssa/decompose.go`に`decomposeComplexPhi`関数が追加されました。これは、複素数型のPHIノードを、その実部と虚部に対応する2つの浮動小数点数型のPHIノードに分解する役割を担います。
    例えば、`c = (x ? a : b)`というコードで`a`と`b`が複素数の場合、SSAでは`c = Φ(a, b)`となります。このPHIノードは、`real_c = Φ(real_a, real_b)`と`imag_c = Φ(imag_a, imag_b)`という2つのPHIノードに分解され、最終的に`c = ComplexMake(real_c, imag_c)`として再構成されます。この分解は、SSAの最適化パスが個々の浮動小数点数に対して動作できるようにするために重要です。

5.  **メモリ操作の分解 (`Load`/`Store` rewrite rules)**:
    `src/cmd/compile/internal/ssa/gen/generic.rules`と`src/cmd/compile/internal/ssa/rewritegeneric.go`に、複素数型のロード（`Load`) およびストア（`Store`）操作を分解するルールが追加されました。
    *   **ロード**: `Load`オペレーションが複素数型を対象とする場合、それは2つの`Load`オペレーションに分解されます。1つは実部（先頭アドレスから）、もう1つは虚部（実部の直後のアドレスから）を読み込むためのものです。
    *   **ストア**: `Store`オペレーションが複素数型を対象とする場合、`ComplexMake`オペレーションによって構成された複素数から実部と虚部を抽出し、それぞれをメモリの適切なオフセットにストアする2つの`Store`オペレーションに分解されます。
    これにより、コンパイラは複素数をメモリから読み書きする際に、その内部表現（2つの浮動小数点数）を直接操作できるようになります。

6.  **型システムへの統合**:
    `src/cmd/compile/internal/gc/type.go`と`src/cmd/compile/internal/ssa/type.go`に`IsComplex()`メソッドが追加され、型が複素数型であるかを判定できるようになりました。また、SSAの`TypeSource`インターフェースに`TypeFloat32()`と`TypeFloat64()`が追加され、SSAバックエンドがフロントエンドから浮動小数点数型に関する情報を取得できるようになりました。

これらの変更により、Goコンパイラは複素数型をSSA形式で表現し、基本的なデータフローを追跡し、メモリとの間でやり取りする能力を獲得しました。これにより、将来的に複素数に対する算術演算やその他の最適化をSSAレベルで実装するための強固な基盤が築かれました。

## コアとなるコードの変更箇所

### 1. `src/cmd/compile/internal/gc/ssa.go` (複素数定数とゼロ値の生成)

```go
// 複素数定数の処理
case CTCPLX:
	c := n.Val().U.(*Mpcplx)
	r := &c.Real
	i := &c.Imag
	switch n.Type.Size() {
	case 8: // complex64
		{
			pt := Types[TFLOAT32]
			return s.newValue2(ssa.OpComplexMake, n.Type,
				s.constFloat32(pt, mpgetflt32(r)),
				s.constFloat32(pt, mpgetflt32(i)))
		}
	case 16: // complex128
		{
			pt := Types[TFLOAT64]
			return s.newValue2(ssa.OpComplexMake, n.Type,
				s.constFloat32(pt, mpgetflt(r)), // Note: mpgetflt for float64
				s.constFloat32(pt, mpgetflt(i))) // Note: mpgetflt for float64
		}
	default:
		s.Fatalf("bad float size %d", n.Type.Size())
		return nil
	}

// 複素数型のゼロ値生成
case t.IsComplex():
	switch t.Size() {
	case 8: // complex64
		z := s.constFloat32(Types[TFLOAT32], 0)
		return s.newValue2(ssa.OpComplexMake, t, z, z)
	case 16: // complex128
		z := s.constFloat64(Types[TFLOAT64], 0)
		return s.newValue2(ssa.OpComplexMake, t, z, z)
	default:
		s.Fatalf("bad sized complex type %s", t)
	}
```

### 2. `src/cmd/compile/internal/ssa/decompose.go` (PHI関数の分解)

```go
func decompose(f *Func) {
	// ... (既存のコード)
	for _, b := range f.Blocks {
		for _, v := range b.Values {
			if v.Op != OpPhi {
				continue
			}
			switch {
			case v.Type.IsComplex(): // 複素数型のPHIを分解
				decomposeComplexPhi(v)
			case v.Type.IsString():
				decomposeStringPhi(v)
			case v.Type.IsSlice():
				decomposeSlicePhi(v)
			case v.Type.IsInterface():
				decomposeInterfacePhi(v)
			}
		}
	}
}

func decomposeComplexPhi(v *Value) {
	fe := v.Block.Func.Config.fe
	var partType Type
	if v.Type.Size() == 8 { // complex64
		partType = fe.TypeFloat32()
	} else if v.Type.Size() == 16 { // complex128
		partType = fe.TypeFloat64()
	} else {
		panic("Whoops, are sizes in bytes or bits?") // エラーハンドリング
	}

	// 実部と虚部それぞれに対応する新しいPHIノードを作成
	real := v.Block.NewValue0(v.Line, OpPhi, partType)
	imag := v.Block.NewValue0(v.Line, OpPhi, partType)
	for _, a := range v.Args {
		// 各引数から実部/虚部を抽出し、新しいPHIノードの引数に追加
		real.AddArg(a.Block.NewValue1(v.Line, OpComplexReal, partType, a))
		imag.AddArg(a.Block.NewValue1(v.Line, OpComplexImag, partType, a))
	}
	// 元のPHIノードをComplexMakeオペレーションに変換し、新しい実部/虚部PHIを引数とする
	v.Op = OpComplexMake
	v.AuxInt = 0
	v.Aux = nil
	v.resetArgs()
	v.AddArg(real)
	v.AddArg(imag)
}
```

### 3. `src/cmd/compile/internal/ssa/gen/generic.rules` (ロード/ストアの書き換えルール)

```go
// ComplexMakeから実部/虚部を抽出するルール
(ComplexReal (ComplexMake real _  )) -> real
(ComplexImag (ComplexMake _ imag )) -> imag

// complex64のロードを2つのfloat32ロードに分解
(Load <t> ptr mem) && t.IsComplex() && t.Size() == 8 ->
  (ComplexMake
    (Load <config.fe.TypeFloat32()> ptr mem)
    (Load <config.fe.TypeFloat32()>
      (OffPtr <config.fe.TypeFloat32().PtrTo()> [4] ptr) // 4バイトオフセット
      mem)
    )

// complex64のストアを2つのfloat32ストアに分解
(Store [8] dst (ComplexMake real imag) mem) ->
  (Store [4]
    (OffPtr <config.fe.TypeFloat32().PtrTo()> [4] dst) // 4バイトオフセット
    imag
    (Store <TypeMem> [4] dst real mem))

// complex128のロードを2つのfloat64ロードに分解
(Load <t> ptr mem) && t.IsComplex() && t.Size() == 16 ->
  (ComplexMake
    (Load <config.fe.TypeFloat64()> ptr mem)
    (Load <config.fe.TypeFloat64()>
      (OffPtr <config.fe.TypeFloat64().PtrTo()> [8] ptr) // 8バイトオフセット
      mem)
    )

// complex128のストアを2つのfloat64ストアに分解
(Store [16] dst (ComplexMake real imag) mem) ->
  (Store [8]
    (OffPtr <config.fe.TypeFloat64().PtrTo()> [8] dst) // 8バイトオフセット
    imag
    (Store <TypeMem> [8] dst real mem))
```

## コアとなるコードの解説

### 1. `src/cmd/compile/internal/gc/ssa.go`

*   `expr`関数内の`CTCPLX`ケースは、Goソースコード中の`1 + 2i`のような複素数リテラルをSSA形式に変換する部分です。`n.Val().U.(*Mpcplx)`でコンパイラ内部の複素数定数表現を取得し、その実部と虚部を`s.constFloat32`または`s.constFloat64`で浮動小数点数定数SSA値に変換します。最終的に、これら2つの浮動小数点数SSA値を引数として`ssa.OpComplexMake`オペレーションを生成し、複素数SSA値を構成します。
*   `zeroVal`関数内の`t.IsComplex()`ケースは、複素数型の変数が初期化されていない場合に、そのゼロ値（`0 + 0i`）を生成します。これも同様に、浮動小数点数ゼロ定数と`ssa.OpComplexMake`を用いて実現されます。

### 2. `src/cmd/compile/internal/ssa/decompose.go`

*   `decompose`関数は、SSAグラフを走査し、特定の複合型（文字列、スライス、インターフェース、そしてこのコミットで追加された複素数）のPHIノードを、その構成要素に分解する役割を担います。
*   `decomposeComplexPhi`関数は、複素数型のPHIノード`v`を受け取ります。まず、複素数型（`complex64`または`complex128`）に応じて、実部と虚部の型（`float32`または`float64`）を決定します。
*   次に、実部と虚部それぞれに対応する新しいPHIノード（`real`と`imag`）を作成します。
*   元の複素数PHIノード`v`の各引数`a`に対して、`OpComplexReal`と`OpComplexImag`オペレーションを適用して実部と虚部を抽出し、それぞれを新しい`real`と`imag`PHIノードの引数として追加します。
*   最後に、元の複素数PHIノード`v`のオペレーションを`OpComplexMake`に変更し、新しく作成した`real`と`imag`PHIノードをその引数として設定します。これにより、高レベルの複素数PHIが、低レベルの浮動小数点数PHIと`ComplexMake`オペレーションの組み合わせに変換されます。

### 3. `src/cmd/compile/internal/ssa/gen/generic.rules`

*   このファイルは、SSAの最適化パスで使用される書き換えルールを定義しています。
*   `(ComplexReal (ComplexMake real _ )) -> real`と`(ComplexImag (ComplexMake _ imag )) -> imag`のルールは、`ComplexMake`によって構成された複素数から実部や虚部を抽出する操作が、直接その構成要素に置き換えられることを示しています。これは、冗長な`ComplexMake`/`ComplexReal`/`ComplexImag`の組み合わせを最適化するのに役立ちます。
*   `Load`と`Store`に関するルールは、複素数型がメモリ上でどのように扱われるかを定義します。`complex64`は2つの`float32`として、`complex128`は2つの`float64`として連続して格納されることを前提としています。
    *   `Load`ルールは、複素数型のロードを、ポインタのオフセット（`complex64`なら4バイト、`complex128`なら8バイト）を使って実部と虚部を個別にロードし、それらを`ComplexMake`で再構成する形に変換します。
    *   `Store`ルールは、複素数型のストアを、`ComplexMake`から実部と虚部を抽出し、それぞれを適切なオフセットに個別にストアする形に変換します。この際、メモリの依存関係を正しく処理するために、ストア操作がチェインされます。

これらの変更は、Goコンパイラが複素数型をSSA形式で効率的に処理するための基盤を確立し、今後の複素数演算の最適化への道を開くものです。

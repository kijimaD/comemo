# [インデックス 23513] ファイルの概要

`shared_test.go` は Go の `misc/cgo/testshared` パッケージ内のテストファイルです。このファイルは、Cgo を使用して共有ライブラリをビルドし、それらが正しくリンクされているか、また期待される RPATH (または RUNPATH) が設定されているかを検証するためのユーティリティ関数とテストケースを含んでいます。具体的には、生成された実行ファイルや共有ライブラリが特定のディレクトリをライブラリ検索パスとして持っていることを確認する `AssertHasRPath` 関数がこのコミットで変更されています。

## コミット

このコミットは、Go の Cgo テストスイートにおいて、共有ライブラリの検索パス (RPATH) のチェックをより堅牢にするための修正です。具体的には、リンカが `DT_RPATH` の代わりに `DT_RUNPATH` を設定する場合があるため、両方のダイナミックタグをチェックするように `AssertHasRPath` 関数を拡張しています。これにより、異なるシステムやリンカの挙動の違いによってテストが失敗するのを防ぎ、テストの信頼性を向上させます。

## 変更の背景

この変更の背景には、ELF (Executable and Linkable Format) 形式の実行ファイルや共有ライブラリにおける動的リンカの挙動の差異があります。特に、`ld` (GNU Linker) の `-rpath` オプションが、システムや `ld` のバージョンによって `DT_RPATH` と `DT_RUNPATH` のどちらのダイナミックタグを設定するかが異なるという問題がありました。

元の `shared_test.go` 内の `AssertHasRPath` 関数は、生成されたバイナリが特定の共有ライブラリ検索パス (RPATH) を持っていることを検証するために、`elf.DT_RPATH` タグのみをチェックしていました。しかし、コミットメッセージにあるように、一部のシステムでは `ld -rpath` が `DT_RPATH` ではなく `DT_RUNPATH` を設定するため、これらのシステムでテストが誤って失敗していました。

このコミットは、このようなリンカの挙動の差異を吸収し、テストがより多くの環境で正しく動作するようにするために導入されました。これにより、Go の Cgo 関連のテストの移植性と信頼性が向上します。

## 前提知識の解説

### ELF (Executable and Linkable Format)

ELF は、Unix系システム (Linux, Solaris, BSDなど) で実行ファイル、共有ライブラリ、オブジェクトファイルなどのバイナリファイルを格納するために使用される標準的なファイル形式です。ELF ファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、および様々なセクションで構成されます。

### 動的リンカ (Dynamic Linker)

動的リンカ (通常 `ld.so` または `ld-linux.so`) は、プログラムの実行時に共有ライブラリをロードし、シンボルを解決する役割を担います。これにより、プログラムのサイズを小さくし、複数のプログラム間でライブラリを共有できるようになります。動的リンカは、共有ライブラリを検索するために、いくつかの定義されたパスを調べます。

### RPATH と RUNPATH (DT_RPATH と DT_RUNPATH)

`DT_RPATH` と `DT_RUNPATH` は、ELF ファイルの `.dynamic` セクションに格納されるダイナミックタグであり、動的リンカが共有ライブラリを検索するためのパスを指定します。これらは、ビルド時に実行ファイルや共有ライブラリに埋め込まれる検索パスです。

*   **`DT_RPATH`**:
    *   **目的**: 実行ファイルや共有ライブラリに、共有ライブラリの検索パスを埋め込みます。
    *   **優先順位**: `LD_LIBRARY_PATH` 環境変数よりも**高い**優先順位で検索されます。つまり、`DT_RPATH` で指定されたパスにライブラリが見つかった場合、`LD_LIBRARY_PATH` は無視されます。
    *   **推移的継承**: `DT_RPATH` は推移的に継承されます。もし実行ファイルが `libA` にリンクし、`libA` が `libB` にリンクしている場合、実行ファイルの `DT_RPATH` は `libB` の検索にも使用される可能性があります。
    *   **非推奨**: `DT_RPATH` はその柔軟性の低さやセキュリティ上の懸念から、一般的に非推奨とされています。`LD_LIBRARY_PATH` をユーザーがオーバーライドしにくいという問題があります。

*   **`DT_RUNPATH`**:
    *   **目的**: `DT_RPATH` と同様に、共有ライブラリの検索パスを埋め込みます。`DT_RPATH` の欠点を改善するために導入されました。
    *   **優先順位**: `LD_LIBRARY_PATH` 環境変数よりも**低い**優先順位で検索されます。これにより、ユーザーは `LD_LIBRARY_PATH` を使って埋め込まれたパスをオーバーライドする柔軟性が得られます。
    *   **推移的継承**: `DT_RUNPATH` は推移的に継承されません。`DT_RUNPATH` エントリは、そのオブジェクト (実行ファイルまたは共有ライブラリ) の直接の依存関係 (`DT_NEEDED` エントリ) を見つけるためにのみ使用されます。もし直接の依存関係がさらに依存関係を持つ場合、それ自身の `DT_RUNPATH` エントリが必要です。
    *   **現代的な使用**: 現代のリンカ (例: GNU `ld`) では、`-rpath` オプションを使用すると、通常 `DT_RPATH` ではなく `DT_RUNPATH` が設定されます。

### Cgo

Cgo は Go 言語の機能の一つで、Go プログラムから C 言語のコードを呼び出したり、C 言語のコードから Go の関数を呼び出したりすることを可能にします。これにより、既存の C ライブラリを Go プロジェクトで利用したり、パフォーマンスが重要な部分を C で記述したりすることができます。Cgo を使用する際には、共有ライブラリのリンクパス (RPATH/RUNPATH) の設定が重要になることがあります。

## 技術的詳細

このコミットの技術的な核心は、ELF バイナリの動的セクションにおける `DT_RPATH` と `DT_RUNPATH` の両方を考慮に入れることで、Cgo テストの堅牢性を高める点にあります。

Go の `misc/cgo/testshared` パッケージは、Cgo を利用した共有ライブラリのビルドとリンクが正しく行われることを検証するためのものです。特に `AssertHasRPath` 関数は、ビルドされたバイナリが特定のディレクトリを共有ライブラリの検索パスとして含んでいることを確認します。これは、Cgo でビルドされた Go プログラムが、依存する C ライブラリを正しく見つけられるようにするために不可欠なチェックです。

問題は、`ld` リンカの挙動がシステムによって異なることです。一部のシステムでは、`-rpath` オプションを指定しても、リンカは伝統的な `DT_RPATH` タグではなく、より現代的で柔軟な `DT_RUNPATH` タグを ELF バイナリに書き込みます。元の `AssertHasRPath` 関数は `elf.DT_RPATH` のみをチェックしていたため、`DT_RUNPATH` が設定されているシステムでは、実際には正しいパスが設定されているにもかかわらず、テストが失敗するという誤検知が発生していました。

この変更は、`AssertHasRPath` 関数が `elf.DT_RPATH` と `elf.DT_RUNPATH` の両方のタグを順にチェックするように修正することで、この問題を解決します。これにより、リンカがどちらのタグを使用しても、テストは正しくパスを検出できるようになります。これは、Go のテストスイートが多様なビルド環境やオペレーティングシステムで一貫して動作するために重要な改善です。

具体的には、`elf.DynTag` のスライス `[]elf.DynTag{elf.DT_RPATH, elf.DT_RUNPATH}` を導入し、このスライスをイテレートしてそれぞれのタグに対応する動的文字列を検索するように変更されています。これにより、コードの重複を避けつつ、両方のタグのチェックを効率的に実装しています。

変更は `misc/cgo/testshared/shared_test.go` ファイル内の `AssertHasRPath` 関数にあります。

+++ b/misc/cgo/testshared/shared_test.go
@@ -192,10 +192,12 @@ func AssertIsLinkedTo(t *testing.T, path, lib string) {

-	for _, dynstring := range dynStrings(path, elf.DT_RPATH) {
-		for _, rpath := range strings.Split(dynstring, ":") {
-			if filepath.Clean(rpath) == filepath.Clean(dir) {
-				return
+	for _, tag := range []elf.DynTag{elf.DT_RPATH, elf.DT_RUNPATH} {
+		for _, dynstring := range dynStrings(path, tag) {

+					return
+				}

## コアとなるコードの解説

変更された `AssertHasRPath` 関数は、指定された `path` (バイナリファイルのパス) が `dir` (期待されるライブラリ検索ディレクトリ) を RPATH として持っていることを検証します。

元のコードでは、`dynStrings(path, elf.DT_RPATH)` を呼び出して、ELF ファイルから `DT_RPATH` タグに関連付けられた動的文字列 (RPATH のリスト) を取得していました。そして、その文字列を `:` で分割し、各パスが `dir` と一致するかどうかをチェックしていました。

このコミットによる変更では、以下の点が異なります。

1.  **タグのリスト化**: `for _, tag := range []elf.DynTag{elf.DT_RPATH, elf.DT_RUNPATH}` というループが追加されました。これにより、`elf.DT_RPATH` と `elf.DT_RUNPATH` の両方のダイナミックタグを順番に処理するようになりました。
2.  **汎用的な `dynStrings` 呼び出し**: 内部のループで `dynStrings(path, tag)` を呼び出すことで、現在の `tag` (`DT_RPATH` または `DT_RUNPATH`) に対応する動的文字列を取得します。
3.  **パスのチェック**: 取得した `dynstring` を `:` で分割し、各 `rpath` が `filepath.Clean(dir)` と一致するかどうかをチェックするロジックは変更されていません。

この修正により、`AssertHasRPath` 関数は、リンカが `DT_RPATH` または `DT_RUNPATH` のどちらを設定した場合でも、期待されるライブラリ検索パスを正しく検出できるようになりました。これにより、異なるシステムやリンカのバージョンに起因するテストの失敗が解消され、Go の Cgo テストの互換性と信頼性が向上します。

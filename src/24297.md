# [インデックス 24297] ファイルの概要

このコミットは、Go言語の `crypto/tls` パッケージにおける重要なセキュリティ修正を導入しています。具体的には、TLS接続のホスト名検証 (`VerifyHostname` 関数) を実行する前に、証明書チェーンが実際に検証されていることを確認するよう変更されました。これにより、証明書チェーンの検証が失敗しているにもかかわらず、ホスト名検証が誤って成功してしまう可能性のある脆弱性が修正されました。

## 変更の背景

このコミットは、Go言語の `crypto/tls` パッケージにおける潜在的なセキュリティ脆弱性に対処するために行われました。以前のバージョンでは、`tls.Config` の `InsecureSkipVerify` フィールドが `true` に設定されている場合、または何らかの理由で証明書チェーンの検証が失敗した場合でも、`Conn.VerifyHostname` メソッドがホスト名検証を続行してしまう可能性がありました。

これは、中間者攻撃 (Man-in-the-Middle, MITM) のリスクを高める可能性がありました。攻撃者が不正な証明書を提示し、その証明書チェーンが検証に失敗したとしても、もしホスト名が偶然一致していれば、クライアントがその接続を信頼してしまう恐れがあったためです。

このコミットは、`Fixes #9063` と記載されており、この問題がGoのイシュートラッカーで報告された脆弱性であったことを示唆しています。この変更により、ホスト名検証は、基盤となる証明書チェーンが正常に検証された場合にのみ実行されるようになり、TLS接続のセキュリティが強化されました。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上での通信のセキュリティを確保するための暗号化プロトコルです。ウェブブラウジング (HTTPS)、電子メール、VoIPなど、様々なアプリケーションで利用されています。TLSは、主に以下の3つのセキュリティ目標を達成します。

1.  **認証 (Authentication)**: 通信相手が主張するエンティティであることを確認します。通常、サーバーはデジタル証明書を提示し、クライアントはその証明書を検証することでサーバーの身元を確認します。
2.  **機密性 (Confidentiality)**: 通信内容が第三者に傍受されても解読されないように暗号化します。
3.  **完全性 (Integrity)**: 通信内容が転送中に改ざんされていないことを保証します。

### デジタル証明書と証明書チェーン

デジタル証明書は、公開鍵と、その公開鍵の所有者の身元情報を結びつける電子的な文書です。信頼できる第三者である認証局 (Certificate Authority, CA) によって署名されます。

**証明書チェーン (Certificate Chain)** は、複数の証明書が連結されたものです。

*   **エンドエンティティ証明書 (End-entity Certificate)**: サーバーやクライアントなどの最終的なエンティティに発行される証明書です。
*   **中間認証局証明書 (Intermediate CA Certificate)**: ルート認証局とエンドエンティティ証明書の間に位置し、エンドエンティティ証明書に署名します。
*   **ルート認証局証明書 (Root CA Certificate)**: 自己署名された証明書で、オペレーティングシステムやブラウザに事前に組み込まれている信頼された証明書です。

クライアントは、エンドエンティティ証明書から始まり、中間認証局証明書をたどり、最終的に信頼されたルート認証局証明書に到達することで、証明書チェーン全体の信頼性を検証します。このプロセスを「証明書チェーンの検証」と呼びます。

### ホスト名検証 (Hostname Verification)

TLSハンドシェイク中にサーバーが提示する証明書には、その証明書が発行されたドメイン名（Common NameやSubject Alternative Name）が含まれています。クライアントは、接続しようとしているホスト名（例: `www.example.com`）が、サーバー証明書に記載されているドメイン名と一致するかどうかを確認します。これがホスト名検証です。

ホスト名検証は、証明書チェーンの検証が成功した後に実行されるべき重要なステップです。これにより、たとえ有効な証明書チェーンを持つ証明書であっても、それが意図しないドメインに発行されたものであれば、接続を拒否することができます。

### `InsecureSkipVerify`

Goの `crypto/tls` パッケージにおける `tls.Config` 構造体には `InsecureSkipVerify` というフィールドがあります。これを `true` に設定すると、クライアントはサーバー証明書の検証（証明書チェーンの検証を含む）をスキップします。

**警告**: `InsecureSkipVerify: true` は、開発環境や特定のテストシナリオでのみ使用されるべきであり、本番環境での使用は**絶対に避けるべき**です。この設定は、TLSの最も基本的なセキュリティ保証であるサーバー認証を無効にするため、中間者攻撃に対して脆弱になります。

### `Conn.VerifyHostname` 関数

`Conn.VerifyHostname(host string)` は、TLS接続が確立された後に、ピア証明書（接続相手の証明書）のホスト名が指定された `host` と一致するかどうかを手動で検証するためのメソッドです。このメソッドは、通常、`InsecureSkipVerify` が `true` に設定されている場合など、自動的な証明書検証がスキップされた状況で、アプリケーションレベルでの追加の検証が必要な場合に使用されることがあります。

### `c.verifiedChains` フィールド

`tls.Conn` 構造体内の `verifiedChains` フィールドは、TLSハンドシェイク中に正常に検証された証明書チェーンのリストを格納します。このリストが空でない場合、少なくとも1つの証明書チェーンが信頼できるものとして検証されたことを意味します。このフィールドが空の場合、証明書チェーンの検証が成功しなかったことを示します。

## 技術的詳細

このコミットの技術的な変更は、主に `src/crypto/tls/conn.go` の `VerifyHostname` メソッドと、その動作を検証するための `src/crypto/tls/tls_test.go` の新しいテストケースにあります。

### `src/crypto/tls/conn.go` の変更

`VerifyHostname` メソッドの冒頭に、以下の新しいチェックが追加されました。

```go
	if len(c.verifiedChains) == 0 {
		return errors.New("tls: handshake did not verify certificate chain")
	}
```

このコードは、`c.verifiedChains` スライスが空であるかどうかを確認します。もし空であれば、TLSハンドシェイク中に証明書チェーンの検証が成功しなかったことを意味します。この場合、`VerifyHostname` は直ちにエラーを返し、ホスト名検証の処理を中断します。これにより、未検証の証明書チェーンに対してホスト名検証が実行されることを防ぎます。

この変更のポイントは、`VerifyHostname` が呼び出される前に、`InsecureSkipVerify` が `true` であったり、その他の理由で証明書チェーンの検証が失敗していたりする状況でも、ホスト名検証が実行されてしまうという以前の挙動を修正することです。

### `src/crypto/tls/tls_test.go` の変更

新しいテスト関数 `TestVerifyHostname` が追加され、この修正の動作を検証しています。

1.  **外部ネットワークの利用**: `testenv.MustHaveExternalNetwork(t)` を呼び出すことで、テストが外部ネットワークにアクセスできることを保証しています。これは、実際のTLS接続を確立して検証を行うためです。
2.  **通常の検証ケース**:
    *   `www.google.com` へのTLS接続を確立します。
    *   `c.VerifyHostname("www.google.com")` を呼び出し、正しいホスト名に対してエラーが発生しないことを確認します。
    *   `c.VerifyHostname("www.yahoo.com")` を呼び出し、間違ったホスト名に対してエラーが発生することを確認します。
3.  **`InsecureSkipVerify: true` のケース**:
    *   `InsecureSkipVerify: true` を設定した `tls.Config` を使用して、再度 `www.google.com` へのTLS接続を確立します。この設定では、証明書チェーンの検証はスキップされます。
    *   **重要な点**: `c.VerifyHostname("www.google.com")` を呼び出し、ホスト名が一致しているにもかかわらず、**エラーが発生すること**を確認します。これは、`InsecureSkipVerify` が `true` の場合、`c.verifiedChains` が空になるため、`VerifyHostname` 内の新しいチェックによってエラーが返されることを検証しています。
    *   同様に、`c.VerifyHostname("www.yahoo.com")` を呼び出し、エラーが発生することを確認します。

このテストケースは、`InsecureSkipVerify` が設定されている状況下で、`VerifyHostname` が証明書チェーンの検証状態を適切に考慮するようになったことを明確に示しています。

## コアとなるコードの解説

### `src/crypto/tls/conn.go` の変更点

`VerifyHostname` 関数は、TLSハンドシェイクが完了していることを確認した後、`c.verifiedChains` の長さをチェックするようになりました。`c.verifiedChains` は、TLSハンドシェイク中にサーバーから提示された証明書チェーンが正常に検証された場合にのみ、検証済みのチェーンを格納します。

*   `if len(c.verifiedChains) == 0 { ... }`
    *   この条件は、`verifiedChains` スライスが空であるかどうかをチェックします。
    *   もし空であれば、それは証明書チェーンの検証が成功しなかったことを意味します。これには、`InsecureSkipVerify: true` が設定されている場合や、証明書自体が無効であった場合などが含まれます。
    *   この場合、関数は `errors.New("tls: handshake did not verify certificate chain")` というエラーを返して直ちに終了します。
    *   これにより、証明書チェーンが信頼できない、または検証されていない状態でホスト名検証が続行されることを防ぎ、セキュリティ上の問題を回避します。

この変更により、`VerifyHostname` は、ホスト名の一致だけでなく、その基盤となる証明書の信頼性も考慮するようになり、より堅牢な検証プロセスが実現されました。

### `src/crypto/tls/tls_test.go` の変更点

`TestVerifyHostname` という新しいテスト関数が追加され、このコミットによる修正の動作を検証しています。

*   `testenv.MustHaveExternalNetwork(t)`: この行は、テストが外部ネットワークにアクセスできる環境で実行されていることを保証します。実際のTLS接続を確立して検証を行うため、ネットワーク接続が必要です。
*   **通常のTLS接続と検証**:
    *   `c, err := Dial("tcp", "www.google.com:https", nil)`: `www.google.com` への通常のTLS接続を確立します。この場合、証明書チェーンは正常に検証されることが期待されます。
    *   `if err := c.VerifyHostname("www.google.com"); err != nil { ... }`: 正しいホスト名 (`www.google.com`) を指定して `VerifyHostname` を呼び出し、エラーが発生しないことを確認します。
    *   `if err := c.VerifyHostname("www.yahoo.com"); err == nil { ... }`: 間違ったホスト名 (`www.yahoo.com`) を指定して `VerifyHostname` を呼び出し、ホスト名が一致しないためエラーが発生することを確認します。
*   **`InsecureSkipVerify: true` を使用したTLS接続と検証**:
    *   `c, err = Dial("tcp", "www.google.com:https", &Config{InsecureSkipVerify: true})`: `InsecureSkipVerify: true` を設定した `tls.Config` を使用して、再度 `www.google.com` へのTLS接続を確立します。この設定では、証明書チェーンの検証は意図的にスキップされます。
    *   `if err := c.VerifyHostname("www.google.com"); err == nil { ... }`: **この部分がこのコミットの修正を検証する核心です。** `InsecureSkipVerify` が `true` の場合、`c.verifiedChains` は空になります。したがって、`VerifyHostname` 内の新しいチェックによってエラーが返されることが期待されます。このテストは、ホスト名が一致していても、証明書チェーンが検証されていないために `VerifyHostname` がエラーを返すことを確認しています。
    *   `if err := c.VerifyHostname("www.yahoo.com"); err == nil { ... }`: ホスト名が一致せず、かつ証明書チェーンも検証されていないため、エラーが発生することを確認します。

このテストは、`VerifyHostname` が単にホスト名の一致だけでなく、証明書チェーンの検証状態も考慮するようになったことを明確に示しており、このセキュリティ修正が正しく機能していることを保証します。

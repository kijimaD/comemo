# [インデックス 23796] ファイルの概要

このコミットは、Go言語の標準ライブラリ `archive/zip` パッケージにおいて、ZIPファイルのデータディスクリプタが途中で途切れている（truncated）場合に、`io.EOF` ではなく `io.ErrUnexpectedEOF` を返すように修正するものです。これにより、ZIPファイルの破損や不完全なデータに対するエラーハンドリングがより正確になります。

## 変更の背景

このコミットは、Go言語の `archive/zip` パッケージにおけるバグを修正するために導入されました。以前のバージョンでは、ZIPファイル内のデータディスクリプタが途中で途切れている（つまり、期待されるバイト数よりも少ないバイト数でファイルが終了している）場合、`io.EOF` エラーが返されていました。

しかし、`io.EOF` は通常、入力ストリームの正常な終端を示すものであり、データが不完全であるという異常な状態を示すものではありません。データディスクリプタは固定長または特定の構造を持つため、その読み込み中にストリームが終了することは「予期せぬ終端」と見なされるべきです。この誤ったエラーハンドリングは、ZIPファイルの破損や不完全なダウンロードなど、実際のデータの問題を正確に診断することを困難にしていました。

このコミットは、このシナリオでより適切な `io.ErrUnexpectedEOF` を返すことで、エラーのセマンティクスを改善し、アプリケーションがより正確なエラー処理を行えるようにすることを目的としています。これは、Goの標準ライブラリが提供するエラーの意図に合致し、開発者がより堅牢なコードを書くのに役立ちます。

## 前提知識の解説

### `io.EOF` と `io.ErrUnexpectedEOF`

Go言語の `io` パッケージには、入力ストリームの終端を示す2つの主要なエラー定数があります。

*   **`io.EOF` (End Of File)**:
    これは、読み取り操作が入力ストリームの終端に到達し、それ以上データがないことを示す「正常な」シグナルです。これはエラーというよりも、読み取りが完了したことを示す状態として扱われます。例えば、ファイルを最後まで読み込んだ場合や、ネットワークストリームが正常に閉じられた場合に返されます。通常、ループでデータを読み取る際に、`io.EOF` が返されたら読み取りを終了するという形で利用されます。

*   **`io.ErrUnexpectedEOF` (Unexpected End Of File)**:
    これは、読み取り操作が予期せぬタイミングで入力ストリームの終端に到達したことを示す「エラー」です。具体的には、特定のバイト数や構造化されたデータを期待しているにもかかわらず、その途中でストリームが終了してしまった場合に返されます。これは、データが不完全である、破損している、または途中で切断されたことを意味します。`io.ReadFull` や `io.ReadAtLeast` のような関数は、期待されるバイト数を読み取る前に `io.EOF` に遭遇すると `io.ErrUnexpectedEOF` を返します。

このコミットの文脈では、データディスクリプタという固定長の構造を読み込む際に、その途中でストリームが終了することは `io.ErrUnexpectedEOF` が適切であると判断されました。

### ZIPファイルフォーマットにおけるデータディスクリプタ

ZIPファイルフォーマットは、圧縮されたファイルのエントリに関するメタデータを格納するために、いくつかの構造を使用します。その一つが「データディスクリプタ」です。

*   **データディスクリプタの目的**:
    ZIPファイルを作成する際、特にストリーミングでデータを書き込む場合（例えば、ネットワーク経由でZIPファイルを生成する場合など）、個々のファイルの圧縮データサイズやCRC-32チェックサムは、データがすべて書き込まれるまで確定しません。しかし、ZIPエントリのヘッダ（ローカルファイルヘッダ）は、圧縮データが始まる前にこれらの情報を含んでいる必要があります。
    この問題を解決するために、データディスクリプタが導入されました。ローカルファイルヘッダの「汎用目的ビットフラグ (General Purpose Bit Flag)」のビット3がセットされている場合、ローカルファイルヘッダ内のCRC-32、圧縮サイズ、非圧縮サイズはゼロに設定され、実際の値は圧縮データの直後に続くデータディスクリプタに格納されます。

*   **データディスクリプタの構造**:
    データディスクリプタは通常、以下の情報を格納します。
    *   CRC-32チェックサム (4バイト)
    *   圧縮サイズ (4バイト、ZIP64の場合は8バイト)
    *   非圧縮サイズ (4バイト、ZIP64の場合は8バイト)
    オプションで、`0x08074b50` というシグネチャ（`PK\x07\x08`）が先行することもありますが、これは必須ではありません。

このコミットは、このデータディスクリプタを読み取る際に、期待されるバイト数が読み取られる前にストリームが終了した場合の挙動を修正しています。

## 技術的詳細

`archive/zip` パッケージの `reader.go` 内の `checksumReader` は、ZIPエントリのデータを読み取り、同時にCRC-32チェックサムを計算する役割を担っています。このリーダーは、データディスクリプタが存在する場合、圧縮データの読み取り後にそのディスクリプタを読み取ります。

問題となっていたのは、`readDataDescriptor` 関数がデータディスクリプタを読み取る際に、基となるリーダーから `io.EOF` が返された場合の処理でした。データディスクリプタは固定長の構造であり、特定のバイト数を期待して読み込みます。もし、この期待されるバイト数を読み取る前に `io.EOF` が発生した場合、それはデータディスクリプタが不完全であることを意味します。これは、ZIPファイルが破損しているか、途中で切断されたことを示唆する異常な状態です。

したがって、このような状況で `io.EOF` をそのまま返すのは、エラーの性質を正確に伝えていませんでした。`io.EOF` は正常な終端を意味するため、アプリケーションはデータが完全に読み込まれたと誤解する可能性があります。

このコミットでは、`readDataDescriptor` から返されたエラーが `io.EOF` であった場合に、それを `io.ErrUnexpectedEOF` に変換して返すように変更されました。これにより、呼び出し元はデータディスクリプタが不完全であったことを明確に認識できるようになり、より適切なエラーハンドリング（例えば、ファイル破損として報告するなど）を行うことが可能になります。

この変更は、Goのエラーハンドリングの慣習に沿ったものであり、予期せぬデータ終端は `io.ErrUnexpectedEOF` で示すべきであるという原則に基づいています。

## コアとなるコードの解説

### `src/archive/zip/reader.go` の変更点

`checksumReader` の `Read` メソッド内で、データディスクリプタ (`r.desr`) が存在する場合の処理が変更されています。

元のコード:
```go
			if err1 := readDataDescriptor(r.desr, r.f); err1 != nil {
				err = err1
			}
```
この部分では、`readDataDescriptor` から返されたエラー `err1` がそのまま `err` に代入されていました。

変更後のコード:
```go
			if err1 := readDataDescriptor(r.desr, r.f); err1 != nil {
				if err1 == io.EOF {
					err = io.ErrUnexpectedEOF
				} else {
					err = err1
				}
			}
```
この変更により、`readDataDescriptor` がエラーを返した場合に、そのエラーが `io.EOF` であるかどうかをチェックする条件分岐が追加されました。
*   もし `err1` が `io.EOF` であった場合、それはデータディスクリプタの読み取り中に予期せずストリームが終了したことを意味するため、`err` には `io.ErrUnexpectedEOF` が設定されます。
*   `err1` が `io.EOF` 以外のエラー（例えば、I/Oエラーなど）であった場合は、元のエラー `err1` がそのまま `err` に設定されます。

この修正により、データディスクリプタが不完全な場合に、より正確なエラー情報が呼び出し元に伝達されるようになります。

### `src/archive/zip/reader_test.go` の変更点

`TestIssue11146` という新しいテストケースが追加されました。このテストは、データディスクリプタが途中で途切れている不正なZIPデータを作成し、`archive/zip` パッケージが `io.ErrUnexpectedEOF` を正しく返すことを検証します。

テストのステップ:
1.  `data` 変数に、意図的にデータディスクリプタが不完全なZIPファイルのバイト列を定義します。このバイト列は、ZIPヘッダとファイルデータの一部を含んでいますが、データディスクリプタの途中で終わっています。
2.  `bytes.NewReader` と `NewReader` を使用して、この不正なデータから `zip.Reader` を作成します。
3.  `z.File[0].Open()` で最初のファイルエントリを開きます。
4.  `ioutil.ReadAll(r)` でファイルの内容を読み取ろうとします。この読み取り処理中に、不完全なデータディスクリプタの読み取りが発生し、期待される `io.ErrUnexpectedEOF` が返されるはずです。
5.  返されたエラーが `io.ErrUnexpectedEOF` であることをアサートします。もし異なるエラーが返された場合、テストは失敗します。

このテストの追加は、修正が正しく機能することを確認するだけでなく、将来の回帰を防ぐための重要な安全策となります。

# [インデックス 22806] ファイルの概要

このコミットは、Go言語のコマンドラインツールである`go`コマンドの内部実装に関するものです。具体的には、`go get`コマンドがBitbucket上のプライベートリポジトリを扱う際の挙動を改善するための変更が含まれています。

-   `src/cmd/go/bootstrap.go`: `go`コマンドのブートストラップ（初期起動）に関連するコードが含まれています。このファイルは、`go`コマンドが自身をビルドする際に使用される最小限の機能を提供します。
-   `src/cmd/go/http.go`: `go`コマンドがHTTPリクエストを行うためのユーティリティ関数が含まれています。外部のAPI（この場合はBitbucket API）と通信する際に利用されます。
-   `src/cmd/go/vcs.go`: `go`コマンドが様々なバージョン管理システム（VCS）と連携するためのロジックが含まれています。Git、Mercurial (Hg) など、異なるVCSタイプのリポジトリを扱うための機能が定義されています。

## コミット

`cmd/go`: BitbucketとのAPI呼び出しが失敗した場合に、使用するVCSを検出する。

API呼び出しは、Bitbucketリポジトリがプライベートである場合に失敗します。その場合、`vcsCmd.ping`を使用してリポジトリをプローブします。

Fixes #5375

## 変更の背景

Go言語の`go get`コマンドは、指定されたパスからGoパッケージのソースコードをダウンロードするために使用されます。このコマンドは、リポジトリのホスティングサービス（GitHub, Bitbucketなど）を自動的に検出し、適切なバージョン管理システム（VCS）を使用してコードを取得します。

Bitbucketの場合、`go get`は通常、Bitbucketの公開APIを利用してリポジトリのメタデータ（例えば、使用されているVCSがGitかMercurialかなど）を取得します。しかし、リポジトリがプライベートである場合、このAPI呼び出しは認証なしでは失敗し、HTTP 403 Forbiddenエラーを返します。

この問題が発生すると、`go get`はリポジトリのVCSタイプを特定できず、結果としてプライベートリポジトリからのコード取得に失敗していました。このコミットの目的は、API呼び出しが失敗した場合でも、リポジトリがプライベートである可能性を考慮し、VCSタイプを自動的に検出するフォールバックメカニズムを提供することです。これにより、ユーザーはプライベートBitbucketリポジトリからでも`go get`をよりスムーズに利用できるようになります。

## 前提知識の解説

1.  **`go get`コマンド**: Go言語のビルドツールの一部であり、リモートリポジトリからGoパッケージのソースコードをダウンロードし、依存関係を解決するために使用されます。`go get`は、インポートパスに基づいてリポジトリのホスティングサービスとVCSを自動的に推測します。
2.  **バージョン管理システム (VCS)**: ソースコードの変更履歴を管理するためのシステムです。このコミットでは、主にGitとMercurial (Hg) が関連しています。
    *   **Git**: 分散型VCSのデファクトスタンダード。
    *   **Mercurial (Hg)**: Gitと同様に分散型VCSですが、異なる設計思想を持っています。
3.  **Bitbucket API**: Bitbucketが提供するRESTful APIで、リポジトリ情報、ユーザー情報などをプログラムから取得できます。`go get`は、このAPIを利用してリポジトリのVCSタイプなどのメタデータを取得していました。
4.  **HTTPステータスコード 403 Forbidden**: クライアントがリソースへのアクセスを試みたが、サーバーがそのアクセスを拒否したことを示します。認証情報が不足しているか、権限がない場合に発生します。プライベートリポジトリへのAPIアクセスで認証なしの場合にこのエラーが返されます。
5.  **`vcsCmd.ping`**: `go`コマンドの内部でVCSの存在とリポジトリへのアクセス可能性を確認するために使用されるメカニズムです。例えば、`git ls-remote`や`hg identify`のようなコマンドを内部的に実行し、リポジトリが特定のVCSでアクセス可能かどうかを試行します。この「プローブ」は、API経由でVCSタイプを特定できない場合のフォールバックとして利用されます。
6.  **エラーハンドリングとカスタムエラー型**: Goでは、エラーは`error`インターフェースを実装する型として扱われます。このコミットでは、HTTPエラーの詳細（ステータスコードなど）を保持するためのカスタムエラー型`httpError`が導入されています。これにより、エラーの種類に基づいて異なる処理を行うことが可能になります。

## 技術的詳細

このコミットの主要な変更点は、`go get`コマンドがBitbucketリポジトリのVCSタイプを特定するロジックに、HTTP 403エラー発生時のフォールバックメカニズムを追加したことです。

1.  **`httpError`構造体の導入と利用**:
    *   `src/cmd/go/http.go`に`httpError`という新しい構造体が定義されました。この構造体は、HTTPレスポンスのステータス文字列 (`status`)、ステータスコード (`statusCode`)、およびリクエストURL (`url`) を保持します。
    *   `httpError`は`error`インターフェースを実装しており、`Error()`メソッドを提供します。これにより、標準のエラー処理フローに組み込むことができます。
    *   `httpGET`関数（HTTP GETリクエストを実行する関数）が変更され、HTTPステータスコードが200（OK）以外の場合に、単なる`fmt.Errorf`ではなく、この新しい`httpError`のインスタンスを返すようになりました。これにより、呼び出し元はエラーがHTTPエラーであり、具体的なステータスコードが何であったかをプログラム的に判別できるようになります。
    *   `src/cmd/go/bootstrap.go`にも、ブートストラップ環境での`httpError`のダミー実装が追加されています。これは、ブートストラップ版の`go`コマンドが完全なHTTP機能を持たないため、コンパイルエラーを避けるための措置です。

2.  **`bitbucketVCS`関数でのエラーハンドリングの強化**:
    *   `src/cmd/go/vcs.go`内の`bitbucketVCS`関数は、BitbucketリポジトリのVCSタイプを特定する役割を担っています。
    *   この関数内でBitbucket APIへの`httpGET`呼び出しが行われ、エラーが発生した場合の処理が変更されました。
    *   以前は、API呼び出しが失敗すると単純にエラーを返していました。しかし、変更後は、返されたエラーが`httpError`型であり、かつ`statusCode`が`403`（Forbidden）であるかどうかをチェックするようになりました。
    *   `403`エラーの場合、これはリポジトリがプライベートである可能性が高いと判断されます。この場合、`bitbucketVCS`関数はBitbucket APIからの情報に頼るのではなく、直接VCSをプローブするフォールバックロジックを実行します。

3.  **VCSプローブメカニズム**:
    *   `403`エラーが発生した場合、`bitbucketVCS`は、まずGit (`"git"`)、次にMercurial (`"hg"`) の順に、それぞれのVCSでリポジトリにアクセス可能かどうかを試行します。
    *   これは、`vcsByCmd(vcs).ping("https", root)`という呼び出しによって行われます。`vcsByCmd`はVCSタイプに対応する`vcsCmd`オブジェクトを返し、その`ping`メソッドは指定されたプロトコル（HTTPS）とリポジトリルートURLを使用して、そのVCSがリポジトリを認識できるかどうかを試します。
    *   もし`ping`が成功（エラーを返さない）した場合、そのVCSタイプがリポジトリのSCM (Source Code Management) タイプとして設定され、ループを抜けます。
    *   いずれのVCSでも`ping`が成功しなかった場合、または`httpGET`が`403`以外のエラーを返した場合、元のエラーがそのまま返されます。
    *   API呼び出しが成功した場合は、以前と同様にJSONレスポンスをパースしてVCSタイプを決定します。

この一連の変更により、`go get`はプライベートBitbucketリポジトリに対して、APIが利用できない場合でもVCSタイプを推測し、適切なツール（GitまたはMercurial）を使用してコードを取得できるようになりました。

## コアとなるコードの解説

### `src/cmd/go/http.go` の変更

-   新しい`httpError`構造体が定義され、HTTPステータスコードを含む詳細なエラー情報を提供できるようになりました。
-   `httpGET`関数は、HTTPリクエストが成功しなかった場合（ステータスコードが200以外の場合）に、この`httpError`のインスタンスを返すように変更されました。これにより、呼び出し元はエラーがHTTP関連のものであることを明確に識別し、ステータスコードに基づいて異なる処理を行うことが可能になります。

### `src/cmd/go/vcs.go` の変更

-   `bitbucketVCS`関数は、Bitbucket APIへの`httpGET`呼び出しがエラーを返した場合の処理を強化しました。
-   `if err != nil`ブロック内で、返されたエラーが`httpError`型であり、かつ`statusCode`が`403`（Forbidden）であるかをチェックします。
    -   `httpErr, ok := err.(*httpError)`: これは型アサーションであり、`err`が`*httpError`型に変換可能であれば`httpErr`にその値が代入され、`ok`は`true`になります。
    -   `ok && httpErr.statusCode == 403`: エラーが`httpError`型であり、かつステータスコードが403である場合に、プライベートリポジトリである可能性が高いと判断し、フォールバックロジックに進みます。
-   **フォールバックロジック**:
    -   `root := match["root"]`: リポジトリのルートURLを取得します。
    -   `for _, vcs := range []string{"git", "hg"}`: GitとMercurialの2つの主要なVCSタイプを順番に試します。
    -   `if vcsByCmd(vcs).ping("https", root) == nil`: 各VCSタイプに対して、`ping`メソッドを呼び出します。`ping`メソッドは、そのVCSが指定されたURLのリポジトリにアクセスできるかどうかを試行します。エラーが返されなければ（`nil`であれば）、そのVCSが使用可能であると判断します。
    -   `resp.SCM = vcs`: `ping`が成功したVCSタイプを`resp.SCM`（Source Code Management）フィールドに設定します。
    -   `break`: 適切なVCSが見つかったらループを終了します。
-   `if resp.SCM == ""`: もしVCSが特定できなかった場合（API呼び出しが403以外のエラーを返したか、プローブでもVCSを特定できなかった場合）、元のエラーを返します。
-   `else`ブロック: API呼び出しが成功した場合（エラーが`nil`の場合）、以前と同様にJSONレスポンスをパースしてVCSタイプを決定します。

これらの変更により、`go get`はBitbucketのプライベートリポジトリに対して、APIが直接VCSタイプを教えてくれない場合でも、GitとMercurialを試行することでVCSタイプを自動的に検出し、コードの取得を試みることができるようになりました。

## 元コミット内容

このコミットは、GoコンパイラのSSAバックエンドにおいて、以下の3つの主要な変更を導入しています。

1.  **64ビットシフトの完全な実装**: Go言語の仕様に準拠した64ビット整数に対するシフト演算（左シフト `<<`、符号なし右シフト `>>`、符号あり右シフト `>>`）をAMD64アーキテクチャ向けに正しく実装しました。特に、シフト量がオペランドのビット幅以上の場合の挙動を修正しています。
2.  **複数行リライトルールの許可**: SSAリライトルール定義ファイル (`AMD64.rules`など) で、1つのルールを複数行にわたって記述できるようになりました。これにより、複雑な最適化ルールをより読みやすく、表現力豊かに記述することが可能になります。
3.  **スタックアロケーションにおけるオフセットとアライメントの修正**: スタック上に変数を割り当てる際のオフセット計算とメモリアライメントの処理に存在する問題を修正し、生成されるコードの効率性と正確性を向上させました。

## 変更の背景

このコミットが行われた背景には、GoコンパイラのSSAバックエンドがまだ開発初期段階であり、いくつかの基本的な最適化やアーキテクチャ固有のコード生成において改善の余地があったことが挙げられます。

1.  **64ビットシフトの不正確さ**: 従来のGoコンパイラでは、64ビット整数に対するシフト演算において、シフト量が64以上の場合の挙動がGo言語の仕様と異なる可能性がありました。Go言語の仕様では、シフト量がオペランドのビット幅以上の場合、結果は常にゼロになります。しかし、多くのCPUアーキテクチャ（AMD64を含む）のシフト命令は、シフト量をオペランドのビット幅でマスクする（例: 64ビットレジスタの場合、シフト量を下位6ビットでマスクする）ため、Goの仕様とは異なる結果を生むことがありました。この不一致を解消し、Goのセマンティクスに厳密に準拠したコードを生成する必要がありました。
2.  **リライトルールの表現力不足**: SSAリライトルールは、SSA形式のコードパターンをより効率的なマシンコードパターンに変換するための重要なメカニズムです。しかし、1行でしかルールを記述できないという制約は、複雑な最適化ロジックを表現する上で限界がありました。複数行ルールを導入することで、より高度で読みやすい最適化を記述できるようになります。
3.  **スタックアロケーションのバグ**: スタック上にローカル変数を配置する際、特に構造体や配列などの複合型において、適切なメモリアライメントが保証されない場合がありました。アライメントの不一致は、パフォーマンスの低下や、場合によってはクラッシュなどの未定義動作を引き起こす可能性があります。この問題を修正し、生成されるコードの堅牢性を高める必要がありました。

## 前提知識の解説

### 1. GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木 (AST) に変換した後、中間表現としてSSA (Static Single Assignment) 形式を使用します。SSA形式は、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。SSAバックエンドは、このSSA形式のコードをターゲットアーキテクチャ（この場合はAMD64）の機械語に変換する役割を担います。この変換プロセスには、リライトルールによる最適化やレジスタ割り当て、スタックフレームの構築などが含まれます。

### 2. Go言語のシフト演算の仕様

Go言語の仕様では、シフト演算 `x << y` および `x >> y` について、以下の重要なルールがあります。

*   **シフト量の型**: シフト量 `y` は符号なし整数型であるか、または符号なし整数型に変換可能な型でなければなりません。
*   **シフト量がビット幅以上の場合**: オペランド `x` の型が `T` であり、そのビット幅が `W` であるとき、シフト量 `y` が `W` 以上の場合、シフト演算の結果は常に `0` (ゼロ) になります。これは、すべてのビットがシフトアウトされるためです。
    *   例: `uint64(1) << 64` は `0` になります。
    *   例: `int64(1) >> 64` は `0` になります。
    *   例: `int64(-1) >> 64` は `0` になります (符号拡張されたビットもすべてシフトアウトされるため)。

### 3. AMD64アーキテクチャのシフト命令

AMD64 (x86-64) アーキテクチャには、論理左シフト (SHL)、論理右シフト (SHR)、算術右シフト (SAR) などの命令があります。これらの命令は、シフト量をレジスタ (通常は `CL` レジスタの下位5ビットまたは6ビット) または即値で指定します。

*   **シフト量のマスク**: AMD64のシフト命令は、シフト量がレジスタで指定された場合、そのレジスタの値の下位5ビット (32ビットオペランドの場合) または下位6ビット (64ビットオペランドの場合) のみを使用します。つまり、64ビットオペランドをシフトする場合、シフト量 `N` が `64` であれば `N mod 64 = 0` となり、`SHL QWORD, 0` と解釈され、元の値がそのまま残ってしまいます。これはGoの仕様 (`0` になるべき) とは異なります。
*   **CMOV (Conditional Move) 命令**: `CMOVcc` (Conditional Move if condition `cc` is met) 命令は、特定の条件フラグ (キャリーフラグ、ゼロフラグなど) の状態に基づいて、ソースオペランドをデスティネーションオペランドに移動します。これにより、分岐予測ミスによるペナルティを避けることができ、条件分岐を伴う処理を効率的に実装できます。
*   **SBB (Subtract with Borrow) 命令**: `SBB` 命令は、減算に加えてキャリーフラグ (借用フラグ) の状態も考慮します。`SBBQcarrymask` のようなカスタムオペレーションは、この `SBB` 命令を利用して、キャリーフラグの状態を元にマスク値を生成する目的で使用されます。例えば、`SBBQ R, R` は `R = R - R - CF` となり、`CF=1` なら `-1`、`CF=0` なら `0` を生成します。

### 4. メモリアライメント

メモリアライメントとは、データがメモリ上で特定のバイト境界に配置されることを指します。例えば、8バイトの整数は8バイト境界に配置されるべきです。適切なアライメントは、CPUがメモリにアクセスする際の効率を高め、一部のアーキテクチャではアライメントされていないアクセスがパフォーマンス低下やエラーを引き起こす可能性があります。

## 技術的詳細

### 1. 64ビットシフトの正確な実装

このコミットの最も重要な変更は、Go言語の仕様に準拠した64ビットシフト演算をAMD64アーキテクチャで実現したことです。

*   **問題点**: AMD64の `SHL`, `SHR`, `SAR` 命令は、シフト量が64以上の場合にシフト量を `mod 64` してしまいます。例えば、`x << 64` は `x << 0` となり、`x` がそのまま返されますが、Goの仕様では `0` になるべきです。
*   **解決策**:
    *   **符号なしシフト (`Lsh`, `Rsh` for unsigned)**:
        *   シフト量 `y` が `64` 以上かどうかを `CMPQconst <TypeFlags> [int64(64)] y` で比較します。
        *   この比較結果 (キャリーフラグ) を利用して `SBBQcarrymask` オペレーションを生成します。`SBBQcarrymask` は、キャリーフラグがセットされていれば `int64(-1)` (全ビット1)、クリアされていれば `int64(0)` を返します。
        *   元のシフト演算 (`SHLQ x y` または `SHRQ x y`) の結果と、このマスク値を `ANDQ` 演算で結合します。
        *   これにより、シフト量が64未満の場合は元のシフト結果がそのまま残り、シフト量が64以上の場合はマスク値が `0` となるため、最終結果も `0` になります。
    *   **符号あり右シフト (`Rsh` for signed)**:
        *   Goの仕様では、符号あり右シフトでシフト量がビット幅以上の場合も結果は `0` です。しかし、C言語などでは符号ビットが保持される挙動もあります。Goの仕様に合わせるため、シフト量が `64` 以上の場合、シフト量を `63` にクランプする (`shift = min(shift, 63)`) ようなロジックが導入されました。
        *   これは `CMOVQCC` (Conditional Move if Carry Clear) 命令と `CMPQconst` を組み合わせて実現されます。シフト量 `y` が `64` 以上の場合 (`CMPQconst` でキャリーがセットされる)、`63` を使用し、そうでない場合は `y` をそのまま使用します。

### 2. 複数行リライトルールの許可

`src/cmd/compile/internal/ssa/gen/rulegen.go` の変更により、リライトルールパーサーが複数行にわたるルール定義を正しく処理できるようになりました。

*   **効果**: これにより、`AMD64.rules` の `Lsh` や `Rsh` のような複雑なルールを、より構造化された複数行の形式で記述できるようになり、ルールの可読性と保守性が向上しました。

### 3. スタックアロケーションにおけるオフセットとアライメントの修正

`src/cmd/compile/internal/ssa/stackalloc.go` と `src/cmd/compile/internal/ssa/type.go` の変更により、スタック上の変数アロケーションが改善されました。

*   **問題点**: 以前は、スタック上の変数のオフセット計算において、適切なアライメントが考慮されていませんでした。特に、`v.Type.Align()` のようなアライメント情報を利用する箇所が `TODO` コメントとして残されていました。

    *   `Type` インターフェースに `Alignment()` メソッドが追加され、`TypeImpl` 構造体にも `Align` フィールドが追加されました。これにより、各型の正確なアライメント情報がSSAバックエンドで利用可能になりました。

    *   変数をスタックに割り当てる前に `n = align(n, v.Type.Alignment())` を呼び出すことで、各変数がその型に要求されるアライメント境界に配置されるように修正されました。

## コアとなるコードの解説

### 1. 64ビットシフトの正確な実装 (例: 符号なし左シフト)

`src/cmd/compile/internal/ssa/gen/AMD64.rules` の以下のルールが、Goのシフト仕様を実現する核心部分です。

```
(Lsh <t> x y) && is64BitInt(t) ->
	(ANDQ (SHLQ <t> x y) (SBBQcarrymask <t> (CMPQconst <TypeFlags> [int64(64)] y)))
```

このルールは、GoのSSAオペレーション `Lsh` (左シフト) が64ビット整数 (`is64BitInt(t)`) に適用される場合に発火します。

*   `SHLQ <t> x y`: まず、通常のAMD64の左シフト命令 `SHLQ` を生成します。これは、シフト量 `y` が64以上の場合に `y mod 64` でシフトを実行してしまう可能性があります。
*   `CMPQconst <TypeFlags> [int64(64)] y`: シフト量 `y` が定数 `64` と比較されます。この比較により、CPUのフラグレジスタ (特にキャリーフラグ `CF`) が設定されます。`y >= 64` の場合、キャリーフラグがセットされます。
*   `SBBQcarrymask <t> (...)`: `SBBQcarrymask` は、上記の `CMPQconst` で設定されたキャリーフラグの状態を利用してマスク値を生成するカスタムSSAオペレーションです。
    *   `CF=1` (つまり `y >= 64`) の場合、`SBBQcarrymask` は `int64(-1)` (すべてのビットが1) を生成します。
    *   `CF=0` (つまり `y < 64`) の場合、`SBBQcarrymask` は `int64(0)` を生成します。
    *   **訂正**: `SBBQcarrymask` の実装は `SBBQ R, R` であり、`R = R - R - CF` となります。`CF=1` なら `0 - 0 - 1 = -1`、`CF=0` なら `0 - 0 - 0 = 0` となります。したがって、`y >= 64` の場合に `int64(-1)` (全ビット1) ではなく `0` を生成し、`y < 64` の場合に `0` ではなく `int64(-1)` を生成するはずです。
    *   **再訂正**: `AMD64.rules` のコメント `// mask = shift >= 64 ? 0 : 0xffffffffffffffff` を見ると、`SBBQcarrymask` は `y >= 64` の場合に `0` を、`y < 64` の場合に `0xffffffffffffffff` (つまり `int64(-1)`) を生成することが意図されています。これは `CMPQconst` の結果 (キャリーフラグ) を反転させるか、`SBB` の使い方を工夫することで実現されます。このコミットの `rewriteAMD64.go` の `SBBQcarrymask` の定数畳み込みルールを見ると、`inBounds(d.(int64), c.(int64))` (つまり `d < c`、`y < 64`) の場合に `int64(-1)` を、そうでない場合に `int64(0)` を生成しています。これは意図通りの挙動です。
*   `ANDQ (...) (...)`: 最後に、`SHLQ` の結果と `SBBQcarrymask` で生成されたマスク値を `ANDQ` (ビット論理積) 演算で結合します。
    *   `y < 64` の場合: マスク値は `int64(-1)` なので、`SHLQ` の結果がそのまま残ります。
    *   `y >= 64` の場合: マスク値は `int64(0)` なので、`ANDQ` の結果は `0` になります。

これにより、Goの仕様に完全に準拠した64ビットシフトが実現されます。

### 2. 複数行リライトルール

`src/cmd/compile/internal/ssa/gen/rulegen.go` の `genRules` 関数内の変更は、ルールのパースロジックを改善しています。

```go
	rule := ""
	for scanner.Scan() {
		line := scanner.Text()
		if i := strings.Index(line, "//"); i >= 0 {
			line = line[:i]
		}
		rule += " " + line
		rule = strings.TrimSpace(rule)

			continue
		}
		if !strings.Contains(rule, "->") {
			continue
		}
		if unbalanced(rule) {
			continue
		}
		// ... parse rule ...
		rule = "" // Reset for next rule
	}
```

このコードは、`scanner.Scan()` で1行ずつ読み込んだ内容を `rule` 変数に蓄積していきます。
*   `//` 以降のコメントは削除されます。
*   `rule` が空の場合や、まだ `->` (ルール定義の区切り) が含まれていない場合は、次の行を読み込み続けます。
*   `unbalanced(rule)` 関数が `true` を返す (つまり括弧の数が合わない) 場合も、ルールがまだ完全ではないと判断し、次の行を読み込み続けます。
*   `->` が含まれ、かつ括弧のバランスが取れている場合に、初めて完全なルールとして解析され、`rule` 変数がリセットされます。

これにより、開発者は複雑なルールを複数行に分割して記述できるようになり、ルールの可読性と保守性が大幅に向上しました。

## 変更の背景

2.  **リライトルールの表現力不足**: SSAリライトルールは、SSA形式のコードパターンをより効率的なマシンコードパターンに変換するための重要なメカニズムです。しかし、1行でしかルールを記述できないという制約は、複雑な最適化ロジックを表現する上で限界がありました。複数行ルールを導入することで、より高度で読みやすい最適化を記述できるようになります。

## 前提知識の解説

### 1. GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを抽象構文木 (AST) に変換した後、中間表現としてSSA (Static Single Assignment) 形式を使用します。SSA形式は、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。SSAバックエンドは、このSSA形式のコードをターゲットアーキテクチャ（この場合はAMD64）の機械語に変換する役割を担います。この変換プロセスには、リライトルールによる最適化やレジスタ割り当て、スタックフレームの構築などが含まれます。

### 2. Go言語のシフト演算の仕様

Go言語の仕様では、シフト演算 `x << y` および `x >> y` について、以下の重要なルールがあります。

*   **シフト量の型**: シフト量 `y` は符号なし整数型であるか、または符号なし整数型に変換可能な型でなければなりません。
*   **シフト量がビット幅以上の場合**: オペランド `x` の型が `T` であり、そのビット幅が `W` であるとき、シフト量 `y` が `W` 以上の場合、シフト演算の結果は常に `0` (ゼロ) になります。これは、すべてのビットがシフトアウトされるためです。
    *   例: `uint64(1) << 64` は `0` になります。
    *   例: `int64(1) >> 64` は `0` になります。
    *   例: `int64(-1) >> 64` は `0` になります (符号拡張されたビットもすべてシフトアウトされるため)。

### 3. AMD64アーキテクチャのシフト命令

AMD64 (x86-64) アーキテクチャには、論理左シフト (SHL)、論理右シフト (SHR)、算術右シフト (SAR) などの命令があります。これらの命令は、シフト量をレジスタ (通常は `CL` レジスタの下位5ビットまたは6ビット) または即値で指定します。

*   **シフト量のマスク**: AMD64のシフト命令は、シフト量がレジスタで指定された場合、そのレジスタの値の下位5ビット (32ビットオペランドの場合) または下位6ビット (64ビットオペランドの場合) のみを使用します。つまり、64ビットオペランドをシフトする場合、シフト量 `N` が `64` であれば `N mod 64 = 0` となり、`SHL QWORD, 0` と解釈され、元の値がそのまま残ってしまいます。これはGoの仕様 (`0` になるべき) とは異なります。
*   **CMOV (Conditional Move) 命令**: `CMOVcc` (Conditional Move if condition `cc` is met) 命令は、特定の条件フラグ (キャリーフラグ、ゼロフラグなど) の状態に基づいて、ソースオペランドをデスティネーションオペランドに移動します。これにより、分岐予測ミスによるペナルティを避けることができ、条件分岐を伴う処理を効率的に実装できます。
*   **SBB (Subtract with Borrow) 命令**: `SBB` 命令は、減算に加えてキャリーフラグ (借用フラグ) の状態も考慮します。`SBBQcarrymask` のようなカスタムオペレーションは、この `SBB` 命令を利用して、キャリーフラグの状態を元にマスク値を生成する目的で使用されます。例えば、`SBBQ R, R` は `R = R - R - CF` となり、`CF=1` なら `-1`、`CF=0` なら `0` を生成します。

### 4. メモリアライメント

メモリアライメントとは、データがメモリ上で特定のバイト境界に配置されることを指します。例えば、8バイトの整数は8バイト境界に配置されるべきです。適切なアライメントは、CPUがメモリにアクセスする際の効率を高め、一部のアーキテクチャではアライメントされていないアクセスがパフォーマンス低下やエラーを引き起こす可能性があります。

## 技術的詳細

### 1. 64ビットシフトの正確な実装

このコミットの最も重要な変更は、Go言語の仕様に準拠した64ビットシフト演算をAMD64アーキテクチャで実現したことです。

*   **問題点**: AMD64の `SHL`, `SHR`, `SAR` 命令は、シフト量が64以上の場合にシフト量を `mod 64` してしまいます。例えば、`x << 64` は `x << 0` となり、`x` がそのまま返されますが、Goの仕様では `0` になるべきです。
*   **解決策**:
    *   **符号なしシフト (`Lsh`, `Rsh` for unsigned)**:
        *   シフト量 `y` が `64` 以上かどうかを `CMPQconst <TypeFlags> [int64(64)] y` で比較します。この比較により、CPUのフラグレジスタ (特にキャリーフラグ `CF`) が設定されます。`y >= 64` の場合、キャリーフラグがセットされます。
        *   `SBBQcarrymask` オペレーションは、このキャリーフラグの状態を利用してマスク値を生成します。`y >= 64` の場合に `int64(0)` を、`y < 64` の場合に `int64(-1)` (全ビット1) を生成します。
        *   元のシフト演算 (`SHLQ x y` または `SHRQ x y`) の結果と、このマスク値を `ANDQ` 演算で結合します。
        *   これにより、シフト量が64未満の場合は元のシフト結果がそのまま残り、シフト量が64以上の場合はマスク値が `0` となるため、最終結果も `0` になります。
    *   **符号あり右シフト (`Rsh` for signed)**:
        *   Goの仕様では、符号あり右シフトでシフト量がビット幅以上の場合も結果は `0` です。しかし、C言語などでは符号ビットが保持される挙動もあります。Goの仕様に合わせるため、シフト量が `64` 以上の場合、シフト量を `63` にクランプする (`shift = min(shift, 63)`) ようなロジックが導入されました。
        *   これは `CMOVQCC` (Conditional Move if Carry Clear) 命令と `CMPQconst` を組み合わせて実現されます。シフト量 `y` が `64` 以上の場合 (`CMPQconst` でキャリーがセットされる)、`63` を使用し、そうでない場合は `y` をそのまま使用します。

### 2. 複数行リライトルールの許可

`src/cmd/compile/internal/ssa/gen/rulegen.go` の変更により、リライトルールパーサーが複数行にわたるルール定義を正しく処理できるようになりました。

*   **変更点**: `rulegen.go` の `genRules` 関数内で、行を読み込む際に `rule` 変数に蓄積し、`->` が含まれ、かつ括弧のバランスが取れている場合にのみ1つのルールとして解析するように変更されました。`unbalanced` 関数が追加され、括弧のバランスチェックを行います。
*   **効果**: これにより、`AMD64.rules` の `Lsh` や `Rsh` のような複雑なルールを、より構造化された複数行の形式で記述できるようになり、ルールの可読性と保守性が向上しました。

### 3. スタックアロケーションにおけるオフセットとアライメントの修正

`src/cmd/compile/internal/ssa/stackalloc.go` と `src/cmd/compile/internal/ssa/type.go` の変更により、スタック上の変数アロケーションが改善されました。

*   **問題点**: 以前は、スタック上の変数のオフセット計算において、適切なアライメントが考慮されていませんでした。特に、構造体や配列などの複合型で問題が生じる可能性がありました。
*   **解決策**:
    *   `Type` インターフェースに `Alignment()` メソッドが追加され、`TypeImpl` 構造体にも `Align` フィールドが追加されました。これにより、各型の正確なアライメント情報がSSAバックエンドで利用可能になりました。
    *   `stackalloc.go` の `stackalloc` 関数内で、新しいヘルパー関数 `align(n, a)` が導入されました。これは、現在のオフセット `n` を指定されたアライメント `a` の倍数に切り上げる役割を果たします。
    *   変数をスタックに割り当てる前に `n = align(n, v.Type.Alignment())` を呼び出すことで、各変数がその型に要求されるアライメント境界に配置されるように修正されました。

## コアとなるコードの解説

### 1. 64ビットシフトの正確な実装 (例: 符号なし左シフト)

`src/cmd/compile/internal/ssa/gen/AMD64.rules` の以下のルールが、Goのシフト仕様を実現する核心部分です。

```
(Lsh <t> x y) && is64BitInt(t) ->
	(ANDQ (SHLQ <t> x y) (SBBQcarrymask <t> (CMPQconst <TypeFlags> [int64(64)] y)))
```

このルールは、GoのSSAオペレーション `Lsh` (左シフト) が64ビット整数 (`is64BitInt(t)`) に適用される場合に発火します。

*   `SHLQ <t> x y`: まず、通常のAMD64の左シフト命令 `SHLQ` を生成します。これは、シフト量 `y` が64以上の場合に `y mod 64` でシフトを実行してしまう可能性があります。
*   `CMPQconst <TypeFlags> [int64(64)] y`: シフト量 `y` が定数 `64` と比較されます。この比較により、CPUのフラグレジスタ (特にキャリーフラグ `CF`) が設定されます。`y >= 64` の場合、キャリーフラグがセットされます。
*   `SBBQcarrymask <t> (...)`: `SBBQcarrymask` オペレーションは、上記の `CMPQconst` で設定されたキャリーフラグの状態を利用してマスク値を生成するカスタムSSAオペレーションです。`y >= 64` の場合に `int64(0)` を、`y < 64` の場合に `int64(-1)` (全ビット1) を生成します。
*   `ANDQ (...) (...)`: 最後に、`SHLQ` の結果と `SBBQcarrymask` で生成されたマスク値を `ANDQ` (ビット論理積) 演算で結合します。
    *   `y < 64` の場合: マスク値は `int64(-1)` なので、`SHLQ` の結果がそのまま残ります。
    *   `y >= 64` の場合: マスク値は `int64(0)` なので、`ANDQ` の結果は `0` になります。

これにより、Goの仕様に完全に準拠した64ビットシフトが実現されます。

### 2. 複数行リライトルール

`src/cmd/compile/internal/ssa/gen/rulegen.go` の `genRules` 関数内の変更は、ルールのパースロジックを改善しています。

```go
	rule := ""
	for scanner.Scan() {
		line := scanner.Text()
		if i := strings.Index(line, "//"); i >= 0 {
			line = line[:i]
		}
		rule += " " + line
		rule = strings.TrimSpace(rule)
		if rule == "" {
			continue
		}
		if !strings.Contains(rule, "->") {
			continue
		}
		if unbalanced(rule) {
			continue
		}
		// ... parse rule ...
		rule = "" // Reset for next rule
	}
```

このコードは、`scanner.Scan()` で1行ずつ読み込んだ内容を `rule` 変数に蓄積していきます。
*   `//` 以降のコメントは削除されます。
*   `rule` が空の場合や、まだ `->` (ルール定義の区切り) が含まれていない場合は、次の行を読み込み続けます。
*   `unbalanced(rule)` 関数が `true` を返す (つまり括弧の数が合わない) 場合も、ルールがまだ完全ではないと判断し、次の行を読み込み続けます。
*   `->` が含まれ、かつ括弧のバランスが取れている場合に、初めて完全なルールとして解析され、`rule` 変数がリセットされます。

これにより、開発者は複雑なルールを複数行に分割して記述できるようになり、ルールの可読性と保守性が大幅に向上しました。

### 3. スタックアロケーションのアライメント修正

`src/cmd/compile/internal/ssa/stackalloc.go` の `stackalloc` 関数内の変更は、スタック上の変数配置の正確性を保証します。

```go
func stackalloc(f *Func) {
	// ...
	for _, b := range f.Blocks {
		for _, v := range b.Values {
			// ...
			if v.Type.IsMemory() { // TODO: only "regallocable" types
				continue
			}
			n = align(n, v.Type.Alignment()) // ここでアライメントを適用
			loc := &LocalSlot{n}
			n += v.Type.Size() // アライメント後のオフセットにサイズを加算
			home = setloc(home, v, loc)
			// ...
		}
	}
	// ...
	n = align(n, f.Config.ptrSize) // 関数全体のフレームサイズもアライメント
	n += f.Config.ptrSize // space for return address.  TODO: arch-dependent
	// ...
}

// align increases n to the next multiple of a.  a must be a power of 2.
func align(n int64, a int64) int64 {
	return (n + a - 1) &^ (a - 1)
}
```

*   `v.Type.Alignment()`: 各SSA値 `v` の型が持つアライメント情報を取得します。この情報は `src/cmd/compile/internal/ssa/type.go` で `Type` インターフェースと `TypeImpl` 構造体に追加され、基本型に対して初期化されています。
*   `align(n, v.Type.Alignment())`: 現在のスタックオフセット `n` を、`v` の型が要求するアライメント `v.Type.Alignment()` の倍数に切り上げます。これにより、`v` が常に適切なアライメント境界に配置されることが保証されます。
*   `n += v.Type.Size()`: アライメント調整後のオフセットに `v` のサイズを加算し、次の変数のためのオフセットを計算します。

この修正により、Goコンパイラが生成するコードは、AMD64アーキテクチャのメモリアライメント要件をより正確に満たすようになり、パフォーマンスと安定性が向上します。

## 変更の背景

Goリンカは、プログラムのビルドプロセスにおいて、コンパイルされたオブジェクトファイルやライブラリを結合し、実行可能なバイナリを生成する重要なツールです。このプロセスの中で、リンカはシンボル（関数、変数など）間の依存関係を解決し、到達可能なシンボルを特定する必要があります。この「到達可能なシンボルのマーキング」は、グラフ探索アルゴリズム（幅優先探索や深さ優先探索に似たもの）を用いて行われることが多く、その際にキュー（待ち行列）データ構造が頻繁に利用されます。

以前の実装では、`LSym` 構造体自身が `Queue` というフィールドを持っており、これが次のシンボルへのポインタとして機能することで、シンボルの連結リストをキューとして利用していました。しかし、連結リストは一般的に以下の点でパフォーマンス上の課題を抱えています。

1.  **キャッシュ効率の悪さ**: 連結リストの要素はメモリ上に連続して配置されるとは限りません。そのため、リストを走査する際にCPUキャッシュミスが頻繁に発生し、メモリアクセスが遅くなる可能性があります。
2.  **ポインタのオーバーヘッド**: 各要素が次の要素へのポインタを保持するため、メモリ使用量が増加し、ポインタのデリファレンス（間接参照）にもコストがかかります。
3.  **複雑なキュー操作**: キューの先頭と末尾を管理するために、複数のポインタ（`markq` と `emarkq`）を維持する必要があり、コードが複雑になりがちです。

Goのスライスは、動的配列として実装されており、要素がメモリ上に連続して配置されるという特性を持っています。この特性は、特にリンカのような大量のデータを高速に処理する必要があるシステムにおいて、キャッシュ効率の向上と全体的なパフォーマンス改善に大きく貢献します。この変更は、リンカの効率を向上させるための典型的な最適化の一環として行われました。

## 前提知識の解説

### Goリンカ (`cmd/link`)

Goリンカは、Goプログラムのビルドチェーンの一部であり、コンパイラによって生成されたオブジェクトファイル（`.o` ファイル）を結合して、最終的な実行可能ファイルや共有ライブラリを作成します。その主な役割は以下の通りです。

*   **シンボル解決**: プログラム内の関数や変数の参照を、それらが定義されているメモリ上のアドレスに解決します。
*   **再配置**: コード内のアドレス参照を、最終的な実行可能ファイル内の正しいアドレスに調整します。
*   **デッドコード排除**: 実行時に到達不可能なコードやデータを最終バイナリから除外することで、ファイルサイズを削減します。
*   **実行可能ファイルの生成**: 最終的なバイナリ形式（ELF, Mach-O, PEなど）で出力します。

### `LSym` (Linker Symbol)

`LSym` は "Linker Symbol" の略で、Goリンカが内部で扱うシンボル（関数、グローバル変数、型情報など）を表すデータ構造です。各 `LSym` オブジェクトは、シンボルの名前、型、サイズ、アドレス、関連するデータ（リロケーション情報、デバッグ情報など）といったメタデータを含んでいます。リンカはこれらの `LSym` オブジェクトを操作して、プログラム全体の構造を構築します。

### キュー (Queue) データ構造

キューは、"First-In, First-Out" (FIFO) の原則に従う線形データ構造です。要素は一方の端（「末尾」または「エンキュー側」）に追加され、もう一方の端（「先頭」または「デキュー側」）から削除されます。

*   **連結リストによるキュー**: 各要素がデータと次の要素へのポインタを持つノードで構成されます。エンキューとデキューはO(1)の計算量で行えますが、メモリが連続していないためキャッシュ効率が悪く、ポインタのオーバーヘッドがあります。
*   **配列（スライス）によるキュー**: 配列（Goではスライス）を基盤として実装されます。要素はメモリ上に連続して配置されるため、キャッシュ効率が良いです。
    *   **エンキュー**: スライスの末尾に要素を追加します（`append`）。容量が不足した場合は新しい配列が割り当てられ、要素がコピーされるため、償却O(1)の計算量となります。
    *   **デキュー**: スライスの先頭から要素を削除します。Goでは、`slice = slice[1:]` のようにスライス操作を行うことで、先頭要素を効率的に削除できます。この操作自体はO(1)ですが、ガベージコレクションの観点からは、元の配列の先頭要素が参照されなくなるまでメモリが解放されない可能性がある点に注意が必要です。しかし、リンカの文脈では、キューのサイズが極端に大きくなることは稀であり、このアプローチは十分効率的です。

### Goのスライス

Goのスライスは、配列のセグメントを参照する軽量なデータ構造です。内部的には、ポインタ（基盤となる配列の先頭を指す）、長さ（スライスに含まれる要素の数）、容量（基盤となる配列の最大容量）の3つの要素で構成されます。スライスは動的にサイズを変更でき、`append` 関数を使って要素を追加したり、スライス操作（`a[low:high]`）を使って部分スライスを作成したりできます。メモリの連続性により、CPUキャッシュの恩恵を受けやすく、多くの場面で連結リストよりも高性能を発揮します。

## 技術的詳細

このコミットの技術的詳細な変更点は、Goリンカがシンボルグラフを探索する際に使用する「到達可能シンボルキュー」の実装を根本的に変更したことです。

### 変更前の実装 (`LSym.Queue` を使用した連結リスト)

変更前は、`LSym` 構造体自体に `Queue *LSym` というフィールドが含まれていました。これは、各 `LSym` が次の `LSym` へのポインタを持つことで、シンボルの連結リストを形成していました。

*   `markq *LSym`: キューの先頭を指すグローバル変数。
*   `emarkq *LSym`: キューの末尾を指すグローバル変数。
*   `mark1(s *LSym, parent *LSym)` 関数内で、新しいシンボル `s` をキューに追加する際には、`emarkq.Queue = s` と `emarkq = s` のようにポインタを操作していました。
*   `markflood()` 関数内でキューを処理する際には、`for s := markq; s != nil; s = s.Queue` のように連結リストを走査していました。

この方式は、キューの基本的な操作（追加と削除）がO(1)で可能であるという利点がある一方で、前述の通りキャッシュ効率の悪さやポインタ管理の複雑さという欠点がありました。

### 変更後の実装 (`markQueue []*LSym` を使用したスライス)

変更後は、`LSym` 構造体から `Queue *LSym` フィールドが削除され、代わりに `var markQueue []*LSym` というグローバルなスライスが導入されました。

*   `markQueue []*LSym`: シンボルを格納するスライス。
*   `mark1(s *LSym, parent *LSym)` 関数内で、新しいシンボル `s` をキューに追加する際には、`markQueue = append(markQueue, s)` を使用してスライスの末尾に要素を追加します。これはGoにおいて非常に効率的な操作です。
*   `markflood()` 関数内でキューを処理する際には、`for len(markQueue) > 0` でキューが空になるまでループし、`s := markQueue[0]` で先頭要素を取得し、`markQueue = markQueue[1:]` で先頭要素を削除（デキュー）します。このスライス操作は、新しいスライスヘッダを作成するだけで、基盤となる配列の要素をコピーする必要がないため、非常に高速です。

この変更により、リンカのシンボル探索アルゴリズムは、よりキャッシュフレンドリーなデータ構造を利用できるようになり、特にシンボル数が多い大規模なプログラムのリンク時に、全体的なパフォーマンスが向上することが期待されます。また、ポインタの管理が簡素化され、コードの可読性も向上しています。

## コアとなるコードの解説

### `src/cmd/link/internal/ld/go.go` の変更

1.  **グローバル変数の変更**:
    *   `- var markq *LSym` と `- var emarkq *LSym` が削除されました。これらは連結リストキューの先頭と末尾を管理するためのポインタでした。
    *   `+ var markQueue []*LSym` が追加されました。これは、`LSym` ポインタのスライスであり、新しいキューの実装として機能します。

2.  **`mark1` 関数の変更**:
    *   `mark1` 関数は、シンボル `s` が到達可能であるとマークし、それをキューに追加する役割を担います。
    *   変更前は、`markq` と `emarkq` を使って連結リストの末尾に `s` を追加する複雑なロジックがありました。
    *   変更後は、`+ markQueue = append(markQueue, s)` という簡潔な行に置き換えられました。これは、Goのスライスの `append` 関数を使って、`s` を `markQueue` スライスの末尾に追加します。これにより、コードが大幅に簡素化され、効率も向上します。

3.  **`markflood` 関数の変更**:
    *   `markflood` 関数は、キュー内のすべての到達可能なシンボルを処理し、その依存関係も到達可能としてマークする、リンカの主要な探索アルゴリズムです。
    *   変更前は、`for s := markq; s != nil; s = s.Queue` というループで連結リストを走査していました。
    *   変更後は、`+ for len(markQueue) > 0` というループ条件に変更され、`markQueue` スライスが空になるまで処理を続けます。
    *   ループ内で、`+ s := markQueue[0]` でキューの先頭要素を取得します。
    *   `+ markQueue = markQueue[1:]` で、キューの先頭要素を削除します。これは、スライスを先頭要素の次から再スライスすることで実現され、非常に効率的なデキュー操作です。
    *   また、`var a *Auto` や `var i int` といったループ変数の宣言が、それぞれの `for` ループ内で `for a := s.Autom` や `for i := 0` のようにインライン化されました。これはGoのイディオムに沿った改善であり、変数のスコープを限定し、コードの可読性を高めます。

### `src/cmd/link/internal/ld/link.go` の変更

1.  **`LSym` 構造体の変更**:
    *   `- Queue *LSym` フィールドが `LSym` 構造体から削除されました。これは、`LSym` オブジェクトがもはや連結リストの一部として機能する必要がなくなり、キューの管理が完全に `markQueue` スライスに委譲されたことを意味します。これにより、`LSym` 構造体のメモリフットプリントがわずかに削減され、構造体の目的がより明確になります。

これらの変更は、Goリンカの内部でシンボルを処理するメカニズムを、連結リストからより現代的で効率的なスライスベースのキューへと移行させることで、パフォーマンスと保守性の両面で大きな改善をもたらしています。

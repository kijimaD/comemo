# [インデックス 2306] ファイルの概要

このコミットは、Go言語のツールチェインの一部であるリンカ `5l` の `src/cmd/5l/obj.c` ファイルに対する変更です。`5l` は、Goのソースコードから生成されたオブジェクトファイルをリンクし、実行可能なバイナリを生成する役割を担っています。`obj.c` は、このリンカの主要な処理、特にオブジェクトファイルの読み込み、シンボルの解決、および最終的なバイナリの生成に関連するロジックを含んでいます。

## 変更の背景

このコミットが行われた2009年5月は、Go言語がまだ公開されて間もない、非常に初期の段階でした。当時のGoのビルドシステムやリンカは、現在と比較して未成熟であり、システムライブラリの扱いに課題がありました。

変更の背景には、以下の点が考えられます。

1.  **手動でのライブラリ指定の煩雑さ**: 以前は、Goプログラムが依存するシステムライブラリ（例えば、C言語で書かれた標準ライブラリ `libc` など）をリンクする際に、リンカに対して明示的にパスを指定する必要があった可能性があります。これは、異なるOSやアーキテクチャでビルドを行う際に、手動での設定変更が必要となり、開発者の負担となっていました。
2.  **クロスコンパイルの容易化**: Go言語は設計当初からクロスコンパイルを重要な機能として位置づけていました。異なるターゲット環境（OSとアーキテクチャの組み合わせ）向けのバイナリを生成する際に、システムライブラリのパスを自動的に解決できることは、クロスコンパイルの利便性を大幅に向上させます。
3.  **ビルドプロセスの自動化と堅牢化**: ビルドプロセスにおいて、システムライブラリの検出とリンクを自動化することで、ビルドスクリプトの複雑さを軽減し、環境依存の問題を減らすことができます。これにより、Goプログラムのビルドがより堅牢で再現性の高いものになります。

このコミットは、Go言語の初期段階におけるビルドシステムの改善と、よりポータブルな開発環境の構築に向けた重要な一歩であったと言えます。

## 前提知識の解説

### Go言語のリンカ (5l)

Go言語のビルドプロセスにおいて、リンカは非常に重要な役割を担っています。`5l` は、Goの初期のツールチェインにおけるリンカの一つで、特にPlan 9アーキテクチャの命名規則に由来しています。`5` はARMアーキテクチャ（またはx86アーキテクチャの32ビット版）を指し、`l` はリンカを意味します。

リンカの主な機能は以下の通りです。

*   **オブジェクトファイルの結合**: コンパイラによって生成された複数のオブジェクトファイル（`.o` ファイル）を一つにまとめます。
*   **シンボル解決**: オブジェクトファイル間で参照されている関数や変数のアドレスを解決し、それらがメモリ上のどこに配置されるかを決定します。
*   **ライブラリのリンク**: プログラムが使用する静的ライブラリ（`.a` ファイル）や動的ライブラリ（`.so` や `.dll` ファイル）を結合します。
*   **実行可能ファイルの生成**: 最終的に、OSが実行できる形式のバイナリファイル（実行ファイル）を生成します。

### システムライブラリ

システムライブラリとは、オペレーティングシステムが提供する基本的な機能（ファイルI/O、メモリ管理、ネットワーク通信など）を実装したコードの集合体です。C言語の標準ライブラリである `libc`（Linuxでは `glibc`、macOSでは `libSystem`）がその代表例です。GoプログラムがC言語のコードと連携する場合（Cgoを使用する場合など）、これらのシステムライブラリへのリンクが必要になります。

### Go環境変数 (`goarch`, `goos`, `goroot`)

Go言語のビルドシステムは、いくつかの重要な環境変数に依存しています。

*   **`GOARCH` (Go Architecture)**: ターゲットとするCPUアーキテクチャを指定します。例えば、`amd64` (64ビットx86)、`arm` (ARM)、`arm64` (ARM 64ビット) などがあります。
*   **`GOOS` (Go Operating System)**: ターゲットとするオペレーティングシステムを指定します。例えば、`linux`、`darwin` (macOS)、`windows` などがあります。
*   **`GOROOT`**: Goのインストールディレクトリのパスを指定します。Goの標準ライブラリやツールチェインのバイナリなどがこのディレクトリ以下に配置されています。リンカは、この `GOROOT` を基点として、必要なライブラリやツールを探します。

これらの環境変数を組み合わせることで、Goのビルドシステムは異なるプラットフォーム向けのバイナリを生成するクロスコンパイルを容易に行うことができます。

### `obj.c` と `INITENTRY`

*   **`obj.c`**: 前述の通り、リンカ `5l` の主要なロジックを含むファイルです。オブジェクトファイルの処理、シンボルテーブルの管理、セクションの配置など、リンカの中核的な機能がここに実装されています。
*   **`INITENTRY`**: これは、プログラムの実行開始点（エントリポイント）を示すシンボルです。C言語のプログラムでは通常 `main` 関数がエントリポイントですが、Go言語のプログラムでは、ランタイムの初期化処理を行うための特別なエントリポイントが存在します。このエントリポイントは、OSやアーキテクチャに依存して異なる場合があります。例えば、`_rt0_linux_amd64` のような形式で、Goランタイムの初期化ルーチンを指します。この初期化ルーチンが、Goのスケジューラやガベージコレクタなどをセットアップし、最終的にユーザーが書いた `main` 関数を呼び出します。

## 技術的詳細

このコミットの技術的な核心は、Goリンカ `5l` が、ビルドターゲットのOSとアーキテクチャに基づいて、必要なシステムライブラリとプログラムのエントリポイントを自動的に検出・設定するようになった点です。

具体的な変更点は以下の通りです。

1.  **`compat.h` のインクルード**:
    `#include "compat.h"` が追加されました。このヘッダファイルは、異なるプラットフォーム間での互換性レイヤーを提供し、`mywhatsys()` のようなシステム情報を取得する関数を定義していると考えられます。

2.  **`mywhatsys()` の呼び出し**:
    `main` 関数の初期段階で `mywhatsys()` が呼び出されるようになりました。この関数は、現在のビルドターゲットの `goarch` (アーキテクチャ) と `goos` (OS) の情報を取得し、リンカが利用できるように設定します。これにより、リンカは実行時にこれらの情報を動的に取得できるようになります。

3.  **`INITENTRY` の動的な設定**:
    以前は `INITENTRY` が "_main" や "_mainp" のように固定されていたか、あるいはデバッグフラグによってのみ変更されていました。この変更により、`INITENTRY` は `goarch` と `goos` に基づいて動的に構築されるようになりました。
    具体的には、`_rt0_%s_%s` というフォーマット文字列と、取得した `goarch` および `goos` の値を使って、例えば `_rt0_arm_linux` のようなエントリポイントシンボルが生成されます。これは、Goランタイムが各プラットフォームとアーキテクチャに特化した初期化ルーチンを持っていることを示しています。

4.  **システムライブラリの自動リンク**:
    リンカが `loadlib()` を呼び出した後、`debug['l']` (おそらくライブラリのロードをスキップするデバッグフラグ) が設定されていない場合に、システムライブラリを自動的にリンクする処理が追加されました。
    リンカは `goroot`、`goarch`、`goos` の情報を用いて、`$GOROOT/lib/lib_%s_%s.a` という形式でライブラリのパスを構築します。例えば、`GOROOT` が `/usr/local/go` で、`goarch` が `arm`、`goos` が `linux` の場合、`/usr/local/go/lib/lib_arm_linux.a` というパスのライブラリが自動的に `objfile()` 関数によって読み込まれ、リンクされます。これにより、Goランタイムが依存するプラブラットフォーム固有の静的ライブラリが自動的に含まれるようになります。

これらの変更により、Goのビルドシステムは、ターゲット環境に応じた適切なエントリポイントとシステムライブラリを自動的に選択・リンクできるようになり、開発者が手動でこれらの詳細を管理する必要がなくなりました。これは、Goのクロスコンパイル能力とビルドのポータビリティを大幅に向上させるものです。

## コアとなるコードの解説

### 1. `compat.h` のインクルード

```c
 #include	"l.h"
+#include	"compat.h"
 #include	<ar.h>
```
`compat.h` が新しくインクルードされています。これは、Goのツールチェインが様々なプラットフォームで動作するための互換性レイヤーを提供し、`mywhatsys()` のようなシステム情報を取得する関数を定義していると考えられます。

### 2. `mywhatsys()` の呼び出しとアーキテクチャのチェック

その後の `if(strcmp(goarch, thestring) != 0)` は、取得した `goarch` がリンカが認識しているアーキテクチャと一致するかどうかをチェックしています。`thestring` はおそらく、このリンカがビルドされた際のターゲットアーキテクチャを示す定数でしょう。これにより、リンカが意図しないアーキテクチャのオブジェクトファイルを処理しようとした場合に警告を発することができます。

`INITENTRY` の設定ロジックが大きく変更されました。
変更前は、`INITENTRY` が `0` (NULL) の場合に "_main" または "_mainp" (プロファイリング有効時) に設定されていました。
変更後は、`INITENTRY` が `nil` (NULL) の場合に、`mal` (メモリ確保関数) を使って `goarch` と `goos` の文字列長に基づいたメモリを確保し、`sprint` (文字列フォーマット関数) を使って `_rt0_%s_%s` という形式でエントリポイントのシンボル名を生成しています。
例えば、`goarch` が "amd64" で `goos` が "linux" の場合、`INITENTRY` は `_rt0_amd64_linux` となります。これは、GoランタイムがOSとアーキテクチャに特化した初期化ルーチンを持つことを明確に示しており、リンカがそのルーチンをプログラムのエントリポイントとして参照するように設定します。
`lookup(INITENTRY, 0)->type = SXREF;` は、この `INITENTRY` シンボルが外部参照（`SXREF`）であることをリンカに伝え、リンカがその定義を解決しようとすることを意味します。

### 4. システムライブラリの自動リンク

```c
 	while(*argv)
 		objfile(*argv++);

+\t\ta = mal(strlen(goroot)+strlen(goarch)+strlen(goos)+20);\n+\t\tsprint(a, "%s/lib/lib_%s_%s.a", goroot, goarch, goos);\n+\t\tobjfile(a);\n+\t}\n 	firstp = firstp->link;
```

この部分では、リンカがオブジェクトファイルを処理した後、システムライブラリを自動的にリンクするロジックが追加されています。
変更前は、`debug['l']` (ライブラリのロードをスキップするフラグ) が設定されていない場合に `loadlib()` が呼び出されるだけでした。`loadlib()` は、コマンドラインで指定されたライブラリや、Goの標準ライブラリをロードする役割を担っていたと考えられます。
変更後は、`loadlib()` の呼び出しに加えて、以下の処理が追加されました。
1.  `mal` を使って、`goroot`, `goarch`, `goos` の文字列長に基づいたパスを格納するためのメモリを確保します。
2.  `sprint` を使って、`%s/lib/lib_%s_%s.a` というフォーマットでシステムライブラリのパスを構築します。例えば、`/usr/local/go/lib/lib_amd64_linux.a` のようなパスが生成されます。
3.  構築されたパスを引数として `objfile(a)` を呼び出します。`objfile` 関数は、指定されたパスのオブジェクトファイル（この場合は静的ライブラリ `.a` ファイル）を読み込み、その中のシンボルをリンカのシンボルテーブルに追加し、リンク対象とします。

この一連の処理により、Goのビルドシステムは、ターゲットのOSとアーキテクチャに合わせたGoランタイムの静的ライブラリを自動的に探し出し、リンクするようになりました。これにより、開発者が明示的にこれらのライブラリを指定する必要がなくなり、ビルドのポータビリティと利便性が向上しました。

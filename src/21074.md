## 変更の背景

Go言語のランタイムは、初期の段階ではパフォーマンスやOSとの直接的な連携のために、C言語で書かれた部分が多く存在しました。しかし、C言語で書かれたコードは、Go言語のメモリ安全性、ガベージコレクション、並行処理モデルといった恩恵を直接受けることができません。また、C言語とGo言語が混在するコードベースは、開発の複雑性を増し、保守を困難にする可能性があります。

このコミットの背景には、Goランタイムの大部分をGo言語で記述するというGo開発チームの長期的な目標があります。これにより、以下のようなメリットが期待されます。

*   **可読性と保守性の向上**: Go言語はC言語に比べて、より現代的で表現力豊かな言語であり、Go言語で書かれたランタイムコードは、Go開発者にとって理解しやすく、保守が容易になります。
*   **メモリ安全性の向上**: Go言語の型システムとガベージコレクションは、C言語で頻繁に発生するメモリ関連のバグ（例: dangling pointers, buffer overflows）のリスクを大幅に低減します。
*   **Goの並行処理モデルとの統合**: GoのランタイムはGoルーチンとスケジューラを管理するため、ランタイム自体がGoの並行処理モデルに沿って記述されている方が、より効率的で整合性の取れた設計が可能になります。
*   **クロスプラットフォームの一貫性**: 各OS固有のランタイムコードをGo言語で統一することで、異なるプラットフォーム間でのコードの再利用性が高まり、全体的なコードベースの一貫性が向上します。

特にFreeBSDは、Goがサポートする主要なOSの一つであり、そのランタイムコードをGo化することは、Goエコシステム全体の健全性にとって重要なステップでした。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念について基本的な知識が必要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステム。ガベージコレクション、スケジューラ（Goルーチンの管理）、メモリ割り当て、システムコールインターフェース、シグナルハンドリングなど、Goプログラムが動作するために必要な多くの機能を提供します。Goランタイムの一部は、パフォーマンスやOSとの直接的な連携のために、C言語やアセンブリ言語で書かれていることがあります。
*   **システムコール (System Calls)**: オペレーティングシステムが提供するサービスをプログラムが利用するためのインターフェース。メモリの割り当て（`mmap`）、ファイルの読み書き、プロセスの作成、シグナルの処理など、OSカーネルの機能にアクセスするために使用されます。
*   **`mmap` (Memory Map)**: Unix系OSにおけるシステムコールの一つで、ファイルやデバイス、または匿名メモリ領域をプロセスの仮想アドレス空間にマッピングするために使用されます。メモリ割り当てやファイルI/Oの効率化に利用されます。
*   **`futex` (Fast Userspace Mutex)**: LinuxやFreeBSDなどのUnix系OSで提供される、ユーザー空間での高速な同期プリミティブを実装するためのシステムコール。ミューテックスやセマフォなどのロック機構を効率的に実装するために使用され、競合が少ない場合にはカーネルへの移行を避けることでオーバーヘッドを削減します。FreeBSDでは`umtx_op`として提供されます。
*   **シグナルハンドリング (Signal Handling)**: オペレーティングシステムがプロセスに非同期イベント（例: 割り込み、エラー、終了要求）を通知するメカニズム。プログラムはシグナルを受信し、それに応じた処理（シグナルハンドラ）を実行できます。Goランタイムは、プログラムのクラッシュや割り込みなどの重要なイベントを処理するためにシグナルハンドリングを利用します。
*   **`unsafe.Pointer`**: Go言語における特殊な型で、任意の型のポインタを保持できます。Goの型安全性のルールをバイパスするため、C言語との相互運用や低レベルのメモリ操作に限定して使用されます。Goのガベージコレクタは`unsafe.Pointer`が指すメモリを追跡しないため、誤用するとメモリリークやクラッシュの原因となります。
*   **`uintptr`**: Go言語における整数型で、ポインタを保持するのに十分な大きさを持つ符号なし整数です。`unsafe.Pointer`と同様に、Goの型安全性のルールをバイパスするために使用されますが、`uintptr`自体はポインタではないため、ガベージコレクタは`uintptr`が指すメモリを追跡しません。
*   **Cgo**: Go言語とC言語のコードを相互に呼び出すためのGoのツール。Cgoを使用することで、Goプログラムから既存のCライブラリを呼び出したり、CコードからGo関数を呼び出したりできます。このコミットでは、Cgoを介して呼び出されていたC言語のシステムコールラッパーをGo言語で直接実装し直すことで、Cgoへの依存を減らしています。
*   **OS固有の実装**: Goランタイムは、異なるオペレーティングシステム（Linux, macOS, Windows, FreeBSDなど）の特性に合わせて、一部の機能をOS固有に実装する必要があります。これには、システムコール、メモリ管理、スレッド管理、シグナルハンドリングなどが含まれます。

    *   `src/runtime/signal_freebsd_386.go`、`src/runtime/signal_freebsd_amd64.go`、`src/runtime/signal_freebsd_arm.go`が新しく追加され、各アーキテクチャ（386, amd64, arm）におけるシグナルコンテキスト（レジスタの状態など）をGo言語で操作するための`sigctxt`構造体と関連メソッドが定義されました。これにより、シグナルハンドラ内でレジスタの値を読み書きする処理がGo言語で安全に行えるようになりました。

5.  **`cputicks.go`へのリネームと変更**:
    *   `src/runtime/os_linux_amd64.go`が`src/runtime/cputicks.go`にリネームされ、`cputicks()`関数の定義が移動しました。この関数はCPUのティック数を返すもので、プロファイラや乱数生成のシードとして使用されます。この変更は、`cputicks`が特定のOSに依存するものではなく、より汎用的なランタイム機能であることを示唆しています。

## コアとなるコードの解説

### 型定義の変更 (`defs_freebsd_*.go`)

`thrparam`構造体の変更は、C言語のポインタ表現からGo言語のポインタ表現への移行の典型例です。

*   `start_func unsafe.Pointer` から `start_func uintptr` へ:
    C言語では関数ポインタを`void*`（Goでは`unsafe.Pointer`に相当）で扱うことが一般的ですが、Goでは関数アドレスを`uintptr`として扱うのが慣例です。これは、Goのガベージコレクタが関数アドレスをポインタとして追跡しないため、`unsafe.Pointer`ではなく`uintptr`を使用することで、ガベージコレクタの誤動作を防ぎます。
*   `arg *byte` から `arg unsafe.Pointer` へ:
    汎用的な引数ポインタは、Goでは`unsafe.Pointer`として表現されます。
*   `stack_base *int8` から `stack_base uintptr` へ:
    スタックのベースアドレスも、メモリ上の特定のアドレスを指すため、`uintptr`として扱われます。
*   `child_tid *int32` から `child_tid unsafe.Pointer // *int32` へ:
    `child_tid`はスレッドIDを格納するメモリ領域へのポインタであり、Goでは`unsafe.Pointer`として表現されます。コメントで元の型が示されているのは、Goの型システムでは表現しきれないC言語のセマンティクスを補足するためです。

これらの変更は、GoランタイムがC言語の構造体と直接やり取りするのではなく、Go言語の型システム内でOS固有の構造体を表現し、よりGoらしい方法でメモリやポインタを扱うようにするためのものです。

### メモリ管理のGo化 (`mem_bsd.go`)

`sysAlloc`関数は、OSからメモリを割り当てるためのGo言語による実装です。

```go
//go:nosplit
func sysAlloc(n uintptr, stat *uint64) unsafe.Pointer {
	v := unsafe.Pointer(mmap(nil, n, _PROT_READ|_PROT_WRITE, _MAP_ANON|_MAP_PRIVATE, -1, 0))
	if uintptr(v) < 4096 { // ページサイズ以下の不正なアドレスチェック
		return nil
	}
	xadd64(stat, int64(n)) // 統計情報の更新
	return v
}
```

*   `//go:nosplit`: このディレクティブは、この関数がGoルーチンのスタックを拡張しないことをコンパイラに指示します。ランタイムの低レベルな部分、特にシステムコールを直接呼び出すような場所では、スタックの拡張によるオーバーヘッドを避けるために使用されます。
*   `mmap(nil, n, ...) `: `mmap`システムコールを呼び出して、`n`バイトのメモリを匿名（ファイルに紐づかない）かつプライベート（他のプロセスと共有しない）な領域として割り当てます。`nil`はOSにアドレスの選択を任せることを意味します。
*   `if uintptr(v) < 4096`: `mmap`がエラーを返した場合、通常は`MAP_FAILED`（-1）を返しますが、Goの`unsafe.Pointer`にキャストされると大きな符号なし整数になるため、ここではOSのページサイズ（通常4096バイト）未満のアドレスを不正な戻り値としてチェックしています。
*   `xadd64(stat, int64(n))`: 割り当てられたメモリサイズをランタイムの統計情報に加算します。`xadd64`はアトミックな加算操作を行う関数です。

この`mem_bsd.go`の導入により、GoランタイムはBSD系OSのメモリ管理をGo言語で統一的に扱えるようになり、C言語のコードを排除することで、よりGoのメモリモデルに沿った安全な実装が可能になりました。

### OS固有関数のGo化 (`os1_freebsd.go`)

`futexsleep`関数は、FreeBSDの`umtx_op`システムコールを利用して、Goルーチンが待機状態に入るための実装です。

```go
//go:nosplit
func futexsleep(addr *uint32, val uint32, ns int64) {
	onM(func() { // M (Machine) スレッド上で実行
		futexsleep1(addr, val, ns)
	})
}

func futexsleep1(addr *uint32, val uint32, ns int64) {
	var tsp *timespec
	if ns >= 0 {
		var ts timespec
		ts.tv_nsec = 0
		ts.set_sec(timediv(ns, 1000000000, (*int32)(unsafe.Pointer(&ts.tv_nsec))))
		tsp = &ts
	}
	// umtx_op システムコールを呼び出し
	ret := sys_umtx_op(addr, _UMTX_OP_WAIT_UINT_PRIVATE, val, nil, tsp)
	if ret >= 0 || ret == -_EINTR { // 成功または割り込みの場合
		return
	}
	// エラーハンドリング
	print("umtx_wait addr=", addr, " val=", val, " ret=", ret, "\\n")
	*(*int32)(unsafe.Pointer(uintptr(0x1005))) = 0x1005 // パニックを意図した書き込み
}
```

*   `onM(func() { ... })`: Goランタイムでは、システムコールのようなOSとの直接的なやり取りは、Goスケジューラが管理するM（Machine）スレッド上で行われる必要があります。`onM`は、指定された関数を現在のMスレッド上で実行するためのヘルパー関数です。
*   `sys_umtx_op`: これは、FreeBSDの`umtx_op`システムコールをGoから呼び出すためのラッパー関数です。`_UMTX_OP_WAIT_UINT_PRIVATE`は、指定されたアドレス`addr`の値が`val`と異なるまで待機する操作を示します。`tsp`はタイムアウトを指定するための`timespec`構造体へのポインタです。
*   エラーハンドリング: システムコールの戻り値`ret`をチェックし、成功（`ret >= 0`）または割り込み（`ret == -_EINTR`）の場合は正常終了します。それ以外の場合はエラーメッセージを出力し、意図的にパニックを引き起こすようなメモリ書き込みを行っています。

この`futexsleep`の実装は、GoランタイムがOSの低レベルな同期プリミティブをGo言語で直接制御できるようになったことを示しています。これにより、Cgoを介した間接的な呼び出しが不要になり、ランタイムの効率性とGo言語との統合が向上します。

### システムコールラッパーの宣言変更 (`os_freebsd.go`)

`os_freebsd.go`における`//go:noescape`ディレクティブの追加は、Goコンパイラに対する重要な指示です。

```go
//go:noescape
func thr_new(param *thrparam, size int32)
```

*   `//go:noescape`: このディレクティブは、Goコンパイラに対して、この関数がGoのスタックフレームを持たず、引数がヒープにエスケープしないことを保証します。これは、Goランタイムが直接OSのシステムコールを呼び出す際に使用され、Cgoを介さずにGoのコードから直接アセンブリ言語のスタブを呼び出すことを可能にします。これにより、システムコール呼び出しのオーバーヘッドが削減され、パフォーマンスが向上します。

この変更は、GoランタイムがOSとのインターフェースをより直接的かつ効率的に行うための、低レベルな最適化の一例です。

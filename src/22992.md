## 変更の背景

このコミットの主な目的は、Goコマンドに関する公式ドキュメント（`doc/articles/go_command.html`）に記載されている、Goのビルドシステムとコード生成に関する記述が古くなっていた点を修正することです。特に、`go generate`コマンドが導入されたことにより、Goのソースファイルをビルド前に自動生成する仕組みが提供されました。しかし、既存のドキュメントでは、Goコマンドが「ビルド中にGoソースファイルを生成する機能を持たない」と述べられており、`go generate`の存在が考慮されていませんでした。

この記述は、`go generate`の導入によって誤解を招くものとなっていたため、ドキュメントを最新の状態に保ち、ユーザーがGoのコード生成ツールを適切に理解し利用できるようにするために、この修正が行われました。コミットメッセージにある「Fixes #10489」は、このドキュメントの不正確さを指摘するイシュー（問題報告）に対応するものであることを示唆しています。

## 前提知識の解説

### Goコマンド (`go command`)

Goコマンドは、Go言語のソースコードを管理、ビルド、テスト、実行するための主要なツールです。`go build`、`go run`、`go test`、`go get`など、様々なサブコマンドを提供し、Go開発のワークフローを効率化します。Goコマンドは、依存関係の解決、パッケージの管理、クロスコンパイルなど、多くの複雑なタスクを自動化します。

### `go generate`

`go generate`は、Go 1.4で導入されたコマンドで、Goのソースコードを生成するためのツールです。これは、Goのソースファイル内に特別なコメント（`//go:generate`）を記述することで、そのコメントに続くコマンドを実行し、Goのソースファイルを生成することを可能にします。例えば、`stringer`のようなツールを使って列挙型（enum）の`String()`メソッドを自動生成したり、プロトコルバッファの定義からGoのコードを生成したりする際に利用されます。

`go generate`の重要な点は、**ビルドプロセスの一部ではない**ということです。つまり、`go build`や`go install`を実行しても、`go generate`は自動的に実行されません。開発者は、コード生成が必要な場合に明示的に`go generate`を実行する必要があります。生成されたファイルは、通常、バージョン管理システムにコミットされ、他の開発者がビルドする際に再度生成する必要がないようにします。

### `yacc`

`yacc`（Yet Another Compiler Compiler）は、コンパイラのパーサ部分を生成するためのツールです。文法定義ファイルから、C言語などのソースコードを生成します。Go言語の文脈では、Goのパーサジェネレータ（例: `goyacc`）が`yacc`と同様の機能を提供し、特定の文法を持つファイルを解析するためのGoコードを生成するのに使われることがあります。

### プロトコルバッファコンパイラ (`protocol buffer compiler`)

プロトコルバッファ（Protocol Buffers）は、Googleが開発した、構造化されたデータをシリアライズするための言語ニュートラル、プラットフォームニュートラル、拡張可能なメカニズムです。`.proto`ファイルでデータ構造を定義し、プロトコルバッファコンパイラ（`protoc`）を使って、その定義から様々なプログラミング言語（Goを含む）のソースコードを自動生成します。生成されたコードは、データのシリアライズやデシリアライズを容易にします。

### `GOPATH`

`GOPATH`は、Goのワークスペースのルートディレクトリを指定する環境変数です。Go 1.11でGo Modulesが導入されるまでは、Goのソースコード、パッケージ、実行可能ファイルはすべて`GOPATH`内の特定のディレクトリ構造（`src`、`pkg`、`bin`）に配置される必要がありました。Go Modulesの導入により、`GOPATH`の重要性は低下しましたが、古いプロジェクトや特定のワークフローでは依然として使用されることがあります。

## 技術的詳細

このコミットは、`doc/articles/go_command.html`内の「Limitations」（制限事項）セクションの記述を修正しています。以前の記述では、Goコマンドが「ビルド中にGoソースファイルを生成する機能を持たない」と明確に述べられていました。これは、`go generate`コマンドが導入される前の状況を反映したものでした。

修正後の記述では、この点をより正確に、かつ`go generate`の存在を考慮した形に変更しています。具体的には、以下の点が変更されています。

1.  **「ビルド中に」の強調**: GoコマンドがGoソースファイルを生成する機能を持たないのは「ビルド中（*during* a build）」であるという点が強調されました。これは、`go generate`が「ビルド前（*before* the build）」にコードを生成するツールであることとの対比を明確にするためです。
2.  **`go generate`への言及**: `go generate`コマンドが明示的に言及され、それが`yacc`のようなツールを実行してGoファイルを自動生成できることが説明されました。これにより、Goコマンドがコード生成を全くサポートしないという誤解が解消されます。
3.  **高度なビルド設定に関する記述の修正**: 以前は、`yacc`やプロトコルバッファコンパイラのようなツールを使用する場合、開発者が`makefile`などを作成してGoファイルを生成し、それをリポジトリにコミットする必要があるとされていました。修正後もこの基本的な考え方は変わりませんが、「生成されたソースファイルをリポジトリにチェックインする」という部分がより一般的な表現に修正され、`go generate`の文脈に合うように調整されています。

この変更により、Goのドキュメントは、`go generate`が提供するコード生成のメカニズムを正確に反映し、開発者がGoプロジェクトでコード生成ツールをどのように統合すべきかについて、より明確なガイダンスを提供するようになりました。

## コアとなるコードの解説

変更されたのは、`doc/articles/go_command.html` ファイル内の以下の部分です。

**変更前:**

```html
<p>As mentioned above, the go command is not a general-purpose build
-tool. In particular, it does not have any facility for generating Go
-source files during a build.  Instead, if you want to use a tool like
-yacc or the protocol buffer compiler, you will need to write a
makefile (or a configuration file for the build tool of your choice)
-to generate the Go files and then check those generated source files
into your repository. This is more work for you, the package author,
but it is significantly less work for your users, who can use
"<code>go get</code>" without needing to obtain and build
```

**変更後:**

```html
<p>As mentioned above, the go command is not a general-purpose build
+tool.
+In particular, it does not have any facility for generating Go
+source files <em>during</em> a build, although it does provide
+<a href="/cmd/go/#hdr-Generate_Go_files_by_processing_source"><code>go</code>
+<code>generate</code></a>,
+which can automate the creation of Go files <em>before</em>
+the build, such as by running <code>yacc</code>.
+For more advanced build setups, you may need to write a
makefile (or a configuration file for the build tool of your choice)
+to run whatever tool creates the Go files and then check those generated source files
into your repository. This is more work for you, the package author,
but it is significantly less work for your users, who can use
"<code>go get</code>" without needing to obtain and build
```

具体的な変更点は以下の通りです。

1.  **`tool.` の後に改行と新しい段落の開始**:
    `-tool. In particular, it does not have any facility for generating Go`
    `+tool.`
    `+In particular, it does not have any facility for generating Go`
    これは、文章の区切りを明確にし、続く説明をより読みやすくするための書式変更です。

2.  **`during` の強調と `go generate` の導入**:
    `-source files during a build.  Instead, if you want to use a tool like`
    `+source files <em>during</em> a build, although it does provide`
    `+<a href="/cmd/go/#hdr-Generate_Go_files_by_processing_source"><code>go</code>`
    `+<code>generate</code></a>,`
    `+which can automate the creation of Go files <em>before</em>`
    `+the build, such as by running <code>yacc</code>.`
    ここが最も重要な変更点です。
    *   `during`（ビルド中）という単語が`<em>`タグで強調され、Goコマンドがビルド中にコード生成を行わないという点が明確にされました。
    *   その直後に、`go generate`コマンドが導入され、それが「ビルド前（`<em>before</em>` the build）」にGoファイルを自動生成できることが説明されています。
    *   `go generate`の公式ドキュメントへのリンク（`/cmd/go/#hdr-Generate_Go_files_by_processing_source`）が追加され、ユーザーが詳細情報を参照できるようになりました。
    *   `yacc`が`go generate`の例として挙げられています。

3.  **makefileに関する記述の修正**:
    `-to generate the Go files and then check those generated source files`
    `+to run whatever tool creates the Go files and then check those generated source files`
    以前は「Goファイルを生成するために」makefileを使うと書かれていましたが、より汎用的に「Goファイルを作成するあらゆるツールを実行するために」makefileを使うという表現に修正されました。これは、`go generate`がその「あらゆるツール」の一つであるという文脈に合致させるためです。生成されたファイルをリポジトリにチェックインするという推奨事項は変わりません。

これらの変更により、ドキュメントは`go generate`の存在を認識し、Goのビルドプロセスにおけるコード生成の役割について、より正確で最新の情報を提供するようになりました。

# [インデックス 21692] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）とランタイム（`runtime`）における文字列のメモリ割り当て戦略を最適化するものです。特に、エスケープ解析を拡張し、ヒープではなくスタックに一時的な文字列バッファを割り当てることで、ガベージコレクションの負荷を軽減し、パフォーマンスを向上させます。

## 変更の背景

Go言語では、文字列は不変（immutable）なバイトスライスとして実装されています。これまでのGoコンパイラでは、`[]byte`から`string`への変換や文字列の結合といった操作によって生成される一時的な文字列バッファは、常にヒープに割り当てられていました。

例えば、`if string(byteSlice) == "abc" { ... }` のようなコードでは、`byteSlice`を`string`に変換する際に一時的な文字列が生成され、これがヒープに割り当てられていました。このような一時的なオブジェクトが頻繁に生成されると、ガベージコレクタが頻繁に動作する必要があり、アプリケーションのパフォーマンスに悪影響を与える可能性がありました。特に、短命で小さな文字列が大量に生成されるようなケースでは、ヒープ割り当てとそれに伴うGCのオーバーヘッドが無視できない問題となっていました。

このコミットの目的は、このような一時的な文字列のヒープ割り当てを減らし、可能であればスタックに割り当てることで、メモリ使用量を最適化し、ガベージコレクションの頻度と実行時間を削減し、全体的なパフォーマンスを向上させることにあります。

## 前提知識の解説

### エスケープ解析 (Escape Analysis)

エスケープ解析は、コンパイラ最適化の一種で、変数がその宣言されたスコープ（通常は関数）の外に「エスケープ」するかどうかを決定します。

*   **スタック割り当て (Stack Allocation)**: 変数が関数スコープ内で完結し、関数の実行が終了すると不要になることがコンパイラによって保証される場合、その変数はスタックに割り当てられます。スタックはLIFO（後入れ先出し）構造で、メモリの割り当てと解放が非常に高速であり、ガベージコレクションの対象外となるため、パフォーマンスに優れています。
*   **ヒープ割り当て (Heap Allocation)**: 変数が関数スコープを超えて存続する必要がある場合（例: 関数の戻り値として返される、グローバル変数に格納される、別のゴルーチンに渡されるなど）、その変数はヒープに割り当てられます。ヒープは動的にメモリを管理し、ガベージコレクタによって不要になったメモリが回収されます。ヒープ割り当てはスタック割り当てよりもオーバーヘッドが大きく、GCの対象となるため、パフォーマンスに影響を与える可能性があります。

Goコンパイラは、プログラムのコンパイル時にエスケープ解析を実行し、どの変数をスタックに、どの変数をヒープに割り当てるかを決定します。

### Goにおける文字列 (Strings in Go)

Goの文字列は、バイトの不変シーケンスです。内部的には、文字列はポインタと長さのペアとして表現されます。文字列の内容は通常、ヒープに格納されます。文字列は不変であるため、文字列の結合や部分文字列の抽出などの操作は、新しい文字列を生成し、その内容を新しいメモリ領域にコピーすることを意味します。

このコミットは、特に`[]byte`から`string`への変換や文字列結合といった、一時的な文字列が生成されやすい操作に焦点を当てています。

## 技術的詳細

このコミットの核心は、Goコンパイラのエスケープ解析を拡張し、`[]byte`から`string`への変換（`OARRAYBYTESTR`）と文字列結合（`OADDSTR`）の結果が関数スコープからエスケープしない場合に、ヒープではなくスタックに小さなバッファを割り当てるようにすることです。

1.  **エスケープ解析の拡張**:
    *   `src/cmd/gc/esc.c`が変更され、`OARRAYBYTESTR`と`OADDSTR`ノードがエスケープ解析の対象となります。これらの操作の結果がエスケープしないと判断された場合、`EscNone`としてマークされます。
    *   これにより、コンパイラはこれらの操作によって生成される一時的な文字列が、関数の実行が終了するまでに不要になることを認識できるようになります。

2.  **スタックバッファの導入**:
    *   コンパイラは、エスケープしない文字列操作のために、32バイトの固定サイズのバッファをスタック上に割り当てます。このサイズ（`tmpStringBufSize`）は、`src/cmd/gc/walk.c`と`src/runtime/string.go`で定義されています。
    *   この32バイトというサイズは、標準ライブラリのテストやベンチマークの観察に基づいています。文字列の割り当て頻度が文字列長に反比例し、長さ32バイトまでの文字列の割り当てが非常に多いという傾向があるため、このサイズが選ばれました。

3.  **ランタイム関数の変更**:
    *   `src/cmd/gc/builtin.c`と`src/cmd/gc/runtime.go`で、`concatstringX`（文字列結合）および`slicebytetostring`（バイトスライスから文字列への変換）のランタイム関数のシグネチャが変更されました。これらの関数は、新しく追加された`*[32]byte`型の引数（スタックバッファへのポインタ）を受け取るようになりました。
    *   `src/runtime/string.go`では、`concatstrings`と`slicebytetostring`の実装が更新され、このスタックバッファが渡された場合に、そのバッファに結果の文字列を格納しようと試みます。文字列がバッファのサイズに収まる場合、ヒープ割り当てを回避できます。
    *   `rawstringtmp`という新しいヘルパー関数が導入され、スタックバッファが利用可能な場合にそれを使用し、そうでない場合は通常のヒープ割り当て（`rawstring`）にフォールバックします。
    *   `stringDataOnStack`という関数も追加され、文字列のデータが現在のゴルーチンのスタック上にあるかどうかを報告します。これは、`concatstrings`が単一の文字列を返す際に、その文字列が既にスタック上にある場合にコピーを避けるための最適化に利用されます。

4.  **コンパイラのコード生成ロジックの変更**:
    *   `src/cmd/gc/walk.c`では、`OARRAYBYTESTR`と`OADDSTR`のノードを処理する際に、エスケープ解析の結果（`n->esc == EscNone`）に基づいて、スタックバッファを割り当てるコードを生成するようになりました。
    *   文字列結合の場合、結合後の文字列の合計サイズが`tmpstringbufsize`未満である場合にのみ、スタックバッファが使用されます。

この変更により、短命で小さな文字列の生成において、ヒープ割り当てが大幅に削減され、ガベージコレクションの負担が軽減されます。コミットメッセージに示されているベンチマーク結果は、この最適化が実際に割り当て数を減らし、一部のケースでは実行時間も改善していることを裏付けています。

## コアとなるコードの解説

このコミットの主要な変更は、コンパイラが文字列操作の際にスタックバッファをランタイム関数に「ヒント」として渡すメカニズムを導入した点にあります。

### `src/cmd/gc/walk.c` の変更

`walk.c`は、GoのAST（抽象構文木）を走査し、コード生成を行うコンパイラの重要な部分です。
このコミットでは、`OARRAYBYTESTR`（`string(b)`のようなバイトスライスから文字列への変換）と`OADDSTR`（`s1 + s2`のような文字列結合）の処理が変更されました。

```c
// src/cmd/gc/walk.c
enum
{
	tmpstringbufsize = 32,
};

// OARRAYBYTESTR の処理
case OARRAYBYTESTR:
	a = nodnil();
	if(n->esc == EscNone) { // エスケープしない場合
		// スタックに文字列用の一時バッファを作成
		t = aindex(nodintconst(tmpstringbufsize), types[TUINT8]);
		a = nod(OADDR, temp(t), N); // バッファのアドレスを取得
	}
	// slicebytetostring(*[32]byte, []byte) string;
	n = mkcall("slicebytetostring", n->type, init, a, n->left); // バッファを引数として渡す
	goto ret;

// OADDSTR の処理 (簡略化)
static Node*
addstr(Node *n, NodeList **init)
{
	// ...
	buf = nodnil();
	if(n->esc == EscNone) { // エスケープしない場合
		sz = 0;
		for(l=n->list; l != nil; l=l->next) {
			if(n->op == OLITERAL)
				sz += n->val.u.sval->len;
		}
		// 結果がバッファに収まる場合のみバッファを割り当てる
		if(sz < tmpstringbufsize) {
			// スタックに結果文字列用の一時バッファを作成
			t = aindex(nodintconst(tmpstringbufsize), types[TUINT8]);
			buf = nod(OADDR, temp(t), N);
		}
	}
	// ...
	// concatstrings(*[32]byte, []string) string; のような形で buf を最初の引数として渡す
	args = list1(buf);
	// ...
}
```
コンパイラは、エスケープ解析の結果（`n->esc == EscNone`）に基づいて、スタック上に`tmpstringbufsize`（32バイト）のバイト配列を割り当て、そのアドレスを`slicebytetostring`や`concatstrings`といったランタイム関数に渡すようにコードを生成します。文字列結合の場合、結合後の文字列の合計長が32バイト未満の場合にのみ、この最適化が適用されます。

### `src/runtime/string.go` の変更

`string.go`はGoランタイムにおける文字列操作の核心部分です。

```go
// src/runtime/string.go

const tmpStringBufSize = 32

type tmpBuf [tmpStringBufSize]byte

// concatstrings implements a Go string concatenation x+y+z+...
// The operands are passed in the slice a.
// If buf != nil, the compiler has determined that the result does not
// escape the calling function, so the string data can be stored in buf
// if small enough.
func concatstrings(buf *tmpBuf, a []string) string {
	// ... (長さ計算ロジック) ...

	// If there is just one string and either it is not on the stack
	// or our result does not escape the calling frame (buf != nil),
	// then we can return that string directly.
	if count == 1 && (buf != nil || !stringDataOnStack(a[idx])) {
		return a[idx]
	}
	s, b := rawstringtmp(buf, l) // rawstringtmp を使用
	// ... (文字列のコピーロジック) ...
	return s
}

// Buf is a fixed-size buffer for the result,
// it is not nil if the result does not escape.
func slicebytetostring(buf *tmpBuf, b []byte) string {
	// ... (長さチェック、raceenabledチェック) ...
	s, c := rawstringtmp(buf, l) // rawstringtmp を使用
	copy(c, b)
	return s
}

// stringDataOnStack reports whether the string's data is
// stored on the current goroutine's stack.
func stringDataOnStack(s string) bool {
	ptr := uintptr((*stringStruct)(unsafe.Pointer(&s)).str)
	stk := getg().stack
	return stk.lo <= ptr && ptr < stk.hi
}

func rawstringtmp(buf *tmpBuf, l int) (s string, b []byte) {
	if buf != nil && l <= len(buf) { // バッファが提供され、かつ収まる場合
		b = buf[:l] // バッファのスライスを取得
		s = slicebytetostringtmp(b) // バッファを直接文字列として使用
	} else {
		s, b = rawstring(l) // 通常のヒープ割り当て
	}
	return
}
```
`concatstrings`と`slicebytetostring`は、コンパイラから渡された`buf *tmpBuf`引数を受け取るようになりました。この`buf`が`nil`でなく、かつ結果の文字列が`tmpStringBufSize`（32バイト）に収まる場合、`rawstringtmp`関数を通じて、ヒープ割り当てをせずにスタック上のバッファを直接利用します。これにより、一時的な文字列の生成に伴うヒープ割り当てとガベージコレクションのオーバーヘッドが削減されます。

`stringDataOnStack`は、単一の文字列結合の場合に、元の文字列が既にスタック上にあるかどうかを判断し、不要なコピーを避けるためのさらなる最適化に貢献します。

これらの変更により、Goプログラムは、特に短く一時的な文字列操作において、より効率的なメモリ管理と高速な実行を実現できるようになりました。

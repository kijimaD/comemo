## 変更の背景

このコミットの主な背景は、Goランタイムのガベージコレクタ (GC) とスタック管理のデバッグおよびチューニング能力を向上させることにあります。GoのGCは、バージョン1.5以降、並行GC（Concurrent GC）へと大きく進化し、アプリケーションの一時停止時間（Stop-The-World, STW）を大幅に削減しました。しかし、このような複雑なシステムでは、特定の条件下での挙動を詳細に分析したり、パフォーマンスボトルネックを特定したりするために、よりきめ細やかな制御が必要となることがあります。

具体的には、以下のニーズが考えられます。

1.  **スタック縮小の制御**: Goのランタイムは、ゴルーチンのスタックが過剰に大きくなった場合に、そのサイズを縮小する最適化を行います。しかし、この挙動が特定のバグを引き起こしたり、パフォーマンス特性に影響を与えたりする可能性があり、その影響を調査するためにスタック縮小を一時的に無効にする機能が求められました。
2.  **GCスタックバリアの制御**: 並行GCでは、GCが実行されている最中にアプリケーションがスタックを変更する可能性があるため、「スタックバリア」と呼ばれるメカニズムを使用して、GCがスタックを正確にスキャンできるようにします。このバリアの挙動を無効にすることで、そのオーバーヘッドや、バリアがない場合のGCの正確性への影響を評価できます。
3.  **並行GCの無効化**: Goの並行GCは多くのアプリケーションで優れたパフォーマンスを発揮しますが、特定のワークロードやデバッグシナリオでは、従来のSTW GCの挙動と比較したい場合があります。`gcstoptheworld`変数は、並行GCを無効にし、すべてのGCをSTWイベントとして実行することで、この比較を可能にします。これは、並行GCの導入によって解決された問題や、並行GCがもたらす新たな課題を理解する上で非常に有用です。

これらの変数は、Goランタイムの開発者や、Goアプリケーションのパフォーマンスを深く分析するユーザーにとって、貴重なデバッグツールとなります。また、既存の`GODEBUG`変数のドキュメントを整理し、効果のない変数を削除することで、ランタイムコードの保守性と可読性も向上させています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念について基本的な知識が必要です。

### 1. Goのガベージコレクタ (GC)

Goのガベージコレクタは、メモリ管理を自動化し、開発者が手動でメモリを解放する手間を省きます。Go 1.5以降、GoのGCは「並行マーク＆スイープ（Concurrent Mark and Sweep）」アルゴリズムをベースにしており、アプリケーションの実行と並行してGCの大部分の処理を進めることで、アプリケーションの一時停止時間（Stop-The-World, STW）を最小限に抑えることを目指しています。

*   **Stop-The-World (STW)**: GCのフェーズの一部で、アプリケーションのすべてのゴルーチンが一時的に停止される期間を指します。この期間中、アプリケーションは一切処理を進めることができません。Goの並行GCは、このSTW時間を極力短くするように設計されています。
*   **並行マークフェーズ**: GCがアプリケーションと並行して、到達可能なオブジェクトをマークするフェーズです。
*   **マークターミネーションフェーズ**: 並行マークフェーズの終わりに発生する短いSTWフェーズで、マーク処理を完了させます。
*   **並行スイープフェーズ**: マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放するフェーズで、これもアプリケーションと並行して行われます。

### 2. ゴルーチンのスタック管理

Goのゴルーチンは、非常に軽量なスレッドのようなもので、数KBの小さなスタックから開始し、必要に応じて動的にスタックサイズを増減させます。

*   **スタックの成長 (Stack Growth)**: ゴルーチンが関数呼び出しを深くネストするなどしてスタック領域が不足しそうになると、ランタイムはより大きなスタックを割り当て、既存のスタックの内容を新しいスタックにコピーします。
*   **スタックの縮小 (Stack Shrinking)**: ゴルーチンが多くのスタック領域を消費した後、その領域が不要になった場合（例えば、深い関数呼び出しから戻った場合）、ランタイムはスタックをより小さなサイズに縮小してメモリを解放することがあります。これはメモリ効率を高めるための最適化です。

### 3. GCスタックバリア (GC Stack Barriers)

並行GCの文脈では、GCがスタックをスキャンしている最中に、アプリケーションのゴルーチンがスタック上のポインタを変更する可能性があります。このような競合状態を防ぎ、GCが常に正確なポインタ情報を参照できるようにするために、「スタックバリア」が導入されています。スタックバリアは、スタック上のポインタが書き換えられる際にGCに通知する、あるいはGCがスタックをスキャンする際に特定の処理を挟むことで、ポインタの変更をGCが追跡できるようにするメカニズムです。これにより、GCは並行実行中でもオブジェクトの到達可能性を正確に判断できます。

### 4. `GODEBUG`環境変数

`GODEBUG`は、Goランタイムのデバッグや挙動の調整に使用される環境変数です。`name=val`の形式でカンマ区切りのリストとして設定され、ランタイムの内部動作に影響を与える様々なフラグを有効にしたり、パラメータを設定したりできます。例えば、`gctrace=1`を設定すると、GCの実行状況に関する詳細なログが出力されます。

## 技術的詳細

このコミットは、Goランタイムの`GODEBUG`メカニズムを拡張し、GCとスタック管理の特定の側面を制御するための新しいデバッグ変数を導入しています。これらの変数は、ランタイムの内部構造に深く関わっており、その動作を理解することで、Goアプリケーションのパフォーマンス特性やメモリ使用量をより深く分析できます。

### 1. `gcshrinkstackoff`

*   **目的**: ゴルーチンのスタック縮小機能を無効にします。
*   **技術的詳細**: Goランタイムは、ゴルーチンのスタックが過剰に大きくなった後、そのスタックが不要になった場合に、より小さなスタックにコピーしてメモリを解放する「スタック縮小」を行います。`gcshrinkstackoff=1`を設定すると、この最適化が無効になります。つまり、ゴルーチンのスタックは一度大きくなると、その後は縮小されず、常に最大サイズを維持します。
*   **影響**:
    *   **メモリ使用量**: スタック縮小が無効になるため、アプリケーションのメモリ使用量が増加する可能性があります。特に、多くのゴルーチンが一時的に大きなスタックを必要とするようなアプリケーションでは顕著です。
    *   **パフォーマンス**: スタック縮小に伴うコピー処理のオーバーヘッドがなくなるため、一部のシナリオではわずかにパフォーマンスが向上する可能性があります。しかし、メモリ使用量の増加がGCの頻度や期間に影響を与え、全体的なパフォーマンスを低下させる可能性もあります。
    *   **デバッグ**: スタック縮小が原因で発生する可能性のあるバグ（例えば、スタックの移動に伴うポインタの無効化など）を特定するのに役立ちます。

### 2. `gcstackbarrieroff`

*   **目的**: GCスタックバリアを無効にします。
*   **技術的詳細**: Goの並行GCでは、GCがスタックをスキャンしている最中に、アプリケーションのゴルーチンがスタック上のポインタを書き換える可能性があります。これを防ぐために、ランタイムは「スタックバリア」と呼ばれるメカニズムを使用します。`gcstackbarrieroff=1`を設定すると、このスタックバリアが無効になります。これにより、GCはスタックをスキャンする際にポインタの変更を追跡できなくなり、GCの正確性に影響を与える可能性があります。
*   **影響**:
    *   **GCの正確性**: スタックバリアが無効になると、GCがスタック上のポインタを正確に追跡できなくなり、到達可能なオブジェクトが誤ってガベージとして収集される（Use-After-Freeのような）深刻なバグを引き起こす可能性があります。これは非常に危険な設定であり、通常はデバッグ目的でのみ使用されます。
    *   **パフォーマンス**: スタックバリアのオーバーヘッドがなくなるため、理論的にはわずかにパフォーマンスが向上する可能性があります。しかし、そのリスクは非常に大きいです。
    *   **デバッグ**: スタックバリアの挙動や、それがGCの正確性およびパフォーマンスに与える影響を深く理解するための実験的なツールとして使用されます。

### 3. `gcstoptheworld`

*   **目的**: 並行GCを無効にし、GCをSTWイベントとして強制します。
*   **技術的詳細**: GoのGCは通常、アプリケーションと並行して動作しますが、`gcstoptheworld`変数はこの挙動を変更します。
    *   `gcstoptheworld=1`: 並行GCを無効にし、すべてのGCをSTWイベントとして実行します。GCのマークフェーズ全体がSTW期間中に実行されます。スイープフェーズは並行して行われます。
    *   `gcstoptheworld=2`: `gcstoptheworld=1`と同様に並行GCを無効にし、さらにGC終了後の並行スイープも無効にします。つまり、GCのすべてのフェーズがSTW期間中に実行されます。
*   **影響**:
    *   **アプリケーションの一時停止時間 (STW)**: 並行GCが無効になるため、GC実行中のアプリケーションの一時停止時間が大幅に増加します。これは、Go 1.5以前のGCの挙動に近くなります。
    *   **デバッグと分析**: 並行GCの導入によって得られたパフォーマンス上の利点を定量的に評価したり、並行GCが特定のアプリケーションの挙動に与える影響を理解したりするのに役立ちます。例えば、並行GCが有効な場合と無効な場合で、アプリケーションのスループットやレイテンシがどのように変化するかを比較できます。
    *   **GCのオーバーヘッド**: 並行GCの複雑さや同期メカニズムに伴うオーバーヘッドを、純粋なSTW GCと比較することで分析できます。

### ドキュメントの更新と変数の削除

このコミットでは、`src/runtime/extern.go`内の`GODEBUG`変数のドキュメントも更新されています。これにより、新しい変数の説明が追加され、既存の変数の説明が整理されています。また、`gcdead`のように効果のない変数が削除されており、これはコードベースのクリーンアップと保守性の向上に貢献しています。`gcdead`は、GCが死んだスタックスロットを上書きするデバッグ機能でしたが、おそらくその効果が限定的であったり、他のデバッグツールで代替可能であったりしたため、削除されたと考えられます。

## コアとなるコードの解説

### `src/runtime/runtime1.go` と `src/runtime/extern.go`

これらのファイルは、新しい`GODEBUG`変数をランタイムに登録し、そのドキュメントを提供します。

*   `src/runtime/runtime1.go`では、`debug`構造体に`gcshrinkstackoff`、`gcstackbarrieroff`、`gcstoptheworld`という3つの新しい`int32`フィールドが追加されます。この`debug`構造体は、`GODEBUG`環境変数から設定されるすべてのデバッグフラグを保持します。また、`dbgVar`配列も更新され、これらの新しいフィールドが`GODEBUG`パーサーによって認識されるようにマッピングされます。
*   `src/runtime/extern.go`は、`GODEBUG`変数の公式ドキュメントを提供します。このコミットでは、新しい3つの変数の目的と挙動が詳細に記述されています。また、`gcdead`のような効果のない変数の説明が削除され、ドキュメントが整理されています。

### `src/runtime/mgc.go` (`gcstoptheworld`の制御)

`startGC`関数は、GCサイクルを開始する主要なエントリポイントの一つです。この関数内で、`debug.gcstoptheworld`変数の値がチェックされます。

```go
if debug.gcstoptheworld == 1 {
    mode = gcForceMode
} else if debug.gcstoptheworld == 2 {
    mode = gcForceBlockMode
}
```

*   `gcForceMode`: このモードが設定されると、GCは並行処理を行わず、すべてのマークフェーズをSTW期間中に実行します。スイープフェーズは並行して行われます。
*   `gcForceBlockMode`: このモードが設定されると、GCのマークフェーズだけでなく、スイープフェーズもSTW期間中に実行されます。これは、GCのすべての処理がアプリケーションを完全に停止させて行われることを意味します。

この変更により、`GODEBUG=gcstoptheworld=1`または`GODEBUG=gcstoptheworld=2`を設定することで、開発者はGoの並行GCを無効にし、従来のSTW GCの挙動を強制できるようになります。これは、並行GCのパフォーマンス上の利点を評価したり、特定のGC関連のバグをデバッグしたりする際に非常に有用です。

### `src/runtime/mgcmark.go` (`gcstackbarrieroff`の制御)

`scanstack`関数は、GCがゴルーチンのスタックをスキャンする際に呼び出されます。この関数内で、スタックバリアの挙動を制御するロジックが追加されています。

```go
if debug.gcstackbarrieroff > 0 {
    nextBarrier = ^uintptr(0)
}
```

通常、`nextBarrier`は次のスタックバリアの位置を示し、GCがスタックをスキャンする際にその位置で特別な処理を行います。しかし、`debug.gcstackbarrieroff > 0`が真の場合、`nextBarrier`は`^uintptr(0)`（つまり、`uintptr`の最大値）に設定されます。これは、実質的にスタックバリアを無効にする効果があります。なぜなら、`nextBarrier`が到達不可能な大きな値になるため、GCはスタックスキャン中にバリアに遭遇することがなくなり、バリアに関連する処理がスキップされるからです。

この変更により、スタックバリアがGCのパフォーマンスや正確性に与える影響を調査できるようになります。ただし、スタックバリアは並行GCの正確性を保証するために重要なメカニズムであるため、これを無効にすると深刻なメモリ安全性問題を引き起こす可能性があるため、注意が必要です。

### `src/runtime/stack1.go` (`gcshrinkstackoff`の制御)

`shrinkstack`関数は、ゴルーチンのスタックを縮小する処理を担当します。この関数内で、スタック縮小を無効にするロジックが追加されています。

```go
if debug.gcshrinkstackoff > 0 {
    return
}
```

`debug.gcshrinkstackoff > 0`が真の場合、`shrinkstack`関数はすぐに`return`し、スタック縮小処理が実行されません。これにより、ゴルーチンのスタックは一度大きくなると、その後は縮小されずにそのサイズを維持します。

この機能は、スタック縮小が原因で発生する可能性のあるバグをデバッグしたり、スタック縮小がアプリケーションのメモリ使用量やパフォーマンスに与える影響を分析したりする際に役立ちます。例えば、スタック縮小が頻繁に発生することでコピーオーバーヘッドが生じ、それがパフォーマンスボトルネックになっているかどうかを検証できます。

これらの変更は、Goランタイムの内部動作をより深く理解し、デバッグやパフォーマンスチューニングを行うための強力なツールを開発者に提供します。

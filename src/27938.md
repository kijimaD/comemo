## 変更の背景

このコミットは、Go言語のリンカ (`cmd/link`) における `plt` (Procedure Linkage Table) と `rel` (Relocation Entry) の再配置処理に関するバグを修正するものです。特に、SolarisおよびS/390アーキテクチャのビルド環境で問題が発生していたことが示唆されています。

動的リンクを使用するシステムでは、外部ライブラリの関数呼び出しを解決するためにPLTとGOT (Global Offset Table) が使用されます。これらのテーブルは、実行時に正しいアドレスにジャンプするために必要な情報を含んでいます。リンカは、これらのエントリを適切に配置し、関連する再配置エントリ (`rel`) との順序を保証する必要があります。

以前の実装では、`plt`と`rel`のシンボルを再配置する際に、スライス操作 (`append`など) を用いていました。この方法は、特定の条件下（特にSolarisやS/390のような特定のアーキテクチャのリンカの挙動やABIの違い）で、シンボルの順序が意図せず崩れる可能性がありました。結果として、生成されるバイナリが正しくリンクされず、実行時エラーや予期せぬ動作を引き起こす可能性がありました。

この修正は、より堅牢な方法でシンボルを再配置することで、これらのアーキテクチャでのビルドの安定性と正確性を確保することを目的としています。

## 前提知識の解説

### 1. リンカ (`cmd/link`)
Go言語のビルドプロセスにおいて、リンカ (`cmd/link`) は非常に重要な役割を担います。コンパイラによって生成されたオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリや共有ライブラリを生成するのがリンカの仕事です。この過程で、外部参照の解決、シンボルの配置、セクションの結合などが行われます。

### 2. 動的リンクとELF形式
多くのUnix系システム（Linux, Solarisなど）では、実行可能ファイルや共有ライブラリの標準形式としてELF (Executable and Linkable Format) が使用されます。ELF形式のバイナリは、動的リンクをサポートしており、これにより複数のプログラムが共通のライブラリコードを共有できます。

### 3. PLT (Procedure Linkage Table) と GOT (Global Offset Table)
動的リンクにおいて、外部ライブラリの関数を呼び出す際に重要な役割を果たすのがPLTとGOTです。
*   **PLT (Procedure Linkage Table)**: 外部関数の呼び出しを仲介するコードの小さな断片です。プログラムが初めて外部関数を呼び出す際、PLTエントリは動的リンカを呼び出し、実際の関数のアドレスを解決させます。
*   **GOT (Global Offset Table)**: 外部データや、一度解決された外部関数のアドレスを格納するテーブルです。PLTは、関数アドレスが解決された後、GOTに格納されたアドレスを直接参照するように動作します。

PLTとGOTは密接に関連しており、通常、PLTエントリは対応するGOTエントリを参照し、GOTエントリは実際の関数アドレスを指します。

### 4. 再配置エントリ (Relocation Entry, `rel`)
再配置エントリは、リンカや動的リンカがプログラム内のシンボル参照を解決するために必要な情報です。例えば、あるコードが外部関数のアドレスを参照している場合、その参照は再配置エントリとして記録されます。リンカは、この情報に基づいて、最終的な実行可能ファイル内で正しいアドレスを埋め込みます。PLTやGOTのエントリも、多くの場合、再配置エントリによって解決されます。

### 5. シンボルの順序
リンカが最終的なバイナリを生成する際、様々なシンボル（関数、変数、PLT/GOTエントリなど）を特定の順序で配置する必要があります。特に、PLTとそれに関連する再配置エントリは、リンカやOSのローダーが正しく動作するために、特定の相対的な順序を要求されることがあります。この順序が崩れると、リンクエラーや実行時エラーが発生する可能性があります。

### 6. SolarisとS/390
*   **Solaris**: Sun Microsystems（現在はOracle）が開発したUnix系オペレーティングシステムです。SPARCおよびx86アーキテクチャをサポートしています。
*   **S/390 (System/390)**: IBMのメインフレームコンピュータアーキテクチャです。z/Architectureの前身であり、大規模なエンタープライズシステムで利用されます。
これらのシステムは、一般的なx86-64 Linuxなどとは異なるABI (Application Binary Interface) やリンカの挙動を持つことがあり、それが特定のシンボル再配置の問題を引き起こす原因となることがあります。

## 技術的詳細
このコミットの核心は、`src/cmd/link/internal/ld/data.go` 内の `dodataSect` 関数における `plt` と `rel` シンボルの再配置ロジックの変更です。

元のコードでは、`plt` シンボルが `rel` シンボルの直後にない場合に、スライス操作 (`make`, `append`) を用いて `plt` シンボルを `rel` シンボルの直後に移動させていました。具体的には、`syms` スライスから `plt` シンボルを抽出し、`rel` シンボルの直後に挿入するために新しいスライスを構築していました。

```go
// 元のコードの抜粋
if reli >= 0 && plti >= 0 && plti != reli+1 {
    newSyms := make([]*LSym, 0, len(syms))
    plt := syms[plti]
    newSyms = append(newSyms, syms[:reli+1]...)
    newSyms = append(newSyms, plt)
    newSyms = append(newSyms, syms[reli+1:plti]...)
    newSyms = append(newSyms, syms[plti+1:]...)
    if len(newSyms) != len(syms) {
        Diag("plt move failed: len %d/%d", len(newSyms), len(syms))
    }
    syms = newSyms
}
```
このアプローチは、スライスの再構築に伴うオーバーヘッドがあるだけでなく、特に複雑なシンボル配置のシナリオや、特定のアーキテクチャ（Solaris, S/390）でのリンカの挙動との相互作用において、意図しない副作用やバグを引き起こす可能性がありました。コミットメッセージが「plt move failed」のようなエラーを示唆していることから、`len(newSyms) != len(syms)` のチェックが失敗するケースがあったか、あるいはこのチェックでは捉えられない微妙な順序の問題があったと考えられます。

新しいコードでは、より直接的かつ効率的な方法でシンボルの再配置を行っています。
1.  まず、`reli` (relocation index) と `plti` (PLT index) のどちらが小さいかによって `first` と `second` のインデックスを決定します。これは、`rel` と `plt` のどちらが先に現れるかに関わらず、それらの間の範囲を正確に操作するためです。
2.  次に、`rel` シンボルと `plt` シンボルを一時変数 `rel`, `plt` に保存します。
3.  `copy` 関数を使用して、`first+1` から `second` までの範囲のシンボルを `first+2` 以降に移動させます。これにより、`rel` と `plt` を挿入するためのスペースが確保されます。
4.  最後に、`syms[first+0] = rel` と `syms[first+1] = plt` を使って、`rel` シンボルと `plt` シンボルを正しい位置に直接挿入します。

この新しいアプローチは、スライスの再構築を伴わないため、より効率的であり、またシンボルの順序をより正確に制御できます。これにより、SolarisやS/390のような特定の環境で発生していた、`plt` と `rel` の順序に関する問題が解決されます。

## コアとなるコードの解説

変更されたコードブロックは、`syms` という `*LSym` 型のスライス（リンカシンボルのリスト）内で、`rel` シンボルと `plt` シンボルの相対的な順序を調整する役割を担っています。

**変更前のコードの問題点とアプローチ:**
変更前のコードは、`reli` (relocation entry index) と `plti` (PLT entry index) が有効であり、かつ `plt` が `rel` の直後 (`reli+1`) にない場合に、シンボルの再配置を行っていました。
このアプローチでは、新しいスライス `newSyms` を作成し、元の `syms` スライスを複数の部分に分割して `plt` シンボルを挿入していました。
`newSyms = append(newSyms, syms[:reli+1]...)`
`newSyms = append(newSyms, plt)`
`newSyms = append(newSyms, syms[reli+1:plti]...)`
`newSyms = append(newSyms, syms[plti+1:]...)`
この方法は、スライスの再構築が伴うため、パフォーマンス上のオーバーヘッドがあるだけでなく、特に複雑なケースやエッジケースで、意図しないシンボルの欠落や重複、あるいは順序の誤りを引き起こす可能性がありました。`Diag("plt move failed: len %d/%d", len(newSyms), len(syms))` というエラーチェックが存在することから、実際に `newSyms` の長さが `syms` と一致しない問題が発生していたことが伺えます。

**変更後のコードのアプローチと利点:**
新しいコードは、より効率的で堅牢なインプレース（in-place）でのスライス操作を採用しています。
1.  **インデックスの正規化**:
    ```go
    var first, second int
    if plti > reli {
        first, second = reli, plti
    } else {
        first, second = plti, reli
    }
    ```
    `reli` と `plti` の大小関係に関わらず、常に小さい方のインデックスを `first`、大きい方のインデックスを `second` とすることで、後続の `copy` 操作の範囲を簡潔に定義しています。これにより、`rel` と `plt` のどちらが `syms` スライス内で先に現れても、ロジックが正しく機能するようになります。

2.  **シンボルの退避**:
    ```go
    rel, plt := syms[reli], syms[plti]
    ```
    再配置対象の `rel` シンボルと `plt` シンボルを一時変数に退避させます。これは、スライス操作によってこれらのシンボルが上書きされることを防ぐためです。

3.  **要素のシフト**:
    ```go
    copy(syms[first+2:], syms[first+1:second])
    ```
    この行が変更の核心です。`syms` スライス内で `first+1` から `second-1` までの要素を、`first+2` から始まる位置にシフトします。これにより、`syms[first]` と `syms[first+1]` の位置に `rel` と `plt` を挿入するための2つの空きスロットが確保されます。
    例えば、`syms` が `[A, B, C, D, E]` で `first=1`, `second=3` (`B`が`rel`、`D`が`plt`だったと仮定) の場合、`syms[first+1:second]` は `[C, D]` となり、これを `syms[first+2:]` にコピーすると、`syms` は `[A, B, C, C, D]` のようになります（実際には`B`と`D`は退避されているので、`[A, _, _, C, E]`のような状態から`[A, _, _, C, E]`のような状態を作り出す）。この操作により、`first`と`first+1`の位置に、退避した`rel`と`plt`を挿入する準備が整います。

4.  **シンボルの挿入**:
    ```go
    syms[first+0] = rel
    syms[first+1] = plt
    ```
    退避しておいた `rel` シンボルと `plt` シンボルを、確保された `first` と `first+1` の位置に直接代入します。これにより、`rel` シンボルが `plt` シンボルの直前に配置されることが保証されます。

この新しいアプローチは、スライスの再構築を避けることでメモリ割り当てとコピーの回数を減らし、パフォーマンスを向上させます。また、`copy` 関数と直接代入を用いることで、シンボルの順序をより正確かつ堅牢に制御できるようになり、SolarisやS/390のような特定のアーキテクチャで発生していたリンカの問題を解決します。

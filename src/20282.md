## 変更の背景
このコミットは、`gccgo` コンパイラにおける特定のバグを修正するために、そのバグを再現するテストケースを追加するものです。具体的には、`gccgo` が、アドレス指定不可能な（unaddressable）構造体（struct）や配列（array）の値をインターフェース（interface）の値と比較する際にクラッシュするという問題がありました。

Go言語では、値の比較は型によって厳密に定義されています。特に、インターフェース値との比較は、そのインターフェースが保持する動的な型と値に基づいて行われます。`gccgo` は、この比較ロジックにおいて、一時的な値や関数呼び出しの戻り値など、メモリ上の特定のアドレスを持たない構造体や配列を扱う際に問題が発生していたと考えられます。このバグは、Go言語の仕様に準拠したコードが `gccgo` でコンパイルされると、予期せぬクラッシュを引き起こすという重大なものでした。

このコミットは、このバグが将来的に再発しないように、また、`gccgo` の挙動がGo言語の仕様に沿っていることを保証するために、再現テストを追加することを目的としています。コミットメッセージにある `#8612` は、このバグが報告されたIssue番号を示しています。

## 前提知識の解説

### Go言語の型システム
Go言語は静的型付け言語であり、変数は特定の型を持ちます。

*   **構造体 (Struct):** 複数のフィールドをまとめた複合型です。例えば `type S struct { i int }` のように定義されます。構造体は値型であり、代入や関数への引数渡しでは値がコピーされます。
*   **配列 (Array):** 同じ型の要素を固定長で並べた複合型です。例えば `type A [10]int` のように定義されます。配列も値型であり、代入や関数への引数渡しでは値がコピーされます。

### インターフェース (Interface)
Go言語のインターフェースは、メソッドのシグネチャの集合を定義する型です。インターフェース型の変数は、そのインターフェースが定義するすべてのメソッドを実装する任意の型の値を保持できます。インターフェース値は、内部的に「型」と「値」のペアとして表現されます。

*   **動的な型 (Dynamic Type):** インターフェース値が実際に保持している具体的な型。
*   **動的な値 (Dynamic Value):** インターフェース値が実際に保持している具体的な値。

### アドレス指定可能性 (Addressability)
Go言語において、「アドレス指定可能（addressable）」とは、その値がメモリ上の特定のアドレスを持つことを意味します。変数は通常アドレス指定可能です。しかし、関数呼び出しの戻り値、マップの要素（マップの値が構造体や配列の場合）、定数、文字列リテラルなど、一部の値は一時的なものであり、直接アドレスを持たない場合があります。これらの値は「アドレス指定不可能（unaddressable）」と呼ばれます。

アドレス指定不可能な値に対しては、ポインタを取得する `&` 演算子を使用することはできません。例えば、`&F1()` はコンパイルエラーになります。

### 値の比較
Go言語では、`==` 演算子を用いて値を比較できます。比較の挙動は型によって異なります。

*   **構造体の比較:** 同じ型の構造体同士は、そのすべてのフィールドが再帰的に比較されます。すべてのフィールドが等しい場合に `true` となります。
*   **配列の比較:** 同じ型の配列同士は、そのすべての要素が再帰的に比較されます。すべての要素が等しい場合に `true` となります。
*   **インターフェースの比較:** インターフェース値同士の比較は、そのインターフェースが保持する動的な型と動的な値の両方が等しい場合に `true` となります。インターフェース値と非インターフェース値の比較も可能です。この場合、非インターフェース値は一時的にインターフェース型に変換されてから比較が行われます。この変換の過程で、非インターフェース値がインターフェースの「値」部分に適切に格納される必要があります。

### gccgo
`gccgo` は、GCC (GNU Compiler Collection) のフロントエンドとして実装されたGo言語コンパイラです。Go言語の公式コンパイラである `gc` とは異なる実装であり、Go言語の仕様に準拠しつつも、内部的なコード生成や最適化のロジックが異なります。そのため、`gc` では問題なく動作するコードが `gccgo` では異なる挙動を示したり、バグが発生したりすることが稀にあります。これは、異なるコンパイラが同じ言語仕様を異なる方法で解釈・実装する際に起こりうる典型的な問題です。

## 技術的詳細
このバグは、`gccgo` がアドレス指定不可能な構造体や配列の値をインターフェース値と比較する際の内部処理に起因していました。

Go言語の仕様では、比較可能な型の値はインターフェース値と比較できます。この比較は、インターフェースが保持する動的な型と値に基づいて行われます。非インターフェース値がインターフェース値と比較される場合、非インターフェース値は一時的にインターフェース型に「ボックス化（boxing）」されます。このボックス化の過程で、非インターフェース値がインターフェースの「値」部分に適切に格納される必要があります。

アドレス指定不可能な値の場合、その値は一時的なものであり、特定のメモリ位置に永続的に存在しない可能性があります。`gccgo` は、このようなアドレス指定不可能な構造体や配列をインターフェース値と比較する際に、以下のいずれかの問題が発生していたと考えられます。

1.  **不適切なボックス化:** アドレス指定不可能な構造体や配列の値をインターフェースの「値」部分にコピーまたは参照する際に、`gccgo` がその一時的な性質を正しく扱えず、不正なメモリ参照やデータ破損を引き起こしていた。
2.  **比較ロジックの欠陥:** インターフェース値の比較ロジックが、アドレス指定不可能な値がボックス化された場合の特殊なケースを考慮していなかった。例えば、値のコピーではなく、誤って一時的なアドレスを参照しようとした結果、無効なメモリにアクセスしていた可能性。
3.  **最適化の誤り:** `gccgo` の最適化パスが、アドレス指定不可能な値とインターフェースの比較において、誤ったコードを生成していた。これにより、実行時にクラッシュが発生していた。

この問題は、Go言語の型システムにおける「値のセマンティクス」と「インターフェースの動的な性質」の間の相互作用、そしてコンパイラがそれらをどのように内部的に表現し、操作するかに深く関連しています。特に、構造体や配列のような複合型が、関数からの戻り値として渡される際に、その値が一時的なコピーとして扱われ、アドレスを持たない状態になることが問題のトリガーとなりました。

## コアとなるコードの変更箇所

`test/fixedbugs/issue8612.go` が新規追加されています。

```go
//compile

// Copyright 2014 The Go Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

// Gccgo had a bug comparing a struct or array value with an interface
// values, when the struct or array was not addressable.

package p

type A [10]int

type S struct {
	i int
}

func F1() S {
	return S{0}
}

func F2() A {
	return A{}
}

func Cmp(v interface{}) bool {
	if F1() == v {
		return true
	}
	if F2() == v {
		return true
	}
	return false
}
```

## コアとなるコードの解説

新しく追加された `issue8612.go` は、`gccgo` のバグを再現するために特別に設計されたテストケースです。

1.  **`type A [10]int` と `type S struct { i int }`:**
    それぞれ、固定長の配列型 `A` と構造体型 `S` を定義しています。これらはGo言語の仕様上、比較可能な型です。

2.  **`func F1() S { return S{0} }` と `func F2() A { return A{} }`:**
    これらの関数は、それぞれ構造体 `S` と配列 `A` の値を返します。ここで重要なのは、これらの関数が返す値は「アドレス指定不可能」であるという点です。関数から返される値は一時的なコピーであり、メモリ上の固定されたアドレスを持たないため、直接 `&` 演算子でポインタを取得することはできません。例えば、`&F1()` はコンパイルエラーになります。

3.  **`func Cmp(v interface{}) bool`:**
    この関数は、インターフェース型の引数 `v` を受け取ります。
    *   `if F1() == v { ... }`: ここで、アドレス指定不可能な構造体 `S` の値（`F1()` の戻り値）とインターフェース値 `v` の比較が行われます。
    *   `if F2() == v { ... }`: 同様に、アドレス指定不可能な配列 `A` の値（`F2()` の戻り値）とインターフェース値 `v` の比較が行われます。

`gccgo` のバグは、まさにこの「アドレス指定不可能な構造体/配列の値とインターフェース値の比較」の箇所で発生していました。このテストケースは、`F1()` や `F2()` の戻り値がインターフェース値 `v` と比較される際に、`gccgo` が内部的にクラッシュするかどうかを検証します。このテストがコンパイル時にエラーなく通過すれば、バグが修正されたことを意味します。

このテストはファイルの先頭に `//compile` ディレクティブを含んでいます。これはGoのテストフレームワークに対して、このファイルがコンパイル可能であるべきことを示します。もしバグが修正されていなければ、コンパイル時にクラッシュが発生し、テストは失敗します。この種のテストは、コンパイラ自体の健全性を保証するために非常に重要です。

このコミットは、Go言語の `crypto/cipher` パッケージにおける GCM (Galois/Counter Mode) 実装に、非標準の nonce (初期化ベクトル) 長をサポートする機能を追加するものです。GCM は通常 96 ビットの nonce を使用しますが、標準では任意の長さの nonce が許容されており、特定のプロトコルでは非標準の nonce 長が必要となる場合があります。この変更により、Go の GCM 実装がより柔軟になり、これらの要件に対応できるようになります。

## 元コミット内容

`crypto/cipher: Support unusual GCM nonce lengths`

GCM は伝統的に 96 ビットの nonce を使用しますが、標準では任意のサイズの nonce が許可されています。非標準の nonce サイズは一部のプロトコルで必要とされるため、`crypto/cipher` の GCM 実装にそれらをサポートする機能を追加します。

## 変更の背景

GCM (Galois/Counter Mode) は、認証付き暗号 (Authenticated Encryption with Associated Data, AEAD) モードの一種であり、データの機密性、完全性、および認証性を提供します。GCM の仕様では、nonce (Number used once) の長さについて柔軟性があり、任意の長さを許容しています。しかし、NIST SP 800-38D (Recommendation for Block Cipher Modes of Operation: Galois/Counter Mode (GCM) and GMAC) では、セキュリティと実装の効率性の観点から 96 ビット (12 バイト) の nonce が強く推奨されています。これは、96 ビットの nonce が GCM の内部カウンタの初期化を簡素化し、GHASH 関数を介した追加の処理を不要にするためです。

しかし、現実のプロトコルやシステムの中には、歴史的経緯や特定の要件により、96 ビット以外の nonce 長を使用するものも存在します。例えば、TLS 1.3 では GCM の nonce は 96 ビットですが、他のプロトコルでは異なる長さが採用されることがあります。Go の `crypto/cipher` パッケージの GCM 実装が 96 ビットの nonce にのみ対応している場合、これらの非標準の nonce 長を使用するシステムとの相互運用性が損なわれることになります。

このコミットの背景には、Go の GCM 実装がより広範なユースケースに対応し、非標準の nonce 長を必要とするプロトコルとの互換性を確保する必要性があったと考えられます。これにより、Go の暗号ライブラリの汎用性と実用性が向上します。

## 前提知識の解説

### GCM (Galois/Counter Mode)

GCM は、ブロック暗号をカウンタモード (CTR) と Galois Field Multiplication (GHASH) を組み合わせた認証付き暗号モードです。

*   **カウンタモード (CTR)**: ブロック暗号をストリーム暗号のように動作させ、各ブロックを独立して暗号化/復号化します。各ブロックの暗号化には、nonce とカウンタ値の組み合わせが使用されます。
*   **GHASH**: 認証タグを生成するために使用されるハッシュ関数です。暗号化されたデータと追加認証データ (AAD) の両方から認証タグを計算し、データの完全性と認証性を提供します。

### Nonce (Number used once)

Nonce は、暗号化操作ごとに一度だけ使用されるランダムまたは擬似ランダムな値です。GCM においては、nonce はカウンタの初期値を導出するために使用され、同じ鍵で異なるメッセージを暗号化する際に、同じ (nonce, カウンタ) の組み合わせが二度と使用されないことを保証します。これにより、攻撃者が暗号文のパターンを分析して情報を漏洩させることを防ぎます。

### NIST SP 800-38D

NIST (National Institute of Standards and Technology) が発行する特別刊行物 800-38D は、GCM および GMAC (Galois Message Authentication Code) の使用に関する推奨事項を定めています。この文書は、GCM の実装と利用におけるセキュリティ上のベストプラクティスを提供し、特に nonce の長さと生成方法について詳細なガイダンスを与えています。

NIST SP 800-38D のセクション 7.1 では、GCM の初期カウンタブロックの導出方法について説明されています。
*   **96 ビット (12 バイト) の nonce の場合**: nonce の後に 32 ビットのカウンタ (初期値は 1) を連結して初期カウンタブロックを形成します。これは「高速パス」と呼ばれ、GHASH 処理が不要なため効率的です。
*   **その他の長さの nonce の場合**: nonce を GHASH 関数に入力し、その結果を初期カウンタブロックとして使用します。これは「低速パス」と呼ばれ、追加の GHASH 処理が必要になります。

このコミットは、まさにこの「その他の長さの nonce」に対する「低速パス」の実装を追加するものです。

## 技術的詳細

このコミットの主要な変更点は、`crypto/cipher` パッケージの GCM 実装が、96 ビット以外の nonce 長を処理できるように拡張されたことです。具体的には、以下の点が変更されています。

1.  **`gcm` 構造体への `nonceSize` フィールドの追加**:
    ```go
    type gcm struct {
    	cipher    Block
    	nonceSize int // 新しく追加されたフィールド
    	// ...
    }
    ```
    これにより、GCM インスタンスが自身の nonce 長を保持できるようになります。

2.  **`NewGCMWithNonceSize` 関数の導入**:
    ```go
    func NewGCMWithNonceSize(cipher Block, size int) (AEAD, error) {
    	// ...
    	g := &gcm{cipher: cipher, nonceSize: size}
    	// ...
    }
    ```
    この新しいコンストラクタ関数は、ユーザーが任意の `nonceSize` を指定して GCM インスタンスを作成できるようにします。既存の `NewGCM` 関数は、内部的に `NewGCMWithNonceSize` を `gcmStandardNonceSize` (12 バイト、96 ビット) で呼び出すように変更されました。

3.  **`NonceSize()` メソッドの変更**:
    ```go
    func (g *gcm) NonceSize() int {
    	return g.nonceSize // 固定値ではなく、インスタンスの nonceSize を返す
    }
    ```
    これにより、GCM インスタンスがサポートする nonce 長が動的に決定されるようになります。

4.  **`Seal` および `Open` メソッドにおける nonce 長のチェックの変更**:
    ```go
    func (g *gcm) Seal(dst, nonce, plaintext, data []byte) []byte {
    	if len(nonce) != g.nonceSize { // gcmNonceSize ではなく g.nonceSize を参照
    		panic("cipher: incorrect nonce length given to GCM")
    	}
    	// ...
    }
    ```
    `Seal` および `Open` 関数は、入力された `nonce` の長さが GCM インスタンスに設定された `nonceSize` と一致するかどうかをチェックするようになりました。

5.  **`deriveCounter` 関数の追加**:
    ```go
    func (g *gcm) deriveCounter(counter *[gcmBlockSize]byte, nonce []byte) {
    	if len(nonce) == gcmStandardNonceSize {
    		// Fast path for 96-bit nonces
    		copy(counter[:], nonce)
    		counter[gcmBlockSize-1] = 1
    	} else {
    		// Slow path for other nonce sizes (GHASH processing)
    		var y gcmFieldElement
    		g.update(&y, nonce)
    		y.high ^= uint64(len(nonce)) * 8
    		g.mul(&y)
    		putUint64(counter[:8], y.low)
    		putUint64(counter[8:], y.high)
    	}
    }
    ```
    この新しい内部関数 `deriveCounter` は、NIST SP 800-38D のセクション 7.1 に従って、nonce から初期カウンタブロックを導出するロジックを実装しています。
    *   nonce が標準の 96 ビット長の場合、高速パスが使用されます。
    *   それ以外の長さの場合、nonce は GHASH 関数 (`g.update` と `g.mul` を使用) を通して処理され、その結果が初期カウンタブロックとして使用されます。これは、NIST SP 800-38D で定義されている「低速パス」の実装です。

6.  **テストケースの追加**:
    `gcm_test.go` に、非標準の nonce 長 (例: 5 バイト、75 バイトなど) を使用する新しいテストケースが追加され、この機能が正しく動作することを確認しています。

これらの変更により、Go の GCM 実装は、標準の 96 ビット nonce だけでなく、任意の長さの nonce を安全かつ標準に準拠した方法で処理できるようになりました。ただし、コミットメッセージにもあるように、非標準の nonce 長は特定のプロトコルとの互換性のためのみに使用されるべきであり、それ以外の場合は `NewGCM` (96 ビット nonce) を使用することが推奨されています。これは、96 ビット nonce の方が効率的であり、誤用に対する耐性が高いためです。

## コアとなるコードの解説

### `gcm` 構造体と `nonceSize`

```go
type gcm struct {
	cipher    Block
	nonceSize int // 新しく追加されたフィールド
	// productTable ...
}
```
`nonceSize` フィールドが追加されたことで、`gcm` インスタンスは自身が扱う nonce の長さを動的に保持できるようになりました。これにより、単一の GCM 実装で異なる nonce 長をサポートすることが可能になります。

### `NewGCMWithNonceSize` 関数

```go
func NewGCM(cipher Block) (AEAD, error) {
	return NewGCMWithNonceSize(cipher, gcmStandardNonceSize)
}

func NewGCMWithNonceSize(cipher Block, size int) (AEAD, error) {
	// ...
	g := &gcm{cipher: cipher, nonceSize: size}
	// ...
}
```
`NewGCMWithNonceSize` は、GCM インスタンスを初期化する際に、ユーザーが明示的に nonce の長さを指定できるようにする新しいコンストラクタです。これにより、非標準の nonce 長を必要とするアプリケーションが GCM を利用できるようになります。既存の `NewGCM` は、後方互換性を保ちつつ、標準の 96 ビット nonce を使用する `NewGCMWithNonceSize` のラッパーとして機能します。

### `deriveCounter` 関数

```go
func (g *gcm) deriveCounter(counter *[gcmBlockSize]byte, nonce []byte) {
	// GCM has two modes of operation with respect to the initial counter
	// state: a "fast path" for 96-bit (12-byte) nonces, and a "slow path"
	// for nonces of other lengths. For a 96-bit nonce, the nonce, along
	// with a four-byte big-endian counter starting at one, is used
	// directly as the starting counter. For other nonce sizes, the counter
	// is computed by passing it through the GHASH function.
	if len(nonce) == gcmStandardNonceSize {
		copy(counter[:], nonce)
		counter[gcmBlockSize-1] = 1
	} else {
		var y gcmFieldElement
		g.update(&y, nonce)
		y.high ^= uint64(len(nonce)) * 8
		g.mul(&y)
		putUint64(counter[:8], y.low)
		putUint64(counter[8:], y.high)
	}
}
```
この関数は、このコミットの最も重要な変更点です。NIST SP 800-38D に従って、nonce から GCM の初期カウンタブロックを導出するロジックを実装しています。

*   **高速パス (`len(nonce) == gcmStandardNonceSize`)**: nonce が 96 ビット (12 バイト) の場合、nonce の内容をカウンタブロックの先頭 12 バイトにコピーし、最後の 4 バイトを `0x00000001` に設定します。これは、NIST SP 800-38D のセクション 7.1 で定義されている効率的な方法です。
*   **低速パス (それ以外の長さ)**: nonce が 96 ビットでない場合、nonce は GHASH 関数 (`g.update` と `g.mul`) を通して処理されます。具体的には、nonce のビット長を GHASH の結果に XOR し、最終的な GHASH の結果が初期カウンタブロックとして使用されます。この処理は、nonce の長さが 96 ビットでない場合に、GHASH を用いて初期カウンタを計算するという NIST の仕様に準拠しています。

この `deriveCounter` 関数により、Go の GCM 実装は、異なる nonce 長に対してもセキュリティ要件を満たしつつ、標準に準拠した方法で動作できるようになりました。

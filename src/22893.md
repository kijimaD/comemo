# [インデックス 22893] ファイルの概要

このコミットは、Go言語の`os`パッケージにおける`TestProgWideChdir`テストがmacOS (Darwin) 環境で失敗する問題を修正するものです。具体的には、macOSにおける`/tmp`や`/var`ディレクトリが`/private`へのシンボリックリンクとして扱われる特性に起因する、`os.Getwd()`（現在の作業ディレクトリを取得する関数）の挙動の違いを吸収し、テストが正しく動作するように改善しています。

## 変更の背景

`TestProgWideChdir`は、複数のゴルーチンが同時に作業ディレクトリを変更し、その変更が正しく反映されているかを確認するテストです。このテストは、macOS (Darwin) 環境で失敗していました。

問題の根本原因は、macOSが`/tmp`や`/var`といった一般的なディレクトリを、実際の物理パスである`/private/tmp`や`/private/var`へのシンボリックリンクとして扱っていることにありました。

テスト内で`os.Chdir()`を使って作業ディレクトリを変更した後、`os.Getwd()`で現在の作業ディレクトリを取得し、期待されるパスと比較していました。しかし、macOSのシンボリックリンクの挙動により、`os.Getwd()`がシンボリックリンクを解決しない論理パス（例: `/var/.../T`）を返す場合と、解決された物理パス（例: `/private/var/.../T`）を返す場合があり、これがテストの比較で不一致を引き起こしていました。

また、テスト内のゴルーチンでエラーが発生した場合に`t.Fatal()`を使用していたため、一つのゴルーチンでエラーが発生すると即座にテストが終了し、他のゴルーチンの結果を確認できないという問題もありました。

## 前提知識の解説

### シンボリックリンク (Symbolic Link)
シンボリックリンク（またはソフトリンク）は、ファイルシステム内の別のファイルやディレクトリへの参照（ポインタ）を含む特殊なファイルです。WindowsのショートカットやUnix/Linuxのシンボリックリンクと同様の概念です。シンボリックリンク自体は非常に小さく、参照先のパス情報のみを保持します。

### `os.Chdir()`
Go言語の`os`パッケージに含まれる関数で、現在のプロセス（プログラム）の作業ディレクトリを変更するために使用されます。例えば、`os.Chdir("/path/to/new/directory")`と呼び出すことで、プログラムがファイル操作を行う際の基準となるディレクトリを変更できます。

### `os.Getwd()`
Go言語の`os`パッケージに含まれる関数で、現在のプロセス（プログラム）の作業ディレクトリの絶対パスを取得するために使用されます。この関数は、シンボリックリンクを解決した物理パスを返す場合と、解決しない論理パスを返す場合があり、OSやファイルシステムの構成によって挙動が異なることがあります。

### macOS (Darwin) のファイルシステム構造
macOSでは、一部のシステムディレクトリがシンボリックリンクとして実装されています。特に、`/tmp`、`/var`、`/etc`などは、それぞれ`/private/tmp`、`/private/var`、`/private/etc`へのシンボリックリンクです。これは、macOSの内部的なファイルシステム管理と、Unix系の標準的なディレクトリ構造との互換性を両立させるための設計です。

- `/tmp` -> `/private/tmp`
- `/var` -> `/private/var`
- `/etc` -> `/private/etc`

この挙動は、`pwd -L`（論理パスを表示）と`pwd -P`（物理パスを表示）コマンドで確認できます。

```bash
% cd $TMPDIR; pwd -L
/var/.../T
% pwd -P
/private/var/.../T
```

### Go言語のテストにおける`t.Fatal()`と`t.Errorf()`
Go言語の`testing`パッケージは、テストの実行と結果報告のための機能を提供します。
- `t.Fatal()`: テストを即座に失敗させ、現在のテスト関数を終了します。後続の処理は実行されません。
- `t.Errorf()`: テストを失敗としてマークしますが、現在のテスト関数の実行は継続します。これにより、複数のエラーを報告したり、他のテストロジックが完了するのを待ったりすることができます。
ゴルーチン内で`t.Fatal()`を使用すると、そのゴルーチンがテストを終了させてしまうため、他のゴルーチンの並行処理が中断される可能性があります。

## 技術的詳細

このコミットの技術的詳細は、macOSのシンボリックリンクの挙動と、Goの`os.Getwd()`関数の相互作用に焦点を当てています。

`TestProgWideChdir`テストでは、まず`os.Chdir(d)`で作業ディレクトリを`d`に設定します。その後、複数のゴルーチンを起動し、それぞれのゴルーチン内で`os.Getwd()`を呼び出して現在の作業ディレクトリを取得し、それが期待されるパス`d`と一致するかを検証します。

問題は、macOS上で`d`が`/tmp`や`/var`配下のディレクトリである場合、`os.Chdir(d)`で設定された論理パスと、`os.Getwd()`が返す物理パス（シンボリックリンクを解決したパス）が異なる可能性があることでした。例えば、`d`が`/var/folders/.../T`のようなパスであった場合、`os.Chdir`はこれを設定しますが、`os.Getwd()`は`/private/var/folders/.../T`のようなパスを返すことがあり、この不一致がテストの失敗につながっていました。

この問題を解決するため、コミットでは以下の2つの主要な変更が行われました。

1.  **`os.Chdir()`後の`os.Getwd()`の再呼び出し**:
    `os.Chdir(d)`を実行した後、テストの比較基準となる`d`自体を、`os.Getwd()`を再度呼び出して取得したパスで更新しています。これにより、`d`が常にシンボリックリンクを解決した物理パス（または`os.Getwd()`が返す形式のパス）になるようにします。テストの比較は、この「解決された」`d`と、ゴルーチン内で取得される`pwd`の間で行われるため、パスの不一致が解消されます。コミットメッセージにある`pwd -L`と`pwd -P`の例は、この問題の核心を示しています。`pwd -L`が論理パス、`pwd -P`が物理パスです。`os.Getwd()`の挙動がどちらかに固定されていない、あるいは環境によって変わりうるため、テスト側で正規化する必要がありました。

2.  **`t.Fatal()`から`t.Errorf()`への変更**:
    ゴルーチン内で`os.Getwd()`がエラーを返した場合、以前は`t.Fatal()`を使用していました。`t.Fatal()`はテストを即座に終了させるため、他のゴルーチンがまだ実行中であってもテスト全体が中断されていました。これを`t.Errorf()`に変更することで、エラーが発生してもテスト関数全体の実行は継続され、他のゴルーチンの結果も確認できるようになります。これは、並行処理を含むテストにおいて、より堅牢なエラー報告を可能にするための一般的なプラクティスです。

これらの変更により、macOSのファイルシステム特性に起因するパスの不一致が解消され、`TestProgWideChdir`が安定して動作するようになりました。

## コアとなるコードの解説

### 1. ゴルーチン内のエラーハンドリングの変更

```diff
@@ -1060,7 +1060,8 @@ func TestProgWideChdir(t *testing.T) {
 			<-c
 			pwd, err := Getwd()
 			if err != nil {\n-\t\t\t\tt.Fatal(\"Getwd: %v\", err)\n+\t\t\t\tt.Errorf(\"Getwd on goroutine %d: %v\", i, err)\n+\t\t\t\treturn\n 			}\n 			cpwd <- pwd
 		}(i)\n```

- **変更前**: `t.Fatal("Getwd: %v", err)`
- **変更後**: `t.Errorf("Getwd on goroutine %d: %v", i, err)` と `return`

この変更は、テストの堅牢性を向上させるためのものです。
`TestProgWideChdir`は複数のゴルーチンを起動して並行して作業ディレクトリの変更と取得を行います。以前は、いずれかのゴルーチン内で`Getwd()`がエラーを返した場合、`t.Fatal()`が呼び出され、その時点でテスト全体が即座に終了していました。これにより、他のゴルーチンの実行が中断され、テストの全体的なカバレッジやエラー報告が不完全になる可能性がありました。

変更後は`t.Errorf()`を使用しています。`t.Errorf()`はテストを失敗としてマークしますが、現在のゴルーチン（およびテスト関数全体）の実行は継続されます。エラー発生後に`return`を追加することで、そのゴルーチンはこれ以上処理を進めませんが、他のゴルーチンは引き続き実行され、それぞれの結果を報告できます。これにより、テストの並行処理がより適切に扱われ、複数のゴルーチンからのエラーを同時に捕捉できるようになります。

コメントにある「OS X sets TMPDIR to a symbolic link. So we resolve our working directory again before the test.」は、この修正の意図を明確に示しています。

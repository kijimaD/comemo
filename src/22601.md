## 元コミット内容

ランタイム: nacl向けのnewosprocでライトバリアをトリガーしないようにする

これは、nacl/386ビルダで断続的に発生していた、`mp.p == nil`の状態でライトバリアが呼び出されるという失敗を修正するはずです。

## 変更の背景

Goランタイムは、プログラムの実行を管理する上でガベージコレクション (GC) を利用しています。GCは、不要になったメモリを自動的に解放することで、メモリリークを防ぎ、開発者がメモリ管理に煩わされることなくコードを書けるようにします。このGCの正確な動作を保証するために、Goは「ライトバリア (Write Barrier)」というメカニズムを使用しています。ライトバリアは、ポインタが書き換えられる際に、GCがオブジェクトの参照関係を正しく追跡できるようにするためのフックのようなものです。

このコミットの背景にある問題は、Goランタイムが新しいOSスレッドを作成する際に使用する`newosproc`関数にありました。特に、Googleが開発したサンドボックス技術であるNative Client (NaCl) 環境の`386`アーキテクチャ向けビルドにおいて、この`newosproc`関数が呼び出される際に、`mp.p == nil`という状態、つまりGoスケジューラのM (Machine) がP (Processor) にアタッチされていない状態で、誤ってライトバリアがトリガーされてしまうという断続的な問題が発生していました。

`mp.p`は、GoのM (OSスレッドに相当) が現在実行しているP (論理プロセッサに相当) を指します。`newosproc`が呼び出される初期段階では、MはまだPにアタッチされていないため、`mp.p`は`nil`であるのが正常な状態です。しかし、この`nil`の状態でライトバリアがトリガーされると、GCの内部状態が不正になり、ランタイムエラーやプログラムのクラッシュを引き起こす可能性がありました。これは、Goのビルドシステムにおいて、NaCl/386ビルダで断続的なテスト失敗として現れていました。

このコミットは、この特定のシナリオにおいてライトバリアが不必要にトリガーされるのを防ぐことで、ビルドの安定性とランタイムの堅牢性を向上させることを目的としています。

## 前提知識の解説

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理する一連のライブラリとシステムです。これには、ガベージコレクタ、スケジューラ（ゴルーチンとOSスレッドのマッピングを管理）、メモリ割り当て、プリミティブな同期メカニズムなどが含まれます。Goプログラムは、OSによって直接実行されるのではなく、このランタイム上で動作します。

### ガベージコレクション (Garbage Collection, GC) とライトバリア (Write Barrier)

Goは自動メモリ管理、すなわちガベージコレクションを採用しています。GCは、プログラムがもはや到達できないメモリ領域（オブジェクト）を自動的に識別し、解放するプロセスです。GoのGCは、並行マーク＆スイープ方式をベースにしており、プログラムの実行と並行してGCが動作します。

ライトバリアは、並行GCの正確性を保証するために不可欠なメカニズムです。プログラムがヒープ上のポインタを書き換える（あるオブジェクトから別のオブジェクトへの参照を変更する）際に、GCがその変更を検知し、オブジェクトグラフの整合性を維持できるようにするための小さなコードスニペットが挿入されます。これにより、GCがオブジェクトをマークしている最中に参照が変更されても、GCが誤って到達可能なオブジェクトを解放してしまう（「ストップ・ザ・ワールド」時間を最小限に抑えつつ）ことを防ぎます。

### `newosproc`関数

`newosproc`はGoランタイム内部の関数で、新しいOSスレッドを作成し、そのスレッド上でGoのM (Machine) を初期化して実行を開始するために使用されます。Goのスケジューラは、ゴルーチンをMに、MをOSスレッドにマッピングすることで並行性を実現します。`newosproc`は、Goプログラムがより多くの並行処理を必要とする際に、OSレベルで新しい実行コンテキストを確立する役割を担います。

### `mp.p == nil`

Goのスケジューラは、G (Goroutine)、M (Machine)、P (Processor) の3つのエンティティで構成されます。
- **G (Goroutine)**: Goにおける軽量な実行単位。
- **M (Machine)**: OSススレッドに相当し、Gを実行する実際のOSスレッド。
- **P (Processor)**: MがGを実行するために必要なリソース（コンテキスト、スケジューラのキューなど）を提供する論理プロセッサ。

`mp`は現在のM（Machine）を表すポインタです。`mp.p`は、そのMが現在アタッチされているP（Processor）を指します。通常、MはGを実行するためにPにアタッチされています。しかし、`newosproc`が呼び出されるようなOSスレッドの初期化段階では、MはまだどのPにもアタッチされていないため、`mp.p`は`nil`であるのが正常な状態です。この`nil`の状態でライトバリアがトリガーされると、GCが期待する環境（Pがアタッチされている状態）が整っていないため、問題が発生します。

### Native Client (NaCl)

Native Client (NaCl) は、Googleが開発したオープンソースのサンドボックス技術で、ウェブブラウザ内でネイティブコード（C/C++など）を安全かつポータブルに実行することを可能にします。NaClは、セキュリティとパフォーマンスの両方を考慮して設計されており、ウェブアプリケーションがより複雑な処理をクライアント側で実行できるようにすることを目的としていました。GoはかつてNaClをターゲットプラットフォームの一つとしてサポートしており、GoプログラムをNaCl環境で実行することができました。このコミットは、そのNaCl環境におけるGoランタイムの安定性に関するものです。

### `//go:nowritebarrier` ディレクティブ

`//go:nowritebarrier`は、Goコンパイラに対する特殊なディレクティブ（プラグマ）です。このディレクティブが関数宣言の直前に記述されると、コンパイラはその関数内でポインタの書き込みが行われても、ライトバリアのコードを挿入しないようにします。これは、ランタイムの非常に低レベルな部分や、GCがまだ完全に初期化されていない、あるいはライトバリアが不適切に動作する可能性のある特定のコンテキストで使用されます。このディレクティブは、GCの整合性を損なう可能性があるため、非常に慎重に使用されるべきです。

### `mp.tls`

`mp.tls`は、Goランタイムの`m`（Machine）構造体に含まれるフィールドで、スレッドローカルストレージ（TLS: Thread-Local Storage）に関連する情報を保持します。TLSは、各スレッドが独自のデータコピーを持つことを可能にするメカニズムで、グローバル変数へのアクセス競合を避けるために使用されます。Goランタイムでは、`g0`（システムゴルーチン）や現在のM自身へのポインタなど、スレッド固有の重要な情報がTLSに格納されることがあります。

## 技術的詳細

このコミットの技術的な核心は、`newosproc`関数が新しいOSスレッドを初期化する際に、Goのガベージコレクタのライトバリアが不適切にトリガーされる問題を解決することにあります。

問題の根源は、`newosproc`が呼び出される時点では、新しいM（Machine）はまだP（Processor）にアタッチされていません。つまり、`mp.p`は`nil`の状態です。Goのライトバリアは、通常、Pがアタッチされていることを前提として動作します。Pは、GCがオブジェクトグラフを走査し、マークする際に必要なコンテキスト情報を提供するためです。`mp.p`が`nil`の状態でライトバリアが実行されると、GCの内部状態が不正になり、ランタイムパニックやクラッシュを引き起こす可能性がありました。これは特にNaCl/386環境で顕著に現れていました。

この問題を解決するために、コミットは2つの主要な変更を導入しています。

1.  **`//go:nowritebarrier` ディレクティブの追加**:
    `newosproc`関数の宣言の直前に`//go:nowritebarrier`ディレクティブが追加されました。これにより、Goコンパイラは`newosproc`関数内のポインタ書き込み操作に対してライトバリアのコードを挿入しなくなります。これは、`newosproc`が非常に低レベルな初期化コードであり、GCが完全に機能する前の段階で実行されるため、ライトバリアが不要であるか、むしろ有害であるという判断に基づいています。このディレクティブにより、`mp.p == nil`の状態でライトバリアが誤ってトリガーされることが根本的に回避されます。

2.  **`mp.tls`へのアクセス方法の変更**:
    変更前は、`mp.tls`（`[3]uintptr`型の配列）へのアクセスに`unsafe.Pointer(&mp.tls)`を使用して、それを`*[3]unsafe.Pointer`にキャストし、そのポインタを介して要素に値を代入していました。
    ```go
    tls := (*[3]unsafe.Pointer)(unsafe.Pointer(&mp.tls))
    tls[0] = unsafe.Pointer(mp.g0)
    tls[1] = unsafe.Pointer(mp)
    ```
    この`unsafe.Pointer(&mp.tls)`という操作は、`mp.tls`のアドレスを取得し、それを`unsafe.Pointer`に変換するものです。このポインタの書き込み操作が、ライトバリアの対象となる可能性がありました。

    変更後は、`mp.tls`を直接`uintptr`型の配列として扱い、各要素に`uintptr`にキャストした値を代入しています。
    ```go
    mp.tls[0] = uintptr(unsafe.Pointer(mp.g0))
    mp.tls[1] = uintptr(unsafe.Pointer(mp))
    ```
    `mp.tls`は元々`[3]uintptr`型として定義されており、`uintptr`はポインタを整数として扱う型です。`uintptr(unsafe.Pointer(mp.g0))`のように、`unsafe.Pointer`を介してポインタを`uintptr`に変換し、それを`uintptr`型の配列要素に代入する操作は、Goの型システム上はポインタの書き込みとは見なされず、ライトバリアの対象外となります。これにより、`//go:nowritebarrier`ディレクティブと合わせて、この特定のコードパスでのライトバリアのトリガーを確実に防ぎます。

これらの変更により、`newosproc`が新しいOSスレッドを初期化する際の、GCライトバリアによる不適切な干渉が排除され、NaCl/386ビルダでの断続的な失敗が解消されました。これは、Goランタイムの低レベルな部分における、GCとスケジューラの相互作用の複雑さを浮き彫りにする修正です。

    変更後は、以下のように直接`mp.tls`の要素に値を代入しています。

これらの変更は、Goランタイムの非常にデリケートな部分、特に新しいOSスレッドの初期化とGCのライトバリアの相互作用に関する問題を解決するために行われました。

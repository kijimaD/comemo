## 元コミット内容

このコミットは、`net/http`パッケージにおけるダイヤル処理とキャンセル処理の間の競合状態を修正します。`getConn`関数が接続を取得し、その接続が`persistConn.roundTrip`関数で実際にリクエストを処理するまでの短い時間枠において、リクエストのキャンセルが正しく伝達されない可能性がありました。この問題を解決するため、キャンセル関数がクリアされたかどうかを検査できるようにし、`roundTrip`に入る前にリクエストがキャンセルされたかどうかを確認するメカニズムが導入されました。これにより、Issue #10511で報告された問題が修正されます。

## 変更の背景

Goの`net/http`パッケージは、HTTPクライアントとサーバーの実装を提供します。クライアント側では、`http.Client`がHTTPリクエストを送信するための主要なインターフェースであり、その内部では`http.Transport`が実際のネットワーク接続の管理、リクエストの多重化、接続の再利用などを担当しています。

このコミットが修正しようとしている問題は、`Transport`がHTTPリクエストを処理する際の特定のタイミングで発生する競合状態です。具体的には、以下のシーケンスで問題が発生していました。

1.  クライアントがHTTPリクエストを送信する。
2.  `Transport`は、このリクエストを処理するために既存のアイドル接続を探すか、新しい接続を確立（ダイヤル）しようとします。この処理は`getConn`関数で行われます。
3.  `getConn`が接続を正常に取得または確立した後、その接続を使って実際のリクエストを送信するために`persistConn.roundTrip`関数が呼び出されます。

問題は、`getConn`が接続を返してから`persistConn.roundTrip`がリクエストのキャンセルハンドラを登録するまでの「短いウィンドウ」にありました。この短い期間に、もし外部から`http.Client.CancelRequest`（または`context.Context`のキャンセル）が呼び出された場合、そのキャンセルイベントが`Transport`の内部状態に正しく反映されない可能性がありました。

具体的には、`Transport`は各リクエストに対してキャンセル関数を内部マップ（`reqCanceler`）に登録し、リクエストがキャンセルされた際にその関数を呼び出すことで処理を中断します。しかし、上記の短いウィンドウでは、`getConn`が接続を返した直後にはまだリクエストのキャンセル関数が`reqCanceler`マップに登録されていないか、あるいは一時的なダミー関数が登録されている状態でした。この間にキャンセルが発行されると、`CancelRequest`はマップからキャンセル関数を削除しようとしますが、まだ適切な関数が登録されていないため、キャンセルイベントが「失われ」、リクエストはキャンセルされずに続行されてしまう可能性がありました。これにより、クライアントは不要なネットワークリソースを消費し続けたり、タイムアウトまで待機したりするなどの不適切な動作を引き起こす可能性がありました。

この競合状態は、特に高負荷時やネットワークの不安定な環境で顕在化しやすく、リソースリークやアプリケーションの応答性低下につながる可能性がありました。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語および`net/http`パッケージに関する前提知識が必要です。

### 1. Go言語の`net/http`パッケージ

Goの`net/http`パッケージは、HTTPクライアントとサーバーを構築するための強力な機能を提供します。

*   **`http.Client`**: HTTPリクエストを送信するための高レベルなインターフェースです。通常、ユーザーは`Client.Do()`メソッドなどを使ってリクエストを送信します。
*   **`http.Transport`**: `Client`の内部で使用され、実際のネットワーク接続の管理、接続の再利用（コネクションプーリング）、プロキシ設定、TLS設定、リクエストの多重化などを担当します。`Transport`は、複数のリクエストに対して単一のTCP接続を再利用することで、パフォーマンスを向上させます。
*   **`http.Request`と`http.Response`**: HTTPリクエストとレスポンスを表す構造体です。
*   **`CancelRequest`**: `http.Client`のメソッドで、進行中のHTTPリクエストをキャンセルするために使用されます。Go 1.7以降は`context.Context`を使ったキャンセルが推奨されていますが、それ以前のバージョンや特定のユースケースでは`CancelRequest`が使われていました。内部的には、`Transport`がリクエストとそれに対応するキャンセル関数を管理しています。

### 2. Goにおけるキャンセル処理と`context.Context`

Goでは、長時間実行される操作（ネットワークI/O、CPU集中型計算など）を協調的にキャンセルするための標準的なメカニズムとして`context.Context`が導入されています。

*   `context.Context`は、API境界を越えてデッドライン、キャンセルシグナル、その他のリクエストスコープの値を伝達するために使用されます。
*   `context.WithCancel(parent Context)`関数は、新しい`Context`と、その`Context`をキャンセルするための`CancelFunc`を返します。`CancelFunc`が呼び出されると、その`Context`から派生したすべての`Context`がキャンセルされ、関連する操作が中断されます。
*   `net/http`パッケージでは、`http.Request`に`context.Context`を含めることができ、これによりリクエストのライフサイクル全体でキャンセルシグナルを伝達できます。`Client.Do(req.WithContext(ctx))`のように使用します。

このコミットが対象としているGoのバージョンでは、`CancelRequest`メソッドが主要なキャンセルメカニズムとして存在しており、`Transport`内部でリクエストとキャンセル関数を関連付けるための`reqCanceler`マップが使用されていました。

### 3. 競合状態（Race Condition）

競合状態とは、複数のゴルーチン（またはスレッド）が共有リソースに同時にアクセスし、そのアクセス順序によってプログラムの最終結果が非決定的に変化するバグの一種です。

*   **共有リソース**: このケースでは、`Transport`内部の`reqCanceler`マップや、接続の状態などが該当します。
*   **非決定性**: 競合状態が存在すると、プログラムは同じ入力に対しても異なる結果を生成する可能性があり、デバッグが非常に困難になります。
*   **危険性**: データ破損、リソースリーク、デッドロック、クラッシュなど、様々な問題を引き起こす可能性があります。

このコミットでは、`getConn`が接続を確立し、`roundTrip`がその接続でリクエストを処理するまでの間に、別のゴルーチンがリクエストをキャンセルしようとすることで競合状態が発生していました。

### 4. ミューテックス（`sync.Mutex`）による排他制御

Goの`sync`パッケージは、並行処理のプリミティブを提供します。

*   **`sync.Mutex`**: 相互排他ロック（ミューテックス）を実装します。`Lock()`メソッドでロックを取得し、`Unlock()`メソッドでロックを解放します。これにより、一度に一つのゴルーチンだけが保護されたコードセクション（クリティカルセクション）を実行することを保証し、共有リソースへの同時アクセスを防ぎ、競合状態を回避します。
*   `Transport`内部の`reqCanceler`マップへのアクセスは、`Transport.reqMu`という`sync.Mutex`によって保護されています。しかし、このコミットが修正する問題は、ロックの粒度やタイミングに関するものでした。

## 技術的詳細

このコミットは、`net/http/transport.go`内の`Transport`構造体と`persistConn`構造体のメソッドに修正を加えることで、ダイヤルとキャンセルの間の競合状態を解消しています。

### 問題の具体的なシナリオ

以前の実装では、`Transport.getConn`が接続を取得した後、`persistConn.roundTrip`が呼び出される直前に、`Transport.setReqCanceler`を使ってリクエストのキャンセル関数を登録していました。

```go
// 古いコードの概略
func (t *Transport) getConn(...) {
    // ... 接続を取得または再利用 ...
    // ここではまだリクエストのキャンセル関数は適切に設定されていない
    return pc, nil
}

func (pc *persistConn) roundTrip(req *transportRequest) (resp *Response, err error) {
    pc.t.setReqCanceler(req.Request, pc.cancelRequest) // ここでキャンセル関数を登録
    // ... リクエスト処理 ...
}
```

この「接続を取得してからキャンセル関数を登録するまでの短いウィンドウ」で、もし`http.Client.CancelRequest(req)`が呼び出された場合、`CancelRequest`は`Transport.reqCanceler`マップから`req`に対応するキャンセル関数を削除しようとします。しかし、この時点ではまだ適切なキャンセル関数が登録されていないため、`CancelRequest`は何もしないか、あるいはダミーの関数を削除するだけで、実際のリクエストはキャンセルされずに続行されてしまう可能性がありました。

### 修正アプローチ

このコミットは、以下の2つの主要な変更によってこの競合状態を解決します。

1.  **`replaceReqCanceler`関数の導入**:
    `Transport`に新しいメソッド`replaceReqCanceler(r *Request, fn func()) bool`が追加されました。この関数は、既存のリクエストのキャンセル関数を置き換えることを目的としています。
    *   この関数は、`t.reqCanceler`マップに`r`（リクエスト）のエントリが存在するかどうかを検査します。
    *   もしエントリが存在しない場合（つまり、リクエストが既にキャンセルされて`CancelRequest`によってクリアされている場合）、`false`を返します。
    *   エントリが存在し、`fn`が`nil`でない場合は、既存のキャンセル関数を`fn`で置き換えます。
    *   `fn`が`nil`の場合は、エクエストのエントリをマップから削除します（これは`CancelRequest`が内部的に行う動作と同じです）。
    *   この関数の重要な点は、リクエストが既にキャンセルされているかどうかを`ok`変数で確認できる点です。

2.  **`getConn`と`roundTrip`の連携強化**:
    *   **`getConn`でのダミーキャンセル関数の設定**: `getConn`が接続を返却する直前に、`t.setReqCanceler(req, func(){})`を呼び出し、リクエストに対して一時的な（ダミーの）キャンセル関数を設定します。
        ```go
        // src/net/http/transport.go (getConn内)
        // set request canceler to some non-nil function so we
        // can detect whether it was cleared between now and when
        // we enter roundTrip
        t.setReqCanceler(req, func(){})
        ```
        これにより、`getConn`が接続を返した時点では、`reqCanceler`マップにそのリクエストのエントリが必ず存在するようにします。もしこの短いウィンドウで`CancelRequest`が呼び出された場合、このダミー関数がクリアされることになります。

    *   **`roundTrip`での`replaceReqCanceler`の使用とキャンセルチェック**: `persistConn.roundTrip`の冒頭で、従来の`setReqCanceler`の代わりに新しく導入された`replaceReqCanceler`を使用します。
        ```go
        // src/net/http/transport.go (roundTrip内)
        if !pc.t.replaceReqCanceler(req.Request, pc.cancelRequest) {
            pc.t.putIdleConn(pc)
            return nil, errRequestCanceled
        }
        ```
        `replaceReqCanceler`は、`getConn`で設定されたダミー関数を実際の`pc.cancelRequest`関数（この接続でリクエストをキャンセルするための関数）に置き換えようとします。
        *   もし`replaceReqCanceler`が`false`を返した場合、それは`getConn`がダミー関数を設定してから`roundTrip`が呼び出されるまでの間に、リクエストが既にキャンセルされ、ダミー関数がクリアされてしまったことを意味します。この場合、`roundTrip`はすぐに`errRequestCanceled`を返して処理を中断し、接続をアイドル状態に戻します。
        *   `replaceReqCanceler`が`true`を返した場合、実際のキャンセル関数が正常に設定されたことを意味し、`roundTrip`は通常通りリクエストの処理を続行します。

### テストの追加

この修正を検証するために、`src/net/http/transport_test.go`に`TestTransportDialCancelRace`という新しいテストが追加されました。このテストは、`getConn`と`roundTrip`の間のタイミングで`CancelRequest`が呼び出されるシナリオをシミュレートし、リクエストが正しくキャンセルされることを確認します。

*   `SetEnterRoundTripHook`というテストフックが導入され、`roundTrip`が実行される直前に任意の関数を呼び出せるようにしています。
*   テストでは、このフックを使って`roundTrip`が開始される瞬間に`tr.CancelRequest(req)`を呼び出し、競合状態を意図的に発生させます。
*   期待される結果は、`RoundTrip`が`ExportErrRequestCanceled`エラーを返すことです。これにより、修正が正しく機能していることが確認されます。

これらの変更により、`getConn`と`roundTrip`の間の短いウィンドウでキャンセルイベントが失われることがなくなり、リクエストのキャンセルがより堅牢に処理されるようになりました。

## コアとなるコードの解説

### `src/net/http/transport.go`

#### `replaceReqCanceler`関数の追加

```go
func (t *Transport) replaceReqCanceler(r *Request, fn func()) bool {
	t.reqMu.Lock()
	defer t.reqMu.Unlock()
	_, ok := t.reqCanceler[r]
	if !ok {
		return false
	}
	if fn != nil {
		t.reqCanceler[r] = fn
	} else {
		delete(t.reqCanceler, r)
	}
	return true
}
```

*   この関数は、`Transport`の内部マップ`t.reqCanceler`に格納されている特定のリクエスト`r`のキャンセル関数を安全に置き換えるために導入されました。
*   `t.reqMu.Lock()`と`defer t.reqMu.Unlock()`により、マップへのアクセスは排他的に保護され、競合状態を防ぎます。
*   `_, ok := t.reqCanceler[r]`で、まず`r`に対応するエントリがマップに存在するかどうかを確認します。
    *   `!ok`の場合（エントリが存在しない場合）、それはリクエストが既にキャンセルされ、`CancelRequest`によってマップから削除されたことを意味します。この場合、`false`を返して呼び出し元にその状態を伝えます。
    *   `ok`の場合（エントリが存在する場合）、`fn`が`nil`でなければ、既存のキャンセル関数を`fn`で置き換えます。`fn`が`nil`であれば、エントリをマップから削除します。
*   この関数の戻り値`bool`は、リクエストが`replaceReqCanceler`が呼び出される前にキャンセルされたかどうかを判断するための重要なシグナルとなります。

#### `getConn`での変更

```go
func (t *Transport) getConn(req *Request, cm connectMethod) (*persistConn, error) {
    if pc := t.getIdleConn(cm); pc != nil {
        // set request canceler to some non-nil function so we
        // can detect whether it was cleared between now and when
        // we enter roundTrip
        t.setReqCanceler(req, func(){})
    	return pc, nil
    }
    // ... 既存の接続がない場合のダイヤル処理 ...
}
```

*   `getConn`がアイドル接続を取得した場合（または新しい接続を確立した場合）、`persistConn`を返す直前に`t.setReqCanceler(req, func(){})`を呼び出しています。
*   ここで設定される`func(){}`は、何もしないダミーのキャンセル関数です。
*   この目的は、`getConn`が接続を返した時点で、`reqCanceler`マップにそのリクエストのエントリが必ず存在するようにすることです。これにより、`getConn`から`roundTrip`が呼び出されるまでの短い期間に`CancelRequest`が呼び出されても、削除すべきエントリがマップに存在するため、キャンセルイベントが「失われる」ことを防ぎます。もしキャンセルされた場合、このダミー関数がマップから削除されます。

#### `roundTrip`での変更

```go
func (pc *persistConn) roundTrip(req *transportRequest) (resp *Response, err error) {
    if hook := testHookEnterRoundTrip; hook != nil {
        hook()
    }
    if !pc.t.replaceReqCanceler(req.Request, pc.cancelRequest) {
        pc.t.putIdleConn(pc)
        return nil, errRequestCanceled
    }
    // ... 既存のロジック ...
}
```

*   `roundTrip`の冒頭で、まずテスト用のフック`testHookEnterRoundTrip`が呼び出されます（これはテストでのみ使用されます）。
*   次に、`!pc.t.replaceReqCanceler(req.Request, pc.cancelRequest)`という条件が評価されます。
    *   `pc.cancelRequest`は、この`persistConn`がリクエストをキャンセルするために使用する実際の関数です。
    *   `replaceReqCanceler`は、`getConn`で設定されたダミー関数を`pc.cancelRequest`に置き換えようとします。
    *   もし`replaceReqCanceler`が`false`を返した場合、それは`getConn`がダミー関数を設定してからこの`roundTrip`が実行されるまでの間に、リクエストが既にキャンセルされ、ダミー関数がマップから削除されてしまったことを意味します。
    *   この場合、`roundTrip`はすぐに`pc.t.putIdleConn(pc)`を呼び出して現在の接続をアイドル状態に戻し、`errRequestCanceled`エラーを返して処理を中断します。これにより、既にキャンセルされたリクエストに対して無駄な処理が続行されることを防ぎます。
*   `replaceReqCanceler`が`true`を返した場合、実際のキャンセル関数が正常に設定されたことを意味し、`roundTrip`は通常通りリクエストの処理を続行します。

### `src/net/http/transport_test.go`

#### `TestTransportDialCancelRace`の追加

```go
func TestTransportDialCancelRace(t *testing.T) {
	defer afterTest(t)

	ts := httptest.NewServer(HandlerFunc(func(w ResponseWriter, r *Request) {}))
	defer ts.Close()

	tr := &Transport{}
	defer tr.CloseIdleConnections()

	req, err := NewRequest("GET", ts.URL, nil)
	if err != nil {
		t.Fatal(err)
	}
	SetEnterRoundTripHook(func() {
		tr.CancelRequest(req)
	})
	defer SetEnterRoundTripHook(nil)
	res, err := tr.RoundTrip(req)
	if err != ExportErrRequestCanceled {
		t.Errorf("expected canceled request error; got %v", err)
		if err == nil {
			res.Body.Close()
		}
	}
}
```

*   このテストは、`net/http`クライアントの`Transport`におけるダイヤルとキャンセルの競合状態を再現し、修正が正しく機能することを確認します。
*   `httptest.NewServer`でダミーのHTTPサーバーを起動します。
*   `http.Transport`のインスタンスを作成します。
*   `SetEnterRoundTripHook`を使って、`persistConn.roundTrip`が実行される直前に`tr.CancelRequest(req)`を呼び出すようにフックを設定します。これにより、競合状態が発生するタイミングでリクエストがキャンセルされるようにします。
*   `tr.RoundTrip(req)`を呼び出し、リクエストを送信します。
*   期待される結果は、`RoundTrip`が`ExportErrRequestCanceled`エラーを返すことです。もしこのエラーが返されなければ、競合状態が修正されていないか、またはキャンセルが正しく処理されていないことを意味します。

これらの変更とテストにより、`net/http`パッケージは、リクエストのダイヤルとキャンセルの間のタイミングの問題に対してより堅牢になりました。

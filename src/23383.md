# [インデックス 23383] ファイルの概要

このコミットでは、Goコンパイラ (`cmd/gc`) のエラーメッセージ表示に関する変更が行われています。具体的には、内部的に生成されるブランク識別子 (`_`) の表現が、ユーザーに表示されるエラーメッセージにおいてより分かりやすい形に修正されました。

変更されたファイルは以下の通りです。

*   `src/cmd/internal/gc/fmt.go`: Goコンパイラがコードのフォーマットやエラーメッセージの生成に使用する内部関数が含まれています。このファイルで、ブランク識別子の表示ロジックが修正されました。
*   `test/fixedbugs/issue9521.go`: このコミットで修正された問題 (`issue9521`) を検証するための新しいテストファイルです。ブランク識別子の誤用が正しくエラーとして検出され、かつエラーメッセージが期待通りに表示されることを確認します。

## コミット

Goコンパイラ (`cmd/gc`) において、エラーメッセージ内で内部的なブランク識別子 (`~b` で始まる識別子) が表示されるのを抑制し、代わりにユーザーにとってより理解しやすい `_` (ブランク識別子) を表示するように変更しました。これにより、ユーザーの混乱を軽減します。

## 変更の背景

Go言語には「ブランク識別子 (`_`)」という特殊な識別子が存在します。これは、変数や戻り値を受け取る際に、その値を明示的に破棄したい場合に使用されます。例えば、関数の複数の戻り値のうち一部だけが必要な場合や、インポートしたパッケージの副作用だけを利用したい場合などに利用されます。

しかし、Goコンパイラ (`cmd/gc`) の内部では、このブランク識別子も他の変数と同様に処理される必要があり、内部的には `~b` のようなプレフィックスと数字を組み合わせた一意の識別子（例: `~b1`, `~b2`）に変換されていました。

この内部的な識別子が、コンパイルエラーメッセージにそのまま表示されてしまうという問題がありました。例えば、ブランク識別子を誤って使用した場合に、ユーザーには `cannot use ~b1 (type []int) as type int in assignment` のようなエラーメッセージが表示されていました。この `~b1` という表記はGo言語の仕様には存在しない内部的なものであり、ユーザーにとっては非常に分かりにくく、混乱を招く原因となっていました。

このコミットは、このようなユーザーの混乱を解消し、エラーメッセージの可読性を向上させることを目的としています。具体的には、エラーメッセージの生成時に `~b` 形式の内部識別子を、ユーザーが認識している `_` に変換して表示するように修正されました。

## 前提知識の解説

### Go言語のブランク識別子 (`_`)

Go言語のブランク識別子 (`_`) は、特定の値を意図的に無視するために使用される特別な識別子です。これは以下のような状況で利用されます。

1.  **多値戻り値の無視**: Goの関数は複数の値を返すことができます。そのうち一部の値だけが必要な場合、不要な値を受け取る位置に `_` を置きます。
    ```go
    func getCoords() (int, int, error) {
        return 10, 20, nil
    }

    x, _, err := getCoords() // y座標を無視
    ```
2.  **未使用変数の回避**: Goでは宣言された変数は必ず使用しなければなりません。使用しない変数がある場合、その変数名を `_` にすることでコンパイルエラーを回避できます。
    ```go
    func main() {
        _ = "hello" // この文字列は使用されないが、エラーにならない
    }
    ```
3.  **パッケージの副作用のみの利用**: パッケージをインポートする際に、そのパッケージの初期化処理（`init` 関数など）だけを実行し、パッケージ内の識別子を直接使用しない場合に `_` を使用します。
    ```go
    import _ "net/http/pprof" // pprofのHTTPハンドラを登録するが、pprofパッケージの識別子は直接使わない
    ```

ブランク識別子は、Go言語の設計思想である「明示性」と「簡潔性」を両立させるための重要な機能です。

### Goコンパイラ (`cmd/gc`) の内部動作とシンボル管理

Goコンパイラ (`cmd/gc`) は、Goのソースコードを機械語に変換する役割を担っています。この過程で、コンパイラはソースコード内のすべての識別子（変数名、関数名など）を内部的に管理します。

コンパイラの内部では、ソースコード上の識別子と、それに対応する内部的なシンボル（Symbol）が関連付けられます。シンボルは、識別子の名前、型、スコープ、メモリ上の位置などの情報を持つデータ構造です。

ブランク識別子 (`_`) は、ソースコード上では単一の `_` として表現されますが、コンパイラ内部ではそれぞれが異なる、一意のシンボルとして扱われる必要があります。これは、例えば `_ = a` と `_ = b` のように複数のブランク識別子が同じスコープ内で使用された場合でも、それぞれが異なるメモリ位置や目的を持つ可能性があるためです。

このため、`cmd/gc` はブランク識別子を内部的に `~b` で始まる一意の識別子（例: `~b1`, `~b2`, `~b3` など）に変換して管理していました。この `~b` は "blank" の略であり、コンパイラが内部的にブランク識別子を区別するための命名規則です。

### エラーメッセージ生成と `fmt.go`

Goコンパイラは、コンパイル中に構文エラーや型エラーなどの問題を発見すると、ユーザーにエラーメッセージを出力します。これらのエラーメッセージは、コンパイラの内部状態をユーザーが理解できる形式に変換して表示する役割を担っています。

`src/cmd/internal/gc/fmt.go` ファイルは、Goコンパイラのバックエンドの一部であり、主に抽象構文木 (AST) のノードや型情報を文字列としてフォーマットする機能を提供します。これは、デバッグ情報の出力、コード生成、そしてエラーメッセージの生成など、様々な場面で利用されます。

このファイル内の `exprfmt` 関数は、式 (`Node`) を文字列としてフォーマットする主要な関数の一つです。この関数は、コンパイラの現在の「フォーマットモード」に応じて、異なる方法でノードを表現することができます。

## 技術的詳細

### `fmt.go` ファイルの役割と `exprfmt` 関数

`src/cmd/internal/gc/fmt.go` は、Goコンパイラの内部で、ASTノードや型情報を人間が読める形式の文字列に変換するためのユーティリティ関数群を提供します。これは、コンパイラのデバッグ出力、コード生成、そして特にエラーメッセージの生成において重要な役割を果たします。

`exprfmt` 関数は、Goの式を表す `Node` オブジェクトを受け取り、それを文字列に変換します。この関数は、コンパイラの現在のコンテキスト（例えば、エクスポート目的か、エラーメッセージ表示目的かなど）に応じて、異なるフォーマットを適用できるように設計されています。

### `fmtmode` の種類と意味

`exprfmt` 関数は、`fmtmode` というグローバル変数（またはそれに準ずるコンテキスト情報）を参照して、どのようにノードをフォーマットするかを決定します。このコミットに関連する `fmtmode` の値は以下の通りです。

*   `FExp` (Format Export): 主にエクスポートされるシンボルや、内部的なコード生成の際に使用されるフォーマットモードです。このモードでは、内部的な識別子もそのまま表示されることがあります。
*   `FErr` (Format Error): エラーメッセージを生成する際に使用されるフォーマットモードです。このモードでは、ユーザーにとって分かりやすい形式で情報を表示することが求められます。

コミット前のコードでは、`FExp` モードの場合にのみ `~b` 識別子を `_` に変換していましたが、エラーメッセージ表示時 (`FErr`) には変換が行われていませんでした。

### `n.Sym.Name[0] == '~' && n.Sym.Name[1] == 'b'` の条件

この条件は、現在の `Node` オブジェクト `n` が参照するシンボル (`n.Sym`) の名前が、Goコンパイラ内部でブランク識別子を表すために使用される `~b` プレフィックスで始まっているかどうかをチェックしています。

*   `n.Sym != nil`: シンボルが存在することを確認します。
*   `n.Sym.Name[0] == '~'`: シンボル名の最初の文字が `~` であることを確認します。
*   `n.Sym.Name[1] == 'b'`: シンボル名の2番目の文字が `b` であることを確認します。

この条件が真である場合、そのシンボルは内部的なブランク識別子 (`~b1`, `~b2` など) であると判断されます。

### なぜ `FErr` モードが追加されたのか

コミット前のコードでは、`fmtmode == FExp` の場合にのみ `~b` 識別子を `_` に変換していました。これは、エクスポートされるシンボル名や内部的なコード生成の際に、ブランク識別子を `_` として扱う必要があったためと考えられます。

しかし、エラーメッセージを生成する際 (`fmtmode == FErr`) には、この変換ロジックが適用されていませんでした。その結果、エラーメッセージには `~b1` のような内部的な識別子がそのまま表示され、ユーザーを混乱させていました。

このコミットでは、`FErr` モードの場合にも `FExp` と同様に `~b` 識別子を `_` に変換するように変更することで、エラーメッセージの可読性を向上させ、ユーザーエクスペリエンスを改善しました。

## コアとなるコードの変更箇所

`src/cmd/internal/gc/fmt.go` ファイルの `exprfmt` 関数内の以下の行が変更されました。

```diff
--- a/src/cmd/internal/gc/fmt.go
+++ b/src/cmd/internal/gc/fmt.go
@@ -1127,7 +1127,7 @@ func exprfmt(n *Node, prec int) string {
 		// Special case: name used as local variable in export.
 	// _ becomes ~b%d internally; print as _ for export
 	case ONAME:
-		if fmtmode == FExp && n.Sym != nil && n.Sym.Name[0] == '~' && n.Sym.Name[1] == 'b' {
+		if (fmtmode == FExp || fmtmode == FErr) && n.Sym != nil && n.Sym.Name[0] == '~' && n.Sym.Name[1] == 'b' {
 			return "_"

```

## コアとなるコードの解説

変更は、`ONAME` (名前付き識別子) を処理する `case` ブロック内で行われています。

元のコード:
`if fmtmode == FExp && n.Sym != nil && n.Sym.Name[0] == '~' && n.Sym.Name[1] == 'b' {`

変更後のコード:
`if (fmtmode == FExp || fmtmode == FErr) && n.Sym != nil && n.Sym.Name[0] == '~' && n.Sym.Name[1] == 'b' {`

この変更は、条件式に `|| fmtmode == FErr` を追加しています。

*   **変更前**: `fmtmode` が `FExp` (エクスポートフォーマットモード) の場合にのみ、シンボル名が `~b` で始まる内部的なブランク識別子を `_` に変換していました。
*   **変更後**: `fmtmode` が `FExp` **または** `FErr` (エラーフォーマットモード) の場合に、シンボル名が `~b` で始まる内部的なブランク識別子を `_` に変換するようになりました。

これにより、コンパイラがエラーメッセージを生成する際 (`fmtmode == FErr`) に、内部的な `~b` 識別子がユーザーに表示されることなく、代わりに標準のブランク識別子 `_` が表示されるようになります。これは、ユーザーがエラーメッセージをより直感的に理解できるようにするための重要な改善です。

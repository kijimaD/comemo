# [インデックス 21458] ファイルの概要

このコミットは、Go言語のCgoツールにおける変更を反映しています。具体的には、Goツールチェインから`6c`（GoのCコンパイラ）が不要になった「ポスト-6c」の世界に対応するため、Cgoのコードとドキュメントが更新されました。これにより、`6c`への言及が削除または`6g`（Goコンパイラ）に置き換えられ、Cgoが生成する一部のCソース出力が不要になりました。

## 元コミット内容

`cmd/cgo`: ポスト-6cの世界を反映するようにコードとドキュメントを更新

gcツールチェインにはCコンパイラが含まれなくなったため、`6c`への言及は適切に削除または`6g`に置き換えられます。同様に、以前はCソース出力を生成していた一部のcgo関数は、もはやその必要がありません。

## 変更の背景

このコミットは、Go言語のツールチェインにおける重要な移行期を反映しています。Goの初期のバージョンでは、`gc`ツールチェイン（Goの公式ツールチェイン）の一部として、`6c`（amd64アーキテクチャ向けのCコンパイラ）、`8c`（armアーキテクチャ向け）、`5c`（386アーキテクチャ向け）といったCコンパイラが含まれていました。これらのCコンパイラは、Goコンパイラ自体の一部がCで書かれていたため、Goのビルドプロセスで必要とされていました。

しかし、Go 1.5（2015年8月リリース）に向けて、Goコンパイラ（`6g`など）はGo言語自体で書き直され、「セルフホスティング」されるようになりました。これにより、Goのビルドプロセスにおいて外部のCコンパイラ（`6c`など）への依存がなくなりました。このコミットは、Go 1.5のリリースに先立つ2015年1月に行われており、`6c`が不要になるという将来の変更を見越して、`cgo`ツールがその新しい環境に適応するための準備作業の一環です。

具体的には、`cgo`はGoとCの相互運用を可能にするツールであり、GoコードからC関数を呼び出したり、CコードからGo関数を呼び出したりする際に、GoとCの間の橋渡しとなるコードを生成します。`6c`がツールチェインから外れることで、`cgo`が生成するコードやその処理フローも変更する必要が生じました。特に、`6c`がコンパイルすることを前提としていたCソースファイルの生成や、`#pragma`ディレクティブによるリンカへの指示方法などが影響を受けます。この変更は、Goツールチェイン全体の簡素化と、Go言語の独立性を高めるという長期的な目標に沿ったものです。

## 前提知識の解説

### Cgoとは

Cgoは、GoプログラムがC言語のコードを呼び出したり、C言語のコードからGo関数を呼び出したりするためのGoツールです。Goは通常、GoランタイムとGoコンパイラによって完全に管理された環境で動作しますが、Cgoを使用することで、既存のCライブラリを利用したり、OSの低レベルな機能にアクセスしたりすることが可能になります。

Cgoの基本的な仕組みは以下の通りです。
1.  Goソースファイル内に`import "C"`という特殊なインポート文を記述し、その直後にC言語のコード（プリアンブルと呼ばれる）を記述します。
2.  Goコード内で`C.関数名`や`C.型名`のようにCのシンボルを参照します。
3.  `go build`コマンドが実行されると、`cgo`ツールがGoとCの間の相互運用に必要な「グルーコード」（GoとCの間の呼び出し規約を変換するコード）を生成します。
4.  生成されたGoコードはGoコンパイラ（`6g`など）で、生成されたCコードはCコンパイラ（通常はGCCやClang）でコンパイルされます。
5.  最終的に、Goのリンカ（`6l`など）が、コンパイルされたGoオブジェクトファイルとCオブジェクトファイルをリンクして実行可能ファイルを生成します。

### Goツールチェインとコンパイラ (`6g`, `6c`, `gcc`)

*   **`gc`ツールチェイン**: Go言語の公式かつ主要なツールチェインです。これには、Goコンパイラ、アセンブラ、リンカなどが含まれます。
*   **`6g`**: `gc`ツールチェインの一部であるGoコンパイラです。`amd64`アーキテクチャ向けのGoコードをコンパイルします。同様に、`8g`はARM向け、`5g`は386向けです。
*   **`6c`**: かつて`gc`ツールチェインの一部であったCコンパイラです。`amd64`アーキテクチャ向けのCコードをコンパイルしていました。Go 1.5以降、GoコンパイラがGo自身で書かれるようになったため、その役割は終了しました。
*   **`gcc`**: GNU Compiler CollectionのCコンパイラです。Cgoは、Goの`gc`ツールチェインのCコンパイラ（`6c`など）だけでなく、システムにインストールされている`gcc`（またはClangなどの互換コンパイラ）も利用してCコードをコンパイルできます。特に、複雑なCライブラリやシステムライブラリとのリンクには`gcc`が使われることが多かったです。

### 内部リンキングと外部リンキング

Goのリンカ（`6l`など）は、Goプログラムを最終的な実行可能ファイルにリンクする際に、主に2つのモードで動作します。

*   **内部リンキング (Internal Linking)**: Goのリンカが、Goコードだけでなく、Cgoによって生成されたCオブジェクトファイルも直接処理してリンクするモードです。このモードでは、GoのリンカがCのオブジェクトファイルの構造を理解し、シンボル解決を行います。
*   **外部リンキング (External Linking)**: GoのリンカはGoコードのみを処理し、Goのオブジェクトファイル（`go.o`など）を生成します。その後、システムにインストールされている外部リンカ（通常は`gcc`）を呼び出して、GoのオブジェクトファイルとCのオブジェクトファイルを結合し、最終的な実行可能ファイルを生成するモードです。このモードは、Goのリンカが直接処理できない複雑なCライブラリや、特定のリンカフラグが必要な場合に利用されます。

このコミットの変更は、特に`6c`の廃止に伴い、Cgoが生成するリンキング関連の指示（`#pragma`ディレクティブなど）の扱いにも影響を与えています。

## 技術的詳細

このコミットの主要な技術的変更点は、`6c`コンパイラの廃止に伴い、Cgoの内部処理と生成されるファイル、そしてドキュメントが更新されたことです。

1.  **`6c`への依存の排除**:
    *   以前は、CgoはGoソースファイル（`x.go`, `y.go`）から`x.cgo1.go`（`6g`用）と`_cgo_defun.c`（`6c`用）などのファイルを生成していました。このコミットにより、`_cgo_defun.c`のような`6c`がコンパイルすることを前提としたファイル生成の必要性がなくなりました。
    *   `src/cmd/cgo/out.go`の`writeDefs`関数や`writeDefsFunc`関数から、`6c`向けの出力ストリーム（`fc`）を引数として受け取ることがなくなりました。これは、`6c`向けのCソースコードを生成する必要がなくなったことを直接的に示しています。

2.  **リンキングディレクティブの変更**:
    *   以前は、リンカへの指示（動的ライブラリのインポート、シンボルのエクスポートなど）は、`6c`がコンパイルするCソースファイル内に`#pragma cgo_import_dynamic`のような形式で記述されていました。
    *   このコミットにより、これらのディレクティブはGoソースファイル内で`//go:cgo_import_dynamic`のような`//go:`ディレクティブ形式で記述されるようになりました。これは、Goコンパイラ（`6g`）がこれらのディレクティブを直接処理し、生成されるGoオブジェクトファイル（`.6`ファイル）に埋め込むことを意味します。これにより、`6c`を介さずにリンカに情報を伝えることが可能になります。
    *   具体的には、`_cgo_import.c`というCファイルが生成されなくなり、代わりに`_cgo_import.go`というGoファイルが生成されるようになりました。この`_cgo_import.go`ファイルには、`//go:cgo_import_dynamic`などのディレクティブが含まれます。

3.  **Cgo生成ファイルの変更**:
    *   `doc.go`の「Translating Go」セクションで、Cgoが生成するファイルリストが更新されました。
        *   `_cgo_defun.c`（`6c`用）がリストから削除され、`gcc`用として`_cgo_defun.c`が残る形になりました（これは`gccgo`コンパイラを使用する場合）。
        *   `_cgo_import.c`が`_cgo_import.go`に置き換えられました。
        *   `_cgo_export.h`が追加されました。
        *   `_cgo_flags`というファイルが追加され、代替ビルドツール向けのフラグを格納するようになりました。
    *   最終的なGoパッケージの構成も変更され、`_cgo_defun.6`（`6c`コンパイル済みオブジェクト）や`_cgo_import.6`（`6c`コンパイル済みオブジェクト）が不要になり、`_go_.6`が`_cgo_gotypes.go`, `_cgo_import.go`, `*.cgo1.go`をまとめて含むようになりました。

4.  **GoとCの関数呼び出しスタブの変更**:
    *   `_cgo_gotypes.go`内で生成されるC関数呼び出しのGo側スタブの記述方法が変更されました。以前はGo側で外部宣言のみを行い、実装は`6c`がコンパイルするCファイルに依存していましたが、新しい形式では`//go:cgo_import_static`や`//go:linkname`ディレクティブを使用して、Go側で直接C関数のシンボルを参照し、`runtime.cgocall`を呼び出すGo関数として実装されるようになりました。これにより、`6c`を介さずにGoコンパイラが直接C関数呼び出しのスタブを生成できるようになります。

これらの変更は、GoツールチェインがCコンパイラに依存しない「ブートストラップ可能」な状態に移行する過程で、`cgo`がその新しいアーキテクチャに適応するために不可欠なものでした。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

1.  **`src/cmd/cgo/doc.go`**:
    *   `Usage:`セクションで、`go tool cgo`の引数から`file.go`が`gofiles...`に変更され、複数のGoファイルを指定できるようになったことを示唆しています。
    *   `-dynout`、`-dynpackage`、`-dynlinker`フラグの説明が更新されました。
    *   「Translating Go」セクションで、`6c`への言及が`6g`に置き換えられ、Cgoが生成するファイルリストが更新されました。特に、`_cgo_defun.c`が`6c`用から`gcc`用（`gccgo`の場合）に変更され、`_cgo_import.c`が`_cgo_import.go`に置き換えられました。
    *   `_cgo_gotypes.go`で生成されるGo関数のスタブの例が、`//go:cgo_import_static`と`//go:linkname`ディレクティブを含む新しい形式に更新されました。
    *   リンキングディレクティブのセクションで、`#pragma`形式のディレクティブが`//go:`形式のディレクティブに置き換えられました（例: `#pragma cgo_import_dynamic` -> `//go:cgo_import_dynamic`）。

2.  **`src/cmd/cgo/main.go`**:
    *   `dynout`、`dynpackage`、`dynlinker`フラグのコメントが微修正されました。機能的な変更はありません。

3.  **`src/cmd/cgo/out.go`**:
    *   `writeDefs`関数のコメントが「`6g`と`gcc`によってコンパイルされる出力ファイルを作成する」に更新され、`6c`への言及が削除されました。
    *   `writeDefsFunc`関数から`fc`（`6c`向けの出力ライター）引数が削除されました。
    *   `writeExports`関数から`fc`引数が削除されました。
    *   `writeGccgoExports`関数から`fc`引数が削除されました。
    *   `writeOutput`関数のコメントが「`6g`によってコンパイルされるスタブを作成する」に更新され、`6c`への言及が削除されました。
    *   `writeOutput`関数内で、`6c`と`gcc`の出力について言及していたコメントが「`gcc`出力」のみに修正されました。
    *   `structType`関数や`writeOutputFunc`関数内のコメントで、`6c`のレイアウトにマッチさせるという記述が`6g`のレイアウトにマッチさせるという記述に修正されました。
    *   `packedAttribute`関数内のコメントで、`6c/8c/5c`のレイアウトにマッチさせるという記述が`6g`のレイアウトにマッチさせるという記述に修正されました。

## コアとなるコードの解説

*   **`src/cmd/cgo/doc.go`の変更**:
    *   ドキュメントの更新は、ユーザーや開発者に対して、`cgo`の動作が`6c`の存在に依存しなくなったことを明確に伝えるためのものです。特に、リンキングディレクティブが`#pragma`から`//go:`形式に変わったことは、Goコンパイラが直接これらの指示を処理するようになったという重要な変更を示しています。これにより、CgoのビルドプロセスがよりGoツールチェインに統合され、外部のCコンパイラへの依存が減ることを意味します。

*   **`src/cmd/cgo/out.go`の変更**:
    *   `writeDefsFunc`、`writeExports`、`writeGccgoExports`関数から`fc`（`6c`向けの出力ライター）引数が削除されたことは、`cgo`がもはや`6c`がコンパイルするCソースコードを生成する必要がないことを直接的に示しています。これは、`6c`がGoツールチェインから削除されるという大きな変更の具体的な実装側面です。
    *   コメントの変更は、コードが意図する動作を正確に反映させるためのものです。`6c`が不要になったため、`cgo`が生成するCコードは主に`gcc`（または他のシステムCコンパイラ）によってコンパイルされることを前提とするようになりました。また、GoとCの間のデータ構造のレイアウトを合わせる際に、`6c`ではなく`6g`の規約に合わせるようになったことも、Goコンパイラがこのプロセスにおいてより中心的な役割を果たすようになったことを示しています。

これらの変更は、Goツールチェインのセルフホスティング化という大きな目標に向けた、`cgo`の内部的な適応とクリーンアップ作業の一環です。

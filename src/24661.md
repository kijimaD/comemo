# [インデックス 24661] ファイルの概要

## コミット
`[dev.ssa] cmd/compile: add decompose pass`

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドに「decompose (分解)」パスを追加するものです。このパスの主な目的は、文字列、スライス、インターフェースといった複合型オブジェクトを、ターゲットアーキテクチャが操作しやすいより単純な構成要素に分解することです。

## 変更の背景

Goコンパイラは、プログラムの最適化とコード生成のためにSSA (Static Single Assignment) 形式を使用します。SSA形式では、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。しかし、文字列、スライス、インターフェースのようなGoの複合型は、内部的には複数の要素（例えば、文字列はデータポインタと長さ、スライスはデータポインタ、長さ、容量）で構成されています。

これらの複合型をSSA形式で直接扱うことは、コンパイラのバックエンドにとって複雑さを増す要因となります。特に、異なる制御フローパスから来る複合型の値をマージするPhi関数（`OpPhi`）を処理する際に問題が生じます。例えば、`if/else`文の各ブランチで異なる文字列が生成され、その結果がマージされる場合、SSAバックエンドは文字列全体を一つの「値」として扱う必要があります。これは、レジスタ割り当てや低レベルの最適化において非効率的になる可能性があります。

このコミットの背景には、複合型をその構成要素（例えば、文字列をポインタと長さに）に分解することで、SSAバックエンドがより単純な型（ポインタや整数）としてこれらを扱い、より効果的な最適化（レジスタ割り当ての改善など）を可能にするという目的があります。これにより、生成される機械語コードの効率が向上することが期待されます。

## 前提知識の解説

1.  **SSA (Static Single Assignment) 形式**:
    *   コンパイラ最適化の中間表現の一つで、プログラム中の各変数が一度だけ代入されるように変換されます。これにより、データフロー解析が非常に簡単になり、デッドコード削除、共通部分式除去、レジスタ割り当てなどの最適化が効率的に行えます。
    *   SSA形式では、複数の制御フローパスが合流する点（例: `if/else`文の終わり、ループの開始）で、異なるパスから来る同じ論理変数に対応する値をマージするために「Phi関数」（Φ関数）が導入されます。Phi関数は、どのパスから来たかに応じて適切な値を選択します。

2.  **Goの複合型とその内部表現**:
    *   **文字列 (string)**: 読み取り専用のバイト列へのポインタと、その長さを保持します。
    *   **スライス ([]T)**: 要素へのポインタ、スライスの長さ、スライスの容量（基底配列のサイズ）を保持します。
    *   **インターフェース (interface{})**: 型情報（`itab`または`_type`）へのポインタと、実際のデータへのポインタ（`data`）を保持します。
    *   **構造体 (struct)**: 複数のフィールドをまとめたものです。
    *   **配列 ([N]T)**: 固定長の要素のシーケンスです。

3.  **GoコンパイラのSSAバックエンド**:
    *   Goのコンパイラは、ソースコードを抽象構文木 (AST) に変換し、その後、中間表現としてSSA形式に変換します。
    *   SSAバックエンドは、このSSA形式のコードに対して様々な最適化を適用し、最終的にターゲットアーキテクチャの機械語コードを生成します。
    *   `generic.rules`は、SSAオペレーションをより低レベルなオペレーションやターゲット固有のオペレーションに書き換えるためのルールを定義したファイルです。

## 技術的詳細

このコミットで導入された`decompose`パスは、GoコンパイラのSSAバックエンドにおいて、複合型（文字列、スライス、インターフェース）の`OpPhi`オペレーションを、その構成要素（ポインタ、長さ、容量など）に対する個別の`OpPhi`オペレーションに変換します。

具体的には、以下の複合型が分解の対象となります。

*   **文字列 (string)**: `OpPhi`オペレーションが、文字列のデータポインタに対する`OpPhi`と、文字列の長さに対する`OpPhi`に分解されます。最終的に`OpStringMake`オペレーションによって再構築されます。
*   **スライス ([]T)**: `OpPhi`オペレーションが、スライスのデータポインタ、長さ、容量それぞれに対する`OpPhi`に分解されます。最終的に`OpSliceMake`オペレーションによって再構築されます。
*   **インターフェース (interface{})**: `OpPhi`オペレーションが、インターフェースの型情報ポインタ（`itab`）とデータポインタ（`data`）それぞれに対する`OpPhi`に分解されます。最終的に`OpIMake`オペレーションによって再構築されます。

この分解は、`decompose.go`ファイル内の`decompose`関数によって行われます。この関数は、SSAグラフ内のすべてのブロックと値（`Value`）を走査し、複合型の`OpPhi`オペレーションを見つけると、対応する分解関数（`decomposeStringPhi`, `decomposeSlicePhi`, `decomposeInterfacePhi`）を呼び出します。

分解された構成要素は、`generic.rules`ファイルに定義された書き換えルールによって、さらに低レベルの操作に変換されます。例えば、`StringPtr`や`StringLen`といったオペレーションは、`StringMake`オペレーションの引数から直接ポインタや長さを抽出するように書き換えられます。同様に、`SlicePtr`, `SliceLen`, `SliceCap`や`ITab`, `IData`といったオペレーションも導入され、複合型の各要素へのアクセスを可能にします。

この変更により、SSAバックエンドは複合型全体を一つの大きな値として扱うのではなく、その構成要素を個別に最適化できるようになります。これにより、レジスタ割り当ての効率が向上し、不要なメモリ操作が削減される可能性があります。

**現在の制限事項**:
*   配列は、動的なインデックス付けがSSA変数ではサポートされていないため、このパスでは分解されません。
*   構造体は、このコミット時点ではまだ分解の対象外であり、今後のコミットで対応が予定されています。
*   分解後、元の複合型としての関連性（例: 文字列のポインタと長さのペア）が失われるため、デバッグ情報の生成に影響が出る可能性が指摘されています。

## コアとなるコードの解説

このコミットの核心は、`src/cmd/compile/internal/ssa/decompose.go`で定義されている`decompose`パスと、`src/cmd/compile/internal/ssa/gen/generic.rules`および`src/cmd/compile/internal/ssa/rewritegeneric.go`で定義されている書き換えルールにあります。

**`decompose.go`の主要なロジック**:

```go
// decompose converts phi ops on compound types into phi
// ops on simple types.
// (The remaining compound ops are decomposed with rewrite rules.)
func decompose(f *Func) {
	for _, b := range f.Blocks {
		for _, v := range b.Values {
			if v.Op != OpPhi {
				continue
			}
			switch {
			case v.Type.IsString():
				decomposeStringPhi(v)
			case v.Type.IsSlice():
				decomposeSlicePhi(v)
			case v.Type.IsInterface():
				decomposeInterfacePhi(v)
			//case v.Type.IsStruct():
			//	decomposeStructPhi(v)
			case v.Type.Size() > f.Config.IntSize:
				f.Unimplementedf("undecomposed type %s", v.Type)
			}
		}
	}
	// TODO: decompose complex?
	// TODO: decompose 64-bit ops on 32-bit archs?
}
```
この`decompose`関数は、SSA関数`f`内のすべてのブロック`b`と値`v`を反復処理します。もし値`v`が`OpPhi`オペレーションであり、かつその型が文字列、スライス、またはインターフェースである場合、それぞれ対応する`decomposeStringPhi`、`decomposeSlicePhi`、`decomposeInterfacePhi`関数を呼び出します。これらの関数は、元の複合型の`OpPhi`を、その構成要素（ポインタ、長さ、容量など）に対する複数の`OpPhi`に置き換え、最終的に`OpStringMake`、`OpSliceMake`、`OpIMake`といった「Make」オペレーションで再構築します。

例えば、`decomposeStringPhi`は以下のようになります（簡略化）。

```go
func decomposeStringPhi(v *Value) {
	// ... 型情報の取得 ...

	// 文字列のポインタと長さのための新しいPhiオペレーションを作成
	ptr := v.Block.NewValue0(v.Line, OpPhi, ptrType)
	len := v.Block.NewValue0(v.Line, OpPhi, lenType)

	// 元のPhiオペレーションの各引数に対して、StringPtrとStringLenオペレーションを適用し、
	// 新しいPhiオペレーションの引数として追加
	for _, a := range v.Args {
		ptr.AddArg(a.Block.NewValue1(v.Line, OpStringPtr, ptrType, a))
		len.AddArg(a.Block.NewValue1(v.Line, OpStringLen, lenType, a))
	}

	// 元のPhiオペレーションをOpStringMakeに変換し、新しいポインタと長さのPhiを引数として設定
	v.Op = OpStringMake
	v.resetArgs()
	v.AddArg(ptr)
	v.AddArg(len)
}
```
このプロセスにより、SSAグラフ上では複合型がその構成要素に分解され、個々の要素に対して最適化が適用できるようになります。

**`generic.rules`と`rewritegeneric.go`の役割**:

`generic.rules`ファイルには、SSAオペレーションをより具体的なオペレーションに変換するためのパターンマッチングルールが記述されています。このコミットでは、特に複合型の`Load`、`Store`、および`Const`オペレーションを分解するためのルールが追加されています。

例えば、文字列の`Load`オペレーションに対するルールは以下のようになります（簡略化）。

```
(Load <t> ptr mem) && t.IsString() ->
  (StringMake
    (Load <config.fe.TypeBytePtr()> ptr mem)
    (Load <config.fe.TypeUintptr()>
      (OffPtr <config.fe.TypeUintptr().PtrTo()> [config.PtrSize] ptr)
      mem))
```
これは、「文字列型`t`の`Load`オペレーションは、`StringMake`オペレーションに変換され、その引数として文字列のポインタと長さをメモリからロードするオペレーションが使われる」ことを意味します。

これらのルールは`rewritegeneric.go`内の`rewriteValuegeneric`関数によって適用され、SSAグラフを段階的に変換していきます。`decompose`パスが`OpPhi`を処理し、`rewritegeneric`が`Load`や`Store`などの他の複合型オペレーションを処理することで、複合型全体の分解が実現されます。

*   **文字列 (string)**: `OpPhi`オペレーションが、文字列のデータポインタに対する`OpPhi`と、文字列の長さに対する`OpPhi`に分解されます。最終的に`OpStringMake`オペレーションによって再構築されます。
*   **スライス ([]T)**: `OpPhi`オペレーションが、スライスのデータポインタ、長さ、容量それぞれに対する`OpPhi`に分解されます。最終的に`OpSliceMake`オペレーションによって再構築されます。
*   **インターフェース (interface{})**: `OpPhi`オペレーションが、インターフェースの型情報ポインタ（`itab`）とデータポインタ（`data`）それぞれに対する`OpPhi`に分解されます。最終的に`OpIMake`オペレーションによって再構築されます。

この分解は、`decompose.go`ファイル内の`decompose`関数によって行われます。この関数は、SSAグラフ内のすべてのブロックと値（`Value`）を走査し、複合型の`OpPhi`オペレーションを見つけると、対応する分解関数（`decomposeStringPhi`, `decomposeSlicePhi`, `decomposeInterfacePhi`）を呼び出します。

分解された構成要素は、`generic.rules`ファイルに定義された書き換えルールによって、さらに低レベルの操作に変換されます。例えば、`StringPtr`や`StringLen`といったオペレーションは、`StringMake`オペレーションの引数から直接ポインタや長さを抽出するように書き換えられます。同様に、`SlicePtr`, `SliceLen`, `SliceCap`や`ITab`, `IData`といったオペレーションも導入され、複合型の各要素へのアクセスを可能にします。

この変更により、SSAバックエンドは複合型全体を一つの大きな値として扱うのではなく、その構成要素を個別に最適化できるようになります。これにより、レジスタ割り当ての効率が向上し、不要なメモリ操作が削減される可能性があります。

**現在の制限事項**:
*   配列は、動的なインデックス付けがSSA変数ではサポートされていないため、このパスでは分解されません。
*   構造体は、このコミット時点ではまだ分解の対象外であり、今後のコミットで対応が予定されています。
*   分解後、元の複合型としての関連性（例: 文字列のポインタと長さのペア）が失われるため、デバッグ情報の生成に影響が出る可能性が指摘されています。

## コアとなるコードの解説

このコミットの核心は、`src/cmd/compile/internal/ssa/decompose.go`で定義されている`decompose`パスと、`src/cmd/compile/internal/ssa/gen/generic.rules`および`src/cmd/compile/internal/ssa/rewritegeneric.go`で定義されている書き換えルールにあります。

**`decompose.go`の主要なロジック**:

```go
// decompose converts phi ops on compound types into phi
// ops on simple types.
// (The remaining compound ops are decomposed with rewrite rules.)
func decompose(f *Func) {
	for _, b := range f.Blocks {
		for _, v := range b.Values {
			if v.Op != OpPhi {
				continue
			}
			switch {
			case v.Type.IsString():
				decomposeStringPhi(v)
			case v.Type.IsSlice():
				decomposeSlicePhi(v)
			case v.Type.IsInterface():
				decomposeInterfacePhi(v)
			//case v.Type.IsStruct():
			//	decomposeStructPhi(v)
			case v.Type.Size() > f.Config.IntSize:
				f.Unimplementedf("undecomposed type %s", v.Type)
			}
		}
	}
	// TODO: decompose complex?
	// TODO: decompose 64-bit ops on 32-bit archs?
}
```
この`decompose`関数は、SSA関数`f`内のすべてのブロック`b`と値`v`を反復処理します。もし値`v`が`OpPhi`オペレーションであり、かつその型が文字列、スライス、またはインターフェースである場合、それぞれ対応する`decomposeStringPhi`、`decomposeSlicePhi`、`decomposeInterfacePhi`関数を呼び出します。これらの関数は、元の複合型の`OpPhi`を、その構成要素（ポインタ、長さ、容量など）に対する複数の`OpPhi`に置き換え、最終的に`OpStringMake`、`OpSliceMake`、`OpIMake`といった「Make」オペレーションで再構築します。

例えば、`decomposeStringPhi`は以下のようになります（簡略化）。

```go
func decomposeStringPhi(v *Value) {
	// ... 型情報の取得 ...

	// 文字列のポインタと長さのための新しいPhiオペレーションを作成
	ptr := v.Block.NewValue0(v.Line, OpPhi, ptrType)
	len := v.Block.NewValue0(v.Line, OpPhi, lenType)

	// 元のPhiオペレーションの各引数に対して、StringPtrとStringLenオペレーションを適用し、
	// 新しいPhiオペレーションの引数として追加
	for _, a := range v.Args {
		ptr.AddArg(a.Block.NewValue1(v.Line, OpStringPtr, ptrType, a))
		len.AddArg(a.Block.NewValue1(v.Line, OpStringLen, lenType, a))
	}

	// 元のPhiオペレーションをOpStringMakeに変換し、新しいポインタと長さのPhiを引数として設定
	v.Op = OpStringMake
	v.resetArgs()
	v.AddArg(ptr)
	v.AddArg(len)
}
```
このプロセスにより、SSAグラフ上では複合型がその構成要素に分解され、個々の要素に対して最適化が適用できるようになります。

**`generic.rules`と`rewritegeneric.go`の役割**:

`generic.rules`ファイルには、SSAオペレーションをより具体的なオペレーションに変換するためのパターンマッチングルールが記述されています。このコミットでは、特に複合型の`Load`、`Store`、および`Const`オペレーションを分解するためのルールが追加されています。

例えば、文字列の`Load`オペレーションに対するルールは以下のようになります（簡略化）。

```
(Load <t> ptr mem) && t.IsString() ->
  (StringMake
    (Load <config.fe.TypeBytePtr()> ptr mem)
    (Load <config.fe.TypeUintptr()>
      (OffPtr <config.fe.TypeUintptr().PtrTo()> [config.PtrSize] ptr)
      mem))
```
これは、「文字列型`t`の`Load`オペレーションは、`StringMake`オペレーションに変換され、その引数として文字列のポインタと長さをメモリからロードするオペレーションが使われる」ことを意味します。

これらのルールは`rewritegeneric.go`内の`rewriteValuegeneric`関数によって適用され、SSAグラフを段階的に変換していきます。`decompose`パスが`OpPhi`を処理し、`rewritegeneric`が`Load`や`Store`などの他の複合型オペレーションを処理することで、複合型全体の分解が実現されます。

# [インデックス 26885] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）における文字列連結（`OADDSTR`）のバッファサイズ計算の誤りを修正するものです。具体的には、非エスケープ文字列連結のためにスタック上に一時バッファを割り当てる際のサイズ計算ロジックが誤っていた点を修正し、不要な一時バッファの生成を回避します。

## 元コミット内容

`cmd/compile: fix OADDSTR buffer size calculation`

このコードが最初にコミットされた [https://golang.org/cl/3120](https://golang.org/cl/3120) 以来、サイズ計算が誤っていました。その結果、コンパイラは非エスケープ文字列連結のために常にスタック上に一時バッファを割り当てていました。しかし、コンパイラは常に同じサイズ（32バイト）のバッファを割り当て、ランタイムは連結された文字列が収まる場合にのみ一時バッファを使用するため（`runtime/string.go` の `rawstringtmp` でチェックされます）、実際には実用上の違いはありませんでした。

この変更の目的は、使用されない一時バッファをスタック上に生成するのを避けることです。

## 変更の背景

Goコンパイラは、文字列連結操作（`OADDSTR`）を処理する際に、最適化の一環として、結果の文字列を格納するための一時バッファをスタック上に割り当てることがあります。これは特に、文字列がヒープにエスケープしない（`EscNone`）場合に適用されます。この一時バッファのサイズを計算するロジックに、初期の実装から誤りがありました。

具体的には、連結される個々のリテラル文字列の長さを合計してバッファサイズを決定するべき箇所で、連結式全体のプロパティを参照していました。この誤りにより、コンパイラは常に一時バッファを割り当てていましたが、そのサイズは固定の32バイトであり、Goランタイムの `rawstringtmp` 関数が、実際に連結される文字列の合計長がこのバッファに収まるかどうかをチェックしていました。結果として、バッファが不要な場合でも割り当てられていましたが、ランタイムのチェックにより誤用されることはなく、実用上の問題は発生していませんでした。

しかし、不要なリソースの割り当ては、たとえそれが小さな一時バッファであっても、コンパイラの効率性や生成されるバイナリの品質の観点からは望ましくありません。このコミットは、この長年のバグを修正し、コンパイラが実際に必要とされない一時バッファを生成するのを防ぐことを目的としています。これにより、コンパイラがより正確なコードを生成し、わずかながらもリソースの無駄を削減します。

## 前提知識の解説

### Goコンパイラ (`gc`)
Go言語の公式コンパイラは `gc` と呼ばれ、Goのソースコードを機械語に変換する役割を担います。コンパイルプロセスには、字句解析、構文解析、型チェック、中間表現（IR）の生成、最適化、コード生成など、複数のフェーズがあります。このコミットが関連するのは、中間表現の処理と最適化のフェーズです。

### `OADDSTR`
`OADDSTR` は、Goコンパイラの内部で文字列連結操作を表すオペレーションコード（OpCode）です。Go言語で `s1 + s2 + s3` のように文字列を連結するコードを書くと、コンパイラはこの操作を `OADDSTR` として内部的に表現し、処理します。

### `EscNone` (エスケープ解析)
Goコンパイラは「エスケープ解析（Escape Analysis）」と呼ばれる最適化を行います。これは、変数がヒープに割り当てられるべきか、それともスタックに割り当てられるべきかを決定するプロセスです。
*   **スタック割り当て**: 関数呼び出しのたびに確保され、関数が終了すると自動的に解放されるメモリ領域です。高速で、ガベージコレクションの対象外です。
*   **ヒープ割り当て**: プログラムの実行中に動的に確保されるメモリ領域です。ガベージコレクションの対象となり、スタックよりもアクセスが遅い傾向があります。
`EscNone` は、エスケープ解析の結果、変数がヒープにエスケープせず、スタックに割り当てられることが決定された状態を示します。文字列連結の結果が `EscNone` と判断された場合、コンパイラはスタック上に一時バッファを割り当てて、そこに連結結果を格納しようと試みることがあります。

### Goにおける文字列連結
Go言語では、`+` 演算子を使って文字列を連結できます。内部的には、Goランタイムは連結操作を効率的に処理するために様々な最適化を行います。特に、結果の文字列の長さが事前にわかる場合、必要なサイズのメモリを一度だけ割り当てて、そこに各部分文字列をコピーすることで、複数回のメモリ再割り当てを避けることができます。このコミットは、この「必要なサイズのメモリを一度だけ割り当てる」ためのサイズ計算に関するものです。

### 一時バッファと `rawstringtmp`
コンパイラがスタック上に一時バッファを割り当てる場合、そのバッファは連結操作の結果を一時的に保持するために使用されます。`runtime/string.go` にある `rawstringtmp` 関数は、この一時バッファが実際に使用可能かどうか、つまり連結される文字列の合計長がバッファサイズに収まるかを最終的にチェックする役割を担っています。このチェックがあるため、今回のバグは実用上の問題を引き起こしませんでした。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの `src/cmd/compile/internal/gc/walk.go` ファイル内の `addstr` 関数における文字列連結の長さ計算ロジックの修正です。

`addstr` 関数は、`OADDSTR` オペレーションコードを持つノード（文字列連結式）を処理し、その結果を生成します。この関数内で、連結される文字列がヒープにエスケープしない（`n.Esc == EscNone`）場合、スタック上に一時バッファを割り当てるために、連結されるリテラル文字列の合計長を計算します。

元のコードは以下のようになっていました。

```go
 		for l := n.List; l != nil; l = l.Next {
-			if n.Op == OLITERAL {
-				sz += int64(len(n.Val().U.(string)))
+			if l.N.Op == OLITERAL {
+				sz += int64(len(l.N.Val().U.(string)))
 			}
 		}
```

ここで `n` は文字列連結式全体のノードを表し、`n.List` は連結される個々の部分文字列を表すノードのリンクリストです。`l` はこのリンクリストの現在の要素であり、`l.N` がその部分文字列のノードです。

問題は、`if n.Op == OLITERAL` と `len(n.Val().U.(string))` の部分にありました。
*   `n.Op == OLITERAL`: これは、連結式全体（`n`）がリテラルであるかどうかをチェックしています。しかし、文字列連結式全体がリテラルであることは稀であり、通常は複数のリテラルや変数が連結されます。このチェックは、個々の部分文字列がリテラルであるかを判断する目的には適していません。
*   `len(n.Val().U.(string))`: 同様に、`n.Val()` は連結式全体の値を参照しようとしますが、これは連結式がまだ評価されていない段階では意味をなしません。

この誤ったロジックのため、`sz`（合計サイズ）は常に0のままでした。しかし、コンパイラは固定の32バイトのバッファを割り当てるようにフォールバックしていたため、このバグは実用上の問題を引き起こしませんでした。

修正は、`n.Op` を `l.N.Op` に、`n.Val()` を `l.N.Val()` に変更することです。
*   `l.N.Op == OLITERAL`: これにより、リンクリストの現在の要素（`l.N`）がリテラル文字列である場合にのみ、その長さを計算対象とします。
*   `len(l.N.Val().U.(string))`: `l.N.Val()` は、現在のリテラル文字列ノードの実際の値を取得し、その長さを正確に `sz` に加算します。

この修正により、`sz` は連結されるすべてのリテラル文字列の合計長を正確に反映するようになり、コンパイラは必要に応じて適切なサイズの一時バッファを割り当て、不要なバッファの生成を回避できるようになります。

## コアとなるコードの解説

変更は `src/cmd/compile/internal/gc/walk.go` ファイル内の `addstr` 関数にあります。この関数は、Goコンパイラのバックエンドの一部であり、抽象構文木（AST）を走査してコード生成のための準備を行います。

具体的には、`addstr` 関数内で文字列連結ノード `n` がエスケープしない（`n.Esc == EscNone`）と判断された場合、スタック上に一時バッファを割り当てるためのサイズ `sz` を計算するループがあります。

```go
		for l := n.List; l != nil; l = l.Next {
			// ...
		}
```
このループは、連結される個々の部分文字列を表すノードのリンクリスト `n.List` をイテレートします。`l` はリストの現在の要素であり、`l.N` がその部分文字列のノードです。

**変更前:**
```go
-			if n.Op == OLITERAL {
-				sz += int64(len(n.Val().U.(string)))
```
この行では、`n.Op` をチェックしていました。`n` は文字列連結式全体のノードであり、そのオペレーション（`n.Op`）は `OADDSTR` です。したがって、`n.Op == OLITERAL` という条件は常に偽となり、この `if` ブロック内のコードは実行されませんでした。結果として、`sz` は常に初期値の `0` のままでした。

**変更後:**
```go
+			if l.N.Op == OLITERAL {
+				sz += int64(len(l.N.Val().U.(string)))
```
この修正では、`n.Op` を `l.N.Op` に、`n.Val()` を `l.N.Val()` に変更しています。
*   `l.N.Op == OLITERAL`: これにより、現在処理している部分文字列ノード `l.N` がリテラル文字列であるかどうかを正しくチェックします。例えば、`"hello" + "world"` という連結では、ループの最初のイテレーションで `l.N` は `"hello"` のノードになり、`l.N.Op` は `OLITERAL` となります。
*   `len(l.N.Val().U.(string))`: `l.N.Val()` は、現在のリテラル文字列ノードの実際の値（例: `"hello"`)を取得し、その長さを `sz` に加算します。

この修正により、`sz` は連結されるすべてのリテラル文字列の合計長を正確に計算するようになります。この正確なサイズ情報に基づいて、コンパイラはスタック上に適切なサイズの一時バッファを割り当てることができ、不要な固定サイズのバッファ割り当てを回避します。これは、コンパイラが生成するコードの効率性を向上させる小さな最適化です。

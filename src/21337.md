## 元コミット内容

Go言語のリンカである `cmd/5l` (ARM), `cmd/6l` (x86-64), `cmd/8l` (x86-32) において、動的シンボル (dynamic symbols) のセクションインデックスが誤って生成されていた問題を修正します。以前のコードでは、動的シンボルの種類 (テキスト、読み取り専用データ、データ、BSS) に応じて、`11` から `14` までの「謎の定数」をセクションインデックスとして割り当てていました。しかし、実行可能ファイルを生成する際には、シンボルが定義されているか未定義であるかのみが重要であり、これらの具体的なセクションインデックスは実際には使用されていませんでした。このコミットは、この不要で混乱を招くコードを削除し、未定義シンボルと区別するためにセクションインデックス `1` を使用するように変更します。

## 変更の背景

Go言語のリンカは、コンパイルされたGoプログラムを最終的な実行可能ファイルやライブラリに結合する役割を担っています。このプロセスの中で、シンボル（関数名、変数名など）の情報を管理し、それらがメモリ上のどのセクションに配置されるかを決定します。

このコミットの背景には、以下の問題がありました。

1.  **誤ったセクションインデックスの生成**: 以前のリンカは、動的シンボルに対して、そのシンボルが属するセクション（コード、データなど）を示すセクションインデックスを生成していました。しかし、これらのインデックスは、実際にはそのシンボルが定義されているか（`SHN_UNDEF`ではないか）を区別するためだけに用いられており、具体的なセクション番号としての意味は持っていませんでした。
2.  **「謎の定数」の存在**: コード内には `11`, `12`, `13`, `14` といったマジックナンバー（謎の定数）がセクションインデックスとしてハードコードされており、コードの可読性と保守性を著しく低下させていました。これらの定数が何を意味するのか、なぜその値なのかがコードからは全く読み取れませんでした。
3.  **不要な複雑性**: 実行可能ファイルの生成において、動的シンボルのセクションインデックスは、シンボルが「定義済み」であるか「未定義」であるか（`SHN_UNDEF`）を区別できれば十分でした。それにもかかわらず、シンボルの種類に応じて異なる「誤った」セクションインデックスを割り当てるという、不要な複雑なロジックが存在していました。

このコミットは、これらの問題を解決し、リンカのコードをよりシンプルで理解しやすいものにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **リンカ (Linker)**:
    *   コンパイラによって生成されたオブジェクトファイル（機械語コードとデータを含む）を結合し、実行可能ファイルやライブラリを生成するプログラムです。
    *   シンボル解決（あるオブジェクトファイルで定義された関数や変数を、別のオブジェクトファイルから参照できるようにする）や、メモリレイアウトの決定（コードやデータをメモリ上のどこに配置するか）を行います。
    *   Go言語では、`cmd/5l`, `cmd/6l`, `cmd/8l` はそれぞれ異なるCPUアーキテクチャ（ARM, x86-64, x86-32）向けのリンカでした。これらはGo 1.5以降、`cmd/link` に統合されましたが、このコミットがなされた2014年時点ではまだ個別のリンカが存在していました。

2.  **ELF (Executable and Linkable Format)**:
    *   Unix系システムで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。
    *   ELFファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、そして様々なセクション（`.text`、`.data`、`.rodata`、`.bss`など）で構成されます。
    *   **セクション (Section)**: コード、初期化済みデータ、未初期化データなど、プログラムの異なる種類の情報を格納する領域です。
        *   `.text`: 実行可能な機械語コード。
        *   `.rodata`: 読み取り専用データ（文字列リテラルなど）。
        *   `.data`: 初期化済みデータ（グローバル変数など）。
        *   `.bss`: 未初期化データ（ゼロ初期化されるグローバル変数など）。
    *   **シンボルテーブル (Symbol Table)**: プログラム内の関数や変数などのシンボルに関する情報（名前、値、サイズ、型、そして**属するセクションのインデックス**など）を格納します。
    *   **動的シンボル (Dynamic Symbols)**: 実行時に解決されるシンボルです。主に共有ライブラリ（DLLや.soファイル）を使用する場合に重要になります。実行可能ファイル自体が持つシンボルとは異なり、外部のライブラリからインポートされるシンボルや、外部にエクスポートされるシンボルがこれに該当します。ELFファイルには、動的リンカが使用する `.dynsym` セクションに動的シンボルテーブルが格納されます。

3.  **セクションインデックス (Section Index / `sh_shndx`)**:
    *   ELFシンボルテーブルのエントリには、そのシンボルが定義されているセクションを示すインデックス (`st_shndx`) が含まれます。
    *   特別なセクションインデックスも存在します。
        *   `SHN_UNDEF`: シンボルがこのオブジェクトファイル内で定義されていないことを示します。つまり、外部で定義されているシンボル（未定義シンボル）です。リンカは、このようなシンボルを解決するために、他のオブジェクトファイルやライブラリを探します。

## 技術的詳細

このコミットの技術的な核心は、ELFフォーマットにおける動的シンボルのセクションインデックスの扱いにあります。

ELFの仕様では、シンボルテーブルのエントリ (`Elf_Sym` 構造体) には `st_shndx` というフィールドがあり、これはシンボルが定義されているセクションのインデックスを示します。しかし、動的シンボル、特に実行可能ファイル内の動的シンボルに関しては、この `st_shndx` の意味合いが少し異なります。

コミットメッセージが述べているように、実行可能ファイルを生成する際、動的シンボルについて重要なのは、そのシンボルが「定義済み」であるか「未定義」であるか、という点だけです。

*   **`SDYNIMPORT` (Dynamic Import)**: これは外部ライブラリからインポートされるシンボル、つまりこの実行可能ファイル内では「未定義」のシンボルです。この場合、`st_shndx` は `SHN_UNDEF` (0) に設定されます。これはリンカに対して、このシンボルは外部で解決する必要があることを伝えます。
*   **それ以外の動的シンボル**: これらは実行可能ファイル内で定義されている動的シンボルです。例えば、実行可能ファイル自身が外部にエクスポートするシンボルなどがこれに該当します。この場合、`st_shndx` は `SHN_UNDEF` 以外の値である必要があります。

以前のコードでは、後者の「定義済み」の動的シンボルに対して、シンボルの種類（テキスト、データなど）に応じて `11`, `12`, `13`, `14` といった具体的なセクションインデックスを割り当てていました。しかし、これらの値は実際のELFセクションヘッダテーブルのインデックスとは一致せず、単に `SHN_UNDEF` (0) と異なる値であれば何でもよかったのです。リンカは、これらの「誤った」インデックスを実際のセクションへのポインタとして使用するのではなく、単にシンボルが定義済みであることを示すフラグとして扱っていました。

この「謎の定数」は、コードの可読性を損ねるだけでなく、将来的にELFフォーマットの変更やリンカの内部構造の変更があった場合に、誤解やバグの原因となる可能性がありました。

コミットの変更は、この問題を解決するために、定義済みの動的シンボルに対して一律にセクションインデックス `1` を割り当てるようにします。`1` という値は `SHN_UNDEF` (0) とは異なるため、シンボルが定義済みであることを正しく示すことができます。また、この値自体に特別な意味を持たせないことで、コードの意図が明確になり、将来的な保守性が向上します。

なぜ `1` なのか？
コミットメッセージには「Unfortunately, this happens too early to put in real section indexes」とあります。これは、`adddynsym` 関数が実行される段階では、まだ最終的なELFセクションヘッダテーブルが完全に構築されておらず、シンボルが実際にどのセクションに配置されるかの「本当の」インデックスを決定できないことを示唆しています。そのため、`SHN_UNDEF` ではない、任意の有効な非ゼロ値を使用する必要があり、最もシンプルな `1` が選ばれたと考えられます。

## コアとなるコードの変更箇所

変更は `src/cmd/5l/asm.c`, `src/cmd/6l/asm.c`, `src/cmd/8l/asm.c` の3つのファイルにわたって行われています。これらのファイルは、それぞれ異なるアーキテクチャ向けのリンカの共通のアセンブリコード生成部分を扱っています。

各ファイルにおいて、`adddynsym` 関数内の `s->type == SDYNIMPORT` でない場合の `shndx` の設定ロジックが変更されています。

**変更前:**
```c
		else {
			switch(s->type) {
			default:
			case STEXT:
				t = 11;
				break;
			case SRODATA:
				t = 12;
				break;
			case SDATA:
				t = 13;
				break;
			case SBSS:
				t = 14;
				break;
			}
			adduint16(ctxt, d, t);
		}
```

**変更後:**
```c
		else
			adduint16(ctxt, d, 1);
```

## コアとなるコードの解説

`adddynsym` 関数は、動的シンボルテーブル (`.dynsym` セクション) にシンボルエントリを追加する役割を担っています。この関数内で、シンボルのセクションインデックス (`shndx`) が設定されます。

*   `s->type == SDYNIMPORT` の場合:
    *   これは、シンボルが外部から動的にインポートされる（つまり、このオブジェクトファイル内では未定義である）ことを意味します。
    *   この場合、`adduint16(ctxt, d, SHN_UNDEF);` が呼び出され、セクションインデックスとして `SHN_UNDEF` (通常は0) が設定されます。これは、リンカに対してこのシンボルが外部で解決されるべきであることを明確に伝えます。この部分は変更されていません。

*   `s->type != SDYNIMPORT` の場合 (変更の対象):
    *   これは、シンボルがこの実行可能ファイル内で定義されている動的シンボルであることを意味します。
    *   **変更前**: `switch` 文を使用して、シンボルの種類 (`STEXT`, `SRODATA`, `SDATA`, `SBSS`) に応じて `t` という変数に `11`, `12`, `13`, `14` といった値を割り当てていました。そして、この `t` の値をセクションインデックスとして `adduint16` で書き込んでいました。これらの値は、実際のELFセクションインデックスとは無関係な「謎の定数」でした。
    *   **変更後**: `switch` 文が完全に削除され、代わりに `adduint16(ctxt, d, 1);` が直接呼び出されています。これにより、定義済みの動的シンボルには一律にセクションインデックス `1` が割り当てられるようになりました。この `1` は `SHN_UNDEF` (0) とは異なるため、シンボルが定義済みであることを示す目的は果たしつつ、コードの複雑性を大幅に削減しています。

この変更により、リンカは動的シンボルのセクションインデックスをよりシンプルかつ正確に扱うようになり、コードの保守性と理解度が向上しました。

3.  **セクションインデックス (Section Index / `sh_shndx`)**:
    *   ELFシンボルテーブルのエントリには、そのシンボルが定義されているセクションを示すインデックス (`st_shndx`) が含まれます。
    *   特別なセクションインデックスも存在します。
        *   `SHN_UNDEF`: シンボルがこのオブジェクトファイル内で定義されていないことを示します。つまり、外部で定義されているシンボル（未定義シンボル）です。リンカは、このようなシンボルを解決するために、他のオブジェクトファイルやライブラリを探します。

## 技術的詳細

このコミットの技術的な核心は、ELFフォーマットにおける動的シンボルのセクションインデックスの扱いにあります。

ELFの仕様では、シンボルテーブルのエントリ (`Elf_Sym` 構造体) には `st_shndx` というフィールドがあり、これはシンボルが定義されているセクションのインデックスを示します。しかし、動的シンボル、特に実行可能ファイル内の動的シンボルに関しては、この `st_shndx` の意味合いが少し異なります。

コミットメッセージが述べているように、実行可能ファイルを生成する際、動的シンボルについて重要なのは、そのシンボルが「定義済み」であるか「未定義」であるか、という点だけです。

*   **`SDYNIMPORT` (Dynamic Import)**: これは外部ライブラリからインポートされるシンボル、つまりこの実行可能ファイル内では「未定義」のシンボルです。この場合、`st_shndx` は `SHN_UNDEF` (0) に設定されます。これはリンカに対して、このシンボルは外部で解決する必要があることを伝えます。
*   **それ以外の動的シンボル**: これらは実行可能ファイル内で定義されている動的シンボルです。例えば、実行可能ファイル自身が外部にエクスポートするシンボルなどがこれに該当します。この場合、`st_shndx` は `SHN_UNDEF` 以外の値である必要があります。

以前のコードでは、後者の「定義済み」の動的シンボルに対して、シンボルの種類（テキスト、データなど）に応じて `11`, `12`, `13`, `14` といった具体的なセクションインデックスを割り当てていました。しかし、これらの値は実際のELFセクションヘッダテーブルのインデックスとは一致せず、単に `SHN_UNDEF` (0) と異なる値であれば何でもよかったのです。リンカは、これらの「誤った」インデックスを実際のセクションへのポインタとして使用するのではなく、単にシンボルが定義済みであることを示すフラグとして扱っていました。

この「謎の定数」は、コードの可読性を損ねるだけでなく、将来的にELFフォーマットの変更やリンカの内部構造の変更があった場合に、誤解やバグの原因となる可能性がありました。

コミットの変更は、この問題を解決するために、定義済みの動的シンボルに対して一律にセクションインデックス `1` を割り当てるようにします。`1` という値は `SHN_UNDEF` (0) とは異なるため、シンボルが定義済みであることを正しく示すことができます。また、この値自体に特別な意味を持たせないことで、コードの意図が明確になり、将来的な保守性が向上します。

なぜ `1` なのか？
コミットメッセージには「Unfortunately, this happens too early to put in real section indexes」とあります。これは、`adddynsym` 関数が実行される段階では、まだ最終的なELFセクションヘッダテーブルが完全に構築されておらず、シンボルが実際にどのセクションに配置されるかの「本当の」インデックスを決定できないことを示唆しています。そのため、`SHN_UNDEF` ではない、任意の有効な非ゼロ値を使用する必要があり、最もシンプルな `1` が選ばれたと考えられます。

## コアとなるコードの変更箇所

変更は `src/cmd/5l/asm.c`, `src/cmd/6l/asm.c`, `src/cmd/8l/asm.c` の3つのファイルにわたって行われています。これらのファイルは、それぞれ異なるアーキテクチャ向けのリンカの共通のアセンブリコード生成部分を扱っています。

各ファイルにおいて、`adddynsym` 関数内の `s->type == SDYNIMPORT` でない場合の `shndx` の設定ロジックが変更されています。

**変更前:**
```c
		else {
			switch(s->type) {
			default:
			case STEXT:
				t = 11;
				break;
			case SRODATA:
				t = 12;
				break;
			case SDATA:
				t = 13;
				break;
			case SBSS:
				t = 14;
				break;
			}
			adduint16(ctxt, d, t);
		}
```

**変更後:**
```c
		else
			adduint16(ctxt, d, 1);
```

## コアとなるコードの解説

`adddynsym` 関数は、動的シンボルテーブル (`.dynsym` セクション) にシンボルエントリを追加する役割を担っています。この関数内で、シンボルのセクションインデックス (`shndx`) が設定されます。

*   `s->type == SDYNIMPORT` の場合:
    *   これは、シンボルが外部から動的にインポートされる（つまり、このオブジェクトファイル内では未定義である）ことを意味します。
    *   この場合、`adduint16(ctxt, d, SHN_UNDEF);` が呼び出され、セクションインデックスとして `SHN_UNDEF` (通常は0) が設定されます。これは、リンカに対してこのシンボルが外部で解決されるべきであることを明確に伝えます。この部分は変更されていません。

*   `s->type != SDYNIMPORT` の場合 (変更の対象):
    *   これは、シンボルがこの実行可能ファイル内で定義されている動的シンボルであることを意味します。
    *   **変更前**: `switch` 文を使用して、シンボルの種類 (`STEXT`, `SRODATA`, `SDATA`, `SBSS`) に応じて `t` という変数に `11`, `12`, `13`, `14` といった値を割り当てていました。そして、この `t` の値をセクションインデックスとして `adduint16` で書き込んでいました。これらの値は、実際のELFセクションインデックスとは無関係な「謎の定数」でした。
    *   **変更後**: `switch` 文が完全に削除され、代わりに `adduint16(ctxt, d, 1);` が直接呼び出されています。これにより、定義済みの動的シンボルには一律にセクションインデックス `1` が割り当てられるようになりました。この `1` は `SHN_UNDEF` (0) とは異なるため、シンボルが定義済みであることを示す目的は果たしつつ、コードの複雑性を大幅に削減しています。

この変更により、リンカは動的シンボルのセクションインデックスをよりシンプルかつ正確に扱うようになり、コードの保守性と理解度が向上しました。

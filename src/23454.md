# [インデックス 23454] ファイルの概要

このコミットは、Go言語のランタイムにおける`reflect`パッケージで作成された型（特にマップの要素型）のゼロ値のメモリ割り当て方法を最適化するものです。以前は`reflect`パッケージ内でゼロ値が事前に割り当てられていましたが、この変更により、マップの要素型として使用される際にオンデマンドで割り当てられ、かつ共有されるようになりました。これにより、不要なメモリ割り当てが削減され、特に大きな型を`reflect`で操作する際のメモリ効率が向上します。

## コミット

`runtime: allocate map element zero values for reflect-created types on demand`

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/7e26a2d9a80b825d019c2cdaf6437d89001506a9](https://github.com/golang/go/commit/7e26a2d9a80b825d019c2cdaf6437d89001506a9)

## 元コミット内容

```
runtime: allocate map element zero values for reflect-created types on demand

Preallocating them in reflect means that
(1) if you say _ = PtrTo(ArrayOf(1000000000, reflect.TypeOf(byte(0)))), you just allocated 1GB of data
(2) if you say it again, that's *another* GB of data.

The only use of t.zero in the runtime is for map elements.
Delay the allocation until the creation of a map with that element type,
and share the zeros.

The one downside of the shared zero is that it's not garbage collected,
but it's also never written, so the OS should be able to handle it fairly
efficiently.

Reviewed-on: https://go-review.googlesource.com/10111
Reviewed-by: Keith Randall <khr@golang.org>
```

## 変更の背景

Goの`reflect`パッケージは、プログラムの実行中に型情報を検査したり、動的に型を構築したりするための強力な機能を提供します。しかし、以前の実装では、`reflect`パッケージを使って新しい型（例えば、`ArrayOf`や`MapOf`など）が作成される際に、その型のゼロ値（初期値）を格納するためのメモリが事前に割り当てられていました。

この事前割り当てには、以下のような問題がありました。

1.  **過剰なメモリ消費**: `reflect.ArrayOf`のように非常に大きな配列型を定義した場合、たとえその配列型のインスタンスが実際に作成されなくても、そのゼロ値のために大量のメモリ（例: 1GB）が割り当てられていました。
2.  **重複するメモリ割り当て**: 同じ型のゼロ値が複数回必要とされる場合、そのたびに新しいメモリが割り当てられてしまい、メモリの無駄が生じていました。
3.  **`t.zero`の限定的な用途**: コミットメッセージによると、ランタイム内で`t.zero`（型のゼロ値を指すポインタ）が使用されるのは、主にマップの要素型としてのみでした。この限定的な用途に対して、`reflect`パッケージ内で常にゼロ値を事前割り当てするのは非効率的でした。

これらの問題に対処するため、ゼロ値の割り当てを、実際にマップがその要素型で作成されるまで遅延させ、さらに同じ型のゼロ値を共有するメカニズムが導入されました。これにより、メモリのフットプリントが大幅に削減され、特に`reflect`を多用するアプリケーションのパフォーマンスが向上します。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念とランタイムの内部構造に関する知識が必要です。

*   **`reflect`パッケージ**: Goの`reflect`パッケージは、実行時にプログラムの型情報を検査し、操作するための機能を提供します。`reflect.Type`インターフェースは、Goのあらゆる型のメタデータを表現します。`reflect.ArrayOf`, `reflect.MapOf`, `reflect.PtrTo`などの関数は、実行時に新しい型を動的に構築するために使用されます。
*   **型のゼロ値**: Goの各型には「ゼロ値」と呼ばれるデフォルトの初期値があります。例えば、`int`のゼロ値は`0`、`string`のゼロ値は`""`、ポインタやスライスのゼロ値は`nil`です。構造体の場合、そのフィールドがそれぞれのゼロ値で初期化されたものが構造体のゼロ値となります。
*   **`_type`構造体**: Goランタイムの内部では、すべての型が`_type`（または`rtype`）構造体で表現されます。この構造体には、型のサイズ、アラインメント、メソッドセットなどのメタデータが含まれます。以前は、この`_type`構造体の中に`zero`フィールドがあり、その型のゼロ値を指すポインタが格納されていました。
*   **マップ (`map`) の実装**: Goのマップはハッシュテーブルとして実装されており、ランタイムの`runtime/hashmap.go`でそのロジックが定義されています。マップに新しい要素を挿入する際、要素のゼロ値が必要になることがあります。
*   **`unsafe.Pointer`**: Goの`unsafe`パッケージは、型安全性をバイパスしてメモリを直接操作する機能を提供します。`unsafe.Pointer`は、任意の型のポインタを保持できる汎用ポインタ型です。ランタイムコードでは、メモリ管理や型変換のために頻繁に使用されます。
*   **`persistentalloc`**: Goランタイムの内部関数で、ガベージコレクションの対象とならないメモリを永続的に割り当てるために使用されます。これは、ランタイムの内部データ構造や、今回のゼロ値バッファのように、プログラムの寿命を通じて存在し続ける必要があるデータに利用されます。
*   **アトミック操作 (`atomicloadp`, `atomicstorep`)**: 複数のゴルーチンが共有データにアクセスする際に、競合状態を防ぐために使用される低レベルの操作です。`atomicloadp`はポインタをアトミックに読み込み、`atomicstorep`はポインタをアトミックに書き込みます。これにより、データの一貫性が保証されます。
*   **ミューテックス (`mutex`)**: 共有リソースへのアクセスを同期するためのロックメカニズムです。`lock()`と`unlock()`で保護されたクリティカルセクションでは、一度に一つのゴルーチンのみが実行を許可されます。

## 技術的詳細

このコミットの核心は、`reflect`パッケージで動的に作成される型の`t.zero`フィールドの初期化方法を変更し、`runtime`パッケージでその割り当てをオンデマンドかつ共有で行うようにした点です。

**変更前**:
`src/reflect/type.go`内の`ptrTo`, `ChanOf`, `MapOf`, `FuncOf`, `SliceOf`, `ArrayOf`といった型構築関数内で、`t.zero = unsafe.Pointer(&make([]byte, t.size)[0])`のようなコードによって、その型のゼロ値が即座にメモリに割り当てられていました。特に`ArrayOf`では、`if array.size > 0 { zero := make([]byte, array.size); array.zero = unsafe.Pointer(&zero[0]) }`という形で、サイズが0より大きい場合にゼロ値が割り当てられていました。

**変更後**:
1.  **`reflect`からのゼロ値割り当ての削除**: `src/reflect/type.go`から、`t.zero`フィールドへのゼロ値の事前割り当てに関するコードがすべて削除されました。これにより、`reflect`で型が作成された時点では、`t.zero`は`nil`のままとなります。
2.  **`runtime/hashmap.go`への`mapzero`関数の追加**:
    *   `makemap`関数（マップを作成するランタイム関数）の冒頭に`mapzero(t.elem)`が追加されました。これは、マップの要素型`t.elem`のゼロ値が必要になったときに、`mapzero`関数を呼び出してゼロ値を確保するトリガーとなります。
    *   `mapzero`関数は、`_type`構造体の`t.zero`フィールドがまだ`nil`の場合に、その型のゼロ値を割り当てます。
    *   **静的バッファの利用**: `t.size`（型のサイズ）が`zerotiny`配列（1024バイトの静的バッファ）に収まる場合、`zerotiny`の先頭アドレスを`t.zero`に設定します。これは非常に小さな型の場合に、動的なメモリ割り当てを避けるための最適化です。
    *   **動的バッファの利用と共有**: `t.size`が`zerotiny`よりも大きい場合、`zerobuf`というグローバルな構造体を利用して、より大きなゼロ値バッファを管理します。
        *   `zerobuf`は`lock`（ミューテックス）、`p`（バッファのポインタ）、`size`（バッファの現在のサイズ）を持ちます。
        *   `mapzero`が呼び出された際、`zerobuf.lock`でロックを取得し、`zerobuf.size`が要求された`t.size`よりも小さい場合は、`zerobuf.size`を倍々に増やしながら`persistentalloc`を使って新しい、より大きなバッファを割り当てます。
        *   割り当てられたバッファのポインタ`zerobuf.p`を`t.zero`に設定し、ロックを解放します。
        *   この`zerobuf`はガベージコレクションの対象外のメモリ領域から割り当てられ、一度確保されると、その後の同じかより小さいサイズのゼロ値要求に対して再利用されます。これにより、同じサイズのゼロ値が複数回必要とされても、メモリ割り当ては一度しか行われません。
    *   **アトミック操作**: `mapzero`関数の冒頭で`atomicloadp`を使って`t.zero`が`nil`でないかチェックし、割り当て後に`atomicstorep`を使って`t.zero`を設定しています。これにより、複数のゴルーチンが同時に`mapzero`を呼び出しても安全に処理が進むようになっています。

このアプローチにより、`reflect`で型を定義しただけではメモリが消費されず、実際にマップが作成されるまで割り当てが遅延されます。さらに、割り当てられたゼロ値バッファは共有されるため、メモリの重複割り当てがなくなります。コミットメッセージにあるように、この共有ゼロ値バッファはガベージコレクションの対象外ですが、決して書き込まれることがないため、OSは効率的にページ共有などの最適化を行うことが期待されます。

+// mapzero ensures that t.zero points at a zero value for type t.
+// Types known to the compiler are in read-only memory and all point
+// to a single zero in the bss of a large enough size.
+// Types allocated by package reflect are in writable memory and
+// start out with zero set to nil; we initialize those on demand.
+func mapzero(t *_type) {
+	// Already done?
+	// Check without lock, so must use atomicload to sync with atomicstore in allocation case below.
+	if atomicloadp(unsafe.Pointer(&t.zero)) != nil {
+		return
+	}
+
+	// Small enough for static buffer?
+	if t.size <= uintptr(len(zerotiny)) {
+		atomicstorep(unsafe.Pointer(&t.zero), unsafe.Pointer(&zerotiny[0]))
+		return
+	}
+
+	// Use allocated buffer.
+	lock(&zerobuf.lock)
+	if zerobuf.size < t.size {
+		if zerobuf.size == 0 {
+			zerobuf.size = 4 * 1024
+		}
+		for zerobuf.size < t.size {
+			zerobuf.size *= 2

+	}

## コアとなるコードの解説

### `src/reflect/type.go` の変更

`reflect`パッケージ内の型構築関数から`t.zero`への直接的なメモリ割り当てが削除されたことで、`reflect.ArrayOf(1000000000, reflect.TypeOf(byte(0)))`のような操作を行っても、その時点では1GBものメモリが割り当てられることはなくなりました。これにより、`reflect`で大きな型を定義する際のメモリフットプリントが大幅に削減されます。`t.zero`フィールドは、これらの関数が実行された直後は`nil`のままとなります。

### `src/runtime/hashmap.go` の変更

1.  **`makemap`関数への`mapzero`呼び出し追加**:
    `makemap`はGoのマップを作成するランタイム関数です。この関数が呼び出される際に、`mapzero(t.elem)`が実行されます。`t.elem`は作成されるマップの要素型を指します。これにより、マップが実際に作成され、その要素のゼロ値が必要になった時点で初めてゼロ値の確保が試みられます。

2.  **`zerobuf`と`zerotiny`グローバル変数**:
    *   `zerotiny [1024]byte`: 1024バイトの静的なバイト配列です。比較的小さな型のゼロ値は、この配列の先頭を指すように設定されます。これにより、ヒープ割り当てを完全に回避できます。
    *   `zerobuf struct { lock mutex; p *byte; size uintptr }`: より大きな型のゼロ値のために動的に割り当てられるバッファを管理する構造体です。`lock`は複数のゴルーチンからのアクセスを保護するためのミューテックス、`p`は割り当てられたバッファの先頭ポインタ、`size`は現在のバッファサイズを保持します。

3.  **`mapzero(t *_type)`関数**:
    この関数は、特定の型`t`のゼロ値ポインタ`t.zero`が利用可能であることを保証します。
    *   **`atomicloadp`による初期チェック**: `if atomicloadp(unsafe.Pointer(&t.zero)) != nil`
        まず、`t.zero`が既に設定されているか（`nil`でないか）をアトミックにチェックします。これにより、ロックを取得せずに高速に既存のゼロ値を利用できる可能性があります。
    *   **静的バッファの利用**: `if t.size <= uintptr(len(zerotiny))`
        型のサイズ`t.size`が`zerotiny`のサイズ（1024バイト）以下の場合、`zerotiny`の先頭アドレスを`t.zero`に設定します。`atomicstorep`を使ってアトミックに設定することで、他のゴルーチンからの可視性を保証します。
    *   **動的バッファの利用と拡張**:
        型のサイズが`zerotiny`よりも大きい場合、`zerobuf.lock`でミューテックスをロックし、排他的に処理を行います。
        `if zerobuf.size < t.size`の条件で、現在の`zerobuf`のサイズが要求された`t.size`よりも小さい場合、`zerobuf.size`を倍々に増やしていきます。この際、`persistentalloc`関数を使って、ガベージコレクションの対象とならないメモリ領域から新しいバッファを割り当て、`zerobuf.p`を更新します。
        `throw("map element too large")`は、32ビットシステムで2GBを超えるゼロ値が必要になった場合にパニックを発生させます。
        最後に、`atomicstorep`を使って`zerobuf.p`を`t.zero`に設定し、`zerobuf.lock`をアンロックします。

この`mapzero`関数により、`reflect`で作成された型のゼロ値は、実際にマップの要素として必要になったときに初めて割り当てられ、かつその割り当ては効率的に共有されるようになりました。これにより、メモリ使用量の削減とパフォーマンスの向上が実現されています。

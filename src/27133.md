# [インデックス 27133] ファイルの概要

このコミットは、Goリンカー（`cmd/link`）におけるWindows実行可能ファイル（PE形式）のCOFFシンボルテーブル生成ロジックを最適化するものです。具体的には、シンボル情報をメモリ上の大きな配列に一時的に格納してからファイルに書き出すという従来の複数ステップのプロセスを、シンボルを走査しながら直接ファイルに書き出す単一ステップのストリーミング処理に書き換えることで、メモリ使用量を削減し、パフォーマンスの向上を目指しています。

## コミット

```
cmd/link: rewrite pe symbol table generating code

Every go executable has COFF symbol table appended at the end. The table is
used by nm and addr2line and contains all symbols present in the executable.
The table is quite large. For example, my go.exe has 11736 records.

To generate symbol table:
1) we walk "all symbols" list to count symbols we want for the table;
2) we allocate large global array of COFFSym structs (32 bytes each)
   to fit our symbols;
3) we walk "all symbols" list again to fill our array with contents;
4) we iterate over our global array to write all records to the file.

This CL changes all these steps with single step:
- walk "all symbols" list and write each COFF symbol table record to
  the file as we go.

how to benchmark this.
```

## 変更の背景

Goの実行可能ファイル、特にWindows向けのPE（Portable Executable）形式のバイナリには、デバッグツール（`nm`や`addr2line`など）がシンボル情報を解決するために使用するCOFF（Common Object File Format）シンボルテーブルが末尾に付加されます。このシンボルテーブルは、Goのバイナリでは非常に大きくなる傾向があり、コミットメッセージの例では11,736ものレコードを持つことが示されています。

従来のシンボルテーブル生成プロセスは、以下の4つのステップで構成されていました。

1.  **シンボル数のカウント**: まず、シンボルテーブルに含めるべきシンボルの総数を把握するために、すべてのシンボルリストを一度走査します。
2.  **中間配列の確保**: カウントしたシンボル数に基づいて、`COFFSym`構造体（各32バイト）の大きなグローバル配列をメモリ上に確保します。
3.  **中間配列の充填**: 再びすべてのシンボルリストを走査し、各シンボルの情報を先ほど確保した`COFFSym`配列に格納します。
4.  **ファイルへの書き出し**: 最後に、充填された`COFFSym`配列をイテレートし、各レコードをファイルに書き出します。

この多段階のプロセスは、特に大きなGoバイナリの場合、以下の問題を引き起こす可能性がありました。

*   **メモリ使用量の増大**: 大量のシンボル情報を一時的に保持するための`COFFSym`配列が、リンカーのメモリフットプリントを不必要に増加させていました。これは「garbage」（ガベージ）と表現されており、ガベージコレクションの負荷にも影響を与える可能性があります。
*   **処理の非効率性**: シンボルリストを複数回（少なくとも3回）走査する必要があり、I/OとCPUの両面でオーバーヘッドが生じていました。

このコミットは、これらの問題を解決し、シンボルテーブル生成をより効率的にするために、単一パスで直接ファイルに書き出すストリーミング方式に移行することを目的としています。これにより、中間的な大きなメモリ割り当てが不要になり、メモリ使用量の削減と処理速度の向上が期待されます。

## 前提知識の解説

### COFF (Common Object File Format)

COFFは、コンパイルされたオブジェクトコードや実行可能ファイルを格納するためのファイル形式です。主にUnix系システムで広く使われていたA.OUT形式の後継として開発され、WindowsのPE（Portable Executable）形式の基盤となっています。COFFファイルは、ヘッダ、セクションテーブル、セクションデータ、シンボルテーブル、文字列テーブルなどで構成されます。

### PE (Portable Executable)

PEは、Microsoft Windowsオペレーティングシステムで使用される実行可能ファイル、オブジェクトコード、DLL（ダイナミックリンクライブラリ）、FON（フォントファイル）などのファイル形式です。PE形式はCOFF形式をベースにしており、Windowsがプログラムをロードし、実行するために必要な情報（インポート/エクスポートテーブル、リソースデータ、デバッグ情報など）を含んでいます。

### COFFシンボルテーブル

COFFシンボルテーブルは、実行可能ファイル内のシンボル（関数名、変数名など）に関する情報（名前、アドレス、型、所属セクションなど）を格納するセセクションです。デバッグ情報の一部として機能し、`nm`（シンボルリスト表示）や`addr2line`（アドレスからソースコード行への変換）といったツールが、実行時アドレスとソースコード上のシンボルを関連付けるために利用します。シンボル名が8文字を超える場合は、文字列テーブル（String Table）に格納され、シンボルテーブルからはそのオフセットが参照されます。

### Goリンカー (`cmd/link`)

Go言語のビルドプロセスにおいて、`cmd/link`はコンパイルされたオブジェクトファイルを結合し、最終的な実行可能ファイルを生成する役割を担います。この過程で、Goランタイムや標準ライブラリのコードとユーザーコードをリンクし、プラットフォーム固有の実行可能ファイル形式（WindowsではPE、LinuxではELFなど）に変換します。シンボルテーブルの生成もこのリンカーの重要な機能の一つです。

### `LSym`

`LSym`はGoリンカー内部でシンボルを表す構造体です。プログラム内の関数、変数、型などの各シンボルは`LSym`インスタンスとして管理され、その名前、アドレス、サイズ、型、所属セクションなどの情報が含まれています。

### `strtbl` (String Table)

COFF形式では、シンボル名が8バイトを超える場合、その名前はシンボルテーブルとは別の文字列テーブル（String Table）に格納されます。シンボルテーブルの該当エントリには、文字列テーブル内での名前のオフセットが記録されます。これにより、シンボルテーブルの各エントリのサイズを固定に保ちつつ、任意の長さのシンボル名を扱うことができます。

## 技術的詳細

このコミットの核心は、`src/cmd/link/internal/ld/pe.go`ファイル内のCOFFシンボルテーブル生成ロジックを、メモリ効率の良いストリーミング方式に完全に書き換えた点にあります。

**変更前（旧方式）**:

1.  `COFFSym`というカスタム構造体が定義されていました。この構造体は、Goの内部シンボル表現である`LSym`からCOFFシンボルテーブルエントリに必要な情報を抽出して一時的に保持するためのものでした。
    ```go
    type COFFSym struct {
    	sym       *LSym
    	strtbloff int
    	sect      int
    	value     int64
    	typ       uint16
    }
    var coffsym []COFFSym // COFFSym構造体のスライス
    var ncoffsym int      // スライス内の要素数
    ```
2.  `addpesym`関数は、シンボルを処理するたびに、この`coffsym`スライスに`COFFSym`インスタンスを追加していました。
3.  `addpesymtable`関数内で、まず`pegenasmsym(addpesym)`を呼び出して`ncoffsym`（シンボル数）をカウントし、その数で`coffsym`スライスを`make`で確保していました。
4.  その後、再度`pegenasmsym(addpesym)`を呼び出して`coffsym`スライスを充填し、最後にこのスライスをイテレートしてファイルに書き出していました。

この方式では、すべてのシンボル情報をメモリ上に`COFFSym`の大きな配列として保持する必要があり、特にシンボル数が多い場合に大量のメモリを消費していました。

**変更後（新方式）**:

1.  `COFFSym`構造体、`coffsym`スライス、および`ncoffsym`変数は完全に削除されました。これにより、中間的なメモリ割り当てが不要になります。
2.  新たに`writePESymTableRecords()`関数が導入されました。この関数は、シンボルを走査しながら、COFFシンボルテーブルの各レコードを直接出力ファイルに書き込みます。
3.  `writePESymTableRecords()`関数内部では、`put`というクロージャが定義されています。このクロージャが個々の`LSym`シンボルを受け取り、その情報をCOFFシンボルテーブルのフォーマットに従って直接ファイルに書き出すロジックを含んでいます。
    *   シンボル名が8文字を超える場合は、文字列テーブルにオフセットを書き込みます。
    *   シンボルの値（アドレス）と所属セクションを計算し、`Lputl`（32ビットリトルエンディアン書き込み）、`Wputl`（16ビットリトルエンディアン書き込み）、`Cput`（8ビット書き込み）といった低レベルのI/O関数を使って、COFFシンボルエントリの各フィールドを直接出力ストリームに書き込みます。
    *   `s.Dynid`には、書き込まれたシンボルのインデックス（`symcnt`）が設定されます。
4.  `addpesymtable`関数は、`writePESymTableRecords()`を一度だけ呼び出し、その戻り値（書き込まれたシンボル数）を利用してCOFFファイルヘッダの`NumberOfSymbols`フィールドを更新します。また、シンボルテーブルの開始位置（`symtabStartPos`）も記録し、`PointerToSymbolTable`フィールドに設定します。

この変更により、シンボルテーブル生成は単一パスのストリーミング処理となり、中間的な大きなメモリ割り当てが不要になったため、リンカーのメモリ使用量が大幅に削減され、ガベージコレクションの頻度も減少する可能性があります。結果として、リンキング処理全体のパフォーマンス向上が期待されます。

## コアとなるコードの解説

このコミットの核となるのは、`writePESymTableRecords`関数とその内部で定義される`put`クロージャです。

```go
// writePESymTableRecords writes all COFF symbol table records.
// It returns number of records written.
func writePESymTableRecords() int {
	var symcnt int // 書き込まれたシンボル数をカウント

	// put クロージャは、個々のLSymシンボルを受け取り、その情報をCOFFシンボルテーブル形式で直接ファイルに書き込む
	put := func(s *LSym, name string, type_ int, addr int64, size int64, ver int, gotype *LSym) {
		if s == nil {
			return
		}
		if s.Sect == nil && type_ != 'U' { // セクションを持たないシンボル（未定義シンボル以外）はスキップ
			return
		}
		switch type_ { // 特定のシンボルタイプのみを処理
		default:
			return
		case 'D', 'B', 'T', 'U': // データ、BSS、テキスト、未定義シンボル
		}

		// Windows/386の外部シンボルにはアンダースコアプレフィックスを追加
		if Thearch.Thechar == '8' && Linkmode == LinkExternal && (s.Type == obj.SHOSTOBJ || s.Attr.CgoExport()) && s.Name == s.Extname {
			s.Name = "_" + s.Name
		}

		var typ uint16 // COFFシンボルタイプ
		var sect int    // 所属セクション番号
		var value int64 // シンボルの値（アドレス）

		// シンボルのアドレスに基づいて所属セクションと値を計算
		// .bssセクションのシンボル
		if uint64(s.Value) >= Segdata.Vaddr+Segdata.Filelen && s.Type != obj.SDATA && Linkmode == LinkExternal {
			value = int64(uint64(s.Value) - Segdata.Vaddr - Segdata.Filelen)
			sect = bsssect
		} else if uint64(s.Value) >= Segdata.Vaddr { // .dataセクションのシンボル
			value = int64(uint64(s.Value) - Segdata.Vaddr)
			sect = datasect
		} else if uint64(s.Value) >= Segtext.Vaddr { // .textセクションのシンボル
			value = int64(uint64(s.Value) - Segtext.Vaddr)
			sect = textsect
		} else if type_ == 'U' { // 未定義シンボル
			typ = IMAGE_SYM_DTYPE_FUNCTION // 関数として扱う
		} else {
			Diag("addpesym %#x", addr) // 予期しないアドレスの場合
		}

		// COFFシンボルテーブルレコードを直接ファイルに書き込む
		if len(s.Name) > 8 { // シンボル名が8文字を超える場合は文字列テーブルを参照
			Lputl(0) // 名前フィールドは0
			Lputl(uint32(strtbladd(s.Name))) // 文字列テーブル内のオフセット
		} else {
			strnput(s.Name, 8) // 8文字以内の場合は直接書き込む
		}
		Lputl(uint32(value)) // シンボルの値
		Wputl(uint16(sect))  // 所属セクション番号
		if typ != 0 {
			Wputl(typ)
		} else if Linkmode == LinkExternal {
			Wputl(0)
		} else {
			Wputl(0x0308) // "array of structs" - デフォルトの型情報
		}
		Cput(2) // storage class: external (外部リンケージ)
		Cput(0) // no aux entries (補助エントリなし)

		s.Dynid = int32(symcnt) // シンボルに動的IDを設定
		symcnt++                // 書き込んだシンボル数をインクリメント
	}

	// genasmsymは、すべてのシンボルを走査し、putクロージャを呼び出す
	// Linkmode == LinkExternal の場合は、外部シンボルも処理
	if Linkmode == LinkExternal {
		for d := dr; d != nil; d = d.next {
			for m := d.ms; m != nil; m = m.next {
				genasmsym(put) // 外部シンボルを処理
			}
		}
	}
	genasmsym(put) // すべてのGoシンボルを処理

	return symcnt // 書き込まれたシンボル総数を返す
}
```

この`writePESymTableRecords`関数は、`genasmsym`（Goリンカーがすべてのシンボルを走査するための汎用関数）に`put`クロージャを渡すことで、シンボルが発見されるたびにその場でCOFFシンボルテーブルエントリをファイルに書き出すことを可能にしています。

`put`クロージャ内では、以下の処理が行われます。

1.  **シンボルのフィルタリング**: `s == nil`や`s.Sect == nil && type_ != 'U'`、`switch type_`文によって、COFFシンボルテーブルに含めるべきシンボルが選別されます。
2.  **シンボル名の処理**: シンボル名が8文字を超える場合は、`strtbladd(s.Name)`で文字列テーブルに名前を追加し、そのオフセットをシンボルテーブルに書き込みます。8文字以下の場合は、直接シンボルテーブルに名前を書き込みます。
3.  **アドレスとセクションの計算**: シンボルの仮想アドレス（`s.Value`）とセクション情報（`Segdata.Vaddr`, `Segtext.Vaddr`など）に基づいて、COFFシンボルテーブルに必要な`value`（セクション内オフセット）と`sect`（セクション番号）を計算します。
4.  **COFFシンボルエントリの書き込み**: `Lputl`, `Wputl`, `Cput`といった関数を使用して、COFFシンボルエントリの各フィールド（名前、値、セクション、型、ストレージクラス、補助エントリ数）を直接出力ファイルに書き込みます。これにより、中間的な`COFFSym`構造体への格納が不要になります。
5.  **シンボルカウントの更新**: `symcnt`変数をインクリメントし、最終的に書き込まれたシンボル数を返します。

このストリーミングアプローチにより、リンカーはシンボルテーブル生成のために大量のメモリを一時的に確保する必要がなくなり、メモリフットプリントが削減され、ガベージコレクションの負担も軽減されます。

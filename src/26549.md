# [インデックス 26549] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおけるAMD64アーキテクチャ向けのコード生成最適化に関するものです。具体的には、複数のSSA操作をより効率的な単一の機械語命令（特にインデックス付きロード命令とLEA命令）に結合する改善が行われています。

変更されたファイルとその役割は以下の通りです。

-   `src/cmd/compile/internal/gc/ssa.go`: GoコンパイラのSSA生成および低レベル化ロジックが含まれています。SSA値がどのように機械語命令に変換されるか、特に新しいインデックス付きロード命令のケースが追加されています。
-   `src/cmd/compile/internal/ssa/gen/AMD64.rules`: AMD64 SSAバックエンドの書き換えルールを定義するファイルです。これらのルールは、SSA操作のシーケンスをより最適化されたシーケンスや単一の機械語命令に変換するために使用されます。このファイルには、認識され、置き換えられる特定のパターンが記述されています。
-   `src/cmd/compile/internal/ssa/gen/AMD64Ops.go`: AMD64に特化したSSA操作（Opコード）を定義するファイルです。新しいインデックス付きロード操作がここで定義されています。
-   `src/cmd/compile/internal/ssa/opGen.go`: SSA操作の定義を生成するファイルです。`AMD64Ops.go`で追加された新しい操作が反映されます。
-   `src/cmd/compile/internal/ssa/rewriteAMD64.go`: AMD64向けの実際の書き換え関数が含まれています。`AMD64.rules`で定義されたルールがここで実装されています。このファイルには、新しい結合ロジックの実装が最も多く含まれています。
-   `src/cmd/compile/internal/ssa/value.go`: `AuxInt`の`LongString()`におけるフォーマットに関する軽微な変更で、デバッグ目的である可能性が高いです。

## コミット

GoコンパイラのSSAバックエンドにおいて、AMD64アーキテクチャ向けに、より多くのSSA操作を単一の機械語命令に結合する最適化が施されました。主な変更点はインデックス付きロード命令の結合と、LEA (Load Effective Address) 命令の利用ケースの拡張です。これにより、生成されるアセンブリコードの効率が向上し、プログラムの実行速度が改善されることが期待されます。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現としてSSA (Static Single Assignment) 形式を使用します。SSA形式は最適化を適用しやすいという利点がありますが、最終的な機械語命令に変換する際には、ターゲットアーキテクチャの特性を最大限に活かすことが重要です。

AMD64アーキテクチャには、メモリへのアクセスを効率化するための強力なアドレッシングモードがいくつか存在します。特に、ベースレジスタ、インデックスレジスタ、スケールファクタ、オフセットを組み合わせて複雑なメモリアドレスを計算し、一度の命令でメモリから値をロードまたはストアできる「インデックス付きアドレッシングモード」は、配列や構造体へのアクセスにおいて非常に有効です。また、LEA (Load Effective Address) 命令は、メモリアドレスの計算結果をレジスタに格納する命令ですが、実際にはアドレス計算ユニットを利用して、加算やシフトなどの算術演算を効率的に実行するためにも使われます。

このコミットの背景には、GoコンパイラのSSAバックエンドが、これらのAMD64の強力なアドレッシングモードや命令を十分に活用できていなかったという課題があります。複数のSSA操作（例えば、ベースアドレスへのインデックスの加算、その結果へのオフセットの加算、そしてそのアドレスからのロード）がそれぞれ独立した機械語命令として生成されると、命令数が増え、実行効率が低下します。

この変更は、コンパイラがSSA形式のコードパターンを認識し、それらを単一のインデックス付きロード命令やLEA命令に「結合（combining）」することで、生成されるアセンブリコードの命令数を減らし、CPUのパイプライン効率を向上させ、結果としてプログラムの実行速度を改善することを目的としています。特に、配列要素へのアクセスやポインタ演算が頻繁に行われるコードにおいて、この最適化は大きな効果を発揮します。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化で広く用いられる中間表現です。この形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が容易になり、様々な最適化（定数伝播、共通部分式除去、デッドコード削除など）を効率的に適用できます。Goコンパイラも、最適化の大部分をSSA形式のコードに対して行います。

### 2. AMD64アーキテクチャのメモリアドレッシングモード

AMD64 (x86-64) アーキテクチャは、柔軟なメモリアドレッシングモードを提供します。特に重要なのは以下の形式です。

`[base + index*scale + displacement]`

-   **base (ベースレジスタ)**: メモリアドレスの基準となるレジスタ（例: `RBX`, `RBP`）。
-   **index (インデックスレジスタ)**: 配列のインデックスなど、オフセットを計算するためのレジスタ（例: `RSI`, `RDI`）。
-   **scale (スケールファクタ)**: インデックスレジスタの値に乗算される定数。`1`, `2`, `4`, `8`のいずれか（バイト、ワード、ダブルワード、クアッドワードのサイズに対応）。
-   **displacement (ディスプレースメント/オフセット)**: 定数オフセット。

このアドレッシングモードにより、例えば `MOVQ (%RBX,%RSI,8), %RAX` のような命令で、`RBX + RSI * 8` で計算されるアドレスから8バイトの値を`RAX`レジスタにロードするといった操作を、単一の命令で実行できます。

### 3. LEA (Load Effective Address) 命令

`LEA`命令は、`[base + index*scale + displacement]` の形式で計算されるメモリアドレスを、実際にメモリにアクセスすることなく、指定されたレジスタに格納する命令です。例えば、`LEAQ (%RBX,%RSI,8), %RAX` は、`RBX + RSI * 8` の計算結果を`RAX`に格納します。

`LEA`命令の重要な点は、メモリロード/ストア命令のアドレッシングモードと同じ強力なアドレス計算能力を持つにもかかわらず、メモリにアクセスしないため、算術演算（加算、シフト、乗算）の組み合わせを効率的に実行する手段として利用されることが多い点です。特に、`ADD`や`SHL`命令の組み合わせを`LEA`命令1つに置き換えることで、命令数を削減し、実行効率を向上させることができます。

### 4. Goコンパイラの構造

Goコンパイラは、おおまかに以下の段階で動作します。

-   **フロントエンド**: Goソースコードを解析し、抽象構文木 (AST) を構築します。
-   **ミドルエンド**: ASTをSSA形式に変換し、型チェックや様々な高レベル最適化を行います。
-   **バックエンド**: SSA形式のコードをターゲットアーキテクチャ（この場合はAMD64）の機械語命令に変換します。この段階で、SSA操作を実際のCPU命令にマッピングし、さらに低レベルな最適化（レジスタ割り当て、命令スケジューリング、命令結合など）が行われます。

このコミットは、主にバックエンドのSSAから機械語への変換フェーズにおける最適化に焦点を当てています。

## 技術的詳細

このコミットの技術的詳細は、GoコンパイラのSSAバックエンドが、特定のSSA操作のパターンを認識し、それらをAMD64のより効率的な命令に変換する「書き換えルール」を追加・改善した点にあります。

### 1. インデックス付きロード/ストア命令の結合

以前のコンパイラでは、例えば `ptr + idx*scale + offset` のようなアドレス計算と、そのアドレスからのメモリロードが、複数のSSA操作として表現され、それぞれ独立した機械語命令に変換される可能性がありました。

このコミットでは、以下のようなSSAパターンを認識し、`MOVBloadidx1`, `MOVWloadidx2`, `MOVLloadidx4`, `MOVQloadidx8` などのインデックス付きロード命令に結合するルールが追加されています。

-   `MOVBload [off1] {sym1} (LEAQ1 [off2] {sym2} ptr idx) mem`
    -   これは、`ptr + idx*1 + off2` で計算されるアドレスに `off1` を加えたアドレスから1バイトをロードする操作です。`LEAQ1`はベースレジスタとインデックスレジスタ（スケール1）を持つアドレス計算を表します。
    -   このパターンは `MOVBloadidx1 [addOff(off1, off2)] {mergeSym(sym1,sym2)} ptr idx mem` という単一のインデックス付きロード命令に変換されます。
-   `MOVBload [off] {sym} (ADDQ ptr idx) mem`
    -   `ptr + idx` で計算されるアドレスに `off` を加えたアドレスから1バイトをロードする操作です。
    -   これは `MOVBloadidx1 [off] {sym} ptr idx mem` に変換されます。

同様に、`MOVWloadidx2` (2バイトロード)、`MOVLloadidx4` (4バイトロード)、`MOVQloadidx8` (8バイトロード) および対応するストア命令についても、`LEAQ`命令や`ADDQ`命令と組み合わせたアドレス計算を、インデックス付きロード/ストア命令に結合するルールが追加されています。

さらに、インデックス付きロード/ストア命令のオフセットやインデックスレジスタに定数加算がある場合も、それらを命令のオフセットに統合するルールが追加されています。
例: `(MOVWloadidx2 [c] {sym} ptr (ADDQconst [d] idx) mem)` は `(MOVWloadidx2 [c+2*d] {sym} ptr idx mem)` に変換されます。ここで `2*d` となるのは、`MOVWloadidx2`がインデックスに2のスケールを適用するためです。

### 2. LEA命令の利用ケース拡張

`LEA`命令は、アドレス計算だけでなく、加算やシフトを伴う算術演算の最適化にも利用されます。このコミットでは、以下のような`ADDQ`と`SHLQconst`（左シフト定数）の組み合わせを`LEAQ`命令に結合するルールが追加されています。

-   `(ADDQ x (SHLQconst [3] y))` -> `(LEAQ8 x y)`
    -   これは `x + y * 8` の計算を `LEAQ8` 命令で実行します。
-   `(ADDQ x (SHLQconst [2] y))` -> `(LEAQ4 x y)`
    -   これは `x + y * 4` の計算を `LEAQ4` 命令で実行します。
-   `(ADDQ x (SHLQconst [1] y))` -> `(LEAQ2 x y)`
    -   これは `x + y * 2` の計算を `LEAQ2` 命令で実行します。
-   `(ADDQ x (ADDQ y y))` -> `(LEAQ2 x y)`
    -   これは `x + y + y` すなわち `x + y * 2` の計算を `LEAQ2` 命令で実行します。

また、`ADDQconst`（定数加算）と`LEAQ`命令の組み合わせを、`LEAQ`命令のオフセットに定数を統合する形で最適化するルールも追加されています。
例: `(ADDQconst [c] (LEAQ [d] {s} x))` -> `(LEAQ [c+d] {s} x)`

これらの最適化により、コンパイラはより少ない命令で同じ計算を実行できるようになり、結果として生成されるコードのパフォーマンスが向上します。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、主に`src/cmd/compile/internal/ssa/gen/AMD64.rules`と`src/cmd/compile/internal/ssa/rewriteAMD64.go`に集中しています。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules`

このファイルには、SSA操作をAMD64命令に変換するための書き換えルールが記述されています。

-   **LEA命令の結合ルールの追加**:
    -   `ADDQ`と`SHLQconst`の組み合わせを`LEAQ2`, `LEAQ4`, `LEAQ8`に変換するルールが追加されました。
    -   `ADDQ`と`ADDQ`の組み合わせを`LEAQ2`に変換するルールが追加されました。
    -   `ADDQconst`と既存の`LEAQ`命令を結合し、オフセットを統合するルールが追加されました。
    -   `ADDQ`と`LEAQ`を結合し、`LEAQ1`を生成するルールが追加されました。
-   **インデックス付きロード/ストア命令の生成ルールの追加**:
    -   `MOVBload`, `MOVWload`, `MOVLload`, `MOVQload`, `MOVSSload`, `MOVSDload`が`LEAQx`と組み合わされた場合に、対応するインデックス付きロード命令（`MOVBloadidx1`など）に変換するルールが追加されました。
    -   同様に、`MOVBstore`, `MOVWstore`, `MOVLstore`, `MOVQstore`, `MOVSSstore`, `MOVSDstore`が`LEAQx`と組み合わされた場合に、対応するインデックス付きストア命令に変換するルールが追加されました。
    -   `ADDQconst`がインデックス付きロード/ストア命令のベースレジスタまたはインデックスレジスタに適用される場合に、オフセットを統合するルールが追加されました。

### `src/cmd/compile/internal/ssa/rewriteAMD64.go`

このファイルは、`AMD64.rules`で定義された書き換えルールを実際に実装するGoコードを含んでいます。

-   新しいSSA操作（`OpAMD64MOVBloadidx1`, `OpAMD64MOVWloadidx2`, `OpAMD64MOVLloadidx4`など）に対応する`rewriteValueAMD64_OpAMD64...`関数が追加されました。
-   既存の`rewriteValueAMD64_OpAMD64ADDQ`や`rewriteValueAMD64_OpAMD64ADDQconst`、`rewriteValueAMD64_OpAMD64LEAQ`などの関数に、新しい結合ルールを適用するためのロジックが追加されました。これらの関数は、入力SSA値のオペレーションと引数をチェックし、パターンに一致すればより最適化されたSSA操作に変換します。

### `src/cmd/compile/internal/ssa/gen/AMD64Ops.go` および `src/cmd/compile/internal/ssa/opGen.go`

-   `MOVBloadidx1`, `MOVWloadidx2`, `MOVLloadidx4`などの新しいインデックス付きロード操作が定義され、それらのレジスタ制約やアセンブリ命令が指定されました。これにより、コンパイラがこれらの新しい命令を認識し、利用できるようになります。

### `src/cmd/compile/internal/gc/ssa.go`

-   `genValue`関数に、新しいインデックス付きロード操作（`ssa.OpAMD64MOVLloadidx4`, `ssa.OpAMD64MOVWloadidx2`, `ssa.OpAMD64MOVBloadidx1`）を実際のAMD64アセンブリ命令に変換するためのケースが追加されました。

## コアとなるコードの解説

`src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更は、SSA最適化の具体的な実装を示しています。ここでは、いくつかの代表的な変更箇所を抜粋して解説します。

### LEA命令への結合の例

```go
// match: (ADDQ x (SHLQconst [2] y))
// cond:
// result: (LEAQ4 x y)
{
	x := v.Args[0]
	if v.Args[1].Op != OpAMD64SHLQconst {
		goto end153955fe292c5ecb20b76bba7da8f451
	}
	if v.Args[1].AuxInt != 2 {
		goto end153955fe292c5ecb20b76bba7da8f451
	}
	y := v.Args[1].Args[0]
	v.reset(OpAMD64LEAQ4)
	v.AddArg(x)
	v.AddArg(y)
	return true
}
```
このコードスニペットは、`ADDQ`（加算）と`SHLQconst [2]`（定数2での左シフト、つまり4倍）のSSA操作の組み合わせを、`LEAQ4`という単一のSSA操作に変換するルールを実装しています。
-   `v.Args[0]`が`x`、`v.Args[1]`が`y`を4倍する操作です。
-   `v.Args[1].Op != OpAMD64SHLQconst` と `v.Args[1].AuxInt != 2` で、2倍シフトの定数左シフト操作であることを確認します。
-   条件が満たされれば、元の`ADDQ`操作`v`を`LEAQ4`操作にリセットし、引数として`x`と`y`を追加します。
-   これにより、`x + y * 4`という計算が、AMD64の`LEAQ`命令のスケールファクタ4を利用して効率的に実行されるようになります。

### インデックス付きロード命令への結合の例

```go
// match: (MOVBload [off] {sym} (ADDQ ptr idx) mem)
// cond: ptr.Op != OpSB
// result: (MOVBloadidx1 [off] {sym} ptr idx mem)
{
	off := v.AuxInt
	sym := v.Aux
	if v.Args[0].Op != OpAMD64ADDQ {
		goto end2abf84efc0e06ed9cda71fb8a1ffaacd
	}
	ptr := v.Args[0].Args[0]
	idx := v.Args[0].Args[1]
	mem := v.Args[1]
	if !(ptr.Op != OpSB) { // OpSBはスタックベースポインタを表す特殊なオペランド
		goto end2abf84efc0e06ed9cda71fb8a1ffaacd
	}
	v.reset(OpAMD64MOVBloadidx1)
	v.AuxInt = off
	v.Aux = sym
	v.AddArg(ptr)
	v.AddArg(idx)
	v.AddArg(mem)
	return true
}
```
このスニペットは、`ADDQ`（ポインタとインデックスの加算）と`MOVBload`（1バイトロード）の組み合わせを、`MOVBloadidx1`という単一のインデックス付きロード操作に変換するルールです。
-   `v.Args[0]`が`ptr + idx`のアドレス計算、`v.Args[1]`がメモリ状態を表します。
-   `ptr.Op != OpSB`は、ベースポインタがスタックベースポインタでないことを確認する条件です。スタックベースポインタは特別な扱いが必要な場合があります。
-   条件が満たされれば、元の`MOVBload`操作`v`を`MOVBloadidx1`操作にリセットし、オフセット`off`、シンボル`sym`、ベースポインタ`ptr`、インデックス`idx`、メモリ状態`mem`を引数として設定します。
-   これにより、`ptr + idx + off`で計算されるアドレスからの1バイトロードが、AMD64のインデックス付きアドレッシングモードを利用して単一の命令で実行されるようになります。

これらの変更は、Goコンパイラが生成するAMD64アセンブリコードの品質を向上させ、より効率的な実行を可能にするための重要なステップです。

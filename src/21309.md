# [インデックス 21309] ファイルの概要

このコミットは、Go言語の標準ライブラリである`net/http`パッケージにおける`Client.Timeout`の挙動を改善するものです。具体的には、`http.Client`がタイムアウトによってエラーを返した場合に、そのエラーがGoのネットワークエラーインターフェースである`net.Error`を満たし、かつ`Timeout()`メソッドが`true`を返すように変更されています。これにより、アプリケーションがタイムアウトエラーをより確実に識別し、適切に処理できるようになります。

`net/http: make Client.Timeout return net.Error errors indicating timeout`

## 変更の背景

このコミットが作成された2014年12月当時、`http.Client`の`Timeout`フィールドはGo 1.3（2014年6月リリース）で導入された比較的新しい機能でした。それ以前のGoのバージョンでは、HTTPリクエスト全体のタイムアウトを設定する統一的な方法はなく、開発者は`net.Dialer.Timeout`や`net.Conn`のデッドラインを個別に設定する必要がありました。

`Client.Timeout`の導入により、リクエスト全体のタイムアウト設定が容易になった一方で、タイムアウトが発生した際に返されるエラーの挙動に一貫性がないという問題がありました。具体的には、タイムアウトによってエラーが返された場合でも、そのエラーが必ずしも`net.Error`インターフェースを満たし、`Timeout()`メソッドが`true`を返すとは限りませんでした。これにより、アプリケーションがプログラム的にタイムアウトエラーを検出し、それに応じたリカバリロジック（例えばリトライなど）を実装することが困難でした。

このコミットは、この一貫性の問題を解決し、`Client.Timeout`によって発生したエラーが常に`net.Error`インターフェースの`Timeout()`メソッドを通じてタイムアウトであることを明示的に示すようにすることで、より堅牢なエラーハンドリングを可能にすることを目的としています。

## 前提知識の解説

*   **Goの`net/http`パッケージ**: Go言語の標準ライブラリで、HTTPクライアントとサーバーの機能を提供します。ウェブアプリケーションやAPIクライアントを構築する上で中心的な役割を果たします。
*   **`http.Client`**: `net/http`パッケージ内でHTTPリクエストを実行するための構造体です。`Get`, `Post`, `Do`などのメソッドを通じてHTTP通信を行います。`Client`構造体には、リダイレクトの挙動、クッキー、そして本コミットの主題であるタイムアウトなどの設定を行うためのフィールドが含まれています。
*   **`Client.Timeout`フィールド**: `http.Client`構造体のフィールドで、HTTPリクエスト全体（接続確立、リクエスト送信、レスポンスヘッダ受信、レスポンスボディ読み込みを含む）の最大許容時間を設定します。この時間を超えると、リクエストはキャンセルされ、エラーが返されます。
*   **`net.Error`インターフェース**: Goの`net`パッケージで定義されているインターフェースで、ネットワーク関連のエラーに特化した情報を提供します。通常の`error`インターフェースを埋め込んでおり、さらに以下の2つのメソッドを持ちます。
    *   `Timeout() bool`: エラーがタイムアウトによるものである場合に`true`を返します。
    *   `Temporary() bool`: エラーが一時的なものであり、リトライによって解決する可能性がある場合に`true`を返します。
    アプリケーションはこれらのメソッドを利用して、エラーの種類に応じて異なる処理を行うことができます。
*   **`sync/atomic`パッケージ**: Goの標準ライブラリで、アトミック操作（不可分操作）を提供します。複数のゴルーチンが共有データに同時にアクセスする際に発生する競合状態（race condition）を防ぐために使用されます。`atomic.LoadInt32`や`atomic.StoreInt32`は、`int32`型の値を安全に読み書きするために使われます。
*   **`context`パッケージとの関連性**: このコミットは2014年に行われましたが、Go 1.7（2016年8月リリース）で標準ライブラリに導入された`context`パッケージは、Goにおけるタイムアウトやキャンセル処理のより柔軟でイディオマティックな方法を提供します。`context.WithTimeout`や`context.WithCancel`を使用することで、リクエストスコープのデッドラインやキャンセルシグナルを伝播させることができます。本コミットは`context`パッケージが標準ライブラリに導入される前の改善であり、当時の`Client.Timeout`の限界と、それを補うための工夫が反映されています。

## 技術的詳細

このコミットの主要な目的は、`http.Client`の`Timeout`によって発生したエラーが、`net.Error`インターフェースの`Timeout()`メソッドで`true`を返すようにすることです。これを実現するために、以下の技術的な変更が加えられています。

1.  **タイムアウト発生の追跡**:
    *   `doFollowingRedirects`関数内に`atomicWasCanceled int32`というアトミックな変数が導入されました。これは、タイムアウトが発生してリクエストがキャンセルされたかどうかを安全に追跡するためのフラグとして機能します（`1`がキャンセル済み、`0`が未キャンセル）。
    *   `time.AfterFunc`で設定されるタイムアウト処理のコールバック内で、`atomic.StoreInt32(&atomicWasCanceled, 1)`を呼び出すことで、タイムアウトが発生したことを記録します。
    *   `wasCanceled`という関数が定義され、`atomic.LoadInt32(&atomicWasCanceled) != 0`を返すことで、現在のリクエストがタイムアウトによってキャンセルされたかどうかをチェックします。

2.  **エラーのラップと`net.Error`の実装**:
    *   HTTPリクエストの送信（ヘッダの受信前）でエラーが発生した場合、`c.send(req)`の戻り値のエラーをチェックします。もし`wasCanceled()`が`true`であれば、元のエラーを`httpError`という内部的な構造体でラップします。
    *   `httpError`構造体は、`net.Error`インターフェースを満たすように実装されており、`Timeout()`メソッドが`true`を返すように設定されます。これにより、タイムアウトによるエラーが明示的に識別可能になります。エラーメッセージには「(Client.Timeout exceeded while awaiting headers)」という情報が追加されます。
    *   同様に、レスポンスボディの読み込み中にタイムアウトが発生した場合も考慮されます。`cancelTimerBody`という`io.ReadCloser`をラップする構造体が変更され、`reqWasCanceled func() bool`フィールドが追加されました。`cancelTimerBody.Read`メソッド内で読み込みエラーが発生し、かつ`reqWasCanceled()`が`true`であれば、同様に`httpError`でエラーをラップし、エラーメッセージに「(Client.Timeout exceeded while reading body)」という情報が追加されます。

これらの変更により、`Client.Timeout`が発動した際に返されるエラーは、ヘッダ受信前でもボディ読み込み中でも、常に`net.Error`インターフェースを満たし、`Timeout()`が`true`を返すことが保証されます。

## コアとなるコードの解説

### `src/net/http/client.go`の変更点

*   **`sync/atomic`のインポート**: 複数のゴルーチンから安全にアクセスできる共有変数を扱うために`sync/atomic`パッケージが導入されました。
*   **`atomicWasCanceled`と`wasCanceled`**:
    *   `atomicWasCanceled`は`int32`型のアトミック変数で、`Client.Timeout`によってリクエストがキャンセルされたかどうかを`1`または`0`で示します。これにより、タイムアウト処理のゴルーチンとメインのHTTPリクエスト処理のゴルーチン間で、競合状態を発生させることなくタイムアウトの状態を共有できます。
    *   `wasCanceled`は、`atomicWasCanceled`の値を読み取って`bool`型で返すクロージャです。これにより、タイムアウト状態のチェックが簡潔に行えます。
*   **`time.AfterFunc`内の`atomic.StoreInt32`**: `Client.Timeout`で設定された時間が経過し、`time.AfterFunc`のコールバックが実行される際に、`atomic.StoreInt32(&atomicWasCanceled, 1)`が呼び出されます。これは、リクエストがタイムアウトによってキャンセルされたことをアトミックに記録するものです。
*   **`c.send(req)`後のエラーハンドリング**: `c.send(req)`はHTTPリクエストを送信し、レスポンスヘッダを受信するまでの処理を行います。この呼び出し後にエラーが発生した場合、`wasCanceled()`をチェックします。もし`true`であれば、それはタイムアウトによるキャンセルが原因であるため、元のエラーを`httpError`でラップし、`timeout: true`を設定します。これにより、ヘッダ受信前のタイムアウトも`net.Error`として適切に扱われます。
*   **`cancelTimerBody`の変更**:
    *   `cancelTimerBody`は、レスポンスボディの読み込み中にタイムアウトタイマーを管理するためのラッパーです。この構造体に`reqWasCanceled func() bool`フィールドが追加されました。これは、`doFollowingRedirects`関数内で定義された`wasCanceled`クロージャが渡されることで、ボディ読み込み中もリクエストがタイムアウトによってキャンセルされたかどうかをチェックできるようになります。
    *   `cancelTimerBody.Read`メソッド内で、ボディの読み込み中にエラーが発生し、かつ`reqWasCanceled()`が`true`であれば、同様に`httpError`でエラーをラップし、`timeout: true`を設定します。これにより、ボディ読み込み中のタイムアウトも`net.Error`として適切に扱われます。

### `src/net/http/client_test.go`の変更点

*   **`TestClientTimeout`の改善**: 既存のテストが強化され、返されたエラーが単にエラーであるだけでなく、`net.Error`インターフェースを満たし、その`Timeout()`メソッドが`true`を返すことを明示的に検証するようになりました。また、エラーメッセージに「Client.Timeout exceeded」という文字列が含まれていることも確認します。
*   **`TestClientTimeout_Headers`の追加**: この新しいテストは、特にレスポンスヘッダを受信する前に`Client.Timeout`が発動した場合の挙動を検証するために追加されました。これは、サーバーが応答を遅延させるシナリオをシミュレートし、その際に返されるエラーが期待通り`net.Error`であり、`Timeout()`が`true`を返すことを確認します。

これらの変更により、`http.Client`の`Timeout`機能は、より堅牢で予測可能なエラーハンドリングを提供するようになりました。

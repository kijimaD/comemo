# [インデックス 27089] ファイルの概要

## コミット
`cmd/compile`: defer/deferreturn の修正

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおける `defer` および `deferreturn` の処理に関するバグを修正します。特に、`panic` から `recover` を介して関数が復帰する際の、関数の終了処理の正確性を保証することを目的としています。

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/ddc6b64444c3914621b3b1ff019e02b5aabdc20c](https://github.com/golang/go/commit/ddc6b64444c3914621b3b1ff019e02b5aabdc20c)

## 元コミット内容
```
cmd/compile: fix defer/deferreturn

Make sure we do any just-before-return cleanup on all paths out of a
function, including when recovering. Each exit path should include
deferreturn (if there are any defers) and then the exit
code (e.g. copying heap-escaping return values back to the stack).

Introduce a Defer SSA block type which has two outgoing edges - one the
fallthrough edge (the defer was queued successfully) and one which
immediately returns (the defer had a successful recover() call and
normal execution should resume at the return point).

Fixes #14725

Change-Id: Iad035c9fd25ef8b7a74dafbd7461cf04833d981f
Reviewed-on: https://go-review.googlesource.com/20486
Reviewed-by: David Chase <drchase@google.com>
```

## 変更の背景

Go言語の `defer` ステートメントは、関数がリターンする直前に実行される関数呼び出しをスケジュールするために使用されます。これはリソースのクリーンアップ（ファイルのクローズ、ロックの解放など）に非常に便利です。また、`panic` と `recover` は、Goにおけるエラーハンドリングのメカニズムの一部であり、`panic` が発生すると通常の実行フローが中断され、`defer` された関数が実行されます。`defer` された関数内で `recover` を呼び出すことで、`panic` から回復し、プログラムの実行を継続できます。

このコミット以前は、`panic` から `recover` を介して関数が復帰する際に、関数の「通常の」終了パスとは異なる処理が行われる可能性があり、`defer` 関連のクリーンアップコード（`deferreturn`）や、ヒープエスケープした戻り値をスタックにコピーするなどの終了コードが、すべての終了パスで適切に実行されないという問題がありました。具体的には、Issue #14725 で報告されたバグは、`recover` が成功した場合に、関数の戻り値が正しく設定されないというものでした。これは、`defer` が実行された後に `recover` が成功し、関数が通常の戻りパスに戻る際に、必要なクリーンアップや戻り値の処理がスキップされてしまうことが原因でした。

この問題は、コンパイラが関数の終了パスをSSA形式で表現する際に、`defer` の実行と `recover` による復帰の複雑な相互作用を十分にモデル化できていなかったことに起因します。

## 前提知識の解説

### Goの `defer`, `panic`, `recover`
- **`defer`**: 関数がリターンする直前に実行される関数呼び出しをスケジュールします。`defer` はLIFO（後入れ先出し）順で実行されます。
- **`panic`**: プログラムの通常の実行フローを中断し、現在のゴルーチンをパニック状態にします。パニックが発生すると、現在の関数から呼び出し元へとスタックを巻き戻しながら、`defer` された関数が順次実行されます。
- **`recover`**: `panic` 状態のゴルーチン内で `defer` された関数の中からのみ呼び出すことができます。`recover` が呼び出されると、パニック状態が解除され、`panic` が発生した時点ではなく、`recover` を呼び出した `defer` 関数の直後から通常の実行が再開されます。`recover` は、パニックの値（`panic` に渡された引数）を返します。パニック状態でないときに `recover` を呼び出しても `nil` を返します。

### GoコンパイラのSSA (Static Single Assignment) 形式
SSA（Static Single Assignment）形式は、コンパイラの最適化フェーズで中間表現として使用されるプログラム表現の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。

Goコンパイラでは、ソースコードがAST（Abstract Syntax Tree）にパースされた後、SSA形式に変換されます。このSSA形式上で様々な最適化（レジスタ割り当て、デッドコード削除など）が行われ、最終的に機械語に変換されます。

SSA形式におけるプログラムの制御フローは「ブロック（Block）」と「値（Value）」で表現されます。
- **ブロック**: 連続した命令のシーケンスであり、単一のエントリポイントと単一の終了ポイントを持ちます。ブロック間はエッジで接続され、プログラムの制御フローグラフ（CFG）を形成します。
- **値**: 変数への代入や演算の結果など、プログラム内で計算されるデータを表します。

### `deferreturn`
`deferreturn` はGoランタイム内部の関数で、`defer` された関数がすべて実行された後に、関数の戻り値を処理したり、スタックフレームをクリーンアップしたりする役割を担います。これは、コンパイラによって生成されるコードの一部であり、ユーザーが直接呼び出すものではありません。

## 技術的詳細

このコミットの主要な変更点は、SSA形式に新しいブロックタイプ `BlockDefer` を導入したことです。これにより、`defer` の実行と `recover` による復帰の複雑な制御フローをより正確にモデル化できるようになりました。

### `BlockDefer` の導入
- **目的**: `defer` 呼び出しが `recover` によって中断され、関数が通常の実行パスに戻るケースを明示的に表現するため。
- **構造**: `BlockDefer` は2つの出力エッジを持つように設計されています。
    1.  **Fallthrough Edge (Succs[0])**: `defer` が正常にキューに入れられ、通常の実行が継続されるパス。
    2.  **Recover Edge (Succs[1])**: `defer` された関数内で `recover()` が成功し、関数が即座にリターンポイントに復帰するパス。このパスでは、`defer` の実行結果（`recover` の戻り値）に基づいて、関数の終了処理が再開されます。

### 制御フローの変更
- `src/cmd/compile/internal/gc/ssa.go` の `call` 関数において、`callDefer` の種類で呼び出された場合に `BlockDefer` が生成されるようになりました。
- `BlockDefer` が生成される際、`recover` エッジは `s.exit()` を呼び出す新しいブロック（`r`）に接続されます。これにより、`recover` が成功した場合でも、`deferreturn` や戻り値のコピーといった関数の終了処理が確実に実行されるようになります。
- `s.exit()` 関数自体も変更され、`hasdefer` フラグが設定されている場合は、`deferreturn` が呼び出されるようになりました。これにより、すべての終了パスで `deferreturn` が実行されることが保証されます。

### コード生成の変更
- `src/cmd/compile/internal/gc/ssa.go` の `genState` 構造体から `deferBranches` と `deferTarget` フィールドが削除されました。これは、`BlockDefer` の導入により、`defer` の分岐処理がSSAレベルでより抽象的に扱われるようになったため、これらの低レベルなコード生成のフックが不要になったことを示唆しています。
- `ssa.OpAMD64CALLstatic` の処理において、`Deferreturn.Sym` への呼び出しの前にハードウェア `NOP` 命令が挿入されるようになりました。これは、スタックトレースの正確性を向上させるための変更です。`defer` された呼び出しが `deferreturn` の呼び出し元として表示される際、その直前の命令の行番号がスタックトレースに表示されることがあります。この `NOP` を挿入することで、`deferreturn` の呼び出し自体が正しい行番号を持つようになります。

### その他のSSAパスへの影響
- `src/cmd/compile/internal/ssa/check.go`: 新しい `BlockDefer` タイプに対するバリデーションロジックが追加されました。`BlockDefer` は常に2つの後続ブロックを持つこと、および制御値がメモリタイプであることを確認します。
- `src/cmd/compile/internal/ssa/flagalloc.go`: `BlockDefer` がフラグ値を内部的に使用または破壊する可能性があるため、`BlockDefer` の後ではフラグ値が無効になるように処理が追加されました。
- `src/cmd/compile/internal/ssa/gen/genericOps.go` および `src/cmd/compile/internal/ssa/opGen.go`: `BlockDefer` がSSAブロックタイプとして正式に定義されました。
- `src/cmd/compile/internal/ssa/likelyadjust.go`: `BlockDefer` も `BlockCall` と同様に、`likelyadjust` パスで処理されるようになりました。これは、`defer` 呼び出しがプログラムの実行パスに与える影響を考慮するためです。
- `src/cmd/compile/internal/ssa/phiopt.go`: `phiopt` パスにおけるブロックの探索ロジックが `len(b0.Succs) == 1 && len(b0.Preds) == 1` を条件とするように変更されました。これは、`BlockDefer` のような複数の後続を持つブロックが導入されたことによる、より一般的な制御フローグラフの構造に対応するためと考えられます。
- `src/cmd/compile/internal/ssa/regalloc.go`: `BlockDefer` も `BlockCall` と同様に、レジスタ割り当ての際に「呼び出し」として扱われるようになりました。これは、`defer` 呼び出しがレジスタの状態を破壊する可能性があるため、レジスタ割り当ての正確性を保つために必要です。

## コアとなるコードの解説

このコミットの核心は、GoコンパイラのSSAバックエンドが `defer` と `recover` の相互作用をどのようにモデル化し、コード生成するかを根本的に変更した点にあります。

以前は、`defer` の実行と `recover` による復帰は、SSAレベルで十分に抽象化されておらず、低レベルなコード生成段階で特殊な分岐ロジック（`deferBranches`, `deferTarget` など）を用いて処理されていました。しかし、このアプローチでは、`panic` から `recover` された場合の関数の終了処理（`deferreturn` の呼び出しや戻り値のコピー）が、通常の終了パスと異なるために適切に実行されないという問題が発生していました。

新しい `BlockDefer` SSAブロックタイプは、この問題を解決するために導入されました。
`BlockDefer` は、`defer` 呼び出しの直後に配置され、その `defer` が `recover` によって中断される可能性があることをコンパイラに明示的に伝えます。
- `BlockDefer` の `Succs[0]` は、`recover` が発生しなかった場合の通常の実行パス（`defer` がキューに入れられ、関数が継続される）を表します。
- `BlockDefer` の `Succs[1]` は、`recover` が成功した場合のパスを表します。このパスは、`s.exit()` を呼び出す新しいブロックに接続されます。`s.exit()` は、`deferreturn` の呼び出しや戻り値のコピーなど、関数終了時に必要なすべてのクリーンアップ処理を実行します。

これにより、`panic` から `recover` された場合でも、コンパイラは `BlockDefer` の `Succs[1]` パスをたどることで、必要な終了処理を確実に実行できるようになります。この変更は、SSA形式の抽象度を高め、`defer`/`recover` のセマンティクスをより正確に表現することで、コンパイラの堅牢性と正確性を向上させました。

また、`deferreturn` 呼び出しの前にハードウェア `NOP` 命令を挿入する変更は、デバッグ時のスタックトレースの品質を向上させるための細かな改善です。これにより、`defer` 関連のスタックフレームがより意味のある行番号を持つようになります。

`phiopt` や `regalloc` などの他のSSAパスも `BlockDefer` を認識するように更新されており、SSA形式全体の整合性が保たれています。

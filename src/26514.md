## 元コミット内容

このコミットは、GoコンパイラのSSAバックエンドにおいて、ロードと他の演算（load+op）を結合する最適化の準備を行います。具体的には、定数ストア操作で使用されていた`StoreConst`型を`ValAndOff`にリネームし、他の操作でも利用できるように汎用化します。また、`ValAndOff`の出力形式を改善し、以前試みられたCMP+ロード操作の結合に関するメモとチェックを追加しています。

## 変更の背景

GoコンパイラのSSAバックエンドは、プログラムの最適化を目的としています。このコミットの主な動機は、メモリからのデータロードとそれに続く演算を単一のCPU命令に結合する最適化（load+op combining）を可能にすることです。このような結合は、命令数を減らし、パイプラインの効率を高めることで、生成されるコードのパフォーマンスを向上させることができます。

以前は、定数値をメモリにストアする際に、その定数とオフセットを`AuxInt`フィールドにエンコードするために`StoreConst`という特定の型が使用されていました。しかし、ロードと他の演算を結合する最適化を実装するためには、定数ストアだけでなく、より広範な種類の操作で「値とオフセット」のペアを表現できる汎用的なメカニズムが必要でした。

このコミットは、`StoreConst`を`ValAndOff`というより一般的な名前に変更し、その機能を拡張することで、将来的な最適化のための柔軟な基盤を提供します。また、以前の試みで直面した課題（特にフラグを生成する操作とフラグアロケーションの相互作用）に関するメモを追加し、今後の開発の指針としています。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを中間表現（IR）に変換し、様々な最適化を適用します。SSA（Static Single Assignment）形式はその中間表現の一つです。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が容易になり、デッドコード削除、共通部分式除去、レジスタ割り当てなどの最適化が効率的に行えるようになります。

SSA形式のプログラムは、`Value`と呼ばれるノードのグラフとして表現されます。各`Value`は特定の操作（`Op`）を表し、入力として他の`Value`を取り、出力として結果の`Value`を生成します。

### AuxIntフィールド

GoコンパイラのSSAバックエンドにおいて、`ssa.Value`構造体には`AuxInt`というフィールドがあります。このフィールドは、特定の操作（`Op`）に追加の整数定数情報を付加するために使用されます。例えば、定数ロード操作ではロードする定数値、メモリ操作ではオフセット値、シフト操作ではシフト量などが`AuxInt`に格納されます。

`AuxInt`は`int64`型であり、このコミットで変更される`ValAndOff`のように、複数の情報をビットフィールドとしてパックして格納することがあります。これにより、`Value`構造体自体のフィールド数を抑えつつ、必要な情報を効率的に表現できます。

### ストア定数最適化 (Store Constant Optimization)

ストア定数最適化とは、プログラムがメモリ上の特定のアドレスに定数値を書き込む操作を最適化する手法です。例えば、`MOVQconst`（定数をレジスタにロード）と`MOVQstore`（レジスタの内容をメモリにストア）という2つの命令がある場合、これらを`MOVQstoreconst`（定数を直接メモリにストア）という単一の命令に結合することで、命令フェッチやデコードのオーバーヘッドを削減し、パフォーマンスを向上させることができます。

この最適化は、コンパイラのバックエンド、特にリライトルールによって実現されます。リライトルールは、特定のパターンに一致するSSA操作のシーケンスを、より効率的な単一の操作に変換します。

### ロード+演算の結合 (Load+Op Combining)

ロード+演算の結合は、メモリから値をロードする操作と、そのロードされた値に対して行われる演算を、単一のCPU命令に結合する最適化です。多くのCPUアーキテクチャ（特にx86-64）では、メモリオペランドを直接演算命令に指定できるため、この種の最適化が可能です。

例えば、メモリから値をロードしてレジスタに格納し、そのレジスタの値に別の値を加算する代わりに、メモリからロードした値を直接加算する命令を使用できます。これにより、中間的なレジスタへのロード操作が不要になり、命令数と実行サイクルを削減できます。

この最適化は、コンパイラのSSAバックエンドにおけるリライトルールで実装されますが、フラグレジスタに影響を与える演算（例: 比較命令）と組み合わせる際には、フラグアロケーションの複雑さが増すという課題があります。

### AMD64アセンブリ命令

*   **MOVQstoreconst, MOVLstoreconst, MOVWstoreconst, MOVBstoreconst**: それぞれ8バイト（Qword）、4バイト（Dword）、2バイト（Word）、1バイト（Byte）の定数値をメモリに直接ストアする命令を表すSSAオペレーション。
*   **LEAQ (Load Effective Address Qword)**: メモリのアドレス計算結果をレジスタにロードする命令。ポインタ演算やオフセットの加算によく使用されます。
*   **ADDQconst**: 定数を加算する命令。
*   **CMP (Compare)**: 2つのオペランドを比較し、CPUのフラグレジスタを設定する命令。

### フラグレジスタとフラグアロケーション (Flag Register and Flag Allocation)

x86-64アーキテクチャには、演算結果の状態（ゼロ、符号、オーバーフローなど）を示すフラグを保持するフラグレジスタ（RFLAGS）があります。比較（CMP）や算術演算（ADD, SUBなど）の多くは、このフラグレジスタを更新します。

コンパイラは、これらのフラグが後続の条件分岐などで正しく使用されるように、フラグレジスタの状態を管理する必要があります。これをフラグアロケーションと呼びます。ロード+演算の結合において、もし結合される演算がフラグを生成する場合、そのフラグが後続の命令で必要とされるかどうか、またそのフラグが他の命令によって上書きされないか、といった複雑な考慮が必要になります。このコミットの`TODO`ファイルにあるメモは、この課題に言及しています。

## 技術的詳細

このコミットの技術的な核心は、`StoreConst`型を`ValAndOff`にリネームし、その機能を拡張して、より広範な最適化の可能性を開くことにあります。

1.  **`StoreConst`から`ValAndOff`へのリネームと汎用化**:
    *   `src/cmd/compile/internal/ssa/op.go`において、以前は定数ストア専用だった`StoreConst`型が`ValAndOff`にリネームされました。
    *   `ValAndOff`は`int64`のエイリアスであり、高32ビットに値（`Val`）、低32ビットにオフセット（`Off`）を格納する構造は変わりません。
    *   新しい`ValAndOff`型には、`Val()`、`Off()`、`Int64()`メソッドに加えて、デバッグ出力用の`String()`メソッドが追加されました。これにより、`ValAndOff`の内容が`val=X,off=Y`という形式で分かりやすく表示されるようになります。

    ```go

    }

    }
    func (x ValAndOff) Int64() int64 {
    	return int64(x)
    ```

2.  **`valid*`および`make*`関数の更新**:
    *   `validStoreConstOff`は`validOff`に、`validStoreConst`は`validValAndOff`にリネームされました。
    *   `makeStoreConst`は`makeValAndOff`にリネームされ、`ValAndOff`のインスタンスを生成します。
    *   これらの関数は、値とオフセットがそれぞれ32ビット整数に収まることを確認し、`ValAndOff`の`int64`表現に正しくパックできるかを検証します。

    ```go
    // op.go
    func validVal(val int64) bool {
    	return val == int64(int32(val))
    }
    func validOff(off int64) bool {
    	return off == int64(int32(off))
    }
    func validValAndOff(val, off int64) bool {
    	if !validVal(val) {
    		return false
    	}
    	if !validOff(off) {
    		return false
    	}
    	return true
    }
    func makeValAndOff(val, off int64) int64 {
    	if !validValAndOff(val, off) {
    		panic("invalid makeValAndOff")
    	}
    	return ValAndOff(val<<32 + int64(uint32(off))).Int64()
    }
    ```

### `src/cmd/compile/internal/ssa/op.go`

`StoreConst`型が`ValAndOff`にリネームされ、`String()`メソッドが追加されました。また、関連するヘルパー関数も`ValAndOff`に合わせてリネーム・修正されています。

```go
// op.go
import "fmt" // fmtパッケージがインポートされた

// A ValAndOff is used by the several opcodes.  It holds
// both a value and a pointer offset.
// A ValAndOff is intended to be encoded into an AuxInt field.
// The zero ValAndOff encodes a value of 0 and an offset of 0.
// The high 32 bits hold a value.
// The low 32 bits hold a pointer offset.
type ValAndOff int64

func (x ValAndOff) Val() int64 {
	return int64(x) >> 32
}
func (x ValAndOff) Off() int64 {
	return int64(int32(x))
}
func (x ValAndOff) Int64() int64 {
	return int64(x)
}
func (x ValAndOff) String() string {
	return fmt.Sprintf("val=%d,off=%d", x.Val(), x.Off())
}

// validVal reports whether the value can be used
// as an argument to makeValAndOff.
func validVal(val int64) bool {
	return val == int64(int32(val))
}

// validOff reports whether the offset can be used
// as an argument to makeValAndOff.
func validOff(off int64) bool {
	return off == int64(int32(off))
}

// validValAndOff reports whether we can fit the value and offset into
// a ValAndOff value.
func validValAndOff(val, off int64) bool {
	if !validVal(val) {
		return false
	}
	if !validOff(off) {
		return false
	}
	return true
}

// makeValAndOff encodes a ValAndOff into an int64 suitable for storing in an AuxInt field.
func makeValAndOff(val, off int64) int64 {
	if !validValAndOff(val, off) {
		panic("invalid makeValAndOff")
	}
	return ValAndOff(val<<32 + int64(uint32(off))).Int64()
}

func (x ValAndOff) canAdd(off int64) bool {
	newoff := x.Off() + off
	return newoff == int64(int32(newoff))
}

func (x ValAndOff) add(off int64) int64 {
	if !x.canAdd(off) {
		panic("invalid ValAndOff.add")
	}
	return makeValAndOff(x.Val(), x.Off()+off)
}
```

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/op.go` の変更

このファイルは、GoコンパイラのSSA中間表現における基本的な操作（Op）と、それに関連する補助データ型を定義しています。

最も重要な変更は、`StoreConst`型が`ValAndOff`にリネームされたことです。

```go
type ValAndOff int64
```

このリネームは、この型が単に「定数ストア」のためだけでなく、より広範な「値とオフセット」のペアを表現するために使用されることを示唆しています。`AuxInt`フィールドは`int64`型であり、この`ValAndOff`型は、その`int64`値の高32ビットに実際の値（`Val`）を、低32ビットにオフセット（`Off`）をパックして格納します。

新しく追加された`String()`メソッドは、デバッグやログ出力の際に`ValAndOff`の内容を人間が読みやすい形式で表示するために役立ちます。

```go
func (x ValAndOff) String() string {
	return fmt.Sprintf("val=%d,off=%d", x.Val(), x.Off())
}
```

例えば、`ValAndOff(0x123456780000000A)`という値があった場合、`String()`メソッドは`"val=305419896,off=10"`のような出力を生成し、値とオフセットを明確に区別して表示します。

また、`validVal`、`validOff`、`validValAndOff`、`makeValAndOff`といったヘルパー関数は、値とオフセットがそれぞれ32ビットの範囲に収まることを保証し、`int64`へのパック/アンパックが正しく行われるようにします。これは、`AuxInt`が32ビットのオフセットと32ビットの値を格納するために使用されるため、オーバーフローを防ぐ上で重要です。

`canAdd`と`add`メソッドは、既存の`ValAndOff`にオフセットを加算する機能を提供します。これも、加算後のオフセットが32ビットの範囲に収まることを確認することで、安全な操作を保証します。

これらの変更により、`ValAndOff`はSSAバックエンド内で「値とオフセット」の概念を表現するための汎用的なツールとなり、将来的な最適化（特にロードと演算の結合）において、より柔軟なデータ表現を可能にします。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` の変更

このファイルは、GoコンパイラのSSAバックエンドがAMD64アーキテクチャ向けにコードを生成する際に適用するリライトルールを定義しています。これらのルールは、SSA形式の操作パターンを、より効率的な単一の機械語命令に変換するために使用されます。

このコミットでは、定数ストアに関連する全てのリライトルールが、`StoreConst`の代わりに新しい`ValAndOff`型を使用するように更新されました。例えば、以下のルールは、定数`c`を`ptr`が指すアドレスの`off`オフセットにストアする`MOVQstore`と`MOVQconst`の組み合わせを、単一の`MOVQstoreconst`命令に結合するものです。

```diff
-(MOVQstore [off] {sym} ptr (MOVQconst [c]) mem) && validStoreConst(c,off) ->
-	(MOVQstoreconst [makeStoreConst(c,off)] {sym} ptr mem)
+(MOVQstore [off] {sym} ptr (MOVQconst [c]) mem) && validValAndOff(c,off) ->
+	(MOVQstoreconst [makeValAndOff(c,off)] {sym} ptr mem)
```

この変更は、ルールの意味論を変えるものではなく、単に基盤となるデータ型とそれに関連するヘルパー関数がリネームされたことに対応するものです。これにより、既存の最適化ロジックが新しい`ValAndOff`の定義と一貫性を保つことができます。

### `src/cmd/compile/internal/gc/ssa.go` の変更

このファイルは、SSA中間表現から最終的な機械語コードを生成するプロセスの一部を担っています。具体的には、`genValue`関数は特定のSSA `Value`ノードに対応するアセンブリ命令を生成します。

このコミットでは、`MOVXstoreconst`（`MOVQstoreconst`, `MOVLstoreconst`など）オペレーションを処理する部分が変更されました。以前は`ssa.StoreConst(v.AuxInt)`を使用して`AuxInt`から値とオフセットを抽出していましたが、これが`ssa.ValAndOff(v.AuxInt)`に置き換えられました。

```go
// gc/ssa.go
case ssa.OpAMD64MOVQstoreconst, ssa.OpAMD64MOVLstoreconst, ssa.OpAMD64MOVWstoreconst, ssa.OpAMD64MOVBstoreconst:
	p := Prog(v.Op.Asm())
	p.From.Type = obj.TYPE_CONST
	sc := ssa.ValAndOff(v.AuxInt) // ここが変更された
	i := sc.Val()
	// ...
```

この変更も、`StoreConst`から`ValAndOff`への型のリネームに対応するものであり、コード生成ロジックが新しい型定義と整合するように更新されています。機能的な変更ではなく、APIの変更に追従するものです。

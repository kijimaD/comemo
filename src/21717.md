# [インデックス 21717] ファイルの概要

`src/liblink/sym.c`は、Go言語のリンカ（`liblink`）の一部であり、シンボル処理に関連するC言語のソースファイルです。このファイルは、リンカが様々なオペレーティングシステム（OS）のヘッダ情報を識別し、それに対応する内部表現をマッピングするために使用されるデータ構造を含んでいます。具体的には、OSタイプを文字列に変換する際のルックアップテーブルの一部を管理していました。

## コミット

このコミットは、Go言語のリンカ（`liblink`）において、Linuxターゲット向けにビルドする際に「unknown TLS base」というエラーメッセージが表示される問題に対する修正です。この問題は、リンカが内部的にOSタイプを文字列に変換する際に、誤ってLinuxをAndroidとして識別してしまうことに起因していました。コミットは、OS識別ロジック内のエントリの順序を修正することで、この誤った識別を解消し、より正確なエラーメッセージが表示されるようにします。

## 元コミット内容

```

headstr(Hlinux) was reporting "android",
making for some confusing error messages.

## 変更の背景

この変更の背景には、Go言語のリンカが特定のOS（この場合はLinux）向けにバイナリを生成する際に、誤ったエラーメッセージを出力するという問題がありました。具体的には、リンカがスレッドローカルストレージ（TLS）のベースアドレスを解決できない場合に表示されるエラーメッセージが、「unknown TLS base on android」のように、ターゲットがLinuxであるにもかかわらず「android」と報告されていました。

この混乱の原因は、リンカ内部でOSタイプを文字列に変換する`headstr`関数（またはそれに相当するロジック）が、`Hlinux`というLinuxを示す内部定数に対して、誤って"android"という文字列を返していたことにありました。これは、OSタイプと文字列のマッピングを定義する内部配列の順序に問題があったためです。配列内で`Hlinux`に対応する"android"のエントリが、本来の"linux"のエントリよりも前に定義されていたため、ルックアップ時に先に"android"がマッチしてしまっていたのです。

この誤解を招くエラーメッセージは、開発者が問題を診断する上で大きな障害となるため、正確なOS情報を反映するように修正する必要がありました。このコミットは、その修正を目的としています。

## 前提知識の解説

### Go言語のリンカ (liblink)

Go言語のビルドプロセスにおいて、リンカは非常に重要な役割を担っています。Goのソースコードは、まずコンパイラによってオブジェクトファイルに変換され、その後、これらのオブジェクトファイルと必要なライブラリがリンカによって結合され、実行可能なバイナリが生成されます。

かつて、GoのリンカはC言語で書かれた`liblink`というコンポーネントを一部利用していました。このコミットがなされた2015年時点では、まだC言語のコードがGoのビルドツールチェインの一部として存在していました。現在では、Goのリンカの大部分はGo言語自体で書かれており、`cmd/link`パッケージとして提供されています。しかし、このコミットは、Goの進化の過程でC言語のレガシーコンポーネントがどのように扱われていたかを示す良い例です。

### Thread Local Storage (TLS)

スレッドローカルストレージ（TLS）は、マルチスレッド環境において、各スレッドがそれぞれ独立したデータを持つことを可能にするメカニズムです。通常、グローバル変数や静的変数はプロセス内のすべてのスレッドで共有されますが、TLSを使用すると、同じ変数名であっても各スレッドが独自のコピーを持つことができます。

Go言語のランタイムは、ゴルーチン（Goの軽量スレッド）のスタック管理やスケジューリングなど、内部的な処理のためにTLSを間接的に利用することがあります。特に、OSが提供するTLSメカニズムは、Goランタイムが低レベルの操作を行う際に利用されることがあります。リンカは、実行可能ファイルがTLS領域をどのように配置し、アクセスするかを決定する上で重要な役割を果たします。

このコミットにおける「TLS base」とは、ネットワーク通信で用いられるTransport Layer Security (TLS) とは異なり、リンカが実行可能ファイル内でスレッドローカルストレージの基底アドレスをどのように扱うか、という文脈でのTLSを指します。

### `GOOS`とクロスコンパイル

`GOOS`はGo言語の環境変数の一つで、ビルドターゲットとなるオペレーティングシステムを指定します。例えば、`GOOS=linux`はLinux向け、`GOOS=windows`はWindows向け、`GOOS=android`はAndroid向けにビルドすることを意味します。

Go言語は、この`GOOS`と`GOARCH`（アーキテクチャ）環境変数を設定することで、異なるOSやCPUアーキテクチャ向けのバイナリを簡単に生成できる「クロスコンパイル」の能力を標準で備えています。リンカは、この`GOOS`の値に基づいて、ターゲットOSに特有の実行可能ファイル形式（例: Linux/AndroidではELF、macOSではMach-O、WindowsではPE）や、OS固有のシステムコール、メモリ配置などを適切に処理します。

### `headstr`関数とOS識別

コミットメッセージに登場する`headstr`は、Goのリンカ内部でOSの内部表現（例: `Hlinux`）を対応する文字列（例: "linux"）に変換するために使用される関数、またはそのロジックを指します。リンカは、ビルドターゲットのOSを識別し、それに基づいて適切な処理を行う必要があります。この識別は、エラーメッセージの生成や、OS固有のコードパスの選択など、様々な場面で利用されます。

このコミットでは、このOS識別ロジックが、特定の条件下で誤った文字列を返してしまうという問題が発生していました。

## 技術的詳細

このコミットの技術的な核心は、`src/liblink/sym.c`ファイル内の`headers`という静的配列の定義にあります。この配列は、OSの内部定数（例: `Hlinux`）と、それに対応する文字列名（例: "linux"）をマッピングするために使用されていました。

```c
static struct {
	char *name;
	int val;
} headers[] = {
	{"android",	Hlinux}, // 問題の原因となっていた行
	{"darwin",	Hdarwin},
	{"dragonfly",	Hdragonfly},
	{"elf",		Helf},
	{"freebsd",	Hfreebsd},
	{"linux",	Hlinux},   // 本来のLinuxのエントリ
	{"android",	Hlinux}, // 修正後のAndroidのエントリ
	{"nacl",	Hnacl},
	{"netbsd",	Hnetbsd},
	{"openbsd",	Hopenbsd},
	// ... 他のエントリ ...
};
```

リンカ内部の`headstr`関数（または類似のルックアップロジック）は、この`headers`配列を線形に走査し、引数として与えられたOSの内部定数（例えば`Hlinux`）に最初にマッチしたエントリの`name`フィールドを返していました。

問題が発生したのは、配列の初期の定義において、`{"android", Hlinux}`というエントリが、本来の`{"linux", Hlinux}`というエントリよりも前に配置されていたためです。`Hlinux`という同じ内部定数に対して、"android"と"linux"の2つの文字列がマッピングされていました。

リンカが`Hlinux`に対応する文字列を検索する際、配列の先頭から順に走査するため、最初に`{"android", Hlinux}`というエントリに遭遇し、その結果`headstr(Hlinux)`は"android"を返してしまっていました。これにより、Linux向けにビルドしているにもかかわらず、TLSベースのエラーメッセージが「unknown TLS base on android」と表示されるという、誤解を招く状況が生じていました。

このコミットは、`{"android", Hlinux}`のエントリを`{"linux", Hlinux}`のエントリの後に移動させることで、このルックアップの順序の問題を解決しています。

## コアとなるコードの変更箇所

変更は`src/liblink/sym.c`ファイル内の`headers`配列の定義にあります。

```diff
--- a/src/liblink/sym.c
+++ b/src/liblink/sym.c
@@ -44,12 +44,12 @@ static struct {

 	int val;
 } headers[] = {

 	{"darwin",	Hdarwin},
 	{"dragonfly",	Hdragonfly},

具体的には、以下の変更が行われました。

1.  `{"android", Hlinux},` の行が、元の位置（`{"darwin", Hdarwin},` の直前）から削除されました。
2.  削除された行が、`{"linux", Hlinux},` の行の直後に再挿入されました。この際、コメント `// must be after "linux" entry or else headstr(Hlinux) == "android"` が追加され、変更の意図が明確にされています。

## コアとなるコードの解説

このコミットの核心は、`headers`配列内のエントリの**順序**を修正することにあります。

元のコードでは、`headers`配列は以下のような順序で定義されていました（関連部分のみ抜粋）：

```c
	{"android",	Hlinux}, // (1)
	// ...
	{"linux",	Hlinux},   // (2)
```

リンカが`Hlinux`という内部定数に対応する文字列名を検索する際、配列を先頭から順に走査します。この場合、まず`(1)`のエントリ`{"android", Hlinux}`にマッチしてしまい、`headstr(Hlinux)`は"android"を返していました。これは、Linuxターゲット向けにビルドしているにもかかわらず、誤ったOS名がエラーメッセージに表示される原因となっていました。

修正後のコードでは、`{"android", Hlinux}`のエントリが`{"linux", Hlinux}`の後に移動されました：

```c
	// ...
	{"linux",	Hlinux},   // (2)
	{"android",	Hlinux}, // (1) がここに移動
```

この変更により、`headstr(Hlinux)`が呼び出された際、リンカはまず`(2)`のエントリ`{"linux", Hlinux}`に遭遇し、正しく"linux"という文字列を返すようになります。その後、`(1)`のエントリは、`Hlinux`が既にマッチしているため、この特定のルックアップでは到達されません。

このシンプルな順序の変更によって、リンカはLinuxターゲットに対して正確なOS情報をエラーメッセージに含めることができるようになり、開発者が問題を診断する際の混乱が解消されました。コメントが追加されたことで、将来のコード読者にとってもこの順序がなぜ重要であるかが明確になっています。

2.  削除された行が、`{"linux", Hlinux},` の行の直後に再挿入されました。この際、コメント `// must be after "linux" entry or else headstr(Hlinux) == "android"` が追加され、変更の意図が明確にされています。

## コアとなるコードの解説

このコミットの核心は、`headers`配列内のエントリの**順序**を修正することにあります。

元のコードでは、`headers`配列は以下のような順序で定義されていました（関連部分のみ抜粋）：

```c
	{"android",	Hlinux}, // (1)
	// ...
	{"linux",	Hlinux},   // (2)
```

リンカが`Hlinux`という内部定数に対応する文字列名を検索する際、配列を先頭から順に走査します。この場合、まず`(1)`のエントリ`{"android", Hlinux}`にマッチしてしまい、`headstr(Hlinux)`は"android"を返していました。これは、Linuxターゲット向けにビルドしているにもかかわらず、誤ったOS名がエラーメッセージに表示される原因となっていました。

修正後のコードでは、`{"android", Hlinux}`のエントリが`{"linux", Hlinux}`の後に移動されました：

```c
	// ...
	{"linux",	Hlinux},   // (2)
	{"android",	Hlinux}, // (1) がここに移動
```

この変更により、`headstr(Hlinux)`が呼び出された際、リンカはまず`(2)`のエントリ`{"linux", Hlinux}`に遭遇し、正しく"linux"という文字列を返すようになります。その後、`(1)`のエントリは、`Hlinux`が既にマッチしているため、この特定のルックアップでは到達されません。

このシンプルな順序の変更によって、リンカはLinuxターゲットに対して正確なOS情報をエラーメッセージに含めることができるようになり、開発者が問題を診断する際の混乱が解消されました。コメントが追加されたことで、将来のコード読者にとってもこの順序がなぜ重要であるかが明確になっています。

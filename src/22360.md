## 変更の背景

## 前提知識の解説

このコミットを理解するためには、以下の概念について理解しておく必要がある。

1.  **Thread Local Storage (TLS)**:
    *   TLSは、各スレッドがそれぞれ固有のデータを保持するためのメカニズムである。グローバル変数とは異なり、TLSに格納されたデータは、同じプロセス内の他のスレッドからは直接アクセスできない。
    *   Go言語において、TLSは特にGoルーチン (goroutine) のコンテキスト管理において重要である。GoルーチンはOSのスレッドとは異なる軽量な実行単位であり、GoランタイムはGoルーチンの状態 (例えば、現在のGoルーチンを示す `g` ポインタ) をOSスレッド間で切り替える際に、TLSを利用してその状態を保持・復元することがある。特にC言語のコードと相互運用する際に、Goルーチンの状態をOSスレッドに紐付けるためにTLSが用いられる。
    *   x86アーキテクチャでは、TLSベースアドレスは通常、特定のレジスタ (例: `FS` または `GS` セグメントレジスタ) を介してアクセスされるか、あるいは特別な命令やリロケーションタイプを用いて間接的にアクセスされる。

2.  **共有ライブラリ (`-shared` フラグ)**:
    *   Go言語は、`-buildmode=shared` フラグを使用して、Goのコードを共有ライブラリ (`.so` や `.dll` など) としてビルドする機能を提供する。これにより、他のプログラム (Goプログラムであるか否かを問わず) からGoの機能を呼び出すことが可能になる。
    *   共有ライブラリは、実行時にメモリにロードされ、複数のプロセスで共有されることでメモリ使用量を削減したり、モジュール性を高めたりする利点がある。
    *   しかし、共有ライブラリとしてビルドされたGoプログラムは、自身のGoランタイムを内包するため、複数のGo共有ライブラリが同じプロセスにロードされた場合や、GoプログラムがGo共有ライブラリをロードした場合に、ランタイムの管理やTLSの取り扱いにおいて複雑な問題が生じることがある。

3.  **リロケーション (Relocation)**:
    *   コンパイルされたプログラムやライブラリには、実行時にアドレスが確定するシンボル (変数や関数など) への参照が含まれる。リロケーションとは、リンカがこれらの参照を、実際のメモリ上のアドレスに解決するプロセスである。
    *   TLSに関連するリロケーションタイプはいくつか存在する。このコミットで言及されている `R_TLS_IE` (Thread-Local Storage, Initial Exec) は、特に共有ライブラリにおいて、TLS変数を効率的にアクセスするためのリロケーションモデルの一つである。
    *   `R_TLS_IE` は、通常、GOT (Global Offset Table) を介してTLS変数のオフセットを取得し、それを用いてTLSベースから目的の変数にアクセスする。これは、プログラムが起動時にTLSベースアドレスを一度だけ計算し、その後のアクセスを高速化する「Initial Exec」モデルの一部である。

4.  **Goのアセンブラ (`cmd/internal/obj/x86/asm6.go`)**:
    *   `cmd/internal/obj/x86/asm6.go` は、Goのツールチェーンの一部であり、x86アーキテクチャ向けのアセンブリコードを生成する役割を担っている。Goのコンパイラは、Goのソースコードを中間表現に変換し、最終的にこのアセンブラがターゲットアーキテクチャの機械語に変換する。
    *   このファイル内の `doasm` 関数は、アセンブリ命令を処理し、対応する機械語を生成する主要なロジックを含んでいる。TLSベースの計算やリロケーションの処理は、このアセンブラの段階で行われる。

## 技術的詳細

このコミットがrevertした元の変更は、`src/cmd/internal/obj/x86/asm6.go` 内の `doasm` 関数に、Linux環境で `-shared` フラグが有効な場合のTLSベースの計算ロジックを追加しようとしたものであった。

削除されたコードブロックは、以下の処理を行おうとしていた:

*   **`case obj.Hlinux:`**: Linuxホスト環境での処理を指定。
*   **`if ctxt.Flag_shared == 0 { ... }`**: `-shared` フラグが設定されていない場合にエラーを出す。これは、このコードが共有ライブラリビルド専用であることを示唆している。
*   **`MOV TLS, R_to` の変換**: コメントに `MOV TLS, R_to` が `movq g@gottpoff(%rip), R_to` に変換されると記載されている。
    *   `MOV TLS, R_to` は、Goのアセンブリ言語における擬似命令で、TLSベースアドレスをレジスタ `R_to` にロードすることを意図している。
    *   `movq g@gottpoff(%rip), R_to` は、x86-64のアセンブリ命令である。
        *   `movq`: 64ビットの値を移動する命令。
        *   `g@gottpoff(%rip)`: これは、`g` (Goルーチンポインタ) シンボルに関連するTLSオフセットを、GOT (Global Offset Table) を介して、プログラムカウンタ (`%rip`) 相対アドレス指定で取得することを示している。`gottpoff` は "GOT Thread Pointer Offset" の略で、TLS変数のオフセットがGOTに格納されていることを意味する。
        *   `R_to`: ターゲットレジスタ。
*   **`R_TLS_IE` リロケーション**:
    *   この命令は、`R_TLS_IE` (Thread-Local Storage, Initial Exec) リロケーションタイプを伴う。
    *   `R_TLS_IE` は、リンカが実行時にTLS変数のアドレスを解決するために使用する。具体的には、GOT内のエントリを指し、そのエントリがTLSベースからのオフセットを提供する。
    *   元のコードでは、`obj.Addrel(ctxt.Cursym)` を呼び出してリロケーションエントリを作成し、`r.Type = obj.R_TLS_IE` を設定していた。
    *   `r.Add = -4` は、リロケーションの加算値であり、命令のオフセット調整に使用される。
*   **`ctxt.Andptr` の操作**: `ctxt.Andptr` は、アセンブリ命令のバイト列を構築するためのバッファポインタである。削除されたコードは、`movq` 命令のオペコード (`0x8B`, `0x05`) や、リロケーションに必要なゼロバイトをこのバッファに書き込んでいた。

このコードは、Goランタイムが共有ライブラリとしてビルドされた際に、Goルーチンポインタ `g` のようなTLS変数を効率的にアクセスするためのメカニズムを実装しようとしていた。しかし、この実装がビルドプロセスに問題を引き起こしたため、revertされた。問題の原因としては、リロケーションの計算ミス、特定のリンカとの非互換性、あるいはGoランタイムの他の部分との競合などが考えられる。

## コアとなるコードの解説

削除されたコードは、`doasm` 関数内の `switch` ステートメントの一部であり、特定のオペレーティングシステム (`obj.Hlinux`、つまりLinux) とビルドモード (`ctxt.Flag_shared` が設定されている場合) に特化したTLSベースのロード命令を生成するロジックを含んでいた。

このブロックの主要な役割は以下の通りである:

1.  **共有ビルドの確認**: `if ctxt.Flag_shared == 0` で、共有ライブラリとしてビルドされていない場合に致命的なエラーを発生させる。これは、このTLS処理が共有ライブラリのコンテキストでのみ意味を持つことを強制している。
2.  **命令の生成**:
    *   `movq g@gottpoff(%rip), R_to` というアセンブリ命令を生成しようとしていた。これは、Goルーチンポインタ `g` のTLSオフセットをGOTから取得し、それをPC相対アドレス指定でターゲットレジスタ `R_to` にロードするものである。
    *   `ctxt.Rexflag`、`ctxt.Andptr` の操作は、この `movq` 命令の機械語バイト列を正確に生成するためのアセンブラ内部の処理である。`0x8B` と `0x05` は `movq` 命令のオペコードの一部であり、`reg[p.To.Reg] << 3` はターゲットレジスタのエンコーディングに関連する。
3.  **リロケーションの追加**:
    *   `r := obj.Addrel(ctxt.Cursym)` で新しいリロケーションエントリを作成し、現在のシンボル (`ctxt.Cursym`) に関連付ける。
    *   `r.Off` はリロケーションのオフセット (命令内のどこにリロケーションが必要か) を設定する。
    *   `r.Type = obj.R_TLS_IE` は、このリロケーションが `R_TLS_IE` タイプであることを明示する。これは、リンカがTLSベースアドレスを解決するために使用する重要な情報である。
    *   `r.Siz = 4` はリロケーションのサイズ (4バイト) を示し、`r.Add = -4` はリロケーションの加算値である。

このコードブロック全体が削除されたことにより、Goのx86アセンブラは、共有ライブラリビルド時のLinuxにおけるTLSベースの特別な計算ロジックを持たなくなった。これは、元の実装がビルドを壊すという問題があったため、その機能を一時的に無効化する措置である。

    *   このファイル内の `doasm` 関数は、アセンブリ命令を処理し、対応する機械語を生成する主要なロジックを含んでいる。TLSベースの計算やリロケーションの処理は、このアセンブラの段階で行われる。

## 技術的詳細

このコミットがrevertした元の変更は、`src/cmd/internal/obj/x86/asm6.go` 内の `doasm` 関数に、Linux環境で `-shared` フラグが有効な場合のTLSベースの計算ロジックを追加しようとしたものであった。

削除されたコードブロックは、以下の処理を行おうとしていた:

*   **`case obj.Hlinux:`**: Linuxホスト環境での処理を指定。
*   **`if ctxt.Flag_shared == 0 { ... }`**: `-shared` フラグが設定されていない場合にエラーを出す。これは、このコードが共有ライブラリビルド専用であることを示唆している。
*   **`MOV TLS, R_to` の変換**: コメントに `MOV TLS, R_to` が `movq g@gottpoff(%rip), R_to` に変換されると記載されている。
    *   `MOV TLS, R_to` は、Goのアセンブリ言語における擬似命令で、TLSベースアドレスをレジスタ `R_to` にロードすることを意図している。
    *   `movq g@gottpoff(%rip), R_to` は、x86-64のアセンブリ命令である。
        *   `movq`: 64ビットの値を移動する命令。
        *   `g@gottpoff(%rip)`: これは、`g` (Goルーチンポインタ) シンボルに関連するTLSオフセットを、GOT (Global Offset Table) を介して、プログラムカウンタ (`%rip`) 相対アドレス指定で取得することを示している。`gottpoff` は "GOT Thread Pointer Offset" の略で、TLS変数のオフセットがGOTに格納されていることを意味する。
        *   `R_to`: ターゲットレジスタ。
*   **`R_TLS_IE` リロケーション**:
    *   この命令は、`R_TLS_IE` (Thread-Local Storage, Initial Exec) リロケーションタイプを伴う。
    *   `R_TLS_IE` は、リンカが実行時にTLS変数のアドレスを解決するために使用する。具体的には、GOT内のエントリを指し、そのエントリがTLSベースからのオフセットを提供する。
    *   元のコードでは、`obj.Addrel(ctxt.Cursym)` を呼び出してリロケーションエントリを作成し、`r.Type = obj.R_TLS_IE` を設定していた。
    *   `r.Add = -4` は、リロケーションの加算値であり、命令のオフセット調整に使用される。
*   **`ctxt.Andptr` の操作**: `ctxt.Andptr` は、アセンブリ命令のバイト列を構築するためのバッファポインタである。削除されたコードは、`movq` 命令のオペコード (`0x8B`, `0x05`) や、リロケーションに必要なゼロバイトをこのバッファに書き込んでいた。

このコードは、Goランタイムが共有ライブラリとしてビルドされた際に、Goルーチンポインタ `g` のようなTLS変数を効率的にアクセスするためのメカニズムを実装しようとしていた。しかし、この実装がビルドプロセスに問題を引き起こしたため、revertされた。問題の原因としては、リロケーションの計算ミス、特定のリンカとの非互換性、あるいはGoランタイムの他の部分との競合などが考えられる。

## コアとなるコードの解説

削除されたコードは、`doasm` 関数内の `switch` ステートメントの一部であり、特定のオペレーティングシステム (`obj.Hlinux`、つまりLinux) とビルドモード (`ctxt.Flag_shared` が設定されている場合) に特化したTLSベースのロード命令を生成するロジックを含んでいた。

このブロックの主要な役割は以下の通りである:

1.  **共有ビルドの確認**: `if ctxt.Flag_shared == 0` で、共有ライブラリとしてビルドされていない場合に致命的なエラーを発生させる。これは、このTLS処理が共有ライブラリのコンテキストでのみ意味を持つことを強制している。
2.  **命令の生成**:
    *   `movq g@gottpoff(%rip), R_to` というアセンブリ命令を生成しようとしていた。これは、Goルーチンポインタ `g` のTLSオフセットをGOTから取得し、それをPC相対アドレス指定でターゲットレジスタ `R_to` にロードするものである。
    *   `ctxt.Rexflag`、`ctxt.Andptr` の操作は、この `movq` 命令の機械語バイト列を正確に生成するためのアセンブラ内部の処理である。`0x8B` と `0x05` は `movq` 命令のオペコードの一部であり、`reg[p.To.Reg] << 3` はターゲットレジスタのエンコーディングに関連する。
3.  **リロケーションの追加**:
    *   `r := obj.Addrel(ctxt.Cursym)` で新しいリロケーションエントリを作成し、現在のシンボル (`ctxt.Cursym`) に関連付ける。
    *   `r.Off` はリロケーションのオフセット (命令内のどこにリロケーションが必要か) を設定する。
    *   `r.Type = obj.R_TLS_IE` は、このリロケーションが `R_TLS_IE` タイプであることを明示する。これは、リンカがTLSベースアドレスを解決するために使用する重要な情報である。
    *   `r.Siz = 4` はリロケーションのサイズ (4バイト) を示し、`r.Add = -4` はリロケーションの加算値である。

このコードブロック全体が削除されたことにより、Goのx86アセンブラは、共有ライブラリビルド時のLinuxにおけるTLSベースの特別な計算ロジックを持たなくなった。これは、元の実装がビルドを壊すという問題があったため、その機能を一時的に無効化する措置である。

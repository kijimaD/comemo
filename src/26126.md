## 変更の背景

この変更の背景には、HTTP/1.x プロトコルにおけるヘッダーの構文規則の厳密な適用があります。HTTPヘッダーフィールド名と値には、RFC 7230 (以前は RFC 2616) で定義された特定の文字セットのみが許可されています。過去には、一部のHTTPサーバー実装がこれらの規則を緩やかに解釈し、不正な文字を含むヘッダーを受け入れてしまうことがありました。

このような不正なヘッダーを受け入れることは、以下のような問題を引き起こす可能性があります。

1.  **セキュリティ脆弱性**:
    *   **HTTPレスポンス分割 (HTTP Response Splitting)**: 攻撃者が不正な改行文字（CRLF）をヘッダー値に挿入することで、サーバーが生成するHTTPレスポンスを操作し、複数のレスポンスに分割させることが可能になります。これにより、キャッシュポイズニング、クロスサイトスクリプティング (XSS)、セッション固定などの攻撃につながる可能性があります。
    *   **プロトコル曖昧性**: 不正な文字は、プロキシサーバーやロードバランサーなどの中間デバイスがヘッダーを正しく解釈できない原因となり、予期せぬ動作や情報漏洩を引き起こす可能性があります。
2.  **相互運用性の問題**: 標準に準拠しないヘッダーは、異なるHTTPクライアントやサーバー、プロキシ間で互換性の問題を引き起こす可能性があります。
3.  **デバッグの困難さ**: 不正な文字が原因で発生するエラーは、原因の特定が困難になることがあります。

Issue #11207 は、まさにこの問題、すなわち `net/http` サーバーが不正なバイトを含むヘッダーを許容してしまうという報告に対応するものです。このコミットは、これらの問題を解決し、GoのHTTPサーバーがより堅牢で安全なものとなるように、ヘッダーの検証を強化することを目的としています。

## 前提知識の解説

### HTTP/1.x ヘッダーの構文規則 (RFC 7230)

HTTP/1.x プロトコルでは、ヘッダーフィールドの構文が厳密に定義されています。

*   **ヘッダーフィールド名 (Field Name)**:
    *   フィールド名は、`token` として定義されます。
    *   `token` は、RFC 7230 のセクション 3.2.6 で定義されており、特定のASCII文字の集合（英数字と一部の記号）のみで構成される必要があります。具体的には、`!`、`#`、`$`、`%`、`&`、`'`、`*`、`+`、`-`、`.`、`^`、`_`、``` ` ``、`|`、`~` の記号と、英数字（`A-Z`, `a-z`, `0-9`）が許可されます。スペースや制御文字は許可されません。
    *   例: `Content-Type`, `X-Request-ID` は有効。`Content Type` (スペースを含む) や `Content\x00Type` (ヌルバイトを含む) は無効。

*   **ヘッダーフィールド値 (Field Value)**:
    *   フィールド値は、`field-content` として定義されます。
    *   `field-content` は、RFC 7230 のセクション 3.2.4 で定義されており、ASCII文字の集合（`HTAB` (タブ)、`SP` (スペース)、`VCHAR` (可視文字)）で構成される必要があります。
    *   `VCHAR` は、ASCIIコードで `!` (33) から `~` (126) までの文字を指します。
    *   つまり、タブ (`\t`) とスペース (` `) および `!` から `~` までの文字が許可されます。制御文字（ヌルバイト `\x00` など）や非ASCII文字は許可されません。
    *   歴史的に、フィールド値は `obs-fold` (複数行にわたるヘッダー値) を含むことができましたが、RFC 7230 では `obs-fold` は非推奨とされており、単一行で表現されるべきです。このコミットでは、単一行の検証に焦点を当てています。

### Go言語の `net/http` パッケージ

`net/http` パッケージは、Go言語におけるHTTPクライアントおよびサーバーの実装を提供します。このパッケージは、HTTPプロトコルの詳細を抽象化し、開発者が簡単にWebアプリケーションを構築できるように設計されています。サーバーサイドでは、`http.Server` がリクエストを受け取り、`http.Handler` インターフェースを実装するハンドラにディスパッチします。リクエストのパースは内部的に行われ、`http.Request` オブジェクトとしてハンドラに渡されます。このコミットは、`http.Request` オブジェクトが生成される前の、リクエストヘッダーのパース段階での検証ロジックを追加しています。

## 技術的詳細

このコミットは、HTTPリクエストヘッダーのフィールド名と値の検証ロジックを `net/http` パッケージに追加します。具体的には、以下の2つの新しいヘルパー関数が `src/net/http/request.go` に導入され、`src/net/http/server.go` のリクエスト処理ロジック内で利用されます。

1.  **`validHeaderName(v string) bool`**:
    *   この関数は、与えられた文字列 `v` が有効なHTTPヘッダーフィールド名であるかどうかをチェックします。
    *   HTTPヘッダーフィールド名は、RFC 7230 で定義されている `token` 文字セットに準拠する必要があります。
    *   実装では、`strings.IndexFunc(v, isNotToken)` を使用しています。`isNotToken` は、`token` 文字セットに含まれない文字を見つけるための内部的なヘルパー関数であると推測されます（コミットの差分には含まれていませんが、既存のコードベースに存在するはずです）。`IndexFunc` が `-1` を返した場合、それは `v` 内に `token` ではない文字が存在しないことを意味し、ヘッダー名が有効であることを示します。
    *   ヘッダー名が空文字列である場合は `false` を返します。

2.  **`validHeaderValue(v string) bool`**:
    *   この関数は、与えられた文字列 `v` が有効なHTTPヘッダーフィールド値であるかどうかをチェックします。
    *   HTTPヘッダーフィールド値は、RFC 7230 で定義されている `HTAB` (タブ)、`SP` (スペース)、`VCHAR` (可視文字) のいずれかで構成される必要があります。
    *   実装では、文字列 `v` をバイトごとにループし、各バイト `b` が以下の条件を満たすかを確認します。
        *   `b == '\t'` (タブ文字)
        *   `' ' <= b && b <= '~'` (スペースからチルダまでの可視ASCII文字)
    *   これらの条件のいずれも満たさないバイトが見つかった場合、そのヘッダー値は不正であると判断され、関数は `false` を返します。ループが最後まで到達した場合、すべてのバイトが有効であったため `true` を返します。

これらの検証関数は、`src/net/http/server.go` 内の `(c *conn) readRequest()` メソッドに統合されます。このメソッドは、クライアントからの生のリクエストを読み込み、`http.Request` オブジェクトにパースする役割を担っています。

変更後、`readRequest()` は `Host` ヘッダーの検証に加えて、`req.Header` マップ内のすべてのヘッダーについて、そのキー（ヘッダー名）と値（ヘッダー値）を検証します。
*   `validHeaderName(k)` が `false` を返した場合、`"invalid header name"` というエラーメッセージと共に `badRequestError` を返します。
*   `validHeaderValue(v)` が `false` を返した場合、`"invalid header value"` というエラーメッセージと共に `badRequestError` を返します。

`badRequestError` が返されると、HTTPサーバーはクライアントに対して `400 Bad Request` ステータスコードを返送し、不正なリクエストを拒否します。これにより、不正なヘッダーを持つリクエストがアプリケーション層に到達するのを防ぎ、上述のセキュリティリスクを軽減します。

また、`src/net/http/serve_test.go` に `TestServerValidatesHeaders` という新しいテストケースが追加され、この検証ロジックが正しく機能することを確認しています。このテストは、有効なヘッダーと無効なヘッダー（スペースを含むヘッダー名、ヌルバイトや非ASCII文字を含むヘッダー名や値）の両方に対して、サーバーが期待通りのレスポンス（200 OK または 400 Bad Request）を返すことを検証します。

## コアとなるコードの変更箇所

### `src/net/http/request.go`

```go
// 新しいヘルパー関数: ヘッダー名が有効かチェック
func validHeaderName(v string) bool {
	if len(v) == 0 {
		return false
	}
	return strings.IndexFunc(v, isNotToken) == -1
}

// 新しいヘルパー関数: ヘッダー値が有効かチェック
func validHeaderValue(v string) bool {
	for i := 0; i < len(v); i++ {
		b := v[i]
		if b == '\t' { // タブ文字は許可
			continue
		}
		if ' ' <= b && b <= '~' { // スペースからチルダまでの可視ASCII文字は許可
			continue
		}
		return false // それ以外の文字は不正
	}
	return true
}
```

## コアとなるコードの解説

このコミットの核となるのは、HTTPヘッダーの厳密な構文チェックを導入する `validHeaderName` と `validHeaderValue` の2つの関数です。

`validHeaderName` 関数は、HTTPヘッダー名がRFC 7230で定義された `token` 形式に準拠していることを保証します。`strings.IndexFunc` と `isNotToken` を組み合わせることで、ヘッダー名に許可されていない文字（例えばスペースや制御文字）が含まれていないかを効率的にチェックします。これにより、プロトコル違反や、中間プロキシがヘッダーを誤って解釈する可能性を防ぎます。

`validHeaderValue` 関数は、HTTPヘッダー値がタブ、スペース、および可視ASCII文字（`!` から `~` まで）のみで構成されていることを確認します。この関数は、ヘッダー値に含まれる可能性のあるヌルバイト (`\x00`) やその他の制御文字、非ASCII文字を検出して拒否します。これらの不正な文字は、HTTPレスポンス分割攻撃などのセキュリティ脆弱性の原因となるため、この検証は非常に重要です。

これらの検証関数は、`http.Server` のリクエスト処理パイプラインの早い段階、具体的には `readRequest` メソッド内で呼び出されます。これにより、不正なヘッダーを持つリクエストは、アプリケーションのロジックに到達する前に `400 Bad Request` エラーとして拒否されます。この「早期拒否」のメカニズムは、サーバーの堅牢性を高め、潜在的な攻撃ベクトルを減少させる上で効果的です。

追加されたテストケース `TestServerValidatesHeaders` は、これらの検証ロジックが意図した通りに機能することを保証します。様々な有効および無効なヘッダーの組み合わせをテストすることで、実装の正確性と完全性を確認しています。

全体として、このコミットはGoの `net/http` パッケージのセキュリティとプロトコル準拠を向上させ、より安全で信頼性の高いHTTPサーバー実装を提供します。

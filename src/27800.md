# [インデックス 27800] ファイルの概要

このコミットは、Goコンパイラ (`cmd/compile`) におけるエクスポートデータの構造に関する変更を扱っています。具体的には、インライン化可能な関数の本体情報を、プラットフォーム非依存のエクスポートデータセクションから、コンパイラ固有のエクスポートセクションへと移動させるものです。これにより、エクスポートデータの効率化とコードの簡素化が図られています。

## 変更の背景

Goコンパイラは、パッケージ間で情報を共有するためにエクスポートデータを使用します。これには、型情報、関数シグネチャ、そしてインライン化可能な関数の本体などが含まれます。以前の実装では、各関数シグネチャの隣に、その関数がインライン化可能な本体を持つかどうかを示す情報（`inl`という`int`値）が含まれていました。しかし、この`inl`値は、インライン化可能な本体を持たない関数に対しても存在し、エクスポートデータの肥大化を招いていました。

このコミットの背景には、エクスポートデータの効率化と、コンパイラ固有の情報をプラットフォーム非依存のデータセクションから分離するという設計思想があります。インライン化はコンパイラの最適化戦略の一部であり、その本体情報はコンパイラが利用する詳細な情報です。これをプラットフォーム非依存の汎用的なエクスポートデータから切り離すことで、データの構造をよりクリーンにし、将来的な変更や異なるコンパイラバックエンドへの対応を容易にすることが目的とされています。

具体的には、インライン化可能な関数本体の有無を個々の関数シグネチャで示すのではなく、インライン化可能な関数本体を持つ関数のみをまとめて、プラットフォーム固有のセクションでその本体と対応する関数インデックスをエクスポートするように変更されました。これにより、インライン化可能な本体を持たない関数から余分な`int`値が削除され、エクスポートデータが削減されます。

## 前提知識の解説

このコミットを理解するためには、以下の概念に関する知識が必要です。

1.  **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。Goのツールチェインの一部として提供されます。
2.  **エクスポートデータ (Export Data)**: Goコンパイラがパッケージをコンパイルする際に生成するメタデータの一種です。このデータには、パッケージが外部に公開する（エクスポートする）型、関数、変数などの情報が含まれます。他のパッケージがこのパッケージをインポートする際に、このエクスポートデータを読み込んで、インポートされた要素の情報を取得します。
3.  **インライン化 (Inlining)**: コンパイラの最適化手法の一つで、呼び出し元の関数に呼び出される関数の本体を直接埋め込むことです。これにより、関数呼び出しのオーバーヘッド（スタックフレームの作成、引数の渡し、戻り値の処理など）を削減し、プログラムの実行速度を向上させることができます。Goコンパイラは、特定の条件を満たす小さな関数を自動的にインライン化します。
4.  **プラットフォーム非依存 (Platform-independent)**: 特定のCPUアーキテクチャ（例: x86, ARM）やオペレーティングシステム（例: Linux, Windows）に依存しない性質を指します。エクスポートデータの一部は、どのプラットフォームでも共通して解釈できる形式であるべきです。
5.  **プラットフォーム固有 (Platform-specific)**: 特定のCPUアーキテクチャやオペレーティングシステムに依存する性質を指します。コンパイラの最適化に関する詳細な情報（例: インライン化されたコードの具体的な表現）は、プラットフォーム固有のセクションに含めるのが適切です。
6.  **`*Func` および `*Node`**: Goコンパイラの内部表現におけるデータ構造です。`*Func`は関数に関する情報を、`*Node`は抽象構文木 (AST) のノードを表します。インライン化可能な関数本体は、`*Node`のリストとして表現されることがあります。
7.  **`bexport.go` と `bimport.go`**: Goコンパイラの内部パッケージ (`src/cmd/compile/internal/gc`) に存在するファイルで、それぞれエクスポートデータの書き出し (binary export) と読み込み (binary import) を担当します。
8.  **`src/go/internal/gcimporter/bimport.go`**: Go言語の標準ライブラリの一部で、`go/importer`パッケージがコンパイラのエクスポートデータを読み込むための低レベルな実装を提供します。

## 技術的詳細

このコミットの主要な変更点は、Goコンパイラのエクスポートデータフォーマットと、それを処理するロジックの変更にあります。

以前の`bexport.go`では、`exporter`構造体に`inlined []*Func`というフィールドがあり、インライン化可能な関数本体を持つ関数をこのリストに集めていました。そして、各関数シグネチャをエクスポートする際に、その関数が`inlined`リストのどこに位置するかを示すインデックス（`int`値）をエクスポートしていました。インライン化可能な本体を持たない関数に対しては、`-1`がエクスポートされていました。

このコミットでは、以下の変更が行われました。

1.  **`exporter`構造体の変更**:
    *   `inlined []*Func`フィールドが削除され、代わりに`funcList []*Func`が追加されました。`funcList`は、エクスポートされるすべての関数を出現順に格納するリストです。インライン化可能な本体を持たない関数は`nil`エントリとして格納されます。
2.  **エクスポートロジックの変更 (`bexport.go`)**:
    *   関数シグネチャをエクスポートする際に、`inlineable`フラグに基づいて`p.int(index)`を書き出す代わりに、`p.funcList = append(p.funcList, f)`として、関数オブジェクト`f`を`funcList`に追加するようになりました。`f`はインライン化可能な関数であればその`*Func`ポインタ、そうでなければ`nil`です。これにより、個々の関数シグネチャにインライン化の有無を示す`int`値を埋め込む必要がなくなりました。
    *   インライン化可能な関数本体のセクションでは、`p.inlined`リストをイテレートする代わりに、`p.funcList`をイテレートするようになりました。`funcList`内の`nil`ではないエントリ（つまり、インライン化可能な本体を持つ関数）に対してのみ、その関数のインデックスと本体を書き出します。リストの終端は`-1`で示されます。
    *   これにより、インライン化可能な本体を持たない関数に対しては、エクスポートデータに余分な`int`値が書き込まれなくなります。
3.  **インポートロジックの変更 (`bimport.go`)**:
    *   `importer`構造体も同様に`inlined []*Node`が削除され、`funcList []*Node`が追加されました。
    *   関数シグネチャをインポートする際に、以前は`p.int()`でインライン化インデックスを読み取っていましたが、これが削除されました。代わりに、`p.funcList = append(p.funcList, n)`として、インポートされた関数ノード`n`を`funcList`に追加します。
    *   インライン化可能な関数本体のセクションでは、`-1`でリストの終端が示されるまで、関数インデックスと本体を読み取ります。読み取ったインデックス`i`に対応する`p.funcList[i]`が`nil`ではない場合（つまり、その関数がインライン化可能な本体を持つ場合）、その本体を読み込んで設定します。
    *   `src/go/internal/gcimporter/bimport.go`では、`p.int() // read and discard index of inlined function body`という行が削除され、インライン化インデックスの読み捨てが不要になったことを示しています。

この変更により、エクスポートデータはよりコンパクトになり、インライン化に関する情報はコンパイラ固有のセクションに集約されるため、エクスポートデータの構造がより論理的になりました。

## コアとなるコードの変更箇所

### `src/cmd/compile/internal/gc/bexport.go`

*   `exporter`構造体から`inlined []*Func`が削除され、`funcList []*Func`が追加されました。
*   `export`関数のインライン化関数本体を書き出す部分が変更されました。
    *   以前は`p.int(len(p.inlined))`で`inlined`リストの長さを書き出し、その後`p.inlined`をイテレートしていました。
    *   変更後は、`p.funcList`をイテレートし、`f != nil`の場合にのみ関数のインデックス`i`と本体`f.Inl`を書き出すようになりました。リストの終端は`p.tag(-1)`で示されます。
*   `obj`メソッドと`typ`メソッド（メソッドの定義をエクスポートする部分）において、`inlineable`な関数/メソッドの場合に`p.inlined`に`sym.Def.Func`や`mfn.Func`を追加し、そのインデックスを`p.int(index)`で書き出していたロジックが削除され、代わりに`p.funcList = append(p.funcList, f)`として`f`（インライン化可能な関数であれば`*Func`、そうでなければ`nil`）を追加するようになりました。

### `src/cmd/compile/internal/gc/bimport.go`

*   `importer`構造体から`inlined []*Node`が削除され、`funcList []*Node`が追加されました。
*   `Import`関数のインライン化関数本体を読み込む部分が変更されました。
    *   以前は`bcount := p.int()`で`inlined`リストの長さを読み込み、その後`p.inlined`をイテレートしていました。
    *   変更後は、`-1`が読み込まれるまでループし、関数インデックス`i`を読み取ります。`p.funcList[i]`が`nil`ではない場合、その関数本体を読み込んで設定します。
*   `obj`メソッドと`typ`メソッドにおいて、`inl := p.int()`でインライン化インデックスを読み取っていた部分が削除されました。代わりに、`p.funcList = append(p.funcList, n)`として、インポートされた関数ノード`n`を`funcList`に追加するようになりました。

### `src/go/internal/gcimporter/bimport.go`

*   `obj`メソッドと`typ`メソッドにおいて、`p.int() // read and discard index of inlined function body`という行が削除されました。これは、エクスポートデータからインライン化インデックスがなくなったため、読み捨てる必要がなくなったことを意味します。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラがパッケージのエクスポートデータをどのように構造化し、シリアライズ/デシリアライズするかという点にあります。

**エクスポート側 (`bexport.go`)**:

以前は、各関数がエクスポートされる際に、その関数がインライン化可能かどうかを示す`int`値（インデックスまたは`-1`）が、その関数のシグネチャ情報の一部として書き込まれていました。これは、インライン化可能な本体を持たない関数に対しても`-1`という値が書き込まれるため、データが冗長になる可能性がありました。

新しいアプローチでは、`exporter`は`funcList []*Func`というリストを保持します。このリストには、エクスポートされるすべての関数が、その宣言順に格納されます。インライン化可能な本体を持つ関数は実際の`*Func`ポインタとして、そうでない関数は`nil`として格納されます。

そして、エクスポートデータの「インライン化関数本体」セクションでは、`funcList`を走査し、`nil`ではないエントリ（つまり、インライン化可能な本体を持つ関数）が見つかった場合にのみ、その関数の`funcList`内でのインデックスと、その関数本体（`f.Inl`）を書き出します。このセクションの終わりは、特別なマーカー値（`-1`）で示されます。

これにより、インライン化可能な本体を持たない関数については、そのシグネチャ情報に余分な`int`値を含める必要がなくなり、またインライン化関数本体セクションでもその本体を書き出す必要がなくなります。結果として、エクスポートデータがより効率的になります。

**インポート側 (`bimport.go`)**:

インポート側も、エクスポート側の変更に合わせてロジックが変更されました。`importer`は`funcList []*Node`を保持し、エクスポートデータから関数シグネチャを読み込む際に、対応する`*Node`をこのリストに追加します。

インライン化関数本体セクションを読み込む際には、`-1`マーカーに到達するまで関数インデックスを読み取ります。読み取ったインデックス`i`を使用して`p.funcList[i]`にアクセスし、それが`nil`ではない場合（つまり、インライン化可能な本体を持つ関数である場合）、その本体をエクスポートデータから読み込み、対応する関数ノードに設定します。

この変更により、エクスポートデータからインライン化に関するコンパイラ固有の情報が分離され、プラットフォーム非依存のコアエクスポートデータはよりクリーンで汎用的なものになりました。これは、コンパイラのモジュール性向上と、将来的な拡張性にとって重要な改善です。

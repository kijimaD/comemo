# [インデックス 22846] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/internal/ld`) におけるシンボルテーブルの処理に関するものです。具体的には、定数文字列やバイトリテラルの実データに対応するシンボルをローカル化することで、生成されるバイナリの最適化を図っています。`symtab.go` ファイルは、リンカが実行可能ファイルを生成する際に、シンボルテーブルを構築し、シンボルの可視性やタイプを決定するロジックを含んでいます。

## 変更の背景

このコミットの背景には、Go言語のリンカが生成するバイナリの効率化と最適化があります。プログラムがコンパイルされると、コードやデータはシンボルとして表現され、リンカによって最終的な実行可能ファイルに配置されます。シンボルには「グローバル」と「ローカル」の2種類があり、グローバルシンボルは他のオブジェクトファイルやライブラリから参照される可能性があるのに対し、ローカルシンボルはそれが定義されたオブジェクトファイル内でのみ参照されます。

定数文字列やバイトリテラル（例: `var s = "hello"` や `var b = []byte{1, 2, 3}`) の実データは、通常、そのデータが使用される特定のコンパイル単位（オブジェクトファイル）内でのみ意味を持ちます。これらのデータ自体が外部から直接参照されることは稀であり、通常はポインタやオフセットを介してアクセスされます。

もしこれらのシンボルがグローバルとして扱われると、リンカはそれらを外部から参照される可能性があるものとして扱い、シンボルテーブルにその情報を保持する必要があります。これにより、以下のような非効率性が生じる可能性があります。

1.  **シンボルテーブルの肥大化**: 不要なグローバルシンボルが増えることで、実行可能ファイルのシンボルテーブルが大きくなり、ファイルサイズが増加します。
2.  **リンカの処理負荷**: リンカはグローバルシンボルの解決により多くの時間を費やす必要があり、リンク時間が長くなる可能性があります。
3.  **最適化の機会損失**: リンカや後続のツール（例: ストリッピングツール）が、これらのシンボルが内部的なものであることを認識できないため、より積極的な最適化（例: シンボルの削除や名前の難読化）を行う機会を失います。

このコミットは、定数文字列やバイトリテラルの実データに対応するシンボルを明示的にローカルとしてマークすることで、これらの非効率性を解消し、バイナリサイズを削減し、リンクプロセスを効率化することを目的としています。

## 前提知識の解説

### Go言語のコンパイルとリンクプロセス

Go言語のプログラムは、まずGoコンパイラ (`go tool compile`) によって各ソースファイルがオブジェクトファイル（`.o` ファイル）にコンパイルされます。その後、Goリンカ (`go tool link`、内部的には `cmd/internal/ld` パッケージが使用される）によって、これらのオブジェクトファイルと必要なランタイムライブラリが結合され、単一の実行可能バイナリが生成されます。

### シンボルとシンボルテーブル

プログラムのコンパイル過程において、変数、関数、型、定数などのプログラム要素は「シンボル」として表現されます。これらのシンボルとそのアドレスや属性（型、サイズ、可視性など）の対応関係を記録したものが「シンボルテーブル」です。シンボルテーブルは、デバッグ情報や動的リンクのためにバイナリ内に含まれることがあります。

*   **グローバルシンボル**: プログラム全体から参照可能なシンボル。他のオブジェクトファイルや共有ライブラリからアクセスされる可能性があります。
*   **ローカルシンボル**: そのシンボルが定義されたオブジェクトファイル内でのみ参照可能なシンボル。外部からは直接アクセスされません。リンカはローカルシンボルを外部に公開する必要がないため、最終的なバイナリから削除したり、名前を難読化したりするなどの最適化が可能です。

### `cmd/internal/ld` パッケージ

`cmd/internal/ld` はGo言語の標準リンカの実装です。このパッケージは、Goコンパイラによって生成されたオブジェクトファイルを読み込み、それらを結合して実行可能ファイルや共有ライブラリを生成する役割を担っています。シンボル解決、セクションの配置、リロケーションの適用など、リンクプロセスの中心的な機能を提供します。

### `SRODATA` (Read-Only Data Section)

`SRODATA` は、Goリンカが使用するシンボルタイプの一つで、読み取り専用データが格納されるセクションを指します。定数文字列やバイトリテラルの実データは、通常この `SRODATA` セクションに配置されます。

### `s.Reachable` と `s.Special`

リンカのシンボル処理において、`s.Reachable` はそのシンボルが最終的なバイナリに含まれるべきかどうかを示すフラグです。到達可能な（`Reachable`）シンボルのみがバイナリに含められます。
`s.Special` は、そのシンボルが特別な扱いを受けるべきかどうかを示すフラグです。例えば、リンカが内部的に生成する特定のシンボルや、ユーザーが明示的にエクスポートしないシンボルなどがこれに該当する場合があります。

### `..gostring.` および `..gobytes.` シンボル

Goコンパイラは、ソースコード内の文字列リテラル（例: `"hello"`）やバイトリテラル（例: `[]byte{1, 2, 3}`）を処理する際に、その実データを格納するための内部的なシンボルを生成します。これらのシンボルは、Goの内部的な命名規則に従い、通常 `..gostring.` や `..gobytes.` といったプレフィックスを含む名前を持ちます。これらはコンパイラが生成する一時的なシンボルであり、通常はユーザーコードから直接参照されることを意図していません。

## 技術的詳細

このコミットは、`src/cmd/internal/ld/symtab.go` ファイルの `symtab()` 関数内のシンボル処理ロジックを変更しています。`symtab()` 関数は、リンカがすべてのシンボルを走査し、その属性（タイプ、可視性など）を調整する主要な場所の一つです。

変更の核心は、以下の新しい条件を追加し、特定のシンボルをローカルとしてマークすることです。

```go
		if strings.Contains(s.Name, "..gostring.") || strings.Contains(s.Name, "..gobytes.") {
			s.Local = true
		}
```

このコードブロックは、リンカが処理するすべてのシンボル `s` をループで走査する中で実行されます。

1.  **`s.Reachable || s.Special` のチェック**:
    変更前は `!s.Reachable || s.Special != 0 || s.Type != SRODATA` という条件でループをスキップしていました。
    変更後は `!s.Reachable || s.Special != 0` となり、`s.Type != SRODATA` の条件が削除されました。これは、`..gostring.` や `..gobytes.` シンボルが `SRODATA` 以外のタイプである可能性も考慮し、より広範なシンボルに対してローカル化のチェックを適用できるようにするためです。

2.  **`strings.Contains(s.Name, "..gostring.") || strings.Contains(s.Name, "..gobytes.")`**:
    この行が追加された主要なロジックです。現在のシンボル `s` の名前 (`s.Name`) が文字列 `"..gostring."` または `"..gobytes."` を含んでいるかどうかをチェックします。
    前述の通り、Goコンパイラは文字列リテラルやバイトリテラルの実データに対して、このようなプレフィックスを持つ内部シンボルを生成します。

3.  **`s.Local = true`**:
    もしシンボル名が上記の条件に合致した場合、そのシンボル `s` の `Local` フラグが `true` に設定されます。これにより、リンカはこのシンボルを外部に公開する必要のないローカルシンボルとして扱い、最終的なバイナリから削除したり、シンボルテーブルでの扱いを簡素化したりするなどの最適化が可能になります。

4.  **`s.Type != SRODATA` の再導入**:
    `..gostring.` や `..gobytes.` シンボルのローカル化処理の後、再び `if s.Type != SRODATA { continue }` という条件が追加されています。これは、`..gostring.` や `..gobytes.` シンボル以外の `SRODATA` ではないシンボルについては、その後の `type.` プレフィックスを持つシンボルの処理（`STYPE` への変更と `Hide` フラグの設定）をスキップするためです。これにより、リンカの処理が意図した範囲に限定されます。

この変更により、Goのリンカは、内部的に生成される定数文字列やバイトリテラルのデータシンボルをより適切に管理し、バイナリの効率性を向上させることができます。

## コアとなるコードの解説

この変更は、`symtab.go` ファイル内の `symtab()` 関数にあります。この関数は、リンカがすべてのシンボルを反復処理し、その属性を調整する場所です。

1.  **変更前**:
    ```go
    	for s := Ctxt.Allsym; s != nil; s = s.Allsym {
    		if !s.Reachable || s.Special != 0 || s.Type != SRODATA {
    			continue
    		}
    		// ... 続く処理 ...
    	}
    ```
    この部分では、シンボル `s` が到達可能でない (`!s.Reachable`)、または特別なシンボルである (`s.Special != 0`)、または `SRODATA` タイプではない (`s.Type != SRODATA`) 場合、そのシンボルに対する以降の処理をスキップしていました。つまり、`SRODATA` タイプの到達可能な非特殊シンボルのみが、その後の `type.` プレフィックスを持つシンボルの処理対象となっていました。

2.  **変更後**:
    ```go
    	for s := Ctxt.Allsym; s != nil; s = s.Allsym {
    		if !s.Reachable || s.Special != 0 {
    			continue
    		}
    
    		if strings.Contains(s.Name, "..gostring.") || strings.Contains(s.Name, "..gobytes.") {
    			s.Local = true
    		}
    
    		if s.Type != SRODATA {
    			continue
    		}
    
    		if strings.HasPrefix(s.Name, "type.") && !DynlinkingGo() {
    			s.Type = STYPE
    			s.Hide = 1
    		}
    	}
    ```
    *   **`if !s.Reachable || s.Special != 0 { continue }`**:
        最初のスキップ条件から `s.Type != SRODATA` が削除されました。これにより、`SRODATA` 以外のシンボルであっても、到達可能で特殊でない限り、次のローカル化のチェックに進むことができるようになりました。これは、`..gostring.` や `..gobytes.` シンボルが常に `SRODATA` タイプであるとは限らない可能性を考慮しているか、あるいは、ローカル化の判断をより早い段階で行うための変更です。

    *   **`if strings.Contains(s.Name, "..gostring.") || strings.Contains(s.Name, "..gobytes.") { s.Local = true }`**:
        この行がこのコミットの主要な変更点です。現在のシンボル `s` の名前が `"..gostring."` または `"..gobytes."` という部分文字列を含んでいる場合、そのシンボルをローカル (`s.Local = true`) としてマークします。これは、Goコンパイラが生成する内部的な文字列リテラルやバイトリテラルのデータシンボルを識別し、それらを外部に公開する必要のないローカルシンボルとして扱うためのものです。これにより、リンカはこれらのシンボルをより効率的に処理し、最終的なバイナリのシンボルテーブルを最適化できます。

    *   **`if s.Type != SRODATA { continue }`**:
        ローカル化のチェックの後、再び `s.Type != SRODATA` のチェックが追加されました。これは、`..gostring.` や `..gobytes.` シンボルのローカル化処理が完了した後、その後の `if strings.HasPrefix(s.Name, "type.")` の処理（`type.` プレフィックスを持つシンボルを `STYPE` に変更し、`Hide` フラグを設定する処理）が、引き続き `SRODATA` タイプのシンボルにのみ適用されるようにするためです。これにより、リンカの処理の意図が明確に保たれています。

この変更により、Goのリンカは、内部的なデータシンボルをより適切にローカル化し、生成される実行可能ファイルのサイズとリンク時の効率を向上させることができます。

# [インデックス 25679] ファイルの概要

このコミットは、GoツールチェーンにおけるCgoと内部リンキングの挙動を改善し、特に`libgcc.a`の取り扱いを最適化することを目的としています。具体的には、リンカがCコンパイラのサポートライブラリである`libgcc.a`のコピーを内部リンキング時に使用するように変更し、`cmd/dist`ツールがこのライブラリをGoのインストールディレクトリ内にコピーするようにします。これにより、CコンパイラがインストールされていないシステムでもGoプログラムのビルドが可能になり、またCgoオブジェクトへの`libgcc`の不要なリンクを排除します。さらに、ELFオブジェクトにおける弱シンボルのリンカ処理が修正され、`freebsd-amd64`環境での特定の問題が解決されています。

## 変更の背景

このコミットは、主にGoのCgo機能と内部リンキングにおけるいくつかの課題を解決するために導入されました。

1.  **Cコンパイラ非依存性の向上**: 以前のGoのビルドシステムでは、Cgoを使用するGoプログラムをビルドする際に、システムにCコンパイラ（通常はGCC）がインストールされていることを前提としていました。これは、CgoがCコードをコンパイルし、その際に`libgcc.a`のようなGCCのサポートライブラリが必要となるためです。しかし、Goの設計思想の一つに、一度Goツールチェーンがビルドされれば、その後のGoプログラムのビルドにはCコンパイラが不要であるべきという考え方があります。このコミットは、`libgcc.a`をGoのインストールディレクトリ内にコピーすることで、このCコンパイラ非依存性を高めようとしています。

2.  **`libgcc.a`の重複リンク問題**: Cgoを使用するGoプログラムでは、Cコードがコンパイルされ、Goのランタイムとリンクされます。この際、`libgcc.a`がCgoオブジェクトに重複してリンクされる可能性がありました。これはビルド時間の増加や、場合によってはシンボル競合などの問題を引き起こす可能性があります。

3.  **弱シンボルのリンキング問題 (Issue #9510)**: 特定の環境、特に`freebsd-amd64`において、`libgcc.a`が`compilerrt_abort_impl`という弱シンボル（weak symbol）の定義を含んでいました。GoのリンカがELF入力オブジェクト内の弱シンボルを処理する際に、常に新しいシンボルを作成しようとする挙動があったため、既存のシンボルがあるにもかかわらず重複した定義が生成され、リンキングエラーや予期せぬ動作を引き起こしていました。Issue #9510はこの問題に起因するもので、このコミットはこのリンカの挙動を修正することで解決を図っています。

これらの課題に対処することで、Goのビルドシステムはより堅牢で、移植性が高く、効率的になることが期待されます。

## 前提知識の解説

### Goの内部リンキング (Internal Linking)

Goのリンカは、GoのオブジェクトファイルとCgoによって生成されたCのオブジェクトファイルを結合して実行可能ファイルを生成します。Goのリンカには「内部リンキング」と「外部リンキング」の二つのモードがあります。
*   **内部リンキング**: Goのリンカが、Cgoによって生成されたCのオブジェクトファイルも直接処理し、最終的な実行可能ファイルを生成するモードです。このモードでは、外部のCリンカ（例: `gcc`）を呼び出す必要がありません。Goのリンカは、Cのオブジェクトファイル内のシンボル解決も自身で行おうとします。
*   **外部リンキング**: GoのリンカがGoのオブジェクトファイルを生成した後、最終的なリンク処理を外部のCリンカに委ねるモードです。Cgoを使用する場合や、特定のシステムライブラリにリンクする必要がある場合によく使用されます。

このコミットは、内部リンキングのシナリオにおいて`libgcc.a`の取り扱いを改善することに焦点を当てています。

### Cgo

Cgoは、GoプログラムからCコードを呼び出すためのGoの機能です。Goのソースファイル内にCコードを直接記述したり、既存のCライブラリをGoから利用したりすることを可能にします。Cgoを使用すると、Goのビルドプロセス中にCコンパイラが呼び出され、CコードがコンパイルされてGoのオブジェクトファイルとリンクされます。

### `libgcc.a` (GCCのサポートライブラリ)

`libgcc.a`は、GCC（GNU Compiler Collection）が生成するC/C++コードが依存するランタイムサポートルーチンを含む静的ライブラリです。これには、特定のアーキテクチャ固有の操作（例: 64ビット整数演算を32ビットCPUでエミュレートする）、浮動小数点演算のヘルパー関数、例外処理のサポートなどが含まれます。CgoによってコンパイルされたCコードがこれらのルーチンを必要とする場合、`libgcc.a`へのリンクが必要になります。

### ELF (Executable and Linkable Format) と弱シンボル (Weak Symbols)

*   **ELF**: Unix系システムで広く使用されている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。シンボルテーブル、セクション、セグメントなどの情報を含みます。
*   **弱シンボル (Weak Symbols)**: リンカにおけるシンボルの種類の一つです。通常のシンボル（強シンボル、strong symbol）が複数定義されているとリンキングエラーになりますが、弱シンボルは同じ名前の強シンボルが存在する場合、強シンボルが優先されます。強シンボルが存在しない場合は、弱シンボルが使用されます。これにより、ライブラリがデフォルトの実装を提供しつつ、ユーザーが独自のより特化した実装でオーバーライドできるような柔軟なメカニズムを提供します。`compilerrt_abort_impl`のようなランタイムサポート関数は、システムやライブラリが独自のバージョンを提供できるように、弱シンボルとして定義されることがあります。

### `cmd/link`, `cmd/go`, `cmd/dist` の役割

*   **`cmd/link`**: Goのリンカです。Goのオブジェクトファイル、Cgoのオブジェクトファイル、および必要なライブラリを結合して実行可能ファイルを生成します。
*   **`cmd/go`**: Goコマンドラインツールの中核であり、Goプログラムのビルド、テスト、インストールなどを管理します。Cgoを使用する際には、Cコンパイラの呼び出しやリンカへの適切な引数渡しなどを調整します。
*   **`cmd/dist`**: Goのツールチェーン自体をビルドするためのツールです。Goのソースコードからコンパイラ、リンカ、その他のツールを構築し、インストールディレクトリに配置します。このコミットでは、`libgcc.a`をGoのインストールディレクトリにコピーする役割を担います。

## 技術的詳細

このコミットは、Goのビルドシステムにおける`libgcc.a`の取り扱いと弱シンボルのリンキング挙動を根本的に改善するために、`cmd/link`、`cmd/go`、`cmd/dist`の3つの主要なツールにわたる協調的な変更を導入しています。

### `cmd/dist`による`libgcc.a`のコピー

最も重要な変更点の一つは、`cmd/dist`ツールがGoのビルドプロセス中にCコンパイラの`libgcc.a`をGoのインストールディレクトリ（`GOROOT/pkg/libgcc`以下）にコピーするようになったことです。

*   **目的**: Goツールチェーンが一度ビルドされた後、Cgoを使用するGoプログラムをビルドする際に、システムにCコンパイラがインストールされている必要がないようにするためです。これにより、Goのビルド環境のポータビリティと自己完結性が向上します。
*   **実装**: `src/cmd/dist/build.go`に`copyLibgcc()`関数が追加されました。この関数は、`defaultcctarget`（ターゲットアーキテクチャ用のCコンパイラ）を`-print-libgcc-file-name`オプション付きで実行し、`libgcc.a`のパスを取得します。その後、このファイルを`GOROOT/pkg/libgcc/<goos>_<goarch>/libgcc`というパスにコピーします。`cmdbootstrap()`関数内で`copyLibgcc()`が呼び出されることで、Goツールチェーンの初期ビルド時にこの処理が実行されます。

### `cmd/go`からの`libgcc`リンクの削除

以前は、`cmd/go`ツールがCgoオブジェクトをリンクする際に、明示的に`libgcc`をリンクしようとしていました。このコミットでは、この挙動が変更されました。

*   **目的**: `libgcc.a`がGoのリンカによって内部的に処理されるようになるため、`cmd/go`がCgoオブジェクトに対して個別に`libgcc`をリンクする必要がなくなりました。これにより、重複リンクの回避とビルドプロセスの簡素化が図られます。
*   **実装**: `src/cmd/go/build.go`から、`libgcc`のファイル名を特定し、それをCgoオブジェクトにリンクするためのロジック（`libgcc`関数や`cgoLibGccFile`関連のコード）が削除されました。

### `cmd/link`における`libgcc.a`の内部処理と弱シンボル修正

Goのリンカ（`cmd/link`）は、内部リンキングモードにおいて、`libgcc.a`をよりインテリジェントに処理し、またELFオブジェクト内の弱シンボルの挙動を修正しました。

*   **`libgcc.a`の内部処理**: `src/cmd/link/internal/ld/lib.go`の`loadlib()`関数内で、内部リンキングモードの場合に、未定義のシンボルが存在すれば、`GOROOT/pkg/libgcc`にコピーされた`libgcc.a`を読み込むようになりました。この処理は、新しく追加された`hostArchive`関数によって行われます。`hostArchive`は、アーカイブファイル（`libgcc.a`のような静的ライブラリ）を解析し、未解決のシンボルを定義しているオブジェクトファイルのみをロードするスマートなメカニズムを提供します。これにより、必要な部分だけがリンクされ、不要なコードの取り込みが防がれます。
*   **弱シンボルのリンキング修正**: `src/cmd/link/internal/ld/ldelf.go`において、ELF入力オブジェクト内の弱シンボル（`ElfSymBindWeak`）の処理が修正されました。以前は、弱シンボルが見つかった場合に常に新しいシンボルを作成しようとしていましたが、この変更により、既存のシンボルが同じ名前で存在する場合は、その既存のシンボルを使用するようになりました。これは、`freebsd-amd64`環境で`libgcc`が`compilerrt_abort_impl`の弱定義を含んでいる問題（Issue #9510）を解決するために不可欠でした。既存のシンボルを再利用することで、重複定義によるリンキングエラーを回避します。

これらの変更により、GoのビルドシステムはCgoと`libgcc.a`をより効率的かつ正確に処理できるようになり、特にクロスコンパイルやCコンパイラが利用できない環境でのGoプログラムのビルドがよりスムーズになります。

## コアとなるコードの解説

### `src/cmd/dist/build.go` の `copyLibgcc()`

```go
// copyLibgcc copies the C compiler's libgcc into the pkg directory.
func copyLibgcc() {
	if !needCC() {
		return
	}
	var args []string
	switch goarch {
	case "386":
		args = []string{"-m32"}
	case "amd64", "amd64p32":
		args = []string{"-m64"}
	case "arm":
		args = []string{"-marm"}
	}
	args = append(args, "--print-libgcc-file-name")
	output, err := exec.Command(defaultcctarget, args...).Output()
	if err != nil {
		fatal("cannot find libgcc file name: %v", err)
	}
	libgcc := strings.TrimSpace(string(output))
	if len(libgcc) == 0 {
		return
	}
	in, err := os.Open(libgcc)
	if err != nil {
		if os.IsNotExist(err) {
			return
		}
		fatal("cannot open libgcc for copying: %v", err)
	}
	defer in.Close()
	outdir := filepath.Join(goroot, "pkg", "libgcc", goos+"_"+goarch)
	if err := os.MkdirAll(outdir, 0777); err != nil {
		fatal("cannot create libgcc.a directory: %v", err)
	}
	out, err := os.Create(filepath.Join(outdir, "libgcc"))
	if err != nil {
		fatal("cannot create libgcc.a for copying: %v", err)
	}
	if _, err := io.Copy(out, in); err != nil {
		fatal("error copying libgcc: %v", err)
	}
	if err := out.Close(); err != nil {
		fatal("error closing new libgcc: %v", err)
	}
}
```
この関数は、Goツールチェーンのビルド時に実行されます。
1.  `needCC()`でCコンパイラが必要かどうかを確認します。
2.  ターゲットアーキテクチャ（`goarch`）に応じて、Cコンパイラ（`defaultcctarget`）に`-m32`や`-m64`などの適切なフラグを追加します。
3.  Cコンパイラを`--print-libgcc-file-name`オプション付きで実行し、`libgcc.a`の絶対パスを取得します。
4.  取得したパスから`libgcc.a`を開き、`GOROOT/pkg/libgcc/<goos>_<goarch>/libgcc`という新しいディレクトリにコピーします。これにより、Goツールチェーンがインストールされた後、Cコンパイラがシステムに存在しなくても`libgcc.a`が利用可能になります。

### `src/cmd/go/build.go` からの `libgcc` 関連ロジックの削除

このコミットでは、`cmd/go`が`libgcc`のパスを動的に解決し、Cgoオブジェクトにリンクする責任を負う部分が削除されました。具体的には、`libgcc`関数や`cgoLibGccFile`などの変数が削除されています。これは、`cmd/dist`が`libgcc.a`をGoのインストールディレクトリにコピーし、`cmd/link`がそれを内部的に処理するようになったため、`cmd/go`がこの役割を果たす必要がなくなったためです。これにより、ビルドプロセスの責任分担が明確化され、簡素化されます。

### `src/cmd/link/internal/ld/ar.go` の `hostArchive()`

```go
// hostArchive reads an archive file holding host objects and links in
// required objects.  The general format is the same as a Go archive
// file, but it has an armap listing symbols and the objects that
// define them.  This is used for the compiler support library
// libgcc.a.
func hostArchive(name string) {
	f, err := obj.Bopenr(name)
	// ... (エラーハンドリング) ...
	defer obj.Bterm(f)

	// ... (アーカイブマジックナンバーのチェック) ...

	var arhdr ArHdr
	l := nextar(f, obj.Boffset(f), &arhdr)
	if l <= 0 {
		Exitf("%s missing armap", name)
	}

	var armap archiveMap
	if arhdr.name == "/" || arhdr.name == "/SYM64/" {
		armap = readArmap(name, f, arhdr)
	} else {
		Exitf("%s missing armap", name)
	}

	loaded := make(map[uint64]bool)
	any := true
	for any {
		var load []uint64
		for s := Ctxt.Allsym; s != nil; s = s.Allsym {
			for _, r := range s.R {
				if r.Sym != nil && r.Sym.Type&obj.SMASK == obj.SXREF {
					if off := armap[r.Sym.Name]; off != 0 && !loaded[off] {
						load = append(load, off)
						loaded[off] = true
					}
				}
			}
		}

		for _, off := range load {
			l := nextar(f, int64(off), &arhdr)
			if l <= 0 {
				Exitf("%s missing archive entry at offset %d", name, off)
			}
			pname := fmt.Sprintf("%s(%s)", name, arhdr.name)
			l = atolwhex(arhdr.size)

			h := ldobj(f, "libgcc", l, pname, name, ArchiveObj)
			obj.Bseek(f, h.off, 0)
			h.ld(f, h.pkg, h.length, h.pn)
		}

		any = len(load) > 0
	}
}
```
この関数は、`libgcc.a`のようなホストオブジェクトを含むアーカイブファイルを読み込み、Goのリンカのシンボル解決プロセスに統合します。
1.  アーカイブファイルを開き、そのシンボルマップ（`armap`）を読み込みます。`armap`は、シンボル名と、そのシンボルを定義するアーカイブメンバーのファイル内オフセットをマッピングします。
2.  Goのリンカが現在解決できていない未定義のシンボル（`obj.SXREF`）を走査します。
3.  未定義のシンボルが`armap`内に存在し、まだロードされていないアーカイブメンバーによって定義されている場合、そのメンバーのオフセットを`load`リストに追加します。
4.  `load`リストにある各アーカイブメンバーを`ldobj`関数を使ってロードし、その内容をリンカのシンボルテーブルに統合します。
5.  このプロセスを、未定義のシンボルがなくなるか、これ以上解決できるシンボルがなくなるまで繰り返します。これにより、`libgcc.a`全体をロードするのではなく、実際に必要な部分だけをオンデマンドでロードする効率的なリンキングが可能になります。

*   以前は、弱シンボルが見つかると常に`linknewsym(Ctxt, sym.name, 0)`を呼び出し、新しいシンボルを作成しようとしていました。
*   修正後は`Linklookup(Ctxt, sym.name, 0)`を呼び出すようになりました。これは、指定された名前のシンボルが既に存在するかどうかをリンカのシンボルテーブルで検索します。

## 変更の背景

このコミットは、主にGoのCgo機能と内部リンキングにおけるいくつかの課題を解決するために導入されました。

1.  **Cコンパイラ非依存性の向上**: 以前のGoのビルドシステムでは、Cgoを使用するGoプログラムをビルドする際に、システムにCコンパイラ（通常はGCC）がインストールされていることを前提としていました。これは、CgoがCコードをコンパイルし、その際に`libgcc.a`のようなGCCのサポートライブラリが必要となるためです。しかし、Goの設計思想の一つに、一度Goツールチェーンがビルドされれば、その後のGoプログラムのビルドにはCコンパイラが不要であるべきという考え方があります。このコミットは、`libgcc.a`をGoのインストールディレクトリ内にコピーすることで、このCコンパイラ非依存性を高めようとしています。

2.  **`libgcc.a`の重複リンク問題**: Cgoを使用するGoプログラムでは、Cコードがコンパイルされ、Goのランタイムとリンクされます。この際、`libgcc.a`がCgoオブジェクトに重複してリンクされる可能性がありました。これはビルド時間の増加や、場合によってはシンボル競合などの問題を引き起こす可能性があります。

3.  **弱シンボルのリンキング問題 (Issue #9510)**: 特定の環境、特に`freebsd-amd64`において、`libgcc.a`が`compilerrt_abort_impl`という弱シンボル（weak symbol）の定義を含んでいました。GoのリンカがELF入力オブジェクト内の弱シンボルを処理する際に、常に新しいシンボルを作成しようとする挙動があったため、既存のシンボルがあるにもかかわらず重複した定義が生成され、リンキングエラーや予期せぬ動作を引き起こしていました。Issue #9510はこの問題に起因するもので、このコミットはこのリンカの挙動を修正することで解決を図っています。

これらの課題に対処することで、Goのビルドシステムはより堅牢で、移植性が高く、効率的になることが期待されます。

## 前提知識の解説

### Goの内部リンキング (Internal Linking)

Goのリンカは、GoのオブジェクトファイルとCgoによって生成されたCのオブジェクトファイルを結合して実行可能ファイルを生成します。Goのリンカには「内部リンキング」と「外部リンキング」の二つのモードがあります。
*   **内部リンキング**: Goのリンカが、Cgoによって生成されたCのオブジェクトファイルも直接処理し、最終的な実行可能ファイルを生成するモードです。このモードでは、外部のCリンカ（例: `gcc`）を呼び出す必要がありません。Goのリンカは、Cのオブジェクトファイル内のシンボル解決も自身で行おうとします。
*   **外部リンキング**: GoのリンカがGoのオブジェクトファイルを生成した後、最終的なリンク処理を外部のCリンカに委ねるモードです。Cgoを使用する場合や、特定のシステムライブラリにリンクする必要がある場合によく使用されます。

このコミットは、内部リンキングのシナリオにおいて`libgcc.a`の取り扱いを改善することに焦点を当てています。

### Cgo

Cgoは、GoプログラムからCコードを呼び出すためのGoの機能です。Goのソースファイル内にCコードを直接記述したり、既存のCライブラリをGoから利用したりすることを可能にします。Cgoを使用すると、Goのビルドプロセス中にCコンパイラが呼び出され、CコードがコンパイルされてGoのオブジェクトファイルとリンクされます。

### `libgcc.a` (GCCのサポートライブラリ)

`libgcc.a`は、GCC（GNU Compiler Collection）が生成するC/C++コードが依存するランタイムサポートルーチンを含む静的ライブラリです。これには、特定のアーキテクチャ固有の操作（例: 64ビット整数演算を32ビットCPUでエミュレートする）、浮動小数点演算のヘルパー関数、例外処理のサポートなどが含まれます。CgoによってコンパイルされたCコードがこれらのルーチンを必要とする場合、`libgcc.a`へのリンクが必要になります。

### ELF (Executable and Linkable Format) と弱シンボル (Weak Symbols)

*   **ELF**: Unix系システムで広く使用されている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。シンボルテーブル、セクション、セグメントなどの情報を含みます。
*   **弱シンボル (Weak Symbols)**: リンカにおけるシンボルの種類の一つです。通常のシンボル（強シンボル、strong symbol）が複数定義されているとリンキングエラーになりますが、弱シンボルは同じ名前の強シンボルが存在する場合、強シンボルが優先されます。強シンボルが存在しない場合は、弱シンボルが使用されます。これにより、ライブラリがデフォルトの実装を提供しつつ、ユーザーが独自のより特化した実装でオーバーライドできるような柔軟なメカニズムを提供します。`compilerrt_abort_impl`のようなランタイムサポート関数は、システムやライブラリが独自のバージョンを提供できるように、弱シンボルとして定義されることがあります。

### `cmd/link`, `cmd/go`, `cmd/dist` の役割

*   **`cmd/link`**: Goのリンカです。Goのオブジェクトファイル、Cgoのオブジェクトファイル、および必要なライブラリを結合して実行可能ファイルを生成します。
*   **`cmd/go`**: Goコマンドラインツールの中核であり、Goプログラムのビルド、テスト、インストールなどを管理します。Cgoを使用する際には、Cコンパイラの呼び出しやリンカへの適切な引数渡しなどを調整します。
*   **`cmd/dist`**: Goのツールチェーン自体をビルドするためのツールです。Goのソースコードからコンパイラ、リンカ、その他のツールを構築し、インストールディレクトリに配置します。このコミットでは、`libgcc.a`をGoのインストールディレクトリにコピーする役割を担います。

## 技術的詳細

このコミットは、Goのビルドシステムにおける`libgcc.a`の取り扱いと弱シンボルのリンキング挙動を根本的に改善するために、`cmd/link`、`cmd/go`、`cmd/dist`の3つの主要なツールにわたる協調的な変更を導入しています。

### `cmd/dist`による`libgcc.a`のコピー

最も重要な変更点の一つは、`cmd/dist`ツールがGoのビルドプロセス中にCコンパイラの`libgcc.a`をGoのインストールディレクトリ（`GOROOT/pkg/libgcc`以下）にコピーするようになったことです。

*   **目的**: Goツールチェーンが一度ビルドされた後、Cgoを使用するGoプログラムをビルドする際に、システムにCコンパイラがインストールされている必要がないようにするためです。これにより、Goのビルド環境のポータビリティと自己完結性が向上します。
*   **実装**: `src/cmd/dist/build.go`に`copyLibgcc()`関数が追加されました。この関数は、`defaultcctarget`（ターゲットアーキテクチャ用のCコンパイラ）を`-print-libgcc-file-name`オプション付きで実行し、`libgcc.a`のパスを取得します。その後、このファイルを`GOROOT/pkg/libgcc/<goos>_<goarch>/libgcc`というパスにコピーします。`cmdbootstrap()`関数内で`copyLibgcc()`が呼び出されることで、Goツールチェーンの初期ビルド時にこの処理が実行されます。

### `cmd/go`からの`libgcc`リンクの削除

以前は、`cmd/go`ツールがCgoオブジェクトをリンクする際に、明示的に`libgcc`をリンクしようとしていました。このコミットでは、この挙動が変更されました。

*   **目的**: `libgcc.a`がGoのリンカによって内部的に処理されるようになるため、`cmd/go`がCgoオブジェクトに対して個別に`libgcc`をリンクする必要がなくなりました。これにより、重複リンクの回避とビルドプロセスの簡素化が図られます。
*   **実装**: `src/cmd/go/build.go`から、`libgcc`のファイル名を特定し、それをCgoオブジェクトにリンクするためのロジック（`libgcc`関数や`cgoLibGccFile`関連のコード）が削除されました。

### `cmd/link`における`libgcc.a`の内部処理と弱シンボル修正

Goのリンカ（`cmd/link`）は、内部リンキングモードにおいて、`libgcc.a`をよりインテリジェントに処理し、またELFオブジェクト内の弱シンボルの挙動を修正しました。

*   **`libgcc.a`の内部処理**: `src/cmd/link/internal/ld/lib.go`の`loadlib()`関数内で、内部リンキングモードの場合に、未定義のシンボルが存在すれば、`GOROOT/pkg/libgcc`にコピーされた`libgcc.a`を読み込むようになりました。この処理は、新しく追加された`hostArchive`関数によって行われます。`hostArchive`は、アーカイブファイル（`libgcc.a`のような静的ライブラリ）を解析し、未解決のシンボルを定義しているオブジェクトファイルのみをロードするスマートなメカニズムを提供します。これにより、必要な部分だけがリンクされ、不要なコードの取り込みが防がれます。
*   **弱シンボルのリンキング修正**: `src/cmd/link/internal/ld/ldelf.go`において、ELF入力オブジェクト内の弱シンボル（`ElfSymBindWeak`）の処理が修正されました。以前は、弱シンボルが見つかった場合に常に新しいシンボルを作成しようとしていましたが、この変更により、既存のシンボルが同じ名前で存在する場合は、その既存のシンボルを使用するようになりました。これは、`freebsd-amd64`環境で`libgcc`が`compilerrt_abort_impl`の弱定義を含んでいる問題（Issue #9510）を解決するために不可欠でした。既存のシンボルを再利用することで、重複定義によるリンキングエラーを回避します。

これらの変更により、GoのビルドシステムはCgoと`libgcc.a`をより効率的かつ正確に処理できるようになり、特にクロスコンパイルやCコンパイラが利用できない環境でのGoプログラムのビルドがよりスムーズになります。

### `src/cmd/dist/build.go` の `copyLibgcc()`

```go
// copyLibgcc copies the C compiler's libgcc into the pkg directory.
func copyLibgcc() {
	if !needCC() {
		return
	}
	var args []string
	switch goarch {
	case "386":
		args = []string{"-m32"}
	case "amd64", "amd64p32":
		args = []string{"-m64"}
	case "arm":
		args = []string{"-marm"}
	}
	args = append(args, "--print-libgcc-file-name")
	output, err := exec.Command(defaultcctarget, args...).Output()
	if err != nil {
		fatal("cannot find libgcc file name: %v", err)
	}
	libgcc := strings.TrimSpace(string(output))
	if len(libgcc) == 0 {
		return
	}
	in, err := os.Open(libgcc)
	if err != nil {
		if os.IsNotExist(err) {
			return
		}
		fatal("cannot open libgcc for copying: %v", err)
	}
	defer in.Close()
	outdir := filepath.Join(goroot, "pkg", "libgcc", goos+"_"+goarch)
	if err := os.MkdirAll(outdir, 0777); err != nil {
		fatal("cannot create libgcc.a directory: %v", err)
	}
	out, err := os.Create(filepath.Join(outdir, "libgcc"))
	if err != nil {
		fatal("cannot create libgcc.a for copying: %v", err)
	}
	if _, err := io.Copy(out, in); err != nil {
		fatal("error copying libgcc: %v", err)
	}
	if err := out.Close(); err != nil {
		fatal("error closing new libgcc: %v", err)
	}
}
```
この関数は、Goツールチェーンのビルド時に実行されます。
1.  `needCC()`でCコンパイラが必要かどうかを確認します。
2.  ターゲットアーキテクチャ（`goarch`）に応じて、Cコンパイラ（`defaultcctarget`）に`-m32`や`-m64`などの適切なフラグを追加します。
3.  Cコンパイラを`--print-libgcc-file-name`オプション付きで実行し、`libgcc.a`の絶対パスを取得します。
4.  取得したパスから`libgcc.a`を開き、`GOROOT/pkg/libgcc/<goos>_<goarch>/libgcc`という新しいディレクトリにコピーします。これにより、Goツールチェーンがインストールされた後、Cコンパイラがシステムに存在しなくても`libgcc.a`が利用可能になります。

### `src/cmd/go/build.go` からの `libgcc` 関連ロジックの削除

このコミットでは、`cmd/go`が`libgcc`のパスを動的に解決し、Cgoオブジェクトにリンクする責任を負う部分が削除されました。具体的には、`libgcc`関数や`cgoLibGccFile`などの変数が削除されています。これは、`cmd/dist`が`libgcc.a`をGoのインストールディレクトリにコピーし、`cmd/link`がそれを内部的に処理するようになったため、`cmd/go`がこの役割を果たす必要がなくなったためです。これにより、ビルドプロセスの責任分担が明確化され、簡素化されます。

### `src/cmd/link/internal/ld/ar.go` の `hostArchive()`

```go
// hostArchive reads an archive file holding host objects and links in
// required objects.  The general format is the same as a Go archive
// file, but it has an armap listing symbols and the objects that
// define them.  This is used for the compiler support library
// libgcc.a.
func hostArchive(name string) {
	f, err := obj.Bopenr(name)
	// ... (エラーハンドリング) ...
	defer obj.Bterm(f)

	// ... (アーカイブマジックナンバーのチェック) ...

	var arhdr ArHdr
	l := nextar(f, obj.Boffset(f), &arhdr)
	if l <= 0 {
		Exitf("%s missing armap", name)
	}

	var armap archiveMap
	if arhdr.name == "/" || arhdr.name == "/SYM64/" {
		armap = readArmap(name, f, arhdr)
	} else {
		Exitf("%s missing armap", name)
	}

	loaded := make(map[uint64]bool)
	any := true
	for any {
		var load []uint64
		for s := Ctxt.Allsym; s != nil; s = s.Allsym {
			for _, r := range s.R {
				if r.Sym != nil && r.Sym.Type&obj.SMASK == obj.SXREF {
					if off := armap[r.Sym.Name]; off != 0 && !loaded[off] {
						load = append(load, off)
						loaded[off] = true
					}
				}
			}
		}

		for _, off := range load {
			l := nextar(f, int64(off), &arhdr)
			if l <= 0 {
				Exitf("%s missing archive entry at offset %d", name, off)
			}
			pname := fmt.Sprintf("%s(%s)", name, arhdr.name)
			l = atolwhex(arhdr.size)

			h := ldobj(f, "libgcc", l, pname, name, ArchiveObj)
			obj.Bseek(f, h.off, 0)
			h.ld(f, h.pkg, h.length, h.pn)
		}

		any = len(load) > 0
	}
}
```
この関数は、`libgcc.a`のようなホストオブジェクトを含むアーカイブファイルを読み込み、Goのリンカのシンボル解決プロセスに統合します。
1.  アーカイブファイルを開き、そのシンボルマップ（`armap`）を読み込みます。`armap`は、シンボル名と、そのシンボルを定義するアーカイブメンバーのファイル内オフセットをマッピングします。
2.  Goのリンカが現在解決できていない未定義のシンボル（`obj.SXREF`）を走査します。
3.  未定義のシンボルが`armap`内に存在し、まだロードされていないアーカイブメンバーによって定義されている場合、そのメンバーのオフセットを`load`リストに追加します。
4.  `load`リストにある各アーカイブメンバーを`ldobj`関数を使ってロードし、その内容をリンカのシンボルテーブルに統合します。
5.  このプロセスを、未定義のシンボルがなくなるか、これ以上解決できるシンボルがなくなるまで繰り返します。これにより、`libgcc.a`全体をロードするのではなく、実際に必要な部分だけをオンデマンドでロードする効率的なリンキングが可能になります。

### `src/cmd/link/internal/ld/ldelf.go` の弱シンボル処理修正

```go
		case ElfSymBindWeak:
			if needSym != 0 {
				s = Linklookup(Ctxt, sym.name, 0) // 変更点: linknewsym から Linklookup へ
				if sym.other == 2 {
					s.Type |= obj.SHIDDEN
				}
```
この変更は、ELFオブジェクトファイル内の弱シンボル（`ElfSymBindWeak`）の処理方法を修正します。
*   以前は、弱シンボルが見つかると常に`linknewsym(Ctxt, sym.name, 0)`を呼び出し、新しいシンボルを作成しようとしていました。
*   修正後は`Linklookup(Ctxt, sym.name, 0)`を呼び出すようになりました。これは、指定された名前のシンボルが既に存在するかどうかをリンカのシンボルテーブルで検索します。
*   もし既存のシンボルがあればそれを使用し、なければ新しいシンボルを作成します。この挙動により、`freebsd-amd64`における`compilerrt_abort_impl`のような弱シンボルの重複定義問題が解決されます。

### `src/cmd/link/internal/ld/lib.go` の `loadlib()` と `ldobj()`

```go
func loadlib() {
	// ...
	// In internal link mode, read the host object files.
	if Linkmode == LinkInternal {
		hostobjs()

		// If we have any undefined symbols in external
		// objects, try to read them from our copy of the C
		// compiler support library, libgcc.a.
		any := false
		for s := Ctxt.Allsym; s != nil; s = s.Allsym {
			for _, r := range s.R {
				if r.Sym != nil && r.Sym.Type&obj.SMASK == obj.SXREF {
					any = true
					break
				}
			}
		}
		if any {
			hostArchive(fmt.Sprintf("%s/pkg/libgcc/%s_%s/libgcc", goroot, goos, goarch))
		}
	} else {
		hostlinksetup()
	}
	// ...
}

// ldobj loads an input object.  If it is a host object (an object
// compiled by a non-Go compiler) it returns the Hostobj pointer.  If
// it is a Go object, it returns nil.
func ldobj(f *obj.Biobuf, pkg string, length int64, pn string, file string, whence int) *Hostobj {
	// ... (オブジェクトファイルのヘッダを読み込み、種類を判別) ...
	if magic == 0x7f454c46 { // \x7F E L F
		return ldhostobj(ldelf, f, pkg, length, pn, file) // ホストオブジェクトの場合、ldhostobjを呼び出し、その結果を返す
	}
	// ... (Mach-O, PEなどのホストオブジェクトの判別と処理) ...
	// Goオブジェクトの場合の処理
	// ...
	return nil // Goオブジェクトの場合はnilを返す
}
```
*   **`loadlib()`**: Goのリンカがライブラリをロードする主要な関数です。内部リンキングモード（`Linkmode == LinkInternal`）の場合、まず`hostobjs()`を呼び出して通常のホストオブジェクトを処理します。その後、現在のシンボルテーブルに未定義の外部シンボル（`obj.SXREF`）が残っているかどうかを確認します。もし未定義シンボルがあれば、`GOROOT/pkg/libgcc`にコピーされた`libgcc.a`を`hostArchive`関数を使って読み込み、これらのシンボルを解決しようと試みます。
*   **`ldobj()`**: オブジェクトファイルをロードし、その種類（Goオブジェクトかホストオブジェクトか）を判別する関数です。このコミットでは、`ldobj`がホストオブジェクトをロードした場合に`*Hostobj`ポインタを返すように変更されました。これにより、`hostArchive`関数が`ldobj`を呼び出して`libgcc.a`内の個々のオブジェクトファイルをロードする際に、そのオブジェクトがホストオブジェクトであることを認識し、適切に処理できるようになります。

これらの変更は、GoのビルドシステムがCgoと外部Cライブラリ（特に`libgcc.a`）をよりシームレスかつ効率的に統合するための重要なステップです。

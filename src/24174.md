## 元コミット内容

このコミットは、ハッシュ `3b411bf1a1bb08d6868083981cecba8088dc7aea` のコミットをリバートするものです。元コミットのタイトルは「cmd/compile: define func value symbols at declaration」であり、その内容はGoコンパイラにおいて、関数値（関数リテラルやクロージャなど）のシンボルを、その宣言時に定義するように変更することでした。

通常、コンパイラはプログラムの各要素（変数、関数など）に対して内部的なシンボルを生成し、これらを管理します。このシンボルは、コンパイルの様々な段階（型チェック、コード生成、リンクなど）で参照されます。元コミットは、このシンボル定義のタイミングを「宣言時」に前倒しすることで、コンパイラの内部処理を最適化したり、特定のバグを修正したりすることを意図していたと考えられます。

## 変更の背景

元コミット `3b411bf1a1bb08d6868083981cecba8088dc7aea` は、関数値シンボルの定義タイミングを変更することで、何らかの改善を目指していました。しかし、その変更が意図しない副作用を引き起こした可能性が高いです。リバートが行われる主な理由は以下のいずれか、または複合的なものです。

1.  **バグの導入:** 変更によって、以前は存在しなかったコンパイラのバグ（例: 誤ったコード生成、クラッシュ、不正なシンボル解決）が導入された。
2.  **パフォーマンスの低下:** 変更がコンパイル時間の増加や生成されるバイナリの効率低下を招いた。
3.  **既存のコードベースとの非互換性:** 変更が、Go言語の既存のセマンティクスや他のコンパイラ部分との整合性を損なった。
4.  **複雑性の増加:** 変更がコンパイラのコードベースを不必要に複雑にし、メンテナンス性を低下させた。

このリバートは、元の変更がもたらした問題が、そのメリットを上回ると判断されたため、安定性と正確性を優先して以前の動作に戻すことを決定した結果と考えられます。

## 前提知識の解説

このコミットの変更を理解するためには、Goコンパイラの内部構造と、いくつかの基本的な概念を理解しておく必要があります。

*   **Goコンパイラ (`cmd/compile`):** Go言語の公式コンパイラであり、Goソースコードを機械語に変換する役割を担います。コンパイルプロセスは、字句解析、構文解析、型チェック、中間表現生成、最適化、コード生成など、複数の段階に分かれています。
*   **シンボル (Symbol):** プログラム内の識別子（変数名、関数名、型名など）に対応するコンパイラ内部のデータ構造です。シンボルは、その識別子の型、スコープ、メモリ上の位置などの情報を含み、コンパイラがプログラムの意味を理解し、正しくコードを生成するために不可欠です。
*   **関数値 (Function Value):** Go言語では、関数は第一級オブジェクト（first-class citizen）です。これは、関数を変数に代入したり、他の関数の引数として渡したり、戻り値として返したりできることを意味します。関数リテラル（`func(...) { ... }`）やクロージャも関数値の一種です。
*   **クロージャ (Closure):** 周囲の環境（定義されたスコープ）にある変数を「キャプチャ」して参照できる関数リテラルです。クロージャは、その定義されたスコープが終了した後でも、キャプチャした変数にアクセスできます。
*   **抽象構文木 (AST: Abstract Syntax Tree):** ソースコードの構文構造を木構造で表現したものです。コンパイラの構文解析フェーズで生成され、その後の型チェックやコード生成の基盤となります。
*   **`*Node`:** Goコンパイラの内部でASTのノードを表す型です。
*   **`*Sym` (Symbol):** コンパイラ内部でシンボルを表す型です。`Node`と`Sym`は密接に関連しており、ASTの各ノードは対応するシンボルを持つことがあります。
*   **`Pkglookup(name, pkg)`:** 指定されたパッケージ内で名前（`name`）に対応するシンボルを検索または作成する関数。
*   **`newfuncname(sym)`:** 新しい関数名を生成し、それに対応する`Node`を返す関数。
*   **`makefuncsym(sym)`:** 関数シンボルを生成または処理するための関数。元のコミットで導入され、このリバートで削除されています。
*   **`funcsym(sym)`:** 関数シンボルを処理するための関数。`makefuncsym`と関連して使用されていました。
*   **`dclcontext`:** 宣言が行われている現在のコンテキスト（例: グローバルスコープ、関数スコープ、構造体フィールドなど）を示す変数。
*   **`PAUTO`:** `dclcontext`の値の一つで、自動変数（スタックに割り当てられるローカル変数）の宣言コンテキストを示します。

## 技術的詳細

このリバートコミットは、主に`src/cmd/compile/internal/gc/closure.go`と`src/cmd/compile/internal/gc/dcl.go`の2つのファイルに影響を与えています。変更の核心は、関数値のシンボルを定義するタイミングと、そのためのヘルパー関数`makefuncsym`の扱いに関するものです。

**`src/cmd/compile/internal/gc/closure.go` の変更:**

*   `makeclosure` 関数内で、クロージャの関数シンボルを生成する際に呼び出されていた `makefuncsym(xfunc.Func.Nname.Sym)` の行が削除されています。
    *   `makeclosure` は、Goのクロージャ（関数リテラル）がコンパイルされる際に呼び出される関数です。
    *   `xfunc.Func.Nname.Sym` は、クロージャに対応するシンボルを表します。
    *   この変更により、クロージャのシンボル定義が、`makeclosure`の処理フローのこの時点では行われなくなり、以前の（リバート前の）メカニズムに依存するようになります。

**`src/cmd/compile/internal/gc/dcl.go` の変更:**

*   `funchdr` 関数内で、`importpkg == nil && n.Func.Nname != nil` の条件の下で呼び出されていた `makefuncsym(n.Func.Nname.Sym)` のブロックが削除されています。
    *   `funchdr` は、関数のヘッダー（宣言部分）を処理する際に呼び出される関数です。
    *   このブロックは、パッケージ外からのインポートではない通常の関数宣言において、その関数シンボルを宣言時に定義しようとしていました。この削除により、このタイミングでのシンボル定義は行われなくなります。
*   `funcsym` 関数と `makefuncsym` 関数の定義が変更されています。
    *   元のコミットでは、`funcsym` はシンボルを検索し、`makefuncsym` が実際にシンボルを`newfuncname`で作成し、`funcsyms`リストに追加する役割を担っていました。
    *   このリバートでは、`makefuncsym` 関数自体が完全に削除されています。
    *   `funcsym` 関数内に、`s1.Def == nil` の場合に `newfuncname` を呼び出してシンボルを定義し、`funcsyms` リストに追加するロジックが復元されています。これは、`makefuncsym` が導入される前の`funcsym`の動作に戻すものです。

要するに、このリバートは、関数値のシンボルを「宣言時」に積極的に定義しようとした試みを撤回し、シンボルが「必要になった時」または「特定のコンパイルフェーズ」で定義されるという、より遅延的な（または異なるタイミングの）アプローチに戻しています。これは、宣言時にシンボルを定義することが、コンパイラの他の部分との相互作用において問題を引き起こしたためと考えられます。

## コアとなるコードの解説

このリバートコミットの主要な変更点は、`makefuncsym` 関数の削除と、それに伴うシンボル定義ロジックの巻き戻しです。

1.  **`src/cmd/compile/internal/gc/closure.go` の変更:**
    *   `- makefuncsym(xfunc.Func.Nname.Sym)`: `makeclosure` 関数内で、クロージャのシンボルに対して `makefuncsym` を呼び出す行が削除されました。これは、クロージャのシンボルが宣言時に強制的に定義されることを防ぎます。以前の動作では、シンボルは別の場所またはタイミングで処理されていたと考えられます。この変更により、クロージャのコンパイルパスが、`makefuncsym` が導入される前の状態に戻ります。

2.  **`src/cmd/compile/internal/gc/dcl.go` の変更:**
    *   `- if importpkg == nil && n.Func.Nname != nil { makefuncsym(n.Func.Nname.Sym) }`: `funchdr` 関数内のこのブロックが削除されました。このブロックは、通常の関数宣言（インポートされた関数ではない）に対して、そのシンボルを宣言時に `makefuncsym` を使って定義しようとしていました。この削除により、関数ヘッダーの処理時にシンボルが強制的に定義されることはなくなります。
    *   `funcsym` 関数の変更:
        *   `- return s1` の行が削除され、`func makefuncsym(s *Sym) { ... }` 関数全体が削除されました。
        *   `+ if s1.Def == nil { s1.Def = newfuncname(s1); s1.Def.Func.Shortname = newname(s); funcsyms = list(funcsyms, s1.Def) }` のブロックが `funcsym` 関数内に復元されました。
        *   この変更は、`makefuncsym` が行っていたシンボル定義のロジックを、`funcsym` 関数自体に統合し直すものです。具体的には、`s1.Def`（シンボルの定義ノード）がまだ存在しない場合にのみ、`newfuncname` を使って新しい関数名ノードを作成し、それをシンボルの定義として設定し、`funcsyms` リストに追加します。これにより、シンボルは `funcsym` が呼び出された際に、必要に応じて（まだ定義されていない場合のみ）定義されるようになります。

これらの変更は、Goコンパイラが関数値のシンボルをいつ、どのように定義するかという内部的なメカニズムを、元の（リバート前の）安定した状態に戻すことを目的としています。元のコミットが導入した「宣言時にシンボルを定義する」というアプローチが、何らかの理由で問題を引き起こしたため、このリバートによってその問題が解消されることが期待されます。

## 変更の背景

この変更の背景には、Goコンパイラの最適化フェーズ、特にSSA（Static Single Assignment）形式における定数畳み込みの改善があります。コンパイラは、プログラムの実行前に可能な限り多くの計算を完了させることで、実行時のオーバーヘッドを削減しようとします。ビットシフト演算は、特に低レベルの操作やパフォーマンスが重要なコードで頻繁に使用されます。

以前のコンパイラでは、`((x << c1) >> c2) << c3` や `((x >> c1) << c2) >> c3` のような特定のパターンを持つビットシフトの連鎖を効率的に最適化できていませんでした。これらのパターンは、中間的なシフト操作が実質的に無効化されたり、より単純な単一のシフト操作にまとめることができる場合があります。例えば、`x << 5 >> 2 << 2` のような式は、特定の条件下で `x << 5` と同等になる可能性があります。

Issue #14825（コミットメッセージに記載されているが、詳細な内容は不明）は、おそらくこのような冗長なシフト操作が最適化されずに残ってしまうケースを指摘していたと考えられます。このコミットは、これらの特定のパターンを認識し、より効率的な単一のシフト操作に変換することで、コンパイラの最適化能力を向上させることを目的としています。これにより、生成されるバイナリのサイズが小さくなり、実行速度が向上する可能性があります。

## 前提知識の解説

### 1. GoコンパイラとSSA (Static Single Assignment)

Goコンパイラは、ソースコードを機械語に変換する過程で、様々な最適化を行います。その最適化フェーズの一つに、中間表現としてSSA形式を使用する段階があります。

*   **SSA形式**: プログラム中の各変数が一度だけ代入されるようにする中間表現です。これにより、データフロー解析や最適化が容易になります。SSA形式では、各操作が「値（Value）」として表現され、これらの値がグラフ構造を形成します。
*   **SSAバックエンド**: GoコンパイラのSSAバックエンドは、SSA形式のプログラムグラフに対して、レジスタ割り当て、命令スケジューリング、様々な最適化（定数畳み込み、デッドコード削除など）を行います。

### 2. 定数畳み込み (Constant Folding)

定数畳み込みは、コンパイル時最適化の一種で、コンパイル時に値が既知である式を、その計算結果の定数に置き換えるプロセスです。例えば、`2 + 3` という式があれば、コンパイラはこれを `5` に置き換えます。これにより、実行時に加算操作を行う必要がなくなり、プログラムの実行速度が向上します。

このコミットでは、ビットシフト操作の連鎖が定数畳み込みの対象となっています。シフト量が定数である場合、コンパイラはこれらのシフト操作を組み合わせて、最終的なシフト量を計算し、単一のシフト操作に変換しようとします。

### 3. ビットシフト演算

*   **左シフト (`<<`)**: オペランドのビットを左に指定された回数だけ移動させます。右側には0が埋められます。`x << n` は `x * 2^n` と同等です（オーバーフローを無視すれば）。
*   **右シフト (`>>`)**: オペランドのビットを右に指定された回数だけ移動させます。符号なし整数 (`uint`) の場合、左側には0が埋められます（論理右シフト）。符号付き整数 (`int`) の場合、左側には符号ビットが埋められるか（算術右シフト）、0が埋められるか（論理右シフト）は言語や実装に依存しますが、Goの符号付き右シフトは算術右シフトです。このコミットでは `RshUx` (Unsigned Right Shift) が使われているため、符号なし右シフトが対象です。

### 4. リライトルール (Rewrite Rules)

GoコンパイラのSSAバックエンドでは、プログラムグラフのパターンを認識し、より効率的なパターンに変換するための「リライトルール」が定義されています。これらのルールは、`generic.rules` のようなファイルに記述され、`rewritegeneric.go` のようなファイルで実際のコードに変換されます。リライトルールは、特定のオペレーションの組み合わせ（例: `(Add (Const x) (Const y))`）を、より単純なオペレーション（例: `(Const (x+y))`）に変換するのに役立ちます。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドに新しいリライトルールを追加し、既存のリライト関数を更新することで、特定のビットシフト操作の連鎖を最適化します。

具体的には、以下の2つのパターンを対象としています。

1.  **`((x << c1) >> c2) << c3` の形式**:
    *   これは、左シフト、符号なし右シフト、左シフトの順に適用されるパターンです。
    *   `c1`, `c2`, `c3` は定数のシフト量です。
    *   このパターンは、`c1 >= c2` かつ `c3 >= c2` という条件が満たされる場合に、`x << (c1 - c2 + c3)` という単一の左シフト操作に簡略化できます。
    *   例: `((x << 5) >> 2) << 2` の場合、`c1=5, c2=2, c3=2`。条件 `5 >= 2 && 2 >= 2` は真。結果は `x << (5 - 2 + 2)` = `x << 5` となります。

2.  **`((x >> c1) << c2) >> c3` の形式**:
    *   これは、符号なし右シフト、左シフト、符号なし右シフトの順に適用されるパターンです。
    *   `c1`, `c2`, `c3` は定数のシフト量です。
    *   このパターンは、`c1 >= c2` かつ `c3 >= c2` という条件が満たされる場合に、`x >> (c1 - c2 + c3)` という単一の符号なし右シフト操作に簡略化できます。
    *   例: `((x >> 5) << 2) >> 2` の場合、`c1=5, c2=2, c3=2`。条件 `5 >= 2 && 2 >= 2` は真。結果は `x >> (5 - 2 + 3)` = `x >> 5` となります。

これらの最適化は、8ビット、16ビット、32ビット、64ビットの符号なし整数型 (`uint8`, `uint16`, `uint32`, `uint64`) に対して適用されます。

### 最適化のメカニズム

GoコンパイラのSSAバックエンドは、プログラムをSSA形式のオペレーショングラフとして表現します。このグラフに対して、`generic.rules` に記述されたパターンマッチングとリライトが適用されます。

1.  **パターンマッチング**: コンパイラは、SSAグラフ内で `(Lsh64x64 (Rsh64Ux64 (Lsh64x64 x (Const64 [c1])) (Const64 [c2])) (Const64 [c3]))` のような特定のオペレーションの組み合わせを検出します。
2.  **条件チェック**: パターンがマッチした場合、`c1 >= c2 && c3 >= c2` のような追加の条件がチェックされます。この条件は、中間シフトが元の値を完全に復元できるか、または少なくとも一部が復元され、最終的なシフト量が正しく計算できることを保証するために重要です。
3.  **リライト**: 条件が満たされれば、元の複雑なオペレーションの連鎖は、`Lsh64x64 x (Const64 [c1-c2+c3])` のような単一のより単純なオペレーションに置き換えられます。

このプロセスにより、コンパイラは実行時に複数のシフト命令を発行する代わりに、単一のシフト命令を発行できるようになり、CPUサイクルとコードサイズを節約します。

### `src/cmd/compile/internal/ssa/gen/generic.rules` の変更

追加されたルールは以下の形式です。

```
// ((x >> c1) << c2) >> c3 
(Rsh64Ux64 (Lsh64x64 (Rsh64Ux64 x (Const64 [c1])) (Const64 [c2])) (Const64 [c3])) && c1 >= c2 && c3 >= c2 ->  (Rsh64Ux64 x (Const64 <config.fe.TypeUInt64()> [c1-c2+c3]))

// ((x << c1) >> c2) << c3
(Lsh64x64 (Rsh64Ux64 (Lsh64x64 x (Const64 [c1])) (Const64 [c2])) (Const64 [c3])) && c1 >= c2 && c3 >= c2 ->  (Lsh64x64 x (Const64 <config.fe.TypeUInt64()> [c1-c2+c3]))
```

*   `Rsh64Ux64`: 64ビット符号なし右シフト操作。
*   `Lsh64x64`: 64ビット左シフト操作。
*   `x`: シフトされる元の値。
*   `Const64 [c1]`, `Const64 [c2]`, `Const64 [c3]`: 定数のシフト量。
*   `&& c1 >= c2 && c3 >= c2`: リライトが適用されるための条件。この条件は、中間的なシフト操作が元のビットパターンを破壊しない、または最終的な結果に影響を与えないことを保証します。例えば、`x >> c1 << c2` の場合、`c1 >= c2` であれば、`c1 - c2` だけ右にシフトした後に左にシフトしても、元の `c1` ビットの損失は回復せず、結果として `x >> (c1 - c2)` となります。さらに `>> c3` が続くため、最終的なシフト量は `c1 - c2 + c3` となります。
*   `->`: リライトの矢印。左側のパターンがマッチし、条件が満たされた場合、右側のパターンに置き換えられます。
*   `(Rsh64Ux64 x (Const64 <config.fe.TypeUInt64()> [c1-c2+c3]))`: 簡略化された単一のシフト操作。

これらのルールは、`go generate` コマンドによって `rewritegeneric.go` 内のGoコードに変換されます。

### `src/cmd/compile/internal/ssa/rewritegeneric.go` の変更

`rewritegeneric.go` には、各SSAオペレーションに対応するリライト関数があります。例えば、`rewriteValuegeneric_OpLsh64x64` 関数内に、上記ルールに対応するGoコードが追加されています。

```go
// match: (Lsh64x64 (Rsh64Ux64 (Lsh64x64 x (Const64 [c1])) (Const64 [c2])) (Const64 [c3]))
// cond: c1 >= c2 && c3 >= c2
// result: (Lsh64x64 x (Const64 <config.fe.TypeUInt64()> [c1-c2+c3]))
for {
    if v.Args[0].Op != OpRsh64Ux64 {
        break
    }
    if v.Args[0].Args[0].Op != OpLsh64x64 {
        break
    }
    x := v.Args[0].Args[0].Args[0]
    if v.Args[0].Args[0].Args[1].Op != OpConst64 {
        break
    }
    c1 := v.Args[0].Args[0].Args[1].AuxInt
    if v.Args[0].Args[1].Op != OpConst64 {
        break
    }
    c2 := v.Args[0].Args[1].AuxInt
    if v.Args[1].Op != OpConst64 {
        break
    }
    c3 := v.Args[1].AuxInt
    if !(c1 >= c2 && c3 >= c2) {
        break
    }
    v.reset(OpLsh64x64) // オペレーションをLsh64x64にリセット
    v.AddArg(x)         // 元の値xを追加
    v0 := b.NewValue0(v.Line, OpConst64, config.fe.TypeUInt64()) // 新しい定数シフト量を作成
    v0.AuxInt = c1 - c2 + c3 // シフト量を計算
    v.AddArg(v0)        // 新しいシフト量を追加
    return true         // リライト成功
}
```

このコードブロックは、SSAグラフを走査し、特定のパターン（`Lsh64x64` の第一引数が `Rsh64Ux64` であり、その第一引数が `Lsh64x64` である、といったネストされた構造）を検出します。そして、各シフト操作の定数シフト量 `c1`, `c2`, `c3` を抽出し、条件 `c1 >= c2 && c3 >= c2` をチェックします。条件が満たされれば、`v.reset` と `v.AddArg` を使って、現在のSSA値を簡略化された単一のシフト操作に変換します。

Issue #14825（コミットメッセージに記載されているが、詳細な内容は不明）は、おそらくこのような冗長なシフト操作が最適化されずに残ってしまうケースを指摘していたと考えられます。このコミットは、これらの特定のパターンを認識し、より効率的な単一のシフト操作に変換することで、コンパイラの最適化能力を向上させることを目的としています。これにより、生成されるバイナリのサイズが小さくなり、実行速度が向上する可能性があります。

## 前提知識の解説

### 1. GoコンパイラとSSA (Static Single Assignment)

Goコンパイラは、ソースコードを機械語に変換する過程で、様々な最適化を行います。その最適化フェーズの一つに、中間表現としてSSA形式を使用する段階があります。

*   **SSA形式**: プログラム中の各変数が一度だけ代入されるようにする中間表現です。これにより、データフロー解析や最適化が容易になります。SSA形式では、各操作が「値（Value）」として表現され、これらの値がグラフ構造を形成します。
*   **SSAバックエンド**: GoコンパイラのSSAバックエンドは、SSA形式のプログラムグラフに対して、レジスタ割り当て、命令スケジューリング、様々な最適化（定数畳み込み、デッドコード削除など）を行います。

### 2. 定数畳み込み (Constant Folding)

定数畳み込みは、コンパイル時最適化の一種で、コンパイル時に値が既知である式を、その計算結果の定数に置き換えるプロセスです。例えば、`2 + 3` という式があれば、コンパイラはこれを `5` に置き換えます。これにより、実行時に加算操作を行う必要がなくなり、プログラムの実行速度が向上します。

このコミットでは、ビットシフト操作の連鎖が定数畳み込みの対象となっています。シフト量が定数である場合、コンパイラはこれらのシフト操作を組み合わせて、最終的なシフト量を計算し、単一のシフト操作に変換しようとします。

### 3. ビットシフト演算

*   **左シフト (`<<`)**: オペランドのビットを左に指定された回数だけ移動させます。右側には0が埋められます。`x << n` は `x * 2^n` と同等です（オーバーフローを無視すれば）。
*   **右シフト (`>>`)**: オペランドのビットを右に指定された回数だけ移動させます。符号なし整数 (`uint`) の場合、左側には0が埋められます（論理右シフト）。符号付き整数 (`int`) の場合、左側には符号ビットが埋められるか（算術右シフト）、0が埋められるか（論理右シフト）は言語や実装に依存しますが、Goの符号付き右シフトは算術右シフトです。このコミットでは `RshUx` (Unsigned Right Shift) が使われているため、符号なし右シフトが対象です。

### 4. リライトルール (Rewrite Rules)

GoコンパイラのSSAバックエンドでは、プログラムグラフのパターンを認識し、より効率的なパターンに変換するための「リライトルール」が定義されています。これらのルールは、`generic.rules` のようなファイルに記述され、`rewritegeneric.go` のようなファイルで実際のコードに変換されます。リライトルールは、特定のオペレーションの組み合わせ（例: `(Add (Const x) (Const y))`）を、より単純なオペレーション（例: `(Const (x+y))`）に変換するのに役立ちます。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドに新しいリライトルールを追加し、既存のリライト関数を更新することで、特定のビットシフト操作の連鎖を最適化します。

具体的には、以下の2つのパターンを対象としています。

1.  **`((x << c1) >> c2) << c3` の形式**:
    *   これは、左シフト、符号なし右シフト、左シフトの順に適用されるパターンです。
    *   `c1`, `c2`, `c3` は定数のシフト量です。
    *   このパターンは、`c1 >= c2` かつ `c3 >= c2` という条件が満たされる場合に、`x << (c1 - c2 + c3)` という単一の左シフト操作に簡略化できます。
    *   例: `((x << 5) >> 2) << 2` の場合、`c1=5, c2=2, c3=2`。条件 `5 >= 2 && 2 >= 2` は真。結果は `x << (5 - 2 + 2)` = `x << 5` となります。

2.  **`((x >> c1) << c2) >> c3` の形式**:
    *   これは、符号なし右シフト、左シフト、符号なし右シフトの順に適用されるパターンです。
    *   `c1`, `c2`, `c3` は定数のシフト量です。
    *   このパターンは、`c1 >= c2` かつ `c3 >= c2` という条件が満たされる場合に、`x >> (c1 - c2 + c3)` という単一の符号なし右シフト操作に簡略化できます。
    *   例: `((x >> 5) << 2) >> 2` の場合、`c1=5, c2=2, c3=2`。条件 `5 >= 2 && 2 >= 2` は真。結果は `x >> (5 - 2 + 3)` = `x >> 5` となります。

これらの最適化は、8ビット、16ビット、32ビット、64ビットの符号なし整数型 (`uint8`, `uint16`, `uint32`, `uint64`) に対して適用されます。

### 最適化のメカニズム

GoコンパイラのSSAバックエンドは、プログラムをSSA形式のオペレーショングラフとして表現します。このグラフに対して、`generic.rules` に記述されたパターンマッチングとリライトが適用されます。

1.  **パターンマッチング**: コンパイラは、SSAグラフ内で `(Lsh64x64 (Rsh64Ux64 (Lsh64x64 x (Const64 [c1])) (Const64 [c2])) (Const64 [c3]))` のような特定のオペレーションの組み合わせを検出します。
2.  **条件チェック**: パターンがマッチした場合、`c1 >= c2 && c3 >= c2` のような追加の条件がチェックされます。この条件は、中間シフトが元の値を完全に復元できるか、または少なくとも一部が復元され、最終的なシフト量が正しく計算できることを保証するために重要です。
3.  **リライト**: 条件が満たされれば、元の複雑なオペレーションの連鎖は、`Lsh64x64 x (Const64 [c1-c2+c3])` のような単一のより単純なオペレーションに置き換えられます。

このプロセスにより、コンパイラは実行時に複数のシフト命令を発行する代わりに、単一のシフト命令を発行できるようになり、CPUサイクルとコードサイズを節約します。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/gen/generic.rules` の変更

追加されたルールは以下の形式です。

```
// ((x >> c1) << c2) >> c3 
(Rsh64Ux64 (Lsh64x64 (Rsh64Ux64 x (Const64 [c1])) (Const64 [c2])) (Const64 [c3])) && c1 >= c2 && c3 >= c2 ->  (Rsh64Ux64 x (Const64 <config.fe.TypeUInt64()> [c1-c2+c3]))

// ((x << c1) >> c2) << c3
(Lsh64x64 (Rsh64Ux64 (Lsh64x64 x (Const64 [c1])) (Const64 [c2])) (Const64 [c3])) && c1 >= c2 && c3 >= c2 ->  (Lsh64x64 x (Const64 <config.fe.TypeUInt64()> [c1-c2+c3]))
```

*   `Rsh64Ux64`: 64ビット符号なし右シフト操作。
*   `Lsh64x64`: 64ビット左シフト操作。
*   `x`: シフトされる元の値。
*   `Const64 [c1]`, `Const64 [c2]`, `Const64 [c3]`: 定数のシフト量。
*   `&& c1 >= c2 && c3 >= c2`: リライトが適用されるための条件。この条件は、中間的なシフト操作が元のビットパターンを破壊しない、または最終的な結果に影響を与えないことを保証します。例えば、`x >> c1 << c2` の場合、`c1 >= c2` であれば、`c1 - c2` だけ右にシフトした後に左にシフトしても、元の `c1` ビットの損失は回復せず、結果として `x >> (c1 - c2)` となります。さらに `>> c3` が続くため、最終的なシフト量は `c1 - c2 + c3` となります。
*   `->`: リライトの矢印。左側のパターンがマッチし、条件が満たされた場合、右側のパターンに置き換えられます。
*   `(Rsh64Ux64 x (Const64 <config.fe.TypeUInt64()> [c1-c2+c3]))`: 簡略化された単一のシフト操作。

これらのルールは、`go generate` コマンドによって `rewritegeneric.go` 内のGoコードに変換されます。

### `src/cmd/compile/internal/ssa/rewritegeneric.go` の変更

`rewritegeneric.go` には、各SSAオペレーションに対応するリライト関数があります。例えば、`rewriteValuegeneric_OpLsh64x64` 関数内に、上記ルールに対応するGoコードが追加されています。

```go
// match: (Lsh64x64 (Rsh64Ux64 (Lsh64x64 x (Const64 [c1])) (Const64 [c2])) (Const64 [c3]))
// cond: c1 >= c2 && c3 >= c2
// result: (Lsh64x64 x (Const64 <config.fe.TypeUInt64()> [c1-c2+c3]))
for {
    if v.Args[0].Op != OpRsh64Ux64 {
        break
    }
    if v.Args[0].Args[0].Op != OpLsh64x64 {
        break
    }
    x := v.Args[0].Args[0].Args[0]
    if v.Args[0].Args[0].Args[1].Op != OpConst64 {
        break
    }
    c1 := v.Args[0].Args[0].Args[1].AuxInt
    if v.Args[0].Args[1].Op != OpConst64 {
        break
    }
    c2 := v.Args[0].Args[1].AuxInt
    if v.Args[1].Op != OpConst64 {
        break
    }
    c3 := v.Args[1].AuxInt
    if !(c1 >= c2 && c3 >= c2) {
        break
    }
    v.reset(OpLsh64x64) // オペレーションをLsh64x64にリセット
    v.AddArg(x)         // 元の値xを追加
    v0 := b.NewValue0(v.Line, OpConst64, config.fe.TypeUInt64()) // 新しい定数シフト量を作成
    v0.AuxInt = c1 - c2 + c3 // シフト量を計算
    v.AddArg(v0)        // 新しいシフト量を追加
    return true         // リライト成功
}
```

このコードブロックは、SSAグラフを走査し、特定のパターン（`Lsh64x64` の第一引数が `Rsh64Ux64` であり、その第一引数が `Lsh64x64` である、といったネストされた構造）を検出します。そして、各シフト操作の定数シフト量 `c1`, `c2`, `c3` を抽出し、条件 `c1 >= c2 && c3 >= c2` をチェックします。条件が満たされれば、`v.reset` と `v.AddArg` を使って、現在のSSA値を簡略化された単一のシフト操作に変換します。

### `src/cmd/compile/internal/gc/testdata/arith_ssa.go` の変更

追加されたテスト関数 `testShiftRemoval` は、これらの最適化が期待通りに機能するかを検証します。

```go
//go:noinline
func lshNop1(x uint64) uint64 {
	// two outer shifts should be removed
	return (((x << 5) >> 2) << 2)
}
// ... (他のlshNop, rshNop関数) ...

func testShiftRemoval() {
    allSet := ^uint64(0) // 全ビットが1のuint64
    // ... (rshNopシリーズのテスト) ...
    if want, got := uint64(0xffffffffffffffe0), lshNop1(allSet); want != got {
        println("testShiftRemoval lshNop1 failed, wanted", want, "got", got)
        failed = true
    }
    // ... (他のlshNopシリーズのテスト) ...
}
```

`lshNop1` の例では、`((x << 5) >> 2) << 2` という式が定義されています。
*   `c1 = 5`, `c2 = 2`, `c3 = 2`
*   条件 `c1 >= c2 && c3 >= c2` (すなわち `5 >= 2 && 2 >= 2`) は真です。
*   したがって、この式は `x << (5 - 2 + 2)` = `x << 5` に最適化されるべきです。
テストでは、`allSet` (すべてのビットが1) を入力として `lshNop1` を呼び出し、期待される結果 (`0xffffffffffffffe0` は `allSet << 5` の結果) と比較することで、最適化が正しく行われたことを確認します。

`lshNotNop` や `rshNotNop` のような関数は、条件が満たされない場合に最適化が適用されないことを確認するためのものです。例えば、`lshNotNop` の `(((x << 5) >> 2) << 1)` では `c3=1` であり、`c3 >= c2` (すなわち `1 >= 2`) が偽となるため、このリライトルールは適用されません。

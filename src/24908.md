## 変更の背景

Goのランタイムにおけるガベージコレクション（GC）は、そのパフォーマンス特性において非常に重要な要素です。GCのコードベースは複雑であり、特に並行GCの導入以降、様々な最適化とメカニズムが組み込まれてきました。

このコミットが行われた2015年8月時点では、GoのGCはまだ進化の途上にあり、特にスタックの処理に関して、Stop-The-World (STW) フェーズでのスタック再スキャンがGCポーズ時間の主要な原因の一つとなっていました。スタックバリアに関するコードは、GCのマークフェーズとスキャンフェーズのコードと密接に混在しており、コードの可読性や保守性を低下させていました。

このコミットの目的は、機能的な変更を加えることなく、スタックバリアに関連するロジックを独立したファイルに分離することで、コードベースの構造を改善し、将来的な開発や理解を容易にすることにあります。これにより、GCの異なる側面（マーク、スキャン、スタックバリア）がより明確に分離され、それぞれのコンポーネントの責任が明確になります。

## 前提知識の解説

### Goのガベージコレクション (GC) の概要

GoのGCは、並行（concurrent）、三色（tri-color）、マーク＆スイープ（mark-and-sweep）アルゴリズムを基本としています。これは、アプリケーション（ミューテーター）が実行中にGCのマークフェーズを並行して進めることで、STWポーズ時間を最小限に抑えることを目指しています。

*   **三色マーキング**: GCはオブジェクトを以下の3色に分類します。
    *   **白 (White)**: まだGCによって発見されていないオブジェクト。回収候補。
    *   **灰 (Grey)**: GCによって発見されたが、その参照先（子オブジェクト）がまだスキャンされていないオブジェクト。
    *   **黒 (Black)**: GCによって発見され、その参照先もすべてスキャンされたオブジェクト。回収されないことが確定。
*   **ルートからのスキャン**: GCは、グローバル変数やゴルーチンのスタック上にあるポインタなど、プログラムの「ルート」から到達可能なオブジェクトを灰色にマークすることから始めます。
*   **並行マーキング**: GCは、灰色オブジェクトの参照先をスキャンし、白オブジェクトを灰色に、灰色オブジェクトを黒に移行させます。このプロセスはアプリケーションの実行と並行して行われます。

### 並行GCとスタックの課題

並行GCの大きな課題の一つは、GCがオブジェクトグラフをスキャンしている間に、アプリケーションがポインタを変更する可能性があることです。特にゴルーチンのスタックは頻繁に変化するため、スタック上のポインタの整合性を保つことが難しい問題でした。

Go 1.8以前のGCでは、スタック上のすべてのポインタ変更にライトバリアを適用することはオーバーヘッドが大きすぎると考えられていました。そのため、GCの並行マークフェーズ中、スタックは「パーマグレー（permagrey）」として扱われました。これは、スタック上のオブジェクトはGCによってスキャンされるまで一時的に灰色とみなされることを意味します。

このアプローチの欠点は、GCサイクル終了時に、STWポーズ中にすべてのゴルーチンのスタックを再スキャンする必要があることでした。この再スキャンは、並行フェーズ中にスタック上で変更されたポインタによって、到達可能な白オブジェクトが誤って回収されるのを防ぐために必要でした。このSTWスタック再スキャンが、GCポーズ時間の主要な原因の一つでした。

### スタックバリアの役割

このコミットにおける「スタックバリア」は、Go 1.8で導入されたハイブリッドライトバリアとは異なる、Go 1.8以前のGCにおけるスタック処理メカニズムの一部を指します。具体的には、STWスタック再スキャンを効率的に行うための準備や、スタックの巻き戻し（panic/recoverなど）時にGCの整合性を保つためのメカニズムに関連しています。

スタックバリアは、特定のスタックフレームの戻りアドレス（Return PC）を一時的に書き換えることで機能します。これにより、関数呼び出しが特定のポイントに到達した際に、GCランタイムが介入し、スタックの状態を検査または調整できるようになります。これは、GCがスタックを安全にスキャンし、ポインタの変更を追跡するために必要な情報を提供するためのものです。

## 技術的詳細

このコミットで移動されたコードは、Go 1.8以前のGCにおけるスタックバリアの実装を構成するものです。主な機能は以下の通りです。

*   **`debugStackBarrier`**: スタックバリアのデバッグを有効にするためのフラグ。`true` に設定すると、スタックバリアのインストールや削除に関する詳細なログが出力されます。
*   **`firstStackBarrierOffset`**: 最初のスタックバリアを現在のスタックポインタ (SP) からどの程度のオフセットに配置するかを決定する近似的なバイトオフセット。この値は、マーク終了時に再スキャンする必要があるスタックの量を下限としています。デバッグ目的で `0` に設定すると、すべてのフレームにスタックバリアがインストールされます。
*   **`gcMaxStackBarriers(stackSize int)`**: 指定された `stackSize` のスタックにインストールできるスタックバリアの最大数を計算します。`firstStackBarrierOffset` の値に基づいて、指数関数的にオフセットを増やしながらバリアを配置するロジックが含まれています。
*   **`gcInstallStackBarrier(gp *g, frame *stkframe)`**: 指定されたスタックフレームの戻りアドレス (Return PC) にスタックバリアをインストールします。
    *   `frame.lr` (Link Register) が `0` の場合や、`cgocallback_gofunc` の戻りアドレスにはバリアをインストールしません。これは、これらのケースでは通常の関数呼び出しとは異なる戻りメカニズムが使用されるためです。
    *   戻りアドレスを保存し、それを `stackBarrierPC` という特別な値で上書きします。保存された元の戻りアドレスは `gp.stkbar` (goroutine のスタックバリア情報) に記録されます。
*   **`gcRemoveStackBarriers(gp *g)`**: 指定されたゴルーチン `gp` のスタックにインストールされているすべてのスタックバリアを削除します。
    *   `gp.stkbar` に記録されている情報に基づいて、元の戻りアドレスを復元します。
    *   `gp.stkbarPos` と `gp.stkbar` をクリアし、記録されたスタックバリア情報をリセットします。
*   **`gcRemoveStackBarrier(gp *g, stkbar stkbar)`**: 単一のスタックバリアを削除します。`gcInstallStackBarrier` の逆操作です。
    *   `nosplit` プラグマが付与されており、`gp` のスタックが移動しないことを保証します。
*   **`gcPrintStkbars(stkbar []stkbar)`**: デバッグ目的で `[]stkbar` の内容を出力します。
*   **`gcUnwindBarriers(gp *g, sp uintptr)`**: `sp` を含むフレームまでのすべてのスタックバリアを「ヒット済み」としてマークし、削除します。これは、panic/recoverによるスタックの巻き戻し時や、`heapBitsBulkBarrier` がスタック上の宛先を強制的に再スキャンする必要がある場合に使用されます。
    *   `nosplit` プラグマが付与されており、`gp` のスタックが移動しないことを保証します。
*   **`nextBarrierPC()`**: 次のスタックバリアの元の戻りアドレスを返します。`getcallerpc` によって使用され、`nosplit` です。
*   **`setNextBarrierPC(pc uintptr)`**: 次のスタックバリアの戻りアドレスを設定します。`setcallerpc` によって使用され、`nosplit` です。

これらの関数は、GCがスタックを安全に操作し、ポインタの整合性を保つための低レベルなメカニズムを提供していました。特に、STWフェーズでのスタック再スキャン時に、どの部分をスキャンすべきか、あるいはスタックの巻き戻し時にGCの状態をどのように調整すべきかを制御するために重要でした。

このコミットにおける「コアとなるコードの変更」は、機能的なロジックの変更ではなく、既存のコードの物理的な配置の変更にあります。

これは、スタックバリアの概念と実装が、GCの一般的なマーク＆スキャンロジックから独立した、より専門的なサブシステムとして扱われるべきであるという設計上の判断を反映しています。これにより、GCの全体像を把握する際に、スタックバリアの詳細が他のGCメカニズムと混同されることなく、より明確に理解できるようになります。また、将来的にスタックバリアの実装に変更を加える際も、関連するコードが1箇所に集約されているため、作業がしやすくなります。

この変更は、Goランタイムのコードベースが成熟し、よりモジュール化された構造へと進化していく過程の一部と見なすことができます。

    *   戻りアドレスを保存し、それを `stackBarrierPC` という特別な値で上書きします。保存された元の戻りアドレスは `gp.stkbar` (goroutine のスタックバリア情報) に記録されます。
*   **`gcRemoveStackBarriers(gp *g)`**: 指定されたゴルーチン `gp` のスタックにインストールされているすべてのスタックバリアを削除します。
    *   `gp.stkbar` に記録されている情報に基づいて、元の戻りアドレスを復元します。
    *   `gp.stkbarPos` と `gp.stkbar` をクリアし、記録されたスタックバリア情報をリセットします。
*   **`gcRemoveStackBarrier(gp *g, stkbar stkbar)`**: 単一のスタックバリアを削除します。`gcInstallStackBarrier` の逆操作です。
    *   `nosplit` プラグマが付与されており、`gp` のスタックが移動しないことを保証します。
*   **`gcPrintStkbars(stkbar []stkbar)`**: デバッグ目的で `[]stkbar` の内容を出力します。
*   **`gcUnwindBarriers(gp *g, sp uintptr)`**: `sp` を含むフレームまでのすべてのスタックバリアを「ヒット済み」としてマークし、削除します。これは、panic/recoverによるスタックの巻き戻し時や、`heapBitsBulkBarrier` がスタック上の宛先を強制的に再スキャンする必要がある場合に使用されます。
    *   `nosplit` プラグマが付与されており、`gp` のスタックが移動しないことを保証します。
*   **`nextBarrierPC()`**: 次のスタックバリアの元の戻りアドレスを返します。`getcallerpc` によって使用され、`nosplit` です。
*   **`setNextBarrierPC(pc uintptr)`**: 次のスタックバリアの戻りアドレスを設定します。`setcallerpc` によって使用され、`nosplit` です。

これらの関数は、GCがスタックを安全に操作し、ポインタの整合性を保つための低レベルなメカニズムを提供していました。特に、STWフェーズでのスタック再スキャン時に、どの部分をスキャンすべきか、あるいはスタックの巻き戻し時にGCの状態をどのように調整すべきかを制御するために重要でした。

## コアとなるコードの解説

このコミットにおける「コアとなるコードの変更」は、機能的なロジックの変更ではなく、既存のコードの物理的な配置の変更にあります。

`src/runtime/mgc.go` と `src/runtime/mgcmark.go` から削除された `debugStackBarrier`、`firstStackBarrierOffset`、そして `gcMaxStackBarriers` から `setNextBarrierPC` までのすべての関数は、`src/runtime/mstkbar.go` にそのままの形で移動されました。

これは、スタックバリアの概念と実装が、GCの一般的なマーク＆スキャンロジックから独立した、より専門的なサブシステムとして扱われるべきであるという設計上の判断を反映しています。これにより、GCの全体像を把握する際に、スタックバリアの詳細が他のGCメカニズムと混同されることなく、より明確に理解できるようになります。また、将来的にスタックバリアの実装に変更を加える際も、関連するコードが1箇所に集約されているため、作業がしやすくなります。

この変更は、Goランタイムのコードベースが成熟し、よりモジュール化された構造へと進化していく過程の一部と見なすことができます。

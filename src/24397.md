# [インデックス 24397] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における、並行マークフェーズ中の潜在的なパフォーマンスボトルネックを解消するためのものです。具体的には、GC作業（`gcWork`）が並行マークから隠蔽される可能性のあるタイミングウィンドウを閉じ、Stop-The-World（STW）ポーズの長さを短縮することを目的としています。

## コミット

runtime: close window that hides GC work from concurrent mark

    runtime: close window that hides GC work from concurrent mark
    
    Currently we enter mark 2 by first flushing all existing gcWork caches
    and then setting gcBlackenPromptly, which disables further gcWork
    caching. However, if a worker or assist pulls a work buffer in to its
    gcWork cache after that cache has been flushed but before caching is
    disabled, that work may remain in that cache until mark termination.
    If that work represents a heap bottleneck (e.g., a single pointer that
    is the only way to reach a large amount of the heap), this can force
    mark termination to do a large amount of work, resulting in a long
    STW.
    
    Fix this by reversing the order of these steps: first disable caching,
    then flush all existing caches.

    combined with CL 12672 and CL 12646 distills the critical parts of his

## 変更の背景

Goのガベージコレクタは、アプリケーションの実行と並行して動作する並行マーク・アンド・スイープ方式を採用しています。しかし、GCのマークフェーズの特定の段階（マークフェーズ2への移行時）において、GC作業（`gcWork`）が一時的にGCシステムから「隠れてしまう」可能性のある競合状態が存在していました。

具体的には、GCはマークフェーズ2に入る際に、まず既存の`gcWork`キャッシュをすべてフラッシュし、その後`gcBlackenPromptly`フラグを設定してそれ以上の`gcWork`のキャッシュを無効にします。この2つの操作の間に短い時間窓が存在し、その間にGCワーカーやアシストがワークバッファを自身の`gcWork`キャッシュに取り込んでしまうことがありました。

この取り込まれたワークバッファは、キャッシュが無効化される前に取得されたため、マーク終了時までそのキャッシュ内に留まり、GCシステムによって処理されないままでした。もしこの隠れたワークがヒープの大部分に到達するための唯一の経路となるような重要なポインタを含んでいた場合、マーク終了時に大量の作業が集中して行われることになり、結果として長いStop-The-World（STW）ポーズが発生し、アプリケーションの応答性に悪影響を与えていました。

このコミットは、この競合状態を解消し、STWポーズの長さを短縮することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションの基本的な仕組み、特に並行マークフェーズと三色マーキング、そして関連する内部メカニズムについて理解しておく必要があります。

1.  **Goのガベージコレクション (GC)**: GoのGCは、主に並行三色マーク・アンド・スイープアルゴリズムを使用しています。これは、アプリケーション（ミューテーター）の実行と並行してGC作業の大部分を行うことで、STWポーズを最小限に抑えることを目指しています。
2.  **三色マーキング (Tri-color Marking)**:
    *   **白 (White)**: まだ到達可能かどうかが不明なオブジェクト、または到達不可能と判断され回収対象となるオブジェクト。
    *   **灰 (Gray)**: 到達可能と判断されたが、そのオブジェクトが参照する他のオブジェクトがまだスキャンされていないオブジェクト。
    *   **黒 (Black)**: 到達可能と判断され、そのオブジェクトが参照するすべてのオブジェクトもスキャン済みのオブジェクト。
    GCは、ルート（グローバル変数やゴルーチンのスタックなど）から開始し、到達可能なオブジェクトを白から灰へ、そして灰から黒へと色を塗っていきます。
3.  **並行マーク (Concurrent Mark)**: GCの主要なフェーズの一つで、アプリケーションの実行と並行して到達可能なオブジェクトをマークします。このフェーズ中、Goはライトバリアを使用して、ミューテーターがオブジェクトグラフを変更した際にGCの整合性を保ちます。
4.  **Stop-The-World (STW)**: プログラム内のすべてのゴルーチンが一時的に停止される期間です。GoのGCはほとんど並行で動作しますが、GCルートの特定やマーク終了の最終処理など、ごく短いSTWポーズが不可欠です。Goの目標は、このSTWポーズをミリ秒単位に抑えることです。
5.  **`gcWork`**: GoのGC内部で、マーク作業の単位を管理するためのメカニズムです。GCワーカーは、マークすべきオブジェクトのポインタを`gcWork`バッファに格納し、それを処理します。これらのバッファは、パフォーマンス向上のために各プロセッサ（P）のローカルキャッシュに一時的に保持されることがあります。
6.  **`gcBlackenPromptly`**: このフラグは、GCがオブジェクトを「黒」状態に迅速に移行させるための指示です。並行マーク中にミューテーターがヒープを変更する可能性があるため、三色不変条件を維持するために、到達可能なオブジェクトを速やかに黒くすることが重要になります。このフラグが`true`に設定されると、`gcWork`のキャッシュが無効化され、GCワーカーはワークバッファをローカルにキャッシュするのではなく、直接共有のワークキューにプッシュするようになります。これにより、マーク作業がより迅速に中央に集約され、マーク終了時の処理が効率化されます。

## 技術的詳細

このコミットが修正する問題は、GoのGCがマークフェーズ2に移行する際の特定の順序に起因する競合状態です。

従来の処理順序は以下の通りでした。
1.  `forEachP`ループで、すべてのプロセッサ（P）の`gcWork`キャッシュをフラッシュする（`_p_.gcw.dispose()`を呼び出す）。
2.  `gcBlackenPromptly = true`を設定し、それ以降の`gcWork`のキャッシュを無効にする。

この順序では、`forEachP`ループが実行されて各Pのキャッシュがフラッシュされた直後から、`gcBlackenPromptly = true`が設定されるまでの間に、非常に短い時間窓が存在しました。この時間窓内で、もしGCワーカーやアシストが新しいGC作業を自身の`gcWork`キャッシュに取得してしまった場合、その作業はフラッシュされた後であるため、再度フラッシュされることはありません。しかし、`gcBlackenPromptly`がまだ`false`であるため、その作業はローカルキャッシュに保持され続けてしまいます。

この「隠れた」GC作業は、マーク終了時までGCシステムの中央キューに戻されず、処理されません。もしこの隠れた作業が、ヒープの大部分をマークするために不可欠なポインタを含んでいた場合、マーク終了時にSTWポーズ中にその大量の作業を処理する必要が生じ、結果としてSTWポーズが不必要に長くなっていました。これは、GCの並行性を損ない、アプリケーションのレイテンシを増加させる原因となっていました。

このコミットは、この問題の根本原因である処理順序を反転させることで解決します。

新しい処理順序は以下の通りです。
1.  `gcBlackenPromptly = true`を設定し、それ以降の`gcWork`のキャッシュを直ちに無効にする。
2.  `forEachP`ループで、すべてのプロセッサ（P）の既存の`gcWork`キャッシュをフラッシュする。

この変更により、`gcBlackenPromptly`が`true`に設定された後は、いかなるGCワーカーも新しい`gcWork`をローカルキャッシュに取得することができなくなります。その後で既存のキャッシュがフラッシュされるため、キャッシュに隠れたGC作業が発生する可能性が完全に排除されます。これにより、すべてのGC作業がマーク終了前に適切に処理されることが保証され、STWポーズの長さが短縮され、GCの効率と予測可能性が向上します。

## コアとなるコードの変更箇所

変更は `src/runtime/mgc.go` ファイル内の `gc` 関数のマークフェーズ2への移行部分で行われています。

```diff
--- a/src/runtime/mgc.go
+++ b/src/runtime/mgc.go
@@ -1003,12 +1003,18 @@ func gc(mode int) {
 			// rescan global data and bss.
 			markroot(nil, _RootData)
 			markroot(nil, _RootBss)
+\n+\t\t\t// Disallow caching workbufs.\n+\t\t\tgcBlackenPromptly = true\n+\n+\t\t\t// Flush all currently cached workbufs. This\n+\t\t\t// also forces any remaining background\n+\t\t\t// workers out of their loop.\n 			forEachP(func(_p_ *p) {
 				_p_.gcw.dispose()
 			})
 		})
 \n-\t\tgcBlackenPromptly = true
 		// Wait for this more aggressive background mark to complete.
 		work.bgMark2.clear()
 		work.bgMark2.wait()
```

具体的には、以下の2行の順序が入れ替えられました。

*   `gcBlackenPromptly = true`
*   `forEachP(func(_p_ *p) { _p_.gcw.dispose() })`

変更前は`forEachP`が先に実行され、その後`gcBlackenPromptly = true`が設定されていました。
変更後は`gcBlackenPromptly = true`が先に設定され、その後`forEachP`が実行されるようになりました。

## コアとなるコードの解説

このコード変更の核心は、`gcBlackenPromptly`フラグの設定と、各Pの`gcWork`キャッシュのフラッシュ（`_p_.gcw.dispose()`）の順序を反転させた点にあります。

1.  **`gcBlackenPromptly = true` の先行設定**:
    このフラグを最初に`true`に設定することで、システム全体に対して「これ以降、GC作業バッファをローカルにキャッシュしてはならない」という指示が即座に伝達されます。これにより、GCワーカーやアシストが、キャッシュフラッシュとキャッシュ無効化の間の短い時間窓で新しいワークバッファをローカルキャッシュに取り込んでしまう可能性が完全に排除されます。すべての新しいGC作業は、ローカルキャッシュではなく、共有のワークキューに直接プッシュされるようになります。

2.  **`forEachP(func(_p_ *p) { _p_.gcw.dispose() })` の後続実行**:
    `gcBlackenPromptly`が`true`になった後で、`forEachP`ループが実行され、現在各Pのローカルキャッシュに残っているすべての`gcWork`バッファがフラッシュされます。このフラッシュ操作は、残っている作業を中央のGCワークキューに戻すか、適切に処理することを保証します。また、コメントにもあるように、これにより残りのバックグラウンドワーカーもループから強制的に抜け出すことになります。

この順序の反転により、GC作業がローカルキャッシュに「隠れて」しまい、マーク終了時まで処理されないという競合状態が解消されます。結果として、マーク終了時に処理すべき未処理のGC作業が大幅に減少し、STWポーズの時間が短縮され、GCの全体的なパフォーマンスと予測可能性が向上します。これは、Goランタイムのレイテンシ特性にとって重要な改善です。

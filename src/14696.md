# [インデックス 14696] ファイルの概要

このコミットは、Go言語のCgo（C言語との相互運用機能）をOpenBSDオペレーティングシステム上で有効にするための重要な変更を導入します。OpenBSDの動的リンカ（`ld.so(1)`）が`PT_TLS`（Thread-Local Storageのプログラムヘッダタイプ）セクションを直接サポートしていないというOS固有の課題に対処するため、Goランタイムがスレッドローカルストレージ（TLS）を適切に管理するための複雑なワークアラウンドが実装されています。これには、`librthread`によって提供される既存のThread Control Block (TCB) を修正し、TLSのための追加スペースを持つ新しいTCBを再割り当てする処理、およびGoの外部で作成されたスレッドに対してもゼロ初期化されたTLSが割り当てられるように`pthread_create`のラッパーを提供することが含まれます。

## 元コミット内容

このコミットの元の内容は、OpenBSD上でのCgoの有効化に関するものです。OpenBSDの`ld.so(1)`が`PT_TLS`セクションをサポートしていないため、`librthread`によって提供されるTCBを修正し、TLSのための追加スペースを持つTCBを再割り当てすることでこの問題を回避しています。また、Goの外部で作成されたスレッドに対してもゼロ初期化されたTLSが割り当てられるように、`pthread_create`のラッパーも提供されています。この作業はShenghou Ma (minux) との共同作業であり、変更6846064に依存し、Issue #3205を修正します。

## 変更の背景

Go言語は、C言語のコードをGoプログラムから呼び出すためのCgoというメカニズムを提供しています。これにより、既存のCライブラリを利用したり、OS固有の低レベル機能にアクセスしたりすることが可能になります。しかし、Cgoが正しく機能するためには、GoランタイムとCライブラリがスレッド管理、特にスレッドローカルストレージ（TLS）のメカニズムについて協調する必要があります。

OpenBSDは、そのセキュリティと堅牢性で知られるUNIX系オペレーティングシステムです。しかし、当時のOpenBSDの動的リンカ`ld.so(1)`は、ELFバイナリの`PT_TLS`プログラムヘッダタイプをサポートしていませんでした。`PT_TLS`は、コンパイラやリンカがスレッドローカル変数（各スレッドが独自のコピーを持つ変数）を効率的に配置するために使用する標準的な方法です。Goランタイムは、ゴルーチン（Goのスレッドに相当）やM（OSスレッド）などの重要なランタイム情報をTLSに格納するためにこのメカニズムに依存しています。

この`PT_TLS`の非サポートは、OpenBSD上でCgoを有効にする上での大きな障壁となっていました。Goランタイムが期待するTLSのセットアップと、OpenBSDのシステムが提供するスレッド管理（特に`librthread`が提供するThread Control Block: TCB）との間に不整合が生じるためです。このコミットは、このOS固有の課題を解決し、OpenBSDユーザーがGoのCgo機能を利用できるようにすることを目的としています。

## 前提知識の解説

### Cgo (Go言語)
Cgoは、GoプログラムがC言語のコードを呼び出すことを可能にするGoの機能です。Goのソースファイル内にCコードを直接記述したり、既存のCライブラリにリンクしたりできます。Cgoを使用すると、Goの標準ライブラリでは提供されていないOS固有の機能や、パフォーマンスが重要な部分でCの最適化されたコードを利用できます。

### スレッドローカルストレージ (TLS)
TLSは、マルチスレッドプログラミングにおいて、各スレッドが独自のデータコピーを持つことを可能にするメカニズムです。グローバル変数とは異なり、TLS変数はスレッド間で共有されず、各スレッドが独立してアクセス・変更できます。Goランタイムは、現在のゴルーチン（`g`）やOSスレッド（`m`）に関する情報など、ランタイムの内部状態をTLSに格納するために利用します。

### ELFバイナリとPT_TLSセクション
ELF (Executable and Linkable Format) は、UNIX系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFファイルは、プログラムヘッダテーブルを持ち、これにはプログラムのセグメント（コード、データなど）に関する情報が含まれます。`PT_TLS`は、このプログラムヘッダタイプの一つで、スレッドローカルストレージの初期化データと配置に関する情報を示します。動的リンカは、この情報を使用して、プログラムが起動する際に各スレッドのTLS領域を適切に設定します。

### `ld.so(1)` (動的リンカ/ローダ)
`ld.so(1)`は、UNIX系システムにおける動的リンカ/ローダです。プログラムが実行される際に、必要な共有ライブラリをメモリにロードし、それらのライブラリ内のシンボルをプログラムのコードに解決する役割を担います。`PT_TLS`セクションの処理も、通常はこの動的リンカの責任範囲です。

### Thread Control Block (TCB)
TCBは、オペレーティングシステムまたはスレッドライブラリが各スレッドの状態を管理するために使用するデータ構造です。これには、スレッドのスタックポインタ、レジスタの状態、スレッドID、そしてTLSへのポインタなどが含まれます。`librthread`はOpenBSDのユーザーレベルスレッドライブラリであり、スレッドの作成と管理、およびTCBの初期設定を行います。

### `pthread_create`
`pthread_create`は、POSIXスレッド（Pthreads）APIの一部であり、新しいスレッドを作成するための標準的な関数です。Cgoを使用するGoプログラムでは、GoランタイムがOSスレッドを作成する際にこの関数を呼び出すことがあります。また、Cgoを介してリンクされたCライブラリが独自にスレッドを作成する場合にも使用されます。

### `strtol(3)` (OpenBSDのバグ)
`strtol(3)`は、C標準ライブラリ関数の一つで、文字列を長整数に変換します。第3引数で基数（base）を指定できます。コミットメッセージで言及されているOpenBSDの`strtol(3)`のバグは、「base > 36」の場合に予期せぬ動作をするというものです。通常、基数は2から36（数字0-9とアルファベットA-Z）の範囲で有効ですが、OpenBSDの実装ではこれを超える基数でも成功してしまうという問題があったようです。

## 技術的詳細

このコミットの核となる技術的課題は、OpenBSDの`ld.so(1)`が`PT_TLS`セクションをサポートしていないことと、GoランタイムがTLSを必要とすることの間のギャップを埋めることです。Goは、`g`（現在のゴルーチン）と`m`（現在のOSスレッド）のポインタをTLSに格納することで、高速なアクセスを実現しています。

この問題を解決するために、以下の主要な技術的アプローチが取られています。

1.  **TCBの修正と再割り当て (`tcb_fixup`関数)**:
    *   OpenBSDの`librthread`は、スレッドが作成される際に基本的なTCBを割り当てます。しかし、このTCBにはGoがTLSとして使用する追加のスペースがありません。
    *   `tcb_fixup`関数は、既存のTCB（`__get_tcb()`で取得）の内容を、`malloc`で新しく確保したより大きなメモリ領域にコピーします。この新しい領域は、元のTCBのサイズ（`TCB_SIZE`）に加えて、Goが使用するTLSのサイズ（`TLS_SIZE`、`g`と`m`のポインタを格納するための2つのポインタサイズ）を確保します。
    *   新しい領域のTLS部分（`TLS_SIZE`分）は`bzero`でゼロ初期化されます。これは、シグナルハンドラがTLSスロットをゼロであると期待するため、特に重要です。
    *   `__set_tcb()`を呼び出すことで、スレッドのTCBポインタが新しく割り当てられた領域の適切なオフセット（`newtcb + TLS_SIZE`）を指すように更新されます。これにより、`librthread`が管理するTCB情報とGoが使用するTLS情報が共存できるようになります。
    *   メインスレッドのTCBは静的に割り当てられているため解放されませんが、それ以外のスレッドで元のTCBが動的に割り当てられていた場合は`free`されます。

2.  **`pthread_create`のラッパー (`pthread_create`関数)**:
    *   Goランタイム自身がスレッドを作成する場合だけでなく、Cgoを介してリンクされたCライブラリが`pthread_create`を呼び出してスレッドを作成する可能性もあります。これらの外部で作成されたスレッドも、Goランタイムが期待するTLSのセットアップを持つ必要があります。
    *   このコミットでは、システムコールとしての`pthread_create`を直接呼び出すのではなく、Goが提供するラッパー関数が呼び出されるようにフックしています。
    *   このラッパーは、元の`start_routine`と`arg`を`thread_args`構造体にラップし、この構造体を動的に割り当てます。
    *   新しいスレッドの開始ルーチンとして`thread_start_wrapper`を指定します。`thread_start_wrapper`は、元の`start_routine`を呼び出す前に`tcb_fixup(0)`（メインスレッドではないことを示す）を呼び出し、新しく作成されたスレッドのTLSを適切に設定します。

3.  **Goランタイムの初期化 (`xinitcgo`関数)**:
    *   Goランタイムが起動する際に、`xinitcgo`関数が呼び出されます。
    *   この関数は、`dlopen`と`dlsym`を使用して、システムライブラリ`libpthread.so`から実際の`pthread_create`関数のアドレスを動的に取得し、`sys_pthread_create`に格納します。これにより、Goのラッパーがシステム関数を呼び出せるようになります。
    *   メインスレッドに対しても`tcb_fixup(1)`を呼び出し、Goランタイムが起動する最初のスレッドのTLSを適切に設定します。

4.  **Goスレッドの開始 (`libcgo_sys_thread_start`関数)**:
    *   GoランタイムがCgoを介して新しいOSスレッドを開始する際に呼び出される`libcgo_sys_thread_start`関数も変更されています。
    *   この関数は、`pthread_create`を呼び出して新しいスレッドを作成し、そのスレッドの開始ルーチンとして`threadentry`を指定します。
    *   `threadentry`関数も、スレッドの実行を開始する前に`tcb_fixup(0)`を呼び出し、TLSをセットアップします。
    *   特に重要なのは、`threadentry`内で`%gs`（32-bit x86）または`%fs`（64-bit x86-64）レジスタを介してTLSに直接アクセスし、`g`と`m`のポインタを格納するアセンブリコードです。これは、OpenBSDのELFバイナリにおけるTLSの配置規則に合わせたものです。

5.  **Cランタイムの依存関係の解決 (`openbsd.c`)**:
    *   Goは標準のCランタイムスタートアップコード（`crt0.o`）にリンクしないため、`libc`が期待する特定のグローバルシンボル（`environ`, `__progname`, `__guard_local`）が未定義になります。
    *   `src/pkg/runtime/cgo/openbsd.c`では、これらのシンボルをGoランタイム内で定義し、`#pragma dynexport`ディレクティブを使用して動的にエクスポートすることで、`libc`がこれらのシンボルを見つけられるようにしています。
    *   `pthread_create`も`#pragma dynexport`でエクスポートされ、Goのラッパーがシステム関数をオーバーライドできるようにしています。

6.  **OpenBSD `strtol(3)`のバグ回避**:
    *   `misc/cgo/test/basic.go`では、OpenBSDの`strtol(3)`関数に存在する「基数が36を超える場合に誤った結果を返す」バグに対する特定のワークアラウンドが追加されています。これは、Cgoテストの正確性を保証するために必要です。

これらの変更により、GoランタイムはOpenBSDのOS環境と協調し、`PT_TLS`の非サポートという制約を回避しながら、Cgoを介したCコードとの相互運用を可能にしています。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、主に以下のファイルに集中しています。

*   `src/pkg/go/build/build.go`: CgoがOpenBSDの386およびamd64アーキテクチャで有効になるように設定が追加されます。
*   `src/pkg/net/cgo_openbsd.go` (新規ファイル): OpenBSD固有のネットワーク関連Cgoフラグを定義します。
*   `src/pkg/net/cgo_unix.go` および `src/pkg/os/user/lookup_unix.go`: ビルドタグに`openbsd`が追加され、これらのファイルがOpenBSDでもコンパイルされるようになります。
*   `src/pkg/runtime/cgo/gcc_openbsd_386.c` (新規ファイル): OpenBSD/386アーキテクチャ向けのCgoランタイムサポート。`tcb_fixup`、`pthread_create`ラッパー、`xinitcgo`、`libcgo_sys_thread_start`、およびTLS設定のためのアセンブリコードが含まれます。
*   `src/pkg/runtime/cgo/gcc_openbsd_amd64.c` (新規ファイル): OpenBSD/amd64アーキテクチャ向けのCgoランタイムサポート。`gcc_openbsd_386.c`と同様の機能を提供しますが、64ビットアーキテクチャに合わせたアセンブリコード（`%fs`レジスタの使用）が異なります。
*   `src/pkg/runtime/cgo/openbsd.c` (新規ファイル): OpenBSDの`libc`が期待するグローバルシンボル（`environ`, `__progname`, `__guard_local`）の定義と、`pthread_create`のオーバーライドを可能にするための`dynexport`プラグマが含まれます。

## コアとなるコードの解説

### `src/pkg/runtime/cgo/gcc_openbsd_386.c` および `src/pkg/runtime/cgo/gcc_openbsd_amd64.c`

これらのファイルは、OpenBSD上でのCgoの動作を可能にするための最も重要な部分です。

#### `tcb_fixup` 関数

```c
static void
tcb_fixup(int mainthread)
{
    void *newtcb, *oldtcb;

    // OpenBSDのld.so(1)はPT_TLSをサポートしていないため、
    // librthreadによって設定された既存のTCBを維持しつつ、
    // 独自のTLSスペースを割り当てる必要がある。

    newtcb = malloc(TCB_SIZE + TLS_SIZE); // TCBとTLSのための新しい領域を確保
    if(newtcb == NULL)
        abort();

    // シグナルトランポリンはTLSスロットがゼロであることを期待する。
    bzero(newtcb, TLS_SIZE); // TLS部分をゼロ初期化

    oldtcb = __get_tcb(); // 現在のスレッドのTCBを取得
    bcopy(oldtcb, newtcb + TLS_SIZE, TCB_SIZE); // 古いTCBの内容を新しい領域のTLSの後にコピー
    __set_tcb(newtcb + TLS_SIZE); // スレッドのTCBポインタを新しい領域の適切な位置に設定

    // メインスレッドのTCBは静的割り当てなので解放しない。
    if(!mainthread)
        free(oldtcb); // メインスレッド以外では古いTCBを解放
}
```
この関数は、OpenBSDの`ld.so(1)`が`PT_TLS`をサポートしないという問題を回避するために、スレッドのTCBを修正します。`librthread`が提供する既存のTCBを、Goが使用するTLSのための追加スペースを持つ新しいメモリ領域にコピーし、スレッドのTCBポインタを更新します。これにより、Goランタイムが`g`と`m`のポインタをTLSに格納できるようになります。

#### `pthread_create` ラッパー関数

```c
int
pthread_create(pthread_t *thread, const pthread_attr_t *attr,
    void *(*start_routine)(void *), void *arg)
{
    struct thread_args *p;

    p = malloc(sizeof(*p)); // スレッド引数を格納する構造体を動的に確保
    if(p == NULL) {
        errno = ENOMEM;
        return -1;
    }
    p->func = start_routine; // 元の開始ルーチンを保存
    p->arg = arg; // 元の引数を保存

    // システムのpthread_createを呼び出し、ラッパー関数を新しいスレッドの開始ルーチンとして指定
    return sys_pthread_create(thread, attr, thread_start_wrapper, p);
}
```
この関数は、GoのCgoコードやリンクされたCライブラリが`pthread_create`を呼び出す際に、その呼び出しをインターセプトします。新しいスレッドが開始される前に`thread_start_wrapper`が実行され、その中で`tcb_fixup`が呼び出されることで、Goランタイムが期待するTLSのセットアップが保証されます。

#### TLSへのアセンブリによるアクセス

`threadentry`関数内では、Goの`g`（ゴルーチン）と`m`（OSスレッド）のポインタをスレッドローカルストレージに格納するために、アーキテクチャ固有のアセンブリ命令が使用されています。

**32-bit (i386) の場合 (`gcc_openbsd_386.c`)**:
```assembly
    asm volatile (
        "movl %0, %%gs:-8\\n"    // MOVL g, -8(GS)
        "movl %1, %%gs:-4\\n"    // MOVL m, -4(GS)
        :: "r"(ts.g), "r"(ts.m)
    );
```
`%gs`セグメントレジスタは、32ビットLinuxやOpenBSDなどのシステムでTLSのベースアドレスを指すためによく使用されます。`-8(GS)`と`-4(GS)`は、`%gs`レジスタが指すアドレスからのオフセットを示し、Goの`g`と`m`ポインタが格納される場所です。

**64-bit (amd64) の場合 (`gcc_openbsd_amd64.c`)**:
```assembly
    asm volatile (
        "movq %0, %%fs:-16\\n"    // MOVL g, -16(FS)
        "movq %1, %%fs:-8\\n"    // MOVL m, -8(FS)
        :: "r"(ts.g), "r"(ts.m)
    );
```
64ビットシステムでは、`%fs`セグメントレジスタがTLSのベースアドレスを指すことが一般的です。`-16(FS)`と`-8(FS)`は、`%fs`レジスタが指すアドレスからのオフセットを示し、Goの`g`と`m`ポインタが格納される場所です。`movq`は64ビット値を移動するための命令です。

これらのアセンブリ命令は、Goランタイムが現在のゴルーチンとOSスレッドのコンテキストに高速にアクセスするために不可欠な、低レベルのTLS設定を実行します。

### `src/pkg/runtime/cgo/openbsd.c`

```c
// Supply environ, __progname and __guard_local, because
// we don't link against the standard OpenBSD crt0.o and
// the libc dynamic library needs them.

char *environ[1];
char *__progname;
long __guard_local;

#pragma dynexport environ environ
#pragma dynexport __progname __progname

// This is normally marked as hidden and placed in the
// .openbsd.randomdata section.
#pragma dynexport __guard_local __guard_local

// We override pthread_create to support PT_TLS.
#pragma dynexport pthread_create pthread_create
```
このファイルは、Goが標準のCランタイムスタートアップ（`crt0.o`）にリンクしないOpenBSD環境で、`libc`が期待する特定のグローバルシンボル（`environ`, `__progname`, `__guard_local`）を提供します。`#pragma dynexport`は、これらのシンボルが動的リンカによって解決可能になるようにエクスポートされることを保証します。また、`pthread_create`もエクスポートされ、Goのラッパーがシステム関数をオーバーライドできるようにします。

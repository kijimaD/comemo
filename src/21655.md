## 変更の背景

このコミットは、Goコンパイラ（`cmd/gc`）のコードベースを、C言語からGo言語へ段階的に移行するプロジェクト「`c2go`」の一環として行われました。初期のGoコンパイラはC言語で書かれていましたが、Go言語自体の成熟に伴い、コンパイラ自身もGo言語で書かれるべきであるという方針が立てられました。

`c2go`は、C言語のコードをGo言語に自動変換するためのツールであり、その変換プロセスを容易にするために、元のCコードをGo言語の慣習に近づけるリファクタリングが継続的に行われていました。このコミットは、特に以下の点に焦点を当てています。

1.  **Go言語との整合性向上**: C言語特有の構文やデータ型（例: `int32`）を、Go言語の対応する概念（例: `int`、スライス）に合わせることで、将来的な自動変換の精度を高めます。
2.  **可読性と保守性の向上**: 三項演算子（`? :`）のようなC言語特有の簡潔すぎる表現を、より明示的な`if-else`文に置き換えることで、コードの意図を明確にし、Go言語への変換後も自然なコードになるようにします。
3.  **命名規則の統一**: Go言語の命名規則や慣習に合わせるため、変数名や関数名の変更が行われています。特に、大文字・小文字を区別しないファイルシステムや環境での衝突を避けるための配慮も見られます。
4.  **バグの修正と堅牢性の向上**: `printf`フォーマットの修正や、文字列操作の安全性の向上など、細かなバグ修正や堅牢性向上のための変更も含まれています。

これらの変更は、Goコンパイラの長期的な進化戦略の一部であり、コンパイラ開発の効率化と、Go言語エコシステム全体の健全性を保つ上で重要なステップでした。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が役立ちます。

*   **Goコンパイラ (`cmd/gc`)**: Go言語の公式コンパイラの一つで、Goソースコードを機械語に変換する役割を担っています。初期のバージョンではC言語で書かれていましたが、後にGo言語自身で書き直されました。このコミットは、その移行期におけるC言語コードのリファクタリングです。
*   **`c2go` プロジェクト**: C言語で書かれたGoコンパイラのコードを、Go言語に自動変換するためのツールおよびプロジェクト。このプロジェクトの目標は、コンパイラ全体をGo言語で記述し、Go言語の自己ホスト（self-hosting）能力を強化することでした。
*   **三項演算子 (`? :`)**: C言語に存在する条件演算子で、`条件 ? 真の場合の値 : 偽の場合の値` の形式で記述されます。Go言語にはこの直接的な構文は存在せず、同様のロジックは`if-else`文で表現されます。
*   **C言語のポインタと配列**: C言語では、`uint32 *hash[]` のように配列のポインタを関数引数として渡すことが一般的です。これは `uint32 **hash` と同義として扱われることがありますが、Go言語ではスライスやポインタの扱いがより厳密であり、C言語のポインタ演算に依存する表現はGo言語への変換時に問題となる可能性があります。
*   **Go言語のスライス**: Go言語の組み込み型で、可変長配列のような機能を提供します。C言語の配列とは異なり、長さと容量を持ち、より安全で柔軟なデータ構造です。C言語の`int32`のような固定幅整数型ではなく、Go言語の`int`型はプラットフォームのワードサイズに合わせた適切なサイズ（32ビットまたは64ビット）を持ちます。
*   **Go言語の命名規則**: Go言語では、エクスポートされる（外部から参照可能な）識別子は大文字で始まり、エクスポートされない（パッケージ内部のみで参照可能な）識別子は小文字で始まるという明確な規則があります。また、略語の使用や、変数名の長さに関する慣習も存在します。
*   **`printf` フォーマット指定子**: C言語の標準ライブラリ関数`printf`は、書式文字列と引数に基づいて出力を整形します。フォーマット指定子（例: `%d`、`%s`、`%p`）は、引数の型と表示形式を指定します。誤った指定子は、コンパイルエラーや実行時エラー、または意図しない出力につながります。
*   **文字列リテラルとシンボルテーブル**: コンパイラ内部では、文字列リテラルや識別子（変数名、関数名など）がシンボルテーブルに格納され、効率的に管理されます。これらの文字列を生成・管理する関数は、コンパイラの性能と正確性に直結します。`strlit`のような関数は、文字列リテラルをシンボルテーブルに登録し、その内部表現を返す役割を担います。

## 技術的詳細

このコミットで行われた主要な技術的変更は以下の通りです。

1.  **三項演算子 (`? :`) の削除**:
    C言語の三項演算子は、簡潔な条件分岐を記述するのに便利ですが、Go言語には同等の構文がありません。この変更では、三項演算子を使用している箇所を、より明示的な`if-else`文に置き換えることで、`c2go`ツールによるGo言語への変換を容易にし、変換後のコードの可読性を向上させています。例えば、`wr ? "racewriterange" : "racereadrange"` のような表現は、`if (wr) name = "racewriterange"; else name = "racereadrange";` のように変更されています。

2.  **`uint32 *hash[]` から `uint32 **hash` への変更**:
    C言語では、`T *arr[]` と `T **arr` は関数引数の文脈でしばしば同義として扱われますが、ポインタのポインタとして明示的に `**` を使用することで、意図をより明確にしています。これは、Go言語のポインタの扱いに近づけるための、型表現の統一化の一環と考えられます。特に、`src/cmd/gc/typecheck.c` 内の `fielddup`, `keydup`, `indexdup` 関数でこの変更が適用されています。

3.  **`array.c` APIの `int32` から `int` への変更**:
    `src/cmd/gc/array.c` は、コンパイラ内部で動的な配列（Goのスライスに相当する概念）を管理するためのユーティリティ関数を提供しています。このコミットでは、`arraynew`, `arraylength`, `arrayget`, `arrayset`, `ensurecapacity` といった関数の引数や戻り値の型が `int32` から `int` に変更されています。これは、Go言語のスライスがインデックスに`int`型を使用することに合わせたもので、Go言語への変換時に型の一貫性を保つための重要な変更です。C言語の`int`型は、Go言語の`int`型と同様に、ターゲットアーキテクチャのネイティブなワードサイズ（32ビットまたは64ビット）に最適化された整数型として扱われることが多いため、この変更はより自然なGoコードへの移行を促進します。

4.  **`strlit` から `newstrlit` へのリネーム**:
    `src/cmd/gc/go.h` で定義されている `strlit` 関数が `newstrlit` にリネームされ、それに伴い呼び出し箇所もすべて変更されています。コミットメッセージには「`Strlit` との大文字・小文字を区別しない衝突を避けるため」と明記されています。これは、C言語の構造体 `Strlit` と関数 `strlit` が、一部のファイルシステムやツールチェーンで大文字・小文字を区別しない場合に名前の衝突を引き起こす可能性があったためです。Go言語は厳密に大文字・小文字を区別するため、このリネームはGo言語への移行を見据えた命名規則の整理と、潜在的なビルド環境依存の問題を回避するための措置です。

5.  **`printf` フォーマットの修正**:
    `src/cmd/gc/dcl.c` と `src/cmd/gc/subr.c` で、`fatal` 関数内で使用されている `printf` フォーマット指定子が修正されています。例えば、`fatal("addmethod: not TFIELD: %N", f);` が `fatal("addmethod: not TFIELD: %lT", f);` に、`fatal("brcom: no com for %A\\n", a);` が `fatal("brcom: no com for %O\\n", a);` に変更されています。これは、引数 `f` や `a` の型と、それに対応するフォーマット指定子が一致していなかったために発生する可能性のある警告や実行時エラーを修正し、コードの正確性を高めるものです。

6.  **変数名 `len` から `n` または `length` へのリネーム**:
    `src/cmd/gc/plive.c` や `src/cmd/gc/typecheck.c` などで、`len` という名前の変数が `n` や `length` に変更されています。Go言語には組み込み関数 `len()` が存在するため、C言語コード内で `len` という変数名を使用すると、Go言語への変換時に混乱や衝突を招く可能性があります。このリネームは、Go言語の慣習に合わせ、将来的な変換の障害を取り除くためのものです。

7.  **直接的な文字列編集による名前構築の排除**:
    `src/cmd/gc/walk.c` では、`convI2T` や `assertI2T` のような関数名を文字列操作で直接構築していた箇所が、より構造化された方法（例: `snprint` を使用して `from` と `to` の文字列を結合する）に変更されています。これは、文字列操作の安全性を高め、コードの可読性を向上させるとともに、Go言語の文字列操作のイディオムに近づけるための変更です。C言語の `strcpy` や `strcat` はバッファオーバーフローのリスクがあるため、より安全な `snprintf` のような関数への移行は良いプラクティスです。

これらの変更は、個々には小さいものですが、全体としてGoコンパイラのC言語コードベースをGo言語への移行に向けて体系的に準備し、将来的なメンテナンスコストを削減するための重要なステップでした。

*   **C言語のポインタと配列**: C言語では、`uint32 *hash[]` のように配列のポインタを関数引数として渡すことが一般的です。これは `uint32 **hash` と同義として扱われることがありますが、Go言語ではスライスやポインタの扱いがより厳密であり、C言語のポインタ演算に依存する表現はGo言語への変換時に問題となる可能性があります。
*   **Go言語のスライス**: Go言語の組み込み型で、可変長配列のような機能を提供します。C言語の配列とは異なり、長さと容量を持ち、より安全で柔軟なデータ構造です。C言語の`int32`のような固定幅整数型ではなく、Go言語の`int`型はプラットフォームのワードサイズに合わせた適切なサイズ（32ビットまたは64ビット）を持ちます。
*   **Go言語の命名規則**: Go言語では、エクスポートされる（外部から参照可能な）識別子は大文字で始まり、エクスポートされない（パッケージ内部のみで参照可能な）識別子は小文字で始まるという明確な規則があります。また、略語の使用や、変数名の長さに関する慣習も存在します。
*   **`printf` フォーマット指定子**: C言語の標準ライブラリ関数`printf`は、書式文字列と引数に基づいて出力を整形します。フォーマット指定子（例: `%d`、`%s`、`%p`）は、引数の型と表示形式を指定します。誤った指定子は、コンパイルエラーや実行時エラー、または意図しない出力につながります。
*   **文字列リテラルとシンボルテーブル**: コンパイラ内部では、文字列リテラルや識別子（変数名、関数名など）がシンボルテーブルに格納され、効率的に管理されます。これらの文字列を生成・管理する関数は、コンパイラの性能と正確性に直結します。`strlit`のような関数は、文字列リテラルをシンボルテーブルに登録し、その内部表現を返す役割を担います。

## 技術的詳細

このコミットで行われた主要な技術的変更は以下の通りです。

1.  **三項演算子 (`? :`) の削除**:
    C言語の三項演算子は、簡潔な条件分岐を記述するのに便利ですが、Go言語には同等の構文がありません。この変更では、三項演算子を使用している箇所を、より明示的な`if-else`文に置き換えることで、`c2go`ツールによるGo言語への変換を容易にし、変換後のコードの可読性を向上させています。例えば、`wr ? "racewriterange" : "racereadrange"` のような表現は、`if (wr) name = "racewriterange"; else name = "racereadrange";` のように変更されています。

2.  **`uint32 *hash[]` から `uint32 **hash` への変更**:
    C言語では、`T *arr[]` と `T **arr` は関数引数の文脈でしばしば同義として扱われますが、ポインタのポインタとして明示的に `**` を使用することで、意図をより明確にしています。これは、Go言語のポインタの扱いに近づけるための、型表現の統一化の一環と考えられます。特に、`src/cmd/gc/typecheck.c` 内の `fielddup`, `keydup`, `indexdup` 関数でこの変更が適用されています。

3.  **`array.c` APIの `int32` から `int` への変更**:
    `src/cmd/gc/array.c` は、コンパイラ内部で動的な配列（Goのスライスに相当する概念）を管理するためのユーティリティ関数を提供しています。このコミットでは、`arraynew`, `arraylength`, `arrayget`, `arrayset`, `ensurecapacity` といった関数の引数や戻り値の型が `int32` から `int` に変更されています。これは、Go言語のスライスがインデックスに`int`型を使用することに合わせたもので、Go言語への変換時に型の一貫性を保つための重要な変更です。C言語の`int`型は、Go言語の`int`型と同様に、ターゲットアーキテクチャのネイティブなワードサイズ（32ビットまたは64ビット）に最適化された整数型として扱われることが多いため、この変更はより自然なGoコードへの移行を促進します。

4.  **`strlit` から `newstrlit` へのリネーム**:
    `src/cmd/gc/go.h` で定義されている `strlit` 関数が `newstrlit` にリネームされ、それに伴い呼び出し箇所もすべて変更されています。コミットメッセージには「`Strlit` との大文字・小文字を区別しない衝突を避けるため」と明記されています。これは、C言語の構造体 `Strlit` と関数 `strlit` が、一部のファイルシステムやツールチェーンで大文字・小文字を区別しない場合に名前の衝突を引き起こす可能性があったためです。Go言語は厳密に大文字・小文字を区別するため、このリネームはGo言語への移行を見据えた命名規則の整理と、潜在的なビルド環境依存の問題を回避するための措置です。

5.  **`printf` フォーマットの修正**:
    `src/cmd/gc/dcl.c` と `src/cmd/gc/subr.c` で、`fatal` 関数内で使用されている `printf` フォーマット指定子が修正されています。例えば、`fatal("addmethod: not TFIELD: %N", f);` が `fatal("addmethod: not TFIELD: %lT", f);` に、`fatal("brcom: no com for %A\\n", a);` が `fatal("brcom: no com for %O\\n", a);` に変更されています。これは、引数 `f` や `a` の型と、それに対応するフォーマット指定子が一致していなかったために発生する可能性のある警告や実行時エラーを修正し、コードの正確性を高めるものです。

6.  **変数名 `len` から `n` または `length` へのリネーム**:
    `src/cmd/gc/plive.c` や `src/cmd/gc/typecheck.c` などで、`len` という名前の変数が `n` や `length` に変更されています。Go言語には組み込み関数 `len()` が存在するため、C言語コード内で `len` という変数名を使用すると、Go言語への変換時に混乱や衝突を招く可能性があります。このリネームは、Go言語の慣習に合わせ、将来的な変換の障害を取り除くためのものです。

7.  **直接的な文字列編集による名前構築の排除**:
    `src/cmd/gc/walk.c` では、`convI2T` や `assertI2T` のような関数名を文字列操作で直接構築していた箇所が、より構造化された方法（例: `snprint` を使用して `from` と `to` の文字列を結合する）に変更されています。これは、文字列操作の安全性を高め、コードの可読性を向上させるとともに、Go言語の文字列操作のイディオムに近づけるための変更です。C言語の `strcpy` や `strcat` はバッファオーバーフローのリスクがあるため、より安全な `snprintf` のような関数への移行は良いプラクティスです。

これらの変更は、個々には小さいものですが、全体としてGoコンパイラのC言語コードベースをGo言語への移行に向けて体系的に準備し、将来的なメンテナンスコストを削減するための重要なステップでした。

## コアとなるコードの解説

上記のコードスニペットは、Goコンパイラの内部で使われる動的配列（`Array`構造体）を操作する関数群の変更を示しています。

*   **`arraynew(int32 capacity, int32 size)` から `arraynew(int capacity, int32 size)`**:
    `arraynew` 関数は新しい`Array`オブジェクトを初期化します。ここで、配列の容量を示す `capacity` 引数の型が `int32` から `int` に変更されています。これは、Go言語のスライスが容量や長さを表現する際に `int` 型を使用することに合わせたものです。Go言語の `int` 型は、実行環境のアーキテクチャ（32ビットまたは64ビット）に応じて適切なサイズを持つため、より汎用的な表現となります。`size` 引数（各要素のサイズ）は引き続き `int32` ですが、これは要素のバイトサイズを表すため、固定幅の型が適切であると判断されたためと考えられます。

*   **`int32 arraylength(Array *array)` から `int arraylength(Array *array)`**:
    `arraylength` 関数は配列の現在の長さを返します。この戻り値の型も `int32` から `int` に変更されています。これもGo言語の `len()` 関数が `int` を返すこととの整合性を取るためです。

*   **`arrayget(Array *array, int32 index)` から `arrayget(Array *array, int index)`**:
    `arrayget` 関数は指定されたインデックスの要素を取得します。インデックスを示す `index` 引数の型が `int32` から `int` に変更されています。Go言語のスライスアクセスも `int` 型のインデックスを使用するため、この変更は自然な対応です。

*   **`arrayset(Array *array, int32 index, void *element)` から `arrayset(Array *array, int index, void *element)`**:
    `arrayset` 関数は指定されたインデックスに要素を設定します。ここでも `index` 引数の型が `int32` から `int` に変更されています。

*   **`ensurecapacity(Array *array, int32 capacity)` から `ensurecapacity(Array *array, int capacity)`**:
    `ensurecapacity` 関数は配列の容量を確保します。`capacity` 引数の型が `int32` から `int` に変更されています。

これらの変更は、GoコンパイラのC言語部分がGo言語のスライスとより密接に連携できるようにするための基盤を築いています。C言語の `int` 型は、通常、プラットフォームのネイティブな整数サイズにマップされるため、Go言語の `int` 型（これもプラットフォーム依存のサイズ）との互換性が高まります。これにより、将来的にこれらのC言語の配列操作コードがGo言語に自動変換される際に、型変換の複雑さを軽減し、より自然で効率的なGoコードが生成されることが期待されます。

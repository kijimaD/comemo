## 前提知識の解説

*   **Cgo**: Go言語とC言語のコードを相互に呼び出すためのGoの機能です。GoプログラムからCライブラリの関数を呼び出したり、CコードからGoの関数を呼び出したりすることができます。Cgoは、Goの標準ライブラリの一部として提供されており、Goプログラムが既存のCライブラリを利用する際に不可欠なツールです。
*   **共有ライブラリ (Shared Library / Dynamic Link Library - DLL/SO)**: 複数のプログラムから共有して利用できるライブラリのことです。WindowsではDLL (Dynamic Link Library)、Unix系システムではSO (Shared Object) と呼ばれます。プログラムの実行時にロードされ、メモリを効率的に利用できる利点があります。Cgoでは、Goプログラムがこれらの共有ライブラリをロードし、その中の関数や変数にアクセスすることが可能です。
*   **Go Issue 4339**: このコミットがリバートした元の変更が修正しようとしていた問題です。GoのIssueトラッカーで管理されている特定のバグや機能リクエストを指します。この場合、Cgoと共有ライブラリの連携、特にWindows環境でのCのグローバル変数へのアクセスに関する問題であったと推測されます。
*   **ビルドブロークン (Broken Builders)**: 継続的インテグレーション（CI）システムにおいて、コードの変更が原因でビルドプロセスが失敗する状態を指します。これは、コンパイルエラー、リンクエラー、テストの失敗など、様々な形で現れます。ビルドが壊れると、その後の開発が滞るため、迅速な対応が求められます。
*   **リバート (Revert)**: バージョン管理システム（Gitなど）において、特定のコミットで行われた変更を元に戻す操作です。リバートコミットは、元のコミットの変更を打ち消す新しいコミットを作成します。これにより、履歴をきれいに保ちつつ、問題のある変更を安全に取り消すことができます。

これらの変更は、Cgoを介したCの共有ライブラリからの変数エクスポートと、それに対するGo側からのアクセスをテストするメカニズム全体を元に戻すものです。特に、Windows環境でのDLLのエクスポート/インポートメカニズムに関連するコードが削除されていることから、元の問題（Issue 4339）がWindows特有のCgoの挙動に関連していた可能性が高いです。

## コアとなるコードの変更箇所

このコミットはリバートであるため、元のコミットで追加されたコードを削除しています。コアとなる変更箇所は、Cgoを介してCの共有ライブラリからGoに値をエクスポートし、Go側でそれを利用するテストロジックが削除された点です。

具体的には、以下のファイルが影響を受けています。

*   `misc/cgo/testso/cgoso.c`: `getVar()`関数の削除とヘッダーインクルードの削除。
*   `misc/cgo/testso/cgoso.go`: `testExportedVar()`関数の削除、Cgoディレクティブの変更、C関数宣言の削除。
*   `misc/cgo/testso/cgoso_c.c`: `exported_var`グローバル変数の削除とヘッダーインクルードの削除。
*   `misc/cgo/testso/cgoso_c.h`: ファイル全体の削除。
*   `misc/cgo/testso/test.bat`: ビルドスクリプトの変更。

これらの変更により、`exported_var`というCのグローバル変数をCgo経由でGoからアクセスするテストが完全に削除されました。

## コアとなるコードの解説

このリバートコミットは、特定の機能を追加するのではなく、既存の機能（以前のコミットで追加されたテスト）を削除しています。したがって、「コアとなるコードの解説」は、削除されたコードが何を行っていたのか、そしてなぜそれが削除されたのかに焦点を当てます。

削除されたコードの核心は、Cgoを使ってCの共有ライブラリ（`libcgosotest.dll` / `libcgosotest.so`）から`exported_var`というCのグローバル変数をGoプログラムに公開し、Go側でその値が正しく読み取れることを検証するテストでした。

1.  **`cgoso_c.h` (削除されたファイル)**:
    このヘッダーファイルは、`exported_var`という`const char*`型の変数を宣言していました。特にWindows環境では、`__declspec(dllexport)`や`__declspec(dllimport)`といったマクロを使って、DLLからのエクスポートやDLLへのインポートを明示的に指定していました。これは、WindowsのDLLがシンボルをエクスポート/インポートする際の標準的なメカニズムです。

2.  **`cgoso_c.c` (変更されたファイル)**:
    このファイルでは、`exported_var`が`"Hello world"`という文字列で初期化されていました。この変数が共有ライブラリの一部としてコンパイルされ、Goプログラムからアクセスされることを意図していました。

3.  **`cgoso.c` (変更されたファイル)**:
    `getVar()`関数が定義されており、これは単に`exported_var`の値を返していました。Go側からはこの`getVar()`関数を呼び出すことで、`exported_var`の値を取得することができました。

4.  **`cgoso.go` (変更されたファイル)**:
    Go側では、`import "C"`を使ってCgoを有効にし、Cの関数や変数にアクセスしていました。
    *   `#cgo windows CFLAGS: -DIMPORT_DLL` は、WindowsでDLLをインポートする際に必要なコンパイルフラグでした。
    *   `const char* getVar(void);` は、Cの`getVar`関数をGoから呼び出すための宣言でした。
    *   `testExportedVar()`関数は、`C.GoString(C.getVar())`や`C.GoString(C.exported_var)`を使って、Cからエクスポートされた変数の値を取得し、期待される値（"Hello world"）と比較していました。これにより、Cgoを介したC変数のアクセスが正しく行われるかを検証していました。

この一連のコードは、GoとCの共有ライブラリ間でデータをやり取りする、特にCのグローバル変数をGoから参照するという、Cgoの高度な機能のテストケースでした。しかし、このテストがDarwinとNetBSDのビルドを壊したため、一時的に削除されました。これは、異なるOS環境でのCgoの挙動や、共有ライブラリのリンクメカニズムにプラットフォーム間の差異があり、それが問題を引き起こした可能性を示唆しています。

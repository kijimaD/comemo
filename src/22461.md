# [インデックス 22461] ファイルの概要

このコミットは、Go言語の `crypto/tls` パッケージにおける重要なバグ修正と機能改善に関するものです。具体的には、TLS 1.2ハンドシェイク中にクライアント証明書を使用する際に、正しいハッシュ関数が選択されない問題を解決し、SHA384ハッシュ関数を使用する新しいテストケースを追加しています。

## 元コミット内容

このコミットは、以前のコミット `f1d669aee994b28e1afcfe974680565932d25b70` によって導入された問題の修正です。元のコミットは、RFC 5289で定義された `AES_256_GCM_SHA384` 暗号スイートのサポートを追加しましたが、TLSクライアントハンドシェイクでクライアント証明書を使用する際に、任意のハッシュ関数を考慮していませんでした。

## 変更の背景

TLS (Transport Layer Security) プロトコルにおいて、クライアント証明書を用いた認証は、サーバーがクライアントの身元を確認するための重要なメカニズムです。この認証プロセスでは、クライアントは自身の秘密鍵を用いてハンドシェイクメッセージのハッシュに署名し、その署名をサーバーに送信します。サーバーはこの署名をクライアントの公開鍵で検証することで、クライアントが秘密鍵の正当な所有者であることを確認します。

問題は、Goの `crypto/tls` パッケージが、TLS 1.2ハンドシェイク中にクライアント証明書に署名する際に、常にSHA256ハッシュ関数を使用すると仮定していた点にありました。しかし、RFC 5289で導入された `AES_256_GCM_SHA384` のような新しい暗号スイートでは、SHA384のような異なるハッシュ関数が使用されることがあります。

`hashForClientCertificate` メソッドが、実際にダイジェストの計算に使用されたハッシュ関数とは異なるSHA256を返していたため、クライアント証明書による署名検証が失敗し、「`tls: failed to sign handshake with client certificate: crypto/rsa: input must be hashed message`」というエラーが発生していました。このエラーは、RSA署名関数が、期待されるハッシュ化された入力ではなく、不適切な形式のデータを受け取ったことを示しています。RSA署名アルゴリズムは、メッセージ全体ではなく、メッセージの暗号学的ハッシュに署名するように設計されているため、入力が正しくハッシュ化されていることが不可欠です。

このコミットは、この不整合を修正し、クライアント証明書に署名する際に、実際に使用されたハッシュ関数（例えばSHA384）を正しく返すようにすることで、TLSハンドシェイクが正常に完了するようにします。

## 前提知識の解説

*   **TLS (Transport Layer Security)**: インターネット上で安全な通信を行うための暗号化プロトコルです。ウェブブラウザとサーバー間のHTTPS通信などで広く利用されています。
*   **TLSハンドシェイク**: クライアントとサーバーが安全な通信を開始する前に、互いの身元を確認し、暗号化アルゴリズムや鍵をネゴシエートするプロセスです。
*   **クライアント証明書認証**: サーバーがクライアントの身元を確認するために、クライアントがデジタル証明書を提示し、秘密鍵を用いて署名を行う認証方式です。
*   **暗号スイート (Cipher Suite)**: TLSハンドシェイク中にネゴシエートされる、鍵交換アルゴリズム、認証アルゴリズム、バルク暗号化アルゴリズム、メッセージ認証コード (MAC) アルゴリズムの組み合わせを定義するものです。
*   **RFC 5289**: 「TLS Elliptic Curve Cipher Suites with SHA-256/384 and AES Galois Counter Mode (GCM)」と題されたRFCで、SHA-256/384ハッシュ関数とAES GCMモードを用いた新しい暗号スイートを定義しています。これにより、TLSのセキュリティが強化されました。
    *   **AES_256_GCM_SHA384**: この暗号スイートは以下の要素で構成されます。
        *   **AES (Advanced Encryption Standard) 256**: 256ビットの鍵長を持つ対称ブロック暗号で、データの機密性を提供します。
        *   **GCM (Galois/Counter Mode)**: ブロック暗号の動作モードの一つで、暗号化と認証の両方を提供します。高速で効率的な認証付き暗号化を実現します。
        *   **SHA384 (Secure Hash Algorithm 384)**: 暗号学的ハッシュ関数の一つで、TLS 1.2では擬似乱数関数 (PRF) やメッセージ認証コード (MAC) に使用されます。AES-256のセキュリティレベルと整合性の取れた128ビットの衝突耐性を提供します。
*   **ハッシュ関数**: 任意の長さの入力データから、固定長の出力（ハッシュ値またはダイジェスト）を生成する一方向関数です。データの完全性検証やデジタル署名に利用されます。
*   **デジタル署名**: メッセージの送信者の身元を証明し、メッセージが改ざんされていないことを保証する技術です。送信者はメッセージのハッシュ値を自身の秘密鍵で暗号化（署名）し、受信者は送信者の公開鍵で復号（検証）します。
*   **`crypto/rsa: input must be hashed message` エラー**: Go言語の `crypto/rsa` パッケージでRSA署名を行う際に発生するエラーです。RSA署名関数は、署名対象のデータが事前にハッシュ化されていることを期待しますが、そうでない場合にこのエラーが発生します。

## 技術的詳細

このコミットの核心は、TLS 1.2におけるクライアント証明書の署名プロセスで、正しいハッシュ関数が使用されるようにすることです。

TLS 1.2では、`CertificateVerify` メッセージの署名に使用されるハッシュ関数は、ネゴシエートされた暗号スイートや、クライアント証明書の鍵タイプ（RSA、ECDSAなど）によって決定されます。以前の実装では、`finishedHash` 構造体の `hashForClientCertificate` メソッドが、TLS 1.2の場合に常に `crypto.SHA256` を返していました。これは、`AES_256_GCM_SHA384` のようなSHA384を使用する暗号スイートが選択された場合に問題となります。

修正は以下の点に集中しています。

1.  **`src/crypto/tls/common.go`**:
    *   `hashSHA384 uint8 = 5` という新しい定数が追加されました。これは、TLS 1.2の `HashAlgorithm` フィールドでSHA384を識別するためのIDです。

2.  **`src/crypto/tls/prf.go`**:
    *   `finishedHash` 構造体に `serverHash crypto.Hash` フィールドが追加されました。これは、サーバー側で使用される実際のハッシュ関数を保持するためのものです。
    *   `newFinishedHash` 関数が変更され、TLS 1.2の場合に `finishedHash` 構造体の `serverHash` フィールドが、ネゴシエートされた `tls12Hash` で初期化されるようになりました。これにより、`finishedHash` オブジェクトが、ハンドシェイクで使用される正しいハッシュ関数を認識できるようになります。
    *   `hashForClientCertificate` 関数が修正されました。TLS 1.2の場合、以前は常に `crypto.SHA256` と `hashSHA256` を返していましたが、修正後は `h.serverHash` と `tls12HashID(h.serverHash)` を返すようになりました。これにより、実際にハンドシェイクで使用されているハッシュ関数（例: SHA384）がクライアント証明書の署名プロセスに正しく渡されるようになります。
    *   `tls12HashID` という新しいヘルパー関数が追加されました。この関数は `crypto.Hash` 型のハッシュ関数を受け取り、対応するTLS 1.2の `HashAlgorithm` ID（`hashSHA256` または `hashSHA384`）を返します。これにより、ハッシュ関数とIDのマッピングが明確になります。

3.  **`src/crypto/tls/handshake_client_test.go` と `src/crypto/tls/testdata/Client-TLSv12-ClientCert-RSA-AES256-GCM-SHA384`**:
    *   `ClientCert-RSA-AES256-GCM-SHA384` という新しいテストケースが追加されました。このテストは、SHA384ハッシュ関数を使用する `AES_256_GCM_SHA384` 暗号スイートを用いたクライアント証明書認証のシナリオを検証します。これにより、修正が正しく機能し、将来的な回帰を防ぐことができます。

これらの変更により、GoのTLS実装は、クライアント証明書認証において、ネゴシエートされた暗号スイートで指定された任意のハッシュ関数を正しく使用できるようになり、互換性と堅牢性が向上しました。

## コアとなるコードの解説

*   **`src/crypto/tls/common.go` の変更**:
    *   `hashSHA384` 定数の追加は、TLS 1.2の `HashAlgorithm` フィールドでSHA384を識別するために必要です。これにより、TLSプロトコル内でSHA384ハッシュ関数を明示的に参照できるようになります。

*   **`src/crypto/tls/prf.go` の変更**:
    *   `finishedHash` 構造体への `serverHash crypto.Hash` フィールドの追加は、ハンドシェイク中にサーバー側で実際に使用されるハッシュ関数を `finishedHash` オブジェクトが内部的に保持できるようにするためのものです。これにより、`hashForClientCertificate` メソッドが、ハードコードされたSHA256ではなく、この動的な値を使用できるようになります。
    *   `newFinishedHash` 関数での `serverHash` の初期化は、TLS 1.2ハンドシェイクの開始時に、ネゴシエートされたハッシュ関数（`tls12Hash`）を `finishedHash` オブジェクトに正しく設定することを保証します。
    *   `hashForClientCertificate` 関数の修正は、このコミットの最も重要な部分です。以前は、TLS 1.2の場合に常に `crypto.SHA256` を返していましたが、変更後は `h.serverHash` を返すようになりました。これにより、クライアント証明書の署名に使用されるハッシュ関数が、実際にネゴシエートされた暗号スイート（例: `AES_256_GCM_SHA384` の場合はSHA384）と一致するようになります。これは、RSA署名が特定のハッシュアルゴリズムのダイジェストを期待するため、非常に重要です。
    *   `tls12HashID` ヘルパー関数の導入は、`crypto.Hash` 型のハッシュ関数と、TLS 1.2プロトコルで定義されている対応する `HashAlgorithm` IDとの間のマッピングをカプセル化します。これにより、コードの可読性と保守性が向上します。

*   **`src/crypto/tls/handshake_client_test.go` の変更**:
    *   新しいテストケース `ClientCert-RSA-AES256-GCM-SHA384` の追加は、この修正が正しく機能することを検証するために不可欠です。このテストは、SHA384ハッシュ関数を使用する特定の暗号スイートでクライアント証明書認証が成功することを確認します。これにより、バグの再発を防ぎ、GoのTLS実装の堅牢性を高めます。

これらの変更は、Goの `crypto/tls` パッケージがTLS 1.2の仕様に完全に準拠し、より広範な暗号スイートとハッシュ関数の組み合わせを正しく処理できるようにするために不可欠でした。

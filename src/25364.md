# [インデックス 25364] ファイルの概要

このコミットは、Goランタイムにおけるスタック走査のパフォーマンスを向上させるために、`pcvalue`ルックアップにキャッシュ機構を追加するものです。特に、深い再帰的なスタックを持つプログラムにおいて、スタック走査の速度が大幅に改善されます。

    runtime: add pcvalue cache to improve stack scan speed

    The cost of scanning large stacks is currently dominated by the time
    spent looking up and decoding the pcvalue table. However, large stacks
    are usually large not because they contain calls to many different
    functions, but because they contain many calls to the same, small set
    of recursive functions. Hence, walking large stacks tends to make the
    same pcvalue queries many times.

    Based on this observation, this commit adds a small, very simple, and
    fast cache in front of pcvalue lookup. We thread this cache down from
    operations that make many pcvalue calls, such as gentraceback, stack
    scanning, and stack adjusting.

    nicht effective. I also tried a hashed direct-map cache, CLOCK-based
    replacement, round-robin replacement, and round-robin with lookups
    disabled until there had been at least 16 probes, but none of these
    approaches had obvious wins over the random replacement policy in this
    commit.

## 元コミット内容

Goランタイムにおいて、スタック走査の速度を向上させるために`pcvalue`ルックアップにキャッシュを追加します。特に、深いスタックを持つプログラムでは、同じ再帰関数が何度も呼び出されるため、`pcvalue`の問い合わせが繰り返し発生します。このコミットでは、この観察に基づき、小さくシンプルなキャッシュを`pcvalue`ルックアップの前に導入します。このキャッシュは、`gentraceback`、スタック走査、スタック調整など、多くの`pcvalue`呼び出しを行う操作からスレッド経由で渡されます。

このシンプルなキャッシュは、効果がない場合でもオーバーヘッドが最小限であるため、うまく機能します。コミットメッセージでは、ハッシュ化されたダイレクトマップキャッシュ、CLOCKベースの置換、ラウンドロビン置換、および16回以上のプローブがあるまでルックアップを無効にするラウンドロビンなど、他のアプローチも試されたが、このコミットで採用されたランダム置換ポリシーよりも明確な利点を持つものはなかったと述べられています。

この変更により、issue #10898の深いスタックテストプログラムの全体的なパフォーマンスが約2倍に向上しました（16.5秒から9.2秒へ44.37%改善）。ガベージベンチマークではわずかな改善（-0.75%）が見られ、go1ベンチマークでは特に深いスタックがないため、パフォーマンスに大きな影響はありませんでした（悪影響もありません）。

## 変更の背景

Goランタイムでは、ガベージコレクション（GC）やスタックトレースの生成など、様々な場面で実行中のゴルーチンのスタックを走査する必要があります。このスタック走査の過程で、各スタックフレームのPC（プログラムカウンタ）に対応するメタデータ（例えば、スタックマップのインデックスや関数名、ファイル名、行番号など）を`pcvalue`テーブルからルックアップし、デコードする処理が頻繁に発生します。

特に、再帰的な関数呼び出しが多用されるプログラムや、非常に深いスタックを持つプログラムでは、同じ関数の`pcvalue`情報が何度も繰り返し要求されることが観測されていました。このような状況では、`pcvalue`テーブルのルックアップとデコードがスタック走査全体のボトルネックとなり、パフォーマンスを著しく低下させていました。

このコミットの目的は、この`pcvalue`ルックアップのオーバーヘッドを削減し、特に深いスタックを持つプログラムにおけるスタック走査の効率を向上させることにあります。

## 前提知識の解説

### GoランタイムのスタックとPC（プログラムカウンタ）

Goの各ゴルーチンは独自のスタックを持っています。スタックは関数呼び出しの情報を格納し、各スタックフレームには呼び出し元のPC（プログラムカウンタ）が含まれます。PCは現在実行中の命令のアドレスを示します。

### `pcvalue`テーブル

Goのバイナリには、実行時のPC値から様々なメタデータ（例えば、スタックマップ、関数名、ファイル名、行番号など）を効率的に取得するための`pcvalue`テーブルと呼ばれるデータ構造が含まれています。これらのテーブルは、コンパイル時に生成され、ランタイムがスタックを走査する際に利用されます。

*   **`_PCDATA_StackMapIndex`**: スタックフレーム内のポインタの位置を示すスタックマップのインデックスを決定するために使用される`pcvalue`テーブルの一種です。ガベージコレクタがスタック上のポインタを正確に識別するために不可欠です。
*   **`_func`構造体**: Goランタイムが関数に関するメタデータを格納するために使用する内部構造体です。関数のエントリポイント、PCデータテーブルへのオフセット（`pcfile`, `pcln`, `pcsp`など）などが含まれます。
*   **`pcfile`, `pcln`, `pcsp`**: `_func`構造体内のフィールドで、それぞれファイル名、行番号、スタックポインタのデルタ（スタックフレームのサイズ）に関する`pcvalue`テーブルへのオフセットを示します。

### スタック走査とガベージコレクション

Goのガベージコレクタは、到達可能なオブジェクトを特定するために、実行中のすべてのゴルーチンのスタックを走査します。この際、各スタックフレーム内のどの位置にポインタが存在するかを正確に知る必要があります。この情報は`_PCDATA_StackMapIndex`に対応する`pcvalue`テーブルから取得されます。スタック走査はGCの重要なフェーズであり、その効率はGCの一時停止時間（STW: Stop-The-World）に直接影響します。

### `gentraceback`

`gentraceback`関数は、スタックトレースを生成するためのGoランタイムの内部関数です。デバッグ情報やパニック発生時などに呼び出され、スタックフレームを一つずつ遡りながら、各フレームのPCに対応する関数情報などを取得します。この処理も`pcvalue`ルックアップを多用します。

## 技術的詳細

このコミットの核心は、`pcvalue`ルックアップの前に導入された`pcvalueCache`です。

### `pcvalueCache`構造体

```go
type pcvalueCache struct {
	entries [16]pcvalueCacheEnt
}

type pcvalueCacheEnt struct {
	// targetpc and off together are the key of this cache entry.
	targetpc uintptr
	off      int32
	// val is the value of this cached pcvalue entry.
	val int32
}
```

*   `pcvalueCache`は、`pcvalueCacheEnt`の配列を保持するシンプルな構造体です。配列のサイズは16であり、非常に小さいキャッシュであることがわかります。
*   `pcvalueCacheEnt`は、キャッシュエントリのキーと値を定義します。
    *   `targetpc`: プログラムカウンタの値。
    *   `off`: `_func`構造体内の`pcvalue`テーブルへのオフセット（例: `f.pcfile`, `f.pcln`, `f.pcsp`、または`_PCDATA_StackMapIndex`に対応するオフセット）。
    *   `val`: `pcvalue`ルックアップの結果として得られる値。

このキャッシュは、`targetpc`と`off`の組み合わせをキーとして使用します。これは、同じPCであっても異なる種類の`pcvalue`情報（ファイル名、行番号、スタックマップなど）をルックアップする可能性があるためです。

### キャッシュの動作原理

1.  **キャッシュチェック**: `pcvalue`関数が呼び出されると、まず`pcvalueCache`が渡されているかを確認します。キャッシュが利用可能な場合、`cache.entries`内の既存のエントリを線形探索し、`ent.off == off && ent.targetpc == targetpc`が一致するエントリがあるかを確認します。
2.  **キャッシュヒット**: 一致するエントリが見つかった場合（キャッシュヒット）、そのエントリの`val`が直接返されます。これにより、高コストな`pcvalue`テーブルのデコード処理をスキップできます。
3.  **キャッシュミスと置換**: キャッシュミスが発生した場合、通常の`pcvalue`ルックアップとデコード処理が実行されます。結果として得られた`val`は、キャッシュに格納されます。
    *   **ランダム置換ポリシー**: キャッシュに新しいエントリを追加する際、`cache.entries`内のランダムなインデックス（`fastrand1() % uint32(len(cache.entries))`で決定）のエントリが新しいエントリで上書きされます。
    *   このランダム置換は、特定のアクセスパターンによるパフォーマンスの偏りを避けるための選択です。コミットメッセージによると、他の複雑な置換ポリシー（ハッシュ化されたダイレクトマップ、CLOCKベース、ラウンドロビンなど）も試されたが、このシンプルなランダム置換が最も効果的であったか、少なくとも他のアプローチよりも明確な利点を示さなかったとされています。特に、再帰的なスタックのサイクルがキャッシュサイズよりわずかに大きい場合にパフォーマンスが急激に低下する「パフォーマンスクリフ」を防ぐ効果があります。

### キャッシュの伝播

この`pcvalueCache`は、`gentraceback`、スタック走査（`scanstack`）、スタック調整（`adjustinfo`）など、`pcvalue`ルックアップを頻繁に行う主要なランタイム操作に引数として渡されるように変更されています。これにより、これらの操作全体でキャッシュが共有され、再帰的な呼び出しや繰り返し発生するルックアップの効率が向上します。

## コアとなるコードの解説

このコミットの主要な変更は、`src/runtime/symtab.go` に`pcvalueCache`構造体とそのロジックが追加されたことです。

`pcvalue`関数は、特定のPCとオフセットに基づいて`pcvalue`テーブルから値を取得するGoランタイムの重要な関数です。この関数は、スタック走査、トレースバック、デバッグ情報の取得など、多くの場面で呼び出されます。

新しい`pcvalue`関数の実装では、`cache *pcvalueCache`という引数が追加されました。この引数が`nil`でない場合、関数はまずこのキャッシュをチェックします。

1.  **キャッシュヒットの処理**:
    `cache.entries`配列をループし、現在の`targetpc`と`off`の組み合わせに一致するエントリがあるかを確認します。
    `ent.off == off && ent.targetpc == targetpc`が真であれば、キャッシュヒットと判断し、`ent.val`を即座に返します。これにより、`pcvalue`テーブルのデコード処理という比較的コストの高い操作を回避できます。

2.  **キャッシュミスの処理と更新**:
    キャッシュミスの場合、通常の`pcvalue`テーブルのデコードロジックが実行され、`val`が計算されます。
    計算された`val`は、`pcvalueCache`に格納されます。この際、`fastrand1() % uint32(len(cache.entries))`を使用してランダムに選択されたインデックスのエントリが新しい値で上書きされます。このランダム置換ポリシーは、特定のアクセスパターンによるキャッシュの効率低下（例えば、キャッシュサイズよりわずかに大きいループを持つ再帰関数）を防ぐために採用されています。

このキャッシュは、`gentraceback`、`scanstack`、`adjustframe`などの関数に引数として渡され、これらの操作全体で共有されます。これにより、これらの操作が深いスタックを走査する際に、同じ`pcvalue`ルックアップが繰り返し発生するのを効率的に削減し、全体的なパフォーマンスを向上させます。

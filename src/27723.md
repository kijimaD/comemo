# [インデックス 27723] ファイルの概要

このコミットでは、Goの標準ライブラリである `net/http` パッケージにおいて、HTTPサーバーが受信するリクエストに `context.Context` を関連付ける機能が導入されました。これにより、サーバーサイドのリクエスト処理中にコンテキストを利用したキャンセル処理や値の伝播が可能になります。

変更されたファイルは以下の通りです。

*   `src/net/http/serve_test.go`: サーバーリクエストのコンテキストが適切にキャンセルされることを検証するための新しいテストケースが追加されました。
*   `src/net/http/server.go`: サーバーが受信したリクエストに対して `context.Context` を生成し、リクエストに紐付け、適切なタイミングでキャンセルするロジックが実装されました。

## 変更の背景

このコミットの主な背景には、Goの `net/http` サーバーが受信するリクエストに対して、クライアントリクエストと同様に `context.Context` を提供する必要性がありました。以前のバージョンでは、サーバーリクエストには `context.Context` が直接関連付けられておらず、リクエストのライフサイクル（タイムアウト、キャンセル、リクエスト固有の値の伝播など）を管理するための標準的なメカニズムが不足していました。

具体的には、以下のGitHub Issueがこの変更の動機となっています。

*   **Issue #13021: net/http: Request.Context for server requests**: このIssueでは、サーバーリクエストにも `context.Context` を導入し、リクエストの処理中にキャンセルシグナルを伝播できるようにすることが提案されていました。これにより、例えばクライアントが接続を閉じた場合や、サーバー側で処理がタイムアウトした場合に、ハンドラ内で実行中のゴルーチンを安全に停止できるようになります。
*   **Issue #15224: net/http: context for server requests should be canceled when client closes connection**: このIssueは、特にクライアントが接続を閉じた際に、サーバーリクエストのコンテキストがキャンセルされるべきであるという具体的な要件を提起しています。これにより、リソースリークを防ぎ、不要な処理を停止させることが可能になります。

これらの課題に対応するため、`net/http` パッケージのサーバーサイドで `context.Context` を適切に生成し、リクエストに紐付け、リクエストの終了時やクライアント接続の切断時にキャンセルするメカニズムが導入されました。

## 前提知識の解説

### `context.Context` とは

Go言語における `context.Context` は、API境界を越えてデッドライン、キャンセルシグナル、およびリクエストスコープの値を伝播するためのインターフェースです。主に、複数のゴルーチンにまたがる処理において、以下のような目的で使用されます。

1.  **キャンセルシグナル**: 親の操作がキャンセルされた場合、子操作もキャンセルされるようにシグナルを伝播します。これにより、不要な計算やネットワークリクエストを停止し、リソースを解放できます。
2.  **デッドライン/タイムアウト**: 操作が完了すべき時間や期間を設定し、その時間を過ぎた場合に自動的にキャンセルシグナルを発生させます。
3.  **値の伝播**: リクエストID、認証情報、トレース情報など、リクエスト固有の値をAPI呼び出しチェーン全体で安全に伝播させます。

`context.Context` はイミュータブルであり、`context.Background()` または `context.TODO()` から派生させ、`context.WithCancel()`, `context.WithDeadline()`, `context.WithTimeout()`, `context.WithValue()` などの関数を使って新しいコンテキストを作成します。これらの関数は、新しい `Context` と、そのコンテキストをキャンセルするための `CancelFunc` を返すことがあります。

### `net/http` における `context.Context` の利用

Goの `net/http` パッケージでは、クライアントリクエスト（`http.Client` を使用して送信されるリクエスト）において、`Request.WithContext()` メソッドを通じてコンテキストを設定することが以前から可能でした。これにより、クライアントはリクエストのタイムアウトやキャンセルを制御できました。

しかし、サーバーリクエスト（`http.Server` が受信するリクエスト）においては、`Request` オブジェクトに直接関連付けられたコンテキストが存在せず、ハンドラ内でリクエストのライフサイクルを管理するための統一された方法がありませんでした。このコミットは、このギャップを埋めることを目的としています。

## 技術的詳細

このコミットの核心は、`net/http` サーバーが受信した各HTTPリクエストに対して、専用の `context.Context` を生成し、そのライフサイクルを管理することにあります。

1.  **コンテキストの生成**:
    `(*conn).serve()` メソッド内で、新しいHTTP/1.xリクエストの処理が開始される前に、`context.Background()` を基点として `context.WithCancel(baseCtx)` が呼び出されます。これにより、新しい `context.Context` と、それをキャンセルするための `cancelCtx` 関数が生成されます。この `cancelCtx` は、リクエストの処理が終了した際に呼び出されるように `defer cancelCtx()` として登録されます。

2.  **リクエストへのコンテキストの紐付け**:
    `(*conn).readRequest()` メソッドが変更され、引数として親コンテキスト（`(*conn).serve()` で生成されたもの）を受け取るようになりました。`readRequest` の内部で、この親コンテキストを基に再度 `context.WithCancel(ctx)` が呼び出され、リクエスト固有のコンテキストが生成されます。このリクエスト固有のコンテキストは、`*http.Request` 構造体の内部フィールド `ctx` に設定されます。また、このリクエスト固有のコンテキストをキャンセルするための `cancelCtx` 関数は、`*http.response` 構造体の新しいフィールド `cancelCtx` に保存されます。

3.  **コンテキストのキャンセル**:
    リクエストの処理が `serverHandler{c.server}.ServeHTTP(w, w.req)` を通じて完了した後、`w.cancelCtx()` が呼び出されます。これにより、`ServeHTTP` メソッドが終了した時点で、そのリクエストに紐付けられた `context.Context` がキャンセルされます。これにより、ハンドラ内でこのコンテキストを監視しているゴルーチンは、リクエスト処理の終了を検知し、適切にクリーンアップ処理を行うことができます。

4.  **`Request.Context()` メソッドの更新**:
    `*http.Request` の `Context()` メソッドのドキュメントが更新され、サーバーリクエストにおけるコンテキストの振る舞いが明記されました。具体的には、「受信サーバーリクエストの場合、クライアントの接続が閉じられたとき、または `ServeHTTP` メソッドが戻ったときにコンテキストがキャンセルされる」と記述されています。ただし、このコミット時点では、クライアント接続のクローズによるキャンセルはまだ完全に実装されておらず、Issue #15224 として追跡されています。

この変更により、GoのHTTPサーバーハンドラは `r.Context()` を呼び出すことで、現在処理中のリクエストに紐付けられたコンテキストにアクセスできるようになり、タイムアウト、キャンセル、リクエスト固有の値の伝播といった高度なリクエスト管理が可能になりました。

## コアとなるコードの解説

このコミットの主要な変更は、`net/http` サーバーが各受信リクエストに対して `context.Context` をどのように生成し、管理するかという点に集約されます。

1.  **`response` 構造体への `cancelCtx` の追加**:
    `response` 構造体は、HTTPリクエストに対するサーバーの応答を管理する内部構造です。ここに `cancelCtx context.CancelFunc` を追加することで、各リクエストに固有のコンテキストをキャンセルするためのフックが用意されました。`ServeHTTP` メソッドが完了した際に、この `cancelCtx` を呼び出すことで、リクエストに関連するすべてのゴルーチンにキャンセルシグナルを伝播させることが可能になります。

2.  **`(*conn).readRequest(ctx context.Context)` の変更**:
    `readRequest` は、クライアントからの新しいHTTPリクエストを読み込む役割を担います。この関数が親コンテキスト `ctx` を受け取るようになったことで、コネクションレベルのコンテキストからリクエストレベルのコンテキストを派生させることが可能になりました。
    `ctx, cancelCtx := context.WithCancel(ctx)` の行では、新しいリクエスト固有のコンテキストが生成されます。このコンテキストは `req.ctx = ctx` によって `http.Request` オブジェクトに設定され、ハンドラから `r.Context()` を通じてアクセスできるようになります。また、生成された `cancelCtx` は `w.cancelCtx = cancelCtx` によって `response` オブジェクトに保存され、後でキャンセルするために使用されます。

3.  **`(*conn).serve()` におけるコンテキストのライフサイクル管理**:
    `serve()` メソッドは、単一のTCPコネクション上で複数のHTTPリクエストを処理するループを担当します。このループの開始時に `baseCtx := context.Background()` から `ctx, cancelCtx := context.WithCancel(baseCtx)` を使ってコネクションレベルのコンテキストが生成され、`defer cancelCtx()` によってコネクションが閉じられる際にこのコンテキストがキャンセルされるように設定されます。
    このコネクションレベルのコンテキストは、`c.readRequest(ctx)` を呼び出す際に引数として渡されます。これにより、各リクエスト固有のコンテキストは、コネクション全体のコンテキストの子として機能し、コネクションが閉じられた場合にもリクエストがキャンセルされる可能性が生まれます（ただし、このコミット時点では #15224 の課題が残っています）。
    最も重要な変更は、`serverHandler{c.server}.ServeHTTP(w, w.req)` の呼び出し直後に `w.cancelCtx()` が追加されたことです。これは、HTTPハンドラがリクエストの処理を終えて戻った直後に、そのリクエストに紐付けられたコンテキストをキャンセルすることを保証します。これにより、ハンドラ内で起動されたゴルーチンが、リクエストの完了を検知してクリーンアップやリソース解放を行うための信頼できるメカニズムが提供されます。

4.  **テストケースの追加**:
    `TestServerRequestContextCancel_ServeHTTPDone` は、`ServeHTTP` が完了した後にリクエストコンテキストがキャンセルされることを検証します。これは、`w.cancelCtx()` の呼び出しが正しく機能していることを確認するための重要なテストです。
    `TestServerRequestContextCancel_ConnClose` は、クライアント接続が閉じられたときにリクエストコンテキストがキャンセルされるべきであるという、より複雑なシナリオをテストしようとしますが、このコミット時点ではまだ `t.Skip` されています。これは、サーバーが常に接続から読み取りを行うように変更されるまで、この機能が完全に動作しないためです（Issue #15224 に関連）。

これらの変更により、Goの `net/http` サーバーは、より堅牢でリソース効率の良いリクエスト処理をサポートするための基盤を確立しました。ハンドラは、リクエストのライフサイクルを `context.Context` を通じてより細かく制御できるようになり、タイムアウト処理、シャットダウン時のクリーンな終了、リクエスト固有のデータ伝播などが容易になります。

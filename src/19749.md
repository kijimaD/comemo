このコミットは、Go言語のリンカーライブラリである`liblink`内の`pcln.c`ファイルにおける、`pcdata`の比較処理に関するバグ修正です。具体的には、ビットマスクのチェックに使用されていた条件式における演算子の優先順位の問題を解決しています。

## 元コミット内容

`liblink: fix precedence bug in pcdata comparison`

このコミットは、`pcdata`の比較における優先順位のバグを修正します。

元のコードでは、`!`演算子が`&1`よりも先に適用されていました。
これにより、関数内で非連続なIDを使用した場合に、不足している`pcdata`テーブルの書き出し時にクラッシュする可能性がありました。
現状では非連続なIDは使用していませんが、念のため修正します。

## 変更の背景

Go言語のコンパイラとリンカーは、実行可能ファイルを生成する際に、プログラムの実行に関する様々なメタデータを埋め込みます。その一つが`pcdata`（Program Counter Data）です。`pcdata`は、ガベージコレクション、スタックトレース、デバッグ情報など、実行時の重要な情報を提供するために、特定のプログラムカウンタ（PC）値に関連付けられたデータです。

`liblink`はGoのリンカーのコアライブラリであり、この`pcdata`テーブルの生成と処理を担当しています。`pcln.c`ファイルは、特にPC-Lineテーブル（プログラムカウンタとソースコードの行番号のマッピング）や`pcdata`テーブルの処理に関連するロジックを含んでいます。

このコミットの背景にある問題は、`pcdata`テーブルの存在をチェックするためのビットマスク操作におけるC言語の演算子優先順位の誤解または見落としです。開発者は、特定の`pcdata`エントリが存在するかどうかをビット単位で確認しようとしましたが、記述された式が意図しない評価順序になっていました。

具体的には、`!(havepc[i/32]>>(i%32))&1`という式が問題でした。C言語では、論理NOT演算子`!`はビットAND演算子`&`よりも高い優先順位を持ちます。このため、開発者が意図した「ビットを抽出し、そのビットが0であるかをチェックする」という動作とは異なる評価が行われる可能性がありました。

コミットメッセージによると、このバグは現在のGoのランタイムの利用方法では直接クラッシュを引き起こすものではなかったものの、将来的に関数内で非連続な`pcdata` IDが使用されるようになった場合には、不足している`pcdata`テーブルの書き出し時にクラッシュする潜在的なリスクがありました。これは、コードの堅牢性を高め、将来の変更に対する安全性を確保するための予防的な修正として行われました。

## 前提知識の解説

### 1. Go言語のツールチェインと`liblink`

Go言語のプログラムは、`go build`コマンドによってコンパイルされ、実行可能ファイルが生成されます。このプロセスには、コンパイラ、アセンブラ、リンカーといった複数のツールが関与します。
- **コンパイラ**: Goのソースコードをアセンブリコードに変換します。
- **アセンブラ**: アセンブリコードをオブジェクトファイル（機械語）に変換します。
- **リンカー**: 複数のオブジェクトファイルやライブラリを結合し、最終的な実行可能ファイルを生成します。

`liblink`は、Goのリンカーが使用する内部ライブラリであり、オブジェクトファイルの結合、シンボル解決、そして実行可能ファイルに必要なメタデータ（`pcdata`など）の配置を担当します。`pcln.c`ファイルは、特にプログラムカウンタと関連するメタデータ（PCDATA）の処理に深く関わっています。

### 2. PCDATA (Program Counter Data)

Goの実行可能ファイルには、ランタイムがプログラムの実行状態を理解するために必要な様々なメタデータが埋め込まれています。`pcdata`はその一種で、特定のプログラムカウンタ（PC）値（つまり、コード内の特定の位置）に関連付けられたデータです。
`pcdata`は主に以下の目的で使用されます。
- **ガベージコレクション (GC)**: GCは、スタック上のポインタを正確に識別する必要があります。`pcdata`は、特定のPCにおいてどのレジスタやスタック上のスロットがポインタを含んでいるかを示す情報を提供します。
- **スタックトレース**: プログラムがパニックを起こしたり、デバッガがアタッチされたりした際に、現在の実行位置から呼び出し元の関数を辿るために使用されます。
- **デバッグ情報**: デバッガがソースコードの行番号と実行可能コードのアドレスをマッピングするために使用します。

`pcdata`は通常、PC値の範囲とそれに対応するデータ値のペアとして表現されます。これにより、ランタイムはPC値に基づいて必要なメタデータを効率的にルックアップできます。

### 3. C言語のビット演算と演算子優先順位

このバグの核心はC言語の演算子優先順位にあります。
- **ビットシフト演算子 (`>>`)**: 右シフト。`A >> B`は、`A`のビットを`B`だけ右にシフトします。これにより、特定のビットを抽出したり、値を2のべき乗で割ったりできます。
- **剰余演算子 (`%`)**: 剰余。`A % B`は、`A`を`B`で割った余りを計算します。ビットマスクの文脈では、配列のインデックスやビット位置を計算するのに使われます。
- **ビットAND演算子 (`&`)**: ビットごとの論理積。`A & B`は、`A`と`B`の対応するビットが両方とも1の場合にのみ1となるビットを生成します。特定のビットをマスクして抽出するのに使われます。例えば、`X & 1`は`X`の最下位ビット（LSB）を抽出します。
- **論理NOT演算子 (`!`)**: 論理否定。`!A`は、`A`が非ゼロ（真）であれば0（偽）を、`A`がゼロ（偽）であれば1（真）を返します。
- **等価演算子 (`==`)**: 等しいかどうかの比較。

**演算子優先順位**: C言語では、演算子には明確な優先順位があります。
高い優先順位から低い優先順位へ（関連する演算子のみ）：
1.  `()` (括弧): 最も高い優先順位で、式の評価順序を明示的に制御します。
2.  `!` (論理NOT): 単項演算子。
3.  `>>` (ビットシフト)
4.  `%` (剰余)
5.  `&` (ビットAND)
6.  `==` (等価)

この優先順位が、元のコードの意図しない動作を引き起こしました。

### 4. `havepc`配列

コードスニペットから推測すると、`havepc`配列は`pcdata`エントリの存在を示すビットマスクとして機能しています。
- `havepc[i/32]`: `i`番目の`pcdata`エントリに対応するビットが含まれる32ビット整数（またはそれ以上のサイズの整数）を配列から取得します。`i/32`は、`i`番目のビットがどの整数に格納されているかを計算します。
- `(i%32)`: `i`番目のビットが、その整数内のどの位置（0から31）にあるかを計算します。

したがって、`havepc[i/32]>>(i%32)`は、`i`番目の`pcdata`エントリに対応するビットを、その整数の最下位ビット位置にシフトして抽出する操作です。この結果は、そのビットが1であれば非ゼロ、0であればゼロになります。

## 技術的詳細

このコミットの技術的詳細は、C言語の演算子優先順位がコードの意図にどのように影響を与え、それがどのように修正されたかに集約されます。

### 元のコードの問題点

元のコードは以下の通りでした。
```c
if(!(havepc[i/32]>>(i%32))&1)
```

この式は、C言語の演算子優先順位に従って以下のように評価されます。

1.  **`havepc[i/32]>>(i%32)`**: まず、`havepc`配列から適切な32ビット整数が選択され、`i%32`ビットだけ右にシフトされます。これにより、`i`番目の`pcdata`エントリに対応するビットが最下位ビット（LSB）に移動します。この結果を`extracted_bit_value`とします。`extracted_bit_value`は、元のビットが1であれば非ゼロ（通常は1）、0であれば0になります。

2.  **`!(extracted_bit_value)`**: 次に、論理NOT演算子`!`が`extracted_bit_value`に適用されます。
    *   もし`extracted_bit_value`が非ゼロ（つまり、元のビットが1）であれば、`!(非ゼロ)`は`0`（偽）になります。
    *   もし`extracted_bit_value`がゼロ（つまり、元のビットが0）であれば、`!(ゼロ)`は`1`（真）になります。
    この結果を`logical_not_result`とします。

3.  **`logical_not_result & 1`**: 最後に、`logical_not_result`と`1`のビットAND演算が行われます。
    *   `logical_not_result`は`0`か`1`のいずれかであるため、`0 & 1`は`0`、`1 & 1`は`1`となります。
    *   したがって、このビットAND演算は実質的に`logical_not_result`の値をそのまま返します。

結果として、元の式`!(havepc[i/32]>>(i%32))&1`は、`i`番目のビットが`0`であれば`1`を返し、`i`番目のビットが`1`であれば`0`を返します。これは、**「`i`番目のビットが0である場合に真」**という条件を評価していることになります。

この動作自体は、ビットが0であるかをチェックするという意図と合致しているように見えます。しかし、問題は、この表現が非常に紛らわしく、将来のコード変更や他の開発者による解釈の際に誤解を招く可能性があったことです。特に、`!`がビット演算の前に適用されるという点が、ビットマスク操作の一般的なイディオムから外れており、バグの温床となり得ました。コミットメッセージが「`!` applies before the `&1`」と明示しているのは、この優先順位の誤解が問題であったことを示唆しています。

### 修正後のコード

修正後のコードは以下の通りです。
```c
if(((havepc[i/32]>>(i%32))&1) == 0)
```

この式は、括弧によって評価順序が明確に制御されています。

1.  **`havepc[i/32]>>(i%32)`**: 元のコードと同様に、`i`番目のビットが最下位ビットにシフトされます。

2.  **`(extracted_bit_value & 1)`**: 次に、このシフトされた値と`1`のビットAND演算が行われます。これにより、`i`番目のビットが正確に抽出され、結果は`0`か`1`のいずれかになります。この結果を`isolated_bit`とします。

3.  **`isolated_bit == 0`**: 最後に、抽出されたビット`isolated_bit`が`0`と等しいかどうかが明示的に比較されます。

この修正により、式は**「`i`番目のビットを抽出し、それが0であるかをチェックする」**という意図を明確かつ安全に表現しています。演算子の優先順位に依存する曖昧さがなくなり、コードの可読性と堅牢性が向上しました。

### 潜在的なクラッシュの可能性

コミットメッセージでは、「This would crash writing out missing pcdata tables if we ever used non-contiguous IDs in a function.」と述べられています。これは、現在のGoのランタイムでは`pcdata`のIDが連続的であるため、このバグが顕在化していなかったことを示唆しています。

しかし、もし将来的に`pcdata`のIDが非連続になった場合、`havepc`ビットマスクの構造や、`i`番目のビットが実際に意味する内容がより複雑になる可能性があります。その際、元の曖昧な条件式が、意図しないビットをチェックしたり、誤った結果を返したりすることで、リンカーが`pcdata`テーブルを正しく生成できなくなり、結果として実行可能ファイルの破損やリンカー自体のクラッシュを引き起こす可能性がありました。

この修正は、現在の動作に影響を与えないものの、将来的なGoのランタイムの進化や、より複雑な`pcdata`の利用シナリオに対する防御的なプログラミングとして非常に重要です。

## コアとなるコードの変更箇所

変更は`src/liblink/pcln.c`ファイルの一箇所のみです。

```diff
--- a/src/liblink/pcln.c
+++ b/liblink/pcln.c
@@ -279,7 +279,7 @@ linkpcln(Link *ctxt, LSym *cursym)

## コアとなるコードの解説

変更された行は、`linkpcln`関数内の`pcdata`処理ループの一部です。

`for(i=0; i<npcdata; i++) { ... }`
このループは、`npcdata`（関数内の`pcdata`エントリの総数）の各`pcdata`エントリを反復処理します。

`if(...) continue;`
この条件文は、特定の`pcdata`エントリが「存在しない」または「処理する必要がない」場合に、現在のループの反復をスキップし、次のエントリに進むためのものです。つまり、条件が真の場合に`continue`が実行されます。

**変更前:**
`if(!(havepc[i/32]>>(i%32))&1)`

この式は、前述の「技術的詳細」セクションで解説したように、`i`番目のビットが`0`である場合に`1`（真）を返します。したがって、この`if`文は「`i`番目の`pcdata`エントリに対応するビットが`0`である場合（つまり、その`pcdata`が存在しない場合）、ループの残りの処理をスキップする」という意味になります。

**変更後:**
`if(((havepc[i/32]>>(i%32))&1) == 0)`

この式も、`i`番目のビットを抽出し（`((havepc[i/32]>>(i%32))&1)`）、その結果が`0`と等しいか（`== 0`）を明示的にチェックしています。これにより、変更前と同じ論理（`i`番目のビットが`0`である場合に真）が、より明確で安全な方法で表現されています。

この`if`文の目的は、`havepc`ビットマスクに基づいて、実際に存在する`pcdata`エントリのみを後続の`funcpctab`関数で処理することです。もしビットが`0`であれば、その`pcdata`エントリは存在しないと見なされ、処理がスキップされます。この修正は、この重要なチェックの信頼性と可読性を向上させるものです。

- **スタックトレース**: プログラムがパニックを起こしたり、デバッガがアタッチされたりした際に、現在の実行位置から呼び出し元の関数を辿るために使用されます。
- **デバッグ情報**: デバッガがソースコードの行番号と実行可能コードのアドレスをマッピングするために使用します。

`pcdata`は通常、PC値の範囲とそれに対応するデータ値のペアとして表現されます。これにより、ランタイムはPC値に基づいて必要なメタデータを効率的にルックアップできます。

### 3. C言語のビット演算と演算子優先順位

このバグの核心はC言語の演算子優先順位にあります。
- **ビットシフト演算子 (`>>`)**: 右シフト。`A >> B`は、`A`のビットを`B`だけ右にシフトします。これにより、特定のビットを抽出したり、値を2のべき乗で割ったりできます。
- **剰余演算子 (`%`)**: 剰余。`A % B`は、`A`を`B`で割った余りを計算します。ビットマスクの文脈では、配列のインデックスやビット位置を計算するのに使われます。
- **ビットAND演算子 (`&`)**: ビットごとの論理積。`A & B`は、`A`と`B`の対応するビットが両方とも1の場合にのみ1となるビットを生成します。特定のビットをマスクして抽出するのに使われます。例えば、`X & 1`は`X`の最下位ビット（LSB）を抽出します。
- **論理NOT演算子 (`!`)**: 論理否定。`!A`は、`A`が非ゼロ（真）であれば0（偽）を、`A`がゼロ（偽）であれば1（真）を返します。
- **等価演算子 (`==`)**: 等しいかどうかの比較。

**演算子優先順位**: C言語では、演算子には明確な優先順位があります。
高い優先順位から低い優先順位へ（関連する演算子のみ）：
1.  `()` (括弧): 最も高い優先順位で、式の評価順序を明示的に制御します。
2.  `!` (論理NOT): 単項演算子。
3.  `>>` (ビットシフト)
4.  `%` (剰余)
5.  `&` (ビットAND)
6.  `==` (等価)

この優先順位が、元のコードの意図しない動作を引き起こしました。

### 4. `havepc`配列

コードスニペットから推測すると、`havepc`配列は`pcdata`エントリの存在を示すビットマスクとして機能しています。
- `havepc[i/32]`: `i`番目の`pcdata`エントリに対応するビットが含まれる32ビット整数（またはそれ以上のサイズの整数）を配列から取得します。`i/32`は、`i`番目のビットがどの整数に格納されているかを計算します。
- `(i%32)`: `i`番目のビットが、その整数内のどの位置（0から31）にあるかを計算します。

したがって、`havepc[i/32]>>(i%32)`は、`i`番目の`pcdata`エントリに対応するビットを、その整数の最下位ビット位置にシフトして抽出する操作です。この結果は、そのビットが1であれば非ゼロ、0であればゼロになります。

## 技術的詳細

このコミットの技術的詳細は、C言語の演算子優先順位がコードの意図にどのように影響を与え、それがどのように修正されたかに集約されます。

### 元のコードの問題点

元のコードは以下の通りでした。
```c
if(!(havepc[i/32]>>(i%32))&1)
```

この式は、C言語の演算子優先順位に従って以下のように評価されます。

1.  **`havepc[i/32]>>(i%32)`**: まず、`havepc`配列から適切な32ビット整数が選択され、`i%32`ビットだけ右にシフトされます。これにより、`i`番目の`pcdata`エントリに対応するビットが最下位ビット（LSB）に移動します。この結果を`extracted_bit_value`とします。`extracted_bit_value`は、元のビットが1であれば非ゼロ（通常は1）、0であれば0になります。

2.  **`!(extracted_bit_value)`**: 次に、論理NOT演算子`!`が`extracted_bit_value`に適用されます。
    *   もし`extracted_bit_value`が非ゼロ（つまり、元のビットが1）であれば、`!(非ゼロ)`は`0`（偽）になります。
    *   もし`extracted_bit_value`がゼロ（つまり、元のビットが0）であれば、`!(ゼロ)`は`1`（真）になります。
    この結果を`logical_not_result`とします。

3.  **`logical_not_result & 1`**: 最後に、`logical_not_result`と`1`のビットAND演算が行われます。
    *   `logical_not_result`は`0`か`1`のいずれかであるため、`0 & 1`は`0`、`1 & 1`は`1`となります。
    *   したがって、このビットAND演算は実質的に`logical_not_result`の値をそのまま返します。

結果として、元の式`!(havepc[i/32]>>(i%32))&1`は、`i`番目のビットが`0`であれば`1`を返し、`i`番目のビットが`1`であれば`0`を返します。これは、**「`i`番目のビットが0である場合に真」**という条件を評価していることになります。

この動作自体は、ビットが0であるかをチェックするという意図と合致しているように見えます。しかし、問題は、この表現が非常に紛らわしく、将来のコード変更や他の開発者による解釈の際に誤解を招く可能性があったことです。特に、`!`がビット演算の前に適用されるという点が、ビットマスク操作の一般的なイディオムから外れており、バグの温床となり得ました。コミットメッセージが「`!` applies before the `&1`」と明示しているのは、この優先順位の誤解が問題であったことを示唆しています。

### 修正後のコード

修正後のコードは以下の通りです。
```c
if(((havepc[i/32]>>(i%32))&1) == 0)
```

この式は、括弧によって評価順序が明確に制御されています。

1.  **`havepc[i/32]>>(i%32)`**: 元のコードと同様に、`i`番目のビットが最下位ビットにシフトされます。

2.  **`(extracted_bit_value & 1)`**: 次に、このシフトされた値と`1`のビットAND演算が行われます。これにより、`i`番目のビットが正確に抽出され、結果は`0`か`1`のいずれかになります。この結果を`isolated_bit`とします。

3.  **`isolated_bit == 0`**: 最後に、抽出されたビット`isolated_bit`が`0`と等しいかどうかが明示的に比較されます。

この修正により、式は**「`i`番目のビットを抽出し、それが0であるかをチェックする」**という意図を明確かつ安全に表現しています。演算子の優先順位に依存する曖昧さがなくなり、コードの可読性と堅牢性が向上しました。

### 潜在的なクラッシュの可能性

コミットメッセージでは、「This would crash writing out missing pcdata tables if we ever used non-contiguous IDs in a function.」と述べられています。これは、現在のGoのランタイムでは`pcdata`のIDが連続的であるため、このバグが顕在化していなかったことを示唆しています。

しかし、もし将来的に`pcdata`のIDが非連続になった場合、`havepc`ビットマスクの構造や、`i`番目のビットが実際に意味する内容がより複雑になる可能性があります。その際、元の曖昧な条件式が、意図しないビットをチェックしたり、誤った結果を返したりすることで、リンカーが`pcdata`テーブルを正しく生成できなくなり、結果として実行可能ファイルの破損やリンカー自体のクラッシュを引き起こす可能性がありました。

この修正は、現在の動作に影響を与えないものの、将来的なGoのランタイムの進化や、より複雑な`pcdata`の利用シナリオに対する防御的なプログラミングとして非常に重要です。

## コアとなるコードの変更箇所

変更は`src/liblink/pcln.c`ファイルの一箇所のみです。

```diff
--- a/src/liblink/pcln.c
+++ b/src/liblink/pcln.c
@@ -279,7 +279,7 @@ linkpcln(Link *ctxt, LSym *cursym)
 	}
 	// pcdata.
 	for(i=0; i<npcdata; i++) {
-		if(!(havepc[i/32]>>(i%32))&1) 
+		if(((havepc[i/32]>>(i%32))&1) == 0) 
 			continue;
 		funcpctab(ctxt, &pcln->pcdata[i], cursym, "pctopcdata", pctopcdata, (void*)(uintptr)i);
 	}
```

## コアとなるコードの解説

変更された行は、`linkpcln`関数内の`pcdata`処理ループの一部です。

`for(i=0; i<npcdata; i++) { ... }`
このループは、`npcdata`（関数内の`pcdata`エントリの総数）の各`pcdata`エントリを反復処理します。

`if(...) continue;`
この条件文は、特定の`pcdata`エントリが「存在しない」または「処理する必要がない」場合に、現在のループの反復をスキップし、次のエントリに進むためのものです。つまり、条件が真の場合に`continue`が実行されます。

**変更前:**
`if(!(havepc[i/32]>>(i%32))&1)`

この式は、前述の「技術的詳細」セクションで解説したように、`i`番目のビットが`0`である場合に`1`（真）を返します。したがって、この`if`文は「`i`番目の`pcdata`エントリに対応するビットが`0`である場合（つまり、その`pcdata`が存在しない場合）、ループの残りの処理をスキップする」という意味になります。

**変更後:**
`if(((havepc[i/32]>>(i%32))&1) == 0)`

この式も、`i`番目のビットを抽出し（`((havepc[i/32]>>(i%32))&1)`）、その結果が`0`と等しいか（`== 0`）を明示的にチェックしています。これにより、変更前と同じ論理（`i`番目のビットが`0`である場合に真）が、より明確で安全な方法で表現されています。

この`if`文の目的は、`havepc`ビットマスクに基づいて、実際に存在する`pcdata`エントリのみを後続の`funcpctab`関数で処理することです。もしビットが`0`であれば、その`pcdata`エントリは存在しないと見なされ、処理がスキップされます。この修正は、この重要なチェックの信頼性と可読性を向上させるものです。

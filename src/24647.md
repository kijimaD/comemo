## 元コミット内容

GoコンパイラのSSAバックエンドにおいて、文字列をメモリにストアする際の書き換えルールに不備がありました。`Store`オペレーションは、その操作が書き込むデータのサイズを`auxint`フィールドに保持する必要がありますが、文字列のストア処理においてこのサイズ情報の設定が漏れていました。このコミットは、その漏れを修正し、文字列のストアが正しくサイズ情報を持つように変更します。

## 変更の背景

Goコンパイラは、最適化のためにプログラムをSSA形式に変換します。SSA形式では、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。`Store`オペレーションは、SSA形式においてメモリへの書き込みを表す重要な操作です。

このコミットが行われた時期（2015年8月）は、Goコンパイラが従来のAST（Abstract Syntax Tree）ベースの最適化から、より高度なSSAベースの最適化へと移行している過渡期でした。SSAバックエンドの導入に伴い、各SSAオペレーション（`Op`）には、その操作のセマンティクスを補足するための追加情報（`Aux`や`AuxInt`）が必要となることが多くなりました。

`Store`オペレーションの場合、書き込むデータのサイズはメモリ安全性や正確なコード生成のために不可欠な情報です。例えば、ポインタのサイズ（`config.PtrSize`）はアーキテクチャによって異なり（32ビットシステムでは4バイト、64ビットシステムでは8バイト）、このサイズを正確に`Store`オペレーションに伝えることで、コンパイラは適切なロード/ストア命令を生成できます。

文字列はGoにおいて特別な型であり、通常はデータへのポインタと文字列の長さという2つの要素で構成されます。したがって、文字列をメモリにストアするということは、実際にはこの2つの要素をストアすることを意味します。このコミット以前は、文字列のストアをSSA形式で表現する際に、この2つの要素の合計サイズ（`2 * config.PtrSize`）が`Store`オペレーションの`auxint`フィールドに適切に伝達されていませんでした。この不備は、コンパイラが誤ったサイズのストア命令を生成する可能性があり、ランタイムエラーや不正なメモリ操作につながる恐れがありました。

## 前提知識の解説

### 1. GoコンパイラのSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを中間表現に変換し、様々な最適化を適用してから最終的な機械語を生成します。SSAは、この中間表現の一つで、プログラム中の各変数が一度だけ代入されるように変換された形式です。これにより、データフロー解析が容易になり、デッドコード削除、共通部分式除去、レジスタ割り当てなどの高度な最適化を効率的に行えるようになります。

SSA形式では、プログラムの操作は「オペレーション（Op）」として表現されます。例えば、`Add`、`Load`、`Store`などがオペレーションです。各オペレーションは、入力となる値（`Args`）と、そのオペレーションのセマンティクスを補足する追加情報（`Aux`や`AuxInt`）を持つことがあります。

### 2. `Store`オペレーションと`AuxInt`

`Store`オペレーションは、SSA形式においてメモリへの書き込みを表します。`Store`オペレーションは通常、以下の情報を受け取ります。
*   `dst`: 書き込み先のメモリアドレス。
*   `src`: 書き込む値。
*   `mem`: 以前のメモリの状態（SSAではメモリも値として扱われ、メモリ操作の順序を保証するために使われます）。

このコミットの文脈では、`Store`オペレーションには`auxint`フィールドを通じて「書き込むデータのサイズ」を伝える必要があります。このサイズ情報は、コンパイラがターゲットアーキテクチャに合わせた適切なストア命令（例: `MOVQ` (8バイト), `MOVL` (4バイト) など）を選択するために重要です。

### 3. Goにおける文字列の内部表現

Goの文字列は、不変なバイトシーケンスです。内部的には、文字列は通常、以下の2つの要素で構成される構造体として表現されます。
*   **データポインタ**: 文字列の実際のバイトデータが格納されているメモリ領域へのポインタ。
*   **長さ**: 文字列のバイト長。

これらの要素は、Goのポインタサイズ（`config.PtrSize`）に依存します。例えば、64ビットシステムでは、ポインタも長さも8バイトの整数として扱われるため、文字列全体は`8 + 8 = 16`バイトを占めます。つまり、`2 * config.PtrSize`のサイズになります。

### 4. `config.PtrSize`

`config.PtrSize`は、Goコンパイラがターゲットとするアーキテクチャにおけるポインタのサイズ（バイト単位）を表す定数です。32ビットシステムでは4、64ビットシステムでは8となります。文字列の内部表現をメモリにストアする際には、この`config.PtrSize`を考慮して、データポインタと長さの合計サイズを正確に指定する必要があります。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおける文字列のストア処理の正確性を向上させることにあります。具体的には、`Store`オペレーションが書き込むデータのサイズを`auxint`フィールドに持つというSSAの新しい要件に、文字列のストア処理が対応していなかった点を修正しています。

Goの文字列は、内部的にはポインタと長さのペアとして表現されます。したがって、文字列をメモリにストアするということは、このポインタと長さの2つの値を連続したメモリ領域に書き込むことを意味します。それぞれの値は`config.PtrSize`のサイズを持つため、合計で`2 * config.PtrSize`のデータが書き込まれることになります。

## コアとなるコードの解説

### `generic.rules` の変更

この変更の最も重要な部分は、`generic.rules`ファイルにおける文字列ストアの書き換えルールの修正です。

**変更前:**
`(Store dst str mem) && str.Type.IsString() -> (Store (OffPtr <config.Frontend().TypeBytePtr()> [config.PtrSize] dst) (StringLen <config.Frontend().TypeUintptr()> str) (Store <TypeMem> dst (StringPtr <config.Frontend().TypeBytePtr()> str) mem))`

このルールは、文字列`str`をアドレス`dst`にストアする操作を、以下の2つのより基本的なストア操作に分解しています。
1.  `dst`から`config.PtrSize`だけオフセットしたアドレスに、文字列の長さ（`StringLen`）をストアする。
2.  `dst`に、文字列のデータポインタ（`StringPtr`）をストアする。

問題は、元の`Store`オペレーション`(Store dst str mem)`に、それが書き込むデータの合計サイズが明示されていなかった点です。Goの文字列はポインタと長さのペアなので、合計で`2 * config.PtrSize`のサイズを占めます。

**変更後:**
`(Store [2*config.PtrSize] dst str mem) && str.Type.IsString() -> (Store [config.PtrSize] (OffPtr <config.Frontend().TypeBytePtr()> [config.PtrSize] dst) (StringLen <config.Frontend().TypeUintptr()> str) (Store [config.PtrSize] <TypeMem> dst (StringPtr <config.Frontend().TypeBytePtr()> str) mem))`

この修正では、以下の点が変更されています。
*   元の`Store`オペレーションに`[2*config.PtrSize]`が追加されました。これは、この`Store`オペレーションが`2 * config.PtrSize`バイトのデータを書き込むことを明示しています。
*   分解された2つの`Store`オペレーション（文字列の長さとデータポインタをストアするもの）それぞれにも`[config.PtrSize]`が追加されました。これにより、それぞれのストア操作が`config.PtrSize`バイトのデータを書き込むことが明確になります。

この変更により、SSAバックエンドは文字列のストア操作の正確なサイズ情報を持ち、それに基づいて適切な機械語命令を生成できるようになります。

### `rewritegeneric.go` の変更

`rewritegeneric.go`ファイルは、`generic.rules`で定義されたルールをGoのコードとして実装しています。このファイル内の`rewriteValuegeneric`関数は、SSAの`Value`（オペレーション）を書き換える役割を担っています。

変更された`OpStore`のケースでは、`generic.rules`の変更を反映して、以下のロジックが追加されています。

1.  **`if v.AuxInt != 2*config.PtrSize { ... }`**:
    これは、書き換え対象の`Store`オペレーション`v`が、文字列のストアとして期待される合計サイズ`2*config.PtrSize`を`AuxInt`に持っているかをチェックするガード条件です。もしサイズが一致しなければ、この書き換えルールは適用されません。これにより、コンパイラは不正な状態の`Store`オペレーションを誤って書き換えることを防ぎます。

2.  **`v.AuxInt = config.PtrSize`**:
    書き換え後の最初の`Store`オペレーション（文字列の長さをストアするもの）に対して、`AuxInt`フィールドに`config.PtrSize`を設定しています。

3.  **`v2.AuxInt = config.PtrSize`**:
    書き換え後の2番目の`Store`オペレーション（文字列のデータポインタをストアするもの）に対して、`AuxInt`フィールドに`config.PtrSize`を設定しています。

これらの変更により、`rewritegeneric.go`は`generic.rules`の新しい定義に完全に準拠し、文字列のストア操作がSSA形式で正確なサイズ情報を持つように保証します。

### `rulegen.go` の変更

`rulegen.go`の変更は、`isVariable`関数内の正規表現の修正です。
*   **変更前**: `"[A-Za-z_][A-Za-z_0-9]*"`
*   **変更後**: `"^[A-Za-z_][A-Za-z_0-9]*$"`

この変更は、正規表現に`^`（行頭アンカー）と`$`（行末アンカー）を追加しています。これにより、`isVariable`関数は、入力文字列`s`が「完全に」Goの識別子（変数名）のパターンに一致する場合にのみ`true`を返すようになります。変更前は、文字列の一部がパターンに一致すれば`true`を返す可能性がありましたが、変更後はより厳密なチェックが行われます。この修正は、SSAの文字列ストアの修正とは直接的な関連はありませんが、コンパイラのコード生成ルールに関連するユーティリティ関数の正確性を向上させるものです。

## 元コミット内容

GoコンパイラのSSAバックエンドにおいて、文字列をメモリにストアする際の書き換えルールに不備がありました。`Store`オペレーションは、その操作が書き込むデータのサイズを`auxint`フィールドに保持する必要がありますが、文字列のストア処理においてこのサイズ情報の設定が漏れていました。このコミットは、その漏れを修正し、文字列のストアが正しくサイズ情報を持つように変更します。

## 変更の背景

Goコンパイラは、ソースコードを機械語に変換する過程で、プログラムをSSA（Static Single Assignment）形式という中間表現に変換し、様々な最適化を適用します。SSA形式は、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を非常に効率的に行えるようにします。

このコミットが行われた2015年8月は、Goコンパイラが従来のAST（Abstract Syntax Tree）ベースの最適化から、より高度なSSAベースの最適化へと移行している時期でした。SSAバックエンドの導入に伴い、各SSAオペレーション（`Op`）には、その操作のセマンティクスを補足するための追加情報（`Aux`や`AuxInt`）が必要となることが多くなりました。

`Store`オペレーションは、SSA形式においてメモリへの書き込みを表す基本的な操作です。この`Store`オペレーションには、書き込むデータのサイズを`auxint`フィールドを通じて伝えるという新しい要件が導入されました。このサイズ情報は、コンパイラがターゲットアーキテクチャに合わせた適切なロード/ストア命令（例: 32ビットシステムでは4バイト、64ビットシステムでは8バイトを扱う命令）を生成するために不可欠です。サイズが不正確だと、コンパイラは誤った命令を生成し、ランタイムエラーや不正なメモリ操作を引き起こす可能性があります。

Goの文字列は、内部的にはデータへのポインタと文字列の長さという2つの要素で構成される構造体として表現されます。したがって、文字列をメモリにストアするということは、実際にはこの2つの要素を連続したメモリ領域にストアすることを意味します。それぞれの要素は`config.PtrSize`（ポインタのサイズ）のサイズを持つため、合計で`2 * config.PtrSize`のデータが書き込まれることになります。

このコミット以前は、文字列のストアをSSA形式に書き換える際に、この`2 * config.PtrSize`という合計サイズ情報が`Store`オペレーションの`auxint`フィールドに適切に設定されていませんでした。この不備が、コンパイラが文字列のストアに対して誤ったサイズの命令を生成する可能性があったため、この修正が必要とされました。

## 前提知識の解説

### 1. GoコンパイラのSSA (Static Single Assignment) 形式

Goコンパイラは、ソースコードを解析し、抽象構文木（AST）を構築した後、さらに最適化のためにSSA形式という中間表現に変換します。SSA形式の主な特徴は以下の通りです。
*   **単一代入**: 各変数はプログラム中で一度だけ代入されます。これにより、変数の値がどこで定義され、どこで使われているか（use-def chain）が明確になり、データフロー解析が非常に容易になります。
*   **オペレーション（Op）**: プログラムの操作は、`Add`、`Load`、`Store`などの具体的なオペレーションとして表現されます。
*   **値（Value）**: 各オペレーションの結果は「値」として扱われ、他のオペレーションの入力となります。メモリ操作もSSAでは値として扱われ、メモリの読み書きの順序を保証します。
*   **補助情報（Aux, AuxInt）**: 各オペレーションは、そのセマンティクスを補足するための追加情報を持つことがあります。`Aux`は任意の型、`AuxInt`は整数値を格納するために使われます。例えば、`Load`や`Store`オペレーションでは、アクセスするデータのサイズやオフセットが`AuxInt`に格納されることがあります。

### 2. `Store`オペレーションと`AuxInt`

`Store`オペレーションは、SSA形式においてメモリへの書き込みを表します。一般的な形式は `(Store dst src mem)` で、`src`の値を`dst`アドレスに書き込み、その結果として新しいメモリの状態`mem`を生成します。

このコミットの文脈では、`Store`オペレーションには`auxint`フィールドを通じて「書き込むデータのサイズ」を伝える必要があります。このサイズ情報は、コンパイラがターゲットアーキテクチャ（例: x86-64, ARM64）に合わせた適切なストア命令（例: 8バイトをストアする`MOVQ`、4バイトをストアする`MOVL`など）を選択するために極めて重要です。サイズが指定されていないと、コンパイラはデフォルトのサイズを使用したり、誤ったサイズの命令を生成したりするリスクがあります。

### 3. Goにおける文字列の内部表現

Goの文字列は、不変なバイトシーケンスです。内部的には、Goのランタイムは文字列を以下の2つの要素で構成される構造体として扱います。
*   **データポインタ**: 文字列の実際のバイトデータが格納されているメモリ領域の先頭へのポインタ。型は通常 `*byte` に相当します。
*   **長さ**: 文字列のバイト長。型は通常 `uintptr` に相当します。

これらの要素は、Goが動作するシステムのアーキテクチャに依存します。例えば、64ビットシステムでは、ポインタも`uintptr`も8バイトの整数として扱われるため、文字列全体は`8バイト（ポインタ） + 8バイト（長さ） = 16バイト`を占めます。

### 4. `config.PtrSize`

`config.PtrSize`は、Goコンパイラがターゲットとするアーキテクチャにおけるポインタのサイズ（バイト単位）を表す定数です。
*   32ビットシステム（例: `GOARCH=386`）では `4` バイト。
*   64ビットシステム（例: `GOARCH=amd64`）では `8` バイト。

文字列の内部表現（ポインタと長さ）をメモリにストアする際には、この`config.PtrSize`を考慮して、データポインタと長さの合計サイズを正確に指定する必要があります。文字列全体をストアする場合、そのサイズは常に`2 * config.PtrSize`となります。

## 技術的詳細

このコミットの主要な目的は、GoコンパイラのSSAバックエンドが文字列のストア操作を正確に処理し、適切な機械語を生成できるようにすることです。これは、`Store`オペレーションに書き込むデータのサイズを`auxint`フィールドで明示するというSSAの要件を満たすことで達成されます。

Goの文字列は、前述の通りデータポインタと長さのペアとしてメモリに格納されます。したがって、文字列をメモリにストアするSSAの`Store`オペレーションは、実際にはこの2つの`config.PtrSize`サイズの値を連続したメモリ領域に書き込むことになります。合計で`2 * config.PtrSize`バイトのデータが書き込まれることになります。

このコミットでは、主に以下の2つのファイルが変更され、この問題が解決されています。

1.  **`src/cmd/compile/internal/ssa/gen/generic.rules`**:
    このファイルは、SSAオペレーションの書き換えルールを定義するものです。コンパイラはこれらのルールを使用して、高レベルなSSAオペレーションをより低レベルなオペレーションに分解したり、最適化を適用したりします。

    変更されたルールは、文字列型（`str.Type.IsString()`）の`Store`オペレーションに関するものです。

    *   `dst`から`config.PtrSize`だけオフセットしたアドレスに、文字列の長さ（`StringLen`）をストアする。
    *   `dst`に、文字列のデータポインタ（`StringPtr`）をストアする。

## コアとなるコードの解説

### `generic.rules` の変更点

この変更の最も重要な部分は、`generic.rules`ファイルにおける文字列ストアの書き換えルールの修正です。

**変更前:**
`(Store dst str mem) && str.Type.IsString() -> (Store (OffPtr <config.Frontend().TypeBytePtr()> [config.PtrSize] dst) (StringLen <config.Frontend().TypeUintptr()> str) (Store <TypeMem> dst (StringPtr <config.Frontend().TypeBytePtr()> str) mem))`

このルールは、文字列`str`をアドレス`dst`にストアする操作を、以下の2つのより基本的なストア操作に分解していました。
1.  `dst`から`config.PtrSize`だけオフセットしたアドレスに、文字列の長さ（`StringLen`）をストアする。
2.  `dst`に、文字列のデータポインタ（`StringPtr`）をストアする。

問題は、元の`Store`オペレーション`(Store dst str mem)`に、それが書き込むデータの合計サイズが明示されていなかった点です。Goの文字列はポインタと長さのペアなので、合計で`2 * config.PtrSize`のサイズを占めます。

**変更後:**
`(Store [2*config.PtrSize] dst str mem) && str.Type.IsString() -> (Store [config.PtrSize] (OffPtr <config.Frontend().TypeBytePtr()> [config.PtrSize] dst) (StringLen <config.Frontend().TypeUintptr()> str) (Store [config.PtrSize] <TypeMem> dst (StringPtr <config.Frontend().TypeBytePtr()> str) mem))`

この修正では、以下の点が変更されています。
*   元の`Store`オペレーションに`[2*config.PtrSize]`が追加されました。これは、この`Store`オペレーションが`2 * config.PtrSize`バイトのデータを書き込むことを明示しています。
*   分解された2つの`Store`オペレーション（文字列の長さとデータポインタをストアするもの）それぞれにも`[config.PtrSize]`が追加されました。これにより、それぞれのストア操作が`config.PtrSize`バイトのデータを書き込むことが明確になります。

この変更により、SSAバックエンドは文字列のストア操作の正確なサイズ情報を持ち、それに基づいて適切な機械語命令を生成できるようになります。

### `rewritegeneric.go` の変更点

`rewritegeneric.go`ファイルは、`generic.rules`で定義されたルールをGoのコードとして実装しています。このファイル内の`rewriteValuegeneric`関数は、SSAの`Value`（オペレーション）を走査し、定義されたルールに基づいて書き換えを行います。

変更された`OpStore`のケースでは、`generic.rules`の変更を反映して、以下のロジックが追加されています。

1.  **`if v.AuxInt != 2*config.PtrSize { ... }`**:
    これは、書き換え対象の`Store`オペレーション`v`が、文字列のストアとして期待される合計サイズ`2*config.PtrSize`を`AuxInt`に持っているかをチェックするガード条件です。もしサイズが一致しなければ、この書き換えルールは適用されません。これにより、コンパイラは不正な状態の`Store`オペレーションを誤って書き換えることを防ぎます。

2.  **`v.AuxInt = config.PtrSize`**:
    書き換え後の最初の`Store`オペレーション（文字列の長さをストアするもの）に対して、`AuxInt`フィールドに`config.PtrSize`を設定しています。

3.  **`v2.AuxInt = config.PtrSize`**:
    書き換え後の2番目の`Store`オペレーション（文字列のデータポインタをストアするもの）に対して、`AuxInt`フィールドに`config.PtrSize`を設定しています。

これらの変更により、`rewritegeneric.go`は`generic.rules`の新しい定義に完全に準拠し、文字列のストア操作がSSA形式で正確なサイズ情報を持つように保証します。

### `rulegen.go` の変更点

`rulegen.go`の変更は、`isVariable`関数内の正規表現の修正です。
*   **変更前**: `regexp.MatchString("[A-Za-z_][A-Za-z_0-9]*", s)`
*   **変更後**: `regexp.MatchString("^[A-Za-z_][A-Za-z_0-9]*$", s)`

この変更は、正規表現に`^`（行頭アンカー）と`$`（行末アンカー）のアンカーを追加することで、入力文字列`s`が「完全に」Goの識別子（変数名）のパターンに一致する場合にのみ`true`を返すように、チェックをより厳密にしています。この修正は、SSAの文字列ストアの修正とは直接的な関連はありませんが、コンパイラのコード生成ルールに関連するユーティリティ関数の正確性を向上させるための、独立した改善と考えられます。

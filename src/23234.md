## 変更の背景

Go言語では、変数がスタックに割り当てられるかヒープに割り当てられるかを決定する「エスケープ解析」がコンパイル時に行われます。スタック割り当ては高速でガベージコレクション（GC）のオーバーヘッドがないため、可能な限りスタックに割り当てることでパフォーマンスが向上します。一方、ヒープ割り当てはGCの対象となり、パフォーマンスに影響を与える可能性があります。

このコミットの主な目的は、Goコンパイラのエスケープ解析の精度を向上させ、不要なヒープ割り当てを削減することです。特に、関数間のパラメータのポインタフローをより正確に追跡することで、変数がヒープにエスケープする必要があるかどうかをより適切に判断できるようになります。これにより、メモリ使用量の削減とプログラム実行速度の向上が期待されます。

コミットメッセージに記載されているように、`src/std`のコンパイルで420箇所のヒープ割り当てサイトが削減され、`src/html/template`のプロファイリングではコンパイラによる割り当てが15%削減されたという具体的な成果が示されており、この改善がパフォーマンスに大きく貢献していることがわかります。

## 前提知識の解説

### Goのエスケープ解析

Goのエスケープ解析は、コンパイラが変数の生存期間を分析し、その変数をスタックに配置するかヒープに配置するかを決定するプロセスです。

- **スタック割り当て**: 変数の生存期間がその変数を宣言した関数の実行期間を超えないことがコンパイラによって証明できる場合、その変数はスタックに割り当てられます。スタック割り当ては非常に高速で、関数が終了すると自動的にメモリが解放されるため、ガベージコレクションのオーバーヘッドが発生しません。
- **ヒープ割り当て**: コンパイラが変数の生存期間を関数の実行期間内に限定できない場合、または変数のアドレスがそのスコープ外で共有される可能性がある場合、その変数はヒープに「エスケープ」します。ヒープ割り当てはスタック割り当てよりも遅く、ガベージコレクタが定期的にメモリを管理する必要があるため、CPU時間を消費します。

変数がヒープにエスケープする一般的なシナリオには以下のようなものがあります。

1.  **ローカル変数のポインタを返す**: 関数が終了した後もそのポインタが参照され続ける可能性があるため。
2.  **ポインタを別の関数に渡し、その関数がポインタを保存する可能性がある場合**: 呼び出された関数がポインタを保存する場合、元の変数は呼び出し元の関数の生存期間を超えて存在する必要があります。
3.  **ゴルーチン内で変数を使用する場合**: ゴルーチンは独立して実行されるため、変数の生存期間が作成元の関数を超える可能性があります。
4.  **クロージャ内で変数をキャプチャする場合**: クロージャが外側の関数が戻った後に実行される可能性があるため。
5.  **スタックには大きすぎる変数**: スタックオーバーフローを防ぐため、非常に大きな値はヒープに割り当てられます。
6.  **グローバル変数や関数の生存期間を超えるデータ構造に保存する場合**: 変数がそのローカルスコープを超えてアクセス可能になるため。

### `gcflags -m`

Goコンパイラには、エスケープ解析の結果を観察するためのフラグが用意されています。

-   **`-gcflags="-m"`**: このフラグは、ヒープにエスケープした変数をリストアップする簡潔な出力を提供します。
-   **`-gcflags="-m=2"` (または `-m` を繰り返す)**: より詳細な出力を提供し、変数がエスケープした理由を示す詳細なフローラインが含まれます。これにより、ヒープ割り当ての正確な原因を特定するのに役立ちます。

これらの「レベル」は、コンパイラのエスケープ解析に関する診断出力の冗長性を指します。

### G0スタック

Goでは、各ゴルーチンが独自のスタックを持っています。通常のゴルーチンのスタックは比較的小さな初期サイズ（約2KiB）で始まり、必要に応じて動的に拡大・縮小します。

`G0`スタックとは、Goランタイム内部の特別なゴルーチンである`G0`が使用するスタックを指します。`G0`はスケジューリング、ガベージコレクション、その他の低レベルのランタイムタスクを処理します。ユーザーレベルのゴルーチンとは異なり、`G0`は通常、固定サイズのスタックを持ち、通常のゴルーチンの初期スタックよりも大きいです。これは、`G0`がより多くのスタック空間を必要とする可能性のある重要なランタイム操作を実行するためです。このコミットでは、エスケープ解析の改善により、一部のランタイムテストで`G0`スタックに過剰な割り当てが発生し、テストが失敗したため、関連するコードの修正が必要となりました。

## 技術的詳細

このコミットは、エスケープ解析の精度を大幅に向上させるために、特にパラメータのフロー分析に焦点を当てています。

### パラメータフローの新しいエンコーディング

関数ごとのサマリー情報に、以下の新しいポインタフローのエンコーディングが導入されました。

-   `outK = paramJ`: `paramJ`が`outK`番目の出力パラメータに直接流れることを示します。
-   `outK = *paramJ`: `paramJ`が指す内容（間接参照された値）が`outK`番目の出力パラメータに流れることを示します。
-   `heap = paramJ`: `paramJ`自体がヒープにエスケープすることを示します（`EscHeap`）。
-   `heap = *paramJ`: `paramJ`が指す内容（間接参照された値）がヒープにエスケープすることを示します（`EscContentEscapes`）。

特に`EscContentEscapes`は、パラメータ自体ではなく、そのパラメータが指すデータがヒープにエスケープする場合に設定されます。これは、ポインタの指す先がヒープに割り当てられる必要があることを示し、よりきめ細やかなエスケープ解析を可能にします。

### 「レベル」の3分割と間接参照の打ち消し効果

エスケープ解析の「レベル」の概念がさらに改善され、3つの部分に分割されました。

1.  **従来の「レベル」**: ポインタの間接参照の深さを追跡します。例えば、`*p`は`p`よりも1レベル深い、`**p`は2レベル深い、といった具合です。
2.  **`highest-level-suffix-from-copy`の2つの部分**: これは、間接参照とアドレス取得（`&`演算子）が組み合わさった場合の「打ち消し効果」をモデル化するために使用されます。例えば、`&(*p)`のような操作では、間接参照とアドレス取得が互いに打ち消し合い、元の`p`と同じレベルになることがあります。この新しいレベル追跡は、このような複雑なポインタ操作におけるエスケープの挙動をより正確に把握することを目的としています。

`esc.go`の`Level`構造体と関連するメソッド（`inc()`, `dec()`, `copy()`, `min()`, `guaranteedDereference()`）がこの新しいレベル追跡を実装しています。`Level`は`value`と`suffixValue`という2つの`int8`フィールドを持ち、`value`が従来のレベル、`suffixValue`が`highest-level-suffix-from-copy`に関連する情報を保持します。

### 調整可能なビット数

関数ごとのサマリー情報におけるパラメータフローのエンコーディングには、調整可能なビット数（`bitsPerOutputInTag`）が使用されます。コミットメッセージでは「2ビットが1ビットよりも明らかに優れており、3ビットはおそらくやりすぎだろう」と述べられており、このビット数を調整することで、エスケープ解析の精度とコンパイラのパフォーマンスのバランスを取ることができます。

### `MinLevel`定数

`esc.go`には`MinLevel = -2`という定数が導入されています。これは、エスケープグラフにループが存在する場合に、解析が無限に深く再帰するのを防ぐためのものです。`MinLevel`に到達すると、それ以上レベルを下げることができなくなりますが、上げることもできなくなります。これにより、解析の収束が保証されます。

### ヒープ割り当ての削減

この改善により、Goプログラムのヒープ割り当てが大幅に削減されました。

-   `src/std`のコンパイルにおいて、ヒープ割り当てサイトが420箇所減少（10968箇所から10538箇所へ）。
-   `src/html/template`のプロファイリングにおいて、コンパイラによる割り当てが15%削減。

これは、エスケープ解析の精度向上によって、これまでヒープに割り当てられていた多くの変数がスタックに割り当てられるようになったことを意味し、Goプログラム全体の実行効率とメモリ効率の向上に貢献します。

### ランタイムテストの修正

エスケープ解析の改善により、一部のランタイムテストで`G0`スタックに過剰な割り当てが発生し、テストが失敗する問題が発生しました。これは、解析がより正確になった結果、これまでヒープに割り当てられていた一部のデータが`G0`スタックに割り当てられるようになったためと考えられます。この問題に対処するため、`src/runtime/proc1.go`に`pSink`というグローバル変数が追加され、特定のポインタが強制的にヒープに割り当てられるように修正されました。

## コアとなるコードの解説

このコミットの核心は、エスケープ解析がポインタの「レベル」を追跡する方法の根本的な変更と、関数間のパラメータフローをより詳細にエンコードするメカニズムにあります。

### `Level`構造体とポインタのレベル追跡

以前のエスケープ解析では、ポインタのレベルは単純な整数（`int`または`int32`）で表されていました。これは、間接参照（`*`）ごとにレベルが増加し、アドレス取得（`&`）ごとにレベルが減少するというものでした。しかし、この単純なモデルでは、`&(*p)`のような操作でレベルが打ち消されるケースや、より複雑なポインタ操作のセマンティクスを正確に捉えることができませんでした。

新しい`Level`構造体は、`value`と`suffixValue`という2つの`int8`フィールドを持つことで、この問題を解決しようとします。

-   `value`: 従来のレベル追跡を継続します。
-   `suffixValue`: 「コピーから始まる最高レベルのサフィックス」を計算します。これは、間接参照とアドレス取得が組み合わさったときに、ポインタの「実効的な」レベルがどのように変化するかをモデル化するために使用されます。例えば、`&Node{&Node{x.left}}`のようなケースでは、`x`の値が新しく割り当てられた`Node`のフィールドにコピーされるという暗黙のコピー操作が発生します。`suffixValue`は、このようなコピー操作を考慮に入れた上で、ポインタがどれだけ間接参照されているかを追跡します。

`Level`構造体のメソッドは、これらのレベルを正確に更新します。
-   `inc()`: ポインタが間接参照される（`*`）と呼び出され、`value`と`suffixValue`の両方を増加させます。
-   `dec()`: アドレスが取得される（`&`）と呼び出され、`value`と`suffixValue`の両方を減少させます。
-   `copy()`: 値がコピーされるときに呼び出され、`suffixValue`を`max8(l.suffixValue, 0)`に設定します。これは、コピーによって間接参照の深さがリセットされる可能性があることを示唆しています。
-   `min()`: 複数のパスから同じノードに到達した場合に、最も「エスケープしにくい」レベル（つまり、最も小さいレベル値）を選択するために使用されます。

`escwalk`関数は、この新しい`Level`型を使用して、エスケープグラフをトラバースし、各ノードのエスケープレベルを計算します。これにより、ポインタの複雑なフローをより正確に分析し、ヒープ割り当ての必要性をより適切に判断できるようになります。

### パラメータフローのエンコーディングと`EscContentEscapes`

`esc.go`の`escNoteOutputParamFlow`関数は、関数の入力パラメータが出力パラメータにどのように流れるかをエンコードします。これは、`bitsPerOutputInTag`で定義されたビット数（デフォルトは3ビット）を使用して、各出力パラメータへのフローの「レベル」を表現します。

-   `level.int() <= 0 && level.guaranteedDereference() > 0`の場合、`EscContentEscapes`が設定されます。これは、パラメータ自体ではなく、その内容（間接参照された値）がヒープにエスケープすることを示します。例えば、`func f(p *int) *int { return *p }`のような関数では、`p`自体はエスケープしないかもしれませんが、`*p`（`p`が指す内容）は戻り値としてエスケープする可能性があります。`EscContentEscapes`は、このようなシナリオを正確に識別し、コンパイラがより適切な割り当て決定を下せるようにします。

`describeEscape`関数は、このエンコードされた情報を人間が読める形式に変換するデバッグツールです。例えば、`contentToHeap _ =`のような出力は、パラメータの内容がヒープにエスケープし、最初の出力には流れないが、2番目の出力には直接流れることを示します。

これらの変更により、Goコンパイラは、関数間のポインタフローをより詳細かつ正確に理解できるようになり、結果として不要なヒープ割り当てを削減し、Goプログラムのパフォーマンスを向上させます。

-   Go's escape analysis is a compile-time optimization performed by the Go compiler to determine whether a variable should be allocated on the stack or the heap. This decision significantly impacts application performance and memory management. (sobyte.net)
-   At its core, escape analysis aims to keep as many variables as possible on the stack because stack allocations are significantly faster and do not incur garbage collection (GC) overhead. (sobyte.net)
-   If a variable's lifetime can be guaranteed to not outlive the function in which it's declared, it can be safely allocated on the stack. If the compiler cannot prove this, or if the variable's address is shared outside its immediate scope, it \"escapes\" to the heap. (dzone.com)
-   Common scenarios that cause variables to escape to the heap include: Returning a pointer to a local variable, Passing a pointer to another function that might store it, Using a variable in a goroutine, Capturing a variable in a closure, Variables too large for the stack, Storing in global variables or data structures that outlive the function, Interface conversions. (medium.com, dev.to, syntactic-sugar.dev)
-   The Go compiler provides flags to observe the results of escape analysis: `-gcflags="-m"` and `-gcflags="-m=2"`. (devgenius.io, medium.com)
-   Parameter flow analysis is a crucial part of escape analysis. The compiler tracks how parameters are used within a function and whether their values or addresses are passed to other functions, stored, or returned. (sobyte.net)
-   In Go, each goroutine has its own stack. The initial size of a goroutine's stack is relatively small (around 2 KiB) and it can grow or shrink on demand. (sobyte.net, reddit.com)
-   The term \"G0 stack allocation\" specifically refers to the stack used by the special goroutine `G0`. `G0` is a runtime-internal goroutine that handles scheduling, garbage collection, and other low-level runtime tasks. (sobyte.net)

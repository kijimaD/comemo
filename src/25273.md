# [インデックス 25273] ファイルの概要

このコミットは、Go言語の標準ライブラリである `net/http` パッケージにおいて、HTTPクライアントが `Expect: 100-continue` ヘッダーを適切にサポートするための機能追加と修正を行っています。具体的には、リクエストボディを送信する前にサーバーからの `100 Continue` レスポンスを待機するメカニズムを導入し、不要なボディの送信を防ぐことで、ネットワークリソースの効率化とエラーハンドリングの改善を図っています。

## 元コミット内容

このコミットの目的は、GoのHTTPクライアントが `Expect: 100-continue` リクエストヘッダーをサポートすることです。これまでのクライアントは、このヘッダーが存在してもリクエストボディを時期尚早に送信してしまう問題がありました。

この変更の意図は以下の通りです。
- `http.Request` ヘッダーにボディと `Expect: 100-continue` ヘッダーが含まれる場合、最初のレスポンスを受け取るまでボディの送信をブロックします。
- 最初のステータスコードが `100 (Continue)` であれば、リクエストボディの送信を開始します。そうでなければ、ボディの送信はキャンセルされます。
- `Transport.ExpectContinueTimeout` は、最初のレスポンスを待機する時間を指定します。

これにより、Issue #3665 が修正されます。

## 変更の背景

HTTP/1.1プロトコルでは、クライアントが大きなリクエストボディ（例えば、ファイルアップロードなど）を送信する際に、まずヘッダーのみを送信し、サーバーがそのヘッダーを受け入れ可能かどうかを確認するメカニズムとして `Expect: 100-continue` ヘッダーが定義されています（RFC2616-8 / RFC7231-5.1.1）。

このメカニズムの主な目的は以下の通りです。
1.  **帯域幅の節約**: サーバーがリクエストヘッダーを見て、認証エラーやリクエストサイズ超過などの理由でリクエストを処理できないと判断した場合、クライアントは大きなボディを送信する前にその事実を知ることができます。これにより、不要なデータ転送を避け、ネットワーク帯域幅を節約できます。
2.  **サーバーリソースの節約**: サーバーも、無効なリクエストのボディ全体を受信して解析する手間を省くことができます。
3.  **効率的なエラーハンドリング**: クライアントは、ボディを送信する前にサーバーからの早期フィードバックを得られるため、より迅速かつ効率的にエラーに対応できます。

このコミット以前のGoの `net/http` クライアントは、`Expect: 100-continue` ヘッダーが設定されていても、その意図を適切に解釈せず、リクエストボディをすぐに送信してしまう問題がありました。これは、クライアントがサーバーからの `100 Continue` レスポンスを待たずにボディを「時期尚早に消費」してしまうことを意味します。結果として、`Expect: 100-continue` ヘッダーの持つ利点が活かされず、サーバーがリクエストを拒否する可能性のある状況でも無駄なデータ転送が発生していました。

このコミットは、この問題を解決し、GoのHTTPクライアントがHTTP/1.1の仕様に準拠し、より堅牢で効率的な通信を行えるようにするために導入されました。

## 前提知識の解説

### HTTP/1.1の `Expect: 100-continue` ヘッダー

`Expect: 100-continue` は、HTTP/1.1で導入されたリクエストヘッダーです。クライアントがリクエストボディを送信する前に、サーバーがそのリクエストヘッダーを受け入れる準備ができているかを確認するために使用されます。

**動作シーケンス:**
1.  **クライアントの初期リクエスト**: クライアントは、`Expect: 100-continue` ヘッダーを含むリクエストヘッダーのみをサーバーに送信し、リクエストボディの送信を一時停止します。
2.  **サーバーの応答**:
    *   **`100 Continue`**: サーバーがリクエストヘッダーを受け入れ可能であると判断した場合、`100 Continue` という中間レスポンスを返します。クライアントはこれを受け取ると、残りのリクエストボディを送信します。
    *   **最終的なエラーレスポンス**: サーバーがリクエストヘッダーに問題があると判断した場合（例: 認証失敗、リクエストが大きすぎるなど）、`4xx` や `5xx` のような最終的なエラーレスポンスを直接返します。この場合、クライアントはリクエストボディを送信せずに、エラー処理を行います。
    *   **タイムアウト**: サーバーが一定時間内に何も応答しない場合、クライアントはタイムアウトと判断し、リクエストボディを送信するか、あるいはリクエストを中止するかのいずれかの動作をします。このコミットでは、タイムアウトした場合にボディを送信する動作が導入されています。

### Go言語の `net/http` パッケージ

`net/http` パッケージは、Go言語でHTTPクライアントとサーバーを実装するための標準ライブラリです。
-   **`http.Client`**: HTTPリクエストを送信するためのクライアントを提供します。
-   **`http.Request`**: HTTPリクエストを表す構造体です。ヘッダー、URL、メソッド、ボディなどが含まれます。
-   **`http.Transport`**: `http.Client` の内部で実際にネットワーク通信を行う部分を担います。コネクションの管理、リクエストの送信、レスポンスの受信などを担当します。`Expect: 100-continue` のような低レベルなプロトコル動作は `Transport` で処理されます。

## 技術的詳細

このコミットは、`net/http` パッケージの `http.Request` と `http.Transport` の両方に変更を加えています。

### `http.Request` の変更

`http.Request` の `write` メソッドは、リクエストヘッダーとボディを `io.Writer` に書き込む役割を担っています。このコミットでは、`write` メソッドのシグネチャが変更され、`waitForContinue func() bool` という新しい引数が追加されました。

```go
// 変更前
func (req *Request) write(w io.Writer, usingProxy bool, extraHeaders Header) error

// 変更後
func (req *Request) write(w io.Writer, usingProxy bool, extraHeaders Header, waitForContinue func() bool) error
```

この `waitForContinue` 関数は、`Expect: 100-continue` ヘッダーが設定されている場合にのみ `nil` ではない値が渡されます。`write` メソッド内で、この関数が呼び出され、サーバーからの `100 Continue` レスポンスを待機します。

具体的には、以下のロジックが追加されました。
1.  `Expect: 100-continue` が期待される場合 (`waitForContinue != nil`)、まずヘッダーが書き込まれた後、`io.Writer` が `*bufio.Writer` であれば `Flush()` されます。これにより、ヘッダーが確実にサーバーに送信されます。
2.  次に `waitForContinue()` が呼び出されます。この関数は、`100 Continue` レスポンスが来るか、タイムアウトするか、コネクションがクローズされるまでブロックします。
3.  `waitForContinue()` が `false` を返した場合（つまり、`100 Continue` 以外のレスポンスが来たか、コネクションがクローズされた場合）、リクエストボディの送信はキャンセルされ、`req.closeBody()` が呼び出されてボディが閉じられます。

### `http.Transport` の変更

`http.Transport` は、`Expect: 100-continue` のロジックを管理する主要な場所です。

1.  **`ExpectContinueTimeout` フィールドの追加**:
    `http.Transport` 構造体に `ExpectContinueTimeout time.Duration` フィールドが追加されました。これは、`Expect: 100-continue` ヘッダーを持つリクエストのヘッダーを完全に書き込んだ後、サーバーからの最初のレスポンスヘッダーを待機する時間を指定します。デフォルト値は `1 * time.Second` です。

2.  **`requestAndChan` および `writeRequest` 構造体の変更**:
    `Transport` の内部で使用される `requestAndChan` と `writeRequest` 構造体に、`continueCh chan<- struct{}` および `continueCh <-chan struct{}` というチャネルが追加されました。これらは、`readLoop` と `writeLoop` の間で `100 Continue` イベントを通知するために使用されます。

3.  **`roundTrip` メソッドの変更**:
    `roundTrip` メソッドは、`http.Client` からのリクエストを受け取り、実際のHTTP通信を行うエントリポイントです。
    -   リクエストが `Expect: 100-continue` ヘッダーを持つ場合、`continueCh` というチャネルが作成されます。
    -   この `continueCh` は、`writeRequest` と `requestAndChan` を介して `writeLoop` と `readLoop` に渡されます。

4.  **`readLoop` メソッドの変更**:
    `readLoop` は、サーバーからのレスポンスを読み取るゴルーチンです。
    -   レスポンスを読み取った際、もし `continueCh` が存在し、かつステータスコードが `100 (Continue)` であれば、`continueCh` に値を送信して `writeLoop` に通知します。
    -   `100 (Continue)` 以外のステータスコードであれば、`continueCh` をクローズして、ボディの送信をキャンセルするシグナルを送ります。
    -   以前は `100 Continue` レスポンスを単にスキップして次のレスポンスを読んでいましたが、この変更により `100 Continue` を適切に処理するようになりました。

5.  **`waitForContinue` ヘルパー関数の追加**:
    `persistConn` に `waitForContinue` という新しいヘルパー関数が追加されました。この関数は、`roundTrip` から渡された `continueCh` を監視し、`ExpectContinueTimeout` を使用してタイムアウトを管理します。
    -   `continueCh` から値が受信された場合（`100 Continue` が来た場合）、`true` を返してボディの送信を許可します。
    -   `ExpectContinueTimeout` が経過した場合、`true` を返してボディの送信を許可します（サーバーが `100 Continue` を返さなかったが、タイムアウト後にボディを送信するシナリオ）。
    -   コネクションがクローズされた場合、`false` を返してボディの送信をキャンセルします。

6.  **`writeLoop` メソッドの変更**:
    `writeLoop` は、リクエストを書き込むゴルーチンです。
    -   `wr.req.Request.write` を呼び出す際に、`pc.waitForContinue(wr.continueCh)` から返された関数を `waitForContinue` 引数として渡します。これにより、`write` メソッド内で `Expect: 100-continue` の待機ロジックが実行されます。

### `src/net/http/transport_test.go` の変更

`TestTransportExpect100Continue` という新しいテストケースが追加されました。このテストは、`Expect: 100-continue` ヘッダーを持つリクエストが、様々なサーバーの応答（`100 Continue`、`200 OK`、`500 Internal Server Error`、タイムアウトなど）に対して正しく動作するかどうかを検証します。これにより、新しい機能が期待通りに動作し、リクエストボディの時期尚早な送信が防止されることが保証されます。

## コアとなるコードの解説

このコミットの核心は、`Expect: 100-continue` ヘッダーの処理を、`http.Transport` の `readLoop` と `writeLoop` という2つのゴルーチン間で協調させるメカニズムにあります。

1.  **`roundTrip` での `continueCh` の生成**:
    `http.Client` がリクエストを送信する際、`Transport` の `roundTrip` メソッドが呼び出されます。ここで、リクエストが `Expect: 100-continue` ヘッダーを持つ場合、`continueCh` というバッファ付きチャネル（サイズ1）が作成されます。このチャネルは、`readLoop` から `writeLoop` へのシグナル伝達に使用されます。

2.  **`writeLoop` でのボディ送信のブロック**:
    `writeLoop` はリクエストヘッダーとボディをサーバーに書き込む役割を担います。`Request.write` メソッドが呼び出される際、`waitForContinue` 関数が引数として渡されます。この関数は、`continueCh` を監視し、`ExpectContinueTimeout` を使用してタイムアウトを管理します。
    -   `Request.write` はまずヘッダーをフラッシュし、`waitForContinue()` を呼び出します。
    -   `waitForContinue()` は、`select` ステートメントを使って以下のいずれかのイベントを待ちます。
        -   `continueCh` から値が受信される（`readLoop` が `100 Continue` を受け取ったことを意味する）。
        -   `ExpectContinueTimeout` が経過する。
        -   コネクションがクローズされる。
    -   `100 Continue` が受信された場合、またはタイムアウトした場合、`waitForContinue()` は `true` を返し、`write` メソッドはボディの送信を続行します。
    -   コネクションがクローズされた場合、`waitForContinue()` は `false` を返し、`write` メソッドはボディの送信をキャンセルします。

3.  **`readLoop` での `100 Continue` の処理**:
    `readLoop` はサーバーからのレスポンスを読み取ります。
    -   レスポンスのステータスコードが `100 (Continue)` であった場合、`readLoop` は `continueCh` に値を送信します。これにより、`writeLoop` の `waitForContinue()` がブロック解除され、ボディの送信が開始されます。
    -   レスポンスのステータスコードが `100 (Continue)` 以外であった場合（例: `401 Unauthorized`）、`readLoop` は `continueCh` をクローズします。これにより、`writeLoop` の `waitForContinue()` がブロック解除され、`false` を返すため、ボディの送信はキャンセルされます。

この協調メカニズムにより、GoのHTTPクライアントは `Expect: 100-continue` ヘッダーの意図を正確に解釈し、サーバーの応答に基づいてリクエストボディの送信を適切に制御できるようになりました。これにより、無駄なデータ転送が削減され、より効率的で堅牢なHTTP通信が実現されます。

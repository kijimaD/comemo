## 変更の背景

このコミット `725cd2ea72de70f2ff469b7a739a64e5fb6aa539` は、Go言語のビルドツール `cmd/go` に `-buildmode=shared` オプションのサポートを追加するものです。この変更の主な目的は、Goプログラムが共有ライブラリ（ダイナミックリンクライブラリ、例: Linuxにおける `.so` ファイル）を利用できるようにすることにあります。

Go言語の従来のビルドシステムは、デフォルトで全ての依存関係を単一のバイナリに静的にリンクする方式を採用していました。これはデプロイの簡素化という大きな利点がある一方で、特に複数のGoプログラムが同じシステム上で動作する場合、各プログラムがGoランタイムや標準ライブラリのコピーをそれぞれ持つため、ディスクスペースやメモリ使用量の観点から非効率になる可能性がありました。

`-buildmode=shared` の導入は、この問題に対処するための一歩です。これにより、Goの標準ライブラリ（`std`）やその他のGoパッケージを共有ライブラリとしてビルドし、複数のGoプログラム間で共有することが可能になります。コミットメッセージにあるように、`go install -buildmode=shared std` を実行することで、`libstd.so` のような共有ライブラリが生成されます。

ただし、コミットメッセージにも明記されているように、この機能は `-linkshared` オプションによる動的リンクのサポートがなければ、それ単独では実用的なものではありませんでした。つまり、共有ライブラリを生成できるようになったとしても、Goプログラムがその共有ライブラリを利用してビルドされる仕組みがなければ、その恩恵を受けることはできません。このコミットは、将来的な `-linkshared` サポートへの布石となる重要な一歩でした。

この機能は、特にGoのバイナリサイズを削減し、大規模なシステムでGoアプリケーションをデプロイする際の効率を向上させる可能性を秘めていました。しかし、GoのABI（Application Binary Interface）の不安定性という根本的な課題により、この `buildmode=shared` および `-linkshared` は、後に実験的な機能として位置づけられ、実運用での利用は限定的となりました。GoのABIは、コンパイラのバージョンやコードのわずかな変更によっても容易に破壊されるため、共有ライブラリの互換性を維持することが非常に困難だったためです。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語のビルドシステムと共有ライブラリに関する基本的な知識が必要です。

1.  **Goのビルドプロセス**:
    *   `go build`: Goのソースコードをコンパイルして実行可能なバイナリを生成するコマンドです。デフォルトでは、全ての依存関係がバイナリに静的にリンクされます。
    *   `go install`: `go build` と似ていますが、コンパイルされたパッケージやコマンドを `$GOPATH/pkg` や `$GOPATH/bin` (Go Modulesでは `$GOBIN`) にインストールします。
    *   **静的リンク**: Goのデフォルトのビルド方式。全ての必要なコード（Goランタイム、標準ライブラリ、依存パッケージ）が単一の実行ファイルに組み込まれます。これにより、デプロイが非常に簡単になりますが、バイナリサイズは大きくなる傾向があります。

2.  **ビルドモード (`-buildmode`)**:
    `go build` や `go install` コマンドには、`-buildmode` フラグを指定することで、異なる種類の出力形式を選択できます。
    *   `-buildmode=exe` (デフォルト): 実行可能ファイルを生成します。
    *   `-buildmode=c-archive`: C言語のアーカイブファイル（`.a`）を生成し、GoパッケージをC/C++プロジェクトに組み込むことを可能にします。
    *   `-buildmode=c-shared`: C言語の共有ライブラリ（`.so` や `.dll`）を生成し、Goの関数をC/C++から呼び出せるようにします。このコミット以前にも存在していました。
    *   **`-buildmode=shared` (このコミットで追加)**: GoパッケージをGoプログラム間で共有可能な共有ライブラリとしてビルドします。これはC言語との連携のためではなく、Goプログラム自身の依存関係を動的に解決するために設計されました。

3.  **共有ライブラリ (Dynamic Link Library - DLL / Shared Object - SO)**:
    *   複数のプログラムが共通のコードを共有するために使用されるライブラリ形式です。プログラムの実行時にロードされ、メモリを効率的に利用できます。
    *   Linuxでは `.so` (Shared Object) ファイル、Windowsでは `.dll` (Dynamic Link Library) ファイル、macOSでは `.dylib` ファイルとして知られています。
    *   **動的リンク**: プログラムが実行時に共有ライブラリをロードし、その中の関数やデータを利用する方式です。静的リンクと比較して、バイナリサイズを小さくし、メモリ使用量を削減できる可能性があります。また、ライブラリの更新が容易になるという利点もあります。

4.  **Goのビルドフラグ**:
    Goのビルドプロセスでは、コンパイラやリンカに渡す追加のフラグを指定できます。
    *   `gcflags`: Goコンパイラ (`go tool compile`) に渡すフラグ。
    *   `asmflags`: Goアセンブラ (`go tool asm`) に渡すフラグ。
    *   `ldflags`: Goリンカ (`go tool link`) に渡すフラグ。
    *   `-dynlink`: コンパイラやリンカに、動的リンクを考慮したコード生成やリンクを行うよう指示するフラグ。

5.  **Goのパッケージとビルドコンテキスト**:
    *   `Package` 構造体: Goのパッケージに関する情報（インポートパス、ソースファイル、ビルド設定など）を保持します。
    *   `builder` 構造体: Goのビルドプロセス全体を管理するオブジェクト。ビルドの依存関係、アクションの実行などを担当します。
    *   `action` 構造体: ビルドプロセスにおける個々のアクション（コンパイル、リンク、インストールなど）を表します。

## 技術的詳細

このコミットは、Goのビルドシステムに `-buildmode=shared` オプションを統合するために、主に `src/cmd/go/build.go` ファイルに大幅な変更を加えています。

1.  **`buildModeInit()` 関数の変更**:
    *   この関数は、`go build` や `go install` コマンドが実行された際に、指定されたビルドモードに基づいてビルド設定を初期化する役割を担っています。
    *   `case "shared":` ブロックが新たに追加されました。
    *   `pkgsFilter = pkgsNotMain`: `shared` モードでは、`main` パッケージ（実行可能ファイルを生成するパッケージ）は対象外となり、ライブラリパッケージのみが処理されます。
    *   プラットフォームの制限: 当初は `linux/amd64` のみがサポートされており、それ以外のプラットフォームではエラーとなるように設定されています。これは、共有ライブラリのサポートが特定の環境から段階的に導入される一般的なアプローチです。
    *   `-o` フラグとの非互換性: `-buildmode=shared` と `-o` (出力ファイル名を指定するオプション) は同時に使用できないように制限が追加されました。これは、共有ライブラリの命名規則が内部的に決定されるためと考えられます。
    *   `codegenArg = "-dynlink"`: コンパイラとアセンブラに動的リンク用のコードを生成するよう指示する `-dynlink` フラグが設定されます。これは、生成されるコードが共有ライブラリとして適切に機能するために不可欠です。
    *   `ldBuildmode = "shared"`: リンカに対して、共有ライブラリを生成するモードであることを伝えます。

2.  **`codegenArg` の適用ロジックの変更**:
    *   以前は `c-shared` モードでのみ `buildGcflags` に `codegenArg` が直接追加されていましたが、このコミットにより、`codegenArg` は `buildAsmflags` と `buildGcflags` の両方に適用されるようになりました。これにより、アセンブラとコンパイラの両方が動的リンクに対応したコードを生成するようになります。

3.  **`runBuild()` 関数の変更**:
    *   `buildBuildmode == "shared"` の場合に、`b.libaction(libname(args))` を呼び出して共有ライブラリをビルドするためのアクションを生成するロジックが追加されました。
    *   `a.deps = append(a.deps, b.action(mode, depMode, p))` の行で、`modeBuild` ではなく `mode` 変数を使用するように変更され、`shared` モードでのビルド動作が適切に伝播されるようになりました。

4.  **`libname()` 関数の追加**:
    *   この新しい関数は、`-buildmode=shared` でビルドされる共有ライブラリのファイル名を生成するロジックをカプセル化しています。
    *   入力されたパッケージパス（例: `std`, `gopkg.in/tomb.v2`）から、`libstd.so` や `libgopkg.in-tomb.v2.so` のような形式のファイル名を生成します。
    *   `/...` のサフィックスを削除し、`/` を `-` に置換するなどのルールが適用されます。これは、ファイルシステム上のパスを共有ライブラリの命名規則に適合させるための処理です。

5.  **`runInstall()` 関数の変更**:
    *   `buildModeInit()` の呼び出しが `runInstall` の冒頭に追加され、インストールプロセスでもビルドモードの初期化が確実に行われるようになりました。
    *   `buildBuildmode == "shared"` の場合の特別な処理が追加されました。
        *   `libdir` の決定: 共有ライブラリがインストールされるディレクトリを決定します。
        *   `a.f = (*builder).install`: 最終的なインストールアクションとして `install` メソッドが設定されます。
        *   `linkSharedAction := b.libaction(libfilename)`: 共有ライブラリをリンクするためのアクションが作成されます。
        *   `installShlibname` アクションの追加: 各パッケージに対して `.shlibname` ファイル（共有ライブラリの名前を記録するファイル）をインストールするアクションが追加されます。これは、Goのリンカが共有ライブラリの依存関係を解決するために使用するメタデータの一部と考えられます。
        *   依存関係の連鎖: `installShlibname` アクションが `linkSharedAction` に依存し、`linkSharedAction` が個々のパッケージのインストールアクションに依存するように、アクションの依存関係が構築されます。これにより、正しい順序でビルドとインストールが行われます。

6.  **`libaction()` 関数の追加**:
    *   `builder` 型に新しいメソッド `libaction` が追加されました。これは、共有ライブラリをリンクするための `action` オブジェクトを生成します。
    *   `a.f = (*builder).linkShared`: このアクションが実行される際に `linkShared` メソッドが呼び出されるように設定されます。
    *   `a.target = filepath.Join(b.work, libname)`: 共有ライブラリの出力パスを設定します。

7.  **`installShlibname()` 関数の追加**:
    *   この関数は、共有ライブラリのベース名を内容とする `.shlibname` ファイルを生成し、インストールします。これは、Goのビルドシステムが共有ライブラリの依存関係を追跡し、適切にリンクするために必要な内部的なメカニズムです。

8.  **`linkShared()` 関数の追加**:
    *   この関数は、共有ライブラリを実際にリンクする処理を担います。
    *   `gcToolchain.ld` からのコピーペーストとコメントされており、既存のリンカロジックを再利用していることが示唆されています。
    *   `ldflags` には、インストールサフィックスやその他のリンカフラグが追加されます。
    *   特に重要なのは、`for _, d := range a.deps { ... ldflags = append(ldflags, d.p.ImportPath+"="+d.target) }` の部分です。これは、共有ライブラリに含めるべき各Goパッケージのインポートパスと、それに対応するコンパイル済みオブジェクトファイルのパスをリンカに渡します。これにより、リンカはこれらのパッケージのコードを共有ライブラリに組み込むことができます。
    *   `tool(archChar() + "l")` を使用して、アーキテクチャに応じたリンカ（例: `amd64l`）を呼び出します。

9.  **ドキュメントの更新**:
    *   `src/cmd/go/doc.go` と `src/cmd/go/help.go` に、`-buildmode=shared` オプションに関する説明が追加されました。これにより、ユーザーは `go help buildmode` コマンドなどでこの新しいオプションの存在と機能を知ることができます。

これらの変更は、Goのビルドシステムが共有ライブラリを生成するための複雑なロジックを内部的に処理できるようにするためのものです。特に、ビルドモードの初期化、共有ライブラリの命名規則、そしてインストールプロセスにおける依存関係の管理が重要なポイントとなります。

## コアとなるコードの解説

1.  **`buildModeInit()` 関数内の `case "shared":` ブロック**:
    *   このブロックは、`go install -buildmode=shared` が指定されたときに実行されるビルド設定の初期化を定義します。
    *   `pkgsFilter = pkgsNotMain` は、`main` パッケージ（実行可能ファイルを生成するパッケージ）ではなく、ライブラリとして機能するパッケージのみを対象とすることを保証します。
    *   `fatalf` によるプラットフォームチェックは、この機能が `linux/amd64` に限定されていることを示しており、段階的な導入のアプローチを反映しています。
    *   `-o` フラグとの排他制御は、共有ライブラリの出力ファイル名が内部的に決定されるため、ユーザーによる明示的な指定を許可しない設計であることを示唆しています。
    *   `codegenArg = "-dynlink"` は、Goコンパイラとアセンブラに対して、動的リンクに適したコード（例えば、PIC: Position-Independent Code）を生成するよう指示する最も重要な設定です。これにより、生成される共有ライブラリがメモリ上の任意のアドレスにロードされても正しく動作するようになります。
    *   `ldBuildmode = "shared"` は、Goリンカに対して、最終的な出力が共有ライブラリであることを伝え、それに応じたリンク処理を行うよう指示します。

2.  **`libname()` 関数の新規追加**:
    *   この関数は、ユーザーが `go install -buildmode=shared` に渡したパッケージパス（例: `std` や `gopkg.in/tomb.v2`）から、標準的な共有ライブラリの命名規則（`lib<name>.so`）に従ったファイル名を生成します。
    *   `strings.TrimSuffix(arg, "/...")` は、`a/b/...` のようなパターンが指定された場合に、末尾の `...` を取り除き、パッケージのルート名のみを抽出します。
    *   `strings.Replace(arg, "/", "-", -1)` は、パッケージパス内のスラッシュをハイフンに置換することで、ファイル名として有効な形式に変換します。
    *   複数のパッケージが指定された場合は、カンマで連結して単一のライブラリ名とします（例: `liba,b.so`）。これは、複数のGoパッケージを一つの共有ライブラリにまとめることを意図しています。

3.  **`runInstall()` 関数内の `shared` モード処理の追加**:
    *   このセクションは、`-buildmode=shared` が指定された場合の `go install` コマンドの複雑なワークフローを定義します。
    *   `libaction` の生成と `linkSharedAction` への割り当ては、共有ライブラリの最終的なリンクステップを表すアクションを作成します。
    *   `installShlibname` アクションの導入は、Goのビルドシステムが共有ライブラリの依存関係を内部的に管理するためのメタデータ（`.shlibname` ファイル）を生成することを示しています。このファイルには、共有ライブラリのベース名が記述され、Goのリンカが他のGoプログラムをビルドする際に、どの共有ライブラリにリンクすべきかを判断するために利用されます。
    *   アクションの依存関係（`shlibnameaction.deps = append(shlibnameaction.deps, linkSharedAction)` など）は、ビルドの順序を厳密に制御し、共有ライブラリが完全にビルドされてから、そのメタデータが生成・インストールされることを保証します。

4.  **`libaction()` 関数の新規追加**:
    *   このヘルパー関数は、共有ライブラリのリンク処理を担当する `action` オブジェクトを簡潔に作成するためのものです。
    *   `a.f = (*builder).linkShared` は、このアクションが実行される際に `linkShared` メソッドが呼び出されるように設定し、実際のリンク処理を委譲します。

5.  **`installShlibname()` 関数の新規追加**:
    *   この関数は、共有ライブラリのベース名（例: `libstd.so` から `libstd.so`）を内容とする小さなファイル（例: `std.shlibname`）を生成します。このファイルは、Goのビルドシステムが動的リンクを行う際に、どの共有ライブラリに依存しているかを識別するための内部的な参照として機能します。

6.  **`linkShared()` 関数の新規追加**:
    *   この関数は、Goのリンカ（`go tool link`）を呼び出して、実際に共有ライブラリを生成します。
    *   `ldflags` には、インストールサフィックスやその他のリンカフラグが追加されます。
    *   特に重要なのは、`for _, d := range a.deps { ... ldflags = append(ldflags, d.p.ImportPath+"="+d.target) }` の部分です。これは、共有ライブラリに含めるべき各Goパッケージのインポートパスと、それに対応するコンパイル済みオブジェクトファイルのパスをリンカに渡します。これにより、リンカはこれらのパッケージのコードを共有ライブラリに組み込むことができます。
    *   `tool(archChar() + "l")` は、現在のアーキテクチャ（例: `amd64`）に対応するGoリンカ（例: `amd64l`）を動的に選択して実行します。

これらの変更は、Goのビルドシステムが静的リンク中心の設計から、限定的ではあるものの動的リンクをサポートするための基盤を構築したことを示しています。特に、共有ライブラリの命名、ビルド依存関係の管理、そしてリンカへの適切なフラグの引き渡しといった、複雑な側面が考慮されています。

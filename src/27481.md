# [インデックス 27481] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）とリンカ（`cmd/link`）におけるオブジェクトファイルフォーマットの変更と、それに伴うリンカのパフォーマンス改善に関するものです。具体的には、オブジェクトファイル内にリロケーション、PCデータ、自動変数、関数データ、ファイルパスといった各種セクションの総数を記録するようにし、リンカがこれらの情報を利用して、シンボルを格納するためのスライスを事前に連続したメモリ領域に確保できるようにすることで、リンク時間の短縮とメモリ使用量の削減（一部ケースを除く）を実現しています。

## コミット

Goのコンパイラとリンカが生成・処理するオブジェクトファイルに、各種メタデータ（リロケーション、PCデータ、自動変数、関数データ、ファイルパス）の総数を記録する機能を追加しました。これにより、リンカはこれらのデータを格納するためのメモリ領域を事前に効率的に確保できるようになり、リンク処理のパフォーマンスが向上します。ベンチマーク結果では、リンク時間の短縮と、一部ケースでのメモリ使用量の削減が示されています。

## 変更の背景

Goのリンカは、コンパイルされた複数のオブジェクトファイル（`.o`ファイル）を結合して実行可能ファイルやライブラリを生成する役割を担っています。このプロセスでは、各オブジェクトファイルに含まれるシンボル（関数、変数など）やそのメタデータ（リロケーション情報、デバッグ情報、GC情報など）を読み込み、メモリ上に構築する必要があります。

従来のリンカは、これらの情報を読み込む際に、必要なメモリ領域を動的に確保していました。Goの`slice`は、要素を追加する際に容量が不足すると、より大きな新しい配列を確保して既存の要素をコピーするという再割り当て（reallocation）が発生します。この再割り当ては、特に大量のシンボルやメタデータを処理する場合、頻繁に発生し、CPU時間とメモリ使用量のオーバーヘッドを引き起こす可能性があります。また、メモリの断片化も発生しやすくなります。

このコミットの背景には、リンカのパフォーマンスを改善し、特に大規模なGoプログラムのリンク時間を短縮するという目的があります。オブジェクトファイルに各セクションの総数を事前に記録することで、リンカは必要なメモリ量を正確に把握し、一度に適切なサイズの`slice`を確保できるようになります。これにより、動的な再割り当ての回数を劇的に減らし、効率的なメモリ利用と高速なリンク処理を実現しようとしています。

ベンチマーク結果に示されているように、`LinkJuju`の`MaxRSS`（最大常駐セットサイズ）が`+8.29%`と増加しているケースがありますが、これはおそらく、事前に確保するメモリ量が従来よりも大きくなるため、一時的に多くのメモリを消費するものの、再割り当てのオーバーヘッドがなくなることで全体的な処理時間が短縮されるというトレードオフを示唆しています。`GOGC=off`のベンチマークでは`MaxRSS`も減少していることから、このメモリ増加はGoのガベージコレクタが動的に確保されたメモリを管理するオーバーヘッドに関連している可能性も考えられます。

## 前提知識の解説

このコミットを理解するためには、以下のGoの内部構造とリンカの概念に関する知識が必要です。

1.  **Goのオブジェクトファイルフォーマット**:
    *   Goのコンパイラは、ソースコードをコンパイルしてオブジェクトファイル（通常は`.o`拡張子を持たない内部形式）を生成します。これらのファイルには、機械語コード、データ、シンボル情報、リロケーション情報、デバッグ情報、GC情報などが含まれています。
    *   オブジェクトファイルは、リンカが効率的に読み込めるように特定の構造を持っています。このコミットでは、その構造に「各種セクションの総数」という新しいメタデータが追加されます。

2.  **Goリンカ（`cmd/link`）**:
    *   Goのリンカは、複数のGoオブジェクトファイルとC/C++のオブジェクトファイル（もしあれば）、そしてGoランタイムライブラリを結合して、最終的な実行可能バイナリを生成します。
    *   リンカの主要なタスクには、シンボルの解決（どの関数がどこにあるか）、リロケーションの適用（アドレスの修正）、デバッグ情報の結合、実行可能ファイルのフォーマット（ELF, Mach-O, PEなど）への書き出しなどがあります。

3.  **`LSym` (Linker Symbol)**:
    *   Goのリンカ内部で、関数、グローバル変数、型情報など、プログラム内のあらゆるシンボルを表すデータ構造です。
    *   `LSym`には、シンボルの名前、型、サイズ、実際のデータ（機械語コードや初期値）、そしてそのシンボルに関連するリロケーション情報（`R`フィールド）、PCデータ（`Pcln`フィールド）、自動変数（`Autom`フィールド）などが含まれます。

4.  **リロケーション（Relocation）**:
    *   コンパイル時には、関数呼び出しやグローバル変数へのアクセスのアドレスは確定できません。リンカが最終的なメモリ配置を決定した後に、これらのアドレスを修正する作業をリロケーションと呼びます。
    *   オブジェクトファイルには、どの場所をどのように修正すべきかを示すリロケーション情報が含まれています。

5.  **PCデータ（Program Counter Data）**:
    *   Goのバイナリには、プログラムカウンタ（PC）の値に基づいて様々な情報を取得するためのメタデータが含まれています。これらは主に以下の目的で使用されます。
        *   **スタックトレース**: 実行中のPCから関数名やファイル名、行番号を特定するため。
        *   **ガベージコレクション**: GCがスタック上のポインタを正確に識別し、マークするために、PCに基づいてどのスタックフレームにポインタがあるかを判断します。
        *   **デバッグ**: デバッガがソースコードレベルの情報を提供するため。
    *   PCデータは、`Pcsp`（PC-SPオフセット）、`Pcfile`（PC-ファイル）、`Pcline`（PC-行番号）、`Pcdata`（汎用PCデータ）などのサブセクションに分かれています。

6.  **自動変数（Automatics / Autos）**:
    *   関数内で宣言されるローカル変数で、スタック上に割り当てられます。リンカはこれらの自動変数の情報（名前、型、オフセットなど）を管理し、デバッグ情報やGC情報の一部として利用します。

7.  **関数データ（FuncData）**:
    *   関数に関連付けられた追加のデータへのポインタのリストです。例えば、ガベージコレクションのためのGCビットマップへのポインタなどが含まれます。

8.  **Goの`slice`**:
    *   Goの`slice`は、可変長配列のようなデータ構造です。内部的には、基盤となる配列へのポインタ、長さ（`len`）、容量（`cap`）を持っています。
    *   `append`操作などで`slice`の長さが容量を超えると、Goランタイムはより大きな新しい基盤配列を確保し、既存の要素を新しい配列にコピーします。この操作はコストが高く、頻繁に発生するとパフォーマンスに影響を与えます。
    *   `make([]T, length, capacity)`のように、事前に容量を指定して`slice`を作成することで、再割り当ての回数を減らし、パフォーマンスを向上させることができます。

## 技術的詳細

このコミットの技術的な核心は、Goのオブジェクトファイルフォーマットに新しいメタデータを導入し、リンカがそのメタデータを利用してメモリ割り当てを最適化する点にあります。

### オブジェクトファイルフォーマットの変更

`src/cmd/internal/obj/objfile.go`の`Writeobjfile`関数は、Goのオブジェクトファイルを書き出す役割を担っています。このコミットでは、オブジェクトファイルのデータセクションの前に、以下の総数を記録するようになりました。

*   `total data length`: 全てのシンボルのデータ（コードや初期値）の合計バイト数。
*   `total number of relocations`: 全てのリロケーションエントリの総数。
*   `total number of pcdata`: 全てのPCデータセクションの総数。
*   `total number of automatics`: 全ての自動変数の総数。
*   `total number of funcdata`: 全ての関数データエントリの総数。
*   `total number of files`: 全てのファイルパスエントリの総数。

これらの総数は、`sectionLengths`という新しい構造体で集計され、`wrlengths`関数によってオブジェクトファイルに書き込まれます。

### リンカのメモリ割り当て最適化

`src/cmd/link/internal/ld/objfile.go`の`ldobjfile`関数は、オブジェクトファイルを読み込むリンカ側の主要な関数です。この関数は、オブジェクトファイルから上記の総数を読み取り、`slices`という新しい構造体に格納します。

`slices`構造体は、リロケーション、PCデータ、自動変数、関数データ、ファイルパスといった各要素を格納するための`slice`を保持します。`rdslices`関数は、オブジェクトファイルから読み取った総数に基づいて、これらの`slice`を`make`関数を使って適切な容量で事前に確保します。

```go
type slices struct {
	data        []byte
	reloc       []Reloc
	pcdata      []Pcdata
	autom       []Auto
	funcdata    []*LSym
	funcdataoff []int64
	file        []*LSym
}

func rdslices(f *obj.Biobuf) *slices {
	sl := &slices{}
	// 各セクションの総数を読み込み、それに基づいてsliceをmakeで事前に確保
	n := rdint(f)
	sl.data = make([]byte, n) // 全データ用のバイトスライス
	n = rdint(f)
	sl.reloc = make([]Reloc, n) // 全リロケーション用のスライス
	n = rdint(f)
	sl.pcdata = make([]Pcdata, n) // 全PCデータ用のスライス
	n = rdint(f)
	sl.autom = make([]Auto, n) // 全自動変数用のスライス
	n = rdint(f)
	sl.funcdata = make([]*LSym, n) // 全関数データ用のスライス
	sl.funcdataoff = make([]int64, n)
	n = rdint(f)
	sl.file = make([]*LSym, n) // 全ファイルパス用のスライス
	return sl
}
```

その後、`readsym`関数が個々のシンボルを読み込む際に、これらの事前に確保された`slice`から必要な部分を切り出して（`sl.reloc[:n:n]`のように）、シンボルの`R`、`Autom`、`Pcln.Pcdata`などのフィールドに割り当てます。これにより、シンボルごとに新しい`slice`を`make`したり、既存の`slice`が再割り当てされたりするのを防ぎます。

### `isdup`フラグの導入

`readsym`関数には`isdup`という新しいブールフラグが導入されています。これは、リンカが重複するシンボル（例えば、複数のオブジェクトファイルで同じ名前のシンボルが定義されている場合）を処理する際に使用されます。重複シンボルの場合、そのシンボルに関連するデータは既に別の場所で処理されているため、事前に確保されたグローバルな`slice`からその部分を消費しないように制御します。これにより、メモリの二重消費や誤ったインデックス付けを防ぎます。

### `src/cmd/internal/goobj/read.go`の変更

このファイルは、Goのオブジェクトファイルを読み取るための内部パッケージです。このコミットでは、オブジェクトファイルフォーマットの変更に伴い、新しく追加された長さ情報を読み飛ばすように変更されています。これは、このパッケージの現在の利用目的ではこれらの長さ情報が必要ないため、互換性を保ちつつ、将来的な利用のためにフォーマット変更に対応していることを示しています。

## コアとなるコードの解説

### `src/cmd/internal/obj/objfile.go` における変更

```go
// 新しい構造体 sectionLengths の定義
type sectionLengths struct {
	data     int // 全シンボルのデータ合計バイト数
	reloc    int // 全リロケーションの総数
	pcdata   int // 全PCデータの総数
	autom    int // 全自動変数の総数
	funcdata int // 全関数データの総数
	file     int // 全ファイルパスの総数
}

// LSym から各セクションの長さを集計するメソッド
func (l *sectionLengths) add(s *LSym) {
	l.data += len(s.P) // シンボルのデータ長を加算
	l.reloc += len(s.R) // リロケーション数を加算

	if s.Type != STEXT { // テキストシンボル（関数）以外はPCデータなどを考慮しない
		return
	}

	pc := s.Pcln // PCデータ情報
	l.data += len(pc.Pcsp.P)
	l.data += len(pc.Pcfile.P)
	l.data += len(pc.Pcline.P)
	for i := 0; i < len(pc.Pcdata); i++ {
		l.data += len(pc.Pcdata[i].P)
	}

	l.pcdata += len(pc.Pcdata) // PCデータセクション数を加算

	autom := 0
	for a := s.Autom; a != nil; a = a.Link { // 自動変数をカウント
		autom++
	}
	l.autom += autom // 自動変数数を加算
	l.funcdata += len(pc.Funcdataoff) // 関数データ数を加算
	l.file += len(pc.File) // ファイルパス数を加算
}

// sectionLengths をオブジェクトファイルに書き込む関数
func wrlengths(b *Biobuf, sl sectionLengths) {
	wrint(b, int64(sl.data))
	wrint(b, int64(sl.reloc))
	wrint(b, int64(sl.pcdata))
	wrint(b, int64(sl.autom))
	wrint(b, int64(sl.funcdata))
	wrint(b, int64(sl.file))
}

// Writeobjfile 関数内で sectionLengths を計算し、書き出す部分
func Writeobjfile(ctxt *Link, b *Biobuf) {
	// ... (既存の処理) ...

	var lengths sectionLengths // sectionLengths 構造体を宣言

	// シンボルをイテレートし、各セクションの長さを集計
	for _, s := range ctxt.Text {
		writerefs(ctxt, b, s)
		lengths.add(s) // add メソッドで長さを加算
	}
	for _, s := range ctxt.Data {
		writerefs(ctxt, b, s)
		lengths.add(s) // add メソッドで長さを加算
	}
	Bputc(b, 0xff)

	wrlengths(b, lengths) // 集計した長さをオブジェクトファイルに書き出す

	// ... (既存の処理) ...
}
```
この変更により、コンパイラはオブジェクトファイルを生成する際に、リンカが必要とする各種メタデータの総数を事前に計算し、オブジェクトファイルに埋め込むようになりました。これにより、リンカは後続の処理でこれらの情報を効率的に利用できるようになります。

```go
	// 例: pc.Funcdata = sl.funcdata[:n:n]
	// 例: pc.File = sl.file[:n:n]

	// ... (既存の処理) ...
}
```
リンカ側では、オブジェクトファイルから読み取った総数に基づいて、必要なメモリ領域を一度に確保します。これにより、個々のシンボルを処理する際に発生する`slice`の再割り当てが大幅に削減され、メモリの断片化が抑制されます。`isdup`フラグは、重複シンボルが検出された場合に、そのシンボルに関連するデータが既に処理済みであるため、グローバルなスライスからその部分を「消費」しないように制御するために使用されます。これは、メモリの効率的な利用と正確なデータ管理のために重要です。

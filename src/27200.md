# [インデックス 27200] ファイルの概要

このコミットは、Go言語の標準ライブラリ`net`パッケージにおけるUDPソケット関連コードのリファクタリングに関するものです。具体的には、`UDPAddr`と`UDPConn`に関連する関数とメソッドの重複を解消し、保守性を向上させることを目的としています。プラットフォーム固有のコード（`udpsock_plan9.go`と`udpsock_posix.go`）から共通ロジックを`udpsock.go`に移動することで、コードベースの簡素化と将来的なドキュメント更新の準備を行っています。

## コミット

`net`パッケージ内のUDPソケット関連コードの重複を解消し、特にドキュメントの保守性を高めるために、`UDPAddr`と`UDPConn`に関連する関数とメソッドを統合しました。この変更に続いて、コメントと例が更新される予定です。

## 変更の背景

Go言語の`net`パッケージは、ネットワーク通信機能を提供し、TCP/IPプロトコルスタックを抽象化しています。UDP（User Datagram Protocol）は、コネクションレス型のプロトコルであり、信頼性よりも速度と効率が重視されるアプリケーションで利用されます。

このコミットが行われた背景には、主に以下の点があります。

1.  **コードの重複と保守性の問題**: 以前の`net`パッケージのUDPソケット実装では、POSIX準拠システム（Linux, macOSなど）とPlan 9システム向けに、`ReadFromUDP`や`WriteToUDP`といった高レベルのメソッドがそれぞれ`udpsock_posix.go`と`udpsock_plan9.go`に重複して実装されていました。これらのメソッドは、プラットフォーム固有の低レベルなシステムコールを呼び出す部分を除けば、共通のロジックを多く含んでいました。このような重複は、機能追加やバグ修正の際に両方のファイルで同じ変更を行う必要があり、保守の負担を増やし、バグを導入するリスクを高めていました。

2.  **ドキュメントの整合性**: 重複したコードは、それぞれの実装でドキュメントが異なる可能性があり、APIの理解を妨げる原因となります。共通化により、一貫性のあるドキュメントを提供しやすくなります。コミットメッセージにも「特にドキュメントの保守性のため」と明記されており、ドキュメントの品質向上も重要な目的でした。

3.  **将来的な変更への準備**: コミットメッセージにある「The followup changes will update comments and examples.」という記述から、このコードの共通化が、その後のドキュメントや使用例の更新を容易にするための前提作業であったことが伺えます。

4.  **Issue #10624の解決**: このコミットは、GitHub Issue #10624に関連しています。このIssueは、`net`パッケージのUDP関連のドキュメントと実装の改善を求めるものでした。コードの重複解消は、このIssueを解決するための一環として行われました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **UDP (User Datagram Protocol)**:
    *   TCPと同様にIP上で動作するトランスポート層のプロトコルですが、TCPとは異なり、コネクションの確立や切断、データの順序保証、再送制御、フロー制御、輻輳制御といった信頼性メカニズムを持ちません。
    *   そのため、オーバーヘッドが少なく高速ですが、パケットの損失、重複、順序の入れ替わりが発生する可能性があります。
    *   DNS、NTP、VoIP、オンラインゲームなど、リアルタイム性や低遅延が求められるアプリケーションで利用されます。
    *   Goの`net`パッケージでは、`UDPConn`型がUDPソケットを表します。

*   **Go言語の`net`パッケージ**:
    *   Goの標準ライブラリで、ネットワークI/Oプリミティブを提供します。
    *   TCP/UDP/IPなどのネットワークプロトコルを扱うためのインターフェースや構造体が定義されています。
    *   `net.Conn`インターフェースは、汎用的なストリーム指向ネットワーク接続を表し、`Read`と`Write`メソッドを持ちます。
    *   `net.PacketConn`インターフェースは、汎用的なパケット指向ネットワーク接続を表し、`ReadFrom`と`WriteTo`メソッドを持ちます。これらは、コネクションレス型プロトコル（UDPなど）で、パケットごとに送信元/宛先アドレスを指定・取得するために使用されます。
    *   `net.UDPAddr`はUDPエンドポイントのアドレス（IPアドレスとポート番号）を表す構造体です。
    *   `net.UDPConn`はUDPネットワーク接続の実装であり、`net.Conn`と`net.PacketConn`の両方のインターフェースを満たします。

*   **プラットフォーム固有の実装 (`_posix.go`, `_plan9.go`)**:
    *   Go言語では、異なるオペレーティングシステム（OS）やアーキテクチャに対応するために、ファイル名に`_os.go`や`_arch.go`といったサフィックスを付けて、プラットフォーム固有のコードを記述する慣習があります。
    *   `udpsock_posix.go`は、LinuxやmacOSなどのPOSIX準拠システム向けのUDPソケット実装を含んでいました。
    *   `udpsock_plan9.go`は、Plan 9オペレーティングシステム向けのUDPソケット実装を含んでいました。Plan 9はベル研究所で開発された分散OSで、Go言語の開発に影響を与えたことで知られています。

*   **`syscall`パッケージ**:
    *   Goの`syscall`パッケージは、低レベルなOSプリミティブへのインターフェースを提供します。これには、ファイルI/O、プロセス管理、ネットワークソケット操作などが含まれます。
    *   ネットワーク操作においては、`syscall.Sockaddr`のようなOS固有のソケットアドレス構造体や、`syscall.EINVAL`（無効な引数）のようなエラーコードが利用されます。

*   **`net.OpError`**:
    *   `net`パッケージで発生するネットワーク操作エラーをラップするための構造体です。
    *   `Op`（操作の種類、例: "read", "write", "dial"）、`Net`（ネットワークの種類、例: "udp", "tcp"）、`Source`（送信元アドレス）、`Addr`（宛先アドレス）、`Err`（元のエラー）などの情報を含み、エラーの詳細なコンテキストを提供します。

## 技術的詳細

このコミットの主要な技術的変更は、UDPソケット操作に関する高レベルなメソッド（`ReadFromUDP`, `WriteToUDP`など）の共通ロジックを、プラットフォーム固有のファイルから`src/net/udpsock.go`に移動し、プラットフォーム固有のファイルでは、共通ロジックが呼び出す低レベルなヘルパー関数（`readFrom`, `writeTo`, `readMsg`, `writeMsg`）を実装するように変更した点です。

具体的な変更点は以下の通りです。

1.  **`UDPConn`構造体の定義とコンストラクタの共通化**:
    *   以前は`udpsock_plan9.go`と`udpsock_posix.go`の両方に`UDPConn`構造体の定義と`newUDPConn`関数が存在していましたが、これらが`udpsock.go`に移動され、一元化されました。
    *   `type UDPConn struct { conn }` と `func newUDPConn(fd *netFD) *UDPConn { return &UDPConn{conn{fd}} }` が`udpsock.go`に定義されました。

2.  **高レベルなUDPソケットメソッドの共通化**:
    *   `UDPConn`の以下のメソッドが、`udpsock_plan9.go`と`udpsock_posix.go`から`udpsock.go`に移動されました。
        *   `ReadFromUDP(b []byte) (int, *UDPAddr, error)`
        *   `ReadFrom(b []byte) (int, Addr, error)` (PacketConnインターフェースの実装)
        *   `ReadMsgUDP(b, oob []byte) (n, oobn, flags int, addr *UDPAddr, err error)`
        *   `WriteToUDP(b []byte, addr *UDPAddr) (int, error)`
        *   `WriteTo(b []byte, addr Addr) (int, error)` (PacketConnインターフェースの実装)
        *   `WriteMsgUDP(b, oob []byte, addr *UDPAddr) (n, oobn int, err error)`
    *   これらのメソッドは、共通のエラーハンドリング（`OpError`の生成）や引数チェック（`c.ok()`、`syscall.EINVAL`）を行い、実際の低レベルなI/O操作は、新たに導入されたプラットフォーム固有のヘルパーメソッド（`c.readFrom`, `c.writeTo`, `c.readMsg`, `c.writeMsg`）に委譲する形になりました。

3.  **UDP接続確立・リッスン関数の共通化**:
    *   `DialUDP(net string, laddr, raddr *UDPAddr) (*UDPConn, error)`
    *   `ListenUDP(net string, laddr *UDPAddr) (*UDPConn, error)`
    *   `ListenMulticastUDP(network string, ifi *Interface, gaddr *UDPAddr) (*UDPConn, error)`
    *   これらの関数も`udpsock.go`に移動され、ネットワークタイプチェック、アドレスチェック、`OpError`の生成といった共通ロジックが`udpsock.go`で処理されるようになりました。実際のソケット作成やバインドなどのプラットフォーム固有の処理は、`dialUDP`, `listenUDP`, `listenMulticastUDP`といった内部ヘルパー関数に委譲されます。

4.  **プラットフォーム固有のヘルパーメソッドの導入**:
    *   `udpsock_plan9.go`と`udpsock_posix.go`では、上記で共通化された高レベルメソッドの代わりに、`UDPConn`型に紐付けられた以下の低レベルヘルパーメソッドが実装されました。
        *   `func (c *UDPConn) readFrom(b []byte) (n int, addr *UDPAddr, err error)`
        *   `func (c *UDPConn) readMsg(b, oob []byte) (n, oobn, flags int, addr *UDPAddr, err error)`
        *   `func (c *UDPConn) writeTo(b []byte, addr *UDPAddr) (int, error)`
        *   `func (c *UDPConn) writeMsg(b, oob []byte, addr *UDPAddr) (n, oobn int, err error)`
    *   これらのヘルパーメソッドは、それぞれのプラットフォームのシステムコール（例: `c.fd.Read(buf)`、`c.fd.writeTo(b, sa)`）を直接呼び出し、プラットフォーム固有のソケットアドレス変換などを行います。エラーが発生した場合、`OpError`でラップする前の生のエラーを返します。

このリファクタリングにより、`udpsock.go`はUDPソケットAPIの共通インターフェースと共通ロジックを定義する中心的なファイルとなり、`udpsock_plan9.go`と`udpsock_posix.go`は、その共通インターフェースを各プラットフォームの低レベルなネットワークAPIにマッピングする薄い層として機能するようになりました。

## コアとなるコードの解説

このコミットの核心は、UDPソケット操作における共通の「ビジネスロジック」とプラットフォーム固有の「システムコール呼び出し」を分離した点にあります。

例えば、`UDPConn.ReadFromUDP`メソッドを見てみましょう。

**変更前（`udpsock_posix.go`の例）**:

```go
// ReadFromUDP reads a UDP packet from c, copying the payload into b.
// ...
func (c *UDPConn) ReadFromUDP(b []byte) (int, *UDPAddr, error) {
	if !c.ok() {
		return 0, nil, syscall.EINVAL
	}
	var addr *UDPAddr
	n, sa, err := c.fd.readFrom(b) // 低レベルな読み込み
	switch sa := sa.(type) {
	case *syscall.SockaddrInet4:
		addr = &UDPAddr{IP: sa.Addr[0:], Port: sa.Port}
	case *syscall.SockaddrInet6:
		addr = &UDPAddr{IP: sa.Addr[0:], Port: sa.Port, Zone: zoneToString(int(sa.ZoneId))}
	}
	if err != nil {
		err = &OpError{Op: "read", Net: c.fd.net, Source: c.fd.laddr, Addr: c.fd.raddr, Err: err} // エラーラップ
	}
	return n, addr, err
}
```

この変更前のコードでは、`c.ok()`による接続状態チェック、`c.fd.readFrom(b)`による実際のデータ読み込み、`syscall.Sockaddr`から`UDPAddr`への変換、そして`OpError`によるエラーのラップという一連の処理がすべて`udpsock_posix.go`内に記述されていました。`udpsock_plan9.go`でも同様のロジックが、Plan 9固有の`c.fd.data.Read(buf)`などの呼び出しを使って実装されていました。

**変更後**:

1.  **`src/net/udpsock.go`に移動された`UDPConn.ReadFromUDP`**:

    ```go
    // ReadFromUDP reads a UDP packet from c, copying the payload into b.
    // ...
    func (c *UDPConn) ReadFromUDP(b []byte) (int, *UDPAddr, error) {
        if !c.ok() {
            return 0, nil, syscall.EINVAL
        }
        n, addr, err := c.readFrom(b) // プラットフォーム固有のヘルパーを呼び出す
        if err != nil {
            err = &OpError{Op: "read", Net: c.fd.net, Source: c.fd.laddr, Addr: c.fd.raddr, Err: err} // 共通のエラーラップ
        }
        return n, addr, err
    }
    ```
    `udpsock.go`内の`ReadFromUDP`は、`c.ok()`チェックと`OpError`によるエラーラップという共通ロジックを担当します。実際のデータ読み込みとアドレス変換は、`c.readFrom(b)`という内部ヘルパーメソッドに委譲されます。

2.  **`src/net/udpsock_posix.go`に残された`UDPConn.readFrom`（ヘルパーメソッド）**:

    ```go
    func (c *UDPConn) readFrom(b []byte) (int, *UDPAddr, error) {
        var addr *UDPAddr
        n, sa, err := c.fd.readFrom(b) // 低レベルな読み込み
        switch sa := sa.(type) {
        case *syscall.SockaddrInet4:
            addr = &UDPAddr{IP: sa.Addr[0:], Port: sa.Port}
        case *syscall.SockaddrInet6:
            addr = &UDPAddr{IP: sa.Addr[0:], Port: sa.Port, Zone: zoneToString(int(sa.ZoneId))}
        }
        return n, addr, err // 生のエラーを返す
    }
    ```
    `udpsock_posix.go`の`readFrom`は、プラットフォーム固有の`c.fd.readFrom(b)`を呼び出し、`syscall.Sockaddr`を`UDPAddr`に変換する役割のみを担います。ここでは`OpError`によるエラーラップは行わず、生のエラーを返します。

同様のパターンが`WriteToUDP`, `ReadMsgUDP`, `WriteMsgUDP`などの他のメソッドや、`DialUDP`, `ListenUDP`, `ListenMulticastUDP`関数にも適用されています。

この分離により、以下の利点が得られます。

*   **コードの重複排除**: `c.ok()`チェックや`OpError`の生成といった共通ロジックが`udpsock.go`に一箇所にまとめられ、各プラットフォーム固有のファイルから削除されました。
*   **保守性の向上**: 共通ロジックの変更は`udpsock.go`のみで行えばよくなり、複数のファイルを修正する必要がなくなります。これにより、バグの導入リスクが減少し、コードの理解も容易になります。
*   **ドキュメントの簡素化**: 高レベルなAPIのドキュメントは`udpsock.go`に集約され、一貫性のある説明を提供しやすくなります。
*   **関心事の分離**: 各ファイルが担当する役割が明確になりました。`udpsock.go`は高レベルなAPIと共通ロジック、プラットフォーム固有のファイルは低レベルなシステムコールとのインターフェースを担当します。

このリファクタリングは、Goの標準ライブラリがどのようにして異なるプラットフォームの差異を吸収しつつ、一貫性のあるAPIを提供しているかを示す良い例と言えます。

## 変更の背景

Go言語の`net`パッケージは、ネットワーク通信機能を提供し、TCP/IPプロトコルスタックを抽象化しています。UDP（User Datagram Protocol）は、コネクションレス型のプロトコルであり、信頼性よりも速度と効率が重視されるアプリケーションで利用されます。

このコミットが行われた背景には、主に以下の点があります。

1.  **コードの重複と保守性の問題**: 以前の`net`パッケージのUDPソケット実装では、POSIX準拠システム（Linux, macOSなど）とPlan 9システム向けに、`ReadFromUDP`や`WriteToUDP`といった高レベルのメソッドがそれぞれ`udpsock_posix.go`と`udpsock_plan9.go`に重複して実装されていました。これらのメソッドは、プラットフォーム固有の低レベルなシステムコールを呼び出す部分を除けば、共通のロジックを多く含んでいました。このような重複は、機能追加やバグ修正の際に両方のファイルで同じ変更を行う必要があり、保守の負担を増やし、バグを導入するリスクを高めていました。

2.  **ドキュメントの整合性**: 重複したコードは、それぞれの実装でドキュメントが異なる可能性があり、APIの理解を妨げる原因となります。共通化により、一貫性のあるドキュメントを提供しやすくなります。コミットメッセージにも「特にドキュメントの保守性のため」と明記されており、ドキュメントの品質向上も重要な目的でした。

3.  **将来的な変更への準備**: コミットメッセージにある「The followup changes will update comments and examples.」という記述から、このコードの共通化が、その後のドキュメントや使用例の更新を容易にするための前提作業であったことが伺えます。

4.  **Issue #10624の解決**: このコミットは、GitHub Issue #10624に関連しています。このIssueは、`net`パッケージのUDP関連のドキュメントと実装の改善を求めるものでした。コードの重複解消は、このIssueを解決するための一環として行われました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **UDP (User Datagram Protocol)**:
    *   TCPと同様にIP上で動作するトランスポート層のプロトコルですが、TCPとは異なり、コネクションの確立や切断、データの順序保証、再送制御、フロー制御、輻輳制御といった信頼性メカニズムを持ちません。
    *   そのため、オーバーヘッドが少なく高速ですが、パケットの損失、重複、順序の入れ替わりが発生する可能性があります。
    *   DNS、NTP、VoIP、オンラインゲームなど、リアルタイム性や低遅延が求められるアプリケーションで利用されます。
    *   Goの`net`パッケージでは、`UDPConn`型がUDPソケットを表します。

*   **Go言語の`net`パッケージ**:
    *   Goの標準ライブラリで、ネットワークI/Oプリミティブを提供します。
    *   TCP/UDP/IPなどのネットワークプロトコルを扱うためのインターフェースや構造体が定義されています。
    *   `net.Conn`インターフェースは、汎用的なストリーム指向ネットワーク接続を表し、`Read`と`Write`メソッドを持ちます。
    *   `net.PacketConn`インターフェースは、汎用的なパケット指向ネットワーク接続を表し、`ReadFrom`と`WriteTo`メソッドを持ちます。これらは、コネクションレス型プロトコル（UDPなど）で、パケットごとに送信元/宛先アドレスを指定・取得するために使用されます。
    *   `net.UDPAddr`はUDPエンドポイントのアドレス（IPアドレスとポート番号）を表す構造体です。
    *   `net.UDPConn`はUDPネットワーク接続の実装であり、`net.Conn`と`net.PacketConn`の両方のインターフェースを満たします。

*   **プラットフォーム固有の実装 (`_posix.go`, `_plan9.go`)**:
    *   Go言語では、異なるオペレーティングシステム（OS）やアーキテクチャに対応するために、ファイル名に`_os.go`や`_arch.go`といったサフィックスを付けて、プラットフォーム固有のコードを記述する慣習があります。
    *   `udpsock_posix.go`は、LinuxやmacOSなどのPOSIX準拠システム向けのUDPソケット実装を含んでいました。
    *   `udpsock_plan9.go`は、Plan 9オペレーティングシステム向けのUDPソケット実装を含んでいました。Plan 9はベル研究所で開発された分散OSで、Go言語の開発に影響を与えたことで知られています。

*   **`syscall`パッケージ**:
    *   Goの`syscall`パッケージは、低レベルなOSプリミティブへのインターフェースを提供します。これには、ファイルI/O、プロセス管理、ネットワークソケット操作などが含まれます。
    *   ネットワーク操作においては、`syscall.Sockaddr`のようなOS固有のソケットアドレス構造体や、`syscall.EINVAL`（無効な引数）のようなエラーコードが利用されます。

*   **`net.OpError`**:
    *   `net`パッケージで発生するネットワーク操作エラーをラップするための構造体です。
    *   `Op`（操作の種類、例: "read", "write", "dial"）、`Net`（ネットワークの種類、例: "udp", "tcp"）、`Source`（送信元アドレス）、`Addr`（宛先アドレス）、`Err`（元のエラー）などの情報を含み、エラーの詳細なコンテキストを提供します。

## 技術的詳細

このコミットの主要な技術的変更は、UDPソケット操作に関する高レベルなメソッド（`ReadFromUDP`, `WriteToUDP`など）の共通ロジックを、プラットフォーム固有のファイルから`src/net/udpsock.go`に移動し、プラットフォーム固有のファイルでは、共通ロジックが呼び出す低レベルなヘルパー関数（`readFrom`, `writeTo`, `readMsg`, `writeMsg`）を実装するように変更した点です。

具体的な変更点は以下の通りです。

1.  **`UDPConn`構造体の定義とコンストラクタの共通化**:
    *   以前は`udpsock_plan9.go`と`udpsock_posix.go`の両方に`UDPConn`構造体の定義と`newUDPConn`関数が存在していましたが、これらが`udpsock.go`に移動され、一元化されました。
    *   `type UDPConn struct { conn }` と `func newUDPConn(fd *netFD) *UDPConn { return &UDPConn{conn{fd}} }` が`udpsock.go`に定義されました。

2.  **高レベルなUDPソケットメソッドの共通化**:
    *   `UDPConn`の以下のメソッドが、`udpsock_plan9.go`と`udpsock_posix.go`から`udpsock.go`に移動されました。
        *   `ReadFromUDP(b []byte) (int, *UDPAddr, error)`
        *   `ReadFrom(b []byte) (int, Addr, error)` (PacketConnインターフェースの実装)
        *   `ReadMsgUDP(b, oob []byte) (n, oobn, flags int, addr *UDPAddr, err error)`
        *   `WriteToUDP(b []byte, addr *UDPAddr) (int, error)`
        *   `WriteTo(b []byte, addr Addr) (int, error)` (PacketConnインターフェースの実装)
        *   `WriteMsgUDP(b, oob []byte, addr *UDPAddr) (n, oobn int, err error)`
    *   これらのメソッドは、共通のエラーハンドリング（`OpError`の生成）や引数チェック（`c.ok()`、`syscall.EINVAL`）を行い、実際の低レベルなI/O操作は、新たに導入されたプラットフォーム固有のヘルパーメソッド（`c.readFrom`, `c.writeTo`, `c.readMsg`, `c.writeMsg`）に委譲する形になりました。

3.  **UDP接続確立・リッスン関数の共通化**:
    *   `DialUDP(net string, laddr, raddr *UDPAddr) (*UDPConn, error)`
    *   `ListenUDP(net string, laddr *UDPAddr) (*UDPConn, error)`
    *   `ListenMulticastUDP(network string, ifi *Interface, gaddr *UDPAddr) (*UDPConn, error)`
    *   これらの関数も`udpsock.go`に移動され、ネットワークタイプチェック、アドレスチェック、`OpError`の生成といった共通ロジックが`udpsock.go`で処理されるようになりました。実際のソケット作成やバインドなどのプラットフォーム固有の処理は、`dialUDP`, `listenUDP`, `listenMulticastUDP`といった内部ヘルパー関数に委譲されます。

4.  **プラットフォーム固有のヘルパーメソッドの導入**:
    *   `udpsock_plan9.go`と`udpsock_posix.go`では、上記で共通化された高レベルメソッドの代わりに、`UDPConn`型に紐付けられた以下の低レベルヘルパーメソッドが実装されました。
        *   `func (c *UDPConn) readFrom(b []byte) (n int, addr *UDPAddr, err error)`
        *   `func (c *UDPConn) readMsg(b, oob []byte) (n, oobn, flags int, addr *UDPAddr, err error)`
        *   `func (c *UDPConn) writeTo(b []byte, addr *UDPAddr) (int, error)`
        *   `func (c *UDPConn) writeMsg(b, oob []byte, addr *UDPAddr) (n, oobn int, err error)`
    *   これらのヘルパーメソッドは、それぞれのプラットフォームのシステムコール（例: `c.fd.Read(buf)`、`c.fd.writeTo(b, sa)`）を直接呼び出し、プラットフォーム固有のソケットアドレス変換などを行います。エラーが発生した場合、`OpError`でラップする前の生のエラーを返します。

このリファクタリングにより、`udpsock.go`はUDPソケットAPIの共通インターフェースと共通ロジックを定義する中心的なファイルとなり、`udpsock_plan9.go`と`udpsock_posix.go`は、その共通インターフェースを各プラットフォームの低レベルなネットワークAPIにマッピングする薄い層として機能するようになりました。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/net/udpsock.go`**:
    *   `UDPConn`構造体の定義が追加されました。
    *   `newUDPConn`関数が追加されました。
    *   `UDPConn`の以下のメソッドが追加されました（これらは以前`udpsock_plan9.go`と`udpsock_posix.go`に存在していました）。
        *   `ReadFromUDP`
        *   `ReadFrom`
        *   `ReadMsgUDP`
        *   `WriteToUDP`
        *   `WriteTo`
        *   `WriteMsgUDP`

3.  **`src/net/udpsock_posix.go`**:
    *   `UDPConn`構造体の定義と`newUDPConn`関数が削除されました。
    *   `ReadFromUDP`, `ReadFrom`, `ReadMsgUDP`, `WriteToUDP`, `WriteTo`, `WriteMsgUDP`, `DialUDP`, `ListenUDP`, `ListenMulticastUDP` の各関数/メソッドが削除されました。

## コアとなるコードの解説

このコミットの核心は、UDPソケット操作における共通の「ビジネスロジック」とプラットフォーム固有の「システムコール呼び出し」を分離した点にあります。

例えば、`UDPConn.ReadFromUDP`メソッドを見てみましょう。

**変更前（`udpsock_posix.go`の例）**:

```go
// ReadFromUDP reads a UDP packet from c, copying the payload into b.
// ...
func (c *UDPConn) ReadFromUDP(b []byte) (int, *UDPAddr, error) {
	if !c.ok() {
		return 0, nil, syscall.EINVAL
	}
	var addr *UDPAddr
	n, sa, err := c.fd.readFrom(b) // 低レベルな読み込み
	switch sa := sa.(type) {
	case *syscall.SockaddrInet4:
		addr = &UDPAddr{IP: sa.Addr[0:], Port: sa.Port}
	case *syscall.SockaddrInet6:
		addr = &UDPAddr{IP: sa.Addr[0:], Port: sa.Port, Zone: zoneToString(int(sa.ZoneId))}
	}
	if err != nil {
		err = &OpError{Op: "read", Net: c.fd.net, Source: c.fd.laddr, Addr: c.fd.raddr, Err: err} // エラーラップ
	}
	return n, addr, err
}
```

この変更前のコードでは、`c.ok()`による接続状態チェック、`c.fd.readFrom(b)`による実際のデータ読み込み、`syscall.Sockaddr`から`UDPAddr`への変換、そして`OpError`によるエラーのラップという一連の処理がすべて`udpsock_posix.go`内に記述されていました。`udpsock_plan9.go`でも同様のロジックが、Plan 9固有の`c.fd.data.Read(buf)`などの呼び出しを使って実装されていました。

**変更後**:

1.  **`src/net/udpsock.go`に移動された`UDPConn.ReadFromUDP`**:

    ```go
    // ReadFromUDP reads a UDP packet from c, copying the payload into b.
    // ...
    func (c *UDPConn) ReadFromUDP(b []byte) (int, *UDPAddr, error) {
        if !c.ok() {
            return 0, nil, syscall.EINVAL
        }
        n, addr, err := c.readFrom(b) // プラットフォーム固有のヘルパーを呼び出す
        if err != nil {
            err = &OpError{Op: "read", Net: c.fd.net, Source: c.fd.laddr, Addr: c.fd.raddr, Err: err} // 共通のエラーラップ
        }
        return n, addr, err
    }
    ```
    `udpsock.go`内の`ReadFromUDP`は、`c.ok()`チェックと`OpError`によるエラーラップという共通ロジックを担当します。実際のデータ読み込みとアドレス変換は、`c.readFrom(b)`という内部ヘルパーメソッドに委譲されます。

2.  **`src/net/udpsock_posix.go`に残された`UDPConn.readFrom`（ヘルパーメソッド）**:

    ```go
    func (c *UDPConn) readFrom(b []byte) (int, *UDPAddr, error) {
        var addr *UDPAddr
        n, sa, err := c.fd.readFrom(b) // 低レベルな読み込み
        switch sa := sa.(type) {
        case *syscall.SockaddrInet4:
            addr = &UDPAddr{IP: sa.Addr[0:], Port: sa.Port}
        case *syscall.SockaddrInet6:
            addr = &UDPAddr{IP: sa.Addr[0:], Port: sa.Port, Zone: zoneToString(int(sa.ZoneId))}
        }
        return n, addr, err // 生のエラーを返す
    }
    ```
    `udpsock_posix.go`の`readFrom`は、プラットフォーム固有の`c.fd.readFrom(b)`を呼び出し、`syscall.Sockaddr`を`UDPAddr`に変換する役割のみを担います。ここでは`OpError`によるエラーラップは行わず、生のエラーを返します。

同様のパターンが`WriteToUDP`, `ReadMsgUDP`, `WriteMsgUDP`などの他のメソッドや、`DialUDP`, `ListenUDP`, `ListenMulticastUDP`関数にも適用されています。

この分離により、以下の利点が得られます。

*   **コードの重複排除**: `c.ok()`チェックや`OpError`の生成といった共通ロジックが`udpsock.go`に一箇所にまとめられ、各プラットフォーム固有のファイルから削除されました。
*   **保守性の向上**: 共通ロジックの変更は`udpsock.go`のみで行えばよくなり、複数のファイルを修正する必要がなくなります。これにより、バグの導入リスクが減少し、コードの理解も容易になります。
*   **ドキュメントの簡素化**: 高レベルなAPIのドキュメントは`udpsock.go`に集約され、一貫性のある説明を提供しやすくなります。
*   **関心事の分離**: 各ファイルが担当する役割が明確になりました。`udpsock.go`は高レベルなAPIと共通ロジック、プラットフォーム固有のファイルは低レベルなシステムコールとのインターフェースを担当します。

このリファクタリングは、Goの標準ライブラリがどのようにして異なるプラットフォームの差異を吸収しつつ、一貫性のあるAPIを提供しているかを示す良い例と言えます。

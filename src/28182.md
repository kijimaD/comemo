## 元コミット内容

`runtime/cgo: add context argument to crosscall2 on mips64`

このコミットは、Goランタイムの`cgo`コンポーネントにおいて、MIPS64アーキテクチャ向けの`crosscall2`関数にコンテキスト引数を追加するものです。

## 変更の背景

Go言語の`cgo`メカニズムは、GoコードとCコードの間で相互運用を可能にするためのものです。特に、CコードからGoコード内の関数を呼び出す（コールバック）際には、`crosscall2`のような特殊なアセンブリ関数が使用されます。これらの関数は、GoとCの異なる呼び出し規約、スタックフレーム、レジスタ使用法を橋渡しする役割を担います。

以前の`crosscall2`の実装では、Go関数に渡せる引数の数に制限がありました。しかし、Goランタイムの進化や、CコードからGoコードへより複雑な状態や情報を渡す必要性が生じたため、追加の「コンテキスト」引数を渡せるようにする要求が出てきました。このコンテキスト引数は、Goのガベージコレクタが追跡できるGoの値をCコード経由で安全に受け渡しするために特に重要です。

MIPS64アーキテクチャは、Goがサポートする多くのアーキテクチャの一つであり、他のアーキテクチャと同様に、`cgo`の機能が完全にサポートされる必要があります。このコミットは、MIPS64における`crosscall2`が、他のアーキテクチャと同様に、より柔軟なコールバックメカニズムを提供できるようにするためのものです。

## 前提知識の解説

*   **cgo**: Go言語がC言語のコードを呼び出したり、C言語のコードからGo言語のコードを呼び出したりするためのメカニズムです。これにより、既存のCライブラリをGoプロジェクトで利用したり、パフォーマンスが重要な部分をCで記述したりすることが可能になります。
*   **crosscall2**: `cgo`において、CコードからGoコードへのコールバックを処理するためにGoランタイムが提供する低レベルのアセンブリ関数です。Cの呼び出し規約からGoの呼び出し規約への変換、レジスタの保存と復元、スタックフレームの調整などを行います。
*   **MIPS64**: MIPSアーキテクチャの64ビット版です。RISC（Reduced Instruction Set Computer）アーキテクチャの一種で、組み込みシステムやネットワーク機器などで広く使用されています。Goランタイムは、MIPS64を含む複数のアーキテクチャをサポートしています。
*   **呼び出し規約 (Calling Convention)**: 関数が呼び出される際に、引数をどのように渡し、戻り値をどのように返し、レジスタをどのように使用するかといった、関数呼び出しに関する取り決めです。CとGoでは異なる呼び出し規約を持つため、`cgo`はこれらを適切に変換する必要があります。
*   **レジスタ (Registers)**: CPU内部にある高速な記憶領域で、プログラムの実行中にデータやアドレスを一時的に保持するために使用されます。関数呼び出しの際には、引数や戻り値がレジスタを介して渡されることがよくあります。
*   **スタックフレーム (Stack Frame)**: 関数が呼び出されるたびに、その関数のローカル変数、引数、戻りアドレス、保存されたレジスタなどが格納されるメモリ領域です。スタックフレームのサイズは、関数が必要とするメモリ量によって決まります。
*   **`uintptr`**: Go言語における符号なし整数型で、ポインタを保持するのに十分な大きさがあります。`cgo`では、GoのポインタをCの`void*`として渡し、C側でその値を変更せずにGoに戻す際に、`uintptr`として扱うことが一般的です。これにより、Goのガベージコレクタがポインタの内容を追跡できなくなる問題を回避しつつ、Goの値をC経由で受け渡す「コンテキスト」として利用できます。
*   **`cgo.Handle`**: Go 1.17で導入された`cgo`パッケージの機能で、任意のGoの値を整数値としてCコードに安全に渡すためのメカニズムです。C側ではこの整数値を`void*`として扱い、Go側に戻ってきた際に元のGoの値を復元できます。これにより、Goのガベージコレクタの追跡を妨げずに、Goの値をC経由で受け渡す「コンテキスト」を安全に実現できます。このコミットの時点では`cgo.Handle`はまだ存在していませんが、この変更はそのような安全なコンテキスト受け渡しを可能にする基盤となります。

## 技術的詳細

このコミットの核心は、MIPS64アーキテクチャにおける`crosscall2`アセンブリ関数のシグネチャと実装の変更です。

1.  **関数シグネチャの変更**:
    元の`crosscall2`のコメント上のシグネチャは以下のようでした。
    `void crosscall2(void (*fn)(void*, int32), void*, int32)`
    これが以下のように変更されました。
    `void crosscall2(void (*fn)(void*, int32, uintptr), void*, int32, uintptr)`
    この変更は、`fn`（Go側のコールバック関数）が受け取る引数に`uintptr`型のコンテキスト引数が追加されたことを示しています。また、`crosscall2`自体も最後の引数として`uintptr`を受け取るようになっています。これは、C側からGo側へ渡される追加のコンテキスト情報に対応します。

2.  **スタックフレームサイズの調整**:
    `crosscall2`関数は、GoとCの呼び出し規約の橋渡しをするために、呼び出し元（C側）のレジスタを保存し、Go側の関数を呼び出す前に必要なレジスタを設定し、Go関数からの戻り後にレジスタを復元します。
    変更前は、スタックフレームのサイズを確保するために`ADDV $(-8*22), R29`という命令がありました。これは22個の8バイトレジスタ（またはそれに相当するデータ）を保存するための領域を確保していることを意味します。
    変更後は、`ADDV $(-8*23), R29`となり、スタックフレームのサイズが8バイト分（1レジスタ分）増加しています。これは、追加のコンテキスト引数を処理するために、さらに1つのレジスタを保存・復元する必要が生じたためです。

3.  **レジスタの保存と復元**:
    MIPS64の呼び出し規約では、関数引数は特定のレジスタ（例: `R4`, `R5`, `R6`, `R7`など）を介して渡されます。このコミットでは、`crosscall2`が受け取る引数の数が増えたため、追加のレジスタを保存・復元する必要があります。
    具体的には、変更前は`R5`と`R6`が引数として扱われ、それ以外のカリィセーブレジスタ（`R16`から`R23`など）が保存されていました。
    変更後には、`R7`レジスタが新たに保存・復元される対象に追加されています。これは、新しい`uintptr`コンテキスト引数がMIPS64の呼び出し規約に従って`R7`レジスタを介して渡されるためです。
    -   `MOVV R7, (8*3)(R29)`: `R7`レジスタの値をスタックフレームのオフセット`8*3`の位置に保存します。
    -   `MOVV (8*3)(R29), R7`: スタックフレームから`R7`レジスタの値を復元します。

これらの変更により、MIPS64アーキテクチャにおいても、`crosscall2`を介してGo関数に3つの引数（`void*`, `int32`, `uintptr`）を渡すことが可能になり、より柔軟な`cgo`コールバックが実現されます。

## コアとなるコードの解説

このアセンブリコードは、MIPS64アーキテクチャにおける`crosscall2`関数の実装です。GoのアセンブリはPlan 9アセンブラの構文を使用しており、一般的なGAS（GNU Assembler）構文とは異なります。

1.  **`TEXT crosscall2(SB),NOSPLIT,$-8`**:
    -   `TEXT`は関数の開始を宣言します。
    -   `crosscall2(SB)`は、`crosscall2`という名前の関数を定義し、`SB`（Static Base）を基準としたアドレス指定を使用することを示します。
    -   `NOSPLIT`は、この関数がスタックを分割しないことを示します。これは、非常に短い関数や、スタックの分割が不適切な低レベル関数でよく使用されます。
    -   `$-8`は、この関数の引数と戻り値の合計サイズが8バイトであることを示します。

2.  **スタックフレームの調整**:
    -   `ADDV $(-8*23), R29`: スタックポインタ`R29`（MIPS64では通常`SP`レジスタ）から`8*23`バイト（184バイト）を減算し、新しいスタックフレームのための領域を確保します。これは、23個の64ビットレジスタ（またはそれに相当するデータ）を保存するためのスペースです。変更前は`8*22`（176バイト）でした。

3.  **レジスタの保存**:
    -   `MOVV R5, (8*1)(R29)`: `R5`レジスタの値を、スタックポインタ`R29`から`8*1`バイトオフセットしたアドレスに保存します。
    -   `MOVV R6, (8*2)(R29)`: `R6`レジスタの値を、スタックポインタ`R29`から`8*2`バイトオフセットしたアドレスに保存します。
    -   `MOVV R7, (8*3)(R29)`: **この行が追加された変更点です。** `R7`レジスタの値を、スタックポインタ`R29`から`8*3`バイトオフセットしたアドレスに保存します。これは、新しいコンテキスト引数を保持するレジスタを保存するためです。
    -   以降、`R16`から`R23`、`RSB`、`g`（Goのgoroutine構造体へのポインタ）、`R31`（リンクレジスタ）、そして浮動小数点レジスタ`F24`から`F31`が同様にスタックに保存されます。これらはGoの呼び出し規約においてカリィセーブレジスタ（呼び出された関数が保存・復元する責任を持つレジスタ）に相当します。

4.  **Go ABI環境の初期化**:
    -   `// Initialize Go ABI environment`
    -   `// prepare SB register = PC & 0xffffffff00000000`
    -   これらのコメントは、GoのABI（Application Binary Interface）に従って環境をセットアップしていることを示唆しています。特に`SB`レジスタの準備は、Goのコードが正しく実行されるために重要です。

5.  **Go関数呼び出し**:
    -   `MOVV (8*0)(R29), R4`: `crosscall2`の最初の引数（Go側のコールバック関数`fn`のアドレス）をスタックから`R4`レジスタにロードします。MIPS64の呼び出し規約では、最初の引数は`R4`に渡されます。
    -   `MOVV (8*1)(R29), R5`: `crosscall2`の2番目の引数（`fn`の最初の引数）をスタックから`R5`レジスタにロードします。
    -   `MOVV (8*2)(R29), R6`: `crosscall2`の3番目の引数（`fn`の2番目の引数）をスタックから`R6`レジスタにロードします。
    -   `MOVV (8*3)(R29), R7`: **この行が追加された変更点です。** `crosscall2`の4番目の引数（`fn`の3番目の引数、すなわち新しいコンテキスト引数）をスタックから`R7`レジスタにロードします。
    -   `JALR R4`: `R4`レジスタに格納されているアドレス（Go側のコールバック関数`fn`）にジャンプし、リンクレジスタ`R31`に現在の戻りアドレスを保存します。これにより、Go関数が実行されます。

6.  **レジスタの復元**:
    -   Go関数からの戻り後、保存されていたレジスタが逆の順序でスタックから復元されます。
    -   `MOVV (8*3)(R29), R7`: **この行が追加された変更点です。** スタックから`R7`レジスタの値を復元します。
    -   以降、`R16`から`R23`、`RSB`、`g`、`R31`、`F24`から`F31`が復元されます。
    -   `MOVV (8*1)(R29), R5`と`MOVV (8*2)(R29), R6`は、`crosscall2`の引数として渡された元の`R5`と`R6`の値を復元します。

7.  **スタックポインタの復元**:
    -   `ADDV $(8*23), R29`: スタックポインタ`R29`に`8*23`バイトを加算し、スタックフレームを解放します。変更前は`8*22`でした。

8.  **`RET`**:
    -   関数から戻ります。

この変更により、MIPS64アーキテクチャの`cgo`コールバックにおいて、Go関数に`uintptr`型のコンテキスト引数を渡すための低レベルな基盤が整備されました。これにより、Goのガベージコレクタと協調しながら、CコードとGoコードの間でより複雑な状態を安全に受け渡すことが可能になります。

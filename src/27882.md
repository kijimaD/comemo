# [インデックス 27882] ファイルの概要

このコミットは、Goコンパイラにおける構造体リテラルのキーとしてドット式（セレクタ式）が誤って使用された場合に、適切なエラーを報告するように修正するものです。具体的には、`src/cmd/compile/internal/gc/typecheck.go`内の型チェックロジックが更新され、`OXDOT`（ドット式を表す内部表現）が構造体リテラルのキーとして検出された場合にエラーを発生させるようになります。また、この修正を検証するための新しいテストケース`test/fixedbugs/issue15311.go`が追加されています。

## 変更の背景

Go言語において、構造体リテラルは`TypeName{Field: Value}`のような形式でフィールドに値を割り当てて構造体のインスタンスを初期化するために使用されます。ここで`Field`の部分には、構造体の定義で宣言されたフィールド名が直接記述される必要があります。

このコミットが修正する問題は、Goコンパイラが、`foo.toInt: make(map[string]int)`のように、構造体リテラルのキーとしてドット式（例: `foo.toInt`）が使用された場合に、適切なコンパイルエラーを報告できていなかった点にあります。このような記述はGoの文法上不正であり、コンパイラはこれを検出し、開発者にエラーとして通知するべきです。

以前のコンパイラの挙動では、`l.Left.Sym`が`nil`である場合にのみエラーを報告していましたが、ドット式（`OXDOT`）の場合、`l.Left.Sym`は`nil`ではないため、このチェックをすり抜けてしまっていました。結果として、不正なコードがコンパイルエラーにならず、予期せぬ動作や後続のコンパイルフェーズでの問題を引き起こす可能性がありました。

この変更は、Goコンパイラの堅牢性を高め、Go言語の仕様に厳密に従わないコードに対して、より正確なエラーメッセージを提供することを目的としています。`Fixes #15311`という記述から、この問題が特定のバグトラッカーの課題として認識され、修正されたことがわかります。

## 前提知識の解説

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。複数のフェーズ（字句解析、構文解析、型チェック、最適化、コード生成など）を経てコンパイルを行います。
*   **構造体リテラル (Struct Literal)**: Go言語で構造体の新しいインスタンスを作成し、そのフィールドを初期化するための構文です。例: `type Point { X, Y int }; p := Point{X: 10, Y: 20}`。
*   **ドット式 (Dot Expression / Selector Expression)**: `object.field`や`package.identifier`のように、ドット（`.`）を使って構造体のフィールドやパッケージのエクスポートされた識別子にアクセスする式です。コンパイラの内部では`OXDOT`というオペレーションコードで表現されることがあります。
*   **型チェック (Type Checking)**: コンパイラのフェーズの一つで、プログラムがGo言語の型システム規則に準拠しているかを確認します。例えば、変数の型と代入される値の型が一致するか、関数呼び出しの引数の型が正しいかなどを検証します。
*   **`OXDOT`**: Goコンパイラの内部表現（ASTノードのオペレーションコード）の一つで、ドット式（セレクタ式）を表します。例えば、`foo.bar`という式は、AST上では`OXDOT`ノードとして表現されます。
*   **`toolstash -cmp`**: Goプロジェクトで使われる内部ツールの一つで、コンパイラの変更が既存のコードベースのコンパイル結果に予期せぬ影響を与えないことを検証するために使用されます。通常、変更前後のコンパイル結果（例えば、生成されるバイナリや中間表現）を比較し、差異がないことを確認します。これにより、コンパイラの変更が意図しない副作用を引き起こしていないことを保証します。
*   **`Yyerror`**: Goコンパイラの内部関数で、コンパイルエラーを報告するために使用されます。

## 技術的詳細

このコミットの核心は、Goコンパイラの型チェックフェーズにおける構造体リテラルの処理ロジックの改善にあります。

Goコンパイラは、ソースコードを抽象構文木（AST）に変換し、そのASTを走査しながら型チェックを行います。構造体リテラルを処理する関数`typecheckcomplit`は、リテラル内の各フィールドと値のペアを検証します。

変更前のコードでは、構造体リテラルのキー（フィールド名）がシンボル（`l.Left.Sym`）を持たない場合にのみエラーを報告していました。しかし、ドット式（例: `foo.toInt`）は、`foo`という識別子と`toInt`というフィールドセレクタから構成されるため、`l.Left`自体は`OXDOT`という種類のノードになり、その内部には`toInt`というシンボル情報が含まれる可能性があります。このため、`l.Left.Sym`が`nil`ではないという条件を満たしてしまい、不正なドット式がエラーとして検出されませんでした。

このコミットでは、`typecheckcomplit`関数内のエラーチェック条件が拡張されました。具体的には、以下の条件が追加されています。

```go
if s == nil || l.Left.Op == OXDOT {
    Yyerror("invalid field name %v in struct initializer", l.Left)
    // ...
}
```

この変更により、構造体リテラルのキーとして使用されている式（`l.Left`）が`OXDOT`（ドット式）である場合、たとえそれがシンボルを持っていたとしても、即座に「無効なフィールド名」としてエラー（`Yyerror`）が報告されるようになります。これは、Go言語の仕様において、構造体リテラルのキーは単純なフィールド名であるべきであり、複雑な式（特にセレクタ式）であってはならないという規則を厳密に適用するための修正です。

この修正は、コンパイラのフロントエンド、特に型チェックの段階で不正な構文を早期に捕捉し、より明確なエラーメッセージを開発者に提供することで、デバッグの効率を向上させます。

## コアとなるコードの解説

`src/cmd/compile/internal/gc/typecheck.go`の変更点:

*   `typecheckcomplit`関数は、構造体リテラル（`Node` `n`）の型チェックを担当します。
*   `l.Left`は構造体リテラルのキー部分（フィールド名）を表すASTノードです。
*   `s := l.Left.Sym`は、`l.Left`ノードに関連付けられたシンボルを取得しようとします。通常のフィールド名であれば、そのフィールドのシンボルが取得されます。
*   変更前の`if s == nil`という条件は、シンボルが見つからない場合にエラーを報告していました。しかし、`foo.toInt`のようなドット式の場合、`l.Left`は`OXDOT`ノードであり、その内部には`toInt`というシンボル情報が含まれるため、`s`は`nil`になりませんでした。
*   新しい条件`if s == nil || l.Left.Op == OXDOT`は、この問題を解決します。
    *   `s == nil`: 以前からのチェックで、シンボルが見つからない場合（例: 存在しないフィールド名）にエラーを報告します。
    *   `l.Left.Op == OXDOT`: 新しく追加された条件で、`l.Left`ノードのオペレーションコードが`OXDOT`（ドット式）である場合にエラーを報告します。これにより、`foo.toInt`のような不正なドット式が構造体リテラルのキーとして使用された際に、確実にエラーとして検出されるようになります。
*   `Yyerror("invalid field name %v in struct initializer", l.Left)`は、指定されたメッセージと不正なノード情報を含むコンパイルエラーを発生させます。

`test/fixedbugs/issue15311.go`の解説:

*   このファイルは、`// errorcheck`ディレクティブによって、コンパイラが特定の行でエラーを報告することを期待するテストであることを示しています。
*   `type T struct { ... }`で、`toInt`と`toString`という2つのマップ型フィールドを持つ構造体`T`を定義しています。
*   `var t = T{ ... }`で、構造体`T`のインスタンスを初期化しようとしています。
*   `foo.toInt: make(map[string]int)`と`bar.toString: make(map[int]string)`の部分が、このコミットで修正された不正なドット式を構造体リテラルのキーとして使用する例です。
*   各行の末尾にある`// ERROR "field name"`コメントは、Goのテストフレームワークに対して、その行で「field name」という文字列を含むエラーメッセージがコンパイラによって出力されることを期待していることを示します。このテストは、修正が正しく機能し、コンパイラが期待通りにエラーを報告することを確認します。

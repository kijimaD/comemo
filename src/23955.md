# [インデックス 23955] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおける変数ハンドリングの根本的な改善を目的としています。特に、異なるスコープで同じ名前を持つ変数のエイリアシング問題の解決、変数のオフセット情報を保持するための新しい`Aux`値の導入、そしてローカル変数（`AUTO`変数）のスタック割り当ての正確性の向上に焦点を当てています。

## 元コミット内容

このコミットは、GoコンパイラのSSAバックエンドにおける変数管理の正確性を向上させるための複数の変更を導入しています。主な変更点は以下の通りです。

1.  **変数マップのキー変更**: 変数を管理するマップのキーとして、これまでの文字列（変数名）ではなく、`ONAME`型の`*Node`を使用するように変更されました。これにより、異なるスコープで同じ名前を持つ変数が誤って同じものとして扱われる「エイリアシング」の問題が解消されます。
2.  **変数オフセットのための`Aux`値の導入**: 変数がベースポインタ（グローバルベースポインタまたはスタックポインタ）からどれだけオフセットしているかをエンコードするための新しい`Aux`値が導入されました。これにより、変数のアドレス計算がより柔軟かつ正確になります。
3.  **`LEAQ`命令とその派生命令での`Aux`フィールドのサポート**: `LEAQ` (Load Effective Address) 命令や`MOVQ`などの関連命令が、この新しい`Aux`フィールドを持つことができるようになりました。これにより、アドレス計算時にオフセット情報を直接利用できるようになります。
4.  **`AUTO`変数のスタック割り当て**: ローカル変数（`AUTO`変数）のためのスタック領域の割り当てが、`stackalloc`フェーズで適切に行われるようになりました。

## 変更の背景

GoコンパイラのSSAバックエンドは、コードの最適化と機械語生成の効率化を目的として導入されました。しかし、初期の実装では、変数の識別とアドレス計算に関していくつかの課題がありました。

最も顕著な問題の一つは、**変数名のエイリアシング**です。Go言語では、異なる関数やブロック内で同じ名前の変数を宣言できます。コンパイラのSSA中間表現において、これらの変数を単に文字列の名前で識別していると、異なるスコープの同じ名前の変数が誤って同じ実体として扱われ、最適化の誤りや不正なコード生成につながる可能性がありました。

また、変数のメモリ上の位置（スタック上かグローバル領域か）とそのベースポインタからのオフセットを効率的かつ正確に表現する方法も課題でした。特に、`LEAQ`のようなアドレス計算命令は、オフセット情報を直接扱うことが多いため、SSAの`Value`がこの情報を適切に保持できる必要があります。

さらに、ローカル変数（`AUTO`変数）のスタックフレーム内での配置は、コンパイラの重要な役割です。`stackalloc`フェーズでこれらの変数のための領域が適切に確保され、そのオフセットが正確に決定される必要があります。

このコミットは、これらの課題に対処し、SSAバックエンドの堅牢性と正確性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が役立ちます。

*   **Goコンパイラの構造**: Goコンパイラは、ソースコードをAST (Abstract Syntax Tree) にパースし、それを中間表現（IR）に変換し、最終的に機械語を生成します。このコミットは、中間表現の一つであるSSA (Static Single Assignment) 形式の処理に関連しています。
*   **SSA (Static Single Assignment) 形式**: プログラムの各変数が一度だけ代入されるように変換された中間表現です。これにより、データフロー解析や最適化が容易になります。SSA形式では、変数の各定義は新しい「バージョン」として扱われます（例: `x1 = ...`, `x2 = ...`）。
*   **`cmd/compile/internal/ssa`パッケージ**: GoコンパイラのSSAバックエンドの実装が含まれるパッケージです。ここでSSA形式への変換、最適化、機械語への変換が行われます。
*   **`*Node`と`ONAME`**: Goコンパイラのフロントエンド（`cmd/compile/internal/gc`）で使われるASTノードの型です。`ONAME`は変数や関数などの名前を表すノードです。`*Node`は、AST内の特定のエンティティを一意に識別するためのポインタとして機能します。
*   **`ssa.Value`**: SSA形式における基本的な計算単位です。オペレーション（`Op`）、型（`Type`）、引数（`Args`）、補助情報（`Aux`、`AuxInt`）などを含みます。
*   **`Aux`値**: `ssa.Value`に付随する補助情報で、オペレーションの種類に応じて異なるデータを保持します。例えば、定数値、シンボル、型情報などです。このコミットでは、変数のオフセット情報を保持するための新しい`Aux`型が導入されました。
*   **`LEAQ` (Load Effective Address)**: x86-64アーキテクチャの命令で、メモリからデータをロードするのではなく、指定されたオペランドのアドレスを計算してレジスタに格納します。これは、ポインタ演算やアドレス計算の最適化によく使用されます。
*   **`FP` (Frame Pointer)**: 関数呼び出しのスタックフレームの基点を指すポインタです。通常、ローカル変数や引数は`FP`からのオフセットでアクセスされます。
*   **`SP` (Stack Pointer)**: 現在のスタックトップを指すポインタです。
*   **`SB` (Static Base Pointer)**: グローバル変数や静的データセクションの基点を指すポインタです。Goコンパイラでは、グローバル変数へのアクセスに`SB`からのオフセットが使われることがあります。
*   **`AUTO`変数**: Goコンパイラにおけるローカル変数の内部的な分類の一つです。スタック上に割り当てられる自動変数（automatic variable）を指します。
*   **`stackalloc`フェーズ**: SSAバックエンドのフェーズの一つで、関数のスタックフレームのレイアウトを決定し、ローカル変数や一時変数のためのスタック上のオフセットを割り当てます。

## 技術的詳細

このコミットの技術的詳細は、主に以下の3つの側面で構成されます。

1.  **変数識別の一意性向上**:
    *   以前は、SSAの`state`構造体内の`vars`マップ（現在のブロックでの変数割り当てを追跡）が`map[string]*ssa.Value`として定義されていました。これは変数名をキーとして使用していたため、異なるスコープで同じ名前の変数が衝突する可能性がありました。
    *   このコミットでは、`vars`マップの型が`map[*Node]*ssa.Value`に変更されました。`*Node`はASTノードへのポインタであり、`ONAME`型のノードは特定の変数を一意に識別します。これにより、スコープに関わらず変数を正確に区別できるようになり、エイリアシングの問題が解決されます。
    *   同様に、`defvars`（各ブロックの終端で定義されている変数）も`map[*Node]*ssa.Value`に変更されました。
    *   `lookupVarIncoming`や`variable`といった変数アクセス関連の関数も、引数として`string`ではなく`*Node`を受け取るように変更されています。

2.  **変数のアドレス表現の強化**:
    *   変数のアドレスを表現するために、新しい`ssa.OpAddr`オペレーションが導入されました。これは、ベースポインタ（`SP`または`SB`）と、変数を識別する`Aux`フィールド（`ExternSymbol`, `ArgSymbol`, `AutoSymbol`）を取ります。
    *   `ssa/value.go`に、`ExternSymbol`, `ArgSymbol`, `AutoSymbol`という3つの新しい構造体が定義されました。これらは`ssa.Value`の`Aux`フィールドとして使用され、それぞれグローバル変数、引数/戻り値、ローカル変数（`AUTO`）のオフセットとシンボル情報を保持します。
        *   `ExternSymbol`: グローバル変数用。`Sym`（`*gc.Sym`）と`Typ`（Go型）を持つ。オフセットはリンク時に決定される。
        *   `ArgSymbol`: 引数または戻り値用。`Offset`（フレームポインタからのオフセット）、`Sym`、`Typ`を持つ。
        *   `AutoSymbol`: ローカル変数用。`Offset`（スタックポインタからのオフセット）、`Sym`、`Typ`を持つ。`Offset`は`stackalloc`フェーズで設定される。
    *   `gc/ssa.go`の`buildssa`関数内で、`PARAM`, `PARAMOUT`, `AUTO`変数のアドレスを生成する際に、これらの新しい`Aux`型と`OpAddr`が使用されるようになりました。これにより、変数のアドレスがSSAグラフ内でより明示的かつ構造化された形で表現されます。
    *   `OpGlobal`オペレーションは削除され、グローバル変数のアドレスも`OpAddr`と`ExternSymbol`を使って表現されるようになりました。

3.  **スタック割り当てとコード生成の調整**:
    *   `stackalloc.go`では、`AUTO`変数のためのスタック領域の割り当てロジックが変更されました。`AutoSymbol`の`Offset`フィールドがこのフェーズで計算され、設定されます。
    *   以前は、`FP` (Frame Pointer) を基準としたアドレスを`SP` (Stack Pointer) を基準としたアドレスに変換する処理が`stackalloc`フェーズで行われていましたが、このコミットにより`FP`の概念がSSAバックエンドからほぼ排除され、`SP`と`SB`が主要なベースポインタとなりました。これにより、`FP`から`SP`への変換ロジックが削除され、コードが簡素化されました。
    *   `AMD64.rules`および`AMD64Ops.go`では、`LEAQ`命令が`Aux`フィールドを持つことができるように更新され、`OpAMD64LEAQglobal`が削除されました。`OpAMD64LEAQ1`などの新しい`LEAQ`派生オペレーションも導入され、より柔軟なアドレス計算が可能になりました。
    *   `rewriteAMD64.go`では、`OpAddr`を`LEAQ`に書き換えるルールが追加され、`MOVQload`や`MOVQstore`が`LEAQ`と`Aux`フィールドを組み合わせてオフセットを処理できるようになりました。`mergeSym`関数が導入され、複数のシンボルオフセットを結合するロジックが提供されています。
    *   `opGen.go`では、新しいオペレーションの定義と、レジスタマスクの更新が行われ、`FP`が`SB`に置き換えられています。

これらの変更により、GoコンパイラのSSAバックエンドは、変数の管理、アドレス計算、およびスタック割り当てにおいて、より正確で効率的な処理を実現しています。

## コアとなるコードの変更箇所

### `src/cmd/compile/internal/gc/ssa.go`

## コアとなるコードの解説

このコミットの核心は、SSA中間表現における変数の表現方法と、それに対応するアドレス計算のメカニズムの変更にあります。

1.  **`*Node`による変数の一意な識別**:
    *   `src/cmd/compile/internal/gc/ssa.go`の`state`構造体における`vars`マップのキーが`string`から`*Node`に変更されたことは、コンパイラが変数を識別する際の堅牢性を大幅に向上させます。`*Node`はAST内の特定のノードへのポインタであり、Goコンパイラ内部では各変数宣言に対して一意の`ONAME`ノードが生成されます。これにより、たとえ同じ名前の変数が異なるスコープに存在しても、それらは異なる`*Node`ポインタによって区別されるため、エイリアシングの問題が根本的に解決されます。
    *   `s.variable(n *Node, t ssa.Type)`のように、変数名を文字列ではなく`*Node`で受け取るように変更されたことで、SSA生成ロジック全体でこの一意な識別子が利用されるようになります。

2.  **`OpAddr`と`Aux`値によるアドレス表現**:
    *   `ssa/value.go`で導入された`ExternSymbol`, `ArgSymbol`, `AutoSymbol`は、変数のメモリ上の位置に関するメタデータを`ssa.Value`に直接付加するための強力なメカニズムです。
    *   `src/cmd/compile/internal/gc/ssa.go`の`buildssa`関数では、関数の引数（`PPARAM`, `PPARAMOUT`）やローカル変数（`PAUTO`）に対して、`s.entryNewValue1A(ssa.OpAddr, Ptrto(n.Type), aux, s.sp)`のような形で`OpAddr`オペレーションが生成されます。ここで`aux`には対応する`ArgSymbol`や`AutoSymbol`が渡され、`s.sp`（スタックポインタ）がベースポインタとして使用されます。これにより、SSAグラフの初期段階で変数のアドレスがその種類とオフセット情報と共に正確に表現されます。
    *   グローバル変数（`PEXTERN`）についても、`OpGlobal`が削除され、`OpAddr`と`ExternSymbol`を使って`s.sb`（スタティックベースポインタ）を基準としたアドレスが生成されるようになりました。これは、Goのグローバル変数が通常、データセクションに配置され、`SB`からの相対アドレスでアクセスされるというアーキテクチャ上の特性を反映しています。

3.  **`stackalloc`での`AUTO`変数処理の改善**:
    *   `src/cmd/compile/internal/ssa/stackalloc.go`では、`AUTO`変数のためのスタック領域の割り当てが明示的に行われるようになりました。`AutoSymbol`の`Offset`フィールドが、このフェーズで計算されたスタックポインタからのオフセットで更新されます。これにより、ローカル変数のメモリレイアウトがSSAバックエンド内で完全に決定され、後続のコード生成フェーズで正確なアドレス指定が可能になります。
    *   `FP` (Frame Pointer) の概念がSSAバックエンドからほぼ排除され、`SP` (Stack Pointer) と`SB` (Static Base Pointer) が主要なベースポインタとなったことで、`stackalloc`内の`FP`から`SP`へのアドレス調整ロジックが不要になり、コードが簡素化されました。これは、Goのランタイムが通常、`FP`を明示的に使用せず、`SP`からの相対アドレスでスタックフレームにアクセスする設計思想と一致しています。

これらの変更は、SSA中間表現の正確性と表現力を高め、コンパイラがより効率的で正しい機械語を生成するための基盤を強化しています。特に、変数のエイリアシング問題の解決は、コンパイラの最適化パスがよりアグレッシブに適用できるようになることを意味し、生成されるコードの品質向上に寄与します。

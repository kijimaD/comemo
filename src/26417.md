net: improve netsh usage in Windows unit tests

The TestInterfaceAddrsWithNetsh Windows unit test parses and compares the
output of the "netsh" command against more low level Windows API calls. In
at least two cases, some quirks of netsh cause these comparisons to fail.

One example appears to be wi-fi adapters. After a reboot, before it has
been allowed to connect to a network, netsh for IPv4 will not show an
address, whereas netsh for IPv6 will. If the interface is allowed to
connect, and then disconnected, netsh for IPv4 now shows an address and
the test will pass.

The fix is to not compare netsh output if the interface is down.

A related issue is that the IPv6 version of "netsh" can return an
IPv4-embedded IPv6 address where the IPv4 component of the address
is in decimal form, whilst the test is expecting hexadecimal form.

For example, output might be:

  Address fe80::5efe:192.168.1.7%6 Parameters
    ...

Whilst this is valid notation, the fix is to recognise this format in the
"netsh" output and re-parse the address into the all-hexadecimal
representation that the test is expecting.

## 変更の背景

このコミットは、Go言語の`net`パッケージ内のWindows固有の単体テスト`TestInterfaceAddrsWithNetsh`が、特定の条件下で誤って失敗する問題を解決するために導入されました。このテストは、Windowsのコマンドラインユーティリティである`netsh`の出力と、より低レベルなWindows API呼び出しによって取得されるネットワークインターフェースのアドレス情報を比較することで、Goのネットワーク機能がWindows上で正しく動作するかを検証します。

しかし、`netsh`コマンドにはいくつかの「癖」があり、これがテストの比較ロジックと合致しないことが判明しました。具体的には以下の2つの問題が挙げられます。

1.  **Wi-Fiアダプターの状態によるIPv4アドレスの表示不一致**:
    *   システム再起動後、Wi-Fiアダプターがネットワークに接続する前は、`netsh`のIPv4アドレス表示が空になることがあります。しかし、同じ状況でもIPv6アドレスは表示されることがあります。
    *   一度接続され、その後切断されたWi-Fiアダプターの場合、`netsh`はIPv4アドレスを表示するようになり、テストは成功します。
    *   この挙動の不一致により、インターフェースが「ダウン」状態にある場合に、`netsh`の出力が期待されるAPIの結果と異なり、テストが失敗していました。

2.  **IPv4埋め込みIPv6アドレスの表記形式の不一致**:
    *   `netsh`のIPv6関連コマンドは、IPv4アドレスをIPv6アドレス内に埋め込んだ形式（例: `fe80::5efe:192.168.1.7%6`）で返すことがあります。この際、埋め込まれたIPv4部分（`192.168.1.7`）が10進数表記で出力されます。
    *   しかし、テストの比較ロジックは、このIPv4部分が16進数表記（例: `fe80::5efe:c0a8:0107`）であることを期待していました。
    *   `netsh`の出力自体は有効な表記ですが、テストが期待する形式と異なるため、比較が失敗していました。

これらの問題により、Goのネットワーク機能自体に問題がないにもかかわらず、テストが不安定になり、開発者が誤解する可能性がありました。このコミットは、これらの`netsh`の癖を考慮に入れ、テストのロバスト性を向上させることを目的としています。

## 前提知識の解説

### `netsh`コマンドについて

`netsh` (Network Shell) は、Windowsオペレーティングシステムに搭載されているコマンドラインスクリプトユーティリティです。ローカルまたはリモートのコンピューターのネットワーク構成を表示したり、変更したりするために使用されます。TCP/IP、DNS、DHCP、Wi-Fi、ファイアウォールなど、多岐にわたるネットワークコンポーネントの設定を管理できます。

Goの`net`パッケージのテストでは、`netsh`コマンドの出力をパースして、Goが提供するネットワークインターフェース情報（Windows API経由で取得）と比較することで、Goのネットワークスタックの実装がWindowsの実際のネットワーク状態と一致しているかを確認します。

### IPv4埋め込みIPv6アドレス

IPv4埋め込みIPv6アドレス（IPv4-mapped IPv6 address）は、IPv6ネットワーク内でIPv4ノードを表現するために使用される特別なIPv6アドレス形式です。これは、IPv6アドレス空間の一部をIPv4アドレスのために予約し、IPv4アドレスをIPv6アドレスの形式で表現するものです。

一般的な形式は `::ffff:C.D.E.F` または `::C.D.E.F` ですが、このコミットで言及されているのは、リンクローカルアドレスの`fe80::5efe:`の後にIPv4アドレスが続く形式です。例えば、`fe80::5efe:192.168.1.7`のように、IPv4部分が10進数で表記されます。これは、IPv6アドレスの標準的な16進数表記とは異なるため、パース時に特別な処理が必要になります。

### Goの`net`パッケージとWindows API

Goの標準ライブラリである`net`パッケージは、ネットワークプログラミングのための豊富な機能を提供します。このパッケージは、OSに依存しない抽象化されたインターフェースを提供しますが、内部的には各OSのネイティブなネットワークAPI（WindowsではWinsock APIなど）を呼び出して動作します。

`TestInterfaceAddrsWithNetsh`のようなテストは、Goの`net`パッケージがこれらのネイティブAPIを正しくラップし、期待されるネットワーク情報を提供していることを確認するために重要です。

### Goのテストフレームワーク

Goには、標準ライブラリとして`testing`パッケージが提供されており、単体テスト、ベンチマークテスト、サンプルテストなどを記述できます。テスト関数は`TestXxx`という命名規則に従い、`*testing.T`型の引数を取ります。`t.Fatal`や`t.Skip`などのメソッドを使ってテストの失敗やスキップを指示できます。

このコミットでは、以前`t.Skip`でスキップされていたテストが、修正によって実行可能になることが示されています。

## 技術的詳細

このコミットが対処する技術的な課題は、主にWindowsの`netsh`コマンドの出力の非一貫性と、Goのテストが期待するデータ形式とのミスマッチにあります。

1.  **インターフェースの状態と`netsh`の出力**:
    *   Windowsのネットワークインターフェースは、「アップ」（接続済み、または接続可能）と「ダウン」（切断済み、または無効）の状態を持ちます。
    *   `netsh`コマンドは、特にWi-Fiアダプターのような動的なインターフェースにおいて、インターフェースが「ダウン」状態の場合にIPv4アドレス情報を報告しないことがあります。これは、`netsh`が特定のネットワークプロファイルや接続状態に依存して情報を表示するためと考えられます。
    *   しかし、Goの`net`パッケージが低レベルAPIから取得する情報には、インターフェースがダウン状態であっても、そのインターフェースに割り当てられたアドレス情報が含まれることがあります。
    *   この不一致が、テストの比較ロジックにおいて「`netsh`はアドレスを報告しないが、GoのAPIは報告する」という状況を生み出し、テストが失敗する原因となっていました。

2.  **IPv4埋め込みIPv6アドレスのパース問題**:
    *   `netsh`のIPv6アドレス表示において、`fe80::5efe:192.168.1.7%6`のような形式でIPv4アドレスが埋め込まれることがあります。ここで、`192.168.1.7`は10進数表記です。
    *   Goの`net`パッケージや一般的なIPv6アドレスの内部表現では、このようなIPv4埋め込みアドレスもすべて16進数で統一的に扱われることが期待されます（例: `fe80::5efe:c0a8:0107`、ここで`192.168.1.7`は`c0a8:0107`に相当）。
    *   テストは、`netsh`の出力とGoのAPIからの出力を文字列として比較するため、表記形式のわずかな違いが比較失敗につながっていました。`netsh`の出力が有効なIPv6アドレス表記であるにもかかわらず、テストの期待値と異なるために問題が発生していました。

これらの問題は、Goのネットワーク機能自体のバグではなく、テストハーネスが外部ツール（`netsh`）の特定の挙動を十分に考慮していなかったことに起因します。このコミットは、テストがより堅牢になるように、`netsh`の出力の「癖」を吸収するロジックを追加することで、この問題を解決しています。

### IPv4埋め込みIPv6アドレス

IPv4埋め込みIPv6アドレス（IPv4-mapped IPv6 address）は、IPv6ネットワーク内でIPv4ノードを表現するために使用される特別なIPv6アドレス形式です。これは、IPv6アドレス空間の一部をIPv4アドレスのために予約し、IPv4アドレスをIPv6アドレスの形式で表現するものです。

一般的な形式は `::ffff:C.D.E.F` または `::C.D.E.F` ですが、このコミットで言及されているのは、リンクローカルアドレスの`fe80::5efe:`の後にIPv4アドレスが続く形式です。例えば、`fe80::5efe:192.168.1.7`のように、IPv4部分が10進数で表記されます。これは、IPv6アドレスの標準的な16進数表記とは異なるため、パース時に特別な処理が必要になります。

### Goの`net`パッケージとWindows API

Goの標準ライブラリである`net`パッケージは、ネットワークプログラミングのための豊富な機能を提供します。このパッケージは、OSに依存しない抽象化されたインターフェースを提供しますが、内部的には各OSのネイティブなネットワークAPI（WindowsではWinsock APIなど）を呼び出して動作します。

`TestInterfaceAddrsWithNetsh`のようなテストは、Goの`net`パッケージがこれらのネイティブAPIを正しくラップし、期待されるネットワーク情報を提供していることを確認するために重要です。

### Goのテストフレームワーク

Goには、標準ライブラリとして`testing`パッケージが提供されており、単体テスト、ベンチマークテスト、サンプルテストなどを記述できます。テスト関数は`TestXxx`という命名規則に従い、`*testing.T`型の引数を取ります。`t.Fatal`や`t.Skip`などのメソッドを使ってテストの失敗やスキップを指示できます。

このコミットでは、以前`t.Skip`でスキップされていたテストが、修正によって実行可能になることが示されています。

## 技術的詳細

このコミットが対処する技術的な課題は、主にWindowsの`netsh`コマンドの出力の非一貫性と、Goのテストが期待するデータ形式とのミスマッチにあります。

1.  **インターフェースの状態と`netsh`の出力**:
    *   Windowsのネットワークインターフェースは、「アップ」（接続済み、または接続可能）と「ダウン」（切断済み、または無効）の状態を持ちます。
    *   `netsh`コマンドは、特にWi-Fiアダプターのような動的なインターフェースにおいて、インターフェースが「ダウン」状態の場合にIPv4アドレス情報を報告しないことがあります。これは、`netsh`が特定のネットワークプロファイルや接続状態に依存して情報を表示するためと考えられます。
    *   しかし、Goの`net`パッケージが低レベルAPIから取得する情報には、インターフェースがダウン状態であっても、そのインターフェースに割り当てられたアドレス情報が含まれることがあります。
    *   この不一致が、テストの比較ロジックにおいて「`netsh`はアドレスを報告しないが、GoのAPIは報告する」という状況を生み出し、テストが失敗する原因となっていました。

2.  **IPv4埋め込みIPv6アドレスのパース問題**:
    *   `netsh`のIPv6アドレス表示において、`fe80::5efe:192.168.1.7%6`のような形式でIPv4アドレスが埋め込まれることがあります。ここで、`192.168.1.7`は10進数表記です。
    *   Goの`net`パッケージや一般的なIPv6アドレスの内部表現では、このようなIPv4埋め込みアドレスもすべて16進数で統一的に扱われることが期待されます（例: `fe80::5efe:c0a8:0107`、ここで`192.168.1.7`は`c0a8:0107`に相当）。
    *   テストは、`netsh`の出力とGoのAPIからの出力を文字列として比較するため、表記形式のわずかな違いが比較失敗につながっていました。`netsh`の出力が有効なIPv6アドレス表記であるにもかかわらず、テストの期待値と異なるために問題が発生していました。

これらの問題は、Goのネットワーク機能自体のバグではなく、テストハーネスが外部ツール（`netsh`）の特定の挙動を十分に考慮していなかったことに起因します。このコミットは、テストがより堅牢になるように、`netsh`の出力の「癖」を吸収するロジックを追加することで、この問題を解決しています。

## コアとなるコードの解説

このコミットのコード変更は、`netsh`コマンドの出力の「癖」を吸収し、テストの信頼性を向上させるためのものです。

1.  **IPv4埋め込みIPv6アドレスの正規化**:
    *   `netshInterfaceIPv6ShowAddress`関数は、`netsh`コマンドのIPv6アドレス出力をパースする役割を担っています。
    *   `netsh`が`fe80::5efe:192.168.1.7%6`のような形式でIPv4埋め込みIPv6アドレスを返す場合、テストが期待する16進数表記（`fe80::5efe:c0a8:0107`）とは異なります。
    *   追加された正規表現`:\d+\.\d+\.\d+\.\d+$`は、この10進数表記のIPv4部分を効率的に検出します。
    *   検出された場合、`ParseIP(string(f[0])).String()`が呼び出されます。`ParseIP`はGoの`net`パッケージの関数で、IPアドレス文字列をパースし、そのIPアドレスの標準的な文字列表現を返します。これにより、`192.168.1.7`のような10進数表記が`c0a8:0107`のような16進数表記に変換され、テストの期待値と一致するようになります。
    *   この処理により、`netsh`の出力形式の差異が吸収され、テストが正しく比較できるようになります。

2.  **ダウン状態のインターフェースのスキップ**:
    *   `TestInterfaceAddrsWithNetsh`関数は、システム上のすべてのネットワークインターフェースを列挙し、それぞれのアドレス情報を`netsh`とGoのAPIの両方から取得して比較します。
    *   `if (ifi.Flags & FlagUp) == 0 { continue }`という行は、インターフェースのフラグ（`ifi.Flags`）をチェックし、`FlagUp`ビットがセットされていない（つまり、インターフェースがダウン状態である）場合に、そのインターフェースのテストをスキップします。
    *   この変更は、Wi-Fiアダプターなどのインターフェースがダウン状態のときに`netsh`がIPv4アドレスを報告しないという問題に対処します。インターフェースがダウンしている場合、`netsh`の出力が不安定であるため、そのインターフェースの比較を避けることで、テストの誤った失敗を防ぎます。これにより、テストはGoのネットワーク機能の実際の動作に集中できるようになります。

これらの変更により、`TestInterfaceAddrsWithNetsh`は、Windowsの`netsh`コマンドの特定の挙動に左右されることなく、Goの`net`パッケージのWindows上での動作をより正確かつ安定して検証できるようになりました。

## 変更の背景

Go言語のコンパイラの一つである`gccgo`に、特定の条件下で関数が意図せず複数回実行されるというバグが存在していました。このバグは、複合リテラル（structやarrayなどの初期化）の内部で関数呼び出しが行われ、かつその結果が異なるインターフェース型に変換される際に顕在化しました。関数が複数回実行されると、その関数が持つ副作用（例えば、グローバル変数の変更やI/O操作など）も複数回発生し、プログラムの論理が破綻する原因となります。このコミットは、このバグを再現し、将来的な回帰を防ぐためのテストケースを追加することで、`gccgo`の堅牢性を向上させることを目的としています。

## 前提知識の解説

### 1. `gccgo`とは

`gccgo`は、Go言語のフロントエンドとしてGCC（GNU Compiler Collection）に統合されたコンパイラです。Go言語の公式コンパイラである`gc`とは異なり、GCCの最適化バックエンドを利用できるため、特定のプラットフォームで異なるパフォーマンス特性を持つことがあります。Goプログラムをコンパイルする際に、`gc`と`gccgo`の2つの主要な選択肢が存在します。

### 2. Goの複合リテラル (Composite Literals)

Go言語において、複合リテラルは構造体（struct）、配列（array）、スライス（slice）、マップ（map）などの複合型を初期化するための構文です。例えば、構造体の複合リテラルは以下のようになります。

```go
type Point struct {
    X int
    Y int
}

p := Point{X: 10, Y: 20} // 構造体の複合リテラル
```

複合リテラルの要素には、定数だけでなく、変数や関数呼び出しの結果も指定できます。

```go
func getX() int { return 10 }
func getY() int { return 20 }

p := Point{X: getX(), Y: getY()} // 関数呼び出しを含む複合リテラル
```

Goの仕様では、複合リテラルの評価順序は定義されており、各要素は一度だけ評価されることが保証されています。

### 3. Goのインターフェース (Interfaces)

Goのインターフェースは、メソッドのシグネチャの集合を定義する型です。Goのインターフェースは、JavaやC#のような明示的な`implements`キーワードを必要とせず、型がインターフェースで定義されたすべてのメソッドを実装していれば、そのインターフェースを満たすと見なされます（構造的型付け）。

```go
type Greeter interface {
    Greet() string
}

type Person struct {
    Name string
}

func (p Person) Greet() string {
    return "Hello, " + p.Name
}

// Person型はGreet()メソッドを持つため、Greeterインターフェースを満たす
var g Greeter = Person{Name: "Alice"}
```

### 4. インターフェース型間の変換

Goでは、あるインターフェース型から別のインターフェース型への変換が可能です。これは、ソースインターフェースがターゲットインターフェースのすべてのメソッドを「含む」場合に特に重要です。例えば、`io.ReadWriter`は`io.Reader`と`io.Writer`の両方のメソッドを持つため、`io.ReadWriter`型の値は`io.Reader`型や`io.Writer`型に変換できます。

```go
type Reader interface { Read([]byte) (int, error) }
type Writer interface { Write([]byte) (int, error) }
type ReadWriter interface {
    Reader
    Writer
}

var rw ReadWriter = &MyReadWriter{} // MyReadWriterはReadWriterを満たすとする
var r Reader = rw                   // ReadWriterからReaderへの変換
```

この変換は、基となる具象値が両方のインターフェースを満たしている場合に有効です。

## 技術的詳細

このバグは、`gccgo`が複合リテラル内でインターフェース型間の変換を処理する際に、内部的な最適化やコード生成の誤りにより、特定の関数呼び出しを複数回評価してしまうことに起因していました。

具体的には、以下の条件が重なった場合に問題が発生しました。

1.  **複合リテラル内での関数呼び出し**: 構造体などの複合リテラルのフィールドに、関数呼び出しの結果を代入している。
2.  **関数が副作用を持つ**: 呼び出される関数が、グローバル変数や外部の状態を変更するなどの副作用を持つ。
3.  **異なるインターフェース型への変換**: 複合リテラル内で、関数が返す値が、異なるインターフェース型に変換される必要がある。特に、より「広い」インターフェース型からより「狭い」インターフェース型への変換、またはその逆の変換が絡む場合。

`gccgo`のコンパイラは、複合リテラルの初期化コードを生成する際に、インターフェース変換の過程で、関数呼び出しの評価結果を一時的に保持するメカニズムに問題があったと考えられます。これにより、本来一度だけ評価されるべき関数が、インターフェース変換の準備段階や実際の変換処理中に、誤って再評価されてしまうという現象が発生しました。

この問題は、特に`gccgo`のコード生成バックエンドが、Goの型システム、特にインターフェースの動的な性質と、複合リテラルの静的な初期化のセマンティクスを完全に整合させる際に生じた複雑さに起因すると推測されます。`gc`コンパイラではこの問題は発生しなかったことから、`gccgo`固有の実装上の課題であったことが示唆されます。

## コアとなるコードの解説

追加された`bug494.go`テストケースは、`gccgo`のバグを正確に再現するように設計されています。

1.  **`MyInt`型とグローバル変数`c`**:
    ```go
    type MyInt int
    var c MyInt
    ```
    `MyInt`は`int`のエイリアス型で、グローバル変数`c`が宣言されています。この`c`が、関数`f()`の副作用によって変更される対象となります。

2.  **メソッド`S`と`V`**:
    ```go
    func (c *MyInt) S(i int) {
    	*c = MyInt(i)
    }

    func (c *MyInt) V() int {
    	return int(*c)
    }
    ```
    `*MyInt`型に`S`と`V`という2つのメソッドが定義されています。これらは後述のインターフェースで利用されます。

3.  **インターフェース`i1`と`i2`**:
    ```go
    type i1 interface {
    	S(int)
    	V() int
    }

    type i2 interface {
    	V() int
    }
    ```
    `i1`は`S`と`V`の両方を要求するインターフェース、`i2`は`V`のみを要求するインターフェースです。`i1`は`i2`よりも「広い」インターフェースです。

4.  **構造体`s`**:
    ```go
    type s struct {
    	i i2
    }
    ```
    構造体`s`は、`i2`型のフィールド`i`を持ちます。

5.  **副作用を持つ関数`f()`**:
    ```go
    func f() i1 {
    	c++
    	return &c
    }
    ```
    この関数`f()`がバグのトリガーとなります。
    *   `c++`：グローバル変数`c`をインクリメントするという**副作用**を持ちます。
    *   `return &c`：`*MyInt`型のポインタを返しますが、これは`i1`インターフェースを満たします（`S`と`V`メソッドを持つため）。

6.  **`main`関数でのバグ再現**:
    ```go
    func main() {
    	p := &s{f()}
    	if v := p.i.V(); v != 1 {
    		panic(v)
    	}
    	if c != 1 {
    		panic(c)
    	}
    }
    ```
    *   `p := &s{f()}`: ここが複合リテラルとインターフェース変換が絡む核心部分です。
        *   `f()`が呼び出され、`i1`型の値（`&c`）を返します。
        *   この`i1`型の値が、構造体`s`のフィールド`i`（`i2`型）に代入されます。このとき、`i1`から`i2`へのインターフェース変換が発生します。
    *   **期待される動作**: `f()`は一度だけ実行されるため、`c`の値は`0`から`1`にインクリメントされ、最終的に`1`になるはずです。`p.i.V()`も`1`を返すはずです。
    *   **`gccgo`のバグによる動作**: バグのある`gccgo`では、`f()`が複数回実行されてしまい、`c`の値が`1`よりも大きくなってしまいます。例えば、`f()`が2回実行されると`c`は`2`になり、`p.i.V()`も`2`を返します。
    *   `if v := p.i.V(); v != 1 { panic(v) }`：`p.i.V()`が`1`でない場合にパニックを起こします。
    *   `if c != 1 { panic(c) }`：グローバル変数`c`が`1`でない場合にパニックを起こします。

このテストケースは、`f()`の副作用と、複合リテラル内でのインターフェース変換を組み合わせることで、`gccgo`の特定のバグを効果的に露呈させます。テストが成功するためには、`f()`が正確に一度だけ実行され、`c`の値が期待通り`1`になる必要があります。

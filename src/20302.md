## 元コミット内容

このコミットは、Go言語のネットワークパッケージ（`net`）に存在する、組み込みのスタブリゾルバにおけるDNSクエリの非効率性を修正することを目的としています。具体的には、特定の条件下で同一のDNSクエリが複数回送信されてしまう問題を解決します。

問題の核心は、`ndots`という設定値に関連しています。`ndots`は、ホスト名にいくつのドットが含まれていれば、そのホスト名を完全修飾ドメイン名（FQDN）として扱うか、あるいは検索ドメイン（search domain）のサフィックスを付加して試行するかを決定するしきい値です。このコミット以前は、`ndots`を超えるドットを含む非ルート（末尾にドットがない）クエリがDNSルックアップでエラーになった場合、そのクエリが不必要に再度試行される可能性がありました。

この重複試行は、特に存在しないホスト名（`NoSuchHost`）のルックアップにおいて顕著なパフォーマンス低下を引き起こしていました。コミットメッセージに示されているベンチマーク結果は、この修正が`BenchmarkGoLookupIPNoSuchHost`において、実行時間、メモリ割り当て、およびバイト割り当てを約50%削減したことを明確に示しています。これは、DNSルックアップの効率が大幅に向上したことを意味します。

## 変更の背景

この変更の背景には、GoアプリケーションがDNSルックアップを行う際のパフォーマンスと効率の改善という明確な目的があります。特に、存在しないドメイン名や解決に失敗するドメイン名に対するルックアップは、ネットワークアプリケーションにおいて頻繁に発生しうるシナリオです。このような失敗ケースでの無駄な再試行は、アプリケーションの応答性を低下させ、リソースを無駄に消費します。

従来のGoの組み込みスタブリゾルバのロジックでは、`ndots`設定と非ルートクエリの処理に不整合がありました。具体的には、ホスト名に`ndots`で指定された数以上のドットが含まれていても、末尾にドットが付加されていない（非ルート）場合、最初の試行が失敗すると、そのクエリが再度、今度は末尾にドットを付加した形で試行される可能性がありました。これは、実質的に同じクエリを二度送信することになり、特にDNSサーバーからの応答が遅い場合や、タイムアウトが発生する場合に、顕著な遅延を引き起こしていました。

このコミットは、このような重複試行を特定し、排除することで、DNSルックアップのロジックをより賢く、効率的にすることを目的としています。これにより、特にエラーパスにおけるDNS解決のオーバーヘッドが削減され、全体的なネットワーク操作のパフォーマンスが向上します。

## 前提知識の解説

このコミットの理解には、以下の前提知識が役立ちます。

### 1. DNS (Domain Name System)

DNSは、インターネット上のコンピュータ、サービス、またはその他のリソースに割り当てられたドメイン名を、コンピュータが理解できるIPアドレスに変換する分散型の命名システムです。ユーザーがウェブサイトのドメイン名（例: `www.example.com`）を入力すると、DNSがそのドメイン名に対応するIPアドレスを見つけ出し、ブラウザがそのIPアドレスに接続できるようにします。

### 2. スタブリゾルバ (Stub Resolver)

スタブリゾルバは、DNSクライアントの一部であり、アプリケーションからのDNSクエリを受け取り、それをフルサービスリゾルバ（通常はISPが提供するDNSサーバー）に転送する役割を担います。Go言語の`net`パッケージには、Cライブラリ（`libc`）に依存せずにDNS解決を行うための組み込みスタブリゾルバが含まれています。これは、クロスプラットフォーム互換性や、Cgoを使わない環境での利用に役立ちます。

### 3. `/etc/resolv.conf`

Unix系システムでは、DNSリゾルバの設定は通常`/etc/resolv.conf`ファイルに記述されています。このファイルには、DNSサーバーのIPアドレス（`nameserver`）、検索ドメイン（`search`）、そして`ndots`などのオプションが含まれます。

### 4. `ndots`オプション

`ndots`は`/etc/resolv.conf`の`options`ディレクティブで設定されるパラメータです。これは、ホスト名にいくつのドットが含まれていれば、そのホスト名を完全修飾ドメイン名（FQDN）として扱うかを指定します。
*   **`ndots:N`**: クエリされる名前にN個以上のドットが含まれている場合、その名前はまずFQDNとして試行されます。
*   N個未満のドットしか含まれていない場合、またはFQDNとしての試行が失敗した場合、`search`リストに指定されたドメインサフィックスが名前に追加されて試行されます。
*   このコミットの文脈では、`ndots`を超えるドットを持つ名前が、末尾にドットがない（非ルート）ために、FQDNとして試行された後に、再度サフィックスを付加する試行（または末尾にドットを付加する試行）が行われることが問題となっていました。

### 5. ルートクエリと非ルートクエリ

*   **ルートクエリ (Rooted Query)**: ドメイン名の末尾にドット（`.`）が付いているクエリです（例: `www.example.com.`）。これは、その名前がすでに完全修飾ドメイン名（FQDN）であることを明示的に示しており、検索ドメインのサフィックスは付加されません。
*   **非ルートクエリ (Non-rooted Query)**: ドメイン名の末尾にドットが付いていないクエリです（例: `www.example.com`）。この場合、リゾルバは`/etc/resolv.conf`の`search`リストに基づいて、自動的にサフィックスを付加して解決を試みることがあります。

### 6. `tryOneName`関数

Goの`net`パッケージ内のDNS解決ロジックにおいて、`tryOneName`関数は、与えられた単一のドメイン名に対して実際にDNSクエリを送信し、その解決を試みる役割を担います。この関数は、DNSサーバーとの通信、クエリの送信、応答の受信、およびエラーハンドリングを行います。

## 技術的詳細

このコミットが修正する問題は、Goの組み込みスタブリゾルバの`lookup`関数（`src/pkg/net/dnsclient_unix.go`内）のロジックにありました。`lookup`関数は、与えられたホスト名を解決するために、様々な戦略を試行します。

従来のロジックでは、`lookup`関数はまず、与えられた名前がルートクエリであるか、または`ndots`のしきい値を超えるドットを持つ非ルートクエリであるかに応じて、そのままの名前（または末尾にドットを付加した名前）で`tryOneName`を呼び出して解決を試みていました。

問題は、この最初の試行がエラーになった場合、特に非ルートクエリで`ndots`を超えるドットを持つ場合、`lookup`関数が「最後の手段」として、再度末尾にドットを付加した形で`tryOneName`を呼び出してしまう可能性があった点です。これは、実質的に同じFQDNに対するクエリを二度送信することになり、無駄なネットワークトラフィックと遅延を引き起こしていました。

新しいロジックでは、この重複試行を避けるために、以下の条件が導入されました。

1.  **最初の試行の変更**: `rooted`クエリの場合、または最初の`tryOneName`呼び出しが成功した場合は、すぐに結果を返します。これにより、ルートクエリが不必要に再試行されることを防ぎます。
2.  **最後の手段の条件付け**: 「最後の手段」として末尾にドットを付加して再試行するロジックに、`ndots`のチェックが追加されました。具体的には、`count(name, '.') < cfg.dnsConfig.ndots`という条件が追加され、元の名前が`ndots`で指定された数未満のドットしか持たない場合にのみ、末尾にドットを付加した再試行が行われるようになりました。

これにより、`ndots`を超えるドットを持つ非ルートクエリは、最初の試行でエラーになった場合でも、不必要に末尾にドットを付加して再試行されることがなくなりました。これは、DNS解決のロジックをより効率的にし、特に存在しないホスト名に対するルックアップのパフォーマンスを大幅に向上させます。

`dnsclient_unix_test.go`には、`BenchmarkGoLookupIPNoSuchHost`という新しいベンチマークが追加されています。これは、存在しないホスト名に対する`goLookupIP`のパフォーマンスを測定するためのもので、このコミットによる改善効果を定量的に示すために用いられました。

### `src/pkg/net/dnsclient_unix.go` の変更点

`lookup`関数の変更は、DNSクエリの重複を防ぐための主要なロジックを含んでいます。

1.  **最初の`tryOneName`呼び出し後の条件変更**:
    ```diff
    -		if err == nil {
    +		if rooted || err == nil {
     			return
     		}
     ```
    この変更は、最初の`tryOneName`呼び出しの結果を処理する部分です。
    *   変更前は、`tryOneName`がエラーなく成功した場合にのみ`return`していました。
    *   変更後は、`rooted`（クエリがすでに完全修飾ドメイン名であるとマークされている）であるか、または`tryOneName`が成功した場合に`return`するようになりました。
    *   これにより、もしクエリが`rooted`であると判断された場合、たとえ`tryOneName`がエラーを返したとしても、それ以上サフィックスを試行するなどの処理を行わずに、すぐに`lookup`関数を終了させることができます。これは、`rooted`クエリが失敗した場合に、不必要に他の解決パスを試行するのを防ぎ、効率を向上させます。

2.  **`if rooted { return }` の削除**:
    ```diff
    -	if rooted {
    -		return
    -	}
    ```
    この行は、上記の変更によって冗長になったため削除されました。`rooted`クエリの早期リターンは、新しい`if rooted || err == nil`の条件に含まれるようになりました。

3.  **「最後の手段」のロジックの変更**:
    ```diff
    -	// Last ditch effort: try unsuffixed.
    -	rname := name
    -	if !rooted {
    -		rname += "."
    -	}
    -	cname, addrs, err = tryOneName(cfg.dnsConfig, rname, qtype)
    -	if err == nil {
    -		return
    -	}
    +	// Last ditch effort: try unsuffixed only if we haven't already,
    +	// that is, name is not rooted and has less than ndots dots.
    +	if count(name, '.') < cfg.dnsConfig.ndots {
    +		cname, addrs, err = tryOneName(cfg.dnsConfig, name+".", qtype)
    +		if err == nil {
    +			return
    +		}
    	}
    ```
    このブロックは、検索ドメインのサフィックスをすべて試行した後に実行される「最後の手段」のロジックです。
    *   変更前は、`rooted`でない場合に名前の末尾にドットを付加して（つまりFQDNとして）`tryOneName`を再試行していました。これは、`ndots`を超えるドットを持つ非ルートクエリが、最初の試行でエラーになった場合に、実質的に同じFQDNを再度試行してしまう原因となっていました。
    *   変更後は、`if count(name, '.') < cfg.dnsConfig.ndots`という新しい条件が追加されました。`count(name, '.')`は、ホスト名に含まれるドットの数を数えます。
    *   この条件により、「最後の手段」として末尾にドットを付加して再試行するのは、元の名前が`ndots`で指定された数未満のドットしか持たない場合に限定されます。
    *   つまり、`ndots`以上のドットを持つ非ルートクエリは、最初の試行でエラーになった場合、この「最後の手段」のパスでは再試行されなくなります。これにより、重複するDNSクエリが効果的に排除されます。

### `src/pkg/net/dnsclient_unix_test.go` の変更点

*   **`BenchmarkGoLookupIPNoSuchHost` の追加**:
    ```go
    func BenchmarkGoLookupIPNoSuchHost(b *testing.B) {

    このベンチマーク関数は、存在しないホスト名（`some.nonexistent`）に対する`goLookupIP`（Goの組み込みリゾルバを使用したIPアドレスルックアップ）のパフォーマンスを測定するために追加されました。このベンチマークは、このコミットが解決しようとしている問題（存在しないホスト名に対する非効率な再試行）の直接的な影響を評価するために使用され、コミットメッセージに示されているパフォーマンス改善の数値の根拠となっています。

## 変更の背景

この変更の背景には、GoアプリケーションがDNSルックアップを行う際のパフォーマンスと効率の改善という明確な目的があります。特に、存在しないドメイン名や解決に失敗するドメイン名に対するルックアップは、ネットワークアプリケーションにおいて頻繁に発生しうるシナリオです。このような失敗ケースでの無駄な再試行は、アプリケーションの応答性を低下させ、リソースを無駄に消費します。

従来のGoの組み込みスタブリゾルバのロジックでは、`ndots`設定と非ルートクエリの処理に不整合がありました。具体的には、ホスト名に`ndots`で指定された数以上のドットが含まれていても、末尾にドットが付加されていない（非ルート）場合、最初の試行が失敗すると、そのクエリが再度、今度は末尾にドットを付加した形で試行される可能性がありました。これは、実質的に同じクエリを二度送信することになり、特にDNSサーバーからの応答が遅い場合や、タイムアウトが発生する場合に、顕著な遅延を引き起こしていました。

このコミットは、このような重複試行を特定し、排除することで、DNSルックアップのロジックをより賢く、効率的にすることを目的としています。これにより、特にエラーパスにおけるDNS解決のオーバーヘッドが削減され、全体的なネットワーク操作のパフォーマンスが向上します。

## 前提知識の解説

このコミットの理解には、以下の前提知識が役立ちます。

### 1. DNS (Domain Name System)

DNSは、インターネット上のコンピュータ、サービス、またはその他のリソースに割り当てられたドメイン名を、コンピュータが理解できるIPアドレスに変換する分散型の命名システムです。ユーザーがウェブサイトのドメイン名（例: `www.example.com`）を入力すると、DNSがそのドメイン名に対応するIPアドレスを見つけ出し、ブラウザがそのIPアドレスに接続できるようにします。

### 2. スタブリゾルバ (Stub Resolver)

スタブリゾルバは、DNSクライアントの一部であり、アプリケーションからのDNSクエリを受け取り、それをフルサービスリゾルバ（通常はISPが提供するDNSサーバー）に転送する役割を担います。Go言語の`net`パッケージには、Cライブラリ（`libc`）に依存せずにDNS解決を行うための組み込みスタブリゾルバが含まれています。これは、クロスプラットフォーム互換性や、Cgoを使わない環境での利用に役立ちます。

### 3. `/etc/resolv.conf`

Unix系システムでは、DNSリゾルバの設定は通常`/etc/resolv.conf`ファイルに記述されています。このファイルには、DNSサーバーのIPアドレス（`nameserver`）、検索ドメイン（`search`）、そして`ndots`などのオプションが含まれます。

### 4. `ndots`オプション

`ndots`は`/etc/resolv.conf`の`options`ディレクティブで設定されるパラメータです。これは、ホスト名にいくつのドットが含まれていれば、そのホスト名を完全修飾ドメイン名（FQDN）として扱うかを指定します。
*   **`ndots:N`**: クエリされる名前にN個以上のドットが含まれている場合、その名前はまずFQDNとして試行されます。
*   N個未満のドットしか含まれていない場合、またはFQDNとしての試行が失敗した場合、`search`リストに指定されたドメインサフィックスが名前に追加されて試行されます。
*   このコミットの文脈では、`ndots`を超えるドットを持つ名前が、末尾にドットがない（非ルート）ために、FQDNとして試行された後に、再度サフィックスを付加する試行（または末尾にドットを付加する試行）が行われることが問題となっていました。

### 5. ルートクエリと非ルートクエリ

*   **ルートクエリ (Rooted Query)**: ドメイン名の末尾にドット（`.`）が付いているクエリです（例: `www.example.com.`）。これは、その名前がすでに完全修飾ドメイン名（FQDN）であることを明示的に示しており、検索ドメインのサフィックスは付加されません。
*   **非ルートクエリ (Non-rooted Query)**: ドメイン名の末尾にドットが付いていないクエリです（例: `www.example.com`）。この場合、リゾルバは`/etc/resolv.conf`の`search`リストに基づいて、自動的にサフィックスを付加して解決を試みることがあります。

### 6. `tryOneName`関数

Goの`net`パッケージ内のDNS解決ロジックにおいて、`tryOneName`関数は、与えられた単一のドメイン名に対して実際にDNSクエリを送信し、その解決を試みる役割を担います。この関数は、DNSサーバーとの通信、クエリの送信、応答の受信、およびエラーハンドリングを行います。

## 技術的詳細

このコミットが修正する問題は、Goの組み込みスタブリゾルバの`lookup`関数（`src/pkg/net/dnsclient_unix.go`内）のロジックにありました。`lookup`関数は、与えられたホスト名を解決するために、様々な戦略を試行します。

従来のロジックでは、`lookup`関数はまず、与えられた名前がルートクエリであるか、または`ndots`のしきい値を超えるドットを持つ非ルートクエリであるかに応じて、そのままの名前（または末尾にドットを付加した名前）で`tryOneName`を呼び出して解決を試みていました。

問題は、この最初の試行がエラーになった場合、特に非ルートクエリで`ndots`を超えるドットを持つ場合、`lookup`関数が「最後の手段」として、再度末尾にドットを付加した形で`tryOneName`を呼び出してしまう可能性があった点です。これは、実質的に同じFQDNに対するクエリを二度送信することになり、無駄なネットワークトラフィックと遅延を引き起こしていました。

新しいロジックでは、この重複試行を避けるために、以下の条件が導入されました。

1.  **最初の試行の変更**: `rooted`クエリの場合、または最初の`tryOneName`呼び出しが成功した場合は、すぐに結果を返します。これにより、ルートクエリが不必要に再試行されることを防ぎます。
2.  **最後の手段の条件付け**: 「最後の手段」として末尾にドットを付加して再試行するロジックに、`ndots`のチェックが追加されました。具体的には、`count(name, '.') < cfg.dnsConfig.ndots`という条件が追加され、元の名前が`ndots`で指定された数未満のドットしか持たない場合にのみ、末尾にドットを付加した再試行が行われるようになりました。

これにより、`ndots`を超えるドットを持つ非ルートクエリは、最初の試行でエラーになった場合でも、不必要に末尾にドットを付加して再試行されることがなくなりました。これは、DNS解決のロジックをより効率的にし、特に存在しないホスト名に対するルックアップのパフォーマンスを大幅に向上させます。

`dnsclient_unix_test.go`には、`BenchmarkGoLookupIPNoSuchHost`という新しいベンチマークが追加されています。これは、存在しないホスト名に対する`goLookupIP`のパフォーマンスを測定するためのもので、このコミットによる改善効果を定量的に示すために用いられました。

## コアとなるコードの解説

### `src/pkg/net/dnsclient_unix.go` の変更点

`lookup`関数の変更は、DNSクエリの重複を防ぐための主要なロジックを含んでいます。

1.  **最初の`tryOneName`呼び出し後の条件変更**:
    ```diff
    -		if err == nil {
    +		if rooted || err == nil {
     			return
     		}
     ```
    この変更は、最初の`tryOneName`呼び出しの結果を処理する部分です。
    *   変更前は、`tryOneName`がエラーなく成功した場合にのみ`return`していました。
    *   変更後は、`rooted`（クエリがすでに完全修飾ドメイン名であるとマークされている）であるか、または`tryOneName`が成功した場合に`return`するようになりました。
    *   これにより、もしクエリが`rooted`であると判断された場合、たとえ`tryOneName`がエラーを返したとしても、それ以上サフィックスを試行するなどの処理を行わずに、すぐに`lookup`関数を終了させることができます。これは、`rooted`クエリが失敗した場合に、不必要に他の解決パスを試行するのを防ぎ、効率を向上させます。

2.  **`if rooted { return }` の削除**:
    ```diff
    -	if rooted {
    -		return
    -	}
    ```
    この行は、上記の変更によって冗長になったため削除されました。`rooted`クエリの早期リターンは、新しい`if rooted || err == nil`の条件に含まれるようになりました。

3.  **「最後の手段」のロジックの変更**:
    ```diff
    -	// Last ditch effort: try unsuffixed.
    -	rname := name
    -	if !rooted {
    -		rname += "."
    -	}
    -	cname, addrs, err = tryOneName(cfg.dnsConfig, rname, qtype)
    -	if err == nil {
    -		return
    -	}
    +	// Last ditch effort: try unsuffixed only if we haven't already,
    +	// that is, name is not rooted and has less than ndots dots.
    +	if count(name, '.') < cfg.dnsConfig.ndots {
    +		cname, addrs, err = tryOneName(cfg.dnsConfig, name+".", qtype)
    +		if err == nil {
    +			return
    +		}
    	}
    ```
    このブロックは、検索ドメインのサフィックスをすべて試行した後に実行される「最後の手段」のロジックです。
    *   変更前は、`rooted`でない場合に名前の末尾にドットを付加して（つまりFQDNとして）`tryOneName`を再試行していました。これは、`ndots`を超えるドットを持つ非ルートクエリが、最初の試行でエラーになった場合に、実質的に同じFQDNを再度試行してしまう原因となっていました。
    *   変更後は、`if count(name, '.') < cfg.dnsConfig.ndots`という新しい条件が追加されました。`count(name, '.')`は、ホスト名に含まれるドットの数を数えます。
    *   この条件により、「最後の手段」として末尾にドットを付加して再試行するのは、元の名前が`ndots`で指定された数未満のドットしか持たない場合に限定されます。
    *   つまり、`ndots`以上のドットを持つ非ルートクエリは、最初の試行でエラーになった場合、この「最後の手段」のパスでは再試行されなくなります。これにより、重複するDNSクエリが効果的に排除されます。

### `src/pkg/net/dnsclient_unix_test.go` の変更点

*   **`BenchmarkGoLookupIPNoSuchHost` の追加**:
    ```go
    func BenchmarkGoLookupIPNoSuchHost(b *testing.B) {
    	for i := 0; i < b.N; i++ {
    		goLookupIP("some.nonexistent")
    	}
    }
    ```
    このベンチマーク関数は、存在しないホスト名（`some.nonexistent`）に対する`goLookupIP`（Goの組み込みリゾルバを使用したIPアドレスルックアップ）のパフォーマンスを測定するために追加されました。このベンチマークは、このコミットが解決しようとしている問題（存在しないホスト名に対する非効率な再試行）の直接的な影響を評価するために使用され、コミットメッセージに示されているパフォーマンス改善の数値の根拠となっています。

これらの変更により、Goの組み込みスタブリゾルバは、DNSクエリの処理においてより賢明な判断を下すようになり、特にエラーパスにおける無駄な再試行を排除することで、全体的なネットワークパフォーマンスが向上しました。

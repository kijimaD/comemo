## 変更の背景

Go言語では、関数が明示的な `return` ステートメントなしに関数の終わりに到達した場合、暗黙的に（fall-through）戻ります。この際、`runtime.Caller` のようなデバッグ情報を提供する関数が、この暗黙的なリターンが発生した正確な行番号を報告できないというバグが存在していました。

この問題は、コンパイラのSSAバックエンドが、関数の終了時に生成されるリターンブロックに正しい行番号情報をアタッチしていなかったことに起因します。結果として、スタックトレースやデバッグ時に、誤った行番号が表示される可能性がありました。このコミットは、この行番号の不正確さを修正し、デバッグ情報の信頼性を向上させることを目的としています。

## 前提知識の解説

### GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを機械語に変換する過程で、中間表現としてSSA (Static Single Assignment) 形式を使用します。SSA形式は、各変数が一度だけ代入されるようにプログラムを変換するもので、データフロー解析や最適化を容易にします。GoコンパイラのSSAバックエンドは、このSSA形式のコードを処理し、最終的な機械語コードを生成する役割を担っています。この過程で、ソースコードの行番号情報も保持され、デバッグ情報として利用されます。

### `runtime.Caller` 関数

`runtime.Caller` はGoの標準ライブラリ `runtime` パッケージに含まれる関数で、呼び出し元の関数に関する情報を取得するために使用されます。具体的には、呼び出し元のプログラムカウンタ、ファイル名、行番号、および関数名を取得できます。これは、エラーロギング、デバッグ、または特定の実行コンテキストを特定する際に非常に有用です。この関数が正確な情報を返すためには、コンパイラが生成するバイナリに正しい行番号情報が埋め込まれている必要があります。

### Fall-through return

Goの関数は、明示的な `return` ステートメントがなくても、関数の本体の終わりに到達すると自動的に呼び出し元に戻ります。これを「fall-through return」と呼びます。例えば、以下の関数 `f` は、`return` ステートメントがありませんが、実行が `}` に到達すると戻ります。

```go
func f() {
    // 何らかの処理
} // ここで暗黙的に戻る
```

この暗黙的なリターンが発生する場所の行番号が、デバッグ情報として正しく報告されることが重要です。

### 行番号情報 (Line Number Information)

プログラムの実行中に発生したイベント（パニック、エラー、デバッグブレークポイントなど）の場所を特定するために、行番号情報は不可欠です。コンパイラは、ソースコードの各命令に対応する行番号情報を生成された機械語コードに埋め込みます。この情報が不正確だと、デバッガが誤ったソースコードの行を指し示したり、スタックトレースが混乱したりする原因となります。

## 技術的詳細

このコミットの技術的な核心は、GoコンパイラのSSAバックエンドにおけるリターンブロックの行番号情報の取り扱いにあります。

変更は `src/cmd/compile/internal/gc/ssa.go` ファイルの `buildssa` 関数内で行われています。`buildssa` 関数は、GoのAST (Abstract Syntax Tree) をSSA形式に変換する主要な関数の一つです。この関数内で、Goの関数が終了する際のリターン処理をモデル化する部分があります。

具体的には、関数の終了時に `s.endBlock()` を呼び出してリターンブロック (`ssa.BlockRet` 型のブロック) を取得し、そのブロックに適切な制御フローとメモリ状態をアタッチします。このコミット以前は、`fallthru-return` のシナリオにおいて、このリターンブロックに明示的な行番号が設定されていませんでした。そのため、デバッグ情報が不正確になる可能性がありました。

このコミットでは、以下の行が追加されました。
```go
b.Line = fn.Func.Endlineno
```
ここで、`b` は `s.endBlock()` によって取得されたリターンブロックであり、`fn.Func.Endlineno` はコンパイラが認識している現在の関数の物理的な終了行番号です。この行を追加することで、関数の暗黙的なリターンを表現するSSAブロックに、関数の実際の終了行が正確に紐付けられるようになります。

これにより、`runtime.Caller` などのツールが、関数が暗黙的に終了した際に、その関数の最後の行を正確に報告できるようになります。これは、特にデバッグやプロファイリングにおいて、より信頼性の高い情報を提供するために重要です。

また、この変更には `test/fixedbugs/issue14646.go` という新しいテストファイルが追加されています。このテストは、無名関数が暗黙的に終了するケースで `runtime.Caller(1)` が返す行番号が期待通りであるかを確認することで、この修正が正しく機能していることを検証します。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更点

`buildssa` 関数は、Goの関数ノード (`fn *Node`) を受け取り、その関数に対応するSSA形式の関数 (`*ssa.Func`) を構築します。変更が加えられた箇所は、関数の終了処理、特に暗黙的なリターンを扱うブロックの生成に関連しています。

1.  `s.stmts(s.exitCode)`: 関数の終了コードに関連するステートメントを処理します。
2.  `m := s.mem()`: 現在のメモリ状態を取得します。SSAではメモリも値として扱われます。
3.  `b := s.endBlock()`: 関数の終了を表すSSAブロック（リターンブロック）を取得または生成します。
4.  `b.Line = fn.Func.Endlineno`: **この行が追加されました。** ここで、生成されたリターンブロック `b` の `Line` フィールドに、現在の関数 `fn` の物理的な終了行番号 (`fn.Func.Endlineno`) が設定されます。これにより、このリターンブロックがソースコードのどの行に対応するかが明確になります。
5.  `b.Kind = ssa.BlockRet`: ブロックの種類をリターンブロック (`BlockRet`) に設定します。
6.  `b.Control = m`: リターンブロックの制御値として、最終的なメモリ状態 `m` を設定します。

この変更により、`fallthru-return` の場合でも、SSAバックエンドが生成するリターン命令に、関数の実際の終了行番号が正確に紐付けられるようになり、`runtime.Caller` などがこの情報を利用して正しい行番号を報告できるようになります。

### `test/fixedbugs/issue14646.go` のテストコード

このテストコードは、修正が正しく機能していることを検証するために設計されています。

1.  `main` 関数内で、`file` と `line` という変数を宣言します。これらは `runtime.Caller` から取得した情報を格納するために使われます。
2.  無名関数 `func() { ... }()` を定義し、即座に実行しています。この無名関数は明示的な `return` ステートメントを持たず、`}` に到達することで暗黙的に終了します。
3.  無名関数内には `defer` 関数が設定されており、この `defer` 関数内で `runtime.Caller(1)` を呼び出しています。`runtime.Caller(1)` は、`defer` 関数を呼び出した関数（この場合は無名関数）の呼び出し元の情報、つまり無名関数が終了した場所の情報を取得します。
4.  `// this is the expected line` というコメントがある行が、無名関数が暗黙的に終了する行であり、`runtime.Caller(1)` が報告すべき行番号です。
5.  `const EXPECTED = 18` は、このテストファイルにおける期待される行番号（無名関数の終了行）です。
6.  最後に、`if line != EXPECTED` で、実際に取得された行番号 `line` が期待値 `EXPECTED` と一致するかを検証しています。一致しない場合はエラーメッセージを出力します。

このテストは、コンパイラの修正がなければ `line` が `EXPECTED` と異なる値になる可能性があり、修正が適用されることで正しく `18` が報告されることを確認します。

# [インデックス 23051] ファイルの概要

このコミットは、Goツールチェインにおいて、外部リンキングモードが強制される場合に`runtime/cgo`パッケージへの依存関係を明示的に追加する変更です。これにより、ユーザーが非標準のコンパイルオプションを使用する際に発生する可能性のあるビルドエラーを防ぎ、`go`コマンドがより堅牢に動作するように改善されています。

## 元コミット内容

```
cmd/go: depend on runtime/cgo if external linking mode is forced

In external linking mode, the linker automatically imports
runtime/cgo.  When the user uses non-standard compilation options,
they have to know to run go install runtime/cgo.  When the go tool
adds non-standard compilation options itself, we can't force the user
to do that.  So add the dependency ourselves.

Bad news: we don't currently have a clean way to know whether we are
going to use external linking mode.  This CL duplicates logic split
between cmd/6l and cmd/internal/ld.

Good news: adding an unnecessary dependency on runtime/cgo does no
real harm.  We aren't going to force the linker to pull it in, we're
just going to build it so that its available if the linker wants it.
```

## 変更の背景

Goのビルドシステムでは、特定のビルドモード（例: `shared`や`c-shared`）や、Cgoを使用する場合に、最終的な実行可能ファイルを生成するために外部リンカ（通常はGCCやClang）を使用する「外部リンキングモード」が強制されます。この外部リンキングモードでは、Goのリンカは自動的に`runtime/cgo`パッケージをインポートし、そのランタイムサポートを必要とします。

問題は、ユーザーが`go build`コマンドで非標準のコンパイルオプション（例えば、`go build -buildmode=shared`）を指定した場合、`runtime/cgo`が事前にビルドされていないと、リンカがそのパッケージを見つけられずにビルドが失敗する可能性があったことです。通常、ユーザーはこのような状況で`go install runtime/cgo`を実行して手動で`runtime/cgo`をビルドする必要がありました。

しかし、`go`ツール自身が内部的に非標準のコンパイルオプションを追加する場合（例えば、特定のビルドモードを選択した場合）、ユーザーに`runtime/cgo`の手動ビルドを強制することはできません。このコミットの目的は、`go`ツールが外部リンキングモードを強制する状況で、`runtime/cgo`への依存関係を明示的に追加することで、この問題を解決し、ビルドプロセスをよりスムーズにすることです。これにより、`runtime/cgo`が必要な場合に確実にビルドされるようになります。

## 前提知識の解説

### 1. Goのビルドプロセスとリンキング

Goのプログラムは、Goコンパイラによってオブジェクトファイルにコンパイルされ、その後Goリンカ（`cmd/link`）によって実行可能ファイルにリンクされます。リンキングには主に2つのモードがあります。

*   **内部リンキング (internal linking)**: GoリンカがGoのオブジェクトファイルと、Goのランタイムライブラリを直接リンクして実行可能ファイルを生成するモードです。Cgoを使用しないGoプログラムのデフォルトのビルドモードです。
*   **外部リンキング (external linking)**: GoリンカがGoのオブジェクトファイルを生成した後、最終的な実行可能ファイルの生成を外部のCリンカ（通常はGCCやClang）に委ねるモードです。これは、Cgoを使用する場合や、特定のビルドモード（例: 共有ライブラリのビルド）で必要となります。外部リンカは、Goのランタイムライブラリだけでなく、Cのライブラリなどもリンクできます。

### 2. `runtime/cgo`パッケージ

`runtime/cgo`は、GoプログラムがC言語のコードを呼び出す（Cgo）ためのランタイムサポートを提供するGoの標準ライブラリパッケージです。Cgoを使用するGoプログラムは、このパッケージに暗黙的に依存します。このパッケージには、GoとCの間のスタック切り替え、メモリ管理、スレッド管理など、Cgoの相互運用に必要な低レベルの機能が含まれています。外部リンキングモードでは、Goリンカがこのパッケージの機能を必要とするため、自動的にインポートしようとします。

### 3. Goのビルドモード (`-buildmode`)

`go build`コマンドには、`-buildmode`フラグがあり、様々な種類のバイナリを生成できます。このコミットに関連する主なビルドモードは以下の通りです。

*   **`-buildmode=shared`**: 複数のGoプログラムで共有できるGoの共有ライブラリをビルドします。このモードは、Goのパッケージを共有ライブラリとしてコンパイルし、他のGoプログラムが動的にリンクできるようにします。このモードは外部リンキングを強制します。
*   **`-buildmode=c-shared`**: GoのパッケージをCの共有ライブラリとしてビルドします。これにより、GoのコードをC、C++、Pythonなどの他の言語から呼び出すことができる共有ライブラリ（`.so`, `.dll`, `.dylib`など）を生成します。このモードも外部リンキングを強制します。
*   **`-linkshared`**: 実行可能ファイルをビルドする際に、Goの共有ライブラリ（`-buildmode=shared`でビルドされたもの）に動的にリンクするように指定します。このフラグを使用する場合も、外部リンキングモードが使用されます。

### 4. `go install`コマンド

`go install`コマンドは、指定されたパッケージをコンパイルし、その結果のバイナリ（実行可能ファイルまたはパッケージアーカイブ）を`GOPATH/bin`または`GOPATH/pkg`（Go Modulesを使用している場合は`GOCACHE`）にインストールします。これにより、他のGoプログラムがそのパッケージを依存関係として利用できるようになります。

## 技術的詳細

このコミットの核心は、Goのビルドシステムが外部リンキングモードを使用する際に、`runtime/cgo`パッケージが確実にビルドされ、利用可能であることを保証することです。

Goのリンカは、外部リンキングモードで動作する場合、`runtime/cgo`パッケージが提供する特定のシンボルや機能に依存します。もし`runtime/cgo`が事前にコンパイルされていなければ、リンカは必要な依存関係を解決できず、ビルドエラーが発生します。

コミットメッセージでは、この問題に対するアプローチについて「Bad news」と「Good news」が述べられています。

*   **Bad news**: `go`ツールが、ビルド時に「外部リンキングモードを使用するかどうか」をクリーンな方法で事前に判断するメカニズムが当時存在しなかったことです。これは、リンカ（`cmd/6l`、現在の`cmd/link`）と、Goのビルドコマンド（`cmd/go`）の間で、リンキングモードを決定するロジックが分散していたためです。このため、`cmd/go`は、リンカが最終的に外部リンキングモードを使用するかどうかを正確に予測することが困難でした。結果として、このコミットでは、リンカのロジックの一部を`cmd/go`に複製して、外部リンキングモードが強制される条件を判断しています。

*   **Good news**: `runtime/cgo`への依存関係を不必要に追加しても、実質的な害はないということです。この変更は、リンカに`runtime/cgo`を強制的にリンクさせるものではなく、単に`runtime/cgo`がビルドされ、リンカが必要とした場合に利用できるようにすることを目的としています。つまり、`runtime/cgo`がビルド済みであれば、リンカはそれを利用でき、ビルドが成功します。もしリンカが`runtime/cgo`を必要としなければ、ビルドされた`runtime/cgo`は単に未使用のまま残るだけで、大きなオーバーヘッドにはなりません。

この変更により、`go build -buildmode=shared`や`go build -buildmode=c-shared`、または`-linkshared`フラグを使用する際に、`runtime/cgo`が自動的にビルドされるようになり、ユーザーが手動で`go install runtime/cgo`を実行する必要がなくなります。これは、Goのビルドシステムの使いやすさと堅牢性を向上させるための重要な改善です。

## コアとなるコードの解説

### `src/cmd/go/build.go` の変更点

このファイルは、`go build`コマンドの主要なロジックを扱います。変更は`runBuild`関数内で行われています。

*   **`if buildBuildmode == "shared"` ブロック内**:
    *   `buildBuildmode == "shared"`は、ユーザーが`go build -buildmode=shared`を指定した場合に真となります。
    *   このブロック内で、`runtime/cgo`パッケージを明示的にロードし、そのパッケージを現在のビルドアクションの依存関係に追加しています。
    *   `loadPackage("runtime/cgo", &stk)`: `runtime/cgo`パッケージをロードします。`stk`はインポートスタックで、循環依存の検出などに使われます。
    *   `if p.Error != nil { fatalf("load runtime/cgo: %v", p.Error) }`: `runtime/cgo`のロードに失敗した場合（例えば、パッケージが見つからないなど）、致命的なエラーとして処理します。
    *   `a.deps = append(a.deps, b.action(mode, depMode, p))`: ロードした`runtime/cgo`パッケージを、現在のビルドアクション`a`の依存関係リスト`a.deps`に追加します。これにより、`go build`は`shared`モードでビルドする前に`runtime/cgo`がビルドされることを保証します。

この変更により、`go build -buildmode=shared`を使用する際に、`runtime/cgo`が自動的にビルドされるようになり、外部リンキングモードでの依存関係の問題が解決されます。

### `src/cmd/go/pkg.go` の変更点

このファイルは、Goパッケージのロードと依存関係の解決に関連するロジックを扱います。変更は`(*Package) load`メソッド内で行われています。

*   **新しい条件付きインポートの追加**:
    *   `if p.Name == "main" && !p.Goroot && (buildBuildmode == "c-shared" || buildLinkshared)`: この条件は、以下のすべてが真の場合に`runtime/cgo`をインポートパスに追加します。
        *   `p.Name == "main"`: 現在のパッケージが`main`パッケージであること。これは実行可能ファイルをビルドする際に該当します。
        *   `!p.Goroot`: 現在のパッケージがGoの標準ライブラリ（`GOROOT`内）ではないこと。標準ライブラリは特別な扱いを受けるため除外されます。
        *   `(buildBuildmode == "c-shared" || buildLinkshared)`: ビルドモードが`c-shared`であるか、または`-linkshared`フラグが指定されていること。これらのモードは外部リンキングを強制します。
    *   `importPaths = append(importPaths, "runtime/cgo")`: 上記の条件が満たされた場合、`runtime/cgo`を現在のパッケージのインポートパスリストに追加します。これにより、`go`ツールはこれらのビルドモードで`main`パッケージをビルドする際に、`runtime/cgo`への依存関係を認識し、ビルドプロセスに含めるようになります。

この変更により、`go build -buildmode=c-shared`や`go build -linkshared`を使用する際に、`runtime/cgo`が自動的にビルドされるようになり、外部リンキングモードでの依存関係の問題が解決されます。

これらの変更は、`go`コマンドが外部リンキングモードを必要とする特定のビルドシナリオにおいて、`runtime/cgo`の可用性を事前に保証することで、ビルドの信頼性を高めるものです。

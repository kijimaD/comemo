## 変更の背景

このコミットの主な背景には、Goコンパイラの**エスケープ解析**（Escape Analysis）が、`**Node`のようなツリー構造を効率的に扱えないという問題がありました。Goコンパイラは、プログラムの抽象構文木（AST）を`Node`構造体で表現しており、コンパイル処理の様々な段階でこれらの`Node`を操作します。

過去のGoのコンパイラでは、ASTのノードを操作する関数が、しばしば`**Node`（`*Node`へのポインタ）を引数として受け取っていました。これは、関数内でノード自体を置き換える必要がある場合に、呼び出し元が持つ`*Node`ポインタの指す先を変更するためによく用いられるパターンです。しかし、この`**Node`という引数渡しが、エスケープ解析にとって大きな課題となっていました。

エスケープ解析は、変数がスタックに割り当てられるべきか、それともヒープに割り当てられるべきかを決定するコンパイラの最適化プロセスです。スタック割り当ては高速ですが、ヒープ割り当てはガベージコレクションのオーバーヘッドを伴うため、一般的に低速です。エスケープ解析が変数をスタックに割り当てられないと判断した場合、その変数はヒープに割り当てられます。

`**Node`を引数として渡す場合、エスケープ解析は、その`*Node`が関数呼び出し後も生存し続ける可能性がある（つまり、呼び出し元によって参照され続ける可能性がある）と判断しやすくなります。特に、ツリー構造のノードが頻繁に更新されるような状況では、エスケープ解析は保守的に判断し、多くの`*Node`インスタンスをヒープに割り当ててしまう傾向がありました。これは、コンパイラ自身の実行時におけるメモリ使用量（`alloc/op`）とアロケーション回数（`allocs/op`）の増加につながり、コンパイル時間のパフォーマンス低下の一因となっていました。

この問題は、GoのIssueトラッカーで#13493と#14858として議論されていました。これらの問題は、`**Node`パラメータがエスケープ解析を困難にし、不必要なヒープアロケーションを引き起こすことを指摘していました。このコミットは、これらの問題に対処し、コンパイラのパフォーマンスを改善するための抜本的な変更として導入されました。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

Goコンパイラは、Go言語で書かれたソースコードを機械語に変換するプログラムです。`cmd/compile`はGoツールチェーンの一部であり、Goプログラムのビルドプロセスにおいて中心的な役割を担います。コンパイラは、字句解析、構文解析、型チェック、中間表現の生成、最適化、コード生成といった複数のフェーズを経て、最終的な実行可能ファイルを生成します。

### 抽象構文木 (AST - Abstract Syntax Tree) と `Node` 構造体

Goコンパイラは、ソースコードを解析する際に、その構造を抽象構文木（AST）として内部的に表現します。ASTは、プログラムの構造を木構造で表したもので、各ノードがプログラムの構成要素（変数、式、文、関数など）に対応します。Goコンパイラでは、このASTの各要素を`Node`という構造体で表現しています。`Node`構造体は、その種類（演算子、リテラル、変数など）、型情報、子ノードへのポインタなど、様々な情報を含んでいます。コンパイラの各フェーズは、この`Node`ツリーを走査し、変換し、情報を付加していきます。

### エスケープ解析 (Escape Analysis)

エスケープ解析は、コンパイラ最適化の一種で、プログラム中の変数がどこに割り当てられるべきか（スタックかヒープか）を決定します。

*   **スタック割り当て (Stack Allocation):** 関数内で宣言された変数が、その関数が終了するまでにのみ使用され、外部に参照が漏れない（エスケープしない）場合、その変数はスタックに割り当てられます。スタックは高速で、メモリの解放も関数の終了と同時に自動的に行われるため、ガベージコレクションの負担がありません。
*   **ヒープ割り当て (Heap Allocation):** 変数が関数のスコープを超えて生存する必要がある場合（例: グローバル変数、関数から返されるポインタ、他のゴルーチンから参照される可能性がある場合など）、その変数はヒープに割り当てられます。ヒープは柔軟なメモリ管理を可能にしますが、割り当てと解放にはオーバーヘッドがあり、ガベージコレクションの対象となります。

エスケープ解析の目的は、可能な限り多くの変数をスタックに割り当てることで、ヒープアロケーションを減らし、ガベージコレクションの頻度と時間を削減し、プログラムの実行速度を向上させることです。

### ヒープアロケーション (Heap Allocation)

ヒープアロケーションとは、プログラムが実行時に動的にメモリを確保することです。Goでは、`new`や`make`を使って明示的にヒープにメモリを割り当てることもできますが、コンパイラのエスケープ解析によって暗黙的にヒープに割り当てられることもあります。ヒープアロケーションは、スタックアロケーションに比べてコストが高く、ガベージコレクタが不要なメモリを回収するまでメモリを占有し続けるため、パフォーマンスに影響を与えます。

### ポインタと二重ポインタ (`*T` と `**T`)

*   **`*T` (ポインタ):** 型`T`の値が格納されているメモリのアドレスを保持する変数です。`*T`型の変数を介して、元の`T`型の値を読み書きできます。
*   **`**T` (二重ポインタ):** 型`*T`の値（つまり、`T`型へのポインタ）が格納されているメモリのアドレスを保持する変数です。`**T`型の変数を介して、`*T`型の値を読み書きでき、結果として元の`T`型の値も間接的に操作できます。

Goコンパイラの文脈では、`Node`はASTのノードを表す構造体です。
`*Node`は、特定のASTノードへのポインタです。
`**Node`は、`*Node`へのポインタです。関数が`**Node`を引数として受け取る場合、その関数は呼び出し元が持つ`*Node`変数の指す先（つまり、その`*Node`が参照しているASTノード）を直接変更することができます。これは、ASTのノードを別のノードに置き換えるような操作で使われていました。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラ内部でASTノードを操作する関数のシグネチャと呼び出し規約を根本的に変更した点にあります。

**変更前:**
多くのAST操作関数は、`func foo(np **Node, ...)` のようなシグネチャを持っていました。
この場合、関数`foo`は`*Node`へのポインタ（`np`）を受け取り、`*np = newNode` のようにして、呼び出し元が持つ`*Node`変数の指す先を直接新しいノードに置き換えることができました。

しかし、前述の通り、この`**Node`パラメータはエスケープ解析にとって問題でした。`**Node`が渡されると、エスケープ解析は`*Node`が関数スコープ外に「エスケープ」する可能性が高いと判断し、不必要にヒープに割り当ててしまう傾向がありました。

**変更後:**
このコミットでは、関数のシグネチャを `func foo(n *Node, ...) *Node` の形式に変更しました。
これは、Goの組み込み関数である`append`スライス関数に似たパターンです。`append`は、スライスを受け取り、要素を追加した新しいスライス（または元のスライスが拡張されたもの）を返します。同様に、変更後のAST操作関数は、`*Node`を受け取り、必要に応じてノードを変更し、その結果として得られる`*Node`を返します。

呼び出し元は、この戻り値を元の変数に再代入する必要があります。
例えば、`*np = typecheck(&n, Etop)` のようなコードは、`n = typecheck(n, Etop)` のように変更されます。また、`n.Left`のような子ノードを操作する場合も、`n.Left = typecheck(n.Left, Erv)` のように再代入が行われます。

この変更により、エスケープ解析はより正確な情報を得られるようになります。関数が`*Node`を返す場合、その`*Node`がヒープに割り当てられるべきかどうかを、呼び出し元での使用状況に基づいてより適切に判断できるようになります。これにより、不必要なヒープアロケーションが削減され、コンパイラのメモリ使用量と実行速度が改善されます。

コミットメッセージに記載されているベンチマーク結果は、この変更が実際に`alloc/op`（操作あたりのメモリ割り当て量）と`allocs/op`（操作あたりの割り当て回数）を大幅に削減し、コンパイル時間も短縮されたことを示しています。特に`allocs/op`の削減率は14%から20%と顕著です。

この変更は、Goコンパイラのコードベース全体にわたる広範なものであり、エスケープ解析の連鎖的な性質により、多くの関数シグネチャと呼び出し箇所を更新する必要がありました。手動でのシグネチャ変更と、専用スクリプトによる呼び出し箇所の自動更新というハイブリッドなアプローチが取られました。

**変更後 (`convlit` 関数):**

```go
// convert n, if literal, to type t.
// The result of convlit MUST be assigned back to n, e.g.
// 	n.Left = convlit(n.Left, t)
func convlit(n *Node, t *Type) *Node {
	return convlit1(n, t, false)
}

// convert n, if literal, to type t.
// return a new node if necessary
// (if n is a named constant, can't edit n->type directly).
// The result of convlit1 MUST be assigned back to n, e.g.
// 	n.Left = convlit1(n.Left, t, explicit)
func convlit1(n *Node, t *Type, explicit bool) *Node {
	if n == nil || t == nil || n.Type == nil || isideal(t) || n.Type == t {
		return n // 変更点: 変更がない場合は元のノードを返す
	}
	if !explicit && !isideal(n.Type) {
		return n // 変更点: 変更がない場合は元のノードを返す
	}

	if n.Op == OLITERAL {
		nn := Nod(OXXX, nil, nil)
		*nn = *n
		n = nn
		// *np = n の行が削除され、代わりに n が返される
	}
	// ... (中略) ...
	// 内部で再帰的に convlit を呼び出す箇所
	// n.Left = convlit(n.Left, t) // 変更点: 戻り値を再代入
	// n.Right = convlit(n.Right, t) // 変更点: 戻り値を再代入
	// ... (中略) ...
	// n = defaultlit(n, nil) // 変更点: 戻り値を再代入
	// ... (中略) ...
	return n // 変更点: 最終的に変更されたノードを返す
```

**`**Node`から`*Node`を返す形式への変更の意義:**

1.  **エスケープ解析の精度向上:**
    *   `func foo(np **Node)` のような関数シグネチャでは、`np`が指す`*Node`が関数呼び出し後も生存し続ける可能性があるとエスケープ解析が判断しやすくなります。これは、`np`が指すメモリ領域が、呼び出し元のスタックフレーム外に「エスケープ」する可能性があるためです。結果として、`*Node`が不必要にヒープに割り当てられることが多くなります。
    *   `func foo(n *Node) *Node` のようなシグネチャでは、関数`foo`は`n`という`*Node`のコピーを受け取り、新しい`*Node`を返すか、既存の`n`を変更して返します。呼び出し元は、`n = foo(n)` のように戻り値を再代入します。このパターンでは、エスケープ解析は`foo`の内部で生成された`*Node`が、`foo`の呼び出し元に返されるかどうか、そしてその戻り値がさらにどこで使われるかをより正確に追跡できます。これにより、`*Node`がスタックに割り当てられる可能性が高まり、ヒープアロケーションが削減されます。

2.  **ヒープアロケーションの削減:**
    *   コミットメッセージのベンチマーク結果が示すように、この変更は`allocs/op`（操作あたりのアロケーション回数）と`alloc/op`（操作あたりのメモリ量）を大幅に削減しました。これは、多くの`*Node`インスタンスがヒープではなくスタックに割り当てられるようになったためです。ヒープアロケーションの削減は、ガベージコレクションの頻度と実行時間を減らし、コンパイラ自体の実行速度を向上させます。

3.  **「appendライク」なイディオム:**
    *   この変更は、Go言語の`append`関数が採用しているイディオムに似ています。`append`は、スライスに要素を追加し、新しいスライス（または容量が拡張された元のスライス）を返します。呼び出し元は `s = append(s, elem)` のように戻り値を再代入します。このパターンは、Goのコードベースで広く認識されており、一貫性のある設計原則に従っています。

4.  **コードの明確化と安全性:**
    *   `**Node`を使用する場合、呼び出し元はポインタのポインタを渡す必要があり、コードがやや複雑になることがあります。また、`*np = ...` のような直接的なポインタの書き換えは、意図しない副作用を引き起こす可能性もゼロではありません。
    *   `n = foo(n)` の形式は、関数が新しい値を返すことを明確にし、呼び出し元がその新しい値を明示的に受け取る必要があることを示します。これにより、コードの意図がより明確になり、予期せぬ副作用のリスクが低減されます。

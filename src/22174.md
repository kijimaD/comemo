# [インデックス 22174] ファイルの概要

このコミットは、Goランタイムのメモリ管理における重要な修正を導入しています。具体的には、物理ページサイズがGoの論理ヒープページサイズよりも大きいシステム（例: 64KBの物理ページサイズを持つシステム）において、メモリスカベンジャー（scavenger）の動作を無効にすることで、`madvise(2)`システムコールが引き起こす可能性のあるヒープ破損の問題を回避します。この問題は、特にppc64およびppc64leアーキテクチャで顕著でした。

## 変更の背景

Goランタイムは、ガベージコレクション（GC）後に不要になったメモリをオペレーティングシステム（OS）に解放するために「スカベンジャー（scavenger）」と呼ばれるメカニズムを使用します。このスカベンジャーは、`madvise(2)`システムコールを利用して、特定のメモリ範囲がアプリケーションによって今後アクセスされないことをOSに通知し、OSがそのメモリを再利用できるようにします。

しかし、一部のシステム、特にppc64やppc64leのようなアーキテクチャでは、OSの物理ページサイズがGoランタイムが内部的に管理する論理ヒープページサイズ（通常は8KB）よりもはるかに大きい（例: 64KB）場合があります。このような環境で`madvise(2)`を呼び出すと、OSは要求されたメモリ解放の範囲を物理ページサイズの境界に切り上げて処理します。この切り上げ処理が問題を引き起こす可能性がありました。具体的には、Goランタイムが解放を意図したメモリ領域の近くにある、まだ使用中のヒープページまで誤って解放してしまう（またはOSがそのページを破棄してしまう）ことで、ヒープが破損する危険性があったのです。

この問題は、GoのIssue #9993で報告されており、このコミットはその問題を解決するために、一時的にスカベンジャーの動作を無効化する措置を講じています。

## 前提知識の解説

*   **メモリページとページサイズ**: 現代のOSは、メモリを「ページ」という固定サイズのブロックで管理します。CPUとOSは、仮想アドレスを物理アドレスに変換する際にこのページ単位で処理を行います。ページサイズはシステムによって異なり、一般的なx86-64システムでは4KBですが、一部のアーキテクチャ（例: ppc64）では64KBのような大きなページサイズを使用することがあります。
*   **Goランタイムのヒープ管理**: Goランタイムは独自のメモリマネージャを持ち、OSから大きなメモリブロックを確保し、それをGoのヒープとして管理します。Goは内部的に、このヒープをより小さな「スパン（span）」や「ページ」に分割して使用します。このGoが管理する内部的なページサイズは、OSの物理ページサイズとは異なる場合があります。
*   **`madvise(2)`システムコール**: `madvise`は、プロセスが特定のメモリ範囲の将来のアクセスパターンについてカーネルに助言（advise）するためのシステムコールです。これにより、カーネルはメモリ管理の最適化を行うことができます。例えば、`MADV_DONTNEED`フラグを使用すると、そのメモリ範囲の内容が不要になったことをカーネルに伝え、カーネルは物理メモリを解放して再利用できるようになります。
*   **Goのスカベンジャー**: Goのガベージコレクタは、到達不能なオブジェクトが占めていたメモリを解放しますが、そのメモリはすぐにOSに返されるわけではありません。スカベンジャーは、GCによって解放されたメモリ領域のうち、一定期間使用されていないものをOSに返却する役割を担っています。これにより、Goアプリケーションが使用する物理メモリのフットプリントを削減し、システム全体のメモリ効率を向上させます。

## 技術的詳細

このコミットの核心は、GoランタイムがOSの物理ページサイズとGoの論理ヒープページサイズとの間に不一致がある場合に、スカベンジャーの動作を条件付きで無効にすることです。

Goランタイムは、`_PhysPageSize`という内部変数でOSの物理ページサイズを、`_PageSize`という内部変数でGoが内部的に使用する論理ヒープページサイズを保持しています。このコミットでは、`src/runtime/mheap.go`内の`scavengelist`関数（スカベンジャーの主要なロジックを含む）に以下のチェックが追加されました。

```go
if _PhysPageSize > _PageSize {
    // golang.org/issue/9993
    // If the physical page size of the machine is larger than
    // our logical heap page size the kernel may round up the
    // amount to be freed to its page size and corrupt the heap
    // pages surrounding the unused block.
    return 0
}
```

このコードは、もし物理ページサイズがGoの論理ページサイズよりも大きい場合、スカベンジャーの処理を即座に終了し、メモリをOSに解放しないようにします。これにより、`madvise(2)`が意図しないメモリ領域を解放してしまうリスクを排除します。

この問題は、特にppc64およびppc64leアーキテクチャで確認されており、これらのシステムでは64KBの物理ページサイズが一般的です。NaCl（Native Client）も64KBページサイズを使用する可能性がありますが、コミット時点では影響を受けるか不明確でした。

また、`src/runtime/debug/garbage_test.go`内の`TestFreeOSMemory`テストには、ppc64, ppc64le, naclアーキテクチャでこのテストをスキップするロジックが追加されています。これは、スカベンジャーが無効化された環境では、このテストが期待通りに動作しないためです。

## コアとなるコードの変更箇所

1.  **`src/runtime/mheap.go`**:
    *   `scavengelist`関数に、`_PhysPageSize > _PageSize`の条件チェックが追加されました。
    *   この条件が真の場合、関数は即座に`0`を返してスカベンジャーの処理を停止します。

2.  **`src/runtime/debug/garbage_test.go`**:
    *   `TestFreeOSMemory`関数に、`runtime.GOARCH`が`"ppc64"`, `"ppc64le"`, または`"nacl"`の場合にテストをスキップする`t.Skip()`呼び出しが追加されました。

## コアとなるコードの解説

### `src/runtime/mheap.go`の変更

`mheap.go`はGoランタイムのヒープ管理の中核を担うファイルです。`scavengelist`関数は、ガベージコレクション後に解放されたメモリ領域をOSに返却する処理を行います。

```go
func scavengelist(list *mspan, now, limit uint64) uintptr {
    if _PhysPageSize > _PageSize {
        // golang.org/issue/9993
        // If the physical page size of the machine is larger than
        // our logical heap page size the kernel may round up the
        // amount to be freed to its page size and corrupt the heap
        // pages surrounding the unused block.
        return 0
    }

    // ... 既存のスカベンジャーロジック ...
}
```

この`if`文は、Goランタイムが起動時に検出した物理ページサイズ（`_PhysPageSize`）が、Goが内部的に使用する論理ページサイズ（`_PageSize`、通常は8KB）よりも大きい場合に発動します。この条件が満たされると、コメントに記載されているように、`madvise(2)`が意図しないメモリ領域を解放し、ヒープを破損させる可能性があるため、スカベンジャーの処理を中断し、`0`を返します。これにより、問題のある環境でのヒープ破損を防ぎます。

### `src/runtime/debug/garbage_test.go`の変更

`garbage_test.go`は、Goランタイムのガベージコレクションおよびメモリ管理に関連するテストを含むファイルです。

```go
func TestFreeOSMemory(t *testing.T) {
    switch runtime.GOARCH {
    case "ppc64", "ppc64le", "nacl":
        t.Skip("issue 9993; scavenger temporarily disabled on systems with 64k pages")
    }
    var ms1, ms2 runtime.MemStats

    // ... 既存のテストロジック ...
}
```

`TestFreeOSMemory`は、GoがOSにメモリを解放する機能（スカベンジャーの動作を含む）をテストするものです。上記の`switch`文は、現在の実行アーキテクチャが`ppc64`、`ppc64le`、または`nacl`のいずれかである場合、このテストをスキップするように指示します。これは、これらのアーキテクチャではスカベンジャーが意図的に無効化されているため、テストが失敗する可能性があるためです。テストをスキップすることで、CI/CDパイプラインでの不必要な失敗を防ぎ、この特定の修正がこれらのプラットフォームで正しく適用されていることを間接的に示します。

## 変更の背景

この変更の背景には、Goコンパイラにおけるクロージャのエスケープ解析の挙動と、Goランタイムの特殊な要件が絡んでいます。

Go 1.5.3では、クロージャの最適化が改善され、以前のバージョン（Go 1.4など）と比較して、変数のキャプチャが必ずしもその変数をヒープにエスケープさせるとは限らなくなりました。Go 1.4では、クロージャが外部の変数をキャプチャすると、その変数はヒープに割り当てられる傾向がありました。しかし、Go 1.5.3では、コンパイラがより賢くなり、変数の寿命がクロージャの寿命を超えないと判断した場合、スタックに割り当てることが可能になりました。

この最適化の進展により、新たな問題が浮上しました。クロージャがキャプチャする変数リストに、コンパイラ内部で特殊な意味を持つ`OXXX`ノードが含まれている場合、コンパイラがこれを正しく処理せず、エスケープ解析が誤動作することが判明しました。結果として、本来スタックに割り当てられるべきクロージャが、誤ってヒープに割り当てられてしまう「偽のエスケープ（spurious escape）」が発生していました。

特に問題となったのは、Goランタイムのコード内でこのようなヒープ割り当てが発生することです。Goランタイムは、ガベージコレクションのオーバーヘッドを最小限に抑え、予測可能なパフォーマンスを維持するために、ヒープ割り当てを極力避けるように設計されています。ランタイム内で不必要なヒープ割り当てが発生すると、パフォーマンスの低下やガベージコレクションの頻度増加につながり、システム全体の安定性に悪影響を及ぼす可能性があります。

このコミットは、`issue #14999`で報告されたこの問題を解決するために行われました。コミットメッセージでは、`fixedbugs/issue14999.go`の`f`と`g`の例を挙げて、Go 1.5.3が`g`は拒否するが`f`は拒否しないのに対し、Go 1.4は両方を拒否していたと説明されています。これは、Go 1.5.3のクロージャ最適化が、このバグを顕在化させたことを示唆しています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラに関する前提知識が必要です。

1.  **Goコンパイラ (`cmd/compile`) の内部構造**:
    Goコンパイラは、Goのソースコードを機械語に変換するプログラムです。このプロセスには、字句解析、構文解析、型チェック、中間表現（IR）の生成、最適化、コード生成などの段階があります。コンパイラは、ソースコードを抽象構文木（AST）として表現し、それを内部的なデータ構造に変換して処理を進めます。

2.  **クロージャ (Closures)**:
    Goにおけるクロージャは、関数が定義された環境（レキシカルスコープ）の変数を「記憶」し、その変数にアクセスできる関数です。クロージャは、外部の変数をキャプチャ（捕捉）することで機能します。キャプチャされた変数は、クロージャが実行される際に利用されます。

3.  **エスケープ解析 (Escape Analysis)**:
    エスケープ解析は、Goコンパイラが行う重要な最適化の一つです。これは、プログラム中の変数がスタックに割り当てられるべきか、それともヒープに割り当てられるべきかを静的に決定するプロセスです。
    *   **スタック割り当て**: 関数内で宣言され、その関数の実行が終了すると不要になる変数は、通常スタックに割り当てられます。スタック割り当ては高速で、ガベージコレクションの対象になりません。
    *   **ヒープ割り当て**: 変数がその変数を宣言した関数のスコープを超えて「エスケープ」する場合（例: ポインタが関数から返される、グローバル変数に代入される、クロージャによってキャプチャされ、クロージャが関数スコープを超えるなど）、その変数はヒープに割り当てられる必要があります。ヒープ割り当てはスタック割り当てよりも遅く、ガベージコレクションの対象となるため、パフォーマンスに影響を与えます。
    エスケープ解析は、不必要なヒープ割り当てを減らし、プログラムのパフォーマンスを向上させるために不可欠です。

4.  **`OXXX` ノード**:
    Goコンパイラの内部では、ソースコードの各要素がノードとして表現されます。`OXXX`ノードは、Goコンパイラの内部的な中間表現（IR）における特殊なオペコード（opcode）またはノードタイプを指します。これはGo言語の公開API（`go/ast`パッケージなど）には現れない、コンパイラの実装詳細です。通常、`OXXX`のようなノードは、特定の内部処理のためのプレースホルダーやマーカーとして使用され、他の多くの処理では明示的に無視されるか、特別な方法で扱われます。このコミットでは、クロージャのキャプチャ変数リストにこの`OXXX`ノードが誤って含まれており、それがエスケープ解析の誤動作を引き起こしていました。

5.  **Goランタイム (Go Runtime)**:
    Goランタイムは、Goプログラムの実行を管理する一連のライブラリとコードです。これには、ガベージコレクタ、ゴルーチン（goroutine）スケジューラ、メモリ管理、プリミティブな同期メカニズムなどが含まれます。ランタイムのコードは、Goプログラム全体の基盤となるため、非常に高いパフォーマンスと信頼性が求められます。そのため、ランタイムのコードは、通常のGoアプリケーションコードよりも厳しい制約の下で書かれることが多く、特にヒープ割り当ては厳しく制限されます。これは、ガベージコレクションの頻度を減らし、レイテンシを予測可能にするためです。

6.  **`compiling_runtime` フラグ**:
    Goコンパイラには、現在コンパイルしているコードがGoランタイムの一部であるかどうかを示す内部フラグ`compiling_runtime`が存在します。このフラグが設定されている場合、コンパイラはランタイムコードに特有の追加のチェックや制約を適用します。例えば、ランタイムコード内での特定の操作（ヒープ割り当てなど）を禁止することで、ランタイムの健全性とパフォーマンスを保証します。

## 技術的詳細

このコミットの技術的詳細は、Goコンパイラがクロージャのキャプチャ変数をどのように処理し、エスケープ解析がどのように行われるか、そしてGoランタイムの制約をどのように適用するかに関わっています。

問題の核心は、クロージャがキャプチャする変数リスト（`func_.Func.Cvars.Slice()`）に、コンパイラ内部の特殊な`OXXX`ノードが含まれていたことです。通常、`OXXX`ノードは他のコンパイラ処理で無視されるべきですが、クロージャのキャプチャ変数リストの処理においては、この無視が適切に行われていませんでした。その結果、コンパイラは、実際には有効なキャプチャ変数が存在しないにもかかわらず、`OXXX`ノードを「キャプチャされた変数」として誤認識し、クロージャがヒープにエスケープする必要があると判断してしまうことがありました。

この誤ったエスケープ解析は、特にGoランタイムのコード内で問題を引き起こしました。Goランタイムは、パフォーマンス上の理由から、ヒープ割り当てを厳しく制限しています。しかし、このバグにより、ランタイム内のクロージャが不必要にヒープに割り当てられ、ランタイムのパフォーマンス特性に悪影響を与える可能性がありました。

このコミットは、以下の主要な変更によってこの問題を解決します。

1.  **`hasemptycvars` 関数の導入**:
    この新しい関数は、与えられたクロージャが実質的に空のキャプチャ変数リストを持っているかどうかを判断します。この関数は、クロージャのキャプチャ変数リストを走査する際に、`OXXX`ノードを明示的に無視します。これにより、コンパイラは、`OXXX`ノードが存在しても、それが実際のキャプチャ変数ではないことを正しく認識し、クロージャが本当に変数をキャプチャしているかどうかを正確に判断できるようになります。

2.  **`closuredebugruntimecheck` 関数の導入**:
    この関数は、クロージャのエスケープ解析の結果をチェックし、特に`compiling_runtime`フラグが有効な場合に、ヒープ割り当てされたクロージャを検出します。もしランタイムのコンパイル中にヒープ割り当てされたクロージャが見つかった場合、`yyerrorl`（コンパイラエラー）を発生させて、このような不適切な状況をコンパイル時に阻止します。これにより、Goランタイムのコードがヒープ割り当ての制約に違反することを防ぎます。
    また、新しいデバッグフラグ`-d closure`が有効な場合、クロージャがヒープ割り当てされたかスタック割り当てされたか、およびキャプチャされた変数に関する詳細な警告メッセージを出力し、開発者がクロージャのエスケープ解析の挙動をデバッグしやすくします。

3.  **既存の処理の修正**:
    `walkclosure`関数と`staticassign`関数（特に`OCLOSURE`ケース）において、クロージャのキャプチャ変数リストの空判定に`hasemptycvars`関数を使用するように変更されました。これにより、キャプチャ変数が実質的に存在しないクロージャが、不必要にヒープにエスケープされることなく、グローバル変数として扱われるべき場合に正しく変換されるようになります。

4.  **デバッグフラグ `-d closure` の追加**:
    `src/cmd/compile/internal/gc/main.go`に`Debug_closure`という新しいデバッグフラグが追加されました。このフラグをコンパイラに渡すことで、クロージャのコンパイルに関する詳細な情報を出力させることができ、エスケープ解析のデバッグや理解に役立ちます。

5.  **テストケースの追加**:
    `test/fixedbugs/issue14999.go`という新しいテストファイルが追加されました。このテストは、ランタイム内でヒープ割り当てされたクロージャがコンパイルエラーとなることを検証し、将来的に同様のバグが再発しないことを保証します。

これらの変更により、Goコンパイラはクロージャのキャプチャ変数リストをより正確に解析し、`OXXX`ノードによる誤ったエスケープ解析を防ぎます。特にGoランタイムにおいては、ヒープ割り当てされたクロージャをコンパイル時に検出してエラーとすることで、ランタイムのパフォーマンスと安定性を維持します。

### `src/cmd/compile/internal/gc/closure.go`

```go
// hasemptycvars returns true iff closure func_ has an
// empty list of captured vars. OXXX nodes don't count.
func hasemptycvars(func_ *Node) bool {
	for _, v := range func_.Func.Cvars.Slice() {
		if v.Op == OXXX {
			continue // OXXXノードは無視する
		}
		return false // OXXX以外のキャプチャ変数が見つかったら、空ではない
	}
	return true // 全てのキャプチャ変数がOXXXだったか、リストが空だった
}

// closuredebugruntimecheck applies boilerplate checks for debug flags
// and compiling runtime
func closuredebugruntimecheck(r *Node) {
	if Debug_closure > 0 {
		if r.Esc == EscHeap {
			Warnl(r.Lineno, "heap closure, captured vars = %v", r.Func.Cvars)
		} else {
			Warnl(r.Lineno, "stack closure, captured vars = %v", r.Func.Cvars)
		}
	}
	if compiling_runtime > 0 && r.Esc == EscHeap {
		yyerrorl(r.Lineno, "heap-allocated closure, not allowed in runtime.")
	}
}

func walkclosure(func_ *Node, init *Nodes) *Node {
	// If no closure vars, don't bother wrapping.
	// 変更前: if len(func_.Func.Cvars.Slice()) == 0 {
	if hasemptycvars(func_) { // hasemptycvars を使用して空判定
		if Debug_closure > 0 {
			Warnl(func_.Lineno, "closure converted to global")
		}
		return func_.Func.Closure.Func.Nname
	} else {
		closuredebugruntimecheck(func_) // クロージャが空でない場合にチェック
	}

	// ... (後続の処理は省略)
}
```
*   **`hasemptycvars`**: この関数は、クロージャのキャプチャ変数リストを反復処理し、各変数のオペレーション（`v.Op`）が`OXXX`であるかどうかをチェックします。`OXXX`ノードであれば無視し、それ以外のノードが見つかれば、そのクロージャは空ではないと判断して`false`を返します。リストが完全に空であるか、または`OXXX`ノードのみで構成されている場合に`true`を返します。これにより、`OXXX`ノードが原因で誤ってキャプチャ変数があると判断されることを防ぎます。
*   **`closuredebugruntimecheck`**: この関数は、クロージャのエスケープ解析結果（`r.Esc`）が`EscHeap`（ヒープエスケープ）であるかどうかをチェックします。
    *   `Debug_closure`フラグが有効な場合、クロージャがヒープに割り当てられたかスタックに割り当てられたか、およびキャプチャ変数に関する警告を出力します。
    *   `compiling_runtime`フラグが有効で、かつクロージャがヒープに割り当てられている場合、`yyerrorl`を呼び出してコンパイルエラーを発生させます。これは、Goランタイムコード内でのヒープ割り当てクロージャを厳しく禁止するためです。
*   **`walkclosure`**: この関数は、クロージャの変換処理を担当します。変更前は`len(func_.Func.Cvars.Slice()) == 0`でキャプチャ変数の有無を判定していましたが、`hasemptycvars(func_)`に置き換えられました。これにより、`OXXX`ノードを無視した正確な空判定が可能になります。また、クロージャが空でないと判断された場合に`closuredebugruntimecheck`を呼び出し、ランタイムの制約チェックを行います。

```go
		} else {
			closuredebugruntimecheck(r) // クロージャが空でない場合にチェック
		}
	}
	// ... (後続の処理は省略)
}
```
*   `staticassign`関数は、静的な割り当て（コンパイル時に解決できる割り当て）を処理します。`OCLOSURE`ノードの場合、以前は`len(r.Func.Cvars.Slice()) == 0`でキャプチャ変数の有無を判定していましたが、ここでも`hasemptycvars(r)`に置き換えられました。これにより、キャプチャ変数が実質的に空のクロージャがグローバルとして扱われるべきかどうかの判断が正確になり、不必要なヒープ割り当てを防ぎます。また、`walkclosure`と同様に、空でないクロージャに対して`closuredebugruntimecheck`が呼び出されます。

### `test/fixedbugs/issue14999.go`

```go
// errorcheck -+

package p

func f(x int) func(int) int {
	return func(y int) int { return x + y } // ERROR "heap-allocated closure, not allowed in runtime."
}

func g(x int) func(int) int { // ERROR "x escapes to heap, not allowed in runtime."
	return func(y int) int { // ERROR "heap-allocated closure, not allowed in runtime."
		x += y
		return x + y
	}
}
```
*   このテストファイルは、`errorcheck -+`ディレクティブを使用しており、コンパイル時に特定の行で指定されたエラーメッセージが出力されることを期待します。
*   `f`と`g`の関数は、外部変数`x`をキャプチャするクロージャを返します。これらのクロージャは、ランタイム内で使用されることを想定しており、ヒープ割り当てが禁止されているため、コンパイルエラーとなるべきです。このテストは、`closuredebugruntimecheck`によってこれらのケースが正しく検出され、エラーが報告されることを検証します。

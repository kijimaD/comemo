# [インデックス 21788] ファイルの概要

このコミットは、Goランタイムにおける`defer`ステートメントの実行に使用される`_defer`構造体のプール管理に関する重要な改善を導入しています。以前の設計では、各論理プロセッサ（P）に紐付けられた`defer`プールが無限に成長する可能性があり、特にゴルーチンがP間を移動するシナリオでメモリリークや過剰なメモリ使用を引き起こす問題がありました。このコミットは、中央の`defer`プールを導入し、各Pのローカルプールを固定サイズに制限することで、この問題を解決し、メモリ使用の効率化と安定化を図っています。

## 元コミット内容

```
runtime: bound defer pools

The unbounded list-based defer pool can grow infinitely.
This can happen if a goroutine routinely allocates a defer;
then blocks on one P; and then unblocked, scheduled and
frees the defer on another P.
The scenario was reported on golang-nuts list.

We've been here several times. Any unbounded local caches
are bad and grow to infinite size. This change introduces
central defer pool; local pools become fixed-size
with the only purpose of amortizing accesses to the
central pool.

Change-Id: Iadcfb113ccecf912e1b64afc07926f0de9de2248
Reviewed-on: https://go-review.googlesource.com/3741
Reviewed-by: Keith Randall <khr@golang.org>
```

## 変更の背景

この変更の主な背景は、Goランタイムにおける`defer`構造体（`_defer`）のプールが、特定の条件下で無限に成長し、メモリを過剰に消費する問題が発生していたことです。

具体的には、以下のようなシナリオが問題を引き起こしていました。

1.  **無制限なローカルプール**: 以前のGoランタイムでは、`_defer`構造体は各論理プロセッサ（P）に紐付けられたローカルなプール（`p.deferpool`）にキャッシュされていました。このプールはリストベースであり、サイズに上限がありませんでした。
2.  **ゴルーチンのP間移動**: あるゴルーチンが頻繁に`defer`を割り当て、その後、あるP上でブロックし、別のP上でスケジュールされて`defer`を解放する、という状況が発生することがありました。
3.  **メモリリーク**: このようなP間移動が発生すると、`defer`構造体が元のPのローカルプールに戻されず、新しいPのローカルプールに解放されるため、元のPのプールには使用されなくなった`_defer`構造体が蓄積されていきました。結果として、元のPのローカルプールは無限に成長し、メモリを解放しない状態に陥りました。
4.  **コミュニティからの報告**: この問題は、Goコミュニティのメーリングリストである`golang-nuts`で報告されており、実際のアプリケーションでメモリ使用量の増大として顕在化していました。

コミットメッセージにもあるように、「無制限なローカルキャッシュは悪であり、無限のサイズに成長する」という認識が開発チームにはありました。この問題は`defer`プールに限らず、他のランタイムのキャッシュ機構でも過去に同様の問題が発生していたため、根本的な解決策が求められていました。

このコミットは、この無限に成長する問題を解決し、ランタイムのメモリ管理をより堅牢で予測可能なものにすることを目的としています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoランタイムの概念と`defer`の仕組みに関する知識が必要です。

### 1. Goの`defer`ステートメント

`defer`ステートメントは、関数がリターンする直前（パニックが発生した場合も含む）に、指定された関数呼び出しを遅延実行させるためのGoの機能です。主にリソースの解放（ファイルクローズ、ロック解除など）や、エラーハンドリングの簡素化に使用されます。

*   **実行順序**: 複数の`defer`ステートメントが同じ関数内で宣言された場合、それらはLIFO（Last-In, First-Out）の順序で実行されます。つまり、最後に宣言された`defer`が最初に実行されます。
*   **`_defer`構造体**: ランタイム内部では、各`defer`呼び出しは`_defer`という構造体として表現されます。この構造体には、遅延実行される関数の情報や引数などが含まれます。これらの`_defer`構造体は、関数の実行中にスタック上に積まれ、関数が終了する際に順次実行・解放されます。

### 2. Goランタイムのスケジューラ（M-P-Gモデル）

Goランタイムは、効率的な並行処理を実現するために、M-P-Gという独自のスケジューラモデルを採用しています。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。数KB程度のスタックを持ち、数百万個のゴルーチンを同時に実行できます。
*   **M (Machine/OS Thread)**: オペレーティングシステムのスレッドです。Goランタイムは、M上でゴルーチンを実行します。MはOSスケジューラによって管理されます。
*   **P (Processor/Logical Processor)**: 論理的なプロセッサであり、MとGの仲介役を果たします。Pは実行可能なゴルーチンのキューを持ち、MはPからゴルーチンを取得して実行します。Pの数は通常、CPUのコア数に設定され、MがPにアタッチされることでゴルーチンを実行できます。Pは、ゴルーチンがシステムコールなどでブロックされた際に、他のMに引き渡されることがあります。

このM-P-Gモデルにより、GoランタイムはOSスレッドの切り替えコストを最小限に抑えつつ、多数のゴルーチンを効率的にスケジューリングします。

### 3. `defer`プールの概念

`defer`ステートメントが頻繁に使用されるアプリケーションでは、`_defer`構造体の割り当てと解放が頻繁に発生します。これらの小さな構造体を毎回ヒープに割り当てると、GCの負荷が増大し、パフォーマンスに影響を与える可能性があります。このオーバーヘッドを削減するため、Goランタイムは`_defer`構造体を再利用するためのプール（キャッシュ）を保持しています。

*   **ローカルプール（Per-P Pool）**: 以前は、各Pが自身の`_defer`構造体のプール（`p.deferpool`）を持っていました。これは、ゴルーチンが現在実行されているPから直接`_defer`構造体を取得・解放することで、ロックの競合を減らし、キャッシュの局所性を高めることを目的としていました。
*   **問題点**: このローカルプールがリストベースで無制限に成長する設計だったため、前述のP間移動のシナリオでメモリリークが発生する可能性がありました。

### 4. メモリ管理とガベージコレクション（GC）

Goは自動メモリ管理（ガベージコレクション）を採用しています。ヒープに割り当てられたオブジェクトは、参照されなくなった時点でGCによって回収されます。しかし、プールにキャッシュされたオブジェクトは、たとえ使用されていなくても参照されていると見なされ、GCの対象になりません。そのため、プールが無限に成長すると、GCが動作してもメモリが解放されず、アプリケーションのメモリ使用量が際限なく増加するという問題が発生します。

これらの前提知識を理解することで、このコミットがGoランタイムの安定性と効率性をどのように向上させたかが明確になります。

## 技術的詳細

このコミットは、Goランタイムの`defer`プールが無限に成長する問題を解決するために、以下の主要な技術的変更を導入しています。

### 1. 中央`defer`プールの導入

*   **`sched.deferpool`**: グローバルなスケジューラ構造体`schedt`に、新しい中央`defer`プール`sched.deferpool`が追加されました。これは、様々なサイズの`_defer`構造体をキャッシュするためのプールであり、複数のP間で共有されます。
*   **ロック機構**: 中央プールへのアクセスは、`sched.deferlock`というミューテックスによって保護されます。これにより、複数のPからの同時アクセスに対する安全性が確保されます。

### 2. ローカル`defer`プールの固定サイズ化

*   **`p.deferpool`の変更**: 各Pが持つローカルな`defer`プール`p.deferpool`は、以前の無制限なリストベースの構造から、固定サイズの`_defer`構造体のスライス（`[5][]*_defer`）に変更されました。
*   **`p.deferpoolbuf`の導入**: `p.deferpool`の実体となるバッファとして、`p.deferpoolbuf [5][32]*_defer`が導入されました。これにより、各サイズの`defer`構造体に対して最大32個の`_defer`構造体をローカルにキャッシュできるようになります。この固定サイズ化により、各Pが保持する`defer`構造体のメモリ使用量が厳密に制限されます。

### 3. `_defer`構造体の取得（`newdefer`関数）の変更

`newdefer`関数は、新しい`_defer`構造体を割り当てる際に呼び出されます。

*   **ローカルキャッシュの優先**: まず、現在のPのローカルプール（`pp.deferpool[sc]`）から`_defer`構造体を取得しようとします。
*   **中央プールからの補充**: もしローカルプールが空の場合、`sched.deferlock`をロックし、中央プール（`sched.deferpool[sc]`）からローカルプールに`_defer`構造体を補充します。この際、ローカルプールの容量の半分まで補充されます。これにより、ローカルプールが完全に空になることを防ぎ、中央プールへのアクセス頻度を減らします。
*   **新規割り当て**: ローカルプールも中央プールも空の場合、新しい`_defer`構造体がヒープに割り当てられます。

### 4. `_defer`構造体の解放（`freedefer`関数）の変更

`freedefer`関数は、`_defer`構造体の実行が完了し、解放される際に呼び出されます。

*   **ローカルキャッシュへの返却**: 解放された`_defer`構造体は、まず現在のPのローカルプール（`pp.deferpool[sc]`）に追加されます。
*   **中央プールへの排出**: もしローカルプールがその容量（`cap(pp.deferpool[sc])`）に達した場合、ローカルプールの内容の半分が`sched.deferlock`をロックして中央プール（`sched.deferpool[sc]`）に転送されます。これにより、ローカルプールが過剰に肥大化することを防ぎ、中央プールが他のPに`_defer`構造体を提供できるようになります。

### 5. プールクリア処理の変更（`clearpools`関数）

*   **中央プールのクリア**: ガベージコレクションのサイクル中に呼び出される`clearpools`関数は、以前は各Pのローカルプールをクリアしていましたが、この変更により、中央`defer`プール（`sched.deferpool`）をクリアするようになりました。これにより、中央プールに蓄積された`_defer`構造体が適切に解放されます。
*   **ローカルプールの扱い**: 各Pのローカルプールは固定サイズになったため、明示的にクリアする必要がなくなりました。

### 6. Pの初期化/リサイズ処理の変更（`procresize`関数）

*   `procresize`関数は、Pの数が変更されたり、Pが初期化される際に呼び出されます。この変更により、新しく作成されるPの`p.deferpool`が適切に初期化され、`p.deferpoolbuf`がゼロクリアされるようになりました。

これらの変更により、`defer`構造体の割り当てと解放のメカニズムが、ローカルキャッシュと中央プールの連携によって効率的かつメモリ使用量に上限を持つように再設計されました。これにより、以前の無限成長の問題が解決され、Goランタイムの安定性とパフォーマンスが向上しました。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は、以下のファイルに集中しています。

1.  **`src/runtime/mgc0.go`**:
    *   `clearpools`関数において、以前は各Pのローカル`defer`プールをクリアしていたロジックが削除され、代わりに中央`defer`プール（`sched.deferpool`）をクリアするロジックが追加されました。これにより、中央プールに蓄積された`_defer`構造体が適切に解放されるようになります。

2.  **`src/runtime/panic.go`**:
    *   `newdefer`関数（`_defer`構造体の割り当て）と`freedefer`関数（`_defer`構造体の解放）のロジックが大幅に変更されました。
        *   `newdefer`では、ローカルプールが空の場合に中央プールから`_defer`構造体を補充する処理が追加されました。
        *   `freedefer`では、ローカルプールが満杯の場合に、その内容の半分を中央プールに転送する処理が追加されました。
        *   `p.deferpool`がリストからスライスベースのプールに変更されたことに伴い、`d.link`によるリスト操作からスライス操作（`append`, スライスによる切り詰め）に変わっています。

3.  **`src/runtime/proc1.go`**:
    *   `procresize`関数において、新しいPが作成される際や既存のPがリサイズされる際に、`p.deferpool`（スライスベースになった）の初期化と、そのバッキング配列である`p.deferpoolbuf`のゼロクリアを行う処理が追加されました。

4.  **`src/runtime/runtime2.go`**:
    *   `p`構造体の定義が変更されました。
        *   `deferpool`フィールドの型が`[5]*_defer`から`[5][]*_defer`（`_defer`構造体のスライスの配列）に変更されました。
        *   `deferpoolbuf [5][32]*_defer`という、固定サイズの`_defer`構造体バッファが追加されました。これが`p.deferpool`の実際のストレージとなります。
    *   `schedt`構造体の定義が変更されました。
        *   `deferlock mutex`（中央プールを保護するためのミューテックス）が追加されました。
        *   `deferpool [5]*_defer`（中央`defer`プール）が追加されました。

これらの変更は、`defer`構造体のライフサイクル管理とメモリプーリング戦略の根本的な再設計を反映しています。

## コアとなるコードの解説

このコミットの核心は、`src/runtime/panic.go`内の`newdefer`と`freedefer`関数の変更、および`src/runtime/runtime2.go`内の`p`と`schedt`構造体の定義変更にあります。

### `src/runtime/runtime2.go`における構造体定義の変更

```go
// type p struct
type p struct {
    // ...
    deferpool    [5][]*_defer // pool of available defer structs of different sizes (see panic.go)
    deferpoolbuf [5][32]*_defer // Fixed-size buffer for deferpool
    // ...
}

// type schedt struct
type schedt struct {
    // ...
    deferlock mutex // Mutex to protect the central defer pool
    deferpool [5]*_defer // central pool of available defer structs of different sizes
    // ...
}
```
*   `p.deferpool`: 各Pが持つローカルプールです。以前は`_defer`へのポインタの配列でしたが、`_defer`スライスの配列になりました。これにより、各サイズの`_defer`構造体を可変長のスライスとして管理できるようになります。
*   `p.deferpoolbuf`: `p.deferpool`のスライスが参照する実際の固定サイズバッファです。`[5]`は`_defer`構造体のサイズカテゴリに対応し、`[32]`は各カテゴリで最大32個の`_defer`構造体をキャッシュできることを意味します。これにより、ローカルプールのメモリ使用量が厳密に制限されます。
*   `sched.deferlock`: 中央`defer`プール`sched.deferpool`へのアクセスを保護するためのミューテックスです。複数のPが同時に中央プールにアクセスする際の競合を防ぎます。
*   `sched.deferpool`: 中央`defer`プールです。各サイズの`_defer`構造体のリストのヘッドを保持します。

### `src/runtime/panic.go`における`newdefer`関数の変更

```go
func newdefer(siz int32) *_defer {
    // ...
    if sc < uintptr(len(p{}.deferpool)) { // sc is size class
        pp := mp.p // Current P
        if len(pp.deferpool[sc]) == 0 { // If local pool is empty
            lock(&sched.deferlock) // Acquire lock for central pool
            // Transfer from central pool to local pool until local pool is half full
            for len(pp.deferpool[sc]) < cap(pp.deferpool[sc])/2 && sched.deferpool[sc] != nil {
                d := sched.deferpool[sc]
                sched.deferpool[sc] = d.link // Remove from central pool
                d.link = nil // Clear link to prevent dangling refs
                pp.deferpool[sc] = append(pp.deferpool[sc], d) // Add to local pool
            }
            unlock(&sched.deferlock) // Release lock
        }
        if ln := len(pp.deferpool[sc]); ln > 0 { // If local pool has elements
            d = pp.deferpool[sc][ln-1] // Get last element
            pp.deferpool[sc][ln-1] = nil // Clear reference
            pp.deferpool[sc] = pp.deferpool[sc][:ln-1] // Shrink slice
        }
    }
    if d == nil { // If no defer struct found in pools, allocate new one
        // ... allocate new _defer ...
    }
    // ...
    return d
}
```
*   `newdefer`は、まず現在のPのローカルプール（`pp.deferpool[sc]`）から`_defer`構造体を取得しようとします。
*   ローカルプールが空の場合（`len(pp.deferpool[sc]) == 0`）、`sched.deferlock`をロックし、中央プール`sched.deferpool[sc]`から`_defer`構造体をローカルプールに補充します。補充はローカルプールの容量の半分（`cap(pp.deferpool[sc])/2`）に達するまで行われます。これにより、中央プールへのロック取得の頻度を減らしつつ、ローカルキャッシュのヒット率を維持します。
*   ローカルプールから取得する際は、スライスの末尾から要素を取り出し、スライスを切り詰めます。

### `src/runtime/panic.go`における`freedefer`関数の変更

```go
func freedefer(d *_defer) {
    // ...
    if sc < uintptr(len(p{}.deferpool)) { // sc is size class
        mp := acquirem()
        pp := mp.p // Current P
        if len(pp.deferpool[sc]) == cap(pp.deferpool[sc]) { // If local pool is full
            // Transfer half of local cache to the central cache.
            var first, last *_defer
            for len(pp.deferpool[sc]) > cap(pp.deferpool[sc])/2 { // Until local pool is half full
                ln := len(pp.deferpool[sc])
                d := pp.deferpool[sc][ln-1] // Get last element
                pp.deferpool[sc][ln-1] = nil // Clear reference
                pp.deferpool[sc] = pp.deferpool[sc][:ln-1] // Shrink slice
                if first == nil {
                    first = d
                } else {
                    last.link = d // Link to the list being transferred
                }
                last = d
            }
            lock(&sched.deferlock) // Acquire lock for central pool
            last.link = sched.deferpool[sc] // Link the transferred list to central pool
            sched.deferpool[sc] = first // Set new head of central pool
            unlock(&sched.deferlock) // Release lock
        }
        *d = _defer{} // Zero out the defer struct
        pp.deferpool[sc] = append(pp.deferpool[sc], d) // Add to local pool
        releasem(mp)
    }
}
```
*   `freedefer`は、解放された`_defer`構造体をまず現在のPのローカルプール（`pp.deferpool[sc]`）に追加します。
*   ローカルプールが満杯の場合（`len(pp.deferpool[sc]) == cap(pp.deferpool[sc])`）、ローカルプールの内容の半分を中央プールに転送します。この転送は、ローカルプールが容量の半分になるまで行われます。
*   転送される`_defer`構造体は、一時的にリストとして連結され、その後`sched.deferlock`をロックして中央プール`sched.deferpool[sc]`の先頭に連結されます。
*   `_defer`構造体は再利用される前にゼロクリアされます（`*d = _defer{}`）。

これらの変更により、`defer`構造体の割り当てと解放が、ローカルキャッシュと中央プールの間で効率的に行われるようになり、各Pのローカルプールが無限に成長する問題が解決されました。中央プールはグローバルなリソースとして管理され、必要に応じてロックによって保護されます。

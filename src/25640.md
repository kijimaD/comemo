# [インデックス 25640] ファイルの概要

このコミットは、Goランタイムにおけるスタック管理、特に`ppc64x`アーキテクチャ上での`nosplit`関数のスタックフレームサイズ増加に対応するための変更を導入しています。具体的には、スタックガードの制限値を引き上げ、関連するテストケースを更新することで、より大きなスタックフレームを持つ関数が正しく動作するようにしています。

## コミット

`cmd/internal/obj`, `cmd/link`, `runtime`: `ppc64x`上のより大きなフレームに対応するためスタック制限を増加

## 元コミット内容

```
cmd/internal/obj, cmd/link, runtime: increase stack limit to accommodate larger frames on ppc64x

Larger stack frames mean nosplit functions use more stack and so the limit
needs to increase.
```

## 変更の背景

Goランタイムは、関数の呼び出し時にスタックを効率的に管理します。特に、スタックのオーバーフローを防ぐために「スタックガード」と呼ばれるメカニズムを使用しています。これは、スタックの現在の使用量と利用可能な領域を監視し、必要に応じてスタックを拡張（スプリット）するものです。

`nosplit`関数は、スタックの拡張チェックを行わない特殊な関数です。これらの関数は、非常に短い処理や、スタック拡張処理自体がデッドロックを引き起こす可能性があるような低レベルの操作（例えば、スタック拡張処理自体）で使用されます。`nosplit`関数はスタック拡張チェックを行わないため、呼び出し時に十分なスタック領域が確保されていることを前提とします。

このコミットの背景には、`ppc64x`（PowerPC 64-bit）アーキテクチャにおいて、特定の`nosplit`関数のスタックフレームサイズが以前よりも大きくなったという状況があります。スタックフレームが大きくなると、`nosplit`関数が使用するスタック領域が増加し、既存のスタックガード制限ではスタックオーバーフローが発生するリスクが高まります。この問題を解決するためには、スタックガードの制限値を引き上げ、`nosplit`関数が安全に実行できる十分なスタック領域を確保する必要がありました。

また、`test/nosplit.go`の変更が「少し醜い」とコメントされているのは、アーキテクチャごとのスタック使用量の違いをテストケースで細かく調整する必要があったためです。特に`ppc64`アーキテクチャの`CallSize`（関数呼び出しに必要な最小スタックサイズ）が他のアーキテクチャと異なるため、テストの期待値を調整する必要がありました。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するシステム。ガベージコレクション、スケジューリング、スタック管理など、低レベルの機能を提供します。
*   **スタック (Stack)**: 関数呼び出しの際に、ローカル変数、引数、戻りアドレスなどを格納するために使用されるメモリ領域。Goでは、必要に応じてスタックが動的に拡張されます（スタックスプリット）。
*   **スタックガード (Stack Guard)**: スタックオーバーフローを防ぐためのメカニズム。スタックの現在のポインタがスタックガードの閾値に近づくと、ランタイムはスタックを拡張する処理（`morestack`）を呼び出します。
*   **`nosplit`関数**: Goコンパイラによって生成される関数の一種で、スタック拡張チェックを行わない関数。これらの関数は、スタック拡張処理自体がデッドロックを引き起こす可能性があるような、非常に低レベルのランタイムコードで使用されます。`nosplit`関数は、呼び出し時に十分なスタック領域が確保されていることを前提とします。
*   **`stackGuardMultiplier`**: スタックガードのサイズを計算する際に使用される乗数。これは、コンパイルオプション（特に`-N`フラグによる最適化無効化）によって値が変わり、デバッグビルドなどでスタックガードを大きくするために使用されます。
*   **`ppc64x` (PowerPC 64-bit)**: IBMが開発したPowerPCアーキテクチャの64ビット版。Goは様々なアーキテクチャをサポートしており、`ppc64`や`ppc64le`（リトルエンディアン版）などが含まれます。アーキテクチャによって、レジスタの使用方法や関数呼び出し規約、スタックフレームの構造が異なる場合があります。
*   **`CallSize`**: 関数呼び出しに必要な最小スタックサイズ。アーキテクチャによって異なる値を取ります。例えば、`ppc64`では32バイトとされています。これは、関数が呼び出される際に、戻りアドレスやレジスタの保存などに最低限必要なスタック領域を指します。
*   **スタックフレーム (Stack Frame)**: 関数が呼び出されるたびにスタック上に割り当てられる領域。これには、関数の引数、ローカル変数、戻りアドレス、保存されたレジスタなどが含まれます。

## 技術的詳細

このコミットの主要な変更点は、Goランタイムがスタックオーバーフローを検出するために使用する`StackGuard`定数の値を増加させたことです。

以前は、`StackGuard`は`640 * stackGuardMultiplier + StackSystem`として定義されていました。このコミットでは、`640`が`720`に増加され、新しい定義は`720 * stackGuardMultiplier + StackSystem`となります。この変更は、`src/cmd/internal/obj/stack.go`（コンパイラが使用するオブジェクトファイル生成関連の定義）と`src/runtime/stack.go`（ランタイムが使用するスタック関連の定義）の両方で行われています。これにより、Goプログラムが利用できるスタックの最小安全マージンが実質的に増加します。

この`StackGuard`の増加は、特に`ppc64x`アーキテクチャにおける`nosplit`関数のスタックフレームサイズの増加に対応するためのものです。`nosplit`関数はスタック拡張チェックを行わないため、呼び出し時に十分なスタック領域が確保されていることが極めて重要です。スタックフレームが大きくなると、より多くのスタック領域が必要となり、`StackGuard`の値を引き上げなければ、スタックオーバーフローが発生する可能性がありました。

`test/nosplit.go`の変更は、この`StackGuard`の増加と`ppc64`アーキテクチャの特性を反映したものです。
*   `nosplit`リーフ関数（他の関数を呼び出さない`nosplit`関数）が利用できるスタックサイズに関するテストケースの期待値が調整されています。特に`ppc64`および`ppc64le`アーキテクチャでは、`CallSize`が32バイトであるため、他のアーキテクチャよりも利用可能なスタック領域が少なくなることを考慮し、テストの期待値が`main 112 nosplit`から`main 96 nosplit`などに変更され、特定のアーキテクチャでテストがスキップされる（`REJECT ppc64 ppc64le`）ようになっています。
*   `nosplit`関数から別の`nosplit`関数を呼び出す場合、および`nosplit`関数からスタック拡張を行う関数を呼び出す場合のテストケースも同様に調整されています。ここでも`ppc64`の`CallSize`が考慮され、他のアーキテクチャとのスタック使用量の違いが反映されています。
*   テストの初期スタックフレームサイズを調整するロジックも更新されています。以前は`512 - 128`バイトが追加されていましたが、新しい`StackGuard`の値に合わせて`592 - 128`バイトが追加されるようになっています。また、`-N`フラグ（最適化無効化）が指定された場合のスタックガードの調整値も`640`から`720`に更新されています。

これらの変更により、`ppc64x`アーキテクチャ上で`nosplit`関数がより大きなスタックフレームを使用しても、Goランタイムが安定して動作することが保証されます。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/cmd/internal/obj/stack.go`**:
    *   `StackGuard`定数の値が`640*stackGuardMultiplier + StackSystem`から`720*stackGuardMultiplier + StackSystem`に変更されました。

2.  **`src/runtime/stack.go`**:
    *   `_StackGuard`定数の値が`640*sys.StackGuardMultiplier + _StackSystem`から`720*sys.StackGuardMultiplier + _StackSystem`に変更されました。

3.  **`test/nosplit.go`**:
    *   `nosplit`関数のスタック使用量に関するテストケースの期待値が、特に`ppc64`および`ppc64le`アーキテクチャ向けに調整されました。
    *   `REJECT ppc64 ppc64le`などのディレクティブが追加され、特定のアーキテクチャでテストがスキップされるようになりました。
    *   テストの初期スタックフレームサイズを調整するロジックにおいて、追加されるバイト数が`512 - 128`から`592 - 128`に、また`-N`フラグ時の調整値が`640`から`720`にそれぞれ変更されました。

## コアとなるコードの解説

### `src/cmd/internal/obj/stack.go` および `src/runtime/stack.go`

これらのファイルにおける変更は非常にシンプルで、`StackGuard`（または`_StackGuard`）という定数の数値が`640`から`720`に更新されただけです。

```go
// src/cmd/internal/obj/stack.go
const (
	// ...
	StackGuard  = 720*stackGuardMultiplier + StackSystem // 変更後
	// StackGuard  = 640*stackGuardMultiplier + StackSystem // 変更前
	// ...
)

// src/runtime/stack.go
const (
	// ...
	_StackGuard = 720*sys.StackGuardMultiplier + _StackSystem // 変更後
	// _StackGuard = 640*sys.StackGuardMultiplier + _StackSystem // 変更前
	// ...
)
```

この`StackGuard`は、Goランタイムがスタックオーバーフローを検出するための閾値を定義しています。スタックポインタがこの値に近づくと、ランタイムはスタックを拡張する処理（`morestack`）をトリガーします。この値を増加させることで、`nosplit`関数がより大きなスタックフレームを使用しても、スタックオーバーフローが発生する前に十分な警告と対応が可能になります。`stackGuardMultiplier`は、コンパイル時の設定（特に最適化の有無）によってスタックガードのサイズを調整するための乗数です。

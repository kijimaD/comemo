# [インデックス 25973] ファイルの概要

`cmd/compile/internal/gc: fix internal compiler error on invalid declaration`

このコミットは、Goコンパイラ（`gc`）において、不正な宣言（具体的には、空の`import`文の後に`var?`のような無効なシンボルを含む宣言）が存在する場合に発生していた内部コンパイラエラー（Internal Compiler Error, ICE）を修正するものです。これにより、コンパイラがクラッシュする代わりに、より適切なエラーメッセージを出力するようになります。

## 変更の背景

この変更の背景には、Goコンパイラが特定の不正なGoコードに対して、内部コンパイラエラー（ICE）を引き起こすというバグが存在していました。具体的には、以下のようなコードスニペットが問題でした。

```go
package a
import"" // 空のインポートパス
var?      // 不正なシンボル '?' を含む変数宣言
```

このコードをコンパイルしようとすると、Goコンパイラはまず2行目の空のインポートパスに対してエラーを報告します。しかし、その後の3行目の`var?`という不正な宣言を処理する際に、コンパイラ内部の`newname`関数（または関連するシンボル宣言ロジック）が`nil`シンボルを受け取ってしまい、結果として「`internal compiler error: newname nil`」というメッセージと共にコンパイラがクラッシュしていました。

内部コンパイラエラーは、コンパイラ自身のバグを示しており、ユーザーの不正な入力に対してコンパイラが予期せぬ動作をする状態です。理想的には、ユーザーのコードが不正である場合は、コンパイラは明確で理解しやすいエラーメッセージを報告し、クラッシュすることなく処理を終了すべきです。このコミットは、このコンパイラの堅牢性を向上させ、不正な入力に対するより適切なエラーハンドリングを実現することを目的としています。

この問題はGoのIssueトラッカーで `#11610` として報告されていました。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの基本的な構造と、シンボル管理に関する知識が必要です。

*   **Goコンパイラ (gc)**: Go言語の公式コンパイラは`gc`と呼ばれます。これは、Goのソースコードを機械語に変換する役割を担っています。`gc`は複数のフェーズ（字句解析、構文解析、意味解析、中間コード生成、最適化、コード生成など）を経てコンパイルを行います。
*   **`cmd/compile/internal/gc`パッケージ**: これはGoコンパイラの主要な部分であり、コンパイラのバックエンド（コード生成、最適化、型チェックなど）のロジックが含まれています。`parser.go`ファイルは、このパッケージ内で構文解析を担当する重要な部分です。
*   **字句解析 (Lexical Analysis)**: ソースコードをトークン（キーワード、識別子、演算子、リテラルなど）のストリームに分解するプロセスです。例えば、`var?`という文字列は、`var`というキーワードと、`?`という（Go言語の文法では不正な）シンボルに分解されます。
*   **構文解析 (Syntax Analysis)**: 字句解析によって生成されたトークンのストリームを基に、プログラムの構文構造がGo言語の文法規則に準拠しているかを確認し、抽象構文木（Abstract Syntax Tree, AST）を構築するプロセスです。この段階で文法エラーが検出されます。
*   **`Sym` (Symbol)**: コンパイラ内部で、変数名、関数名、型名などの識別子を表すデータ構造です。各シンボルは、その名前、スコープ、型などの情報を持っています。
*   **`Node`**: 抽象構文木（AST）を構成する基本的な要素です。各`Node`は、プログラムの特定の構文要素（例えば、変数宣言、関数呼び出し、式など）を表します。
*   **`newname` および `dclname` 関数**:
    *   `newname`は、新しいシンボル（`Sym`）を作成し、それに対応する`Node`を生成する役割を持つ関数であると推測されます。
    *   `dclname`は、既存のシンボル、または`newname`によって生成されたシンボルを受け取り、それを宣言（`dcl`は"declare"の略）として処理する関数であると推測されます。この関数は、シンボルが有効であることを前提として動作します。問題は、`dclname`が`nil`のシンボルを受け取った場合に、その前提が崩れて内部エラーを引き起こす点にありました。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの構文解析フェーズにおけるシンボル宣言の堅牢性向上にあります。

1.  **問題の特定**:
    Goコンパイラの`src/cmd/compile/internal/gc/parser.go`ファイルには、`dcl_name_list`という関数が存在します。この関数は、変数宣言リストなどを処理する際に、`p.sym()`を呼び出してシンボルを取得し、その結果を直接`dclname`関数に渡していました。
    `p.sym()`は、現在のトークンからシンボルを生成しようとしますが、`var?`のような不正なシンボル（`?`はGoの識別子として無効）に遭遇した場合、有効な`Sym`オブジェクトを生成できず、`nil`を返す可能性がありました。
    `dclname`関数は、引数として有効な`Sym`オブジェクトが渡されることを期待しており、`nil`が渡されると内部でパニック（クラッシュ）を引き起こしていました。これが「`internal compiler error: newname nil`」の根本原因でした。

2.  **修正アプローチ**:
    この問題を解決するために、コミットでは`parser.go`に`dcl_name`という新しいヘルパー関数が導入されました。この`dcl_name`関数は、`dclname`を呼び出す前に、渡された`Sym`が`nil`でないことを明示的にチェックします。
    *   もし`Sym`が`nil`であれば、`yyerrorl`関数を使って「`invalid declaration`」という適切なエラーメッセージを報告し、`nil`を返します。
    *   `Sym`が`nil`でなければ、既存の`dclname(sym)`を呼び出します。

3.  **`dcl_name_list`の変更**:
    `dcl_name_list`関数内の`dclname(p.sym())`という直接的な呼び出しは、新しく導入された`p.dcl_name(p.sym())`に置き換えられました。これにより、`dclname`が`nil`シンボルを受け取る前に、`dcl_name`ヘルパー関数によるチェックとエラーハンドリングが介在するようになります。

4.  **エラーメッセージの改善**:
    この修正により、コンパイラは不正な宣言に対してクラッシュする代わりに、よりユーザーフレンドリーなエラーメッセージ「`invalid declaration`」を出力するようになります。これにより、開発者はコードのどこに問題があるかをより明確に理解できるようになります。

5.  **新旧パーサーへの対応**:
    コミットメッセージには「This CL was initially meant to be applied to the old parser, and has been updated to apply to the new parser.」とあります。これは、Goコンパイラのパーサーが進化する過程で、この修正が古いパーサー向けに考案されたものの、最終的には新しいパーサーの構造に合わせて調整・適用されたことを示唆しています。これは、コンパイラの内部構造が変更されても、バグ修正のロジックが適切に移行されたことを意味します。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は、以下の2つのファイルに集中しています。

1.  **`src/cmd/compile/internal/gc/parser.go`**:
    *   **`dcl_name`関数の追加**:
        ```go
        func (p *parser) dcl_name(sym *Sym) *Node {
            if trace && Debug['x'] != 0 {
                defer p.trace("dcl_name")()
            }

            if sym == nil {
                yyerrorl(int(prevlineno), "invalid declaration")
                return nil
            }
            return dclname(sym)
        }
        ```
        この新しいメソッドは、`Sym`が`nil`である場合に`yyerrorl`を呼び出してエラーを報告し、`nil`を返します。そうでない場合は、元の`dclname`関数を呼び出します。

    *   **`dcl_name_list`関数の変更**:
        ```go
        // 変更前
        // l := list1(dclname(p.sym()))
        // for p.got(',') {
        //  l = list(l, dclname(p.sym()))
        // }

        // 変更後
        l := list1(p.dcl_name(p.sym()))
        for p.got(',') {
            l = list(l, p.dcl_name(p.sym()))
        }
        ```
        `dclname(p.sym())`の直接呼び出しが、新しく定義された`p.dcl_name(p.sym())`に置き換えられています。

2.  **`test/fixedbugs/issue11610.go`**:
    このコミットでは、修正を検証するための新しいテストファイルも追加されています。
    ```go
    // errorcheck

    // Copyright 2015 The Go Authors. All rights reserved.
    // Use of this source code is governed by a BSD-style
    // license that can be found in the LICENSE file.

    // Test an internal compiler error on ? symbol in declaration
    // following an empty import.

    package a
    import""  // ERROR "import path is empty"
    var?      // ERROR "invalid declaration"

    var x int // ERROR "unexpected var"

    func main() {
    }
    ```
    このテストファイルは、問題となっていた不正なコードスニペットを含み、`// ERROR "..."`コメントによって、期待されるエラーメッセージが正確に出力されることを検証しています。これにより、コンパイラがクラッシュせず、適切なエラーを報告することが保証されます。

## コアとなるコードの解説

`parser.go`における変更は、Goコンパイラの堅牢性を高める上で非常に重要です。

新しく追加された`dcl_name`メソッドは、シンボル宣言処理の安全弁として機能します。
`func (p *parser) dcl_name(sym *Sym) *Node`
この関数は、`p.sym()`から取得した`Sym`ポインタを引数として受け取ります。
`if sym == nil`のチェックが最も重要です。もし`p.sym()`が不正な入力（例: `var?`の`?`）のために有効なシンボルを生成できず`nil`を返した場合、このチェックがそれを捕捉します。
`yyerrorl(int(prevlineno), "invalid declaration")`は、`nil`シンボルが検出された場合に、コンパイラがクラッシュする代わりに、指定された行番号（`prevlineno`）で「`invalid declaration`」というエラーメッセージを出力するようにします。`yyerrorl`は、Goコンパイラがエラーを報告するために使用する内部関数の一つです。
このエラー報告の後、関数は`nil`を返し、後続の処理が不正な`Node`で続行されるのを防ぎます。
`return dclname(sym)`は、`sym`が有効な場合にのみ実行され、既存の正しいシンボル宣言ロジックを維持します。

`dcl_name_list`関数内の変更は、この新しい安全弁を既存の構文解析フローに統合するものです。
`l := list1(p.dcl_name(p.sym()))`および`l = list(l, p.dcl_name(p.sym()))`という変更により、`dclname`が直接呼び出される前に、常に`p.dcl_name`による`nil`チェックが挟まれるようになります。これにより、不正なシンボルが原因で`dclname`がクラッシュする可能性が排除されます。

`test/fixedbugs/issue11610.go`の追加は、回帰テストの観点から非常に重要です。このテストは、将来の変更によってこのバグが再発しないことを保証します。`// ERROR "..."`ディレクティブは、Goのテストフレームワークが特定の行で特定のエラーメッセージが出力されることを期待していることを示し、コンパイラの出力が期待通りであることを自動的に検証します。

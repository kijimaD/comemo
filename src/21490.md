# [インデックス 21490] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）の並行性を向上させるための重要な変更を導入しています。具体的には、GCを専用のバックグラウンドゴルーチンで実行し、リソースが利用可能な場合に呼び出し元（ミューテーター）が実行可能になるようにすることで、特に単一ゴルーチンアプリケーションにおけるGCの停止時間を削減することを目指しています。また、大量にメモリを割り当てるゴルーチンがGCを支援し、それによって自身の割り当てを抑制するメカニズムも導入されています。

## 変更の背景

このコミットは、Go 1.5リリースに向けたガベージコレクション（GC）の抜本的な改善の一環として行われました。Goの初期バージョンでは、GCは「Stop-the-World (STW)」方式を採用しており、GCが実行される間、すべてのアプリケーションゴルーチンが一時停止していました。これにより、特に大規模なヒープを持つアプリケーションでは、顕著なレイテンシースパイクが発生し、ユーザーエクスペリエンスやサーバーの応答性に悪影響を与える可能性がありました。

このコミットの主な目的は、GCの実行中にアプリケーションの実行を可能な限り継続させることで、STWの時間を最小限に抑え、GCによるレイテンシーを削減することです。特に、単一のゴルーチンしか持たないアプリケーションでは、GCがバックグラウンドで実行されることで、そのゴルーチンがGCの完了を待つことなく、より早く再開できるようになります。

また、メモリ割り当てが活発なゴルーチンがGC作業を「手伝う」メカニズムを導入することで、GCの進行を加速させると同時に、そのゴルーチン自身のメモリ割り当て速度を自然に抑制するという、巧妙なフィードバックループを形成しています。これは、GCが追いつかないほど高速にメモリが割り当てられる状況（GCスループットの問題）に対処するための一歩でもあります。

コミットメッセージに「Memory efficiency work will happen later in 1.5」とあるように、このコミットはGCの並行性（concurrency）とレイテンシーの改善に焦点を当てており、メモリ効率の最適化はGo 1.5の後の段階で取り組まれる予定であったことが示唆されています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの基本的な概念とガベージコレクションの仕組みに関する知識が必要です。

### Goランタイムとゴルーチン (Goroutines)
Goプログラムは、Goランタイムによって管理されます。Goランタイムは、スケジューラ、メモリマネージャ、ガベージコレクタなどを含みます。
ゴルーチンはGoの軽量な並行処理単位であり、OSのスレッドよりもはるかに少ないリソースで作成・管理されます。Goランタイムのスケジューラが、これらのゴルーチンをOSスレッドにマッピングして実行します。

### ガベージコレクション (GC)
ガベージコレクションは、プログラムが動的に割り当てたメモリのうち、もはや到達不可能（参照されていない）になったオブジェクトを自動的に解放するプロセスです。これにより、開発者は手動でのメモリ管理から解放され、メモリリークのリスクが軽減されます。

GoのGCは、主に以下のフェーズで構成されます（このコミット以前の一般的なGCの概念）：
1.  **マーク (Mark)**: GCのルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトをマークします。
2.  **スイープ (Sweep)**: マークされなかった（到達不可能な）オブジェクトが占めていたメモリを解放し、再利用可能な状態にします。

### Stop-the-World (STW)
STWは、GCの特定のフェーズ（特にマークフェーズの開始時や終了時）において、すべてのアプリケーションゴルーチンの実行を一時的に停止させる期間を指します。この期間中、アプリケーションは一切処理を進めることができません。STWはGCの正確性を保証するために必要ですが、その時間が長くなるとアプリケーションの応答性に悪影響を与えます。Go 1.5以前のGCは、このSTW時間が長くなる傾向がありました。

### ヒープ (Heap)
ヒープは、プログラムが実行時に動的にメモリを割り当てる領域です。Goのオブジェクトは通常、ヒープに割り当てられます。GCは主にこのヒープ領域を管理します。

### mcache, mspan, mheap
Goのメモリ管理は、階層的な構造を持っています。
-   **mcache**: 各P（プロセッサ、Goスケジューラの論理的なCPU）にローカルなキャッシュです。小さなオブジェクトの割り当てを高速化するために使用されます。
-   **mspan**: 連続したメモリページの集合です。mspanは特定のサイズのオブジェクトを格納するために使用されます。
-   **mheap**: すべてのmspanを管理するグローバルなヒープ構造です。OSからメモリを要求し、mspanに分割してmcacheや直接ゴルーチンに提供します。

### ワークバッファ (Work Buffer)
並行GCにおいて、マークフェーズ中に発見された到達可能なオブジェクト（ポインタ）を一時的に格納するためのバッファです。GCワーカーゴルーチンは、このワークバッファからポインタを取り出し、さらにマーク作業を進めます。

## 技術的詳細

このコミットは、GoランタイムのGCを並行化するための複数の重要な変更を導入しています。

### 1. バックグラウンドGCゴルーチンの導入
最も大きな変更点は、GC作業を専用のバックグラウンドゴルーチン (`backgroundgc`) で実行するようにしたことです。
-   `src/runtime/mgc0.go` に `backgroundgc` 関数が追加されました。この関数は無限ループで `gcwork(0)` を呼び出し、GC作業が完了すると `goparkunlock` を使って自身をパーク（一時停止）させます。
-   `src/runtime/malloc.go` の `gogc` 関数が変更され、`force == 0` の場合（通常のGCトリガー時）に、`bggc` 構造体（`bggc.g` はバックグラウンドGCゴルーチン、`bggc.working` はGCがアクティブかどうかを示すフラグ）の状態を確認し、バックグラウンドGCゴルーチンを起動または再開するようになりました。これにより、GCがアプリケーションの実行と並行して進むことが可能になります。

### 2. ミューテーターによるGC支援 (`gchelpwork`)
メモリを大量に割り当てるアプリケーションゴルーチン（ミューテーター）が、GC作業を支援するメカニズムが導入されました。
-   `src/runtime/malloc.go` の `mallocgc` 関数内で、`shouldhelpgc` というフラグが導入されました。これは、`mCache_Refill` や `largeAlloc` のように、メモリ割り当てがGCに影響を与える可能性のある操作が行われた場合に `true` に設定されます。
-   `mallocgc` のエピローグで、`shouldhelpgc` が `true` かつバックグラウンドGCがアクティブ (`bggc.working == 1`) な場合に、`systemstack(gchelpwork)` が呼び出されます。
-   `src/runtime/mgc.go` に `gchelpwork` 関数が追加されました。この関数は、現在のGCフェーズに応じて、GC作業の一部を実行します。特に `_GCmark` フェーズでは、`trygetfull()` でワークバッファを取得し、`drainobjects` を呼び出してそのワークバッファ内のオブジェクトを処理します。これにより、ミューテーターが自身の割り当てを続けながら、GCの進行を助けることができます。これは、GCが追いつかないほど速い割り当てが行われる場合に、ミューテーターが自らGCを助けることで、割り当て速度を間接的に抑制する効果も持ちます。

### 3. GCトリガーのヒューリスティック変更
-   `src/runtime/malloc.go` に `shouldtriggergc()` 関数が追加されました。この関数は、`memstats.heap_alloc`（現在のヒープ割り当て量）と `memstats.next_gc`（次回のGCがトリガーされるべきヒープサイズ）を比較し、GCをトリガーすべきかどうかを判断します。以前は `memstats.heap_alloc >= memstats.next_gc/2` という単純な条件でしたが、より洗練された `memstats.heap_alloc+memstats.heap_alloc*3/4 >= memstats.next_gc` という条件と、バックグラウンドGCが現在実行中でないこと (`atomicloaduint(&bggc.working) == 0`) を確認するようになりました。これにより、GCの開始タイミングがより適切に制御され、不必要なGCの繰り返しが避けられます。

### 4. ワークバッファサイズの調整
-   `src/runtime/mgc.go` で `_WorkbufSize` が `4 * 1024` から `4 * 256` に削減されました。これは、ワークバッファのサイズを小さくすることで、キャッシュ効率の向上や、GCヘルパーゴルーチン間でのワークバッファの共有をより細かく制御することを意図している可能性があります。

### 5. テストの調整
-   `test/init1.go` のテストロジックが変更され、メモリ使用量の閾値が `chunk*50` から `chunk*500` に緩和されました。これは、このコミットがGCの並行性向上に焦点を当てており、メモリ効率の厳密なテストは後のバージョン（Go 1.5）で行われるというコミットメッセージの意図を反映しています。

### 6. `gcwork` 関数の導入とSTWの管理
-   `gogc` からGCの実際の作業が `gcwork` 関数に分離されました。
-   `gcwork` 関数内では、`semacquire(&worldsema, false)` と `semrelease(&worldsema)` を使用して、STWのセマフォを管理しています。これにより、GCの特定のクリティカルセクションでのみSTWが適用され、それ以外の時間は並行して作業が進められるようになります。
-   `stoptheworld` と `starttheworld` の呼び出しが、GCフェーズの特定のポイント（マーク開始前、マーク終了後など）に限定されるようになりました。

これらの変更により、GoのGCは、従来の完全なSTW方式から、より並行性の高い方式へと移行し、アプリケーションの応答性とスループットのバランスを改善しました。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

-   `src/runtime/malloc.go`: メモリ割り当て時のGCトリガーロジック、GCヘルプメカニズム、および `gogc` 関数の大幅な改修。
-   `src/runtime/mgc.go`: GCの内部処理、特にワークバッファの管理、`drainobjects` や `gchelpwork` といったGCヘルプ関連関数の追加。
-   `src/runtime/mgc0.go`: バックグラウンドGCゴルーチン (`backgroundgc`) の定義。
-   `test/init1.go`: GCテストの閾値調整。

特に、`src/runtime/malloc.go` の `mallocgc` 関数と `gogc` 関数、`src/runtime/mgc.go` の `gchelpwork` 関数、そして `src/runtime/mgc0.go` の `backgroundgc` 関数が、この変更の核心をなしています。

## コアとなるコードの解説

### `src/runtime/malloc.go` の変更点

#### `shouldtriggergc()` 関数
```go
func shouldtriggergc() bool {
	return memstats.heap_alloc+memstats.heap_alloc*3/4 >= memstats.next_gc && atomicloaduint(&bggc.working) == 0
}
```
この関数は、GCをトリガーすべきかどうかを判断します。
-   `memstats.heap_alloc+memstats.heap_alloc*3/4 >= memstats.next_gc`: 現在のヒープ割り当て量 (`heap_alloc`) が、次回のGCがトリガーされるべき閾値 (`next_gc`) を超えているか、またはその閾値に近づいているかをチェックします。`heap_alloc*3/4` は、前回のGCで解放されたメモリの約半分が再利用された場合にGCをトリガーするというヒューリスティックを示唆しています。
-   `atomicloaduint(&bggc.working) == 0`: バックグラウンドGCが現在実行中でないことを確認します。これにより、GCが既に進行中の場合に新たなGCを不必要にトリガーするのを防ぎます。

#### `mallocgc` 関数内のGCトリガーとヘルプ
```go
// ... (snip) ...
	if shouldtriggergc() {
		gogc(0)
	} else if shouldhelpgc && atomicloaduint(&bggc.working) == 1 {
		// bggc.lock not taken since race on bggc.working is benign.
		// At worse we don't call gchelpwork.
		// Delay the gchelpwork until the epilogue so that it doesn't
		// interfere with the inner working of malloc such as
		// mcache refills that might happen while doing the gchelpwork
		systemstack(gchelpwork)
	}
// ... (snip) ...
```
-   `shouldtriggergc()` が `true` の場合、`gogc(0)` を呼び出してGCをトリガーします。`0` は通常の（強制ではない）GCを示します。
-   `shouldhelpgc` が `true`（メモリ割り当てがGCに影響を与える可能性のある操作が行われた）かつ、バックグラウンドGCがアクティブ (`bggc.working == 1`) な場合、`gchelpwork` を呼び出します。`systemstack` は、現在のゴルーチンをシステムスタックに切り替えて `gchelpwork` を実行することを意味します。これにより、ミューテーターゴルーチンがGC作業の一部を分担します。

#### `gogc` 関数の変更
```go
func gogc(force int32) {
	// ... (snip) ...
	if force == 0 {
		lock(&bggc.lock)
		if !bggc.started {
			bggc.working = 1
			bggc.started = true
			go backgroundgc() // Start the background GC goroutine
		} else if bggc.working == 0 {
			bggc.working = 1
			ready(bggc.g) // Resume the background GC goroutine
		}
		unlock(&bggc.lock)
	} else {
		gcwork(force) // Force GC directly
	}
}

func gcwork(force int32) {
	// ... (snip) ...
	semacquire(&worldsema, false) // Acquire semaphore for STW
	// ... (snip) ...
	systemstack(stoptheworld) // Stop all goroutines
	// ... (snip) ...
	systemstack(starttheworld) // Resume all goroutines
	// ... (snip) ...
	semrelease(&worldsema) // Release semaphore
}
```
-   `gogc` は、`force` 引数によって動作が変わります。
    -   `force == 0` の場合（通常のGC）：`bggc` の状態をチェックし、まだ開始されていない場合は `backgroundgc()` ゴルーチンを起動します。既に開始されているが停止している場合は、`ready(bggc.g)` でそのゴルーチンを再開します。これにより、GCがバックグラウンドで並行して実行されます。
    -   `force != 0` の場合（強制GC）：`gcwork(force)` を直接呼び出し、GCを即座に実行します。
-   `gcwork` 関数は、実際のGCのマーク、スイープなどのフェーズを実行します。この関数内で `stoptheworld` と `starttheworld` が呼び出され、GCのクリティカルな部分でのみアプリケーションゴルーチンが停止されるように制御されます。

### `src/runtime/mgc.go` の変更点

#### `gchelpwork()` 関数
```go
//go:nowritebarrier
func gchelpwork() {
	switch gcphase {
	// ... (snip) ...
	case _GCmark:
		// Get a full work buffer and empty it.
		var wbuf *workbuf
		wbuf = trygetfull()
		if wbuf != nil {
			drainobjects(wbuf, uintptr(len(wbuf.obj))) // drain upto one buffer's worth of objects
		}
	// ... (snip) ...
	}
}
```
-   この関数は、ミューテーターゴルーチンがGCを支援する際の具体的な処理を定義します。
-   `_GCmark` フェーズ中に呼び出された場合、`trygetfull()` を使って利用可能なワークバッファ（GCがマークしたオブジェクトのポインタが格納されている）を取得します。
-   ワークバッファが取得できた場合、`drainobjects` を呼び出してそのワークバッファ内のオブジェクトを処理（マーク作業を継続）します。これにより、ミューテーターがGCのマークフェーズの進行を助けます。

#### `drainobjects()` 関数
```go
// Scan at most count objects in the wbuf.
//go:nowritebarrier
func drainobjects(wbuf *workbuf, count uintptr) {
	for i := uintptr(0); i < count; i++ {
		if wbuf.nobj == 0 {
			putempty(wbuf)
			return
		}
		wbuf.nobj--
		b := wbuf.obj[wbuf.nobj]
		wbuf = scanobject(b, mheap_.arena_used-b, nil, wbuf)
	}
	putpartial(wbuf)
	return
}
```
-   `gchelpwork` から呼び出され、指定された `count` のオブジェクトをワークバッファから取り出し、`scanobject` を使ってそれらをスキャン（マーク作業を継続）します。
-   ワークバッファが空になった場合や、指定されたオブジェクト数を処理し終えた場合、ワークバッファを `putempty` または `putpartial` で適切なリストに戻します。

### `src/runtime/mgc0.go` の変更点

#### `backgroundgc()` 関数
```go
func backgroundgc() {
	bggc.g = getg()
	bggc.g.issystem = true
	for {
		gcwork(0) // Perform GC work
		lock(&bggc.lock)
		bggc.working = 0 // Mark as not working
		goparkunlock(&bggc.lock, "Concurrent GC wait") // Park itself
	}
}
```
-   この関数は、Goランタイムによって新しいゴルーチンとして起動されます。
-   無限ループ内で `gcwork(0)` を呼び出し、GCの実際の作業を実行します。
-   GC作業が完了すると、`bggc.working` を `0` に設定して非アクティブ状態にし、`goparkunlock` を使って自身をパークします。これにより、GCが不要な間はゴルーチンがCPUリソースを消費しないようになります。GCが再度トリガーされると、`gogc` 関数内で `ready(bggc.g)` が呼び出され、このゴルーチンが再開されます。

これらの変更は、GoのGCを「並行マーク＆スイープ」GCへと進化させるための基盤を築きました。これにより、GCのSTW時間が大幅に短縮され、Goアプリケーションのレイテンシー特性が改善されました。

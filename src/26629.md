# [インデックス 26629] ファイルの概要

このコミットは、Goコンパイラのアセンブラバックエンドにおけるフィールドトラッキングロジックのリファクタリングに関するものです。具体的には、x86アーキテクチャ固有のコードから、より汎用的な`cmd/internal/obj`パッケージへと`fieldtrack`機能が移動されました。

`src/cmd/internal/obj/obj.go`: Goアセンブラの共通オブジェクトファイルフォーマットと関連するユーティリティ関数を定義するファイルです。アセンブラのバックエンド間で共有される汎用的な処理が含まれます。
`src/cmd/internal/obj/objfile.go`: アセンブラが生成するオブジェクトファイルの処理、特にプログラムリストのフラッシュやシンボル処理に関連する機能が含まれます。
`src/cmd/internal/obj/x86/asm6.go`: x86アーキテクチャ向けのアセンブラバックエンドの実装ファイルです。x86固有の命令のエンコードや処理ロジックが含まれます。

## 変更の背景

この変更の主な背景は、Goコンパイラのアセンブラバックエンドにおけるコードの汎用化と保守性の向上です。元々、構造体のフィールド使用を追跡する`fieldtrack`ロジックは、x86アーキテクチャ固有のアセンブラバックエンド（`src/cmd/internal/obj/x86/asm6.go`）内に埋め込まれていました。しかし、このフィールドトラッキングの概念はx86アーキテクチャに特有のものではなく、他のアーキテクチャ（ARM、PPC64など）でも同様に必要とされる可能性があります。

特定のアーキテクチャのバックエンドに汎用的なロジックが混在していると、以下の問題が生じます。

1.  **コードの重複**: 他のアーキテクチャで同様の機能が必要になった場合、同じロジックを各バックエンドに実装し直す必要があり、コードの重複が発生します。
2.  **保守性の低下**: 汎用的なロジックが特定のバックエンドに依存しているため、そのロジックの変更やバグ修正が、すべてのバックエンドに適切に反映されているかを確認する手間が増えます。
3.  **アーキテクチャ非依存性の欠如**: Goコンパイラは複数のアーキテクチャをサポートしており、可能な限りアーキテクチャ非依存のコードを共有することで、開発効率とコード品質を向上させることができます。

このコミットは、`fieldtrack`ロジックをx86バックエンドから`cmd/internal/obj`というより上位の、アーキテクチャ非依存のパッケージに移動することで、これらの問題を解決し、コードの再利用性と保守性を高めることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラのアセンブラ部分に関するいくつかの前提知識が必要です。

1.  **Goコンパイラの構造**: Goコンパイラは、ソースコードを中間表現に変換し、最終的に各ターゲットアーキテクチャ向けのアセンブリコードを生成します。`cmd/internal/obj`パッケージは、このアセンブリコード生成の共通部分と、各アーキテクチャ固有のバックエンド（例: `cmd/internal/obj/x86`、`cmd/internal/obj/arm`）を連携させる役割を担っています。
2.  **`obj.Prog` (Program Instruction)**: Goアセンブラにおける単一の命令（オペコードとオペランド）を表す構造体です。アセンブラはソースコードを`Prog`のリストに変換し、これを処理します。
3.  **`obj.LSym` (Linker Symbol)**: リンカが扱うシンボル（関数、グローバル変数など）を表す構造体です。各`LSym`は、そのシンボルに関連する`Prog`のリスト（つまり、そのシンボルを実装するアセンブリコード）を持つことができます。
4.  **`AUSEFIELD` (Pseudo-instruction)**: これは実際のCPU命令ではなく、Goアセンブラが内部的に使用する「擬似命令」の一つです。`AUSEFIELD`は、特定のシンボル（通常は構造体のフィールド）がコード内で使用されていることをマークするために挿入されます。これは、デバッグ情報生成や、未使用フィールドの検出、あるいはガベージコレクションの最適化など、コンパイラやランタイムがフィールドの使用状況を把握するために利用されます。
5.  **`R_USEFIELD` (Relocation Type)**: リロケーションとは、リンカがプログラムを結合する際に、アドレスやオフセットを修正する処理のことです。`R_USEFIELD`は、`AUSEFIELD`擬似命令によってマークされたフィールド使用情報に対応する特殊なリロケーションタイプです。このリロケーションは、リンカに対して、特定のシンボル（フィールド）が参照されていることを通知し、リンカがその情報をオブジェクトファイルや実行ファイルに適切に埋め込むために使用されます。
6.  **`obj.Link` (Linker Context)**: アセンブラとリンカの間で状態や設定を共有するためのコンテキスト構造体です。シンボルテーブル、リロケーション情報、エラーハンドリングなどが含まれます。
7.  **アセンブラバックエンド**: Goコンパイラは、x86、ARM、ARM64などの異なるCPUアーキテクチャをサポートしています。各アーキテクチャには、その命令セットに特化したアセンブリコードを生成するための「バックエンド」が存在します。`src/cmd/internal/obj/x86/asm6.go`は、x86アーキテクチャのバックエンドの一部です。

## 技術的詳細

このコミットの技術的詳細は、`fieldtrack`という特定の処理が、Goコンパイラのアセンブラパイプラインのどの段階で、どのように実行されるように変更されたかにあります。

### `fieldtrack`関数の役割

`fieldtrack`関数は、与えられたシンボル（`cursym *LSym`）に関連付けられたすべてのアセンブリ命令（`Prog`）を走査します。その目的は、`AUSEFIELD`という擬似命令を探し出すことです。`AUSEFIELD`命令が見つかった場合、その命令が参照しているシンボル（`p.From.Sym`）に対して、`R_USEFIELD`タイプのリロケーションエントリを追加します。

リロケーションエントリは、`Addrel(ctxt.Cursym)`によって現在のシンボル（`cursym`）に追加されます。このリロケーションは、オフセット（`r.Off`）とサイズ（`r.Siz`）が0に設定され、参照されるシンボル（`r.Sym`）とタイプ（`r.Type = R_USEFIELD`）が指定されます。これにより、リンカは後でこの情報を使用して、どのフィールドが使用されているかを把握できるようになります。

### 変更前: x86バックエンドでの処理

変更前は、`AUSEFIELD`命令の処理ロジックが`src/cmd/internal/obj/x86/asm6.go`内の`asmins`関数に直接記述されていました。`asmins`関数は、x86アーキテクチャの各`Prog`命令をアセンブルする際に呼び出される関数です。

```go
// src/cmd/internal/obj/x86/asm6.go (変更前)
if p.As == obj.AUSEFIELD {
    r := obj.Addrel(ctxt.Cursym)
    r.Off = 0
    r.Siz = 0
    r.Sym = p.From.Sym
    r.Type = obj.R_USEFIELD
    return // AUSEFIELDは実際の命令ではないため、ここで処理を終了
}
```

この実装では、`AUSEFIELD`の処理がx86固有のアセンブラロジックと密接に結合していました。

### 変更後: 汎用パッケージへの移動

このコミットでは、`fieldtrack`関数が`src/cmd/internal/obj/obj.go`に新しく定義され、`AUSEFIELD`の処理ロジックがそこに移されました。

```go
// src/cmd/internal/obj/obj.go (変更後)
func fieldtrack(ctxt *Link, cursym *LSym) {
    p := cursym.Text
    if p == nil || p.Link == nil { // 外部関数やELFセクションシンボルを処理
        return
    }
    ctxt.Cursym = cursym

    for ; p != nil; p = p.Link {
        if p.As == AUSEFIELD {
            r := Addrel(ctxt.Cursym)
            r.Off = 0
            r.Siz = 0
            r.Sym = p.From.Sym
            r.Type = R_USEFIELD
        }
    }
}
```

そして、この新しい`fieldtrack`関数は、`src/cmd/internal/obj/objfile.go`内の`Flushplist`関数から呼び出されるようになりました。`Flushplist`は、アセンブラがシンボルごとのプログラムリスト（`Prog`のリスト）の処理を終え、オブジェクトファイルに書き出す準備をする段階で呼び出される関数です。

```go
// src/cmd/internal/obj/objfile.go (変更後)
func Flushplist(ctxt *Link) {
    // ... 既存の処理 ...
    for _, s := range ctxt.Text {
        // ... 既存の処理 ...
        ctxt.Arch.Follow(ctxt, s)
        ctxt.Arch.Preprocess(ctxt, s)
        ctxt.Arch.Assemble(ctxt, s)
        fieldtrack(ctxt, s) // ここでfieldtrackが呼び出される
        linkpcln(ctxt, s)
    }
    // ... 既存の処理 ...
}
```

この変更により、`fieldtrack`のロジックは特定のアーキテクチャバックエンドから切り離され、アセンブラの共通処理の一部として実行されるようになりました。`ctxt.Arch.Assemble(ctxt, s)`が呼び出された後、つまり各シンボルのアセンブリが完了した後に`fieldtrack`が実行されるため、`AUSEFIELD`命令が適切に処理されることが保証されます。

### なぜこのタイミングで？

`Flushplist`は、各シンボル（関数など）のアセンブリ処理が完了した後に呼び出されるため、そのシンボル内のすべての`Prog`命令が生成され、`AUSEFIELD`擬似命令も含まれている状態です。この段階で`fieldtrack`を実行することで、アセンブリ処理の最終段階でフィールド使用情報を収集し、リロケーションとして記録することができます。これは、アセンブリコード生成とフィールドトラッキングという異なる関心事を分離しつつ、適切なタイミングで連携させるための設計判断と言えます。

## コアとなるコードの解説

### `src/cmd/internal/obj/obj.go` に追加された `fieldtrack` 関数

この関数は、Goアセンブラの共通ユーティリティとして、フィールド使用の追跡ロジックをカプセル化します。

```go
func fieldtrack(ctxt *Link, cursym *LSym) {
    p := cursym.Text
    // cursym.Text は、現在のシンボル (関数など) に関連付けられた最初の命令 (Prog) を指します。
    // このリストを走査して AUSEFIELD 命令を探します。

    if p == nil || p.Link == nil { // handle external functions and ELF section symbols
        // シンボルに命令がない場合 (例: 外部関数宣言、ELFセクションシンボルなど) は処理をスキップします。
        return
    }
    ctxt.Cursym = cursym
    // 現在処理しているシンボルをリンカコンテキストに設定します。
    // これは Addrel 関数がリロケーションをどのシンボルに追加すべきかを知るために必要です。

    for ; p != nil; p = p.Link {
        // シンボルに関連付けられたすべての命令を順に走査します。
        if p.As == AUSEFIELD {
            // AUSEFIELD 擬似命令が見つかった場合、フィールド使用のリロケーションを追加します。
            r := Addrel(ctxt.Cursym)
            // Addrel は、現在のシンボル (ctxt.Cursym) に新しいリロケーションエントリを追加し、そのポインタを返します。
            r.Off = 0
            // オフセットは0に設定されます。AUSEFIELDは実際のコードを生成しないため、特定のオフセットは不要です。
            r.Siz = 0
            // サイズも0に設定されます。
            r.Sym = p.From.Sym
            // リロケーションが参照するシンボルは、AUSEFIELD 命令の From フィールドに格納されているシンボルです。
            // これは通常、使用されている構造体フィールドのシンボルです。
            r.Type = R_USEFIELD
            // リロケーションのタイプを R_USEFIELD に設定します。
            // これにより、リンカはこのリロケーションがフィールド使用情報であることを認識します。
        }
    }
}
```

### `src/cmd/internal/obj/objfile.go` の `Flushplist` 関数における変更

`Flushplist`関数は、アセンブラが各シンボルのプログラムリストを処理し終えた後、オブジェクトファイルに書き出す前に呼び出されます。

```go
func Flushplist(ctxt *Link) {
    // ... 既存の処理 ...
    for _, s := range ctxt.Text {
        // ctxt.Text は、アセンブル対象のすべてのテキストシンボル (関数など) のリストです。
        // 各シンボル s に対して以下の処理を行います。
        ctxt.Arch.Follow(ctxt, s)
        ctxt.Arch.Preprocess(ctxt, s)
        ctxt.Arch.Assemble(ctxt, s)
        // ここで、ターゲットアーキテクチャ固有のアセンブラバックエンドが、
        // シンボル s の Prog リストを実際の機械語命令に変換します。
        // この処理が完了すると、Prog リストには AUSEFIELD などの擬似命令が含まれている可能性があります。

        fieldtrack(ctxt, s) // ここでfieldtrackが呼び出される
        // 各シンボルのアセンブリが完了した後、fieldtrack 関数が呼び出されます。
        // これにより、アセンブルされた Prog リスト内の AUSEFIELD 命令が走査され、
        // 適切な R_USEFIELD リロケーションがシンボル s に追加されます。
        // このタイミングは、フィールド使用情報を収集するのに最適です。
        // なぜなら、すべての命令が処理され、AUSEFIELD が存在していればそれが確定しているからです。

        linkpcln(ctxt, s)
    }
    // ... 既存の処理 ...
}
```

この変更の主な背景は、Goコンパイラのアセンブラバックエンドにおけるコードの汎用化と保守性の向上です。元々、構造体のフィールド使用を追跡する`fieldtrack`ロジックは、x86アーキテクチャ固有のアセンブラバックエンド（`src/cmd/internal/obj/x86/asm6.go`）内に埋め込まれていました。しかし、このフィールドトラッキングの概念はx86アーキテクチャに特有のものではなく、他のアーキテクチャ（ARM、PPC64など）でも同様に必要とされる可能性があります。

特定のアーキテクチャのバックエンドに汎用的なロジックが混在していると、以下の問題が生じます。

1.  **コードの重複**: 他のアーキテクチャで同様の機能が必要になった場合、同じロジックを各バックエンドに実装し直す必要があり、コードの重複が発生します。
2.  **保守性の低下**: 汎用的なロジックが特定のバックエンドに依存しているため、そのロジックの変更やバグ修正が、すべてのバックエンドに適切に反映されているかを確認する手間が増えます。
3.  **アーキテクチャ非依存性の欠如**: Goコンパイラは複数のアーキテクチャをサポートしており、可能な限りアーキテクチャ非依存のコードを共有することで、開発効率とコード品質を向上させることができます。

このコミットは、`fieldtrack`ロジックをx86バックエンドから`cmd/internal/obj`というより上位の、アーキテクチャ非依存のパッケージに移動することで、これらの問題を解決し、コードの再利用性と保守性を高めることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラのアセンブラ部分に関するいくつかの前提知識が必要です。

1.  **Goコンパイラの構造**: Goコンパイラは、ソースコードを中間表現に変換し、最終的に各ターゲットアーキテクチャ向けのアセンブリコードを生成します。`cmd/internal/obj`パッケージは、このアセンブリコード生成の共通部分と、各アーキテクチャ固有のバックエンド（例: `cmd/internal/obj/x86`、`cmd/internal/obj/arm`）を連携させる役割を担っています。
2.  **`obj.Prog` (Program Instruction)**: Goアセンブラにおける単一の命令（オペコードとオペランド）を表す構造体です。アセンブラはソースコードを`Prog`のリストに変換し、これを処理します。
3.  **`obj.LSym` (Linker Symbol)**: リンカが扱うシンボル（関数、グローバル変数など）を表す構造体です。各`LSym`は、そのシンボルに関連する`Prog`のリスト（つまり、そのシンボルを実装するアセンブリコード）を持つことができます。
4.  **`AUSEFIELD` (Pseudo-instruction)**: これは実際のCPU命令ではなく、Goアセンブラが内部的に使用する「擬似命令」の一つです。`AUSEFIELD`は、特定のシンボル（通常は構造体のフィールド）がコード内で使用されていることをマークするために挿入されます。これは、デバッグ情報生成や、未使用フィールドの検出、あるいはガベージコレクションの最適化など、コンパイラやランタイムがフィールドの使用状況を把握するために利用されます。
5.  **`R_USEFIELD` (Relocation Type)**: リロケーションとは、リンカがプログラムを結合する際に、アドレスやオフセットを修正する処理のことです。`R_USEFIELD`は、`AUSEFIELD`擬似命令によってマークされたフィールド使用情報に対応する特殊なリロケーションタイプです。このリロケーションは、リンカに対して、特定のシンボル（フィールド）が参照されていることを通知し、リンカがその情報をオブジェクトファイルや実行ファイルに適切に埋め込むために使用されます。
6.  **`obj.Link` (Linker Context)**: アセンブラとリンカの間で状態や設定を共有するためのコンテキスト構造体です。シンボルテーブル、リロケーション情報、エラーハンドリングなどが含まれます。
7.  **アセンブラバックエンド**: Goコンパイラは、x86、ARM、ARM64などの異なるCPUアーキテクチャをサポートしています。各アーキテクチャには、その命令セットに特化したアセンブリコードを生成するための「バックエンド」が存在します。`src/cmd/internal/obj/x86/asm6.go`は、x86アーキテクチャのバックエンドの一部です。

## 技術的詳細

このコミットの技術的詳細は、`fieldtrack`という特定の処理が、Goコンパイラのアセンブラパイプラインのどの段階で、どのように実行されるように変更されたかにあります。

### `fieldtrack`関数の役割

`fieldtrack`関数は、与えられたシンボル（`cursym *LSym`）に関連付けられたすべてのアセンブリ命令（`Prog`）を走査します。その目的は、`AUSEFIELD`という擬似命令を探し出すことです。`AUSEFIELD`命令が見つかった場合、その命令が参照しているシンボル（`p.From.Sym`）に対して、`R_USEFIELD`タイプのリロケーションエントリを追加します。

リロケーションエントリは、`Addrel(ctxt.Cursym)`によって現在のシンボル（`cursym`）に追加されます。このリロケーションは、オフセット（`r.Off`）とサイズ（`r.Siz`）が0に設定され、参照されるシンボル（`r.Sym`）とタイプ（`r.Type = R_USEFIELD`）が指定されます。これにより、リンカは後でこの情報を使用して、どのフィールドが使用されているかを把握できるようになります。

### 変更前: x86バックエンドでの処理

変更前は、`AUSEFIELD`命令の処理ロジックが`src/cmd/internal/obj/x86/asm6.go`内の`asmins`関数に直接記述されていました。`asmins`関数は、x86アーキテクチャの各`Prog`命令をアセンブルする際に呼び出される関数です。

```go
// src/cmd/internal/obj/x86/asm6.go (変更前)
if p.As == obj.AUSEFIELD {
    r := obj.Addrel(ctxt.Cursym)
    r.Off = 0
    r.Siz = 0
    r.Sym = p.From.Sym
    r.Type = obj.R_USEFIELD
    return // AUSEFIELDは実際の命令ではないため、ここで処理を終了
}
```

この実装では、`AUSEFIELD`の処理がx86固有のアセンブラロジックと密接に結合していました。

### 変更後: 汎用パッケージへの移動

このコミットでは、`fieldtrack`関数が`src/cmd/internal/obj/obj.go`に新しく定義され、`AUSEFIELD`の処理ロジックがそこに移されました。

```go
// src/cmd/internal/obj/obj.go (変更後)
func fieldtrack(ctxt *Link, cursym *LSym) {
    p := cursym.Text
    if p == nil || p.Link == nil { // 外部関数やELFセクションシンボルを処理
        return
    }
    ctxt.Cursym = cursym

    for ; p != nil; p = p.Link {
        if p.As == AUSEFIELD {
            r := Addrel(ctxt.Cursym)
            r.Off = 0
            r.Siz = 0
            r.Sym = p.From.Sym
            r.Type = R_USEFIELD
        }
    }
}
```

そして、この新しい`fieldtrack`関数は、`src/cmd/internal/obj/objfile.go`内の`Flushplist`関数から呼び出されるようになりました。`Flushplist`は、アセンブラがシンボルごとのプログラムリスト（`Prog`のリスト）の処理を終え、オブジェクトファイルに書き出す準備をする段階で呼び出される関数です。

```go
// src/cmd/internal/obj/objfile.go (変更後)
func Flushplist(ctxt *Link) {
    // ... 既存の処理 ...
    for _, s := range ctxt.Text {
        // ... 既存の処理 ...
        ctxt.Arch.Follow(ctxt, s)
        ctxt.Arch.Preprocess(ctxt, s)
        ctxt.Arch.Assemble(ctxt, s)
        fieldtrack(ctxt, s) // ここでfieldtrackが呼び出される
        linkpcln(ctxt, s)
    }
    // ... 既存の処理 ...
}
```

この変更により、`fieldtrack`のロジックは特定のアーキテクチャバックエンドから切り離され、アセンブラの共通処理の一部として実行されるようになりました。`ctxt.Arch.Assemble(ctxt, s)`が呼び出された後、つまり各シンボルのアセンブリが完了した後に`fieldtrack`が実行されるため、`AUSEFIELD`命令が適切に処理されることが保証されます。

### なぜこのタイミングで？

`Flushplist`は、各シンボル（関数など）のアセンブリ処理が完了した後に呼び出されるため、そのシンボル内のすべての`Prog`命令が生成され、`AUSEFIELD`擬似命令も含まれている状態です。この段階で`fieldtrack`を実行することで、アセンブリ処理の最終段階でフィールド使用情報を収集し、リロケーションとして記録することができます。これは、アセンブリコード生成とフィールドトラッキングという異なる関心事を分離しつつ、適切なタイミングで連携させるための設計判断と言えます。

## コアとなるコードの解説

### `src/cmd/internal/obj/obj.go` に追加された `fieldtrack` 関数

この関数は、Goアセンブラの共通ユーティリティとして、フィールド使用の追跡ロジックをカプセル化します。

```go
func fieldtrack(ctxt *Link, cursym *LSym) {
    p := cursym.Text
    // cursym.Text は、現在のシンボル (関数など) に関連付けられた最初の命令 (Prog) を指します。
    // このリストを走査して AUSEFIELD 命令を探します。

    if p == nil || p.Link == nil { // handle external functions and ELF section symbols
        // シンボルに命令がない場合 (例: 外部関数宣言、ELFセクションシンボルなど) は処理をスキップします。
        return
    }
    ctxt.Cursym = cursym
    // 現在処理しているシンボルをリンカコンテキストに設定します。
    // これは Addrel 関数がリロケーションをどのシンボルに追加すべきかを知るために必要です。

    for ; p != nil; p = p.Link {
        // シンボルに関連付けられたすべての命令を順に走査します。
        if p.As == AUSEFIELD {
            // AUSEFIELD 擬似命令が見つかった場合、フィールド使用のリロケーションを追加します。
            r := Addrel(ctxt.Cursym)
            // Addrel は、現在のシンボル (ctxt.Cursym) に新しいリロケーションエントリを追加し、そのポインタを返します。
            r.Off = 0
            // オフセットは0に設定されます。AUSEFIELDは実際のコードを生成しないため、特定のオフセットは不要です。
            r.Siz = 0
            // サイズも0に設定されます。
            r.Sym = p.From.Sym
            // リロケーションが参照するシンボルは、AUSEFIELD 命令の From フィールドに格納されているシンボルです。
            // これは通常、使用されている構造体フィールドのシンボルです。
            r.Type = R_USEFIELD
            // リロケーションのタイプを R_USEFIELD に設定します。
            // これにより、リンカはこのリロケーションがフィールド使用情報であることを認識します。
        }
    }
}
```

### `src/cmd/internal/obj/objfile.go` の `Flushplist` 関数における変更

`Flushplist`関数は、アセンブラが各シンボルのプログラムリストを処理し終えた後、オブジェクトファイルに書き出す前に呼び出されます。

```go
func Flushplist(ctxt *Link) {
    // ... 既存の処理 ...
    for _, s := range ctxt.Text {
        // ctxt.Text は、アセンブル対象のすべてのテキストシンボル (関数など) のリストです。
        // 各シンボル s に対して以下の処理を行います。
        ctxt.Arch.Follow(ctxt, s)
        ctxt.Arch.Preprocess(ctxt, s)
        ctxt.Arch.Assemble(ctxt, s)
        // ここで、ターゲットアーキテクチャ固有のアセンブラバックエンドが、
        // シンボル s の Prog リストを実際の機械語命令に変換します。
        // この処理が完了すると、Prog リストには AUSEFIELD などの擬似命令が含まれている可能性があります。

        fieldtrack(ctxt, s) // ここでfieldtrackが呼び出される
        // 各シンボルのアセンブリが完了した後、fieldtrack 関数が呼び出されます。
        // これにより、アセンブルされた Prog リスト内の AUSEFIELD 命令が走査され、
        // 適切な R_USEFIELD リロケーションがシンボル s に追加されます。
        // このタイミングは、フィールド使用情報を収集するのに最適です。
        // なぜなら、すべての命令が処理され、AUSEFIELD が存在していればそれが確定しているからです。

        linkpcln(ctxt, s)
    }
    // ... 既存の処理 ...
}
```

### `src/cmd/internal/obj/x86/asm6.go` からの削除

x86バックエンドの`asmins`関数から`AUSEFIELD`の処理ロジックが削除されました。


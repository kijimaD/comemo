# [インデックス 2407] ファイルの概要

このコミットは、Go言語の初期のツールチェインで使用されていた`8l`リンカに、x86アーキテクチャ向けの16ビット整数乗算命令である`AIMULW`のサポートを追加するものです。これにより、`8l`リンカが`AIMULW`命令を正しく解釈し、対応する機械語に変換できるようになります。

## コミット

```
8l: add AIMULW

R=ken
OCL=29972
CL=29972
```

## 変更の背景

Go言語の初期バージョン（Go 1.5以前）では、コンパイラとリンカはPlan 9オペレーティングシステムのツールチェインをベースにしていました。`8l`は、このツールチェインの一部であるx86（Intel 386）アーキテクチャ向けのリンカです。

アセンブリ言語で書かれたコードを機械語に変換し、実行可能なバイナリを生成するためには、リンカがすべてのアセンブリ命令を認識し、それに対応する正しい機械語バイト列を生成できる必要があります。このコミット以前は、`8l`リンカが`AIMULW`（Add Immediate Multiply Word）命令を適切に処理する機能が欠けていたと考えられます。

`AIMULW`はx86アーキテクチャにおける16ビット整数乗算命令の一種であり、特定の状況下でこの命令を使用するコードを正しくリンクするためには、リンカにそのサポートを組み込む必要がありました。この変更は、`8l`リンカのx86命令セットに対する網羅性を高め、より多様なアセンブリコードのリンクを可能にすることを目的としています。

## 前提知識の解説

### Goの初期ツールチェインとPlan 9

Go言語は、その初期段階において、Rob PikeやKen ThompsonといったPlan 9オペレーティングシステムの開発者によって設計されました。そのため、Goの初期のコンパイラやリンカは、Plan 9のツールチェイン（`8c`コンパイラ、`8l`リンカなど）の設計思想やコードベースを強く継承していました。`8l`はx86アーキテクチャ（32ビット）をターゲットとするリンカであり、アセンブリコードを機械語に変換し、実行ファイルを生成する役割を担っていました。Go 1.5以降、ツールチェインはGo言語自体で完全に書き直され、Plan 9ベースのツールは使われなくなりましたが、このコミットはGoの歴史における重要な一側面を示しています。

### x86アセンブリと`IMUL`命令

x86アーキテクチャには、整数乗算を行うための`IMUL`（Integer MULtiply）命令があります。この命令にはいくつかの形式があり、オペランドのサイズによって異なるサフィックスが使われることがあります。
*   `IMUL`：汎用的な整数乗算。
*   `IMULW`：ワード（Word、16ビット）サイズのオペランドに対する乗算。
*   `IMULL`：ロング（Long、32ビット）サイズのオペランドに対する乗算。
*   `IMULQ`：クアッド（Quad、64ビット）サイズのオペランドに対する乗算（x86-64の場合）。

このコミットで追加された`AIMULW`は、おそらく「Add Immediate Multiply Word」の略で、即値（Immediate）を乗算するワードサイズの命令を指していると考えられます。これは、アセンブラやリンカが内部的に命令を分類・表現するための記号であり、実際のx86命令セットにおける`IMUL`命令の特定の形式に対応します。

### リンカの役割

リンカは、コンパイラによって生成された一つ以上のオブジェクトファイル（機械語コードとデータを含む）を結合し、実行可能なプログラムやライブラリを生成するプログラムです。このプロセスには、シンボルの解決（あるオブジェクトファイルで定義された関数や変数を、別のオブジェクトファイルから参照できるようにする）、再配置（メモリ上の最終的な配置に基づいてアドレスを調整する）、そして最終的な機械語コードの生成が含まれます。リンカは、アセンブリ命令を対応する機械語バイト列に変換する知識を持っている必要があります。

### `ymovtab`と`span.c`

*   **`span.c`**: `src/cmd/8l/span.c`というファイルパスから、これは`8l`リンカのソースコードの一部であることがわかります。リンカの文脈において「span」という言葉は、メモリセグメント、コードブロック、またはアドレス範囲を指すことがあります。このファイルは、リンカがコードやデータをメモリ上に配置する方法、または命令のエンコーディングに関連するロジックを扱っていた可能性があります。
*   **`ymovtab`**: コミットの差分に`ymovtab[]`という配列が登場します。これは「move table」のような意味合いを持つ内部データ構造であると推測されます。リンカやアセンブラでは、アセンブリ命令のニーモニック（例: `AIMULW`）と、それに対応する機械語のオペコードバイト列、オペランドのタイプ、命令の特性などをマッピングするためのテーブルがよく使われます。`ymovtab`は、おそらくこのような命令エンコーディング情報の一部を格納するテーブルであり、`AIMULW`命令の機械語表現をリンカに教えるためにこのテーブルにエントリが追加されたと考えられます。

### `Pq`, `Pe`, `Pm`

これらは、`8l`リンカの内部で定義された定数であり、x86機械語の特定のプレフィックスバイトやオペコードバイトを表すものと推測されます。x86命令セットでは、命令の前に特定のプレフィックスバイト（例: オペランドサイズオーバーライドプレフィックス、セグメントオーバーライドプレフィックスなど）が付加されることがあります。
*   `Pq`：`AIMULW`命令に関連付けられていることから、特定の命令形式やオペランドサイズを示すプレフィックスまたはフラグである可能性があります。
*   `Pe`、`Pm`：`Pq`が検出された際に`Pe`と`Pm`が出力されることから、これらは`AIMULW`命令の機械語エンコーディングに必要な追加のプレフィックスバイトまたはオペコードバイトであると考えられます。

## 技術的詳細

このコミットは、`src/cmd/8l/span.c`ファイル内の2つの主要な箇所を変更しています。

1.  **`ymovtab`への`AIMULW`エントリの追加**:
    `ymovtab`という`uchar`（符号なし文字、つまりバイト）の配列に、`AIMULW`命令の定義が追加されました。
    ```c
    AIMULW, Yml, Yrl, 7, Pq,0xaf,0,0,
    ```
    このエントリは、`AIMULW`命令に関する以下の情報を提供していると解釈できます。
    *   `AIMULW`: 命令の識別子。
    *   `Yml`: 最初のオペランドのタイプ。`Yml`は「Memory or Long」を意味し、メモリまたはレジスタのいずれかであることを示唆します。
    *   `Yrl`: 2番目のオペランドのタイプ。`Yrl`は「Register or Long」を意味し、レジスタであることを示唆します。
    *   `7`: 命令のカテゴリまたはグループ番号。`imul rm,r`命令が`case 7`で処理されていることから、`AIMULW`もこのカテゴリに属することがわかります。
    *   `Pq,0xaf,0,0`: この命令の機械語エンコーディングに関する情報。`Pq`は前述の通り特定のプレフィックスまたはフラグ、`0xaf`は`IMUL`命令のオペコードの一部（特に`IMUL r/m16, reg16`や`IMUL r/m32, reg32`などの形式で使われることが多い）である可能性が高いです。残りの`0,0`は未使用のバイトまたは追加情報がないことを示します。

2.  **`case 7`（`imul rm,r`）処理ロジックの変更**:
    `mfound`関数内の`switch`文の`case 7`ブロックが変更されました。このブロックは、`imul rm,r`形式の命令（レジスタとメモリ/レジスタ間の乗算）を処理します。
    ```c
    case 7: /* imul rm,r */
    -		*andptr++ = t[4];
    +		if(t[4] == Pq) {
    +			*andptr++ = Pe;
    +			*andptr++ = Pm;
    +		} else
    +			*andptr++ = t[4];
    		*andptr++ = t[5];
    		asmand(&p->from, reg[p->to.type]);
    		break;
    ```
    この変更は、`ymovtab`エントリの`t[4]`（つまり`Pq`）が検出された場合に、通常の`t[4]`の代わりに`Pe`と`Pm`という2つのバイトを機械語ストリームに出力するように指示しています。これは、`AIMULW`命令が、その機械語エンコーディングにおいて、`Pq`が示す特定の条件（例えば、16ビットオペランドサイズを示すプレフィックス）を満たす場合に、`Pe`と`Pm`という追加のプレフィックスバイトまたはオペコードバイトを必要とすることを示唆しています。これにより、`AIMULW`命令がx86プロセッサによって正しく解釈される機械語に変換されるようになります。

## コアとなるコードの解説

### `ymovtab`へのエントリ追加

`ymovtab`配列は、リンカがアセンブリ命令を機械語に変換する際に参照するテーブルです。追加された行 `AIMULW, Yml, Yrl, 7, Pq,0xaf,0,0,` は、`AIMULW`という命令がどのようにエンコードされるべきかをリンカに伝えます。
*   `AIMULW`: このエントリが`AIMULW`命令に関するものであることを示します。
*   `Yml`, `Yrl`: オペランドのタイプを定義します。`Yml`はメモリまたはレジスタ、`Yrl`はレジスタを指す内部的な記号です。
*   `7`: この命令が属する命令グループの識別子です。`mfound`関数内の`switch`文の`case 7`がこのグループを処理します。
*   `Pq,0xaf,0,0`: この命令の機械語エンコーディングのパターンです。`Pq`は特定のプレフィックスやフラグを示し、`0xaf`はx86の`IMUL`命令のオペコードの一部（特に2バイトオペコードの2バイト目）である可能性が高いです。

### `case 7`の処理ロジック変更

`mfound`関数は、リンカが命令を処理し、対応する機械語バイト列を生成する中心的な部分です。`case 7`は、`imul rm,r`形式の命令を処理します。
変更前は、`t[4]`（`ymovtab`エントリの5番目の要素、この場合は`Pq`）を直接出力していました。
変更後は、`t[4]`が`Pq`であるかどうかをチェックする`if`文が追加されました。
*   `if(t[4] == Pq)`: もし現在の命令が`AIMULW`であり、その`ymovtab`エントリの`t[4]`が`Pq`である場合、リンカは`Pe`と`Pm`という2つのバイトを機械語ストリームに出力します。これは、`AIMULW`命令が特定のオペランドサイズプレフィックス（`Pe`）と、それに続くオペコードの追加バイト（`Pm`）を必要とすることを示唆しています。
*   `else`: `t[4]`が`Pq`でない場合は、以前と同様に`t[4]`をそのまま出力します。これは、他の`imul rm,r`形式の命令（例えば`AIMULL`）が異なるエンコーディングパターンを持つためです。

この変更により、`8l`リンカは`AIMULW`命令を正しく認識し、x86プロセッサが実行できる適切な機械語バイト列（特定のプレフィックスとオペコードを含む）を生成できるようになりました。

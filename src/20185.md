# [インデックス 20185] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）の重要なデータ構造である `mheap.allspans` に対するデータ競合を修正するものです。この競合は、特にスタックがヒープに移動された後や、並行スタック縮小の導入によって顕在化し、GC中に `fatal error: gc: unswept span` のような致命的なエラーを引き起こす可能性がありました。コミットは、`mheap.allspans` へのアクセスをヒープロックで保護し、GCのマーキングフェーズとスイープフェーズで `allspans` のキャッシュを導入することで、この問題を解決しています。

## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）プロセス中に発生するデータ競合に起因する致命的なエラーを解決するために導入されました。具体的には、`mheap.allspans` という重要なデータ構造への同時アクセスが問題でした。

問題の根本原因は、Goのスタック管理の変更とGCの並行処理にありました。

1.  **スタックがヒープに移動されたこと**: 以前のGoバージョンでは、ゴルーチンのスタックは独立したメモリ領域に割り当てられていましたが、Go 1.3以降、スタックもヒープの一部として管理されるようになりました。これにより、スタックの伸縮や割り当てがヒープの操作と密接に絡み合うようになり、`mheap.allspans` へのアクセス競合のリスクが増大しました。
2.  **並行スタック縮小**: Goランタイムは、ゴルーチンのスタック使用量が減少した場合に、そのスタックを縮小してメモリを解放する機能を持っています。このスタック縮小はGCのマークフェーズ中にも並行して行われることがあり、驚くべきことに、この縮小プロセス自体が新しいスタック領域をヒープから割り当てることで、ヒープを「成長」させる可能性がありました。例えば、多くのゴルーチンが一時的に大きなスタックを使用し、その後GC中に一斉に縮小される場合、大量の小さなスタックがヒープから再割り当てされる必要が生じます。
3.  **`exitsyscall` と STW (Stop-The-World)**: `exitsyscall` は、ゴルーチンがシステムコールからGoランタイムに戻る際に呼び出される関数です。コミットメッセージが指摘するように、この `exitsyscall` は、GCのSTW（Stop-The-World）フェーズ中であっても、ヒープからスタックを割り当てることが可能でした。STWフェーズは、GCがメモリの一貫性を確保するために全てのゴルーチンを一時停止させる期間ですが、この期間中にヒープへの予期せぬ割り当てが発生すると、GCの内部状態、特に `mheap.allspans` の整合性が損なわれる可能性がありました。

これらの要因が複合的に作用し、GCが `mheap.allspans` を参照する際に、そのデータが予期せず変更される（例えば、新しいスパンが追加されたり、既存のスパンが解放されたりする）ことでデータ競合が発生し、結果として `fatal error: gc: unswept span` のような致命的なエラー（GCが整合性のないスパンを検出する）を引き起こしていました。

このコミットは、これらの競合状態を特定し、`mheap.allspans` へのアクセスを適切に同期させることで、ランタイムの安定性とGCの堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

### Goのメモリ管理の基本

*   **ヒープ (Heap)**: プログラム実行中に動的に割り当てられるメモリ領域です。Goでは、`make` や `new` で作成されたオブジェクト、およびゴルーチンのスタック（Go 1.3以降）がヒープに割り当てられます。
*   **スタック (Stack)**: 関数呼び出しやローカル変数のために使用されるメモリ領域です。Goのゴルーチンはそれぞれ独立したスタックを持ち、必要に応じて動的にサイズが伸縮します。
*   **スパン (`mspan`)**: Goのメモリ管理において、ヒープは `mspan` と呼ばれる連続したメモリブロックの単位で管理されます。各 `mspan` は特定のサイズのオブジェクトを格納するために使用されるか、またはゴルーチンのスタックとして使用されます。
*   **`mheap`**: Goランタイムのグローバルなヒープ管理構造体です。全ての `mspan` のリスト (`mheap.allspans`) や、空きスパン、使用中スパンのリストなどを管理します。`mheap.allspans` は、Goランタイムが認識している全てのスパンのポインタを保持する配列（またはスライス）です。

### Goのガベージコレクション (GC)

GoのGCは、並行（concurrent）、三色（tri-color）、マーク＆スイープ（mark-and-sweep）アルゴリズムをベースにしています。

*   **STW (Stop-The-World) フェーズ**: GCプロセスの一部で、全てのゴルーチン（ユーザーコード）の実行が一時的に停止される期間です。この期間は非常に短く保たれるように設計されており、GCがメモリの状態を安全かつ一貫性のある形で操作するために必要です。例えば、スイープの終了処理や、マークフェーズの準備などで行われます。
*   **マークフェーズ (Mark Phase)**: GCが到達可能なオブジェクト（使用中のメモリ）を識別するフェーズです。ルート（グローバル変数、実行中のゴルーチンのスタックなど）から開始し、ポインタをたどって到達可能な全てのオブジェクトに「マーク」を付けます。GoのGCは、このマークフェーズの大部分をユーザーコードと並行して実行します。
*   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不可能なメモリ、つまりガベージ）を解放し、メモリを再利用可能にするフェーズです。このフェーズも大部分が並行して実行されます。

### スタックの動的伸縮

Goのゴルーチンスタックは、必要に応じて自動的に成長・縮小します。
*   **成長**: 関数呼び出しが深くなったり、大きなローカル変数が割り当てられたりしてスタック領域が不足すると、ランタイムはより大きな新しいスタックを割り当て、古いスタックの内容をコピーして切り替えます。
*   **縮小**: スタックの使用量が減少し、割り当てられているスタック領域が過剰になった場合、ランタイムはスタックを縮小して未使用のメモリをヒープに返却します。この縮小は通常、GCサイクル中に行われます。

### `exitsyscall`

Goのゴルーチンがシステムコール（例: ファイルI/O、ネットワーク通信）を実行する際、GoランタイムはゴルーチンをOSのスレッドに切り替えます。システムコールが完了し、ゴルーチンがGoランタイムに戻る際に `exitsyscall` 関数が呼び出されます。この関数は、ゴルーチンがGoの実行コンテキストに安全に戻るための様々な処理（スケジューリング、スタックの調整など）を行います。

### データ競合 (Data Race)

複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に発生します。データ競合は予測不能な動作、プログラムのクラッシュ、データの破損などを引き起こす可能性があり、Goのメモリモデルではデータ競合を含むプログラムの動作は未定義とされています。

## 技術的詳細

このコミットが修正しようとしている技術的な問題は、GoランタイムのGCにおける `mheap.allspans` というグローバルなスパンリストへのアクセス競合です。

1.  **`mheap.allspans` へのロックなしアクセス**:
    `mheap.allspans` は、Goランタイムが管理する全てのメモリブロック（スパン）のポインタを保持する配列です。この配列は、新しいスパンが割り当てられたり、既存のスパンが解放されたりする際に動的にサイズが変更される可能性があります。本来、このような共有データ構造へのアクセスは、データの一貫性を保つためにロック（`mheap.lock`）によって保護されるべきです。しかし、GCの特定のフェーズ、特にマークフェーズやスイープフェーズにおいて、`mheap.allspans` がロックなしで参照されている箇所が複数存在していました。

2.  **`exitsyscall` による STW 中のヒープ割り当て**:
    コミットメッセージが指摘するように、`exitsyscall` は、GCがSTWフェーズに入り、全てのゴルーチンが停止している最中であっても、ヒープから新しいスタックを割り当てることができました。これは、システムコールから戻るゴルーチンが、Goランタイムに戻るために必要なスタック領域を確保する必要があるためです。STW中であっても、ランタイム内部の特定の操作は許可されていますが、このスタック割り当てが `mheap.allspans` の内容を予期せず変更する可能性がありました。

3.  **並行スタック縮小によるマーキング中のヒープ成長**:
    Goのスタックは動的に伸縮しますが、特に並行スタック縮小のプロセスは、GCのマーキングフェーズ中にヒープを成長させる可能性がありました。これは、大きなスタックが縮小される際に、新しい小さなスタックがヒープから割り当てられるためです。もし、多くのゴルーチンが同時にスタックを縮小しようとすると、大量の新しいスパンがヒープに割り当てられ、`mheap.allspans` が頻繁に更新されることになります。

これらのシナリオが組み合わさることで、GCが `mheap.allspans` を走査している最中に、別のゴルーチン（またはランタイムの内部処理）が `mheap.allspans` を変更し、結果としてGCが不正なメモリ状態を読み取ったり、存在しないスパンにアクセスしたりするデータ競合が発生していました。これが `fatal error: gc: unswept span` のようなクラッシュを引き起こす原因となっていました。

**修正アプローチ**:

このコミットは、以下の2つの主要なアプローチでこの問題を解決しています。

1.  **`mheap.allspans` へのアクセス保護**:
    `runtime·updatememstats` のように、`mheap.allspans` を直接走査する箇所では、`runtime·lock(&runtime·mheap.lock)` と `runtime·unlock(&runtime·mheap.lock)` を使用してヒープロックを取得し、排他的アクセスを保証するように変更されました。これにより、`mheap.allspans` の内容が変更される可能性のある他の操作との競合を防ぎます。

2.  **GCマーキングフェーズのための `allspans` キャッシュの導入**:
    GCのマークフェーズとスイープフェーズは、`mheap.allspans` の内容を繰り返し走査する必要があります。これらのフェーズの開始時に `mheap.allspans` のスナップショットをキャッシュすることで、走査中に `mheap.allspans` が変更されても影響を受けないようにします。
    *   以前はスイープフェーズのために `mheap.sweepspans` というキャッシュが存在しましたが、このコミットでは `MSpan **gcspans` という新しいフィールドを `MHeap` 構造体に導入し、GCのマーカーとスイーパーの両方でこのキャッシュを使用するように統一しました。
    *   `gc` 関数（GCのメインエントリポイント）の開始時に、`runtime·mheap.allspans` の現在の状態を `work.spans` (GCワーカーが使用するローカルキャッシュ) にコピーし、`work.nspan` でそのサイズを記録します。このコピー操作は `mheap.lock` で保護されます。
    *   GCのマークフェーズ (`markroot` 関数など) やスイープフェーズ (`runtime·sweepone` 関数など) では、`mheap.allspans` を直接参照する代わりに、このキャッシュされた `work.spans` を使用するように変更されました。これにより、GCの実行中に `mheap.allspans` が動的に変更されても、GCは一貫性のあるスナップショットに対して動作し続けることができます。

この修正により、GCの並行性とランタイムの安定性を維持しつつ、`mheap.allspans` へのアクセス競合が効果的に排除されました。

## コアとなるコードの解説

これらのコード変更は、`mheap.allspans` へのデータ競合を根本的に解決し、GoランタイムのGCの堅牢性を大幅に向上させます。

1.  **`MSpan **gcspans` への名称変更と役割の明確化**:
    `malloc.h` で `sweepspans` が `gcspans` に変更されたことは、このキャッシュが単にスイープのためだけでなく、GCのマーキングフェーズでも使用されることを明確に示しています。これにより、GCの異なるフェーズ間で `allspans` の一貫したスナップショットが共有されるようになります。

2.  **`work` 構造体内の `spans` と `nspan`**:
    `mgc0.c` の `work` 構造体に `spans` と `nspan` が追加されたことで、GCの各ワーカーが `mheap.allspans` の独自の（しかし共有された）スナップショットを持つことができるようになりました。これにより、GCの実行中に `mheap.allspans` が動的に変更されても、GCワーカーは安定したデータに対して処理を続行できます。

3.  **`markroot` および `runtime·sweepone` でのキャッシュ利用**:
    `markroot` 関数（GCのマークフェーズの一部）と `runtime·sweepone` 関数（GCのスイープフェーズの一部）が、`mheap.allspans` を直接参照する代わりに `work.spans` を使用するように変更されたことは非常に重要です。これにより、これらのGCのコア処理が、`mheap.allspans` の動的な変更（例えば、`exitsyscall` や並行スタック縮小による新しいスパンの割り当て）から隔離されます。GCは、そのサイクルが開始された時点のメモリレイアウトのスナップショットに基づいて安全に動作できます。

4.  **`runtime·updatememstats` でのロック導入**:
    `runtime·updatememstats` 関数は、メモリ統計を更新するために `mheap.allspans` を走査します。この走査中に `mheap.allspans` が変更されると、統計の不正確さやクラッシュにつながる可能性があります。`runtime·lock(&runtime·mheap.lock)` と `runtime·unlock(&runtime·mheap.lock)` の導入により、この操作が排他的に行われることが保証され、データ競合が排除されます。これは、`mheap.allspans` の整合性を維持するための直接的な同期メカニズムです。

5.  **`gc` 関数での `allspans` キャッシュの管理**:
    `gc` 関数における `mheap.allspans` のキャッシュロジックは、このコミットの核心部分です。
    *   GCサイクルの開始時に `mheap.lock` を取得し、`mheap.allspans` の現在のポインタを `runtime·mheap.gcspans` と `work.spans` にコピーします。これにより、GCがこのサイクルで使用する `allspans` のスナップショットが作成されます。
    *   古いキャッシュが `mheap.allspans` と異なる場合は解放するロジックも含まれており、メモリリークを防ぎます。
    *   このキャッシュ操作全体が `mheap.lock` で保護されているため、キャッシュの作成中に `mheap.allspans` が変更されることはありません。
    *   このキャッシュ戦略により、GCの大部分の処理はロックなしで `allspans` にアクセスできるようになり、GCの並行性を維持しつつ、データの一貫性を保証します。

6.  **`RecordSpan` でのキャッシュ参照の更新**:
    `mheap.c` の `RecordSpan` 関数は、新しいスパンが追加されて `mheap.allspans` の基盤となる配列が再割り当てされる際に呼び出されます。ここで、古い `allspans` 配列を解放する際に `runtime·mheap.sweepspans` ではなく `runtime·mheap.gcspans` を参照するように変更されたことは、GCが現在使用しているキャッシュが誤って解放されるのを防ぐために重要です。これにより、GCがまだ古い `allspans` 配列のコピーを使用している間に、その配列が解放されてしまうというユースアフターフリー（use-after-free）のシナリオが回避されます。

これらの変更は、Goランタイムのメモリ管理とGCの複雑な相互作用を考慮し、並行処理の安全性とパフォーマンスのバランスを取りながら、以前のデータ競合によって引き起こされていたクラッシュを解決しています。

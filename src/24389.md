# [インデックス 24389] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるマークフェーズの完了検出ロジックに関するバグ修正です。具体的には、GCのマークフェーズにおいて、フラクショナルワーカー（fractional worker）およびアイドルワーカー（idle worker）がGC作業の完了を誤って報告する可能性のある競合状態（race condition）を解消します。これにより、GCの正確性と堅牢性が向上します。

## コミット

```
commit cf225a1748a9efe401edd3cf8879692391a31d8b
Author: Austin Clements <austin@google.com>
Date:   Fri Jul 24 16:38:19 2015 -0400

    runtime: fix mark 2 completion in fractional/idle workers
    
    Currently fractional and idle mark workers dispose of their gcWork
    cache during mark 2 after incrementing work.nwait and after checking
    whether there are any workers or any work available. This creates a
    window for two races:
    
    1) If the only remaining work is in this worker's gcWork cache, it
       will see that there are no more workers and no more work on the
       global lists (since it has not yet flushed its own cache) and
       prematurely signal mark 2 completion.
    
    2) After this worker has incremented work.nwait but before it has
       flushed its cache, another worker may observe that there are no
       more workers and no more work and prematurely signal mark 2
       completion.
    
    We can fix both of these by simply moving the cache flush above the
    increment of nwait and the test of the completion condition.
    
    This is probably contributing to #11694, though this alone is not
    enough to fix it.
```

## 元コミット内容

Goランタイムにおいて、フラクショナルGCワーカーとアイドルGCワーカーがマークフェーズ2の完了を処理する方法に存在する競合状態を修正します。これらのワーカーは、`work.nwait`をインクリメントし、他のワーカーやグローバルな作業キューに作業が残っているかを確認した後に、自身の`gcWork`キャッシュを破棄していました。この順序が原因で、以下の2つの競合状態が発生する可能性がありました。

1.  **自己キャッシュ内の作業による誤検出**: もし残りのGC作業がこのワーカーの`gcWork`キャッシュ内にのみ存在する場合、ワーカーは自身のキャッシュをフラッシュする前にグローバルな作業リストに作業がないと判断し、他のワーカーもいないと認識して、マークフェーズ2の完了を時期尚早にシグナルしてしまう。
2.  **他ワーカーによる誤検出**: このワーカーが`work.nwait`をインクリメントした後、かつ自身のキャッシュをフラッシュする前に、別のワーカーがグローバルな作業リストに作業がなく、他のワーカーもいないと判断し、マークフェーズ2の完了を時期尚早にシグナルしてしまう。

この修正は、`gcWork`キャッシュのフラッシュ処理を、`work.nwait`のインクリメントおよび完了条件のチェックよりも前に行うことで、これらの競合状態を解消します。この変更は、Issue #11694に寄与している可能性がありましたが、単独では完全に解決するものではないとされています。

## 変更の背景

Goのガベージコレクションは、並行性（concurrency）と低レイテンシ（low latency）を重視して設計されています。GCのマークフェーズでは、到達可能なオブジェクトを特定するために、複数のGCワーカーが並行してヒープをスキャンします。これらのワーカーは、`gcWork`というローカルキャッシュを使用して、スキャンすべきポインタを一時的に保持します。

GCのマークフェーズの完了を正確に検出することは非常に重要です。もしGCが時期尚早に完了を宣言してしまうと、まだ到達可能であるにもかかわらずスキャンされていないオブジェクトが存在する可能性があり、それらが誤って解放されてしまう（Use-After-Freeなどの）深刻なバグやメモリ破損につながる恐れがあります。

このコミットの背景には、フラクショナルワーカーとアイドルワーカーという特定の種類のGCワーカーが、GC作業の完了を検出するロジックに潜在的な欠陥を抱えていたことがあります。これらのワーカーは、システムのリソースを効率的に利用するために、通常のGCワーカーとは異なる振る舞いをすることがあります。特に、GC作業が少なくなってきた終盤において、自身のローカルキャッシュに作業が残っているにもかかわらず、グローバルな作業キューが空であることや、他のワーカーが待機状態にあることを誤って解釈し、GCの完了を早まって報告してしまうという問題がありました。

コミットメッセージで言及されているIssue #11694は、GoのGCにおけるメモリリークやGCの誤動作に関連する問題であり、このコミットはその問題の一因となっていた可能性のある競合状態を解消することを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにした並行（concurrent）かつ非同期（asynchronous）なコレクタです。主なフェーズは以下の通りです。

1.  **マークフェーズ (Mark Phase)**:
    *   GCルート（スタック、グローバル変数など）から到達可能なすべてのオブジェクトを特定し、「マーク」します。
    *   このフェーズは、アプリケーションの実行と並行して行われます（concurrent mark）。
    *   **マークワーカー**: ヒープをスキャンし、到達可能なオブジェクトをマークするゴルーチンです。
        *   **通常のマークワーカー**: GCがアクティブな期間に動作します。
        *   **フラクショナルワーカー (Fractional Worker)**: アプリケーションの実行中に、CPU時間の一部をGCに割り当てるワーカーです。アプリケーションのレイテンシへの影響を最小限に抑えつつ、GC作業を進めます。
        *   **アイドルワーカー (Idle Worker)**: システムがアイドル状態のときにGC作業を行うワーカーです。システムリソースの有効活用を目的とします。
    *   **`gcWork`キャッシュ**: 各マークワーカーは、スキャンすべきポインタを一時的に保持するためのローカルなキュー（キャッシュ）を持っています。これにより、グローバルな作業キューへのアクセス競合を減らし、並行性を高めます。

2.  **マーク終了フェーズ (Mark Termination Phase)**:
    *   すべてのマークワーカーが作業を完了し、ヒープ全体のスキャンが終了したことを確認します。
    *   このフェーズは「ストップ・ザ・ワールド（STW）」を伴うことがありますが、Go 1.5以降はSTW時間を最小限に抑える工夫がされています。

3.  **スイープフェーズ (Sweep Phase)**:
    *   マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放し、再利用可能にします。
    *   このフェーズもアプリケーションの実行と並行して行われます（concurrent sweep）。

### 競合状態 (Race Condition)

複数の並行プロセスやスレッドが共有リソースにアクセスする際に、そのアクセス順序によって結果が非決定的に変わってしまう状態を指します。GCの完了検出のような共有状態（`work.nwait`、グローバル作業キュー）に依存するロジックでは、競合状態が発生しやすいです。

### `work.nwait`とGC完了検出

*   `work.nwait`: GCワーカーが作業を待機している（または完了した）状態を示すカウンターです。各ワーカーが作業を終えるか、作業がないと判断するとこのカウンターをインクリメントします。
*   GCのマークフェーズの完了は、通常、すべてのワーカーが作業を終え、かつグローバルな作業キューが空になったときに検出されます。`work.nwait`が`work.nproc`（総ワーカー数）と等しくなり、かつ`work.full`と`work.partial`（グローバル作業キュー）が両方とも0になった場合に、GCが完了したと判断されます。

### `p.gcw.dispose()`

`gcWork`キャッシュを破棄する（またはグローバルな作業キューにフラッシュする）操作です。ローカルキャッシュに残っている作業をグローバルに公開し、他のワーカーがそれを見つけて処理できるようにするために重要です。

## 技術的詳細

このコミットの核心は、`src/runtime/mgc.go`内の`gcBgMarkWorker`関数における`p.gcw.dispose()`の呼び出し位置の変更です。

`gcBgMarkWorker`関数は、バックグラウンドでGCのマーク作業を行うワーカーのメインループです。この関数内で、ワーカーは自身のモード（通常のマークワーカー、フラクショナルワーカー、アイドルワーカー）に応じてGC作業を実行します。

変更前のコードでは、`gcMarkWorkerFractionalMode`または`gcMarkWorkerIdleMode`の場合、ワーカーは`gcDrainUntilPreempt`を呼び出してGC作業を処理した後、以下の順序で処理を進めていました。

1.  `work.nwait`をインクリメントする (`incnwait := xadd(&work.nwait, +1)`)。
2.  GC完了条件をチェックする (`done = incnwait == work.nproc && work.full == 0 && work.partial == 0`)。
3.  `gcBlackenPromptly`が真の場合に`p.gcw.dispose()`を呼び出す。

この順序が問題でした。

*   **問題点1**: `p.gcw.dispose()`が`work.nwait`のインクリメントと完了条件のチェックの**後**に実行されるため、ワーカー自身の`gcWork`キャッシュにまだスキャンすべきポインタが残っているにもかかわらず、グローバルな作業キューが空であると判断し、かつ自身が`nwait`をインクリメントしたことで、GCが完了したと誤って判断してしまう可能性がありました。
*   **問題点2**: 別のワーカーが、このワーカーが`work.nwait`をインクリメントした後、かつ`p.gcw.dispose()`を呼び出す前に、GC完了条件をチェックした場合、グローバルな作業キューが空であり、かつ`nwait`が`nproc`に達していると判断し、時期尚早にGC完了をシグナルしてしまう可能性がありました。

### 修正内容

コミットは、`p.gcw.dispose()`の呼び出しを、`work.nwait`のインクリメントとGC完了条件のチェックの**前**に移動させました。

```go
// 変更前 (簡略化)
case gcMarkWorkerFractionalMode, gcMarkWorkerIdleMode:
    gcDrainUntilPreempt(&p.gcw, gcBgCreditSlack)
    incnwait := xadd(&work.nwait, +1)
    // ... 完了条件チェック ...
    if gcBlackenPromptly {
        p.gcw.dispose() // ここにあった
    }

// 変更後 (簡略化)
case gcMarkWorkerFractionalMode, gcMarkWorkerIdleMode:
    gcDrainUntilPreempt(&p.gcw, gcBgCreditSlack)
    // キャッシュのフラッシュを先に実行
    if gcBlackenPromptly {
        p.gcw.dispose() // ここに移動
    }
    incnwait := xadd(&work.nwait, +1)
    // ... 完了条件チェック ...
```

この変更により、ワーカーがGC完了条件をチェックする前に、自身のローカルキャッシュに残っているすべての作業がグローバルな作業キューにフラッシュされることが保証されます。これにより、GC完了の判断がより正確になり、上記の競合状態が解消されます。

また、`if !p.gcw.empty() { throw("gcDrain returned with buffer") }`というアサーションが追加されています。これは、`gcDrain`が呼び出された後には`gcWork`キャッシュが空になっているべきであるという前提を検証するためのもので、デバッグや将来的なバグの早期発見に役立ちます。

## コアとなるコードの解説

変更の中心は、`gcBgMarkWorker`関数内の`gcMarkWorkerFractionalMode`および`gcMarkWorkerIdleMode`の`case`ブロックです。

1.  **`if !p.gcw.empty() { throw("gcDrain returned with buffer") }` の追加**:
    *   これは、`gcDrain`（または`gcDrainUntilPreempt`）が呼び出された後、ワーカーのローカル`gcWork`キャッシュ（`p.gcw`）が空になっていることを保証するためのアサーションです。もし空でなければ、それは予期せぬ状態であり、ランタイムエラー（`throw`）を引き起こします。これは、GC作業が正しく処理されていることを確認するための防御的なプログラミングです。

2.  **`p.gcw.dispose()` の移動**:
    *   以前は`incnwait`のインクリメントと`done`の計算の後にあった`p.gcw.dispose()`の呼び出しが、`gcDrainUntilPreempt`の直後、かつ`incnwait`のインクリメントの前に移動されました。
    *   新しいコメントで説明されているように、この移動は非常に重要です。
        *   「If we are nearing the end of mark, dispose of the cache promptly.」: マークフェーズの終わりに近づいている場合、キャッシュを速やかに破棄します。
        *   「We must do this before signaling that we're no longer working so that other workers can't observe no workers and no work while we have this cached, and before we compute done.」: 他のワーカーが、このワーカーがキャッシュを持っている間に「ワーカーも作業もない」と誤って判断しないように、また`done`（完了）を計算する前に、この処理を行う必要があります。

この変更により、ワーカーが自身の作業を完了し、グローバルなGC完了条件を評価する前に、ローカルキャッシュ内のすべての作業がグローバルな作業キューにフラッシュされることが保証されます。これにより、GCの完了検出における競合状態が解消され、GCの正確性が向上します。

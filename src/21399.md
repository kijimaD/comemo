# [インデックス 21399] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）におけるデバッグ出力のフォーマットに関するバグ修正です。具体的には、`-s` フラグ（最適化の抑制）が有効な場合に、冗長な型情報が出力される際のファイル名表示が意図しない形式になる問題を修正しています。ファイル名が既に絶対パスであるにもかかわらず、`%lL` というフォーマット指定子が現在のディレクトリをファイル名の前に付加してしまい、出力が重複してしまっていた点を、適切な `%L` に変更することで修正しています。

## 元コミット内容

このコミットは、Goコンパイラの `cmd/gc` において、`-s` フラグ（最適化の抑制）使用時のファイル名出力フォーマット指定子を修正するものです。

問題は、`%lL` というフォーマット指定子がファイル名の前に現在の作業ディレクトリを付加してしまうことにありました。しかし、このコンテキストではファイル名が既に絶対パスであったため、現在の作業ディレクトリが重複して付加されるのは意図しない挙動でした。

この修正は、Issue #9150 を解決します。

## 変更の背景

この変更の背景には、Goコンパイラ `gc` のデバッグ出力の正確性に関する問題がありました。Goコンパイラには、コンパイル時の挙動を詳細に確認するための様々なデバッグフラグが用意されています。その一つに `-s` フラグがあります。これは、コンパイラの最適化処理を抑制し、より詳細な中間コードや型情報を出力させるために使用されることがあります。

`src/cmd/gc/typecheck.c` は、Goコンパイラの型チェックフェーズを司るC言語のソースファイルです。このファイル内で、`debug['s']` フラグが有効な場合に、冗長な型定義が検出された際に警告メッセージを出力するロジックが存在しました。この警告メッセージのフォーマットには、ファイル名と行番号を含めるために `print` 関数が使用されていました。

問題は、この `print` 関数内でファイル名を出力するために `%lL` というフォーマット指定子が使われていた点にありました。`%lL` は、ファイル名に行番号を付加するだけでなく、ファイル名が相対パスの場合に現在の作業ディレクトリをその前に付加するという挙動を持っていました。しかし、この特定のコンテキストでは、`n->lineno` から取得されるファイル名情報が既に絶対パスとして提供されていたため、`%lL` を使用すると「現在の作業ディレクトリ/絶対パス/ファイル名:行番号」のような冗長な出力になってしまっていました。これはデバッグ出力として混乱を招くものであり、正確な情報提供の妨げとなっていました。

この問題を解決するために、ファイル名が既に絶対パスであることを考慮し、単にファイル名と行番号を出力する `%L` フォーマット指定子に変更する必要がありました。

## 前提知識の解説

### Goコンパイラ `gc` について

Go言語の公式コンパイラは `gc` と呼ばれます。これはGo言語のツールチェインの一部であり、Goのソースコードを機械語に変換する役割を担っています。`gc` は、Go言語の設計思想に合わせて、高速なコンパイルと効率的な実行ファイルを生成することを目指しています。

### `cmd/gc` の役割

`cmd/gc` は、Go言語のソースコードをコンパイルする際の主要なコンポーネントです。Goのソースコードは、まず抽象構文木（AST）にパースされ、その後、型チェック、最適化、コード生成といった複数のフェーズを経て最終的なバイナリが生成されます。`src/cmd/gc` ディレクトリには、これらのコンパイルフェーズを実装するC言語（および一部Go言語）のソースコードが含まれています。

### `debug['s']` フラグ（`go build -gcflags=-s`）の役割と出力内容

Goコンパイラ `gc` には、コンパイル時の挙動を制御するための様々なフラグがあります。その中でも `-gcflags` は、`gc` 固有のフラグを渡すために使用されます。

`-gcflags=-s` は、`gc` コンパイラに対して「最適化を抑制する」という指示を与えます。通常、コンパイラは生成されるバイナリのサイズを小さくしたり、実行速度を向上させたりするために様々な最適化を行います。しかし、デバッグやコンパイラの内部挙動の調査を行う際には、これらの最適化が邪魔になることがあります。`-s` フラグを有効にすることで、コンパイラは最適化を控え、より「素直な」コードを生成したり、デバッグに役立つ追加情報を出力したりするようになります。

このコミットの文脈では、`debug['s']` はコンパイラの内部で `-s` フラグが有効になっているかどうかを示す内部変数（またはマップのエントリ）を指します。このフラグが有効な場合、`typecheck.c` 内の特定のデバッグ出力がアクティブになります。具体的には、冗長な型定義が検出された際に、その情報が標準エラー出力（またはコンパイラのログ）に出力されるようになります。

### `print` 関数のフォーマット指定子（特に `%L` と `%lL` の違い）

Goコンパイラの内部では、デバッグやエラー報告のために独自の `print` 関数が使用されています。これはC言語の `printf` に似た機能を提供しますが、Goコンパイラ特有のフォーマット指定子を持っています。

*   **`%L`**: このフォーマット指定子は、ファイル名と行番号を `filename:lineno` の形式で出力するために使用されます。例えば、`/path/to/file.go:123` のようになります。これは、ソースコード上の特定の場所を正確に指し示すための標準的な形式です。

*   **`%lL`**: このフォーマット指定子もファイル名と行番号を出力しますが、追加の挙動があります。ファイル名が相対パスである場合、`%lL` はそのファイル名の前に現在の作業ディレクトリを付加します。例えば、現在の作業ディレクトリが `/home/user/project` で、ファイル名が `src/main.go` の場合、`%lL` は `/home/user/project/src/main.go:lineno` のように出力します。しかし、ファイル名が既に `/absolute/path/to/file.go` のような絶対パスである場合でも、`%lL` は現在の作業ディレクトリを無条件に付加しようとします。これが今回の問題の原因でした。つまり、`/home/user/project//absolute/path/to/file.go:lineno` のような、パスが重複した不正確な出力が生成されてしまっていたのです。

このコミットは、この `%lL` の意図しない挙動を修正し、ファイル名が既に絶対パスである場合には単に `%L` を使用して、冗長なパスの付加を防ぐことを目的としています。

## 技術的詳細

このコミットは、Goコンパイラの型チェックフェーズにおけるデバッグ出力の微細なバグを修正しています。問題の核心は、`src/cmd/gc/typecheck.c` 内の `pushtype` 関数にありました。

`pushtype` 関数は、Go言語の型システムにおいて、あるノード（ASTの一部）に型を割り当てる役割を担っています。この関数内には、コンパイラのデバッグフラグ `debug['s']` が有効な場合に実行される条件分岐があります。

```c
    else if(debug['s']) {
        typecheck(&n->right, Etype);
        if(n->right->type != T && eqtype(n->right->type, t))
            print("%lL: redundant type: %T\\n", n->lineno, t);
    }
```

このコードスニペットは、`debug['s']` が真（つまり、`go build -gcflags=-s` が指定されている）であり、かつ `n->right` の型が `T` ではないが、割り当てようとしている型 `t` と等しい場合に実行されます。これは、コード内で冗長な型指定が行われている可能性を示唆しており、デバッグ情報として出力されるべきものです。

問題は、この `print` 関数呼び出しで使用されているフォーマット指定子 `%lL` にありました。前述の通り、`%lL` はファイル名が相対パスの場合に現在の作業ディレクトリを付加する挙動を持ちます。しかし、`n->lineno` から取得されるファイル名情報は、コンパイラの内部処理において既に絶対パスとして扱われていました。

例えば、ソースファイルが `/home/user/project/src/main.go` であり、現在の作業ディレクトリが `/home/user/project` であるとします。
もし `n->lineno` が `/home/user/project/src/main.go:10` のような情報を持っていた場合、`%lL` はこれをさらに処理しようとします。結果として、`print` 関数は `/home/user/project//home/user/project/src/main.go:10: redundant type: ...` のような、パスが二重になった不正確な出力を生成してしまっていました。これは、デバッグ情報の可読性を著しく損なうものでした。

このコミットは、この問題を解決するために、`%lL` を `%L` に変更しました。`%L` は、ファイル名が絶対パスであるか相対パスであるかに関わらず、単に `filename:lineno` の形式で出力します。これにより、ファイル名が既に絶対パスである場合には、余計なパスの付加が行われなくなり、正確で簡潔なデバッグ出力が得られるようになります。

この修正は、コンパイラの出力の正確性を向上させ、開発者やデバッガーがGoコードの問題を特定する際の助けとなります。

        typecheck(&n->right, Etype);
        if(n->right->type != T && eqtype(n->right->type, t))
            print("%lL: redundant type: %T\\n", n->lineno, t);
    }
```

このコードスニペットは、`debug['s']` が真（つまり、`go build -gcflags=-s` が指定されている）であり、かつ `n->right` の型が `T` ではないが、割り当てようとしている型 `t` と等しい場合に実行されます。これは、コード内で冗長な型指定が行われている可能性を示唆しており、デバッグ情報として出力されるべきものです。

問題は、この `print` 関数呼び出しで使用されているフォーマット指定子 `%lL` にありました。前述の通り、`%lL` はファイル名が相対パスの場合に現在の作業ディレクトリを付加します。しかし、このコンテキストでは `n->lineno` から取得されるファイル名情報は、コンパイラの内部処理において既に絶対パスとして扱われていました。

例えば、ソースファイルが `/home/user/project/src/main.go` であり、現在の作業ディレクトリが `/home/user/project` であるとします。
もし `n->lineno` が `/home/user/project/src/main.go:10` のような情報を持っていた場合、`%lL` はこれをさらに処理しようとします。結果として、`print` 関数は `/home/user/project//home/user/project/src/main.go:10: redundant type: ...` のような、パスが二重になった不正確な出力を生成してしまっていました。これは、デバッグ情報の可読性を著しく損なうものでした。

このコミットは、この問題を解決するために、`%lL` を `%L` に変更しました。`%L` は、ファイル名が絶対パスであるか相対パスであるかに関わらず、単に `filename:lineno` の形式で出力します。これにより、ファイル名が既に絶対パスである場合には、余計なパスの付加が行われなくなり、正確で簡潔なデバッグ出力が得られるようになります。

この修正は、コンパイラの出力の正確性を向上させ、開発者やデバッガーがGoコードの問題を特定する際の助けとなります。

## コアとなるコードの解説

変更は `src/cmd/gc/typecheck.c` ファイルの `pushtype` 関数内の一行のみです。

元のコード:
```c
print("%lL: redundant type: %T\\n", n->lineno, t);
```
修正後のコード:
```c
print("%L: redundant type: %T\\n", n->lineno, t);
```

この変更は、`print` 関数に渡されるフォーマット文字列内のファイル名/行番号のフォーマット指定子を `%lL` から `%L` に変更しています。

*   **`%lL` (変更前)**: この指定子は、ファイル名が相対パスの場合に現在の作業ディレクトリを付加します。しかし、このコンテキストでは `n->lineno` が既に絶対パス情報を含んでいたため、パスが重複して出力される問題が発生していました。
*   **`%L` (変更後)**: この指定子は、ファイル名と行番号を `filename:lineno` の形式で出力します。ファイル名が既に絶対パスであれば、そのまま絶対パスが出力され、余計なパスの付加は行われません。

この修正により、`go build -gcflags=-s` を使用した際に、冗長な型定義に関するデバッグメッセージが、正確なファイルパスと行番号で出力されるようになります。これにより、コンパイラのデバッグ出力の品質と可読性が向上します。

# [インデックス 25131] ファイルの概要

このコミットは、Go言語のビルドツールである `cmd/dist` における重要な改善を導入しています。主な目的は、パッケージのビルドプロセスを並列化し、コードベースをよりGoらしい慣用的なスタイルに近づけることです。これにより、Goツールチェイン全体のビルド時間が短縮され、保守性が向上します。

## 元コミット内容

`cmd/dist: build packages in parallel, make code more Go-like`

このコミットは、`cmd/dist` ツールがパッケージを並列でビルドするように変更し、同時にコードをよりGo言語の慣用的なスタイルに近づけることを目的としています。元のRuss CoxによるバージョンにBrad Fitzpatrickが修正を加えたものです。

## 変更の背景

Go言語のビルドプロセス、特にツールチェイン自体のブートストラップビルドは、多くのパッケージのコンパイルとリンクを伴います。以前のバージョンでは、これらのパッケージは主に逐次的にビルドされており、特に多数の依存関係を持つ大規模なプロジェクトや、マルチコアCPUを搭載したマシンでは、ビルド時間がボトルネックとなる可能性がありました。

このコミットの背景には、以下の課題と目標がありました。

1.  **ビルド時間の短縮**: Goツールチェインのビルドは、開発者にとって頻繁に行われる操作であり、その時間を短縮することは開発効率の向上に直結します。並列ビルドは、この目標を達成するための最も効果的な手段の一つです。
2.  **依存関係の効率的な管理**: 以前は、パッケージのビルド順序が `buildorder` というハードコードされたスライスで手動で管理されていました。これは、依存関係が複雑になるにつれて保守が困難になり、エラーの原因となる可能性がありました。自動化された依存関係解決と管理の必要性がありました。
3.  **Goらしいコードへの移行**: `cmd/dist` はGoツールチェインの初期段階から存在し、一部のコードはGo言語の進化とともに古くなっていた可能性があります。`sync.WaitGroup` や `chan` といったGoの並行処理プリミティブをより効果的に活用することで、コードの可読性、保守性、そしてGo言語の哲学への適合性を高めることが目指されました。
4.  **ブートストラッププロセスの改善**: GoコンパイラはGo自身で書かれているため、新しいバージョンのGoをビルドするには、既存のGoコンパイラ（ブートストラップコンパイラ）を使用します。このブートストラッププロセス自体を高速化し、より堅牢にすることは、Go言語全体の開発サイクルにとって重要です。

この変更は、Goのビルドシステムが元々持っていた並列処理の能力（例えば `go build -p n` フラグ）を `cmd/dist` のブートストラッププロセスにも適用し、より洗練された形で実現しようとするものです。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

### 1. Go言語のブートストラップ (Bootstrapping)

GoコンパイラはGo言語自体で書かれています。これは「自己ホスティング (self-hosting)」と呼ばれます。新しいバージョンのGoコンパイラをビルドする際には、通常、以前の安定版のGoコンパイラ（ブートストラップコンパイラ）を使用して新しいコンパイラをコンパイルします。このプロセス全体をブートストラップと呼びます。

*   **初期のブートストラップ**: Go言語の非常に初期の段階では、C言語で書かれた小さなコンパイラが最初のGoコンパイラをビルドするために使用されました。
*   **現在のブートストラップ**: 現在では、Go 1.4などの安定版Goコンパイラが、Go 1.5以降のGoコンパイラをビルドするために使用されます。これにより、Go言語の開発者はGo言語を使ってGo言語を開発できるというメリットがあります。

### 2. `cmd/dist` ツール

`cmd/dist` はGo言語のソースコードリポジトリに含まれる内部ツールであり、Goツールチェイン全体のビルド、テスト、インストールを管理します。開発者が `all.bash` (Unix系) や `all.bat` (Windows) を実行すると、内部的に `cmd/dist` が呼び出され、Goのコンパイラ、リンカ、標準ライブラリ、その他のツールがビルドされます。

### 3. Goの並行処理プリミティブ

Go言語は、並行処理を容易にするための強力なプリミティブを提供します。

*   **Goroutine**: 軽量なスレッドのようなもので、Goランタイムによって管理されます。数千、数万のGoroutineを同時に実行することが可能です。
*   **Channel**: Goroutine間でデータを安全にやり取りするための通信メカニズムです。チャネルは、Goroutine間の同期にも使用できます。
*   **`sync.WaitGroup`**: 複数のGoroutineの完了を待つためのメカニズムです。カウンタをインクリメント (`Add`) し、各Goroutineが完了時にデクリメント (`Done`) し、`Wait` メソッドでカウンタがゼロになるまでブロックします。
*   **`sync.Once`**: 特定のコードブロックが一度だけ実行されることを保証するためのメカニズムです。

### 4. パッケージの依存関係

Goのパッケージは、他のパッケージに依存することがよくあります。例えば、`net/http` パッケージは `net` パッケージや `io` パッケージに依存します。パッケージをビルドする際には、その依存関係にあるパッケージが先にビルドされている必要があります。

## 技術的詳細

このコミットの核心は、Goツールチェインのビルドプロセスにおけるパッケージの依存関係解決と並列ビルドの導入です。

### 1. 依存関係の自動生成と管理

*   **`mkdeps.bash` の導入**: 以前は手動で管理されていた `buildorder` スライスに代わり、`src/cmd/dist/mkdeps.bash` という新しいシェルスクリプトが導入されました。このスクリプトは、`go list` コマンドを使用してGoパッケージの依存関係を動的に抽出し、`src/cmd/dist/deps.go` ファイルに `builddeps` マップとして出力します。
    *   `go list -tags cmd_go_bootstrap -f '{{printf "%q" .ImportPath}}: { {{range .Deps}}{{if not (eq . "unsafe")}}{{printf "%q" .}}, {{end}}{{end}} },'` というコマンドが使用されており、これは指定されたパッケージとその依存関係をJSONのような形式で出力します。`cmd_go_bootstrap` タグは、ブートストラップビルドに必要なパッケージのみを対象とするために使用されます。
    *   `deps.go` は、`map[string][]string` 型の `builddeps` 変数を定義し、各パッケージのインポートパスをキーとして、そのパッケージが直接依存するパッケージのリストを値として保持します。これにより、依存関係の管理が自動化され、手動でのエラーが減少します。

### 2. 並列ビルドのメカニズム

*   **`installed` マップとチャネル**: `build.go` に `var installed = make(map[string]chan struct{})` が導入されました。これは、各パッケージのビルドが完了したことを通知するためのチャネルのマップです。
    *   `install(dir string)` 関数が呼び出される際、まず `installed[dir]` に対応するチャネルが存在するかを確認し、存在すれば `defer close(ch)` で関数終了時にチャネルを閉じます。
    *   次に、`for _, dep := range builddeps[dir] { <-installed[dep] }` のループで、現在のパッケージが依存するすべてのパッケージのチャネルが閉じられるのを待ちます。これにより、依存関係が解決されてからビルドが開始されることが保証されます。
*   **`sync.WaitGroup` の活用**: `install` 関数内のコンパイルステップ (`for _, p := range files`) で、各ファイルのコンパイルをバックグラウンドで実行するために `sync.WaitGroup` が使用されるようになりました。
    *   `bgrun(&wg, path, compile...)` が呼び出される際に `wg.Add(1)` が行われ、バックグラウンドで実行されるGoroutineが完了すると `defer wg.Done()` が呼び出されます。
    *   `bgwait(&wg)` は、すべてのバックグラウンドタスクが完了するまで `wg.Wait()` を呼び出して待ちます。
*   **`cmdbootstrap` の変更**: `cmdbootstrap` 関数は、`buildlist` (すべてのビルド対象パッケージのソート済みリスト) を使用して、各パッケージの `installed` チャネルを初期化し、その後、各パッケージの `install` 関数をGoroutineとして並行して起動します。
    *   `go install(dir)` により、各パッケージのビルドが並行して実行されます。
    *   `<-installed["cmd/go"]` は、最終的に `cmd/go` パッケージのビルドが完了するまでメインのGoroutineをブロックします。これは、ブートストラッププロセスの最終目標が `cmd/go` のビルドであるためです。

### 3. `util.go` のリファクタリング

*   **`bgdied` から `bghelpers` へ**: 以前は `bgdied` という `sync.WaitGroup` と `nfatal` という `int32` のアトミックカウンタでバックグラウンドGoroutineの終了とエラー状態を管理していましたが、よりGoらしい `sync.WaitGroup` と `chan struct{}` を組み合わせた `bghelpers` と `dying` チャネルに置き換えられました。
*   **`fatal` 関数の改善**: `fatal` 関数が呼び出された際に、`dieOnce.Do(func() { close(dying) })` を使用して `dying` チャネルを一度だけ閉じ、すべてのバックグラウンドヘルパーGoroutineに終了を通知します。これにより、エラー発生時のクリーンアップがより堅牢になります。
*   **`bgrun` と `bgwait` のシグネチャ変更**: `bgrun` は `*sync.WaitGroup` を引数として受け取るようになり、`bgwait` も同様に `*sync.WaitGroup` を受け取ることで、特定のビルドフェーズの並行タスクの完了をより細かく制御できるようになりました。

これらの変更により、Goツールチェインのビルドプロセスは、依存関係を自動的に解決し、利用可能なCPUコアを最大限に活用してパッケージを並行してビルドできるようになり、全体的なビルド時間が大幅に短縮されました。

## コアとなるコードの変更箇所

### `src/cmd/dist/build.go`

*   `import` に `sort` と `sync` パッケージが追加されました。
*   `installed` マップ (`map[string]chan struct{}`) が導入され、パッケージのインストール完了を通知するチャネルを管理します。
*   `install` 関数が大幅に修正され、依存パッケージのインストール完了を待つロジック (`<-installed[dep]`) と、並列コンパイルのための `sync.WaitGroup` (`wg`) が導入されました。
*   `buildorder` スライスが削除され、代わりに `builddeps` マップと `buildlist` スライスが使用されるようになりました。
*   `cmdbootstrap` 関数が、`installed` マップとGoroutineを使用してパッケージを並行してインストールするように変更されました。

### `src/cmd/dist/deps.go` (新規ファイル)

*   `mkdeps.bash` スクリプトによって生成されるファイルで、`builddeps` という `map[string][]string` 型の変数を定義します。このマップは、各Goパッケージが依存する他のGoパッケージのリストを格納します。

### `src/cmd/dist/mkdeps.bash` (新規ファイル)

*   Goパッケージの依存関係を動的に抽出し、`deps.go` ファイルを生成するためのシェルスクリプトです。`go list` コマンドを `GOOS=windows` の環境で実行し、最も多くの依存関係を持つWindows環境での依存関係をベースに生成します。

### `src/cmd/dist/util.go`

*   `sync/atomic` パッケージのインポートが削除されました。
*   バックグラウンド処理を管理する `bgdied`, `nwork`, `ndone`, `nfatal` といった変数が削除され、`bghelpers` (`sync.WaitGroup`) と `dying` (`chan struct{}`) に置き換えられました。
*   `bghelper` 関数が `select` ステートメントを使用して `dying` チャネルからの終了通知を処理するように変更されました。
*   `bgrun` 関数と `bgwait` 関数のシグネチャが変更され、`sync.WaitGroup` を引数として受け取るようになりました。
*   `fatal` 関数が `sync.Once` を使用して `dying` チャネルを一度だけ閉じ、`bghelpers.Wait()` で全てのバックグラウンドGoroutineの終了を待つように変更されました。

## コアとなるコードの解説

### `src/cmd/dist/build.go` の `install` 関数 (抜粋)

```go
// installed maps from a dir name (as given to install) to a chan
// closed when the dir's package is installed.
var installed = make(map[string]chan struct{})

// install installs the library, package, or binary associated with dir,
// which is relative to $GOROOT/src.
func install(dir string) {
	if ch, ok := installed[dir]; ok {
		defer close(ch) // このパッケージのビルドが完了したらチャネルを閉じる
	}
	for _, dep := range builddeps[dir] {
		<-installed[dep] // 依存パッケージのチャネルが閉じられるまで待機
	}

    // ... (既存のビルドロジック) ...

	// Compile the files.
	var wg sync.WaitGroup // ファイルの並列コンパイルのためのWaitGroup
	for _, p := range files {
		if !strings.HasSuffix(p, ".s") {
			continue
		}
		// ... (コンパイルコマンドの準備) ...
		bgrun(&wg, path, compile...) // バックグラウンドでコンパイルを実行し、wgにタスクを追加
	}
	bgwait(&wg) // すべてのバックグラウンドコンパイルが完了するまで待機

    // ... (既存のビルドロジック) ...
}
```
この `install` 関数は、並列ビルドの核心部分です。
1.  `installed` マップとチャネルを使って、パッケージ間の依存関係を解決します。あるパッケージをビルドする前に、その依存パッケージがすべてビルドされていることを `<-installed[dep]` で確認します。
2.  `sync.WaitGroup` を使用して、単一パッケージ内の複数のソースファイル（特にアセンブリファイル `.s`）のコンパイルを並行して実行します。`bgrun` が各コンパイルタスクをGoroutineとして起動し、`bgwait` がそれらの完了を待ちます。

### `src/cmd/dist/mkdeps.bash` (新規ファイル)

```bash
#!/bin/bash

set -e

# Windows has the most dependencies.
export GOOS=windows

(
	echo '// generated by mkdeps.bash'
	echo
	echo 'package main'
	echo
	echo 'var builddeps = map[string][]string{'

	deps=$(GOOS=windows go list -tags cmd_go_bootstrap -f '{{join .Deps "\n"}}' cmd/go | grep -v '^unsafe$')
	GOOS=windows go list -tags cmd_go_bootstrap -f '{{printf "%q" .ImportPath}}: { {{range .Deps}}{{if not (eq . "unsafe")}}{{printf "%q" .}}, {{end}}{{end}} },' $deps cmd/go

	echo '}'
) |gofmt >deps.go
```
このスクリプトは、`go list` コマンドを利用してGoパッケージの依存関係を動的に解析し、その結果をGoソースファイル `deps.go` として出力します。`GOOS=windows` を設定しているのは、Windows環境が一般的に最も多くのシステムコール関連の依存関係を持つため、網羅的な依存関係リストを生成するためです。`cmd_go_bootstrap` タグは、ブートストラップビルドに必要なパッケージのみを対象とします。

### `src/cmd/dist/util.go` の `fatal` 関数 (抜粋)

```go
var (
	dieOnce sync.Once // guards close of dying
	dying   = make(chan struct{})
)

func fatal(format string, args ...interface{}) {
	fmt.Fprintf(os.Stderr, "go tool dist: %s\n", fmt.Sprintf(format, args...))

	dieOnce.Do(func() { close(dying) }) // dyingチャネルを一度だけ閉じる

	// Wait for background goroutines to finish,
	// so that exit handler that removes the work directory
	// is not fighting with active writes or open files.
	bghelpers.Wait() // すべてのバックグラウンドヘルパーGoroutineの終了を待つ

	xexit(2)
}
```
`fatal` 関数は、エラーが発生した際にプログラムを終了させる役割を担います。このコミットでは、`sync.Once` と `dying` チャネルを導入することで、エラー発生時にすべてのバックグラウンドGoroutineが安全に終了できるように改善されました。`dieOnce.Do` は、`close(dying)` が複数回呼び出されるのを防ぎ、`bghelpers.Wait()` は、バックグラウンドで実行中のタスクがすべて完了するまで待機することで、作業ディレクトリのクリーンアップなどが競合状態に陥るのを防ぎます。

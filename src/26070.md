# [インデックス 26070] ファイルの概要

このコミットは、Go言語の標準ライブラリである `net/http` パッケージ内の `Transport` 型における競合状態（race condition）を修正します。具体的には、ボディを持たないHTTPレスポンス（例: `HEAD` リクエストのレスポンスや `Content-Length: 0` のレスポンス）を処理する際に、コネクションの再利用が意図通りに行われない問題を解決します。`src/net/http/transport.go` が主要な変更ファイルであり、`export_test.go` と `transport_test.go` も関連するテストの修正や削除が行われています。

## コミット

`net/http` パッケージの `Transport` において、ボディを持たないレスポンスを返却し、かつコネクションを再利用する際の競合状態を修正しました。`readLoop` ゴルーチンと `RoundTrip` ゴルーチンの間のデリケートなプロトコルを簡素化し、ドキュメントを改善しました。これにより、ボディを持たないレスポンスが返された際に、永続的なコネクションがアイドルプールに適切に返却されるようになり、コネクションの再利用効率が向上しました。

## 元コミット内容

```
net/http: fix Transport race returning bodyless responses and reusing conns

The Transport had a delicate protocol between its readLoop goroutine
and the goroutine calling RoundTrip. The basic concern is that the
caller's RoundTrip goroutine wants to wait for either a
connection-level error (the conn dying) or the response. But sometimes
both happen: there's a valid response (without a body), but the conn
is also going away. Both goroutines' logic dealing with this had grown
large and complicated with hard-to-follow comments over the years.

Simplify and document. Pull some bits into functions and do all
bodyless stuff in one place (it's special enough), rather than having
a bunch of conditionals scattered everywhere. One test is no longer
even applicable since the race it tested is no longer possible (the
code doesn't exist).

The bug that this fixes is that when the Transport reads a bodyless
response from a server, it was returning that response before
returning the persistent connection to the idle pool. As a result,
~1/1000 of serial requests would end up creating a new connection
rather than re-using the just-used connection due to goroutine
scheduling chance. Instead, this now adds bodyless responses'
connections back to the idle pool first, then sends the response to
the RoundTrip goroutine, but making sure that the RoundTrip goroutine
is outside of its select on the connection dying.

There's a new buffered channel involved now, which is a minor
complication, but it's much more self-contained and well-documented
than the previous complexity. (The alternative of making the
responseAndError channel itself unbuffered is too invasive and risky
at this point; it would require a number of changes to avoid
deadlocked goroutines in error cases)

In any case, flakes look to be gone now. We'll see if trybots agree.

Fixes #13633
```

## 変更の背景

この変更の背景には、Goの `net/http` クライアントがHTTPリクエストを送信し、レスポンスを受信する際の内部的な競合状態がありました。特に、ボディを持たないHTTPレスポンス（例えば、`Content-Length: 0` のレスポンスや `HEAD` リクエストに対するレスポンス）を処理する際に問題が発生していました。

`net/http.Transport` は、HTTPコネクションの確立、再利用、および管理を担当します。パフォーマンス向上のため、HTTP/1.xでは永続的なコネクション（Keep-Alive）を再利用することが一般的です。`Transport` 内部では、`readLoop` というゴルーチンがコネクションからレスポンスを読み取り、`RoundTrip` を呼び出したクライアントゴルーチンにそのレスポンスを渡します。

問題は、ボディを持たないレスポンスが受信された際に、`readLoop` がレスポンスを `RoundTrip` ゴルーチンに返却するタイミングと、そのコネクションをアイドルプールに返却するタイミングの間に競合状態が存在したことです。以前の実装では、`readLoop` はレスポンスをクライアントゴルーチンに返してから、コネクションをアイドルプールに戻していました。この順序が原因で、ごく稀に（約1000回に1回程度）、クライアントが次のリクエストを送信しようとした際に、直前に使用したばかりのコネクションがまだアイドルプールに戻されておらず、新しいコネクションが確立されてしまうことがありました。これは、ゴルーチンのスケジューリングのタイミングに依存する問題であり、コネクションの再利用効率を低下させ、不必要なコネクション確立のオーバーヘッドを発生させていました。

この問題は、GitHub Issue #13633 で報告されており、このコミットはその修正を目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の `net/http` パッケージに関する前提知識が必要です。

1.  **`net/http.Transport`**:
    *   HTTPクライアントがリクエストを送信する際に使用する低レベルのインターフェースです。
    *   コネクションの確立、TLSハンドシェイク、プロキシの処理、コネクションプーリング（Keep-Alive）などを担当します。
    *   `http.Client` は内部的に `Transport` を使用してリクエストを実行します。

2.  **永続的なコネクション（Keep-Alive）とアイドルプール**:
    *   HTTP/1.1以降では、複数のリクエスト/レスポンスサイクルで同じTCPコネクションを再利用する「永続的なコネクション」がサポートされています。これにより、コネクション確立のオーバーヘッド（TCPハンドシェイク、TLSハンドシェイクなど）を削減し、パフォーマンスを向上させます。
    *   `Transport` は、使用されていないが再利用可能なコネクションを「アイドルプール」に保持します。新しいリクエストが来た際、アイドルプールに適切なコネクションがあればそれを再利用し、なければ新しいコネクションを確立します。

3.  **`readLoop` ゴルーチン**:
    *   `persistConn`（永続的なコネクションを表す内部構造体）ごとに起動されるゴルーチンです。
    *   このゴルーチンの主な役割は、ネットワークから生のHTTPレスポンスデータを読み取り、パースすることです。
    *   レスポンスボディの読み取りが完了するまで、またはコネクションがクローズされるまで動作します。

4.  **`RoundTrip` メソッド**:
    *   `http.RoundTripper` インターフェースの一部であり、`Transport` が実装しています。
    *   クライアントが `http.Client.Do()` などを呼び出すと、最終的に `Transport.RoundTrip()` が呼び出されます。
    *   このメソッドは、リクエストを送信し、レスポンスを受信するまでブロックします。

5.  **ボディを持たないレスポンス**:
    *   HTTPレスポンスの中には、ボディ部分を持たないものがあります。
    *   例:
        *   `HEAD` メソッドに対するレスポンス（ヘッダのみでボディなし）。
        *   `Content-Length: 0` ヘッダを持つレスポンス。
        *   `204 No Content` や `304 Not Modified` などの特定のステータスコードを持つレスポンス。
    *   これらのレスポンスは、ボディの読み取りを待つ必要がないため、`readLoop` と `RoundTrip` の間のプロトコルにおいて特別な処理が必要になります。

6.  **ゴルーチン間の通信と競合状態**:
    *   Goでは、ゴルーチンはチャネルを介して通信します。
    *   複数のゴルーチンが共有リソース（この場合はアイドルコネクションプール）にアクセスする際に、適切な同期メカニズムがないと競合状態が発生し、予期せぬ動作やパフォーマンスの問題を引き起こす可能性があります。

## 技術的詳細

このコミットが修正する問題は、`net/http.Transport` の `readLoop` ゴルーチンと `RoundTrip` を呼び出すクライアントゴルーチンの間の「デリケートなプロトコル」に起因していました。

以前の実装では、`readLoop` はコネクションからレスポンスヘッダを読み取り、それがボディを持たないレスポンスであると判断した場合、以下の順序で処理を行っていました。

1.  `RoundTrip` ゴルーチンにレスポンスオブジェクトを送信する。
2.  その後、`persistConn`（永続的なコネクション）をアイドルプールに返却する。

この順序が問題でした。`RoundTrip` ゴルーチンはレスポンスを受け取るとすぐに処理を開始し、次のリクエストを送信する可能性があります。しかし、その時点では `persistConn` はまだアイドルプールに戻されていませんでした。結果として、`RoundTrip` ゴルーチンが次のリクエストのためにコネクションを要求した際に、アイドルプールにはまだ直前に使用されたコネクションが存在せず、新しいコネクションが確立されてしまうことがありました。これは、特にCPU負荷が高い環境や、ゴルーチンのスケジューリングが特定のタイミングで発生した場合に顕著に現れる、タイミングに依存する競合状態でした。

この問題は、`readLoop` がレスポンスを送信するチャネル (`rc.ch`) と、コネクションがクローズされたことを通知するチャネル (`pc.closech`) の両方を `RoundTrip` ゴルーチンが `select` ステートメントで待機していることと関連していました。ボディを持たないレスポンスの場合、`readLoop` はすぐにレスポンスを送信し、その後コネクションをアイドルプールに戻そうとします。しかし、`RoundTrip` がレスポンスを受け取る前に `pc.closech` が発火してしまうと、`RoundTrip` はコネクションが死んだと判断し、エラーを返すか、新しいコネクションを確立してしまう可能性がありました。

このコミットでは、この問題を解決するために以下の技術的な変更が導入されました。

1.  **`responseAndError` 構造体の変更**:
    *   以前は `res *Response` フィールドで直接レスポンスを保持していましたが、`ch chan *Response` (バッファなしチャネル) と `r *Response` フィールドを持つように変更されました。
    *   ボディを持つレスポンスの場合は `r` に直接レスポンスが格納され、`RoundTrip` はそれを直接読み取ります。
    *   **ボディを持たないレスポンスの場合**、`ch` フィールドにバッファなしチャネルが作成され、`responseAndError` はこのチャネルを `RoundTrip` に送信します。

2.  **ボディを持たないレスポンスの処理順序の変更**:
    *   `readLoop` 内でボディを持たないレスポンスが検出された場合、まず `pc.t.setReqCanceler(rc.req, nil)` を呼び出してリクエストのキャンセル処理をクリアします。
    *   次に、`resc := make(chan *Response)` というバッファなしチャネルを作成し、`rc.ch <- responseAndError{ch: resc}` を通じて `RoundTrip` ゴルーチンに `responseAndError` を送信します。この送信はバッファ付きチャネル `rc.ch` を介して行われるため、`readLoop` はブロックされません。
    *   **ここで重要なのは、`readLoop` が `resc <- resp` を通じて実際のレスポンスを送信する前に、`pc.t.putIdleConn(pc)` を呼び出して `persistConn` をアイドルプールに返却する点です。**
    *   `RoundTrip` ゴルーチンは `responseAndError` を受け取ると、`re.res()` メソッドを呼び出します。ボディを持たないレスポンスの場合、このメソッドは `<-re.ch` からレスポンスを読み取ろうとします。これはバッファなしチャネルであるため、`readLoop` が `resc <- resp` を実行するまで `RoundTrip` はブロックされます。
    *   この新しい順序により、`persistConn` は必ずアイドルプールに返却されてから、`RoundTrip` ゴルーチンがレスポンスを受け取り、次のリクエストを開始できるようになります。これにより、コネクションの再利用が保証されます。

3.  **`readLoopPeekFailLocked` および `readResponse` ヘルパー関数の導入**:
    *   `readLoop` のロジックが複雑化していたため、一部の処理が `readLoopPeekFailLocked` と `readResponse` という新しいヘルパー関数に切り出され、コードの可読性と保守性が向上しました。

4.  **テストの変更**:
    *   以前の競合状態をテストしていた `TestTransportResponseCloseRace` は、その競合状態がもはや発生しないため削除されました。
    *   新しいテスト `TestTransportReuseConnEmptyResponseBody` が追加され、ボディを持たないレスポンスの場合でもコネクションが適切に再利用されることを検証します。このテストは、連続するリクエストが常に同じリモートアドレス（つまり同じコネクション）を使用することを確認します。

この変更により、`readLoop` と `RoundTrip` の間のプロトコルがより堅牢になり、ボディを持たないレスポンスの処理におけるコネクション再利用の信頼性が大幅に向上しました。

1.  **`src/net/http/export_test.go`**:

2.  **`src/net/http/transport.go`**:

        *   `pc.readLoopPeekFailLocked(err)` の呼び出しが追加され、アイドル状態のコネクションで予期せぬデータが受信された場合の処理がカプセル化されました。
        *   レスポンスの読み取りロジックが `pc.readResponse(rc)` ヘルパー関数に切り出されました。
        *   ボディを持たないレスポンス (`!hasBody`) の処理フローが完全に変更されました。
            *   `pc.t.setReqCanceler(rc.req, nil)` でリクエストキャンセラーをクリア。
            *   `resc := make(chan *Response)` (バッファなしチャネル) を作成。
            *   `rc.ch <- responseAndError{ch: resc}` で `RoundTrip` に `responseAndError` を送信。
            *   **`pc.t.putIdleConn(pc)` を呼び出してコネクションをアイドルプールに返却。**
            *   `resc <- resp` で実際のレスポンスを `RoundTrip` に送信。
        *   ボディを持つレスポンスの処理も簡素化され、`bodyEOFSignal` を使用したボディの読み取り完了待機ロジックが整理されました。
    *   新しいヘルパー関数 `maybeUngzipResponse(resp *Response)` が追加され、gzip圧縮されたレスポンスの処理をカプセル化しました。
    *   新しいヘルパー関数 `(pc *persistConn) readLoopPeekFailLocked(peekErr error)` が追加され、`readLoop` 内でのエラー処理を整理しました。
    *   新しいヘルパー関数 `(pc *persistConn) readResponse(rc requestAndChan) (resp *Response, err error)` が追加され、レスポンスの読み取りと `100 Continue` レスポンスの処理をカプセル化しました。
    *   `responseAndError` 構造体が変更されました。
        ```go
        type responseAndError struct {
            ch  chan *Response // if non-nil, res should be read from here
            r   *Response      // else use this response (see res method)
            err error
        }

        func (re responseAndError) res() *Response {
            switch {
            case re.err != nil:
                return nil
            case re.ch != nil:
                return <-re.ch
            default:
                return re.r
            }
        }
        ```
        これにより、ボディを持たないレスポンスの場合にバッファなしチャネルを介してレスポンスを遅延して送信するメカニズムが導入されました。
    *   `RoundTrip` メソッド内の `select` ステートメントのロジックが簡素化され、`pc.closech` が発火した場合の処理がより直接的になりました。

3.  **`src/net/http/transport_test.go`**:
    *   `TestTransportResponseCloseRace` テストが削除されました。このテストが対象としていた競合状態が修正されたため、もはや不要となりました。
    *   `TestTransportReuseConnEmptyResponseBody` という新しいテストが追加されました。このテストは、ボディを持たないレスポンスの場合でも、連続するリクエストが同じコネクションを再利用することを確認します。

## コアとなるコードの解説

このコミットの核心は、`readLoop` ゴルーチンと `RoundTrip` ゴルーチンの間の通信プロトコル、特にボディを持たないレスポンスの処理方法の変更にあります。

以前は、`readLoop` はボディなしレスポンスを `RoundTrip` に直接送信し、その後コネクションをアイドルプールに戻していました。この順序では、`RoundTrip` がレスポンスを受け取って次のリクエストを準備する間に、コネクションがまだプールに戻されていない可能性がありました。

新しい実装では、`responseAndError` 構造体に `ch chan *Response` というバッファなしチャネルが導入されました。

1.  **ボディを持たないレスポンスの場合**:
    *   `readLoop` はまず、`responseAndError{ch: resc}` (ここで `resc` は新しく作成されたバッファなしチャネル) を `RoundTrip` ゴルーチンに送信します。この送信は `rc.ch` というバッファ付きチャネルを介して行われるため、`readLoop` はブロックされません。
    *   `RoundTrip` ゴルーチンは `responseAndError` を受け取りますが、実際のレスポンスオブジェクトはまだ手に入れていません。`RoundTrip` は `re.res()` を呼び出すことでレスポンスを取得しようとしますが、この呼び出しは `<-re.ch` (つまり `<-resc`) から読み取ろうとするため、`readLoop` が `resc <- resp` を実行するまでブロックされます。
    *   **このブロックされるタイミングを利用して、`readLoop` は `resc <- resp` を実行する直前に `pc.t.putIdleConn(pc)` を呼び出し、コネクションをアイドルプールに返却します。**
    *   これにより、`RoundTrip` がレスポンスを受け取り、次のリクエストのためにコネクションを要求する際には、直前に使用されたコネクションがすでにアイドルプールに存在することが保証されます。

この巧妙なチャネルの利用により、`readLoop` と `RoundTrip` の間の同期が改善され、ボディを持たないレスポンスの場合でもコネクションの再利用が確実に行われるようになりました。以前の複雑で理解しにくいコメントだらけのロジックが、より明確で自己完結型のメカニズムに置き換えられています。

また、`readLoop` のコードが `readResponse` や `readLoopPeekFailLocked` といったヘルパー関数に分割されたことで、各部分の責任が明確になり、全体の可読性と保守性が向上しています。

## 元コミット内容

このコミットは、Goコンパイラの内部パッケージ `cmd/compile/internal` における `galign.go` ファイル群の定数定義を整理することを目的としています。具体的には、C言語のヘッダファイルスタイルで定義されていたアーキテクチャ固有の定数（`thechar`, `thestring`, `thelinkarch`, `MAXWIDTH`など）を、各アーキテクチャの `Main` メソッド内に移動させています。これにより、これらの定数がより適切なスコープで定義され、コードのクリーンアップが図られています。

## 変更の背景

Goコンパイラは、複数の異なるCPUアーキテクチャ（amd64, arm, arm64, mips64, ppc64, x86など）をサポートしています。各アーキテクチャには、その特性に応じたアライメント、レジスタ、ポインタサイズなどの情報が必要です。これらの情報は、コンパイラの初期化段階で設定されます。

このコミット以前は、これらのアーキテクチャ固有の定数の一部が、各アーキテクチャの `galign.go` ファイル内でパッケージレベルのグローバル変数として定義されていました。これは、C言語のヘッダファイルでマクロや定数を定義するようなスタイルに似ていました。しかし、Goの設計思想では、可能な限りグローバルな状態を避け、変数のスコープを限定することが推奨されます。グローバル変数は、コードの依存関係を複雑にし、予期せぬ副作用を引き起こす可能性があり、テストや保守を困難にする傾向があります。

この変更の背景には、Goコンパイラ内部のコードベースをよりGoらしいイディオムに準拠させ、保守性と可読性を向上させるという意図があります。`Main()` 関数は各アーキテクチャのコンパイラが起動する際に一度だけ実行される初期化関数であるため、そこでこれらの定数を設定することは、その定数がそのアーキテクチャのコンパイラ初期化にのみ関連していることを明確にし、スコープを適切に限定する効果があります。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造と概念に関する知識が必要です。

1.  **Goコンパイラの構造 (`cmd/compile/internal`)**:
    Goコンパイラは、`cmd/compile` ディレクトリ以下に実装されています。その中でも `cmd/compile/internal` は、コンパイラのバックエンド部分、特にコード生成やアーキテクチャ固有の処理を担当するパッケージ群を含んでいます。各サブディレクトリ（例: `amd64`, `arm`, `arm64`など）は、特定のCPUアーキテクチャに対応するコードを含んでいます。

2.  **`galign.go` ファイルの役割**:
    各アーキテクチャの `cmd/compile/internal/<arch>/galign.go` ファイルは、その名の通り "Go alignment" に関連する設定を扱います。具体的には、ポインタのサイズ (`gc.Widthptr`)、整数のサイズ (`gc.Widthint`)、最大幅 (`gc.Thearch.MAXWIDTH`)、レジスタの定義、アライメントルールなど、コンパイラがコード生成を行う上で必要となるアーキテクチャ固有の基本的なプロパティを初期化する役割を担っています。

3.  **`gc.Thearch` 構造体**:
    `cmd/compile/internal/gc` パッケージには、コンパイラ全体で共有されるグローバルな状態やユーティリティ関数が定義されています。`gc.Thearch` は、現在のターゲットアーキテクチャに関する情報を一元的に保持するための構造体です。この構造体には、アーキテクチャの文字コード (`Thechar`)、文字列名 (`Thestring`)、リンカアーキテクチャ情報 (`Thelinkarch`)、レジスタ情報 (`REGSP`, `REGCTXT`など)、最大幅 (`MAXWIDTH`) などが含まれます。コンパイラの各フェーズは、この `gc.Thearch` を参照してアーキテクチャ固有の動作を決定します。

4.  **`obj.LinkArch`**:
    `cmd/internal/obj` パッケージは、Goのオブジェクトファイルフォーマットとアセンブラ、リンカの共通基盤を提供します。`obj.LinkArch` は、リンカが特定のアーキテクチャのオブジェクトファイルを処理するために必要な情報（例: 命令セット、レジスタセット、アライメント要件など）をカプセル化した構造体です。各アーキテクチャの `galign.go` は、この `obj.LinkArch` のインスタンスを `gc.Thearch.Thelinkarch` に設定します。

5.  **`thechar`, `thestring`, `MAXWIDTH` などの定数**:
    *   `thechar`: 伝統的にGoのツールチェーンでアーキテクチャを識別するために使われてきた単一の文字です。例えば、`amd64` は `'6'`、`arm` は `'5'`、`arm64` は `'7'`、`x86` (386) は `'8'` です。
    *   `thestring`: アーキテクチャの文字列名（例: "amd64", "arm"）。
    *   `MAXWIDTH`: コンパイラが処理できる最大のアドレス空間またはデータ幅を示します。64ビットアーキテクチャでは `1 << 50` (非常に大きな値)、32ビットアーキテクチャでは `(1 << 32) - 1` といった値が設定されます。これは、コンパイラがメモリレイアウトやアライメント計算を行う際の制約となります。

## 技術的詳細

このコミットの技術的詳細は、主に「スコープの限定」と「初期化ロジックの集約」にあります。

変更前は、`galign.go` ファイルのトップレベルで以下のようなグローバル変数が定義されていました。

```go
// 例: amd64/galign.go
var thechar int = '6'
var thestring string = "amd64"
var thelinkarch *obj.LinkArch = &x86.Linkamd64
var MAXWIDTH int64 = 1 << 50
```

これらの変数はパッケージ全体からアクセス可能であり、理論的にはパッケージ内のどの関数からでも変更されうる状態でした（実際には変更されることはありませんでしたが、コードの意図としては不明瞭でした）。

変更後、これらの変数は削除され、その値は各アーキテクチャの `Main()` 関数内で `gc.Thearch` 構造体のフィールドに直接代入されるようになりました。

```go
// 例: amd64/galign.go の Main() 関数内
func Main() {
    // ...
    gc.Thearch.Thechar = '6'
    gc.Thearch.Thestring = "amd64"
    gc.Thearch.Thelinkarch = &x86.Linkamd64
    // ...
    gc.Thearch.MAXWIDTH = 1 << 50
    // ...
}
```

この変更により得られる技術的な利点は以下の通りです。

1.  **スコープの限定とカプセル化の向上**:
    これらの定数は、コンパイラの初期化時に一度だけ設定され、その後は変更されない性質を持っています。`Main()` 関数内で直接 `gc.Thearch` に代入することで、これらの値がパッケージレベルのグローバル変数として存在する必要がなくなり、そのライフサイクルと使用目的が `Main()` 関数による初期化に限定されることが明確になります。これにより、コードの意図がより明確になり、誤って変更されるリスクが減少します。

2.  **グローバル状態の削減**:
    Goのコードベースでは、グローバル変数の使用は慎重に行うべきとされています。グローバル変数を減らすことは、コードの推論を容易にし、並行処理における競合状態のリスクを低減し、テストの独立性を高める効果があります。この変更は、コンパイラ内部のグローバル状態をわずかながら削減する一歩となります。

3.  **Cヘッダスタイルからの脱却**:
    コミットメッセージにある「C header style architecture constants」という表現が示すように、以前の定義方法はC言語のヘッダファイルで `#define` や `const` を使うようなスタイルに似ていました。Goでは、このような定数定義は、それが実際に定数であり、かつグローバルにアクセス可能である必要がある場合にのみ行われるべきです。この変更は、Goのイディオムに沿ったより現代的なコードスタイルへの移行を示しています。

4.  **一貫性の向上**:
    `gc.Thearch` 構造体は、アーキテクチャ固有の情報を集約するためのものです。これらの定数を `Main()` 関数内で `gc.Thearch` に直接設定することで、アーキテクチャ固有の初期化ロジックが一箇所に集約され、コード全体の一貫性が向上します。

この変更は、コンパイラの機能に直接的な影響を与えるものではなく、主に内部的なコード品質と保守性の向上を目的としたリファクタリングです。

## コアとなるコードの解説

上記の差分からわかるように、主要な変更点は以下の通りです。

1.  **パッケージレベルの変数宣言の削除**:
    *   `thechar int = 'X'` (Xはアーキテクチャ固有の文字)
    *   `thestring string = "archname"`
    *   `thelinkarch *obj.LinkArch = &arch.Linkarchname`
    *   `MAXWIDTH int64 = ...`
    これらのグローバル変数の宣言が各 `galign.go` ファイルのトップレベルから削除されました。

2.  **`Main()` 関数内での直接代入**:
    削除されたグローバル変数の値は、各アーキテクチャの `Main()` 関数内で `gc.Thearch` 構造体の対応するフィールドに直接代入されるようになりました。
    *   `gc.Thearch.Thechar = 'X'`
    *   `gc.Thearch.Thestring = "archname"`
    *   `gc.Thearch.Thelinkarch = &arch.Linkarchname`
    *   `gc.Thearch.MAXWIDTH = ...`

    例えば、`amd64/galign.go` では、`thechar` 変数が削除され、`Main()` 関数内で `gc.Thearch.Thechar = '6'` と直接ハードコードされています。同様に、`MAXWIDTH` 変数も削除され、`gc.Thearch.MAXWIDTH = 1 << 50` と直接代入されています。

    `thestring` と `thelinkarch` については、`amd64` の例では `var` ブロック内に残されていますが、これは `addptr`, `movptr`, `leaptr`, `cmpptr` といった他のアーキテクチャ固有の定数とグループ化するためです。しかし、これらの値も最終的には `Main()` 関数内で `gc.Thearch` に代入されるため、実質的にはスコープが `Main()` 関数による初期化に限定されるという意図は変わりません。`arm` や `arm64` の例では、`thestring` と `thelinkarch` も完全に `Main()` 関数内に移動し、直接代入されています。これは、アーキテクチャによって初期化のパターンが若干異なるためですが、目的は同じです。

この変更により、これらのアーキテクチャ固有の定数が、コンパイラの初期化ロジックの一部として明確に位置づけられ、パッケージのグローバル状態を汚染することなく、必要な場所で設定されるようになりました。これは、コードの意図を明確にし、保守性を向上させるための典型的なリファクタリング手法です。

# [インデックス 24968] ファイルの概要

このコミットは、Go言語の公式コード整形ツールである `go/printer` パッケージにおける、`*ast.CallExpr` (関数呼び出しやメソッド呼び出し) の引数リストのインデントに関するバグ修正です。特に、メソッドチェーンが複数行にわたる場合に、引数のインデントが不適切になる問題を解決し、より一貫性のある整形結果を提供します。

## コミット

go/printer: fix indentation of *ast.CallExpr parameters

The current version of go/printer formats the following code
like this:

        foo.Bar().
                Run(func() {
                do()
        }).
                Set(map[string]interface{}{
                "x": "three",
                "y": 4,
        }).
                Run(
                func() {
                        do()
                },
        )

This CL changes the go/printer behaviour to make the code look
like this.

        foo.Bar().
                Run(func() {
                        do()
                }).
                Set(map[string]interface{}{
                        "x": "three",
                        "y": 4,
                }).
                Run(
                        func() {

                        },
                )

## 変更の背景

この変更の背景には、`go/printer` パッケージがGoコードを整形する際に、特にメソッドチェーンとそれに続く関数呼び出しの引数リストのインデント処理に一貫性のない挙動があったという問題があります。

コミットメッセージに示されている「現在のバージョン」の整形結果を見ると、`foo.Bar().Run(...)` の `Run` メソッドの引数である `func() { do() }` の内部の `do()` が、`Run` の開始位置からさらにインデントされずに、`Run` と同じレベルで始まってしまっています。同様に、`Set` メソッドの引数であるマップリテラルのキーと値も、不適切なインデントになっています。

Go言語では、`gofmt` という標準のコード整形ツールがあり、その基盤となっているのが `go/printer` パッケージです。`gofmt` はGoコミュニティ全体でコードの一貫性を保つために非常に重要であり、その出力は常に予測可能でなければなりません。しかし、このバグにより、特定の複雑なメソッドチェーンのパターンで `gofmt` の出力が期待されるインデントルール（通常は、新しいブロックや引数リストの開始でインデントレベルが深くなる）に違反していました。

この不適切なインデントは、コードの可読性を損なうだけでなく、`gofmt` を実行するたびにコードの見た目が変わる可能性があり、開発者の混乱を招く原因となります。このコミットは、このインデントの不整合を修正し、`gofmt` が常に一貫した、Goのスタイルガイドに沿った整形結果を生成するようにすることを目的としています。具体的には、メソッドチェーンの途中で改行が入る場合でも、その後の引数やブロックが適切にインデントされるように挙動を改善しています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念と `go/printer` パッケージの内部動作に関する知識が必要です。

### 1. Go言語の抽象構文木 (AST)

Goコンパイラは、ソースコードを直接解釈するのではなく、まずソースコードを解析して「抽象構文木 (Abstract Syntax Tree, AST)」と呼ばれるツリー構造のデータ表現に変換します。ASTは、プログラムの構造を階層的に表現し、各ノードがコードの特定の要素（変数宣言、関数呼び出し、式など）に対応します。

*   **`go/ast` パッケージ**: Go標準ライブラリの `go/ast` パッケージは、GoソースコードのASTを定義する型を提供します。
    *   **`ast.Expr`**: 式を表すインターフェースです。
    *   **`*ast.CallExpr`**: 関数呼び出しやメソッド呼び出しを表すASTノードです。`Fun` (呼び出される関数/メソッド) と `Args` (引数リスト) を持ちます。
    *   **`*ast.SelectorExpr`**: セレクタ式（例: `object.field` や `object.method`）を表すASTノードです。`X` (セレクタの左側の式) と `Sel` (選択される識別子) を持ちます。メソッドチェーン `foo.Bar().Run()` の `foo.Bar` や `Bar().Run` の部分がこれに該当します。

### 2. `go/printer` パッケージ

`go/printer` パッケージは、`go/ast` パッケージで定義されたASTを受け取り、それを整形されたGoソースコードとして出力する役割を担います。これは `gofmt` コマンドの基盤となるパッケージであり、Goコードの標準的な整形ルールを実装しています。

*   **整形処理**: `go/printer` は、ASTをトラバースしながら、適切なインデント、改行、スペースなどを挿入してコードを整形します。
*   **インデント管理**: `go/printer` は内部的にインデントレベルを管理しており、`indent` (インデントを増やす)、`unindent` (インデントを減らす)、`newline` (改行を挿入する) といった特殊なトークンを生成することで、出力されるコードの構造を制御します。

### 3. メソッドチェーン

Go言語では、構造体やインターフェースのメソッドを連続して呼び出す「メソッドチェーン」のパターンがよく使われます。例えば、`obj.Method1().Method2(arg).Method3()` のような形式です。このようなコードは、特に複数行にわたる場合に、可読性を保つために適切なインデントが求められます。

### 4. `gofmt` の役割と重要性

`gofmt` はGo言語の公式なコード整形ツールであり、Goコミュニティ全体でコードスタイルの一貫性を強制するために広く利用されています。`gofmt` が生成する出力は、Goのコードスタイルガイドに厳密に従うことが期待されており、その出力が不適切であると、開発者の間で混乱や不満が生じます。このコミットは、`gofmt` の出力品質を向上させるためのものです。

## 技術的詳細

このコミットは、`src/go/printer/nodes.go` ファイル内の `expr1` 関数、および新しく導入されたヘルパー関数 `possibleSelectorExpr` と `selectorExpr` を中心に、`*ast.CallExpr` と `*ast.SelectorExpr` の整形ロジックを改善しています。

### 1. `expr1` 関数の役割

`expr1` 関数は、`go/printer` の中で最も重要な関数の1つで、Goの様々な種類の式 (`ast.Expr`) を整形する役割を担っています。この関数は、式の種類に応じて適切な整形ロジックを適用し、インデントや改行を制御します。

### 2. `*ast.SelectorExpr` の整形ロジックの変更

コミット前の `expr1` 関数内の `*ast.SelectorExpr` の処理は以下のようでした。

```go
case *ast.SelectorExpr:
    p.expr1(x.X, token.HighestPrec, depth)
    p.print(token.PERIOD)
    if line := p.lineFor(x.Sel.Pos()); p.pos.IsValid() && p.pos.Line < line {
        p.print(indent, newline, x.Sel.Pos(), x.Sel, unindent)
    } else {
        p.print(x.Sel.Pos(), x.Sel)
    }
```

このコードでは、セレクタ式 (`x.X.Sel`) の `Sel` 部分が新しい行にある場合 (`p.pos.Line < line`) に `indent`, `newline`, `unindent` を出力していました。しかし、この `unindent` が常に適切であるとは限りませんでした。特に、メソッドチェーンの途中で改行が入る場合、その後のメソッド呼び出しの引数リストのインデントに影響を与えていました。

このコミットでは、この部分を `p.selectorExpr(x, depth, false)` の呼び出しに置き換えています。これにより、セレクタ式の整形ロジックが `selectorExpr` という専用のヘルパー関数に集約され、より細かく制御できるようになりました。

### 3. `*ast.CallExpr` の整形ロジックの変更

`*ast.CallExpr` の処理では、呼び出される関数 (`x.Fun`) の整形方法が変更されました。

コミット前は、`x.Fun` が `*ast.FuncType` (関数型リテラル) の場合は `p.expr1(x.Fun, token.HighestPrec, depth)` を直接呼び出し、それ以外の場合も同様に `p.expr1` を呼び出していました。

変更後、これらの `p.expr1` の呼び出しは `wasIndented = p.possibleSelectorExpr(x.Fun, token.HighestPrec, depth)` に置き換えられました。

この変更のポイントは以下の通りです。

*   **`possibleSelectorExpr` の導入**: この新しいヘルパー関数は、`x.Fun` が `*ast.SelectorExpr` であるかどうかをチェックします。もしそうであれば、`selectorExpr` を呼び出して整形し、セレクタ式が複数行にわたってインデントされたかどうかを示すブール値を返します。`*ast.SelectorExpr` でない場合は、通常の `p.expr1` を呼び出し、`false` を返します。
*   **`wasIndented` フラグ**: `possibleSelectorExpr` が返す `wasIndented` フラグは、呼び出された式（特にセレクタ式）が複数行にわたってインデントされたかどうかを追跡します。
*   **条件付き `unindent`**: `*ast.CallExpr` の整形が完了した後、`if wasIndented { p.print(unindent) }` という行が追加されました。これは、もし `x.Fun` が複数行にわたるセレクタ式であり、その過程で `indent` が追加されていた場合、ここで対応する `unindent` を出力してインデントレベルを元に戻すことを意味します。これにより、メソッドチェーンの次の要素や、`CallExpr` の後のコードが適切なインデントレベルで開始されるようになります。

### 4. 新しいヘルパー関数 `possibleSelectorExpr` と `selectorExpr`

*   **`possibleSelectorExpr(expr ast.Expr, prec1, depth int) bool`**:
    *   引数 `expr` が `*ast.SelectorExpr` 型であるかをチェックします。
    *   もし `*ast.SelectorExpr` であれば、`selectorExpr` を呼び出し、その戻り値を返します。
    *   そうでなければ、通常の `p.expr1` を呼び出して `false` を返します。
    *   この関数は、`CallExpr` の `Fun` 部分がセレクタ式である場合に、特別なインデント処理を適用するためのゲートウェイとして機能します。

*   **`selectorExpr(x *ast.SelectorExpr, depth int, isMethod bool) bool`**:
    *   `*ast.SelectorExpr` の整形を担当します。
    *   `x.X` (セレクタの左側) を `p.expr1` で整形し、`.` (ピリオド) を出力します。
    *   `x.Sel` (選択される識別子) が新しい行にある場合、`indent`, `newline`, `x.Sel.Pos()`, `x.Sel` を出力します。
    *   ここで重要なのは、`if !isMethod { p.print(unindent) }` という条件付き `unindent` です。
        *   `isMethod` が `true` の場合（つまり、このセレクタ式がメソッド呼び出しの一部である場合）、`unindent` は出力されません。これは、メソッドチェーンが続くことを想定しており、その後のメソッド呼び出しの引数リストが適切にインデントされるようにするためです。
        *   `isMethod` が `false` の場合（つまり、単なるフィールドアクセスなど、メソッドチェーンの途中でない場合）、`unindent` が出力され、インデントレベルが元に戻されます。
    *   この関数は、セレクタ式が複数行にわたってインデントされたかどうかを示すブール値を返します。

これらの変更により、`go/printer` はメソッドチェーンの途中で改行が入る場合でも、その後の `*ast.CallExpr` の引数リストが適切にインデントされるように、インデントレベルの管理をより正確に行えるようになりました。特に、`isMethod` フラグの導入は、セレクタ式がメソッド呼び出しの一部であるか否かによって、インデントの挙動をきめ細かく制御するための鍵となっています。

## コアとなるコードの解説

### `expr1` 関数内の `*ast.SelectorExpr` 処理

*   **変更前**: `*ast.SelectorExpr` の整形ロジックが `expr1` 関数内に直接記述されており、`Sel` (セレクタの右側) が改行される場合に `indent`, `newline`, `unindent` を出力していました。この `unindent` が、メソッドチェーンの文脈で問題を引き起こす可能性がありました。
*   **変更後**: `p.selectorExpr(x, depth, false)` という新しいヘルパー関数呼び出しに置き換えられました。これにより、セレクタ式の整形ロジックがカプセル化され、`selectorExpr` 関数内でより柔軟なインデント制御が可能になります。`isMethod` 引数に `false` を渡しているのは、このコンテキストではセレクタ式が必ずしもメソッド呼び出しの一部ではないことを示唆しています。

### `expr1` 関数内の `*ast.CallExpr` 処理

*   **`var wasIndented bool` の追加**: `*ast.CallExpr` の処理ブロックの冒頭に `wasIndented` というブール変数が追加されました。これは、呼び出される関数 (`x.Fun`) の整形中にインデントが追加されたかどうかを追跡するために使用されます。
*   **`p.expr1(x.Fun, ...)` から `p.possibleSelectorExpr(x.Fun, ...)` への変更**:
    *   呼び出される関数 (`x.Fun`) の整形に `p.possibleSelectorExpr` が使用されるようになりました。この関数は、`x.Fun` が `*ast.SelectorExpr` である場合に特別な処理を行い、インデントが追加されたかどうかを `wasIndented` に返します。
    *   これにより、`CallExpr` の `Fun` 部分がメソッドチェーンの一部である場合に、そのインデント状態を正確に把握できるようになります。
*   **`if wasIndented { p.print(unindent) }` の追加**: `*ast.CallExpr` の整形が完了し、`RPAREN` (閉じ括弧) が出力された直後に、この条件付き `unindent` が追加されました。
    *   もし `x.Fun` の整形中に `indent` が追加されていた場合 (`wasIndented` が `true`)、ここで対応する `unindent` が出力され、インデントレベルが元に戻されます。
    *   この修正により、メソッドチェーンの次の要素や、`CallExpr` の後のコードが適切なインデントレベルで開始されるようになり、不適切なインデントが解消されます。

### 新しいヘルパー関数 `possibleSelectorExpr`

*   この関数は、与えられた式 `expr` が `*ast.SelectorExpr` であるかを判断し、もしそうであれば `p.selectorExpr` を呼び出します。
*   `p.selectorExpr` を呼び出す際に `isMethod` 引数に `true` を渡しています。これは、`CallExpr` の `Fun` として渡されるセレクタ式は、通常メソッド呼び出し (`obj.Method()`) の一部であるためです。
*   `isMethod: true` の場合、`selectorExpr` はセレクタ式の `Sel` 部分が改行されても `unindent` を出力しません。これは、メソッドチェーンが続くことを想定しているため、インデントレベルを維持する必要があるからです。

### 新しいヘルパー関数 `selectorExpr`

*   この関数は `*ast.SelectorExpr` の整形に特化しています。
*   `x.X` (セレクタの左側) を整形し、`.` (ピリオド) を出力します。
*   `x.Sel` (セレクタの右側) が新しい行にある場合、`indent` と `newline` を出力してインデントを深くします。
*   **`if !isMethod { p.print(unindent) }`**: ここが重要な変更点です。
    *   もし `isMethod` が `false` であれば、`unindent` を出力してインデントレベルを元に戻します。これは、例えば `obj.Field` のように、セレクタ式がメソッド呼び出しのチェーンの一部ではない場合に適用されます。
    *   もし `isMethod` が `true` であれば、`unindent` は出力されません。これは、`obj.Method().AnotherMethod()` のようにメソッドチェーンが続く場合、`Method()` の後の `AnotherMethod()` が適切なインデントレベルで開始されるようにするためです。`CallExpr` の処理で最終的に `unindent` が行われるため、ここで二重に `unindent` する必要がありません。
*   この関数は、セレクタ式が複数行にわたってインデントされた場合に `true` を返します。

これらの変更により、`go/printer` は、メソッドチェーンの複雑なインデントシナリオにおいて、より正確で一貫性のある整形結果を生成できるようになりました。特に、`isMethod` フラグと `wasIndented` フラグの連携により、インデントの追加と削除が適切なタイミングで行われるようになり、Goのコードスタイルに沿った整形が実現されています。

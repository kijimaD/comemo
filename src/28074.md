## 変更の背景

Go言語のドキュメンテーションツール（`go doc`や`godoc`など）は、ソースコード内のコメントから自動的にドキュメントを生成します。このツールは、特定の書式規則に従ってコメントを解析し、HTMLなどの形式でレンダリングします。特に、コード例や構造体定義などのプリフォーマットされたテキストブロックは、コメント内で特定のインデント（通常はタブまたは複数のスペース）を持つことで、コードとして認識され、適切なフォントや背景色で表示されます。

このコミットが行われる前は、`SetCgoTraceback`関数のドキュメントコメント内の構造体定義のインデントが、この規則に完全に準拠していなかったため、`godoc`によって生成されるHTMLドキュメントで正しくコードブロックとしてレンダリングされていませんでした。その結果、ドキュメントの可読性が損なわれていました。この変更は、この表示上の問題を解決し、ドキュメントの品質を向上させることを目的としています。

## 前提知識の解説

### Go言語のドキュメンテーションコメント

Go言語では、関数、型、変数などの宣言の直前に記述されたコメントがドキュメンテーションコメントとして扱われます。これらのコメントは`go doc`コマンドや`godoc`ツールによって解析され、開発者向けのドキュメントが生成されます。

### `godoc`のレンダリング規則

`godoc`は、Markdownに似た独自の書式規則を使用してコメントをHTMLに変換します。重要な規則の一つに、プリフォーマットされたテキストブロックの扱いがあります。

*   **コードブロックの認識**: コメント内の行が、その行の最初の非空白文字の前にタブ文字 (`\t`) または少なくとも8つのスペースでインデントされている場合、その行はプリフォーマットされたテキスト（コードブロック）として扱われます。これにより、HTMLでは`<pre>`タグで囲まれ、等幅フォントで表示されます。
*   **インデントの重要性**: インデントが不適切であると、`godoc`はその行を通常の段落の一部として解釈し、コードブロックとしてレンダリングしません。これは、特に構造体定義やコード例のような、書式が重要な部分で問題となります。

### `SetCgoTraceback`関数とCgo

`SetCgoTraceback`は、GoランタイムがCgo呼び出し中に発生したトレースバックをどのように処理するかを設定するための関数です。CgoはGoプログラムからC言語のコードを呼び出すためのメカニズムであり、GoとCの境界を越える際にスタックトレースの取得方法が複雑になることがあります。この関数は、カスタムのトレースバックコンテキスト、トレースバック関数、シンボライザ関数を設定することで、Cgo関連のデバッグを支援します。これらの関数は、Goランタイムが特定の構造体ポインタを引数として呼び出すC関数として定義されます。

## 技術的詳細

このコミットの技術的詳細は、Goドキュメンテーションのレンダリングメカニズムにおけるインデントの厳密な解釈にあります。

`src/runtime/traceback.go`内の`SetCgoTraceback`関数のドキュメントコメントには、Cgoコールバック関数に渡される引数の構造体定義がGoとCの両方の構文で記述されていました。これらの構造体定義は、ドキュメント上でコードブロックとして表示されるべきものです。

元のコードでは、これらの構造体定義が以下のような形式で記述されていました（例として一部抜粋）：

```go
// struct {
//	Context uintptr
// }
```

このインデントは、`//`の後にスペースが続き、その後に構造体定義が続く形です。`godoc`のレンダリングエンジンは、このインデントをコードブロックとして認識するのに十分ではないと判断していました。具体的には、`//`コメントマーカーの後のインデントが、タブ文字または8スペースの要件を満たしていなかった可能性があります。

このコミットでは、インデントをタブ文字 (`\t`) に変更することで、この問題を解決しています。

```go
//	struct {
//		Context uintptr
//	}
```

このように、`//`の直後にタブ文字を挿入することで、`godoc`はこれらの行をプリフォーマットされたテキストとして正しく解釈し、HTMLドキュメント上でコードブロックとしてレンダリングするようになります。これにより、ドキュメントの視覚的な整合性と正確性が向上します。

この変更は、Goのドキュメンテーションコメントの書式規則、特にコード例や構造体定義の表示に関する厳密な要件を浮き彫りにしています。適切なインデントは、単なる見た目の問題ではなく、ドキュメントのセマンティックな解釈とレンダリングに直接影響を与えます。

## コアとなるコードの解説

上記の`diff`を見ると、変更はすべてコメント行のインデント調整であることがわかります。具体的には、`//`の後に続いていた複数のスペースが、タブ文字 (`\t`) に置き換えられています。

例えば、以下の行が変更されています。

```diff
-// struct {
-//	Context uintptr
-// }
+//	struct {
+//		Context uintptr
+//	}
```

この変更の意図は、Goのドキュメンテーションツール（`godoc`）がコメント内のコードブロックを正しく認識し、HTML出力で適切にレンダリングできるようにすることです。`godoc`は、行頭にタブ文字または8つ以上のスペースがある行をプリフォーマットされたテキストとして扱います。元のコメントでは、この規則が満たされていなかったため、構造体定義が通常のテキストとしてレンダリングされ、コードとしての書式が失われていました。

タブ文字に置き換えることで、これらの構造体定義は`godoc`によってコードブロックとして認識され、等幅フォントで表示されるようになります。これにより、`SetCgoTraceback`関数のドキュメントがより明確で読みやすくなります。これは機能的な変更ではなく、ドキュメンテーションの品質向上を目的とした純粋な書式設定の修正です。

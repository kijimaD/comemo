# [インデックス 26343] ファイルの概要

このコミットは、Go言語の `crypto/tls` パッケージにおける `Conn.Close` メソッドの挙動を改善するものです。具体的には、`Conn.Write` が実行中の場合に `Conn.Close` がブロックするのを防ぎ、ネットワークエラー発生時のゴルーチンリークや `net/http.Transport` のハングアップといった問題を解決します。

## コミット

```
crypto/tls: don't block in Conn.Close if Writes are in-flight

Conn.Close sends an encrypted "close notify" to signal secure EOF.
But writing that involves acquiring mutexes (handshake mutex + the
c.out mutex) and writing to the network. But if the reason we're
calling Conn.Close is because the network is already being
problematic, then Close might block, waiting for one of those mutexes.

Instead of blocking, and instead of introducing new API (at least for
now), distinguish between a normal Close (one that sends a secure EOF)
and a resource-releasing destructor-style Close based on whether there
are existing Write calls in-flight.

Because io.Writer and io.Closer aren't defined with respect to
concurrent usage, a Close with active Writes is already undefined, and
should only be used during teardown after failures (e.g. deadlines or
cancelations by HTTP users). A normal user will do a Write then
serially do a Close, and things are unchanged for that case.

This should fix the leaked goroutines and hung net/http.Transport
requests when there are network errors while making TLS requests.
```

## 変更の背景

TLS (Transport Layer Security) コネクションを閉じる際、`crypto/tls` パッケージの `Conn.Close` メソッドは、通常、セキュアなEOF (End Of File) を通知するために暗号化された "close notify" アラートを送信します。この "close notify" の送信には、ハンドシェイクミューテックスや出力ミューテックスといった内部ロックの取得、およびネットワークへの書き込みが伴います。

しかし、ネットワークに問題が発生している状況（例えば、タイムアウトや接続切断など）で `Close` が呼び出された場合、これらのミューテックスの取得やネットワーク書き込みがブロックされ、`Close` 呼び出し元がハングアップする可能性がありました。特に、`net/http.Transport` のようなHTTPクライアントがTLSリクエスト中にネットワークエラーに遭遇すると、`Conn.Close` がブロックし、結果としてゴルーチンがリークしたり、リクエストがハングアップしたりする問題が発生していました。

このコミットは、このような状況下での `Close` のブロックを防ぎ、リソースを適切に解放することを目的としています。

## 前提知識の解説

*   **TLS (Transport Layer Security)**: インターネット上でデータを安全にやり取りするための暗号化プロトコルです。Go言語の `crypto/tls` パッケージは、このプロトコルを実装しています。
*   **`io.Writer` と `io.Closer`**: Go言語の標準ライブラリで定義されているインターフェースです。
    *   `io.Writer` は `Write([]byte) (int, error)` メソッドを持つ型が実装し、データの書き込み機能を提供します。
    *   `io.Closer` は `Close() error` メソッドを持つ型が実装し、リソースの解放機能を提供します。
    *   これらのインターフェースは、並行利用（concurrent usage）に関して明確な定義を持っていません。つまり、複数のゴルーチンが同時に `Write` や `Close` を呼び出した場合の挙動は、実装依存であり、一般的には未定義と見なされます。
*   **`sync.Mutex`**: Go言語で排他制御を行うための基本的なプリミティブです。複数のゴルーチンが共有リソースに同時にアクセスするのを防ぎます。
*   **`sync/atomic` パッケージ**: Go言語でアトミック操作（不可分操作）を提供するためのパッケージです。ミューテックスを使用せずに、単一のCPU命令で変数の読み書きや比較交換を行うことで、より効率的な並行処理を実現します。特に、カウンタの増減やフラグのセットなど、単純な共有状態の管理に適しています。
*   **`close notify` アラート**: TLSプロトコルにおいて、通信の終了を安全に通知するためにクライアントまたはサーバーが送信する特別なメッセージです。これにより、相手側は通信が正常に終了したことを認識し、セッションを安全に閉じることができます。

## 技術的詳細

この変更の核心は、`Conn.Close` が呼び出された際に、現在 `Conn.Write` が実行中であるかどうかをアトミックに判定し、その状況に応じて `Close` の挙動を変える点にあります。

1.  **`activeCall` フィールドの導入**:
    `tls.Conn` 構造体に `activeCall int32` という新しいフィールドが追加されました。この `int32` 型の変数は、以下のようにビットフラグとカウンタの役割を兼ねています。
    *   最下位ビット (low bit) は、`Conn.Close` が呼び出されたかどうかを示すフラグとして使用されます (`1` なら `Close` 済み)。
    *   残りのビットは、現在アクティブな `Conn.Write` 呼び出しの数を追跡するカウンタとして使用されます。各 `Write` 呼び出しはカウンタを `2` ずつ増減させます（最下位ビットを `Close` フラグのために空けておくため）。

2.  **`Conn.Write` の変更**:
    `Write` メソッドの冒頭で、`activeCall` の値をアトミックに読み込み、`Close` フラグがセットされていないか（最下位ビットが `0` か）を確認します。もし `Close` が既に呼び出されている場合、`errClosed` エラーを即座に返します。
    `Write` がアクティブであることを示すために、`activeCall` カウンタをアトミックに `2` 増やします。`Write` メソッドの終了時には、`defer` を使ってカウンタをアトミックに `2` 減らします。これにより、複数の `Write` が同時に実行されても正確なカウントが維持されます。

3.  **`Conn.Close` の変更**:
    `Close` メソッドの冒頭で、`activeCall` の値をアトミックに読み込み、`Close` フラグをセットします（最下位ビットを `1` にします）。
    重要なのは、`activeCall` の値が `0` でない場合（つまり、`Close` が既に呼び出されているか、またはアクティブな `Write` 呼び出しが存在する場合）の挙動です。この場合、`Close` は "close notify" アラートの送信をスキップし、基盤となる `net.Conn` の `Close()` メソッドを直接呼び出します。これは、リソースを強制的に解放する「デストラクタースタイル」の `Close` と見なされます。
    これにより、ネットワークが問題のある状態であっても、`Close` がミューテックスの取得やネットワーク書き込みでブロックされることなく、迅速にリソースを解放できるようになります。

このアプローチは、`io.Writer` と `io.Closer` の並行利用が未定義であるという前提を利用しています。つまり、`Write` がアクティブな状態で `Close` が呼び出される状況は、通常、ネットワークエラーやタイムアウトなど、異常なシャットダウンシーケンス中に発生すると考えられます。このような状況では、セキュアなEOF通知よりも、リソースの迅速な解放が優先されるべきであるという判断に基づいています。

## コアとなるコードの変更箇所

### `src/crypto/tls/conn.go`

```go
 // activeCall is an atomic int32; the low bit is whether Close has
 // been called. the rest of the bits are the number of goroutines
 // in Conn.Write.
 activeCall int32

 var errClosed = errors.New("crypto/tls: use of closed connection")

 // Write writes data to the connection.
 func (c *Conn) Write(b []byte) (int, error) {
 	// interlock with Close below
 	for {
 		x := atomic.LoadInt32(&c.activeCall)
 		if x&1 != 0 {
 			return 0, errClosed
 		}
 		if atomic.CompareAndSwapInt32(&c.activeCall, x, x+2) {
 			defer atomic.AddInt32(&c.activeCall, -2)
 			break
 		}
 	}

 	if err := c.Handshake(); err != nil {
 		return 0, err
 	}
 	// ... (既存のWriteロジック)
 }

 // Close closes the connection.
 func (c *Conn) Close() error {
 	// Interlock with Conn.Write above.
 	var x int32
 	for {
 		x = atomic.LoadInt32(&c.activeCall)
 		if x&1 != 0 {
 			return errClosed
 		}
 		if atomic.CompareAndSwapInt32(&c.activeCall, x, x|1) {
 			break
 		}
 	}
 	if x != 0 {
 		// io.Writer and io.Closer should not be used concurrently.
 		// If Close is called while a Write is currently in-flight,
 		// interpret that as a sign that this Close is really just
 		// being used to break the Write and/or clean up resources and
 		// avoid sending the alertCloseNotify, which may block
 		// waiting on handshakeMutex or the c.out mutex.
 		return c.conn.Close()
 	}

 	var alertErr error
 	// ... (既存のCloseロジック: alertCloseNotifyの送信など)
 }
```

## コアとなるコードの解説

### `activeCall` フィールド

`activeCall` は `int32` 型のアトミック変数で、`Conn` の状態を効率的に管理します。
*   `x&1 != 0`: `activeCall` の最下位ビットが `1` であるかを確認します。これは `Close` が既に呼び出されたことを意味します。
*   `x+2`: `Write` が開始される際に `activeCall` を `2` 増やします。これにより、最下位ビット（`Close` フラグ）に影響を与えずに、アクティブな `Write` の数をカウントできます。
*   `x|1`: `Close` が呼び出された際に `activeCall` の最下位ビットを `1` にセットします。これにより、`Close` フラグが立ちます。

### `Conn.Write` メソッドの変更

`Write` メソッドは、`atomic.LoadInt32` と `atomic.CompareAndSwapInt32` を使用して、`activeCall` の値を安全に更新します。
`for` ループと `CompareAndSwapInt32` は、楽観的ロック（optimistic locking）のパターンを形成し、複数のゴルーチンが同時に `activeCall` を変更しようとした場合に競合を解決します。
`defer atomic.AddInt32(&c.activeCall, -2)` は、`Write` メソッドがどのような経路で終了しても（正常終了、エラー終了、パニックなど）、必ず `activeCall` カウンタを適切にデクリメントすることを保証します。

### `Conn.Close` メソッドの変更

`Close` メソッドも同様にアトミック操作を使用して `activeCall` を更新し、`Close` フラグをセットします。
`if x != 0` の条件がこの変更の肝です。
*   `x` は `Close` が呼び出される直前の `activeCall` の値です。
*   もし `x` が `0` でない場合、それは `Close` が既に呼び出されているか（最下位ビットが `1`）、または `Write` がアクティブであるか（残りのビットが `0` でない）のいずれかを意味します。
*   この場合、`Close` は `alertCloseNotify` の送信をスキップし、直接 `c.conn.Close()` を呼び出します。これにより、ミューテックスの競合やネットワーク書き込みによるブロックを回避し、基盤となるネットワーク接続を強制的に閉じます。これは、リソースを迅速に解放するための「デストラクタースタイル」の `Close` として機能します。

### `tls_test.go` の追加テスト

`TestConnCloseBreakingWrite` は、この変更が意図通りに機能することを保証するための重要なテストです。
`changeImplConn` を使用して、基盤となる `net.Conn` の `Write` メソッドを意図的にブロックさせ、その間に `tls.Conn` の `Close` メソッドが呼び出されたときに、`Close` がブロックせずに `Write` を中断し、リソースを解放することを確認します。これにより、ネットワーク問題時のハングアップが解消されることが検証されます。

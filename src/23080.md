## 元コミット内容

このコミットの目的は、Goプログラムがホスト名を解決する際に、Cgo（C言語のコードをGoから呼び出すメカニズム）を介したlibc（C標準ライブラリ）のDNSリゾルバの使用を可能な限り避け、Goネイティブのリゾルバを優先することです。従来のGoのDNS解決は、システムのリゾルバ設定が複雑な場合や、特定の機能（例: mDNS）に依存する場合に、libcの`getaddrinfo`関数などをCgo経由で呼び出す必要がありました。しかし、このアプローチには以下の問題がありました。

1.  **Cgoオーバーヘッド**: Cgo呼び出しは、GoとCのランタイム間のコンテキストスイッチを伴い、パフォーマンスオーバーヘッドが発生します。
2.  **スレッドブロック**: libcのDNSリゾルバは通常、ブロッキングI/Oを使用するため、各DNSリクエストがGoのOSスレッドをブロックする可能性がありました。これにより、多数の同時DNSリクエストが発生した場合に、Goランタイムが利用可能なスレッドを使い果たし、デッドロックやパフォーマンス低下を引き起こすリスクがありました。
3.  **同時リクエスト数の制限**: 以前のGoのCgoルックアップには、約500という同時DNSリクエスト数の上限がありました。この制限を超えると、リクエストがブロックされる可能性がありました。

このコミットは、これらの問題を解決し、Goアプリケーションがより効率的かつスケーラブルにDNS解決を行えるようにすることを目指しています。

## 変更の背景

Goのネットワークパッケージは、ホスト名の解決に際して、Goネイティブの実装とCgoを介したlibcの実装の2つのパスを持っていました。Goネイティブのリゾルバは、Goランタイム内で完全に非同期に動作するため、スレッドブロックの問題がなく、高い並行性を実現できます。しかし、libcのリゾルバは、`/etc/hosts`、`/etc/resolv.conf`、`/etc/nsswitch.conf`といったシステム設定ファイルをより詳細に解釈し、mDNS（Multicast DNS）のような特殊な解決メカニズムをサポートできるという利点がありました。

これまでのGoの設計では、システムのリゾルバ設定が少しでも複雑であったり、Goネイティブのリゾルバが完全にサポートしていない機能（例: `.local`ドメインのmDNS解決）が使われていると判断された場合、安全のためにCgoパスにフォールバックしていました。これは、Goネイティブのリゾルバがシステム設定を誤って解釈し、ホスト名の解決に失敗するリスクを避けるための保守的なアプローチでした。

しかし、この保守的なアプローチは、前述のCgoオーバーヘッド、スレッドブロック、同時リクエスト数の制限といったパフォーマンス上の問題を引き起こしていました。特に、多数のマイクロサービスが相互に通信するような現代のクラウドネイティブアプリケーションでは、大量のDNSリクエストが頻繁に発生するため、これらの問題は深刻でした。

このコミットは、システム設定ファイルをより賢く解析し、Goネイティブのリゾルバで安全に処理できると判断された場合にのみ、Goネイティブのリゾルバを優先的に使用するように変更することで、このトレードオフを改善しようとしています。これにより、Goアプリケーションは、システム設定の互換性を保ちつつ、より高いパフォーマンスとスケーラビリティでDNS解決を行えるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のシステム設定ファイルと概念についての知識が必要です。

1.  **`/etc/resolv.conf`**:
    *   Unix系システムにおけるDNSリゾルバの設定ファイルです。
    *   DNSサーバーのアドレス（`nameserver`）、検索ドメイン（`search`）、ドットの数（`ndots`）、タイムアウト（`timeout`）、リトライ回数（`attempts`）、ラウンドロビン（`rotate`）などのオプションが記述されます。
    *   GoのネイティブDNSリゾルバは、このファイルを解析してDNSクエリの挙動を決定します。
    *   OpenBSDでは、`lookup`という特別なキーワードがあり、ホスト名の解決順序（例: `file bind`で`/etc/hosts`の後にDNSを検索）を指定できます。

2.  **`/etc/nsswitch.conf` (Name Service Switch configuration file)**:
    *   Unix系システムにおいて、様々な「名前サービス」（ホスト名、パスワード、グループなど）の解決にどのソース（ファイル、DNS、NIS、LDAPなど）をどのような順序で使用するかを定義するファイルです。
    *   特に`hosts:`エントリは、ホスト名の解決順序を決定します。例えば、`hosts: files dns`は、まず`/etc/hosts`ファイルを検索し、次にDNSを検索することを意味します。
    *   各ソースには、`[status=action]`形式の「基準（criteria）」を付加できます。例えば、`[NOTFOUND=return]`は、前のソースでエントリが見つからなかった場合に、それ以上検索せずにすぐに結果を返すことを意味します。
    *   `mdns4`や`mdns4_minimal`といったソースは、mDNS（Multicast DNS）によるローカルネットワーク内のホスト名解決に使用されます。`.local`ドメインのホスト名解決によく使われます。

3.  **Cgo**:
    *   Go言語の機能の一つで、C言語の関数やライブラリをGoコードから呼び出すことを可能にします。
    *   Goの`net`パッケージでは、システム固有のDNS解決機能（特に複雑な`/etc/nsswitch.conf`のルールやmDNSなど）を利用するために、libcの`getaddrinfo`関数などをCgo経由で呼び出すことがありました。
    *   Cgo呼び出しは、GoランタイムとCランタイム間のスタック切り替えやコンテキストスイッチを伴うため、純粋なGoコードに比べてパフォーマンスオーバーヘッドが発生します。また、CコードがブロッキングI/Oを行う場合、Goのゴルーチンがブロックされ、OSスレッドが消費される問題があります。

4.  **DNS解決の順序**:
    *   ホスト名をIPアドレスに解決する際、システムは通常、複数の情報源を定義された順序で検索します。一般的な順序は以下の通りです。
        *   **`files`**: `/etc/hosts`ファイル。静的なホスト名とIPアドレスのマッピングが記述されています。
        *   **`dns`**: DNSサーバー。インターネット上のホスト名解決に利用されます。
        *   **`mdns`**: mDNS。ローカルネットワーク内のホスト名解決に利用されます。

これらの前提知識を踏まえることで、Goがどのようにシステム設定を解析し、Cgoの使用を最適化しようとしているのかを深く理解できます。

## 技術的詳細

このコミットの核心は、Goがシステムのリゾルバ設定をよりインテリジェントに解析し、Goネイティブのリゾルバで安全に処理できるかどうかを判断するロジックを導入した点にあります。

主要な変更点は以下の通りです。

1.  **`conf`構造体の導入 (`src/net/conf.go`)**:
    *   システム全体のネットワーク設定を表現する`conf`構造体が新しく導入されました。これには、Cgoの使用を強制するかどうか（`forceCgoLookupHost`）、`/etc/mdns.allow`ファイルの存在（`hasMDNSAllow`）、解析された`nsswitch.conf`（`nss`）、解析された`resolv.conf`（`resolv`）などの情報が含まれます。
    *   `systemConf()`関数は、この`conf`構造体を一度だけ初期化し、システム設定を読み込みます。
    *   初期化ロジックでは、以下の条件でCgoの使用を強制します。
        *   OSがmacOS（`darwin`）の場合: macOSは独自のDNSダイアログを出すため、libcに任せるのが安全。
        *   `RES_OPTIONS`、`HOSTALIASES`、`LOCALDOMAIN`などの環境変数が設定されている場合: これらの環境変数はlibcリゾルバの挙動に影響を与えるため、Goネイティブでは完全に再現が難しい。
        *   OpenBSDで`ASR_CONFIG`環境変数が設定されている場合: `resolv.conf`の場所が変更されている可能性があるため。
        *   `/etc/resolv.conf`の読み込みに失敗した場合（ファイルが存在しない場合を除く）: 設定ファイルが壊れている可能性があり、libcに任せるのが安全。
        *   `/etc/mdns.allow`ファイルが存在する場合: mDNSの挙動が複雑になる可能性があるため。

2.  **`hostLookupOrder`の導入と決定ロジック (`src/net/dnsclient_unix.go`, `src/net/conf.go`)**:
    *   `hostLookupOrder`という新しい型が導入され、ホスト名解決の戦略（`hostLookupCgo`, `hostLookupFilesDNS`, `hostLookupDNSFiles`, `hostLookupFiles`, `hostLookupDNS`）を表現します。
    *   `conf.hostLookupOrder(hostname string)`メソッドが、与えられたホスト名とシステム設定に基づいて、最適な`hostLookupOrder`を決定します。
    *   このメソッドは、`/etc/nsswitch.conf`の`hosts`エントリを解析し、`files`、`dns`、`mdns`などのソースの順序と、各ソースに付随する基準（`[NOTFOUND=return]`など）を考慮します。
    *   Goネイティブのリゾルバが処理できない複雑な設定（例: `myhostname`のようなGoがサポートしないNSSソース、非標準の基準、`.local`ドメイン以外のmDNSソース、特殊な文字を含むホスト名）が検出された場合、`hostLookupCgo`を返してCgoにフォールバックします。
    *   OpenBSDの`resolv.conf`の`lookup`キーワードも特別に処理され、その設定に基づいて`hostLookupOrder`が決定されます。

3.  **`/etc/nsswitch.conf`の解析 (`src/net/nss.go`)**:
    *   `nssConf`構造体と`parseNSSConf`関数が新しく導入され、`/etc/nsswitch.conf`ファイルを解析します。
    *   このパーサーは、`hosts:`エントリだけでなく、他のデータベース（`passwd`, `group`など）も解析し、各ソースとその基準（`[NOTFOUND=return]`など）を抽出します。
    *   `nssSource.standardCriteria()`メソッドは、特定のソースに付随する基準がGoネイティブで安全に処理できる標準的なものであるかどうかを判断します。

4.  **`/etc/resolv.conf`の解析強化 (`src/net/dnsconfig_unix.go`)**:
    *   `dnsConfig`構造体に`unknownOpt`と`lookup`フィールドが追加されました。
    *   `dnsReadConfig`関数は、`resolv.conf`内の未知のオプションやOpenBSDの`lookup`キーワードを検出した場合に`unknownOpt`を`true`に設定します。これにより、Goネイティブのリゾルバが安全に処理できない可能性を検出し、Cgoへのフォールバックを促します。

5.  **DNSルックアップ関数の変更 (`src/net/dnsclient_unix.go`, `src/net/lookup_unix.go`)**:
    *   `lookupHost`と`lookupIP`関数は、まず`systemConf().hostLookupOrder(host)`を呼び出して、どの解決戦略を使用すべきかを決定します。
    *   結果が`hostLookupCgo`であればCgoパスを試み、Cgoが利用できない場合（例: `netgo`ビルドタグが使用されている場合）はGoネイティブにフォールバックします。
    *   それ以外の`hostLookupOrder`（`files,dns`など）であれば、`goLookupHostOrder`や`goLookupIPOrder`といったGoネイティブの関数が、指定された順序で`/etc/hosts`とDNSを検索します。

これらの変更により、Goはシステムのリゾルバ設定をより正確に理解し、Goネイティブのリゾルバで安全に処理できる場合にのみそれを使用することで、Cgoへの依存を減らし、DNS解決のパフォーマンスとスケーラビリティを向上させています。

## コアとなるコードの解説

### `src/net/conf.go` の `hostLookupOrder` メソッド

```go
// hostLookupOrder determines which strategy to use to resolve hostname.
func (c *conf) hostLookupOrder(hostname string) hostLookupOrder {
	if c.forceCgoLookupHost {
		return hostLookupCgo
	}
	// ... (特殊なホスト名やOpenBSDの処理) ...

	// /etc/nsswitch.conf の解析結果に基づいて順序を決定
	nss := c.nss
	srcs := nss.sources["hosts"]

	// nsswitch.conf が存在しないか、hosts のソースが指定されていない場合
	if os.IsNotExist(nss.err) || (nss.err == nil && len(srcs) == 0) {
		// OSごとのデフォルトの挙動
		if c.goos == "solaris" {
			return hostLookupCgo // Solarisはデフォルトでlibcに任せる
		}
		if c.goos == "linux" {
			// glibcのデフォルトは "dns [!UNAVAIL=return] files"
			return hostLookupDNSFiles
		}
		return hostLookupFilesDNS // その他のOSのデフォルト
	}
	if nss.err != nil {
		// nsswitch.conf の解析に失敗した場合、Cgoにフォールバック
		return hostLookupCgo
	}

	var mdnsSource, filesSource, dnsSource bool
	var first string
	for _, src := range srcs {
		// Goが扱えないNSSソースや非標準の基準があればCgoにフォールバック
		if src.source == "myhostname" { /* ... */ return hostLookupCgo }
		if !src.standardCriteria() { return hostLookupCgo }
		// ... (mdnsソースの検出) ...
	}

	// Goネイティブで処理できるケース
	switch {
	case filesSource && dnsSource:
		if first == "files" {
			return hostLookupFilesDNS
		} else {
			return hostLookupDNSFiles
		}
	case filesSource:
		return hostLookupFiles
	case dnsSource:
		return hostLookupDNS
	}

	// それ以外はCgoにフォールバック
	return hostLookupCgo
}
```
この関数は、ホスト名解決の最も重要な決定ロジックを含んでいます。まず、`forceCgoLookupHost`フラグが設定されている場合は無条件にCgoを使用します。次に、OpenBSDの特殊な`resolv.conf`設定や、バックスラッシュやパーセント記号を含む特殊なホスト名を処理します。

その後、`/etc/nsswitch.conf`の`hosts`エントリを解析し、`files`、`dns`、`mdns`などのソースの有無と順序、および各ソースに付随する基準（`[NOTFOUND=return]`など）を評価します。Goネイティブのリゾルバが安全に処理できないと判断された場合（例: `myhostname`のようなGoがサポートしないNSSソース、非標準の基準、`.local`ドメイン以外のmDNSソース）、`hostLookupCgo`を返してCgoにフォールバックします。

Goネイティブで処理できると判断された場合は、`files`と`dns`の組み合わせと順序に基づいて、`hostLookupFilesDNS`、`hostLookupDNSFiles`、`hostLookupFiles`、`hostLookupDNS`のいずれかを返します。これにより、Goはシステム設定に合わせた最適なDNS解決戦略を動的に選択できるようになります。

### `src/net/nss.go` の `parseNSSConf` 関数

```go
func parseNSSConf(r io.Reader) *nssConf {
	slurp, err := readFull(r)
	if err != nil {
		return &nssConf{err: err}
	}
	conf := new(nssConf)
	conf.err = foreachLine(slurp, func(line []byte) error {
		line = trimSpace(removeComment(line))
		if len(line) == 0 {
			return nil
		}
		colon := bytesIndexByte(line, ':')
		if colon == -1 {
			return errors.New("no colon on line")
		}
		db := string(trimSpace(line[:colon])) // データベース名 (e.g., "hosts")
		srcs := line[colon+1:]               // ソースリスト (e.g., "files mdns4_minimal [NOTFOUND=return] dns mdns4")
		for {
			srcs = trimSpace(srcs)
			if len(srcs) == 0 {
				break
			}
			sp := bytesIndexByte(srcs, ' ')
			var src string
			if sp == -1 {
				src = string(srcs)
				srcs = nil
			} else {
				src = string(srcs[:sp])
				srcs = trimSpace(srcs[sp+1:])
			}
			var criteria []nssCriterion
			// 基準ブロック (例: "[!a=b X=Y]") の解析
			if len(srcs) > 0 && srcs[0] == '[' {
				bclose := bytesIndexByte(srcs, ']')
				if bclose == -1 {
					return errors.New("unclosed criterion bracket")
				}
				var err error
				criteria, err = parseCriteria(srcs[1:bclose])
				if err != nil {
					return errors.New("invalid criteria: " + string(srcs[1:bclose]))
				}
				srcs = srcs[bclose+1:]
			}
			if conf.sources == nil {
				conf.sources = make(map[string][]nssSource)
			}
			conf.sources[db] = append(conf.sources[db], nssSource{
				source:   src,
				criteria: criteria,
			})
		}
		return nil
	})
	return conf
}
```
この関数は、`/etc/nsswitch.conf`ファイルを読み込み、その内容を`nssConf`構造体に解析します。各行をデータベース名（例: `hosts`）とそれに続くソースのリストに分割します。さらに、各ソースに付随するオプションの基準ブロック（例: `[NOTFOUND=return]`）も解析し、`nssCriterion`構造体のスライスとして格納します。この詳細な解析により、Goはシステムがホスト名解決にどのようなソースとルールを使用しているかを正確に把握し、Goネイティブのリゾルバで処理できるかどうかを判断するための情報を提供します。

### `src/net/lookup_unix.go` の `lookupHost` 関数

```go
func lookupHost(host string) (addrs []string, err error) {
	order := systemConf().hostLookupOrder(host) // ここで解決順序を決定
	if order == hostLookupCgo {
		if addrs, err, ok := cgoLookupHost(host); ok {
			return addrs, err
		}
		// cgo が利用できない場合 (netgo など)、Goネイティブのデフォルトにフォールバック
		order = hostLookupFilesDNS
	}
	return goLookupHostOrder(host, order) // Goネイティブのリゾルバを呼び出す
}
```
この`lookupHost`関数は、GoのDNS解決フローのエントリポイントの一つです。まず、`systemConf().hostLookupOrder(host)`を呼び出して、現在のシステム設定とホスト名に基づいて最適な解決順序（`hostLookupOrder`）を決定します。

もし決定された順序が`hostLookupCgo`であれば、`cgoLookupHost`（Cgoを介したlibcリゾルバ）を試みます。`cgoLookupHost`が成功すればその結果を返しますが、Cgoが利用できない場合（例えば、`netgo`ビルドタグでコンパイルされた場合など）は、Goネイティブのデフォルト順序である`hostLookupFilesDNS`にフォールバックします。

最終的に、`goLookupHostOrder(host, order)`を呼び出して、Goネイティブのリゾルバに実際の解決処理を委ねます。この関数は、決定された`order`に基づいて、`/etc/hosts`とDNSのどちらを先に検索するかを制御します。

この変更により、Goはシステム設定を動的に評価し、Cgoのオーバーヘッドを回避できる場合はGoネイティブのリゾルバを優先的に使用するようになりました。これにより、DNS解決のパフォーマンスとスケーラビリティが向上します。

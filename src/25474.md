# [インデックス 25474] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるマーキングフェーズに関連する`src/runtime/mgcmark.go`ファイルに対する変更です。具体的には、GCアシストの動作を改善し、プリエンプション（横取り）可能にすることで、GCの効率性とアプリケーションの応答性を向上させることを目的としています。

## 変更の背景

Goのガベージコレクション（GC）は、アプリケーションの実行と並行して動作する「コンカレントGC」を採用しています。しかし、GCがオブジェクトをスキャンしてマークする際に、アプリケーションのゴルーチン（mutator Gs）がGCの進行を「アシスト」することがあります。これは、GCが追いつかない場合に、mutatorが自身のメモリ割り当てを続行するために、GC作業の一部を肩代わりするメカニズムです。

このコミット以前は、GCアシスト中のゴルーチンはプリエンプション（横取り）不可能でした。これは以下の問題を引き起こしていました。

1.  **他のゴルーチンのブロック**: 大量のアシストを行うゴルーチン（`heavily assisting G`）が、長時間CPUを占有し、他の実行可能なゴルーチンがスケジュールされるのを妨げていました。これにより、アプリケーション全体の応答性が低下する可能性がありました。
2.  **`scang`の遅延**: GCサイクルの開始時、GCのマークフェーズを主導する`scang`（スキャナーゴルーチン）が、アシスト中のゴルーチンが完了するまで待機（スピン）する必要がありました。`scang`はGCの進行において重要な役割を果たすため、その遅延はGCのマークフェーズ全体の期間を著しく延長させていました。特に、当時のスキャン処理がシーケンシャルに行われていたため、この影響はより顕著でした。
3.  **ワークバッファ拡張の阻害**: GCアシストがプリエンプション不可能であることは、GCが使用するワークバッファ（GC作業を一時的に保持するメモリ領域）を拡大する上での障壁となっていました。ワークバッファを大きくすることでGCの効率を向上させる可能性がありますが、プリエンプションができないと、ワークバッファが大きくなるほど`scang`の遅延やスピンが増加するという問題が生じていました。

このコミットは、これらの問題を解決し、GCアシスト中のゴルーチンもプリエンプション可能にすることで、GCの効率とアプリケーションの応答性を改善することを目的としています。

## 前提知識の解説

### Goランタイムとスケジューラ

*   **Goroutine (G)**: Goにおける軽量な実行単位。OSのスレッドよりもはるかに軽量で、数百万個作成することも可能です。Goランタイムのスケジューラによって管理されます。
*   **M (Machine)**: OSのスレッドに対応します。GoランタイムはM上でGを実行します。
*   **P (Processor)**: 論理的なプロセッサを表します。MはPにアタッチされ、Pは実行可能なGのキューを保持します。Goスケジューラは、PにアタッチされたM上でGを実行します。
*   **プリエンプション (Preemption)**: Goランタイムは、長時間実行されるゴルーチンがCPUを独占するのを防ぐために、プリエンプション機構を持っています。これにより、他のゴルーチンも公平にCPU時間を獲得できます。Go 1.4から非同期プリエンプションが導入され、Go 1.14からはより正確な非同期プリエンプションが可能になりました。しかし、特定の状況下（例えばシステムコール中やGCアシスト中）では、プリエンプションが困難な場合があります。

### Goのガベージコレクション (GC)

GoのGCは、主に以下のフェーズで構成される「トライカラーマーク＆スイープ」アルゴリズムをベースにしたコンカレントGCです。

*   **マークフェーズ (Mark Phase)**:
    *   **マーク準備 (Mark Setup)**: 短いSTW (Stop The World) フェーズ。GCを開始するための初期設定を行います。
    *   **コンカレントマーク (Concurrent Mark)**: アプリケーションの実行と並行して、到達可能なオブジェクトをマークします。このフェーズで、mutator GsがGCアシストを行うことがあります。
    *   **マーク終了 (Mark Termination)**: 短いSTWフェーズ。マークフェーズを終了し、次のスイープフェーズの準備をします。
*   **スイープフェーズ (Sweep Phase)**: マークされなかった（到達不能な）オブジェクトが解放されます。これもコンカレントに行われます。

### GCアシスト (GC Assists)

GoのコンカレントGCでは、アプリケーションのゴルーチン（mutator Gs）がメモリを割り当てようとした際に、GCが十分な速度でマーク作業を進められていない場合、そのmutator G自身がGC作業の一部を手伝うことがあります。これが「GCアシスト」です。これにより、GCの進行を加速させ、メモリ割り当ての遅延を防ぎます。アシストは、mutatorが割り当てたメモリ量に応じて、GCに貢献すべき作業量が計算され、その作業量を達成するまでGC作業を行います。

### `gcDrainN`関数

`gcDrainN`関数は、GCのマークフェーズにおいて、特定の量のスキャン作業（`scanWork`）を実行するために使用される内部関数です。この関数は、GCワークバッファからオブジェクトを取り出し、それらをスキャンしてマークする処理を行います。

### GCワークバッファ (GC Work Buffers)

GCは、マーク作業中に発見した「グレイオブジェクト」（まだスキャンされていないが、到達可能であることが分かっているオブジェクト）を一時的に保存するためのワークバッファを使用します。これらのバッファは、GCワーカーゴルーチンやGCアシストを行うmutatorゴルーチンによって共有され、GC作業の効率的な分散処理を可能にします。

### システムスタックとゴルーチンスタック

Goのゴルーチンは、通常、比較的小さな「ゴルーチンスタック」を使用します。しかし、特定のランタイム関数（例えば、システムコールを行う関数やGCの低レベルな処理を行う関数）は、より大きな「システムスタック」に切り替えて実行されることがあります。システムスタックで実行されている間は、通常のゴルーチンスタックのプリエンプションメカニズムが適用されにくいという特性があります。

## 技術的詳細

このコミットの核心は、GCアシストを協調的プリエンプション（cooperative preemption）可能にすることです。これは、アシスト中のゴルーチンが自らプリエンプションポイントを認識し、スケジューラに制御を返すことで実現されます。

1.  **プリエンプションポイントの導入**: `gcDrainN`関数のループ条件に`!gp.preempt`が追加されました。`gp.preempt`は、現在のゴルーチン（`gp`）がプリエンプションを要求されているかどうかを示すフラグです。このフラグがセットされると、`gcDrainN`は現在のスキャン作業を中断し、ループを抜けます。
2.  **システムスタックからの復帰と`Gosched()`**: コミットメッセージによると、アシストはワークバッファを保持し、システムスタックで実行されるため、通常のプリエンプションが困難でした。この変更では、`gcDrainN`がプリエンプションによって早期にリターンした後、アシストを行っていたゴルーチンはシステムスタックから通常のゴルーチンスタックに戻り、自発的に`Gosched()`を呼び出します。`Gosched()`は、現在のゴルーチンを一時停止し、他の実行可能なゴルーチンにCPUを譲る関数です。これにより、アシスト中のゴルーチンがCPUを独占するのを防ぎ、他のゴルーチンが実行される機会を得られます。
3.  **`retry`ラベルと`Gosched()`**: `src/runtime/mgcmark.go`の変更箇所を見ると、GCアシストがメモリ割り当てを試みる部分で、`gp.preempt`が真の場合に`Gosched()`を呼び出し、その後`goto retry`で再度アシスト処理を試みるロジックが追加されています。これは、プリエンプションされた後も、GCアシストの必要性が残っていれば、再度アシストを試みることを意味します。しかし、一度`Gosched()`を呼び出すことで、他のゴルーチンに実行機会を与え、GCの全体的な進行を妨げないようにします。
4.  **`getg().m.curg`の使用**: `gcDrainN`内で現在のゴルーチン（`gp`）の`preempt`フラグにアクセスするために、`getg().m.curg`が使用されています。`getg()`は現在のゴルーチン構造体へのポインタを返し、`.m.curg`は現在のM（OSスレッド）が実行しているゴルーチンを指します。これにより、正確に現在のゴルーチンのプリエンプション状態をチェックできます。

この変更により、GCアシストが長時間にわたってCPUを占有することがなくなり、`scang`の遅延が解消され、GCのマークフェーズがよりスムーズに進行するようになります。また、将来的にワークバッファを拡大する際の基盤も築かれました。ベンチマーク結果（`XBenchGarbage-12`で6.11%の改善）は、この変更がGCのパフォーマンスに良い影響を与えていることを示しています。

`gcDrainN`関数のコメントが更新され、この関数が`scanWork`単位のスキャン作業を実行するか、**またはゴルーチンがプリエンプションされた場合**に終了するようになったことが明記されました。これにより、関数の新しい動作が正確に反映されています。


*   `gp := getg().m.curg`: 現在実行中のゴルーチン（`g`）を取得し、その`m`（OSスレッド）が現在実行しているゴルーチン（`curg`）へのポインタを`gp`変数に代入しています。これにより、現在のゴルーチンの状態にアクセスできるようになります。

### 3. GCアシストの再試行ロジックの追加

```diff
--- a/src/runtime/mgcmark.go
+++ b/src/runtime/mgcmark.go
@@ -440,6 +440,13 @@ retry:
 		// do one of these before letting the mutator allocate
 		// more to prevent over-allocation.
 		//
+		// If this is because we were preempted, reschedule
+		// and try some more.
+		if gp.preempt {
+			Gosched()
+			goto retry
+		}
+
 		// Add this G to an assist queue and park. When the GC
 		// has more background credit, it will satisfy queued
 		// assists before flushing to the global credit pool.
```
これは、GCアシストが必要な状況（mutatorがメモリを割り当てようとしているが、GCが追いついていない状況）で、アシストを行うゴルーチンがプリエンプションされた場合の処理です。
*   `if gp.preempt { ... }`: もし現在のゴルーチン（`gp`）がプリエンプションを要求されている場合、以下の処理が実行されます。
*   `Gosched()`: 現在のゴルーチンを一時停止し、Goスケジューラに制御を戻します。これにより、他の実行可能なゴルーチンがCPU時間を獲得できるようになります。これは協調的プリエンプションの重要な部分です。
*   `goto retry`: `Gosched()`によって他のゴルーチンに実行機会を与えた後、再度`retry`ラベルに戻り、GCアシストの処理を試みます。これにより、プリエンプションによってアシストが中断されても、必要であれば後で再開されることが保証されます。

これらの変更により、GCアシスト中のゴルーチンがプリエンプション可能になり、Goランタイムのスケジューラがより公平にCPU時間を分配できるようになりました。結果として、GCの効率が向上し、アプリケーションのレイテンシが改善されることが期待されます。

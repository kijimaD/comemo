## 変更の背景

Go言語の初期段階では、エラーは主に `os.NewError` 関数によって生成される `os._Error` 型のインスタンスとして扱われていました。この `_Error` 型は、エラーメッセージを保持する文字列フィールドを持つシンプルな構造体でした。しかし、このアプローチにはいくつかの課題がありました。

1.  **エラーの識別**: 全てのエラーが同じ `_Error` 型であるため、エラーの種類を識別するためにはエラーメッセージの文字列を比較するしかありませんでした。これは、エラーメッセージが変更されるとコードが壊れる可能性があり、堅牢性に欠けます。
2.  **エラー情報の不足**: `_Error` 型は単一の文字列しか保持できないため、より詳細なエラー情報（例えば、エラーコード、発生源、ラップされた元のエラーなど）を伝えることが困難でした。
3.  **Goのインターフェースの活用**: Go言語の強力な機能であるインターフェースをエラーハンドリングに活用できていませんでした。Goでは、`error` インターフェース（`Error() string` メソッドを持つ）を実装する任意の型をエラーとして扱うことができます。この柔軟性を活かすことで、より表現力豊かで型安全なエラーハンドリングが可能になります。

このコミットは、これらの課題を解決し、Go言語の設計哲学に沿ったエラーハンドリングの方向性を示すための重要な一歩でした。具体的には、`os._Error` のような汎用的なエラー型に依存するのではなく、各パッケージがそのパッケージ固有のエラーを表現するためのカスタムエラー型を定義することを推奨しています。これにより、エラーを型で識別し、必要に応じて追加の情報を構造体として持たせることが可能になります。

### Go言語におけるエラーハンドリングの基本

Go言語には、例外処理のための `try-catch` のような構文はありません。その代わりに、関数がエラーを返す場合は、戻り値の最後の要素として `error` 型の値を返します。慣例として、エラーがない場合は `nil` を返します。

```go
func doSomething() (resultType, error) {
    // ... 処理 ...
    if somethingWentWrong {
        return zeroValue, errors.New("something went wrong") // またはカスタムエラー型
    }
    return actualResult, nil
}
```

`error` はGoの組み込みインターフェースであり、以下のように定義されています。

```go
type error interface {
    Error() string
}
```

このインターフェースを実装する任意の型は、エラーとして扱うことができます。

### `os.NewError` と `os._Error` (コミット以前)

このコミット以前のGo言語の初期バージョンでは、`os` パッケージに `NewError` 関数と `_Error` 型が存在しました。

-   `os._Error`: エラーメッセージを保持する内部的な構造体。
-   `os.NewError(s string) Error`: 文字列 `s` を受け取り、`_Error` 型のインスタンスを返す関数。この関数は、同じ文字列に対しては同じ `_Error` インスタンスを返すようにキャッシュメカニズムを持っていました。

この仕組みは、エラーを文字列として比較することで識別するという、C言語のようなアプローチに近いものでした。

### 型によるエラー識別への移行

このコミットは、エラーを文字列ではなく型で識別するという、Go言語の現在のエラーハンドリングの基礎を築くものです。これにより、以下のようなメリットが生まれます。

-   **型アサーションによるエラーの識別**: `err, ok := someError.(*MyCustomError)` のように、型アサーションを使って特定のエラー型であるかをチェックできます。これにより、エラーメッセージの文字列に依存することなく、エラーの種類を確実に識別できます。
-   **エラー情報のカプセル化**: カスタムエラー型は、エラーメッセージだけでなく、エラーコード、タイムスタンプ、元のエラーなど、追加の情報をフィールドとして持つことができます。これにより、よりリッチなエラー情報を提供できます。
-   **インターフェースの活用**: `error` インターフェースを実装することで、カスタムエラー型も汎用的な `error` 型として扱うことができ、柔軟なエラーハンドリングロジックを構築できます。

## 技術的詳細

このコミットの技術的な核心は、`os/error.go` から `_Error` 型とそれに関連する `NewError` 関数の古い実装を削除し、代わりに各パッケージが `error` インターフェースを実装する独自の型を定義するように変更した点にあります。

具体的には、以下の変更が行われています。

1.  **`os/error.go` の変更**:
    *   古い `type _Error struct { s string }` の定義と、それに関連する `NewError` 関数、`errorStringTab` (エラー文字列のキャッシュ) が削除されました。
    *   新しい `NewError` 関数が追加されましたが、これは単に `ErrorString(s)` を返すシンプルなヘルパー関数であり、`ErrorString` は `string` 型に `Error()` メソッドを追加したものです。これは、文字列リテラルを直接 `error` インターフェースとして扱えるようにするための過渡的な措置と考えられます。
    *   `ErrorString` 型が `Error()` メソッドを実装することで、`string` 型も `error` インターフェースを満たすようになりました。

2.  **各パッケージでのカスタムエラー型の導入**:
    *   `src/lib/bufio/bufio.go`: `bufio.Error` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。そして、`PhaseError`, `BufferFull` などのパッケージ固有のエラー変数が、この `bufio.Error` 型のインスタンスとして定義されるようになりました。
    *   `src/lib/http/request.go`: `http.ProtocolError` という新しい型が導入され、同様に `os.ErrorString` を埋め込んでいます。
    *   `src/lib/http/url.go`: `http.BadURL` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。`ParseURL` 関数内で `BadURL` のインスタンスが直接生成されるようになりました。
    *   `src/lib/io/io.go`: `io.Error` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。`ErrEOF` がこの型のインスタンスとして定義されました。
    *   `src/lib/net/dnsclient.go`: `net.DNSError` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。
    *   `src/lib/net/net.go`: `net.Error` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。
    *   `src/lib/net/parse.go`: `net.Error` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。
    *   `src/lib/net/port.go`: `net.Error` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。

3.  **`os.NewError` の呼び出し箇所の変更**:
    *   以前 `os.NewError("some error")` のようにエラーを生成していた箇所が、新しく定義されたカスタムエラー型のインスタンスを直接生成するように変更されました。例えば、`&Error{"phase error"}` のように、構造体リテラルを使ってエラーインスタンスを作成しています。

4.  **`src/lib/net/Makefile` の変更**:
    *   ビルドシステム関連の変更で、`fd.o` と `fd_$(GOOS).o` のリンケージ順序が調整されています。これはエラーハンドリングの変更に直接関連するものではなく、依存関係の整理の一環と考えられます。

この変更により、Go言語のエラーハンドリングは、文字列ベースの比較から型ベースの識別へと大きく舵を切りました。これは、Go言語がその後のバージョンで `errors.Is` や `errors.As` といった関数を導入し、エラーの比較やアンラップをより柔軟に行えるようにする基盤となりました。

このコミットの核心は、Go言語のエラーハンドリングのパラダイムシフトにあります。

1.  **`os._Error` の廃止**:
    *   以前の `os._Error` は、エラーメッセージを文字列として保持し、`os.NewError` を通じてシングルトンとして管理されていました。これは、エラーを文字列の同一性で比較するという、Goのインターフェースの柔軟性を十分に活用しないアプローチでした。
    *   このコミットにより、`_Error` 型と、その背後にあるエラー文字列のキャッシュメカニズムが完全に削除されました。これにより、エラーはもはやグローバルなシングルトンとして管理されるのではなく、各エラー発生時に新しいインスタンスが作成されるようになります。

2.  **パッケージ固有のカスタムエラー型の導入**:
    *   `bufio`, `http`, `io`, `net` といった各パッケージで、`Error` や `ProtocolError`, `BadURL`, `DNSError` といった独自の構造体型が導入されました。これらの型は、`os.ErrorString` を埋め込むことで、`Error()` string メソッドを自動的に継承し、`error` インターフェースを満たします。
    *   `os.ErrorString` は、`string` 型に `Error()` メソッドを追加したもので、文字列リテラルを直接 `error` インターフェースとして扱えるようにするためのものです。これは、Goのエラーハンドリングが進化する過程での中間的なステップであり、最終的には `errors.New("message")` のように、`string` を直接 `error` に変換するのではなく、`errors` パッケージのヘルパー関数を使う形に落ち着きます。
    *   これらのカスタムエラー型は、エラーメッセージを保持するだけでなく、将来的にはエラーコードや追加情報など、よりリッチなコンテキストをカプセル化するための基盤となります。

3.  **エラー生成方法の変更**:
    *   以前は `os.NewError("some message")` としていた箇所が、`&MyCustomError{"some message"}` のように、カスタムエラー型のポインタを直接生成する形に変わりました。これにより、エラーの生成と同時にその型が明確になり、型アサーションによるエラーの識別が可能になります。

この変更は、Go言語がエラーを単なる文字列ではなく、型として扱うことで、より堅牢で表現力豊かなエラーハンドリングを実現するための重要なマイルストーンでした。これにより、開発者はエラーの種類に基づいて異なる処理を行ったり、エラーに付随する追加情報にアクセスしたりすることが容易になりました。これは、現在のGo言語におけるエラーハンドリングのベストプラクティス（`errors.Is`, `errors.As`, カスタムエラー型）の基礎を築いたと言えます。

このコミットは、エラーを文字列ではなく型で識別するという、Go言語の現在のエラーハンドリングの基礎を築くものです。これにより、以下のようなメリットが生まれます。

-   **型アサーションによるエラーの識別**: `err, ok := someError.(*MyCustomError)` のように、型アサーションを使って特定のエラー型であるかをチェックできます。これにより、エラーメッセージの文字列に依存することなく、エラーの種類を確実に識別できます。
-   **エラー情報のカプセル化**: カスタムエラー型は、エラーメッセージだけでなく、エラーコード、タイムスタンプ、元のエラーなど、追加の情報をフィールドとして持つことができます。これにより、よりリッチなエラー情報を提供できます。
-   **インターフェースの活用**: `error` インターフェースを実装することで、カスタムエラー型も汎用的な `error` 型として扱うことができ、柔軟なエラーハンドリングロジックを構築できます。

## 技術的詳細

このコミットの技術的な核心は、`os/error.go` から `_Error` 型とそれに関連する `NewError` 関数の古い実装を削除し、代わりに各パッケージが `error` インターフェースを実装する独自の型を定義するように変更した点にあります。

具体的には、以下の変更が行われています。

1.  **`os/error.go` の変更**:
    *   古い `type _Error struct { s string }` の定義と、それに関連する `NewError` 関数、`errorStringTab` (エラー文字列のキャッシュ) が削除されました。
    *   新しい `NewError` 関数が追加されましたが、これは単に `ErrorString(s)` を返すシンプルなヘルパー関数であり、`ErrorString` は `string` 型に `Error()` メソッドを追加したものです。これは、文字列リテラルを直接 `error` インターフェースとして扱えるようにするための過渡的な措置と考えられます。
    *   `ErrorString` 型が `Error()` メソッドを実装することで、`string` 型も `error` インターフェースを満たすようになりました。

2.  **各パッケージでのカスタムエラー型の導入**:
    *   `src/lib/bufio/bufio.go`: `bufio.Error` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。そして、`PhaseError`, `BufferFull` などのパッケージ固有のエラー変数が、この `bufio.Error` 型のインスタンスとして定義されるようになりました。
    *   `src/lib/http/request.go`: `http.ProtocolError` という新しい型が導入され、同様に `os.ErrorString` を埋め込んでいます。
    *   `src/lib/http/url.go`: `http.BadURL` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。`ParseURL` 関数内で `BadURL` のインスタンスが直接生成されるようになりました。
    *   `src/lib/io/io.go`: `io.Error` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。`ErrEOF` がこの型のインスタンスとして定義されました。
    *   `src/lib/net/dnsclient.go`: `net.DNSError` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。
    *   `src/lib/net/net.go`: `net.Error` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。
    *   `src/lib/net/parse.go`: `net.Error` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。
    *   `src/lib/net/port.go`: `net.Error` という新しい型が導入され、`os.ErrorString` を埋め込んでいます。

3.  **`os.NewError` の呼び出し箇所の変更**:
    *   以前 `os.NewError("some error")` のようにエラーを生成していた箇所が、新しく定義されたカスタムエラー型のインスタンスを直接生成するように変更されました。例えば、`&Error{"phase error"}` のように、構造体リテラルを使ってエラーインスタンスを作成しています。

4.  **`src/lib/net/Makefile` の変更**:
    *   ビルドシステム関連の変更で、`fd.o` と `fd_$(GOOS).o` のリンケージ順序が調整されています。これはエラーハンドリングの変更に直接関連するものではなく、依存関係の整理の一環と考えられます。

この変更により、Go言語のエラーハンドリングは、文字列ベースの比較から型ベースの識別へと大きく舵を切りました。これは、Go言語がその後のバージョンで `errors.Is` や `errors.As` といった関数を導入し、エラーの比較やアンラップをより柔軟に行えるようにする基盤となりました。

## コアとなるコードの解説

このコミットの核心は、Go言語のエラーハンドリングのパラダイムシフトにあります。

1.  **`os._Error` の廃止**:
    *   以前の `os._Error` は、エラーメッセージを文字列として保持し、`os.NewError` を通じてシングルトンとして管理されていました。これは、エラーを文字列の同一性で比較するという、Goのインターフェースの柔軟性を十分に活用しないアプローチでした。
    *   このコミットにより、`_Error` 型と、その背後にあるエラー文字列のキャッシュメカニズムが完全に削除されました。これにより、エラーはもはやグローバルなシングルトンとして管理されるのではなく、各エラー発生時に新しいインスタンスが作成されるようになります。

2.  **パッケージ固有のカスタムエラー型の導入**:
    *   `bufio`, `http`, `io`, `net` といった各パッケージで、`Error` や `ProtocolError`, `BadURL`, `DNSError` といった独自の構造体型が導入されました。これらの型は、`os.ErrorString` を埋め込むことで、`Error()` string メソッドを自動的に継承し、`error` インターフェースを満たします。
    *   `os.ErrorString` は、`string` 型に `Error()` メソッドを追加したもので、文字列リテラルを直接 `error` インターフェースとして扱えるようにするためのものです。これは、Goのエラーハンドリングが進化する過程での中間的なステップであり、最終的には `errors.New("message")` のように、`string` を直接 `error` に変換するのではなく、`errors` パッケージのヘルパー関数を使う形に落ち着きます。
    *   これらのカスタムエラー型は、エラーメッセージを保持するだけでなく、将来的にはエラーコードや追加情報など、よりリッチなコンテキストをカプセル化するための基盤となります。

3.  **エラー生成方法の変更**:
    *   以前は `os.NewError("some message")` としていた箇所が、`&MyCustomError{"some message"}` のように、カスタムエラー型のポインタを直接生成する形に変わりました。これにより、エラーの生成と同時にその型が明確になり、型アサーションによるエラーの識別が可能になります。

この変更は、Go言語がエラーを単なる文字列ではなく、型として扱うことで、より堅牢で表現力豊かなエラーハンドリングを実現するための重要なマイルストーンでした。これにより、開発者はエラーの種類に基づいて異なる処理を行ったり、エラーに付随する追加情報にアクセスしたりすることが容易になりました。これは、現在のGo言語におけるエラーハンドリングのベストプラクティス（`errors.Is`, `errors.As`, カスタムエラー型）の基礎を築いたと言えます。

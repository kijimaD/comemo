# [インデックス 23240] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ（GC）における「マーク済みバイト数」と「スキャン作業量」の計算方法の誤りを修正するものです。特に、ルート（グローバル変数やスタック）からの到達可能なヒープオブジェクトのサイズを正確に計上することで、GCのトリガー頻度を最適化し、Go 1.4と比較して発生していたパフォーマンス低下を改善します。

## 変更の背景

Goのガベージコレクタ（GC）は、ヒープの使用状況に基づいて次のGCサイクルをいつ開始するかを決定します。この決定は、GCが「マーク」したライブオブジェクトの総バイト数に大きく依存します。このコミット以前のGoランタイムでは、GCのマークフェーズにおいて、ヒープ上のライブオブジェクトのサイズを正確に計上できていないという問題がありました。

具体的には、以下の2つの主要な問題がありました。

1.  **ポインタを含まないオブジェクトの誤った計上:** グローバル変数やスタックなどの「ルート」から到達可能なオブジェクトのうち、ポインタを含まない大きなデータ構造（例: `[]byte`）が、GCのマーク済みバイト数の合計に正しく加算されていませんでした。これは、ルートのスキャン後にマーク合計が誤ってゼロにリセットされていたためです。
2.  **ルート自体の誤った計上:** ヒープの一部ではないルート（スタックやグローバル変数そのもの）のバイト数が、誤ってマーク済みヒープサイズに加算される可能性がありました。

これらの誤った計上により、GCは実際のライブヒープサイズを過小評価していました。結果として、GCは必要以上に頻繁にトリガーされ、特にGo 1ベンチマークにおいて、Go 1.4と比較してパフォーマンスが低下する原因となっていました。コミットメッセージに記載されているように、256MBのグローバルな`[]byte`を持つベンチマークで顕著な遅延が発生していました。このコミットは、これらの会計上の誤りを修正し、GCの効率を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクタの基本的な動作と、いくつかの専門用語について知っておく必要があります。

*   **ガベージコレクタ (GC):** プログラムが動的に確保したメモリのうち、もはやプログラムから到達できない（参照されていない）メモリ領域を自動的に解放するシステムです。GoのGCは、並行マーク＆スイープ方式を採用しています。
*   **マーク＆スイープ (Mark and Sweep):** GCのアルゴリズムの一つで、主に以下の2つのフェーズから構成されます。
    *   **マークフェーズ (Mark Phase):** プログラムの実行を一時停止（または並行して）し、ルート（後述）から到達可能なすべてのオブジェクトを「ライブ」（生きている）としてマークします。
    *   **スイープフェーズ (Sweep Phase):** マークされなかった（到達不可能な）オブジェクトが占めるメモリ領域を解放し、再利用可能にします。
*   **ルート (Roots):** GCがライブオブジェクトを探索し始める起点となる参照のことです。Goにおいては、主に以下のものがルートとして扱われます。
    *   **グローバル変数:** プログラム全体からアクセス可能な変数。
    *   **スタック:** 各Goroutineの実行スタック上に存在するローカル変数や関数引数。
    *   **レジスタ:** CPUのレジスタに保持されている値。
*   **ヒープ (Heap):** プログラムが動的にメモリを確保する領域です。`make`や`new`で確保されるオブジェクトはヒープに配置されます。GCの主な対象はこのヒープ領域です。
*   **`gcw.bytesMarked`:** GCのマークフェーズ中に、ライブとしてマークされたヒープオブジェクトの総バイト数を追跡するためのカウンタです。この値は、次のGCサイクルをいつ開始するかを決定する重要な指標となります。
*   **`gcw.scanWork`:** GCがオブジェクトをスキャンするために費やした作業量を追跡するためのカウンタです。これもGCの進行状況を把握するために使用されます。
*   **ポインタフリーオブジェクト (Pointer-free objects):** そのオブジェクト自体が他のヒープオブジェクトへのポインタを含まないオブジェクトです。例えば、`[]byte`や`int`の配列などがこれに該当します。これらのオブジェクトは、それ自体がポインタを持たなくても、他のオブジェクトから参照されていればライブであり、GCの対象となります。

GoのGCは、`GOGC`環境変数や内部のヒューリスティックに基づいて、ヒープの使用量が一定の閾値を超えると次のGCサイクルを開始します。この閾値は、前回のGCでマークされたライブヒープサイズに基づいて計算されます。したがって、`gcw.bytesMarked`の正確な計上は、GCのトリガータイミングと全体的なパフォーマンスに直接影響します。

## 技術的詳細

このコミットは、Goランタイムのガベージコレクタ（GC）のマークフェーズにおける`gcw.bytesMarked`（マーク済みバイト数）と`gcw.scanWork`（スキャン作業量）の会計ロジックを修正します。

主要な変更点は以下の3つです。

1.  **ルートスキャン後の`gcw.bytesMarked`と`gcw.scanWork`のゼロクリアの廃止:**
    *   以前のコードでは、`markroot`関数（グローバル変数などのルートをスキャンする関数）および`scanstack`関数（Goroutineのスタックをスキャンする関数）の実行後に、`gcw.bytesMarked`と`gcw.scanWork`がゼロにリセットされていました。
    *   このリセットにより、ルートから到達可能なヒープオブジェクト（特にポインタを含まない大きな`[]byte`のようなオブジェクト）が正しくマーク済みバイト数に計上されず、GCがヒープサイズを過小評価していました。
    *   修正後は、これらのカウンタがリセットされなくなり、ルートスキャン中に見つかったライブヒープオブジェクトのバイト数とスキャン作業量が累積して計上されるようになります。これにより、実際のライブヒープサイズが正確に反映されます。

2.  **`scanblock`におけるルート自体のバイト数計上の廃止:**
    *   `scanblock`関数は、メモリブロックをスキャンしてポインタを見つけ、参照先のオブジェクトをマークする汎用的な関数です。
    *   以前のコードでは、この関数内で`gcw.bytesMarked += uint64(n)`という行があり、スキャン対象のブロックのサイズ`n`を無条件に`gcw.bytesMarked`に加算していました。
    *   問題は、この`scanblock`がルート（スタックやグローバル変数）をスキャンするためにも使用されていた点です。ルート自体はヒープの一部ではないため、そのバイト数をマーク済みヒープサイズに含めるのは誤りでした。
    *   このコミットでは、`gcw.bytesMarked += uint64(n)`の行が削除されました。これにより、`gcw.bytesMarked`は純粋にヒープ上のライブオブジェクトのサイズのみを計上するようになります。ルートスキャン中に`scanblock`が呼び出されても、ルート自体のサイズは加算されず、ルートから参照されるヒープオブジェクトのみが計上されます。

3.  **`scanstack`における`gcw.bytesMarked`と`gcw.scanWork`の保存・復元の廃止:**
    *   `scanstack`関数では、スタックをスキャンする前に`origBytesMarked`と`origScanWork`に現在の値を保存し、スキャン後にこれらの値を`gcw.bytesMarked`と`gcw.scanWork`に復元していました。
    *   これは、スタック自体がヒープの一部ではないため、スタックのバイト数をマーク済みヒープサイズに含めないようにするための試みでしたが、結果的にスタックから到達可能なヒープオブジェクトのマーク済みバイト数もリセットしてしまうという副作用がありました。
    *   このコミットでは、この保存・復元ロジックが削除されました。これにより、スタックから到達可能なヒープオブジェクトが正しく`gcw.bytesMarked`と`gcw.scanWork`に加算され、累積されるようになります。

これらの変更により、GCはヒープ上のライブオブジェクトの総量をより正確に把握できるようになります。特に、ポインタを含まない大きなデータ構造が正しく計上されることで、GCがヒープの成長を正確に認識し、不必要なGCサイクルを減らすことができます。結果として、GCのオーバーヘッドが減少し、アプリケーションの全体的なパフォーマンスが向上します。コミットメッセージに示されているベンチマーク結果は、この修正がもたらす顕著なパフォーマンス改善を裏付けています。

    *   **解説:** `markroot`関数は、グローバル変数などのGCルートをスキャンする役割を担います。以前は、この関数が終了する際に`gcw.bytesMarked`と`gcw.scanWork`をゼロにリセットしていました。コメントには「ルートはヒープの一部ではないため、マーク済みヒープバイト数に含めない」とありますが、このゼロクリアは、ルートから到達可能な**ヒープ上のオブジェクト**がマークされたバイト数も消去してしまうという誤った動作を引き起こしていました。この行を削除することで、ルートスキャン中にマークされたヒープオブジェクトのバイト数とスキャン作業量が正しく累積されるようになります。

2.  **`func scanstack(gp *g)` 内の変更:**
    *   削除された行:
        ```go
        origBytesMarked := gcw.bytesMarked
        origScanWork := gcw.scanWork
        // ... (スタックフレームのスキャンロジック) ...
        // Stacks aren't part of the heap, so don't count them toward
        // marked heap bytes.
        gcw.bytesMarked = origBytesMarked
        gcw.scanWork = origScanWork
        ```
    *   **解説:** `scanstack`関数は、特定のGoroutineのスタックをスキャンし、スタック上のポインタから到達可能なヒープオブジェクトをマークします。以前は、スタックのスキャンを開始する前に`gcw.bytesMarked`と`gcw.scanWork`の値を保存し、スキャン後に元の値に戻していました。これは`markroot`と同様に、スタック自体がヒープではないため、そのバイト数を計上しないという意図でしたが、結果的にスタックから到達可能な**ヒープオブジェクト**のマーク済みバイト数も計上されないという問題がありました。これらの行を削除することで、スタックから到達可能なヒープオブジェクトが正しく`gcw.bytesMarked`と`gcw.scanWork`に加算され、累積されるようになります。

3.  **`func scanblock(b0, n0 uintptr, ptrmask *uint8, gcw *gcWork)` 内の変更:**
    *   削除された行:
        ```go
        gcw.bytesMarked += uint64(n)
        ```
    *   **解説:** `scanblock`関数は、与えられたメモリブロックをスキャンし、その中に含まれるポインタを処理します。以前は、この関数が呼び出されるたびに、スキャン対象のブロックのサイズ`n`を`gcw.bytesMarked`に無条件に加算していました。この関数はルートスキャンの一部としても使用されるため、ルート（ヒープではない）のメモリブロックが誤ってマーク済みヒープサイズに計上される原因となっていました。この行を削除することで、`gcw.bytesMarked`は純粋にヒープ上のオブジェクトのサイズのみを計上するようになり、ルート自体のサイズが誤って含まれることがなくなります。

これらの変更は、GCのマークフェーズにおける`gcw.bytesMarked`と`gcw.scanWork`の計上ロジックを根本的に修正し、ヒープ上のライブオブジェクトのサイズをより正確に反映させることを可能にしています。これにより、GCのトリガータイミングが最適化され、全体的なパフォーマンスが向上します。

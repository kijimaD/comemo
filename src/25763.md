# [インデックス 25763] ファイルの概要

このコミットは、Goコンパイラの`nowritebarrierrec`解析が`runtime.allocm`関数を特別に扱うように変更するものです。`allocm`関数はGoランタイム内で非常に特殊な役割を担っており、その動作が`nowritebarrierrec`の最適化と競合する可能性があるため、コンパイラが`allocm`を検出した際には`nowritebarrierrec`の解析を停止するように修正されました。これにより、ランタイムの安定性と正確性が保証されます。

## コミット

```
cmd/compile: special case nowritebarrierrec for allocm

allocm is a very unusual function: it is specifically designed to
allocate in contexts where m.p is nil by temporarily taking over a P.
Since allocm is used in many contexts where it would make sense to use
nowritebarrierrec, this commit teaches the nowritebarrierrec analysis
to stop at allocm.

Updates #10600.
```

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行中にメモリを自動的に管理します。特に、並行GCでは、GCがオブジェクトグラフを走査している最中に、ミューテーター（ユーザープログラム）がポインタを書き換えることによってオブジェクトグラフの整合性が損なわれるのを防ぐために「ライトバリア（Write Barrier）」という仕組みが導入されています。ライトバリアは、ポインタの書き込み時に特定の処理（例えば、GCが追跡できるように古い値や新しい値を記録する）を挿入するものです。

`go:nowritebarrierrec`は、コンパイラに対するアノテーション（指示）であり、特定の関数とその呼び出しツリー内でライトバリアを挿入しないように指示します。これは、その関数がヒープへのポインタ書き込みを行わないか、あるいはGCにとって安全な方法で書き込みを行うことが保証されている場合に、パフォーマンス最適化のために使用されます。

`runtime.allocm`関数は、Goランタイム内で新しいM（OSスレッド）を割り当てるための非常に特殊な関数です。この関数は、`m.p`（現在のMに割り当てられているP、つまり論理プロセッサ）が`nil`であるような状況で、一時的にPを占有して割り当てを行うように設計されています。このような特殊な動作のため、`allocm`は内部でメモリ割り当て（ヒープへの書き込み）を行いますが、そのコンテキストは通常のユーザーコードとは大きく異なります。

問題は、`allocm`が`nowritebarrierrec`が適用されるべき多くのコンテキストで使用される可能性があるにもかかわらず、その内部的なPの操作とメモリ割り当ての性質が、`nowritebarrierrec`の解析ロジックと衝突する可能性があったことです。もし`allocm`に対して誤って`nowritebarrierrec`が適用されてしまうと、ライトバリアが省略され、GCの正確性やランタイムの安定性に問題を引き起こす恐れがありました。このコミットは、この潜在的な問題を回避するために、コンパイラが`allocm`を特別扱いするように変更することで、ランタイムの堅牢性を向上させることを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC) とライトバリア

Goのガベージコレクションは、主に三色マーク＆スイープアルゴリズムをベースにしています。このアルゴリズムでは、オブジェクトを白（未訪問）、灰色（訪問済みだが子を未訪問）、黒（訪問済みで子も訪問済み）のいずれかの色でマークします。並行GCでは、GCがマークフェーズを実行している最中にもユーザープログラム（ミューテーター）が実行され、オブジェクトグラフが変更される可能性があります。

このグラフの変更によってGCの正確性が損なわれないようにするために、「ライトバリア」が導入されています。ライトバリアは、ミューテーターがヒープ上のポインタを書き換える際に自動的に挿入されるコードスニペットです。具体的には、ポインタ`*dst = src`のような書き込みが行われる際に、GCがオブジェクトの参照関係の変化を正しく追跡できるように、追加の処理（例えば、`*dst`が指していたオブジェクトを灰色にする、`src`が指すオブジェクトを灰色にするなど）を実行します。これにより、GCがオブジェクトを見落とすことを防ぎ、メモリリークや不正なメモリ解放を防ぎます。

### `go:nowritebarrierrec` アノテーション

`go:nowritebarrierrec`は、Goコンパイラに対する特別なディレクティブ（アノテーション）です。このアノテーションが付けられた関数は、コンパイラによってライトバリアの挿入がスキップされます。これは、以下のような場合に利用されます。

1.  **ポインタ書き込みを行わない関数**: 関数がヒープ上のポインタを一切書き換えない場合、ライトバリアは不要です。
2.  **GCにとって安全な方法でポインタ書き込みを行う関数**: 例えば、GCが停止している間にのみポインタ書き込みを行う関数や、ライトバリアが不要な特殊なメモリ領域（スタックなど）に書き込む関数などです。

このアノテーションは、ライトバリアのオーバーヘッドを削減し、パフォーマンスを向上させるための最適化手段として使用されます。しかし、誤って適用されるとGCの不正確性を招くため、非常に慎重に扱われる必要があります。

### `m` と `p` (Goroutineスケジューラ)

Goランタイムのスケジューラは、G（Goroutine）、M（Machine/OSスレッド）、P（Processor/論理プロセッサ）という3つの主要なエンティティで構成されます。

*   **G (Goroutine)**: Goの軽量な実行単位。ユーザーコードが実行される場所。
*   **M (Machine)**: OSスレッド。Gを実行するための実際のOSレベルのスレッド。
*   **P (Processor)**: 論理プロセッサ。MがGを実行するために必要なリソース（スケジューラのキュー、GC関連のデータなど）を提供します。MはPを1つ占有してGを実行します。

通常、MはPと関連付けられており、`m.p`はMが現在使用しているPを指します。Pは、GCのライトバリアの状態など、GCに関連する重要なコンテキスト情報も保持しています。

### `runtime.allocm` 関数

`runtime.allocm`は、Goランタイムの内部関数であり、新しいM（OSスレッド）を割り当てて初期化するために使用されます。この関数の特異な点は、`m.p`が`nil`であるような、つまりMがPと関連付けられていないコンテキストで呼び出される可能性があることです。このような状況で、`allocm`は一時的にPを「借りて」メモリ割り当てなどの処理を行います。この「Pを借りる」という動作は、通常のユーザーコードや他のランタイム関数とは異なる特殊なリソース管理を伴います。

## 技術的詳細

このコミットの核心は、`go:nowritebarrierrec`アノテーションの解析ロジックと`runtime.allocm`関数の特殊な動作との間の潜在的な不整合を解消することにあります。

`nowritebarrierrec`は、関数がヒープへのポインタ書き込みを行わない、またはGCにとって安全な方法で行うことを前提として、ライトバリアの挿入を省略します。しかし、`allocm`は新しいMを割り当てる際に、内部でメモリ割り当て（ヒープへの書き込み）を行います。さらに、`allocm`は`m.p`が`nil`の状況でPを一時的に占有するという、スケジューラレベルでの低レベルな操作を行います。

この「Pを一時的に占有する」という動作は、GCのライトバリアの状態や、Pが持つGC関連のコンテキストと密接に関連しています。もし`allocm`が`nowritebarrierrec`の対象となり、ライトバリアが省略された状態でPを操作したり、メモリ割り当てを行ったりすると、GCがオブジェクトグラフの変更を正しく追跡できなくなり、結果としてGCの不正確性やランタイムのクラッシュにつながる可能性があります。

コンパイラの`nowritebarrierrec`解析は、通常、関数の呼び出しツリーを辿って、ライトバリアを省略できる範囲を決定します。しかし、`allocm`のような特殊な関数がそのツリーに含まれる場合、一般的な解析ルールではその特殊性を考慮できませんでした。

このコミットでは、コンパイラが`allocm`関数を特別に認識し、その関数に到達した時点で`nowritebarrierrec`の解析を停止するように変更されました。これにより、`allocm`内部でのメモリ割り当てやPの操作が、常に適切なライトバリアの保護下で行われることが保証され、ランタイムの堅牢性が維持されます。つまり、`allocm`は`nowritebarrierrec`の最適化の対象から除外されることになります。

コミットメッセージで参照されているIssue #10600は、Web検索の結果ではEtcdのデッドロックに関するものであり、このコミットの直接的な原因とは関連が薄いように見えます。これは、コミットメッセージ内のIssue番号が、より広範な議論や、この変更につながる間接的な問題を参照しているか、あるいは単なる誤記である可能性があります。このコミットの主な目的は、`allocm`の特殊な性質と`nowritebarrierrec`の解析との間の技術的な不整合を解消することにあります。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/dcl.go` の変更

このファイルはGoコンパイラの宣言（declaration）処理に関連する部分です。`nowritebarrierrecChecker`は、`go:nowritebarrierrec`アノテーションの適用可能性をチェックする構造体です。`visitcall`メソッドは、関数呼び出しを訪問し、その呼び出しが`nowritebarrierrec`の対象となるかどうかを判断します。

追加されたコードブロックは以下の通りです。

```go
	if (compiling_runtime != 0 || fn.Sym.Pkg == Runtimepkg) && fn.Sym.Name == "allocm" {
		return
	}
```

このコードは、`visitcall`メソッドの冒頭に追加されています。
*   `compiling_runtime != 0`: コンパイラが現在ランタイム自体をコンパイルしているかどうかを示すフラグです。
*   `fn.Sym.Pkg == Runtimepkg`: 呼び出されている関数のシンボルが`runtime`パッケージに属しているかどうかをチェックします。
*   `fn.Sym.Name == "allocm"`: 呼び出されている関数の名前が`allocm`であるかどうかをチェックします。

この条件文は、「現在ランタイムをコンパイルしている最中であるか、または呼び出されている関数が`runtime`パッケージの`allocm`である場合」に真となります。この条件が真の場合、`return`ステートメントが実行され、`nowritebarrierrecChecker`はそれ以上この関数呼び出しの解析を行いません。

これは、コンパイラが`runtime.allocm`関数を特別扱いし、その関数に対しては`nowritebarrierrec`の解析（およびそれに伴うライトバリアの省略）を適用しないようにするための明示的なルールです。これにより、`allocm`の特殊な動作がGCの正確性を損なうことを防ぎます。

### `src/runtime/proc.go` の変更

このファイルはGoランタイムのプロセッサ（P）とM（OSスレッド）の管理に関連する部分です。`allocm`関数の定義にコメントが追加されました。

```diff
 // This function it known to the compiler to inhibit the
 // go:nowritebarrierrec annotation because it uses P for allocation.
 func allocm(_p_ *p, fn func()) *m {
```

追加されたコメントは、`allocm`関数がコンパイラによって`go:nowritebarrierrec`アノテーションを抑制することが知られている理由を説明しています。その理由は「`P`を割り当てに使用するから」と明記されています。これは、`allocm`がPを一時的に占有してメモリ割り当てを行うという特殊な動作が、`nowritebarrierrec`の最適化と互換性がないことを開発者に対して明確に伝えるためのドキュメンテーションです。このコメントは、将来のコード変更やレビューにおいて、`allocm`の特殊性を理解し、同様の問題を再発させないための重要な情報となります。

# [インデックス 21910] ファイルの概要

このコミットは、Goランタイムにおけるデータ競合検出器（Race Detector）の計測に関するバグ修正です。具体的には、`append`操作によって内部的に呼び出される`typedslicecopy`関数が、Race Detectorによって適切に計測されていなかった問題を解決します。これにより、`append`操作が関与するデータ競合が検出されない可能性がありました。この修正は、コンパイラ側での対応が複雑であるため、ランタイム側で`typedslicecopy`の読み書き操作を明示的に計測することで実現されています。

## 元コミット内容

このコミットは、Goランタイムにおける`append`操作のデータ競合計測の不備を修正します。`typedslicecopy`という関数が、Race Detectorのコンパイラ側計測（`racewalk`）によって適切に処理されないライトバリア（write barrier）であったため、ランタイム側で明示的に計測を行うように変更されました。この修正は、Issue #9796 に関連しています。

## 変更の背景

GoのRace Detectorは、並行プログラムにおけるデータ競合を検出するための強力なツールです。データ競合は、複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に発生します。このような競合は、予測不能なプログラムの動作やバグを引き起こす可能性があります。

Race Detectorは、コンパイラによるコードの計測（`racewalk`）と、ランタイムにおけるメモリアクセスの監視によって機能します。コンパイラは、メモリへの読み書き操作の前に、Race Detectorのランタイム関数を呼び出すコードを挿入します。これらのランタイム関数は、メモリアクセス履歴を追跡し、競合を検出します。

しかし、`append`組み込み関数がスライス容量を拡張する際に内部的に呼び出す`typedslicecopy`関数が、このコンパイラによる計測の対象外となっていました。`typedslicecopy`は、新しい基底配列への要素のコピーを行うため、実質的にはメモリへの書き込み操作（ライトバリア）を伴います。この操作がRace Detectorによって監視されない場合、`append`操作が関与するデータ競合（特に、`append`が新しい基底配列に要素をコピーしている最中に、別のゴルーチンがそのメモリ領域にアクセスするようなケース）が検出されず、偽陰性（false negative）が発生する可能性がありました。

コミットメッセージにある「`typedslicecopy` is another write barrier that is not understood by `racewalk`」という記述は、この問題の核心を突いています。コンパイラが`typedslicecopy`を特別なライトバリアとして認識し、適切な計測コードを挿入できなかったため、ランタイム側での明示的な対応が必要とされました。コンパイラ側での対応が「quite complex」であると判断されたため、より直接的なランタイムでの計測が選択されました。

## 前提知識の解説

### GoのRace Detector

GoのRace Detectorは、Goプログラムの実行中にデータ競合を検出するツールです。`go run -race`、`go build -race`、`go test -race`などのコマンドで有効にできます。有効にすると、コンパイラはメモリアクセスを監視するための追加コードを生成し、ランタイムはこれらのアクセスを追跡して競合を報告します。

### `racewalk`

`racewalk`は、Goコンパイラの一部であり、Race Detectorのためにコードを計測する役割を担っています。プログラムの抽象構文木（AST）を走査し、メモリへの読み書き操作（ロード、ストア）を特定して、対応するRace Detectorのランタイム関数呼び出しを挿入します。これにより、Race Detectorは実行時にメモリアクセスを監視できます。

### ライトバリア (Write Barrier)

ライトバリアは、ガベージコレクタ（GC）が正確に動作するために、特定のメモリ書き込み操作の前後で実行されるコードスニペットです。GoのGCは並行GCであり、オブジェクトの移動や参照の更新を追跡する必要があります。ライトバリアは、ポインタの書き込み時にGCに通知したり、GCがオブジェクトを移動する際に古いポインタと新しいポインタの整合性を保つために使用されます。`typedslicecopy`のような関数は、内部でポインタのコピーを行うため、GCの観点からはライトバリアとして機能します。Race Detectorの観点からも、メモリへの書き込み操作であるため、計測の対象となるべきです。

### `typedslicecopy`

`typedslicecopy`は、Goランタイム内部の関数で、スライスのコピー操作（特に`copy`組み込み関数や`append`組み込み関数がスライスの容量を拡張する際に新しい基底配列に要素をコピーする場合）を型情報に基づいて実行します。これは、単なるバイト列のコピーではなく、要素の型に応じた適切なコピー（例えば、ポインタを含む構造体のコピーなど）を行うために使用されます。

### `append`組み込み関数

`append`はGoの組み込み関数で、スライスに要素を追加するために使用されます。
`s = append(s, elem1, elem2)`
`append`は、既存のスライスの容量が不足している場合、より大きな新しい基底配列を割り当て、既存の要素を新しい配列にコピーし、その後新しい要素を追加します。この「既存の要素を新しい配列にコピーする」プロセスで`typedslicecopy`が内部的に呼び出されることがあります。

## 技術的詳細

このコミットの技術的詳細は、GoのRace Detectorがどのようにメモリアクセスを計測し、なぜ`typedslicecopy`がその計測から漏れていたのか、そしてどのように修正されたのかに焦点を当てます。

GoのRace Detectorは、コンパイラが生成するコードに`raceread`や`racewrite`といったランタイム関数への呼び出しを挿入することで機能します。これらの関数は、特定のメモリ範囲へのアクセスを記録し、競合を検出します。しかし、`typedslicecopy`のようなランタイム内部の低レベルなメモリ操作は、通常、コンパイラによる直接的な計測の対象外となることがあります。これは、ランタイムコード自体が非常にパフォーマンスに敏感であり、また、コンパイラがランタイムの内部実装の詳細をすべて把握しているわけではないためです。

`typedslicecopy`は、スライスの要素をコピーする際に、ソーススライスからデスティネーションスライスへデータを移動させます。この操作は、特にポインタを含むスライスの場合、ガベージコレクタにとって重要なライトバリア操作となります。Race Detectorの観点からも、これはメモリへの書き込み（および読み込み）操作であり、競合の可能性を秘めています。

元の実装では、`racewalk`（コンパイラ側の計測ロジック）が`typedslicecopy`を通常のメモリ操作として認識せず、Race Detectorの計測コードを挿入していませんでした。コミットメッセージが示唆するように、コンパイラ側で`typedslicecopy`の特殊性を理解し、適切に計測することは非常に複雑であったと考えられます。例えば、`typedslicecopy`は汎用的なコピー関数であり、様々な型のスライスに対して動作するため、コンパイラがその呼び出しサイトごとに適切な計測を生成するのは困難です。

そこで、このコミットでは、コンパイラ側での対応を避け、ランタイムの`typedslicecopy`関数自体にRace Detectorの計測コードを直接埋め込むというアプローチが取られました。

具体的には、`src/runtime/mbarrier.go`内の`typedslicecopy`関数に、`raceenabled`（Race Detectorが有効かどうかを示すフラグ）が`true`の場合に実行されるコードブロックが追加されました。このブロックでは、`racewriterangepc`と`racereadrangepc`というRace Detectorのランタイム関数が呼び出されます。

*   `racewriterangepc(dstp, uintptr(n)*typ.size, callerpc, pc)`: デスティネーションメモリ範囲への書き込みを計測します。`dstp`はデスティネーションスライスの基底ポインタ、`uintptr(n)*typ.size`はコピーされるバイト数（書き込み範囲のサイズ）です。
*   `racereadrangepc(srcp, uintptr(n)*typ.size, callerpc, pc)`: ソースメモリ範囲からの読み込みを計測します。`srcp`はソーススライスの基底ポインタ、`uintptr(n)*typ.size`は読み込まれるバイト数（読み込み範囲のサイズ）です。

これらの関数呼び出しにより、`typedslicecopy`が実行するメモリ操作がRace Detectorによって正確に監視されるようになります。`callerpc`と`pc`は、それぞれ呼び出し元のプログラムカウンタと現在の関数（`slicecopy`）のプログラムカウンタを渡し、Race Detectorが競合発生時のスタックトレースを正確に報告できるようにします。

また、`src/cmd/gc/racewalk.c`には、`typedslicecopy`がランタイムで計測されることを示すコメントが追加され、コンパイラがこの関数を特別扱いする必要がないことが明示されました。

最後に、`src/runtime/race/testdata/slice_test.go`に多数の新しいテストケースが追加されました。これらのテストは、ポインタを含むスライスに対する`copy`や`append`操作が関与する様々なデータ競合シナリオを網羅しており、今回の修正が正しく機能することを確認するために不可欠です。例えば、`TestRacePointerSliceAppend`や`TestRacePointerSliceCopyWrite2`のようなテストは、`append`や`copy`の最中に別のゴルーチンがスライス要素にアクセスした場合に競合が検出されることを検証します。

このアプローチは、コンパイラの複雑性を回避しつつ、Race Detectorの精度を向上させる効果的な方法です。

## コアとなるコードの解説

### `src/runtime/mbarrier.go` の変更

このファイルの`typedslicecopy`関数への変更が、このコミットの核心です。

```go
func typedslicecopy(typ *_type, dst, src slice) int {
	dstp := unsafe.Pointer(dst.array)
	srcp := unsafe.Pointer(src.array)

	if raceenabled {
		callerpc := getcallerpc(unsafe.Pointer(&typ))
		pc := funcPC(slicecopy)
		racewriterangepc(dstp, uintptr(n)*typ.size, callerpc, pc)
		racereadrangepc(srcp, uintptr(n)*typ.size, callerpc, pc)
	}

	if !needwb() {
		memmove(dstp, srcp, uintptr(n)*typ.size)
		return int(n)
	}
	// ... (既存のライトバリアロジック)
}
```

*   `if raceenabled { ... }` ブロック: このブロックは、GoのRace Detectorが有効になっている場合にのみ実行されます。`raceenabled`は、`go run -race`などのコマンドでRace Detectorが有効にされたときに`true`になるグローバル変数です。
*   `callerpc := getcallerpc(unsafe.Pointer(&typ))`: `getcallerpc`は、現在の関数の呼び出し元のプログラムカウンタ（PC）を取得します。これは、Race Detectorが競合を報告する際に、どのコードが問題のメモリアクセスを行ったかを特定するために使用されます。
*   `pc := funcPC(slicecopy)`: `funcPC`は、指定された関数のエントリポイントのプログラムカウンタを取得します。ここでは`slicecopy`（`typedslicecopy`が内部的に使用する可能性のある関数、または`typedslicecopy`自身を指すエイリアス）のPCを取得しています。これもRace Detectorのレポートに役立ちます。
*   `racewriterangepc(dstp, uintptr(n)*typ.size, callerpc, pc)`: この関数呼び出しは、デスティネーションスライス（`dstp`が指すメモリ領域）への書き込み操作をRace Detectorに通知します。`uintptr(n)*typ.size`は、コピーされる要素の総バイト数であり、書き込みが行われるメモリ範囲のサイズを示します。
*   `racereadrangepc(srcp, uintptr(n)*typ.size, callerpc, pc)`: この関数呼び出しは、ソーススライス（`srcp`が指すメモリ領域）からの読み込み操作をRace Detectorに通知します。同様に、`uintptr(n)*typ.size`は読み込みが行われるメモリ範囲のサイズです。

これらの変更により、`typedslicecopy`が実行するメモリコピー操作（ソースからの読み込みとデスティネーションへの書き込み）が、Race Detectorによって明示的に監視されるようになります。これにより、`append`や`copy`が関与するデータ競合が正確に検出されるようになります。

### `src/cmd/gc/racewalk.c` の変更

このファイルへの変更はコメントの追加のみです。

```c
// typedslicecopy is instrumented in runtime.
```

このコメントは、コンパイラの`racewalk`が`typedslicecopy`を特別に計測する必要がないことを示しています。これは、前述の`src/runtime/mbarrier.go`でのランタイム計測によって、すでにこの関数が適切に処理されるようになったためです。これにより、コンパイラとランタイム間の責任分担が明確になります。

### `src/runtime/race/testdata/slice_test.go` の変更

このファイルには、`typedslicecopy`の計測が正しく機能することを確認するための多数の新しいテストケースが追加されました。これらのテストは、ポインタを含むスライスに対する`copy`や`append`操作が関与する様々なデータ競合シナリオをシミュレートしています。

例えば、`TestRacePointerSliceAppend`は以下のようなシナリオをテストします。

```go
func TestRacePointerSliceAppend(t *testing.T) {
	c := make(chan bool, 1)
	s := make([]*int, 10, 20) // 容量20のスライス
	go func() {
		_ = append(s, new(int)) // ゴルーチンA: スライスに要素を追加（容量が足りなければtypedslicecopyが呼ばれる）
		c <- true
	}()
	_ = append(s, new(int)) // ゴルーチンB: スライスに要素を追加
	<-c
}
```

このテストでは、2つのゴルーチンが同時に同じスライスに対して`append`操作を行っています。もし`append`が新しい基底配列を割り当て、`typedslicecopy`がそのコピー中に競合を引き起こすような状況であれば、Race Detectorがそれを検出するはずです。これらのテストは、Race Detectorが以前見逃していた可能性のある競合パターンを網羅的に検証し、修正の有効性を保証します。

## 元コミット内容

このコミットは、Goランタイムにおける`append`操作のデータ競合計測の不備を修正します。`typedslicecopy`という関数が、Race Detectorのコンパイラ側計測（`racewalk`）によって適切に処理されないライトバリア（write barrier）であったため、ランタイム側で明示的に計測を行うように変更されました。この修正は、Issue #9796 に関連しています。

## 変更の背景

GoのRace Detectorは、並行プログラムにおけるデータ競合を検出するための強力なツールです。データ競合は、複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に発生します。このような競合は、予測不能なプログラムの動作やバグを引き起こす可能性があります。

Race Detectorは、コンパイラによるコードの計測（`racewalk`）と、ランタイムにおけるメモリアクセスの監視によって機能します。コンパイラは、メモリへの読み書き操作の前に、Race Detectorのランタイム関数を呼び出すコードを挿入します。これらのランタイム関数は、メモリアクセス履歴を追跡し、競合を検出します。

しかし、`append`組み込み関数がスライス容量を拡張する際に内部的に呼び出す`typedslicecopy`関数が、このコンパイラによる計測の対象外となっていました。`typedslicecopy`は、新しい基底配列への要素のコピーを行うため、実質的にはメモリへの書き込み操作（ライトバリア）を伴います。この操作がRace Detectorによって監視されない場合、`append`操作が関与するデータ競合（特に、`append`が新しい基底配列に要素をコピーしている最中に、別のゴルーチンがそのメモリ領域にアクセスするようなケース）が検出されず、偽陰性（false negative）が発生する可能性がありました。

コミットメッセージにある「`typedslicecopy` is another write barrier that is not understood by `racewalk`」という記述は、この問題の核心を突いています。コンパイラが`typedslicecopy`を特別なライトバリアとして認識し、適切な計測コードを挿入できなかったため、ランタイム側での明示的な対応が必要とされました。コンパイラ側での対応が「quite complex」であると判断されたため、より直接的なランタイムでの計測が選択されました。

## 前提知識の解説

### GoのRace Detector

GoのRace Detectorは、Goプログラムの実行中にデータ競合を検出するツールです。`go run -race`、`go build -race`、`go test -race`などのコマンドで有効にできます。有効にすると、コンパイラはメモリアクセスを監視するための追加コードを生成し、ランタイムはこれらのアクセスを追跡して競合を報告します。

### `racewalk`

`racewalk`は、Goコンパイラの一部であり、Race Detectorのためにコードを計測する役割を担っています。プログラムの抽象構文木（AST）を走査し、メモリへの読み書き操作（ロード、ストア）を特定して、対応するRace Detectorのランタイム関数呼び出しを挿入します。これにより、Race Detectorは実行時にメモリアクセスを監視できます。

### ライトバリア (Write Barrier)

ライトバリアは、ガベージコレクタ（GC）が正確に動作するために、特定のメモリ書き込み操作の前後で実行されるコードスニペットです。GoのGCは並行GCであり、オブジェクトの移動や参照の更新を追跡する必要があります。ライトバリアは、ポインタの書き込み時にGCに通知したり、GCがオブジェクトを移動する際に古いポインタと新しいポインタの整合性を保つために使用されます。`typedslicecopy`のような関数は、内部でポインタのコピーを行うため、GCの観点からはライトバリアとして機能します。Race Detectorの観点からも、メモリへの書き込み操作であるため、計測の対象となるべきです。

### `typedslicecopy`

`typedslicecopy`は、Goランタイム内部の関数で、スライスのコピー操作（特に`copy`組み込み関数や`append`組み込み関数がスライスの容量を拡張する際に新しい基底配列に要素をコピーする場合）を型情報に基づいて実行します。これは、単なるバイト列のコピーではなく、要素の型に応じた適切なコピー（例えば、ポインタを含む構造体のコピーなど）を行うために使用されます。

### `append`組み込み関数

`append`はGoの組み込み関数で、スライスに要素を追加するために使用されます。
`s = append(s, elem1, elem2)`
`append`は、既存のスライスの容量が不足している場合、より大きな新しい基底配列を割り当て、既存の要素を新しい配列にコピーし、その後新しい要素を追加します。この「既存の要素を新しい配列にコピーする」プロセスで`typedslicecopy`が内部的に呼び出されることがあります。

## 技術的詳細

このコミットの技術的詳細は、GoのRace Detectorがどのようにメモリアクセスを計測し、なぜ`typedslicecopy`がその計測から漏れていたのか、そしてどのように修正されたのかに焦点を当てます。

GoのRace Detectorは、コンパイラが生成するコードに`raceread`や`racewrite`といったランタイム関数への呼び出しを挿入することで機能します。これらの関数は、特定のメモリ範囲へのアクセスを記録し、競合を検出します。しかし、`typedslicecopy`のようなランタイム内部の低レベルなメモリ操作は、通常、コンパイラによる直接的な計測の対象外となることがあります。これは、ランタイムコード自体が非常にパフォーマンスに敏感であり、また、コンパイラがランタイムの内部実装の詳細をすべて把握しているわけではないためです。

`typedslicecopy`は、スライスの要素をコピーする際に、ソーススライスからデスティネーションスライスへデータを移動させます。この操作は、特にポインタを含むスライスの場合、ガベージコレクタにとって重要なライトバリア操作となります。Race Detectorの観点からも、これはメモリへの書き込み（および読み込み）操作であり、競合の可能性を秘めています。

元の実装では、`racewalk`（コンパイラ側の計測ロジック）が`typedslicecopy`を通常のメモリ操作として認識せず、Race Detectorの計測コードを挿入していませんでした。コミットメッセージが示唆するように、コンパイラ側で`typedslicecopy`の特殊性を理解し、適切に計測することは非常に複雑であったと考えられます。例えば、`typedslicecopy`は汎用的なコピー関数であり、様々な型のスライスに対して動作するため、コンパイラがその呼び出しサイトごとに適切な計測を生成するのは困難です。

そこで、このコミットでは、コンパイラ側での対応を避け、ランタイムの`typedslicecopy`関数自体にRace Detectorの計測コードを直接埋め込むというアプローチが取られました。

これらの関数呼び出しにより、`typedslicecopy`が実行するメモリ操作がRace Detectorによって正確に監視されるようになります。`callerpc`と`pc`は、それぞれ呼び出し元のプログラムカウンタと現在の関数（`slicecopy`）のプログラムカウンタを渡し、Race Detectorが競合発生時のスタックトレースを正確に報告できるようにします。

また、`src/cmd/gc/racewalk.c`には、`typedslicecopy`がランタイムで計測されることを示すコメントが追加され、コンパイラがこの関数を特別扱いする必要がないことが明示されました。

最後に、`src/runtime/race/testdata/slice_test.go`に多数の新しいテストケースが追加されました。これらのテストは、ポインタを含むスライスに対する`copy`や`append`操作が関与する様々なデータ競合シナリオを網羅しており、今回の修正が正しく機能することを確認するために不可欠です。例えば、`TestRacePointerSliceAppend`や`TestRacePointerSliceCopyWrite2`のようなテストは、`append`や`copy`の最中に別のゴルーチンがスライス要素にアクセスした場合に競合が検出されることを検証します。

このアプローチは、コンパイラの複雑性を回避しつつ、Race Detectorの精度を向上させる効果的な方法です。

### `src/runtime/mbarrier.go` の変更

このファイルの`typedslicecopy`関数への変更が、このコミットの核心です。

```go
func typedslicecopy(typ *_type, dst, src slice) int {
	dstp := unsafe.Pointer(dst.array)
	srcp := unsafe.Pointer(src.array)

	if raceenabled {
		callerpc := getcallerpc(unsafe.Pointer(&typ))
		pc := funcPC(slicecopy)
		racewriterangepc(dstp, uintptr(n)*typ.size, callerpc, pc)
		racereadrangepc(srcp, uintptr(n)*typ.size, callerpc, pc)
	}

	if !needwb() {
		memmove(dstp, srcp, uintptr(n)*typ.size)
		return int(n)
	}
	// ... (既存のライトバリアロジック)
}
```

*   `if raceenabled { ... }` ブロック: このブロックは、GoのRace Detectorが有効になっている場合にのみ実行されます。`raceenabled`は、`go run -race`などのコマンドでRace Detectorが有効にされたときに`true`になるグローバル変数です。
*   `callerpc := getcallerpc(unsafe.Pointer(&typ))`: `getcallerpc`は、現在の関数の呼び出し元のプログラムカウンタ（PC）を取得します。これは、Race Detectorが競合を報告する際に、どのコードが問題のメモリアクセスを行ったかを特定するために使用されます。
*   `pc := funcPC(slicecopy)`: `funcPC`は、指定された関数のエントリポイントのプログラムカウンタを取得します。ここでは`slicecopy`（`typedslicecopy`が内部的に使用する可能性のある関数、または`typedslicecopy`自身を指すエイリアス）のPCを取得しています。これもRace Detectorのレポートに役立ちます。
*   `racewriterangepc(dstp, uintptr(n)*typ.size, callerpc, pc)`: この関数呼び出しは、デスティネーションスライス（`dstp`が指すメモリ領域）への書き込み操作をRace Detectorに通知します。`uintptr(n)*typ.size`は、コピーされる要素の総バイト数であり、書き込みが行われるメモリ範囲のサイズを示します。
*   `racereadrangepc(srcp, uintptr(n)*typ.size, callerpc, pc)`: この関数呼び出しは、ソーススライス（`srcp`が指すメモリ領域）からの読み込み操作をRace Detectorに通知します。同様に、`uintptr(n)*typ.size`は読み込みが行われるメモリ範囲のサイズです。

これらの変更により、`typedslicecopy`が実行するメモリコピー操作（ソースからの読み込みとデスティネーションへの書き込み）が、Race Detectorによって明示的に監視されるようになります。これにより、`append`や`copy`が関与するデータ競合が正確に検出されるようになります。

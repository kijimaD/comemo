## 元コミット内容

このコミットは、Goランタイムの`gccheckmark`モードにおけるバグを修正し、このデバッグ機能を一時的にデフォルトで有効にするものです。以前の変更（CL 2991）でのリファクタリング中に、GCのマークビットをチェックするロジックが誤って反転してしまい、ルートが指すオブジェクトだけでなく、ヒープ上の残りのライブオブジェクトのマークビットが正しく検証されない状態になっていました。このコミットではその反転したチェックを修正し、ビルダ上での完全な`checkmark`チェックを実行するために、一時的に`gccheckmark`をデフォルトで有効にしています。次のコミットで再びデフォルトで無効に戻される予定です。

## 変更の背景

Goのガベージコレクタは、並行（concurrent）に動作するように設計されており、プログラムの実行と並行して不要なメモリを回収します。このような並行GCは複雑であり、GC自身のバグによって本来解放してはいけないメモリを解放してしまったり、逆に解放すべきメモリを解放し忘れたりする可能性があります。

`gccheckmark`は、このようなGCのバグを検出するためのデバッグ機能です。GCの並行マークフェーズが完了した後、プログラムの実行を一時停止（Stop-The-World: STW）させて、ヒープ全体を再度スキャンし、並行マークフェーズでマークされるべきだったがマークされなかったオブジェクトがないかを確認します。もしそのようなオブジェクトが見つかった場合、それはGCのバグを示唆するため、ランタイムはパニックを起こします。

このコミットの背景には、以前のCL 2991でのリファクタリング作業中に、この`gccheckmark`のチェックロジックが誤って反転してしまったという問題がありました。その結果、`gccheckmark`が意図した通りに機能せず、GCの潜在的なバグを見逃す可能性がありました。このコミットは、そのバグを修正し、`gccheckmark`が正しく機能するようにすることで、Goランタイムの安定性と信頼性を向上させることを目的としています。また、修正が正しく適用されたことを確認するため、一時的にビルダ上でこの機能を有効にしてテストランを実行する意図も含まれています。

## 前提知識の解説

### ガベージコレクタ (GC)

ガベージコレクタは、プログラムが動的に割り当てたメモリのうち、もはやプログラムから到達不可能になった（「ガベージ」となった）メモリ領域を自動的に解放するシステムです。Go言語のGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにしています。

*   **三色マーク＆スイープ**:
    *   **マークフェーズ**: ヒープ上のオブジェクトを「白（未訪問）」「灰（訪問済みだが参照先未訪問）」「黒（訪問済みかつ参照先も訪問済み）」の三色で分類します。プログラムのルート（スタック、グローバル変数など）から到達可能なオブジェクトを辿り、マークしていきます。GoのGCは、このマークフェーズをプログラムの実行と並行して行います（並行マーク）。
    *   **スイープフェーズ**: マークされなかった「白」のオブジェクトをガベージとして認識し、メモリを解放します。

### 並行GC (Concurrent GC)

GoのGCは、ほとんどの処理をアプリケーションの実行と並行して行います。これにより、アプリケーションの応答性を損なうことなく、メモリ管理を行うことができます。しかし、並行処理は複雑さを伴い、GC自身のバグが発生するリスクも高まります。

### Stop-The-World (STW)

GCの処理の一部（特にマークフェーズの開始時や、マークフェーズの完了後の最終的な処理など）では、アプリケーションの全てのゴルーチン（Goの軽量スレッド）を一時的に停止させる必要があります。この停止期間をStop-The-World (STW) と呼びます。STWの時間は、アプリケーションの応答性に直接影響するため、GoのGCはSTW時間を最小限に抑えるように設計されています。

### `gccheckmark`

`gccheckmark`は、Goランタイムのデバッグオプションの一つで、`GODEBUG=gccheckmark=1`を設定することで有効になります。このオプションが有効な場合、GCの並行マークフェーズが完了した後、追加のSTWフェーズが挿入されます。このSTWフェーズでは、ヒープ全体を再度スキャンし、並行マークフェーズでマークされるべきだったがマークされなかったオブジェクトがないかを確認します。もし、マークされていないライブオブジェクトが見つかった場合、それはGCの並行マークロジックにバグがあることを意味するため、ランタイムはパニックを起こします。これは、GCの並行処理の正確性を検証するための重要なツールです。

### `heapBits`

`heapBits`は、Goランタイム内部でヒープ上のオブジェクトのメタデータを管理するために使用されるデータ構造です。各オブジェクトのメモリ領域に対応するビットが割り当てられており、オブジェクトがマークされているか（GCによって到達可能と判断されたか）などの情報が格納されます。`isCheckmarked()`や`setCheckmarked()`のようなメソッドは、この`heapBits`を操作して、オブジェクトのチェックマーク状態を問い合わせたり設定したりするために使われます。

## 技術的詳細

このコミットの核心は、`src/runtime/mgcmark.go`内の`greyobject`関数における条件式の修正です。`greyobject`関数は、GCのマークフェーズ中にオブジェクトを走査し、その参照先をマークする役割を担っています。

元のコードでは、`hbits.isCheckmarked()`というメソッドの戻り値を反転させた`!hbits.isCheckmarked()`という条件でチェックが行われていました。これは、「もしオブジェクトがチェックマークされていないならば、`throw("checkmark found unmarked object")`でパニックを起こす」という意図だったと考えられます。しかし、コミットメッセージによると、以前のCL 2991でのリファクタリング中にこのロジックが誤って反転してしまったため、実際には「もしオブジェクトがチェックマークされているならば、処理をスキップする」という逆の動作になっていました。

この誤ったロジックでは、`gccheckmark`が有効な場合でも、並行マークフェーズでマークされなかったライブオブジェクトがSTWフェーズで発見されたとしても、パニックを起こすことなく処理が続行されてしまう可能性がありました。つまり、`gccheckmark`がGCのバグを検出するという本来の目的を果たせていなかったのです。

このコミットでは、条件式を`!hbits.isCheckmarked()`から`hbits.isCheckmarked()`に修正しています。これにより、`throw("checkmark found unmarked object")`が実行されるのは、「オブジェクトがチェックマークされていない」という本来の条件が満たされた場合になります。これは、`gccheckmark`が期待通りに、並行マークフェーズでマーク漏れがあった場合にパニックを引き起こすように修正されたことを意味します。

また、`src/runtime/runtime1.go`では、`parsedebugvars`関数内で`debug.gccheckmark=1`が追加されています。これは、`GODEBUG`環境変数を明示的に設定しなくても、このコミットが適用されたビルドでは`gccheckmark`がデフォルトで有効になることを意味します。コミットメッセージにある通り、これはビルダ上で完全な`checkmark`チェックを実行するための一時的な措置であり、次のコミットで無効に戻される予定です。この一時的な有効化は、修正が正しく機能し、GCの並行マークロジックに新たな問題がないことを広範囲にわたって検証するための戦略的な判断です。

## コアとなるコードの解説

### `src/runtime/mgcmark.go`の変更

`greyobject`関数は、GCのマークフェーズにおいて、ヒープ上のオブジェクトを走査し、その参照先をマークする中心的な役割を担っています。この関数内で、`gccheckmark`モードが有効な場合に、オブジェクトのマーク状態を検証するロジックが含まれています。

変更前のコード:
```go
		if !hbits.isCheckmarked() {
			return
		}
```
この条件式は、「もし`hbits`がチェックマークされていないならば、関数を終了する」という意味になります。しかし、`throw("checkmark found unmarked object")`の直後にこの`if`文があることから、本来の意図は「もし`hbits`がチェックマークされているならば、それは既に処理済みなのでスキップする」というものでした。つまり、`!hbits.isCheckmarked()`という条件は、意図とは逆に、チェックマークされていないオブジェクトに対して処理をスキップしてしまっていたため、マーク漏れを検出できませんでした。

変更後のコード:
```go
		if hbits.isCheckmarked() {
			return
		}
```
この修正により、条件式は「もし`hbits`がチェックマークされているならば、関数を終了する」という意味に変わります。これにより、`throw("checkmark found unmarked object")`は、`hbits.isCheckmarked()`が`false`（つまり、オブジェクトがチェックマークされていない）の場合にのみ実行されるようになります。これは、`gccheckmark`の本来の目的である「並行マークフェーズでマークされるべきだったがマークされなかったオブジェクト」を検出した場合にパニックを引き起こすという動作を正確に実現します。

### `src/runtime/runtime1.go`の変更

`parsedebugvars`関数は、`GODEBUG`環境変数からデバッグオプションを解析し、ランタイムの内部デバッグ変数に設定する役割を担っています。

追加された行:
```go
	debug.gccheckmark=1
```
この行は、`GODEBUG`環境変数の設定に関わらず、`debug.gccheckmark`という内部変数を`1`に設定します。これは、`gccheckmark`モードを強制的に有効にする効果があります。コミットメッセージにある通り、これは一時的な措置であり、このコミットが適用されたビルドがGoのビルダ上で実行される際に、`gccheckmark`による完全な検証が行われるようにするためのものです。これにより、修正された`gccheckmark`ロジックが正しく機能し、GCの健全性が保証されることを確認できます。

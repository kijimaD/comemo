## 変更の背景

このコミットの主な背景は、Go言語の標準ライブラリである`net/http`パッケージにおけるHTTP/2プロトコルの実装の改善と、それに伴う既知のバグの修正です。

GoはHTTP/2を標準ライブラリでサポートしており、その実装は`golang.org/x/net/http2`パッケージをベースにしています。このパッケージは`net/http`内部にバンドルされており、定期的に最新の状態に保つ必要があります。このコミットは、そのバンドルされているHTTP/2実装を更新し、より安定したバージョンにすることで、パフォーマンス向上やバグ修正を取り込むことを目的としています。

特に、コミットメッセージで言及されているIssue #13495とIssue #13532は、HTTP/2プロトコルにおけるヘッダの処理に関する具体的な問題を示唆しています。これらの問題は、HTTP/2のレスポンス生成時に`Content-Length`ヘッダや`Content-Type`ヘッダが正しく扱われない場合に発生する可能性があり、クライアントとサーバー間の互換性やプロトコル準拠に影響を与える可能性があります。これらの問題を修正し、それらを検証するためのテストを追加することで、`net/http`パッケージの堅牢性を高め、開発者が安心してHTTP/2を使用できる環境を提供することが、この変更の重要な動機となっています。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

1.  **HTTP/2プロトコル**:
    *   HTTP/2は、HTTP/1.1の後継となるWebプロトコルです。主な特徴として、多重化（Multiplexing）、ヘッダ圧縮（HPACK）、サーバープッシュなどがあり、Webパフォーマンスの向上を目的としています。
    *   HTTP/2では、リクエストとレスポンスがストリームと呼ばれる独立した双方向のバイトシーケンスで送受信されます。各ストリームには一意のIDが割り当てられ、複数のストリームが単一のTCP接続上で同時に多重化されます。
    *   ヘッダはHPACK形式で圧縮され、冗長な情報を削減します。
    *   `Content-Length`ヘッダは、HTTPメッセージボディの長さをバイト単位で示すもので、特にHTTP/1.1ではボディの終端を判断するために重要でした。HTTP/2ではストリームの終端でボディの終端が示されるため、`Content-Length`の扱いはHTTP/1.1とは異なる側面があります。
    *   `Content-Type`ヘッダは、メッセージボディのメディアタイプ（例: `text/html`, `application/json`）を示すもので、クライアントがボディの内容を適切に解釈するために不可欠です。

2.  **Go言語の`net/http`パッケージ**:
    *   Goの標準ライブラリである`net/http`は、HTTPクライアントとサーバーを実装するための強力なパッケージです。HTTP/1.1とHTTP/2の両方をサポートしています。
    *   `http.ResponseWriter`インターフェースは、HTTPサーバーハンドラがクライアントにレスポンスを書き込むために使用します。
    *   `http.Request`構造体は、受信したHTTPリクエストの情報をカプセル化します。
    *   `http.Client`は、HTTPリクエストを送信するためのクライアントを提供します。
    *   `h2_bundle.go`ファイルは、`golang.org/x/net/http2`パッケージのコードが`net/http`パッケージ内にバンドルされている部分です。これにより、外部依存なしにHTTP/2機能を提供しています。

3.  **Go言語のテストフレームワーク**:
    *   Goは標準で`testing`パッケージを提供しており、ユニットテストやベンチマークテストを記述できます。
    *   `t.Errorf`や`t.Fatalf`などのメソッドを使用してテストの失敗を報告します。
    *   `h12Compare`のようなテストヘルパー構造体は、HTTP/1とHTTP/2の両方で同じテストロジックを実行し、両プロトコル間での挙動の一貫性を検証するために使用されます。

## 技術的詳細

このコミットは、主に以下の2つのファイルに影響を与えています。

1.  **`src/net/http/h2_bundle.go`**:
    *   このファイルは、`net/http`パッケージにバンドルされているHTTP/2プロトコル実装のコアロジックを含んでいます。
    *   変更点を見ると、`http2responseWriterState`構造体の`writeChunk`メソッド内で、`Content-Length`ヘッダと`Content-Type`ヘッダの生成ロジックが修正されています。
    *   **`Content-Length`の修正**: 以前のコードでは、`handlerDone`（ハンドラがレスポンスボディの書き込みを完了したことを示す）が`true`で、かつ`http2bodyAllowedForStatus`（現在のHTTPステータスコードでボディが許可されているか）が`true`の場合に、`Content-Length`ヘッダが設定されていました。
        *   修正後には、`len(p) > 0 || !isHeadResp`という条件が追加されています。これは、実際に書き込むデータ`p`が存在するか、またはリクエストが`HEAD`メソッドではない場合にのみ`Content-Length`を設定するという意味です。
        *   `HEAD`リクエストの場合、サーバーはボディを返しませんが、`Content-Length`ヘッダは`GET`リクエストの場合と同じ値を持つべきです。しかし、サーバーがボディを書き込まない場合、`len(p)`は0になり、誤って`Content-Length`が設定されない可能性がありました。この修正は、`HEAD`リクエストに対する`Content-Length`の正しい振る舞いを保証するためのものです。
    *   **`Content-Type`の修正**: 以前のコードでは、`rws.snapHeader.Get("Content-Type") == ""`という条件で`Content-Type`ヘッダが設定されていない場合に`DetectContentType`が呼び出されていました。
        *   修正後には、`_, hasContentType := rws.snapHeader["Content-Type"]`でヘッダの存在を直接確認し、`!hasContentType`という条件に変更されています。これは、ヘッダが存在しない場合にのみ`DetectContentType`を呼び出すことを明確にしています。`Get`メソッドはヘッダが存在しない場合に空文字列を返すため、`""`と比較するだけでは、意図的に空の`Content-Type`ヘッダが設定された場合と、ヘッダが全く存在しない場合を区別できませんでした。この修正により、`Content-Type`ヘッダの自動検出ロジックがより正確に動作するようになります。

2.  **`src/net/http/clientserver_test.go`**:
    *   このファイルには、`net/http`パッケージのクライアントとサーバーの挙動をテストするためのコードが含まれています。
    *   `h12Compare`というテストヘルパー構造体が定義されており、HTTP/1とHTTP/2の両方で同じハンドラとリクエスト関数を使用してテストを実行し、結果を比較することができます。
    *   **Issue #13532のテスト追加**: `TestH12_HeadContentLengthNoBody`, `TestH12_HeadContentLengthSmallBody`, `TestH12_HeadContentLengthLargeBody`という3つの新しいテストが追加されています。これらは、`HEAD`リクエストに対する`Content-Length`ヘッダの挙動を検証するためのものです。
        *   これらのテストは、サーバーがボディを書き込まない場合、少量書き込む場合、大量書き込む場合など、様々なシナリオで`HEAD`リクエストを送信し、`Content-Length`ヘッダが正しく設定されていることを確認します。これは、`h2_bundle.go`での`Content-Length`の修正が正しく機能していることを保証します。
    *   **Issue #13495のテスト追加**: `TestH12_ServerEmptyContentLength`というテストが追加されています。これは、サーバーが意図的に空の`Content-Type`ヘッダを設定した場合の挙動を検証するためのものです。
        *   このテストでは、ハンドラが`w.Header()["Content-Type"] = []string{""}`のように空の`Content-Type`ヘッダを設定し、その後ボディを書き込みます。このシナリオで、HTTP/2実装が`Content-Type`を自動検出せずに、意図された空のヘッダを尊重することを確認します。これは、`h2_bundle.go`での`Content-Type`の修正が正しく機能していることを保証します。
    *   `reqFunc`の型定義が`func(c *Client, url string) (*Response, error)`から`reqFunc`という新しい型エイリアスに変更され、`h12Compare`構造体内でこの型エイリアスが使用されています。これはコードの可読性と保守性を向上させるための小さなリファクタリングです。

これらの変更は、HTTP/2プロトコルの複雑なヘッダ処理において、エッジケースや特定のシナリオでの正確な挙動を保証するために重要です。特に、`HEAD`リクエストや意図的に空のヘッダを設定するケースは、プロトコル準拠の観点から正しく処理される必要があります。

## コアとなるコードの解説

### `src/net/http/clientserver_test.go` の変更点

1.  **`reqFunc` 型エイリアスの導入**:
    *   `type reqFunc func(c *Client, url string) (*Response, error)` が追加されました。これは、`http.Client`のメソッド（例: `Get`, `Head`）を抽象化するための関数型です。
    *   `h12Compare`構造体の`ReqFunc`フィールドと、その`reqFunc()`メソッドの戻り値の型が、この新しい`reqFunc`型を使用するように変更されました。これにより、コードの意図がより明確になり、可読性が向上します。

2.  **Issue #13532 関連テストの追加 (`TestH12_HeadContentLength*`)**:
    *   `HEAD`リクエストに対する`Content-Length`ヘッダの挙動を検証する3つのテストが追加されました。
    *   `TestH12_HeadContentLengthNoBody`: サーバーがボディを全く書き込まない場合の`HEAD`リクエストをテストします。
    *   `TestH12_HeadContentLengthSmallBody`: サーバーが少量のボディを書き込む場合の`HEAD`リクエストをテストします。
    *   `TestH12_HeadContentLengthLargeBody`: サーバーが大量のボディを書き込む場合の`HEAD`リクエストをテストします。
    *   これらのテストは、`h12Compare`ヘルパーを使用してHTTP/1とHTTP/2の両方で実行され、`HEAD`リクエストに対する`Content-Length`ヘッダが、対応する`GET`リクエストのボディ長と一致することを確認します。これは、HTTP/2実装が`HEAD`リクエストのセマンティクスを正しく処理していることを保証するために重要です。

3.  **Issue #13495 関連テストの追加 (`TestH12_ServerEmptyContentLength`)**:
    *   サーバーが意図的に空の`Content-Type`ヘッダを設定した場合の挙動を検証するテストが追加されました。
    *   このテストでは、ハンドラ内で`w.Header()["Content-Type"] = []string{""}`として`Content-Type`ヘッダを明示的に空に設定します。
    *   このテストの目的は、HTTP/2実装が、ハンドラによって明示的に設定された空の`Content-Type`ヘッダを尊重し、ボディの内容に基づいて自動的に`Content-Type`を検出しないことを確認することです。

### `src/net/http/h2_bundle.go` の変更点

1.  **`Content-Length`ヘッダ生成ロジックの修正**:
    *   変更前: `if clen == "" && rws.handlerDone && http2bodyAllowedForStatus(rws.status) {`
    *   変更後: `if clen == "" && rws.handlerDone && http2bodyAllowedForStatus(rws.status) && (len(p) > 0 || !isHeadResp) {`
    *   この修正は、`Content-Length`ヘッダを設定する条件に`(len(p) > 0 || !isHeadResp)`という条件を追加しています。
        *   `len(p) > 0`: 実際に書き込むボディデータが存在する場合。
        *   `!isHeadResp`: リクエストが`HEAD`メソッドではない場合。
    *   この追加により、`HEAD`リクエストの場合でも、`Content-Length`ヘッダが正しく設定されるようになります。`HEAD`リクエストではボディは送信されませんが、`Content-Length`ヘッダは対応する`GET`リクエストのボディ長を示すべきです。以前の実装では、`len(p)`が0の場合に`Content-Length`が設定されない可能性がありましたが、この修正により、`HEAD`リクエストであっても`Content-Length`が適切に処理されるようになります。

2.  **`Content-Type`ヘッダ自動検出ロジックの修正**:
    *   変更前: `if rws.snapHeader.Get("Content-Type") == "" && http2bodyAllowedForStatus(rws.status) {`
    *   変更後: `_, hasContentType := rws.snapHeader["Content-Type"]`
                `if !hasContentType && http2bodyAllowedForStatus(rws.status) {`
    *   この修正は、`Content-Type`ヘッダが設定されているかどうかを判断する方法を変更しています。
        *   以前は`Get("Content-Type") == ""`でチェックしていましたが、これはヘッダが存在しない場合と、ヘッダが明示的に空文字列に設定されている場合を区別できませんでした。
        *   新しいコードでは、`rws.snapHeader["Content-Type"]`を使用してマップから直接値を取得し、`hasContentType`というブール値でヘッダの存在を正確に確認しています。
    *   これにより、ハンドラが意図的に空の`Content-Type`ヘッダを設定した場合（Issue #13495のシナリオ）、HTTP/2実装がその意図を尊重し、ボディの内容に基づいて`Content-Type`を自動検出することを避けることができます。

これらの変更は、HTTP/2プロトコルにおけるヘッダ処理の正確性を高め、特にエッジケースでの挙動を改善することを目的としています。

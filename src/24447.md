# [インデックス 24447] ファイルの概要

このコミットは、GoランタイムおよびリフレクションパッケージにおけるARM64アーキテクチャでのスタックフレームサイズのアライメントに関する修正です。具体的には、ARM64のABI（Application Binary Interface）要件に従い、スタックフレームが正しくアラインされるようにアセンブリコードを更新しています。

Author: Russ Cox <rsc@golang.org>
Date:   Wed Jul 29 15:04:30 2015 -0400

    runtime, reflect: use correctly aligned stack frame sizes on arm64
    
    arm64 requires either no stack frame or a frame with a size that is 8 mod 16
    (adding the saved LR will make it 16-aligned).
    
    The cmd/internal/obj/arm64 has been silently aligning frames, but it led to
    a terrible bug when the compiler and obj disagreed on the frame size,
    and it's just generally confusing, so we're going to make misaligned frames
    an error instead of something that is silently changed.

    Note that the changes in this CL are already being done silently by
    cmd/internal/obj/arm64, so there is no semantic effect here,

このCLでの変更は、cmd/internal/obj/arm64によってすでに暗黙的に行われているため、意味的な影響はなく、明確化の効果のみです。

#9880に対応。

## 変更の背景

ARM64アーキテクチャでは、関数呼び出し規約（ABI）によってスタックフレームのアライメントに特定の要件があります。具体的には、スタックポインタ（SP）は常に16バイト境界にアラインされている必要があります。関数がスタックフレームを割り当てる際、リターンアドレスを格納するためのリンクレジスタ（LR）をスタックに保存することが一般的です。このLRの保存によってスタックフレームのサイズが変化するため、最終的なスタックフレームの合計サイズが16バイトアラインになるように、ローカル変数や一時領域のために確保するスタックフレームのサイズを調整する必要があります。

以前のGoコンパイラ（`cmd/internal/obj/arm64`）は、このARM64のABI要件を満たすために、生成されるアセンブリコードにおいてスタックフレームサイズを暗黙的に調整していました。しかし、この「暗黙的なアライメント」は、コンパイラが想定するフレームサイズと、実際にオブジェクトファイルが生成される際に適用されるアライメントが食い違う場合に、検出が困難なバグを引き起こす可能性がありました。このような不一致は、特に複雑な関数や最適化が絡む場合に発生しやすく、デバッグを非常に困難にします。

このコミットの目的は、このような暗黙的な動作を排除し、スタックフレームサイズのアライメント要件をアセンブリコード内で明示的に指定することで、コードの明確性を高め、将来的なバグのリスクを低減することにあります。これにより、コンパイラとアセンブラの間でのフレームサイズに関する認識のずれを防ぎ、より堅牢なコード生成を実現します。

## 前提知識の解説

### ARM64アーキテクチャとABI

ARM64（AArch64）は、64ビットのARMプロセッサアーキテクチャです。このアーキテクチャには、関数呼び出し規約（Application Binary Interface, ABI）が定義されており、関数がどのように引数を渡し、戻り値を返し、レジスタを使用し、スタックを管理するかを規定しています。

- **スタックアライメント**: ARM64のABIでは、スタックポインタ（SP）が常に16バイト境界にアラインされている必要があります。これは、特定の命令（例: SIMD命令）が16バイトアラインされたメモリへのアクセスを要求するため、パフォーマンスと正確性を保証するために重要です。
- **リンクレジスタ（LR）**: 関数が別の関数を呼び出す際、呼び出し元に戻るためのアドレス（リターンアドレス）をLRレジスタに保存します。関数がスタックフレームを持つ場合、このLRレジスタの値は通常、スタックに保存されます。LRは8バイトのレジスタです。
- **スタックフレーム**: 関数が実行中に使用するスタック上の領域です。これには、ローカル変数、保存されたレジスタ（LRを含む）、引数などが含まれます。

### スタックフレームサイズとアライメントの計算

ARM64のABI要件を満たすためには、関数がスタックフレームを割り当てる際、以下の条件を満たす必要があります。

1.  **関数エントリ時**: スタックポインタ（SP）は16バイトアラインされている。
2.  **LR保存時**: 関数がLRをスタックに保存する場合、その保存によってSPが移動します。この移動後もSPは16バイトアラインを維持する必要があります。
3.  **スタックフレーム合計サイズ**: 関数が使用するスタックフレームの合計サイズ（ローカル変数、保存されたレジスタなど全てを含む）は、LRが保存されることを考慮して、最終的にSPが16バイトアラインになるように調整される必要があります。

コミットメッセージにある「8 mod 16」という表現は、LR（8バイト）がスタックに保存されることを前提としたスタックフレームのサイズを指しています。
- もし関数がローカル変数などのために `S` バイトのスタック領域を必要とし、LRをスタックに保存する場合、合計で `S + 8` バイトのスタックが消費されます。
- この `S + 8` が16の倍数である必要があります。
- したがって、`S` は `8 mod 16` である必要があります（例: 8, 24, 40, ...）。
- `S` が `8 mod 16` であれば、`S + 8` は `(8 mod 16) + 8 = 16 mod 16 = 0 mod 16` となり、16バイトアラインが達成されます。

### Goのアセンブリと`TEXT`ディレクティブ

Go言語では、一部のパフォーマンスクリティカルな部分や、特定のアーキテクチャに依存する処理のために、Goアセンブリ（Plan 9アセンブリの派生）を使用します。
`TEXT`ディレクティブは、Goアセンブリで関数を定義するために使用されます。

`TEXT ·funcname(SB),flags,$framesize-argsize`

- `funcname`: 関数の名前。
- `SB`: スタティックベースレジスタ。グローバルシンボルへのオフセットを指定するために使用されます。
- `flags`: 関数の特性を示すフラグ（例: `NOSPLIT`はスタックの分割を無効にします）。
- `$framesize`: この関数がローカル変数などのために割り当てるスタックフレームのサイズ。この値が今回のコミットで変更されています。
- `argsize`: この関数が引数として受け取るバイト数。

## 技術的詳細

このコミットの核心は、ARM64アーキテクチャにおけるスタックフレームのアライメント要件を、Goのアセンブリコード内で明示的に満たすように変更することです。

以前は、Goコンパイラのバックエンドである`cmd/internal/obj/arm64`が、生成されたアセンブリコードのスタックフレームサイズをABI要件に合わせて暗黙的に調整していました。例えば、アセンブリコードで`$16`と指定されていても、実際には`$24`として扱われるような状況です。これは、コンパイラがABIを「知っている」ため、開発者が明示的に正しいサイズを指定しなくても、最終的には正しいアラインメントが保証されるという考えに基づいていた可能性があります。

しかし、この暗黙的な動作は以下の問題を引き起こしました。

1.  **コンパイラとアセンブラの不一致**: コンパイラがスタックフレームのサイズを計算するロジックと、アセンブラが実際にフレームをアラインするロジックが完全に同期していない場合、スタックフレームのサイズに関する認識のずれが生じます。これは、特に複雑な最適化や、ABIの微妙な変更があった場合に、予測不能なバグ（例: スタックオーバーフロー、データ破損）につながる可能性があります。コミットメッセージでは「terrible bug when the compiler and obj disagreed on the frame size」と明記されています。
2.  **コードの不明瞭さ**: アセンブリコードに書かれているフレームサイズと、実際に実行時に使用されるフレームサイズが異なるため、コードを読む開発者にとっては混乱の元となります。なぜ`$16`と書かれているのに、実際には`$24`が使われるのか、という疑問が生じます。これはデバッグやメンテナンスを困難にします。

このコミットでは、これらの問題を解決するために、アセンブリコード内の`TEXT`ディレクティブで指定されるスタックフレームサイズを、ARM64のABI要件に厳密に合致するように明示的に変更しています。

具体的には、LR（8バイト）がスタックに保存されることを考慮し、ローカル変数などのために確保するスタックフレームのサイズを「8 mod 16」となるように調整しています。これにより、LRが保存された後の合計スタックフレームサイズが16バイトアラインメントを満たすようになります。

例えば、元のスタックフレームサイズが`$16`だった場合、LRの8バイトが加わると合計`24`バイトになります。`24`は`16`の倍数ではないため、ABI要件を満たしません。このコミットでは、ローカル変数などのためのスタックフレームサイズを`$24`に変更しています。これにより、LRの8バイトが加わると合計`32`バイトとなり、`32`は`16`の倍数であるため、正しくアラインされます。

コミットメッセージにある「no semantic effect here, just a clarity effect」という記述は、`cmd/internal/obj/arm64`がすでに暗黙的に正しいアライメントを行っていたため、この変更によってプログラムの動作自体が変わるわけではないことを意味します。しかし、コードの意図が明確になり、将来的なバグの発生を防ぐ上で非常に重要な変更です。

この変更は、アラインされていないフレームをエラーとして扱うための準備段階でもあります。将来的には、コンパイラやリンカがアラインされていないフレームを検出した場合に、ビルドエラーを発生させることで、開発者が早期に問題を特定し修正できるようにする方針が示唆されています。

## コアとなるコードの変更箇所

変更は主に以下の3つのアセンブリファイルで行われています。

1.  `src/reflect/asm_arm64.s`
2.  `src/runtime/asm_arm64.s`
3.  `src/runtime/sys_linux_arm64.s`

これらのファイルでは、`TEXT`ディレクティブで定義されている関数のスタックフレームサイズ（`$framesize`の部分）が変更されています。

### `src/reflect/asm_arm64.s`

-   `TEXT ·makeFuncStub(SB),(NOSPLIT|WRAPPER),$16` が `$24` に変更。
-   `TEXT ·methodValueCall(SB),(NOSPLIT|WRAPPER),$16` が `$24` に変更。

### `src/runtime/asm_arm64.s`

-   `CALLFN`マクロを使用している一連の関数（`·call16`から`·call1073741824`まで）のスタックフレームサイズが、元の値に8を加えた値に変更されています。
    -   例: `CALLFN(·call16, 16)` が `CALLFN(·call16, 24)` に変更。
    -   これは、元のフレームサイズに8バイト（LR用）を追加した結果が16の倍数になるように調整されたものです。
-   `TEXT ·cgocallback_gofunc(SB),NOSPLIT,$16-24` が `$24-24` に変更。
-   `TEXT _cgo_topofstack(SB),NOSPLIT,$16` が `$24` に変更。

### `src/runtime/sys_linux_arm64.s`

-   `TEXT runtime·usleep(SB),NOSPLIT,$16-4` が `$24-4` に変更。
-   `TEXT time·now(SB),NOSPLIT,$16-12` が `$24-12` に変更。
-   `TEXT runtime·nanotime(SB),NOSPLIT,$16-8` が `$24-8` に変更。

## コアとなるコードの解説

変更のほとんどは、`TEXT`ディレクティブの`$framesize`部分の数値の変更です。

例として、`src/reflect/asm_arm64.s`の`makeFuncStub`関数を見てみましょう。

**変更前:**
```go
TEXT ·makeFuncStub(SB),(NOSPLIT|WRAPPER),$16
```
ここでは、`makeFuncStub`関数がローカル変数などのために16バイトのスタックフレームを割り当てると宣言しています。しかし、ARM64のABIでは、LR（8バイト）がスタックに保存されることを考慮すると、合計スタック使用量は`16 + 8 = 24`バイトとなり、これは16バイトアラインではありません。

**変更後:**
```go
TEXT ·makeFuncStub(SB),(NOSPLIT|WRAPPER),$24
```
変更後では、ローカル変数などのために24バイトのスタックフレームを割り当てると宣言しています。LRの8バイトが加わると、合計スタック使用量は`24 + 8 = 32`バイトとなります。`32`は16の倍数であるため、正しく16バイトアラインされます。

`src/runtime/asm_arm64.s`の`CALLFN`マクロの変更も同様の理由です。`CALLFN`は様々なサイズのスタックフレームを持つ関数を生成するためのマクロであり、それぞれの関数がABI要件を満たすようにフレームサイズが調整されています。コメントにも「These have 8 added to make the overall frame size a multiple of 16, as required by the ABI. (There is another +8 for the saved LR.)」と明記されており、LRのために8バイトが追加されることを考慮して、全体のフレームサイズが16の倍数になるように調整されていることがわかります。

これらの変更は、GoのアセンブリコードがARM64のABIに明示的に準拠するようにすることで、コンパイラの暗黙的な動作に依存することなく、スタックフレームのアライメントが保証されるようにしています。これにより、コードの意図が明確になり、将来的にアライメントの不一致によるバグが発生するリスクが低減されます。

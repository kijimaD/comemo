# [インデックス 25506] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）に関連する`src/runtime/mgc.go`ファイルを変更します。

## コミット

Goランタイムの並行マークフェーズのセットアップ処理を、システムスタックから通常のゴルーチンスタックへ移動させる変更です。これにより、システムスタック上で実行されるコードの範囲が最小限に抑えられ、コードのクリーンアップと保守性の向上が図られています。

## 変更の背景

Goのガベージコレクタ（GC）は、アプリケーションの実行と並行して動作する「並行GC」を採用しています。この並行GCの「マークフェーズ」を開始する際、歴史的な理由から多くのセットアップ処理がシステムスタック上で実行されていました。

システムスタックは、Goランタイムの内部処理やシグナルハンドラなどで使用される特別なスタックであり、通常のゴルーチンスタックとは異なる特性を持ちます。システムスタック上での処理は、その性質上、非常に注意深く扱われるべきであり、必要最小限のコードのみが実行されることが望ましいです。

このコミットの背景には、並行マークフェーズのセットアップにおいて、実際にシステムスタック上で実行する必要があるのは「Stop-the-World (STW)」フェーズの終了と「Worldの再開（start-the-world）」のみであるという認識がありました。それ以外の処理は、通常のゴルーチンスタック上で安全に実行できるため、システムスタックの利用範囲を最小限に絞り込むことで、コードの複雑性を減らし、潜在的なバグのリスクを低減し、ランタイムの健全性を向上させる目的がありました。

コミットメッセージにもあるように、この変更は主にコードのクリーンアップとリファクタリングであり、機能的な変更は伴いません。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する知識が必要です。

1.  **Goのガベージコレクタ (GC)**:
    *   GoのGCは、主に三色マーク＆スイープアルゴリズムをベースにした並行（Concurrent）かつ低遅延（Low-latency）なGCです。
    *   **Stop-the-World (STW)**: GCの特定のフェーズ（例えば、マークフェーズの開始や終了）では、すべてのゴルーチンの実行を一時的に停止させる必要があります。これをSTWと呼びます。GoのGCはSTW時間を極力短くするように設計されています。
    *   **並行マークフェーズ**: STW中にGCルート（グローバル変数、スタック上の変数など）をスキャンした後、GCはアプリケーションのゴルーチンと並行して到達可能なオブジェクトをマークしていきます。
    *   **ライトバリア (Write Barrier)**: 並行GC中にミューテータ（アプリケーションのゴルーチン）がヒープ上のポインタを書き換える際に、GCの正確性を保つために実行される特別な処理です。これにより、GCがオブジェクトを見落とすことを防ぎます。

2.  **Goのスタック**:
    *   **ゴルーチンスタック**: 各ゴルーチンが持つスタックで、動的にサイズが変更されます。通常のGoコードはここで実行されます。
    *   **システムスタック**: Goランタイムの内部処理（スケジューラ、GC、シグナルハンドラなど）が実行される際に使用される特別なスタックです。これは固定サイズであり、通常のゴルーチンスタックとは異なるメモリ領域に存在します。`systemstack`関数は、現在のゴルーチンスタックからシステムスタックに切り替えてコードを実行するために使用されます。システムスタック上での実行は、スタックオーバーフローのリスクやデバッグの複雑さが増すため、最小限に抑えるべきです。

3.  **`gc(mode gcMode)`関数**:
    *   `src/runtime/mgc.go`に定義されている、Goのガベージコレクションのメインエントリポイントとなる関数です。GCの各フェーズ（マーク、スイープなど）の調整を行います。

4.  **`startTheWorldWithSema()`**:
    *   STWフェーズを終了し、停止していたすべてのP（Processor、Goスケジューラの論理CPU）を再開させる関数です。これにより、アプリケーションのゴルーチンが再び実行を開始します。

5.  **`atomicstore(&gcBlackenEnabled, 1)`**:
    *   `atomicstore`はアトミック操作でメモリに値を書き込む関数です。`gcBlackenEnabled`フラグを1に設定することで、ライトバリアが有効になり、ミューテータアシスト（GCが追いつかない場合にミューテータにGC作業を分担させる仕組み）が開始されます。

## 技術的詳細

このコミットの技術的な核心は、`gc`関数内で`systemstack`の呼び出し範囲を極限まで狭めた点にあります。

変更前は、`systemstack(func() { ... })`という形で、並行マークフェーズのセットアップに関する多くの処理（`setGCPhase`、`gcCopySpans`、`gcBgMarkPrepare`、`gcMarkRootPrepare`、`atomicstore(&gcBlackenEnabled, 1)`など）が匿名関数として`systemstack`に渡され、システムスタック上で実行されていました。

しかし、これらの処理のほとんどは、STWが終了し、ゴルーチンが再開される前に完了していれば、システムスタック上で実行される必要はありません。通常のゴルーチンスタック上で実行しても問題ない、あるいはむしろその方が望ましい処理です。システムスタックは限られたリソースであり、その上で複雑な処理を実行することは、スタックオーバーフローの可能性を高めたり、デバッグを困難にしたりする可能性があります。

このコミットでは、`systemstack`の呼び出しを`systemstack(startTheWorldWithSema)`という形に修正しました。これにより、システムスタック上で実行されるのは`startTheWorldWithSema`関数のみとなり、STWの終了とWorldの再開という、システムスタック上で実行されるべき唯一の処理に限定されます。それ以外のセットアップ処理は、`systemstack`の呼び出しの外側に移動され、通常のゴルーチンスタック上で実行されるようになりました。

コミットメッセージが「The diff for this change looks large, but the only code change is to narrow the systemstack call. Everything else is re-indentation.」と述べているように、コードの機能的な変更はほとんどなく、主にコードの構造と実行コンテキストの整理が目的です。これにより、GoランタイムのGCコードの可読性、保守性、そして堅牢性が向上します。

## コアとなるコードの変更箇所

`src/runtime/mgc.go`ファイルの`gc`関数内の変更です。

変更前:
```go
		systemstack(func() {
			// Enter concurrent mark phase and enable
			// write barriers.
			// ... (多くのセットアップ処理) ...
			setGCPhase(_GCmark)
			gcCopySpans()
			gcBgMarkPrepare() // Must happen before assist enable.
			gcMarkRootPrepare()
			atomicstore(&gcBlackenEnabled, 1)

			// Concurrent mark.
			startTheWorldWithSema()
			now = nanotime()
			work.pauseNS += now - work.pauseStart
			gcController.assistStartTime = now
		})
```

変更後:
```go
		// Enter concurrent mark phase and enable
		// write barriers.
		// ... (多くのセットアップ処理) ...
		setGCPhase(_GCmark)

		// markrootSpans uses work.spans, so make sure
		// it is up to date.
		gcCopySpans()

		gcBgMarkPrepare() // Must happen before assist enable.
		gcMarkRootPrepare()

		// At this point all Ps have enabled the write
		// barrier, thus maintaining the no white to
		// black invariant. Enable mutator assists to
		// put back-pressure on fast allocating
		// mutators.
		atomicstore(&gcBlackenEnabled, 1)

		// Concurrent mark.
		systemstack(startTheWorldWithSema)
		now = nanotime()
		work.pauseNS += now - work.pauseStart
		gcController.assistStartTime = now
```

## コアとなるコードの解説

変更の核心は、`systemstack`関数への呼び出し方が変わった点です。

*   **変更前**: `systemstack`は、並行マークフェーズの開始に必要な一連のセットアップ処理（`setGCPhase`, `gcCopySpans`, `gcBgMarkPrepare`, `gcMarkRootPrepare`, `atomicstore(&gcBlackenEnabled, 1)`）と、実際にWorldを再開する`startTheWorldWithSema`をすべて含む匿名関数を引数として受け取っていました。これにより、これらの処理全体がシステムスタック上で実行されていました。

*   **変更後**: 上記のセットアップ処理は`systemstack`の呼び出しの外側に移動され、通常のゴルーチンスタック上で実行されるようになりました。`systemstack`関数に渡される引数は`startTheWorldWithSema`関数ポインタのみとなり、システムスタック上で実行されるコードは`startTheWorldWithSema`の内部処理に限定されます。

この変更により、システムスタックの利用が最小限に抑えられ、ランタイムの内部構造がより明確になりました。システムスタックは、本当に低レベルで特権的な操作（この場合はSTWの終了とPの再開）が必要な場合にのみ使用されるべきであるという原則に沿った改善です。これにより、コードの意図がより明確になり、将来的なメンテナンスやデバッグが容易になります。

The commit `384259628460f9975471332a0618d5bffa40507d` (index 25506) is titled "runtime: move concurrent mark setup off system stack".

This commit refactors the `gc` function in `src/runtime/mgc.go` to reduce the amount of code executed on the system stack during the setup of the concurrent mark phase.

**Background:**
In Go, the garbage collector (GC) operates in several phases. The "concurrent mark" phase is where the GC identifies live objects in the heap while user goroutines are still running. To ensure correctness and minimize "Stop-the-World" (STW) pauses, certain setup operations, like enabling write barriers, need to happen at specific times.

Historically, a significant portion of this concurrent mark setup was performed on the system stack. The system stack is a special stack used by the Go runtime for critical operations, distinct from the regular goroutine stacks. While necessary for some low-level operations (like switching contexts or handling signals), executing extensive code on the system stack can be less flexible and potentially harder to debug than on a goroutine stack.

The commit author identified that, at this point in the Go runtime's evolution, the *only* operation that truly required execution on the system stack during this setup was `startTheWorldWithSema()`, which signals the end of the STW pause and resumes user goroutines. All other setup tasks could safely and more cleanly be performed on a regular goroutine stack.

**Purpose of the Change:**
The primary goal of this commit is code cleanup and improved clarity. By narrowing the `systemstack` call to only the essential `startTheWorldWithSema()` function, the code explicitly states which operations absolutely require the system stack context. This makes the runtime code easier to understand, maintain, and potentially reduces the risk of issues related to system stack usage. The commit message explicitly states that the diff looks large mainly due to re-indentation, with the actual code change being minimal.

**Technical Details:**
The `gc` function orchestrates the entire garbage collection process. Within this function, there's a block of code responsible for initiating the concurrent mark phase.

Before this commit, a large anonymous function containing several setup steps was passed to `systemstack`. This meant that all these steps were executed on the system stack:
*   `setGCPhase(_GCmark)`: Sets the current GC phase to marking.
*   `gcCopySpans()`: Ensures `work.spans` is up to date for root scanning.
*   `gcBgMarkPrepare()`: Prepares for background marking.
*   `gcMarkRootPrepare()`: Prepares for root marking.
*   `atomicstore(&gcBlackenEnabled, 1)`: Atomically enables write barriers and mutator assists.
*   `startTheWorldWithSema()`: Resumes user goroutines.

The change moves all the setup operations *before* `startTheWorldWithSema()` out of the `systemstack` call. These operations are now executed on the regular goroutine stack. Only `startTheWorldWithSema()` remains wrapped by `systemstack`.

This refactoring doesn't change the functional behavior of the GC. The order of operations remains the same, and write barriers are still enabled before the world restarts. The key difference is *where* these operations are executed. By moving non-critical system stack operations to the goroutine stack, the runtime adheres more closely to the principle of using the system stack only when absolutely necessary, leading to a cleaner and more robust codebase.

**Core Code Changes:**

The primary change is in `src/runtime/mgc.go`, specifically within the `gc` function.

**Before the change:**
```go
		systemstack(func() {
			// Enter concurrent mark phase and enable
			// write barriers.
			// ... (comments explaining write barrier necessity) ...
			setGCPhase(_GCmark)

			// markrootSpans uses work.spans, so make sure
			// it is up to date.
			gcCopySpans()

			gcBgMarkPrepare() // Must happen before assist enable.
			gcMarkRootPrepare()

			// At this point all Ps have enabled the write
			// barrier, thus maintaining the no white to
			// black invariant. Enable mutator assists to
			// put back-pressure on fast allocating
			// mutators.
			atomicstore(&gcBlackenEnabled, 1)

			// Concurrent mark.
			startTheWorldWithSema()
			now = nanotime()
			work.pauseNS += now - work.pauseStart
			gcController.assistStartTime = now
		})
```

**After the change:**
```go
		// Enter concurrent mark phase and enable
		// write barriers.
		// ... (comments explaining write barrier necessity) ...
		setGCPhase(_GCmark)

		// markrootSpans uses work.spans, so make sure
		// it is up to date.
		gcCopySpans()

		gcBgMarkPrepare() // Must happen before assist enable.
		gcMarkRootPrepare()

		// At this point all Ps have enabled the write
		// barrier, thus maintaining the no white to
		// black invariant. Enable mutator assists to
		// put back-pressure on fast allocating
		// mutators.
		atomicstore(&gcBlackenEnabled, 1)

		// Concurrent mark.
		systemstack(startTheWorldWithSema) // Only this remains on system stack
		now = nanotime()
		work.pauseNS += now - work.pauseStart
		gcController.assistStartTime = now
```

**Core Code Explanation:**

The key modification is the transformation of the `systemstack` call. Previously, `systemstack` took an anonymous function that encapsulated a series of GC setup operations. This meant all those operations were executed on the system stack.

The refactoring moves the initial setup calls (`setGCPhase`, `gcCopySpans`, `gcBgMarkPrepare`, `gcMarkRootPrepare`, `atomicstore`) *outside* the `systemstack` block. These functions are now called directly within the `gc` function's scope, meaning they execute on the current goroutine's stack.

The `systemstack` call is now much narrower: `systemstack(startTheWorldWithSema)`. This explicitly limits the system stack usage to only the `startTheWorldWithSema` function, which is responsible for ending the STW pause and resuming the execution of all goroutines. This is a critical, low-level operation that benefits from being on the system stack.

This change improves the clarity of the code by making it explicit which operations truly require the system stack and which can be handled by the more flexible goroutine stack. It's a good practice to minimize system stack usage to reduce complexity and potential issues.

# [インデックス 27415] ファイルの概要

## 変更の背景

このコミットは、GoランタイムがSolaris/AMD64環境でシグナルを処理する際に発生していた不具合を修正するために導入されました。コミットメッセージによると、この問題は以前のコミット `https://go-review.googlesource.com/21006` で意図せず導入されたものでした。

具体的な問題は、シグナル発生時にOSからGoランタイムのシグナルハンドラ（`runtime·sigtramp`）に渡されるシグナルコンテキスト情報（`siginfo`と`ucontext`）の処理方法にありました。以前の変更により、これらの構造体がスタック上で正しく配置されなかったか、あるいはそのポインタが誤って解釈される可能性が生じていました。結果として、Goランタイムがシグナル発生時のプロセスの状態を正確に把握できず、シグナル処理が不安定になったり、クラッシュを引き起こしたりする可能性がありました。

このコミットは、`sigtramp`アセンブリコードにおけるスタックフレームのセットアップと、`siginfo`および`ucontext`ポインタの取得方法を修正することで、この回帰バグを解決し、Solaris上でのGoプログラムの堅牢性を向上させることを目的としています。

## 前提知識の解説

### Goランタイムのシグナルハンドリング

Goプログラムは、OSからのシグナル（例: `SIGINT`、`SIGSEGV`）を独自の方法で処理します。これは、`os/signal`パッケージを通じてユーザーがシグナルを捕捉できるようにするためだけでなく、Goランタイム自身がガーベージコレクション、スケジューラ、デッドロック検出などの内部処理のためにシグナルを利用するためでもあります。

Goランタイムは、プログラム起動時に`sigaction`システムコールを使用して、特定のシグナルに対するカスタムハンドラを登録します。シグナルが発生すると、OSはGoランタイムが登録した低レベルなシグナルハンドラ（通常はアセンブリコードで実装された`sigtramp`関数）を呼び出します。このハンドラは、シグナルに関する情報（`siginfo`）と、シグナル発生時のCPUの状態（レジスタ、スタックポインタなどを含む`ucontext`）を受け取ります。

`sigtramp`の主な役割は、OSから受け取った情報をGoランタイムのC/Goコードが処理できる形式に変換し、適切なGoルーチンにシグナル処理を委譲することです。

### Solarisのシグナルコンテキスト

Unix系OSでは、シグナルハンドラが呼び出される際に、シグナルに関する詳細情報と、シグナル発生時のプロセスのコンテキストが渡されます。

*   **`siginfo_t`構造体**: 発生したシグナルの種類、シグナルを送信したプロセスID、シグナルに関連するエラーコードやアドレスなど、シグナルに関する詳細な情報を含みます。
*   **`ucontext_t`構造体**: シグナル発生時のプロセスの実行コンテキスト（CPUレジスタの値、スタックポインタ、プログラムカウンタ、シグナルマスクなど）を保存します。これにより、シグナルハンドラはシグナル発生時のプロセスの状態を検査したり、必要に応じて変更したりすることができます。

これらの構造体は、シグナルハンドラがシグナルを適切に処理し、場合によってはクラッシュの原因を特定したり、回復処理を行ったりするために不可欠です。

### `sigtramp`とアセンブリコード

`sigtramp`は、Goランタイムのシグナルハンドリングの最前線に位置するアセンブリコードの関数です。OSがシグナルをGoプロセスに送信すると、カーネルは`sigtramp`を呼び出し、`siginfo_t`と`ucontext_t`へのポインタを特定のレジスタ（AMD64では通常`RSI`と`RDX`）に格納して渡します。

`sigtramp`の役割は以下の通りです。
1.  OSから渡されたレジスタの値を保存する。
2.  GoランタイムのC/Go関数を呼び出すためのスタックフレームを適切に設定する。
3.  `siginfo_t`と`ucontext_t`のポインタを、GoランタイムのC/Go関数が期待する引数の位置に配置する。
4.  GoランタイムのC/Go関数（例: `runtime·badsignal`）を呼び出し、シグナル処理を委譲する。

このアセンブリコードはOSとGoランタイムの間の重要な橋渡し役であり、その実装はOSやアーキテクチャに強く依存します。

### AMD64の関数呼び出し規約

AMD64アーキテクチャでは、関数呼び出しの際に引数をレジスタで渡すことが一般的です。Linux/SolarisのSystem V AMD64 ABIでは、最初の6つの整数/ポインタ引数は`RDI`, `RSI`, `RDX`, `RCX`, `R8`, `R9`レジスタで渡されます。それ以降の引数はスタックにプッシュされます。

また、スタックポインタ`RSP`（アセンブリでは`SP`と表記されることが多い）は、常に16バイトアラインメントされている必要があります。関数内でローカル変数や引数をスタックに保存する場合、このアラインメントを維持するように注意が必要です。

## 技術的詳細

このコミットの技術的詳細は、主にSolaris/AMD64環境におけるGoランタイムのシグナルハンドラ`runtime·sigtramp`のアセンブリコードの変更に集約されます。

### `makesigctxt`関数の削除

`src/runtime/signal_solaris_amd64.go`から`makesigctxt`関数が削除されました。この関数は、`siginfo`と`ucontext`のポインタを受け取り、それらを含む`sigctxt`構造体を作成して返していました。

```go
// 変更前
func makesigctxt(info *siginfo, ctxt unsafe.Pointer) *sigctxt {
	return &sigctxt{info, ctxt}
}

// 変更後: この関数が完全に削除された
```

この削除は、`sigtramp`アセンブリコードが`siginfo`と`ucontext`のポインタを直接操作するように変更されたため、中間的な`sigctxt`オブジェクトを作成する必要がなくなったことを意味します。これにより、不要なメモリ割り当てやポインタの多重間接参照が回避され、より直接的かつ効率的なコンテキストアクセスが可能になります。

### `runtime·sigtramp`アセンブリコードの変更

最も重要な変更は、`src/runtime/sys_solaris_amd64.s`内の`runtime·sigtramp`関数にあります。この関数は、OSからシグナルハンドラが呼び出されたときに実行されるアセンブリコードです。

変更の核心は、`siginfo`と`ucontext`のポインタをスタックに保存し、`runtime·badsignal`関数に渡す方法の修正です。

**変更前のアセンブリコードの挙動:**

```assembly
	MOVQ	SI, 0(SP)   // siginfoへのポインタ (RSI) をスタックの0(SP)に保存
	MOVQ	DX, 8(SP)   // ucontextへのポインタ (RDX) をスタックの8(SP)に保存
	CALL	runtime·makesigctxt(SB) // makesigctxtを呼び出し、sigctxtオブジェクトを作成
	MOVQ	16(SP), AX  // makesigctxtの戻り値（sigctxtへのポインタ）をAXにロード
```

このコードでは、`siginfo`と`ucontext`をスタックに保存した後、`runtime·makesigctxt`を呼び出して`sigctxt`オブジェクトを作成し、そのポインタを`AX`レジスタにロードしていました。`makesigctxt`はGo関数であるため、呼び出し規約に従ってスタックフレームが設定され、戻り値が処理されます。

**変更後のアセンブリコードの挙動:**

```assembly
	MOVQ	SI, 80(SP)  // siginfoへのポインタ (RSI) をスタックの80(SP)に保存
	MOVQ	DX, 88(SP)  // ucontextへのポインタ (RDX) をスタックの88(SP)に保存
	LEAQ	80(SP), AX  // スタックの80(SP)のアドレスをAXにロード (siginfoへのポインタ)
```

変更点:
1.  **スタックオフセットの変更**: `siginfo`と`ucontext`のポインタが、スタックの`0(SP)`と`8(SP)`ではなく、`80(SP)`と`88(SP)`に保存されるようになりました。これは、`sigtramp`関数が使用するスタックフレームのレイアウトが変更されたか、または`runtime·badsignal`が期待する引数の位置に合わせて調整されたことを示唆しています。特に、Goの関数呼び出し規約では、呼び出し元が呼び出し先の引数をスタックにプッシュする際に、一定のオフセットを確保することがあります。この変更は、そのオフセットの不一致を修正した可能性があります。
2.  **`makesigctxt`呼び出しの削除**: `CALL runtime·makesigctxt(SB)`が削除されました。これにより、Go関数呼び出しに伴うオーバーヘッドがなくなります。
3.  **`LEAQ`命令の使用**: `LEAQ 80(SP), AX`命令が導入されました。`LEAQ` (Load Effective Address) 命令は、オペランドのアドレスをレジスタにロードします。ここでは、スタック上の`80(SP)`番地（`siginfo`ポインタが保存されている場所）のアドレスを`AX`レジスタにロードしています。これは、`runtime·badsignal`関数が`siginfo`構造体へのポインタを直接引数として受け取ることを期待しているためと考えられます。

これらの変更により、`sigtramp`は`siginfo`と`ucontext`のポインタをスタック上の正しい位置に配置し、`runtime·badsignal`に`siginfo`への正しいポインタを直接渡すことができるようになりました。これにより、Solaris上でのシグナルコンテキストの誤解釈が解消され、シグナルハンドリングの信頼性が回復しました。

## コアとなるコードの解説

### `src/runtime/signal_solaris_amd64.go`

このファイルでは、`makesigctxt`関数が完全に削除されました。

```diff
--- a/src/runtime/signal_solaris_amd64.go
+++ b/src/runtime/signal_solaris_amd64.go
@@ -11,10 +11,6 @@ type sigctxt struct {
 	ctxt unsafe.Pointer
 }
 
-func makesigctxt(info *siginfo, ctxt unsafe.Pointer) *sigctxt {
-	return &sigctxt{info, ctxt}
-}
-
 func (c *sigctxt) regs() *mcontext {
 	return (*mcontext)(unsafe.Pointer(&(*ucontext)(c.ctxt).uc_mcontext))
 }
```

`makesigctxt`は、`siginfo`と`ucontext`のポインタから`sigctxt`構造体を作成するヘルパー関数でした。この関数が削除されたのは、アセンブリコード側で`siginfo`と`ucontext`のポインタを直接操作し、`runtime·badsignal`に渡すように変更されたため、中間的な`sigctxt`オブジェクトの生成が不要になったからです。これにより、コードの簡素化と、潜在的なポインタの誤用を防ぐ効果があります。

### `src/runtime/sys_solaris_amd64.s`

このファイルでは、`runtime·sigtramp`アセンブリ関数の以下の部分が変更されました。

```diff
--- a/src/runtime/sys_solaris_amd64.s
+++ b/src/runtime/sys_solaris_amd64.s
@@ -173,10 +173,9 @@ TEXT runtime·sigtramp(SB),NOSPLIT,$0
 	MOVQ	g(BX), R10
 	CMPQ	R10, $0
 	JNE	allgood
-	MOVQ	SI, 0(SP)
-	MOVQ	DX, 8(SP)
-	CALL	runtime·makesigctxt(SB)
-	MOVQ	16(SP), AX
+	MOVQ	SI, 80(SP)
+	MOVQ	DX, 88(SP)
+	LEAQ	80(SP), AX
 	MOVQ	DI, 0(SP)
 	MOVQ	AX, 8(SP)
 	MOVQ	$runtime·badsignal(SB), AX
```

このアセンブリコードは、シグナルハンドラが呼び出された直後の処理を担当します。

**変更前:**
1.  `MOVQ SI, 0(SP)`: `RSI`レジスタ（`siginfo`へのポインタ）の内容を、現在のスタックポインタ`SP`から0バイトオフセットした位置に保存します。
2.  `MOVQ DX, 8(SP)`: `RDX`レジスタ（`ucontext`へのポインタ）の内容を、`SP`から8バイトオフセットした位置に保存します。
3.  `CALL runtime·makesigctxt(SB)`: Go関数`runtime·makesigctxt`を呼び出します。この関数は、スタックに保存された`siginfo`と`ucontext`のポインタを使用して`sigctxt`オブジェクトを作成し、そのポインタを`AX`レジスタに返します。
4.  `MOVQ 16(SP), AX`: `makesigctxt`の戻り値（`sigctxt`へのポインタ）を`AX`レジスタにロードします。この`16(SP)`というオフセットは、Goの関数呼び出し規約における戻り値の格納位置に対応しています。

**変更後:**
1.  `MOVQ SI, 80(SP)`: `RSI`レジスタ（`siginfo`へのポインタ）の内容を、`SP`から80バイトオフセットした位置に保存します。
2.  `MOVQ DX, 88(SP)`: `RDX`レジスタ（`ucontext`へのポインタ）の内容を、`SP`から88バイトオフセットした位置に保存します。
3.  `LEAQ 80(SP), AX`: `SP`から80バイトオフセットしたメモリアドレス（つまり、`siginfo`ポインタが保存されている場所のアドレス）を`AX`レジスタにロードします。

この変更のポイントは、`makesigctxt`関数を呼び出す代わりに、`siginfo`と`ucontext`のポインタをスタック上の異なるオフセット（`80(SP)`と`88(SP)`）に直接保存し、`LEAQ`命令を使って`siginfo`ポインタが格納されているメモリアドレスを`AX`レジスタにロードしている点です。

`AX`レジスタは、続く`MOVQ AX, 8(SP)`命令で`runtime·badsignal`関数への第2引数としてスタックにプッシュされるため、この変更により`runtime·badsignal`は`siginfo`構造体への正しいポインタを直接受け取ることになります。

この修正は、Solaris/AMD64環境におけるGoランタイムのシグナルハンドラが、OSから渡されるシグナルコンテキスト情報を正しく解釈し、処理するために不可欠でした。以前のコードでは、スタックのレイアウトやポインタの渡し方に誤りがあり、シグナル処理のバグにつながっていたと考えられます。

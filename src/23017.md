# [インデックス 23017] ファイルの概要

このコミットは、Goランタイムにおけるライトバリアのスキップ方法を、関数ベースから型ベースへと変更するものです。これにより、特定のポインタフィールドに対するライトバリアの挙動がより予測可能になり、ガベージコレクション（GC）の整合性とデバッグの容易性が向上します。

## 元コミット内容

このコミットは、Goランタイムのガベージコレクション（GC）におけるライトバリアの扱いに関する変更です。以前は、特定のポインタ更新時にライトバリアをスキップするために、`setGNoWriteBarrier`のような特殊な関数を使用していました。しかし、このアプローチでは、ライトバリアがスキップされる場合とされない場合が混在し、GCの整合性問題やデバッグの困難さを引き起こす可能性がありました。

このコミットの目的は、ライトバリアをスキップすべきフィールドを`uintptr`型として明示的に宣言することで、常にライトバリアなしで更新されるようにすることです。これにより、GCがこれらのフィールドを「見ない」ようになり、参照の欠落が問題を引き起こす場合でも、それが常に発生するため、デバッグが容易になります。また、`GODEBUG=wbshadow=1`環境変数を使用したライトバリアの整合性チェックにおいて、誤った検出を避けることができます。

## 変更の背景

Goのガベージコレクションは、並行マーク＆スイープ方式を採用しており、プログラムの実行中にGCが動作します。この際、GCが正しく動作するためには、ポインタの更新時に「ライトバリア」と呼ばれる処理を挿入し、GCがオブジェクトグラフの変更を追跡できるようにする必要があります。

しかし、ランタイム内部の特定のクリティカルなセクション（例えば、スケジューラがP（プロセッサ）をM（OSスレッド）から切り離すような処理）では、ライトバリアの実行がパフォーマンスに影響を与えたり、GCの状態と不整合を起こしたりする可能性があります。このような場合、ライトバリアをスキップする必要がありました。

以前のアプローチでは、ライトバリアをスキップするために、`setGNoWriteBarrier`のようなヘルパー関数が使用されていました。これらの関数は、内部的に`unsafe.Pointer`と`uintptr`のキャストを利用して、Goの型システムを迂回し、ライトバリアを挿入しないようにしていました。しかし、この「関数ベース」のスキップは、以下のような問題を引き起こす可能性がありました。

1.  **不整合なライトバリアの検出**: `GODEBUG=wbshadow=1`は、ライトバリアが正しく挿入されているかをチェックするデバッグモードです。関数ベースのスキップでは、同じメモリワードに対する更新でも、ライトバリアが挿入される場合とされない場合が混在するため、このデバッグモードで「不整合なライトバリア」として誤って報告されることがありました。
2.  **GCの整合性問題**: GCが世界を停止している（STW: Stop The World）と認識している間に、ライトバリアが部分的に実行され、オブジェクトがマークされたものの、GCにキューイングされなかった場合、GCがそのオブジェクトをスキップしてしまい、誤って解放してしまう可能性がありました。
3.  **予測不可能性**: ライトバリアがスキップされるタイミングが、特定の関数の呼び出しに依存するため、コードの理解やデバッグが困難になることがありました。

このコミットは、これらの問題を解決するために、ライトバリアをスキップすべきポインタを明示的に`uintptr`型として定義することで、常にライトバリアなしで更新されるようにする「型ベース」のアプローチを導入しました。

## 前提知識の解説

### ガベージコレクション (GC) とライトバリア

GoのGCは、メモリ管理を自動化する仕組みです。不要になったメモリ領域を自動的に解放し、メモリリークを防ぎます。GoのGCは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行してGCが動作します。

GCが正しく動作するためには、プログラムがポインタを更新する際に、GCがその変更を追跡できる必要があります。この追跡メカニズムが「ライトバリア」です。ライトバリアは、ポインタが変更される直前または直後に実行される小さなコードスニペットで、GCに「このポインタが変更された」という情報を伝えます。これにより、GCはオブジェクトグラフの整合性を保ち、到達可能なオブジェクトを正しくマークできます。

### Goランタイムの内部構造 (G, M, P)

Goランタイムは、ゴルーチン（G）、OSスレッド（M）、プロセッサ（P）という3つの主要な抽象化を使用して、並行処理を管理します。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。ユーザーが書くGoコードはゴルーチンとして実行されます。
*   **M (Machine/OS Thread)**: オペレーティングシステムのスレッドです。Goランタイムは、M上でGを実行します。
*   **P (Processor)**: MがGを実行するために必要な論理的なプロセッサです。Pは、実行可能なGのキュー（ローカル実行キュー）を保持し、MにGをディスパッチします。

MとPは、GCの動作に密接に関連しており、特にMとP間のポインタの更新は、ライトバリアの挙動に影響を与えます。

### `unsafe.Pointer` と `uintptr`

Goの`unsafe`パッケージは、Goの型システムを迂回して、メモリを直接操作するための機能を提供します。

*   `unsafe.Pointer`: 任意の型のポインタを保持できる特殊なポインタ型です。C言語の`void*`に似ています。
*   `uintptr`: ポインタの値を整数として表現する型です。ポインタ演算を行う際に使用されます。

これらの型は、Goの型安全性を損なう可能性があるため、慎重に使用する必要があります。特に、`unsafe.Pointer`と`uintptr`の間で変換を行うと、GCがポインタを追跡できなくなる可能性があります。

### `GODEBUG=wbshadow=1`

これはGoランタイムのデバッグ環境変数の一つで、ライトバリアのシャドウチェックを有効にします。このモードでは、ライトバリアが正しく挿入されているか、または意図的にスキップされているかを検証し、不整合な挙動があれば報告します。

## 技術的詳細

このコミットの核心は、Goランタイム内部の特定の構造体フィールドの型を、通常のポインタ型（例: `*g`, `*m`, `*p`）から、`guintptr`, `muintptr`, `puintptr`という新しい`uintptr`ベースの型に変更することです。これらの新しい型は、それぞれ`*g`, `*m`, `*p`へのポインタを`uintptr`として保持し、ライトバリアを完全にバイパスします。

具体的には、`src/runtime/runtime2.go`に以下の新しい型が導入されました。

```go
type guintptr uintptr
func (gp guintptr) ptr() *g   { return (*g)(unsafe.Pointer(gp)) }
func (gp *guintptr) set(g *g) { *gp = guintptr(unsafe.Pointer(g)) }

type puintptr uintptr
func (pp puintptr) ptr() *p   { return (*p)(unsafe.Pointer(pp)) }
func (pp *puintptr) set(p *p) { *pp = puintptr(unsafe.Pointer(p)) }

type muintptr uintptr
func (mp muintptr) ptr() *m   { return (*m)(unsafe.Pointer(mp)) }
func (mp *muintptr) set(m *m) { *mp = muintptr(unsafe.Pointer(m)) }
```

これらの型は、ポインタを`uintptr`として格納し、`ptr()`メソッドで元のポインタ型に変換し、`set()`メソッドでポインタ値を設定します。これにより、これらのフィールドへの代入はGoの型システムによって`uintptr`への代入と見なされ、ライトバリアが挿入されなくなります。

コミットメッセージで述べられているように、このアプローチには以下の重要な特性があります。

1.  **GCがフィールドを完全に無視する**: `uintptr`として格納されたポインタは、GCによって通常のポインタとして認識されません。これにより、GCはこれらのフィールドをスキャンせず、参照の欠落が問題を引き起こす場合でも、それが常に発生するため、デバッグが容易になります。以前の関数ベースのスキップでは、GCがフィールドを部分的にスキャンする可能性があり、不整合な状態を引き起こすリスクがありました。
2.  **ライトバリアの不整合検出の回避**: `GODEBUG=wbshadow=1`モードでは、ライトバリアが挿入されるべき場所でスキップされたり、その逆の状況が発生したりすると警告が出ます。型ベースのアプローチでは、これらのフィールドへの更新は常にライトバリアなしで行われるため、このデバッグモードでの誤った警告がなくなります。

この変更は、特にGCがSTW状態にあるときや、Pが解放されているときなど、ライトバリアが実行されると問題を引き起こす可能性のあるランタイムのクリティカルなセクションで重要です。これらの状況では、GCは世界が停止していると認識しており、予期せぬライトバリアはGCと同期せず、部分的に実行されたライトバリアがオブジェクトをマークしてもキューに入れられず、GCがオブジェクトを誤って解放する可能性があります。

`G`, `M`, `P`のポインタは、`allgs`, `allm`, `allp`リスト、またはスタック変数から常に到達可能であるため、GCがこれらのポインタを追跡できなくても問題ありません。

## コアとなるコードの変更箇所

このコミットでは、主に`src/runtime/runtime2.go`で新しい`uintptr`ベースのポインタ型が定義され、それらの型がランタイムの様々な構造体（`g`, `m`, `p`, `schedt`など）のフィールドに適用されています。

具体的な変更ファイルと変更内容は以下の通りです。

*   **`src/runtime/runtime2.go`**:
    *   `guintptr`, `muintptr`, `puintptr`型が新しく定義され、それぞれ`*g`, `*m`, `*p`へのポインタを`uintptr`として保持するようになりました。
    *   これらの新しい型には、元のポインタ型への変換を行う`ptr()`メソッドと、ポインタ値を設定する`set()`メソッドが追加されました。
    *   以前の`setGNoWriteBarrier`, `setMNoWriteBarrier`, `setPNoWriteBarrier`, `setMcacheNoWriteBarrier`といった関数ベースのライトバリアスキップ関数が削除されました。
    *   `g`, `m`, `p`, `schedt`構造体内のポインタフィールドが、対応する`uintptr`ベースの型に変更されました（例: `g.schedlink *g` -> `g.schedlink guintptr`）。

*   **`src/runtime/malloc.go`**:
    *   `mp.p`の参照が`mp.p.ptr()`に変更され、`puintptr`型を介して`p`構造体へのポインタを取得するようになりました。

*   **`src/runtime/mbarrier.go`**:
    *   `mp.p == nil`のチェックが`mp.p == 0`に変更され、`puintptr`型のゼロ値と比較するようになりました。

*   **`src/runtime/netpoll.go`, `src/runtime/netpoll_epoll.go`, `src/runtime/netpoll_kqueue.go`, `src/runtime/netpoll_solaris.go`, `src/runtime/netpoll_windows.go`**:
    *   `netpollready`関数の引数や、`netpoll`関数内の`gp`変数が`guintptr`型に変更され、`set()`メソッドや`ptr()`メソッドを使用してポインタの操作を行うようになりました。
    *   `netpoll`関数の戻り値が`*g`から`*g`に変更されましたが、内部での`guintptr`の使用が徹底されました。

*   **`src/runtime/os1_windows.go`, `src/runtime/os3_plan9.go`**:
    *   `mp.libcallg`や`_g_.m.caughtsig`といったフィールドが`guintptr`型に変更され、`set()`メソッドを使用するようになりました。

*   **`src/runtime/panic.go`, `src/runtime/proc.go`, `src/runtime/proc1.go`**:
    *   `mp.p`の参照が`mp.p.ptr()`に変更され、`puintptr`型を介して`p`構造体へのポインタを取得するようになりました。
    *   `allocm`関数のシグネチャが変更され、`fn func()`引数が追加されました。
    *   `mp.nextp`, `mp.schedlink`, `ts.g`などのフィールドが`puintptr`や`guintptr`型に変更され、`set()`メソッドを使用するようになりました。
    *   `sched.runqhead`, `sched.runqtail`, `sched.midle`, `sched.pidle`といったスケジューラのキュー関連のフィールドも`guintptr`, `muintptr`, `puintptr`型に変更されました。

*   **`src/runtime/signal_*.go`**:
    *   `_g_.m.caughtsig`フィールドが`guintptr`型に変更され、`set()`メソッドを使用するようになりました。

## コアとなるコードの解説

このコミットの最も重要な変更は、`src/runtime/runtime2.go`で導入された`guintptr`, `muintptr`, `puintptr`という新しい型と、それらがランタイムの主要な構造体（`g`, `m`, `p`, `schedt`）のポインタフィールドに適用されたことです。

以前は、ライトバリアをスキップしたいポインタの代入には、以下のような関数が使われていました。

```go
// setGNoWriteBarrier does *gdst = gval without a write barrier.
func setGNoWriteBarrier(gdst **g, gval *g) {
	*(*uintptr)(unsafe.Pointer(gdst)) = uintptr(unsafe.Pointer(gval))
}
```

この関数は、`**g`型のポインタを受け取り、その指す先の`*g`値を`uintptr`にキャストして代入することで、Goのコンパイラがライトバリアを挿入しないようにしていました。しかし、この方法は、同じポインタフィールドに対して、通常の代入（ライトバリアあり）とこの関数による代入（ライトバリアなし）が混在する可能性があり、デバッグやGCの整合性チェックを複雑にしていました。

新しいアプローチでは、ポインタフィールド自体の型を`uintptr`ベースのラッパー型（`guintptr`など）に変更します。例えば、`g`構造体の`schedlink`フィールドは、以前は`*g`型でしたが、このコミットで`guintptr`型に変更されました。

```go
// src/runtime/runtime2.go (変更後)
type g struct {
    // ...
    schedlink    guintptr
    // ...
}
```

この変更により、`g.schedlink = someG`のような直接的な代入はできなくなります。代わりに、`set()`メソッドを使用する必要があります。

```go
// src/runtime/proc1.go (変更後の一例)
// 以前: gp.schedlink = sched.runqhead
// 変更後: gp.schedlink.set(sched.runqhead)
```

また、このフィールドから元のポインタ値を取得する際には、`ptr()`メソッドを使用します。

```go
// src/runtime/proc1.go (変更後の一例)
// 以前: for gp := glist; gp != nil; gp = gp.schedlink
// 変更後: for gp := glist; gp != nil; gp = gp.schedlink.ptr()
```

この「型ベース」のアプローチの利点は、ライトバリアをスキップしたいフィールドが、その型定義によって明確に識別されることです。これにより、コンパイラはこれらのフィールドへの代入が常にライトバリアなしで行われることを保証でき、コードの意図がより明確になります。

コミットメッセージで強調されているように、この変更は以下の2つの重要な特性をもたらします。

1.  **GCの視点からの透明性**: `uintptr`として格納された値は、GCにとっては単なる数値であり、ポインタとしては認識されません。したがって、GCはこれらのフィールドをスキャンせず、それらが指すオブジェクトの到達可能性を判断する際に考慮しません。これにより、GCの動作がより予測可能になり、もし参照の欠落が問題を引き起こす場合でも、それが常に発生するため、デバッグが容易になります。
2.  **`GODEBUG=wbshadow=1`との整合性**: このデバッグモードは、ライトバリアの不整合を検出します。以前の関数ベースのスキップでは、同じメモリ位置に対する更新がライトバリアあり/なしで混在する可能性があり、誤った警告を生成することがありました。型ベースのアプローチでは、これらのフィールドへの更新は常にライトバリアなしで行われるため、不整合の警告がなくなります。

この変更は、Goランタイムの内部実装におけるGCの正確性とパフォーマンス、そしてデバッグの容易性を向上させるための重要なステップです。特に、スケジューラやGCの低レベルな操作において、ライトバリアの挙動を厳密に制御する必要がある場合に有効です。

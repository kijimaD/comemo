## 元コミット内容

`hash: update documentation for MakeTable in crc32 and crc64`

このコミットは、`crc32` および `crc64` パッケージの `MakeTable` 関数に関するドキュメンテーションを更新します。具体的には、`MakeTable` が返す `*Table` の内容を変更してはならないことを明示的に記述しています。この変更は、テーブルが変更された場合に発生する可能性のある、非常に発見しにくいバグを防ぐことを目的としています。

`crc64` パッケージにも同様のコメントが追加されており、これは `crc32` が効果的に行っているテーブルのキャッシュの将来的な可能性を考慮したものです。

このコミットは、Issue #12487 を修正します。

## 変更の背景

この変更の背景には、`crc32.MakeTable` 関数が特定の多項式（例えば `IEEE` や `Castagnoli`）に対して、内部的にキャッシュされたグローバルなテーブルへの参照を返すという実装の詳細があります。これはパフォーマンス最適化のためであり、これらの標準的なCRC32計算に頻繁にアクセスされるテーブルを再計算するコストを避けるためのものです。

しかし、この実装は、ユーザーが `MakeTable` から取得した `*Table` オブジェクトの内容を誤って変更した場合に、深刻な問題を引き起こす可能性がありました。もしユーザーがキャッシュされたテーブルを変更してしまうと、その変更はプログラム全体に影響を及ぼし、標準的なCRC32計算に依存する他の部分で誤った結果が生じることになります。このようなバグは、その性質上、非常に発見しにくく、デバッグが困難です。

Issue #12487 はこの問題提起から生まれました。このコミットは、この潜在的な問題を未然に防ぐため、ドキュメンテーションを明確にすることで、開発者に対して `MakeTable` が返すテーブルを変更してはならないという制約を伝えることを目的としています。`crc64` パッケージにも同様の注意書きが追加されたのは、将来的に `crc64` でも同様のキャッシュ機構が導入される可能性を考慮し、一貫性を持たせるためです。

## 前提知識の解説

### CRC (Cyclic Redundancy Check)

CRC（巡回冗長検査）は、デジタルデータのエラー検出によく用いられるハッシュ関数の一種です。データブロックの最後に短いチェック値（CRC値）を付加し、受信側で同じ計算を行うことで、データが転送中に破損していないかを確認します。CRCは、主に偶発的なビットエラーの検出に優れています。

### CRC32とCRC64

-   **CRC32**: 32ビットのCRC値を生成します。ファイル転送、ネットワークプロトコル（例: Ethernet、ZIPファイル）などで広く利用されています。Go言語の `hash/crc32` パッケージは、このCRC32計算を提供します。
-   **CRC64**: 64ビットのCRC値を生成します。CRC32よりも衝突耐性が高く、より大きなデータセットや高い信頼性が求められる場面で使用されることがあります。Go言語の `hash/crc64` パッケージは、このCRC64計算を提供します。

### 多項式 (Polynomial)

CRC計算は、有限体上の多項式除算に基づいています。CRCの「種類」（例: CRC-32-IEEE、CRC-64-ISO）は、使用される生成多項式によって定義されます。`MakeTable` 関数は、この多項式を引数として受け取り、CRC計算を効率的に行うためのルックアップテーブルを生成します。

### ルックアップテーブル (Lookup Table)

CRC計算はバイト単位でデータを処理することが多く、各バイトに対する計算結果を事前に計算してテーブルに格納しておくことで、実行時の計算コストを大幅に削減できます。このテーブルが「ルックアップテーブル」であり、`MakeTable` 関数が生成する `*Table` オブジェクトがこれに該当します。

### キャッシュ (Caching)

プログラムのパフォーマンスを向上させるために、頻繁にアクセスされるデータや計算結果を一時的に保存しておく仕組みです。`crc32` パッケージでは、標準的な多項式（`IEEE`など）に対応するルックアップテーブルが内部的にキャッシュされており、`MakeTable` が呼ばれるたびに新しいテーブルを生成するのではなく、既存のキャッシュされたテーブルへの参照を返します。これにより、テーブル生成のオーバーヘッドを削減しています。

### ポインタと参照渡し

Go言語では、変数を関数に渡す際に値渡しが基本ですが、ポインタを渡すことで参照渡しのような動作を実現できます。`MakeTable` が `*Table` を返すということは、テーブルの実体へのポインタを返していることを意味します。これにより、呼び出し元はテーブルの内容を直接操作できますが、同時に意図しない変更が元のテーブルに影響を与えるリスクも伴います。

## 技術的詳細

このコミットの技術的詳細の核心は、Go言語の `hash/crc32` および `hash/crc64` パッケージにおける `MakeTable` 関数の戻り値の性質にあります。

`crc32.MakeTable` 関数は、引数としてCRC多項式（`uint32`型）を受け取り、その多項式に対応する `*Table` 型のポインタを返します。`Table` 型は `[256]uint32` の配列であり、各バイトに対するCRC計算の中間結果を格納するルックアップテーブルです。

特に `crc32` パッケージでは、`IEEE` や `Castagnoli` といった標準的な多項式に対しては、テーブルが一度生成されると内部的にキャッシュされ、以降の `MakeTable` 呼び出しではそのキャッシュされたテーブルへのポインタが返されます。これは `sync.Once` を使用してスレッドセーフに初期化されるグローバル変数として実装されています（例: `iEEETable8`）。

```go
// src/hash/crc32/crc32.go (変更前後の関連部分)
var iEEETable8 *slicing8Table
var iEEETable8Once sync.Once

func MakeTable(poly uint32) *Table {
    switch poly {
    case IEEE:
        // IEEE多項式の場合、キャッシュされたテーブルを返す
        iEEETable8Once.Do(func() {
            iEEETable8 = makeSlicing8Table(IEEE)
        })
        return &iEEETable8[0] // slicing8Tableの最初のTableへのポインタを返す
    // ... 他の多項式の場合、新しいテーブルを生成
    }
}
```

この挙動により、ユーザーが `MakeTable(crc32.IEEE)` を呼び出して得た `*Table` の内容を直接変更すると、それはキャッシュされたグローバルなテーブルを直接変更することになります。その結果、同じ `IEEE` 多項式を使用する他のCRC計算も、変更されたテーブルに基づいて行われるため、誤った結果を生成する可能性があります。これは、Goの標準ライブラリが提供するCRC計算の整合性を損なうことになります。

このコミットは、この潜在的な問題に対するコードレベルでの変更ではなく、ドキュメンテーションレベルでの解決策を提供します。つまり、`MakeTable` の利用者がこの実装の詳細を意識し、返されたテーブルを変更しないように注意を促すことで、バグの発生を防ぎます。

`crc64` パッケージに関しては、このコミット時点では `crc32` のような明示的なキャッシュ機構は実装されていませんでしたが、将来的な拡張性を考慮し、同様の注意書きを追加することで、設計の一貫性と将来的な互換性を保っています。これにより、もし将来的に `crc64` でもテーブルのキャッシュが導入された場合でも、既存のドキュメンテーションが既にその制約をカバーしていることになります。

## コアとなるコードの解説

変更されたのは、`MakeTable` 関数のドキュメンテーションコメントです。

以前のコメントは以下の通りでした。
`// MakeTable returns the Table constructed from the specified polynomial.`
（指定された多項式から構築されたテーブルを返します。）

このコミットにより、以下の行が追加されました。
`// The contents of this Table must not be modified.`
（このテーブルの内容は変更してはなりません。）

この追加された一文が、このコミットの最も重要な変更点です。これにより、`MakeTable` 関数が返す `*Table` ポインタが指すデータ構造が、ユーザーによって変更されるべきではないという明確な制約が課せられました。これは、特に `crc32` パッケージで内部的にキャッシュされているテーブルへの参照が返される場合に、そのテーブルが意図せず変更されることによるグローバルな状態の破損を防ぐためのものです。

このドキュメンテーションの更新は、Go言語のAPI設計における「契約による設計 (Design by Contract)」の一例と見なすことができます。関数が特定の前提条件（precondition）と事後条件（postcondition）を持つことを明示し、利用者がその契約に従うことで、システムの堅牢性と予測可能性を高めます。ここでは、`MakeTable` が返すオブジェクトに対する「変更不可」という制約が、その契約の一部として明示されています。

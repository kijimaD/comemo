# [インデックス 22949] ファイルの概要

このコミットは、GoコンパイラのARM64アーキテクチャ向けバックエンドである`cmd/7g`における、nilポインタチェック（`CHECKNIL`擬似命令）のシーケンスを変更するものです。具体的には、既存の`CMP`（比較）と`BNE`（非等号分岐）の2命令からなるシーケンスを、`CBNZ`（非ゼロ条件分岐）という単一命令に置き換えることで、生成されるコードの効率を向上させています。この変更により、`godoc`バイナリのサイズが66KB削減されるという具体的な効果が報告されています。

## 元コミット内容

GoコンパイラのARM64バックエンド（`cmd/7g`）において、`CHECKNIL`擬似命令の展開シーケンスを変更します。
`CBNZ`命令を使用することで、命令シーケンスを1命令短縮できます。
これにより、`godoc`バイナリのサイズが66KB削減されます。

## 変更の背景

Go言語では、nilポインタのデリファレンスはランタイムパニックを引き起こします。これを検出するために、コンパイラはポインタがnilであるかどうかをチェックするコードを挿入します。このチェックは、特にポインタが頻繁にデリファレンスされるようなコードにおいて、生成されるバイナリのサイズと実行性能に影響を与えます。

このコミットの背景には、以下の目的があります。

1.  **コードサイズの削減**: 既存のnilチェックシーケンスは複数のアセンブリ命令で構成されており、これがバイナリサイズを増大させる一因となっていました。特に`godoc`のような大規模なGoプログラムでは、このオーバーヘッドが顕著になります。
2.  **実行効率の向上**: 命令数を減らすことで、CPUの命令フェッチ、デコード、実行の各段階でのオーバーヘッドを削減し、nilチェックの実行速度を向上させることが期待されます。
3.  **ARM64アーキテクチャの特性活用**: ARM64プロセッサが提供する特定の命令（この場合は`CBNZ`）をより効果的に利用することで、より最適化されたコードを生成することを目指しています。

この変更は、Goコンパイラが生成するコードの品質を継続的に改善し、より小さく、より高速なバイナリを提供するための取り組みの一環です。

## 前提知識の解説

### 1. Goコンパイラと`cmd/7g`

Goコンパイラは、Go言語のソースコードを機械語に変換するツールチェーンです。Goのコンパイラは、ターゲットアーキテクチャごとに異なるバックエンドを持っています。
*   `cmd/7g`: ARM64 (AArch64) アーキテクチャ向けのGoコンパイラバックエンドです。Go 1.5以前の命名規則では、数字がアーキテクチャを示していました（例: `6g`はamd64、`8g`は386）。
*   **擬似命令 (Pseudo-op)**: コンパイラの内部で使われる抽象的な命令で、最終的な機械語命令に展開される前の段階のものです。`CHECKNIL`は、Goコンパイラがnilポインタチェックを表現するために使用する擬似命令の一つです。

### 2. nilポインタチェック

Go言語では、nilポインタをデリファレンスしようとすると、ランタイムパニックが発生します。これは、プログラムの安全性を保証するための重要なメカニズムです。コンパイラは、ポインタが使用される前にその値がnilでないことを保証するために、特定のコードポイントにnilチェックを挿入します。

一般的なnilチェックのロジックは以下のようになります。
1.  ポインタの値がゼロ（nil）であるかをチェックする。
2.  もしゼロであれば、パニックを発生させるためのコードにジャンプする。
3.  ゼロでなければ、通常の実行を続ける。

### 3. ARM64アセンブリ命令

ARM64は、ARMv8-Aアーキテクチャに基づく64ビット命令セットです。このコミットで関連する命令は以下の通りです。

*   **`CMP` (Compare)**: 2つのレジスタまたはレジスタと即値の値を比較し、結果をステータスフラグ（N, Z, C, V）に設定します。比較結果自体はレジスタに保存されません。
*   **`BNE` (Branch if Not Equal)**: 直前の比較命令の結果、Z（ゼロ）フラグがクリア（非ゼロ）の場合に、指定されたアドレスに分岐します。`CMP X, #0`の後に`BNE target`とすると、「Xがゼロでなければtargetに分岐」という意味になります。
*   **`MOVD` (Move Doubleword)**: 64ビットの値をレジスタ間で移動したり、レジスタからメモリに書き込んだりする命令です。この文脈では、`MOVD ZR, 0(arg)`はゼロレジスタ（`ZR`）の内容（つまり0）を、`arg`レジスタが指すアドレスのオフセット0に書き込むことを意味します。これはnilポインタデリファレンスによるクラッシュを意図的に引き起こすための一般的な手法です。
*   **`CBNZ` (Compare and Branch if Not Zero)**: この命令は、レジスタの値がゼロでない場合に、指定されたアドレスに分岐します。`CMP`と`BNE`の組み合わせを1つの命令にまとめたもので、より効率的な条件分岐を提供します。`CBNZ X, target`は、「Xがゼロでなければtargetに分岐」という意味になります。

### 4. `obj.Prog`構造体

Goコンパイラのバックエンドでは、アセンブリ命令を表現するために`obj.Prog`という内部構造体を使用します。これは、命令の種類（`As`フィールド）、オペランド（`From`, `To`フィールド）、リンク（`Link`フィールドで次の命令を指す）などの情報を含みます。

## 技術的詳細

このコミットの核心は、GoコンパイラのARM64バックエンドが`CHECKNIL`擬似命令をどのようにアセンブリコードに展開するかを変更することにあります。

### 変更前の`CHECKNIL`展開シーケンス

変更前は、`CHECKNIL`は以下の3つのARM64アセンブリ命令に展開されていました。

```armasm
CMP arg, ZR       // argレジスタの内容とゼロレジスタ(ZR)を比較
BNE 2(PC)         // 比較結果が非ゼロ（argがnilでない）なら、2命令先に分岐
MOVD ZR, 0(arg)   // argがnilの場合、ゼロレジスタの内容(0)をアドレス0に書き込み、クラッシュさせる
```

このシーケンスの動作は以下の通りです。
1.  `CMP arg, ZR`: `arg`レジスタ（チェック対象のポインタ）がゼロレジスタ（値が常に0）と比較されます。この比較の結果、`arg`が0であればZフラグがセットされ、そうでなければクリアされます。
2.  `BNE 2(PC)`: Zフラグがクリアされている（`arg`がnilでない）場合、プログラムカウンタ（PC）から2命令分先に分岐します。これにより、`MOVD`命令をスキップして、nilチェック後の正常なコードパスに進みます。
3.  `MOVD ZR, 0(arg)`: `arg`がnilであった場合（Zフラグがセットされ、`BNE`が分岐しなかった場合）、この命令が実行されます。ゼロレジスタの内容（0）を、`arg`が指すアドレス（この場合は0x0）に書き込もうとします。これは、オペレーティングシステムによって保護されたメモリ領域への書き込みとなり、セグメンテーション違反などの例外を引き起こし、Goランタイムがこれを捕捉してパニックとして報告します。

### 変更後の`CHECKNIL`展開シーケンス

変更後は、`CHECKNIL`は以下の2つのARM64アセンブリ命令に展開されます。

```armasm
CBNZ arg, 2(PC)   // argレジスタの内容が非ゼロなら、2命令先に分岐
MOVD ZR, 0(arg)   // argがnilの場合、ゼロレジスタの内容(0)をアドレス0に書き込み、クラッシュさせる
```

このシーケンスの動作は以下の通りです。
1.  `CBNZ arg, 2(PC)`: `arg`レジスタ（チェック対象のポインタ）の値がゼロでない場合、プログラムカウンタ（PC）から2命令分先に分岐します。これにより、`MOVD`命令をスキップして、nilチェック後の正常なコードパスに進みます。
2.  `MOVD ZR, 0(arg)`: `arg`がnilであった場合（`CBNZ`が分岐しなかった場合）、この命令が実行されます。前述と同様に、アドレス0への書き込みを試み、パニックを引き起こします。

### 変更によるメリット

*   **命令数の削減**: 3命令から2命令への削減は、生成されるコードのサイズを直接的に減少させます。これが`godoc`バイナリの66KB削減という結果に繋がっています。
*   **実行効率の向上**: 命令数が減ることで、命令フェッチ、デコード、実行のサイクルが短縮され、nilチェックのオーバーヘッドが減少します。`CBNZ`は単一命令で比較と分岐を同時に行うため、パイプラインの効率も向上する可能性があります。
*   **コードの簡潔化**: コンパイラ内部でのアセンブリ命令生成ロジックも簡素化されます。

この最適化は、Goコンパイラがターゲットアーキテクチャの特性を深く理解し、それらを活用してより効率的なコードを生成しようとする継続的な努力を示しています。

## コアとなるコードの解説

### `src/cmd/7g/ggen.go` の `expandchecks` 関数

`expandchecks`関数は、Goコンパイラの内部で`obj.ACheck`（`CHECKNIL`擬似命令に対応）という命令を見つけると、それを実際のnilポインタチェックのアセンブリ命令シーケンスに展開する役割を担っています。

**変更点:**

1.  **`p2`変数の削除**: 変更前は、`CMP`、`BNE`、`MOVD`の3命令を表現するために`p`（元の`ACheck`命令）、`p1`（`BNE`）、`p2`（`MOVD`）の3つの`obj.Prog`構造体を使用していました。`CBNZ`の導入により、`BNE`と`CMP`が1つの命令に統合されたため、`p2`は不要となり削除されました。
2.  **命令シーケンスの変更**:
    *   元の`p.As = arm64.ACMP`と`p1.As = arm64.ABNE`の組み合わせが削除されました。
    *   代わりに、元の`p`命令が`arm64.ACBNZ`に設定されます。
    *   `p.To.Type = obj.TYPE_BRANCH`と`p.To.Val = p1.Link`が設定され、`CBNZ`命令が`p1`（`MOVD`命令）の次の命令に分岐するように指示されます。
3.  **`MOVD`命令のターゲット変更**: 以前は`p2`が`MOVD`命令を表現していましたが、`p2`が削除されたため、`p1`が`MOVD`命令を表現するように変更されました。これにより、`p1.As = arm64.AMOVD`などの設定が`p1`に対して行われます。

この変更により、`expandchecks`関数はより少ない`obj.Prog`構造体とより簡潔なロジックで、効率的なnilチェックシーケンスを生成するようになりました。

### `src/cmd/7g/prog.go` の `progtable`

`progtable`は、Goコンパイラのバックエンドが各アセンブリ命令に関するメタデータ（例えば、それがジャンプ命令であるか、呼び出し命令であるかなど）を格納するために使用するテーブルです。

**変更点:**

*   `arm64.ACBZ`と`arm64.ACBNZ`の2つの新しいエントリが`progtable`に追加されました。
*   これらの命令は、`gc.Cjmp`（条件付きジャンプ）タイプとしてマークされています。これは、コンパイラがこれらの命令を条件分岐として正しく認識し、コードフロー解析や最適化を行う上で重要です。

この追加は、`CBNZ`命令がGoコンパイラのARM64バックエンドで正式にサポートされ、その特性がコンパイラに認識されるようになったことを意味します。

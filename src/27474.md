# [インデックス 27474] ファイルの概要

このコミットは、Go言語の静的解析ツールである`go vet`の`copylock`アナライザにおける誤検知（false positive）を修正するものです。具体的には、組み込みの`new()`関数を使用して`sync.Mutex`のようなロック型を初期化する際に、`go vet`が不適切に「ロックの値渡し」として警告を発する問題を解決します。`new()`関数は常にポインタを返すため、この操作は実際にはロックの値渡しではなく、ポインタの値渡しであり、Goの並行処理モデルにおいて安全かつ一般的なパターンです。この修正により、開発者は不必要な警告に煩わされることなく、より正確な静的解析結果を得られるようになります。

## 変更の背景

Go言語の`go vet`ツールは、コードの潜在的な問題を検出するための静的解析ツールです。その中の`copylock`アナライザは、`sync.Mutex`や`sync.WaitGroup`のような同期プリミティブを含む構造体が誤って値渡しされるケースを検出することを目的としています。同期プリミティブは内部状態を持つため、値渡しされるとコピーされたインスタンスは元のインスタンスとは独立した状態となり、並行処理の同期が破綻し、競合状態やデッドロックといった深刻なバグを引き起こす可能性があります。

しかし、この`copylock`アナライザには、組み込みの`new()`関数が使用された場合に誤検知が発生するという問題がありました。例えば、`new(sync.Mutex)`というコードは、`sync.Mutex`型のゼロ値が割り当てられたメモリへのポインタ（`*sync.Mutex`）を返します。ポインタ自体は値型であり、そのコピーは参照先のアドレスをコピーするだけで、同期プリミティブの実体をコピーするわけではありません。したがって、`new(sync.Mutex)`はロックの値渡しには該当せず、安全な操作です。

にもかかわらず、`go vet`の`copylock`アナライザは、この`new(sync.Mutex)`のようなパターンを「関数呼び出しがロックの値をコピーしている」として誤って警告していました。これは開発者にとって混乱を招き、不必要なコードの修正や警告の無視につながる可能性がありました。このコミットは、この誤検知を修正し、`go vet`の`copylock`アナライザの精度を向上させることを目的としています。コミットメッセージに記載されている`Updates #14839`と`Fixes #14994`は、この問題に関する既存の課題を指しています。

## 前提知識の解説

### `go vet`ツール

`go vet`はGo言語に標準で付属する静的解析ツールです。コンパイラでは検出できないが、実行時に問題を引き起こす可能性のある疑わしいコード構造を特定します。例えば、到達不能なコード、誤ったフォーマット文字列、構造体のフィールドタグの誤り、そして本コミットの主題である同期プリミティブの誤ったコピーなどを検出します。`go vet`はGo開発ワークフローにおいて、早期に潜在的なバグを発見し、コード品質を向上させるために重要な役割を果たします。

### `copylock`アナライザ

`copylock`アナライザは`go vet`のサブツールの一つで、`sync.Mutex`、`sync.RWMutex`、`sync.WaitGroup`、`sync.Cond`、`sync.Pool`などのGoの標準ライブラリに含まれる同期プリミティブが誤って値渡しされるケースを検出します。

**なぜロックの値渡しが問題なのか？**

*   **状態の独立性**: `sync.Mutex`のような同期プリミティブは、ロックの状態（ロックされているか、どのGoroutineがロックを保持しているかなど）を内部に保持しています。構造体や関数引数として値渡しされると、その同期プリミティブのコピーが作成されます。このコピーは元の同期プリミティブとは完全に独立した状態を持つため、元のロックとコピーされたロックは互いに影響を与えません。
*   **同期の破綻**: 複数のGoroutineが共有リソースにアクセスする際に、異なるロックのインスタンス（元のロックとコピーされたロック）を使用すると、本来意図した排他制御が機能しなくなります。これにより、複数のGoroutineが同時に共有リソースにアクセスしてしまい、競合状態（Race Condition）が発生し、データの破損や予期せぬ動作につながります。
*   **デッドロック**: 例えば、あるGoroutineが元のロックを保持し、別のGoroutineがコピーされたロックを待っている場合、互いに相手のロック解除を待つことになり、デッドロックが発生する可能性があります。

これらの理由から、同期プリミティブは常にポインタとして渡すか、構造体に埋め込む場合はその構造体自体をポインタとして扱うのがGoの慣習であり、`copylock`アナライザはその慣習からの逸脱を警告します。

### `new()`組み込み関数

Go言語には、メモリを割り当てるための組み込み関数として`new()`と`make()`の二つがあります。

*   **`new(Type)`**:
    *   任意の型`Type`のゼロ値が割り当てられたメモリを確保し、そのメモリへのポインタ（`*Type`）を返します。
    *   例えば、`new(int)`は`*int`型で値が`0`のメモリへのポインタを返します。`new(MyStruct)`は`*MyStruct`型で、`MyStruct`の全フィールドがそれぞれのゼロ値で初期化されたメモリへのポインタを返します。
    *   `new()`は、スライス、マップ、チャネル以外のすべての型に使用できます。
    *   `new()`は常にポインタを返します。

*   **`make(Type, size, capacity)`**:
    *   スライス、マップ、チャネルといった参照型（reference type）の初期化とメモリ割り当てに使用されます。
    *   `make()`は初期化された（ゼロ値ではない）型`Type`のインスタンスを返します。ポインタは返しません。
    *   例えば、`make([]int, 5)`は長さ5の`int`型スライスを返します。

本コミットの文脈では、`new()`関数が常にポインタを返すという特性が重要です。`new(sync.Mutex)`は`*sync.Mutex`を返すため、このポインタを値渡ししても、`sync.Mutex`の実体がコピーされるわけではありません。

### ポインタの値渡し

Goにおいて、変数を関数に渡す際、デフォルトでは値渡しが行われます。
*   **値型（例: `int`, `bool`, `struct`）の値渡し**: 変数の内容全体がコピーされます。
*   **参照型（例: `slice`, `map`, `channel`）の値渡し**: 参照ヘッダ（内部のデータ構造へのポインタや長さ、容量などの情報）がコピーされます。参照ヘッダが指す基盤のデータはコピーされません。
*   **ポインタ型（例: `*int`, `*MyStruct`）の値渡し**: ポインタが保持するメモリアドレスの値がコピーされます。ポインタが指す先のデータ（実体）はコピーされません。

`new(sync.Mutex)`が返す`*sync.Mutex`はポインタ型です。このポインタを値渡ししても、コピーされるのは`sync.Mutex`オブジェクトが格納されているメモリアドレスであり、`sync.Mutex`オブジェクト自体がコピーされるわけではありません。したがって、複数のGoroutineが同じ`*sync.Mutex`ポインタのコピーを保持し、それを通じて同じ`sync.Mutex`オブジェクトにアクセスすることは可能です。これは同期の目的を損なわないため、`copylock`アナライザが警告すべきケースではありません。

## 技術的詳細

このコミットの技術的詳細の中心は、`go vet`の`copylock`アナライザが、関数呼び出しの引数として渡される値の中にロック型が含まれていないかをチェックするロジックに、組み込みの`new()`関数に対する特別な処理を追加した点です。

`src/cmd/vet/copylock.go`ファイルには、`checkCopyLocksCallExpr`という関数が存在します。この関数は、抽象構文木（AST: Abstract Syntax Tree）を走査し、関数呼び出し（`ast.CallExpr`）の引数（`ce.Args`）を分析して、ロック型の値渡しが行われていないかを検出します。

変更前は、`checkCopyLocksCallExpr`関数は、関数呼び出しが`new()`であるかどうかに関わらず、引数にロック型が含まれていれば一律に警告を発していました。このため、`new(sync.Mutex)`のように、実際にはポインタを返す安全な操作であっても、`sync.Mutex`というロック型が関与しているという理由だけで誤って警告されていました。

今回の修正では、`checkCopyLocksCallExpr`関数の冒頭に以下のロジックが追加されました。

1.  **関数が`new`であるかどうかの識別**:
    `ce.Fun`は関数呼び出しの関数部分を表すASTノードです。これが`*ast.Ident`（識別子、つまり関数名）であり、その名前が`"new"`であるかをチェックします。
2.  **組み込み`new`関数であることの確認**:
    Go言語では、ユーザーが`new`という名前の関数を独自に定義することも可能です。しかし、`copylock`アナライザが誤検知していたのは、Goの組み込み`new()`関数によるものです。したがって、ユーザー定義の`new`関数と組み込みの`new`関数を区別する必要があります。
    `f.pkg.types[id].IsBuiltin()`という呼び出しは、識別子`id`が指す型情報が、現在のパッケージ（`f.pkg`）のコンテキストにおいて組み込み型（または組み込み関数）であるかどうかを判定します。これにより、組み込みの`new()`関数のみを対象とすることができます。
3.  **チェックのスキップ**:
    上記の条件（関数が組み込みの`new()`である）が満たされた場合、`checkCopyLocksCallExpr`関数は直ちに`return`し、それ以降の引数チェックをスキップします。これにより、`new(sync.Mutex)`のような正当なコードに対して`copylock`アナライザが警告を発することを防ぎます。

この修正は、`go vet`の`copylock`アナライザのロジックに、Go言語の組み込み関数のセマンティクスをより正確に反映させることで、ツールの実用性と信頼性を向上させています。

## コアとなるコードの解説

### `src/cmd/vet/copylock.go`の変更点

`checkCopyLocksCallExpr`関数は、GoのASTを解析して関数呼び出しの引数にロック型の値渡しがないかをチェックします。このコミットで追加された以下のコードブロックが、この関数の動作を根本的に変更します。

```go
	if id, ok := ce.Fun.(*ast.Ident); ok && id.Name == "new" && f.pkg.types[id].IsBuiltin() {
		// Skip 'new(Type)' for built-in 'new'
		return
	}
```

*   `ce.Fun.(*ast.Ident)`: `ce.Fun`は`ast.CallExpr`（関数呼び出し）の関数部分を表す式です。この部分が`*ast.Ident`型（識別子、つまり関数名）に型アサーションできるかを試みます。成功した場合、`id`にはその識別子（関数名）が、`ok`には`true`がセットされます。
*   `id.Name == "new"`: 識別子の名前が文字列`"new"`であるかをチェックします。これにより、呼び出されている関数が`new`という名前であることが確認されます。
*   `f.pkg.types[id].IsBuiltin()`: ここが最も重要な部分です。Goでは、ユーザーが`new`という名前の関数を独自に定義することも可能です。しかし、`copylock`アナライザが誤検知していたのは、Goの組み込み`new()`関数によるものです。`f.pkg.types[id]`は、現在のパッケージの型情報から`id`（識別子`new`）に対応するオブジェクトの型情報を取得します。その型情報に対して`IsBuiltin()`メソッドを呼び出すことで、それが組み込み関数であるかどうかを厳密に判定します。
*   `return`: 上記の3つの条件がすべて真（つまり、呼び出されているのが組み込みの`new()`関数である）の場合、関数は直ちに終了します。これにより、`new()`関数の引数（例えば`new(sync.Mutex)`における`sync.Mutex`）に対する`copylock`チェックが完全にスキップされ、誤検知が回避されます。

この変更により、`go vet`は組み込み`new()`関数のセマンティクスを正しく理解し、`new(sync.Mutex)`のようなコードに対して不必要な警告を発しなくなります。

### `src/cmd/vet/testdata/copylock.go`の変更点

このファイルは`go vet`の`copylock`アナライザのテストデータを含んでいます。変更は主に`OkFunc`関数と`BadFunc`関数に追加されたテストケースです。

#### `OkFunc`関数への追加

```go
	nl := new(sync.Mutex)
	mx := make([]sync.Mutex, 10)
	xx := struct{ L *sync.Mutex }{
		L: new(sync.Mutex),
	}
```

*   `nl := new(sync.Mutex)`: `sync.Mutex`のポインタを`new()`で作成する典型的なケースです。この行は、修正後の`go vet`では警告されないことを確認するためのものです。`new()`は`*sync.Mutex`を返すため、`nl`は`*sync.Mutex`型となり、ロックの値渡しは発生しません。
*   `mx := make([]sync.Mutex, 10)`: `make`関数で`sync.Mutex`のスライスを作成するケースです。`make`はスライスヘッダを返し、スライス内の要素は`sync.Mutex`のゼロ値で初期化されます。この操作もロックの値渡しには該当しないため、警告されないことを確認します。
*   `xx := struct{ L *sync.Mutex }{ L: new(sync.Mutex), }`: 構造体のフィールドとして`*sync.Mutex`を持つ場合で、その初期化に`new()`を使用するケースです。これもポインタの値渡しであり、ロックの値渡しではないため、警告されないことを確認します。

これらのテストケースは、`go vet`が組み込み`new()`関数と`make()`関数を正しく処理し、誤検知を回避できるようになったことを検証します。

#### `BadFunc`関数への追加

```go
	// override 'new' keyword
	new := func(interface{}) {}
	new(t) // ERROR "function call copies lock value: testdata.Tlock contains sync.Once contains sync.Mutex"
```

*   `new := func(interface{}) {}`: このコードは、スコープ内で`new`という名前のユーザー定義関数を宣言しています。Goでは、組み込み関数と同じ名前の変数を宣言することで、そのスコープ内での組み込み関数の参照を「シャドウ」することができます。
*   `new(t) // ERROR ...`: この行は、ユーザー定義の`new`関数を呼び出しています。この`new`関数は組み込み関数ではないため、`copylock.go`で追加されたスキップロジックの対象外となります。したがって、もし`t`がロック型を含む構造体であれば、この呼び出しは依然としてロックの値渡しとして警告されるべきです。このテストケースは、`go vet`が組み込み`new()`とユーザー定義の`new`関数を正しく区別し、後者に対しては引き続き`copylock`チェックを適用することを確認します。

これらのテストケースは、`go vet`の`copylock`アナライザが、組み込み`new()`関数に対する修正後も、その意図された目的（ロックの誤った値渡しを検出する）を維持していることを保証します。

# [インデックス 23270] ファイルの概要

このコミットは、Go言語のビルドシステムにおいて、将来的にサポートされる可能性のある一般的なアーキテクチャの`GOARCH`値を`go/build`パッケージ内の`syslist.go`ファイルに予約（追加）するものです。これにより、新しい`GOARCH`が導入された際に、古いGoリリースがそれらを認識できないことによって生じる問題を回避し、ユーザーおよび開発者の双方にとっての不便さを解消することを目的としています。

## 元コミット内容

go/build: すべての一般的なアーキテクチャのGOARCH値を予約する

新しいGOARCHを導入するたびに、古いGoリリースはそれらを認識せず、これはユーザーと我々（不必要なビルドタグを追加する必要がある）の両方にとって問題を引き起こします。

Go 1.5ではこれまでにarm64、ppc64、ppc64leの3つの新しいGOARCHが導入されました。この問題を回避するために、Goが将来サポートする可能性のあるすべての一般的なアーキテクチャのGOARCHを導入する時間を取ることができます。

Fixes #10165.

## 変更の背景

Go言語は、その強力なクロスコンパイル機能で知られています。開発者は、`GOOS`（オペレーティングシステム）と`GOARCH`（アーキテクチャ）という環境変数を設定することで、異なるプラットフォーム向けのバイナリを簡単にビルドできます。しかし、Goの新しいバージョンがリリースされ、新たなアーキテクチャのサポートが追加されるたびに、問題が発生していました。

具体的には、古いGoのツールチェイン（コンパイラやビルドツール）は、新しいGoのバージョンで導入された`GOARCH`の値を認識できませんでした。例えば、Go 1.5で`arm64`が正式にサポートされたとしても、Go 1.4のツールチェインは`arm64`を有効な`GOARCH`として認識しないため、`GOARCH=arm64`を指定してビルドしようとするとエラーが発生しました。

この問題は、以下のような不便さを引き起こしていました。

1.  **ユーザーの混乱と不便**: ユーザーは、特定のアーキテクチャ向けのコードをビルドするために、常に最新のGoツールチェインを使用する必要がありました。また、古いGoバージョンで新しいアーキテクチャ向けのコードを扱う場合、`// +build`タグを使って条件付きコンパイルを行う際に、そのアーキテクチャが認識されないために、より複雑なビルドタグ（例: `// +build linux,arm64`ではなく、`// +build linux`と`// +build arm64`を組み合わせるなど）を使用する必要が生じることがありました。
2.  **開発者の負担**: Goの開発者側も、新しいアーキテクチャが追加されるたびに、古いGoバージョンとの互換性を考慮して、不必要なビルドタグを追加したり、ビルドシステムを調整したりする必要がありました。これは、コードベースの複雑性を増し、メンテナンスの負担となっていました。

Go 1.5では、`arm64`、`ppc64`、`ppc64le`といった新しいアーキテクチャが導入される予定であり、この問題が顕在化する可能性がありました。そこで、将来的な問題を未然に防ぐため、Goがサポートする可能性のある一般的なアーキテクチャの`GOARCH`値を事前に`go/build`パッケージに登録しておくことが決定されました。これにより、古いGoツールチェインでもこれらの`GOARCH`値を「有効なもの」として認識できるようになり、上記の問題が解消されることが期待されました。

## 前提知識の解説

### Goのビルドシステムと環境変数 (`GOOS`, `GOARCH`)

Go言語のビルドシステムは、環境変数`GOOS`と`GOARCH`に大きく依存しています。

*   **`GOOS` (Go Operating System)**: ビルド対象のオペレーティングシステムを指定します。例えば、`linux`、`darwin`（macOS）、`windows`、`freebsd`などがあります。
*   **`GOARCH` (Go Architecture)**: ビルド対象のCPUアーキテクチャを指定します。例えば、`amd64`（64-bit x86）、`386`（32-bit x86）、`arm`、`arm64`などがあります。

これらの変数を設定することで、Goは異なるOSやCPUアーキテクチャ向けの実行ファイルを生成する「クロスコンパイル」を容易に行うことができます。例えば、macOS上で`GOOS=linux GOARCH=amd64 go build`と実行すると、Linuxの64-bit x86環境で動作するバイナリが生成されます。

### ビルドタグ (Build Tags)

Goのソースコードでは、特定の環境でのみコンパイルされるべきコードブロックを指定するために「ビルドタグ」を使用します。これは、ファイルの先頭に`// +build tagname`のようなコメントとして記述されます。

例:
```go
// +build linux,amd64

package main

import "fmt"

func main() {
    fmt.Println("This runs only on Linux AMD64.")
}
```
このコードは、`GOOS=linux`かつ`GOARCH=amd64`の場合にのみコンパイルされます。ビルドタグは、プラットフォーム固有のコードや、特定の機能が利用可能な場合にのみ含めるコードを管理するために非常に重要です。

しかし、古いGoツールチェインが新しい`GOARCH`値を認識しない場合、たとえ`// +build arm64`のようなタグがコードに存在しても、そのタグは無視されるか、あるいは無効なタグとして扱われる可能性がありました。これにより、開発者は`GOARCH`に依存しない、より汎用的な（しかし意図しない）ビルドタグを使用せざるを得なくなることがありました。

### `go/build`パッケージと`syslist.go`

`go/build`パッケージは、Goのソースコードを解析し、ビルドプロセスを管理するためのGo標準ライブラリの一部です。このパッケージは、Goのツールチェインがソースファイルをどのように見つけ、どのファイルをコンパイルに含めるかを決定する際に使用されます。

このパッケージの内部には、`syslist.go`というファイルが存在します。このファイルは、Goが認識する有効な`GOOS`と`GOARCH`のリストを定数として保持しています。Goのビルドツールは、このリストを参照して、指定された`GOOS`や`GOARCH`が有効であるか、またビルドタグが正しく解釈できるかを判断します。

このコミットの変更は、まさにこの`syslist.go`ファイル内の`goarchList`定数を更新し、将来的にサポートされる可能性のあるアーキテクチャ名を事前に登録することで、古いGoツールチェインでもこれらの名前を「有効なアーキテクチャ名」として認識できるようにすることを目的としています。これにより、たとえそのアーキテクチャ向けのコンパイラバックエンドがまだ存在しなくても、ビルドタグの解析やクロスコンパイルの指定において、構文的なエラーを回避できるようになります。

## 技術的詳細

このコミットの核心は、Goのビルドシステムが認識する有効なCPUアーキテクチャのリストを拡張することにあります。具体的には、`src/go/build/syslist.go`ファイル内の`goarchList`という文字列定数が変更されました。

変更前は、`goarchList`にはGoが当時サポートしていた、または認識していた主要なアーキテクチャのみが含まれていました。しかし、Go 1.5で`arm64`、`ppc64`、`ppc64le`といった新しいアーキテクチャが導入されるにあたり、Goチームは、将来的にGoがサポートする可能性のある他の一般的なアーキテクチャも事前にこのリストに追加しておくべきだと判断しました。

この「予約」のメカニズムは、Goのビルドツールが、たとえ特定の`GOARCH`向けのコンパイラバックエンドがまだ完全に実装されていなくても、その`GOARCH`名を有効な識別子として認識できるようにすることを可能にします。これにより、以下のような利点が得られます。

1.  **後方互換性の向上**: 古いGoツールチェインが、新しいGoバージョンで導入された`GOARCH`値を無効なものとして扱わなくなります。これにより、新しいアーキテクチャ向けのコードを含むプロジェクトを古いGoバージョンで開いた場合でも、少なくとも構文エラーやビルドタグの解釈に関する問題が発生しにくくなります。
2.  **ビルドタグの簡素化**: 開発者は、将来のアーキテクチャをターゲットとするコードを書く際に、不必要な複雑なビルドタグ（例: `// +build !go1.5`のようなバージョンチェックを含むタグ）を避けることができます。単に`// +build mips64`のように記述するだけで、Goツールチェインはそのタグを認識し、適切な条件でコンパイルをスキップまたは実行できるようになります。
3.  **将来の拡張性**: Goが実際にこれらの予約されたアーキテクチャを完全にサポートする準備ができたとき、ビルドシステム側での大きな変更は不要となり、コンパイラバックエンドの実装に集中できます。

追加された`GOARCH`値には、`mips`、`mipsle`、`mips64`、`mips64le`、`mips64p32`、`mips64p32le`（MIPSアーキテクチャの様々なバリアント）、`ppc`（32-bit PowerPC）、`s390`、`s390x`（IBM System/390およびz/Architecture）、`sparc`、`sparc64`（SPARCアーキテクチャ）などが含まれています。これらは、エンタープライズシステム、組み込みシステム、高性能コンピューティングなど、様々な分野で利用されている一般的なアーキテクチャです。これらの値を事前に登録することで、Goがより広範なプラットフォームへの対応をスムーズに進めるための基盤が築かれました。

## コアとなるコードの解説

このコミットにおける唯一かつ最も重要な変更は、`src/go/build/syslist.go`ファイル内の`goarchList`定数の定義です。

変更前:
```go
const goarchList = "386 amd64 amd64p32 arm arm64 ppc64 ppc64le "
```

変更後:
```go
const goarchList = "386 amd64 amd64p32 arm arm64 ppc64 ppc64le mips mipsle mips64 mips64le mips64p32 mips64p32le ppc s390 s390x sparc sparc64 "
```

この変更は、`goarchList`文字列に以下の新しい`GOARCH`値を追加しています。

*   `mips`
*   `mipsle`
*   `mips64`
*   `mips64le`
*   `mips64p32`
*   `mips64p32le`
*   `ppc`
*   `s390`
*   `s390x`
*   `sparc`
*   `sparc64`

これらの文字列は、Goのビルドツールが有効なアーキテクチャ名を認識するために使用されます。このリストに名前を追加することで、Goのツールチェインは、これらのアーキテクチャ名を指定したビルドコマンド（例: `GOARCH=mips64 go build`）や、これらのアーキテクチャ名を指定したビルドタグ（例: `// +build mips64`）を、たとえその時点では完全なコンパイラサポートがなくても、構文的に有効なものとして処理できるようになります。

これにより、Goの将来的なアーキテクチャサポートに向けた基盤が強化され、新しいアーキテクチャが追加されるたびに発生していた互換性の問題やビルドタグの複雑化が軽減されます。

## 変更の背景

Goの`io`パッケージが提供する`Pipe`関数は、`io.Reader`と`io.Writer`インターフェースを実装する2つのエンドポイント（読み取り側と書き込み側）を持つインメモリパイプを作成します。これは、あるコンポーネントの出力を別のコンポーネントの入力に直接接続する際に非常に便利です。

このコミット以前の`io.Pipe`の実装では、パイプの読み取り側または書き込み側を`Close()`メソッドで閉じると、接続されたもう一方の側には、書き込み側が閉じられた場合は読み取り側で`nil`エラー（EOF）、読み取り側が閉じられた場合は書き込み側で`os.EPIPE`エラーが伝播されるだけでした。

しかし、実際のアプリケーションでは、パイプのクローズが単なる終了ではなく、特定のエラー状態を示す場合があります。例えば、書き込み側が何らかの理由で処理を中断し、その理由を読み取り側に伝えたい場合、従来の`Close()`ではそれができませんでした。常に`os.EPIPE`（パイプが壊れたことを示す一般的なエラー）しか返せないため、より詳細なエラー情報を伝える手段が不足していました。

この問題に対処するため、`CloseWithError`メソッドが導入されました。これにより、パイプのいずれかの端を閉じる際に、任意の`os.Error`（現在の`error`インターフェース）を渡すことが可能になり、そのエラーがパイプのもう一方の端に伝播されるようになります。これにより、パイプを介したエラーハンドリングの柔軟性と表現力が大幅に向上しました。

また、この変更に伴い、内部的に使用されていた`pipeRead`と`pipeWrite`という非公開型が、`PipeReader`と`PipeWriter`という公開型に変更されました。これにより、ユーザーはこれらの型を直接参照し、新しい`CloseWithError`メソッドを利用できるようになりました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の基本的な概念と`io`パッケージの知識が必要です。

1.  **`io.Reader`と`io.Writer`インターフェース**:
    *   `io.Reader`は`Read(p []byte) (n int, err error)`メソッドを持つインターフェースで、データソースからの読み取りを抽象化します。
    *   `io.Writer`は`Write(p []byte) (n int, err error)`メソッドを持つインターフェースで、データシンクへの書き込みを抽象化します。
    *   これらはGoにおけるI/O操作の基本的な構成要素です。

2.  **`io.Closer`インターフェース**:
    *   `Close() error`メソッドを持つインターフェースで、リソースのクリーンアップ（ファイルディスクリプタの解放、ネットワーク接続の切断など）を抽象化します。
    *   `io.Pipe`の各エンドポイントも`io.Closer`を実装しています。

3.  **`os.Error` (現在の`error`インターフェース)**:
    *   Go 1.0以前のバージョンでは、エラーは`os.Error`というインターフェースで表現されていました。これは現在の`error`インターフェースに相当します。`Error() string`メソッドを持ち、エラーメッセージを返します。
    *   `os.EPIPE`は、パイプが壊れている、または読み取り側が閉じられているために書き込みができない場合に発生する標準的なエラーです。

4.  **Goのチャネル (Channels)**:
    *   チャネルは、Goルーチン間で値を送受信するための通信メカニズムです。Goルーチン間の同期とデータ転送に不可欠です。
    *   `io.Pipe`の内部では、読み取り側と書き込み側の間でデータを転送し、同期を取るためにチャネルが使用されています。

5.  **Goの`sync.Mutex`**:
    *   `Mutex`（ミューテックス）は、共有リソースへのアクセスを同期するためのプリミティブです。複数のGoルーチンが同時に同じデータにアクセスするのを防ぎ、データ競合を回避するために使用されます。
    *   `io.Pipe`の実装では、パイプの状態（閉じられているか、書き込み中のデータなど）を保護するためにミューテックスが使用されています。

6.  **`io.Pipe`の基本的な動作**:
    *   `io.Pipe()`は、`io.Reader`と`io.Writer`のペアを返します。
    *   `Writer`への書き込みは、`Reader`がデータを読み取るまでブロックされます（バッファリングなし）。
    *   `Reader`からの読み取りは、`Writer`がデータを書き込むまでブロックされます。
    *   いずれかの端が閉じられると、もう一方の端の読み書き操作は適切なエラー（またはEOF）で終了します。

## 技術的詳細

このコミットの核心は、`io.Pipe`の内部構造と外部インターフェースの両方に変更を加え、エラー伝播のメカニズムを強化した点にあります。

### 1. `pipe`構造体の変更

`io.Pipe`の内部で共有される`pipe`構造体に、新しいフィールドが追加されました。

```go
type pipe struct {
	rclosed bool;		// Read end closed?
	rerr os.Error;		// Error supplied to CloseReader
	wclosed bool;		// Write end closed?
	werr os.Error;		// Error supplied to CloseWriter
	wpend []byte;		// Written data waiting to be read.
	wtot int;		// Bytes consumed so far in current write.
	cr chan []byte;		// Write sends data here...
	cw chan pipeReturn;	// ...and waits for return here.
}
```

*   `rerr os.Error;`: 読み取り側が`CloseWithError`で閉じられた際に指定されたエラーを保持します。
*   `werr os.Error;`: 書き込み側が`CloseWithError`で閉じられた際に指定されたエラーを保持します。

これらのフィールドにより、パイプの各端が閉じられた際に、そのクローズ操作に関連付けられた特定のエラーを内部的に保存できるようになります。

### 2. `Read`および`Write`メソッドのエラー伝播

`pipe`構造体の`Read`および`Write`メソッドが変更され、`rerr`または`werr`フィールドに保存されたエラーを返すようになりました。

*   `Read`メソッドは、書き込み側が閉じられ、かつ`wpend`（書き込み待ちデータ）が`nil`の場合、以前は`nil`エラーを返していましたが、`p.werr`を返すように変更されました。これにより、書き込み側が`CloseWithError`で閉じられた場合、そのエラーが読み取り側に伝播されます。
*   `Write`メソッドは、読み取り側が閉じられている場合、以前は`os.EPIPE`を返していましたが、`p.rerr`を返すように変更されました。これにより、読み取り側が`CloseWithError`で閉じられた場合、そのエラーが書き込み側に伝播されます。もし`rerr`が`nil`であれば、デフォルトで`os.EPIPE`が使用されます。

### 3. `CloseReader`および`CloseWriter`メソッドの変更

内部的な`CloseReader`と`CloseWriter`メソッドが、`os.Error`型の引数を受け取るように変更されました。

```go
func (p *pipe) CloseReader(rerr os.Error) os.Error {
    // ...
    if rerr == nil {
        rerr = os.EPIPE; // デフォルトエラー
    }
    p.rerr = rerr;
    // ...
    p.cw <- pipeReturn{p.wtot, rerr}; // 書き込み側にもエラーを通知
    // ...
}

func (p *pipe) CloseWriter(werr os.Error) os.Error {
    // ...
    p.werr = werr; // 書き込みエラーを保存
    // ...
    // 読み取り側にはwerrがnilの場合、EOFが伝播される（Readメソッドの変更により）
    // ...
}
```

これらの変更により、パイプのクローズ時にカスタムエラーを内部`pipe`構造体に保存し、チャネルを通じて接続されたもう一方の端にそのエラーを通知するメカニズムが確立されました。

### 4. `PipeReader`と`PipeWriter`型の公開と`CloseWithError`の追加

最もユーザーに影響を与える変更は、`pipeRead`と`pipeWrite`という非公開型が、それぞれ`PipeReader`と`PipeWriter`という公開型に変更されたことです。そして、これらの公開型に`CloseWithError`メソッドが追加されました。

```go
type PipeReader struct {
	lock sync.Mutex;
	p *pipe;
}

func (r *PipeReader) Close() os.Error {
	// ...
	return r.p.CloseReader(nil); // 従来のCloseはnilエラーで内部CloseReaderを呼び出す
}

func (r *PipeReader) CloseWithError(rerr os.Error) os.Error {
	// ...
	return r.p.CloseReader(rerr); // カスタムエラーで内部CloseReaderを呼び出す
}

type PipeWriter struct {
	lock sync.Mutex;
	p *pipe;
}

func (w *PipeWriter) Close() os.Error {
	// ...
	return w.p.CloseWriter(nil); // 従来のCloseはnilエラーで内部CloseWriterを呼び出す
}

func (w *PipeWriter) CloseWithError(werr os.Error) os.Error {
	// ...
	return w.p.CloseWriter(werr); // カスタムエラーで内部CloseWriterを呼び出す
}
```

`PipeReader`と`PipeWriter`は、それぞれ`Read`と`Write`メソッドを実装し、内部の`pipe`構造体の対応するメソッドを呼び出します。`Close()`メソッドは、`CloseWithError(nil)`を呼び出すことで、従来の動作（エラーなしで閉じる）を維持します。新しい`CloseWithError`メソッドは、ユーザーが指定したエラーを内部の`CloseReader`または`CloseWriter`に渡し、そのエラーがパイプのもう一方の端に伝播されるようにします。

### 5. `Pipe()`関数の戻り値の変更

`Pipe()`関数のシグネチャも変更され、`io.ReadCloser, io.WriteCloser`から`*PipeReader, *PipeWriter`を直接返すようになりました。

```go
// 変更前
func Pipe() (io.ReadCloser, io.WriteCloser) { ... }

// 変更後
func Pipe() (*PipeReader, *PipeWriter) { ... }
```

これにより、ユーザーは`Pipe()`の戻り値から直接`PipeReader`と`PipeWriter`の具体的な型を受け取り、`CloseWithError`メソッドを呼び出すことができるようになります。

### テストの変更

`pipe_test.go`も大幅に修正され、新しい`CloseWithError`メソッドの動作を検証するテストケースが追加されました。特に、`pipeTest`構造体が導入され、非同期クローズ、エラーの有無、`CloseWithError`の使用有無など、様々なシナリオでパイプの読み書きが期待通りにエラーを返すかどうかがテストされています。

## コアとなるコードの解説

### `pipe`構造体への`rerr`, `werr`フィールドの追加

これは、パイプの読み取り側または書き込み側が閉じられた際に、そのクローズ操作に関連付けられた特定のエラーを永続的に保存するためのメカニズムです。これにより、従来の`nil`または`os.EPIPE`という限定的なエラー情報だけでなく、より詳細なエラー情報をパイプの内部状態として保持できるようになります。

### `pipe.Read`および`pipe.Write`メソッドのエラー伝播ロジック変更

*   `pipe.Read`が`p.werr`を返すようになったことで、書き込み側が`CloseWithError`で閉じられた場合に、そのカスタムエラーが読み取り側に伝播されるようになりました。これにより、読み取り側は書き込み側がなぜ終了したのかを具体的に知ることができます。
*   `pipe.Write`が`p.rerr`を返すようになったことで、読み取り側が`CloseWithError`で閉じられた場合に、そのカスタムエラーが書き込み側に伝播されるようになりました。これにより、書き込み側は読み取り側がなぜ終了したのかを具体的に知ることができます。`rerr`が`nil`の場合は、従来の`os.EPIPE`がデフォルトとして使用されます。

これらの変更は、パイプのデータ転送チャネルが閉じられた後に、`pipe`構造体に保存されたエラー情報を参照して、適切なエラーを呼び出し元に返すというロジックを確立します。

### `pipe.CloseReader`および`pipe.CloseWriter`メソッドの変更

これらの内部メソッドは、`rerr`または`werr`という引数を受け取るように変更されました。
*   `CloseReader`では、`rerr`が`nil`の場合にデフォルトで`os.EPIPE`を設定し、そのエラーを`p.rerr`に保存します。また、書き込み側がまだ閉じられていない場合、`pipeReturn`チャネルを通じてこのエラーを書き込み側に通知します。
*   `CloseWriter`では、`werr`を`p.werr`に保存します。読み取り側がまだ閉じられていない場合、`pipeReturn`チャネルを通じて読み取り側に通知しますが、この通知は`Read`メソッドが`p.werr`を参照するロジックと連携して機能します。

これらの変更により、パイプのクローズ時にカスタムエラーを内部的に処理し、もう一方の端に伝播させるための基盤が構築されました。

### `PipeReader`と`PipeWriter`の公開と`CloseWithError`の追加

*   `pipeRead`と`pipeWrite`が公開型`PipeReader`と`PipeWriter`になったことで、ユーザーはこれらの型を直接操作できるようになりました。これにより、`CloseWithError`メソッドを呼び出すことが可能になります。
*   `CloseWithError`メソッドは、ユーザーが指定したエラーを内部の`pipe.CloseReader`または`pipe.CloseWriter`に渡します。これにより、アプリケーションはパイプのクローズ時に発生した具体的なエラーを、もう一方の端に伝えることができるようになり、より堅牢なエラーハンドリングが可能になります。
*   既存の`Close()`メソッドは、`CloseWithError(nil)`を呼び出すことで、後方互換性を保ちつつ、新しいエラー伝播メカニズムを利用しています。

### `Pipe()`関数の戻り値の変更

`Pipe()`関数が`*PipeReader, *PipeWriter`を直接返すようになったことで、ユーザーは型アサーションなしに`CloseWithError`メソッドにアクセスできるようになりました。これは、APIの使いやすさを向上させる変更です。

これらの変更全体として、`io.Pipe`は単なるデータ転送だけでなく、パイプのライフサイクルにおけるエラー状態もより詳細に管理できるようになり、GoのI/Oプログラミングの柔軟性と表現力を高めています。

# [インデックス 22597] ファイルの概要

このコミットは、Goランタイムのシグナルハンドラにおける書き込みバリアの挙動を修正するものです。以下のファイルが影響を受けています。

*   `src/runtime/os3_plan9.go`: Plan 9オペレーティングシステム向けのランタイムシグナルハンドラ実装。
*   `src/runtime/signal_386.go`: 32ビットx86アーキテクチャ向けのランタイムシグナルハンドラ実装。
*   `src/runtime/signal_amd64x.go`: AMD64（64ビットx86）アーキテクチャ向けのランタイムシグナルハンドラ実装。
*   `src/runtime/signal_arm.go`: ARMアーキテクチャ向けのランタイムシグナルハンドラ実装。
*   `src/runtime/signal_arm64.go`: ARM64アーキテクチャ向けのランタイムシグナルハンドラ実装。
*   `src/runtime/signal_ppc64x.go`: PowerPC 64ビットアーキテクチャ向けのランタイムシグナルハンドラ実装。

これらのファイルはすべて、GoランタイムがOSからのシグナルを処理するための低レベルなコードを含んでいます。

## コミット

このコミットは、Goランタイムのシグナルハンドラ関数において、G（ゴルーチン）へのポインタ書き込み時に発生する書き込みバリアを削除するものです。シグナルハンドラは、P（プロセッサ）が利用できないStop-The-World (STW) フェーズ中に実行される可能性があり、その状況下では書き込みバリアが許可されないため、この変更が必要とされました。具体的には、Gへの書き込みが書き込みバリアを無効にして行われるように修正され、シグナルハンドラ関数自体が`nowritebarrier`としてマークされました。この変更は、Gが`allgs`（すべてのゴルーチンのリスト）から到達可能であるため安全です。

## 変更の背景

Go言語のガベージコレクション（GC）は、プログラムの実行と並行して動作する「並行GC」を採用しています。この並行性を維持しつつ、メモリの整合性を保証するために「書き込みバリア（Write Barrier）」というメカニズムが導入されています。書き込みバリアは、ヒープ上のポインタが変更される際に自動的に実行される小さなコードスニペットであり、GCがオブジェクトグラフの変更を追跡し、誤って到達可能なオブジェクトを回収してしまうことを防ぎます。

しかし、Goランタイムには「Stop-The-World (STW)」と呼ばれる、すべてのゴルーチンの実行を一時的に停止させる短い期間が存在します。STWはGCの特定のフェーズ（例えば、マークフェーズの開始と終了）で必要とされ、GCの正確性を保証するために不可欠です。

シグナルハンドラは、オペレーティングシステムからのシグナル（例: セグメンテーション違反、割り込み）を受け取った際に非同期に実行される特別な関数です。Goランタイムは、これらのシグナルを処理するために独自のシグナルハンドラを持っています。問題は、このシグナルハンドラがSTW中に、かつGoのスケジューラモデルにおけるP（プロセッサ）が割り当てられていないM（OSスレッド）上で実行される可能性がある点にありました。

Pが割り当てられていないM上では、通常のGoランタイムのコンテキストが完全に確立されておらず、書き込みバリアが正しく機能しない、あるいは予期せぬ副作用（デッドロックやクラッシュなど）を引き起こす可能性があります。シグナルハンドラ内でG（ゴルーチン）へのポインタ書き込みが行われる際、もし書き込みバリアが発動すると、このような不安定な状況下でGCの整合性が損なわれるリスクがありました。

このコミットは、このような特定のシナリオ（STW中のシグナルハンドラ、Pなし）において、書き込みバリアが不要かつ危険であると判断し、それを明示的に無効化することでランタイムの堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットの理解には、Goランタイムの内部構造、ガベージコレクション、およびシグナル処理に関するいくつかの前提知識が必要です。

1.  **Goランタイム (Go Runtime)**:
    Goプログラムの実行を管理するシステム全体を指します。これには、ゴルーチンのスケジューリング、メモリ管理（ガベージコレクションを含む）、チャネル操作、システムコールインターフェースなどが含まれます。Goプログラムは、OS上で直接実行されるのではなく、このランタイム上で動作します。

2.  **GPMモデル (Goroutine-Processor-Machine Model)**:
    Goの並行処理を支えるスケジューラモデルです。
    *   **G (Goroutine)**: Goにおける軽量な実行単位です。OSスレッドよりもはるかに軽量で、数百万個作成することも可能です。Goの関数呼び出しがゴルーチンとして実行されます。
    *   **P (Processor)**: 論理的なプロセッサであり、Gを実行するためのコンテキストを提供します。PはM（OSスレッド）にアタッチされ、GをM上で実行可能にします。Pの数は通常、CPUのコア数に設定され、GoスケジューラがGをPに割り当て、PがM上でGを実行します。
    *   **M (Machine / OS Thread)**: オペレーティングシステムのスレッドです。Goランタイムは、OSスレッドをMとして抽象化し、その上でPとGを実行します。MはOSによってスケジューリングされます。

3.  **ガベージコレクション (Garbage Collection, GC)**:
    GoのGCは、不要になったメモリを自動的に解放するメカニズムです。Go 1.5以降、GoのGCは「並行マーク＆スイープ」方式を採用しており、ほとんどのGC作業をアプリケーションの実行と並行して行います。これにより、GCによるアプリケーションの一時停止（ポーズ）時間を最小限に抑えています。

4.  **書き込みバリア (Write Barrier)**:
    並行GCにおいて、GCの正確性を保証するために不可欠な技術です。GCがオブジェクトグラフを走査している最中に、アプリケーションがポインタを書き換える（新しいオブジェクトへの参照を作成する）と、GCがその変更を認識できず、まだ到達可能なオブジェクトを誤って回収してしまう可能性があります。これを防ぐために、ポインタの書き込み操作が行われるたびに、GCにその変更を通知する小さなコード（バリア）が実行されます。GoのGCは「三色マーキング」アルゴリズム（白、灰、黒）を使用しており、書き込みバリアはこの三色不変条件を維持する役割を担います。

5.  **Stop-The-World (STW)**:
    GCの特定のフェーズで、すべてのゴルーチンの実行を一時的に停止させる期間です。GoのGCはほとんどが並行ですが、GCの開始時（マークセットアップ）と終了時（マークターミネーション）には、GCの整合性を確保するために短いSTWポーズが必要です。この期間中、アプリケーションのゴルーチンは一切実行されません。Goランタイムは、このSTWポーズの時間を極力短くするよう最適化されています。

6.  **シグナルハンドラ (Signal Handler)**:
    OSがプロセスに送信する「シグナル」と呼ばれる非同期イベントを処理するための関数です。シグナルは、プログラムの異常終了（例: セグメンテーション違反）、ユーザーからの割り込み（Ctrl+C）、タイマーイベントなど、様々な状況で発生します。Goランタイムは、これらのシグナルを捕捉し、適切に処理するために低レベルなシグナルハンドラを内部に持っています。シグナルハンドラは、通常のプログラム実行フローとは独立して、OSによって任意のタイミングで呼び出される可能性があります。

## 技術的詳細

このコミットの核心は、Goランタイムのシグナルハンドラが実行される特定のコンテキストにあります。

1.  **シグナルハンドラの特殊な実行コンテキスト**:
    シグナルハンドラは、OSによって非同期に呼び出されます。これは、Goランタイムが現在どのような状態にあるかに関わらず発生し得ます。特に重要なのは、シグナルハンドラがGoのGPMスケジューラモデルにおけるP（プロセッサ）がアタッチされていないM（OSスレッド）上で実行される可能性があるという点です。Pがない状態では、Goランタイムの多くの機能（特にGCの書き込みバリアなど）が正しく動作するための前提条件が満たされません。

2.  **書き込みバリアの危険性**:
    書き込みバリアは、GCがヒープ上のポインタ変更を追跡するために必要ですが、PがないM上で実行されると、GCの状態が不整合になったり、デッドロックを引き起こしたりする可能性があります。シグナルハンドラは、クラッシュなどの緊急事態に対応するために設計されており、その実行は可能な限りシンプルで堅牢である必要があります。GCの複雑なロジックが介在することは望ましくありません。

3.  **`//go:nowritebarrier` ディレクティブ**:
    Goコンパイラには、特定の関数に対して書き込みバリアの生成を抑制する特別なディレクティブ（指示子）が存在します。`//go:nowritebarrier` は、その関数内でポインタの書き込みが行われても、コンパイラが書き込みバリアのコードを挿入しないように指示します。このコミットでは、`sighandler`関数がこのディレクティブでマークされました。これにより、シグナルハンドラがSTW中にPなしで実行されても、書き込みバリアによる問題が発生しないようにします。もし、このディレクティブが指定されているにも関わらず、コンパイラが書き込みバリアが必要だと判断するようなコードが関数内に存在すれば、コンパイルエラーが発生します。

4.  **`setGNoWriteBarrier` 関数の導入（または利用）**:
    コミットの差分を見ると、`_g_.m.caughtsig = gp` という直接的なポインタ代入が `setGNoWriteBarrier(&_g_.m.caughtsig, gp)` という関数呼び出しに置き換えられています。`setGNoWriteBarrier` はGoランタイム内部の関数であり、その名前が示す通り、書き込みバリアを介さずにGへのポインタを安全に設定するためのものです。これは、`_g_.m.caughtsig` に代入される `gp`（シグナルを受け取ったゴルーチン）が、Goランタイムが管理するすべてのゴルーチンのリストである `allgs` から既に到達可能であることが保証されているため、書き込みバリアを省略してもGCが誤ってこのGを回収することはない、という前提に基づいています。つまり、GCは既にこのGの存在を認識しているため、このポインタの更新を特別に追跡する必要がないのです。

これらの変更により、シグナルハンドラはGoランタイムの最も不安定な状態（STW中、Pなし）でも安全かつ確実に動作し、GCの整合性を損なうことなく、クラッシュなどの重要なイベントを処理できるようになります。

## コアとなるコードの解説

これらの変更は、Goランタイムのシグナルハンドラが、ガベージコレクションの書き込みバリアと安全に共存できるようにするためのものです。

1.  **`//go:nowritebarrier` ディレクティブの追加**:
    この行は、Goコンパイラに対する指示です。`sighandler`関数は、Goランタイムの非常に低レベルな部分であり、特にStop-The-World (STW) フェーズ中に、P（プロセッサ）が割り当てられていないM（OSスレッド）上で実行される可能性があります。このような状況では、通常の書き込みバリアのロジックが正しく機能しない、あるいはデッドロックやクラッシュを引き起こす危険性があります。
    `//go:nowritebarrier` を追加することで、コンパイラは`sighandler`関数内のポインタ書き込み（特に`_g_.m.caughtsig = gp`のような操作）に対して、GCの書き込みバリアコードを挿入しなくなります。これにより、シグナルハンドラが実行される際のランタイムの不安定な状態が回避され、GCの整合性を損なうことなく、シグナル処理が堅牢に行われるようになります。

2.  **`_g_.m.caughtsig = gp` から `setGNoWriteBarrier(&_g_.m.caughtsig, gp)` への変更**:
    *   `_g_.m.caughtsig`: これは、現在のM（OSスレッド）がシグナルを捕捉したG（ゴルーチン）へのポインタを保持するフィールドです。Mは、パニックなどの際に、どのゴルーチンがシグナルによって中断されたかを記録するためにこのフィールドを使用します。
    *   `gp`: シグナルを受け取った実際のゴルーチンへのポインタです。
    *   元のコード `_g_.m.caughtsig = gp` は、通常のGoのポインタ代入であり、コンパイラによって自動的に書き込みバリアが挿入される可能性があります。
    *   新しいコード `setGNoWriteBarrier(&_g_.m.caughtsig, gp)` は、Goランタイム内部で定義されている特別な関数 `setGNoWriteBarrier` を呼び出しています。この関数は、その名前が示す通り、「書き込みバリアなしでGを設定する」ためのものです。
    *   この変更の安全性は、コミットメッセージにある「this is safe because the G is reachable from allgs」という説明に基づいています。`gp`が指すゴルーチンは、Goランタイムが管理するすべてのゴルーチンのリストである`allgs`に既に含まれており、GCによって到達可能であることが保証されています。したがって、このポインタへの書き込みバリアを省略しても、GCが誤ってこのゴルーチンを回収してしまうことはありません。この関数は、GCの整合性を損なうことなく、特定の低レベルなポインタ操作を最適化するために使用されます。

これらの変更は、Goランタイムの堅牢性とパフォーマンスを向上させるための、非常に低レベルかつ重要な最適化です。

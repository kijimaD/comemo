# [インデックス 24478] ファイルの概要

このコミットは、Goランタイムと`sync/atomic`パッケージにおけるARMアーキテクチャ向けのCAS (Compare-And-Swap) ルーチンにメモリバリアを追加するものです。具体的には、ARMv7以上のプロセッサを対象とし、Apple iPad Mini 3上での`TestLFStress`テストの失敗および`sync/atomic`テストのタイムアウト問題を解決することを目的としています。

## 元コミット内容

Goランタイムおよび`sync/atomic`パッケージのARM向けCASルーチンにメモリバリアを追加します。この変更はARMv7以上のプロセッサでのみ有効になります。もし重要なSMP ARMv6マシンが存在する場合には再検討の余地があります。この変更により、Apple iPad Mini 3上での`TestLFStress`テストがパスし、`sync/atomic`テストがタイムアウトしなくなります。Go issue #7977と#10189を修正します。

## 変更の背景

Go言語は、その並行処理モデルと、`sync/atomic`パッケージのような低レベルの同期プリミティブを通じて、強力なメモリモデルの保証を提供します。しかし、実際のハードウェア、特にARMアーキテクチャのような「弱いメモリモデル」を持つプロセッサでは、コンパイラやCPUによる命令の並べ替え（リオーダリング）が発生し、プログラマが意図したメモリ操作の順序が保証されないことがあります。

このコミットの背景には、Apple iPad Mini 3（ARMv7+プロセッサを搭載）上でGoの並行処理テストが失敗したりタイムアウトしたりするという具体的な問題がありました。具体的には、`TestLFStress`テスト（ロックフリーデータ構造のストレス試験）や`sync/atomic`パッケージのテストが、メモリ操作の順序が正しく保証されないために、期待通りの動作をしなかったと考えられます。これは、Goのメモリモデルが提供する保証と、ARMハードウェアの実際の動作との間にギャップがあったことを示唆しています。

このような問題は、特にマルチコアプロセッサ環境において、複数のCPUコアが共有メモリにアクセスする際に顕在化します。あるコアが行ったメモリへの書き込みが、別のコアからすぐに可視になるとは限らず、また、書き込みの順序がプログラムの意図と異なる順序で観測される可能性があります。これを解決するためには、明示的なメモリバリア（またはメモリフェンス）を挿入し、特定のメモリ操作の順序を強制する必要があります。

## 前提知識の解説

### 弱いメモリモデルと強いメモリモデル

*   **強いメモリモデル (Strong Memory Model)**: プロセッサがメモリ操作をプログラムで指定された順序で実行し、その順序がすべてのプロセッサから一貫して観測されることを保証するモデルです。x86/x64アーキテクチャは比較的強いメモリモデルを持っています。
*   **弱いメモリモデル (Weak Memory Model)**: プロセッサが性能向上のためにメモリ操作の順序を自由に並べ替えることができるモデルです。ARMアーキテクチャは弱いメモリモデルの代表例であり、明示的な同期命令なしにはメモリ操作の順序が保証されません。

### メモリバリア (Memory Barrier / Memory Fence)

メモリバリアは、コンパイラやプロセッサによる命令の並べ替えを制限し、特定のメモリ操作の順序を強制する命令です。これにより、複数のプロセッサやスレッドが共有メモリにアクセスする際のデータの一貫性を保証します。

### ARMアーキテクチャにおけるメモリバリア (`DMB`)

ARMアーキテクチャでは、`DMB` (Data Memory Barrier) 命令がメモリバリアとして使用されます。`DMB`命令は、その命令より前に発生したすべてのメモリアクセスが、その命令より後に発生するすべてのメモリアクセスよりも先に完了することを保証します。`DMB`にはいくつかのバリエーションがあり、その効果範囲（Shareability Domain）と対象となるアクセスタイプ（Load/Store）を指定できます。

*   **Shareability Domain**:
    *   `ISH` (Inner Shareable): 内部共有可能ドメイン内のメモリ操作に適用されます。通常、マルチコアプロセッサ内のコア間同期に使用されます。
    *   `SY` (System): システム全体に適用されます。
    *   `OSH` (Outer Shareable): 外部共有可能ドメイン内のメモリ操作に適用されます。
    *   `NSH` (Non-shareable): 非共有可能ドメイン内のメモリ操作に適用されます。
*   **Access Types**:
    *   指定なし (例: `ISH`): ロードとストアの両方に適用されるフルバリア。
    *   `ST` (Store): ストア（書き込み）操作のみに適用されるバリア。

このコミットで追加された`dmb ishst`と`dmb ish`は以下の意味を持ちます。

*   **`dmb ishst`**: Inner Shareableドメイン内でのストア操作のみを順序付けるデータメモリバリアです。このバリアより前のストア操作は、このバリアより後のストア操作よりも先に完了することが保証されます。ロード操作は順序付けの対象外です。
*   **`dmb ish`**: Inner Shareableドメイン内でのロードとストアの両方の操作を順序付けるデータメモリバリアです。このバリアより前のロード/ストア操作は、このバリアより後のロード/ストア操作よりも先に完了することが保証されます。これはフルメモリバリアとして機能します。

### `LDREX`と`STREX`命令

ARMv6以降のARMアーキテクチャでは、アトミック操作を実装するために`LDREX` (Load Exclusive) と`STREX` (Store Exclusive) 命令のペアが提供されています。これらは「ロード・ロック/ストア・コンディショナル」というメカニズムを実装します。

*   **`LDREX`**: 指定されたメモリアドレスから値をロードし、そのアドレスを現在のプロセッサに対して「排他的」としてマークします。
*   **`STREX`**: `LDREX`で排他的にマークされたアドレスに値をストアしようとします。ストアが成功するのは、`LDREX`以降、他のプロセッサがそのメモリアドレスに書き込みを行っていない場合のみです。もし他のプロセッサが書き込みを行っていた場合、ストアは失敗し、`STREX`は失敗を示す値を返します。

この`LDREX`/`STREX`のペアは、ループ内で使用されることで、競合状態なしにメモリ位置をアトミックに更新するCAS操作などを効率的に実装できます。しかし、これらの命令自体はメモリ操作の順序付けを完全に保証するものではなく、弱いメモリモデルのアーキテクチャでは、`DMB`のような明示的なメモリバリアと組み合わせて使用されることが一般的です。

## 技術的詳細

このコミットは、Goランタイムと`sync/atomic`パッケージ内のARMアセンブリコードに、`DMB`命令を条件付きで挿入します。条件とは、`runtime·goarm`変数の値が7以上、つまりARMv7以上のプロセッサである場合です。これは、ARMv6以前のプロセッサでは`DMB`命令のサポートが異なるか、あるいはその必要性が低いと判断されたためと考えられます。

具体的には、`src/runtime/asm_arm.s`と`src/sync/atomic/asm_arm.s`のファイルが変更されています。これらのファイルには、Goのアトミック操作（CAS, Add, Swap, Load, Storeなど）を実装するためのアセンブリルーチンが含まれています。

変更の核心は、`LDREX`と`STREX`命令の間に`dmb ishst`を、そして`STREX`命令の後に`dmb ish`を挿入することです。

*   **`dmb ishst` (Data Memory Barrier, Inner Shareable, Store)**: `LDREX`と`STREX`の間、特に`STREX`の直前に挿入されます。これは、`STREX`が実際にメモリに書き込む前に、その前のストア操作が完了していることを保証するために使用されます。CAS操作において、新しい値を書き込む前に、その前の操作（例えば、比較対象のロード）が適切に完了していることを保証するのに役立ちます。
*   **`dmb ish` (Data Memory Barrier, Inner Shareable)**: `STREX`が成功した後に挿入されます。これは、アトミック操作が完了し、その結果が他のプロセッサからすぐに可視になることを保証するためのフルメモリバリアです。これにより、アトミック操作の「効果」がシステム全体に伝播し、後続のメモリ操作がこのアトミック操作の結果を正しく観測できるようになります。

これらのメモリバリアの追加は、ARMの弱いメモリモデルにおいて、Goのメモリモデルが要求する厳密な順序付けと可視性の保証を満たすために不可欠です。特に、`sync/atomic`パッケージは、Goのメモリモデルにおいて最も強い保証（逐次一貫性）を提供するように設計されており、その実装にはこのような低レベルのハードウェア同期プリミティブが不可欠となります。

## コアとなるコードの解説

各アトミック操作ルーチンにおいて、`LDREX`または`LDREXD`命令と`STREX`または`STREXD`命令の間に、以下のパターンでメモリバリアが挿入されています。

1.  **`LDREX` / `LDREXD` の後、`STREX` / `STREXD` の前**:
    ```assembly
    	MOVB	runtime·goarm(SB), R11
    	CMP	$7, R11
    	BLT	2(PC)
    	WORD	$0xf57ff05a	// dmb ishst
    ```
    または、`sync/atomic`ではマクロとして定義された`DMB_ISHST_7`が使用されます。
    これは、`LDREX`で値を読み込んだ後、`STREX`で書き込む前に、それ以前のストア操作が完了していることを保証するためのストアバリアです。これにより、アトミック操作の「読み込み」部分と「書き込み」部分の間の順序が正しく保たれます。特に、CAS操作で古い値を比較し、新しい値を書き込む際に、比較対象の古い値が最新であることを保証するのに役立ちます。

2.  **`STREX` / `STREXD` の後**:
    ```assembly
    	MOVB	runtime·goarm(SB), R11
    	CMP	$7, R11
    	BLT	2(PC)
    	WORD	$0xf57ff05b	// dmb ish
    ```
    または、`sync/atomic`ではマクロとして定義された`DMB_ISH_7`が使用されます。
    これは、`STREX`が成功してメモリへの書き込みが完了した後、その結果が他のプロセッサからすぐに可視になることを保証するためのフルメモリバリアです。このバリアにより、アトミック操作によって変更された値が、その後のすべてのメモリ操作に対して正しく観測されるようになります。

`MOVB runtime·goarm(SB), R11`、`CMP $7, R11`、`BLT 2(PC)` の部分は、`runtime·goarm`変数の値（Goが実行されているARMプロセッサのバージョンを示す）が7未満（つまりARMv6以前）の場合には、続く`DMB`命令をスキップするための条件分岐です。`WORD $0xf57ff05a`と`WORD $0xf57ff05b`は、それぞれ`dmb ishst`と`dmb ish`命令の機械語表現です。

これらの変更により、ARMv7以上のプロセッサを搭載したデバイス（例: Apple iPad Mini 3）上で、Goの`sync/atomic`操作がGoメモリモデルの保証に従って正しく動作するようになり、並行処理テストの失敗やタイムアウトが解消されました。

# [インデックス 20755] ファイルの概要

このコミットは、Go言語の `net/http` パッケージにおける潜在的なセキュリティリスクを修正するものです。具体的には、HTTPリクエストの `Referer` ヘッダーに認証情報（ユーザー名やパスワード）が意図せず含まれてしまう情報漏洩の脆弱性に対処しています。この修正により、`Referer` ヘッダーから認証情報が削除され、またHTTPSからHTTPへのリダイレクト時に `Referer` ヘッダーが送信されないようにすることで、セキュリティが強化されています。

## 変更の背景

このコミットは、Go言語の `net/http` パッケージにおける `Referer` ヘッダーの取り扱いに関するセキュリティ上の脆弱性（Issue #8417）を修正するために導入されました。

問題の根源は、`http.Client` がリダイレクト処理などで `Referer` ヘッダーを設定する際に、以前のリクエストのURLを `URL.String()` メソッドで文字列化してそのまま使用していた点にありました。もし元のURLに認証情報（例: `http://user:pass@example.com/path` のような形式）が含まれていた場合、その認証情報が `Referer` ヘッダーとして次のリクエストにそのまま含まれてしまい、意図しない情報漏洩が発生する可能性がありました。

特に、認証情報を含むURLから別のサイトへリダイレクトされる場合や、HTTPSサイトからHTTPサイトへリダイレクトされる場合に、この情報漏洩は深刻なセキュリティリスクとなります。認証情報が漏洩すると、セッションハイジャックや資格情報の盗用など、様々な攻撃に悪用される恐れがあります。

このコミットは、このような情報漏洩を防ぐために、`Referer` ヘッダーに認証情報を含めないようにし、さらにHTTPSからHTTPへのリダイレクト時には `Referer` ヘッダーを送信しないという、Webセキュリティのベストプラクティスに準拠した修正を施しています。

## 前提知識の解説

### Refererヘッダー

`Referer` ヘッダーは、HTTPリクエストヘッダーの一つで、現在のリクエストがどこから来たのか（参照元URL）を示すために使用されます。例えば、ウェブページ上のリンクをクリックして別のページに移動した場合、新しいページへのリクエストには、リンク元ページのURLが `Referer` ヘッダーとして含まれます。

用途としては、以下のようなものがあります。
*   **アクセス解析**: どのページからユーザーが来たのかを分析する。
*   **セキュリティ**: CSRF（Cross-Site Request Forgery）攻撃の防御策の一つとして、リクエストの参照元を検証する。
*   **コンテンツの最適化**: 参照元に基づいてコンテンツを調整する。

しかし、`Referer` ヘッダーにはプライバシーやセキュリティ上の懸念も存在します。特に、URLに機密情報（認証情報、セッショントークンなど）が含まれている場合、それが意図せず第三者に漏洩するリスクがあります。

### URLの認証情報

HTTP/HTTPSのURLには、ユーザー名とパスワードを埋め込むための構文が存在します。形式は `scheme://user:password@host:port/path?query#fragment` のようになります。
例: `http://admin:secret@example.com/dashboard`

この形式は、主にHTTPのBasic認証などで使用されることがありますが、現代のウェブアプリケーションでは、セキュリティ上の理由からURLに直接認証情報を埋め込むことは推奨されません。なぜなら、URLはブラウザの履歴、サーバーのログ、プロキシサーバー、そして今回の `Referer` ヘッダーなど、様々な場所に記録・送信される可能性があり、情報漏洩のリスクが高まるためです。

### セキュリティリスク

`Referer` ヘッダーを介した認証情報の漏洩は、以下のような深刻なセキュリティリスクを引き起こします。
*   **資格情報の盗用**: 攻撃者が `Referer` ヘッダーを傍受することで、ユーザー名とパスワードを直接取得し、不正ログインを行う可能性があります。
*   **セッションハイジャック**: URLにセッショントークンが含まれている場合、それが漏洩することで攻撃者がユーザーのセッションを乗っ取り、ユーザーとして振る舞うことが可能になります。
*   **プライバシー侵害**: ユーザーの閲覧履歴や個人を特定できる情報が、意図しない第三者に渡る可能性があります。

### RFC 7231 Section 5.5.2

このコミットのコードコメントで参照されている `RFC 7231, Section 5.5.2` は、HTTP/1.1のセマンティクスとコンテンツに関する仕様の一部です。このセクションは `Referer` ヘッダーの取り扱いについて記述しており、特にセキュリティに関する重要なガイドラインを含んでいます。

関連する記述は以下の通りです。
> "Clients SHOULD NOT include a Referer header field in a (non-secure) HTTP request if the referring page was transferred with a secure protocol."
> （クライアントは、参照元のページがセキュアなプロトコルで転送された場合、(非セキュアな) HTTP リクエストに Referer ヘッダーフィールドを含めるべきではない。）

これは、HTTPSページからHTTPページへのリダイレクトやリンク遷移の際に、`Referer` ヘッダーを送信してはならないというセキュリティ上の推奨事項です。HTTPSは通信内容を暗号化しますが、HTTPは暗号化しません。HTTPSページからHTTPページへ `Referer` ヘッダーを送信すると、HTTPSで保護されていたはずの参照元URLが、暗号化されていないHTTP通信で平文で送信されてしまい、中間者攻撃などによって傍受されるリスクがあるためです。このコミットは、このRFCの推奨事項に厳密に従っています。

## 技術的詳細

このコミットの主要な変更点は、`net/http` パッケージに `refererForURL` という新しい内部関数を導入し、既存のリダイレクト処理 (`doFollowingRedirects`) でこの関数を使用するように変更したことです。

### `refererForURL` 関数の導入

`refererForURL` 関数は、以下の2つの主要なセキュリティ対策を実装しています。

1.  **HTTPSからHTTPへのReferer送信の抑制**:
    *   関数は `lastReq` (前のリクエストのURL) と `newReq` (新しいリクエストのURL) を引数として受け取ります。
    *   `if lastReq.Scheme == "https" && newReq.Scheme == "http"` の条件で、前のリクエストがHTTPSであり、新しいリクエストがHTTPであるかをチェックします。
    *   この条件が真の場合、RFC 7231の推奨に従い、空文字列 `""` を返します。これにより、HTTPSからHTTPへの遷移時に `Referer` ヘッダーが送信されなくなります。

2.  **URLからの認証情報の削除**:
    *   `lastReq.User != nil` をチェックし、前のリクエストのURLにユーザー情報（認証情報）が含まれているかを確認します。
    *   もしユーザー情報が含まれている場合、`lastReq.User.String() + "@"` の形式で認証部分（例: `user:pass@`）を構築します。
    *   `strings.Replace(referer, auth, "", 1)` を使用して、元のURL文字列からこの認証部分を1回だけ削除します。
    *   コメントには「This is not very efficient」とありますが、これは `strings.Replace` が文字列操作であり、URL構造を直接操作するよりも効率が悪いことを示しています。しかし、APIの変更を避け、競合状態を発生させず、将来のメンテナンス問題を避けるためのトレードオフとして、このアプローチが選択されています。

この関数は、`net/url.URL` 型の `String()` メソッドが認証情報を含む文字列を返すという既存の動作を利用しつつ、その結果から認証情報を安全に除去する役割を担っています。

### `doFollowingRedirects` の変更

`Client` 型の `doFollowingRedirects` メソッドは、HTTPリダイレクトを処理する際に `Referer` ヘッダーを設定するロジックを含んでいます。

変更前は以下のようになっていました。
```go
if len(via) > 0 {
    // Add the Referer header.
    lastReq := via[len(via)-1]
    if lastReq.URL.Scheme != "https" { // HTTPS以外のスキームの場合のみRefererを設定
        nreq.Header.Set("Referer", lastReq.URL.String())
    }
}
```
このコードでは、`lastReq.URL.Scheme != "https"` という条件で、前のリクエストがHTTPSでない場合にのみ `Referer` ヘッダーを設定していました。しかし、これではHTTPSからHTTPSへのリダイレクト時に認証情報が漏洩する可能性が残っていました。また、HTTPSからHTTPへの遷移時のRFCの推奨事項も完全にカバーしていませんでした。

変更後は以下のようになりました。
```go
if len(via) > 0 {
    // Add the Referer header.
    lastReq := via[len(via)-1]
    if ref := refererForURL(lastReq.URL, nreq.URL); ref != "" { // 新しいrefererForURL関数を使用
        nreq.Header.Set("Referer", ref)
    }
}
```
新しいコードでは、`refererForURL` 関数を呼び出し、その戻り値 `ref` が空文字列でない場合にのみ `Referer` ヘッダーを設定するように変更されています。これにより、`refererForURL` 関数が提供する認証情報の削除とHTTPSからHTTPへのReferer抑制のロジックが、リダイレクト処理に組み込まれました。

### テストの追加

`src/net/http/client_test.go` に `TestReferer` という新しいテスト関数が追加されました。このテストは、`refererForURL` 関数の様々なシナリオにおける挙動を検証します。

テストケースには以下のようなものが含まれます。
*   ユーザー名のみ、またはユーザー名とパスワードを含むURLからのReferer生成（認証情報が削除されることを確認）。
*   認証情報を含まない通常のURLからのReferer生成。
*   HTTPSからHTTPへの遷移時にRefererが空文字列になることの確認。

テストのために、`src/net/http/export_test.go` に `ExportRefererForURL` というエクスポートされた関数が追加されています。これは、内部関数である `refererForURL` をテストコードから呼び出すためのメカニズムです。Go言語では、テスト対象のパッケージと同じパッケージにテストファイルを置くことで内部関数をテストできますが、`_test.go` ファイルから直接アクセスできない場合に、このように `export_test.go` を用いてテスト用のエクスポートを行うことがあります。

## コアとなるコードの解説

このコミットの核心は、`src/net/http/client.go` に追加された `refererForURL` 関数と、それが `doFollowingRedirects` メソッドに統合された点にあります。

### `refererForURL` 関数

```go
// refererForURL returns a referer without any authentication info or
// an empty string if lastReq scheme is https and newReq scheme is http.
func refererForURL(lastReq, newReq *url.URL) string {
	// https://tools.ietf.org/html/rfc7231#section-5.5.2
	//   "Clients SHOULD NOT include a Referer header field in a
	//    (non-secure) HTTP request if the referring page was
	//    transferred with a secure protocol."
	if lastReq.Scheme == "https" && newReq.Scheme == "http" {
		return ""
	}
	referer := lastReq.String()
	if lastReq.User != nil {
		// This is not very efficient, but is the best we can
		// do without:
		// - introducing a new method on URL
		// - creating a race condition
		// - copying the URL struct manually, which would cause
		//   maintenance problems down the line
		auth := lastReq.User.String() + "@"
		referer = strings.Replace(referer, auth, "", 1)
	}
	return referer
}
```
この関数は、`Referer` ヘッダーとして使用するURL文字列を生成する責任を負います。
1.  **RFC 7231準拠のチェック**: まず、前のリクエスト (`lastReq`) がHTTPSであり、新しいリクエスト (`newReq`) がHTTPである場合、セキュリティ上の理由から `Referer` ヘッダーを送信すべきではないため、即座に空文字列を返します。これにより、HTTPSで保護された情報が非セキュアなHTTP通信で漏洩するのを防ぎます。
2.  **認証情報の除去**: 次に、`lastReq.String()` で元のURL文字列を取得します。もし `lastReq.User` が `nil` でなければ（つまり、URLにユーザー名やパスワードが含まれている場合）、`lastReq.User.String() + "@"` の形式で認証部分（例: `user:pass@`）を生成し、`strings.Replace` を使って元のURL文字列からその部分を削除します。この処理は、URLの構造を直接解析して変更するのではなく、文字列置換で行われるため、コメントにあるように効率的ではない可能性がありますが、APIの変更や複雑な状態管理を避けるための選択です。

### `doFollowingRedirects` メソッドへの統合

`doFollowingRedirects` メソッドは、HTTPクライアントがリダイレクトを処理する際の中心的なロジックです。このメソッド内で、以前のリクエストのURLから新しいリクエストの `Referer` ヘッダーを構築する部分が変更されました。

変更前は、単に `lastReq.URL.String()` を使用し、HTTPSスキームでない場合にのみ `Referer` を設定していました。しかし、この方法では認証情報の漏洩やHTTPSからHTTPSへのリダイレクト時の問題が残っていました。

変更後は、`refererForURL` 関数を呼び出すことで、これらのセキュリティ上の懸念が解消されました。
```go
// ...
if ref := refererForURL(lastReq.URL, nreq.URL); ref != "" {
    nreq.Header.Set("Referer", ref)
}
// ...
```
この変更により、`Referer` ヘッダーは `refererForURL` によって安全に生成された文字列のみが設定されるようになり、空文字列が返された場合はヘッダー自体が設定されなくなります。これにより、Goの `net/http` クライアントは、`Referer` ヘッダーに関するセキュリティベストプラクティスに準拠するようになりました。

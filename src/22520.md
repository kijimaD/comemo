# [インデックス 22520] ファイルの概要

このコミットは、Goランタイムにおける`atomicand8`関数の実装に関するものです。具体的には、これまでミューテックスベースで実装されていた`atomicand8`関数を、各アーキテクチャ（386, amd64, ppc64x, arm, arm64）のハードウェアレベルのアトミック操作を利用するように変更しています。これにより、真にアトミックなバイト単位のAND演算が保証され、並行処理における予期せぬ競合状態を防ぎます。

影響を受けるファイルは以下の通りです。

*   `src/runtime/asm_386.s`: 32-bit x86アーキテクチャ向けのアセンブリコード。`atomicand8`の新しい実装が追加されています。
*   `src/runtime/asm_amd64.s`: 64-bit x86 (AMD64) アーキテクチャ向けのアセンブリコード。`atomicand8`の新しい実装が追加されています。
*   `src/runtime/asm_ppc64x.s`: PowerPC 64-bitアーキテクチャ向けのアセンブリコード。`atomicand8`の新しい実装が追加されています。
*   `src/runtime/atomic_386.go`: 32-bit x86アーキテクチャ向けのアトミック操作のGoインターフェース。`atomicand8`の宣言が追加されています。
*   `src/runtime/atomic_amd64x.go`: 64-bit x86 (AMD64) アーキテクチャ向けのアトミック操作のGoインターフェース。`atomicand8`の宣言が追加されています。
*   `src/runtime/atomic_arm.go`: ARMアーキテクチャ向けのアトミック操作のGo実装。`atomicand8`のGo言語での実装が追加されています。
*   `src/runtime/atomic_arm64.go`: ARM64アーキテクチャ向けのアトミック操作のGo実装。`atomicand8`のGo言語での実装が追加されています。
*   `src/runtime/atomic_ppc64x.go`: PowerPC 64-bitアーキテクチャ向けのアトミック操作のGoインターフェース。`atomicand8`の宣言が追加されています。
*   `src/runtime/mgc.go`: Goのガベージコレクタ関連のコード。以前のミューテックスベースの`atomicand8`実装が削除されています。

## 変更の背景

このコミットの背景には、Goランタイムにおける`atomicand8`関数の既存の実装が、真にアトミックではなかったという問題があります。コミットメッセージにある「We're skating on thin ice, and things are finally starting to melt around here. (I want to avoid the debugging session that will happen when someone uses atomicand8 expecting it to be atomic with respect to other operations.)」という記述は、この問題の深刻さを物語っています。

以前の`atomicand8`関数は、`mgc.go`ファイル内でミューテックス（`andlock`）を使用して実装されていました。ミューテックスは、複数のゴルーチンが同時に共有データにアクセスするのを防ぐための排他制御メカニズムであり、これによりデータの一貫性は保たれます。しかし、ミューテックスによるロックはソフトウェアレベルでのアトミック性を提供しますが、ハードウェアレベルでのアトミック操作とは異なります。

ハードウェアレベルのアトミック操作は、CPUが単一の不可分な命令として実行することを保証します。これにより、他のCPUコアやハードウェアからの割り込みによって操作が中断されることなく、メモリの読み書きや変更が完了します。ミューテックスを使用した場合、ロックの取得と解放の間にコンテキストスイッチが発生する可能性があり、その結果、他の操作との間で真のアトミック性が保証されない場合があります。特に、ガベージコレクタのような低レベルのランタイムコードでは、厳密なアトミック性が求められる場面があります。

このコミットは、`atomicand8`が他の操作に対してアトミックであることを期待する開発者が直面するであろうデバッグセッションを回避するために、この関数を真にアトミックなハードウェア操作で実装し直すことを目的としています。これにより、Goランタイムの堅牢性と信頼性が向上します。

## 前提知識の解説

### アトミック操作 (Atomic Operations)

アトミック操作とは、複数のスレッドやプロセスが共有データにアクセスする際に、その操作全体が中断されることなく、単一の不可分な単位として実行されることを保証する操作です。これにより、競合状態（Race Condition）を防ぎ、データの一貫性と正確性を保つことができます。

アトミック操作には主に2つのレベルがあります。

1.  **ソフトウェアレベルのアトミック性**: ミューテックス（Mutex）やセマフォ（Semaphore）などの同期プリミティブを使用して、共有データへのアクセスを排他的に制御することで実現されます。これにより、一度に一つのスレッドのみがクリティカルセクションに入ることができ、データ破損を防ぎます。しかし、ロックの取得と解放にはオーバーヘッドがあり、また、ロックの粒度によってはデッドロックやパフォーマンスの問題を引き起こす可能性があります。
2.  **ハードウェアレベルのアトミック性**: CPUが提供する特殊な命令セットを利用して実現されます。これらの命令は、メモリの読み書きや変更を単一の不可分なステップとして実行することを保証します。例えば、x86アーキテクチャの`LOCK`プレフィックス、ARMやPowerPCのLoad-Link/Store-Conditional (LL/SC) 命令などがあります。これらは通常、ソフトウェアレベルの同期よりも高速で、より低レベルでの制御を可能にします。

Goランタイムのような並行性の高いシステムでは、パフォーマンスと正確性の両方を確保するために、ハードウェアレベルのアトミック操作が頻繁に利用されます。

### Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理する低レベルのシステムです。これには、ゴルーチン（Goroutine）のスケジューリング、メモリ管理（ガベージコレクションを含む）、チャネル（Channel）の実装、システムコールインターフェースなどが含まれます。Goランタイムは、Go言語の並行処理モデルを支える基盤であり、その内部では非常に多くの並行処理が行われています。そのため、ランタイムの内部状態を安全かつ効率的に操作するために、アトミック操作が不可欠です。

### アセンブリ言語 (Assembly Language)

アセンブリ言語は、特定のCPUアーキテクチャの機械語命令と一対一に対応する低レベルのプログラミング言語です。Goランタイムの多くの部分はGo言語で書かれていますが、パフォーマンスが非常に重要であったり、ハードウェアの特定の機能（今回のようなアトミック操作など）に直接アクセスする必要がある場合、アセンブリ言語が使用されます。

このコミットでは、以下のアーキテクチャのアセンブリ言語が関わっています。

*   **x86 (386/AMD64)**: IntelおよびAMDプロセッサで広く使用されているアーキテクチャ。`LOCK`プレフィックスは、次の命令がアトミックに実行されることを保証します。
*   **PowerPC (PPC64)**: IBMが開発したRISCアーキテクチャ。Load-Link (`LWAR`) と Store-Conditional (`STWCCC`) 命令のペアを使用してアトミック操作を実現します。これは、メモリ位置を読み込み（Load-Link）、その後に条件付きで書き込み（Store-Conditional）を試み、その間に他のプロセッサが同じメモリ位置を変更していないことを確認するメカニズムです。
*   **ARM/ARM64**: モバイルデバイスや組み込みシステムで広く使用されているRISCアーキテクチャ。PowerPCと同様に、Load-Link/Store-Conditional（またはそれに類する排他的ロード/ストア命令）の概念を使用してアトミック操作を実現します。

### Goコンパイラディレクティブ (`go:noescape`, `go:nosplit`)

Goコンパイラには、特定の関数の挙動を制御するための特別なコメント形式のディレクティブがあります。

*   **`//go:noescape`**: このディレクティブは、関数がヒープにポインタをエスケープしないことをコンパイラに伝えます。これにより、コンパイラはスタック割り当てを最適化し、ガベージコレクタの負担を軽減できます。アトミック操作のような低レベルの関数では、通常、メモリ割り当てを行わないため、このディレクティブが適用されます。
*   **`//go:nosplit`**: このディレクティブは、関数がスタックを拡張しないことをコンパイラに伝えます。Goランタイムは、ゴルーチンのスタックが不足した場合に自動的にスタックを拡張（スプリット）しますが、非常に低レベルで時間制約のある操作（例えば、スケジューラやガベージコレクタの内部）では、スタックのスプリットを避ける必要があります。`atomicand8`のような関数は、ランタイムのクリティカルパスで呼び出される可能性があるため、`//go:nosplit`が適用されることがあります。

## 技術的詳細

このコミットの主要な目的は、`atomicand8`関数を、各アーキテクチャのネイティブなアトミック命令を使用して実装し、真のハードウェアレベルのアトミック性を保証することです。

### 以前の実装 (`src/runtime/mgc.go` からの削除)

以前の`atomicand8`は、`mgc.go`ファイル内で以下のように実装されていました。

```go
var andlock mutex

//go:nowritebarrier
func atomicand8(src *byte, val byte) {
	lock(&andlock)
	*src &= val
	unlock(&andlock)
}
```

この実装は、`andlock`というグローバルミューテックスを使用して、バイトへのAND演算を保護していました。これはソフトウェアレベルでの排他制御を提供しますが、以下の問題がありました。

*   **真のアトミック性ではない**: ミューテックスのロックとアンロックの間で、他のゴルーチンが実行される可能性があります。これにより、`atomicand8`が他の操作に対して「不可分」であるという保証が完全ではありませんでした。
*   **パフォーマンスオーバーヘッド**: ミューテックスの取得と解放には、コンテキストスイッチやキャッシュの無効化などのオーバーヘッドが伴います。低レベルのランタイム関数では、このオーバーヘッドが問題となる場合があります。
*   **デバッグの困難さ**: コミットメッセージにあるように、ミューテックスベースの実装が期待されるアトミック性を提供しない場合、デバッグが非常に困難になる可能性があります。

このコミットでは、このミューテックスベースの実装が完全に削除されています。

### 新しい実装 (アーキテクチャ別)

#### x86 (386, amd64)

x86アーキテクチャでは、`LOCK`プレフィックスを命令の前に付けることで、その命令がアトミックに実行されることを保証できます。

*   `src/runtime/asm_386.s` および `src/runtime/asm_amd64.s` に追加されたコード:

    ```assembly
    // void	runtime·atomicand8(byte volatile*, byte);
    TEXT runtime·atomicand8(SB), NOSPLIT, $0-5
    	MOVL	ptr+0(FP), AX  // 386: ptrをAXレジスタにロード
    	MOVB	val+4(FP), BX  // 386: valをBXレジスタにロード
    	LOCK                 // 次の命令をアトミックにする
    	ANDB	BX, (AX)     // メモリ位置(AX)のバイトとBXのバイトをAND演算し、結果をメモリに書き込む
    	RET
    ```
    AMD64では、レジスタが`MOVQ`と`val+8(FP)`に変わるだけで、基本的なロジックは同じです。
    `LOCK`プレフィックスは、CPUがその命令の実行中にバスをロックし、他のプロセッサやDMAコントローラがメモリにアクセスするのを防ぐことで、アトミック性を保証します。

#### PowerPC 64-bit (ppc64x)

PowerPCアーキテクチャでは、Load-Link (LL) と Store-Conditional (SC) 命令のペアを使用してアトミック操作を実現します。これは、操作が成功したかどうかをチェックし、競合が発生した場合はリトライするループを構築します。

*   `src/runtime/asm_ppc64x.s` に追加されたコード:

    ```assembly
    // void	runtime·atomicand8(byte volatile*, byte);
    TEXT runtime·atomicand8(SB), NOSPLIT, $0-9
    	MOVD	ptr+0(FP), R3      // ptrをR3にロード
    	MOVBZ	val+8(FP), R4      // valをR4にゼロ拡張してロード
    	// Align ptr down to 4 bytes so we can use 32-bit load/store.
    	// R5 = (R3 << 0) & ~3
    	RLDCR	$0, R3, $~3, R5    // ptrを4バイト境界にアライン（R5に格納）
    	// Compute val shift.
    #ifdef GOARCH_ppc64
    	// Big endian.  ptr = ptr ^ 3
    	XOR	$3, R3             // ビッグエンディアンの場合、バイトオフセットを調整
    #endif
    	// R6 = ((ptr & 3) * 8) = (ptr << 3) & (3*8)
    	RLDC	$3, R3, $(3*8), R6 // バイトオフセットに応じたシフト量を計算 (R6に格納)
    	// Shift val for aligned ptr.  R4 = val << R6 | ^(0xFF << R6)
    	MOVD	$0xFF, R7          // 0xFFをR7にロード
    	SLD	R6, R4             // valをシフト量R6だけ左シフト
    	SLD	R6, R7             // 0xFFをシフト量R6だけ左シフト
    	XOR $-1, R7            // R7をビット反転 (マスクの準備)
    	OR	R7, R4             // valとマスクをOR (AND演算のための準備)
    again:
    	SYNC                   // メモリバリア
    	LWAR	(R5), R6           // アラインされたアドレスR5からワードをロードリンク (R6に格納)
    	AND	R4, R6             // ロードしたワードR6と準備したR4をAND演算
    	STWCCC	R6, (R5)           // 結果R6をアラインされたアドレスR5にストアコンディショナル
    	BNE	again              // ストアが失敗したらリトライ
    	SYNC                   // メモリバリア
    	ISYNC                  // 命令同期バリア
    	RETURN
    ```
    このコードは、バイト単位のAND操作を32ビットワードに対するLL/SC操作で実現しています。バイトアドレスを4バイト境界にアラインし、バイトオフセットに応じて値とマスクをシフトすることで、目的のバイトのみを操作するようにしています。

#### ARM/ARM64

ARMアーキテクチャでも、PowerPCと同様にCompare-And-Swap (CAS) ループを使用してアトミック操作を実現します。Go言語で実装されていますが、内部的にはアトミックなCASプリミティブ（`cas`関数）を利用しています。

*   `src/runtime/atomic_arm.go` および `src/runtime/atomic_arm64.go` に追加されたコード:

    ```go
    //go:nosplit
    func atomicand8(addr *uint8, v uint8) {
    	// Align down to 4 bytes and use 32-bit CAS.
    	uaddr := uintptr(unsafe.Pointer(addr))
    	addr32 := (*uint32)(unsafe.Pointer(uaddr &^ 3)) // アドレスを4バイト境界にアライン
    	mask := uint32(0xFF) << ((uaddr & 3) * 8)      // バイトオフセットに応じたマスクを生成
    	word := uint32(v) << ((uaddr & 3) * 8)         // バイトオフセットに応じた値をシフト
    	word |= ^mask                                  // AND演算のための最終的なワードを準備
    	for {
    		old := *addr32                             // 現在のワードを読み込む
    		if cas(addr32, old, old&word) {            // CAS操作: oldが現在の値と一致すれば、old&wordを書き込む
    			return                                 // 成功したら終了
    		}
    	}
    }
    ```
    ARM64のコードもほぼ同じですが、コメントに`// TODO(dfc) implement this in asm.`とあり、将来的にはアセンブリで最適化される可能性があることを示唆しています。
    この実装は、バイト単位の操作を32ビットワードに対するCAS操作に変換しています。目的のバイトがワード内のどこにあるかに応じて、適切なマスクとシフトを適用することで、そのバイトのみが変更されるようにしています。

### `NOTE: Do not add atomicxor8 (XOR is not idempotent).`

`atomic_386.go`, `atomic_amd64x.go`, `atomic_ppc64x.go` の各ファイルには、`atomicand8`と`atomicor8`の宣言の後に、`// NOTE: Do not add atomicxor8 (XOR is not idempotent).`というコメントが追加されています。

これは非常に重要な注意点です。
*   **AND (`&`) と OR (`|`) は冪等ではない**: ANDとORは、複数回同じ値を適用しても結果が変わらないという意味では冪等ではありません。しかし、アトミック操作の文脈では、これらの操作は「特定のビットをセットする/クリアする」という目的で使われることが多く、その意味では「結果が予測可能」です。
*   **XOR (`^`) は冪等ではない**: XORは、同じ値を2回適用すると元の値に戻るという特性があります（A ^ B ^ B = A）。この特性は、アトミック操作として使用する際に問題を引き起こす可能性があります。例えば、あるビットをトグルしたい場合、XORは便利ですが、複数のゴルーチンが同時にXOR操作を行うと、最終的な状態が予測不能になる可能性があります。アトミックなXOR操作は、通常、特定のビットを「トグル」するために使用されますが、その性質上、競合状態が発生した場合に期待通りの結果が得られない可能性が高いため、Goランタイムでは提供しないという判断がなされています。

この注意書きは、アトミック操作の設計における慎重な考慮と、特定の操作が並行環境でどのように振る舞うかについての深い理解を示しています。

## コアとなるコードの解説

### x86-64 (`src/runtime/asm_amd64.s`) の `atomicand8`

このアセンブリコードは、x86-64アーキテクチャにおける`atomicand8`関数の実装です。

1.  `MOVQ ptr+0(FP), AX`: 関数呼び出しの引数である`ptr`（バイトへのポインタ）を`AX`レジスタにロードします。`FP`はフレームポインタで、スタック上の引数にアクセスするために使用されます。
2.  `MOVB val+8(FP), BX`: もう一つの引数である`val`（AND演算するバイト値）を`BX`レジスタにロードします。
3.  `LOCK`: このプレフィックスは、次の命令（`ANDB`）がアトミックに実行されることを保証します。CPUは、この命令の実行中にメモリバスをロックし、他のプロセッサやDMAコントローラが対象のメモリ位置にアクセスするのを防ぎます。
4.  `ANDB BX, (AX)`: `AX`が指すメモリ位置にあるバイトと`BX`レジスタのバイト値に対してビット単位のAND演算を実行し、その結果を`AX`が指すメモリ位置に書き戻します。この操作全体が`LOCK`プレフィックスによってアトミックに実行されます。
5.  `RET`: 関数から戻ります。

この実装は、x86のハードウェアが提供する強力なアトミック命令を直接利用しており、非常に効率的です。

### PowerPC 64-bit (`src/runtime/asm_ppc64x.s`) の `atomicand8`

PowerPCのアセンブリコードは、x86とは異なり、Load-Link/Store-Conditional (LL/SC) のメカニズムを使用してアトミック性を実現します。これは、操作が成功するまでループでリトライするパターンです。

1.  `MOVD ptr+0(FP), R3` と `MOVBZ val+8(FP), R4`: ポインタ`ptr`を`R3`に、値`val`をゼロ拡張して`R4`にロードします。
2.  **アドレスのアラインメントとバイトオフセットの計算**:
    *   `RLDCR $0, R3, $~3, R5`: `ptr`を4バイト境界にアラインします。PowerPCのLL/SC命令はワード単位で動作するため、バイト単位の操作を行うには、対象のバイトを含むワードのアドレスを特定する必要があります。`R5`にはアラインされたワードのアドレスが格納されます。
    *   `#ifdef GOARCH_ppc64 ... XOR $3, R3`: ビッグエンディアンの場合、バイトオフセットを調整します。これは、ワード内のバイトの順序がエンディアンによって異なるためです。
    *   `RLDC $3, R3, $(3*8), R6`: `ptr`の最下位2ビット（`ptr & 3`）から、ワード内のバイトオフセット（0, 1, 2, 3）を計算し、それをビットシフト量（0, 8, 16, 24）に変換して`R6`に格納します。
3.  **AND演算のための値とマスクの準備**:
    *   `MOVD $0xFF, R7`: 8ビットのマスク`0xFF`を`R7`にロードします。
    *   `SLD R6, R4` と `SLD R6, R7`: `val`と`0xFF`マスクを、計算したシフト量`R6`だけ左シフトします。これにより、操作対象のバイトがワード内の正しい位置に配置されます。
    *   `XOR $-1, R7` と `OR R7, R4`: `R7`（シフトされた`0xFF`）をビット反転し、それを`R4`（シフトされた`val`）とOR演算します。この結果、`R4`には、対象バイト位置には`val`が、それ以外のバイト位置には`1`がセットされたワードが準備されます。これは、`old & word`というAND演算で、対象バイトのみを`val`でANDし、他のバイトは変更しないようにするための巧妙なテクニックです。
4.  **アトミックループ (`again`ラベル)**:
    *   `SYNC`: メモリバリア命令。これ以前のメモリ操作が完了し、これ以降のメモリ操作が開始される前に、メモリの一貫性を保証します。
    *   `LWAR (R5), R6`: `R5`が指すメモリ位置からワードをロードリンクします。この命令は、その後の`STWCCC`命令が成功するかどうかを追跡するための予約を確立します。
    *   `AND R4, R6`: ロードしたワード`R6`と、準備した`R4`をビット単位でAND演算します。
    *   `STWCCC R6, (R5)`: `R6`の値を`R5`が指すメモリ位置にストアコンディショナルします。この命令は、`LWAR`以降に他のプロセッサが同じメモリ位置を変更していない場合にのみ成功します。成功した場合、予約は解除されます。
    *   `BNE again`: `STWCCC`が失敗した場合（ゼロフラグがセットされない）、`again`ラベルに分岐して操作をリトライします。
    *   `SYNC` と `ISYNC`: 成功後もメモリバリアと命令同期バリアを挿入し、メモリの一貫性と命令の順序を保証します。
5.  `RETURN`: 関数から戻ります。

このLL/SCループは、競合が発生した場合に自動的にリトライすることで、アトミック性を保証します。

### ARM (`src/runtime/atomic_arm.go`) の `atomicand8`

ARMのGo言語実装は、PowerPCのアセンブリと同様に、バイト単位の操作をワード単位のCAS操作に変換するロジックを使用しています。

1.  `uaddr := uintptr(unsafe.Pointer(addr))`: `uint8`へのポインタを`uintptr`に変換します。
2.  `addr32 := (*uint32)(unsafe.Pointer(uaddr &^ 3))`: `uaddr`を4バイト境界にアラインし、そのアドレスを`uint32`へのポインタに変換します。これにより、ワード単位でのアクセスが可能になります。
3.  `mask := uint32(0xFF) << ((uaddr & 3) * 8)`: 対象のバイトがワード内のどこにあるかに応じて、そのバイト位置に対応する`0xFF`マスクを生成します。例えば、アドレスが`0x1001`の場合、オフセットは1なので、マスクは`0xFF00`となります。
4.  `word := uint32(v) << ((uaddr & 3) * 8)`: AND演算する値`v`を、対象のバイト位置にシフトします。
5.  `word |= ^mask`: ここが重要な部分です。`mask`をビット反転（`^mask`）すると、対象バイト位置のビットはすべて`0`になり、それ以外のビットはすべて`1`になります。この反転したマスクとシフトされた`v`をOR演算することで、`word`には、対象バイト位置には`v`が、それ以外のバイト位置には`1`がセットされた値が準備されます。
6.  **CASループ**:
    *   `old := *addr32`: 現在のワードの値を読み込みます。
    *   `if cas(addr32, old, old&word)`: `cas`関数（Compare-And-Swap）を呼び出します。これは、`addr32`が指すメモリ位置の値が`old`と等しい場合、その値を`old&word`にアトミックに更新します。
        *   `old&word`の計算では、`word`の対象バイト位置には`v`が、それ以外のバイト位置には`1`がセットされているため、`old`の対象バイトは`v`でANDされ、他のバイトは`old`の元の値が保持されます（`X & 1 = X`）。
    *   `return`: `cas`が成功した場合、ループを終了します。
    *   ループは、`cas`が成功するまで繰り返されます。これは、他のゴルーチンが同時に同じメモリ位置を変更した場合に、操作をリトライするためです。

このGo言語での実装は、アセンブリでのLL/SCループと同様のロジックを、Goの`cas`プリミティブとビット操作を組み合わせて実現しています。

### `src/runtime/mgc.go` からの削除

`mgc.go`からミューテックスベースの`atomicand8`が削除されたことは、このコミットの意図を明確に示しています。Goランタイムのクリティカルな部分で、より効率的で真にアトミックな操作が必要とされたため、古い実装は廃止されました。

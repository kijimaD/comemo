## 元コミット内容

このコミットは、Goランタイムのガベージコレクション（GC）サイクル中に、`gcMark`関数が呼び出された後に、呼び出し元の関数のスタックが移動している可能性があるという問題に対処しています。`gcMark`はスタックを縮小する可能性があり、これには`gc`関数自身のスタックも含まれることがあります。もしスタックが移動した場合、`gcMark`の後に`gc`関数内のローカル変数にアクセスしようとすると、その変数が古い（無効な）スタックアドレスを指しているため、ダングリングポインタエラーが発生する可能性があります。

コミットメッセージでは、「Dangling pointer error. Unlikely to trigger in practice, but still.」と述べられており、実際にこの問題が表面化することは稀であるものの、潜在的なバグとして修正の必要性が認識されていました。この問題は、`GODEBUG=efence=1 GOGC=1 trace.test`という特定のデバッグ設定でテストを実行した際に発見されました。

## 変更の背景

Goランタイムのガベージコレクタは、プログラムの実行中に不要になったメモリを自動的に解放する役割を担っています。GoのGCは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行してマークフェーズを実行します。このマークフェーズ中に、GCは到達可能なオブジェクトを特定し、マークします。

Goのゴルーチンは、可変サイズのスタックを使用します。これは、必要に応じてスタックを拡張したり、不要な場合には縮小したりできることを意味します。スタックの縮小は、メモリ使用量を最適化するために行われます。

`gc`関数はGCの主要なエントリポイントの一つであり、`systemstack`という特殊な関数を使ってシステムスタックに切り替えて`gcMark`を呼び出します。`systemstack`は、現在のゴルーチンのスタックではなく、ランタイムが管理する特別なスタック（システムスタック）上でコードを実行するためのメカニズムです。これは、GCのような低レベルの操作が、通常のゴルーチンのスタック管理に影響されずに実行できるようにするために重要です。

問題の背景には、`gcMark`が実行される際に、現在のゴルーチン（この場合は`gc`関数を実行しているゴルーチン）のスタックが縮小される可能性があるという事実があります。もし`gcMark`が`gc`関数のスタックを縮小し、その結果スタックが新しいメモリ位置に移動した場合、`gcMark`から戻った後に`gc`関数内のローカル変数にアクセスしようとすると、それらの変数が古いスタックアドレスを指したままになるため、ダングリングポインタが発生します。これはメモリ破壊や予期せぬ動作につながる可能性があります。

このコミットは、このような潜在的なメモリ安全性の問題を解決し、GCプロセスの堅牢性を向上させることを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に以下のフェーズで構成されます。

1.  **マークフェーズ (Mark Phase)**: プログラムが使用しているオブジェクト（到達可能なオブジェクト）を特定し、マークします。GoのGCは並行マークを採用しており、ほとんどのマーク作業はアプリケーションの実行と並行して行われます。
2.  **マーク終結フェーズ (Mark Termination Phase)**: 短いSTW (Stop The World) フェーズで、マークフェーズの最終処理を行います。
3.  **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（不要なオブジェクト）が占めていたメモリを解放し、再利用可能にします。これも並行して行われます。

### ゴルーチンのスタック管理

Goのゴルーチンは、非常に軽量なスレッドのようなものです。各ゴルーチンは独自のスタックを持っていますが、このスタックは固定サイズではなく、必要に応じて動的に拡張・縮小されます。スタックの拡張や縮小が発生すると、スタックの基底アドレスが変更される可能性があります。

### `systemstack`

`systemstack`はGoランタイムの内部関数で、現在のゴルーチンのスタックではなく、ランタイムが管理する特別な「システムスタック」上で指定された関数を実行するために使用されます。これは、GCやスケジューラのような低レベルのランタイム操作が、通常のゴルーチンのスタックの状態に依存せずに安全に実行されることを保証するために重要です。`systemstack`内で実行されるコードは、通常のゴルーチンのスタックが移動したり、GCによって操作されたりしても影響を受けません。

### ダングリングポインタ (Dangling Pointer)

ダングリングポインタとは、解放されたメモリ領域を指しているポインタのことです。そのメモリ領域が別の目的で再利用された場合、ダングリングポインタを介してアクセスすると、意図しないデータが読み書きされたり、プログラムがクラッシュしたりする可能性があります。このコミットのケースでは、スタックが移動した後に古いスタックアドレスを指し続けるローカル変数（ポインタ）がダングリングポインタとなります。

## 技術的詳細

この問題は、`gc`関数が`systemstack`を使って`gcMark`を呼び出すという特定のシーケンスで発生します。

1.  `gc`関数が実行を開始し、ローカル変数（例: `heap2`など、`gcMark`後に使用される変数）が現在のゴルーチンのスタック上に割り当てられます。
2.  `gc`関数は`systemstack(func() { gcMark(startTime) })`を呼び出します。これにより、`gcMark`はシステムスタック上で実行されます。
3.  `gcMark`の実行中、Goランタイムはメモリ使用量を最適化するために、現在のゴルーチン（`gc`関数を実行しているゴルーチン）のスタックを縮小する可能性があります。スタックが縮小されると、そのスタックのメモリ領域が移動し、新しいアドレスに再配置されます。
4.  `gcMark`が完了し、`systemstack`から元のゴルーチンのスタックに戻ります。
5.  この時点で、`gc`関数内のローカル変数（例: `heap2`）は、スタックが移動する前の古いアドレスを指したままになっています。
6.  もし`gcMark`の後にこれらのローカル変数にアクセスしようとすると、それらは無効なメモリ領域を指しているため、ダングリングポインタエラーが発生します。

このコミットの解決策は、`gcMark`の呼び出しを`systemstack`ブロックで囲み、その`systemstack`ブロックからすぐに戻るようにすることです。これにより、`gcMark`がスタックを縮小してスタックが移動した場合でも、`systemstack`ブロックから戻る際に、ランタイムが自動的に新しいスタックアドレスを認識し、`gc`関数内のローカル変数が正しく更新されたアドレスを指すようになります。

具体的には、`gcMark`の呼び出しを独立した`systemstack`ブロックに分離し、そのブロックの直後に別の`systemstack`ブロックを追加して残りの処理を行うことで、この問題を回避しています。最初の`systemstack`ブロックから戻ることで、ランタイムはスタックの移動を検出し、必要なポインタの更新を行います。その後の処理は、更新された正しいスタックアドレス上で実行されるため、ダングリングポインタの問題は発生しません。

```go

		heap2 = work.bytesMarked
		if debug.gccheckmark > 0 {
			// Run a full stop-the-world mark using checkmark bits,
			// ...
		}
	})
```

## コアとなるコードの解説

元のコードでは、`gcMark(startTime)`の呼び出しと、その後の`heap2 = work.bytesMarked`などの処理が、単一の`systemstack`ブロック内に含まれていました。

変更後のコードでは、`gcMark(startTime)`の呼び出しが独立した`systemstack`ブロックに分離されています。

```go
	systemstack(func() {
		gcMark(startTime)
		// Must return immediately.
		// The outer function's stack may have moved
		// during gcMark (it shrinks stacks, including the
		// outer function's stack), so we must not refer
		// to any of its variables. Return back to the
		// non-system stack to pick up the new addresses
		// before continuing.
	})
```

この変更の肝は、`gcMark`が実行された後、この`systemstack`ブロックから**すぐに戻る**という点です。コメントにも明記されているように、`gcMark`の実行中に`gc`関数自身のスタックが縮小・移動している可能性があるため、このブロック内では`gc`関数のローカル変数にアクセスしてはなりません。`systemstack`ブロックから戻ることで、Goランタイムは現在のゴルーチンのスタックが移動したことを検出し、`gc`関数内のローカル変数（ポインタ）が新しいスタックアドレスを指すように適切に更新します。

その後、残りの処理は新しい`systemstack`ブロック内で実行されます。

```go
	systemstack(func() {
		heap2 = work.bytesMarked
		if debug.gccheckmark > 0 {
			// Run a full stop-the-world mark using checkmark bits,
			// ...
		}
	})
```

この二段階の`systemstack`呼び出しにより、`gcMark`によるスタックの移動が発生しても、その後の処理が常に正しいスタックアドレスを参照することが保証されます。これにより、ダングリングポインタの問題が根本的に解決されます。

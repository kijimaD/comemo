# [インデックス 20579] ファイルの概要

このコミットは、GoランタイムにおけるARMアーキテクチャ、特に`GOARM`が7未満の古いARMv5/ARMv6環境でのビルドに関する重要なバグ修正を扱っています。具体的には、スレッドローカルストレージ (TLS) のアクセス方法と、Goリンカ (`liblink`) がTLSをサポートしないホスト環境向けに提供するフォールバックメカニズムに起因する無限ループの問題を解決します。

## 変更の背景

このコミットは、GoランタイムがARMアーキテクチャ上で動作する際に発生する特定のビルド問題、特に`GOARM`環境変数が7未満に設定されている（つまり、ARMv5またはARMv6のような古いARMプロセッサをターゲットとしている）場合に発生する問題を修正します。

問題の根源は、Goランタイムがゴルーチン (`g`) ポインタをスレッドローカルストレージ (TLS) を介して効率的にアクセスしようとする方法にありました。ARMアーキテクチャでは、TLSベースポインタを直接取得するために`MRC` (Move to Register from Coprocessor) 命令を使用することが一般的です。しかし、一部の古いARMシステムや特定のカーネル設定では、この`MRC`命令によるTLSアクセスがサポートされていない場合があります。

このような状況に対応するため、Goのリンカである`liblink`はフォールバックメカニズムを備えています。`liblink`は、ホスト環境が`MRC`命令によるTLSアクセスをサポートしていないと判断した場合、`MRC`命令を`BL runtime.tls_read_fallback`という命令に置き換えます。`runtime.tls_read_fallback`関数は、`__kuser_get_tls`というカーネル提供のヘルパー関数を呼び出すことで、ソフトウェア的にTLSポインタを取得しようとします。

このフォールバックメカニズム自体は正しいのですが、問題は`runtime`パッケージ内の`save_g`関数（および`load_g`関数）の内部で発生しました。`save_g`関数は、`MRC`命令が直接実行されることを前提として設計されており、`BL`命令による関数呼び出しが行われることを想定していませんでした。`BL`命令は、呼び出し元の次の命令のアドレスをリンクレジスタ (LR) に保存してから分岐します。`runtime.tls_read_fallback`が`BL`によって呼び出され、その処理が完了して`RET`（リターン）命令が実行されると、LRに保存されていたアドレス（つまり`save_g`関数内の`MRC`命令の次のアドレス）に戻ります。しかし、`save_g`関数自体が`RET`命令で終了する際、LRには`save_g`を呼び出した関数のアドレスではなく、`save_g`関数内のアドレスが残ってしまっていたため、`save_g`が無限ループに陥るというバグが発生していました。

このコミットは、この無限ループを解消し、`GOARM<7`環境でのGoプログラムのビルドと実行を可能にすることを目的としています。

## 前提知識の解説

このコミットの理解には、以下の技術的な前提知識が役立ちます。

1.  **ARMアーキテクチャの基本**:
    *   **レジスタ**: ARMプロセッサは汎用レジスタ（R0-R12）、スタックポインタ (SP, R13)、リンクレジスタ (LR, R14)、プログラムカウンタ (PC, R15) を持ちます。
    *   **リンクレジスタ (LR)**: 関数呼び出し (`BL`命令など) が行われる際に、呼び出し元に戻るアドレスが自動的にLRに保存されます。関数から戻る際には、LRに保存されたアドレスに分岐することで呼び出し元に戻ります。
    *   **プログラムカウンタ (PC)**: 現在実行中の命令のアドレスを指します。
    *   **`BL` (Branch with Link) 命令**: 指定されたアドレスに分岐し、同時に現在のPCの次の命令のアドレスをLRに保存します。これは関数呼び出しに使用されます。
    *   **`RET` (Return) 命令**: ARMアセンブリでは、通常`MOV PC, LR`や`BX LR`といった命令で実装され、LRに保存されたアドレスに分岐することで関数から戻ります。

2.  **スレッドローカルストレージ (TLS)**:
    *   各スレッドがそれぞれ独立したデータを持つためのメカニズムです。Goランタイムでは、現在のゴルーチン (`g`) ポインタをTLSに保存し、高速にアクセスするために利用します。
    *   ARM Linuxでは、TLSベースポインタは通常、`TPIDRURW` (Thread ID Register, User Read/Write) というシステムレジスタに格納されます。

3.  **`MRC` (Move to Register from Coprocessor) 命令**:
    *   コプロセッサから汎用レジスタにデータを転送するためのARM命令です。
    *   `MRC p15, 0, Rd, c13, c0, 3`という形式は、システムコプロセッサ (p15) から、TLSベースポインタを格納する`TPIDRURW`レジスタ (c13, c0, 3) の値を読み出し、汎用レジスタ`Rd`に格納するために使用されます。これはハードウェアによる高速なTLSアクセス方法です。

4.  **`__kuser_get_tls`**:
    *   ARM Linuxカーネルが提供するユーザー空間ヘルパー関数です。
    *   `0xffff0fe0`という固定アドレスに配置された「ベクターページ」と呼ばれる特殊なメモリ領域に存在します。
    *   `MRC`命令が利用できない、またはサポートされていない環境において、ソフトウェア的にTLSポインタを取得するためのフォールバックとして機能します。

5.  **Goのリンカ (`liblink`)**:
    *   Goのコンパイルプロセスの一部であり、オブジェクトファイルを結合して実行可能ファイルを生成します。
    *   `liblink`は、ターゲット環境の特性（例: `GOARM`の値）を考慮し、必要に応じてコードの変換や最適化を行います。今回のケースでは、`MRC`命令のサポート状況に応じてコードを書き換える役割を担っていました。

6.  **`GOARM`環境変数**:
    *   Goのビルドシステムで使用される環境変数で、ターゲットとするARMプロセッサのバージョンを指定します。
    *   `GOARM=7`はARMv7以降のプロセッサを指し、通常はハードウェアTLS (`MRC`命令) をサポートしています。
    *   `GOARM<7`（例: `GOARM=5`や`GOARM=6`）はARMv5やARMv6のような古いプロセッサを指し、これらの環境ではハードウェアTLSが利用できない場合があります。

## 技術的詳細

このバグは、GoランタイムがARMアーキテクチャ上でTLSポインタを取得する際の、ハードウェアサポートの有無に応じた`liblink`の挙動と、ランタイムアセンブリコードの設計のミスマッチによって引き起こされました。

1.  **TLSポインタの取得**:
    Goランタイムは、現在のゴルーチン (`g`) ポインタを効率的に管理するためにTLSを利用します。ARM環境では、理想的には`MRC 15, 0, R0, C13, C0, 3`命令を使用して、ハードウェアから直接TLSベースポインタをR0レジスタに読み込みます。

2.  **`liblink`によるフォールバック**:
    しかし、`GOARM<7`のような古いARM環境では、この`MRC`命令がサポートされていないか、またはカーネルがTLSレジスタを公開していない場合があります。`liblink`は、ビルド時にこの状況を検出し、`MRC`命令を直接実行する代わりに、以下のようなフォールバック処理に置き換えます。
    *   元の`MRC`命令は、`BL runtime.tls_read_fallback`という命令に置き換えられます。
    *   `runtime.tls_read_fallback`関数は、`__kuser_get_tls`というカーネル提供のヘルパー関数を呼び出します。このヘルパー関数は、ソフトウェア的にTLSポインタを取得し、R0レジスタにその値を返します。

3.  **`save_g`関数内の問題**:
    `src/runtime/tls_arm.s`ファイルには、`runtime·save_g`というアセンブリ関数が含まれています。この関数は、現在のゴルーチンポインタをTLSに保存する役割を担っています。元のコードでは、この関数内でTLSポインタを取得するために`MRC`命令が直接記述されていました。
    `save_g`関数は、`MRC`命令がインラインで実行され、関数呼び出し（特に`BL`命令）が発生しないことを前提としていました。しかし、`liblink`が`MRC`を`BL runtime.tls_read_fallback`に置き換えると、`BL`命令が実行されます。

4.  **リンクレジスタ (LR) の破壊と無限ループ**:
    `BL`命令は、呼び出し元の次の命令のアドレスをLRに保存します。`runtime.tls_read_fallback`が`BL`によって呼び出されると、LRには`save_g`関数内の`MRC`命令の次のアドレスが保存されます。
    `runtime.tls_read_fallback`が処理を終えて`RET`（リターン）すると、LRに保存されていたアドレス（`save_g`関数内のアドレス）に戻ります。問題は、`save_g`関数自体が最後に`RET`命令を実行する際に、LRには`save_g`を呼び出した本来の呼び出し元のアドレスではなく、`runtime.tls_read_fallback`からのリターンによって上書きされた`save_g`関数内のアドレスが残ってしまっていたことです。
    結果として、`save_g`の`RET`命令は、`save_g`関数内のどこか（通常は`MRC`命令の直後）に再び分岐してしまい、無限ループに陥りました。

このコミットは、`BL`命令によるLRの変更を一時的に保存・復元することで、この問題を回避します。

## コアとなるコードの変更箇所

変更は`src/runtime/tls_arm.s`ファイルに集中しています。

```diff
--- a/src/runtime/tls_arm.s
+++ b/src/runtime/tls_arm.s
@@ -29,7 +29,13 @@ TEXT runtime·save_g(SB),NOSPLIT,$-4
  	MOVW	g, R0 // preserve R0 across call to setg<>
  	RET
  #endif
+	// If the host does not support MRC the linker will replace it with
+	// a call to runtime.read_tls_fallback which jumps to __kuser_get_tls.
+	// Both functions are written to only disturb R0 so it should be safe to 
+	// use R11 here to temporarily store LR.
+	MOVW	LR, R11
  	MRC	15, 0, R0, C13, C0, 3 // fetch TLS base pointer
+	MOVW	R11, LR
  	// $runtime.tlsg(SB) is a special linker symbol.
  	// It is the offset from the TLS base pointer to our
  	// thread-local storage for g.
@@ -51,7 +57,10 @@ TEXT runtime·load_g(SB),NOSPLIT,$0
  	// nothing to do as nacl/arm does not use TLS at all.
  	RET
  #endif
+	// See comment in save_g.
+	MOVW	LR, R11
  	MRC		15, 0, R0, C13, C0, 3 // fetch TLS base pointer
+	MOVW	R11, LR
  	// $runtime.tlsg(SB) is a special linker symbol.
  	// It is the offset from the TLS base pointer to our
  	// thread-local storage for g.
```

具体的には、`runtime·save_g`と`runtime·load_g`関数の両方で、`MRC`命令の直前と直後に以下の2行が追加されています。

*   `MOVW LR, R11`
*   `MOVW R11, LR`

## コアとなるコードの解説

追加された`MOVW LR, R11`と`MOVW R11, LR`のペアは、リンクレジスタ (LR) の値を一時的にR11レジスタに保存し、TLSポインタ取得処理（`MRC`命令、または`liblink`によるフォールバック後の`BL`呼び出し）の後にその値を復元するという役割を果たします。

1.  **`MOVW LR, R11`**:
    これは、`MRC`命令（または`liblink`によって置き換えられた`BL runtime.tls_read_fallback`）が実行される直前に、現在のLRレジスタの値をR11レジスタにコピーします。LRには、`runtime·save_g`（または`runtime·load_g`）を呼び出した関数のリターンアドレスが保存されています。この操作により、`BL`命令が実行されてLRが上書きされたとしても、本来のリターンアドレスがR11に安全にバックアップされます。

2.  **`MRC 15, 0, R0, C13, C0, 3`**:
    この命令は、TLSベースポインタをR0レジスタに読み込みます。`liblink`によって`BL runtime.tls_read_fallback`に置き換えられた場合、この`BL`命令が実行され、LRは`save_g`関数内の次の命令のアドレスに上書きされます。

3.  **`MOVW R11, LR`**:
    `MRC`命令（または`BL`呼び出しとそのリターン）の直後に、R11にバックアップしておいた本来のリターンアドレスをLRレジスタに復元します。これにより、`save_g`関数が自身の`RET`命令を実行する際に、LRには正しく`save_g`を呼び出した関数のリターンアドレスが設定されていることが保証されます。

この変更により、`liblink`が`MRC`命令を`BL`命令に置き換えるフォールバックパスを通ったとしても、`save_g`関数（および`load_g`関数）のLRレジスタが破壊されることがなくなり、無限ループが回避されます。コメントにもあるように、`runtime.tls_read_fallback`と`__kuser_get_tls`はR0レジスタのみを破壊するように書かれているため、R11を一時的な保存場所として使用することは安全です。

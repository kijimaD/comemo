# [インデックス 21534] ファイルの概要

このコミットは、Go言語のコマンドラインツール`go`の一部である`cmd/go/get.go`ファイルに対する変更です。`get.go`は、`go get`コマンドのロジックを実装しており、リモートリポジトリからGoパッケージをダウンロードおよびインストールする役割を担っています。具体的には、インポートパスに基づいて適切なリポジトリを特定し、その内容をローカルの`GOPATH`にチェックアウトする処理が含まれています。

## 変更の背景

この変更の背景には、Go言語のエコシステムにおけるパッケージ管理と、特に`golang.org/x`リポジトリ群の進化があります。

Go言語では、`go get`コマンドを使用して外部パッケージをインポートします。このコマンドは、インポートパス（例: `golang.org/x/net/context`）を解析し、そのパスに対応するリポジトリからソースコードをダウンロードします。一部のインポートパス、特に`golang.org/x`配下のものは「カスタムインポートパス」として知られています。これらは、実際のリポジトリURLとは異なる、より人間が読みやすい、またはGoプロジェクトの公式な場所を示すために設定された仮想的なパスです。

`golang.org/x`リポジトリ群は、Go 1.4のリリース（2014年12月）前後で導入されました。これらは、Goの標準ライブラリには含まれないが、Goチームによってメンテナンスされているパッケージ（例: `net`, `crypto`, `tools`など）をホストするために作られました。当初、これらのパッケージの一部は`code.google.com/p/go.net`のような古いGoogle Codeのインフラでホストされていましたが、GoプロジェクトがGoogle Sourceに移行するにつれて、これらのリポジトリも`go.googlesource.com`に移行しました。

ユーザーが`go get golang.org/x/net/context`のようなコマンドを実行すると、`go get`は`golang.org/x/net`が実際には`https://go.googlesource.com/net`から取得されるべきであることを認識します。しかし、もしユーザーのローカル環境に、以前の`https://code.google.com/p/go.net`からチェックアウトされた`golang.org/x/net`のコピーが既に存在していた場合、`go get`は矛盾を検出します。

このコミット以前のエラーメッセージは、単に「`X`は`Y`から来たが、`Z`から来るべきだ」というものでした。これは技術的には正しいものの、なぜそのような状況が発生したのか、特にカスタムインポートパスの概念に馴染みのないユーザーにとっては理解しにくいものでした。

新しいエラーメッセージは、この状況をより明確に説明することを目的としています。「`golang.org/x/net`は`https://go.googlesource.com/net`のカスタムインポートパスであるにもかかわらず、ローカルの`/Users/rsc/g/src/golang.org/x/net`は`https://code.google.com/p/go.net`からチェックアウトされている」と具体的に述べることで、ユーザーは問題の根本原因（カスタムインポートパスと実際のチェックアウト元の不一致）をより容易に把握できるようになります。これにより、ユーザーは古いリポジトリを削除して新しいリポジトリから再取得するなどの適切な対処を取りやすくなります。

## 前提知識の解説

### 1. Goの`go get`コマンド

`go get`は、Go言語のワークスペースに外部パッケージをダウンロードし、インストールするためのコマンドです。
-   **動作原理**: `go get`は、指定されたインポートパス（例: `github.com/user/repo`）を解析し、対応するバージョン管理システム（Git, Mercurial, Subversionなど）のリポジトリを特定します。その後、そのリポジトリからソースコードを`GOPATH/src`ディレクトリ配下にダウンロードします。
-   **カスタムインポートパス**: 一部のGoパッケージは、そのインポートパスが実際のリポジトリURLと直接一致しない場合があります。これは、HTMLページの`<meta>`タグを使用して、`go get`に「このインポートパスは実際にはこのリポジトリから取得すべきだ」と指示することで実現されます。例えば、`golang.org/x/net`のようなパスは、`go get`が`https://go.googlesource.com/net`からコードを取得するようにリダイレクトされます。これにより、パッケージのホスティング場所が変更されても、インポートパスを変更せずに済むという柔軟性が得られます。

### 2. `golang.org/x`リポジトリ群

`golang.org/x`は、Go言語の公式プロジェクトの一部ですが、標準ライブラリとは別に管理されているパッケージ群です。
-   **目的**: 標準ライブラリの厳格な後方互換性要件に縛られずに、新しい機能や実験的なコードを開発するために使用されます。また、標準ライブラリには含まれないが、Goエコシステムで広く利用される補助的なツールやライブラリ（例: `x/tools`, `x/crypto`, `x/net`）を提供します。
-   **歴史的経緯**: Goプロジェクトの初期には、一部のパッケージはGoogle Code（`code.google.com/p/...`）でホストされていました。しかし、GoプロジェクトがGoogle Source（`go.googlesource.com/...`）に移行するにつれて、これらのパッケージも新しいホスティング先に移されました。この移行期間中、ユーザーのローカル環境には古いホスティング元からチェックアウトされたパッケージが残っている可能性があり、それが`go get`が検出する不一致の原因となることがありました。

### 3. `GOPATH`

`GOPATH`は、Goのソースコード、コンパイル済みバイナリ、パッケージキャッシュが配置されるワークスペースのルートディレクトリです。`go get`コマンドは、ダウンロードしたパッケージを`$GOPATH/src`以下に配置します。

## 技術的詳細

このコミットは、`src/cmd/go/get.go`ファイル内の`downloadPackage`関数におけるエラーハンドリングロジックを変更しています。

`downloadPackage`関数は、指定されたパッケージをダウンロードする際に、そのパッケージのインポートパスがカスタムインポートパスであるかどうかをチェックします。カスタムインポートパスの場合、`go get`は、そのパスが指し示すべき「正しい」リポジトリURL（`repo`変数）を特定します。

同時に、`go get`はローカルの`GOPATH`内に既に存在するパッケージのディレクトリ（`dir`変数）を調べ、そのディレクトリが実際にどのリモートリポジトリ（`remote`変数）からチェックアウトされたものかを判断します。

問題が発生するのは、`remote != repo`、つまりローカルに存在するパッケージのチェックアウト元リポジトリが、カスタムインポートパスが指し示すべき正しいリポジトリと異なる場合です。これは、前述の`golang.org/x`パッケージのホスティング移行のような状況で発生し得ます。

変更前のコードでは、この不一致が検出された際に、以下のようなエラーメッセージを生成していました。

```go
return fmt.Errorf("%s is from %s, should be from %s", dir, remote, repo)
```

このメッセージは、`dir`（ローカルパス）、`remote`（実際のチェックアウト元）、`repo`（期待されるチェックアウト元）の3つの情報を含んでいました。しかし、カスタムインポートパスの文脈では、このメッセージはやや情報が不足していました。特に、`golang.org/x/net`のようなインポートパスがなぜ特定の`go.googlesource.com`のリポジトリと関連付けられているのかが不明瞭でした。

このコミットでは、エラーメッセージのフォーマット文字列が以下のように変更されました。

```go
return fmt.Errorf("%s is a custom import path for %s, but %s is checked out from %s", rr.root, repo, dir, remote)
```

新しいメッセージは、以下の4つの情報を含んでいます。

1.  `rr.root`: これは、カスタムインポートパスのルート（例: `golang.org/x/net`）です。
2.  `repo`: カスタムインポートパスが指し示すべき「正しい」リポジトリURL（例: `https://go.googlesource.com/net`）です。
3.  `dir`: ローカルに存在するパッケージのディレクトリパス（例: `/Users/rsc/g/src/golang.org/x/net`）です。
4.  `remote`: ローカルのディレクトリが実際にチェックアウトされたリモートリポジトリのURL（例: `https://code.google.com/p/go.net`）です。

この変更により、エラーメッセージは「`[カスタムインポートパスのルート]`は`[正しいリポジトリURL]`のカスタムインポートパスですが、`[ローカルディレクトリ]`は`[実際のチェックアウト元URL]`からチェックアウトされています」という形式になり、ユーザーにとって状況がより明確に伝わるようになりました。これにより、ユーザーはカスタムインポートパスの概念と、ローカルの古いリポジトリが原因で問題が発生していることを理解しやすくなります。

## コアとなるコードの解説

変更は`src/cmd/go/get.go`ファイルの293行目（変更後）にあります。

元のコードでは、`remote != repo`（ローカルのチェックアウト元と期待されるリポジトリが異なる）という条件が真になった場合に、`fmt.Errorf`関数を使ってエラーメッセージを生成していました。

-   **変更前**:
    ```go
    return fmt.Errorf("%s is from %s, should be from %s", dir, remote, repo)
    ```
    このフォーマット文字列は、`dir`（ローカルのディレクトリパス）、`remote`（ローカルのディレクトリがチェックアウトされた実際のリモートリポジトリ）、`repo`（カスタムインポートパスが指し示すべき正しいリポジトリ）の3つのプレースホルダーを持っていました。

-   **変更後**:
    ```go
    return fmt.Errorf("%s is a custom import path for %s, but %s is checked out from %s", rr.root, repo, dir, remote)
    ```
    新しいフォーマット文字列は、4つのプレースホルダーを使用しています。
    1.  `rr.root`: これは`RepoRoot`構造体の一部であり、カスタムインポートパスのルート（例: `golang.org/x/net`）を表します。
    2.  `repo`: カスタムインポートパスが指し示すべき正しいリポジトリURL（例: `https://go.googlesource.com/net`）です。
    3.  `dir`: ローカルに存在するパッケージのディレクトリパス（例: `/Users/rsc/g/src/golang.org/x/net`）です。
    4.  `remote`: ローカルのディレクトリが実際にチェックアウトされたリモートリポジトリのURL（例: `https://code.google.com/p/go.net`）です。

この変更により、エラーメッセージは単なる「AはBから来たが、Cから来るべきだ」という事実の提示から、「AはCのカスタムインポートパスだが、ローカルのDはBからチェックアウトされている」という、より詳細で文脈に沿った説明に変わりました。これにより、ユーザーはエラーの原因がカスタムインポートパスの解決とローカルリポジトリの不一致にあることを明確に理解できるようになり、問題解決のための次のステップ（例えば、古いリポジトリの削除と再取得）を判断しやすくなります。

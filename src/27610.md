# [インデックス 27610] ファイルの概要

このコミットは、Goランタイムにおけるスケジューラのワークスチール（work stealing）メカニズムに関連するスリープ時間の最適化を目的としています。具体的には、`runqgrab` 関数内で実行されるスリープ時間を100マイクロ秒から3マイクロ秒に短縮し、Windows環境では `osyield` を使用するように変更することで、並列アプリケーションのレイテンシとスループットを向上させています。これにより、特に同期チャネル操作が多いアプリケーションや、Windows環境でのパフォーマンスが改善されることが期待されます。

## 変更の背景

Goランタイムのスケジューラは、複数のゴルーチン（goroutine）を効率的にCPUコアに割り当て、並列実行を管理します。このプロセスにおいて、あるプロセッサ（P）が実行可能なゴルーチンを使い果たした場合、他のプロセッサのローカル実行キューやグローバル実行キューからゴルーチンを「盗む（steal）」ことで、CPUリソースの有効活用を図ります。これをワークスチールと呼びます。

以前のGoランタイムでは、ワークスチールを行う際に、`runqgrab` 関数内で100マイクロ秒（`usleep(100)`）の短いスリープが導入されていました。このスリープの目的は、ワークスチールが頻繁に発生しすぎること（「スラッシング」と呼ばれる状態）を防ぎ、ゴルーチンが異なるP間を頻繁に行き来することで発生するオーバーヘッドを軽減することでした。特に、`GOMAXPROCS` が1の場合など、特定のシナリオでパフォーマンスが低下するのを防ぐために導入された経緯があります（参照: `https://golang.org/s/go15gomaxprocs`）。

しかし、この100マイクロ秒のスリープは、特に並列処理を多用するアプリケーションにおいて、レイテンシとスループットに悪影響を与えることが判明しました。スリープ中はCPUがアイドル状態になり、本来実行できるはずの有用な作業が行われないためです。この問題は、Windows環境で特に顕著でした。Windowsのシステムタイマーの粒度が1〜15ミリ秒と粗いため、100マイクロ秒のスリープを要求しても、実際にはそれよりもはるかに長い時間（最小で1ミリ秒）スリープしてしまうことがあり、これがパフォーマンスのボトルネックとなっていました。

このコミットは、この過剰なスリープがもたらすパフォーマンス低下を解消し、より効率的なワークスチールを実現するために行われました。

## 前提知識の解説

このコミットの理解には、以下のGoランタイムの概念が不可欠です。

1.  **Goroutine (G)**: Goにおける軽量な実行スレッドです。数千、数万のゴルーチンを同時に実行できます。
2.  **Processor (P)**: 論理的なCPUコアを表します。Goスケジューラは、`GOMAXPROCS` の値に基づいてPの数を決定します。各Pはローカル実行キューを持ち、そこに実行可能なゴルーチンを保持します。
3.  **Machine (M)**: OSのスレッドを表します。MはPにアタッチされ、Pのローカル実行キューからゴルーチンを取り出して実行します。
4.  **Goスケジューラ**: G、P、Mを管理し、ゴルーチンを効率的にCPUコアに割り当てる役割を担います。
5.  **実行キュー (Run Queue)**:
    *   **ローカル実行キュー**: 各Pが持つ、実行可能なゴルーチンのキューです。
    *   **グローバル実行キュー**: どのPにも割り当てられていないゴルーチンが待機するキューです。
6.  **ワークスチール (Work Stealing)**: あるPが自身のローカル実行キューに実行可能なゴルーチンがない場合、他のPのローカル実行キューやグローバル実行キューからゴルーチンを「盗んで」きて実行するメカニズムです。これにより、CPUリソースのアイドル状態を防ぎ、全体のスループットを向上させます。
7.  **`usleep`**: 指定されたマイクロ秒数だけ現在のスレッドを一時停止させるシステムコールです。OSによって最小スリープ時間が異なり、特にWindowsでは粒度が粗いという特性があります。
8.  **`osyield`**: 現在の実行スレッドがCPUを他のスレッドに譲ることをOSに示唆する関数です。これにより、現在のスレッドは実行を一時停止し、OSは他の実行可能なスレッドにCPUを割り当てることができます。`usleep` と異なり、具体的なスリープ時間を指定するものではなく、CPUを譲ることを目的とします。
9.  **チャネル (Channel)**: ゴルーチン間で値を送受信するための同期メカニズムです。バッファなしチャネル（同期チャネル）の場合、送信と受信が同時に行われるまでゴルーチンはブロックされます。
10. **`GOMAXPROCS`**: Goプログラムが同時に使用できるOSスレッド（M）の最大数を制御する環境変数です。デフォルトでは論理CPUコア数に設定されます。

## 技術的詳細

このコミットの核心は、Goスケジューラのワークスチールロジック、具体的には `src/runtime/proc.go` 内の `runqgrab` 関数におけるスリープ戦略の変更にあります。

`runqgrab` 関数は、あるPが他のPからゴルーチンを盗もうとする際に呼び出されます。以前の実装では、この関数内で `usleep(100)` が実行されていました。これは、ワークスチールが過度に頻繁に行われることによる「スラッシング」を防ぐためのものでした。スラッシングとは、ゴルーチンがP間を頻繁に移動することで、キャッシュの無効化やスケジューリングオーバーヘッドが増大し、かえってパフォーマンスが低下する現象を指します。100マイクロ秒のスリープは、このスラッシングを抑制し、ゴルーチンが現在のPで実行される機会を与えるための「バックオフ」メカニズムとして機能していました。

しかし、この100マイクロ秒という値は、現代のCPU速度や同期チャネル操作の速度（約50ナノ秒）と比較して長すぎることが問題となりました。特に、同期チャネルを介して頻繁に通信を行う並列アプリケーションでは、ゴルーチンが次の作業を待つ間に不必要にスリープしてしまうため、レイテンシが増大し、スループットが低下していました。コミットメッセージにあるように、「有用な作業を行う代わりにスリープしている」状態でした。

この問題は、Windows環境でさらに深刻でした。Windowsのシステムタイマーの粒度が1〜15ミリ秒と粗いため、`usleep(100)` を呼び出しても、実際には最低でも1ミリ秒（1000マイクロ秒）程度のスリープが発生してしまうことがありました。これは、意図したスリープ時間の10倍以上であり、パフォーマンスへの悪影響は甚大でした。コミットメッセージのベンチマーク結果 (`BenchmarkDefaultResolution-8` や `Benchmark1ms-8`) が示すように、Windows環境では99%以上のパフォーマンス改善が見られています。

このコミットでは、以下の変更が導入されました。

1.  **スリープ時間の短縮**: `usleep` の時間を100マイクロ秒から3マイクロ秒に大幅に短縮しました。これにより、CPUがアイドル状態になる時間を最小限に抑えつつ、スラッシング抑制の目的も一定程度維持しようとしています。コミットメッセージでは、同期チャネルの送受信が約50ナノ秒であることを考慮すると、3マイクロ秒でも約50倍のオーバーシュート（必要以上の待機）があることを指摘しており、これ以上短縮するとスラッシングのリスクが高まる可能性を示唆しています。
2.  **Windows固有の対応**: `GOOS != "windows"` の条件分岐を導入し、Windows環境では `usleep(3)` の代わりに `osyield()` を呼び出すように変更しました。`osyield()` は、現在のスレッドがCPUを他のスレッドに譲ることをOSに示唆するもので、具体的なスリープ時間を指定しません。Windowsの粗いタイマー粒度の問題を回避し、より効率的にCPUを他のゴルーチンに譲ることを可能にします。これにより、Windows環境でのパフォーマンスが劇的に改善されました。

ベンチマーク結果は、これらの変更がもたらす効果を明確に示しています。

*   `BenchmarkChanSyncWork-12`: ワークを伴うチャネル同期のベンチマークで、5.13%の改善が見られます。これは、スリープ時間が短縮されたことで、ゴルーチンがより早く次の作業に取り掛かれるようになったことを示唆しています。
*   Windowsでのベンチマーク (`BenchmarkDefaultResolution-8`, `Benchmark1ms-8`): 99%以上の劇的な改善が見られます。これは、Windowsの粗いタイマー粒度の問題が `osyield` の導入によって解消されたことの直接的な結果です。
*   HTTPリクエスト処理の99パーセンタイルレイテンシが最大15%改善されたという言及は、この変更が実際のアプリケーションの応答性にも良い影響を与えることを示しています。

一方で、CPU消費量がわずかに増加するケースも報告されています (`BenchmarkChanSync-12` で106%から108%、`BenchmarkChanSyncWork-12` で107%から125%)。これは、スリープ時間が短縮されたことで、CPUがより積極的にゴルーチンのスケジューリングやワークスチールに関与するようになったためと考えられます。しかし、全体的なスループットとレイテンシの改善効果が、このわずかなCPU消費量の増加を上回ると判断されたものと推測されます。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は、以下の2つのファイルに集中しています。

1.  `src/runtime/chan_test.go`: ベンチマークの追加と修正。
2.  `src/runtime/proc.go`: スケジューラのワークスチールロジックの変更。

### `src/runtime/chan_test.go` の変更

*   `BenchmarkChanSync` 関数が `benchmarkChanSync` というヘルパー関数にリファクタリングされ、`work` パラメータを受け取るようになりました。
*   `benchmarkChanSync` 内で、チャネルの送受信後に `localWork(work)` が呼び出されるようになりました。これにより、チャネル操作の間に任意の量の「作業」をシミュレートできるようになり、より現実的なシナリオでのベンチマークが可能になります。
*   新しいベンチマーク関数 `BenchmarkChanSync` (work=0) と `BenchmarkChanSyncWork` (work=1000) が追加されました。
*   `localWork` というヘルパー関数が追加されました。これは、ループ内で簡単な計算を行うことで、CPUバウンドな作業をシミュレートします。`alwaysFalse` と `workSink` を使用して、コンパイラによる最適化でループが完全に削除されないように工夫されています。

### `src/runtime/proc.go` の変更

*   `runqgrab` 関数内の `usleep(100)` の呼び出し箇所が変更されました。
*   `GOOS != "windows"` の条件分岐が追加され、Windows以外のOSでは `usleep(3)` が呼び出されるようになりました。
*   Windows環境 (`GOOS == "windows"`) では、`usleep(3)` の代わりに `osyield()` が呼び出されるようになりました。

*   **`usleep(100)` から `usleep(3)` への変更**:
    *   以前は100マイクロ秒スリープしていましたが、これを3マイクロ秒に短縮しました。これにより、CPUがアイドル状態になる時間を大幅に削減し、ゴルーチンがより迅速に実行されるようになります。
    *   コメントにあるように、同期チャネルの送受信が約50ナノ秒であるため、3マイクロ秒でも50倍程度のオーバーシュート（必要以上の待機）があることを示唆しており、これ以上短縮するとスラッシングのリスクが高まる可能性を考慮したバランスの取れた値であることが伺えます。
*   **Windows固有の `osyield()` の導入**:
    *   `if GOOS != "windows"` の条件分岐により、Windows以外のOSでは引き続き `usleep(3)` を使用します。
    *   しかし、Windows環境では `osyield()` が呼び出されます。これは、Windowsのシステムタイマーの粒度が粗く、短い `usleep` を指定しても実際には長い時間スリープしてしまう問題を回避するためです。`osyield()` はCPUを他のスレッドに譲ることをOSに示唆するものであり、具体的なスリープ時間を指定しないため、Windowsのタイマー粒度の影響を受けにくく、より効率的なコンテキストスイッチが期待できます。

この変更により、特に並列アプリケーションにおけるゴルーチンのスケジューリング効率が向上し、レイテンシの削減とスループットの向上が実現されました。

    *   `BenchmarkChanSync(b *testing.B)`: `benchmarkChanSync(b, 0)` を呼び出し、チャネル操作の間に作業を行わない（`work=0`）純粋なチャネル同期のパフォーマンスを測定します。
    *   `BenchmarkChanSyncWork(b *testing.B)`: `benchmarkChanSync(b, 1000)` を呼び出し、チャネル操作の間に1000単位の作業を行うシナリオでのパフォーマンスを測定します。このベンチマークは、CPUバウンドな作業とチャネル同期が混在する実際のアプリケーションの挙動をよりよく反映します。
*   **`localWork` 関数の実装**:
    *   `localWork(w int)` は、`w` の値に基づいてループを回し、簡単な計算 (`foo /= (foo + 1)`) を行います。
    *   `alwaysFalse` と `workSink` というグローバル変数が導入されています。`alwaysFalse` は常に `false` であるため、`if alwaysFalse` ブロック内のコードは実行されません。しかし、コンパイラが `foo` の計算を完全に最適化して削除してしまうのを防ぐために、このダミーのコードが追加されています。これにより、`localWork` が実際にCPU時間を消費することを保証し、ベンチマークの信頼性を高めています。

これらのベンチマークの変更は、ランタイムの変更がチャネル同期とCPUバウンドな作業が混在するシナリオでどのように影響するかを正確に評価するために不可欠です。

## 変更の背景

Goランタイムのスケジューラは、複数のゴルーチン（goroutine）を効率的にCPUコアに割り当て、並列実行を管理します。このプロセスにおいて、あるプロセッサ（P）が実行可能なゴルーチンを使い果たした場合、他のプロセッサのローカル実行キューやグローバル実行キューからゴルーチンを「盗む（steal）」ことで、CPUリソースの有効活用を図ります。これをワークスチールと呼びます。

以前のGoランタイムでは、ワークスチールを行う際に、`runqgrab` 関数内で100マイクロ秒（`usleep(100)`）の短いスリープが導入されていました。このスリープの目的は、ワークスチールが頻繁に発生しすぎること（「スラッシング」と呼ばれる状態）を防ぎ、ゴルーチンが異なるP間を頻繁に行き来することで発生するオーバーヘッドを軽減することでした。特に、`GOMAXPROCS` が1の場合など、特定のシナリオでパフォーマンスが低下するのを防ぐために導入された経緯があります（参照: `https://golang.org/s/go15gomaxprocs`）。

しかし、この100マイクロ秒というスリープは、特に並列処理を多用するアプリケーションにおいて、レイテンシとスループットに悪影響を与えることが判明しました。スリープ中はCPUがアイドル状態になり、本来実行できるはずの有用な作業が行われないためです。この問題は、Windows環境で特に顕著でした。Windowsのシステムタイマーの粒度が1〜15ミリ秒と粗いため、100マイクロ秒のスリープを要求しても、実際にはそれよりもはるかに長い時間（最小で1ミリ秒）スリープしてしまうことがあり、これがパフォーマンスのボトルネックとなっていました。

このコミットは、この過剰なスリープがもたらすパフォーマンス低下を解消し、より効率的なワークスチールを実現するために行われました。

## 前提知識の解説

このコミットの理解には、以下のGoランタイムの概念が不可欠です。

1.  **Goroutine (G)**: Goにおける軽量な実行スレッドです。数千、数万のゴルーチンを同時に実行できます。
2.  **Processor (P)**: 論理的なCPUコアを表します。Goスケジューラは、`GOMAXPROCS` の値に基づいてPの数を決定します。各Pはローカル実行キューを持ち、そこに実行可能なゴルーチンを保持します。
3.  **Machine (M)**: OSのスレッドを表します。MはPにアタッチされ、Pのローカル実行キューからゴルーチンを取り出して実行します。
4.  **Goスケジューラ**: G、P、Mを管理し、ゴルーチンを効率的にCPUコアに割り当てる役割を担います。
5.  **実行キュー (Run Queue)**:
    *   **ローカル実行キュー**: 各Pが持つ、実行可能なゴルーチンのキューです。
    *   **グローバル実行キュー**: どのPにも割り当てられていないゴルーチンが待機するキューです。
6.  **ワークスチール (Work Stealing)**: あるPが自身のローカル実行キューに実行可能なゴルーチンがない場合、他のPのローカル実行キューやグローバル実行キューからゴルーチンを「盗んで」きて実行するメカニズムです。これにより、CPUリソースのアイドル状態を防ぎ、全体のスループットを向上させます。
7.  **`usleep`**: 指定されたマイクロ秒数だけ現在のスレッドを一時停止させるシステムコールです。OSによって最小スリープ時間が異なり、特にWindowsでは粒度が粗いという特性があります。
8.  **`osyield`**: 現在の実行スレッドがCPUを他のスレッドに譲ることをOSに示唆する関数です。これにより、現在のスレッドは実行を一時停止し、OSは他の実行可能なスレッドにCPUを割り当てることができます。`usleep` と異なり、具体的なスリープ時間を指定するものではなく、CPUを譲ることを目的とします。
9.  **チャネル (Channel)**: ゴルーチン間で値を送受信するための同期メカニズムです。バッファなしチャネル（同期チャネル）の場合、送信と受信が同時に行われるまでゴルーチンはブロックされます。
10. **`GOMAXPROCS`**: Goプログラムが同時に使用できるOSスレッド（M）の最大数を制御する環境変数です。デフォルトでは論理CPUコア数に設定されます。

## 技術的詳細

このコミットの核心は、Goスケジューラのワークスチールロジック、具体的には `src/runtime/proc.go` 内の `runqgrab` 関数におけるスリープ戦略の変更にあります。

`runqgrab` 関数は、あるPが他のPからゴルーチンを盗もうとする際に呼び出されます。以前の実装では、この関数内で `usleep(100)` が実行されていました。これは、ワークスチールが過度に頻繁に行われることによる「スラッシング」を防ぐためのものでした。スラッシングとは、ゴルーチンがP間を頻繁に移動することで、キャッシュの無効化やスケジューリングオーバーヘッドが増大し、かえってパフォーマンスが低下する現象を指します。100マイクロ秒のスリープは、このスラッシングを抑制し、ゴルーチンが現在のPで実行される機会を与えるための「バックオフ」メカニズムとして機能していました。

しかし、この100マイクロ秒という値は、現代のCPU速度や同期チャネル操作の速度（約50ナノ秒）と比較して長すぎることが問題となりました。特に、同期チャネルを介して頻繁に通信を行う並列アプリケーションでは、ゴルーチンが次の作業を待つ間に不必要にスリープしてしまうため、レイテンシが増大し、スループットが低下していました。コミットメッセージにあるように、「有用な作業を行う代わりにスリープしている」状態でした。

この問題は、Windows環境でさらに深刻でした。Windowsのシステムタイマーの粒度が1〜15ミリ秒と粗いため、短い `usleep` を指定しても、実際には最低でも1ミリ秒（1000マイクロ秒）程度のスリープが発生してしまうことがありました。これは、意図したスリープ時間の10倍以上であり、パフォーマンスへの悪影響は甚大でした。コミットメッセージのベンチマーク結果 (`BenchmarkDefaultResolution-8` や `Benchmark1ms-8`) が示すように、Windows環境では99%以上のパフォーマンス改善が見られています。

このコミットでは、以下の変更が導入されました。

1.  **スリープ時間の短縮**: `usleep` の時間を100マイクロ秒から3マイクロ秒に大幅に短縮しました。これにより、CPUがアイドル状態になる時間を最小限に抑えつつ、スラッシング抑制の目的も一定程度維持しようとしています。コミットメッセージでは、同期チャネルの送受信が約50ナノ秒であることを考慮すると、3マイクロ秒でも約50倍のオーバーシュート（必要以上の待機）があることを指摘しており、これ以上短縮するとスラッシングのリスクが高まる可能性を示唆しています。
2.  **Windows固有の対応**: `GOOS != "windows"` の条件分岐を導入し、Windows環境では `usleep(3)` の代わりに `osyield()` を呼び出すように変更しました。`osyield()` は、現在のスレッドがCPUを他のスレッドに譲ることをOSに示唆するもので、具体的なスリープ時間を指定しません。Windowsの粗いタイマー粒度の問題を回避し、より効率的にCPUを他のゴルーチンに譲ることを可能にします。これにより、Windows環境でのパフォーマンスが劇的に改善されました。

ベンチマーク結果は、これらの変更がもたらす効果を明確に示しています。

*   `BenchmarkChanSyncWork-12`: ワークを伴うチャネル同期のベンチマークで、5.13%の改善が見られます。これは、スリープ時間が短縮されたことで、ゴルーチンがより早く次の作業に取り掛かれるようになったことを示唆しています。
*   Windowsでのベンチマーク (`BenchmarkDefaultResolution-8`, `Benchmark1ms-8`): 99%以上の劇的な改善が見られます。これは、Windowsの粗いタイマー粒度の問題が `osyield` の導入によって解消されたことの直接的な結果です。
*   HTTPリクエスト処理の99パーセンタイルレイテンシが最大15%改善されたという言及は、この変更が実際のアプリケーションの応答性にも良い影響を与えることを示しています。

一方で、CPU消費量がわずかに増加するケースも報告されています (`BenchmarkChanSync-12` で106%から108%、`BenchmarkChanSyncWork-12` で107%から125%)。これは、スリープ時間が短縮されたことで、CPUがより積極的にゴルーチンのスケジューリングやワークスチールに関与するようになったためと考えられます。しかし、全体的なスループットとレイテンシの改善効果が、このわずかなCPU消費量の増加を上回ると判断されたものと推測されます。

## コアとなるコードの解説

### `src/runtime/proc.go` の変更点

```go
// ... (前略) ...

func runqgrab(_p_ *p, batch *[256]guintptr, batchHead uint32, stealRunNextG bool) (stolen int, runnextG *g) {
	// ... (中略) ...

	// Instead of stealing runnext in this window, back off
	// to give _p_ a chance to schedule runnext. This will avoid
	// thrashing gs between different Ps.
	// A sync chan send/recv takes ~50ns as of time of writing,
	// so 3us gives ~50x overshoot.
	if GOOS != "windows" {
		usleep(3)
	} else {
		// On windows system timer granularity is 1-15ms,
		// which is way too much for this optimization.
		// So just yield.
		osyield()
	}
	if !_p_.runnext.cas(next, 0) {
		continue
	}

	// ... (後略) ...
}
```

この変更は、`runqgrab` 関数内で他のPからゴルーチンを盗む際に、`_p_.runnext` (次に実行されるべきゴルーチン) が設定されている場合に、そのPにゴルーチンを実行する機会を与えるためのバックオフメカニズムを修正しています。

*   **`usleep(100)` から `usleep(3)` への変更**:
    *   以前は100マイクロ秒スリープしていましたが、これを3マイクロ秒に短縮しました。これにより、CPUがアイドル状態になる時間を大幅に削減し、ゴルーチンがより迅速に実行されるようになります。
    *   コメントにあるように、同期チャネルの送受信が約50ナノ秒であるため、3マイクロ秒でも50倍程度のオーバーシュート（必要以上の待機）があることを示唆しており、これ以上短縮するとスラッシングのリスクが高まる可能性を考慮したバランスの取れた値であることが伺えます。
*   **Windows固有の `osyield()` の導入**:
    *   `if GOOS != "windows"` の条件分岐により、Windows以外のOSでは引き続き `usleep(3)` を使用します。
    *   しかし、Windows環境では `osyield()` が呼び出されます。これは、Windowsのシステムタイマーの粒度が粗く、短い `usleep` を指定しても実際には長い時間スリープしてしまう問題を回避するためです。`osyield()` はCPUを他のスレッドに譲ることをOSに示唆するものであり、具体的なスリープ時間を指定しないため、Windowsのタイマー粒度の影響を受けにくく、より効率的なコンテキストスイッチが期待できます。

この変更により、特に並列アプリケーションにおけるゴルーチンのスケジューリング効率が向上し、レイテンシの削減とスループットの向上が実現されました。

このファイルでは、チャネル同期のベンチマークをより柔軟に、かつ現実的なシナリオで評価できるようにするための変更が加えられています。

*   **`BenchmarkChanSync` のリファクタリングと `localWork` の導入**:

*   **新しいベンチマーク関数の追加**:
    *   `BenchmarkChanSync(b *testing.B)`: `benchmarkChanSync(b, 0)` を呼び出し、チャネル操作の間に作業を行わない（`work=0`）純粋なチャネル同期のパフォーマンスを測定します。
    *   `BenchmarkChanSyncWork(b *testing.B)`: `benchmarkChanSync(b, 1000)` を呼び出し、チャネル操作の間に1000単位の作業を行うシナリオでのパフォーマンスを測定します。このベンチマークは、CPUバウンドな作業とチャネル同期が混在する実際のアプリケーションの挙動をよりよく反映します。
*   **`localWork` 関数の実装**:
    *   `localWork(w int)` は、`w` の値に基づいてループを回し、簡単な計算 (`foo /= (foo + 1)`) を行います。
    *   `alwaysFalse` と `workSink` というグローバル変数が導入されています。`alwaysFalse` は常に `false` であるため、`if alwaysFalse` ブロック内のコードは実行されません。しかし、コンパイラが `foo` の計算を完全に最適化して削除してしまうのを防ぐために、このダミーのコードが追加されています。これにより、`localWork` が実際にCPU時間を消費することを保証し、ベンチマークの信頼性を高めています。

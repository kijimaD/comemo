このコミットは、Go言語の標準ライブラリ`net`パッケージにおける、Plan 9オペレーティングシステム上でのUDPコネクションの`WriteTo`および`WriteToUDP`メソッドの挙動に関するバグ修正です。具体的には、`WriteTo`が書き込んだバイト数を報告する際に、内部的なUDPヘッダのサイズを含めてしまっていた問題を修正し、ユーザーが実際に送信したデータ（ペイロード）のサイズのみを返すように変更しています。

## 元コミット内容

`net: fix WriteTo on Plan 9`

この変更は、`WriteTo`で書き込まれたバイト数の結果から、内部UDPヘッダサイズを除外します。

## 変更の背景

Go言語の`net`パッケージは、様々なオペレーティングシステム（OS）に対応しており、それぞれのOSのネットワークAPIや特性に合わせて実装が調整されています。Plan 9は、ベル研究所で開発された分散オペレーティングシステムであり、そのネットワークスタックはUnix系OSとは異なる独自のアプローチを採用しています。

Goの`net.UDPConn`型には、UDPデータグラムを送信するための`WriteTo`および`WriteToUDP`メソッドがあります。これらのメソッドは、ユーザーが提供したバイトスライス（データペイロード）をネットワークに書き込み、実際に書き込まれたバイト数を返します。しかし、Plan 9環境では、内部的にUDPヘッダ情報がユーザーデータに付加されてカーネルに渡されることがあります。

このコミット以前の`udpsock_plan9.go`の実装では、`WriteToUDP`メソッドが、ユーザーデータに加えて内部的なUDPヘッダ情報を含んだバッファ全体を基盤となるファイルディスクリプタに書き込み、そのファイルディスクリプタが返した「書き込まれたバイト数」をそのまま`WriteTo`の戻り値としていました。この「書き込まれたバイト数」には、ユーザーが意図しない内部ヘッダのサイズが含まれてしまっていたため、`WriteTo`の呼び出し元が期待する「実際に送信したペイロードのバイト数」と一致しないという問題が発生していました。これは、APIのセマンティクス（ユーザーが提供したデータのバイト数を返す）に反する挙動であり、アプリケーションが正確な送信バイト数を把握できない原因となっていました。

このバグは、特にネットワークプロトコルの実装や、送信バイト数に基づいて何らかの処理を行うアプリケーションにおいて、予期せぬ動作や誤った計算を引き起こす可能性がありました。

## 前提知識の解説

*   **UDP (User Datagram Protocol)**: TCP/IPプロトコルスイートの一部であり、コネクションレス型のプロトコルです。信頼性や順序保証はありませんが、オーバーヘッドが少なく高速なデータ転送に適しています。DNSクエリ、NTP、ストリーミングなど、リアルタイム性や低遅延が求められるアプリケーションで利用されます。
*   **`net.UDPConn`**: Go言語の`net`パッケージで提供されるUDPコネクションを表す型です。UDPソケットの操作（データの送受信など）を行います。
*   **`WriteTo`メソッド**: `net.PacketConn`インターフェースの一部であり、`net.UDPConn`が実装しています。このメソッドは、指定されたアドレスにデータグラムを送信し、書き込まれたバイト数とエラーを返します。通常、返されるバイト数は、ユーザーが提供したデータのバイト数（ペイロードサイズ）であるべきです。
*   **`WriteToUDP`メソッド**: `net.UDPConn`に特化したメソッドで、`WriteTo`と同様にUDPデータグラムを送信します。内部的には`WriteTo`が`WriteToUDP`を呼び出すか、あるいは`WriteToUDP`がより低レベルなOS固有のシステムコールをラップすることがあります。
*   **Plan 9**: ベル研究所で開発された分散オペレーティングシステムです。Unixの概念をさらに推し進め、すべてのリソース（ファイル、デバイス、ネットワーク接続など）をファイルシステムとして表現するという特徴があります。ネットワーク通信もファイル操作として行われるため、Goの`net`パッケージのPlan 9向け実装では、通常のUnix系OSとは異なるアプローチが取られます。
*   **内部UDPヘッダ**: ネットワークプロトコルでは、データ本体（ペイロード）の前に、送信元・送信先アドレス、ポート番号、チェックサムなどの情報を含むヘッダが付加されます。OSのネットワークスタックが、ユーザーが提供したデータにこれらのヘッダを付加して実際に送信します。Plan 9のネットワークスタックの実装によっては、このヘッダ情報が、ユーザーデータと共に単一のバッファとしてカーネルに渡され、そのバッファ全体のサイズが「書き込まれたバイト数」として報告されることがありました。

## 技術的詳細

このコミットの技術的な核心は、`net.UDPConn`の`WriteToUDP`メソッドが、Plan 9環境において、実際にネットワークに書き込まれたバイト数（内部UDPヘッダを含む）ではなく、ユーザーが提供したデータ（ペイロード）のバイト数のみを正確に返すように修正した点にあります。

修正前のコードでは、`WriteToUDP`関数内で、ユーザーが送信しようとするバイトスライス`b`の前に、`udpHeaderSize`分のヘッダ情報（`h.Bytes()`）を結合した新しいバッファ`buf`を作成していました。そして、この`buf`全体を`c.fd.data.Write(buf)`という形で基盤となるファイルディスクリプタに書き込んでいました。この`Write`システムコールは、実際に書き込まれたバイト数`n`を返します。問題は、この`n`が`udpHeaderSize + len(b)`、つまり内部ヘッダとペイロードの両方を含んだサイズであったことです。

Goの`net.PacketConn`インターフェースの`WriteTo`メソッドのセマンティクスは、ユーザーが提供したデータのバイト数を返すことを期待しています。しかし、Plan 9の実装では、内部ヘッダのサイズが`n`に含まれてしまっていたため、APIの期待と実際の挙動が異なっていました。

このコミットでは、以下の2つの変更によってこの問題を解決しています。

1.  **戻り値の変更**: `c.fd.data.Write(buf)`の戻り値`n`を破棄し、常に`len(b)`（ユーザーが提供したペイロードのサイズ）を返すように変更しました。これにより、`WriteTo`メソッドのセマンティクスが正しく満たされます。
2.  **エラーハンドリングの簡素化**: 以前は`n, err := c.fd.data.Write(buf)`としていた部分が、`if _, err := c.fd.data.Write(buf); err != nil { ... }`と変更され、書き込まれたバイト数`n`が不要になったため、エラーチェックのみを行う形に簡素化されました。エラーが発生した場合は、引き続き`OpError`を返します。

この修正により、Plan 9上でもGoのネットワークAPIが他のOSと同様に一貫した挙動を示すようになり、アプリケーション開発者はOSの違いを意識することなく、`WriteTo`が返すバイト数を信頼できるようになりました。

## コアとなるコードの解説

変更された`WriteToUDP`メソッドの主要な部分は以下の通りです。

```go
func (c *UDPConn) WriteToUDP(b []byte, addr *UDPAddr) (int, error) {
	// 内部UDPヘッダとユーザーデータ(b)を結合するためのバッファを確保
	buf := make([]byte, udpHeaderSize+len(b))
	// ヘッダ情報をバッファの先頭にコピー
	i := copy(buf, h.Bytes())
	// ユーザーデータ(b)をヘッダの直後にコピー
	copy(buf[i:], b)

	// 基盤となるファイルディスクリプタにバッファ全体を書き込む
	// 以前は n, err := ... としていたが、n は不要になったため破棄
	if _, err := c.fd.data.Write(buf); err != nil {
		// 書き込みエラーが発生した場合、OpErrorを生成して返す
		return 0, &OpError{Op: "write", Net: c.fd.dir, Addr: addr, Err: err}
	}
	// エラーがなければ、ユーザーが提供したデータのバイト数 (len(b)) を返す
	// 以前は n (内部ヘッダを含む書き込みバイト数) を返していた
	return len(b), nil
}
```

1.  **`buf := make([]byte, udpHeaderSize+len(b))`**:
    *   `udpHeaderSize`は、Plan 9のUDPソケットが内部的に使用するヘッダのサイズです。
    *   `len(b)`は、ユーザーが送信しようとしている実際のデータ（ペイロード）のサイズです。
    *   この行では、ヘッダとペイロードの両方を格納できる十分なサイズのバイトスライス`buf`を確保しています。

2.  **`i := copy(buf, h.Bytes())`**:
    *   `h.Bytes()`は、Plan 9のUDPヘッダ情報をバイトスライスとして返します。
    *   このヘッダ情報を`buf`の先頭にコピーし、コピーされたバイト数（`udpHeaderSize`に等しい）が`i`に格納されます。

3.  **`copy(buf[i:], b)`**:
    *   `buf[i:]`は、`buf`のヘッダの直後から始まる部分スライスです。
    *   ユーザーデータ`b`をこの部分スライスにコピーします。これにより、`buf`は`[UDPヘッダ | ユーザーデータ]`という構造になります。

4.  **`if _, err := c.fd.data.Write(buf); err != nil { ... }`**:
    *   `c.fd.data`は、Plan 9のファイルディスクリプタ（`io.Writer`インターフェースを実装している）を表します。
    *   `Write(buf)`は、構築された`buf`全体を基盤となるOSのネットワークインターフェースに書き込みます。
    *   以前のコードでは、この`Write`呼び出しの戻り値である`n`（実際に書き込まれたバイト数）と`err`を受け取っていました。しかし、`n`は内部ヘッダサイズを含んでいたため、今回の修正で不要になりました。
    *   `_`（ブランク識別子）を使用することで、`n`の値を破棄し、`err`のみをチェックしています。
    *   書き込み中にエラーが発生した場合、`OpError`を生成して即座に`0`バイトとエラーを返します。

5.  **`return len(b), nil`**:
    *   これが最も重要な変更点です。
    *   書き込みが成功し、エラーがなかった場合、この行が実行されます。
    *   以前は`return n, err`としていましたが、`n`は内部ヘッダサイズを含んでいたため、`len(b)`（ユーザーが提供した実際のペイロードサイズ）を返すように変更されました。
    *   これにより、`WriteToUDP`（そしてそれを呼び出す`WriteTo`）は、GoのネットワークAPIの期待通り、ユーザーが送信したデータのバイト数のみを正確に報告するようになります。

この修正により、Plan 9環境におけるUDPソケットの`WriteTo`メソッドの挙動が、他のOS環境と一貫性を持つようになり、Goアプリケーションのポータビリティと信頼性が向上しました。

Goの`net.PacketConn`インターフェースの`WriteTo`メソッドのセマンティクスは、ユーザーが提供したデータのバイト数を返すことを期待しています。しかし、Plan 9の実装では、内部ヘッダのサイズが`n`に含まれてしまっていたため、APIの期待と実際の挙動が異なっていました。

このコミットでは、以下の2つの変更によってこの問題を解決しています。

1.  **戻り値の変更**: `c.fd.data.Write(buf)`の戻り値`n`を破棄し、常に`len(b)`（ユーザーが提供したペイロードのサイズ）を返すように変更しました。これにより、`WriteTo`メソッドのセマンティクスが正しく満たされます。
2.  **エラーハンドリングの簡素化**: 以前は`n, err := c.fd.data.Write(buf)`としていた部分が、`if _, err := c.fd.data.Write(buf); err != nil { ... }`と変更され、書き込まれたバイト数`n`が不要になったため、エラーチェックのみを行う形に簡素化されました。エラーが発生した場合は、引き続き`OpError`を返します。

この修正により、Plan 9上でもGoのネットワークAPIが他のOSと同様に一貫した挙動を示すようになり、アプリケーション開発者はOSの違いを意識することなく、`WriteTo`が返すバイト数を信頼できるようになりました。

## コアとなるコードの解説

変更された`WriteToUDP`メソッドの主要な部分は以下の通りです。

```go
func (c *UDPConn) WriteToUDP(b []byte, addr *UDPAddr) (int, error) {
	// 内部UDPヘッダとユーザーデータ(b)を結合するためのバッファを確保
	buf := make([]byte, udpHeaderSize+len(b))
	// ヘッダ情報をバッファの先頭にコピー
	i := copy(buf, h.Bytes())
	// ユーザーデータ(b)をヘッダの直後にコピー
	copy(buf[i:], b)

	// 基盤となるファイルディスクリプタにバッファ全体を書き込む
	// 以前は n, err := ... としていたが、n は不要になったため破棄
	if _, err := c.fd.data.Write(buf); err != nil {
		// 書き込みエラーが発生した場合、OpErrorを生成して返す
		return 0, &OpError{Op: "write", Net: c.fd.dir, Addr: addr, Err: err}
	}
	// エラーがなければ、ユーザーが提供したデータのバイト数 (len(b)) を返す
	// 以前は n (内部ヘッダを含む書き込みバイト数) を返していた
	return len(b), nil
}
```

1.  **`buf := make([]byte, udpHeaderSize+len(b))`**:
    *   `udpHeaderSize`は、Plan 9のUDPソケットが内部的に使用するヘッダのサイズです。
    *   `len(b)`は、ユーザーが送信しようとしている実際のデータ（ペイロード）のサイズです。
    *   この行では、ヘッダとペイロードの両方を格納できる十分なサイズのバイトスライス`buf`を確保しています。

2.  **`i := copy(buf, h.Bytes())`**:
    *   `h.Bytes()`は、Plan 9のUDPヘッダ情報をバイトスライスとして返します。
    *   このヘッダ情報を`buf`の先頭にコピーし、コピーされたバイト数（`udpHeaderSize`に等しい）が`i`に格納されます。

3.  **`copy(buf[i:], b)`**:
    *   `buf[i:]`は、`buf`のヘッダの直後から始まる部分スライスです。
    *   ユーザーデータ`b`をこの部分スライスにコピーします。これにより、`buf`は`[UDPヘッダ | ユーザーデータ]`という構造になります。

4.  **`if _, err := c.fd.data.Write(buf); err != nil { ... }`**:
    *   `c.fd.data`は、Plan 9のファイルディスクリプタ（`io.Writer`インターフェースを実装している）を表します。
    *   `Write(buf)`は、構築された`buf`全体を基盤となるOSのネットワークインターフェースに書き込みます。
    *   以前のコードでは、この`Write`呼び出しの戻り値である`n`（実際に書き込まれたバイト数）と`err`を受け取っていました。しかし、`n`は内部ヘッダサイズを含んでいたため、今回の修正で不要になりました。
    *   `_`（ブランク識別子）を使用することで、`n`の値を破棄し、`err`のみをチェックしています。
    *   書き込み中にエラーが発生した場合、`OpError`を生成して即座に`0`バイトとエラーを返します。

5.  **`return len(b), nil`**:
    *   これが最も重要な変更点です。
    *   書き込みが成功し、エラーがなかった場合、この行が実行されます。
    *   以前は`return n, err`としていましたが、`n`は内部ヘッダサイズを含んでいたため、`len(b)`（ユーザーが提供した実際のペイロードサイズ）を返すように変更されました。
    *   これにより、`WriteToUDP`（そしてそれを呼び出す`WriteTo`）は、GoのネットワークAPIの期待通り、ユーザーが送信したデータのバイト数のみを正確に報告するようになります。

この修正により、Plan 9環境におけるUDPソケットの`WriteTo`メソッドの挙動が、他のOS環境と一貫性を持つようになり、Goアプリケーションのポータビリティと信頼性が向上しました。

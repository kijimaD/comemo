## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行中に不要になったメモリを自動的に解放する重要な機能です。GCの効率は、アプリケーションのパフォーマンスに直接影響します。GoのGCは、主に「マーク・アンド・スイープ」アルゴリズムに基づいており、オブジェクトが到達可能（使用中）であるかをマークし、マークされなかったオブジェクトをスイープ（解放）します。

このコミットの背景には、GCのトリガータイミングの精度向上という目的があります。従来のGoのGCは、ヒープサイズが一定の閾値を超えた場合にGCをトリガーしていました。しかし、この閾値の決定は、実際にどれだけのメモリが「生きている」（マークされる）かという情報に基づいていないため、GCの実行が早すぎたり遅すぎたりする可能性がありました。

「マークされたヒープバイト数」を正確に追跡することで、Goランタイムは次回のGCをトリガーするタイミングをよりインテリジェントに決定できるようになります。例えば、前回のGCでマークされたバイト数が少なかった場合、次回のGCはより遅くトリガーされるべきかもしれません。これにより、GCのオーバーヘッドを削減し、アプリケーションのスループットを向上させることが期待されます。

この変更は、GoのGCがより適応的で効率的になるための重要なステップであり、後のGC調整アルゴリズム（例えば、GCの目標ヒープ比率を動的に調整するGOGCの自動調整など）の基盤となります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

### Goのガベージコレクション (GC) の基本

GoのGCは、並行（Concurrent）かつ三色（Tri-color）マーク・アンド・スイープ方式を採用しています。

*   **三色マーク**:
    *   **白 (White)**: まだGCによって到達可能かどうかが確認されていないオブジェクト。GC開始時にはすべてのオブジェクトが白。
    *   **灰 (Grey)**: 到達可能であることは確認されたが、そのオブジェクトが参照している他のオブジェクトがまだスキャンされていないオブジェクト。
    *   **黒 (Black)**: 到達可能であり、かつそのオブジェクトが参照しているすべてのオブジェクトもスキャン済みのオブジェクト。
*   **マークフェーズ**: GCの開始時に、ルート（グローバル変数、スタック、レジスタなど）から到達可能なオブジェクトを白から灰へ、そして灰から黒へとマークしていきます。
*   **スイープフェーズ**: マークされなかった白のオブジェクト（到達不可能と判断されたオブジェクト）をメモリから解放します。
*   **並行GC**: GoのGCは、ほとんどのマークフェーズをアプリケーションの実行と並行して行います。これにより、アプリケーションの一時停止（Stop-The-World, STW）時間を最小限に抑えます。

### GCワーカーと`gcWork`

GoのGCは、複数のGCワーカーゴルーチンによって並行して実行されます。これらのワーカーは、マーク作業を分担します。

*   **`gcWork`**: 各GCワーカーがマーク作業を行う際に使用するローカルなバッファです。オブジェクトをスキャンして見つかった参照を一時的にこのバッファに格納し、後で処理します。これにより、グローバルなデータ構造へのアトミック操作の回数を減らし、並行処理の効率を高めます。
*   **`dispose`**: `gcWork`バッファに蓄積された作業（このコミットではマークされたバイト数）を、グローバルなカウンタに集約する操作です。これは、`gcWork`バッファがいっぱいになったり、GCワーカーが一時停止したりする際に呼び出されます。

### P (Processor)

Goランタイムは、OSのスレッドを抽象化した「M」（Machine）と、論理プロセッサを表す「P」（Processor）という概念を持っています。GoのゴルーチンはP上で実行され、PはMにアタッチされます。Pは、スケジューリングやGCワーカーの管理など、ランタイムの重要なコンテキストを保持します。

### アトミック操作 (`xadd64`)

並行処理において、複数のゴルーチンが同時に同じメモリ位置を更新しようとすると、競合状態（Race Condition）が発生し、データの不整合を引き起こす可能性があります。これを防ぐために、アトミック操作が使用されます。

*   **`xadd64`**: Goランタイム内部で使用されるアトミックな加算操作です。これは、指定されたメモリ位置の値を、他のゴルーチンの干渉なしに安全に加算します。このコミットでは、複数のGCワーカーがマークしたバイト数をグローバルな`bytesMarked`カウンタに安全に集約するために使用されます。

### ヒープバイト数とGCトリガー

GoのGCは、ヒープの使用量に基づいてトリガーされます。具体的には、前回のGC終了時のライブヒープサイズ（マークされたバイト数）と、GC目標比率（GOGC環境変数で設定可能、デフォルトは100%）に基づいて、次回のGCがトリガーされるヒープサイズを決定します。このコミットは、この「前回のGC終了時のライブヒープサイズ」をより正確に把握するためのものです。

## 技術的詳細

このコミットの主要な技術的詳細は、GCサイクル中にマークされたヒープバイト数を正確に追跡するためのメカニズムの導入にあります。

1.  **`work.bytesMarked`の導入**:
    *   `src/runtime/mgc.go`内の`work`構造体に`bytesMarked uint64`フィールドが追加されました。これは、現在のGCサイクルでマークされた合計バイト数を保持するグローバルなカウンタです。
    *   このカウンタは、GCサイクルの開始時に`0`にリセットされます。
    *   コミットメッセージにあるように、この値はGCサイクルの終わりにのみ読み取られるため、更新はバッチ処理される可能性があります。

2.  **`gcWork.bytesMarked`の導入と集約**:
    *   `src/runtime/mgcwork.go`内の`gcWork`構造体に`bytesMarked uint64`フィールドが追加されました。これは、個々のGCワーカーがローカルでマークしたバイト数を一時的に保持するためのカウンタです。
    *   GCワーカーがオブジェクトをマークする際、そのオブジェクトのサイズが`gcWork.bytesMarked`に加算されます。
    *   `gcWork.dispose()`および`gcWork.disposeToCache()`メソッドが変更され、`gcWork.bytesMarked`に蓄積された値が、グローバルな`work.bytesMarked`カウンタにアトミックに加算されるようになりました。これは`xadd64`関数を使用して行われます。
    *   コミットメッセージでは、`dispose`が比較的まれに発生するため、グローバルカウンタへの競合は低いと述べられています。しかし、もし問題になるようであれば、`dispose`の頻度を減らすか、各P（プロセッサ）ごとにカウンタを持つように切り替えることが代替案として示唆されています。

3.  **マーク処理におけるバイト数加算**:
    *   `src/runtime/mgcmark.go`内の`scanobject`関数が変更され、スキャンされたオブジェクトのサイズが`gcw.bytesMarked`（現在のGCワーカーのローカルカウンタ）に加算されるようになりました。
    *   `greyobject`関数も変更され、`noscan`オブジェクト（ポインタを含まないオブジェクトで、すぐに黒にマークされるオブジェクト）がマークされる際に、そのサイズが`gcw.bytesMarked`に加算されるようになりました。
    *   `gcmarknewobject_m`関数（GCマーク終了フェーズで新しく割り当てられたオブジェクトをマークする関数）も変更され、新しくマークされたオブジェクトのサイズがグローバルな`work.bytesMarked`に直接アトミックに加算されるようになりました。これは、このフェーズではGCワーカーのローカルバッファを介さずに直接グローバルカウンタを更新するためです。

4.  **ルートとスタックの除外**:
    *   `markroot`関数と`scanstack`関数では、`gcw.bytesMarked`が`0`にリセットされています。これは、ルートオブジェクト（グローバル変数など）やスタック上のオブジェクトはヒープの一部ではないため、マークされたヒープバイト数には含めないという意図を示しています。

この変更により、GoランタイムはGCサイクル中に実際に「生きている」とマークされたヒープメモリの総量を正確に把握できるようになります。この情報は、次回のGCトリガーの決定において、より洗練されたヒューリスティックを適用するための重要な入力となります。例えば、前回のGCでマークされたバイト数が少なかった場合、次回のGCはより遅く開始されることで、GCの頻度を減らし、全体的なパフォーマンスを向上させることができます。

### `src/runtime/mgc.go`

```go
var work struct {
	// ... 既存のフィールド ...
	totaltime int64

	// bytesMarked is the number of bytes marked this cycle. This
	// includes bytes blackened in scanned objects, noscan objects
	// that go straight to black, and permagrey objects scanned by
	// markroot during the concurrent scan phase. This is updated
	// atomically during the cycle. Updates may be batched
	// arbitrarily, since the value is only read at the end of the
	// cycle.
	//
	// Because of benign races during marking, this number may not
	// be the exact number of marked bytes, but it should be very
	// close.
	bytesMarked uint64
}

// GC runs a garbage collection.
func gc(mode int) {
	// ...
	clearpools()

	work.bytesMarked = 0 // GCサイクル開始時にリセット
	// ...
}
```
`work.bytesMarked`は、GCサイクル全体でマークされたヒープバイトの総数を追跡するためのグローバルカウンタです。GCの開始時に`0`にリセットされます。コメントには、マーク中の競合により厳密な値ではない可能性があるが、非常に近い値であると説明されています。

	// ...
	// Root aren't part of the heap, so don't count them toward
	// marked heap bytes.
	gcw.bytesMarked = 0 // ルートはヒープではないため、カウントしない

func scanstack(gp *g) {
	// ...
	// Stacks aren't part of the heap, so don't count them toward
	// marked heap bytes.
	gcw.bytesMarked = 0 // スタックはヒープではないため、カウントしない
	gcw.disposeToCache()
	gp.gcscanvalid = true

func scanobject(b, n uintptr, ptrmask *uint8, gcw *gcWork) {
	// ...
	// Mark the object.
	if obj, hbits, span := heapBitsForObject(obj); obj != 0 {
		greyobject(obj, b, i, hbits, span, gcw)
	}
	gcw.bytesMarked += uint64(n) // スキャンされたオブジェクトのサイズを加算
}

//go:nowritebarrier
func greyobject(obj, base, off uintptr, hbits heapBits, span *mspan, gcw *gcWork) {
	// ...
	// If this is a noscan object, fast-track it to black
	// instead of greying it.
	if hbits.typeBits() == typeDead {
		gcw.bytesMarked += uint64(span.elemsize) // noscanオブジェクトのサイズを加算
		return
	}
	// ...
}

//go:nowritebarrier
func gcmarknewobject_m(obj, size uintptr) {
	if gcphase != _GCmarktermination {
		throw("marking new object while not in mark termination phase")
	}
	// ...
	heapBitsForAddr(obj).setMarked()
	xadd64(&work.bytesMarked, int64(size)) // 新しくマークされたオブジェクトのサイズをグローバルカウンタにアトミックに加算

### `src/runtime/mgcwork.go`

```go
type gcWork struct {
	// Invariant: wbuf is never full or empty
	wbuf wbufptr

	// Bytes marked (blackened) on this gcWork. This is aggregated
	// into work.bytesMarked by dispose.
	bytesMarked uint64
}

func (w *gcWork) dispose() {
	// ...
	if w.bytesMarked != 0 {
		// dispose happens relatively infrequently. If this
		// atomic becomes a problem, we should first try to
		// dispose less and if necessary aggregate in a per-P
		// counter.
		xadd64(&work.bytesMarked, int64(w.bytesMarked)) // ローカルカウンタの値をグローバルカウンタにアトミックに集約
		w.bytesMarked = 0
	}
}

func (w *gcWork) disposeToCache() {
	// ...
	if w.bytesMarked != 0 {
		xadd64(&work.bytesMarked, int64(w.bytesMarked)) // ローカルカウンタの値をグローバルカウンタにアトミックに集約
		w.bytesMarked = 0
	}
}
```
`gcWork`構造体に`bytesMarked`フィールドが追加され、各GCワーカーがローカルでマークしたバイト数を保持します。`dispose`および`disposeToCache`メソッドが呼び出される際に、このローカルカウンタの値がグローバルな`work.bytesMarked`に`xadd64`を使ってアトミックに加算されます。これにより、各ワーカーの作業が安全に集約されます。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行中に不要になったメモリを自動的に解放する重要な機能です。GCの効率は、アプリケーションのパフォーマンスに直接影響します。GoのGCは、主に「マーク・アンド・スイープ」アルゴリズムに基づいており、オブジェクトが到達可能（使用中）であるかをマークし、マークされなかったオブジェクトをスイープ（解放）します。

このコミットの背景には、GCのトリガータイミングの精度向上という目的があります。従来のGoのGCは、ヒープサイズが一定の閾値を超えた場合にGCをトリガーしていました。しかし、この閾値の決定は、実際にどれだけのメモリが「生きている」（マークされる）かという情報に基づいていないため、GCの実行が早すぎたり遅すぎたりする可能性がありました。

「マークされたヒープバイト数」を正確に追跡することで、Goランタイムは次回のGCをトリガーするタイミングをよりインテリジェントに決定できるようになります。例えば、前回のGCでマークされたバイト数が少なかった場合、次回のGCはより遅くトリガーされるべきかもしれません。これにより、GCのオーバーヘッドを削減し、アプリケーションのスループットを向上させることが期待されます。

この変更は、GoのGCがより適応的で効率的になるための重要なステップであり、後のGC調整アルゴリズム（例えば、GCの目標ヒープ比率を動的に調整するGOGCの自動調整など）の基盤となります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

### Goのガベージコレクション (GC) の基本

GoのGCは、並行（Concurrent）かつ三色（Tri-color）マーク・アンド・スイープ方式を採用しています。

*   **三色マーク**:
    *   **白 (White)**: まだGCによって到達可能かどうかが確認されていないオブジェクト。GC開始時にはすべてのオブジェクトが白。
    *   **灰 (Grey)**: 到達可能であることは確認されたが、そのオブジェクトが参照している他のオブジェクトがまだスキャンされていないオブジェクト。
    *   **黒 (Black)**: 到達可能であり、かつそのオブジェクトが参照しているすべてのオブジェクトもスキャン済みのオブジェクト。
*   **マークフェーズ**: GCの開始時に、ルート（グローバル変数、スタック、レジスタなど）から到達可能なオブジェクトを白から灰へ、そして灰から黒へとマークしていきます。
*   **スイープフェーズ**: マークされなかった白のオブジェクト（到達不可能と判断されたオブジェクト）をメモリから解放します。
*   **並行GC**: GoのGCは、ほとんどのマークフェーズをアプリケーションの実行と並行して行います。これにより、アプリケーションの一時停止（Stop-The-World, STW）時間を最小限に抑えます。

### GCワーカーと`gcWork`

GoのGCは、複数のGCワーカーゴルーチンによって並行して実行されます。これらのワーカーは、マーク作業を分担します。

*   **`gcWork`**: 各GCワーカーがマーク作業を行う際に使用するローカルなバッファです。オブジェクトをスキャンして見つかった参照を一時的にこのバッファに格納し、後で処理します。これにより、グローバルなデータ構造へのアトミック操作の回数を減らし、並行処理の効率を高めます。
*   **`dispose`**: `gcWork`バッファに蓄積された作業（このコミットではマークされたバイト数）を、グローバルなカウンタに集約する操作です。これは、`gcWork`バッファがいっぱいになったり、GCワーカーが一時停止したりする際に呼び出されます。

### P (Processor)

Goランタイムは、OSのスレッドを抽象化した「M」（Machine）と、論理プロセッサを表す「P」（Processor）という概念を持っています。GoのゴルーチンはP上で実行され、PはMにアタッチされます。Pは、スケジューリングやGCワーカーの管理など、ランタイムの重要なコンテキストを保持します。

### アトミック操作 (`xadd64`)

並行処理において、複数のゴルーチンが同時に同じメモリ位置を更新しようとすると、競合状態（Race Condition）が発生し、データの不整合を引き起こす可能性があります。これを防ぐために、アトミック操作が使用されます。

*   **`xadd64`**: Goランタイム内部で使用されるアトミックな加算操作です。これは、指定されたメモリ位置の値を、他のゴルーチンの干渉なしに安全に加算します。このコミットでは、複数のGCワーカーがマークしたバイト数をグローバルな`bytesMarked`カウンタに安全に集約するために使用されます。

### ヒープバイト数とGCトリガー

GoのGCは、ヒープの使用量に基づいてトリガーされます。具体的には、前回のGC終了時のライブヒープサイズ（マークされたバイト数）と、GC目標比率（GOGC環境変数で設定可能、デフォルトは100%）に基づいて、次回のGCがトリガーされるヒープサイズを決定します。このコミットは、この「前回のGC終了時のライブヒープサイズ」をより正確に把握するためのものです。

## 技術的詳細

このコミットの主要な技術的詳細は、GCサイクル中にマークされたヒープバイト数を正確に追跡するためのメカニズムの導入にあります。

1.  **`work.bytesMarked`の導入**:
    *   `src/runtime/mgc.go`内の`work`構造体に`bytesMarked uint64`フィールドが追加されました。これは、現在のGCサイクルでマークされた合計バイト数を保持するグローバルなカウンタです。
    *   このカウンタは、GCサイクルの開始時に`0`にリセットされます。
    *   コミットメッセージにあるように、この値はGCサイクルの終わりにのみ読み取られるため、更新はバッチ処理される可能性があります。

2.  **`gcWork.bytesMarked`の導入と集約**:
    *   `src/runtime/mgcwork.go`内の`gcWork`構造体に`bytesMarked uint64`フィールドが追加されました。これは、個々のGCワーカーがローカルでマークしたバイト数を一時的に保持するためのカウンタです。
    *   GCワーカーがオブジェクトをマークする際、そのオブジェクトのサイズが`gcWork.bytesMarked`に加算されます。
    *   `gcWork.dispose()`および`gcWork.disposeToCache()`メソッドが変更され、`gcWork.bytesMarked`に蓄積された値が、グローバルな`work.bytesMarked`カウンタにアトミックに加算されるようになりました。これは`xadd64`関数を使用して行われます。
    *   コミットメッセージでは、`dispose`が比較的まれに発生するため、グローバルカウンタへの競合は低いと述べられています。しかし、もし問題になるようであれば、`dispose`の頻度を減らすか、各P（プロセッサ）ごとにカウンタを持つように切り替えることが代替案として示唆されています。

3.  **マーク処理におけるバイト数加算**:
    *   `src/runtime/mgcmark.go`内の`scanobject`関数が変更され、スキャンされたオブジェクトのサイズが`gcw.bytesMarked`（現在のGCワーカーのローカルカウンタ）に加算されるようになりました。
    *   `greyobject`関数も変更され、`noscan`オブジェクト（ポインタを含まないオブジェクトで、すぐに黒にマークされるオブジェクト）がマークされる際に、そのサイズが`gcw.bytesMarked`に加算されるようになりました。
    *   `gcmarknewobject_m`関数（GCマーク終了フェーズで新しく割り当てられたオブジェクトをマークする関数）も変更され、新しくマークされたオブジェクトのサイズがグローバルな`work.bytesMarked`に直接アトミックに加算されるようになりました。これは、このフェーズではGCワーカーのローカルバッファを介さずに直接グローバルカウンタを更新するためです。

4.  **ルートとスタックの除外**:
    *   `markroot`関数と`scanstack`関数では、`gcw.bytesMarked`が`0`にリセットされています。これは、ルートオブジェクト（グローバル変数など）やスタック上のオブジェクトはヒープの一部ではないため、マークされたヒープバイト数には含めないという意図を示しています。

この変更により、GoランタイムはGCサイクル中に実際に「生きている」とマークされたヒープメモリの総量を正確に把握できるようになります。この情報は、次回のGCトリガーの決定において、より洗練されたヒューリスティックを適用するための重要な入力となります。例えば、前回のGCでマークされたバイト数が少なかった場合、次回のGCはより遅く開始されることで、GCの頻度を減らし、全体的なパフォーマンスを向上させることができます。

## コアとなるコードの変更箇所

このコミットでは、以下の4つのファイルが変更されています。

1.  **`src/runtime/malloc.go`**:

## コアとなるコードの解説

### `src/runtime/mgc.go`

```go
var work struct {
	// ... 既存のフィールド ...
	totaltime int64

	// bytesMarked is the number of bytes marked this cycle. This
	// includes bytes blackened in scanned objects, noscan objects
	// that go straight to black, and permagrey objects scanned by
	// markroot during the concurrent scan phase. This is updated
	// atomically during the cycle. Updates may be batched
	// arbitrarily, since the value is only read at the end of the
	// cycle.
	//
	// Because of benign races during marking, this number may not
	// be the exact number of marked bytes, but it should be very
	// close.
	bytesMarked uint64
}

// GC runs a garbage collection.
func gc(mode int) {
	// ...
	clearpools()

	work.bytesMarked = 0 // GCサイクル開始時にリセット
	// ...
}
```
`work.bytesMarked`は、GCサイクル全体でマークされたヒープバイトの総数を追跡するためのグローバルカウンタです。GCの開始時に`0`にリセットされます。コメントには、マーク中の競合により厳密な値ではない可能性があるが、非常に近い値であると説明されています。

### `src/runtime/mgcmark.go`

```go
func markroot(desc *parfor, i uint32) {
	// ...
	// Root aren't part of the heap, so don't count them toward
	// marked heap bytes.
	gcw.bytesMarked = 0 // ルートはヒープではないため、カウントしない
	gcw.dispose()
}

func scanstack(gp *g) {
	// ...
	// Stacks aren't part of the heap, so don't count them toward
	// marked heap bytes.
	gcw.bytesMarked = 0 // スタックはヒープではないため、カウントしない
	gcw.disposeToCache()
	gp.gcscanvalid = true
}

func scanobject(b, n uintptr, ptrmask *uint8, gcw *gcWork) {
	// ...
	// Mark the object.
	if obj, hbits, span := heapBitsForObject(obj); obj != 0 {
		greyobject(obj, b, i, hbits, span, gcw)
	}
	gcw.bytesMarked += uint64(n) // スキャンされたオブジェクトのサイズを加算
}

//go:nowritebarrier
func greyobject(obj, base, off uintptr, hbits heapBits, span *mspan, gcw *gcWork) {
	// ...
	// If this is a noscan object, fast-track it to black
	// instead of greying it.
	if hbits.typeBits() == typeDead {
		gcw.bytesMarked += uint64(span.elemsize) // noscanオブジェクトのサイズを加算
		return
	}
	// ...
}

//go:nowritebarrier
func gcmarknewobject_m(obj, size uintptr) {
	if gcphase != _GCmarktermination {
		throw("marking new object while not in mark termination phase")
	}
	// ...
	heapBitsForAddr(obj).setMarked()
	xadd64(&work.bytesMarked, int64(size)) // 新しくマークされたオブジェクトのサイズをグローバルカウンタにアトミックに加算
}
```
`markroot`と`scanstack`では、ヒープ外のメモリをマーク対象から除外するために`gcw.bytesMarked`をリセットしています。`scanobject`では、実際にスキャンされたオブジェクトのサイズを`gcw.bytesMarked`に加算しています。`greyobject`では、`noscan`オブジェクト（ポインタを含まないため、すぐに黒にできるオブジェクト）のサイズも加算しています。`gcmarknewobject_m`は、GCマーク終了フェーズで新しく割り当てられたオブジェクトをマークする際に、そのサイズを直接グローバルな`work.bytesMarked`にアトミックに加算します。

### `src/runtime/mgcwork.go`

```go
type gcWork struct {
	// Invariant: wbuf is never full or empty
	wbuf wbufptr

	// Bytes marked (blackened) on this gcWork. This is aggregated
	// into work.bytesMarked by dispose.
	bytesMarked uint64
}

func (w *gcWork) dispose() {
	// ...
	if w.bytesMarked != 0 {
		// dispose happens relatively infrequently. If this
		// atomic becomes a problem, we should first try to
		// dispose less and if necessary aggregate in a per-P
		// counter.
		xadd64(&work.bytesMarked, int64(w.bytesMarked)) // ローカルカウンタの値をグローバルカウンタにアトミックに集約
		w.bytesMarked = 0
	}
}

func (w *gcWork) disposeToCache() {
	// ...
	if w.bytesMarked != 0 {
		xadd64(&work.bytesMarked, int64(w.bytesMarked)) // ローカルカウンタの値をグローバルカウンタにアトミックに集約
		w.bytesMarked = 0
	}
}
```
`gcWork`構造体に`bytesMarked`フィールドが追加され、各GCワーカーがローカルでマークしたバイト数を保持します。`dispose`および`disposeToCache`メソッドが呼び出される際に、このローカルカウンタの値がグローバルな`work.bytesMarked`に`xadd64`を使ってアトミックに加算されます。これにより、各ワーカーの作業が安全に集約されます。

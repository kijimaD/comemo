## 元コミット内容

このコミットは、`default`ブランチの変更を`dev.garbage`ブランチにマージするものです。主な目的は、「selectdone dangling pointer fix」を含む複数の修正を`dev.garbage`ブランチに取り込むことです。この修正は、Goランタイムの`select`文の処理におけるメモリ管理のバグを解決し、システムの安定性を向上させます。

## 変更の背景

Go言語のランタイムは、並行処理を効率的に管理するために、ゴルーチン（goroutine）とチャネル（channel）という強力なプリミティブを提供しています。`select`文は、複数のチャネル操作を同時に待機し、準備ができた最初の操作を実行するための構文です。この`select`文の内部実装には、`sudog`というランタイム内部のデータ構造が深く関わっています。

過去には、`select`操作が完了した後に`sudog`構造体とその`selectdone`フィールドが適切にクリーンアップされない場合に、「dangling pointer」（宙に浮いたポインタ）の問題が発生することがありました。具体的には、`selectdone`フィールドが、もはや有効ではないメモリ領域を指し続けることで、ランタイムのメモリが破損したり、一貫性のない状態に陥ったりする可能性がありました。これは、`fatal error: runtime: sudog with non-nil selectdone`のような致命的なエラーとして顕在化することがありました（関連するGo issue #11042）。

このコミットは、このようなメモリ管理の不備に起因するバグを修正し、`select`文の堅牢性を高めることを目的としています。`dev.garbage`ブランチは、Goのガベージコレクション（GC）やランタイムの低レベルな変更を実験的に開発するためのブランチであったと考えられ、この重要な修正をそのブランチに統合することで、将来のGoバージョンにおける安定したGCとランタイムの動作を保証しようとしています。

なお、このマージコミットは、提出直後に`linux-amd64-race`ビルダ（レース検出器を含むビルド設定）を壊したという報告があり、その後の修正が必要であったことが示唆されています。これは、ランタイムの低レベルな変更が、他のシステムコンポーネントやビルド設定に予期せぬ影響を与える可能性があることを示しています。

## 前提知識の解説

### Goランタイムと並行処理

Go言語は、軽量なスレッドであるゴルーチンと、ゴルーチン間の安全な通信を可能にするチャネルを言語レベルでサポートしています。Goランタイムは、これらのゴルーチンを効率的にスケジューリングし、マルチコアプロセッサ上で並行に実行するための複雑なメカニズムを内包しています。

### `select`文

`select`文は、複数のチャネル操作（送信または受信）を同時に待機し、そのうちのいずれかが準備できた場合に、その操作を実行するためのGoの構文です。例えば、タイムアウト処理や、複数のデータソースからの入力を処理する際に利用されます。

```go
select {
case <-ch1:
    // ch1から値を受信
case data := <-ch2:
    // ch2から値を受信
case ch3 <- value:
    // ch3へ値を送信
case <-time.After(5 * time.Second):
    // 5秒後にタイムアウト
default:
    // どのチャネルも準備できていない場合
}
```

### `sudog`構造体

`sudog`（scheduler goroutine）は、Goランタイム内部で使用されるデータ構造で、チャネル操作を待機しているゴルーチンを表します。`select`文において、ゴルーチンがチャネル操作を待機する必要がある場合、ランタイムは`sudog`構造体を作成し、それを待機しているチャネルにリンクさせます。`sudog`は、ゴルーチンがどのチャネルで待機しているか、そしてその待機が完了した際にどの`select`ケースが選択されたかなどの情報を保持します。

### `selectdone`フィールド

`selectdone`は、`sudog`構造体または関連するゴルーチン構造体の一部として存在するフィールドです。このフィールドは、`select`操作の完了を調整するために使用されます。複数のチャネルが同時に準備可能になった場合でも、`selectdone`は、どの`select`ケースが最終的に選択され、実行されるかを決定し、他のケースが誤って進行するのを防ぐ役割を担います。

### ダングリングポインタ (Dangling Pointer)

ダングリングポインタとは、解放されたメモリ領域を指し続けているポインタのことです。このメモリ領域は、その後別のデータによって再利用される可能性があるため、ダングリングポインタを介してアクセスすると、予期せぬデータが読み込まれたり、メモリが破損したりする可能性があります。ガベージコレクタがこのようなポインタを検出すると、ランタイムエラーやクラッシュにつながることがあります。

## 技術的詳細

このコミットの核心は、`src/runtime/select.go`における`selectdone`フィールドの取り扱いに関する修正です。以前のコードでは、`gp.waiting`（ゴルーチンが待機している`sudog`のリスト）から`sudog`を切り離す前に、`selectdone`と`elem`フィールドをクリアしていました。しかし、コメントによると、このクリア処理が`sudog`を`sudog`キャッシュに戻す前に行われる必要があり、もし`sudog`がリストから切り離された後にスタックコピーが発生した場合、`selectdone`が古いスタックを指したままになり、ダングリングポインタが発生する可能性がありました。ガベージコレクタがこれを検出すると問題となります。

新しいコードでは、`gp.waiting`から`sudog`を切り離す前に、`sg1.selectdone = nil`という行が追加され、`selectdone`フィールドが明示的に`nil`に設定されるようになりました。これにより、`sudog`がキャッシュに戻される前に`selectdone`が確実にクリアされ、スタックコピーが発生してもダングリングポインタが発生するリスクがなくなります。

この修正は、`select`操作が完了し、ゴルーチンが待機状態から解除された後に、`sudog`構造体が確実にクリーンな状態になることを保証します。これにより、ランタイムのメモリ管理における潜在的な競合状態や不整合が解消され、Goプログラムの安定性が向上します。

このコミットは、`selectdone`の修正以外にも、GoのCコンパイラ（`src/cmd/cc`）の生成ファイル、`fmt`パッケージ、Windows固有のシステムコール関連ファイルなど、広範囲にわたる変更を含んでいます。これは、`default`ブランチから`dev.garbage`ブランチへの大規模なマージであったため、多くのコンポーネントが更新された結果です。

2.  **ダングリングポインタの防止**: `selectdone`が`nil`に設定されることで、`sudog`が`sudog`キャッシュに再利用される際に、古いスタックフレームを指すダングリングポインタが残る可能性がなくなります。これは、Goランタイムがスタックを移動（コピー）する際に、ポインタが更新されないことによる問題を回避するために重要です。ガベージコレクタは、有効なポインタのみを追跡するため、`nil`に設定することで、不正なメモリ参照を排除できます。
3.  **メモリ安全性の向上**: この修正により、`select`文の実行中に発生しうるメモリ破損やランタイムクラッシュのリスクが低減され、Goプログラム全体のメモリ安全性が向上します。

この小さな変更は、Goランタイムの低レベルなメモリ管理と並行処理の複雑さを反映しており、システムの安定性を確保するための重要なバグ修正です。

ダングリングポインタとは、解放されたメモリ領域を指し続けているポインタのことです。このメモリ領域は、その後別のデータによって再利用される可能性があるため、ダングリングポインタを介してアクセスすると、予期せぬデータが読み込まれたり、メモリが破損したりする可能性があります。ガベージコレクタがこのようなポインタを検出すると、ランタイムエラーやクラッシュにつながることがあります。

## 技術的詳細

このコミットの核心は、`src/runtime/select.go`における`selectdone`フィールドの取り扱いに関する修正です。以前のコードでは、`gp.waiting`（ゴルーチンが待機している`sudog`のリスト）から`sudog`を切り離す前に、`selectdone`と`elem`フィールドをクリアしていました。しかし、コメントによると、このクリア処理が`sudog`を`sudog`キャッシュに戻す前に行われる必要があり、もし`sudog`がリストから切り離された後にスタックコピーが発生した場合、`selectdone`が古いスタックを指したままになり、ダングリングポインタが発生する可能性がありました。ガベージコレクタがこれを検出すると問題となります。

新しいコードでは、`gp.waiting`から`sudog`を切り離す前に、`sg1.selectdone = nil`という行が追加され、`selectdone`フィールドが明示的に`nil`に設定されるようになりました。これにより、`sudog`がキャッシュに戻される前に`selectdone`が確実にクリアされ、スタックコピーが発生してもダングリングポインタが発生するリスクがなくなります。

この修正は、`select`操作が完了し、ゴルーチンが待機状態から解除された後に、`sudog`構造体が確実にクリーンな状態になることを保証します。これにより、ランタイムのメモリ管理における潜在的な競合状態や不整合が解消され、Goプログラムの安定性が向上します。

このコミットは、`selectdone`の修正以外にも、GoのCコンパイラ（`src/cmd/cc`）の生成ファイル、`fmt`パッケージ、Windows固有のシステムコール関連ファイルなど、広範囲にわたる変更を含んでいます。これは、`default`ブランチから`dev.garbage`ブランチへの大規模なマージであったため、多くのコンポーネントが更新された結果です。

## コアとなるコードの解説

上記の差分は、`src/runtime/select.go`内の`loop`というラベルが付いたセクション（おそらく`select`文の内部ループ処理の一部）における変更を示しています。

変更前は、`gp.waiting`リストをイテレートしながら、`sudog`構造体（`sg1`）の`selectdone`と`elem`フィールドをクリアしていました。コメントには、「`sudog`キャッシュに戻す前にクリアする必要がある。切り離し後にスタックコピーが発生した場合、古いスタックを指したままになり、ダングリングポインタが発生する可能性があるため、切り離す前にクリアする」と書かれていました。

変更後では、コメントが「`gp.waiting`から切り離す前にすべての`elem`をクリアする」と変更され、ループ内で明示的に`sg1.selectdone = nil`という行が追加されています。

この変更のポイントは以下の通りです。

1.  **`selectdone`の明示的な`nil`化**: 以前は`selectdone`と`elem`をまとめてクリアする意図でしたが、新しいコードでは`sg1.selectdone = nil`が明確に記述されています。これにより、`sudog`が`gp.waiting`リストから切り離される前に、`selectdone`フィールドが確実に`nil`に設定されることが保証されます。
2.  **ダングリングポインタの防止**: `selectdone`が`nil`に設定されることで、`sudog`が`sudog`キャッシュに再利用される際に、古いスタックフレームを指すダングリングポインタが残る可能性がなくなります。これは、Goランタイムがスタックを移動（コピー）する際に、ポインタが更新されないことによる問題を回避するために重要です。ガベージコレクタは、有効なポインタのみを追跡するため、`nil`に設定することで、不正なメモリ参照を排除できます。
3.  **メモリ安全性の向上**: この修正により、`select`文の実行中に発生しうるメモリ破損やランタイムクラッシュのリスクが低減され、Goプログラム全体のメモリ安全性が向上します。

この小さな変更は、Goランタイムの低レベルなメモリ管理と並行処理の複雑さを反映しており、システムの安定性を確保するための重要なバグ修正です。

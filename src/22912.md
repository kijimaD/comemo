# [インデックス 22912] ファイルの概要

このコミットは、Go言語の`image/png`パッケージにおいて、PNG仕様で許可されていない複数の`tRNS`（透過情報）チャンクを含むPNG画像を拒否するように変更を加えるものです。これにより、PNG仕様への準拠を強化し、不正な形式のPNGファイルに対する堅牢性を向上させます。

## 元コミット内容

このコミットは、Go言語の標準ライブラリに含まれる`image/png`パッケージに対して行われた変更です。主な目的は、PNG（Portable Network Graphics）画像のデコード処理において、複数の`tRNS`（Transparency）チャンクが存在する場合にそれを拒否することです。

PNGの公式仕様であるW3Cの「Portable Network Graphics (PNG) Specification」のセクション5「Chunk ordering」では、`tRNS`チャンクは最大で1つしか存在してはならないと明確に規定されています。しかし、これまでの`image/png`パッケージの実装では、この制約が十分に適用されておらず、複数の`tRNS`チャンクを持つ不正なPNGファイルを正常にデコードしてしまう可能性がありました。

この問題は、GoのIssueトラッカーで`#10423`として報告されており、本コミットはその問題を修正するために導入されました。変更は、`src/image/png/reader.go`におけるPNGチャンクのパースロジックと、それに対応するテストケースを`src/image/png/reader_test.go`に追加することで実現されています。

具体的には、デコードステージに`dsSeentRNS`という新しい状態が追加され、`tRNS`チャンクが既に一度検出されている場合に再度検出されたらエラーを返すようにロジックが修正されています。また、パレット化された画像（インデックスカラー画像）の処理に関連するロジックも、より汎用的なヘルパー関数`cbPaletted`を使用するようにリファクタリングされています。

## 変更の背景

この変更の背景には、PNG画像の仕様遵守と、それによってもたらされるセキュリティおよび堅牢性の向上が挙げられます。

PNGは、可逆圧縮を特徴とするビットマップ画像フォーマットであり、ウェブやグラフィックアプリケーションで広く利用されています。その仕様は、W3Cによって厳密に定義されており、各チャンクの役割、構造、そして出現順序や回数に関するルールが定められています。

`tRNS`チャンクは、PNG画像における透過情報を定義するために使用されます。パレットベースの画像ではパレットエントリごとのアルファ値を、グレースケール画像やRGB画像では単一の透過色を定義します。この`tRNS`チャンクは、画像ごとに最大で1つしか存在してはならないという明確なルールがPNG仕様（特に[http://www.w3.org/TR/PNG/#5ChunkOrdering](http://www.w3.org/TR/PNG/#5ChunkOrdering)）で定められています。

しかし、Goの`image/png`パッケージの以前の実装では、この「`tRNS`チャンクは1つのみ」という制約が適切にチェックされていませんでした。その結果、複数の`tRNS`チャンクを含む不正なPNGファイルが入力された場合でも、エラーを発生させずにデコード処理を進めてしまう可能性がありました。このような挙動は、以下のような問題を引き起こす可能性があります。

1.  **仕様不遵守**: PNG仕様に準拠しないファイルを「有効」とみなしてしまうため、他のPNGパーサーとの互換性問題や、予期せぬ挙動を引き起こす可能性があります。
2.  **セキュリティリスク**: 不正な形式のファイルが、意図しない方法で処理されることで、サービス拒否（DoS）攻撃や、メモリ破損などの脆弱性につながる可能性があります。特に、画像処理ライブラリは、外部からの信頼できない入力を扱うことが多いため、堅牢性が非常に重要です。
3.  **デバッグの困難さ**: 不正なファイルがエラーなく処理されると、問題の根本原因を特定するのが難しくなります。

このコミットは、これらの問題を解決するために、`image/png`パッケージがPNG仕様に厳密に準拠し、複数の`tRNS`チャンクを持つファイルを明確に拒否するように修正を加えるものです。これにより、ライブラリの堅牢性と信頼性が向上します。

## 前提知識の解説

このコミットの理解を深めるために、以下の前提知識が必要です。

### 1. PNG (Portable Network Graphics) フォーマット

PNGは、可逆圧縮を特徴とするビットマップ画像フォーマットです。ウェブ上で広く利用されており、透過性（アルファチャンネル）をサポートします。PNGファイルは、一連の「チャンク」と呼ばれるデータブロックで構成されています。

### 2. PNGチャンクの構造と種類

PNGファイルは、シグネチャ（ファイルの先頭にある固定バイト列）に続き、複数のチャンクが連続して配置されます。各チャンクは以下の構造を持ちます。

*   **Length (4バイト)**: チャンクのデータ部分のバイト数。
*   **Chunk Type (4バイト)**: チャンクの種類を示すASCII文字列（例: `IHDR`, `PLTE`, `IDAT`, `tRNS`, `IEND`）。
*   **Chunk Data (Lengthバイト)**: チャンクの実際のデータ。
*   **CRC (4バイト)**: Chunk TypeとChunk DataのCRC-32チェックサム。データの破損を検出するために使用されます。

主要なチャンクには以下のようなものがあります。

*   **IHDR (Image Header)**: 必須チャンク。画像の幅、高さ、ビット深度、カラータイプ、圧縮方式、フィルタ方式、インターレース方式などの基本情報を含みます。ファイル内で最初に現れるチャンクです。
*   **PLTE (Palette)**: パレットベースの画像（カラータイプ3）の場合に必須。パレットエントリ（RGB値）のリストを含みます。
*   **tRNS (Transparency)**: 透過情報を定義するオプションチャンク。
    *   パレットベースの画像（カラータイプ3）の場合：PLTEチャンクの各エントリに対応するアルファ値のリスト。
    *   グレースケール画像（カラータイプ0, 4）の場合：単一の透過グレースケール値。
    *   RGB画像（カラータイプ2, 6）の場合：単一の透過RGB値。
    **重要**: PNG仕様では、`tRNS`チャンクは最大で1つしか存在してはならないと規定されています。
*   **IDAT (Image Data)**: 必須チャンク。画像ピクセルデータを含みます。通常、複数のIDATチャンクが連続して存在し、それらを連結してデコードすることで完全な画像データが得られます。
*   **IEND (Image End)**: 必須チャンク。PNGファイルの終わりを示します。ファイル内で最後に現れるチャンクです。

### 3. PNGチャンクの順序

PNG仕様では、チャンクの出現順序にも厳密なルールがあります。特に、以下の順序が必須とされています。

`IHDR` -> (`PLTE` (もしあれば)) -> (`tRNS` (もしあれば)) -> `IDAT` -> `IEND`

また、`IDAT`チャンクは連続して出現する必要があり、他のチャンクが`IDAT`チャンクの間に割り込むことはできません。

### 4. Go言語の `image/png` パッケージ

Go言語の標準ライブラリには、画像処理のための`image`パッケージと、特定の画像フォーマット（JPEG, PNG, GIFなど）を扱うためのサブパッケージが含まれています。`image/png`パッケージは、PNG形式の画像をエンコードおよびデコードするための機能を提供します。

*   **`Decode(r io.Reader) (image.Image, error)`**: `io.Reader`からPNG画像をデコードし、`image.Image`インターフェースを実装する画像オブジェクトを返します。
*   **`DecodeConfig(r io.Reader) (image.Config, error)`**: `io.Reader`からPNG画像の構成情報（幅、高さ、カラーモデルなど）のみをデコードします。画像データ全体を読み込む必要がない場合に便利です。

このコミットでは、主に`image/png`パッケージ内のデコード処理、特にチャンクのパースと順序チェックを行う部分が変更されています。

## 技術的詳細

このコミットは、`src/image/png/reader.go`と`src/image/png/reader_test.go`の2つのファイルに影響を与えています。

### `src/image/png/reader.go` の変更

1.  **`cbPaletted` ヘルパー関数の追加**:
    *   以前は、パレット化されたカラータイプ（`cbP1`, `cbP2`, `cbP4`, `cbP8`）をチェックするために、複数の`||`演算子を用いた冗長な条件式が使われていました。
    *   新しく`func cbPaletted(cb int) bool`関数が追加され、このチェックをカプセル化しました。これにより、コードの可読性と保守性が向上しています。

2.  **デコードステージ定数 `dsSeentRNS` の追加**:
    *   PNGデコード処理は、チャンクの出現順序を追跡するために内部的な「ステージ」を使用します。
    *   `const`ブロックに`dsSeentRNS`という新しいステージが追加されました。これは、`tRNS`チャンクが既に検出されたことを示す状態です。
    *   既存のステージ定数（`dsStart`, `dsSeenIHDR`, `dsSeenPLTE`, `dsSeenIDAT`, `dsSeenIEND`）の間に挿入され、`PLTE`の後に`tRNS`が来るというPNG仕様の順序を反映しています。

3.  **`parseChunk` メソッドの変更**:
    *   このメソッドは、PNGファイルからチャンクを読み込み、そのタイプに基づいて適切なパース処理を行う中心的なロジックです。
    *   **`tRNS`チャンクの処理**:
        *   `case "tRNS":`ブロック内で、`d.stage != dsSeenPLTE`という条件が追加されました。これは、`tRNS`チャンクが`PLTE`チャンクの直後に（または`PLTE`がない場合は`IHDR`の直後に）出現しなければならないという仕様を強制します。
        *   最も重要な変更は、`d.stage = dsSeentRNS`という行が追加されたことです。これにより、`tRNS`チャンクが一度パースされた後、デコーダの状態が`dsSeentRNS`に遷移します。
        *   この状態遷移により、もしファイル内に2つ目の`tRNS`チャンクが出現した場合、`parseChunk`メソッドは`chunkOrderError`を返すようになります。これは、`tRNS`チャンクが`dsSeentRNS`ステージで再度検出されると、`d.stage != dsSeenPLTE`（または`d.stage < dsSeenIHDR`など）の条件に合致しなくなるためです。
    *   **`IDAT`チャンクの処理**:
        *   `case "IDAT":`ブロック内の条件式が変更されました。以前は`d.stage == dsSeenIHDR && d.cb == cbP8`という特定の条件でパレット化された画像に対するチェックを行っていましたが、これが`d.stage == dsSeenIHDR && cbPaletted(d.cb)`に置き換えられました。
        *   これは、`cbPaletted`ヘルパー関数を使用することで、より汎用的かつ明確なチェックになっています。`IDAT`チャンクは、`IHDR`、`PLTE`、`tRNS`のいずれかの後に来る必要がありますが、パレット化された画像の場合、`IDAT`が`IHDR`の直後に来ることは許されません（`PLTE`と`tRNS`が間に必要）。

4.  **`DecodeConfig` 関数の変更**:
    *   この関数は、PNG画像のヘッダ情報のみをデコードします。
    *   `paletted := d.cb == cbP8 || d.cb == cbP4 || d.cb == cbP2 || d.cb == cbP1`という行が、新しく追加された`paletted := cbPaletted(d.cb)`に置き換えられました。これにより、コードの重複が排除され、一貫性が保たれています。

### `src/image/png/reader_test.go` の変更

1.  **`TestMultipletRNSChunks` テストケースの追加**:
    *   このテストは、複数の`tRNS`チャンクを含むPNGファイルが正しく拒否されることを検証するために追加されました。
    *   テストは、有効な1x1のパレット化されたPNG画像のバイト列をベースに、`tRNS`チャンクの数を0個、1個、2個、3個と変化させてテストデータを生成します。
    *   **0個の`tRNS`チャンク**: デコードが成功し、アルファ値がデフォルトの`0xff`（完全に不透明）になることを期待します。
    *   **1個の`tRNS`チャンク**: デコードが成功し、`tRNS`チャンクで指定されたアルファ値（このテストケースでは`0x7f`）が適用されることを期待します。
    *   **2個以上の`tRNS`チャンク**: PNG仕様に違反するため、デコードが失敗し、エラーが返されることを期待します。
    *   このテストは、`bytes.NewReader`を使用してバイト列から画像をデコードし、`Decode`関数が期待通りの結果（画像オブジェクトまたはエラー）を返すことを確認します。また、デコードされた画像のピクセルデータが正しいアルファ値を持つことも検証しています。

これらの変更により、`image/png`パッケージはPNG仕様の`tRNS`チャンクに関する制約を厳密に適用し、不正な形式のファイルに対する処理をより堅牢にしています。

## コアとなるコードの解説

### `src/image/png/reader.go`

1.  **`func cbPaletted(cb int) bool`**:
    *   この関数は、与えられたカラータイプ`cb`がパレット化された画像（インデックスカラー画像）に属するかどうかを判定します。
    *   PNG仕様では、カラータイプ1, 2, 4, 8がパレット化された画像に対応します。この関数は、これらのカラータイプを効率的にチェックするためのユーティリティとして導入されました。
    *   これにより、コードの重複が減り、`d.cb == cbP8 || d.cb == cbP4 || d.cb == cbP2 || d.cb == cbP1`のような冗長な条件式が`cbPaletted(d.cb)`という簡潔な表現に置き換えられました。

2.  **`const ( ... dsSeentRNS ... )`**:
    *   `dsSeentRNS`は、PNGデコード処理の内部状態を表す新しい定数です。
    *   デコーダは、PNGチャンクを読み込む際に、そのチャンクがPNG仕様で定められた順序で出現しているかを検証します。このために、`d.stage`というフィールドで現在のデコードステージを管理しています。
    *   `dsSeentRNS`が追加されたことで、`tRNS`チャンクが既に処理されたことをデコーダが記憶できるようになりました。

3.  **`case "tRNS":` ブロック内の変更**:
    *   `d.stage = dsSeentRNS`という行が追加されました。これは、`tRNS`チャンクが正常にパースされた直後に、デコーダのステージを`dsSeentRNS`に更新することを意味します。
    *   この変更により、もし同じPNGファイル内に2つ目の`tRNS`チャンクが出現した場合、`parseChunk`メソッドは`d.stage`が既に`dsSeentRNS`であるため、`chunkOrderError`を返すようになります。これは、PNG仕様が複数の`tRNS`チャンクを許可していないため、正しい挙動です。

4.  **`case "IDAT":` ブロック内の条件式の変更**:
    *   `if d.stage < dsSeenIHDR || d.stage > dsSeenIDAT || (d.stage == dsSeenIHDR && cbPaletted(d.cb))`
    *   この条件式は、`IDAT`チャンクが出現する際のデコードステージの妥当性をチェックします。
    *   特に注目すべきは、`(d.cb == cbP8 && d.stage == dsSeenIHDR)`が`(d.stage == dsSeenIHDR && cbPaletted(d.cb))`に置き換えられた点です。
    *   これは、パレット化された画像（`cbPaletted(d.cb)`がtrueの場合）において、`IDAT`チャンクが`IHDR`チャンクの直後に出現することは許可されない（`PLTE`チャンクや`tRNS`チャンクが間に必要）というPNG仕様のルールをより正確に、かつ汎用的に適用するための変更です。

5.  **`DecodeConfig` 関数内の変更**:
    *   `paletted := cbPaletted(d.cb)`
    *   ここでも、`cbPaletted`ヘルパー関数が使用され、パレット化された画像であるかどうかのチェックが簡潔になりました。これは、`DecodeConfig`が画像の基本情報を取得する際に、カラータイプに基づいて特定の処理を行う必要があるためです。

### `src/image/png/reader_test.go`

1.  **`TestMultipletRNSChunks` 関数の追加**:
    *   このテスト関数は、PNGデコーダが複数の`tRNS`チャンクを正しく拒否することを確認するためのものです。
    *   テストデータとして、PNGヘッダ、`IHDR`、`PLTE`、`IDAT`、`IEND`チャンクのバイト列が定数として定義されています。
    *   ループ内で、`tRNS`チャンクを0回、1回、2回、3回と異なる回数で挿入したPNGバイト列を動的に生成します。
    *   `Decode(bytes.NewReader(b))`を呼び出して、生成されたバイト列をデコードします。
    *   **`i == 0` (tRNSチャンクなし)**: エラーが発生しないこと、およびデコードされた画像のアルファ値がデフォルトの不透明（`0xff`）であることを検証します。
    *   **`i == 1` (tRNSチャンクが1つ)**: エラーが発生しないこと、およびデコードされた画像のアルファ値が`tRNS`チャンクで指定された値（`0x7f`）であることを検証します。
    *   **`i >= 2` (tRNSチャンクが複数)**: PNG仕様違反のため、`Decode`関数がエラーを返すことを検証します。
    *   このテストは、コミットによって導入された`tRNS`チャンクの複数回出現に対する拒否ロジックが正しく機能していることを、具体的なテストケースで保証します。

これらのコード変更は、PNG仕様の厳密な遵守を目的としており、特に`tRNS`チャンクの出現回数に関する制約を強制することで、`image/png`パッケージの堅牢性と信頼性を向上させています。

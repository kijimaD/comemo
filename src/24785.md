# [インデックス 24785] ファイルの概要

このコミットは、Goリンカ（`cmd/link`）におけるARM64アーキテクチャ向けのリロケーション処理を改善するものです。具体的には、リロケーション対象の値を`archreloc`関数に直接渡すように変更し、ARM64のリロケーションロジック、特に`R_CALLARM64`および`R_ADDRARM64`タイプのリロケーションにおける処理の混乱を解消しています。これにより、リロケーションのセマンティクスがより明確になり、将来的なリンカの改善や異なるアーキテクチャへの対応が容易になります。

## 変更の背景

この変更の背景には、Goリンカにおけるリロケーション処理、特に`obj.Reloc`構造体の`Add`フィールドのセマンティクスに関する混乱がありました。以前のリンカでは、`Reloc.Add`フィールドが純粋な加算値（オフセット）としてだけでなく、リロケーション対象の命令の一部をエンコードするためにも使用されることがありました。これは、特にARM64のような複雑な命令セットを持つアーキテクチャにおいて、リロケーション処理のロジックを複雑にし、バグの原因となる可能性がありました。

Issue #10050「liblink, cmd/ld: don't encode the instruction being relocated in Reloc.add」は、この問題点を明確に指摘しています。このイシューは、`Reloc.Add`がリロケーション対象の命令自体ではなく、純粋な加算値としてのみ扱われるべきであると提唱していました。

このコミットは、この問題に対処するために、`archreloc`関数にリロケーション対象の値を直接`*val`引数として渡すように変更しました。これにより、`archreloc`関数は、`Reloc.Add`に依存することなく、リロケーション対象の命令の現在の値を読み取り、変更できるようになります。結果として、`Reloc.Add`は純粋な加算値としてのみ機能するようになり、リンカのコードベース全体の整合性と可読性が向上します。特にARM64アーキテクチャにおけるリロケーション処理の「混乱 (mess)」を解消することを目的としています。

## 前提知識の解説

### Goリンカ (`cmd/link`)

Go言語のコンパイルプロセスにおいて、`cmd/link`はオブジェクトファイル（`.o`ファイル）を結合し、実行可能ファイルや共有ライブラリを生成する役割を担うプログラムです。このプロセスには、シンボルの解決や、コード内のアドレス参照を実際のメモリ位置に調整する「リロケーション」が含まれます。

### リロケーション (Relocation)

リロケーションとは、プログラムがメモリにロードされる際に、コードやデータ内のアドレス参照を修正するプロセスです。コンパイル時には、関数呼び出しやデータアクセスのアドレスは相対的なものや仮のものであり、最終的な実行可能ファイルが生成される際に、リンカがこれらのアドレスを実際のメモリ位置に合わせて調整します。リロケーションエントリは、どの場所をどのように修正すべきかをリンカに指示します。

### `obj.Reloc`構造体

Goのリンカ内部では、リロケーション情報は`obj.Reloc`構造体で表現されます。この構造体には、リロケーションの種類（`Type`）、オフセット（`Off`）、サイズ（`Siz`）、関連するシンボル（`Sym`）、そして加算値（`Add`）などのフィールドが含まれます。
*   `Type`: リロケーションの種類（例: `R_CALLARM64`, `R_ADDRARM64`）。
*   `Off`: リロケーションが適用されるセクション内のオフセット。
*   `Siz`: リロケーションが適用されるデータのサイズ（バイト単位）。
*   `Sym`: リロケーションのターゲットとなるシンボル。
*   `Add`: リロケーション計算に加算される値。このフィールドのセマンティクスが今回の変更の焦点です。

### `archreloc`関数

`archreloc`は、Goリンカ内でアーキテクチャ固有のリロケーション処理を行う関数です。異なるCPUアーキテクチャ（例: x86-64, ARM64）は、それぞれ独自のリロケーション規則や命令フォーマットを持つため、この関数がそれらの違いを吸収し、適切なリロケーション処理を適用します。

### ARM64アーキテクチャのリロケーション

ARM64（AArch64）は、64ビットのRISCアーキテクチャであり、その命令セットは固定長で、アドレス指定モードも特定の形式に従います。特に、関数呼び出し（`BL`命令など）やアドレスロード（`ADRP`/`ADD`命令ペアなど）に関するリロケーションは、命令の特定のビットフィールドにオフセットをエンコードする必要があるため、複雑になることがあります。
*   `R_CALLARM64`: ARM64の関数呼び出し命令（`BL`など）に対するリロケーション。呼び出し先のアドレスを命令のオフセットフィールドにエンコードします。
*   `R_ADDRARM64`: ARM64のアドレス参照に対するリロケーション。通常、`ADRP`（アドレスページをロード）と`ADD`（ページ内オフセットを加算）の命令ペアと組み合わせて使用され、64ビットアドレスを2つの命令に分割してエンコードします。

### エンディアン (Endianness)

エンディアンとは、複数バイトのデータをメモリに格納する際のバイト順序のことです。
*   **ビッグエンディアン**: 最上位バイトが最も小さいアドレスに格納されます。
*   **リトルエンディアン**: 最下位バイトが最も小さいアドレスに格納されます。
Goリンカは、ターゲットアーキテクチャのエンディアンを考慮して、メモリからのバイト列の読み書きや、バイト列から数値への変換を行います。`ld.Thelinkarch.ByteOrder`や`ld.Ctxt.Arch.ByteOrder`がこれらを管理します。

## 技術的詳細

このコミットの主要な技術的変更点は、`archreloc`関数のシグネチャと、それに伴うリロケーション処理のロジックの変更です。

1.  **`archreloc`関数のシグネチャ変更と`val`引数の導入**:
    *   以前の`archreloc`関数は、リロケーション情報（`r *ld.Reloc`）とシンボル情報（`s *ld.LSym`）を受け取り、リロケーション計算の結果を`r.Add`フィールドに格納したり、`s.P`（シンボルのバイト列）を直接操作したりしていました。
    *   このコミットでは、`func archreloc(r *ld.Reloc, s *ld.LSym, val *int64) int` のように、`val *int64`という新しい引数が追加されました。この`val`は、リロケーションが適用されるメモリ位置の現在の64ビット値を指すポインタです。
    *   これにより、`archreloc`関数は、リロケーション対象の命令やデータの現在の値を直接読み取り（`*val`）、それを変更して書き戻すことができるようになりました。これは、`Reloc.Add`が命令の一部をエンコードするのではなく、純粋な加算値としてのみ機能するというセマンティクスを強制する上で非常に重要です。

2.  **`Reloc.Add`フィールドのセマンティクス変更**:
    *   `src/cmd/internal/obj/arm64/asm7.go`の`R_CALLARM64`リロケーションの箇所で、`rel.Add = int64(o1) | (p.To.Offset>>2)&0x3ffffff` から `rel.Add = p.To.Offset` に変更されています。これは、`Reloc.Add`が命令のオフセット部分を直接エンコードするのではなく、純粋なオフセット値（加算値）としてのみ設定されるようになったことを示しています。命令のエンコードは、リンカの後半ステージで行われるべきであり、`Reloc.Add`の役割ではないという原則に沿った変更です。

3.  **`src/cmd/link/internal/ld/data.go`における`relocsym`関数の変更**:
    *   `relocsym`関数は、各シンボル内のリロケーションエントリを処理する主要な場所です。
    *   この変更により、`archreloc`を呼び出す前に、リロケーション対象のメモリ位置から現在の値（`o`）を読み込み、それを`archreloc`に`&o`として渡すようになりました。
    *   `switch siz`ブロックが追加され、リロケーションのサイズ（1, 2, 4, 8バイト）に応じて、`s.P[off:]`から適切なバイトオーダーで値を読み込むようになっています。これにより、`archreloc`は常にリロケーション対象の現在の値を受け取って処理できるようになります。

4.  **ARM64固有のリロケーション処理のクリーンアップ (`src/cmd/link/internal/arm64/asm.go`)**:
    *   **`R_ADDRARM64`リロケーション**:
        *   以前は、`s.P[r.Off : r.Off+4]`などから命令のバイト列を直接読み取って`o0`, `o1`を構築していました。
        *   変更後は、`*val`から`o0`, `o1`を抽出するようになりました。これにより、`archreloc`は、`val`が指すメモリ位置の現在の命令値を操作するようになります。
        *   Mach-O (Darwin) 向けの特殊な処理ブロックも、`*val`を基に`o0`, `o1`を初期化するように変更されています。
    *   **`R_CALLARM64`リロケーション**:
        *   以前は、`*val = int64(0xfc000000 & uint32(r.Add))` のように、`r.Add`から命令の一部を抽出し、`r.Xadd`にオフセットを格納していました。
        *   変更後は、`r.Xadd = r.Add` となり、`Reloc.Add`が純粋な加算値として`r.Xadd`に渡されるようになりました。
        *   `*val |= (t >> 2) & 0x03ffffff` のように、計算された相対オフセット`t`を直接`*val`（命令値）に適用するようになりました。これにより、`archreloc`が命令の値を直接修正する責任を持つことが明確になります。

これらの変更により、`Reloc.Add`は純粋な加算値としてのみ機能し、アーキテクチャ固有のリロケーション処理は、リロケーション対象の現在の値を直接操作する、より明確で一貫性のある方法で行われるようになりました。これにより、リンカのコードベースの理解と保守が容易になり、将来的な拡張性も向上します。

## コアとなるコードの解説

### `src/cmd/internal/obj/arm64/asm7.go`の変更

*   **`rel.Add = p.To.Offset`**:
    *   この変更は、アセンブラが`R_CALLARM64`タイプのリロケーションを作成する際に、`Reloc.Add`フィールドに純粋なターゲットオフセット（`p.To.Offset`）を格納するようにします。
    *   以前は、`o1`（命令の一部）とオフセットの一部をビット演算で結合して`rel.Add`に格納していましたが、これは`Reloc.Add`が純粋な加算値であるべきという原則に反していました。この修正により、`Reloc.Add`のセマンティクスが明確化され、リンカの後半ステージで命令のエンコードが行われるようになります。

### `src/cmd/link/internal/arm64/asm.go`の変更

*   **`archreloc`関数の`val *int64`引数の利用**:
    *   `R_ADDRARM64`リロケーションの処理において、以前は`s.P`（シンボルのバイト列）から直接命令のバイトを読み取って`o0`, `o1`（命令の各部分）を構築していました。
    *   変更後は、`*val`（リロケーション対象の現在の64ビット値）から`o0`, `o1`を抽出するようになりました。これにより、`archreloc`は、リンカが既にメモリから読み込んだ命令の値を操作するようになり、`s.P`への直接アクセスが不要になります。
    *   Mach-O (Darwin) 向けの特殊な処理ブロック内でも同様に、`*val`から`o0`, `o1`を初期化するように変更されています。
    *   最終的に、変更された`o0`, `o1`を結合して`*val`に書き戻すことで、リロケーションが適用された新しい命令値がメモリに反映されます。
*   **`R_CALLARM64`リロケーションの簡素化**:
    *   以前は、`r.Add`から命令の一部を抽出し、`*val`に格納していましたが、これは`Reloc.Add`の誤用でした。
    *   変更後は、`r.Xadd = r.Add` となり、`Reloc.Add`が純粋な加算値として`r.Xadd`に渡されます。
    *   `t := (ld.Symaddr(r.Sym) + r.Add) - (s.Value + int64(r.Off))` でターゲットアドレスと現在の命令位置からの相対オフセット`t`を計算します。
    *   `*val |= (t >> 2) & 0x03ffffff` により、計算された相対オフセット`t`を、`*val`が指す命令の適切なビットフィールドに直接書き込みます。これにより、`archreloc`が命令の値を直接修正する責任を持つことが明確になり、`Reloc.Add`の役割が純粋な加算値に限定されます。

### `src/cmd/link/internal/ld/data.go`の変更

*   **`relocsym`関数における`val`引数の準備**:
    *   `archreloc`関数が`val *int64`引数を受け取るようになったため、`relocsym`関数は`archreloc`を呼び出す前に、リロケーション対象のメモリ位置から現在の値（`o`）を読み込む必要があります。
    *   新しい`switch siz`ブロックは、リロケーションのサイズ（1, 2, 4, 8バイト）に基づいて、`s.P[off:]`から適切なバイトオーダーで値を読み込み、`o`に格納します。
    *   この`o`のアドレスが`&o`として`Thearch.Archreloc`（つまり`archreloc`）に渡されます。これにより、`archreloc`は常にリロケーション対象の現在の値を受け取って処理できるようになり、リロケーション処理の整合性が保たれます。

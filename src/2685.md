## 元コミット内容

`wait`ステータスにおける`SIGTRAP`の原因にアクセスするアクセサを追加。

## 変更の背景

Linuxシステムでは、`waitpid`や`wait4`といったシステムコールを使用して子プロセスの状態変化（終了、停止、再開など）を監視します。これらのシステムコールは、子プロセスの状態を示す整数値（`wait status`）を返します。特に、プロセスが`SIGTRAP`シグナルによって停止した場合、この`wait status`には`SIGTRAP`の原因に関する追加情報が含まれることがあります。

`SIGTRAP`は、主にデバッグ目的で使用されるシグナルです。例えば、`ptrace`システムコールを使用してプロセスをトレースしているデバッガは、ブレークポイントに到達したり、シングルステップ実行が完了したりした際に、トレース対象プロセスから`SIGTRAP`を受け取ります。この`SIGTRAP`がどのような理由で発生したのか（例えば、`PTRACE_EVENT_FORK`のような`ptrace`イベントによるものか、通常のブレークポイントによるものかなど）は、`wait status`の下位バイトにエンコードされたトラップコードによって示されます。

このコミット以前は、Goの`syscall`パッケージには`WaitStatus`から`SIGTRAP`の原因を直接抽出する便利なメソッドがありませんでした。デバッガやプロファイラのようなツールをGoで実装する際、この情報にアクセスできないと、`SIGTRAP`の発生理由を特定するのが困難でした。この変更は、そのようなツールが`SIGTRAP`の具体的な原因をプログラム的に判別できるようにするために導入されました。

## 前提知識の解説

### 1. Linuxのプロセス状態と`wait`システムコール

Linuxでは、親プロセスは`waitpid`や`wait4`などのシステムコールを使って子プロセスの状態変化を待ちます。これらの関数は、子プロセスのPIDと、その状態を示す整数値（`wait status`）を返します。`wait status`はビットフィールドであり、様々なマクロ（`WIFEXITED`, `WEXITSTATUS`, `WIFSIGNALED`, `WTERMSIG`, `WIFSTOPPED`, `WSTOPSIG`など）を使って解析されます。

### 2. `SIGTRAP`シグナル

`SIGTRAP`（Signal Trap）は、プログラムの実行中に特定のイベントが発生した際にカーネルによってプロセスに送信されるシグナルです。主にデバッグやトレースの目的で使用されます。
*   **ブレークポイント:** デバッガが設定したブレークポイントに到達すると、CPUは`INT3`命令（x86の場合）などを実行し、カーネルが`SIGTRAP`をデバッグ対象プロセスに送信します。
*   **シングルステップ実行:** デバッガがプログラムを1命令ずつ実行させる際、各命令の実行後に`SIGTRAP`が発生します。
*   **`ptrace`イベント:** `ptrace`システムコールを使ってプロセスをトレースしている場合、`fork`, `exec`, `exit`などの特定のシステムコールイベントが発生した際に、カーネルは`SIGTRAP`を送信し、デバッガに通知します。この`SIGTRAP`は、通常のブレークポイントによる`SIGTRAP`とは異なる「原因」を持ちます。

### 3. `ptrace`システムコール

`ptrace`は、プロセスをトレース（監視・制御）するためのLinuxシステムコールです。デバッガ（例: GDB）はこれを利用して、プロセスのメモリやレジスタを読み書きしたり、実行を一時停止・再開したりします。`ptrace`によってトレースされているプロセスが特定のイベント（システムコール呼び出し、シグナル受信など）に遭遇すると、カーネルはトレース対象プロセスを停止させ、`SIGTRAP`を送信してデバッガに通知します。この際、`wait status`には`SIGTRAP`の原因を示す追加情報が格納されます。

### 4. `WaitStatus`の構造と`SIGTRAP`の原因エンコーディング

Linuxの`wait status`は、通常16ビットまたは32ビットの整数で、そのビットパターンによって様々な情報がエンコードされています。
プロセスがシグナルによって停止した場合（`WIFSTOPPED`が真の場合）、`WSTOPSIG`マクロで停止シグナル（例: `SIGTRAP`）を取得できます。
`SIGTRAP`の場合、さらにその原因を示す情報が`wait status`の下位バイト（通常は`WSTOPSIG`が取得するバイトの次のバイト）にエンコードされていることがあります。これは`ptrace`イベントのタイプ（`PTRACE_EVENT_FORK`, `PTRACE_EVENT_VFORK`, `PTRACE_EVENT_EXEC`, `PTRACE_EVENT_EXIT`, `PTRACE_EVENT_SECCOMP`, `PTRACE_EVENT_STOP`など）を示す値です。これらの値は、`ptrace`のmanページやLinuxカーネルのソースコードで定義されています。

具体的には、`wait status`の構造は以下のようになっています（一般的なLinuxシステムの場合）：
*   下位8ビット: シグナル番号（プロセスが終了した場合）または停止シグナル（プロセスが停止した場合）
*   次の8ビット: `SIGTRAP`のトラップコード（`ptrace`イベントなど）または終了コード（プロセスが終了した場合）
*   上位ビット: その他のフラグ

このコミットでは、`WaitStatus`の`shift`定数（通常は8ビットシフト）を利用して、`SIGTRAP`の原因が格納されているバイトを抽出しています。

## 技術的詳細

このコミットは、`src/pkg/syscall/syscall_linux.go`ファイルに`WaitStatus`型に対する新しいメソッド`TrapCause()`を追加します。

`WaitStatus`は、Linuxの`wait4`システムコールが返すプロセスの状態情報をGo言語で表現するための型です。この型は、C言語の`wait status`整数値をラップしており、`StopSignal()`などの既存のメソッドを通じて、プロセスがどのシグナルによって停止したかなどを判別できます。

新しく追加された`TrapCause()`メソッドのロジックは以下の通りです。

1.  **`SIGTRAP`の確認**:
    まず、`w.StopSignal() != SIGTRAP`という条件で、現在の`WaitStatus`が`SIGTRAP`によってプロセスが停止した状態であるかどうかを確認します。`StopSignal()`は、プロセスを停止させたシグナル番号を返します。
    もし`SIGTRAP`で停止した状態でない場合、`TrapCause()`は`-1`を返します。これは、`SIGTRAP`の原因を問い合わせる意味がないため、エラーまたは無効な状態を示す値として機能します。

2.  **トラップコードの抽出**:
    `SIGTRAP`によって停止した状態である場合、`wait status`の整数値からトラップコードを抽出します。
    `int(w >> shift) >> 8`という式が使われています。
    *   `w >> shift`: `WaitStatus`の内部表現`w`を`shift`ビット（通常は8ビット）右シフトします。これにより、下位8ビット（停止シグナルが格納されている部分）が取り除かれ、次の8ビット（トラップコードが格納されている部分）が最下位バイトに移動します。
    *   `>> 8`: さらに8ビット右シフトします。これは、`wait status`の構造が`WSTOPSIG`が下位8ビット、その次の8ビットが`SIGTRAP`のトラップコード、という並びになっていることを示唆しています。`shift`が8の場合、`w >> shift`は`WSTOPSIG`の次のバイトを最下位バイトに持ってくるはずです。その値をさらに8ビット右シフトするということは、`WaitStatus`の内部表現が`[上位バイト][トラップコード][停止シグナル]`のような構造で、`shift`が停止シグナル部分のサイズ（8ビット）を指していると仮定すると、`w >> shift`で`[上位バイト][トラップコード]`が得られ、それをさらに`>> 8`することで`[上位バイト]`が取り除かれ、`トラップコード`が最下位バイトに移動するという計算になります。
    *   最終的に、この計算結果が`int`型にキャストされ、`SIGTRAP`の原因を示す整数値として返されます。この値は、`ptrace`イベント（例: `PTRACE_EVENT_FORK`など）に対応する定数と比較することで、具体的な`SIGTRAP`の原因を特定するために使用されます。

この変更により、GoプログラムからLinuxの`ptrace`イベントをより詳細に処理できるようになり、デバッガやプロファイラなどのシステムレベルのツール開発が容易になります。

## コアとなるコードの解説

追加された`TrapCause()`メソッドは、`WaitStatus`型のレシーバ`w`に対して定義されています。

```go
func (w WaitStatus) TrapCause() int {
	if w.StopSignal() != SIGTRAP {
		return -1;
	}
	return int(w >> shift) >> 8;
}
```

*   `func (w WaitStatus) TrapCause() int`: `WaitStatus`型に`TrapCause`という名前のメソッドを追加し、`int`型の値を返すことを宣言しています。
*   `if w.StopSignal() != SIGTRAP`: まず、`WaitStatus`が`SIGTRAP`によって停止した状態であるかを確認します。`StopSignal()`は、`wait status`から停止シグナルを抽出する既存のメソッドです。`SIGTRAP`は`syscall`パッケージで定義されている定数で、トラップシグナルを表します。
*   `return -1`: もし停止シグナルが`SIGTRAP`でなければ、`TrapCause`は意味を持たないため、`-1`を返して無効な状態を示します。
*   `return int(w >> shift) >> 8`: `SIGTRAP`で停止した場合、`wait status`の特定のビット位置にエンコードされているトラップコードを抽出します。
    *   `w >> shift`: `WaitStatus`の基となる整数値を`shift`ビットだけ右シフトします。`shift`は通常8であり、これにより下位8ビット（停止シグナル）が取り除かれます。
    *   `>> 8`: さらに8ビット右シフトします。これは、`wait status`の構造において、`SIGTRAP`のトラップコードが停止シグナルの次の8ビットに格納されていることを前提としています。この操作により、トラップコードが最下位バイトに移動し、他のビットが取り除かれます。
    *   `int(...)`: 結果を`int`型にキャストして返します。この返される値は、`ptrace`イベント（例: `PTRACE_EVENT_FORK`など）に対応する整数値となります。

このメソッドにより、Goプログラムは`wait status`を低レベルでビット操作することなく、`SIGTRAP`の具体的な原因を簡単に取得できるようになりました。

    *   最終的に、この計算結果が`int`型にキャストされ、`SIGTRAP`の原因を示す整数値として返されます。この値は、`ptrace`イベント（例: `PTRACE_EVENT_FORK`など）に対応する定数と比較することで、具体的な`SIGTRAP`の原因を特定するために使用されます。

この変更により、GoプログラムからLinuxの`ptrace`イベントをより詳細に処理できるようになり、デバッガやプロファイラなどのシステムレベルのツール開発が容易になります。

## コアとなるコードの解説

追加された`TrapCause()`メソッドは、`WaitStatus`型のレシーバ`w`に対して定義されています。

```go
func (w WaitStatus) TrapCause() int {
	if w.StopSignal() != SIGTRAP {
		return -1;
	}
	return int(w >> shift) >> 8;
}
```

*   `func (w WaitStatus) TrapCause() int`: `WaitStatus`型に`TrapCause`という名前のメソッドを追加し、`int`型の値を返すことを宣言しています。
*   `if w.StopSignal() != SIGTRAP`: まず、`WaitStatus`が`SIGTRAP`によって停止した状態であるかを確認します。`StopSignal()`は、`wait status`から停止シグナルを抽出する既存のメソッドです。`SIGTRAP`は`syscall`パッケージで定義されている定数で、トラップシグナルを表します。
*   `return -1`: もし停止シグナルが`SIGTRAP`でなければ、`TrapCause`は意味を持たないため、`-1`を返して無効な状態を示します。
*   `return int(w >> shift) >> 8`: `SIGTRAP`で停止した場合、`wait status`の特定のビット位置にエンコードされているトラップコードを抽出します。
    *   `w >> shift`: `WaitStatus`の基となる整数値を`shift`ビットだけ右シフトします。`shift`は通常8であり、これにより下位8ビット（停止シグナル）が取り除かれます。
    *   `>> 8`: さらに8ビット右シフトします。これは、`wait status`の構造において、`SIGTRAP`のトラップコードが停止シグナルの次の8ビットに格納されていることを前提としています。この操作により、トラップコードが最下位バイトに移動し、他のビットが取り除かれます。
    *   `int(...)`: 結果を`int`型にキャストして返します。この返される値は、`ptrace`イベント（例: `PTRACE_EVENT_FORK`など）に対応する整数値となります。

このメソッドにより、Goプログラムは`wait status`を低レベルでビット操作することなく、`SIGTRAP`の具体的な原因を簡単に取得できるようになりました。

# [インデックス 26716] ファイルの概要

このコミットは、Goコンパイラの内部パッケージ `cmd/compile/internal/gc/parser.go` における、特定の行番号処理に関する「ハック」を削除するものです。以前の変更（golang.org/cl/19652）によって、このハックが不要になったため、コードのクリーンアップと正確性の向上が図られています。

## 元コミット内容

`cmd/compile: remove parser lineno hack for issue #13267`

このコミットは、Goコンパイラのパーサーにおける行番号処理の「ハック」を削除します。このハックは、以前の変更（golang.org/cl/19652）によって「canned imports」の解析時に行われていた `lexlineno{++,--}` という奇妙な操作が削除されたため、もはや不要となりました。

具体的には、`$ echo -n 0 > /tmp/0.go` のような不正なGoファイルをコンパイルした際に `/tmp/0.go:1: syntax error: package statement must be first` というエラーメッセージが正しく表示されることを確認しています。

以前は、「canned imports」を解析する際に `lexlineno` が2に設定され、それが `prevlineno` と `lineno` にも影響を与えていました。インポート解析が完了し `lexlineno` が1に戻された後でも、ソースファイルの最初のトークンである "package" を処理する際に `lineno` は1に修正されるものの、`prevlineno` は2のまま残ってしまうという問題がありました。このコミットは、この不整合を解消します。

## 変更の背景

この変更の背景には、Goコンパイラのパーサーにおける行番号管理の正確性に関する問題がありました。特に、Goのソースファイルは `package` ステートメントで始まる必要がありますが、コンパイラが内部的に処理する「canned imports」（Goコンパイラが事前に知っている、または内部的に生成するインポートパス）の解析方法が、この行番号の正確性を損なう可能性がありました。

以前のコミット `golang.org/cl/19652` で、「canned imports」を解析する際の `lexlineno{++,--}` という特殊な行番号操作が削除されました。この操作は、特定の状況下でパーサーの内部状態（特に `lineno` と `prevlineno`）を混乱させ、結果として誤った行番号でエラーが報告される原因となっていました。

このコミットは、`golang.org/cl/19652` の変更によって、以前の行番号の不整合を修正するために導入されていた「ハック」（`prevlineno = lineno` の行）が不要になったため、それを削除し、コードベースを簡素化することを目的としています。これにより、コンパイラのエラー報告の正確性が向上し、内部コードの理解も容易になります。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **Goコンパイラの構造**: Goコンパイラ (`cmd/compile`) は、ソースコードを解析し、中間表現を経て、最終的に実行可能なバイナリを生成します。このプロセスには、字句解析（lexing）、構文解析（parsing）、型チェック、最適化、コード生成などが含まれます。
2.  **字句解析器 (Lexer/Scanner)**: ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換する部分です。`lexlineno` は、字句解析器が現在処理している行番号を追跡するために使用される変数です。
3.  **構文解析器 (Parser)**: 字句解析器から受け取ったトークンのストリームを基に、プログラムの構文ツリー（AST: Abstract Syntax Tree）を構築する部分です。`parser.go` はこの構文解析器の一部です。
4.  **行番号 (lineno, prevlineno)**:
    *   `lineno`: 現在処理中のソースコードの行番号を示します。
    *   `prevlineno`: 以前に処理されたトークンの行番号を示します。これらは、エラーメッセージやデバッグ情報において正確な位置を報告するために非常に重要です。
5.  **canned imports**: Goコンパイラが内部的に処理する、または特定のビルドプロセスで事前に定義されるインポートパスを指します。これらは通常のソースファイルとは異なる方法で扱われることがあり、それが過去に行番号の追跡を複雑にしていた原因の一つです。
6.  **Issue #13267**: このコミットが参照しているGoのバグトラッカーの課題です。これは、不正なGoファイルをコンパイルした際に、`package` ステートメントが最初の行にない場合に、誤った行番号が報告される問題に関連していました。

## 技術的詳細

このコミットは、`src/cmd/compile/internal/gc/parser.go` ファイル内の `package_()` メソッドに対する変更です。このメソッドは、Goソースファイルの `package` ステートメントを解析する役割を担っています。

変更前のコードは以下のようになっていました。

```go
func (p *parser) package_() {
	if p.trace_ {
		defer p.trace("package_")()
	}

	if p.got(LPACKAGE) {
		mkpackage(p.sym().Name)
	} else {
		prevlineno = lineno // see issue #13267
		p.syntax_error("package statement must be first")
		errorexit()
	}
}
```

ここで注目すべきは `else` ブロック内の `prevlineno = lineno // see issue #13267` という行です。これは、`package` キーワードが見つからなかった（つまり、`package` ステートメントがファイルの最初にない）場合に実行されるコードパスです。

コミットメッセージによると、この「ハック」は、`canned imports` の解析中に `lexlineno` が一時的に2に設定され、それが `lineno` と `prevlineno` にも影響を与えていた問題に対処するためのものでした。`canned imports` の解析が終わり `lexlineno` が1に戻された後でも、`package` キーワードがファイルの最初のトークンとして処理される際に `lineno` は1に修正されるものの、`prevlineno` は2のまま残ってしまうという不整合が発生していました。この不整合が、`package` ステートメントがない場合に報告されるエラーメッセージの行番号を狂わせる可能性があったため、`prevlineno = lineno` で明示的に `prevlineno` を現在の `lineno` に合わせることで、この問題を回避していました。

しかし、`golang.org/cl/19652` の変更によって、`canned imports` の解析における `lexlineno{++,--}` という「奇妙な」操作が削除されました。この変更により、`canned imports` の解析中に行番号が不適切に操作されることがなくなり、結果として `prevlineno` と `lineno` の不整合も発生しなくなりました。そのため、以前の `prevlineno = lineno` というハックはもはや不要となり、削除されることになりました。

変更後のコードは以下のようになります。

```go
func (p *parser) package_() {
	if p.trace_ {
		defer p.trace("package_")()
	}

	if !p.got(LPACKAGE) {
		p.syntax_error("package statement must be first")
		errorexit()
	}
	mkpackage(p.sym().Name)
}
```

この変更により、コードはより簡潔になり、行番号の管理がより直接的で正確になりました。`package` キーワードが見つからない場合は、直接構文エラーを報告し、プログラムを終了します。`package` キーワードが見つかった場合は、`mkpackage` 関数を呼び出してパッケージを構築します。

## コアとなるコードの変更箇所

`src/cmd/compile/internal/gc/parser.go` ファイルの `package_()` 関数内。

```diff
--- a/src/cmd/compile/internal/gc/parser.go

具体的には、以下の変更が行われました。

*   `if p.got(LPACKAGE)` ブロックと `else` ブロックが統合されました。
*   `else` ブロック内にあった `prevlineno = lineno // see issue #13267` の行が削除されました。
*   `if !p.got(LPACKAGE)` という条件で、`package` キーワードが見つからなかった場合の構文エラー処理が先に行われるようになりました。
*   `mkpackage(p.sym().Name)` の呼び出しは、`package` キーワードが見つかった場合にのみ実行されるように、条件分岐の外に出されました。

## コアとなるコードの解説

変更された `package_()` 関数は、Goソースファイルの `package` 宣言を解析するGoコンパイラのパーサーの一部です。

**変更前**:
`package_()` 関数は、まず `p.got(LPACKAGE)` を使って `package` キーワードが存在するかどうかをチェックしていました。
*   `package` キーワードが存在する場合 (`if p.got(LPACKAGE)` が真の場合): `mkpackage(p.sym().Name)` を呼び出してパッケージを構築していました。
*   `package` キーワードが存在しない場合 (`else` ブロック):
    *   `prevlineno = lineno` を実行していました。これは `issue #13267` に対応するためのハックであり、`canned imports` の解析による行番号の不整合を修正する目的がありました。
    *   `p.syntax_error("package statement must be first")` を呼び出して構文エラーを報告し、`errorexit()` でコンパイルを終了していました。

**変更後**:
変更後の `package_()` 関数は、ロジックがよりシンプルかつ直接的になりました。
*   まず `if !p.got(LPACKAGE)` を使って、`package` キーワードが**存在しない**場合をチェックします。
    *   `package` キーワードが存在しない場合: `p.syntax_error("package statement must be first")` を呼び出して構文エラーを報告し、`errorexit()` でコンパイルを終了します。
*   上記の `if` ブロックが実行されなかった場合（つまり、`package` キーワードが存在する場合）: `mkpackage(p.sym().Name)` を呼び出してパッケージを構築します。

この変更の核心は、`prevlineno = lineno` という行番号調整のハックが削除されたことです。これは、`golang.org/cl/19652` によって `canned imports` 処理における行番号の不適切な操作が修正されたため、もはや不要になったためです。これにより、コンパイラのコードはよりクリーンになり、行番号の追跡がより正確で予測可能になりました。

# [インデックス 22375] ファイルの概要

このコミットは、Goランタイムのトレース機能において、スタックトレースから不要なランタイムフレームを除去することを目的としています。これにより、生成されるトレースファイルのサイズが削減され、トレースビューアでのスタックの可読性が向上します。

## 変更の背景

Goのランタイムトレーサーは、アプリケーションの実行に関する詳細なイベント（ゴルーチンのスケジューリング、ガベージコレクション、システムコールなど）を収集し、パフォーマンス分析やデバッグに役立てます。しかし、トレースイベントに関連するスタックトレースには、ユーザーコードの実行とは直接関係のない、ランタイム内部の関数呼び出し（ランタイムフレーム）が多数含まれることがありました。

これらのランタイムフレームは、以下の問題を引き起こしていました。

1.  **トレースファイルの肥大化**: 不要なスタックフレームが記録されることで、生成されるトレースファイルのサイズが不必要に大きくなっていました。
2.  **可読性の低下**: トレースビューアでスタックトレースを分析する際、多数のランタイムフレームが混在することで、ユーザーが関心のあるコードパスを特定しにくく、可読性が低下していました。

このコミットは、これらの問題を解決するために、トレーススタックから「面白くない（uninteresting）」下位および上位のランタイムフレームを除去することを目的としています。

## 前提知識の解説

### Goランタイムトレーシング

Goのランタイムトレーサーは、`runtime/trace`パッケージを通じて提供される強力なツールです。これは、Goプログラムの実行中に発生する様々なイベント（ゴルーチンの生成、ブロック、アンブロック、システムコール、GC活動など）を詳細に記録します。生成されたトレースファイルは、`go tool trace`コマンドを使用して視覚化および分析でき、イベントのタイムラインやゴルーチンの状態変化を把握するのに役立ちます。これにより、従来のプロファイリングツールでは見逃されがちなパフォーマンスのボトルネック、スケジューラの挙動、並行処理の問題などを特定できます。

### スタックフレーム

スタックフレームは、関数呼び出しがコールスタック上で占める領域を表します。Goのランタイムトレーシングやデバッグにおいて、スタックフレームはゴルーチンの実行パスを理解するために不可欠です。

*   **スタックアンワインディング**: スタックフレームを収集するプロセスは「スタックアンワインディング」として知られています。これはコストのかかる操作であり、特に実行トレーサーのコンテキストでは、オーバーヘッドを削減するためにフレームポインタアンワインディングなどの技術が採用されています。
*   **ランタイムフレーム**: Goのプログラムが実行される際、ユーザーが記述したコードだけでなく、Goランタイム自体が提供する様々な内部関数も呼び出されます。これらのランタイム内部の関数呼び出しがスタック上に積まれたものが「ランタイムフレーム」です。例えば、ゴルーチンのスケジューリング、メモリ管理、チャネル操作など、多くの低レベルな処理はランタイム関数によって行われます。

### `gopark`と`goready`

これらはGoランタイムスケジューラ内部の関数で、ゴルーチンの状態遷移を管理します。

*   **`gopark`**: ゴルーチンが「パーク（park）」される、つまり待機状態に入る必要があるときに呼び出されます。`gopark`が呼び出されると、現在のゴルーチンはスケジューラの実行キューから削除され、スケジューラは現在のM/P（Machine/Processor）で実行する別のゴルーチンを選択します。スタックトレースに`runtime.gopark`が表示される場合、それはゴルーチンがチャネル操作やミューテックスなどのイベントを待機している間に、ランタイムスケジューラによって一時的に停止されたことを示します。
*   **`goready`**: パークされたゴルーチンを「実行可能（runnable）」状態に戻し、スケジューラの実行キューに追加して、実行される準備ができたことを示します。

### `traceskip`

`traceskip`は、`gopark`や`goready`のような内部ランタイム関数に渡される新しいパラメータです。その目的は、トレースイベントのスタックトレースをキャプチャする際に、スキップするスタックフレームの数を指定することです。これは一般的な最適化であり、記録されるスタックトレースが、イベントを引き起こした関連するユーザーレベルのコードに焦点を当てるようにします。これにより、実際の原因を不明瞭にしたり、トレースデータに不要なノイズを追加したりする可能性のある、多数の内部ランタイム呼び出しを含めることを避けます。

## 技術的詳細

このコミットの主要な変更点は、トレースイベントのスタックトレース収集時に、ランタイムフレームをスキップするための`traceskip`パラメータを導入したことです。

1.  **`gopark`および`goready`関数の変更**:
    *   `gopark`関数に`traceskip int`という新しいパラメータが追加されました。このパラメータは、スタックトレースを収集する際にスキップすべきフレームの数を指定します。
    *   `goready`関数にも同様に`traceskip int`パラメータが追加されました。
    *   これらの関数を呼び出す既存のコード箇所（チャネル操作、ファイナライザ、GC、ネットワークポーリング、セマフォ、タイマーなど）が更新され、適切な`traceskip`値が渡されるようになりました。例えば、`gopark(nil, nil, "chan send (nil chan)", traceEvGoStop)`は`gopark(nil, nil, "chan send (nil chan)", traceEvGoStop, 2)`のように変更されています。この`2`という値は、`gopark`呼び出し元から2フレームをスキップすることを意味します。

2.  **`m`構造体への`waittraceskip`フィールドの追加**:
    *   `src/runtime/runtime2.go`の`m`構造体（OSスレッドを表す）に`waittraceskip int`フィールドが追加されました。これは、`gopark`が呼び出された際に、そのゴルーチンが待機状態に入る理由に関連するスタックトレースを収集する際にスキップすべきフレーム数を保持します。

3.  **`traceEvent`関数の変更**:
    *   `src/runtime/trace.go`の`traceEvent`関数は、スタックトレースを収集する際のロジックが変更されました。以前は`stack bool`パラメータでスタックを収集するかどうかを制御していましたが、新しい`skip int`パラメータが導入されました。
    *   `skip >= 0`の場合にスタックを収集し、`skip`の値に基づいて`callers`または`gcallers`関数に渡すスキップ数を決定します。
    *   特に、`skip > 0`の場合、`callers(skip, buf.stk[:])`または`gcallers(gp, skip, buf.stk[:])`が呼び出され、指定された数のフレームがスキップされます。
    *   さらに、`runtime.goexit`と`runtime.main`といった特定のランタイムフレームも、スタックトレースの末尾から自動的に除去されるようになりました。これにより、トレースビューアでのスタックの表示がより簡潔になります。

4.  **`trace_stack_test.go`の追加**:
    *   `src/runtime/pprof/trace_stack_test.go`という新しいテストファイルが追加されました。このテストは、スタックトレースのシンボル化と、ランタイムフレームが適切に除去されていることを検証します。様々なゴルーチンのブロックイベント（チャネル、select、mutex、WaitGroup、Cond、ネットワークI/O、パイプI/Oなど）を発生させ、それぞれのイベントで期待されるスタックフレームが正しく記録されているかを確認します。

これらの変更により、トレースイベントが発生した際に、`gopark`や`goready`などのランタイム内部の呼び出しスタックが自動的にスキップされ、ユーザーコードに関連するより意味のあるスタックトレースが記録されるようになります。

## コアとなるコードの解説

このコミットの核心は、`traceskip`パラメータの導入と、それを利用したスタックトレースのフィルタリングです。

`gopark`や`goready`のようなランタイム関数は、ゴルーチンの状態遷移を引き起こし、その際にトレースイベントが記録されます。これらの関数自体はランタイムの内部実装であり、通常、ユーザーが関心を持つのは、これらの関数が呼び出される原因となったユーザーコードのスタックフレームです。

`traceskip`パラメータは、この問題を解決します。

*   **`gopark(..., traceskip int)`**:
    `gopark`が呼び出される際、`traceskip`に渡される整数値は、`gopark`の呼び出し元から何フレームをスキップしてスタックトレースを収集するかを`traceEvent`に指示します。例えば、`traceskip`が`1`であれば、`gopark`自身のフレームがスキップされ、その呼び出し元のフレームからスタックトレースが開始されます。これにより、トレースデータからランタイム内部のノイズが減り、よりユーザーコードに焦点を当てたスタックトレースが得られます。

*   **`goready(..., traceskip int)`**:
    同様に、`goready`が呼び出される際にも`traceskip`が使用されます。これにより、ゴルーチンが実行可能になったイベントのスタックトレースも、関連性の低いランタイムフレームが除去されます。

*   **`traceEvent(ev byte, skip int, args ...uint64)`**:
    この関数は、実際にトレースイベントをバッファに書き込む役割を担います。`skip`パラメータを受け取り、`callers`または`gcallers`関数（スタックトレースを収集する内部関数）にこの`skip`値を渡します。これにより、指定された数のフレームがスタックトレースの先頭から除去されます。
    さらに、`traceEvent`は、`runtime.goexit`（ゴルーチンが終了する際の最終的なランタイム関数）と、メインゴルーチン（`goid == 1`）の`runtime.main`フレームを自動的に除去するロジックも追加しました。これらのフレームは、ほとんどのトレース分析において関心が低いため、明示的に除去することでスタックトレースをさらに簡潔にします。

このメカニズムにより、トレースファイルはより小さくなり、トレースビューアで表示されるスタックトレースは、ユーザーがデバッグやパフォーマンス分析を行う上でより関連性の高い情報のみを含むようになります。

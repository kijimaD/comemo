## 変更の背景

このコミットは、Goコンパイラが特定の状況下で誤った行番号を報告するというバグ（Issue 14520）を修正するために行われました。この問題は主に2つのシナリオで発生していました。

1.  **複数行コメント内の改行文字の扱い**: Goのコンパイラは、ソースコードを字句解析（lexing）する際に、コメントをスキップします。しかし、複数行コメント（`/* ... */`）が複数の改行文字を含む場合、コメントの終了マーカー`*/`の直前で字句解析器が行番号を誤ってリセットしてしまうことがありました。これにより、コメントの直後に続くコード要素に対して、実際よりも前の行番号が報告される可能性がありました。これは、特にセミコロン自動挿入（automatic semicolon insertion, ASI）の挙動に影響を与え、予期せぬコンパイルエラーを引き起こす可能性がありました。
2.  **`import`文の行番号の扱い**: `import`文を処理する際、コンパイラはインポートパスを読み取った後、次のトークンに進む前に`importfile`関数を呼び出していました。この順序が原因で、`lineno`（現在の行番号）がインポートパスが見つかった行ではなく、その後のトークンの行を指してしまうことがありました。結果として、`import`パスに関連するエラーメッセージが誤った行番号で報告されることになり、デバッグを困難にしていました。

これらの問題は、コンパイラが報告するエラーメッセージの正確性に直接影響し、開発者の生産性を低下させる可能性があったため、修正が必要とされました。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの概念とGo言語の仕様に関する知識が役立ちます。

*   **字句解析器 (Lexer/Scanner)**: ソースコードを読み込み、意味のある最小単位（トークン）に分割するコンポーネントです。例えば、`func`、`main`、`(`、`)`、`{`、`}`、`=`、`+`、数値リテラル、文字列リテラルなどがトークンになります。字句解析器は通常、現在の行番号（`lineno`）を追跡します。
*   **構文解析器 (Parser)**: 字句解析器が生成したトークンのストリームを受け取り、Go言語の文法規則に従って構文木（AST: Abstract Syntax Tree）を構築するコンポーネントです。
*   **`cmd/compile`**: Go言語の公式コンパイラです。Goのソースコードを機械語に変換します。
*   **行番号 (Line Number)**: コンパイラがエラーや警告を報告する際に、ソースコード内の位置を示すために使用する情報です。正確な行番号は、開発者が問題を迅速に特定するために不可欠です。
*   **複数行コメント (`/* ... */`)**: Go言語におけるコメントの一種で、`/*`で始まり`*/`で終わります。このコメントは、字句解析の段階でスキップされますが、その内部の改行文字は行番号のカウントに影響を与える可能性があります。
*   **セミコロン自動挿入 (Automatic Semicolon Insertion, ASI)**: Go言語の文法規則の一つで、特定の状況下で改行の後に自動的にセミコロンが挿入されるというものです。これにより、多くのGoプログラムでセミコロンを明示的に書く必要がなくなります。字句解析器が行番号を誤って解釈すると、ASIの挙動が意図しないものになる可能性があります。
*   **`import`文**: 外部パッケージを現在のファイルにインポートするために使用されるGo言語のキーワードです。`import "path/to/package"`のような形式を取ります。
*   **`p.next()`**: 構文解析器（`parser`）が字句解析器から次のトークンを取得するためのメソッドです。この操作は通常、字句解析器の内部状態（`lineno`を含む）を進めます。
*   **`l.getr()` / `l.ungetr()`**: 字句解析器（`lexer`）が入力ストリームから文字を読み取る（`getr`）および読み取った文字をストリームに戻す（`ungetr`）ための内部関数です。`ungetr`は、特定の条件が満たされた場合に、字句解析器の状態を少し巻き戻すために使用されます。

## 技術的詳細

このコミットは、Goコンパイラの字句解析器と構文解析器の2つの異なる部分に修正を加えています。

### 1. 複数行コメント内の行番号の修正 (`src/cmd/compile/internal/gc/lex.go`)

元の実装では、複数行コメント`/* ... */`を処理する際に、コメント内に改行文字が含まれているかどうかを`nl`というブール変数で追跡していました。コメントの終了マーカー`*/`が見つかった後、もし`nl`が`true`（つまりコメント内に改行があった）であれば、字句解析器は`l.ungetr('\n')`を呼び出して改行文字を「読み戻し」、その後`goto l0`で字句解析の初期状態に戻っていました。この「読み戻し」と再字句解析のプロセスが問題でした。

問題の核心は、`l.ungetr('\n')`が字句解析器の内部状態（特に`lineno`）を適切に巻き戻さなかったことにあります。コメントが複数の改行を含んでいた場合、`lineno`はコメントの開始行から大きく進んでいました。しかし、`ungetr('\n')`は単一の改行を読み戻すだけで、`lineno`をコメント終了マーカーの直前の行にリセットするのではなく、コメント開始行の直前の行にリセットしてしまう可能性がありました。これにより、コメントの直後に続くコード要素が、実際よりも前の行番号を持つと誤って解釈されることがありました。

修正後のコードでは、`nl`変数を削除し、コメント内の改行の有無を直接`lexlineno > lineno`でチェックするように変更されました。`lexlineno`は字句解析器が現在処理している行番号、`lineno`は現在のトークンの開始行番号を指します。コメントが複数の改行を含み、かつ`nlsemi`（セミコロン自動挿入が有効な状態）であれば、コメントは改行として扱われ、自動的にセミコロンが挿入されるべき状況を適切に処理します。`l.ungetr('\n')`のような行番号を誤ってリセットする可能性のある操作は削除され、コメント処理後に直接`goto l0`で字句解析の初期状態に戻ることで、行番号の整合性が保たれるようになりました。

### 2. `import`文の行番号の修正 (`src/cmd/compile/internal/gc/parser.go`)

元の実装では、`import`文を処理する`importdcl`関数内で、以下の順序で処理が行われていました。

1.  `line := int32(parserline())`：現在の行番号を保存。
2.  `path := p.val`：インポートパスの文字列を保存。
3.  `p.next()`：次のトークンに進む。この時点で`lineno`が更新される。
4.  `importfile(&path, p.indent)`：インポートパスを処理。

この順序では、`importfile`が呼び出される時点では、すでに`p.next()`によって字句解析器が次のトークンに進んでしまっており、`lineno`はインポートパスの行ではなく、その後のトークンの行を指していました。

修正後のコードでは、この順序が変更されました。

1.  `line := int32(parserline())`：現在の行番号を保存。
2.  `importfile(&p.val, p.indent)`：**`p.next()`を呼び出す前に**インポートパスを処理。これにより、`importfile`が参照する`p.val`（インポートパス）と`lineno`が、インポートパスが実際にソースコードに現れる行を正確に指すようになります。
3.  `ipkg := importpkg`：`importfile`によって設定されたパッケージ情報を一時変数に保存。
4.  `importpkg = nil`：グローバル変数`importpkg`をクリア。
5.  `p.next()`：次のトークンに進む。

この変更により、`importfile`が呼び出される際の`lineno`が正確になり、`import`文に関連するエラーメッセージが正しい行番号で報告されるようになります。コミットメッセージにある`// TODO(mdempsky): Fix this clumsy API.`というコメントは、`importpkg`のようなグローバル変数を使用していることに対する設計上の懸念を示唆しており、この修正がAPIの根本的な改善ではなく、既存のAPI構造内でのバグ修正であることを示しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/lex.go` の変更点

字句解析器のコメント処理部分では、`/*`で始まるコメントを検出した際のロジックが変更されています。
元のコードでは、コメント内に改行があった場合に`nl`フラグを立て、コメント終了後に`l.ungetr('\n')`で改行を読み戻していました。これは、コメントが単一の改行を含む場合に、その改行がセミコロン自動挿入のトリガーとなるように意図されていた可能性があります。しかし、複数行コメントの場合、`lineno`がコメントの開始行から大きく進んだ後で、単一の改行を読み戻しても`lineno`が適切にリセットされず、誤った行番号が報告される原因となっていました。

修正後のコードでは、`nl`フラグと`l.ungetr('\n')`の呼び出しが削除されました。代わりに、コメント処理ループが終了した後、`lexlineno > lineno && nlsemi`という条件で、コメントが改行として扱われるべきかを判定しています。
*   `lexlineno`は字句解析器が現在処理している行番号です。
*   `lineno`は現在のトークン（この場合はコメントの開始トークン）の開始行番号です。
*   `nlsemi`はセミコロン自動挿入が有効な状態かどうかを示すフラグです。

この条件が真であれば、コメントは実質的に改行として機能し、自動的にセミコロンが挿入されるべき状況と判断されます。この変更により、複数行コメントが`lineno`に与える影響がより正確に制御され、コンパイラが報告する行番号の正確性が向上しました。

### `src/cmd/compile/internal/gc/parser.go` の変更点

構文解析器の`importdcl`関数では、`import`文の処理順序が変更されました。
元のコードでは、インポートパスを読み取った後、`p.next()`を呼び出して次のトークンに進んでから`importfile`を呼び出していました。このため、`importfile`がインポートパスに関連するエラーを報告しようとした場合、すでに`lineno`が次のトークンの行に更新されてしまっており、誤った行番号が報告される可能性がありました。

修正後のコードでは、`p.next()`を呼び出す前に`importfile(&p.val, p.indent)`を呼び出すように変更されました。これにより、`importfile`が実行される時点では、`p.val`にはインポートパスの文字列が、`lineno`にはインポートパスがソースコードに現れる正確な行番号が保持されています。この修正によって、`import`文に関連するエラーメッセージが正しい行番号で報告されるようになり、デバッグの精度が向上します。

また、`importpkg`というグローバル変数を一時変数`ipkg`に保存し、`importpkg`を`nil`にクリアする処理が`p.next()`の前に移動されています。これは、`p.next()`が`lexlineno`に影響を与える可能性があり、その前に`importpkg`の状態を適切に管理する必要があるためです。`TODO(mdempsky): Fix this clumsy API.`というコメントは、`importpkg`のようなグローバル状態に依存する設計が理想的ではないことを示唆しており、将来的なリファクタリングの可能性を示しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの概念とGo言語の仕様に関する知識が役立ちます。

*   **字句解析器 (Lexer/Scanner)**: ソースコードを読み込み、意味のある最小単位（トークン）に分割するコンポーネントです。例えば、`func`、`main`、`(`、`)`、`{`、`}`、`=`、`+`、数値リテラル、文字列リテラルなどがトークンになります。字句解析器は通常、現在の行番号（`lineno`）を追跡します。
*   **構文解析器 (Parser)**: 字句解析器が生成したトークンのストリームを受け取り、Go言語の文法規則に従って構文木（AST: Abstract Syntax Tree）を構築するコンポーネントです。
*   **`cmd/compile`**: Go言語の公式コンパイラです。Goのソースコードを機械語に変換します。
*   **行番号 (Line Number)**: コンパイラがエラーや警告を報告する際に、ソースコード内の位置を示すために使用する情報です。正確な行番号は、開発者が問題を迅速に特定するために不可欠です。
*   **複数行コメント (`/* ... */`)**: Go言語におけるコメントの一種で、`/*`で始まり`*/`で終わります。このコメントは、字句解析の段階でスキップされますが、その内部の改行文字は行番号のカウントに影響を与える可能性があります。
*   **セミコロン自動挿入 (Automatic Semicolon Insertion, ASI)**: Go言語の文法規則の一つで、特定の状況下で改行の後に自動的にセミコロンが挿入されるというものです。これにより、多くのGoプログラムでセミコロンを明示的に書く必要がなくなります。字句解析器が行番号を誤って解釈すると、ASIの挙動が意図しないものになる可能性があります。
*   **`import`文**: 外部パッケージを現在のファイルにインポートするために使用されるGo言語のキーワードです。`import "path/to/package"`のような形式を取ります。
*   **`p.next()`**: 構文解析器（`parser`）が字句解析器から次のトークンを取得するためのメソッドです。この操作は通常、字句解析器の内部状態（`lineno`を含む）を進めます。
*   **`l.getr()` / `l.ungetr()`**: 字句解析器（`lexer`）が入力ストリームから文字を読み取る（`getr`）および読み取った文字をストリームに戻す（`ungetr`）ための内部関数です。`ungetr`は、特定の条件が満たされた場合に、字句解析器の状態を少し巻き戻すために使用されます。

## 技術的詳細

このコミットは、Goコンパイラの字句解析器と構文解析器の2つの異なる部分に修正を加えています。

### 1. 複数行コメント内の行番号の修正 (`src/cmd/compile/internal/gc/lex.go`)

元の実装では、複数行コメント`/* ... */`を処理する際に、コメント内に改行文字が含まれているかどうかを`nl`というブール変数で追跡していました。コメントの終了マーカー`*/`が見つかった後、もし`nl`が`true`（つまりコメント内に改行があった）であれば、字句解析器は`l.ungetr('\n')`を呼び出して改行文字を「読み戻し」、その後`goto l0`で字句解析の初期状態に戻っていました。この「読み戻し」と再字句解析のプロセスが問題でした。

問題の核心は、`l.ungetr('\n')`が字句解析器の内部状態（特に`lineno`）を適切に巻き戻さなかったことにあります。コメントが複数の改行を含んでいた場合、`lineno`はコメントの開始行から大きく進んでいました。しかし、`ungetr('\n')`は単一の改行を読み戻すだけで、`lineno`をコメント終了マーカーの直前の行にリセットするのではなく、コメント開始行の直前の行にリセットしてしまう可能性がありました。これにより、コメントの直後に続くコード要素が、実際よりも前の行番号を持つと誤って解釈されることがありました。

修正後のコードでは、`nl`変数を削除し、コメント内の改行の有無を直接`lexlineno > lineno`でチェックするように変更されました。`lexlineno`は字句解析器が現在処理している行番号、`lineno`は現在のトークンの開始行番号を指します。コメントが複数の改行を含み、かつ`nlsemi`（セミコロン自動挿入が有効な状態）であれば、コメントは改行として扱われ、自動的にセミコロンが挿入されるべき状況を適切に処理します。`l.ungetr('\n')`のような行番号を誤ってリセットする可能性のある操作は削除され、コメント処理後に直接`goto l0`で字句解析の初期状態に戻ることで、行番号の整合性が保たれるようになりました。

### 2. `import`文の行番号の修正 (`src/cmd/compile/internal/gc/parser.go`)

元の実装では、`import`文を処理する`importdcl`関数内で、以下の順序で処理が行われていました。

1.  `line := int32(parserline())`：現在の行番号を保存。
2.  `path := p.val`：インポートパスの文字列を保存。
3.  `p.next()`：次のトークンに進む。この時点で`lineno`が更新される。
4.  `importfile(&path, p.indent)`：インポートパスを処理。

この順序では、`importfile`が呼び出される時点では、すでに`p.next()`によって字句解析器が次のトークンに進んでしまっており、`lineno`はインポートパスの行ではなく、その後のトークンの行を指していました。

修正後のコードでは、この順序が変更されました。

1.  `line := int32(parserline())`：現在の行番号を保存。
2.  `importfile(&p.val, p.indent)`：**`p.next()`を呼び出す前に**インポートパスを処理。これにより、`importfile`が参照する`p.val`（インポートパス）と`lineno`が、インポートパスが実際にソースコードに現れる行を正確に指すようになります。
3.  `ipkg := importpkg`：`importfile`によって設定されたパッケージ情報を一時変数に保存。
4.  `importpkg = nil`：グローバル変数`importpkg`をクリア。
5.  `p.next()`：次のトークンに進む。

この変更により、`importfile`が呼び出される際の`lineno`が正確になり、`import`文に関連するエラーメッセージが正しい行番号で報告されるようになります。コミットメッセージにある`// TODO(mdempsky): Fix this clumsy API.`というコメントは、`importpkg`のようなグローバル変数を使用していることに対する設計上の懸念を示唆しており、この修正がAPIの根本的な改善ではなく、既存のAPI構造内でのバグ修正であることを示しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/lex.go` の変更点

字句解析器のコメント処理部分では、`/*`で始まるコメントを検出した際のロジックが変更されています。
元のコードでは、コメント内に改行があった場合に`nl`フラグを立て、コメント終了後に`l.ungetr('\n')`で改行を読み戻していました。これは、コメントが単一の改行を含む場合に、その改行がセミコロン自動挿入のトリガーとなるように意図されていた可能性があります。しかし、複数行コメントの場合、`lineno`がコメントの開始行から大きく進んだ後で、単一の改行を読み戻しても`lineno`が適切にリセットされず、誤った行番号が報告される原因となっていました。

修正後のコードでは、`nl`フラグと`l.ungetr('\n')`の呼び出しが削除されました。代わりに、コメント処理ループが終了した後、`lexlineno > lineno && nlsemi`という条件で、コメントが改行として扱われるべきかを判定しています。
*   `lexlineno`は字句解析器が現在処理している行番号です。
*   `lineno`は現在のトークン（この場合はコメントの開始トークン）の開始行番号です。
*   `nlsemi`はセミコロン自動挿入が有効な状態かどうかを示すフラグです。

この条件が真であれば、コメントは実質的に改行として機能し、自動的にセミコロンが挿入されるべき状況と判断されます。この変更により、複数行コメントが`lineno`に与える影響がより正確に制御され、コンパイラが報告する行番号の正確性が向上しました。

### `src/cmd/compile/internal/gc/parser.go` の変更点

構文解析器の`importdcl`関数では、`import`文の処理順序が変更されました。
元のコードでは、インポートパスを読み取った後、`p.next()`を呼び出して次のトークンに進んでから`importfile`を呼び出していました。このため、`importfile`がインポートパスに関連するエラーを報告しようとした場合、すでに`lineno`が次のトークンの行に更新されてしまっており、誤った行番号が報告される可能性がありました。

修正後のコードでは、`p.next()`を呼び出す前に`importfile(&p.val, p.indent)`を呼び出すように変更されました。これにより、`importfile`が実行される時点では、`p.val`にはインポートパスの文字列が、`lineno`にはインポートパスがソースコードに現れる正確な行番号が保持されています。この修正によって、`import`文に関連するエラーメッセージが正しい行番号で報告されるようになり、デバッグの精度が向上します。

また、`importpkg`というグローバル変数を一時変数`ipkg`に保存し、`importpkg`を`nil`にクリアする処理が`p.next()`の前に移動されています。これは、`p.next()`が`lexlineno`に影響を与える可能性があり、その前に`importpkg`の状態を適切に管理する必要があるためです。`TODO(mdempsky): Fix this clumsy API.`というコメントは、`importpkg`のようなグローバル状態に依存する設計が理想的ではないことを示唆しており、将来的なリファクタリングの可能性を示しています。

## 元コミット内容

このコミットは、Goランタイム内のアーキテクチャ固有のC言語のヘッダーファイル（.h）とソースファイル（.c）をGo言語に変換することを目的としています。変換は自動化されたツールによって行われ、その後、コンパイルと実行のために必要な修正のみが加えられました。

特に、`vlrt.c`というファイルはC言語からのみ呼び出されていたため、純粋に削除されました。

この変更は、GoランタイムからC言語コードを削除する大規模な取り組み（`golang.org/s/dev.cc`で概要が説明されています）の一部です。

## 変更の背景

Go言語は、その設計思想として「シンプルさ」と「効率性」を重視しています。初期のGoランタイムには、低レベルの操作やプラットフォーム固有の機能を実現するために、C言語で書かれた部分が多く存在しました。これは、既存のシステムプログラミングの知識やライブラリを活用するための現実的な選択でした。

しかし、C言語とGo言語の混在は、以下のような課題をもたらしていました。

*   **保守性の複雑さ:** C言語とGo言語のコードベースが混在していると、開発者は両方の言語の知識とツールチェインを維持する必要があり、コードの理解とデバッグが複雑になります。
*   **ガベージコレクションの課題:** GoのガベージコレクタはGo言語のメモリモデルに基づいて設計されていますが、C言語で管理されるメモリはGoのGCの対象外となるため、CとGo間のインターフェースで特別な注意が必要でした。これは、メモリリークやGCの効率低下につながる可能性がありました。
*   **移植性の制限:** C言語のコードはプラットフォーム固有の記述が多くなりがちで、新しいアーキテクチャやオペレーティングシステムへのGoの移植を困難にする要因となっていました。
*   **Go言語の進化の阻害:** Go言語自体が進化し、より低レベルの操作やシステムプログラミングに適した機能（例: `unsafe`パッケージ、アセンブリ言語との連携）が提供されるにつれて、C言語に依存する必要性が薄れてきました。

このような背景から、Go開発チームは「dev.cc」という大規模なイニシアチブを開始しました。これは、GoランタイムからC言語コードを段階的に削除し、Go言語で再実装することを目的としたプロジェクトです。このコミットは、そのイニシアチブの重要な一歩として、アーキテクチャ固有のC言語ファイルをGo言語に変換することで、ランタイムの純粋なGo化を推進しています。これにより、Goランタイムはより一貫性があり、保守しやすく、Go言語の特性を最大限に活用できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

1.  **Goランタイム (Go Runtime):**
    Goランタイムは、Goプログラムの実行を管理する低レベルのシステムです。これには、ガベージコレクション（GC）、ゴルーチン（軽量スレッド）のスケジューリング、メモリ管理、システムコール、プリミティブな同期メカニズムなどが含まれます。Goプログラムは、オペレーティングシステム上で直接実行されるのではなく、このランタイム上で動作します。ランタイムはGo言語で書かれていますが、歴史的に一部の非常に低レベルな部分やプラットフォーム固有の部分はC言語やアセンブリ言語で実装されていました。

2.  **アーキテクチャ固有のコード:**
    コンピュータのアーキテクチャ（例: x86, AMD64, ARM）によって、CPUの命令セット、レジスタの構成、メモリのアライメント、キャッシュラインのサイズなどが異なります。Goランタイムは、これらのアーキテクチャの特性を考慮して最適化されたコードを持つ必要があります。C言語では、`#ifdef`などのプリプロセッサディレクティブや、アーキテクチャ固有のヘッダーファイル（例: `arch_386.h`）を使用して、これらの違いを吸収していました。

3.  **アトミック操作 (Atomic Operations):**
    マルチスレッド環境（Goではゴルーチン）において、複数のゴルーチンが同時に共有データにアクセスする場合、競合状態（race condition）が発生する可能性があります。アトミック操作は、このような競合状態を防ぐために、読み取り、書き込み、更新などの操作が不可分（atomic）であることを保証するものです。つまり、操作の途中で他のゴルーチンによる割り込みが発生しないことが保証されます。CPUは通常、アトミック操作をサポートする特別な命令を提供しており、C言語ではこれらの命令を直接呼び出すための組み込み関数やアセンブリコードが使用されることがありました。Goでは`sync/atomic`パッケージがこれを提供します。

4.  **システムコール (System Calls):**
    プログラムがオペレーティングシステムの機能（ファイルI/O、ネットワーク通信、メモリ割り当てなど）を利用する際には、システムコールを介してOSカーネルに処理を依頼します。システムコールは通常、低レベルのインターフェースであり、C言語やアセンブリ言語で直接呼び出されることが一般的です。Goランタイムも、OSとのやり取りのためにシステムコールを利用します。

5.  **`go:nosplit` と `go:noescape` ディレクティブ:**
    Goコンパイラには、特殊なコメント形式で記述されるディレクティブ（指示）があります。
    *   `//go:nosplit`: この関数がスタックを分割しないことをコンパイラに指示します。ランタイムの非常に低レベルな部分や、スタックの成長が許されないクリティカルなパスで使用されます。
    *   `//go:noescape`: この関数内でポインタがヒープにエスケープしないことをコンパイラに指示します。これにより、コンパイラはより効率的なコードを生成できます。

これらの概念を理解することで、C言語からGo言語への変換がGoランタイムの内部でどのような影響を持つのか、そしてなぜそれが重要なのかを深く把握することができます。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムのC言語部分をGo言語で再実装することにあります。これは単なる言語の置き換え以上の意味を持ちます。

1.  **自動変換と手動調整:**
    コミットメッセージにあるように、変換は「自動化されたツール」によって行われ、その後「コンパイルと実行のために必要な修正のみ」が加えられました。これは、C言語の構文をGo言語の構文に機械的に変換する初期ステップがあったことを示唆しています。しかし、C言語とGo言語のセマンティクスの違い（例: ポインタの扱い、メモリ管理、型システム）や、Goランタイム特有の最適化（例: `go:nosplit`, `go:noescape`ディレクティブの適用）のため、手動での調整が不可欠であったと考えられます。

2.  **アーキテクチャ固有の定数のGo化:**
    `src/runtime/arch_386.h`、`src/runtime/arch_amd64.h`、`src/runtime/arch_arm.h`といったC言語のヘッダーファイルは、`enum`キーワードを使ってアーキテクチャ固有の定数（例: `CacheLineSize`, `PhysPageSize`）を定義していました。これらのファイルは削除され、対応する`src/runtime/arch1_386.go`、`src/runtime/arch1_amd64.go`、`src/runtime/arch1_arm.go`ファイルが追加されました。Go言語では、これらの定数は`const`キーワードを使って定義されます。これにより、Goコンパイラがこれらの定数を直接理解し、Cプリプロセッサに依存することなく、型安全な方法で利用できるようになります。

3.  **アトミック操作のGo言語での再実装:**
    `src/runtime/atomic_386.c`と`src/runtime/atomic_amd64x.c`は、アトミック操作（例: `xadd`, `xchg`, `atomicload`）をC言語で実装していました。これらのファイルは削除され、`src/runtime/atomic_386.go`と`src/runtime/atomic_amd64x.go`が追加されました。Go言語のバージョンでは、これらのアトミック操作はGoの組み込み機能（例: `sync/atomic`パッケージの低レベルなプリミティブ）や、場合によってはGoのアセンブリ言語（`textflag NOSPLIT`のようなディレクティブがCコードにあったことから示唆される）を介して実装されます。Go言語のコードでは、`for`ループ内で`cas64`（Compare-And-Swap）のような操作を繰り返し試行するスピンロック的な実装が見られます。また、`xchgp`や`atomicstorep`のようなポインタを扱うアトミック操作には、`noescape`ディレクティブの適用に関する注意深いコメントが追加されており、Goのコンパイラによるエスケープ解析の挙動を考慮した設計がなされています。`nop()`関数の呼び出しは、コンパイラによるインライン化を防ぎ、メモリアクセスの相対的な順序を保証するためのテクニックです。

4.  **システム関連関数のGo化:**
    `src/runtime/sys_arm.c`と`src/runtime/sys_x86.c`は、`gostartcall`や`rewindmorestack`といったシステム関連の低レベル関数をC言語で提供していました。これらのファイルは削除またはリネームされ、`src/runtime/sys_arm.go`と`src/runtime/sys_x86.go`としてGo言語で再実装されました。これらの関数は、ゴルーチンのスタック管理や、`morestack`（スタック拡張）からの復帰など、Goランタイムのコアな動作に関わるものです。Go言語での再実装により、これらの低レベルな操作もGoの型システムとメモリモデルの恩恵を受けることができます。

5.  **`vlrt.c`の完全削除:**
    `src/runtime/vlrt.c`は、64ビット整数演算や浮動小数点数と64ビット整数の変換など、Go言語がまだこれらの操作を直接サポートしていなかった初期段階で、C言語で実装されていたランタイムサポート関数群です。コミットメッセージにあるように、このファイルは「C言語からのみ呼び出されていた」ため、Go言語への変換ではなく、純粋に削除されました。これは、Goコンパイラとランタイムが進化し、これらの操作をGo言語自体で効率的に処理できるようになったことを示唆しています。このファイルの削除は、GoランタイムのC言語依存を大幅に削減する象徴的な変更です。

これらの変更は、Goランタイムの内部構造をよりGo言語に特化したものにし、将来的な最適化や機能追加の基盤を強化することを目的としています。

## コアとなるコードの解説

### `src/runtime/arch1_*.go` (例: `src/runtime/arch1_386.go`)

これらのファイルは、C言語のヘッダーファイル（例: `arch_386.h`）からGo言語の定数定義に変換されたものです。

**C言語 (`arch_386.h`):**
```c
enum {
	thechar = '8',
	BigEndian = 0,
	CacheLineSize = 64,
	RuntimeGogoBytes = 64,
#ifdef GOOS_nacl
	PhysPageSize = 65536,
#else
	PhysPageSize = 4096,
#endif
	PCQuantum = 1,
	Int64Align = 4
};
```

**Go言語 (`arch1_386.go`):**
```go
package runtime

const (
	thechar           = '8'
	_BigEndian        = 0
	_CacheLineSize    = 64
	_RuntimeGogoBytes = 64
	_PhysPageSize     = _NaCl*65536 + (1-_NaCl)*4096 // 4k normally; 64k on NaCl
	_PCQuantum        = 1
	_Int64Align       = 4
)
```
C言語の`enum`で定義されていた定数が、Go言語の`const`ブロックに移行されています。`#ifdef`による条件付きコンパイルは、Go言語のビルドタグや、`_NaCl`のようなランタイム定数を使った式に置き換えられています。これにより、Goコンパイラが直接これらの定数を処理できるようになり、Cプリプロセッサへの依存がなくなります。

### `src/runtime/atomic_386.go` (例: `src/runtime/atomic_386.go`)

このファイルは、C言語で実装されていたアトミック操作をGo言語で再実装したものです。

**C言語 (`atomic_386.c`):**
```c
#pragma textflag NOSPLIT
uint32
runtime·atomicload(uint32 volatile* addr)
{
	return *addr;
}

// ... other atomic functions ...
```

**Go言語 (`atomic_386.go`):**
```go
package runtime

import "unsafe"

// The calls to nop are to keep these functions from being inlined.
// If they are inlined we have no guarantee that later rewrites of the
// code by optimizers will preserve the relative order of memory accesses.

//go:nosplit
func atomicload(ptr *uint32) uint32 {
	nop()
	return *ptr
}

// ... other atomic functions like xadd64, xchg64 ...

//go:nosplit
func xchgp(ptr unsafe.Pointer, new unsafe.Pointer) unsafe.Pointer {
	return xchgp1(noescape(ptr), new)
}

func xchgp1(ptr unsafe.Pointer, new unsafe.Pointer) unsafe.Pointer

// ... atomicstorep ...

func nop() // call to prevent inlining of function body
```
C言語の関数がGo言語の関数として再定義されています。`atomicload`のような単純な読み込みは直接Goで実装されています。`xadd64`や`xchg64`のような複雑なアトミック操作は、`cas64`（Compare-And-Swap）をループ内で使用する形でGoで実装されています。

注目すべきは、`//go:nosplit`と`//go:noescape`ディレクティブの使用です。`nosplit`は、これらの関数がスタックを拡張しないことを保証し、ランタイムのクリティカルなパスでの使用に適しています。`noescape`は、ポインタがヒープにエスケープしないことをコンパイラに伝え、より効率的なコード生成を可能にします。`xchgp`や`atomicstorep`のコメントは、`noescape`の適用に関するGoコンパイラのエスケープ解析の挙動を考慮した、ランタイム開発における深い理解を示しています。`nop()`関数の導入は、コンパイラによるインライン化を防ぎ、メモリ操作の順序を保証するためのテクニックです。

### `src/runtime/sys_arm.go` (例: `src/runtime/sys_arm.go`)

このファイルは、C言語で実装されていたシステム関連の低レベル関数をGo言語で再実装したものです。

**C言語 (`sys_arm.c`):**
```c
void
runtime·gostartcall(Gobuf *gobuf, void (*fn)(void), void *ctxt)
{
	if(gobuf->lr != 0)
		runtime·throw("invalid use of gostartcall");
	gobuf->lr = gobuf->pc;
	gobuf->pc = (uintptr)fn;
	gobuf->ctxt = ctxt;
}

// ... rewindmorestack ...
```

**Go言語 (`sys_arm.go`):**
```go
package runtime

import "unsafe"

func gostartcall(buf *gobuf, fn, ctxt unsafe.Pointer) {
	if buf.lr != 0 {
		gothrow("invalid use of gostartcall")
	}
	buf.lr = buf.pc
	buf.pc = uintptr(fn)
	buf.ctxt = ctxt
}

func rewindmorestack(buf *gobuf) {
	var inst uint32
	if buf.pc&3 == 0 && buf.pc != 0 {
		inst = *(*uint32)(unsafe.Pointer(buf.pc))
		if inst>>24 == 0x9a {
			buf.pc += uintptr(int32(inst<<8)>>6) + 8
			return
		}
	}

	print("runtime: pc=", hex(buf.pc), " ", hex(inst), "\\n")
	gothrow("runtime: misuse of rewindmorestack")
}
```
C言語の関数シグネチャがGo言語のそれに変換され、ポインタ操作は`unsafe.Pointer`を使用してGoの型システム内で安全に（ただし注意深く）行われています。`rewindmorestack`のような関数は、スタックの巻き戻しという非常に低レベルな操作を行いますが、これもGo言語で表現されています。

### `src/runtime/stubs.go`

このファイルは、Goランタイムの他の部分からC言語で実装された関数を呼び出すためのスタブ（宣言）を含んでいました。C言語ファイルがGo言語に変換されたため、これらのスタブの多くは不要となり、削除されました。

**削除されたスタブの例:**
```go
// func acquirem() *m
// func releasem(mp *m)
// func gomcache() *mcache
// func readgstatus(*g) uint32 // proc.c
// ...
// func starttheworld()
// func stoptheworld()
// func newextram()
// func lockOSThread()
// func unlockOSThread()
// ...
```
これらのスタブの削除は、GoランタイムがC言語の外部関数に依存しなくなったことを明確に示しています。

### `src/runtime/vlrt.c`

このファイルは完全に削除されました。これは、Goコンパイラとランタイムが進化し、このファイルで提供されていた64ビット整数演算や浮動小数点数変換などの機能が、Go言語自体で直接かつ効率的に実装できるようになったためです。`vlrt.c`はGo言語のコードからは直接呼び出されていなかったため、その削除はGoランタイムのC言語依存をさらに減らすことに貢献しました。

これらの変更は、GoランタイムのC言語からの脱却という大きな目標に向けた重要なステップであり、Go言語の自己完結性を高め、将来的な開発と最適化の道を拓くものです。

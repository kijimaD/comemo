# [インデックス 27471] ファイルの概要

このコミットは、Go言語の静的解析ツールである `go vet` の `cmd/vet` パッケージにおける `printf` ライクな関数のフォーマット引数検出ロジックを改善するものです。具体的には、外部パッケージで宣言された関数に対して `vet` がフォーマット文字列を正しく識別できない問題を解決し、より堅牢な解析を可能にしています。

## 元コミット内容

`cmd/vet`: `printf` ライクなフォーマット引数の検出を改善

以前は、フォーマット引数は関数型の引数をスキャンすることで検出されていました。
これは、関数が外部パッケージで宣言されている場合に、関数型を決定できないと機能しませんでした。
この場合、最初の文字列呼び出し引数をスキャンするようにフォールバックします。

`Fixes #14754`

## 変更の背景

`go vet` は、Goプログラムの静的解析を行い、潜在的なバグや疑わしいコードパターンを検出するツールです。その機能の一つに、`fmt.Printf` のような `printf` ライクな関数呼び出しにおけるフォーマット文字列と引数の整合性チェックがあります。例えば、`fmt.Printf("%d", "hello")` のように、`%d` (整数) のフォーマット指定子に対して文字列を渡すと `vet` は警告を発します。

この機能は、関数呼び出しのシグネチャ（引数の型と数）を解析し、どの引数がフォーマット文字列であるかを特定することで実現されていました。しかし、このコミット以前の `vet` の実装では、解析対象の `printf` ライクな関数が**外部パッケージ**で定義されている場合、その関数の型情報（`types.Signature`）を正確に取得できないことがありました。

型情報が取得できないと、`vet` はフォーマット文字列がどの引数であるかを特定できず、結果としてフォーマット文字列のチェックがスキップされたり、誤った解析が行われたりする問題が発生していました。これは、特に大規模なプロジェクトや、多くのサードパーティライブラリを使用するGoアプリケーションにおいて、`vet` の有用性を損なう可能性がありました。

このコミットは、この問題を解決し、外部パッケージの関数に対しても `printf` ライクなフォーマット引数をより確実に検出できるようにすることを目的としています。

## 前提知識の解説

### `go vet` とは

`go vet` は、Go言語の標準ツールチェーンに含まれる静的解析ツールです。コンパイルは通るものの、実行時に問題を引き起こす可能性のある疑わしいコード構造や一般的なエラーパターンを検出します。例えば、到達不能なコード、誤った構造体タグ、`printf` フォーマット文字列の不一致などをチェックします。

### `printf` ライクな関数とフォーマット文字列

`fmt.Printf` や `log.Printf` など、GoにはC言語の `printf` に似た動作をする関数が多数存在します。これらの関数は、第一引数に「フォーマット文字列」を取り、その後の引数をフォーマット文字列の指示に従って整形して出力します。フォーマット文字列には `%d` (整数)、`%s` (文字列)、`%v` (デフォルトフォーマット) などの「動詞（verb）」が含まれ、対応する型の引数を期待します。

### 可変長引数 (Variadic Arguments)

Goの関数は、最後の引数に `...T` の形式で可変長引数を取ることができます。これにより、関数は任意の数の引数を受け入れることができます。`printf` ライクな関数の多くは、フォーマット文字列の後に可変長引数 `...interface{}` を取ります。

### Goの型システムと `types` パッケージ

Goコンパイラは、プログラムの型情報を管理しています。`go vet` のようなツールは、`go/types` パッケージを利用して、プログラム内の識別子や式の型情報を取得します。
*   `types.Signature`: 関数のシグネチャ（引数と戻り値の型、可変長引数かどうか）を表す構造体です。
*   `types.Basic`: プリミティブ型（`int`, `string`, `bool` など）を表します。
*   `types.Type`: Goの型システムにおける任意の型を表すインターフェースです。

### GoのAST (Abstract Syntax Tree) と `ast` パッケージ

Goコンパイラは、ソースコードを解析して抽象構文木（AST）を構築します。`go/ast` パッケージは、このASTをプログラム的に操作するための機能を提供します。`go vet` はASTを走査し、特定のパターンや構造を検出します。
*   `ast.CallExpr`: 関数呼び出しを表すASTノードです。`Fun` フィールドには呼び出される関数、`Args` フィールドには引数のリストが含まれます。

### `go/constant` パッケージ

`go/constant` パッケージは、Goの定数値を表現するための型と関数を提供します。`vet` は、フォーマット文字列が定数であるかどうかを判断するためにこれを利用します。
*   `constant.String`: 文字列定数を表します。
*   `constant.StringVal(lit)`: `constant.Value` から文字列値を取得します。

## 技術的詳細

このコミットの核心は、`go vet` が `printf` ライクな関数のフォーマット文字列を特定するロジックの改善にあります。

### 以前の検出ロジックの問題点

以前の `vet` は、関数呼び出し `call` が与えられた際、まず `call.Fun` (呼び出される関数) の型情報を `f.pkg.types[call.Fun].Type` から取得し、それが `types.Signature` であることを期待していました。そして、その `types.Signature` を解析して、引数リストの中から `string` 型の引数を探し、それをフォーマット文字列と見なしていました。特に、可変長引数を持つ関数の場合、可変長引数の直前の `string` 型引数をフォーマット文字列と特定するロジックが用いられていました。

このアプローチは、`vet` が解析しているパッケージ内で定義された関数や、型情報が完全に解決できる場合には機能しました。しかし、問題は、**外部パッケージ**で定義された関数に対して `vet` が解析を行う場合でした。この場合、`f.pkg.types[call.Fun].Type` が `nil` を返したり、完全な `types.Signature` を提供できなかったりすることがありました。これにより、`vet` はフォーマット文字列を特定できず、結果として `printf` フォーマットチェックが正しく行われませんでした。

### 新しい検出ロジック

新しいロジックは、この問題を解決するために二段階のアプローチを採用しています。

1.  **第一段階（既存のロジックの改善）**:
    まず、以前と同様に `call.Fun` の型情報から `types.Signature` を取得しようと試みます。
    *   `types.Signature` が取得でき、かつ関数が可変長引数 (`sig.Variadic()`) を持つ場合、可変長引数の直前の引数（`sig.Params().Len() - 2` のインデックス）をフォーマット文字列候補とします。
    *   この候補が実際に文字列リテラルまたは文字列定数であるかを `stringLiteralArg` ヘルパー関数を使って確認します。
    *   この段階でフォーマット文字列が特定できれば、それが採用されます。

2.  **第二段階（フォールバックロジック）**:
    もし第一段階で `types.Signature` が取得できなかったり、取得できてもフォーマット文字列を特定できなかったりした場合（例えば、関数が可変長引数ではない場合や、可変長引数直前の引数が文字列ではない場合）、`vet` はより一般的なフォールバック戦略に切り替えます。
    *   関数呼び出し `call.Args` のすべての引数を先頭から順に走査します。
    *   `stringLiteralArg` ヘルパー関数を使用して、**最初に見つかった文字列リテラルまたは文字列定数**をフォーマット文字列として採用します。
    *   このフォールバックロジックは、`printf` ライクな関数の多くがフォーマット文字列を最初の引数として取るという一般的なパターンに基づいています。

この二段階のアプローチにより、`vet` は外部パッケージの関数に対しても、より高い確率でフォーマット文字列を正しく特定できるようになり、`printf` フォーマットチェックの信頼性が向上しました。

### `stringLiteralArg` ヘルパー関数

このコミットで新しく導入された `stringLiteralArg` 関数は、特定の引数が文字列リテラルまたは文字列定数であるかを効率的に判断するためのものです。
*   引数のASTノード (`arg`) を受け取り、`f.pkg.types[arg].Value` を使ってその引数の定数値を取得します。
*   取得した定数値が `nil` でなく、かつ `constant.String` 型であれば、その文字列値を返します。
*   これにより、`vet` は実行時に評価される可能性のある変数ではなく、コンパイル時に確定している文字列定数のみをフォーマット文字列として扱うことができます。

## コアとなるコードの解説

### `func formatString(f *File, call *ast.CallExpr) (string, int)`

この関数は、`printf` ライクな関数呼び出し `call` からフォーマット文字列とそのインデックスを特定する主要なロジックを含んでいます。

1.  **型シグネチャによる検出の試み**:
    ```go
    	typ := f.pkg.types[call.Fun].Type
    	if typ != nil {
    		if sig, ok := typ.(*types.Signature); ok {
    			if !sig.Variadic() {
    				// Skip checking non-variadic functions
    				return "", -1
    			}
    			idx := sig.Params().Len() - 2
    			if idx < 0 {
    				// Skip checking variadic functions without
    				// fixed arguments.
    				return "", -1
    			}
    			s, ok := stringLiteralArg(f, call, idx)
    			if !ok {
    				// The last argument before variadic args isn't a string
    				return "", -1
    			}
    			return s, idx
    		}
    	}
    ```
    *   まず、関数 `call.Fun` の型情報を `f.pkg.types[call.Fun].Type` から取得します。
    *   型が `types.Signature` であり、かつ関数が可変長引数 (`sig.Variadic()`) であることを確認します。
    *   可変長引数の直前の引数（`sig.Params().Len() - 2`）のインデックス `idx` を計算します。例えば、`func F(a, b string, args ...interface{})` の場合、`sig.Params().Len()` は3（`a`, `b`, `args`）なので、`idx` は `3 - 2 = 1` となり、`b` のインデックスを指します。
    *   `stringLiteralArg` を使って、その引数が文字列リテラルであるかを確認します。文字列であれば、その値とインデックスを返します。

2.  **フォールバックロジック**:
    ```go
    	// Cannot determine call's signature. Fallback to scanning for the first
    	// string argument in the call
    	for idx := range call.Args {
    		if s, ok := stringLiteralArg(f, call, idx); ok {
    			return s, idx
    		}
    	}
    	return "", -1
    ```
    *   型シグネチャからフォーマット文字列を特定できなかった場合、このフォールバックロジックが実行されます。
    *   `call.Args` (関数呼び出しの全引数) を先頭から順にループします。
    *   各引数に対して `stringLiteralArg` を呼び出し、最初に見つかった文字列リテラルをフォーマット文字列として採用し、その値とインデックスを返します。
    *   どの引数も文字列リテラルでなければ、空文字列と `-1` を返します。

### `func stringLiteralArg(f *File, call *ast.CallExpr, idx int) (string, bool)`

この関数は、指定されたインデックス `idx` の引数が文字列リテラルまたは文字列定数であるかをチェックします。

```go
func stringLiteralArg(f *File, call *ast.CallExpr, idx int) (string, bool) {
	if idx >= len(call.Args) {
		return "", false
	}
	arg := call.Args[idx]
	lit := f.pkg.types[arg].Value
	if lit != nil && lit.Kind() == constant.String {
		return constant.StringVal(lit), true
	}
	return "", false
}
```
*   まず、`idx` が引数の範囲内にあるかを確認します。
*   `arg := call.Args[idx]` で対象の引数ASTノードを取得します。
*   `lit := f.pkg.types[arg].Value` を使って、その引数の定数値を取得します。`f.pkg.types` は、`go/types` パッケージによって提供される型情報マップです。
*   `lit != nil && lit.Kind() == constant.String` で、取得した定数値が存在し、かつそれが文字列定数であるかを確認します。
*   条件を満たせば `constant.StringVal(lit)` で文字列値を取得し、`true` と共に返します。そうでなければ、空文字列と `false` を返します。

### `func (f *File) checkPrintf(call *ast.CallExpr, name string)`

この関数は、`printf` ライクな関数呼び出し `call` をチェックするメインの関数です。

```go
func (f *File) checkPrintf(call *ast.CallExpr, name string) {
	format, idx := formatString(f, call) // 新しいformatString関数を使用
	if idx < 0 {
		if *verbose {
			f.Warn(call.Pos(), "can't check non-constant format in call to", name)
		}
		return
	}
	// ... (以降のロジックはフォーマット文字列と引数の整合性チェック)
}
```
*   以前は `formatIndex(signature(f, call))` を直接呼び出していましたが、この変更により `formatString(f, call)` を呼び出すようになりました。
*   `formatString` がフォーマット文字列を特定できなかった場合 (`idx < 0`)、警告を出して処理を終了します。
*   フォーマット文字列が特定できた場合、その後のロジックでフォーマット文字列 (`format`) と残りの引数 (`call.Args[idx+1:]`) の整合性チェックが行われます。

これらの変更により、`go vet` は外部パッケージの関数に対しても、より正確かつ堅牢に `printf` フォーマットチェックを実行できるようになりました。

Goコンパイラは、プログラムの型情報を管理しています。`go vet` のようなツールは、`go/types` パッケージを利用して、プログラム内の識別子や式の型情報を取得します。
*   `types.Signature`: 関数のシグネチャ（引数と戻り値の型、可変長引数かどうか）を表す構造体です。
*   `types.Basic`: プリミティブ型（`int`, `string`, `bool` など）を表します。
*   `types.Type`: Goの型システムにおける任意の型を表すインターフェースです。

### GoのAST (Abstract Syntax Tree) と `ast` パッケージ

Goコンパイラは、ソースコードを解析して抽象構文木（AST）を構築します。`go/ast` パッケージは、このASTをプログラム的に操作するための機能を提供します。`go vet` はASTを走査し、特定のパターンや構造を検出します。
*   `ast.CallExpr`: 関数呼び出しを表すASTノードです。`Fun` フィールドには呼び出される関数、`Args` フィールドには引数のリストが含まれます。

### `go/constant` パッケージ

`go/constant` パッケージは、Goの定数値を表現するための型と関数を提供します。`vet` は、フォーマット文字列が定数であるかどうかを判断するためにこれを利用します。
*   `constant.String`: 文字列定数を表します。
*   `constant.StringVal(lit)`: `constant.Value` から文字列値を取得します。

## 技術的詳細

このコミットの核心は、`go vet` が `printf` ライクな関数のフォーマット文字列を特定するロジックの改善にあります。

### 以前の検出ロジックの問題点

以前の `vet` は、関数呼び出し `call` が与えられた際、まず `call.Fun` (呼び出される関数) の型情報を `f.pkg.types[call.Fun].Type` から取得し、それが `types.Signature` であることを期待していました。そして、その `types.Signature` を解析して、引数リストの中から `string` 型の引数を探し、それをフォーマット文字列と見なしていました。特に、可変長引数を持つ関数の場合、可変長引数の直前の `string` 型引数をフォーマット文字列と特定するロジックが用いられていました。

このアプローチは、`vet` が解析しているパッケージ内で定義された関数や、型情報が完全に解決できる場合には機能しました。しかし、問題は、**外部パッケージ**で定義された関数に対して `vet` が解析を行う場合でした。この場合、`f.pkg.types[call.Fun].Type` が `nil` を返したり、完全な `types.Signature` を提供できなかったりすることがありました。これにより、`vet` はフォーマット文字列を特定できず、結果として `printf` フォーマットチェックが正しく行われませんでした。

### 新しい検出ロジック

新しいロジックは、この問題を解決するために二段階のアプローチを採用しています。

1.  **第一段階（既存のロジックの改善）**:
    まず、以前と同様に `call.Fun` の型情報から `types.Signature` を取得しようと試みます。
    *   `types.Signature` が取得でき、かつ関数が可変長引数 (`sig.Variadic()`) を持つ場合、可変長引数の直前の引数（`sig.Params().Len() - 2` のインデックス）をフォーマット文字列候補とします。
    *   この候補が実際に文字列リテラルまたは文字列定数であるかを `stringLiteralArg` ヘルパー関数を使って確認します。
    *   この段階でフォーマット文字列が特定できれば、それが採用されます。

2.  **第二段階（フォールバックロジック）**:
    もし第一段階で `types.Signature` が取得できなかったり、取得できてもフォーマット文字列を特定できなかったりした場合（例えば、関数が可変長引数ではない場合や、可変長引数直前の引数が文字列ではない場合）、`vet` はより一般的なフォールバック戦略に切り替えます。
    *   関数呼び出し `call.Args` のすべての引数を先頭から順に走査します。
    *   `stringLiteralArg` ヘルパー関数を使用して、**最初に見つかった文字列リテラルまたは文字列定数**をフォーマット文字列として採用します。
    *   このフォールバックロジックは、`printf` ライクな関数の多くがフォーマット文字列を最初の引数として取るという一般的なパターンに基づいています。

この二段階のアプローチにより、`vet` は外部パッケージの関数に対しても、より高い確率でフォーマット文字列を正確に特定できるようになり、`printf` フォーマットチェックの信頼性が向上しました。

### `stringLiteralArg` ヘルパー関数

このコミットで新しく導入された `stringLiteralArg` 関数は、特定の引数が文字列リテラルまたは文字列定数であるかを効率的に判断するためのものです。
*   引数のASTノード (`arg`) を受け取り、`f.pkg.types[arg].Value` を使ってその引数の定数値を取得します。
*   取得した定数値が `nil` でなく、かつ `constant.String` 型であれば、その文字列値を返します。
*   これにより、`vet` は実行時に評価される可能性のある変数ではなく、コンパイル時に確定している文字列定数のみをフォーマット文字列として扱うことができます。

## コアとなるコードの解説

### `func formatString(f *File, call *ast.CallExpr) (string, int)`

この関数は、`printf` ライクな関数呼び出し `call` からフォーマット文字列とそのインデックスを特定する主要なロジックを含んでいます。

1.  **型シグネチャによる検出の試み**:
    ```go
    	typ := f.pkg.types[call.Fun].Type
    	if typ != nil {
    		if sig, ok := typ.(*types.Signature); ok {
    			if !sig.Variadic() {
    				// Skip checking non-variadic functions
    				return "", -1
    			}
    			idx := sig.Params().Len() - 2
    			if idx < 0 {
    				// Skip checking variadic functions without
    				// fixed arguments.
    				return "", -1
    			}
    			s, ok := stringLiteralArg(f, call, idx)
    			if !ok {
    				// The last argument before variadic args isn't a string
    				return "", -1
    			}
    			return s, idx
    		}
    	}
    ```
    *   まず、関数 `call.Fun` の型情報を `f.pkg.types[call.Fun].Type` から取得します。
    *   型が `types.Signature` であり、かつ関数が可変長引数 (`sig.Variadic()`) であることを確認します。
    *   可変長引数の直前の引数（`sig.Params().Len() - 2`）のインデックス `idx` を計算します。例えば、`func F(a, b string, args ...interface{})` の場合、`sig.Params().Len()` は3（`a`, `b`, `args`）なので、`idx` は `3 - 2 = 1` となり、`b` のインデックスを指します。
    *   `stringLiteralArg` を使って、その引数が文字列リテラルであるかを確認します。文字列であれば、その値とインデックスを返します。

2.  **フォールバックロジック**:
    ```go
    	// Cannot determine call's signature. Fallback to scanning for the first
    	// string argument in the call
    	for idx := range call.Args {
    		if s, ok := stringLiteralArg(f, call, idx); ok {
    			return s, idx
    		}
    	}
    	return "", -1
    ```
    *   型シグネチャからフォーマット文字列を特定できなかった場合、このフォールバックロジックが実行されます。
    *   `call.Args` (関数呼び出しの全引数) を先頭から順にループします。
    *   各引数に対して `stringLiteralArg` を呼び出し、最初に見つかった文字列リテラルをフォーマット文字列として採用し、その値とインデックスを返します。
    *   どの引数も文字列リテラルでなければ、空文字列と `-1` を返します。

### `func stringLiteralArg(f *File, call *ast.CallExpr, idx int) (string, bool)`

この関数は、指定されたインデックス `idx` の引数が文字列リテラルまたは文字列定数であるかをチェックします。

```go
func stringLiteralArg(f *File, call *ast.CallExpr, idx int) (string, bool) {
	if idx >= len(call.Args) {
		return "", false
	}
	arg := call.Args[idx]
	lit := f.pkg.types[arg].Value
	if lit != nil && lit.Kind() == constant.String {
		return constant.StringVal(lit), true
	}
	return "", false
}
```
*   まず、`idx` が引数の範囲内にあるかを確認します。
*   `arg := call.Args[idx]` で対象の引数ASTノードを取得します。
*   `lit := f.pkg.types[arg].Value` を使って、その引数の定数値を取得します。`f.pkg.types` は、`go/types` パッケージによって提供される型情報マップです。
*   `lit != nil && lit.Kind() == constant.String` で、取得した定数値が存在し、かつそれが文字列定数であるかを確認します。
*   条件を満たせば `constant.StringVal(lit)` で文字列値を取得し、`true` と共に返します。そうでなければ、空文字列と `false` を返します。

### `func (f *File) checkPrintf(call *ast.CallExpr, name string)`

この関数は、`printf` ライクな関数呼び出し `call` をチェックするメインの関数です。

```go
func (f *File) checkPrintf(call *ast.CallExpr, name string) {
	format, idx := formatString(f, call) // 新しいformatString関数を使用
	if idx < 0 {
		if *verbose {
			f.Warn(call.Pos(), "can't check non-constant format in call to", name)
		}
		return
	}
	// ... (以降のロジックはフォーマット文字列と引数の整合性チェック)
}
```
*   以前は `formatIndex(signature(f, call))` を直接呼び出していましたが、この変更により `formatString(f, call)` を呼び出すようになりました。
*   `formatString` がフォーマット文字列を特定できなかった場合 (`idx < 0`)、警告を出して処理を終了します。
*   フォーマット文字列が特定できた場合、その後のロジックでフォーマット文字列 (`format`) と残りの引数 (`call.Args[idx+1:]`) の整合性チェックが行われます。

これらの変更により、`go vet` は外部パッケージの関数に対しても、より正確かつ堅牢に `printf` フォーマットチェックを実行できるようになりました。

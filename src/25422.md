# [インデックス 25422] ファイルの概要

このコミットは、GoランタイムがAndroid/amd64環境でスレッドローカルストレージ (TLS) を適切に設定するための変更を導入しています。特に、Goのスケジューラが現在のゴルーチン (`g` ポインタ) のコンテキストにアクセスするために使用するTLSスロットを、Androidのリンカが自動的に処理しないという問題に対処しています。この解決策は、`%fs` セグメントレジスタからの固定オフセット (`0x1d0`) を利用するという、一時的かつ「ハック的」なアプローチを採用しています。

## 変更の背景

Goランタイムは、現在のゴルーチン (`g`) のコンテキストを効率的に取得するために、スレッドローカルストレージ (TLS) を利用しています。これは、Goのスケジューラがゴルーチンを切り替える際に、現在のゴルーチンの状態（スタック、レジスタなど）に素早くアクセスするために不可欠です。

しかし、Androidの`amd64`アーキテクチャ環境において、Androidのリンカ（Bionic libcの一部）は、Goランタイムが期待するようなTLSの自動的なセットアップを提供しませんでした。このため、GoプログラムがAndroid/amd64上で正しく動作するためには、Goランタイム自身がTLSスロットを明示的に設定する必要がありました。

このコミットは、この問題を解決するために導入されました。特に、`golang/go#10743`で報告された問題に対応しています。この解決策は、`darwin/386,amd64`環境で採用されているアプローチと同様に、`%fs`セグメントレジスタからの固定オフセットを使用して`g`ポインタのTLSスロットにアクセスするというものです。コミットメッセージでは、このアプローチが「disgusting and fragile（忌まわしく、脆い）」と表現されており、将来的にTLS IE (Initial Executable) モデルの実装を利用して改善される予定であることが示唆されています。

## 前提知識の解説

### 1. スレッドローカルストレージ (TLS: Thread-Local Storage)

TLSは、マルチスレッドプログラミングにおいて、各スレッドが自分専用のグローバル変数を持つためのメカニズムです。通常、グローバル変数はすべてのスレッドで共有されますが、TLS変数にアクセスすると、各スレッドは自分自身の独立したコピーを受け取ります。これにより、スレッド間のデータ競合を防ぎ、同期メカニズムの必要性を減らすことができます。

Goランタイムでは、現在のゴルーチン (`g`) のポインタをTLSに格納することで、どの関数からでも現在のゴルーチンコンテキストに高速にアクセスできるようにしています。これは、Goの軽量なゴルーチンとスケジューリングモデルにおいて非常に重要な最適化です。

### 2. Goの `g` ポインタ

Goのプログラムは、OSのスレッド上で多数のゴルーチンを多重化して実行します。各ゴルーチンは、独自のスタック、レジスタ、および実行コンテキストを持っています。Goランタイムは、現在の実行中のゴルーチンを識別するために、`g`という特殊なポインタを使用します。この`g`ポインタは、現在のゴルーチンの構造体 (`runtime.g` 型) を指し、そのゴルーチンの状態（スタック情報、スケジューラ情報など）にアクセスするために不可欠です。

`g`ポインタへのアクセスは非常に頻繁に行われるため、そのアクセスは可能な限り高速である必要があります。TLSは、この高速アクセスを実現するための一般的な方法の一つです。

### 3. CGO

CGOは、GoプログラムからC言語のコードを呼び出すためのGoの機能です。CGOを使用すると、GoとCのコード間でデータを受け渡ししたり、Cのライブラリ関数を呼び出したりできます。GoランタイムとOSの間の低レベルなインタラクション（スレッドの作成、シグナルハンドリング、TLSのセットアップなど）の多くは、CGOを介してCコードを利用して行われます。

### 4. x86-64アーキテクチャとFS/GSセグメントレジスタ

x86-64アーキテクチャでは、`FS`および`GS`セグメントレジスタが、スレッドローカルストレージ (TLS) のベースアドレスを指すために慣習的に使用されます。特にLinuxでは`FS`レジスタが、macOSでは`GS`レジスタがTLSのベースアドレスとして使われることが多いです。これらのレジスタは、メモリセグメントの開始アドレスを保持し、オフセットを加えることでTLS変数にアクセスできます（例: `MOVQ %fs:0x1d0, %rax` は`FS`レジスタが指すアドレスから`0x1d0`バイトオフセットしたメモリ位置の値を`RAX`レジスタにロードします）。

### 5. AndroidのBionic libcとリンカの特性

AndroidはLinuxカーネルをベースにしていますが、標準のGNU Cライブラリ (glibc) ではなく、Bionicと呼ばれる独自のCライブラリを使用しています。Bionicのリンカは、デスクトップLinuxのリンカとは異なるTLSの扱い方をすることがあり、Goランタイムが期待するようなTLSの自動的な初期化やリロケーションをサポートしていない場合があります。これが、Goランタイムが手動でTLSを設定する必要がある主な理由です。

### 6. ELF (Executable and Linkable Format) とTLSリロケーションタイプ

ELFは、Unix系システムで実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFファイルには、プログラムのコード、データ、およびリンカがプログラムをロードして実行するために必要な情報（リロケーションエントリなど）が含まれています。

TLSに関連する主要なリロケーションタイプには以下のようなものがあります。

*   **R_X86_64_TLSGD (TLS General Dynamic model)**: 最も柔軟なモデルで、TLS変数がどの共有ライブラリに存在してもアクセスできます。ただし、アクセスコードが最も複雑になります。
*   **R_X86_64_TLSLD (TLS Local Dynamic model)**: 実行可能ファイル内のTLS変数にアクセスする場合に、TLSGDよりも効率的です。
*   **R_X86_64_DTPOFF32/64 (TLS Initial Executable model)**: 実行可能ファイル内のTLS変数にアクセスする場合に、最も効率的なモデルです。TLS変数のオフセットがコンパイル時に決定できる場合に利用されます。
*   **R_X86_64_TPOFF32/64 (TLS Local Executable model)**: 現在のスレッドのTLSブロックの先頭からのオフセットとしてTLS変数を参照します。

このコミットでは、AndroidのリンカがこれらのリロケーションタイプをGoランタイムが期待するように処理しないため、Goが独自の「ハック」を実装する必要がありました。コミットメッセージで言及されている「TLS IE model implementation」は、将来的に`R_X86_64_DTPOFF32/64`のような効率的なモデルを利用して、現在の固定オフセットの「ハック」を置き換えることを示唆しています。

## 技術的詳細

このコミットの核心は、Android/amd64環境でGoランタイムの`g`ポインタを格納するためのTLSスロットを、OSのリンカに頼らずにGo自身が設定することにあります。

1.  **AndroidリンカのTLS非サポート**: AndroidのBionicリンカは、Goランタイムが`g`ポインタのために必要とするTLSのセットアップを自動的に行いません。これは、GoがCGOを介してOSスレッドを管理し、各OSスレッドにGoの`m` (machine) 構造体を関連付け、さらに`m`から現在の`g`ポインタにアクセスするという独自のランタイムモデルを持っているため、標準的なTLSの利用方法と異なるためです。

2.  **固定オフセット `0x1d0` の採用**: このコミットでは、`%fs`セグメントレジスタからの固定オフセット`0x1d0`を、`g`ポインタのTLSスロットとして使用するという「ハック」が導入されました。
    *   `%fs`はx86-64アーキテクチャでTLSベースアドレスを指すために使用されるレジスタです。
    *   `0x1d0`という値は、`src/runtime/cgo/gcc_android_amd64.c`内の`inittls`関数で動的に探索され、検証されます。この値は、Androidの特定のバージョン（API22, API23）のエミュレータで動作することが確認されていますが、AndroidのBionic libcの実装は変更される可能性があるため、非常に脆い（fragile）とされています。

3.  **`pthread_key_create`によるTLSスロットの動的検出**: `src/runtime/cgo/gcc_android_amd64.c`の`inittls`関数は、`pthread_key_create`を繰り返し呼び出し、`pthread_setspecific`で特定の「マジック値」をセットし、`%fs:0x1d0`からその値を読み出すことで、`0x1d0`オフセットが実際に利用可能で、Goが制御できるTLSスロットを指していることを確認します。これは、利用可能なTLSスロットを「力ずくで」見つけるようなアプローチであり、非常に非効率的で、環境依存性が高いことを示しています。

4.  **`darwin/386,amd64`との類似性**: コミットメッセージでは、このアプローチが`darwin/386,amd64`環境でのTLSセットアップに似ていると述べられています。macOSでも、Goランタイムは`GS`レジスタからの固定オフセットを使用して`g`ポインタのTLSスロットにアクセスする同様の「ハック」を採用していました。これは、特定のOS環境のリンカやCライブラリのTLSサポートがGoの要件を満たさない場合に、Goランタイムが独自の低レベルな解決策を講じる必要があることを示しています。

5.  **将来的な改善**: コミットメッセージでは、この「醜いハック」が将来的にTLS IE (Initial Executable) モデルの実装を利用して修正される予定であることが明記されています。TLS IEモデルは、TLS変数のオフセットがコンパイル時に決定できる場合に、より効率的なアクセスを提供します。これにより、固定オフセットに依存する脆い実装を、より堅牢で標準的な方法に置き換えることが期待されます。

### `src/runtime/cgo/gcc_android_amd64.c` (新規ファイル)

```c
#include <pthread.h>
#include "libcgo.h"

static pthread_key_t k1;
#define magic1 (0x23581321345589ULL)

static void
inittls(void)
{
    uint64 x;
    pthread_key_t tofree[128], k;
    int i, ntofree;

    // ... (コメントで「disgusting hack」と説明)
    // We chose %fs:0x1d0 which seems to work in testing with Android
    // emulators (API22, API23) but it may break any time.
    // ...
    // The linker and runtime hard-code this constant offset
    // from %fs where we expect to find g. Disgusting.
    // Known to src/cmd/link/internal/ld/sym.go:/0x1d0
    // and to src/runtime/sys_linux_amd64.s:/0x1d0 or /GOOS_android.
    // ...

    ntofree = 0;
    for(;;) {
        if(pthread_key_create(&k, nil) < 0) { /* エラー処理 */ }
        pthread_setspecific(k, (void*)magic1);
        asm volatile("movq %%fs:0x1d0, %0" : "=r"(x)); // %fs:0x1d0から値を読み込む
        pthread_setspecific(k, 0);
        if(x == magic1) { // 読み込んだ値がマジック値と一致すれば、このキーが0x1d0にマップされている
            k1 = k;
            break;
        }
        // ... (エラー処理と他のキーの解放)
    }
    // ... (他のキーの解放)
}

static void*
threadentry(void *v)
{
    ThreadStart ts;
    ts = *(ThreadStart*)v;
    free(v);
    pthread_setspecific(k1, (void*)ts.g); // gポインタをTLSにセット
    crosscall_amd64(ts.fn);
    return nil;
}

void (*x_cgo_inittls)(void) = inittls;
void* (*x_cgo_threadentry)(void*) = threadentry;
```
このファイルは、Android/amd64環境でのCGOスレッドの初期化とTLSセットアップを担当します。
*   `inittls`関数は、`pthread_key_create`を繰り返し呼び出し、`pthread_setspecific`で`magic1`という特定の値（`0x23581321345589ULL`）をTLSに設定します。その後、インラインアセンブリ`asm volatile("movq %%fs:0x1d0, %0" : "=r"(x));`を使って`%fs:0x1d0`から値を読み出し、それが`magic1`と一致するかどうかを検証します。一致した場合、その`pthread_key_t`が`k1`として保存され、`0x1d0`オフセットがGoのTLSスロットとして機能することが確認されます。これは、利用可能なTLSスロットを動的に「発見」する試みです。
*   `threadentry`関数は、CGOによって作成された新しいスレッドのエントリポイントです。ここで、`pthread_setspecific(k1, (void*)ts.g);`を呼び出すことで、現在のゴルーチン (`g`) のポインタを、先ほど`inittls`で特定したTLSスロットに格納します。
*   `x_cgo_inittls`と`x_cgo_threadentry`は、`gcc_linux_amd64.c`から呼び出されるフックとして機能します。

```assembly
TEXT runtime·settls(SB),NOSPLIT,$32
#ifdef GOOS_android
    // Same as in sys_darwin_386.s:/ugliness, different constant.
    // DI currently holds m->tls, which must be fs:0x1d0.
    // See cgo/gcc_android_amd64.c for the derivation of the constant.
    SUBQ    $0x1d0, DI  // In android, the tls base 
#else
    ADDQ    $8, DI    // ELF wants to use -8(FS)
#endif
    MOVQ    DI, SI
    MOVQ    $0x1002, DI    // ARCH_SET_FS
    MOVQ    $158, AX    // arch_prctl
    SYSCALL
    RET
```
`runtime·settls`関数は、現在のスレッドのTLSベースアドレスを設定するために使用されます。`GOOS_android`が定義されている場合（つまりAndroid環境の場合）、`DI`レジスタ（`m->tls`の値が格納されている）から`0x1d0`を減算します。これは、`%fs`レジスタが指すアドレスから`0x1d0`オフセットした位置にTLSスロットがあるという前提に基づいています。`arch_prctl`システムコールを使って、`FS`レジスタに計算されたTLSベースアドレスを設定します。これにより、Goランタイムは`%fs:0x1d0`を介して`g`ポインタにアクセスできるようになります。

これらの変更は、GoランタイムがAndroid/amd64環境でTLSを「手動で」設定し、`g`ポインタへの高速アクセスを可能にするための連携した努力を示しています。しかし、その実装は固定オフセットに依存しており、将来的な改善が期待される一時的な解決策であることが強調されています。

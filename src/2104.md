## 変更の背景

このコミットは、Goコンパイラの初期段階で報告された「bug 139」という特定のバグを修正するために行われました。コミットメッセージ自体は簡潔ですが、変更されたファイルとテストケースの移動から、このバグがコンパイラのコード生成フェーズ、特に条件分岐やブール式の評価に関連する問題であったことが推測されます。

`test/golden.out`の変更履歴を見ると、修正前は`bug139.go`のコンパイル時に「`fatal error: naddr: ONAME class x 5`」という致命的なエラーが発生していたことがわかります。このエラーメッセージは、コンパイラが`ONAME`（名前付きエンティティ、例えば変数）ノードのアドレスを適切に処理できない、またはそのクラス分類に問題があることを示唆しています。これは、コンパイラが特定の種類の変数や式を扱う際に、誤ったコードを生成しようとしたり、内部的な不整合に陥ったりしていた可能性が高いです。

このバグは、Goプログラムの正確なコンパイルを妨げるものであり、コンパイラの安定性と信頼性を確保するために修正が必要でした。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラのバックエンド、特にコード生成に関する基本的な知識が必要です。

*   **Goコンパイラ (6g)**: `6g`は、Go言語の初期のコンパイラの一つで、64ビットアーキテクチャ（x86-64）向けのコードを生成する役割を担っていました。Goコンパイラは、フロントエンド（構文解析、型チェックなど）とバックエンド（コード生成、最適化など）に分かれています。
*   **`src/cmd/6g/cgen.c`**: このファイルは、`6g`コンパイラのコード生成（`cgen`は"code generation"の略）の中核をなす部分です。抽象構文木（AST）をトラバースし、ターゲットアーキテクチャ（この場合はx86-64）の機械語命令に変換する処理が含まれています。
*   **抽象構文木 (AST)**: ソースコードの構造を木構造で表現したものです。コンパイラはASTを操作して、コードの解析、最適化、コード生成を行います。
*   **`Node`**: ASTの各要素（変数、リテラル、演算子など）を表すデータ構造です。
*   **`n->op`**: `Node`の操作の種類（オペレーションコード）を示します。例えば、`ONAME`は名前付きエンティティ、`OLITERAL`はリテラル値を表します。
*   **`bgen`関数**: この関数は、ブール式や条件分岐のコード生成を担当していると考えられます。`true`と`false`のパスに応じて、適切なジャンプ命令を生成します。
*   **`regalloc`**: レジスタ割り当てを行う関数。変数をレジスタに割り当てることで、高速なアクセスを可能にします。
*   **`cgen`**: 一般的なコード生成を行う関数。
*   **`nodconst`**: 定数ノードを作成する関数。
*   **`gins`**: 命令を生成する関数。
*   **`optoas`**: オペレーションコードをアセンブリ命令に変換する関数。
*   **`AJNE`, `AJMP`**: アセンブリのジャンプ命令。`AJNE`は"Jump if Not Equal"、`AJMP`は"Jump"（無条件ジャンプ）を意味します。
*   **`patch`**: ジャンプ命令のターゲットアドレスを後から埋める（パッチする）ための関数。
*   **`gbranch`**: ジャンプ命令を生成する関数。
*   **`n->addable`**: ノードが「アドレス可能」であるかを示すフラグ。つまり、そのノードがメモリ上の特定のアドレスを持つ単純な変数であるか、または複雑な式の結果であるかなどを区別するために使われます。`addable == 0`は、そのノードが直接アドレス可能ではないことを示唆します。

## 技術的詳細

このコミットの技術的な核心は、`bgen`関数における`OLITERAL`（リテラル値）と`ONAME`（名前付きエンティティ）の処理の改善にあります。

**1. `OLITERAL`（リテラル値）の処理の修正:**

修正前は、ブールリテラル（`true`や`false`）が条件式として使われた場合に、コンパイラが正しくコードを生成できない問題があった可能性があります。
変更点:
```c
- // need to ask if it is bool?
+ // need to ask if it is bool?
  if(!true == !n->val.u.bval)
  	patch(gbranch(AJMP, T), to);
```
この変更は、`OLITERAL`がブール値であるかどうかを判断し、その値に基づいて無条件ジャンプ（`AJMP`）を生成するロジックを追加しています。`!true == !n->val.u.bval`という条件は、リテラル値`n->val.u.bval`が現在の`true`パスと一致するかどうかをチェックしています。もし一致すれば、指定されたターゲット`to`へジャンプする命令を生成し、そのジャンプ命令のターゲットを後でパッチ（埋める）します。これにより、ブールリテラルが条件として使われた場合に、適切な分岐コードが生成されるようになりました。

**2. `ONAME`（名前付きエンティティ）の処理の修正:**

修正前は、`ONAME`ノードが「アドレス可能ではない」（`n->addable == 0`）場合に、コンパイラが誤った処理を行っていた可能性があります。`test/golden.out`のエラーメッセージ「`fatal error: naddr: ONAME class x 5`」は、まさにこの問題、つまり`ONAME`ノードのアドレス計算や分類に関する問題を示唆しています。
変更点:
```c
case ONAME:
+	if(n->addable == 0)
+		goto def;
 	nodconst(&n1, n->type, 0);
 	gins(optoas(OCMP, n->type), n, &n1);
 	a = AJNE;
```
この修正は、`ONAME`ノードが`addable == 0`（アドレス可能ではない）と判断された場合、`def:`ラベルにジャンプするようにしています。`def:`ラベルは、`bgen`関数のデフォルトの処理パスであり、`regalloc`（レジスタ割り当て）と`cgen`（一般的なコード生成）を通じて、より汎用的な方法でノードを処理します。これにより、コンパイラはアドレス可能ではない`ONAME`ノードを、特殊なケースとしてではなく、より一般的な式として扱うようになり、`naddr`エラーのような問題を回避できるようになりました。

要するに、このコミットは、Goコンパイラがブールリテラルや複雑な名前付きエンティティを条件式として扱う際の、コード生成の堅牢性を向上させたものです。

## コアとなるコードの解説

上記の差分は、`src/cmd/6g/cgen.c`ファイル内の`bgen`関数に対する変更を示しています。

1.  **`def:` ラベルの追加**:
    ```c
    	default:
    +	def:
    		regalloc(&n1, n->type, N);
    		cgen(n, &n1);
    		nodconst(&n2, n->type, 0);
    ```
    `default`ケースの直前に`def:`という新しいラベルが追加されました。これは、他の特定のケースで処理できないノードを、この汎用的なコード生成パスにフォールバックさせるためのジャンプターゲットとして機能します。このパスでは、ノードに対してレジスタ割り当て（`regalloc`）と一般的なコード生成（`cgen`）が行われます。

2.  **`OLITERAL` ケースの修正**:
    ```c
    	case OLITERAL:
    -// need to ask if it is bool?
    +\t\t// need to ask if it is bool?\
    \t\tif(!true == !n->val.u.bval)\
    \t\t\tpatch(gbranch(AJMP, T), to);\
    \t\tgoto ret;\
    ```
    `OLITERAL`（リテラル値）を処理する部分で、コメントアウトされていた行の後に新しい条件分岐ロジックが追加されました。
    -   `!true == !n->val.u.bval`: これは、現在の`bgen`関数が処理しているブールコンテキスト（`true`引数で示される）と、リテラルノード`n`のブール値（`n->val.u.bval`）が一致するかどうかをチェックしています。
    -   `patch(gbranch(AJMP, T), to);`: もし条件が一致すれば、無条件ジャンプ命令（`AJMP`）を生成し、そのジャンプ先を`to`（`bgen`関数の引数で渡されるターゲット）に設定します。`patch`は、生成されたジャンプ命令のターゲットアドレスを後で解決するために使用されます。
    この変更により、ブールリテラルが条件式として使われた場合に、コンパイラが正しい分岐命令を生成できるようになりました。

3.  **`ONAME` ケースの修正**:
    ```c
    	case ONAME:
    +	if(n->addable == 0)
    +		goto def;
    \t\tnodconst(&n1, n->type, 0);\
    \t\tgins(optoas(OCMP, n->type), n, &n1);\
    \t\ta = AJNE;\
    ```
    `ONAME`（名前付きエンティティ、例えば変数）を処理する部分に新しい条件分岐が追加されました。
    -   `if(n->addable == 0)`: これは、現在の`ONAME`ノードが「アドレス可能ではない」場合に真となります。`addable`フラグは、ノードがメモリ上の直接的なアドレスを持つ単純な変数であるか、あるいはより複雑な式の結果であるかなどを区別するために使われます。
    -   `goto def;`: もしノードがアドレス可能ではない場合、処理は新しく追加された`def:`ラベルにジャンプします。これにより、このような複雑な`ONAME`ノードは、`bgen`関数の汎用的なコード生成パスで処理されるようになり、以前発生していた`naddr`エラーのような問題を回避できます。

これらの変更は、Goコンパイラがブールリテラルや、アドレス計算が複雑な名前付きエンティティを扱う際のロジックを改善し、より堅牢なコード生成を可能にしました。

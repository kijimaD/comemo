# [インデックス 27917] ファイルの概要

このコミットは、Go言語の`debug/pe`パッケージに`StringTable`型を導入し、PE (Portable Executable) ファイルにおける長いセクション名やシンボル名の処理を改善するものです。具体的には、PEファイルの仕様で規定されている文字列テーブルからの名前の読み取り機能が実装されています。

## 元コミット内容

PE (Portable Executable) の仕様では、長いセクション名やシンボル名はPE文字列テーブルに格納される必要があります。このコミットは、この機能を実現する`StringTable`を導入します。現時点では、文字列テーブルの読み取りのみが実装されています。

Issue #15345 を更新します。

## 変更の背景

Windowsの実行可能ファイル形式であるPEファイルは、COFF (Common Object File Format) 形式をベースにしています。COFF形式では、セクション名やシンボル名などの識別子を格納する際に、固定長の領域が割り当てられています。しかし、この固定長を超える長い名前を使用したい場合、その名前全体をオブジェクトファイル内の別の場所に格納し、固定長領域にはその名前が格納されている場所へのオフセット（ポインタ）を記述するという仕組みが採用されています。この「別の場所」がCOFF文字列テーブルです。

Go言語の`debug/pe`パッケージは、PEファイルを解析するためのライブラリですが、これまでの実装では、このCOFF文字列テーブルからの長い名前の読み取りに対応していませんでした。そのため、長いセクション名やシンボル名を持つPEファイルを正確に解析できないという問題がありました。このコミットは、この欠落していた機能、特に文字列テーブルからの読み取り機能を追加することで、`debug/pe`パッケージの堅牢性と互換性を向上させることを目的としています。

関連するIssue #15345は、まさにこの長いシンボル名の処理に関するもので、`debug/pe`が長いシンボル名を正しく読み取れないという報告がなされていました。このコミットは、その問題を解決するための直接的な対応となります。

## 前提知識の解説

### PE (Portable Executable) ファイル形式

PEファイル形式は、Windowsオペレーティングシステムで使用される実行可能ファイル、オブジェクトコード、DLL (Dynamic Link Library) などのファイル形式です。COFF (Common Object File Format) をベースにしており、ヘッダ、セクションテーブル、セクションデータなどで構成されます。

### COFF (Common Object File Format)

COFFは、Unix系システムで広く使われていたオブジェクトファイル形式であり、PEファイル形式の基盤となっています。COFFファイルは、ヘッダ、オプションヘッダ、セクションヘッダ、セクションデータ、シンボルテーブル、文字列テーブルなどから構成されます。

### COFFシンボルテーブル

COFFファイルには、プログラム内のシンボル（関数名、変数名など）に関する情報が格納されるシンボルテーブルが存在します。各シンボルエントリは固定長であり、シンボル名、値、セクション番号、型などの情報を含みます。

### COFF文字列テーブル

COFFシンボルテーブルのシンボル名フィールドは通常8バイトの固定長です。もしシンボル名が8バイト以下であれば、その名前はシンボルエントリ自体に直接格納されます。しかし、シンボル名が8バイトを超える場合、シンボルエントリの最初の4バイトには0が格納され、次の4バイトにはCOFF文字列テーブル内の名前へのオフセットが格納されます。COFF文字列テーブルは、COFFシンボルテーブルの直後に配置され、可変長の文字列が格納されます。テーブルの先頭には、テーブル全体のサイズ（バイト単位）が格納されます。

### `io.ReaderAt` と `io.ReadSeeker` インターフェース

Go言語の`io`パッケージで定義されているインターフェースです。
- `io.ReaderAt`: 任意のオフセットからデータを読み取る機能を提供します。ファイルのランダムアクセスに適しています。
- `io.ReadSeeker`: 読み取り (`Read`) とシーク (`Seek`) の両方の機能を提供します。ファイル内の現在位置を変更しながら読み進めることができます。

## 技術的詳細

このコミットの主要な変更点は、`debug/pe`パッケージに`StringTable`型を導入し、PEファイル内のCOFF文字列テーブルを読み取る機能を追加したことです。

1.  **`StringTable`型の導入**:
    `type StringTable []byte` として定義され、COFF文字列テーブルの生データをバイトスライスとして保持します。

2.  **`readStringTable`関数の追加**:
    この関数は、`FileHeader`と`io.ReadSeeker`を受け取り、COFF文字列テーブルを読み込んで`StringTable`型を返します。
    - COFF文字列テーブルは、COFFシンボルテーブルの直後に配置されるというPE/COFFの仕様に基づき、`FileHeader.PointerToSymbolTable`と`FileHeader.NumberOfSymbols`から文字列テーブルの開始オフセットを計算します。
    - `io.ReadSeeker`の`Seek`メソッドを使用して、計算されたオフセットに移動します。
    - 文字列テーブルの最初の4バイトはテーブル全体のサイズ（バイト単位）を表すため、`binary.Read`でこのサイズを読み取ります。
    - 読み取ったサイズから4バイト（自身のサイズ）を引いた残りのバイト数を`make([]byte, l)`でバッファとして確保し、`io.ReadFull`で文字列テーブルのデータを読み込みます。
    - 読み込んだバイトスライスを`StringTable`型にキャストして返します。

3.  **`StringTable.String`メソッドの追加**:
    このメソッドは、`StringTable`から指定されたオフセット`start`にある文字列を抽出します。
    - `start`オフセットは、文字列テーブルのサイズ情報（最初の4バイト）を含んだオフセットとして渡されるため、実際のデータ開始位置に合わせるために`start - 4`の調整が行われます。
    - オフセットが文字列テーブルの範囲内にあるかどうかの検証が行われます。
    - 内部で`cstring`関数を呼び出し、指定されたオフセットからヌル終端文字列を抽出します。

4.  **`File`構造体への`StringTable`フィールドの追加**:
    `debug/pe.File`構造体に`StringTable StringTable`フィールドが追加され、PEファイル全体を解析する際に文字列テーブルの情報が保持されるようになります。

5.  **`NewFile`関数での`StringTable`の読み込み**:
    `NewFile`関数内で、`readStringTable`が呼び出され、PEファイルの解析時に文字列テーブルが読み込まれ、`File`構造体の`StringTable`フィールドに格納されます。

6.  **`cstring`関数の移動と修正**:
    元々`file.go`にあった`cstring`関数（バイトスライスからヌル終端文字列を抽出するヘルパー関数）が、新しく作成された`string.go`ファイルに移動されました。これにより、文字列テーブル関連のロジックが一箇所に集約され、コードのモジュール性が向上しています。また、`cstring(b []byte) string`の引数`b`の型が`b[:i]`に変更され、より正確なスライス操作が行われるようになりました。

+func cstring(b []byte) string {
+	var i int
+	for i = 0; i < len(b) && b[i] != 0; i++ {
+	}

+// StringTable is a COFF string table.
+type StringTable []byte
+
+func readStringTable(fh *FileHeader, r io.ReadSeeker) (StringTable, error) {
+	// COFF string table is located right after COFF symbol table.
+	offset := fh.PointerToSymbolTable + COFFSymbolSize*fh.NumberOfSymbols
+	_, err := r.Seek(int64(offset), io.SeekStart)
+	if err != nil {
+		return nil, fmt.Errorf("fail to seek to string table: %v", err)
+	}
+	var l uint32
+	err = binary.Read(r, binary.LittleEndian, &l)
+	if err != nil {
+		return nil, fmt.Errorf("fail to read string table length: %v", err)
+	}
+	// string table length includes itself
+	if l <= 4 {
+		return nil, nil
+	}
+	l -= 4
+	buf := make([]byte, l)
+	_, err = io.ReadFull(r, buf)
+	if err != nil {
+		return nil, fmt.Errorf("fail to read string table: %v", err)
+	}
+	return StringTable(buf), nil
+}
+
+// TODO(brainman): decide if start parameter should be int instead of uint32
+
+// String extracts string from COFF string table st at offset start.
+func (st StringTable) String(start uint32) (string, error) {
+	// start includes 4 bytes of string table length
+	if start < 4 {
+		return "", fmt.Errorf("offset %d is before the start of string table", start)
+	}
+	start -= 4
+	if int(start) > len(st) {
+		return "", fmt.Errorf("offset %d is beyond the end of string table", start)
+	}
+	return cstring(st[start:]), nil

## コアとなるコードの解説

このコミットの核となるのは、`src/debug/pe/string.go`で定義されている`StringTable`型と、それに関連する`readStringTable`関数、そして`StringTable.String`メソッドです。

-   **`StringTable`型**: `type StringTable []byte` は、COFF文字列テーブルの生データをバイトスライスとして抽象化します。これにより、文字列テーブルのデータへのアクセスと操作が容易になります。

-   **`readStringTable`関数**:
    -   この関数は、PEファイルのヘッダ情報 (`*FileHeader`) と、ファイルの内容を読み取るための`io.ReadSeeker`インターフェースを受け取ります。
    -   `offset := fh.PointerToSymbolTable + COFFSymbolSize*fh.NumberOfSymbols` の行で、COFFシンボルテーブルの終了位置、すなわちCOFF文字列テーブルの開始位置を計算しています。`COFFSymbolSize`はCOFFシンボルエントリの固定長サイズ（通常18バイト）です。
    -   `r.Seek(int64(offset), io.SeekStart)` を使用して、ファイルポインタを文字列テーブルの開始位置に移動させます。
    -   `binary.Read(r, binary.LittleEndian, &l)` で、文字列テーブルの最初の4バイトを読み込み、テーブル全体のサイズ`l`（`uint32`型）を取得します。PE/COFFの仕様では、このサイズには自身の4バイトも含まれます。
    -   `if l <= 4 { return nil, nil }` は、文字列テーブルが空であるか、サイズ情報のみで実データがない場合のハンドリングです。
    -   `l -= 4` で、テーブル全体のサイズから自身のサイズを引くことで、純粋な文字列データのサイズを計算します。
    -   `buf := make([]byte, l)` で、文字列データを格納するためのバイトスライスを確保します。
    -   `io.ReadFull(r, buf)` で、残りの文字列データをバッファに読み込みます。
    -   最終的に、読み込んだ`buf`を`StringTable(buf)`として型変換し、返します。

-   **`StringTable.String(start uint32) (string, error)`メソッド**:
    -   このメソッドは、`StringTable`のインスタンスに対して呼び出され、指定された`start`オフセットからヌル終端文字列を抽出します。
    -   `start < 4` のチェックは、渡されたオフセットが文字列テーブルのサイズ情報（最初の4バイト）よりも前を指している場合にエラーを返すためのものです。
    -   `start -= 4` は、外部から渡されるオフセットが文字列テーブルのサイズ情報を含んだものであるため、実際の文字列データが始まる位置に調整するためのものです。
    -   `int(start) > len(st)` のチェックは、オフセットが文字列テーブルの範囲を超えている場合にエラーを返すためのものです。
    -   `cstring(st[start:])` を呼び出すことで、指定されたオフセットから始まるバイトスライスからヌル終端文字列を効率的に抽出します。

-   **`cstring(b []byte) string`関数**:
    -   このヘルパー関数は、バイトスライス`b`を受け取り、最初のヌルバイト (`0`) が見つかるまでの部分をGoの`string`型に変換します。これは、C言語スタイルのヌル終端文字列を扱うための標準的なパターンです。

これらの変更により、`debug/pe`パッケージはPEファイル内の長いセクション名やシンボル名を、COFF文字列テーブルから正確に読み取ることができるようになり、PEファイルの解析能力が向上しました。

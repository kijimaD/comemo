# [インデックス 25206] ファイルの概要

このコミットは、GoランタイムのARM64アーキテクチャ向け`memmove`（メモリコピー）および`memclr`（メモリクリア）関数において、パフォーマンス最適化を目的とした変更を導入します。具体的には、これらの関数が可能な限りワード（64ビット、8バイト）単位で操作を行うように調整され、これにより特に大きなメモリブロックの処理速度が大幅に向上しています。同時に、ガベージコレクタ（GC）が部分的に書き込まれたポインタを誤って参照しないようにするための安全対策も考慮されています。

## 変更の背景

このコミットの主な目的は、ARM64アーキテクチャにおけるGoランタイムの`memmove`および`memclr`関数のパフォーマンスを向上させることです。これらの関数は、メモリのコピーやクリアといった基本的な操作を行うため、Goプログラム全体の実行速度に大きな影響を与えます。

従来のバイト単位でのメモリ操作は、特に現代の64ビットプロセッサにおいては効率が悪い場合があります。CPUは通常、一度に複数のバイト（ワード単位）を処理できるため、この能力を最大限に活用することで、より高速なメモリ操作が期待できます。

コミットメッセージに示されているベンチマーク結果は、この最適化の有効性を明確に示しています。特に、16バイト以上の大きなメモリブロックを扱う場合、`memmove`と`memclr`の両方で顕著な速度向上が見られます。例えば、`BenchmarkMemmove4096-4`では約7.91倍、`BenchmarkMemclr65536-4`では約8.39倍の速度向上を達成しています。

一方で、1バイトから7バイト程度の小さなサイズでは、わずかながら性能が低下しているケースも確認できます。これは、ワード単位での処理に切り替えるためのオーバーヘッドが、小さなデータ量では相対的に大きくなるためと考えられます。しかし、全体としては、より頻繁に発生するであろう大きなメモリ操作の高速化が、小さな操作のわずかな性能低下を上回るメリットをもたらすと判断されたのでしょう。

また、この変更にはGoのガベージコレクタ（GC）との連携という重要な考慮事項があります。GCがメモリをスキャンする際に、部分的に書き込まれたポインタを誤って参照してしまうと、プログラムのクラッシュや不正な動作につながる可能性があります。そのため、メモリ操作はGCに対して安全な方法で行われる必要があり、この制約が実装の複雑さに影響を与えています。コミットの作者は、より洗練された最適化（例：`ldp`/`stp`命令による16バイト単位の移動やループアンロール）も可能であると認識しつつも、GCの安全性を確保しつつ、シンプルで「合理的に明らかに正しい」実装を選択したと述べています。

## 前提知識の解説

### ARM64アーキテクチャ

ARM64（またはAArch64）は、ARMv8-A命令セットアーキテクチャに基づく64ビットプロセッサの総称です。スマートフォン、タブレット、サーバー、組み込みシステムなど、幅広いデバイスで利用されています。ARM64プロセッサは、64ビットの汎用レジスタを持ち、一度に64ビット（8バイト）のデータを処理する能力に優れています。この64ビットのデータ単位を「ワード」と呼びます。メモリ操作において、CPUのネイティブなワードサイズでデータを扱うことは、バイト単位で扱うよりもはるかに効率的です。

### `memmove`と`memclr`

*   **`memmove`**: メモリブロックを別のメモリブロックにコピーする関数です。C言語の標準ライブラリにも存在する関数で、Goランタイムでも内部的に使用されます。特に、コピー元とコピー先のメモリ領域がオーバーラップしている場合でも正しく動作するように設計されている点が特徴です。オーバーラップしている場合は、コピー方向を調整することでデータの破壊を防ぎます（順方向または逆方向）。
*   **`memclr`**: メモリブロックを指定されたバイト数だけゼロでクリア（初期化）する関数です。これもGoランタイムの内部で、新しいメモリ領域の初期化や、不要になったメモリ領域のクリアなどに使用されます。

これらの関数は、Goのガベージコレクタ（GC）がメモリを管理する上で非常に重要であり、パフォーマンスがクリティカルな部分です。

### アセンブリ言語とGoランタイム

Go言語のランタイムは、Go言語自体で書かれている部分が多いですが、パフォーマンスが極めて重要な部分（スケジューラ、GC、特定のメモリ操作など）や、特定のハードウェア機能に直接アクセスする必要がある部分では、アセンブリ言語が使用されます。`memmove`や`memclr`のような低レベルのメモリ操作は、まさにアセンブリ言語で最適化される典型的な例です。これにより、CPUの命令セットを最大限に活用し、Go言語のコンパイラが生成するコードよりも高速な実行を実現できます。

### メモリのアライメント

メモリのアライメントとは、データがメモリ上で特定のバイト境界に配置されることを指します。例えば、64ビット（8バイト）のワードを扱う場合、そのデータが8の倍数のアドレスから始まるように配置されていると「8バイトアラインされている」と言います。多くのCPUアーキテクチャでは、アラインされたデータへのアクセスは、アラインされていないデータへのアクセスよりも高速です。場合によっては、アラインされていないデータへのアクセスがパフォーマンスを著しく低下させたり、ハードウェア例外を引き起こしたりすることもあります。

このコミットでは、メモリ操作をワード単位で行うことでパフォーマンスを向上させようとしていますが、コピー元やコピー先のメモリブロックが常にワードアラインされているとは限りません。そのため、アラインされていない部分（残りのバイト）はバイト単位で処理し、アラインされた部分をワード単位で処理するというハイブリッドなアプローチが取られます。

### Goのガベージコレクション (GC) とポインタの安全性

Goは自動メモリ管理（ガベージコレクション）を採用しています。GCは、プログラムが使用しなくなったメモリ領域を自動的に解放する役割を担います。GCが動作する際、ヒープ上のオブジェクトをスキャンして、どのオブジェクトがまだ参照されているかを判断します。

このスキャン中に、`memmove`のようなメモリ操作が途中で行われ、ポインタが部分的に書き換えられた状態（例えば、ポインタの半分だけが新しい値になり、残りの半分は古い値のまま）でGCがそのメモリ領域をスキャンしてしまうと、GCは不正なポインタを読み取ってしまい、誤った判断を下す可能性があります。これは、プログラムのクラッシュやメモリリーク、データ破損といった深刻な問題を引き起こす可能性があります。

したがって、`memmove`や`memclr`のようなポインタを含む可能性のあるメモリ領域を操作する関数は、GCがスキャンするタイミングと競合しないように、あるいはGCがスキャンしても安全なように、細心の注意を払って実装される必要があります。コミットメッセージの「GCが部分的に書き込まれたポインタを見ないようにする必要がある」という記述は、この安全性の要件を指しています。

### ベンチマーク

ベンチマークは、プログラムや特定の関数の性能を測定するためのテストです。このコミットでは、`BenchmarkMemmove`や`BenchmarkMemclr`といったベンチマークが使用され、変更前後のメモリ操作の速度（MB/s）を比較しています。これにより、最適化が実際にどの程度の効果をもたらしたかを定量的に評価できます。ベンチマーク結果は、異なるサイズのメモリブロックに対する性能変化を示しており、最適化の有効範囲や潜在的な回帰（性能低下）を特定するのに役立ちます。

## 技術的詳細

このコミットにおける`memmove`と`memclr`の最適化は、主に以下の技術的アプローチに基づいています。

1.  **ワード単位処理の導入**:
    ARM64アーキテクチャでは、64ビット（8バイト）がネイティブなワードサイズです。CPUは一度に8バイトのデータをロード/ストアする命令（例: `MOVD`）を持つため、これを活用することで、バイト単位の操作よりもはるかに効率的にメモリを処理できます。
    変更されたアセンブリコードでは、コピー/クリアする合計サイズ`N`を、ワード単位で処理できる部分 (`N & ~7`、つまり8の倍数部分) と、残りのバイト単位で処理する必要がある部分 (`N & 7`、つまり0〜7バイト) に分割します。

2.  **`memclr`の最適化**:
    `memclr`はメモリ領域をゼロで埋めるため、ポインタの整合性に関する懸念は`memmove`ほど複雑ではありませんが、GCの安全性は依然として重要です。
    変更後、`memclr_arm64.s`では、まず8バイト単位でゼロを書き込むループ (`wordloop`) を実行し、その後、残りのバイトを1バイト単位でゼロを書き込むループ (`byteloop`) を実行します。これにより、大きな領域では高速なワード単位操作が適用されます。

3.  **`memmove`の最適化とオーバーラップ処理**:
    `memmove`はコピー元とコピー先がオーバーラップする可能性があるため、コピー方向を考慮する必要があります。
    *   **順方向コピー (Forward Copy)**: コピー元アドレスがコピー先アドレスよりも小さい場合（`src < dst`）、またはオーバーラップしない場合、メモリは先頭から末尾に向かってコピーされます。この場合、まずワード単位でコピー (`forwardlargeloop`で`MOVD.P`を使用) し、その後残りのバイトをコピー (`forwardtailloop`で`MOVBU.P`を使用) します。
    *   **逆方向コピー (Backward Copy)**: コピー元アドレスがコピー先アドレスよりも大きい場合（`src > dst`）で、かつオーバーラップしている場合、メモリは末尾から先頭に向かってコピーされます。これにより、まだコピーされていない元のデータが上書きされるのを防ぎます。この場合、まず残りのバイトを末尾からコピー (`backwardtailloop`で`MOVBU.W`を使用) し、その後ワード単位で末尾からコピー (`backwardlargeloop`で`MOVD.W`を使用) します。

4.  **GCの安全性への配慮**:
    コミットメッセージで「GCが部分的に書き込まれたポインタを見ないようにする必要がある」と明記されているように、メモリ操作中にポインタが一時的に不正な状態になることを避けるための工夫がされています。アセンブリコードのコメントにも、より高度な最適化（例: `ldp`/`stp`命令による16バイト単位の移動）が可能であるにもかかわらず、シンプルで「合理的に明らかに正しい」実装が選ばれた理由として、このGCの安全性が挙げられています。これは、ポインタを含む可能性のあるメモリ領域を操作する際に、アトミック性や特定の順序での書き込みが求められることを示唆しています。

5.  **アセンブリ命令の選択**:
    *   `MOVD.P 8(R4), R8`: ARM64の`LDR`命令に相当し、`R4`が指すアドレスから8バイト（ワード）を`R8`にロードし、`R4`を8バイト進めます（ポストインクリメント）。
    *   `MOVD.P R8, 8(R3)`: ARM64の`STR`命令に相当し、`R8`の値を`R3`が指すアドレスに8バイト（ワード）ストアし、`R3`を8バイト進めます（ポストインクリメント）。
    *   `MOVBU.P 1(R4), R8`: ARM64の`LDRB`命令に相当し、`R4`が指すアドレスから1バイトを`R8`にロードし、`R4`を1バイト進めます（ポストインクリメント）。
    *   `MOVBU.P R8, 1(R3)`: ARM64の`STRB`命令に相当し、`R8`の値を`R3`が指すアドレスに1バイトストアし、`R3`を1バイト進めます（ポストインクリメント）。
    *   `MOVD.W -8(R4), R8`: ARM64の`LDR`命令に相当し、`R4`が指すアドレスから8バイト手前のアドレスから8バイト（ワード）を`R8`にロードし、`R4`を8バイト戻します（プリデクリメント）。逆方向コピーで使用されます。
    *   `MOVD.W R8, -8(R3)`: ARM64の`STR`命令に相当し、`R8`の値を`R3`が指すアドレスから8バイト手前のアドレスに8バイト（ワード）ストアし、`R3`を8バイト戻します（プリデクリメント）。逆方向コピーで使用されます。

    これらの命令は、ループ内でポインタの更新とデータ転送を効率的に行うために選択されています。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/runtime/memclr_arm64.s`**:
    *   `runtime·memclr`関数の実装が変更されました。
    *   以前はバイト単位でメモリをクリアするループのみでしたが、変更後はまずワード（8バイト）単位でクリアできる部分を処理し、その後残りのバイトをクリアするロジックが追加されました。
    *   具体的には、クリアするサイズ`N`を8の倍数部分 (`R5`) と残りのバイト部分 (`R6`) に分割し、`wordloop`で`MOVD.P $0, 8(R3)`（8バイトゼロ書き込み）を、`byteloop`で`MOVBU.P $0, 1(R3)`（1バイトゼロ書き込み）を使用しています。

2.  **`src/runtime/memmove_arm64.s`**:
    *   `runtime·memmove`関数の実装が大幅に変更されました。
    *   以前はバイト単位でメモリを移動するループのみでしたが、変更後はコピー方向（順方向/逆方向）に応じて、ワード単位での移動とバイト単位での移動を組み合わせるロジックが導入されました。
    *   コピーするサイズ`N`を8の倍数部分 (`R7`) と残りのバイト部分 (`R6`) に分割します。
    *   **順方向コピー (`forward`ラベル以降)**: まずワード単位でコピー (`forwardlargeloop`で`MOVD.P 8(R4), R8`と`MOVD.P R8, 8(R3)`) し、その後残りのバイトをコピー (`forwardtailloop`で`MOVBU.P 1(R4), R8`と`MOVBU.P R8, 1(R3)`) します。
    *   **逆方向コピー (`backward`ラベル以降)**: まず残りのバイトを末尾からコピー (`backwardtailloop`で`MOVBU.W -1(R4), R8`と`MOVBU.W R8, -1(R3)`) し、その後ワード単位で末尾からコピー (`backwardlargeloop`で`MOVD.W -8(R4), R8`と`MOVD.W R8, -8(R3)`) します。

3.  **`src/runtime/memmove_test.go`**:
    *   アラインメントされていないメモリコピーのパフォーマンスを測定するための新しいベンチマーク関数 `bmMemmoveUnaligned` および関連する`BenchmarkMemmoveUnaligned*`関数が追加されました。
    *   これは、`copy(x[1:], y)`のように、コピー元またはコピー先（あるいはその両方）がワード境界にアラインされていない状況をシミュレートし、最適化がアラインされていないケースでどのように機能するかを評価するために重要です。

## コアとなるコードの解説

### `src/runtime/memclr_arm64.s` の変更点

```assembly
TEXT runtime·memclr(SB),NOSPLIT,$0-16
 	MOVD	ptr+0(FP), R3 // R3 = ptr (クリア対象メモリの開始アドレス)
 	MOVD	n+8(FP), R4  // R4 = n (クリアするバイト数)

 	// TODO(mwhudson): this is written this way to avoid tickling
 	// warnings from addpool when written as AND $7, R4, R6 (see
 	// https://golang.org/issue/12708)
 	AND	$~7, R4, R5	// R5 = n & ~7 (nを8で割った商 * 8、つまり8バイト単位で処理できる部分のサイズ)
 	SUB	R5, R4, R6	// R6 = n & 7 (nを8で割った余り、つまり残りのバイト数)

 	CMP	$0, R5
 	BEQ	nowords		// 8バイト単位で処理する部分がなければ、直接バイト単位処理へ

 	ADD	R3, R5, R5	// R5 = ptr + (8バイト単位処理部分のサイズ)、つまり8バイト単位処理の終了アドレス

wordloop: // TODO: Optimize for unaligned ptr.
 	MOVD.P	$0, 8(R3)	// R3が指すアドレスに8バイトのゼロを書き込み、R3を8バイト進める
 	CMP	R3, R5
 	BNE	wordloop	// R3がR5に達するまでループ (8バイト単位でクリア)

nowords:
    CMP	$0, R6
    BEQ	done		// 残りのバイトがなければ終了

 	ADD	R3, R6, R6	// R6 = 現在のR3 + (残りのバイト数)、つまりバイト単位処理の終了アドレス

byteloop:
 	MOVBU.P	$0, 1(R3)	// R3が指すアドレスに1バイトのゼロを書き込み、R3を1バイト進める
 	CMP	R3, R6
 	BNE	byteloop	// R3がR6に達するまでループ (1バイト単位でクリア)
done:
 	RET
```
この変更により、`memclr`はまず8バイト単位でメモリをクリアし、その後残りの1〜7バイトをクリアするようになりました。これにより、特に大きなメモリ領域のクリアが高速化されます。`MOVD.P`はARM64の`STR`命令のポストインクリメント形式に相当し、データをストアした後にアドレスレジスタを自動的に更新します。

### `src/runtime/memmove_arm64.s` の変更点

`memmove`はコピー元とコピー先がオーバーラップする可能性があるため、順方向コピーと逆方向コピーのロジックが必要です。

#### 順方向コピー (`forward`ラベル以降)

```assembly
check:
 	AND	$~7, R5, R7	// R7 = N & ~7 (Nを8で割った商 * 8、つまり8バイト単位で処理できる部分のサイズ)
 	// TODO(mwhudson): this is written this way to avoid tickling
 	// warnings from addpool when written as AND $7, R5, R6 (see
 	// https://golang.org/issue/12708)
 	SUB	R7, R5, R6	// R6 = N & 7 (Nを8で割った余り、つまり残りのバイト数)

 	CMP	R3, R4		// R3 = dst, R4 = src
 	BLT	backward	// dst < src の場合、逆方向コピーへ (オーバーラップ対策)

 	// Copying forward proceeds by copying R7/8 words then copying R6 bytes.
 	// R3 and R4 are advanced as we copy.

    // (There may be implementations of armv8 where copying by bytes until
    // at least one of source or dest is word aligned is a worthwhile
    // optimization, but the on the one tested so far (xgene) it did not
    // make a significance difference.)

 	CMP	$0, R7		// Do we need to do any word-by-word copying?
 	BEQ	noforwardlarge	// 8バイト単位で処理する部分がなければ、直接バイト単位処理へ

 	ADD	R3, R7, R9	// R9 = dst + (8バイト単位処理部分のサイズ)、つまり8バイト単位処理の終了アドレス

forwardlargeloop:
 	MOVD.P	8(R4), R8	// R4が指すアドレスから8バイトをR8にロードし、R4を8バイト進める
 	MOVD.P	R8, 8(R3)	// R8の値をR3が指すアドレスに8バイトストアし、R3を8バイト進める
 	CMP	R3, R9
 	BNE	forwardlargeloop // R3がR9に達するまでループ (8バイト単位でコピー)

noforwardlarge:
 	CMP	$0, R6		// Do we need to do any byte-by-byte copying?
 	BNE	forwardtail	// 残りのバイトがあれば、バイト単位処理へ
 	RET			// なければ終了

forwardtail:
 	ADD	R3, R6, R9	// R9 = 現在のR3 + (残りのバイト数)、つまりバイト単位処理の終了アドレス

forwardtailloop:
 	MOVBU.P 1(R4), R8	// R4が指すアドレスから1バイトをR8にロードし、R4を1バイト進める
 	MOVBU.P	R8, 1(R3)	// R8の値をR3が指すアドレスに1バイトストアし、R3を1バイト進める
 	CMP	R3, R9
 	BNE	forwardtailloop	// R3がR9に達するまでループ (1バイト単位でコピー)
 	RET
```
順方向コピーでは、まず8バイト単位でデータをコピーし、その後残りのバイトをコピーします。`MOVD.P`と`MOVBU.P`は、それぞれ8バイトと1バイトのロード/ストアとポインタのポストインクリメントを同時に行います。

#### 逆方向コピー (`backward`ラベル以降)

```assembly
backward:
 	// Copying backwards proceeds by copying R6 bytes then copying R7/8 words.
 	// R3 and R4 are advanced to the end of the destination/source buffers
 	// respectively and moved back as we copy.

 	ADD	R4, R5, R4	// R4 = src + N (コピー元バッファの末尾の次)
 	ADD	R3, R5, R3	// R3 = dst + N (コピー先バッファの末尾の次)

 	CMP	$0, R6		// Do we need to do any byte-by-byte copying?
 	BEQ	nobackwardtail	// 残りのバイトがなければ、直接ワード単位処理へ

 	SUB	R6, R3, R9	// R9 = dst + N - R6 (バイト単位でコピーする最低のコピー先アドレス)
backwardtailloop:
 	MOVBU.W	-1(R4), R8	// R4が指すアドレスの1バイト手前から1バイトをR8にロードし、R4を1バイト戻す
 	MOVBU.W	R8, -1(R3)	// R8の値をR3が指すアドレスの1バイト手前に1バイトストアし、R3を1バイト戻す
 	CMP	R9, R3
 	BNE	backwardtailloop // R3がR9に達するまでループ (1バイト単位で末尾からコピー)

nobackwardtail:
 	CMP     $0, R7		// Do we need to do any word-by-word copying?
 	BNE	backwardlarge	// 8バイト単位で処理する部分があれば、ワード単位処理へ
 	RET			// なければ終了

backwardlarge:
    SUB	R7, R3, R9      // R9 = dst + N - R7 (ワード単位でコピーする最低のコピー先アドレス)

backwardlargeloop:
 	MOVD.W	-8(R4), R8	// R4が指すアドレスの8バイト手前から8バイトをR8にロードし、R4を8バイト戻す
 	MOVD.W	R8, -8(R3)	// R8の値をR3が指すアドレスの8バイト手前に8バイトストアし、R3を8バイト戻す
 	CMP	R9, R3
 	BNE	backwardlargeloop // R3がR9に達するまでループ (8バイト単位で末尾からコピー)
 	RET
```
逆方向コピーでは、まずポインタをバッファの末尾の次に設定し、そこから逆方向にコピーを進めます。まず残りのバイトを末尾からコピーし、その後8バイト単位で末尾からコピーします。`MOVBU.W`と`MOVD.W`は、それぞれ1バイトと8バイトのロード/ストアとポインタのプリデクリメントを同時に行います。

これらの変更により、`memmove`はオーバーラップを考慮しつつ、可能な限りワード単位で高速なメモリコピーを実行できるようになりました。

### `src/runtime/memmove_test.go` の変更点

`bmMemmoveUnaligned`関数は、`copy(x[1:], y)`のように、コピー元またはコピー先がワード境界にアラインされていない状況を意図的に作り出し、そのパフォーマンスを測定します。これは、アラインメントされていないメモリ操作が最適化によってどのように影響を受けるかを評価するために重要です。新しいアセンブリコードは、アラインされていない部分をバイト単位で処理し、アラインされた部分をワード単位で処理するため、このようなテストケースは最適化の堅牢性を確認する上で不可欠です。

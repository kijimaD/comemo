## 変更の背景

このコミットの主な背景は、Goの継続的インテグレーション（CI）システム、特に「race builders」と呼ばれる競合状態検出ツールが有効化されたビルド環境で、`net/http` パッケージのベンチマークテストが失敗していた問題に対処することです。

GoのHTTPクライアント（`net/http` パッケージ）を使用してHTTPリクエストを行う際、レスポンスボディ（`http.Response.Body`）は `io.ReadCloser` インターフェースを実装しており、その内容を読み終えた後、または読み終える前に、必ず `Close()` メソッドを呼び出す必要があります。これを怠ると、基盤となるネットワーク接続が解放されず、接続リークやリソースリークが発生する可能性があります。

ベンチマークテストのような高頻度で多数のリクエストを生成するシナリオでは、レスポンスボディのクローズ忘れは深刻な問題を引き起こします。具体的には、以下のような影響が考えられます。

1.  **リソースリーク**: ネットワークソケットやファイルディスクリプタが適切に閉じられず、システムリソースを枯渇させる可能性があります。
2.  **ゴルーチンリーク**: HTTPリクエストを処理するゴルーチンが、レスポンスボディが閉じられるのを待機し続けることで、終了せずに残り続ける可能性があります。
3.  **競合状態の発生**: 未クローズの接続やゴルーチンがバックグラウンドで動作し続けることで、テスト環境の共有リソースに対して予期せぬアクセスが発生し、競合状態検出器（Go Race Detector）がこれを検知してテストを失敗させる原因となります。

このコミットは、ベンチマークテストにおいてこれらの問題を解消し、race buildersが正常に動作するようにするために導入されました。

## 前提知識の解説

### Go言語の `net/http` パッケージ

Go言語の `net/http` パッケージは、HTTPクライアントとサーバーの実装を提供します。

*   **HTTPクライアント**: `http.Get()` 関数や `http.Client` 型を使用してHTTPリクエストを送信できます。`http.Get(url string)` は指定されたURLにGETリクエストを送信し、`*http.Response` と `error` を返します。
*   **`http.Response.Body`**: HTTPレスポンスのボディは `io.ReadCloser` インターフェースとして提供されます。これは、ボディの内容を読み取るための `Read()` メソッドと、リソースを解放するための `Close()` メソッドを持ちます。**`Close()` メソッドの呼び出しは非常に重要であり、これを怠ると接続が再利用されなかったり、リソースがリークしたりする可能性があります。**

### Go言語の `testing` パッケージとベンチマーク

Go言語には、標準でテストとベンチマークをサポートする `testing` パッケージが用意されています。

*   **ベンチマークテスト**: 関数名のプレフィックスが `Benchmark` で始まる関数はベンチマークテストとして認識されます（例: `func BenchmarkXxx(b *testing.B)`）。`*testing.B` 型は、ベンチマークの実行回数 (`b.N`) や時間計測、メモリ割り当てのレポートなどの機能を提供します。
*   **`b.ReportAllocs()`**: ベンチマーク中に発生したメモリ割り当ての回数をレポートするように指示します。
*   **`b.StopTimer()` / `b.StartTimer()`**: ベンチマークの計測を一時停止/再開します。セットアップやクリーンアップの時間を計測から除外するために使用されます。
*   **`defer` ステートメント**: `defer` に続く関数呼び出しは、それを囲む関数がリターンする直前に実行されます。リソースのクリーンアップ処理によく使用されます。

### 競合状態（Race Condition）とGo Race Detector

*   **競合状態**: 複数のゴルーチンが同時に共有リソースにアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期されていない場合に発生するバグです。実行順序によって結果が非決定的に変わるため、デバッグが困難です。
*   **Go Race Detector**: Goには、プログラム実行中に競合状態を検出する強力なツールが組み込まれています。`go run -race`、`go test -race`、`go build -race`、`go install -race` のように `-race` フラグを付けてコマンドを実行することで有効化できます。競合状態が検出されると、詳細なレポートが出力され、プログラムは通常終了します。CI環境の「race builders」は、この機能が有効化されたビルド環境を指します。

## コアとなるコードの解説

### `main_test.go` の `afterTest` 関数シグネチャ変更

*   **変更前**: `func afterTest(t *testing.T)`
*   **変更後**: `func afterTest(t testing.TB)`

この変更は、`afterTest` 関数が `*testing.T` (テスト) と `*testing.B` (ベンチマーク) の両方のコンテキストで使用できるようにするために行われました。`testing.TB` インターフェースは `testing.T` と `testing.B` の両方が実装している共通のメソッドセット（例: `Error`, `Fatal`, `Log` など）を定義しています。これにより、コードの再利用性が向上し、ベンチマークのクリーンアップ処理をテストと同様に統一的に扱うことが可能になります。

### `serve_test.go` の `getNoBody` ヘルパー関数

```go
// getNoBody wraps Get but closes any Response.Body before returning the response.
func getNoBody(urlStr string) (*Response, error) {
	res, err := Get(urlStr)
	if err != nil {
		return nil, err
	}
	res.Body.Close() // ここで即座にボディをクローズ
	return res, nil
}
```

この新しい関数は、`http.Get` を呼び出した直後に `res.Body.Close()` を呼び出すことを保証します。HTTPレスポンスボディは `io.ReadCloser` であり、その内容を読み終えるか否かに関わらず、必ず `Close()` を呼び出して基盤となる接続を解放する必要があります。ベンチマークでは、レスポンスボディの内容を実際に読み取る必要がない場合が多く、`Close()` を忘れると接続がリークし、リソース枯渇やゴルーチンリークの原因となります。`getNoBody` を導入することで、この一般的な落とし穴を回避し、ベンチマークの信頼性を高めています。

### `BenchmarkClient` の修正

1.  **`defer afterTest(b)` の追加**:
    `BenchmarkClient` の冒頭に `defer afterTest(b)` が追加されました。これにより、`BenchmarkClient` 関数が終了する際に、`afterTest` 関数が確実に呼び出され、`http.DefaultTransport.(*http.Transport).CloseIdleConnections()` が実行されます。これは、ベンチマーク中に確立されたアイドル状態のHTTP接続をクリーンアップし、リソースリークを防ぐために重要です。以前はベンチマークの最後に明示的に呼び出されていましたが、`defer` を使用することで、関数がどのように終了しても（正常終了、パニックなど）、クリーンアップ処理が保証されます。

2.  **`Get` から `getNoBody` への置き換え**:
    `BenchmarkClient` 内で `http.Get(url)` を直接呼び出していた箇所が、新しく定義された `getNoBody(url)` に置き換えられました。これにより、ベンチマークの各イテレーションでHTTPリクエストが送信されるたびに、レスポンスボディが確実にクローズされるようになります。これは、前述のリソースリークや競合状態の防止に直接貢献します。

3.  **`ListenAndServe` のアドレス変更**:
    `log.Fatal(ListenAndServe(":"+port, nil))` が `log.Fatal(ListenAndServe("localhost:"+port, nil))` に変更されました。
    *   `":"+port` は、すべての利用可能なネットワークインターフェース（0.0.0.0）でリッスンすることを意味します。
    *   `"localhost:"+port` は、ループバックインターフェース（127.0.0.1）でのみリッスンすることを意味します。
    ベンチマークのようなローカルでのテストシナリオでは、`localhost` にバインドすることで、外部からのアクセスを制限し、ネットワーク設定による予期せぬ挙動や競合状態のリスクを低減できます。

4.  **`DefaultTransport.(*Transport).CloseIdleConnections()` の削除**:
    `BenchmarkClient` の最後で明示的に呼び出されていた `DefaultTransport.(*Transport).CloseIdleConnections()` が削除されました。これは、`defer afterTest(b)` によってこの処理が `afterTest` 経由で確実に実行されるようになったため、冗長な呼び出しを避けるためです。

これらの変更は、`net/http` パッケージのベンチマークテストがより堅牢になり、特にGo Race Detectorが有効な環境で正確に動作することを保証します。レスポンスボディの適切なクローズは、HTTPクライアントを使用する際のベストプラクティスであり、このコミットはそれをベンチマークテストに適用することで、テストの信頼性とシステムの安定性を向上させています。

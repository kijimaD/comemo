このコミットは、Go言語の標準ライブラリである `os` パッケージ内の `src/os/file_unix.go` ファイルに対する変更です。このファイルは、Unix系システムにおけるファイル操作、特にファイルのオープンに関する低レベルなシステムコールとの連携を扱っています。具体的には、`OpenFile` 関数がシステムコール `syscall.Open` を呼び出す際の挙動を定義しています。

## 変更の背景

この変更は、Goの `os` パッケージにおけるファイルオープン処理の堅牢性を向上させることを目的としています。特に、Unix系システムコールが `EINTR` エラーを返す場合のハンドリングと、その挙動が特定のOS（Darwin/macOS）で異なるという問題に対処しています。

以前の実装では、`syscall.Open` が `EINTR` エラーを返した場合に `goto retry` を使用してシステムコールを再試行していました。しかし、この `goto` の使用はGoのコーディングスタイルガイドラインでは一般的に推奨されていません。また、この `EINTR` の再試行ロジックは、特にDarwin（macOS）環境で問題を引き起こすことが知られていました。

具体的には、`issue/11180` (http://golang.org/issue/11180) で報告されたように、macOSでは `sigaction(2)` の `SA_RESTART` フラグが設定されていても、`open(2)` システムコールが通常のファイルに対して自動的に再開されない場合があるという問題がありました。これは特にFUSEファイルシステム上で顕著でした。このため、`EINTR` エラーが発生した際に無限ループに陥る可能性や、不必要な再試行が行われる可能性がありました。

このコミットは、`http://golang.org/cl/14484` でのコードレビューコメントに対応し、以下の点を改善しています。
1.  `goto` ステートメントの使用を廃止し、よりGoらしい `for` ループに置き換える。
2.  `EINTR` の再試行ロジックを `runtime.GOOS == "darwin"` の場合に限定することで、問題が顕在化する環境でのみ特別なハンドリングを行うようにする。これにより、他のUnix系システムでの不必要なオーバーヘッドや潜在的な問題を回避します。

## 前提知識の解説

### `syscall.EINTR` (Interrupted system call)

`EINTR` は、システムコールがシグナルによって中断されたことを示すエラーコードです。Unix系システムでは、プロセスがシステムコールを実行中にシグナルを受信すると、そのシステムコールは中断され、`EINTR` エラーを返して呼び出し元に戻ることがあります。これは、シグナルハンドラが実行された後にシステムコールを再開するか、エラーを返すかを決定するためのメカニズムです。多くのシステムコールは、`EINTR` を受け取った場合に自動的に再試行されるように設定できますが、常にそうとは限りません。

### `SA_RESTART` フラグ

`SA_RESTART` は、`sigaction(2)` システムコールでシグナルハンドラを設定する際に使用できるフラグの一つです。このフラグが設定されていると、シグナルによって中断された一部のシステムコール（例えば `read(2)`, `write(2)`, `wait(2)` など）は、シグナルハンドラの実行後に自動的に再開されます。これにより、アプリケーションは `EINTR` エラーを明示的に処理する必要がなくなります。しかし、すべてのシステムコールが `SA_RESTART` の恩恵を受けるわけではありません。特に、`open(2)` のような一部のシステムコールは、このフラグが設定されていても再開されない場合があります。

### Darwin (macOS) における `open(2)` と `EINTR` の挙動

macOS（Darwinカーネル）では、`open(2)` システムコールが `SA_RESTART` フラグの影響を受けにくいという特性があります。特に、通常のファイルに対する `open(2)` は、シグナルによって中断された場合に `EINTR` を返し、自動的に再開されないことがあります。これは、他のUnix系システム（Linuxなど）とは異なる挙動であり、Goのようなクロスプラットフォーム言語では特別な考慮が必要です。この挙動は、特にFUSE（Filesystem in Userspace）ベースのファイルシステムを使用している場合に顕著になることがあります。

### `goto` ステートメント

`goto` ステートメントは、プログラムの実行フローをコード内の任意のラベルにジャンプさせる制御構造です。C言語などでは一般的な機能ですが、Go言語ではその使用は推奨されません。`goto` はコードの可読性を低下させ、複雑なスパゲッティコードを生み出す可能性があるためです。Goでは、`for` ループ、`break`、`continue`、`return` などの構造化された制御フローを使用して、`goto` を避けることが推奨されています。

## 技術的詳細

このコミットの核心は、`syscall.Open` が `EINTR` エラーを返した場合の処理を改善することにあります。

以前のコードは以下のようになっていました。

```go
retry:
	r, e := syscall.Open(name, flag|syscall.O_CLOEXEC, syscallMode(perm))
	if e != nil {
		// ...
		if e == syscall.EINTR {
			goto retry
		}
		// ...
	}
```

このコードの問題点は以下の通りです。
1.  **`goto` の使用**: Goのスタイルガイドに反し、コードの追跡を困難にする可能性があります。
2.  **無条件の再試行**: `EINTR` エラーが発生した場合、OSの種類に関わらず無条件に再試行していました。しかし、前述の通り、この問題は主にDarwinで顕在化します。他のOSでは `SA_RESTART` が適切に機能し、`EINTR` が返されること自体が稀であるか、または再試行が不要な場合もあります。
3.  **Darwin特有の問題**: `issue/11180` で指摘されたように、Darwinでは `open(2)` が `EINTR` を返しても自動的に再開されないことがあり、この `goto` による再試行が必要でした。しかし、このロジックがDarwinに限定されていなかったため、他のOSで不必要な再試行ロジックが実行される可能性がありました。

新しいコードでは、これらの問題に対処するために `for` ループと `runtime.GOOS` を使用しています。

```go
	var r int
	for {
		var e error
		r, e = syscall.Open(name, flag|syscall.O_CLOEXEC, syscallMode(perm))
		if e == nil {
			break // 成功したらループを抜ける
		}

		// Darwinの場合のみEINTRを再試行
		if runtime.GOOS == "darwin" && e == syscall.EINTR {
			continue // ループの先頭に戻り再試行
		}

		// その他のエラーは処理して終了
		return nil, &PathError{"open", name, e}
	}
```

この変更により、以下の利点が得られます。
*   **構造化された制御フロー**: `goto` が `for` ループと `continue`/`break` に置き換えられ、コードの可読性と保守性が向上しました。
*   **OS固有のハンドリング**: `runtime.GOOS == "darwin"` のチェックが追加され、`EINTR` の再試行ロジックがDarwin環境に限定されました。これにより、他のOSでの不必要な処理が回避され、より効率的で正確なエラーハンドリングが実現されます。
*   **問題の正確な解決**: Darwinにおける `open(2)` の `EINTR` 問題に対して、的確な解決策が適用されています。

## コアとなるコードの解説

変更は `OpenFile` 関数の内部、`syscall.Open` を呼び出す部分に集中しています。

1.  **`goto retry:` の削除**:
    *   以前のコードでは `retry:` というラベルが定義され、`goto retry` でシステムコール呼び出しを再試行していました。この `goto` が完全に削除されました。

2.  **`for` ループの導入**:
    *   `var r int` がループの外で宣言され、`syscall.Open` の戻り値 `r` を保持します。
    *   `for { ... }` という無限ループが導入されました。これにより、`goto` を使わずにシステムコールを繰り返し試行する構造が実現されます。

3.  **`syscall.Open` の呼び出しとエラーチェック**:
    *   ループ内で `r, e = syscall.Open(...)` が呼び出されます。`e` はエラーを保持します。
    *   `if e == nil { break }`：システムコールが成功（エラーが `nil`）した場合、`break` でループを抜け、正常な処理に進みます。

4.  **Darwin固有の `EINTR` 処理**:
    *   `if runtime.GOOS == "darwin" && e == syscall.EINTR { continue }`：
        *   `runtime.GOOS == "darwin"` は、現在の実行環境がmacOSであるかどうかをチェックします。
        *   `e == syscall.EINTR` は、発生したエラーが `EINTR` であるかどうかをチェックします。
        *   この両方の条件が真である場合、`continue` が実行され、ループの先頭に戻って `syscall.Open` が再試行されます。これにより、macOS特有の `EINTR` 問題に対処します。

5.  **その他のエラー処理**:
    *   上記の `if` 文の条件に合致しない（つまり、macOS以外のOSで `EINTR` が発生したか、または `EINTR` 以外のエラーが発生した）場合、`return nil, &PathError{"open", name, e}` が実行され、エラーを返して関数を終了します。

この変更により、コードはより構造化され、`EINTR` の再試行ロジックが問題の根本原因であるDarwin環境に限定されることで、より堅牢かつ効率的になりました。

## 元コミット内容

このコミットは、`cmd/doc` ツールにおけるテキスト整形、特にコメントの折り返し幅に関する変更です。具体的には、テキストの折り返し幅を80カラムに固定するよう修正しています。コミットメッセージは、この80カラムという慣習に対するRob Pike氏の皮肉と抵抗を表明しつつも、最終的にはコミュニティの期待に応える形で変更を受け入れたことを示しています。

## 変更の背景

変更の背景には、Go言語のドキュメンテーションツール `cmd/doc` が生成するテキストの整形に関する問題がありました。具体的には、Issue #11639 で報告されたように、生成されるドキュメントのコメントが80カラムの幅で適切に折り返されないという問題がありました。多くの開発者は、ターミナルやエディタの表示幅を80カラムに設定する慣習があり、これに合わせた整形が求められていました。

コミットメッセージにあるように、80カラムという幅は、かつてのパンチカードシステムに由来する古い慣習であり、現代の環境では必ずしも技術的な必然性があるわけではありません。しかし、プログラミングコミュニティにおいては、コードの可読性や一貫性を保つための「デファクトスタンダード」として広く受け入れられています。Rob Pike氏はこの慣習に懐疑的でありながらも、ユーザーからの要望（Issue #11639）に応える形で、この「パンチカードの専制政治 (punched card tyranny)」に従うことを表明しています。

この変更は、Go言語のツールが、開発者の一般的な作業環境や期待に沿うように調整された一例と言えます。

## 前提知識の解説

*   **`cmd/doc`**: Go言語の標準ツールの一つで、Goのソースコードからドキュメンテーションを生成するために使用されます。`go doc` コマンドの基盤となるツールでもあります。パッケージ、関数、型などのコメントを解析し、整形されたテキストとして出力します。
*   **80カラムの慣習**: プログラミングの世界で長らく続いてきた、コードやテキストの1行の長さを80文字（カラム）に制限する慣習です。これは、初期のパンチカード（1行が80カラム）や、古いターミナルエミュレータの表示幅に由来します。現代ではより広い画面が一般的ですが、コードレビューのしやすさ、サイド・バイ・サイドでの比較、複数のファイルを並べて表示する際の視認性などの理由から、依然として多くのプロジェクトやコーディングスタイルガイドで推奨されています。
*   **`doc.ToText` 関数**: Go言語の `go/doc` パッケージに含まれる関数で、Goのコメントブロックを整形されたプレーンテキストに変換するために使用されます。この関数は、コメント文字列、インデント文字列、タブ展開文字列、そして折り返し幅（`maxwidth`）を引数として受け取ります。
*   **`ast.Node`**: Go言語の `go/ast` パッケージで定義されているインターフェースで、Goプログラムの抽象構文木（Abstract Syntax Tree, AST）におけるノードを表します。`cmd/doc` はGoのソースコードをASTとして解析し、そのノードに付随するコメントを処理します。

## 技術的詳細

このコミットの技術的な核心は、`src/cmd/doc/pkg.go` ファイル内の `doc.ToText` 関数の呼び出しにおいて、ハードコードされていたテキストの折り返し幅 `80` を、定数として定義された `indentedWidth` に置き換えた点です。

以前のコードでは、コメントの整形時に `doc.ToText` 関数に直接 `80` という数値が渡されていました。これは、コメントが常に80カラムで折り返されることを意味します。しかし、コメントがインデントされている場合、そのインデント分を考慮すると実質的なテキスト幅は80カラムよりも短くなり、結果として行が途中で不自然に折り返されたり、80カラムを超過したりする可能性がありました。

このコミットでは、以下の新しい定数が導入されました。

*   `punchedCardWidth = 80`: 80カラムという「パンチカードの幅」を象徴する定数。
*   `indent = "    "`: 4スペースのインデント文字列を定義。
*   `indentedWidth = punchedCardWidth - len(indent)`: 実際のテキストが利用できる幅を計算します。これは `80 - 4 = 76` となります。

そして、`pkg.emit` メソッドと `pkg.packageDoc` メソッド内の `doc.ToText` の呼び出しが以下のように変更されました。

```go
// 変更前
doc.ToText(&pkg.buf, comment, "    ", "\t", 80)
// 変更後
doc.ToText(&pkg.buf, comment, "    ", indent, indentedWidth)
```
```go
// 変更前
doc.ToText(&pkg.buf, pkg.doc.Doc, "", "\t", 80)
// 変更後
doc.ToText(&pkg.buf, pkg.doc.Doc, "", indent, indentedWidth)
```

この変更により、`doc.ToText` 関数に渡される折り返し幅が、インデントを考慮した `76` カラムに設定されるようになりました。これにより、`cmd/doc` が生成するドキュメント内のコメントが、インデントされていても全体として80カラムの幅に収まるように適切に整形されるようになります。また、インデント文字列も `indent` 定数を使用することで、コードの一貫性が向上しています。

この修正は、見た目の問題だけでなく、自動生成されるドキュメントの品質と、それを読む開発者の体験を向上させるための重要な改善です。

## コアとなるコードの解説

このコミットの主要な変更は、`src/cmd/doc/pkg.go` 内で `doc.ToText` 関数を呼び出す際の引数 `maxwidth` と `tabwidth` の扱いを改善した点にあります。

*   **定数 `punchedCardWidth`, `indentedWidth`, `indent` の導入**:
    *   `punchedCardWidth` は、80カラムという伝統的な幅を明示的に定義しています。これは、コミットメッセージの皮肉なトーンを反映しつつ、コード内でその意味を明確にする役割も果たしています。
    *   `indent` は、コメントのインデントに使用される4スペースの文字列を定数として定義します。これにより、マジックナンバー（直接埋め込まれたリテラル値）を避け、コードの可読性と保守性を向上させています。
    *   `indentedWidth` は、`punchedCardWidth` から `indent` の長さを引くことで、インデントされたテキストが実際に利用できる最大幅を計算します。これにより、インデントされたコメントが80カラムの総幅内に収まるように、テキストの折り返しが適切に行われるようになります。

*   **`doc.ToText` 関数の引数変更**:
    *   以前は `doc.ToText` の `maxwidth` 引数に直接 `80` が渡されていました。これは、インデントの有無にかかわらず、テキスト全体を80カラムで折り返そうとするため、インデントされた行では実質的なテキスト部分が80カラムを超えてしまう可能性がありました。
    *   変更後は `maxwidth` に `indentedWidth` (76) が渡されるようになりました。これにより、コメントが4スペースでインデントされている場合でも、テキスト本体は76カラム内で折り返され、結果として行全体が80カラムの制約内に収まるようになります。
    *   また、`tabwidth` 引数には以前は `"\t"` が渡されていましたが、`pkg.emit` の呼び出しでは `indent` 定数が使用されるようになりました。これにより、タブ文字の扱いとインデントの表現が一貫します。

この修正は、Goのドキュメンテーション生成ツールが、より視覚的に快適で、一般的なコーディングスタイルガイドに準拠した出力を生成できるようにするための、細かではあるが重要な改善です。

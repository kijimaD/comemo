# [インデックス 22599] ファイルの概要

このコミットは、Go言語の`syscall`パッケージにおける`Dup`, `Dup2`, `Dup3`システムコールが、`RawSyscall`ではなく`Syscall`を使用するように変更するものです。この変更の主な目的は、GoプログラムがFUSE (Filesystem in Userspace) ファイルシステムを使用している際に発生する可能性のあるハングアップ問題を解決することにあります。特に、`dup`システムコールがファイルディスクリプタをクローズする必要がある場合に問題が発生していました。

## コミット

```
syscall: change Dup,Dup2,Dup3 to use Syscall, not RawSyscall

This avoids hanging when a Go program uses a FUSE filesystem and the
dup system call has to close a file descriptor.  When dup uses
RawSyscall then the goroutine calling dup will occupy a scheduler slot
(a p structure) during the call, and may block waiting for some other
goroutine to respond to the close call on the FUSE filesystem.
Changing to Syscall avoids the problem.  This makes Dup a tiny bit
slower but is quite unlikely to make a difference for any real
programs.

Fixes #10202.

Reviewed-on: https://go-review.googlesource.com/8095
Reviewed-by: Rob Pike <r@golang.org>
```

## 変更の背景

この変更は、GoプログラムがFUSEファイルシステムと連携する際に発生する特定のハングアップ問題を解決するために導入されました。FUSEは、ユーザー空間でファイルシステムを実装するためのメカニズムを提供します。GoプログラムがFUSEファイルシステム上のファイルディスクリプタに対して`dup`（または`dup2`, `dup3`）システムコールを実行する際、内部的にファイルディスクリプタのクローズ操作が発生することがあります。

問題は、これらの`dup`関連のシステムコールが以前は`RawSyscall`を使用して実装されていたことにありました。`RawSyscall`はGoランタイムのスケジューラに通知せずに直接システムコールを実行するため、システムコールがブロックした場合、そのシステムコールを実行しているゴルーチンがOSスレッド（P構造体、プロセッサ）を占有し続けます。FUSEファイルシステムの場合、ファイルクローズ操作はユーザー空間のFUSEデーモンに処理を委譲するため、FUSEデーモンが応答するまでブロックする可能性があります。このブロックが原因で、他のゴルーチンがFUSEデーモンからの応答を待っている場合、デッドロックやハングアップが発生し、プログラム全体が応答しなくなる事態を招いていました。

このコミットは、`Dup`, `Dup2`, `Dup3`が`Syscall`を使用するように変更することで、この問題を回避します。`Syscall`はGoランタイムと連携し、システムコールがブロックする可能性があることをランタイムに通知するため、ランタイムは必要に応じてOSスレッドを解放し、他のゴルーチンが実行できるようにします。これにより、FUSE関連のハングアップが解消されます。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語のランタイムとシステムコールに関する知識が不可欠です。

1.  **Goランタイムとスケジューラ (M, P, G)**:
    *   **G (Goroutine)**: Goにおける軽量な実行単位です。数千、数万のゴルーチンを同時に実行できます。
    *   **M (Machine)**: OSスレッドに対応します。GoランタイムはOSスレッドを管理し、その上でゴルーチンを実行します。
    *   **P (Processor)**: 論理プロセッサに対応し、MとGを仲介します。Pは実行可能なゴルーチンのキューを持ち、Mにゴルーチンを割り当てて実行させます。Goのスケジューラは、MがPを占有し、PがGを実行するというモデルで動作します。
    *   **スケジューリング**: Goランタイムのスケジューラは、Mがシステムコールなどでブロックされる可能性がある場合、そのMからPをデタッチし、別のMにPを割り当てて他のゴルーチンを実行させることで、OSスレッドの有効活用と並行性の維持を図ります。

2.  **`syscall.Syscall` と `syscall.RawSyscall`**:
    *   **`syscall.Syscall`**: Goランタイムと連携するシステムコールラッパーです。システムコールを実行する前に`runtime.entersyscall`を呼び出し、システムコールから戻った後に`runtime.exitsyscall`を呼び出します。これにより、Goランタイムはシステムコールがブロックする可能性があることを認識し、必要に応じて現在のゴルーチンをデスケジュールし、OSスレッドを他のゴルーチンに解放することができます。これは、I/O操作など、ブロックする可能性のあるシステムコールに適しています。
    *   **`syscall.RawSyscall`**: Goランタイムに通知せずに直接システムコールを実行するラッパーです。`runtime.entersyscall`や`runtime.exitsyscall`を呼び出しません。このため、`RawSyscall`がブロックすると、そのOSスレッド全体がブロックされ、そのスレッド上で実行される他のゴルーチンも停止します。これは、`getpid`のようにブロックしないことが保証されているシステムコールや、非常に低レイテンシが求められるがブロックしないことが確実な場合にのみ使用されます。

3.  **FUSE (Filesystem in Userspace)**:
    *   FUSEは、ユーザー空間でファイルシステムを実装するためのフレームワークです。通常、ファイルシステムはカーネル空間で実装されますが、FUSEを使用すると、開発者は通常のアプリケーションとしてファイルシステムロジックを記述できます。
    *   FUSEファイルシステムへのアクセスは、カーネルからユーザー空間のFUSEデーモンへのリクエストとして転送され、デーモンがそのリクエストを処理して結果をカーネルに返します。このユーザー空間とカーネル空間間の通信は、ブロックする可能性があります。

4.  **`dup`, `dup2`, `dup3` システムコール**:
    *   これらはファイルディスクリプタを複製するためのシステムコールです。
    *   `dup(oldfd)`: `oldfd`を指す新しいファイルディスクリプタを返します。
    *   `dup2(oldfd, newfd)`: `newfd`を`oldfd`のコピーにします。もし`newfd`が既に開いている場合、`dup2`はまず`newfd`をクローズします。このクローズ操作がFUSEファイルシステム上で実行される場合に問題が発生していました。
    *   `dup3(oldfd, newfd, flags)`: `dup2`に似ていますが、`flags`引数を取ります。

## 技術的詳細

このコミットの技術的詳細の核心は、Goランタイムのスケジューリングメカニズムとシステムコール実行の連携にあります。

Goのスケジューラは、M（OSスレッド）がP（論理プロセッサ）を占有し、PがG（ゴルーチン）を実行するというモデルを採用しています。システムコールが実行される際、そのシステムコールがブロックする可能性があるかどうかによって、Goランタイムの挙動が変わります。

*   **`RawSyscall`の問題点**:
    `Dup`, `Dup2`, `Dup3`が`RawSyscall`を使用していた場合、これらのシステムコールが実行されると、Goランタイムはそれがブロックする可能性があることを認識しません。特に`dup2`や`dup3`が既存のファイルディスクリプタをクローズする必要がある場合、そのクローズ操作がFUSEファイルシステム上のファイルディスクリプタに対して行われると、FUSEデーモンが応答するまでシステムコールがブロックします。
    このブロック中、`RawSyscall`を使用しているため、システムコールを実行しているMはPを占有し続けます。もしFUSEデーモンが別のゴルーチンによって実行されている場合、そのゴルーチンが実行されるためにはPが必要ですが、`dup`を呼び出したゴルーチンがPを占有してブロックしているため、FUSEデーモン側のゴルーチンが実行できず、結果としてデッドロックが発生し、プログラム全体がハングアップするというシナリオが考えられます。

*   **`Syscall`への変更による解決**:
    `Dup`, `Dup2`, `Dup3`を`Syscall`を使用するように変更することで、この問題が解決されます。`Syscall`はシステムコールを実行する前に`runtime.entersyscall`を呼び出し、システムコールがブロックする可能性があることをランタイムに通知します。システムコールがブロックした場合、Goランタイムは現在のMからPをデタッチし、そのPを他の実行可能なMに割り当てることができます。これにより、FUSEデーモンを処理するゴルーチンが別のM上で実行される機会を得て、ブロックしている`dup`システムコールが最終的に完了できるようになります。
    システムコールが完了すると、`Syscall`は`runtime.exitsyscall`を呼び出し、ランタイムは必要に応じてPを元のMに戻します。

この変更は、`Dup`関連のシステムコールの実行をわずかに遅くする可能性があります。これは、`Syscall`が`RawSyscall`よりもGoランタイムとの連携のためのオーバーヘッドがあるためです。しかし、コミットメッセージにあるように、実際のプログラムのパフォーマンスに大きな影響を与える可能性は低いとされています。このトレードオフは、FUSEファイルシステム使用時のハングアップという深刻な問題を解決するために許容できるものです。

## コアとなるコードの変更箇所

このコミットでは、Goの`syscall`パッケージ内の様々なOS固有のファイル（例: `syscall_darwin.go`, `syscall_linux.go`, `syscall_freebsd.go`など）と、それらに対応する`zsyscall_*.go`ファイルが変更されています。

具体的には、`Dup`, `Dup2`, `Dup3`システムコールの定義において、`//sysnb`というディレクティブが`//sys`に変更されています。

*   `src/syscall/syscall_darwin.go`
*   `src/syscall/syscall_dragonfly.go`
*   `src/syscall/syscall_freebsd.go`
*   `src/syscall/syscall_linux.go` (Dup, Dup3)
*   `src/syscall/syscall_linux_386.go` (Dup2)
*   `src/syscall/syscall_linux_amd64.go` (Dup2)
*   `src/syscall/syscall_linux_arm.go` (Dup2)
*   `src/syscall/syscall_linux_ppc64x.go` (Dup2)
*   `src/syscall/syscall_netbsd.go`
*   `src/syscall/syscall_openbsd.go`

そして、これらの変更に対応して、自動生成される`zsyscall_*.go`ファイル群（例: `src/syscall/zsyscall_darwin_386.go`, `src/syscall/zsyscall_linux_amd64.go`など）において、`Dup`, `Dup2`, `Dup3`の実装が`RawSyscall`の呼び出しから`Syscall`の呼び出しに変更されています。

例:
```go
// THIS FILE IS GENERATED BY THE COMMAND AT THE TOP; DO NOT EDIT

func Dup(fd int) (nfd int, err error) {
-	r0, _, e1 := RawSyscall(SYS_DUP, uintptr(fd), 0, 0)
+	r0, _, e1 := Syscall(SYS_DUP, uintptr(fd), 0, 0)
	nfd = int(r0)
	if e1 != 0 {
		err = e1
	}
	return
}
```
この変更は、各アーキテクチャおよびOS固有の`syscall`実装にわたって一貫して適用されています。

## コアとなるコードの解説

変更の核心は、`syscall`パッケージ内のシステムコールラッパーの生成方法を制御するディレクティブの変更と、それによって生成されるコードの変更です。

Goの`syscall`パッケージでは、`//sys`や`//sysnb`といった特殊なコメントディレクティブを使用して、システムコールラッパーのコードを自動生成しています。

*   `//sys`: このディレクティブが付与されたシステムコールは、`syscall.Syscall`を使用して実装されます。これは、システムコールがブロックする可能性があることをGoランタイムに通知し、スケジューラが適切にゴルーチンを管理できるようにします。
*   `//sysnb`: このディレクティブが付与されたシステムコールは、`syscall.RawSyscall`を使用して実装されます。これは、システムコールがブロックしないことが保証されている場合に、ランタイムとの連携オーバーヘッドを避けるために使用されます。

このコミットでは、`Dup`, `Dup2`, `Dup3`の定義から`//sysnb`を削除し、暗黙的に`//sys`が適用されるように変更しています（または明示的に`//sys`を追加しています）。これにより、これらのシステムコールが自動生成される際に、`RawSyscall`ではなく`Syscall`を呼び出すコードが生成されるようになります。

結果として、`zsyscall_*.go`ファイル内の`Dup`, `Dup2`, `Dup3`関数の実装が、以下のように変更されます。

変更前:
```go
func Dup(fd int) (nfd int, err error) {
	r0, _, e1 := RawSyscall(SYS_DUP, uintptr(fd), 0, 0) // RawSyscallを直接呼び出す
	// ...
}
```

変更後:
```go
func Dup(fd int) (nfd int, err error) {
	r0, _, e1 := Syscall(SYS_DUP, uintptr(fd), 0, 0) // Syscallを呼び出す
	// ...
}
```

このシンプルな変更が、Goランタイムのスケジューラとの連携方法を根本的に変え、FUSEファイルシステム使用時のハングアップ問題を解決する鍵となります。`Syscall`を使用することで、`dup`操作がFUSEデーモンからの応答を待ってブロックする間、GoランタイムはOSスレッドを解放し、他のゴルーチン（例えばFUSEデーモン自体）が実行される機会を得られるようになります。これにより、デッドロック状態が回避され、プログラムの応答性が維持されます。

## 変更の背景

このコミットは、GoプログラムがCgo（GoとC/C++コードを連携させるためのメカニズム）を使用する際に発生する特定の問題を解決するために導入されました。具体的には、AddressSanitizer (ASan) やThreadSanitizer (TSan) といったサニタイザー（実行時エラー検出ツール）を有効にしてC/C++コードをコンパイルする際に、サニタイザーのランタイムライブラリが二重にリンクされてしまう問題がありました。

通常のC/C++プロジェクトでは、`-fsanitize=`フラグを付けてコンパイルすると、コンパイラドライバーはそれが最終リンクであることを想定し、必要なサニタイザーランタイムを自動的にリンクします。しかし、Cgoのビルドプロセスでは、C/C++コードはまずオブジェクトファイルにコンパイルされ、その後Goのビルドプロセスによって最終的な実行可能ファイルにリンクされます。この二段階のリンクプロセスにおいて、Cgoのオブジェクトファイル生成時にサニタイザーランタイムが一度リンクされ、さらに最終リンク時にもう一度リンクされることで、プログラム内にサニタイザーランタイムのコピーが二つ存在することになり、予期せぬ動作やクラッシュを引き起こす可能性がありました。

この問題はGoのIssue 8788として報告されており、このコミットはその問題を修正することを目的としています。

## 前提知識の解説

*   **Cgo**: Go言語の機能の一つで、GoプログラムからC言語の関数を呼び出したり、C言語のコードをGoプログラムに組み込んだりすることを可能にします。Cgoを使用すると、GoのガベージコレクションとCのメモリ管理が連携し、異なる言語間のデータ受け渡しや関数呼び出しを円滑に行うことができます。
*   **サニタイザー (Sanitizers)**: プログラムの実行時エラー（メモリリーク、データ競合、未定義動作など）を検出するためのツール群です。代表的なものに以下があります。
    *   **AddressSanitizer (ASan)**: メモリ関連のエラー（ヒープオーバーフロー、ユーズアフターフリーなど）を検出します。
    *   **ThreadSanitizer (TSan)**: スレッド間のデータ競合を検出します。
    これらのサニタイザーは、コンパイル時にコードに計測（instrumentation）を挿入し、実行時に特別なランタイムライブラリと連携してエラーを検出します。
*   **`-fsanitize=`フラグ**: GCCやClangなどのコンパイラで使用されるフラグで、特定のサニタイザーを有効にするために使用されます。例えば、`-fsanitize=address`はAddressSanitizerを有効にします。
*   **コンパイラドライバー**: コンパイル、アセンブル、リンクといった一連の処理を自動的に実行するプログラムです。通常、ユーザーが`gcc`や`clang`といったコマンドを実行すると、このコンパイラドライバーが起動し、適切なツール（プリプロセッサ、コンパイラ、アセンブラ、リンカ）を呼び出します。
*   **リンク (Linking)**: コンパイルされたオブジェクトファイルやライブラリを結合して、実行可能なプログラムを生成するプロセスです。
    *   **静的リンク**: 必要なライブラリのコードが実行可能ファイルに直接組み込まれます。
    *   **動的リンク**: 必要なライブラリが実行時にロードされます。
*   **オブジェクトファイル**: ソースコードがコンパイルされた後の中間ファイルで、機械語コードやデータが含まれていますが、まだ実行可能なプログラムではありません。

## 技術的詳細

このコミットの技術的な核心は、Cgoのビルドプロセスにおける`-fsanitize=`フラグの扱いを修正することにあります。

Cgoは、GoのビルドシステムとC/C++のコンパイラ（通常はGCCやClang）を連携させます。Cgoのビルドステップでは、Goコードから参照されるC/C++コードがまず独立したオブジェクトファイルにコンパイルされます。この際、Goのビルドシステムは、C/C++コンパイラに渡すフラグを制御します。

問題は、ユーザーがC/C++コンパイラに`-fsanitize=`フラグを渡した場合に発生しました。コンパイラドライバーは、このフラグを見ると、それが最終的な実行可能ファイルを生成するためのリンクステップであると誤解し、サニタイザーのランタイムライブラリをそのオブジェクトファイルに静的にリンクしようとします。しかし、Cgoのビルドプロセスでは、このオブジェクトファイルはまだ中間生成物であり、後でGoのリンカによって最終的な実行可能ファイルにリンクされることになります。

結果として、最終的な実行可能ファイルには、Cgoによって生成されたオブジェクトファイルに含まれるサニタイザーランタイムのコピーと、Goのリンカが最終リンク時に追加するサニタイザーランタイムのコピーの、二つのサニタイザーランタイムが含まれてしまいます。これにより、サニタイザーが正しく機能しなかったり、プログラムがクラッシュしたりする原因となっていました。

このコミットは、`cmd/go/build.go`内のCgoビルドロジックに修正を加え、Cgoオブジェクトをビルドする際に、C/C++コンパイラに渡されるフラグの中から`-fsanitize=`で始まるフラグを明示的に削除するようにします。これにより、C/C++コンパイラはサニタイザーランタイムを中間オブジェクトファイルにリンクしなくなり、最終的なGoのリンクステップでのみサニタイザーランタイムが適切にリンクされるようになります。

## コアとなるコードの変更箇所

変更は `src/cmd/go/build.go` ファイルの `builder` 構造体の `cgo` メソッド内で行われています。

```diff
--- a/src/cmd/go/build.go
+++ b/src/cmd/go/build.go
@@ -2228,6 +2228,14 @@ func (b *builder) cgo(p *Package, cgoExe, obj string, pcCFLAGS, pcLDFLAGS, gccfi
 			strings.HasSuffix(f, ".so"),
 			strings.HasSuffix(f, ".dll"):\n 			continue
+		// Remove any -fsanitize=foo flags.
+		// Otherwise the compiler driver thinks that we are doing final link
+		// and links sanitizer runtime into the object file. But we are not doing
+		// the final link, we will link the resulting object file again. And
+		// so the program ends up with two copies of sanitizer runtime.
+		// See issue 8788 for details.

+			continue
 		default:
 			bareLDFLAGS = append(bareLDFLAGS, f)
 		}
```

## コアとなるコードの解説

上記のコードスニペットは、`bareLDFLAGS`というスライス（Goにおける動的配列）を構築するループの一部です。このスライスには、CgoのビルドプロセスでC/C++リンカに渡されるべきフラグが含まれています。

追加された`case strings.HasPrefix(f, "-fsanitize="): continue`という行がこのコミットの核心です。

*   `f` は、C/C++リンカに渡される個々のフラグ文字列を表します。
*   `strings.HasPrefix(f, "-fsanitize=")` は、現在のフラグ`f`が文字列`-fsanitize=`で始まるかどうかをチェックします。
*   もしフラグが`-fsanitize=`で始まる場合（例: `-fsanitize=address`, `-fsanitize=thread`など）、`continue`ステートメントが実行されます。これは、現在のループのイテレーションをスキップし、次のフラグの処理に移ることを意味します。

この変更により、`-fsanitize=`フラグは`bareLDFLAGS`スライスに追加されなくなり、結果としてCgoのオブジェクトファイル生成時にC/C++コンパイラに渡されなくなります。これにより、C/C++コンパイラがサニタイザーランタイムを中間オブジェクトファイルに誤ってリンクすることを防ぎ、サニタイザーランタイムの二重リンク問題を解決します。

コメントで明記されているように、この変更の目的は「コンパイラドライバーが最終リンクを行っていると誤解し、サニタイザーランタイムをオブジェクトファイルにリンクしてしまうのを防ぐ」ことです。これにより、最終的なプログラムがサニタイザーランタイムの二重コピーを持つことを回避します。

# [インデックス 25707] ファイルの概要

このコミットは、Goコンパイラの内部パッケージである `cmd/compile/internal/gc` におけるエラー報告の挙動を修正するものです。具体的には、`parser.go` ファイル内の `syntax_error` 関数における `Yyerror` の呼び出し方が変更されています。また、この修正が正しく機能することを確認するための新しいテストケース `test/fixedbugs/issue13266.go` が追加されています。

## コミット

`cmd/compile/internal/gc` パッケージにおいて、エラー報告に使用される `Yyerror` 関数の内部的な呼び出し方を修正し、フォーマット文字列を正しく使用するように変更しました。これにより、エラーメッセージ内の `%` 文字が誤ってフォーマット指定子として解釈される問題を解決します。

## 変更の背景

この変更は、Goコンパイラが特定の構文エラーメッセージを生成する際に発生していたバグ、具体的には [Issue 13266](https://github.com/golang/go/issues/13266) を修正するために行われました。

問題は、Goのコンパイラが構文エラーを報告する際に使用する `Yyerror` 関数が、`fmt.Printf` のようなフォーマット文字列を期待する実装になっていたにもかかわらず、呼び出し側でエラーメッセージを単純な文字列連結で構築していたことにありました。このため、エラーメッセージの文字列内に `%` (パーセント) 文字が含まれていると、`Yyerror` がそれをフォーマット指定子（例: `%s`, `%d`）として誤って解釈し、予期せぬ挙動（例えば、プログラムのクラッシュや不正確なエラーメッセージの表示）を引き起こしていました。

特に、`package%` のような不正なパッケージ宣言があった場合、`%` がフォーマット指定子として扱われ、後続の引数がないために問題が発生していました。このコミットは、`Yyerror` を呼び出す際に、フォーマット文字列とそれに続く引数を明示的に渡すように修正することで、この問題を解決します。

## 前提知識の解説

### Goコンパイラの構造 (cmd/compile/internal/gc)

Goコンパイラは複数のステージで構成されており、`cmd/compile/internal/gc` はその主要な部分を担っています。このパッケージは、Go言語のソースコードを解析し、抽象構文木 (AST) を構築し、型チェックを行い、最終的に中間表現 (IR) を生成する役割を担っています。`parser.go` は、字句解析器 (lexer) と構文解析器 (parser) のロジックを含み、ソースコードをトークンに分割し、それらのトークンから構文木を構築する部分です。

### Yacc/Goyacc とエラー報告

`parser.go` のようなファイルは、`yacc` (Yet Another Compiler Compiler) またはそのGo言語版である `goyacc` のようなツールによって生成される構文解析器の一部であることが多いです。これらのツールは、文法定義に基づいて構文解析器を生成し、構文エラーが発生した際に呼び出される `yyerror` (または `Yyerror`) という関数を定義することが一般的です。

### フォーマット文字列と可変引数関数

C言語の `printf` やGo言語の `fmt.Printf` のように、多くのプログラミング言語には、フォーマット文字列とそれに続く可変個の引数を受け取る関数が存在します。フォーマット文字列は、出力される文字列の構造を定義し、`%s` (文字列)、`%d` (整数) などのフォーマット指定子を使って、可変引数リストから対応する値を取り出して埋め込みます。

このコミットで問題となったのは、`Yyerror` がこのようなフォーマット文字列を期待する関数であったにもかかわらず、呼び出し側が単一の連結された文字列を渡していた点です。もし連結された文字列内に `%` が含まれていると、`Yyerror` はそれをフォーマット指定子と誤解し、予期せぬ動作を引き起こします。これは、セキュリティ上の脆弱性（フォーマット文字列の脆弱性）にもつながる可能性のある一般的なプログラミングエラーです。

## 技術的詳細

このコミットの技術的な核心は、`Yyerror` 関数の呼び出し規約の誤解と修正にあります。

元のコードでは、`parser.go` 内の `syntax_error` 関数がエラーメッセージを生成する際に、以下のように文字列連結を使用していました。

```go
Yyerror("syntax error: " + msg)
Yyerror("syntax error: unexpected " + tok + msg)
p.syntax_error("") // この場合、Yyerrorは直接呼び出されないが、最終的に問題を引き起こす可能性があった
```

ここで `Yyerror` が `fmt.Printf` のような可変引数を受け取る関数として実装されている場合、`"syntax error: " + msg` のような連結された文字列が第一引数として渡されると、`Yyerror` はその文字列全体をフォーマット文字列として解釈しようとします。もし `msg` の中に `%` が含まれていれば、それはフォーマット指定子として扱われ、対応する引数が存在しないためにランタイムエラーや予期せぬ出力が発生します。

修正後のコードでは、この問題を解決するために、`Yyerror` をフォーマット文字列とそれに続く引数という正しい形式で呼び出すように変更されています。

```go
Yyerror("syntax error: %s", msg)
Yyerror("syntax error: unexpected %s", tok + msg)
p.syntax_error("expecting name") // 具体的なエラーメッセージを渡すように変更
```

これにより、`"syntax error: %s"` がフォーマット文字列として認識され、`msg` や `tok + msg` が `%s` に対応する引数として渡されます。この方法であれば、`msg` や `tok` の中に `%` 文字が含まれていても、それは単なる文字列の一部として扱われ、フォーマット指定子として誤解されることはありません。

`p.syntax_error("")` が `p.syntax_error("expecting name")` に変更された点も重要です。これは、引数なしで `syntax_error` を呼び出すと、内部で `Yyerror` が呼び出される際に、より具体的なエラーメッセージを渡すように修正されたことを示唆しています。これにより、エラーメッセージの質も向上しています。

`test/fixedbugs/issue13266.go` は、この修正が正しく機能することを確認するためのテストケースです。`package%` という不正なコードスニペットを含み、コンパイラが `unexpected %` というエラーを正しく報告することを期待しています。これは、まさに `%` 文字の誤解釈が問題であったことを明確に示しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/parser.go` の変更

1.  **`Yyerror("syntax error: " + msg)` から `Yyerror("syntax error: %s", msg)` への変更**:
    *   **変更前**: `Yyerror` 関数に、`"syntax error: "` と `msg` を連結した単一の文字列を渡していました。もし `msg` の中に `%` が含まれていると、`Yyerror` がそれをフォーマット指定子として解釈し、問題を引き起こす可能性がありました。
    *   **変更後**: `Yyerror` 関数に、フォーマット文字列 `("syntax error: %s")` と、そのフォーマット指定子 `%s` に対応する引数 `msg` を明示的に渡すように変更されました。これにより、`msg` の内容に関わらず、`%` がフォーマット指定子として誤解されることはなくなり、安全かつ意図した通りのエラーメッセージが生成されるようになります。

2.  **`Yyerror("syntax error: unexpected " + tok + msg)` から `Yyerror("syntax error: unexpected %s", tok + msg)` への変更**:
    *   上記と同様の理由で、`unexpected` エラーメッセージの生成方法も修正されました。`tok + msg` という連結された文字列全体が `%s` に対応する引数として渡されるため、安全性が確保されます。

3.  **`p.syntax_error("")` から `p.syntax_error("expecting name")` への変更**:
    *   これは、`sym()` 関数内で構文エラーが発生した場合に呼び出される `syntax_error` の引数を変更したものです。以前は空文字列を渡していましたが、より具体的なエラーメッセージ `"expecting name"` を渡すように修正されました。これにより、ユーザーにとってより分かりやすいエラーメッセージが提供されるようになります。この変更自体は `%` の問題とは直接関係ありませんが、エラー報告の品質向上に寄与しています。

これらの変更により、`Yyerror` がフォーマット文字列を期待する関数であるという前提に基づき、その呼び出し方が統一され、エラーメッセージの生成における潜在的なバグが解消されました。

### `test/fixedbugs/issue13266.go` の追加

この新しいテストファイルは、修正されたエラー報告メカニズムを検証するために特別に設計されています。

*   `// errorcheck`: このコメントは、Goのテストフレームワークに対して、このファイルがコンパイルエラーを期待するテストであることを示します。
*   `package% // ERROR "unexpected %"`: この行がテストの核心です。
    *   `package%`: これはGo言語の不正な構文です。パッケージ名の後に `%` が続くことはありません。
    *   `// ERROR "unexpected %"`: このコメントは、コンパイラがこの行で `"unexpected %"` というエラーメッセージを出力することを期待していることを示します。
    *   このテストケースは、まさに `unexpected %` のようなメッセージが、`%` をフォーマット指定子として誤解することなく、リテラルな `%` 文字として正しく表示されることを確認します。

このテストの追加により、将来的に同様の回帰バグが発生するのを防ぐための安全網が提供されます。

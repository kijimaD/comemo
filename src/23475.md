# [インデックス 23475] ファイルの概要

このコミットは、Go言語の標準ライブラリである`text/template`パッケージにおいて、テンプレートの関数マップ（function maps）に関するレースコンディションを修正するものです。具体的には、ネストされたテンプレートのエスケープ処理中に、関数マップへの同時読み書きアクセスによって発生する可能性のある競合状態を、`sync.RWMutex`を導入することで解決しています。

## コミット

```
text/template: fix race condition on function maps

The Template objects are supposed to be goroutine-safe once they
have been parsed. This includes the text and html ones.

For html/template, the escape mechanism is triggered at execution
time. It may alter the internal structures of the template, so
a mutex protects them against concurrent accesses.

The text/template package is free of any synchronization primitive.

A race condition may occur when nested templates are escaped:
the escape algorithm alters the function maps of the associated
text templates, while a concurrent template execution may access
the function maps in read mode.

The less invasive fix I have found is to introduce a RWMutex in
text/template to protect the function maps. This is unfortunate
but it should be effective.

Fixes #9945
```

## 変更の背景

Go言語の`text/template`および`html/template`パッケージで提供される`Template`オブジェクトは、一度パースされるとゴルーチンセーフ（複数のゴルーチンから同時に安全にアクセスできる）であることが期待されています。しかし、`text/template`パッケージには、このゴルーチンセーフティを保証するための同期プリミティブ（ミューテックスなど）が欠けていました。

特に問題となったのは、ネストされたテンプレートがエスケープ処理される際に発生するレースコンディションです。`html/template`パッケージでは、実行時にエスケープメカニズムがトリガーされ、これがテンプレートの内部構造を変更する可能性があるため、既にミューテックスによって同時アクセスから保護されていました。しかし、`text/template`ではそのような保護がなく、エスケープアルゴリズムが関連するテキストテンプレートの関数マップを変更している最中に、別のゴルーチンがその関数マップを読み取りモードでアクセスしようとすると、競合状態が発生し、予期せぬ動作やクラッシュにつながる可能性がありました。

このコミットは、この特定のレースコンディションを解消し、`text/template`パッケージの`Template`オブジェクトが期待通りにゴルーチンセーフであることを保証するために導入されました。

## 前提知識の解説

### Goの`text/template`と`html/template`パッケージ

Go言語の標準ライブラリには、テキストベースの出力やHTML出力を生成するためのテンプレートエンジンが用意されています。
*   **`text/template`**: 任意のテキスト形式の出力を生成するための汎用テンプレートエンジンです。設定ファイル、コード生成、メールの本文など、様々な用途に使用されます。
*   **`html/template`**: `text/template`をベースにしており、HTML出力に特化しています。クロスサイトスクリプティング（XSS）攻撃を防ぐために、自動的にコンテンツをエスケープする機能が組み込まれています。これにより、ユーザーが提供したデータがHTMLに挿入される際に、悪意のあるスクリプトが実行されるのを防ぎます。

これらのパッケージでは、テンプレートをパース（解析）し、データと組み合わせて最終的な出力を生成します。テンプレート内では、変数、条件分岐、繰り返し処理、そしてカスタム関数（関数マップに登録された関数）を使用できます。

### Goの並行処理とレースコンディション

Go言語はゴルーチン（goroutine）とチャネル（channel）という強力な機能によって、並行処理を容易に記述できます。
*   **ゴルーチン**: 軽量なスレッドのようなもので、Goランタイムによって管理されます。数千、数万のゴルーチンを同時に実行することが可能です。
*   **レースコンディション（Race Condition）**: 複数のゴルーチンが共有リソース（変数、データ構造など）に同時にアクセスし、少なくとも1つのゴルーチンがそのリソースを変更する可能性がある場合に発生する競合状態です。アクセス順序によって結果が変わるため、プログラムの動作が非決定論的になり、デバッグが困難なバグの原因となります。

レースコンディションを防ぐためには、共有リソースへのアクセスを同期させる必要があります。Goでは主に以下の同期プリミティブが提供されています。
*   **`sync.Mutex`**: 排他ロック（Mutual Exclusion Lock）を提供します。一度に1つのゴルーチンだけがロックを取得でき、共有リソースにアクセスできます。読み書き両方の操作を保護します。
*   **`sync.RWMutex`**: 読み書きロック（Reader-Writer Mutex）を提供します。これは`sync.Mutex`の特殊な形式で、以下のルールで動作します。
    *   複数のゴルーチンが同時に読み取りロック（`RLock`）を取得し、共有リソースを読み取ることができます。
    *   書き込みロック（`Lock`）は一度に1つのゴルーチンしか取得できません。
    *   書き込みロックが保持されている間は、読み取りロックも書き込みロックも取得できません。
    *   読み取りロックが1つでも保持されている間は、書き込みロックは取得できません。
    この特性により、読み取り操作が頻繁で書き込み操作が少ない場合に、`sync.Mutex`よりも高い並行性を実現できます。

### テンプレートのエスケープ処理

`html/template`パッケージにおけるエスケープ処理は、テンプレートの実行時に行われます。この処理は、テンプレートの内部表現（AST: 抽象構文木など）を分析し、安全でない可能性のある部分を特定して、適切なエスケープ関数を挿入します。この過程で、テンプレートの内部構造、特にカスタム関数を管理する関数マップが変更されることがあります。

### 関数マップ (Function Maps)

`text/template`および`html/template`では、ユーザーが独自の関数を定義し、テンプレート内で呼び出すことができます。これらの関数は`FuncMap`という型のマップに登録され、テンプレートエンジンがテンプレートをパースまたは実行する際に参照されます。関数マップは、テンプレートの柔軟性を高める重要な機能です。

## 技術的詳細

このコミットで修正されたレースコンディションは、`text/template`パッケージにおいて、ネストされたテンプレートのエスケープ処理と、関数マップへの同時アクセスが原因で発生していました。

1.  **問題の発生源**: `html/template`パッケージは、セキュリティ上の理由から、テンプレートの実行時にエスケープ処理を行います。このエスケープ処理は、テンプレートの内部構造、特にカスタム関数を管理する`FuncMap`を動的に変更する可能性があります。
2.  **`html/template`の既存の対策**: `html/template`は、この内部構造の変更が並行して行われることを防ぐために、既にミューテックスを使用して保護していました。これにより、エスケープ処理中に他のゴルーチンがテンプレートの内部状態を読み書きしようとしても、安全性が保たれていました。
3.  **`text/template`の欠陥**: しかし、`text/template`パッケージには、このような同期プリミティブが導入されていませんでした。`html/template`が`text/template`の機能を利用してエスケープ処理を行う際、`text/template`の関数マップが変更される可能性がありました。
4.  **レースコンディションのシナリオ**:
    *   ゴルーチンAが、ネストされたテンプレートのエスケープ処理を開始し、その過程で`text/template`の関数マップを更新しようとします。
    *   同時に、ゴルーチンBが、別のテンプレートの実行中に、同じ`text/template`の関数マップから関数を検索（読み取り）しようとします。
    *   ゴルーチンAがマップを変更している最中にゴルーチンBがマップを読み取ると、マップが不完全な状態であったり、破損した状態であったりする可能性があり、これがレースコンディションを引き起こします。結果として、プログラムのクラッシュや不正な動作につながります。
5.  **`sync.RWMutex`の選択**: この問題に対する修正として、`text/template`パッケージの`Template`構造体に`sync.RWMutex`が導入されました。`RWMutex`は、読み取り操作が頻繁で書き込み操作が比較的少ない場合に効率的です。関数マップは、テンプレートのパース時や`Funcs`メソッドでカスタム関数が追加される際に書き込まれ、テンプレートの実行時や関数検索時に頻繁に読み取られます。このアクセスパターンに`RWMutex`は最適であり、読み取りの並行性を維持しつつ、書き込み操作の安全性を確保できます。

この修正は、`text/template`パッケージのゴルーチンセーフティを向上させ、特に`html/template`との連携において発生しうる潜在的なバグを解消しました。

## コアとなるコードの解説

このコミットの核心は、`text/template`パッケージの`common`構造体に`sync.RWMutex`型のフィールド`muFuncs`を導入し、関数マップ（`parseFuncs`と`execFuncs`）へのアクセスをこのミューテックスで同期させる点にあります。

1.  **`muFuncs sync.RWMutex`の導入**:
    *   `common`構造体は、関連する複数のテンプレート間で共有される情報を保持します。関数マップもこの共有情報の一部です。
    *   `muFuncs`は、`parseFuncs`（パース時に使用される関数マップ）と`execFuncs`（実行時に使用される関数マップ）の両方を保護します。

2.  **`findFunction`関数での`RLock`**:
    *   `findFunction`は、テンプレート内で特定の名前の関数を検索する（読み取る）ために使用されます。
    *   `tmpl.muFuncs.RLock()`と`defer tmpl.muFuncs.RUnlock()`が追加されたことで、複数のゴルーチンが同時に関数を検索しても、互いにブロックすることなく並行して実行できるようになります。これは`RWMutex`の「複数のリーダーを許可する」という特性によるものです。

3.  **`Template.Clone()`メソッドでの`RLock`**:
    *   `Clone()`メソッドは、既存のテンプレートのコピーを作成します。この際、元のテンプレートの関数マップを読み取って新しいテンプレートにコピーする必要があります。
    *   ここでも`RLock`を使用することで、クローン操作中に他のゴルーチンが関数マップを読み取ることを妨げず、並行性を維持します。

4.  **`Template.Funcs()`メソッドでの`Lock`**:
    *   `Funcs()`メソッドは、テンプレートに新しいカスタム関数を追加する（関数マップを書き換える）ために使用されます。
    *   `tmpl.muFuncs.Lock()`と`defer tmpl.muFuncs.Unlock()`が追加されたことで、関数マップへの書き込み操作は排他的に実行されます。つまり、`Funcs()`が実行されている間は、他のゴルーチンは関数マップの読み取りも書き込みもできません。これにより、関数マップの整合性が保たれます。

5.  **`Template.Parse()`メソッドでの`RLock`**:
    *   `Parse()`メソッドは、テンプレートのテキストを解析し、内部表現を構築します。この解析プロセス中に、既存の関数マップを参照して、テンプレート内で使用されている関数が有効かどうかをチェックします。
    *   `RLock`を使用することで、パース処理中に他のゴルーチンが関数マップを読み取ることを許可しつつ、パース処理自体が関数マップの変更によって影響を受けないように保護します。

これらの変更により、`text/template`パッケージの関数マップへのアクセスが適切に同期され、特に`html/template`のエスケープ処理のような動的な変更が発生するシナリオにおいても、レースコンディションが効果的に防止されるようになりました。`RWMutex`の採用は、読み取り操作の並行性を最大限に活かしつつ、書き込み操作の安全性を確保するという、このユースケースに最適な選択と言えます。

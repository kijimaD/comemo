## 変更の背景

この変更の背景には、Go言語のプロファイリングツール `pprof` のブロックプロファイルテスト (`TestBlockProfile`) が、特定の環境、特に新しい `arm64` ポートで不安定になるという問題がありました。

`pprof.writeBlock` 関数がデバッグモードで使用される際、その出力は `text/tabwriter` パッケージを介して整形されます。`text/tabwriter` は、テキストをタブ区切りで整形し、列を揃えるためのユーティリティですが、その内部的なタブ展開ロジックは、環境や出力される内容によって、単一のタブ文字 (`\t`) が複数のタブ文字に展開される可能性があります。

`TestBlockProfile` は、`pprof` の出力結果を正規表現で検証することで、プロファイルデータが期待通りに生成されているかを確認しています。しかし、`tabwriter` によるタブの不規則な展開が発生すると、テストコード内で定義された正規表現が実際の出力と一致しなくなり、テストが失敗する原因となっていました。

この問題は、特に `arm64` アーキテクチャでのテスト実行時に顕著に観測されたため、クロスプラットフォームでのテストの堅牢性を確保するために、正規表現をより柔軟なものに変更する必要が生じました。

## 前提知識の解説

### Goのプロファイリングツール `pprof`

`pprof` は、Goプログラムのパフォーマンスを分析するための強力なツールです。CPU使用率、メモリ割り当て、ゴルーチンのブロック、ミューテックスの競合など、様々な種類のプロファイルデータを収集し、可視化することができます。

*   **ブロックプロファイル (Block Profile)**: ゴルーチンが同期プリミティブ（ミューテックス、チャネル、`sync.Cond` など）によってブロックされた時間のプロファイルです。これにより、プログラム内の並行処理のボトルネックや競合箇所を特定するのに役立ちます。`pprof` は、ブロックされたゴルーチンのスタックトレースと、ブロックされた時間の合計を記録します。

### `text/tabwriter` パッケージ

`text/tabwriter` パッケージは、Go言語の標準ライブラリの一部であり、タブ区切りのテキストを整形して、列をきれいに揃えるためのライターを実装しています。これは、表形式のデータを整形して出力する際に非常に便利です。

*   **動作原理**: `tabwriter` は、入力ストリームからタブ文字 (`\t`) を読み取り、それらを適切な数のスペースに変換して、次の列の開始位置を揃えます。しかし、その内部的なロジックは、出力先の幅や、タブ文字の前に来るテキストの長さによって、単一のタブが複数のタブ文字（またはスペース）として解釈・展開されることがあります。これは、特にデバッグ出力やテストの検証において、厳密な文字列マッチングを行う場合に問題となることがあります。

### 正規表現 (`regexp` パッケージ)

Go言語の `regexp` パッケージは、正規表現による文字列の検索、置換、分割などの操作を提供します。正規表現は、特定のパターンに一致する文字列を記述するための強力なミニ言語です。

*   **`regexp.MustCompile`**: 与えられた正規表現パターンをコンパイルします。パターンが無効な場合、パニックを引き起こします。
*   **`MatchString`**: コンパイルされた正規表現が与えられた文字列に一致するかどうかを判定します。
*   **`\t`**: 正規表現において、タブ文字そのものに一致します。
*   **`+`**: 直前の要素が1回以上繰り返されることに一致します。例えば、`a+` は "a", "aa", "aaa" などに一致します。
*   **`\t+`**: 1つ以上のタブ文字に一致します。これにより、単一のタブだけでなく、複数のタブが連続している場合にも対応できます。

### クロスプラットフォームでのテストの頑健性

ソフトウェア開発において、特に低レベルなランタイムやシステムに近いコードでは、異なるCPUアーキテクチャ（例: `amd64`, `arm64`）やオペレーティングシステム（例: Linux, Windows, macOS）間で挙動が微妙に異なることがあります。これは、アラインメント、メモリレイアウト、システムコールのセマンティクス、あるいは今回のようにテキスト整形ライブラリの挙動の違いに起因することがあります。

テストコードは、このような環境依存性を吸収し、どのプラットフォームでも一貫して成功するように設計されるべきです。今回のケースでは、`tabwriter` の出力が環境によって異なる可能性があったため、テストの正規表現をより柔軟にすることで、この環境依存性を吸収し、テストの頑健性を高める必要がありました。

## 技術的詳細

`pprof.writeBlock` のデバッグ出力は、スタックトレースやアドレスなどの情報を含み、これらが `text/tabwriter` を通して整形されます。`tabwriter` は、出力の列を揃えるためにタブ文字をスペースに変換しますが、その変換ロジックは、タブ文字の前のテキストの長さや、出力先のタブストップの設定によって、生成されるスペースの数が変動する可能性があります。

例えば、`tabwriter` は、ある列のテキストが短い場合、次の列との間に多くのスペース（またはタブ）を挿入して揃えようとします。しかし、別の環境や異なる入力では、同じタブ文字が異なる数のスペースに展開されることがあります。

元の `TestBlockProfile` の正規表現は、特定の数のタブ文字 (`\t`) に厳密に一致することを期待していました。しかし、`arm64` 環境で観測されたように、`tabwriter` が単一のタブを複数のタブ（またはスペース）として展開してしまうと、元の正規表現は期待するパターンに一致せず、テストが失敗していました。

この問題を解決するためには、正規表現が「1つ以上のタブ文字」に一致するように変更する必要があります。これにより、`tabwriter` が単一のタブをどのように展開しても、テストは正しく動作するようになります。

## コアとなるコードの解説

変更は `src/runtime/pprof/pprof_test.go` ファイルの `TestBlockProfile` 関数内で行われています。

元のコードでは、`test.re` という変数に格納された正規表現パターンを直接コンパイルし、`prof` （`pprof` の出力文字列）に一致するかどうかを `MatchString` で確認していました。

```go
if !regexp.MustCompile(test.re).MatchString(prof) {
```

このコミットでは、`test.re` を直接使用するのではなく、`strings.Replace` 関数を使って `test.re` 内のタブ文字 (`\t`) を `\t+` に置換しています。

```go
if !regexp.MustCompile(strings.Replace(test.re, "\t", "\t+", -1)).MatchString(prof) {
```

*   **`strings.Replace(test.re, "\t", "\t+", -1)`**:
    *   `test.re`: 置換対象の文字列（元の正規表現パターン）。
    *   `"\t"`: 検索対象の文字列（単一のタブ文字）。
    *   `"\t+"`: 置換後の文字列（正規表現の `\t+`）。これは「1つ以上のタブ文字」に一致します。
    *   `-1`: すべての一致を置換することを意味します。

この変更により、元の正規表現パターンに含まれるすべての単一のタブ文字 (`\t`) が、`\t+`（1つ以上のタブ文字）に変換されます。例えば、元の `test.re` が `"#\t0x1088ec\tsync.(*Cond).Wait+0xfc"` のようなパターンを含んでいた場合、この置換によって `"#\t+0x1088ec\t+sync.(*Cond).Wait+0xfc"` のようなパターンに変換されます。

結果として、`pprof.writeBlock` の出力が `text/tabwriter` によってタブが複数に展開されたとしても、`\t+` はそれらの複数のタブにも一致するため、テストは期待通りに成功するようになります。これにより、`TestBlockProfile` は異なる環境や `tabwriter` の挙動の差異に対してより堅牢になりました。

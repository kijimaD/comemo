# [インデックス 24467] ファイルの概要

このコミットは、Goの`cmd/cgo`ツールにおける、C言語の構造体とGo言語の構造体のサイズ不一致の問題を解決するための変更です。具体的には、C言語の構造体の末尾にゼロサイズのフィールドが存在する場合に、Goコンパイラが追加のパディングバイトを挿入してしまうことで発生するサイズの違いを解消します。

Author: Ian Lance Taylor <iant@golang.org>
Date:   Wed Jul 29 22:04:09 2015 -0700

    cmd/cgo: discard trailing zero-sized fields in a non-empty C struct
    
    In order to fix issue #9401 the compiler was changed to add a padding
    byte to any non-empty Go struct that ends in a zero-sized field.  That
    causes the Go version of such a C struct to have a different size than
    the C struct, which can considerable confusion.  Change cgo so that it
    discards any such zero-sized fields, so that the Go and C structs are
    the same size.
    
    This is a change from previous releases, in that it used to be
    possible to refer to a zero-sized trailing field (by taking its
    address), and with this change it no longer is.  That is unfortunate,
    but something has to change.  It seems better to visibly break
    programs that do this rather than to silently break programs that rely
    on the struct sizes being the same.

## 元コミット内容

`cmd/cgo`: 非空のC構造体における末尾のゼロサイズフィールドを破棄する

Issue #9401を修正するために、コンパイラはゼロサイズのフィールドで終わる非空のGo構造体にパディングバイトを追加するように変更されました。これにより、そのようなC構造体のGoバージョンがC構造体とは異なるサイズになり、かなりの混乱を引き起こす可能性がありました。cgoを変更し、そのようなゼロサイズのフィールドを破棄することで、GoとCの構造体が同じサイズになるようにします。

これは以前のリリースからの変更点であり、以前はゼロサイズの末尾フィールドを参照（そのアドレスを取得することによって）することが可能でしたが、この変更によりそれができなくなります。これは残念ですが、何かを変更する必要がありました。構造体サイズが同じであることに依存するプログラムを黙って壊すよりも、これを行うプログラムを明示的に壊す方が良いと思われます。

#9401を更新。
#11925を修正。

## 変更の背景

この変更の背景には、Go言語とC言語の相互運用を可能にする`cgo`ツールにおける、構造体のメモリレイアウトに関する深い問題がありました。

1.  **Goコンパイラの変更 (Issue #9401関連)**: 以前のGoコンパイラは、ゼロサイズのフィールド（例: `[0]byte`や`[0]char`）で終わる非空のGo構造体に対して、メモリレイアウトの整合性を保つために1バイトのパディングを追加するようになりました。これは、Goの型システムとメモリ管理の内部的な要件によるものです。例えば、`struct { int i; [0]byte }`のような構造体は、Goでは`int`の後に1バイトのパディングが追加され、`sizeof`演算子で取得されるサイズが`int`のサイズよりも大きくなる可能性がありました。

2.  **C言語のゼロサイズ配列**: C言語では、構造体の末尾にゼロサイズの配列（例: `char a[0];` や `char b[];`）を配置することがあります。これは「フレキシブル配列メンバー (Flexible Array Member, FAM)」と呼ばれることもあり、構造体の直後に可変長のデータを配置するためのテクニックとして使われます。C言語の仕様では、このようなゼロサイズ配列は構造体のサイズには寄与しないとされています。

3.  **cgoにおける問題**: `cgo`はC言語の型をGo言語の型にマッピングする役割を担っています。Goコンパイラの変更により、C言語の構造体が末尾にゼロサイズのフィールドを持つ場合、`cgo`が生成するGo側の構造体は、Goコンパイラのパディングルールに従ってC言語の構造体とは異なるサイズになってしまうという問題が発生しました。このサイズ不一致は、特にC言語のライブラリとGo言語のコード間で構造体をやり取りする際に、メモリ破壊や予期せぬ動作を引き起こす可能性がありました（Issue #11925）。

4.  **設計上のトレードオフ**: この問題に対する解決策として、GoとCの構造体サイズを一致させることを優先し、そのためにGo側からゼロサイズの末尾フィールドへの参照を不可能にするというトレードオフが選択されました。これは、構造体サイズの一貫性が、ゼロサイズフィールドへの参照可能性よりも重要であるという判断に基づいています。コミットメッセージにあるように、「構造体サイズが同じであることに依存するプログラムを黙って壊すよりも、これを行うプログラムを明示的に壊す方が良い」という思想が反映されています。

## 前提知識の解説

### 1. Go言語の`cgo`

`cgo`はGo言語のツールチェーンの一部であり、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのメカニズムを提供します。これにより、既存のCライブラリをGoプロジェクトで利用したり、パフォーマンスが重要な部分をCで記述したりすることが可能になります。`cgo`は、Cの型定義をGoの型定義に変換し、GoとCの間の呼び出し規約を処理するためのラッパーコードを生成します。

### 2. Go言語の構造体とメモリレイアウト

Go言語の構造体は、フィールドがメモリ上に連続して配置されます。しかし、CPUのアーキテクチャによっては、特定のデータ型が特定のメモリアドレス境界に配置される必要がある（アライメント要件）ため、コンパイラは構造体のフィールド間にパディングバイトを挿入することがあります。これにより、構造体の実際のサイズが、各フィールドのサイズの合計よりも大きくなることがあります。

### 3. C言語の構造体とゼロサイズ配列 (Flexible Array Member)

C言語（特にC99以降）では、構造体の最後のメンバーとして不完全な配列型（例: `char data[];` や `char data[0];`）を宣言することができます。これをフレキシブル配列メンバー (FAM) と呼びます。この配列自体は構造体のサイズには含まれず、その直後に可変長のデータを配置するためのプレースホルダーとして機能します。これは、動的にサイズが決まるデータを効率的に扱うための一般的なイディオムです。

例:
```c
struct Packet {
    int header;
    char payload[]; // ゼロサイズ配列、構造体のサイズには含まれない
};
```
この`payload`フィールドのアドレスは、`Packet`構造体の直後のメモリを指すことになります。

### 4. Go言語におけるゼロサイズフィールドのパディング (Issue #9401)

Go言語では、`struct{}`（空の構造体）はサイズが0ですが、メモリ上に配置される際には、そのアドレスが一意であることを保証するために1バイトのパディングが追加されることがあります。特に、非空の構造体の末尾にゼロサイズのフィールド（例: `[0]byte`）がある場合、Goコンパイラは、そのゼロサイズフィールドのアドレスが有効なポインタとして扱われることを保証するために、1バイトのパディングを追加するようになりました。これにより、`unsafe.Sizeof(struct { int i; [0]byte } )` の結果が `sizeof(int)` よりも1バイト大きくなる、といった現象が発生していました。

## 技術的詳細

このコミットの技術的詳細な変更は、`src/cmd/cgo/gcc.go`ファイル内の`typeConv.Struct`メソッドに集中しています。このメソッドは、C言語の構造体定義をGo言語の構造体定義に変換する際の主要なロジックを含んでいます。

変更の核心は以下の点にあります。

1.  **`pad`関数の変更**:
    *   `pad`関数は、構造体のフィールド間にパディングを追加するために使用されます。
    *   変更前は`fld` (フィールドのリスト) のみを引数としていましたが、変更後は`sizes` (各フィールドのサイズを保持するリスト) も引数として受け取るようになりました。これにより、パディングフィールドのサイズも追跡できるようになります。

2.  **`typeConv.Struct`内の`sizes`スライスの導入**:
    *   C構造体をGo構造体に変換する際、各フィールドのGo側でのサイズを追跡するために、`sizes := make([]int64, 0, ...)`という新しいスライスが導入されました。
    *   フィールドが追加されるたびに、そのフィールドのサイズが`sizes`スライスに追加されます。パディングフィールドが追加される際も、そのパディングサイズが`sizes`スライスに記録されます。

3.  **末尾のゼロサイズフィールドの破棄ロジック**:
    *   `typeConv.Struct`メソッドの最後に、以下の新しいロジックが追加されました。
        ```go
        	// If the last field in a non-zero-sized struct is zero-sized
        	// the compiler is going to pad it by one (see issue 9401).
        	// We can't permit that, because then the size of the Go
        	// struct will not be the same as the size of the C struct.
        	// Our only option in such a case is to remove the field,
        	// which means that it can not be referenced from Go.
        	for off > 0 && sizes[len(sizes)-1] == 0 {
        		n := len(sizes)
        		fld = fld[0 : n-1]
        		sizes = sizes[0 : n-1]
        	}
        ```
    *   このコードブロックは、Go構造体の変換が完了した後で実行されます。
    *   `off > 0` は、構造体自体が空ではないことを確認します。
    *   `sizes[len(sizes)-1] == 0` は、Go構造体の最後のフィールドがゼロサイズであることをチェックします。
    *   もしこれらの条件が満たされた場合（つまり、非空のGo構造体の末尾にゼロサイズのフィールドがある場合）、GoコンパイラがIssue #9401で述べられているように1バイトのパディングを追加してしまうため、C構造体とのサイズ不一致が発生します。
    *   この不一致を避けるため、`cgo`はGo構造体の末尾からゼロサイズのフィールドを削除します (`fld = fld[0 : n-1]`, `sizes = sizes[0 : n-1]`)。これにより、Go側で生成される構造体は、C側の構造体と完全に同じサイズになります。
    *   結果として、Goコードからは、C構造体の末尾にあるゼロサイズフィールドに直接アクセスしたり、そのアドレスを取得したりすることはできなくなります。

この変更により、`cgo`はC言語のフレキシブル配列メンバーのようなゼロサイズフィールドを、Goの型システムに適合させつつ、Cとのメモリレイアウト互換性を維持するように処理します。

## コアとなるコードの解説

`src/cmd/cgo/gcc.go` の `typeConv.Struct` メソッド内の以下の部分が、この変更の核心です。

```go
	// If the last field in a non-zero-sized struct is zero-sized
	// the compiler is going to pad it by one (see issue 9401).
	// We can't permit that, because then the size of the Go
	// struct will not be the same as the size of the C struct.
	// Our only option in such a case is to remove the field,
	// which means that it can not be referenced from Go.
	for off > 0 && sizes[len(sizes)-1] == 0 {
		n := len(sizes)
		fld = fld[0 : n-1]
		sizes = sizes[0 : n-1]
	}
```

*   `for off > 0 && sizes[len(sizes)-1] == 0`: このループは、Go構造体が空ではなく (`off > 0`)、かつ、現在処理しているGo構造体の最後のフィールドがゼロサイズである (`sizes[len(sizes)-1] == 0`) 限り繰り返されます。
*   `n := len(sizes)`: 現在のフィールド数（およびサイズ数）を取得します。
*   `fld = fld[0 : n-1]`: Go構造体のフィールドリスト `fld` から最後のフィールドを削除します。
*   `sizes = sizes[0 : n-1]`: 同様に、フィールドサイズを追跡する `sizes` リストからも最後の要素を削除します。

このロジックにより、C言語の構造体の末尾に存在するゼロサイズのフィールド（Goコンパイラがパディングを追加してしまう原因となるもの）が、`cgo`によって生成されるGo構造体からは完全に削除されます。これにより、GoとCの構造体のサイズが一致し、`cgo`を介した相互運用におけるメモリレイアウトの不整合が解消されます。

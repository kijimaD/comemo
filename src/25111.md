# [インデックス 25111] ファイルの概要

このコミットは、Go言語の `syscall` パッケージにおけるBSD系OS（FreeBSD, OpenBSDなど）でのリンク層情報（`sockaddr_dl`構造体）のパース処理におけるアライメントチェックの不具合を修正するものです。特に、ネットワークルーティングメッセージからリンク層アドレスを抽出する際に、データの長さ計算とアライメント処理が正しく行われるように改善されています。

## 変更の背景

BSD系OSでは、ネットワークインターフェースやルーティングテーブルに関する情報が `sysctl` や `route` ソケットを通じてカーネルから取得されます。これらの情報は、`sockaddr` 構造体の一種である `sockaddr_dl` (datalink socket address) を用いて表現されることがよくあります。`sockaddr_dl` は、インターフェース名、ハードウェアアドレス（MACアドレスなど）、およびプロトコルアドレスを含むリンク層情報をカプセル化します。

このコミット以前のGoの `syscall` パッケージでは、これらのリンク層情報をパースする際に、データの長さ計算とメモリアライメントの処理に不整合がありました。具体的には、`sockaddr_dl` 構造体自体が提供する長さ情報と、その内部に含まれるリンク層情報の実際の長さ、そしてシステムが要求するメモリアライメントの間の関係が正しく扱われていませんでした。

この不整合は、特に `sockaddr_dl` がルーティングメッセージ内で「裸の（naked）」リンク層情報として現れる場合と、`sockaddr_dl` 構造体によって「ラップされた（wrapped）」リンク層情報として現れる場合とで、異なる長さの解釈が必要となるにもかかわらず、一貫性のない処理が行われていたことに起因します。結果として、不正なメモリアクセスや、`EINVAL` (Invalid argument) エラーが発生する可能性がありました。コミットメッセージで言及されている `Fixes #12641` は、この問題がGoのイシュートラッカーで報告されていたことを示唆しています。

## 前提知識の解説

*   **`syscall` パッケージ**: Go言語の `syscall` パッケージは、オペレーティングシステムが提供する低レベルなプリミティブ（システムコール）へのインターフェースを提供します。これにより、ファイルシステム操作、ネットワーク通信、プロセス管理など、OSカーネルと直接対話する機能を実現します。
*   **BSD系OSのネットワークスタック**: FreeBSD, OpenBSDなどのBSD系OSは、ネットワークインターフェースやルーティング情報を `sysctl` や `route` ソケットを介してユーザー空間に公開します。これらの情報は、特定の構造体形式でエンコードされており、正確なパースが必要です。
*   **`sockaddr_dl` 構造体**: `sockaddr_dl` は、BSD系OSでデータリンク層のアドレス（例: イーサネットのMACアドレス）を表現するために使用されるソケットアドレス構造体です。この構造体は、インターフェースのタイプ、名前の長さ、アドレスの長さ、セレクタの長さ、そして実際のデータ（インターフェース名やMACアドレスなど）を含みます。
    ```c
    struct sockaddr_dl {
        u_char  sdl_len;    /* struct length */
        u_char  sdl_family; /* AF_LINK */
        u_short sdl_index;  /* if index */
        u_char  sdl_type;   /* interface type */
        u_char  sdl_nlen;   /* interface name length */
        u_char  sdl_alen;   /* link level address length */
        u_char  sdl_slen;   /* selector length */
        char    sdl_data[120]; /* raw link-level address and name */
    };
    ```
    `sdl_len` フィールドは構造体全体の長さをバイト単位で示し、`sdl_nlen`, `sdl_alen`, `sdl_slen` はそれぞれインターフェース名、リンク層アドレス、セレクタの長さを指定します。
*   **メモリアライメント**: コンピュータのアーキテクチャによっては、メモリ上のデータが特定のバイト境界に配置されている必要があります。これをメモリアライメントと呼びます。例えば、4バイトの整数は4の倍数のアドレスに配置される必要がある、といった制約です。アライメントが正しくないと、パフォーマンスの低下や、最悪の場合、ハードウェア例外（バスエラーなど）が発生する可能性があります。`rsaAlignOf` のような関数は、このアライメント要件を満たすために、指定された長さを次の有効なアライメント境界に切り上げるために使用されます。
*   **`EINVAL`**: `errno` の値の一つで、"Invalid argument"（無効な引数）を意味します。システムコールやライブラリ関数に渡された引数が、その関数の期待する形式や範囲に合致しない場合に返されます。この文脈では、パースしようとしているデータが期待される構造体の長さや形式を満たしていない場合に発生します。

## 技術的詳細

このコミットの核心は、BSD系OSのルーティングメッセージからリンク層アドレスをパースする際の、データの長さ計算とアライメント処理の正確性を確保することにあります。

`sockaddr_dl` 構造体は、その `sdl_len` フィールドで構造体全体の長さを指定します。しかし、ルーティングメッセージの文脈では、`sockaddr_dl` 構造体自体がメッセージの一部として含まれる場合と、`sockaddr_dl` の内部データ（`sdl_data`）が直接メッセージの一部として扱われる場合があります。

問題は、`parseLinkLayerAddr` 関数が、`sockaddr_dl` 構造体のヘッダ部分（`sdl_len`, `sdl_family` など）と、その後に続く可変長のデータ（インターフェース名、MACアドレスなど）をどのように解釈するか、という点にありました。

以前の実装では、`rsaAlignOf` 関数を使ってアライメントを考慮した長さを計算していましたが、この計算が常に正しいとは限りませんでした。特に、`sockaddr_dl` 構造体の `sdl_len` フィールドが示す長さと、実際にパースすべきリンク層情報の長さが異なるケース（例えば、`sockaddr_dl` が単なるラッパーとして機能し、その内部のデータ長が重要になる場合）で問題が生じていました。

このコミットでは、以下の2つのシナリオを明確に区別し、それぞれに対応する長さ計算を導入しています。

1.  **`sockaddr_dl` でラップされたリンク層情報**: この場合、`sockaddr_dl` 構造体自体の `sdl_len` フィールドが示す長さに従う必要があります。
2.  **「裸の」リンク層情報**: この場合、`sockaddr_dl` 構造体のヘッダは存在せず、リンク層情報全体の長さを直接使用する必要があります。

修正は、`parseLinkLayerAddr` 関数内で、まずリンク層情報の実際のデータ長 `l` を計算し、その後にこの `l` を `rsaAlignOf` でアライメント調整するという二段階のアプローチを取ることで、この問題を解決しています。これにより、データの読み取り範囲が正確になり、`EINVAL` エラーの発生を防ぎます。

また、`parseSockaddrLink` 関数に `len(b) < 8` のチェックが追加されたことで、最低限の `sockaddr_dl` ヘッダ（`sdl_len` から `sdl_slen` までの8バイト）が存在しない場合に早期にエラーを返すようになり、不正な入力に対する堅牢性が向上しています。

## コアとなるコードの解説

### `src/syscall/route_bsd.go` の変更点

1.  **`parseSockaddrLink` 関数への早期エラーチェック追加**:
    ```go
    +	if len(b) < 8 {
    +		return nil, EINVAL
    +	}
    ```
    `parseSockaddrLink` は `sockaddr_dl` 構造体をパースすることを期待しています。`sockaddr_dl` のヘッダ部分（`sdl_len` から `sdl_slen` まで）は最低8バイトを占めます。この変更により、入力バイトスライス `b` の長さが8バイト未満の場合、`sockaddr_dl` のヘッダすら読み取れないため、早期に `EINVAL` エラーを返して不正な入力に対する堅牢性を高めています。

2.  **`parseLinkLayerAddr` 関数における長さ `l` の計算方法の変更**:
    ```go
    -	l := rsaAlignOf(int(4 + lla.Nlen + lla.Alen + lla.Slen))
    +	l := 4 + int(lla.Nlen) + int(lla.Alen) + int(lla.Slen)
    ```
    以前は、リンク層情報の実際の長さ（4バイトのヘッダ + 名前長 + アドレス長 + セレクタ長）を計算した直後に `rsaAlignOf` でアライメント調整を行っていました。この修正では、まず `l` を**アライメントを考慮しない実際のデータ長**として計算しています。`4` は `linkLayerAddr` 構造体の固定ヘッダ部分（`Type`, `Nlen`, `Alen`, `Slen`）の合計バイト数です。この変更により、`l` はデータが占める正確なバイト数を表すようになります。

3.  **`for` ループの条件変更**:
    ```go
    -	for i := 0; len(sa.Data) > i && i < int(lla.Nlen+lla.Alen+lla.Slen); i++ {
    +	for i := 0; len(sa.Data) > i && i < l-4; i++ {
    ```
    リンク層データを `sa.Data` にコピーするループの条件が変更されました。以前は `lla.Nlen+lla.Alen+lla.Slen` を直接使用していましたが、これは `linkLayerAddr` ヘッダの後の可変長データの合計長です。新しい条件 `l-4` は、`l`（アライメントを考慮しない実際のデータ長）から固定ヘッダの4バイトを引いたものであり、これもまた可変長データの合計長を正確に表します。この変更は、`l` の計算方法の変更と一貫性を保つためのものです。

4.  **`parseLinkLayerAddr` 関数の戻り値の変更**:
    ```go
    -	return sa, l, nil
    +	return sa, rsaAlignOf(l), nil
    ```
    `parseLinkLayerAddr` は、パースされた `SockaddrDatalink` 構造体と、パースに使用されたバイトスライスの長さ（次のパース開始位置を示すため）を返します。以前は、アライメント調整前の `l` を返していました。この修正では、**アライメント調整後の `rsaAlignOf(l)` を返す**ように変更されています。これは、ルーティングメッセージのパースにおいて、次の構造体がアライメントされた境界から始まることを保証するために重要です。この変更により、`parseLinkLayerAddr` の呼び出し元が常にアライメントされた長さを取得し、後続のパース処理が正しく行われるようになります。

これらの変更により、`syscall` パッケージはBSD系OSのルーティングメッセージに含まれるリンク層情報を、その形式（`sockaddr_dl` でラップされているか、裸のデータか）に関わらず、正確な長さとアライメントでパースできるようになりました。

### `src/syscall/route_bsd_test.go` の変更点

このファイルでは、`parseInterfaceMessageTests` という新しいテストデータセットと、それを使用する `TestParseInterfaceMessage` 関数が追加されています。

*   **`parseInterfaceMessageTests`**:
    *   `// with link-layer address`: リンク層アドレスを含む典型的な `InterfaceMessage` のデータ例。
    *   `// without link-layer address`: リンク層アドレスを含まない `InterfaceMessage` のデータ例。
    *   `// no data`: 最小限のヘッダ情報のみで、実データがほとんどない `InterfaceMessage` のデータ例。
    これらのテストケースは、`parseSockaddrLink` および `parseLinkLayerAddr` 関数が、様々な形式のリンク層情報に対して正しく動作するかを検証するために設計されています。特に、長さ計算とアライメント処理が異なるシナリオで問題なく機能することを確認します。

*   **`TestParseInterfaceMessage` 関数**:
    `parseInterfaceMessageTests` の各テストケースをループで処理し、`syscall.ParseRoutingSockaddr` 関数を呼び出しています。`ParseRoutingSockaddr` は、ルーティングメッセージ全体をパースし、その中に含まれるソケットアドレス（`sockaddr_dl` など）を抽出する高レベルな関数です。このテストは、修正された低レベルのパースロジックが、システムコールパッケージのより広範なコンテキストで正しく機能することを確認します。エラーが発生した場合 (`err != nil`)、テストは失敗を報告します。

これらのテストの追加は、修正が意図した通りに機能し、回帰バグを防ぐための重要な安全策となります。

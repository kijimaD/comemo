## 変更の背景

この変更は、Goプログラムの実行中に発生する可能性のある「不正な戻り（bad returns）」の問題を診断するためのデバッグメカニズムを導入します。不正な戻りとは、関数が呼び出し元に制御を戻す際に、予期しないアドレスにジャンプしたり、スタックの状態が破損したりする状況を指します。これは、コンパイラやリンカのバグ、あるいはアセンブリコードの誤った記述によって引き起こされることがあり、プログラムのクラッシュや未定義の動作につながります。

このような問題は、特に低レベルのランタイムコードやアセンブリコードにおいて、スタックフレームの管理、レジスタの保存と復元、呼び出し規約の遵守が正確に行われない場合に発生しやすいです。このコミットで追加されたコードは、リンカが生成する最終的なバイナリに、特定のデバッグ命令を埋め込むことで、問題発生時のレジスタやメモリの状態を捕捉し、根本原因の特定を支援することを目的としています。デフォルトで無効になっているのは、通常は不要なオーバーヘッドを避けるためですが、デバッグが必要な場合には非常に強力なツールとなります。

## 前提知識の解説

### Go言語のツールチェインと`liblink`

Go言語のプログラムは、ソースコードから実行可能なバイナリに変換されるまでに、いくつかの段階を経ます。
*   **コンパイラ (`go tool compile`)**: Goのソースコードをアセンブリコード（Goアセンブリ）に変換します。
*   **アセンブラ (`go tool asm`)**: Goアセンブリコードをオブジェクトファイル（`.o`ファイル）に変換します。
*   **リンカ (`go tool link`、内部で`liblink`を使用)**: 複数のオブジェクトファイルやライブラリを結合し、最終的な実行可能バイナリを生成します。`liblink`は、このリンカのコア部分を構成するライブラリです。リンカは、関数呼び出しのアドレス解決、グローバル変数の配置、スタックフレームの構築など、プログラムの実行に必要な低レベルの詳細を処理します。

### 不正な戻り（Bad Returns）

「不正な戻り」は、関数がその実行を終えて呼び出し元に戻る際に、制御が誤った場所に移る現象です。これは以下のような原因で発生する可能性があります。
*   **スタックの破損**: 関数がスタックフレームを正しく設定または解放しない場合、戻りアドレスが上書きされたり、スタックポインタが不正な値を指したりすることがあります。
*   **呼び出し規約の不遵守**: 関数呼び出し規約（例: 引数の渡し方、戻り値の受け取り方、レジスタの保存・復元ルール）が守られない場合、呼び出し元と呼び出された関数の間で状態の不整合が生じ、戻り処理が失敗することがあります。
*   **アセンブリコードのバグ**: 手書きのアセンブリコードにおいて、`RET`（リターン）命令の前にスタックポインタや戻りアドレスが誤って操作されると、不正な戻りが発生します。

### Plan 9アセンブリとGo

Go言語のコンパイラとリンカは、内部的にPlan 9アセンブリという独自のアセンブリ言語を使用しています。これは、特定のCPUアーキテクチャ（例: x86-64, ARM）に依存しない抽象的なアセンブリ言語であり、Goのクロスコンパイル能力を支えています。

*   **`AMOVD`**: これはPlan 9アセンブリにおける「Move Doubleword」または「Move Quadword」命令に相当し、データをある場所から別の場所へ移動させるために使用されます。x86-64アーキテクチャでは、`MOVQ`（Move Quadword）に相当することが多いです。
*   **`D_OREG`**: オフセット付きレジスタ間接アドレッシングモードを示します。`offset(reg)`のような形式で、`reg`レジスタの値に`offset`を加えたアドレスが指すメモリ位置を意味します。
*   **`D_REG`**: レジスタ直接アドレッシングモードを示します。レジスタそのものを指します。
*   **`REGTMP`**: Goのコンパイラやリンカが内部的に使用する一時レジスタです。特定の目的のために値を一時的に保持するために使われます。

## 技術的詳細

このコミットで追加されたデバッグコードは、`src/liblink/obj9.c`内の`addstacksplit`関数に挿入されています。`addstacksplit`は、Goの関数プロローグ（関数の開始時に実行されるコード）の一部として、スタックの分割（stack split）処理に関連する命令を生成する役割を担っています。スタック分割は、Goのgoroutineが小さなスタックで開始し、必要に応じて自動的に拡張されるメカニズムです。

追加されたコードブロックは、`if(0)`という条件で囲まれているため、デフォルトではコンパイル時に削除され、最終的なバイナリには含まれません。しかし、この`if(0)`を`if(1)`に変更して再コンパイルすることで、デバッグコードを有効にできます。

有効化された場合、このコードは以下のPlan 9アセンブリ命令を生成します（x86-64を想定した場合）：

```assembly
AMOVD 0(REGTMP), REGTMP
```

この命令は、`REGTMP`レジスタが指すアドレス（オフセット0）から8バイト（Quadword）のデータを読み込み、その値を再び`REGTMP`レジスタに書き込みます。一見すると無意味な自己代入のように見えますが、これはデバッグの目的で特定のレジスタ（この場合は`REGTMP`）の値を、そのレジスタが指すメモリ位置に保存されている値で上書きする、あるいは単にそのメモリ位置の値を読み出してレジスタにロードする操作です。

「不正な戻り」のデバッグにおいて、この命令が挿入される位置が重要です。`addstacksplit`関数内で、スタック分割処理の直後、または関数からの戻り処理の直前にこの命令が挿入されることで、デバッガは特定の時点での`REGTMP`レジスタの内容（例えば、戻りアドレスやスタックポインタのコピーなど）を検査できるようになります。もし`REGTMP`が戻りアドレスを保持している場合、この命令は戻りアドレスが指すメモリの内容を`REGTMP`にロードし直すことになります。これにより、デバッガは、関数が実際にどこに戻ろうとしているのか、あるいは戻りアドレスが指すメモリの内容が期待通りであるかを確認するためのフックを得ることができます。

この種のデバッグコードは、特にコンパイラやリンカが生成する低レベルのアセンブリコードのバグを追跡する際に役立ちます。例えば、スタックが破損している場合、戻りアドレスが指すメモリの内容が予期しない値になっている可能性があり、この命令によってその異常を捕捉できるかもしれません。

## コアとなるコードの解説

追加されたコードブロックは、`if(0)`で囲まれているため、デフォルトでは無効です。この条件を`if(1)`に変更することで、デバッグコードが有効になります。

コードの各行は、Plan 9アセンブリ命令を生成するためのリンカ内部の構造体とフィールドを設定しています。

*   `q = ctxt->arch->prg();`: 新しいプログラム命令（`Prog`構造体）を割り当てます。`prg()`は、リンカがアセンブリ命令を表現するために使用する内部データ構造を生成する関数です。
*   `q->as = AMOVD;`: 生成する命令のオペレーションコード（opcode）を`AMOVD`に設定します。これは「Move Doubleword/Quadword」命令を意味します。
*   `q->lineno = p->lineno;`: 生成される命令のソースコード行番号を、直前の命令`p`の行番号に設定します。これにより、デバッグ時に命令がどのソースコードに対応するかを追跡しやすくなります。
*   `q->from.type = D_OREG;`: 命令のソースオペランドのタイプを「オフセット付きレジスタ間接」に設定します。
*   `q->from.offset = 0;`: ソースオペランドのオフセットを`0`に設定します。
*   `q->from.reg = REGTMP;`: ソースオペランドのベースレジスタを`REGTMP`に設定します。これにより、ソースオペランドは`0(REGTMP)`、つまり`REGTMP`レジスタが指すアドレスのメモリ内容を意味します。
*   `q->to.type = D_REG;`: 命令のデスティネーションオペランドのタイプを「レジスタ直接」に設定します。
*   `q->to.reg = REGTMP;`: デスティネーションオペランドのレジスタを`REGTMP`に設定します。これにより、デスティネーションオペランドは`REGTMP`レジスタそのものを意味します。
*   `q->link = p->link;`: 新しい命令`q`を、既存の命令リストの適切な位置に挿入します。具体的には、`p`の次の命令が`q`の次になるようにリンクを設定します。
*   `p->link = q;`: `p`の次の命令を`q`に設定します。
*   `p = q;`: 現在の命令ポインタ`p`を新しく追加した命令`q`に進めます。

この一連の操作により、リンカは`addstacksplit`が生成する命令シーケンスの中に、`AMOVD 0(REGTMP), REGTMP`というアセンブリ命令を挿入します。この命令は、`REGTMP`レジスタが保持するアドレスからデータを読み込み、そのデータを再び`REGTMP`レジスタに書き戻すという動作をします。これは、デバッグ時に特定のレジスタの内容や、そのレジスタが指すメモリの内容を検査するためのブレークポイントや監視ポイントを設定するのに役立ちます。特に、関数からの戻り直前のスタックやレジスタの状態を検証する際に有用です。

## 技術的詳細

このコミットで追加されたデバッグコードは、`src/liblink/obj9.c`内の`addstacksplit`関数に挿入されています。`addstacksplit`は、Goの関数プロローグ（関数の開始時に実行されるコード）の一部として、スタックの分割（stack split）処理に関連する命令を生成する役割を担っています。スタック分割は、Goのgoroutineが小さなスタックで開始し、必要に応じて自動的に拡張されるメカニズムです。

追加されたコードブロックは、`if(0)`という条件で囲まれているため、デフォルトではコンパイル時に削除され、最終的なバイナリには含まれません。しかし、この`if(0)`を`if(1)`に変更して再コンパイルすることで、デバッグコードを有効にできます。

有効化された場合、このコードは以下のPlan 9アセンブリ命令を生成します（x86-64を想定した場合）：

```assembly
AMOVD 0(REGTMP), REGTMP
```

この命令は、`REGTMP`レジスタが指すアドレス（オフセット0）から8バイト（Quadword）のデータを読み込み、その値を再び`REGTMP`レジスタに書き込みます。一見すると無意味な自己代入のように見えますが、これはデバッグの目的で特定のレジスタ（この場合は`REGTMP`）の値を、そのレジスタが指すメモリ位置に保存されている値で上書きする、あるいは単にそのメモリ位置の値を読み出してレジスタにロードする操作です。

「不正な戻り」のデバッグにおいて、この命令が挿入される位置が重要です。`addstacksplit`関数内で、スタック分割処理の直後、または関数からの戻り処理の直前にこの命令が挿入されることで、デバッガは特定の時点での`REGTMP`レジスタの内容（例えば、戻りアドレスやスタックポインタのコピーなど）を検査できるようになります。もし`REGTMP`が戻りアドレスを保持している場合、この命令は戻りアドレスが指すメモリの内容を`REGTMP`にロードし直すことになります。これにより、デバッガは、関数が実際にどこに戻ろうとしているのか、あるいは戻りアドレスが指すメモリの内容が期待通りであるかを確認するためのフックを得ることができます。

この種のデバッグコードは、特にコンパイラやリンカが生成する低レベルのアセンブリコードのバグを追跡する際に役立ちます。例えば、スタックが破損している場合、戻りアドレスが指すメモリの内容が予期しない値になっている可能性があり、この命令によってその異常を捕捉できるかもしれません。

## コアとなるコードの解説

追加されたコードブロックは、`if(0)`で囲まれているため、デフォルトでは無効です。この条件を`if(1)`に変更することで、デバッグコードが有効になります。

コードの各行は、Plan 9アセンブリ命令を生成するためのリンカ内部の構造体とフィールドを設定しています。

*   `q = ctxt->arch->prg();`: 新しいプログラム命令（`Prog`構造体）を割り当てます。`prg()`は、リンカがアセンブリ命令を表現するために使用する内部データ構造を生成する関数です。
*   `q->as = AMOVD;`: 生成する命令のオペレーションコード（opcode）を`AMOVD`に設定します。これは「Move Doubleword/Quadword」命令を意味します。
*   `q->lineno = p->lineno;`: 生成される命令のソースコード行番号を、直前の命令`p`の行番号に設定します。これにより、デバッグ時に命令がどのソースコードに対応するかを追跡しやすくなります。
*   `q->from.type = D_OREG;`: 命令のソースオペランドのタイプを「オフセット付きレジスタ間接」に設定します。
*   `q->from.offset = 0;`: ソースオペランドのオフセットを`0`に設定します。
*   `q->from.reg = REGTMP;`: ソースオペランドのベースレジスタを`REGTMP`に設定します。これにより、ソースオペランドは`0(REGTMP)`、つまり`REGTMP`レジスタが指すアドレスのメモリ内容を意味します。
*   `q->to.type = D_REG;`: 命令のデスティネーションオペランドのタイプを「レジスタ直接」に設定します。
*   `q->to.reg = REGTMP;`: デスティネーションオペランドのレジスタを`REGTMP`に設定します。これにより、デスティネーションオペランドは`REGTMP`レジスタそのものを意味します。
*   `q->link = p->link;`: 新しい命令`q`を、既存の命令リストの適切な位置に挿入します。具体的には、`p`の次の命令が`q`の次になるようにリンクを設定します。
*   `p->link = q;`: `p`の次の命令を`q`に設定します。
*   `p = q;`: 現在の命令ポインタ`p`を新しく追加した命令`q`に進めます。

この一連の操作により、リンカは`addstacksplit`が生成する命令シーケンスの中に、`AMOVD 0(REGTMP), REGTMP`というアセンブリ命令を挿入します。この命令は、`REGTMP`レジスタが保持するアドレスからデータを読み込み、そのデータを再び`REGTMP`レジスタに書き戻すという動作をします。これは、デバッグ時に特定のレジスタの内容や、そのレジスタが指すメモリの内容を検査するためのブレークポイントや監視ポイントを設定するのに役立ちます。特に、関数からの戻り直前のスタックやレジスタの状態を検証する際に有用です。

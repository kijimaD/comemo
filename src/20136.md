# [インデックス 20136] ファイルの概要

Goランタイムにおける`onM`フレームのコピーを許可する変更。これにより、GCをトリガーするゴルーチンを含む、`onM`状態のゴルーチンのスタックコピー/シュリンクが可能になります。

## 変更の背景

このコミットは、Goランタイムのスタック管理メカニズム、特にゴルーチンのスタックコピーとシュリンク（縮小）に関する重要な改善を目的としています。Go 1.4（2014年12月リリース）では、それまでの「セグメントスタック」モデルから「連続スタック」（スタックコピー）モデルへの移行が行われました。セグメントスタックは、スタックが成長するたびに新しい小さなメモリセグメントを割り当ててリンクする方式でしたが、スタックの頻繁な成長と縮小がパフォーマンス上の問題を引き起こしていました。

新しい連続スタックモデルでは、スタックが不足しそうになると、ランタイムはより大きな連続したメモリブロックを割り当て、古いスタックの内容を新しい場所にコピーします。これにより、スタックの成長が効率的になり、特にスタックの縮小が「無料」でできるようになりました。

しかし、この新しいスタックコピーの仕組みには課題がありました。特に、OSスレッド（M）上でアクティブに実行されているゴルーチン（`onM`状態のゴルーチン）のスタックをコピーまたはシュリンクすることが困難でした。コミットメッセージが示唆するように、GC（ガベージコレクション）をトリガーするゴルーチンでさえ、この問題に直面していました。これは、`onM`状態のゴルーチンが、スタックコピーに必要な完全なGC情報（ガベージコレクタがポインタを正確に追跡するために必要なメタデータ）を持っていない場合があるためです。特に、アセンブリで書かれた低レベルのランタイム関数（例: `runtime·switchtoM`）のフレームは、このGC情報が不足していることが多く、スタックコピーの妨げとなっていました。

このコミットは、このような特定のケース、特に`runtime·switchtoM`のフレームを持つ`onM`ゴルーチンに対して、スタックコピーを特別に許可することで、この問題を解決しようとしています。これにより、Goランタイムのスタック管理の堅牢性と効率性が向上し、GCの動作にも良い影響を与えることが期待されます。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とスタック管理の背景知識が必要です。

1.  **Goの並行性モデル (GMPモデル)**:
    *   **G (Goroutine)**: Goの軽量な並行実行単位です。OSスレッドよりもはるかに軽量で、数百万個作成することも可能です。
    *   **M (Machine/OS Thread)**: 実際のOSスレッドを表します。Goのコードを実行する責任を持ちます。
    *   **P (Processor/Logical Processor)**: 論理プロセッサを表し、MがGoコードを実行するために必要なリソースです。Pはローカルな実行キューを持ち、MはPと関連付けられてゴルーチンを実行します。
    *   **onM**: ゴルーチンがM上でアクティブに実行されている状態を指します。

2.  **Goのスタック管理**:
    *   **動的なスタックサイズ**: Goのゴルーチンは、従来のOSスレッドのように固定された大きなスタックサイズを持つのではなく、小さな初期スタックサイズ（Go 1.4以降は2KB）で開始します。これにより、多数のゴルーチンを効率的に管理し、メモリ使用量を節約できます。
    *   **スタックの成長と縮小**: ゴルーチンのスタックが不足しそうになると、Goランタイムは自動的にスタックを成長させます。また、スタックの使用量が減少した場合は、ランタイムがスタックを縮小することもあります。
    *   **セグメントスタック (Go 1.3まで)**: スタックが成長すると、新しいセグメントが割り当てられ、既存のスタックにリンクされました。しかし、この方式は「ホットスプリット問題」を引き起こし、パフォーマンス上のオーバーヘッドがありました。
    *   **連続スタック (Go 1.4以降)**: スタックが成長する必要がある場合、ランタイムは新しい、より大きな連続したメモリブロックを割り当て、古いスタックの内容をそこにコピーします。これにより、スタックの成長と縮小がより効率的になりました。このコミットは、この連続スタックモデルへの移行期またはその直後の改善として位置づけられます。

3.  **GC情報 (Garbage Collection Information)**:
    *   Goのガベージコレクタは、ヒープ上のオブジェクトだけでなく、スタック上のポインタもスキャンして、到達可能なオブジェクトを特定します。
    *   スタック上のポインタを正確に識別するためには、各スタックフレームに「GC情報」または「ポインタマップ」と呼ばれるメタデータが必要です。これは、どのスタック上の値がポインタであり、どの値がそうでないかをコレクタに伝えます。
    *   アセンブリで書かれた関数など、一部の低レベルなランタイム関数は、このGC情報が不足している場合があります。

4.  **`runtime·switchtoM`**:
    *   これはGoランタイム内部の非常に低レベルな関数で、GoスケジューラがゴルーチンとOSスレッドの管理を行う際に使用されます。
    *   M（OSスレッド）が実行コンテキストを切り替える必要がある場合に呼び出されます。例えば、ゴルーチンのプリエンプション（横取り）、ブロッキングシステムコール、またはゴルーチンが自発的に実行を譲る場合（`runtime.Gosched()`）などに使用されます。
    *   この関数は、CPUレジスタ（プログラムカウンタやスタックポインタなど）やその他のゴルーチン固有のデータを保存・復元する複雑な処理を担います。コミットのコード変更から、この関数がアセンブリで書かれており、GC情報が不足していることが示唆されています。

## 技術的詳細

このコミットの核心は、Goランタイムがゴルーチンのスタックをコピーまたはシュリンクする際の、特定の「エッジケース」を処理することにあります。特に、`onM`状態のゴルーチン、つまりOSスレッド上で現在実行中のゴルーチンが対象です。

Go 1.4で導入された連続スタックモデルでは、スタックの成長が必要になった際に、現在のスタックの内容を新しい、より大きなメモリ領域にコピーします。このコピー操作は、スタック上のすべてのポインタを正確に更新する必要があります。そのためには、スタックフレーム内のどの値がポインタであるかをガベージコレクタが知るための「GC情報」（ポインタマップ）が不可欠です。

問題は、`runtime·switchtoM`のような一部の低レベルなランタイム関数がアセンブリで実装されており、通常のGo関数が持つような完全なGC情報を持っていない点にありました。このような関数がスタックフレームに含まれている場合、ランタイムはスタックコピーを安全に行うことができませんでした。コミットメッセージにある「Currently goroutines in onM can't be copied/shrunk (including the very goroutine that triggers GC)」という記述は、この問題を明確に示しています。GCをトリガーするゴルーチンでさえ、`onM`状態にあるためにスタックコピーができないという状況は、ランタイムの安定性と効率性にとって大きな障害となります。

このコミットは、`src/pkg/runtime/stack.c`内の`checkframecopy`関数と`adjustframe`関数に変更を加えることで、この問題を解決しています。

*   `checkframecopy`関数は、スタックフレームがコピー可能かどうかをチェックする際に、`runtime·switchtoM`のエントリポイントを持つフレームを特別扱いします。このフレームは、完全なGC情報がないにもかかわらず、コピーを許可されます。これは、`runtime·switchtoM`がスタックの最下部に位置する特殊なルーチンであり、その性質上、安全にコピーできると判断されたためです。
*   `adjustframe`関数は、スタックフレームを調整する際に、`runtime·main`だけでなく、`runtime·switchtoM`のエントリポイントを持つフレームも同様に特別扱いします。これは、これらのフレームがスタックの根元に近い特殊なフレームであり、通常のスタックフレームとは異なる処理が必要であることを示しています。

この変更により、`runtime·switchtoM`のフレームを含む`onM`ゴルーチンでもスタックコピーが安全に行えるようになり、Goランタイムのスタック管理の柔軟性と堅牢性が向上しました。これにより、GCの動作が阻害されることなく、より多くのシナリオでスタックの効率的な管理が可能になります。

## コアとなるコードの解説

このコミットは、Goランタイムのスタック管理において、特に`onM`状態のゴルーチンのスタックコピーを可能にするための変更です。

1.  **`runtime·switchtoM`の宣言追加**:
    ```c
    void runtime·switchtoM(void(*)(void));
    ```
    `runtime·switchtoM`関数が、スタックフレームのチェックと調整を行う`stack.c`内で認識されるように、そのプロトタイプが追加されました。これは、この関数がGoランタイムの内部で重要な役割を果たすことを示しています。

2.  **`checkframecopy`関数における`runtime·switchtoM`の特別扱い**:
    `checkframecopy`関数は、スタックフレームがコピー可能であるかどうかを判断するロジックを含んでいます。
    ```c
    	if(f->entry == (uintptr)runtime·switchtoM) {
    		// A special routine at the bottom of stack of a goroutine that does onM call.
    		// We will allow it to be copied even though we don't
    		// have full GC info for it (because it is written in asm).
    		cinfo->frames++;
    		return true;
    	}
    ```
    この追加されたコードブロックは、現在のスタックフレームの`entry`ポイントが`runtime·switchtoM`である場合に適用されます。
    *   コメントが示すように、`runtime·switchtoM`は「`onM`呼び出しを行うゴルーチンのスタックの最下部にある特別なルーチン」です。
    *   重要なのは、「完全なGC情報がないにもかかわらず（アセンブリで書かれているため）、コピーを許可する」という点です。これは、`runtime·switchtoM`がスタックの根元に位置し、その性質上、GC情報がなくても安全にコピーできるというランタイムの判断に基づいています。
    *   `return true;`によって、このフレームはコピー可能であるとマークされ、スタックコピー処理が続行できるようになります。

3.  **`adjustframe`関数における`runtime·switchtoM`の考慮**:
    `adjustframe`関数は、スタックフレームを新しいスタックアドレスに合わせて調整する役割を担います。
    ```c
    	if(f->entry == (uintptr)runtime·main ||
    		f->entry == (uintptr)runtime·switchtoM)
    		return true;
    ```
    以前は`runtime·main`のエントリポイントを持つフレームのみが特別扱いされていましたが、この変更により`runtime·switchtoM`のエントリポイントを持つフレームも同様に特別扱いされるようになりました。これは、これらのフレームがスタックの最下部に位置する特殊なフレームであり、通常のスタックフレームとは異なる調整ロジックが必要であることを示しています。`return true;`は、これらのフレームに対しては特別な調整が不要であるか、あるいは別のメカニズムで処理されることを意味します。

これらの変更により、Goランタイムは`runtime·switchtoM`のようなアセンブリで書かれた低レベルの関数を含むスタックフレームでも、安全かつ効率的にスタックコピーを実行できるようになりました。これにより、`onM`状態のゴルーチンがGCをトリガーする際など、スタックのコピーやシュリンクが必要なシナリオで、ランタイムがより堅牢に動作するようになります。

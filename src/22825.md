## 変更の背景

このコミットは、以前のコミット `https://go-review.googlesource.com/#/c/7504/` によって導入された、システムコール終了時のトレーシングに関する問題を修正するために行われました。元のコミット `7504` の具体的な内容は直接参照できませんが、このコミットのメッセージから、システムコール終了イベント（`EvGoSysExit`）の記録方法に変更が加えられ、その結果としてトレーシングの不正確さや整合性の問題が発生したと推測されます。

特に問題となっていたのは、システムコールから復帰したゴルーチンが、すぐにP（プロセッサ）を取得できない場合に、`EvGoSysExit` イベントが正確なタイムスタンプで記録されないことでした。Goのランタイムトレーシングコードは、ライトバリアなどの処理を行う際にPを必要とすることがあり、Pがない状態でこれらの処理を実行すると問題が発生する可能性があります。このため、システムコール終了イベントの記録が遅延される必要がありましたが、その際のタイムスタンプの扱いが不適切であったと考えられます。

このコミットは、システムコール終了時の正確なタイムスタンプを、Pの有無に関わらず記録し、Pが利用可能になった時点で安全にイベントを発行することで、この問題を解決しようとしています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoランタイムの概念とトレーシングの仕組みに関する知識が必要です。

*   **Goランタイムトレーシング (Go Runtime Tracing)**:
    Goランタイムは、プログラムの実行中に発生する様々なイベント（ゴルーチンのスケジューリング、ガベージコレクション、システムコール、ネットワークI/Oなど）を詳細に記録する機能を提供します。この記録されたデータはトレースファイルとして出力され、`go tool trace` コマンドなどのツールを使って視覚的に解析することで、プログラムのパフォーマンス特性やボトルネックを特定するのに役立ちます。トレーシングは、Goプログラムの内部動作を深く理解するための強力なツールです。

*   **Goroutine (G)**:
    Go言語における並行処理の基本単位です。OSのスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行することも可能です。Goランタイムのスケジューラによって管理され、M（OSスレッド）上で実行されます。

*   **Processor (P)**:
    Goスケジューラがゴルーチンを実行するために必要な論理プロセッサです。PはM（OSスレッド）にアタッチされ、G（ゴルーチン）を実行するためのコンテキストを提供します。Pの数は通常、CPUのコア数に設定され、同時に実行できるゴルーチンの数を制限します。Pは、スケジューラがゴルーチンをMにディスパッチする際に重要な役割を果たします。

*   **Machine (M)**:
    OSのスレッドに相当します。MはPを保持し、そのP上でゴルーチンを実行します。システムコールを実行する際など、MがOSにブロックされる場合、そのMはPを解放し、他のMがそのPを利用できるようにします。

*   **Goroutineの状態**:
    ゴルーチンは、そのライフサイクルにおいて様々な状態を遷移します。このコミットに関連する主要な状態は以下の通りです。
    *   `gRunnable`: ゴルーチンが実行可能であり、P上で実行されるのを待っているか、現在実行中であることを示します。
    *   `gWaiting`: ゴルーチンが何らかのイベント（ネットワークI/O、タイマー、チャネル操作、ロックの取得など）を待っており、一時的に実行を停止している状態です。
    *   `gInSyscall`: ゴルーチンがシステムコールを実行中であることを示します。この状態では、MはOSスレッドとしてシステムコールを実行しており、Pは他のゴルーチンに利用される可能性があります。

*   **システムコール (Syscall)**:
    プログラムがオペレーティングシステム（OS）のサービス（ファイルI/O、ネットワーク通信、メモリ管理など）を直接要求するためのメカニズムです。GoプログラムがOSと対話する際には、システムコールが使用されます。システムコール中は、Goランタイムのスケジューラはゴルーチンを一時的にブロックし、OSが処理を完了するのを待ちます。

*   **`cputicks()`**:
    CPUのティック数を返す関数で、非常に高分解能な時間測定に用いられます。Goランタイムトレーシングでは、イベントの正確な発生時刻を記録するために使用されます。

*   **ライトバリア (Write Barrier)**:
    Goのガベージコレクタ（GC）がオブジェクトのポインタを更新する際に、GCの整合性を保つために実行される特別な処理です。ライトバリアは、GCがオブジェクトグラフを正確にトラバースし、到達可能なオブジェクトを誤って回収しないようにするために重要です。Pがない状態でライトバリアを実行すると、ランタイムの整合性が損なわれる可能性があるため、Pの可用性が重要になります。

## 技術的詳細

このコミットは、主に以下の3つのファイルにわたって変更を加えています。

1.  **`src/runtime/proc1.go`**: システムコールからの復帰処理 (`exitsyscall` 関数) におけるトレーシングイベントの発行ロジックが変更されました。
    *   以前は、システムコール終了イベント (`traceGoSysExit`) を直接呼び出そうとしていましたが、コメントアウトされており、「GCが実行されている可能性があり、このコードはライトバリアを呼び出す可能性がある」という問題が指摘されていました。つまり、Pがない状態で `traceGoSysExit` を呼び出すと、ランタイムの整合性が損なわれるリスクがあったのです。
    *   この問題を解決するため、`exitsyscall` 関数内に `exitTicks = cputicks()` が導入されました。これは、システムコールが実際に終了した正確な時刻を、Pの有無に関わらず記録するためのものです。
    *   `traceGoSysExit` の呼び出しは、`exitTicks` が0でない（つまり、トレーシングが有効で、時刻が記録された）場合に、`systemstack` 内で遅延して行われるようになりました。`systemstack` は、現在のゴルーチンがシステムスタックに切り替わり、Pを保持した状態で実行されることを保証します。これにより、ライトバリアの問題を回避しつつ、安全にトレースイベントを発行できるようになりました。
    *   `_g_.m.locks++` と `_g_.m.locks--` が追加され、`traceGoSysExit` が呼び出されるまでの間、ゴルーチンが不整合な状態で再スケジュールされないように、Mのロックを一時的に保持するようになりました。これは、`GoStart` イベントが発行された後に `GoSysExit` が発行されないという、トレースの不整合を防ぐためです。
    *   `exitsyscallfast` 関数内の `traceGoSysExit()` 呼び出しも、`traceGoSysExit(0)` に変更されました。これは、`traceGoSysExit` 関数がタイムスタンプを引数として受け取るように変更されたためです。

2.  **`src/runtime/trace.go`**: トレーシングイベントの定義と、`traceGoSysExit` 関数のシグネチャが変更されました。
    *   `traceEvGoSysExit` イベントの定義が、以前の `syscall exit [timestamp, goroutine id]` から `syscall exit [timestamp, goroutine id, real timestamp]` に拡張されました。これにより、イベントが実際に発生した「リアルタイムスタンプ」という追加情報を持つことができるようになりました。これは、`proc1.go` での遅延記録に対応するための重要な変更です。
    *   `traceGoSysExit` 関数のシグネチャが `func traceGoSysExit()` から `func traceGoSysExit(ts int64)` に変更され、システムコール終了時のタイムスタンプを受け取るようになりました。この `ts` 引数は、`proc1.go` で記録された `exitTicks` が渡されます。
    *   `traceEvent` の呼び出しも、新しい `ts` 引数を `uint64(ts)/traceTickDiv` として追加し、イベントにリアルタイムスタンプを記録するように変更されました。

3.  **`src/internal/trace/parser.go`**: トレースファイルを解析するパーサーが、新しい `EvGoSysExit` イベントの形式に対応するように修正されました。
    *   `parseEvents` 関数内で `EvGoSysExit` イベントの処理が追加されました。イベントの引数 `e.Args[1]` にリアルタイムスタンプが格納されている場合（0でない場合）、その値でイベントのメインタイムスタンプ `e.Ts` を上書きします。これにより、遅延して発行された `EvGoSysExit` イベントであっても、トレース解析時に正確な時間軸でイベントを配置できるようになります。
    *   `postProcessTrace` 関数内で、`EvGoInSyscall` イベントの処理が修正されました。以前は意図的に空でしたが、ゴルーチンの状態が `gRunnable` でない場合にエラーを返すチェックが追加され、状態を `gWaiting` に設定するように変更されました。これは、システムコールに入ったゴルーチンが `gWaiting` 状態になることを期待しているためです。
    *   同様に、`EvGoSysExit` イベントの処理も修正されました。以前は `g.state != gRunnable` をチェックしていましたが、`g.state != gWaiting` をチェックするように変更されました。システムコールから戻ったゴルーチンは `gWaiting` 状態であるべきという前提に基づいています。また、`g.state = gRunnable` が追加され、システムコール終了後にゴルーチンが実行可能状態に戻ることを明示しています。これらの状態チェックの厳格化は、トレースの整合性を高め、不正な状態遷移を早期に検出するためのものです。
    *   `EvGoSysExit` の `EventDescriptions` に `ts` 引数が追加され、パーサーがイベントの引数を正しく解釈できるようにしました。
    *   デバッグ用の `Print` 関数が追加されました。

これらの変更により、Goランタイムのトレーシングは、システムコール終了イベントをより正確かつ堅牢に記録できるようになり、トレースデータの信頼性が向上しました。

## コアとなるコードの解説

*   **`src/runtime/proc1.go` の `exitsyscall` 関数における変更**:
    この変更の核心は、システムコール終了イベントの記録を、P（プロセッサ）の可用性から切り離し、正確なタイムスタンプを保証することにあります。
    1.  **`exitTicks = cputicks()` の導入**: システムコールが実際に終了した瞬間を、`cputicks()` を使って `exitTicks` に記録します。この時点では、ゴルーチンはまだPを再取得していない可能性があり、ライトバリアを伴う処理（`traceGoSysExit` の呼び出しなど）は安全に実行できません。`exitTicks` は、イベントの「リアルタイムスタンプ」として機能します。
    2.  **`traceGoSysExit` の遅延呼び出し**: 以前は直接呼び出されていた `traceGoSysExit` はコメントアウトされ、代わりに `exitTicks` が記録された場合にのみ、`systemstack` 内で遅延して呼び出されるようになりました。`systemstack` は、現在のゴルーチンがシステムスタックに切り替わり、Pを保持した状態で実行されることを保証するため、ライトバリアの問題を回避し、安全にトレースイベントを発行できます。
    3.  **`_g_.m.locks` を用いたロック**: `_g_.m.locks++` と `_g_.m.locks--` の追加は、`exitTicks` が記録されてから `traceGoSysExit` が実際に呼び出されるまでの短い期間、ゴルーチンが不整合な状態で再スケジュールされるのを防ぐためのものです。これにより、トレースデータにおける `GoStart` イベントと `GoSysExit` イベントの順序の整合性が保たれます。

*   **`src/runtime/trace.go` の変更**:
    このファイルでの変更は、`EvGoSysExit` イベントのデータ構造を拡張し、より詳細な情報（リアルタイムスタンプ）を記録できるようにした点にあります。
    1.  **`traceEvGoSysExit` の定義変更**: イベントが `real timestamp` という追加の引数を持つように変更されました。これにより、イベントが実際に発生した時刻と、トレースに記録された時刻との間にずれがある場合でも、正確な情報を保持できるようになります。
    2.  **`traceGoSysExit(ts int64)` へのシグネチャ変更**: `traceGoSysExit` 関数が `ts` (タイムスタンプ) を引数として受け取るようになりました。この `ts` は `proc1.go` で記録された `exitTicks` であり、イベントの「リアルタイムスタンプ」として `traceEvent` に渡されます。

*   **`src/internal/trace/parser.go` の変更**:
    このファイルでの変更は、新しい形式の `EvGoSysExit` イベントを正しく解釈し、トレースの整合性を維持するためのものです。
    1.  **`EvGoSysExit` のタイムスタンプ上書きロジック**: `parseEvents` 関数内で、`EvGoSysExit` イベントの `e.Args[1]` にリアルタイムスタンプが格納されている場合、その値でイベントのメインタイムスタンプ `e.Ts` を上書きします。これは、`proc1.go` での遅延記録と連携し、トレース解析時にイベントを正確な時間軸で配置するために不可欠です。
    2.  **`EvGoInSyscall` および `EvGoSysExit` の状態チェックの厳格化**: `postProcessTrace` 関数内で、`EvGoInSyscall` および `EvGoSysExit` イベント処理時のゴルーチンの状態チェックがより厳格になりました。
        *   `EvGoInSyscall` では、ゴルーチンがシステムコールに入る前に `gRunnable` 状態であること、そしてシステムコールに入った後は `gWaiting` 状態になることを期待しています。
        *   `EvGoSysExit` では、システムコールから戻ったゴルーチンが `gWaiting` 状態であること、そしてシステムコール終了後に `gRunnable` 状態に戻ることを期待しています。
        これらのチェックは、トレースの整合性を高め、ランタイムの状態遷移が期待通りに行われているかを検証するために重要です。不正な状態遷移は、トレースデータの信頼性を損なう可能性があるため、早期に検出することが望ましいです。

これらの変更は、Goランタイムトレーシングの正確性と堅牢性を向上させ、より信頼性の高いプロファイリングとデバッグを可能にするための重要なステップです。

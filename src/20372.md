# [インデックス 20372] ファイルの概要

このコミットは、Goランタイムにおける`onM`関数の呼び出しに関する重要な修正を含んでいます。具体的には、シグナルハンドリング用のスタック（`gsignal`スタック）から`onM`が呼び出されることを禁止し、プログラムのクラッシュを防ぐための変更が導入されました。

変更されたファイルは以下の通りです。

*   `src/pkg/runtime/asm_386.s`: 386アーキテクチャ向けのアセンブリコード
*   `src/pkg/runtime/asm_amd64.s`: AMD64アーキテクチャ向けのアセンブリコード
*   `src/pkg/runtime/asm_amd64p32.s`: AMD64 (32-bit pointers)アーキテクチャ向けのアセンブリコード
*   `src/pkg/runtime/asm_arm.s`: ARMアーキテクチャ向けのアセンブリコード
*   `src/pkg/runtime/stubs.go`: ランタイムのスタブ関数定義

## コミット

```
runtime: reject onM calls from gsignal stack

The implementation and use patterns of onM assume
that they run on either the m->curg or m->g0 stack.

Calling onM from m->gsignal has two problems:

(1) When not on g0, onM switches to g0 and then "back" to curg.
If we didn't start at curg, bad things happen.

(2) The use of scalararg/ptrarg to pass C arguments and results
assumes that there is only one onM call at a time.
If a gsignal starts running, it may have interrupted the
setup/teardown of the args for an onM on the curg or g0 stack.
Using scalararg/ptrarg itself would smash those.

We can fix (1) by remembering what g was running before the switch.

We can fix (2) by requiring that uses of onM that might happen
on a signal handling stack must save the old scalararg/ptrarg
and restore them after the call, instead of zeroing them.
The only sane way to do this is to introduce a separate
onM_signalsafe that omits the signal check, and then if you
see a call to onM_signalsafe you know the surrounding code
must preserve the old scalararg/ptrarg values.
(The implementation would be that onM_signalsafe just calls
fn if on the signal stack or else jumps to onM. It's not necessary
to have two whole copies of the function.)

(2) is not a problem if the caller and callee are both Go and
a closure is used instead of the scalararg/ptrarg slots.

For now, I think we can avoid calling onM from code executing
on gsignal stacks, so just reject it.

In the long term, (2) goes away (as do the scalararg/ptrarg slots)
once everything is in Go, and at that point fixing (1) would be
trivial and maybe worth doing just for regularity.

## 変更の背景

Goランタイムの`onM`関数は、特定の処理をM（Machine、OSスレッド）のスタック上で実行するために設計されています。この関数は、通常、現在のゴルーチン（`m->curg`）のスタック、またはスケジューラゴルーチン（`m->g0`）のスタックから呼び出されることを前提としていました。

しかし、シグナルハンドリング中に使用される特別なスタックである`gsignal`スタックから`onM`が呼び出されると、以下の2つの深刻な問題が発生する可能性がありました。

1.  **スタック切り替えの不整合**: `onM`は、`g0`スタック上にいない場合、一度`g0`スタックに切り替えてから、元の`curg`スタックに戻るという動作をします。もし`onM`が`curg`スタックではない`gsignal`スタックから呼び出された場合、`curg`に戻ろうとすると予期せぬ動作やクラッシュを引き起こす可能性がありました。
2.  **引数渡しメカニズムの破壊**: `onM`は、C言語で書かれた関数に引数を渡すために`scalararg`と`ptrarg`という一時的なスロットを使用します。これらのスロットは、一度に一つの`onM`呼び出しのみが使用することを前提としています。もし`gsignal`が実行中に割り込み、別の`onM`呼び出しの引数設定や後処理を中断した場合、`gsignal`スタックからの`onM`呼び出しがこれらのスロットを上書き（"smash"）してしまい、データの破損や不正な動作につながる可能性がありました。

これらの問題を回避するため、このコミットでは、`gsignal`スタックからの`onM`呼び出しを一時的に禁止し、検出した場合はプログラムをクラッシュさせるという、より安全なアプローチが採用されました。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の概念を理解しておく必要があります。

### GoランタイムのM, G, Pモデル

Goランタイムは、ゴルーチン（G）、論理プロセッサ（P）、OSスレッド（M）という3つの主要な抽象化を用いて並行性を管理します。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。数KB程度のスタックを持ち、数百万個作成することも可能です。Goプログラムの並行処理の基本となります。
*   **P (Processor)**: 論理プロセッサを表します。GをMにディスパッチするためのコンテキストを提供し、GoスケジューラがGをPに割り当て、PがGをM上で実行します。Pの数は通常、CPUコア数に制限されます。
*   **M (Machine)**: OSスレッドを表します。Gのコードを実行する実際のOSスレッドです。MはPと関連付けられ、Pが管理するGを実行します。Mは、システムコールやCgo呼び出しなど、Goランタイムの外部でブロックされる可能性がある場合、Pから切り離されることがあります。

### `onM`関数

`onM`関数は、Goランタイム内部で使用される特殊な関数で、GoのコードからOSスレッド（M）のスタック上で直接C言語の関数などを実行するために使われます。これは、Goのスケジューラやガベージコレクタなど、OSスレッドのコンテキストで特定の低レベル操作を実行する必要がある場合に利用されます。`onM`は、呼び出し元のゴルーチンスタックから`g0`スタック（Mに紐づく特別なスタック）に切り替えて処理を実行し、完了後に元のスタックに戻るという動作をします。

### `gsignal`スタック

Goランタイムは、OSからのシグナル（例: SIGSEGV、SIGINTなど）を処理するために、各M（OSスレッド）に専用のシグナルハンドリングスタックである`gsignal`スタックを持っています。これは、通常のゴルーチンスタックや`g0`スタックがシグナル発生時に破損している可能性があるため、安全にシグナルハンドラを実行するための隔離された環境を提供します。シグナルハンドラは、非常に限られた操作しか実行できず、通常のGoコードの実行とは異なる制約があります。

### `scalararg`と`ptrarg`

これらは、GoランタイムのM構造体内に存在する一時的なフィールドで、C言語で書かれたランタイム関数に引数を渡したり、戻り値を受け取ったりするために使用されます。`scalararg`はポインタ以外のスカラー値（整数など）を、`ptrarg`はポインタ値を渡すために使われます。これらはグローバルなレジスタやメモリ領域のように機能し、`onM`のような関数呼び出しの前後で設定・クリアされることが期待されます。

## 技術的詳細

このコミットは、`onM`関数が`gsignal`スタックから呼び出された場合に発生する2つの主要な問題を解決するために導入されました。

**問題1: スタック切り替えの不整合**

`onM`の設計は、呼び出しが`m->curg`（現在の実行中のゴルーチン）または`m->g0`（スケジューラゴルーチン）のスタックから行われることを前提としています。`onM`は、`g0`スタック上にいない場合、まず`g0`スタックに切り替えてから、指定された関数を実行し、その後元の`curg`スタックに戻ります。

しかし、`gsignal`スタックは`curg`スタックとは異なる特殊なスタックです。もし`onM`が`gsignal`スタックから呼び出された場合、`onM`が「元のスタックに戻る」と判断する場所が`curg`スタックになってしまい、`gsignal`スタックのコンテキストが失われるか、不正なスタックポインタで実行が再開される可能性があります。これは、プログラムのクラッシュや未定義の動作につながります。

**問題2: `scalararg`/`ptrarg`の破壊**

`scalararg`と`ptrarg`は、GoランタイムとC言語で書かれた部分との間で引数や戻り値を一時的に受け渡すための共有メモリ領域です。これらのスロットは、一度に一つの`onM`呼び出しによってのみ使用されることが期待されます。

シグナルは非同期に発生し、任意の時点で実行中のコードを中断する可能性があります。もし、あるゴルーチン（`curg`または`g0`）が`onM`を呼び出し、その引数を`scalararg`/`ptrarg`に設定している最中にシグナルが発生し、そのシグナルハンドラ内でさらに`onM`が呼び出された場合、シグナルハンドラ内の`onM`が`scalararg`/`ptrarg`を上書きしてしまいます。これにより、中断された元の`onM`呼び出しが不正な引数で再開され、ランタイムの内部状態が破壊される可能性があります。

**検討された解決策と採用されたアプローチ**

コミットメッセージでは、これらの問題に対するいくつかの潜在的な解決策が議論されています。

*   **問題1の解決策**: `onM`がスタックを切り替える前に、どのゴルーチンが実行されていたかを記憶しておくことで解決できる可能性があります。
*   **問題2の解決策**: シグナルハンドリングスタックから`onM`が呼び出される可能性がある場合、呼び出し元が`scalararg`/`ptrarg`の古い値を保存し、`onM`呼び出し後に復元することを義務付ける方法が考えられました。これは、`onM_signalsafe`のような別の関数を導入し、その関数がシグナルスタック上で実行された場合は直接関数を呼び出し、それ以外の場合は通常の`onM`にジャンプするという形で実現できます。これにより、`onM_signalsafe`の呼び出し元は、`scalararg`/`ptrarg`の保存と復元を行う責任を負うことになります。

しかし、これらの解決策は複雑であり、特に`scalararg`/`ptrarg`の問題は、呼び出し元と呼び出し先が両方Go言語で書かれており、クロージャが引数渡しに使われるようになれば、将来的には自然に解消されると述べられています。

**採用されたアプローチ**:
現時点では、`gsignal`スタックから`onM`を呼び出す必要がないと判断されたため、最もシンプルで安全な解決策として、`gsignal`スタックからの`onM`呼び出しを**拒否**する（つまり、検出したらプログラムをクラッシュさせる）というアプローチが採用されました。これにより、未定義の動作やランタイムの破損を防ぎ、将来的に`scalararg`/`ptrarg`がGo言語のクロージャに置き換えられることで問題2が解消されれば、問題1の修正もより単純になると考えられています。

この変更は、Goランタイムの堅牢性を高め、特にシグナルハンドリングのようなクリティカルなパスでの予期せぬ動作を防ぐことを目的としています。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、Goランタイムのアセンブリコード（`asm_*.s`ファイル）と`stubs.go`ファイルにあります。

**アセンブリコード (`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `asm_arm.s`) の変更:**

各アーキテクチャのアセンブリコードにある`runtime·onM`関数の実装に、現在のゴルーチンが`g0`スタックでも`curg`スタックでもない場合に、`runtime·badonm`関数を呼び出すチェックが追加されました。

変更前:
```assembly
TEXT runtime·onM(SB), NOSPLIT, $0-4
    MOVL    fn+0(FP), DI    // DI = fn
    get_tls(CX)
    MOVL    g(CX), AX    // AX = g
    MOVL    g_m(AX), BX    // BX = m
    MOVL    m_g0(BX), DX    // DX = g0
    CMPL    AX, DX
    JEQ    onm
    // ... (oncurgへのジャンプ、または元のコメント)
```

変更後 (例: `asm_amd64.s`):
```assembly
TEXT runtime·onM(SB), NOSPLIT, $0-8
    MOVQ    fn+0(FP), DI    // DI = fn
    get_tls(CX)
    MOVQ    g(CX), AX    // AX = g
    MOVQ    g_m(AX), BX    // BX = m

    MOVQ    m_g0(BX), DX    // DX = g0
    CMPQ    AX, DX
    JEQ    onm

    MOVQ    m_curg(BX), BP
    CMPQ    AX, BP
    JEQ    oncurg

    // Not g0, not curg. Must be gsignal, but that's not allowed.
    // Hide call from linker nosplit analysis.
    MOVQ    $runtime·badonm(SB), AX
    CALL    AX

oncurg:
    // save our state in g->sched.  Pretend to
    // be switchtoM if the G stack is scanned.
    MOVQ    $runtime·switchtoM(SB), BP
    // ...
```

この変更により、`onM`が呼び出された際に、現在のゴルーチン（`AX`レジスタに格納されている`g`）が`m->g0`（`DX`レジスタ）でも`m->curg`（`BP`レジスタ）でもない場合、それは`gsignal`スタックであると判断され、`runtime·badonm`が呼び出されます。

**`src/pkg/runtime/stubs.go` の変更:**

`onM`関数のドキュメントが更新され、`gsignal`スタックから呼び出された場合にプログラムがクラッシュすることが明記されました。また、`badonm`関数が追加されました。

変更前:
```go
// in asm_*.s
func mcall(func(*g))
func onM(fn func())
```

変更後:
```go
// mcall switches from the g to the g0 stack and invokes fn(g),
// ... (mcallの新しい詳細なコメント)
//go:noescape
func mcall(fn func(*g))

// onM switches from the g to the g0 stack and invokes fn().
// ... (onMの新しい詳細なコメント)
// If onM is called from a gsignal stack, it crashes the program.
// The implication is that functions used in signal handlers must
// not use onM.
// ... (onMの新しい詳細なコメントと、onMsignalに関する議論)
//go:noescape
func onM(fn func())

func badonm() {
    gothrow("onM called from signal goroutine")
}
```

`badonm`関数は、`gothrow`を呼び出してパニックを発生させ、"onM called from signal goroutine"というメッセージを出力します。

## コアとなるコードの解説

### アセンブリコードの変更

各アーキテクチャのアセンブリコードにおける`runtime·onM`関数の変更は、以下のロジックを実装しています。

1.  **現在のゴルーチン (g) の取得**: `get_tls`マクロと`g(CX)`（または`g`レジスタ）を使って、現在実行中のゴルーチン（`g`）のポインタをレジスタ（例: `AX`）にロードします。
2.  **現在のM (m) の取得**: `g_m(AX)`を使って、`g`が関連付けられているM（OSスレッド）のポインタをレジスタ（例: `BX`）にロードします。
3.  **`g0`スタックとの比較**: `m_g0(BX)`を使ってMの`g0`スタックのポインタをレジスタ（例: `DX`）にロードし、現在の`g`が`g0`であるかどうかを比較します（`CMPL AX, DX`または`CMPQ AX, DX`）。もし`g0`であれば、通常の`onm`ラベルにジャンプして処理を続行します。
4.  **`curg`スタックとの比較**: `m_curg(BX)`を使ってMの`curg`スタックのポインタをレジスタ（例: `BP`）にロードし、現在の`g`が`curg`であるかどうかを比較します。もし`curg`であれば、`oncurg`ラベルにジャンプして処理を続行します。
5.  **`gsignal`スタックからの呼び出しの検出と拒否**: もし現在の`g`が`g0`でも`curg`でもない場合、それは`gsignal`スタックであると判断されます。この場合、`runtime·badonm`関数のアドレスをレジスタ（例: `AX`）にロードし、`CALL AX`命令を使ってその関数を呼び出します。この呼び出しは、リンカのnosplit解析から隠蔽するために、直接関数名ではなくレジスタ経由で行われます。`badonm`が呼び出されると、プログラムはクラッシュします。

このアセンブリレベルのチェックにより、`onM`が意図しない`gsignal`スタックから呼び出されることを厳密に防ぎ、ランタイムの整合性を保護しています。

### `stubs.go`の変更

`stubs.go`ファイルでは、`onM`関数のGo側の宣言にコメントが追加され、その動作、特に`gsignal`スタックからの呼び出しに対する挙動が明確に記述されました。

最も重要な追加は`badonm`関数です。
```go
func badonm() {
    gothrow("onM called from signal goroutine")
}
```
この関数は、アセンブリコードから呼び出されると、`gothrow`というランタイム内部関数を呼び出します。`gothrow`はGoのパニックメカニズムの低レベルな実装であり、指定された文字列メッセージ（"onM called from signal goroutine"）とともにプログラムを異常終了させます。これにより、開発者は`onM`が不正なコンテキストで呼び出されたことを即座に認識できます。

しかし、シグナルハンドリング中に使用される特別なスタックである`gsignal`スタックから`onM`が呼び出されると、以下の2つの深刻な問題が発生する可能性がありました。

1.  **スタック切り替えの不整合**: `onM`は、`g0`スタック上にいない場合、一度`g0`スタックに切り替えてから、元の`curg`スタックに戻るという動作をします。もし`onM`が`curg`スタックではない`gsignal`スタックから呼び出された場合、`curg`に戻ろうとすると予期せぬ動作やクラッシュを引き起こす可能性がありました。
2.  **引数渡しメカニズムの破壊**: `onM`は、C言語で書かれた関数に引数を渡すために`scalararg`と`ptrarg`という一時的なスロットを使用します。これらのスロットは、一度に一つの`onM`呼び出しのみが使用することを前提としています。もし`gsignal`が実行中に割り込み、別の`onM`呼び出しの引数設定や後処理を中断した場合、`gsignal`スタックからの`onM`呼び出しがこれらのスロットを上書き（"smash"）してしまい、データの破損や不正な動作につながる可能性がありました。

これらの問題を回避するため、このコミットでは、`gsignal`スタックからの`onM`呼び出しを一時的に禁止し、検出した場合はプログラムをクラッシュさせるという、より安全なアプローチが採用されました。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の概念を理解しておく必要があります。

### GoランタイムのM, G, Pモデル

Goランタイムは、ゴルーチン（G）、論理プロセッサ（P）、OSスレッド（M）という3つの主要な抽象化を用いて並行性を管理します。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。数KB程度のスタックを持ち、数百万個作成することも可能です。Goプログラムの並行処理の基本となります。
*   **P (Processor)**: 論理プロセッサを表します。GをMにディスパッチするためのコンテキストを提供し、GoスケジューラがGをPに割り当て、PがGをM上で実行します。Pの数は通常、CPUコア数に制限されます。
*   **M (Machine)**: OSスレッドを表します。Gのコードを実行する実際のOSスレッドです。MはPと関連付けられ、Pが管理するGを実行します。Mは、システムコールやCgo呼び出しなど、Goランタイムの外部でブロックされる可能性がある場合、Pから切り離されることがあります。

### `onM`関数

`onM`関数は、Goランタイム内部で使用される特殊な関数で、GoのコードからOSスレッド（M）のスタック上で直接C言語の関数などを実行するために使われます。これは、Goのスケジューラやガベージコレクタなど、OSスレッドのコンテキストで特定の低レベル操作を実行する必要がある場合に利用されます。`onM`は、呼び出し元のゴルーチンスタックから`g0`スタック（Mに紐づく特別なスタック）に切り替えて処理を実行し、完了後に元のスタックに戻るという動作をします。

### `gsignal`スタック

Goランタイムは、OSからのシグナル（例: SIGSEGV、SIGINTなど）を処理するために、各M（OSスレッド）に専用のシグナルハンドリングスタックである`gsignal`スタックを持っています。これは、通常のゴルーチンスタックや`g0`スタックがシグナル発生時に破損している可能性があるため、安全にシグナルハンドラを実行するための隔離された環境を提供します。シグナルハンドラは、非常に限られた操作しか実行できず、通常のGoコードの実行とは異なる制約があります。

### `scalararg`と`ptrarg`

これらは、GoランタイムのM構造体内に存在する一時的なフィールドで、C言語で書かれたランタイム関数に引数を渡したり、戻り値を受け取ったりするために使用されます。`scalararg`はポインタ以外のスカラー値（整数など）を、`ptrarg`はポインタ値を渡すために使われます。これらはグローバルなレジスタやメモリ領域のように機能し、`onM`のような関数呼び出しの前後で設定・クリアされることが期待されます。

## 技術的詳細

このコミットは、`onM`関数が`gsignal`スタックから呼び出された場合に発生する2つの主要な問題を解決するために導入されました。

**問題1: スタック切り替えの不整合**

`onM`の設計は、呼び出しが`m->curg`（現在の実行中のゴルーチン）または`m->g0`（スケジューラゴルーチン）のスタックから行われることを前提としています。`onM`は、`g0`スタック上にいない場合、まず`g0`スタックに切り替えてから、指定された関数を実行し、その後元の`curg`スタックに戻ります。

しかし、`gsignal`スタックは`curg`スタックとは異なる特殊なスタックです。もし`onM`が`gsignal`スタックから呼び出された場合、`onM`が「元のスタックに戻る」と判断する場所が`curg`スタックになってしまい、`gsignal`スタックのコンテキストが失われるか、不正なスタックポインタで実行が再開される可能性があります。これは、プログラムのクラッシュや未定義の動作につながります。

**問題2: `scalararg`/`ptrarg`の破壊**

`scalararg`と`ptrarg`は、GoランタイムとC言語で書かれた部分との間で引数や戻り値を一時的に受け渡すための共有メモリ領域です。これらのスロットは、一度に一つの`onM`呼び出しによってのみ使用されることが期待されます。

シグナルは非同期に発生し、任意の時点で実行中のコードを中断する可能性があります。もし、あるゴルーチン（`curg`または`g0`）が`onM`を呼び出し、その引数を`scalararg`/`ptrarg`に設定している最中にシグナルが発生し、そのシグナルハンドラ内でさらに`onM`が呼び出された場合、シグナルハンドラ内の`onM`が`scalararg`/`ptrarg`を上書きしてしまいます。これにより、中断された元の`onM`呼び出しが不正な引数で再開され、ランタイムの内部状態が破壊される可能性があります。

**検討された解決策と採用されたアプローチ**

コミットメッセージでは、これらの問題に対するいくつかの潜在的な解決策が議論されています。

*   **問題1の解決策**: `onM`がスタックを切り替える前に、どのゴルーチンが実行されていたかを記憶しておくことで解決できる可能性があります。
*   **問題2の解決策**: シグナルハンドリングスタックから`onM`が呼び出される可能性がある場合、呼び出し元が`scalararg`/`ptrarg`の古い値を保存し、`onM`呼び出し後に復元することを義務付ける方法が考えられました。これは、`onM_signalsafe`のような別の関数を導入し、その関数がシグナルスタック上で実行された場合は直接関数を呼び出し、それ以外の場合は通常の`onM`にジャンプするという形で実現できます。これにより、`onM_signalsafe`の呼び出し元は、`scalararg`/`ptrarg`の保存と復元を行う責任を負うことになります。

しかし、これらの解決策は複雑であり、特に`scalararg`/`ptrarg`の問題は、呼び出し元と呼び出し先が両方Go言語で書かれており、クロージャが引数渡しに使われるようになれば、将来的には自然に解消されると述べられています。

**採用されたアプローチ**:
現時点では、`gsignal`スタックから`onM`を呼び出す必要がないと判断されたため、最もシンプルで安全な解決策として、`gsignal`スタックからの`onM`呼び出しを**拒否**する（つまり、検出したらプログラムをクラッシュさせる）というアプローチが採用されました。これにより、未定義の動作やランタイムの破損を防ぎ、将来的に`scalararg`/`ptrarg`がGo言語のクロージャに置き換えられることで問題2が解消されれば、問題1の修正もより単純になると考えられています。

この変更は、Goランタイムの堅牢性を高め、特にシグナルハンドリングのようなクリティカルなパスでの予期せぬ動作を防ぐことを目的としています。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、Goランタイムのアセンブリコード（`asm_*.s`ファイル）と`stubs.go`ファイルにあります。

**アセンブリコード (`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `asm_arm.s`) の変更:**

各アーキテクチャのアセンブリコードにある`runtime·onM`関数の実装に、現在のゴルーチンが`g0`スタックでも`curg`スタックでもない場合に、`runtime·badonm`関数を呼び出すチェックが追加されました。

変更前:
```assembly
TEXT runtime·onM(SB), NOSPLIT, $0-4
    MOVL    fn+0(FP), DI    // DI = fn
    get_tls(CX)
    MOVL    g(CX), AX    // AX = g
    MOVL    g_m(AX), BX    // BX = m
    MOVL    m_g0(BX), DX    // DX = g0
    CMPL    AX, DX
    JEQ    onm
    // ... (oncurgへのジャンプ、または元のコメント)
```

変更後 (例: `asm_amd64.s`):
```assembly
TEXT runtime·onM(SB), NOSPLIT, $0-8
    MOVQ    fn+0(FP), DI    // DI = fn
    get_tls(CX)
    MOVQ    g(CX), AX    // AX = g
    MOVQ    g_m(AX), BX    // BX = m

    MOVQ    m_g0(BX), DX    // DX = g0
    CMPQ    AX, DX
    JEQ    onm

    MOVQ    m_curg(BX), BP
    CMPQ    AX, BP
    JEQ    oncurg

    // Not g0, not curg. Must be gsignal, but that's not allowed.
    // Hide call from linker nosplit analysis.
    MOVQ    $runtime·badonm(SB), AX
    CALL    AX

oncurg:
    // save our state in g->sched.  Pretend to
    // be switchtoM if the G stack is scanned.
    MOVQ    $runtime·switchtoM(SB), BP
    // ...
```

この変更により、`onM`が呼び出された際に、現在のゴルーチン（`AX`レジスタに格納されている`g`）が`m->g0`（`DX`レジスタ）でも`m->curg`（`BP`レジスタ）でもない場合、それは`gsignal`スタックであると判断され、`runtime·badonm`が呼び出されます。

**`src/pkg/runtime/stubs.go` の変更:**

`onM`関数のドキュメントが更新され、`gsignal`スタックから呼び出された場合にプログラムがクラッシュすることが明記されました。また、`badonm`関数が追加されました。

変更前:
```go
// in asm_*.s
func mcall(func(*g))
func onM(fn func())
```

変更後:
```go
// mcall switches from the g to the g0 stack and invokes fn(g),
// ... (mcallの新しい詳細なコメント)
//go:noescape
func mcall(fn func(*g))

// onM switches from the g to the g0 stack and invokes fn().
// ... (onMの新しい詳細なコメント)
// If onM is called from a gsignal stack, it crashes the program.
// The implication is that functions used in signal handlers must
// not use onM.
// ... (onMの新しい詳細なコメントと、onMsignalに関する議論)
//go:noescape
func onM(fn func())

func badonm() {
    gothrow("onM called from signal goroutine")
}
```

`badonm`関数は、`gothrow`を呼び出してパニックを発生させ、"onM called from signal goroutine"というメッセージを出力します。

## コアとなるコードの解説

### アセンブリコードの変更

各アーキテクチャのアセンブリコードにおける`runtime·onM`関数の変更は、以下のロジックを実装しています。

1.  **現在のゴルーチン (g) の取得**: `get_tls`マクロと`g(CX)`（または`g`レジスタ）を使って、現在実行中のゴルーチン（`g`）のポインタをレジスタ（例: `AX`）にロードします。
2.  **現在のM (m) の取得**: `g_m(AX)`を使って、`g`が関連付けられているM（OSスレッド）のポインタをレジスタ（例: `BX`）にロードします。
3.  **`g0`スタックとの比較**: `m_g0(BX)`を使ってMの`g0`スタックのポインタをレジスタ（例: `DX`）にロードし、現在の`g`が`g0`であるかどうかを比較します（`CMPL AX, DX`または`CMPQ AX, DX`）。もし`g0`であれば、通常の`onm`ラベルにジャンプして処理を続行します。
4.  **`curg`スタックとの比較**: `m_curg(BX)`を使ってMの`curg`スタックのポインタをレジスタ（例: `BP`）にロードし、現在の`g`が`curg`であるかどうかを比較します。もし`curg`であれば、`oncurg`ラベルにジャンプして処理を続行します。
5.  **`gsignal`スタックからの呼び出しの検出と拒否**: もし現在の`g`が`g0`でも`curg`でもない場合、それは`gsignal`スタックであると判断されます。この場合、`runtime·badonm`関数のアドレスをレジスタ（例: `AX`）にロードし、`CALL AX`命令を使ってその関数を呼び出します。この呼び出しは、リンカのnosplit解析から隠蔽するために、直接関数名ではなくレジスタ経由で行われます。`badonm`が呼び出されると、プログラムはクラッシュします。

このアセンブリレベルのチェックにより、`onM`が意図しない`gsignal`スタックから呼び出されることを厳密に防ぎ、ランタイムの整合性を保護しています。

### `stubs.go`の変更

`stubs.go`ファイルでは、`onM`関数のGo側の宣言にコメントが追加され、その動作、特に`gsignal`スタックからの呼び出しに対する挙動が明確に記述されました。

最も重要な追加は`badonm`関数です。
```go
func badonm() {
    gothrow("onM called from signal goroutine")
}
```
この関数は、アセンブリコードから呼び出されると、`gothrow`というランタイム内部関数を呼び出します。`gothrow`はGoのパニックメカニズムの低レベルな実装であり、指定された文字列メッセージ（"onM called from signal goroutine"）とともにプログラムを異常終了させます。これにより、開発者は`onM`が不正なコンテキストで呼び出されたことを即座に認識できます。

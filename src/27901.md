# [インデックス 27901] ファイルの概要

このコミットは、Go言語の標準ライブラリ `crypto/aes` パッケージにおけるAES暗号の実装方法を根本的に変更するものです。具体的には、アセンブリ言語で最適化された実装（主に`amd64`向け）と、純粋なGo言語で書かれた汎用実装との間の結合度を低減し、より柔軟で拡張性の高い構造を目指しています。

変更された主なファイルは以下の通りです。

*   `src/crypto/aes/aes_gcm.go`: AES-GCMモードの実装に関連するファイル。
*   `src/crypto/aes/aes_test.go`: AESパッケージのテストファイル。特にキー拡張のベンチマークが変更されています。
*   `src/crypto/aes/cipher.go`: AES暗号の主要なインターフェースとGo言語による汎用実装の基盤を提供するファイル。
*   `src/crypto/aes/cipher_amd64.go`: `amd64`アーキテクチャ向けのアセンブリ最適化されたAES実装を扱う新しいファイル。
*   `src/crypto/aes/cipher_asm.go`: 以前、アセンブリとGoの実装を切り替えるロジックを含んでいたファイルですが、このコミットで削除されました。
*   `src/crypto/aes/cipher_generic.go`: 純粋なGo言語による汎用AES実装のヘルパー関数を含むファイル。

## コミット

このコミットは、`crypto/aes`パッケージにおけるアセンブリ言語による最適化されたAES実装と、純粋なGo言語による実装の間の結合を解消することを目的としています。これにより、異なるアーキテクチャ（例: s390x）の特性に合わせたデータ構造の設計が可能になり、GCM以外のブロック暗号モード（CTRやCBCなど）のサポートも容易になります。また、キー拡張のベンチマークがGo言語実装をテストするように変更されています。

## 元コミット内容

```
crypto/aes: de-couple asm and go implementations

There is currently only one assembly implementation of AES
(amd64). While it is possible to fit other implementations to the
same pattern it complicates the code. For example s390x does not
use expanded keys, so having enc and dec in the aesCipher struct
is confusing.

By separating out the asm implementations we can more closely
match the data structures to the underlying implementation. This
also opens the door for AES implementations that support block
cipher modes other than GCM (e.g. CTR and CBC).

This commit changes BenchmarkExpandKey to test the go
implementation of key expansion. It might be better to have some
sort of 'initialisation' benchmark instead to cover the startup
costs of the assembly implementations (which might be doing
key expansion in a different way, or not at all).
```

## 変更の背景

この変更の主な背景には、`crypto/aes`パッケージにおけるAES実装の現状と将来的な拡張性に関する課題がありました。

1.  **アセンブリ実装の限定性:** 当時、Goの`crypto/aes`パッケージには`amd64`アーキテクチャ向けのアセンブリ言語によるAES実装しか存在しませんでした。他のアーキテクチャ（例: `s390x`）でもアセンブリ最適化を導入しようとすると、既存のコードパターンに無理に合わせる必要があり、コードが複雑化するという問題がありました。
2.  **データ構造の不整合:** 特に`s390x`のような一部のアーキテクチャでは、AESのキー拡張（`expanded keys`）を使用しない場合があります。しかし、既存の`aesCipher`構造体には暗号化（`enc`）と復号（`dec`）のための拡張キーが常に含まれており、これはキー拡張を使用しない実装にとっては混乱を招くものでした。データ構造が基盤となる実装と密接に一致していないことが問題視されていました。
3.  **ブロック暗号モードの拡張性:** 既存の設計では、AES-GCM（Galois/Counter Mode）以外のブロック暗号モード（例: CTR、CBC）をサポートすることが困難でした。アセンブリ実装とGo実装が密接に結合しているため、新しいモードを追加する際に、両方の実装にわたる変更が必要となり、複雑さが増していました。
4.  **ベンチマークの改善:** キー拡張のベンチマークが、アセンブリ実装の起動コストを適切に測定できていない可能性がありました。アセンブリ実装ではキー拡張の処理がGo実装とは異なる、あるいは全く行われない場合があるため、より適切な「初期化」ベンチマークが必要であるという認識がありました。

これらの課題を解決し、よりクリーンで、保守しやすく、将来の拡張に対応しやすいAES実装を提供するために、アセンブリ実装とGo実装の分離が決定されました。

## 前提知識の解説

### AES (Advanced Encryption Standard)

AESは、現代において最も広く利用されている対称鍵ブロック暗号の一つです。128ビットのブロックサイズを持ち、鍵長は128ビット、192ビット、256ビットのいずれかを選択できます。鍵長に応じて、暗号化・復号のラウンド数（10、12、14ラウンド）が異なります。AESはSPN（Substitution-Permutation Network）構造に基づいており、複数のラウンドでバイト置換（SubBytes）、行シフト（ShiftRows）、列混合（MixColumns）、鍵加算（AddRoundKey）といった操作を繰り返します。

### キー拡張 (Key Expansion)

AESでは、ユーザーが提供する秘密鍵（マスターキー）から、各ラウンドで使用される「ラウンドキー」を生成するプロセスが必要です。このプロセスをキー拡張と呼びます。キー拡張は、マスターキーを基に一連の数学的変換を行い、各ラウンドで必要なサイズのラウンドキーを生成します。このラウンドキーは、暗号化・復号の各ラウンドでデータとXORされることで、セキュリティを強化します。キー拡張は、暗号化・復号処理の前に一度だけ行われる初期化ステップです。

### アセンブリ言語実装とGo言語実装

*   **Go言語実装:** Go言語で書かれたコードは、クロスプラットフォームで動作し、可読性が高く、保守が容易です。しかし、CPUの特定の命令セット（例: AES-NI命令）を利用した最適化は直接行えません。
*   **アセンブリ言語実装:** アセンブリ言語で書かれたコードは、特定のCPUアーキテクチャ（例: `amd64`）の低レベルな命令（例: AES-NI命令）を直接利用できるため、非常に高いパフォーマンスを発揮します。AES-NIは、IntelおよびAMDプロセッサに搭載されているAES暗号化・復号をハードウェアレベルで高速化する命令セットです。しかし、アセンブリコードは特定のアーキテクチャに依存し、可読性が低く、移植性や保守が困難になるという欠点があります。

Goの`crypto`パッケージでは、パフォーマンスが重要な暗号処理において、可能な限りアセンブリ言語による最適化された実装（「asm」実装）を利用し、それが利用できない環境では純粋なGo言語による実装（「generic」実装）にフォールバックするパターンがよく見られます。

### ブロック暗号モード (Block Cipher Modes)

ブロック暗号は固定長のブロック（AESの場合は128ビット）を暗号化・復号しますが、実際のデータは通常、ブロックサイズよりも大きいか小さいです。そのため、ブロック暗号を連続したデータに適用するための「ブロック暗号モード」が定義されています。

*   **GCM (Galois/Counter Mode):** 認証付き暗号モードの一つで、データの機密性（暗号化）と完全性・認証（改ざん検知）の両方を提供します。並列処理が可能で高速なため、TLSなどのプロトコルで広く利用されています。
*   **CTR (Counter Mode):** ブロック暗号をストリーム暗号のように動作させるモードです。カウンタを暗号化し、その結果を平文とXORすることで暗号文を生成します。並列処理が可能で、エラー伝播が限定的です。認証機能は提供しません。
*   **CBC (Cipher Block Chaining Mode):** 各ブロックの暗号化が前のブロックの暗号文に依存するモードです。初期化ベクトル（IV）が必要です。認証機能は提供しません。

このコミットの背景には、GCM以外のCTRやCBCといったモードも将来的に効率的にサポートしたいという意図があります。

## 技術的詳細

このコミットの核心は、`crypto/aes`パッケージ内のAES実装のディスパッチ（どの実装を使用するかを決定するロジック）を再構築し、アセンブリ実装とGo実装の間の依存関係を解消することにあります。

### 1. `aesCipher`構造体の役割分担

以前は、`aesCipher`構造体がGo実装とアセンブリ実装の両方の基盤となっていました。このコミットでは、`aesCipher`は純粋なGo実装の基盤として残され、アセンブリ実装に特化した`aesCipherAsm`という新しい構造体が導入されました。

*   **`aesCipher` (Go実装用):**
    *   `enc`, `dec`フィールド（拡張キー）を持つ。
    *   `Encrypt`および`Decrypt`メソッドは、`encryptBlockGo`および`decryptBlockGo`という純粋なGo関数を明示的に呼び出すように変更されました。
    *   キー拡張も`expandKeyGo`を呼び出す`newCipherGeneric`関数によって行われます。

*   **`aesCipherAsm` (アセンブリ実装用):**
    *   `aesCipher`を埋め込みます。これにより、`aesCipher`のフィールド（`enc`, `dec`）を再利用しつつ、アセンブリ特有の動作をオーバーライドできます。
    *   `Encrypt`および`Decrypt`メソッドは、`encryptBlockAsm`および`decryptBlockAsm`というアセンブリ関数を呼び出すように実装されます。
    *   キー拡張も`expandKeyAsm`を呼び出すように実装されます。

### 2. `newCipher`関数のディスパッチロジックの変更

`cipher.go`の`NewCipher`関数は、AESブロック暗号のインスタンスを作成するエントリポイントです。この関数は、内部的に`newCipher`という関数を呼び出すように変更されました。

*   **`cipher_amd64.go`の導入:**
    *   `amd64`アーキテクチャ向けに`cipher_amd64.go`という新しいファイルが作成されました。このファイルには、`newCipher`関数が定義されています。
    *   この`newCipher`関数は、`hasAsm()`（アセンブリ実装が利用可能かチェックする関数）の結果に基づいて、`aesCipherAsm`のインスタンスを返すか、または`newCipherGeneric`（純粋なGo実装）を呼び出すかを決定します。
    *   これにより、アセンブリ実装の有無による分岐ロジックが`amd64`固有のファイルにカプセル化され、他のアーキテクチャの実装に影響を与えなくなりました。

*   **`cipher_generic.go`の変更:**
    *   `cipher_generic.go`にも`newCipher`関数が追加されましたが、こちらは常に`newCipherGeneric`を呼び出します。これは、アセンブリ実装が存在しない、または利用できないアーキテクチャ（例: `arm`, `s390x`など）でコンパイルされる際に使用されます。
    *   以前`cipher_generic.go`にあった`encryptBlock`, `decryptBlock`, `expandKey`といったディスパッチ関数は削除されました。これらの関数は、Go実装とアセンブリ実装のどちらを呼び出すかを決定する役割を担っていましたが、新しい構造では不要になりました。

### 3. `cipher_asm.go`の削除

以前は、`cipher_asm.go`が`amd64`向けのアセンブリ関数（`encryptBlockAsm`, `decryptBlockAsm`, `expandKeyAsm`）の宣言と、それらをGo実装と切り替える`encryptBlock`, `decryptBlock`, `expandKey`関数を含んでいました。このコミットにより、`cipher_asm.go`は削除され、その機能は`cipher_amd64.go`と`cipher.go`/`cipher_generic.go`に分散されました。

### 4. `aes_gcm.go`の変更

`aesCipherGCM`構造体は、GCMモードでAESを使用する際にアセンブリ最適化を利用するためのものです。この構造体は、以前は汎用的な`aesCipher`を埋め込んでいましたが、この変更により`aesCipherAsm`を埋め込むように変更されました。これにより、GCMモードでもアセンブリ最適化されたAESブロック暗号の機能が直接利用されるようになります。

### 5. ベンチマークの変更

`aes_test.go`の`BenchmarkExpand`関数は、キー拡張のパフォーマンスを測定するためのものです。このベンチマークは、以前は`expandKey`関数を呼び出していましたが、このコミットで`expandKeyGo`を呼び出すように変更されました。これにより、純粋なGo言語によるキー拡張の実装のパフォーマンスが直接測定されるようになります。コミットメッセージにもあるように、アセンブリ実装の起動コストを考慮した「初期化」ベンチマークの必要性が示唆されています。

これらの変更により、Goの`crypto/aes`パッケージは、アーキテクチャ固有のアセンブリ最適化と汎用Go実装をより明確に分離し、それぞれの実装が自身のデータ構造とロジックをより密接に管理できるようになりました。これにより、コードの複雑さが軽減され、将来的に新しいアーキテクチャやブロック暗号モードのサポートが容易になります。

```go
// Copyright 2012 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package aes

import (
	"crypto/cipher"
)

// defined in asm_amd64.s
func hasAsm() bool
func encryptBlockAsm(nr int, xk *uint32, dst, src *byte)
func decryptBlockAsm(nr int, xk *uint32, dst, src *byte)
func expandKeyAsm(nr int, key *byte, enc *uint32, dec *uint32)

type aesCipherAsm struct {
	aesCipher
}

var useAsm = hasAsm()

func newCipher(key []byte) (cipher.Block, error) {
	if !useAsm {
		return newCipherGeneric(key)
	}
	n := len(key) + 28
	c := aesCipherAsm{aesCipher{make([]uint32, n), make([]uint32, n)}}
	rounds := 10
	switch len(key) {
	case 128 / 8:
		rounds = 10
	case 192 / 8:
		rounds = 12
	case 256 / 8:
		rounds = 14
	}
	expandKeyAsm(rounds, &key[0], &c.enc[0], &c.dec[0])
	if hasGCMAsm() {
		return &aesCipherGCM{c}, nil
	}

	return &c, nil
}

func (c *aesCipherAsm) BlockSize() int { return BlockSize }

func (c *aesCipherAsm) Encrypt(dst, src []byte) {
	if len(src) < BlockSize {
		panic("crypto/aes: input not full block")
	}
	if len(dst) < BlockSize {
		panic("crypto/aes: output not full block")
	}
	encryptBlockAsm(len(c.enc)/4-1, &c.enc[0], &dst[0], &src[0])
}

func (c *aesCipherAsm) Decrypt(dst, src []byte) {
	if len(src) < BlockSize {
		panic("crypto/aes: input not full block")
	}
	if len(dst) < BlockSize {
		panic("crypto/aes: output not full block")
	}
	decryptBlockAsm(len(c.dec)/4-1, &c.dec[0], &dst[0], &src[0])
}
```

## コアとなるコードの解説

このコミットの主要な目的は、AES暗号のGo言語実装とアセンブリ言語実装を明確に分離し、それぞれの実装が独立して管理できるようにすることです。

1.  **`aesCipher`と`aesCipherAsm`の分離:**
    *   以前は、`aesCipher`がGo実装とアセンブリ実装の両方の基盤となっており、内部で`useAsm`フラグなどを用いて分岐していました。
    *   新しい設計では、`aesCipher`は純粋なGo実装のデータ構造とメソッドを保持します。
    *   `aesCipherAsm`は`aesCipher`を埋め込むことで、Go実装の基本的な構造を再利用しつつ、`Encrypt`や`Decrypt`といったコアな暗号操作をアセンブリ関数（`encryptBlockAsm`, `decryptBlockAsm`）でオーバーライドします。これにより、アセンブリ実装に特有のデータ構造やロジックをより自然に組み込むことが可能になります。特に、`s390x`のようにキー拡張が不要なアーキテクチャでは、`aesCipher`の`enc`/`dec`フィールドが混乱を招くという問題が解消されます。

2.  **`newCipher`によるディスパッチの抽象化:**
    *   `crypto/aes`パッケージのエントリポイントである`NewCipher`関数は、直接実装の詳細に踏み込むのではなく、`newCipher`という内部関数を呼び出すように変更されました。
    *   この`newCipher`関数は、ビルドタグ（`+build amd64`など）によって異なるファイルで定義されます。
        *   `cipher_amd64.go`では、`hasAsm()`関数でCPUがAES-NIなどのアセンブリ最適化をサポートしているかをチェックし、サポートしていれば`aesCipherAsm`のインスタンスを返します。サポートしていなければ`newCipherGeneric`を呼び出します。
        *   `cipher_generic.go`では、常に`newCipherGeneric`を呼び出し、純粋なGo実装を提供します。
    *   このメカニズムにより、`NewCipher`の呼び出し側は、どの実装が使われているかを意識することなく、最適なAES実装が自動的に選択されるようになります。また、アーキテクチャ固有のディスパッチロジックがそれぞれのファイルにカプセル化され、コード全体の見通しが良くなります。

3.  **`cipher_asm.go`の削除と機能の再配置:**
    *   以前の`cipher_asm.go`は、アセンブリ関数の宣言と、Go実装とアセンブリ実装を切り替えるためのラッパー関数を含んでいました。
    *   このコミットでは、このファイルが削除され、その役割は`cipher_amd64.go`（アセンブリ実装のディスパッチとラッパー）と`cipher.go`/`cipher_generic.go`（Go実装の直接呼び出し）に再分配されました。これにより、アセンブリ実装とGo実装の間の結合が完全に解消され、それぞれの実装がより独立した存在となりました。

4.  **ブロック暗号モードの拡張性向上:**
    *   アセンブリ実装とGo実装が分離されたことで、GCM以外のブロック暗号モード（CTR、CBCなど）を導入する際に、それぞれの実装に対してより柔軟なアプローチが可能になります。例えば、特定のモードに特化したアセンブリ最適化を導入したり、Go実装で新しいモードを容易に追加したりできるようになります。

これらの変更は、Goの`crypto/aes`パッケージの内部構造を改善し、パフォーマンス、保守性、および将来の拡張性を向上させるための重要なステップです。

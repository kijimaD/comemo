# [インデックス 19965] ファイルの概要

このコミットは、Goランタイムの`nacl/amd64p32`ビルドにおける問題を修正するものです。具体的には、Cコンパイラが匿名フィールド（unnamed fields）をサポートしていないことに起因するビルドエラーを解消します。

影響を受けるファイルは以下の2つです。

*   `src/pkg/runtime/defs_nacl_amd64p32.h`
*   `src/pkg/runtime/signal_nacl_amd64p32.h`

## コミット

このコミットは、Goランタイムの`nacl/amd64p32`ターゲットにおけるビルドエラーを修正します。問題は、Cコンパイラが構造体内の匿名フィールドを適切に処理できないことにありました。修正は、匿名フィールドに明示的な名前を付与し、それに応じて関連するマクロの参照を更新することで行われました。

## 変更の背景

この変更は、Goランタイムの`nacl/amd64p32`ターゲット向けビルドが失敗するという問題に対応するために行われました。根本的な原因は、Goランタイムの一部がC言語で記述されており、そのCコード内で使用されていた構造体定義に「匿名フィールド（unnamed fields）」が含まれていたことです。

特定のCコンパイラ（この場合は`nacl/amd64p32`ビルドで使用されるコンパイラ）は、C言語の標準では許可されていない、または特定のコンパイラ拡張としてのみサポートされる匿名フィールドの構文をサポートしていませんでした。これにより、コンパイル時にエラーが発生し、ビルドが中断していました。

Goはクロスプラットフォーム対応を重視しており、様々なOSやアーキテクチャで動作するように設計されています。そのため、特定のターゲット環境（この場合はNative Clientの`amd64p32`）でのビルドが失敗することは、Goのポータビリティ目標に反します。このコミットは、このビルド問題を解決し、`nacl/amd64p32`ターゲットでのGoランタイムのコンパイルを可能にすることを目的としています。

## 前提知識の解説

### Native Client (NaCl)

Google Native Client (NaCl) は、ウェブブラウザ内でコンパイルされたCおよびC++コードを安全かつ効率的に実行するためのサンドボックス技術でした。これにより、ウェブアプリケーションはネイティブコードのパフォーマンスを活用しつつ、セキュリティ上のリスクを低減することが可能でした。NaClは、特定のCPUアーキテクチャ（x86、ARM、MIPSなど）に依存する形で提供されていました。

### amd64p32アーキテクチャ

`amd64p32`は、64ビット命令セットを使用しながらも、ポインタと`int`/`uint`型が32ビットであるという特徴を持つアーキテクチャです。これは、標準の`amd64`（64ビットポインタ）と比較して、メモリフットプリントを削減することを目的としていました。特に、メモリ使用量が重要な組み込みシステムや、特定のサンドボックス環境（NaClなど）で利用されることがありました。Goはかつて`nacl`を`GOOS`（Go Operating System）ターゲットとしてサポートしており、`amd64p32`はその`GOARCH`（Go Architecture）の一つでした。ただし、Go 1.14以降、`nacl`のサポートは終了しており、それに伴い`amd64p32`も削除されています。

### C言語における匿名フィールド（Unnamed Fields）

C言語の構造体や共用体において、フィールドに名前を付けずに別の構造体や共用体を埋め込む構文を「匿名フィールド」と呼びます。これは、C11標準で導入された機能であり、それ以前のC標準ではサポートされていませんでした。

例:
```c
struct Outer {
    int a;
    struct { // 匿名構造体
        int b;
        int c;
    }; // フィールド名がない
};
```
この場合、`struct Outer`のインスタンス`o`から`b`や`c`にアクセスする際に、`o.b`や`o.c`のように直接アクセスできます。もし匿名構造体に名前が付けられていた場合（例: `struct Inner inner_field;`）、`o.inner_field.b`のようにアクセスする必要がありました。

匿名フィールドはコードの簡潔さを向上させることがありますが、古いCコンパイラや、特定のコンパイラがC11標準のこの機能を完全にサポートしていない場合、コンパイルエラーの原因となることがあります。GoランタイムのCコードは、様々なCコンパイラでコンパイルされる可能性があるため、このような標準外または新しい標準の機能に依存すると、互換性の問題が発生することがあります。

## 技術的詳細

このコミットで修正された問題は、`src/pkg/runtime/defs_nacl_amd64p32.h`ファイル内の`ExcContext`構造体定義に起因していました。元のコードでは、以下のように共用体（union）が匿名フィールドとして定義されていました。

```c
struct ExcContext
{
 	union {
 		ExcRegs386	regs;
 		ExcRegsAmd64	regs64;
 	}; // ここが匿名フィールド
};
```

この`union`は、`ExcRegs386`と`ExcRegsAmd64`という2つの異なるレジスタセット構造体を保持するためのもので、コンテキストに応じてどちらか一方を使用することを意図していました。Goランタイムは、32ビットと64ビットのレジスタセットを切り替えるために、この共用体を利用していました。

しかし、`nacl/amd64p32`ビルドで使用されるCコンパイラは、この匿名共用体の構文をサポートしていませんでした。その結果、コンパイル時に「unnamed union/struct is not supported」のようなエラーが発生し、ビルドが失敗していました。

この問題を解決するために、コミットでは匿名共用体に明示的に`regs`という名前を付与しました。

```c
struct ExcContext
{
 	union {
 		ExcRegs386	regs;
 		ExcRegsAmd64	regs64;
 	} regs; // ここに 'regs' という名前が付与された
};
```

これにより、共用体はもはや匿名ではなくなり、Cコンパイラが正しく解析できるようになりました。

この変更に伴い、`ExcContext`構造体のメンバーへのアクセス方法も変更する必要がありました。元のコードでは、匿名フィールドであったため、共用体のメンバー（`regs`または`regs64`）に直接アクセスできていました。例えば、`SIG_REGS`マクロでは`((ExcContext*)(ctxt))->regs64`のようにアクセスしていました。

しかし、共用体に`regs`という名前が付与されたため、アクセスパスは`((ExcContext*)(ctxt))->regs.regs64`のように、新しく追加されたフィールド名`regs`を介して行う必要が生じました。この変更は、`src/pkg/runtime/signal_nacl_amd64p32.h`ファイル内の`SIG_REGS`マクロに適用されました。

この修正により、`nacl/amd64p32`ターゲットでのGoランタイムのビルドが正常に完了するようになり、Goのクロスプラットフォーム対応が維持されました。

## コアとなるコードの解説

### `src/pkg/runtime/defs_nacl_amd64p32.h` の変更

このファイルでは、`ExcContext`構造体の定義が変更されました。
元のコードでは、`union`が匿名で定義されていました。これは、C11標準で導入された機能であり、一部のCコンパイラ（特に古いものや、特定のプラットフォーム向けにカスタマイズされたもの）ではサポートされていませんでした。

```c
 	union {
 		ExcRegs386	regs;
 		ExcRegsAmd64	regs64;
 	}; // 匿名共用体
```

この変更により、この`union`に`regs`という明示的な名前が与えられました。

```c
 	union {
 		ExcRegs386	regs;
 		ExcRegsAmd64	regs64;
 	} regs; // 'regs' という名前が付与された共用体
```

これにより、Cコンパイラは共用体を正しく認識し、コンパイルエラーが解消されます。この変更は、構造体のメモリレイアウトには影響を与えませんが、共用体内のメンバーにアクセスするための構文に影響を与えます。

### `src/pkg/runtime/signal_nacl_amd64p32.h` の変更

このファイルでは、`SIG_REGS`マクロの定義が変更されました。このマクロは、`ExcContext`構造体からレジスタ情報を取得するために使用されていました。

元の定義では、`ExcContext`内の匿名共用体のメンバーに直接アクセスしていました。

```c
#define SIG_REGS(ctxt) (((ExcContext*)(ctxt))->regs64)
```

`ExcContext`構造体内の共用体に`regs`という名前が付与されたため、`regs64`メンバーにアクセスするには、まず`regs`共用体を介してアクセスする必要があります。したがって、マクロの定義は以下のように変更されました。

```c
#define SIG_REGS(ctxt) (((ExcContext*)(ctxt))->regs.regs64)
```

この変更により、`SIG_REGS`マクロは新しい構造体定義と互換性を持つようになり、レジスタ情報への正しいアクセスが保証されます。この修正は、Goランタイムがシグナルハンドリングやコンテキスト切り替えを行う際に、正しいレジスタ状態を読み取れるようにするために不可欠です。

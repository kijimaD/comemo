## 元コミット内容

Goランタイムにおいて、強制ガベージコレクション (GC) を行うヘルパーゴルーチンとの間で発生しうる競合状態を修正します。また、このヘルパーゴルーチンに適切な関数名を与えることで、スタックトレースにおける可読性を向上させます。

## 変更の背景

Goランタイムは、自動的なメモリ管理のためにガベージコレクタ (GC) を内蔵しています。通常、GCはランタイムが決定したタイミングで自動的に実行されますが、`runtime.GC()` のような関数を呼び出すことで明示的にGCを強制実行することも可能です。また、ランタイム内部には、一定期間GCが実行されていない場合に強制的にGCをトリガーするメカニズムが存在します。このメカニズムは `sysmon` (system monitor) ゴルーチンによって監視されており、`forcegc` ヘルパーゴルーチンを起動することでGCを強制します。

このコミットが行われる前は、`sysmon` が `forcegc.g` (強制GCヘルパーゴルーチンを表す `g` 構造体へのポインタ) を参照する際に、その `g` がまだ完全に初期化されていない、あるいは別の状態にある可能性があり、これが競合状態を引き起こす可能性がありました。具体的には、`sysmon` が `forcegc.g` を `injectglist` (実行可能なゴルーチンリストに追加する関数) に渡そうとした際に、`forcegc.g` が `nil` である可能性が考慮されていませんでした。これは、`forcegc` ヘルパーゴルーチンが起動された直後で、まだ `getg()` を呼び出して自身の `g` 構造体を取得し、`forcegc.g` に設定する前のタイミングで `sysmon` が動作した場合に発生しえます。

また、元のコードでは `forcegc` ヘルパーゴルーチンが匿名関数として定義されていたため、スタックトレースにその関数名が表示されず、デバッグが困難になるという問題がありました。

## 前提知識の解説

*   **Goランタイム**: Goプログラムの実行を管理する低レベルのシステム。スケジューラ、ガベージコレクタ、メモリ管理などが含まれます。
*   **ゴルーチン (Goroutine)**: Goにおける軽量な並行実行単位。OSのスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行することも可能です。
*   **`g` 構造体**: Goランタイム内部で各ゴルーチンを表すデータ構造。ゴルーチンのスタック、状態、スケジューリング情報などが含まれます。
*   **`sysmon` (System Monitor)**: Goランタイムの重要なシステムゴルーチンの一つ。バックグラウンドで動作し、ネットワークポーリング、タイマーの実行、GCの強制実行、アイドル状態のP (Processor) の解放など、様々なランタイムのハウスキーピングタスクを担当します。
*   **ガベージコレクション (GC)**: プログラムが不要になったメモリを自動的に解放するプロセス。GoのGCは並行・世代別・三色マーク＆スイープ方式を採用しています。
*   **`forcegc`**: Goランタイムが特定の条件（例: 長期間GCが実行されていない場合）でGCを強制的にトリガーするための内部メカニズム。
*   **競合状態 (Race Condition)**: 複数の並行プロセスやスレッドが共有リソースにアクセスする際に、そのアクセス順序によって結果が非決定的に変わってしまう状態。予期せぬバグの原因となります。
*   **`lock` と `unlock`**: 共有リソースへのアクセスを同期するためのミューテックス操作。競合状態を防ぐために使用されます。
*   **`goparkunlock`**: ゴルーチンを一時停止 (park) させ、指定されたロックを解放するランタイム関数。他のゴルーチンがロックを取得し、停止中のゴルーチンを再開 (inject) するまで待機します。
*   **`injectglist`**: 停止中のゴルーチンを実行可能なゴルーチンリストに追加し、スケジューラによって再開されるようにするランタイム関数。
*   **匿名関数**: 関数リテラルとも呼ばれ、名前を持たない関数。Goではクロージャとしてよく利用されます。

## 技術的詳細

このコミットは、主に以下の2つの側面でGoランタイムの堅牢性とデバッグ可能性を向上させています。

1.  **`forcegc` ヘルパーゴルーチンとの競合状態の回避**:
    `src/pkg/runtime/proc.c` の `sysmon` 関数内で、`forcegc` ヘルパーゴルーチンを再開するロジックに修正が加えられました。
    元のコードでは、`sysmon` が `forcegc.lock` を取得した後、無条件に `forcegc.g` を `injectglist` に渡していました。しかし、`forcegc` ヘルパーゴルーチンが起動された直後で、まだ `forcegc.g = getg()` が実行されていない場合、`forcegc.g` は `nil` のままです。この状態で `injectglist(nil)` を呼び出すと、ランタイムがパニックを起こすか、未定義の動作を引き起こす可能性がありました。

    修正後のコードでは、`injectglist(runtime·forcegc.g)` を呼び出す前に `if(runtime·forcegc.g != nil)` というチェックが追加されました。これにより、`forcegc.g` が `nil` でないことを確認してからゴルーチンを再開するようになり、競合状態が回避されます。コメント `// Goroutine may be started but has not initialized g yet.` が追加され、この問題の背景が明確に示されています。

2.  **`gc helper` の関数名の明確化**:
    `src/pkg/runtime/proc.go` において、`init()` 関数内で匿名関数として定義されていた `forcegc` ヘルパーゴルーチンが、`forcegchelper()` という名前付きの関数として分離されました。
    元のコード:
    ```go
    func init() {
        go func() {
            // ... forcegc logic ...
        }()
    }
    ```
    修正後のコード:
    ```go
    func init() {
        go forcegchelper()
    }

    func forcegchelper() {
        // ... forcegc logic ...
    }
    ```
    この変更により、`forcegc` ヘルパーゴルーチンがスタックトレースに表示される際に、`forcegchelper` という具体的な関数名が示されるようになります。これにより、デバッグ時にどのゴルーチンがGCを強制実行しているのか、そのスタックトレースがどこから来ているのかを容易に特定できるようになり、ランタイムの挙動の理解や問題の診断が格段に容易になります。

## コアとなるコードの解説

### `src/pkg/runtime/proc.c` の変更

`sysmon` 関数は、Goランタイムのバックグラウンドで動作し、様々なシステムタスクを処理します。その中には、一定期間GCが実行されていない場合に `forcegc` ヘルパーゴルーチンを再開してGCを強制実行するロジックが含まれています。

変更前は、`sysmon` が `forcegc.lock` を取得した後、`runtime·forcegc.g` を直接 `injectglist` に渡していました。しかし、`forcegc` ヘルパーゴルーチンが `init()` 関数内で `go forcegchelper()` として起動された直後、`forcegchelper` 関数内の `forcegc.g = getg()` が実行される前に `sysmon` が動作するタイミングが存在します。この短い期間では `runtime·forcegc.g` はまだ `nil` のままです。

追加された `if(runtime·forcegc.g != nil)` チェックは、この競合状態を解決します。`injectglist` を呼び出す前に `runtime·forcegc.g` が有効なゴルーチンポインタであることを確認することで、`nil` ポインタのデリファレンスや不正なゴルーチン操作を防ぎ、ランタイムの安定性を向上させています。

### `src/pkg/runtime/proc.go` の変更

このファイルでは、`forcegc` ヘルパーゴルーチンの定義方法が変更されました。

変更前は、`init()` 関数内で匿名関数として `forcegc` ヘルパーゴルーチンが起動されていました。匿名関数はデバッグ時にスタックトレース上で識別しにくいという欠点があります。例えば、スタックトレースには単に「goroutine」と表示されるか、あるいはその匿名関数が定義されているファイルと行番号しか表示されないため、そのゴルーチンの具体的な役割を把握するのが困難でした。

変更後は、匿名関数が `forcegchelper()` という名前付きの関数として抽出されました。そして、`init()` 関数からは `go forcegchelper()` と、この名前付き関数を起動するように変更されています。このシンプルなリファクタリングにより、`forcegc` ヘルパーゴルーチンがスタックトレースに現れる際に `forcegchelper` という明確な名前が表示されるようになります。これにより、ランタイムの内部動作をデバッグする際に、どのゴルーチンがGCの強制実行を担当しているのかを一目で理解できるようになり、デバッグ効率が大幅に向上します。

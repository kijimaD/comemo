# [インデックス 26377] ファイルの概要

このコミットは、Go言語のコマンドラインツール `go` の `go run` サブコマンドが、`internal` ディレクトリのパッケージに対する可視性ルールを正しく尊重するように修正するものです。具体的には、`go run` で実行される単一のGoファイルが、そのファイル自身が属するパッケージの `internal` ディレクトリ内のパッケージをインポートできる一方で、その外部にある `internal` パッケージをインポートしようとした場合にはエラーとなるように挙動が変更されました。

## 元コミット内容

Issue #12217 を解決。

## 変更の背景

Go言語には、パッケージの内部実装を外部に公開しないためのメカニズムとして `internal` ディレクトリがあります。`internal` ディレクトリ内のパッケージは、その `internal` ディレクトリの親ディレクトリと同じモジュールパスを持つパッケージからのみインポートが許可されます。例えば、`foo/internal/bar` というパッケージは `foo` パッケージ内からのみインポート可能で、`baz` パッケージからはインポートできません。

しかし、このコミット以前の `go run` コマンドは、単一のGoファイルを直接実行する際に、この `internal` パッケージの可視性ルールを正しく適用していませんでした。具体的には、`go run` は実行対象のGoファイルを「メインパッケージ」として扱い、そのパッケージが `internal` パッケージをインポートする際に、本来であれば許可されないはずのインポートも通してしまう、あるいは逆に許可されるべきインポートを拒否してしまうといった不整合がありました。

この問題は Issue #12217 で報告されており、`go run` が `internal` パッケージのルールを正しく解釈し、開発者が意図しない形で内部パッケージが利用されることを防ぐために、この修正が導入されました。

## 前提知識の解説

### Go Modulesとパッケージの可視性

Go言語のコードは「パッケージ」という単位で構成されます。関連する機能は一つのパッケージにまとめられ、他のパッケージからインポートして利用されます。Go 1.11以降はGo Modulesが導入され、依存関係管理がより体系化されましたが、このコミットがなされた2016年時点ではまだGOPATHベースのワークスペースが主流でした。しかし、`internal` パッケージの概念はGOPATH時代から存在し、Go Modulesにおいてもそのルールは引き継がれています。

### `internal` パッケージ

Go 1.4で導入された `internal` パッケージは、パッケージの内部実装をカプセル化するための機能です。`internal` という名前のディレクトリの下に配置されたパッケージは、その `internal` ディレクトリの**直近の親ディレクトリ**に属するパッケージからのみインポートが許可されます。

例:
- `github.com/user/project/foo/internal/bar` というパッケージがある場合、
- `github.com/user/project/foo` パッケージからは `bar` をインポートできます。
- `github.com/user/project/baz` パッケージからは `bar` をインポートできません。
- `github.com/user/project/foo/cmd/mytool` のようなサブパッケージからも、`foo` の一部とみなされるためインポート可能です。

このルールは、ライブラリの作者が意図しないAPIの利用を防ぎ、内部構造の変更が外部に影響を与えないようにするために非常に重要です。

### `go run` コマンド

`go run` コマンドは、一つまたは複数のGoソースファイルをコンパイルし、すぐに実行するためのコマンドです。通常、`main` パッケージを持つ単一の実行可能ファイルを一時的にビルドして実行する際に使用されます。開発中のスクリプトや簡単なテストコードを実行するのに便利です。

`go run main.go` のように実行すると、`main.go` が属するディレクトリが一時的に「メインパッケージ」として扱われ、そのコンテキストで依存関係が解決されます。この「メインパッケージ」のコンテキストが `internal` パッケージの可視性ルールにどのように影響するかが、このコミットの焦点となっています。

## 技術的詳細

このコミットの技術的な核心は、`go run` コマンドが単一のGoファイルを処理する際に、`internal` パッケージの可視性チェックを正しく行うように `go/build` パッケージのロジックを調整した点にあります。

Goのビルドシステムは、パッケージの依存関係を解決し、`internal` パッケージの可視性ルールを適用する際に、現在のパッケージがどの「ルート」パッケージ（またはモジュール）に属しているかを判断する必要があります。`internal` パッケージのルールは、インポート元のパッケージが `internal` パッケージの親ディレクトリと同じインポートパスを持つ場合にのみ許可されます。

`go run` は、通常、ファイルシステム上の任意の場所にある単一の `.go` ファイルをコンパイルして実行します。このとき、`go run` はそのファイルを一時的に「メインパッケージ」として扱います。この「メインパッケージ」のコンテキストが `internal` パッケージの可視性チェックにおいて、`internal` パッケージの親パッケージとして正しく認識される必要がありました。

変更点を見ると、`src/cmd/go/build.go` 内の `goFilesPackage` 関数に `stk.push("main")` と `stk.pop()` が追加されています。
`stk` は `build` パッケージ内で使用されるスタックのようなもので、パッケージのロード中に現在のコンテキスト（どのパッケージがどのパッケージをインポートしようとしているか）を追跡するために使われます。

- `stk.push("main")`: `go run` が処理する単一のGoファイルを「メインパッケージ」としてロードする前に、スタックに「main」というマーカーをプッシュします。これにより、`internal` パッケージの可視性チェックロジックが、この「メインパッケージ」を `internal` パッケージの親として正しく認識できるようになります。
- `pkg.load(&stk, bp, err)`: 実際のパッケージロードと依存関係解決が行われます。このプロセス中に `internal` パッケージの可視性チェックが実行されます。
- `stk.pop()`: パッケージロードが完了した後、スタックから「main」マーカーをポップします。

この変更により、`go run` で実行されるファイルが、そのファイル自身が属するパッケージの `internal` ディレクトリ内のパッケージをインポートすることは許可され、それ以外の `internal` パッケージのインポートは拒否されるようになります。これは、`go build` や `go install` といった他のコマンドでの `internal` パッケージの挙動と一貫性を持たせるための重要な修正です。

## コアとなるコードの解説

`src/cmd/go/build.go` の変更は非常に小さいですが、その影響は大きいです。
`goFilesPackage` 関数は、`go run` コマンドが引数として受け取ったGoファイルをパッケージとしてロードする際に呼び出されます。

1.  `stk.push("main")`:
    `stk` は `go/build` パッケージ内部で使われる `importStack` 型の変数で、パッケージのインポートパスを追跡するためのスタックです。`internal` パッケージの可視性ルールをチェックする際、このスタックのトップにある要素（つまり、現在インポートを行おうとしているパッケージ）と `internal` パッケージの親パッケージのパスを比較します。
    `go run` が単一のファイルを処理する場合、そのファイルは一時的に「メインパッケージ」として扱われます。この `push("main")` は、この「メインパッケージ」のコンテキストをスタックに明示的に追加することで、`internal` パッケージのチェックロジックが、この「メインパッケージ」を `internal` パッケージの親として正しく認識できるようにします。

2.  `pkg.load(&stk, bp, err)`:
    ここで実際のパッケージのロードと依存関係の解決が行われます。この処理の中で、インポートされる各パッケージ（特に `internal` パッケージ）に対して可視性チェックが実行されます。`stk` に「main」がプッシュされていることで、`go run` のコンテキストが正しく伝わり、`internal` パッケージのルールが適切に適用されます。

3.  `stk.pop()`:
    パッケージのロードが完了したら、プッシュした「main」マーカーをスタックから取り除きます。これにより、スタックの状態がクリーンアップされ、後続の処理に影響を与えないようにします。

この修正により、`go run` は `go build` や `go install` と同様に、`internal` パッケージの可視性ルールを厳密に適用するようになり、Go言語のパッケージ設計原則との一貫性が保たれます。

# [インデックス 26301] ファイルの概要

このコミットは、Go言語の標準ライブラリ`net`パッケージにおける、不正な形式のドメイン名に対するエラー報告の一貫性を確保しようとした以前のコミット（`bb8c2e19a7fe2ca2283eca44dba2047c9f4307fe`）を元に戻す（リバートする）ものです。具体的には、`net`パッケージ内の各種DNSルックアップ関数から、ドメイン名の形式を早期にチェックし、一貫したエラーを返すロジックと、それに関連するテストコードが削除されました。

## 変更の背景

このコミットは、以前のコミット `bb8c2e19a7fe2ca2283eca44dba2047c9f4307fe` をリバートするものです。元のコミットは、`net`パッケージ内のDNSルックアップ関数において、不正な形式のドメイン名が与えられた場合に、GoのネイティブDNSリゾルバ（netgo）とCgoベースのDNSリゾルバ（netcgo）のどちらを使用しているかに関わらず、一貫したエラー（`DNSError` with "invalid domain name"）を報告することを目的としていました。

この目的を達成するため、元のコミットでは、`LookupHost`、`LookupIP`、`LookupCNAME`などの複数のルックアップ関数の冒頭に、`isDomainName`という内部関数によるドメイン名形式の早期チェックが追加されていました。しかし、このリバートコミットは、その変更が何らかの予期せぬ問題（例えば、既存の動作との非互換性、パフォーマンスの低下、あるいは特定の有効なドメイン名が誤って不正と判断されるケースなど）を引き起こしたか、あるいはそのアプローチが望ましくないと判断されたことを示唆しています。コミットメッセージには具体的なリバートの理由は記載されていませんが、一貫性よりも他の側面（柔軟性、既存の挙動の維持など）が優先されたと考えられます。

## 前提知識の解説

*   **Goの`net`パッケージ**: Go言語の標準ライブラリの一部で、ネットワーク通信に関する機能を提供します。TCP/IP接続、UDP通信、DNSルックアップなどが含まれます。
*   **DNSルックアップ**: Domain Name System (DNS) を利用して、人間が読みやすいドメイン名（例: `example.com`）を、コンピュータが理解できるIPアドレス（例: `93.184.216.34`）に変換するプロセスです。
*   **`DNSError`**: `net`パッケージで定義されているエラー型の一つで、DNS関連の操作中に発生したエラーを表します。このエラー型には、エラーメッセージ（`Err`フィールド）や関連するドメイン名（`Name`フィールド）などの情報が含まれます。
*   **`isDomainName`関数**: Goの`net`パッケージ内部で使用される可能性のある（または以前使用されていた）関数で、与えられた文字列が有効なドメイン名の形式に準拠しているかをチェックします。RFCに準拠したドメイン名の命名規則（文字の種類、長さ、ハイフンの位置など）に基づいて検証を行います。
*   **`LookupHost`, `LookupIP`, `LookupCNAME`, `LookupSRV`, `LookupMX`, `LookupNS`, `LookupTXT`**: これらは`net`パッケージが提供する主要なDNSルックアップ関数です。
    *   `LookupHost`: ホスト名に対応するIPアドレスを検索します。
    *   `LookupIP`: ホスト名に対応するIPアドレスを検索し、`net.IP`型で返します。
    *   `LookupCNAME`: ドメイン名のCanonical Name (CNAME) を検索します。
    *   `LookupSRV`: サービスロケータレコード (SRVレコード) を検索します。
    *   `LookupMX`: メールエクスチェンジャーレコード (MXレコード) を検索します。
    *   `LookupNS`: ネームサーバレコード (NSレコード) を検索します。
    *   `LookupTXT`: テキストレコード (TXTレコード) を検索します。
*   **netgoとnetcgo**: Goの`net`パッケージは、DNSルックアップにおいて、Go言語で実装されたネイティブなリゾルバ（`netgo`）と、C言語の標準ライブラリ（通常はglibc）を介してOSのリゾルバを使用するCgoベースのリゾルバ（`netcgo`）の2つのモードを持つことがあります。これらのモードは、特にLinux環境で挙動が異なる場合があります。

## 技術的詳細

このリバートコミットの技術的な影響は、`net`パッケージのDNSルックアップ関数が不正なドメイン名に対してどのように振る舞うかという点に集約されます。

元のコミットでは、`LookupHost`、`LookupIP`、`LookupCNAME`、`LookupSRV`、`LookupMX`、`LookupNS`、`LookupTXT`といった複数のDNSルックアップ関数の実行パスの非常に早い段階で、`isDomainName`関数によるドメイン名の形式チェックが導入されていました。このチェックが失敗した場合、これらの関数は直ちに `&DNSError{Err: "invalid domain name", Name: host}` の形式でエラーを返していました。これにより、不正な形式のドメイン名に対しては、常に同じタイプと内容のエラーが返されることが保証されていました。また、`src/net/ip_test.go` に追加された `TestLookupBadName` は、この一貫したエラー報告を `netgo` と `netcgo` の両方のモードで検証していました。

今回のリバートにより、これらの早期チェックが削除されました。その結果、ドメイン名の形式検証は、各ルックアップ関数のより深い層、またはGoのネイティブリゾルバやCgoを介したOSのリゾルバといった、基盤となるDNS解決メカニズムに委ねられることになります。

この変更の具体的な影響は以下の通りです。

1.  **エラーの一貫性の喪失**: 不正なドメイン名に対するエラーの種類やメッセージが、どのルックアップ関数を呼び出したか、あるいはどのDNSリゾルバ（netgoかnetcgoか）が使用されているかによって異なる可能性があります。例えば、ある関数では「invalid domain name」というエラーが返されるかもしれませんが、別の関数では「no such host」や、OS固有のDNSエラーコードがラップされたエラーが返されるかもしれません。
2.  **テストの削除**: `TestLookupBadName` の削除は、もはや不正なドメイン名に対するエラー報告の一貫性を積極的にテストし、強制しないことを意味します。
3.  **柔軟性の向上（または意図しない挙動）**: 早期チェックがなくなることで、`net`パッケージは、より広範な（あるいは非標準的な）ドメイン名形式を、基盤となるリゾルバが処理できる限り受け入れる可能性があります。これは、特定のユースケースでは柔軟性をもたらすかもしれませんが、開発者が予期しないエラー挙動に遭遇する可能性も高まります。
4.  **パフォーマンスへの影響**: 早期チェックは、不正な入力に対する無駄なDNSクエリを防ぐことで、わずかながらパフォーマンス上の利点をもたらす可能性がありました。このリバートにより、不正なドメイン名であっても、実際にDNSクエリが発行されるまでエラーが検出されないケースが増えるかもしれません。

総じて、このリバートは、不正なドメイン名に対するエラー処理のポリシーを、より基盤となるDNS解決メカニズムに任せるという方向性への回帰を示しています。

## コアとなるコードの解説

*   **`TestLookupBadName` の削除**:
    このテスト関数は、Goの`net`パッケージが不正なドメイン名（例: "!!!.local"）をどのように扱うかについて、特定の期待される挙動を強制していました。具体的には、`netgo`（Goネイティブのリゾルバ）と `netcgo`（Cgo経由のOSリゾルバ）の両方で、`LookupHost`、`LookupIP`などのDNSルックアップ関数が、不正な入力に対して一貫して `DNSError` 型で `Err: "invalid domain name"` というエラーを返すことを検証していました。このテストの削除は、もはやこのレベルでのエラー報告の一貫性を保証しないという方針転換を意味します。これにより、不正なドメイン名に対するエラーは、使用されるリゾルバやOSの挙動に依存する可能性が高まります。

*   **`lookup.go` からの `isDomainName` チェックの削除**:
    `src/net/lookup.go` 内の複数のDNSルックアップ関数（`LookupHost`, `LookupIP`, `LookupCNAME`, `LookupSRV`, `LookupMX`, `LookupNS`, `LookupTXT`）から削除されたコードブロックは、以下のパターンに従っていました。
    ```go
    if !isDomainName(name) {
        return ..., &DNSError{Err: "invalid domain name", Name: name}
    }
    ```
    このコードは、ルックアップ処理が開始される前に、引数として渡されたドメイン名が有効な形式であるかを `isDomainName` 関数でチェックしていました。もしドメイン名が不正な形式であれば、実際のDNSクエリを発行することなく、すぐに `DNSError` を返していました。この早期リターンロジックの削除により、ドメイン名の形式検証は、これらの関数の内部実装、またはGoのネイティブDNSリゾルバやCgoを介したOSのDNSリゾルバといった、より低レベルのコンポーネントに委ねられることになります。結果として、不正なドメイン名が与えられた場合でも、エラーが報告されるタイミングや、返されるエラーの種類が、以前よりも多様になる可能性があります。これは、`net`パッケージのユーザーが、不正な入力に対するエラー処理をより詳細に考慮する必要があることを意味するかもしれません。

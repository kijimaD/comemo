# [インデックス 26992] ファイルの概要

このコミットは、Go言語の標準ライブラリ `mime/multipart` パッケージにおける `io.Reader` の利用方法に関する潜在的なバグを修正するものです。具体的には、`io.Reader` がエラーを返した後に再度 `Read` メソッドを呼び出すことによって発生しうる未定義の動作を防ぐための変更が加えられました。この修正は、`io.Reader` の契約がエラー後の動作について明確な保証をしていないという点に対応し、特に `zlib.Reader` のような特定の `Reader` 実装で発生した回帰バグ（バグ #14676）に対処しています。

## 変更の背景

この変更の背景には、Go言語の `io.Reader` インターフェースの契約に関する重要な側面と、それに関連して `mime/multipart` パッケージが抱えていた潜在的な問題があります。

`io.Reader` インターフェースの `Read` メソッドは、データを読み込む際にエラーが発生した場合、そのエラーを返します。しかし、**`io.Reader` の契約は、一度エラーを返した後に、その `Reader` に対して再度 `Read` メソッドが呼び出された場合の動作について何も保証していません。** 多くの `Reader` 実装（例えば `bytes.Reader` や `strings.Reader` など）では、一度エラー（特に `io.EOF` などの終端エラー）を返すと、それ以降の `Read` 呼び出しでも同じエラーを返し続ける、いわゆる「スティッキーエラー (sticky error)」の挙動を示します。しかし、これはあくまで慣習であり、インターフェースの契約上の義務ではありません。

`mime/multipart` パッケージは、HTTP multipart/form-data の解析を行うために、内部でユーザーが提供する `io.Reader` を利用しています。このパッケージの内部ロジックでは、`io.Reader` がエラーを返した後でも、さらに `Read` を呼び出す可能性がありました。これは、通常は問題になりませんが、`zlib.Reader` のような特定の `Reader` 実装において、エラー後に `Read` を呼び出すと予期せぬ動作を引き起こす回帰バグ（バグ #14676）が発見されました。この `zlib.Reader` のバグは、以前のバージョンではスティッキーエラーの挙動を示していたにもかかわらず、変更によってその挙動が変わったために顕在化しました。

このコミットの目的は、`io.Reader` の契約の曖昧さに依存しないように `mime/multipart` パッケージを修正し、エラー後の `Read` 呼び出しによる潜在的な問題を根本的に解決することです。特に、`multipart` の複雑なステートマシンに大きな変更を加えることなく、最小限の修正でこの問題を解決することを目指しています。

## 前提知識の解説

### `io.Reader` インターフェース

Go言語における `io.Reader` は、データを読み込むための最も基本的なインターフェースです。

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}
```

`Read` メソッドは、`p` に最大 `len(p)` バイトのデータを読み込み、読み込んだバイト数 `n` とエラー `err` を返します。
重要なのは、**`Read` メソッドがエラーを返した場合の、その後の `Read` 呼び出しの動作は未定義である**という点です。多くの実装はエラーを「スティッキー」にしますが、これは保証された挙動ではありません。

### `mime/multipart` パッケージ

`mime/multipart` パッケージは、HTTP の `multipart/form-data` 形式のデータを解析するための機能を提供します。これは、ウェブフォームでファイルアップロードを行う際などに広く利用されます。このパッケージは、内部で `io.Reader` を使用して入力ストリームからデータを読み込み、各パート（フォームフィールドやファイル）を解析します。

### `bufio.Reader`

`bufio.Reader` は、`io.Reader` をラップしてバッファリング機能を追加する構造体です。これにより、小さな読み取り要求が多数発生する場合でも、基になる `io.Reader` への呼び出し回数を減らし、I/O 効率を向上させることができます。`mime/multipart` パッケージは、効率的なデータ解析のために `bufio.Reader` を内部で使用しています。

### スティッキーエラー (Sticky Error)

「スティッキーエラー」とは、`io.Reader` が一度エラー（特に `io.EOF` や永続的なI/Oエラー）を返した後、それ以降の `Read` 呼び出しでも常に同じエラーを返し続ける挙動を指します。これは多くの `io.Reader` 実装で採用されている一般的なパターンですが、`io.Reader` インターフェースの契約上は必須ではありません。このコミットの背景にある問題は、`mime/multipart` パッケージがこの「スティッキーエラー」の挙動に暗黙的に依存していたために発生しました。

## 技術的詳細

このコミットの技術的な解決策は、ユーザーが `mime/multipart.NewReader` に提供する元の `io.Reader` を、`stickyErrorReader` という新しいカスタム `io.Reader` でラップすることです。

`stickyErrorReader` は、その名の通り、一度エラーを検出するとそのエラーを内部に保持し、それ以降の `Read` 呼び出しでは常にその保持したエラーを返すことを保証します。これにより、元の `io.Reader` がエラー後にどのような挙動をするかに関わらず、`mime/multipart` パッケージの内部ロジックは常に一貫した「スティッキーエラー」の挙動を持つ `Reader` を扱うことになります。

具体的には、`stickyErrorReader` は以下の構造とメソッドを持ちます。

```go
type stickyErrorReader struct {
	r   io.Reader // ラップする元のio.Reader
	err error     // 検出された最初のエラーを保持
}

func (r *stickyErrorReader) Read(p []byte) (n int, _ error) {
	if r.err != nil {
		// 既にエラーが検出されている場合、そのエラーを返す
		return 0, r.err
	}
	// 元のReaderから読み込みを試みる
	n, r.err = r.r.Read(p)
	// 読み込み結果とエラーを返す
	return n, r.err
}
```

`NewReader` 関数内で、元の `io.Reader` `r` は `&stickyErrorReader{r: r}` としてラップされ、その結果が `bufio.NewReaderSize` に渡されます。

```go
func NewReader(r io.Reader, boundary string) *Reader {
	b := []byte("\r\n--" + boundary + "--")
	return &Reader{
		bufReader:        bufio.NewReaderSize(&stickyErrorReader{r: r}, peekBufferSize), // ここが変更点
		nl:               b[:2],
		nlDashBoundary:   b[:len(b)-2],
		dashBoundaryDash: b[2:],
	}
}
```

このアプローチの利点は、`mime/multipart` パッケージの既存の複雑な解析ロジック（ステートマシン）に一切変更を加える必要がない点です。`io.Reader` の契約の曖昧さに起因する問題を、`Reader` のラッパーという形で透過的に解決しています。これにより、修正による副作用のリスクを最小限に抑えつつ、堅牢性を向上させています。

また、この変更には `formdata_test.go` に新しいテストケース `TestReadForm_NoReadAfterEOF` が追加されています。このテストは、`failOnReadAfterErrorReader` というカスタム `Reader` を使用して、エラーが返された後に `Read` が呼び出されないことを検証します。`failOnReadAfterErrorReader` は、一度エラーを返した後に `Read` が呼び出されるとテストを失敗させるように設計されており、`stickyErrorReader` が正しく機能していることを間接的に確認します。

## コアとなるコードの解説

### `stickyErrorReader` の実装 (`multipart.go`)

`stickyErrorReader` は、`io.Reader` インターフェースを満たすカスタム型です。その目的は、ラップしている元の `io.Reader` (`r`) が一度エラーを返した場合、それ以降の `Read` 呼び出しでは常にその最初のエラーを返すようにすることです。

- **`type stickyErrorReader struct { r io.Reader; err error }`**:
    - `r`: 実際にデータを読み込むための基となる `io.Reader` を保持します。
    - `err`: `Read` メソッドが最初に返したエラーを記憶するために使用されます。初期値は `nil` です。

- **`func (r *stickyErrorReader) Read(p []byte) (n int, _ error)`**:
    - このメソッドが呼び出されると、まず `r.err != nil` をチェックします。
    - もし `r.err` が `nil` でなければ（つまり、以前の `Read` 呼び出しでエラーが発生していた場合）、`n=0` と `r.err` を即座に返します。これにより、基となる `r.r.Read(p)` は呼び出されず、エラーが「スティッキー」に保たれます。
    - `r.err` が `nil` の場合、`r.r.Read(p)` を呼び出して実際の読み込みを行います。
    - 読み込みが完了すると、`n` と `err` が返されますが、この `err` は `r.err` にも保存されます。これにより、次回以降の `Read` 呼び出しでこのエラーが再利用されるようになります。

この `stickyErrorReader` を `NewReader` 関数内で `bufio.NewReaderSize` に渡すことで、`mime/multipart` パッケージの内部ロジックは、常にエラーがスティッキーであると仮定できる安全な `io.Reader` を扱うことになります。

### `TestReadForm_NoReadAfterEOF` と `failOnReadAfterErrorReader` の実装 (`formdata_test.go`)

このテストケースは、`stickyErrorReader` が導入されたことで、`mime/multipart` パッケージがエラー後に `io.Reader` を不適切に呼び出さなくなったことを検証するために追加されました。

- **`type failOnReadAfterErrorReader struct { t *testing.T; r io.Reader; sawErr error }`**:
    - `t`: テストの失敗を報告するために `*testing.T` を保持します。
    - `r`: ラップする基となる `io.Reader` です。
    - `sawErr`: この `Reader` が以前にエラーを返したかどうかを追跡します。

- **`func (r *failOnReadAfterErrorReader) Read(p []byte) (n int, err error)`**:
    - この `Read` メソッドは、`r.sawErr` が `nil` でない場合（つまり、以前にエラーを返していた場合）に `r.t.Fatalf` を呼び出してテストを強制的に失敗させます。これは、「エラー後に `Read` が呼び出された」という不正な状態を検出するためのものです。
    - `r.sawErr` が `nil` の場合、基となる `r.r.Read(p)` を呼び出し、その結果のエラーを `r.sawErr` に保存してから返します。

`TestReadForm_NoReadAfterEOF` テストでは、`NewReader` に `&failOnReadAfterErrorReader{t: t, r: strings.NewReader(body)}` を渡しています。もし `mime/multipart` の内部で `stickyErrorReader` が正しく機能せず、エラー後に基となる `Reader` が呼び出されてしまうと、`failOnReadAfterErrorReader` が `Fatalf` を呼び出してテストが失敗します。このテストが成功するということは、`stickyErrorReader` が期待通りに機能し、`mime/multipart` が `io.Reader` の契約を尊重していることを示します。

# [インデックス 26831] ファイルの概要

このコミットは、Go言語の標準ライブラリ `compress/bzip2` パッケージにおける、bzip2圧縮データのブロックサイズ計算の誤りを修正するものです。具体的には、ブロックサイズの乗数として `1024` (2の10乗) ではなく `1000` (10の3乗) を使用するように変更し、それに伴いテストケースを追加しています。この修正により、不正なブロックサイズを持つbzip2ファイルを正しくエラーとして処理できるようになります。

## コミット

`compress/bzip2`: 正しいブロックサイズを使用する

bzip2のブロックサイズは `100 * 1000` の倍数であり、`100 * 1024` ではありません。
このため、bzip2デコーダは、本来であれば失敗すべきである、より大きなブロックサイズを持つファイルを誤ってデコードしていました。
幸いなことに、Goには不正なブロックを生成するbzip2エンコーダの実装がないため、後方互換性を保ったままこれを修正できます。

C言語のbzip2ユーティリティがこのデータでエラーになることを確認するには：
```
$ echo "425a683131415926535936dc55330063ffc0006000200020a40830008b00
08b8bb9229c28481b6e2a998" | xxd -r -p | bzip2 -d

bzip2: Data integrity error when decompressing.
```

## 変更の背景

この変更の背景には、Go言語の `compress/bzip2` デコーダが、bzip2圧縮フォーマットの仕様を誤って解釈していたという問題があります。bzip2フォーマットでは、ブロックサイズは100KB (100 * 1000バイト) の倍数として定義されていますが、Goの実装では誤って100KiB (100 * 1024バイト) の倍数として扱っていました。

この誤った解釈により、Goのデコーダは、本来であれば不正なフォーマットとして拒否すべき、特定の大きなブロックサイズを持つbzip2ファイルを誤って受け入れてデコードしようとしていました。これは、データ破損や予期せぬ動作につながる可能性がありました。

コミットメッセージに示されているように、C言語で実装された標準的な `bzip2` ユーティリティは、この種の不正なデータに対して「Data integrity error when decompressing.」というエラーを報告します。Goのデコーダも同様に、このような不正なデータに対してエラーを報告し、デコードを停止すべきであるという認識から、この修正が行われました。

幸いなことに、Goの `compress/bzip2` パッケージにはエンコーダの実装が存在しないため、Go自身がこの誤ったブロックサイズでファイルを生成することはありませんでした。そのため、この修正は既存のGoで生成されたbzip2ファイルとの後方互換性を損なうことなく適用できるという利点がありました。

この問題は、GoのIssueトラッカーで #13941 として報告されており、このコミットはそのIssueを解決するものです。

## 前提知識の解説

### bzip2圧縮フォーマット

bzip2は、Burrows-Wheeler変換 (BWT) とMove-to-Front (MTF) 変換、ランレングス符号化 (RLE)、ハフマン符号化を組み合わせたブロックソート型データ圧縮アルゴリズムです。高い圧縮率を誇りますが、処理速度はgzipなどに比べて遅い傾向があります。

bzip2のデータ構造は、マジックナンバー、ファイルヘッダ、そして複数の圧縮ブロックから構成されます。各圧縮ブロックは独立して圧縮・伸長が可能であり、ブロックサイズは圧縮時に指定されます。

### bzip2のブロックサイズ

bzip2のブロックサイズは、圧縮効率とメモリ使用量のトレードオフを決定する重要なパラメータです。bzip2の仕様では、ブロックサイズは100KB (100 * 1000バイト) から900KB (900 * 1000バイト) の範囲で、100KB単位で指定されます。これは、`100 * 1000 * N` (Nは1から9の整数) という形式で表現されます。

ここで重要なのは、`1000` という基数です。コンピュータの世界では `1024` (2の10乗、キロバイトの「キビ」を表すKiB) がよく使われますが、bzip2の仕様では `1000` (10の3乗、キロバイトの「キロ」を表すKB) が採用されています。この違いが、今回のバグの根本原因となりました。

### Burrows-Wheeler変換 (BWT)

BWTは、データを可逆的に変換し、同じ文字が連続して出現しやすいように並べ替えることで、後続の圧縮アルゴリズム（MTF、RLE、ハフマン符号化など）の効率を高める前処理です。BWT自体はデータを圧縮しませんが、圧縮しやすい形にデータを「並べ替える」役割を果たします。

### Move-to-Front (MTF) 変換

MTF変換は、BWTの出力に対して適用される変換です。最近出現した文字ほど小さな数値にマッピングすることで、ランレングス符号化の効率を高めます。

### CRC (Cyclic Redundancy Check)

CRCは、データ転送や保存中に発生したエラーを検出するためのハッシュ関数の一種です。bzip2では、各ブロックとファイル全体に対してCRC値が計算され、デコード時にこのCRC値を検証することで、データの整合性を確認します。CRC値が一致しない場合、データが破損していると判断されます。

## 技術的詳細

このコミットの技術的な核心は、`src/compress/bzip2/bzip2.go` ファイル内の `blockSize` 変数の計算ロジックの修正にあります。

元のコードでは、`blockSize` の計算に `100 * 1024` を使用していました。
```go
// src/compress/bzip2/bzip2.go (修正前)
type reader struct {
	// ...
	blockSize    int  // blockSize in bytes, i.e. 900 * 1024.
	// ...
}

func (bz2 *reader) setup(needMagic bool) error {
	// ...
	bz2.blockSize = 100 * 1024 * (int(level) - '0')
	// ...
}
```

この `1024` という値は、コンピュータサイエンスでよく使われる2進数のキロバイト (KiB) の定義に由来しますが、bzip2の仕様では10進数のキロバイト (KB) である `1000` が正しいです。

修正後のコードでは、この `1024` が `1000` に変更されています。
```go
// src/compress/bzip2/bzip2.go (修正後)
type reader struct {
	// ...
	blockSize    int  // blockSize in bytes, i.e. 900 * 1000.
	// ...
}

func (bz2 *reader) setup(needMagic bool) error {
	// ...
	bz2.blockSize = 100 * 1000 * (int(level) - '0')
	// ...
}
```

この変更により、`bzip2.reader` 構造体の `blockSize` フィールドが、bzip2フォーマットの仕様に合致する正しい値で初期化されるようになります。`level` はbzip2ヘッダから読み取られるブロックサイズを示す文字（'1'から'9'）であり、`int(level) - '0'` で数値に変換されます。例えば、`level` が '9' であれば、`900 * 1000` バイト（900KB）が `blockSize` として設定されます。

`blockSize` は、デコーダが内部的に使用するバッファ (`bz2.tt`) のサイズを決定するために使用されます。`bz2.tt = make([]uint32, bz2.blockSize)` の行で、この `blockSize` に基づいてバッファが確保されます。誤った `blockSize` を使用すると、バッファが小さすぎたり大きすぎたりする可能性があり、特に小さすぎる場合は、デコード中にバッファオーバーフローや不正なメモリアクセスを引き起こす可能性があります。

この修正によって、Goのbzip2デコーダは、bzip2の仕様に厳密に従ってブロックサイズを解釈するようになり、本来エラーとなるべき不正なブロックサイズを持つファイルを正しくエラーとして処理できるようになります。これにより、デコーダの堅牢性と信頼性が向上します。

また、`src/compress/bzip2/bzip2_test.go` に `TestBadBlockSize` という新しいテストケースが追加されています。このテストは、コミットメッセージで示された、C言語のbzip2ユーティリティがエラーを出す特定の不正なbzip2データ (`badBlockSize` 定数で定義) をGoのデコーダに与え、エラーが返されることを確認します。これにより、修正が正しく機能していることが検証されます。

## コアとなるコードの解説

### `src/compress/bzip2/bzip2.go` の変更

`bzip2.go` ファイルでは、`reader` 構造体の `blockSize` フィールドのコメントと、`setup` メソッド内の `bz2.blockSize` の計算式が変更されています。

1.  **`blockSize` フィールドのコメント修正**:
    `blockSize int // blockSize in bytes, i.e. 900 * 1024.`
    が
    `blockSize int // blockSize in bytes, i.e. 900 * 1000.`
    に変更されました。これは、`blockSize` が `1024` ではなく `1000` の倍数であることを明確にするためのドキュメント上の修正です。

2.  **`bz2.blockSize` 計算式の修正**:
    `bz2.blockSize = 100 * 1024 * (int(level) - '0')`
    が
    `bz2.blockSize = 100 * 1000 * (int(level) - '0')`
    に変更されました。これがこのコミットの最も重要な機能的変更点です。`level` はbzip2ヘッダから読み取られるブロックサイズを示す文字（'1'から'9'）であり、`int(level) - '0'` で数値に変換されます。この修正により、デコーダが内部的に使用するブロックサイズがbzip2の仕様に準拠するようになります。

この修正は、bzip2デコーダが不正なブロックサイズを持つファイルを正しく識別し、エラーとして処理するために不可欠です。

### `src/compress/bzip2/bzip2_test.go` の変更

`bzip2_test.go` ファイルには、`TestBadBlockSize` という新しいテスト関数が追加されています。

1.  **`badBlockSize` 定数の追加**:
    `const badBlockSize = "425a683131415926535936dc55330063ffc0006000200020a40830008b0008b8bb9229c28481b6e2a998"`
    この定数は、コミットメッセージでC言語のbzip2ユーティリティがエラーを出すと示された、特定の不正なbzip2データのヘックス表現です。

2.  **`TestBadBlockSize` 関数の追加**:
    このテスト関数は、`badBlockSize` で定義された不正なデータを `decompressHex` 関数（テストユーティリティ関数）に渡し、デコードが失敗すること（つまりエラーが返されること）を期待します。
    `if err == nil { t.Errorf("unexpected success") }`
    この行は、エラーが返されなかった場合（つまり、不正なデータが誤って成功裏にデコードされた場合）にテストを失敗させます。これにより、デコーダが不正なブロックサイズを正しく検出してエラーを報告するようになったことが検証されます。

このテストの追加は、バグが修正されたことを確認するだけでなく、将来的に同様の回帰バグが発生しないようにするための重要な安全策となります。

## 変更の背景

このコミットの背景には、Goランタイムのガベージコレクション（GC）におけるデバッグとパフォーマンスのバランスに関する課題があります。

`gcMarkRootCheck`は、GCのマークフェーズが完了した後に、すべての到達可能なオブジェクトが正しくマークされているかを確認するための重要なデバッグチェックです。これは、GCのバグを発見するのに非常に役立ちます。しかし、このチェックは実行コストが高く、特に多数のGoroutine（Goにおける軽量スレッド）が存在する場合に顕著なオーバーヘッドを発生させます。

以前は、この`gcMarkRootCheck`はマーク終了フェーズ中に無条件に実行されていましたが、そのパフォーマンスコストのためにコメントアウトされていました（`// TODO: Re-enable once this is cheap.`というコメントが残っていたことから伺えます）。

このコミットでは、`gcMarkRootCheck`の有用性を認識しつつ、そのコストを考慮して、特定の条件下でのみ有効化するように変更しています。その条件とは、`checkmark mode`が有効になっている場合です。`checkmark mode`自体がGCのデバッグや検証を目的としたモードであるため、このモードが有効な場合にのみ高コストな`gcMarkRootCheck`を実行することは、デバッグの網羅性を高めつつ、通常の実行時のパフォーマンスへの影響を最小限に抑えるという合理的な判断です。

つまり、この変更は、GCの正確性を検証するためのデバッグ機能を、パフォーマンスへの影響を許容できるデバッグモードに限定して再導入することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクション（GC）の基本的な仕組みと、関連する用語について知っておく必要があります。

1.  **Goのガベージコレクション (GC)**:
    GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにしています。これは、オブジェクトを「白（未訪問）」「灰（訪問済みだが参照先は未訪問）」「黒（訪問済みで参照先も訪問済み）」の3色に分類しながら、到達可能なオブジェクトをマークし、マークされなかった（到達不可能な）オブジェクトを解放する仕組みです。GoのGCは並行（concurrent）かつ増分（incremental）に動作し、アプリケーションの実行とGC処理を同時に進めることで、Stop-The-World（STW）ポーズの時間を最小限に抑えるように設計されています。

2.  **GCのフェーズ**:
    GoのGCは、大まかに以下のフェーズで構成されます。
    *   **Mark Assist**: アプリケーションがメモリを割り当てる際に、GCのマーク処理を補助的に実行するフェーズ。
    *   **Marking**: ルート（スタック、グローバル変数など）から到達可能なオブジェクトをマークしていくフェーズ。これは並行して行われます。
    *   **Mark Termination (STW)**: マークフェーズの最終段階で、すべてのGoroutineを一時停止（Stop-The-World: STW）させて、GCの状態を確定させるフェーズ。このSTW時間はGo GCの重要な最適化目標の一つです。このフェーズでは、グローバルなGC状態の更新や、マーク処理の最終的な調整が行われます。
    *   **Sweeping**: マークされなかったオブジェクトが占めていたメモリを解放するフェーズ。これは並行して行われます。

3.  **`gcMarkRootCheck`**:
    これは、GCのマークフェーズが終了した後に、すべてのルート（スタック、グローバル変数など）から到達可能なオブジェクトが、実際にGCによって「マーク済み」とされているかを検証するデバッグ用のチェック関数です。もしGCにバグがあれば、到達可能なオブジェクトがマークされずに誤って解放されてしまう可能性があります。`gcMarkRootCheck`はこのようなバグを早期に発見するために非常に有用です。しかし、システム内のすべての到達可能なオブジェクトを再走査する必要があるため、実行コストが高い処理です。

4.  **`checkmark mode` (debug.gccheckmark)**:
    Goランタイムには、GCの動作を詳細に検証するためのデバッグモードがいくつか存在します。`checkmark mode`はその一つで、GCの正確性をより厳密にチェックするために設計されたモードです。このモードが有効な場合、GCは追加の検証ステップを実行し、潜在的なバグや不整合を検出します。通常、このモードは開発時やテスト時にのみ使用され、本番環境でのパフォーマンスは考慮されません。`debug.gccheckmark`は、このモードを制御するための内部的なフラグまたは設定値と考えられます。

5.  **STW (Stop-The-World)**:
    ガベージコレクタが動作する際に、アプリケーションの実行を一時的に完全に停止させる期間のことです。GoのGCはSTW時間を極力短くするように設計されていますが、GCの特定のフェーズ（特にマーク終了フェーズ）では、データの一貫性を保つためにSTWが不可欠となります。STW時間が長くなると、アプリケーションの応答性が低下するため、GCの重要な最適化ポイントとなります。

## 技術的詳細

このコミットは、`src/runtime/mgc.go`ファイル内の`gcMark`関数、具体的にはマーク終了（mark termination）フェーズのロジックを変更しています。

変更前は、`gcMarkRootCheck()`の呼び出しがコメントアウトされていました。これは、このチェックが「高価すぎる」ため、通常のGCサイクルでは実行しないという判断がなされていたことを示しています。

```go
// TODO: Re-enable once this is cheap.
//gcMarkRootCheck()
```

このコミットでは、このコメントアウトされた行を削除し、代わりに条件付きで`gcMarkRootCheck()`を呼び出すロジックを導入しています。

```go
	if debug.gccheckmark > 0 {
		// This is expensive when there's a large number of
		// Gs, so only do it if checkmark is also enabled.
		gcMarkRootCheck()
	}
```

この変更の技術的なポイントは以下の通りです。

*   **条件付き実行**: `gcMarkRootCheck()`は、`debug.gccheckmark > 0`という条件が真の場合にのみ実行されるようになりました。これは、`checkmark mode`が有効になっている場合に相当します。
*   **パフォーマンスとデバッグのバランス**: `gcMarkRootCheck`は、GCの正確性を検証する上で非常に価値のあるデバッグ機能ですが、その実行コストは無視できません。特に、多数のGoroutineが存在するシステムでは、このチェックがSTW時間を大幅に延長させる可能性があります。この変更により、通常の運用時にはこの高コストなチェックをスキップし、GCのデバッグや開発時にのみ有効化することで、パフォーマンスとデバッグの網羅性のバランスを取っています。
*   **STWフェーズでの実行**: `gcMarkRootCheck`は、`gcMark`関数内のマーク終了フェーズ（STW中）に呼び出されます。STW中はすべてのGoroutineが停止しているため、GCの状態が安定しており、正確なルートチェックを実行するのに適したタイミングです。しかし、STW中であるからこそ、このチェックの実行時間がアプリケーションのポーズ時間に直結するため、そのコストが問題視されていました。
*   **`debug.gccheckmark`の役割**: `debug.gccheckmark`は、Goランタイムの内部的なデバッグフラグであり、GCのチェックマークモードを制御します。このフラグが設定されている場合、開発者やテスターはGCのより厳密な検証を行うことができます。このコミットは、この既存のデバッグメカニズムを活用して、`gcMarkRootCheck`の実行を制御しています。

この変更により、GoのGCは、通常の実行時には高速性を維持しつつ、デバッグ時にはより強力な整合性チェックを実行できるようになり、GCのバグ検出能力が向上しました。

## コアとなるコードの解説

この変更は、`gcMark`関数内でガベージコレクションのマークフェーズが完了し、`gcDrain`と`gcw.dispose()`が実行された直後に位置しています。この時点は、GCのマーク処理がほぼ終了し、STW（Stop-The-World）状態にあるマーク終了フェーズの重要なポイントです。

削除されたコメントアウト行は、以前は`gcMarkRootCheck()`がパフォーマンス上の理由で無効化されていたことを明確に示しています。開発者はこのチェックの重要性を認識しつつも、そのコストのために一時的に停止していたわけです。

追加されたコードブロックは、この`gcMarkRootCheck()`を条件付きで再有効化するものです。

*   `if debug.gccheckmark > 0 { ... }`: この条件文が、`gcMarkRootCheck()`を実行するかどうかを決定します。`debug.gccheckmark`はGoランタイムの内部的なデバッグフラグであり、GCのチェックマークモードが有効になっているかどうかを示します。`> 0`という条件は、このモードが有効になっていることを意味します。
*   `// This is expensive when there's a large number of // Gs, so only do it if checkmark is also enabled.`: このコメントは、`gcMarkRootCheck`が高コストであること、特に多数のGoroutineが存在する場合に顕著であることを改めて強調しています。そして、そのコストを許容できるデバッグモードである`checkmark mode`が有効な場合にのみ実行するという設計意図を説明しています。
*   `gcMarkRootCheck()`: この関数が呼び出されると、GCによってマークされたオブジェクトの整合性が検証されます。具体的には、ルートから到達可能なすべてのオブジェクトが正しくマークされているかを確認し、もし不整合があればランタイムエラーを発生させることで、GCのバグを検出します。

この変更により、Goランタイムは、通常の実行時には`gcMarkRootCheck`のオーバーヘッドを回避しつつ、GCのデバッグやテスト時にはこの強力な整合性チェックを利用できるようになり、GCの信頼性向上に貢献しています。

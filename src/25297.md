# [インデックス 25297] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）に関連する`src/runtime/mgc.go`ファイルに対する変更です。`mgc.go`は、Goのメモリ管理とガベージコレクションの核心部分を担うファイルであり、GCのスケジューリング、マーキング、スイープといった主要なフェーズの実装が含まれています。GoのGCは、並行（concurrent）かつ低遅延（low-latency）であることを目指しており、このファイルはその複雑なロジックを管理しています。

## コミット

このコミットは、ガベージコレクションの初期化フェーズで行われる2つの関連する状態リセット関数`gcResetGState`と`gcResetMarkState`を統合することを目的としています。これらの関数が常に一緒に呼び出され、論理的に関連する状態リセットを実行するため、コードの簡素化と保守性の向上を図っています。

## 変更の背景

Goのガベージコレクションプロセスでは、各GCサイクルが開始される前に、特定の内部状態をリセットする必要があります。これには、Goroutine（G）の状態とマーキングプロセスの状態が含まれます。以前は、これらのリセットは`gcResetGState`と`gcResetMarkState`という2つの別々の関数によって行われていました。

コミットメッセージによると、これらの関数は常に一緒に呼び出されており、論理的にも密接に関連する状態リセットを実行していました。このような状況は、コードの重複や不必要な複雑さを生み出す可能性があります。`Fixes #11427`という記述は、この問題が以前から認識されており、このコミットがその解決策であることを示しています。

この変更の主な目的は、コードの簡素化、保守性の向上、および潜在的なバグの削減です。2つの密接に関連する操作を1つの関数にまとめることで、GCの初期化ロジックがより明確になり、将来の変更が容易になります。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクションの基本的な概念と、特にその「マーキング」フェーズにおける状態管理について理解しておく必要があります。

1.  **Goのガベージコレクション (GC)**: GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースにしています。これは、オブジェクトを「白（未訪問）」「灰（訪問済みだが参照先未訪問）」「黒（訪問済みで参照先も訪問済み）」の3色に分類し、到達可能なオブジェクトをマークし、マークされなかった（白のままの）オブジェクトを回収するプロセスです。GoのGCは、アプリケーションの実行と並行して動作する「並行GC」を特徴とし、アプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑えるように設計されています。

2.  **GCサイクル**: GoのGCは、以下の主要なフェーズで構成されます。
    *   **マーク開始 (Mark Start)**: GCサイクルの開始。一部の初期化とSTWフェーズが含まれることがあります。
    *   **並行マーク (Concurrent Mark)**: アプリケーションの実行と並行して、到達可能なオブジェクトをマークします。
    *   **マーク終了 (Mark Termination)**: 並行マークの完了を調整し、最終的なSTWフェーズで残りのマーク作業を完了します。
    *   **並行スイープ (Concurrent Sweep)**: マークされなかったオブジェクトをメモリから回収します。

3.  **Goroutine (G) の状態**: Goランタイムは、各Goroutineのスタックをスキャンして、スタック上に存在するポインタを特定し、それらが参照するオブジェクトをマークする必要があります。このスキャンプロセス中に、GoroutineのGC関連の状態（例: スタックがスキャンされたかどうか、GCアシストバイト数など）が管理されます。

4.  **GCアシスト (GC Assist)**: 並行GC中、アプリケーションが大量のメモリを割り当てると、GCの進行が追いつかなくなる可能性があります。これを防ぐため、Goランタイムは「GCアシスト」というメカニズムを使用します。これは、メモリを割り当てようとするGoroutineが、その割り当ての一部としてGC作業を手伝うことを強制するものです。`gcAssistBytes`はそのために使用されるカウンタです。

5.  **`gcResetGState`と`gcResetMarkState`の役割（変更前）**:
    *   `gcResetGState`: 各GoroutineのGC関連の状態（特にスタックのスキャン状態や`gcAssistBytes`カウンタ）をリセットする役割を担っていました。これは、新しいGCサイクルが始まる前に、すべてのGoroutineが「未スキャン」の状態に戻ることを保証するために必要です。
    *   `gcResetMarkState`: マーキングプロセス全体の状態（例: `work.bytesMarked`や`work.initialHeapLive`など、GCサイクル中にマークされたバイト数やヒープの初期ライブサイズ）をリセットする役割を担っていました。これは、新しいGCサイクルが前のサイクルの情報に影響されないようにするために必要です。

これらのリセットは、GCの正確性と効率性を保証するために不可欠です。

## 技術的詳細

このコミットの技術的な核心は、`gcResetGState`と`gcResetMarkState`という2つの関数が持つ責任範囲を再評価し、それらを`gcResetMarkState`という単一の関数に統合することにあります。

変更前は、`gcResetGState`は主にGoroutineごとのGC状態（`gp.gcAssistBytes`のリセットなど）を処理し、`gcResetMarkState`はGCマーキングプロセス全体のグローバルな状態（`work.bytesMarked`や`work.initialHeapLive`のリセットなど）を処理していました。

コミットメッセージが指摘するように、これらの関数は常に一緒に呼び出されていました。これは、GCサイクルを開始する際には、Goroutineの状態とマーキングプロセスの両方の状態をリセットする必要があるためです。この密接な関係性から、これらを別々の関数として維持することは、以下のようなデメリットがありました。

*   **冗長な呼び出し**: 常に2つの関数を呼び出す必要がありました。
*   **論理的結合の不明瞭さ**: 2つの関数が論理的に強く結合しているにもかかわらず、コード上は独立しているように見えました。
*   **保守性の低下**: 将来的にこれらのリセットロジックに変更を加える場合、両方の関数またはその呼び出し箇所を考慮する必要がありました。

このコミットでは、`gcResetGState`のロジック（Goroutineの`gcAssistBytes`のリセット）を`gcResetMarkState`関数内に移動させました。これにより、`gcResetMarkState`はGoroutineごとの状態リセットとグローバルなマーキング状態リセットの両方を担当するようになります。

新しい`gcResetMarkState`関数のコメントは、その新しい役割を明確にしています。「`gcResetMarkState resets global state prior to marking (concurrent or STW) and resets the stack scan state of all Gs. Any Gs created after this will also be in the reset state.`」（並行またはSTWマーキングに先立ってグローバル状態をリセットし、すべてのGのスタックスキャン状態をリセットします。この後に作成されるGもリセットされた状態になります。）

この統合により、GCの初期化ロジックがより凝集され、単一責任の原則に近づきます。また、`gcResetGState`関数が完全に削除されることで、コードベースがわずかに小さくなり、理解しやすくなります。

## コアとなるコードの解説

このコミットによるコード変更は、主に以下の3つの側面から構成されています。

1.  **`gc`関数内での`gcResetGState`の呼び出し削除**:
    `src/runtime/mgc.go`の`gc`関数は、Goのガベージコレクションのメインエントリポイントです。この関数内で、GCサイクルが開始される際や、特定のGCフェーズの移行時に`gcResetGState()`が呼び出されていました。
    変更前:
    ```go
    	gcResetGState()
    	gcResetMarkState()
    ```
    変更後:
    ```go
    	gcResetMarkState()
    ```
    これは、`gcResetGState`の機能が`gcResetMarkState`に統合されたため、個別に呼び出す必要がなくなったことを示しています。同様の削除が、`gc`関数内の他の2箇所（`initCheckmarks()`の前後）でも行われています。

2.  **`gcResetGState`関数の削除と`gcResetMarkState`への統合**:
    変更前は、`gcResetGState`という独立した関数が存在し、Goroutineの状態をリセットしていました。
    ```go
    // gcResetGState resets the GC state of all G's. Any Gs created after
    // this will also be in this reset state.
    func gcResetGState() {
    	// ... Goroutineの状態リセットロジック ...
    	for _, gp := range allgs {
    		gp.gcAssistBytes = 0
    	}
    	// ...
    }
    ```
    このコミットでは、`gcResetGState`関数自体が削除され、その内部ロジック（特に`allgs`をイテレートして`gp.gcAssistBytes = 0`を設定する部分）が既存の`gcResetMarkState`関数内に移動されました。

3.  **`gcResetMarkState`関数のシグネチャとコメントの変更**:
    `gcResetMarkState`関数は、`gcResetGState`のロジックを取り込むために変更されました。
    変更前:
    ```go
    // gcResetMarkState resets state prior to marking (concurrent or STW).
    //
    // TODO(austin): Merge with gcResetGState. See issue #11427.
    func gcResetMarkState() {
    	work.bytesMarked = 0
    	work.initialHeapLive = memstats.heap_live
    }
    ```
    変更後:
    ```go
    // gcResetMarkState resets global state prior to marking (concurrent
    // or STW) and resets the stack scan state of all Gs. Any Gs created
    // after this will also be in the reset state.
    func gcResetMarkState() {
    	// This may be called during a concurrent phase, so make sure
    	// allgs doesn't change.
    	lock(&allglock)
    	for _, gp := range allgs {
    		gp.gcAssistBytes = 0
    	}
    	unlock(&allglock)
    
    	work.bytesMarked = 0
    	work.initialHeapLive = memstats.heap_live
    }
    ```
    新しいコメントは、この関数がグローバルなマーキング状態のリセットに加えて、すべてのGoroutineのスタックスキャン状態もリセットするという拡張された役割を明確にしています。また、`TODO(austin): Merge with gcResetGState. See issue #11427.`というコメントが削除されており、このコミットがまさにそのTODOを解決したことを示しています。

この変更により、GCの初期化ロジックがより一元化され、コードの可読性と保守性が向上しました。

# [インデックス 25909] ファイルの概要

このコミットは、Goランタイムの`amd64`アーキテクチャ向けアセンブリコードにおける`stackBarrier`関数の健全性チェックのバグ修正に関するものです。具体的には、スタックバリア配列のエントリをアンワインドする際のポインタ比較と条件分岐のロジックが誤っていた点を修正しています。

## コミット

Author: Austin Clements <austin@google.com>
Date:   Wed Nov 18 16:48:22 2015 -0500

    runtime: fix sanity check in stackBarrier
    
    stackBarrier on amd64 sanity checks that it's unwinding the correct
    entry in the stack barrier array. However, this check is wrong in two
    ways that make it unlikely to catch anything, right or wrong:
    
    1) It checks that savedLRPtr == SP, but, in fact, it should be that
       savedLRPtr+8 == SP because the RET that returned to stackBarrier
       popped the saved LR. However, we didn't notice this check was wrong
       because,
    
    2) the sense of the conditional branch is also wrong.
    
    Fix both of these.

## 元コミット内容

`src/runtime/asm_amd64.s` ファイル内の `runtime·stackBarrier` 関数において、スタックポインタと保存されたリンクレジスタポインタを比較する健全性チェックのロジックが誤っていました。

具体的には、以下のコードが問題でした。

```assembly
	MOVQ	stkbar_savedLRPtr(DX)(BX*1), R8
	MOVQ	stkbar_savedLRVal(DX)(BX*1), BX
	// Assert that we're popping the right saved LR.
	CMPQ	R8, SP
	JNE	2(PC)
	MOVL	$0, 0
	// Record that this stack barrier was hit.
	ADDQ	$1, g_stkbarPos(CX)
```

このコードでは、`R8`（`savedLRPtr`）と`SP`（スタックポインタ）を直接比較し、等しくない場合にジャンプ（`JNE`）していました。

## 変更の背景

`stackBarrier`関数は、`amd64`アーキテクチャにおいて、スタックバリア配列内の正しいエントリをアンワインドしていることを確認するための健全性チェックを含んでいました。しかし、このチェックには2つの誤りがあり、その結果、意図した通りに問題を検出できない状態でした。

1.  **ポインタ比較の誤り**: `savedLRPtr == SP`という比較が行われていましたが、実際には`stackBarrier`にリターンした`RET`命令が保存されたリンクレジスタ（LR）をポップするため、`savedLRPtr+8 == SP`であるべきでした。`RET`命令はスタックからリターンアドレスをポップし、`SP`を8バイト増加させます。したがって、`savedLRPtr`が指すアドレスは、`RET`命令実行後の`SP`よりも8バイト小さい位置を指しているはずです。
2.  **条件分岐の誤り**: 上記の比較が間違っていたにもかかわらず、このチェックが機能不全であることに気づかなかったのは、条件分岐のロジックも逆になっていたためです。`JNE`（Jump if Not Equal）が使用されていましたが、これは`R8`と`SP`が等しくない場合にジャンプするという意味です。しかし、健全性チェックの目的は、両者が期待通りに「等しい」場合に処理を進めるか、あるいは「等しくない」場合にエラーを検出することです。この文脈では、期待される状態（`savedLRPtr+8 == SP`）が成立しない場合に異常としてジャンプすべきであり、元の`JNE`ではその逆の動作をしていました。

これらの誤りにより、健全性チェックはほとんど意味をなさず、本来検出されるべき問題を見逃す可能性がありました。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステム。ガベージコレクション、スケジューリング、スタック管理など、多くの重要な機能を提供します。
*   **アセンブリ言語 (Assembly Language)**: コンピュータのプロセッサが直接理解できる機械語に非常に近い低レベルのプログラミング言語。Goランタイムのパフォーマンスが重要な部分や、特定のハードウェア機能にアクセスする必要がある部分で利用されます。
*   **amd64**: Intel 64またはx86-64としても知られる、64ビットの命令セットアーキテクチャ。Goは様々なアーキテクチャをサポートしており、`amd64`はその一つです。
*   **スタック (Stack)**: プログラム実行中にローカル変数、関数呼び出しの引数、リターンアドレスなどを一時的に格納するために使用されるメモリ領域。LIFO（Last-In, First-Out）の原則で動作します。
*   **スタックポインタ (SP: Stack Pointer)**: 現在のスタックの最上位（または最下位、アーキテクチャによる）を指すレジスタ。`amd64`では、スタックは通常、高アドレスから低アドレスに向かって成長し、`SP`はスタックの最上位要素の次の空き領域を指します。
*   **リンクレジスタ (LR: Link Register)**: 関数呼び出し時にリターンアドレスを保存するために使用されるレジスタ（またはスタック上の場所）。`amd64`では、`CALL`命令がリターンアドレスをスタックにプッシュし、`RET`命令がそれをポップして`IP`（Instruction Pointer）にロードします。
*   **`RET`命令**: サブルーチンからリターンするための命令。スタックからリターンアドレスをポップし、プログラムカウンタ（`IP`）にロードして実行を継続します。この際、`SP`はポップされたバイト数（`amd64`では8バイト）だけ増加します。
*   **`CMPQ`命令**: 2つの64ビット値を比較する命令。比較結果はフラグレジスタに格納され、その後の条件分岐命令（`JNE`, `JEQ`など）によって利用されます。
*   **`JNE` (Jump if Not Equal)**: 比較結果が等しくない場合に指定されたアドレスにジャンプする条件分岐命令。
*   **`JEQ` (Jump if Equal)**: 比較結果が等しい場合に指定されたアドレスにジャンプする条件分岐命令。
*   **スタックバリア (Stack Barrier)**: Goランタイムにおけるスタックバリアは、ガベージコレクション（GC）やスタックの拡張・縮小、あるいはゴルーチンのプリエンプション（横取り）など、スタックの状態が変化する際に特定の処理をトリガーするためのメカニズムに関連している可能性があります。このコミットの文脈では、`stackBarrier`というアセンブリルーチンが、スタックのアンワインド（関数呼び出しの逆順でのスタックフレームの解放）中に、特定のスタックバリアエントリを正しく処理しているかを確認するための健全性チェックを行っていたと推測されます。

## 技術的詳細

このコミットは、`amd64`アーキテクチャにおけるGoランタイムの`stackBarrier`アセンブリルーチン内の健全性チェックの論理的な誤りを修正しています。

`stackBarrier`ルーチンは、スタックバリア配列から`savedLRPtr`（保存されたリンクレジスタへのポインタ）と`savedLRVal`（保存されたリンクレジスタの値）を読み出しています。その後、`savedLRPtr`が指すアドレスと現在のスタックポインタ`SP`を比較することで、スタックの整合性を確認しようとしていました。

問題は以下の2点でした。

1.  **`savedLRPtr`のオフセット**: `stackBarrier`ルーチンが呼び出される直前には、`RET`命令が実行されています。`RET`命令は、スタックからリターンアドレス（8バイト）をポップし、その結果`SP`レジスタの値が8だけ増加します。したがって、`savedLRPtr`が指すアドレスは、`RET`命令実行後の`SP`の値よりも8バイト小さいはずです。元のコードではこのオフセットが考慮されておらず、`savedLRPtr == SP`という誤った比較が行われていました。
2.  **条件分岐の論理反転**: 健全性チェックの目的は、`savedLRPtr`と`SP`が期待される関係にあることを確認することです。期待される関係が成立しない場合に異常として処理を中断するか、エラーを報告すべきです。元のコードでは`CMPQ R8, SP`の後に`JNE 2(PC)`（等しくない場合にジャンプ）が続いていました。これは、`R8`と`SP`が等しくない場合に異常と判断してジャンプするという意味になります。しかし、正しいオフセットを考慮すると、`R8`と`SP`は「等しい」ことが期待される状態です。したがって、期待される状態が成立した場合にジャンプ（またはスキップ）し、成立しない場合にエラーを発生させるべきでした。この場合、`JEQ`（等しい場合にジャンプ）を使用するのが適切です。

修正は、これらの2つの誤りを直接的に解決しています。まず、`savedLRPtr`を保持する`R8`レジスタに8を加算することで、`RET`命令による`SP`の増加を相殺し、正しい比較ができるようにします。次に、条件分岐命令を`JNE`から`JEQ`に変更することで、健全性チェックの論理を反転させ、期待される状態（`R8`と`SP`が等しい）が成立した場合に正常なパスを継続するように修正しています。

この修正により、`stackBarrier`の健全性チェックが意図した通りに機能し、スタック管理における潜在的な問題を早期に検出できるようになります。

## コアとなるコードの解説

変更されたアセンブリコードのセクションは、`runtime·stackBarrier`関数内の健全性チェック部分です。

1.  **`MOVQ stkbar_savedLRPtr(DX)(BX*1), R8`**:
    *   `stkbar_savedLRPtr`は、スタックバリア構造体内の`savedLRPtr`フィールドへのオフセットを示します。
    *   `DX`と`BX`レジスタは、スタックバリア配列内の特定のエントリを指すベースアドレスとインデックス計算に使用されます。
    *   この命令は、スタックバリア配列の現在のエントリから`savedLRPtr`の値を読み出し、`R8`レジスタに格納します。`savedLRPtr`は、`stackBarrier`が呼び出される前のリターンアドレスがスタックにプッシュされた位置を指すポインタです。

2.  **`MOVQ stkbar_savedLRVal(DX)(BX*1), BX`**:
    *   同様に、`stkbar_savedLRVal`は`savedLRVal`フィールドへのオフセットです。
    *   この命令は、スタックバリア配列の現在のエントリから`savedLRVal`の値を読み出し、`BX`レジスタに格納します。これは、実際にスタックに保存されていたリターンアドレスの値です。

3.  **`// Assert that we're popping the right saved LR.`**:
    *   このコメントは、続くコードが「正しい保存されたLRをポップしていることをアサートする」ための健全性チェックであることを示しています。

4.  **`+	ADDQ	$8, R8`**:
    *   **追加された行**: `R8`レジスタ（`savedLRPtr`の値）に8バイトを加算します。
    *   これは、`RET`命令がスタックからリターンアドレス（8バイト）をポップし、その結果`SP`が8バイト増加することを考慮した修正です。この加算により、`R8`は`RET`命令実行後の`SP`と同じアドレスを指すようになります。

5.  **`	CMPQ	R8, SP`**:
    *   `R8`レジスタ（修正後の`savedLRPtr`）と`SP`レジスタ（現在のスタックポインタ）の値を比較します。
    *   この比較は、`savedLRPtr`が指すアドレスが、`RET`命令実行後の`SP`と一致しているかを確認するためのものです。一致していれば、スタックの整合性が保たれていることを意味します。

6.  **`-	JNE	2(PC)`**:
    *   **削除された行**: 比較結果が等しくない場合（`R8 != SP`）に、現在のプログラムカウンタ（`PC`）から2バイト先にジャンプします。
    *   これは誤ったロジックでした。期待される状態は`R8 == SP`であるため、等しくない場合にジャンプすると、正常なケースでジャンプしてしまい、異常なケースを見逃す可能性がありました。

7.  **`+	JEQ	2(PC)`**:
    *   **追加された行**: 比較結果が等しい場合（`R8 == SP`）に、現在のプログラムカウンタ（`PC`）から2バイト先にジャンプします。
    *   これは正しいロジックです。`R8`と`SP`が期待通りに等しい場合、健全性チェックは成功とみなされ、次の命令（`MOVL $0, 0`）をスキップして、`stackBarrier`の残りの処理に進みます。もし等しくない場合は、ジャンプせずに次の命令（`MOVL $0, 0`）が実行され、これは通常、パニックを引き起こすための命令（無効なアドレスへの書き込みなど）であり、ランタイムエラーとして報告されます。

8.  **`	MOVL	$0, 0`**:
    *   この命令は、`JEQ`（修正前は`JNE`）の条件が満たされなかった場合に実行されます。
    *   `0`番地（NULLアドレス）に`0`を書き込もうとする命令であり、通常はセグメンテーション違反を引き起こし、プログラムをクラッシュさせます。これは、健全性チェックが失敗した（スタックの整合性が崩れている）ことを示すための意図的なパニックメカニズムです。

9.  **`	ADDQ	$1, g_stkbarPos(CX)`**:
    *   健全性チェックが成功した場合に実行される命令。
    *   `g_stkbarPos`は、グローバルなスタックバリア位置カウンタのようなもので、現在のスタックバリアがヒットしたことを記録するために1増加させます。

この修正により、`stackBarrier`ルーチンは、スタックのアンワインド中に`savedLRPtr`と`SP`の間の正しい関係を正確に検証できるようになり、Goランタイムの安定性と信頼性が向上します。

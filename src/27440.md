## 変更の背景

この変更の主な背景は、Goコンパイラおよびリンカの内部コードの品質と保守性の向上です。`LSym`構造体内のいくつかのフィールドが、論理的な真偽値（フラグ）を表すにもかかわらず、`uint8`型で宣言されていました。`uint8`は8ビットの符号なし整数型であり、0または1以外の値も取り得ます。しかし、これらのフィールドは実際にはブーリアンとしてのみ使用されており、0を偽、1を真として扱っていました。

このような`uint8`をブーリアンとして使用する慣習は、以下のような問題を引き起こす可能性があります。

1.  **可読性の低下**: `if s.Cfunc != 0`のようなコードは、`s.Cfunc`がブーリアンであることを直接的に示しません。`if s.Cfunc`と書く方が、そのフィールドが論理的な状態を表していることが明確になります。
2.  **意図の不明確さ**: `uint8`型であるため、将来的に0と1以外の値が誤って割り当てられる可能性があり、予期せぬバグにつながるリスクがあります。`bool`型を使用することで、コンパイラがこの種の誤用を検出できます。
3.  **型安全性**: `bool`型は、その名の通り真偽値のみを表現するための型であり、Goの型システムによる安全性を最大限に活用できます。

このコミットは、これらの問題を解決し、コードの意図をより明確にし、将来的なメンテナンスを容易にすることを目的としています。コミットメッセージに「No performance regression measurable」とあるように、この型変更がコンパイラやリンカのパフォーマンスに悪影響を与えないことが確認されています。

## 前提知識の解説

### Goコンパイラ/リンカの構造

Goのツールチェインは、ソースコードを最終的な実行可能ファイルに変換する複雑なプロセスを担っています。
-   **`cmd/compile`**: Goのコンパイラ本体です。Goのソースコードを中間表現（ASTなど）に変換し、最終的には各ターゲットアーキテクチャ（x86, ARMなど）のアセンブリコードに変換します。
-   **`cmd/internal/obj`**: コンパイラとリンカの間で共有される、オブジェクトファイルフォーマットやシンボル表現に関する共通の定義とユーティリティを提供します。アセンブラのバックエンドもこのパッケージに含まれます。
-   **`cmd/link`**: Goのリンカ本体です。コンパイラによって生成されたオブジェクトファイルや、Goランタイム、標準ライブラリのオブジェクトファイルを結合し、実行可能ファイルを生成します。

### `LSym`構造体

`LSym`（Linker Symbol）は、`cmd/internal/obj/link.go`で定義されている構造体で、Goのリンカが扱うシンボル（関数、グローバル変数、型情報など）の情報を保持します。プログラム内の各エンティティは、リンカによって`LSym`インスタンスとして表現され、その属性（名前、型、サイズ、各種フラグなど）がこの構造体に格納されます。

### `uint8`と`bool`

-   **`uint8`**: 0から255までの符号なし整数を格納できる8ビットの整数型です。メモリ効率が良いことから、過去にはブーリアンフラグの集合をビットフィールドとして表現したり、単一のブーリアン値を0または1で表現するために使われることがありました。
-   **`bool`**: `true`または`false`の2つの値のみを取るブーリアン型です。Goでは、ブーリアン値を表現する際には`bool`型を使用することが推奨されており、これによりコードの意図が明確になり、型安全性が保証されます。

### `LSym`のブーリアンフィールドの意味

このコミットで`uint8`から`bool`に変更された`LSym`のフィールドは、それぞれ以下のような意味を持ちます。

-   **`Dupok`**: (Duplicate OK) このシンボルが複数の場所で定義されても問題ないかを示すフラグ。例えば、弱いシンボル（weak symbol）などで使用されます。
-   **`Cfunc`**: このシンボルがC言語の関数として扱われるべきかを示すフラグ。GoランタイムがC言語の関数を呼び出す際や、C言語からGoの関数を呼び出す際に、スタック管理などの挙動が変わるため重要です。特にスタック分割の挙動に影響します。
-   **`Nosplit`**: この関数がスタック分割（stack splitting）を必要としないことを示すフラグ。Goの関数は通常、必要に応じてスタックを自動的に拡張しますが、一部の低レベルな関数（特にランタイム内部の関数）ではスタック分割が不要、あるいは望ましくない場合があります。
-   **`Leaf`**: この関数がリーフ関数（leaf function）、つまり他の関数を呼び出さない関数であることを示すフラグ。コンパイラはリーフ関数に対して最適化を適用できる場合があります。
-   **`Seenglobl`**: このシンボルが既にグローバルシンボルとして処理されたかを示すフラグ。リンカがシンボルテーブルを構築する際に、重複処理を防ぐために使用されます。
-   **`Onlist`**: このシンボルがリンカの処理リスト（例えば、データシンボルやテキストシンボルのリスト）に現在含まれているかを示すフラグ。リンカの内部的な状態管理に使用されます。

### スタック分割 (Stack Splitting)

Goランタイムの重要な機能の一つにスタック分割があります。Goの関数は、固定サイズの小さなスタックで開始し、必要に応じて自動的にスタックを拡張します。これにより、スタックオーバーフローを防ぎつつ、メモリ使用量を効率的に保つことができます。関数が呼び出される前に、現在のスタックが十分なサイズを持っているかチェックし、足りなければ新しい、より大きなスタックに切り替える処理が行われます。`Cfunc`や`Nosplit`フラグは、このスタック分割の挙動に直接影響を与えます。例えば、`Nosplit`が設定された関数はスタックチェックをスキップします。

### ベンチマーク結果の解釈

コミットメッセージに含まれるベンチマーク結果は、変更がパフォーマンスに与える影響を評価したものです。
-   `name`: ベンチマークの対象（`Template`, `GoTypes`, `Compiler`はGoのコンパイルプロセスにおける異なるフェーズや側面を測定していると考えられます）。
-   `old time/op`: 変更前の操作あたりの平均時間。
-   `new time/op`: 変更後の操作あたりの平均時間。
-   `delta`: 変更による時間の増減率。
-   `p`: 統計的有意性を示すp値。一般的にp値が0.05未満であれば、その差は統計的に有意であると判断されます。
-   `n`: ベンチマークの実行回数。

この結果では、`Template`でわずかな改善が見られますが、`GoTypes`と`Compiler`では`~`（有意な差なし）とされており、全体としてパフォーマンスの回帰（低下）は測定されなかったと結論付けられています。これは、`uint8`から`bool`への型変更が、コンパイラやリンカの実行速度に実質的な影響を与えなかったことを示しています。

## 技術的詳細

このコミットの技術的な詳細としては、`LSym`構造体のフィールド型変更と、それに伴うコードベース全体での参照箇所の更新が挙げられます。

1.  **`LSym`構造体の定義変更**:
    `src/cmd/internal/obj/link.go`において、以下のフィールドが`uint8`から`bool`に変更されました。
    ```go
    // 変更前
    // Dupok     uint8
    // Cfunc     uint8
    // Nosplit   uint8
    // Leaf      uint8
    // Seenglobl uint8
    // Onlist    uint8

    // 変更後
    Dupok     bool
    Cfunc     bool
    Nosplit   bool
    Leaf      bool
    Seenglobl bool
    Onlist    bool
    ```
    この変更により、これらのフィールドはGoの型システムによって真偽値としてのみ扱われるようになります。

2.  **条件式の更新**:
    `uint8`型がブーリアンとして使用されていた箇所では、`!= 0`という比較演算子が使われていました。`bool`型への変更に伴い、これらの条件式はより簡潔でGoらしい表現に更新されました。
    -   `if s.Cfunc != 0` は `if s.Cfunc` に変更。
    -   `if s.Dupok != 0` は `if s.Dupok` に変更。
    同様に、`s.Leaf = 1`のような代入は`s.Leaf = true`に変更されました。

3.  **シリアライズ/デシリアライズロジックの更新 (`objfile.go`)**:
    `src/cmd/internal/obj/objfile.go`は、リンカがオブジェクトファイルを読み書きする際のロジックを含んでいます。`LSym`構造体のフィールドが`uint8`から`bool`に変更されたため、これらのブーリアンフラグをオブジェクトファイルに書き込む際（シリアライズ）と、オブジェクトファイルから読み込む際（デシリアライズ）の処理も更新が必要でした。
    以前は`int64(s.Dupok)`のように`uint8`値を直接`int64`にキャストして書き込んでいましたが、`bool`型になったことで、明示的にビットフラグを構築するロジックが導入されました。
    例えば、`Dupok`フィールドのシリアライズは以下のように変更されました。
    ```go
    // 変更前
    // flags := int64(s.Dupok)

    // 変更後
    flags := int64(0)
    if s.Dupok {
        flags |= 1
    }
    ```
    これにより、`bool`値が適切に整数フラグの一部としてエンコードされ、オブジェクトファイルに保存されるようになります。他のブーリアンフィールドについても同様のビット演算によるフラグ管理が導入されています。

この変更は、Goのコンパイラとリンカの内部実装において、データ型のセマンティクスをより正確に反映させるための重要なステップです。パフォーマンスへの影響がないことを確認しつつ、コードの品質と保守性を向上させています。

## コアとなるコードの解説

### `src/cmd/internal/obj/link.go`の変更

このファイルでは、`LSym`構造体の定義が直接変更されています。`Dupok`, `Cfunc`, `Nosplit`, `Leaf`, `Seenglobl`, `Onlist`といったフィールドが、それぞれ`uint8`から`bool`型に置き換えられました。これは、これらのフィールドが真偽値（フラグ）としてのみ機能するという設計意図をコードレベルで明確にするための最も根本的な変更です。これにより、これらのフィールドに`true`または`false`以外の値が誤って代入されることをコンパイラが防ぐことができます。

### `src/cmd/compile/internal/gc/pgen.go`の変更

`pgen.go`では、`LSym`の`Dupok`および`Cfunc`フィールドへの代入方法が変更されています。
-   `ls.Dupok = 1` が `ls.Dupok = true` に。
-   `ptxt.From.Sym.Cfunc = 1` が `ptxt.From.Sym.Cfunc = true` に。
これは、`uint8`型で0/1を代入していた箇所を、`bool`型で`true`/`false`を代入するように修正したものです。これにより、コードの可読性が向上し、フィールドの役割がより直感的に理解できるようになります。

### `src/cmd/internal/obj/arm/obj5.go`の変更（および他のアーキテクチャ固有ファイル）

`obj5.go`（ARMアーキテクチャのアセンブラバックエンド）や他のアーキテクチャ固有のファイル（`arm64/obj7.go`, `mips/obj0.go`, `ppc64/obj9.go`, `x86/obj6.go`）では、`LSym`のブーリアンフィールドを参照する条件式が変更されています。
-   `if ctxt.Cursym.Cfunc != 0` が `if ctxt.Cursym.Cfunc` に。
-   `if cursym.Text.Mark&LEAF != 0` の後に続く `cursym.Leaf = 1` が `cursym.Leaf = true` に。
これらの変更は、`uint8`型をブーリアンとして扱う際の`!= 0`という比較を、`bool`型を直接評価する形に簡略化したものです。これはGoのイディオムに沿った変更であり、コードの意図をより明確にします。

### `src/cmd/internal/obj/objfile.go`の変更

このファイルでは、`LSym`構造体のフィールドをオブジェクトファイルに書き込む（シリアライズする）際のロジックが更新されています。`uint8`から`bool`への型変更は、ファイルフォーマットの互換性を維持しつつ、ブーリアン値を適切にエンコードする必要があるため、この部分の変更が最も複雑です。
-   `Dupok`フィールドのシリアライズでは、以前は`int64(s.Dupok)`と直接キャストしていましたが、変更後は`flags := int64(0)`で初期化し、`if s.Dupok { flags |= 1 }`のように、`bool`値に基づいてビットフラグを立てる方式に変更されました。
-   `Nosplit`, `Leaf`, `Cfunc`についても同様に、`bool`値からビットフラグを構築し、それを`int64`として書き込むロジックが導入されています。例えば、`Nosplit`は単独で`wrint(b, 1)`または`wrint(b, 0)`として書き込まれ、`Leaf`と`Cfunc`は他のフラグと共にビットマスクとしてエンコードされます。

これらの変更は、`bool`型が直接整数値として扱えないため、シリアライズ時には明示的に整数フラグに変換し、デシリアライズ時にはその逆の処理を行う必要があることを示しています。これにより、内部的なデータ表現の変更が、外部のファイルフォーマットに与える影響を最小限に抑えつつ、型安全性を向上させています。

# [インデックス 27929] ファイルの概要

このコミットは、Goコンパイラとランタイムにおけるマップ（`map`）の大きな値の取り扱い方法を変更するものです。特に、マップにキーが存在しない場合に返されるゼロ値のメモリ管理メカニズムを改善し、パフォーマンスとコードの複雑さを軽減することを目的としています。

    cmd/compile: change the way we handle large map values
    
    mapaccess{1,2} returns a pointer to the value. When the key
    is not in the map, it returns a pointer to zeroed memory.

    dynamically allocates zeroed memory for this purpose. It is ugly
    code and requires an atomic.Load in a bunch of places we'd rather
    not have it.

    large return values pass in a pointer to zeroed memory that

    for the large value acccesses, plus a bit of bss space.

    all the tricks to make the right size zero value were done by the
    linker. That scheme broke in the presence of dyamic linking.
    The scheme in this CL works even when dynamic linking.

## 元コミット内容

このコミットは、Goのコンパイラ（`cmd/compile`）とランタイム（`src/runtime`）におけるマップの大きな値の処理方法を変更します。具体的には、マップからキーを検索し、そのキーが存在しない場合にゼロ値が返される際のメモリ管理メカニズムを改善します。

以前のシステムでは、`mapaccess{1,2}`（マップからの値の読み出しを行うランタイム関数）がキーを見つけられなかった場合、動的にゼロ初期化されたメモリを割り当ててそのポインタを返していました。この動的割り当ては複雑で、多くの場所で`atomic.Load`操作を必要とし、コードの可読性とパフォーマンスに悪影響を与えていました。

新しいアプローチでは、大きな値（1024バイトを超える）を期待する`mapaccess{1,2}`の呼び出し元が、あらかじめゼロ初期化されたメモリへのポインタを`mapaccess`関数に渡すように変更されます。これにより、`mapaccess`関数はキーが見つからない場合に、この渡されたゼロ値メモリのポインタを直接返すことができます。この変更により、不要な`atomic.Load`操作が回避され、コードが簡素化され、パフォーマンスが向上します。

この変更は、動的リンク環境でも正しく機能するように設計されており、過去のGoバージョン（1.4および1.5）でリンカがゼロ値のサイズ調整を行っていた際に動的リンクで問題が発生した経験を踏まえています。

## 変更の背景

Goのマップは、キーが存在しない場合にその型のゼロ値を返します。例えば、`m := make(map[string]int)`とした場合、`m["nonexistent"]`は`0`を返します。これは、値が構造体や配列のような大きな型である場合でも同様です。

以前の実装では、マップの値が大きなサイズ（例えば数KBの構造体や配列）である場合、キーが見つからなかったときに、その大きなゼロ値を格納するためのメモリをランタイムが動的に確保し、ゼロ初期化していました。この動的なメモリ確保とゼロ初期化のプロセスは、以下の問題を引き起こしていました。

1.  **複雑なコード**: 動的にサイズを調整し、ゼロ初期化されたメモリを管理するためのロジックが複雑でした。
2.  **パフォーマンスオーバーヘッド**: 特に、`zeroptr`というゼロ値メモリへのポインタを管理するために`atomic.Load`操作が頻繁に必要とされていました。`atomic.Load`は、通常のメモリ読み出しよりもコストが高い操作であり、マップアクセス全体のパフォーマンスに影響を与えていました。
3.  **動的リンクの問題**: 過去には、リンカがゼロ値のサイズ調整を行うアプローチが試みられましたが、これは動的リンク環境で問題が発生することが判明していました。

このコミットは、これらの問題を解決し、特に大きな値を持つマップのアクセス性能を向上させ、ランタイムコードの複雑さを軽減することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoの概念と内部実装に関する知識が必要です。

1.  **Goのマップ（`map`）**:
    *   Goのマップはハッシュテーブルとして実装されています。
    *   `map[KeyType]ValueType`のように宣言され、キーと値のペアを格納します。
    *   マップからキーを検索する際、キーが存在しない場合は`ValueType`のゼロ値が返されます。例えば、`map[string]int`であれば`0`、`map[string]struct{A int}`であれば`struct{A int}{A: 0}`が返されます。
    *   マップアクセスには、単一の値を取得する`v := m[key]`形式と、値と存在フラグを取得する`v, ok := m[key]`形式があります。これらはそれぞれランタイム内部で`mapaccess1`および`mapaccess2`系の関数にコンパイルされます。

2.  **ゼロ値（Zero Value）**:
    *   Goの各型には「ゼロ値」があります。これは、変数が宣言されたが明示的に初期化されていない場合に割り当てられるデフォルト値です。
    *   数値型は`0`、ブール型は`false`、文字列型は`""`、ポインタ、関数、インターフェース、スライス、チャネル、マップ型は`nil`、構造体や配列は各要素のゼロ値で構成されます。
    *   マップからキーが見つからない場合にゼロ値が返されるのは、この言語仕様の一部です。

3.  **`unsafe.Pointer`**:
    *   Goの`unsafe`パッケージは、型安全性をバイパスして任意の型へのポインタを扱うことを可能にします。
    *   `unsafe.Pointer`は、任意の型のポインタと`uintptr`（整数型）の間で変換可能であり、メモリを直接操作する低レベルなコードで利用されます。
    *   ランタイムやコンパイラの内部では、パフォーマンスや特定のメモリレイアウト要件のために`unsafe.Pointer`が頻繁に使用されます。

4.  **`atomic`操作**:
    *   `sync/atomic`パッケージは、アトミックな（不可分な）操作を提供します。これは、複数のゴルーチンが同時に共有メモリにアクセスする際に、データ競合を防ぐために使用されます。
    *   `atomic.Loadp`は、`unsafe.Pointer`型のアドレスからアトミックに値を読み出す関数です。以前のゼロ値管理では、`zeroptr`へのアクセスにこれが使われていました。

5.  **Goコンパイラの内部構造**:
    *   `cmd/compile/internal/gc`ディレクトリには、Goコンパイラの主要な部分が含まれています。
    *   `walk.go`: 抽象構文木（AST）を走査し、高レベルなGoの構文をランタイム関数呼び出しや低レベルな操作に変換する「ウォーク」処理を行います。マップアクセスもここでランタイム関数に変換されます。
    *   `builtin.go`, `builtin/runtime.go`: ランタイムで提供される組み込み関数の宣言が含まれます。コンパイラはこれらの宣言を利用して、適切なランタイム関数呼び出しを生成します。
    *   `obj.go`: オブジェクトファイルの生成に関連する処理を行います。グローバルシンボルの宣言などもここで行われます。
    *   `reflect.go`: 型情報（リフレクションデータ）の生成に関連する処理が含まれます。`zeroaddr`関数がここに追加されています。

6.  **BSSセクション（Block Started by Symbol）**:
    *   コンパイルされたプログラムのデータセクションの一つで、初期化されていないグローバル変数や静的変数が格納されます。プログラムのロード時にゼロ初期化されることが保証されます。
    *   このコミットでは、大きなゼロ値を格納するための領域としてBSSセクションが利用されます。

## 技術的詳細

このコミットの技術的詳細な変更点は、主に以下の3つの側面から構成されます。

1.  **ランタイムにおけるゼロ値メモリ管理の変更**:
    *   **旧方式**: `src/runtime/hashmap.go`には、`zeroptr`という`unsafe.Pointer`型のアトミック変数と、`zerosize`という`uintptr`型のアトミック変数がありました。`mapzero`関数は、要求されたゼロ値のサイズに応じて`zeroptr`が指すメモリ領域を動的に拡張し、ゼロ初期化していました。この拡張は`persistentalloc`（永続的なメモリ割り当て）を使用して行われ、`atomic.Loadp`で`zeroptr`を読み出す必要がありました。
    *   **新方式**:
        *   `zeroptr`、`zerosize`、`mapzero`関数は削除されました。
        *   代わりに、`src/runtime/hashmap.go`に`const maxZero = 1024`と`var zeroVal [maxZero]byte`という固定サイズのゼロ初期化されたバイト配列が導入されました。これは、比較的小さなゼロ値（1024バイトまで）に対応します。
        *   `mapaccess1`および`mapaccess2`（およびその高速版）関数は、キーが見つからない場合に`unsafe.Pointer(&zeroVal[0])`を直接返すようになりました。これにより、`atomic.Loadp`が不要になります。
        *   大きなゼロ値（1024バイトを超える）に対応するため、新たに`mapaccess1_fat`と`mapaccess2_fat`というランタイム関数が追加されました。これらの関数は、呼び出し元から渡されたゼロ値メモリへのポインタ（`zero unsafe.Pointer`）を受け取ります。もし内部の`mapaccess1`/`mapaccess2`が`zeroVal`のポインタを返した場合、それはキーが見つからなかったことを意味するため、`mapaccess1_fat`/`mapaccess2_fat`は呼び出し元から渡された`zero`ポインタを返します。

2.  **コンパイラにおけるマップアクセスコード生成の変更**:
    *   `src/cmd/compile/internal/gc/walk.go`が変更され、マップアクセス（`OMAP`ノード）の処理ロジックが更新されました。
    *   マップの値のサイズ（`t.Val().Width`）が`maxZero`（1024バイト）以下の場合、コンパイラは引き続き既存の`mapaccess1`または`mapaccess2`系のランタイム関数を呼び出します。
    *   マップの値のサイズが`maxZero`を超える場合、コンパイラは新たに導入された`mapaccess1_fat`または`mapaccess2_fat`関数を呼び出すように変更されました。この際、`zeroaddr(w)`関数（後述）を呼び出して、必要なサイズのゼロ値メモリへのポインタを生成し、それを`mapaccess_fat`関数に引数として渡します。

3.  **コンパイラによる大きなゼロ値メモリの管理**:
    *   `src/cmd/compile/internal/gc/go.go`と`src/cmd/compile/internal/gc/main.go`で、`mappkg`という擬似パッケージと`zerosize`という変数が導入されました。`mappkg`は、マップのゼロ値に関連するシンボルを管理するためのものです。
    *   `src/cmd/compile/internal/gc/reflect.go`に`zeroaddr(size int64) *Node`関数が追加されました。この関数は、指定された`size`以上のゼロ値メモリ領域を指すシンボル（`"zero"`という名前で`mappkg`に属する）のアドレスを返します。
        *   `zerosize`変数は、コンパイル中に遭遇した最大のゼロ値サイズを追跡します。
        *   `Pkglookup("zero", mappkg)`でシンボルを検索し、もし存在しなければ新しい外部シンボルとして定義します。
        *   このシンボルは、最終的にBSSセクションに配置され、プログラム起動時にゼロ初期化されることが保証されます。
    *   `src/cmd/compile/internal/gc/obj.go`では、`zerosize > 0`の場合に`ggloblsym`を呼び出し、`mappkg`の`"zero"`シンボルを`zerosize`のサイズでグローバルシンボルとして宣言します。これにより、リンカがこのシンボルに対応するBSS領域を確保します。

この新しいスキームにより、ランタイムは動的なメモリ割り当てとアトミック操作のオーバーヘッドを回避し、コンパイラが静的にゼロ値メモリへのポインタを生成して渡すことで、効率的な大きなマップ値のゼロ値処理を実現しています。特に、`atomic.Load`が不要になったことで、マップアクセスのホットパスから同期オーバーヘッドが削減されます。

+// zeroaddr returns the address of a symbol with at least
+// size bytes of zeros.
+func zeroaddr(size int64) *Node {
+	if size >= 1<<31 {
+		Fatalf("map value too big %d", size)

## コアとなるコードの解説

このコミットの核心は、Goのマップがキーを見つけられなかった場合に返すゼロ値のメモリ管理戦略を根本的に変更した点にあります。

### `src/runtime/hashmap.go` の変更

*   **`zeroptr`と`mapzero`の削除**: 以前は、`zeroptr`というポインタが動的に拡張可能なゼロ値メモリ領域を指していました。`mapzero`関数は、必要に応じてこの領域を大きくし、ゼロ初期化する役割を担っていました。この動的な管理は、`atomic.Loadp`のようなアトミック操作を必要とし、オーバーヘッドの原因となっていました。これらの要素が完全に削除されました。
*   **`zeroVal`配列の導入**: 代わりに、`const maxZero = 1024`と`var zeroVal [maxZero]byte`が導入されました。これは、最大1024バイトまでのゼロ値を格納できる静的なバイト配列です。この配列はBSSセクションに配置されるため、プログラム起動時に自動的にゼロ初期化されます。これにより、動的な割り当てやアトミック操作が不要になります。
*   **`mapaccess1`/`mapaccess2`の簡素化**: キーが見つからない場合、これらの関数は直接`unsafe.Pointer(&zeroVal[0])`を返すようになりました。これは、`zeroVal`配列の先頭アドレスを指すポインタであり、常にゼロ初期化されたメモリを指します。
*   **`mapaccess1_fat`/`mapaccess2_fat`の追加**: 1024バイトを超える大きな値の場合、`zeroVal`配列では対応できません。このため、これらの新しい関数が導入されました。これらの関数は、コンパイラが生成したコードから、あらかじめゼロ初期化されたメモリ領域へのポインタ（`zero`引数）を受け取ります。もし、通常の`mapaccess1`/`mapaccess2`が`zeroVal`のポインタを返した場合（つまりキーが見つからなかった場合）、`mapaccess_fat`関数は代わりに呼び出し元から渡された`zero`ポインタを返します。これにより、ランタイムは大きなゼロ値のメモリを動的に管理する必要がなくなります。

### `src/cmd/compile/internal/gc/walk.go` の変更

*   **条件付きランタイム関数呼び出し**: コンパイラの`walk`フェーズで、マップアクセス（`OMAP`ノード）が処理される際に、マップの値のサイズ（`t.Val().Width`）がチェックされます。
    *   値のサイズが1024バイト以下の場合、コンパイラは従来の`mapaccess1`または`mapaccess2`系のランタイム関数を呼び出します。
    *   値のサイズが1024バイトを超える場合、コンパイラは新しく追加された`mapaccess1_fat`または`mapaccess2_fat`関数を呼び出します。この際、`zeroaddr(w)`関数を使って、必要なサイズのゼロ値メモリへのポインタを生成し、それを`mapaccess_fat`関数の追加引数として渡します。

### `src/cmd/compile/internal/gc/reflect.go` の `zeroaddr` 関数

*   この関数は、コンパイル時に遭遇した最大のゼロ値サイズを`zerosize`変数に記録します。
*   `mappkg`という擬似パッケージに属する`"zero"`という名前のグローバルシンボルを生成または参照します。このシンボルは、最終的にBSSセクションに配置され、プログラム起動時にゼロ初期化される大きなメモリ領域を表します。
*   `zeroaddr`は、このグローバルシンボルへのアドレスを指すASTノードを返します。コンパイラは、このノードを使って`mapaccess_fat`関数にゼロ値メモリのポインタを渡します。

この一連の変更により、Goのマップにおけるゼロ値の取り扱いが、動的な割り当てとアトミック操作から、静的なBSSセクションとコンパイラによるポインタ渡しへと移行しました。これにより、特に大きな値を持つマップのアクセス性能が向上し、ランタイムのコードベースが簡素化されました。

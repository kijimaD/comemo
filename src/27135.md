## 変更の背景

このコミットの背景には、GoコンパイラのSSAバックエンドにおける最適化、特に共通部分式除去（CSE）の効率化があります。以前の実装では、ローカル変数（`PAUTO`）のアドレスを取得する際（`OpAddr`操作）、毎回新しい`ssa.AutoSymbol`インスタンスが生成されていました。これにより、たとえ同じローカル変数のアドレスを複数回取得するコードがあったとしても、コンパイラはそれらを異なるシンボルとして認識し、共通部分式として除去することができませんでした。

コミットメッセージの削除されたコメント部分には、以前の挙動に関する懸念が示されています。

```
// We need to regenerate the address of autos
// at every use. This prevents LEA instructions
// from occurring before the corresponding VarDef
// op and confusing the liveness analysis into thinking
// the variable is live at function entry.
// TODO: I'm not sure if this really works or we're just
// getting lucky. We might need a real dependency edge
// between vardef and addr ops.
```

このコメントは、以前は`PAUTO`変数のアドレスを毎回再生成する必要があった理由として、`LEA`命令が`VarDef`操作の前に発生するのを防ぎ、生存期間解析（liveness analysis）が変数を関数エントリー時に「生きている」と誤認するのを避けるためだと説明しています。しかし、このアプローチが本当に正しいのか、あるいは単に偶然うまくいっているだけなのかという疑問も呈されており、`VarDef`と`OpAddr`の間に真の依存関係エッジが必要かもしれないと示唆しています。

このコミットは、この問題に対するより洗練された解決策として、`ssa.AutoSymbol`の再利用を導入しました。これにより、同じローカル変数を参照する`OpAddr`操作が共通部分式として認識され、CSEによって最適化される道が開かれました。結果として、生成されるコードの効率が向上し、コンパイラの内部的な整合性も改善されることが期待されます。

## 前提知識の解説

### GoコンパイラのSSAバックエンド

Goコンパイラは、ソースコードを中間表現に変換し、様々な最適化を適用してから最終的な機械語コードを生成します。その中間表現の一つがSSA（Static Single Assignment）形式です。SSA形式では、各変数が一度だけ代入されるという特性を持ち、これによりデータフロー解析や最適化が容易になります。GoコンパイラのSSAバックエンドは、ASTからSSA形式への変換、そしてCSE、Dead Code Elimination（DCE）、Constant Foldingなどの多くの最適化パスを実行します。

### PAUTO (Auto Symbols)

`PAUTO`は、Goコンパイラ内部で「自動変数」または「ローカル変数」を指すシンボルタイプです。これらは関数内で宣言され、その関数のスタックフレーム上に割り当てられる変数です。

### OpAddr

`OpAddr`は、SSA形式における操作（オペレーション）の一つで、指定された変数のメモリアドレスを取得する操作を表します。Go言語では、変数のアドレスを`&`演算子を使って取得できます（例: `&x`）。コンパイラはこれを`OpAddr`として表現します。

### LEA (Load Effective Address)

`LEA`は、主にx86アーキテクチャの命令セットに見られる命令で、「実効アドレスをロードする」という意味です。これは、メモリから値を読み込むのではなく、指定されたオペランドのアドレスを計算し、そのアドレス値をレジスタに格納します。コンパイラは、変数のアドレスを計算する際に`LEA`命令を生成することがあります。

### VarDef

`VarDef`は、SSA形式における操作の一つで、変数が定義される（メモリ上に割り当てられる）時点を示します。これは、変数の生存期間解析において重要なマーカーとなります。

### Liveness Analysis (生存期間解析)

生存期間解析は、コンパイラのデータフロー解析の一種で、プログラムの各ポイントにおいて、どの変数が将来使用される可能性があるか（「生きている」か）を判断します。変数が「生きている」と判断された場合、その変数はメモリ上に保持される必要があります。この解析は、レジスタ割り当てやスタックフレームの最適化に不可欠です。

### CSE (Common Subexpression Elimination)

共通部分式除去（CSE）は、コンパイラの最適化手法の一つです。プログラム内で同じ計算が複数回行われている場合、その計算を一度だけ実行し、その結果を再利用することで、冗長な計算を排除し、実行速度を向上させます。例えば、`a = (b + c) * 2`と`d = (b + c) * 3`というコードがあった場合、`(b + c)`という共通部分式を一度だけ計算し、その結果を`a`と`d`の両方に利用します。

### ssa.Value

`ssa.Value`は、GoコンパイラのSSA形式において、計算結果や変数の値を表す基本的な単位です。各`ssa.Value`は、特定の操作（`Op`）と引数（`Args`）、型（`Type`）、補助情報（`Aux`）などを持っています。

### ssa.AutoSymbol

`ssa.AutoSymbol`は、SSA形式においてローカル変数（`PAUTO`）を識別するための補助情報（`Aux`）として使用される構造体です。これには、変数の型や元のASTノードへの参照が含まれます。

### s.lookupSymbol

`s.lookupSymbol`は、GoコンパイラのSSA構築フェーズで使用される内部関数で、特定のASTノードと補助情報（`Aux`）に対応する既存のシンボルを検索し、もし存在すればそれを再利用するメカニズムを提供します。存在しない場合は新しいシンボルを生成して登録します。これにより、同じ論理的なエンティティ（この場合はローカル変数）がSSA形式で一意のシンボルとして扱われるようになります。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSA構築フェーズにおけるローカル変数（`PAUTO`）のアドレス取得（`OpAddr`）の扱いの変更です。

**変更前:**
`ssa.go`の`addr`関数内で`PAUTO`型のノードのアドレスを取得する際、毎回新しい`ssa.AutoSymbol`インスタンスが作成されていました。

```go
// 変更前のコードスニペット (削除された部分)
case PAUTO:
    // We need to regenerate the address of autos
    // at every use. This prevents LEA instructions
    // from occurring before the corresponding VarDef
    // op and confusing the liveness analysis into thinking
    // the variable is live at function entry.
    // TODO: I'm not sure if this really works or we're just
    // getting lucky. We might need a real dependency edge
    // between vardef and addr ops.
    aux := &ssa.AutoSymbol{Typ: n.Type, Node: n} // 毎回新しいシンボルを生成
    return s.newValue1A(ssa.OpAddr, t, aux, s.sp)
```

この「毎回新しいシンボルを生成する」という挙動は、同じローカル変数`x`に対して`&x`という操作が複数回行われた場合でも、それぞれの`OpAddr`操作が異なる`ssa.AutoSymbol`インスタンスを参照することになります。結果として、コンパイラの共通部分式除去（CSE）パスは、これらの`OpAddr`操作が同じ値を計算していると認識できず、冗長なアドレス計算が残ってしまう可能性がありました。

また、削除されたコメントが示唆するように、この挙動は`LEA`命令の生成タイミングと生存期間解析（liveness analysis）との間の潜在的な問題を回避するための「回避策」であった可能性があります。`VarDef`（変数の定義）の前に`LEA`（アドレス計算）が発生すると、生存期間解析が変数を誤って「生きている」と判断し、最適化の妨げになる、あるいは誤ったコードを生成する可能性があったため、毎回新しいシンボルを生成することで、この問題を間接的に回避しようとしていたと考えられます。しかし、このアプローチはCSEを阻害し、また根本的な解決策ではないという認識があったようです。

**変更後:**
新しい実装では、`s.lookupSymbol`関数を使用して、既存の`ssa.AutoSymbol`インスタンスを検索し、再利用するようになりました。

```go
// 変更後のコードスニペット
case PAUTO:
    aux := s.lookupSymbol(n, &ssa.AutoSymbol{Typ: n.Type, Node: n}) // 既存のシンボルを検索・再利用
    return s.newValue1A(ssa.OpAddr, t, aux, s.sp)
```

`s.lookupSymbol`は、特定のASTノード（`n`）と、そのノードに対応する`ssa.AutoSymbol`の「テンプレート」を受け取ります。この関数は、既に同じASTノードに対応する`ssa.AutoSymbol`が登録されていればそれを返し、なければ新しい`ssa.AutoSymbol`を作成して登録し、それを返します。

この変更により、同じローカル変数`x`に対する`&x`操作は、常に同じ`ssa.AutoSymbol`インスタンスを参照するようになります。これにより、CSEパスは、これらの`OpAddr`操作が共通の計算であると正しく認識し、冗長なアドレス計算を排除できるようになります。例えば、以下のようなコードがあったとします。

```go
func foo() *int {
    x := 10
    ptr1 := &x
    ptr2 := &x // ptr1とptr2は同じアドレスを指す
    _ = ptr1
    return ptr2
}
```

変更前は`&x`の2つの操作が異なる`ssa.AutoSymbol`を参照していたため、CSEは適用されませんでした。変更後は、両方の`&x`操作が同じ`ssa.AutoSymbol`を参照するため、CSEによって2番目の`&x`操作が除去され、より効率的なコードが生成される可能性があります。

この変更は、コンパイラの最適化能力を向上させるだけでなく、SSA形式の内部表現の一貫性を高め、将来的な最適化や解析の基盤を強化するものです。以前のコメントで示唆されていた「真の依存関係エッジ」の必要性に対する間接的な解決策とも言えるかもしれません。シンボルを再利用することで、同じ論理的なエンティティに対する操作がSSAグラフ上でより明確に表現されるようになります。

## コアとなるコードの解説

変更は`src/cmd/compile/internal/gc/ssa.go`ファイルの`(*state).addr`メソッド内で行われています。このメソッドは、ASTノード`n`のアドレスに対応する`ssa.Value`を生成する役割を担っています。

特に、`n.Op`が`PAUTO`（ローカル変数）である場合の処理が変更されました。

**変更前:**

```go
aux := &ssa.AutoSymbol{Typ: n.Type, Node: n}
```

この行では、ローカル変数`n`のアドレスを取得するたびに、新しい`ssa.AutoSymbol`構造体のインスタンスが作成され、それが`aux`（補助情報）として`OpAddr`操作に渡されていました。これにより、同じローカル変数のアドレスを複数回取得しても、SSA形式上は異なる`ssa.AutoSymbol`が関連付けられるため、CSEが適用されませんでした。

**変更後:**

```go
aux := s.lookupSymbol(n, &ssa.AutoSymbol{Typ: n.Type, Node: n})
```

この行では、`s.lookupSymbol`メソッドが呼び出されています。
- 最初の引数`n`は、アドレスを取得しようとしているローカル変数のASTノードです。
- 2番目の引数`&ssa.AutoSymbol{Typ: n.Type, Node: n}`は、`n`に対応する`ssa.AutoSymbol`の「テンプレート」です。

`s.lookupSymbol`メソッドは、内部的にマップなどを使用して、既に`n`に対応する`ssa.AutoSymbol`が生成されているかをチェックします。
- もし既に存在すれば、その既存の`ssa.AutoSymbol`インスタンスを返します。
- もし存在しなければ、提供されたテンプレート（`&ssa.AutoSymbol{Typ: n.Type, Node: n}`）に基づいて新しい`ssa.AutoSymbol`インスタンスを作成し、それを登録してから返します。

この変更により、同じローカル変数`n`に対して`addr`メソッドが複数回呼び出されても、常に同じ`ssa.AutoSymbol`インスタンスが`aux`として返されるようになります。結果として、`OpAddr`操作が同じ`ssa.AutoSymbol`を参照することになり、コンパイラのCSEパスがこれらの操作を共通部分式として正しく認識し、最適化（冗長なアドレス計算の除去）を実行できるようになります。

削除されたコメントは、以前の挙動が生存期間解析の問題を回避するためのものであった可能性を示唆していますが、この新しいアプローチは、よりクリーンな方法でCSEを可能にし、コンパイラの最適化能力を向上させます。

### Liveness Analysis (生存期間解析)

生存期間解析は、コンパイラのデータフロー解析の一種で、プログラムの各ポイントにおいて、どの変数が将来使用される可能性があるか（「生きている」か）を判断します。変数が「生きている」と判断された場合、その変数はメモリ上に保持される必要があります。この解析は、レジスタ割り当てやスタックフレームの最適化に不可欠です。

### CSE (Common Subexpression Elimination)

共通部分式除去（CSE）は、コンパイラの最適化手法の一つです。プログラム内で同じ計算が複数回行われている場合、その計算を一度だけ実行し、その結果を再利用することで、冗長な計算を排除し、実行速度を向上させます。例えば、`a = (b + c) * 2`と`d = (b + c) * 3`というコードがあった場合、`(b + c)`という共通部分式を一度だけ計算し、その結果を`a`と`d`の両方に利用します。

### ssa.Value

`ssa.Value`は、GoコンパイラのSSA形式において、計算結果や変数の値を表す基本的な単位です。各`ssa.Value`は、特定の操作（`Op`）と引数（`Args`）、型（`Type`）、補助情報（`Aux`）などを持っています。

### ssa.AutoSymbol

`ssa.AutoSymbol`は、SSA形式においてローカル変数（`PAUTO`）を識別するための補助情報（`Aux`）として使用される構造体です。これには、変数の型や元のASTノードへの参照が含まれます。

### s.lookupSymbol

`s.lookupSymbol`は、GoコンパイラのSSA構築フェーズで使用される内部関数で、特定のASTノードと補助情報（`Aux`）に対応する既存のシンボルを検索し、もし存在すればそれを再利用するメカニズムを提供します。存在しない場合は新しいシンボルを生成して登録します。これにより、同じ論理的なエンティティ（この場合はローカル変数）がSSA形式で一意のシンボルとして扱われるようになります。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSA構築フェーズにおけるローカル変数（`PAUTO`）のアドレス取得（`OpAddr`）の扱いの変更です。

**変更前:**
`ssa.go`の`addr`関数内で`PAUTO`型のノードのアドレスを取得する際、毎回新しい`ssa.AutoSymbol`インスタンスが作成されていました。

```go
// 変更前のコードスニペット (削除された部分)
case PAUTO:
    // We need to regenerate the address of autos
    // at every use. This prevents LEA instructions
    // from occurring before the corresponding VarDef
    // op and confusing the liveness analysis into thinking
    // the variable is live at function entry.
    // TODO: I'm not sure if this really works or we're just
    // getting lucky. We might need a real dependency edge
    // between vardef and addr ops.
    aux := &ssa.AutoSymbol{Typ: n.Type, Node: n} // 毎回新しいシンボルを生成
    return s.newValue1A(ssa.OpAddr, t, aux, s.sp)
```

この「毎回新しいシンボルを生成する」という挙動は、同じローカル変数`x`に対して`&x`という操作が複数回行われた場合でも、それぞれの`OpAddr`操作が異なる`ssa.AutoSymbol`インスタンスを参照することになります。結果として、コンパイラの共通部分式除去（CSE）パスは、これらの`OpAddr`操作が同じ値を計算していると認識できず、冗長なアドレス計算が残ってしまう可能性がありました。

また、削除されたコメントが示唆するように、この挙動は`LEA`命令の生成タイミングと生存期間解析（liveness analysis）との間の潜在的な問題を回避するための「回避策」であった可能性があります。`VarDef`（変数の定義）の前に`LEA`（アドレス計算）が発生すると、生存期間解析が変数を誤って「生きている」と判断し、最適化の妨げになる、あるいは誤ったコードを生成する可能性があったため、毎回新しいシンボルを生成することで、この問題を間接的に回避しようとしていたと考えられます。しかし、このアプローチはCSEを阻害し、また根本的な解決策ではないという認識があったようです。

**変更後:**
新しい実装では、`s.lookupSymbol`関数を使用して、既存の`ssa.AutoSymbol`インスタンスを検索し、再利用するようになりました。

```go
// 変更後のコードスニペット
case PAUTO:
    aux := s.lookupSymbol(n, &ssa.AutoSymbol{Typ: n.Type, Node: n}) // 既存のシンボルを検索・再利用
    return s.newValue1A(ssa.OpAddr, t, aux, s.sp)
```

`s.lookupSymbol`は、内部的にマップなどを使用して、既に`n`に対応する`ssa.AutoSymbol`が生成されているかをチェックします。
- もし既に存在すれば、その既存の`ssa.AutoSymbol`インスタンスを返します。
- もし存在しなければ、提供されたテンプレート（`&ssa.AutoSymbol{Typ: n.Type, Node: n}`）に基づいて新しい`ssa.AutoSymbol`インスタンスを作成し、それを登録してから返します。

この変更により、同じローカル変数`n`に対する`addr`メソッドが複数回呼び出されても、常に同じ`ssa.AutoSymbol`インスタンスが`aux`として返されるようになります。結果として、`OpAddr`操作が同じ`ssa.AutoSymbol`を参照することになり、コンパイラのCSEパスがこれらの操作を共通部分式として正しく認識し、最適化（冗長なアドレス計算の除去）を実行できるようになります。

例えば、以下のようなGoコードがあったとします。

```go
func example() *int {
    x := 10
    ptrA := &x
    ptrB := &x // ここで再度 'x' のアドレスが取得される
    _ = ptrA
    return ptrB
}
```

変更前は、`ptrA := &x`と`ptrB := &x`のそれぞれで異なる`ssa.AutoSymbol`が生成されていたため、コンパイラは2つの`OpAddr`操作が異なるものと見なし、両方のアドレス計算を実行していました。

変更後は、`s.lookupSymbol`によって`&x`の2つの操作が同じ`ssa.AutoSymbol`を参照するようになります。これにより、SSA最適化パス（特にCSE）は、2番目の`&x`が最初の`&x`と同じ結果を生成することを発見し、冗長なアドレス計算を排除して、より効率的な機械語コードを生成できるようになります。

この変更は、コンパイラの最適化能力を向上させるだけでなく、SSA形式の内部表現の一貫性を高め、将来的な最適化や解析の基盤を強化するものです。以前のコメントで示唆されていた「真の依存関係エッジ」の必要性に対する間接的な解決策とも言えるかもしれません。シンボルを再利用することで、同じ論理的なエンティティに対する操作がSSAグラフ上でより明確に表現されるようになります。

## コアとなるコードの解説

変更は`src/cmd/compile/internal/gc/ssa.go`ファイルの`(*state).addr`メソッド内で行われています。このメソッドは、ASTノード`n`のアドレスに対応する`ssa.Value`を生成する役割を担っています。

特に、`n.Op`が`PAUTO`（ローカル変数）である場合の処理が変更されました。

**変更前:**

```go
aux := &ssa.AutoSymbol{Typ: n.Type, Node: n}
```

この行では、ローカル変数`n`のアドレスを取得するたびに、新しい`ssa.AutoSymbol`構造体のインスタンスが作成され、それが`aux`（補助情報）として`OpAddr`操作に渡されていました。これにより、同じローカル変数のアドレスを複数回取得しても、SSA形式上は異なる`ssa.AutoSymbol`が関連付けられるため、CSEが適用されませんでした。

**変更後:**

```go
aux := s.lookupSymbol(n, &ssa.AutoSymbol{Typ: n.Type, Node: n})
```

この行では、`s.lookupSymbol`メソッドが呼び出されています。
- 最初の引数`n`は、アドレスを取得しようとしているローカル変数のASTノードです。
- 2番目の引数`&ssa.AutoSymbol{Typ: n.Type, Node: n}`は、`n`に対応する`ssa.AutoSymbol`の「テンプレート」です。

`s.lookupSymbol`メソッドは、内部的にマップなどを使用して、既に`n`に対応する`ssa.AutoSymbol`が生成されているかをチェックします。
- もし既に存在すれば、その既存の`ssa.AutoSymbol`インスタンスを返します。
- もし存在しなければ、提供されたテンプレート（`&ssa.AutoSymbol{Typ: n.Type, Node: n}`）に基づいて新しい`ssa.AutoSymbol`インスタンスを作成し、それを登録してから返します。

この変更により、同じローカル変数`n`に対して`addr`メソッドが複数回呼び出されても、常に同じ`ssa.AutoSymbol`インスタンスが`aux`として返されるようになります。結果として、`OpAddr`操作が同じ`ssa.AutoSymbol`を参照することになり、コンパイラのCSEパスがこれらの操作を共通部分式として正しく認識し、最適化（冗長なアドレス計算の除去）を実行できるようになります。

削除されたコメントは、以前の挙動が生存期間解析の問題を回避するためのものであった可能性を示唆していますが、この新しいアプローチは、よりクリーンな方法でCSEを可能にし、コンパイラの最適化能力を向上させます。

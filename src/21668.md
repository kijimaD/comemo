## 変更の背景

このコミットの背景には、Goランタイムの歴史とコンパイラの進化があります。Goランタイムは元々C言語で書かれていましたが、後にGo言語自体で書き直されました。C言語で書かれていた時代には、特定の算術演算、特に剰余（モジュロ）演算 `X % N` のパフォーマンスを向上させるための「ハック」が用いられていました。

具体的には、`tick % 61 == 0` という条件を判定する際に、除算命令（DIV）よりも乗算命令（MUL）とビットシフトを組み合わせた方が、当時のプロセッサ（特に一部のアーキテクチャ）で高速であるという最適化手法が採用されていました。これは、除算が一般的に乗算よりも多くのCPUサイクルを必要とするためです。

しかし、Goコンパイラが成熟し、より高度な最適化を行うようになった結果、このような手動での最適化は不要になりました。Goコンパイラが `tick % 61 == 0` のような単純な剰余演算を、内部的に効率的な命令シーケンス（乗算やビットシフトなど）に変換できるようになり、開発者が明示的に複雑な式を書く必要がなくなったため、コードの簡素化が可能になりました。

この変更は、コードの可読性を向上させ、将来的なメンテナンスを容易にすることを目的としています。Goコンパイラが賢くなったことで、ランタイムコードから低レベルな最適化の痕跡を取り除くことができた好例と言えます。

## 前提知識の解説

*   **Goランタイム**: Goプログラムの実行を管理するシステムです。ゴルーチンのスケジューリング、メモリ管理（ガベージコレクション）、チャネル通信など、Go言語の並行処理モデルを支える重要な役割を担っています。
*   **ゴルーチン (Goroutine)**: Go言語における軽量な実行スレッドです。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行することも可能です。Goランタイムのスケジューラが、これらのゴルーチンをOSスレッドにマッピングし、効率的に実行します。
*   **ゴルーチン・スケジューラ**: Goランタイムの一部で、多数のゴルーチンを限られた数のOSスレッド上で効率的に実行するための仕組みです。スケジューラは、ゴルーチンをいつ実行し、いつ一時停止し、いつ別のゴルーチンに切り替えるかを決定します。
*   **ローカル実行キューとグローバル実行キュー**: Goスケジューラは、各プロセッサ（P）にローカルな実行キューを持ち、そこにゴルーチンを配置します。また、すべてのプロセッサで共有されるグローバルな実行キューも存在します。ローカルキューが空になった場合や、公平性を保つために、グローバルキューからゴルーチンを取得することがあります。
*   **`schedtick`**: スケジューラがゴルーチンを切り替えるたびにインクリメントされるカウンタです。このカウンタは、スケジューラの内部的な動作や、特定の処理を定期的に実行するためのトリガーとして使用されます。
*   **剰余演算の最適化**: `X % N` のような剰余演算は、一般的に除算命令を伴います。除算命令は、乗算や加算、ビットシフトなどの他の算術命令に比べて、CPUサイクルを多く消費する傾向があります。そのため、特にパフォーマンスが重視されるシステムプログラミング（ランタイムなど）では、除算を避けて乗算やビットシフトで同等の結果を得る最適化手法が用いられることがあります。例えば、`X % N == 0` の判定は、`X - (X / N) * N == 0` と同等ですが、特定の定数 `N` の場合、`X * MagicNumber >> ShiftAmount` のような乗算とシフトの組み合わせで `X / N` を近似し、剰余を計算する手法が存在します。

## 技術的詳細

このコミットで削除されたコードは、`tick % 61 == 0` という条件を判定するための、以下のような「ハック」でした。

```go
tick := _g_.m.p.schedtick
// This is a fancy way to say tick%61==0,
// it uses 2 MUL instructions instead of a single DIV and so is faster on modern processors.
if uint64(tick)-((uint64(tick)*0x4325c53f)>>36)*61 == 0 && sched.runqsize > 0 {
    // ...
}
```

この式は、`tick` が `61` の倍数であるかどうかを判定しています。
*   `uint64(tick)*0x4325c53f`：`tick` に特定の「マジックナンバー」を乗算します。このマジックナンバーは、`1/61` の固定小数点表現のようなもので、除算を乗算に変換するために使用されます。
*   `>>36`：右シフト演算です。これは、固定小数点表現の小数点以下の部分を切り捨てることで、実質的に除算の結果（`tick / 61`）を得るためのものです。
*   `((uint64(tick)*0x4325c53f)>>36)*61`：これは `(tick / 61) * 61` と同等です。
*   `uint64(tick) - ((uint64(tick)*0x4325c53f)>>36)*61 == 0`：この式全体は、`tick - (tick / 61) * 61 == 0` と同等であり、これは `tick % 61 == 0` を意味します。

この最適化は、特にC言語で書かれたコードにおいて、コンパイラが除算命令を効率的に最適化できない場合に有効でした。当時のプロセッサによっては、除算命令が非常に高コストであったため、このような乗算とビットシフトによる代替手法がパフォーマンス向上に寄与しました。

しかし、Goコンパイラは進化し、このような定数による除算や剰余演算を自動的に効率的な命令シーケンス（乗算やビットシフトなど）に変換できるようになりました。これは、コンパイラの最適化パスがより洗練され、特定の算術恒等式やプロセッサの特性を考慮したコード生成が可能になったためです。

したがって、手動でこのような複雑な式を書く必要がなくなり、より直感的で読みやすい `_g_.m.p.schedtick%61 == 0` という記述に置き換えることが可能になりました。これにより、コードの保守性が向上し、コンパイラに最適化を任せることで、将来的なプロセッサアーキテクチャの進化にも対応しやすくなります。

## コアとなるコードの解説

変更されたのは、`src/runtime/proc1.go` ファイル内のゴルーチン・スケジューラの一部です。この部分は、グローバルな実行キューを定期的にチェックし、ゴルーチンの公平性を確保するためのロジックです。

元のコードでは、以下の3行が削除されました。

1.  `tick := _g_.m.p.schedtick`
    *   現在のM（マシン）がP（プロセッサ）にアタッチされており、そのPのスケジューラティックカウンタ `schedtick` を `tick` 変数に代入しています。

2.  `// This is a fancy way to say tick%61==0,`
    `// it uses 2 MUL instructions instead of a single DIV and so is faster on modern processors.`
    *   これはコメントであり、次に続く複雑な式が `tick % 61 == 0` の最適化された形式であることを説明しています。また、この最適化がC言語時代に導入された背景（除算よりも乗算が高速であること）も示唆しています。

3.  `if uint64(tick)-((uint64(tick)*0x4325c53f)>>36)*61 == 0 && sched.runqsize > 0 {`
    *   これが、`tick % 61 == 0` を判定するための、乗算とビットシフトを用いた複雑な式です。`sched.runqsize > 0` は、グローバル実行キューにゴルーチンが存在する場合にのみこのチェックを行うことを意味します。

これらの行は、以下の1行に置き換えられました。

*   `if _g_.m.p.schedtick%61 == 0 && sched.runqsize > 0 {`
    *   これは、元の複雑な式と同じ論理的な意味を持つ、より簡潔で読みやすい剰余演算です。Goコンパイラがこの剰余演算を自動的に最適化するため、手動での複雑な記述は不要になりました。

この変更により、コードの意図がより明確になり、可読性が大幅に向上しました。ランタイムの内部的な動作は変わりませんが、その実装がより現代のGoコンパイラの能力に合わせた形に更新されたと言えます。

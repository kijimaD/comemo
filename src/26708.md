# [インデックス 26708] ファイルの概要

このコミットは、Go言語の`net`パッケージにおけるDualStack (Happy Eyeballs) ダイヤリングの改善に関するものです。特に、`dialTCP`のキャンセル機能を利用して、並行して行われる接続試行において、不要になった接続が適切に終了されるように変更されました。これにより、以前のバージョンで発生していた接続リークの問題が解決され、テストコードからも不要な`time.Sleep`が削除されています。

## 変更の背景

このコミットの主な背景は、Goの`net`パッケージにおけるDualStack (Happy Eyeballs) ダイヤリングの実装が抱えていた接続リークの問題を解決することにあります。

以前のHappy Eyeballsの実装では、IPv4とIPv6の両方で接続を試みる際に、先に成功した方の接続を採用し、もう一方の接続試行は不要となります。しかし、この不要になった接続試行（特に`dialTCP`呼び出し）を確実にキャンセルして終了させるメカニズムが不十分でした。その結果、レースに負けた側の接続試行が完了するまでリソースを保持し続け、意図的に接続がリーク（解放されないまま残存）してしまう可能性がありました。これは、特に多数の接続を扱うアプリケーションにおいて、メモリやファイルディスクリプタなどのリソース枯渇につながる潜在的な問題でした。

Goの`dialTCP`関数がキャンセルをサポートするようになった（ただしPlan 9を除く）ことで、この問題に対処する機会が生まれました。キャンセル機能が導入されたことにより、`dialParallel`関数は、プライマリとフォールバックの両方の接続試行が完了するか、またはキャンセルされるまで待機し、不要になった接続試行を確実に終了させることが可能になりました。これにより、接続リークが解消され、リソース管理が改善されます。

この変更は、Issue #11225 (dialTCPのキャンセルサポート) と Issue #14279 (Happy Eyeballsでの接続リーク) に関連しています。

## 前提知識の解説

### Goの`net`パッケージ
Go言語の標準ライブラリである`net`パッケージは、ネットワークI/Oプリミティブへのポータブルなインターフェースを提供します。TCP/IP、UDP、IP、Unixドメインソケットなどのネットワークプロトコルを扱うための機能が含まれており、クライアントとサーバーの両方を実装できます。このコミットで変更される`Dial`関数は、指定されたネットワークアドレスへの接続を確立するための主要なインターフェースです。

### TCP/IPスタック
TCP/IPは、インターネットを含む多くのコンピュータネットワークで利用されている通信プロトコル群です。TCP (Transmission Control Protocol) は信頼性の高いデータ転送を提供し、IP (Internet Protocol) はデータのルーティングを担当します。クライアントがサーバーに接続する際には、これらのプロトコルが連携して動作します。

### DualStack (Happy Eyeballs)
Happy Eyeballs（RFC 8305）は、クライアントがIPv4とIPv6の両方のアドレスを持つサーバーに接続する際に、ユーザー体験を向上させるためのアルゴリズムです。現代のネットワーク環境では、IPv4とIPv6が共存しており、どちらか一方のプロトコルでの接続が遅延したり失敗したりする可能性があります。Happy Eyeballsは、この問題を解決するために、IPv4とIPv6の両方で同時に（またはわずかな時間差で）接続試行を開始し、最初に成功した方の接続を採用します。これにより、ユーザーはネットワークの遅延や障害を意識することなく、迅速に接続を確立できます。

このメカニズムは「レース（競合）」として実装され、複数の接続試行が並行して行われます。先に成功した方が「勝者」となり、他の試行は「敗者」としてキャンセルされる必要があります。

### `context.Context`とキャンセルメカニズム
Go言語では、`context.Context`パッケージがAPI境界を越えてデッドライン、キャンセルシグナル、その他のリクエストスコープの値を伝播するための標準的な方法を提供します。特に、`context.WithCancel`関数は、キャンセル可能な`Context`を作成し、その`cancel`関数を呼び出すことで、その`Context`から派生したすべての`Context`にキャンセルシグナルを送信できます。これにより、長時間実行される操作や並行処理において、不要になったゴルーチンやリソースを安全に終了させることが可能になります。

このコミットでは、`dialTCP`がこのキャンセルメカニズムに対応したことが重要です。これにより、Happy Eyeballsのレースで敗者となった接続試行を、`context.Context`を通じて確実にキャンセルできるようになりました。

### リソースリーク
リソースリークとは、プログラムが獲得したメモリ、ファイルディスクリプタ、ネットワーク接続などのシステムリソースを、使用後に適切に解放しない状態を指します。リソースリークが発生すると、プログラムが利用可能なリソースを徐々に消費し尽くし、最終的にはパフォーマンスの低下、エラーの発生、またはプログラムのクラッシュにつながる可能性があります。Happy Eyeballsの以前の実装では、レースに負けた接続が適切に閉じられずにリークする可能性があり、これがこのコミットで解決される主要な問題でした。

## 技術的詳細

このコミットは、主に`src/net/dial.go`と`src/net/dial_test.go`の2つのファイルに影響を与えています。

### `src/net/dial.go`の変更点

1.  **`Dialer.Dial`関数の変更**:
    *   `d.DualStack && network == "tcp"`の条件に加えて、`runtime.GOOS != "plan9"`が追加されました。これは、Plan 9オペレーティングシステムでは`dialTCP`のキャンセルがサポートされていないため、DualStackダイヤリングを無効にするためのものです。
    *   `dialSerial`および`dialParallel`関数への`cancel`チャネルの引数追加。以前は`dialSerial`には`nil`、`dialParallel`には`defer close(cancel)`で閉じられるローカルな`cancel`チャネルが渡されていましたが、変更後は`ctx.Cancel`（ユーザーが提供するキャンセルチャネル）が直接渡されるようになりました。

2.  **`dialParallel`関数の大幅な変更**:
    *   **`results`チャネルのバッファリング**: 以前は`unbuffered`チャネルでしたが、`make(chan dialResult, 2)`としてバッファリングされるようになりました。これにより、`dialSerialAsync`が結果を送信する際にブロックされることなく、`dialParallel`が両方のレーサーの結果を待つことができるようになります。
    *   **キャンセルロジックの変更**: 以前は`defer close(cancel)`で`cancel`チャネルを閉じていましたが、新しい実装では`userCancel`チャネル（外部からのキャンセル要求）と`results`チャネルからの結果を`select`文で待機するようになりました。
    *   **両方のレーサーの結果待機**: `primaryResult`と`fallbackResult`という2つの`dialResult`構造体を導入し、両方のレーサーが`done`状態になるまでループで待機します。
    *   **成功時のキャンセル**: どちらかのレーサーが成功した場合、`cancel`チャネルを閉じることで、もう一方のレーサーをキャンセルします。
    *   **`fallbackTimer`の制御**: `fallbackTimer`がペンディング状態の場合、成功時には`Stop()`して`Reset(0)`することで、フォールバック接続の試行を即座に開始させるか、または不要になった場合は停止させます。
    *   **戻り値の優先順位**: プライマリ接続が成功していればそれを返し、そうでなければフォールバック接続を返し、どちらも失敗していればプライマリのエラーを返します。成功した接続が複数ある場合、プライマリ接続を返し、フォールバック接続は閉じられます。

3.  **`dialResult`構造体の変更**:
    *   `done bool`フィールドが追加されました。これは、各レーサーの接続試行が完了したかどうかを示すために使用されます。

4.  **`dialSerialAsync`関数の変更**:
    *   `results <- dialResult{c, err, timer == nil}`の行が`results <- dialResult{Conn: c, error: err, primary: timer == nil, done: true}`に変更されました。これにより、`done: true`が明示的に設定され、`dialParallel`がレーサーの完了状態を追跡できるようになります。
    *   以前の`select`文によるレース勝敗判定と、負けた場合の接続クローズロジックが削除されました。これは、`dialParallel`が両方の結果を待機し、不要な接続を閉じる責任を持つようになったためです。
    *   `cancel`チャネルが発火した場合、`dialSerial`が即座に`errCanceled`を返すように期待されるようになりました。

5.  **`dialSerial`関数の変更**:
    *   `dialTCP does not support cancelation`というコメントが更新され、`If this dial is canceled, the implementation is expected to complete quickly`という記述に変更されました。これは、`dialTCP`がキャンセルをサポートするようになったことを反映しています。
    *   `dialSingle`関数を呼び出す際に、`cancel`チャネルが引数として渡されるようになりました。

6.  **`dialSingle`関数の変更**:
    *   `cancel <-chan struct{}`引数が追加されました。
    *   `testHookDialTCP`を呼び出す際に、この`cancel`チャネルが渡されるようになりました。

### `src/net/dial_test.go`の変更点

1.  **ベンチマークIPv4アドレスの修正**:
    *   `slowDst4`のアドレスが`192.18.0.254`から`198.18.0.254`に修正されました。これはRFC 6890でベンチマーク用に予約されているアドレスです。

2.  **`slowDialTCP`関数の変更**:
    *   以前は`time.Sleep(deadline.Sub(time.Now()))`で意図的に遅延させていましたが、`select`文を使って`cancel`チャネルまたは`time.After`のいずれかを待つように変更されました。これにより、テスト中にキャンセルシグナルを受け取った場合に、即座に遅延を終了できるようになります。

3.  **`TestDialParallel`関数の変更**:
    *   Plan 9でのスキップ条件が追加されました。
    *   `dialParallel`の呼び出しで、`cancel`チャネルが引数として渡されるようになりました（最初は`nil`）。
    *   テストケースの繰り返し部分で、明示的に`cancel`チャネルを作成し、短い遅延後に`close(cancel)`を呼び出すことで、`dialParallel`が迅速にキャンセルされることを検証するテストが追加されました。これにより、接続リークが解消されたことを確認します。
    *   以前の`time.Sleep(slowTimeout * 3 / 2)`が削除されました。これは、接続リークがなくなったため、テストの最後に不要な接続がタイムアウトするのを待つ必要がなくなったためです。

4.  **`TestDialerFallbackDelay`関数の変更**:
    *   `Dialer`の`Timeout`フィールドの設定が削除されました。
    *   テストケースから`{false, 0, slowTimeout}`が削除されました。

5.  **`TestDialSerialAsyncSpuriousConnection`から`TestDialParallelSpuriousConnection`への変更**:
    *   テスト名が変更され、`dialParallel`の動作を検証するようになりました。
    *   DualStackサーバーをセットアップし、`testHookDialTCP`を一時的に上書きして、意図的に接続試行を遅延させ、かつキャンセルを抑制するように変更されました。これにより、`dialParallel`が両方の接続を成功させてしまう状況を作り出し、その際に不要な接続が適切に閉じられることを検証します。
    *   `dialParallel`が1つの接続を返し、もう一方を閉じることを確認します。サーバー側では両方の接続が受け入れられ、クライアントが適切に閉じていることを`wg.Wait()`で確認します。

### 全体的な影響

このコミットにより、Goの`net`パッケージにおけるHappy Eyeballsの実装がより堅牢になり、リソースリークの可能性が排除されました。`dialTCP`のキャンセル機能が活用されることで、並行して行われるネットワーク接続試行の管理が改善され、より効率的で信頼性の高いネットワーク通信が実現されます。

## 変更の背景

このコミットの主な背景は、Goの`net`パッケージにおけるDualStack (Happy Eyeballs) ダイヤリングの実装が抱えていた接続リークの問題を解決することにあります。

以前のHappy Eyeballsの実装では、IPv4とIPv6の両方で接続を試みる際に、先に成功した方の接続を採用し、もう一方の接続試行は不要となります。しかし、この不要になった接続試行（特に`dialTCP`呼び出し）を確実にキャンセルして終了させるメカニズムが不十分でした。その結果、レースに負けた側の接続試行が完了するまでリソースを保持し続け、意図的に接続がリーク（解放されないまま残存）してしまう可能性がありました。これは、特に多数の接続を扱うアプリケーションにおいて、メモリやファイルディスクリプタなどのリソース枯渇につながる潜在的な問題でした。

Goの`dialTCP`関数がキャンセルをサポートするようになった（ただしPlan 9を除く）ことで、この問題に対処する機会が生まれました。キャンセル機能が導入されたことにより、`dialParallel`関数は、プライマリとフォールバックの両方の接続試行が完了するか、またはキャンセルされるまで待機し、不要になった接続試行を確実に終了させることが可能になりました。これにより、接続リークが解消され、リソース管理が改善されます。

この変更は、Issue #11225 (dialTCPのキャンセルサポート) と Issue #14279 (Happy Eyeballsでの接続リーク) に関連しています。

## 前提知識の解説

### Goの`net`パッケージ
Go言語の標準ライブラリである`net`パッケージは、ネットワークI/Oプリミティブへのポータブルなインターフェースを提供します。TCP/IP、UDP、IP、Unixドメインソケットなどのネットワークプロトコルを扱うための機能が含まれており、クライアントとサーバーの両方を実装できます。このコミットで変更される`Dial`関数は、指定されたネットワークアドレスへの接続を確立するための主要なインターフェースです。

### TCP/IPスタック
TCP/IPは、インターネットを含む多くのコンピュータネットワークで利用されている通信プロトコル群です。TCP (Transmission Control Protocol) は信頼性の高いデータ転送を提供し、IP (Internet Protocol) はデータのルーティングを担当します。クライアントがサーバーに接続する際には、これらのプロトコルが連携して動作します。

### DualStack (Happy Eyeballs)
Happy Eyeballs（RFC 8305）は、クライアントがIPv4とIPv6の両方のアドレスを持つサーバーに接続する際に、ユーザー体験を向上させるためのアルゴリズムです。現代のネットワーク環境では、IPv4とIPv6が共存しており、どちらか一方のプロトコルでの接続が遅延したり失敗したりする可能性があります。Happy Eyeballsは、この問題を解決するために、IPv4とIPv6の両方で同時に（またはわずかな時間差で）接続試行を開始し、最初に成功した方の接続を採用します。これにより、ユーザーはネットワークの遅延や障害を意識することなく、迅速に接続を確立できます。

このメカニズムは「レース（競合）」として実装され、複数の接続試行が並行して行われます。先に成功した方が「勝者」となり、他の試行は「敗者」としてキャンセルされる必要があります。

### `context.Context`とキャンセルメカニズム
Go言語では、`context.Context`パッケージがAPI境界を越えてデッドライン、キャンセルシグナル、その他のリクエストスコープの値を伝播するための標準的な方法を提供します。特に、`context.WithCancel`関数は、キャンセル可能な`Context`を作成し、その`cancel`関数を呼び出すことで、その`Context`から派生したすべての`Context`にキャンセルシグナルを送信できます。これにより、長時間実行される操作や並行処理において、不要になったゴルーチンやリソースを安全に終了させることが可能になります。

このコミットでは、`dialTCP`がこのキャンセルメカニズムに対応したことが重要です。これにより、Happy Eyeballsのレースで敗者となった接続試行を、`context.Context`を通じて確実にキャンセルできるようになりました。

### リソースリーク
リソースリークとは、プログラムが獲得したメモリ、ファイルディスクリプタ、ネットワーク接続などのシステムリソースを、使用後に適切に解放しない状態を指します。リソースリークが発生すると、プログラムが利用可能なリソースを徐々に消費し尽くし、最終的にはパフォーマンスの低下、エラーの発生、またはプログラムのクラッシュにつながる可能性があります。Happy Eyeballsの以前の実装では、レースに負けた接続が適切に閉じられずにリークする可能性があり、これがこのコミットで解決される主要な問題でした。

## 技術的詳細

このコミットは、主に`src/net/dial.go`と`src/net/dial_test.go`の2つのファイルに影響を与えています。

### `src/net/dial.go`の変更点

1.  **`Dialer.Dial`関数の変更**:
    *   `d.DualStack && network == "tcp"`の条件に加えて、`runtime.GOOS != "plan9"`が追加されました。これは、Plan 9オペレーティングシステムでは`dialTCP`のキャンセルがサポートされていないため、DualStackダイヤリングを無効にするためのものです。
    *   `dialSerial`および`dialParallel`関数への`cancel`チャネルの引数追加。以前は`dialSerial`には`nil`、`dialParallel`には`defer close(cancel)`で閉じられるローカルな`cancel`チャネルが渡されていましたが、変更後は`ctx.Cancel`（ユーザーが提供するキャンセルチャネル）が直接渡されるようになりました。

2.  **`dialParallel`関数の大幅な変更**:
    *   **`results`チャネルのバッファリング**: 以前は`unbuffered`チャネルでしたが、`make(chan dialResult, 2)`としてバッファリングされるようになりました。これにより、`dialSerialAsync`が結果を送信する際にブロックされることなく、`dialParallel`が両方のレーサーの結果を待つことができるようになります。
    *   **キャンセルロジックの変更**: 以前は`defer close(cancel)`で`cancel`チャネルを閉じていましたが、新しい実装では`userCancel`チャネル（外部からのキャンセル要求）と`results`チャネルからの結果を`select`文で待機するようになりました。
    *   **両方のレーサーの結果待機**: `primaryResult`と`fallbackResult`という2つの`dialResult`構造体を導入し、両方のレーサーが`done`状態になるまでループで待機します。
    *   **成功時のキャンセル**: どちらかのレーサーが成功した場合、`cancel`チャネルを閉じることで、もう一方のレーサーをキャンセルします。
    *   **`fallbackTimer`の制御**: `fallbackTimer`がペンディング状態の場合、成功時には`Stop()`して`Reset(0)`することで、フォールバック接続の試行を即座に開始させるか、または不要になった場合は停止させます。
    *   **戻り値の優先順位**: プライマリ接続が成功していればそれを返し、そうでなければフォールバック接続を返し、どちらも失敗していればプライマリのエラーを返します。成功した接続が複数ある場合、プライマリ接続を返し、フォールバック接続は閉じられます。

3.  **`dialResult`構造体の変更**:
    *   `done bool`フィールドが追加されました。これは、各レーサーの接続試行が完了したかどうかを示すために使用されます。

4.  **`dialSerialAsync`関数の変更**:
    *   `results <- dialResult{c, err, timer == nil}`の行が`results <- dialResult{Conn: c, error: err, primary: timer == nil, done: true}`に変更されました。これにより、`done: true`が明示的に設定され、`dialParallel`がレーサーの完了状態を追跡できるようになります。
    *   以前の`select`文によるレース勝敗判定と、負けた場合の接続クローズロジックが削除されました。これは、`dialParallel`が両方の結果を待機し、不要な接続を閉じる責任を持つようになったためです。
    *   `cancel`チャネルが発火した場合、`dialSerial`が即座に`errCanceled`を返すように期待されるようになりました。

5.  **`dialSerial`関数の変更**:
    *   `dialTCP does not support cancelation`というコメントが更新され、`If this dial is canceled, the implementation is expected to complete quickly`という記述に変更されました。これは、`dialTCP`がキャンセルをサポートするようになったことを反映しています。
    *   `dialSingle`関数を呼び出す際に、`cancel`チャネルが引数として渡されるようになりました。

6.  **`dialSingle`関数の変更**:
    *   `cancel <-chan struct{}`引数が追加されました。
    *   `testHookDialTCP`を呼び出す際に、この`cancel`チャネルが渡されるようになりました。

### `src/net/dial_test.go`の変更点

1.  **ベンチマークIPv4アドレスの修正**:
    *   `slowDst4`のアドレスが`192.18.0.254`から`198.18.0.254`に修正されました。これはRFC 6890でベンチマーク用に予約されているアドレスです。

2.  **`slowDialTCP`関数の変更**:
    *   以前は`time.Sleep(deadline.Sub(time.Now()))`で意図的に遅延させていましたが、`select`文を使って`cancel`チャネルまたは`time.After`のいずれかを待つように変更されました。これにより、テスト中にキャンセルシグナルを受け取った場合に、即座に遅延を終了できるようになります。

3.  **`TestDialParallel`関数の変更**:
    *   Plan 9でのスキップ条件が追加されました。
    *   `dialParallel`の呼び出しで、`cancel`チャネルが引数として渡されるようになりました（最初は`nil`）。
    *   テストケースの繰り返し部分で、明示的に`cancel`チャネルを作成し、短い遅延後に`close(cancel)`を呼び出すことで、`dialParallel`が迅速にキャンセルされることを検証するテストが追加されました。これにより、接続リークが解消されたことを確認します。
    *   以前の`time.Sleep(slowTimeout * 3 / 2)`が削除されました。これは、接続リークがなくなったため、テストの最後に不要な接続がタイムアウトするのを待つ必要がなくなったためです。

4.  **`TestDialerFallbackDelay`関数の変更**:
    *   `Dialer`の`Timeout`フィールドの設定が削除されました。
    *   テストケースから`{false, 0, slowTimeout}`が削除されました。

5.  **`TestDialSerialAsyncSpuriousConnection`から`TestDialParallelSpuriousConnection`への変更**:
    *   テスト名が変更され、`dialParallel`の動作を検証するようになりました。
    *   DualStackサーバーをセットアップし、`testHookDialTCP`を一時的に上書きして、意図的に接続試行を遅延させ、かつキャンセルを抑制するように変更されました。これにより、`dialParallel`が両方の接続を成功させてしまう状況を作り出し、その際に不要な接続が適切に閉じられることを検証します。
    *   `dialParallel`が1つの接続を返し、もう一方を閉じることを確認します。サーバー側では両方の接続が受け入れられ、クライアントが適切に閉じていることを`wg.Wait()`で確認します。

### 全体的な影響

このコミットにより、Goの`net`パッケージにおけるHappy Eyeballsの実装がより堅牢になり、リソースリークの可能性が排除されました。`dialTCP`のキャンセル機能が活用されることで、並行して行われるネットワーク接続試行の管理が改善され、より効率的で信頼性の高いネットワーク通信が実現されます。

#### `dialParallel`関数の変更

```go

*   **`results := make(chan dialResult, 2)`**: `dialResult`チャネルがバッファリングされるようになりました。以前はアンバッファードチャネルでしたが、バッファリングすることで、`dialSerialAsync`が結果を送信する際にブロックされることなく、`dialParallel`が両方のレーサーの結果を待つことができるようになります。

```go

 	var primaryResult, fallbackResult dialResult
 	for !primaryResult.done || !fallbackResult.done {
 		select {
 		case <-userCancel:
 			// Forward an external cancelation request.
 			if cancel != nil {
 				close(cancel)
 				cancel = nil
 			}

 			// Drop the result into its assigned bucket.
 			if res.primary {
 				primaryResult = res
 			} else {
 				fallbackResult = res
 			}
 			// On success, cancel the other racer (if one exists.)
 			if res.error == nil && cancel != nil {
 				close(cancel)
 				cancel = nil
 			}
 			// If the fallbackTimer was pending, then either we've canceled the
 			// fallback because we no longer want it, or we haven't canceled yet
 			// and therefore want it to wake up immediately.
 			if fallbackTimer.Stop() && cancel != nil {
 				fallbackTimer.Reset(0)
 			}
 		}
 	}
```
*   **`for !primaryResult.done || !fallbackResult.done`**: このループは、プライマリとフォールバックの両方の接続試行が完了するまで継続します。`dialResult`構造体に新しく追加された`done`フィールドが、各試行の完了状態を示します。
*   **`select`文**:
    *   **`case <-userCancel`**: 外部から`userCancel`シグナルが送られてきた場合、内部の`cancel`チャネルを閉じ、`userCancel`を`nil`に設定して、それ以降の外部キャンセルを無視します。これにより、内部のレーサーにキャンセルシグナルが伝播されます。
    *   **`case res := <-results`**: `dialSerialAsync`から結果が送られてきた場合、それがプライマリかフォールバックかに応じて`primaryResult`または`fallbackResult`に格納します。
    *   **`if res.error == nil && cancel != nil`**: 接続が成功した場合、まだ閉じられていない内部`cancel`チャネルを閉じます。これにより、もう一方のレーサー（まだ実行中であれば）がキャンセルされ、不要な接続試行が停止します。
    *   **`if fallbackTimer.Stop() && cancel != nil`**: `fallbackTimer`がまだアクティブな場合、それを停止させます。接続が成功した場合は、フォールバックタイマーをリセットして即座に起動させるか、またはキャンセルされた場合は不要なタイマーを停止させます。

```go

 	// 1. The primary connection (but close the other if we got both.)
 	// 2. The fallback connection.
 	// 3. The primary error.

*   **戻り値のロジック**: 両方のレーサーが完了した後、以下の優先順位で接続を返します。
    1.  プライマリ接続が成功していれば、それを返します。もしフォールバック接続も成功していた場合、フォールバック接続は閉じられます。
    2.  プライマリ接続が失敗し、フォールバック接続が成功していれば、フォールバック接続を返します。
    3.  どちらの接続も失敗していれば、プライマリ接続のエラーを返します。

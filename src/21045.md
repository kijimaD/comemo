## 元コミット内容

このコミットの元の内容は、Goランタイムのガベージコレクション（GC）に関連する重要な改善です。主な目的は以下の2点です。

1.  **`casp` (Compare-and-Swap Pointer) へのライトバリアの追加**: `casp` はポインタ値をアトミックに比較し、条件が一致すれば新しい値に交換する操作です。GCが正しく動作するためには、ヒープ上のポインタが変更される際にGCにその変更を通知する必要があります。この通知メカニズムがライトバリアです。`casp` のようなアトミック操作は、通常の代入とは異なる経路でメモリを変更するため、GCがその変更を追跡できるよう、明示的にライトバリアを適用する必要がありました。これにより、GCがオブジェクトの到達可能性を正確に判断し、誤って使用中のオブジェクトを回収してしまうことを防ぎます。

2.  **真のポインタではない `casp` の使用箇所の `casuintptr` への置き換え**: `casp` は `unsafe.Pointer` を引数にとりますが、これは任意の型を指すことができるため、実際にはポインタではない整数値などを `unsafe.Pointer` にキャストして使用しているケースが存在しました。このような場合、GCはそれがポインタであると誤解し、不必要なライトバリアの処理を行ったり、GCのロジックが複雑になったりする可能性があります。`casuintptr` は `uintptr` 型（ポインタを保持できる整数型）に対するCAS操作であり、GCの対象外となる純粋な数値操作に適しています。この変更により、コードの意図が明確になり、GCのオーバーヘッドを削減し、潜在的なバグを防ぐことができます。

## 変更の背景

Goのガベージコレクションは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行してGCが動作します。この並行GCの正確性と効率性を保証するために、ライトバリアは不可欠な要素です。

ライトバリアは、プログラムがヒープ上のポインタを書き換える際に、GCがその変更を検知し、必要に応じてオブジェクトをマークする（到達可能であると記録する）ためのメカニズムです。これにより、GCがオブジェクトグラフを走査している最中にポインタが変更されても、GCが古いポインタを追跡し損ねて、まだ到達可能なオブジェクトを誤って回収してしまう「ストップ・ザ・ワールド（STW）時間の短縮」や「GCの正確性維持」といった問題を防ぎます。

従来のGoランタイムでは、通常のポインタ代入にはライトバリアが適用されていましたが、`casp` のようなアトミック操作によるポインタの変更にはライトバリアが明示的に適用されていませんでした。これは、`casp` が低レベルのアセンブリコードで実装されており、GCのライトバリア機構と統合されていなかったためです。このギャップは、特定の条件下でGCの不正確性や、最悪の場合、メモリ破壊を引き起こす可能性がありました。

また、`unsafe.Pointer` はGoの型システムを迂回して任意のメモリを操作できる強力な機能ですが、その分、誤用するとGCの動作を混乱させる可能性があります。特に、ポインタではない整数値を `unsafe.Pointer` として扱い、`casp` で操作するようなケースは、GCにとって余計な複雑さをもたらしていました。このような状況を改善し、GCのロジックを簡潔かつ堅牢にするために、真のポインタではない値に対する操作には `casuintptr` を使用するという明確な分離が必要とされました。

このコミットは、Goランタイムの安定性とパフォーマンスをさらに向上させるための、ガベージコレクションとアトミック操作の間の重要な同期と最適化の一環として行われました。

## 前提知識の解説

### Goのガベージコレクション (GC) の基本

GoのGCは、主に**並行マーク＆スイープ**アルゴリズムに基づいています。これは、プログラムの実行と並行してGCが動作し、アプリケーションの停止時間（Stop-The-World: STW）を最小限に抑えることを目指しています。

1.  **マークフェーズ**: GCは、プログラムのルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトを識別し、マークします。このフェーズの一部は並行して実行されますが、一部の重要な処理（例えば、ルートの走査開始時）では短いSTWが発生します。
2.  **スイープフェーズ**: マークされなかったオブジェクト（到達不可能と判断されたオブジェクト）は、メモリから解放されます。このフェーズも並行して実行されます。

並行GCの課題の一つは、GCがオブジェクトグラフを走査している最中に、アプリケーションがポインタを書き換える可能性があることです。これにより、GCがオブジェクトの到達可能性を誤って判断する可能性があります。この問題を解決するために、ライトバリアが導入されています。

### ライトバリア (Write Barrier) とその目的

ライトバリアは、Goの並行GCにおいて、ヒープ上のポインタが変更される際にGCにその変更を通知するためのメカニズムです。具体的には、`*dst = src` のようなポインタ代入が行われる際に、コンパイラやランタイムが追加のコード（バリアコード）を挿入します。

ライトバリアの主な目的は以下の通りです。

*   **GCの正確性の保証**: GCがオブジェクトグラフを走査している間に、アプリケーションがポインタを書き換えても、GCがその変更を検知し、到達可能なオブジェクトを誤って回収しないようにします。
*   **STW時間の短縮**: ライトバリアがない場合、GCはオブジェクトグラフの整合性を保つために、より長いSTW時間を必要とする可能性があります。ライトバリアにより、GCは並行性を高め、STW時間を短縮できます。

Goのライトバリアは、主に「Dijkstraの三色マーク」アルゴリズムと組み合わせて使用されます。オブジェクトは白（未訪問）、灰色（訪問済みだが子を未走査）、黒（訪問済みで子も走査済み）のいずれかの色でマークされます。ライトバリアは、黒から白へのポインタの書き込みを防ぐ（または検知する）ことで、GCの正確性を保証します。

### アトミック操作 (Atomic Operations): CAS (Compare-and-Swap)

アトミック操作は、複数のCPUコアやゴルーチンが共有メモリに同時にアクセスする際に、データの一貫性を保証するための不可分な操作です。CAS (Compare-and-Swap) は、アトミック操作の中でも特に重要なものです。

CAS操作は、以下の3つの引数を取ります。

1.  **メモリ上のアドレス (ptr)**: 操作対象のメモリ位置。
2.  **期待する値 (old)**: 現在メモリにあると期待される値。
3.  **新しい値 (new)**: 期待する値と一致した場合に書き込む新しい値。

CASは、`ptr` の現在の値が `old` と一致する場合にのみ、`ptr` の値を `new` に更新します。この操作全体がアトミック（不可分）に実行されるため、他のゴルーチンからの干渉を受けません。操作が成功したかどうかを示すブール値を返します。

Goランタイムでは、`sync/atomic` パッケージを通じてユーザーレベルでアトミック操作が提供されていますが、ランタイム内部でも低レベルな同期プリミティブとしてCASが広く利用されています。

### `unsafe.Pointer` と `uintptr` の違いと使い分け

Goには、メモリを直接操作するための2つの特殊な型があります。

*   **`unsafe.Pointer`**:
    *   任意の型のポインタを保持できる汎用ポインタ型です。
    *   Goの型システムを迂回して、異なる型のポインタ間で変換を行うことができます。
    *   GCは `unsafe.Pointer` が指すメモリを追跡し、必要に応じて移動させたり、ライトバリアを適用したりします。
    *   **用途**: C言語との相互運用、低レベルなデータ構造の操作、Goの型システムでは表現できない特殊なメモリ操作など。
    *   **注意**: `unsafe.Pointer` を誤って使用すると、メモリ破壊やGCの誤動作を引き起こす可能性があるため、非常に慎重に扱う必要があります。

*   **`uintptr`**:
    *   ポインタを保持できる符号なし整数型です。
    *   `uintptr` は単なる数値であり、GCは `uintptr` が指すメモリを追跡しません。つまり、`uintptr` に変換されたポインタは、GCからは通常の整数値として扱われ、その参照先のオブジェクトがGCによって回収される可能性があります。
    *   **用途**: ポインタのアドレス値を数値として計算したり、ポインタのオフセットを操作したりする場合など。
    *   **注意**: `uintptr` に変換されたポインタはGCの対象外となるため、GCによって参照先のオブジェクトが移動または回収された場合、`uintptr` が指すアドレスは無効になる可能性があります。

**使い分け**:

*   **`unsafe.Pointer`**: GCによって追跡されるべきポインタ（ヒープ上のオブジェクトへの参照）を扱う場合に使用します。
*   **`uintptr`**: GCの追跡が不要な純粋なメモリアドレスの数値表現や、GCの対象外となるメモリ領域を操作する場合に使用します。

このコミットでは、真のポインタではない値（例えば、ロックの状態を示すフラグなど）を `unsafe.Pointer` 経由で `casp` で操作していた箇所を、GCの追跡が不要な `uintptr` 型の `casuintptr` に変更することで、GCのオーバーヘッドを削減し、コードの意図を明確にしています。

## 技術的詳細

このコミットの技術的詳細は、Goランタイムの低レベルなアトミック操作とガベージコレクションのライトバリアの統合に焦点を当てています。

### `casp` にライトバリアが追加された理由と影響

Goの並行GCは、ヒープ上のポインタの変更をライトバリアを通じて監視します。しかし、`casp` のようなアトミック操作は、通常の代入とは異なるパスでメモリを更新するため、GCがその変更を検知できない可能性がありました。

このコミットでは、`src/runtime/atomic.go` 内の `casp` 関数にライトバリアが追加されました。具体的には、`casp` の内部で `writebarrierptr_nostore` が呼び出されるようになりました。

```go
// src/runtime/atomic.go
func casp(ptr *unsafe.Pointer, old, new unsafe.Pointer) bool {
	ok := casp1((*unsafe.Pointer)(noescape(unsafe.Pointer(ptr))), old, new)
	if !ok {
		return false
	}
	writebarrierptr_nostore((*uintptr)(unsafe.Pointer(ptr)), uintptr(new)) // ここが追加
	return true
}
```

*   `casp1` は、実際のCAS操作を行う低レベルなアセンブリ関数です。
*   `writebarrierptr_nostore` は、すでにストア（書き込み）が行われたポインタに対してライトバリア処理を実行する関数です。`casp` はCAS操作が成功した場合にのみ新しい値を書き込むため、この `_nostore` バージョンが適切です。

この変更により、`casp` を介してヒープ上のポインタが更新された場合でも、GCは確実にその変更を検知し、オブジェクトの到達可能性を正確に追跡できるようになります。これにより、GCの正確性が向上し、潜在的なメモリ関連のバグが減少します。

同様に、`xchgp` (Exchange Pointer) と `atomicstorep` (Atomic Store Pointer) にもライトバリアが追加されています。これらの関数もポインタをアトミックに書き換えるため、GCの追跡が必要でした。

### `casp` から `casuintptr` への変更の意図

Goランタイムのコードベースには、実際にはポインタではない整数値（例えば、ロックの状態やフラグなど）を `unsafe.Pointer` にキャストして `casp` で操作している箇所がいくつか存在しました。このような使用方法は、GCにとって以下のような問題を引き起こす可能性がありました。

*   **不必要なライトバリアの実行**: GCは `unsafe.Pointer` をポインタとして扱うため、実際にはポインタではない値の変更に対してもライトバリアを適用しようとします。これは無駄なオーバーヘッドとなり、GCのパフォーマンスに影響を与えます。
*   **GCロジックの複雑化**: GCはポインタの追跡に特化しているため、ポインタではない値が混在すると、GCの内部ロジックが不必要に複雑になる可能性があります。
*   **意図の不明確さ**: コードを読んだ際に、その `unsafe.Pointer` が本当にポインタを指しているのか、それとも単なる数値として扱われているのかが不明確になります。

このコミットでは、これらの問題を解決するために、真のポインタではない値に対するCAS操作を `casuintptr` に置き換えています。`casuintptr` は `uintptr` 型（ポインタを保持できる整数型）に対するCAS操作であり、GCは `uintptr` が指すメモリを追跡しません。

変更例:

*   `src/runtime/proc.c`: `runtime·extram` のロック機構で `MLOCKED` という整数値を `casp` で比較していましたが、これを `casuintptr` に変更しています。`MLOCKED` はポインタではなく、単なる状態を示す数値であるため、この変更は適切です。
    ```c
    // src/runtime/proc.c
    // 変更前:
    // if(!runtime·casp(&runtime·extram, mp, MLOCKED)) {
    // 変更後:
    // if(!runtime·casuintptr((uintptr*)&runtime·extram, mpx, MLOCKED)) {
    ```
*   `src/runtime/string.c`: `runtime·maxstring` の更新で `casp` を使用していましたが、これも `casuintptr` に変更されています。`runtime·maxstring` は文字列の最大長を示す数値であり、ポインタではありません。
    ```c
    // src/runtime/string.c
    // 変更前:
    // if(s.len <= ms || runtime·casp((void**)&runtime·maxstring, (void*)ms, (void*)s.len))
    // 変更後:
    // if(s.len <= ms || runtime·casuintptr(&runtime·maxstring, ms, s.len))
    ```

この変更により、コードの意図が明確になり、GCは真のポインタのみを追跡することに集中できるため、GCの効率性と正確性が向上します。

// Like writebarrierptr, but the store has already been applied.

## コアとなるコードの解説

### `src/runtime/atomic.go` の `casp` ラッパー関数

変更後の `casp` 関数は、アセンブリで実装された低レベルな `casp1` 関数を呼び出すGoのラッパー関数として機能します。

1.  `ok := casp1(...)`: まず、実際のCAS操作が `casp1` によって実行されます。`noescape(unsafe.Pointer(ptr))` は、`ptr` がこの関数呼び出しのスコープ外にエスケープしないことをコンパイラに伝えます。これは、GCがポインタを追跡する上で重要なヒントとなります。

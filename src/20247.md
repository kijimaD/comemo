# [インデックス 20247] ファイルの概要

このコミットは、Goリンカによって内部的に定義されるシンボル（例: `text`, `data`, `bss` など）を `runtime.` プレフィックスを付けて `runtime` パッケージに移動させるものです。これにより、特にCGOを使用する際に発生する可能性のある、Goの内部シンボルとC言語のシンボルとの名前衝突を防ぎ、リンカの堅牢性を向上させます。

## 変更の背景

Go言語のプログラムは、コンパイル後にリンカによって実行可能ファイルに結合されます。この過程で、リンカはプログラムの様々なセクション（コード、初期化済みデータ、初期化されていないデータなど）の開始アドレスや終了アドレスを示すために、`text`, `data`, `bss`, `end` といった特定のシンボルを内部的に定義します。

しかし、GoプログラムがC言語のコードと連携するCGOを使用する場合、問題が発生する可能性がありました。C言語のコードもまた、`text` や `data` のような一般的な名前のシンボルを定義することがあります。GoのリンカとCのリンカが連携して動作する際、これらの一般的なシンボル名が衝突し、"duplicate symbol"（シンボル重複）エラーや予期せぬリンカエラーを引き起こすことがありました。

特に、Goの内部シンボルがC言語の標準ライブラリやユーザー定義のCコード内のシンボルと衝突することは、Goプログラムのビルドを妨げ、開発者に混乱をもたらす原因となっていました。このコミットは、このようなシンボル衝突の問題を根本的に解決するために、Goのリンカが定義する内部シンボルに `runtime.` というプレフィックスを付けることで、それらをGoランタイムのプライベートなシンボルとして明確に区別し、名前空間を分離することを目的としています。

コミットに含まれる `misc/cgo/test/issue8092.go` という新しいテストファイルは、まさにこの問題（リンカ定義シンボルとCシンボルの衝突）を再現し、この変更によって問題が解決されることを確認するために追加されました。

## 前提知識の解説

*   **Goリンカ (`cmd/ld`, `cmd/link`)**: Goのビルドツールチェーンの一部であり、コンパイルされたGoのオブジェクトファイル（`.o`）やアーカイブファイル（`.a`）を結合し、最終的な実行可能バイナリを生成する役割を担います。プログラムのセクション配置、シンボル解決、リロケーション処理などを行います。
*   **リンカ定義シンボル (Linker-defined Symbols)**: プログラムのメモリレイアウトに関する情報を提供する特殊なシンボルです。これらはソースコードで明示的に定義されるのではなく、リンカがビルドプロセス中に自動的に生成します。一般的なものには以下があります。
    *   `text` / `etext`: コードセクションの開始/終了アドレス。
    *   `data` / `edata`: 初期化済みデータセクションの開始/終了アドレス。
    *   `bss` / `ebss`: 初期化されていないデータセクション（BSSセクション）の開始/終了アドレス。
    *   `end`: プログラム全体のメモリフットプリントの終了アドレス。
    *   `pclntab`: Goのプログラムカウンタ-行番号テーブル（PC-Line Table）の開始アドレス。デバッグ情報やスタックトレースの生成に利用されます。
    *   `symtab`: シンボルテーブルの開始アドレス。
*   **CGO**: Go言語の機能の一つで、GoプログラムからC言語の関数を呼び出したり、C言語のデータ構造を利用したりするためのメカニズムです。CGOを使用すると、GoのコンパイラとCのコンパイラ（通常はGCCやClang）が連携し、GoとCのコードが混在するバイナリを生成します。この連携がシンボル衝突の原因となることがあります。
*   **シンボル衝突 (Symbol Collision)**: 複数の異なるコンパイル単位（例: GoのオブジェクトファイルとCのオブジェクトファイル）が、同じ名前のグローバルシンボルを定義している場合に発生する問題です。リンカは、どの定義を使用すべきか判断できなくなり、通常は「multiple definition of symbol」のようなエラーを出力してビルドを中断します。
*   **`runtime` パッケージ**: Go言語の標準ライブラリの一部であり、Goプログラムの実行を支える低レベルな機能（ガベージコレクション、ゴルーチン管理、スケジューラ、メモリ割り当て、システムコールインターフェースなど）を提供します。Goプログラムの実行に不可欠な部分であり、Goコンパイラやリンカと密接に連携しています。

## 技術的詳細

このコミットの主要な技術的変更は、Goリンカが内部的に使用するセクション関連のシンボル（`text`, `data`, `bss`, `pclntab` など）に `runtime.` というプレフィックスを一貫して付与することです。これにより、これらのシンボルは `runtime.text`, `runtime.data`, `runtime.pclntab` のように変更されます。

この変更は、Goのビルドツールチェーンの複数のコンポーネントに影響を与えます。

1.  **リンカ (`cmd/ld`, `cmd/link`)**:
    *   `src/cmd/ld/data.c`: 各セクション（`noptrdata`, `data`, `bss`, `noptrbss`, `rodata`, `typelink`, `symtab`, `pclntab`, `text`）の開始/終了シンボルを定義する箇所で、シンボル名に `runtime.` プレフィックスが追加されます。例えば、`linklookup(ctxt, "data", 0)` は `linklookup(ctxt, "runtime.data", 0)` に変更されます。
    *   `src/cmd/ld/symtab.c`: リンカがシンボルテーブルにこれらのシンボルを定義する際にも、新しい名前が使用されます。
    *   `src/cmd/link/auto.go`: リンカが自動的に生成するシンボルをリストアップする `linkerDefined` マップが更新され、`text` などの代わりに `runtime.text` などの新しい名前がキーとして追加されます。
    *   `src/cmd/link/layout.go`: `defineConst` 関数が呼び出される箇所で、セクションの開始/終了アドレスを示す定数シンボルにも `runtime.` プレフィックスが適用されます。
    *   `src/cmd/link/pclntab.go`, `src/cmd/link/runtime.go`: 内部で参照される `pclntab`, `gcdata`, `gcbss` などのシンボル名も `runtime.` プレフィックス付きの名前に変更されます。

2.  **オブジェクトダンプツール (`cmd/objdump`)**:
    *   `src/cmd/objdump/main.go`: `objdump` ツールがバイナリからシンボル情報を解析する際、`text`, `etext` などのシンボルを特別扱いするロジックが更新され、`runtime.text`, `runtime.etext` も認識するように変更されます。

3.  **デバッグ/Goシンボルパッケージ (`debug/gosym`)**:
    *   `src/pkg/debug/gosym/symtab.go`: Goバイナリのシンボルテーブルを解析するこのパッケージも、`etext` シンボルを処理する際に `runtime.etext` を認識するように更新されます。

4.  **Goランタイム (`src/pkg/runtime`)**:
    *   `src/pkg/runtime/heapdump.c`, `src/pkg/runtime/malloc.c`, `src/pkg/runtime/mem_plan9.c`, `src/pkg/runtime/mgc0.c`, `src/pkg/runtime/os_*.c`, `src/pkg/runtime/proc.c`, `src/pkg/runtime/race.c`, `src/pkg/runtime/race_amd64.s`, `src/pkg/runtime/stubs.goc`, `src/pkg/runtime/symtab.c`, `src/pkg/runtime/symtab.go`: Goランタイムの様々なCコードおよびGoコードで、`extern byte data[]` のようなリンカ定義シンボルへの参照が `extern byte runtime·data[]` のように変更されます。これにより、ランタイムコードが新しいシンボル名で正しくセクションアドレスを参照できるようになります。特に、`symtab.go` では `pclntab` が `pclntable` にリネームされ、`runtime.` プレフィックスが適用されています。

この変更は、Goの内部シンボルと外部（特にCGO経由のC言語）シンボルとの間の名前空間の分離を強化し、将来的なシンボル衝突のリスクを低減する上で重要なステップです。

## コアとなるコードの解説

上記のコードスニペットは、Goリンカの `dodata` 関数の一部であり、様々なデータセクション（`noptrdata`, `data`, `bss`, `noptrbss` など）の開始および終了シンボルを定義している箇所です。

変更前は、`linklookup(ctxt, "data", 0)->sect = sect;` のように、シンボル名が直接 `"data"` や `"bss"` といった一般的な文字列で指定されていました。`linklookup` 関数は、指定された名前のシンボルをリンカのコンテキスト (`ctxt`) から検索または作成し、そのシンボルが属するセクション (`sect`) を設定します。

このコミットでは、これらのシンボル名が `linklookup(ctxt, "runtime.data", 0)->sect = sect;` のように、すべて `runtime.` プレフィックス付きの名前に変更されています。

この変更の意図は以下の通りです。

1.  **名前空間の分離**: `runtime.` プレフィックスを付けることで、これらのシンボルがGoランタイムの内部的なものであることを明確にします。これにより、ユーザーがCGO経由でC言語のコードをリンクする際に、Cコード内で `data` や `text` といった一般的な名前のグローバルシンボルが定義されていても、Goの内部シンボルと衝突する可能性がなくなります。
2.  **堅牢性の向上**: シンボル衝突は、ビルドエラーや予期せぬ実行時動作の原因となることがあり、デバッグが困難です。この名前変更により、Goのビルドシステムはより堅牢になり、外部のコードとの統合がスムーズになります。
3.  **明確な意図**: `runtime.data` のような名前は、そのシンボルがGoランタイムのデータセクションに関連していることを一目で示し、コードの可読性と保守性を向上させます。

この変更は、Goのリンカ、ランタイム、デバッグツールなど、Goバイナリの構造を扱うすべてのコンポーネントで一貫して適用されており、Goの内部シンボル管理における重要な改善点と言えます。

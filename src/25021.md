# [インデックス 25021] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおいて、`append`操作（`OAPPEND`）の実装を追加するものです。具体的には、`src/cmd/compile/internal/gc/ssa.go`ファイルに`append`のSSA変換ロジックが追加され、スライスが拡張される際の`growslice`呼び出しと、それに伴うライトバリアの挿入が処理されます。また、ライトバリアの挿入ロジックが`insertWB`というヘルパー関数に抽象化され、`assign`関数内で利用されるよう変更されています。テストファイル`src/cmd/compile/internal/gc/ssa_test.go`には新しい`TestAppend`が追加され、`src/cmd/compile/internal/gc/testdata/append_ssa.go`には`append`操作のSSA変換を検証するための具体的なテストケースが記述されています。

## 変更の背景

このコミットは、Goコンパイラが従来の抽象構文木（AST）ベースの最適化から、より高度なSSA (Static Single Assignment) 形式への移行を進める「dev.ssa」ブランチの一部として行われました。SSA形式は、プログラムの各変数が一度だけ代入されるように表現する中間表現であり、これによりコンパイラはより強力で正確な最適化を適用できるようになります。

`append`関数はGo言語において非常に頻繁に使用される組み込み関数であり、その効率的なコンパイルはGoプログラム全体のパフォーマンスに直結します。従来のASTベースのコンパイルでは、`append`の複雑なロジック（特にスライスの容量が不足した場合の再割り当てとコピー、いわゆる`growslice`）が最適化の障壁となることがありました。SSA形式で`append`を表現することで、コンパイラはスライスのポインタ、長さ、容量といった要素を個別のSSA値として扱い、より詳細なデータフロー解析と最適化（例えば、不要な再割り当ての回避や、ライトバリアのより正確な配置）が可能になります。

特に、`append`がスライスを拡張する際に新しいメモリを割り当てる場合、ガベージコレクタ（GC）が正しく動作するために「ライトバリア（write barrier）」を挿入する必要があります。これは、GCがオブジェクトグラフを正確に追跡し、誤って参照されているオブジェクトを回収しないようにするためです。このコミットでは、`append`のSSA変換において、このライトバリアの挿入ロジックも適切に組み込まれています。

## 前提知識の解説

### Goのスライス (Slice)
Go言語のスライスは、配列への参照であり、以下の3つの要素で構成されます。
1.  **ポインタ (Pointer)**: スライスの基底となる配列の先頭要素へのポインタ。
2.  **長さ (Length)**: スライスに含まれる要素の数。
3.  **容量 (Capacity)**: スライスの基底となる配列の、ポインタから数えて利用可能な要素の総数。

`append`関数は、スライスに要素を追加するために使用されます。容量が不足している場合、`append`はより大きな容量を持つ新しい基底配列を割り当て、既存の要素をコピーし、新しい要素を追加します。この再割り当てとコピーの処理は`growslice`というランタイム関数によって行われます。

### ガベージコレクション (Garbage Collection) とライトバリア (Write Barrier)
Go言語は自動メモリ管理（ガベージコレクション）を採用しています。GCは、プログラムがもはや到達できないメモリ領域を自動的に解放し、メモリリークを防ぎます。

ライトバリアは、GCが実行されている最中に、プログラムがポインタを書き換える（つまり、オブジェクトグラフを変更する）際に挿入される特別なコードです。ライトバリアの目的は、GCがオブジェクトグラフをスキャンしている間にポインタが変更された場合でも、GCがすべてのライブオブジェクトを正確に識別できるようにすることです。特に、三色マーク＆スイープGCのような並行GCでは、GCがマークフェーズ中にオブジェクトの参照関係が変更されると、オブジェクトが誤って回収されてしまう「stale pointer problem」が発生する可能性があります。ライトバリアはこれを防ぎます。

`append`操作が新しい基底配列を割り当て、既存の要素を新しい配列にコピーする場合、ポインタの書き換えが発生します。このため、`growslice`が呼び出されるパスでは、GCの正確性を保証するためにライトバリアの挿入が不可欠となります。

### SSA (Static Single Assignment) 形式
SSA形式は、コンパイラの中間表現の一種で、プログラム中の各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、コンパイラはより効果的な最適化（例: 共通部分式の削除、デッドコードの削除、レジスタ割り当ての改善など）を実行できるようになります。

Goコンパイラでは、ASTからSSA形式に変換された後、様々な最適化パスが適用され、最終的に機械語コードが生成されます。`OAPPEND`をSSA形式で処理することは、`append`のセマンティクスをより低レベルで正確に表現し、コンパイラがその動作をより深く理解して最適化できるようにすることを意味します。

## 技術的詳細

このコミットにおける`OAPPEND`のSSA変換は、`append`関数の動作をSSA形式の命令とブロックに分解することで実現されています。

1.  **スライスの分解**: `append(s, e1, e2, e3)`のような操作は、まず元のスライス`s`からポインタ(`p`)、長さ(`l`)、容量(`c`)を抽出するSSA値に変換されます。
2.  **新しい長さの計算**: 追加される要素の数に基づいて、新しい長さ(`nl`)が計算されます。
3.  **容量チェックと分岐**: `nl`が現在の容量`c`を超えるかどうかをチェックする比較命令が生成されます。この結果に基づいて、プログラムの実行フローは2つのブロックに分岐します。
    *   **`grow`ブロック**: 容量が不足している場合、`growslice`ランタイム関数を呼び出すためのコードが生成されます。`growslice`は新しい、より大きな基底配列を割り当て、既存の要素をコピーし、新しいポインタ、長さ、容量を返します。
    *   **`assign`ブロック**: 容量が十分な場合、または`growslice`が完了した後、新しい要素をスライスの末尾に追加するためのコードが生成されます。
4.  **`growslice`の呼び出し**: `grow`ブロック内では、`growslice`関数を呼び出すための準備が行われます。これには、`growslice`が必要とする引数（元のスライス情報、新しい長さなど）をスタックに配置する処理が含まれます。`growslice`は`ssa.OpStaticCall`として表現されます。
5.  **`growslice`の結果の読み取り**: `growresult`ブロックでは、`growslice`の呼び出し結果（新しいポインタと容量）がスタックから読み取られ、SSA値として利用可能になります。
6.  **要素の代入とライトバリア**: `assign`ブロックでは、新しい要素がスライスの適切な位置に格納されます。この際、要素の型がポインタを含む場合（`haspointers(et)`）、ガベージコレクタの正確性を保証するために`insertWB`関数を介してライトバリアが挿入されます。これは、`typedmemmove_nostore`というランタイム関数を呼び出すことで実現されます。
7.  **結果スライスの構築**: 最終的に、新しいポインタ、長さ、容量を使用して、結果となるスライスを表すSSA値（`ssa.OpSliceMake`）が構築され、返されます。

`insertWB`関数は、ライトバリアのロジックをカプセル化しており、`writeBarrierEnabled`フラグのチェックと、`typedmemmove_nostore`ランタイム関数の呼び出しを含んでいます。この関数は、`assign`関数からも呼び出されるようになり、ポインタを含む値の代入時に常にライトバリアが考慮されるようになりました。

## コアとなるコードの解説

### `expr`関数内の`OAPPEND`ケース

このセクションは、`append`組み込み関数がどのようにSSA形式に変換されるかの核心部分です。

1.  **スライスと引数の評価**:
    *   `slice := s.expr(n.List.N)`: `append`の最初の引数である元のスライスをSSA値として評価します。
    *   `nargs := int64(count(n.List) - 1)`: 追加される要素の数を計算します。
    *   `args := make([]*ssa.Value, 0, nargs)`: 追加される各要素をSSA値として評価し、`args`スライスに格納します。

2.  **スライス情報の抽出**:
    *   `p := s.newValue1(ssa.OpSlicePtr, pt, slice)`: スライスから基底配列へのポインタを抽出します。
    *   `l := s.newValue1(ssa.OpSliceLen, Types[TINT], slice)`: スライスの長さを抽出します。
    *   `c := s.newValue1(ssa.OpSliceCap, Types[TINT], slice)`: スライスの容量を抽出します。

3.  **容量チェックと分岐**:
    *   `nl := s.newValue2(s.ssaOp(OADD, Types[TINT]), Types[TINT], l, s.constInt(Types[TINT], nargs))`: 新しい長さ`nl`を計算します（現在の長さ + 追加要素数）。
    *   `cmp := s.newValue2(s.ssaOp(OGT, Types[TINT]), Types[TBOOL], nl, c)`: `nl > c`（新しい長さが容量を超えるか）を比較します。
    *   この比較結果に基づいて、`ssa.BlockIf`タイプのブロックが生成され、`grow`ブロック（容量不足の場合）と`assign`ブロック（容量十分の場合）に分岐します。`ssa.BranchUnlikely`は、通常は容量が足りていると仮定し、`growslice`の呼び出しは稀なケースであることをコンパイラに伝えます。

4.  **`grow`ブロック (容量不足の場合)**:
    *   このブロックでは、`growslice`ランタイム関数を呼び出すための準備と実行が行われます。
    *   `taddr`, `spplus1`など: `growslice`に渡す引数（スライスの型情報、ポインタ、長さ、容量、新しい長さ）をスタックに格納するためのアドレス計算と`ssa.OpStore`命令が生成されます。
    *   `call := s.newValue1A(ssa.OpStaticCall, ssa.TypeMem, syslook("growslice", 0).Sym, s.mem())`: `growslice`関数を静的呼び出しとして表現します。
    *   `grow`ブロックは`ssa.BlockCall`タイプとなり、`growresult`ブロックに遷移します。

5.  **`growresult`ブロック (`growslice`の結果の読み取り)**:
    *   `growslice`が返した新しいポインタと容量をスタックから読み取り、`ptrvar`と`capvar`に格納します。

6.  **`assign`ブロック (要素の代入)**:
    *   `p = s.variable(&ptrvar, pt)`: `grow`ブロックと`assign`ブロックからの`ptr`のSSA値を結合するPHI関数が生成されます。これにより、`p`は常に正しい基底配列ポインタを参照します。`c`（容量）についても同様です。
    *   `p2 := s.newValue2(ssa.OpPtrIndex, pt, p, l)`: 新しい要素を格納する開始位置（現在の長さの次）を計算します。
    *   `for i, arg := range args`: 追加される各要素についてループします。
        *   `addr := s.newValue2(ssa.OpPtrIndex, pt, p2, s.constInt(Types[TUINTPTR], int64(i)))`: 各要素の格納アドレスを計算します。
        *   `s.vars[&memvar] = s.newValue3I(ssa.OpStore, ssa.TypeMem, et.Size(), addr, arg, s.mem())`: 要素を計算されたアドレスに格納します。
        *   `if haspointers(et) { s.insertWB(et, addr) }`: 要素の型がポインタを含む場合、`insertWB`を呼び出してライトバリアを挿入します。

7.  **結果スライスの構築**:
    *   `r := s.newValue3(ssa.OpSliceMake, n.Type, p, nl, c)`: 最終的なスライス（ポインタ`p`、新しい長さ`nl`、容量`c`）を表すSSA値を作成し、`append`操作の結果として返します。

### `insertWB`関数

この関数は、ライトバリアの挿入ロジックを共通化するために導入されました。

1.  **`writeBarrierEnabled`チェック**:
    *   `flagaddr := s.newValue1A(ssa.OpAddr, Ptrto(Types[TBOOL]), aux, s.sb)`: グローバル変数`writeBarrierEnabled`のアドレスを取得します。
    *   `flag := s.newValue2(ssa.OpLoad, Types[TBOOL], flagaddr, s.mem())`: `writeBarrierEnabled`の値をロードします。
    *   このフラグの値に基づいて、`ssa.BlockIf`タイプのブロックが生成され、ライトバリアを挿入する`bThen`ブロックと、スキップする`bNext`ブロックに分岐します。`ssa.BranchUnlikely`は、ライトバリアが有効でないケースが稀であることを示唆します。

2.  **`bThen`ブロック (ライトバリアの挿入)**:
    *   `typedmemmove_nostore`ランタイム関数を呼び出すための準備が行われます。この関数は、GCがポインタの書き換えを追跡するために使用されます。
    *   `taddr`, `spplus8`: `typedmemmove_nostore`に渡す引数（書き込まれた値の型情報、書き込み先のアドレス）をスタックに格納するためのアドレス計算と`ssa.OpStore`命令が生成されます。
    *   `call := s.newValue1A(ssa.OpStaticCall, ssa.TypeMem, syslook("typedmemmove_nostore", 0).Sym, s.mem())`: `typedmemmove_nostore`関数を静的呼び出しとして表現します。
    *   このブロックは`ssa.BlockCall`タイプとなり、`bNext`ブロックに遷移します。

この`insertWB`関数は、`assign`関数からも呼び出されるようになり、`append`だけでなく、ポインタを含む値の一般的な代入操作においてもライトバリアが適切に挿入されるようになりました。これにより、GCの正確性が向上し、コンパイラのコード生成がより堅牢になります。

## 変更の背景

このコミットは、Goコンパイラが従来の抽象構文木（AST）ベースの最適化から、より高度なSSA (Static Single Assignment) 形式への移行を進める「dev.ssa」ブランチの一部として行われました。SSA形式は、プログラムの各変数が一度だけ代入されるように表現する中間表現であり、これによりコンパイラはより強力で正確な最適化を適用できるようになります。

`append`関数はGo言語において非常に頻繁に使用される組み込み関数であり、その効率的なコンパイルはGoプログラム全体のパフォーマンスに直結します。従来のASTベースのコンパイルでは、`append`の複雑なロジック（特にスライスの容量が不足した場合の再割り当てとコピー、いわゆる`growslice`）が最適化の障壁となることがありました。SSA形式で`append`を表現することで、コンパイラはスライスのポインタ、長さ、容量といった要素を個別のSSA値として扱い、より詳細なデータフロー解析と最適化（例えば、不要な再割り当ての回避や、ライトバリアのより正確な配置）が可能になります。

特に、`append`がスライスを拡張する際に新しいメモリを割り当てる場合、ガベージコレクタ（GC）が正しく動作するために「ライトバリア（write barrier）」を挿入する必要があります。これは、GCがオブジェクトグラフを正確に追跡し、誤って参照されているオブジェクトを回収しないようにするためです。このコミットでは、`append`のSSA変換において、このライトバリアの挿入ロジックも適切に組み込まれています。

## 前提知識の解説

### Goのスライス (Slice)
Go言語のスライスは、配列への参照であり、以下の3つの要素で構成されます。
1.  **ポインタ (Pointer)**: スライスの基底となる配列の先頭要素へのポインタ。
2.  **長さ (Length)**: スライスに含まれる要素の数。
3.  **容量 (Capacity)**: スライスの基底となる配列の、ポインタから数えて利用可能な要素の総数。

`append`関数は、スライスに要素を追加するために使用されます。容量が不足している場合、`append`はより大きな容量を持つ新しい基底配列を割り当て、既存の要素をコピーし、新しい要素を追加します。この再割り当てとコピーの処理は`growslice`というランタイム関数によって行われます。

### ガベージコレクション (Garbage Collection) とライトバリア (Write Barrier)
Go言語は自動メモリ管理（ガベージコレクション）を採用しています。GCは、プログラムがもはや到達できないメモリ領域を自動的に解放し、メモリリークを防ぎます。

ライトバリアは、GCが実行されている最中に、プログラムがポインタを書き換える（つまり、オブジェクトグラフを変更する）際に挿入される特別なコードです。ライトバリアの目的は、GCがオブジェクトグラフをスキャンしている間にポインタが変更された場合でも、GCがすべてのライブオブジェクトを正確に識別できるようにすることです。特に、三色マーク＆スイープGCのような並行GCでは、GCがマークフェーズ中にオブジェクトの参照関係が変更されると、オブジェクトが誤って回収されてしまう「stale pointer problem」が発生する可能性があります。ライトバリアはこれを防ぎます。

`append`操作が新しい基底配列を割り当て、既存の要素を新しい配列にコピーする場合、ポインタの書き換えが発生します。このため、`growslice`が呼び出されるパスでは、GCの正確性を保証するためにライトバリアの挿入が不可欠となります。

### SSA (Static Single Assignment) 形式
SSA形式は、コンパイラの中間表現の一種で、プログラム中の各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、コンパイラはより効果的な最適化（例: 共通部分式の削除、デッドコードの削除、レジスタ割り当ての改善など）を実行できるようになります。

Goコンパイラでは、ASTからSSA形式に変換された後、様々な最適化パスが適用され、最終的に機械語コードが生成されます。`OAPPEND`をSSA形式で処理することは、`append`のセマンティクスをより低レベルで正確に表現し、コンパイラがその動作をより深く理解して最適化できるようにすることを意味します。

## 技術的詳細

このコミットにおける`OAPPEND`のSSA変換は、`append`関数の動作をSSA形式の命令とブロックに分解することで実現されています。

1.  **スライスの分解**: `append(s, e1, e2, e3)`のような操作は、まず元のスライス`s`からポインタ(`p`)、長さ(`l`)、容量(`c`)を抽出するSSA値に変換されます。
2.  **新しい長さの計算**: 追加される要素の数に基づいて、新しい長さ(`nl`)が計算されます。
3.  **容量チェックと分岐**: `nl`が現在の容量`c`を超えるかどうかをチェックする比較命令が生成されます。この結果に基づいて、プログラムの実行フローは2つのブロックに分岐します。
    *   **`grow`ブロック**: 容量が不足している場合、`growslice`ランタイム関数を呼び出すためのコードが生成されます。`growslice`は新しい、より大きな基底配列を割り当て、既存の要素をコピーし、新しいポインタ、長さ、容量を返します。
    *   **`assign`ブロック**: 容量が十分な場合、または`growslice`が完了した後、新しい要素をスライスの末尾に追加するためのコードが生成されます。
4.  **`growslice`の呼び出し**: `grow`ブロック内では、`growslice`関数を呼び出すための準備が行われます。これには、`growslice`が必要とする引数（元のスライス情報、新しい長さなど）をスタックに配置する処理が含まれます。`growslice`は`ssa.OpStaticCall`として表現されます。
5.  **`growslice`の結果の読み取り**: `growresult`ブロックでは、`growslice`の呼び出し結果（新しいポインタと容量）がスタックから読み取られ、SSA値として利用可能になります。
6.  **要素の代入とライトバリア**: `assign`ブロックでは、新しい要素がスライスの適切な位置に格納されます。この際、要素の型がポインタを含む場合（`haspointers(et)`）、ガベージコレクタの正確性を保証するために`insertWB`関数を介してライトバリアが挿入されます。これは、`typedmemmove_nostore`というランタイム関数を呼び出すことで実現されます。
7.  **結果スライスの構築**: 最終的に、新しいポインタ、長さ、容量を使用して、結果となるスライスを表すSSA値（`ssa.OpSliceMake`）が構築され、返されます。

`insertWB`関数は、ライトバリアのロジックをカプセル化しており、`writeBarrierEnabled`フラグのチェックと、`typedmemmove_nostore`ランタイム関数の呼び出しを含んでいます。この関数は、`assign`関数からも呼び出されるようになり、ポインタを含む値の代入時に常にライトバリアが考慮されるようになりました。

## コアとなるコードの解説

### `expr`関数内の`OAPPEND`ケース

このセクションは、`append`組み込み関数がどのようにSSA形式に変換されるかの核心部分です。

1.  **スライスと引数の評価**:
    *   `slice := s.expr(n.List.N)`: `append`の最初の引数である元のスライスをSSA値として評価します。
    *   `nargs := int64(count(n.List) - 1)`: 追加される要素の数を計算します。
    *   `args := make([]*ssa.Value, 0, nargs)`: 追加される各要素をSSA値として評価し、`args`スライスに格納します。

2.  **スライス情報の抽出**:
    *   `p := s.newValue1(ssa.OpSlicePtr, pt, slice)`: スライスから基底配列へのポインタを抽出します。
    *   `l := s.newValue1(ssa.OpSliceLen, Types[TINT], slice)`: スライスの長さを抽出します。
    *   `c := s.newValue1(ssa.OpSliceCap, Types[TINT], slice)`: スライスの容量を抽出します。

3.  **新しい長さの計算と容量チェック、分岐**:
    *   `nl := s.newValue2(s.ssaOp(OADD, Types[TINT]), Types[TINT], l, s.constInt(Types[TINT], nargs))`: 新しい長さ`nl`を計算します（現在の長さ + 追加要素数）。
    *   `cmp := s.newValue2(s.ssaOp(OGT, Types[TINT]), Types[TBOOL], nl, c)`: `nl > c`（新しい長さが容量を超えるか）を比較します。
    *   この比較結果に基づいて、`ssa.BlockIf`タイプのブロックが生成され、`grow`ブロック（容量不足の場合）と`assign`ブロック（容量十分の場合）に分岐します。`ssa.BranchUnlikely`は、通常は容量が足りていると仮定し、`growslice`の呼び出しは稀なケースであることをコンパイラに伝えます。

4.  **`grow`ブロック (容量不足の場合)**:
    *   このブロックでは、`growslice`ランタイム関数を呼び出すための準備と実行が行われます。
    *   `taddr`, `spplus1`など: `growslice`に渡す引数（スライスの型情報、ポインタ、長さ、容量、新しい長さ）をスタックに格納するためのアドレス計算と`ssa.OpStore`命令が生成されます。
    *   `call := s.newValue1A(ssa.OpStaticCall, ssa.TypeMem, syslook("growslice", 0).Sym, s.mem())`: `growslice`関数を静的呼び出しとして表現します。
    *   `grow`ブロックは`ssa.BlockCall`タイプとなり、`growresult`ブロックに遷移します。

5.  **`growresult`ブロック (`growslice`の結果の読み取り)**:
    *   `growslice`が返した新しいポインタと容量をスタックから読み取り、`ptrvar`と`capvar`に格納します。

6.  **`assign`ブロック (要素の代入)**:
    *   `p = s.variable(&ptrvar, pt)`: `grow`ブロックと`assign`ブロックからの`ptr`のSSA値を結合するPHI関数が生成されます。これにより、`p`は常に正しい基底配列ポインタを参照します。`c`（容量）についても同様です。
    *   `p2 := s.newValue2(ssa.OpPtrIndex, pt, p, l)`: 新しい要素を格納する開始位置（現在の長さの次）を計算します。
    *   `for i, arg := range args`: 追加される各要素についてループします。
        *   `addr := s.newValue2(ssa.OpPtrIndex, pt, p2, s.constInt(Types[TUINTPTR], int64(i)))`: 各要素の格納アドレスを計算します。
        *   `s.vars[&memvar] = s.newValue3I(ssa.OpStore, ssa.TypeMem, et.Size(), addr, arg, s.mem())`: 要素を計算されたアドレスに格納します。
        *   `if haspointers(et) { s.insertWB(et, addr) }`: 要素の型がポインタを含む場合、`insertWB`を呼び出してライトバリアを挿入します。

7.  **結果スライスの構築**:
    *   `r := s.newValue3(ssa.OpSliceMake, n.Type, p, nl, c)`: 最終的なスライス（ポインタ`p`、新しい長さ`nl`、容量`c`）を表すSSA値を作成し、`append`操作の結果として返します。

### `insertWB`関数

この関数は、ライトバリアの挿入ロジックを共通化するために導入されました。

1.  **`writeBarrierEnabled`チェック**:
    *   `flagaddr := s.newValue1A(ssa.OpAddr, Ptrto(Types[TBOOL]), aux, s.sb)`: グローバル変数`writeBarrierEnabled`のアドレスを取得します。
    *   `flag := s.newValue2(ssa.OpLoad, Types[TBOOL], flagaddr, s.mem())`: `writeBarrierEnabled`の値をロードします。
    *   このフラグの値に基づいて、`ssa.BlockIf`タイプのブロックが生成され、ライトバリアを挿入する`bThen`ブロックと、スキップする`bNext`ブロックに分岐します。`ssa.BranchUnlikely`は、ライトバリアが有効でないケースが稀であることを示唆します。

2.  **`bThen`ブロック (ライトバリアの挿入)**:
    *   `typedmemmove_nostore`ランタイム関数を呼び出すための準備が行われます。この関数は、GCがポインタの書き換えを追跡するために使用されます。
    *   `taddr`, `spplus8`: `typedmemmove_nostore`に渡す引数（書き込まれた値の型情報、書き込み先のアドレス）をスタックに格納するためのアドレス計算と`ssa.OpStore`命令が生成されます。
    *   `call := s.newValue1A(ssa.OpStaticCall, ssa.TypeMem, syslook("typedmemmove_nostore", 0).Sym, s.mem())`: `typedmemmove_nostore`関数を静的呼び出しとして表現します。
    *   このブロックは`ssa.BlockCall`タイプとなり、`bNext`ブロックに遷移します。

この`insertWB`関数は、`assign`関数からも呼び出されるようになり、`append`だけでなく、ポインタを含む値の一般的な代入操作においてもライトバリアが適切に挿入されるようになりました。これにより、GCの正確性が向上し、コンパイラのコード生成がより堅牢になります。

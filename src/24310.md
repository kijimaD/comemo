# [インデックス 24310] ファイルの概要

このコミットは、Goランタイムの`cgo`パッケージがGoのレース検出器（Race Detector）と互換性を持つようにするための重要な変更を導入しています。特に、Goランタイム内で`m`（マシン/OSスレッド）や`g`（ゴルーチン）のコンテキストなしで実行される特定の関数について、レース検出器による監視を明示的に無効化する`//go:norace`プラグマを追加しています。これにより、これらの特殊な関数がレース検出器の誤検出を引き起こすことなく、正しく機能するようになります。

## 元コミット内容

Goランタイムの`cgo`関連コードをレース検出器と互換性のあるものにする。
一部のルーチンは`m`（OSスレッド）や`g`（ゴルーチン）のコンテキストなしで実行されるため、レース検出器のランタイムを呼び出すことができない。これらのルーチンはランタイムに対して不透明である必要がある。以前はC言語で書かれていたため、この特性は自然に満たされていた。しかし、これらのルーチンがGo言語で書かれるようになった現在、それらの関数に対するレース検出器のアノテーションを明示的に無効にする必要がある。
この変更にはテストも追加されている。
Issue #10874 を修正する。

## 変更の背景

Goのレース検出器は、並行処理におけるデータ競合（data race）を検出するための強力なツールです。しかし、Goランタイムの特定の低レベルな部分、特にC言語との相互運用（cgo）に関連するコードやシグナルハンドリングのコードは、通常のGoプログラムとは異なる特殊な実行コンテキストで動作します。

具体的には、`cgo`コールバック関数やシグナルハンドラのようなルーチンは、Goのスケジューラが管理する`g`（ゴルーチン）や`m`（OSスレッド）のコンテキストが完全に確立されていない状態で実行されることがあります。このような環境では、レース検出器が期待するランタイムの状態（例えば、現在のゴルーチンやOSスレッドに関する情報）が存在しないため、レース検出器の内部ロジックが正しく動作せず、誤ったデータ競合を報告したり、クラッシュを引き起こしたりする可能性があります。

以前は、これらの特殊なルーチンはC言語で実装されていたため、Goのレース検出器の監視対象外でした。しかし、Go言語の進化に伴い、これらのルーチンの一部がGoで再実装されるようになりました。Goで書かれたコードはデフォルトでレース検出器の対象となるため、特殊な実行コンテキストで動作するこれらのルーチンがレース検出器によって誤って監視され、問題が発生する可能性が出てきました。

このコミットは、この問題を解決するために、Goコンパイラに新しいプラグマ`//go:norace`を導入し、特定の関数に対してレース検出器のアノテーション生成を明示的に抑制することを目的としています。これにより、Goで書かれた低レベルなランタイムコードがレース検出器と安全に共存できるようになります。

## 前提知識の解説

### Goの並行処理とゴルーチン、OSスレッド（M, G, P）

Go言語は、軽量な並行処理の単位である「ゴルーチン（goroutine）」を提供します。ゴルーチンはOSスレッドよりもはるかに軽量で、数百万個を同時に実行することも可能です。Goランタイムは、これらのゴルーチンをOSスレッドにマッピングし、効率的にスケジューリングします。

このスケジューリングモデルは、一般的に「M:Nスケジューリング」と呼ばれ、Goランタイム内部では以下の3つの主要なエンティティによって管理されます。

*   **G (Goroutine)**: Goの並行処理の単位。軽量なスレッドのようなもの。
*   **M (Machine/OS Thread)**: 実際のOSスレッド。Goランタイムは複数のMを管理し、その上でGを実行します。
*   **P (Processor)**: 論理的なプロセッサ。MとGの間の仲介役となり、GがM上で実行されるためのコンテキストを提供します。Pは実行可能なGのキューを保持し、MがPからGを取得して実行します。

通常のGoコードは、常にGとMのコンテキスト内で実行されます。しかし、`cgo`コールバックやシグナルハンドラのような特殊なケースでは、これらのコンテキストが完全に確立されていない状態でコードが実行されることがあります。

### Goのレース検出器（Race Detector）

Goのレース検出器は、Goプログラムにおけるデータ競合（複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に発生するバグ）を検出するためのツールです。`go run -race`や`go build -race`、`go test -race`のように`-race`フラグを付けてコンパイル・実行することで有効になります。

レース検出器は、コンパイル時に特別なインストゥルメンテーションコードを挿入し、実行時にメモリアクセスを監視します。これにより、データ競合が発生した際に詳細なレポートを出力し、開発者がバグを特定・修正するのを助けます。

レース検出器は、Goランタイムの特定の機能（例えば、現在のゴルーチンIDの取得など）に依存して動作します。そのため、GやMのコンテキストが不完全な状態で実行されるコードでは、レース検出器が正しく機能しないか、あるいは予期せぬ動作を引き起こす可能性があります。

### Goコンパイラプラグマ（Compiler Pragmas）

Goコンパイラは、コードの特定の振る舞いを制御するために、特別なコメント形式の「プラグマ」をサポートしています。これらは`//go:`で始まる行として記述され、コンパイラにヒントや指示を与えます。

このコミットで関連するのは以下のプラグマです。

*   `//go:nosplit`: この関数はスタックを分割しないことをコンパイラに指示します。これは、スタックの拡張が必要な場合に発生する可能性のある、`m`や`g`のコンテキストに依存する処理を避けるために使用されます。低レベルなランタイムコードでよく見られます。
*   `//go:norace` (このコミットで導入): この関数に対してレース検出器のアノテーションを生成しないことをコンパイラに指示します。

### cgo

`cgo`は、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのメカニズムです。GoとCの間のインターフェースを提供し、OSのシステムコールや既存のCライブラリを利用する際に不可欠です。

`cgo`のコールバックメカニズムは、CコードがGo関数を呼び出す際に使用されます。このコールバックは、Goランタイムが通常のゴルーチンをスケジューリングするのとは異なる方法で実行されるため、特殊なコンテキストの問題が発生しやすい箇所です。

## 技術的詳細

このコミットの核心は、Goコンパイラが`//go:norace`プラグマを認識し、そのプラグマが付与された関数に対してレース検出器のインストゥルメンテーションコードを生成しないようにすることです。

具体的な変更点は以下の通りです。

1.  **コンパイラの変更**:
    *   `src/cmd/compile/internal/gc/syntax.go`の`Func`構造体に`Norace bool`フィールドが追加されました。これは、関数が`norace`としてマークされているかどうかを示すフラグです。
    *   `src/cmd/compile/internal/gc/go.go`に`norace`というグローバル変数が追加されました。これは、パーサーが`//go:norace`プラグマを検出したときに設定される一時的なフラグです。
    *   `src/cmd/compile/internal/gc/lex.go`の`getlinepragma`関数が変更され、`//go:norace`という文字列を認識し、`norace`グローバル変数を`true`に設定するようになりました。
    *   `src/cmd/compile/internal/gc/go.y` (Goコンパイラの構文解析器の定義ファイル) が更新され、関数宣言を解析する際に`norace`グローバル変数の値を`Func`構造体の`Norace`フィールドにコピーするようになりました。これにより、`//go:norace`プラグマが関数定義に紐付けられます。
    *   `src/cmd/compile/internal/gc/racewalk.go`の`racewalk`関数（レース検出器のインストゥルメンテーションを決定する部分）が変更され、`fn.Func.Norace`が`true`の場合にはレース検出器の処理をスキップするようになりました。

2.  **ランタイムおよびcgoコードへの適用**:
    *   `src/cmd/cgo/out.go`: `cgo`がGo関数をCにエクスポートする際に生成するラッパー関数（`_cgoexp%s_%s`）に`//go:norace`プラグマが追加されました。これらの関数はCから呼び出されるため、Goの`m`や`g`のコンテキストなしで実行される可能性があります。
    *   `src/runtime/cgo/callbacks.go`: `_cgo_panic`関数に`//go:norace`プラグマが追加されました。この関数は`cgo`コールバック中にパニックが発生した場合に呼び出される可能性があり、特殊なコンテキストで動作します。
    *   `src/runtime/sigqueue.go`: `badsignal`関数に`//go:norace`プラグマが追加されました。この関数はシグナルハンドラの一部として、外部スタック上で`m`や`g`なしで実行されるため、レース検出器の監視から除外する必要があります。

3.  **テストの追加**:
    *   `src/cmd/dist/test.go`: `cgo`が有効な場合に、`-race`フラグを付けて`misc/cgo/test`ディレクトリのテストを実行する新しいテストケースが追加されました。これにより、`cgo`とレース検出器の互換性が検証されます。

これらの変更により、Goコンパイラは`//go:norace`プラグマを認識し、その指示に従ってレース検出器のコード生成を抑制します。これにより、Goランタイムの低レベルな部分がレース検出器の誤検出やクラッシュを引き起こすことなく、安全にGoで実装できるようになりました。

## コアとなるコードの解説

### コンパイラ側の変更

*   **`src/cmd/compile/internal/gc/syntax.go` (`Func`構造体への`Norace`フィールド追加)**:
    Goコンパイラは、ソースコードを抽象構文木（AST）に変換し、その中で関数に関する情報を`Func`構造体に格納します。`Norace bool`フィールドの追加は、特定の関数がレース検出器の対象外であることをコンパイラが内部的に追跡できるようにするためのものです。このフラグは、後続のコンパイルフェーズ、特にレース検出器のインストゥルメンテーションコードを挿入するフェーズで参照されます。

*   **`src/cmd/compile/internal/gc/go.go` (`norace`グローバル変数の追加)**:
    これは、Goコンパイラの字句解析器（lexer）と構文解析器（parser）の間で`//go:norace`プラグマの状態を一時的に保持するためのフラグです。字句解析器がプラグマを読み取るとこのフラグをセットし、構文解析器が関数定義を処理する際にこのフラグの値を`Func`構造体に転送します。

*   **`src/cmd/compile/internal/gc/lex.go` (`getlinepragma`関数の変更)**:
    `getlinepragma`関数は、Goソースコード内の`//go:`で始まるプラグマを解析する役割を担っています。この変更により、`"go:norace"`という文字列が検出された場合、前述の`norace`グローバル変数を`true`に設定します。これにより、コンパイラは現在の関数定義に`norace`プラグマが適用されていることを認識します。

*   **`src/cmd/compile/internal/gc/go.y` (構文解析器の更新)**:
    `go.y`はGo言語の文法を定義するYacc/Bison形式のファイルです。このファイルが更新され、関数宣言が解析される際に、`norace`グローバル変数の値が`Func`構造体の`Norace`フィールドに適切に割り当てられるようになりました。これにより、ソースコード上の`//go:norace`プラグマが、コンパイラの内部表現に正確に反映されます。

*   **`src/cmd/compile/internal/gc/racewalk.go` (`racewalk`関数の変更)**:
    `racewalk`関数は、Goコンパイラのバックエンドの一部であり、レース検出器のインストゥルメンテーションを挿入するかどうかを決定するロジックを含んでいます。変更された行`if ispkgin(omit_pkgs) || isforkfunc(fn) || fn.Func.Norace { return }`は、関数が特定のパッケージに属しているか（`ispkgin`）、特定のフォーク関連関数であるか（`isforkfunc`）、または`Norace`フラグが設定されている場合（`fn.Func.Norace`）に、レース検出器の処理をスキップするように指示しています。これにより、`//go:norace`が指定された関数は、レース検出器の監視対象から除外されます。

### ランタイムコードへの適用

*   **`src/cmd/cgo/out.go` (`//go:norace`の追加)**:
    `cgo`が生成するGoのエクスポート関数（Cから呼び出されるGo関数）に`//go:norace`が追加されました。これらの関数は、Cコードから呼び出される際にGoのスケジューラが管理する通常のゴルーチンコンテキスト外で実行されるため、レース検出器の誤検出を避けるために明示的に除外されます。`//go:nosplit`も同時に指定されており、これはスタックの分割も行わないことを示しています。

*   **`src/runtime/cgo/callbacks.go` (`_cgo_panic`への`//go:norace`追加)**:
    `_cgo_panic`関数は、`cgo`コールバック中にGo側でパニックが発生した場合に呼び出されるランタイム関数です。この関数もまた、通常のGoの実行コンテキストとは異なる状況で呼び出される可能性があるため、レース検出器の監視から除外されます。

*   **`src/runtime/sigqueue.go` (`badsignal`への`//go:norace`追加)**:
    `badsignal`関数は、Goランタイムのシグナルハンドリングの一部です。コメントにもあるように、「外部スタック上で、`m`や`g`なしで実行される」ため、レース検出器の監視から除外する必要があります。

### テストの追加

*   **`src/cmd/dist/test.go` (`raceTest`関数の変更)**:
    `dist`ツールはGoのビルドとテストの実行を管理します。この変更は、`cgo`が有効な環境で、`misc/cgo/test`ディレクトリ内のテストを`-race`フラグ付きで実行するように指示しています。これにより、`cgo`とレース検出器の組み合わせが正しく機能し、`//go:norace`が意図通りに動作していることを検証します。`GOTRACEBACK=2`環境変数を設定することで、パニック発生時のスタックトレースをより詳細に表示するようにしています。

これらの変更は、Goランタイムの堅牢性を高め、特に低レベルなシステムプログラミングやC言語との相互運用において、レース検出器の有用性を維持しつつ、誤検出を排除するための重要なステップです。

# [インデックス 23879] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるマークフェーズの動作を調整し、特にマーク終了フェーズ（Stop-The-World: STWフェーズ）での作業量を減らすことで、GCレイテンシを削減することを目的としています。具体的には、マークフェーズが作業を終えたと判断した際に、より積極的にオブジェクトを「黒く」塗る（blacken）ことで、STWフェーズでの負担を軽減します。

## コミット

```
commit 90a19961f2b885ee253b2d51820977dc9c635f0c
Author: Rick Hudson <rlh@golang.org>
Date:   Mon Jun 1 18:16:03 2015 -0400

    runtime: reduce latency by aggressively ending mark phase

    Some latency regressions have crept into our system over the past few
    weeks. This CL fixes those by having the mark phase more aggressively
    blacken objects so that the mark termination phase, a STW phase, has less
    work to do. Three approaches were taken when the mark phase believes
    it has no more work to do, ie all work buffers are empty.
    If things have gone well the mark phase is correct and there is
    in fact little or no work. In that case the following items will
    take very little time. If the mark phase is wrong this CL will
    ferret that work out and give the mark phase a chance to deal with
    it concurrently before mark termination begins.

    When the mark phase first appears to be out of work, it does three things:
    1) It switches from allocating white to allocating black to reduce the
    number of unmarked objects reachable only from stacks.
    2) It flushes and disables per-P GC work caches so all work must be in
    globally visible work buffers.
    3) It rescans the global roots---th e BSS and data segments---so there
    are fewer objects to blacken during mark termination. We do not rescan
    stacks at this point, though that could be done in a later CL.
    After these steps, it again drains the global work buffers.

    On a lightly loaded machine the garbage benchmark has reduced the
    number of GC cycles with latency > 10 ms from 83 out of 4083 cycles
    down to 2 out of 3995 cycles. Maximum latency was reduced from
    60+ msecs down to 20 ms.
```

## 元コミット内容

Goランタイムにおいて、マークフェーズを積極的に終了させることでレイテンシを削減する。

過去数週間にわたりシステムに忍び寄っていたいくつかのレイテンシ回帰を、このCL（Change List）は修正する。これは、マークフェーズがより積極的にオブジェクトを黒く塗ることで、STWフェーズであるマーク終了フェーズの作業量を減らすことによって実現される。マークフェーズが作業を終えたと判断した際、つまりすべてのワークバッファが空になった際に、3つのアプローチが取られる。

もし順調に進んでいれば、マークフェーズは正しく、実際にはほとんど、あるいは全く作業がない。その場合、以下の項目はほとんど時間を要しないだろう。もしマークフェーズが間違っている場合、このCLはその作業を見つけ出し、マーク終了が始まる前にマークフェーズが並行してそれに対処する機会を与える。

マークフェーズが最初に作業がなくなったように見えたとき、それは3つのことを行う：
1) スタックからのみ到達可能なマークされていないオブジェクトの数を減らすために、白いオブジェクトの割り当てから黒いオブジェクトの割り当てに切り替える。
2) すべての作業がグローバルに可視なワークバッファにあるように、PごとのGCワークキャッシュをフラッシュして無効にする。
3) グローバルルート（BSSおよびデータセグメント）を再スキャンし、マーク終了中に黒く塗るオブジェクトを減らす。この時点ではスタックは再スキャンしないが、これは後のCLで行うことができる。
これらのステップの後、再びグローバルワークバッファをドレインする。

負荷の低いマシンでのガベージベンチマークでは、レイテンシが10ミリ秒を超えるGCサイクル数が、4083サイクル中83回から3995サイクル中2回に減少した。最大レイテンシは60ミリ秒以上から20ミリ秒に削減された。

## 変更の背景

このコミットの背景には、Goランタイムのガベージコレクション（GC）において、いくつかのレイテンシ回帰（latency regressions）が発生していたという問題があります。GoのGCは、アプリケーションの実行と並行して動作するコンカレントGCを基本としていますが、GCの特定のフェーズ、特にマーク終了フェーズでは、すべてのアプリケーションゴルーチンが一時停止する「Stop-The-World (STW)」が発生します。このSTWの時間が長くなると、アプリケーションの応答性が低下し、ユーザー体験に悪影響を及ぼします。

コミットメッセージによると、過去数週間にわたってこのレイテンシが増加する傾向が見られたため、その原因を特定し、改善する必要がありました。GoのGCは、STW時間を最小限に抑えることを目標としており、この目標を達成するために、マークフェーズの効率を向上させ、マーク終了フェーズでの作業量を削減することが重要であると判断されました。

具体的には、マークフェーズが「作業がなくなった」と判断した際に、実際にはまだ処理すべきオブジェクトが残っている可能性があり、それがSTWフェーズに持ち越されてレイテンシを増加させていたと考えられます。このコミットは、この問題を解決するために、マークフェーズがより積極的に残りの作業を処理し、STWフェーズでの負担を軽減するメカニズムを導入しています。

## 前提知識の解説

このコミットを理解するためには、Goのガベージコレクション（GC）の基本的な概念と用語を把握しておく必要があります。

### Goのガベージコレクション (GC)

GoのGCは、主に**三色マーク＆スイープ**アルゴリズムに基づいています。これは、オブジェクトを以下の3つの色に分類して管理します。

*   **白 (White)**: まだGCによって到達可能であると判断されていないオブジェクト。GCサイクルの開始時には、すべてのオブジェクトが白として扱われます。最終的に白のまま残ったオブジェクトは、到達不可能と判断され、回収の対象となります。
*   **灰 (Gray)**: GCによって到達可能であると判断されたが、そのオブジェクトが参照している他のオブジェクト（子オブジェクト）がまだスキャンされていない状態のオブジェクト。
*   **黒 (Black)**: GCによって到達可能であると判断され、かつそのオブジェクトが参照しているすべての子オブジェクトもスキャン済みである状態のオブジェクト。黒いオブジェクトは、このGCサイクルでは回収されません。

GCのプロセスは、大まかに以下のフェーズで構成されます。

1.  **マーク開始 (Mark Start)**: 短いSTWフェーズ。GCルート（グローバル変数、スタック上のポインタなど）を特定し、それらが参照するオブジェクトを灰にマークします。
2.  **マークフェーズ (Mark Phase)**: コンカレントフェーズ。アプリケーションの実行と並行して、灰色のオブジェクトをスキャンし、その子オブジェクトを灰にマークし、自身を黒にマークします。このフェーズの大部分はSTWなしで実行されます。
3.  **マーク終了 (Mark Termination)**: 短いSTWフェーズ。マークフェーズで取りこぼされた可能性のあるオブジェクトの最終処理や、GCの状態のクリーンアップを行います。このフェーズのSTW時間が、アプリケーションのレイテンシに直接影響します。
4.  **スイープフェーズ (Sweep Phase)**: コンカレントフェーズ。マークされなかった白いオブジェクト（到達不可能なオブジェクト）をメモリから解放します。

### Stop-The-World (STW)

STWは、ガベージコレクションの特定の段階で、すべてのアプリケーションゴルーチン（Goの軽量スレッド）の実行を一時的に停止させる期間を指します。GoのGCはSTW時間を最小限に抑えるように設計されていますが、メモリの整合性を保証するために、マーク開始とマーク終了の2つのフェーズでSTWが不可欠です。このSTW時間が長くなると、アプリケーションの応答性が低下し、ユーザー体験に悪影響を及ぼします。

### ライトバリア (Write Barrier)

コンカレントGCにおいて、アプリケーションがオブジェクトの参照を変更する際に、GCの整合性を保つために実行されるメカニズムです。GoのGCでは、アプリケーションがポインタを書き換える際にライトバリアが挿入され、GCがオブジェクトの参照関係を正しく追跡できるようにします。これにより、GCが実行中にオブジェクトの参照が変更されても、誤ってライブオブジェクトが回収されることを防ぎます。

### オブジェクトの黒塗り (Blackening Objects)

三色マークアルゴリズムにおける「黒」の状態にオブジェクトを遷移させることを指します。オブジェクトが黒に塗られると、そのオブジェクトは到達可能であり、かつその参照先もすべてスキャン済みであることが保証されます。このコミットでは、マークフェーズ中に積極的にオブジェクトを黒く塗ることで、マーク終了フェーズでの作業量を減らすことを目指しています。

### ワークバッファ (Work Buffers)

GCのマークフェーズ中に、スキャンすべき灰色のオブジェクトのポインタを一時的に格納するバッファです。GCワーカーはこれらのバッファからオブジェクトを取り出し、スキャンし、新しい灰色のオブジェクトをバッファに追加します。GoのGCでは、グローバルなワークバッファと、各P（Processor）に紐づくローカルなワークキャッシュが存在します。

### P (Processor)

Goランタイムにおける論理的なプロセッサの抽象化です。GoスケジューラはゴルーチンをOSスレッドにマッピングし、これらのスレッドはPに割り当てられます。多くのランタイム操作、GCの側面を含む、は利用可能なCPUコア間で作業を効率的に分散し、競合を最小限に抑えるために「Pごと」に設計されています。

### グローバルルート (Global Roots)

GCが到達可能なオブジェクトの探索を開始する起点となるオブジェクト群です。これらはプログラムによって直接アクセス可能であり、常に「ライブ」であると保証されます。グローバルルートには、グローバル変数やゴルーチンのスタック上のポインタなどが含まれます。

### BSSおよびデータセグメント (BSS and Data Segments)

プログラムのメモリレイアウトにおけるセグメントの一部です。
*   **データセグメント (.data)**: 初期化された静的変数（グローバル変数や静的ローカル変数）が格納されます。
*   **BSSセグメント (.bss)**: 初期化されていない静的変数（グローバル変数や静的ローカル変数）が格納されます。これらの変数はプログラム開始前にシステムローダーによってゼロで初期化されます。
これらのセグメントに存在するグローバル変数は、GCルートとして機能し、GCによってスキャンされる必要があります。

## 技術的詳細

このコミットは、GoのGCにおけるマークフェーズのレイテンシを削減するために、マークフェーズが「作業がなくなった」と判断した際に、より積極的に残りの作業を処理する3つのアプローチを導入しています。これにより、STWフェーズであるマーク終了フェーズでの作業量を大幅に削減し、結果としてアプリケーションの応答性を向上させます。

### 1. 白から黒へのオブジェクト割り当ての切り替え (`gcBlackenPromptly`)

通常、GCのマークフェーズ中は、新しく割り当てられるオブジェクトは「白」として扱われます。これは、もしこれらのオブジェクトがGCサイクル中に到達不可能になった場合、そのサイクルで回収できる可能性があるためです。しかし、マークフェーズの終盤に差し掛かり、ほとんどの作業が完了したと判断された場合、このコミットは`gcBlackenPromptly`というフラグを導入し、新しく割り当てられるオブジェクトを「黒」として割り当てるように切り替えます。

*   **目的**: スタックからのみ到達可能なマークされていないオブジェクトの数を減らすことです。マークフェーズの終盤で新しく割り当てられたオブジェクトが白のままだと、それらがスタックから参照されている場合、マーク終了フェーズでSTW中にスキャンする必要が生じます。これを黒として割り当てることで、STWフェーズでの追加のスキャン作業を回避し、レイテンシを削減します。
*   **トレードオフ**: 新しく割り当てられたオブジェクトを黒として扱うことは、もしそれらがすぐに到達不可能になったとしても、現在のGCサイクルでは回収されないことを意味します。しかし、マークフェーズの終盤では、このトレードオフを受け入れてでもSTWレイテンシを削減する方が全体的なパフォーマンス向上に寄与すると判断されています。

### 2. PごとのGCワークキャッシュのフラッシュと無効化

GoのGCでは、各P（Processor）がGC作業を効率的に処理するために、ローカルなGCワークキャッシュを持っています。これは、グローバルなワークバッファへのアクセスを減らし、キャッシュ効率を高めるためのものです。しかし、マークフェーズの終盤で、これらのローカルキャッシュにまだ処理されていないオブジェクトのポインタが残っていると、それらがグローバルなワークバッファにフラッシュされるまで、GCは「作業がない」と誤解する可能性があります。

*   **目的**: すべてのGC作業がグローバルに可視なワークバッファに集約されるようにすることです。マークフェーズが作業がなくなったと判断した際に、すべてのPのGCワークキャッシュを強制的にフラッシュし、無効にします。これにより、ローカルキャッシュに隠れていた作業がグローバルワークバッファに移動し、マークフェーズがSTWなしでそれらを処理する機会を得ます。
*   **効果**: STWフェーズでこれらのキャッシュを処理する必要がなくなり、STWレイテンシが削減されます。

### 3. グローバルルート（BSSおよびデータセグメント）の再スキャン

GCのマーク開始フェーズでは、グローバルルート（グローバル変数、スタックなど）がスキャンされ、そこから到達可能なオブジェクトがマークされます。しかし、マークフェーズが進行中に、グローバル変数への参照が変更される可能性があります。ライトバリアはヒープ上のオブジェクトへの書き込みを捕捉しますが、グローバル変数自体への書き込みは直接捕捉しない場合があります。

*   **目的**: マーク終了フェーズで黒く塗るオブジェクトの数を減らすことです。マークフェーズが作業がなくなったと判断した際に、BSSおよびデータセグメントに存在するグローバルルートを再スキャンします。これにより、マークフェーズ中に変更された可能性のあるグローバル変数からの新しい参照を捕捉し、それらが指すオブジェクトをSTWなしでマークすることができます。
*   **注意点**: このコミットではスタックの再スキャンは行っていません。スタックは頻繁に変化するため、再スキャンはより複雑であり、将来の改善点として残されています。

これらの3つのアプローチは、マークフェーズが「作業がない」と判断した際に、残りの作業を積極的に「掘り起こし」、STWフェーズが始まる前に並行して処理することを可能にします。これにより、STWフェーズでの作業量が最小限に抑えられ、GCレイテンシが大幅に改善されます。

### `bgMarkSignal`構造体

このコミットでは、`bgMarkSignal`という新しい構造体が導入されています。これは、GCコーディネーターとバックグラウンドマークワーカー間の同期を目的としています。

```go
type bgMarkSignal struct {
	// Workers race to cas to 1. Winner signals coordinator.
	done uint32
	// Coordinator to wake up.
	lock mutex
	g    *g
	wake bool
}
```

*   `done`: 複数のワーカーがこのフィールドを1にCAS（Compare And Swap）しようと競合します。最初に成功したワーカーがコーディネーターにシグナルを送ります。
*   `lock`: 同期のためのミューテックス。
*   `g`: 待機中のコーディネーターゴルーチン。
*   `wake`: コーディネーターがまだパークしていない場合に、ウェイクアップを保留するためのフラグ。

この構造体は、マークフェーズの2つの部分（`bgMark1`と`bgMark2`）の完了を調整するために使用されます。これにより、マークフェーズの各段階の完了を正確に検出し、次のステップ（例えば、`gcBlackenPromptly`の有効化やマーク終了への移行）に進むタイミングを制御します。

## コアとなるコードの解説

このコミットの核心は、GoのGCマークフェーズの終盤における動作を根本的に変更し、STWフェーズであるマーク終了フェーズへの依存を減らすことにあります。

### `gcBlackenPromptly` フラグの導入と利用

`gcBlackenPromptly`という新しいグローバル変数は、マークフェーズが終わりに近づき、残りの作業を積極的に処理すべきであることを示すフラグとして機能します。

*   **`src/runtime/mgc.go`**: このファイルで`gcBlackenPromptly`が宣言され、その目的が詳細にコメントされています。マークフェーズの終盤で、グローバルワークバッファが空になったと判断された後、グローバルルートの再スキャンとPごとのワークキャッシュのフラッシュが行われます。この後、もしまだ処理すべき作業（`work.full`または`work.partial`が非ゼロ）がある場合、`gcBlackenPromptly`が`true`に設定されます。これにより、GCは「第2のマークフェーズ」に入り、より積極的にオブジェクトを黒く塗るモードに移行します。
*   **`src/runtime/malloc.go`**: `mallocgc`関数は、新しいオブジェクトを割り当てる際に呼び出されます。`gcBlackenPromptly`が`true`の場合、新しく割り当てられるオブジェクトは即座に`gcmarknewobject_m`によって黒く塗られます。これにより、これらのオブジェクトがSTWフェーズでスキャンされる必要がなくなり、STWレイテンシが削減されます。
*   **`src/runtime/mgcmark.go`**: `shade`関数（ライトバリアの一部）や`gcAssistAlloc`関数（GCアシスト中に呼び出される）でも`gcBlackenPromptly`がチェックされます。`gcBlackenPromptly`が`true`の場合、PごとのGCワークキャッシュが`dispose()`され、ローカルキャッシュに隠れた作業がグローバルワークバッファにフラッシュされます。また、`gcmarknewobject_m`関数も`gcBlackenPromptly`が`true`の場合にオブジェクトを黒く塗るロジックを含んでいます。

### `bgMarkSignal`による同期の強化

以前は`work.bgMarkDone`という単一の`uint32`と`work.bgMarkWake`という構造体でバックグラウンドマークの完了を同期していましたが、このコミットでは`bgMarkSignal`構造体を導入し、`work.bgMark1`と`work.bgMark2`という2つのインスタンスを使用することで、マークフェーズの2つの段階の完了をより細かく制御しています。

*   **`work.bgMark1`**: 最初のマークフェーズの完了を通知します。この完了後、グローバルルートの再スキャンとPごとのワークキャッシュのフラッシュが行われます。
*   **`work.bgMark2`**: `gcBlackenPromptly`が`true`に設定された後の、より積極的な第2のマークフェーズの完了を通知します。

この2段階の同期メカニズムにより、GCコーディネーターはマークフェーズの進行状況をより正確に把握し、適切なタイミングで次のアクション（例えば、`gcBlackenPromptly`の有効化やマーク終了への移行）を実行できるようになります。これにより、STWフェーズに持ち越される作業が最小限に抑えられます。

### グローバルルートの再スキャンとPごとのワークキャッシュのフラッシュ

`src/runtime/mgc.go`の`gc`関数内で、`work.bgMark1.wait()`が完了した後、`systemstack`内で以下の処理が実行されます。

```go
			// rescan global data and bss.
			markroot(nil, _RootData)
			markroot(nil, _RootBss)
			forEachP(func(_p_ *p) {
				_p_.gcw.dispose()
			})
```

*   `markroot(nil, _RootData)`と`markroot(nil, _RootBss)`: データセグメントとBSSセグメントに存在するグローバルルートを再スキャンします。これにより、マークフェーズ中にこれらのグローバル変数への参照が変更された場合でも、新しい参照先が確実にマークされます。
*   `forEachP(func(_p_ *p) { _p_.gcw.dispose() })`: すべてのPに対して、そのGCワークキャッシュ（`_p_.gcw`）を`dispose()`します。`dispose()`は、キャッシュ内のすべての作業をグローバルワークバッファにフラッシュし、キャッシュを無効にする役割があります。これにより、ローカルキャッシュに隠れていた作業がグローバルに可視化され、マークフェーズがSTWなしでそれらを処理できるようになります。

これらの変更は、マークフェーズが「作業がない」と判断した後も、潜在的に残っている作業を積極的に探し出し、STWフェーズが始まる前にそれらを処理することで、GCのSTWレイテンシを大幅に削減するというコミットの目的を達成しています。ベンチマーク結果が示すように、このアプローチはGoアプリケーションのパフォーマンス向上に大きく貢献しました。

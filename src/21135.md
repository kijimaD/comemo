# [インデックス 21135] ファイルの概要

このコミットは、Goランタイムにおける`GOOS`（オペレーティングシステム）および`GOARCH`（アーキテクチャ）に特化したファイルの生成方法を、`cmd/dist`ツールによる生成から`go generate`コマンドによる生成へと移行するものです。これにより、Goのビルドプロセス、特にブートストラッププロセスを簡素化し、生成されたファイルをバージョン管理下に置くことを目指しています。

## 元コミット内容

このコミットの元の内容は、Goランタイムが使用する`GOOS`および`GOARCH`に依存する定数やコードの生成方法を変更することです。具体的には、これまで`cmd/dist`ツールがビルド時に生成していたこれらの情報を、`go generate`コマンドを使って生成し、その結果をソースコードとしてリポジトリにチェックインするようにします。これにより、Goのブートストラッププロセスを簡素化し、ビルドの再現性を高めることが目的です。

変更の要点は以下の通りです。

*   `cmd/dist`から`zgoarch_`および`zgoos_`ファイルの生成ロジックを削除。
*   `src/runtime/gengoos.go`という新しいGoプログラムを追加。このプログラムは、`go generate`によって実行され、各`GOOS`および`GOARCH`に対応する定数を含む`zgoos_*.go`および`zgoarch_*.go`ファイルを生成します。
*   ランタイムコード内の`_NaCl`、`_Windows`、`_Solaris`、`_Plan9`といったハードコードされた定数を、新しく生成される`goos_nacl`、`goos_windows`、`goos_solaris`、`goos_plan9`などの定数に置き換えます。同様に、`_386`などのアーキテクチャ定数も`goarch_386`などに置き換えられます。
*   `src/runtime/runtime2.go`に`//go:generate go run gengoos.go`というディレクティブを追加し、`go generate`が`gengoos.go`を実行するように設定します。

## 変更の背景

この変更の背景には、Goのビルドシステム、特にブートストラッププロセスの簡素化という長期的な目標があります。

1.  **ブートストラッププロセスの簡素化**: Goのビルドは、Go自身を使ってGoをビルドするというブートストラッププロセスを含みます。このプロセスは、初期のGoコンパイラ（通常はC言語で書かれたもの）から始まり、徐々にGoで書かれたコンパイラへと移行していきます。`cmd/dist`は、このブートストラッププロセスにおいて、特定のプラットフォームに依存するファイルを生成する役割を担っていました。しかし、`cmd/dist`が生成するファイルが多いと、ブートストラッププロセスが複雑になり、依存関係の管理も難しくなります。コミットメッセージにあるように、将来的には`cmd/dist`の役割を最小限に抑え、現在の実験情報やバージョン情報など、本当に必要なものだけを生成するようにしたいという意図があります。
2.  **`go generate`の活用**: `go generate`は、Go 1.4で導入されたコード生成ツールです。ソースコード内の`//go:generate`ディレクティブに基づいて外部コマンドを実行し、コードを自動生成する機能を提供します。このツールを活用することで、プラットフォーム固有の定数などの生成を、ビルドプロセスの一部としてではなく、開発者が明示的に実行するコード生成ステップとして切り出すことができます。
3.  **生成されたファイルのバージョン管理**: `go generate`によって生成されたファイルをリポジトリにチェックインすることで、ビルド環境に依存せず、常に同じ生成済みファイルを使用できるようになります。これにより、異なる環境でのビルドの再現性が向上し、開発者がGoのソースコードをビルドする際の複雑さが軽減されます。
4.  **ハードコードされた定数の排除**: 以前は、`_NaCl`のような定数がGoランタイムのコード内にハードコードされていました。これは、特定のプラットフォームでのみ有効なコードパスを条件付きでコンパイルするために使用されていましたが、新しい`goos_nacl`のような生成された定数に置き換えることで、より柔軟で拡張性の高い方法でプラットフォーム固有のロジックを扱うことができるようになります。

## 前提知識の解説

このコミットを理解するためには、以下のGoの概念とツールに関する知識が必要です。

1.  **Goのクロスコンパイルと環境変数（`GOOS`, `GOARCH`）**:
    *   Goは強力なクロスコンパイル機能を備えています。これは、あるオペレーティングシステム（OS）とアーキテクチャの組み合わせ（例: macOS上のx86-64）で、別のOSとアーキテクチャの組み合わせ（例: Linux上のARM）向けのバイナリを生成できることを意味します。
    *   `GOOS`環境変数はターゲットのオペレーティングシステムを指定します（例: `linux`, `windows`, `darwin`, `android`, `freebsd`, `nacl`など）。
    *   `GOARCH`環境変数はターゲットのCPUアーキテクチャを指定します（例: `amd64`, `386`, `arm`, `arm64`, `ppc64`, `mips`など）。
    *   これらの環境変数を設定することで、Goコンパイラは指定されたターゲットプラットフォームに最適化されたコードを生成します。

2.  **`cmd/dist`ツール**:
    *   `cmd/dist`は、Goのソースコードリポジトリ内に存在する内部ツールです。Goのコンパイラ、ツール、標準ライブラリなどをビルドし、テストするためのブートストラッププロセスを管理します。
    *   これはGoの自己ホスト型コンパイラ（Go自身でGoをコンパイルする）の性質上、Goの初期ビルドや更新時に重要な役割を果たします。
    *   歴史的に、`cmd/dist`はGoのビルドに必要な多くのプラットフォーム固有のファイルを生成していました。

3.  **`go generate`コマンド**:
    *   `go generate`は、Go 1.4で導入されたコード生成ツールです。
    *   Goのソースファイル内に記述された特別なコメントディレクティブ`//go:generate <command>`を読み取り、指定されたコマンドを実行します。
    *   このコマンドは、Goのビルドプロセスの一部ではなく、開発者が明示的に実行する必要があります。
    *   主な用途は、定型的なコード（例: `String()`メソッドの実装、モックオブジェクト、プロトコルバッファのコードなど）の自動生成、アセットの埋め込み、あるいは本コミットのようにプラットフォーム固有の定数の生成などです。
    *   `go generate`によって生成されたファイルは、通常、バージョン管理システム（Gitなど）にコミットされます。これにより、プロジェクトをクローンした他の開発者が`go generate`を実行する必要なく、すぐにビルドを開始できます。

4.  **ビルドタグ（Build Tags）**:
    *   Goのソースファイルには、`// +build <tag>`のようなビルドタグを記述できます。これは、特定の条件が満たされた場合にのみそのファイルをコンパイルに含めるためのディレクティブです。
    *   例えば、`// +build linux`と書かれたファイルはLinux環境でのみコンパイルされ、`// +build darwin,amd64`と書かれたファイルはmacOS上のamd64アーキテクチャでのみコンパイルされます。
    *   このコミットで生成される`zgoos_*.go`ファイルには、対応するOSのビルドタグが含まれています（例: `zgoos_android.go`には`// +build android`）。これにより、Goコンパイラは現在の`GOOS`設定に基づいて適切なファイルを選択してコンパイルします。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムがプラットフォーム固有の情報をどのように取得し、利用するかというメカニズムの変更にあります。

以前のGoランタイムでは、`_NaCl`、`_Windows`、`_Solaris`、`_Plan9`といった定数が、特定のOS環境を示すために直接コード内に定義されていました。これらの定数は、例えば`_PhysPageSize`のような他の定数の計算や、条件付きのコードパス（例: `if _Windows ...`）で使用されていました。これらの定数の値は、`cmd/dist`ツールがビルド時に生成する`zgoos_*.go`や`zgoarch_*.go`ファイルによって設定されていました。

このコミットでは、このアプローチをより汎用的で`go generate`フレンドリーなものに刷新しています。

1.  **`gengoos.go`の導入**:
    *   新しく追加された`src/runtime/gengoos.go`は、Goプログラムとして実装されています。このプログラムは、Goのビルドシステムが認識するすべての`GOOS`と`GOARCH`の組み合わせを列挙し、それぞれに対応するGoソースファイルを生成します。
    *   `gengoos.go`は、`../go/build/syslist.go`から`goosList`と`goarchList`を読み込み、サポートされているOSとアーキテクチャのリストを取得します。
    *   各`GOOS`（例: `android`）に対して、`zgoos_android.go`のようなファイルを生成します。このファイルには、`const theGoos = "android"`という定数と、すべての`GOOS`に対する`goos_<os_name> = 0`または`1`という定数が含まれます。例えば、`zgoos_android.go`には`goos_android = 1`と、他のすべての`goos_<other_os> = 0`が定義されます。
    *   同様に、各`GOARCH`（例: `386`）に対して、`zgoarch_386.go`のようなファイルを生成します。このファイルには、`const theGoarch = "386"`という定数と、すべての`GOARCH`に対する`goarch_<arch_name> = 0`または`1`という定数が含まれます。
    *   生成される`zgoos_*.go`ファイルには、対応するOSのビルドタグ（例: `// +build android`）も含まれるため、Goコンパイラは現在のビルドターゲットに基づいて適切な`zgoos_*.go`ファイルのみをコンパイルに含めます。

2.  **`go generate`による自動生成**:
    *   `src/runtime/runtime2.go`に`//go:generate go run gengoos.go`というディレクティブが追加されました。これにより、開発者が`go generate`コマンドを実行すると、`gengoos.go`が自動的に実行され、最新の`GOOS`および`GOARCH`情報に基づいて`zgoos_*.go`および`zgoarch_*.go`ファイルが生成されます。
    *   これらの生成されたファイルは、Goのソースツリーにコミットされるため、Goのソースコードをダウンロードした開発者は、特別なビルドステップなしに、すぐにGoをビルドできます。

3.  **定数の置き換え**:
    *   `src/runtime/arch1_386.go`、`src/runtime/arch1_amd64.go`、`src/runtime/arch1_arm.go`、`src/runtime/malloc2.go`、`src/runtime/stack1.go`、`src/runtime/stack2.go`などのファイルでは、これまで使用されていた`_NaCl`、`_Windows`、`_Solaris`、`_Plan9`といった定数が、新しく生成される`goos_nacl`、`goos_windows`、`goos_solaris`、`goos_plan9`などの定数に置き換えられています。
    *   これらの新しい定数は、現在のビルドターゲットのOSまたはアーキテクチャに合致する場合に`1`、そうでない場合に`0`となるため、以前のブール値の定数と同じように、あるいは乗算と組み合わせることで、条件付きのロジックを簡潔に表現できます（例: `goos_nacl*65536 + (1-goos_nacl)*4096`）。

この変更により、Goのビルドシステムはよりクリーンになり、プラットフォーム固有の定数の管理が`go generate`という標準的なGoツールによって行われるようになりました。これは、Goのブートストラッププロセスを簡素化し、Goのソースコードの保守性を向上させるための重要な一歩です。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は以下の通りです。

1.  **`src/cmd/dist/build.c`**:
    *   `mkzgoarch`と`mkzgoos`の生成関数への参照が削除されました。
    *   `clean`関数において、`src/runtime/z*`ファイルの削除ロジックが変更され、`zgoos`と`zgoarch`ファイルは`go generate`で管理されるようになったため、無条件に削除しないようになりました。

2.  **`src/cmd/dist/buildruntime.c`**:
    *   `mkzgoarch`関数と`mkzgoos`関数が完全に削除されました。これらの関数は、以前は`zgoarch_*.go`と`zgoos_*.go`ファイルを生成する役割を担っていました。

3.  **`src/runtime/gengoos.go` (新規ファイル)**:
    *   このファイルは新しく追加されたGoプログラムで、`go generate`によって実行されます。
    *   `go/build/syslist.go`からサポートされている`GOOS`と`GOARCH`のリストを読み込みます。
    *   各`GOOS`と`GOARCH`に対応する`zgoos_*.go`と`zgoarch_*.go`ファイルを生成します。これらのファイルには、現在のOS/アーキテクチャを示す`theGoos` / `theGoarch`定数と、すべてのOS/アーキテクチャに対する`goos_<os_name>` / `goarch_<arch_name>`定数（値は0または1）が含まれます。

4.  **`src/runtime/runtime2.go`**:
    *   `_NaCl`, `_Windows`, `_Solaris`, `_Plan9`といったハードコードされた定数の定義が削除されました。
    *   `//go:generate go run gengoos.go`というディレクティブが追加されました。これは、`go generate`コマンドがこのディレクトリで実行されたときに`gengoos.go`を実行するように指示します。

5.  **`src/runtime/arch1_386.go`, `src/runtime/arch1_amd64.go`, `src/runtime/arch1_arm.go`, `src/runtime/malloc2.go`, `src/runtime/stack1.go`, `src/runtime/stack2.go`**:
    *   これらのファイル内で、以前使用されていた`_NaCl`, `_Windows`, `_Solaris`, `_Plan9`などの定数が、新しく生成される`goos_nacl`, `goos_windows`, `goos_solaris`, `goos_plan9`などの定数に置き換えられました。

6.  **`src/runtime/zgoarch_*.go` および `src/runtime/zgoos_*.go` (新規ファイル群)**:
    *   これらのファイルは`gengoos.go`によって生成され、このコミットで新しく追加されました。
    *   各ファイルは特定の`GOOS`または`GOARCH`に対応し、そのOS/アーキテクチャが現在のビルドターゲットである場合に`1`となる定数（例: `goos_linux = 1`）と、他のすべてのOS/アーキテクチャに対して`0`となる定数を定義します。
    *   `zgoos_*.go`ファイルには、対応するOSのビルドタグ（例: `// +build linux`）も含まれます。

## コアとなるコードの解説

このコミットの核心は、Goランタイムがプラットフォーム固有の情報を扱う方法のパラダイムシフトにあります。

以前は、Goのビルドシステムの一部である`cmd/dist`が、ビルド時に特定のOSやアーキテクチャに対応する定数を含むGoファイルを生成していました。例えば、`zgoos_windows.go`のようなファイルが生成され、その中には`const theGoos = "windows"`や、`_Windows = 1`のような定数が含まれていました。これらの定数は、ランタイムコード内で条件付きコンパイルやプラットフォーム固有のロジックの分岐に使用されていました。

このアプローチの問題点は、`cmd/dist`がGoのブートストラッププロセスにおいて多くの責任を負い、ビルドシステムが複雑になることでした。また、生成されたファイルがバージョン管理下にない場合、異なるビルド環境での再現性が保証されにくいという課題もありました。

このコミットでは、この問題を解決するために`go generate`を活用します。

1.  **`gengoos.go`の役割**:
    *   `gengoos.go`は、Goの標準ライブラリの一部として提供される新しいGoプログラムです。このプログラムは、GoがサポートするすべてのOSとアーキテクチャのリストを内部的に持っています。
    *   `go generate`が`gengoos.go`を実行すると、`gengoos.go`はこれらのリストを反復処理し、各OSとアーキテクチャに対応するGoソースファイル（`zgoos_*.go`と`zgoarch_*.go`）を生成します。
    *   例えば、`zgoos_linux.go`が生成される場合、そのファイルには`const theGoos = "linux"`という文字列定数と、`const goos_linux = 1`、そして他のすべてのOSに対する`const goos_darwin = 0`, `const goos_windows = 0`といった整数定数が含まれます。
    *   重要なのは、`zgoos_*.go`ファイルには、対応するOSのビルドタグ（例: `// +build linux`）が含まれることです。これにより、Goコンパイラは、現在のビルドターゲットがLinuxである場合にのみ`zgoos_linux.go`をコンパイルに含め、他の`zgoos_*.go`ファイルは無視します。

2.  **ランタイムコードの変更**:
    *   ランタイムコード（例: `arch1_386.go`, `malloc2.go`など）では、以前使用されていた`_NaCl`のようなブール値の定数が、新しく生成される`goos_nacl`のような整数定数に置き換えられました。
    *   これらの整数定数は、現在のビルドターゲットのOS/アーキテクチャに合致する場合に`1`、そうでない場合に`0`となるため、例えば`_PhysPageSize = _NaCl*65536 + (1-_NaCl)*4096`のような式は、`_PhysPageSize = goos_nacl*65536 + (1-goos_nacl)*4096`と書き換えられます。この式は、`goos_nacl`が`1`であれば`65536`を、`0`であれば`4096`を選択するという、以前と同じロジックをより明示的に表現しています。

3.  **ブートストラッププロセスの簡素化**:
    *   この変更により、`cmd/dist`は`zgoos_*.go`や`zgoarch_*.go`ファイルを生成する責任から解放されます。これにより、`cmd/dist`のコードベースが簡素化され、Goのブートストラッププロセスがより軽量になります。
    *   生成されたファイルがリポジトリにチェックインされるため、Goのソースコードをクローンした開発者は、`go generate`を一度実行するだけで、プラットフォーム固有の定数を最新の状態に保つことができます。これにより、Goのビルド環境のセットアップが簡素化され、ビルドの信頼性が向上します。

このコミットは、Goのビルドシステムをよりモジュール化し、標準的なGoツールである`go generate`を活用することで、Goのランタイムがプラットフォーム固有の情報を扱う方法を改善し、Go全体の開発体験を向上させるための重要なステップです。

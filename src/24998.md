# [インデックス 24998] ファイルの概要

## 元コミット内容

符号拡張とロードの組み合わせに関するGoコンパイラのSSAバックエンドのバグを修正します。ロードと符号拡張を行うオペコードが誤ったブロックで生成されていたため、複数のメモリ変数が同時にライブ状態になる問題が発生していました。このルールを修正し、テストを追加します。

## 変更の背景

GoコンパイラのSSAバックエンドでは、プログラムのメモリ状態は特別な「メモリ変数」として扱われます。SSAの原則に従い、各メモリ変数は一度だけ定義され、その後の操作は新しいメモリ変数を生成します。これにより、メモリ操作の順序と依存関係が明確になります。

このコミット以前は、`MOVBQSX` (バイトをクアッドワードに符号拡張) や `MOVBQZX` (バイトをクアッドワードにゼロ拡張) といった命令が、`MOVBload` (バイトロード) と組み合わされる際に、コンパイラの書き換えルールが不適切に適用されることがありました。具体的には、ロード操作とそれに続く拡張操作が、異なる基本ブロックにまたがって最適化され、単一の複合命令（例: `MOVBQSXload`）に変換される際に問題が生じていました。

この問題の核心は、複合命令が生成される際に、元のロード命令が属していたブロックとは異なるブロックに配置されてしまう可能性があったことです。SSA形式では、メモリ変数は特定のブロック内で定義され、そのブロックの終端で「ライブ」でなくなるか、後続のブロックに引き継がれます。もしロードと拡張の複合命令が元のロード命令とは異なるブロックに移動してしまうと、その複合命令が参照するメモリ変数が、そのブロックの開始時点では「ライブ」ではない、あるいは、そのブロックの開始時点ですでに別のメモリ変数が「ライブ」であるという状況が発生し得ました。

結果として、SSAのメモリモデルの重要な制約である「任意の時点でライブなメモリ変数は常に一つであるべき」という原則が破られ、コンパイラの内部状態が不正になる可能性がありました。これは、レジスタアロケーションや他の最適化パスで予期せぬ動作やクラッシュを引き起こす原因となります。

## 前提知識の解説

### SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化で広く用いられる中間表現です。この形式では、各変数が一度だけ代入（定義）されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、最適化の機会が増えます。例えば、`x = a + b; x = c + d;` というコードは、SSAでは `x1 = a + b; x2 = c + d;` のように変換され、各 `x` の使用がどの定義に対応するかが明確になります。

### GoコンパイラのSSAバックエンド

Goコンパイラは、Go 1.7からSSAバックエンドを導入しました。これにより、より高度な最適化が可能になり、生成されるコードの品質が向上しました。SSAバックエンドでは、Goのソースコードが抽象構文木 (AST) から中間表現 (IR) に変換され、最終的にSSA形式に変換されます。その後、SSA形式に対して様々な最適化が適用され、最終的に機械語に変換されます。

### メモリ変数 (Memory Variable)

GoコンパイラのSSA形式では、プログラムのメモリ状態全体を抽象的に表現するために「メモリ変数」という特殊な値が導入されています。これは、実際のメモリ位置を指すのではなく、プログラムのある時点でのメモリの「状態」を表します。メモリを読み書きする操作（ロード、ストア、関数呼び出しなど）は、古いメモリ変数を入力として受け取り、新しいメモリ変数を生成します。これにより、メモリ操作間の依存関係がSSAのデータフローとして表現され、メモリのエイリアシング解析が容易になります。SSA形式では、常に単一のメモリ変数が「ライブ」であるべきという厳格な制約があります。これは、プログラムの任意の時点において、メモリの「現在の状態」は一意であるという考え方に基づいています。

### ロードと符号拡張/ゼロ拡張

CPUアーキテクチャによっては、メモリから小さなサイズの値をロードし、それをより大きなレジスタに格納する際に、自動的に符号拡張 (Sign Extension) またはゼロ拡張 (Zero Extension) を行う命令が提供されます。
*   **符号拡張**: 符号付きの小さな整数値をより大きな型に変換する際に、元の値の符号を保持するために最上位ビットを新しい上位ビットにコピーします。例えば、1バイトの-1 (0xFF) を4バイトに符号拡張すると、0xFFFFFFFF になります。
*   **ゼロ拡張**: 符号なしの小さな整数値をより大きな型に変換する際に、新しい上位ビットをすべて0で埋めます。例えば、1バイトの255 (0xFF) を4バイトにゼロ拡張すると、0x000000FF になります。
Goコンパイラでは、これらの操作を効率的に行うために、`MOVBQSX` (Move Byte to Quadword Sign Extend) や `MOVBQZX` (Move Byte to Quadword Zero Extend) といったSSAオペレーションが使用されます。

### 書き換えルール (Rewrite Rules)

GoコンパイラのSSAバックエンドでは、`src/cmd/compile/internal/ssa/gen/*.rules` ファイル群に定義された書き換えルールを使用して、SSA命令をより効率的な命令シーケンスや、ターゲットアーキテクチャ固有の命令に変換します。これらのルールは、パターンマッチングと置換の形式で記述されており、特定のSSA命令の組み合わせを、より最適化された単一の命令や命令シーケンスに変換します。例えば、`MOVBQSX (MOVBload ...)` のようなパターンを `MOVBQSXload ...` のような単一の命令に変換することで、命令数を減らし、パフォーマンスを向上させることができます。

## 技術的詳細

このコミットの技術的な核心は、SSA形式におけるメモリ変数のライブネス制約を維持しながら、ロードと拡張の最適化を正しく適用することにあります。

問題は、`MOVBQSX (MOVBload [off] {sym} ptr mem)` のようなSSA命令パターンを `MOVBQSXload [off] {sym} ptr mem` のような単一の複合命令に書き換える際に発生していました。この書き換えは、`src/cmd/compile/internal/ssa/gen/AMD64.rules` および `src/cmd/compile/internal/ssa/rewriteAMD64.go` で定義されています。

元のルールでは、`MOVBQSX` オペレーションが `MOVBload` オペレーションの引数として与えられた場合、無条件に複合命令に書き換えられていました。しかし、`MOVBload` オペレーション自体がメモリ変数 `mem` を引数として取り、新しいメモリ変数を生成します。この `MOVBload` が属する基本ブロックと、`MOVBQSX` が属する基本ブロックが異なる場合、問題が発生します。

具体的には、`MOVBload` がブロック `B1` にあり、`MOVBQSX` がブロック `B2` にあるとします。`MOVBload` は `B1` のメモリ変数を消費し、新しいメモリ変数を生成します。この新しいメモリ変数は `B1` の後続ブロックに引き継がれます。もし `MOVBQSX` が `B2` にあり、`MOVBload` の結果を使用している場合、`MOVBQSX` は `B2` のメモリ変数を消費し、新しいメモリ変数を生成します。

複合命令 `MOVBQSXload` は、元の `MOVBload` と `MOVBQSX` の両方の役割を果たすため、メモリ変数を一つだけ消費し、一つだけ生成する必要があります。しかし、もし `MOVBQSXload` が `B2` に配置され、そのメモリ引数が `B1` で生成されたメモリ変数である場合、`B2` の開始時点では、`B2` 自身のメモリ変数と、`B1` から引き継がれたメモリ変数の両方が「ライブ」であるかのように見えてしまいます。これはSSAのメモリモデルの制約に違反します。

この問題を解決するため、書き換えルールに `&& b == v.Args[0].Block` という条件が追加されました。
*   `v` は `MOVBQSX` (または `MOVBQZX`) オペレーションを表します。
*   `v.Args[0]` は `MOVBload` オペレーションを表します。
*   `b` は `v` (つまり `MOVBQSX`) が属する基本ブロックです。
*   `v.Args[0].Block` は `v.Args[0]` (つまり `MOVBload`) が属する基本ブロックです。

この条件 `b == v.Args[0].Block` は、「符号拡張オペレーション (`v`) とロードオペレーション (`v.Args[0]`) が同じ基本ブロックに属している場合にのみ、それらを単一の複合命令 (`MOVBQSXload` または `MOVBQZXload`) に書き換える」ことを強制します。これにより、複合命令が生成される際にメモリ変数のライブネス制約が破られることを防ぎます。

さらに、`src/cmd/compile/internal/ssa/regalloc.go` には、レジスタアロケーションの前にメモリ変数のライブネスを検証するアサーションが追加されました。これは、デバッグとコンパイラの健全性チェックを目的としています。`f.Fatalf("more than one mem live on edge %v->%v: %v", b, c, live[b.ID][i])` という行は、もしSSAのメモリモデルが破られ、複数のメモリ変数が同時にライブ状態になった場合に、コンパイラが致命的なエラーで終了するようにします。これにより、将来的に同様のバグが導入された際に早期に発見できるようになります。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules`

このファイルは、GoコンパイラのSSAバックエンドがAMD64アーキテクチャ向けにSSA命令を書き換えるためのルールを定義しています。
変更された箇所は、`MOVBQSX` と `MOVBQZX` の書き換えルールです。

```
// sign extended loads
-(MOVBQSX (MOVBload [off] {sym} ptr mem)) -> (MOVBQSXload [off] {sym} ptr mem)
-(MOVBQZX (MOVBload [off] {sym} ptr mem)) -> (MOVBQZXload [off] {sym} ptr mem)
```
上記の行は、元のルールで、`MOVBQSX` (または `MOVBQZX`) と `MOVBload` の組み合わせを、単一の複合命令 `MOVBQSXload` (または `MOVBQZXload`) に書き換えることを示しています。

追加されたコメントと条件が重要です。

```
// Note: The combined instruction must end up in the same block
// as the original load.  If not, we end up making a value with
// memory type live in two different blocks, which can lead to
// multiple memory values alive simultaneously.
// TODO: somehow have this rewrite rule put the new MOVBQSXload in
// v.Args[0].Block instead of in v.Block?
(MOVBQSX (MOVBload [off] {sym} ptr mem)) && b == v.Args[0].Block -> (MOVBQSXload [off] {sym} ptr mem)
(MOVBQZX (MOVBload [off] {sym} ptr mem)) && b == v.Args[0].Block -> (MOVBQZXload [off] {sym} ptr mem)
```

`&& b == v.Args[0].Block` という条件が追加されました。
*   `b` は現在処理しているSSA値 `v` (ここでは `MOVBQSX` または `MOVBQZX`) が属する基本ブロックです。
*   `v.Args[0]` は `MOVBload` オペレーションです。
*   `v.Args[0].Block` は `MOVBload` オペレーションが属する基本ブロックです。

この条件は、`MOVBQSX` (または `MOVBQZX`) と `MOVBload` が**同じ基本ブロック内にある場合にのみ**、これらを単一の複合命令 `MOVBQSXload` (または `MOVBQZXload`) に書き換えることを強制します。これにより、複合命令が生成される際に、メモリ変数のライブネスが複数のブロックにまたがって不整合になることを防ぎます。

## 変更の背景

GoコンパイラのSSAバックエンドでは、プログラムのメモリ状態は特別な「メモリ変数」として扱われます。SSAの原則に従い、各メモリ変数は一度だけ定義され、その後の操作は新しいメモリ変数を生成します。これにより、メモリ操作の順序と依存関係が明確になります。

このコミット以前は、`MOVBQSX` (バイトをクアッドワードに符号拡張) や `MOVBQZX` (バイトをクアッドワードにゼロ拡張) といった命令が、`MOVBload` (バイトロード) と組み合わされる際に、コンパイラの書き換えルールが不適切に適用されることがありました。具体的には、ロード操作とそれに続く拡張操作が、異なる基本ブロックにまたがって最適化され、単一の複合命令（例: `MOVBQSXload`）に変換される際に問題が生じていました。

この問題の核心は、複合命令が生成される際に、元のロード命令が属していたブロックとは異なるブロックに配置されてしまう可能性があったことです。SSA形式では、メモリ変数は特定のブロック内で定義され、そのブロックの終端で「ライブ」でなくなるか、後続のブロックに引き継がれます。もしロードと拡張の複合命令が元のロード命令とは異なるブロックに移動してしまうと、その複合命令が参照するメモリ変数が、そのブロックの開始時点では「ライブ」ではない、あるいは、そのブロックの開始時点ですでに別のメモリ変数が「ライブ」であるという状況が発生し得ました。

結果として、SSAのメモリモデルの重要な制約である「任意の時点でライブなメモリ変数は常に一つであるべき」という原則が破られ、コンパイラの内部状態が不正になる可能性がありました。これは、レジスタアロケーションや他の最適化パスで予期せぬ動作やクラッシュを引き起こす原因となります。

## 前提知識の解説

### SSA (Static Single Assignment) 形式

SSA形式は、コンパイラ最適化で広く用いられる中間表現です。この形式では、各変数が一度だけ代入（定義）されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、最適化の機会が増えます。例えば、`x = a + b; x = c + d;` というコードは、SSAでは `x1 = a + b; x2 = c + d;` のように変換され、各 `x` の使用がどの定義に対応するかが明確になります。

### GoコンパイラのSSAバックエンド

Goコンパイラは、Go 1.7からSSAバックエンドを導入しました。これにより、より高度な最適化が可能になり、生成されるコードの品質が向上しました。SSAバックエンドでは、Goのソースコードが抽象構文木 (AST) から中間表現 (IR) に変換され、最終的にSSA形式に変換されます。その後、SSA形式に対して様々な最適化が適用され、最終的に機械語に変換されます。

### メモリ変数 (Memory Variable)

GoコンパイラのSSA形式では、プログラムのメモリ状態全体を抽象的に表現するために「メモリ変数」という特殊な値が導入されています。これは、実際のメモリ位置を指すのではなく、プログラムのある時点でのメモリの「状態」を表します。メモリを読み書きする操作（ロード、ストア、関数呼び出しなど）は、古いメモリ変数を入力として受け取り、新しいメモリ変数を生成します。これにより、メモリ操作間の依存関係がSSAのデータフローとして表現され、メモリのエイリアシング解析が容易になります。SSA形式では、常に単一のメモリ変数が「ライブ」であるべきという厳格な制約があります。これは、プログラムの任意の時点において、メモリの「現在の状態」は一意であるという考え方に基づいています。

### ロードと符号拡張/ゼロ拡張

CPUアーキテクチャによっては、メモリから小さなサイズの値をロードし、それをより大きなレジスタに格納する際に、自動的に符号拡張 (Sign Extension) またはゼロ拡張 (Zero Extension) を行う命令が提供されます。
*   **符号拡張**: 符号付きの小さな整数値をより大きな型に変換する際に、元の値の符号を保持するために最上位ビットを新しい上位ビットにコピーします。例えば、1バイトの-1 (0xFF) を4バイトに符号拡張すると、0xFFFFFFFF になります。
*   **ゼロ拡張**: 符号なしの小さな整数値をより大きな型に変換する際に、新しい上位ビットをすべて0で埋めます。例えば、1バイトの255 (0xFF) を4バイトにゼロ拡張すると、0x000000FF になります。
Goコンパイラでは、これらの操作を効率的に行うために、`MOVBQSX` (Move Byte to Quadword Sign Extend) や `MOVBQZX` (Move Byte to Quadword Zero Extend) といったSSAオペレーションが使用されます。

### 書き換えルール (Rewrite Rules)

GoコンパイラのSSAバックエンドでは、`src/cmd/compile/internal/ssa/gen/*.rules` ファイル群に定義された書き換えルールを使用して、SSA命令をより効率的な命令シーケンスや、ターゲットアーキテクチャ固有の命令に変換します。これらのルールは、パターンマッチングと置換の形式で記述されており、特定のSSA命令の組み合わせを、より最適化された単一の命令や命令シーケンスに変換します。例えば、`MOVBQSX (MOVBload ...)` のようなパターンを `MOVBQSXload ...` のような単一の命令に変換することで、命令数を減らし、パフォーマンスを向上させることができます。

## 技術的詳細

このコミットの技術的な核心は、SSA形式におけるメモリ変数のライブネス制約を維持しながら、ロードと拡張の最適化を正しく適用することにあります。

問題は、`MOVBQSX (MOVBload [off] {sym} ptr mem)` のようなSSA命令パターンを `MOVBQSXload [off] {sym} ptr mem` のような単一の複合命令に書き換える際に発生していました。この書き換えは、`src/cmd/compile/internal/ssa/gen/AMD64.rules` および `src/cmd/compile/internal/ssa/rewriteAMD64.go` で定義されています。

元のルールでは、`MOVBQSX` オペレーションが `MOVBload` オペレーションの引数として与えられた場合、無条件に複合命令に書き換えられていました。しかし、`MOVBload` オペレーション自体がメモリ変数 `mem` を引数として取り、新しいメモリ変数を生成します。この `MOVBload` が属する基本ブロックと、`MOVBQSX` が属する基本ブロックが異なる場合、問題が発生します。

具体的には、`MOVBload` がブロック `B1` にあり、`MOVBQSX` がブロック `B2` にあるとします。`MOVBload` は `B1` のメモリ変数を消費し、新しいメモリ変数を生成します。この新しいメモリ変数は `B1` の後続ブロックに引き継がれます。もし `MOVBQSX` が `B2` にあり、`MOVBload` の結果を使用している場合、`MOVBQSX` は `B2` のメモリ変数を消費し、新しいメモリ変数を生成します。

複合命令 `MOVBQSXload` は、元の `MOVBload` と `MOVBQSX` の両方の役割を果たすため、メモリ変数を一つだけ消費し、一つだけ生成する必要があります。しかし、もし `MOVBQSXload` が `B2` に配置され、そのメモリ引数が `B1` で生成されたメモリ変数である場合、`B2` の開始時点では、`B2` 自身のメモリ変数と、`B1` から引き継がれたメモリ変数の両方が「ライブ」であるかのように見えてしまいます。これはSSAのメモリモデルの制約に違反します。

この問題を解決するため、書き換えルールに `&& b == v.Args[0].Block` という条件が追加されました。
*   `v` は `MOVBQSX` (または `MOVBQZX`) オペレーションを表します。
*   `v.Args[0]` は `MOVBload` オペレーションを表します。
*   `b` は `v` (つまり `MOVBQSX`) が属する基本ブロックです。
*   `v.Args[0].Block` は `v.Args[0]` (つまり `MOVBload`) が属する基本ブロックです。

この条件 `b == v.Args[0].Block` は、「符号拡張オペレーション (`v`) とロードオペレーション (`v.Args[0]`) が同じ基本ブロックに属している場合にのみ、それらを単一の複合命令 (`MOVBQSXload` または `MOVBQZXload`) に書き換える」ことを強制します。これにより、複合命令が生成される際にメモリ変数のライブネス制約が破られることを防ぎます。

さらに、`src/cmd/compile/internal/ssa/regalloc.go` には、レジスタアロケーションの前にメモリ変数のライブネスを検証するアサーションが追加されました。これは、デバッグとコンパイラの健全性チェックを目的としています。`f.Fatalf("more than one mem live on edge %v->%v: %v", b, c, live[b.ID][i])` という行は、もしSSAのメモリモデルが破られ、複数のメモリ変数が同時にライブ状態になった場合に、コンパイラが致命的なエラーで終了するようにします。これにより、将来的に同様のバグが導入された際に早期に発見できるようになります。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/testdata/loadstore_ssa.go`

このファイルには、コンパイラのSSA最適化が正しく機能していることを検証するためのテストケースが含まれています。追加された `testExtStore_ssa` 関数は、バイトポインタからのロード (`*p`) と、それに続くストア (`*p = 7`)、そしてロードした値の符号拡張 (`int(x)`) を含むシンプルなコードです。このシーケンスは、まさにこのコミットが修正しようとしている「ロードと拡張の組み合わせ」のシナリオを再現しています。`testExtStore` 関数は、`testExtStore_ssa` を呼び出し、結果が期待通りであるかを確認します。これにより、コンパイラがこの特定のパターンを正しく処理し、メモリ変数のライブネス違反を引き起こさないことを保証します。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules`

このファイルは、GoコンパイラのSSAバックエンドがAMD64アーキテクチャ向けにSSA命令を書き換えるためのルールを定義しています。
変更された箇所は、`MOVBQSX` と `MOVBQZX` の書き換えルールです。

```
// sign extended loads
-(MOVBQSX (MOVBload [off] {sym} ptr mem)) -> (MOVBQSXload [off] {sym} ptr mem)
-(MOVBQZX (MOVBload [off] {sym} ptr mem)) -> (MOVBQZXload [off] {sym} ptr mem)
```
上記の行は、元のルールで、`MOVBQSX` (または `MOVBQZX`) と `MOVBload` の組み合わせを、単一の複合命令 `MOVBQSXload` (または `MOVBQZXload`) に書き換えることを示しています。

追加されたコメントと条件が重要です。

```
// Note: The combined instruction must end up in the same block
// as the original load.  If not, we end up making a value with
// memory type live in two different blocks, which can lead to
// multiple memory values alive simultaneously.
// TODO: somehow have this rewrite rule put the new MOVBQSXload in
// v.Args[0].Block instead of in v.Block?
(MOVBQSX (MOVBload [off] {sym} ptr mem)) && b == v.Args[0].Block -> (MOVBQSXload [off] {sym} ptr mem)
(MOVBQZX (MOVBload [off] {sym} ptr mem)) && b == v.Args[0].Block -> (MOVBQZXload [off] {sym} ptr mem)
```

`&& b == v.Args[0].Block` という条件が追加されました。
*   `b` は現在処理しているSSA値 `v` (ここでは `MOVBQSX` または `MOVBQZX`) が属する基本ブロックです。
*   `v.Args[0]` は `MOVBload` オペレーションです。
*   `v.Args[0].Block` は `MOVBload` オペレーションが属する基本ブロックです。

この条件は、`MOVBQSX` (または `MOVBQZX`) と `MOVBload` が**同じ基本ブロック内にある場合にのみ**、これらを単一の複合命令 `MOVBQSXload` (または `MOVBQZXload`) に書き換えることを強制します。これにより、複合命令が生成される際に、メモリ変数のライブネスが複数のブロックにまたがって不整合になることを防ぎます。

`TODO` コメントは、理想的には書き換えルール自体が新しい命令を適切なブロックに配置できるべきだが、現状ではその機能がないため、この条件で回避していることを示唆しています。

### `src/cmd/compile/internal/ssa/regalloc.go`

このファイルは、SSA形式の値をレジスタに割り当てるレジスタアロケータに関連するコードを含んでいます。
追加されたコードブロックは、レジスタアロケーションの前にSSA形式のメモリモデルの整合性を検証するためのアサーションです。

```go
	// Make sure that there is only one live memory variable in each set.
	// Ideally we should check this at every instructiom, but at every
	// edge seems good enough for now.
	isMem := make([]bool, f.NumValues())
	for _, b := range f.Blocks {
		for _, v := range b.Values {
			isMem[v.ID] = v.Type.IsMemory()
		}
	}
	for _, b := range f.Blocks {
		for i, c := range b.Succs {
			nmem := 0
			for _, id := range live[b.ID][i] {
				if isMem[id] {
					nmem++
				}
			}
			if nmem > 1 {
				f.Fatalf("more than one mem live on edge %v->%v: %v", b, c, live[b.ID][i])
			}
			// TODO: figure out why we get nmem==0 occasionally.
			//if nmem == 0 {
			//	f.Fatalf("no mem live on edge %v->%v: %v", b, c, live[b.ID][i])
			//}
		}
	}
```

このコードは、各基本ブロックのサクセッサ（後続ブロック）へのエッジにおいて、同時にライブなメモリ変数が1つだけであることを確認します。
1.  まず、`isMem` スライスを作成し、各SSA値がメモリ変数であるかどうかを記録します。
2.  次に、すべての基本ブロック `b` とそのサクセッサ `c` の間のエッジを反復処理します。
3.  各エッジでライブなSSA値のセット (`live[b.ID][i]`) を調べ、その中にメモリ変数がいくつ含まれているかを `nmem` でカウントします。
4.  もし `nmem` が1より大きい場合（つまり、複数のメモリ変数が同時にライブである場合）、`f.Fatalf` を呼び出してコンパイラをクラッシュさせます。これは、SSAのメモリモデルの重要な制約が破られていることを意味し、コンパイラのバグを示唆します。

このアサーションは、今回のバグ修正が正しく機能していることを検証するだけでなく、将来的に同様のメモリモデル違反が発生した場合に早期に問題を検出するためのセーフティネットとして機能します。`TODO` コメントは、`nmem == 0` のケースも理想的にはチェックすべきだが、現状では特定の状況で発生するため保留していることを示しています。

### `src/cmd/compile/internal/ssa/rewriteAMD64.go`

このファイルは、`AMD64.rules` ファイルで定義されたルールに基づいて、実際にSSA命令の書き換えを実行するGoコードを生成するために使用されます。`gen/AMD64.rules` の変更が、このファイルの対応する `rewriteValueAMD64` 関数内のロジックに反映されています。

`OpAMD64MOVBQSX` と `OpAMD64MOVBQZX` のケースにおいて、書き換えの条件として `if !(b == v.Args[0].Block)` が追加されています。

```go

		// match: (MOVBQSX (MOVBload [off] {sym} ptr mem))

		// result: (MOVBQSXload [off] {sym} ptr mem)
		{
			if v.Args[0].Op != OpAMD64MOVBload {
				goto end4fcdab76af223d4a6b942b532ebf860b
			}
			off := v.Args[0].AuxInt
			sym := v.Args[0].Aux
			ptr := v.Args[0].Args[0]
			mem := v.Args[0].Args[1]
			if !(b == v.Args[0].Block) { // <-- ここが追加された条件
				goto end4fcdab76af223d4a6b942b532ebf860b
			}
			v.Op = OpAMD64MOVBQSXload
			// ... (後続のコード)
		}
```

この `if !(b == v.Args[0].Block)` 条件は、`gen/AMD64.rules` で追加された `&& b == v.Args[0].Block` と直接対応しています。もしこの条件が偽（つまり、両方のオペレーションが異なるブロックにある）であれば、書き換えはスキップされ、元のSSA命令のまま残されます。これにより、メモリ変数のライブネス制約が破られるような不適切な最適化が防止されます。

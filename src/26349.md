# [インデックス 26349] ファイルの概要

このコミットは、Go言語の `net/http` パッケージにおいて、HTTPレスポンスのステータスコードが3桁でない場合に `ReadResponse` 関数がエラーを返すように修正するものです。これにより、HTTP/1.xの仕様に準拠しない不正なステータスコードを厳密に拒否し、パーシングの堅牢性を向上させます。

## 変更の背景

HTTP/1.xプロトコルでは、ステータスコードは常に3桁の整数で構成されることがRFC 7230 (旧RFC 2616) によって厳密に定義されています。しかし、Goの `net/http` パッケージの `ReadResponse` 関数は、これまでステータスコードの桁数に関する厳密な検証を行っていませんでした。このため、例えば "20 OK" のように2桁のステータスコードや、"1000 OK" のように4桁のステータスコードなど、非標準の形式を持つHTTPレスポンスを受信した場合でも、エラーとせずに処理を続行してしまう可能性がありました。

このような非標準のステータスコードを許容することは、以下のような問題を引き起こす可能性があります。

1.  **プロトコル違反**: HTTP仕様に準拠しないレスポンスを透過的に処理してしまうことで、GoのHTTPクライアントが不正なサーバーと通信する際に、その不正を検出できない。
2.  **セキュリティリスク**: 意図しないステータスコードの解釈により、アプリケーションロジックに予期せぬ動作や脆弱性が生じる可能性がある。例えば、特定のステータスコードに基づいて処理を分岐するロジックが、非標準のコードによって誤動作する。
3.  **相互運用性の問題**: 他の厳密なHTTPクライアントやサーバーとの間で、予期せぬ互換性の問題が発生する可能性がある。

このコミットは、これらの問題を解決し、`net/http` パッケージがHTTP/1.xの仕様にさらに厳密に準拠するようにするために導入されました。具体的には、`ReadResponse` 関数がステータスコードの桁数を検証し、3桁でない場合にはエラーを返すように変更されました。

## 前提知識の解説

### HTTPステータスコード

HTTPステータスコードは、HTTPレスポンスの最初の行（ステータスライン）に含まれる3桁の整数で、リクエストが成功したか、失敗したか、あるいは追加のアクションが必要かなど、サーバーがクライアントにリクエストの結果を伝えるために使用されます。

*   **1xx (Informational)**: リクエストは受信され、処理が継続していることを示す。
*   **2xx (Success)**: リクエストが正常に受信、理解、受理されたことを示す。例: 200 OK, 201 Created.
*   **3xx (Redirection)**: リクエストを完了するために、さらなるアクションが必要であることを示す。例: 301 Moved Permanently, 302 Found.
*   **4xx (Client Error)**: クライアントがエラーを発生させたことを示す。例: 400 Bad Request, 404 Not Found.
*   **5xx (Server Error)**: サーバーがリクエストの処理に失敗したことを示す。例: 500 Internal Server Error, 503 Service Unavailable.

RFC 7230 (Section 3.1.2) では、ステータスコードは `status-code = 3DIGIT` と定義されており、常に3桁の数字でなければなりません。

### Goの `net/http` パッケージ

`net/http` パッケージは、Go言語でHTTPクライアントとサーバーを実装するための標準ライブラリです。このパッケージは、HTTPリクエストの送信、レスポンスの受信、ヘッダーの解析、ボディの読み書きなど、HTTPプロトコルに関する広範な機能を提供します。

### `http.ReadResponse` 関数

`http.ReadResponse` 関数は、`bufio.Reader` からHTTPレスポンスを読み込み、`*http.Response` 構造体にパースする役割を担います。この関数は、ステータスライン、ヘッダー、そして必要に応じてボディを読み込み、それらをGoのデータ構造にマッピングします。

ステータスラインの形式は `HTTP/1.1 200 OK` のようになります。`ReadResponse` はこの行を解析し、プロトコルバージョン、ステータスコード、および理由フレーズを抽出します。

## 技術的詳細

このコミットの変更は、`src/net/http/response.go` 内の `ReadResponse` 関数に集中しています。

`ReadResponse` 関数は、まず `r.ReadLine()` を使用してステータスラインを読み込み、それをスペースで分割して `f` という文字列スライスに格納します。`f[0]` はプロトコルバージョン (例: "HTTP/1.1")、`f[1]` はステータスコード (例: "200")、そして `f[2]` 以降は理由フレーズ (例: "OK") に対応します。

変更前は、`f[1]` (ステータスコード部分) を `strconv.Atoi` で整数に変換する前に、その文字列の長さに関するチェックがありませんでした。このため、"20" や "1000" のような文字列も `Atoi` によって整数に変換され、`resp.StatusCode` に格納されていました。その後、`resp.StatusCode < 0` のチェックはありましたが、これは負の数に対するものであり、桁数に関するものではありませんでした。

このコミットでは、以下の2つの主要な変更が導入されました。

1.  **ステータスコードの桁数チェックの追加**: `f[1]` の長さが3ではない場合、`badStringError` を返してエラーとします。これは `if len(f[1]) != 3` という条件で実装されています。
2.  **`resp.Status` の設定順序の変更**: 以前は `resp.Status = f[1] + " " + reasonPhrase` が `strconv.Atoi` の前に実行されていましたが、新しい桁数チェックの後に移動されました。これにより、不正なステータスコードが検出された場合、`resp.Status` に不正な値が設定される前にエラーが返されるようになります。

これらの変更により、`ReadResponse` はHTTP/1.xの仕様に厳密に準拠し、3桁以外のステータスコードを含むレスポンスを不正なものとして扱います。

`src/net/http/response_test.go` では、この新しい検証ロジックをテストするための新しいテストケースが追加されています。これには、"20 OK"、"00 OK"、"-10 OK"、"1000 OK" など、以前は許容されていたが現在は拒否されるべき非標準のステータスコードが含まれています。

## コアとなるコードの解説

### `src/net/http/response.go` の変更点

1.  **ステータスコードの桁数検証の追加**:
    ```go
    	if len(f[1]) != 3 {
    		return nil, &badStringError{"malformed HTTP status code", f[1]}
    	}
    ```
    このコードブロックが `resp.StatusCode` のパース処理の直前に追加されました。`f[1]` はステータスコードの文字列部分（例: "200"）を含んでいます。HTTP/1.xの仕様ではステータスコードは常に3桁であるため、`len(f[1])` が3と等しくない場合（つまり、2桁や4桁以上のステータスコードの場合）、`badStringError` を含むエラーを即座に返します。これにより、不正な形式のステータスコードがそれ以上処理されるのを防ぎます。

2.  **`resp.Status` の設定位置の変更**:
    ```go
    	resp.StatusCode, err = strconv.Atoi(f[1])
    	if err != nil || resp.StatusCode < 0 {
    		return nil, &badStringError{"malformed HTTP status code", f[1]}
    	}
    	resp.Status = f[1] + " " + reasonPhrase
    ```
    変更前は `resp.Status = f[1] + " " + reasonPhrase` が `strconv.Atoi` の呼び出しとエラーチェックの前にありました。変更後は、ステータスコードの桁数チェックと `strconv.Atoi` による数値変換、およびその結果が負でないことの検証がすべて成功した後に `resp.Status` が設定されるようになりました。この順序変更により、不正なステータスコードが検出された場合、`Response` オブジェクトの `Status` フィールドに不正な値が設定される前にエラーが返され、オブジェクトの一貫性が保たれます。

### `src/net/http/response_test.go` の変更点

テストファイルでは、`TestReadResponseErrors` 関数内の `status` ヘルパー関数呼び出しリストが更新されています。

*   **削除された行**:
    ```go
    		status("20 OK", nil), // TODO: wrong. we should reject non-three digit
    ```
    以前は "20 OK" が `nil` (エラーなし) で処理されることを期待していましたが、コメントで「非3桁を拒否すべき」と指摘されていました。このコミットにより、この `TODO` が解決され、このテストケースはエラーを期待するように変更されます。

*   **追加された行**:
    ```go
    		status("000 OK", nil),
    		status("001 OK", nil),
    		status("404 NOTFOUND", nil),
    		status("20 OK", true),
    		status("00 OK", true),
    		status("-10 OK", true),
    		status("1000 OK", true),
    		status("999 Done", nil),
    		status("-1 OK", true),
    		status("-200 OK", true),
    ```
    これらの新しいテストケースは、新しい検証ロジックの動作を検証します。
    *   `status("000 OK", nil)`, `status("001 OK", nil)`, `status("404 NOTFOUND", nil)`, `status("999 Done", nil)`: これらは3桁の有効なステータスコード（またはその形式）であり、エラーを発生させないことを期待します (`nil` はエラーがないことを意味します)。
    *   `status("20 OK", true)`, `status("00 OK", true)`, `status("-10 OK", true)`, `status("1000 OK", true)`, `status("-1 OK", true)`, `status("-200 OK", true)`: これらはすべて3桁ではない、または負のステータスコードであり、新しい検証ロジックによってエラーが発生することを期待します (`true` はエラーが発生することを意味します)。特に "20 OK" と "1000 OK" は、以前はパースされていた可能性のあるケースを明示的にエラーとして扱うことをテストしています。

これらのテストケースの追加により、`ReadResponse` 関数がHTTPステータスコードの桁数に関する仕様を正しく強制していることが保証されます。

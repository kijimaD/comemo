# [インデックス 22880] ファイルの概要

このコミットは、GoランタイムのCGO（C言語との相互運用）部分において、Darwin (macOS/iOS) 上のARM64アーキテクチャで発生する`EXC_BAD_ACCESS`例外（セグメンテーション違反に相当）のハンドリングを改善するものです。これにより、CGOコード内で不正なメモリアクセスが発生した場合に、Goランタイムが適切にパニックを検出し、処理できるようになります。

## 変更の背景

GoプログラムがCGOを介してCコードを呼び出す際、Cコード内で不正なメモリアクセス（例えば、ヌルポインタ参照や解放済みメモリへのアクセス）が発生すると、オペレーティングシステムは通常、セグメンテーション違反（SIGSEGV）のようなシグナルをプロセスに送信します。Darwin（macOS/iOS）システムでは、これはMach例外メカニズムを通じて`EXC_BAD_ACCESS`として通知されます。

Goランタイムは、このような致命的なエラーを捕捉し、Goのパニックメカニズムに変換して、プログラムが予期せぬ終了をする前に適切な処理（例えば、スタックトレースの出力）を行おうとします。しかし、ARM64アーキテクチャがGoのサポート対象として登場した際、既存のシグナルハンドリングロジックがARM64のレジスタセットや例外処理の特性に完全に対応していませんでした。

このコミット以前は、ARM64環境でCGOを介したCコードが`EXC_BAD_ACCESS`を引き起こした場合、Goランタイムがその例外を適切に捕捉・処理できず、プログラムがクラッシュする可能性がありました。この変更は、ARM64アーキテクチャにおける`EXC_BAD_ACCESS`のハンドリングを確立し、Goプログラムの堅牢性を向上させることを目的としています。

## 前提知識の解説

### 1. `EXC_BAD_ACCESS`と`SIGSEGV`

*   **`SIGSEGV` (Segmentation Fault)**: Unix系システムで、プログラムが不正なメモリアクセス（例えば、読み取り専用メモリへの書き込み、存在しないアドレスへのアクセス）を試みた際にカーネルがプロセスに送信するシグナルです。これにより、通常はプログラムが異常終了します。
*   **`EXC_BAD_ACCESS`**: Darwin（macOS/iOS）システムにおけるMach例外の一種で、`SIGSEGV`に相当します。Mach例外は、Unixシグナルよりも低レベルで、カーネルが直接プロセスに通知する例外処理メカニズムです。Goランタイムは、これらのMach例外を捕捉し、Goのパニックに変換することで、よりGoらしいエラー処理フローを提供します。

### 2. CGO (C Foreign Function Interface for Go)

Go言語からC言語の関数を呼び出したり、C言語からGoの関数を呼び出したりするためのメカニズムです。CGOを使用すると、Goプログラムは既存のCライブラリを利用できます。CGOを介して呼び出されたCコード内で発生したエラーは、Goランタイムが処理する必要があります。

### 3. Goランタイムのシグナルハンドリング

Goランタイムは、プログラムの実行中に発生する様々なシグナル（例えば、`SIGINT`、`SIGTERM`、`SIGSEGV`など）を捕捉し、Goの内部メカニズム（例えば、パニック、ゴルーチンの停止）に変換します。特に`SIGSEGV`のような致命的なシグナルは、Goのパニックとして処理され、スタックトレースが出力された後にプログラムが終了します。

### 4. Mach例外ハンドリング

Darwinシステムでは、シグナルよりも低レベルなMach例外という概念があります。プロセスは、特定のMach例外（例えば`EXC_BAD_ACCESS`）が発生した際に通知を受け取るためのポートを設定できます。Goランタイムは、このメカニズムを利用して、CGOコード内で発生したメモリアクセス違反を捕捉します。

### 5. ARM64アーキテクチャ

Apple Siliconや一部のAndroidデバイスなどで採用されている64ビットARMプロセッサアーキテクチャです。レジスタセットや命令セットが従来のARMv7（32ビット）とは異なり、例外処理のコンテキスト（スレッドの状態）も異なります。このコミットは、特にARM64のレジスタ（`__x`レジスタ、`__lr`リンクレジスタ、`__pc`プログラムカウンタ）の扱いを考慮しています。

### 6. `g`レジスタとGoルーチン

Goランタイムは、各Goルーチン（軽量スレッド）の状態を`g`という構造体で管理しています。`g`レジスタ（または`g`ポインタ）は、現在のGoルーチンを示すポインタであり、Goランタイムの多くの低レベル操作で利用されます。CコードからGoランタイムの関数を呼び出す場合など、`g`レジスタが適切に設定されているかを確認する必要があります。

### 7. `sigpanic`と`setsigsegv`

Goランタイム内部の関数です。
*   `sigpanic`: セグメンテーション違反などのシグナルによって引き起こされるパニックを処理するGoランタイムの関数です。スタックトレースを生成し、プログラムを終了させます。
*   `setsigsegv`: `sigpanic`を呼び出す前に、Goルーチンの状態にセグメンテーション違反が発生したことを記録するための関数です。これにより、スタックトレースがより正確になります。

## 技術的詳細

このコミットの主要な目的は、Darwin ARM64環境で`EXC_BAD_ACCESS`が発生した際に、Goランタイムがそれを捕捉し、Goのパニックとして処理するメカニズムを実装することです。

変更は主に以下の2つのファイルで行われています。

1.  **`src/runtime/cgo/gcc_signal_darwin_armx.c`**:
    *   このCファイルは、DarwinにおけるMach例外ハンドラのエントリポイントである`catch_exception_raise`関数を含んでいます。この関数は、`EXC_BAD_ACCESS`などの例外がMachカーネルによって通知された際に呼び出されます。
    *   変更点として、ARM64アーキテクチャ（`__arm64__`マクロで識別）の場合の処理が追加されました。具体的には、例外発生時のスレッドの状態（`thread_state`）から、リンクレジスタ（`__lr`）とプログラムカウンタ（`__pc`）の値を抽出し、これらを`x_cgo_panicmem`というアセンブリ関数の引数として渡すように設定しています。
    *   以前は32ビットARM（`__r`レジスタ）のみに対応していましたが、この変更で64ビットARM（`__x`レジスタ）に対応しました。
    *   デバッグ用の`fprintf`文と、無限ループを防ぐための`pass1`フラグが追加されていますが、これらはデバッグ目的のコードであり、最終的なリリースビルドでは通常無効化されます。
    *   `darwin_arm_init_mach_exception_handler`関数内で、`pthread_create`に渡す引数として`mach_exception_handler_port_set`を`uintptr_t`にキャストする変更が行われています。これは、ポインタの型安全性を高めるための小さな修正です。

2.  **`src/runtime/cgo/signal_darwin_arm64.s`**:
    *   このファイルは新しく追加されたもので、ARM64アセンブリ言語で記述されています。
    *   `·panicmem`という関数が定義されています。これは、`gcc_signal_darwin_armx.c`から呼び出される`x_cgo_panicmem`に対応するGoランタイムのアセンブリ関数です。
    *   このアセンブリ関数の主な役割は、`EXC_BAD_ACCESS`が発生したスレッドがGoルーチン上にあるかどうかを判断し、適切にGoのパニック処理（`sigpanic`）をトリガーすることです。
    *   まず、`runtime·load_g(SB)`を呼び出して現在のGoルーチン（`g`）のポインタをロードします。
    *   もし`g`がヌル（つまり、Goルーチンではない外部Cスレッドで例外が発生した場合）であれば、`runtime·exit(SB)`を呼び出してプログラムを終了させます（TODOとして`badsignal`の呼び出しがコメントされています）。
    *   Goルーチン上であれば、`runtime·setsigsegv(SB)`を呼び出して、セグメンテーション違反の情報をGoルーチンの状態に記録します。この際、例外発生時のPC（プログラムカウンタ）とLR（リンクレジスタ）をスタックに保存し、`setsigsegv`に渡します。
    *   最後に、例外発生時のPCとLRをレジスタに復元し、`runtime·sigpanic(SB)`を呼び出します。これにより、Goのパニック処理が開始され、適切なスタックトレースが生成されます。

この一連の処理により、ARM64環境でCGOコードが不正なメモリアクセスを行った場合でも、Goランタイムがその例外を捕捉し、Goのパニックとして処理できるようになり、デバッグ情報（スタックトレース）の取得が可能になります。

## コアとなるコードの解説

### `src/runtime/cgo/gcc_signal_darwin_armx.c`

このファイルは、Mach例外ハンドラである`catch_exception_raise`関数を含んでいます。この関数は、カーネルから`EXC_BAD_ACCESS`などの例外通知を受け取った際に呼び出されます。

*   **ビルドタグの変更**:
    ```c
    // +build !lldb
    // +build darwin
    // +build arm arm64
    ```
    以前は`darwin,arm,!lldb`と`TODO(crawshaw): darwin,arm64,!lldb`というコメントがありましたが、新しいビルドタグは`arm`と`arm64`の両方を対象とし、`lldb`タグがない場合にビルドされるように変更されています。これにより、ARM64アーキテクチャが正式にサポート対象に含まれるようになりました。

*   **ARM64固有のレジスタ操作**:
    ```c
    #ifdef __arm64__
    	thread_state.ts_64.__x[1] = thread_state.ts_64.__lr;
    	thread_state.ts_64.__x[2] = thread_state.ts_64.__pc;
    	thread_state.ts_64.__pc = x_cgo_panicmem;
    #else
    	thread_state.ts_32.__r[1] = thread_state.ts_32.__lr;
    	thread_state.ts_32.__r[2] = thread_state.ts_32.__pc;
    	thread_state.ts_32.__pc = x_cgo_panicmem;
    #endif
    ```
    この部分が最も重要な変更点です。`__arm64__`マクロが定義されている場合（つまりARM64アーキテクチャの場合）、`thread_state.ts_64`構造体（64ビットスレッドの状態）を使用します。
    *   `thread_state.ts_64.__lr` (リンクレジスタ) の値を`__x[1]`に、`thread_state.ts_64.__pc` (プログラムカウンタ) の値を`__x[2]`にコピーしています。これは、後続のアセンブリコード（`x_cgo_panicmem`）がこれらの値を引数として受け取るための準備です。
    *   `thread_state.ts_64.__pc`を`x_cgo_panicmem`のアドレスに設定しています。これにより、例外ハンドラから復帰する際に、元の実行パスではなく`x_cgo_panicmem`が実行されるようになります。
    *   `else`ブロックは32ビットARMアーキテクチャ向けの既存のロジックで、同様に`__r`レジスタを操作しています。

*   **デバッグロジック**:
    ```c
    	if (0) { // ...
    ```
    `if (0)`で囲まれているため、このコードは通常コンパイルされません。これは、`panicmem`が壊れた場合のデバッグに役立つコメントと`fprintf`文、そしてiOSデバイスがロックアップするのを防ぐための`pass1`フラグを含んでいます。

*   **`pthread_create`の引数キャスト**:
    ```c
    	uintptr_t port_set = (uintptr_t)mach_exception_handler_port_set;
    	ret = pthread_create(&thr, &attr, mach_exception_handler, (void*)port_set);
    ```
    `mach_exception_handler_port_set`を`uintptr_t`に明示的にキャストしてから`void*`にキャストしています。これは、ポインタのサイズが異なる環境での潜在的な警告や問題を回避するための、より堅牢なコーディングスタイルです。

### `src/runtime/cgo/signal_darwin_arm64.s`

この新しいアセンブリファイルは、ARM64アーキテクチャ専用の`panicmem`関数を定義しています。この関数は、`gcc_signal_darwin_armx.c`から`x_cgo_panicmem`として呼び出されます。

*   **`TEXT ·panicmem(SB),NOSPLIT,$-8`**:
    `panicmem`というGoのアセンブリ関数を定義しています。`NOSPLIT`はスタックフレームを分割しないことを意味し、`$-8`はスタックフレームサイズが8バイトであることを示します。

*   **`BL runtime·load_g(SB)`**:
    `runtime·load_g`関数を呼び出し、現在のGoルーチン（`g`）のポインタをロードします。これは、例外が発生したスレッドがGoルーチンであるか、それとも外部のCスレッドであるかを判断するために必要です。

*   **`CMP $0, g` と `BNE ongothread`**:
    ロードされた`g`レジスタの値が0と比較されます。もし`g`が0でなければ（つまりGoルーチン上であれば）、`ongothread`ラベルに分岐します。

*   **外部スレッドの場合**:
    ```asm
    	// On a foreign thread.
    	// TODO(crawshaw): call badsignal
    	MOVW $139, R1
    	MOVW R1, (RSP)
    	B    runtime·exit(SB)
    ```
    `g`が0の場合（外部Cスレッドで例外が発生した場合）、`runtime·exit(SB)`を呼び出してプログラムを終了させます。`MOVW $139, R1`と`MOVW R1, (RSP)`は、終了コード139（SIGSEGVに対応する終了コード）をスタックに設定している可能性があります。`TODO(crawshaw): call badsignal`というコメントは、将来的により適切なシグナル処理（`badsignal`関数）を呼び出すべきであることを示唆しています。

*   **Goルーチン上の場合 (`ongothread`ラベル)**:
    ```asm
    	STP.W (R1, R2), -16(RSP)
    	BL runtime·setsigsegv(SB)
    	LDP.P 16(RSP), (R1, R2)
    ```
    *   `STP.W (R1, R2), -16(RSP)`: `R1`（元のLR）と`R2`（元のPC）の値をスタックに保存します。`STP`はPair Store命令で、2つのレジスタを同時にストアします。`-16(RSP)`はスタックポインタから16バイト引いたアドレスにストアすることを意味し、スタックを拡張しています。
    *   `BL runtime·setsigsegv(SB)`: `runtime·setsigsegv`関数を呼び出します。この関数は、Goルーチンの状態にセグメンテーション違反が発生したことを記録します。
    *   `LDP.P 16(RSP), (R1, R2)`: スタックから元のLRとPCの値を`R1`と`R2`にロードし直します。`LDP`はPair Load命令で、2つのレジスタを同時にロードします。`16(RSP)`はスタックポインタから16バイト加算したアドレスからロードすることを意味し、スタックを元に戻しています。

*   **`sigpanic`の呼び出し**:
    ```asm
    	MOVD R1, 8(RSP)
    	MOVD R2, R30 // link register
    	B runtime·sigpanic(SB)
    ```
    *   `MOVD R1, 8(RSP)`: `R1`（元のLR）の値をスタックの8バイトオフセットに移動します。これは、`sigpanic`がスタックトレースを生成する際に、呼び出し元のPCとしてこの値を使用できるようにするためです。
    *   `MOVD R2, R30`: `R2`（元のPC）の値を`R30`レジスタ（ARM64のリンクレジスタ）に移動します。これにより、`sigpanic`が呼び出された際に、あたかも元のPCから直接呼び出されたかのように見せかけることができます。
    *   `B runtime·sigpanic(SB)`: `runtime·sigpanic`関数に無条件分岐します。これにより、Goのパニック処理が開始されます。

このアセンブリコードは、Mach例外ハンドラからGoランタイムのパニック処理への橋渡しを行い、特にARM64のレジスタ規約とスタックフレームの扱いに対応しています。これにより、CGOコードで発生したメモリアクセス違反がGoのパニックとして適切に処理され、デバッグが容易になります。

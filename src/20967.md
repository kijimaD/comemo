## 変更の背景

この変更の背景には、GoランタイムがPowerPC 64-bit (power64) アーキテクチャのサポートを導入したことがあります。Goのランタイムは、異なるCPUアーキテクチャ上で正しく動作するために、アーキテクチャ固有のコードや考慮事項を持つことがあります。特に、パニックからの回復処理やスタックのアンワインド（巻き戻し）は、アーキテクチャによってスタックフレームの構造やレジスタの扱いが異なるため、注意が必要です。

以前のコメントは、ARMアーキテクチャにおけるスタックの特性（特にLink Register (LR) の扱い）について言及していましたが、PowerPCアーキテクチャも同様の特性を持つようになったにもかかわらず、その情報が反映されていませんでした。このコミットは、コードの動作自体を変更するものではなく、その動作を説明するコメントが最新のランタイムのサポート状況と一致するように修正することを目的としています。これにより、コードの可読性と正確性が向上し、将来のメンテナンスや理解が容易になります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびCPUアーキテクチャに関する基本的な知識が必要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルのシステムです。これには、ゴルーチンのスケジューリング、メモリ管理（ガベージコレクション）、チャネル通信、パニックと回復の処理などが含まれます。ランタイムはGoプログラムとオペレーティングシステムおよびハードウェアの間の橋渡しをします。`src/runtime`ディレクトリには、このランタイムのコア部分のソースコードが含まれています。

*   **`panic`と`recover`**:
    *   `panic`: Goにおける例外処理メカニズムの一つです。プログラムの通常の実行フローを中断し、現在のゴルーチンの遅延関数（`defer`で登録された関数）を順次実行しながらスタックを巻き戻していきます。最終的に、`recover`が呼び出されない限り、プログラムは異常終了します。
    *   `recover`: `panic`によって中断されたゴルーチンの実行を再開するために使用される組み込み関数です。`recover`は`defer`関数内でのみ有効であり、パニックが発生したときに`recover`を呼び出すことで、パニックの値を取得し、プログラムの異常終了を防ぐことができます。

*   **`defer`**: Goのキーワードで、関数がリターンする直前（またはパニックが発生してスタックが巻き戻される際）に実行される関数を登録するために使用されます。`defer`は、リソースの解放（ファイルのクローズ、ロックの解除など）や、`panic`からの回復処理によく利用されます。

*   **スタックのアンワインド (Stack Unwinding)**: `panic`が発生した際に、現在の関数呼び出しスタックを逆順にたどり、各スタックフレームに関連付けられた遅延関数を実行していくプロセスです。このプロセス中に、スタックポインタ（SP）などのレジスタが適切に調整されます。

*   **アーキテクチャ固有のコード**: CPUアーキテクチャ（例: ARM, PowerPC, x86）によって、レジスタのセット、命令セット、メモリのアクセス方法、スタックフレームのレイアウトなどが異なります。Goランタイムのような低レベルのコードでは、これらのアーキテクチャ固有の特性を考慮し、場合によっては異なる実装を提供する必要があります。

*   **Link Register (LR)**: ARMやPowerPCなどの一部のRISCアーキテクチャに存在する特殊なレジスタです。関数呼び出しが行われる際に、呼び出し元に戻るアドレス（リターンアドレス）がこのLRに保存されます。関数から戻る際には、LRに保存されたアドレスにジャンプすることで、呼び出し元に制御が戻されます。スタックのアンワインド時には、このLRの値が適切に処理される必要があります。

## 技術的詳細

このコミットは、`src/runtime/panic.c`ファイル内の`runtime·recovery_m`関数に関連するコメントの修正です。

`runtime·recovery_m`関数は、Goの`recover`メカニズムの中核をなす部分であり、パニックが発生したゴルーチンが`recover`によって回復される際に、そのゴルーチンの実行状態（特にスタックポインタ`gp->sched.sp`）を調整する役割を担っています。

変更されたコメントは以下の部分です。

```c
// On the arm there are 2 saved LRs mixed in too.
```

このコメントは、ARMアーキテクチャにおいて、スタック上に2つのLink Register (LR) が保存されることを示していました。これは、特定の呼び出し規約やスタックフレームの構造に起因するもので、`panic`からの回復時にスタックポインタを正しく調整するために重要な情報です。

このコミットでは、このコメントが以下のように修正されました。

```c
// On the arm and power there are 2 saved LRs mixed in too.
```

この修正は、GoランタイムがPowerPCアーキテクチャ（`power`）もサポートするようになり、そのPowerPCアーキテクチャにおいても、ARMと同様に2つのLink Registerがスタックに保存されるという特性を持つことを反映しています。

コードの該当箇所では、`thechar`という変数が使用されています。これは、Goの古いツールチェイン（Plan 9由来）でアーキテクチャを識別するために使われていた単一文字の識別子です。
*   `'5'` はARMアーキテクチャを指します。
*   `'9'` はPowerPCアーキテクチャ（特にppc64）を指すと推測されます。

```c
if(thechar == '5' || thechar == '9')
    gp->sched.sp = (uintptr)argp - 4*sizeof(uintptr);
else
    // ...
```

この`if`文は、現在のアーキテクチャがARMまたはPowerPCである場合に、スタックポインタ`gp->sched.sp`を特定のオフセット（`4*sizeof(uintptr)`）だけ調整することを示しています。このオフセットは、スタックに保存されたLRなどのレジスタのサイズを考慮したものであり、コメントはこのオフセットが必要となる理由を説明しています。

したがって、この変更は、PowerPCアーキテクチャがGoランタイムに統合され、そのスタック回復メカニズムがARMと類似の特性を持つようになったことを、コメントを通じて明確にするものです。機能的なバグ修正ではなく、ドキュメンテーションの正確性を高めるための「ハウスキーピング」的な変更と言えます。

## コアとなるコードの解説

変更は`src/runtime/panic.c`ファイルの`runtime·recovery_m`関数内の一行のコメントに限定されています。

元のコメント:
`// On the arm there are 2 saved LRs mixed in too.`
このコメントは、ARMアーキテクチャにおいて、スタック上に2つのLink Register (LR) が保存されており、これがスタックのレイアウトに影響を与えることを示していました。これは、`panic`からの回復時にスタックポインタを正しく調整するために考慮すべき点でした。

変更後のコメント:
`// On the arm and power there are 2 saved LRs mixed in too.`
この変更により、「arm」に加えて「power」という記述が追加されました。これは、GoランタイムがPowerPCアーキテクチャ（`power`）をサポートするようになり、そのPowerPCアーキテクチャにおいても、ARMと同様に2つのLink Registerがスタックに保存されるという特性を持つことを明示しています。

このコメントの直後にある`if(thechar == '5' || thechar == '9')`という条件分岐は、`thechar`がARM (`'5'`) またはPowerPC (`'9'`) の場合に、スタックポインタ`gp->sched.sp`を特定のオフセットだけ調整する処理を行っています。このコード自体は変更されていませんが、コメントの修正により、この条件分岐がなぜARMとPowerPCの両方を対象としているのかがより明確になりました。

このコミットは、機能的な動作を変更するものではなく、Goランタイムがサポートするアーキテクチャの範囲が広がり、それに伴うスタック処理の特性が、既存のコメントでは不完全であったために行われた、ドキュメンテーションの更新です。これにより、コードの意図がより正確に伝わるようになります。

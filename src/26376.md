# [インデックス 26376] ファイルの概要

このコミットは、Goランタイムの`futex_test.go`ファイルにおける`TestFutexsleep`テストの複数の問題を修正し、テストの信頼性と正確性を向上させるものです。特に、`futex`（Fast Userspace muTex）の動作を正しくテストできるよう、同期メカニズムの誤用を是正しています。

## コミット

```

Author: Austin Clements <austin@google.com>
Date:   Wed Jan 13 15:14:26 2016 -0500

    runtime: fix several issues in TestFutexsleep
    
    TestFutexsleep is supposed to clean up before returning by waking up
    the goroutines it started and left blocked in futex sleeps. However,
    it currently fails at this in several ways:
    
    1. Both the sleep and wakeup are done on the address of tt.mtx, but in
       both cases tt is a *local copy* of the futexsleepTest created by a
       loop, so the sleep and wakeup happen on completely different
       addresses. Fix this by making them both use the address of the
       global tt.mtx.
    
    2. If the sleep happens after the wakeup (not likely, but not
       impossible), it won't wake up. Fix this by using the futex protocol
       properly: sleep if the mutex's value is 0, and set the mutex's
       value to non-zero before doing the wakeup.

       left over from the first run will interfere with later runs. Fix
       this by clearing the mutex value and creating a new channel for
       each test and waiting for goroutines to finish before returning
       (lest they send their completion to the channel for the next run).
    
    As an added bonus, this test now actually tests that futex
    sleep/wakeup work. Previously this test would have been satisfied if
    futexsleep was an infinite loop and futexwakeup was a no-op.
```

## 元コミット内容

`runtime: fix several issues in TestFutexsleep`

`TestFutexsleep`は、開始したゴルーチンを`futex`スリープでブロックさせた後、それらをウェイクアップしてクリーンアップするはずでした。しかし、以下の点で失敗していました。

1.  スリープとウェイクアップの両方が`tt.mtx`のアドレスに対して行われていましたが、ループによって作成された`futexsleepTest`の*ローカルコピー*である`tt`のアドレスが使われていたため、スリープとウェイクアップが全く異なるアドレスに対して行われていました。これを、グローバルな`tt.mtx`のアドレスを使用するように修正しました。
2.  スリープがウェイクアップの後に発生した場合（可能性は低いが、ありえないことではない）、ウェイクアップされません。これを、`futex`プロトコルを適切に使用することで修正しました。具体的には、ミューテックスの値が0の場合にスリープし、ウェイクアップを行う前にミューテックスの値を非ゼロに設定するようにしました。
3.  `TestFutexsleep`が複数回実行された場合、最初の実行で残されたチャネルやミューテックスの値が、後続の実行に干渉していました。これを、各テストでミューテックスの値をクリアし、新しいチャネルを作成し、ゴルーチンが完了するまで待機してから戻るようにすることで修正しました（そうしないと、完了通知が次の実行のチャネルに送られてしまうため）。

さらに、このテストは`futex`のスリープ/ウェイクアップが実際に機能することをテストするようになりました。以前は、`futexsleep`が無限ループで`futexwakeup`が何もしない操作であっても、このテストは成功してしまっていました。

## 変更の背景

このコミットの背景には、Goランタイムの低レベル同期プリミティブである`futex`のテストが、その本来の目的を十分に果たしていなかったという問題があります。`futex`は、Linuxカーネルが提供する高速なユーザー空間ミューテックスであり、Goランタイムのスケジューラや同期メカニズムの基盤として重要な役割を担っています。

`TestFutexsleep`は、この`futex`の`sleep`と`wakeup`の動作を検証するためのテストですが、元の実装にはいくつかの論理的な欠陥がありました。これらの欠陥により、テストが誤った結果を報告したり、テストの実行が不安定になったり、最悪の場合、`futex`の実装にバグがあってもテストがそれを検出できないという状況に陥っていました。

具体的には、テストのセットアップとクリーンアップのロジックが不完全であり、特に並行処理のコンテキストで発生しうる競合状態や、テストの再実行時の状態の持ち越しが問題となっていました。これらの問題は、テストの信頼性を損ない、Goランタイムの安定性や正確性に対する確信を揺るがす可能性がありました。

このコミットは、これらの根本的な問題を解決し、`TestFutexsleep`が`futex`の正しい動作を確実に検証できるようにすることで、Goランタイムの堅牢性を高めることを目的としています。

## 前提知識の解説

### Futex (Fast Userspace muTex)

`futex`は、Linuxカーネルが提供する同期プリミティブであり、ユーザー空間で高速なミューテックス（相互排他ロック）を実装するために使用されます。一般的なミューテックスは、ロックの取得と解放のたびにカーネルモードへの切り替え（システムコール）を伴いますが、`futex`は競合が発生しない限りユーザー空間で処理を完結させることができます。

`futex`の基本的な動作は以下の通りです。

1.  **ユーザー空間での競合チェック**: スレッドはまず、共有メモリ上の特定の整数値（`futex`変数）をユーザー空間でチェックします。
2.  **ユーザー空間でのロック取得**: 競合がなければ、アトミック操作で`futex`変数を変更し、ロックを取得します。この際、カーネルへのシステムコールは不要です。
3.  **カーネルへのフォールバック**: 競合が発生した場合（`futex`変数が既にロックされていることを示す値の場合）、スレッドは`futex`システムコールを呼び出してカーネルに処理を委ねます。
4.  **スリープ**: カーネルは、`futex`変数が解放されるまでスレッドをスリープ状態にします。
5.  **ウェイクアップ**: ロックを解放するスレッドは、`futex`システムコールを呼び出して、その`futex`変数でスリープしているスレッドをウェイクアップします。

`futex`システムコールには、主に`FUTEX_WAIT`と`FUTEX_WAKE`があります。
*   `FUTEX_WAIT(addr, val, timeout)`: `addr`が指すメモリ位置の値が`val`と等しい場合、スレッドをスリープさせます。`timeout`が指定されていれば、その時間経過後にタイムアウトします。
*   `FUTEX_WAKE(addr, num_wake)`: `addr`が指すメモリ位置でスリープしているスレッドのうち、最大`num_wake`個をウェイクアップします。

このコミットでは、`runtime.Futexsleep`と`runtime.Futexwakeup`というGoランタイム内部の関数が使用されており、これらが上記の`futex`システムコールをラップしていると考えられます。

### Goのゴルーチンとチャネル

*   **ゴルーチン (Goroutine)**: Goにおける軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数千から数百万のゴルーチンを同時に実行できます。Goランタイムのスケジューラによって管理されます。
*   **チャネル (Channel)**: ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは、ゴルーチン間の同期と通信を安全に行うための主要な手段です。バッファ付きチャネルとバッファなしチャネルがあります。

### `sync.WaitGroup`

`sync.WaitGroup`は、複数のゴルーチンの完了を待機するために使用される同期プリミティブです。カウンタを内部に持ち、`Add`メソッドでカウンタを増やし、`Done`メソッドでカウンタを減らします。`Wait`メソッドは、カウンタがゼロになるまでブロックします。これにより、メインのゴルーチンが、開始したすべてのバックグラウンドゴルーチンが処理を完了するまで待機することができます。

### `sync/atomic`パッケージ

`sync/atomic`パッケージは、低レベルのアトミック操作（不可分操作）を提供します。これにより、複数のゴルーチンが共有メモリ上の変数を同時に読み書きする際に、競合状態を避けて安全に操作を行うことができます。例えば、`atomic.StoreUint32`は、`uint32`型の値をアトミックに書き込むために使用されます。

### Y2038問題

Y2038問題は、Unix時間（エポックからの秒数）を32ビット符号付き整数で表現しているシステムにおいて、2038年1月19日3時14分7秒 (UTC) を超えるとオーバーフローが発生し、時間が負の値として解釈されることで様々な問題を引き起こす可能性があるというものです。このコミットのテストコードには`beforeY2038`と`afterY2038`というテストケースがあり、`futex`のタイムアウト処理がこの問題の影響を受けないことを検証しようとしています。

## 技術的詳細

このコミットは、`TestFutexsleep`の以下の3つの主要な問題を解決しています。

1.  **ローカルコピーの問題**:
    元のコードでは、`for _, tt := range futexsleepTests`というループを使っていました。Goでは、`range`ループで構造体をイテレートすると、`tt`は元のスライス要素の*コピー*になります。したがって、`&tt.mtx`はループの各イテレーションで異なるローカル変数のアドレスを指していました。しかし、`futex`は特定のメモリ位置（アドレス）を監視するため、スリープとウェイクアップが異なるアドレスに対して行われると、ウェイクアップがスリープ中のゴルーチンに到達しませんでした。
    **修正**: `for i := range futexsleepTests`に変更し、`tt := &futexsleepTests[i]`とすることで、`tt`が元のスライス内の要素へのポインタを指すようにしました。これにより、スリープとウェイクアップが常に同じグローバルな`mtx`フィールドのアドレスに対して行われるようになります。また、`futexsleepTest`構造体のチャネルもポインタ型`chan *futexsleepTest`に変更され、チャネルを通じて送受信される値もポインタになりました。

2.  **不適切なFutexプロトコル**:
    `futex`の`wait`操作（`FUTEX_WAIT`）は、指定されたメモリ位置の値が期待値と一致する場合にのみスリープします。元のコードでは、`runtime.Futexsleep(&tt.mtx, tt.mtx, tt.ns)`となっており、`tt.mtx`の現在の値を期待値として渡していました。しかし、ウェイクアップがスリープより先に発生した場合、`tt.mtx`の値は変更されず、スリープが実行されてもウェイクアップの通知を受け取ることができませんでした。
    **修正**:
    *   `runtime.Futexsleep(&tt.mtx, 0, tt.ns)`: スリープする際の期待値を`0`に固定しました。これは、`futex`が通常、ロックされていない状態を`0`で表現することに対応しています。
    *   `atomic.StoreUint32(&tt.mtx, 1)`: `runtime.Futexwakeup`を呼び出す前に、`tt.mtx`の値をアトミックに`1`に設定しました。これにより、`futex`プロトコルに従い、ウェイクアップの意図を明確に示し、スリープ中のゴルーチンがウェイクアップされるべき状態であることを保証します。もしスリープがウェイクアップより先に発生し、`tt.mtx`が`0`であれば、スリープは正しく実行されます。ウェイクアップが先に発生した場合、`tt.mtx`は`1`になり、スリープは実行されません（期待値`0`と異なるため）。

3.  **テスト実行間の状態の持ち越し**:
    元のテストでは、`futexsleepTest`構造体の`ch`フィールドがグローバルに初期化されており、`mtx`フィールドもリセットされていませんでした。これにより、`TestFutexsleep`が複数回実行されると、前回の実行で残されたチャネルやミューテックスの状態が次の実行に影響を与え、テストの信頼性を損なっていました。
    **修正**:
    *   `tt.mtx = 0`: 各テストケースの開始時に`mtx`フィールドを`0`にクリアします。
    *   `tt.ch = make(chan *futexsleepTest, 1)`: 各テストケースの開始時に新しいチャネルを作成します。これにより、テストケース間でチャネルの状態が共有されることを防ぎます。
    *   `var wg sync.WaitGroup`と`wg.Add(1)`, `wg.Done()`, `wg.Wait()`: `sync.WaitGroup`を導入し、各ゴルーチンが完了するまで`TestFutexsleep`関数が待機するようにしました。これにより、ゴルーチンがテスト関数の終了後にバックグラウンドで実行され続け、次のテスト実行に干渉するのを防ぎます。

これらの修正により、`TestFutexsleep`は`futex`の動作をより正確かつ信頼性高くテストできるようになり、以前のように`futexsleep`が無限ループで`futexwakeup`が何もしない場合でもテストが成功してしまうような誤った陽性反応を防ぐことができます。

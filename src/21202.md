## 変更の背景

このコミットの主な背景は、Goランタイムにおけるガベージコレクション（GC）のライトバリアが持つスタックフットプリントの問題です。ライトバリアは、GCがオブジェクトグラフを正確に追跡し、並行して実行されるアプリケーションコードとの整合性を保つために不可欠なメカニズムです。しかし、当時の実装では、ライトバリアが頻繁に呼び出されることで、特にスタック使用量が増大し、これがパフォーマンスのボトルネックとなったり、特定の機能（例えばレース検出器）の動作を妨げたりする可能性がありました。

コミットメッセージにある「This is going to hurt a bit but we'll make it better later. Now the race detector can be run again.」という記述は、この変更が一時的に何らかのパフォーマンス上の「痛み」を伴う可能性があるものの、将来的には改善されること、そしてこの変更によってレース検出器が再び利用可能になるという重要なメリットがあることを示唆しています。レース検出器は、並行処理におけるデータ競合を検出するための強力なツールであり、その有効化はGoプログラムの信頼性向上に大きく貢献します。

また、「CL 183020043からのライトバリア最適化を追加した」という言及は、このコミットが単独の変更ではなく、以前の最適化作業の延長線上にあることを示しています。これは、ライトバリアの効率化が継続的な課題であったことを示唆しています。

## 前提知識の解説

### Goのガベージコレクション（GC）とライトバリア

Goのガベージコレクションは、メモリ管理を自動化し、開発者が手動でメモリを解放する手間を省きます。GoのGCは、並行（concurrent）、三色マーク＆スイープ（tri-color mark-and-sweep）アルゴリズムをベースにしています。

*   **三色マーク＆スイープ**:
    *   **白（White）**: GCによってまだ到達可能と判断されていないオブジェクト。GCの対象候補。
    *   **灰（Grey）**: GCによって到達可能と判断されたが、その参照先がまだスキャンされていないオブジェクト。
    *   **黒（Black）**: GCによって到達可能と判断され、その参照先もすべてスキャンされたオブジェクト。
    GCは、ルート（グローバル変数、スタック上の変数など）からオブジェクトグラフを辿り、到達可能なオブジェクトを白から灰、そして黒へと色付けしていきます。

*   **ライトバリア（Write Barrier）**:
    GCが並行して動作している間、アプリケーションのゴルーチンもメモリを書き換える可能性があります。このとき、アプリケーションが黒いオブジェクトから白いオブジェクトへの参照を作成してしまうと、GCがその白いオブジェクトを到達不可能と誤判断し、誤って回収してしまう「見落とし」が発生する可能性があります。これを防ぐために導入されるのがライトバリアです。
    ライトバリアは、ポインタの書き込み操作が行われる際に自動的に挿入される小さなコードスニペットです。Goのライトバリアは、一般的に「Dijkstraのライトバリア」または「Hybrid Write Barrier」と呼ばれる方式を採用しており、ポインタの書き込み時に、書き込まれるオブジェクト（新しい参照先）がGCによってマークされるようにします。これにより、GCがオブジェクトグラフを正確に追跡し、メモリ安全性を保証します。

### GCのフェーズ

GoのGCは、主に以下のフェーズで構成されます。

*   **Mark Setup (`_GCmark`)**: GCサイクルの開始フェーズで、短いSTW（Stop-The-World）ポーズを伴います。このフェーズでライトバリアが有効になり、GCがマークを開始するための準備が行われます。
*   **Marking (Concurrent)**: アプリケーションと並行して実行されるマークフェーズです。GCはオブジェクトグラフを辿り、到達可能なオブジェクトをマークします。
*   **Mark Termination (`_GCmarktermination`)**: マークフェーズの終了フェーズで、再び短いSTWポーズを伴います。このフェーズでライトバリアが無効になり、GCのクリーンアップ作業が行われます。
*   **Sweep (Concurrent)**: マークされなかったオブジェクトのメモリを解放するフェーズで、アプリケーションと並行して実行されます。

### `systemstack`

`systemstack`はGoランタイムの内部関数で、現在のゴルーチンのスタックからシステムスタック（またはMスタック）に切り替えてコードを実行するために使用されます。システムスタックは、Goランタイムの低レベルな操作（例えば、スタックの拡張、GCの特定のフェーズ、スケジューラの操作など）のために予約された、固定サイズのスタックです。

通常のゴルーチンスタックは動的に伸縮しますが、`systemstack`上で実行されるコードはプリエンプト（横取り）されず、スタックの拡張も行われません。これは、GCのようなクリティカルな操作が中断されることなく、かつスタックの再帰的な成長によるオーバーフローを防ぐために重要です。

### `memmove`

`memmove`は、Goランタイム内部で使用される低レベルのメモリコピー関数です。C言語の`memmove`と同様に、ソースとデスティネーションのメモリ領域が重複している場合でも、正しくメモリをコピーできることが特徴です。Goの組み込み関数`copy`や、スライスの拡張・再割り当てなど、多くのメモリ操作の基盤として内部的に利用されています。ライトバリアが不要な場合や、ポインタではないデータの大量コピーを行う場合に効率的です。

## 技術的詳細

このコミットの技術的な核心は、ライトバリアの呼び出しを条件付きにすることで、そのスタックフットプリントを削減することにあります。

変更前は、`writebarrierptr`、`writebarrierfat`、`writebarriercopy`といったライトバリア関連の関数が、常に`writebarrierptr_nostore`を呼び出したり、ポインタの書き込みを個別に処理したりしていました。これらの関数は、GCのマークフェーズ中だけでなく、常にライトバリアのロジックを実行していました。

変更後、`needwb()`という新しい関数が導入されました。この関数は、現在のGCフェーズが`_GCmark`または`_GCmarktermination`である場合にのみ`true`を返します。つまり、GCが実際にオブジェクトをマークしている期間にのみライトバリアが必要であることを示します。

*   **`writebarrierptr`の変更**:
    `writebarrierptr`関数内で、`if needwb()`という条件が追加されました。これにより、GCのマークフェーズ中でない限り、`writebarrierptr_nostore`の呼び出しがスキップされるようになりました。これは、ライトバリアの最も基本的な操作であり、その呼び出し頻度を減らすことで、スタックフットプリントの削減に大きく貢献します。

*   **`writebarrierptr_nostore`の変更**:
    `writebarrierptr_nostore`関数にも`!needwb()`という条件が追加され、GCのマークフェーズ中でない場合は早期リターンするようになりました。これは二重のチェックのように見えますが、`writebarrierptr`を介さずに直接`writebarrierptr_nostore`が呼び出されるケース（例えば、非常に低レベルな起動時）にも対応するためのものです。

*   **`writebarrierfat`および`writebarriercopy`の変更**:
    これらの関数では、`if !needwb()`という条件が追加され、GCのマークフェーズ中でない場合は、ライトバリアのロジックを完全にスキップし、代わりに`memmove`を使用してメモリをコピーするようになりました。
    さらに重要な変更点として、ライトバリアが必要な場合（`needwb()`が`true`の場合）には、ライトバリアの実際の処理が`systemstack(func() { ... })`ブロック内で実行されるようになりました。これにより、ライトバリアの実行がゴルーチンスタックではなくシステムスタック上で行われるため、ゴルーチンスタックのフットプリントが削減されます。また、`systemstack`上で実行されることで、GCのクリティカルな処理が中断されることなく、より安定して実行されることが保証されます。

これらの変更により、GCのマークフェーズ中でない期間はライトバリアのオーバーヘッドが大幅に削減され、必要な場合でもスタックフットプリントがシステムスタックにオフロードされることで、全体的なパフォーマンスと安定性が向上します。特に、レース検出器のようなツールは、ライトバリアの頻繁な呼び出しによるスタックの深さやパフォーマンスへの影響を受けやすいため、この最適化はそれらのツールの再有効化に繋がったと考えられます。

## コアとなるコードの解説

### `src/run.bash`の変更

`src/run.bash`の変更は非常に小さいですが、重要です。
変更前は、レース検出器のテストが`XXX-DISABLED`という文字列を含む`case`文の条件によって無効化されていました。
変更後、この`XXX-DISABLED`が削除され、`$GOHOSTOS-$GOOS-$GOARCH-$CGO_ENABLED`という通常の環境変数に基づいてレース検出器のテストが実行されるようになりました。
これは、このコミットの目的の一つである「レース検出器を再び実行可能にする」という目標を直接的に反映した変更です。ライトバリアのスタックフットプリント削減によって、レース検出器が安定して動作する環境が整ったため、この無効化フラグが削除されたと考えられます。

### `src/runtime/mgc0.go`の変更

このファイルはGoランタイムのガベージコレクションに関するコードを含んでいます。変更の大部分は、ライトバリアの呼び出しを条件付きにし、スタックフットプリントを削減することに焦点を当てています。

1.  **`needwb()`関数の追加**:
    ```go
    func needwb() bool {
        return gcphase == _GCmark || gcphase == _GCmarktermination
    }
    ```
    この新しいヘルパー関数は、現在のGCフェーズが`_GCmark`（マーク開始）または`_GCmarktermination`（マーク終了）である場合にのみ`true`を返します。これは、ライトバリアが実際にオブジェクトをマークする必要がある期間を正確に特定するために使用されます。

2.  **`writebarrierptr`関数の変更**:
    ```go
    func writebarrierptr(dst *uintptr, src uintptr) {
        *dst = src
        if needwb() { // 追加された条件
            writebarrierptr_nostore(dst, src)
        }
    }
    ```
    `writebarrierptr`は、ポインタの書き込みを行う基本的なライトバリア関数です。変更前は常に`writebarrierptr_nostore`を呼び出していましたが、変更後は`needwb()`が`true`の場合にのみ呼び出すようになりました。これにより、GCのマークフェーズ中でない期間は、ライトバリアの処理が完全にスキップされ、不要なオーバーヘッドとスタック使用量が削減されます。

3.  **`writebarrierptr_nostore`関数の変更**:
    ```go
    func writebarrierptr_nostore(dst *uintptr, src uintptr) {
        if getg() == nil || !needwb() { // 変更された条件
            return
        }
        // ... 既存のライトバリアロジック ...
    }
    ```
    この関数は、ストアが既に適用された後にライトバリア処理を行うものです。変更前は、非常に低レベルな起動時（`getg() == nil`）にのみ早期リターンしていましたが、変更後は`!needwb()`（GCのマークフェーズ中でない場合）も早期リターンの条件に追加されました。これは、`writebarrierptr`を介さずに直接この関数が呼び出される可能性のあるシナリオ（例えば、ランタイム内部の特定のパス）においても、不要なライトバリア処理を避けるための防御的な変更です。

4.  **`writebarrierfat`関数の変更**:
    ```go
    func writebarrierfat(typ *_type, dst, src unsafe.Pointer) {

            memmove(dst, src, typ.size)

        }

        systemstack(func() { // 追加されたsystemstackブロック
    ```

    `writebarrierfat`は、構造体や配列のような「fat」なオブジェクトのポインタを含むフィールドをコピーする際に使用されるライトバリアです。
    *   **条件付き`memmove`**: `needwb()`が`false`の場合（GCのマークフェーズ中でない場合）、ライトバリアの複雑なロジックをスキップし、代わりに`memmove`を使用してメモリを直接コピーするようになりました。`memmove`はライトバリアのオーバーヘッドなしに効率的なメモリコピーを提供します。
    *   **`systemstack`への移行**: `needwb()`が`true`の場合（ライトバリアが必要な場合）、ライトバリアの実際の処理全体が`systemstack(func() { ... })`ブロック内に移動されました。これにより、このライトバリア処理がゴルーチンスタックではなく、固定サイズのシステムスタック上で実行されるようになります。これは、ライトバリアが頻繁に呼び出されることによるゴルーチンスタックの深さの増大を防ぎ、スタックオーバーフローのリスクを軽減し、GCの安定性を向上させます。

    `writebarriercopy`は、スライスのような連続したメモリ領域をコピーする際に使用されるライトバリアです。`writebarrierfat`と同様に、`needwb()`の条件に基づいて`memmove`による高速コピーに切り替えるか、または`systemstack`上でライトバリア処理を実行するようになりました。これにより、スライスのコピー操作におけるライトバリアのオーバーヘッドが削減され、特にGCのマークフェーズ外でのパフォーマンスが向上します。

これらの変更は、GoランタイムのGCにおけるライトバリアの効率を大幅に向上させ、不要なスタック使用量を削減し、全体的なパフォーマンスと安定性を改善することを目的としています。特に、`systemstack`の活用は、GCのようなクリティカルなランタイム処理が、アプリケーションのゴルーチンスタックの制約から解放され、より堅牢に実行されるための重要なアーキテクチャ上の改善と言えます。

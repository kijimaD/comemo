## コミット

```
[dev.garbage] runtime: allocate directly from GC mark bits

Instead of building a freelist from the mark bits generated
by the GC this CL allocates directly from the mark bits.

The approach moves the mark bits from the pointer/no pointer
heap structures into their own per span data structures. The
mark/allocation vectors consist of a single mark bit per
object. Two vectors are maintained, one for allocation and
one for the GC's mark phase. During the GC cycle's sweep
phase the interpretation of the vectors is swapped. The
mark vector becomes the allocation vector and the old
allocation vector is cleared and becomes the mark vector that
the next GC cycle will use.

Marked entries in the allocation vector indicate that the
object is not free. Each allocation vector maintains a boundary
between areas of the span already allocated from and areas
not yet allocated from. As objects are allocated this boundary
is moved until it reaches the end of the span. At this point
further allocations will be done from another span.

Since we no longer sweep a span inspecting each freed object
the responsibility for maintaining pointer/scalar bits in
the heapBitMap containing is now the responsibility of the
the routines doing the actual allocation.

This CL is functionally complete and ready for performance
tuning.
```

## 変更の背景

Goのガベージコレクション（GC）は、メモリ管理の重要な側面であり、アプリケーションのパフォーマンスに直接影響を与えます。従来のGoランタイムでは、GCのスイープフェーズが完了した後、解放されたメモリ領域を「フリーリスト」として構築し、その後のメモリ割り当て（アロケーション）はこのフリーリストから行われていました。このアプローチは、メモリの再利用を効率的に行うための一般的な手法ですが、いくつかの課題を抱えていました。

1.  **フリーリスト構築のオーバーヘッド:** スイープフェーズ中に解放されたオブジェクトをフリーリストに連結する作業自体が、一定のCPU時間とメモリ帯域を消費します。特に、大量のオブジェクトが解放される場合、このオーバーヘッドは無視できませんでした。
2.  **フリーリストの走査コスト:** 新しいオブジェクトを割り当てる際、適切なサイズの空き領域を見つけるためにフリーリストを走査する必要がありました。これもまた、アロケーションパスにレイテンシを追加する要因となります。
3.  **GCとアロケーションの複雑な相互作用:** フリーリストはGCのスイープフェーズによって更新され、アロケーションによって消費されるため、GCとアロケーションの間でフリーリストの状態を同期させるための複雑なロジックが必要でした。

このコミットの背景にあるのは、これらの課題を解決し、GCの効率とアロケーションのパフォーマンスを向上させることです。具体的には、GCがオブジェクトの生存状態をマークする際に使用する「マークビット」を、直接アロケーションに利用することで、フリーリストの構築と走査のステップを排除しようとしています。これにより、GCのスイープフェーズが軽量化され、アロケーションパスも簡素化されることが期待されます。

## 前提知識の解説

### Goのメモリ管理とGCの基本

Goランタイムは、プログラムが使用するメモリをヒープとスタックに分けて管理します。スタックは関数呼び出しやローカル変数に使用され、ヒープは`make`や`new`で動的に割り当てられるオブジェクトに使用されます。GoのGCは、ヒープ上の不要になったオブジェクト（どこからも参照されていないオブジェクト）を自動的に回収し、メモリを再利用する役割を担います。

GoのGCは「三色マーク＆スイープ」アルゴリズムをベースにしており、コンカレント（並行）に動作します。これは、GCがアプリケーションの実行と同時に動作し、アプリケーションの一時停止（STW: Stop The World）時間を最小限に抑えることを目指しています。

*   **マークフェーズ (Mark Phase):** GCは、ルート（グローバル変数、実行中のゴルーチンのスタックなど）から到達可能なすべてのオブジェクトを「マーク」します。三色アルゴリズムでは、オブジェクトは「白」（未訪問、潜在的なゴミ）、「灰」（訪問済みだが子を走査していない）、「黒」（訪問済みで子も走査済み、生存確定）のいずれかの色で表現されます。
*   **スイープフェーズ (Sweep Phase):** マークフェーズが完了した後、GCはヒープ全体を走査し、マークされていないオブジェクト（白のままのオブジェクト）を「ゴミ」と判断して回収します。回収されたメモリは、その後のアロケーションのために再利用可能になります。

### mspan

`mspan`はGoランタイムのメモリ管理における基本的な単位です。Goのヒープは、`mspan`と呼ばれる連続したメモリページのチャンクに分割されています。各`mspan`は、特定の「サイズクラス」に属し、そのサイズクラスに対応する固定サイズのオブジェクトのみを格納します。例えば、8バイトのオブジェクトを格納する`mspan`、16バイトのオブジェクトを格納する`mspan`などがあります。これにより、メモリの断片化を減らし、効率的な割り当てと回収を可能にしています。

### フリーリスト (Freelist)

従来のGoランタイムでは、`mspan`内に空きオブジェクトを管理するためにフリーリストが使用されていました。スイープフェーズでオブジェクトが解放されると、そのオブジェクトは`mspan`内のフリーリストに連結されます。新しいオブジェクトが割り当てられる際には、まず`mspan`のフリーリストから空きオブジェクトが取得されます。フリーリストが空の場合、新しい`mspan`がヒープから取得されるか、既存の`mspan`がスイープされてフリーリストが補充されます。

### マークビット (Mark Bits) とヒープビット (Heap Bits)

Goランタイムは、ヒープ上のオブジェクトに関するメタデータを管理するためにビットマップを使用します。

*   **`heapBits`:** オブジェクト内のどのワードがポインタであるか、どのワードがスカラー（非ポインタ）であるかを示す情報（ポインタマップ）を格納します。これはGCがオブジェクトの内部を走査する際に必要となります。
*   **`gcmarkBits`:** GCのマークフェーズ中に、特定のオブジェクトが「マークされた」（生存している）かどうかを示すために使用されます。各オブジェクトに対して1ビットが割り当てられ、オブジェクトがマークされるとこのビットがセットされます。

これらのビットマップは、メモリ効率を最大化するためにコンパクトな形式で格納されています。

### アロケーションベクトル (Allocation Vector) とマークベクトル (Mark Vector)

このコミットで導入される新しい概念です。`mspan`ごとに、オブジェクトの割り当て状態とGCのマーク状態を追跡するために、それぞれ独立したビットマップ（ベクトル）が導入されます。

*   **アロケーションベクトル (`allocBits`):** `mspan`内の各オブジェクトが現在割り当てられているか（使用中か）どうかを示します。
*   **マークベクトル (`gcmarkBits`):** GCのマークフェーズ中に、`mspan`内の各オブジェクトが生存しているとマークされたかどうかを示します。

これらのベクトルは、GCのスイープフェーズ中に役割を交換（スワップ）することで、GCとアロケーションの間の同期を簡素化し、効率を高めます。

### スイープフェーズ (Sweep Phase)

GCのスイープフェーズは、マークフェーズで生存が確認されなかったオブジェクトを回収する段階です。従来のシステムでは、スイープフェーズ中にヒープを走査し、マークされていないオブジェクトをフリーリストに連結していました。このコミットでは、スイープフェーズの役割が変更され、フリーリストの構築ではなく、`allocBits`と`gcmarkBits`の役割をスワップし、次のGCサイクルに備えて`gcmarkBits`をクリアする処理が中心となります。これにより、スイープフェーズ自体の処理が大幅に軽量化されます。

## 技術的詳細

このコミットの核心は、Goランタイムのメモリ割り当てとGCのスイープフェーズの連携方法を根本的に変更することにあります。従来のフリーリストベースのアロケーションを廃止し、GCのマークビットを直接アロケーションに利用する新しいメカニズムを導入しています。

### GCマークビットからの直接アロケーション

従来のシステムでは、GCのスイープフェーズが完了した後、解放されたオブジェクトは`mspan`内のフリーリストに連結され、その後のアロケーションはこのフリーリストから行われていました。このコミットでは、このフリーリストの概念を排除します。代わりに、GCがオブジェクトの生存状態を記録するために使用するマークビットを、そのままアロケーションの状態管理に利用します。

具体的には、`mspan`は`allocBits`と`gcmarkBits`という2つのビットマップを保持します。

*   `allocBits`: 現在のGCサイクルにおいて、どのオブジェクトが割り当て済みであるか（つまり、空きではないか）を示します。
*   `gcmarkBits`: 次のGCサイクルにおいて、どのオブジェクトがマークされるか（つまり、生存しているか）を記録するためにGCマークフェーズが使用します。

アロケーションは、`allocBits`を参照して空き領域を見つけ、割り当てると同時に`allocBits`の対応するビットをセットします。これにより、フリーリストの走査や連結といったオーバーヘッドがなくなります。

### mspanごとのデータ構造としてのマークビット

この変更により、マークビット（`allocBits`と`gcmarkBits`）は、従来のポインタ/非ポインタヒープ構造から独立した、`mspan`ごとのデータ構造として管理されるようになります。これにより、マークビットの管理がよりシンプルになり、GCとアロケーションのロジックが分離されやすくなります。

`mspan`構造体には、`markbits1`と`markbits2`という2つの`[8192]uint8`配列が追加され、これらが`allocBits`と`gcmarkBits`として交互に使用されます。

### 二つのベクトルの役割とスワップ

GCサイクルが進行するにつれて、`allocBits`と`gcmarkBits`の役割はスイープフェーズで交換されます。

1.  **GCマークフェーズ中:** `gcmarkBits`がGCによって生存オブジェクトをマークするために使用されます。`allocBits`は、この時点での割り当て済みオブジェクトの状態を反映しています。
2.  **GCスイープフェーズ開始時:** スイープフェーズが始まると、`allocBits`と`gcmarkBits`の役割がスワップされます。
    *   現在の`gcmarkBits`（マークフェーズで生存が確認されたオブジェクトを示す）が、次のアロケーションサイクルで使用される新しい`allocBits`になります。これにより、生存オブジェクトは引き続き「割り当て済み」として扱われます。
    *   古い`allocBits`はクリアされ、次のGCマークフェーズで使用される新しい`gcmarkBits`になります。

このスワップメカニズムにより、GCとアロケーションの間の同期が大幅に簡素化されます。スイープフェーズは、フリーリストを構築する代わりに、単にビットマップのポインタを交換し、古いビットマップをクリアするだけで済みます。

### アロケーションの境界管理

新しいアロケーション戦略では、各`mspan`は`freeindex`というフィールドを保持します。これは、`mspan`内で次に空きオブジェクトを探し始めるべきインデックスを示します。アロケーションは、`freeindex`から順に`allocBits`をチェックし、空き領域を見つけます。オブジェクトが割り当てられると、`freeindex`は次の位置に進みます。`freeindex`が`mspan`の末尾に達すると、その`mspan`は満杯と見なされ、次のアロケーションは別の`mspan`から行われます。

これにより、アロケーションは非常に高速な線形走査となり、フリーリストの複雑な管理が不要になります。

### ヒープビットマップの責任の変更

従来のスイープフェーズでは、解放されたオブジェクトのポインタ/スカラービットを`heapBitMap`に設定する責任がありました。しかし、新しいアプローチでは、スイープフェーズは個々の解放オブジェクトを検査しなくなります。その代わりに、`heapBitMap`内のポインタ/スカラービットの維持は、実際にオブジェクトを割り当てるルーチン（アロケーションルーチン）の責任となります。これにより、スイープフェーズの処理がさらに軽量化されます。

このコミットは、機能的には完成しており、今後はパフォーマンスチューニングが焦点となります。

## コアとなるコードの解説

### `mspan`構造体の変更 (`src/runtime/mheap.go`)

最も基本的な変更は、`mspan`構造体から`freelist`フィールドが削除されたことです。これは、フリーリストベースの割り当てメカニズムが完全に廃止されたことを意味します。代わりに、`allocBits`と`gcmarkBits`という2つのポインタが追加されています。これらは、`mspan`内に定義された`markbits1`と`markbits2`という2つの`[8192]uint8`配列を指します。これらの配列が、それぞれアロケーションとGCマークのためのビットマップとして機能します。

`mspan.init`関数では、新しい`mspan`が初期化される際に、`freeindex`が0に設定され、`allocBits`が`markbits1`を、`gcmarkBits`が`markbits2`を指すように設定されます。また、これらのビットマップはすべて0でクリアされます。

### `mcache.nextFree`関数の変更 (`src/runtime/malloc.go`)

`mcache.nextFree`は、`mcache`（各P（プロセッサ）にローカルなキャッシュ）から新しいオブジェクトを割り当てるための主要な関数です。この関数は、従来の`s.freelist`からオブジェクトを取得する代わりに、`s.freeindex`と`s.allocBits`を利用するように変更されました。

1.  `s.nextFreeIndex(s.freeindex)`を呼び出して、`s.allocBits`に基づいて次に利用可能な空きオブジェクトのインデックスを検索します。
2.  もし`freeIndex`が`s.nelems`（`mspan`内のオブジェクトの総数）に達している場合、その`mspan`は満杯であると判断され、`c.refill`を呼び出して新しい`mspan`を取得します。
3.  有効な`freeIndex`が見つかった場合、そのインデックスと`s.base()`（`mspan`の開始アドレス）からオブジェクトのアドレス`v`を計算します。
4.  `s.freeindex`をインクリメントし、`s.ref`（`mspan`内の参照されているオブジェクトの数）を増やします。

この変更により、アロケーションはビットマップの線形走査とインデックスの更新という非常に高速な操作に簡素化されます。

### `mbitmap.go`におけるマークビット操作の変更

`src/runtime/mbitmap.go`では、`mspan`のマークビットを操作するための新しいヘルパー関数が導入されています。

*   `s.markBitsForAddr(p uintptr) markBits`: 特定のアドレス`p`に対応する`gcmarkBits`内の`markBits`構造体を返します。
*   `s.markBitsForBase() markBits`: `mspan`のベースアドレスに対応する`gcmarkBits`内の`markBits`構造体を返します。
*   `markBits.advance()`: `markBits`を次のオブジェクトのビット位置に進めます。これはビットマップを効率的に走査するために使用されます。
*   `heapBitsSweep8BitPtrs`、`heapBitsSweepMap`、`markBits.nextFreed`などの新しい関数が追加され、`heapBitsSweepSpan`がこれらの関数を利用するように書き換えられています。これらの関数は、スイープフェーズ中に`gcmarkBits`と`allocBits`を効率的に走査し、解放されたオブジェクトを識別するために使用されます。

特に注目すべきは、`heapBits`構造体から`isMarked`、`setMarked`、`setMarkedNonAtomic`といったGCマーク関連のメソッドが削除され、`mspan`の`markBits`構造体にその責任が移管されたことです。これにより、GCマークのロジックが`heapBits`（ポインタマップ）から分離され、よりクリーンな設計になっています。

### `mgcsweep.go`におけるスイープフェーズの変更

`src/runtime/mgcsweep.go`の`s.sweep`関数は、新しいアロケーション戦略に合わせて大幅に書き換えられています。

1.  **フリーリスト関連ロジックの削除:** 従来の`s.freelist`を走査し、解放されたオブジェクトをマークするロジックが完全に削除されました。
2.  **`allocBits`と`gcmarkBits`のスワップ:** スイープフェーズの終わりに、`s.allocBits, s.gcmarkBits = s.gcmarkBits, s.allocBits`という行で、`allocBits`と`gcmarkBits`のポインタが交換されます。これにより、マークフェーズで生存が確認されたオブジェクトを示す`gcmarkBits`が、次のアロケーションサイクルで使用される`allocBits`となり、古い`allocBits`は次のGCマークフェーズで使用される`gcmarkBits`となります。
3.  **`gcmarkBits`のクリア:** `s.clearGCMarkBits()`が呼び出され、新しい`gcmarkBits`（以前の`allocBits`）がすべて0にクリアされます。これは、次のGCマークフェーズに備えて、すべてのオブジェクトが最初は「マークされていない」状態であることを保証するためです。
4.  **`s.freeindex`のリセット:** `s.freeindex = 0`が設定され、`mspan`の割り当てインデックスが先頭にリセットされます。

これらの変更により、スイープフェーズはフリーリストの構築という重い処理から解放され、ビットマップのポインタ交換とクリアという軽量な処理に特化するようになりました。

### その他の変更

*   `src/runtime/mcentral.go`では、`mcentral`が`mspan`を管理する際に、`freelist`の代わりに`s.freeindex`を利用するように変更されています。
*   `src/runtime/mgcmark.go`では、`greyobject`や`gcmarknewobject_m`といったGCマーク関連の関数が、`heapBits`の代わりに`mspan`の`markBits`を利用するように更新されています。

これらの変更は全体として、Goランタイムのメモリ管理をより効率的で、GCとアロケーションの間の相互作用をよりシンプルにすることを目指しています。

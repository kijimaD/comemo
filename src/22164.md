# [インデックス 22164] ファイルの概要

このコミットは、Go言語の`archive/zip`パッケージにおけるZIP64形式の「end of central directory record」のサイズ計算に関するバグ修正です。具体的には、ZIP64の仕様（セクション4.3.14.1）に従い、このレコードのサイズを正しく設定するように変更されました。以前の実装では、仕様で除外すべき12バイトを含んだままサイズを書き込んでいたため、ZIPファイルの互換性問題を引き起こす可能性がありました。この修正により、ZIP64ファイルの生成が仕様に準拠するようになります。

## 変更の背景

この変更は、ZIP64ファイルフォーマットの仕様に準拠するためのバグ修正です。ZIPファイルフォーマットは、PKWARE社によって策定された標準であり、その仕様書（APPNOTE.TXT）には、各レコードの構造と値に関する厳密な規定があります。

特に、ZIP64形式の「end of central directory record」（ZIP64中央ディレクトリ終了レコード）には、そのレコード自体のサイズを示すフィールドが存在します。PKWAREのZIPファイルフォーマット仕様書（セクション4.3.14.1）には、この「size of zip64 end of central directory record」フィールドに格納される値は、「残りのレコードのサイズであり、先頭の12バイトを含めるべきではない」と明記されています。

Go言語の`archive/zip`パッケージの以前の実装では、この仕様に反して、先頭の12バイト（シグネチャとサイズフィールド自体）を含んだフルサイズをこのフィールドに書き込んでいました。この誤ったサイズ情報が書き込まれると、他のZIPツールやライブラリが生成されたZIP64ファイルを正しく解釈できない可能性があり、互換性の問題やデータ破損として認識されるリスクがありました。

このコミットは、この仕様不適合を修正し、生成されるZIP64ファイルがより広範なツールやシステムとの互換性を保つことを目的としています。コミットメッセージにある`Fixes #9857`は、この問題がGoのイシュートラッカーで報告されたバグであることを示唆しています。

## 前提知識の解説

### ZIPファイルフォーマットとZIP64

ZIPファイルは、複数のファイルを圧縮して1つのアーカイブにまとめるための一般的なファイルフォーマットです。その構造は、主に以下の部分から構成されます。

1.  **ローカルファイルヘッダ (Local File Header)**: 各ファイルのエントリの先頭にあり、ファイル名、圧縮方法、圧縮・非圧縮サイズなどの情報を含みます。
2.  **ファイルデータ (File Data)**: 実際の圧縮されたファイルデータです。
3.  **データ記述子 (Data Descriptor)**: ローカルファイルヘッダに圧縮・非圧縮サイズが不明な場合に、ファイルデータの後に続くオプションのフィールドです。
4.  **中央ディレクトリ (Central Directory)**: ZIPファイル内のすべてのファイルエントリの情報を集約したものです。各エントリは「中央ディレクトリファイルヘッダ」として記録され、ファイル名、圧縮・非圧縮サイズ、ローカルファイルヘッダへのオフセットなど、ファイルに関する重要なメタデータを含みます。この中央ディレクトリは、ZIPファイル全体を効率的にスキャンし、特定のファイルを見つけるために使用されます。
5.  **中央ディレクトリ終了レコード (End of Central Directory Record - EOCD)**: ZIPファイルの末尾に位置し、中央ディレクトリの開始オフセット、中央ディレクトリのサイズ、エントリ数などの情報を含みます。これにより、ZIPファイルの構造を迅速に解析できます。

**ZIP64拡張**:
オリジナルのZIPフォーマットには、ファイルサイズやアーカイブ全体のサイズ、エントリ数、オフセットなどに2GBの制限がありました。この制限を超えるファイルを扱うために導入されたのが**ZIP64拡張**です。ZIP64では、これらのサイズやオフセットのフィールドが32ビットから64ビットに拡張され、より大きなファイルを扱えるようになりました。

ZIP64拡張が使用される場合、通常の中央ディレクトリ終了レコード（EOCD）に加えて、以下の2つの追加レコードが導入されます。

*   **ZIP64中央ディレクトリロケータ (ZIP64 End of Central Directory Locator)**: ZIP64中央ディレクトリ終了レコードのオフセットと、それが存在するディスクの番号を指し示します。
*   **ZIP64中央ディレクトリ終了レコード (ZIP64 End of Central Directory Record)**: ZIP64形式の中央ディレクトリに関する詳細情報（エントリ数、中央ディレクトリのサイズ、中央ディレクトリの開始オフセットなど）を64ビット値で格納します。このレコードは、通常のEOCDの前に配置されます。

### ZIP64中央ディレクトリ終了レコードの構造と「サイズ」フィールド

ZIP64中央ディレクトリ終了レコードの構造は、PKWAREの仕様書（APPNOTE.TXT）のセクション4.3.14に定義されています。このレコードの先頭には、以下のフィールドがあります。

*   **`zip64 end of central dir signature` (4バイト)**: レコードの識別子（`0x06064b50`）。
*   **`size of zip64 end of central directory record` (8バイト)**: このレコード自体のサイズを示すフィールド。

このコミットの核心は、この「`size of zip64 end of central directory record`」フィールドに書き込む値の解釈にあります。仕様書セクション4.3.14.1には、このフィールドの値は「残りのレコードのサイズであり、先頭の12バイト（シグネチャ4バイト + このサイズフィールド8バイト）を含まない」と明確に規定されています。つまり、このフィールドに書き込むべき値は、レコード全体のサイズから12を引いた値でなければなりません。

## 技術的詳細

このコミットの技術的な問題は、Go言語の`archive/zip`パッケージがZIP64中央ディレクトリ終了レコードを書き込む際に、そのレコードのサイズを示すフィールド（`size of zip64 end of central directory record`）に誤った値を設定していた点にあります。

具体的には、`src/archive/zip/writer.go`内の`Close()`メソッドで、ZIP64中央ディレクトリ終了レコードを構築する際に、`b.uint64(directory64EndLen)`というコードを使用していました。ここで`directory64EndLen`は、ZIP64中央ディレクトリ終了レコード全体の固定長（シグネチャ、サイズフィールド、バージョン情報、ディスク番号、エントリ数、中央ディレクトリサイズ、オフセットなど、すべてのフィールドを含んだ合計バイト数）を表す定数です。

しかし、前述のZIP64仕様（セクション4.3.14.1）によれば、このサイズフィールドに書き込むべき値は、レコード全体のサイズから先頭の12バイト（シグネチャの4バイトと、このサイズフィールド自体の8バイト）を除外した「残りのレコードのサイズ」でなければなりません。

したがって、正しい値は`directory64EndLen - 12`であるべきでした。以前の実装では、この12バイトのオフセットが考慮されていなかったため、生成されるZIP64ファイルは仕様に厳密には準拠していませんでした。

この修正は、`b.uint64(directory64EndLen)`を`b.uint64(directory64EndLen - 12)`に変更することで、このサイズフィールドに正しい値を書き込むようにします。これにより、Goの`archive/zip`パッケージが生成するZIP64ファイルが、他のZIPツールやライブラリとの互換性を高め、より堅牢になります。

また、この変更を検証するために、`src/archive/zip/zip_test.go`に新しいテストケース`testZip64DirectoryRecordLength`が追加されました。このテストは、生成されたZIP64ファイルのZIP64中央ディレクトリ終了レコードを読み込み、そのサイズフィールドが期待される値（`directory64EndLen - 12`）と一致するかどうかを確認します。これにより、将来的に同様の回帰バグが発生するのを防ぎます。

## コアとなるコードの解説

### `src/archive/zip/writer.go` の変更

このファイルの変更は非常にシンプルかつ直接的です。

*   **変更前**: `b.uint64(directory64EndLen)`
*   **変更後**: `b.uint64(directory64EndLen - 12) // length minus signature (uint32) and length fields (uint64)`

`b`は、ZIPファイルにバイトを書き込むためのヘルパーオブジェクト（おそらく`binary.Writer`のようなもの）です。`uint64`メソッドは、指定された`uint64`値をファイルに書き込みます。

`directory64EndLen`は、ZIP64中央ディレクトリ終了レコード全体のバイト長を示す定数です。このレコードの先頭12バイトは、以下の2つのフィールドで構成されます。
1.  `directory64EndSignature` (4バイト): レコードの識別子。
2.  `size of zip64 end of central directory record` (8バイト): このフィールド自体が、残りのレコードのサイズを格納します。

ZIP64の仕様では、この8バイトの`size`フィールドに書き込む値は、レコード全体のサイズから、上記の12バイト（シグネチャ4バイト + サイズフィールド8バイト）を引いた値でなければならないと規定されています。

したがって、`directory64EndLen - 12`とすることで、仕様に準拠した正しいサイズ値が書き込まれるようになります。コメント`// length minus signature (uint32) and length fields (uint64)`は、この減算の理由を明確に説明しています。

### `src/archive/zip/zip_test.go` の変更

このファイルでは、ZIP64のテストスイートに新しいテストケースが追加されました。

1.  **`TestZip64`関数の変更**:
    *   変更前は`testZip64(t, size)`を呼び出すだけでした。
    *   変更後は、`testZip64`が`*rleBuffer`を返すように変更され、その戻り値を使って新しく追加された`testZip64DirectoryRecordLength(buf, t)`関数が呼び出されています。これにより、生成されたZIPファイルのバッファを新しいテスト関数に渡せるようになりました。

2.  **`testZip64`関数の変更**:
    *   戻り値の型が`*rleBuffer`に変更され、最後に`return buf`が追加されました。これにより、テストで生成されたZIPファイルのバイトデータが呼び出し元に返されるようになります。

3.  **`testZip64DirectoryRecordLength`関数の追加**:
    *   この新しい関数は、`Issue 9857`（このコミットが修正するバグ）を具体的に検証するために作成されました。
    *   **目的**: 生成されたZIP64ファイルの中央ディレクトリ終了レコードの「サイズ」フィールドが、正しく`directory64EndLen - 12`になっていることを確認します。
    *   **処理**:
        *   まず、ZIPファイルの末尾からデータを読み込み、ZIP64中央ディレクトリ終了レコードのシグネチャを探します（`findSignatureInBlock`）。
        *   シグネチャが見つかったら、そのオフセットからZIP64中央ディレクトリ終了レコードの開始位置を特定します（`findDirectory64End`）。
        *   特定されたオフセットから、`directory64EndLen`バイト分のレコードデータを読み込みます。
        *   読み込んだデータから`readBuf`を使ってバイトリーダーを作成し、先頭の4バイト（シグネチャ）を読み飛ばします。
        *   次に、続く8バイト（サイズフィールド）を`b.uint64()`で読み取ります。
        *   最後に、読み取った`size`が期待値`directory64EndLen - 12`と一致するかどうかをアサートします。一致しない場合はテストが失敗します。

このテストの追加により、ZIP64中央ディレクトリ終了レコードのサイズ計算が正しく行われていることが自動的に検証されるようになり、将来的な回帰を防ぐための重要なセーフティネットが提供されます。

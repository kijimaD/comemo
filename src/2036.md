`gobuild` をGo言語で書き直す。

## 変更の背景

このコミットは、Go言語がまだ非常に初期の段階にあった2009年4月に行われました。当時のGo言語のツールチェインは、C言語で書かれたコンポーネントに大きく依存していました。`gobuild` は、Goプログラムやライブラリをビルドするための重要なツールでしたが、これもC言語で実装されていました。

この変更の主な背景には、Go言語プロジェクトの長期的な目標である「セルフホスティング」の推進があります。セルフホスティングとは、プログラミング言語のコンパイラやツールチェインが、その言語自身で書かれている状態を指します。これにより、以下のようなメリットが期待されます。

1.  **開発の効率化**: Go言語のツールをGo言語で書くことで、Go言語開発者は自身の言語の強みを活かしてツール開発を進めることができます。C言語とGo言語の間でコンテキストスイッチを行う必要がなくなります。
2.  **依存関係の削減**: 外部のCコンパイラやライブラリへの依存を減らし、Goツールチェイン全体のポータビリティとビルドの容易性を向上させます。
3.  **言語の成熟度**: 自身の言語で複雑なシステムツールを実装できることは、その言語の表現力、パフォーマンス、安定性を示す重要な指標となります。
4.  **ブートストラッププロセスの簡素化**: 将来的には、Go言語のコンパイラ自体もGo言語で書かれることになります（Go 1.5でのブートストラップ）。その前段階として、ビルドツールをGo化することは自然な流れでした。

このコミットは、Go言語がそのエコシステム全体をGo言語で統一していくという戦略の初期段階における具体的な実装の一つと言えます。

## 前提知識の解説

### `gobuild` (初期のGoビルドツール)

Go言語の初期において、`gobuild` はGoソースコードをコンパイルし、実行可能なバイナリやライブラリを生成するための主要なコマンドラインツールでした。C言語の `make` コマンドに似た役割を果たし、ソースファイルの依存関係を解決し、適切なコンパイラ（`6g`, `6c`, `6a` など、当時のGoコンパイラはターゲットアーキテクチャに応じて命名されていました）を呼び出してオブジェクトファイルを生成し、それらをリンクして最終成果物を作成する責任を負っていました。

### セルフホスティング (Self-hosting)

セルフホスティングとは、プログラミング言語のコンパイラやランタイム、あるいはその開発ツールが、その言語自身で書かれている状態を指します。例えば、Go言語のコンパイラがGo言語で書かれている場合、それはセルフホスティングされていると言えます。セルフホスティングは、言語の成熟度を示す重要な指標であり、開発者が自身の言語の能力を最大限に活用してツールを改善できるという利点があります。Go言語は、初期のC言語ベースのツールから段階的にGo言語自身でツールチェインを構築する方向へと進化しました。

### Go言語の初期のビルドプロセスとツール

Go言語の初期（2009年頃）は、現在の `go build` コマンドのような統合されたビルドシステムは存在せず、`gobuild` のような個別のツールや `make.bash` のようなシェルスクリプトがビルドプロセスを管理していました。コンパイラは `6g` (Goコンパイラ for amd64), `6c` (Cコンパイラ for amd64), `6a` (アセンブラ for amd64) のように、ターゲットアーキテクチャ（例: `6` は `amd64` を指す）とコンパイラの種類を示す文字を組み合わせた名前を持っていました。これらのツールは、Go言語のソースコードを機械語に変換し、ライブラリをアーカイブし、最終的な実行ファイルを生成するために連携していました。

### Makefile

`Makefile` は、ソフトウェアのビルドプロセスを自動化するためのファイルです。`make` ユーティリティによって解釈され、ソースコードのコンパイル、リンク、テストなどのタスクを定義します。このコミットでは、C言語版 `gobuild` の `Makefile` が変更され、Go言語版 `gobuild` のビルドプロセスを反映するように更新されています。また、Go言語版 `gobuild` 自身が `Makefile` を生成する機能を持つようになります。

このコミットの技術的詳細は、C言語で書かれた `gobuild` のロジックをGo言語に移植し、Go言語の特性（特にパッケージ管理、エラーハンドリング、標準ライブラリの利用）を活かして再実装した点にあります。

    *   `src/cmd/gobuild/main.go`: `gobuild` コマンドのエントリポイントです。`gobuild` パッケージの `Main()` 関数を呼び出します。

    *   `src/cmd/gobuild/util.go`: ビルドプロセスで共通して使用されるユーティリティ関数（例: コマンドの実行、ファイルパスの操作、環境変数の取得、エラーハンドリング）が含まれています。特に、Go言語の `exec` パッケージを利用して外部コマンド（コンパイラやアーカイバ）を実行する部分が実装されています。
3.  **ビルドスクリプトの更新**:
    *   `src/cmd/gobuild/Makefile`: `gobuild` 自身のビルド方法がC言語からGo言語に変更されたため、この `Makefile` も更新されました。Goコンパイラ (`6g`) とGoアーカイバ (`6ar`) を使用して `gobuild` をビルドする手順が記述されています。
    *   `src/cmd/make.bash` および `src/make.bash`: Goプロジェクト全体のビルドを管理するシェルスクリプトも更新され、`gobuild` がGo言語でビルドされるようになったことを反映しています。特に `src/make.bash` では、`cmd/gobuild` がビルド対象のモジュールリストに追加されています。

新しいGo言語版 `gobuild` は、ソースファイルをスキャンしてパッケージとインポートの依存関係を構築し、それらの依存関係に基づいてコンパイルとアーカイブのフェーズを決定します。これは、C言語版が手動で依存関係を管理していたり、より単純なルールベースで動作していたのに対し、より洗練されたアプローチです。特に、`text/template` を用いた `Makefile` 生成機能は、ビルドシステムの柔軟性と自動化を大きく向上させました。

## コアとなるコードの解説

### `gobuild.go` の `Build` メソッドのロジック

`gobuild.go` の `Build` メソッドは、Go言語版 `gobuild` の中核をなす部分です。これは、Goソースコードのコンパイルとリンクのプロセスを管理します。

1.  **初期アーカイブの作成**: まず、検出された各パッケージに対して空のアーカイブファイル（例: `pkgname.a`）を作成します。これは、後でコンパイルされたオブジェクトファイルを追加するための準備です。
2.  **段階的なコンパイル (Phased Compilation)**:
    *   `gobuild` は、ソースファイルを一度にすべてコンパイルするのではなく、依存関係が解決されたファイルを段階的にコンパイルしていきます。これは、循環依存を避けるため、また、コンパイル順序を適切に管理するために重要です。
    *   `pending` リストには、まだコンパイルされていないすべてのファイルが含まれます。
    *   各「フェーズ」において、`gobuild` は `pending` リスト内のファイルの中から、現在コンパイル可能なもの（つまり、そのファイルが依存するすべてのパッケージが既にアーカイブされているか、または同じフェーズでコンパイルされるもの）を特定します。
    *   特定されたファイルは、適切なGoコンパイラ (`6g`)、Cコンパイラ (`6c`)、またはアセンブラ (`6a`) を使用してコンパイルされます。
    *   コンパイルが成功したファイルは `success` リストに移動し、失敗したファイルは `fail` リストに移動します。
3.  **アーカイブの更新**:
    *   各フェーズの終わりに、`success` リストにあるファイルから生成されたオブジェクトファイルが、それぞれの所属するパッケージのアーカイブに追加されます。
    *   オブジェクトファイルはアーカイブに追加された後、一時ファイルとして削除されます。
4.  **デッドロック検出**: もしあるフェーズで一つもファイルがコンパイルできなかった場合（`len(success) == 0`）、それは依存関係の循環や解決不能な問題を示唆しており、`gobuild` は「stalemate」（手詰まり）としてエラーを報告し終了します。
5.  **最終処理**: すべてのファイルがコンパイルされ、アーカイブが更新されるまでこのプロセスが繰り返されます。

この段階的なアプローチは、複雑な依存関係を持つ大規模なGoプロジェクトを効率的かつ正確にビルドするために不可欠です。

### `makefile.go` のテンプレート生成

`makefile.go` は、Go言語の `text/template` パッケージを使用して、動的に `Makefile` を生成する機能を提供します。

`makefileTemplate` は、以下のような構造を持つ文字列です。

```go
var makefileTemplate =
	`# DO NOT EDIT.  Automatically generated by gobuild.\n` +
	`{Args|args} >Makefile\n` +
	`...\n` +
	`{.repeated section Phases}\n` +
	`O{Phase}=\\\\\\n` +
	`{.repeated section ArCmds}\n` +
	`{.repeated section Files}\n` +
	`\t{Name|basename}.$O\\\\\\n` +
	`{.end}\n` +
	`{.end}\n` +
	`\n` +
	`{.end}\n` +
	`...\n`
```

このテンプレートは、`gobuild` が `ScanFiles` および `Build` プロセスで収集した `Info` 構造体のデータ（例: `z.Phases`, `z.Packages`, `z.Files`）を埋め込むことで、具体的な `Makefile` の内容を生成します。

*   `{.repeated section Phases}`: ビルドの各フェーズを反復処理します。
*   `O{Phase}`: 各フェーズで生成されるオブジェクトファイルの名前を定義します。
*   `{.repeated section ArCmds}`: 各アーカイブコマンド（どのオブジェクトファイルをどのパッケージアーカイブに追加するか）を反復処理します。
*   `{Name|basename}.$O`: ファイル名から拡張子を除いた部分（`basename`）とオブジェクトファイルの拡張子（`$O`）を組み合わせて、オブジェクトファイル名を生成します。
*   `{Args|args}`: `gobuild` に渡された引数を `Makefile` のコメントとして出力します。

この機能により、`gobuild` はビルドのたびに最新の依存関係とビルド設定を反映した `Makefile` を生成でき、手動での `Makefile` 更新の手間を省き、ビルドの一貫性を保つことができます。

Go言語の初期（2009年頃）は、現在の `go build` コマンドのような統合されたビルドシステムは存在せず、`gobuild` のような個別のツールや `make.bash` のようなシェルスクリプトがビルドプロセスを管理していました。コンパイラは `6g` (Goコンパイラ for amd64), `6c` (Cコンパイラ for amd64), `6a` (アセンブラ for amd64) のように、ターゲットアーキテクチャ（例: `6` は `amd64` を指す）とコンパイラの種類を示す文字を組み合わせた名前を持っていました。これらのツールは、Go言語のソースコードを機械語に変換し、ライブラリをアーカイブし、最終的な実行ファイルを生成するために連携していました。

### Makefile

`Makefile` は、ソフトウェアのビルドプロセスを自動化するためのファイルです。`make` ユーティリティによって解釈され、ソースコードのコンパイル、リンク、テストなどのタスクを定義します。このコミットでは、C言語版 `gobuild` の `Makefile` が変更され、Go言語版 `gobuild` のビルドプロセスを反映するように更新されています。また、Go言語版 `gobuild` 自身が `Makefile` を生成する機能を持つようになります。

## コアとなるコードの解説

### `gobuild.go` の `Build` メソッドのロジック

`gobuild.go` の `Build` メソッドは、Go言語版 `gobuild` の中核をなす部分です。これは、Goソースコードのコンパイルとリンクのプロセスを管理します。

1.  **初期アーカイブの作成**: まず、検出された各パッケージに対して空のアーカイブファイル（例: `pkgname.a`）を作成します。これは、後でコンパイルされたオブジェクトファイルを追加するための準備です。
2.  **段階的なコンパイル (Phased Compilation)**:
    *   `gobuild` は、ソースファイルを一度にすべてコンパイルするのではなく、依存関係が解決されたファイルを段階的にコンパイルしていきます。これは、循環依存を避けるため、また、コンパイル順序を適切に管理するために重要です。
    *   `pending` リストには、まだコンパイルされていないすべてのファイルが含まれます。
    *   各「フェーズ」において、`gobuild` は `pending` リスト内のファイルの中から、現在コンパイル可能なもの（つまり、そのファイルが依存するすべてのパッケージが既にアーカイブされているか、または同じフェーズでコンパイルされるもの）を特定します。
    *   特定されたファイルは、適切なGoコンパイラ (`6g`)、Cコンパイラ (`6c`)、またはアセンブラ (`6a`) を使用してコンパイルされます。
    *   コンパイルが成功したファイルは `success` リストに移動し、失敗したファイルは `fail` リストに移動します。
3.  **アーカイブの更新**:
    *   各フェーズの終わりに、`success` リストにあるファイルから生成されたオブジェクトファイルが、それぞれの所属するパッケージのアーカイブに追加されます。
    *   オブジェクトファイルはアーカイブに追加された後、一時ファイルとして削除されます。
4.  **デッドロック検出**: もしあるフェーズで一つもファイルがコンパイルできなかった場合（`len(success) == 0`）、それは依存関係の循環や解決不能な問題を示唆しており、`gobuild` は「stalemate」（手詰まり）としてエラーを報告し終了します。
5.  **最終処理**: すべてのファイルがコンパイルされ、アーカイブが更新されるまでこのプロセスが繰り返されます。

この段階的なアプローチは、複雑な依存関係を持つ大規模なGoプロジェクトを効率的かつ正確にビルドするために不可欠です。

### `makefile.go` のテンプレート生成

`makefile.go` は、Go言語の `text/template` パッケージを使用して、動的に `Makefile` を生成する機能を提供します。

`makefileTemplate` は、以下のような構造を持つ文字列です。

```go
var makefileTemplate =
	`# DO NOT EDIT.  Automatically generated by gobuild.\n` +
	`{Args|args} >Makefile\n` +
	`...\n` +
	`{.repeated section Phases}\n` +
	`O{Phase}=\\\\\\n` +
	`{.repeated section ArCmds}\n` +
	`{.repeated section Files}\n` +
	`\t{Name|basename}.$O\\\\\\n` +
	`{.end}\n` +
	`{.end}\n` +
	`\n` +
	`{.end}\n` +
	`...\n`
```

このテンプレートは、`gobuild` が `ScanFiles` および `Build` プロセスで収集した `Info` 構造体のデータ（例: `z.Phases`, `z.Packages`, `z.Files`）を埋め込むことで、具体的な `Makefile` の内容を生成します。

*   `{.repeated section Phases}`: ビルドの各フェーズを反復処理します。
*   `O{Phase}`: 各フェーズで生成されるオブジェクトファイルの名前を定義します。
*   `{.repeated section ArCmds}`: 各アーカイブコマンド（どのオブジェクトファイルをどのパッケージアーカイブに追加するか）を反復処理します。
*   `{Name|basename}.$O`: ファイル名から拡張子を除いた部分（`basename`）とオブジェクトファイルの拡張子（`$O`）を組み合わせて、オブジェクトファイル名を生成します。
*   `{Args|args}`: `gobuild` に渡された引数を `Makefile` のコメントとして出力します。

この機能により、`gobuild` はビルドのたびに最新の依存関係とビルド設定を反映した `Makefile` を生成でき、手動での `Makefile` 更新の手間を省き、ビルドの一貫性を保つことができます。

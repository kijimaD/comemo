# [インデックス 21538] ファイルの概要

このコミットは、Go言語の`syscall`パッケージ内のLinux ARMアーキテクチャ向けアセンブリコードにおける`seek`システムコールラッパーの引数サイズ宣言の不一致を修正するものです。具体的には、`go vet`ツールによって検出された、アセンブリ関数`·seek`のスタックフレームにおける引数と戻り値の合計サイズが、期待される値と異なっていた問題に対処しています。

## 変更の背景

この変更は、Goの静的解析ツールである`go vet`によって報告された警告に対応するために行われました。`go vet`は、`src/syscall/asm_linux_arm.s`ファイル内の`seek`システムコールをラップするアセンブリ関数`·seek`の定義において、引数と戻り値のために確保されているスタック上のサイズ（32バイト）が、GoのABI（Application Binary Interface）が期待するサイズ（28バイト）と一致しないことを指摘しました。

このような不一致は、潜在的なスタック破損、引数の誤った解釈、または未定義の動作につながる可能性があるため、修正が必要です。`go vet`は、Goプログラムの信頼性と正確性を向上させるために、このような疑わしい構造を検出するように設計されています。

## 前提知識の解説

### Go Vet

`go vet`は、Go言語のソースコードを静的に解析し、潜在的なバグや疑わしい構造を報告するツールです。例えば、フォーマット文字列の誤用、ロックの誤った使用、そして今回のようにアセンブリコードにおける引数サイズの不一致などを検出します。開発者がコードの品質を維持し、一般的な落とし穴を避けるのに役立ちます。

### システムコール (syscall)

システムコールは、ユーザー空間で実行されるプログラムが、オペレーティングシステム（OS）のカーネルが提供するサービスを要求するためのメカニズムです。ファイルI/O、メモリ管理、プロセス制御など、低レベルの操作を実行するために使用されます。Go言語の`syscall`パッケージは、これらのシステムコールをGoプログラムから呼び出すためのインターフェースを提供します。

### アセンブリ言語 (ARM)

アセンブリ言語は、特定のCPUアーキテクチャ（この場合はARM）の命令セットに直接対応する低レベルのプログラミング言語です。Goのランタイムや、パフォーマンスが非常に重要であったり、ハードウェアに直接アクセスする必要がある一部の低レベル関数は、アセンブリ言語で実装されています。Goのアセンブリは、Plan 9アセンブラの構文に基づいています。

### Goアセンブリにおける `TEXT` ディレクティブ

Goのアセンブリ言語では、`TEXT`ディレクティブは関数を定義するために使用されます。その一般的な形式は次のとおりです。

`TEXT symbol(SB), flags, $framesize-argsize`

*   `symbol(SB)`: 関数のシンボル名。`SB`は静的ベースポインタで、グローバルシンボルを参照します。
*   `flags`: 関数の特性を示すフラグ（例: `NOSPLIT`はスタックを分割しないことを示します）。
*   `$framesize-argsize`: スタックフレームのサイズと引数/戻り値のサイズの指定です。
    *   `framesize`: 関数内のローカル変数に使用されるスタックフレームのサイズ。
    *   `argsize`: 関数に渡される引数と、関数から返される戻り値のためにスタック上で確保される合計サイズ。このサイズは、GoのABIに従って決定されます。

### `llseek` システムコール

`llseek`はLinuxカーネルが提供するシステムコールの一つで、ファイルの読み書きオフセットを再配置するために使用されます。特に、32ビットシステム上で64ビットのファイルオフセットを扱うために設計されています。そのシグネチャは通常以下のようになります。

`long long llseek(int fd, long hi, long lo, long long *res, int whence);`

*   `fd`: ファイルディスクリプタ。
*   `hi`, `lo`: 64ビットオフセットの上位32ビットと下位32ビット。
*   `res`: 結果の64ビットオフセットが書き込まれるポインタ。
*   `whence`: オフセットの基準（例: `SEEK_SET`, `SEEK_CUR`, `SEEK_END`）。

Goの`syscall.Seek`関数は、この`llseek`システムコールをラップし、Goの`int64`型を`llseek`の`hi`と`lo`に分割して渡す役割を担います。

## 技術的詳細

このコミットの核心は、Goの`syscall.Seek`関数がARM Linux上でどのように実装されているか、そして`go vet`がそのABIの一貫性をどのようにチェックしているかにあります。

Goの`syscall.Seek`関数のGo言語でのシグネチャは通常以下のようになります。
`func Seek(fd int, offset int64, whence int) (newoffset int64, err error)`

このGo関数がアセンブリで実装される際、`TEXT`ディレクティブの`argsize`は、GoのABIに従って、入力引数と出力戻り値の合計サイズを反映する必要があります。

*   **入力引数**:
    *   `fd int`: 4バイト
    *   `offset int64`: 8バイト（32ビットARMでは通常、2つの32ビットレジスタまたはスタック上の2つの32ビットスロットとして扱われます）
    *   `whence int`: 4バイト
    *   合計: 4 + 8 + 4 = 16バイト

*   **出力戻り値**:
    *   `newoffset int64`: 8バイト
    *   `err error`: 8バイト（Goのインターフェースは通常、型情報とデータポインタの2つのワードで構成され、32ビットシステムでは合計8バイト）
    *   合計: 8 + 8 = 16バイト

したがって、一般的なGo関数のABIに従えば、`argsize`は入力16バイト + 出力16バイト = 32バイトとなるはずです。これは、変更前の`TEXT ·seek(SB),NOSPLIT,$0-32`と一致します。

しかし、`go vet`は`asm_linux_arm.s:110: [arm] seek: wrong argument size 32; expected $...-28`という警告を発しました。これは、`go vet`が`syscall`パッケージ内の特定の関数、特にARMアーキテクチャにおける`seek`のようなシステムコールラッパーに対して、異なるABIの期待値を持っていることを示唆しています。

この「期待される28バイト」という値は、`error`インターフェースの戻り値の扱いに関する特定の最適化やABIの慣習に起因している可能性が高いです。例えば、システムコールが成功した場合に`error`が`nil`であると保証される場合、`error`インターフェースの片方のワード（例えばデータポインタ）がスタック上で明示的に渡されない、あるいは別の方法で処理されることで、スタック上のサイズが4バイト削減されるといったケースが考えられます。結果として、`argsize`が32バイトから28バイトに減少します（32 - 4 = 28）。

このコミットは、この`go vet`の指摘に従い、アセンブリコードの`TEXT`ディレクティブにおける`argsize`を`32`から`28`に修正することで、Goのツールチェインが期待するABIに合致させ、警告を解消し、コードの正確性を保証しています。

## コアとなるコードの変更箇所

変更は`src/syscall/asm_linux_arm.s`ファイルの一箇所のみです。

```diff
--- a/src/syscall/asm_linux_arm.s
+++ b/src/syscall/asm_linux_arm.s
@@ -107,7 +107,7 @@ ok2:
 // taking the address of the return value newoffset.
 // Underlying system call is
 //	llseek(int fd, int offhi, int offlo, int64 *result, int whence)
-TEXT ·seek(SB),NOSPLIT,$0-32
+TEXT ·seek(SB),NOSPLIT,$0-28
 	BL	runtime·entersyscall(SB)
 	MOVW	$SYS__LLSEEK, R7	// syscall entry
 	MOVW	4(SP), R0	// fd
```

## コアとなるコードの解説

変更された行は`TEXT ·seek(SB),NOSPLIT,$0-32`から`TEXT ·seek(SB),NOSPLIT,$0-28`です。

*   `TEXT ·seek(SB)`: `seek`という名前の関数を定義しています。`SB`は静的ベースポインタで、この関数がグローバルシンボルであることを示します。
*   `NOSPLIT`: この関数がスタックを分割しないことを示すフラグです。これは、関数が他のGo関数を呼び出さないか、または非常に短い関数であることを意味します。
*   `$0-32` (変更前): ローカル変数に0バイト、引数と戻り値に32バイトのスタック領域を確保することを宣言していました。
*   `$0-28` (変更後): ローカル変数に0バイト、引数と戻り値に28バイトのスタック領域を確保することを宣言しています。

この変更は、`go vet`が指摘したABIの不一致を修正するものです。`go vet`は、Goの`syscall.Seek`関数のシグネチャとARMアーキテクチャの特定のABI規則に基づいて、このアセンブリ関数がスタック上で28バイトの引数/戻り値領域を使用することを期待していました。この修正により、アセンブリコードの宣言がGoツールチェインの期待と一致し、潜在的なランタイムエラーや未定義の動作が回避されます。

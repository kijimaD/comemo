# [インデックス 21623] ファイルの概要

このコミットは、Go言語のツールチェインにおけるアセンブラのC言語実装からGo言語実装への移行プロセスの一環として、新しいGo言語製アセンブラの正確性を検証するためのビルド時テストメカニズムを導入するものです。具体的には、アセンブリファイルを処理する際に、既存のC言語製アセンブラ（例: `6a`）と新しいGo言語製アセンブラ（例: `new6a`）の両方を並行して実行し、両者が生成する出力ファイルが完全に一致するかどうかを検証します。これにより、新しいアセンブラが古いアセンブラの正確な変換であることを保証し、移行期間中の品質を維持します。

## 変更の背景

このコミットの背景には、Go言語のツールチェイン、特にアセンブラをC言語からGo言語自身で書き直すという、Goプロジェクトの大きな方針転換があります。Go言語の初期のツールチェイン（コンパイラ、アセンブラ、リンカなど）は、Ken ThompsonとRob Pikeが開発したPlan 9オペレーティングシステムのツールチェインをベースにしており、その多くがC言語で書かれていました。

しかし、Go言語が成熟するにつれて、ツールチェイン自体をGo言語で記述することにはいくつかのメリットがあると考えられました。
1.  **自己ホスティングの実現**: ツールチェインがGo言語で書かれていれば、Go言語のコンパイラを使ってGo言語のコンパイラをビルドできる、いわゆる「自己ホスティング」が可能になります。これにより、Go言語のビルドシステムがよりシンプルになり、Cコンパイラへの依存がなくなります。
2.  **開発の効率化**: Go言語はC言語に比べて、並行処理のサポートやメモリ安全性の向上など、現代的なプログラミングパラダイムに適しています。ツールチェインをGoで書くことで、開発者がより効率的にツールチェインの改善や新機能の追加を行えるようになります。
3.  **移植性の向上**: C言語のコードは、特定のプラットフォームやコンパイラに依存する場合があります。Go言語でツールチェインを書き直すことで、より多くのプラットフォームへの移植が容易になります。

このコミットが行われた2015年頃は、Go 1.3のリリース（2014年）でツールチェインのGo言語化が大きく進められた時期と重なります。特に、コンパイラのフロントエンドがGo言語で書き直され、アセンブラやリンカも順次Go言語化が進められていました。

この移行期間中、新しいGo言語製アセンブラが既存のC言語製アセンブラと全く同じ出力を生成することを保証することが非常に重要でした。もし出力が異なれば、Goプログラムの動作に予期せぬ影響を与える可能性があるためです。このコミットは、その正確性をビルド時に自動的に検証するためのメカニズムを導入することで、移行プロセスを安全に進めることを目的としています。コミットメッセージにある「Once the C conversion is done, we'll throw away the C code and this checking.」という記述は、この検証メカニズムが一時的なものであることを明確に示しています。

## 前提知識の解説

### Goツールチェインと`cmd/go`

Go言語のプログラムをビルド、テスト、実行するためのツール群を「Goツールチェイン」と呼びます。これには、コンパイラ（`go tool compile`）、アセンブラ（`go tool asm`）、リンカ（`go tool link`）などが含まれます。
`cmd/go`は、これらのツールチェインの各コンポーネントを統合し、ユーザーが`go build`や`go run`といったコマンドを通じてGoプログラムを簡単に扱えるようにするコマンドラインツールです。`cmd/go`は、内部で必要に応じて適切なコンパイラやアセンブラを呼び出します。

### Goのアセンブラ（`6a`, `8a`, `5a`など）と`new6a`

Go言語は、特定のパフォーマンスが要求される部分や、OSとのインターフェース部分などでアセンブリ言語を使用します。Goのアセンブリ言語は、一般的なx86アセンブリとは異なり、Plan 9アセンブリの記法に基づいています。

歴史的に、GoのアセンブラはターゲットアーキテクチャごとにC言語で実装されていました。例えば、x86-64アーキテクチャ向けには`6a`（`a`はassemblerの略、`6`はx86-64のコードネーム）、ARM向けには`5a`、x86-32向けには`8a`といった名前のアセンブラが存在しました。

「新しいアセンブラ」（`new6a`など）とは、これらのC言語製アセンブラの機能をGo言語で再実装したものです。このコミットの時点では、まだC言語製アセンブラとGo言語製アセンブラが共存しており、Go言語製アセンブラが`new`プレフィックス付きで呼ばれていました。

### ビルド時テストとランタイムテスト

*   **ビルド時テスト (Build-time test)**: ソフトウェアがビルドされる過程で行われるテストです。コンパイルエラーのチェック、リンティング、静的解析、そしてこのコミットのように、生成されるバイナリや中間ファイルの正確性を検証するなどが含まれます。ビルドが成功すれば、ある程度の品質が保証されます。
*   **ランタイムテスト (Run-time test)**: ソフトウェアが実行される環境で行われるテストです。ユニットテスト、統合テスト、システムテスト、パフォーマンステストなどがこれに該当します。実際にプログラムを動かして、期待通りの動作をするか、パフォーマンス要件を満たすかなどを確認します。

このコミットでは、アセンブラの出力が正しいことを「ビルド時」に検証することで、アセンブラ自体の「ランタイムテスト」を不要にしています。なぜなら、アセンブラが生成するバイト列が既存の正確なアセンブラと完全に一致していれば、そのアセンブラが正しく機能していると判断できるためです。

## 技術的詳細

このコミットの核となる技術的詳細は、`cmd/go`がアセンブリファイルを処理する際に、既存のC言語製アセンブラと新しいGo言語製アセンブラの両方を呼び出し、その出力を比較するメカニズムにあります。

1.  **`verifyAsm`定数**:
    `src/cmd/go/build.go`に`const verifyAsm = true`という定数が導入されています。この定数が`true`である間は、アセンブラの出力検証が有効になります。これは、移行期間中のみ有効にするためのフラグであり、Go言語製アセンブラが完全に安定し、C言語製アセンブラが削除された後には`false`に設定されるか、関連コードと共に削除されることが意図されています。

2.  **`asm`関数の変更**:
    `gcToolchain`構造体の`asm`関数は、アセンブリファイルをアセンブルする役割を担っています。この関数が変更され、以下のロジックが追加されました。
    *   まず、通常の（既存のC言語製）アセンブラ（例: `6a`）を呼び出し、指定された出力ファイル（`ofile`）に結果を書き込みます。
    *   `verifyAsm`が`true`の場合、新しいGo言語製アセンブラ（例: `new6a`）を呼び出します。この際、出力ファイル名は元のファイル名に`.new`というサフィックスを追加したもの（例: `ofile + ".new"`）になります。これにより、元の出力ファイルを上書きすることなく、新しいアセンブラの出力を独立して保存します。
    *   両方のアセンブラの実行が成功した後、`ioutil.ReadFile`を使って両方の出力ファイルの内容をバイト列として読み込みます。
    *   `bytes.Equal`関数を使用して、これら二つのバイト列が完全に一致するかどうかを比較します。
    *   もしバイト列が一致しない場合、`fmt.Errorf`を使ってエラーを生成し、ビルドプロセスを停止させます。このエラーメッセージには、どのコマンドが異なる出力を生成したかを示す情報が含まれます。

3.  **出力のバイト比較**:
    アセンブラの出力は、最終的に機械語のバイト列です。このバイト列が完全に一致するということは、両方のアセンブラが全く同じ機械語を生成していることを意味します。これにより、アセンブラの機能的な正確性を、実行時ではなくビルド時に厳密に検証することが可能になります。

4.  **一時的なメカニズム**:
    この検証メカニズムは、Go言語製アセンブラがC言語製アセンブラと同等の品質と正確性を持つことを確認するための一時的なものです。コミットメッセージにもあるように、C言語製アセンブラのコードが完全に削除された後には、この検証コードも不要となり削除される予定でした。これは、Goプロジェクトが段階的に、かつ安全にツールチェインのGo言語化を進めていたことを示しています。

## コアとなるコードの解説

### `src/cmd/go/build.go`の変更

1.  **`verifyAsm`定数の追加**:
    ```go
    const verifyAsm = true
    ```
    この行は、アセンブラの出力検証を有効にするためのブール定数を定義しています。`true`に設定されている間は、後述の検証ロジックが実行されます。

2.  **`asm`関数の変更**:
    `asm`関数は、アセンブリソースファイル（`.s`ファイル）をアセンブルしてオブジェクトファイル（`.o`ファイル）を生成する役割を担っています。

    *   **既存アセンブラの実行**:
        ```go
        args := []interface{}{tool(archChar + "a"), "-o", ofile, "-trimpath", b.work, "-I", obj, "-I", inc, "-D", "GOOS_" + goos, "-D", "GOARCH_" + goarch, sfile}
        if err := b.run(p.Dir, p.ImportPath, nil, args...); err != nil {
            return err
        }
        ```
        まず、`tool(archChar + "a")`（例: `6a`）を使って既存のC言語製アセンブラを実行します。`b.run`は、指定された引数で外部コマンドを実行するヘルパー関数です。エラーが発生した場合は、すぐにそのエラーを返します。

    *   **`verifyAsm`による条件分岐**:
        ```go
        if verifyAsm {
            // ... 検証ロジック ...
        }
        return nil
        ```
        `verifyAsm`が`true`の場合にのみ、以下の検証ロジックが実行されます。検証が成功すれば`nil`（エラーなし）を返します。

    *   **新しいアセンブラの実行**:
        ```go
        newArgs := make([]interface{}, len(args))
        copy(newArgs, args)
        newArgs[0] = tool("new" + archChar + "a")
        newArgs[2] = ofile + ".new" // x.6 becomes x.6.new
        if err := b.run(p.Dir, p.ImportPath, nil, newArgs...); err != nil {
            return err
        }
        ```
        `args`スライスをコピーして`newArgs`を作成し、新しいアセンブラ（`new` + `archChar` + `a`、例: `new6a`）を呼び出すようにコマンドを変更します。重要なのは、出力ファイル名を`ofile + ".new"`とすることで、既存アセンブラの出力と競合しないようにしている点です。ここでも、実行中にエラーが発生すればすぐに返します。

    *   **出力ファイルの読み込みと比較**:
        ```go
        data1, err := ioutil.ReadFile(ofile)
        if err != nil {
            return err
        }
        data2, err := ioutil.ReadFile(ofile + ".new")
        if err != nil {
            return err
        }
        if !bytes.Equal(data1, data2) {
            return fmt.Errorf("%sa and n%sa produced different output files:\\n%s\\n%s", archChar, archChar, strings.Join(stringList(args...), " "), strings.Join(stringList(newArgs...), " "))
        }
        ```
        `ioutil.ReadFile`を使用して、既存アセンブラの出力ファイル（`ofile`）と新しいアセンブラの出力ファイル（`ofile + ".new"`）の内容をそれぞれバイトスライスとして読み込みます。
        `bytes.Equal(data1, data2)`は、二つのバイトスライスが完全に同じ内容であるかを比較します。もし一致しない場合（`!bytes.Equal`）、`fmt.Errorf`を使ってエラーメッセージを生成し、ビルドを失敗させます。エラーメッセージには、どのコマンドが異なる出力を生成したかを示す情報が含まれており、デバッグに役立ちます。

### `src/cmd/go/main.go`の変更

```go
// 変更前
// panic("stringList: invalid argument")
// 変更後
panic("stringList: invalid argument of type " + fmt.Sprintf("%T", arg))
```
この変更は、`stringList`関数が予期しない型の引数を受け取った場合に発生するパニックメッセージを改善するものです。変更前は汎用的なメッセージでしたが、変更後は`fmt.Sprintf("%T", arg)`を使って引数の具体的な型をメッセージに含めることで、デバッグ時の情報量を増やしています。これは、アセンブラ検証のロジックとは直接関係ありませんが、このコミットで同時に行われた小さな改善です。

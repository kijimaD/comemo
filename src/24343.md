# [インデックス 24343] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）におけるクロージャの引数処理に関するバグ修正です。具体的には、キャプチャされた変数をクロージャのパラメータリストに渡す際、以前は「追加（append）」していましたが、可変長引数（`...` param）を持つクロージャの場合に問題が発生していました。このコミットでは、キャプチャされた変数をパラメータリストの「先頭に追加（prepend）」するように変更することで、この問題を解決しています。

## 変更の背景

Go言語のコンパイラにおいて、クロージャが外部スコープの変数を「キャプチャ」する際の内部的な処理に問題がありました。特に、キャプチャされた変数をクロージャの呼び出し時に引数として渡す際、コンパイラはこれらの変数をクロージャの通常の引数リストの「末尾に追加」する方式を採用していました。

この方式は、通常の固定引数を持つクロージャでは問題なく機能していましたが、クロージャが可変長引数（`...` param、例: `func(names ...string)`）を持つ場合に予期せぬ挙動を引き起こしました。可変長引数は、Goの関数呼び出し規約において特殊な扱いを受けます。具体的には、可変長引数はスライスとして関数内部に渡されます。

既存の実装では、キャプチャされた変数が可変長引数のスライスの「後」に追加されるため、コンパイラが引数の型チェックやスタックフレームのレイアウトを正しく処理できなくなり、`mkdotargslice: typecheck failed` のようなコンパイルエラーや、実行時の不正なメモリアクセスにつながる可能性がありました。

この問題は [Issue #11075](https://github.com/golang/go/issues/11075) として報告され、このコミットはその解決を目的としています。

## 前提知識の解説

### 1. Go言語のクロージャ (Closures)

Go言語におけるクロージャは、関数リテラルが自身の宣言された環境（外部スコープ）の変数を参照できる機能です。クロージャは、その外部関数が実行を終了した後でも、キャプチャした変数にアクセスし、変更することができます。

例:
```go
func makeGreeter(greeting string) func(name string) string {
    return func(name string) string {
        return greeting + ", " + name + "!"
    }
}

func main() {
    hello := makeGreeter("Hello")
    fmt.Println(hello("Alice")) // "Hello, Alice!"
}
```
この例では、内部関数 `func(name string) string` が外部関数の `greeting` 変数を「キャプチャ」しています。

### 2. キャプチャされた変数 (Captured Variables) の内部処理

Goコンパイラは、クロージャがキャプチャする変数を、クロージャの実体（関数ポインタと環境ポインタのペア）の一部として扱います。具体的には、キャプチャされた変数は、クロージャが呼び出される際に、そのクロージャの「隠れた引数」として渡されるか、あるいはクロージャの環境（コンテキスト）の一部としてアクセスされます。このコミットの文脈では、コンパイラがクロージャを変換する際に、キャプチャされた変数を明示的な引数として扱うように変更していました。

### 3. 可変長引数 (Variadic Parameters)

Goの関数は、最後のパラメータに `...` を付けることで、任意の数の引数を受け取ることができます。これを可変長引数と呼びます。

例:
```go
func sum(nums ...int) int {
    total := 0
    for _, num := range nums {
        total += num
    }
    return total
}

func main() {
    fmt.Println(sum(1, 2, 3)) // 6
    fmt.Println(sum(10, 20))  // 30
}
```
関数内部では、`nums` は `[]int` 型のスライスとして扱われます。

### 4. コンパイラの引数処理とスタックフレーム

Goコンパイラは、関数呼び出しの際に、引数をスタックフレーム上に配置します。引数の順序と型は、関数シグネチャに基づいて厳密に決定されます。可変長引数の場合、個々の引数はスライスとしてまとめられ、そのスライスヘッダ（ポインタ、長さ、容量）がスタックに配置されます。

### 5. `cmd/compile/internal/gc` パッケージ

`cmd/compile/internal/gc` は、Goコンパイラの主要な部分であり、Goソースコードの構文解析、型チェック、中間表現への変換、最適化、そして最終的な機械語コード生成を担当します。
*   `closure.go`: クロージャの変換（`transformclosure` 関数など）に関するロジックが含まれています。キャプチャされた変数をどのように処理し、クロージャの関数シグネチャをどのように変更するかが定義されています。
*   `walk.go`: 抽象構文木（AST）を走査し、高レベルなGoの構文をコンパイラのバックエンドが処理しやすい中間表現に変換する「ウォーク」処理が含まれています。関数呼び出しの変換などもここで行われます。

## 技術的詳細

このコミットの核心は、Goコンパイラがクロージャのキャプチャされた変数を、そのクロージャの呼び出し時の引数リストにどのように組み込むか、という点にあります。

以前の実装では、`transformclosure` 関数内で、キャプチャされた変数をクロージャの「入力引数リストの末尾に**追加**」していました。これは、クロージャの型を書き換え、キャプチャされた変数を通常の引数のように見せかけるための一般的な手法です。

しかし、クロージャが可変長引数（`...`）を持つ場合、問題が発生しました。Goの関数呼び出し規約では、可変長引数は内部的にスライスとして扱われます。もしキャプチャされた変数がこの可変長引数スライスの「後」に追加されると、コンパイラは引数のレイアウトを正しく計算できなくなります。可変長引数スライスは、その性質上、引数リストの「最後」に位置することが期待されており、その後に別の引数が続くことは想定されていませんでした。

このコミットでは、この問題を解決するために、キャプチャされた変数をクロージャの「入力引数リストの**先頭に挿入**」するように変更しました。

具体的には、以下の2つの主要な変更が行われました。

1.  **`src/cmd/compile/internal/gc/closure.go`**:
    *   `transformclosure` 関数内で、キャプチャされた変数をクロージャの引数リストに組み込むロジックが変更されました。
    *   以前は、既存の引数リストの末尾までポインタを辿り、そこにキャプチャ変数を追加していました。
    *   変更後、既存の引数リスト（`original_args`）を一時的に保存し、キャプチャされた変数を新しい引数リストの先頭に構築します。その後、保存しておいた `original_args` を、キャプチャ変数リストの末尾に連結します。これにより、キャプチャ変数が通常の引数よりも「前」に位置するようになります。
    *   コメントも「append」から「insert before」に変更され、意図が明確化されています。

2.  **`src/cmd/compile/internal/gc/walk.go`**:
    *   `walkexpr` 関数内で、クロージャの直接呼び出しを変換する部分が変更されました。
    *   以前は、`n.List = concat(n.List, n.Left.Func.Enter)` のように、キャプチャされた変数リスト（`n.Left.Func.Enter`）を既存の引数リスト（`n.List`）の「後」に連結していました。
    *   変更後、`n.List = concat(n.Left.Func.Enter, n.List)` のように、キャプチャされた変数リストを既存の引数リストの「前」に連結するように修正されました。これにより、`closure.go` での変更と整合性が取れ、キャプチャ変数が常に引数リストの先頭に配置されるようになります。

この変更により、可変長引数を持つクロージャであっても、キャプチャされた変数が正しく処理され、コンパイラが引数の型チェックやスタックレイアウトを適切に行えるようになりました。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/closure.go` の変更点

1.  **コメントの変更**:
    *   `// We are going to append captured variables to input args.` から `// We are going to insert captured variables before input args.` へ変更され、処理の意図が「追加」から「挿入」に変わったことを示しています。
    *   例示コードのコメントも `}(42, byval, &byref)` から `}(byval, &byref, 42)` に変更され、キャプチャ変数が引数の先頭に来ることを示唆しています。

2.  **引数リストの操作ロジックの変更**:
    *   以前は `for ; *param != nil; param = &(*param).Down {}` ループで既存の引数リストの末尾まで `param` ポインタを進めていました。
    *   変更後、`original_args := *param` で既存の入力引数リストを保存し、`xfunc.Func.Dcl = nil` でクロージャの宣言リストを一時的にクリアしています。
    *   キャプチャされた変数を処理するループ（`for _, v := range xfunc.Func.Enter`）内で、`*param = fld` と `param = &fld.Down` を使って、新しい引数リストの先頭にキャプチャ変数を順次追加していきます。
    *   ループ終了後、`*param = original_args` によって、保存しておいた元の引数リストを、キャプチャ変数で構成された新しい引数リストの末尾に連結します。
    *   `xfunc.Func.Dcl = concat(xfunc.Func.Dcl, original_dcl)` で、宣言リストも同様に連結し直しています。

この変更により、クロージャの内部的な関数シグネチャが、`[キャプチャ変数リスト], [元の引数リスト]` の順序で構築されるようになります。

### `src/cmd/compile/internal/gc/walk.go` の変更点

1.  **`concat` 関数の引数順序の変更**:
    *   `n.List = concat(n.List, n.Left.Func.Enter)` は、既存の引数リスト `n.List` の後にキャプチャ変数リスト `n.Left.Func.Enter` を連結していました。
    *   `n.List = concat(n.Left.Func.Enter, n.List)` に変更されたことで、キャプチャ変数リスト `n.Left.Func.Enter` が既存の引数リスト `n.List` の前に連結されるようになりました。

この変更は、`closure.go` での引数リスト構築順序の変更と同期しており、クロージャ呼び出しの際に実際に渡される引数の順序が `[キャプチャ変数], [通常の引数]` となるように調整しています。

### `test/fixedbugs/issue11750.go` の新規追加

このテストファイルは、可変長引数を持つクロージャがキャプチャされた変数を持つシナリオを再現しています。
```go
func main() {
	fn := func(names string) {
		// 何もしない関数
	}
	// 可変長引数を持つクロージャを定義し、即時実行
	func(names ...string) { // ここで `names` は可変長引数
		for _, name := range names {
			fn(name) // 外部の `fn` をキャプチャしているわけではないが、
			         // このクロージャ自体が可変長引数を持つことが重要
		}
	}("one", "two") // 2つの文字列を引数として渡す
}
```
このコード自体は、直接的に外部変数をキャプチャしているわけではありませんが、可変長引数を持つクロージャの定義と呼び出しを含んでいます。この種の構造が、以前の「末尾に追加」ロジックと衝突し、コンパイルエラーを引き起こしていたと考えられます。このテストがコンパイルエラーなく通過することで、修正が正しく機能していることを確認します。

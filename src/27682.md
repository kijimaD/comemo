# [インデックス 27682] ファイルの概要

このコミットは、Goコマンドラインツールにおけるベンダーパッケージのインポートパス解決に関するバグ修正と、それに関連するテストケースの追加を目的としています。具体的には、`parent.ImportPath`が`command-line-arguments`という特殊な値を持つ場合に、ベンダーパッケージのインポートパスが正しく計算されない問題を解決します。

## 変更の背景

Go 1.5で導入されたベンダー実験機能（Go 1.6でデフォルト有効化）は、プロジェクトが自身の依存関係を`vendor/`ディレクトリ内に隔離することを可能にしました。これにより、依存関係の管理がより予測可能になり、ビルドの再現性が向上しました。しかし、このベンダーメカニズムとGoツールのインポートパス解決ロジックの間には、特定のコーナーケースで問題が発生することがありました。

このコミットが修正しようとしているのは、`go build`や`go test`コマンドが特定のパッケージを直接コマンドライン引数として受け取った際に発生する問題です。この場合、Goツールは対象パッケージの`ImportPath`を`command-line-arguments`という特殊な文字列に設定します。この特殊な`ImportPath`を持つパッケージが、自身の`vendor/`ディレクトリ内のパッケージをインポートしようとすると、`vendoredImportPath`関数がベンダーパッケージの正しいインポートパスを計算できず、結果としてビルドエラーや予期せぬ動作を引き起こしていました。

具体的には、`vendoredImportPath`関数は、親パッケージのインポートパスを基にベンダーパッケージの相対パスを計算します。しかし、親パッケージのインポートパスが`command-line-arguments`である場合、この文字列は実際のファイルシステム上のパスやリポジトリのインポートパスとは何の関係もないため、パスの切り詰め（chopping）ロジックが破綻していました。このコミットは、この特殊なケースを検出し、親パッケージの実際のディレクトリ構造に基づいてインポートパスを再構築することで問題を解決します。

## 前提知識の解説

### Goのパッケージとインポートパス

Go言語では、コードはパッケージにまとめられます。各パッケージは一意の「インポートパス」によって識別されます。例えば、`"fmt"`や`"github.com/gorilla/mux"`などです。Goツールは、このインポートパスを使用して、ソースコードを`GOPATH`や`GOROOT`内の適切なディレクトリにマッピングし、依存関係を解決します。

### `command-line-arguments`

`command-line-arguments`は、Goツールが特定の状況下で内部的に使用する特殊なインポートパスです。これは、`go run main.go`のように単一のGoファイルを直接実行したり、`go build .`のようにカレントディレクトリのパッケージをビルドしたりする場合に発生します。これらのケースでは、Goツールは「メイン」パッケージに正式なインポートパスを割り当てることができないため、このプレースホルダーを使用します。このパッケージは、他のパッケージからインポートされることを意図していないため、通常は問題になりません。しかし、ベンダーパッケージの解決ロジックのように、親パッケージのインポートパスを基に相対パスを計算するような場合には、この特殊な値が問題を引き起こす可能性があります。

### Goのベンダーメカニズム (Vendoring)

Go 1.5で導入され、Go 1.6でデフォルトで有効になったベンダーメカニズムは、プロジェクトが依存する外部パッケージのコピーを自身の`vendor/`ディレクトリ内に保持することを可能にします。これにより、以下の利点があります。

*   **再現性:** 依存関係のバージョンが固定され、ビルドの再現性が保証されます。
*   **ネットワークの独立性:** 外部リポジトリがダウンしてもビルドが可能です。
*   **依存関係の衝突回避:** 異なるプロジェクトが同じ依存関係の異なるバージョンを必要とする場合に、衝突を回避できます。

Goツールは、パッケージをインポートする際に、まず現在のパッケージの`vendor/`ディレクトリ内を検索し、次に親ディレクトリを遡って`vendor/`ディレクトリを検索します。それでも見つからない場合は、`GOPATH`や`GOROOT`を検索します。

### `filepath.Join`とパス操作

Goの標準ライブラリ`path/filepath`パッケージは、ファイルパスを操作するためのユーティリティを提供します。`filepath.Join`は、複数のパス要素を結合して、オペレーティングシステムに適した形式のパスを生成します。このコミットでは、ファイルシステム上のディレクトリパスとGoのインポートパス（スラッシュ区切り）の間で変換を行うロジックが関係しています。

## 技術的詳細

このコミットの核心は、`src/cmd/go/pkg.go`内の`vendoredImportPath`関数の修正にあります。この関数は、親パッケージとインポートされるパスに基づいて、ベンダーパッケージの完全なインポートパスを決定する役割を担っています。

修正前のコードでは、`vendoredImportPath`関数は、親パッケージの`ImportPath`を直接使用して、ベンダーパッケージのインポートパスを計算していました。具体的には、親パッケージのディレクトリパスを遡りながら`vendor/`ディレクトリを見つけ、その`vendor/`ディレクトリまでのパス要素の長さを親パッケージの`ImportPath`から「切り詰める」ことで、ベンダーパッケージの相対インポートパスを導き出していました。

しかし、親パッケージの`ImportPath`が`command-line-arguments`である場合、この文字列は実際のディレクトリ構造とは無関係なため、切り詰めロジックが正しく機能しませんでした。`len(parent.ImportPath)`は`len("command-line-arguments")`となり、これが実際のディレクトリパスの長さと一致しないため、誤ったインポートパスが生成されていました。

このコミットでは、この問題を解決するために以下の変更が導入されました。

1.  **`command-line-arguments`の検出と処理:**
    `vendoredImportPath`関数内で、`importPath := parent.ImportPath`という行の直後に、以下の条件分岐が追加されました。
    ```go
    if importPath == "command-line-arguments" {
        // If parent.ImportPath is 'command-line-arguments'.
        // set to relative directory to root (also chopped root directory)
        importPath = dir[len(root)+1:]
    }
    ```
    このコードは、もし親パッケージの`ImportPath`が`command-line-arguments`である場合、`importPath`変数を、親パッケージの実際のディレクトリ`dir`から`GOPATH`の`src`ディレクトリ（`root`）からの相対パスに再設定します。これにより、`command-line-arguments`という特殊な値ではなく、実際のファイルシステム上の位置に基づいた有効なインポートパスが`importPath`に設定されます。

2.  **計算ロジックの修正:**
    `chopped := len(dir) - i`で計算される`chopped`変数は、親パッケージのディレクトリパスから`vendor/`ディレクトリまでのパス要素の長さを表します。修正前は、この`chopped`を`len(parent.ImportPath)`と比較していましたが、修正後は、新しく設定された`importPath`変数（`command-line-arguments`の場合は実際の相対パス）と比較するように変更されました。
    ```go
    // 修正前: if chopped == len(parent.ImportPath)+1 {
    if chopped == len(importPath)+1 {
    ```
    そして、最終的なベンダーパッケージのインポートパスを生成する際も、`parent.ImportPath`ではなく`importPath`を使用するように変更されました。
    ```go
    // 修正前: return parent.ImportPath[:len(parent.ImportPath)-chopped] + "/" + vpath
    return importPath[:len(importPath)-chopped] + "/" + vpath
    ```
    これにより、`command-line-arguments`の場合でも、`importPath`が実際の相対パスを反映しているため、切り詰めロジックが正しく機能し、ベンダーパッケージのインポートパスが正確に計算されるようになります。

これらの変更により、`go build .`や`go test .`のように`command-line-arguments`が使用される状況下でも、ベンダーパッケージが正しく解決され、ビルドやテストが成功するようになります。

また、`src/cmd/go/vendor_test.go`には、この修正を検証するための新しいテストケース`TestVendorTest3`が追加されました。このテストは、`github.com/clsung/go-vendor-issue-14613`というリポジトリを`go get`し、その中のベンダーパッケージを含む構造に対して`go build`および`go test`を実行します。特に、`command-line-arguments`のシナリオをシミュレートし、ベンダーパッケージのインポートが正しく機能することを確認しています。`myapp_test.go`のテストでは、意図的に「imported and not used」のエラーを発生させ、そのエラーメッセージが期待通りに出力されることを確認することで、コンパイルが正しく行われていることを間接的に検証しています。

## コアとなるコードの解説

### `src/cmd/go/pkg.go`の変更点

1.  **`importPath`変数の導入と条件付き再割り当て:**
    `vendoredImportPath`関数の冒頭で、`parent.ImportPath`を`importPath`という新しいローカル変数に代入します。
    ```go
    importPath := parent.ImportPath
    ```
    そして、この`importPath`が`"command-line-arguments"`であるかどうかをチェックします。
    ```go
    if importPath == "command-line-arguments" {
        // ...
        importPath = dir[len(root)+1:]
    }
    ```
    もし`"command-line-arguments"`であれば、`importPath`を実際のファイルシステム上の相対パスに再設定します。`dir`は親パッケージの物理的なディレクトリパス、`root`は`GOPATH/src`のようなGoのワークスペースのルートディレクトリです。`dir[len(root)+1:]`は、`root`のパス部分を`dir`から取り除き、`GOPATH/src`からの相対パス（Goのインポートパス形式）を生成します。例えば、`root`が`/home/user/go/src`で`dir`が`/home/user/go/src/myproject`であれば、`importPath`は`myproject`となります。これにより、`command-line-arguments`という無意味な文字列ではなく、ベンダーパス計算に適した有効なインポートパスが提供されます。

2.  **`len(importPath)`の使用:**
    ベンダーパスの切り詰めロジックにおいて、以前は`len(parent.ImportPath)`を使用していた箇所が、新しく導入された`importPath`変数を使用するように変更されました。
    ```go
    // 以前: if chopped == len(parent.ImportPath)+1 {
    if chopped == len(importPath)+1 {
    ```
    ```go
    // 以前: return parent.ImportPath[:len(parent.ImportPath)-chopped] + "/" + vpath
    return importPath[:len(importPath)-chopped] + "/" + vpath
    ```
    この変更により、`command-line-arguments`の場合でも、`importPath`が実際の相対パスを保持しているため、`chopped`（物理パスの長さ）と`importPath`の長さが正しく比較され、ベンダーパッケージのインポートパスが正確に計算されるようになります。

### `src/cmd/go/vendor_test.go`の変更点

`TestVendorTest3`という新しいテスト関数が追加されました。このテストは、`command-line-arguments`のシナリオでベンダーパッケージが正しく機能することを確認するためのものです。

1.  **外部ネットワークの確認:** `testenv.MustHaveExternalNetwork(t)`により、テスト実行環境が外部ネットワークにアクセスできることを確認します。これは、`go get`コマンドを使用するためです。
2.  **テスト環境のセットアップ:** `testgo(t)`でテスト用のGo環境をセットアップし、一時ディレクトリを作成して`GOPATH`に設定します。
3.  **リポジトリの取得:** `tg.run("get", "github.com/clsung/go-vendor-issue-14613")`を実行し、テスト対象となるリポジトリを`GOPATH`にダウンロードします。このリポジトリは、`command-line-arguments`の状況で問題を引き起こす可能性のあるベンダーパッケージ構造を含んでいると推測されます。
4.  **ビルドとテストの実行:**
    *   `tg.run("build", "-i", "github.com/clsung/go-vendor-issue-14613")`: リポジトリをビルドします。`-i`フラグは依存関係もインストールします。
    *   `tg.run("test", "-i", "github.com/clsung/go-vendor-issue-14613")`と`tg.run("test", "github.com/clsung/go-vendor-issue-14613")`: リポジトリ内のパッケージに対してテストを実行します。
    *   `tg.cd(filepath.Join(tg.path("."), "src"))`の後に、特定のテストファイル`vendor_test.go`を指定してテストを実行します。これは、`command-line-arguments`のシナリオをより直接的にシミュレートするためと考えられます。
5.  **エラーケースの検証:**
    `tg.runFail("test", "github.com/clsung/go-vendor-issue-14613/vendor/mylibtesttest/myapp/myapp_test.go")`を実行し、意図的に失敗するテストケースを検証します。このテストは、`imported and not used`というコンパイルエラーを発生させることを期待しており、`tg.grepStderr("imported and not used:", ...)`でそのエラーメッセージが標準エラー出力に含まれていることを確認します。これにより、ベンダーパッケージが正しくコンパイルされ、Goコンパイラの通常のチェックが適用されていることを間接的に証明しています。

これらのテストは、`command-line-arguments`の状況下でベンダーパッケージのインポートパス解決が正しく行われることを、具体的なシナリオを通じて検証しています。

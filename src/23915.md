# [インデックス 23915] ファイルの概要

このコミットは、Goランタイムのメモリ管理に関連する2つのファイル、`src/runtime/malloc.go` と `src/runtime/mheap.go` に変更を加えています。`malloc.go` はヒープメモリの割り当てと管理の低レベルな詳細を扱い、`mheap.go` はGoランタイムのグローバルヒープ構造 (`mheap`) を定義し、その操作を管理します。

## 変更の背景

このコミットは、Goランタイムのメモリ管理における競合状態（レースコンディション）を解消するために導入されました。Goのガベージコレクタ（GC）やライトバリアは、ヒープ上のオブジェクトを正確に追跡するために、ヒープビットマップとスパン配列というメタデータに依存しています。

問題は、ヒープの利用可能な領域を示す `h.arena_used` フィールドが更新されたにもかかわらず、その新しい領域に対応するヒープビットマップとスパン配列のメモリがまだOSにマップされていない（または初期化されていない）場合に発生しました。このような状況で、GCやライトバリアが同時に動作し、新しく `arena_used` に含まれるようになったアドレスを指すポインタを検出すると、そのポインタのメタデータ（スパン情報やGCビット）を取得しようとします。しかし、メタデータが格納されるべきメモリ領域がまだマップされていないため、不正なメモリアクセス（セグメンテーション違反など）が発生し、プログラムがクラッシュする可能性がありました。

以前のコミット `d57c889` は、この問題の多くの発生箇所を修正し、`arena_used` が更新される前に対応するビットマップとスパンをマップするように変更しました。しかし、このコミットが指摘するように、`d57c889` は特定のコードパス、特に32-bitシステムでアドレス空間の「穴」を越えてヒープ予約を拡張する際に発生するケースを見落としていました。この見落とされたケースでは、`arena_used` が一時的に更新され、その後にビットマップとスパンのマッピングが行われるという時間的な窓が存在し、元の競合状態が再発する可能性がありました。

このコミットは、その「残された一つ」のケースを特定し、`arena_used` が更新される直前に `mHeap_MapBits` と `mHeap_MapSpans` を呼び出すことで、この競合状態を完全に解消することを目的としています。

## 前提知識の解説

### Goランタイムのメモリ管理

Goランタイムは独自のメモリ管理システムを持っています。
*   **ヒープ (Heap)**: プログラムが動的にオブジェクトを割り当てる領域です。GoのGCによって管理されます。
*   **アリーナ (Arena)**: ヒープメモリの大きな連続したブロックを指します。`mheap` 構造体は、このアリーナの開始 (`arena_start`)、使用済み (`arena_used`)、終了 (`arena_end`) アドレスを管理します。
*   **`mspan` (Memory Span)**: Goランタイムのメモリ管理の基本単位です。通常、複数のOSページ（8KB）から構成される連続したメモリブロックで、特定のサイズのオブジェクトを割り当てるために使用されます。各 `mspan` は、その中に割り当てられたオブジェクトの状態（使用中か空きか）を追跡するためのビットマップ (`allocBits`) を持ちます。
*   **ヒープビットマップ (Heap Bitmap)**: ヒープ上の各メモリワードがポインタであるか、またはGCにとって意味のある他の情報を持っているかを追跡するためのデータ構造です。GCがオブジェクトグラフを走査する際に、どのフィールドがポインタであるかを効率的に判断するために使用されます。これにより、GCはポインタではないデータ（整数など）をスキャンする無駄を省き、パフォーマンスを向上させます。

### Goのガベージコレクション (GC) とライトバリア

GoのGCは、並行（concurrent）なトライカラーマーキングアルゴリズムを採用しています。
*   **トライカラーマーキング**: オブジェクトを「白（未訪問、回収候補）」「灰（訪問済みだが参照先未スキャン）」「黒（訪問済み、参照先もスキャン済み）」の3色に分類して、到達可能なオブジェクトをマークします。
*   **ライトバリア (Write Barrier)**: GCが動作している最中に、ユーザープログラム（ミューテーター）がヒープ上のポインタを書き換えることで、GCがオブジェクトを見落とす（誤って回収してしまう）ことを防ぐためのメカニズムです。例えば、黒いオブジェクトが白いオブジェクトを指すように変更された場合、ライトバリアはその白いオブジェクトを灰色にマークし、GCが後でスキャンするようにします。これにより、GCとユーザープログラムが並行して動作しても、メモリの安全性が保たれます。ライトバリアは、コンパイラによってポインタの書き込み命令の前に自動的に挿入される小さなコードスニペットです。

### レースコンディション

複数のゴルーチン（またはスレッド）が共有リソースに同時にアクセスし、そのアクセス順序によって結果が非決定的に変わる状態をレースコンディションと呼びます。このコミットのケースでは、`arena_used` の更新と、それに対応するメタデータ（ヒープビットマップ、スパン配列）のOSへのマッピングが非同期に行われることで、GCやライトバリアが古い状態のメタデータにアクセスしようとして問題が発生しました。

### 32-bitシステムにおけるアドレス空間の「穴」

32-bitシステムでは、利用可能な仮想アドレス空間が4GBに制限されます。OSは、このアドレス空間の一部をカーネルや共有ライブラリ、スタックなどに割り当てます。そのため、連続した大きなメモリブロックを確保しようとすると、既に他の用途で使われているアドレス範囲によって「穴」ができてしまい、希望するサイズの連続した領域を一度に確保できないことがあります。このような場合、Goランタイムは複数の非連続なメモリ領域を確保し、それらを論理的に連続したヒープとして管理する必要があります。このコミットで言及されている「アドレス空間の穴を越えてヒープ予約を拡張する」とは、このような状況でヒープが新しい非連続なメモリ領域を獲得するシナリオを指します。

## 技術的詳細

Goランタイムの `mHeap_SysAlloc` 関数は、GoヒープがOSから新しいメモリを要求する際に呼び出されます。この関数は、要求されたサイズのメモリをOSから `mmap` システムコールなどを通じて確保し、それをGoヒープのアリーナに組み込みます。

このコミットが修正する問題は、`mHeap_SysAlloc` 内でヒープアリーナの `h.arena_used` フィールドが更新されるタイミングと、その新しい領域に対応するヒープビットマップおよびスパン配列のメモリがOSにマップされるタイミングの間に発生する競合状態です。

具体的には、以下のステップで問題が発生する可能性がありました。

1.  `mHeap_SysAlloc` がOSから新しいメモリ領域 `p` を確保する。
2.  `h.arena_used` が、この新しい領域 `p` を含むように更新される。
3.  この時点では、新しい `arena_used` の範囲に対応するヒープビットマップとスパン配列のメモリはまだOSにマップされていない。
4.  この間に、並行して動作するGCスレッドやライトバリアが、新しく `arena_used` に含まれたアドレスを指すポインタを検出する。
5.  GC/ライトバリアは、そのポインタのメタデータ（`mspan` やヒープビット）を検索するために、まだマップされていないメモリ領域にアクセスしようとする。
6.  結果として、不正なメモリアクセスが発生し、プログラムがクラッシュする。

以前のコミット `d57c889` は、この問題のほとんどのケースを修正し、`h.arena_used` を更新する前に `mHeap_MapBits` と `mHeap_MapSpans` を呼び出すようにしました。`mHeap_MapBits` はヒープビットマップのメモリを、`mHeap_MapSpans` はスパン配列のメモリをOSにマップする役割を担います。これにより、`arena_used` が指す範囲のメモリは常に有効なメタデータ領域を持つことが保証されます。

しかし、`d57c889` は、32-bitシステムでアドレス空間の「穴」を越えてヒープ予約を拡張する特定のコードパスを見落としていました。このパスでは、`h.arena_used` が一度更新された後、さらに後続の処理で再度更新され、その際にビットマップとスパンのマッピングが行われることを期待していました。この「一時的な更新」と「最終的なマッピング」の間に、上記のような競合状態が発生する可能性が残っていたのです。

このコミットは、その見落とされた特定の `arena_used` 更新の直前にも `mHeap_MapBits` と `mHeap_MapSpans` を呼び出すことで、この最後の競合状態の窓を閉じます。コミットメッセージが述べているように、このコードパスは32-bitシステムでのみ発生し、追加の `mmap` 呼び出しによるパフォーマンスへの影響は無視できる程度であるとされています。

`mheap` 構造体の `arena_used` フィールドのコメントが `// always mHeap_Map{Bits,Spans} before updating` に変更されたことは、このコミットが確立しようとしている重要な不変条件（invariant）を明確に示しています。つまり、`arena_used` を更新する際には、常にその前に対応するビットマップとスパンのメモリがマップされている必要がある、という原則です。

## コアとなるコードの解説

### `src/runtime/malloc.go` の変更

変更の中心は、`mHeap_SysAlloc` 関数内で `h.arena_used` が更新されるロジックです。

**変更前:**
```go
h.arena_used = p + (-uintptr(p) & (_PageSize - 1))
```
この行では、新しく確保されたメモリ領域 `p` の開始アドレスを基に、ページアラインメントを考慮した `arena_used` の新しい値が直接 `h.arena_used` に代入されていました。この代入の直後には、対応するヒープビットマップとスパン配列のメモリがまだマップされていない可能性がありました。

**変更後:**
```go
used := p + (-uintptr(p) & (_PageSize - 1))
mHeap_MapBits(h, used)
mHeap_MapSpans(h, used)
h.arena_used = used
```
1.  `used := p + (-uintptr(p) & (_PageSize - 1))`: まず、`h.arena_used` に設定されるべき新しい値が一時変数 `used` に計算されます。これは、新しく確保されたメモリ領域 `p` の開始アドレスを、Goランタイムのページサイズ (`_PageSize`) にアラインメントしたものです。
2.  `mHeap_MapBits(h, used)`: 次に、この `used` アドレスまでの範囲に対応するヒープビットマップのメモリがOSにマップされます。これにより、GCがこの領域のオブジェクトのポインタ情報を参照できるようになります。
3.  `mHeap_MapSpans(h, used)`: 同様に、`used` アドレスまでの範囲に対応するスパン配列のメモリがOSにマップされます。これにより、GCやランタイムがこの領域のメモリがどの `mspan` に属するかを効率的に検索できるようになります。
4.  `h.arena_used = used`: 最後に、ヒープビットマップとスパン配列のメモリが適切にマップされたことを確認した上で、`h.arena_used` が新しい値 `used` に更新されます。

この変更により、`h.arena_used` が指すメモリ領域は、常にそのメタデータ（ヒープビットマップとスパン配列）が有効な状態であることが保証され、並行するGCやライトバリアによる不正なメモリアクセスのリスクが排除されます。

### `src/runtime/mheap.go` の変更

`mheap` 構造体の `arena_used` フィールドのコメントが以下のように変更されました。

**変更前:**
```go
arena_used     uintptr
```

**変更後:**
```go
arena_used     uintptr // always mHeap_Map{Bits,Spans} before updating
```
このコメントの追加は、`arena_used` フィールドを更新する際の重要な不変条件を明示しています。つまり、`arena_used` の値を変更する際には、常にその前に `mHeap_MapBits` と `mHeap_MapSpans` を呼び出して、対応するメタデータ領域がマップされていることを保証しなければならない、というランタイムの設計原則を強調しています。これは、このコミットが解決しようとした問題の根本原因と、その解決策の重要性を開発者に伝えるためのものです。

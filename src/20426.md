# [インデックス 20426] ファイルの概要

このコミットは、GoランタイムにおけるARMアーキテクチャでの重要なバグ修正に関するものです。特に、`g`（現在のゴルーチンを示すポインタ）がスレッドローカルストレージ（TLS）に適切に保存されないことによって引き起こされる、シグナルハンドリング時のクラッシュを解決します。

## コミット

```
commit b4bfa6c96415f4a578c1e100a515c2c62981b546
Author: Russ Cox <rsc@golang.org>
Date:   Sun Sep 7 19:47:40 2014 -0400

    runtime: save g to TLS more aggressively

    This is one of those "how did this ever work?" bugs.
    The current build failures are happening because
    a fault comes up while executing on m->curg on a
    system-created thread using an m obtained from needm,
    but TLS is set to m->g0, not m->curg. On fault,
    sigtramp starts executing, assumes r10 (g) might be
    incorrect, reloads it from TLS, and gets m->g0, not
    m->curg. Then sighandler dutifully pushes a call to
    sigpanic onto the stack and returns to it.
    We're now executing on the m->curg stack but with
    g=m->g0. Sigpanic does a stack split check, sees that
    the SP is not in range (50% chance depending on relative
    ordering of m->g0's and m->curg's stacks), and then
    calls morestack. Morestack sees that g=m->g0 and
    crashes the program.

    The fix is to replace every change of g in asm_arm.s
    with a call to a function that both updates g and
    saves the updated g to TLS.

    Why did it start happening? That's unclear.
    Unfortunately there were other bugs in the initial
    checkin that mask exactly which of a sequence of
    CLs started the behavior where sigpanic would end
    up tripping the stack split.

    Fixes arm build.
    Fixes #8675.

    CC=dave, golang-codereviews, khr, minux, r
```

## 元コミット内容

このコミットは、GoランタイムがARMアーキテクチャ上で`g`（現在のゴルーチン構造体へのポインタ）をスレッドローカルストレージ（TLS）に保存する方法をより積極的に変更するものです。

問題は、システムが作成したスレッド上で`m->curg`（現在のMが実行しているゴルーチン）のスタックで実行中にフォールト（例外）が発生した際に、TLSに保存されている`g`が`m->g0`（Mのシステムゴルーチン）を指しているために発生しました。フォールト発生時、シグナルハンドラ（`sigtramp`）が実行を開始し、`g`レジスタ（ARMでは通常`r10`）が不正である可能性を考慮してTLSから`g`を再ロードしますが、この時に`m->g0`がロードされてしまいます。

結果として、`m->curg`のスタック上で実行しているにもかかわらず、`g`は`m->g0`を指すという矛盾した状態になります。この状態で`sigpanic`（Goのパニック処理の一部）がスタック分割チェックを行うと、現在のスタックポインタ（SP）が`g`（この場合は`m->g0`）のスタック範囲内にないため、`morestack`が呼び出されます。`morestack`は`g=m->g0`であることを見て、プログラムをクラッシュさせます。

この修正は、`asm_arm.s`内の`g`レジスタの変更箇所すべてを、`g`を更新し、その更新された`g`をTLSに保存する関数呼び出しに置き換えることで行われます。

この問題がなぜ突然発生し始めたのかは不明ですが、初期のチェックインには他のバグがあり、どの変更がこの挙動を引き起こしたのかを特定するのが困難であったと述べられています。

このコミットはARMビルドの問題を修正し、Issue #8675を解決します。

## 変更の背景

Goランタイムは、複数のゴルーチンを効率的にスケジューリングするために、M（OSスレッド）とG（ゴルーチン）という抽象化を使用しています。各Mは、現在実行中のゴルーチン（`m->curg`）と、M自身のスタックで実行されるシステムゴルーチン（`m->g0`）を持っています。`g`レジスタ（ARMでは`r10`）は常に現在のゴルーチンを指すように設計されています。

しかし、シグナルハンドリングのような非同期イベントが発生した場合、OSは現在の実行コンテキストを中断し、シグナルハンドラに制御を移します。この際、Goランタイムはシグナルハンドラ内で現在のゴルーチン（`g`）を正確に把握し、必要に応じてコンテキストを切り替える必要があります。

このコミットが修正しようとしている問題は、ARMアーキテクチャにおいて、`g`レジスタの値とTLSに保存されている`g`の値が同期していない場合に発生する競合状態です。特に、`m->curg`のスタックで実行中にフォールトが発生し、シグナルハンドラがTLSから`g`を再ロードする際に、誤って`m->g0`をロードしてしまうことが問題でした。これにより、`g`レジスタが指すゴルーチンと、実際に実行されているスタックが異なるという矛盾が生じ、スタック分割チェックが失敗してクラッシュに至っていました。

この問題は、Goの安定性と信頼性に直接影響を与えるものであり、特にARMベースのシステムでのGoプログラムの実行を妨げる深刻なバグでした。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とARMアセンブリの基礎知識が必要です。

### Goランタイムの基本概念

*   **G (Goroutine)**: Goにおける軽量な実行単位。OSスレッドよりもはるかに軽量で、数百万個作成することも可能です。各Gは独自のスタックを持ちます。
*   **M (Machine/OS Thread)**: OSが管理するスレッド。Goランタイムは、GをM上で実行します。MはOSスケジューラによってスケジューリングされます。
*   **P (Processor)**: MとGを仲介する論理プロセッサ。Pは実行可能なGのキューを持ち、MにGを割り当てます。
*   **`g` (現在のゴルーチンポインタ)**: Goランタイムの内部では、現在のMが実行しているゴルーチンへのポインタが特定のレジスタ（ARMでは`r10`）に保持されています。このポインタは、スタックの境界チェックやスケジューリングなど、ランタイムの多くの操作で利用されます。
*   **`m->curg`**: 現在のMが実行しているユーザーゴルーチン（G）へのポインタ。
*   **`m->g0`**: 各Mが持つ特別なゴルーチンで、ランタイムの内部処理（スケジューリング、ガベージコレクション、シグナルハンドリングなど）を実行するために使用されます。`g0`は通常のユーザーゴルーチンとは異なる、固定サイズのスタックを持ちます。
*   **スレッドローカルストレージ (TLS: Thread Local Storage)**: 各OSスレッドが独自のデータを保存できるメモリ領域。Goランタイムは、現在のMやGへのポインタなど、スレッド固有の情報をTLSに保存することがあります。これにより、OSスレッドが切り替わっても、そのスレッドに関連するGoランタイムのコンテキストを迅速に取得できます。
*   **シグナルハンドリング**: OSがプロセスにシグナル（例: セグメンテーション違反、割り込み）を送信した際に、そのシグナルを処理するために実行される特別な関数。Goランタイムは、クラッシュやデバッグなどのためにシグナルハンドラを設定します。
*   **`sigtramp`**: シグナルが発生した際にOSから最初に呼び出される、アセンブリ言語で書かれたシグナルハンドラの入り口。Goランタイムのシグナルハンドラに制御を渡す前に、レジスタの保存やコンテキストのセットアップを行います。
*   **`sigpanic`**: Goランタイムのパニック処理の一部で、シグナルによって引き起こされたエラー（例: nilポインタ参照）をGoのパニックとして処理するための関数。
*   **`morestack`**: Goのスタックが不足した際に、より大きなスタックを割り当てるために呼び出されるランタイム関数。スタックの拡張は、現在のゴルーチンのスタックポインタがスタックの境界を超えた場合にトリガーされます。
*   **スタック分割 (Stack Split)**: Goのゴルーチンスタックは動的に伸縮します。関数呼び出しの際に、現在のスタックが不足していると判断されると、`morestack`が呼び出されてスタックが拡張されます。

### ARMアセンブリの基礎

*   **レジスタ**: ARMプロセッサの内部にある高速な記憶領域。`R0`から`R15`まであり、それぞれ特定の役割を持つことがあります（例: `SP`はスタックポインタ、`LR`はリンクレジスタ、`PC`はプログラムカウンタ）。
*   **`MOVW`**: レジスタまたはメモリからレジスタへワード（32ビット）を移動する命令。
*   **`BL` (Branch with Link)**: 関数呼び出しを行う命令。呼び出し元のアドレスを`LR`レジスタに保存し、指定されたアドレスにジャンプします。
*   **`TEXT`**: アセンブリコードで関数の開始を宣言するディレクティブ。
*   **`SB` (Static Base)**: グローバルシンボルや静的データへのオフセットを計算するためのベースレジスタ。
*   **`FP` (Frame Pointer)**: 現在のスタックフレームのベースアドレスを指すレジスタ。
*   **`SP` (Stack Pointer)**: 現在のスタックのトップを指すレジスタ。
*   **`LR` (Link Register)**: 関数呼び出しからの戻りアドレスを保持するレジスタ。
*   **`PC` (Program Counter)**: 次に実行される命令のアドレスを保持するレジスタ。
*   **`CMP`**: 2つのオペランドを比較し、フラグレジスタを設定する命令。
*   **`BEQ` (Branch if Equal)**: 比較結果が等しい場合に分岐する命令。
*   **`B.NE` (Branch if Not Equal)**: 比較結果が等しくない場合に分岐する命令。
*   **`MRC` (Move from Coprocessor to Register)**: コプロセッサからレジスタへデータを移動する命令。ARMでは、TLSベースポインタの取得にシステムコプロセッサが使用されることがあります。

## 技術的詳細

このコミットの核心は、ARMアーキテクチャにおける`g`レジスタ（`r10`）とTLSに保存されている`g`ポインタの同期を強化することです。

従来のGoランタイムでは、`g`レジスタが変更された際に、必ずしもその変更がTLSに反映されるわけではありませんでした。特に、`runtime.gogo`や`runtime.mcall`、`runtime.morestack`、`runtime.lessstack`、`asmcgocall`といった、ゴルーチンやMのコンテキストを切り替える重要なアセンブリ関数において、`g`レジスタの更新とTLSへの保存が分離されているか、あるいはTLSへの保存が省略されているケースがありました。

問題は、シグナルハンドラが非同期に割り込む可能性がある点にあります。シグナルハンドラは、現在の実行中のゴルーチン（`m->curg`）のコンテキストで発生しますが、TLSに保存されている`g`が`m->g0`を指していると、シグナルハンドラがTLSから`g`を再ロードした際に誤ったゴルーチンコンテキスト（`m->g0`）を取得してしまいます。

これにより、`m->curg`のスタックで実行しているにもかかわらず、ランタイムが`m->g0`のコンテキストで動作しようとするという矛盾が生じます。特に`sigpanic`がスタック分割チェックを行う際、現在のスタックポインタが`m->g0`のスタック範囲外にあると判断され、`morestack`が呼び出されます。`morestack`は`g=m->g0`であると認識し、`m->g0`のスタックを拡張しようとしますが、これは通常、`m->g0`のスタックは固定サイズであるため、プログラムのクラッシュにつながります。

この修正では、`asm_arm.s`内の`g`レジスタへのすべての代入（`MOVW`命令）を、新しいヘルパー関数`setg<>(SB)`の呼び出しに置き換えます。`setg<>(SB)`は、`g`レジスタを更新するだけでなく、その更新された`g`の値を直ちにTLSにも保存することを保証します。これにより、`g`レジスタとTLSの`g`ポインタが常に同期されるようになり、シグナルハンドラがTLSから`g`をロードする際に常に正しいゴルーチンコンテキストを取得できるようになります。

また、`src/pkg/runtime/arch_arm.h`の`RuntimeGogoBytes`が`84`から`60`に減少しています。これは、`runtime.gogo`関数内でスタックに保存されるレジスタの数が変更されたことを示唆しており、おそらく`setg`関数の導入によるスタックフレームの調整に関連している可能性があります。

`src/pkg/runtime/tls_arm.s`では、`runtime·save_g`関数が`g`の値を`R0`レジスタに保持して戻るように変更されています。これは、`setg`関数が`runtime·save_g`を呼び出した後に`g`の値を再利用できるようにするためです。

## コアとなるコードの変更箇所

主要な変更は以下の3つのファイルにわたります。

1.  **`src/pkg/runtime/arch_arm.h`**:
    *   `RuntimeGogoBytes`の値が`84`から`60`に減少。

2.  **`src/pkg/runtime/asm_arm.s`**:
    *   `runtime·gogo`、`runtime·mcall`、`runtime·morestack`、`runtime·lessstack`、`asmcgocall`などの関数内で、`g`レジスタに直接値を代入していた`MOVW`命令の多くが、`setg<>(SB)`関数への`BL`（Branch with Link）呼び出しに置き換えられています。
    *   新しいヘルパー関数`setg<>(SB)`が追加されています。この関数は、引数として渡された`g`の値を`g`レジスタに設定し、さらに`runtime·save_g`を呼び出してその値をTLSに保存します。
    *   `runtime·setg`という既存の関数が、`setg<>(SB)`を呼び出すように変更されています。

3.  **`src/pkg/runtime/tls_arm.s`**:
    *   `runtime·save_g`関数のシグネチャが変更され、`g`の値を`R0`レジスタに保持して戻るようになりました。これにより、呼び出し元が`g`の値を再利用できるようになります。

## コアとなるコードの解説

### `src/pkg/runtime/asm_arm.s` の変更

最も重要な変更は、`g`レジスタへの直接的な代入を`setg<>(SB)`関数への呼び出しに置き換えた点です。

**変更前（例: `runtime·gogo`内）:**

```armasm
	MOVW	gobuf_g(R1), g
	MOVW	0(g), R2		// make sure g != nil
	MOVB	runtime·iscgo(SB), R2
	CMP 	$0, R2 // if in Cgo, we have to save g
	BL.NE	runtime·save_g(SB) // this call will clobber R0
```

ここでは、`gobuf_g(R1)`から`g`レジスタに直接値をロードし、その後Cgoが有効な場合にのみ`runtime·save_g`を条件付きで呼び出していました。

**変更後（例: `runtime·gogo`内）:**

```armasm
	MOVW	gobuf_g(R1), R0
	BL	setg<>(SB)
```

変更後では、まず`gobuf_g(R1)`の値を`R0`レジスタにロードし、その後無条件に`setg<>(SB)`を呼び出しています。

**新しく追加された `setg<>(SB)` 関数:**

```armasm
TEXT setg<>(SB),NOSPLIT,$-4-0
	MOVW	R0, g

	// Save g to thread-local storage.
	MOVB	runtime·iscgo(SB), R0
	CMP	$0, R0
	B.EQ	2(PC)
	B	runtime·save_g(SB)

	MOVW	g, R0
	RET
```

この`setg<>(SB)`関数は以下の処理を行います。
1.  `MOVW R0, g`: 引数として`R0`に渡された新しい`g`の値を`g`レジスタに設定します。
2.  `Save g to thread-local storage.`: ここが重要な部分です。
    *   `MOVB runtime·iscgo(SB), R0`: `iscgo`（Cgoが有効かどうかを示すフラグ）の値を`R0`にロードします。
    *   `CMP $0, R0`: `R0`が0（Cgoが無効）かどうかを比較します。
    *   `B.EQ 2(PC)`: もしCgoが無効であれば、次の2命令をスキップして`MOVW g, R0`にジャンプします（つまり`runtime·save_g`を呼び出しません）。
    *   `B runtime·save_g(SB)`: Cgoが有効であれば、`runtime·save_g`関数を呼び出して、現在の`g`の値をTLSに保存します。
3.  `MOVW g, R0`: `g`レジスタの値を`R0`にコピーして戻ります。これは、`setg`を呼び出した元のコードが`g`の値を`R0`で受け取れるようにするためです。

この変更により、`g`レジスタが変更されるたびに、その新しい値がTLSにも確実に保存されるようになります。これにより、シグナルハンドラがTLSから`g`をロードする際に、常に最新かつ正しいゴルーチンコンテキストを取得できるようになり、前述のクラッシュが回避されます。

### `src/pkg/runtime/tls_arm.s` の変更

`runtime·save_g`関数の変更は、`setg<>(SB)`からの呼び出しに対応するためのものです。

**変更前:**

```armasm
TEXT runtime·save_g(SB),NOSPLIT,$0
// ...
	MOVW	g, 0(R0)
	RET
```

**変更後:**

```armasm
TEXT runtime·save_g(SB),NOSPLIT,$-4
// ...
	MOVW	g, 0(R0)
	MOVW	g, R0 // preserve R0 across call to setg<>
	RET
```

変更後では、TLSに`g`を保存した後、さらに`g`の値を`R0`レジスタにコピーしてから`RET`（戻り）しています。これは、`setg<>(SB)`が`runtime·save_g`を呼び出した後に、`g`の値を`R0`で受け取って、その後の処理（`MOVW g, R0`）で利用できるようにするためです。

### `src/pkg/runtime/arch_arm.h` の変更

`RuntimeGogoBytes`の減少は、`runtime.gogo`関数がスタックに保存するレジスタの数が減ったことを示唆しています。これは、`setg`関数の導入により、一部のレジスタの保存/復元ロジックが変更された結果として、スタックフレームのサイズが最適化された可能性を示しています。

## 元コミット内容

このコミットは、GoランタイムがARMアーキテクチャ上で`g`（現在のゴルーチン構造体へのポインタ）をスレッドローカルストレージ（TLS）に保存する方法をより積極的に変更するものです。

問題は、システムが作成したスレッド上で`m->curg`（現在のMが実行しているゴルーチン）のスタックで実行中にフォールト（例外）が発生した際に、TLSに保存されている`g`が`m->g0`（Mのシステムゴルーチン）を指しているために発生しました。フォールト発生時、シグナルハンドラ（`sigtramp`）が実行を開始し、レジスタ`r10`（`g`）が不正である可能性を考慮してTLSから`g`を再ロードしますが、この時に`m->g0`がロードされてしまいます。

結果として、`m->curg`のスタック上で実行しているにもかかわらず、`g`は`m->g0`を指すという矛盾した状態になります。この状態で`sigpanic`（Goのパニック処理の一部）がスタック分割チェックを行うと、現在のスタックポインタ（SP）が`g`（この場合は`m->g0`）のスタック範囲内にないため、`morestack`が呼び出されます。`morestack`は`g=m->g0`であることを見て、プログラムをクラッシュさせます。

この修正は、`asm_arm.s`内の`g`レジスタの変更箇所すべてを、`g`を更新し、その更新された`g`をTLSに保存する関数呼び出しに置き換えることで行われます。

この問題がなぜ突然発生し始めたのかは不明ですが、初期のチェックインには他のバグがあり、どの変更がこの挙動を引き起こしたのかを特定するのが困難であったと述べられています。

このコミットはARMビルドの問題を修正し、Issue #8675を解決します。

## 変更の背景

Goランタイムは、複数のゴルーチンを効率的にスケジューリングするために、M（OSスレッド）とG（ゴルーチン）という抽象化を使用しています。各Mは、現在実行中のゴルーチン（`m->curg`）と、M自身のスタックで実行されるシステムゴルーチン（`m->g0`）を持っています。`g`レジスタ（ARMでは`r10`）は常に現在のゴルーチンを指すように設計されています。

しかし、シグナルハンドリングのような非同期イベントが発生した場合、OSは現在の実行コンテキストを中断し、シグナルハンドラに制御を移します。この際、Goランタイムはシグナルハンドラ内で現在のゴルーチン（`g`）を正確に把握し、必要に応じてコンテキストを切り替える必要があります。

このコミットが修正しようとしている問題は、ARMアーキテクチャにおいて、`g`レジスタの値とTLSに保存されている`g`の値が同期していない場合に発生する競合状態です。特に、`m->curg`のスタックで実行中にフォールトが発生し、シグナルハンドラがTLSから`g`を再ロードする際に、誤って`m->g0`をロードしてしまうことが問題でした。これにより、`g`レジスタが指すゴルーチンと、実際に実行されているスタックが異なるという矛盾が生じ、スタック分割チェックが失敗してクラッシュに至っていました。

この問題は、Goの安定性と信頼性に直接影響を与えるものであり、特にARMベースのシステムでのGoプログラムの実行を妨げる深刻なバグでした。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とARMアセンブリの基礎知識が必要です。

### Goランタイムの基本概念

*   **G (Goroutine)**: Goにおける軽量な実行単位。OSスレッドよりもはるかに軽量で、数百万個作成することも可能です。各Gは独自のスタックを持ちます。
*   **M (Machine/OS Thread)**: OSが管理するスレッド。Goランタイムは、GをM上で実行します。MはOSスケジューラによってスケジューリングされます。
*   **P (Processor)**: MとGを仲介する論理プロセッサ。Pは実行可能なGのキューを持ち、MにGを割り当てます。
*   **`g` (現在のゴルーチンポインタ)**: Goランタイムの内部では、現在のMが実行しているゴルーチンへのポインタが特定のレジスタ（ARMでは`r10`）に保持されています。このポインタは、スタックの境界チェックやスケジューリングなど、ランタイムの多くの操作で利用されます。
*   **`m->curg`**: 現在のMが実行しているユーザーゴルーチン（G）へのポインタ。
*   **`m->g0`**: 各Mが持つ特別なゴルーチンで、ランタイムの内部処理（スケジューリング、ガベージコレクション、シグナルハンドリングなど）を実行するために使用されます。`g0`は通常のユーザーゴルーチンとは異なる、固定サイズのスタックを持ちます。
*   **スレッドローカルストレージ (TLS: Thread Local Storage)**: 各OSスレッドが独自のデータを保存できるメモリ領域。Goランタイムは、現在のMやGへのポインタなど、スレッド固有の情報をTLSに保存することがあります。これにより、OSスレッドが切り替わっても、そのスレッドに関連するGoランタイムのコンテキストを迅速に取得できます。
*   **シグナルハンドリング**: OSがプロセスにシグナル（例: セグメンテーション違反、割り込み）を送信した際に、そのシグナルを処理するために実行される特別な関数。Goランタイムは、クラッシュやデバッグなどのためにシグナルハンドラを設定します。
*   **`sigtramp`**: シグナルが発生した際にOSから最初に呼び出される、アセンブリ言語で書かれたシグナルハンドラの入り口。Goランタイムのシグナルハンドラに制御を渡す前に、レジスタの保存やコンテキストのセットアップを行います。
*   **`sigpanic`**: Goランタイムのパニック処理の一部で、シグナルによって引き起こされたエラー（例: nilポインタ参照）をGoのパニックとして処理するための関数。
*   **`morestack`**: Goのスタックが不足した際に、より大きなスタックを割り当てるために呼び出されるランタイム関数。スタックの拡張は、現在のゴルーチンのスタックポインタがスタックの境界を超えた場合にトリガーされます。
*   **スタック分割 (Stack Split)**: Goのゴルーチンスタックは動的に伸縮します。関数呼び出しの際に、現在のスタックが不足していると判断されると、`morestack`が呼び出されてスタックが拡張されます。

### ARMアセンブリの基礎

*   **レジスタ**: ARMプロセッサの内部にある高速な記憶領域。`R0`から`R15`まであり、それぞれ特定の役割を持つことがあります（例: `SP`はスタックポインタ、`LR`はリンクレジスタ、`PC`はプログラムカウンタ）。
*   **`MOVW`**: レジスタまたはメモリからレジスタへワード（32ビット）を移動する命令。
*   **`BL` (Branch with Link)**: 関数呼び出しを行う命令。呼び出し元のアドレスを`LR`レジスタに保存し、指定されたアドレスにジャンプします。
*   **`TEXT`**: アセンブリコードで関数の開始を宣言するディレクティブ。
*   **`SB` (Static Base)**: グローバルシンボルや静的データへのオフセットを計算するためのベースレジスタ。
*   **`FP` (Frame Pointer)**: 現在のスタックフレームのベースアドレスを指すレジスタ。
*   **`SP` (Stack Pointer)**: 現在のスタックのトップを指すレジスタ。
*   **`LR` (Link Register)**: 関数呼び出しからの戻りアドレスを保持するレジスタ。
*   **`PC` (Program Counter)**: 次に実行される命令のアドレスを保持するレジスタ。
*   **`CMP`**: 2つのオペランドを比較し、フラグレジスタを設定する命令。
*   **`BEQ` (Branch if Equal)**: 比較結果が等しい場合に分岐する命令。
*   **`B.NE` (Branch if Not Equal)**: 比較結果が等しくない場合に分岐する命令。
*   **`MRC` (Move from Coprocessor to Register)**: コプロセッサからレジスタへデータを移動する命令。ARMでは、TLSベースポインタの取得にシステムコプロセッサが使用されることがあります。

## 技術的詳細

このコミットの核心は、ARMアーキテクチャにおける`g`レジスタ（`r10`）とTLSに保存されている`g`ポインタの同期を強化することです。

従来のGoランタイムでは、`g`レジスタが変更された際に、必ずしもその変更がTLSに反映されるわけではありませんでした。特に、`runtime.gogo`や`runtime.mcall`、`runtime.morestack`、`runtime.lessstack`、`asmcgocall`といった、ゴルーチンやMのコンテキストを切り替える重要なアセンブリ関数において、`g`レジスタの更新とTLSへの保存が分離されているか、あるいはTLSへの保存が省略されているケースがありました。

問題は、シグナルハンドラが非同期に割り込む可能性がある点にあります。シグナルハンドラは、現在の実行中のゴルーチン（`m->curg`）のコンテキストで発生しますが、TLSに保存されている`g`が`m->g0`を指していると、シグナルハンドラがTLSから`g`を再ロードした際に誤ったゴルーチンコンテキスト（`m->g0`）を取得してしまいます。

これにより、`m->curg`のスタックで実行しているにもかかわらず、ランタイムが`m->g0`のコンテキストで動作しようとするという矛盾が生じます。特に`sigpanic`がスタック分割チェックを行う際、現在のスタックポインタが`m->g0`のスタック範囲外にあると判断され、`morestack`が呼び出されます。`morestack`は`g=m->g0`であると認識し、`m->g0`のスタックを拡張しようとしますが、これは通常、`m->g0`のスタックは固定サイズであるため、プログラムのクラッシュにつながります。

この修正では、`asm_arm.s`内の`g`レジスタへのすべての代入（`MOVW`命令）を、新しいヘルパー関数`setg<>(SB)`の呼び出しに置き換えます。`setg<>(SB)`は、`g`レジスタを更新するだけでなく、その更新された`g`の値を直ちにTLSにも保存することを保証します。これにより、`g`レジスタとTLSの`g`ポインタが常に同期されるようになり、シグナルハンドラがTLSから`g`をロードする際に常に正しいゴルーチンコンテキストを取得できるようになります。

また、`src/pkg/runtime/arch_arm.h`の`RuntimeGogoBytes`が`84`から`60`に減少しています。これは、`runtime.gogo`関数内でスタックに保存されるレジスタの数が変更されたことを示唆しており、おそらく`setg`関数の導入によるスタックフレームの調整に関連している可能性があります。

`src/pkg/runtime/tls_arm.s`では、`runtime·save_g`関数が`g`の値を`R0`レジスタに保持して戻るように変更されています。これは、`setg`関数が`runtime·save_g`を呼び出した後に`g`の値を再利用できるようにするためです。

## コアとなるコードの変更箇所

主要な変更は以下の3つのファイルにわたります。

1.  **`src/pkg/runtime/arch_arm.h`**:
    *   `RuntimeGogoBytes`の値が`84`から`60`に減少。

2.  **`src/pkg/runtime/asm_arm.s`**:
    *   `runtime·gogo`、`runtime·mcall`、`runtime·morestack`、`runtime·lessstack`、`asmcgocall`などの関数内で、`g`レジスタに直接値を代入していた`MOVW`命令の多くが、`setg<>(SB)`関数への`BL`（Branch with Link）呼び出しに置き換えられています。
    *   新しいヘルパー関数`setg<>(SB)`が追加されています。この関数は、引数として渡された`g`の値を`g`レジスタに設定し、さらに`runtime·save_g`を呼び出してその値をTLSに保存します。
    *   `runtime·setg`という既存の関数が、`setg<>(SB)`を呼び出すように変更されています。

3.  **`src/pkg/runtime/tls_arm.s`**:
    *   `runtime·save_g`関数のシグネチャが変更され、`g`の値を`R0`レジスタに保持して戻るようになりました。これにより、呼び出し元が`g`の値を再利用できるようになります。

## コアとなるコードの解説

### `src/pkg/runtime/asm_arm.s` の変更

最も重要な変更は、`g`レジスタへの直接的な代入を`setg<>(SB)`関数への呼び出しに置き換えた点です。

**変更前（例: `runtime·gogo`内）:**

```armasm
	MOVW	gobuf_g(R1), g
	MOVW	0(g), R2		// make sure g != nil
	MOVB	runtime·iscgo(SB), R2
	CMP 	$0, R2 // if in Cgo, we have to save g
	BL.NE	runtime·save_g(SB) // this call will clobber R0
```

ここでは、`gobuf_g(R1)`から`g`レジスタに直接値をロードし、その後Cgoが有効な場合にのみ`runtime·save_g`を条件付きで呼び出していました。

**変更後（例: `runtime·gogo`内）:**

```armasm
	MOVW	gobuf_g(R1), R0
	BL	setg<>(SB)
```

変更後では、まず`gobuf_g(R1)`の値を`R0`レジスタにロードし、その後無条件に`setg<>(SB)`を呼び出しています。

**新しく追加された `setg<>(SB)` 関数:**

```armasm
TEXT setg<>(SB),NOSPLIT,$-4-0
	MOVW	R0, g

	// Save g to thread-local storage.
	MOVB	runtime·iscgo(SB), R0
	CMP	$0, R0
	B.EQ	2(PC)
	B	runtime·save_g(SB)

	MOVW	g, R0
	RET
```

この`setg<>(SB)`関数は以下の処理を行います。
1.  `MOVW R0, g`: 引数として`R0`に渡された新しい`g`の値を`g`レジスタに設定します。
2.  `Save g to thread-local storage.`: ここが重要な部分です。
    *   `MOVB runtime·iscgo(SB), R0`: `iscgo`（Cgoが有効かどうかを示すフラグ）の値を`R0`にロードします。
    *   `CMP $0, R0`: `R0`が0（Cgoが無効）かどうかを比較します。
    *   `B.EQ 2(PC)`: もしCgoが無効であれば、次の2命令をスキップして`MOVW g, R0`にジャンプします（つまり`runtime·save_g`を呼び出しません）。
    *   `B runtime·save_g(SB)`: Cgoが有効であれば、`runtime·save_g`関数を呼び出して、現在の`g`の値をTLSに保存します。
3.  `MOVW g, R0`: `g`レジスタの値を`R0`にコピーして戻ります。これは、`setg`を呼び出した元のコードが`g`の値を`R0`で受け取れるようにするためです。

この変更により、`g`レジスタが変更されるたびに、その新しい値がTLSにも確実に保存されるようになります。これにより、シグナルハンドラがTLSから`g`をロードする際に、常に最新かつ正しいゴルーチンコンテキストを取得できるようになり、前述のクラッシュが回避されます。

### `src/pkg/runtime/tls_arm.s` の変更

`runtime·save_g`関数の変更は、`setg<>(SB)`からの呼び出しに対応するためのものです。

**変更前:**

```armasm
TEXT runtime·save_g(SB),NOSPLIT,$0
// ...
	MOVW	g, 0(R0)
	RET
```

**変更後:**

```armasm
TEXT runtime·save_g(SB),NOSPLIT,$-4
// ...
	MOVW	g, 0(R0)
	MOVW	g, R0 // preserve R0 across call to setg<>
	RET
```

変更後では、TLSに`g`を保存した後、さらに`g`の値を`R0`レジスタにコピーしてから`RET`（戻り）しています。これは、`setg<>(SB)`が`runtime·save_g`を呼び出した後に、`g`の値を`R0`で受け取って、その後の処理（`MOVW g, R0`）で利用できるようにするためです。

### `src/pkg/runtime/arch_arm.h` の変更

`RuntimeGogoBytes`の減少は、`runtime.gogo`関数がスタックに保存するレジスタの数が減ったことを示唆しています。これは、`setg`関数の導入により、一部のレジスタの保存/復元ロジックが変更された結果として、スタックフレームのサイズが最適化された可能性を示しています。

# [インデックス 25497] ファイルの概要

このコミットは、Goランタイムの内部パッケージ `internal/syscall/unix` における乱数生成のためのシステムコール番号 (`randomTrap`) の初期化方法を改善し、`arm64` アーキテクチャで `getrandom` システムコールを有効にすることを目的としています。具体的には、これまでの `map` を用いた動的な初期化を、各アーキテクチャ固有のファイルで `const` 定数として直接定義する方法に変更することで、初期化の複雑さを排除しています。

## 変更の背景

このコミットには主に二つの背景があります。

1.  **`randomTrap` の初期化の複雑さの解消**: 以前の `randomTrap` の定義は、`runtime.GOARCH` の値に基づいて `map` からシステムコール番号を取得する形式でした。このような `map` を用いた初期化は、コンパイル時に定数として解決されず、実行時に初期化ロジックが必要となるため、「非自明な初期化 (non-trivial initializer)」と見なされていました。Goのランタイムや低レベルのシステムコールラッパーでは、可能な限り静的な初期化や定数を用いることがパフォーマンスやコードの単純さの観点から好まれます。このコミットは、この動的な初期化を排除し、よりシンプルで効率的な定数による定義に置き換えることを目的としています。

2.  **`arm64` アーキテクチャでの `getrandom` システムコールの有効化**: `getrandom` は、Linuxカーネルが提供するセキュアな乱数生成のためのシステムコールです。以前は `arm64` アーキテクチャにおいてこのシステムコールがGoランタイムから利用可能になっていませんでした。この変更により、`arm64` 環境でも `getrandom` を利用できるようになり、より高品質でセキュアな乱数生成が可能になります。これは、特に暗号関連の処理やセキュリティが要求されるアプリケーションにおいて重要です。コミットメッセージでは、`include/uapi/asm-generic/unistd.h` から `arm64` のシステムコール番号を取得したと述べられており、これはLinuxカーネルのヘッダーファイルを参照して正しい番号を特定したことを示しています。

`Updates #10848` とありますが、Goの公開されているIssueトラッカーでこの番号の具体的なIssueを見つけることはできませんでした。しかし、通常 `Updates #XXXXX` は、特定のバグ修正や機能追加のIssueに対応する変更であることを示します。この場合、`randomTrap` の初期化の改善や `arm64` サポートの追加が、何らかの形で報告されていた問題や要望に対応するものと考えられます。

## 前提知識の解説

### `getrandom` システムコール

`getrandom` は、Linuxカーネル 3.17 以降で導入されたシステムコールで、暗号学的に安全な乱数（CSPRNG: Cryptographically Secure PseudoRandom Number Generator）を生成するために使用されます。従来の `/dev/random` や `/dev/urandom` と比較して、より安全かつ効率的に乱数を取得できる点が特徴です。特に、エントロピーが不足している場合にブロックするかどうかをフラグで制御できるなど、柔軟な利用が可能です。

### Goにおける `syscall` の利用

Go言語は、低レベルのシステムコールを直接呼び出すための `syscall` パッケージ（現在は `golang.org/x/sys/unix` や `internal/syscall/unix` などに分割・再編成されている）を提供しています。これにより、GoプログラムからOSの機能（ファイル操作、ネットワーク通信、プロセス管理、乱数生成など）を直接利用できます。システムコールを呼び出す際には、システムコール番号と引数を指定してカーネルに処理を依頼します。

### `GOARCH` とクロスコンパイル

`GOARCH` はGoの環境変数の一つで、ターゲットとするCPUアーキテクチャ（例: `amd64`, `386`, `arm`, `arm64`, `ppc64`, `ppc64le` など）を指定します。Goはクロスコンパイルを強力にサポートしており、例えば `GOOS=linux GOARCH=arm64 go build` のように指定することで、現在の環境とは異なるOSやアーキテクチャ向けのバイナリを生成できます。システムコール番号はアーキテクチャによって異なるため、`GOARCH` に応じて適切なシステムコール番号を選択する必要があります。

### Goのビルドタグ（`+build` ディレクティブ）

Goでは、ソースファイルの先頭に `// +build tag` の形式でビルドタグを記述することで、特定の条件が満たされた場合にのみそのファイルをコンパイル対象に含めることができます。例えば、`// +build linux,amd64` と書かれたファイルは、OSがLinuxでアーキテクチャがAMD64の場合にのみコンパイルされます。この機能は、OSやアーキテクチャに依存するコードを分離し、クロスプラットフォーム対応を容易にするために広く利用されています。

### システムコール番号

システムコール番号は、各システムコールに割り当てられた一意の識別子です。ユーザー空間のプログラムがシステムコールを呼び出す際、この番号を使ってどのカーネル機能を利用したいかを指定します。システムコール番号はOSやCPUアーキテクチャによって異なるため、移植性の高いコードを書く際にはこれらの違いを考慮する必要があります。Linuxカーネルのヘッダーファイル（例: `include/uapi/asm-generic/unistd.h`）には、これらのシステムコール番号が定義されています。

## 技術的詳細

このコミットの主要な技術的変更点は、`randomTrap` 変数の初期化方法の変更と、それに関連するファイル構造の再編成です。

### `randomTrap` の初期化方法の変更点

変更前は、`src/internal/syscall/unix/getrandom_linux.go` ファイル内で以下のように `map` を使用して `randomTrap` が初期化されていました。

```go
var randomTrap = map[string]uintptr{
	"386":     355,
	"amd64":   318,
	"arm":     384,
	"ppc64":   359,
	"ppc64le": 359,
}[runtime.GOARCH]
```

このコードは、`runtime.GOARCH` の値（現在のビルドターゲットのアーキテクチャ）に基づいて、対応するシステムコール番号を `map` からルックアップして `randomTrap` に代入します。これは実行時に行われる処理であり、コンパイル時に定数として解決されるわけではありません。

変更後は、この `map` による初期化が削除され、代わりに各アーキテクチャ専用のファイルが作成され、その中で `randomTrap` が `const` 定数として直接定義されるようになりました。例えば、`src/internal/syscall/unix/getrandom_linux_amd64.go` では以下のようになります。

```go
const randomTrap uintptr = 318
```

### なぜ `map` が「非自明な初期化」と見なされたのか

`map` を使用した初期化は、以下の理由から「非自明 (non-trivial)」と見なされます。

*   **実行時コスト**: `map` の作成、ルックアップ、および `runtime.GOARCH` の評価は、コンパイル時ではなくプログラムの実行時に行われます。これは、低レベルのシステムコールラッパーのようなパフォーマンスが重視される部分ではオーバーヘッドとなり得ます。
*   **コンパイル時最適化の妨げ**: コンパイラは、定数として定義された値に対してより積極的な最適化を適用できます。`map` を介した動的な初期化は、このような最適化の機会を減少させます。
*   **コードの複雑さ**: 各アーキテクチャ固有のシステムコール番号は、ビルド時に既に決定されている情報です。それを動的にルックアップするロジックは、本質的に不要な複雑さを導入します。

`const` 定数として直接定義することで、これらの問題が解消され、コードがよりシンプルで効率的になります。

### `arm64` での `getrandom` 有効化の詳細

このコミットでは、`arm64` アーキテクチャ向けに `getrandom` システムコールが有効化されました。具体的には、`src/internal/syscall/unix/getrandom_linux_generic.go` という新しいファイルが作成され、その中で `arm64` 用の `randomTrap` が定義されています。

```go
// +build arm64

package unix

const randomTrap uintptr = 278
```

ここで注目すべきは、ファイルの先頭にある `// +build arm64` というビルドタグです。これにより、このファイルは `GOARCH=arm64` でビルドされる場合にのみコンパイル対象となります。`arm64` の `getrandom` システムコール番号は `278` であると定義されています。この値は、Linuxカーネルのヘッダーファイル `include/uapi/asm-generic/unistd.h` を参照して特定されたものです。

### 各アーキテクチャごとの `randomTrap` の定義

この変更により、各アーキテクチャ（`386`, `amd64`, `arm`, `arm64`, `ppc64`/`ppc64le`）ごとに個別のファイルが作成され、それぞれに適切な `randomTrap` の値が `const` 定数として定義されました。これにより、Goのビルドシステムが `GOARCH` の値に基づいて適切なファイルをコンパイルに含めることで、正しいシステムコール番号が選択されるようになります。

## コアとなるコードの解説

### `src/internal/syscall/unix/getrandom_linux.go` の変更

このファイルからは、`randomTrap` を `map` で初期化していた部分が完全に削除されました。これにより、このファイルは `randomTrap` の具体的な値を持たなくなり、共通のロジック（`randomUnsupported` 変数や `GetRandomFlag` 定数など）のみを保持する形になりました。

### 新規作成されたアーキテクチャ固有のファイル群

以下のファイルが新規に作成されました。

*   `src/internal/syscall/unix/getrandom_linux_386.go`
*   `src/internal/syscall/unix/getrandom_linux_amd64.go`
*   `src/internal/syscall/unix/getrandom_linux_arm.go`
*   `src/internal/syscall/unix/getrandom_linux_generic.go` (主に `arm64` 用)
*   `src/internal/syscall/unix/getrandom_linux_ppc64x.go` (`ppc64` および `ppc64le` 用)

これらのファイルは、それぞれ対応する `GOARCH` のビルドタグ（例: `// +build 386` や `// +build arm64`）を持ち、そのアーキテクチャにおける `getrandom` システムコールの番号を `const randomTrap uintptr = <syscall_number>` の形式で直接定義しています。

例えば、`src/internal/syscall/unix/getrandom_linux_amd64.go` の内容は以下の通りです。

```go
// Copyright 2014 The Go Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package unix

const randomTrap uintptr = 318
```

この構造により、Goコンパイラはビルドターゲットのアーキテクチャに応じて、これらのファイルの中から適切な `randomTrap` の定義を含むファイルのみをコンパイルに含めることができます。これにより、実行時のルックアップが不要となり、より効率的でシンプルなコードベースが実現されました。特に `arm64` のサポートが追加されたことで、このアーキテクチャ上での乱数生成のセキュリティとパフォーマンスが向上しました。

# [インデックス 20335] ファイルの概要

このコミットは、Goランタイムのプロファイリング機能、特にメモリプロファイリングとブロッキングプロファイリングに関するコードベースの重要な変更を扱っています。具体的には、プロファイリングロジックの実装が、C言語のような構文を持つ`.goc`ファイルから、純粋なGo言語で記述された`.go`ファイルへと移行されています。これにより、Goランタイムのプロファイリング部分がよりGoらしいイディオムに準拠し、メンテナンス性と可読性が向上することが期待されます。

## コミット

Goランタイムのプロファイリング実装を`mprof.goc`から`mprof.go`へ変換。
`mprof.go`に現れるエクスポートされたGoの定義は、`debug.go`からそのままコピーされています。
エクスポートされていないGoの関数と型は新規です。
C言語の`Bucket`型は共用体を使用しており、逐語的な変換ではありませんでした。

## 変更の背景

このコミットの主な背景は、Goランタイムのコードベースをより純粋なGo言語で記述することへの継続的な取り組みです。初期のGoランタイムには、C言語の構文とGo言語の構文が混在する`.goc`ファイルが多数存在しました。これらは、Go言語がまだ成熟していなかった時期に、低レベルのシステムプログラミングやOSとのインタラクションを容易にするために導入されたものです。

しかし、Go言語が進化し、その表現力と機能が向上するにつれて、`.goc`ファイルの必要性は薄れていきました。`.goc`ファイルは、Goの通常のツールチェーンでは直接扱えず、特別なビルドステップを必要とするため、ビルドプロセスの複雑性を増し、Go開発者にとっての学習コストとなっていました。また、C言語のイディオムが混在することで、純粋なGoコードと比較して可読性やメンテナンス性が低下する可能性がありました。

このコミットは、プロファイリングというGoアプリケーションのパフォーマンス分析に不可欠な機能のコア部分を、よりGoらしい方法で再実装することで、ランタイム全体の整合性を高め、将来的な機能拡張や最適化を容易にすることを目的としています。特に、C言語の`union`のようなGoには直接存在しない概念を、Goの型システムでどのように表現し直すかという課題に取り組んでいます。

## 前提知識の解説

### Goランタイム

Goランタイムは、Goプログラムの実行を管理するソフトウェア層です。これには、ガベージコレクタ、スケジューラ（ゴルーチンの管理）、メモリ管理、プリミティブな同期メカニズム、システムコールインターフェースなどが含まれます。Goプログラムは、オペレーティングシステム上で直接実行されるのではなく、このランタイム上で動作します。ランタイムはGo言語自体で記述されており、一部の低レベルな部分はアセンブリ言語やC言語（かつては`.goc`ファイルも）で記述されていました。

### Goにおけるプロファイリング

Goは、プログラムのパフォーマンス特性を分析するための強力なプロファイリングツールを標準で提供しています。主なプロファイリングの種類には以下があります。

*   **CPUプロファイリング**: プログラムがCPU時間をどこで消費しているかを特定します。
*   **メモリプロファイリング**: プログラムがメモリをどのように割り当て、使用しているかを分析します。リークの特定やメモリ使用量の最適化に役立ちます。
*   **ブロッキングプロファイリング**: ゴルーチンが同期プリミティブ（ミューテックス、チャネルなど）によってブロックされている時間を測定します。並行処理のボトルネックを特定するのに役立ちます。
*   **Goroutineプロファイリング**: 実行中のゴルーチンのスタックトレースを収集します。

これらのプロファイリングデータは、`runtime/pprof`パッケージを通じて利用可能であり、`go tool pprof`などのツールで可視化されます。

### `.goc`ファイル

`.goc`ファイルは、Go言語の初期のバージョンで使われていた特殊なファイル形式です。これらは、C言語のプリプロセッサによって処理されるGoコードであり、C言語のマクロや`union`のような構文をGoコード内で使用することを可能にしていました。Goランタイムの低レベルな部分、特にOSとのインタラクションやハードウェアに近い部分の実装に用いられていました。しかし、Go言語の進化とともに、これらのファイルは徐々に純粋なGoコードに置き換えられていきました。`.goc`ファイルは、Goのビルドシステムにおいて特別な扱いが必要であり、通常のGoコードとは異なるコンパイルパスを辿っていました。

### C言語の`union`

C言語の`union`（共用体）は、異なる型の複数のメンバーが同じメモリ領域を共有する特殊なデータ型です。`union`のサイズは、そのメンバーの中で最も大きい型のサイズによって決まります。一度に`union`のメンバーのうち1つだけが有効な値を保持すると想定されており、メモリを節約するために使用されます。Go言語には`union`に直接対応する構文はありませんが、同様の機能は、インターフェース型、空のインターフェース（`interface{}`）、または構造体内のフィールドの組み合わせによって実現されることがあります。

### `Bucket`データ構造

プロファイリングにおいて、`Bucket`（バケット）は特定のコールスタック（スタックトレース）に関連付けられたプロファイリング情報を保持するためのデータ構造です。プログラムの実行中に、特定の関数呼び出しシーケンス（スタックトレース）で発生したメモリ割り当てやブロッキングイベントが、対応するバケットに集計されます。これにより、どのコードパスがリソースを多く消費しているかを特定できます。各バケットは、そのスタックトレースのハッシュ値に基づいてハッシュテーブルに格納され、効率的なルックアップを可能にします。

## 技術的詳細

このコミットの核心は、Goランタイムのプロファイリングメカニズムを、C言語のイディオムが混在する`mprof.goc`から、純粋なGo言語で記述された`mprof.go`へと移行した点にあります。この移行は、単なるファイル形式の変更以上の意味を持ちます。

### `mprof.goc`から`mprof.go`への変換プロセス

*   **C言語構文の除去**: `mprof.goc`ファイルには、C言語の`#include`ディレクティブ、`enum`、`struct`、`union`、そしてC言語スタイルの関数定義などが含まれていました。これらの要素は、Go言語の対応する構文に置き換えられました。
*   **Goらしいデータ構造への変換**: 特に顕著なのが、C言語の`union`を使用していた`Bucket`構造体の変換です。Goには`union`が直接存在しないため、`Bucket`型は、プロファイリングの種類（メモリプロファイルかブロッキングプロファイルか）を示す`typ`フィールドと、それぞれのプロファイルデータに対応する`memRecord`と`blockRecord`という独立した構造体を持つように再設計されました。`Bucket`構造体自体は、これらのレコードデータへのポインタを直接保持するのではなく、`unsafe.Pointer`とポインタ演算を用いて、`Bucket`構造体の直後に続くメモリ領域にレコードデータが配置されるという、より低レベルなメモリレイアウトを採用しています。これは、C言語の`union`がメモリを共有する特性をGoで模倣するための効率的な方法です。
*   **関数シグネチャの調整**: C言語スタイルの関数シグネチャは、Goの関数シグネチャに変換されました。例えば、ポインタの渡し方や、`bool`型などのGoの組み込み型への変更が行われました。
*   **Goの組み込み機能の活用**: `eqslice`のようなスライス比較のためのヘルパー関数が導入され、Goのスライス操作が活用されています。また、`atomicstore64`のようなアトミック操作もGoの`sync/atomic`パッケージの概念に沿って使用されています。

### `Bucket`データ構造の再設計

旧来の`mprof.goc`では、`Bucket`構造体内に`union`を用いて`MProfRecord`（メモリプロファイル用）と`BProfRecord`（ブロッキングプロファイル用）を切り替えていました。

```c
struct Bucket
{
    // ...
    union
    {
        struct MProfRecord mp;
        struct BProfRecord bp;
    } data;
    // ...
};
```

これが`mprof.go`では、以下のように再設計されました。

```go
type bucket struct {
	next    *bucket
	allnext *bucket
	typ     bucketType // memBucket or blockBucket
	hash    uintptr
	size    uintptr
	nstk    uintptr
}

type memRecord struct {
	// ... memory profiling stats ...
}

type blockRecord struct {
	// ... blocking profiling stats ...
}

// mp returns the memRecord associated with the memProfile bucket b.
func (b *bucket) mp() *memRecord {
	if b.typ != memProfile {
		gothrow("bad use of bucket.mp")
	}
	data := add(unsafe.Pointer(b), unsafe.Sizeof(*b)+b.nstk*unsafe.Sizeof(uintptr(0)))
	return (*memRecord)(data)
}

// bp returns the blockRecord associated with the blockProfile bucket b.
func (b *bucket) bp() *blockRecord {
	if b.typ != blockProfile {
		gothrow("bad use of bucket.bp")
	}
	data := add(unsafe.Pointer(b), unsafe.Sizeof(*b)+b.nstk*unsafe.Sizeof(uintptr(0)))
	return (*blockRecord)(data)
}
```

この新しい設計では、`bucket`構造体自体はプロファイルの種類を示す`typ`フィールドを持ち、実際のプロファイルデータ（`memRecord`または`blockRecord`）は`bucket`構造体の直後のメモリ領域に配置されます。`mp()`と`bp()`メソッドは、`unsafe.Pointer`とポインタ演算を使用して、このメモリ領域を適切な型として解釈し、アクセスを提供します。これにより、C言語の`union`が提供していたメモリ効率をGoで実現しつつ、Goの型システムに適合させています。

### その他の変更点

*   **`debug.go`からの定義の移動**: `MemProfileRate`, `MemProfileRecord`, `StackRecord`, `BlockProfileRecord`, `SetBlockProfileRate`, `GoroutineProfile`といった、Goのユーザーランドからアクセスされるプロファイリング関連の型や関数が、`debug.go`から`mprof.go`に移動されました。これにより、プロファイリング関連のコードが一箇所に集約され、モジュール性が向上しています。
*   **`allgs`スライスの導入**: `src/pkg/runtime/proc.c`では、`runtime·allg`という`G**`（ゴルーチンへのポインタの配列）に加えて、`Slice runtime·allgs`というGoのスライスが導入されました。これは、Goのランタイム内部でゴルーチンリストをGoのスライスとして扱うことで、よりGoらしいイディオムでアクセスできるようにするための変更です。
*   **`malloc.go`と`malloc.h`の変更**: メモリ割り当てプロファイリングに関連する`MProf_Malloc`などの関数呼び出しが、新しいGoの関数名（`mProf_Malloc`）に更新されました。また、`malloc.h`からプロファイリング関連の宣言が削除されました。
*   **`heapdump.c`、`mgc0.c`、`mheap.c`の変更**: これらのファイルでも、プロファイリング関連のC関数呼び出しが、新しいGoの関数名に更新されています。
*   **`src/cmd/api/goapi.go`の変更**: `goapi.go`はGoのAPI定義を生成するツールの一部であり、`Bucket`構造体がGoのAPIから削除されたことを反映しています。これは、`Bucket`がランタイム内部のデータ構造となり、直接APIとして公開されなくなったことを示唆しています。

これらの変更は、Goランタイムの内部構造をよりGoらしく、よりクリーンに保つための継続的な努力の一環です。これにより、将来的なランタイムの改善や、プロファイリング機能の拡張がより容易になります。

## コアとなるコードの解説

### `mprof.go`における`bucket`構造体と関連メソッド

このコミットの最も重要な変更は、プロファイリングデータの格納方法です。C言語の`union`は、異なる型のデータを同じメモリ位置に格納することを可能にし、メモリ効率を高めます。Goには`union`が直接存在しないため、このコミットでは`unsafe.Pointer`とポインタ演算を駆使して、C言語の`union`と同様のメモリレイアウトを実現しています。

`bucket`構造体は、プロファイリングの種類（`memProfile`または`blockProfile`）を示す`typ`フィールドを持ちます。実際のプロファイリングデータ（メモリ割り当て統計やブロッキング統計）は、`bucket`構造体の直後のメモリ領域に連続して配置されます。

*   `mp()`メソッドは、`bucket`の`typ`が`memProfile`であることを確認した後、`unsafe.Pointer(b)`（`bucket`構造体のアドレス）に`unsafe.Sizeof(*b)`（`bucket`構造体のサイズ）と`b.nstk*unsafe.Sizeof(uintptr(0))`（スタックトレースのサイズ）を加算することで、`memRecord`が格納されているメモリ位置を計算し、そのポインタを返します。
*   同様に、`bp()`メソッドは`blockRecord`へのポインタを返します。

このアプローチにより、Goの型安全性を一部犠牲にしつつも（`unsafe`パッケージの使用）、C言語の`union`が提供していたメモリ効率と柔軟性をGoで実現しています。これは、Goランタイムのようなパフォーマンスが非常に重要な低レベルコードにおいて、妥協点として採用されることがあります。

### `stkbucket`関数

`stkbucket`関数は、与えられたスタックトレース、サイズ、プロファイルタイプに基づいて、既存の`bucket`をハッシュテーブルから検索するか、新しい`bucket`を作成して返します。

1.  **ハッシュ計算**: スタックトレースの各要素とサイズを組み合わせてハッシュ値を計算します。これにより、同じスタックトレースとサイズを持つ割り当ては同じバケットに集約されます。
2.  **既存バケットの検索**: 計算されたハッシュ値とスタックトレースの内容が一致する既存のバケットをハッシュテーブルから検索します。
3.  **新規バケットの作成**: 既存のバケットが見つからない場合、`newBucket`関数を呼び出して新しいバケットを割り当て、ハッシュテーブルに追加します。この際、`persistentalloc`が使用されており、これはガベージコレクタの管理外のメモリを割り当てるためのランタイム内部関数です。プロファイリングデータはGCの対象外であるため、このように直接メモリを管理します。

### プロファイリング統計の更新ロジック

`mprof_GC`、`mProf_Malloc`、`mProf_Free`などの関数は、メモリプロファイリングの統計を更新するロジックを含んでいます。特に`memRecord`内の`allocs`, `frees`, `alloc_bytes`, `free_bytes`、そして`prev_`と`recent_`プレフィックスを持つフィールドは、Goのメモリプロファイリングがどのように割り当てと解放を追跡しているかを示しています。

*   **`recent_`**: 直近のGCサイクル以降の割り当て/解放。
*   **`prev_`**: 前回のGCサイクルと前々回のGCサイクルの間の割り当て/解放。
*   **`allocs`/`frees`**: オブジェクトの数。
*   **`alloc_bytes`/`free_bytes`**: バイト数。

`mprof_GC`が呼び出されると、`recent_`の統計が`prev_`に移動され、`prev_`の統計が最終的な`allocs`/`frees`に加算されます。これにより、GCのタイミングに依存しない、より正確なメモリ使用量のスナップショットを提供しようとしています。

### `SetBlockProfileRate`と`blockevent`

これらの関数はブロッキングプロファイリングに関連します。

*   `SetBlockProfileRate`は、ブロッキングイベントをプロファイルに記録する頻度を制御します。レートが低いほど、より多くのイベントが記録されます。
*   `blockevent`は、ゴルーチンがブロックされた際に呼び出され、そのイベントのサイクル数（ブロックされた時間）とスタックトレースを記録します。`fastrand1()`のようなランダム関数と`blockprofilerate`を用いて、サンプリングレートに基づいてイベントを記録するかどうかを決定します。

これらの変更は、Goランタイムのプロファイリング機能が、よりGoらしいコードベースで、かつ効率的に動作するように再構築されたことを示しています。

## 前提知識の解説

### Goランタイム

Goランタイムは、Goプログラムの実行を管理するソフトウェア層です。これには、ガベージコレクタ、スケジューラ（ゴルーチンの管理）、メモリ管理、プリミティブな同期メカニズム、システムコールインターフェースなどが含まれます。Goプログラムは、オペレーティングシステム上で直接実行されるのではなく、このランタイム上で動作します。ランタイムはGo言語自体で記述されており、一部の低レベルな部分はアセンブリ言語やC言語（かつては`.goc`ファイルも）で記述されていました。

### Goにおけるプロファイリング

Goは、プログラムのパフォーマンス特性を分析するための強力なプロファイリングツールを標準で提供しています。主なプロファイリングの種類には以下があります。

*   **CPUプロファイリング**: プログラムがCPU時間をどこで消費しているかを特定します。
*   **メモリプロファイリング**: プログラムがメモリをどのように割り当て、使用しているかを分析します。リークの特定やメモリ使用量の最適化に役立ちます。
*   **ブロッキングプロファイリング**: ゴルーチンが同期プリミティブ（ミューテックス、チャネルなど）によってブロックされている時間を測定します。並行処理のボトルネックを特定するのに役立ちます。
*   **Goroutineプロファイリング**: 実行中のゴルーチンのスタックトレースを収集します。

これらのプロファイリングデータは、`runtime/pprof`パッケージを通じて利用可能であり、`go tool pprof`などのツールで可視化されます。

### `.goc`ファイル

`.goc`ファイルは、Go言語の初期のバージョンで使われていた特殊なファイル形式です。これらは、C言語のプリプロセッサによって処理されるGoコードであり、C言語のマクロや`union`のような構文をGoコード内で使用することを可能にしていました。Goランタイムの低レベルな部分、特にOSとのインタラクションやハードウェアに近い部分の実装に用いられていました。しかし、Go言語の進化とともに、これらのファイルは徐々に純粋なGoコードに置き換えられていきました。`.goc`ファイルは、Goのビルドシステムにおいて特別な扱いが必要であり、通常のGoコードとは異なるコンパイルパスを辿っていました。

### C言語の`union`

C言語の`union`（共用体）は、異なる型の複数のメンバーが同じメモリ領域を共有する特殊なデータ型です。`union`のサイズは、そのメンバーの中で最も大きい型のサイズによって決まります。一度に`union`のメンバーのうち1つだけが有効な値を保持すると想定されており、メモリを節約するために使用されます。Go言語には`union`に直接対応する構文はありませんが、同様の機能は、インターフェース型、空のインターフェース（`interface{}`）、または構造体内のフィールドの組み合わせによって実現されることがあります。

### `Bucket`データ構造

プロファイリングにおいて、`Bucket`（バケット）は特定のコールスタック（スタックトレース）に関連付けられたプロファイリング情報を保持するためのデータ構造です。プログラムの実行中に、特定の関数呼び出しシーケンス（スタックトレース）で発生したメモリ割り当てやブロッキングイベントが、対応するバケットに集計されます。これにより、どのコードパスがリソースを多く消費しているかを特定できます。各バケットは、そのスタックトレースのハッシュ値に基づいてハッシュテーブルに格納され、効率的なルックアップを可能にします。

旧来の`mprof.goc`では、`Bucket`構造体内に`union`を用いて`MProfRecord`（メモリプロファイル用）と`BProfRecord`（ブロッキングプロファイル用）を切り替えていました。

    union
    {
        struct MProfRecord mp;
        struct BProfRecord bp;

    // ...
};
```

これが`mprof.go`では、以下のように再設計されました。

```go
type bucket struct {
	next    *bucket
	allnext *bucket
	typ     bucketType // memBucket or blockBucket
	hash    uintptr
	size    uintptr
	nstk    uintptr
}

type memRecord struct {
	// ... memory profiling stats ...
}

type blockRecord struct {
	// ... blocking profiling stats ...
}

// mp returns the memRecord associated with the memProfile bucket b.
func (b *bucket) mp() *memRecord {
	if b.typ != memProfile {
		gothrow("bad use of bucket.mp")
	}
	data := add(unsafe.Pointer(b), unsafe.Sizeof(*b)+b.nstk*unsafe.Sizeof(uintptr(0)))
	return (*memRecord)(data)
}

// bp returns the blockRecord associated with the blockProfile bucket b.
func (b *bucket) bp() *blockRecord {
	if b.typ != blockProfile {
		gothrow("bad use of bucket.bp")
	}
	data := add(unsafe.Pointer(b), unsafe.Sizeof(*b)+b.nstk*unsafe.Sizeof(uintptr(0)))
	return (*blockRecord)(data)
}

この新しい設計では、`bucket`構造体自体はプロファイルの種類を示す`typ`フィールドを持ち、実際のプロファイルデータ（`memRecord`または`blockRecord`）は`bucket`構造体の直後のメモリ領域に配置されます。`mp()`と`bp()`メソッドは、`unsafe.Pointer`とポインタ演算を使用して、このメモリ領域を適切な型として解釈し、アクセスを提供します。これにより、C言語の`union`が提供していたメモリ効率をGoで実現しつつ、Goの型システムに適合させています。

## コアとなるコードの解説

### `mprof.go`における`bucket`構造体と関連メソッド

このコミットの最も重要な変更は、プロファイリングデータの格納方法です。C言語の`union`は、異なる型のデータを同じメモリ位置に格納することを可能にし、メモリ効率を高めます。Goには`union`が直接存在しないため、このコミットでは`unsafe.Pointer`とポインタ演算を駆使して、C言語の`union`と同様のメモリレイアウトを実現しています。

`bucket`構造体は、プロファイリングの種類（`memProfile`または`blockProfile`）を示す`typ`フィールドを持ちます。実際のプロファイリングデータ（メモリ割り当て統計やブロッキング統計）は、`bucket`構造体の直後のメモリ領域に連続して配置されます。

*   `mp()`メソッドは、`bucket`の`typ`が`memProfile`であることを確認した後、`unsafe.Pointer(b)`（`bucket`構造体のアドレス）に`unsafe.Sizeof(*b)`（`bucket`構造体のサイズ）と`b.nstk*unsafe.Sizeof(uintptr(0))`（スタックトレースのサイズ）を加算することで、`memRecord`が格納されているメモリ位置を計算し、そのポインタを返します。
*   同様に、`bp()`メソッドは`blockRecord`へのポインタを返します。

このアプローチにより、Goの型安全性を一部犠牲にしつつも（`unsafe`パッケージの使用）、C言語の`union`が提供していたメモリ効率と柔軟性をGoで実現しています。これは、Goランタイムのようなパフォーマンスが非常に重要な低レベルコードにおいて、妥協点として採用されることがあります。

### `stkbucket`関数

`stkbucket`関数は、与えられたスタックトレース、サイズ、プロファイルタイプに基づいて、既存の`bucket`をハッシュテーブルから検索するか、新しい`bucket`を作成して返します。

1.  **ハッシュ計算**: スタックトレースの各要素とサイズを組み合わせてハッシュ値を計算します。これにより、同じスタックトレースとサイズを持つ割り当ては同じバケットに集約されます。
2.  **既存バケットの検索**: 計算されたハッシュ値とスタックトレースの内容が一致する既存のバケットをハッシュテーブルから検索します。
3.  **新規バケットの作成**: 既存のバケットが見つからない場合、`newBucket`関数を呼び出して新しいバケットを割り当て、ハッシュテーブルに追加します。この際、`persistentalloc`が使用されており、これはガベージコレクタの管理外のメモリを割り当てるためのランタイム内部関数です。プロファイリングデータはGCの対象外であるため、このように直接メモリを管理します。

### プロファイリング統計の更新ロジック

`mprof_GC`、`mProf_Malloc`、`mProf_Free`などの関数は、メモリプロファイリングの統計を更新するロジックを含んでいます。特に`memRecord`内の`allocs`, `frees`, `alloc_bytes`, `free_bytes`、そして`prev_`と`recent_`プレフィックスを持つフィールドは、Goのメモリプロファイリングがどのように割り当てと解放を追跡しているかを示しています。

*   **`recent_`**: 直近のGCサイクル以降の割り当て/解放。
*   **`prev_`**: 前回のGCサイクルと前々回のGCサイクルの間の割り当て/解放。
*   **`allocs`/`frees`**: オブジェクトの数。
*   **`alloc_bytes`/`free_bytes`**: バイト数。

`mprof_GC`が呼び出されると、`recent_`の統計が`prev_`に移動され、`prev_`の統計が最終的な`allocs`/`frees`に加算されます。これにより、GCのタイミングに依存しない、より正確なメモリ使用量のスナップショットを提供しようとしています。

### `SetBlockProfileRate`と`blockevent`

これらの関数はブロッキングプロファイリングに関連します。

*   `SetBlockProfileRate`は、ブロッキングイベントをプロファイルに記録する頻度を制御します。レートが低いほど、より多くのイベントが記録されます。
*   `blockevent`は、ゴルーチンがブロックされた際に呼び出され、そのイベントのサイクル数（ブロックされた時間）とスタックトレースを記録します。`fastrand1()`のようなランダム関数と`blockprofilerate`を用いて、サンプリングレートに基づいてイベントを記録するかどうかを決定します。

これらの変更は、Goランタイムのプロファイリング機能が、よりGoらしいコードベースで、かつ効率的に動作するように再構築されたことを示しています。

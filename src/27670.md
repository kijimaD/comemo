## 変更の背景

Goコンパイラは、プログラムの実行効率を最大化するために様々な最適化を行います。その一つが「定数畳み込み（Constant Folding）」です。これは、コンパイル時に値が確定する式を事前に計算し、その結果をコードに直接埋め込むことで、実行時の計算を不要にする最適化手法です。

このコミットの背景には、`CMPconst`（定数との比較）と`SHR`（右シフト）という二つの操作が組み合わされたパターンにおいて、より積極的な定数畳み込みを適用する機会があるという認識がありました。特に、右シフトの結果が比較対象の定数に対して十分に小さい場合、比較の結果は常に真または偽のいずれかになることがコンパイル時に判断できます。

このような最適化は、特にハッシュ関数（例: MurmurHashのミキシング処理）やビット演算を多用するアルゴリズム（例: De Bruijnシーケンスを用いた整数Log2計算）において、頻繁に現れるパターンに効果を発揮します。これらのアルゴリズムでは、ビットシフトがデータの分布を均一化したり、特定のビットパターンを抽出したりするために不可欠な操作であり、その結果に対する比較が最適化されることで、全体的なパフォーマンス向上が期待されます。

GoコンパイラのSSAバックエンドは、プログラムをSSA形式で表現し、この形式に対して様々な最適化ルール（リライトルール）を適用します。このコミットは、AMD64アーキテクチャ向けのリライトルールに新しいエントリを追加することで、上記の特定のパターンを認識し、最適化された形式に変換することを目的としています。

## 前提知識の解説

### 1. GoコンパイラのSSAバックエンドとリライトルール

Goコンパイラは、ソースコードを中間表現に変換し、最終的に機械語を生成します。この過程で重要な役割を果たすのがSSA（Static Single Assignment）形式です。SSA形式では、各変数が一度だけ代入されるように表現され、データフロー解析や最適化が容易になります。

SSAバックエンドでは、「リライトルール（Rewrite Rules）」と呼ばれる一連の規則が適用されます。これらのルールは、SSAグラフ内の特定のパターン（オペレーションの組み合わせ）を検出し、より効率的な同等のパターンに置き換えることで最適化を行います。リライトルールは、`cmd/compile/internal/ssa/gen/*.rules`ファイルにLispのようなS式で記述され、`rulegen.go`ツールによってGoのソースコード（例: `rewriteAMD64.go`）に変換されます。この生成されたGoコードが、コンパイラのSSA最適化フェーズで実際に実行されます。

### 2. 定数畳み込み (Constant Folding)

定数畳み込みは、コンパイル時に値が確定する式を評価し、その結果を直接コードに埋め込むコンパイラ最適化です。例えば、`x = 1 + 2`という式があれば、コンパイラはこれを`x = 3`に変換します。これにより、実行時に加算を行う必要がなくなり、プログラムの速度が向上します。このコミットでは、`CMPconst`と`SHR`の組み合わせにおいて、シフトの結果が定数と比較して十分に小さい場合に、比較結果を定数として畳み込むことを目指しています。

### 3. MurmurHashのミキシング処理と高位ビットの重要性

MurmurHashは、高速で衝突耐性の高い非暗号学的ハッシュ関数です。ハッシュ関数の目的は、入力データを均一に分散された固定長の出力（ハッシュ値）に変換することです。MurmurHashのようなハッシュ関数では、「ミキシング処理」と呼ばれる一連のビット演算（乗算、XOR、シフトなど）を用いて、入力データの各ビットがハッシュ値のすべてのビットに影響を与えるようにします（アバランシェ効果）。

特に「高位ビットが望ましい」とされるのは、ハッシュ値のすべてのビットが均一に分布していることが、ハッシュテーブルの性能や衝突の最小化に不可欠だからです。もし低位ビットだけがよく分布し、高位ビットが予測可能であったり常に一定であったりすると、有効なハッシュ値の範囲が狭まり、衝突の可能性が高まります。シフト操作は、入力のエントロピーをハッシュ値のすべてのビットに広げるために重要な役割を果たします。

### 4. De Bruijnシーケンスを用いた整数Log2計算

De Bruijnシーケンスは、特定の数学的特性を持つバイナリシーケンスで、ビット演算を効率的に行うために利用されます。特に、整数のLog2（最上位ビットの位置）を高速に計算するアルゴリズムで用いられます。

このアルゴリズムは通常、以下のステップで構成されます。
1.  入力値`v`の最上位ビットより下位のビットをすべて1で埋める（例: `v |= v >> 1; v |= v >> 2; ...`）。これにより`v`は`2^k - 1`の形になる。
2.  `v`を特定のDe Bruijnシーケンス定数で乗算する。
3.  その結果を右シフトし、ルックアップテーブルのインデックスを生成する。
4.  ルックアップテーブルからLog2の値を直接取得する。

この方法では、ループや条件分岐を避け、ビット演算とテーブルルックアップのみでLog2を計算できるため、非常に高速です。ここでも、右シフト（`SHR`）はルックアップテーブルのインデックスを生成するために不可欠な操作として登場します。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおいて、`CMPLconst`（32ビット整数と定数の比較）および`CMPQconst`（64ビット整数と定数の比較）と、それに続く`SHRLconst`（32ビット右シフト）および`SHRQconst`（64ビット右シフト）の組み合わせを最適化します。

具体的には、以下の条件が満たされる場合に、比較演算の結果をコンパイル時に`FlagLT_ULT`（符号なしで「より小さい」または「等しい」）として畳み込みます。

### 32ビット整数 (`CMPLconst (SHRLconst _ [c]) [n]`) の場合

新しいリライトルールは、`src/cmd/compile/internal/ssa/gen/AMD64.rules`に以下の行として追加されました。

```
(CMPLconst (SHRLconst _ [c]) [n]) && 0 <= n && 0 < c && c <= 32 && (1<<uint64(32-c)) <= uint64(n) -> (FlagLT_ULT)
```

このルールは、`CMPLconst`オペレーションの最初の引数が`SHRLconst`オペレーションであり、以下の条件がすべて満たされる場合に適用されます。

*   `n`: 比較対象の定数（`CMPLconst`のAuxInt）。
*   `c`: 右シフト量（`SHRLconst`のAuxInt）。

条件の内訳:
1.  `0 <= n`: 比較対象の定数`n`が非負であること。
2.  `0 < c && c <= 32`: 右シフト量`c`が1から32の範囲内であること（32ビット整数に対する有効なシフト量）。
3.  `(1<<uint64(32-c)) <= uint64(n)`: この条件が最適化の核心です。
    *   `32-c`: シフト後に残るビット数。
    *   `1<<uint64(32-c)`: シフト後の値が取りうる最小の非ゼロ値（つまり、シフト前の最上位ビットが1だった場合）。
    *   この条件は、「右シフト`c`ビット後の値が、比較対象の定数`n`よりも常に小さいか等しい」ことを保証します。
        *   例えば、`uint32(X) >> c`という操作を考えます。この結果は最大でも `(1<< (32-c)) - 1` にしかなりません。
        *   もし `n` が `(1<< (32-c))` 以上であれば、`uint32(X) >> c` の結果は常に `n` より小さくなるか、あるいは `n` が `0` の場合は `0` と等しくなります。
        *   したがって、`uint32(X) >> c < n` は常に真となります。

これらの条件が満たされる場合、`CMPLconst`の結果は常に「より小さいか等しい」（`FlagLT_ULT`）と判断でき、コンパイル時にその結果を畳み込むことができます。

### 64ビット整数 (`CMPQconst (SHRQconst _ [c]) [n]`) の場合

同様に、`src/cmd/compile/internal/ssa/gen/AMD64.rules`に以下の行が追加されました。

```
(CMPQconst (SHRQconst _ [c]) [n]) && 0 <= n && 0 < c && c <= 64 && (1<<uint64(64-c)) <= uint64(n) -> (FlagLT_ULT)
```

これは32ビットの場合と全く同じロジックですが、64ビット整数 (`uint64`) に適用されます。

*   `0 <= n`: 比較対象の定数`n`が非負であること。
*   `0 < c && c <= 64`: 右シフト量`c`が1から64の範囲内であること。
*   `(1<<uint64(64-c)) <= uint64(n)`: 64ビット整数に対する同様の条件。右シフト`c`ビット後の値が、比較対象の定数`n`よりも常に小さいか等しいことを保証します。

### 実装

これらのルールは、`rulegen.go`によって`src/cmd/compile/internal/ssa/rewriteAMD64.go`内の`rewriteValueAMD64_OpAMD64CMPLconst`および`rewriteValueAMD64_OpAMD64CMPQconst`関数にGoコードとして生成されます。生成されたコードは、SSAオペレーションツリーを走査し、上記のパターンと条件に合致するものを見つけると、`v.reset(OpAMD64FlagLT_ULT)`を呼び出して、比較オペレーションを定数結果に置き換えます。

この最適化は、特に配列の境界チェック（Bounds Check Elimination, BCE）にも影響を与える可能性があります。例えば、`a[uint32(i * C) >> 18]`のようなアクセスにおいて、シフト後のインデックスが配列の最大長よりも常に小さいことが証明できれば、実行時の境界チェックを省略できるようになります。`test/checkbce.go`にテストケースが追加されていることから、この最適化がBCEに寄与することが意図されていることがわかります。

## コアとなるコードの解説

`AMD64.rules`に追加されたルールは、GoコンパイラのSSA最適化フェーズで特定のパターンを検出するためのものです。

### ルール定義の構造

`(CMPLconst (SHRLconst _ [c]) [n]) && 0 <= n && 0 < c && c <= 32 && (1<<uint64(32-c)) <= uint64(n) -> (FlagLT_ULT)`

*   **`CMPLconst (SHRLconst _ [c]) [n]`**: これはSSAオペレーションのパターンマッチング部分です。
    *   `CMPLconst`: 32ビット整数と定数`n`の比較オペレーション。
    *   `SHRLconst _ [c]`: `CMPLconst`の左オペランドが、何らかの値`_`を定数`c`ビットだけ右シフトする`SHRLconst`オペレーションであることを示します。
    *   `[n]`と`[c]`は、それぞれ`CMPLconst`と`SHRLconst`のAuxInt（補助整数値、ここでは定数`n`とシフト量`c`）を表します。
*   **`&& 0 <= n && 0 < c && c <= 32 && (1<<uint64(32-c)) <= uint64(n)`**: これはパターンに適用される条件（`cond`）です。
    *   `0 <= n`: 比較対象の定数`n`が非負であること。
    *   `0 < c && c <= 32`: シフト量`c`が32ビット整数の有効な範囲（1から32）内であること。
    *   `(1<<uint64(32-c)) <= uint64(n)`: この条件が、シフト後の値が常に`n`より小さいか等しいことを保証します。
        *   `uint32`の値を`c`ビット右シフトした場合、その結果は最大でも `(1 << (32 - c)) - 1` にしかなりません。
        *   もし比較対象の定数`n`が `(1 << (32 - c))` 以上であれば、シフト結果は常に`n`より小さくなります（または`n=0`の場合は`0`と等しくなります）。
        *   したがって、この比較は常に真となります。
*   **`-> (FlagLT_ULT)`**: これはリライト結果（`result`）です。上記のパターンと条件が満たされた場合、元の`CMPLconst`オペレーションは`FlagLT_ULT`（符号なしで「より小さい」または「等しい」）という定数結果に置き換えられます。これは、比較が常に真であることを意味します。

`rewriteAMD64.go`内の生成されたGoコードは、これらのルールを直接実装しています。`v.Args[0]`で`SHRLconst`オペレーションをチェックし、`v.AuxInt`と`v_0.AuxInt`からそれぞれ`n`と`c`を取得します。そして、上記の条件式を評価し、真であれば`v.reset(OpAMD664FlagLT_ULT)`を呼び出してSSAグラフを書き換えます。

64ビット整数版のルールとコードも同様のロジックで動作し、`CMPQconst`と`SHRQconst`、そして`c <= 64 && (1<<uint64(64-c)) <= uint64(n)`という64ビット整数向けの条件が適用されます。

`test/checkbce.go`に追加された`f6`関数は、この最適化が実際に機能し、特に配列の境界チェック除去に貢献することを示しています。例えば、`a[uint32(i*0x07C4ACDD)>>27]`のような式では、`uint32(i*0x07C4ACDD)>>27`の結果が配列`a`のサイズ（32）よりも常に小さいことがコンパイラによって証明できれば、実行時の境界チェックが不要になります。このコミットの最適化は、このようなケースでシフト結果が小さいことを証明し、境界チェック除去を可能にするための重要なステップとなります。

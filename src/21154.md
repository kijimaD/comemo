# [インデックス 21154] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）の重要な変更を導入しています。具体的には、並行GCをデフォルトで有効にし、GCの内部構造（フリーリストなど）に対するライトバリアを回避するための新しいポインタ型を導入しています。これにより、GCのパフォーマンスと効率が向上することが期待されます。

## 元コミット内容

`[dev.garbage] runtime: Turn concurrent GC on by default. Avoid write barriers for GC internal structures such as free lists.`

このコミットは、Goランタイムにおいて、並行ガベージコレクション（GC）をデフォルトで有効にし、GCの内部構造、特にフリーリストのようなデータ構造に対するライトバリアの適用を回避することを目的としています。

## 変更の背景

Goのガベージコレクションは、アプリケーションの実行中に一時停止（Stop-the-World, STW）を発生させ、その間はプログラムの実行が停止します。STW時間は、特に大規模なヒープを持つアプリケーションにおいて、レイテンシの大きな原因となる可能性があります。並行GCは、GC作業の大部分をアプリケーションの実行と並行して行うことで、STW時間を短縮し、全体的なレイテンシを改善することを目的としています。

このコミットが行われた2014年当時、GoのGCは進化の途上にあり、より効率的で低レイテンシなGCの実現が重要な課題でした。特に、Go 1.5で導入される予定だった新しい並行GC（Tri-color Mark-and-Sweep GC）の開発が進められていました。このコミットは、その開発ブランチ（`dev.garbage`）の一部であり、新しい並行GCをデフォルトで有効にするための準備と、その効率をさらに高めるための最適化（GC内部構造からのライトバリア回避）を含んでいます。

ライトバリアは、GCがオブジェクトの参照関係を正確に追跡するために必要なメカニズムですが、GC自身の内部データ構造（例えば、メモリのフリーリスト）を操作する際にも適用されると、不要なオーバーヘッドを発生させる可能性があります。これらの内部構造はGCによって管理されており、アプリケーションコードからは直接アクセスされないため、ライトバリアの対象から外すことで、GCのパフォーマンスを向上させることができます。

## 前提知識の解説

### ガベージコレクション (GC)

ガベージコレクションは、プログラムが動的に確保したメモリ領域のうち、もはや使用されていない（到達不可能になった）ものを自動的に解放する仕組みです。これにより、プログラマは手動でのメモリ管理から解放され、メモリリークなどのバグを減らすことができます。GoのGCは、主に「マーク＆スイープ」アルゴリズムをベースにしています。

*   **マークフェーズ**: GCは、プログラムが現在使用しているすべてのオブジェクト（ルートセットから到達可能なオブジェクト）を特定し、マークします。
*   **スイープフェーズ**: マークされなかったオブジェクト（到達不可能なオブジェクト）を「ガベージ」とみなし、それらが占めていたメモリ領域を解放し、将来の割り当てのためにフリーリストに戻します。

### 並行GC (Concurrent GC)

従来のGCでは、マークフェーズやスイープフェーズの一部でプログラムの実行を完全に停止させる「Stop-the-World (STW)」フェーズが必要でした。並行GCは、これらのGC作業の大部分をアプリケーションの実行と並行して行うことで、STW時間を大幅に短縮します。これにより、アプリケーションの応答性が向上し、レイテンシが低減されます。Go 1.5で導入された並行GCは、三色マーク＆スイープ（Tri-color Mark-and-Sweep）アルゴリズムを採用しています。

### ライトバリア (Write Barrier)

ライトバリアは、並行GCにおいて、GCがオブジェクトグラフを走査している最中に、アプリケーションがオブジェクトの参照を変更（書き込み）する際に介入するメカニズムです。これにより、GCがオブジェクトを見落とす（ガベージではないオブジェクトを誤って解放してしまう）ことを防ぎます。具体的には、ポインタの書き込みが発生した際に、GCがその変更を認識し、必要に応じてオブジェクトを再マークするなどの処理を行います。ライトバリアはGCの正確性を保証するために不可欠ですが、その実行にはオーバーヘッドが伴います。

### `mlink` と `gclinkptr`

Goランタイムのメモリ管理では、`mspan`という構造体が連続したメモリページを管理し、その中にオブジェクトを割り当てます。`mspan`は、解放されたオブジェクトを管理するためにフリーリストを持ちます。このフリーリストは、通常、`mlink`という構造体で構成されるリンクリストとして実装されていました。

*   **`mlink`**: 以前のGoランタイムで、メモリのフリーリストなどの内部リンクリストを構成するために使用されていた構造体です。`next *mlink`フィールドを持ち、次の要素へのポインタを保持します。このポインタは通常のポインタであるため、ライトバリアの対象となります。

このコミットでは、`gclink`と`gclinkptr`という新しい型が導入されています。

*   **`gclink`**: `mlink`と同様にリンクリストのノードとして機能しますが、その`next`フィールドは`gclinkptr`型です。
*   **`gclinkptr`**: `uintptr`を基盤とするポインタ型で、ガベージコレクタに対して「不透明（opaque）」です。つまり、GCはこの型のポインタを追跡せず、この型の値への代入に対してコンパイラはライトバリアを生成しません。これは、GCの内部データ構造（フリーリストなど）がGCによって直接管理され、アプリケーションコードからは到達不可能であるため、ライトバリアが不要であるという特性を利用した最適化です。

### Goランタイムのメモリ管理構造 (`mspan`, `mcache`, `mcentral`, `mheap`)

*   **`mheap`**: Goランタイム全体のヒープメモリを管理するグローバルな構造体です。`mspan`の割り当てと解放を調整します。
*   **`mcentral`**: 特定のサイズのオブジェクトを割り当てるための`mspan`のリストを管理します。`mcache`からの要求に応じて`mspan`を提供し、解放された`mspan`を受け取ります。
*   **`mcache`**: 各P（プロセッサ、Goスケジューラにおける論理CPU）に紐付けられたローカルなキャッシュです。小さなオブジェクトの割り当てを高速化するために、`mcentral`から取得した`mspan`を一時的に保持します。これにより、ロックの競合を減らします。
*   **`mspan`**: 連続したメモリページ（通常は8KBの倍数）の塊を表す構造体です。`mspan`は、特定のサイズのオブジェクトを割り当てるために使用され、その中にフリーリストを保持して、解放されたオブジェクトを管理します。

## 技術的詳細

このコミットの主要な技術的変更点は以下の2つです。

1.  **並行GCのデフォルト有効化**:
    `src/runtime/mgc.go`内の`gogc`関数において、並行GCを制御するフラグが`if false`から`if true`に変更されました。
    ```diff
    --- a/src/runtime/malloc.go
    +++ b/src/runtime/malloc.go
    @@ -475,7 +475,7 @@ func gogc(force int32) {
     
     	systemstack(stoptheworld)
     	systemstack(finishsweep_m) // finish sweep before we start concurrent scan.
    -	if false {                 // To turn on concurrent scan and mark set to true...
    +	if true {                  // To turn on concurrent scan and mark set to true...
     		systemstack(starttheworld)
     		// Do a concurrent heap scan before we stop the world.
     		systemstack(gcscan_m)
    ```
    この変更により、Goランタイムは起動時から並行GCモードで動作するようになります。これは、Go 1.5で導入される新しいGCアルゴリズムの安定性とパフォーマンスに対する自信の表れであり、より低レイテンシなアプリケーション実行を目指すGoの方向性を示しています。

2.  **GC内部構造からのライトバリア回避 (`gclinkptr`の導入)**:
    `src/runtime/malloc2.go`に`gclink`と`gclinkptr`という新しい型が導入されました。
    ```go
    // A gclink is a node in a linked list of blocks, like mlink,
    // but it is opaque to the garbage collector.
    // The GC does not trace the pointers during collection,
    // and the compiler does not emit write barriers for assignments
    // of gclinkptr values. Code should store references to gclinks
    // as gclinkptr, not as *gclink.
    type gclink struct {
    	next gclinkptr
    }

    // A gclinkptr is a pointer to a gclink, but it is opaque
    // to the garbage collector.
    type gclinkptr uintptr

    // ptr returns the *gclink form of p.
    // The result should be used for accessing fields, not stored
    // in other data structures.
    func (p gclinkptr) ptr() *gclink {
    	return (*gclink)(unsafe.Pointer(p))
    }
    ```
    `gclinkptr`は`uintptr`のエイリアスであり、GCはこの型の値をポインタとして認識せず、その指す先を追跡しません。また、`gclinkptr`型への代入時にはライトバリアが生成されません。これにより、`mspan`の`freelist`や`stackfreelist`の`list`など、GCの内部データ構造で使用されるリンクリストの操作において、不要なライトバリアのオーバーヘッドを回避できるようになりました。

    この変更に伴い、`src/runtime/heapdump.go`, `src/runtime/malloc.go`, `src/runtime/mcache.go`, `src/runtime/mcentral.go`, `src/runtime/mheap.go`, `src/runtime/stack1.go`など、フリーリストを扱う多くのファイルで`mlink`から`gclinkptr`への型変更と、それに伴うアクセス方法の変更（`v.ptr()`の利用）が行われています。

    例えば、`malloc.go`では、フリーリストからのオブジェクト取得と更新のロジックが以下のように変更されています。
    ```diff
    --- a/src/runtime/malloc.go
    +++ b/src/runtime/malloc.go
    @@ -140,14 +140,14 @@ func mallocgc(size uintptr, typ *_type, flags uint32) unsafe.Pointer {
     		// Allocate a new maxTinySize block.
     		s = c.alloc[tinySizeClass]
     		v := s.freelist
    -		if v == nil {
    +		if v.ptr() == nil {
     			systemstack(func() {
     				mCache_Refill(c, tinySizeClass)
     			})
     			s = c.alloc[tinySizeClass]
     			v = s.freelist
     		}
    -		s.freelist = v.next
    +		s.freelist = v.ptr().next
     		s.ref++
     		//TODO: prefetch v.next
     		x = unsafe.Pointer(v)
    ```
    `v == nil`が`v.ptr() == nil`に、`v.next`が`v.ptr().next`に変更されています。これは、`gclinkptr`が直接ポインタとして扱えないため、`ptr()`メソッドを介して`*gclink`型に変換してからフィールドにアクセスする必要があるためです。

    また、`malloc.go`では、GCのトリガー条件も調整されています。
    ```diff
    --- a/src/runtime/malloc.go
    +++ b/src/runtime/malloc.go
    @@ -341,7 +341,7 @@ marked:
     		}
     	}
     
    -	if memstats.heap_alloc >= memstats.next_gc {
    +	if memstats.heap_alloc >= memstats.next_gc/2 {
     		gogc(0)
     	}
    ```
    `memstats.next_gc`は次回のGCがトリガーされるヒープサイズを示しますが、この変更により、GCがより早く（`next_gc`の半分に達した時点で）トリガーされる可能性があります。これは、並行GCが導入されることでGCのオーバーヘッドが低減されるため、より頻繁にGCを実行してもパフォーマンスへの影響が少なくなるという判断に基づいている可能性があります。これにより、ヒープサイズが過度に大きくなるのを防ぎ、STW時間をさらに短縮する効果が期待できます。

## コアとなるコードの解説

### `src/runtime/malloc2.go`における`gclink`と`gclinkptr`の定義

```go
// A gclink is a node in a linked list of blocks, like mlink,
// but it is opaque to the garbage collector.
// The GC does not trace the pointers during collection,
// and the compiler does not emit write barriers for assignments
// of gclinkptr values. Code should store references to gclinks
// as gclinkptr, not as *gclink.
type gclink struct {
	next gclinkptr
}

// A gclinkptr is a pointer to a gclink, but it is opaque
// to the garbage collector.
type gclinkptr uintptr

// ptr returns the *gclink form of p.
// The result should be used for accessing fields, not stored
// in other data structures.
func (p gclinkptr) ptr() *gclink {
	return (*gclink)(unsafe.Pointer(p))
}
```
`gclink`構造体は、リンクリストのノードとして機能します。その`next`フィールドは`gclinkptr`型であり、これがGCの追跡対象外となるポイントです。
`gclinkptr`は`uintptr`の型エイリアスであり、GoのGCは`uintptr`型の値をポインタとして自動的に追跡しません。これにより、GCの内部データ構造のポインタ操作時にライトバリアが不要になります。
`ptr()`メソッドは、`gclinkptr`型の値を一時的に`*gclink`型に変換し、そのフィールド（`next`など）にアクセスできるようにするためのユーティリティです。この変換は、フィールドアクセスのための一時的なものであり、`*gclink`型の値を他のデータ構造に永続的に保存すべきではないとコメントで明記されています。これは、`*gclink`型として保存すると、再びGCの追跡対象となり、ライトバリアが適用される可能性があるためです。

### `src/runtime/mgc.go`における並行GCの有効化

```diff

+++ b/src/runtime/malloc.go
@@ -475,7 +475,7 @@ func gogc(force int32) {

 	systemstack(finishsweep_m) // finish sweep before we start concurrent scan.
-	if false {                 // To turn on concurrent scan and mark set to true...
+	if true {                  // To turn on concurrent scan and mark set to true...
```

この変更は非常にシンプルですが、GoのGC戦略において大きな意味を持ちます。`if false`が`if true`に変更されたことで、`gcscan_m`（並行マークフェーズの一部）がデフォルトで実行されるようになります。これにより、GCの大部分がアプリケーションと並行して動作し、STW時間が最小限に抑えられます。

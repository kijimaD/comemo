## 変更の背景

この変更の背景には、異なるCPUアーキテクチャ間でのLinuxシステムコール（特に`clone`）の引数渡し規約（ABI: Application Binary Interface）の違いがあります。Go言語のランタイムは、様々なアーキテクチャ上で動作するように設計されており、それぞれのアーキテクチャの低レベルな特性に適合する必要があります。

`clone`システムコールは、新しいプロセスやスレッドを作成するために使用されます。このシステムコールは、新しいプロセスの動作を制御するための様々なフラグや、新しいスタックポインタなどの引数を取ります。一般的なx86-64アーキテクチャなどでは、特定の引数順序が確立されていますが、IBMのメインフレームで使用される`s390x`アーキテクチャでは、この引数順序が他のアーキテクチャと異なることが判明しました。

Goの`syscall`パッケージは、OSのシステムコールを直接呼び出すための機能を提供します。`RawSyscall6`のような関数は、Goのコードから直接カーネルのシステムコールを呼び出すためのラッパーです。このラッパー関数に渡される引数の順序は、ターゲットとなるOSとアーキテクチャのABIに厳密に一致している必要があります。一致しない場合、システムコールは正しく動作せず、予期せぬ挙動やクラッシュを引き起こす可能性があります。

このコミットは、`s390x`アーキテクチャ上でGoプログラムが`clone`システムコールを正しく呼び出せるように、引数の順序を調整することを目的としています。

## 前提知識の解説

### システムコール (System Call)

システムコールは、ユーザー空間で実行されるプログラムが、カーネル空間で提供されるOSのサービス（ファイルI/O、プロセス管理、メモリ管理など）を利用するためのインターフェースです。プログラムは直接ハードウェアにアクセスできないため、OSカーネルが提供するシステムコールを介して間接的にアクセスします。Go言語では、`syscall`パッケージを通じてこれらの低レベルな操作を行うことができます。

### `clone()` システムコール

`clone()`はLinuxカーネルが提供するシステムコールの一つで、新しいプロセスまたはスレッドを作成するために使用されます。`fork()`と似ていますが、`clone()`はより細かく新しいプロセスと親プロセスの間で共有するリソース（メモリ空間、ファイルディスクリプタ、シグナルハンドラなど）を制御できる点が異なります。引数として渡されるフラグによって、その挙動が大きく変わります。例えば、`SIGCHLD`は子プロセスが終了したときに親プロセスに送られるシグナルを指定し、`CLONE_VM`などのフラグはメモリ空間を共有するかどうかなどを指定します。

### ABI (Application Binary Interface)

ABIは、オペレーティングシステムとアプリケーション、またはアプリケーションの異なるモジュール間で、バイナリレベルでの互換性を定義する一連の規約です。これには、関数呼び出し規約（引数の渡し方、戻り値の受け取り方）、データ型のメモリレイアウト、システムコールの呼び出し規約などが含まれます。CPUアーキテクチャが異なれば、レジスタの数や種類、メモリへのアクセス方法などが異なるため、ABIも異なるのが一般的です。

### `s390x` アーキテクチャ

`s390x`は、IBMのメインフレームコンピュータ（System/390およびz/Architecture）で使用される64ビットのCPUアーキテクチャです。これはビッグエンディアンであり、一般的なx86-64やARMとは異なるレジスタセットや命令セットを持っています。そのため、システムコールの引数渡し規約も他のアーキテクチャとは異なる場合があります。

### Go `syscall` パッケージと `RawSyscall6`

Goの`syscall`パッケージは、OSの低レベルなプリミティブ（システムコール）へのアクセスを提供します。`RawSyscall6`関数は、最大6つの引数を取るシステムコールを直接呼び出すためのGoの関数です。この関数は、Goのランタイムが提供する抽象化をバイパスし、OSカーネルが期待する形式で引数を直接渡します。そのため、`RawSyscall6`を使用する際には、ターゲットアーキテクチャのABIに厳密に従う必要があります。

## 技術的詳細

`clone`システムコールは、Linuxカーネルにおいて新しい実行コンテキスト（プロセスまたはスレッド）を作成する非常に強力で柔軟なメカニズムです。その引数は、新しいコンテキストが親と何を共有し、何を独立させるかを決定するフラグのセットと、新しいスタックの場所、子プロセスのPIDを格納する場所などを指定します。

一般的なLinuxシステムコールでは、引数は特定のレジスタに順番に格納されてカーネルに渡されます。しかし、`s390x`アーキテクチャのLinux ABIでは、`clone`システムコールの引数順序が他の一般的なアーキテクチャ（例: x86-64）と異なります。具体的には、`clone`のフラグとスタックポインタの引数の位置が入れ替わっています。

Goの`src/syscall/exec_linux.go`ファイル内の`forkAndExecInChild`関数は、新しいプロセスを生成する際に`clone`システムコールを利用しています。この関数内で`RawSyscall6`を呼び出す際、GoランタイムはOSのABIに従って引数を設定する必要があります。

コミット前のコードでは、`RawSyscall6`の呼び出しは、`uintptr(SIGCHLD)|sys.Cloneflags`を最初の引数として、スタックポインタ（この場合は0）を2番目の引数として渡していました。これは多くのアーキテクチャでは正しいのですが、`s390x`ではこの順序が逆であるため、システムコールが正しく解釈されませんでした。

このコミットは、`runtime.GOARCH == "s390x"`という条件分岐を追加することで、このアーキテクチャ固有のABIの差異に対応しています。`s390x`の場合には、フラグとスタックポインタの引数の位置を入れ替えて`RawSyscall6`を呼び出すように修正されました。これにより、`s390x`上でもGoプログラムが`clone`システムコールを正しく利用できるようになります。

## コアとなるコードの解説

この変更は、Goのクロスプラットフォーム対応における重要な側面を示しています。Goは様々なCPUアーキテクチャで動作しますが、OSの低レベルな機能（システムコール）を呼び出す際には、各アーキテクチャ固有のABIに適合する必要があります。

`forkAndExecInChild`関数は、Goプログラムが新しい子プロセスを生成し、その中で別のプログラムを実行する（`exec`）ための準備を行うGoランタイムの内部関数です。このプロセス生成の初期段階で`clone`システムコールが使用されます。

変更前のコードでは、`RawSyscall6(SYS_CLONE, uintptr(SIGCHLD)|sys.Cloneflags, 0, ...)`という形で`clone`を呼び出していました。ここで、`uintptr(SIGCHLD)|sys.Cloneflags`は`clone`システムコールに渡すフラグの組み合わせであり、`0`は新しいプロセスのスタックポインタを意味します（このコンテキストでは、カーネルが適切なスタックを割り当てるため0が渡されることが多い）。

しかし、`s390x`アーキテクチャのLinux ABIでは、`clone`システムコールのシグネチャが`long clone(void *stack, unsigned long flags, ...)`となっており、スタックポインタが最初の引数、フラグが2番目の引数として期待されます。

このコミットは、`runtime.GOARCH`というGoの組み込み変数を利用して、現在の実行環境のアーキテクチャを判別しています。
*   `runtime.GOARCH == "s390x"`の場合、`RawSyscall6`の引数を`RawSyscall6(SYS_CLONE, 0, uintptr(SIGCHLD)|sys.Cloneflags, ...)`とすることで、`s390x`のABIに合致するようにスタックポインタ（`0`）を最初の引数に、フラグ（`uintptr(SIGCHLD)|sys.Cloneflags`）を2番目の引数に渡しています。
*   それ以外のアーキテクチャでは、従来の引数順序を維持しています。

この条件分岐により、Goランタイムは`s390x`を含む多様なアーキテクチャ上で、`clone`システムコールを正しく、かつ安全に呼び出すことができるようになりました。これは、Goが提供する「一度書けばどこでも動く」という哲学を低レベルなシステムインターフェースのレベルで実現するための、細部にわたる調整の一例です。

# [インデックス 25062] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）最適化に関連する変更であり、特に`varkill`命令の使用をSSA化されない変数に限定することで、スタックフレームサイズの削減を目指しています。また、それに伴いスタックガードのサイズ調整も行われています。

## コミット

```
commit d29e92be523efd8270c0e7ca0eaa6afa86bbedca
Author: Keith Randall <khr@golang.org>
Date:   Sat Sep 19 12:01:39 2015 -0700

    [dev.ssa] cmd/compile: Use varkill only for non-SSAable vars
    
    For variables which get SSA'd, SSA keeps track of all the def/kill.
    It is only for on-stack variables that we need them.
    
    This reduces stack frame sizes significantly because often the
    only use of a variable was a varkill, and without that last use
    the variable doesn't get allocated in the frame at all.
```

## 元コミット内容

`[dev.ssa] cmd/compile: Use varkill only for non-SSAable vars`

このコミットは、Goコンパイラにおいて、`varkill`命令をSSA（Static Single Assignment）形式に変換されない変数（主にスタック上の変数）にのみ使用するように変更します。SSA化される変数については、SSA自体が変数の定義（def）と使用終了（kill）を追跡するため、明示的な`varkill`は不要であるという判断に基づいています。この変更により、スタックフレームサイズの削減が期待されます。

## 変更の背景

Goコンパイラは、コードの最適化のためにSSA形式の中間表現を使用しています。SSA形式では、各変数が一度だけ定義されるという特性があり、変数のライフタイム（定義から最後の使用まで）を正確に追跡できます。

従来のコンパイラでは、変数のライフタイムの終了を示すために`varkill`という命令が使用されていました。これは、変数がもう使用されないことをコンパイラに伝え、その変数が占めていたスタック領域を解放したり、レジスタを再利用したりするためのヒントとして機能します。

しかし、SSA形式に変換される変数については、SSAの性質上、変数の定義と使用が明確に管理されており、そのライフタイムはSSAグラフによって自然に決定されます。したがって、SSA化された変数に対して`varkill`を明示的に挿入することは冗長であり、場合によっては最適化の妨げになる可能性がありました。

このコミットの背景には、以下の問題意識があります。

1.  **冗長な`varkill`の生成**: SSA化される変数に対しても`varkill`が生成されることで、コンパイラの中間表現が不必要に複雑になり、処理オーバーヘッドが増加する可能性がありました。
2.  **スタックフレームサイズの肥大化**: コミットメッセージにあるように、「変数の唯一の用途が`varkill`であった場合、その最後の用途がなければ、変数はフレームに全く割り当てられない」という状況がありました。つまり、`varkill`が存在することで、実際にはもう必要ない変数がスタックフレーム上に残され、スタックフレームサイズを不必要に大きくしていた可能性があります。これは、特に多くのローカル変数を持つ関数において、メモリ使用量の増加やキャッシュ効率の低下につながります。
3.  **Issue #12602の解決**: この変更は、GoのIssueトラッカーで報告された問題 #12602 を修正することを目的としています。このIssueは、おそらくスタックフレームサイズの最適化に関するものであったと推測されます。

これらの背景から、SSA化されない変数（主にスタック上に直接割り当てられる変数）にのみ`varkill`を限定することで、コンパイラの効率を向上させ、生成されるバイナリの性能を改善しようとしたのがこのコミットの意図です。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **SSA (Static Single Assignment) 形式**:
    *   コンパイラの最適化段階で用いられる中間表現の一種です。
    *   SSA形式では、各変数がプログラム中で一度だけ定義されるという制約があります。もし同じ論理的な変数が複数回代入される場合、SSAでは新しい「バージョン」の変数が導入されます（例: `x1 = ...`, `x2 = ...`）。
    *   この特性により、データフロー解析が非常に容易になり、コンパイラは変数の定義と使用の関係を正確に把握できます。これにより、デッドコード削除、共通部分式除去、レジスタ割り当てなどの強力な最適化が可能になります。
    *   Goコンパイラは、Go 1.7以降でSSAバックエンドを導入し、大幅な最適化を実現しました。このコミットは、そのSSAバックエンドの開発段階（`dev.ssa`ブランチ）での変更です。

2.  **`varkill`命令**:
    *   コンパイラの中間表現において、変数の「使用終了」を示す擬似命令です。
    *   この命令は、特定の変数がそれ以降のコードで参照されないことをコンパイラに伝えます。これにより、コンパイラはその変数が占めていたリソース（レジスタやスタックメモリ）を解放し、他の用途に再利用できるようになります。
    *   特に、レジスタ割り当てやスタックフレームのレイアウトを決定する際に重要なヒントとなります。

3.  **オンスタック変数 (On-stack variables)**:
    *   関数内で宣言され、その関数のスタックフレーム上に直接割り当てられるローカル変数のことです。
    *   Goでは、変数がスタックに割り当てられるかヒープにエスケープされるか（エスケープ解析）はコンパイラが決定します。
    *   SSAは主にレジスタに割り当てられる変数や、最適化によってレジスタに昇格できる変数に対して効果を発揮しますが、スタック上に残る変数（例えば、アドレスが取られる変数や、SSAで追跡しきれない複雑なデータ構造の一部）については、従来の方式でのライフタイム管理が必要になる場合があります。

4.  **スタックフレーム (Stack Frame)**:
    *   関数が呼び出されるたびに、その関数に必要なローカル変数、引数、戻りアドレスなどを格納するためにスタック上に確保されるメモリ領域です。
    *   スタックフレームのサイズは、関数の実行に必要なメモリ量に直接影響し、プログラム全体のメモリ使用量やパフォーマンス（特にキャッシュ効率）に影響を与えます。

5.  **スタックガード (Stack Guard)**:
    *   Goランタイムにおけるスタックオーバーフロー検出のためのメカニズムです。
    *   各Goroutineのスタックの末尾近くに「ガードページ」と呼ばれる領域が設定されており、スタックポインタがこのガードページに到達すると、スタックの拡張が必要であることを示すシグナルがトリガーされます。
    *   `StackGuard`定数は、スタックの底からどれくらいの距離にガードを置くかを示す値です。この値が小さいほど、スタック拡張のチェックがより頻繁に行われる可能性がありますが、スタックの利用効率は上がります。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドにおける`varkill`命令の生成ロジックの変更です。

変更前は、`src/cmd/compile/internal/gc/ssa.go`内の`stmt`関数（ステートメントをSSA形式に変換する部分）において、変数の使用終了を示す`ssa.OpVarKill`命令が、無条件に生成されていました。具体的には、`s.vars[&memVar] = s.newValue1A(ssa.OpVarKill, ssa.TypeMem, n.Left, s.mem())`という行が、変数のライフタイム終了時に常に実行されていました。

このコミットでは、この`varkill`の生成に条件が追加されました。
`if !canSSA(n.Left) { ... }`
この条件は、`n.Left`（`varkill`の対象となる変数）がSSA形式に変換可能であるかどうかをチェックします。
*   `canSSA(n.Left)`が`true`の場合（つまり、変数がSSA化される場合）、`varkill`命令は生成されません。SSA形式自体が変数のライフタイムを管理するため、冗長だからです。
*   `canSSA(n.Left)`が`false`の場合（つまり、変数がSSA化されない場合）、`varkill`命令が生成されます。これは、主にスタック上に直接割り当てられる変数であり、SSAによるライフタイム管理の恩恵を受けられないため、明示的な`varkill`が必要となるケースです。

この変更の直接的な効果は、SSA化される変数の`varkill`命令が中間表現から削除されることです。これにより、コンパイラはこれらの変数が不要になったことをより効率的に認識し、スタックフレームから完全に削除したり、レジスタをより早く再利用したりできるようになります。結果として、スタックフレームサイズの削減と、それに伴うメモリ使用量の最適化が期待されます。

また、この変更に伴い、`src/cmd/internal/obj/stack.go`と`src/runtime/stack2.go`で定義されている`StackGuard`定数の値が変更されています。
*   変更前: `960*stackGuardMultiplier + StackSystem`
*   変更後: `640*stackGuardMultiplier + StackSystem`

`StackGuard`の値が`960`から`640`に減少しています。これは、`varkill`の最適化によってスタックフレームサイズが全体的に小さくなるため、スタックガードの閾値を調整しても問題ないと判断されたことを示唆しています。スタックガードの値を小さくすることで、スタックの利用効率が向上し、スタック拡張のためのチェックがわずかに遅れる可能性がありますが、全体的なスタック使用量の削減効果の方が大きいと見込まれます。

`test/nosplit.go`の変更は、この`StackGuard`の変更に合わせてテストケースの期待値を調整するものです。特に、スタックフレームのサイズ計算において、`832 - 128`が`512 - 128`に、`-N`フラグ（nooptビルド）時の`960`が`640`にそれぞれ変更されており、これは新しい`StackGuard`の値と整合しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の変更

このファイルはGoコンパイラのSSAバックエンドの中核部分です。`stmt`関数は、Goのソースコードの抽象構文木（AST）ノードをSSA形式の中間表現に変換する役割を担っています。

変更された箇所は、`ssa.OpVarKill`命令の生成ロジックです。
*   `s.vars[&memVar] = s.newValue1A(ssa.OpVarKill, ssa.TypeMem, n.Left, s.mem())`
    *   これは、`n.Left`で表される変数のライフタイムが終了したことを示す`VarKill`命令を生成し、メモリの状態（`s.mem()`）に連結する処理です。`memVar`はメモリの状態を表す特別な変数です。
*   `if !canSSA(n.Left) { ... }`
    *   この条件が追加されたことで、`n.Left`がSSA化可能でない場合にのみ`VarKill`命令が生成されるようになりました。
    *   `canSSA`関数は、与えられた変数がSSA形式で効率的に扱えるかどうかを判断する内部関数です。例えば、アドレスが取られる変数や、コンパイラがそのライフタイムをSSAで完全に追跡できないような複雑なケースでは`false`を返す可能性があります。

この変更により、SSA化される変数の`VarKill`命令が不要になり、中間表現が簡素化され、コンパイラの最適化パスがより効率的に動作するようになります。特に、変数の最後の使用が`VarKill`のみであった場合、その変数はスタックフレームに割り当てられる必要がなくなるため、スタックフレームサイズの削減に大きく貢献します。

### `src/cmd/internal/obj/stack.go` および `src/runtime/stack2.go` の変更

これらのファイルは、Goランタイムにおけるスタック管理とスタックガードの定義に関連しています。

*   `StackGuard` (または `_StackGuard`) 定数は、スタックオーバーフローを検出するための閾値を定義します。スタックポインタがこの値に近づくと、ランタイムはスタックの拡張を試みます。
*   値が`960`から`640`に減少したことは、SSA最適化によるスタックフレームサイズの削減が全体的に効果を発揮し、スタックの利用可能な領域が増えたため、スタックガードの閾値をより小さく設定しても安全になったことを示しています。これにより、スタックの利用効率がさらに向上します。

### `test/nosplit.go` の変更

このファイルは、Goのテストスイートの一部であり、特にスタック分割（stack split）が発生しないことを保証する関数（`nosplit`関数）のテストに関連しています。

*   テストケース内でスタックフレームのサイズを計算するロジックが変更されています。
*   `size += 832 - 128` が `size += 512 - 128` に、そして `-N` (noopt) ビルド時の `size += 960` が `size += 640` に変更されています。
*   これらの数値は、スタックガードの変更（`960` -> `640`）と整合しており、新しいスタックガードの値に基づいてテストの期待値を調整していることを示しています。これにより、スタックフレームサイズの最適化が正しく機能していることを検証できます。

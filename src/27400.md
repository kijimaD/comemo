## 変更の背景

HMAC（Keyed-Hash Message Authentication Code）は、メッセージの完全性と認証性を保証するために広く使用される暗号学的メカニズムです。その計算プロセスでは、秘密鍵とメッセージを組み合わせてハッシュ関数を適用します。HMACの仕様（RFC 2104）では、内部ハッシュと外部ハッシュの2段階の計算が行われ、それぞれ異なるパディングされたキー（`ipad` と `opad`）を使用します。

従来のGoの `crypto/hmac` 実装では、HMAC構造体内に生のキーを保持し、`Reset` や `Sum` といった操作が呼ばれるたびに、その場で `ipad` や `opad` を生成するためのパディング処理を行っていました。このアプローチは、特に `Reset-Write-Sum` のシーケンスが頻繁に発生するシナリオ（例えば、PBKDF2のような鍵導出関数でHMACが繰り返し使用される場合）において、オーバーヘッドとなっていました。

このコミットの背景には、この繰り返し行われるパディング処理を最適化し、HMACのパフォーマンスを向上させるという明確な目的があります。特に、`/x/crypto/pbkdf2` のような、HMACを内部で何度も呼び出すライブラリの性能改善が期待されていました。

## 前提知識の解説

### HMAC (Keyed-Hash Message Authentication Code)

HMACは、ハッシュ関数（例: SHA-256）と秘密鍵を組み合わせてメッセージ認証コード（MAC）を生成するメカニズムです。これにより、メッセージが改ざんされていないこと（完全性）と、メッセージが秘密鍵を知っている送信者によって生成されたこと（認証性）を検証できます。

HMACの計算手順は以下の通りです（RFC 2104に基づく）：

1.  **鍵の準備**:
    *   秘密鍵 `K` がハッシュ関数のブロックサイズよりも長い場合、`K` をハッシュして新しい鍵 `K'` を生成します。
    *   `K` がブロックサイズよりも短い場合、`K` をゼロでブロックサイズまでパディングします。
    *   結果として得られるブロックサイズの鍵を `K0` とします。
2.  **内部ハッシュの計算**:
    *   `ipad` (inner padding) は、`K0` と `0x36` をXORしたものです。
    *   `ipad` とメッセージ `M` を連結し、ハッシュ関数 `H` を適用します: `H(ipad || M)`。この結果を `I` とします。
3.  **外部ハッシュの計算**:
    *   `opad` (outer padding) は、`K0` と `0x5c` をXORしたものです。
    *   `opad` と `I` を連結し、ハッシュ関数 `H` を適用します: `H(opad || I)`。この結果が最終的なHMAC値となります。

### `hash.Hash` インターフェース

Go言語の `crypto` パッケージでは、ハッシュ関数は `hash.Hash` インターフェースを実装します。このインターフェースには以下の主要なメソッドが含まれます。

*   `Write(p []byte) (n int, err error)`: データをハッシュ関数に書き込みます。
*   `Sum(b []byte) []byte`: 現在のハッシュ値を計算し、`b` に追加して返します。ハッシュ関数は状態をリセットしません。
*   `Reset()`: ハッシュ関数を初期状態に戻します。これにより、同じハッシュインスタンスを再利用して新しいメッセージのハッシュを計算できます。
*   `Size() int`: ハッシュ値のバイト長を返します。
*   `BlockSize() int`: ハッシュ関数のブロックサイズを返します。

### PBKDF2 (Password-Based Key Derivation Function 2)

PBKDF2は、パスワードから暗号鍵を導出するための関数です。HMACを基盤としており、ソルトと繰り返し回数（イテレーションカウント）を使用することで、ブルートフォース攻撃や辞書攻撃に対する耐性を高めます。PBKDF2の内部では、HMACが指定された回数だけ繰り返し適用されるため、HMACの性能はPBKDF2の全体的な性能に直接影響します。

## 技術的詳細

このコミットの核心は、HMAC構造体 `hmac` の内部状態管理の変更にあります。

**変更前**:
`hmac` 構造体は `key []byte` と `tmp []byte` フィールドを持っていました。
*   `key`: 生の秘密鍵を保持。
*   `tmp`: パディングされたキー（`ipad` または `opad`）を一時的に生成するために使用されるバッファ。

`tmpPad` メソッドが定義されており、`Reset` や `Sum` が呼ばれるたびに、`key` を基に `tmp` バッファに `ipad` または `opad` を生成していました。

```go
type hmac struct {
	size         int
	blocksize    int
	key, tmp     []byte // 変更前: 生のキーと一時バッファ
	outer, inner hash.Hash
}

func (h *hmac) tmpPad(xor byte) {
	for i, k := range h.key {
		h.tmp[i] = xor ^ k
	}
	for i := len(h.key); i < h.blocksize; i++ {
		h.tmp[i] = xor
	}
}

func (h *hmac) Sum(in []byte) []byte {
	// ...
	h.tmpPad(0x5c) // Sum時にopadを生成
	// ...
}

func (h *hmac) Reset() {
	// ...
	h.tmpPad(0x36) // Reset時にipadを生成
	// ...
}
```

このアプローチでは、`Reset` や `Sum` が呼び出されるたびに、`key` から `ipad` や `opad` を計算し、`tmp` バッファに書き込むというCPUサイクルを消費する操作が発生していました。

**変更後**:
`hmac` 構造体は `key` と `tmp` フィールドを削除し、代わりに `ipad []byte` と `opad []byte` フィールドを持つようになりました。
*   `ipad`: 既にパディングされ、`0x36` でXORされた内部パディングキーを保持。
*   `opad`: 既にパディングされ、`0x5c` でXORされた外部パディングキーを保持。

これらの `ipad` と `opad` は、`New` 関数でHMACインスタンスが作成される際に一度だけ計算され、構造体内に永続的に保存されます。

```go
type hmac struct {
	size         int
	blocksize    int
	opad, ipad   []byte // 変更後: 既にパディングされたキー
	outer, inner hash.Hash
}

func (h *hmac) Sum(in []byte) []byte {
	// ...
	// h.tmpPad(0x5c) の呼び出しが削除され、直接 h.opad を使用
	h.outer.Write(h.opad)
	// ...
}

func (h *hmac) Reset() {
	// ...
	// h.tmpPad(0x36) の呼び出しが削除され、直接 h.ipad を使用
	h.inner.Write(h.ipad)
}
```

この変更により、`Reset` や `Sum` のたびにパディング計算を行う必要がなくなり、これらの操作が大幅に高速化されます。特に、`Reset-Write-Sum` のサイクルが頻繁に繰り返されるシナリオ（例: PBKDF2）で顕著なパフォーマンス向上が見られます。

ベンチマーク結果が示すように、特に短いメッセージ（32バイト）のHMAC計算で `ns/op` が約7.6%改善し、`MB/s` が約8%向上しています。PBKDF2のベンチマークでも約7%の改善が見られ、この最適化が実用的なアプリケーションに良い影響を与えることを示しています。

## コアとなるコードの変更箇所

### `src/crypto/hmac/hmac.go`

1.  **`hmac` 構造体の変更**:
    *   `key, tmp []byte` フィールドが削除され、`opad, ipad []byte` フィールドが追加されました。
    ```diff
    -	key, tmp     []byte
    +	opad, ipad   []byte
    ```

2.  **`tmpPad` メソッドの削除**:
    *   一時的なパディングを生成する `tmpPad` メソッドが完全に削除されました。

3.  **`Sum` メソッドの変更**:
    *   `h.tmpPad(0x5c)` の呼び出しが削除され、代わりに `h.outer.Write(h.opad)` が直接使用されるようになりました。
    ```diff
    -	in = h.inner.Sum(in)
    -	h.tmpPad(0x5c)
    -	copy(h.tmp[h.blocksize:], in[origLen:])
    	h.outer.Reset()
    -	h.outer.Write(h.tmp)
    +	h.outer.Write(h.opad)
    +	h.outer.Write(in[origLen:])
    	return h.outer.Sum(in[:origLen])
    ```

4.  **`Reset` メソッドの変更**:
    *   `h.tmpPad(0x36)` の呼び出しが削除され、代わりに `h.inner.Write(h.ipad)` が直接使用されるようになりました。
    ```diff
    	h.inner.Reset()
    -	h.tmpPad(0x36)
    -	h.inner.Write(h.tmp[:h.blocksize])
    +	h.inner.Write(h.ipad)
    ```

5.  **`New` 関数（コンストラクタ）の変更**:
    *   `hm.tmp` の初期化が削除されました。
    *   `hm.key` のコピーと `hm.Reset()` の呼び出しが削除されました。
    *   代わりに、`hm.ipad` と `hm.opad` が `make` で作成され、キーに基づいて一度だけパディングとXOR処理が行われ、初期化されます。
    *   最後に `hm.inner.Write(hm.ipad)` が呼び出され、内部ハッシュの状態が初期化されます。
    ```diff
    	hm.inner = h()
    	hm.size = hm.inner.Size()
    	hm.blocksize = hm.inner.BlockSize()
    -	hm.tmp = make([]byte, hm.blocksize+hm.size)
    +	hm.ipad = make([]byte, hm.blocksize)
    +	hm.opad = make([]byte, hm.blocksize)
    	if len(key) > hm.blocksize {
    		// If key is too big, hash it.
    		hm.outer.Write(key)
    		key = hm.outer.Sum(nil)
    	}
    -	hm.key = make([]byte, len(key))
    -	copy(hm.key, key)
    -	hm.Reset()
    +	copy(hm.ipad, key)
    +	copy(hm.opad, key)
    +	for i := range hm.ipad {
    +		hm.ipad[i] ^= 0x36
    +	}
    +	for i := range hm.opad {
    +		hm.opad[i] ^= 0x5c
    +	}
    +	hm.inner.Write(hm.ipad)
    	return hm
    ```

### `src/crypto/hmac/hmac_test.go`

*   HMACSHA256のパフォーマンスを測定するための新しいベンチマーク関数が追加されました。
    *   `BenchmarkHMACSHA256_1K`: 1KBのメッセージに対するHMAC計算のベンチマーク。
    *   `BenchmarkHMACSHA256_32`: 32バイトのメッセージに対するHMAC計算のベンチマーク。
    これらのベンチマークは、`Reset-Write-Sum` のシーケンスを繰り返し実行し、変更によるパフォーマンス改善を定量的に評価するために使用されます。

## コアとなるコードの解説

このコミットの主要な変更点は、HMACの内部状態 `hmac` 構造体から、生のキー `key` と一時バッファ `tmp` を削除し、代わりに事前に計算されたパディング済みキー `ipad` と `opad` を直接保持するようにしたことです。

1.  **`hmac` 構造体の効率化**:
    *   `key` と `tmp` の削除により、構造体のメモリフットプリントがわずかに減少し、また `tmpPad` メソッドの呼び出しが不要になります。
    *   `ipad` と `opad` を直接持つことで、HMACの計算サイクル（特に `Reset` と `Sum`）において、パディング計算のオーバーヘッドが完全に排除されます。

2.  **`New` 関数での初期化の変更**:
    *   `New` 関数内で、入力された `key` を基に `ipad` と `opad` を一度だけ計算し、それぞれのバイトスライスに格納します。
    *   キーがハッシュ関数のブロックサイズを超える場合は、RFC 2104の規定に従い、まずキーをハッシュしてブロックサイズに収まるように処理します。
    *   その後、`ipad` と `opad` の各バイトに対して、それぞれ `0x36` と `0x5c` でXOR演算を行い、パディング済みキーを生成します。
    *   最後に `hm.inner.Write(hm.ipad)` を呼び出すことで、HMACの内部ハッシュの状態を初期化します。これにより、HMACインスタンスが生成された直後から、メッセージの書き込みを開始できる状態になります。

3.  **`Reset` および `Sum` メソッドの簡素化**:
    *   `Reset` メソッドでは、`h.inner.Reset()` の後、以前は `h.tmpPad(0x36)` を呼び出して `ipad` を生成していましたが、変更後は `h.inner.Write(h.ipad)` を直接呼び出すだけで済みます。これにより、ハッシュ関数に事前に計算された `ipad` を書き込み、内部ハッシュの状態をリセットします。
    *   `Sum` メソッドでは、`h.outer.Reset()` の後、以前は `h.tmpPad(0x5c)` を呼び出して `opad` を生成していましたが、変更後は `h.outer.Write(h.opad)` を直接呼び出すだけで済みます。これにより、外部ハッシュ関数に事前に計算された `opad` を書き込みます。

この変更は、HMACの計算ロジック自体を変更するものではなく、その実装の詳細を最適化することで、特に繰り返し利用される場合の効率を大幅に向上させています。これにより、HMACを多用するPBKDF2のような暗号プリミティブの性能が向上し、結果としてそれらを利用するアプリケーション全体のセキュリティ関連処理の高速化に貢献します。

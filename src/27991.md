## 元コミット内容

このコミットは、GoコンパイラのAMD64バックエンドにおいて、8ビットおよび16ビットの命令（バイトおよびワード命令）の大部分を廃止し、代わりに32ビット命令に変換することを目的としています。これは、部分レジスタストール（partial register stalls）を回避するために、8ビット/16ビットの論理演算に32ビット演算を使用するようになった現在の状況を反映したものです。

コミットの主な変更点は以下の通りです。

*   8ビットおよび16ビットの演算子（例: `ADDB`, `ADDW`, `MOVBconst`, `MOVWconst`など）を、対応する32ビット演算子（例: `ADDL`, `MOVLconst`など）に置き換える。
*   SSA（Static Single Assignment）ルール、SSAオペレーション定義、およびSSAリライトルールから、これらのバイト/ワード命令を削除する。
*   この変更により、定数に関する一部の情報が失われる可能性があるという副作用が指摘されています。例えば、`byte`型の変数に`128`を2回加算するようなケースでは、`a += 256`と変換され、本来であれば加算自体を最適化で削除できる可能性があったものが失われます。しかし、これは稀なシナリオであるため、この最適化の放棄は許容されると判断されています。

## 変更の背景

この変更の主要な背景には、x86アーキテクチャにおける「部分レジスタストール（partial register stalls）」というパフォーマンス上の問題があります。

x86プロセッサでは、`EAX`や`RAX`のような汎用レジスタは、`AL`（下位8ビット）、`AX`（下位16ビット）、`EAX`（下位32ビット）、`RAX`（64ビット）といった異なるサイズのサブコンポーネントにアクセスできます。現代のCPUは、命令の並列実行やレジスタリネーミングといった高度な最適化技術を用いていますが、ある命令がレジスタの小さい部分（例: `AL`）に書き込み、その直後の命令が同じレジスタの大きい部分（例: `EAX`）を読み取ろうとすると、CPU内部でデータの一貫性を保つために「ストール（停止）」が発生することがあります。

このストールは、CPUが部分的な書き込みを完了し、その結果をレジスタの他の部分と結合するまで、パイプラインを一時停止させることで発生します。特に`AH`, `BH`, `CH`, `DH`といった上位8ビットレジスタへの書き込みは、古いIntel P6世代のCPUでは顕著なペナルティがありましたが、新しいアーキテクチャでも完全に解消されているわけではありません。

Goコンパイラは、この部分レジスタストールを回避するために、8ビットや16ビットの論理演算であっても、内部的に32ビット演算を使用する方針を採用しました。この方針が導入されたことで、もはや8ビットや16ビットの専用命令をSSAバックエンドで維持する必要性が薄れました。むしろ、それらを維持することは、コンパイラの複雑性を増し、最適化の機会を限定する可能性がありました。

したがって、このコミットは、既に採用されている32ビット演算への変換戦略をさらに推し進め、コンパイラのコードベースから冗長なバイト/ワード命令を削除することで、コンパイラの簡素化と潜在的なパフォーマンス向上（部分レジスタストール回避による）を図るものです。

## 前提知識の解説

### GoコンパイラのSSA（Static Single Assignment）フォーム

Goコンパイラは、最適化の主要な段階としてSSA（Static Single Assignment）フォームを使用しています。SSAフォームは、プログラム内の各変数が一度だけ代入されるように変換された中間表現です。これにより、データフロー解析や最適化が容易になります。

SSAバックエンドは、以下の主要なコンポーネントで構成されます。

1.  **SSAオペレーション (Op)**: SSAフォームにおける基本的な演算単位です。例えば、`OpAMD64ADDQ`はAMD64アーキテクチャにおける64ビット加算を表します。
2.  **SSAルール (.rulesファイル)**: `src/cmd/compile/internal/ssa/gen/AMD64.rules`のようなファイルで定義され、高レベルのSSAオペレーションを低レベルの、より具体的なマシン命令に変換するためのパターンマッチングルールを含んでいます。これらのルールは、コンパイラがコードを最適化し、ターゲットアーキテクチャの命令セットにマッピングする方法を決定します。
3.  **SSAオペレーション定義 (.goファイル)**: `src/cmd/compile/internal/ssa/gen/AMD64Ops.go`や`src/cmd/compile/internal/ssa/opGen.go`のようなファイルで、各SSAオペレーションのプロパティ（引数の数、レジスタ割り当てのヒント、アセンブリ命令へのマッピングなど）が定義されます。
4.  **SSAリライトルール (rewrite*.goファイル)**: `src/cmd/compile/internal/ssa/rewriteAMD64.go`のようなファイルで、特定のSSAオペレーションの組み合わせを、より効率的な別のSSAオペレーションの組み合わせに変換するルールが記述されています。これは、コンパイラが生成するコードの品質を向上させるための重要な最適化ステップです。

### x86アーキテクチャのレジスタと命令サイズ

x86アーキテクチャでは、レジスタのサイズに応じて異なる命令が存在します。

*   **8ビット (Byte)**: `AL`, `AH`, `BL`, `BH` など。命令のサフィックスは通常 `B` (例: `ADDB`, `MOVB`).
*   **16ビット (Word)**: `AX`, `BX`, `CX`, `DX` など。命令のサフィックスは通常 `W` (例: `ADDW`, `MOVW`).
*   **32ビット (Long/Doubleword)**: `EAX`, `EBX`, `ECX`, `EDX` など。命令のサフィックスは通常 `L` (例: `ADDL`, `MOVL`).
*   **64ビット (Quadword)**: `RAX`, `RBX`, `RCX`, `RDX` など。命令のサフィックスは通常 `Q` (例: `ADDQ`, `MOVQ`).

### 部分レジスタストール (Partial Register Stalls)

前述の通り、レジスタの小さい部分に書き込み、その後すぐに大きい部分を読み出すと、CPUのパイプラインがストールする可能性があります。これを回避するためには、常にレジスタ全体（32ビットまたは64ビット）に書き込むか、`MOVZX`（ゼロ拡張移動）や`MOVSX`（符号拡張移動）のような命令を使用して、小さい値を大きいレジスタにロードする際に上位ビットを適切にクリア/符号拡張することが推奨されます。

このコミットは、Goコンパイラがこの推奨事項に従い、8ビットや16ビットの演算を内部的に32ビット演算として扱うことで、部分レジスタストールを積極的に回避しようとするものです。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおけるAMD64アーキテクチャ固有の命令生成ロジックを広範囲にわたって変更しています。具体的には、8ビット (`B`) および16ビット (`W`) の演算子を、対応する32ビット (`L`) 演算子に置き換えることで、部分レジスタストールを回避し、コンパイラの複雑性を軽減しています。

### `src/cmd/compile/internal/amd64/ssa.go` の変更

このファイルは、SSA値からAMD64アセンブリ命令を生成する役割を担っています。
変更点としては、`ssaGenValue` 関数内で、`MOVBconst` や `MOVWconst` といったバイト/ワード定数ロード命令が `MOVLconst` に統合されています。同様に、`ADDW`, `ADDB`, `SUBW`, `SUBB` などのバイト/ワード演算命令が、対応する32ビット演算命令のケースから削除されています。これは、これらの命令がもはや直接生成されず、32ビット命令に変換されることを意味します。

例:
```diff
-	case ssa.OpAMD64ADDQ, ssa.OpAMD64ADDL, ssa.OpAMD64ADDW, ssa.OpAMD64ADDB:
+	case ssa.OpAMD64ADDQ, ssa.OpAMD64ADDL:
```
や
```diff
-	case ssa.OpAMD64MOVBconst, ssa.OpAMD64MOVWconst, ssa.OpAMD64MOVLconst, ssa.OpAMD64MOVQconst:
+	case ssa.OpAMD64MOVLconst, ssa.OpAMD64MOVQconst:
```
のように、バイト/ワード命令のケースが削除されています。

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` の変更

このファイルは、SSAの汎用オペレーションをAMD64固有のSSAオペレーションに変換するためのルールを定義しています。
変更の核心は、`Add16`, `Add8`, `Sub16`, `Sub8`, `Mul16`, `Mul8`, `And16`, `And8`, `Or16`, `Or8`, `Xor16`, `Xor8`, `Neg16`, `Neg8`, `Com16`, `Com8` といったバイト/ワード幅の演算が、それぞれ対応する32ビット幅の演算 (`ADDL`, `SUBL`, `MULL`, `ANDL`, `ORL`, `XORL`, `NEGL`, `NOTL`) に直接変換されるようにルールが変更された点です。

例:
```diff
-(Add16 x y) -> (ADDW x y)
-(Add8 x y) -> (ADDB x y)
+(Add16 x y) -> (ADDL x y)
+(Add8 x y) -> (ADDL x y)
```
これにより、コンパイラのSSA最適化パスの早い段階で、バイト/ワード演算が32ビット演算として扱われるようになります。シフト演算 (`Lsh`, `Rsh`) や比較演算 (`CMPWconst`, `CMPBconst`) のルールも同様に、32ビット演算を介するように変更されています。

また、`Const8`, `Const16`, `ConstBool` といった定数生成も `MOVLconst` に統一されています。

### `src/cmd/compile/internal/ssa/gen/AMD64Ops.go` の変更

このファイルは、AMD64アーキテクチャの各SSAオペレーションのメタデータを定義しています。
`ADDW`, `ADDB`, `SUBW`, `SUBB`, `MULW`, `MULB`, `ANDW`, `ANDB`, `ORW`, `ORB`, `XORW`, `XORB`, `SHLW`, `SHLB`, `NEGW`, `NEGB`, `NOTW`, `NOTB`, `MOVBconst`, `MOVWconst` といったオペレーションの定義がこのファイルから完全に削除されています。これは、これらのオペレーションがSSAバックエンドの内部で直接使用されなくなることを意味します。

### `src/cmd/compile/internal/ssa/opGen.go` の変更

このファイルは、SSAオペレーションの列挙型と、それらのオペレーションに関する詳細情報を含むテーブルを生成します。
`OpAMD64ADDW`, `OpAMD64ADDB` など、削除されたバイト/ワード命令に対応する定数と、`opcodeTable` 内の関連エントリが削除されています。これにより、コンパイラのSSA中間表現からこれらの命令が完全に姿を消します。

### `src/cmd/compile/internal/ssa/regalloc_test.go` の変更

レジスタ割り当てのテストファイルです。
`OpAMD64MOVBconst` を使用していたテストケースが `OpAMD64MOVLconst` に変更されています。これは、バイト定数が32ビット定数として扱われるようになったことを反映したものです。

例:
```diff
-			Valu("x", OpAMD64MOVBconst, TypeInt8, 1, nil),
-			Valu("y", OpAMD64MOVBconst, TypeInt8, 2, nil),
+			Valu("x", OpAMD64MOVLconst, TypeInt8, 1, nil),
+			Valu("y", OpAMD64MOVLconst, TypeInt8, 2, nil),
```

### `src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更

このファイルは、AMD64固有のSSAリライトルールを含んでいます。
`rewriteValueAMD64` 関数から、削除されたバイト/ワード命令に対応するリライト関数への呼び出しが削除されています。また、`rewriteValueAMD64_OpAMD64ADDB`, `rewriteValueAMD64_OpAMD64ADDBconst` など、多くのバイト/ワード命令に関するリライト関数自体がファイルから削除されています。これは、これらの命令がSSA中間表現に存在しなくなるため、それらを処理するリライトルールも不要になったためです。

## コアとなるコードの解説

上記のコード変更は、GoコンパイラのSSAバックエンドが、AMD64アーキテクチャにおいて8ビットおよび16ビットの整数演算を、明示的に32ビットの整数演算として扱うように再構築されたことを示しています。

1.  **`src/cmd/compile/internal/ssa/gen/AMD64.rules` の変更**:
    *   `Add16 x y) -> (ADDL x y)` や `(Add8 x y) -> (ADDL x y)` のようなルールは、Go言語のソースコードで16ビットまたは8ビットの加算が記述された場合、SSA中間表現の段階で直接AMD64の32ビット加算命令 (`ADDL`) にマッピングされることを意味します。
    *   同様に、`Const8 [val]) -> (MOVLconst [val])` や `(Const16 [val]) -> (MOVLconst [val])` は、8ビットや16ビットの定数が、32ビット定数ロード命令 (`MOVLconst`) を使ってレジスタにロードされることを示します。
    *   これらの変更は、コンパイラが生成するアセンブリコードにおいて、バイト/ワード幅のレジスタ操作を極力避け、代わりに32ビット幅のレジスタ操作を利用することで、前述の「部分レジスタストール」を回避し、CPUのパイプライン効率を向上させることを狙っています。32ビット操作は、レジスタ全体を書き換えるため、CPUが古い部分レジスタの値と新しい部分レジスタの値を結合する手間が省けます。

2.  **`src/cmd/compile/internal/ssa/gen/AMD64Ops.go` および `src/cmd/compile/internal/ssa/opGen.go` の変更**:
    *   これらのファイルから `ADDW`, `ADDB`, `MOVBconst`, `MOVWconst` などのオペレーション定義が削除されたことは、SSA中間表現自体がこれらの粒度の低い命令を直接表現しなくなることを意味します。つまり、コンパイラの内部モデルからこれらの概念が取り除かれ、より抽象度の高い（この場合は32ビット幅の）操作に統一されます。これにより、コンパイラのコードベースが簡素化され、保守性が向上します。

3.  **`src/cmd/compile/internal/amd64/ssa.go` および `src/cmd/compile/internal/ssa/rewriteAMD64.go` の変更**:
    *   `ssaGenValue` 関数からバイト/ワード命令のケースが削除されたこと、および `rewriteAMD64.go` から関連するリライト関数が削除されたことは、これらの命令がもはやコード生成の最終段階や最適化の段階で直接扱われることがないという結果を反映しています。SSAルールによって32ビット命令に変換された後、それらの32ビット命令が通常のフローで処理されるようになります。

このアプローチの唯一の欠点として、コミットメッセージで述べられているように、`var a byte = ...; a += 128; a += 128` のような特定のケースで、コンパイラが `a += 256` と変換してしまい、本来可能であった「加算の削除」という最適化を見逃す可能性があります。これは、バイト型変数のオーバーフロー挙動が32ビット演算に持ち上げられることで、コンパイラが元のバイト型のセマンティクスを完全に追跡できなくなるためです。しかし、このようなシナリオは稀であると判断され、部分レジスタストール回避による全体的なパフォーマンス向上とコンパイラの簡素化のメリットが上回ると考えられています。

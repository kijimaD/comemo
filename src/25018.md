## 元コミット内容

Go言語のパーサーが、不正な型スイッチのヘッダーに対して、より適切なエラーメッセージを生成するように変更されました。これはIssue 11829を修正するものです。

## 変更の背景

Go言語の型スイッチは、インターフェース型の変数が実行時にどの具体的な型を持つかを判断し、それに応じた処理を行うための強力な構文です。型スイッチのヘッダーでは、通常、`switch v := x.(type)` のように、新しい変数を宣言し、その変数に型アサーションの結果を代入する形式（ショート変数宣言 `:=`）が用いられます。

しかし、ユーザーが誤って代入演算子`=`を使用して `switch v = x.(type)` のように記述した場合、Goパーサーは以前、この構文エラーに対して必ずしも明確なエラーメッセージを返していませんでした。例えば、`switch t = t.(type)` のようなコードは、`expected switch expression` のような、直接的ではないエラーメッセージを生成することがありました。これは、ユーザーがなぜコードがコンパイルされないのかを理解するのを困難にしていました。

このコミットは、このような一般的な構文エラーに対して、より具体的で分かりやすいエラーメッセージ（例: `expected ':=', found '='`）を提供することで、開発者のデバッグ体験を向上させることを目的としています。Issue 11829で報告された問題に対応しています。

## 前提知識の解説

### Go言語のパーサー (`go/parser`パッケージ)

`go/parser`パッケージは、Go言語のソースコードを解析し、抽象構文木（AST: Abstract Syntax Tree）を構築するための標準ライブラリです。コンパイラや各種ツール（`go fmt`, `go vet`など）の基盤として利用されます。パーサーは、ソースコードの字句解析（トークン化）と構文解析を行い、文法規則に沿っているかをチェックし、エラーがあれば報告します。

### 型スイッチ (Type Switch)

型スイッチは、Go言語における制御構造の一つで、インターフェース型の変数の動的な型に基づいて異なるコードブロックを実行するために使用されます。

基本的な構文は以下の通りです。

```go
switch v := i.(type) {
case int:
    fmt.Printf("iはint型で、値は%dです\n", v)
case string:
    fmt.Printf("iはstring型で、値は%sです\n", v)
default:
    fmt.Printf("iは未知の型です (型: %T)\n", i)
}
```

ここで、`v := i.(type)` の部分が「型スイッチのガード句」と呼ばれます。`i.(type)` は特別な型アサーションで、`switch`ステートメントのコンテキストでのみ有効です。`:=` はショート変数宣言であり、`v`という新しい変数を宣言し、`i`の具体的な型をその変数に代入します。

### `token`パッケージ

`go/token`パッケージは、Go言語のソースコードを構成するトークン（識別子、キーワード、演算子、リテラルなど）を定義します。例えば、`token.ASSIGN`は代入演算子`=`を、`token.DEFINE`はショート変数宣言演算子`:=`を表します。パーサーはこれらのトークンを識別して構文解析を進めます。

### `ast`パッケージ

`go/ast`パッケージは、`go/parser`によって生成される抽象構文木（AST）のノード型を定義します。例えば、`ast.ExprStmt`は式ステートメントを、`ast.AssignStmt`は代入ステートメントを表します。

## 技術的詳細

この変更の核心は、`go/parser`パッケージ内の`isTypeSwitchGuard`関数にあります。この関数は、`switch`ステートメントの初期化部分が型スイッチのガード句として有効かどうかを判断します。

変更前は、`isTypeSwitchGuard`関数は、`*ast.AssignStmt`（代入ステートメント）の場合に、左辺が1つ、右辺が1つ、トークンが`token.DEFINE`（`:=`）であり、右辺が型アサーション（`x.(type)`）である場合にのみ`true`を返していました。つまり、`v = x.(type)` のような`=`を使った代入は、型スイッチのガード句として認識されず、結果としてパーサーはより一般的な、そしてしばしば誤解を招くエラーを報告していました。

変更後、`isTypeSwitchGuard`関数は以下のように動作します。

1.  `*ast.AssignStmt`の場合、まず左辺が1つ、右辺が1つ、右辺が型アサーションであるという条件をチェックします。
2.  次に、代入トークンが`token.ASSIGN`（`=`）であるかどうかを調べます。
3.  もし`token.ASSIGN`であれば、パーサーの`error`メソッドを呼び出して、`expected ':=', found '='` という具体的なエラーメッセージを報告します。
4.  エラーを報告した後、`fallthrough`キーワードを使用することで、処理を`token.DEFINE`の場合に継続させます。これにより、パーサーは`v = x.(type)`を`v := x.(type)`として解釈しようと試み、後続の解析を可能にしつつ、適切なエラーメッセージをユーザーに提供します。
5.  `token.DEFINE`であれば、そのまま`true`を返します。

この変更により、パーサーは不正な`=`の使用を早期に検出し、ユーザーに直接的なフィードバックを提供できるようになりました。

## コアとなるコードの解説

### `src/go/parser/parser.go`

-   **`func isTypeSwitchGuard(s ast.Stmt) bool` から `func (p *parser) isTypeSwitchGuard(s ast.Stmt) bool` への変更**:
    -   関数がトップレベルの関数から`parser`構造体のメソッドに変更されました。これにより、`isTypeSwitchGuard`関数内で`parser`インスタンスの`error`メソッドを呼び出してエラーを報告できるようになります。これは、パーサーが構文エラーを検出した際に、そのエラーをパーサーの状態（エラーリストなど）に記録するための標準的なパターンです。

-   **`case *ast.AssignStmt:` ブロック内の変更**:
    -   `if len(t.Lhs) == 1 && len(t.Rhs) == 1 && isTypeSwitchAssert(t.Rhs[0])`：この条件は、代入ステートメントが単一の左辺と単一の右辺を持ち、右辺が型アサーション（`x.(type)`）であるという、型スイッチガード句の基本的な構造を満たしているかをチェックします。
    -   `switch t.Tok { case token.ASSIGN:`：代入トークンが`=`（`token.ASSIGN`）である場合に特化した処理が追加されました。
    -   `p.error(t.TokPos, "expected ':=', found '='")`：ここで、`parser`インスタンスの`error`メソッドが呼び出され、具体的なエラーメッセージ「`expected ':=', found '='`」が生成されます。`t.TokPos`はエラーが発生したトークンの位置を示します。
    -   `fallthrough`：このキーワードは、`token.ASSIGN`ケースの処理が完了した後、次の`token.DEFINE`ケースの処理も実行するように指示します。これにより、パーサーは`=`を`:=`として「許容」し、構文解析を続行できます。これは、エラーを報告しつつも、その後の解析が可能な限り進むようにするための一般的なパーサーのテクニックです。
    -   `case token.DEFINE:`：トークンが`:=`（`token.DEFINE`）である場合は、以前と同様に`true`を返します。

-   **`parseSwitchStmt` 関数内の変更**:
    -   `typeSwitch := isTypeSwitchGuard(s2)` から `typeSwitch := p.isTypeSwitchGuard(s2)` へと変更されました。これは、`isTypeSwitchGuard`関数が`parser`メソッドになったことに伴う呼び出し元の修正です。

### `src/go/parser/short_test.go`

-   **テストケースの修正**:
    -   `package p; func f() { switch t /* ERROR "expected switch expression" */ = t.(type) {} };`
        が

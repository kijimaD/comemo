# [インデックス 25485] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）におけるインストゥルメンテーション（特にデータ競合検出器やMemorySanitizer）の処理に関するバグ修正です。外部変数（`PEXTERN`）の型情報がインストゥルメンテーションパス実行時に適切に設定されていない場合に発生する問題を解決し、`uintptr`のオーバーフローエラーを防ぎます。

## 元コミット内容

このコミットは、Goコンパイラの`cmd/compile`において、インストゥルメンテーションされた呼び出しが型の幅（`type width`）を持つことを保証するものです。具体的には、型リテラルで定義された外部変数（`PEXTERN`）の型の幅が、インストゥルメンテーションパスが実行される際に設定されていない可能性があるという問題に対処しています。この問題により、標準ライブラリの`encoding/base32`と`encoding/json`で`constant -1000000000 overflows uintptr`というエラーが発生していました。修正は、`dowidth`関数を呼び出すことで、型の幅が確実に設定されるようにすることです。

## 変更の背景

Goコンパイラは、プログラムの実行時に特定の動作を監視・検出するために、コードに特別な命令（インストゥルメンテーション）を挿入することがあります。代表的なものに、データ競合を検出するRace Detectorや、メモリの不正アクセスを検出するMemorySanitizer (MSan) があります。これらのインストゥルメンテーションは、変数の読み書きの際に、その変数のアドレスとサイズ（型の幅）をランタイム関数に渡すことで機能します。

このコミットが修正しようとしている問題は、特定の条件下で、インストゥルメンテーションが必要とする変数の「型の幅」情報が、コンパイル時にまだ計算されていない、または設定されていないというものでした。具体的には、型リテラル（例: `var myVar struct { ... }`）で定義された外部変数（`PEXTERN`）がこの問題を引き起こしていました。

型の幅が未設定（`BADWIDTH`）の状態でインストゥルメンテーションコードが生成されると、ランタイム関数に渡されるべきサイズ情報が不正な値となり、結果として`constant -1000000000 overflows uintptr`のようなコンパイルエラーが発生していました。コミットメッセージに記載されているように、`src/encoding/base32/base32.go`と`src/encoding/json/encode.go`でこのエラーが報告されていました。これは、これらのパッケージが特定の外部変数を型リテラルで定義しており、それがインストゥルメンテーションの対象となった際に問題が顕在化したことを示唆しています。

この変更の目的は、インストゥルメンテーションコードを生成する前に、対象となる変数の型の幅が常に正しく計算され、設定されていることを保証し、コンパイルエラーを防ぐことにあります。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造と概念に関する知識が必要です。

1.  **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。複数のステージ（字句解析、構文解析、型チェック、中間表現生成、最適化、コード生成など）を経て処理を行います。
2.  **インストゥルメンテーション (Instrumentation)**: プログラムの実行時に特定のイベント（例: メモリアクセス、関数呼び出し）を監視するために、コンパイラが自動的に追加するコードのことです。Goでは主に以下の目的で利用されます。
    *   **Race Detector**: 複数のゴルーチンが共有メモリに同時にアクセスし、少なくとも一方が書き込みである場合に発生するデータ競合を検出します。
    *   **MemorySanitizer (MSan)**: 初期化されていないメモリの読み取りを検出します。
3.  **型の幅 (`Type Width`)**: Goコンパイラ内部で、各データ型がメモリ上で占めるバイト数を指します。例えば、`int32`の幅は4バイト、`int64`は8バイトです。構造体や配列の場合、その要素の型や配置によって幅が計算されます。この幅情報は、メモリの割り当て、アクセス、およびインストゥルメンテーションにおいて非常に重要です。
4.  **`PEXTERN` (External Variable)**: Goコンパイラ内部の概念で、外部リンケージを持つ変数、つまり他のパッケージから参照可能なグローバル変数を指します。これらの変数は、コンパイルの初期段階では完全な型情報（特にメモリ上の幅）が確定していない場合があります。
5.  **`dowidth` 関数**: `src/cmd/compile/internal/gc/type.go`（当時のパス）などに存在するコンパイラ内部関数で、与えられた型のメモリ上の幅を計算し、その型情報に設定する役割を担います。この関数は、型の完全な情報が必要になった時点で呼び出されることがあります。
6.  **`BADWIDTH`**: 型の幅がまだ計算されていない、または無効な状態であることを示す内部的な定数です。
7.  **`uintptr`**: Goの組み込み型で、ポインタ値を整数として表現できる型です。通常、ポインタ演算やシステムコールなどで使用されます。`uintptr`に不正な定数（例: `BADWIDTH`が変換された負の値）を渡そうとすると、オーバーフローエラーが発生します。
8.  **`mkcall`**: コンパイラ内部で、ランタイム関数への呼び出しを表すASTノードを生成する関数です。インストゥルメンテーションでは、この`mkcall`を使って`msanread`や`raceread`などのランタイム関数呼び出しを挿入します。
9.  **`Node`**: Goコンパイラの抽象構文木（AST）におけるノードを表す構造体です。プログラムの各要素（変数、式、関数呼び出しなど）が`Node`として表現されます。
10. **`NodeList`**: `Node`のリストです。
11. **`uintptraddr(n)`**: `Node n`のアドレスを`uintptr`として取得するコンパイラ内部関数です。
12. **`Nodintconst(v)`**: 整数定数`v`を表す`Node`を生成するコンパイラ内部関数です。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの`cmd/compile/internal/gc/racewalk.go`ファイル内の`callinstr`関数にあります。`callinstr`関数は、Race DetectorやMemorySanitizerのためのインストゥルメンテーションコードを挿入する役割を担っています。

インストゥルメンテーションでは、メモリの読み書きを監視するために、対象となるメモリ領域の開始アドレスとサイズ（幅）をランタイム関数に渡す必要があります。このサイズ情報は、変数の型情報（`t.Width`）から取得されます。

問題は、`PEXTERN`として定義された外部変数の場合、`callinstr`が実行される時点で、その変数の型`t`の`Width`フィールドがまだ計算されていない（`BADWIDTH`の状態である）可能性があったことです。これは、コンパイラの処理順序や、型の遅延評価のメカニズムに起因します。特に、型リテラルで定義された外部変数は、その型の完全な情報がすぐに必要とされない限り、`dowidth`関数による幅の計算が後回しにされることがあります。

`callinstr`関数内で`t.Width`を直接参照すると、`BADWIDTH`が使用されてしまい、これが`Nodintconst`を通じて`uintptr`に変換される際に、不正な値（例: `-1000000000`）となり、`uintptr`の範囲を超過するというエラーが発生していました。

このコミットの修正は、`t.Width`を使用する直前に`dowidth(t)`を明示的に呼び出すことで、この問題を解決しています。`dowidth(t)`が呼び出されることで、`t`の型の幅が強制的に計算され、`t.Width`には正しい値が設定されることが保証されます。これにより、インストゥルメンテーションコードが正しいサイズ情報で生成され、コンパイルエラーが解消されます。

また、`test.bash`の変更は、MemorySanitizer (`-msan`) を有効にした状態で標準ライブラリをビルドするテストを追加しており、この修正がMSan環境下でも正しく機能することを確認するためのものです。

## コアとなるコードの解説

`src/cmd/compile/internal/gc/racewalk.go`内の`callinstr`関数は、インストゥルメンテーションの対象となるメモリ操作（読み書き）に対して、対応するランタイム関数呼び出しを挿入する役割を担います。

変更前のコードでは、`mkcall`関数を使ってランタイム関数呼び出しを生成する際に、引数として`t.Width`（型の幅）を直接渡していました。

```go
f = mkcall(name, nil, init, uintptraddr(n), Nodintconst(t.Width))
```

しかし、前述の通り、`PEXTERN`変数などの場合、この時点で`t.Width`が`BADWIDTH`である可能性がありました。

変更後のコードでは、`t.Width`を使用する直前に以下の行が追加されています。

```go
// dowidth may not have been called for PEXTERN.
dowidth(t)
w := t.Width
if w == BADWIDTH {
    Fatalf("instrument: %v badwidth", t)
}
f = mkcall(name, nil, init, uintptraddr(n), Nodintconst(w))
```

1.  `dowidth(t)`: この行が最も重要な変更点です。`t`で表される型の幅がまだ計算されていない場合、この呼び出しによって幅が強制的に計算され、`t.Width`フィールドに正しい値が設定されます。これにより、後続の処理で常に有効な幅情報が利用可能になります。
2.  `w := t.Width`: `dowidth`の呼び出し後、`t.Width`から計算された幅を取得し、ローカル変数`w`に格納します。
3.  `if w == BADWIDTH { Fatalf("instrument: %v badwidth", t) }`: 安全策として、`dowidth`を呼び出した後でも`w`が`BADWIDTH`である場合は、コンパイラを異常終了させます。これは、`dowidth`が何らかの理由で幅を計算できなかった場合のデバッグを助けるためのチェックです。
4.  `f = mkcall(name, nil, init, uintptraddr(n), Nodintconst(w))`: 最後に、`mkcall`を使ってランタイム関数呼び出しを生成しますが、このとき`t.Width`の代わりに、`dowidth`によって保証された正しい幅`w`を使用します。

この修正により、インストゥルメンテーションが必要とする型の幅が常に正確に提供されるようになり、`uintptr`オーバーフローエラーが解消されました。

`misc/cgo/testsanitizers/test.bash`の変更は、`go build -msan std`コマンドを追加することで、MemorySanitizerを有効にした状態でGo標準ライブラリ全体が問題なくビルドできることを確認するテストケースを追加しています。これにより、この修正が広範囲にわたって有効であることを検証しています。

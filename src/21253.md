# [インデックス 21253] ファイルの概要

このコミットは、Goコンパイラ（`cmd/gc`）とGoランタイム（`src/runtime`）に、新しいコンパイラディレクティブ `//go:nowritebarrier` を導入するものです。このディレクティブは、特定の関数がライトバリアを必要としないことをコンパイラにアサート（表明）させるためのもので、主にGoランタイム内部でのみ使用されます。変更は、コンパイラの字句解析、構文解析、およびコード生成フェーズにわたって行われ、ランタイムのガベージコレクション関連のコードにこのディレクティブが適用されています。

変更された主なファイルは以下の通りです。

*   `src/cmd/gc/go.h`: コンパイラの内部データ構造に `nowritebarrier` フラグを追加。
*   `src/cmd/gc/go.y`: コンパイラの構文解析器の定義ファイルで、関数宣言に `nowritebarrier` フラグを関連付けるルールを追加。
*   `src/cmd/gc/lex.c`: コンパイラの字句解析器で `//go:nowritebarrier` ディレクティブを認識し、対応するフラグを設定するロジックを追加。
*   `src/cmd/gc/walk.c`: コンパイラのウォークフェーズ（コード変換）で、ライトバリアが挿入されるべき場所で `nowritebarrier` フラグが設定されている場合にエラーを報告するロジックを追加。
*   `src/cmd/gc/y.tab.c`: `go.y` から生成される構文解析器のC言語ソースファイル。
*   `src/runtime/mgc.go`: Goランタイムのガベージコレクション関連のコード。多くのGCヘルパー関数に `//go:nowritebarrier` ディレクティブが追加されています。
*   `src/runtime/proc1.go`: Goランタイムのプロセス管理関連のコード。一部の関数に `//go:nowritebarrier` ディレクティブが追加されています。

## 元コミット内容

このコミットは、Goコンパイラに `//go:nowritebarrier` という新しいディレクティブを追加します。このディレクティブは、意図しないライトバリアの挿入を診断することを目的としています。`//go:nowritebarrier` は `runtime` パッケージ内でのみ使用が許可されており、ライトバリアを無効にするものではなく、その後の関数がライトバリアを必要としないというコンパイラによるアサート（表明）として機能します。コンパイラはこのアサートをチェックし、違反があればエラーを報告します。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行と並行して動作するコンカレントGCを採用しています。この並行性を維持しつつGCの正確性を保証するために、「ライトバリア」というメカニズムが導入されています。ライトバリアは、ヒープ上のポインタフィールドが変更される際に自動的に挿入される小さなコード片で、GCにオブジェクト参照グラフの変更を通知する役割を担います。

しかし、Goランタイムの非常に低レベルでパフォーマンスが重視される部分では、ライトバリアのオーバーヘッドが無視できない場合があります。また、ランタイムの特定の関数は、GCの内部状態を直接操作したり、GCが停止している間に実行されたりするため、ライトバリアが不要であるか、あるいはむしろGCの動作を妨げる可能性さえあります。

このような背景から、開発者は特定の関数がライトバリアを必要としないことをコンパイラに明示的に伝え、もし誤ってライトバリアが挿入されそうになった場合にコンパイラエラーとして検出したいというニーズがありました。このコミットは、そのためのメカニズムとして `//go:nowritebarrier` ディレクティブを導入することで、ランタイムコードの正確性とパフォーマンスを向上させることを目的としています。

## 前提知識の解説

### Goのガベージコレクション (GC)

Goは、自動メモリ管理のためにガベージコレクション（GC）を使用します。GoのGCは、**コンカレント（並行）**かつ**トライカラー（三色）マーキング**アルゴリズムに基づいています。

*   **コンカレントGC**: アプリケーションの実行（ミューテーター）とGCのマークフェーズが並行して動作します。これにより、アプリケーションの一時停止時間（ストップ・ザ・ワールド、STW）を最小限に抑え、レイテンシを低減します。
*   **トライカラーマーキング**: GCはヒープ上のオブジェクトを以下の三色に分類して追跡します。
    *   **白 (White)**: GCによってまだ訪問されていないオブジェクト。到達不可能であれば最終的に回収されます。
    *   **灰 (Gray)**: GCによって訪問されたが、その参照先（子オブジェクト）がまだスキャンされていないオブジェクト。
    *   **黒 (Black)**: GCによって訪問され、その参照先もすべてスキャンされたオブジェクト。

GCの基本的な不変条件は、「黒オブジェクトが白オブジェクトを指してはならない」というものです。もし黒オブジェクトが白オブジェクトを指すことが許されると、その白オブジェクトはGCによって到達不可能と誤判断され、誤って回収されてしまう可能性があります。

### ライトバリア (Write Barrier)

コンカレントGCにおいて、ミューテーターがヒープ上のポインタを変更する際に、GCの不変条件（黒が白を指さない）を維持するために挿入されるのが**ライトバリア**です。

ライトバリアは、ポインタの書き込み操作の直前または直後に実行される小さなコードスニペットです。その主な役割は、ミューテーターが黒オブジェクトから白オブジェクトへの参照を作成しようとした場合に、その白オブジェクトをすぐに灰色の状態にマークすることです。これにより、GCがそのオブジェクトを誤って回収することを防ぎます。

例えば、`objA.field = objB` というポインタ書き込み操作があった場合、`objA` が黒で `objB` が白であれば、ライトバリアは `objB` を灰色にマークします。これにより、GCは `objB` が到達可能であることを認識し、回収対象から除外します。

### Goランタイム

Goランタイムは、Goプログラムの実行を支える低レベルなシステムです。これには、スケジューラ、ガベージコレクタ、メモリ管理、プリミティブな同期メカニズム、システムコールインターフェースなどが含まれます。GoランタイムのコードはGo言語とアセンブリ言語で書かれており、Goプログラムが効率的かつ安全に動作するための基盤を提供します。ランタイムのコードは非常にパフォーマンスに敏感であり、細部にわたる最適化が施されています。

## 技術的詳細

このコミットで導入された `//go:nowritebarrier` ディレクティブは、Goコンパイラに対する特別な指示（プラグマ）です。その技術的な詳細は以下の通りです。

1.  **目的はアサート、無効化ではない**: `//go:nowritebarrier` は、その後に続く関数がライトバリアを必要としないことをコンパイラに「アサート」するものです。これは、ライトバリアの挿入を強制的に無効にするものではありません。むしろ、コンパイラがその関数内でライトバリアを挿入する必要があると判断した場合、コンパイル時にエラーを発生させます。これにより、開発者は意図しないライトバリアの挿入を早期に発見し、修正することができます。

2.  **`runtime` パッケージに限定**: このディレクティブは、Goの標準ライブラリの中でも特に低レベルな `runtime` パッケージ内でのみ使用が許可されています。`src/cmd/gc/lex.c` の変更で、`compiling_runtime` フラグがチェックされ、`runtime` パッケージ以外でこのディレクティブが使用された場合はコンパイルエラー `yyerror("go:nowritebarrier only allowed in runtime")` が発生します。これは、`//go:nowritebarrier` が非常に特殊なケース（GCの内部動作やパフォーマンスクリティカルな低レベルコード）のために設計されており、一般的なアプリケーションコードでの使用は推奨されないためです。

3.  **コンパイラによるチェック**:
    *   **字句解析と構文解析**: `src/cmd/gc/lex.c` で `//go:nowritebarrier` コメントが認識されると、コンパイラの内部状態に `nowritebarrier` フラグが設定されます。`src/cmd/gc/go.y` では、関数宣言の構文解析時にこのフラグが読み取られ、関数の抽象構文木（AST）ノードに `nowritebarrier` プロパティとして記録されます。
    *   **ライトバリア挿入時の検証**: `src/cmd/gc/walk.c` の `applywritebarrier` 関数は、コンパイラがライトバリアを挿入すべき場所を特定する際に呼び出されます。この関数内で、現在処理中の関数（`curfn`）の `nowritebarrier` フラグが設定されているかどうかがチェックされます。もし設定されていれば、コンパイラは `yyerror("write barrier prohibited")` というエラーを発生させ、コンパイルを中断します。

4.  **なぜランタイムでライトバリアを無効にする必要があるのか**:
    *   **パフォーマンスの最適化**: Goランタイムの多くの部分は、非常にパフォーマンスがクリティカルです。ライトバリアはわずかなオーバーヘッドを導入するため、これらの関数からライトバリアを排除することで、全体の実行速度を向上させることができます。
    *   **直接的なメモリ操作**: ランタイムは、GCの内部状態と密接に連携しながらメモリを直接操作することがよくあります。このような場合、通常のライトバリアのロジックは冗長であるか、あるいはGCの内部不変条件と衝突する可能性があります。
    *   **GC状態の認識**: `//go:nowritebarrier` が適用される関数は、GCが特定の状態（例: STW中、またはライトバリアが不要なフェーズ）にあるときに呼び出されることが想定されます。このような状況では、ライトバリアは不要であり、むしろGCの動作を妨げる可能性があります。
    *   **デッドロック/ライブロックの回避**: ごく稀なケースですが、ランタイムの特定のシナリオでは、ライトバリアの挿入がGCの内部メカニズムとの間でデッドロックやライブロックを引き起こす可能性があります。`//go:nowritebarrier` は、このような潜在的な問題を回避するための手段を提供します。

このディレクティブは、Goランタイム開発者がミューテーターとガベージコレクタ間の相互作用を微調整し、Goシステムの最も深い層で正確性と最適なパフォーマンスの両方を確保するための強力なツールです。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は、Goコンパイラが `//go:nowritebarrier` ディレクティブを認識し、処理し、そしてランタイムコードに適用されるようにするためのものです。

1.  **`src/cmd/gc/go.h`**:
    `Node` 構造体（コンパイラがコードの各要素を表すために使用するノード）に新しいフィールド `nowritebarrier` が追加されました。これは `uchar` 型で、関数がライトバリアを必要としないことを示すフラグとして機能します。

    ```diff
     	uchar	walkdef;
     	uchar	typecheck;
     	uchar	local;
    @@ -987,6 +988,7 @@ EXTERN	int	flag_race;
     EXTERN	int	flag_largemodel;

     EXTERN	int	nosplit;
    +EXTERN	int	nowritebarrier;
    ```

    字句解析器において、`//go:nowritebarrier` というコメントが検出された場合に、`nowritebarrier` グローバルフラグを `1` に設定するロジックが追加されました。同時に、`compiling_runtime` フラグをチェックし、`runtime` パッケージ以外でこのディレクティブが使用された場合はエラーを報告します。

    `applywritebarrier` 関数（コンパイラがライトバリアを挿入すべき場所を決定する際に呼び出される）において、現在処理中の関数（`curfn`）の `nowritebarrier` フラグが設定されている場合、ライトバリアの挿入が禁止されていることを示すエラー `yyerror("write barrier prohibited")` を発生させるチェックが追加されました。

5.  **`src/runtime/mgc.go` および `src/runtime/proc1.go`**:
    Goランタイムのガベージコレクションおよびプロセス管理に関連する多数の関数に、新しく導入された `//go:nowritebarrier` ディレクティブが追加されました。これにより、これらの関数がライトバリアを必要としないことがコンパイラに明示的に伝えられます。例えば、`mgc.go` では `inheap`, `slottombits`, `greyobject`, `scanobject` など、GCのコアとなる多くのヘルパー関数にこのディレクティブが適用されています。

    ```go
    //go:nowritebarrier

    // src/runtime/proc1.go の例
    //go:nosplit
    //go:nowritebarrier
    func save(pc, sp uintptr) { ... }
    ```

## コアとなるコードの解説

これらの変更は、Goコンパイラが `//go:nowritebarrier` ディレクティブをエンドツーエンドで処理し、ランタイムコードの特定のセクションでライトバリアの挿入を「アサート」としてチェックするメカニズムを構築しています。

1.  **ディレクティブの認識 (`src/cmd/gc/lex.c`)**:
    コンパイラの字句解析フェーズで、ソースコード中の `//go:nowritebarrier` というコメントが特別なディレクティブとして認識されます。`lex.c` の `go:` ラベル内の `strcmp` 呼び出しがこれを行います。このディレクティブが検出されると、グローバル変数 `nowritebarrier` が `1` に設定されます。同時に、`compiling_runtime` フラグがチェックされ、`runtime` パッケージのコンパイル中でない場合はエラーが報告されます。これは、このディレクティブがランタイムの内部実装に特化したものであることを強制するためです。

2.  **関数ノードへのフラグの伝播 (`src/cmd/gc/go.y`)**:
    字句解析器が `nowritebarrier` フラグを設定した後、構文解析器（`go.y` で定義）が関数宣言を処理する際に、このグローバルな `nowritebarrier` フラグの値を、現在解析中の関数の抽象構文木（AST）ノードの `nowritebarrier` フィールドにコピーします。これにより、個々の関数がライトバリアを必要としないという情報が、その関数のASTノードに永続的に関連付けられます。関数宣言の処理が完了すると、グローバルな `nowritebarrier` フラグはリセットされ、次の関数宣言に影響を与えないようにします。

3.  **ライトバリア挿入時のチェック (`src/cmd/gc/walk.c`)**:
    コンパイラの「ウォーク」フェーズ（ASTを走査し、最適化やコード変換を行うフェーズ）において、`applywritebarrier` 関数が呼び出されます。この関数は、ポインタの書き込み操作が行われる場所で、ライトバリアを挿入する必要があるかどうかを判断します。ここで、現在処理中の関数（`curfn`）のASTノードに設定されている `nowritebarrier` フラグがチェックされます。もしこのフラグが `1` であれば、それは開発者がこの関数ではライトバリアが不要であると明示的にアサートしていることを意味します。したがって、もし `applywritebarrier` がライトバリアを挿入する必要があると判断した場合、このアサートに違反するため、コンパイラは `yyerror("write barrier prohibited")` というエラーを発生させ、コンパイルを停止します。

4.  **ランタイムへの適用 (`src/runtime/mgc.go`, `src/runtime/proc1.go`)**:
    最終的に、Goランタイムのソースコード、特にガベージコレクションに関連する `mgc.go` や、低レベルなプロセス管理を行う `proc1.go` の多くの関数に、この `//go:nowritebarrier` ディレクティブが追加されました。これにより、これらのパフォーマンスクリティカルな関数において、意図しないライトバリアの挿入がコンパイル時に検出されるようになり、ランタイムの正確性と効率性が向上します。

この一連の変更により、Goコンパイラはランタイム開発者に対して、ライトバリアの挙動をより細かく制御し、潜在的な問題を早期に特定するための強力な診断ツールを提供することになります。

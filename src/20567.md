# [インデックス 20567] ファイルの概要

このコミットは、Go言語の標準ライブラリである`bytes`パッケージと`strings`パッケージに含まれる`FieldsFunc`関数のドキュメントを更新し、この関数に渡される分割関数`f`がステートフルであってはならないことを明記するものです。これにより、`FieldsFunc`の予期せぬ動作やクラッシュを防ぎ、開発者がより安全にこの関数を使用できるようになります。

## 変更の背景

このコミットは、Go言語の`bytes.FieldsFunc`および`strings.FieldsFunc`関数が、ユーザーが提供する分割関数`f`がステートフルである場合に、予期せぬ動作やクラッシュを引き起こす可能性があった問題（Issue #8738）に対応するために行われました。

`FieldsFunc`は、文字列やバイトスライスを特定の条件に基づいて分割するための柔軟なメカニズムを提供します。この関数は、各Unicodeコードポイント（`rune`）に対してユーザー定義の関数`f`を呼び出し、`f`が`true`を返す場合にそのコードポイントを区切り文字として扱います。しかし、`FieldsFunc`の実装は、`f`が呼び出される順序について何の保証もしていません。つまり、`FieldsFunc`は内部的に最適化のために、文字列の異なる部分に対して`f`を任意の順序で、あるいは複数回呼び出す可能性があります。

もし`f`がステートフル（つまり、呼び出されるたびに内部状態が変化し、同じ入力に対して異なる結果を返す可能性がある）である場合、この順序の保証がないことが問題を引き起こします。例えば、`f`が呼び出し回数に基づいて異なる結果を返すように設計されている場合、`FieldsFunc`が`f`を呼び出す順序や回数が不定であるため、最終的な分割結果が非決定論的になったり、最悪の場合、`f`の内部状態が不正になりプログラムがクラッシュしたりする可能性がありました。

このコミットは、コードの動作を変更するのではなく、この重要な制約をドキュメントに明記することで、開発者が`FieldsFunc`を安全かつ正しく使用するための指針を提供することを目的としています。

## 前提知識の解説

### `bytes.FieldsFunc`と`strings.FieldsFunc`

Go言語の`bytes`パッケージと`strings`パッケージは、それぞれバイトスライスと文字列を操作するためのユーティリティ関数を提供します。`FieldsFunc`は、これらのパッケージに共通して存在する関数で、以下のようなシグネチャを持ちます。

- `func FieldsFunc(s []byte, f func(rune) bool) [][]byte` (bytesパッケージ)
- `func FieldsFunc(s string, f func(rune) bool) []string` (stringsパッケージ)

これらの関数は、入力としてバイトスライス`s`または文字列`s`、そして`func(rune) bool`型の関数`f`を受け取ります。関数`f`は、各Unicodeコードポイント（`rune`）が区切り文字であるかどうかを判断するために使用されます。`f(c)`が`true`を返す場合、その`rune c`は区切り文字とみなされ、`s`はその区切り文字の連続で分割されます。結果は、分割された部分文字列（またはバイトスライス）の配列として返されます。

### `rune`とは

Go言語において、`rune`はUnicodeコードポイントを表す組み込み型です。これは`int32`のエイリアスであり、UTF-8でエンコードされた文字列内の単一の文字（正確にはコードポイント）を表現するために使用されます。Goの文字列はUTF-8バイトのシーケンスであり、`FieldsFunc`のような関数は、バイトレベルではなくUnicodeコードポイントレベルで操作を行うため、`rune`を使用します。

### ステートフルな関数とは

プログラミングにおいて、関数が「ステートフル（stateful）」であるとは、その関数の振る舞いが、過去の呼び出しや外部の状態（グローバル変数、オブジェクトのフィールドなど）に依存して変化することを指します。つまり、同じ入力引数を与えても、呼び出すたびに異なる結果を返す可能性がある関数です。

対照的に、「ステートレス（stateless）」な関数は、その振る舞いが完全にその入力引数のみに依存し、常に同じ入力に対して同じ結果を返します。ステートレスな関数は、参照透過性（referential transparency）を持つと言われ、並行処理や最適化において有利です。

`FieldsFunc`に渡される関数`f`がステートフルである場合、`FieldsFunc`が`f`を呼び出す順序や回数が不定であるため、結果が非決定論的になったり、予期せぬ副作用が発生したりする可能性があります。

## 技術的詳細

`FieldsFunc`の内部実装は、効率的な文字列分割のために、`f`関数を呼び出す順序を最適化する場合があります。例えば、並列処理を利用したり、キャッシュを利用したり、あるいは文字列の異なる部分を非連続的に処理したりすることが考えられます。このような最適化は、`f`が常に同じ入力に対して同じ結果を返す（つまりステートレスである）ことを前提としています。

もし`f`がステートフルである場合、例えば内部カウンタを持っていて呼び出されるたびにそのカウンタをインクリメントし、特定のカウンタ値で`true`を返すようなロジックが含まれているとします。この場合、`FieldsFunc`が`f`を呼び出す順序や回数が保証されないため、期待通りの分割が行われないだけでなく、`f`の内部状態が予期せぬ形で変化し、プログラムのクラッシュや無限ループ、あるいはセキュリティ上の脆弱性につながる可能性さえあります。

このコミットは、このような潜在的な問題を未然に防ぐために、`FieldsFunc`のドキュメントに以下の重要な警告を追加しました。

- `FieldsFunc makes no guarantees about the order in which it calls f(c).` (FieldsFuncはf(c)を呼び出す順序について何の保証も行いません。)
- `If f does not return consistent results for a given c, FieldsFunc may crash.` (もしfが特定のcに対して一貫した結果を返さない場合、FieldsFuncはクラッシュする可能性があります。)

これにより、開発者は`FieldsFunc`に渡す関数`f`が必ずステートレスであるように設計する必要があることを明確に理解できます。これは、Go言語の設計哲学である「明確さ」と「安全性」に合致する変更です。

## コアとなるコードの解説

変更は、`bytes.go`と`strings.go`内の`FieldsFunc`関数のドキュメントコメントに、以下の2行を追加したことです。

1.  `// FieldsFunc makes no guarantees about the order in which it calls f(c).`
    *   この行は、`FieldsFunc`が分割関数`f`を呼び出す順序について、いかなる保証も行わないことを明確に述べています。これは、内部的な最適化や並列処理の可能性を示唆しており、`f`が呼び出される順序に依存するようなロジックを持つべきではないことを開発者に警告しています。

2.  `// If f does not return consistent results for a given c, FieldsFunc may crash.`
    *   この行は、もし`f`が同じ入力`c`に対して一貫した（同じ）結果を返さない場合、`FieldsFunc`がクラッシュする可能性があるという、より直接的な警告です。これは、`f`がステートフルである場合に発生しうる問題の核心を突いています。クラッシュは、`f`の非一貫性によって`FieldsFunc`の内部状態が不正になったり、予期せぬロジックパスが実行されたりすることで引き起こされる可能性があります。

これらの追加されたドキュメントは、`FieldsFunc`の契約を明確にし、開発者がこの関数を安全かつ意図した通りに使用するための重要な情報を提供します。これにより、将来的に同様の問題が発生するのを防ぐことができます。

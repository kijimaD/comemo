## 変更の背景

Goの `testing` パッケージは、テストとベンチマークのための強力なツールを提供します。しかし、このコミット以前は、ベンチマークはフラットな構造でしか定義できませんでした。つまり、関連する複数のベンチマークをグループ化したり、共通のセットアップ/ティアダウンロジックを持つベンチマーク群を効率的に管理したりする機能がありませんでした。

このコミットの背景には、以下のような課題意識があったと考えられます。

1.  **ベンチマークの整理と構造化**: 複雑なシステムや複数のコンポーネントのパフォーマンスを測定する場合、関連するベンチマークを論理的にグループ化したいというニーズがあります。例えば、異なる入力サイズや設定で同じアルゴリズムをベンチマークする場合、それぞれを独立したベンチマーク関数として定義すると、コードが冗長になり、管理が難しくなります。サブベンチマークを導入することで、親ベンチマークの下に子ベンチマークをネストさせ、より整理された構造でベンチマークを記述できるようになります。
2.  **共通のセットアップ/ティアダウン**: 複数のベンチマークで共通の初期化処理や後処理が必要な場合、サブベンチマークを使用することで、親ベンチマークで一度だけセットアップを行い、そのコンテキストをすべての子ベンチマークで共有できます。これにより、コードの重複を避け、ベンチマークの保守性を向上させることができます。
3.  **特定のシナリオの分離**: 特定の条件下でのみ実行したいベンチマークや、特定の機能に焦点を当てたベンチマークを、他のベンチマークから分離して実行・報告したい場合があります。サブベンチマークは、このようなシナリオを明確に区別し、個別に結果を分析するのに役立ちます。
4.  **`testing.T.Run` との一貫性**: Goのテスト (`testing.T`) では既に `t.Run` を用いたサブテストの機能が提供されており、テストの構造化に大きく貢献していました。ベンチマークにおいても同様の機能を提供することで、`testing` パッケージ全体の一貫性と使いやすさが向上します。

このコミットは、これらの課題を解決し、より柔軟で強力なベンチマーク機能を提供するための第一歩として、サブベンチマークの内部的な基盤を構築しました。

## 前提知識の解説

### Go言語の `testing` パッケージ

Go言語には、標準ライブラリとして `testing` パッケージが用意されており、ユニットテストとベンチマークテストをサポートしています。

*   **`go test` コマンド**: Goのテストを実行するためのコマンドです。`go test ./...` のように実行すると、現在のモジュール内のすべてのテストを実行します。
*   **`testing.T` (テスト関数)**: `func TestXxx(t *testing.T)` というシグネチャを持つ関数で、ユニットテストを記述するために使用されます。`t.Fail()`, `t.Error()`, `t.Log()` などのメソッドを提供し、テストの失敗やログ出力を行います。`t.Run(name, func(t *testing.T))` を使用してサブテストを定義できます。
*   **`testing.B` (ベンチマーク関数)**: `func BenchmarkXxx(b *testing.B)` というシグネチャを持つ関数で、コードのパフォーマンスを測定するために使用されます。`b.N` はベンチマークを実行する回数を示し、`b.ResetTimer()`, `b.StartTimer()`, `b.StopTimer()` などのメソッドで測定範囲を制御します。`b.SetBytes(n)` で1回の操作で処理されるバイト数を設定し、`Ns/op` (操作あたりのナノ秒) と `MB/s` (秒あたりのメガバイト) の両方で結果を報告できます。

### ベンチマークの目的

ベンチマークテストの主な目的は以下の通りです。

*   **パフォーマンスの測定**: 特定のコードブロックやアルゴリズムがどれくらいの時間で実行されるか、どれくらいのメモリを消費するかを定量的に測定します。
*   **ボトルネックの特定**: パフォーマンスが低下している箇所（ボトルネック）を特定し、最適化の対象を絞り込みます。
*   **回帰の検出**: コード変更によってパフォーマンスが意図せず低下していないかを確認します。
*   **異なる実装の比較**: 複数のアルゴリズムや実装の中から、最もパフォーマンスの良いものを選択するための客観的なデータを提供します。

### サブテストの概念 (`testing.T.Run`)

Go 1.7で導入された `testing.T.Run` は、テスト関数内でさらにネストされたテスト（サブテスト）を定義する機能です。これにより、テストの構造化、共通のセットアップ/ティアダウン、特定のサブテストのみの実行などが可能になりました。

```go
func TestFoo(t *testing.T) {
    // 親テストのセットアップ
    t.Run("SubTestA", func(t *testing.T) {
        // SubTestA のテストロジック
    })
    t.Run("SubTestB", func(t *testing.T) {
        // SubTestB のテストロジック
    })
    // 親テストのティアダウン
}
```

このコミットは、ベンチマークにおいても同様の階層化機能 (`testing.B.Run`) を導入するための基盤を構築しています。

### `GOMAXPROCS`

`GOMAXPROCS` は、Goランタイムが同時に実行できるOSスレッドの最大数を制御する環境変数または関数 (`runtime.GOMAXPROCS`) です。ベンチマークの実行において、`GOMAXPROCS` の値は並行処理のパフォーマンスに大きな影響を与えるため、異なる `GOMAXPROCS` 設定でのベンチマーク結果を比較することは一般的です。このコミットの変更箇所でも、`GOMAXPROCS` を変更しながらベンチマークを実行するロジックが関連しています。

## 技術的詳細

このコミットの主要な変更は、`src/testing/benchmark.go` と `src/testing/sub_test.go` に集中しており、`testing.B` 型の拡張と、サブベンチマークの実行ロジックの導入が含まれます。

### `testing.B` 構造体への変更

`testing.B` 構造体に以下のフィールドが追加されました。

*   `benchTime time.Duration`: ベンチマークを実行する目標時間。以前はグローバル変数 `*benchTime` を直接参照していましたが、`B` 構造体内に持つことで、サブベンチマークごとに異なる目標時間を設定する柔軟性が生まれます。
*   `missingBytes bool`: サブベンチマークのいずれかが `b.SetBytes()` を呼び出さなかった場合に `true` に設定されます。これにより、集計された `Bytes` の結果が意味をなさない場合に `0` を報告するロジックが導入されます。
*   `hasSub bool`: このベンチマークがサブベンチマークを持っているかどうかを示すフラグ。`b.Run()` が呼び出された場合に `true` に設定され、親ベンチマーク自体は測定されなくなります。

### `run` メソッドの変更と `probe()`, `doBench()` の導入

以前は `B.run()` がベンチマークの実行と結果の返却を直接行っていましたが、このコミットで役割が分割されました。

*   `B.probe()`: 新たに導入されたメソッドで、ベンチマーク関数がサブベンチマークを持っているかどうかを事前に「プローブ」（調査）するために使用されます。`b.benchFunc(b)` を `N=0` で一度実行し、その中で `b.Run()` が呼び出されるかどうかを確認します。これにより、サブベンチマークを持つ親ベンチマークはそれ自体が測定対象から外れるようになります。
*   `B.run()`: `B.context` の有無に応じて、`B.context.processBench(b)` または `B.doBench()` を呼び出すようになりました。
*   `B.doBench()`: 実際のベンチマーク実行ロジック（`launch()` を呼び出す部分）が `doBench()` に移動しました。これにより、`run()` がサブベンチマークの有無に応じたディスパッチの役割を担い、`doBench()` が単一ベンチマークの実行に専念する形になります。

### `runBench()` メソッドの変更とサブベンチマークの実行

`B.runBench(name string, f func(b *B)) *B` は、サブベンチマークを実行するための内部メソッドです。このコミットで、その動作が大幅に変更されました。

*   **`b.hasSub = true`**: `runBench` が呼び出されると、親ベンチマークの `hasSub` フラグが `true` に設定されます。これは、親ベンチマーク自体は測定されず、その子ベンチマークの結果が集計されることを意味します。
*   **ロックの管理**: `benchmarkLock.Unlock()` と `defer benchmarkLock.Lock()` が追加されました。これは、ベンチマーク実行中にグローバルな `benchmarkLock` を一時的に解放し、サブベンチマークが独立して実行されることを可能にするための重要な変更です。これにより、複数のベンチマークが並行して実行される際の競合状態を防ぎます。
*   **サブベンチマークの生成**: 新しい `testing.B` インスタンス `sub` が作成され、親ベンチマークのコンテキスト (`b.context`) や目標時間 (`b.benchTime`) を継承します。
*   **プローブと実行**: `sub.probe()` を呼び出して、子ベンチマークがさらにサブベンチマークを持つかどうかを確認します。もし子ベンチマークがサブベンチマークを持たない場合 (`!sub.hasSub`)、`sub.run()` を呼び出して実際にベンチマークを実行し、その結果を親ベンチマークの `add()` メソッドで集計します。

### `add()` メソッド

`B.add(other BenchmarkResult)` は、サブベンチマークの結果を親ベンチマークの結果に集計するための新しいメソッドです。

*   **`r.N = 1`**: 集計された `BenchmarkResult` の `N` は常に `1` に設定されます。これは、サブベンチマークが「単一のベンチマーク実行」として扱われるためです。
*   **`r.T += time.Duration(other.NsPerOp())`**: 各サブベンチマークの `NsPerOp` (操作あたりのナノ秒) を合計し、親ベンチマークの合計実行時間 `T` に加算します。
*   **`Bytes` の集計ロジック**: `missingBytes` フラグが導入されたことで、すべてのサブベンチマークが `b.SetBytes()` を呼び出している場合にのみ `Bytes` を合計します。一つでも呼び出していないサブベンチマークがある場合、集計された `Bytes` は `0` に設定され、結果の誤解釈を防ぎます。
*   **メモリ統計の集計**: `MemAllocs` (割り当て回数) と `MemBytes` (割り当てバイト数) も同様に集計されます。

### `benchContext` 構造体への変更

`benchContext` 構造体に `extLen int` フィールドが追加されました。これは、ベンチマーク名の最大長を計算する際に、`GOMAXPROCS` の情報など、ベンチマーク名に追加される可能性のある拡張部分の長さを考慮するためのものです。

### `runBenchmarksInternal` 関数の変更

`runBenchmarksInternal` 関数は、ベンチマークの実行をオーケストレーションする役割を担います。このコミットでは、`benchContext` の初期化方法が変更され、`expandCPU` 関数が削除され、代わりに `main.runN(1)` を呼び出すことで、`main` ベンチマークがサブベンチマークとして登録された実際のベンチマークを実行するようになりました。

### `expandCPU` 関数の削除と `processBench` メソッドの導入

以前は `expandCPU` 関数が `GOMAXPROCS` の異なる設定でベンチマークを実行していましたが、このロジックは `benchContext.processBench(b *B)` メソッドに移動しました。これにより、`benchContext` がベンチマークの実行コンテキストをより密接に管理できるようになり、コードの凝集度が高まりました。

### `src/testing/sub_test.go` での `b.Run` のスタブ実装とテストケース

`src/testing/sub_test.go` には、`b.Run` メソッドのスタブ実装 (`func (b *B) Run(name string, f func(b *B)) bool { return b.runBench(name, f) }`) と、サブベンチマークの動作を検証するための `TestBRun` テスト関数が追加されました。このテスト関数は、サブベンチマークのシーケンシャルな実行、`Bytes` の集計、メモリ割り当ての集計、および失敗の伝播といった、サブベンチマークの主要な機能が正しく動作することを確認します。特に、`Bytes` の集計ロジック (`missingBytes` の挙動) や、親ベンチマークの `N` が `1` になることなどが検証されています。

## コアとなるコードの解説

### `B` 構造体へのフィールド追加

*   `benchTime`, `missingBytes`, `hasSub` の追加は、サブベンチマークの動作を制御し、その結果を正確に集計するために不可欠です。
    *   `benchTime` を `B` 構造体内に持つことで、各ベンチマーク（親または子）が自身の目標実行時間を持つことができ、より柔軟なベンチマーク設定が可能になります。
    *   `missingBytes` は、`b.SetBytes()` が呼び出されなかった場合に、集計結果の `Bytes` を `0` にすることで、誤解を招くような不正確なデータが表示されるのを防ぎます。
    *   `hasSub` は、ベンチマークがサブベンチマークを持つかどうかを追跡し、親ベンチマーク自体が測定対象から外れるべきかどうかを判断するために使用されます。

### `probe()` メソッド

`probe()` メソッドは、ベンチマーク関数がサブベンチマークを定義しているかどうかを事前に検出する「偵察」の役割を果たします。`b.N = 0` で `b.benchFunc(b)` を実行することで、実際のベンチマークループは実行せずに、`b.Run()` の呼び出しだけをトリガーします。これにより、親ベンチマークがサブベンチマークを持つことが判明した場合、親ベンチマーク自体は測定されず、その子ベンチマークの結果が集計されるという動作を実現します。これは、`testing.T.Run` と同様に、親テストが子テストのコンテナとして機能し、それ自体はテストロジックを実行しないというパターンをベンチマークにも適用するものです。

### `run()` と `doBench()` の役割分担

`run()` メソッドが `B.context` の有無に応じて `processBench` または `doBench` を呼び出すように変更されたことで、ベンチマークの実行フローがより明確に分離されました。
*   `processBench` は、`go test --test.bench` コマンドで実行されるベンチマーク（通常はトップレベルのベンチマーク）の処理を担当し、`GOMAXPROCS` の異なる設定での実行を管理します。
*   `doBench` は、単一のベンチマーク（サブベンチマークを含む）の実際の実行ロジックをカプセル化します。この分離により、コードのモジュール性が向上し、サブベンチマークの導入が容易になりました。

### `runBench()` メソッドの変更

`runBench()` はサブベンチマークの核心部分です。
*   `b.hasSub = true` の設定は、親ベンチマークがサブベンチマークのコンテナであることを明確にし、親ベンチマーク自体の測定を抑制します。
*   `benchmarkLock.Unlock()` と `defer benchmarkLock.Lock()` は、複数のベンチマークが並行して実行される可能性のある環境で、グローバルなロックを適切に管理するために重要です。これにより、サブベンチマークが独立して実行され、親ベンチマークのロックが不必要に保持されることを防ぎます。
*   `sub.probe()` の呼び出しは、ネストされたサブベンチマークの可能性を考慮した再帰的なプローブメカニズムを導入しています。
*   `sub.run()` の結果を `b.add()` で集計するロジックは、複数のサブベンチマークの結果を親ベンチマークの単一の結果に統合するためのものです。これにより、ユーザーは親ベンチマークの結果を見るだけで、その下のすべてのサブベンチマークの集計されたパフォーマンスを把握できます。

### `add()` メソッド

`add()` メソッドは、複数のサブベンチマークの結果を論理的に結合し、親ベンチマークの `BenchmarkResult` に反映させる役割を担います。
*   `r.N = 1` は、集計された結果が単一の「論理的な」ベンチマーク実行を表すことを示します。
*   `NsPerOp`、`MemAllocs`、`MemBytes` の合計は、サブベンチマーク全体のパフォーマンス特性を包括的に把握するために重要です。
*   `missingBytes` フラグによる `Bytes` の条件付き集計は、データの一貫性と正確性を保つための賢明な設計です。一部のサブベンチマークが `SetBytes` を呼び出さない場合、合計バイト数は意味をなさないため、`0` に設定することで誤解釈を防ぎます。

### `src/testing/sub_test.go` の `B.Run` スタブと `TestBRun`

`B.Run` のスタブ実装は、このコミットが内部的な実装段階であり、まだ正式なAPIとして公開されていないことを示しています。しかし、このスタブと `TestBRun` テスト関数は、サブベンチマークの機能が意図通りに動作するかを検証するための重要な役割を果たします。`TestBRun` のテストケースは、サブベンチマークの基本的な動作、`Bytes` の集計ルール、メモリ統計の集計、および失敗の伝播といった、この新機能の主要な側面を網羅的にカバーしており、実装の堅牢性を保証しています。

これらの変更全体として、Goのベンチマーク機能は、より複雑なパフォーマンス測定シナリオに対応できるようになり、開発者がより整理された、保守しやすいベンチマークコードを記述するための強力な基盤が提供されました。

## 変更の背景

Goの `testing` パッケージは、テストとベンチマークのための強力なツールを提供します。しかし、このコミット以前は、ベンチマークはフラットな構造でしか定義できませんでした。つまり、関連する複数のベンチマークをグループ化したり、共通のセットアップ/ティアダウンロジックを持つベンチマーク群を効率的に管理したりする機能がありませんでした。

このコミットの背景には、以下のような課題意識があったと考えられます。

1.  **ベンチマークの整理と構造化**: 複雑なシステムや複数のコンポーネントのパフォーマンスを測定する場合、関連するベンチマークを論理的にグループ化したいというニーズがあります。例えば、異なる入力サイズや設定で同じアルゴリズムをベンチマークする場合、それぞれを独立したベンチマーク関数として定義すると、コードが冗長になり、管理が難しくなります。サブベンチマークを導入することで、親ベンチマークの下に子ベンチマークをネストさせ、より整理された構造でベンチマークを記述できるようになります。
2.  **共通のセットアップ/ティアダウン**: 複数のベンチマークで共通の初期化処理や後処理が必要な場合、サブベンチマークを使用することで、親ベンチマークで一度だけセットアップを行い、そのコンテキストをすべての子ベンチマークで共有できます。これにより、コードの重複を避け、ベンチマークの保守性を向上させることができます。
3.  **特定のシナリオの分離**: 特定の条件下でのみ実行したいベンチマークや、特定の機能に焦点を当てたベンチマークを、他のベンチマークから分離して実行・報告したい場合があります。サブベンチマークは、このようなシナリオを明確に区別し、個別に結果を分析するのに役立ちます。
4.  **`testing.T.Run` との一貫性**: Goのテスト (`testing.T`) では既に `t.Run` を用いたサブテストの機能が提供されており、テストの構造化に大きく貢献していました。ベンチマークにおいても同様の機能を提供することで、`testing` パッケージ全体の一貫性と使いやすさが向上します。

このコミットは、これらの課題を解決し、より柔軟で強力なベンチマーク機能を提供するための第一歩として、サブベンチマークの内部的な基盤を構築しました。

## 前提知識の解説

### Go言語の `testing` パッケージ

Go言語には、標準ライブラリとして `testing` パッケージが用意されており、ユニットテストとベンチマークテストをサポートしています。

*   **`go test` コマンド**: Goのテストを実行するためのコマンドです。`go test ./...` のように実行すると、現在のモジュール内のすべてのテストを実行します。
*   **`testing.T` (テスト関数)**: `func TestXxx(t *testing.T)` というシグネチャを持つ関数で、ユニットテストを記述するために使用されます。`t.Fail()`, `t.Error()`, `t.Log()` などのメソッドを提供し、テストの失敗やログ出力を行います。`t.Run(name, func(t *testing.T))` を使用してサブテストを定義できます。
*   **`testing.B` (ベンチマーク関数)**: `func BenchmarkXxx(b *testing.B)` というシグネチャを持つ関数で、コードのパフォーマンスを測定するために使用されます。`b.N` はベンチマークを実行する回数を示し、`b.ResetTimer()`, `b.StartTimer()`, `b.StopTimer()` などのメソッドで測定範囲を制御します。`b.SetBytes(n)` で1回の操作で処理されるバイト数を設定し、`Ns/op` (操作あたりのナノ秒) と `MB/s` (秒あたりのメガバイト) の両方で結果を報告できます。

### ベンチマークの目的

ベンチマークテストの主な目的は以下の通りです。

*   **パフォーマンスの測定**: 特定のコードブロックやアルゴリズムがどれくらいの時間で実行されるか、どれくらいのメモリを消費するかを定量的に測定します。
*   **ボトルネックの特定**: パフォーマンスが低下している箇所（ボトルネック）を特定し、最適化の対象を絞り込みます。
*   **回帰の検出**: コード変更によってパフォーマンスが意図せず低下していないかを確認します。
*   **異なる実装の比較**: 複数のアルゴリズムや実装の中から、最もパフォーマンスの良いものを選択するための客観的なデータを提供します。

### サブテストの概念 (`testing.T.Run`)

Go 1.7で導入された `testing.T.Run` は、テスト関数内でさらにネストされたテスト（サブテスト）を定義する機能です。これにより、テストの構造化、共通のセットアップ/ティアダウン、特定のサブテストのみの実行などが可能になりました。

```go
func TestFoo(t *testing.T) {
    // 親テストのセットアップ
    t.Run("SubTestA", func(t *testing.T) {
        // SubTestA のテストロジック
    })
    t.Run("SubTestB", func(t *testing.T) {
        // SubTestB のテストロジック
    })
    // 親テストのティアダウン
}
```

このコミットは、ベンチマークにおいても同様の階層化機能 (`testing.B.Run`) を導入するための基盤を構築しています。

### `GOMAXPROCS`

`GOMAXPROCS` は、Goランタイムが同時に実行できるOSスレッドの最大数を制御する環境変数または関数 (`runtime.GOMAXPROCS`) です。ベンチマークの実行において、`GOMAXPROCS` の値は並行処理のパフォーマンスに大きな影響を与えるため、異なる `GOMAXPROCS` 設定でのベンチマーク結果を比較することは一般的です。このコミットの変更箇所でも、`GOMAXPROCS` を変更しながらベンチマークを実行するロジックが関連しています。

## 技術的詳細

このコミットの主要な変更は、`src/testing/benchmark.go` と `src/testing/sub_test.go` に集中しており、`testing.B` 型の拡張と、サブベンチマークの実行ロジックの導入が含まれます。

### `testing.B` 構造体への変更

`testing.B` 構造体に以下のフィールドが追加されました。

*   `benchTime time.Duration`: ベンチマークを実行する目標時間。以前はグローバル変数 `*benchTime` を直接参照していましたが、`B` 構造体内に持つことで、サブベンチマークごとに異なる目標時間を設定する柔軟性が生まれます。
*   `missingBytes bool`: サブベンチマークのいずれかが `b.SetBytes()` を呼び出さなかった場合に `true` に設定されます。これにより、集計された `Bytes` の結果が意味をなさない場合に `0` を報告するロジックが導入されます。
*   `hasSub bool`: このベンチマークがサブベンチマークを持っているかどうかを示すフラグ。`b.Run()` が呼び出された場合に `true` に設定され、親ベンチマーク自体は測定されなくなります。

### `run` メソッドの変更と `probe()`, `doBench()` の導入

以前は `B.run()` がベンチマークの実行と結果の返却を直接行っていましたが、このコミットで役割が分割されました。

*   `B.probe()`: 新たに導入されたメソッドで、ベンチマーク関数がサブベンチマークを持っているかどうかを事前に「プローブ」（調査）するために使用されます。`b.benchFunc(b)` を `N=0` で一度実行し、その中で `b.Run()` が呼び出されるかどうかを確認します。これにより、サブベンチマークを持つ親ベンチマークはそれ自体が測定対象から外れるようになります。
*   `B.run()`: `B.context` の有無に応じて、`B.context.processBench(b)` または `B.doBench()` を呼び出すようになりました。
*   `B.doBench()`: 実際のベンチマーク実行ロジック（`launch()` を呼び出す部分）が `doBench()` に移動しました。これにより、`run()` がサブベンチマークの有無に応じたディスパッチの役割を担い、`doBench()` が単一ベンチマークの実行に専念する形になります。

### `runBench()` メソッドの変更とサブベンチマークの実行

`B.runBench(name string, f func(b *B)) *B` は、サブベンチマークを実行するための内部メソッドです。このコミットで、その動作が大幅に変更されました。

*   **`b.hasSub = true`**: `runBench` が呼び出されると、親ベンチマークの `hasSub` フラグが `true` に設定されます。これは、親ベンチマーク自体は測定されず、その子ベンチマークの結果が集計されることを意味します。
*   **ロックの管理**: `benchmarkLock.Unlock()` と `defer benchmarkLock.Lock()` が追加されました。これは、ベンチマーク実行中にグローバルな `benchmarkLock` を一時的に解放し、サブベンチマークが独立して実行されることを可能にするための重要な変更です。これにより、複数のベンチマークが並行して実行される際の競合状態を防ぎます。
*   **サブベンチマークの生成**: 新しい `testing.B` インスタンス `sub` が作成され、親ベンチマークのコンテキスト (`b.context`) や目標時間 (`b.benchTime`) を継承します。
*   **プローブと実行**: `sub.probe()` を呼び出して、子ベンチマークがさらにサブベンチマークを持つかどうかを確認します。もし子ベンチマークがサブベンチマークを持たない場合 (`!sub.hasSub`)、`sub.run()` を呼び出して実際にベンチマークを実行し、その結果を親ベンチマークの `add()` メソッドで集計します。

### `add()` メソッド

`B.add(other BenchmarkResult)` は、サブベンチマークの結果を親ベンチマークの結果に集計するための新しいメソッドです。

*   **`r.N = 1`**: 集計された `BenchmarkResult` の `N` は常に `1` に設定されます。これは、サブベンチマークが「単一のベンチマーク実行」として扱われるためです。
*   **`r.T += time.Duration(other.NsPerOp())`**: 各サブベンチマークの `NsPerOp` (操作あたりのナノ秒) を合計し、親ベンチマークの合計実行時間 `T` に加算します。
*   **`Bytes` の集計ロジック**: `missingBytes` フラグが導入されたことで、すべてのサブベンチマークが `b.SetBytes()` を呼び出している場合にのみ `Bytes` を合計します。一つでも呼び出していないサブベンチマークがある場合、集計された `Bytes` は `0` に設定され、結果の誤解釈を防ぎます。
*   **メモリ統計の集計**: `MemAllocs` (割り当て回数) と `MemBytes` (割り当てバイト数) も同様に集計されます。

### `benchContext` 構造体への変更

`benchContext` 構造体に `extLen int` フィールドが追加されました。これは、ベンチマーク名の最大長を計算する際に、`GOMAXPROCS` の情報など、ベンチマーク名に追加される可能性のある拡張部分の長さを考慮するためのものです。

### `runBenchmarksInternal` 関数の変更

`runBenchmarksInternal` 関数は、ベンチマークの実行をオーケストレーションする役割を担います。このコミットでは、`benchContext` の初期化方法が変更され、`expandCPU` 関数が削除され、代わりに `main.runN(1)` を呼び出すことで、`main` ベンチマークがサブベンチマークとして登録された実際のベンチマークを実行するようになりました。

### `expandCPU` 関数の削除と `processBench` メソッドの導入

以前は `expandCPU` 関数が `GOMAXPROCS` の異なる設定でベンチマークを実行していましたが、このロジックは `benchContext.processBench(b *B)` メソッドに移動しました。これにより、`benchContext` がベンチマークの実行コンテキストをより密接に管理できるようになり、コードの凝集度が高まりました。

### `src/testing/sub_test.go` での `b.Run` のスタブ実装とテストケース

`src/testing/sub_test.go` には、`b.Run` メソッドのスタブ実装 (`func (b *B) Run(name string, f func(b *B)) bool { return b.runBench(name, f) }`) と、サブベンチマークの動作を検証するための `TestBRun` テスト関数が追加されました。このテスト関数は、サブベンチマークのシーケンシャルな実行、`Bytes` の集計、メモリ割り当ての集計、および失敗の伝播といった、サブベンチマークの主要な機能が正しく動作することを確認します。特に、`Bytes` の集計ロジック (`missingBytes` の挙動) や、親ベンチマークの `N` が `1` になることなどが検証されています。

これらの変更全体として、Goのベンチマーク機能は、より複雑なパフォーマンス測定シナリオに対応できるようになり、開発者がより整理された、保守しやすいベンチマークコードを記述するための強力な基盤が提供されました。

## コアとなるコードの解説

### `B` 構造体へのフィールド追加

*   `benchTime`, `missingBytes`, `hasSub` の追加は、サブベンチマークの動作を制御し、その結果を正確に集計するために不可欠です。
    *   `benchTime` を `B` 構造体内に持つことで、各ベンチマーク（親または子）が自身の目標実行時間を持つことができ、より柔軟なベンチマーク設定が可能になります。
    *   `missingBytes` は、`b.SetBytes()` が呼び出されなかった場合に、集計結果の `Bytes` を `0` にすることで、誤解を招くような不正確なデータが表示されるのを防ぎます。
    *   `hasSub` は、ベンチマークがサブベンチマークを持つかどうかを追跡し、親ベンチマーク自体が測定対象から外れるべきかどうかを判断するために使用されます。

### `probe()` メソッド

`probe()` メソッドは、ベンチマーク関数がサブベンチマークを定義しているかどうかを事前に検出する「偵察」の役割を果たします。`b.N = 0` で `b.benchFunc(b)` を実行することで、実際のベンチマークループは実行せずに、`b.Run()` の呼び出しだけをトリガーします。これにより、親ベンチマークがサブベンチマークを持つことが判明した場合、親ベンチマーク自体は測定されず、その子ベンチマークの結果が集計されるという動作を実現します。これは、`testing.T.Run` と同様に、親テストが子テストのコンテナとして機能し、それ自体はテストロジックを実行しないというパターンをベンチマークにも適用するものです。

### `run()` と `doBench()` の役割分担

`run()` メソッドが `B.context` の有無に応じて `processBench` または `doBench` を呼び出すように変更されたことで、ベンチマークの実行フローがより明確に分離されました。
*   `processBench` は、`go test --test.bench` コマンドで実行されるベンチマーク（通常はトップレベルのベンチマーク）の処理を担当し、`GOMAXPROCS` の異なる設定での実行を管理します。
*   `doBench` は、単一のベンチマーク（サブベンチマークを含む）の実際の実行ロジックをカプセル化します。この分離により、コードのモジュール性が向上し、サブベンチマークの導入が容易になりました。

### `runBench()` メソッドの変更

`runBench()` はサブベンチマークの核心部分です。
*   `b.hasSub = true` の設定は、親ベンチマークがサブベンチマークのコンテナであることを明確にし、親ベンチマーク自体の測定を抑制します。
*   `benchmarkLock.Unlock()` と `defer benchmarkLock.Lock()` は、複数のベンチマークが並行して実行される可能性のある環境で、グローバルなロックを適切に管理するために重要です。これにより、サブベンチマークが独立して実行され、親ベンチマークのロックが不必要に保持されることを防ぎます。
*   `sub.probe()` の呼び出しは、ネストされたサブベンチマークの可能性を考慮した再帰的なプローブメカニズムを導入しています。
*   `sub.run()` の結果を `b.add()` で集計するロジックは、複数のサブベンチマークの結果を親ベンチマークの単一の結果に統合するためのものです。これにより、ユーザーは親ベンチマークの結果を見るだけで、その下のすべてのサブベンチマークの集計されたパフォーマンスを把握できます。

### `add()` メソッド

`add()` メソッドは、複数のサブベンチマークの結果を論理的に結合し、親ベンチマークの `BenchmarkResult` に反映させる役割を担います。
*   `r.N = 1` は、集計された結果が単一の「論理的な」ベンチマーク実行を表すことを示します。
*   `NsPerOp`、`MemAllocs`、`MemBytes` の合計は、サブベンチマーク全体のパフォーマンス特性を包括的に把握するために重要です。
*   `missingBytes` フラグによる `Bytes` の条件付き集計は、データの一貫性と正確性を保つための賢明な設計です。一部のサブベンチマークが `SetBytes` を呼び出さない場合、合計バイト数は意味をなさないため、`0` に設定することで誤解釈を防ぎます。

### `src/testing/sub_test.go` の `B.Run` スタブと `TestBRun`

`B.Run` のスタブ実装は、このコミットが内部的な実装段階であり、まだ正式なAPIとして公開されていないことを示しています。しかし、このスタブと `TestBRun` テスト関数は、サブベンチマークの機能が意図通りに動作するかを検証するための重要な役割を果たします。`TestBRun` のテストケースは、サブベンチマークの基本的な動作、`Bytes` の集計ルール、メモリ統計の集計、および失敗の伝播といった、この新機能の主要な側面を網羅的にカバーしており、実装の堅牢性を保証しています。

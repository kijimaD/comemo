# [インデックス 20411] ファイルの概要

このコミットは、Goランタイムにおけるパニックとリカバリーのメカニズム、特に`reflect.call`のようなラッパー関数が関与する場合のスタックポインタの調整に関する重要なバグ修正と改善を目的としています。以前の`gp->panicwrap`という調整方法が根本的に欠陥を抱えていたため、`Panic.argp`フィールドを使用する新しいアプローチに移行することで、パニック時のスタックアンワインド処理を簡素化し、堅牢性を向上させています。

## 変更の背景

このコミットの主な背景は、Goランタイムにおけるパニックとリカバリーの処理、特に`reflect.call`のような「ラッパー関数」が関与する場合のスタックポインタの調整メカニズムに存在していた根本的な欠陥を修正することです。

以前のGoランタイムでは、`g`（ゴルーチン）構造体内の`panicwrap`フィールド（`gp->panicwrap`）を使用して、ラッパー関数がスタックフレームを調整する際に、パニック時のスタックアンワインド処理を正しく行うためのオフセットを管理していました。しかし、このアプローチは「致命的な欠陥（fatally flawed）」を抱えていました。具体的には、`panicwrap`の調整がラッパー関数のエントリ時とエグジット時の両方で行われる必要があったため、複雑性が増していました。

問題は、関数が通常の戻りではなくパニックによって終了する場合に顕著になります。パニックが発生すると、通常の関数のエグジットパスは実行されず、`panicwrap`の「元に戻す」調整が行われない可能性がありました。これにより、パニック時のスタックアンワインドが不正確になり、`recover`が期待通りに機能しない、あるいは誤ったスタックフレームを指すといった問題を引き起こす可能性がありました。コミットメッセージにある「broken test I never checked in」という記述は、この問題が開発中に認識されていたことを示唆しています。

この欠陥を解決するため、コミットは`Panic`構造体（Goランタイムのパニック情報を保持する内部構造体）に`argp`フィールドを導入し、このフィールドをパニック時のスタックポインタの基準として使用する新しい戦略を採用しました。これにより、ラッパー関数はエントリ時に一度だけ`Panic.argp`を更新すればよくなり、パニック時のアンワインド処理が大幅に簡素化され、堅牢性が向上しました。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGoランタイムの概念とメカニズムに関する知識が必要です。

### Goのパニックとリカバリー (Panic and Recover)

*   **パニック (Panic)**: Goにおけるパニックは、プログラムの通常の実行フローを中断する予期せぬエラーや例外的な状況を示すメカニズムです。これは、`panic()`組み込み関数の明示的な呼び出し、またはゼロ除算、nilポインタのデリファレンス、配列の範囲外アクセスなどのランタイムエラーによって引き起こされます。パニックが発生すると、現在のゴルーチンの実行は停止し、スタックアンワインドが開始されます。
*   **リカバリー (Recover)**: `recover()`は、パニック状態のゴルーチンの制御を取り戻すために使用される組み込み関数です。`recover()`は、`defer`された関数内でのみ有効です。`defer`された関数内で`recover()`が呼び出されると、パニックの値が捕捉され、スタックアンワインドが停止し、プログラムは`recover()`が呼び出された地点から実行を再開します。これにより、プログラムのクラッシュを防ぎ、エラーを適切に処理することができます。

### Goランタイムのスタック管理とスタックアンワインド (Stack Management and Unwinding)

Goのゴルーチンは、動的にサイズが変更されるスタックを使用します。スタックは必要に応じて拡張（スタックコピー）されます。
*   **スタックアンワインド**: パニックが発生すると、Goランタイムはコールスタックを逆順に辿り（アンワインド）、各スタックフレームに関連付けられた`defer`関数を実行します。このプロセス中に`recover()`が呼び出されない場合、プログラムは終了し、スタックトレースが出力されます。

### `reflect.call`の役割

`reflect.call`（または`reflect.Value.Call`）は、Goの`reflect`パッケージが提供する機能で、実行時に動的に関数やメソッドを呼び出すことを可能にします。これは、関数の引数や戻り値の型がコンパイル時には不明な場合や、汎用的なディスパッチャを実装する場合などに使用されます。`reflect.call`は、内部的にGoランタイムの低レベルなアセンブリコードを呼び出して、引数の準備、関数の呼び出し、戻り値の処理を行います。この動的な性質のため、通常の関数呼び出しよりもオーバーヘッドが大きくなります。

### `g` (goroutine) 構造体と `_panic` 構造体

*   **`g` (goroutine) 構造体**: Goランタイムは、各ゴルーチンを`g`構造体で表現します。この構造体には、スタック情報、スケジューリング情報、パニック情報（`_panic`へのポインタなど）など、ゴルーチンの状態に関する様々なフィールドが含まれています。
*   **`_panic` 構造体**: パニックが発生すると、Goランタイムは`_panic`構造体のインスタンスを作成し、現在のパニックに関する情報を格納します。これには、パニックの値、以前のパニックへのリンク、そしてこのコミットで追加された`argp`フィールドなどが含まれます。

### `WRAPPER` 関数とは何か

Goランタイムの文脈における「ラッパー関数（`WRAPPER`）」は、特定の目的のために生成される特殊な関数を指します。これらは通常、Goのソースコードから直接書かれるのではなく、コンパイラやリンカによって生成されます。`reflect.call`によって呼び出される関数や、CGOコールバックなどがラッパー関数として扱われることがあります。これらのラッパー関数は、通常のGo関数とは異なるプロローグ/エピローグ（関数の開始と終了時に実行されるアセンブリコード）を持つことがあり、スタックの調整やレジスタの保存/復元といった特殊な処理を行うことがあります。

## 技術的詳細

このコミットの技術的な核心は、パニック時のスタックポインタの調整方法を`gp->panicwrap`から`Panic.argp`へと変更した点にあります。

**旧アプローチ (`gp->panicwrap`) の問題点:**
以前は、`g`構造体（`gp`）の`panicwrap`フィールドが、ラッパー関数がスタックフレームを調整する際に、パニック時の`recover`が正しいスタック位置を特定できるようにするためのオフセットとして使用されていました。
*   ラッパー関数のプロローグ（関数開始時）で`gp->panicwrap`にスタックサイズのオフセットが加算されます。
*   ラッパー関数のエピローグ（関数終了時）で`gp->panicwrap`から同じオフセットが減算され、元に戻されます。

この「加算と減算」のペアリングが問題でした。もしラッパー関数内でパニックが発生し、通常の関数のエピローグが実行されない場合、`gp->panicwrap`は正しく元に戻されず、その後の`recover`処理が誤ったスタックポインタを基準にしてしまう可能性がありました。コミットメッセージが「fatally flawed」と表現しているのはこのためです。

**新アプローチ (`Panic.argp`) の解決策:**
新しいアプローチでは、`_panic`構造体に`argp`（argument pointer）フィールドが追加されました。この`argp`は、パニック時に`defer`された関数が実行される際の引数ポインタを保持します。
*   **エントリ時のみの更新**: ラッパー関数は、そのプロローグで`Panic.argp`を一度だけ更新します。この更新は、現在のスタックフレームの底（bottom-of-frame）を指すように行われます。
*   **アンワインドの簡素化**: パニックが発生し、スタックがアンワインドされる際、`recover`は`Panic.argp`を参照して、`defer`された関数の引数ポインタがどこにあるべきかを正確に判断できます。エグジット時の調整が不要になったため、パニックによって通常の実行フローが中断されても、`Panic.argp`は常に正しい状態を保ちます。

この変更により、ラッパー関数のプロローグには数命令が追加されますが、システム全体のパニック/リカバリー処理は大幅に簡素化され、堅牢性が向上します。特に、`reflect.call`のような動的な関数呼び出しのコンテキストで、`recover`がより信頼性高く機能するようになります。

`gorecover`関数も`gp->panicwrap`の調整を考慮する必要がなくなり、単に`argp == p.argp`というシンプルな比較でリカバリーの条件を判断できるようになりました。

## コアとなるコードの変更箇所

このコミットは、Goランタイムの複数のコンポーネントにわたる広範な変更を含んでいます。

1.  **`src/liblink/obj*.c` (リンカのアセンブリコード生成)**:
    *   `obj5.c` (ARM), `obj6.c` (AMD64), `obj8.c` (386) の各ファイルで、`addstacksplit`関数内の`WRAPPER`関数に対するスタック調整ロジックが変更されています。
    *   以前の`g->panicwrap += autosize;`および`g->panicwrap -= autosize;`といった`panicwrap`の加算/減算ロジックが削除され、代わりに`Panic.argp`を更新する新しいアセンブリ命令が挿入されています。
    *   新しいアセンブリコードは、`g->panic`がnilでないこと、および`g->panic->argp`が現在のフレームポインタ（FP）と一致する場合にのみ`g->panic->argp`を更新する条件付きロジックを含んでいます。これは、パニックが実際に進行中であり、かつ現在のラッパー関数がパニックの起点である場合にのみ`argp`を調整するためです。

2.  **`src/pkg/reflect/value.go`**:
    *   `call`関数のシグネチャから、最後の引数`panicpos unsafe.Pointer`が削除されています。これは、`Panic.argp`が`_panic`構造体の一部として直接管理されるようになったため、外部から渡す必要がなくなったことを示しています。
    *   `Value.call`および`callMethod`内の`call`関数の呼び出し箇所も、引数の変更に合わせて修正されています。

3.  **`src/pkg/runtime/asm_*.s` (ランタイムアセンブリ)**:
    *   `asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `asm_arm.s`の各ファイルで、`reflect·call`関数の定義と、`CALLFN`マクロ内のラッパー関数のプロローグ/エピローグが変更されています。
    *   特に`CALLFN`マクロ内で、以前の`panic argp`の初期化とクリアに関するアセンブリコード（`MOVL panic+16(FP), CX; CMPL CX, $0; JEQ ...; LEAL ...; MOVL BX, panic_argp(CX);`など）が完全に削除されています。これは、`Panic.argp`の管理がリンカによって生成されるコード（`obj*.c`）に移動したためです。
    *   `reflect·call`のスタックフレームサイズも、引数の変更に合わせて調整されています（例: `$-20`から`$-16`へ）。

4.  **`src/pkg/runtime/panic1.go`**:
    *   `gopanic`関数内で、`gp.ispanic`および`gp.panicwrap`に関する古いロジックが削除されています。
    *   `reflectcall`の呼び出しから`_panic`ポインタの引数が削除されています。
    *   `p.argp = getargp(0)`という行が追加され、パニック時に`_panic`構造体の`argp`フィールドが初期化されるようになりました。
    *   `gorecover`関数内のリカバリー条件が簡素化され、`argp == p.argp-uintptr(gp.panicwrap)`から`argp == p.argp`に変更されています。これは、`panicwrap`による調整が不要になったためです。
    *   `getargp`という新しい`go:nosplit`関数が追加されています。この関数は、呼び出し元の引数ポインタ（スタックフレームの底）を返す役割を担います。

5.  **`src/pkg/runtime/runtime.h`**:
    *   `G`構造体から`panicwrap`フィールドと`ispanic`フィールドが削除されています。
    *   `G`構造体に`Panic* panic;`フィールドが追加されています（以前は`Defer* defer;`の後にあったものが移動）。
    *   `Stktop`構造体から`panicwrap`フィールドが削除されています。
    *   `Panic`構造体内で、`argp`フィールドの定義が移動し、`outerwrap`フィールドが削除されています。`argp`は`// cannot move - known to liblink`というコメントが付けられています。

6.  **`src/pkg/runtime/proc.c`, `src/pkg/runtime/stack.c`, `src/pkg/runtime/stubs.go`**:
    *   `proc.c`の`runtime·newproc1`関数から`newg->panicwrap = 0;`の行が削除されています。
    *   `stack.c`の`runtime·oldstack`および`runtime·newstack`関数から`gp->panicwrap`に関する処理が削除されています。
    *   `stubs.go`の`reflectcall`関数のシグネチャから`p *_panic`引数が削除されています。

7.  **`test/recover.go`**:
    *   新しいテストケース`test111()`と`badstate()`が追加されています。これらは、ラッパー関数内でパニックが発生し、`recover`が正しく機能するかどうかを検証するためのものです。特に`badstate()`のコメントは、このコミットが以前の`recover`実装では機能しなかった特定のシナリオを修正したことを明確に述べています。

## コアとなるコードの解説

このコミットの核心的な変更は、Goランタイムがパニックとリカバリーを処理する方法、特に`reflect.call`のようなラッパー関数が関与する場合のスタックポインタの管理方法を根本的に改善した点にあります。

**`gp->panicwrap`から`Panic.argp`への移行:**

以前の`gp->panicwrap`は、ラッパー関数がスタックフレームを調整する際に、パニック時の`recover`が正しいスタック位置を特定できるようにするためのオフセットでした。しかし、このオフセットは関数のエントリとエグジットの両方で調整する必要があり、パニックによってエグジット時の調整がスキップされると、`recover`が誤動作する原因となっていました。

このコミットでは、`_panic`構造体に`argp`フィールドが導入されました。この`argp`は、`defer`された関数が実行される際の引数ポインタを保持します。重要なのは、この`argp`が**ラッパー関数のエントリ時のみ**に更新されるようになった点です。

**リンカによるアセンブリコード生成の変更 (`src/liblink/obj*.c`)**:

Goのリンカ（`liblink`）は、Goのソースコードから最終的な実行可能ファイルを生成する際に、アセンブリコードを生成・最適化します。このコミットでは、特に`WRAPPER`としてマークされた関数（例: `reflect.call`によって呼び出される関数）のプロローグに生成されるアセンブリコードが変更されました。

例えば、`src/liblink/obj5.c`（ARMアーキテクチャ向け）の変更を見ると、以前の`g->panicwrap`を操作するコードが削除され、代わりに以下のロジックが追加されています（擬似コード）：

```c
// if(g->panic != nil && g->panic->argp == FP) g->panic->argp = bottom-of-frame
//
//	MOVW g_panic(g), R1  // g->panic を R1 にロード
//	CMP $0, R1           // R1 が nil かチェック
//	B.EQ end             // nil ならスキップ
//	MOVW panic_argp(R1), R2 // panic->argp を R2 にロード
//	ADD $(autosize+4), R13, R3 // 現在のフレームの底を計算 (R13はSP)
//	CMP R2, R3           // panic->argp と計算した底を比較
//	B.NE end             // 異なればスキップ
//	ADD $4, R13, R4      // 新しい argp を計算 (SP + 4)
//	MOVW R4, panic_argp(R1) // panic->argp を更新
// end:
//	NOP
```

このコードは、現在のゴルーチンにアクティブなパニックがあり（`g->panic != nil`）、かつそのパニックの`argp`が現在のフレームポインタ（FP）と一致する場合にのみ、`Panic.argp`を現在のスタックフレームの底に更新します。これにより、`recover`が呼び出された際に、正しいスタックフレームの引数ポインタを確実に参照できるようになります。エグジット時の調整が不要になったため、パニックによる中断の影響を受けなくなりました。

**`panic1.go`と`gorecover`の簡素化:**

`src/pkg/runtime/panic1.go`の`gopanic`関数では、パニック発生時に`p.argp = getargp(0)`という行が追加され、`_panic`構造体の`argp`フィールドが初期化されるようになりました。`getargp`は、現在のスタックフレームの引数ポインタ（スタックフレームの底）を返すヘルパー関数です。

最も重要な変更は`gorecover`関数にあります。以前は、`recover`が正しいスタックフレームを特定するために、`argp == p.argp-uintptr(gp.panicwrap)`という複雑な計算を行っていました。しかし、`Panic.argp`が常に正しいスタックフレームの底を指すようになったため、この計算は不要になり、`argp == p.argp`という非常にシンプルな比較でリカバリーの条件を判断できるようになりました。これにより、`recover`のロジックが大幅に簡素化され、堅牢性が向上しました。

これらの変更により、Goのパニックとリカバリーのメカニズムは、特に`reflect.call`のような動的な呼び出しやラッパー関数が関与する複雑なシナリオにおいて、より予測可能で信頼性の高いものとなりました。

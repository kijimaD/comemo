## 元コミット内容

このコミットは、`net` パッケージ内の `(*resolverConfig).tryUpdate` メソッドにおける競合状態を修正します。この競合状態は、`/etc/resolv.conf` ファイルの変更時刻を追跡し、DNS設定を更新するロジックに関連していました。

主な変更点は以下の通りです。

*   `resolverConfig` 構造体から `modTime` フィールドを削除。
*   `dnsConfig` 構造体に `mtime` フィールド（`/etc/resolv.conf` の最終更新時刻）を追加。
*   `dnsReadConfig` 関数が `/etc/resolv.conf` を読み込む際に、そのファイルの最終更新時刻を `dnsConfig.mtime` に保存するように変更。
*   `(*resolverConfig).tryUpdate` メソッドが、現在有効な `dnsConfig` に格納されている `mtime` と、`/etc/resolv.conf` の現在の最終更新時刻を比較して、設定の再読み込みが必要かどうかを判断するように変更。

これにより、`resolverConfig` の `modTime` が `dnsConfig` の更新と同期しないことによって発生していた競合状態が解消されます。

## 変更の背景

この変更は、GoのIssue #14072 で報告された問題に対応しています。このIssueでは、Goプログラムが `/etc/resolv.conf` の変更を検知してDNS設定を更新する際に、まれに古い設定を使用し続ける競合状態があることが指摘されていました。

具体的には、`resolverConfig` 構造体は `/etc/resolv.conf` の最終更新時刻を `modTime` フィールドで保持し、`dnsConfig` フィールドでパースされたDNS設定を保持していました。`tryUpdate` メソッドは、`modTime` をチェックしてファイルが変更されたかどうかを判断し、必要であれば新しい `dnsConfig` を読み込んでいました。しかし、`modTime` の更新と `dnsConfig` の更新がアトミックに行われていなかったため、以下のシナリオで問題が発生する可能性がありました。

1.  `tryUpdate` が `modTime` を読み込み、ファイルが変更されていないと判断する。
2.  別のゴルーチンや外部プロセスが `/etc/resolv.conf` を変更し、その結果 `modTime` が更新される。
3.  しかし、`tryUpdate` は既にファイルが変更されていないと判断しているため、新しい `dnsConfig` を読み込まず、古い設定を使い続けてしまう。

この競合状態により、システム管理者が `/etc/resolv.conf` を更新しても、Goアプリケーションがその変更をすぐに反映しないという問題が発生していました。

## 前提知識の解説

### DNS (Domain Name System)

DNSは、インターネット上のコンピュータやサービスを識別するための階層的な分散型命名システムです。人間が覚えやすいドメイン名（例: `www.example.com`）を、コンピュータが理解できるIPアドレス（例: `192.0.2.1`）に変換する役割を担っています。Go言語の `net` パッケージは、このDNSルックアップ機能を提供します。

### `/etc/resolv.conf`

Unix系OSにおいて、`/etc/resolv.conf` はDNSリゾルバの設定ファイルです。このファイルには、DNSクエリを解決するために使用されるDNSサーバーのIPアドレス（`nameserver` エントリ）、ドメイン名の解決時に検索されるドメインサフィックス（`search` エントリ）、その他のリゾルバオプション（`options` エントリ）などが記述されています。Goの `net` パッケージは、このファイルを読み込んでDNS解決の動作を決定します。

### 競合状態 (Race Condition)

競合状態とは、複数のプロセスやスレッドが共有リソースにアクセスする際に、そのアクセス順序によって結果が非決定的に変化してしまうプログラミング上のバグの一種です。このコミットで修正された問題は、`modTime` と `dnsConfig` という二つの関連するデータが、アトミックに更新されないために発生していました。

### `sync.RWMutex`

Go言語の `sync` パッケージが提供する `RWMutex` は、読み取り/書き込みロックです。複数の読み取り操作は同時に許可されますが、書き込み操作は排他的に行われます。このコミットでは、`resolverConfig` の `dnsConfig` フィールドへのアクセスを保護するために `sync.RWMutex` が使用されています。

### `os.Stat()` と `FileInfo.ModTime()`

`os.Stat(name string)` 関数は、指定されたファイルまたはディレクトリの情報を返します。返される `os.FileInfo` インターフェースには、ファイルの最終更新時刻を返す `ModTime()` メソッドが含まれています。この機能は、ファイルが変更されたかどうかを検知するために利用されます。

## 技術的詳細

このコミットの核心は、`/etc/resolv.conf` の最終更新時刻の管理方法を変更することで、DNS設定の更新における競合状態を解消することです。

以前の実装では、`resolverConfig` 構造体が `modTime` フィールドで `/etc/resolv.conf` の最終更新時刻を直接保持していました。そして、`dnsConfig` フィールドでパースされたDNS設定を保持していました。`tryUpdate` メソッドは、一定間隔で `/etc/resolv.conf` の現在の `ModTime` を取得し、それを `resolverConfig.modTime` と比較していました。もし異なっていれば、ファイルが変更されたと判断し、`dnsReadConfig` を呼び出して新しい `dnsConfig` を読み込み、`resolverConfig.dnsConfig` を更新していました。同時に `resolverConfig.modTime` も新しいファイルの `ModTime` で更新していました。

このアプローチの問題点は、`resolverConfig.modTime` と `resolverConfig.dnsConfig` の更新が別々のステップで行われるため、その間に競合状態が発生する可能性があったことです。

新しいアプローチでは、`dnsConfig` 構造体自体に `mtime` フィールドが追加されました。`dnsReadConfig` 関数が `/etc/resolv.conf` を読み込んで `dnsConfig` オブジェクトを生成する際に、そのファイルの最終更新時刻を `dnsConfig.mtime` に格納するように変更されました。

これにより、`resolverConfig.dnsConfig` が指す `dnsConfig` オブジェクトは、それがパースされた時点の `/etc/resolv.conf` の最終更新時刻を常に内部に保持するようになります。

`(*resolverConfig).tryUpdate` メソッドは、設定の更新が必要かどうかを判断する際に、以下のロジックを使用します。

1.  `/etc/resolv.conf` の現在の最終更新時刻 (`current_mtime`) を取得します。
2.  現在有効な `dnsConfig` オブジェクト（`conf.dnsConfig`）に格納されている `mtime` (`stored_mtime`) と `current_mtime` を比較します。
3.  もし `current_mtime` と `stored_mtime` が異なっていれば、`/etc/resolv.conf` が変更されたと判断し、`dnsReadConfig` を呼び出して新しい `dnsConfig` を読み込み、`conf.dnsConfig` を更新します。

この変更により、`dnsConfig` オブジェクトと、それがどの時点の `/etc/resolv.conf` から生成されたかという情報が常に一体となるため、競合状態が解消されます。`resolverConfig` は、`dnsConfig` オブジェクトへのポインタを保持するだけでよくなり、`modTime` を別途管理する必要がなくなりました。

## コアとなるコードの解説

### `resolverConfig` 構造体からの `modTime` 削除

`resolverConfig` は、DNSリゾルバ全体の状態を管理する構造体です。以前は `/etc/resolv.conf` の最終更新時刻を `modTime` として直接保持していました。しかし、この `modTime` は `dnsConfig` (パースされた設定) とは独立して更新される可能性があり、これが競合状態の原因となっていました。`modTime` を削除することで、`resolverConfig` は設定ファイルの更新時刻の管理責任から解放され、その責任は `dnsConfig` オブジェクト自体に移譲されます。

### `dnsConfig` 構造体への `mtime` 追加

`dnsConfig` は、`/etc/resolv.conf` からパースされた具体的なDNS設定（ネームサーバー、検索ドメインなど）を保持する構造体です。この構造体に `mtime time.Time` フィールドを追加することで、**「この `dnsConfig` オブジェクトは、いつの時点の `/etc/resolv.conf` から生成されたか」**という情報が、設定データと一体となって管理されるようになります。これにより、`dnsConfig` オブジェクトが有効である限り、その生成元のファイルの更新時刻も同時に参照できるようになります。

### `dnsReadConfig` での `mtime` 設定

`dnsReadConfig` 関数は、指定されたファイル（通常は `/etc/resolv.conf`）を読み込み、その内容をパースして `dnsConfig` オブジェクトを生成します。このコミットでは、ファイルの内容をパースする前に `file.file.Stat()` を呼び出し、ファイルの `ModTime()` を取得して、新しく生成される `dnsConfig` オブジェクトの `mtime` フィールドに設定するロジックが追加されました。これにより、`dnsConfig` オブジェクトが生成されると同時に、その「鮮度」情報も埋め込まれることになります。

### `(*resolverConfig).tryUpdate` の変更

`tryUpdate` メソッドは、定期的に `/etc/resolv.conf` の変更をチェックし、必要に応じてDNS設定を更新する役割を担います。
変更後、このメソッドは以下の手順で動作します。

1.  現在の `/etc/resolv.conf` の最終更新時刻 (`mtime`) を `os.Stat()` で取得します。
2.  現在 `resolverConfig` が保持している `dnsConfig` オブジェクト (`conf.dnsConfig`) の `mtime` フィールドと、上記で取得した現在の `mtime` を比較します。
3.  もし両者が等しければ、ファイルは変更されていないと判断し、更新処理をスキップします。
4.  もし両者が異なっていれば、ファイルが変更されたと判断し、`dnsReadConfig` を呼び出して新しい `dnsConfig` オブジェクトを生成し、`conf.dnsConfig` を更新します。

この変更により、`resolverConfig` が保持する `dnsConfig` オブジェクトと、そのオブジェクトがどの時点のファイルから生成されたかという情報が常に同期されるため、競合状態が解消され、より堅牢な設定更新メカニズムが実現されます。

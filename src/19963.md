# [インデックス 19963] ファイルの概要

このコミットは、Goのビルドツール (`cmd/go`) において、`cgo` を使用して中間オブジェクトファイルを生成する際に、リンカに `--build-id=none` オプションを渡すように変更するものです。これにより、最終的なGoの実行ファイルに複数のビルドIDが不必要に埋め込まれる問題を解決し、バイナリの健全性とデバッグ情報の整合性を保ちます。

## 元コミット内容

```
cmd/go: pass --build-id=none when generating a cgo .o

Some systems, like Ubuntu, pass --build-id when linking. The
effect is to put a note in the output file. This is not
useful when generating an object file with the -r option, as
it eventually causes multiple build ID notes in the final
executable, all but one of which are for tiny portions of the
file and are therefore useless.

linking with -r on systems that might do this.
```

## 変更の背景

この変更の背景には、特定のLinuxディストリビューション（特にUbuntuなど）におけるリンカのデフォルト挙動と、Goの `cgo` ビルドプロセスが密接に関連しています。

Goプログラムをビルドする際、通常はGoコンパイラとGoリンカが使用されます。しかし、`cgo` を利用してGoコードからC/C++コードを呼び出す場合、GoのビルドシステムはC/C++コンパイラ（GCCやClangなど）とそのリンカも利用します。

問題は、一部のシステムにおいて、C/C++リンカがデフォルトで `--build-id` オプションを有効にしてリンクを行うことにありました。`--build-id` オプションは、生成される実行ファイルや共有ライブラリに一意のビルドID（通常はファイルのコンテンツのハッシュ値）を埋め込むためのものです。このビルドIDは、デバッグ情報やクラッシュレポートの解析において、特定のバイナリバージョンを識別するために非常に有用です。

しかし、`cgo` が中間オブジェクトファイル（`.o` ファイル）を生成する際に、GoのビルドシステムはC/C++リンカに `-r` オプション（再配置可能オブジェクトファイルを生成するオプション）を渡していました。この中間オブジェクトファイル自体にビルドIDが埋め込まれると、最終的にGoのリンカがこれらの中間オブジェクトファイルを結合して最終的な実行ファイルを生成する際に、複数のビルドIDが最終バイナリに混入してしまうという問題が発生しました。

コミットメッセージにあるように、「最終的な実行ファイルに複数のビルドIDノートが生成され、そのほとんどがファイルの小さな部分に対するものであり、したがって役に立たない」状態になっていました。これは、デバッグツールが正しいビルドIDを識別するのを妨げたり、バイナリのサイズを不必要に増加させたりする可能性がありました。

この問題を解決するため、`cgo` が中間オブジェクトファイルを生成する際に、明示的にC/C++リンカに `--build-id=none` オプションを渡すことで、不必要なビルドIDの埋め込みを抑制する必要がありました。これにより、最終的なGoの実行ファイルにはGoリンカによって生成された単一のビルドIDのみが含まれるようになり、デバッグ情報の整合性が保たれます。

## 前提知識の解説

### 1. Goのビルドプロセスと `cgo`

Goのビルドプロセスは、Goソースコードをコンパイルし、Goランタイムと標準ライブラリをリンクして実行可能ファイルを生成します。
`cgo` は、GoプログラムからC言語のコードを呼び出すためのGoの組み込み機能です。`cgo` を使用すると、GoコンパイラはCコードを通常のCコンパイラ（GCCやClangなど）に渡し、生成されたオブジェクトファイルをGoのビルドプロセスに統合します。この際、Goのビルドツール (`cmd/go`) は、Cコンパイラとリンカを呼び出して中間オブジェクトファイルを生成し、それをGoのリンカが最終的な実行ファイルに結合します。

### 2. ビルドID (`--build-id`)

ビルドIDは、実行可能ファイルや共有ライブラリに埋め込まれる一意の識別子です。これは通常、ファイルのコンテンツのハッシュ値に基づいて生成されます。ビルドIDの主な目的は、特定のバイナリのバージョンを正確に識別することにあります。デバッグツール（GDBなど）やクラッシュレポートシステムは、このビルドIDを使用して、対応するデバッグ情報（シンボルテーブルなど）を見つけ出し、クラッシュダンプを解析します。
Linuxシステムでは、GNU Binutilsのリンカ (`ld`) やGoldリンカ、Clangのリンカなどが `--build-id` オプションをサポートしています。このオプションが指定されると、ELFバイナリの `.note.gnu.build-id` セクションにビルドIDが記録されます。

### 3. ELF (Executable and Linkable Format)

ELFは、Unix系システム（Linux、BSDなど）で広く使用されている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、および様々なセクション（コード、データ、シンボルテーブル、デバッグ情報など）で構成されます。ビルドIDは、ELFファイルの `.note` セクションの一種である `.note.gnu.build-id` に格納されます。`.note` セクションは、バイナリに関する任意のメタデータを格納するために使用されます。

### 4. リンカオプション `-r` (relocatable)

リンカの `-r` オプションは、再配置可能なオブジェクトファイルを生成するために使用されます。通常、リンカは最終的な実行可能ファイルや共有ライブラリを生成しますが、`-r` オプションを使用すると、複数のオブジェクトファイルを結合して、さらに別のリンクステップで最終的なバイナリに結合できる中間オブジェクトファイルを生成できます。`cgo` のビルドプロセスでは、CコードをコンパイルしてGoコードとリンクする前に、この中間オブジェクトファイルを生成するためにC/C++リンカに `-r` が渡されます。

### 5. `ldflags`

`ldflags` は、Goのビルドコマンド (`go build` や `go install`) でリンカに渡す追加のフラグを指定するための環境変数またはビルドオプションです。例えば、`-ldflags="-s -w"` は、シンボルテーブルとデバッグ情報を削除してバイナリサイズを削減するために使われます。このコミットでは、Goのビルドツールが内部的にC/C++リンカを呼び出す際に、この `ldflags` に `--build-id=none` を追加しています。

### 6. `gccld` 関数

Goの `src/cmd/go/build.go` 内にある `gccld` 関数は、GoのビルドツールがC/C++リンカ（通常は `gcc` コマンド）を呼び出すための内部ヘルパー関数です。この関数が、`cgo` が生成したオブジェクトファイルをリンクする際に使用されます。

## 技術的詳細

このコミットの技術的な核心は、`cgo` が中間オブジェクトファイルを生成する際のC/C++リンカの挙動を、Goのビルドツールが明示的に制御することにあります。

1.  **問題の再確認**: 一部のシステム（特にUbuntuのようなLinuxディストリビューション）では、C/C++リンカがデフォルトで `--build-id` オプションを有効にしてリンクを行います。これは、最終的な実行ファイルには有用ですが、`cgo` が生成する中間オブジェクトファイル（`-r` オプションでリンクされるもの）にビルドIDが埋め込まれると、最終的なGoの実行ファイルに複数のビルドIDが混入するという副作用がありました。これらの余分なビルドIDは、中間オブジェクトファイルの小さな部分に対応するものであり、最終バイナリ全体の識別には役立たず、むしろデバッグツールが正しいビルドIDを識別するのを妨げたり、バイナリのサイズを不必要に増加させたりする可能性がありました。

2.  **解決策としての `--build-id=none`**: この問題を解決するために、Goのビルドツールは、`cgo` が中間オブジェクトファイルを生成する際に、C/C++リンカに明示的に `--build-id=none` オプションを渡すように変更されました。このオプションは、リンカに対してビルドIDを生成しないように指示します。これにより、`cgo` によって生成される中間オブジェクトファイルにはビルドIDが含まれなくなり、最終的なGoの実行ファイルにはGoリンカによって生成された単一のビルドIDのみが含まれるようになります。

3.  **条件付き適用とOSの考慮**: コミットメッセージとコードの変更箇所を見ると、この `--build-id=none` オプションは、特定のオペレーティングシステム（`android`, `dragonfly`, `freebsd`, `linux`, `netbsd`, `openbsd`）でのみ適用されるようになっています。これは、これらのシステムが通常、GoldリンカやGNUリンカを使用しており、`--build-id` オプションのデフォルト挙動が問題を引き起こす可能性が高いと判断されたためです。他のシステムでは、この問題が発生しないか、異なるリンカの挙動があるため、一律に適用する必要がないと判断されたと考えられます。この選択的な適用は、不必要な変更を避け、影響範囲を最小限に抑えるためのGoのビルドシステムの設計思想を反映しています。

4.  **Clangリンカへの対応**: コミットメッセージには、「clang 3.0 はプレーンな `-r` をサポートしていない」という言及があります。これは、一部のリンカでは `-r` オプション自体が `--build-id` の生成を抑制する効果を持つことがありますが、Clangのような特定のリンカではそうではないことを示唆しています。そのため、より確実な方法として、明示的に `--build-id=none` を渡すアプローチが採用されました。これにより、リンカの種類に関わらず、ビルドIDの生成を確実に抑制できます。

5.  **テストによる検証**: この変更の正しさを検証するために、`misc/cgo/test/buildid_linux.go` という新しいテストファイルが追加されました。このテストは、生成された実行ファイルにビルドIDが1つだけ含まれていることを確認します。これは、複数のビルドIDが混入する問題が解決されたことを保証するための重要なステップです。テストはELFファイルの構造を解析し、`.note` セクションを調べて `NT_GNU_BUILD_ID` タイプのノートが1つだけ存在することを確認します。これにより、Goのビルドシステムが期待通りに動作し、単一のビルドIDのみが最終バイナリに埋め込まれることが保証されます。

**`misc/cgo/test/buildid_linux.go` の追加:**

```go
// Copyright 2014 The Go Authors.  All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package cgotest

// Test that we have no more than one build ID.  In the past we used
// to generate a separate build ID for each package using cgo, and the
// linker concatenated them all.  We don't want that--we only want
// one.

import (
	"bytes"
	"debug/elf"
	"os"
	"testing"
)

func testBuildID(t *testing.T) {
	f, err := elf.Open("/proc/self/exe")
	if err != nil {
		if os.IsNotExist(err) {
			t.Skip("no /proc/self/exe")
		}
		t.Fatalf("opening /proc/self/exe: ", err)
	}
	defer f.Close()

	c := 0
	for i, s := range f.Sections {
		if s.Type != elf.SHT_NOTE {
			continue
		}

		d, err := s.Data()
		if err != nil {
			t.Logf("reading data of note section %d: %v", i, err)
			continue
		}

		for len(d) > 0 {

			// ELF standards differ as to the sizes in
			// note sections.  Both the GNU linker and
			// gold always generate 32-bit sizes, so that
			// is what we assume here.

			if len(d) < 12 {
				t.Logf("note section %d too short (%d < 12)", i, len(d))
				continue
			}

			namesz := f.ByteOrder.Uint32(d)
			descsz := f.ByteOrder.Uint32(d[4:])
			typ := f.ByteOrder.Uint32(d[8:])

			an := (namesz + 3) &^ 3
			ad := (descsz + 3) &^ 3

			if int(12+an+ad) > len(d) {
				t.Logf("note section %d too short for header (%d < 12 + align(%d,4) + align(%d,4))", i, len(d), namesz, descsz)
				continue
			}

			// 3 == NT_GNU_BUILD_ID
			if typ == 3 && namesz == 4 && bytes.Equal(d[12:16], []byte("GNU\\000")) {
				c++
			}

			d = d[12+an+ad:]
		}
	}

	if c > 1 {
		t.Errorf("found %d build ID notes", c)
	}
}
```

## コアとなるコードの解説

### `src/cmd/go/build.go` の変更

このファイルはGoのビルドコマンド (`cmd/go`) の中核をなす部分で、特に `cgo` を使用する際の外部リンカの呼び出しを管理しています。

変更前は、`cgo` が生成するオブジェクトファイルをリンクする際に、`b.gccld` 関数に直接 `stringList(bareLDFLAGS, "-Wl,-r", "-nostdlib", staticLibs)` というリンカフラグのリストを渡していました。

変更後、このリンカフラグのリストは `ldflags` という変数に格納されるようになりました。そして、`goos` (GoがターゲットとするOS) の値に基づいて、条件分岐が追加されました。

```go
	ldflags := stringList(bareLDFLAGS, "-Wl,-r", "-nostdlib", staticLibs)

	// Some systems, such as Ubuntu, always add --build-id to
	// every link, but we don't want a build ID since we are
	// producing an object file. On some of those system a plain
	// -r (not -Wl,-r) will turn off --build-id, but clang 3.0
	// doesn't support a plain -r. I don't know how to turn off
	// --build-id when using clang other than passing a trailing
	// --build-id=none. So that is what we do, but only on
	// systems likely to support it, which is to say, systems that
	// normally use gold or the GNU linker.
	switch goos {
	case "android", "dragonfly", "freebsd", "linux", "netbsd", "openbsd":
		ldflags = append(ldflags, "-Wl,--build-id=none")
	}

	if err := b.gccld(p, ofile, ldflags, gccObjs); err != nil {
		return nil, nil, err
	}
```

この `switch` ステートメントは、ターゲットOSが `android`, `dragonfly`, `freebsd`, `linux`, `netbsd`, `openbsd` のいずれかである場合にのみ、`"-Wl,--build-id=none"` というリンカフラグを `ldflags` リストに追加します。

*   `-Wl,` は、続くオプションをリンカに直接渡すことを意味します。これは、`gcc` や `clang` のようなコンパイラドライバが、リンカに特定のオプションを渡すための一般的な方法です。
*   `--build-id=none` は、リンカに対してビルドIDを生成しないように明示的に指示するオプションです。

これにより、これらのOS上で `cgo` を使用して中間オブジェクトファイルを生成する際に、不必要なビルドIDが埋め込まれるのを防ぎます。

### `misc/cgo/test/buildid_linux.go` の追加

このファイルは、ビルドIDが適切に処理されていることを検証するための新しいテスト `testBuildID` を定義しています。

```go
package cgotest

import (
	"bytes"
	"debug/elf"
	"os"
	"testing"
)

func testBuildID(t *testing.T) {
	f, err := elf.Open("/proc/self/exe") // 現在実行中のバイナリ（テストバイナリ自体）をELFファイルとして開く
	if err != nil {
		if os.IsNotExist(err) {
			t.Skip("no /proc/self/exe") // /proc/self/exe がない場合はテストをスキップ（一部の環境では存在しないため）
		}
		t.Fatalf("opening /proc/self/exe: ", err) // ファイルを開けなかった場合は致命的なエラーとして報告
	}
	defer f.Close() // 関数終了時にファイルを確実に閉じる

	c := 0 // ビルドIDノートのカウント用変数
	for i, s := range f.Sections { // ELFファイルの各セクションをイテレート
		if s.Type != elf.SHT_NOTE { // NOTEセクション以外はスキップ
			continue
		}

		d, err := s.Data() // セクションの生データを読み込む
		if err != nil {
			t.Logf("reading data of note section %d: %v", i, err) // データ読み込みエラーはログに記録し、次のセクションへ
			continue
		}

		for len(d) > 0 { // ノートセクション内に複数のノートがある可能性があるのでループ
			// ELF noteセクションの構造を解析
			// namesz (name size), descsz (descriptor size), typ (type) を読み取る
			// GNUリンカとgoldリンカは32ビットサイズを生成すると仮定
			if len(d) < 12 { // ノートヘッダの最小サイズ（12バイト）に満たない場合は不正なノートとしてスキップ
				t.Logf("note section %d too short (%d < 12)", i, len(d))
				continue
			}

			namesz := f.ByteOrder.Uint32(d)     // ノート名のサイズ
			descsz := f.ByteOrder.Uint32(d[4:]) // ノートディスクリプタのサイズ
			typ := f.ByteOrder.Uint32(d[8:])    // ノートのタイプ

			an := (namesz + 3) &^ 3 // ノート名のサイズを4バイトアラインメント
			ad := (descsz + 3) &^ 3 // ノートディスクリプタのサイズを4バイトアラインメント

			if int(12+an+ad) > len(d) { // ノート全体のサイズが残りのデータ長を超える場合は不正なノートとしてスキップ
				t.Logf("note section %d too short for header (%d < 12 + align(%d,4) + align(%d,4))", i, len(d), namesz, descsz)
				continue
			}

			// 3 == NT_GNU_BUILD_ID (GNUビルドIDのタイプ)
			// namesz == 4 && bytes.Equal(d[12:16], []byte("GNU\\000")) は、
			// ノートの所有者が "GNU" であり、それがビルドIDであることを確認します。
			// "GNU\000" は、ELFノートの所有者名が "GNU" であり、ヌル終端されていることを意味します。
			if typ == 3 && namesz == 4 && bytes.Equal(d[12:16], []byte("GNU\\000")) {
				c++ // ビルドIDノートの数をカウント
			}

			d = d[12+an+ad:] // 現在のノートをスキップし、残りのデータから次のノートを解析
		}
	}

	if c > 1 {
		t.Errorf("found %d build ID notes", c) // ビルドIDノートが1つより多い場合はエラーとして報告
	}
}
```

このテストは、以下の手順でビルドIDの数を検証します。
1.  現在実行中のGoバイナリ（`/proc/self/exe`）をELFファイルとして開きます。これは、テストが実行されるGoプログラム自体が、`cgo` を含むビルドプロセスを経て生成されたものであることを前提としています。
2.  ELFファイルのすべてのセクションを走査し、タイプが `elf.SHT_NOTE` であるノートセクションを探します。
3.  各ノートセクションのデータを解析し、ELFノートの構造（`namesz`, `descsz`, `typ`）を読み取ります。特に、GNUリンカが生成するビルドIDノートは、`typ` が `NT_GNU_BUILD_ID` (値は3) であり、かつノートの所有者名が "GNU" であるという特徴を持ちます。
4.  識別されたビルドIDノートの数をカウントします。
5.  最終的に、カウントされたビルドIDノートの数が1より大きい場合、テストは失敗します。これは、複数のビルドIDが混入していることを意味し、このコミットが解決しようとしている問題がまだ存在することを示します。このテストの目的は、最終的なGoバイナリにGoリンカによって生成された単一のビルドIDのみが含まれることを保証することです。

### `misc/cgo/test/cgo_linux_test.go` の変更

このファイルは、既存の `cgo` 関連のテストスイートに、新しく追加された `TestBuildID` 関数を組み込むための変更です。これにより、`go test misc/cgo/test` を実行した際に、ビルドIDのテストも自動的に実行されるようになります。これは、回帰テストとして機能し、将来の変更がこのビルドIDの問題を再発させないことを保証します。

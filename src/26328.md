## 変更の背景

この変更の背景には、Goのテストフレームワーク、特に`runtime`パッケージのテストにおいて、テストプログラムのビルドに失敗した場合のエラー報告の質を向上させるという目的があります。

`src/runtime/crash_test.go`のようなファイルは、Goランタイムの特定の挙動（この場合はクラッシュ関連のテスト）を検証するために、補助的なテストプログラムを動的にビルドして実行することがあります。このようなテストでは、テスト対象のコードが正しく動作するかどうかを確認するために、まずテスト用のバイナリをコンパイルする必要があります。

元のコードでは、`buildTestProg`関数がテストプログラムのビルドに失敗した場合、`fmt.Errorf`でラップされた詳細なエラーメッセージを`target.err`に格納しつつも、関数自体は元のビルドエラー`err`をそのまま返していました。この`err`は、`fmt.Errorf`によって追加されたコンテキスト情報（ビルド対象のバイナリ名や標準出力/標準エラー出力の内容）を含んでいませんでした。

結果として、テストの実行者がビルド失敗のエラーを受け取った際、そのエラーメッセージが不十分であるため、何が問題だったのか（どのバイナリのビルドに失敗し、どのようなコンパイルエラーが出たのかなど）を特定するのが困難でした。このコミットは、より詳細なエラー情報を含む`target.err`を返すことで、デバッグの効率を向上させることを目的としています。

## 前提知識の解説

*   **Go言語の`runtime`パッケージ**: Goプログラムの実行時システム（ガベージコレクション、スケジューラ、メモリ管理など）を実装しているパッケージです。非常に低レベルな処理を扱い、Go言語自体の動作に深く関わっています。`crash_test.go`のようなファイルは、このランタイムの堅牢性を保証するための重要なテストを含んでいます。
*   **Go言語の`testing`パッケージ**: Go言語に組み込まれているテストフレームワークです。`go test`コマンドを通じて利用され、ユニットテスト、ベンチマークテスト、例（Example）テストなどを記述するための機能を提供します。`*testing.T`はテスト関数に渡される型で、テストの失敗を報告したり、ログを出力したりするメソッドを提供します。
*   **`fmt.Errorf`**: Go言語の`fmt`パッケージが提供する関数で、フォーマット文字列と引数を受け取り、新しいエラー値を生成します。特に、既存のエラーにコンテキスト情報を追加して新しいエラーを作成する際によく使用されます。これにより、エラーが発生した場所や状況に関する詳細な情報をエラーチェーンに含めることができます。
*   **テストプログラムの動的ビルド**: 一部の複雑なテスト（特にランタイムやコンパイラ関連のテスト）では、テスト中に特定のコードをコンパイルして実行する必要があります。これは、テスト対象の挙動が通常のテスト関数では再現しにくい場合や、異なるコンパイルオプションや環境でテストする必要がある場合に用いられます。`buildTestProg`関数は、このような動的ビルドのロジックをカプセル化しています。
*   **エラーハンドリングのベストプラクティス**: Go言語では、エラーは戻り値として明示的に扱われます。エラーが発生した際には、そのエラーに適切なコンテキスト情報を付加して上位に伝えることが推奨されます。これにより、最終的にエラーを受け取った側が問題の原因を特定しやすくなります。このコミットは、まさにこのベストプラクティスに沿った改善と言えます。

## 技術的詳細

この変更は、`src/runtime/crash_test.go`ファイル内の`buildTestProg`関数に焦点を当てています。この関数は、テスト目的で特定のGoプログラムをビルドし、その実行可能ファイルのパスとエラーを返します。

変更前のコードでは、ビルドプロセス中にエラーが発生した場合、以下の処理が行われていました。

1.  `fmt.Errorf("building %s: %v\\n%s", binary, err, out)`を使用して、より詳細なエラーメッセージ（ビルド対象のバイナリ名、元のエラー、ビルドコマンドの標準出力/標準エラー出力）を含む新しいエラーオブジェクトを作成し、`target.err`フィールドに格納していました。
2.  しかし、`buildTestProg`関数自体の戻り値としては、元のビルドエラー`err`（`fmt.Errorf`でラップされる前の、より情報量の少ないエラー）をそのまま返していました。

この挙動により、`buildTestProg`の呼び出し元は、`target.err`に格納された豊富なデバッグ情報にアクセスできず、単に「ビルドに失敗した」という情報しか得られない可能性がありました。

このコミットによる変更は非常にシンプルですが、その効果は大きいです。関数が返すエラーを、詳細なコンテキスト情報を含む`target.err`に変更することで、テストの失敗時に開発者が受け取るエラーメッセージが格段に分かりやすくなります。これにより、ビルド失敗の原因（例えば、コンパイルエラーの具体的な内容）を迅速に特定し、デバッグ時間を短縮することが可能になります。

これは、Goのエラーハンドリングにおける「エラーにコンテキストを追加する」という原則を具体的に適用した例であり、特に複雑なテスト環境における診断能力の向上に貢献します。

## コアとなるコードの解説

変更が行われたのは、`buildTestProg`関数内のエラー処理ブロックです。

```go
func buildTestProg(t *testing.T, binary string) (string, error) {
    // ... (前略) ...

    if err != nil { // ビルド中にエラーが発生した場合
        exe = "" // 実行可能ファイルのパスをクリア
        // 詳細なエラーメッセージを作成し、target.err に格納
        target.err = fmt.Errorf("building %s: %v\n%s", binary, err, out)
        // testprog.target マップを更新
        testprog.target[binary] = target
        // 変更前: return "", err // 元の、情報量の少ないエラーを返す
        // 変更後:
        return "", target.err // 詳細なエラー情報を含む target.err を返す
    }

    // ... (後略) ...
}
```

*   **`if err != nil`**: `go build`コマンドの実行結果としてエラーが発生したことを検出する条件分岐です。
*   **`target.err = fmt.Errorf("building %s: %v\\n%s", binary, err, out)`**: ここで、元のビルドエラー`err`と、ビルドコマンドの標準出力/標準エラー出力`out`、そしてビルド対象のバイナリ名`binary`を組み合わせて、より詳細なエラーメッセージを作成しています。この詳細なエラーは`target`構造体の`err`フィールドに保存されます。
*   **`return "", target.err`**: この行が変更の核心です。変更前は`return "", err`となっており、`fmt.Errorf`でラップされる前の、情報量の少ない`err`が返されていました。変更後は`return "", target.err`となり、`target.err`に格納された、より詳細なコンテキスト情報を含むエラーが呼び出し元に返されるようになりました。

この修正により、`buildTestProg`を呼び出すテストコードは、ビルド失敗時に「`building <binary_name>: <original_error_message>\n<build_output>`」のような、具体的な原因を特定しやすいエラーメッセージを受け取ることができるようになります。

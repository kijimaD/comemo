# [インデックス 24391] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション (GC) のアシストメカニズムに関する重要な変更を導入しています。具体的には、非プリエンプティブなコンテキスト（割り込み不可能な状況）でのGCアシストの実行を禁止することで、ランタイムの安定性と将来的なGC機能拡張への互換性を向上させています。

## コミット

```
commit 4f188c2d1c88d68d3f74a82c148cde804573d691
Author: Austin Clements <austin@google.com>
Date:   Wed Jul 22 15:14:54 2015 -0400

    runtime: disallow GC assists in non-preemptible contexts
    
    Currently it's possible to perform GC work on a system stack or when
    locks are held if there's an allocation that triggers an assist. This
    is generally a bad idea because of the fragility of these contexts,
    and it's incompatible with two changes we're about to make: one is to
    yield after signaling mark completion (which we can't do from a
    non-preemptible context) and the other is to make assists block if
    there'll be no other way for them to pay off the assist debt.
    
    This commit simply skips the assist if it's called from a
    non-preemptible context. The allocation will still count toward the
    assist debt, so it will be paid off by a later assist. There should be
    little allocation from non-preemptible contexts, so this shouldn't
    harm the overall assist mechanism.
    
    Change-Id: I7bf0e6c73e659fe6b52f27437abf39d76b245c79
    Reviewed-on: https://go-review.googlesource.com/12649
    Reviewed-by: Russ Cox <rsc@golang.org>
```

## 元コミット内容

Goランタイムにおいて、非プリエンプティブなコンテキスト（システムスタック上やロックを保持している状態）でメモリ割り当てが発生し、それがGCアシストをトリガーする可能性があるという問題がありました。このようなコンテキストでのGC作業は、その性質上非常に脆弱であり、将来的に導入される予定の2つの変更（マーク完了シグナル後のyieldと、アシストが債務を解消できない場合にブロックするメカニズム）と互換性がありませんでした。

このコミットでは、非プリエンプティブなコンテキストからGCアシストが呼び出された場合、そのアシストを単純にスキップするように変更しています。割り当て自体はGCアシスト債務として計上されるため、後続のアシストによって支払われることになります。非プリエンプティブなコンテキストからのメモリ割り当ては少ないと予想されるため、この変更が全体的なアシストメカニズムに悪影響を与えることはないと判断されています。

## 変更の背景

この変更の背景には、Goランタイムのガベージコレクタ (GC) の進化と安定性への配慮があります。GoのGCは、アプリケーションの実行と並行して動作するコンカレントGCを採用しており、プログラムの停止時間を最小限に抑えることを目指しています。この目標を達成するために、「GCアシスト」というメカニズムが導入されています。

しかし、GCアシストが特定の「非プリエンプティブなコンテキスト」で実行されると、問題が発生する可能性がありました。非プリエンプティブなコンテキストとは、Goランタイムの内部で非常にデリケートな処理が行われている状態を指し、例えばシステムコール中や、ランタイム内部の重要なロックを保持している間などが該当します。これらのコンテキストでは、予期せぬ割り込みや処理の停止が、ランタイムのクラッシュやデッドロックといった深刻な問題を引き起こす可能性があります。

コミットメッセージでは、特に以下の2つの将来的な変更との非互換性が指摘されています。

1.  **マーク完了シグナル後のyield:** GCのマークフェーズが完了した際に、ランタイムがスケジューラに制御を戻す（yieldする）ことで、他のゴルーチンに実行機会を与える変更が予定されていました。しかし、非プリエンプティブなコンテキストからはyieldできないため、この新しいメカニズムと衝突します。
2.  **アシストが債務を解消できない場合のブロック:** GCアシストが、割り当てられたメモリに対するGC作業（アシスト債務）を解消できない場合に、そのゴルーチンをブロックするような変更が計画されていました。非プリエンプティブなコンテキストでブロックが発生すると、ランタイム全体の停止やデッドロックにつながる危険性があります。

これらの問題を未然に防ぎ、将来のGC機能拡張をスムーズに行うために、非プリエンプティブなコンテキストでのGCアシストを禁止する変更が必要とされました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

### 1. Goのガベージコレクション (GC)

Goは、コンカレントな三色マーク＆スイープGCを採用しています。これは、GCの大部分の作業（オブジェクトのマークなど）がアプリケーションのゴルーチンと並行して実行されることを意味します。これにより、GCによるアプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑え、高いスループットと低いレイテンシを実現しています。

### 2. GCアシスト (GC Assist / Allocation Debt)

GCアシストは、GoのコンカレントGCを支える重要なメカニズムの一つです。GCがアクティブな期間中に、アプリケーションのゴルーチンがメモリを割り当てようとすると、そのゴルーチンは自身で少量のGC作業（マークフェーズの補助など）を行うよう「アシスト」を要求されることがあります。この作業は「GCアシスト」と呼ばれ、割り当てられたメモリ量に応じて「アシスト債務 (allocation debt)」として計上されます。

GCアシストの目的は、ヒープの成長速度がGCの処理速度を上回ることを防ぎ、GCが追いつかなくなる状況を回避することです。これにより、GCはヒープサイズを目標範囲内に保ち、STWフェーズの頻度と長さを減らすことができます。アシスト作業は、通常、割り当てを行うゴルーチンによって同期的に実行されます。

### 3. 非プリエンプティブなコンテキスト (Non-Preemptible Contexts)

Goランタイムには、特定の処理中にゴルーチンの実行を中断（プリエンプト）してはならない「非プリエンプティブなコンテキスト」が存在します。これらのコンテキストは、ランタイムの内部で非常に低レベルかつクリティカルな操作を行っており、中断されるとデータ構造の破損、デッドロック、あるいはシステムクラッシュにつながる可能性があります。

非プリエンプティブなコンテキストの典型的な例としては、以下のような状況が挙げられます。

*   **システムスタック (`gp.m.g0`)**: Goランタイムは、通常のゴルーチンが使用するスタック（g-stack）とは別に、ランタイム自身の内部処理やシステムコールを行うための「システムスタック」（g0-stack）を持っています。g0スタック上での実行は、通常、非プリエンプティブです。
*   **ロックの保持 (`mp.locks > 0`)**: ランタイム内部の重要なデータ構造を保護するために、ミューテックスなどのロックが使用されます。ロックを保持している間にゴルーチンがプリエンプトされると、他のゴルーチンがそのロックを待機し続け、デッドロックが発生する可能性があります。`mp.locks` は、現在のM (Machine) が保持しているロックの数を表します。
*   **プリエンプションの明示的な無効化 (`mp.preemptoff != ""`)**: ランタイムコードの一部では、`runtime.preemptoff()` のような関数を呼び出すことで、一時的にプリエンプションを明示的に無効にすることができます。これは、非常にデリケートな操作中に割り込みを防ぐために行われます。`mp.preemptoff` は、プリエンプションが無効になっている理由を示す文字列を保持します。

これらのコンテキストでは、GCアシストのような追加の作業が割り込むと、ランタイムの整合性が損なわれるリスクが高まります。

## 技術的詳細

このコミットの技術的詳細を掘り下げてみましょう。

GoのGCアシストは、`runtime/mgcmark.go` 内の `gcAssistAlloc` 関数によって管理されています。この関数は、メモリ割り当てが発生した際にGCアシストが必要かどうかを判断し、必要であればアシスト作業を実行します。

変更前の `gcAssistAlloc` 関数では、非プリエンプティブなコンテキストであるかどうかをチェックせずにアシスト作業を実行する可能性がありました。これが問題となるのは、非プリエンプティブなコンテキストでは、以下のような制約があるためです。

1.  **スタックの制約**: システムスタック (`g0`) は、通常のゴルーチンスタック (`g`) とは異なり、サイズが固定されているか、非常に限られた拡張性しか持たない場合があります。GCアシストが追加のスタック領域を必要とする場合、スタックオーバーフローを引き起こす可能性があります。
2.  **スケジューリングの制約**: 非プリエンプティブなコンテキストでは、現在のゴルーチン（またはM）は、そのクリティカルな作業が完了するまでCPUを占有し続けることが期待されます。GCアシストが `yield` を呼び出したり、長時間ブロックしたりすると、この期待が破られ、ランタイムのスケジューリングに悪影響を与え、他のゴルーチンの実行を不必要に遅延させる可能性があります。
3.  **ロックの制約**: ロックを保持している間にGCアシストが実行され、そのアシストがさらに別のロックを必要としたり、デッドロックを引き起こす可能性のある操作を行ったりすると、ランタイム全体の停止につながります。

このコミットでは、`gcAssistAlloc` 関数の冒頭に以下のチェックを追加することで、これらの問題を回避しています。

```go
	// Don't assist in non-preemptible contexts. These are
	// generally fragile and won't allow the assist to block.
	if getg() == gp.m.g0 {
		return
	}
	if mp := getg().m; mp.locks > 0 || mp.preemptoff != "" {
		return
	}
```

このコードスニペットは、現在のゴルーチンが非プリエンプティブなコンテキストで実行されているかどうかを判断するための3つの条件をチェックしています。

*   `getg() == gp.m.g0`: 現在のゴルーチン (`getg()`) が、現在のM (Machine) に関連付けられたシステムゴルーチン (`gp.m.g0`) であるかどうかをチェックします。システムゴルーチンは、ランタイムの内部処理を行うための特別なゴルーチンであり、通常はプリエンプトされません。
*   `mp.locks > 0`: 現在のM (`mp`) が一つ以上のランタイム内部ロックを保持しているかどうかをチェックします。ロックを保持している間は、プリエンプションや追加のGC作業は避けるべきです。
*   `mp.preemptoff != ""`: 現在のMがプリエンプションを明示的に無効にしているかどうかをチェックします。`preemptoff` フィールドが空文字列でなければ、プリエンプションが無効になっています。

これらの条件のいずれかが真である場合、`gcAssistAlloc` 関数はすぐに `return` し、GCアシスト作業をスキップします。これにより、非プリエンプティブなコンテキストでのGCアシストの実行が防止されます。

重要な点として、アシストがスキップされた場合でも、その割り当てによって発生した「アシスト債務」は引き続き計上されます。この債務は、後でプリエンプティブなコンテキストで実行される別のアシストによって支払われることになります。コミットメッセージが述べているように、非プリエンプティブなコンテキストからの割り当ては稀であるため、この遅延がGCメカニズム全体に大きな悪影響を与えることはないと判断されています。

## コアとなるコードの解説

追加されたコードブロックは、`gcAssistAlloc` 関数の実行開始直後に、現在の実行コンテキストがGCアシストに適しているかどうかを判断します。

1.  `if getg() == gp.m.g0 { return }`
    *   `getg()`: 現在実行中のゴルーチン (`g`) へのポインタを返します。
    *   `gp.m.g0`: 現在のP (Processor) に関連付けられたM (Machine) のシステムゴルーチン (`g0`) へのポインタです。`g0` はランタイムの内部処理やシステムコールに使用される特別なゴルーチンで、プリエンプトされません。
    *   この行は、もし現在のゴルーチンがシステムゴルーチン (`g0`) であれば、GCアシストを実行せずに即座に `gcAssistAlloc` 関数を終了します。

2.  `if mp := getg().m; mp.locks > 0 || mp.preemptoff != "" { return }`
    *   `mp := getg().m`: 現在のゴルーチンが実行されているM (Machine) へのポインタを取得し、`mp` に代入します。MはOSのスレッドに相当し、P (Processor) 上でゴルーチンを実行します。
    *   `mp.locks > 0`: 現在のMがランタイム内部のロックを保持しているかどうかをチェックします。`locks` フィールドは、Mが保持しているロックの数を表します。ロックを保持している間は、デリケートな操作中であり、プリエンプションやGCアシストのような割り込みは避けるべきです。
    *   `mp.preemptoff != ""`: 現在のMがプリエンプションを明示的に無効にしているかどうかをチェックします。`preemptoff` フィールドは、プリエンプションが無効になっている理由を示す文字列を保持します。このフィールドが空文字列でなければ、プリエンプションは無効になっています。
    *   この行は、もし現在のMがロックを保持しているか、またはプリエンプションが明示的に無効になっている場合、GCアシストを実行せずに即座に `gcAssistAlloc` 関数を終了します。

これらのチェックにより、Goランタイムは、その内部で最もクリティカルで脆弱なコンテキストにおいて、GCアシストによる予期せぬ中断や問題発生を防ぐことができます。これにより、ランタイムの安定性が向上し、将来のGCメカニズムの変更（特に `yield` やブロックを伴うもの）との互換性が確保されます。

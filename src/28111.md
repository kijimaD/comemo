## 変更の背景

Goランタイムは、効率的なメモリ管理とガベージコレクション（GC）を実現するために、オペレーティングシステム（OS）からメモリを確保する際に特定の要件を満たす必要があります。`sysAlloc` 関数は、GoのヒープアリーナのためにOSから生のメモリを割り当てる低レベルなメカニズムです。この関数が返すポインタが常に特定の境界（ページサイズ）にアラインされていることは、ランタイムの他の部分、特にガベージコレクタやアロケータが正しく機能するために極めて重要です。

このコミットの背景には、`sysAlloc` の重要な特性である「常にアラインされたポインタを返す」という事実が、コードベース内で明示的に文書化されていなかったという点があります。この特性は、Goランタイムのメモリモデルの基盤であり、その保証を明確にすることで、将来のメンテナンスや他の開発者がコードを理解する際の助けとなります。`[dev.garbage]` というプレフィックスは、この変更がガベージコレクションやメモリ管理の領域における開発の一環であることを示唆しています。

## 前提知識の解説

### メモリのアラインメント (Memory Alignment)

メモリのアラインメントとは、コンピュータのメモリ上でデータが特定のメモリアドレスの倍数に配置されることを指します。例えば、4バイトのデータ型が4バイト境界にアラインされている場合、そのデータはアドレス0、4、8、12...といったアドレスに配置されます。

*   **なぜ重要か**:
    *   **パフォーマンス**: 多くのCPUは、アラインされたデータへのアクセスを、アラインされていないデータへのアクセスよりも高速に処理できます。アラインされていないアクセスは、追加のCPUサイクルを必要としたり、複数のメモリアクセスに分割されたりする可能性があります。
    *   **ハードウェア要件**: 一部のハードウェア（特に特定の命令セットやDMAコントローラ）は、特定のデータ型が特定の境界にアラインされていることを要求します。アラインされていないアクセスは、ハードウェア例外を引き起こす可能性があります。
    *   **アトミック操作**: マルチスレッド環境でのアトミック操作（不可分操作）は、通常、データが適切にアラインされていることを前提としています。

### Goランタイムのメモリ管理と `sysAlloc`

Goランタイムは、独自のメモリ管理システムを持っています。これは、OSから大きなメモリブロックを要求し、それをGoプログラムが使用する小さなチャンクに分割して管理します。

*   **ヒープアリーナ (Heap Arena)**: Goのヒープは、`mheap` 構造体によって管理され、`arena` と呼ばれる大きなメモリ領域に分割されます。`sysAlloc` は、このヒープアリーナのためにOSから物理メモリを確保する役割を担います。
*   **`sysAlloc` の役割**: `sysAlloc` は、GoランタイムがOSに対してメモリを要求する最も低レベルなインターフェースの一つです。これは、OSのシステムコール（例: Linuxの `mmap`）をラップし、指定されたサイズのメモリブロックを確保します。
*   **`_PageSize`**: OSはメモリをページ単位で管理します。`_PageSize` は、OSがメモリを管理する最小単位であり、通常は4KB（4096バイト）です。`sysAlloc` が返すポインタが `_PageSize` にアラインされているということは、OSから受け取ったメモリブロックの開始アドレスがページの境界に正確に位置していることを意味します。これは、仮想メモリ管理やキャッシュ効率の観点から重要です。
*   **`arena_start` と `arena_end`**: `mheap` 構造体内の `arena_start` と `arena_end` は、Goランタイムが現在管理しているヒープアリーナの開始アドレスと終了アドレスを示します。`sysAlloc` によって確保されたメモリは、この範囲内に収まる必要があります。
*   **対応する解放関数がない**: `sysAlloc` はOSからメモリを確保しますが、対応する `sysFree` のような直接的な解放関数は存在しません。これは、Goランタイムが一度OSから確保したメモリを、自身のメモリ管理システム内で再利用することを基本としているためです。OSへのメモリ返却は、より高レベルな `sysUnmap` などによって行われるか、プロセス終了時にOSによって自動的に解放されます。

## 技術的詳細

このコミットは、`src/runtime/malloc.go` ファイル内の `sysAlloc` 関数にコメントを追加することで、その動作仕様を明確にしています。追加されたコメントは、以下の重要な技術的詳細を保証します。

1.  **アラインメントの保証**: `sysAlloc` が返すポインタは、常に `_PageSize` (OSのページサイズ、通常4KB) にアラインされています。これは、GoランタイムがOSからメモリを取得する際に、ページ境界に正確に位置するアドレスを要求していることを意味します。このアラインメントは、仮想メモリ管理、キャッシュ効率、および特定のハードウェア要件を満たす上で不可欠です。
2.  **ヒープアリーナ内での位置**: 割り当てられたメモリは、`mheap` 構造体の `h.arena_start` と `h.arena_end` の間に位置します。これは、`sysAlloc` がGoランタイムの管理下にあるヒープ領域のためにメモリを確保していることを明確にします。
3.  **失敗時の挙動**: `sysAlloc` は、メモリ確保に失敗した場合に `nil` を返します。これは、呼び出し元がエラーハンドリングを行うための明確な契約を提供します。
4.  **解放関数の不在**: `sysAlloc` には、直接対応する解放関数が存在しません。これは、GoランタイムがOSから一度確保したメモリを、自身のメモリ管理システム（ガベージコレクタなど）を通じて再利用・管理するという設計思想を反映しています。OSへのメモリ返却は、より大きな単位で行われるか、プロセス終了時に行われます。

これらのドキュメントは、`sysAlloc` の低レベルな動作を正確に記述し、Goランタイムのメモリ管理の堅牢性と予測可能性を高める上で重要な役割を果たします。

## コアとなるコードの解説

変更は `src/runtime/malloc.go` ファイルの `sysAlloc` 関数に新しいコメントブロックを追加するものです。

追加されたコメントは以下の通りです。

```go
// sysAlloc allocates the next n bytes from the heap arena. The
// returned pointer is always _PageSize aligned and between
// h.arena_start and h.arena_end. sysAlloc returns nil on failure.
// There is no corresponding free function.
```

このコメントは、`sysAlloc` 関数の以下の重要な特性を明確に記述しています。

*   **`sysAlloc` の目的**: 「ヒープアリーナから次の `n` バイトを割り当てる」と明記されており、この関数がGoランタイムのヒープ管理のためのメモリ確保を行うことを示しています。
*   **ポインタのアラインメント**: 「返されるポインタは常に `_PageSize` にアラインされている」という記述は、この関数がOSから取得するメモリブロックの開始アドレスが、OSのページサイズ（通常4KB）の倍数であることを保証します。これは、メモリの効率的なアクセスと管理のために不可欠です。
*   **メモリ範囲**: 「`h.arena_start` と `h.arena_end` の間にある」という記述は、割り当てられたメモリが `mheap` 構造体によって管理されるヒープアリーナの範囲内にあることを示しています。
*   **エラーハンドリング**: 「失敗時には `nil` を返す」と明記されており、呼び出し元がメモリ確保の失敗を適切に処理できることを示唆しています。

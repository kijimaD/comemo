# [インデックス 26411] ファイルの概要

このコミットは、Goの標準ライブラリである`net/http`パッケージ内のHTTP/2実装（`h2_bundle.go`）を更新し、ヘッダー値の検証ロジックを強化するとともに、`x/net/http2/hpack`パッケージを`vendor`ディレクトリから`internal`ディレクトリへ移動させる変更を含んでいます。これにより、HTTP/2ヘッダーのセキュリティと堅牢性が向上し、Go 1.6における依存関係の管理方法が調整されました。

## 変更の背景

このコミットには主に二つの背景があります。

1.  **HTTP/2ヘッダーのセキュリティと堅牢性の向上**: HTTP/2プロトコルでは、ヘッダーフィールドの名前と値に特定の制約があります。これらの制約に違反する不正なヘッダーは、攻撃者によって悪用される可能性があり、プロトコルスタックの脆弱性につながることがあります。特に、CR (Carriage Return)、LF (Line Feed)、NUL (Null Character) などの制御文字がヘッダー値に含まれると、HTTPレスポンス分割攻撃などのセキュリティ問題を引き起こす可能性があります。このコミットは、これらの潜在的な脆弱性に対処するため、ヘッダーの検証ロジックを強化することを目的としています。これは、`#13961`で報告された問題に対応しています。

2.  **Go 1.6における依存関係管理の調整**: Go 1.5で導入された`vendor`ディレクトリのサポートは、外部依存関係をプロジェクト内に含めるための実験的な機能でした。しかし、Go 1.6のリリースに向けて、`vendor`ディレクトリの扱いに関していくつかの課題が浮上しました。特に、標準ライブラリが`vendor`ディレクトリ内のパッケージに依存することの複雑さや、ビルドシステムとの整合性の問題がありました。このコミットでは、`net/http`パッケージが依存していた`golang.org/x/net/http2/hpack`パッケージを一時的に`vendor`から`internal`ディレクトリに移動させることで、Go 1.6のリリースにおける依存関係管理の問題（`#14029`および`#14047`）を回避しています。`internal`パッケージは、そのパッケージを含むモジュール内からのみインポート可能であり、外部からの直接的な依存を防ぐためのメカニズムです。

## 前提知識の解説

### HTTP/2プロトコルとヘッダー

HTTP/2は、HTTP/1.xのセマンティクスを維持しつつ、パフォーマンスと効率を向上させるために設計されたプロトコルです。HTTP/2では、ヘッダーはHPACK圧縮アルゴリズムを使用して効率的にエンコードされます。ヘッダーフィールドの名前と値には、RFC 7230およびHTTP/2の仕様によって厳格なルールが定められています。

*   **ヘッダーフィールド名 (field-name)**: RFC 7230では`token`として定義されており、特定のASCII文字セット（`!`、`#`、`$`、`%`、`&`、`'`、`*`、`+`、`-`、`.`、`^`、`_`、```、`|`、`~`、および英数字）のみが許可されます。HTTP/2では、ヘッダーフィールド名はエンコード前に小文字に変換される必要があります。
*   **ヘッダーフィールド値 (field-value)**: RFC 7230では`field-vchar`または`obs-text`として定義されています。`field-vchar`は可視ASCII文字（VCHAR）を指し、`obs-text`は`%x80-FF`の範囲のオクテット（非ASCII文字）を指します。しかし、HTTP/2の仕様では、CR (0x0d)、LF (0x0a)、NUL (0x00) の文字はヘッダー値に含めることを明示的に禁止しており、これらを含むリクエストやレスポンスは不正なものとして扱われるべきです。

### Goのパッケージ管理と`vendor`/`internal`ディレクトリ

*   **`vendor`ディレクトリ**: Go 1.5で導入された実験的な機能で、プロジェクトの依存関係をプロジェクトルートの`vendor`ディレクトリ内に配置することを可能にしました。これにより、各プロジェクトが独自の依存関係のコピーを持つことができ、依存関係の競合を防ぎ、ビルドの再現性を高めることが期待されました。しかし、Go 1.6の時点では、標準ライブラリが`vendor`内のパッケージに依存することの複雑さから、一時的にその使用が制限されました。
*   **`internal`ディレクトリ**: Go 1.4で導入された機能で、`internal`ディレクトリ内のパッケージは、その`internal`ディレクトリを含む親ディレクトリのパッケージからのみインポートできます。例えば、`a/b/internal/c`というパッケージは`a/b`内のパッケージからのみインポート可能で、`a/d`や`a/b/x`からはインポートできません。これは、ライブラリの内部実装の詳細を外部に公開しないためのメカニズムとして機能します。

### `golang.org/x/net/http2/hpack`パッケージ

このパッケージは、HTTP/2プロトコルで使用されるHPACKヘッダー圧縮アルゴリズムの実装を提供します。Goの標準ライブラリである`net/http`パッケージのHTTP/2実装は、この外部パッケージに依存していました。

## 技術的詳細

このコミットの技術的詳細は以下の通りです。

1.  **HPACKパッケージの移動**:
    *   `src/vendor/golang.org/x/net/http2/hpack`以下のファイル群が`src/internal/golang.org/x/net/http2/hpack`に移動されました。
    *   これにより、`net/http`パッケージは`internal`パッケージとして`hpack`をインポートするようになります。
    *   `src/go/build/deps_test.go`内の依存関係リストもこれに合わせて更新されました。
    *   `src/go/build/build_test.go`内の`TestImportVendor`テストは、この変更により一時的にスキップされるようになりました。これは、`hpack`が`internal`に移動したため、`vendor`のテストが現状に合わなくなったためです。
    *   `src/vendor/README`が追加され、`vendor`ディレクトリの存在理由とGo 1.7での再利用の可能性、および関連するissue (`#14047`) が説明されています。

2.  **HTTP/2ヘッダー検証の強化**:
    *   既存の汎用的な`http2validHeader`関数が削除され、より具体的な`http2validHeaderFieldName`と`http2validHeaderFieldValue`の2つの関数が導入されました。
    *   `http2validHeaderFieldName`関数は、ヘッダーフィールド名がRFC 7230の`token`ルールに準拠しているか、およびHTTP/2の要件（大文字が含まれていないこと）を満たしているかをチェックします。このチェックを効率化するために、`http2isTokenTable`というブール値の配列が導入され、ASCII文字のトークン性を高速に判定できるようになりました。
    *   `http2validHeaderFieldValue`関数は、ヘッダーフィールド値にCR (0x0d)、LF (0x0a)、NUL (0x00) といった不正な文字が含まれていないかをチェックします。これは、HTTP/2の仕様でこれらの文字が禁止されているためです。
    *   これらの新しい検証関数は、`http2serverConn`の`onNewHeaderField`および`onNewTrailerField`メソッド、そして`http2clientConnReadLoop`の`checkHeaderField`メソッド内で使用されるようになりました。これにより、受信したHTTP/2ヘッダーがプロトコル仕様に厳密に準拠しているかどうかが検証され、不正なヘッダーが検出された場合には適切なエラー（`http2errInvalidHeaderFieldName`、`http2errInvalidHeaderFieldValue`）が返されるようになりました。
    *   以前存在した`http2errInvalidHeaderKey`エラーは、より具体的なエラーに置き換えられたため削除されました。

## コアとなるコードの解説

### `src/net/http/h2_bundle.go` の変更点

1.  **インポートパスの変更**:
    *   `"golang.org/x/net/http2/hpack"` から `"internal/golang.org/x/net/http2/hpack"` への変更は、`hpack`パッケージがGoの標準ライブラリの内部実装の一部として扱われるようになったことを示します。これにより、外部からの直接的な依存を防ぎ、Go 1.6のリリースにおける依存関係管理の課題に対処しています。

2.  **新しいエラー変数の導入**:
    *   `http2errInvalidHeaderFieldName` と `http2errInvalidHeaderFieldValue` は、それぞれ不正なヘッダーフィールド名と不正なヘッダーフィールド値が検出された際に使用される具体的なエラーメッセージを提供します。これにより、エラーの原因がより明確になります。

3.  **ヘッダー検証関数の分割と強化**:
    *   `http2validHeader(v string) bool` 関数は削除され、その機能は `http2validHeaderFieldName` と `http2validHeaderFieldValue` の2つの関数に分割されました。
    *   `http2validHeaderFieldName` は、ヘッダーフィールド名がRFC 7230の`token`の定義に合致し、かつHTTP/2の要件である「小文字であること」を満たしているかを厳密にチェックします。`http2isTokenTable`というルックアップテーブルを使用することで、このチェックが効率的に行われます。大文字のASCII文字が検出された場合も不正と判断されます。
    *   `http2validHeaderFieldValue` は、ヘッダーフィールド値にHTTP/2で禁止されているCR (0x0d)、LF (0x0a)、NUL (0x00) の文字が含まれていないかをチェックします。これにより、HTTPレスポンス分割攻撃などのセキュリティ脆弱性を防ぎます。コメントには、SP (Space) や HTAB (Horizontal Tab) で始まる/終わる文字列の拒否はまだ適切に処理されていないことが明記されており、今後の改善の余地が示唆されています。

4.  **ヘッダー処理ロジックの更新**:
    *   `onNewHeaderField`、`onNewTrailerField`、`checkHeaderField`といったヘッダーを処理するメソッド内で、新しい検証関数が呼び出されるようになりました。
    *   例えば、`onNewHeaderField`では、まずヘッダー値が`http2validHeaderFieldValue`で検証され、次にヘッダー名が`http2validHeaderFieldName`で検証されます。これにより、ヘッダーの各要素がプロトコル仕様に準拠していることが保証されます。
    *   以前の`http2errInvalidHeaderKey`エラーは削除され、より具体的な`http2errInvalidHeaderFieldName`または`http2errInvalidHeaderFieldValue`が使用されるようになりました。

### `src/go/build/deps_test.go` の変更点

*   `pkgDeps`マップ内の`net/http`の依存関係リストにおいて、`"golang.org/x/net/http2/hpack"`が`"internal/golang.org/x/net/http2/hpack"`に変更されました。これは、ビルドシステムが`hpack`パッケージを新しい`internal`パスで認識するようにするための調整です。

### `src/vendor/README` の新規追加

*   このREADMEファイルは、`vendor`ディレクトリが空のままだとGitが追跡できないため、ダミーとして存在する必要があることを説明しています。また、Go 1.6では`vendor`の使用が一時的に制限されたが、Go 1.7では再び使用される予定であること、そして関連する議論が`golang.org/issue/14047`にあることを示しています。これは、Goのパッケージ管理戦略が進化している途中の状況を反映しています。

## 変更の背景

このコミットは、Goコンパイラにおけるエイリアシング解析の不正確さに起因するバグを修正するために導入されました。具体的には、以前のコミット (20907) が `varexpr` というコンパイラ内部の関数を修正した際に、副作用として `aliased` 関数における構造体フィールドのエイリアシング検出ロジックを破壊してしまいました。

コミット 20907 の変更後、構造体のフィールド（例: `s.f`）への参照が、それ自身とエイリアスしていると正しく認識されなくなりました。これは、コンパイラが特定の最適化を行う際に、変数の値が他の操作によって変更される可能性があるかどうかを判断する上で重要な情報です。エイリアシングが正しく検出されないと、コンパイラは誤った最適化を適用し、結果としてプログラムの動作が不正になる可能性があります。

この問題は、Go issue #15042 として報告されました。このイシューでは、構造体の2つのフィールドを交換するような操作（例: `s1.i, s2.i = s2.i, s1.i`）がコンパイラによって誤って処理され、期待される結果が得られないというバグが示されています。このコミットは、この特定のバグを修正することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラの内部構造、特にエイリアシング解析と中間表現に関するいくつかの概念を理解する必要があります。

*   **Goコンパイラ (cmd/compile)**: Go言語のソースコードを機械語に変換するツールです。最適化フェーズを含み、プログラムの実行効率を高めます。
*   **エイリアシング解析 (Aliasing Analysis)**: コンパイラ最適化の重要な部分であり、異なるポインタや変数参照が同じメモリ位置を指す可能性があるかどうかを判断するプロセスです。エイリアシングが存在する場合、コンパイラは特定の最適化（例えば、レジスタ割り当てや命令の並べ替え）を適用する際に慎重になる必要があります。エイリアシングを誤って判断すると、プログラムのセマンティクスが変更され、バグが発生する可能性があります。
*   **`*Node`**: Goコンパイラがプログラムの抽象構文木 (AST) を表現するために使用するデータ構造です。プログラムの各要素（変数、式、文など）は `Node` として表現されます。
*   **`ODOT`**: `Node` の `Op` フィールドが `ODOT` の場合、それは構造体フィールドへのアクセス（例: `s.f`）を表します。`n.Left` は構造体自体を、`n.Right` はフィールド名を指します。
*   **`ONAME`**: `Node` の `Op` フィールドが `ONAME` の場合、それは変数名を表します。
*   **`aliased` 関数**: コンパイラ内部の関数で、ある式 `n` が、特定のリスト `all` 内の他の式によってエイリアスされているかどうかを判断します。これは、主に変数のライブネス解析や最適化の安全性チェックに使用されます。
*   **`varexpr` 関数**: コンパイラ内部の関数で、ある式が「変数式」であるかどうかを判断します。変数式とは、メモリ上の場所を指す式（例: 変数、ポインタの逆参照、構造体フィールド）を指します。
*   **コミット 20907**: このコミットの元となった変更で、`varexpr` 関数のロジックを修正しました。この修正自体は正しかったものの、`aliased` 関数の動作に意図しない影響を与えました。

## 技術的詳細

このコミットの核心は、Goコンパイラの `src/cmd/compile/internal/gc/walk.go` ファイル内の `aliased` 関数と `varexpr` 関数の相互作用にあります。

以前のコミット 20907 は `varexpr` を修正しましたが、その結果 `aliased` 関数が構造体フィールドのエイリアシングを正しく扱えなくなりました。具体的には、`s.f` のような構造体フィールドへの参照が、それ自身とエイリアスしていると見なされなくなりました。

この問題が発生する前の状態では、`aliased` 関数は構造体のすべてのフィールドが「すべて」とエイリアスしていると見なす、より大雑把なロジックを持っていました。これは安全ではあるものの、過度に保守的であり、より積極的な最適化を妨げる可能性がありました。コミット 20907 はこの過度な保守性を改善しようとしましたが、その過程で `s.f` が `s.f` とエイリアスしないという誤った状態を作り出してしまいました。

このコミットは、この問題を修正するために `aliased` 関数に一時的な解決策を導入します。その解決策とは、「構造体のフィールドへのすべての参照を、その構造体全体のエイリアスとして扱う」というものです。

具体的には、`aliased` 関数内で `n.Op == ODOT` である限り `n = n.Left` を繰り返すループが追加されました。これにより、`s.f` のような式が最終的に構造体 `s` 自体を指すように変換されます。同様に、`all` リスト内の要素を処理する際にも、`a.Op == ODOT` である限り `a = a.Left` を繰り返すループが追加されます。これにより、比較対象の式も構造体自体に「昇格」されます。

このアプローチは、`s.f` が `s.f` とエイリアスしていることを保証しますが、`s.f` が `s.g` (同じ構造体の別のフィールド) とエイリアスしていると見なすという、より保守的な判断も行います。これは厳密には不正確です（異なるフィールドは通常エイリアスしません）が、現在の問題に対する「シンプルな修正」として導入されました。コミットメッセージにもあるように、「より良い修正には、特定のフィールドも追跡する必要がある」と認識されており、これは将来的な改善の余地を残しています。

また、`varexpr` 関数からは `ODOT` のケースが削除され、もし `varexpr` が `ODOT` を受け取った場合は `Fatalf` でコンパイラを異常終了させるようになりました。これは、`ODOT` のエイリアシング処理が `aliased` 関数内で完結するようになったため、`varexpr` が `ODOT` を処理する必要がなくなったことを示唆しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/walk.go` の変更点

1.  **`aliased` 関数内の `n` の処理**:
    ```go
    	for n.Op == ODOT {
    		n = n.Left
    	}
    ```
    このループは、`aliased` 関数に渡された `Node` `n` が構造体フィールドアクセス (`ODOT`) である場合、そのアクセスを遡って、最終的に構造体変数自体 (`s` in `s.f`) を指すように `n` を更新します。これにより、`s.f` は `s` とエイリアスしていると見なされるようになります。

2.  **`aliased` 関数内の `a` の処理**:
    ```go
    		for a.Op == ODOT {
    			a = a.Left
    		}
    ```
    これは上記と同様のロジックで、`all` リスト内の各要素 `an` から抽出された `Node` `a` に対しても適用されます。これにより、比較対象となる両方の式が、構造体フィールドアクセスではなく、構造体変数自体として扱われるようになります。この変更により、`s.f` と `s.g` のような異なるフィールドへのアクセスも、両方とも `s` とエイリアスしていると見なされるため、より保守的なエイリアシング判断が行われます。

3.  **`varexpr` 関数内の `ODOT` の削除**:
    ```go
    	case ODOT: // but not ODOTPTR
    		// Should have been handled in aliased.
    		Fatalf("varexpr unexpected ODOT")
    ```
    `varexpr` 関数から `ODOT` のケースが削除され、もしこのケースに到達した場合はコンパイラがパニックを起こすようになりました。これは、構造体フィールドのエイリアシングに関する処理が `aliased` 関数に一元化されたため、`varexpr` が `ODOT` を直接処理する必要がなくなったことを示しています。もし `varexpr` が `ODOT` を受け取った場合、それはコンパイラの内部ロジックの矛盾を示すため、`Fatalf` で早期に問題を検出するように変更されました。

### `test/fixedbugs/issue15042.go` の追加

この新しいテストファイルは、このコミットが修正する特定のバグを再現し、修正が正しく機能することを確認するためのものです。

```go
package main

type S struct {
	i int
}

func F(c bool, s1, s2 S) (int, int) {
	if c {
		s1.i, s2.i = s2.i, s1.i
	}
	return s1.i, s2.i
}

func main() {
	i, j := F(true, S{1}, S{20})
	if i != 20 || j != 1 {
		panic(i+j)
	}
}
```

このテストコードでは、`S` 型の構造体が定義され、`F` 関数内で2つの `S` 型のインスタンス `s1` と `s2` のフィールド `i` の値を交換しています。エイリアシング解析が正しく行われないと、コンパイラはこの交換操作を最適化の過程で誤って処理し、結果として `i` と `j` の値が期待通りにならない可能性がありました。テストは、`i` が `20`、`j` が `1` になることをアサートしており、これが満たされない場合はパニックを起こします。このテストの追加により、将来的に同様の回帰バグが発生するのを防ぐことができます。

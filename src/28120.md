# [インデックス 28120] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるメモリ解放数の計上ロジックのバグを修正するものです。具体的には、`sweep`フェーズでの`nfree`（解放されたオブジェクト数）の解釈変更に伴う`c.local_nsmallfree`への誤った加算と、`mallocgc`における`s.allocCount`の初期化不足を修正しています。これにより、GCの統計が正確になり、`TestArrayHash`のようなテストが失敗する問題が解決されます。

## 変更の背景

このコミットの背景には、Goランタイムのガベージコレクション（GC）におけるメモリ管理の統計情報の不正確さがありました。以前のコミット `8dda1c4` で、GCの`sweep`（スイープ）フェーズ中に使用される変数`nfree`の意味が変更されました。元々`nfree`は「新しく解放されたオブジェクトの数」を意味していましたが、この変更により「スパン内の合計の空きオブジェクト数」を指すようになりました。

しかし、この`nfree`の意味変更にもかかわらず、`sweep`フェーズが`c.local_nsmallfree`（ローカルな小さなオブジェクトの解放数）に`nfree`を加算するロジックは更新されませんでした。結果として、`c.local_nsmallfree`は実際の「新しく解放されたオブジェクト数」ではなく、「スパン内の合計の空きオブジェクト数」を誤って加算し続けることになり、メモリ解放数が過剰に計上されるというバグが発生しました。

この過剰計上は、GCの動作に影響を与え、特に`TestArrayHash`のようなテストケースで「too many allocs NNN - hash not balanced」というエラーを引き起こしていました。これは、GCがメモリ使用状況を正確に把握できていないために、ハッシュテーブルのバランスが崩れるなどの問題が発生したことを示唆しています。

この問題を解決するため、`c.local_nsmallfree`には「新しく解放されたオブジェクト数」のみが加算されるようにロジックを修正する必要がありました。また、この修正には、`mallocgc`関数が大きなオブジェクトを割り当てる際に`s.allocCount`を適切に初期化していないという、関連する別の問題も浮上しました。`s.allocCount`が正しく設定されていないと、`sweep`フェーズが混乱し、正確な「新しく解放されたオブジェクト数」を計算できなくなるため、この点も同時に修正されることになりました。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理とガベージコレクションに関するいくつかの基本的な概念を知っておく必要があります。

1.  **Goランタイムのガベージコレクション (GC)**: GoのGCは、プログラムが不要になったメモリを自動的に解放する仕組みです。GoのGCは、主に「三色マーク＆スイープ」アルゴリズムに基づいており、並行（concurrent）に動作することで、アプリケーションの実行を長時間停止させる「Stop-The-World (STW)」ポーズを最小限に抑えるように設計されています。GCは、マークフェーズで到達可能なオブジェクトを識別し、スイープフェーズで到達不能なオブジェクトが占めるメモリを解放します。

2.  **mspan**: `mspan`は、Goランタイムのメモリ管理における基本的な単位です。これは、連続したメモリページ（通常は8KB）のブロックであり、特定のサイズクラスのオブジェクトを格納します。Goランタイムは、`mheap`から`mspan`を割り当て、`mcentral`および`mcache`構造を通じてこれらを管理します。

3.  **mcache**: `mcache`は、各プロセッサ（P）にローカルに割り当てられるキャッシュです。これにより、グローバルなロックなしで効率的なメモリ割り当てが可能になります。小さなオブジェクトの割り当ては、通常、対応する`mcache`から直接行われます。

4.  **mcentral**: `mcentral`は、特定のサイズクラスの`mspan`を管理する中央のリストです。`mcache`が`mspan`を使い果たした場合、`mcentral`から新しい`mspan`を取得します。

5.  **sweep (スイープ)**: GCの主要なフェーズの一つで、マークフェーズの後に実行されます。スイープフェーズでは、GCは`mspan`を走査し、マークされなかった（つまり、到達不能な）オブジェクトが占めるメモリを再利用可能にします。`mspan.sweep`関数は、個々のヒープスパンをスイープする役割を担います。もし`mspan`内に生きているオブジェクトが一つもなければ、その`mspan`全体がヒープに返却されます。

6.  **nfree**: スイープフェーズ中に、`mspan`内で解放されたオブジェクトの数を指す変数です。このコミットの背景にある問題は、この`nfree`の定義が変更されたにもかかわらず、その利用箇所が更新されなかったことにあります。

7.  **allocCount (s.allocCount)**: `mspan`構造体内のフィールドで、そのスパン内で現在割り当てられているオブジェクトの数を追跡します。これは、GCがスパンの利用状況を把握し、新しく解放されたオブジェクト数を計算するために重要な情報です。

8.  **c.local_nsmallfree**: `mcache`（`c`）内の統計情報の一つで、その`mcache`が管理する小さなオブジェクトの解放数をローカルに計上するために使用されます。この値は、GCの効率性やメモリ使用状況を評価するための重要な指標となります。

## 技術的詳細

このコミットは、Goランタイムのメモリ管理における2つの主要なコンポーネント、`mallocgc`（メモリ割り当て）と`mgcsweep`（ガベージコレクションのスイープフェーズ）にわたる修正です。

問題の核心は、コミット`8dda1c4`によって`mgcsweep.go`内の`sweep`関数における`nfree`変数の意味が変更されたことにあります。以前は「新しく解放されたオブジェクトの数」を意味していた`nfree`が、「スパン内の合計の空きオブジェクト数」を意味するように変わりました。しかし、この変更後も`c.local_nsmallfree`への加算は`nfree`をそのまま使用していたため、実際の解放数よりも多くの値が計上されていました。

この過剰計上は、`TestArrayHash`のようなテストで「too many allocs NNN - hash not balanced」というエラーを引き起こしていました。これは、GCの統計が不正確であるために、メモリ割り当てのバランスが崩れているとシステムが誤認していたことを示しています。

修正は以下の2つの側面から行われました。

1.  **`mgcsweep.go`における`nfreed`の導入と`c.local_nsmallfree`の更新**:
    *   `sweep`関数内で、まず`nalloc`（現在割り当てられているオブジェクト数）を`s.nelems`（スパン内の要素総数）から`nfree`（スパン内の合計空きオブジェクト数）を引くことで計算します。
    *   次に、`nfreed`（新しく解放されたオブジェクト数）を、以前の`s.allocCount`（前回のGCサイクルで割り当てられていたオブジェクト数）から現在の`nalloc`を引くことで計算します。この`nfreed`こそが、`c.local_nsmallfree`に加算されるべき真の「新しく解放されたオブジェクト数」です。
    *   `s.allocCount`は、現在の`nalloc`で更新されます。
    *   `c.local_nsmallfree[cl]`には、`nfreed`が加算されるように変更されました。これにより、正確な解放数が計上されるようになります。
    *   また、`nalloc > s.allocCount`という異常な状態（スイープ中に割り当て数が増加する）を検出した場合に`throw`するチェックが追加され、ランタイムの堅牢性が向上しました。

2.  **`malloc.go`における`s.allocCount`の初期化**:
    *   `mallocgc`関数内で、大きなオブジェクト（large object）が`largeAlloc`によって割り当てられる際に、`s.allocCount`が適切に初期化されていませんでした。これにより、`sweep`フェーズが`s.allocCount`の古い値に依存して`nfreed`を計算しようとした際に、誤った結果を導く可能性がありました。
    *   この修正では、`largeAlloc`の呼び出し後、`s.allocCount`を`1`に設定することで、大きなオブジェクトに対しても`allocCount`が正しく初期化されるようにしました。大きなオブジェクトは通常、スパン全体を占めるため、`allocCount`を`1`とすることで、そのスパンに1つの大きなオブジェクトが割り当てられていることを正確に反映します。

これらの変更により、GCの統計情報が正確になり、`TestArrayHash`のようなテストが正しく動作するようになりました。

## コアとなるコードの解説

### `src/runtime/malloc.go`の変更

`mallocgc`関数は、Goプログラムがメモリを要求したときに、そのメモリを割り当てる役割を担います。この変更は、特に大きなオブジェクト（`largeAlloc`によって割り当てられるもの）の処理に関するものです。

*   `s.allocCount = 1`: `largeAlloc`が呼び出された後、`mspan` `s`の`allocCount`が`1`に設定されます。これは、大きなオブジェクトが割り当てられたスパンには、通常1つの大きなオブジェクトが格納されるため、そのスパンに1つのオブジェクトが割り当てられていることを正確に反映するための修正です。以前は、この`allocCount`が設定されていなかったため、`sweep`フェーズで`nfreed`を計算する際に誤った情報が使用される可能性がありました。

### `src/runtime/mgcsweep.go`の変更

`mgcsweep.go`内の`sweep`関数は、ガベージコレクションのスイープフェーズで個々の`mspan`を処理します。この変更は、メモリ解放数の計上ロジックの核心部分です。

*   `nalloc := uint16(s.nelems) - uint16(nfree)`:
    *   `s.nelems`は、`mspan`が保持できる要素の総数です。
    *   `nfree`は、このコミットの背景で説明したように、スパン内の「合計の空きオブジェクト数」を意味します。
    *   この行では、`s.nelems`から`nfree`を引くことで、現在スパン内に「割り当てられているオブジェクトの数」(`nalloc`)を計算しています。

*   `nfreed := s.allocCount - nalloc`:
    *   `s.allocCount`は、前回のGCサイクル終了時にこのスパンに割り当てられていたオブジェクトの数です。
    *   `nalloc`は、今回のスイープフェーズで計算された、現在割り当てられているオブジェクトの数です。
    *   この差分を取ることで、「今回のGCサイクルで新しく解放されたオブジェクトの数」(`nfreed`)を正確に計算しています。これが、`c.local_nsmallfree`に加算されるべき真の値です。

*   `if nalloc > s.allocCount { ... throw("sweep increased allocation count") }`:
    *   これは、デバッグと堅牢性のためのチェックです。スイープフェーズ中に割り当てられているオブジェクトの数(`nalloc`)が、前回の`allocCount`よりも増えることは通常ありえません。もしそのような状況が発生した場合、それはランタイムの内部状態に深刻な矛盾があることを示唆するため、`throw`（パニック）を発生させて問題を早期に検出します。

*   `s.allocCount = nalloc`:
    *   `mspan`の`allocCount`を、今回のスイープフェーズで計算された現在の割り当てオブジェクト数`nalloc`で更新します。これにより、次回のGCサイクルで`nfreed`を計算する際の基準が正しくなります。

*   `c.local_nsmallfree[cl] += uintptr(nfreed)`:
    *   これが最も重要な修正点です。以前は`nfree`（合計空きオブジェクト数）が加算されていましたが、この変更により、正確に計算された`nfreed`（新しく解放されたオブジェクト数）が`c.local_nsmallfree`に加算されるようになりました。これにより、GCの統計情報が正確になり、メモリ解放数の過剰計上が解消されます。`cl`は、オブジェクトのサイズクラス（class）を表します。

これらの変更により、Goランタイムはメモリの解放状況をより正確に追跡できるようになり、GCの動作の信頼性と正確性が向上しました。

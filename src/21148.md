# [インデックス 21148] ファイルの概要

このコミットでは、Goランタイムが持つ、`noptrdata`、`data`、`bss`、`noptrbss`といったメモリセクションが連続しており、特定の順序で配置されているという仮定が削除されました。この変更は、特に外部リンカを使用した場合に、これらのセクションの順序が保証されない、あるいは非Goセクションが挿入される可能性があるという問題に対処するためのものです。

変更されたファイルは以下の通りです。

-   `src/run.bash`: レース検出器のテストスクリプト
-   `src/runtime/malloc.go`: Goランタイムのメモリ割り当てとガベージコレクション関連のコード
-   `src/runtime/race.c`: Goレース検出器のC言語部分

## 元コミット内容

Goランタイムは、`noptrdata`、`data`、`bss`、`noptrbss`といったメモリセクションが順序通りに連続して配置されているという仮定を持っていました。しかし、外部リンカを使用する場合、この仮定が破られる可能性がありました。外部リンカはこれらのセクションを再配置したり、Go以外のセクションをそれらの間に挿入したりすることがあります。コミットの作者は、GoのデータセクションとBSSセクションを強制的に隣接させる方法を模索しましたが、Go以外のオブジェクトからのデータやBSSが存在する場合、それらがGoのセクション間に割り込む可能性が高いことが判明しました。

このコミットでは、この仮定に依存していた2つの箇所を書き換えることで対処しています。`noptrdata`を検索して、他に同様の仮定をしている箇所がないか確認されました。

この変更なしでは、追加されたレース検出器のテスト（`os/exec`パッケージを外部リンカモードで実行）が、無効なポインタ参照でクラッシュすることが確認されました。

このコミットは、Issue #9133 を修正します。

## 変更の背景

Goプログラムは、コンパイル時に様々なメモリセクションに分割されます。これには、ポインタを含まない初期化済みデータ (`noptrdata`)、ポインタを含む初期化済みデータ (`data`)、初期化されていないデータ (`bss`)、ポインタを含まない初期化されていないデータ (`noptrbss`) などが含まれます。Goランタイムは、これらのセクションが特定の順序でメモリ上に連続して配置されているという内部的な仮定を持っていました。この仮定は、例えば、あるアドレスがGoの静的データ領域内にあるかどうかを効率的にチェックするために利用されていました。

しかし、Goプログラムを外部リンカ（例えばGCCなど）と組み合わせてビルドする場合、リンカはGoランタイムが期待するセクションの順序や連続性を保証しません。外部リンカは、Goのセクションの間にC言語のライブラリや他のオブジェクトファイルのセクションを挿入したり、Goのセクション自体の順序を変更したりする可能性があります。これにより、Goランタイムが持つ「セクションは連続している」という仮定が破られ、不正なメモリアクセスやクラッシュ（特にレース検出器のようなメモリの健全性を厳密にチェックするツールを使用した場合）が発生する可能性がありました。

この問題は、GoのIssue #9133で報告されており、特に`os/exec`パッケージのようなCgoを使用するプログラムで、外部リンカが関与する場合に顕著でした。このコミットは、この根本的な仮定の不一致を解消し、Goランタイムが外部リンカによって生成されたバイナリでも正しく動作するようにするために行われました。

## 前提知識の解説

### メモリセクション (`.data`, `.bss`, etc.)

プログラムの実行可能ファイルは、異なる種類のデータを格納するために複数のセクションに分割されます。主要なセクションは以下の通りです。

-   **`.text` (コードセクション)**: 実行可能な機械語コードが格納されます。
-   **`.rodata` (読み取り専用データセクション)**: 定数や文字列リテラルなど、実行中に変更されないデータが格納されます。
-   **`.data` (初期化済みデータセクション)**: プログラムの開始時に初期値を持つグローバル変数や静的変数が格納されます。これらは書き込み可能です。
-   **`.bss` (初期化されていないデータセクション)**: プログラムの開始時にゼロで初期化されるグローバル変数や静的変数が格納されます。これらは書き込み可能です。`.data`セクションとは異なり、実行ファイル内には実際のデータは含まれず、サイズ情報のみが格納されます。
-   **Go特有のセクション**:
    -   `noptrdata`: ポインタを含まない初期化済みデータ。ガベージコレクタがスキャンする必要がないため、GCの効率化に寄与します。
    -   `noptrbss`: ポインタを含まない初期化されていないデータ。同様にGCの対象外です。

### 外部リンカ (External Linker)

Goコンパイラは、Goのコードをオブジェクトファイルにコンパイルします。通常、Goは独自の内部リンカを使用してこれらのオブジェクトファイルをリンクし、実行可能ファイルを生成します。しかし、Cgo（GoとC言語の相互運用機能）を使用する場合や、特定のビルド設定では、システムにインストールされている外部リンカ（例: `ld`、GCCのリンカ）を使用することがあります。

外部リンカは、Goの内部リンカとは異なるセクションの配置戦略や最適化を行うため、Goランタイムが期待するメモリレイアウト（特にセクションの順序や連続性）が保証されないことがあります。これが、このコミットで修正される問題の根源です。

### Goランタイムのメモリ管理とガベージコレクション (GC)

Goランタイムは、独自のメモリ管理システムとガベージコレクタを持っています。ガベージコレクタは、ヒープ上のオブジェクトをスキャンして到達可能なオブジェクトを特定し、到達不能なオブジェクトを解放します。このスキャンプロセスでは、プログラムの静的データ領域（`.data`や`.bss`など）に存在するポインタも考慮に入れる必要があります。

`runtime.SetFinalizer`関数は、オブジェクトがガベージコレクションによって解放される直前に実行される関数を設定するために使用されます。この関数は、引数として渡されたポインタがGoの管理するメモリブロック内にあるかどうかを検証する必要があります。この検証の一部として、静的データ領域内のポインタであるかどうかのチェックが行われます。

### レース検出器 (Race Detector)

Goのレース検出器は、並行プログラムにおけるデータ競合（複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みである場合に発生するバグ）を検出するためのツールです。レース検出器は、メモリへのアクセスを監視し、不正なアクセスパターンを特定します。この監視プロセスでは、有効なメモリ領域（ヒープ、スタック、静的データ領域など）を正確に識別する必要があります。もし、静的データ領域の範囲が誤って認識されると、レース検出器は誤った競合を報告したり、逆に実際の競合を見逃したり、最悪の場合クラッシュしたりする可能性があります。

## 技術的詳細

このコミットの核心は、Goランタイムが静的データセクション（`noptrdata`, `data`, `bss`, `noptrbss`）がメモリ上で連続しており、特定の順序で配置されているという仮定を削除することです。以前は、これらのセクション全体を単一の連続したブロックとして扱い、その開始アドレスと終了アドレスを使ってポインタの有効性をチェックしていました。

具体的には、以下の2つの主要な箇所で変更が行われました。

1.  **`src/runtime/malloc.go` の `SetFinalizer` 関数内のチェック**:
    `SetFinalizer`関数は、引数として渡されたオブジェクトのポインタがGoの管理するメモリブロック内にあることを確認します。以前は、このチェックが静的データセクションの連続性を仮定していました。
    ```go
    // The segments are, in order: text, rodata, noptrdata, data, bss, noptrbss.
    if uintptr(unsafe.Pointer(&noptrdata)) <= uintptr(e.data) && uintptr(e.data) < uintptr(unsafe.Pointer(&enoptrbss)) {
        return
    }
    ```
    このコードは、`e.data`（ファイナライザを設定しようとしているオブジェクトのポインタ）が`noptrdata`の開始から`enoptrbss`の終了までの連続した範囲内にあるかどうかをチェックしていました。この仮定が外部リンカによって破られると、正当なポインタであってもこのチェックを通過できなくなり、`gothrow("runtime.SetFinalizer: pointer not in allocated block")`によってパニックが発生する可能性がありました。

2.  **`src/runtime/race.c` の `isvalidaddr` 関数と `runtime·raceinit` 関数**:
    レース検出器のC言語部分では、メモリへのアクセスが有効なアドレス範囲内にあるかどうかをチェックする`isvalidaddr`関数と、レース検出器の初期化を行う`runtime·raceinit`関数が、同様に静的データセクションの連続性を仮定していました。
    -   `isvalidaddr`関数は、与えられたアドレスが有効なメモリ領域（ヒープまたは静的データ領域）内にあるかを判断します。以前は、静的データ領域を`noptrdata`から`enoptrbss`までの単一の連続したブロックとして扱っていました。
    -   `runtime·raceinit`関数は、レース検出器が監視する静的データ領域の範囲を決定するために、これらのセクションの開始と終了アドレスを使用していました。

これらの変更は、各セクション（`noptrdata`, `data`, `bss`, `noptrbss`）の開始と終了アドレスを個別に取得し、それぞれが独立した範囲として扱われるようにすることで、外部リンカによるセクションの再配置や非Goセクションの挿入に対応しています。これにより、Goランタイムはより堅牢になり、外部リンカを使用するビルド環境でも安定して動作するようになります。

## コアとなるコードの解説

### `src/runtime/malloc.go` の変更

-   **新しいリンカ提供変数の追加**:
    `var enoptrdata struct{}` と `var noptrbss struct{}` が追加されました。これらは、それぞれ`noptrdata`セクションの終了アドレスと`noptrbss`セクションの開始アドレスをリンカが提供することを期待するものです。以前は`noptrdata`から`enoptrbss`までが連続していると仮定していたため、`enoptrdata`と`noptrbss`の個別の開始/終了アドレスは必要ありませんでした。
-   **`SetFinalizer` 関数内のポインタチェックの修正**:
    以前のコードでは、`e.data`が`noptrdata`から`enoptrbss`までの単一の連続した範囲内にあるかどうかをチェックしていました。
    新しいコードでは、このチェックが4つの独立した条件のOR結合に置き換えられました。
    ```go
    if uintptr(unsafe.Pointer(&noptrdata)) <= uintptr(e.data) && uintptr(e.data) < uintptr(unsafe.Pointer(&enoptrdata)) ||
       uintptr(unsafe.Pointer(&data)) <= uintptr(e.data) && uintptr(e.data) < uintptr(unsafe.Pointer(&edata)) ||
       uintptr(unsafe.Pointer(&bss)) <= uintptr(e.data) && uintptr(e.data) < uintptr(unsafe.Pointer(&ebss)) ||
       uintptr(unsafe.Pointer(&noptrbss)) <= uintptr(e.data) && uintptr(e.data) < uintptr(unsafe.Pointer(&enoptrbss)) {
        return
    }
    ```
    これにより、`e.data`が`noptrdata`、`data`、`bss`、`noptrbss`のいずれかのセクション内に存在すれば、そのポインタが有効な静的データ領域内にあると判断されるようになりました。各セクションがメモリ上で連続している必要はなく、また互いに隣接している必要もなくなりました。これは、外部リンカがセクションを再配置したり、間に他のセクションを挿入したりする可能性に対応するための重要な変更です。

### `src/runtime/race.c` の変更

-   **新しいリンカ提供変数の宣言**:
    `extern byte runtime·enoptrdata[];`、`extern byte runtime·data[];`、`extern byte runtime·edata[];`、`extern byte runtime·bss[];`、`extern byte runtime·ebss[];`、`extern byte runtime·noptrbss[];` が追加されました。これらは、Goの各静的データセクションの開始と終了アドレスをC言語側から参照できるようにするためのものです。
-   **`isvalidaddr` 関数内のアドレスチェックの修正**:
    以前は、`addr`が`runtime·noptrdata`から`runtime·enoptrbss`までの単一の連続した範囲内にあるかをチェックしていました。
    新しいコードでは、`malloc.go`と同様に、各セクションの範囲を個別にチェックするようになりました。
    ```c
    if(addr >= (uintptr)runtime·noptrdata && addr < (uintptr)runtime·enoptrdata)
        return true;
    if(addr >= (uintptr)runtime·data && addr < (uintptr)runtime·edata)
        return true;
    if(addr >= (uintptr)runtime·bss && addr < (uintptr)runtime·ebss)
        return true;
    if(addr >= (uintptr)runtime·noptrbss && addr < (uintptr)runtime·enoptrbss)
        return true;
    ```
    これにより、レース検出器は、外部リンカによってセクションが非連続に配置された場合でも、Goの静的データ領域を正しく識別できるようになります。
-   **`runtime·raceinit` 関数内の静的データ領域範囲の計算修正**:
    この関数は、レース検出器が監視する静的データ領域の全体的な範囲を決定します。以前は、`noptrdata`の開始から`enoptrbss`の終了までを連続したブロックとして扱っていました。
    新しいコードでは、すべての関連する静的データセクション（`noptrdata`, `data`, `bss`, `noptrbss`）の開始アドレスの中で最小のものと、終了アドレスの中で最大のものを見つけることで、より保守的な（つまり、すべてのGoの静的データを含む）範囲を計算するようになりました。
    ```c
    start = ~(uintptr)0; // 最大値で初期化
    end = 0;            // 最小値で初期化

    // 各セクションの開始アドレスの中で最小値を見つける
    if(start > (uintptr)runtime·noptrdata)
        start = (uintptr)runtime·noptrdata;
    if(start > (uintptr)runtime·data)
        start = (uintptr)runtime·data;
    if(start > (uintptr)runtime·noptrbss)
        start = (uintptr)runtime·noptrbss;
    if(start > (uintptr)runtime·bss)
        start = (uintptr)runtime·bss;

    // 各セクションの終了アドレスの中で最大値を見つける
    if(end < (uintptr)runtime·enoptrdata)
        end = (uintptr)runtime·enoptrdata;
    if(end < (uintptr)runtime·edata)
        end = (uintptr)runtime·edata;
    if(end < (uintptr)runtime·enoptrbss)
        end = (uintptr)runtime·enoptrbss;
    if(end < (uintptr)runtime·ebss)
        end = (uintptr)runtime·ebss;

    start = start & ~(PageSize-1); // ページ境界にアライン
    size = ROUND(end - start, PageSize); // ページサイズに丸める
    ```
    この変更により、外部リンカがセクションをどのように配置しても、レース検出器はGoの静的データ領域全体を確実にカバーできるようになります。

### `src/run.bash` の変更

-   **レース検出器テストの追加**:
    `go test -race -i runtime/race flag os/exec` と `go test -race -short flag os/exec` に `os/exec` パッケージが追加されました。
    さらに、`go test -race -short -ldflags=-linkmode=external flag os/exec` という新しいテストが追加されました。
    この新しいテストは、`os/exec` パッケージを**外部リンカモード** (`-ldflags=-linkmode=external`) でビルドし、レース検出器でテストします。コミットメッセージにもあるように、このテストは変更なしではクラッシュするため、このコミットの修正が正しく機能することを確認するための重要な検証ステップとなります。

これらの変更は全体として、Goランタイムが外部リンカによって生成されたバイナリのメモリレイアウトに対してより堅牢になるように設計されており、特にレース検出器のようなメモリの健全性に依存するツールが正しく機能することを保証します。

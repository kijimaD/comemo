# [インデックス 25435] ファイルの概要

このコミットは、Goツールチェーンにおいて、`linux/arm64`アーキテクチャ向けに`-buildmode=shared`および関連するフラグのサポートを有効にするものです。これにより、GoプログラムをLinux上のARM64環境で共有ライブラリとしてビルドする機能が拡張されます。

## 変更の背景

Go言語は、その強力な静的リンク機能により、単一のバイナリで依存関係をすべて含んだ実行ファイルを生成することが一般的です。しかし、特定のシナリオ、特に大規模なシステムやプラグインアーキテクチャ、あるいは他の言語との連携においては、共有ライブラリ（ダイナミックリンクライブラリ）の形式でコードを提供する必要が生じます。

Go 1.5で導入された`-buildmode=shared`は、Goパッケージを共有ライブラリとしてビルドするための機能です。これにより、複数のGoプログラムが同じ共有ライブラリにリンクすることで、個々の実行ファイルのサイズを削減し、メモリ使用量を最適化できる可能性があります。また、Goのコードを他のGoプログラムから動的にロードするような高度な利用ケースも想定されていました。

このコミット以前は、`linux/arm64`アーキテクチャでは`-buildmode=shared`がサポートされていませんでした。ARM64アーキテクチャは、Raspberry Piのような組み込みシステムから、データセンターのサーバーまで、その電力効率の高さから利用が拡大していました。そのため、`linux/arm64`環境でGoの共有ライブラリ機能を利用したいというニーズが高まっていました。この変更は、Goのクロスプラットフォームサポートを強化し、特にARM64ベースのシステムにおけるGoの柔軟性と適用範囲を広げることを目的としています。

## 前提知識の解説

### 1. Goのビルドモード (`-buildmode`)

Goツールチェーンの`go build`コマンドには、`-buildmode`というフラグがあり、Goプログラムのビルド方法を制御します。主なビルドモードには以下のものがあります。

*   **`exe` (デフォルト)**: 実行可能なバイナリを生成します。Goのデフォルトであり、すべての依存関係が静的にリンクされます。
*   **`archive`**: 静的ライブラリ（`.a`ファイル）を生成します。C/C++プログラムなどからGoのコードをリンクする際に使用されます。
*   **`c-archive`**: C言語から呼び出し可能な静的ライブラリを生成します。
*   **`c-shared`**: C言語から呼び出し可能な共有ライブラリ（`.so`ファイル on Linux/macOS, `.dll`ファイル on Windows）を生成します。これは、Goのコードを他の言語のアプリケーションに組み込む際によく使われます。
*   **`shared`**: GoのパッケージをGoの共有ライブラリ（`.so`ファイル）としてビルドします。これは、他のGoプログラムが動的にリンクすることを想定しています。このモードは、GoのABI（Application Binary Interface）の安定性の問題から、Go-to-Goの動的リンクには課題が多く、`c-shared`ほど一般的ではありません。

### 2. `linux/arm64`アーキテクチャ

*   **`linux`**: オペレーティングシステムがLinuxであることを指します。
*   **`arm64` (AArch64)**: 64ビットのARMプロセッサアーキテクチャを指します。従来の32ビットARM（`arm`）と比較して、より大きなメモリアドレス空間と高性能な命令セットを提供します。スマートフォン、タブレット、組み込みシステム、そして近年ではサーバーやデスクトップPCでも採用が進んでいます。

### 3. PIC (Position-Independent Code)

共有ライブラリは、メモリ上の任意のアドレスにロードされる可能性があるため、そのコードは位置独立である必要があります。つまり、コード内のアドレス参照が、ロードされるベースアドレスに依存しないように記述されている必要があります。これを**位置独立コード (Position-Independent Code, PIC)** と呼びます。Goコンパイラは、共有ライブラリをビルドする際にPICを生成する必要があります。

### 4. 動的リンクと静的リンク

*   **静的リンク**: プログラムのビルド時に、必要なライブラリのコードがすべて実行ファイルにコピーされます。結果として生成される実行ファイルは大きくなりますが、外部ライブラリに依存しないため、配布が容易で、実行環境にライブラリが存在しないことによる問題が発生しにくいという利点があります。Goのデフォルトのビルド方法です。
*   **動的リンク**: プログラムのビルド時には、ライブラリへの参照のみが実行ファイルに含まれ、実際のライブラリコードは実行時にOSによってメモリにロードされます。これにより、複数のプログラムが同じライブラリを共有できるため、ディスク容量とメモリ使用量を節約できます。しかし、実行環境に適切なバージョンのライブラリが存在しないとプログラムが起動しない（「DLL地獄」などと呼ばれる問題）可能性があります。

## 技術的詳細

このコミットは、Goツールチェーンの複数のコンポーネントにわたる変更を通じて、`linux/arm64`での`-buildmode=shared`のサポートを有効にしています。

1.  **`cmd/compile/internal/gc/lex.go`**:
    *   Goコンパイラのフロントエンド部分で、`Thearch.Thechar`というアーキテクチャ識別子に基づいて、特定のフラグの有効/無効を制御しています。
    *   変更前は、`Thearch.Thechar == '5' || Thearch.Thechar == '6' || Thearch.Thechar == '8' || Thearch.Thechar == '9'`という条件で`flag_dynlink`（動的リンクをサポートするためのフラグ）が有効になっていました。ここで、`'5'`はARM32、`'6'`はAMD64、`'8'`は386、`'9'`はPPC64を指します。
    *   変更後、`switch`文が導入され、`'7'`（ARM64を指す）がこのリストに追加されました。これにより、`linux/arm64`アーキテクチャでも`flag_dynlink`が有効になり、コンパイラが動的リンクに必要なコード生成を認識するようになります。

2.  **`src/cmd/go/build.go`**:
    *   `go`コマンドのビルドロジックを定義するファイルです。特に`buildModeInit()`関数は、`-buildmode`フラグの処理と、それに応じたコンパイラ/アセンブラへの引数（`codegenArg`, `buildAsmflags`）の設定を行います。
    *   `buildmode=shared`が指定された場合、`platform`（`GOOS/GOARCH`の組み合わせ）が`"linux/386"`, `"linux/amd64"`, `"linux/arm"`のいずれかである場合にのみ、`buildAsmflags`に`-D=shared=1`が追加されていました。
    *   この変更により、`"linux/arm64"`がこのリストに追加されました。これにより、`go build -buildmode=shared`コマンドが`linux/arm64`ターゲットで実行された際に、アセンブラに`shared`ビルドモードであることを伝えるフラグが正しく渡されるようになります。これは、アセンブラが共有ライブラリに適したコード（例えばPIC）を生成するために重要です。

3.  **`src/cmd/link/internal/arm64/obj.go`**:
    *   GoリンカのARM64アーキテクチャ固有のオブジェクトファイル処理ロジックです。
    *   `archinit()`関数内で、リンカのモード設定が行われています。
    *   変更前は、`ld.Buildmode == ld.BuildmodeCShared`（C言語から呼び出し可能な共有ライブラリモード）の場合にのみ、`ld.Linkmode`が`ld.LinkExternal`（外部リンカを使用するモード）に設定されていました。
    *   変更後、`ld.DynlinkingGo()`という新しい条件が追加されました。これは、Goの共有ライブラリとして動的リンクを行う場合に`true`を返す関数です。つまり、`buildmode=shared`の場合にも`ld.LinkExternal`が設定されるようになり、Goの共有ライブラリをビルドする際に外部リンカが適切に利用されるようになります。

4.  **`src/cmd/link/internal/ld/lib.go`**:
    *   Goリンカの一般的なライブラリ処理とビルドモードの検証ロジックです。
    *   `BuildMode`型の`Set`メソッド内で、`-buildmode=shared`が指定された際のプラットフォームチェックが行われていました。
    *   変更前は、`goos != "linux" || (goarch != "386" && goarch != "amd64" && goarch != "arm")`という条件で、`linux`以外のOS、または`386`, `amd64`, `arm`以外のアーキテクチャではエラーを返していました。
    *   この変更により、`goarch != "arm64"`が条件に追加され、`linux/arm64`が`-buildmode=shared`のサポート対象として明示的に許可されるようになりました。

これらの変更は、コンパイラ、`go`コマンド、リンカの各段階で`linux/arm64`が共有ライブラリビルドの対象として認識され、必要な処理が実行されるように調整するものです。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/lex.go` の変更

この変更は、Goコンパイラが動的リンクをサポートするための内部フラグ`flag_dynlink`を、ARM64アーキテクチャ（`Thearch.Thechar == '7'`）でも有効にするものです。`Thearch.Thechar`は、GoコンパイラがターゲットとするCPUアーキテクチャを識別するための内部的な文字コードです。`'7'`がARM64に対応することで、コンパイラはARM64向けに動的リンクに必要なシンボル解決やコード生成の準備を行うことができます。

### `src/cmd/go/build.go` の変更

`go build -buildmode=shared`コマンドが実行された際に、`linux/arm64`プラットフォームでもアセンブラに`-D=shared=1`というフラグを渡すように変更されています。このフラグは、アセンブラが共有ライブラリに適したコード（例えば、位置独立コード (PIC)）を生成するために使用されます。これにより、生成されるオブジェクトファイルが共有ライブラリとして正しく機能するための基盤が整います。

### `src/cmd/link/internal/arm64/obj.go` の変更

ARM64リンカの初期化処理において、`ld.DynlinkingGo()`という条件が追加されました。これは、Goの共有ライブラリとして動的リンクを行う場合に`true`を返す内部関数です。この条件が`true`の場合、`ld.Linkmode`が`ld.LinkExternal`に設定されます。`ld.LinkExternal`は、Goリンカが外部のシステムリンカ（例: `gcc`）を呼び出して最終的な共有ライブラリを生成することを意味します。これにより、Goの共有ライブラリがシステムレベルで正しくリンクされるようになります。

### `src/cmd/link/internal/ld/lib.go` の変更

`-buildmode=shared`フラグが指定された際のプラットフォーム検証ロジックに`goarch != "arm64"`が追加されました。これは、`go build -buildmode=shared`コマンドが`linux/arm64`ターゲットで実行された際に、リンカがこのビルドモードをサポート対象として認識し、エラーを返さずに処理を進めることを保証します。この変更がなければ、`linux/arm64`で`-buildmode=shared`を使用しようとすると、リンカが「サポートされていないプラットフォーム」としてエラーを返してしまうでしょう。

これらの変更は、Goツールチェーン全体で`linux/arm64`を`-buildmode=shared`のサポート対象として統合し、GoプログラムがARM64 Linux環境で共有ライブラリとしてビルドおよび利用できるようにするための重要なステップです。

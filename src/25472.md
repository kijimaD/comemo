# [インデックス 25472] ファイルの概要

このコミットは、Goランタイムのスケジューラにおいて、プロセッサ（P）のローカル実行キュー（`p.runq`）の型を`[]*g`（goroutineへのポインタのスライス）から`[]guintptr`（`uintptr`型のスライス）に変更するものです。この変更の主な目的は、スケジューラコード内の不要なライトバリアを排除し、将来のガベージコレクタ（GC）の変更に備えることです。GCがライトバリアを伴わないコンテキストで実行キュー関数を呼び出す必要が生じるため、この変更は不可欠となります。

## 変更の背景

このコミットの主要な背景は、Goランタイムのガベージコレクタ（GC）の進化と、それに伴うスケジューラの効率化です。

GoのGCは、プログラムの実行と並行して動作するコンカレントGCを採用しています。コンカレントGCの正確性を保証するためには、「ライトバリア（Write Barrier）」というメカニズムが不可欠です。ライトバリアは、ヒープ上のポインタが変更される際に実行されるコードスニペットであり、GCがオブジェクトグラフの変更を追跡し、誤って到達可能なオブジェクトを回収してしまうことを防ぎます。

しかし、ライトバリアはオーバーヘッドを伴います。特に、Goスケジューラの核心部分である`p.runq`（ローカル実行キュー）のような頻繁にアクセスされ、ポインタの読み書きが行われるデータ構造において、ライトバリアが頻繁に発生すると、スケジューラのパフォーマンスに悪影響を及ぼす可能性があります。

コミットメッセージには、「ガベージコレクタがライトバリアを伴わないコンテキストで実行キュー関数を呼び出す必要が生じる将来の変更」に備える、と明記されています。これは、GC自体が実行キューを操作するようなシナリオ（例えば、GCが特定のゴルーチンを一時停止・再開する際など）において、GCの内部処理がライトバリアによって中断されたり、デッドロックを引き起こしたりする可能性を排除する必要があることを示唆しています。

この問題を解決するため、`p.runq`に格納されるゴルーチンへのポインタ`*g`を、GCの監視対象とならない`guintptr`型に変換することで、不要なライトバリアの発生を抑制し、スケジューラの効率を向上させるとともに、将来のGCの変更に対する互換性を確保することが目的です。

## 前提知識の解説

### Goランタイムのスケジューラ (G-M-Pモデル)

Goのスケジューラは、G-M-Pモデルと呼ばれる独自の設計を採用しています。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。OSのスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行できます。
*   **M (Machine/OS Thread)**: オペレーティングシステムのスレッドです。Goプログラムは、M上でGを実行します。MはOSによって管理されます。
*   **P (Processor)**: 論理プロセッサまたはコンテキストです。MがGを実行するために必要なリソース（スケジューラの状態、メモリ割り当てのキャッシュなど）を提供します。`GOMAXPROCS`環境変数によってPの数が制御され、通常はCPUコア数に設定されます。

各Pは、実行可能なゴルーチンを保持するためのローカル実行キュー（`p.runq`）を持っています。MはPにアタッチされ、そのPの`p.runq`からゴルーチンを取り出して実行します。Pのローカルキューが空になった場合、Mはグローバル実行キューや他のPのローカルキューからゴルーチンを「ワークスチール」してきます。

### ライトバリア (Write Barriers)

ライトバリアは、コンカレントガベージコレクタの正確性を保証するために導入されるメカニズムです。GoのGCは、プログラムが実行中にヒープをスキャンし、到達可能なオブジェクトをマークします。このマークフェーズ中に、プログラム（ミューテータ）がポインタを書き換えることでオブジェクトグラフが変更されると、GCがオブジェクトの到達可能性を誤って判断する可能性があります。

ライトバリアは、ポインタの書き込み操作が行われる直前または直後に介入し、GCに対してその変更を通知します。これにより、GCはオブジェクトグラフの最新の状態を把握し、誤った回収を防ぐことができます。GoのGCは、トリコロールマーク＆スイープアルゴリズムに基づいており、ライトバリアはオブジェクトを「グレー」にマークする役割を担うことが多いです。

ライトバリアは、GCの正確性には不可欠ですが、その実行にはCPUサイクルを消費するため、パフォーマンスオーバーヘッドの原因となることがあります。

### ポインタと `uintptr`

*   **ポインタ (`*T`)**: Goにおけるポインタは、メモリ上の特定のアドレスを指し示す変数です。`*g`は`g`型の構造体へのポインタを意味します。GoのGCは、ポインタ型の変数を追跡し、それが指すオブジェクトの到達可能性を判断します。
*   **`uintptr`**: `uintptr`は、ポインタを保持できるだけの大きさを持つ符号なし整数型です。`uintptr`型の変数は、メモリアドレスを数値として扱うことができますが、Goの型システム上はポインタ型とは見なされません。このため、`uintptr`に格納されたアドレスは、GCによって直接追跡されるポインタとしては扱われません。つまり、`uintptr`への書き込みは、通常、ライトバリアの対象外となります。

この特性を利用することで、GCの追跡が不要な、あるいはGCの追跡が望ましくないコンテキストでポインタ値を扱う際に、ライトバリアのオーバーヘッドを回避することができます。ただし、`uintptr`をポインタとして使用する際には、プログラマが手動で型変換を行う必要があり、GCの安全性に関する責任もプログラマが負うことになります。

### `*g` と `guintptr`

*   `*g`: ゴルーチン構造体`g`へのポインタです。これはGCの追跡対象であり、`*g`型の変数への書き込みはライトバリアをトリガーする可能性があります。
*   `guintptr`: Goランタイム内部で定義されている型で、実体は`uintptr`です。この型は、ゴルーチンへのポインタをライトバリアなしで格納するために使用されます。`guintptr`は、`g`へのポインタと相互に変換するためのメソッド（`ptr()`や`set()`など）を持つことが期待されます。

## 技術的詳細

このコミットの核心は、`p`構造体内の`runq`フィールドの型定義を`[256]*g`から`[256]guintptr`に変更することです。

変更前:
```go
type p struct {
    // ...
    runqhead uint32
    runqtail uint32
    runq     [256]*g // goroutineへのポインタのスライス
    // ...
}
```

変更後:
```go
type p struct {
    // ...
    runqhead uint32
    runqtail uint32
    runq     [256]guintptr // uintptr型のスライス
    // ...
}
```

この変更により、`p.runq`にゴルーチンを格納する際や、`p.runq`からゴルーチンを取り出す際に、直接`*g`ポインタを操作するのではなく、`guintptr`を介してポインタ値を数値として扱うようになります。

具体的には、以下の操作でライトバリアが回避されます。

1.  **ゴルーチンの格納 (`runqputslow`関数内)**:
    以前は`_p_.runq[...] = gp`のように直接`*g`ポインタを代入していましたが、変更後は`_p_.runq[...].set(gp)`のように`guintptr`の`set`メソッドを呼び出します。`set`メソッドは`*g`ポインタを`uintptr`に変換して格納するため、この操作はGCによってポインタの書き込みとは見なされず、ライトバリアがトリガーされません。

2.  **ゴルーチンの取り出し (`procresize`, `runqget`, `runqputslow`, `runqsteal`関数内)**:
    以前は`gp := p.runq[...]`のように直接`*g`ポインタを取得していましたが、変更後は`gp := p.runq[...].ptr()`のように`guintptr`の`ptr`メソッドを呼び出します。`ptr`メソッドは`uintptr`値を`*g`ポインタに変換して返すため、GCは関与しません。

この変更は、Goスケジューラのパフォーマンスに直接的な影響を与えます。`p.runq`は非常に頻繁にアクセスされるデータ構造であるため、ここでのライトバリアの排除は、スケジューリングのオーバーヘッドを削減し、全体的な実行効率を向上させる効果があります。

また、将来のGCの変更、特にGCがスケジューラの内部状態（実行キューなど）を直接操作する必要がある場合に、ライトバリアが予期せぬ副作用（例えば、GCの停止時間の延長やデッドロック）を引き起こす可能性を排除します。GCがライトバリアなしで安全に実行キューを操作できるようになることで、GCの設計の柔軟性が高まり、さらなる最適化が可能になります。

## コアとなるコードの解説

変更は主に`p`構造体の`runq`フィールドの型定義と、その`runq`を操作する関数群（`procresize`, `runqputslow`, `runqget`, `runqgrab`, `runqsteal`）におけるゴルーチンポインタの取得・設定方法に集中しています。

1.  **`src/runtime/runtime2.go`における`p.runq`の型変更**:
    *   `runq [256]*g` から `runq [256]guintptr` へと変更されています。
    *   これは、`p`構造体のローカル実行キュー`runq`が、直接`*g`（ゴルーチンへのポインタ）を格納するのではなく、`guintptr`（`uintptr`のエイリアス型で、ポインタ値を数値として扱う）を格納するように変更されたことを意味します。これにより、`runq`への書き込み操作がGCのライトバリアの対象外となります。

2.  **`src/runtime/proc.go`における`gp := p.runq[...].ptr()`**:
    *   `procresize`, `runqputslow` (バッチ処理部分), `runqget`, `runqsteal` 関数内で、`p.runq`からゴルーチンを取り出す際に、`gp := p.runq[...].ptr()`という形式に変更されています。
    *   これは、`guintptr`型の要素から、その数値が表すメモリアドレスを`*g`型のポインタに変換して取得していることを示します。`ptr()`メソッドは`guintptr`に定義されており、内部で`uintptr`から`unsafe.Pointer`を介して`*g`への型変換を行っていると考えられます。この変換はGCのライトバリアをトリガーしません。

3.  **`src/runtime/proc.go`における`_p_.runq[...].set(gp)`**:
    *   `runqputslow` 関数内で、ゴルーチンを`p.runq`に格納する際に、`_p_.runq[...].set(gp)`という形式に変更されています。
    *   これは、`*g`型のゴルーチンポインタ`gp`を、`guintptr`型の要素に設定していることを示します。`set()`メソッドは`guintptr`に定義されており、内部で`*g`ポインタを`uintptr`に変換して格納していると考えられます。この操作もGCのライトバリアをトリガーしません。

4.  **`src/runtime/proc.go`における`batch`引数の型変更**:
    *   `runqgrab`関数の引数`batch`の型が `*[256]*g` から `*[256]guintptr` に変更されています。
    *   これは、`runqgrab`関数がゴルーチンをバッチで取得する際に使用する一時的なバッファも、ライトバリアを回避するために`guintptr`型を使用するように変更されたことを示します。
    *   関連して、`batch[batchHead%uint32(len(batch))] = next` の行では、`next`が`guintptr`型であるため、直接代入が行われています。これは`next.ptr()`で`*g`に変換する前の`guintptr`をそのまま格納していることを意味します。

これらの変更により、Goスケジューラのローカル実行キューに対する操作は、GCのライトバリアの監視から外れ、より高速かつ予測可能な動作が期待できるようになります。これは、GCの停止時間を短縮し、全体的なアプリケーションの応答性を向上させる上で重要な最適化です。

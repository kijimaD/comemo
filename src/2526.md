# [インデックス 2526] ファイルの概要

このコミットは、Goコンパイラ（`gc`）の内部におけるエラー報告の改善と、ソースコードの行番号（`lineno`）の管理方法の整理に焦点を当てています。具体的には、`src/cmd/gc/const.c`、`src/cmd/gc/subr.c`、`src/cmd/gc/walk.c`の3つのファイルが変更されています。

*   `src/cmd/gc/const.c`: 定数評価と型変換に関連する処理を扱います。ここでは、型変換のチェックと数値オーバーフロー検出時の行番号設定が修正されています。
*   `src/cmd/gc/subr.c`: コンパイラのサブルーチンやユーティリティ関数が含まれています。`setlineno`関数のロジックが変更され、特定のノードタイプでの行番号設定がより適切に行われるようになりました。
*   `src/cmd/gc/walk.c`: 抽象構文木（AST）の走査（walk）と型チェック、コード生成の前処理を行う主要なファイルです。ここでは、`walk`関数内での行番号設定の共通化と、`OTYPE`（型が式として使用された場合）および`ODOT`（未定義のフィールドアクセス）エラーの報告ロジックが改善されています。

## 変更の背景

このコミットの主な背景は、Goコンパイラが生成するエラーメッセージの品質向上と、コンパイル中の行番号管理の一貫性向上です。

元のコンパイラでは、不正なコードに対するエラーメッセージが不明瞭であったり、正確な行番号を指し示さない場合がありました。コミットメッセージに示されている`x.go`の例は、この問題点を明確に示しています。

```go
package main
var x = string.Split()
```

このコードは、`string`型を直接レシーバとしてメソッド呼び出しを行おうとしていますが、Go言語では`string`はプリミティブ型であり、メソッドを持つことはできません（`strings`パッケージの関数を使用する必要があります）。また、`Split`は`strings`パッケージの関数であり、`string`型に直接`Split`というメソッドは存在しません。

この不正なコードに対して、変更前のコンパイラは以下のようなエラーを出力していました。

```
x.go:2: type string used as expression
x.go:2: undefined DOT Split on string
x.go:3: illegal types for operand: AS
        undefined
```

ここで注目すべきは、`x.go:3`という行番号が示されている点です。しかし、問題のコードは`x.go:2`にあります。これは、コンパイラがエラーを検出した時点での内部的な行番号が正しく更新されていなかったことを示唆しています。また、「illegal types for operand: AS undefined」というメッセージも、具体的な問題点を把握しにくいものでした。

このコミットは、このような状況を改善し、より正確な行番号で、より分かりやすいエラーメッセージを報告できるようにするために行われました。特に、`string.Split()`のような「型が式として使われる」ケースや「未定義のフィールド/メソッドアクセス」のケースで、エラー報告を改善することが目的です。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラ（`gc`）の基本的な動作と、以下の概念について知っておく必要があります。

1.  **Goコンパイラ (`gc`)**: Go言語の公式コンパイラであり、ソースコードを機械語に変換します。コンパイルプロセスは、字句解析、構文解析、抽象構文木（AST）の構築、型チェック、最適化、コード生成などの段階に分かれます。
2.  **抽象構文木 (AST)**: ソースコードの構文構造を木構造で表現したものです。コンパイラはASTを走査（walk）しながら、意味解析（型チェックなど）やコード変換を行います。`Node`はASTの各要素（ノード）を表す構造体です。
3.  **`Node`構造体**: ASTの各ノードは`Node`構造体で表現されます。これには、ノードの種類（`op`フィールド、例: `ONAME`, `OTYPE`, `ODOT`, `OLITERAL`）、関連する型情報（`type`フィールド）、シンボル情報（`sym`フィールド）、そして**ソースコード上の行番号（`lineno`フィールド）**などが含まれます。
4.  **`lineno`**: コンパイラが現在処理しているソースコードの行番号を追跡するためのグローバル変数です。エラーメッセージを正確な位置で報告するために非常に重要です。
5.  **`yyerror`**: Goコンパイラ内でエラーメッセージを報告するために使用される関数です。この関数が呼び出されると、現在の`lineno`の値と指定されたメッセージが出力されます。
6.  **`convlit1`**: `const.c`内で使用される関数で、リテラル値の型変換を処理します。
7.  **`overflow`**: 数値リテラルがその型で表現できる範囲を超えているかどうかをチェックする関数です。
8.  **`setlineno(Node *n)`**: `subr.c`で定義されている関数で、引数として与えられた`Node`の`lineno`を現在のグローバルな`lineno`変数に設定し、以前の`lineno`を返します。これにより、処理中のノードに対応する行番号に一時的に切り替えることができます。
9.  **`walk`関数**: `walk.c`内の主要な関数で、ASTを再帰的に走査し、各ノードに対して適切な処理（型チェック、変換など）を適用します。
10. **`walkdot`関数**: `walk.c`内で、ドット演算子（`.`）によるフィールドアクセスやメソッド呼び出し（例: `object.field`や`object.method()`）を処理する関数です。
11. **`lookdot`関数**: `walkdot`から呼び出され、指定された型に特定のフィールドやメソッドが存在するかどうかを検索します。

## 技術的詳細

このコミットは、主に以下の3つの側面でGoコンパイラの動作を改善しています。

### 1. `setlineno`関数の改善と利用の統一

以前の`setlineno`関数は、`ONAME`（変数名）ノードに対しては行番号を設定しないという特殊なロジックを持っていました。これは、変数名自体が行番号を持つというよりは、その変数が宣言されたり使用されたりする文脈が行番号を持つべきだという考えに基づいていた可能性があります。しかし、この特殊な扱いは、他のノードタイプでの行番号設定との不整合を生み、結果として不正確なエラー報告につながることがありました。

このコミットでは、`setlineno`関数が以下のように変更されました。

*   **`src/cmd/gc/subr.c`**:
    *   `setlineno`関数内で、`ONAME`だけでなく、`OTYPE`（型名）、`OPACK`（パッケージ名）、`OLITERAL`（リテラル値）のノードタイプも行番号設定の対象外とされました。これらのノードは、それ自体がエラーの直接の原因となるよりも、それらを含む式や文がエラーの原因となることが多いため、この変更は理にかなっています。
    *   これにより、`setlineno`はより汎用的な行番号設定ユーティリティとなり、特定のノードタイプでのみ行番号を更新するという、より洗練されたロジックを持つようになりました。

*   **`src/cmd/gc/const.c`**:
    *   `convlit1`関数内の`overflow`呼び出しの直前で、`lno = lineno; lineno = n->lineno;`という手動での行番号設定が、`lno = setlineno(n);`という`setlineno`関数への呼び出しに置き換えられました。これにより、行番号設定のロジックが共通化され、保守性が向上しました。

*   **`src/cmd/gc/walk.c`**:
    *   `walk`関数の冒頭にあった、`ONAME`, `OPACK`, `OTYPE`, `OLITERAL`ノードに対する行番号設定の`switch`文が削除され、代わりに`setlineno(n);`という単一の呼び出しに置き換えられました。これは、`setlineno`関数自体のロジックが改善されたため、`walk`関数内で個別にこれらのノードタイプを処理する必要がなくなったことを意味します。これにより、コードの重複が排除され、`walk`関数の可読性が向上しました。

### 2. `OTYPE`（型が式として使用された場合）のエラー報告の改善

Go言語では、型（例: `string`, `int`）を直接式として使用することはできません。例えば、`var x = string`のようなコードは不正です。以前のコンパイラは、このようなケースで適切なエラーメッセージを報告しないか、あるいは不明瞭なメッセージを報告することがありました。

このコミットでは、`src/cmd/gc/walk.c`の`walk`関数内に`OTYPE`ケースが追加されました。

*   `case OTYPE:`ブロックが追加され、`n->diag`フラグ（既に診断済みかどうかを示すフラグ）がチェックされます。
*   もし診断されていなければ、`n->diag = 1;`を設定し、`yyerror("type %T used as expression", n->type);`という明確なエラーメッセージを報告します。
*   これにより、`var x = string`のようなコードに対して、「type string used as expression」という、より分かりやすいエラーメッセージが正確な行番号で出力されるようになりました。

### 3. `ODOT`（未定義のフィールド/メソッドアクセス）のエラー報告の改善

コミットメッセージの例`string.Split()`のように、存在しないフィールドやメソッドにアクセスしようとした場合、以前のコンパイラは「undefined DOT Split on string」というメッセージを出力していましたが、場合によっては重複してエラーが報告されたり、不正確な行番号が示されたりすることがありました。

このコミットでは、`src/cmd/gc/walk.c`の`walkdot`関数内で、`lookdot`が失敗した場合のエラー報告ロジックが改善されました。

*   `if(!lookdot(n, t))`ブロック内に、`OTYPE`の場合と同様に`n->diag`フラグのチェックが追加されました。
*   もし診断されていなければ、`n->diag = 1;`を設定し、`yyerror("undefined DOT %S on %T", n->right->sym, n->left->type);`というエラーメッセージを報告します。
*   これにより、`string.Split()`のような不正なドットアクセスに対して、エラーが一度だけ、かつ正確な行番号で報告されるようになります。`n->diag`フラグの導入は、同じエラーがコンパイルプロセスの異なる段階で複数回報告されるのを防ぐ役割も果たします。

これらの変更により、Goコンパイラはよりユーザーフレンドリーになり、開発者がコードの誤りを迅速に特定し、修正するのに役立つようになりました。

## コアとなるコードの解説

### `src/cmd/gc/const.c`の変更

*   `convlit1`関数内の`if(cvttype(n->type, t))`が`if(cvttype(n->type, t) == 1)`に変更されました。これは、`cvttype`関数の戻り値がブール値ではなく、特定の整数値（`1`が成功を示す）を返すようになったため、そのAPI変更に合わせた修正です。
*   `overflow`関数呼び出し前の行番号設定が、`lno = setlineno(n);`に統一されました。これにより、`overflow`エラーが発生した際に、より正確なノードの行番号が`lineno`に設定されるようになります。`setlineno`は現在の`lineno`を保存し、ノードの`lineno`をセットして、元の`lineno`を返すため、処理後に`lineno = lno;`で元の値に戻すことができます。

### `src/cmd/gc/subr.c`の変更

*   `setlineno`関数のロジックが`if(n != N && n->op != ONAME)`から、より詳細な`switch`文に変更されました。
*   新しい`switch`文では、`ONAME`, `OTYPE`, `OPACK`, `OLITERAL`の各ノードタイプに対しては`break`（つまり、`lineno`を更新しない）が実行されます。これら以外のノードタイプの場合にのみ、`lineno = n->lineno;`によってグローバルな`lineno`がノードの行番号で更新されます。
*   この変更により、`setlineno`は、エラー報告に直接関連しない特定のノードタイプでは行番号を更新しないという、より洗練された動作をするようになりました。これにより、エラーメッセージが報告されるべき文脈の行番号がより正確に保たれます。

### `src/cmd/gc/walk.c`の変更

*   `walk`関数の冒頭にあった、特定のノードタイプ（`ONAME`, `OPACK`, `OTYPE`, `OLITERAL`）に対する行番号設定の`switch`文が削除され、代わりに`setlineno(n);`という単一の呼び出しに置き換えられました。これは、`setlineno`関数自体のロジックが改善されたため、`walk`関数内でこれらのノードタイプを個別に処理する必要がなくなったためです。これにより、コードの重複が排除され、`walk`関数の可読性が向上しました。
*   `walk`関数内に`case OTYPE:`ブロックが追加されました。これは、型が式として使用された場合にエラーを報告するためのものです。`!n->diag`チェックは、同じエラーが複数回報告されるのを防ぐためのものです。`yyerror("type %T used as expression", n->type);`というメッセージは、この種のエラーに対して非常に明確です。
*   `walkdot`関数内で、`lookdot`が失敗した場合（つまり、未定義のフィールドやメソッドにアクセスしようとした場合）のエラー報告ロジックが改善されました。ここでも`!n->diag`チェックが導入され、`yyerror("undefined DOT %S on %T", n->right->sym, n->left->type);`という明確なエラーメッセージが一度だけ報告されるようになりました。`n->right->sym`はアクセスしようとしたフィールド/メソッドの名前を、`n->left->type`はレシーバの型を示します。

これらの変更は、Goコンパイラがより正確で、重複のない、そして開発者にとって理解しやすいエラーメッセージを生成するための重要なステップです。

このコミットは、このような状況を改善し、より正確な行番号で、より分かりやすいエラーメッセージを報告できるようにするために行われました。特に、`string.Split()`のような「型が式として使われる」ケースや「未定義のフィールド/メソッドアクセス」のケースで、エラー報告を改善することが目的です。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラ（`gc`）の基本的な動作と、以下の概念について知っておく必要があります。

1.  **Goコンパイラ (`gc`)**: Go言語の公式コンパイラであり、ソースコードを機械語に変換します。コンパイルプロセスは、字句解析、構文解析、抽象構文木（AST）の構築、型チェック、最適化、コード生成などの段階に分かれます。
2.  **抽象構文木 (AST)**: ソースコードの構文構造を木構造で表現したものです。コンパイラはASTを走査（walk）しながら、意味解析（型チェックなど）やコード変換を行います。`Node`はASTの各要素（ノード）を表す構造体です。
3.  **`Node`構造体**: ASTの各ノードは`Node`構造体で表現されます。これには、ノードの種類（`op`フィールド、例: `ONAME`, `OTYPE`, `ODOT`, `OLITERAL`）、関連する型情報（`type`フィールド）、シンボル情報（`sym`フィールド）、そして**ソースコード上の行番号（`lineno`フィールド）**などが含まれます。
4.  **`lineno`**: コンパイラが現在処理しているソースコードの行番号を追跡するためのグローバル変数です。エラーメッセージを正確な位置で報告するために非常に重要です。
5.  **`yyerror`**: Goコンパイラ内でエラーメッセージを報告するために使用される関数です。この関数が呼び出されると、現在の`lineno`の値と指定されたメッセージが出力されます。
6.  **`convlit1`**: `const.c`内で使用される関数で、リテラル値の型変換を処理します。
7.  **`overflow`**: 数値リテラルがその型で表現できる範囲を超えているかどうかをチェックする関数です。
8.  **`setlineno(Node *n)`**: `subr.c`で定義されている関数で、引数として与えられた`Node`の`lineno`を現在のグローバルな`lineno`変数に設定し、以前の`lineno`を返します。これにより、処理中のノードに対応する行番号に一時的に切り替えることができます。
9.  **`walk`関数**: `walk.c`内の主要な関数で、ASTを再帰的に走査し、各ノードに対して適切な処理（型チェック、変換など）を適用します。
10. **`walkdot`関数**: `walk.c`内で、ドット演算子（`.`）によるフィールドアクセスやメソッド呼び出し（例: `object.field`や`object.method()`）を処理する関数です。
11. **`lookdot`関数**: `walkdot`から呼び出され、指定された型に特定のフィールドやメソッドが存在するかどうかを検索します。

## 技術的詳細

このコミットは、主に以下の3つの側面でGoコンパイラの動作を改善しています。

### 1. `setlineno`関数の改善と利用の統一

以前の`setlineno`関数は、`ONAME`（変数名）ノードに対しては行番号を設定しないという特殊なロジックを持っていました。これは、変数名自体が行番号を持つというよりは、その変数が宣言されたり使用されたりする文脈が行番号を持つべきだという考えに基づいていた可能性があります。しかし、この特殊な扱いは、他のノードタイプでの行番号設定との不整合を生み、結果として不正確なエラー報告につながることがありました。

このコミットでは、`setlineno`関数が以下のように変更されました。

*   **`src/cmd/gc/subr.c`**:
    *   `setlineno`関数内で、`ONAME`だけでなく、`OTYPE`（型名）、`OPACK`（パッケージ名）、`OLITERAL`（リテラル値）のノードタイプも行番号設定の対象外とされました。これらのノードは、それ自体がエラーの直接の原因となるよりも、それらを含む式や文がエラーの原因となることが多いため、この変更は理にかなっています。
    *   これにより、`setlineno`はより汎用的な行番号設定ユーティリティとなり、特定のノードタイプでのみ行番号を更新するという、より洗練されたロジックを持つようになりました。

*   **`src/cmd/gc/const.c`**:
    *   `convlit1`関数内の`overflow`呼び出しの直前で、`lno = lineno; lineno = n->lineno;`という手動での行番号設定が、`lno = setlineno(n);`という`setlineno`関数への呼び出しに置き換えられました。これにより、行番号設定のロジックが共通化され、保守性が向上しました。

*   **`src/cmd/gc/walk.c`**:
    *   `walk`関数の冒頭にあった、`ONAME`, `OPACK`, `OTYPE`, `OLITERAL`ノードに対する行番号設定の`switch`文が削除され、代わりに`setlineno(n);`という単一の呼び出しに置き換えられました。これは、`setlineno`関数自体のロジックが改善されたため、`walk`関数内で個別にこれらのノードタイプを処理する必要がなくなったことを意味します。これにより、コードの重複が排除され、`walk`関数の可読性が向上しました。

### 2. `OTYPE`（型が式として使用された場合）のエラー報告の改善

Go言語では、型（例: `string`, `int`）を直接式として使用することはできません。例えば、`var x = string`のようなコードは不正です。以前のコンパイラは、このようなケースで適切なエラーメッセージを報告しないか、あるいは不明瞭なメッセージを報告することがありました。

このコミットでは、`src/cmd/gc/walk.c`の`walk`関数内に`OTYPE`ケースが追加されました。

*   `case OTYPE:`ブロックが追加され、`n->diag`フラグ（既に診断済みかどうかを示すフラグ）がチェックされます。
*   もし診断されていなければ、`n->diag = 1;`を設定し、`yyerror("type %T used as expression", n->type);`という明確なエラーメッセージを報告します。
*   これにより、`var x = string`のようなコードに対して、「type string used as expression」という、より分かりやすいエラーメッセージが正確な行番号で出力されるようになりました。

### 3. `ODOT`（未定義のフィールド/メソッドアクセス）のエラー報告の改善

コミットメッセージの例`string.Split()`のように、存在しないフィールドやメソッドにアクセスしようとした場合、以前のコンパイラは「undefined DOT Split on string」というメッセージを出力していましたが、場合によっては重複してエラーが報告されたり、不正確な行番号が示されたりすることがありました。

このコミットでは、`src/cmd/gc/walk.c`の`walkdot`関数内で、`lookdot`が失敗した場合（つまり、未定義のフィールドやメソッドにアクセスしようとした場合）のエラー報告ロジックが改善されました。

*   `if(!lookdot(n, t))`ブロック内に、`OTYPE`の場合と同様に`n->diag`フラグのチェックが追加されました。
*   もし診断されていなければ、`n->diag = 1;`を設定し、`yyerror("undefined DOT %S on %T", n->right->sym, n->left->type);`というエラーメッセージを報告します。
*   これにより、`string.Split()`のような不正なドットアクセスに対して、エラーが一度だけ、かつ正確な行番号で報告されるようになります。`n->diag`フラグの導入は、同じエラーがコンパイルプロセスの異なる段階で複数回報告されるのを防ぐ役割も果たします。

これらの変更により、Goコンパイラはよりユーザーフレンドリーになり、開発者がコードの誤りを迅速に特定し、修正するのに役立つようになりました。

## コアとなるコードの解説

### `src/cmd/gc/const.c`の変更

*   `convlit1`関数内の`if(cvttype(n->type, t))`が`if(cvttype(n->type, t) == 1)`に変更されました。これは、`cvttype`関数の戻り値がブール値ではなく、特定の整数値（`1`が成功を示す）を返すようになったため、そのAPI変更に合わせた修正です。
*   `overflow`関数呼び出し前の行番号設定が、`lno = setlineno(n);`に統一されました。これにより、`overflow`エラーが発生した際に、より正確なノードの行番号が`lineno`に設定されるようになります。`setlineno`は現在の`lineno`を保存し、ノードの`lineno`をセットして、元の`lineno`を返すため、処理後に`lineno = lno;`で元の値に戻すことができます。

### `src/cmd/gc/subr.c`の変更

*   `setlineno`関数のロジックが`if(n != N && n->op != ONAME)`から、より詳細な`switch`文に変更されました。
*   新しい`switch`文では、`ONAME`, `OTYPE`, `OPACK`, `OLITERAL`の各ノードタイプに対しては`break`（つまり、`lineno`を更新しない）が実行されます。これら以外のノードタイプの場合にのみ、`lineno = n->lineno;`によってグローバルな`lineno`がノードの行番号で更新されます。
*   この変更により、`setlineno`は、エラー報告に直接関連しない特定のノードタイプでは行番号を更新しないという、より洗練された動作をするようになりました。これにより、エラーメッセージが報告されるべき文脈の行番号がより正確に保たれます。

### `src/cmd/gc/walk.c`の変更

*   `walk`関数の冒頭にあった、特定のノードタイプ（`ONAME`, `OPACK`, `OTYPE`, `OLITERAL`）に対する行番号設定の`switch`文が削除され、代わりに`setlineno(n);`という単一の呼び出しに置き換えられました。これは、`setlineno`関数自体のロジックが改善されたため、`walk`関数内でこれらのノードタイプを個別に処理する必要がなくなったためです。これにより、コードの重複が排除され、`walk`関数の可読性が向上しました。
*   `walk`関数内に`case OTYPE:`ブロックが追加されました。これは、型が式として使用された場合にエラーを報告するためのものです。`!n->diag`チェックは、同じエラーが複数回報告されるのを防ぐためのものです。`yyerror("type %T used as expression", n->type);`というメッセージは、この種のエラーに対して非常に明確です。
*   `walkdot`関数内で、`lookdot`が失敗した場合（つまり、未定義のフィールドやメソッドにアクセスしようとした場合）のエラー報告ロジックが改善されました。ここでも`!n->diag`チェックが導入され、`yyerror("undefined DOT %S on %T", n->right->sym, n->left->type);`という明確なエラーメッセージが一度だけ報告されるようになりました。`n->right->sym`はアクセスしようとしたフィールド/メソッドの名前を、`n->left->type`はレシーバの型を示します。

これらの変更は、Goコンパイラがより正確で、重複のない、そして開発者にとって理解しやすいエラーメッセージを生成するための重要なステップです。

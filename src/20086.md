# [インデックス 20086] ファイルの概要

このコミットは、GoランタイムのLinux固有のコードベース、具体的には`src/pkg/runtime/os_linux.c`ファイル内の`getproccount`関数の変更に関するものです。この関数は、システムが利用可能なプロセッサ（CPUコア）の数を決定するために使用されます。コミットの主な目的は、既存の複雑なアルゴリズムをよりシンプルで、かつ当時のGoコンパイラ（9c）との互換性の問題を解決するコードに置き換えることです。

## 変更の背景

このコミットの背景には、主に以下の2つの理由があります。

1.  **コードの複雑性と実行頻度:** `getproccount`関数は、Goプログラムの起動時に一度だけ実行され、システムが利用可能なCPUコア数を取得します。元の実装は、この一度きりの処理に対して過度に複雑なアルゴリズムを使用しており、コミットメッセージにあるように「不可解なアルゴリズム (inscrutable algorithms)」と評されています。Goの設計哲学はシンプルさと明瞭さを重視するため、この複雑さはGoのコードベースの標準に合致していませんでした。
2.  **コンパイラ（9c）との互換性問題:** 当時使用されていたGoコンパイラである`9c`（Plan 9 CコンパイラをベースにしたGoのクロスコンパイラ）が、元の`getproccount`関数のコードを正しくコンパイルできない問題がありました。これは、特定の最適化やビット操作のパターンがコンパイラにとって扱いにくいものであった可能性を示唆しています。コンパイルエラーは、Goプログラムのビルドと実行を妨げるため、早急な修正が必要でした。

これらの理由から、よりシンプルで、かつコンパイラとの互換性があるコードへの置き換えが決定されました。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が役立ちます。

*   **Goランタイム (Go Runtime):** Goプログラムは、Goランタイムと呼ばれる軽量な実行環境上で動作します。ランタイムは、ガベージコレクション、スケジューリング（goroutineの管理）、メモリ管理、システムコールインターフェースなど、プログラムの実行に必要な低レベルの機能を提供します。`os_linux.c`のようなファイルは、特定のオペレーティングシステム（この場合はLinux）に特化したランタイムの側面を扱います。
*   **`sched_getaffinity`システムコール:** Linuxカーネルが提供するシステムコールの一つで、特定のプロセスまたはスレッドが実行を許可されているCPU（CPUアフィニティマスク）を取得するために使用されます。このシステムコールは、CPUのビットマスクを`buf`に書き込み、そのバイト数を返します。各ビットは、対応するCPUコアが利用可能かどうかを示します。
*   **CPUアフィニティマスク:** プロセスやスレッドが実行できるCPUのセットを示すビットマスクです。例えば、`0b0001`はCPU0のみ、`0b0011`はCPU0とCPU1が利用可能であることを示します。
*   **ビット操作:** コンピュータサイエンスにおいて、数値の個々のビットを操作する技術です。このコミットでは、特にCPUアフィニティマスクからセットされているビット（つまり利用可能なCPUコア）の数を数えるためにビット操作が使用されています。
*   **9cコンパイラ:** Go言語の初期のコンパイラの一つで、Plan 9 Cコンパイラをベースにしていました。Goのツールチェーンは進化しており、現在では主に`go tool compile`が使用されていますが、このコミットが作成された2014年当時は`9c`が重要な役割を担っていました。
*   **プロセッサ数 (Processor Count):** Goランタイムは、プログラムの並行性を最適化するために、システムが利用可能な論理プロセッサ（CPUコア）の数を把握する必要があります。これは、GoスケジューラがいくつのOSスレッドを生成し、それらのスレッド上でいくつのgoroutineを並行して実行するかを決定する際の重要な情報となります。

## 技術的詳細

変更の核心は、`getproccount`関数内で`sched_getaffinity`システムコールによって取得されたCPUアフィニティマスク（`buf`配列に格納される）から、セットされているビットの数を数えるアルゴリズムの変更です。

元のコードは、ビットカウントのために以下のような複雑なビット操作の連鎖を使用していました。

```c
t = t - ((t >> 1) & 0x5555555555555555ULL);
t = (t & 0x3333333333333333ULL) + ((t >> 2) & 0x3333333333333333ULL);
cnt += (int32)((((t + (t >> 4)) & 0xF0F0F0F0F0F0F0FULL) * 0x101010101010101ULL) >> 56);
```

これは、いわゆる「SWAR (SIMD Within A Register)」または「Population Count (Popcount)」アルゴリズムの一種で、レジスタ内のビットを並行して数えるための高速な方法です。しかし、この特定の形式は、当時の`9c`コンパイラにとって最適化が難しかったか、あるいは正しくコード生成できなかった可能性があります。また、その見た目から「不可解 (inscrutable)」と評されるように、直感的な理解が難しいコードでした。

新しいコードは、より直接的で理解しやすいループベースのビットカウントアルゴリズムに置き換えられました。

```c
while(t != 0) {
    n += t&1;
    t >>= 1;
}
```

この新しいアルゴリズムは、`t`が0になるまでループを回し、各イテレーションで`t`の最下位ビット（`t&1`）が1であればカウンタ`n`をインクリメントし、その後`t`を1ビット右シフト（`t >>= 1`）して次のビットを調べます。これは、ビットを一つずつ検査していく古典的な方法であり、非常にシンプルで、どのコンパイラでも確実に正しくコンパイルできます。

また、`sched_getaffinity`の戻り値`r`のチェックも改善されています。元のコードでは`r > 0`の場合のみ処理を行っていましたが、新しいコードでは`r <= 0`の場合に`return 1;`として、少なくとも1つのプロセッサがあることを保証しています。これは、システムコールが失敗した場合や、利用可能なCPUがないという異常な状況に対する堅牢性を高めるための変更です。

最後に、`cnt`（新しいコードでは`n`）が0の場合に1を返すロジックも変更されています。元のコードでは`return cnt ? cnt : 1;`でしたが、新しいコードでは`if(n < 1) n = 1; return n;`となり、意味的には同じですが、より明示的な条件分岐になっています。これは、Goランタイムが少なくとも1つのプロセッサを常に想定しているためです。

## コアとなるコードの解説

変更された`getproccount`関数は、以下のステップで動作します。

1.  **`sched_getaffinity`の呼び出し:**
    `runtime·sched_getaffinity(0, sizeof(buf), buf)`を呼び出し、現在のプロセス（PID 0）のCPUアフィニティマスクを`buf`配列に取得します。`buf`は`uintptr`型の配列で、CPUアフィニティマスクがビット列として格納されます。`r`には、実際に読み込まれたバイト数が返されます。

2.  **エラーハンドリングと初期値の設定:**
    `if(r <= 0) return 1;`
    `sched_getaffinity`が失敗した場合（`r`が0以下の場合）、システムが利用可能なCPUコア数を1と見なして直ちに`1`を返します。これは、Goランタイムが少なくとも1つのプロセッサを必要とするためです。

3.  **ビットカウントの初期化:**
    `n = 0;`
    利用可能なCPUコアの数を格納する変数`n`を0で初期化します。

4.  **CPUアフィニティマスクの走査とビットカウント:**
    `for(i = 0; i < r/sizeof(buf[0]); i++) { ... }`
    `buf`配列の各要素（`uintptr`型）をループで処理します。`r/sizeof(buf[0])`は、`buf`配列に格納されている`uintptr`の要素数を示します。
    `t = buf[i];`
    現在の`uintptr`要素を`t`にコピーします。
    `while(t != 0) { n += t&1; t >>= 1; }`
    この`while`ループが新しいビットカウントアルゴリズムです。
    *   `t&1`: `t`の最下位ビットが1であるかをチェックします。1であれば、`n`に1を加算します。
    *   `t >>= 1`: `t`を1ビット右にシフトします。これにより、次のビットが最下位ビットの位置に移動し、次のループで検査されます。
    このループは`t`が0になるまで（つまり、すべてのビットが検査されるまで）繰り返されます。

5.  **結果の調整と返却:**
    `if(n < 1) n = 1;`
    すべてのビットを数え終わった後、もし`n`が0（利用可能なCPUコアが一つも見つからなかった場合）であれば、`n`を1に設定します。これは、Goランタイムが常に少なくとも1つのプロセッサを想定しているためです。
    `return n;`
    最終的に計算された利用可能なCPUコア数`n`を返します。

この変更により、`getproccount`関数はより読みやすく、保守しやすくなり、当時のGoコンパイラとの互換性問題も解決されました。パフォーマンスの観点では、SWARアルゴリズムは理論的には高速ですが、この関数が一度しか実行されないことを考えると、シンプルなループによるオーバーヘッドは無視できるレベルであり、コードの明瞭さとコンパイラ互換性の方が重要であると判断されたと考えられます。

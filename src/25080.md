## 変更の背景

この変更の背景には、Go言語のコンパイラ、特に公式の`gc`コンパイラが、非常に大きな浮動小数点数定数を内部的にどのように表現し、処理するかという問題があります。元のテストケース`issue11326.go`は、`1e2147483647`や`1e646456993`といった極端に大きな指数を持つ浮動小数点数リテラルが「constant too large」（定数が大きすぎる）というコンパイルエラーを発生させることを期待していました。

しかし、`gc`コンパイラは浮動小数点数定数の指数部を32ビットのバイナリ指数として内部的に表現しています。この表現には上限があり、特定の非常に大きな指数を持つ定数は、`gc`コンパイラの内部表現の限界を超えてしまいます。一方で、Go言語の仕様自体は、すべてのGoコンパイラ実装がこれらの極端な定数を同じように扱うことを義務付けているわけではありません。例えば、`gccgo`のような別のGoコンパイラ実装では、異なる内部表現を使用している可能性があり、これらの定数を処理できるかもしれません。

したがって、元のテストケースは、`gc`コンパイラの特定の実装詳細に過度に依存しており、Go言語仕様の精神に反する、あるいは他のGoコンパイラ実装に対して不公平な「過度に厳密な」テストであると判断されました。このコミットは、この「過度に厳密な」テストを緩和し、`gc`コンパイラの内部的な制約とGo言語仕様の柔軟性のバランスを取ることを目的としています。

## 前提知識の解説

1.  **Go言語の数値定数**: Go言語では、数値定数は型付けされていない（untyped）状態で存在します。これは、定数が特定の型（例: `int`, `float64`）に割り当てられるまで、その精度を最大限に保つことを意味します。例えば、`1e100`は`float64`の範囲を超えていますが、`float64`変数に代入されるまではエラーになりません。
2.  **浮動小数点数リテラル**: `1eN`のような表記は、`1 * 10^N`を意味する浮動小数点数リテラルです。`N`が非常に大きい場合、その値は極めて巨大になります。
3.  **`float64`の範囲**: Go言語の`float64`型はIEEE 754倍精度浮動小数点数に準拠しており、約`1.7976931348623157e+308`が表現可能な最大値です。これを超える値はオーバーフローし、`+Inf`（正の無限大）として扱われるか、コンパイル時にエラーとなります。
4.  **コンパイル時の定数評価**: Goコンパイラは、コンパイル時に定数式を評価します。この際、定数の値が大きすぎてコンパイラの内部表現の限界を超える場合や、特定の型に収まらない場合にエラーを報告します。
5.  **`gc`コンパイラと他のGo実装**:
    *   **`gc`**: Goプロジェクトが公式に提供するコンパイラです。Go言語の進化に合わせて開発され、多くの最適化を含んでいます。このコンパイラは、浮動小数点数定数の指数部を32ビットのバイナリ指数として内部的に扱います。
    *   **`gccgo`**: GCC（GNU Compiler Collection）をベースにしたGoコンパイラです。`gc`とは異なる実装であり、内部的な定数表現も異なる可能性があります。
6.  **エラーメッセージの種類**:
    *   `ERROR "constant too large"`: これは、定数そのものがコンパイラの内部表現の限界を超えている、または言語仕様上許容される範囲を超えていることを示唆するエラーです。型への代入とは直接関係なく、定数リテラル自体の問題です。
    *   `ERROR "... overflows float64"`: これは、定数リテラル自体は有効なものの、それを`float64`型に代入しようとした際に、その値が`float64`の表現可能な最大値を超えていることを示すエラーです。

## 技術的詳細

このコミットの核心は、Goコンパイラが浮動小数点数定数をどのように内部的に処理するか、そしてその処理がGo言語仕様とどのように整合するかという点にあります。

`gc`コンパイラは、浮動小数点数定数を内部的に表現する際に、その指数部を32ビットのバイナリ指数として扱います。これは、`1eN`という形式の定数において、`N`が非常に大きい場合（例えば`2147483647`や`646456993`）、`10^N`をバイナリ形式に変換した際の指数が32ビットの範囲を超えてしまうことを意味します。このような場合、`gc`コンパイラは定数を正確に表現できなくなり、「constant too large」というエラーを発生させます。

しかし、Go言語の仕様は、コンパイラの実装に対して、浮動小数点数定数の内部表現に関する特定の制約を課していません。これは、`gccgo`のような他のGoコンパイラが、より大きな指数を扱える異なる内部表現を使用する可能性があることを意味します。もし`gccgo`が`1e2147483647`のような定数を処理できる場合、`gc`コンパイラが「constant too large」エラーを出すことを期待するテストは、`gccgo`にとっては不適切であり、テストが失敗することになります。

このコミットは、この実装依存性の問題を解決するために、`gc`コンパイラの内部的な制限によってのみ「constant too large」となる定数に対するエラーチェックをテストから削除しました。代わりに、Go言語仕様のすべての実装が処理できるべき、しかし`float64`型には収まらない定数（例: `1e646456992`）に対しては、「overflows float64」というエラーチェックを維持しています。これにより、テストはGo言語仕様に準拠しつつ、`gc`コンパイラの現実的な制約も考慮したものとなっています。

## コアとなるコードの解説

このコミットにおける主要な変更点は以下の通りです。

1.  **過度に大きな定数のテストのコメントアウト**:
    ```go
    // var _ = 1e2147483647 // "constant too large"
    // var _ = 1e646456993  // "constant too large"
    ```
    これらの行はコメントアウトされ、対応するエラーチェックが削除されました。これは、`1e2147483647`や`1e646456993`のような定数が、`gc`コンパイラの32ビットバイナリ指数という内部表現の限界を超えるため、「constant too large」エラーを引き起こすものの、Go言語仕様自体は他のコンパイラ実装がこれらの定数を処理することを妨げていない、という判断に基づいています。したがって、これらの定数に対するエラーチェックは、`gc`に特化したものであり、一般的なGoコンパイラのテストとしては適切ではないとされました。

2.  **新しいコメントの追加**:
    ```go
    // The gc compiler implementation uses the minimally required 32bit
    // binary exponent, so these constants cannot be represented anymore
    // internally. However, the language spec does not preclude other
    // implementations from handling these. Don't check the error.

    // Any implementation must be able to handle these constants at
    // compile time (even though they cannot be assigned to a float64).
    ```
    これらのコメントは、変更の理由を明確に説明しています。最初のコメントは、`gc`コンパイラの内部的な制約（32ビットバイナリ指数）により、一部の極端な定数が表現できないことを指摘しています。そして、Go言語仕様が他の実装の柔軟性を許容しているため、これらの定数に対するエラーをチェックすべきではないと述べています。
    二番目のコメントは、残されたテストケース（`1e646456992`など）が、すべてのGoコンパイラ実装がコンパイル時に処理できるべき定数であることを強調しています。これらの定数は`float64`型には収まりませんが、定数としては有効であり、型への代入時にオーバーフローエラーを発生させるべきです。

3.  **`var _ = 1e308`の追加**:
    ```go
    var _ = 1e308
    ```
    この行は、`float64`の最大値に近い、しかしオーバーフローしない有効な浮動小数点数定数が正しく処理されることを確認するために追加されました。これは、テストケースが極端な値だけでなく、境界値付近の正常なケースもカバーしていることを保証します。

この変更により、`issue11326.go`のテストは、`gc`コンパイラの特定の実装詳細に過度に依存することなく、Go言語の浮動小数点数定数に関する一般的な仕様と、`float64`型への代入時のオーバーフロー挙動をより正確にテストするようになりました。

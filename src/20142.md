# [インデックス 20142] ファイルの概要

このコミットは、Go言語の `net/http` パッケージにおける `TimeoutHandler` のデータ競合を修正し、ロックの保持期間を延長することで、タイムアウト発生時のバッファ破損や予期せぬ動作を防ぐものです。また、ヘッダー送信に関する不要な警告を解消するための改善も含まれています。

## コミット

```
net/http: fix TimeoutHandler data races; hold lock longer

The existing lock needed to be held longer. If a timeout occured
while writing (but after the guarded timeout check), the writes
would clobber a future connection's buffer.

Also remove a harmless warning by making Write also set the
flag that headers were sent (implicitly), so we don't try to
write headers later (a no-op + warning) on timeout after we've
started writing.

Fixes #8414
Fixes #8209

LGTM=ruiu, adg
R=adg, ruiu

https://golang.org/cl/123610043
```

## 変更の背景

このコミットは、Go言語の `net/http` パッケージにおける `TimeoutHandler` の既存のデータ競合問題を解決するために導入されました。具体的には、以下の2つの主要な問題に対処しています。

1.  **バッファの破損 (Clobbering future connection's buffer):** `TimeoutHandler` は、設定されたタイムアウト期間内にHTTPハンドラが応答を完了しない場合に、処理を中断する機能を提供します。しかし、既存の実装では、ロックが十分に長く保持されていなかったため、タイムアウトが発生した際に、既にガードされたタイムアウトチェックを通過した後でも、書き込み操作が進行してしまう可能性がありました。これにより、現在のリクエストの書き込みが、将来の接続のバッファを上書き（clobber）してしまうというデータ競合が発生し、異なるリクエスト間でデータが混ざり合ったり、破損したりする可能性がありました。これはIssue #8414に関連していると考えられます。

2.  **ヘッダー送信に関する警告の解消:** `TimeoutHandler` がタイムアウトした後に、HTTPレスポンスヘッダーを書き込もうとすると、既にレスポンスボディの一部が書き込まれている場合があるため、これは無効な操作となり、GoのHTTPサーバーから「ヘッダーが既に送信されている」という警告が出力されることがありました。この警告自体は「無害」とされていましたが、開発者にとっては混乱を招く可能性がありました。このコミットは、`Write` メソッドが呼び出された時点で暗黙的にヘッダーが送信されたとマークすることで、この警告を発生させないように修正しています。これはIssue #8209に関連していると考えられます。

これらの問題は、特に高負荷な環境や、タイムアウトが頻繁に発生するような状況で、アプリケーションの安定性や信頼性に影響を与える可能性がありました。

## 前提知識の解説

このコミットの理解を深めるために、以下の概念について解説します。

### Goの `net/http` パッケージ

`net/http` パッケージは、Go言語でHTTPクライアントとサーバーを構築するための標準ライブラリです。HTTPリクエストの処理、レスポンスの生成、ルーティング、ミドルウェアの組み込みなど、Webアプリケーション開発に必要な基本的な機能を提供します。

### `http.TimeoutHandler`

`http.TimeoutHandler` は、`net/http` パッケージが提供するHTTPハンドララッパー（ミドルウェア）の一つです。これは、指定された `http.Handler` の実行にタイムアウトを設定するために使用されます。もしラップされたハンドラが設定された時間内に応答を完了しない場合、`TimeoutHandler` は処理を中断し、クライアントにタイムアウトエラー（通常はHTTP 503 Service Unavailable）を返します。これにより、遅延するリクエストがサーバーのリソースを占有し続けることを防ぎ、システムの安定性を保ちます。

### データ競合 (Data Race)

データ競合とは、複数のゴルーチン（Goにおける軽量スレッド）が同時に同じメモリ位置にアクセスし、そのうち少なくとも1つのアクセスが書き込みであり、かつアクセスが同期されていない場合に発生するプログラミング上のバグです。データ競合が発生すると、プログラムの動作が予測不能になり、クラッシュ、不正なデータ、セキュリティ脆弱性など、様々な問題を引き起こす可能性があります。Go言語では、`go run -race` コマンドで競合検出器を有効にして実行することで、データ競合を検出できます。

### ミューテックス (Mutex) とロック

ミューテックス（Mutual Exclusion、相互排他）は、データ競合を防ぐための同期プリミティブです。ミューテックスを使用すると、一度に1つのゴルーチンだけが共有リソース（メモリ、ファイルなど）にアクセスできるように制御できます。共有リソースにアクセスする前にミューテックスを「ロック」し、アクセスが完了したら「アンロック」します。これにより、複数のゴルーチンが同時に共有リソースを書き換えることを防ぎ、データの整合性を保ちます。

### `sync.Mutex`

`sync.Mutex` は、Go言語の標準ライブラリ `sync` パッケージで提供されるミューテックスの実装です。`Lock()` メソッドでミューテックスをロックし、`Unlock()` メソッドでアンロックします。

### `defer` キーワード

Go言語の `defer` キーワードは、関数がリターンする直前に実行される関数呼び出しをスケジュールするために使用されます。これは、リソースの解放（ファイルのクローズ、ロックのアンロックなど）を確実に行うために非常に便利です。`defer` を使用することで、エラーパスや複数のリターンポイントがある場合でも、クリーンアップ処理を忘れずに実行できます。このコミットでは、`defer tw.mu.Unlock()` を使用することで、ロックが確実に解放されるようにしています。

## 技術的詳細

このコミットの技術的な核心は、`net/http` パッケージ内の `timeoutWriter` 構造体の `Write` メソッドと `WriteHeader` メソッドにおけるロックの管理方法の変更にあります。

`timeoutWriter` は、`TimeoutHandler` が内部で使用する `http.ResponseWriter` のラッパーです。この構造体は、`sync.Mutex` (`tw.mu`) を保持しており、タイムアウト状態 (`tw.timedOut`) やヘッダーが既に書き込まれたか (`tw.wroteHeader`) といった内部状態を保護するために使用されます。

### `Write` メソッドの変更点

変更前は、`Write` メソッド内で `tw.mu.Lock()` を取得し、`timedOut` の状態を読み取った直後に `tw.mu.Unlock()` を解放していました。

```go
// 変更前
func (tw *timeoutWriter) Write(p []byte) (int, error) {
	tw.mu.Lock()
	timedOut := tw.timedOut
	tw.mu.Unlock() // ここでロックが解放される
	if timedOut {
		return 0, ErrHandlerTimeout
	}
	return tw.w.Write(p) // ロックが解放された状態で書き込みが行われる
}
```

この実装では、`timedOut` のチェックと実際の `tw.w.Write(p)` の間にロックが解放されるため、この短い期間に別のゴルーチン（例えばタイムアウトを処理するゴルーチン）が `timeoutWriter` の状態を変更したり、バッファを操作したりする可能性がありました。これがデータ競合の原因でした。

変更後、`tw.mu.Unlock()` の呼び出しは `defer` ステートメントによって関数の終了時に実行されるように変更されました。

```go
// 変更後
func (tw *timeoutWriter) Write(p []byte) (int, error) {
	tw.mu.Lock()
	defer tw.mu.Unlock() // 関数がリターンするまでロックが保持される
	tw.wroteHeader = true // implicitly at least
	if tw.timedOut {
		return 0, ErrHandlerTimeout
	}
	return tw.w.Write(p)
}
```

これにより、`Write` メソッドの実行中、特に `tw.w.Write(p)` が呼び出されている間も `tw.mu` ロックが保持されることが保証されます。これにより、タイムアウト処理と書き込み操作の間のデータ競合が解消されます。

また、`tw.wroteHeader = true` が `Write` メソッドの冒頭（ロック取得後）に追加されました。これは、`Write` が呼び出された時点で、HTTPヘッダーが暗黙的に（または既に）送信されたと見なすためです。これにより、後続の `WriteHeader` 呼び出しが不要な警告を生成するのを防ぎます。

### `WriteHeader` メソッドの変更点

`WriteHeader` メソッドも同様に、`tw.mu.Unlock()` の呼び出しが `defer` ステートメントによって関数の終了時に実行されるように変更されました。

```go
// 変更前
func (tw *timeoutWriter) WriteHeader(code int) {
	tw.mu.Lock()
	if tw.timedOut || tw.wroteHeader {
		tw.mu.Unlock() // ここでロックが解放される
		return
	}
	tw.wroteHeader = true
	tw.mu.Unlock() // ここでもロックが解放される
	tw.w.WriteHeader(code)
}

// 変更後
func (tw *timeoutWriter) WriteHeader(code int) {
	tw.mu.Lock()
	defer tw.mu.Unlock() // 関数がリターンするまでロックが保持される
	if tw.timedOut || tw.wroteHeader {
		return
	}
	tw.wroteHeader = true
	tw.w.WriteHeader(code)
}
```

変更前は、`if tw.timedOut || tw.wroteHeader` の条件が真の場合に早期リターンする際にロックが解放されていましたが、それ以外の場合も `tw.w.WriteHeader(code)` の直前でロックが解放されていました。変更後は、`defer` を使用することで、`WriteHeader` メソッド全体でロックが保持されるようになり、ヘッダー書き込み中の競合状態が確実に回避されます。

## コアとなるコードの解説

### `src/pkg/net/http/server.go` の変更

`timeoutWriter` の `Write` および `WriteHeader` メソッドにおける `defer tw.mu.Unlock()` の導入は、このコミットの最も重要な変更点です。

*   **`Write` メソッド:**
    変更前は、`tw.mu.Lock()` を取得し、`timedOut` フラグをチェックした後すぐに `tw.mu.Unlock()` を呼び出していました。これにより、`tw.w.Write(p)` が実行されている間はロックが解放された状態になり、この間にタイムアウト処理を行うゴルーチンが `timeoutWriter` の内部状態（特に基になる `http.ResponseWriter` のバッファ）を操作しようとすると、データ競合が発生する可能性がありました。
    `defer tw.mu.Unlock()` を使用することで、`Write` メソッドが完全に終了するまで `tw.mu` ロックが保持されることが保証されます。これにより、`tw.w.Write(p)` の実行中であっても、`timeoutWriter` の内部状態が他のゴルーチンによって不正にアクセスされることを防ぎ、バッファ破損の問題を解決します。
    また、`tw.wroteHeader = true` を `Write` の冒頭に移動したことで、`Write` が呼び出された時点でヘッダーが暗黙的に送信されたとみなされます。これにより、後続の `WriteHeader` 呼び出しが「ヘッダーが既に送信されている」という無害な警告を生成するのを防ぎます。

*   **`WriteHeader` メソッド:**
    `WriteHeader` メソッドも同様に、`defer tw.mu.Unlock()` を導入することで、メソッドの実行全体にわたってロックが保持されるようになりました。これにより、ヘッダーの書き込み中にタイムアウトが発生した場合でも、競合状態を回避し、`WriteHeader` の呼び出しが安全に行われることを保証します。以前は、早期リターンパスや通常の実行パスで明示的に `Unlock` を呼び出す必要がありましたが、`defer` を使うことでコードが簡潔になり、ロックの解放忘れを防ぐことができます。

### `src/pkg/net/http/serve_test.go` の変更

追加されたテストは、これらの修正が実際に機能することを検証するためのものです。

*   **`TestTimeoutHandlerRace`:**
    このテストは、`TimeoutHandler` でラップされたハンドラが `w.Write([]byte("hi"))` を繰り返し呼び出し、意図的に遅延を発生させるシナリオをシミュレートします。複数のゴルーチンから同時にこのエンドポイントにリクエストを送信し、タイムアウトが発生する状況を作り出します。このテストは、`Write` 操作中にデータ競合が発生しないことを確認することを目的としています。

*   **`TestTimeoutHandlerRaceHeader`:**
    このテストは、`TimeoutHandler` でラップされたハンドラが `w.WriteHeader(204)` を呼び出すシナリオをシミュレートします。非常に短いタイムアウト（`time.Nanosecond`）を設定し、複数のゴルーチンから同時にリクエストを送信することで、`WriteHeader` 操作中にタイムアウトが発生する状況を作り出します。このテストは、`WriteHeader` 操作中にデータ競合が発生しないこと、およびヘッダーに関する警告が発生しないことを確認することを目的としています。

これらのテストは、以前のバグが再現されなくなったことを確認するための重要な検証手段であり、`TimeoutHandler` の堅牢性を高める上で不可欠です。

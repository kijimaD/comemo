
## 変更の背景

このコミットは、Go issue #10379 の解決を目的としています。Goの `net/rpc` パッケージは、ネットワーク経由でリモートプロシージャコール（RPC）を可能にするための機能を提供します。RPCサービスとしてメソッドを公開するには、特定の規約に従う必要があります。これには、メソッドがエクスポートされていること（つまり、名前が大文字で始まること）などが含まれます。

しかし、これまでの `net/rpc` のドキュメントでは、RPCサービスとして登録する「型」自体がエクスポートされている必要があるという重要な要件が明示されていませんでした。ユーザーはメソッドがエクスポートされていれば十分だと誤解し、非エクスポート型のメソッドを登録しようとして、期待通りに動作しないという問題に直面することがありました。

Go言語では、パッケージ外部からアクセス可能な識別子（変数、関数、型、メソッドなど）は「エクスポートされている」と見なされ、その名前は常に大文字で始まります。`net/rpc` のようなリフレクションを使用するシステムでは、このエクスポートルールが特に重要になります。なぜなら、リフレクションは公開された（エクスポートされた）情報にのみアクセスできるためです。非エクスポート型に属するメソッドは、たとえメソッド自体がエクスポートされていても、リフレクションを通じて外部からアクセスすることができません。

このコミットは、このドキュメントの不足を解消し、ユーザーが `net/rpc` をより正確に、かつ期待通りに利用できるようにするために行われました。

## 前提知識の解説

### Go言語のエクスポートルール

Go言語において、識別子（変数、関数、型、メソッド、構造体のフィールドなど）がパッケージ外からアクセス可能であるかどうかは、その名前の先頭文字が大文字であるか小文字であるかによって決まります。

*   **大文字で始まる識別子**: エクスポートされます。これは、その識別子が定義されているパッケージの外部からアクセス可能であることを意味します。
*   **小文字で始まる識別子**: エクスポートされません（非エクスポート）。これは、その識別子が定義されているパッケージ内でのみアクセス可能であることを意味します。

このルールは、Goのモジュール性、カプセル化、およびAPI設計において非常に重要です。

### `net/rpc` パッケージ

`net/rpc` パッケージは、Goプログラムがネットワーク経由でリモートプロシージャコール（RPC）サービスを提供および利用するためのメカニズムを提供します。これは、クライアントがリモートサーバー上の関数を、あたかもローカル関数であるかのように呼び出すことを可能にします。

`net/rpc` サービスとしてメソッドを公開するには、以下の規約を満たす必要があります（このコミットで明確化された内容を含む）：

1.  **レシーバの型がエクスポートされていること**: サービスとして登録する構造体やインターフェースの型自体がエクスポートされている必要があります（名前が大文字で始まる）。
2.  **メソッドがエクスポートされていること**: RPCとして公開するメソッドの名前が大文字で始まる必要があります。
3.  **メソッドのシグネチャ**:
    *   2つの引数を持つこと。
    *   両方の引数がエクスポートされた型（または組み込み型）であること。
    *   2番目の引数がポインタであること。
    *   1つの戻り値を持つこと。
    *   戻り値の型が `error` であること。

これらの規約は、`net/rpc` がリフレクションを使用してメソッドを検出し、引数をマーシャリング/アンマーシャリングし、エラーを処理するために必要です。

### Goのリフレクション

Goのリフレクション機能は、実行時にプログラムの構造を検査し、操作する能力を提供します。`reflect` パッケージを通じて、型情報（`reflect.Type`）や値情報（`reflect.Value`）にアクセスできます。

`net/rpc` は、このリフレクションを多用して、登録されたサービスオブジェクトのメソッドを動的に発見し、そのシグネチャを検証します。エクスポートされていない型やメソッドは、リフレクションのメカニズムを通じて外部からアクセスできないため、`net/rpc` はそれらをRPCサービスとして公開することができません。

## 技術的詳細

このコミットの技術的な核心は、Goのリフレクションとエクスポートルールの相互作用にあります。`net/rpc` パッケージは、`reflect` パッケージを使用して、ユーザーが `rpc.Register` 関数に渡したレシーバ値のメソッドを検査します。

`rpc.Register` は内部的に、渡された値の型情報（`reflect.Type`）を取得し、その型が持つメソッドをイテレートします。各メソッドについて、`reflect.Method` オブジェクトを通じてその名前、型、引数、戻り値の情報を取得します。

Goのリフレクションの設計上、エクスポートされていない型やフィールド、メソッドは、リフレクションAPIを通じて外部パッケージからアクセスできません。例えば、`reflect.TypeOf(myNonExportedStruct).MethodByName("MyExportedMethod")` のような呼び出しは、`myNonExportedStruct` が非エクスポート型である場合、たとえ `MyExportedMethod` がエクスポートされていても、そのメソッド情報を見つけることができません。これは、Goのアクセス制御メカニズムがリフレクションレベルでも適用されるためです。

したがって、`net/rpc` がRPCサービスとしてメソッドを公開するためには、そのメソッドが属するレシーバの型自体がエクスポートされている必要があります。もし型がエクスポートされていなければ、`net/rpc` はリフレクションを使ってその型に属するメソッドをそもそも発見することができないため、RPCとして登録することができません。

このコミットは、この暗黙の前提条件を明示的にドキュメントに追加することで、開発者が `net/rpc` を使用する際の混乱を避け、正しい実装を促すことを目的としています。これはコードの動作を変更するものではなく、既存の動作に関するドキュメントの正確性を向上させるものです。

## コアとなるコードの解説

このコミットは、Goの `net/rpc` パッケージの `server.go` ファイル内のドキュメントコメントを更新しています。これは、コードの振る舞いを変更するものではなく、`net/rpc` サービスを正しく実装するための要件をより明確に伝えるためのものです。

`net/rpc` パッケージは、`Register` 関数を通じて、特定のレシーバ値（通常は構造体のインスタンス）のメソッドをRPCサービスとして公開します。この関数は、リフレクションを使用してレシーバのメソッドを走査し、RPCの規約に合致するものだけを登録します。

変更前のドキュメントでは、メソッド自体がエクスポートされていること（名前が大文字で始まること）が強調されていましたが、そのメソッドが属するレシーバの「型」もエクスポートされている必要があるという点が明示されていませんでした。

このコミットによって追加された「`- the method's type is exported.`」という行は、この重要な前提条件を明確にしています。Goのリフレクションメカニズムは、エクスポートされていない型に属するメソッドを外部から発見することができません。したがって、`net/rpc` がRPCサービスとしてメソッドを公開するためには、そのメソッドが属する型自体がエクスポートされている必要があるのです。

例えば、以下のような非エクスポート型 `myService` があったとします。

```go
type myService struct{}

func (s *myService) MyMethod(arg *int, reply *int) error {
    // ...
    return nil
}
```

この `myService` 型は小文字で始まるため、非エクスポート型です。たとえ `MyMethod` がエクスポートされていても、`net/rpc.Register(&myService{})` を呼び出しても `MyMethod` はRPCサービスとして登録されません。これは、`net/rpc` がリフレクションを使って `myService` 型のメソッドを探索しようとした際に、その型自体が非エクスポートであるため、メソッドにアクセスできないためです。

このドキュメントの更新は、このような潜在的な誤解やデバッグの困難さを解消し、開発者が `net/rpc` をよりスムーズに利用できるようにするための重要な改善です。

# [インデックス 20867] ファイルの概要

このコミットは、Go言語の`cmd/cgo`ツールにおけるClangコンパイラの統合アセンブラに関する問題を修正し、`cmd/ld`リンカにおけるELFシンボルテーブルの処理を改善するものです。特に、ARMアーキテクチャでのビルド失敗と、Clang 3.4以降で生成されるシンボルエントリの変更に対応しています。

    cmd/cgo: disable clang's integrated assembler

## 元コミット内容

このコミットは、主に以下の2つの問題に対処しています。

1.  **Clangの統合アセンブラの問題**: Clang 3.4でデフォルトで導入された統合アセンブラが、`.arch`ディレクティブを認識するにもかかわらず、`-march`のデフォルト値を変更しないために、ARMv5以降で利用可能な`BLX`命令を使用する際にビルドが失敗する問題。これはClangのバグである可能性が高いため、cgoのアセンブリシムをコンパイルする際に統合アセンブラを無効にすることで回避しています。
2.  **`ldelf.c`の変更**: Clang 3.4以降がより「奇妙な」シンボルテーブルエントリを生成するようになったため、Goリンカの`ldelf.c`ファイルに小さな変更が加えられました。

## 変更の背景

この変更は、GoのビルドシステムがClangコンパイラ、特にバージョン3.4以降と連携する際に発生した互換性の問題に対応するために行われました。

主要な背景は以下の通りです。

*   **Clang 3.4の統合アセンブラ導入**: Clang 3.4から、コンパイラにアセンブラ機能が統合され、デフォルトで有効になりました。これにより、外部のアセンブラ（例: GNU `as`）を呼び出す必要がなくなり、ビルドプロセスが高速化されることが期待されました。
*   **ARMアーキテクチャにおける問題**: ARMアーキテクチャでは、特定の命令（例: `BLX`）が特定のアーキテクチャバージョン（例: ARMv5以上）でのみ利用可能です。Goのcgoアセンブリシムは、これらの命令を使用することがありました。
*   **`.arch`と`-march`の不整合**: Clangの統合アセンブラは、アセンブリコード内の`.arch`ディレクティブ（ターゲットアーキテクチャを指定）を認識しますが、コンパイラのコマンドラインオプションである`-march`（ターゲットアーキテクチャを指定）のデフォルト値を適切に更新しませんでした。多くのLinuxディストリビューションでは、ClangがデフォルトでARMv4tアーキテクチャ向けにコンパイルされており、これは`BLX`命令が利用できない古いアーキテクチャです。
*   **ビルド失敗**: 結果として、Clangの統合アセンブラが、実際にはサポートされていないARMv4tアーキテクチャ向けにコードをアセンブルしようとし、`BLX`命令のような新しい命令に遭遇するとビルドが失敗しました。これはClang側のバグと見なされました。
*   **Issue 8348**: この問題はGoのIssueトラッカーで[Issue 8348](https://github.com/golang/go/issues/8348)として報告され、このコミットはその修正として行われました。
*   **`ldelf.c`の必要性**: Clang 3.4以降が生成するシンボルテーブルエントリの形式が変更されたため、Goリンカがこれらの新しいエントリを正しく処理できるように`ldelf.c`の調整も必要となりました。特に、ARMのbinutilsが生成するマッピングシンボル（`$a`, `$d`）の処理方法に変更が生じました。

これらの問題に対処することで、GoのビルドがClang 3.4以降を使用する環境でも安定して動作するようにすることが目的でした。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を把握しておく必要があります。

*   **Cgo**:
    *   Go言語とC言語（またはC++）のコードを相互に呼び出すためのGoのツールです。GoプログラムからCライブラリを呼び出したり、CプログラムからGo関数を呼び出したりする際に使用されます。
    *   `cmd/cgo`は、GoとCの間のインターフェースコードを生成し、コンパイルとリンクを調整します。
    *   「cgo assembly shim」とは、Cgoが生成するアセンブリコードの一部で、GoとCの間の呼び出し規約の変換などを行います。

*   **Clang**:
    *   LLVMプロジェクトの一部であるC、C++、Objective-C、Objective-C++コンパイラです。GCCの代替として広く使用されています。
    *   **統合アセンブラ (Integrated Assembler)**: Clangの機能の一つで、アセンブリコードをコンパイルする際に、外部のアセンブラツール（例: GNU `as`）を呼び出す代わりに、コンパイラ自身がアセンブラの機能を持つものです。これにより、コンパイルプロセスが効率化されます。Clang 3.4でデフォルトで有効になりました。

*   **アセンブラディレクティブとコンパイラオプション**:
    *   **.arch ディレクティブ**: アセンブリ言語のソースコード内で使用されるディレクティブ（指示子）の一つで、ターゲットとするCPUアーキテクチャを指定します。例えば、`.arch armv5te`のように記述されます。
    *   **`-march` オプション**: GCCやClangなどのコンパイラで使用されるコマンドラインオプションで、生成するコードのターゲットCPUアーキテクチャを指定します。例えば、`-march=armv5te`のように指定します。このオプションは、コンパイラがどの命令セットやCPUの機能をターゲットにするかを決定するために重要です。

*   **ARMアーキテクチャ**:
    *   モバイルデバイスなどで広く使用されているRISCベースのCPUアーキテクチャです。
    *   **ARMv4t, ARMv5**: ARMアーキテクチャの異なるバージョンです。ARMv4tは古いバージョンで、ARMv5はそれ以降のバージョンです。新しいバージョンでは、より多くの命令や機能が追加されています。
    *   **BLX 命令**: ARMv5T以降のARMアーキテクチャで導入された命令です。これは「Branch with Link and Exchange」の略で、関数呼び出しを行う際に、リンクレジスタ（`lr`）にリターンアドレスを保存し、さらにARMモードとThumbモードの間で切り替える機能を持っています。古いARMv4tではこの命令は存在しません。

*   **ELF (Executable and Linkable Format)**:
    *   Unix系システムで広く使用されている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準ファイル形式です。
    *   **シンボルテーブル (Symbol Table)**: ELFファイル内に含まれるセクションの一つで、プログラム内の関数や変数などのシンボル（名前）とそのアドレスや型などの情報が格納されています。リンカはシンボルテーブルを使用して、異なるオブジェクトファイル間の参照を解決します。
    *   **シンボルテーブルエントリ (Symtab Entries)**: シンボルテーブル内の個々のエントリで、各シンボルに関する詳細情報を含みます。

*   **`ldelf.c`**:
    *   Go言語のリンカ（`cmd/ld`）の一部で、ELF形式のオブジェクトファイルやライブラリからシンボル情報を読み取り、処理する役割を担っています。

*   **`strcmp` と `strncmp`**:
    *   C言語の標準ライブラリ関数です。
    *   `strcmp(s1, s2)`: 2つの文字列`s1`と`s2`を比較し、完全に一致するかどうかを判断します。
    *   `strncmp(s1, s2, n)`: 2つの文字列`s1`と`s2`の先頭`n`文字だけを比較します。このコミットでは、特定のシンボル名が「$a」または「$d」で始まるかどうかをチェックするために、完全一致ではなく前方一致が必要になったため、`strcmp`から`strncmp`への変更が行われました。

*   **Binutils**:
    *   GNUプロジェクトが提供するバイナリツール群で、アセンブラ（`as`）、リンカ（`ld`）などが含まれます。ARMアーキテクチャ向けにコンパイルされたBinutilsは、特定の「マッピングシンボル」（例: `$a`, `$d`）を生成することがあります。これらは、コードとデータのセクションの境界を示すために使用される特殊なシンボルです。

## 技術的詳細

このコミットの技術的詳細は、Clangの統合アセンブラの挙動と、Goリンカがシンボルを処理する方法の2つの側面に焦点を当てています。

### Clangの統合アセンブラの問題

Clang 3.4で導入された統合アセンブラは、アセンブリコードを直接コンパイルできるため、ビルドチェーンを簡素化し、パフォーマンスを向上させることが期待されました。しかし、ARMアーキテクチャにおいて、この統合アセンブラには特定のバグがありました。

1.  **`.arch`ディレクティブの誤解釈**: アセンブリソースコードには、ターゲットアーキテクチャを指定する`.arch`ディレクティブが含まれることがあります。例えば、GoのcgoアセンブリシムがARMv5以降の命令セットを使用する場合、`.arch armv5te`のようなディレクティブが含まれる可能性があります。Clangの統合アセンブラは、このディレクティブを構文的には認識しますが、実際にアセンブルするコードの命令セットを、このディレクティブで指定されたアーキテクチャに切り替えることを怠っていました。
2.  **`-march`オプションとの不整合**: 一方、Clangコンパイラはコマンドラインで`-march`オプションを受け入れ、これによってターゲットアーキテクチャを決定します。しかし、多くのディストリビューションでClangがデフォルトでARMv4t（`BLX`命令をサポートしない古いアーキテクチャ）向けにコンパイルされていたため、たとえアセンブリコードが`.arch armv5te`を含んでいても、統合アセンブラは依然としてARMv4tの制約内でアセンブルしようとしました。
3.  **`BLX`命令の使用とビルド失敗**: Goのcgoアセンブリシムは、ARMv5以降で利用可能な`BLX`命令を使用することがありました。統合アセンブラがARMv4tのコンテキストで`BLX`命令に遭遇すると、その命令が認識できないため、アセンブルエラーが発生し、結果としてGoのビルドが失敗しました。

この問題はClangのバグと判断されたため、Go側では一時的な回避策として、cgoがClangを使用している場合に統合アセンブラを無効にするオプション`-no-integrated-as`を追加することにしました。これにより、Clangは外部のアセンブラ（通常はGNU `as`）を呼び出すようになり、この外部アセンブラは`.arch`ディレクティブを正しく解釈し、適切なアーキテクチャ向けのコードを生成できます。

### `ldelf.c`におけるシンボル処理の変更

Clang 3.4以降は、以前のバージョンと比較して、ELFシンボルテーブルに「より奇妙な」エントリを生成するようになりました。これは、特にARMアーキテクチャのbinutilsが生成する特殊なマッピングシンボル（`$a`や`$d`など）の処理に影響を与えました。

*   **マッピングシンボル**: ARMのbinutilsは、コードセクションとデータセクションの境界を示すために、`$a`（ARMコード）や`$d`（データ）のような特殊なローカルシンボルを生成します。これらはデバッグ情報やリンカの内部処理で使用されることがありますが、Goリンカが通常のシンボルとして誤って解釈すると問題が生じる可能性があります。
*   **`strcmp`から`strncmp`への変更**: 以前の`ldelf.c`では、これらのマッピングシンボルを無視するために、シンボル名が`"$a"`または`"$d"`と**完全に一致する**かどうかを`strcmp`でチェックしていました。しかし、Clang 3.4以降が生成するシンボルエントリでは、これらのマッピングシンボルが`"$a"`や`"$d"`で始まるが、その後にさらに文字が続く形式（例: `$a.some_suffix`）で現れるようになりました。
*   **部分一致の必要性**: この変更に対応するため、シンボル名が`"$a"`または`"$d"`で**始まる**かどうかをチェックするようにロジックを変更する必要がありました。`strncmp`関数は、指定された文字数だけ文字列を比較するため、この部分一致の要件を満たします。具体的には、`strncmp(sym->name, "$a", 2)`とすることで、シンボル名が`"$a"`で始まるかどうかを安全にチェックできるようになりました。これにより、Goリンカは新しい形式のシンボルエントリでも、これらの特殊なマッピングシンボルを正しく識別し、無視できるようになりました。

これらの変更は、Goのビルドシステムが最新のコンパイラツールチェーンと互換性を保ち、安定した動作を保証するために不可欠でした。

## コアとなるコードの解説

### `src/cmd/cgo/gcc.go`の変更

このファイルは、cgoがGCC（または互換性のあるコンパイラ、この場合はClang）を呼び出す際のコマンドライン引数を生成するロジックを含んでいます。

*   **変更前**:
    ```go
    case "arm":
        return []string{"-marm"} // not thumb
    ```
    ARMアーキテクチャの場合、単に`-marm`オプションを返していました。これは、ARMモードでコンパイルすることを指示するものです（Thumbモードではない）。

*   **変更後**:
    ```go
    case "arm":
        args := []string{"-marm"} // not thumb
        if strings.Contains(p.gccBaseCmd()[0], "clang") {
            // The clang integrated assembler understands the .arch directive
            // but does not appear to honor it, so disable it. Issue 8348.
            args = append(args, "-no-integrated-as")
        }
        return args
    ```
    1.  まず、`args`というスライスに`-marm`を初期値として設定します。
    2.  `p.gccBaseCmd()[0]`は、cgoが使用するコンパイラの実行ファイル名（例: `clang`や`gcc`）を返します。
    3.  `strings.Contains(p.gccBaseCmd()[0], "clang")`によって、現在使用しているコンパイラがClangであるかどうかをチェックします。
    4.  もしClangであれば、`args`スライスに`-no-integrated-as`オプションを追加します。このオプションは、Clangの統合アセンブラを無効にし、代わりに外部のアセンブラ（通常はGNU `as`）を使用するように強制します。これにより、Clangの統合アセンブラが`.arch`ディレクティブを正しく処理しない問題が回避されます。コメントにもあるように、これはIssue 8348の修正です。

この変更により、ARM環境でClangを使用している場合に、cgoが生成するアセンブリシムのビルドが安定するようになりました。

### `src/cmd/ld/ldelf.c`の変更

このファイルは、GoリンカがELF形式のオブジェクトファイルからシンボル情報を読み取る部分です。

*   **変更前**:
    ```c
    if(!(thechar == '5' && (strcmp(sym->name, "$a") == 0 || strcmp(sym->name, "$d") == 0))) // binutils for arm generate these mapping symbols, ignore these
    ```
    この行は、ローカルシンボル（`ElfSymBindLocal`）を処理する際に、特定の条件を満たすシンボルを無視するためのものです。
    *   `thechar == '5'`は、ターゲットアーキテクチャがARMであることを示唆しています（Goの内部的なアーキテクチャ識別子）。
    *   `strcmp(sym->name, "$a") == 0 || strcmp(sym->name, "$d") == 0`は、シンボル名が`"$a"`または`"$d"`と**完全に一致する**場合に真となります。これは、ARMのbinutilsが生成する特殊なマッピングシンボルを無視するためのロジックでした。

*   **変更後**:
    ```c
    if(!(thechar == '5' && (strncmp(sym->name, "$a", 2) == 0 || strncmp(sym->name, "$d", 2) == 0))) // binutils for arm generate these mapping symbols, ignore these
    ```
    `strcmp`が`strncmp`に変更され、比較する文字数が`2`に指定されました。
    *   `strncmp(sym->name, "$a", 2) == 0`は、シンボル名が`"$a"`で**始まる**場合に真となります。
    *   `strncmp(sym->name, "$d", 2) == 0`は、シンボル名が`"$d"`で**始まる**場合に真となります。
    この変更は、Clang 3.4以降が生成するシンボルエントリにおいて、マッピングシンボルが`"$a"`や`"$d"`の後にさらに文字が続く形式（例: `$a.some_suffix`）で現れるようになったためです。`strncmp`を使用することで、これらの新しい形式のシンボルでも、先頭の`"$a"`または`"$d"`を正しく識別し、リンカがそれらを無視できるようにしています。

この変更により、GoリンカはClang 3.4以降でコンパイルされたオブジェクトファイルに含まれる新しい形式のシンボルテーブルエントリを正しく処理できるようになり、リンカのエラーや誤ったシンボル解決を防ぎます。

## 元コミット内容

このコミットは、主に以下の2つの問題に対処しています。

1.  **Clangの統合アセンブラの問題**: Clang 3.4でデフォルトで導入された統合アセンブラが、`.arch`ディレクティブを認識するにもかかわらず、`-march`のデフォルト値を変更しないために、ARMv5以降で利用可能な`BLX`命令を使用する際にビルドが失敗する問題。これはClangのバグである可能性が高いため、cgoのアセンブリシムをコンパイルする際に統合アセンブラを無効にすることで回避しています。
2.  **`ldelf.c`の変更**: Clang 3.4以降がより「奇妙な」シンボルテーブルエントリを生成するようになったため、Goリンカの`ldelf.c`ファイルに小さな変更が加えられました。

## 変更の背景

この変更は、GoのビルドシステムがClangコンパイラ、特にバージョン3.4以降と連携する際に発生した互換性の問題に対応するために行われました。

主要な背景は以下の通りです。

*   **Clang 3.4の統合アセンブラ導入**: Clang 3.4から、コンパイラにアセンブラ機能が統合され、デフォルトで有効になりました。これにより、外部のアセンブラ（例: GNU `as`）を呼び出す必要がなくなり、ビルドプロセスが高速化されることが期待されました。
*   **ARMアーキテクチャにおける問題**: ARMアーキテクチャでは、特定の命令（例: `BLX`）が特定のアーキテクチャバージョン（例: ARMv5以上）でのみ利用可能です。Goのcgoアセンブリシムは、これらの命令を使用することがありました。
*   **`.arch`と`-march`の不整合**: Clangの統合アセンブラは、アセンブリコード内の`.arch`ディレクティブ（ターゲットアーキテクチャを指定）を構文的には認識しますが、コンパイラのコマンドラインオプションである`-march`（ターゲットアーキテクチャを指定）のデフォルト値を適切に更新しませんでした。多くのLinuxディストリビューションでは、ClangがデフォルトでARMv4tアーキテクチャ向けにコンパイルされており、これは`BLX`命令が利用できない古いアーキテクチャです。
*   **ビルド失敗**: 結果として、Clangの統合アセンブラが、実際にはサポートされていないARMv4tアーキテクチャ向けにコードをアセンブルしようとし、`BLX`命令のような新しい命令に遭遇するとビルドが失敗しました。これはClang側のバグと見なされました。
*   **Issue 8348**: この問題はGoのIssueトラッカーで[Issue 8348](https://github.com/golang/go/issues/8348)として報告され、このコミットはその修正として行われました。
*   **`ldelf.c`の必要性**: Clang 3.4以降が生成するシンボルテーブルエントリの形式が変更されたため、Goリンカがこれらの新しいエントリを正しく処理できるように`ldelf.c`の調整も必要となりました。特に、ARMのbinutilsが生成するマッピングシンボル（`$a`, `$d`）の処理方法に変更が生じました。

これらの問題に対処することで、GoのビルドがClang 3.4以降を使用する環境でも安定して動作するようにすることが目的でした。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を把握しておく必要があります。

*   **Cgo**:
    *   Go言語とC言語（またはC++）のコードを相互に呼び出すためのGoのツールです。GoプログラムからCライブラリを呼び出したり、CプログラムからGo関数を呼び出したりする際に使用されます。
    *   `cmd/cgo`は、GoとCの間のインターフェースコードを生成し、コンパイルとリンクを調整します。
    *   「cgo assembly shim」とは、Cgoが生成するアセンブリコードの一部で、GoとCの間の呼び出し規約の変換などを行います。

*   **Clang**:
    *   LLVMプロジェクトの一部であるC、C++、Objective-C、Objective-C++コンパイラです。GCCの代替として広く使用されています。
    *   **統合アセンブラ (Integrated Assembler)**: Clangの機能の一つで、アセンブリコードをコンパイルする際に、外部のアセンブラツール（例: GNU `as`）を呼び出す代わりに、コンパイラ自身がアセンブラの機能を持つものです。これにより、コンパイルプロセスが効率化されます。Clang 3.4でデフォルトで有効になりました。

*   **アセンブラディレクティブとコンパイラオプション**:
    *   **.arch ディレクティブ**: アセンブリ言語のソースコード内で使用されるディレクティブ（指示子）の一つで、ターゲットとするCPUアーキテクチャを指定します。例えば、`.arch armv5te`のように記述されます。
    *   **`-march` オプション**: GCCやClangなどのコンパイラで使用されるコマンドラインオプションで、生成するコードのターゲットCPUアーキテクチャを指定します。例えば、`-march=armv5te`のように指定します。このオプションは、コンパイラがどの命令セットやCPUの機能をターゲットにするかを決定するために重要です。

*   **ARMアーキテクチャ**:
    *   モバイルデバイスなどで広く使用されているRISCベースのCPUアーキテクチャです。
    *   **ARMv4t, ARMv5**: ARMアーキテクチャの異なるバージョンです。ARMv4tは古いバージョンで、ARMv5はそれ以降のバージョンです。新しいバージョンでは、より多くの命令や機能が追加されています。
    *   **BLX 命令**: ARMv5T以降のARMアーキテクチャで導入された命令です。これは「Branch with Link and Exchange」の略で、関数呼び出しを行う際に、リンクレジスタ（`lr`）にリターンアドレスを保存し、さらにARMモードとThumbモードの間で切り替える機能を持っています。古いARMv4tではこの命令は存在しません。

*   **ELF (Executable and Linkable Format)**:
    *   Unix系システムで広く使用されている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準ファイル形式です。
    *   **シンボルテーブル (Symbol Table)**: ELFファイル内に含まれるセクションの一つで、プログラム内の関数や変数などのシンボル（名前）とそのアドレスや型などの情報が格納されています。リンカはシンボルテーブルを使用して、異なるオブジェクトファイル間の参照を解決します。
    *   **シンボルテーブルエントリ (Symtab Entries)**: シンボルテーブル内の個々のエントリで、各シンボルに関する詳細情報を含みます。

*   **`ldelf.c`**:
    *   Go言語のリンカ（`cmd/ld`）の一部で、ELF形式のオブジェクトファイルやライブラリからシンボル情報を読み取り、処理する役割を担っています。

*   **`strcmp` と `strncmp`**:
    *   C言語の標準ライブラリ関数です。
    *   `strcmp(s1, s2)`: 2つの文字列`s1`と`s2`を比較し、完全に一致するかどうかを判断します。
    *   `strncmp(s1, s2, n)`: 2つの文字列`s1`と`s2`の先頭`n`文字だけを比較します。このコミットでは、特定のシンボル名が「$a」または「$d」で始まるかどうかをチェックするために、完全一致ではなく前方一致が必要になったため、`strcmp`から`strncmp`への変更が行われました。

*   **Binutils**:
    *   GNUプロジェクトが提供するバイナリツール群で、アセンブラ（`as`）、リンカ（`ld`）などが含まれます。ARMアーキテクチャ向けにコンパイルされたBinutilsは、特定の「マッピングシンボル」（例: `$a`, `$d`）を生成することがあります。これらは、コードとデータのセクションの境界を示すために使用される特殊なシンボルです。`$a`はARM (A32) 命令のシーケンスの開始を示し、`$d`はデータアイテムのシーケンスの開始を示します。これらは、逆アセンブラがコードとデータセクションを正確に区別し、命令セットの状態（ARMとThumbなど）を切り替えるのに役立ちます。

## 技術的詳細

このコミットの技術的詳細は、Clangの統合アセンブラの挙動と、Goリンカがシンボルを処理する方法の2つの側面に焦点を当てています。

### Clangの統合アセンブラの問題

Clang 3.4で導入された統合アセンブラは、アセンブリコードを直接コンパイルできるため、ビルドチェーンを簡素化し、パフォーマンスを向上させることが期待されました。しかし、ARMアーキテクチャにおいて、この統合アセンブラには特定のバグがありました。

1.  **`.arch`ディレクティブの誤解釈**: アセンブリソースコードには、ターゲットアーキテクチャを指定する`.arch`ディレクティブが含まれることがあります。例えば、GoのcgoアセンブリシムがARMv5以降の命令セットを使用する場合、`.arch armv5te`のようなディレクティブが含まれる可能性があります。Clangの統合アセンブラは、このディレクティブを構文的には認識しますが、実際にアセンブルするコードの命令セットを、このディレクティブで指定されたアーキテクチャに切り替えることを怠っていました。
2.  **`-march`オプションとの不整合**: 一方、Clangコンパイラはコマンドラインで`-march`オプションを受け入れ、これによってターゲットアーキテクチャを決定します。しかし、多くのディストリビューションでClangがデフォルトでARMv4t（`BLX`命令をサポートしない古いアーキテクチャ）向けにコンパイルされていたため、たとえアセンブリコードが`.arch armv5te`を含んでいても、統合アセンブラは依然としてARMv4tの制約内でアセンブルしようとしました。
3.  **`BLX`命令の使用とビルド失敗**: Goのcgoアセンブリシムは、ARMv5以降で利用可能な`BLX`命令を使用することがありました。統合アセンブラがARMv4tのコンテキストで`BLX`命令に遭遇すると、その命令が認識できないため、アセンブルエラーが発生し、結果としてGoのビルドが失敗しました。

この問題はClangのバグと判断されたため、Go側では一時的な回避策として、cgoがClangを使用している場合に統合アセンブラを無効にするオプション`-no-integrated-as`を追加することにしました。これにより、Clangは外部のアセンブラ（通常はGNU `as`）を呼び出すようになり、この外部アセンブラは`.arch`ディレクティブを正しく解釈し、適切なアーキテクチャ向けのコードを生成できます。

### `ldelf.c`におけるシンボル処理の変更

Clang 3.4以降は、以前のバージョンと比較して、ELFシンボルテーブルに「より奇妙な」エントリを生成するようになりました。これは、特にARMアーキテクチャのbinutilsが生成する特殊なマッピングシンボル（`$a`や`$d`など）の処理に影響を与えました。

*   **マッピングシンボル**: ARMのbinutilsは、コードセクションとデータセクションの境界を示すために、`$a`（ARMコード）や`$d`（データ）のような特殊なローカルシンボルを生成します。これらはデバッグ情報やリンカの内部処理で使用されることがありますが、Goリンカが通常のシンボルとして誤って解釈すると問題が生じる可能性があります。
*   **`strcmp`から`strncmp`への変更**: 以前の`ldelf.c`では、これらのマッピングシンボルを無視するために、シンボル名が`"$a"`または`"$d"`と**完全に一致する**かどうかを`strcmp`でチェックしていました。しかし、Clang 3.4以降が生成するシンボルエントリでは、これらのマッピングシンボルが`"$a"`や`"$d"`で始まるが、その後にさらに文字が続く形式（例: `$a.some_suffix`）で現れるようになりました。
*   **部分一致の必要性**: この変更に対応するため、シンボル名が`"$a"`または`"$d"`で**始まる**かどうかをチェックするようにロジックを変更する必要がありました。`strncmp`関数は、指定された文字数だけ文字列を比較するため、この部分一致の要件を満たします。具体的には、`strncmp(sym->name, "$a", 2)`とすることで、シンボル名が`"$a"`で始まるかどうかを安全にチェックできるようになりました。これにより、Goリンカは新しい形式のシンボルエントリでも、これらの特殊なマッピングシンボルを正しく識別し、無視できるようになりました。

これらの変更は、Goのビルドシステムが最新のコンパイラツールチェーンと互換性を保ち、安定した動作を保証するために不可欠でした。

## コアとなるコードの解説

### `src/cmd/cgo/gcc.go`の変更

このファイルは、cgoがGCC（または互換性のあるコンパイラ、この場合はClang）を呼び出す際のコマンドライン引数を生成するロジックを含んでいます。

*   **変更前**:
    ```go
    case "arm":
        return []string{"-marm"} // not thumb
    ```
    ARMアーキテクチャの場合、単に`-marm`オプションを返していました。これは、ARMモードでコンパイルすることを指示するものです（Thumbモードではない）。

*   **変更後**:
    ```go
    case "arm":
        args := []string{"-marm"} // not thumb
        if strings.Contains(p.gccBaseCmd()[0], "clang") {
            // The clang integrated assembler understands the .arch directive
            // but does not appear to honor it, so disable it. Issue 8348.
            args = append(args, "-no-integrated-as")
        }
        return args
    ```
    1.  まず、`args`というスライスに`-marm`を初期値として設定します。
    2.  `p.gccBaseCmd()[0]`は、cgoが使用するコンパイラの実行ファイル名（例: `clang`や`gcc`）を返します。
    3.  `strings.Contains(p.gccBaseCmd()[0], "clang")`によって、現在使用しているコンパイラがClangであるかどうかをチェックします。
    4.  もしClangであれば、`args`スライスに`-no-integrated-as`オプションを追加します。このオプションは、Clangの統合アセンブラを無効にし、代わりに外部のアセンブラ（通常はGNU `as`）を使用するように強制します。これにより、Clangの統合アセンブラが`.arch`ディレクティブを正しく処理しない問題が回避されます。コメントにもあるように、これはIssue 8348の修正です。

この変更により、ARM環境でClangを使用している場合に、cgoが生成するアセンブリシムのビルドが安定するようになりました。

### `src/cmd/ld/ldelf.c`の変更

このファイルは、GoリンカがELF形式のオブジェクトファイルからシンボル情報を読み取る部分です。

*   **変更前**:
    ```c
    if(!(thechar == '5' && (strcmp(sym->name, "$a") == 0 || strcmp(sym->name, "$d") == 0))) // binutils for arm generate these mapping symbols, ignore these
    ```
    この行は、ローカルシンボル（`ElfSymBindLocal`）を処理する際に、特定の条件を満たすシンボルを無視するためのものです。
    *   `thechar == '5'`は、ターゲットアーキテクチャがARMであることを示唆しています（Goの内部的なアーキテクチャ識別子）。
    *   `strcmp(sym->name, "$a") == 0 || strcmp(sym->name, "$d") == 0`は、シンボル名が`"$a"`または`"$d"`と**完全に一致する**場合に真となります。これは、ARMのbinutilsが生成する特殊なマッピングシンボルを無視するためのロジックでした。

*   **変更後**:
    ```c
    if(!(thechar == '5' && (strncmp(sym->name, "$a", 2) == 0 || strncmp(sym->name, "$d", 2) == 0))) // binutils for arm generate these mapping symbols, ignore these
    ```
    `strcmp`が`strncmp`に変更され、比較する文字数が`2`に指定されました。
    *   `strncmp(sym->name, "$a", 2) == 0`は、シンボル名が`"$a"`で**始まる**場合に真となります。
    *   `strncmp(sym->name, "$d", 2) == 0`は、シンボル名が`"$d"`で**始まる**場合に真となります。
    この変更は、Clang 3.4以降が生成するシンボルエントリにおいて、マッピングシンボルが`"$a"`や`"$d"`の後にさらに文字が続く形式（例: `$a.some_suffix`）で現れるようになったためです。`strncmp`を使用することで、これらの新しい形式のシンボルでも、先頭の`"$a"`または`"$d"`を正しく識別し、リンカがそれらを無視できるようにしています。

この変更により、GoリンカはClang 3.4以降でコンパイルされたオブジェクトファイルに含まれる新しい形式のシンボルテーブルエントリを正しく処理できるようになり、リンカのエラーや誤ったシンボル解決を防ぎます。

## 変更の背景

Go言語のツールチェインには、コードの潜在的なバグや疑わしい構成を検出するための静的解析ツール `vet` が含まれています。`vet` は、Goの慣習に反するコードや、実行時に問題を引き起こす可能性のあるコードパターンを特定するのに役立ちます。

このコミットの背景には、`crypto/aes` パッケージ内の `gcm_amd64.s` というアセンブリファイルが `vet` ツールによって警告を出していたという問題があります。`gcm_amd64.s` は、AES-GCM (Galois/Counter Mode) 暗号化アルゴリズムのパフォーマンスクリティカルな部分をx86-64アセンブリで実装したものです。アセンブリコードは、Goコンパイラが生成するコードよりもさらに低レベルでハードウェアに最適化された命令を使用するため、非常に高速な処理が可能です。しかし、その分、記述が複雑で、Goのランタイムやコンパイラとのインターフェースに関する厳密な規則に従う必要があります。

特に、GoのアセンブリでGoの関数に渡されるスライス（`[]byte` など）を扱う際には、その内部構造（データへのポインタ、長さ、容量）を正しく解釈し、適切なオフセットでアクセスする必要があります。`vet` は、このアセンブリコードがスライス引数のサイズを誤って解釈していることを検出し、警告を発していました。誤った引数サイズでのアクセスは、メモリ破壊、不正なデータ処理、さらにはセキュリティ脆弱性につながる可能性があるため、暗号化ライブラリにおいては特に重大な問題です。

このコミットは、これらの `vet` 警告を解消し、アセンブリコードがGoのランタイム規約に完全に準拠するようにすることで、`crypto/aes` パッケージの堅牢性と信頼性を向上させることを目的としています。

## 前提知識の解説

### Goの `vet` ツール

`vet` はGo言語の標準的な静的解析ツールです。コンパイルは通るものの、潜在的なバグや非効率なコード、Goの慣習に反する記述などを検出します。例えば、フォーマット文字列の引数ミス、ロックの誤用、到達不能なコード、そして本件のようなアセンブリコードにおける引数サイズの不一致などを警告します。開発者がコードの品質を維持し、早期に問題を特定するのに不可欠なツールです。

### Goのアセンブリ言語

Go言語は、パフォーマンスが非常に重要な部分（例: 暗号化、ランタイムのスケジューラ、GCなど）で、Go独自の擬似アセンブリ言語を使用します。これは、一般的なアセンブリ言語（AT&T構文やIntel構文）とは異なり、Goのコンパイラとリンカが理解する独自の構文を持っています。Goのアセンブリは、Goの関数呼び出し規約（引数と戻り値のスタック上の配置）に厳密に従う必要があります。特に、Goの関数に渡される引数は、`FP` (Frame Pointer) を基準としたオフセットでアクセスされます。

### AES-GCM (Galois/Counter Mode)

AES (Advanced Encryption Standard) は、広く使われているブロック暗号アルゴリズムです。GCM (Galois/Counter Mode) は、AESと組み合わせて使用される認証付き暗号化モードです。GCMは、データの機密性（暗号化）と完全性・認証（改ざん検出）の両方を提供します。これは、現代のセキュアな通信プロトコル（TLSなど）で広く利用されており、非常に高いパフォーマンスが求められます。そのため、Goの `crypto/aes` パッケージでは、x86-64プロセッサのAES-NI命令セットを活用するために、アセンブリ言語で最適化された実装が提供されています。

### Goのアセンブリにおける引数の渡し方とスライス構造

Goの関数がアセンブリ関数を呼び出す際、引数はスタック上に配置されます。スライス（`[]byte`など）は、Goの内部では以下のような構造を持つデータ型です。

```go
type SliceHeader struct {
    Data uintptr // データへのポインタ
    Len  int     // スライスの長さ
    Cap  int     // スライスの容量
}
```

x86-64アーキテクチャでは、`uintptr` と `int` は通常8バイト（64ビット）です。したがって、スライスはスタック上で24バイト（ポインタ8バイト + 長さ8バイト + 容量8バイト）を占めます。アセンブリコードからスライス引数にアクセスする場合、例えば `ks []uint32` という引数がある場合、`ks` はスタック上の特定のオフセットに配置され、そのオフセットから `ks.Data`、`ks.Len`、`ks.Cap` にアクセスするために、それぞれ `ks_base`、`ks_len`、`ks_cap` といった擬似的なシンボルが使用されます。

*   `ks_base+オフセット(FP)`: スライスのデータへのポインタ
*   `ks_len+オフセット(FP)`: スライスの長さ
*   `ks_cap+オフセット(FP)`: スライスの容量

このコミットでは、これらの `_base` や `_len` サフィックスが正しく使われていなかったために、`vet` が警告を発していました。

## 技術的詳細

このコミットで修正された問題は、GoのアセンブリコードがGoの関数に渡されたスライス引数の内部構造を誤って解釈していたことに起因します。具体的には、`src/crypto/aes/gcm_amd64.s` 内の複数の関数（`aesEncBlock`, `gcmAesInit`, `gcmAesData`, `gcmAesEnc`, `gcmAesDec`）で、スライス引数のデータポインタや長さにアクセスする際に、`ks+オフセット(FP)` のような形式で直接アクセスしていました。

しかし、Goのアセンブリでは、スライス引数 `s` のデータポインタは `s_base`、長さは `s_len`、容量は `s_cap` というシンボルを通じてアクセスするのが正しい慣習です。これらのシンボルは、Goコンパイラがアセンブリ関数を呼び出す際に、スライスの各要素がスタック上のどこに配置されるかを抽象化したものです。

例えば、`ks []uint32` というスライス引数がある場合、`ks+16(FP)` のように直接アクセスすると、それはスライス全体の先頭から16バイト目のデータにアクセスしようとします。しかし、Goの呼び出し規約では、スライスのデータポインタ、長さ、容量がそれぞれ8バイトずつ連続して配置されるため、`ks` の先頭は `ks_base` に対応し、`ks_base` のオフセットから `ks_len` や `ks_cap` にアクセスする必要があります。

この誤ったアクセス方法は、`vet` ツールによって「incorrect argument size」として検出されました。これは、アセンブリコードが期待する引数のレイアウトと、Goコンパイラが実際に引数を配置するレイアウトとの間に不一致があったためです。結果として、アセンブリコードは意図しないメモリ領域を読み書きする可能性があり、これは暗号化処理の正確性を損ない、セキュリティ上のリスクを招く恐れがありました。

修正は、これらの直接的なオフセットアクセスを、`ks_base+オフセット(FP)` や `ks_len+オフセット(FP)` のように、Goのアセンブリにおけるスライス構造の正しいアクセス方法に置き換えることで行われました。これにより、アセンブリコードはGoのランタイム規約に完全に準拠し、`vet` 警告が解消され、コードの堅牢性が向上しました。

また、`gcmAesEnc` と `gcmAesDec` 関数のスタックフレームサイズも調整されています。これは、引数のアクセス方法の変更に伴い、スタック上の変数の配置やサイズ計算が影響を受けたため、正しいスタックフレームサイズを反映させるための修正です。

## コアとなるコードの解説

このコミットの主要な変更は、Goのアセンブリコードにおけるスライス引数へのアクセス方法の修正です。

1.  **スライス引数へのアクセス修正**:
    *   変更前: `MOVQ ks+16(FP), DX` や `MOVQ data+16(FP), autLen` のように、スライス引数名に直接オフセットを加えてアクセスしていました。
    *   変更後: `MOVQ ks_base+16(FP), DX` や `MOVQ ks_len+24(FP), CX`、`MOVQ data_base+8(FP), aut`、`MOVQ data_len+16(FP), autLen` のように、`_base` や `_len` サフィックスを付加したシンボルを使用するように変更されました。
    
    これは、Goのアセンブリにおけるスライスの内部構造（`Data`, `Len`, `Cap`）への正しいアクセス方法に準拠するための修正です。`ks` のようなスライス引数は、スタック上で `ks_base` (データポインタ)、`ks_len` (長さ)、`ks_cap` (容量) の順に配置されます。したがって、スライスのデータポインタにアクセスするには `ks_base` を、長さにアクセスするには `ks_len` を使用する必要があります。この修正により、アセンブリコードがGoのランタイムが期待する引数のレイアウトと一致するようになり、`vet` 警告が解消されました。

2.  **スタックフレームサイズの調整**:
    *   `TEXT ·gcmAesEnc(SB),0,$256-144` が `TEXT ·gcmAesEnc(SB),0,$256-96` に変更。
    *   `TEXT ·gcmAesDec(SB),0,$128-144` が `TEXT ·gcmAesDec(SB),0,$128-96` に変更。
    
    `$256-144` や `$128-144` の部分は、アセンブリ関数のスタックフレームサイズを示しています。`$framesize-argsize` の形式で、`framesize` はローカル変数に使用されるスタック領域のサイズ、`argsize` は引数に使用されるスタック領域のサイズです。この修正は、スライス引数のアクセス方法の変更に伴い、Goコンパイラがアセンブリ関数に渡す引数のサイズ計算が影響を受けたため、正しいスタックフレームサイズを反映させるためのものです。これにより、スタックの破損や不正なメモリアクセスを防ぎ、関数の呼び出し規約が正しく維持されます。

これらの変更は、Goの低レベルなアセンブリコードがGoランタイムの厳密な規約に準拠することを保証し、特に暗号化のようなセキュリティクリティカルなコンポーネメントの正確性と信頼性を高める上で非常に重要です。

# [インデックス 2538] ファイルの概要

このコミットは、Go言語のARMアーキテクチャ向けリンカである `5l` において、不正なオペランドの組み合わせ（"bad op combination"）に遭遇した際のデバッグ出力を強化することを目的としています。具体的には、診断メッセージにオペランドの型をより分かりやすい形式で表示するための新しいフォーマット指定子 `%O` を追加しています。

## 変更の背景

Go言語のコンパイラツールチェーンは、初期の段階でPlan 9のツールチェーン（`8c`, `8l`, `6c`, `6l` など）の影響を強く受けていました。`5l` はARMアーキテクチャ向けのリンカであり、アセンブリコードをリンクして実行可能ファイルを生成する役割を担います。

リンカがアセンブリ命令を処理する際、命令コード（opcode）とそれに続くオペランド（operand）の組み合わせが、そのアーキテクチャの命令セットアーキテクチャ（ISA）の規則に準拠している必要があります。例えば、特定の命令はレジスタをオペランドとしてしか取れない、あるいは即値の範囲が限定されている、といった制約があります。これらの制約に違反する「不正なオペランドの組み合わせ」が発生した場合、リンカはエラーを報告する必要があります。

このコミット以前は、`5l` がこのような不正な組み合わせに遭遇した際に出力されるデバッグ情報が不足しており、問題の根本原因を特定するのが困難でした。特に、オペランドの「型」（例：レジスタ、即値、メモリ参照など）が数値として出力されるだけで、その数値が何を意味するのかを開発者が手動で調べる必要がありました。

この変更の背景には、リンカのエラー診断能力を向上させ、開発者がより迅速に問題をデバッグできるようにするという明確な目的があります。特に、新しいアーキテクチャのサポートや命令セットの拡張が行われる際には、このような詳細なデバッグ出力が非常に重要になります。

## 前提知識の解説

### Go言語のツールチェーンとPlan 9の影響

Go言語のコンパイラとリンカは、Rob Pikeらが開発したPlan 9オペレーティングシステムのツールチェーンにルーツを持っています。Plan 9のツールチェーンは、シンプルさ、移植性、そして強力なテキスト処理能力を特徴としていました。Goのツールチェーンもこれらの特性を受け継ぎ、特にアセンブラやリンカの設計にその影響が色濃く残っています。

-   **`5l`**: Go言語のツールチェーンにおけるARMアーキテクチャ向けのリンカです。`5` はARMを指すPlan 9の慣例に由来します（例: `8` はx86、`6` はamd64）。
-   **`diag` 関数**: Goのツールチェーン内で広く使われている診断メッセージ出力関数です。`printf` のようなフォーマット文字列と可変引数を取り、エラーやデバッグ情報を標準エラー出力に出力します。

### Plan 9 Cの `fmtinstall` とカスタムフォーマット指定子

Plan 9 C言語の標準ライブラリには、`fmtinstall` という関数があり、`printf` ファミリの関数にカスタムのフォーマット指定子を追加する機能を提供します。これにより、開発者は独自のデータ型や構造体を、特定のフォーマットで文字列に変換して出力できるようになります。

-   **`Fmt` 構造体**: `fmtinstall` で登録される変換関数（`Xconv`）に渡される構造体で、出力バッファや引数リストなどの情報を含みます。
-   **`fmtstrcpy`**: `Fmt` 構造体を使って文字列をフォーマットバッファにコピーするヘルパー関数です。
-   **カスタムフォーマット指定子**: `%d` (整数), `%s` (文字列) などと同様に、開発者が `%P` や `%S` のように独自の指定子を定義できます。このコミットでは `%O` が追加されています。

### オペランドの型 (`C_type` 定数)

アセンブリ言語の命令は、操作対象となるデータ（オペランド）を持ちます。オペランドには様々な種類があり、それぞれが異なる「型」を持ちます。リンカやアセンブラの内部では、これらの型は通常、列挙型（enum）やマクロ定義された整数定数として表現されます。

このコミットで言及されている `C_type` 定数は、`5l` リンカが内部的にオペランドの種類を識別するために使用する定数群です。例えば、`C_REG` はレジスタ、`C_CON` は定数（即値）、`C_ADDR` はメモリアドレスなどを表します。これらの定数は、リンカが命令の妥当性をチェックしたり、適切な機械語コードを生成したりする上で不可欠な情報です。

## 技術的詳細

このコミットの主要な変更点は、`5l` リンカのデバッグ出力に、オペランドの型を人間が読みやすい文字列で表示する機能を追加したことです。

1.  **`src/cmd/5l/l.h` の変更**:
    *   新しいフォーマット指定子 `%O` に対応する変換関数 `Oconv` のプロトタイプ宣言が追加されました。
    ```c
    int     Oconv(Fmt*);
    ```

2.  **`src/cmd/5l/list.c` の変更**:
    *   `listinit` 関数内で、`Oconv` 関数が `%O` フォーマット指定子に登録されました。これにより、`diag` 関数などのフォーマット文字列で `%O` を使用できるようになります。
    ```c
    fmtinstall('O', Oconv);          // C_type constants
    ```
    *   `cnames` という静的グローバル配列が追加されました。この配列は、`C_type` 定数（オペランドの型を表す整数値）を、対応する文字列名（例: `C_REG` を `"C_REG"`）にマッピングします。配列のインデックスが `C_type` 定数に対応し、その値が文字列リテラルへのポインタとなります。
    ```c
    static char*
    cnames[] =
    {
        [C_ADDR]        = "C_ADDR",
        [C_BCON]        = "C_BCON",
        // ... (他のC_type定数も同様にマッピング)
        [C_SROREG]      = "C_SROREG"
    };
    ```
    *   `Oconv` 関数が実装されました。この関数は `fmtinstall` によって `%O` フォーマット指定子に関連付けられます。
        *   `va_arg(fp->args, int)` を使用して、フォーマット引数リストから整数値（`C_type` 定数）を取得します。
        *   取得した整数値が `cnames` 配列の有効なインデックス範囲内であり、かつ対応する文字列が `nil` でない場合、その文字列を `fmtstrcpy` を使って出力バッファにコピーします。
        *   無効なインデックスや `nil` の場合は、`"C_%d"` の形式で元の整数値を文字列として出力します。これにより、未知の `C_type` 定数に対しても情報が失われないようになっています。

3.  **`src/cmd/5l/span.c` の変更**:
    *   `oplook` 関数内の `diag` 関数の呼び出し箇所が変更されました。以前はオペランドの型を `%d` (整数) で出力していましたが、これを新しく追加された `%O` フォーマット指定子に変更しました。
    ```diff
    -   diag("illegal combination %A %d %d %d, %d %d",
    +   diag("illegal combination %A %O %O %O, %d %d",
            p->as, a1, a2, a3, p->from.type, p->to.type);
    ```
    *   `oplook` 関数は、アセンブリ命令 `p` のオペランド `a1`, `a2`, `a3` の組み合わせが不正であると判断した場合にこの `diag` メッセージを出力します。変更前は `a1`, `a2`, `a3` の整数値がそのまま表示されていましたが、変更後は `Oconv` 関数によってこれらの整数値が対応する `C_type` 定数の文字列名（例: `"C_REG"`, `"C_CON"`）に変換されて表示されるようになります。

## コアとなるコードの解説

このコミットの核心は、`5l` リンカが不正な命令オペランドの組み合わせを検出した際に、より詳細で人間が理解しやすいデバッグ情報を出力するように変更された点にあります。

以前は、`span.c` の `oplook` 関数内で `diag` が呼び出される際、オペランドの型 (`a1`, `a2`, `a3`) は単なる整数値として `%d` フォーマットで出力されていました。例えば、`illegal combination ADD 1 2 3, 4 5` のようなメッセージが出力された場合、開発者は `1`, `2`, `3` といった数値が具体的にどのオペランド型（レジスタ、即値、メモリ参照など）を意味するのかを、ソースコードやドキュメントを参照して手動で調べる必要がありました。これはデバッグ作業において大きな負担となります。

このコミットによって導入された `%O` フォーマット指定子と `Oconv` 関数、そして `cnames` 配列は、この問題を解決します。

1.  **`cnames` 配列**: `C_type` 定数（オペランドの型を表す整数値）と、それに対応する人間が読みやすい文字列（例: `C_REG` -> `"C_REG"`）とのマッピングを提供します。これは、リンカの内部表現を外部に分かりやすく提示するための辞書のような役割を果たします。
2.  **`Oconv` 関数**: `diag` 関数が `%O` を見つけると、この `Oconv` 関数が呼び出されます。`Oconv` は、引数として渡された `C_type` 定数（整数値）を `cnames` 配列を使って対応する文字列に変換します。もし未知の `C_type` 定数が渡された場合でも、`"C_%d"` の形式で元の整数値を表示するため、情報が失われることはありません。
3.  **`oplook` 関数の変更**: `diag` のフォーマット文字列が `%d` から `%O` に変更されたことで、不正なオペランドの組み合わせが検出された際に、例えば `illegal combination ADD C_REG C_CON C_ADDR, 4 5` のような、より意味のあるデバッグメッセージが出力されるようになります。これにより、開発者は一目でどのオペランドの型が問題を引き起こしているのかを把握でき、デバッグの効率が大幅に向上します。

この変更は、Goツールチェーンの堅牢性と開発者体験を向上させるための、地味ながらも非常に重要な改善と言えます。特に、低レベルなアセンブリやリンカの挙動をデバッグする際には、このような詳細な診断情報が不可欠です。

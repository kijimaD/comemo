# [インデックス 23470] ファイルの概要

このコミットは、Goコンパイラの内部SSA（Static Single Assignment）パッケージにおけるテストの記述を簡素化するためのユーティリティ関数群と、SSA形式の関数（`Func`）の等価性を比較する`Equiv`関数を導入します。これにより、SSA変換や最適化のテストコードがより読みやすく、保守しやすくなります。

## 元コミット内容

このコミットは、Goコンパイラの`cmd/internal/ssa`パッケージに、テスト目的で`Func`オブジェクトを構築するためのユーティリティ関数群を追加します。これにより、SSA形式の関数をより簡潔かつ宣言的に定義できるようになります。具体的には、`Fun`, `Bloc`, `Valu`, `Goto`, `If`, `Exit`といった関数が導入され、これらを組み合わせることで、複雑なSSAグラフをテキストベースの記述に近い形で表現できるようになります。

また、2つの`Func`オブジェクトが等価であるかをテストするための`Equiv`関数も追加されています。これは、コンパイラの最適化パスがSSAグラフを正しく変換したことを検証する際に非常に有用です。

## 変更の背景

GoコンパイラのSSAバックエンドは、コードの最適化において重要な役割を担っています。SSA形式のコードは、コンパイラがデータフロー解析や様々な最適化を効率的に行うことを可能にします。しかし、SSA形式の`Func`オブジェクトをプログラム的に構築し、テストケースとして使用することは、非常に冗長でエラーが発生しやすい作業でした。

以前のテストコード（`deadcode_test.go`の変更前を参照）では、`Func`、`Block`、`Value`といったオブジェクトを直接インスタンス化し、手動でリンクしていく必要がありました。これは、特に複雑な制御フローやデータフローを持つ関数を表現する場合に、コードの可読性を著しく低下させ、テストの記述と保守を困難にしていました。

このコミットの背景には、SSAバックエンドのテスト容易性を向上させ、開発者がより効率的にコンパイラの最適化パスを検証できるようにするという目的があります。簡潔なテスト記述は、バグの発見を容易にし、将来的なコンパイラの改善を加速させます。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの最適化において広く用いられる中間表現（IR）の一種です。その主要な特徴は以下の通りです。

*   **単一割り当て**: 各変数はプログラム内で一度だけ値を割り当てられます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が容易になります。
*   **Φ関数 (Phi function)**: 制御フローグラフ（CFG）において、複数のパスが合流する点（支配フロンティア）で、同じ論理変数に対応する異なるSSA変数の中から適切なものを選択するために導入されます。例えば、`x3 = Φ(x1, x2)`は、`x1`と`x2`のどちらかの値が`x3`に割り当てられることを意味します。

GoコンパイラのSSAバックエンドは、GoのソースコードをSSA形式に変換し、その上で様々な最適化（デッドコード削除、定数伝播、共通部分式除去など）を適用します。

### 2. GoコンパイラのSSAパッケージ (`cmd/internal/ssa`)

`cmd/internal/ssa`パッケージは、Goコンパイラの内部でSSA形式のコードを表現・操作するためのデータ構造とアルゴリズムを提供します。

*   **`Func`**: SSA形式の関数全体を表す主要な構造体です。関数内のすべてのブロックと値を管理します。
*   **`Block`**: 制御フローグラフの基本ブロックを表します。基本ブロックは、入り口と出口が一つずつあり、内部に分岐を含まない一連の命令シーケンスです。`BlockPlain`（無条件ジャンプ）、`BlockIf`（条件分岐）、`BlockExit`（関数終了）などの種類があります。
*   **`Value`**: SSA形式における単一の操作または値を表します。これには、定数、関数引数、算術演算の結果などが含まれます。各`Value`は、その操作の種類（`Op`）、型（`Type`）、補助情報（`Aux`）、および引数（`Args`）を持ちます。

### 3. 制御フローグラフ (Control Flow Graph, CFG)

CFGは、プログラムの実行可能なパスを抽象的に表現するグラフです。ノードは基本ブロックを表し、エッジはブロック間の制御フローの遷移を表します。SSA形式のコードは、このCFG上で定義されます。

### 4. テスト駆動開発とコンパイラテスト

コンパイラの開発において、各最適化パスが正しく機能することを保証するために、厳密なテストが不可欠です。特にSSAのような複雑な中間表現を扱う場合、テストケースの作成は大きな課題となります。このコミットで導入されるユーティリティは、SSAグラフを直接構築する手間を減らし、テストコードの記述を簡素化することで、テスト駆動開発を促進します。

## 技術的詳細

このコミットの核となるのは、`src/cmd/internal/ssa/func_test.go`で定義される一連のヘルパー関数です。

### `Fun` 関数

`Fun`関数は、SSA形式の`Func`オブジェクトを構築するためのエントリポイントです。
```go
func Fun(entry string, blocs ...bloc) fun
```
*   `entry`: エントリブロックの名前を指定します。
*   `blocs`: `Bloc`関数によって定義されたブロックのリストを受け取ります。
*   戻り値の`fun`構造体は、構築された`*Func`オブジェクトと、名前から`Block`や`Value`へのマップ（`blocks`と`values`）を含みます。これにより、テストコード内で特定のブロックや値に名前でアクセスできるようになります。

`Fun`の内部では、まずすべてのブロックと値が作成され、次にそれらの間の接続（制御フローとデータフロー）が確立されます。

### `Bloc` 関数

`Bloc`関数は、単一のSSA基本ブロックを定義します。
```go
func Bloc(name string, entries ...interface{}) bloc
```
*   `name`: ブロックの一意な名前を指定します。
*   `entries`: そのブロックに含まれる値の定義（`Valu`）と、ブロックの制御フロー（`Goto`, `If`, `Exit`）を指定します。
*   各ブロックは、`Goto`、`If`、`Exit`のいずれか一つで制御フローを定義する必要があります。

### `Valu` 関数

`Valu`関数は、SSA形式の単一の値を定義します。
```go
func Valu(name string, op Op, t Type, aux interface{}, args ...string) valu
```
*   `name`: 値の一意な名前を指定します。
*   `op`: 値の操作の種類（例: `OpArg`, `OpConst`, `OpAdd`）。
*   `t`: 値の型（例: `TypeMem`, `TypeBool`, `TypeInt64`）。
*   `aux`: 補助情報（定数値、メモリ参照など）。
*   `args`: この値が依存する他の値の名前のリスト。これにより、データフローが表現されます。

### 制御フロー定義関数 (`Goto`, `If`, `Exit`)

*   `Goto(succ string)`: 無条件ジャンプを表し、`BlockPlain`タイプのブロックを定義します。`succ`は次のブロックの名前です。
*   `If(cond, sub, alt string)`: 条件分岐を表し、`BlockIf`タイプのブロックを定義します。`cond`は条件を表す値の名前、`sub`と`alt`はそれぞれ真と偽の場合の次のブロックの名前です。
*   `Exit(arg string)`: 関数からの終了を表し、`BlockExit`タイプのブロックを定義します。`arg`は終了時のメモリ状態などを表す値の名前です。

これらの関数は、内部的に`bloc`, `ctrl`, `valu`というヘルパーストラクトを使用して、SSAグラフの構造を構築します。

### `Equiv` 関数

`Equiv`関数は、2つの`Func`オブジェクトが等価であるかを再帰的に比較します。
```go
func Equiv(f, g *Func) bool
```
この関数は、CFGの同型性（isomorphism）と、対応する値の等価性をチェックします。ただし、現在の実装では、値と先行ブロックの順序が同じであることも要求されます。これは、より厳密な比較であり、将来的に順序に依存しない同型性チェックに拡張される可能性がコメントで示唆されています。

`Equiv`は、`valcor`（値の対応付け）と`blkcor`（ブロックの対応付け）というマップを使用して、既に比較済みの要素を追跡し、無限ループを防ぎます。

## コアとなるコードの変更箇所

### `src/cmd/internal/ssa/deadcode_test.go`

このファイルでは、既存のデッドコード削除テストが、新しく導入されたユーティリティ関数を使用して書き直されています。

**変更前:**
`Func`、`Block`、`Value`を直接インスタンス化し、`NewBlock`、`NewValue`、`addEdge`といった低レベルなAPIを多数呼び出してSSAグラフを構築していました。

```go
func TestDeadLoop(t *testing.T) {
	f := new(Func)
	entry := f.NewBlock(BlockPlain)
	exit := f.NewBlock(BlockExit)
	f.Entry = entry
	addEdge(entry, exit)
	mem := entry.NewValue(OpArg, TypeMem, ".mem")
	exit.Control = mem

	// dead loop
	deadblock := f.NewBlock(BlockIf)
	addEdge(deadblock, deadblock)
	addEdge(deadblock, exit)

	// dead value in dead block
	deadval := deadblock.NewValue(OpConst, TypeBool, true)
	deadblock.Control = deadval
	// ...
}
```

**変更後:**
`Fun`, `Bloc`, `Valu`, `Goto`, `If`, `Exit`といった高レベルなユーティリティ関数を使用して、SSAグラフを宣言的に記述しています。

```go
func TestDeadLoop(t *testing.T) {
	fun := Fun("entry",
		Bloc("entry",
			Valu("mem", OpArg, TypeMem, ".mem"),
			Goto("exit")),
		Bloc("exit",
			Exit("mem")),
		// dead loop
		Bloc("deadblock",
			// dead value in dead block
			Valu("deadval", OpConst, TypeBool, true),
			If("deadval", "deadblock", "exit")))

	CheckFunc(fun.f)
	Deadcode(fun.f)
	CheckFunc(fun.f)

	for _, b := range fun.f.Blocks {
		if b == fun.blocks["deadblock"] {
			t.Errorf("dead block not removed")
		}
		// ...
	}
}
```
この変更により、テストコードの行数が大幅に削減され、SSAグラフの構造が直感的に理解できるようになりました。

## コアとなるコードの解説

### `func_test.go` の `Fun` 関数

`Fun`関数は、SSAグラフの構築プロセスを2つの主要なパスに分けています。

1.  **初期化パス**:
    *   `f := new(Func)`: 新しい`Func`オブジェクトを初期化します。
    *   `blocks := make(map[string]*Block)` と `values := make(map[string]*Value)`: 名前から実際の`Block`および`Value`オブジェクトへのマッピングを保持するためのマップを作成します。
    *   `for _, bloc := range blocs`: 引数として渡された各`bloc`定義をループ処理します。
        *   `b := f.NewBlock(bloc.control.kind)`: `Bloc`で指定された種類（`BlockPlain`, `BlockIf`など）に基づいて新しい`Block`を作成し、`blocks`マップに名前で登録します。
        *   `for _, valu := range bloc.valus`: 各ブロック内の`valu`定義をループ処理します。
            *   `values[valu.name] = b.NewValue(valu.op, valu.t, valu.aux)`: `Valu`で指定された操作、型、補助情報に基づいて新しい`Value`を作成し、`values`マップに名前で登録します。この時点では、`Value`の引数（`Args`）はまだ設定されません。

2.  **接続パス**:
    *   `f.Entry = blocks[entry]`: `Fun`の`entry`引数で指定された名前のブロックを、関数のエントリポイントとして設定します。
    *   `for _, bloc := range blocs`: 再度、各`bloc`定義をループ処理します。
        *   `b := blocks[bloc.name]`: 現在のブロックオブジェクトを取得します。
        *   **制御値の設定**: `if c.control != ""`: `Bloc`で制御値が指定されている場合（例: `If`関数の条件）、`values`マップから対応する`Value`オブジェクトを取得し、`b.Control`に設定します。
        *   **値の引数の設定**: `for _, valu := range bloc.valus`: 各ブロック内の`valu`定義をループ処理します。
            *   `v := values[valu.name]`: 現在の値オブジェクトを取得します。
            *   `for _, arg := range valu.args`: `Valu`で指定された引数名（他の値の名前）をループ処理します。
                *   `a, ok := values[arg]`: `values`マップから引数に対応する`Value`オブジェクトを取得します。
                *   `v.AddArg(a)`: 取得した引数`Value`を現在の`Value`の引数リストに追加します。これにより、データフローが確立されます。
        *   **後続ブロックの接続**: `for _, succ := range c.succs`: `Bloc`で指定された後続ブロックの名前をループ処理します。
            *   `addEdge(b, blocks[succ])`: `addEdge`ヘルパー関数を呼び出して、現在のブロックと後続ブロックの間に制御フローエッジを追加します。`addEdge`は、両方向のリンク（`b.Succs`と`c.Preds`）を設定します。

この2段階の構築プロセスにより、SSAグラフ内のすべての要素が正しく初期化され、相互に接続されます。

### `func_test.go` の `Equiv` 関数

`Equiv`関数は、2つの`Func`オブジェクト`f`と`g`が構造的および意味的に等価であるかを判断します。

*   **対応付けマップ**: `valcor` (Value correlation) と `blkcor` (Block correlation) という2つのマップを使用します。これらは、`f`の要素が`g`のどの要素に対応するかを記録し、既に比較した要素を再帰的に処理する際の無限ループを防ぎます。
*   **`checkVal` 関数**: 2つの`Value`オブジェクトが等価であるかを再帰的にチェックします。
    *   `fv.Op != gv.Op || fv.Type != gv.Type`: 操作の種類と型が一致するかを確認します。
    *   `!reflect.DeepEqual(fv.Aux, gv.Aux)`: 補助情報がディープイコールで一致するかを確認します。
    *   `len(fv.Args) != len(gv.Args)`: 引数の数が一致するかを確認します。
    *   `!checkVal(fv.Args[i], gv.Args[i])`: 各引数を再帰的に比較します。
*   **`checkBlk` 関数**: 2つの`Block`オブジェクトが等価であるかを再帰的にチェックします。
    *   `fb.Kind != gb.Kind`: ブロックの種類が一致するかを確認します。
    *   `len(fb.Values) != len(gb.Values)`: ブロック内の値の数が一致するかを確認します。
    *   `!checkVal(fb.Values[i], gb.Values[i])`: 各値を再帰的に比較します。
    *   `len(fb.Succs) != len(gb.Succs)` と `len(fb.Preds) != len(gb.Preds)`: 後続ブロックと先行ブロックの数が一致するかを確認します。
    *   `!checkBlk(fb.Succs[i], gb.Succs[i])` と `!checkBlk(fb.Preds[i], gb.Preds[i])`: 各後続ブロックと先行ブロックを再帰的に比較します。
*   **エントリポイント**: 最終的に`checkBlk(f.Entry, g.Entry)`を呼び出すことで、両関数のエントリブロックから比較を開始し、グラフ全体を走査します。

この`Equiv`関数は、コンパイラの最適化がSSAグラフの構造と意味を正しく保持していることを検証するための強力なツールとなります。

## 元コミット内容

このコミットは、Goコンパイラの`cmd/internal/ssa`パッケージに、テスト目的で`Func`オブジェクトを構築するためのユーティリティ関数群を追加します。これにより、SSA形式の関数をより簡潔かつ宣言的に定義できるようになります。具体的には、`Fun`, `Bloc`, `Valu`, `Goto`, `If`, `Exit`といった関数が導入され、これらを組み合わせることで、複雑なSSAグラフをテキストベースの記述に近い形で表現できるようになります。

また、2つの`Func`オブジェクトが等価であるかをテストするための`Equiv`関数も追加されています。これは、コンパイラの最適化パスがSSAグラフを正しく変換したことを検証する際に非常に有用です。

## 変更の背景

GoコンパイラのSSAバックエンドは、コードの最適化において重要な役割を担っています。SSA形式のコードは、コンパイラがデータフロー解析や様々な最適化を効率的に行うことを可能にします。しかし、SSA形式の`Func`オブジェクトをプログラム的に構築し、テストケースとして使用することは、非常に冗長でエラーが発生しやすい作業でした。

以前のテストコード（`deadcode_test.go`の変更前を参照）では、`Func`、`Block`、`Value`といったオブジェクトを直接インスタンス化し、手動でリンクしていく必要がありました。これは、特に複雑な制御フローやデータフローを持つ関数を表現する場合に、コードの可読性を著しく低下させ、テストの記述と保守を困難にしていました。

このコミットの背景には、SSAバックエンドのテスト容易性を向上させ、開発者がより効率的にコンパイラの最適化パスを検証できるようにするという目的があります。簡潔なテスト記述は、バグの発見を容易にし、将来的なコンパイラの改善を加速させます。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの最適化において広く用いられる中間表現（IR）の一種です。その主要な特徴は以下の通りです。

*   **単一割り当て**: 各変数はプログラム内で一度だけ値を割り当てられます。これにより、変数の定義と使用の関係が明確になり、データフロー解析が容易になります。
*   **Φ関数 (Phi function)**: 制御フローグラフ（CFG）において、複数のパスが合流する点（支配フロンティア）で、同じ論理変数に対応する異なるSSA変数の中から適切なものを選択するために導入されます。例えば、`x3 = Φ(x1, x2)`は、`x1`と`x2`のどちらかの値が`x3`に割り当てられることを意味します。

GoコンパイラのSSAバックエンドは、GoのソースコードをSSA形式に変換し、その上で様々な最適化（デッドコード削除、定数伝播、共通部分式除去など）を適用します。

### 2. GoコンパイラのSSAパッケージ (`cmd/internal/ssa`)

`cmd/internal/ssa`パッケージは、Goコンパイラの内部でSSA形式のコードを表現・操作するためのデータ構造とアルゴリズムを提供します。

*   **`Func`**: SSA形式の関数全体を表す主要な構造体です。関数内のすべてのブロックと値を管理します。
*   **`Block`**: 制御フローグラフの基本ブロックを表します。基本ブロックは、入り口と出口が一つずつあり、内部に分岐を含まない一連の命令シーケンスです。`BlockPlain`（無条件ジャンプ）、`BlockIf`（条件分岐）、`BlockExit`（関数終了）などの種類があります。
*   **`Value`**: SSA形式における単一の操作または値を表します。これには、定数、関数引数、算術演算の結果などが含まれます。各`Value`は、その操作の種類（`Op`）、型（`Type`）、補助情報（`Aux`）、および引数（`Args`）を持ちます。

### 3. 制御フローグラフ (Control Flow Graph, CFG)

CFGは、プログラムの実行可能なパスを抽象的に表現するグラフです。ノードは基本ブロックを表し、エッジはブロック間の制御フローの遷移を表します。SSA形式のコードは、このCFG上で定義されます。

### 4. テスト駆動開発とコンパイラテスト

コンパイラの開発において、各最適化パスが正しく機能することを保証するために、厳密なテストが不可欠です。特にSSAのような複雑な中間表現を扱う場合、テストケースの作成は大きな課題となります。このコミットで導入されるユーティリティは、SSAグラフを直接構築する手間を減らし、テストコードの記述を簡素化することで、テスト駆動開発を促進します。

## 技術的詳細

このコミットの核となるのは、`src/cmd/internal/ssa/func_test.go`で定義される一連のヘルパー関数です。

### `Fun` 関数

`Fun`関数は、SSA形式の`Func`オブジェクトを構築するためのエントリポイントです。
```go
func Fun(entry string, blocs ...bloc) fun
```
*   `entry`: エントリブロックの名前を指定します。
*   `blocs`: `Bloc`関数によって定義されたブロックのリストを受け取ります。
*   戻り値の`fun`構造体は、構築された`*Func`オブジェクトと、名前から`Block`や`Value`へのマップ（`blocks`と`values`）を含みます。これにより、テストコード内で特定のブロックや値に名前でアクセスできるようになります。

`Fun`の内部では、まずすべてのブロックと値が作成され、次にそれらの間の接続（制御フローとデータフロー）が確立されます。

### `Bloc` 関数

`Bloc`関数は、単一のSSA基本ブロックを定義します。
```go
func Bloc(name string, entries ...interface{}) bloc
```
*   `name`: ブロックの一意な名前を指定します。
*   `entries`: そのブロックに含まれる値の定義（`Valu`）と、ブロックの制御フロー（`Goto`, `If`, `Exit`）を指定します。
*   各ブロックは、`Goto`、`If`、`Exit`のいずれか一つで制御フローを定義する必要があります。

### `Valu` 関数

`Valu`関数は、SSA形式の単一の値を定義します。
```go
func Valu(name string, op Op, t Type, aux interface{}, args ...string) valu
```
*   `name`: 値の一意な名前を指定します。
*   `op`: 値の操作の種類（例: `OpArg`, `OpConst`, `OpAdd`）。
*   `t`: 値の型（例: `TypeMem`, `TypeBool`, `TypeInt64`）。
*   `aux`: 補助情報（定数値、メモリ参照など）。
*   `args`: この値が依存する他の値の名前のリスト。これにより、データフローが表現されます。

### 制御フロー定義関数 (`Goto`, `If`, `Exit`)

*   `Goto(succ string)`: 無条件ジャンプを表し、`BlockPlain`タイプのブロックを定義します。`succ`は次のブロックの名前です。
*   `If(cond, sub, alt string)`: 条件分岐を表し、`BlockIf`タイプのブロックを定義します。`cond`は条件を表す値の名前、`sub`と`alt`はそれぞれ真と偽の場合の次のブロックの名前です。
*   `Exit(arg string)`: 関数からの終了を表し、`BlockExit`タイプのブロックを定義します。`arg`は終了時のメモリ状態などを表す値の名前です。

これらの関数は、内部的に`bloc`, `ctrl`, `valu`というヘルパーストラクトを使用して、SSAグラフの構造を構築します。

### `Equiv` 関数

`Equiv`関数は、2つの`Func`オブジェクトが等価であるかを再帰的に比較します。
```go
func Equiv(f, g *Func) bool
```
この関数は、CFGの同型性（isomorphism）と、対応する値の等価性をチェックします。ただし、現在の実装では、値と先行ブロックの順序が同じであることも要求されます。これは、より厳密な比較であり、将来的に順序に依存しない同型性チェックに拡張される可能性がコメントで示唆されています。

`Equiv`は、`valcor`（Value correlation）と`blkcor`（Block correlation）というマップを使用して、既に比較済みの要素を追跡し、無限ループを防ぎます。

## コアとなるコードの変更箇所

### `src/cmd/internal/ssa/deadcode_test.go`

このファイルでは、既存のデッドコード削除テストが、新しく導入されたユーティリティ関数を使用して書き直されています。

**変更前:**
`Func`、`Block`、`Value`を直接インスタンス化し、`NewBlock`、`NewValue`、`addEdge`といった低レベルなAPIを多数呼び出してSSAグラフを構築していました。

```go
func TestDeadLoop(t *testing.T) {
	f := new(Func)
	entry := f.NewBlock(BlockPlain)
	exit := f.NewBlock(BlockExit)
	f.Entry = entry
	addEdge(entry, exit)
	mem := entry.NewValue(OpArg, TypeMem, ".mem")
	exit.Control = mem

	// dead loop
	deadblock := f.NewBlock(BlockIf)
	addEdge(deadblock, deadblock)
	addEdge(deadblock, exit)

	// dead value in dead block
	deadval := deadblock.NewValue(OpConst, TypeBool, true)
	deadblock.Control = deadval
	// ...
}
```

**変更後:**
`Fun`, `Bloc`, `Valu`, `Goto`, `If`, `Exit`といった高レベルなユーティリティ関数を使用して、SSAグラフを宣言的に記述しています。

```go
func TestDeadLoop(t *testing.T) {
	fun := Fun("entry",
		Bloc("entry",
			Valu("mem", OpArg, TypeMem, ".mem"),
			Goto("exit")),
		Bloc("exit",
			Exit("mem")),
		// dead loop
		Bloc("deadblock",
			// dead value in dead block
			Valu("deadval", OpConst, TypeBool, true),
			If("deadval", "deadblock", "exit")))

	CheckFunc(fun.f)
	Deadcode(fun.f)
	CheckFunc(fun.f)

	for _, b := range fun.f.Blocks {
		if b == fun.blocks["deadblock"] {
			t.Errorf("dead block not removed")
		}
		// ...
	}
}
```
この変更により、テストコードの行数が大幅に削減され、SSAグラフの構造が直感的に理解できるようになりました。

### `src/cmd/internal/ssa/func_test.go` (新規ファイル)

このファイルは完全に新規追加され、以下の主要な要素を含んでいます。

*   `fun`構造体: `Fun`関数の戻り値として、構築された`*Func`と、名前による`Block`および`Value`へのマップを保持します。
*   `Fun`, `Bloc`, `Valu`, `Goto`, `If`, `Exit`関数: 上記で説明したSSAグラフ構築ユーティリティの実装。
*   `bloc`, `ctrl`, `valu`構造体: 上記ユーティリティ関数の内部で使用されるヘルパーストラクト。
*   `addEdge`関数: `Block`間のエッジを追加するヘルパー関数。
*   `Equiv`関数: 2つの`Func`オブジェクトの等価性を比較する実装。
*   `TestArgs`, `TestEquiv`関数: 新しいユーティリティ関数自体のテストケース。`TestEquiv`では、等価なケースと非等価なケースの両方について`Func`の比較を検証しています。

## コアとなるコードの解説

### `func_test.go` の `Fun` 関数

`Fun`関数は、SSAグラフの構築プロセスを2つの主要なパスに分けています。

1.  **初期化パス**:
    *   `f := new(Func)`: 新しい`Func`オブジェクトを初期化します。
    *   `blocks := make(map[string]*Block)` と `values := make(map[string]*Value)`: 名前から実際の`Block`および`Value`オブジェクトへのマッピングを保持するためのマップを作成します。
    *   `for _, bloc := range blocs`: 引数として渡された各`bloc`定義をループ処理します。
        *   `b := f.NewBlock(bloc.control.kind)`: `Bloc`で指定された種類（`BlockPlain`, `BlockIf`など）に基づいて新しい`Block`を作成し、`blocks`マップに名前で登録します。
        *   `for _, valu := range bloc.valus`: 各ブロック内の`valu`定義をループ処理します。
            *   `values[valu.name] = b.NewValue(valu.op, valu.t, valu.aux)`: `Valu`で指定された操作、型、補助情報に基づいて新しい`Value`を作成し、`values`マップに名前で登録します。この時点では、`Value`の引数（`Args`）はまだ設定されません。

2.  **接続パス**:
    *   `f.Entry = blocks[entry]`: `Fun`の`entry`引数で指定された名前のブロックを、関数のエントリポイントとして設定します。
    *   `for _, bloc := range blocs`: 再度、各`bloc`定義をループ処理します。
        *   `b := blocks[bloc.name]`: 現在のブロックオブジェクトを取得します。
        *   **制御値の設定**: `if c.control != ""`: `Bloc`で制御値が指定されている場合（例: `If`関数の条件）、`values`マップから対応する`Value`オブジェクトを取得し、`b.Control`に設定します。
        *   **値の引数の設定**: `for _, valu := range bloc.valus`: 各ブロック内の`valu`定義をループ処理します。
            *   `v := values[valu.name]`: 現在の値オブジェクトを取得します。
            *   `for _, arg := range valu.args`: `Valu`で指定された引数名（他の値の名前）をループ処理します。
                *   `a, ok := values[arg]`: `values`マップから引数に対応する`Value`オブジェクトを取得します。
                *   `v.AddArg(a)`: 取得した引数`Value`を現在の`Value`の引数リストに追加します。これにより、データフローが確立されます。
        *   **後続ブロックの接続**: `for _, succ := range c.succs`: `Bloc`で指定された後続ブロックの名前をループ処理します。
            *   `addEdge(b, blocks[succ])`: `addEdge`ヘルパー関数を呼び出して、現在のブロックと後続ブロックの間に制御フローエッジを追加します。`addEdge`は、両方向のリンク（`b.Succs`と`c.Preds`）を設定します。

この2段階の構築プロセスにより、SSAグラフ内のすべての要素が正しく初期化され、相互に接続されます。

### `func_test.go` の `Equiv` 関数

`Equiv`関数は、2つの`Func`オブジェクト`f`と`g`が構造的および意味的に等価であるかを判断します。

*   **対応付けマップ**: `valcor` (Value correlation) と `blkcor` (Block correlation) という2つのマップを使用します。これらは、`f`の要素が`g`のどの要素に対応するかを記録し、既に比較した要素を再帰的に処理する際の無限ループを防ぎます。
*   **`checkVal` 関数**: 2つの`Value`オブジェクトが等価であるかを再帰的にチェックします。
    *   `fv.Op != gv.Op || fv.Type != gv.Type`: 操作の種類と型が一致するかを確認します。
    *   `!reflect.DeepEqual(fv.Aux, gv.Aux)`: 補助情報がディープイコールで一致するかを確認します。
    *   `len(fv.Args) != len(gv.Args)`: 引数の数が一致するかを確認します。
    *   `!checkVal(fv.Args[i], gv.Args[i])`: 各引数を再帰的に比較します。
*   **`checkBlk` 関数**: 2つの`Block`オブジェクトが等価であるかを再帰的にチェックします。
    *   `fb.Kind != gb.Kind`: ブロックの種類が一致するかを確認します。
    *   `len(fb.Values) != len(gb.Values)`: ブロック内の値の数が一致するかを確認します。
    *   `!checkVal(fb.Values[i], gb.Values[i])`: 各値を再帰的に比較します。
    *   `len(fb.Succs) != len(gb.Succs)` と `len(fb.Preds) != len(gb.Preds)`: 後続ブロックと先行ブロックの数が一致するかを確認します。
    *   `!checkBlk(fb.Succs[i], gb.Succs[i])` と `!checkBlk(fb.Preds[i], gb.Preds[i])`: 各後続ブロックと先行ブロックを再帰的に比較します。
*   **エントリポイント**: 最終的に`checkBlk(f.Entry, g.Entry)`を呼び出すことで、両関数のエントリブロックから比較を開始し、グラフ全体を走査します。

この`Equiv`関数は、コンパイラの最適化がSSAグラフの構造と意味を正しく保持していることを検証するための強力なツールとなります。

# [インデックス 21648] ファイルの概要

このコミットは、Go言語の `database/sql` パッケージにおける `Stmt.connStmt` メソッド内のロック競合を軽減することを目的としています。具体的には、`Stmt.connStmt` が `DB.connIfFree` を呼び出す際に発生していた `Stmt.mu` および `DB.mu` のロック競合を解消し、並行性の高いデータベース操作におけるパフォーマンスを向上させます。

## 変更の背景

このコミットが行われる前は、`database/sql` パッケージの `Stmt.connStmt` メソッドが、ステートメントに紐付けられた接続のリスト (`Stmt.css`) を反復処理し、各接続に対して `DB.connIfFree` を呼び出していました。この処理には以下の2つの主要な問題がありました。

1.  **`Stmt.mu` のロック競合**: `Stmt.connStmt` メソッド自体が `Stmt.mu` (ステートメントのミューテックス) をロックしていました。そのため、複数のゴルーチンが同時に同じ `Stmt` オブジェクトを使用しようとすると、`Stmt.mu` を巡るロック競合が発生し、並行性が阻害されていました。
2.  **`DB.mu` のロック競合**: `DB.connIfFree` メソッドは `DB.mu` (データベースのミューテックス) をロックしていました。この `DB.mu` は、`DB.addDep` や `DB.removeDep` といった他のデータベース操作でも共有されるため、`DB.connIfFree` の頻繁な呼び出しは `DB.mu` のロック競合を引き起こし、データベース全体の並行処理性能に悪影響を与えていました。

これらのロック競合は、特に並行性の高い環境でのデータベースクエリのパフォーマンスを著しく低下させていました。コミットメッセージに記載されているベンチマーク結果が示すように、この変更によって `BenchmarkManyConcurrentQuery` の実行時間が大幅に改善されており、特に並行度が高い場合に顕著な効果が見られます。

## 前提知識の解説

### Go言語の `database/sql` パッケージ

`database/sql` パッケージは、Go言語の標準ライブラリの一部であり、SQLデータベースと対話するための統一されたインターフェースを提供します。このパッケージ自体は特定のデータベースの実装を含まず、データベース固有のドライバ（例: MySQL用 `github.com/go-sql-driver/mysql`、PostgreSQL用 `github.com/lib/pq`）をインポートして使用します。

主要な概念:
*   **`*sql.DB`**: データベースへの接続プールを表します。単一のアクティブな接続ではなく、複数の接続を管理し、再利用することでパフォーマンスを最適化します。
*   **`*sql.Stmt`**: プリペアドステートメントを表します。SQLクエリを事前に準備（プリコンパイル）しておくことで、繰り返し実行する際のパフォーマンスを向上させます。
*   **`driver.Driver`**: データベースドライバが実装すべきインターフェースを定義します。
*   **`driver.Conn`**: データベースへの単一の接続を表します。
*   **`connStmt`**: `Stmt` 内部で使用される構造体で、特定の `driver.Conn` とそれに関連付けられた `driver.Stmt` を保持します。
*   **接続プール**: `*sql.DB` は内部的に接続プールを管理し、データベース接続の確立と切断のオーバーヘッドを削減します。アイドル状態の接続を再利用することで、効率的なリソース利用を促進します。

### `sync.Mutex` とロック競合

`sync.Mutex` はGo言語の `sync` パッケージで提供される相互排他ロック（ミューテックス）です。共有リソースへの同時アクセスを保護するために使用され、一度に1つのゴルーチンのみがロックを取得してクリティカルセクション（共有リソースにアクセスするコード部分）を実行できるようにします。

**ロック競合 (Lock Contention)** は、複数のゴルーチンが同時に同じミューテックスを取得しようとしたときに発生します。ロックがすでに別のゴルーチンによって保持されている場合、他のゴルーチンはロックが解放されるまで待機状態になります。ロック競合が高い場合、ゴルーチンは有用な作業を実行する代わりに待機に多くの時間を費やすことになり、アプリケーションの並行性と全体的なパフォーマンスが著しく低下します。

### `sync/atomic` パッケージ

`sync/atomic` パッケージは、Go言語で提供される低レベルのロックフリーなプリミティブであり、共有変数に対するアトミックな操作（不可分な操作）を実行するために使用されます。アトミック操作は、他のゴルーチンからの割り込みや干渉なしに、単一の不可分な単位として実行されることが保証されます。

主な特徴:
*   **不可分性**: 操作が途中で中断されることなく、完全に実行されるか、全く実行されないかのどちらかであることを保証します。これにより、並行処理におけるデータ競合を防ぎます。
*   **効率性**: 通常、ミューテックスを使用するよりも効率的です。これは、CPUのハードウェアレベルの命令（例: Compare-and-Swap (CAS)）を利用して実装されるため、ロックの取得と解放に伴うオーバーヘッドが少ないためです。
*   **用途**: カウンターのインクリメント、フラグの管理、シンプルな状態遷移など、単一の変数を更新するような単純な操作に最適です。

このコミットでは、`atomic.AddUint64` や `atomic.LoadUint64` といった関数が使用され、ロックなしで接続のクローズ数を安全に追跡しています。

## 技術的詳細

このコミットの核心は、`Stmt.connStmt` メソッドにおけるロック競合の根本原因を排除することです。

1.  **`DB.connIfFree` の削除**:
    *   以前は `Stmt.connStmt` が `DB.connIfFree` を呼び出し、アイドル接続プールから特定の接続がまだ有効で利用可能かどうかを確認していました。この `DB.connIfFree` は `DB.mu` をロックするため、ボトルネックとなっていました。
    *   このコミットでは `DB.connIfFree` メソッドが完全に削除されました。

2.  **`numClosed` と `lastNumClosed` の導入**:
    *   `DB` 構造体に `numClosed` という `uint64` 型のフィールドが追加されました。これは、クローズされた接続の総数を追跡するためのアトミックカウンターです。`sync/atomic` パッケージの関数 (`atomic.AddUint64`, `atomic.LoadUint64`) を使用して、ロックなしで安全にアクセスされます。
    *   `Stmt` 構造体には `lastNumClosed` という `uint64` 型のフィールドが追加されました。これは、`Stmt` が作成された時点、または `Stmt.css` からクローズされた接続が削除された時点での `db.numClosed` の値を保持します。

3.  **`removeClosedStmtLocked` の導入**:
    *   `Stmt` に新しいプライベートメソッド `removeClosedStmtLocked()` が追加されました。このメソッドの目的は、`Stmt.css` (ステートメントに紐付けられた接続のリスト) からクローズされた接続を効率的に削除することです。
    *   このクリーンアップは、`s.db.numClosed - s.lastNumClosed` の差が十分に大きい場合にのみ実行されます。これにより、頻繁なクリーンアップによるオーバーヘッドを避けつつ、古くなった接続情報を定期的に整理します。
    *   このメソッドは `s.db.mu` をロックしますが、その呼び出し頻度が制御されるため、以前の `DB.connIfFree` のように頻繁にロック競合を引き起こすことはありません。

4.  **`Stmt.connStmt` の変更**:
    *   `Stmt.connStmt` から `DB.connIfFree` の呼び出しと、それに伴う `Stmt.css` の即時クリーンアップロジックが削除されました。
    *   代わりに、`Stmt.connStmt` は `s.removeClosedStmtLocked()` を呼び出すことで、クローズされた接続のクリーンアップを委譲します。これにより、`Stmt.mu` のロックが保持されている間に `DB.mu` をロックする機会が減り、ロック競合が緩和されます。
    *   接続の取得は、アイドル接続プールから最初の未使用接続を試みるか、新しい接続を作成する従来の `s.db.conn()` メソッドに依存するようになりました。

この変更により、`Stmt.connStmt` が `Stmt.mu` を保持している間に `DB.mu` をロックする頻度が大幅に減少し、並行性の高いシナリオでのパフォーマンスが向上しました。ベンチマーク結果は、特に多数の並行クエリがある場合に、この変更が顕著な性能改善をもたらしたことを明確に示しています。

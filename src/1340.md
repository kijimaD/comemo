## 変更の背景

このコミットは、Go言語の初期のコンパイラである `6g` のコード生成段階におけるさらなる最適化を目的としています。当時のGoコンパイラは、生成されるアセンブリコードの効率性を高めるために、継続的に改善が加えられていました。特に、メモリ上のデータへのアクセス方法や、定数の扱い方において、より効率的なアセンブリ命令を生成するためのロジックが求められていました。

具体的には、以下の点が背景にあると考えられます。

1.  **アドレス計算の効率化**: 構造体のフィールドや配列の要素へのアクセスは、ベースアドレスにオフセットやインデックスを加えて計算されます。この計算をコンパイラがより賢く行い、可能な限りレジスタや直接アドレス指定モードを活用することで、命令数を減らし、実行速度を向上させることができます。
2.  **定数伝播と最適化**: 小さな整数定数（`smallintconst`）は、特定の条件下で特別な最適化の対象となることがあります。例えば、比較演算において、一方のオペランドが小さな定数である場合、より効率的な命令シーケンスを生成できる可能性があります。
3.  **レジスタ割り当ての改善**: `sudoaddable` のような関数は、特定のノード（式や変数）が直接アドレス指定可能であるか、あるいはレジスタに割り当て可能であるかを判断するために使用されます。この判断ロジックを改善することで、レジスタの利用効率を高め、メモリへのアクセス回数を減らすことができます。
4.  **コンパイラのクリーンアップと保守性**: `sudoclean` の導入は、`sudoaddable` のような一時的なレジスタ割り当てを伴う処理の後で、適切にリソースを解放し、コンパイラの内部状態をクリーンに保つことを目的としている可能性があります。

これらの最適化は、Goプログラム全体のパフォーマンス向上に寄与し、言語の初期段階における重要な改善点でした。

## 前提知識の解説

### Goコンパイラ `6g`

Go言語の初期のコンパイラは、ターゲットアーキテクチャごとに異なる名前を持っていました。`6g` は、`amd64` (x86-64) アーキテクチャ向けのGoコンパイラの名称でした。同様に、`8g` は `386` (x86-32) 向け、`5g` は `arm` 向けでした。これらのコンパイラは、Goのソースコードをオブジェクトファイル（例: `file.6`）に変換し、その後、対応するリンカ（例: `6l`）によって実行可能ファイルが生成されました。

Go 1.5以降、これらのアーキテクチャ固有のコンパイラ名は `go tool compile` という単一のバイナリに統合され、`$GOARCH` や `$GOOS` といった環境変数に基づいてターゲットアーキテクチャが決定されるようになりました。しかし、このコミットが作成された2008年当時は、`6g` が `amd64` 向けの主要なコンパイラでした。

### コンパイラのコード生成と最適化

コンパイラは、ソースコードを機械語に変換するソフトウェアです。その過程で、生成される機械語の効率性を高めるために様々な最適化を行います。

*   **コード生成 (Code Generation)**: 抽象構文木 (AST) などの中間表現から、ターゲットアーキテクチャの命令セットに基づいたアセンブリコードを生成する段階です。この段階で、どの命令を使い、どのレジスタに値を割り当てるかなどが決定されます。
*   **レジスタ割り当て (Register Allocation)**: プログラムの実行中に頻繁にアクセスされる値をCPUのレジスタに割り当てるプロセスです。レジスタはメモリよりもはるかに高速なため、適切にレジスタを割り当てることでプログラムの実行速度が大幅に向上します。Goコンパイラは、線形スキャンレジスタアロケータのバリアントを使用し、SSA (Static Single Assignment) 形式で動作します。
*   **アドレス指定モード (Addressing Modes)**: CPUがメモリ上のデータにアクセスする方法を指します。例えば、`[base + index * scale + displacement]` のような形式で、ベースレジスタ、インデックスレジスタ、スケール（要素サイズ）、オフセット（変位）を組み合わせてアドレスを計算します。コンパイラは、このアドレス計算を効率的に行うことで、命令数を削減し、パフォーマンスを向上させます。
*   **定数伝播 (Constant Propagation)**: コンパイル時に値が確定している定数を、その定数が使用される箇所に直接埋め込む最適化です。これにより、実行時の計算を減らすことができます。
*   **`sudoaddable`**: このコミットで変更されている `sudoaddable` 関数は、Goコンパイラの内部で、特定のノード（変数、構造体フィールド、配列要素など）が、アセンブリ命令のオペランドとして直接アドレス指定可能であるか、あるいはレジスタに割り当て可能であるかを判断するために使用されるヘルパー関数です。この関数が `true` を返す場合、コンパイラはより効率的なアドレス指定モードやレジスタ割り当てを利用してコードを生成できます。
*   **`smallintconst`**: このコミットで新しく導入された `smallintconst` 関数は、与えられたノードが小さな整数定数であるかどうかを判定します。Goコンパイラでは、小さな整数定数（特にインターフェースへの変換時など）に対して特別な最適化を適用することがあります。例えば、Go 1.15以降では、0から255までの小さな整数をインターフェースに変換する際に、ヒープアロケーションを避けるために事前に割り当てられた静的配列が使用されるようになりました。このコミットの時点ではそこまで洗練されていなかったかもしれませんが、同様の最適化の萌芽が見られます。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/6g/cgen.c`、`src/cmd/6g/gg.h`、`src/cmd/6g/gsubr.c` の3つのファイルに集中しています。

1.  **`src/cmd/6g/gg.h` の変更**:
    *   `sudoaddable` 関数のシグネチャが変更されました。以前は `Node* reg` という引数がありましたが、これが削除され、`int sudoaddable(Node*, Type*, Addr*)` となりました。これは、`sudoaddable` がレジスタ割り当ての責任を直接負うのではなく、アドレス指定可能性の判断に特化するように変更されたことを示唆しています。
    *   新しい関数 `smallintconst(Node*)` が追加されました。これは、ノードが小さな整数定数であるかを判定するためのものです。
    *   新しい関数 `sudoclean(void)` が追加されました。これは、`sudoaddable` のような処理で一時的に使用されたリソース（特にレジスタ）をクリーンアップするためのものです。

2.  **`src/cmd/6g/gsubr.c` の変更**:
    *   `sudoaddable` 関数の実装が大幅に変更されました。
        *   `Node* reg` 引数が削除され、代わりに `clean` 配列と `cleani` インデックスを使用して、一時的なレジスタ割り当てを管理するようになりました。これにより、`sudoaddable` の呼び出し元がレジスタの解放を気にする必要がなくなりました。
        *   `ODOT` (構造体フィールドアクセス) と `OINDEX` (配列要素アクセス) の処理が大幅に拡張されました。
            *   `ODOT` の場合、`dotoffset` を使用してオフセットを計算し、`OINDREG` (レジスタ間接参照) を利用してアドレスを構築します。複数のオフセットがある場合（ネストされた構造体など）も、`AMOVQ` 命令を使ってレジスタを更新しながらアドレスを計算します。
            *   `OINDEX` の場合、配列のベースアドレスとインデックスをそれぞれレジスタにロードし、`scale` (要素サイズ) を考慮してアドレスを計算します。
            *   配列の境界チェック (`debug['B']` が無効な場合) が追加されました。インデックスが範囲外の場合、`throwindex` 関数を呼び出して実行時エラーを発生させます。
            *   動的配列 (`ODynam`) の場合、`Array` 構造体の `nel` (要素数) と `array` (データポインタ) フィールドを考慮してアドレスを計算します。
            *   インデックスが定数の場合 (`oindex_const`)、コンパイル時にオフセットを計算し、より効率的なアドレス指定を行います。境界チェックもコンパイル時に行われます。
    *   `smallintconst` 関数の実装が追加されました。これは、ノードが `OLITERAL` であり、かつその型が `TINT8`, `TUINT8`, `TINT16`, `TUINT16`, `TINT32`, `TUINT32`, `TBOOL`, `TPTR32` のいずれかである場合に `1` (true) を返します。
    *   `sudoclean` 関数の実装が追加されました。これは、`clean` 配列に格納された一時的なノードのレジスタを解放します。
    *   `ginit` と `gclean` 関数で、`D_R14` と `D_R15` レジスタが予約済みとして扱われるようになりました。これは、特定の内部処理（例えば、ガベージコレクタのポインタなど）のためにこれらのレジスタが使用されることを示唆しています。

3.  **`src/cmd/6g/cgen.c` の変更**:
    *   `cgen` 関数内で `sudoaddable` の呼び出し箇所が、新しいシグネチャに合わせて変更されました。`Node* n1` 引数が削除され、`sudoclean()` が呼び出されるようになりました。これにより、`cgen` は `sudoaddable` が内部でレジスタを管理し、`sudoclean` で解放することを期待するようになりました。
    *   `bgen` 関数内で、比較演算の最適化が追加されました。`smallintconst(nr)` (右オペランドが小さな整数定数) の場合、`OCMP` 命令と `gbranch` を使用して、より直接的な比較と分岐を行うようになりました。

これらの変更は、Goコンパイラが生成するアセンブリコードの品質を向上させ、特にメモリ上のデータアクセスと定数処理において、より効率的な命令シーケンスを選択できるようにするためのものです。

## コアとなるコードの解説

### `sudoaddable` 関数の変更と役割

`sudoaddable` 関数は、Goコンパイラのコード生成フェーズにおいて、特定のノード（式や変数）が、アセンブリ命令のオペランドとして直接アドレス指定可能であるか、あるいはレジスタに割り当て可能であるかを判断する非常に重要な役割を担っています。この関数が `true` を返す場合、コンパイラはより効率的なアドレス指定モードやレジスタ割り当てを利用してコードを生成できます。

**変更点**:

1.  **引数の変更**: 以前は `Node* reg` という引数がありましたが、これが削除されました。これは、`sudoaddable` がレジスタ割り当ての責任を直接負うのではなく、アドレス指定可能性の判断に特化するように変更されたことを示唆しています。代わりに、`clean` 配列と `cleani` インデックスという内部的なメカニズムを導入し、一時的なレジスタ割り当てを管理するようになりました。これにより、`sudoaddable` の呼び出し元（`cgen` など）は、レジスタの解放を気にする必要がなくなり、コードの簡潔性と保守性が向上しました。
2.  **構造体フィールド (`ODOT`, `ODOTPTR`) の処理強化**:
    *   `dotoffset` を使用して、構造体内のフィールドのオフセットを計算します。
    *   `regalloc` で一時レジスタを割り当て、構造体のベースアドレスをそのレジスタにロードします (`agen` または `cgen`)。
    *   `OINDREG` (レジスタ間接参照) を利用して、`base + offset` の形式でアドレスを構築します。
    *   ネストされた構造体の場合、`AMOVQ` 命令を使ってレジスタを更新しながら、複数のオフセットを順次適用して最終的なアドレスを計算します。
3.  **配列要素 (`OINDEX`) の処理追加**:
    *   配列のベースアドレス (`l`) とインデックス (`r`) をそれぞれレジスタにロードします。
    *   要素の幅 (`w`) を考慮し、`base + index * width` の形式でアドレスを計算します。
    *   **境界チェック**: `debug['B']` フラグが設定されていない場合（つまり、デバッグモードでない場合）、配列のインデックスが有効な範囲内にあるかをチェックします。範囲外の場合、`throwindex` 関数を呼び出して実行時パニックを発生させます。これは、Goの実行時安全性保証の一部です。
    *   **動的配列のサポート**: `ODynam` フラグが設定されている場合（スライスなど）、`Array` 構造体の `nel` (要素数) と `array` (データポインタ) フィールドを考慮してアドレスを計算します。これにより、動的にサイズが変更される配列へのアクセスも正確に処理できます。
    *   **定数インデックスの最適化**: インデックスがコンパイル時に既知の定数である場合 (`whatis(r) == Wlitint`)、コンパイラはインデックスと要素幅の乗算をコンパイル時に行い、直接オフセットを計算します。これにより、実行時の計算を削減し、より効率的なアドレス指定を可能にします。境界チェックもコンパイル時に行われます。

### `smallintconst` 関数の導入と役割

`smallintconst` 関数は、新しく導入されたヘルパー関数で、与えられたノードが特定の条件を満たす「小さな整数定数」であるかを判定します。

**役割**:

*   この関数は、コンパイラが特定の最適化を適用できるかどうかを判断するために使用されます。
*   具体的には、ノードが `OLITERAL` (リテラル定数) であり、かつその型が `TINT8`, `TUINT8`, `TINT16`, `TUINT16`, `TINT32`, `TUINT32`, `TBOOL`, `TPTR32` のいずれかである場合に `true` を返します。これらの型は、一般的にサイズが小さく、特定のCPU命令で効率的に扱える可能性が高い整数型です。
*   `cgen` 関数では、`OLITERAL` のノードに対して `smallintconst` を呼び出し、結果に基づいてレジスタを介したコード生成 (`f = 1`) をスキップするかどうかを決定します。小さな整数定数は、直接命令に埋め込んだり、より効率的な方法で扱えるため、レジスタを介する必要がない場合があります。
*   `bgen` 関数では、比較演算の右オペランドが `smallintconst` である場合に、`OCMP` 命令と `gbranch` を使用して、より直接的で効率的な比較と分岐のコードを生成します。

これらの変更により、Goコンパイラは、メモリ上のデータアクセスと定数処理において、より洗練された最適化を適用できるようになり、結果として生成される機械語の効率性が向上しました。

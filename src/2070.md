## 変更の背景

このコミットが行われた2009年当時、Go言語はまだ初期段階にあり、並行処理のパターンやベストプラクティスが確立されつつある時期でした。`exvar`パッケージは、プログラムの実行中に公開される変数（メトリクスや統計情報など）を管理するためのもので、これらの変数へのアクセスは並行処理環境下で安全に行われる必要がありました。

以前の実装では、共有される`vars`マップへのアクセスを保護するために`sync.Mutex`が使用されていました。しかし、ミューテックスは粒度が粗い場合や、複数のミューテックスが関与する複雑なシナリオではデッドロックのリスクやパフォーマンスのボトルネックとなる可能性があります。また、グローバルなミューテックスは、テスト時に状態を隔離することを困難にし、テスト容易性を低下させる要因となります。

この変更の背景には、Goの並行処理の哲学である「共有メモリを通信によって共有する」という考え方への移行があります。ミューテックスによる共有メモリの保護ではなく、チャネルを介したメッセージパッシングによって共有状態へのアクセスを単一のゴルーチンに集約することで、より安全で、デッドロックのリスクが低く、かつテストしやすい設計を目指しています。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の並行処理に関する基本的な知識が必要です。

1.  **ゴルーチン (Goroutine)**:
    Goランタイムによって管理される軽量なスレッドです。数千、数万といった多数のゴルーチンを同時に実行することが可能で、OSのスレッドよりもはるかに少ないリソースで動作します。`go`キーワードを使って関数呼び出しの前に記述することで、その関数を新しいゴルーチンで実行します。

2.  **チャネル (Channel)**:
    ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは、Goの並行処理における主要な同期プリミティブであり、「共有メモリを通信によって共有する」というGoの哲学を体現しています。チャネルは型付けされており、バッファリングの有無を選択できます。このコミットでは、バッファなしチャネルが使用されており、送信側と受信側が同時に準備ができていないとブロックされます。

3.  **ミューテックス (Mutex)**:
    `sync`パッケージで提供される排他制御のメカニズムです。共有リソースへのアクセスを一度に一つのゴルーチンに制限するために使用されます。`Lock()`メソッドでロックを取得し、`Unlock()`メソッドでロックを解放します。ロックを忘れるとデッドロックの原因となる可能性があります。

4.  **グローバル状態**:
    プログラム全体からアクセス可能な変数やデータ構造のことです。グローバル状態は、複数のゴルーチンから同時にアクセスされると競合状態（Race Condition）を引き起こす可能性があり、その管理は並行処理プログラミングにおける大きな課題の一つです。テスト時にも、グローバル状態が前のテスト実行の影響を受けるなど、問題を引き起こしやすいです。

## 技術的詳細

このコミットの核心は、`exvar`パッケージの内部状態（`vars`マップ）へのアクセスを、ミューテックスによる直接的な保護から、単一のゴルーチンが管理するチャネルベースのワーカーモデルへと移行した点にあります。

**変更前（ミューテックスベース）**:
- `vars`マップはグローバル変数として定義され、`sync.Mutex`によって保護されていました。
- `IncrementInt`, `SetInt`, `GetInt`などの各公開関数は、`vars`マップにアクセスする前にミューテックスをロックし、処理後にアンロックしていました。
- これにより、複数のゴルーチンが同時にこれらの関数を呼び出しても、`vars`マップへのアクセスは排他的に保証されていました。

**変更後（ゴルーチンチャネルワーカーベース）**:
- `vars`マップは、`exVars`という新しい構造体のフィールドとしてカプセル化されました。
- `startWorkerFunc()`関数が導入され、この関数は新しいゴルーチンを起動します。このゴルーチンは、`workFunction`型の関数を受け取るチャネルを監視し続けます。
- `workFunction`は、`exVars`のインスタンスを引数にとるクロージャです。
- `workSync(f workFunction)`関数が導入されました。この関数は、引数として受け取った`workFunction`をワーカーゴルーチンが監視しているチャネルに送信します。そして、ワーカーゴルーチンがその関数を実行し終えるまでブロックします（`nil`値をチャネルに送ることで同期を実現）。
- `IncrementInt`, `SetInt`, `GetInt`などの公開関数は、直接`vars`マップにアクセスする代わりに、`workSync`を呼び出し、その内部で`vars`マップに対する操作を行うクロージャを渡すようになりました。

この新しいアプローチの利点は以下の通りです。

1.  **単一の書き込み者原則 (Single Writer Principle)**: `vars`マップへのすべての変更は、単一のワーカーゴルーチンによってのみ行われます。これにより、競合状態のリスクが大幅に減少します。
2.  **デッドロックの回避**: 複数のミューテックスを扱う際に発生しがちなデッドロックのリスクがなくなります。ワーカーゴルーチンは常にチャネルからメッセージを処理するだけなので、複雑なロック順序の問題が発生しません。
3.  **テスト容易性の向上**: グローバルなミューテックスがなくなったことで、テスト時に`exvar`の状態をより容易に隔離できるようになります。各テストケースでワーカーゴルーチンを独立して起動・停止したり、チャネルをモックしたりすることで、テストの信頼性と並行性が向上します。
4.  **Goの哲学への準拠**: 「共有メモリを通信によって共有する」というGoの並行処理の哲学に沿った設計です。

## コアとなるコードの解説

変更後の`exvar.go`の主要な部分は、`startWorkerFunc`と`workSync`、そしてそれらを利用する各公開関数です。

1.  **`startWorkerFunc()`**:
    この関数は、`workFunction`型のチャネルを作成し、そのチャネルを返すとともに、新しいゴルーチンを起動します。このゴルーチンは無限ループでチャネルから`workFunction`を受け取り、それらを実行します。`exVars`構造体のインスタンス（`state`）は、このワーカーゴルーチンによってのみ直接アクセス・変更されます。これにより、`vars`マップへのアクセスが単一のゴルーチンに限定され、競合状態が排除されます。

2.  **`workSync(f workFunction)`**:
    この関数は、`exvar`の公開API（例: `IncrementInt`）から呼び出されます。引数として渡された`workFunction`（`vars`マップに対する具体的な操作を含むクロージャ）をワーカーゴルーチンが監視している`worker`チャネルに送信します。
    `worker <- f;` の行で、操作をワーカーにキューイングします。
    `worker <- nil` の行は、ワーカーが`f()`の実行を完了した後に`nil`をチャネルに送信することで、呼び出し元のゴルーチンが処理の完了を待つための同期メカニズムとして機能します。これにより、`workSync`を呼び出したゴルーチンは、操作が安全に完了したことを確認できます。

3.  **各公開関数（例: `IncrementInt`）**:
    ```go
    func IncrementInt(name string, inc int) {
        workSync(func(state *exVars) {
            *state.getOrInitIntVar(name) += inc
        })
    }
    ```
    以前はミューテックスをロックして直接操作していましたが、変更後は`workSync`を呼び出し、`exVars`インスタンス（`state`）を引数にとる匿名関数（クロージャ）を渡しています。このクロージャ内で、実際の`vars`マップへの操作（`*state.getOrInitIntVar(name) += inc`）が行われます。このクロージャはワーカーゴルーチンによって実行されるため、`vars`マップへのアクセスは常に安全に、かつ単一のゴルーチンによって行われることが保証されます。

この設計パターンは、Goにおける「アクターモデル」の一種と見なすことができます。ワーカーゴルーチンが「アクター」であり、チャネルが「メッセージボックス」として機能し、すべての状態変更がアクターによって順次処理されます。

        worker <- nil  // will only be sent after f() completes.
    }
    ```
-   `getOrInitIntVar`と`getOrInitMapVar`が`exVars`のメソッドに変更され、引数として`state *exVars`を受け取るように変更。
-   `IncrementInt`, `IncrementMap` (→ `IncrementMapInt`), `SetInt`, `SetMap` (→ `SetMapInt`), `GetInt`, `GetMap` (→ `GetMapInt`), `String`といった公開関数が、`mutex.Lock()`/`Unlock()`の代わりに`workSync`を使用して、内部で`exVars`インスタンスに対する操作を行うクロージャを渡すように変更。

## コアとなるコードの解説

変更後の`exvar.go`の主要な部分は、`startWorkerFunc`と`workSync`、そしてそれらを利用する各公開関数です。

1.  **`startWorkerFunc()`**:
    この関数は、`workFunction`型のチャネルを作成し、そのチャネルを返すとともに、新しいゴルーチンを起動します。このゴルーチンは無限ループでチャネルから`workFunction`を受け取り、それらを実行します。`exVars`構造体のインスタンス（`state`）は、このワーカーゴルーチンによってのみ直接アクセス・変更されます。これにより、`vars`マップへのアクセスが単一のゴルーチンに限定され、競合状態が排除されます。

2.  **`workSync(f workFunction)`**:
    この関数は、`exvar`の公開API（例: `IncrementInt`）から呼び出されます。引数として渡された`workFunction`（`vars`マップに対する具体的な操作を含むクロージャ）をワーカーゴルーチンが監視している`worker`チャネルに送信します。
    `worker <- f;` の行で、操作をワーカーにキューイングします。
    `worker <- nil` の行は、ワーカーが`f()`の実行を完了した後に`nil`をチャネルに送信することで、呼び出し元のゴルーチンが処理の完了を待つための同期メカニズムとして機能します。これにより、`workSync`を呼び出したゴルーチンは、操作が安全に完了したことを確認できます。

3.  **各公開関数（例: `IncrementInt`）**:
    ```go
    func IncrementInt(name string, inc int) {
        workSync(func(state *exVars) {
            *state.getOrInitIntVar(name) += inc
        })
    }
    ```
    以前はミューテックスをロックして直接操作していましたが、変更後は`workSync`を呼び出し、`exVars`インスタンス（`state`）を引数にとる匿名関数（クロージャ）を渡しています。このクロージャ内で、実際の`vars`マップへの操作（`*state.getOrInitIntVar(name) += inc`）が行われます。このクロージャはワーカーゴルーチンによって実行されるため、`vars`マップへのアクセスは常に安全に、かつ単一のゴルーチンによって行われることが保証されます。

この設計パターンは、Goにおける「アクターモデル」の一種と見なすことができます。ワーカーゴルーチンが「アクター」であり、チャネルが「メッセージボックス」として機能し、すべての状態変更がアクターによって順次処理されます。

## 変更の背景

Goのランタイムテストには、`TestCgoExternalThreadSIGPROF`というテストが存在します。このテストは、Cgo（GoとC言語の相互運用機能）が外部スレッドで`SIGPROF`シグナルを適切に処理できるかを確認することを目的としています。

過去には、`ppc64`および`ppc64le`アーキテクチャにおいて、Goのツールチェーンが外部リンキング（C言語のライブラリとリンクする機能）を完全にサポートしていませんでした。このため、`TestCgoExternalThreadSIGPROF`のような外部リンキングに依存するテストは、これらのアーキテクチャではスキップされるように設定されていました。

このコミットが行われた背景には、`ppc64le`アーキテクチャにおける外部リンキングのサポートが進展し、当該テストを実行できる環境が整ったという事実があります。開発者は、`ppc64le`環境でのCgoの正確な動作を検証するために、このテストを再有効化する必要があると判断しました。

## 前提知識の解説

*   **Cgo**: Go言語の重要な機能の一つで、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのメカニズムを提供します。これにより、既存のCライブラリをGoプロジェクトで再利用したり、パフォーマンスが重要な部分をCで記述したりすることが可能になります。
*   **外部リンキング (External Linking)**: プログラムがコンパイルされる際に、Goコンパイラが生成したオブジェクトファイルと、外部のC/C++コンパイラが生成したオブジェクトファイルやライブラリを結合するプロセスを指します。これにより、GoプログラムがCライブラリの関数やデータ構造を利用できるようになります。Goのビルドモードには、内部リンキング（Goのリンカのみを使用）と外部リンキング（システムのリンカを使用）があります。Cgoを使用する場合、多くの場合で外部リンキングが必要となります。
*   **`SIGPROF` シグナル**: Unix系システムにおけるシグナルの一つで、プロファイリング（プログラムの実行時間やメモリ使用量などを測定・分析すること）のために使用されます。通常、カーネルが定期的にプロセスに`SIGPROF`シグナルを送信し、その時点で実行されているコードの情報を収集することで、CPU使用率の高い部分などを特定します。
*   **`ppc64` および `ppc64le`**: IBMが開発したPowerPCアーキテクチャの64ビット版を指します。`ppc64`はビッグエンディアン（most significant byte first）を、`ppc64le`はリトルエンディアン（least significant byte first）をそれぞれ意味します。Goは様々なアーキテクチャをサポートしており、これらのPowerPCアーキテクチャもその対象です。
*   **`runtime.GOARCH`**: Goプログラムが実行されているシステムのアーキテクチャを示す文字列定数です。例えば、`amd64`、`arm64`、`ppc64`、`ppc64le`などがあります。テストコードなどで特定のアーキテクチャに依存する処理を条件分岐させる際に利用されます。

## 技術的詳細

このコミットの技術的な核心は、Goのビルドシステムとランタイムが`ppc64le`アーキテクチャで外部リンキングをサポートするようになったという点にあります。

`TestCgoExternalThreadSIGPROF`テストは、Cgoが関与する複雑なシナリオを検証します。具体的には、Goランタイムが管理するスレッドとは異なる、Cgoによって作成された外部スレッド（Cコードが実行されるスレッド）に対して`SIGPROF`シグナルが送信された場合に、Goのプロファイリングメカニズムが正しく機能するかどうかをテストします。この種のテストは、GoとCのコードが混在する環境での安定性と正確性を保証するために不可欠です。

以前は、`src/runtime/crash_cgo_test.go`内のテストコードで、`runtime.GOARCH`が`ppc64`または`ppc64le`の場合に`t.Skipf("no external linking on ppc64")`という行によってテストがスキップされていました。これは、これらのアーキテクチャで外部リンキングが利用できないため、テストが失敗するか、あるいは意図した検証ができない状態であったことを意味します。

このコミットでは、`ppc64le`アーキテクチャにおいて外部リンキングのサポートが確立されたため、`ppc64le`をスキップ条件から除外します。これにより、`ppc64le`環境でこのテストが実行され、Cgoとプロファイリングの統合が正しく機能することが検証されるようになります。`ppc64`アーキテクチャについては、まだ外部リンキングの課題が残っているため、引き続きテストはスキップされます。

## コアとなるコードの解説

変更された行は、`TestCgoExternalThreadSIGPROF`関数内の条件分岐です。

元のコード:
```go
if runtime.GOARCH == "ppc64" || runtime.GOARCH == "ppc64le" {
    // TODO(austin) External linking not implemented on
    // ppc64 (issue #8912)
    t.Skipf("no external linking on ppc64")
}
```
このコードは、現在の実行アーキテクチャが`ppc64`または`ppc64le`のいずれかである場合に、テストをスキップする指示を出していました。スキップの理由として、`ppc64`における外部リンキングの未実装がコメントで明記されています（issue #8912）。

変更後のコード:
```go
if runtime.GOARCH == "ppc64" {
    // TODO(austin) External linking not implemented on
    // ppc64 (issue #8912)
    t.Skipf("no external linking on ppc64")
}
```
この変更により、`ppc64le`が条件式から削除されました。これは、`ppc64le`アーキテクチャでは外部リンキングが利用可能になったため、このテストをスキップする必要がなくなったことを意味します。`ppc64`アーキテクチャについては、引き続き外部リンキングが未実装であるため、テストはスキップされ続けます。

このシンプルな変更は、Goのクロスプラットフォームサポートと、特定のアーキテクチャにおける機能実装の進捗を反映しています。テストの再有効化は、そのアーキテクチャでのGoランタイムの堅牢性を保証するために重要なステップです。

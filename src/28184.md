# [インデックス 28184] ファイルの概要

## コミット

`cmd/link/internal/ld`: cgoを使用するmips64xアーキテクチャに対して外部リンキングを強制する変更。

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/dcd613862bc51db8455ccd22c03336111afe6883](https://github.com/golang/go/commit/dcd613862bc51db8455ccd22c03336111afe6883)

## 元コミット内容

```
cmd/link/internal/ld: force external linking for mips64x with cgo

cgo internal linking is not supported yet (issue #14449).
```

## 変更の背景

このコミットは、Go言語のリンカ（`cmd/link/internal/ld`）において、Cgoを使用するMIPS64x（`mips64`および`mips64le`）アーキテクチャでの内部リンキングが未サポートであるという問題（Go issue #14449）に対応するために導入されました。

Go言語は、Cgoを介してC言語のコードをGoプログラムに統合する機能を提供します。通常、Goのリンカは、GoのコードとCgoでリンクされたCのコードを一つの実行可能ファイルにまとめる際に、内部リンキング（Goのリンカが直接Cのオブジェクトファイルを処理する）または外部リンキング（システムのCリンカ（例: `gcc`）を使用する）のいずれかのモードを選択できます。

しかし、特定のアーキテクチャ（この場合はMIPS64x）では、Cgoの内部リンキングの実装がまだ完全ではなく、正しく機能しないことが判明していました。同様の問題は以前からARM64アーキテクチャでも存在しており（Go issue #10373）、その際にはARM64に対して外部リンキングを強制する措置が取られていました。

このコミットは、MIPS64xアーキテクチャにおいても同様の未サポート問題が存在するため、一時的な回避策として、Cgoを使用するMIPS64xバイナリのビルド時に、Goのリンカが自動的に外部リンキングモードを選択するように強制することを目的としています。これにより、MIPS64x上でCgoを使用するプログラムが正しくビルドされ、実行できるようになります。

## 前提知識の解説

*   **Cgo**: GoプログラムからC言語のコードを呼び出すためのGoの機能です。Cgoを使用すると、既存のCライブラリをGoプロジェクトに統合したり、パフォーマンスが重要な部分をCで記述したりすることができます。
*   **リンキング (Linking)**: コンパイラによって生成されたオブジェクトファイル（機械語コード）を結合し、実行可能なプログラムやライブラリを作成するプロセスです。リンカは、異なるオブジェクトファイル間の参照（関数呼び出しや変数アクセス）を解決し、最終的なバイナリを生成します。
*   **内部リンキング (Internal Linking)**: Goのリンカ（`cmd/link`）が、CgoでリンクされたCのオブジェクトファイルも直接処理し、GoのコードとCのコードを単一のGo実行可能ファイルに統合するモードです。これにより、ビルドプロセスが簡素化され、Goツールチェーン内で完結します。
*   **外部リンキング (External Linking)**: Goのリンカが、CgoでリンクされたCのオブジェクトファイルの処理をシステムのCリンカ（例: `gcc`や`clang`）に委ねるモードです。GoのリンカはGoのコードをオブジェクトファイルに変換し、その後、システムのCリンカがGoのオブジェクトファイルとCのオブジェクトファイルを結合して最終的な実行可能ファイルを生成します。このモードは、特定のCライブラリに依存する場合や、Goの内部リンカが特定のアーキテクチャやCの機能に対応していない場合に必要となります。
*   **MIPS64x (mips64, mips64le)**: MIPS (Microprocessor without Interlocked Pipeline Stages) アーキテクチャの64ビット版を指します。`mips64`はビッグエンディアン、`mips64le`はリトルエンディアンのバリアントです。これらは組み込みシステムや特定のサーバー環境で利用されることがあります。
*   **Go issue #14449**: "cmd/link: cgo internal linking not supported on mips64" - MIPS64アーキテクチャでのCgo内部リンキングの未サポートに関するGoのバグトラッカー上の課題。
*   **Go issue #10373**: "cmd/link: cgo internal linking not supported on arm64" - ARM64アーキテクチャでのCgo内部リンキングの未サポートに関するGoのバグトラッカー上の課題。

## 技術的詳細

このコミットは、Goのリンカの動作を制御する`src/cmd/link/internal/ld/lib.go`ファイル内の`loadlib()`関数を変更します。

`loadlib()`関数は、リンキングモードを決定する重要な部分です。特に、Cgoが使用されている場合に、特定のアーキテクチャで内部リンキングがサポートされていない場合に外部リンキングを強制するロジックが含まれています。

変更前は、以下の条件で外部リンキングが強制されていました。

```go
if iscgo && goarch == "arm64" {
    Linkmode = LinkExternal
}
```

これは、Cgoが有効（`iscgo`が`true`）で、かつターゲットアーキテクチャがARM64（`goarch == "arm64"`）の場合に、`Linkmode`変数を`LinkExternal`に設定し、外部リンキングを強制するという意味です。この措置は、Go issue #10373で報告されたARM64でのCgo内部リンキングの問題に対応するためのものでした。

このコミットでは、MIPS64xアーキテクチャ（`mips64`および`mips64le`）も同様にCgo内部リンキングが未サポートであるという問題（Go issue #14449）が判明したため、この条件にMIPS64xを追加します。

変更後のコードは以下のようになります。

```go
if iscgo && (goarch == "arm64" || goarch == "mips64" || goarch == "mips64le") {
    Linkmode = LinkExternal
}
```

この変更により、Cgoが有効な場合、ターゲットアーキテクチャがARM64、MIPS64、またはMIPS64LEのいずれかであれば、Goのリンカは自動的に外部リンキングモードを使用するようになります。これにより、これらのアーキテクチャでCgoを使用する際のビルドエラーや実行時エラーを回避し、プログラムが正しく動作するようになります。

この変更は、Goのリンカが特定のアーキテクチャの特性やCgoのサポート状況に合わせて、適切なリンキング戦略を動的に選択するための防御的なプログラミングの一例です。内部リンキングのサポートが将来的にMIPS64xで改善されれば、この条件は削除または修正される可能性があります。

*   `iscgo`: このブール変数は、現在のビルドでCgoが使用されているかどうかを示します。`true`の場合、Cgoが有効であることを意味します。
*   `goarch`: この文字列変数は、ターゲットとなるGoのアーキテクチャ（例: "arm64", "amd64", "mips64"）を示します。
*   `goarch == "arm64"`: 以前の条件で、ARM64アーキテクチャの場合に外部リンキングを強制していました。
*   `goarch == "mips64" || goarch == "mips64le"`: このコミットで追加された部分です。MIPS64（ビッグエンディアン）またはMIPS64LE（リトルエンディアン）アーキテクチャの場合に、外部リンキングを強制する条件を追加します。
*   `Linkmode = LinkExternal`: 上記の条件が`true`になった場合、リンカのモードを`LinkExternal`に設定します。これにより、GoのリンカはシステムのCリンカを呼び出して最終的な実行可能ファイルを生成します。

この変更は、Goのリンカが、Cgoの内部リンキングがまだ安定していない、または実装されていない特定のアーキテクチャに対して、安全かつ機能的なビルドパスを提供するためのものです。これにより、開発者はMIPS64x上でCgoを使用する際に、リンキングの問題に遭遇することなく、Goプログラムをビルドできるようになります。

# [インデックス 16358] ファイルの概要

このコミットは、Go言語の `crypto/tls` パッケージにおいて、Next Protocol Negotiation (NPN) 拡張を送信する際の挙動を修正するものです。具体的には、`tls.Config` の `NextProtos` フィールドが設定されていない場合（空の場合）には、NPN拡張をクライアントに送信しないように変更することで、Firefoxブラウザの特定のバグを回避し、互換性の問題を解決します。

## 元コミット内容

`crypto/tls` パッケージにおいて、`NextProtos` が設定されていない場合、NPN (Next Protocol Negotiation) 拡張を送信しないようにする変更です。これはGo側の明確なバグではないものの、Firefoxのバグを引き起こし、その結果 `crypto/tls` と `net/http` を連携させる際に `NextProtos` に `"http/1.1"` を含めない限り問題が発生していました。`net/http` が `tls.Config` を設定する際には `"http/1.1"` を含めるため問題ありませんでしたが、開発者が独自に `tls.Config` を設定する場合にはFirefoxのバグに遭遇していました。このコミットは、Go issue #5445 を修正します。

## 変更の背景

この変更の背景には、Go言語の `crypto/tls` パッケージとMozilla Firefoxブラウザ間の特定の相互運用性の問題がありました。

TLS (Transport Layer Security) ハンドシェイク中に、クライアントとサーバーは、アプリケーション層プロトコル（例: HTTP/1.1, SPDY, HTTP/2）をネゴシエートするために、Next Protocol Negotiation (NPN) または Application-Layer Protocol Negotiation (ALPN) といった拡張を使用します。

問題は、Goの `crypto/tls` パッケージが、サーバーとして動作する際に、`tls.Config` の `NextProtos` フィールドが空であっても、空のNPN拡張をクライアントに送信することがあった点にありました。RFC 6066 (TLS Extensions) のセクション 7.4.1.2 では、クライアントがサポートするプロトコルリストを空にすることは許可されていますが、サーバーが空のリストを返すことについては明示的に言及されていません。しかし、Goの実装は、`NextProtos` が空の場合でもNPN拡張自体は送信していました。

この挙動が、当時のFirefoxブラウザの特定のバージョンに存在するバグをトリガーしました。Firefoxは、サーバーから空のNPN拡張を受け取ると、TLSハンドシェイクを正しく完了できず、接続エラーやハングアップを引き起こす可能性がありました。

Goの標準ライブラリである `net/http` パッケージは、内部的に `tls.Config` を設定する際に、デフォルトで `NextProtos` に `"http/1.1"` を含めていました。そのため、`net/http` を使用してTLSサーバーを構築している開発者はこの問題に遭遇しませんでした。しかし、`crypto/tls` パッケージを直接使用し、`NextProtos` を明示的に設定しない、または空のままにする開発者は、Firefoxからの接続時にこのバグに直面することになりました。

この問題は、Go issue #5445 として報告され、Goチームは、Go側の実装がRFCに厳密に違反しているわけではないものの、広く使用されているブラウザとの互換性を確保するために、この挙動を修正する必要があると判断しました。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上で安全な通信を行うための暗号化プロトコルです。ウェブブラウジング（HTTPS）、電子メール、VoIPなど、様々なアプリケーションで利用されています。TLSは、クライアントとサーバー間で以下の機能を提供します。

1.  **認証**: 通信相手が本物であることを確認します（通常はサーバー証明書による）。
2.  **機密性**: 通信内容を暗号化し、盗聴を防ぎます。
3.  **完全性**: 通信内容が改ざんされていないことを保証します。

TLSハンドシェイクは、クライアントとサーバーが安全な通信チャネルを確立するために行う一連のメッセージ交換です。このハンドシェイク中に、暗号スイートの選択、鍵交換、証明書の検証などが行われます。

### NPN (Next Protocol Negotiation)

NPNは、TLSハンドシェイク中にアプリケーション層プロトコルをネゴシエートするためのTLS拡張の一つです。これはGoogleによって開発され、主にSPDYプロトコル（HTTP/2の前身）のネゴシエーションに使用されました。

NPNの仕組みは以下の通りです：

1.  **ClientHello**: クライアントは `ClientHello` メッセージの一部として、サポートするアプリケーションプロトコル（例: `http/1.1`, `spdy/3`, `h2` など）のリストをNPN拡張に含めてサーバーに送信します。
2.  **ServerHello**: サーバーは `ServerHello` メッセージの一部として、クライアントが提示したリストの中から、サーバーがサポートするプロトコルを一つ選択し、そのプロトコル名をNPN拡張に含めてクライアントに送信します。
3.  **Finished**: ハンドシェイクの `Finished` メッセージの後に、クライアントとサーバーはネゴシエートされたプロトコルで通信を開始します。

NPNは、サーバーが最終的なプロトコルを選択するという点で、後継のALPN (Application-Layer Protocol Negotiation) とは異なります。ALPNでは、クライアントがプロトコルリストを提示し、サーバーがその中から選択したプロトコルを `ServerHello` で返しますが、NPNはサーバーがプロトコルを提示し、クライアントがその中から選択するという、よりサーバー主導のネゴシエーションでした。現在では、ALPNが主流であり、HTTP/2のネゴシエーションにはALPNが使用されます。

### Go言語の `crypto/tls` パッケージ

`crypto/tls` は、Go言語の標準ライブラリに含まれるパッケージで、TLSプロトコルを実装しています。このパッケージを使用することで、開発者はTLSクライアントやサーバーを簡単に構築できます。

`tls.Config` 構造体は、TLS接続の様々な設定を定義するために使用されます。これには、証明書、鍵、暗号スイート、プロトコルバージョンなどが含まれます。

`NextProtos` フィールドは、`tls.Config` の一部であり、サーバーがNPNまたはALPNを通じてクライアントに提示するアプリケーション層プロトコルのリスト（文字列スライス）を指定するために使用されます。例えば、`[]string{"h2", "http/1.1"}` のように設定することで、HTTP/2とHTTP/1.1の両方をサポートし、クライアントとのネゴシエーションを試みることができます。

## 技術的詳細

このコミットが修正する問題は、Goの `crypto/tls` サーバーが、`tls.Config.NextProtos` が空のスライスであるにもかかわらず、NPN拡張自体をTLSハンドシェイク中に送信していたことに起因します。

TLSハンドシェイクの `ServerHello` メッセージには、サーバーがサポートする拡張のリストが含まれます。NPN拡張は、このリストの一部として含まれることがあります。NPN拡張のデータ部分には、サーバーがネゴシエート可能なプロトコルのリストが格納されます。

Goの以前の挙動では、`config.NextProtos` が空の場合でも、`hs.hello.nextProtoNeg = true` が設定され、NPN拡張が `ServerHello` に含まれていました。この場合、NPN拡張のデータ部分は空のプロトコルリストを示すことになります。

当時のFirefoxブラウザのNPN実装には、この「空のプロトコルリストを持つNPN拡張」の処理に関するバグがありました。Firefoxは、この空のリストを正しく解釈できず、TLSハンドシェイクが失敗するか、接続がハングアップするなどの異常な動作を引き起こしました。これは、Firefoxが空のプロトコルリストを予期していなかったか、あるいはその処理ロジックに欠陥があったためと考えられます。

Goの観点から見ると、空のNPN拡張を送信すること自体は、TLSプロトコルの仕様に厳密に違反しているわけではありませんでした。しかし、現実世界のブラウザとの相互運用性を考慮すると、この挙動は問題を引き起こしていました。特に、`net/http` パッケージが自動的に `NextProtos` に `"http/1.1"` を設定するため、多くのGoユーザーは問題に気づきませんでしたが、`crypto/tls` を直接利用してカスタムサーバーを構築する開発者は、このFirefoxのバグに遭遇し、デバッグに時間を費やす必要がありました。

このコミットは、この問題を回避するために、`config.NextProtos` が空の場合には、NPN拡張自体を `ServerHello` に含めないというシンプルなロジック変更を導入しました。これにより、Firefoxは空のNPN拡張を受け取ることがなくなり、バグがトリガーされなくなります。

## コアとなるコードの変更箇所

変更は `src/pkg/crypto/tls/handshake_server.go` ファイルの1箇所のみです。

```diff
--- a/src/pkg/crypto/tls/handshake_server.go
+++ b/src/pkg/crypto/tls/handshake_server.go
@@ -156,7 +156,11 @@ Curves:
  	if len(hs.clientHello.serverName) > 0 {
  		c.serverName = hs.clientHello.serverName
  	}
-	if hs.clientHello.nextProtoNeg {
+	// Although sending an empty NPN extension is reasonable, Firefox has
+	// had a bug around this. Best to send nothing at all if
+	// config.NextProtos is empty. See
+	// https://code.google.com/p/go/issues/detail?id=5445.
+	if hs.clientHello.nextProtoNeg && len(config.NextProtos) > 0 {
  		hs.hello.nextProtoNeg = true
  		hs.hello.nextProtos = config.NextProtos
  	}
```

## コアとなるコードの解説

変更された行は、TLSサーバーハンドシェイク中にNPN拡張を `ServerHello` メッセージに含めるかどうかを決定する条件式です。

元のコード:
```go
if hs.clientHello.nextProtoNeg {
    hs.hello.nextProtoNeg = true
    hs.hello.nextProtos = config.NextProtos
}
```
このコードは、クライアントが `ClientHello` メッセージでNPN拡張を要求している場合 (`hs.clientHello.nextProtoNeg` が `true`)、サーバーはNPN拡張を `ServerHello` に含める (`hs.hello.nextProtoNeg = true`) というロジックでした。このとき、サーバーが提示するプロトコルリスト (`hs.hello.nextProtos`) は `config.NextProtos` の内容になります。もし `config.NextProtos` が空のスライスであっても、NPN拡張自体は送信されていました。

変更後のコード:
```go
if hs.clientHello.nextProtoNeg && len(config.NextProtos) > 0 {
    hs.hello.nextProtoNeg = true
    hs.hello.nextProtos = config.NextProtos
}
```
この変更では、条件式に `&& len(config.NextProtos) > 0` が追加されました。
これにより、NPN拡張を送信する条件が以下の2つになりました。

1.  `hs.clientHello.nextProtoNeg`: クライアントがNPN拡張を要求していること。
2.  `len(config.NextProtos) > 0`: サーバーの `tls.Config` に、ネゴシエート可能なアプリケーションプロトコルが少なくとも1つ設定されていること。

この修正により、`config.NextProtos` が空の場合、たとえクライアントがNPNを要求していても、サーバーはNPN拡張を `ServerHello` に含めなくなります。これにより、Firefoxのバグがトリガーされるのを防ぎ、互換性の問題が解決されます。

コメントで示されているように、「空のNPN拡張を送信することは合理的である」という認識はありましたが、Firefoxのバグを回避するために、より安全な選択肢として「`config.NextProtos` が空の場合は何も送信しない」という方針が取られました。

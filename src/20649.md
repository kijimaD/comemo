# [インデックス 20649] ファイルの概要

このコミットは、Go言語のツールチェーンにおいて、プログラムがクラッシュした際に報告されるエラーメッセージの改善を目的としています。具体的には、`cmd/go` コマンドが外部ツール（リンカなど）を実行し、そのツールがクラッシュした場合に、エラーメッセージにクラッシュしたプログラムの名前を含めるように変更が加えられました。これにより、問題の特定とデバッグが容易になります。

## 変更の背景

Go言語のビルドプロセスでは、`go` コマンドがコンパイラやリンカといった様々な外部ツールを呼び出して実行可能ファイルを生成します。以前は、これらの外部ツールがクラッシュした場合、`go` コマンドは単に「exit status 1」のような一般的なエラーメッセージを報告するだけでした。このメッセージだけでは、どのツールがクラッシュしたのか、なぜクラッシュしたのかを特定するのが困難であり、デバッグの妨げとなっていました。

この問題はGo issue #6823として報告されており、開発者からの要望として、クラッシュしたプログラムの名前をエラーメッセージに含めることで、より具体的な情報を提供し、デバッグプロセスを改善することが求められていました。このコミットは、その要望に応える形で、エラー報告の質を向上させるために導入されました。

## 前提知識の解説

### Goのビルドプロセスと `cmd/go`

Go言語のプログラムをビルドする際、`go build` コマンドが中心的な役割を果たします。このコマンドは、ソースコードのコンパイル、依存関係の解決、そして最終的な実行可能ファイルのリンクといった一連のプロセスをオーケストレーションします。`cmd/go` は、これらのタスクを実行するために、内部的に `go tool compile` や `go tool link` といった他のGoツールを呼び出します。

### Goのリンカ (`cmd/ld`)

`cmd/ld` はGo言語のリンカであり、コンパイラによって生成されたオブジェクトファイル（`.o` ファイル）を結合し、必要なライブラリとリンクして、最終的な実行可能ファイルを生成する役割を担います。リンカは非常に複雑な処理を行うため、稀に内部的なエラーや不正な入力によってクラッシュすることがあります。

### エラーハンドリングと `exit status`

Unix/Linuxシステムでは、プログラムが正常に終了したか、または何らかのエラーで終了したかを示すために「終了ステータス（exit status）」を使用します。慣例として、`0` は成功を意味し、`0` 以外の値（通常は `1`）はエラーを示します。しかし、`exit status 1` だけでは、具体的にどのようなエラーが発生したのか、どのプログラムがエラーを発生させたのかという詳細な情報は得られません。

### `cmd/go` の `runOut` 関数

`src/cmd/go/build.go` 内にある `runOut` 関数は、`cmd/go` が外部コマンド（コンパイラ、リンカなど）を実行する際に使用される内部ヘルパー関数です。この関数は、指定されたコマンドを実行し、その標準出力と標準エラー出力をキャプチャし、コマンドの終了ステータスをチェックしてエラーを返します。

## 技術的詳細

このコミットは、主に3つのファイルにわたる変更で構成されており、それぞれがエラー報告の改善という目標に貢献しています。

### `src/cmd/go/build.go` の変更

このファイルでは、`runOut` 関数が変更されました。以前は、外部コマンドがエラーを返した場合、そのエラーオブジェクトがそのまま返されていました。変更後、エラーが `nil` でない場合、エラーメッセージの先頭に実行されたプログラムの名前 (`cmdline[0]`) が追加されるようになりました。

例えば、リンカがクラッシュして「exit status 1」というエラーを返した場合、変更前は単に「exit status 1」と表示されていましたが、変更後は「/path/to/linker: exit status 1」のように、クラッシュしたプログラムのパスと名前が明示的に表示されるようになります。これにより、ユーザーはどのツールが問題を引き起こしたのかを一目で理解できるようになります。

コメントにもあるように、`buf.Bytes()` が非空の場合、通常は `err` が表示されないため、この変更がほとんどの出力で冗長になることはありません。これは、外部コマンドが標準エラー出力に詳細なエラーメッセージを出力する場合、その出力が優先されるためです。この変更は、外部コマンドが詳細なエラーメッセージを出力せず、単に非ゼロの終了ステータスを返すような場合に特に有効です。

### `src/cmd/go/test.bash` の変更

このファイルでは、新しいテストケースが追加されました。このテストは、`cmd/go` が外部ツールのクラッシュを正しく報告し、その際にプログラム名を含めることを検証します。

テストでは、`go build` コマンドに `-ldflags -crash_for_testing` という特殊なリンカフラグを渡して `helloworld.go` をビルドしようとします。この `-crash_for_testing` フラグは、リンカを意図的にクラッシュさせるために使用されます。テストスクリプトは、ビルドが失敗することを確認し、そのエラー出力にリンカの名前（例: `/tool/.*/$linker`）が含まれているかを `grep -q` コマンドでチェックします。これにより、エラーメッセージにプログラム名が含まれるという新しい動作が正しく機能していることが保証されます。

### `src/cmd/ld/pobj.c` の変更

このファイルはGoリンカ (`cmd/ld`) のソースコードの一部であり、テスト目的でリンカを意図的にクラッシュさせるための隠しフラグ `-crash_for_testing` が追加されました。

`main` 関数内でコマンドライン引数をループし、`-crash_for_testing` フラグが見つかった場合、`*(volatile int*)0 = 0;` というコードが実行されます。このコードは、アドレス `0` のメモリに整数 `0` を書き込もうとします。通常、アドレス `0` はオペレーティングシステムによって保護されており、ユーザープログラムがアクセスすることはできません。したがって、この操作はセグメンテーション違反（Segmentation Fault）を引き起こし、プログラムをクラッシュさせます。

`volatile` キーワードは、コンパイラがこのメモリ操作を最適化によって削除しないようにするために重要です。コンパイラは、`*(int*)0 = 0;` のようなコードが意味のない操作であると判断し、最適化の一環として削除してしまう可能性があります。`volatile` を付けることで、コンパイラに対してこの操作が外部の状態に影響を与える可能性があることを伝え、最適化を抑制します。これにより、テスト時に確実にクラッシュが発生するようになります。

このフラグは、標準のフラグパーサーには含まれておらず、使用メッセージにも表示されない「未公開」のフラグです。これは、通常のユーザーがこのフラグを使用することを意図しておらず、テスト目的でのみ使用されるためです。

## コアとなるコードの解説

### `src/cmd/go/build.go` の `runOut` 関数内の変更

```go
		if err != nil {
			err = errors.New(cmdline[0] + ": " + err.Error())
		}
```
このコードブロックは、`runOut` 関数が外部コマンドの実行結果としてエラー (`err`) を受け取った場合に実行されます。
- `if err != nil`: エラーが発生した場合にのみ、以下の処理を実行します。
- `cmdline[0]`: 実行されたコマンドのパスまたは名前を表します。例えば、リンカが実行された場合は `/path/to/go/pkg/tool/linux_amd64/link` のような値が入ります。
- `err.Error()`: 元のエラーメッセージ（例: "exit status 1"）を取得します。
- `errors.New(...)`: 新しいエラーオブジェクトを作成します。この新しいエラーメッセージは、`cmdline[0]` と ": "、そして元のエラーメッセージを結合した形になります。これにより、エラーメッセージが「`/path/to/linker: exit status 1`」のようになり、どのプログラムがエラーを発生させたのかが明確になります。

### `src/cmd/go/test.bash` の `TEST 'program name in crash messages'` ブロック

```bash
TEST 'program name in crash messages'
linker=$(./testgo env GOCHAR)l
d=$(TMPDIR=/var/tmp mktemp -d -t testgoXXX)
./testgo build -ldflags -crash_for_testing $(./testgo env GOROOT)/test/helloworld.go 2>$d/err.out || true
if ! grep -q "/tool/.*/$linker" $d/err.out; then
	echo "missing linker name in error message"
	cat $d/err.out
	ok=false
fi
rm -r $d
```
このシェルスクリプトのテストブロックは、以下の手順でエラーメッセージの改善を検証します。
1. `linker=$(./testgo env GOCHAR)l`: 現在の環境のリンカ名を取得します（例: `5l`, `6l`, `8l` など）。
2. `d=$(TMPDIR=/var/tmp mktemp -d -t testgoXXX)`: 一時ディレクトリを作成します。
3. `./testgo build -ldflags -crash_for_testing $(./testgo env GOROOT)/test/helloworld.go 2>$d/err.out || true`:
   - `testgo build`: `go build` コマンドのテスト用ラッパーを実行します。
   - `-ldflags -crash_for_testing`: リンカに `-crash_for_testing` フラグを渡します。このフラグはリンカを意図的にクラッシュさせます。
   - `$(./testgo env GOROOT)/test/helloworld.go`: ビルド対象のシンプルなGoプログラムです。
   - `2>$d/err.out`: 標準エラー出力を一時ファイル `err.out` にリダイレクトします。
   - `|| true`: ビルドがエラーで終了してもスクリプトが停止しないようにします。
4. `if ! grep -q "/tool/.*/$linker" $d/err.out; then ... fi`:
   - `grep -q "/tool/.*/$linker" $d/err.out`: `err.out` ファイルの内容に、リンカのパスと名前（例: `/path/to/tool/linux_amd64/6l`）が含まれているかを検索します。`-q` オプションはマッチした行を出力せず、終了ステータスのみを返します。
   - `! grep -q ...`: `grep` がマッチしなかった場合（つまり、リンカ名がエラーメッセージに含まれていない場合）に、テストを失敗とします。
   - `echo "missing linker name in error message"` と `cat $d/err.out`: テストが失敗した場合、デバッグのためにメッセージとエラー出力の内容を表示します。
   - `ok=false`: テストの全体的な成功/失敗を追跡する変数 `ok` を `false` に設定します。
5. `rm -r $d`: 一時ディレクトリを削除します。

### `src/cmd/ld/pobj.c` の `main` 関数内の変更

```c
	// For testing behavior of go command when tools crash.
	// Undocumented, not in standard flag parser to avoid
	// exposing in usage message.
	for(i=1; i<argc; i++)
		if(strcmp(argv[i], "-crash_for_testing") == 0)
			*(volatile int*)0 = 0;
```
このC言語のコードブロックは、Goリンカ (`cmd/ld`) の `main` 関数内にあります。
- `for(i=1; i<argc; i++)`: コマンドライン引数をループ処理します。`argv[0]` はプログラム名なので、`1` から開始します。
- `if(strcmp(argv[i], "-crash_for_testing") == 0)`: 現在の引数が文字列 `"-crash_for_testing"` と一致するかどうかをチェックします。
- `*(volatile int*)0 = 0;`: この行が、リンカを意図的にクラッシュさせる核心部分です。
    - `(int*)0`: メモリアドレス `0` を `int` 型へのポインタとしてキャストします。
    - `*(volatile int*)0`: そのポインタが指すメモリ位置（アドレス `0`）にアクセスします。
    - `= 0;`: そのメモリ位置に整数 `0` を書き込もうとします。
    - `volatile`: このキーワードは、コンパイラに対して、このメモリ操作が外部の状態に影響を与える可能性があるため、最適化によって削除したり、順序を変更したりしないように指示します。これにより、確実にセグメンテーション違反が発生し、プログラムがクラッシュします。
- コメントにあるように、このフラグはテスト目的でのみ使用され、通常のユーザーには公開されていません。

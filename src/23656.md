## 変更の背景

このコミットの主な背景は、Goツールチェインのテストスイートである `test.bash` が、何らかの理由で失敗するようになったことです。テストが失敗する原因は複数考えられますが、このコミットでは以下の点が対処されています。

1.  **`go get` のエラーメッセージの変更**: `go get` コマンドがカスタムインポートパスを処理する際のエラーメッセージが変更されたため、既存のテストがその新しいメッセージを認識できなくなっていました。
2.  **`gccgo` のテスト環境の依存性**: `cgo` と `gccgo` を使用したリンキングに関するテストが、`gccgo` コンパイラがシステムに存在しない環境でも実行され、失敗していました。
3.  **リンカーのクラッシュシミュレーションの改善**: リンカーがテスト目的でクラッシュする挙動をシミュレートする際、実際のクラッシュではなく、より制御された終了コードを返すように変更する必要がありました。これにより、テストの信頼性とデバッグの容易性が向上します。
4.  **`go vet` のテストの堅牢化**: `go vet` コマンドのテストが、`GOPATH` の設定や `vet` ツールの取得に依存しており、テスト環境の変動に弱かった可能性があります。
5.  **`testdata` ディレクトリの誤認識防止**: Goのビルドシステムが `testdata` ディレクトリを誤って通常のパッケージとして認識し、インポートパス解決の際に問題を引き起こす可能性がありました。

これらの問題に対処することで、`test.bash` が様々な環境で安定して動作し、Goツールチェインの品質保証が維持されるようになります。

## 前提知識の解説

### Goのビルドシステムと `go get`

Go言語のビルドシステムは、ソースコードをコンパイルし、実行可能なバイナリを生成する一連のツールとプロセスを指します。その中心となるのが `go` コマンドです。
`go get` は、リモートリポジトリからGoパッケージとその依存関係をダウンロードし、ローカルの `GOPATH` (Go Modules導入前) またはモジュールキャッシュにインストールするためのコマンドです。カスタムインポートパスは、GitHubなどのホスティングサービス以外の独自のドメイン名を使用してパッケージをインポートする際に使用されます。この場合、`go get` は指定されたドメインにアクセスし、HTML内の `go-import` メタタグを解析して、実際のソースコードリポジトリの場所を特定します。

### `cgo` と `gccgo`、`LDFLAGS`

*   **`cgo`**: GoプログラムからC言語のコードを呼び出したり、その逆を行ったりするためのGoツールです。`import "C"` を使用してCコードをGoプログラムに統合します。
*   **`gccgo`**: 標準の `gc` コンパイラとは異なる、GCC (GNU Compiler Collection) をバックエンドとするGoコンパイラです。`cgo` は `gccgo` 用の出力を生成することもできます。
*   **`LDFLAGS`**: リンカーに渡されるフラグです。`cgo` を使用する際、Goソースコード内の `#cgo LDFLAGS:` ディレクティブを通じて、リンクするライブラリ（例: `-lmy_library`）やライブラリの検索パス（例: `-L/path/to/libs`）を指定できます。

### `go vet`

`go vet` は、Goプログラムの静的解析ツールです。コード内の疑わしい構成（例: 書式文字列の不一致、到達不能なコード、ロックの誤用など）を報告し、潜在的なバグやコード品質の問題を特定するのに役立ちます。

### `testdata` ディレクトリ

Goの慣習として、テストに関連するデータファイルは `testdata` という名前のディレクトリに配置されます。Goツールチェインは、`go build` や `go install` の際に `testdata` ディレクトリを自動的に無視し、ビルド対象に含めません。これは、テストデータが最終的なバイナリに含まれるのを防ぎ、テストとプロダクションコードの分離を明確にするための重要な機能です。

### リンカーのクラッシュシミュレーション

ソフトウェア開発において、特定のコンポーネントが予期せず終了する（クラッシュする）状況をテストすることは重要です。Goのリンカーのような基盤ツールの場合、そのクラッシュ挙動が上位の `go` コマンドにどのように影響するかをテストするために、意図的にクラッシュをシミュレートするメカニズムが組み込まれることがあります。

## 技術的詳細

### `src/cmd/go/test.bash` の変更

*   **`go get` エラーメッセージの適応**:
    `testmove` 関数内で、`go get -d -u $url` コマンドの出力に対する `grep` パターンが変更されました。以前は `grep 'should be from'` を使用していましたが、これが `grep 'is a custom import path for'` に変更されました。これは、`go get` コマンドがカスタムインポートパスの解決に失敗した際に表示するエラーメッセージの文言が変更されたことを示しており、テストスクリプトが新しいメッセージに適合するように更新されたものです。
*   **`hg` および `svn` テストの一時的な無効化**:
    `testmove hg` と `testmove svn` の呼び出しがコメントアウトされ、それぞれ「TODO(rsc): Set up a test case on bitbucket for hg.」と「TODO(rsc): Set up a test case on SourceForge (?) for svn.」というコメントが追加されました。これは、Mercurial (hg) および Subversion (svn) リポジトリに対する `go get` のテストケースが、現在の環境では適切に機能しないか、新しいテスト環境のセットアップが必要であることを示唆しています。一時的に無効化することで、他のテストの実行を妨げないようにしています。
*   **`gccgo` テストの条件付き実行**:
    Issue 7573 (`cmd/cgo: undefined reference when linking a C-library using gccgo`) に関連するテストブロック全体が、`if which gccgo >/dev/null; then ... fi` という条件文で囲まれました。これにより、このテストはシステムに `gccgo` コンパイラがインストールされており、かつPATHが通っている場合にのみ実行されるようになります。これは、`gccgo` がすべてのGo開発環境に必須ではないため、テストの実行環境に柔軟性を持たせるための変更です。
*   **`testdata/std.out` のクリーンアップ追加**:
    `file with non-runnable example was not built` のテスト後に `rm -f testdata/std.out` が追加されました。これは、テスト実行によって生成された一時ファイルを確実にクリーンアップし、後続のテストや環境に影響を与えないようにするための保守的な変更です。
*   **`go vet` テストの改善**:
    `TEST go vet with external tests` のブロックで、`export GOPATH=$d` の後に `./testgo get golang.org/x/tools/cmd/vet` が追加されました。これは、`go vet` のテストを実行する前に、テスト専用の `GOPATH` を設定し、`golang.org/x/tools/cmd/vet` パッケージを明示的に取得することで、テストの独立性と再現性を高めています。これにより、テスト環境に `vet` ツールが事前にインストールされているかどうかに依存せず、テストが常に必要なツールを利用できるようになります。また、クリーンアップ処理も `rm -rf testdata/bin testdata/bin1 testdata/std.out` に更新され、より多くの生成物を削除するようになりました。

### `src/cmd/link/internal/ld/pobj.go` の変更

*   **リンカーのクラッシュシミュレーションの変更**:
    `-crash_for_testing` フラグが指定された際の挙動が変更されました。以前は `*(*int)(nil) = 0` というnilポインタデリファレンスによってプログラムをクラッシュさせていましたが、これを `os.Exit(2)` に変更しました。
    *   `*(*int)(nil) = 0`: これはGoプログラムでnilポインタをデリファレンスしようとするもので、通常はセグメンテーション違反（segmentation fault）を引き起こし、プログラムが予期せず異常終了します。これは制御不能なクラッシュであり、デバッグが難しい場合があります。
    *   `os.Exit(2)`: これはGoプログラムを終了コード `2` で正常に終了させる関数です。終了コード `0` は成功を意味し、非ゼロの値はエラーを示します。この変更により、リンカーは「クラッシュ」する代わりに、特定の終了コードを返して終了するようになります。
    この変更の意図は、リンカーが「サイレントにクラッシュする」（`// For testing behavior of go command when tools crash silently.`）状況をより正確にシミュレートすることです。`os.Exit(2)` は、オペレーティングシステムに対してエラー状態を明確に伝えつつ、デバッガがアタッチされていない環境でも予測可能な挙動を提供します。これにより、`go` コマンドがリンカーの異常終了をどのように処理するかをテストする際の信頼性が向上します。

### `src/go/build/build.go` の変更

*   **`testdata` ディレクトリのインポートパスからの除外**:
    `Import` 関数内で、パッケージの正規インポートパスを決定するロジックに `inTestdata` という新しいヘルパー関数が導入されました。
    `inTestdata` 関数は、与えられたサブパスが `/testdata/` を含むか、`/testdata` で終わるか、`testdata/` で始まるか、あるいは完全に `testdata` であるかをチェックします。
    この `inTestdata` 関数が、`ctxt.hasSubdir` の結果を評価する際に `&& !inTestdata(sub)` という形で組み込まれました。具体的には、`GOROOT` および `GOPATH` 内でサブディレクトリを検索し、それが有効なパッケージのルートであるかを判断する際に、そのサブディレクトリが `testdata` ディレクトリに関連するパスでないことを確認するようになりました。
    この変更は、Goのビルドシステムが `testdata` ディレクトリを誤って通常のソースコードパッケージとして解釈し、インポートパス解決の対象に含めてしまうことを防ぐためのものです。`testdata` はテストデータ専用であり、ビルド対象のパッケージとして扱われるべきではありません。この明示的な除外ルールにより、ビルドの堅牢性が向上し、`testdata` 内のファイルが意図せずビルドプロセスに影響を与える可能性が排除されます。

## コアとなるコードの解説

### `src/cmd/go/test.bash`

*   `elif ! grep 'is a custom import path for' $d/err >/dev/null; then`: `go get` のエラーメッセージの変更に対応するため、`grep` の検索パターンを更新しました。これにより、テストが新しいエラーメッセージを正しく認識し、誤って失敗するのを防ぎます。
*   `# TODO(rsc): Set up a test case on bitbucket for hg.` / `# TODO(rsc): Set up a test case on SourceForge (?) for svn.`：`hg` と `svn` のテストケースを一時的にコメントアウトし、将来的な対応を促すTODOコメントを追加しました。これは、これらのテストが現在の環境で不安定であるか、新しいテストインフラストラクチャが必要であることを示唆しています。
*   `if which gccgo >/dev/null; then ... fi`: `gccgo` を使用するテストを条件付きで実行するように変更しました。`which gccgo` コマンドで `gccgo` がシステムに存在するかどうかを確認し、存在する場合にのみテストブロックを実行します。これにより、`gccgo` がインストールされていない環境でのテスト失敗を防ぎ、テストスイートの柔軟性を高めます。
*   `rm -f testdata/std.out`: テストによって生成された一時ファイル `testdata/std.out` を削除するクリーンアップ処理を追加しました。
*   `export GOPATH=$d` と `./testgo get golang.org/x/tools/cmd/vet`: `go vet` のテストの前に、一時的な `GOPATH` を設定し、`golang.org/x/tools/cmd/vet` を明示的に取得するようにしました。これにより、テストが自己完結型となり、外部環境に依存せず、常に正しい `vet` ツールを使用して実行されることが保証されます。

### `src/cmd/link/internal/ld/pobj.go`

*   `// For testing behavior of go command when tools crash silently.`: コメントが「tools crash」から「tools crash silently」に変更されました。これは、リンカーのテストにおけるクラッシュシミュレーションの意図が、より制御された、静かな終了に変更されたことを示唆しています。
*   `os.Exit(2)`: `-crash_for_testing` フラグが指定された際に、以前のnilポインタデリファレンスによる実際のクラッシュ（`*(*int)(nil) = 0`）を `os.Exit(2)` に置き換えました。これにより、リンカーは特定の終了コード `2` を返して終了します。これは、実際のクラッシュよりも予測可能で、`go` コマンドがリンカーの異常終了をどのように処理するかをテストする際に、より信頼性の高い方法を提供します。

### `src/go/build/build.go`

*   `inTestdata := func(sub string) bool { ... }`: `testdata` ディレクトリに関連するパスを識別するための匿名関数 `inTestdata` を定義しました。この関数は、サブパスが `/testdata/` を含むか、`/testdata` で終わるか、`testdata/` で始まるか、または完全に `testdata` であるかをチェックします。
*   `if sub, ok := ctxt.hasSubdir(root, p.Dir); ok && !inTestdata(sub) { ... }`: `ctxt.hasSubdir` が有効なサブディレクトリを返した場合に、さらに `!inTestdata(sub)` という条件を追加しました。これは、`GOROOT` や `GOPATH` 内でパッケージのインポートパスを解決する際に、`testdata` ディレクトリが誤ってパッケージとして認識されるのを防ぐためのものです。この変更により、ビルドシステムは `testdata` ディレクトリを明示的に無視し、テストデータがビルドプロセスに混入するのを防ぎます。

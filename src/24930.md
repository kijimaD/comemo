## 変更の背景

GoコンパイラのSSAバックエンドにおける共通部分式除去 (CSE) パスでは、コードの最適化のために頻繁に「あるブロックが別のブロックをドミネートするか」というドミネータクエリを実行します。従来のドミネータクエリの実装は、ドミネータツリーの深さに比例する計算量 (O(depth)) を持っていました。しかし、CSEパス内でこのクエリが繰り返し実行される場合、特に大規模な関数や複雑な制御フローグラフを持つ関数では、全体の計算量がブロック数の二乗 (N^2) に悪化する可能性がありました。

このN^2の計算量は、コンパイル時間の著しい増加を引き起こすため、以前は `f.NumBlocks() > 10000` のような条件で、ブロック数が一定以上の場合にCSEをスキップするという一時的な回避策が導入されていました。これは、最適化を諦めることでコンパイル時間の問題を回避するものであり、根本的な解決にはなっていませんでした。

このコミットの目的は、ドミネータクエリの効率を抜本的に改善し、N^2のパフォーマンスボトルネックを解消することにあります。これにより、CSEをより多くの関数に適用できるようになり、コンパイル時間への悪影響なしに最適化の恩恵を拡大することが可能になります。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA (Static Single Assignment) 形式は、コンパイラ最適化において広く用いられる中間表現 (IR) の一種です。SSA形式では、プログラム中の各変数がただ一度だけ代入されるという特性を持ちます。これにより、データフロー解析が簡素化され、共通部分式除去 (CSE) やデッドコード除去 (DCE) など、多くの最適化が容易になります。Goコンパイラも、最適化のバックエンドでSSA形式を採用しています。

### 2. CSE (Common Subexpression Elimination)

共通部分式除去 (CSE) は、コンパイラ最適化の一種で、プログラム内で複数回計算されている同じ式（共通部分式）を検出し、その計算結果を一度だけ計算して再利用することで、冗長な計算を削減します。これにより、実行速度の向上やコードサイズの削減が期待できます。CSEを適用するためには、ある共通部分式が計算された値が、その後の使用箇所まで変更されずに「利用可能」であること（つまり、その値がドミネートされていること）を確認する必要があります。

### 3. ドミネータツリー (Dominator Tree)

制御フローグラフ (CFG) において、あるブロック `D` が別のブロック `B` を「ドミネートする」とは、プログラムのエントリポイントから `B` へのすべてのパスが `D` を通過する場合を指します。ドミネータツリーは、このドミネート関係をツリー構造で表現したものです。ツリーの根はエントリブロックであり、各ブロックの親は、そのブロックを直接ドミネートするブロック（即時ドミネータ）となります。ドミネータツリーは、SSA形式の構築や様々な最適化において中心的な役割を果たします。

### 4. ドミネータクエリの効率化

ドミネータツリーが構築された後、「ブロック `A` がブロック `B` をドミネートするか？」というクエリは頻繁に発生します。素朴な実装では、ドミネータツリーを `B` から根に向かって辿り、途中で `A` が見つかるかをチェックします。この操作はツリーの深さに比例する計算量 (O(depth)) を持ちます。CSEのように多数のクエリが必要な場合、このO(depth)のクエリが繰り返されることで、全体の計算量がN^2に悪化する可能性があります。効率的なコンパイラでは、このクエリをO(1)またはO(log N)で実行できるようなデータ構造やアルゴリズムが用いられます。

### 5. ツリーナンバリング (Tree Numbering)

ツリーナンバリングは、ツリーのノードに番号を割り当てることで、ノード間の関係（親子関係、祖先-子孫関係など）を効率的に判定できるようにする技術です。一般的な方法として、深さ優先探索 (DFS) を用いて、各ノードが最初に訪問された時刻 (entry time) と、そのノードのサブツリーの探索が完了した時刻 (exit time) を記録する手法があります。

この手法では、ノード `X` がノード `Y` の祖先である（または `X` と `Y` が同じノードである）場合、`X` の entry time が `Y` の entry time 以下であり、かつ `Y` の exit time が `X` の exit time 以下である、という関係が成り立ちます。この関係を利用することで、祖先-子孫関係のチェックを定数時間 (O(1)) で行えるようになります。これは、ドミネータツリーにおけるドミネート関係のチェックに直接応用できます。

## 技術的詳細

### 1. 既存の問題点: N^2 ドミネータクエリ

このコミット以前の `cse.go` では、ドミネータクエリに `dom(b, c *Block, idom []*Block) bool` 関数を使用していました。この関数は、ブロック `c` からその即時ドミネータ (`idom` 配列で表現される親) を辿っていき、ブロック `b` に到達するかどうかをチェックするものでした。この操作は、最悪の場合、ドミネータツリーの深さに比例する計算量 (O(depth)) を持ちます。

CSEパスでは、共通部分式候補のペアに対してドミネート関係を頻繁にチェックする必要があるため、多数のブロックを持つ関数では `N` 個のブロックに対して `N` 回のドミネータクエリが実行されると、全体の計算量が `O(N * depth)` となり、ツリーが線形に近い形（深いツリー）の場合には `O(N^2)` に近づく可能性がありました。これが、大規模な関数でコンパイル時間が長くなる原因となっていました。

### 2. 解決策: sparseTree データ構造の導入

このコミットでは、このN^2の問題を解決するために、新しいデータ構造 `sparseTree` を導入しました。`sparseTree` は、ドミネータツリーの各ブロックに「entry」と「exit」という2つの番号を割り当てるツリーナンバリングの手法に基づいています。これにより、2つのブロック間のドミネート関係を定数時間 (O(1)) で判定できるようになります。

### 3. sparseTree の構造

`sparseTree` は `sparseTreeNode` のスライスとして実装されています。各 `sparseTreeNode` は以下のフィールドを持ちます。

*   `block *Block`: このノードが表す制御フローグラフのブロック。
*   `child *Block`: このノードの最初の子ブロック。
*   `sibling *Block`: このノードの次の兄弟ブロック。
*   `parent *Block`: このノードの親ブロック。
*   `entry, exit int32`: ツリーナンバリングによって割り当てられる、このブロックの「入時刻」と「出時刻」。

`ADJUST_BEFORE`, `ADJUST_TOP`, `ADJUST_BOTTOM` という定数も定義されており、これらは特定の定義がブロックのどの位置（phi関数の前、phi関数、ブロック内）で発生したかを区別するために、`entry` および `exit` 番号に調整を加える際に使用されます。

### 4. ツリーナンバリングのアルゴリズム (`numberBlock`)

`sparseTree` の構築時に、`newSparseTree` 関数が `numberBlock` メソッドを呼び出して、各ブロックに `entry` と `exit` 番号を割り当てます。`numberBlock` は深さ優先探索 (DFS) のようにツリーを走査し、以下のように番号を割り当てます。

1.  ブロック `b` に入る際、`entry` 番号を割り当てます。この際、`entry-1` のための番号も予約されます。
2.  `b` のすべての子ブロックに対して再帰的に `numberBlock` を呼び出します。
3.  すべての子ブロックの処理が完了し、`b` に戻ってきた際、`exit` 番号を割り当てます。この際、`exit-1` と `exit+1` のための番号も予約されます。

この「gappy sequence」（間隔を空けたシーケンス）の割り当て方により、`entry` と `exit` 番号の間に他のブロックの `entry` や `exit` 番号が入り込むことで、祖先-子孫関係を効率的に判定できるようになります。

### 5. 効率的なドミネータチェック (`isAncestorEq`)

`sparseTree` には、`isAncestorEq(x, y *Block) bool` というメソッドが追加されました。このメソッドは、ブロック `x` がブロック `y` の祖先であるか、または `x` と `y` が同じブロックであるかを判定します。これは、`x` と `y` の `entry` および `exit` 番号を比較するだけで、定数時間 (O(1)) で実行されます。

具体的には、`xx.entry <= yy.entry && yy.exit <= xx.exit` という条件が真であれば、`x` は `y` をドミネートします。これは、`y` のサブツリーが `x` のサブツリー内に完全に含まれることを意味します。

### 6. CSE への統合

`cse.go` では、ドミネータツリー (`idom`) の構築後、`sdom := newSparseTree(f, idom)` を呼び出して `sparseTree` を構築します。その後、ドミネータクエリが必要な箇所で、従来の `dom` 関数ではなく `sdom.isAncestorEq` メソッドを使用するように変更されました。

```go
// 変更前
if dom(w.Block, v.Block, idom) {
// 変更後
if sdom.isAncestorEq(w.Block, v.Block) {
```

この変更により、ドミネータクエリの計算量が O(depth) から O(1) に劇的に改善され、CSEパス全体のパフォーマンスが向上しました。

### 7. 「大きすぎる関数に対するスキップ」の削除

ドミネータクエリの効率が改善されたため、以前に導入されていた `f.NumBlocks() > 10000` という条件でCSEをスキップする回避策は不要となり、削除されました。これにより、大規模な関数に対してもCSEが適用されるようになり、より多くの最適化の機会が提供されます。

### `sparsetree.go` の主要な関数と構造体

`sparsetree.go` は、`sparseTree` データ構造とその操作を定義する新しいファイルです。

1.  **`sparseTreeNode` 構造体**:
    ```go
    type sparseTreeNode struct {
    	block   *Block
    	child   *Block
    	sibling *Block
    	parent  *Block

    	entry, exit int32
    }
    ```
    ドミネータツリーの各ノードを表します。`block` は対応する制御フローグラフのブロックです。`child`、`sibling`、`parent` はツリー構造を表現するためのポインタです。`entry` と `exit` は、ツリーナンバリングによって割り当てられる重要な番号で、ドミネート関係の効率的なチェックに利用されます。

2.  **`ADJUST_BEFORE`, `ADJUST_TOP`, `ADJUST_BOTTOM` 定数**:
    ```go
    const (
    	ADJUST_BEFORE = -1 // defined before phi
    	ADJUST_TOP    = 0  // defined by phi
    	ADJUST_BOTTOM = 1  // defined within block
    )
    ```
    これらの定数は、`entry` および `exit` 番号に調整を加える際に使用されます。これにより、ブロック内の異なる時点（例えば、phi関数の前、phi関数自体、ブロックの終わり）での定義の「有効範囲」を区別できるようになります。これは、より細かい粒度でのデータフロー解析や最適化に役立ちます。

3.  **`newSparseTree` 関数**:
    ```go
    func newSparseTree(f *Func, parentOf []*Block) sparseTree {
    	t := make(sparseTree, f.NumBlocks())
    	for _, b := range f.Blocks {
    		n := &t[b.ID]
    		n.block = b
    		if p := parentOf[b.ID]; p != nil {
    			n.parent = p
    			n.sibling = t[p.ID].child
    			t[p.ID].child = b
    		}
    	}
    	t.numberBlock(f.Entry, 1)
    	return t
    }
    ```
    `newSparseTree` は、`Func` オブジェクトと、各ブロックの即時ドミネータを示す `parentOf` 配列を受け取り、`sparseTree` を構築します。まず、`parentOf` 配列からツリーの親子・兄弟関係を構築し、その後 `numberBlock` メソッドを呼び出して各ノードに `entry` と `exit` 番号を割り当てます。

4.  **`numberBlock` メソッド**:
    ```go
    func (t sparseTree) numberBlock(b *Block, n int32) int32 {
    	// reserve n for entry-1, assign n+1 to entry
    	n++
    	t[b.ID].entry = n
    	// reserve n+1 for entry+1, n+2 is next free number
    	n += 2
    	for c := t[b.ID].child; c != nil; c = t[c.ID].sibling {
    		n = t.numberBlock(c, n) // preserves n = next free number
    	}
    	// reserve n for exit-1, assign n+1 to exit
    	n++
    	t[b.ID].exit = n
    	// reserve n+1 for exit+1, n+2 is next free number, returned.
    	return n + 2
    }
    ```
    このメソッドは、ツリーを深さ優先で走査し、各ブロック `b` に `entry` と `exit` 番号を割り当てます。番号は「gappy sequence」と呼ばれる、間に未使用の番号を挟む形式で割り当てられます。これにより、`entry` と `exit` 番号の範囲比較だけで祖先-子孫関係を判定できるという特性が生まれます。

5.  **`isAncestorEq` メソッド**:
    ```go
    func (t sparseTree) isAncestorEq(x, y *Block) bool {
    	xx := &t[x.ID]
    	yy := &t[y.ID]
    	return xx.entry <= yy.entry && yy.exit <= xx.exit
    }
    ```
    このメソッドは、ブロック `x` がブロック `y` の祖先であるか、または `x` と `y` が同じブロックであるかを判定します。これは、`x` の `entry` 番号が `y` の `entry` 番号以下であり、かつ `y` の `exit` 番号が `x` の `exit` 番号以下であるという条件をチェックするだけで、O(1) の計算量で実行できます。これは、`y` のサブツリーが `x` のサブツリー内に完全に含まれることを意味し、ドミネート関係の定義と一致します。

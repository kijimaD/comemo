# [インデックス 20441] ファイルの概要

このコミットは、Goランタイムにおける重要な変更を導入し、Goのスタック上でC言語のコードが実行される問題を診断し、修正することを目的としています。具体的には、Goのガーベージコレクタやスタック管理の仕組みとC言語のスタック利用が衝突することで発生する可能性のある、スタック破損やセキュリティ上の脆弱性といった問題を未然に防ぐための動的なチェック機構が導入されました。この変更により、Goランタイムの堅牢性と安全性が向上しています。

    liblink, runtime: diagnose and fix C code running on Go stack
    
    This CL contains compiler+runtime changes that detect C code
    running on Go (not g0, not gsignal) stacks, and it contains
    corrections for what it detected.
    
    The detection works by changing the C prologue to use a different
    stack guard word in the G than Go prologue does. On the g0 and
    gsignal stacks, that stack guard word is set to the usual
    stack guard value. But on ordinary Go stacks, that stack
    guard word is set to ^0, which will make any stack split
    check fail. The C prologue then calls morestackc instead
    of morestack, and morestackc aborts the program with
    a message about running C code on a Go stack.
    
    This check catches all C code running on the Go stack
    except NOSPLIT code. The NOSPLIT code is allowed,
    so the check is complete. Since it is a dynamic check,
    the code must execute to be caught. But unlike the static
    checks we've been using in cmd/ld, the dynamic check
    works with function pointers and other indirect calls.
    For example it caught sigpanic being pushed onto Go
    stacks in the signal handlers.

## 元コミット内容

このコミットは、Goのコンパイラ（`liblink`）とランタイム（`runtime`）にわたる広範な変更を含んでいます。主な目的は、Goの通常のゴルーチンスタック上でC言語のコードが実行されることを検出し、防止することです。

検出メカニズムは以下の通りです。
1.  **スタックガードワードの変更**: C言語の関数のプロローグ（関数が呼び出された直後に実行される初期設定コード）が、Goのプロローグとは異なる「スタックガードワード」を`G`（ゴルーチン）構造体内で使用するように変更されます。
2.  **特殊なスタックでの挙動**: `g0`スタック（ランタイム自身の処理に使用される特殊なスタック）や`gsignal`スタック（シグナルハンドラで使用される特殊なスタック）上では、スタックガードワードは通常のGoのスタックガード値に設定されます。これらのスタックはGoの通常のスタック管理の対象外であり、Cコードが実行されることが許容されるためです。
3.  **通常のGoスタックでの挙動**: しかし、通常のGoゴルーチンスタック上では、スタックガードワードは`^0`（ビット反転した0、つまりすべてのビットが1）に設定されます。この値は、いかなるスタック分割チェック（スタックの拡張が必要かどうかを判断するチェック）も必ず失敗させるように設計されています。
4.  **`morestackc`の呼び出し**: C言語のプロローグは、スタック分割チェックが失敗した場合に、通常の`morestack`（Goのスタック拡張関数）の代わりに`morestackc`を呼び出すように変更されます。
5.  **プログラムの中止**: `morestackc`は、「attempt to execute C code on Go stack」（Goスタック上でCコードを実行しようとしました）というメッセージを出力してプログラムを異常終了させます。

この動的なチェックは、`NOSPLIT`属性を持つCコード（スタック分割チェックを行わないようにコンパイラに指示されたコード）を除く、すべてのGoスタック上で実行されるCコードを捕捉します。`NOSPLIT`コードはGoスタック上での実行が許可されているため、このチェックは完全であると見なされます。

この動的なチェックの利点は、静的なチェック（例えば`cmd/ld`リンカで行われるチェック）では見逃される可能性のある、関数ポインタやその他の間接的な呼び出しを介したCコードの実行を検出できる点にあります。コミットメッセージでは、シグナルハンドラ内で`sigpanic`がGoスタックにプッシュされるケースを検出できたことが例として挙げられています。

このコミットは、Go Issue #8667を修正します。

## 変更の背景

Goランタイムは、効率的なメモリ管理と並行処理を実現するために、独自のスタック管理モデルを採用しています。Goのゴルーチンは、必要に応じてスタックを動的に拡張・縮小する「可変スタック」を使用します。このスタック管理は、Goのランタイムとガーベージコレクタが密接に連携して動作することを前提としています。

しかし、C言語で書かれたコード（特にCGOを介してGoから呼び出されるC関数や、Goランタイム内部でC言語で実装されている部分）が、Goの管理するゴルーチンスタック上で実行されると、問題が発生する可能性がありました。C言語のコードはGoのスタック管理の規約に従わないため、以下のような問題が引き起こされる恐れがありました。

1.  **スタックの破損**: CコードがGoスタックの境界を越えて書き込みを行ったり、GoランタイムがCコードのスタック利用を誤って解釈したりすることで、スタックが破損する可能性があります。
2.  **ガーベージコレクションの不正確さ**: Goのガーベージコレクタは、Goスタック上のポインタをスキャンして到達可能なオブジェクトを特定します。CコードがGoスタック上に不適切な方法でデータを配置したり、ポインタを保持したりすると、GCが誤動作し、本来回収されるべきメモリが回収されなかったり、逆にまだ使用中のメモリが回収されてしまったりする可能性があります。
3.  **セキュリティ上の脆弱性**: スタックの不適切な利用は、バッファオーバーフローなどのセキュリティ脆弱性につながる可能性があります。
4.  **デバッグの困難さ**: GoとCのスタックが混在することで、デバッグが非常に困難になることがあります。

このコミット以前にも、Goは静的なリンカレベルのチェックでCコードがGoスタック上で実行されることを防ごうとしていましたが、関数ポインタを介した間接的な呼び出しなど、すべてのケースを捕捉することはできませんでした。特に、シグナルハンドラのような低レベルの処理でCコードがGoスタックに侵入するケースは、Goランタイムの安定性に直接影響を与えるため、より堅牢な検出と防止メカニズムが必要とされていました。

このコミットは、このような問題を動的に検出し、プログラムを安全に終了させることで、Goランタイムの安定性と信頼性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とC言語の基本的な知識が必要です。

1.  **Goのゴルーチンとスタック**:
    *   **ゴルーチン (Goroutine)**: Goにおける軽量な実行単位です。OSのスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行できます。
    *   **可変スタック (Contiguous Stack)**: 各ゴルーチンは、最初は小さなスタック（数KB）で開始し、必要に応じて自動的にスタック領域を拡張します。スタックが不足しそうになると、Goランタイムはより大きな新しいスタックを割り当て、古いスタックの内容を新しいスタックにコピーし、スタックポインタを更新します。このプロセスを「スタック分割 (stack split)」と呼びます。
    *   **スタックガード (Stack Guard)**: スタックの拡張が必要かどうかを判断するために、Goランタイムはスタックの現在の境界を示す「スタックガード」と呼ばれる値を設定します。関数呼び出しのプロローグで、現在のスタックポインタがこのスタックガード値を超えていないかチェックします。超えている場合、スタック分割処理（`morestack`関数の呼び出し）が行われます。

2.  **`G`構造体**:
    *   Goランタイムは、各ゴルーチンの状態を`G`構造体で管理しています。この構造体には、スタックの開始アドレス、スタックの現在の境界（`stackguard0`）、そしてこのコミットで追加される`stackguard1`などの情報が含まれています。

3.  **`M`と`P`**:
    *   **`M` (Machine)**: OSのスレッドを表します。Goランタイムは、複数の`M`を管理し、その上でゴルーチンを実行します。
    *   **`P` (Processor)**: 論理プロセッサを表します。`P`は`M`とゴルーチンを仲介し、ゴルーチンが実行されるためのコンテキストを提供します。

4.  **`g0`スタックと`gsignal`スタック**:
    *   **`g0`スタック**: Goランタイムの内部処理（スケジューリング、ガーベージコレクションなど）を実行するための特別なスタックです。これはGoの通常のゴルーチンスタックとは異なり、固定サイズで、C言語のコードが実行されることが想定されています。
    *   **`gsignal`スタック**: シグナルハンドラが実行される際に使用される特別なスタックです。これも固定サイズで、C言語のコードが実行されることが想定されています。

5.  **CGO**:
    *   GoプログラムからC言語の関数を呼び出したり、C言語からGoの関数を呼び出したりするためのメカニズムです。CGOを介してGoとCが連携する際、スタックの管理は複雑になります。

6.  **関数プロローグ (Function Prologue)**:
    *   関数が呼び出された直後に実行されるアセンブリコードのシーケンスです。これには、スタックフレームのセットアップ、レジスタの保存、そしてGoの場合にはスタックガードチェックなどが含まれます。

7.  **`NOSPLIT`属性**:
    *   Goのコンパイラやリンカにおいて、特定の関数に付与される属性です。この属性が付与された関数は、スタック分割チェックを行いません。これは通常、非常に小さく、スタックをほとんど消費しない関数や、スタック分割処理自体が不可能な低レベルのランタイム関数に使用されます。

8.  **動的チェックと静的チェック**:
    *   **静的チェック**: コンパイル時やリンク時にコードを分析して問題を検出する方法です。例えば、リンカがCコードがGoスタック上で実行される可能性を検出する試みなど。
    *   **動的チェック**: プログラムの実行時に問題を検出する方法です。このコミットで導入されるスタックガードワードのチェックは動的チェックの一例です。動的チェックは、静的分析では捉えにくい間接的な呼び出しなどにも対応できます。

これらの概念を理解することで、このコミットがGoランタイムのスタック管理とCGOの相互作用において、いかに重要な改善をもたらしたかが明確になります。

## 技術的詳細

このコミットの技術的な核心は、Goのスタック管理モデルとC言語のスタック利用の間の不整合を動的に検出・防止するメカニズムにあります。

### 1. `G`構造体への`stackguard1`の追加

`src/runtime/runtime.h`の`G`構造体に`stackguard1`という新しいフィールドが追加されました。
```c
struct G
{
    // ...
    uintptr stackguard0;    // cannot move - also known to liblink, libmach, runtime/cgo
    uintptr stackbase;      // cannot move - also known to libmach, runtime/cgo
    Panic*  panic;          // cannot move - also known to liblink
    // stackguard1 is checked by C code; it is set to ~0 in ordinary (non-g0, non-gsignal) goroutines
    uintptr stackguard1;    // cannot move - also known to liblink
    // ...
};
```
この`stackguard1`は、C言語で書かれた関数がスタックチェックを行う際に参照する特別なスタックガード値として機能します。コメントにあるように、通常のゴルーチン（`g0`や`gsignal`ではない）では`~0`（すべてのビットが1）に設定されます。

### 2. C言語プロローグの変更 (`liblink/obj*.c`)

Goのリンカ（`liblink`）は、Goのソースコードから生成されるアセンブリコードだけでなく、CGOを介してGoプログラムにリンクされるC言語のコードのアセンブリも処理します。このコミットでは、`src/liblink/obj5.c` (ARM), `src/liblink/obj6.c` (x86), `src/liblink/obj8.c` (PowerPC) など、各アーキテクチャのコード生成部分が変更されました。

変更のポイントは、C言語で書かれた関数のプロローグにおいて、スタックチェックのロジックを修正することです。
*   `ctxt->cursym->cfunc`というフラグ（現在のシンボルがC関数であるかを示す）が導入され、C関数である場合に特別な処理を行います。
*   C関数では、スタックガード値として`g->stackguard1`（`3*ctxt->arch->ptrsize`のオフセットでアクセス）を使用するように変更されます。
*   スタックチェックが失敗した場合（つまり、スタックポインタが`g->stackguard1`を下回った場合）、通常の`runtime.morestack`の代わりに`runtime.morestackc`を呼び出すように変更されます。

これにより、通常のGoゴルーチンスタック上でC関数がスタック拡張を試みると、`g->stackguard1`が`~0`であるため、必ずチェックが失敗し、`runtime.morestackc`が呼び出されるようになります。

### 3. `runtime.morestackc`の導入 (`src/runtime/stack.c`)

`src/runtime/stack.c`に`runtime.morestackc`という新しい関数が追加されました。
```c
// src/runtime/stack.c
static void badc(void);

#pragma textflag NOSPLIT
void
runtime·morestackc(void)
{
    void (*fn)(void);

    fn = badc;
    runtime·onM(&fn);
}

static void
badc(void)
{
    runtime·throw("attempt to execute C code on Go stack");
}
```
`runtime.morestackc`は、`runtime.onM`を介して`badc`関数を呼び出します。`badc`関数は、`runtime.throw("attempt to execute C code on Go stack")`を呼び出し、プログラムを異常終了させます。これは、Goのスタック管理モデルに違反するCコードの実行を検出した際の、安全な停止メカニズムです。

### 4. `stackguard1`の初期化 (`src/runtime/proc.c`)

新しいゴルーチンが作成される際（`runtime.malg`）、その`G`構造体の`stackguard1`フィールドが初期化されます。
```c
// src/runtime/proc.c
// ...
runtime·malg(int32 stacksize)
{
    // ...
    newg->stackguard = (uintptr)stk + StackGuard;
    newg->stackguard0 = newg->stackguard;
    newg->stackguard1 = ~(uintptr)0; // For ordinary Go goroutines
    // ...
}
```
これにより、通常のGoゴルーチンでは`stackguard1`が`~0`に設定され、Cコードがそのスタック上で実行されると即座に検出されるようになります。

一方、`g0`スタックや`gsignal`スタックのような特別なスタックでは、`stackguard1`は通常の`stackguard`と同じ値に設定されます。
```c
// src/runtime/proc.c
// ...
mcommoninit(M *mp)
{
    // ...
    if(mp->gsignal)
        mp->gsignal->stackguard1 = mp->gsignal->stackguard;
    // ...
}

runtime·allocm(P *p)
{
    // ...
    mp->g0->stackguard1 = mp->g0->stackguard;
    // ...
}
```
これは、これらの特殊なスタック上ではCコードの実行が許可されているためです。

### 5. CGOコールバックとシグナルハンドラのGoへの移行

コミットメッセージで言及されているように、この変更は`sigpanic`がGoスタックにプッシュされる問題を検出しました。これに対応するため、`src/runtime/cgo/callbacks.c`にあった`_cgo_allocate_internal`や`_cgo_panic_internal`といったCGOコールバック関数が、`src/runtime/cgocallback.go`という新しいGoファイルに移行されました。同様に、各OS固有の`runtime.sigpanic`の実装（`src/runtime/os_darwin.c`など）が削除され、`src/runtime/sigpanic_unix.go`や`src/runtime/os_nacl.go`、`src/runtime/os_windows.go`といったGoファイルに統合されました。

これらの変更は、Goランタイムの重要な部分をC言語からGo言語へ移行させることで、Goのスタック管理モデルとの整合性を高め、CコードがGoスタック上で不適切に実行されるリスクを根本的に減らすことを目的としています。

### 6. `runtime.main`のGoへの移行

`src/runtime/proc.c`にあった`runtime.main`関数（Goプログラムのエントリポイントとなるメインゴルーチンの処理）が、`src/runtime/proc.go`に完全に移行されました。これは非常に大きな変更であり、Goランタイムの初期化とメインゴルーチンの実行が、よりGoネイティブなコードで制御されるようになったことを意味します。これにより、C言語で書かれた`runtime.main`がGoスタック上で実行されるという潜在的な問題が解消されます。

これらの技術的な変更は、Goランタイムのスタック管理をより厳密にし、CGOとの相互運用における潜在的な問題を動的に検出し、Goプログラムの安定性と安全性を大幅に向上させました。

## コアとなるコードの解説

このコミットのコアとなるコードの変更は、GoランタイムがC言語のコードがGoのゴルーチンスタック上で実行されることをどのように検出し、防止するかを示しています。

### 1. `G`構造体と`stackguard1`

`G`構造体はGoのゴルーチンを表す重要なデータ構造です。このコミットで追加された`stackguard1`フィールドは、C言語のコードがスタックチェックを行う際に参照する特別なスタックガード値です。

*   **通常のGoゴルーチン**: `runtime.malg`関数（新しいゴルーチンを割り当てる関数）内で、新しく作成されるゴルーチンの`g.stackguard1`は`~(uintptr)0`（すべてのビットが1）に設定されます。これは、Cコードがこのスタック上でスタックチェックを行うと、必ずスタック拡張が必要だと判断されるようにするためです。
*   **`g0`および`gsignal`スタック**: `runtime.proc.c`の`mcommoninit`や`runtime.allocm`関数内で、`g0`や`gsignal`スタックの`g.stackguard1`は、通常の`g.stackguard`と同じ値に設定されます。これは、これらの特殊なスタック上ではCコードの実行が許可されており、通常のスタック拡張ロジックが適用されるためです。

### 2. C言語プロローグのフックと`morestackc`

Goのリンカ（`liblink`）は、CGOを介してGoプログラムにリンクされるC言語の関数に対して、特別なプロローグコードを挿入します。このコミットでは、このプロローグが変更され、C関数がスタックチェックを行う際に`g.stackguard1`を参照するようになりました。

もしC関数が通常のGoゴルーチンスタック上で実行され、スタック拡張が必要だと判断された場合（`g.stackguard1`が`~0`であるため常にそうなる）、通常の`runtime.morestack`の代わりに`runtime.morestackc`が呼び出されます。

`runtime.morestackc`は、`runtime.onM`というメカニズム（現在のM（OSスレッド）上で指定された関数を実行する）を介して`badc`関数を呼び出します。

```go
// src/runtime/stack.c
static void badc(void);

#pragma textflag NOSPLIT
void
runtime·morestackc(void)
{
    void (*fn)(void);

    fn = badc;
    runtime·onM(&fn); // 現在のM上でbadcを実行
}

static void
badc(void)
{
    runtime·throw("attempt to execute C code on Go stack"); // エラーメッセージを出力してプログラムを終了
}
```

`badc`関数は、`runtime.throw`を呼び出して「attempt to execute C code on Go stack」というエラーメッセージと共にプログラムを異常終了させます。これにより、Goのスタック管理モデルに違反するCコードの実行が検出された際に、Goランタイムは安全に停止することができます。

### 3. Go言語へのコード移行

このコミットのもう一つの重要な側面は、Goランタイムの多くのC言語で書かれた部分がGo言語に移行されたことです。

*   **CGOコールバック**: `_cgo_allocate_internal`や`_cgo_panic_internal`といったCGOコールバック関数が、`src/runtime/cgo/callbacks.c`から`src/runtime/cgocallback.go`へ移動されました。これにより、CGOを介してGoからCへ、そしてCからGoへコールバックする際のスタック管理がよりGoランタイムの制御下に入ります。
*   **シグナルハンドラ**: 各OS固有の`runtime.sigpanic`の実装がC言語からGo言語へ移行され、`src/runtime/sigpanic_unix.go`などのGoファイルに統合されました。これは、シグナルハンドラのような低レベルの処理がGoスタック上で不適切にCコードを呼び出す問題を解決するためです。
*   **メインゴルーチン**: `runtime.main`関数が`src/runtime/proc.c`から`src/runtime/proc.go`へ移動されました。Goプログラムのエントリポイントとなるメインゴルーチンの初期化と実行がGo言語で記述されることで、Goランタイムの起動プロセス全体がよりGoネイティブなものとなり、C言語のコードがGoスタック上で実行されるリスクがさらに低減されます。

これらの変更は、Goランタイムのスタック管理をより厳密にし、CGOとの相互運用における潜在的な問題を動的に検出し、Goプログラムの安定性と安全性を大幅に向上させるための包括的なアプローチを示しています。

## 元コミット内容

このコミットは、Goのコンパイラ（`liblink`）とランタイム（`runtime`）にわたる広範な変更を含んでいます。主な目的は、Goの通常のゴルーチンスタック上でC言語のコードが実行されることを検出し、防止することです。

検出メカニズムは以下の通りです。
1.  **スタックガードワードの変更**: C言語の関数のプロローグ（関数が呼び出された直後に実行される初期設定コード）が、Goのプロローグとは異なる「スタックガードワード」を`G`（ゴルーチン）構造体内で使用するように変更されます。
2.  **特殊なスタックでの挙動**: `g0`スタック（ランタイム自身の処理に使用される特殊なスタック）や`gsignal`スタック（シグナルハンドラで使用される特殊なスタック）上では、スタックガードワードは通常のGoのスタックガード値に設定されます。これらのスタックはGoの通常のスタック管理の対象外であり、Cコードが実行されることが許容されるためです。
3.  **通常のGoスタックでの挙動**: しかし、通常のGoゴルーチンスタック上では、スタックガードワードは`^0`（ビット反転した0、つまりすべてのビットが1）に設定されます。この値は、いかなるスタック分割チェック（スタックの拡張が必要かどうかを判断するチェック）も必ず失敗させるように設計されています。
4.  **`morestackc`の呼び出し**: C言語のプロローグは、スタック分割チェックが失敗した場合に、通常の`morestack`（Goのスタック拡張関数）の代わりに`morestackc`を呼び出すように変更されます。
5.  **プログラムの中止**: `morestackc`は、「attempt to execute C code on Go stack」（Goスタック上でCコードを実行しようとしました）というメッセージを出力してプログラムを異常終了させます。

この動的なチェックは、`NOSPLIT`属性を持つCコード（スタック分割チェックを行わないようにコンパイラに指示されたコード）を除く、すべてのGoスタック上で実行されるCコードを捕捉します。`NOSPLIT`コードはGoスタック上での実行が許可されているため、このチェックは完全であると見なされます。

この動的なチェックの利点は、静的なチェック（例えば`cmd/ld`リンカで行われるチェック）では見逃される可能性のある、関数ポインタやその他の間接的な呼び出しを介したCコードの実行を検出できる点にあります。コミットメッセージでは、シグナルハンドラ内で`sigpanic`がGoスタックにプッシュされるケースを検出できたことが例として挙げられています。

このコミットは、Go Issue #8667を修正します。

## 変更の背景

Goランタイムは、効率的なメモリ管理と並行処理を実現するために、独自のスタック管理モデルを採用しています。Goのゴルーチンは、必要に応じてスタックを動的に拡張・縮小する「可変スタック」を使用します。このスタック管理は、Goのランタイムとガーベージコレクタが密接に連携して動作することを前提としています。

しかし、C言語で書かれたコード（特にCGOを介してGoから呼び出されるC関数や、Goランタイム内部でC言語で実装されている部分）が、Goの管理するゴルーチンスタック上で実行されると、問題が発生する可能性がありました。C言語のコードはGoのスタック管理の規約に従わないため、以下のような問題が引き起こされる恐れがありました。

1.  **スタックの破損**: CコードがGoスタックの境界を越えて書き込みを行ったり、GoランタイムがCコードのスタック利用を誤って解釈したりすることで、スタックが破損する可能性があります。
2.  **ガーベージコレクションの不正確さ**: Goのガーベージコレクタは、Goスタック上のポインタをスキャンして到達可能なオブジェクトを特定します。CコードがGoスタック上に不適切な方法でデータを配置したり、ポインタを保持したりすると、GCが誤動作し、本来回収されるべきメモリが回収されなかったり、逆にまだ使用中のメモリが回収されてしまったりする可能性があります。
3.  **セキュリティ上の脆弱性**: スタックの不適切な利用は、バッファオーバーフローなどのセキュリティ脆弱性につながる可能性があります。
4.  **デバッグの困難さ**: GoとCのスタックが混在することで、デバッグが非常に困難になることがあります。

このコミット以前にも、Goは静的なリンカレベルのチェックでCコードがGoスタック上で実行されることを防ごうとしていましたが、関数ポインタを介した間接的な呼び出しなど、すべてのケースを捕捉することはできませんでした。特に、シグナルハンドラのような低レベルの処理でCコードがGoスタックに侵入するケースは、Goランタイムの安定性に直接影響を与えるため、より堅牢な検出と防止メカニズムが必要とされていました。

このコミットは、このような問題を動的に検出し、プログラムを安全に終了させることで、Goランタイムの安定性と信頼性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とC言語の基本的な知識が必要です。

1.  **Goのゴルーチンとスタック**:
    *   **ゴルーチン (Goroutine)**: Goにおける軽量な実行単位です。OSのスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行できます。
    *   **可変スタック (Contiguous Stack)**: 各ゴルーチンは、最初は小さなスタック（数KB）で開始し、必要に応じて自動的にスタック領域を拡張します。スタックが不足しそうになると、Goランタイムはより大きな新しいスタックを割り当て、古いスタックの内容を新しいスタックにコピーし、スタックポインタを更新します。このプロセスを「スタック分割 (stack split)」と呼びます。
    *   **スタックガード (Stack Guard)**: スタックの拡張が必要かどうかを判断するために、Goランタイムはスタックの現在の境界を示す「スタックガード」と呼ばれる値を設定します。関数呼び出しのプロローグで、現在のスタックポインタがこのスタックガード値を超えていないかチェックします。超えている場合、スタック分割処理（`morestack`関数の呼び出し）が行われます。

2.  **`G`構造体**:
    *   Goランタイムは、各ゴルーチンの状態を`G`構造体で管理しています。この構造体には、スタックの開始アドレス、スタックの現在の境界（`stackguard0`）、そしてこのコミットで追加される`stackguard1`などの情報が含まれています。

3.  **`M`と`P`**:
    *   **`M` (Machine)**: OSのスレッドを表します。Goランタイムは、複数の`M`を管理し、その上でゴルーチンを実行します。
    *   **`P` (Processor)**: 論理プロセッサを表します。`P`は`M`とゴルーチンを仲介し、ゴルーチンが実行されるためのコンテキストを提供します。

4.  **`g0`スタックと`gsignal`スタック**:
    *   **`g0`スタック**: Goランタイムの内部処理（スケジューリング、ガーベージコレクションなど）を実行するための特別なスタックです。これはGoの通常のゴルーチンスタックとは異なり、固定サイズで、C言語のコードが実行されることが想定されています。
    *   **`gsignal`スタック**: シグナルハンドラが実行される際に使用される特別なスタックです。これも固定サイズで、C言語のコードが実行されることが想定されています。

5.  **CGO**:
    *   GoプログラムからC言語の関数を呼び出したり、C言語からGoの関数を呼び出したりするためのメカニズムです。CGOを介してGoとCが連携する際、スタックの管理は複雑になります。

6.  **関数プロローグ (Function Prologue)**:
    *   関数が呼び出された直後に実行されるアセンブリコードのシーケンスです。これには、スタックフレームのセットアップ、レジスタの保存、そしてGoの場合にはスタックガードチェックなどが含まれます。

7.  **`NOSPLIT`属性**:
    *   Goのコンパイラやリンカにおいて、特定の関数に付与される属性です。この属性が付与された関数は、スタック分割チェックを行いません。これは通常、非常に小さく、スタックをほとんど消費しない関数や、スタック分割処理自体が不可能な低レベルのランタイム関数に使用されます。

8.  **動的チェックと静的チェック**:
    *   **静的チェック**: コンパイル時やリンク時にコードを分析して問題を検出する方法です。例えば、リンカがCコードがGoスタック上で実行される可能性を検出する試みなど。
    *   **動的チェック**: プログラムの実行時に問題を検出する方法です。このコミットで導入されるスタックガードワードのチェックは動的チェックの一例です。動的チェックは、静的分析では捉えにくい間接的な呼び出しなどにも対応できます。

これらの概念を理解することで、このコミットがGoランタイムのスタック管理とCGOの相互作用において、いかに重要な改善をもたらしたかが明確になります。

## 技術的詳細

このコミットの技術的な核心は、Goのスタック管理モデルとC言語のスタック利用の間の不整合を動的に検出・防止するメカニズムにあります。

### 1. `G`構造体への`stackguard1`の追加

`src/runtime/runtime.h`の`G`構造体に`stackguard1`という新しいフィールドが追加されました。
```c
struct G
{
    // ...
    uintptr stackguard0;    // cannot move - also known to liblink, libmach, runtime/cgo
    uintptr stackbase;      // cannot move - also known to libmach, runtime/cgo
    Panic*  panic;          // cannot move - also known to liblink
    // stackguard1 is checked by C code; it is set to ~0 in ordinary (non-g0, non-gsignal) goroutines
    uintptr stackguard1;    // cannot move - also known to liblink
    // ...
};
```
この`stackguard1`は、C言語で書かれた関数がスタックチェックを行う際に参照する特別なスタックガード値として機能します。コメントにあるように、通常のゴルーチン（`g0`や`gsignal`ではない）では`~0`（すべてのビットが1）に設定されます。

### 2. C言語プロローグの変更 (`liblink/obj*.c`)

Goのリンカ（`liblink`）は、Goのソースコードから生成されるアセンブリコードだけでなく、CGOを介してGoプログラムにリンクされるC言語のコードのアセンブリも処理します。このコミットでは、`src/liblink/obj5.c` (ARM), `src/liblink/obj6.c` (x86), `src/liblink/obj8.c` (PowerPC) など、各アーキテクチャのコード生成部分が変更されました。

変更のポイントは、C言語で書かれた関数のプロローグにおいて、スタックチェックのロジックを修正することです。
*   `ctxt->cursym->cfunc`というフラグ（現在のシンボルがC関数であるかを示す）が導入され、C関数である場合に特別な処理を行います。
*   C関数では、スタックガード値として`g->stackguard1`（`3*ctxt->arch->ptrsize`のオフセットでアクセス）を使用するように変更されます。
*   スタックチェックが失敗した場合（つまり、スタックポインタが`g->stackguard1`を下回った場合）、通常の`runtime.morestack`の代わりに`runtime.morestackc`を呼び出すように変更されます。

これにより、通常のGoゴルーチンスタック上でC関数がスタック拡張を試みると、`g->stackguard1`が`~0`であるため、必ずチェックが失敗し、`runtime.morestackc`が呼び出されるようになります。

### 3. `runtime.morestackc`の導入 (`src/runtime/stack.c`)

`src/runtime/stack.c`に`runtime.morestackc`という新しい関数が追加されました。
```c
// src/runtime/stack.c
static void badc(void);

#pragma textflag NOSPLIT

### 4. `stackguard1`の初期化 (`src/runtime/proc.c`)

### 5. CGOコールバックとシグナルハンドラのGoへの移行

コミットメッセージで言及されているように、この変更は`sigpanic`がGoスタックにプッシュされる問題を検出しました。これに対応するため、`src/runtime/cgo/callbacks.c`にあった`_cgo_allocate_internal`や`_cgo_panic_internal`といったCGOコールバック関数が、`src/runtime/cgocallback.go`という新しいGoファイルに移行されました。同様に、各OS固有の`runtime.sigpanic`の実装（`src/runtime/os_darwin.c`など）が削除され、`src/runtime/sigpanic_unix.go`や`src/runtime/os_nacl.go`、`src/runtime/os_windows.go`といったGoファイルに統合されました。

これらの変更は、Goランタイムの重要な部分をC言語からGo言語へ移行させることで、Goのスタック管理モデルとの整合性を高め、CコードがGoスタック上で不適切に実行されるリスクを根本的に減らすことを目的としています。

### 6. `runtime.main`のGoへの移行

`src/runtime/proc.c`にあった`runtime.main`関数（Goプログラムのエントリポイントとなるメインゴルーチンの処理）が、`src/runtime/proc.go`に完全に移行されました。これは非常に大きな変更であり、Goランタイムの初期化とメインゴルーチンの実行が、よりGoネイティブなコードで制御されるようになったことを意味します。これにより、C言語で書かれた`runtime.main`がGoスタック上で実行されるという潜在的な問題が解消されます。

これらの技術的な変更は、Goランタイムのスタック管理をより厳密にし、CGOとの相互運用における潜在的な問題を動的に検出し、Goプログラムの安定性と安全性を大幅に向上させました。

## コアとなるコードの解説

このコミットのコアとなるコードの変更は、GoランタイムがC言語のコードがGoのゴルーチンスタック上で実行されることをどのように検出し、防止するかを示しています。

### 1. `G`構造体と`stackguard1`

`G`構造体はGoのゴルーチンを表す重要なデータ構造です。このコミットで追加された`stackguard1`フィールドは、C言語のコードがスタックチェックを行う際に参照する特別なスタックガード値です。

*   **通常のGoゴルーチン**: `runtime.malg`関数（新しいゴルーチンを割り当てる関数）内で、新しく作成されるゴルーチンの`g.stackguard1`は`~(uintptr)0`（すべてのビットが1）に設定されます。これは、Cコードがこのスタック上でスタックチェックを行うと、必ずスタック拡張が必要だと判断されるようにするためです。
*   **`g0`および`gsignal`スタック**: `runtime.proc.c`の`mcommoninit`や`runtime.allocm`関数内で、`g0`や`gsignal`スタックの`g.stackguard1`は、通常の`g.stackguard`と同じ値に設定されます。これは、これらの特殊なスタック上ではCコードの実行が許可されており、通常のスタック拡張ロジックが適用されるためです。

### 2. C言語プロローグのフックと`morestackc`

Goのリンカ（`liblink`）は、CGOを介してGoプログラムにリンクされるC言語の関数に対して、特別なプロローグコードを挿入します。このコミットでは、このプロローグが変更され、C関数がスタックチェックを行う際に`g.stackguard1`を参照するようになりました。

もしC関数が通常のGoゴルーチンスタック上で実行され、スタック拡張が必要だと判断された場合（`g.stackguard1`が`~0`であるため常にそうなる）、通常の`runtime.morestack`の代わりに`runtime.morestackc`が呼び出されます。

`runtime.morestackc`は、`runtime.onM`というメカニズム（現在のM（OSスレッド）上で指定された関数を実行する）を介して`badc`関数を呼び出します。

```go
// src/runtime/stack.c
static void badc(void);

#pragma textflag NOSPLIT
void
runtime·morestackc(void)
{
    void (*fn)(void);

    fn = badc;
    runtime·onM(&fn); // 現在のM上でbadcを実行
}

static void
badc(void)
{
    runtime·throw("attempt to execute C code on Go stack"); // エラーメッセージを出力してプログラムを終了
}
```

`badc`関数は、`runtime.throw`を呼び出して「attempt to execute C code on Go stack」というエラーメッセージと共にプログラムを異常終了させます。これにより、Goのスタック管理モデルに違反するCコードの実行が検出された際に、Goランタイムは安全に停止することができます。

### 3. Go言語へのコード移行

このコミットのもう一つの重要な側面は、Goランタイムの多くのC言語で書かれた部分がGo言語に移行されたことです。

*   **CGOコールバック**: `_cgo_allocate_internal`や`_cgo_panic_internal`といったCGOコールバック関数が、`src/runtime/cgo/callbacks.c`から`src/runtime/cgocallback.go`へ移動されました。これにより、CGOを介してGoからCへ、そしてCからGoへコールバックする際のスタック管理がよりGoランタイムの制御下に入ります。
*   **シグナルハンドラ**: 各OS固有の`runtime.sigpanic`の実装がC言語からGo言語へ移行され、`src/runtime/sigpanic_unix.go`などのGoファイルに統合されました。これは、シグナルハンドラのような低レベルの処理がGoスタック上で不適切にCコードを呼び出す問題を解決するためです。
*   **メインゴルーチン**: `runtime.main`関数が`src/runtime/proc.c`から`src/runtime/proc.go`へ移動されました。Goプログラムのエントリポイントとなるメインゴルーチンの初期化と実行がGo言語で記述されることで、Goランタイムの起動プロセス全体がよりGoネイティブなものとなり、C言語のコードがGoスタック上で実行されるリスクがさらに低減されます。

これらの変更は、Goランタイムのスタック管理をより厳密にし、CGOとの相互運用における潜在的な問題を動的に検出し、Goプログラムの安定性と安全性を大幅に向上させるための包括的なアプローチを示しています。

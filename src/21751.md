# [インデックス 21751] ファイルの概要

このコミットは、GoランタイムにおけるAMD64アーキテクチャでのBP（Base Pointer）レジスタの使用を排除することを目的としています。これにより、フレームポインタのアンワインド（スタックトレースの再構築）が改善され、特に`GOEXPERIMENT=framepointer`が有効な場合や、`perf`やVTuneのようなプロファイリングツールでのコールグラフの取得が容易になります。

change eliminates uses of BP in the runtime to address this problem.
We have spare registers everywhere this occurs, so there's no downside

## 変更の背景

このコミットの主な背景は、GoランタイムがAMD64アーキテクチャ上でBP（Base Pointer）レジスタを使用している箇所を排除することです。これは以下の2つの主要な問題に対処するためです。

1.  **フレームポインタアンワインドとの干渉**:
    *   `GOEXPERIMENT=framepointer`ビルドフラグが有効な場合、Goは関数呼び出し規約においてフレームポインタ（BPレジスタ）を維持するようにコンパイルされます。これにより、デバッガやプロファイラがコールスタックを正確に再構築（アンワインド）できるようになります。
    *   しかし、Goランタイム内のアセンブリコードがBPレジスタを一時的な目的で「破壊」（clobber）すると、このフレームポインタチェーンが壊れてしまい、スタックアンワインドが正しく行えなくなる可能性がありました。これは、特にデバッグやプロファイリングの際に問題となります。

2.  **プロファイリングツールの改善**:
    *   `perf`やVTuneのようなプロファイリングツールは、プログラムの実行中にコールスタックをサンプリングすることで、どの関数がCPU時間を消費しているかを特定し、コールグラフを生成します。
    *   Goランタイムの内部処理、特にガベージコレクタ（GC）が`systemstack`（Goの内部的なスタック切り替えメカニズム）を介して実行される際、BPレジスタの破壊が原因で、これらのツールがGCのコールスタックを正確に追跡できないことがありました。
    *   BPレジスタの使用を排除することで、`systemstack`を介した呼び出しであっても、プロファイリングツールがコールスタックをアンワインドできるようになり、ガベージコレクタの動作を含む、より詳細で正確なコールグラフを取得できるようになります。これは、ランタイムのパフォーマンス分析において非常に有用です。

コミットメッセージには、BPレジスタを排除しても「スペアなレジスタがどこにでもあるため、デメリットはない」と述べられており、また、NaCL（Native Client）による制約のためにBPを使用しない`amd64p32`ランタイムと同じ新しいレジスタを使用している点も言及されています。これは、レジスタ割り当ての一貫性を保ちつつ、問題を解決するための合理的なアプローチであることを示唆しています。

## 前提知識の解説

### 1. BP (Base Pointer) レジスタ

*   **役割**: x86およびx86-64アーキテクチャにおける汎用レジスタの一つで、通常はスタックフレームのベースアドレス（基点）を指すために使用されます。関数が呼び出されると、その関数のローカル変数や引数はスタック上に配置され、BPレジスタはこれらのデータにアクセスするための基準点として機能します。
*   **フレームポインタ**: BPレジスタがスタックフレームのベースアドレスとして使用される場合、それは「フレームポインタ」と呼ばれます。フレームポインタは、現在のスタックフレームから呼び出し元のスタックフレームへのリンクを提供し、これによりコールスタックを逆順に辿ることができます。
*   **BPの省略 (Frame Pointer Omission)**: 多くのコンパイラ（特に最適化を重視する場合）は、BPレジスタをフレームポインタとして使用せず、代わりに他のレジスタを汎用レジスタとして利用したり、スタックポインタ（SP）からのオフセットでローカル変数にアクセスしたりすることがあります。これは、レジスタの利用効率を高め、コードサイズを削減するためです。しかし、これによりデバッグやプロファイリングが困難になることがあります。

### 2. フレームポインタアンワインド (Frame Pointer Unwinding)

*   **目的**: 実行中のプログラムのコールスタック（関数呼び出しの履歴）を再構築するプロセスです。デバッガやプロファイラは、この情報を使用して、プログラムの現在の実行パスを理解したり、どの関数がどれだけの時間を消費しているかを分析したりします。
*   **仕組み**: フレームポインタが維持されている場合、各スタックフレームには、そのフレームのベースアドレスと、呼び出し元のスタックフレームのベースアドレス（前のBPの値）が保存されています。これにより、BPレジスタを辿っていくことで、関数呼び出しの連鎖を逆順に辿り、コールスタックを再構築できます。
*   **問題点**: BPレジスタが一時的な計算のために「破壊」される（clobberされる）と、このフレームポインタチェーンが途切れてしまい、それ以降のスタックフレームを正確にアンワインドできなくなります。

### 3. `GOEXPERIMENT=framepointer`

*   Goコンパイラには、実験的な機能や最適化を有効にするための`GOEXPERIMENT`環境変数があります。
*   `GOEXPERIMENT=framepointer`は、Goプログラムをコンパイルする際に、関数呼び出し規約においてフレームポインタ（BPレジスタ）を維持するように強制するフラグです。これにより、デバッガやプロファイラがより正確なスタックトレースを取得できるようになります。通常、Goはデフォルトではフレームポインタを維持しない最適化を行っています。

### 4. `systemstack`

*   Goランタイムの内部関数で、現在のゴルーチン（Goの軽量スレッド）のスタックから、より小さな固定サイズの「システムスタック」に切り替えるために使用されます。
*   これは、ガベージコレクタのマークフェーズや、シグナルハンドラなど、特定のランタイム内部処理で、スタックオーバーフローのリスクを避けたり、スタックの切り替えを効率的に行ったりするために利用されます。
*   `systemstack`への切り替えは、通常のGo関数の呼び出しとは異なるアセンブリレベルの操作を伴うため、プロファイリングツールがその間のコールスタックを追跡するのが難しい場合があります。

### 5. `perf`とVTune

*   **`perf`**: Linuxカーネルに組み込まれた強力なパフォーマンス分析ツールです。CPU使用率、キャッシュミス、システムコールなど、様々なパフォーマンスイベントをプロファイルし、コールグラフを生成できます。
*   **VTune Amplifier**: Intelが提供するプロファイリングツールで、CPUパフォーマンス、スレッド並列性、メモリ使用量などを詳細に分析できます。
*   これらのツールは、プログラムのパフォーマンスボトルネックを特定するために、正確なコールスタック情報に大きく依存しています。

### 6. NaCL (Native Client) と `amd64p32`

*   **NaCL**: Googleが開発した、ウェブブラウザ内でネイティブコードを安全に実行するためのサンドボックス技術です。
*   **`amd64p32`**: NaCL環境で実行される32ビットポインタを持つAMD64アーキテクチャのGoランタイムです。NaCLのセキュリティモデルは、特定のレジスタの使用方法に制約を課すことがあり、これがBPレジスタの使用を制限する理由の一つとなります。このコミットは、`amd64p32`ランタイムがBPを使用しないという既存の慣行と整合性を持たせる形で、他のレジスタへの移行を行っています。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのアセンブリコードにおいて、BP（Base Pointer）レジスタへの参照を他の汎用レジスタに置き換えることです。これにより、BPレジスタがフレームポインタとして使用されている場合に、ランタイムの内部処理がその値を破壊するのを防ぎます。

具体的には、以下のレジスタがBPの代替として使用されています。

*   **AX (Accumulator Register)**: 汎用レジスタで、通常は算術演算の結果を保持したり、関数の戻り値を保持したりします。
*   **R8 (General Purpose Register 8)**: AMD64アーキテクチャで追加された汎用レジスタの一つです。
*   **SI (Source Index Register)**: 汎用レジスタで、通常はデータ転送操作のソースインデックスとして使用されます。
*   **BX (Base Register)**: 汎用レジスタで、通常はメモリ操作のベースアドレスとして使用されます。

変更は主に`src/runtime/asm_amd64.s`ファイルで行われており、Goランタイムの低レベルなアセンブリルーチンに影響を与えます。これには、ゴルーチンのスケジューリング、スタック切り替え（`systemstack`）、Cgoコールバック、および一部の最適化されたデータ操作ルーチンが含まれます。

変更のパターンは以下の通りです。

1.  **BPレジスタへの値のロード**: `MOVQ $value, BP` のような命令は、`MOVQ $value, AX` や `MOVQ $value, SI` のように変更されます。
2.  **BPレジスタからの値の読み出し**: `MOVQ (BP), target_reg` のような命令は、`MOVQ (AX), target_reg` や `MOVQ (R8), target_reg` のように変更されます。
3.  **BPレジスタを使用した比較**: `CMPQ AX, BP` のような命令は、`CMPQ AX, R8` のように変更されます。
4.  **BPレジスタをインデックスとして使用**: `(BP)(CX*8)` のようなメモリ参照は、`(AX)(CX*8)` や `(R8*1)` のように変更されます。

これらの変更は、BPレジスタがフレームポインタとして機能している場合に、その値を上書きしないようにすることで、スタックアンワインドの正確性を保証します。Goランタイムは、これらのレジスタを一時的な作業用として利用できるため、BPの代わりにこれらのレジスタを使用しても機能的な問題は発生しません。

また、この変更は、`amd64p32`ランタイムがNaCLの制約によりBPを使用しないという既存の慣行に合わせることで、コードベースの一貫性を高める効果もあります。

## コアとなるコードの解説

上記の変更箇所は、Goランタイムの様々な低レベルな処理において、BPレジスタが一時的なデータ保持やアドレス計算に使用されていた部分を、他の汎用レジスタに置き換えるものです。

1.  **`runtime·main·f` のエントリポイント設定**:
    *   変更前: `MOVQ $runtime·main·f(SB), BP` と `PUSHQ BP` は、`runtime·main·f` のアドレスをBPレジスタにロードし、それをスタックにプッシュしていました。これは新しいゴルーチンを開始するためのエントリポイントを設定する操作です。
    *   変更後: `MOVQ $runtime·main·f(SB), AX` と `PUSHQ AX` に変更されました。これにより、BPレジスタを触ることなく、同じ目的を達成しています。AXレジスタは汎用性が高く、このような一時的な値の保持に適しています。

2.  **`runtime·systemstack` 内での `g` の比較**:
    *   `runtime·systemstack` は、現在のゴルーチン（`m_curg(BX)`）がシステムスタックに切り替えるべきかどうかを判断する際に、BPレジスタを使用して比較を行っていました。
    *   変更後: `MOVQ m_curg(BX), R8` と `CMPQ AX, R8` に変更されました。BPの代わりにR8レジスタを使用することで、フレームポインタの破壊を防ぎつつ、ゴルーチンポインタの比較を継続しています。

3.  **`runtime·systemstack_switch` のPC設定**:
    *   `systemstack`がスタックを切り替える際に、元のゴルーチンの実行コンテキスト（プログラムカウンタ `gobuf_pc`）を保存する部分です。
    *   変更前: `MOVQ $runtime·systemstack_switch(SB), BP` と `MOVQ BP, (g_sched+gobuf_pc)(AX)` は、`systemstack_switch`のアドレスをBPにロードし、それをゴルーチンのスケジューラ情報に保存していました。
    *   変更後: `MOVQ $runtime·systemstack_switch(SB), SI` と `MOVQ SI, (g_sched+gobuf_pc)(AX)` に変更されました。SIレジスタを使用することで、BPレジスタの破壊を回避しています。

4.  **`runtime·morestack` 内での `m->g0` の処理**:
    *   `morestack`は、スタックの拡張が必要な場合に呼び出される関数です。ここでは、現在のM（OSスレッド）の`g0`（システムゴルーチン）のスタックに切り替える処理が含まれます。
    *   変更前: `MOVQ m_g0(BX), BP`、`MOVQ BP, g(CX)`、`MOVQ (g_sched+gobuf_sp)(BP), SP` は、`m->g0`のアドレスをBPにロードし、それを使って`g0`のスタックポインタを取得していました。
    *   変更後: `MOVQ m_g0(BX), BX`、`MOVQ BX, g(CX)`、`MOVQ (g_sched+gobuf_sp)(BX), SP` に変更されました。ここでは、BPの代わりにBXレジスタが使用されています。BXはベースレジスタとしてメモリ参照によく使われるため、この文脈での使用は自然です。

5.  **`asmcgocall` および `cgocallback_gofunc` 内での `g` と `m` の処理**:
    *   これらの関数はCgo（GoとCの相互運用）に関連するもので、GoとCのスタック切り替えやゴルーチン/Mの状態管理を行います。
    *   これらのルーチンでは、現在のゴルーチンやM（OSスレッド）の情報を取得し、それらを一時的にBPレジスタに保持していましたが、これらがR8やBXレジスタに置き換えられました。これにより、Cgoの呼び出しパスにおいてもフレームポインタの整合性が保たれます。

6.  **AES関連ルーチン (`aes0to15`, `endofpage`)**:
    *   これらのルーチンは、AES暗号化の最適化されたアセンブリ実装の一部です。ここでは、BPレジスタがマスクやシフト値へのポインタとして使用されていました。
    *   変更後: `MOVQ $masks<>(SB), AX` や `MOVQ $shifts<>(SB), AX` のように、BPの代わりにAXレジスタが使用されています。これにより、BPレジスタがデータ処理ルーチンで一時的に使用されることによる干渉も排除されます。

7.  **`runtime·cmpbody` (バイト列比較ルーチン)**:
    *   このルーチンは、バイト列の比較を行う際に、比較するバイト数（`min(alen, blen)`）をBPレジスタに保持していました。
    *   変更後: `MOVQ DX, R8` と `CMOVQLT BX, R8` のように、BPの代わりにR8レジスタが使用されています。ループカウンタやインデックスとしてBPを使用していた箇所もR8に置き換えられています。これにより、汎用的なデータ操作ルーチンにおいてもBPの破壊がなくなります。

全体として、このコミットは、Goランタイムの低レベルなアセンブリコードにおけるBPレジスタの利用を体系的に排除し、他の利用可能な汎用レジスタに置き換えることで、`GOEXPERIMENT=framepointer`使用時のスタックアンワインドの信頼性を向上させ、`perf`やVTuneのようなプロファイリングツールによるより正確なコールグラフの生成を可能にしています。これは、Goプログラムのデバッグとパフォーマンス分析の能力を向上させる重要な変更です。

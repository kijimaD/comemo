## 変更の背景

このコミットは、Go 1.4で導入された`crypto/tls`パッケージの新機能である「サーバー証明書のプログラムによる選択（programmatic selection of server certificates）」について、公式ドキュメントである`doc/go1.4.txt`にその存在を明記するために行われました。

以前のGoの`crypto/tls`パッケージでは、TLSサーバーは通常、設定時に単一の証明書をロードするか、複数の証明書を事前に設定し、SNI（Server Name Indication）に基づいて選択する機能を持っていました。しかし、より高度なシナリオ、例えば、クライアントの接続情報に基づいて動的に証明書を選択したり、大量の仮想ホストを効率的に管理したりする場合には、より柔軟な証明書選択メカニズムが必要とされていました。

このニーズに応えるため、Go 1.4では`tls.Config`構造体に`GetCertificate`というコールバック関数が追加されました。この機能により、TLSハンドシェイク中にサーバーがクライアントから受け取った情報（SNIなど）に基づいて、動的に適切なサーバー証明書を選択して提示することが可能になりました。

この重要な新機能がGo 1.4のリリースノートに適切に記載されるよう、このコミットが作成されました。これにより、開発者はこの新しい強力な機能の存在を認識し、その恩恵を受けることができるようになります。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上で安全な通信を行うための暗号化プロトコルです。ウェブサイトのHTTPS接続などで広く利用されており、クライアントとサーバー間の通信を盗聴、改ざん、なりすましから保護します。TLSハンドシェイクと呼ばれる初期の通信フェーズで、クライアントとサーバーは互いの身元を確認し、暗号化のための鍵を交換します。

### サーバー証明書

サーバー証明書は、TLS通信においてサーバーの身元を証明するためのデジタル証明書です。通常、認証局（CA）によって発行され、サーバーの公開鍵、ドメイン名、有効期限などの情報が含まれています。クライアントは、サーバー証明書を検証することで、接続しているサーバーが正当なものであることを確認します。

### SNI (Server Name Indication)

SNIは、TLSプロトコルの拡張機能の一つです。これにより、クライアントはTLSハンドシェイクの初期段階で、接続したいホスト名（ドメイン名）をサーバーに伝えることができます。SNIが導入される前は、一つのIPアドレスで複数のウェブサイトをホストする場合、それぞれのウェブサイトに異なる証明書を設定することが困難でした。SNIの登場により、一つのIPアドレス上で複数のHTTPSサイトを運用し、クライアントが要求したホスト名に応じて適切な証明書を提示することが可能になりました。

### プログラムによる証明書選択 (Programmatic Certificate Selection)

これは、サーバーがTLSハンドシェイク中に、クライアントから提供された情報（SNI、クライアント証明書、接続元IPアドレスなど）に基づいて、提示するサーバー証明書を動的に選択する機能です。従来の静的な証明書設定とは異なり、より柔軟で高度な証明書管理が可能になります。例えば、数千もの仮想ホストを持つCDN（Content Delivery Network）や、ユーザーごとに異なる証明書を生成・管理するサービスなどで非常に有用です。

## 技術的詳細

このコミットが言及している`crypto/tls`パッケージの「サーバー証明書のプログラムによる選択」機能は、`tls.Config`構造体に追加された`GetCertificate`フィールドによって実現されます。

`tls.Config`は、TLS接続の挙動を制御するための設定を保持する構造体です。この構造体には、サーバー証明書をロードするための`Certificates`フィールドが元々存在しますが、これは静的に証明書を設定するものです。

Go 1.4で追加された`GetCertificate`フィールドは、以下の型の関数ポインタです。

```go
type Config struct {
    // ...
    GetCertificate func(*ClientHelloInfo) (*Certificate, error)
    // ...
}
```

この`GetCertificate`コールバック関数は、TLSハンドシェイク中にクライアントから`ClientHello`メッセージを受信した際に呼び出されます。関数には`*ClientHelloInfo`型の引数が渡されます。

### `ClientHelloInfo`構造体

`ClientHelloInfo`構造体は、クライアントの`ClientHello`メッセージから抽出された情報を含んでいます。この情報には、証明書選択の判断材料となる重要なデータが含まれます。

*   **`ServerName`**: クライアントがSNI拡張で指定したホスト名。これは、仮想ホスト環境で適切な証明書を選択する際に最も一般的に使用される情報です。
*   **`CipherSuites`**: クライアントがサポートする暗号スイートのリスト。
*   **`SupportedVersions`**: クライアントがサポートするTLSバージョンのリスト。
*   **`Conn`**: 基となる`net.Conn`インターフェース。これにより、接続元のIPアドレスなど、より低レベルな接続情報にアクセスできます。

### `GetCertificate`の動作

1.  クライアントがTLSハンドシェイクを開始し、`ClientHello`メッセージをサーバーに送信します。
2.  サーバーは`ClientHello`メッセージを受信し、`tls.Config`に`GetCertificate`コールバックが設定されている場合、この関数を呼び出します。
3.  `GetCertificate`関数内で、開発者は`ClientHelloInfo`の情報を参照し、どの証明書をクライアントに提示すべきかを決定するロジックを実装します。
    *   例えば、`info.ServerName`が`example.com`であれば`example.com`用の証明書を、`anotherexample.org`であれば`anotherexample.org`用の証明書をロードして返します。
    *   証明書は、ファイルシステムから読み込んだり、データベースから取得したり、あるいは動的に生成したりすることも可能です。
4.  関数は、選択された`*tls.Certificate`と`nil`エラーを返します。適切な証明書が見つからない場合や、何らかのエラーが発生した場合は、`nil`とエラーを返します。
5.  `GetCertificate`が成功裏に証明書を返すと、サーバーはその証明書を使用してTLSハンドシェイクを続行します。エラーが返された場合、ハンドシェイクは失敗します。

### 利点

*   **仮想ホスティングの効率化**: 単一のTLSサーバーで多数のドメインを効率的にホストできます。すべての証明書を起動時にロードする必要がなく、メモリ使用量を削減できます。
*   **動的な証明書管理**: 証明書をオンデマンドでロードできるため、証明書の更新や追加が容易になります。
*   **高度な選択ロジック**: クライアントのIPアドレス、特定のクライアントプロパティ、外部の証明書管理システム（例: Let's Encryptの`autocert`パッケージ）との統合など、より複雑な証明書選択ロジックを実装できます。

この機能は、特に大規模なサービスや、証明書を頻繁に管理する必要がある環境において、TLSサーバーの柔軟性とスケーラビリティを大幅に向上させます。

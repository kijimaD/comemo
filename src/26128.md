# [インデックス 26128] ファイルの概要

このコミットは、Go言語のコマンドラインツール `go get` において、HTTPS経由で404エラーが返された際に、`meta` タグのパース処理が失敗するバグを修正するものです。具体的には、HTTPレスポンスボディが時期尚早に閉じられてしまうことで発生する「http: read on closed response body」エラーに対処しています。

    cmd/go: fix processing of HTTPS 404 without -insecure

    The change here is to move the closeBody call into the if block.
    The logging adjustments are just arranging to tell the truth:
    in particular if we're not in insecure mode and we get a non-200
    error then we do not actually ignore the response
    (except as caused by closing the body incorrectly).

    As the comment below the change indicates, it is intentional that
    we process non-200 pages. The code does process them, because
    the if err != nil || status != 200 block does not return.
    But that block does close the body, which depending on timing
    can apparently poison the later read from the body.

    See #13037's initial report:

            $ go get -v bosun.org/cmd/bosun/cache
            Fetching https://bosun.org/cmd/bosun/cache?go-get=1
            ignoring https fetch with status code 404
            Parsing meta tags from https://bosun.org/cmd/bosun/cache?go-get=1 (status code 404)
            import "bosun.org/cmd/bosun/cache": parsing bosun.org/cmd/bosun/cache: http: read on closed response body
            package bosun.org/cmd/bosun/cache: unrecognized import path "bosun.org/cmd/bosun/cache"

    The log print about ignoring the https fetch is not strictly true,
    since the next thing that happened was parsing the body of that fetch.
    But the read on the closed response body failed during parsing.

    Moving the closeBody to happen only when we're about to discard the
    result and start over (that is, only in -insecure mode) fixes the parse.

    At least it should fix the parse. I can't seem to break the parse anymore,
    because of #13648 (close not barring future reads anymore),
    but this way is clearly better than the old way. If nothing else the old code
    closed the body twice when err != nil and -insecure was not given.

    Fixes #13037.

## 変更の背景

この変更は、Goのパッケージ管理ツール `go get` が、HTTPS経由でアクセスした際にHTTPステータスコード404 (Not Found) を受け取った場合に、予期せぬエラーで処理が中断される問題（Issue 13037）を解決するために導入されました。

`go get` は、指定されたインポートパスに対応するGoパッケージをダウンロードする際に、まずそのパスに対応するURLにアクセスします。この際、HTMLドキュメント内に埋め込まれた `go-import` メタタグを解析して、実際のソースコードリポジトリの場所を特定します。

問題は、HTTPSリクエストに対してサーバーが404を返した場合に発生しました。`go get` は、たとえ404であっても、そのレスポンスボディに `go-import` メタタグが含まれている可能性を考慮して、ボディの内容を読み取ろうとします。しかし、元のコードでは、HTTPステータスコードが200以外の場合、またはエラーが発生した場合に、レスポンスボディを閉じる `closeBody` 関数が呼び出されていました。この `closeBody` の呼び出しが時期尚早であったため、その後のメタタグ解析のためにレスポンスボディを読み取ろうとした際に、「http: read on closed response body」というエラーが発生し、`go get` の処理が失敗していました。

この挙動は、特に `bosun.org/cmd/bosun/cache` のような特定のパッケージで顕著に現れ、ユーザーは `go get` が正常に機能しないという問題に直面していました。

## 前提知識の解説

### `go get` コマンド
`go get` は、Go言語のワークスペースに外部パッケージをダウンロードし、インストールするためのコマンドです。指定されたインポートパスに基づいて、対応するリポジトリからソースコードを取得します。

### `go-import` メタタグ
`go get` が外部パッケージを解決する際に重要な役割を果たすのが `go-import` メタタグです。これはHTMLドキュメントの `<head>` セクションに記述され、Goパッケージのインポートパスと、そのパッケージのソースコードがホストされているバージョン管理システム（Git, Mercurialなど）のリポジトリURLを関連付けます。`go get` はこのメタタグを解析して、実際にどのリポジトリからコードをクローンすべきかを判断します。

例:
```html
<meta name="go-import" content="example.com/repo git https://github.com/example/repo">
```

### HTTPステータスコード404 (Not Found)
HTTPステータスコード404は、クライアントが要求したリソースがサーバー上で見つからなかったことを示します。通常、これはエラー状況ですが、`go get` の文脈では、ルートパスが見つからなくても、そのパスに対応するHTMLページ内に `go-import` メタタグが含まれている可能性があるため、レスポンスボディを解析する必要があります。

### `http.Response` とレスポンスボディの扱い
Goの `net/http` パッケージでは、HTTPレスポンスは `http.Response` 構造体で表されます。この構造体には、レスポンスボディを表す `Body` フィールドが含まれており、これは `io.ReadCloser` インターフェースを実装しています。`io.ReadCloser` は、データを読み取るための `Read` メソッドと、リソースを解放するための `Close` メソッドを持ちます。HTTPレスポンスボディは通常、ストリームとして扱われるため、読み取りが完了したら必ず `Close` する必要があります。これを怠ると、リソースリークや接続の再利用の問題が発生する可能性があります。

### `-insecure` モード
`go get` コマンドには `-insecure` フラグがあります。これは、HTTPS接続が失敗した場合にHTTP接続へのフォールバックを許可するものです。セキュリティ上の理由から、通常は推奨されません。このコミットの文脈では、`-insecure` モードでない場合でも、HTTPS 404のレスポンスボディを正しく処理する必要がありました。

### `http: read on closed response body` エラー
このエラーは、既に閉じられた `io.ReadCloser` インターフェース（この場合はHTTPレスポンスボディ）に対して `Read` 操作を行おうとした場合に発生します。これは、リソース管理の誤り、特に `Close` の呼び出しが早すぎた場合に起こりやすい問題です。

## 技術的詳細

このコミットの核心的な問題は、`src/cmd/go/http.go` 内の `httpsOrHTTP` 関数における `closeBody` の呼び出しタイミングにありました。

元のコードでは、HTTPSリクエストがエラーを返した (`err != nil`) か、またはステータスコードが200以外 (`res.StatusCode != 200`) であった場合に、無条件に `closeBody(res)` が呼び出されていました。

`go get` の設計思想として、たとえHTTPステータスコードが404であっても、そのレスポンスボディに `go-import` メタタグが含まれている可能性があるため、ボディの内容を解析しようとします。しかし、上記の条件で `closeBody` が呼び出されると、レスポンスボディが閉じられてしまい、その後のメタタグ解析のための読み取り操作が「http: read on closed response body」エラーで失敗していました。

コミットメッセージにあるように、この問題はタイミングに依存しており、`closeBody` がボディの後の読み取りを「毒する」可能性がありました。特に、`err != nil` かつ `-insecure` モードでない場合、古いコードではボディが二重に閉じられる可能性もありました。

この修正は、`closeBody` の呼び出しを、結果を破棄して最初からやり直す場合（つまり、`-insecure` モードでHTTPへのフォールバックを試みる場合）にのみ行うように変更することで、この問題を解決しています。これにより、HTTPSで非200ステータスコードが返された場合でも、レスポンスボディが閉じられることなく、メタタグの解析が正常に行われるようになります。

また、ロギングの調整も行われ、`buildV` (verboseモード) で非200エラーを受け取った際に、レスポンスを「無視している」というログメッセージが、実際にはボディを解析しようとしているという事実に合致するように修正されました。

コミットメッセージで言及されている `#13648` は、「close not barring future reads anymore」という変更に関連しており、これは `net/http` パッケージにおけるレスポンスボディの `Close` メソッドの挙動に関するものです。この変更により、`Close` が呼び出された後でも、特定の条件下でボディからの読み取りがブロックされなくなる可能性があります。このコミットの作者は、この変更のおかげで以前のようにパースを壊すことができなくなったと述べていますが、それでも現在の修正がより良いアプローチであると強調しています。これは、`closeBody` の呼び出しタイミングが根本的な問題であり、`#13648` はその影響を軽減する可能性があったとしても、正しいリソース管理を行うべきであるという考えに基づいています。

## コアとなるコードの解説

### `src/cmd/go/http.go` の変更点

`httpsOrHTTP` 関数は、指定されたインポートパスに対してHTTPSまたはHTTPでリソースをフェッチする役割を担っています。

元のコードでは、以下の条件ブロックがありました。

```go
	if err != nil || res.StatusCode != 200 {
		if buildV {
			if err != nil {
				log.Printf("https fetch failed.")
			} else {
				log.Printf("ignoring https fetch with status code %d", res.StatusCode)
			}
		}
		closeBody(res) // ここでボディが閉じられていた
		if security == insecure {
			urlStr, res, err = fetch("http")
		}
	}
```

この `closeBody(res)` の呼び出しが問題でした。`go get` は、`res.StatusCode` が200以外であっても、レスポンスボディから `go-import` メタタグを解析しようとします。しかし、この行でボディが閉じられてしまうと、その後の読み取り操作が失敗していました。

修正後のコードは以下のようになります。

```go
	if err != nil || res.StatusCode != 200 {
		if buildV && err != nil { // ロギングの調整
			log.Printf("https fetch failed: %v", err)
		}
		// closeBody(res) はここから移動された

		if security == insecure { // -insecure モードの場合のみ
			if buildV && res.StatusCode != 200 { // ロギングの調整
				log.Printf("https fetch: status %s", res.Status)
			}
			closeBody(res) // -insecure モードでHTTPにフォールバックする直前にのみボディを閉じる
			urlStr, res, err = fetch("http")
		}
	}
```

主な変更点は以下の通りです。

1.  **`closeBody(res)` の移動**: 以前は `if err != nil || res.StatusCode != 200` ブロックに入ると無条件に `closeBody(res)` が呼び出されていましたが、これが `if security == insecure` ブロックの内部に移動されました。これにより、`go get` がHTTPSで非200ステータスコードを受け取った場合でも、`security == insecure` でない限り、レスポンスボディは閉じられず、メタタグの解析のために読み取り可能になります。`security == insecure` の場合は、HTTPSのレスポンスを破棄してHTTPにフォールバックするため、ボディを閉じても問題ありません。
2.  **ロギングの調整**: `buildV` (verboseモード) でのログ出力がより正確になりました。
    *   エラーが発生した場合 (`err != nil`) は、「https fetch failed: %v」という具体的なエラーメッセージが出力されます。
    *   `-insecure` モードで、かつステータスコードが200以外の場合 (`res.StatusCode != 200`) にHTTPにフォールバックする直前に、「https fetch: status %s」というログが出力され、実際のステータスコードが示されます。これにより、以前の「ignoring https fetch with status code 404」という、実際には無視していないのに無視していると誤解を招くログが修正されました。

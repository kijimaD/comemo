# [インデックス 22120] ファイルの概要

このコミットは、Go言語の`syscall`パッケージにおける`Pipe`および`Pipe2`システムコールの実装を、特定のオペレーティングシステム（GOOS）ごとに分割する変更です。これにより、各プラットフォームの特性に合わせたシステムコール利用が可能になり、特に`arm64`アーキテクチャへの対応を容易にすることを目的としています。

具体的には、`src/syscall/syscall_linux.go`から汎用的な`Pipe`と`Pipe2`の実装が削除され、`src/syscall/syscall_linux_386.go`、`src/syscall/syscall_linux_amd64.go`、`src/syscall/syscall_linux_arm.go`、`src/syscall/syscall_linux_ppc64x.go`といった各アーキテクチャ固有のファイルに移動・調整されています。また、`zsyscall_linux_*.go`ファイル群でも、`pipe`および`pipe2`のシステムコールラッパーの定義が移動されています。

## 変更の背景

この変更の主な背景は、Go言語の`arm64`アーキテクチャへの移植（ポート）の準備です。Goの`syscall`パッケージは、オペレーティングシステムのシステムコールをGoプログラムから呼び出すためのインターフェースを提供します。システムコールはOSやアーキテクチャによってその挙動や利用可能性が異なるため、特定のプラットフォームに合わせた実装が必要となる場合があります。

`pipe(2)`と`pipe2(2)`は、プロセス間通信（IPC）のためのパイプを作成するシステムコールです。`pipe2(2)`は`pipe(2)`の拡張版であり、パイプのファイルディスクリプタにフラグ（例: `O_CLOEXEC`、`O_NONBLOCK`）を設定する機能を提供します。これにより、パイプ作成と同時にフラグを設定できるため、競合状態を避けるなどの利点があります。しかし、`pipe2(2)`は比較的新しいシステムコールであり、古いLinuxカーネル（特に2.6.23より前のバージョン）ではサポートされていません。

`arm64`のような新しいアーキテクチャへの対応を進めるにあたり、各プラットフォームがサポートするシステムコールのバージョンを適切に扱う必要がありました。特に、`arm64`では`pipe2(2)`が利用可能である一方で、既存の`amd64`や`386`アーキテクチャでは、古いカーネルとの互換性を保つために`pipe(2)`を維持する必要がありました。

このコミットは、これらの違いを吸収し、各GOOS（Go Operating System）の特性に合わせて`Pipe`および`Pipe2`の実装を分離することで、コードベースの保守性を高め、将来的なプラットフォームサポートを容易にすることを目的としています。

## 前提知識の解説

### 1. システムコール (System Call)

システムコールは、ユーザー空間で動作するプログラムが、カーネル空間で提供されるOSのサービス（ファイルI/O、プロセス管理、メモリ管理など）を利用するためのインターフェースです。Go言語の`syscall`パッケージは、これらのシステムコールをGoプログラムから直接呼び出すための機能を提供します。

### 2. `pipe(2)` と `pipe2(2)` システムコール

*   **`pipe(2)`**:
    *   UNIX系OSで利用されるシステムコールで、無名のパイプ（unnamed pipe）を作成します。
    *   パイプは、一方の端に書き込まれたデータがもう一方の端から読み出される、単方向のデータストリームです。
    *   通常、`pipe(2)`は2つのファイルディスクリプタ（読み込み用と書き込み用）を返します。
    *   プロセス間通信（IPC）の基本的なメカニズムとして広く利用されます。

*   **`pipe2(2)`**:
    *   Linuxカーネル2.6.27以降で導入された`pipe(2)`の拡張版です。
    *   `pipe(2)`と同様にパイプを作成しますが、追加の`flags`引数を受け取ります。
    *   この`flags`引数を使用することで、パイプのファイルディスクリプタに`O_CLOEXEC`（`exec`時にクローズする）や`O_NONBLOCK`（非ブロックI/O）などの属性を原子的に設定できます。
    *   `pipe(2)`でこれらのフラグを設定する場合、パイプ作成後に`fcntl(2)`システムコールを別途呼び出す必要がありますが、この間に競合状態が発生する可能性があります。`pipe2(2)`はこれを防ぎます。

### 3. GOOS (Go Operating System) と GOARCH (Go Architecture)

Go言語のビルドシステムでは、`GOOS`と`GOARCH`という環境変数を使用して、ターゲットとなるオペレーティングシステムとアーキテクチャを指定します。

*   **`GOOS`**: ビルド対象のOS（例: `linux`, `windows`, `darwin` (macOS)）。
*   **`GOARCH`**: ビルド対象のCPUアーキテクチャ（例: `amd64`, `386`, `arm`, `arm64`, `ppc64`）。

Goの標準ライブラリ、特に`syscall`パッケージのようなOSに依存する部分は、これらの変数に基づいて異なる実装ファイルを選択的にコンパイルします。例えば、`syscall_linux.go`はLinux全般に適用されるコードを含み、`syscall_linux_amd64.go`はLinux上のAMD64アーキテクチャに特化したコードを含みます。

### 4. `mksyscall.pl`

`mksyscall.pl`は、Goのソースコードツリー内にあるPerlスクリプトです。これは、Goの`syscall`パッケージで使用されるシステムコールラッパーのGoコードを自動生成するために使用されます。Goのソースファイル内に特定のコメント（例: `//sysnb`や`//sys`）でマークされた関数定義を解析し、対応する低レベルのシステムコール呼び出しを行うGoコードを生成します。

コミットメッセージにある「`mksycall.pl` does not sort symbols before generating the output file」という記述は、このスクリプトがシステムコールのシンボルを特定の順序で処理しないため、関連するコードがソースファイル内で移動すると、生成されるファイルの差分（diff）が大きくなることを示しています。これは機能的な問題ではなく、単にdiffが見づらくなるという話です。

## 技術的詳細

このコミットの核心は、`Pipe`および`Pipe2`システムコールのGoラッパーの実装を、汎用的な`syscall_linux.go`から、より具体的なGOOS/GOARCH固有のファイルに移動することです。これにより、各プラットフォームのカーネルが提供する`pipe(2)`と`pipe2(2)`のサポート状況に応じて、最適な実装を選択できるようになります。

具体的な変更点は以下の通りです。

1.  **`syscall_linux.go`からの削除**:
    *   これまでLinux全般の`Pipe`と`Pipe2`の実装が含まれていた`src/syscall/syscall_linux.go`から、これらの関数が完全に削除されました。

2.  **GOOS/GOARCH固有ファイルへの移動と調整**:
    *   **`syscall_linux_386.go` および `syscall_linux_amd64.go`**:
        *   これらのファイルには、`Pipe`と`Pipe2`の両方のGoラッパーが追加されました。
        *   これらのアーキテクチャでは、古いLinuxカーネルとの互換性を考慮し、`Pipe`関数は引き続き`pipe(2)`システムコールを呼び出すように実装されています。`Pipe2`は`pipe2(2)`を呼び出します。
        *   これは、コミットメッセージにある「For platforms where pipe2(2) is not supported in the minimum 2.6.23 kernel, amd64 and 386, we retain pipe(2)」という方針に基づいています。
    *   **`syscall_linux_arm.go` および `syscall_linux_ppc64x.go` (ppc64, ppc64le)**:
        *   これらのファイルにも`Pipe`と`Pipe2`のGoラッパーが追加されました。
        *   これらのアーキテクチャでは、`pipe2(2)`が利用可能であることを前提とし、`Pipe`関数も内部的に`pipe2(2)`システムコールを呼び出すように変更されています（`flags`引数には`0`を渡す）。
        *   これは「For all other platforms pipe(2) is removed and Pipe forwards to pipe2(2)」という方針に合致します。これにより、新しいアーキテクチャではよりモダンな`pipe2(2)`を統一的に利用できます。

3.  **`zsyscall_linux_*.go`ファイルの変更**:
    *   `zsyscall_linux_*.go`ファイルは`mksyscall.pl`によって自動生成されるファイルで、実際のシステムコール呼び出し（`RawSyscall`など）を行う低レベルのラッパーが含まれています。
    *   このコミットでは、`pipe`および`pipe2`システムコールのラッパー定義が、汎用的な`zsyscall_linux.go`から、対応するGOOS/GOARCH固有の`zsyscall_linux_386.go`、`zsyscall_linux_amd64.go`、`zsyscall_linux_arm.go`、`zsyscall_linux_ppc64.go`、`zsyscall_linux_ppc64le.go`に移動されました。
    *   `arm`、`ppc64`、`ppc64le`の場合、`pipe`システムコールラッパー自体は不要になるため、`zsyscall_linux_arm.go`などからは削除され、`pipe2`のみが残されています。これは、Goの`Pipe`関数が内部で`pipe2(2)`を呼び出すようになったためです。

この変更により、Goの`syscall`パッケージは、各プラットフォームのシステムコールAPIの差異をより細かく吸収し、適切なシステムコールを呼び出すことができるようになります。これは、Goが多様なプラットフォームをサポートするための重要なステップです。

## コアとなるコードの解説

このコミットの主要な変更は、Goの`syscall`パッケージが提供する`Pipe`および`Pipe2`関数の実装が、LinuxカーネルのバージョンやCPUアーキテクチャの違いに応じて適切に分岐されるようになった点です。

### `Pipe` および `Pipe2` 関数の役割

*   `func Pipe(p []int) (err error)`:
    *   Goプログラムからパイプを作成するための高レベルなインターフェースです。
    *   `p`は2つの整数を格納するためのスライスで、パイプの読み込み側と書き込み側のファイルディスクリプタが格納されます。
*   `func Pipe2(p []int, flags int) (err error)`:
    *   `Pipe`と同様にパイプを作成しますが、`flags`引数を通じてパイプの挙動を制御できます（例: `O_CLOEXEC`、`O_NONBLOCK`）。

### 変更の意図と実装の違い

1.  **汎用`syscall_linux.go`からの削除**:
    *   以前は、すべてのLinuxアーキテクチャで共通の`Pipe`と`Pipe2`の実装が`syscall_linux.go`にありました。しかし、これは`pipe(2)`と`pipe2(2)`のシステムコールサポートがアーキテクチャやカーネルバージョンによって異なるという現実を十分に反映していませんでした。

2.  **`amd64` および `386` の実装 (`syscall_linux_amd64.go`, `syscall_linux_386.go`)**:
    *   これらのアーキテクチャでは、古いLinuxカーネル（2.6.23未満）との互換性を維持するため、`Pipe`関数は引き続き`pipe(2)`システムコールを呼び出します。
    *   `Pipe2`関数は`pipe2(2)`システムコールを呼び出します。
    *   これにより、古いシステムでもGoプログラムがパイプを正しく利用できることが保証されます。

    ```go
    // Pipe は pipe(2) システムコールを呼び出す
    func Pipe(p []int) (err error) {
        // ...
        err = pipe(&pp) // 低レベルの pipe システムコールラッパーを呼び出す
        // ...
    }

    // Pipe2 は pipe2(2) システムコールを呼び出す
    func Pipe2(p []int, flags int) (err error) {
        // ...
        err = pipe2(&pp, flags) // 低レベルの pipe2 システムコールラッパーを呼び出す
        // ...
    }
    ```

3.  **`arm`, `ppc64`, `ppc64le` の実装 (`syscall_linux_arm.go`, `syscall_linux_ppc64x.go`)**:
    *   これらの比較的新しいアーキテクチャでは、`pipe2(2)`システムコールが一般的に利用可能であると見なされます。
    *   そのため、`Pipe`関数も内部的に`pipe2(2)`システムコールを呼び出すように変更されました（`flags`引数には`0`を渡す）。これにより、これらのプラットフォームでは`pipe(2)`システムコールを直接呼び出す必要がなくなります。
    *   `Pipe2`関数は引き続き`pipe2(2)`システムコールを呼び出します。

    ```go
    // Pipe は pipe2(2) システムコールを呼び出す (flags=0)
    func Pipe(p []int) (err error) {
        // ...
        err = pipe2(&pp, 0) // 低レベルの pipe2 システムコールラッパーを呼び出す
        // ...
    }

    // Pipe2 は pipe2(2) システムコールを呼び出す
    func Pipe2(p []int, flags int) (err error) {
        // ...
        err = pipe2(&pp, flags) // 低レベルの pipe2 システムコールラッパーを呼び出す
        // ...
    }
    ```

### `zsyscall_linux_*.go` ファイルの役割

`zsyscall_linux_*.go`ファイルは、`mksyscall.pl`スクリプトによって自動生成されるファイルで、Goの`syscall`パッケージが実際にカーネルのシステムコールを呼び出すための低レベルのラッパー関数（例: `pipe`, `pipe2`）を含んでいます。

このコミットでは、これらの低レベルラッパーも、対応するGOOS/GOARCH固有のファイルに移動されました。特に、`arm`や`ppc64`などのアーキテクチャでは、Goの`Pipe`関数が`pipe2(2)`のみを使用するようになったため、`pipe(2)`システムコールを直接呼び出すための低レベルラッパーは不要となり、`zsyscall_linux_arm.go`などから削除されています。

この変更は、Goのクロスプラットフォーム対応を強化し、各プラットフォームの特性をより正確に反映したシステムコール実装を可能にするための重要なリファクタリングです。

## 元コミット内容

このコミットは、Goコンパイラ（`cmd`）とランタイム（`runtime`）の両方に変更を加え、Android/386環境でのTLS（Thread Local Storage）のセットアップを改善します。特に、`go-review.googlesource.com/15991` で導入されたAMD64版と同様の「醜いハック」を386アーキテクチャに適用し、Goイシュー `golang/go#9327` で報告された問題を解決することを目的としています。

主な変更点は以下の通りです。

*   `src/cmd/internal/obj/x86/asm6.go`: アセンブラコード生成において、Android/386向けにTLSアクセスに`GS`セグメントレジスタを使用するよう変更。
*   `src/cmd/link/internal/ld/sym.go`: リンカがAndroid/386向けにTLSオフセットを`0xf8`に設定するよう変更。
*   `src/runtime/cgo/gcc_android_386.c`: Android/386固有のCgoランタイムサポートファイルが新規追加され、TLSの初期化ロジック（`inittls`）とスレッドエントリポイント（`threadentry`）が実装されています。このファイルには、`pthread_key_create`と`pthread_setspecific`を繰り返し呼び出して、`%gs:0xf8`にGoの`g`ポインタが格納されるTLSスロットを見つけるための特殊なロジックが含まれています。
*   `src/runtime/cgo/gcc_linux_386.c`: Android固有のTLS初期化およびスレッドエントリポイント関数を条件付きで呼び出すように変更され、汎用Linux CgoランタイムからAndroid固有の処理を分離しています。
*   `src/runtime/rt0_android_386.s`: Android/386向けのランタイムエントリポイントのアセンブリコードが新規追加されています。
*   `src/runtime/sys_linux_386.s`: `runtime·setldt`関数がAndroid向けにTLSベースアドレスを`0xf8`だけ調整するように変更されています。

## 変更の背景

この変更の背景には、GoプログラムがAndroid上でCgo（C言語との相互運用機能）を使用する際に、スレッドローカルストレージ（TLS）の管理に課題があったことが挙げられます。特に、Goのランタイムが管理するgoroutineと、Cライブラリが生成するネイティブスレッドの間で、Goの`g`ポインタ（現在のgoroutineのコンテキストを指すポインタ）を効率的かつ確実にアクセスできるTLSスロットを確保する必要がありました。

Goのランタイムは、各goroutineのスタックやスケジューラ情報などを`g`構造体に格納し、これをTLSを介して高速にアクセスできるようにしています。しかし、Android/386環境では、OSやリンカの挙動、あるいは既存のTLS実装との兼ね合いにより、Goが期待する形でTLSスロットを直接設定することが困難でした。

コミットメッセージで言及されている `golang/go#9327` は、まさにこの問題、すなわちAndroid/x86環境でのTLSのセットアップに関するイシューです。このイシューでは、Goのランタイムが`g`ポインタを格納するために使用するTLSスロットが、Cgoを介して呼び出されるCコードから正しくアクセスできない、あるいは初期化されないという問題が議論されていました。

また、「Same ugly hack as https://go-review.googlesource.com/15991」という記述は、この問題がAndroid/AMD64アーキテクチャでも同様に発生しており、既に同様の回避策が導入されていたことを示唆しています。このコミットは、そのAMD64向けの「ハック」をAndroid/386にも適用することで、問題を一時的に解決しようとするものです。この「ハック」は、システムが提供する`pthread_key_create`を繰り返し呼び出すことで、Goランタイムが利用できるTLSスロットを「探し出す」という、やや強引な手法を採用しています。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を把握しておく必要があります。

1.  **スレッドローカルストレージ (TLS: Thread Local Storage)**:
    *   TLSは、マルチスレッド環境において、各スレッドがそれぞれ独立した変数を持つための仕組みです。グローバル変数や静的変数はプロセス内の全スレッドで共有されますが、TLS変数は各スレッドが独自のコピーを持ち、他のスレッドからはアクセスできません。
    *   Goランタイムでは、現在のgoroutineのコンテキスト（`g`ポインタ）をTLSに格納し、高速にアクセスできるようにしています。これにより、関数呼び出しのたびに`g`ポインタを引数として渡す必要がなくなり、パフォーマンスが向上します。
    *   x86アーキテクチャでは、`FS`または`GS`セグメントレジスタをベースとして、TLS領域にアクセスするのが一般的です。これらのレジスタは、特定のメモリ領域の開始アドレスを指し、オフセットを加えることでTLS変数にアクセスします。

2.  **GoのランタイムとGoroutine**:
    *   Goは、OSスレッドよりも軽量な「goroutine」と呼ばれる並行処理の単位を使用します。Goランタイムは、少数のOSスレッド上で多数のgoroutineをスケジューリングします。
    *   各goroutineは独自のスタックを持ち、`g`ポインタによってその状態が管理されます。Goランタイムは、OSスレッドがどのgoroutineを実行しているかを常に把握している必要があります。

3.  **Cgo**:
    *   Cgoは、GoプログラムからC言語のコードを呼び出すためのGoの機能です。Cgoを使用すると、GoとCの間でデータを受け渡ししたり、Cライブラリの関数を呼び出したりできます。
    *   Cgoを介してCコードが呼び出されると、Goランタイムは現在のgoroutineをOSスレッドに「固定」し、CコードがそのOSスレッド上で実行されるようにします。この際、CコードがGoのランタイムとTLSを共有する必要がある場合があります。

4.  **Android/386アーキテクチャ**:
    *   AndroidはLinuxカーネルをベースとしたモバイルOSです。386（x86）アーキテクチャは、かつてAndroidデバイスで広く使用されていましたが、現在はARMアーキテクチャが主流です。
    *   Android環境では、標準的なLinux環境とは異なるリンカの挙動やシステムライブラリの構成が存在することがあり、これがTLSのセットアップを複雑にする要因となることがあります。

5.  **`pthread_key_create` と `pthread_setspecific`**:
    *   これらはPOSIXスレッド（pthreads）APIの一部で、TLSを管理するための関数です。
    *   `pthread_key_create` は、新しいTLSキーを作成します。このキーは、プロセス内で一意の識別子であり、各スレッドがこのキーに関連付けられた独自のデータを格納するために使用できます。
    *   `pthread_setspecific` は、指定されたキーに対して、現在のスレッドのTLSデータを設定します。
    *   `pthread_getspecific` は、指定されたキーに関連付けられた現在のスレッドのTLSデータを取得します。

6.  **セグメントレジスタ (FS/GS)**:
    *   x86アーキテクチャでは、`FS`および`GS`セグメントレジスタは、特定のメモリ領域（セグメント）のベースアドレスを保持するために使用されます。
    *   Linuxでは、これらのレジスタは通常、TLS領域のベースアドレスを指すように設定されます。Goランタイムは、これらのレジスタと特定のオフセットを組み合わせて`g`ポインタにアクセスします。

## 技術的詳細

このコミットの技術的な核心は、Android/386環境において、Goランタイムが`g`ポインタを格納するTLSスロットを、`GS`セグメントレジスタと固定オフセット`0xf8`を介してアクセスできるようにすることです。しかし、このTLSスロットがOSによってどのように割り当てられ、`GS`レジスタがどのように設定されるかについて、Goランタイムが直接制御できない、あるいは予測できない状況がありました。

特に、Cgoを介してCライブラリがロードされると、Cライブラリが独自のTLSを初期化し、`GS`レジスタの設定を変更する可能性があります。このため、Goランタイムが期待する`GS:0xf8`の位置に`g`ポインタが格納されない、あるいはアクセスできなくなるという問題が発生していました。

このコミットで導入された「醜いハック」は、`src/runtime/cgo/gcc_android_386.c` 内の `inittls` 関数に実装されています。この関数は、以下の手順でGoランタイムが使用するTLSスロットを「探し出し」ます。

1.  **`pthread_key_create` の繰り返し呼び出し**: `inittls` 関数は、`pthread_key_create` を繰り返し呼び出して、新しいTLSキーを次々と作成します。これは、システムが利用可能なTLSキーを使い果たし、最終的にGoランタイムが制御できるTLSスロットが割り当てられることを期待するものです。
2.  **`pthread_setspecific` でマジック値を設定**: 各新しく作成されたキーに対して、`pthread_setspecific` を使用して、現在のスレッドのTLSデータとして特定のマジック値（`magic1 = 0x23581321U`）を設定します。
3.  **`GS:0xf8` の値をチェック**: その後、インラインアセンブリ `asm volatile("movl %%gs:0xf8, %0" : "=r"(x));` を使用して、`GS`セグメントレジスタをベースとしたオフセット`0xf8`の位置にあるメモリの値を読み取ります。
4.  **マジック値との比較**: 読み取った値が、ステップ2で設定したマジック値と一致するかどうかをチェックします。
5.  **正しいキーの特定**: もし値が一致すれば、その`pthread_key_t`がGoランタイムが`g`ポインタを格納するために使用できるTLSスロットに対応していると判断し、そのキーを`k1`として保存します。
6.  **不要なキーの解放**: 正しいキーが見つかった後、それまでに作成された他の不要なTLSキーは `pthread_key_delete` で解放されます。

このメカニズムは、システムがTLSスロットを割り当てる際の挙動に依存しており、非常に脆弱で、将来のAndroidやリンカの変更によって容易に破綻する可能性があります。そのため、コミットメッセージでは「ugly hack」と明記されており、将来的に適切な解決策が導入されるまでの「一時的な」回避策であることが示唆されています。

リンカ（`src/cmd/link/internal/ld/sym.go`）とランタイムのアセンブリコード（`src/runtime/sys_linux_386.s`）も、この`0xf8`というオフセットをハードコードしており、Goの`g`ポインタがこの位置に格納されることを前提としています。

`src/runtime/cgo/gcc_linux_386.c` の変更は、汎用Linux CgoランタイムからAndroid固有のTLS初期化ロジックを分離するためのものです。`x_cgo_inittls` と `x_cgo_threadentry` という関数ポインタを導入し、Android環境でのみ `gcc_android_386.c` で定義された関数が呼び出されるようにしています。これにより、コードのモジュール性が向上し、Android固有の挙動が他のLinux環境に影響を与えないようになっています。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は、主に以下のファイルに集中しています。

1.  **`src/runtime/cgo/gcc_android_386.c` (新規ファイル)**:
    *   このファイルは、Android/386環境でのCgoランタイムのTLSセットアップを処理するために新規に作成されました。
    *   `inittls` 関数は、`pthread_key_create` と `pthread_setspecific` を繰り返し呼び出し、`GS:0xf8` をチェックすることで、Goの`g`ポインタを格納するためのTLSスロットを特定する「ハック」を実装しています。
    *   `threadentry` 関数は、Cgoスレッドのエントリポイントとして機能し、特定されたTLSキー `k1` を使用して、現在のgoroutineの`g`ポインタをTLSに設定します。

    ```c
    // src/runtime/cgo/gcc_android_386.c
    // ...
    static void
    inittls(void)
    {
    	uint32 x;
    	pthread_key_t tofree[128], k;
    	int i, ntofree;

    	// ... (コメントで「ugly hack」と説明されている部分) ...

    	ntofree = 0;
    	for(;;) {
    		if(pthread_key_create(&k, nil) < 0) {
    			fprintf(stderr, "runtime/cgo: pthread_key_create failed\n");
    			abort();
    		}
    		pthread_setspecific(k, (void*)magic1);
    		asm volatile("movl %%gs:0xf8, %0" : "=r"(x)); // GS:0xf8 の値を読み取る
    		pthread_setspecific(k, 0);
    		if (x == magic1) { // マジック値と一致するかチェック
    			k1 = k;
    			break;
    		}
    		// ... (エラーハンドリング) ...
    	}
    	// ... (不要なキーの解放) ...
    }

    static void*
    threadentry(void *v)
    {
    	ThreadStart ts;

    	ts = *(ThreadStart*)v;
    	free(v);

    	pthread_setspecific(k1, (void*)ts.g); // 特定されたキーにgポインタを設定

    	crosscall_386(ts.fn);
    	return nil;
    }

    void (*x_cgo_inittls)(void) = inittls;
    void* (*x_cgo_threadentry)(void*) = threadentry;
    ```

2.  **`src/cmd/link/internal/ld/sym.go`**:
    *   リンカがTLSオフセットを決定するロジックが変更されました。
    *   `obj.Getgoos() == "android"` の条件が追加され、Android環境の場合にアーキテクチャ（`ctxt.Arch.Thechar`）に応じて異なるTLSオフセットを設定するようになりました。
    *   特に、`case '8'` (386アーキテクチャ) の場合に `ctxt.Tlsoffset = 0xf8` が設定されます。

    ```go
    // src/cmd/link/internal/ld/sym.go
    // ...
    		obj.Hopenbsd,
    		obj.Hdragonfly,
    		obj.Hsolaris:
    		if obj.Getgoos() == "android" {
    			switch ctxt.Arch.Thechar {
    			case '6':
    				// Android/amd64 constant - offset from 0(FS) to our TLS slot.
    				// Explained in src/runtime/cgo/gcc_android_*.c
    				ctxt.Tlsoffset = 0x1d0
    			case '8': // Android/386 の場合
    				// Android/386 constant - offset from 0(GS) to our TLS slot.
    				ctxt.Tlsoffset = 0xf8
    			default:
    				ctxt.Tlsoffset = -1 * ctxt.Arch.Ptrsize
    			}
    		} else {
    			ctxt.Tlsoffset = -1 * ctxt.Arch.Ptrsize
    		}
    // ...
    ```

3.  **`src/runtime/sys_linux_386.s`**:
    *   `runtime·setldt` 関数内で、`GOOS_android` が定義されている場合に、TLSベースアドレスを`0xf8`だけ調整するアセンブリコードが追加されました。これは、`g`ポインタが`GS:0xf8`に配置されるという前提をランタイム側で保証するためのものです。

    ```assembly

    // ...
    #ifdef GOOS_android
    	/*
    	 * Same as in sys_darwin_386.s:/ugliness, different constant.
    	 * address currently holds m->tls, which must be %gs:0xf8.
    	 * See cgo/gcc_android_386.c for the derivation of the constant.
    	 */
    	SUBL	$0xf8, CX
    	MOVL	CX, 0(CX)
    #else
    // ...
    #endif
    // ...
    ```

## コアとなるコードの解説

これらの変更は、GoランタイムがAndroid/386環境でCgoを使用する際に、`g`ポインタをTLS経由で正しく管理するための連携を確立します。

*   **`src/cmd/link/internal/ld/sym.go`** の変更は、GoのリンカがAndroid/386向けのバイナリを生成する際に、TLSスロットのオフセットとして`0xf8`を認識し、このオフセットをGoのコード内で利用できるようにするための設定を行います。これにより、Goのコンパイラやアセンブラは、`g`ポインタへのアクセスを`GS:0xf8`として表現できるようになります。

*   **`src/cmd/internal/obj/x86/asm6.go`** の変更は、GoのアセンブラがTLSアクセス命令を生成する際に、Android/386向けには`GS`セグメントレジスタ（`0x65`）を使用するように指示します。これは、`GS`レジスタがAndroid/386環境でTLSベースを指すように設定されていることを前提としています。

*   **`src/runtime/cgo/gcc_android_386.c`** は、このTLS設定の「ハック」の中心です。
    *   `inittls` 関数は、Goランタイムが起動する際に一度だけ呼び出され、`pthread_key_create` と `pthread_setspecific` を試行錯誤的に使用して、`GS:0xf8` にアクセスできるTLSキー `k1` を見つけ出します。このプロセスは、システムがTLSスロットをどのように割り当てるかという不確実性に対応するためのものです。
    *   `threadentry` 関数は、Cgoを介して新しいOSスレッドが作成された際に呼び出されます。この関数は、Goの`g`ポインタを、`inittls` で特定されたTLSキー `k1` に関連付けられたスロットに格納します。これにより、CコードからGoランタイムに戻った際に、Goのコードが現在の`g`ポインタをTLSから正しく取得できるようになります。

*   **`src/runtime/sys_linux_386.s`** の変更は、GoランタイムがOSスレッドのTLSを初期化する際に、`GS`レジスタが指すアドレスから`0xf8`を減算することで、`g`ポインタが格納されるべきTLSスロットの正確なアドレスを計算し、そこに`m->tls`（現在のOSスレッドのTLS情報）を書き込むことを保証します。これは、Goランタイムが期待するTLSレイアウトと、OSが提供するTLSレイアウトとの間のギャップを埋めるためのものです。

これらの変更は全体として、Android/386環境におけるGoのCgoとTLSの間の複雑な相互作用を調整し、GoプログラムがCライブラリと連携する際に安定して動作するための基盤を提供します。しかし、その実装が「ハック」と称されるように、特定のシステム挙動に強く依存しており、長期的な解決策としてはより堅牢なアプローチが求められることを示唆しています。

## 元コミット内容

このコミットは、Goコンパイラ（`cmd`）とランタイム（`runtime`）の両方に変更を加え、Android/386環境でのTLS（Thread Local Storage）のセットアップを改善します。特に、`go-review.googlesource.com/15991` で導入されたAMD64版と同様の「醜いハック」を386アーキテクチャに適用し、Goイシュー `golang/go#9327` で報告された問題を解決することを目的としています。

主な変更点は以下の通りです。

*   `src/cmd/internal/obj/x86/asm6.go`: アセンブラコード生成において、Android/386向けにTLSアクセスに`GS`セグメントレジスタを使用するよう変更。
*   `src/cmd/link/internal/ld/sym.go`: リンカがAndroid/386向けにTLSオフセットを`0xf8`に設定するよう変更。
*   `src/runtime/cgo/gcc_android_386.c`: Android/386固有のCgoランタイムサポートファイルが新規追加され、TLSの初期化ロジック（`inittls`）とスレッドエントリポイント（`threadentry`）が実装されています。このファイルには、`pthread_key_create`と`pthread_setspecific`を繰り返し呼び出して、`%gs:0xf8`にGoの`g`ポインタが格納されるTLSスロットを見つけるための特殊なロジックが含まれています。
*   `src/runtime/cgo/gcc_linux_386.c`: Android固有のTLS初期化およびスレッドエントリポイント関数を条件付きで呼び出すように変更され、汎用Linux CgoランタイムからAndroid固有の処理を分離しています。
*   `src/runtime/rt0_android_386.s`: Android/386向けのランタイムエントリポイントのアセンブリコードが新規追加されています。
*   `src/runtime/sys_linux_386.s`: `runtime·setldt`関数がAndroid向けにTLSベースアドレスを`0xf8`だけ調整するように変更されています。

## 変更の背景

この変更の背景には、GoプログラムがAndroid上でCgo（C言語との相互運用機能）を使用する際に、スレッドローカルストレージ（TLS）の管理に課題があったことが挙げられます。特に、Goのランタイムが管理するgoroutineと、Cライブラリが生成するネイティブスレッドの間で、Goの`g`ポインタ（現在のgoroutineのコンテキストを指すポインタ）を効率的かつ確実にアクセスできるTLSスロットを確保する必要がありました。

Goのランタイムは、各goroutineのスタックやスケジューラ情報などを`g`構造体に格納し、これをTLSを介して高速にアクセスできるようにしています。しかし、Android/386環境では、OSやリンカの挙動、あるいは既存のTLS実装との兼ね合いにより、Goが期待する形でTLSスロットを直接設定することが困難でした。

コミットメッセージで言及されている `golang/go#9327` は、まさにこの問題、すなわちAndroid/x86環境でのTLSのセットアップに関するイシューです。このイシューでは、Goのランタイムが`g`ポインタを格納するために使用するTLSスロットが、Cgoを介して呼び出されるCコードから正しくアクセスできない、あるいは初期化されないという問題が議論されていました。

また、「Same ugly hack as https://go-review.googlesource.com/15991」という記述は、この問題がAndroid/AMD64アーキテクチャでも同様に発生しており、既に同様の回避策が導入されていたことを示唆しています。このコミットは、そのAMD64向けの「ハック」をAndroid/386にも適用することで、問題を一時的に解決しようとするものです。この「ハック」は、システムが提供する`pthread_key_create`を繰り返し呼び出すことで、Goランタイムが利用できるTLSスロットを「探し出す」という、やや強引な手法を採用しています。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を把握しておく必要があります。

1.  **スレッドローカルストレージ (TLS: Thread Local Storage)**:
    *   TLSは、マルチスレッド環境において、各スレッドがそれぞれ独立した変数を持つための仕組みです。グローバル変数や静的変数はプロセス内の全スレッドで共有されますが、TLS変数は各スレッドが独自のコピーを持ち、他のスレッドからはアクセスできません。
    *   Goランタイムでは、現在のgoroutineのコンテキスト（`g`ポインタ）をTLSに格納し、高速にアクセスできるようにしています。これにより、関数呼び出しのたびに`g`ポインタを引数として渡す必要がなくなり、パフォーマンスが向上します。
    *   x86アーキテクチャでは、`FS`または`GS`セグメントレジスタをベースとして、TLS領域にアクセスするのが一般的です。これらのレジスタは、特定のメモリ領域の開始アドレスを指し、オフセットを加えることでTLS変数にアクセスします。

2.  **GoのランタイムとGoroutine**:
    *   Goは、OSスレッドよりも軽量な「goroutine」と呼ばれる並行処理の単位を使用します。Goランタイムは、少数のOSスレッド上で多数のgoroutineをスケジューリングします。
    *   各goroutineは独自のスタックを持ち、`g`ポインタによってその状態が管理されます。Goランタイムは、OSスレッドがどのgoroutineを実行しているかを常に把握している必要があります。

3.  **Cgo**:
    *   Cgoは、GoプログラムからC言語のコードを呼び出すためのGoの機能です。Cgoを使用すると、GoとCの間でデータを受け渡ししたり、Cライブラリの関数を呼び出したりできます。
    *   Cgoを介してCコードが呼び出されると、Goランタイムは現在のgoroutineをOSスレッドに「固定」し、CコードがそのOSスレッド上で実行されるようにします。この際、CコードがGoのランタイムとTLSを共有する必要がある場合があります。

4.  **Android/386アーキテクチャ**:
    *   AndroidはLinuxカーネルをベースとしたモバイルOSです。386（x86）アーキテクチャは、かつてAndroidデバイスで広く使用されていましたが、現在はARMアーキテクチャが主流です。
    *   Android環境では、標準的なLinux環境とは異なるリンカの挙動やシステムライブラリの構成が存在することがあり、これがTLSのセットアップを複雑にする要因となることがあります。

5.  **`pthread_key_create` と `pthread_setspecific`**:
    *   これらはPOSIXスレッド（pthreads）APIの一部で、TLSを管理するための関数です。
    *   `pthread_key_create` は、新しいTLSキーを作成します。このキーは、プロセス内で一意の識別子であり、各スレッドがこのキーに関連付けられた独自のデータを格納するために使用できます。
    *   `pthread_setspecific` は、指定されたキーに対して、現在のスレッドのTLSデータを設定します。
    *   `pthread_getspecific` は、指定されたキーに関連付けられた現在のスレッドのTLSデータを取得します。

6.  **セグメントレジスタ (FS/GS)**:
    *   x86アーキテクチャでは、`FS`および`GS`セグメントレジスタは、特定のメモリ領域（セグメント）のベースアドレスを保持するために使用されます。
    *   Linuxでは、これらのレジスタは通常、TLS領域のベースアドレスを指すように設定されます。Goランタイムは、これらのレジスタと特定のオフセットを組み合わせて`g`ポインタにアクセスします。

## 技術的詳細

このコミットの技術的な核心は、Android/386環境において、Goランタイムが`g`ポインタを格納するTLSスロットを、`GS`セグメントレジスタと固定オフセット`0xf8`を介してアクセスできるようにすることです。しかし、このTLSスロットがOSによってどのように割り当てられ、`GS`レジスタがどのように設定されるかについて、Goランタイムが直接制御できない、あるいは予測できない状況がありました。

特に、Cgoを介してCライブラリがロードされると、Cライブラリが独自のTLSを初期化し、`GS`レジスタの設定を変更する可能性があります。このため、Goランタイムが期待する`GS:0xf8`の位置に`g`ポインタが格納されない、あるいはアクセスできなくなるという問題が発生していました。

このコミットで導入された「醜いハック」は、`src/runtime/cgo/gcc_android_386.c` 内の `inittls` 関数に実装されています。この関数は、以下の手順でGoランタイムが使用するTLSスロットを「探し出し」ます。

1.  **`pthread_key_create` の繰り返し呼び出し**: `inittls` 関数は、`pthread_key_create` を繰り返し呼び出して、新しいTLSキーを次々と作成します。これは、システムが利用可能なTLSキーを使い果たし、最終的にGoランタイムが制御できるTLSスロットが割り当てられることを期待するものです。
2.  **`pthread_setspecific` でマジック値を設定**: 各新しく作成されたキーに対して、`pthread_setspecific` を使用して、現在のスレッドのTLSデータとして特定のマジック値（`magic1 = 0x23581321U`）を設定します。
3.  **`GS:0xf8` の値をチェック**: その後、インラインアセンブリ `asm volatile("movl %%gs:0xf8, %0" : "=r"(x));` を使用して、`GS`セグメントレジスタをベースとしたオフセット`0xf8`の位置にあるメモリの値を読み取ります。
4.  **マジック値との比較**: 読み取った値が、ステップ2で設定したマジック値と一致するかどうかをチェックします。
5.  **正しいキーの特定**: もし値が一致すれば、その`pthread_key_t`がGoランタイムが`g`ポインタを格納するために使用できるTLSスロットに対応していると判断し、そのキーを`k1`として保存します。
6.  **不要なキーの解放**: 正しいキーが見つかった後、それまでに作成された他の不要なTLSキーは `pthread_key_delete` で解放されます。

このメカニズムは、システムがTLSスロットを割り当てる際の挙動に依存しており、非常に脆弱で、将来のAndroidやリンカの変更によって容易に破綻する可能性があります。そのため、コミットメッセージでは「ugly hack」と明記されており、将来的に適切な解決策が導入されるまでの「一時的な」回避策であることが示唆されています。

リンカ（`src/cmd/link/internal/ld/sym.go`）とランタイムのアセンブリコード（`src/runtime/sys_linux_386.s`）も、この`0xf8`というオフセットをハードコードしており、Goの`g`ポインタがこの位置に格納されることを前提としています。

`src/runtime/cgo/gcc_linux_386.c` の変更は、汎用Linux CgoランタイムからAndroid固有のTLS初期化ロジックを分離するためのものです。`x_cgo_inittls` と `x_cgo_threadentry` という関数ポインタを導入し、Android環境でのみ `gcc_android_386.c` で定義された関数が呼び出されるようにしています。これにより、コードのモジュール性が向上し、Android固有の挙動が他のLinux環境に影響を与えないようになっています。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は、主に以下のファイルに集中しています。

1.  **`src/runtime/cgo/gcc_android_386.c` (新規ファイル)**:
    *   このファイルは、Android/386環境でのCgoランタイムのTLSセットアップを処理するために新規に作成されました。
    *   `inittls` 関数は、`pthread_key_create` と `pthread_setspecific` を繰り返し呼び出し、`GS:0xf8` をチェックすることで、Goの`g`ポインタを格納するためのTLSスロットを特定する「ハック」を実装しています。
    *   `threadentry` 関数は、Cgoスレッドのエントリポイントとして機能し、特定されたTLSキー `k1` を使用して、現在のgoroutineの`g`ポインタをTLSに設定します。

    ```c
    // src/runtime/cgo/gcc_android_386.c
    // ...
    static void
    inittls(void)
    {
    	uint32 x;
    	pthread_key_t tofree[128], k;
    	int i, ntofree;

    	/*
    	 * Same logic, code as gcc_android_amd64.c:/inittls.
    	 * Note that this is a temporary hack that should be fixed soon.
    	 *
    	 * TODO: fix this.
    	 *
    	 * The linker and runtime hard-code this constant offset
    	 * from %gs where we expect to find g. Disgusting.
    	 *
    	 * Known to src/cmd/link/internal/ld/sym.go:/0xf8
    	 * and to src/runtime/sys_linux_386.s:/0xf8 or /GOOS_android.
    	 * TODO(hyangah): check 0xb0 works with API23+
    	 *
    	 * As disgusting as on the darwin/386, darwin/amd64.
    	 */
    	ntofree = 0;
    	for(;;) {
    		if(pthread_key_create(&k, nil) < 0) {
    			fprintf(stderr, "runtime/cgo: pthread_key_create failed\n");
    			abort();
    		}
    		pthread_setspecific(k, (void*)magic1);
    		asm volatile("movl %%gs:0xf8, %0" : "=r"(x)); // GS:0xf8 の値を読み取る
    		pthread_setspecific(k, 0);
    		if (x == magic1) { // マジック値と一致するかチェック
    			k1 = k;
    			break;
    		}
    		if(ntofree >= nelem(tofree)) {
    			fprintf(stderr, "runtime/cgo: could not obtain pthread_keys\\n");
    			fprintf(stderr, "\\ttried");
    			for(i=0; i<ntofree; i++)
    				fprintf(stderr, " %#x", (unsigned)tofree[i]);
    			fprintf(stderr, "\\n");
    			abort();
    		}
    		tofree[ntofree++] = k;
    	}
    	// TODO: output to stderr is not useful for apps.
    	// Can we fall back to Android's log library?

    	/*
    	 * We got the key we wanted.  Free the others.
    	 */
    	for(i=0; i<ntofree; i++) {
    		pthread_key_delete(tofree[i]);
    	}
    }


    static void*
    threadentry(void *v)
    {
    	ThreadStart ts;

    	ts = *(ThreadStart*)v;
    	free(v);

    	pthread_setspecific(k1, (void*)ts.g); // 特定されたキーにgポインタを設定

    	crosscall_386(ts.fn);
    	return nil;
    }

    void (*x_cgo_inittls)(void) = inittls;
    void* (*x_cgo_threadentry)(void*) = threadentry;
    ```

2.  **`src/cmd/link/internal/ld/sym.go`**:
    *   リンカがTLSオフセットを決定するロジックが変更されました。
    *   `obj.Getgoos() == "android"` の条件が追加され、Android環境の場合にアーキテクチャ（`ctxt.Arch.Thechar`）に応じて異なるTLSオフセットを設定するようになりました。
    *   特に、`case '8'` (386アーキテクチャ) の場合に `ctxt.Tlsoffset = 0xf8` が設定されます。

    ```go

    // ...
    		obj.Hopenbsd,
    		obj.Hdragonfly,
    		obj.Hsolaris:
    		if obj.Getgoos() == "android" {
    			switch ctxt.Arch.Thechar {
    			case '6':
    				// Android/amd64 constant - offset from 0(FS) to our TLS slot.
    				// Explained in src/runtime/cgo/gcc_android_*.c
    				ctxt.Tlsoffset = 0x1d0
    			case '8': // Android/386 の場合
    				// Android/386 constant - offset from 0(GS) to our TLS slot.
    				ctxt.Tlsoffset = 0xf8
    			default:
    				ctxt.Tlsoffset = -1 * ctxt.Arch.Ptrsize
    			}
    		} else {
    			ctxt.Tlsoffset = -1 * ctxt.Arch.Ptrsize
    		}
    // ...
    ```

3.  **`src/runtime/sys_linux_386.s`**:
    *   `runtime·setldt` 関数内で、`GOOS_android` が定義されている場合に、TLSベースアドレスを`0xf8`だけ調整するアセンブリコードが追加されました。これは、`g`ポインタが`GS:0xf8`に配置されるという前提をランタイム側で保証するためのものです。

    ```assembly
    // src/runtime/sys_linux_386.s
    // ...
    #ifdef GOOS_android
    	/*
    	 * Same as in sys_darwin_386.s:/ugliness, different constant.
    	 * address currently holds m->tls, which must be %gs:0xf8.
    	 * See cgo/gcc_android_386.c for the derivation of the constant.
    	 */
    	SUBL	$0xf8, CX
    	MOVL	CX, 0(CX)
    #else
    	/*
    	 * When linking against the system libraries,
    	 * we use its pthread_create and let it set up %gs
    	 * or %fs.
    	 *
    	 * The TLS base is at 0(GS) or 0(FS).
    	 * The Go TLS slot is at 0(TLS).
    	 * The Go TLS slot contains a pointer to the g structure.
    	 *
    	 * The Go TLS slot is at offset 0 from the TLS base.
    	 * The TLS base is at offset 0 from the segment base.
    	 * So the g structure is at 0(GS) or 0(FS).
    	 *
    	 * The address currently holds m->tls, which must be 0(GS) or 0(FS).
    	 * We want to store m->tls at 0(GS) or 0(FS).
    	 * So we store m->tls at 0(m->tls).
    	 */
    	ADDL	$0x4, CX	// address
    	MOVL	CX, 0(CX)
    #endif
    // ...
    ```

## コアとなるコードの解説

これらの変更は、GoランタイムがAndroid/386環境でCgoを使用する際に、`g`ポインタをTLS経由で正しく管理するための連携を確立します。

*   **`src/cmd/link/internal/ld/sym.go`** の変更は、GoのリンカがAndroid/386向けのバイナリを生成する際に、TLSスロットのオフセットとして`0xf8`を認識し、このオフセットをGoのコード内で利用できるようにするための設定を行います。これにより、Goのコンパイラやアセンブラは、`g`ポインタへのアクセスを`GS:0xf8`として表現できるようになります。

*   **`src/cmd/internal/obj/x86/asm6.go`** の変更は、GoのアセンブラがTLSアクセス命令を生成する際に、Android/386向けには`GS`セグメントレジスタ（`0x65`）を使用するように指示します。これは、`GS`レジスタがAndroid/386環境でTLSベースを指すように設定されていることを前提としています。

*   **`src/runtime/cgo/gcc_android_386.c`** は、このTLS設定の「ハック」の中心です。
    *   `inittls` 関数は、Goランタイムが起動する際に一度だけ呼び出され、`pthread_key_create` と `pthread_setspecific` を試行錯誤的に使用して、`GS:0xf8` にアクセスできるTLSキー `k1` を見つけ出します。このプロセスは、システムがTLSスロットをどのように割り当てるかという不確実性に対応するためのものです。
    *   `threadentry` 関数は、Cgoを介して新しいOSスレッドが作成された際に呼び出されます。この関数は、Goの`g`ポインタを、`inittls` で特定されたTLSキー `k1` に関連付けられたスロットに格納します。これにより、CコードからGoランタイムに戻った際に、Goのコードが現在の`g`ポインタをTLSから正しく取得できるようになります。

*   **`src/runtime/sys_linux_386.s`** の変更は、GoランタイムがOSスレッドのTLSを初期化する際に、`GS`レジスタが指すアドレスから`0xf8`を減算することで、`g`ポインタが格納されるべきTLSスロットの正確なアドレスを計算し、そこに`m->tls`（現在のOSスレッドのTLS情報）を書き込むことを保証します。これは、Goランタイムが期待するTLSレイアウトと、OSが提供するTLSレイアウトとの間のギャップを埋めるためのものです。

これらの変更は全体として、Android/386環境におけるGoのCgoとTLSの間の複雑な相互作用を調整し、GoプログラムがCライブラリと連携する際に安定して動作するための基盤を提供します。しかし、その実装が「ハック」と称されるように、特定のシステム挙動に強く依存しており、長期的な解決策としてはより堅牢なアプローチが求められることを示唆しています。

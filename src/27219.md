# [インデックス 27219] ファイルの概要

このコミットは、Goランタイムにおける`gopark`関数とそのアンロック関数が、ゴルーチンのスタックポインタにアクセスする際の潜在的な危険性に対処するものです。具体的には、`gopark`のアンロック関数が、ゴルーチンが`_Gwaiting`状態になった後に実行されるため、その間にスタックが移動する可能性があり、スタックポインタへのアクセスが安全ではないという問題点を修正しています。

## コミット

Goランタイムにおいて、`gopark`のアンロック関数にスタックポインタを渡さないように変更し、`gcBgMarkWorker`と`selparkcommit`の2箇所でこの制約に違反していた箇所を修正しました。これにより、将来的なスタックの同時縮小機能が導入された際にも、ランタイムの安定性と安全性が確保されます。

    runtime: never pass stack pointers to gopark
    
    gopark calls the unlock function after setting the G to _Gwaiting.
    This means it's generally unsafe to access the G's stack from the
    unlock function because the G may start running on another P. Once we
    start shrinking stacks concurrently, a stack shrink could also move
    the stack the moment after it enters _Gwaiting and before the unlock
    function is called.
    
    Document this restriction and fix the two places where we currently
    violate it.
    
    This is unlikely to be a problem in practice for these two places
    right now, but they're already skating on thin ice. For example, the
    following sequence could in principle cause corruption, deadlock, or a
    panic in the select code:
    
    On M1/P1:
    1. G1 selects on channels A and B.
    2. selectgoImpl calls gopark.
    3. gopark puts G1 in _Gwaiting.
    4. gopark calls selparkcommit.
    5. selparkcommit releases the lock on channel A.
    
    On M2/P2:
    6. G2 sends to channel A.
    7. The send puts G1 in _Grunnable and puts it on P2's run queue.
    8. The scheduler runs, selects G1, puts it in _Grunning, and resumes G1.
    9. On G1, the sellock immediately following the gopark gets called.
    10. sellock grows and moves the stack.
    
    On M1/P1:
    11. selparkcommit continues to scan the lock order for the next
    channel to unlock, but it's now reading from a freed (and possibly
    reused) stack.
    
    This shouldn't happen in practice because step 10 isn't the first call
    to sellock, so the stack should already be big enough. However, once
    we start shrinking stacks concurrently, this reasoning won't work any
    more.

## 変更の背景

この変更の背景には、Goランタイムの`gopark`関数がゴルーチンを待機状態にする際の、スタック管理と並行処理における潜在的な競合状態があります。

`gopark`は、現在のゴルーチンを待機状態（`_Gwaiting`）にし、その後に`unlockf`と呼ばれる関数を呼び出します。この`unlockf`の目的は、ゴルーチンが待機状態に入る前に保持していたロックを解放することです。しかし、`gopark`がゴルーチンを`_Gwaiting`状態に設定した直後、かつ`unlockf`が呼び出される前に、そのゴルーチンが別のプロセッサ（P）で実行可能になり、スタックが移動する可能性があります。

特に、Goランタイムが将来的にスタックの同時縮小（concurrent stack shrinking）を導入した場合、この問題は顕在化します。スタックが縮小されると、ゴルーチンのスタックが新しいメモリ位置に移動する可能性があります。もし`unlockf`が移動前のスタック上のデータにアクセスしようとすると、解放されたメモリを読み込んだり、不正なメモリにアクセスしたりする可能性があり、結果としてデータ破損、デッドロック、またはパニックを引き起こす可能性があります。

コミットメッセージでは、`select`文における具体的なシーケンスを例に挙げて、この潜在的な問題を説明しています。

1.  **M1/P1上でG1がチャネルAとBを選択。**
2.  **`selectgoImpl`が`gopark`を呼び出す。**
3.  **`gopark`がG1を`_Gwaiting`状態にする。**
4.  **`gopark`が`selparkcommit`を呼び出す。**
5.  **`selparkcommit`がチャネルAのロックを解放する。**
6.  **M2/P2上でG2がチャネルAに送信。**
7.  **送信によりG1が`_Grunnable`状態になり、P2の実行キューに追加される。**
8.  **スケジューラがG1を選択し、`_Grunning`状態にしてG1を再開する。**
9.  **G1上で、`gopark`の直後の`sellock`が呼び出される。**
10. **`sellock`がスタックを拡張し、移動させる。**
11. **M1/P1上で、`selparkcommit`が次のチャネルのロックを解除するためにロック順序のスキャンを続けるが、この時、解放された（そして再利用された可能性のある）スタックから読み込んでいる。**

現状では、ステップ10のスタック拡張は`sellock`の最初の呼び出しではないため、スタックは既に十分な大きさであるはずで、この問題は発生しにくいとされています。しかし、スタックの同時縮小が導入されると、この前提が崩れるため、この脆弱性に対処する必要がありました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

*   **ゴルーチン (Goroutine)**: Goにおける軽量な実行スレッドです。Goランタイムによって管理され、OSスレッドに多重化されて実行されます。
*   **M, P, G モデル**: Goスケジューラの基本的なモデルです。
    *   **M (Machine)**: OSスレッドを表します。
    *   **P (Processor)**: Goコードを実行するための論理プロセッサを表します。MとGの仲介役となります。
    *   **G (Goroutine)**: ゴルーチン自体を表します。
*   **ゴルーチンの状態**: ゴルーチンは様々な状態を持ちます。
    *   `_Grunning`: 現在実行中の状態。
    *   `_Grunnable`: 実行可能で、スケジューラの実行キューにある状態。
    *   `_Gwaiting`: 何らかのイベント（チャネル操作、ロックの解放など）を待っている状態。`gopark`によってこの状態に遷移します。
*   **`gopark`関数**: `runtime.gopark`は、現在のゴルーチンを待機状態（`_Gwaiting`）にし、スケジューラから実行を一時停止させるための低レベルな関数です。この関数は、引数として`unlockf`という関数を受け取ります。`unlockf`は、ゴルーチンが待機状態に入る前に、ゴルーチンが保持しているロックを解放するために呼び出されます。これにより、デッドロックを防ぎます。
*   **スタック管理**: Goのゴルーチンは、動的にサイズが変更されるスタックを持っています。必要に応じてスタックは拡張（grow）され、将来的には縮小（shrink）される機能も検討されていました。スタックが拡張または縮小される際、その内容は新しいメモリ領域にコピーされることがあります。
*   **ポインタの安全性**: Goでは、ガベージコレクタがポインタを追跡し、参照されているメモリが解放されないようにします。しかし、`unsafe.Pointer`を使用する場合や、ポインタが指すメモリが移動する可能性がある状況では、プログラマがその安全性を保証する必要があります。特に、スタック上のローカル変数へのポインタは、スタックが移動すると無効になる可能性があります。
*   **`muintptr` / `puintptr`**: Goランタイム内部で使用される型で、それぞれ`*m`（Mへのポインタ）と`*p`（Pへのポインタ）を`uintptr`として扱うためのラッパーです。これらはポインタを直接保持するのではなく、`uintptr`として値を保持することで、ガベージコレクタによるポインタ追跡の対象外とすることができます。これにより、ガベージコレクタがポインタをスキャンする際に、スタック上のポインタが移動しても問題が発生しないようにします。また、`set`メソッドを通じて実際のポインタ型との変換を行います。

## 技術的詳細

このコミットが対処している技術的な問題は、`gopark`の`unlockf`関数が、ゴルーチンのスタック上のデータにアクセスすることの危険性です。

`gopark`の動作シーケンスは以下の通りです。
1.  現在のゴルーチン（G）の状態を`_Gwaiting`に設定する。
2.  `unlockf`関数を呼び出す。
3.  スケジューラに制御を戻し、別のゴルーチンを実行させる。

問題はステップ1とステップ2の間にあります。ゴルーチンが`_Gwaiting`状態になった瞬間から、そのゴルーチンはスケジューラの管理下に置かれ、いつでも別のM/P上で実行可能になる可能性があります。特に、`unlockf`が実行されている間に、元のゴルーチンが別のM/Pに移動し、そのスタックが移動（例えば、スタックの拡張や将来的な縮小によって）する可能性があります。

もし`unlockf`が、`gopark`が呼び出されたゴルーチンのスタック上に存在する変数へのポインタを引数として受け取っていた場合、スタックが移動するとそのポインタは無効になります。`unlockf`が無効なポインタを介してメモリにアクセスしようとすると、未定義の動作を引き起こし、ランタイムのクラッシュやデータ破損につながります。

コミットメッセージで示された`select`文の例は、この競合状態がどのように発生しうるかを具体的に示しています。`selparkcommit`関数は`gopark`の`unlockf`として機能し、以前は`hselect`構造体へのポインタを`unsafe.Pointer`として受け取っていました。この`hselect`構造体は、`select`文を実行しているゴルーチンのスタック上に存在していました。

`selparkcommit`がチャネルのロックを解放している間に、別のゴルーチンがそのチャネルに送信し、元のゴルーチンが再開され、スタックが移動する可能性があります。その結果、`selparkcommit`が引き続きスタック上の無効なポインタを介して`hselect`構造体にアクセスしようとすると、問題が発生します。

この問題は、特にGoランタイムがスタックの同時縮小をサポートするようになった場合に深刻になります。スタックの縮小は、スタックが移動するもう一つの機会を提供するため、`unlockf`がスタックポインタに依存していると、より頻繁に問題が発生する可能性があります。

このコミットは、`gopark`の`unlockf`にスタックポインタを渡すことを禁止し、既存の違反箇所を修正することで、この潜在的な競合状態を根本的に解決しようとしています。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/runtime/mgc.go`**: ガベージコレクションのバックグラウンドマークワーカーに関連する`gcBgMarkWorker`関数内の`parkInfo`構造体の扱いが変更されました。
    *   `parkInfo`構造体のフィールド`m *m`と`attach *p`が、それぞれ`muintptr`と`puintptr`に変更されました。
    *   `parkInfo`構造体がスタック上に直接確保されるのではなく、`new(parkInfo)`によってヒープに確保されるようになりました。
    *   `gopark`の呼び出しで、`noescape(unsafe.Pointer(&park))`から`unsafe.Pointer(park)`に変更され、ヒープ上の`parkInfo`へのポインタが渡されるようになりました。
    *   `park.m`や`park.attach`へのアクセスが、`set`や`ptr`メソッドを介して行われるようになりました。

2.  **`src/runtime/proc.go`**: `gopark`関数のコメントが更新され、`unlockf`がゴルーチンのスタックにアクセスしてはならないという制約が明示されました。
    *   `// unlockf must not access this G's stack, as it may be moved between`
    *   `// the call to gopark and the call to unlockf.`

3.  **`src/runtime/select.go`**: `select`文の処理に関連する`selparkcommit`関数が大幅に変更されました。
    *   `selparkcommit`関数が`usel unsafe.Pointer`引数を受け取らなくなり、`_ unsafe.Pointer`に変更されました。これは、`gopark`に渡される`lock`引数が`nil`になることを意味します。
    *   以前は`usel`から`hselect`構造体へのポインタを復元し、その中の`scase`や`lockorder`といったスタック上のデータにアクセスしていましたが、この処理が削除されました。
    *   代わりに、`gp.waiting`（現在のゴルーチンが待機している`sudog`のリンクリスト）を直接走査し、そこからチャネルのロックを解放するロジックに変更されました。これにより、スタック上のデータに依存しないようになりました。
    *   `gopark`の呼び出しで、`unsafe.Pointer(sel)`が`nil`に変更されました。

## コアとなるコードの解説

このコミットのコアとなる変更は、`gopark`の`unlockf`関数が、**呼び出し元のゴルーチンのスタック上のデータに直接アクセスしない**ようにすることです。

### `src/runtime/mgc.go` の変更

`gcBgMarkWorker`関数では、`parkInfo`という構造体が定義され、`gopark`の`unlockf`に渡されていました。以前は、この`parkInfo`はスタック上に直接確保されていました。

```go
// 変更前
type parkInfo struct {
    m      *m // Release this m on park.
    attach *p // If non-nil, attach to this p on park.
}
var park parkInfo // スタック上に確保
// ...
gopark(..., noescape(unsafe.Pointer(&park)), ...) // スタック上のparkへのポインタを渡す
```

この変更により、`parkInfo`はヒープに確保されるようになりました。

```go
// 変更後
type parkInfo struct {
    m      muintptr // Release this m on park.
    attach puintptr // If non-nil, attach to this p on park.
}
// ...
park := new(parkInfo) // ヒープに確保
// ...
gopark(..., unsafe.Pointer(park), ...) // ヒープ上のparkへのポインタを渡す
```

さらに、`parkInfo`のフィールド`m`と`attach`が、それぞれ`*m`と`*p`から`muintptr`と`puintptr`に変更されました。これらは`uintptr`をラップした型で、ポインタを直接保持するのではなく、そのアドレスを`uintptr`として保持します。これにより、ガベージコレクタがこれらのフィールドをポインタとして追跡しなくなり、スタックが移動しても問題が発生しません。`set`や`ptr`メソッドを通じて、必要に応じて実際のポインタ型との変換が行われます。

この変更により、`gopark`の`unlockf`が`parkInfo`にアクセスする際、それがヒープ上のオブジェクトであるため、スタック移動の影響を受けなくなります。

### `src/runtime/select.go` の変更

`selparkcommit`関数は、`select`文が待機状態に入る際に`gopark`の`unlockf`として呼び出される関数です。以前は、この関数は`select`文のコンテキスト情報を含む`hselect`構造体へのポインタを`unsafe.Pointer`として受け取っていました。この`hselect`構造体は、`select`文を実行しているゴルーチンのスタック上に存在していました。

```go
// 変更前
func selparkcommit(gp *g, usel unsafe.Pointer) bool {
    sel := (*hselect)(usel) // スタック上のhselectへのポインタを復元
    // ... selのフィールドにアクセス ...
    selunlock(scases, lockorder)
    return true
}
// ...
gopark(selparkcommit, unsafe.Pointer(sel), ...) // スタック上のselへのポインタを渡す
```

変更後、`selparkcommit`は`usel unsafe.Pointer`引数を受け取らなくなり、`gopark`に渡される`lock`引数も`nil`になりました。

```go
// 変更後
func selparkcommit(gp *g, _ unsafe.Pointer) bool {
    // This must not access gp's stack (see gopark). In
    // particular, it must not access the *hselect. That's okay,
    // because by the time this is called, gp.waiting has all
    // channels in lock order.
    var lastc *hchan
    for sg := gp.waiting; sg != nil; sg = sg.waitlink {
        if sg.c != lastc && lastc != nil {
            // ...
            unlock(&lastc.lock)
        }
        lastc = sg.c
    }
    if lastc != nil {
        unlock(&lastc.lock)
    }
    return true
}
// ...
gopark(selparkcommit, nil, ...) // nilを渡す
```

`selparkcommit`は、`gp.waiting`（現在のゴルーチンが待機している`sudog`のリンクリスト）を直接走査することで、ロックを解放するチャネルを特定するようになりました。`sudog`構造体はヒープ上に存在するため、`gp.waiting`を介してチャネル情報にアクセスすることは、スタック移動の影響を受けません。これにより、`selparkcommit`はスタック上のデータに依存することなく、安全にロックを解放できるようになりました。

これらの変更により、`gopark`の`unlockf`がゴルーチンのスタック上のデータにアクセスする危険性が排除され、Goランタイムの堅牢性が向上しました。

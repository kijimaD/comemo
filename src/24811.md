## 元コミット内容

このコミットは、Goコンパイラの `cmd/compile/internal/gc` パッケージにおいて、`Label` 構造体の `Use` フィールドのデータ型を `NodeList` から Go のスライス (`[]*Node`) に変更するものです。これにより、ラベルの使用箇所を管理する方法が、カスタムの連結リストからGoの組み込みスライスへと移行されます。

## 変更の背景

Goコンパイラの内部では、GOTO文のターゲットとなるラベルや、ジャンプ命令の解決のためにラベル情報が管理されています。`Label` 構造体は、これらのラベルに関するメタデータを保持します。以前は、特定のラベルがコード内で使用されている箇所（抽象構文木 (AST) のノード）を `NodeList` というカスタムの連結リストで管理していました。

この変更の背景には、以下の理由が考えられます。

1.  **コードの簡素化とGoイディオムへの準拠**: Go言語では、動的な要素のコレクションを扱う際にスライスが最も一般的で推奨されるデータ構造です。カスタムの連結リスト実装 (`NodeList`) を使用するよりも、組み込みのスライスを使用する方がコードが簡潔になり、Goのイディオムに沿った記述が可能になります。
2.  **パフォーマンスの向上**: 連結リストは要素の挿入・削除が高速である一方、要素へのアクセスやイテレーション（走査）はシーケンシャルに行う必要があり、キャッシュ効率が悪い場合があります。一方、スライスは連続したメモリ領域に要素を格納するため、イテレーション時のキャッシュ効率が良く、一般的に高速です。ラベルの使用箇所リストは、主に要素の追加（`newlab`関数）と全要素の走査（`checklabels`関数）が行われるため、スライスの方が適していると判断された可能性があります。
3.  **メンテナンス性の向上**: カスタムデータ構造を維持するよりも、Go言語の標準ライブラリや組み込み機能を使用する方が、コードの理解やメンテナンスが容易になります。

## 前提知識の解説

このコミットを理解するためには、以下の概念が役立ちます。

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。`internal/gc` はそのバックエンド部分であり、型チェック、最適化、コード生成など、コンパイルの主要な段階を担います。
*   **抽象構文木 (AST - Abstract Syntax Tree)**: コンパイラがソースコードを解析して生成する、プログラムの構造を木構造で表現したものです。各ノード (`Node`) は、変数、式、文、関数呼び出しなど、コードの構成要素を表します。
*   **`Label` 構造体**: Goコンパイラの内部で、GOTO文のターゲットとなるラベルや、コンパイラが生成するジャンプ命令のターゲットを表現するために使用されるデータ構造です。`Label` 構造体は、ラベルの名前、定義された場所、そしてそのラベルがコード内で参照されているすべての場所を管理します。
*   **`NodeList`**: このコミット以前に `Label.Use` フィールドで使用されていた型です。コミットの差分から推測すると、これは `Node` 型の要素を保持するカスタムの連結リスト実装であったと考えられます。連結リストは、各要素が次の要素へのポインタを持つことで、要素を順序付けて格納するデータ構造です。
*   **Goのスライス (`[]T`)**: Go言語の組み込みデータ構造であり、可変長配列のようなものです。内部的には、配列へのポインタ、長さ、容量の3つの要素で構成されます。要素の追加（`append`）、削除、走査が効率的に行えます。
*   **`newlab` 関数**: 新しいラベルが定義されたり、使用されたりする際に呼び出される関数です。この関数は、`Label` 構造体を初期化または更新し、ラベルの定義箇所や使用箇所を記録します。
*   **`checklabels` 関数**: コンパイルの最終段階で、すべてのラベルが正しく定義され、使用されているかを検証する関数です。例えば、未定義のラベルへのGOTO文がないか、あるいは定義されたが一度も使用されなかったラベルがないかなどをチェックします。

## 技術的詳細

このコミットの技術的な変更点は、`Label` 構造体の `Use` フィールドの型変更と、それに伴う関連コードの修正に集約されます。

1.  **`Label` 構造体の変更 (`src/cmd/compile/internal/gc/go.go`)**:
    *   変更前: `Use *NodeList`
    *   変更後: `Use []*Node`
    `Label` 構造体の `Use` フィールドが、`NodeList` 型のポインタから `Node` 型のポインタのスライス (`[]*Node`) に変更されました。これにより、ラベルの使用箇所を管理するデータ構造が、カスタムの連結リストからGoの組み込みスライスへと切り替わりました。

2.  **`newlab` 関数の変更 (`src/cmd/compile/internal/gc/gen.go`)**:
    `newlab` 関数は、ラベルが使用されるたびにその使用箇所（ASTノード `n`）を `Label.Use` に追加します。
    *   変更前: `lab.Use = list(lab.Use, n)`
        `list` 関数は、既存の `NodeList` に新しいノードを追加し、更新されたリストを返すヘルパー関数であったと推測されます。
    *   変更後: `lab.Use = append(lab.Use, n)`
        スライスに変更されたため、Goの組み込み関数 `append` を使用して、`lab.Use` スライスに直接 `n` を追加するようになりました。これはスライスに対する要素追加の標準的な方法です。

3.  **`checklabels` 関数の変更 (`src/cmd/compile/internal/gc/gen.go`)**:
    `checklabels` 関数は、すべてのラベルの定義と使用を検証するために `Label.Use` を走査します。
    *   変更前:
        ```go
        var l *NodeList
        // ...
        for l = lab.Use; l != nil; l = l.Next {
            yyerrorl(int(l.N.Lineno), "label %v not defined", lab.Sym)
        }
        // ...
        for l = lab.Use; l != nil; l = l.Next {
            checkgoto(l.N, lab.Def)
        }
        ```
        連結リスト `NodeList` を走査するために、`l` という `*NodeList` 型の変数を宣言し、`l = l.Next` で次の要素へ進むという、典型的な連結リストのイテレーションパターンが使用されていました。また、エラー報告や `checkgoto` 関数には `l.N` (リスト要素が持つ `Node` へのポインタ) が渡されていました。
    *   変更後:
        ```go
        for _, n := range lab.Use {
            yyerrorl(int(n.Lineno), "label %v not defined", lab.Sym)
        }
        // ...
        for _, n := range lab.Use {
            checkgoto(n, lab.Def)
        }
        ```
        スライスに変更されたため、Goの `for...range` ループを使用してスライス `lab.Use` を直接イテレートするようになりました。これにより、コードが大幅に簡潔になり、一時変数 `l` の宣言も不要になりました。ループ変数 `n` は直接 `*Node` 型であるため、`n.Lineno` や `n` を `checkgoto` に渡すことができます。

これらの変更により、ラベルの使用箇所管理がよりGoらしい、効率的でメンテナンスしやすい形に改善されました。

## コアとなるコードの解説

このコミットの核となる変更は、`Label` 構造体の `Use` フィールドの型を `*NodeList` から `[]*Node` へと変更したことです。

1.  **`Label` 構造体の `Use` フィールド**:
    *   このフィールドは、特定のラベルがコード内で参照されているすべての抽象構文木 (AST) ノードを格納するために使用されます。
    *   変更前は `*NodeList` であり、これはおそらく `Node` のポインタを要素とするカスタムの連結リストの先頭へのポインタでした。
    *   変更後は `[]*Node` となり、`Node` のポインタのスライスとして管理されるようになりました。これにより、Goの組み込み機能であるスライスを最大限に活用できるようになります。

2.  **`newlab` 関数内の変更**:
    *   `newlab` 関数は、新しいラベルがコード内で使用されるたびに呼び出され、その使用箇所を表す `*Node` を `lab.Use` に追加します。
    *   以前は `list(lab.Use, n)` という形式で、`NodeList` に要素を追加するヘルパー関数が使われていました。
    *   変更後は `append(lab.Use, n)` となり、Goのスライスに要素を追加する標準的な方法に置き換えられました。これは、スライスの動的な性質を直接利用する、より簡潔で効率的な方法です。

3.  **`checklabels` 関数内の変更**:
    *   `checklabels` 関数は、コンパイルの最終段階で、すべてのラベルが正しく定義され、使用されているかを検証します。この検証プロセスでは、`lab.Use` に格納されているすべての使用箇所を走査する必要があります。
    *   以前は `for l = lab.Use; l != nil; l = l.Next` というループ構造で、連結リストのポインタをたどることで要素を走査していました。この方法では、一時変数 `l` が必要であり、各要素にアクセスするためにポインタのデリファレンスが繰り返されます。
    *   変更後は `for _, n := range lab.Use` という Go の `for...range` ループが使用されています。これはスライスを走査する最もGoらしい方法であり、コードが非常に簡潔になります。ループ変数 `n` は直接 `*Node` 型であるため、`n.Lineno` や `checkgoto(n, lab.Def)` のように直接使用できます。これにより、コードの可読性とメンテナンス性が向上し、潜在的なバグのリスクも低減されます。

これらの変更は、Goコンパイラの内部実装をよりGoのイディオムに合わせ、効率性と保守性を向上させるための典型的なリファクタリングの一例と言えます。

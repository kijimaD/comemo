# [インデックス 23957] ファイルの概要

このコミットは、Goの`net/http`パッケージにおいて、古いバグのあるユーザーエージェントがPOSTリクエストのボディの後に余分なCRLF（キャリッジリターン、ラインフィード）を送信するケースを許容するための変更を導入します。これにより、RFC 2616のセクション4.1で推奨されている堅牢性に従い、後続のリクエストの読み取りが正しく行われるようになります。

## コミット

このコミットは、HTTP/1.1の仕様に厳密に従うGoのHTTPサーバーが、一部のクライアントが送信する非標準的なCRLFシーケンスによって後続のリクエストの解析に失敗する問題を解決します。特に、POSTリクエストの後に余分なCRLFが送信された場合、同じTCP接続上の次のリクエストが「400 Bad Request」となる事象が発生していました。この変更により、サーバーはこれらの余分なCRLFをスキップし、より多くのクライアントとの互換性を確保します。

## 変更の背景

この変更は、GitHubのGoリポジトリで報告されたIssue #10876「net/http: HTTP Server messed up pipelined HTTP requests after POST request」に対応するものです。このIssueでは、GoのHTTPサーバーがパイプライン化されたHTTP/1.1リクエストを処理する際に問題があることが指摘されました。具体的には、POSTリクエストの後に続くリクエスト（GETまたはPOST）が正しく解析されず、「400 Bad Request」エラーが返されるというものでした。

この問題の根本原因は、一部の古い、またはバグのあるクライアント（特にHTTP/1.0クライアント）が、POSTリクエストのメッセージボディの後にHTTP/1.1の仕様で禁止されている余分なCRLF文字を送信することにありました。GoのHTTPサーバーはHTTP/1.1の仕様に厳密に従っていたため、これらの余分なCRLFを次のリクエストの開始行（Request-Line）の一部として誤って解釈し、解析エラーを引き起こしていました。

Nginx、Apache、Node.jsなどの他の一般的なHTTPサーバーは、このような非準拠のクライアント動作に対してより寛容であり、余分なCRLFを無視して後続のリクエストを正常に処理していました。GoのHTTPサーバーも同様の堅牢性を持つべきであるという認識から、この変更が導入されました。

## 前提知識の解説

### HTTP/1.1 メッセージフォーマット (RFC 2616 Section 4.1)

HTTP/1.1のメッセージは、リクエストとレスポンスの両方において、厳格なフォーマットに従います。RFC 2616のセクション4.1は、このフォーマットについて詳細に記述しています。

*   **CRLF (Carriage Return Line Feed):** HTTPプロトコルでは、行の終端記号としてCRLF（ASCII 13とASCII 10のシーケンス）を使用します。
*   **メッセージ構造:** HTTPメッセージは、開始行（Request-LineまたはStatus-Line）、ヘッダーフィールドのゼロ個以上の行、空行、そしてオプションのメッセージボディで構成されます。
*   **空行:** ヘッダーフィールドとメッセージボディを区切る空行は、CRLFのみを含む行として定義されます。
*   **堅牢性:** RFC 2616では、サーバーはRequest-Lineが期待される場所で受信した空行を無視することが推奨されています。これは、プロトコルに厳密に従わないクライアントからの入力に対してサーバーがより堅牢であるべきだという考えに基づいています。
*   **クライアントの制限:** HTTP/1.1クライアントは、リクエストの前後に余分なCRLFを追加することを明示的に禁止されています。

### HTTP パイプライン処理

HTTP/1.1では、クライアントが単一のTCP接続上で複数のHTTPリクエストを連続して送信し、それぞれのレスポンスを待たずに済む「パイプライン処理」が可能です。これにより、ネットワークのレイテンシを削減し、パフォーマンスを向上させることができます。しかし、サーバーはこれらのリクエストを順番に処理し、レスポンスも順番に返す必要があります。

### POSTリクエスト

POSTリクエストは、通常、サーバーにデータを送信するために使用され、リクエストヘッダーの後にメッセージボディを含みます。`Content-Length`ヘッダーは、メッセージボディの長さを指定します。

## 技術的詳細

Goの`net/http`パッケージのHTTPサーバーは、以前はHTTP/1.1の仕様に非常に厳密でした。これは、プロトコル違反を検出してエラーを返すという点では正しい動作ですが、現実世界の多様なクライアント（特に古い実装やバグのある実装）との相互運用性において問題を引き起こす可能性がありました。

このコミットの技術的な核心は、`net/http/server.go`内の`conn`構造体と`readRequest`メソッドの変更にあります。

1.  **`conn`構造体への`lastMethod`フィールドの追加:**
    *   `conn`構造体は、単一のTCP接続を管理し、その接続上でのリクエストとレスポンスのやり取りを処理します。
    *   `lastMethod string`フィールドが追加され、この接続で処理された直前のリクエストのHTTPメソッド（例: "GET", "POST"）を追跡するようになりました。これは、POSTリクエストの後にのみ余分なCRLFをスキップするという条件付きのロジックを実装するために必要です。

2.  **`readRequest`メソッド内のCRLFスキップロジック:**
    *   `readRequest`メソッドは、クライアントからの新しいHTTPリクエストを読み取り、解析する役割を担います。
    *   このメソッドの冒頭で、`c.lastMethod == "POST"`であるかどうかがチェックされます。これは、余分なCRLFがPOSTリクエストの後に発生する可能性が高いという問題の性質に基づいています。
    *   もし直前のリクエストがPOSTであった場合、`c.buf.Reader.Peek(4)`を使用して、入力バッファの先頭4バイトを覗き見します。これは、次のリクエストのRequest-Lineの前に余分なCRLFが存在するかどうかを確認するためです。
    *   `numLeadingCRorLF`という新しいヘルパー関数が呼び出され、覗き見したバイト列の先頭にあるCRまたはLF文字の数を数えます。
    *   `c.buf.Reader.Discard(...)`を使用して、検出された余分なCRLF文字を入力バッファから破棄します。これにより、これらの文字が次の`ReadRequest`呼び出しによってRequest-Lineの一部として誤って解釈されるのを防ぎます。

3.  **`numLeadingCRorLF`ヘルパー関数の追加:**
    *   この関数は、バイトスライスを受け取り、その先頭から連続するCR（`\r`）またはLF（`\n`）文字の数を返します。これは、余分なCRLFを効率的に識別し、破棄するために使用されます。

4.  **テストケースの追加:**
    *   `src/net/http/serve_test.go`に`TestTolerateCRLFBeforeRequestLine`という新しいテストケースが追加されました。
    *   このテストは、`POST`リクエストのボディの後に意図的に余分な`CRLF`シーケンスを挿入し、その後に`GET`リクエストを続けるというシナリオをシミュレートします。
    *   サーバーが両方のリクエストをエラーなく正常に処理し、`numReq`が2になることを検証することで、この変更が期待通りに機能することを確認します。

この変更により、GoのHTTPサーバーは、HTTP/1.1の仕様に準拠しつつも、現実世界のクライアントの多様な振る舞いに対してより堅牢で寛容な実装となりました。

## コアとなるコードの変更箇所

### `src/net/http/server.go`

```go
type conn struct {
	// ... 既存のフィールド ...
	tlsState   *tls.ConnectionState // or nil when not using TLS
	lastMethod string               // method of previous request, or ""

	mu           sync.Mutex // guards the following
	clientGone   bool       // if client has disconnected mid-request
	// ... 既存のフィールド ...
}

func (c *conn) readRequest() (w *response, err error) {
	// ... 既存のコード ...

	c.lr.N = c.server.initialLimitedReaderSize()
	if c.lastMethod == "POST" {
		// RFC 2616 section 4.1 tolerance for old buggy clients.
		peek, _ := c.buf.Reader.Peek(4) // ReadRequest will get err below
		c.buf.Reader.Discard(numLeadingCRorLF(peek))
	}
	var req *Request
	if req, err = ReadRequest(c.buf.Reader); err != nil {
		// ... 既存のコード ...
		return nil, err
	}
	c.lr.N = noLimit
	c.lastMethod = req.Method // ここで次のリクエストのためにメソッドを保存

	// ... 既存のコード ...
}

func numLeadingCRorLF(v []byte) (n int) {
	for _, b := range v {
		if b == '\r' || b == '\n' {
			n++
			continue
		}
		break
	}
	return
}
```

### `src/net/http/serve_test.go`

```go
func TestTolerateCRLFBeforeRequestLine(t *testing.T) {
	req := []byte("POST / HTTP/1.1\r\nHost: golang.org\r\nContent-Length: 3\r\n\r\nABC" +
		"\r\n\r\n" + // <-- this stuff is bogus, but we'll ignore it
		"GET / HTTP/1.1\r\nHost: golang.org\r\n\r\n")
	var buf bytes.Buffer
	conn := &rwTestConn{
		Reader: bytes.NewReader(req),
		Writer: &buf,
		closec: make(chan bool, 1),
	}
	ln := &oneConnListener{conn: conn}
	numReq := 0
	go Serve(ln, HandlerFunc(func(rw ResponseWriter, r *Request) {
		numReq++
	}))
	<-conn.closec
	if numReq != 2 {
		t.Errorf("num requests = %d; want 2", numReq)
		t.Logf("Res: %s", buf.Bytes())
	}
}
```

## コアとなるコードの解説

`src/net/http/server.go`の変更は、`conn`構造体に`lastMethod`という新しいフィールドを追加し、直前のリクエストのHTTPメソッドを記憶するようにします。これは、POSTリクエストの後にのみ特定の処理を行うための条件分岐を可能にします。

`readRequest`メソッド内では、新しいリクエストを読み取る前に、`lastMethod`が"POST"であった場合にのみ、入力バッファの先頭を`Peek`（覗き見）します。`Peek(4)`は、最大で4バイト（例えば`\r\n\r\n`）をチェックするために十分な量です。`numLeadingCRorLF`関数は、この覗き見したバイト列の先頭にある連続するCRまたはLF文字の数を計算します。その後、`Discard`メソッドを使って、これらの余分なCRLF文字をバッファから破棄します。これにより、`ReadRequest`が次に呼び出されたときに、これらの余分な文字がRequest-Lineの解析を妨げることがなくなります。リクエストが正常に読み取られた後、`c.lastMethod = req.Method`によって現在のリクエストのメソッドが`lastMethod`に保存され、次のリクエストの処理に備えます。

`numLeadingCRorLF`関数はシンプルで効率的です。与えられたバイトスライスをイテレートし、各バイトがCRまたはLFである限りカウントを増やします。CRまたはLF以外の文字が見つかった時点でループを終了し、それまでのカウントを返します。

`src/net/http/serve_test.go`に追加された`TestTolerateCRLFBeforeRequestLine`テストは、この変更の動作を検証するための重要な部分です。このテストは、`POST`リクエストの後に余分な`\r\n\r\n`を挿入し、その後に`GET`リクエストを続けるという、まさにこのコミットが解決しようとしているシナリオを再現します。テストは、サーバーが両方のリクエストを正常に処理し、`numReq`が2になることを確認することで、サーバーが余分なCRLFを正しく無視していることを保証します。

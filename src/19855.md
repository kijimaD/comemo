# [インデックス 19855] ファイルの概要

このコミットは、Goランタイムにおける`free`関数の削除に関するものです。Go言語はガベージコレクション（GC）によってメモリ管理を自動化しており、開発者が明示的にメモリを解放する`free`関数を呼び出す必要はありません。しかし、ランタイム内部では、メモリの再利用やOSへの返却のために、低レベルなメモリ解放のメカニズムが存在していました。このコミットは、その内部的な`free`メカニズムを廃止し、ランタイムのメモリ管理をさらに簡素化し、効率化することを目的としています。

## 元コミット内容

このコミットの目的は、Goランタイムから内部的な`free`関数を完全に削除することです。コミットメッセージには、その理由として以下の5点が挙げられています。

1.  **ランタイムの著しい簡素化**: `free`関数とその関連コードを削除することで、ランタイムの複雑性が大幅に軽減されます。
2.  **バグの温床**: 既存の`free`関連コードがバグを引き起こしやすいことが判明していました。
3.  **バンプ・ザ・ポインタ割り当てとの非互換性**: `free`の概念が、Goランタイムが採用している「バンプ・ザ・ポインタ（bump-the-pointer）割り当て」という効率的なメモリ割り当て戦略と相容れないためです。
4.  **ランタイムのGo言語での記述への移行**: 将来的にランタイムの大部分をGo言語で記述することを目指しており、Go言語にはC言語のような明示的な`free`関数が存在しないため、この変更はその方向性に合致します。
5.  **起動時の環境文字列解放コードの削減**: 起動時に環境変数の文字列を解放するためのコードが多すぎることが問題視されていました。

## 変更の背景

Go言語は、C言語やC++のような手動でのメモリ管理（`malloc`/`free`や`new`/`delete`）を必要としない、ガベージコレクション（GC）を備えた言語です。Goのランタイムは、プログラムが使用しなくなったメモリを自動的に識別し、再利用可能な状態に戻します。この自動化されたメモリ管理は、メモリリークの防止や開発の簡素化に大きく貢献しています。

しかし、Goランタイムの初期の実装では、内部的にC言語で書かれた部分が多く、メモリの割り当てには`runtime·malloc`が、そしてその解放には`runtime·free`という関数が使用されていました。この`runtime·free`は、開発者が直接呼び出すものではなく、ランタイム内部で特定の状況下（例えば、GCのスイープフェーズや、特定のデータ構造の解放時）に利用される低レベルなメカニズムでした。

このコミットが行われた2014年頃のGoランタイムは、メモリ管理の効率化と簡素化に向けて大きな進化を遂げている時期でした。特に、GCの性能向上や、メモリ割り当て戦略の最適化が活発に進められていました。このような背景の中で、内部的な`free`関数の存在が、以下の点で問題視されるようになりました。

*   **複雑性**: `free`関数は、メモリの解放だけでなく、特殊なオブジェクト（ファイナライザを持つオブジェクトなど）の処理、GCビットマップの更新、スパン（メモリブロックの単位）の状態管理など、多くの複雑なロジックを含んでいました。
*   **バグの温床**: 手動でのメモリ解放は、たとえランタイム内部であっても、ダブルフリーや解放済みメモリへのアクセスといったバグを引き起こすリスクがありました。コミットメッセージにも「This code proved to be buggy.」と明記されています。
*   **GCとの連携**: GoのGCは、マーク＆スイープ方式を採用しており、到達不能なオブジェクトを「スイープ」してメモリを再利用します。このプロセスと、明示的な`free`が混在することで、GCのロジックが複雑になり、競合状態や不整合が生じる可能性がありました。
*   **バンプ・ザ・ポインタ割り当て**: Goランタイムは、特にスタック割り当てにおいて「バンプ・ザ・ポインタ」という非常に高速な割り当て戦略を利用しています。これは、ポインタを「バンプ」（進める）するだけでメモリを割り当てる方式で、解放はポインタを元に戻すだけで行われます。このような割り当てモデルと、ヒープ上の任意の場所を解放する`free`は、根本的に異なる思想に基づいています。ランタイムがよりバンプ・ザ・ポインタのような効率的なモデルに移行する中で、`free`の存在は足かせとなっていました。
*   **Go言語でのランタイム記述**: Go言語自体には`free`という概念がないため、ランタイムのコードをC言語からGo言語に移行する上で、`free`の存在は障壁となっていました。

これらの理由から、Goランタイムの設計者は、内部的な`free`関数を完全に廃止し、メモリ管理のロジックをGCに一元化する方向へと舵を切りました。

## 前提知識の解説

このコミットの理解を深めるためには、Goランタイムのメモリ管理とガベージコレクションに関するいくつかの前提知識が必要です。

### 1. Goのメモリ管理の基本

Go言語は、開発者が明示的にメモリを割り当てたり解放したりする必要がない、自動メモリ管理を採用しています。これは、Goランタイムに組み込まれたガベージコレクタ（GC）によって実現されます。

*   **スタックとヒープ**: Goプログラムは、メモリを主にスタックとヒープの2つの領域に割り当てます。
    *   **スタック**: 関数呼び出し、ローカル変数、関数引数など、生存期間が短いデータが割り当てられます。スタックの割り当てと解放は非常に高速で、ポインタを移動するだけで行われます（後述の「バンプ・ザ・ポインタ」）。
    *   **ヒープ**: グローバル変数、動的に割り当てられるデータ、関数のスコープを超えて生存するデータ（「エスケープ」する変数）が割り当てられます。ヒープのメモリはGCによって管理されます。
*   **エスケープ解析**: Goコンパイラは「エスケープ解析」という静的解析を行い、変数がスタックに割り当てられるべきか、それともヒープにエスケープすべきかを決定します。これにより、不要なヒープ割り当てを減らし、パフォーマンスを向上させます。

### 2. Goのガベージコレクション (GC)

GoのGCは、並行（Concurrent）、非世代別（Non-generational）、非圧縮（Non-compacting）のマーク＆スイープ（Mark-and-Sweep）コレクタです。

*   **マーク＆スイープ**:
    *   **マークフェーズ**: GCは、プログラムの「ルート」（グローバル変数、アクティブなゴルーチンのスタックなど）から開始し、到達可能なすべてのオブジェクトを「ライブ」（使用中）としてマークします。このフェーズの大部分は、アプリケーションの実行と並行して行われます（並行マーク）。
    *   **スイープフェーズ**: マークフェーズの完了後、GCはヒープをスキャンし、マークされなかったオブジェクト（到達不能なオブジェクト）を「ガーベージ」（不要なメモリ）と判断し、そのメモリを再利用可能な状態に戻します。
*   **並行GC**: GoのGCは、アプリケーションの実行を停止する「ストップ・ザ・ワールド（STW）」時間を最小限に抑えるように設計されています。ほとんどのGC作業は、アプリケーションのゴルーチンと並行して実行されます。STWは、GCの特定のクリティカルな部分（例えば、マークフェーズの開始時や終了時）でのみ発生し、その時間は非常に短いです。
*   **トライカラーマーキング**: 並行GCを実現するために、Goはトライカラーマーキングというアルゴリズムを使用します。オブジェクトは白（未訪問、回収候補）、灰（訪問済みだが参照先は未訪問）、黒（訪問済みで参照先もすべて訪問済み）の3つの色で分類されます。
*   **ライトバリア**: 並行マーク中にアプリケーションがオブジェクトグラフを変更してもGCの正確性を保つために、Goはライトバリアを使用します。これは、ポインタの書き込み時にGCに通知するメカニズムです。

### 3. TCMallocにインスパイアされたメモリ割り当て

Goのヒープアロケータは、GoogleのTCMalloc（Thread-Caching Malloc）にインスパイアされています。これは、マルチスレッド環境での効率的なメモリ割り当てのために設計された階層的なアロケータです。

*   **mcache (Thread Cache)**: 各論理プロセッサ（P）は、ロックなしで高速にメモリを割り当てられるローカルな`mcache`を持っています。小さなオブジェクト（約32KBまで）はここから直接割り当てられます。
*   **mspan**: Goのメモリ管理の基本単位で、8KBのメモリページが連続したブロックです。各`mspan`は、特定のサイズのオブジェクトを割り当てるために使用されます。
*   **mcentral (Central Free List)**: `mcache`が`mspan`を使い果たした場合、`mcentral`から新しい`mspan`を要求します。`mcentral`はすべての論理プロセッサで共有されるため、ロックが必要です。
*   **mheap (Global Heap)**: `mheap`はGoヒープ全体を管理し、必要に応じてOSから大きなメモリブロックを要求します。大きなオブジェクト（32KB以上）は`mheap`から直接割り当てられます。

### 4. バンプ・ザ・ポインタ割り当て (Bump-the-pointer allocation)

これは、非常に単純で高速なメモリ割り当て戦略です。

*   **仕組み**: メモリ領域の最後にポインタを保持し、新しいメモリ要求が来ると、そのポインタを要求されたサイズ分だけ「バンプ」（進める）させ、新しいアドレスを返します。
*   **効率性**: 既存の空きブロックを探すオーバーヘッドがないため、非常に高速です。
*   **Goでの利用**: 主にスタック割り当てで利用されます。関数が呼び出されると、そのローカル変数はスタックポインタを移動させるだけで割り当てられます。関数が戻ると、スタックポインタが元に戻され、メモリが効率的に「解放」されます。ヒープ割り当ての文脈では、特定の連続した領域での一時的な割り当てにこの概念が適用されることがあります。

このコミットは、このようなGoの高度なメモリ管理システムの中で、C言語由来の明示的な`free`がもはや不要であり、むしろシステムを複雑化させ、バグの原因となり、将来の設計（特にバンプ・ザ・ポインタ割り当てとの整合性や、ランタイムのGo言語化）の妨げになっているという判断に基づいています。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのメモリ管理サブシステムから、明示的なメモリ解放関数である`runtime·free`とその関連ロジックを完全に排除することにあります。これにより、メモリの解放はガベージコレクタ（GC）の責任に一元化され、ランタイムの設計が大幅に簡素化されます。

具体的には、以下のコンポーネントと概念に影響を与えます。

1.  **`runtime·free`関数の削除**:
    *   `src/pkg/runtime/malloc.c`から`runtime·free`関数の実装が完全に削除されます。この関数は、与えられたポインタ`v`が指すメモリブロックを解放し、対応する`MSpan`を管理する役割を担っていました。
    *   `runtime·free`は、オブジェクトのサイズクラスに応じて、大きなオブジェクトの場合は`MHeap_Free`を呼び出してヒープに直接返却し、小さなオブジェクトの場合は`MCache`のフリーリストに追加していました。
    *   この削除により、ランタイム内部で明示的にメモリを解放するパスがなくなります。

2.  **`MCache`からの明示的なフリーリストの削除**:
    *   `src/pkg/runtime/malloc.h`の`MCache`構造体から`MCacheList free[NumSizeClasses]`フィールドが削除されます。これは、各`mcache`が明示的に解放されたオブジェクトを一時的に保持するためのリストでした。
    *   `src/pkg/runtime/mcache.c`から`runtime·MCache_Free`関数が削除されます。この関数は、`mcache`にオブジェクトを解放する際に使用されていました。
    *   `runtime·MCache_Refill`や`runtime·MCache_ReleaseAll`といった関数からも、`MCacheList`に関連するロジックが削除されます。
    *   これにより、`mcache`は割り当てられたメモリを保持するのみとなり、解放されたメモリは直接GCのスイープフェーズによって処理されるか、`mspan`が完全に空になった場合に`mcentral`に返却されるようになります。

3.  **`MCentral`からの明示的なフリーリスト管理の削除**:
    *   `src/pkg/runtime/malloc.h`の`MCentral`構造体から`nfree`フィールドが削除されます。これは、`mcentral`が管理する空きオブジェクトの数を追跡するためのものでした。
    *   `src/pkg/runtime/mcentral.c`から`MCentral_Free`および`runtime·MCentral_FreeList`関数が削除されます。これらは、`mcentral`にオブジェクトを解放する際に使用されていました。
    *   `MCentral_UncacheSpan`や`MCentral_Grow`といった関数からも、`nfree`の更新や明示的なフリーリスト管理に関連するロジックが削除されます。
    *   `mspan`が`mcache`によって使用されている間、明示的に解放されたオブジェクトを一時的に保持していた`MSpan`の`freebuf`フィールドも削除されます。
    *   これにより、`mcentral`は`mspan`の管理に特化し、個々のオブジェクトの解放はGCのスイープフェーズに委ねられます。

4.  **`MSpan`からの`freebuf`の削除**:
    *   `src/pkg/runtime/malloc.h`の`MSpan`構造体から`MLink *freebuf`フィールドが削除されます。これは、`mcache`が使用中の`mspan`に対して、明示的に解放されたオブジェクトを一時的にバッファリングするためのものでした。
    *   `src/pkg/runtime/mheap.c`の`runtime·MSpan_Init`からも`span->freebuf = nil;`の初期化が削除されます。

5.  **`runtime·markfreed`の削除**:
    *   `src/pkg/runtime/mgc0.c`および`src/pkg/runtime/malloc.h`から`runtime·markfreed`関数が削除されます。この関数は、GCビットマップ上で特定のメモリブロックが解放されたことをマークするために使用されていました。
    *   `runtime·free`が削除されるため、この関数も不要になります。GCは、到達可能性に基づいてメモリを管理するため、個々のブロックが明示的に解放されたことをマークする必要がなくなります。

6.  **`runtime·freeallspecials`の削除**:
    *   `src/pkg/runtime/mheap.c`および`src/pkg/runtime/malloc.h`から`runtime·freeallspecials`関数が削除されます。この関数は、ファイナライザなどの「スペシャル」な情報を持つオブジェクトが解放された際に、それらのスペシャルレコードを処理するために使用されていました。
    *   `runtime·free`の削除に伴い、この関数も不要になります。ファイナライザの処理は、GCのスイープフェーズ中に適切に行われるようになります。

7.  **その他の影響**:
    *   `src/pkg/runtime/env_posix.c`では、`syscall·setenv_c`関数内で`runtime·malloc`で割り当てたメモリを`runtime·free`で解放していましたが、この`runtime·free`の呼び出しが削除されます。これは、環境文字列のメモリもGCによって管理されるようになることを意味します。
    *   `src/pkg/runtime/panic.c`の`freedefer`関数や、`src/pkg/runtime/proc.c`の`allgadd`関数、`src/pkg/runtime/time.goc`の`addtimer`関数など、ランタイム内の様々な箇所で`runtime·free`の呼び出しが削除されています。これらの変更は、これらのコンポーネントが明示的なメモリ解放に依存しなくなり、GCに完全に委ねるようになったことを示しています。

この変更の全体的な影響は、Goランタイムのメモリ管理モデルが、GCを中心とした「割り当ては高速に行い、解放はGCに任せる」という思想に完全に移行したことです。これにより、ランタイムのコードベースが大幅に簡素化され、バグのリスクが低減し、将来的なGCの改善やランタイムのGo言語化への道が開かれました。特に、バンプ・ザ・ポインタ割り当てのような高速な割り当て戦略との整合性が向上し、メモリ管理のオーバーヘッドがさらに削減されることが期待されます。

```diff
 // Information from the compiler about the layout of stack frames.
```

これらの変更は、Goランタイムのメモリ管理が、明示的な`free`の概念から、GCによる自動的なメモリ回収へと完全に移行したことを明確に示しています。

## コアとなるコードの解説

このコミットの最も重要な変更は、`runtime·free`関数の削除です。この関数は、Goランタイム内部でメモリを明示的に解放するために使用されていました。Go言語はガベージコレクション（GC）によってメモリを自動的に管理するため、開発者が直接`free`を呼び出すことはありませんが、ランタイムの低レベルな部分では、特定のメモリブロックをOSに返却したり、再利用可能な状態にしたりするために、このような内部的な`free`メカニズムが必要とされていました。

`runtime·free`が削除されたことで、Goランタイムのメモリ管理は、以下の点で大きく変わりました。

1.  **GCへの一元化**: メモリの解放は、完全にガベージコレクタの責任となりました。オブジェクトが不要になったと判断された場合、GCのマークフェーズで到達不能とマークされ、その後のスイープフェーズでメモリが再利用可能な状態に戻されます。これにより、メモリ管理のロジックがGCに集約され、複雑性が軽減されます。

2.  **バンプ・ザ・ポインタ割り当てとの整合性**: コミットメッセージにもあるように、`free`は「バンプ・ザ・ポインタ割り当て」と非互換でした。バンプ・ザ・ポインタ割り当ては、ポインタを単純に進めるだけでメモリを割り当てる非常に高速な方法です。この方式では、任意の場所のメモリを個別に解放する`free`の概念は馴染みません。メモリの解放は、ポインタを巻き戻すか、GCによって一括して行われるのが自然です。`free`の削除は、ランタイムがよりバンプ・ザ・ポインタのような効率的な割り当て戦略に最適化されることを意味します。

3.  **バグの削減**: 明示的なメモリ解放は、ダブルフリー（同じメモリを二度解放する）や、解放済みメモリへのアクセス（use-after-free）といった深刻なバグを引き起こす可能性があります。たとえランタイム内部のコードであっても、これらのバグはシステムの不安定性やセキュリティ脆弱性につながります。`free`を削除し、GCにメモリ管理を任せることで、これらの種類のバグのリスクが根本的に排除されます。

4.  **ランタイムのGo言語化の促進**: Goランタイムは、パフォーマンス上の理由からC言語やアセンブリ言語で書かれた部分が多く存在しました。しかし、Go言語自体の進化に伴い、ランタイムの大部分をGo言語で記述する方向へと移行が進められています。Go言語にはC言語のような`free`関数が存在しないため、内部的な`free`の削除は、ランタイムのGo言語化をよりスムーズに進めるための重要なステップとなります。

5.  **`MCache`と`MCentral`の簡素化**: `runtime·free`の削除に伴い、`MCache`（スレッドローカルなキャッシュ）や`MCentral`（中央のフリーリスト）が持っていた、明示的に解放されたオブジェクトを管理するための複雑なロジック（`MCacheList free`、`MLink *freebuf`、`MCentral_Free`など）が不要になりました。これにより、これらのメモリ管理コンポーネントの役割がより明確になり、コードが簡素化されます。`mcache`は割り当てに特化し、`mcentral`は`mspan`の管理に特化する形になります。

このコミットは、Goランタイムのメモリ管理戦略における重要な転換点を示しています。手動（あるいは半自動）のメモリ解放から、完全にGCに依存するモデルへの移行を完了させることで、ランタイムの堅牢性、効率性、そして将来的な拡張性が向上しました。

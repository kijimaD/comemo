# [インデックス 25162] ファイルの概要

このコミットは、Goランタイムのガベージコレクタ（GC）におけるファイナライザを持つオブジェクトのスキャン処理を、ストップ・ザ・ワールド（STW）フェーズから並行（concurrent）フェーズに移行させることで、GCの一時停止時間（pause time）を大幅に削減することを目的としています。特に、巨大なヒープを持つアプリケーションにおいて、その効果は顕著です。

    runtime: scan objects with finalizers concurrently
    
    This reduces pause time by ~25% relative to tip and by ~50% relative
    to Go 1.5.1.
    
    Currently one of the steps of STW mark termination is to loop (in
    parallel) over all spans to find objects with finalizers in order to
    mark all objects reachable from these objects and to treat the
    finalizer special as a root. Unfortunately, even if there are no
    finalizers at all, this loop takes roughly 1 ms/heap GB/core, so
    multi-gigabyte heaps can quickly push our STW time past 10ms.
    
    Fix this by moving this scan from mark termination to concurrent scan,
    where it can run in parallel with mutators. The loop itself could also
    be optimized, but this cost is small compared to concurrent marking.
    
    Making this scan concurrent introduces two complications:
    
    1) The scan currently walks the specials list of each span without
    locking it, which is safe only with the world stopped. We fix this by
    speculatively checking if a span has any specials (the vast majority
    won't) and then locking the specials list only if there are specials
    to check.
    
    2) An object can have a finalizer set after concurrent scan, in which
    case it won't have been marked appropriately by concurrent scan. If
    the finalizer is a closure and is only reachable from the special, it
    could be swept before it is run. Likewise, if the object is not marked
    yet when the finalizer is set and then becomes unreachable before it
    is marked, other objects reachable only from it may be swept before
    the finalizer function is run. We fix this issue by making
    addfinalizer ensure the same marking invariants as markroot does.
    
    For multi-gigabyte heaps, this reduces max pause time by 20%–30%
    relative to tip (depending on GOMAXPROCS) and by ~50% relative to Go
    1.5.1 (where this loop was neither concurrent nor parallel). Here are
    the results for the garbage benchmark:
    
                   ---------------- max pause ----------------

    24GB      4         18ms              25ms            37ms

## 元コミット内容

Goランタイムのガベージコレクタにおいて、ファイナライザを持つオブジェクトのスキャン処理を、従来のSTW（Stop-The-World）マーク終了フェーズから、並行スキャンフェーズへと移行させます。これにより、GCの一時停止時間を最大でGo 1.5.1と比較して約50%、最新のGoバージョンと比較しても約25%削減します。

この変更は、ファイナライザを持つオブジェクトから到達可能なすべてのオブジェクトをマークし、ファイナライザ自体をGCルートとして扱うというGCの不変条件を維持しつつ、並行処理の利点を活用します。特に、数ギガバイト規模のヒープを持つシステムでのパフォーマンス改善に貢献します。

## 変更の背景

Goのガベージコレクタは、アプリケーションの実行を一時停止させるSTWフェーズを最小限に抑えるように設計されています。しかし、Go 1.5.1以前のバージョンでは、STWマーク終了フェーズ中にファイナライザを持つオブジェクトをスキャンする処理がボトルネックとなっていました。このスキャンは、たとえファイナライザが全く登録されていなくても、ヒープサイズ1GBあたり、1コアあたり約1ミリ秒の時間を要していました。そのため、数ギガバイトのヒープを持つアプリケーションでは、この処理だけでSTW時間が10ミリ秒を超えてしまうことがあり、これはGCの一時停止時間の目標値（通常10ミリ秒以下）を逸脱する原因となっていました。

この問題を解決するため、ファイナライザを持つオブジェクトのスキャン処理を、アプリケーションの実行（mutators）と並行して行われる「並行スキャン」フェーズに移動させる必要がありました。これにより、STWフェーズでの作業量を減らし、結果として一時停止時間を短縮することが可能になります。

## 前提知識の解説

### Goのガベージコレクタ (GC)

GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースに、並行（Concurrent）かつ低遅延（Low-latency）を目指して設計されています。

*   **三色マーク＆スイープ**: オブジェクトを白、灰、黒の3色で分類し、到達可能性を判断します。
    *   **白**: まだGCによって発見されていない、または到達不可能と判断されたオブジェクト。最終的に回収されます。
    *   **灰**: GCによって発見されたが、その参照先がまだスキャンされていないオブジェクト。
    *   **黒**: GCによって発見され、その参照先もすべてスキャンされたオブジェクト。回収されません。
*   **STW (Stop-The-World)**: GCの特定のフェーズで、アプリケーションの実行（mutators）を完全に停止させる期間。この期間が短いほど、アプリケーションの応答性が向上します。GoのGCはSTWフェーズを最小限に抑える努力をしています。
*   **並行 (Concurrent) GC**: アプリケーションの実行と並行してGC処理の一部を実行するフェーズ。これにより、STW時間を短縮します。
*   **Mutators**: アプリケーションのコードを実行し、ヒープ上のオブジェクトを生成・変更するゴルーチン群を指します。
*   **ファイナライザ (Finalizers)**: `runtime.SetFinalizer` 関数を使ってオブジェクトに登録できる関数です。オブジェクトがGCによって回収される直前に実行されます。主に、CGOで確保したメモリの解放や、ファイルディスクリプタ、ネットワーク接続などの外部リソースのクリーンアップに使用されます。ファイナライザが登録されたオブジェクトは、GCによって特別に扱われ、そのオブジェクト自体と、ファイナライザ関数から到達可能なすべてのオブジェクトは、ファイナライザが実行されるまで回収されません。
*   **GCルート (GC Roots)**: GCが到達可能性の探索を開始する起点となるオブジェクト群です。例えば、スタック上の変数、グローバル変数、レジスタなどがGCルートとなります。ファイナライザも、その特性上、GCルートとして扱われる必要があります。
*   **Span**: Goのメモリ管理における基本的な単位で、連続したページ（通常8KB）の集合です。ヒープは多数のSpanで構成され、各Spanは特定のサイズのオブジェクトを格納します。
*   **Specials List**: 各Spanには、ファイナライザやプロファイリング情報など、特別な処理が必要なオブジェクト（special objects）のリストが関連付けられています。このリストは `mSpan.specials` として管理されます。

### GCのフェーズ（簡略版）

1.  **GC開始 (GC Start)**: GCサイクルが開始されます。
2.  **マークフェーズ (Mark Phase)**:
    *   **STWマーク準備**: 短いSTWフェーズで、GCの準備を行います。
    *   **並行マーク (Concurrent Mark)**: アプリケーションと並行して、GCルートから到達可能なオブジェクトをマークします。
    *   **STWマーク終了 (Mark Termination)**: 短いSTWフェーズで、並行マーク中に発生した変更を処理し、マークフェーズを完了させます。このフェーズで、ファイナライザを持つオブジェクトのスキャンが行われていました。
3.  **スイープフェーズ (Sweep Phase)**: 並行して、マークされなかった（到達不可能な）オブジェクトが占めていたメモリを解放します。

## 技術的詳細

このコミットの核心は、`markrootSpans` 関数（ファイナライザを持つオブジェクトをスキャンする役割）の実行タイミングをSTWマーク終了フェーズから並行スキャンフェーズに移動させることです。しかし、この変更には以下の2つの主要な技術的課題が伴いました。

1.  **`mSpan.specials` リストへの並行アクセス**:
    *   従来の `markrootSpans` はSTW中に実行されていたため、`mSpan.specials` リストをロックなしで走査しても安全でした。しかし、並行スキャン中にこのリストを走査すると、mutatorが同時にリストを変更する可能性があり、データ競合が発生します。
    *   **解決策**: `markrootSpans` 内で、まず `s.specials == nil` を投機的にチェックします。ほとんどのSpanにはspecial objectsがないため、このチェックで多くのロック取得を回避できます。`specials` が存在する場合にのみ、`s.speciallock` を取得してリストを安全に走査するように変更されました。`addfinalizer` 関数も、GCがアクティブな場合は不変条件を保証するように変更され、競合状態での安全性を確保しています。

2.  **並行スキャン後に設定されたファイナライザの処理**:
    *   並行スキャンが完了した後でオブジェクトにファイナライザが設定された場合、そのオブジェクトやそこから到達可能なオブジェクトは、並行スキャン中に適切にマークされていない可能性があります。もしこれらのオブジェクトがGCによって回収されてしまうと、ファイナライザが実行されなかったり、ファイナライザが依存するオブジェクトが消滅したりする問題が発生します。
    *   **解決策**: `addfinalizer` 関数が強化されました。GCがアクティブな期間（`gcphase != _GCoff`）にファイナライザが追加された場合、`addfinalizer` は直ちにそのオブジェクトとファイナライザ関数自体をマークする責任を負います。これにより、`markrootSpans` が既に実行された後でも、ファイナライザに関するGCの不変条件（オブジェクトとそこから到達可能なものがマークされること、ファイナライザ自体がルートとして扱われること）が保証されます。

これらの変更により、ファイナライザのスキャン処理がSTWフェーズから解放され、GCの一時停止時間が大幅に短縮されました。

## コアとなるコードの変更箇所

### `src/runtime/mgc.go`

*   `work` 構造体に `finalizersDone bool` フィールドが追加されました。これは、ファイナライザを持つオブジェクトのスキャンが完了したかどうかを示すフラグです。
*   `gc` 関数内で、GCサイクルの開始時に `work.finalizersDone` が `false` にリセットされ、並行マーク終了時（`gcBackgroundMode` の場合）またはSTWマーク終了時（`gcMark` の場合）に `true` に設定されるようになりました。これにより、`markrootSpans` がファイナライザのスキャンを一度だけ実行するように制御されます。
*   `gcBackgroundMode` のGCパスで、`gcCopySpans()` が `markrootSpans` の前に呼び出されるようになりました。これは `markrootSpans` が `work.spans` を使用するため、最新の状態を保証するためです。

### `src/runtime/mgcmark.go`

*   `markrootSpans` 関数が大幅に変更されました。
    *   `work.finalizersDone` フラグをチェックし、既にファイナライザのスキャンが完了している場合は早期リターンするようになりました。
    *   Spanの `specials` リストを走査する前に、`s.specials == nil` をチェックして投機的にロックを回避し、`specials` が存在する場合にのみ `lock(&s.speciallock)` と `unlock(&s.speciallock)` でリストを保護するようになりました。
    *   ファイナライザを持つオブジェクト `p` から到達可能なすべてのオブジェクトをマークするために `scanobject(p, gcw)` を呼び出し、ファイナライザ関数自体をルートとしてマークするために `scanblock(...)` を呼び出すロジックが明確化されました。

### `src/runtime/mheap.go`

*   `addspecial` および `removespecial` 関数内のコメントが更新され、`mSpan_EnsureSwept` の呼び出しが、スイープ処理が `specials` リストにロックなしでアクセスするため、同期が必要であることを明確にしました。
*   `addfinalizer` 関数に重要な変更が加えられました。
    *   `addspecial` が成功し、かつGCがアクティブな期間（`gcphase != _GCoff`）である場合、新しくファイナライザが設定されたオブジェクトとファイナライザ関数自体を直ちにマークするロジックが追加されました。これは、`markrootSpans` が既に実行されている可能性がある状況で、GCの不変条件を保証するためです。

## コアとなるコードの解説

### `src/runtime/mgcmark.go` の `markrootSpans` 関数

```go
func markrootSpans(gcw *gcWork, shard int) {
    // ... (コメント省略) ...

    // We process objects with finalizers only during the first
    // markroot pass. In concurrent GC, this happens during
    // concurrent scan and we depend on addfinalizer to ensure the
    // above invariants for objects that get finalizers after
    // concurrent scan. In STW GC, this will happen during mark
    // termination.
    if work.finalizersDone {
        return
    }

    // ... (既存のsweepgenチェックなど) ...

    for _, s := range work.spans[startSpan:endSpan] {
        // ... (s.state != mSpanInUse チェックなど) ...

        // Speculatively check if there are any specials
        // without acquiring the span lock. This may race with
        // adding the first special to a span, but in that
        // case addfinalizer will observe that the GC is
        // active (which is globally synchronized) and ensure
        // the above invariants. We may also ensure the
        // invariants, but it's okay to scan an object twice.
        if s.specials == nil {
            continue
        }

        // Lock the specials to prevent a special from being
        // removed from the list while we're traversing it.
        lock(&s.speciallock)

        for sp := s.specials; sp != nil; sp = sp.next {
            if sp.kind != _KindSpecialFinalizer {
                continue
            }
            spf := (*specialfinalizer)(unsafe.Pointer(sp))
            p := uintptr(s.start<<_PageShift) + uintptr(spf.special.offset)/s.elemsize*s.elemsize

            // Mark everything that can be reached from
            // the object (but *not* the object itself or
            // we'll never collect it).
            scanobject(p, gcw)

            // The special itself is a root.
            scanblock(uintptr(unsafe.Pointer(&spf.fn)), ptrSize, &oneptrmask[0], gcw)
        }

        unlock(&s.speciallock)
    }
}
```

このコードは、ファイナライザを持つオブジェクトのスキャンを並行フェーズで行うための主要な変更点を示しています。

1.  **`work.finalizersDone` のチェック**: このフラグにより、ファイナライザのスキャンがGCサイクル中に一度だけ実行されることが保証されます。並行GCモードでは並行スキャン中に、STW GCモードではマーク終了中に実行されます。
2.  **投機的な `s.specials == nil` チェック**: `mSpan.specials` リストに特別なオブジェクトが存在しない場合、ロックを取得せずに `continue` します。これにより、ほとんどのSpanで不要なロックオーバーヘッドを削減します。
3.  **`s.speciallock` による保護**: `specials` リストが存在する場合、`lock` と `unlock` を使用してリストへのアクセスを保護します。これにより、並行実行中にmutatorがリストを変更しても安全に走査できます。
4.  **`scanobject` と `scanblock`**:
    *   `scanobject(p, gcw)`: ファイナライザが設定されたオブジェクト `p` から到達可能なすべてのオブジェクトをマークします。これにより、ファイナライザが実行される際に必要なオブジェクトがGCによって回収されないことが保証されます。
    *   `scanblock(uintptr(unsafe.Pointer(&spf.fn)), ptrSize, &oneptrmask[0], gcw)`: ファイナライザ関数自体（`spf.fn`）をGCルートとしてマークします。ファイナライザ関数はヒープ上に存在しない可能性があるため、これもGCによって回収されないように明示的にマークする必要があります。

### `src/runtime/mheap.go` の `addfinalizer` 関数

```go
func addfinalizer(p unsafe.Pointer, f *funcval, nret uintptr, fint *_type, ot *ptrtype) bool {
    // ... (既存の初期化処理) ...

    if addspecial(p, &s.special) {
        // This is responsible for maintaining the same
        // GC-related invariants as markrootSpans in any
        // situation where it's possible that markrootSpans
        // has already run but mark termination hasn't yet.
        if gcphase != _GCoff {
            _, base, _ := findObject(p)
            mp := acquirem()
            gcw := &mp.p.ptr().gcw
            // Mark everything reachable from the object
            // so it's retained for the finalizer.
            scanobject(uintptr(base), gcw)
            // Mark the finalizer itself, since the
            // special isn't part of the GC'd heap.
            scanblock(uintptr(unsafe.Pointer(&s.fn)), ptrSize, &oneptrmask[0], gcw)
            if gcBlackenPromptly {
                gcw.dispose()
            }
            releasem(mp)
        }
        return true
    }
    // ... (エラー処理など) ...
}
```

この `addfinalizer` の変更は、並行スキャン後にファイナライザが設定された場合の不変条件を保証します。

1.  **`gcphase != _GCoff` のチェック**: GCがアクティブな期間中にファイナライザが追加された場合にのみ、以下の処理を実行します。
2.  **オブジェクトとファイナライザの即時マーク**:
    *   `scanobject(uintptr(base), gcw)`: ファイナライザが設定されたオブジェクト `p` のベースアドレスから到達可能なすべてのオブジェクトをマークします。
    *   `scanblock(uintptr(unsafe.Pointer(&s.fn)), ptrSize, &oneptrmask[0], gcw)`: ファイナライザ関数 `s.fn` 自体をマークします。
    *   これらの処理により、`markrootSpans` が既に実行されていても、新しくファイナライザが設定されたオブジェクトとその関連オブジェクトがGCによって誤って回収されることを防ぎます。

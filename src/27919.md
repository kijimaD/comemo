# [インデックス 27919] ファイルの概要

このコミットは、Goランタイムのメモリ割り当て関数 `mallocgc` の引数を簡素化することを目的としています。具体的には、`mallocgc` がオブジェクトのスキャン要否（`noscan`）を自身で判断できるようになり、残るフラグ引数であるゼロ初期化要否（`needzero`）を単純なブーリアン引数に変更しています。これにより、`mallocgc` の呼び出し側でのフラグ管理が不要になり、コードの可読性と保守性が向上します。

## 変更の背景

Goランタイムのメモリ割り当て関数 `mallocgc` は、ガベージコレクション（GC）の動作を制御するためのフラグ引数を受け取っていました。これには主に以下の2つのフラグがありました。

*   `flagNoScan`: 割り当てられたメモリ領域にポインタが含まれていないことを示し、GCがこの領域をスキャンする必要がないことを示します。これによりGCのオーバーヘッドを削減できます。
*   `flagNoZero`: 割り当てられたメモリ領域をゼロ初期化しないことを示します。パフォーマンスが重要な場面で、ゼロ初期化のコストを避けるために使用されます。

しかし、`flagNoScan` の値は、割り当てられるオブジェクトの型情報 (`_type`) から導出可能であることが判明しました。具体的には、型がポインタを含まない (`kindNoPointers` フラグを持つ) 場合、そのオブジェクトはスキャン不要であると判断できます。

このコミットの背景には、`mallocgc` の呼び出し側で `flagNoScan` を明示的に指定する必要があることによるコードの冗長性と、将来的な変更に対する柔軟性の欠如がありました。`mallocgc` 自身が `noscan` の要否を判断できるようになれば、呼び出し側のコードはよりシンプルになり、`mallocgc` のインターフェースもクリーンになります。

`flagNoZero` については、オブジェクトのゼロ初期化が必要かどうかを外部から制御する必要があるため、これは残す必要がありました。しかし、`flagNoScan` が内部化されることで、`mallocgc` に渡すフラグは `needzero` のみとなり、これをブーリアン引数として直接渡す方が、ビットフラグの集合として渡すよりも明確で扱いやすくなります。

この変更は、Goランタイムの内部コードのクリーンアップと最適化の一環として行われました。

## 前提知識の解説

### Goランタイムとガベージコレクション (GC)

Goは自動メモリ管理（ガベージコレクション）を採用しています。プログラムがメモリを割り当てると、GCは不要になったメモリを自動的に解放します。GCの効率は、Goプログラムのパフォーマンスに大きく影響します。

*   **メモリ割り当て**: Goプログラムが `make` や `new` などの組み込み関数を使ってメモリを要求すると、ランタイムの `mallocgc` 関数が呼び出され、ヒープからメモリが割り当てられます。
*   **GCスキャン**: GCは、ヒープ上のオブジェクトをスキャンして、到達可能なオブジェクト（まだ使われているオブジェクト）と到達不可能なオブジェクト（不要になったオブジェクト）を識別します。到達不可能なオブジェクトは解放されます。
*   **ポインタ**: GCはポインタをたどってオブジェクトの参照関係を構築します。オブジェクト内にポインタが含まれている場合、GCはそのポインタが指す先のオブジェクトもスキャンする必要があります。
*   **`noscan` オブジェクト**: ポインタを含まないオブジェクト（例: `[]byte`, `string`, プリミティブ型の配列など）は、GCがその内容をスキャンする必要がありません。このようなオブジェクトを `noscan` オブジェクトと呼びます。GCが `noscan` オブジェクトをスキャンしないことで、GCの実行時間を短縮できます。
*   **ゼロ初期化**: Goでは、新しく割り当てられたメモリは通常ゼロ初期化されます。これは、プログラムが未初期化のメモリを誤って使用することによるバグを防ぐための安全策です。しかし、場合によっては、割り当て後にすぐにデータが書き込まれるため、ゼロ初期化が不要なこともあります。

### `mallocgc` 関数

`mallocgc` はGoランタイムの主要なメモリ割り当て関数です。この関数は、指定されたサイズのメモリをヒープから割り当て、必要に応じてGCに関する情報（型情報など）をランタイムに提供します。

変更前は、`mallocgc` は以下のようなシグネチャを持っていました。

```go
func mallocgc(size uintptr, typ *_type, flags uint32) unsafe.Pointer
```

*   `size`: 割り当てるメモリのサイズ。
*   `typ`: 割り当てるオブジェクトの型情報。GCがオブジェクトをスキャンする際に使用します。
*   `flags`: GCの動作を制御するためのビットフラグ。`_FlagNoScan` や `_FlagNoZero` などが含まれていました。

### `_type` 構造体と `kindNoPointers`

Goランタイム内部では、すべての型は `_type` 構造体で表現されます。この構造体には、型のサイズ、アラインメント、そしてその型がポインタを含むかどうかを示す `kind` フィールドなどの情報が含まれています。

`kindNoPointers` は `_type` の `kind` フィールドに含まれるビットフラグの一つで、その型がポインタを含まないことを示します。例えば、`int`、`float64`、`[]byte` などの型は `kindNoPointers` フラグを持ちます。

## 技術的詳細

このコミットの核心は、`mallocgc` 関数のインターフェースと内部ロジックの変更にあります。

1.  **`mallocgc` シグネチャの変更**:
    変更前: `func mallocgc(size uintptr, typ *_type, flags uint32) unsafe.Pointer`
    変更後: `func mallocgc(size uintptr, typ *_type, needzero bool) unsafe.Pointer`
    `flags` 引数が `needzero` というブーリアン引数に置き換えられました。これにより、`mallocgc` の呼び出し側は、GCスキャンに関する情報を渡す必要がなくなりました。

2.  **`noscan` の内部計算**:
    `mallocgc` の内部で、`noscan` の要否が `typ` 引数から導出されるようになりました。
    `noscan := typ == nil || typ.kind&kindNoPointers != 0`
    このロジックにより、`typ` が `nil` の場合（型情報がない、つまりポインタを含まない生メモリ割り当ての場合）または `typ` が `kindNoPointers` フラグを持つ場合、そのメモリ領域はGCスキャン不要と判断されます。

3.  **`flagNoScan` および `flagNoZero` 定数の削除**:
    `src/runtime/malloc.go` から `flagNoScan` と `flagNoZero` の定数定義が削除されました。これは、これらのフラグが `mallocgc` の外部インターフェースから取り除かれ、内部で処理されるようになったためです。

4.  **`rawmem` 関数の削除**:
    `rawmem` 関数は、ポインタを含まずゼロ初期化されないメモリチャンクを返すために使用されていました。この関数は `mallocgc` を `flagNoScan|flagNoZero` フラグ付きで呼び出していました。`mallocgc` のインターフェース変更に伴い、`rawmem` は不要となり削除されました。同様の機能は、`mallocgc(capmem, nil, false)` のように `mallocgc` を直接呼び出すことで実現されます。

5.  **呼び出し箇所の更新**:
    `chan.go`, `mfinal.go`, `os1_plan9.go`, `panic.go`, `select.go`, `slice.go`, `string.go` など、`mallocgc` を呼び出すすべての箇所が新しいシグネチャに合わせて更新されました。
    *   以前 `flagNoScan` を渡していた箇所は、`mallocgc` の `typ` 引数によって `noscan` が自動的に判断されるため、`needzero` 引数には `true` が渡されることが多くなりました（ゼロ初期化が必要な場合）。
    *   以前 `flagNoZero` を渡していた箇所は、`needzero` 引数に `false` が渡されるようになりました。
    *   `newobject` や `newarray` のように、型情報から `noscan` を判断していたロジックは削除され、`mallocgc` に `true` (ゼロ初期化が必要) を渡すように変更されました。

この変更により、`mallocgc` の呼び出し側は、メモリ割り当ての際にGCスキャンに関する詳細を考慮する必要がなくなり、コードがより簡潔になりました。また、`mallocgc` の内部で `noscan` のロジックが一元化されたことで、将来的なGCの改善や変更が容易になります。

## コアとなるコードの解説

### `mallocgc` 関数のシグネチャ変更と `noscan` の内部化

最も重要な変更は `mallocgc` 関数のシグネチャです。

```go
// 変更前
func mallocgc(size uintptr, typ *_type, flags uint32) unsafe.Pointer

// 変更後
func mallocgc(size uintptr, typ *_type, needzero bool) unsafe.Pointer
```

`flags` 引数が `needzero` というブーリアンに置き換えられました。これにより、`mallocgc` の呼び出し側は、GCスキャンに関する情報を `flags` ビットマスクの一部として渡す必要がなくなりました。

`noscan` の判断ロジックは `mallocgc` の内部に移動しました。

```go
	noscan := typ == nil || typ.kind&kindNoPointers != 0
```

この一行が、割り当てられるオブジェクトがGCスキャンを必要とするかどうかを決定します。
*   `typ == nil`: 型情報が提供されていない場合（例: `rawstring` や `rawbyteslice` のような生メモリ割り当て）。このような場合、通常はポインタを含まないデータが格納されるため、`noscan` と判断されます。
*   `typ.kind&kindNoPointers != 0`: 割り当てられるオブジェクトの型 (`typ`) が `kindNoPointers` フラグを持っている場合。これは、その型がポインタを含まないことを意味するため、`noscan` と判断されます。

この `noscan` 変数は、`mallocgc` の後続のロジック（例: tiny allocator の使用条件や、GCスキャン関連の処理）で `flags&flagNoScan != 0` の代わりに使われるようになります。

### `needzero` 引数の利用

`needzero` ブーリアン引数は、割り当てられたメモリをゼロ初期化する必要があるかどうかを直接制御します。

```go
			if needzero {
				v.ptr().next = 0
				if size > 2*sys.PtrSize && ((*[2]uintptr)(x))[1] != 0 {
					memclr(unsafe.Pointer(v), size)
				}
			}
```
この部分では、`needzero` が `true` の場合にのみメモリのゼロ初期化が行われます。これにより、ゼロ初期化が不要なケース（例: `rawstring` や `rawbyteslice` のように、割り当て直後にデータが上書きされることが保証されている場合）でパフォーマンスの最適化が可能になります。

### `newobject` および `newarray` の簡素化

`newobject` (Goの `new` 組み込み関数に対応) と `newarray` (Goの `make` 組み込み関数でスライスやマップの基盤配列を生成する際に対応) は、以前は型情報から `flagNoScan` を計算して `mallocgc` に渡していました。

```go
// 変更前 (newobject の例)
func newobject(typ *_type) unsafe.Pointer {
	flags := uint32(0)
	if typ.kind&kindNoPointers != 0 {
		flags |= flagNoScan
	}
	return mallocgc(typ.size, typ, flags)
}

// 変更後
func newobject(typ *_type) unsafe.Pointer {
	return mallocgc(typ.size, typ, true)
}
```
変更後では、`mallocgc` が `noscan` を内部で計算するため、`newobject` や `newarray` は `flagNoScan` のロジックを持つ必要がなくなりました。また、これらの関数は常にゼロ初期化されたメモリを返す必要があるため、`needzero` 引数には `true` が渡されます。これにより、これらの関数の実装が大幅に簡素化されました。

### `rawmem` の削除と代替

`rawmem` 関数は、ポインタを含まずゼロ初期化されないメモリを割り当てるためのヘルパー関数でした。

```go
// 変更前
func rawmem(size uintptr) unsafe.Pointer {
	return mallocgc(size, nil, flagNoScan|flagNoZero)
}
```
この関数は `mallocgc` の `flags` 引数に `flagNoScan|flagNoZero` を渡していました。`mallocgc` のシグネチャ変更により、この関数は不要となり削除されました。同様の機能は、`mallocgc(size, nil, false)` のように `mallocgc` を直接呼び出すことで実現されます。`nil` を `typ` 引数に渡すことで `noscan` が内部で `true` と判断され、`false` を `needzero` に渡すことでゼロ初期化がスキップされます。

## 変更の背景

Goランタイムのメモリ割り当て関数 `mallocgc` は、ガベージコレクション（GC）の動作を制御するためのフラグ引数を受け取っていました。これには主に以下の2つのフラグがありました。

*   `flagNoScan`: 割り当てられたメモリ領域にポインタが含まれていないことを示し、GCがこの領域をスキャンする必要がないことを示します。これによりGCのオーバーヘッドを削減できます。
*   `flagNoZero`: 割り当てられたメモリ領域をゼロ初期化しないことを示します。パフォーマンスが重要な場面で、ゼロ初期化のコストを避けるために使用されます。

しかし、`flagNoScan` の値は、割り当てられるオブジェクトの型情報 (`_type`) から導出可能であることが判明しました。具体的には、型がポインタを含まない (`kindNoPointers` フラグを持つ) 場合、そのオブジェクトはスキャン不要であると判断できます。

このコミットの背景には、`mallocgc` の呼び出し側で `flagNoScan` を明示的に指定する必要があることによるコードの冗長性と、将来的な変更に対する柔軟性の欠如がありました。`mallocgc` 自身が `noscan` の要否を判断できるようになれば、呼び出し側のコードはよりシンプルになり、`mallocgc` のインターフェースもクリーンになります。

`flagNoZero` については、オブジェクトのゼロ初期化が必要かどうかを外部から制御する必要があるため、これは残す必要がありました。しかし、`flagNoScan` が内部化されることで、`mallocgc` に渡すフラグは `needzero` のみとなり、これをブーリアン引数として直接渡す方が、ビットフラグの集合として渡すよりも明確で扱いやすくなります。

この変更は、Goランタイムの内部コードのクリーンアップと最適化の一環として行われました。

## 前提知識の解説

### Goランタイムとガベージコレクション (GC)

Goは自動メモリ管理（ガベージコレクション）を採用しています。プログラムがメモリを割り当てると、GCは不要になったメモリを自動的に解放します。GCの効率は、Goプログラムのパフォーマンスに大きく影響します。

*   **メモリ割り当て**: Goプログラムが `make` や `new` などの組み込み関数を使ってメモリを要求すると、ランタイムの `mallocgc` 関数が呼び出され、ヒープからメモリが割り当てられます。
*   **GCスキャン**: GCは、ヒープ上のオブジェクトをスキャンして、到達可能なオブジェクト（まだ使われているオブジェクト）と到達不可能なオブジェクト（不要になったオブジェクト）を識別します。到達不可能なオブジェクトは解放されます。
*   **ポインタ**: GCはポインタをたどってオブジェクトの参照関係を構築します。オブジェクト内にポインタが含まれている場合、GCはそのポインタが指す先のオブジェクトもスキャンする必要があります。
*   **`noscan` オブジェクト**: ポインタを含まないオブジェクト（例: `[]byte`, `string`, プリミティブ型の配列など）は、GCがその内容をスキャンする必要がありません。このようなオブジェクトを `noscan` オブジェクトと呼びます。GCが `noscan` オブジェクトをスキャンしないことで、GCの実行時間を短縮できます。
*   **ゼロ初期化**: Goでは、新しく割り当てられたメモリは通常ゼロ初期化されます。これは、プログラムが未初期化のメモリを誤って使用することによるバグを防ぐための安全策です。しかし、場合によっては、割り当て後にすぐにデータが書き込まれるため、ゼロ初期化が不要なこともあります。

### `mallocgc` 関数

`mallocgc` はGoランタイムの主要なメモリ割り当て関数です。この関数は、指定されたサイズのメモリをヒープから割り当て、必要に応じてGCに関する情報（型情報など）をランタイムに提供します。

変更前は、`mallocgc` は以下のようなシグネチャを持っていました。

```go
func mallocgc(size uintptr, typ *_type, flags uint32) unsafe.Pointer
```

*   `size`: 割り当てるメモリのサイズ。
*   `typ`: 割り当てるオブジェクトの型情報。GCがオブジェクトをスキャンする際に使用します。
*   `flags`: GCの動作を制御するためのビットフラグ。`_FlagNoScan` や `_FlagNoZero` などが含まれていました。

### `_type` 構造体と `kindNoPointers`

Goランタイム内部では、すべての型は `_type` 構造体で表現されます。この構造体には、型のサイズ、アラインメント、そしてその型がポインタを含むかどうかを示す `kind` フィールドなどの情報が含まれています。

`kindNoPointers` は `_type` の `kind` フィールドに含まれるビットフラグの一つで、その型がポインタを含まないことを示します。例えば、`int`、`float64`、`[]byte` などの型は `kindNoPointers` フラグを持ちます。

このコミットの核心は、`mallocgc` 関数のインターフェースと内部ロジックの変更にあります。

この変更により、`mallocgc` の呼び出し側は、メモリ割り当ての際にGCスキャンに関する詳細を考慮する必要がなくなり、コードがより簡潔になりました。また、`mallocgc` の内部で `noscan` のロジックが一元化されたことで、将来的なGCの改善や変更が容易になります。

### `mallocgc` 関数のシグネチャ変更と `noscan` の内部化

最も重要な変更は `mallocgc` 関数のシグネチャです。

```go
// 変更前
func mallocgc(size uintptr, typ *_type, flags uint32) unsafe.Pointer

// 変更後
func mallocgc(size uintptr, typ *_type, needzero bool) unsafe.Pointer
```

`flags` 引数が `needzero` というブーリアンに置き換えられました。これにより、`mallocgc` の呼び出し側は、GCスキャンに関する情報を `flags` ビットマスクの一部として渡す必要がなくなりました。

`noscan` の判断ロジックは `mallocgc` の内部に移動しました。

```go
	noscan := typ == nil || typ.kind&kindNoPointers != 0
```

この一行が、割り当てられるオブジェクトがGCスキャンを必要とするかどうかを決定します。
*   `typ == nil`: 型情報が提供されていない場合（例: `rawstring` や `rawbyteslice` のような生メモリ割り当て）。このような場合、通常はポインタを含まないデータが格納されるため、`noscan` と判断されます。
*   `typ.kind&kindNoPointers != 0`: 割り当てられるオブジェクトの型 (`typ`) が `kindNoPointers` フラグを持っている場合。これは、その型がポインタを含まないことを意味するため、`noscan` と判断されます。

この `noscan` 変数は、`mallocgc` の後続のロジック（例: tiny allocator の使用条件や、GCスキャン関連の処理）で `flags&flagNoScan != 0` の代わりに使われるようになります。

### `needzero` 引数の利用

`needzero` ブーリアン引数は、割り当てられたメモリをゼロ初期化する必要があるかどうかを直接制御します。

```go
			if needzero {
				v.ptr().next = 0
				if size > 2*sys.PtrSize && ((*[2]uintptr)(x))[1] != 0 {
					memclr(unsafe.Pointer(v), size)
				}
			}
```
この部分では、`needzero` が `true` の場合にのみメモリのゼロ初期化が行われます。これにより、ゼロ初期化が不要なケース（例: `rawstring` や `rawbyteslice` のように、割り当て直後にデータが上書きされることが保証されている場合）でパフォーマンスの最適化が可能になります。

	return mallocgc(typ.size, typ, flags)
}

// 変更後
func newobject(typ *_type) unsafe.Pointer {
	return mallocgc(typ.size, typ, true)
}
```
変更後では、`mallocgc` が `noscan` を内部で計算するため、`newobject` や `newarray` は `flagNoScan` のロジックを持つ必要がなくなりました。また、これらの関数は常にゼロ初期化されたメモリを返す必要があるため、`needzero` 引数には `true` が渡されます。これにより、これらの関数の実装が大幅に簡素化されました。

### `rawmem` の削除と代替

`rawmem` 関数は、ポインタを含まずゼロ初期化されないメモリを割り当てるためのヘルパー関数でした。

```go
// 変更前
func rawmem(size uintptr) unsafe.Pointer {
	return mallocgc(size, nil, flagNoScan|flagNoZero)
}
```
この関数は `mallocgc` の `flags` 引数に `flagNoScan|flagNoZero` を渡していました。`mallocgc` のシグネチャ変更により、この関数は不要となり削除されました。同様の機能は、`mallocgc(size, nil, false)` のように `mallocgc` を直接呼び出すことで実現されます。`nil` を `typ` 引数に渡すことで `noscan` が内部で `true` と判断され、`false` を `needzero` に渡すことでゼロ初期化がスキップされます。

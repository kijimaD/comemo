## 変更の背景

Go言語のランタイムは、そのポータビリティと効率性を高めるために、可能な限りGo言語自身で記述されることを目指しています。初期のGoランタイムには、OSとのインターフェースや低レベルな操作のためにC言語のコードやヘッダーファイルが多数含まれていました。しかし、C言語のコードはクロスコンパイルの複雑さを増し、特定のアーキテクチャやOSに依存する部分のメンテナンスを困難にする可能性があります。

このコミットの背景には、GoランタイムがLinux/PowerPC 64-bitアーキテクチャ（ビッグエンディアンとリトルエンディアンの両方）と効果的に連携するために必要なシステムコール定数やデータ構造の定義を、CヘッダーファイルからGo言語のコードに移行するという戦略があります。これにより、Goランタイムの全体的なGo言語化を推進し、コードの均一性、可読性、保守性を向上させることが目的です。また、`cgo -cdefs` ツールによって生成されたC言語の定義を、さらにGo言語の慣用的な形式に手動で変換することで、よりGoらしいコードベースを目指しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルな部分です。ガベージコレクション、スケジューリング、システムコールインターフェース、メモリ管理など、Go言語の並行処理モデルや効率的な実行を支える基盤を提供します。ランタイムは、GoプログラムがOSとどのように対話するかを定義します。
*   **PowerPC 64-bit (Power64)**: IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャの一種で、64ビットのプロセッサです。Linuxシステムで利用されることがあり、Go言語もこのアーキテクチャをサポートしています。`power64`はビッグエンディアン、`power64le`はリトルエンディアンを指します。
*   **システムコール (System Call)**: オペレーティングシステムが提供するサービスをプログラムが利用するためのインターフェースです。ファイルI/O、メモリ管理、プロセス制御、ネットワーク通信など、OSのカーネル機能にアクセスするために使用されます。Goランタイムは、これらのシステムコールを直接呼び出すことでOSと連携します。
*   **Cgo**: Go言語とC言語のコードを相互に呼び出すためのGoのツールです。`cgo -cdefs`は、C言語の構造体や定数定義からGo言語の対応する定義を自動生成するために使用されます。これは、GoランタイムがOSのC言語ベースのAPIと連携する際に特に役立ちます。
*   **Linuxカーネルの定義**: Linuxカーネルは、システムコールやデータ構造に関する多くの定数や型定義をC言語のヘッダーファイル（例: `/usr/include/linux/*.h`, `/usr/include/asm/*.h`）で提供しています。GoランタイムがこれらのOSレベルの機能を利用するためには、これらのC言語の定義に対応するGo言語の定義が必要です。
*   **`_EINTR`, `_EAGAIN`, `_ENOMEM`**: これらはLinuxシステムコールが返すエラーコードの定数です。
    *   `EINTR`: システムコールがシグナルによって中断されたことを示します。
    *   `EAGAIN`: 操作が非ブロッキングモードで実行され、すぐに完了できないことを示します（例: リソースが一時的に利用できない）。
    *   `ENOMEM`: メモリ不足エラーを示します。
*   **`_PROT_NONE`, `_PROT_READ`, `_PROT_WRITE`, `_PROT_EXEC`**: `mmap`システムコールなどで使用されるメモリ保護フラグです。
    *   `_PROT_NONE`: アクセス不可。
    *   `_PROT_READ`: 読み取り可能。
    *   `_PROT_WRITE`: 書き込み可能。
    *   `_PROT_EXEC`: 実行可能。
*   **`_MAP_ANON`, `_MAP_PRIVATE`, `_MAP_FIXED`**: `mmap`システムコールなどで使用されるメモリマッピングフラグです。
    *   `_MAP_ANON`: ファイルではなく匿名メモリをマッピングします。
    *   `_MAP_PRIVATE`: プライベートなコピーオンライトマッピングを作成します。
    *   `_MAP_FIXED`: 指定されたアドレスにマッピングを配置しようとします。
*   **`_MADV_DONTNEED`**: `madvise`システムコールで使用されるアドバイスフラグで、指定されたメモリ範囲のページがすぐに必要とされないことをカーネルに伝えます。これにより、カーネルはこれらのページを解放して他の用途に再利用できます。
*   **`_SA_RESTART`, `_SA_ONSTACK`, `_SA_SIGINFO`**: `sigaction`システムコールで使用されるシグナルハンドラフラグです。
    *   `_SA_RESTART`: シグナルハンドラから復帰した際に、中断されたシステムコールを自動的に再開します。
    *   `_SA_ONSTACK`: シグナルハンドラを代替シグナルスタックで実行します。
    *   `_SA_SIGINFO`: シグナルハンドラに `siginfo_t` 構造体を追加の引数として渡し、シグナルに関する詳細情報を提供します。
*   **`_SIGHUP`, `_SIGINT`, `_SIGSEGV` などのシグナル定数**: Linuxシステムで定義されている様々なシグナル（ソフトウェア割り込み）の番号です。Goランタイムは、これらのシグナルを処理して、プログラムの異常終了、中断、再開などを管理します。
*   **`timespec`, `timeval`**: 時間を表すC言語の構造体で、秒とナノ秒（`timespec`）または秒とマイクロ秒（`timeval`）で時間を表現します。タイマーや時間関連のシステムコールで使用されます。
*   **`sigactiont`, `siginfo`, `itimerval`, `epollevent`**: これらはLinuxのシステムプログラミングで頻繁に登場するデータ構造です。
    *   `sigactiont`: シグナルハンドラの動作を定義するための構造体。
    *   `siginfo`: シグナルに関する詳細情報（シグナル番号、エラーコード、発生原因など）を含む構造体。
    *   `itimerval`: インターバルタイマーの設定に使用される構造体。
    *   `epollevent`: `epoll`システムコールで使用されるイベント構造体で、監視対象のファイルディスクリプタで発生したイベントの種類と関連データを格納します。
*   **`ptregs`, `sigaltstackt`, `sigcontext`, `ucontext`**: これらは低レベルなシグナル処理やコンテキストスイッチに関連する構造体です。
    *   `ptregs`: プロセッサのレジスタの状態を保存する構造体（"Processor Trap Registers"）。シグナルハンドラが呼び出された際などに、中断されたプログラムのコンテキストを復元するために使用されます。
    *   `sigaltstackt`: 代替シグナルスタックの情報を定義する構造体。
    *   `sigcontext`: シグナル発生時のCPUレジスタの状態やその他のコンテキスト情報を含む構造体。
    *   `ucontext`: ユーザーコンテキストを表す構造体で、プログラムの実行状態（スタック、レジスタ、シグナルマスクなど）を完全に保存・復元するために使用されます。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムがLinux/PowerPC 64-bit環境でOSと対話するために必要な低レベルな定数とデータ構造の定義を、C言語のヘッダーファイルからGo言語のコードに完全に移行した点にあります。

Goランタイムは、OSの機能を利用するためにシステムコールを直接発行します。これらのシステムコールは、C言語のAPIとして提供されており、その引数や戻り値、関連する定数はC言語のヘッダーファイルで定義されています。GoプログラムがこれらのシステムコールをGo言語から安全かつ効率的に呼び出すためには、C言語の定義に対応するGo言語の型と定数が必要です。

以前は、`defs_linux_power64.h` や `defs_linux_power64le.h` といったCヘッダーファイルがこれらの定義を保持していました。これらのファイルは、`cgo -cdefs` ツールによって生成されたものか、あるいは手動で作成されたものでしょう。`cgo -cdefs` は、C言語のソースコードからGo言語の定数や構造体の定義を抽出するのに役立ちますが、その出力は必ずしもGo言語の慣用的なスタイルに完全に合致するわけではありません。

このコミットでは、これらのCヘッダーファイルの内容が、Go言語の `const` ブロックと `type struct` 定義に変換されています。例えば、C言語の `enum` で定義されていた定数（`EINTR`, `PROT_READ` など）は、Go言語の `const` ブロック内の `_EINTR`, `_PROT_READ` といった形式の定数に変換されています。アンダースコアプレフィックス (`_`) は、これらの定数がGoランタイムの内部で使用されることを示唆しています。

同様に、C言語の `struct` で定義されていたデータ構造（`timespec`, `sigactiont`, `ptregs` など）は、Go言語の `type struct` 定義に変換されています。この変換では、C言語のデータ型（例: `int64`, `uint64`, `uint32`, `byte`）がGo言語の対応する型にマッピングされ、パディングバイト (`pad_cgo_0`) が適切に挿入されることで、C言語の構造体とGo言語の構造体間でメモリレイアウトの互換性が維持されています。これは、GoランタイムがC言語のシステムコールAPIと直接やり取りする際に、メモリ上のデータの解釈が正しく行われるために非常に重要です。

この移行の利点は以下の通りです。

1.  **C言語依存の削減**: GoランタイムのC言語コードベースへの依存が減り、Go言語のみで完結する部分が増えます。これにより、ビルドシステムが簡素化され、クロスコンパイルが容易になります。
2.  **Go言語の慣用性**: Cヘッダーファイルから直接生成されたコードは、Go言語のコーディングスタイルや慣習に必ずしも従っていません。手動でのGo言語への変換は、コードの可読性と保守性を向上させます。
3.  **型安全性とコンパイル時のチェック**: Go言語の型システムは、C言語よりも厳格です。Go言語の構造体と定数を使用することで、コンパイル時に型の一貫性がチェックされ、潜在的なバグを早期に発見できます。
4.  **ツールチェインの簡素化**: Cコンパイラや関連ツールへの依存が減ることで、Goのビルドプロセスがよりシンプルで堅牢になります。

この変更は、Goランタイムが特定のアーキテクチャ（この場合はPowerPC 64-bit）上でどのように動作するかという低レベルな詳細に影響を与えますが、Go言語のユーザーが直接意識するようなAPIの変更ではありません。これは、Go言語の内部実装のクリーンアップと最適化の一環です。

*   **ポインタ型**: C言語のポインタ（例: `void*`, `struct Ptregs*`）は、Go言語の `uintptr` や対応する構造体へのポインタ（例: `*ptregs`）に変換されています。

これらのGo言語の定義は、GoランタイムがPowerPC 64-bit環境でLinuxカーネルと直接対話するための「契約」のようなものです。これにより、GoランタイムはC言語のコードを介さずに、OSの低レベルな機能にアクセスできるようになります。

## 変更の背景

Go言語のランタイムは、そのポータビリティと効率性を高めるために、可能な限りGo言語自身で記述されることを目指しています。初期のGoランタイムには、OSとのインターフェースや低レベルな操作のためにC言語のコードやヘッダーファイルが多数含まれていました。しかし、C言語のコードはクロスコンパイルの複雑さを増し、特定のアーキテクチャやOSに依存する部分のメンテナンスを困難にする可能性があります。

このコミットの背景には、GoランタイムがLinux/PowerPC 64-bitアーキテクチャ（ビッグエンディアンとリトルエンディアンの両方）と効果的に連携するために必要なシステムコール定数やデータ構造の定義を、CヘッダーファイルからGo言語のコードに移行するという戦略があります。これにより、Goランタイムの全体的なGo言語化を推進し、コードの均一性、可読性、保守性を向上させることが目的です。また、`cgo -cdefs` ツールによって生成されたC言語の定義を、さらにGo言語の慣用的な形式に手動で変換することで、よりGoらしいコードベースを目指しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルな部分です。ガベージコレクション、スケジューリング、システムコールインターフェース、メモリ管理など、Go言語の並行処理モデルや効率的な実行を支える基盤を提供します。ランタイムは、GoプログラムがOSとどのように対話するかを定義します。
*   **PowerPC 64-bit (Power64)**: IBMが開発したRISC（Reduced Instruction Set Computer）アーキテクチャの一種で、64ビットのプロセッサです。Linuxシステムで利用されることがあり、Go言語もこのアーキテクチャをサポートしています。`power64`はビッグエンディアン、`power64le`はリトルエンディアンを指します。
*   **システムコール (System Call)**: オペレーティングシステムが提供するサービスをプログラムが利用するためのインターフェースです。ファイルI/O、メモリ管理、プロセス制御、ネットワーク通信など、OSのカーネル機能にアクセスするために使用されます。Goランタイムは、これらのシステムコールを直接呼び出すことでOSと連携します。
*   **Cgo**: Go言語とC言語のコードを相互に呼び出すためのGoのツールです。`cgo -cdefs`は、C言語の構造体や定数定義からGo言語の対応する定義を自動生成するために使用されます。これは、GoランタイムがOSのC言語ベースのAPIと連携する際に特に役立ちます。
*   **Linuxカーネルの定義**: Linuxカーネルは、システムコールやデータ構造に関する多くの定数や型定義をC言語のヘッダーファイル（例: `/usr/include/linux/*.h`, `/usr/include/asm/*.h`）で提供しています。GoランタイムがこれらのOSレベルの機能を利用するためには、これらのC言語の定義に対応するGo言語の定義が必要です。
*   **`_EINTR`, `_EAGAIN`, `_ENOMEM`**: これらはLinuxシステムコールが返すエラーコードの定数です。
    *   `EINTR`: システムコールがシグナルによって中断されたことを示します。
    *   `EAGAIN`: 操作が非ブロッキングモードで実行され、すぐに完了できないことを示します（例: リソースが一時的に利用できない）。
    *   `ENOMEM`: メモリ不足エラーを示します。
*   **`_PROT_NONE`, `_PROT_READ`, `_PROT_WRITE`, `_PROT_EXEC`**: `mmap`システムコールなどで使用されるメモリ保護フラグです。
    *   `_PROT_NONE`: アクセス不可。
    *   `_PROT_READ`: 読み取り可能。
    *   `_PROT_WRITE`: 書き込み可能。
    *   `_PROT_EXEC`: 実行可能。
*   **`_MAP_ANON`, `_MAP_PRIVATE`, `_MAP_FIXED`**: `mmap`システムコールなどで使用されるメモリマッピングフラグです。
    *   `_MAP_ANON`: ファイルではなく匿名メモリをマッピングします。
    *   `_MAP_PRIVATE`: プライベートなコピーオンライトマッピングを作成します。
    *   `_MAP_FIXED`: 指定されたアドレスにマッピングを配置しようとします。
*   **`_MADV_DONTNEED`**: `madvise`システムコールで使用されるアドバイスフラグで、指定されたメモリ範囲のページがすぐに必要とされないことをカーネルに伝えます。これにより、カーネルはこれらのページを解放して他の用途に再利用できます。
*   **`_SA_RESTART`, `_SA_ONSTACK`, `_SA_SIGINFO`**: `sigaction`システムコールで使用されるシグナルハンドラフラグです。
    *   `_SA_RESTART`: シグナルハンドラから復帰した際に、中断されたシステムコールを自動的に再開します。
    *   `_SA_ONSTACK`: シグナルハンドラを代替シグナルスタックで実行します。
    *   `_SA_SIGINFO`: シグナルハンドラに `siginfo_t` 構造体を追加の引数として渡し、シグナルに関する詳細情報を提供します。
*   **`_SIGHUP`, `_SIGINT`, `_SIGSEGV` などのシグナル定数**: Linuxシステムで定義されている様々なシグナル（ソフトウェア割り込み）の番号です。Goランタイムは、これらのシグナルを処理して、プログラムの異常終了、中断、再開などを管理します。
*   **`timespec`, `timeval`**: 時間を表すC言語の構造体で、秒とナノ秒（`timespec`）または秒とマイクロ秒（`timeval`）で時間を表現します。タイマーや時間関連のシステムコールで使用されます。
*   **`sigactiont`, `siginfo`, `itimerval`, `epollevent`**: これらはLinuxのシステムプログラミングで頻繁に登場するデータ構造です。
    *   `sigactiont`: シグナルハンドラの動作を定義するための構造体。
    *   `siginfo`: シグナルに関する詳細情報（シグナル番号、エラーコード、発生原因など）を含む構造体。
    *   `itimerval`: インターバルタイマーの設定に使用される構造体。
    *   `epollevent`: `epoll`システムコールで使用されるイベント構造体で、監視対象のファイルディスクリプタで発生したイベントの種類と関連データを格納します。
*   **`ptregs`, `sigaltstackt`, `sigcontext`, `ucontext`**: これらは低レベルなシグナル処理やコンテキストスイッチに関連する構造体です。
    *   `ptregs`: プロセッサのレジスタの状態を保存する構造体（"Processor Trap Registers"）。シグナルハンドラが呼び出された際などに、中断されたプログラムのコンテキストを復元するために使用されます。
    *   `sigaltstackt`: 代替シグナルスタックの情報を定義する構造体。
    *   `sigcontext`: シグナル発生時のCPUレジスタの状態やその他のコンテキスト情報を含む構造体。
    *   `ucontext`: ユーザーコンテキストを表す構造体で、プログラムの実行状態（スタック、レジスタ、シグナルマスクなど）を完全に保存・復元するために使用されます。

## 技術的詳細

このコミットの技術的な核心は、GoランタイムがLinux/PowerPC 64-bit環境でOSと対話するために必要な低レベルな定数とデータ構造の定義を、C言語のヘッダーファイルからGo言語のコードに完全に移行した点にあります。

Goランタイムは、OSの機能を利用するためにシステムコールを直接発行します。これらのシステムコールは、C言語のAPIとして提供されており、その引数や戻り値、関連する定数はC言語のヘッダーファイルで定義されています。GoプログラムがこれらのシステムコールをGo言語から安全かつ効率的に呼び出すためには、C言語の定義に対応するGo言語の型と定数が必要です。

以前は、`defs_linux_power64.h` や `defs_linux_power64le.h` といったCヘッダーファイルがこれらの定義を保持していました。これらのファイルは、`cgo -cdefs` ツールによって生成されたものか、あるいは手動で作成されたものでしょう。`cgo -cdefs` は、C言語のソースコードからGo言語の定数や構造体の定義を抽出するのに役立ちますが、その出力は必ずしもGo言語の慣用的なスタイルに完全に合致するわけではありません。

このコミットでは、これらのCヘッダーファイルの内容が、Go言語の `const` ブロックと `type struct` 定義に変換されています。例えば、C言語の `enum` で定義されていた定数（`EINTR`, `PROT_READ` など）は、Go言語の `const` ブロック内の `_EINTR`, `_PROT_READ` といった形式の定数に変換されています。アンダースコアプレフィックス (`_`) は、これらの定数がGoランタイムの内部で使用されることを示唆しています。

同様に、C言語の `struct` で定義されていたデータ構造（`timespec`, `sigactiont`, `ptregs` など）は、Go言語の `type struct` 定義に変換されています。この変換では、C言語のデータ型（例: `int64`, `uint64`, `uint32`, `byte`）がGo言語の対応する型にマッピングされ、パディングバイト (`pad_cgo_0`) が適切に挿入されることで、C言語の構造体とGo言語の構造体間でメモリレイアウトの互換性が維持されています。これは、GoランタイムがC言語のシステムコールAPIと直接やり取りする際に、メモリ上のデータの解釈が正しく行われるために非常に重要です。

この移行の利点は以下の通りです。

1.  **C言語依存の削減**: GoランタイムのC言語コードベースへの依存が減り、Go言語のみで完結する部分が増えます。これにより、ビルドシステムが簡素化され、クロスコンパイルが容易になります。
2.  **Go言語の慣用性**: Cヘッダーファイルから直接生成されたコードは、Go言語のコーディングスタイルや慣習に必ずしも従っていません。手動でのGo言語への変換は、コードの可読性と保守性を向上させます。
3.  **型安全性とコンパイル時のチェック**: Go言語の型システムは、C言語よりも厳格です。Go言語の構造体と定数を使用することで、コンパイル時に型の一貫性がチェックされ、潜在的なバグを早期に発見できます。
4.  **ツールチェインの簡素化**: Cコンパイラや関連ツールへの依存が減ることで、Goのビルドプロセスがよりシンプルで堅牢になります。

この変更は、Goランタイムが特定のアーキテクチャ（この場合はPowerPC 64-bit）上でどのように動作するかという低レベルな詳細に影響を与えますが、Go言語のユーザーが直接意識するようなAPIの変更ではありません。これは、Go言語の内部実装のクリーンアップと最適化の一環です。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、以下の4つのファイルに集約されます。

1.  **`src/runtime/defs_linux_power64.go` (新規追加)**:
    *   Linux/PowerPC 64-bit (ビッグエンディアン) アーキテクチャ向けのシステムコール定数とデータ構造のGo言語定義が含まれます。
    *   `_EINTR`, `_EAGAIN`, `_PROT_READ`, `_MAP_ANON`, `_SA_RESTART`, `_SIGHUP` などの定数が `const` ブロックで定義されています。
    *   `timespec`, `timeval`, `sigactiont`, `siginfo`, `itimerval`, `epollevent`, `ptregs`, `sigaltstackt`, `sigcontext`, `ucontext` などの構造体が `type struct` で定義されています。

2.  **`src/runtime/defs_linux_power64.h` (削除)**:
    *   上記 `defs_linux_power64.go` に対応するC言語のヘッダーファイルです。Go言語への移行に伴い削除されました。

3.  **`src/runtime/defs_linux_power64le.go` (新規追加)**:
    *   Linux/PowerPC 64-bit (リトルエンディアン) アーキテクチャ向けのシステムコール定数とデータ構造のGo言語定義が含まれます。
    *   内容は `defs_linux_power64.go` とほぼ同じですが、リトルエンディアン環境に特化した定義が含まれる可能性があります（このコミットのdiffでは同一内容に見えますが、将来的な差異やアーキテクチャ固有の考慮事項があるため、別ファイルとして管理されています）。

4.  **`src/runtime/defs_linux_power64le.h` (削除)**:
    *   上記 `defs_linux_power64le.go` に対応するC言語のヘッダーファイルです。Go言語への移行に伴い削除されました。

これらの変更により、GoランタイムはPowerPC 64-bit環境でのOSとのインターフェースを、C言語のヘッダーファイルではなくGo言語のソースコードを通じて管理するようになります。

## コアとなるコードの解説

新規追加された `defs_linux_power64.go` (および `defs_linux_power64le.go`) の内容は、主に以下の2つのセクションに分けられます。

### 1. 定数定義

```go
package runtime

const (
	_EINTR  = 0x4
	_EAGAIN = 0xb
	_ENOMEM = 0xc

	_PROT_NONE  = 0x0
	_PROT_READ  = 0x1
	_PROT_WRITE = 0x2
	_PROT_EXEC  = 0x4

	_MAP_ANON    = 0x20
	_MAP_PRIVATE = 0x2
	_MAP_FIXED   = 0x10

	_MADV_DONTNEED = 0x4

	_SA_RESTART = 0x10000000
	_SA_ONSTACK = 0x8000000
	_SA_SIGINFO = 0x4

	// ... (その他のシグナル定数、FPE、BUS、SEGV、ITIMER、EPOLL関連の定数) ...

	_O_RDONLY    = 0x0
	_O_CLOEXEC   = 0x80000
	_SA_RESTORER = 0
)
```

このセクションでは、Linuxシステムコールで使用される様々な定数がGo言語の `const` ブロックとして定義されています。これらの定数は、C言語のヘッダーファイルで `enum` や `#define` として定義されていたものに対応します。Go言語では、これらの定数にアンダースコア (`_`) プレフィックスを付けることで、Goランタイム内部での使用を示す慣習があります。値は16進数で直接指定されており、これは対応するC言語の定数値と一致します。

### 2. 構造体定義

```go
type timespec struct {
	tv_sec  int64
	tv_nsec int64
}

type timeval struct {
	tv_sec  int64
	tv_usec int64
}

type sigactiont struct {
	sa_handler  uintptr
	sa_flags    uint64
	sa_restorer uintptr
	sa_mask     uint64
}

type siginfo struct {
	si_signo  int32
	si_errno  int32
	si_code   int32
	pad_cgo_0 [4]byte // Cgoによって挿入されたパディング
	_sifields [112]byte
}

// ... (その他の itimerval, epollevent, ptregs, vreg, sigaltstackt, sigcontext, ucontext 構造体) ...

type ptregs struct {
	gpr       [32]uint64
	nip       uint64
	msr       uint64
	orig_gpr3 uint64
	ctr       uint64
	link      uint64
	xer       uint64
	ccr       uint64
	softe     uint64
	trap      uint64
	dar       uint64
	dsisr     uint64
	result    uint64
}

type sigcontext struct {
	_unused     [4]uint64
	signal      int32
	_pad0       int32
	handler     uint64
	oldmask     uint64
	regs        *ptregs
	gp_regs     [48]uint64
	fp_regs     [33]float64
	v_regs      *vreg
	vmx_reserve [101]int64
}

type ucontext struct {
	uc_flags    uint64
	uc_link     *ucontext
	uc_stack    sigaltstackt
	uc_sigmask  uint64
	__unused    [15]uint64
	uc_mcontext sigcontext
}
```

このセクションでは、LinuxカーネルAPIで使用されるC言語の構造体に対応するGo言語の構造体が定義されています。Go言語の構造体のフィールド名と型は、対応するC言語の構造体とメモリレイアウトが一致するように慎重にマッピングされています。

*   **型マッピング**: C言語の `int`, `long`, `unsigned long`, `void*` などは、Go言語の `int32`, `int64`, `uint32`, `uint64`, `uintptr`, `*byte` などに変換されています。
*   **パディング**: C言語の構造体では、アライメント要件を満たすためにコンパイラが自動的にパディングバイトを挿入することがあります。Go言語の構造体でも、`pad_cgo_0 [4]byte` のように明示的にパディングバイトを挿入することで、C言語の構造体とのメモリレイアウトの互換性を確保しています。これは、Goランタイムがシステムコールを呼び出す際に、C言語のAPIが期待するメモリレイアウトでデータを渡すために不可欠です。
*   **ポインタ型**: C言語のポインタ（例: `void*`, `struct Ptregs*`）は、Go言語の `uintptr` や対応する構造体へのポインタ（例: `*ptregs`）に変換されています。

これらのGo言語の定義は、GoランタイムがPowerPC 64-bit環境でLinuxカーネルと直接対話するための「契約」のようなものです。これにより、GoランタイムはC言語のコードを介さずに、OSの低レベルな機能にアクセスできるようになります。

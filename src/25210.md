# [インデックス 25210] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) において、ELF形式の共有ライブラリを生成する際に `-Wl,-z,nodelete` フラグを渡すように変更するものです。これにより、生成されたGo共有ライブラリが動的リンカによってメモリからアンロードされることを防ぎます。

## コミット

```
commit bd7de94d7fe8a0ba7742e90b1d6a09baa468bb58
Author: Ian Lance Taylor <iant@golang.org>
Date:   Thu Oct 8 10:22:50 2015 -0700

    cmd/link: pass -Wl,-z,nodelete when creating an ELF shared library
    
    Go shared libraries do not support dlclose, and there is no likelihood
    that they will suppose dlclose in the future.  Set the DF_1_NODELETE
    flag to tell the dynamic linker to not attempt to remove them from
    memory.  This makes the shared library act as though every call to
    dlopen passed the RTLD_NODELETE flag.
```

## 元コミット内容

Goのリンカ (`cmd/link`) がELF形式の共有ライブラリを作成する際、`-Wl,-z,nodelete` オプションを渡すように変更します。

Goの共有ライブラリは `dlclose` をサポートしておらず、将来的にサポートする可能性もありません。この変更は、動的リンカに対して共有ライブラリをメモリから削除しようとしないよう指示するために `DF_1_NODELETE` フラグを設定します。これにより、`dlopen` のすべての呼び出しが `RTLD_NODELETE` フラグを渡されたかのように共有ライブラリが動作します。

この変更は、以下のGoイシューを修正または更新します。
- Fixes #12582
- Update #11100
- Update #12873

## 変更の背景

この変更の背景には、Go言語のランタイムが共有ライブラリのアンロード（`dlclose`）をサポートしていないという根本的な設計上の決定があります。

一般的なC/C++などの言語で作成された共有ライブラリは、`dlopen` 関数でロードされ、`dlclose` 関数でアンロードされることが可能です。これにより、アプリケーションは必要に応じてライブラリを動的にロード・アンロードし、メモリリソースを効率的に管理できます。

しかし、Goのランタイムはガベージコレクション（GC）やスケジューラなど、独自の複雑な内部状態を持っています。共有ライブラリとしてロードされたGoコードがアンロードされると、これらのランタイムの状態が適切にクリーンアップされない可能性があり、メモリリークやクラッシュなどの深刻な問題を引き起こす可能性があります。Goの設計思想として、このような複雑な状態管理を `dlclose` のような外部からのアンロードメカニズムと整合させることは非常に困難であり、現在のところサポートする予定はありません。

このコミットは、Goの共有ライブラリが `dlclose` をサポートしないという事実を、OSの動的リンカに対して明示的に伝えることで、潜在的な問題を回避しようとするものです。具体的には、`dlclose` が呼び出されても何も行われないように、共有ライブラリに `DF_1_NODELETE` フラグを設定します。これにより、Goの共有ライブラリを使用するアプリケーションが誤って `dlclose` を呼び出しても、予期せぬ動作が発生するのを防ぎます。

コミットメッセージに記載されているイシュー番号（#12582, #11100, #12873）は、おそらくGoの共有ライブラリと `dlclose` の相互作用に関する問題報告や議論に関連していると考えられます。これらのイシューは、Goの共有ライブラリがアンロードされることによって発生する問題や、その挙動に関する混乱を解決するために、この変更が導入されたことを示唆しています。

## 前提知識の解説

### ELF (Executable and Linkable Format)
ELFは、Unix系OS（Linuxなど）で実行可能ファイル、オブジェクトファイル、共有ライブラリの標準的なファイル形式です。プログラムのコード、データ、シンボル情報などがこの形式で格納されます。

### 動的リンカ (Dynamic Linker)
動的リンカ（またはダイナミックローダー）は、プログラムの実行時に共有ライブラリをメモリにロードし、プログラム内の未解決のシンボル（関数や変数など）を共有ライブラリ内の対応するシンボルに解決する役割を担います。Linuxでは通常 `ld.so` がこれに該当します。

### 共有ライブラリ (Shared Library)
共有ライブラリ（またはダイナミックリンクライブラリ、DLL）は、複数のプログラムで共有されるコードとデータの集まりです。これにより、ディスクスペースの節約やメモリ使用量の削減、プログラムのモジュール化が可能になります。

### `dlopen()`
`dlopen()` は、プログラムの実行中に共有ライブラリを動的にロードするためのC言語の標準ライブラリ関数です。成功すると、ロードされたライブラリへのハンドルを返します。

### `dlclose()`
`dlclose()` は、`dlopen()` でロードされた共有ライブラリをメモリからアンロードするためのC言語の標準ライブラリ関数です。これにより、ライブラリが占有していたリソースが解放されます。

### `RTLD_NODELETE` フラグ
`dlopen()` 関数に渡すことができるフラグの一つです。このフラグを指定してライブラリをロードすると、そのライブラリは `dlclose()` が呼び出されてもメモリからアンロードされなくなります。これは、ライブラリがアンロードされると問題が発生する可能性がある場合や、ライブラリが提供するリソースがプログラムのライフサイクル全体で必要とされる場合に有用です。

### `DF_1_NODELETE` フラグ
ELF形式の共有ライブラリの動的セクション（`.dynamic`）に設定されるフラグの一つです。このフラグが設定されている共有ライブラリは、動的リンカによって `dlclose()` されてもメモリからアンロードされません。これは、ライブラリ自体が `RTLD_NODELETE` フラグが指定されたかのように振る舞うことを動的リンカに指示するものです。

### `cmd/link`
Go言語のツールチェーンの一部であるリンカです。Goのソースコードをコンパイルして生成されたオブジェクトファイルを結合し、実行可能ファイルや共有ライブラリを生成する役割を担います。

### `-Wl,option`
GCCやClangなどのコンパイラで、リンカに直接オプションを渡すための構文です。`-Wl,` の後に続くオプションは、リンカにそのまま渡されます。
- `-z,nodelete`: リンカオプションの一つで、共有ライブラリに `DF_1_NODELETE` フラグを設定するよう指示します。

## 技術的詳細

このコミットの核心は、Goの共有ライブラリが `dlclose` をサポートしないというGoランタイムの特性を、OSの動的リンカに正しく伝える点にあります。

Goの共有ライブラリは、Goランタイムの複雑な状態（ガベージコレクタ、ゴルーチン、スケジューラなど）を内部に持っています。これらの状態は、ライブラリがアンロードされる際に安全にクリーンアップされることを保証するのが非常に困難です。もし `dlclose` が実行され、Goの共有ライブラリがメモリから強制的にアンロードされてしまうと、Goランタイムが管理していたリソースが解放されずに残り、メモリリークや、アンロードされたライブラリ内のコードへの不正なアクセスによるクラッシュなど、深刻な問題を引き起こす可能性があります。

この問題を回避するため、コミットはGoのリンカ (`cmd/link`) がELF形式の共有ライブラリを生成する際に、リンカオプションとして `-Wl,-z,nodelete` を追加します。

- `-Wl,`: これはコンパイラ（この場合はGoのツールチェーンが内部的に呼び出すリンカ）に対して、続くオプションを直接リンカに渡すことを指示します。
- `-z,nodelete`: これはGNUリンカ（`ld`）のオプションであり、生成される共有ライブラリのELFヘッダ内の動的セクションに `DF_1_NODELETE` フラグを設定するよう指示します。

`DF_1_NODELETE` フラグが設定された共有ライブラリは、動的リンカによって「アンロード不可」としてマークされます。これにより、そのライブラリに対して `dlclose()` が呼び出されても、動的リンカは実際にライブラリをメモリからアンロードする処理を行いません。結果として、Goの共有ライブラリは、あたかも `dlopen()` 時に常に `RTLD_NODELETE` フラグが指定されたかのように振る舞うことになります。

この変更により、Goの共有ライブラリを使用する外部プログラムが、Goランタイムの特性を意識せずに `dlclose()` を呼び出してしまった場合でも、Goランタイムの整合性が保たれ、システムの安定性が向上します。これは、Goの共有ライブラリをC/C++などの他の言語で書かれたアプリケーションに組み込む際に特に重要となります。

変更は `src/cmd/link/internal/ld/lib.go` ファイルの `hostlink()` 関数内で行われています。

```go
		argv = append(argv, "-shared")
```

```go
		// Pass -z nodelete to mark the shared library as
		// non-closeable: a dlclose will do nothing.
		argv = append(argv, "-shared", "-Wl,-z,nodelete")
```

## コアとなるコードの解説

このコード変更は、Goのリンカが外部リンカ（通常はGCCやClangが内部的に使用するGNUリンカ `ld`）を呼び出す際に渡す引数リスト (`argv`) に、追加のオプションを追加しています。

1.  `HEADTYPE == obj.Hdarwin` の条件分岐は、ターゲットOSがmacOSであるかどうかを判定しています。macOSでは共有ライブラリの形式がELFとは異なるため、この変更はELF形式を使用するOS（主にLinux）にのみ適用されます。
2.  `else` ブロックに入ると、ターゲットがELF形式のシステムであることが確定します。
3.  既存の `-Wl,-Bsymbolic` や `-Wl,-z,relro` といったリンカオプションに加えて、新たに `-Wl,-z,nodelete` が追加されています。
4.  `-shared` オプションは、出力が共有ライブラリであることをリンカに指示するものです。
5.  追加された `-Wl,-z,nodelete` は、前述の通り、生成される共有ライブラリのELFヘッダに `DF_1_NODELETE` フラグを設定するようリンカに指示します。これにより、このGo共有ライブラリは `dlclose` されてもメモリからアンロードされなくなります。

この変更は、Goの共有ライブラリが持つランタイムの特性と、OSの動的リンカの挙動との間の不整合を解消し、Go共有ライブラリの安定性と信頼性を向上させるための重要な修正です。

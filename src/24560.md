# [インデックス 24560] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）メカニズムにおける特定の不具合を修正するものです。具体的には、以前のコミットで導入されたヒープトリガーの再チェックが、定期的なGCの開始を妨げていた問題を解決します。

## コミット

```
commit d57f03730265c4677ab2ec1ad74cf8cbf592f798
Author: Austin Clements <austin@google.com>
Date:   Wed Aug 5 11:07:47 2015 -0400

    runtime: don't recheck heap trigger for periodic GC
    
    88e945f introduced a non-speculative double check of the heap trigger
    before actually starting a concurrent GC. This was necessary to fix a
    race for heap-triggered GC, but broke sysmon-triggered periodic GC,
    since the heap check will of course fail for periodically triggered
    GC.
    
    Fix this by telling startGC whether or not this GC was triggered by
    heap size or a timer and only doing the heap size double check for GCs
    triggered by heap size.
    
    Fixes #12026.
    
    Change-Id: I7c3f6ec364545c36d619f2b4b3bf3b758e3bcbd6
    Reviewed-on: https://go-review.googlesource.com/13168
    Reviewed-by: Russ Cox <rsc@golang.org>
```

## 元コミット内容

このコミットは、`startGC` 関数に `forceTrigger` という新しいブール型引数を導入し、GCがヒープサイズによってトリガーされたのか、それともタイマー（定期GC）によってトリガーされたのかを区別するように変更しています。これにより、ヒープサイズによるGCの場合にのみヒープトリガーの再チェックが行われるようになり、定期GCが不当にスキップされる問題を解決しています。

## 変更の背景

Goランタイムのガベージコレクションは、プログラムのメモリ管理において重要な役割を果たします。GCは、ヒープの使用量がある閾値を超えた場合（ヒープトリガーGC）や、一定時間ごとに実行される場合（定期GC）など、様々な要因でトリガーされます。

以前のコミット `88e945f` では、並行GCを開始する前にヒープトリガーの非投機的な再チェックが導入されました。これは、ヒープトリガーGCにおける競合状態を修正するために必要でした。しかし、この変更は `sysmon`（システムモニター）によってトリガーされる定期GCに問題を引き起こしました。定期GCはヒープサイズに関係なく実行されるため、ヒープチェックが常に失敗し、結果として定期GCが開始されないという不具合が発生しました。

このコミットは、この問題を解決するために導入されました。定期GCはヒープサイズをトリガーとしないため、ヒープサイズの再チェックは不要であり、むしろGCの開始を妨げる要因となっていました。

## 前提知識の解説

*   **Goのガベージコレクション (GC)**: Goは自動メモリ管理を採用しており、不要になったメモリ領域を自動的に解放するガベージコレクタを備えています。GoのGCは、主に並行（concurrent）GCとして動作し、アプリケーションの実行と並行してGC処理を進めることで、プログラムの一時停止（Stop-The-World: STW）時間を最小限に抑えるように設計されています。
*   **ヒープトリガーGC**: プログラムがメモリを割り当て続け、ヒープの使用量がある一定の閾値（GC目標ヒープサイズ）を超えた場合にトリガーされるGCです。この閾値は、前回のGC後のライブヒープサイズに基づいて動的に計算されます。
*   **定期GC (Periodic GC)**: `sysmon` ゴルーチンによって一定時間ごとにトリガーされるGCです。これは、たとえヒープ使用量がGC目標ヒープサイズに達していなくても、メモリを定期的にクリーンアップし、メモリリークの可能性を低減するために行われます。
*   **`sysmon` (システムモニター)**: Goランタイムの重要なバックグラウンドゴルーチンの一つです。`sysmon` は、スケジューラとは独立して動作し、以下のような様々なタスクを定期的に実行します。
    *   ネットワークポーラーの実行
    *   長時間実行されているゴルーチンのプリエンプション（横取り）
    *   デッドロックの検出
    *   そして、定期的なGCのトリガー
    `sysmon` は、時間ベースのトリガーやヒープサイズの変化を監視し、必要に応じて `forcegchelper` ゴルーチンを起動してGCを開始させます。
*   **`startGC` 関数**: Goランタイム内でGCサイクルを開始するための主要な関数です。この関数は、GCのモード（バックグラウンド、強制ブロックなど）を指定して呼び出されます。
*   **`shouldtriggergc()` 関数**: 現在のヒープの状態がGCをトリガーすべきかどうかを判断する関数です。主にヒープトリガーGCの条件をチェックします。

## 技術的詳細

このコミットの核心は、`startGC` 関数のシグネチャと内部ロジックの変更にあります。

1.  **`startGC` 関数のシグネチャ変更**:
    `func startGC(mode int)` から `func startGC(mode int, forceTrigger bool)` へと変更されました。
    `forceTrigger` 引数は、GCがヒープサイズに関係なく強制的に開始されるべきかどうかを示します。`true` の場合、GCはタイマーなどの外部要因によってトリガーされたと見なされ、ヒープサイズの再チェックはスキップされます。

2.  **`startGC` 内部の条件分岐の変更**:
    以前は `if !shouldtriggergc() { ... }` という条件でGCの開始を再チェックしていました。
    これが `if !(forceTrigger || shouldtriggergc()) { ... }` に変更されました。
    この変更により、以下の挙動が実現されます。
    *   `forceTrigger` が `true` の場合（例: `sysmon` による定期GC）：`forceTrigger || shouldtriggergc()` は常に `true` となり、`! (true)` は `false` となるため、GCは再チェックなしで開始されます。
    *   `forceTrigger` が `false` の場合（例: ヒープトリガーGC）：`shouldtriggergc()` の結果に基づいてGCの開始が再チェックされます。これにより、ヒープトリガーGCにおける競合状態の修正は維持されます。

3.  **`startGC` 呼び出し箇所の更新**:
    `src/runtime/malloc.go` の `mallocgc` 関数内では、ヒープトリガーGCの可能性があるため `startGC(gcBackgroundMode, false)` と呼び出されます。
    `src/runtime/mgc.go` の `GC()` 関数内では、明示的なGC呼び出しであるため `startGC(gcForceBlockMode, false)` と呼び出されます。
    `src/runtime/mheap.go` の `runtime_debug_freeOSMemory` 関数内でも `startGC(gcForceBlockMode, false)` と呼び出されます。
    `src/runtime/proc.go` の `forcegchelper` 関数内では、`sysmon` によってトリガーされる定期GCであるため `startGC(gcBackgroundMode, true)` と呼び出されます。

この変更により、ヒープトリガーGCの正確性を保ちつつ、定期GCが意図通りに実行されるようになります。

## コアとなるコードの解説

このコミットの主要な変更は、`src/runtime/mgc.go` 内の `startGC` 関数とその呼び出し箇所に集中しています。

1.  **`startGC` 関数の定義変更**:
    `func startGC(mode int)` が `func startGC(mode int, forceTrigger bool)` に変更されました。
    新しい引数 `forceTrigger` は、GCがヒープサイズに関わらず強制的に開始されるべきかを示すフラグです。このフラグが `true` の場合、GCはタイマーなどの外部要因によってトリガーされたと見なされます。

2.  **GCトリガー条件の変更**:
    `startGC` 関数内でGCを開始する前の再チェックロジックが変更されました。
    変更前: `if !shouldtriggergc() { ... }`
    変更後: `if !(forceTrigger || shouldtriggergc()) { ... }`
    この変更により、`forceTrigger` が `true` であれば `shouldtriggergc()` の結果に関わらず条件式 `(forceTrigger || shouldtriggergc())` は `true` となり、その否定 `!(...)` は `false` となるため、GCはスキップされずに続行されます。これは、定期GCのようにヒープサイズとは無関係にGCを開始したい場合に重要です。
    一方、`forceTrigger` が `false` の場合、条件式は `!shouldtriggergc()` と同等になり、ヒープトリガーGCの競合状態を修正するための再チェックが引き続き行われます。

3.  **`startGC` の呼び出し箇所の調整**:
    *   `src/runtime/malloc.go` の `mallocgc` 関数: メモリ割り当て時にヒープトリガーGCの可能性をチェックする箇所です。ここではヒープサイズがGCのトリガーであるため、`forceTrigger` は `false` に設定されます (`startGC(gcBackgroundMode, false)`)。
    *   `src/runtime/mgc.go` の `GC()` 関数: ユーザーが明示的にGCを要求する関数です。この場合も、ヒープサイズによる再チェックは不要ではないため、`forceTrigger` は `false` に設定されます (`startGC(gcForceBlockMode, false)`)。
    *   `src/runtime/mheap.go` の `runtime_debug_freeOSMemory` 関数: OSへのメモリ解放をデバッグ目的で行う関数です。ここでも `forceTrigger` は `false` に設定されます (`startGC(gcForceBlockMode, false)`)。
    *   `src/runtime/proc.go` の `forcegchelper` 関数: `sysmon` ゴルーチンによって定期的に呼び出され、定期GCをトリガーする役割を担います。ここではヒープサイズに関わらずGCを開始したいので、`forceTrigger` は `true` に設定されます (`startGC(gcBackgroundMode, true)`)。

これらの変更により、GoランタイムはヒープトリガーGCと定期GCの両方を適切に処理できるようになり、GCの信頼性と効率性が向上しました。

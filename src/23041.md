# [インデックス 23041] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）プロセスにおけるプリエンプション（横取り）の扱いを変更するものです。特に、並行GCフェーズ中のプリエンプションをより一般的に許可することで、GCのスケジューリング動作とリソース利用効率を改善することを目的としています。

## 元コミット内容

```
runtime: generally allow preemption during concurrent GC phases

Currently, the entire GC process runs with g.m.preemptoff set. In the
concurrent phases, the parts that actually need preemption disabled
are run on a system stack and there's no overall need to stay on the
same M or P during the concurrent phases. Hence, move the setting of
g.m.preemptoff to when we start mark termination, at which point we
really do need preemption disabled.

This dramatically changes the scheduling behavior of the concurrent
mark phase. Currently, since this is non-preemptible, concurrent mark
gets one dedicated P (so 1/GOMAXPROCS utilization). With this change,
the GC goroutine is scheduled like any other goroutine during
concurrent mark, so it gets 1/<runnable goroutines> utilization.

You might think it's not even necessary to set g.m.preemptoff at that
point since the world is stopped, but stackalloc/stackfree use this as
a signal that the per-P pools are not safe to access without
synchronization.

Change-Id: I08aebe8179a7d304650fb8449ff36262b3771099
Reviewed-on: https://go-review.googlesource.com/8839
Reviewed-by: Rick Hudson <rlh@golang.org>
```

## 変更の背景

Goのガベージコレクション（GC）は、アプリケーションの実行と並行して動作する「並行GC」を採用しています。しかし、このコミット以前は、GCプロセス全体が `g.m.preemptoff` フラグを設定した状態で実行されていました。`g.m.preemptoff` が設定されている間は、Goランタイムによるゴルーチンのプリエンプション（実行中のゴルーチンを一時停止し、別のゴルーチンにCPUを割り当てること）が無効になります。

これにより、並行GCのフェーズ（特に並行マークフェーズ）においてもプリエンプションが抑制され、GCゴルーチンが特定の論理プロセッサ（P）を専有する形になっていました。コミットメッセージにあるように、「並行マークは1つの専用Pを獲得し、GOMAXPROCSの1/GOMAXPROCSの利用率になる」という状況でした。これは、GCが実行されている間、他のアプリケーションゴルーチンがそのPを利用できず、CPUリソースの利用効率が低下する可能性を意味していました。

コミットの目的は、並行GCフェーズ中に常にプリエンプションを無効にする必要はないという認識に基づいています。実際にプリエンプションを無効にする必要があるのは、GCの特定のクリティカルな部分（例えば、システムスタック上で実行される部分）に限られるため、それ以外の並行フェーズではプリエンプションを許可することで、GCゴルーチンが他の通常のゴルーチンと同様にスケジューリングされるようにし、CPUリソースの利用効率を向上させることにあります。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、不要になったメモリを自動的に解放する仕組みです。Go 1.5以降（このコミットはGo 1.5の開発中に作成されたものと推測されます）、GoのGCは主に「並行マーク＆スイープ」方式を採用しています。

*   **マークフェーズ (Mark Phase)**: どのオブジェクトが到達可能（使用中）で、どのオブジェクトが到達不可能（不要）かを識別します。
    *   **並行マーク (Concurrent Mark)**: アプリケーションの実行と並行して、バックグラウンドで到達可能なオブジェクトをマークします。このフェーズはCPUリソースを消費しますが、アプリケーションの実行を完全に停止させるわけではありません。
    *   **マーク終了 (Mark Termination)**: 並行マークフェーズの最後に、GCがマーク作業を完了させるために、一時的にすべてのゴルーチンを停止させる「Stop-The-World (STW)」フェーズです。このSTWフェーズは非常に短く保たれるように設計されています。
*   **スイープフェーズ (Sweep Phase)**: マークされなかった（不要と判断された）オブジェクトが占めていたメモリを解放し、再利用可能にします。このフェーズも並行して行われます。

### Goroutine、M、P

Goランタイムのスケジューラは、以下の3つの主要な要素で構成されます。

*   **Goroutine (G)**: Goプログラムにおける軽量な実行単位です。数百万個のゴルーチンを同時に実行できます。
*   **論理プロセッサ (P)**: OSスレッド（M）がゴルーチンを実行するために必要なコンテキスト（スケジューラキュー、メモリ割り当てキャッシュなど）を提供します。`GOMAXPROCS`環境変数によってPの数が制御され、通常はCPUコア数に設定されます。
*   **OSスレッド (M)**: 実際のOSスレッドであり、Pにアタッチされてゴルーチンを実行します。MはOSによってプリエンプションされます。

Goスケジューラは、GをPに、PをMに割り当てることで、並行実行を実現します。

### プリエンプション (Preemption)

プリエンプションとは、実行中のタスク（この場合はゴルーチン）を、そのタスクが自発的にCPUを解放するのを待たずに、ランタイムやOSが強制的に中断し、別のタスクにCPUを割り当てる仕組みです。

Goランタイムでは、協調的プリエンプションと非同期プリエンプション（Go 1.14以降）の両方を利用して、ゴルーチンがCPUを独占しすぎないようにしています。

*   **`g.m.preemptoff`**: これはGoランタイム内部のフラグで、現在のM（OSスレッド）上で実行されているゴルーチンがプリエンプションされるのを一時的に防ぐために使用されます。このフラグが設定されている間は、ランタイムは現在のゴルーチンを中断して別のゴルーチンに切り替えることを避けます。これは、アトミックな操作や、データ構造の一貫性を保つ必要があるクリティカルセクションで利用されます。

### システムスタック

Goランタイムは、通常のゴルーチンスタックとは別に、ランタイム内部の特定の処理（例えば、スケジューラやGCの低レベルな操作）を実行するための「システムスタック」を持っています。システムスタック上で実行されるコードは、通常のゴルーチンコードとは異なる制約や要件を持つことがあります。

## 技術的詳細

このコミットの核心は、`g.m.preemptoff` フラグの設定タイミングを変更することにあります。

変更前は、GCプロセス全体が開始されるとすぐに `g.m.preemptoff` が設定され、GCが完了するまで解除されませんでした。これは、並行マークフェーズのような、必ずしもプリエンプションを無効にする必要がない期間でも、GCゴルーチンがPを専有してしまう原因となっていました。

コミットメッセージによると、並行GCフェーズにおいて実際にプリエンプションを無効にする必要があるのは、システムスタック上で実行されるような、ごく一部のクリティカルな操作に限られます。それ以外の並行フェーズでは、GCゴルーチンは他の通常のゴルーチンと同様にスケジューリングされても問題ありません。

この変更により、`g.m.preemptoff` の設定は、GCの「マーク終了 (mark termination)」フェーズが開始される直前に移動されました。マーク終了フェーズは、すべてのゴルーチンを一時停止させるSTWフェーズであり、この期間中はメモリ割り当てやスタック操作に関するクリティカルな処理が行われます。コミットメッセージにあるように、`stackalloc`/`stackfree` のような操作は、`g.m.preemptoff` が設定されていることを「Pごとのプールが同期なしで安全にアクセスできない」というシグナルとして利用します。つまり、STW中であっても、これらの操作の整合性を保つためにプリエンプションを無効にする必要があるのです。

結果として、この変更は並行マークフェーズのスケジューリング動作を劇的に変化させます。

*   **変更前**: 並行マークフェーズは非プリエンプティブであり、GCゴルーチンは1つのPを専有していました。これにより、`GOMAXPROCS`がNの場合、GCはCPUリソースの1/Nしか利用できませんでした（他のPは他のゴルーチンに利用されますが、GC自体は1つのPに縛られる）。
*   **変更後**: 並行マークフェーズ中、GCゴルーチンは他の通常のゴルーチンと同様にスケジューリングされます。これにより、GCゴルーチンは「実行可能なゴルーチンの数」に応じてCPUリソースを共有するようになります。例えば、実行可能なゴルーチンが10個あれば、GCゴルーチンはそのうちの1/10のCPU時間を利用する可能性があります。これは、GCがより多くのPを利用できるようになり、並行マークフェーズの進行が速くなる可能性を示唆しています。

この変更は、GoランタイムのスケジューラがGCゴルーチンをより効率的に扱い、全体的なスループットとリソース利用率を向上させるための重要なステップです。

## コアとなるコードの解説

### 変更前

変更前のコードでは、`gc` 関数が呼び出されるとすぐに、現在のM（OSスレッド）を取得し（`acquirem()`）、そのMの `preemptoff` フラグを `"gcing"` に設定していました。これは、GCプロセス全体がプリエンプションを無効にした状態で実行されることを意味していました。その後、Mを解放（`releasem(mp)`）していますが、`preemptoff` フラグはMに紐付けられているため、このMがGCゴルーチンを実行している間はプリエンプションが無効のままでした。

### 変更後

変更後のコードでは、`gc` 関数の冒頭から `preemptoff` の設定が削除されました。これにより、GCの初期フェーズ（例えば、並行マークフェーズ）では、GCゴルーチンは通常のゴルーチンと同様にプリエンプションの対象となります。

`mp.preemptoff = "gcing"` の設定は、`mark termination` フェーズが開始される直前（`startTime := nanotime()` の後）に移動されました。この時点で `acquirem()` を呼び出して現在のMを取得し、そのMの `preemptoff` フラグを設定しています。

この変更のポイントは以下の通りです。

*   **並行マークフェーズの改善**: 並行マークフェーズ中、GCゴルーチンはもはやPを専有せず、他のゴルーチンとCPUリソースを共有するようになります。これにより、GCの実行がアプリケーションの他の部分の実行を妨げにくくなり、全体的なスループットが向上する可能性があります。
*   **STWフェーズの保護**: `mark termination` フェーズはSTW（Stop-The-World）フェーズであり、この期間中はすべてのアプリケーションゴルーチンが停止します。しかし、このフェーズでは `stackalloc`/`stackfree` のような、Pごとの内部プールにアクセスするクリティカルな操作が行われます。これらの操作は、同期なしで安全に実行されるために `preemptoff` フラグが設定されていることを前提としています。したがって、このSTWフェーズ中に `preemptoff` を設定することで、これらのクリティカルな操作の整合性が保証されます。

このコミットは、GoランタイムがGCの各フェーズの特性をより細かく考慮し、必要な場合にのみプリエンプションを無効にすることで、GCの効率とアプリケーションのパフォーマンスのバランスを最適化しようとするものです。

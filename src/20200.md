## 変更の背景

このコミットの主な背景は、`nacl/arm` (Native Client on ARMアーキテクチャ) 環境でのGoランタイムのビルドが、`TestMemStats` テストで失敗していた問題にあります。`TestMemStats` はGoランタイムのメモリ統計 (`MemStats`) が期待通りの値を持つことを検証するテストですが、特定の環境、特に `nacl/arm` のような制約のある環境では、メモリの割り当てや解放の挙動が通常のデスクトップ/サーバー環境とは異なる場合があります。

具体的には、`MemStats` の `HeapIdle` フィールドがゼロになることがあり、これがテストの失敗を引き起こしていました。`HeapIdle` はアイドル状態（使用されていないがOSに解放されていない）のヒープメモリの量を表しますが、環境によってはこの値が常にゼロになる、あるいは非常に小さい値になることがあり、テストがこれを「異常」と判断して失敗していました。このコミットは、この特定の環境での挙動を許容するようにテストの条件を緩和することで、ビルドの成功を目指しています。

## 前提知識の解説

### Goランタイムのメモリ管理と `MemStats`

Go言語は独自のランタイムを持ち、ガベージコレクション (GC) を含むメモリ管理を自動的に行います。`runtime` パッケージは、このメモリ管理に関する様々な統計情報を提供する `MemStats` 構造体を提供しています。`MemStats` は、Goプログラムが使用しているメモリの状態を詳細に把握するために利用されます。

`MemStats` 構造体には、以下のような重要なフィールドが含まれます。

*   **`Alloc`**: 現在割り当てられているオブジェクトの合計バイト数。
*   **`TotalAlloc`**: 起動以降に割り当てられたオブジェクトの合計バイト数（解放されたものも含む）。
*   **`Sys`**: ランタイムがOSから取得したメモリの合計バイト数。
*   **`HeapAlloc`**: ヒープに割り当てられているオブジェクトの合計バイト数。
*   **`HeapSys`**: ヒープのためにOSから取得したメモリの合計バイト数。
*   **`HeapIdle`**: ヒープ内でアイドル状態（使用されていないがOSに解放されていない）のメモリのバイト数。
*   **`HeapInuse`**: ヒープ内で使用中のメモリのバイト数。
*   **`HeapReleased`**: ヒープ内でOSに解放されたメモリのバイト数。
*   **`StackInuse`**: スタックで使用中のメモリのバイト数。
*   **`StackSys`**: スタックのためにOSから取得したメモリのバイト数。
*   **`NumGC`**: 実行されたGCの回数。

これらの統計は、`runtime.ReadMemStats` 関数を呼び出すことで取得できます。

### `HeapIdle` と `HeapReleased`

*   **`HeapIdle`**: Goランタイムは、不要になったヒープメモリをすぐにOSに返却するとは限りません。将来の割り当てのために、一部のメモリをアイドル状態として保持しておくことがあります。`HeapIdle` はこのアイドル状態のメモリの量を表します。このメモリはGoランタイムが管理していますが、現在オブジェクトには使用されていません。
*   **`HeapReleased`**: GoランタイムがOSに明示的に返却したメモリの量です。これは、ランタイムがメモリを保持しておく必要がないと判断した場合に行われます。

通常、`HeapIdle` の値はゼロではないことが期待されます。これは、Goランタイムがメモリを効率的に再利用するために、ある程度のアイドルメモリを保持しているためです。しかし、特定の環境や非常に小さなプログラムでは、メモリがすぐにOSに返却されるか、そもそもアイドル状態のメモリが発生しない場合があります。

### `nacl/arm`

`nacl/arm` は、Google Native Client (NaCl) のARMアーキテクチャ版を指します。Native Clientは、ウェブブラウザ内でネイティブコードを安全に実行するためのサンドボックス技術です。`nacl` 環境は、通常のOS環境とは異なるメモリ管理やシステムコールに関する制約を持つことが多く、これがGoランタイムの挙動に影響を与える可能性があります。特に、メモリの確保や解放の粒度、OSへのメモリ返却のタイミングなどが、一般的な環境とは異なる挙動を示すことがあります。

## 技術的詳細

`src/pkg/runtime/malloc_test.go` 内の `TestMemStats` 関数は、`runtime.ReadMemStats` を呼び出してメモリ統計を取得し、その値が期待される範囲内にあるか、または特定の条件を満たすかを検証します。

変更前のコードでは、`HeapIdle` の値がゼロでないことを必須条件としていました。

```go
if st.Alloc == 0 || st.TotalAlloc == 0 || st.Sys == 0 || st.Lookups == 0 ||
	st.Mallocs == 0 || st.Frees == 0 || st.HeapAlloc == 0 || st.HeapSys == 0 ||
	st.HeapIdle == 0 || st.HeapInuse == 0 || st.HeapObjects == 0 || st.StackInuse == 0 ||
	st.StackSys == 0 || st.MSpanInuse == 0 || st.MSpanSys == 0 || st.MCacheInuse == 0 ||
	st.MCacheSys == 0 || st.BuckHashSys == 0 || st.GCSys == 0 || st.OtherSys == 0 ||
	st.NextGC == 0 || st.NumGC == 0 {
	t.Fatalf("Bad stats value: %+v", *st)
}
```

この `if` 文は、`MemStats` のいずれかの重要なフィールドがゼロである場合にテストを失敗させるものです。コメントには「Everything except HeapReleased, because it indeed can be 0.」と書かれており、`HeapReleased` はゼロでも許容されることが示されていました。

しかし、`nacl/arm` 環境では `HeapIdle` もゼロになることがあったため、この条件がテストの失敗を引き起こしていました。このコミットでは、`HeapIdle` も `HeapReleased` と同様にゼロを許容するように変更されました。

さらに、このコミットでは `HeapIdle` と `HeapInuse` の合計が `HeapSys` と等しいことを検証する新しいアサーションが追加されました。これは、ヒープのためにOSから取得したメモリ (`HeapSys`) が、現在使用中のメモリ (`HeapInuse`) とアイドル状態のメモリ (`HeapIdle`) の合計と一致するという、メモリ管理の基本的な整合性を確認するためのものです。このアサーションは、`HeapIdle` がゼロであっても、他の統計との整合性が保たれていることを保証します。

    +	st.HeapInuse == 0 || st.HeapObjects == 0 || st.StackInuse == 0 ||
    ```
    元の `if` 文から `st.HeapIdle == 0` の条件が削除されました。これにより、`HeapIdle` がゼロであっても、他の条件が満たされていればテストは失敗しなくなります。これは `nacl/arm` ビルドでのテスト失敗を直接的に解決するための変更です。

3.  **新しい整合性チェックの追加**:
    ```diff
    +	if st.HeapIdle+st.HeapInuse != st.HeapSys {
    +		t.Fatalf("HeapIdle(%d) + HeapInuse(%d) should be equal to HeapSys(%d), but isn't.", st.HeapIdle, st.HeapInuse, st.HeapSys)
    +	}
    ```
    この新しい `if` 文は、`HeapIdle` と `HeapInuse` の合計が `HeapSys` と等しいことを検証します。
    *   `HeapSys`: GoランタイムがOSからヒープのために確保したメモリの総量。
    *   `HeapInuse`: その中で現在オブジェクトが使用しているメモリ量。
    *   `HeapIdle`: その中で現在オブジェクトには使用されていないが、Goランタイムが将来の割り当てのために保持しているメモリ量。

    この関係は常に成り立つべきメモリ管理の基本的な不変条件です。`HeapIdle` がゼロになることを許容する一方で、この新しいチェックを追加することで、メモリ統計の基本的な整合性が保たれていることを確認しています。これにより、`HeapIdle` がゼロであっても、それが異常な状態ではないことを保証し、テストの堅牢性を維持しています。

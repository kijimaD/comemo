# [インデックス 22046] ファイルの概要

このコミットは、Go言語の`net`および`syscall`パッケージにおける、BSD系OS（Darwin, Dragonfly, FreeBSD, NetBSD, OpenBSD）でのルーティングメッセージのパース処理の精度を向上させるものです。特に、FreeBSDのような複数のアーキテクチャをサポートするカーネル環境や、これまで適切に処理されていなかったルーティングメッセージ（ルート、インターフェースアドレス状態通知など）のパースに関する問題を解決します。

```
net, syscall: more accurate parsers for routing messages on BSD variants

This changes fixes two issues with regard to handling routing messages
as follows:
- Misparsing on platforms (such as FreeBSD) supporting multiple
  architectures in the same kernel (kern.supported_archs="amd64 i386")
- Misparsing with unimplemented messages such as route, interface
  address state notifications

To fix those issues, this change implements all the required socket
address parsers, adds a processor architecture identifying function to
FreeBSD and tests.
```

## 変更の背景

このコミットは、Go言語がBSD系OSのネットワークルーティング情報を扱う際に直面していた2つの主要な問題に対処するために導入されました。

1.  **マルチアーキテクチャカーネル環境でのパース誤り**: FreeBSDのような一部のBSD系OSでは、単一のカーネルが複数のプロセッサアーキテクチャ（例: `amd64`と`i386`）をサポートするように設定されている場合があります（`kern.supported_archs="amd64 i386"`）。このような環境では、カーネルが生成するルーティングメッセージ内のデータ構造のアライメントやサイズが、実行中のGoプログラムが想定するアーキテクチャと異なる可能性がありました。これにより、ルーティングメッセージのバイナリデータをGo側でパースする際に、データの読み取り位置がずれ、誤った情報が解釈されるという問題が発生していました。特に、`sockaddr`構造体のような可変長かつアライメントに依存するデータは、この問題の影響を受けやすかったです。

2.  **未実装メッセージタイプのパース誤り**: 既存のルーティングメッセージパーサーは、すべてのメッセージタイプやそのバリエーションを網羅していませんでした。特に、ルート情報やインターフェースアドレスの状態通知など、特定の種類のメッセージが適切にパースされず、Goプログラムが正確なネットワーク情報を取得できない、あるいは予期せぬエラーが発生するという問題がありました。これは、GoがOSから提供される低レベルなネットワーク情報を正確に解釈し、利用する上で大きな障害となっていました。

これらの問題は、GoプログラムがBSD系OS上でネットワーク設定を正確に取得・操作する能力に影響を与え、信頼性の低下を招いていました。このコミットは、これらの根本的なパース問題を解決し、Goのネットワーク機能の堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下の前提知識が役立ちます。

### 1. BSDルーティングメッセージと`AF_ROUTE`ソケット

BSD系OS（FreeBSD, NetBSD, OpenBSD, Darwin, Dragonfly BSDなど）では、カーネルのルーティングテーブルとユーザー空間のプロセスが通信するための特殊なメカニズムとして、**ルーティングソケット**が提供されています。これは通常、`AF_ROUTE`（または`PF_ROUTE`）アドレスファミリーを持つソケットを通じて行われます。ユーザー空間のルーティングデーモンやネットワーク管理ツールは、このソケットを使用してルーティングテーブルの操作（ルートの追加、削除、変更）や、ルーティングイベント（インターフェースの状態変化など）の通知を受け取ります。

ルーティングソケットを通じてやり取りされる情報は、特定のバイナリ形式の**ルーティングメッセージ**としてエンコードされます。

### 2. `rt_msghdr`構造体

ルーティングメッセージは、まず共通のヘッダである`struct rt_msghdr`（またはその派生形）から始まります。このヘッダには、メッセージの総バイト長（`rtm_msglen`）、メッセージのタイプ（`rtm_type`、例: `RTM_ADD`, `RTM_DELETE`, `RTM_IFINFO`など）、そして最も重要な**`rtm_addrs`ビットマスク**が含まれます。

`rtm_addrs`ビットマスクは、ヘッダの後に続く`sockaddr`構造体の種類と順序を示します。例えば、`RTA_DST`ビットがセットされていれば宛先アドレスの`sockaddr`が続くことを意味し、`RTA_GATEWAY`がセットされていればゲートウェイアドレスの`sockaddr`が続くことを意味します。このビットマスクの解釈が誤ると、後続の`sockaddr`データを正しくパースできません。

### 3. `sockaddr`構造体とその種類

`sockaddr`は、ソケットアドレスを表す汎用的な構造体です。ルーティングメッセージでは、様々な種類のアドレス情報がこの`sockaddr`の派生形として表現されます。

*   **`sockaddr_in` / `sockaddr_in6`**: IPv4およびIPv6アドレスを表します。`sa_family`フィールドがそれぞれ`AF_INET`または`AF_INET6`となります。
*   **`sockaddr_dl` (Datalink Socket Address)**: リンク層（データリンク層）のアドレス、例えばMACアドレスやインターフェース名などを表します。`sa_family`フィールドは`AF_LINK`となります。この構造体は、インターフェースのハードウェアアドレスや名前を取得する際に特に重要です。
*   **可変長とアライメント**: `sockaddr`構造体は可変長であり、その実際の長さは`sa_len`フィールドで示されます。また、複数の`sockaddr`構造体が連続して配置される場合、OSやアーキテクチャによっては特定のバイト境界（アライメント）に沿って配置される必要があります。このアライメントが正しく考慮されないと、次の`sockaddr`の開始位置がずれ、パースエラーにつながります。

### 4. Goの`syscall`パッケージとネットワークインターフェース

Go言語では、`syscall`パッケージがOSのシステムコールへの低レベルなアクセスを提供します。ネットワーク関連の機能、特にBSD系OSにおけるルーティングメッセージの処理は、この`syscall`パッケージを通じて行われます。`net`パッケージの一部機能も、内部的には`syscall`パッケージを利用してOS固有のネットワーク情報を取得しています。

### 5. マルチアーキテクチャカーネルとデータパース

FreeBSDのようなOSでは、`kern.supported_archs`という`sysctl`設定を通じて、カーネルが複数のCPUアーキテクチャ（例: `amd64`と`i386`）のバイナリを同時に実行できることを示す場合があります。これは、カーネル自体が特定のアーキテクチャでビルドされていても、異なるアーキテクチャのユーザーランドバイナリが動作することを可能にするものです。

しかし、ルーティングメッセージのようなカーネルからユーザーランドに渡されるバイナリデータは、カーネルがビルドされた際のアーキテクチャのデータ構造アライメント規則に従って生成されます。もしGoプログラムが、カーネルとは異なるアライメント規則を想定してデータをパースしようとすると、構造体のフィールドオフセットがずれ、データが誤って解釈されることになります。このコミットは、このアーキテクチャ間のアライメントの不一致を検出し、適切に処理するメカニズムを導入しています。

## 技術的詳細

このコミットの技術的な核心は、BSD系OSにおけるルーティングメッセージのバイナリパースロジックの堅牢化と正確性の向上にあります。

### 1. `rsaAlignOf`関数の強化

`src/syscall/route_bsd.go`内の`rsaAlignOf`関数は、`sockaddr`構造体の長さを適切にアライメントするためのバイト数を計算します。この関数は、Darwin (32-bitアライメント) やNetBSD (64-bitアライメント) の特殊な要件を既に考慮していましたが、このコミットではFreeBSDのマルチアーキテクチャカーネルのケースが追加されました。

```go
// Round the length of a raw sockaddr up to align it properly.
func rsaAlignOf(salen int) int {
	salign := sizeofPtr
	// ... (既存のDarwin, NetBSDのロジック) ...
	else if runtime.GOOS == "freebsd" {
		// In the case of kern.supported_archs="amd64 i386",
		// we need to know the underlying kernel's
		// architecture because the alignment for routing
		// facilities are set at the build time of the kernel.
		if freebsdConfArch == "amd64" {
			salign = 8
		}
	}
	// ...
}
```

FreeBSDの場合、`kern.conftxt`から取得したカーネルのビルドアーキテクチャ（`freebsdConfArch`）が`amd64`であれば、アライメントを8バイトに設定します。これにより、カーネルが`amd64`としてビルドされている場合に、Goプログラムが正しいアライメントでデータを読み取れるようになります。

### 2. 新しい`sockaddr`パース関数の導入

ルーティングメッセージ内の様々な`sockaddr`タイプを正確にパースするために、以下の新しいヘルパー関数が`src/syscall/route_bsd.go`に導入されました。

*   **`parseSockaddrLink(b []byte) (*SockaddrDatalink, error)`**:
    データリンク層の`sockaddr`（`AF_LINK`）をパースします。これは、インターフェースのMACアドレスや名前などの情報を抽出するために使用されます。以前は`anyToSockaddr`のような汎用関数で処理されていましたが、`sockaddr_dl`の内部構造（特に`Nlen`, `Alen`, `Slen`フィールド）を正確に解釈するために専用のパースロジックが必要でした。

*   **`parseLinkLayerAddr(b []byte) (*SockaddrDatalink, int, error)`**:
    `parseSockaddrLink`の内部で使われる、より低レベルなデータリンク層アドレスのパース関数です。BSDカーネルの慣習的な形式（Type, Nlen, Alen, Slenの各バイトとそれに続くデータ）を解釈します。

*   **`parseSockaddrInet(b []byte, family byte) (Sockaddr, error)`**:
    インターネットアドレス（IPv4: `AF_INET`, IPv6: `AF_INET6`）の`sockaddr`をパースします。これは、`RawSockaddrInet4`や`RawSockaddrInet6`のような生の構造体を、Goの`SockaddrInet4`や`SockaddrInet6`に変換します。

*   **`parseNetworkLayerAddr(b []byte, family byte) (Sockaddr, error)`**:
    ネットワーク層アドレス（IPアドレスなど）をパースするための関数です。これは、ルーティングメッセージ内でネットマスクやジェネリックマスクとして現れるアドレスのパースに使用されます。特に、長さフィールドがバイト単位で示され、アドレスプレフィックスが続くというBSDカーネルの慣習的な形式を扱います。

### 3. `RoutingMessage`インターフェースと`sockaddr()`メソッドの変更

`RoutingMessage`インターフェースの`sockaddr()`メソッドのシグネチャが変更され、エラーを返すようになりました (`[]Sockaddr` から `([]Sockaddr, error)`)。これにより、パース中に発生したエラーを適切に伝播できるようになり、より堅牢なエラーハンドリングが可能になりました。

```go
type RoutingMessage interface {
	sockaddr() ([]Sockaddr, error) // 変更前: sockaddr() []Sockaddr
}
```

これに伴い、`RouteMessage`, `InterfaceMessage`, `InterfaceAddrMessage`, `InterfaceMulticastAddrMessage`といった具体的なルーティングメッセージ構造体の`sockaddr()`メソッドの実装も更新され、新しいパース関数（`parseSockaddrLink`, `parseSockaddrInet`, `parseNetworkLayerAddr`）を利用して、より正確かつエラーを考慮した`sockaddr`の抽出が行われるようになりました。

特に、`RouteMessage.sockaddr()`では、`RTAX_DST`, `RTAX_GATEWAY`, `RTAX_NETMASK`, `RTAX_GENMASK`などの各アドレスタイプに対応する`sockaddr`を、その`Family`（`AF_LINK`, `AF_INET`, `AF_INET6`など）に基づいて適切にパースするロジックが導入されました。以前は`AF_UNSPEC`の`sockaddr`の扱いが曖昧でしたが、新しいロジックでは`family`引数を使って明示的にアドレスファミリーを指定できるようになりました。

### 4. FreeBSD固有のアーキテクチャ検出

`src/syscall/route_freebsd.go`の`init`関数に、FreeBSDカーネルのビルドアーキテクチャを検出するロジックが追加されました。

```go
func init() {
	freebsdVersion, _ = SysctlUint32("kern.osreldate")
	conf, _ := Sysctl("kern.conftxt") // kern.conftxtからカーネル設定を読み取る
	// ... confの内容をパースして "machine <arch>" 行からアーキテクチャを抽出 ...
	// freebsdConfArch に "amd64" や "i386" などが設定される
}
```

この`init`関数は、`kern.conftxt`という`sysctl`変数からカーネルのコンフィギュレーションテキストを読み取り、その中から`"machine <arch>"`という行を検索して、カーネルがビルドされたアーキテクチャ（例: `amd64`, `i386`）を`freebsdConfArch`変数に設定します。この情報が、前述の`rsaAlignOf`関数で利用され、FreeBSD環境での正確なアライメント計算を可能にします。

### 5. `net`パッケージの変更

`src/net/interface_bsd.go`, `src/net/interface_darwin.go`, `src/net/interface_freebsd.go`の各ファイルでは、`syscall.ParseRoutingSockaddr`の呼び出し元が変更され、エラーを適切に処理するようになりました。また、`newLink`, `newAddr`, `newMulticastAddr`といった関数内で、`sockaddr`のパースロジックがより明示的に`syscall.RTAX_IFP`, `syscall.RTAX_NETMASK`, `syscall.RTAX_IFA`といったインデックスを使って特定の`sockaddr`を抽出するように変更されました。これにより、ルーティングメッセージ内の`sockaddr`の順序に依存せず、`rtm_addrs`ビットマスクで示される正確な位置から必要な情報を取得できるようになりました。

### 6. テストの追加

`src/syscall/route_bsd_test.go`, `src/syscall/route_ifma_test.go`, `src/syscall/route_noifma_test.go`といった新しいテストファイルが追加されました。これらのテストは、`RouteRIB`関数がルーティング情報を正しく取得し、`ParseRoutingMessage`および`ParseRoutingSockaddr`が様々なルーティングメッセージタイプと`sockaddr`構造体を正確にパースできることを検証します。特に、ループバックインターフェースの検出や、ルーティングソケットの監視（root権限が必要）といったシナリオが含まれており、変更が意図通りに機能することを確認します。

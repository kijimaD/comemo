# [インデックス 26589] ファイルの概要

このコミットは、GoランタイムのSolarisオペレーティングシステム固有の実装ファイルである `src/runtime/os3_solaris.go` に関連するものです。このファイルは、GoプログラムがSolaris上でメモリ管理やシステムコールを適切に実行するための低レベルなインターフェースを提供します。具体的には、`mmap`（メモリマップ）システムコールのGoラッパーの実装が含まれています。

## コミット

このコミットは、Solarisにおける `mmap` システムコールの挙動を修正し、Goランタイムの `mem_bsd.go` が期待するエラー処理ロジックと整合させることを目的としています。具体的には、`mmap` が失敗した場合に、Goランタイムが `errno` の値を正しく取得し、それを `mmap` 関数の戻り値として返すように変更されました。

## 変更の背景

Goランタイムには、BSD系のオペレーティングシステム（macOS, FreeBSDなど）と共通のメモリ管理ロジックを扱う `mem_bsd.go` というファイルが存在します。このファイル内のコードは、`mmap` システムコールがメモリマッピングに失敗した場合、その戻り値として正の `errno` 値が返されることを期待していました。

しかし、Solarisの `mmap` システムコールを直接呼び出すGoの既存のラッパー（`src/runtime/os3_solaris.go` 内）は、失敗時に `MAP_FAILED` (通常は `(void*)-1` または `^uintptr(0)`) を返し、実際の `errno` 値は別の方法（例えば、レジスタやスレッドローカルストレージ）で設定されるのが一般的です。このGoラッパーは、`errno` 値を `mmap` の戻り値として直接返していなかったため、`mem_bsd.go` の期待とSolarisの実装との間に不整合が生じていました。

この不整合により、Solaris上でGoプログラムがメモリマッピングに失敗した際に、`mem_bsd.go` がエラーを正しく解釈できず、予期せぬ動作やクラッシュを引き起こす可能性がありました。このコミットは、この問題を解決し、Solaris上でのGoランタイムの堅牢性を向上させるために行われました。

## 前提知識の解説

### `mmap` システムコール

`mmap` (memory map) は、Unix系オペレーティングシステムで提供されるシステムコールの一つで、ファイルやデバイスのコンテンツをプロセスのアドレス空間に直接マッピングするために使用されます。これにより、ファイルの内容を通常のメモリ操作（ポインタによるアクセス）で読み書きできるようになり、I/O操作の効率化や共有メモリの実装などに利用されます。

`mmap` の一般的なシグネチャは以下のようになります（C言語の場合）：
`void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);`

*   `addr`: マッピングを開始するアドレスのヒント。`NULL` の場合、システムが適切なアドレスを選択します。
*   `length`: マッピングするバイト数。
*   `prot`: メモリ保護フラグ（例: `PROT_READ`, `PROT_WRITE`, `PROT_EXEC`）。
*   `flags`: マッピングのタイプと動作を制御するフラグ（例: `MAP_SHARED`, `MAP_PRIVATE`, `MAP_ANON`, `MAP_FIXED`）。
*   `fd`: マッピングするファイルのファイルディスクリプタ。`MAP_ANON` の場合は `-1`。
*   `offset`: ファイル内のマッピング開始位置からのオフセット。

成功時にはマッピングされた領域の開始アドレスを返し、失敗時には `MAP_FAILED` (通常は `(void*)-1`) を返し、`errno` グローバル変数にエラーコードを設定します。

### `errno`

`errno` は、C標準ライブラリおよびPOSIXシステムコールがエラーを報告するために使用する整数型のグローバル変数（またはスレッドローカル変数）です。システムコールが失敗した場合、`errno` にはエラーの種類を示す正の整数値が設定されます。例えば、`EACCES` (アクセス拒否)、`ENOMEM` (メモリ不足) などがあります。Goランタイムは、これらの `errno` 値を内部的に処理し、Goのエラーインターフェースに変換することがよくあります。

### Goランタイムのシステムコール呼び出し (`sysvicall6`, `asmcgocall`)

Goランタイムは、OSのシステムコールを直接呼び出すための低レベルなメカニズムを持っています。

*   **`sysvicall6`**: これは、GoランタイムがC言語の関数やシステムコールを呼び出すためのラッパー関数です。`6` は、最大6つの引数を取れることを示唆しています。GoのスタックからCのスタックへの切り替えや、レジスタへの引数の配置など、ABI (Application Binary Interface) に準拠した呼び出しを行います。しかし、この関数は通常、システムコールの戻り値のみを扱い、`errno` のような副次的なエラー情報は別途取得する必要があります。

*   **`asmcgocall`**: これはGoランタイム内のアセンブリ関数で、GoコードがCコード（cgo経由）を呼び出す際や、特定のコンテキスト切り替えが必要なシステムコールを行う際に主に利用されます。`asmcgocall` の主な役割は以下の通りです。
    *   **コンテキスト切り替え**: Goの実行環境（ゴルーチンのスタック）から、C言語互換の環境（OSスレッドのスタック、`g0` スタックと呼ばれることが多い）へ一時的に切り替えます。
    *   **スケジューラへの通知**: Goスケジューラに、現在のOSスレッド（M）が外部コードやシステムコールを実行しようとしていることを通知します。これにより、スケジューラは必要に応じて新しいOSスレッドを作成し、他のゴルーチンを実行してプログラムがブロックされるのを防ぎます。
    *   **戻り値とエラーの取得**: `asmcgocall` は、システムコールからの複数の戻り値（例えば、実際の戻り値と `errno`）を効率的に取得するために使用されることがあります。

### `unsafe.Pointer` と `uintptr`

*   **`unsafe.Pointer`**: Goにおける任意の型のポインタを保持できる特殊なポインタ型です。型安全性をバイパスするため、使用には注意が必要です。C言語の `void*` に似ています。
*   **`uintptr`**: 整数型で、ポインタのビットパターンを保持するのに十分な大きさがあります。ポインタと整数間の変換を可能にしますが、ガベージコレクタの対象外であるため、`unsafe.Pointer` と組み合わせて慎重に使用する必要があります。システムコールの引数や戻り値を扱う際によく使われます。

## 技術的詳細

従来のSolaris向け `mmap` ラッパーは、`sysvicall6` を使用して `libc_mmap` (Cライブラリの `mmap`) を呼び出し、その単一の戻り値を `unsafe.Pointer` にキャストして返していました。Unix系システムでは、`mmap` が失敗すると `MAP_FAILED` を返し、`errno` を設定します。`sysvicall6` は通常、`MAP_FAILED` の値を返すものの、`errno` の値は別のレジスタ（例えば、x86-64アーキテクチャでは `RDI` や `RAX` 以外のレジスタ、あるいは特定のメモリ位置）に格納されるため、単一の戻り値として `errno` を直接取得することはできませんでした。

`mem_bsd.go` のコードは、`mmap` が失敗した際に、その戻り値が `MAP_FAILED` ではなく、直接 `errno` の値であることを期待していました。これは、一部のシステムコールラッパーが、エラー時に `MAP_FAILED` の代わりに `errno` を返すように設計されている場合に発生する可能性があります。

このコミットでは、この不整合を解消するために、`doMmap` という新しいヘルパー関数が導入されました。`doMmap` は `asmcgocall` を利用して `libc_mmap` を呼び出します。`asmcgocall` は、システムコールからの複数の戻り値（この場合は `libc_mmap` の実際の戻り値と `errno`）を効率的に取得できるメカニズムを提供します。

具体的には、`libcall` 構造体を使用して、システムコール呼び出しに必要な情報（関数ポインタ、引数の数、引数へのポインタ）を渡し、`asmcgocall` が実行された後に、`libcall.r1` に `mmap` の実際の戻り値（マッピングされたアドレスまたは `MAP_FAILED`）、`libcall.err` に `errno` の値が格納されるように設計されています。

元の `mmap` 関数は `doMmap` を呼び出し、`p` (マッピングされたアドレス) と `err` (errno) の両方を受け取ります。そして、`p` が `^uintptr(0)` (つまり `MAP_FAILED`) と等しい場合、`unsafe.Pointer(err)` を返します。これにより、`mem_bsd.go` が期待する「失敗時に正の `errno` 値を返す」という挙動がSolaris上でも実現されます。

## コアとなるコードの解説

1.  **`mmap` 関数の変更**:
    *   元の `mmap` 関数は `sysvicall6` を直接呼び出していましたが、変更後は新しく導入された `doMmap` 関数を呼び出すようになりました。
    *   `doMmap` は `p` (マッピングされたアドレスまたは `MAP_FAILED`) と `err` (`errno` の値) の2つの `uintptr` 値を返します。
    *   `if p == ^uintptr(0)` という条件で、`mmap` が失敗したかどうかをチェックします。`^uintptr(0)` は、`uintptr` 型の最大値であり、通常は `(void*)-1` に相当する `MAP_FAILED` を表します。
    *   もし `mmap` が失敗していた場合 (`p == ^uintptr(0)` が真の場合)、`unsafe.Pointer(err)` を返します。これにより、`mem_bsd.go` が期待する `errno` 値が戻り値として渡されます。
    *   `mmap` が成功した場合、`unsafe.Pointer(p)` を返し、マッピングされたメモリ領域の開始アドレスをGoのポインタとして提供します。

2.  **`doMmap` 関数の導入**:
    *   `//go:nosplit` ディレクティブは、この関数がスタックを分割しないことを示し、ランタイムの低レベルな部分で安全に呼び出せるようにします。
    *   `libcall` 構造体が宣言されます。この構造体は、`asmcgocall` を介してC関数を呼び出すための引数と戻り値を保持するために使用されます。
        *   `libcall.fn = uintptr(unsafe.Pointer(&libc_mmap))`: 呼び出すC関数 (`libc_mmap`) のアドレスを設定します。
        *   `libcall.n = 6`: `libc_mmap` が6つの引数を取ることを示します。
        *   `libcall.args = uintptr(noescape(unsafe.Pointer(&addr)))`: `libc_mmap` に渡す引数リストの先頭アドレスを設定します。`noescape` は、このポインタがスタックからエスケープしないことをコンパイラに伝えます。
    *   `asmcgocall(unsafe.Pointer(&asmsysvicall6), unsafe.Pointer(&libcall))`: 実際のシステムコール呼び出しを実行します。`asmsysvicall6` は、`libcall` 構造体で指定された情報を使って `libc_mmap` を呼び出すアセンブリルーチンです。この呼び出しにより、Goの実行コンテキストからOSのコンテキストへ切り替わり、システムコールが実行されます。
    *   `return libcall.r1, libcall.err`: `asmcgocall` の実行後、`libcall.r1` には `libc_mmap` の主要な戻り値（マッピングされたアドレスまたは `MAP_FAILED`）が、`libcall.err` には `errno` の値が格納されます。これら2つの値が `doMmap` の戻り値として返されます。

この変更により、Solaris上での `mmap` のエラー処理が、Goランタイムの他の部分（特に `mem_bsd.go`）の期待と一致するようになり、クロスプラットフォームなGoランタイムの整合性が向上しました。

# [インデックス 21168] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるスタックのスキャンフェーズ中のゴルーチン（`g`）の振る舞いを改善することを目的としています。特に、GCがゴルーチンのスタックをスキャンする際に、すべてのゴルーチンが適切な「スキャン状態」にあることを保証するための変更が含まれています。

## 元コミット内容

このコミットの元のメッセージは以下の通りです。

「[dev.garbage] runtime: GCscanフェーズ中に実行中のゴルーチンを停止する。スタックがスキャンされている間、すべてのゴルーチンがスキャン状態にあることを保証する。」

これは、ガベージコレクションの「スキャンフェーズ」において、実行中のゴルーチンが適切に処理され、そのスタックがスキャンされる際に正しい状態（`_Gscan`プレフィックスを持つ状態）にあることを保証するという意図を明確に示しています。

## 変更の背景

Goのガベージコレクタは、プログラムが使用しているメモリを自動的に管理し、不要になったメモリを解放する役割を担っています。このプロセスには複数のフェーズがあり、その一つが「スキャンフェーズ」（`GCscan`）です。このフェーズでは、GCは到達可能なオブジェクトを特定するために、ゴルーチンのスタックを含むルートセットからポインタをスキャンします。

以前の実装では、`GCscan`フェーズ中に実行中のゴルーチン（`_Grunning`状態）のスタックが適切にスキャンされない、またはスキャンがスキップされる可能性がありました。これは、GCの正確性や完全性に影響を与える可能性があり、特にスタック上に存在するポインタの追跡において問題を引き起こす恐れがありました。

このコミットは、このような潜在的な問題を解決し、GCのスタックスキャンがより堅牢で正確に行われるようにするために導入されました。具体的には、スタックがスキャンされるゴルーチンが必ず`_Gscan`状態にあることを強制し、実行中のゴルーチンもGCスキャンの対象となるように振る舞いを変更しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念に関する知識が必要です。

*   **ガベージコレクション (GC)**: Goの自動メモリ管理システム。不要なメモリを自動的に回収します。
*   **GCのフェーズ**: GoのGCは複数のフェーズに分かれています。
    *   **マークフェーズ (Mark Phase)**: 生きているオブジェクトをマークします。
    *   **スキャンフェーズ (Scan Phase)**: マークされたオブジェクトから到達可能なポインタをスキャンし、さらに生きているオブジェクトを特定します。このコミットが焦点を当てているのはこのフェーズです。
*   **ゴルーチン (Goroutine)**: Goの軽量な並行処理単位。Goプログラムは多数のゴルーチンを同時に実行できます。
*   **ゴルーチンの状態 (Goroutine States)**: ゴルーチンはライフサイクルを通じて様々な状態を取ります。Goランタイム内部では、これらの状態は`g.status`フィールドで管理されます。
    *   `_Grunning`: ゴルーチンが現在実行中である状態。
    *   `_Gwaiting`: ゴルーチンが何らかのイベントを待機している状態（例: チャンネル操作、システムコール）。
    *   `_Gscan`プレフィックスを持つ状態（例: `_Gscanrunning`, `_Gscanwaiting`）: GCがゴルーチンのスタックをスキャンしている間の一時的な状態。これらの状態は、GCがスタック上のポインタを安全に処理できるようにするために使用されます。
*   **スタックスキャン**: GCがゴルーチンのスタックを走査し、スタック上に存在するポインタ（ヒープ上のオブジェクトを指すもの）を特定するプロセス。これにより、GCは到達可能なオブジェクトを正確にマークできます。
*   **`gothrow`**: Goランタイム内部で致命的なエラーが発生した場合に呼び出される関数。通常、回復不可能な状態を示し、プログラムをクラッシュさせます。
*   **`casfrom_Gscanstatus` / `castogscanstatus`**: ゴルーチンの状態をアトミックに遷移させるためのランタイム関数。`cas`はCompare-And-Swapの略で、並行処理における競合状態を避けるために使用されます。

## 技術的詳細

このコミットは、主に以下の3つのファイルにわたる変更を通じて、GCスキャンフェーズ中のゴルーチン状態管理を強化しています。

1.  **`src/runtime/mgc.go`**:
    *   `scanstack(gp *g)`関数内で、ゴルーチン`gp`のステータスが`_Gscan`フラグを含んでいることを厳密にチェックするコードが有効化されました。
        ```go
        if readgstatus(gp)&_Gscan == 0 {
            print("runtime:scanstack: gp=", gp, ", goid=", gp.goid, ", gp->atomicstatus=", hex(readgstatus(gp)), "\n")
            gothrow("scanstack - bad status")
        }
        ```
        この変更により、`scanstack`が呼び出された時点でゴルーチンが`_Gscan`状態にない場合、ランタイムは致命的なエラーを発生させます。これは、GCがスタックをスキャンする際には、ゴルーチンが必ずスキャンに適した状態にあるべきだという強いアサーション（表明）です。以前はコメントアウトされていたこのチェックが有効化されたことは、ランタイムがゴルーチン状態の整合性に対してより厳格になったことを示しています。

2.  **`src/runtime/proc1.go`**:
    *   `casfrom_Gscanstatus(gp *g, oldval, newval uint32)`関数に`default`ケースが追加されました。この関数は、ゴルーチンが`_Gscan`状態から別の状態へ遷移する際に呼び出されます。
        ```go
        default:
            print("runtime: casfrom_Gscanstatus bad oldval gp=", gp, ", oldval=", hex(oldval), ", newval=", hex(newval), "\n")
            dumpgstatus(gp)
            gothrow("casfrom_Gscanstatus:top gp->status is not in scan state")
        ```
        この`default`ケースは、`oldval`が予期される`_Gscan`状態（`_Gscanrunnable`, `_Gscanwaiting`, `_Gscanrunning`）のいずれでもない場合に`gothrow`を呼び出します。これは、ゴルーチンの状態遷移が常に`_Gscan`状態から始まることを保証し、不正な状態遷移を防ぐための防御的なプログラミングです。
    *   `stopg(gp *g)`関数から、`_Grunning`状態のゴルーチンを`GCscan`フェーズ中にスキャン対象から除外するロジックが削除されました。
        ```diff
        -		case _Grunning:
        -			if gcphase == _GCscan {
        -				// Running routines not scanned during
        -				// GCscan phase, we only scan non-running routines.
        -				gp.gcworkdone = true
        -				return false
        -			}
        ```
        この削除は非常に重要です。以前は、実行中のゴルーチンは`GCscan`フェーズ中にスキャンされず、`gcworkdone`が`true`に設定されていました。この変更により、実行中のゴルーチンもGCスキャンの対象となり、そのスタックが適切に処理されるようになりました。これは、GCの正確性を向上させる上で不可欠な変更です。

3.  **`src/runtime/stack1.go`**:
    *   `newstack()`関数内で、`gp.preemptscan`が`true`の場合の処理に重要な変更が加えられました。`preemptscan`は、ゴルーチンがプリエンプティブにスタックをスキャンする必要があることを示します。
        ```go
        for !castogscanstatus(gp, _Gwaiting, _Gscanwaiting) {
            // Likely to be racing with the GC as it sees a _Gwaiting and does the stack scan.
            // If so this stack will be scanned twice which does not change correctness.
        }
        gcphasework(gp)
        casfrom_Gscanstatus(gp, _Gscanwaiting, _Gwaiting)
        casgstatus(gp, _Gwaiting, _Grunning)
        ```
        このコードは、ゴルーチンが`_Gwaiting`状態から`_Gscanwaiting`状態へ遷移するまでループを試みます。コメントにあるように、これはGCが`_Gwaiting`状態のゴルーチンをスキャンしようとしている場合との競合状態を解決するためのものです。このループにより、ゴルーチンは確実に`_Gscanwaiting`状態に入り、そのスタックがスキャンされます。たとえスタックが二度スキャンされたとしても、それは正しさに影響しないとされています。スキャン後、ゴルーチンは`_Gwaiting`に戻され、最終的に`_Grunning`状態に遷移します。

これらの変更は、GCがゴルーチンのスタックをスキャンする際の堅牢性と正確性を大幅に向上させます。特に、実行中のゴルーチンがGCスキャンの対象となるように変更されたこと、およびゴルーチンがスキャン状態にあることの厳密なチェックが導入されたことがポイントです。

## コアとなるコードの解説

*   **`src/runtime/mgc.go` の `scanstack` 関数**:
    *   この関数は、特定のゴルーチンのスタックをスキャンする役割を担っています。変更の核心は、スタックスキャンが開始される前に、ゴルーチンが`_Gscan`状態にあることを強制するアサーションが有効化された点です。これにより、GCがスタック上のポインタを安全かつ正確に識別できる状態が保証されます。もしゴルーチンがこの状態にない場合、それはランタイムの内部的な不整合を示唆するため、`gothrow`でプログラムを終了させます。

*   **`src/runtime/proc1.go` の `casfrom_Gscanstatus` 関数**:
    *   この関数は、ゴルーチンが`_Gscan`状態から他の状態へ遷移する際に使用されます。追加された`default`ケースは、`oldval`（遷移前の状態）が予期される`_Gscan`状態のいずれでもない場合にエラーを発生させます。これは、ゴルーチンの状態遷移の整合性を保ち、GCスキャンに関連する状態管理の厳密性を高めるためのものです。
*   **`src/runtime/proc1.go` の `stopg` 関数**:
    *   `stopg`関数は、GCがゴルーチンを停止させ、その状態をGCに適した状態に遷移させるために使用されます。以前は、`GCscan`フェーズ中に実行中のゴルーチン（`_Grunning`）はスキャン対象から明示的に除外されていました。このロジックの削除は、GCが実行中のゴルーチンのスタックもスキャンする必要があるという新しい要件を反映しています。これにより、GCはより包括的なメモリの到達可能性分析を実行できるようになります。

*   **`src/runtime/stack1.go` の `newstack` 関数**:
    *   `newstack`関数は、ゴルーチンが新しいスタックを必要とする場合（例: スタックの拡張）に呼び出されます。`gp.preemptscan`が`true`の場合、ゴルーチンはプリエンプティブにスキャンされる必要があります。追加された`for`ループは、ゴルーチンが`_Gwaiting`状態から`_Gscanwaiting`状態へアトミックに遷移するまで再試行します。これは、GCが同時にそのゴルーチンをスキャンしようとしている可能性のある競合状態を解決するためのものです。このループにより、ゴルーチンは確実にスキャン状態に入り、GCがそのスタックを安全に処理できるようになります。スキャン後、ゴルーチンは元の`_Gwaiting`状態に戻され、その後`_Grunning`状態に遷移して実行を再開します。

これらの変更は、Goのガベージコレクタがゴルーチンのスタックをスキャンする際の正確性と堅牢性を向上させるための重要なステップです。特に、実行中のゴルーチンを含むすべてのゴルーチンがGCスキャン中に適切な状態にあることを保証することで、メモリリークやGCの不正確さにつながる可能性のあるエッジケースが排除されます。

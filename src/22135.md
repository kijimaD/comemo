# [インデックス 22135] ファイルの概要

このコミットは、Go言語のビルドツールチェーンにおいて、アセンブラの実行順序を変更し、Go言語で書かれた新しいアセンブラ (`asm`) を優先的に使用するようにしたものです。また、`asm` ツールに `-trimpath` フラグのサポートを追加しています。これにより、`asm` 自身のバグ発見を促進し、ビルドの再現性を向上させることを目的としています。

## 元コミット内容

このコミットの主な内容は以下の通りです。

1.  **`asm` アセンブラの優先順位の変更**: `cmd/go` ツールにおいて、アセンブリコードを処理する際に、Go言語で実装された `asm` アセンブラを、従来のC言語で実装されたアセンブラ (`6a`, `8a` など、アーキテクチャに依存するアセンブラ) よりも先に実行するように変更しました。
2.  **`asm` アセンブラへの `-trimpath` フラグの実装**: `asm` ツールが `-trimpath` コマンドラインフラグをサポートするようにしました。このフラグは、コンパイルされたバイナリに記録されるソースファイルパスから、ビルド環境に依存するプレフィックス部分を削除するために使用されます。

## 変更の背景

この変更には、主に二つの背景があります。

1.  **`asm` アセンブラの品質向上と自立**: Go言語で書かれた新しい `asm` アセンブラは、Goのツールチェーンの将来を担う重要なコンポーネントです。しかし、これまでは従来のC言語ベースのアセンブラ (`6a` など) が先に実行され、入力の検証やエラー検出を行っていたため、`asm` 自身のバグや不具合が表面化しにくい状況でした。`asm` を最初に実行することで、`asm` が不正な入力やエッジケースを直接処理し、その結果として `asm` 自身の堅牢性と品質を向上させることが可能になります。これは、`asm` がGoツールチェーンの主要なアセンブラとして成熟するために不可欠なステップでした。
2.  **ビルドの再現性の向上**: `-trimpath` フラグは、Goのビルドプロセスにおいて、生成されるバイナリに含まれるデバッグ情報やスタックトレース内のファイルパスから、ビルド時の絶対パス情報を削除し、相対パスやトリミングされたパスに置き換えるために使用されます。これにより、異なる環境や異なるディレクトリでビルドされたとしても、生成されるバイナリが同一になる「再現可能なビルド (Reproducible Builds)」を実現しやすくなります。`asm` アセンブラがこのフラグをサポートすることで、アセンブリレベルで生成される情報についてもパスのトリミングが適用され、ビルドの再現性がさらに向上します。

## 前提知識の解説

### Go言語のビルドプロセスとツールチェーン

Go言語のプログラムは、ソースコードから実行可能なバイナリを生成する際に、複数のツールが連携して動作します。

*   **`go build` コマンド**: Goプログラムをビルドするための主要なコマンドです。内部的にコンパイラ、アセンブラ、リンカなどを呼び出します。
*   **コンパイラ (`go tool compile`)**: Goのソースコード (`.go` ファイル) をアセンブリコードに変換します。
*   **アセンブラ (`go tool asm` または `go tool 6a`/`8a` など)**: アセンブリコード (`.s` ファイル) をオブジェクトファイル (`.o` ファイル) に変換します。
*   **リンカ (`go tool link`)**: 複数のオブジェクトファイルやライブラリを結合し、最終的な実行可能バイナリを生成します。

### Goのアセンブラ (`asm`) とC言語ベースのアセンブラ (`6a`, `8a` など)

Go言語には、歴史的に2種類のアセンブラが存在しました。

*   **C言語ベースのアセンブラ (`6a`, `8a`, `5a` など)**: これらはGoの初期から存在し、C言語で書かれたアセンブラです。`6a` はamd64アーキテクチャ用、`8a` はarmアーキテクチャ用といったように、アーキテクチャごとに異なるツールが存在しました。これらはPlan 9アセンブラの文法に基づいています。
*   **Go言語で書かれたアセンブラ (`asm`)**: Go 1.5リリースに向けて、Go言語自身で書かれた新しいアセンブラが開発されました。これは、Goツールチェーンの自己ホスト化 (self-hosting) の一環であり、Goのビルドシステム全体をGo言語で記述することを目指す動きの一部でした。`asm` は、従来のC言語ベースのアセンブラと同じ機能を持ちつつ、Go言語で実装されているため、Go開発者にとって保守や改善が容易になるという利点があります。

### `verifyAsm` フラグ

`verifyAsm` は、Goのビルドシステム内部で使用されるデバッグ/検証用のフラグです。このフラグが有効な場合、Goのビルドプロセスは、アセンブリコードを処理する際に、新しいGo言語ベースの `asm` アセンブラと、従来のC言語ベースのアセンブラの両方を実行します。そして、両方のアセンブラが生成したオブジェクトファイルが完全に一致するかどうかを比較します。もし一致しない場合は、エラーとして報告されます。

このメカニズムは、新しい `asm` アセンブラが正しく機能していることを確認し、従来のC言語ベースのアセンブラとの互換性を保証するために非常に重要でした。このコミット以前は、`6a` がプライマリで `asm` がセカンダリとして検証されていましたが、このコミットにより `asm` がプライマリとなり、`6a` がその検証対象となりました。

### `-trimpath` フラグ

`-trimpath` は、Goのビルドコマンド (`go build` など) に渡すことができるコマンドラインフラグです。このフラグを使用すると、Goが生成するバイナリファイルに含まれるソースファイルパス情報（例えば、デバッグ情報、スタックトレース、`runtime.Caller` などで取得されるパス）から、ビルド時の絶対パスのプレフィックス部分が削除されます。

例えば、`/home/user/project/src/main.go` というファイルが `/home/user/project` ディレクトリでビルドされた場合、通常はバイナリに `/home/user/project/src/main.go` というパスが記録されます。しかし、`-trimpath` を指定すると、`src/main.go` のように、プロジェクトルートからの相対パスや、完全にトリミングされたパスが記録されるようになります。

これにより、以下のような利点があります。

*   **再現可能なビルド**: 異なるマシンや異なるディレクトリでビルドしても、生成されるバイナリがビット単位で同一になる可能性が高まります。これは、ソフトウェアの信頼性やセキュリティ監査において非常に重要です。
*   **情報漏洩の防止**: ビルド環境の絶対パスがバイナリに含まれることを防ぎます。
*   **バイナリサイズの削減**: 微々たるものですが、パス情報の冗長性を減らすことができます。

### アセンブラの実行順序の変更

Goのビルドプロセスにおいて、アセンブリファイル (`.s` 拡張子を持つファイル) をオブジェクトファイルに変換する際、`gcToolchain.asm` 関数が呼び出されます。この関数内で、どのアセンブラを実行するかが決定されます。

変更前は、`tool(archChar + "a")`、つまり `6a` や `8a` といったC言語ベースのアセンブラが最初に実行されていました。このコミットでは、この部分が `tool("asm")` に変更されました。これにより、Go言語で書かれた `asm` アセンブラが、アセンブリファイルの処理においてプライマリの役割を担うことになります。

### `verifyAsm` の動作変更

`verifyAsm` フラグが有効な場合、`toolVerify` 関数が呼び出され、アセンブラの出力が検証されます。このコミット以前は、`toolVerify` は `asm` アセンブラの出力を検証していました（つまり、`6a` がプライマリで、`asm` の出力が `6a` の出力と比較されていた）。

変更後は、`toolVerify` の呼び出しが `toolVerify(b, p, archChar+"a", ofile, args)` となっています。これは、`asm` がプライマリとして実行された後、`toolVerify` が今度はC言語ベースのアセンブラ (`6a` など) を実行し、その出力を `asm` が生成した出力と比較することを意味します。これにより、`asm` が生成した結果が、従来のC言語ベースのアセンブラの出力と一致するかどうかが確認され、`asm` の正確性が保証されます。

また、`verifyAsm` のコメントも更新され、この新しい動作が明確に記述されています。

### `src/cmd/asm/internal/flags/flags.go` の変更

この変更は、`asm` コマンドが受け付けるコマンドラインフラグの定義に関するものです。`TrimPath` フラグのコメントから `(unused TODO)` が削除されたことは、このフラグが単なる計画段階のものではなく、実際に機能として実装され、利用可能になったことを示しています。これは、`asm` アセンブラが `-trimpath` の機能を取り込んだことの直接的な証拠です。

### `src/cmd/asm/main.go` の変更

`main.go` は `asm` アセンブラのエントリポイントです。ここで `ctxt.Trimpath = *flags.TrimPath` が追加されたことは、コマンドラインでユーザーが指定した `-trimpath` の値が、アセンブラの内部処理コンテキスト (`ctxt`) に渡されるようになったことを意味します。アセンブラは、この `ctxt.Trimpath` の値に基づいて、生成するオブジェクトファイル内のパス情報をどのように処理するかを決定します。具体的には、ソースファイルパスを記録する際に、指定されたプレフィックスを削除するロジックが内部で動作するようになります。これにより、`-trimpath` フラグが `asm` アセンブラによって実際に尊重され、ビルドの再現性向上に貢献します。

### `src/cmd/go/build.go` の変更

このファイルは、`go build` コマンドのビルドロジックの中核を担っています。

*   **プライマリアセンブラの切り替え**:
    `gcToolchain.asm` 関数内の `args` スライス構築部分で、`tool(archChar + "a")` が `tool("asm")` に変更された点が最も重要です。これは、Goのビルドシステムがアセンブリファイルを処理する際に、従来のC言語ベースのアセンブラ（例: `6a`）ではなく、Go言語で書かれた `asm` アセンブラを最初に呼び出すように指示するものです。この変更により、`asm` がアセンブリ処理の「主役」となり、その動作が直接テストされ、バグが早期に発見されるようになります。

    変更後は、`asm` がプライマリとして実行され、その後に `toolVerify` がC言語ベースのアセンブラ (`archChar+"a"`) を実行し、`asm` の出力と `archChar+"a"` の出力を比較します。これにより、`asm` が生成するオブジェクトファイルが、従来のC言語ベースのアセンブラが生成するものと互換性があることを確認しつつ、`asm` 自身の信頼性を高めることができます。

*   **`verifyAsm` コメントの更新**:
    `verifyAsm` 定数のコメントが「`asm` will run both `asm` and (say) `6a`」と更新されたのは、上記の動作変更を正確に反映するためです。これは、コードの意図を明確にし、将来のメンテナがこのロジックを理解しやすくするための重要なドキュメンテーションの変更です。

## 元コミット内容

このコミットの主な内容は以下の通りです。

1.  **`asm` アセンブラの優先順位の変更**: `cmd/go` ツールにおいて、アセンブリコードを処理する際に、Go言語で実装された `asm` アセンブラを、従来のC言語で実装されたアセンブラ (`6a`, `8a` など、アーキテクチャに依存するアセンブラ) よりも先に実行するように変更しました。
2.  **`asm` アセンブラへの `-trimpath` フラグの実装**: `asm` ツールが `-trimpath` コマンドラインフラグをサポートするようにしました。このフラグは、コンパイルされたバイナリに記録されるソースファイルパスから、ビルド環境に依存するプレフィックス部分を削除するために使用されます。

## 変更の背景

この変更には、主に二つの背景があります。

1.  **`asm` アセンブラの品質向上と自立**: Go言語で書かれた新しい `asm` アセンブラは、Goのツールチェーンの将来を担う重要なコンポーネントです。しかし、これまでは従来のC言語ベースのアセンブラ (`6a` など) が先に実行され、入力の検証やエラー検出を行っていたため、`asm` 自身のバグや不具合が表面化しにくい状況でした。`asm` を最初に実行することで、`asm` が不正な入力やエッジケースを直接処理し、その結果として `asm` 自身の堅牢性と品質を向上させることが可能になります。これは、`asm` がGoツールチェーンの主要なアセンブラとして成熟するために不可欠なステップでした。
2.  **ビルドの再現性の向上**: `-trimpath` フラグは、Goのビルドプロセスにおいて、生成されるバイナリに含まれるデバッグ情報やスタックトレース内のファイルパスから、ビルド時の絶対パス情報を削除し、相対パスやトリミングされたパスに置き換えるために使用されます。これにより、異なる環境や異なるディレクトリでビルドされたとしても、生成されるバイナリが同一になる「再現可能なビルド (Reproducible Builds)」を実現しやすくなります。`asm` アセンブラがこのフラグをサポートすることで、アセンブリレベルで生成される情報についてもパスのトリミングが適用され、ビルドの再現性がさらに向上します。

## 前提知識の解説

### Go言語のビルドプロセスとツールチェーン

Go言語のプログラムは、ソースコードから実行可能なバイナリを生成する際に、複数のツールが連携して動作します。

*   **`go build` コマンド**: Goプログラムをビルドするための主要なコマンドです。内部的にコンパイラ、アセンブラ、リンカなどを呼び出します。
*   **コンパイラ (`go tool compile`)**: Goのソースコード (`.go` ファイル) をアセンブリコードに変換します。
*   **アセンブラ (`go tool asm` または `go tool 6a`/`8a` など)**: アセンブリコード (`.s` ファイル) をオブジェクトファイル (`.o` ファイル) に変換します。
*   **リンカ (`go tool link`)**: 複数のオブジェクトファイルやライブラリを結合し、最終的な実行可能バイナリを生成します。

### Goのアセンブラ (`asm`) とC言語ベースのアセンブラ (`6a`, `8a` など)

Go言語には、歴史的に2種類のアセンブラが存在しました。

*   **C言語ベースのアセンブラ (`6a`, `8a`, `5a` など)**: これらはGoの初期から存在し、C言語で書かれたアセンブラです。`6a` はamd64アーキテクチャ用、`8a` はarmアーキテクチャ用といったように、アーキテクチャごとに異なるツールが存在しました。これらはPlan 9アセンブラの文法に基づいています。
*   **Go言語で書かれたアセンブラ (`asm`)**: Go 1.5リリースに向けて、Go言語自身で書かれた新しいアセンブラが開発されました。これは、Goツールチェーンの自己ホスト化 (self-hosting) の一環であり、Goのビルドシステム全体をGo言語で記述することを目指す動きの一部でした。`asm` は、従来のC言語ベースのアセンブラと同じ機能を持ちつつ、Go言語で実装されているため、Go開発者にとって保守や改善が容易になるという利点があります。

### `verifyAsm` フラグ

`verifyAsm` は、Goのビルドシステム内部で使用されるデバッグ/検証用のフラグです。このフラグが有効な場合、Goのビルドプロセスは、アセンブリコードを処理する際に、新しいGo言語ベースの `asm` アセンブラと、従来のC言語ベースのアセンブラの両方を実行します。そして、両方のアセンブラが生成したオブジェクトファイルが完全に一致するかどうかを比較します。もし一致しない場合は、エラーとして報告されます。

このメカニズムは、新しい `asm` アセンブラが正しく機能していることを確認し、従来のC言語ベースのアセンブラとの互換性を保証するために非常に重要でした。このコミット以前は、`6a` がプライマリで `asm` がセカンダリとして検証されていましたが、このコミットにより `asm` がプライマリとなり、`6a` がその検証対象となりました。

### `-trimpath` フラグ

`-trimpath` は、Goのビルドコマンド (`go build` など) に渡すことができるコマンドラインフラグです。このフラグを使用すると、Goが生成するバイナリファイルに含まれるソースファイルパス情報（例えば、デバッグ情報、スタックトレース、`runtime.Caller` などで取得されるパス）から、ビルド時の絶対パスのプレフィックス部分が削除されます。

例えば、`/home/user/project/src/main.go` というファイルが `/home/user/project` ディレクトリでビルドされた場合、通常はバイナリに `/home/user/project/src/main.go` というパスが記録されます。しかし、`-trimpath` を指定すると、`src/main.go` のように、プロジェクトルートからの相対パスや、完全にトリミングされたパスが記録されるようになります。

これにより、以下のような利点があります。

*   **再現可能なビルド**: 異なるマシンや異なるディレクトリでビルドしても、生成されるバイナリがビット単位で同一になる可能性が高まります。これは、ソフトウェアの信頼性やセキュリティ監査において非常に重要です。
*   **情報漏洩の防止**: ビルド環境の絶対パスがバイナリに含まれることを防ぎます。
*   **バイナリサイズの削減**: 微々たるものですが、パス情報の冗長性を減らすことができます。

## 技術的詳細

このコミットにおける技術的な変更は、主にGoのビルドツールチェーンの内部ロジックと、`asm` アセンブラのコマンドラインフラグ処理に集中しています。

### アセンブラの実行順序の変更

Goのビルドプロセスにおいて、アセンブリファイル (`.s` 拡張子を持つファイル) をオブジェクトファイルに変換する際、`gcToolchain.asm` 関数が呼び出されます。この関数内で、どのアセンブラを実行するかが決定されます。

変更前は、`tool(archChar + "a")`、つまり `6a` や `8a` といったC言語ベースのアセンブラが最初に実行されていました。このコミットでは、この部分が `tool("asm")` に変更されました。これにより、Go言語で書かれた `asm` アセンブラが、アセンブリファイルの処理においてプライマリの役割を担うことになります。

```diff
--- a/src/cmd/go/build.go
+++ b/src/cmd/go/build.go
@@ -1711,12 +1711,12 @@ func (gcToolchain) asm(b *builder, p *Package, obj, ofile, sfile string) error {
 	// Add -I pkg/GOOS_GOARCH so #include "textflag.h" works in .s files.
 	inc := filepath.Join(goroot, "pkg", fmt.Sprintf("%s_%s", goos, goarch))
 	sfile = mkAbs(p.Dir, sfile)
-	args := []interface{}{buildToolExec, tool(archChar + "a"), "-o", ofile, "-trimpath", b.work, "-I", obj, "-I", inc, "-D", "GOOS_" + goos, "-D", "GOARCH_" + goarch, sfile}
+	args := []interface{}{buildToolExec, tool("asm"), "-o", ofile, "-trimpath", b.work, "-I", obj, "-I", inc, "-D", "GOOS_" + goos, "-D", "GOARCH_" + goarch, sfile}
 	if err := b.run(p.Dir, p.ImportPath, nil, args...); err != nil {
 		return err
 	}
 	if verifyAsm {
-		if err := toolVerify(b, p, "asm", ofile, args); err != nil {
+		if err := toolVerify(b, p, archChar+"a", ofile, args); err != nil {
 			return err
 		}
 	}
```

### `verifyAsm` の動作変更

`verifyAsm` フラグが有効な場合、`toolVerify` 関数が呼び出され、アセンブラの出力が検証されます。このコミット以前は、`toolVerify` は `asm` アセンブラの出力を検証していました（つまり、`6a` がプライマリで、`asm` の出力が `6a` の出力と比較されていた）。

変更後は、`toolVerify` の呼び出しが `toolVerify(b, p, archChar+"a", ofile, args)` となっています。これは、`asm` がプライマリとして実行された後、`toolVerify` が今度はC言語ベースのアセンブラ (`6a` など) を実行し、その出力を `asm` が生成した出力と比較することを意味します。これにより、`asm` が生成した結果が、従来のC言語ベースのアセンブラの出力と一致するかどうかが確認され、`asm` の正確性が保証されます。

また、`verifyAsm` のコメントも更新され、この新しい動作が明確に記述されています。

```diff
--- a/src/cmd/go/build.go
+++ b/src/cmd/go/build.go
@@ -1703,7 +1703,7 @@ func (gcToolchain) gc(b *builder, p *Package, archive, obj string, asmhdr bool,
 }
 
 // verifyAsm specifies whether to check the assemblers written in Go
-// against the assemblers written in C. If set, asm will run both (say) 6a and new6a
+// against the assemblers written in C. If set, asm will run both asm and (say) 6a
 // and fail if the two produce different output files.
 const verifyAsm = true
```

1.  **フラグの定義更新 (`src/cmd/asm/internal/flags/flags.go`)**:
    `TrimPath` フラグのコメントから `(unused TODO)` という記述が削除されました。これは、このフラグがもはや「未使用のTODO」ではなく、実際に機能するようになったことを示しています。

## コアとなるコードの解説

### `src/cmd/asm/internal/flags/flags.go` の変更

この変更は、`asm` コマンドが受け付けるコマンドラインフラグの定義に関するものです。`TrimPath` フラグのコメントから `(unused TODO)` が削除されたことは、このフラグが単なる計画段階のものではなく、実際に機能として実装され、利用可能になったことを示しています。これは、`asm` アセンブラが `-trimpath` の機能を取り込んだことの直接的な証拠です。

### `src/cmd/asm/main.go` の変更

`main.go` は `asm` アセンブラのエントリポイントです。ここで `ctxt.Trimpath = *flags.TrimPath` が追加されたことは、コマンドラインでユーザーが指定した `-trimpath` の値が、アセンブラの内部処理コンテキスト (`ctxt`) に渡されるようになったことを意味します。アセンブラは、この `ctxt.Trimpath` の値に基づいて、生成するオブジェクトファイル内のパス情報をどのように処理するかを決定します。具体的には、ソースファイルパスを記録する際に、指定されたプレフィックスを削除するロジックが内部で動作するようになります。これにより、`-trimpath` フラグが `asm` アセンブラによって実際に尊重され、ビルドの再現性向上に貢献します。

### `src/cmd/go/build.go` の変更

このファイルは、`go build` コマンドのビルドロジックの中核を担っています。

*   **プライマリアセンブラの切り替え**:
    `gcToolchain.asm` 関数内の `args` スライス構築部分で、`tool(archChar + "a")` が `tool("asm")` に変更された点が最も重要です。これは、Goのビルドシステムがアセンブリファイルを処理する際に、従来のC言語ベースのアセンブラ（例: `6a`）ではなく、Go言語で書かれた `asm` アセンブラを最初に呼び出すように指示するものです。この変更により、`asm` がアセンブリ処理の「主役」となり、その動作が直接テストされ、バグが早期に発見されるようになります。

*   **`verifyAsm` の検証対象の変更**:
    `verifyAsm` が `true` の場合、`toolVerify` 関数が呼び出されます。この `toolVerify` の引数が `toolVerify(b, p, "asm", ofile, args)` から `toolVerify(b, p, archChar+"a", ofile, args)` に変更されたことは、検証の役割が逆転したことを示します。
    変更前は、`6a` がプライマリで、`asm` の出力が `6a` の出力と比較されていました。
    変更後は、`asm` がプライマリとして実行され、その後に `toolVerify` がC言語ベースのアセンブラ (`archChar+"a"`) を実行し、`asm` の出力と `archChar+"a"` の出力を比較します。これにより、`asm` が生成するオブジェクトファイルが、従来のC言語ベースのアセンブラが生成するものと互換性があることを確認しつつ、`asm` 自身の信頼性を高めることができます。

*   **`verifyAsm` コメントの更新**:
    `verifyAsm` 定数のコメントが「`asm` will run both `asm` and (say) `6a`」と更新されたのは、上記の動作変更を正確に反映するためです。これは、コードの意図を明確にし、将来のメンテナがこのロジックを理解しやすくするための重要なドキュメンテーションの変更です。

これらの変更は、Goツールチェーンの自己ホスト化と、`asm` アセンブラの成熟に向けた重要な一歩であり、Goのビルドシステムの堅牢性と再現性を向上させるものです。

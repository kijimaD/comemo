# [インデックス 26213] ファイルの概要

このコミットは、Go言語の標準ライブラリ `net/http` パッケージにおける `Client` のタイムアウト処理メカニズムを刷新するものです。具体的には、以前使用されていた `Transport.CancelRequest` メソッドから、より新しく、より堅牢な `Request.Cancel` メカニズムへの移行が主要な変更点です。これにより、HTTP/2のサポートが改善され、リクエストキャンセル処理の柔軟性と信頼性が向上しています。

    use correctly and didn't work in all cases. And its error messages

    unfixable problem was that it didn't compose well. All RoundTripper
    implementations had to choose to whether to implement CancelRequest
    and both decisions had negative consequences.

    phases, had nice error messages, etc. But we forgot to use it in the

## 元コミット内容

このコミットは、`net/http` パッケージの `Client` がタイムアウト処理に `Request.Cancel` を使用するように変更し、`Transport.CancelRequest` を非推奨とすることを目的としています。

元々、HTTPリクエストをキャンセルする方法は存在しませんでした。その後、`Transport.CancelRequest` が導入され、基盤となるTCP接続を切断することで進行中のHTTPリクエストをキャンセルできるようになりました。しかし、この方法は正しく使用するのが難しく、すべての場合で機能するわけではなく、エラーメッセージも不明瞭でした。これらの問題は時間とともに一部修正されましたが、最も根本的な問題は、`RoundTripper` の実装間でうまく連携できない（composeできない）点でした。すべての `RoundTripper` 実装は `CancelRequest` を実装するかどうかを選択する必要があり、どちらの選択にも負の結果が伴いました。

Go 1.5では、`Request.Cancel` が導入されました。これは、より連携しやすく、すべてのフェーズで機能し、より良いエラーメッセージを提供するなど、多くの利点がありました。しかし、`Client.Timeout` の実装（複数のリクエストとリクエストボディの読み取りにまたがるタイムアウト）では、この新しいメカニズムの使用が見落とされていました。

Go 1.6（当時開発中）ではHTTP/2のサポートが追加されましたが、`http2.Transport` が `CancelRequest` メソッドを持っていなかったため、`Client.Timeout` が機能しないという問題が発生しました。

このコミットでは、`http2` に `CancelRequest` メソッドを追加するのではなく、`Transport.CancelRequest` を正式に非推奨とし、`Client`（`Client.Cancel` の唯一の呼び出し元）が `Request.Cancel` を使用するように更新します。これにより、HTTP/2クライアントのタイムアウトテストが有効になります。

互換性のために、`Client` は認識できない `RoundTripper` タイプに対しては引き続き `CancelRequest` を使用しますが、ドキュメントは `CancelRequest` が非推奨であることを示すように更新されます。

## 変更の背景

この変更の背景には、Go言語の `net/http` パッケージにおけるリクエストキャンセル処理の進化と、HTTP/2の導入があります。

1.  **初期の課題**: `net/http` の初期バージョンでは、進行中のHTTPリクエストをプログラム的にキャンセルする標準的な方法がありませんでした。これは、長時間実行されるリクエストや、ユーザーが操作を中断したい場合に問題となりました。
2.  **`Transport.CancelRequest` の導入と限界**: この問題を解決するために `Transport.CancelRequest` が導入されました。これは、基盤となるTCP接続を強制的に切断することでリクエストをキャンセルするメカニズムでした。しかし、このアプローチにはいくつかの重大な欠点がありました。
    *   **使いにくさ**: 正しく使用するのが難しく、特定の状況下では期待通りに機能しないことがありました。
    *   **エラーメッセージの質**: キャンセル時のエラーメッセージが不明瞭で、デバッグが困難でした。
    *   **合成の難しさ (Composability)**: `RoundTripper` インターフェースを実装するカスタムトランスポートが `CancelRequest` を実装するかどうかを選択する必要があり、その選択が複雑な影響を及ぼしました。例えば、`CancelRequest` を実装しないトランスポートでは、`Client.Timeout` が機能しないという問題がありました。
    *   **HTTP/2との非互換性**: HTTP/2は単一のTCP接続上で複数のストリームを多重化するため、TCP接続を切断する `CancelRequest` のアプローチはHTTP/2の設計と根本的に合いませんでした。Go 1.6でHTTP/2が導入される際、`http2.Transport` が `CancelRequest` を実装できないという問題が浮上しました。
3.  **`Request.Cancel` の導入 (Go 1.5)**: Go 1.5で `Request.Cancel` フィールドが導入されました。これは `chan struct{}` 型であり、このチャネルがクローズされるとリクエストがキャンセルされるという、より柔軟でGoらしいキャンセルメカニズムを提供しました。この方法は、コンテキスト（`context.Context`）ベースのキャンセルパターンと親和性が高く、よりクリーンなエラー処理と優れた合成性を提供しました。
4.  **`Client.Timeout` との連携不足**: `Request.Cancel` が導入されたにもかかわらず、`Client.Timeout` の実装は依然として `Transport.CancelRequest` に依存していました。これにより、`Client.Timeout` が `Request.Cancel` の利点を享受できず、特にHTTP/2環境での問題が顕在化しました。
5.  **本コミットの目的**: これらの背景から、`Client.Timeout` が `Request.Cancel` を利用するように変更し、`Transport.CancelRequest` を非推奨とすることで、リクエストキャンセル処理を統一し、HTTP/2を含むすべてのシナリオで堅牢かつ一貫した動作を保証することがこのコミットの目的となりました。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の `net/http` パッケージの概念と、リクエストキャンセルに関する一般的な知識が必要です。

### 1. `net/http` パッケージ
Go言語の標準ライブラリであり、HTTPクライアントとサーバーの実装を提供します。ウェブアプリケーションやAPIクライアントを構築する上で不可欠なパッケージです。

### 2. `http.Client`
HTTPリクエストを実行するためのクライアント構造体です。`Get`, `Post`, `Do` などのメソッドを提供し、リクエストの送信、リダイレクトの処理、クッキーの管理などを行います。`Client` は `Transport` を使用して実際のリクエストの送受信を行います。

### 3. `http.Request`
HTTPリクエストを表す構造体です。URL、メソッド、ヘッダー、ボディなどの情報を含みます。

### 4. `http.Response`
HTTPレスポンスを表す構造体です。ステータスコード、ヘッダー、ボディなどの情報を含みます。

### 5. `http.RoundTripper` インターフェース
`net/http` パッケージの核心的なインターフェースの一つです。
```go
type RoundTripper interface {
    RoundTrip(*Request) (*Response, error)
}
```
このインターフェースは、単一のHTTPトランザクション（リクエストの送信とレスポンスの受信）を実行する責任を定義します。`http.Client` は内部で `RoundTripper` を使用してリクエストを処理します。`http.Transport` は `RoundTripper` インターフェースのデフォルトの実装です。カスタムの `RoundTripper` を実装することで、リクエストの変更、認証の追加、ロギング、モックなどの高度な処理を挿入できます。

### 6. `Client.Timeout`
`http.Client` のフィールドで、リクエスト全体（接続確立、ヘッダー送信、ボディ送信、ヘッダー受信、ボディ受信を含む）にかかる最大時間を設定します。この時間を超えると、リクエストはキャンセルされ、エラーが返されます。

### 7. `Transport.CancelRequest(*Request)` (非推奨)
以前のリクエストキャンセルメカニズムです。`Transport` インターフェースを実装する型がこのメソッドを持つことで、特定の `Request` に関連付けられた基盤のTCP接続を強制的に切断し、リクエストをキャンセルすることができました。しかし、これはHTTP/1.xの接続モデルに密接に結びついており、HTTP/2のような多重化された接続では機能しませんでした。また、接続を切断するため、エラーメッセージが汎用的になりがちでした。

### 8. `Request.Cancel` (新しいキャンセルメカニズム)
Go 1.5で導入された、より現代的なリクエストキャンセルメカニズムです。`http.Request` 構造体には `Cancel chan struct{}` フィールドがあります。このチャネルがクローズされると、そのリクエストはキャンセルされるべきであるというシグナルが `RoundTripper` に伝達されます。`RoundTripper` の実装は、このチャネルを監視し、クローズされたときにリクエスト処理を中断する必要があります。この方法は、接続を切断するのではなく、リクエストの論理的なキャンセルを可能にするため、HTTP/2のようなプロトコルでも適切に機能します。また、`context.Context` を用いたキャンセルパターンとも非常に似ており、よりGoらしい並行処理のキャンセル手法と見なされます。

### 9. HTTP/2
HTTP/1.1の後継プロトコルで、単一のTCP接続上で複数のリクエストとレスポンスを多重化（multiplexing）する機能や、ヘッダー圧縮、サーバープッシュなどの機能を提供します。これにより、ウェブのパフォーマンスが大幅に向上します。Go 1.6で `net/http` パッケージにHTTP/2のサポートが追加されました。

## 技術的詳細

このコミットの技術的詳細を掘り下げると、`net/http` パッケージの内部動作、特にリクエストのライフサイクルとキャンセル処理がどのように変更されたかが明らかになります。

### 1. `Client.Timeout` の動作変更
以前の `Client.Timeout` は、`Transport` が `CancelRequest` メソッドを実装していることを前提としていました。タイムアウトが発生すると、`Client` は `Transport.CancelRequest` を呼び出してリクエストをキャンセルしようとしました。
このコミットでは、`Client.Timeout` は `Request.Cancel` チャネルを利用するように変更されます。`Client` は、タイムアウト期間が設定されている場合、内部的に `Request.Cancel` チャネルを作成し、そのチャネルをリクエストに設定します。そして、タイムアウト期間が経過するか、ユーザーが元々設定していた `Request.Cancel` チャネルがクローズされた場合に、この内部チャネルをクローズします。`RoundTripper` の実装（特に `http.Transport` や `http2.Transport`）は、この `Request.Cancel` チャネルを監視し、クローズされたときにリクエスト処理を中断します。

### 2. `send` 関数のシグネチャ変更と役割
`Client` の内部でリクエストを送信する主要な関数である `send` のシグネチャが変更されました。
変更前: `func send(req *Request, t RoundTripper) (resp *Response, err error)`
変更後: `func send(ireq *Request, rt RoundTripper, deadline time.Time) (*Response, error)`
新しい `deadline time.Time` 引数は、リクエストのタイムアウト期限を伝達するために使用されます。これにより、`send` 関数内でタイムアウト処理をより細かく制御できるようになります。

### 3. `setRequestCancel` 関数の導入
このコミットの核心的な変更の一つが `setRequestCancel` 関数の導入です。
```go
func setRequestCancel(req *Request, rt RoundTripper, deadline time.Time) (stopTimer func(), wasCanceled func() bool)
```
この関数は以下の役割を担います。
*   **`Request.Cancel` チャネルの設定**: `deadline` がゼロでない場合、新しい `chan struct{}` を作成し、`req.Cancel` に設定します。
*   **タイマーの起動**: `deadline` に基づいて `time.NewTimer` を起動します。
*   **キャンセルロジックの統合**: ゴルーチン内で以下のいずれかのイベントを待ち受けます。
    *   ユーザーが元々設定していた `req.Cancel` チャネルがクローズされた場合。
    *   タイマーが期限切れになった場合。
    *   `stopTimer` 関数が呼び出された場合（リクエストが正常に完了した場合）。
*   **`doCancel` 関数**: 上記のイベントのいずれかが発生した場合、`doCancel` 関数が呼び出されます。この関数は、新しい `req.Cancel` チャネルをクローズすることで、新しいキャンセルメカニズムをトリガーします。
*   **レガシー `CancelRequest` のサポート**: 互換性のために、`RoundTripper` が `*Transport` または `*http2Transport` でない場合、かつ `canceler` インターフェース（`CancelRequest(*Request)` メソッドを持つ）を実装している場合は、`v.CancelRequest(req)` も呼び出されます。これにより、古いカスタム `RoundTripper` 実装が引き続き機能するようになります。
*   **`stopTimer` と `wasCanceled` の返却**: `stopTimer` はリクエストが正常に完了した際にタイマーを停止するために使用され、`wasCanceled` はリクエストがキャンセルされたかどうかをチェックするために使用されます。

### 4. `cancelTimerBody` の変更
レスポンスボディの読み取り中にタイムアウトが発生した場合の処理を改善するために、`cancelTimerBody` 構造体も変更されました。以前は `*time.Timer` を直接保持していましたが、変更後は `stop func()` と `reqWasCanceled func() bool` を保持するようになりました。これにより、タイマーの停止とキャンセル状態のチェックがより抽象化され、`Request.Cancel` メカニズムと連携しやすくなります。

### 5. `http2.Transport` との連携
この変更により、`http2.Transport` は `CancelRequest` メソッドを実装する必要がなくなりました。`http2.Transport` は `Request.Cancel` チャネルを監視するだけでよくなり、HTTP/2の多重化の特性とより自然に統合されます。これにより、HTTP/2環境での `Client.Timeout` が正しく機能するようになります。

### 6. `cloneHeader` 関数の追加
`src/net/http/header.go` に `cloneHeader` 関数が追加されました。これは、リクエストヘッダーを安全にコピーするために使用されます。`send` 関数内でリクエストがフォークされる際に、元のリクエストのヘッダーを破壊しないように、ヘッダーのディープコピーが必要になるためです。

### 7. テストの有効化
`src/net/http/client_test.go` では、HTTP/2モードでの `TestClientTimeout_h2` および `TestClientTimeout_Headers_h2` テストが有効化されました。これは、このコミットによってHTTP/2環境でのタイムアウト処理が正しく機能するようになったことを示しています。

## コアとなるコードの解説

このコミットのコアとなる変更は、`net/http/client.go` 内の `send` 関数と新しく導入された `setRequestCancel` 関数に集約されています。

### `send` 関数の変更点と役割

```go
func send(ireq *Request, rt RoundTripper, deadline time.Time) (*Response, error) {
    req := ireq // req is either the original request, or a modified fork

    // ... (ヘッダー初期化、認証情報追加などの処理) ...

    if !deadline.IsZero() {
        forkReq() // タイムアウトが設定されている場合、リクエストをフォーク
    }
    stopTimer, wasCanceled := setRequestCancel(req, rt, deadline)

    resp, err := rt.RoundTrip(req)
    if err != nil {
        stopTimer() // エラーが発生した場合、タイマーを停止
        // ... (エラー処理) ...
    }
    if !deadline.IsZero() {
        resp.Body = &cancelTimerBody{
            stop:           stopTimer,
            rc:             resp.Body,
            reqWasCanceled: wasCanceled,
        }
    }
    return resp, nil
}
```
*   `send` 関数は、`ireq` (元のリクエスト)、`rt` (`RoundTripper`)、`deadline` (タイムアウト期限) を受け取るようになりました。
*   `forkReq()` は、リクエストのヘッダーや認証情報が変更される際に、元の `ireq` を変更しないように `req` をシャローコピーするヘルパー関数です。これにより、リクエストの不変性が保たれます。
*   `setRequestCancel` が呼び出され、リクエストのキャンセルチャネルとタイムアウトタイマーが設定されます。`stopTimer` と `wasCanceled` という2つの関数が返されます。
*   `rt.RoundTrip(req)` が実行され、実際のリクエストが送信されます。
*   `RoundTrip` がエラーを返した場合、`stopTimer()` が呼び出され、タイムアウトタイマーが停止されます。
*   タイムアウトが設定されている場合、レスポンスボディは `cancelTimerBody` でラップされます。これは、ボディの読み取り中にもタイムアウトを監視し、キャンセルされた場合に適切なエラーを返すためのものです。

### `setRequestCancel` 関数の詳細

```go
func setRequestCancel(req *Request, rt RoundTripper, deadline time.Time) (stopTimer func(), wasCanceled func() bool) {
    if deadline.IsZero() {
        return nop, alwaysFalse // タイムアウトがない場合は何もしない
    }

    initialReqCancel := req.Cancel // ユーザーが設定した元のRequest.Cancel

    cancel := make(chan struct{})
    req.Cancel = cancel // 新しいキャンセルチャネルをリクエストに設定

    wasCanceled = func() bool {
        select {
        case <-cancel:
            return true
        default:
            return false
        }
    }

    doCancel := func() {
        // 新しい方法: Request.Cancelチャネルをクローズ
        close(cancel)

        // レガシーな互換性維持のため: Transport.CancelRequestを呼び出す
        type canceler interface {
            CancelRequest(*Request)
        }
        switch v := rt.(type) {
        case *Transport, *http2Transport:
            // net/httpパッケージのトランスポートは新しいRequest.Cancelチャネルをサポート
        case canceler:
            v.CancelRequest(req) // 古いRoundTripper実装向け
        }
    }

    stopTimerCh := make(chan struct{})
    var once sync.Once
    stopTimer = func() { once.Once(func() { close(stopTimerCh) }) }

    timer := time.NewTimer(deadline.Sub(time.Now()))
    go func() {
        select {
        case <-initialReqCancel: // ユーザーが元のチャネルをクローズした場合
            doCancel()
        case <-timer.C: // タイムアウトした場合
            doCancel()
        case <-stopTimerCh: // リクエストが正常に完了した場合
            timer.Stop()
        }
    }()

    return stopTimer, wasCanceled
}
```
*   この関数は、`Client.Timeout` のロジックと `Request.Cancel` のメカニズムを統合する中心的な役割を担います。
*   `req.Cancel` に新しいチャネルを設定し、元の `req.Cancel` (もしあれば) を `initialReqCancel` として保存します。
*   `doCancel` 関数は、新しい `req.Cancel` チャネルをクローズし、さらに互換性のために `Transport.CancelRequest` を呼び出すロジックを含んでいます。ただし、`http.Transport` や `http2.Transport` のような標準のトランスポートでは、`Request.Cancel` のみを監視するため、`CancelRequest` は呼び出されません。
*   ゴルーチン内で `select` ステートメントを使用し、`initialReqCancel` がクローズされるか、`timer` が期限切れになるか、`stopTimerCh` がクローズされるのを待ちます。
*   `initialReqCancel` または `timer` がトリガーされた場合、`doCancel()` が呼び出され、リクエストがキャンセルされます。
*   `stopTimerCh` がトリガーされた場合（リクエストが正常に完了した場合）、`timer.Stop()` が呼び出され、リソースリークを防ぎます。

これらの変更により、`Client.Timeout` は `Request.Cancel` を介してリクエストをキャンセルするようになり、HTTP/2を含むすべての `RoundTripper` 実装で一貫した動作が保証されるようになりました。また、レガシーな `Transport.CancelRequest` を使用するカスタム `RoundTripper` との互換性も維持されています。

# [インデックス 25805] ファイルの概要

このコミットは、Goコンパイラ（`cmd/compile`）における重要な変更、すなわちYaccベースのパーサーの削除と、それに伴う手書きパーサーへの移行を記録しています。これにより、コンパイラのビルドプロセスが簡素化され、パーサーの保守性と理解度が向上しました。

## 元コミット内容

このコミットの元の内容は、Goコンパイラ（`cmd/compile`）からYaccベースのパーサーを完全に削除することです。具体的には以下の変更が含まれます。

*   `yySymType` およびトークン定数（`L...`で始まるもの）を `lex.go` へ移動。
*   `oldparser` フラグおよび関連コードの削除。
*   `y.go` を生成していた `go generate` コマンドの削除。

この変更は、Go言語のパーサーがYaccのようなパーサー生成ツールに依存するのではなく、手書きの再帰下降型パーサーに移行したことを示しています。

## 変更の背景

Goコンパイラの初期バージョンでは、構文解析にYacc（Yet Another Compiler Compiler）というパーサー生成ツールが使用されていました。YaccはBNF（Backus-Naur Form）形式の文法定義からC言語のパーサーコードを自動生成するツールで、複雑なプログラミング言語の構文解析器を効率的に作成するのに役立ちます。

しかし、Yaccベースのパーサーにはいくつかの課題がありました。

1.  **可読性と保守性:** 生成されたコードは人間が直接読むことを意図していないため、デバッグや変更が困難でした。Go言語のコンパイラ開発者は、Go言語自体で書かれたコードを好む傾向があり、Yaccの生成コードはGoのイディオムに沿わないものでした。
2.  **ビルドプロセスの複雑化:** Yaccを使用すると、コンパイラのビルドプロセスにYaccの実行ステップが追加され、ビルドが複雑になります。`go generate` コマンドで `y.go` ファイルを生成する必要がありました。
3.  **エラーメッセージの改善:** Yaccベースのパーサーは、構文エラーが発生した際に詳細で分かりやすいエラーメッセージを生成するのが難しい場合があります。手書きパーサーは、よりきめ細やかなエラーハンドリングとメッセージ生成を実装する柔軟性を提供します。
4.  **Go言語の進化:** Go言語自体が進化し、より複雑な構文要素が導入されるにつれて、Yaccの制約が顕在化してきた可能性があります。手書きパーサーは、Go言語の特定の構文規則（特にセミコロン挿入規則など）をより自然に処理できる場合があります。

これらの背景から、GoコンパイラチームはYaccベースのパーサーから手書きパーサーへの移行を決定しました。このコミットは、その移行プロセスの最終段階の一つであり、Yacc関連のコードを完全に削除するものです。関連するIssue #13240 "cmd/compile: remove yacc-based parser" は、この変更の目的を明確に示しています。

## 前提知識の解説

このコミットを理解するためには、以下の概念に関する知識が役立ちます。

### 1. コンパイラの構造

コンパイラは通常、以下の主要なフェーズで構成されます。

*   **字句解析 (Lexical Analysis):** ソースコードをトークン（意味のある最小単位）のストリームに変換します。このフェーズを担当するプログラムを「字句解析器 (Lexer)」または「スキャナー (Scanner)」と呼びます。
*   **構文解析 (Syntactic Analysis):** トークンのストリームが言語の文法規則に準拠しているかを検証し、抽象構文木 (AST: Abstract Syntax Tree) を構築します。このフェーズを担当するプログラムを「構文解析器 (Parser)」と呼びます。
*   **意味解析 (Semantic Analysis):** ASTに対して型チェックや名前解決などの意味的な検証を行います。
*   **中間コード生成 (Intermediate Code Generation):** 抽象構文木を、ターゲットマシンに依存しない中間表現に変換します。
*   **コード最適化 (Code Optimization):** 中間コードを最適化し、実行効率を向上させます。
*   **コード生成 (Code Generation):** 最適化された中間コードを、ターゲットマシン固有の機械語コードに変換します。

このコミットは、主に字句解析と構文解析のフェーズに影響を与えます。

### 2. Yacc (Yet Another Compiler Compiler)

Yaccは、LALR(1)パーサーを生成するためのツールです。

*   **文法定義:** 開発者はBNF（バッカス・ナウア記法）に似た形式で言語の文法規則を定義します。
*   **パーサー生成:** Yaccは、この文法定義を読み込み、C言語（または他の言語）で書かれた構文解析器のソースコードを自動生成します。
*   **シフト・リデュース解析:** Yaccが生成するパーサーは、シフト・リデュース解析という手法を用いて構文解析を行います。これは、入力トークンをスタックに「シフト」したり、スタック上のトークン列を文法規則に従って「リデュース」したりすることで、構文木を構築します。
*   **`go.y` ファイル:** Goコンパイラでは、Go言語の文法定義が `go.y` というファイルに記述されていました。

### 3. 手書きパーサー (Hand-written Parser)

Yaccのようなツールを使わずに、プログラマーが直接コードを書いて実装するパーサーです。

*   **再帰下降型パーサー (Recursive Descent Parser):** 最も一般的な手書きパーサーの実装方法の一つです。文法の非終端記号ごとに、その記号を解析する関数を作成し、関数が再帰的に他の解析関数を呼び出すことで構文解析を進めます。
*   **LL(1)パーサー:** 再帰下降型パーサーは通常、LL(1)文法（左から右へ読み込み、左端導出を行い、1トークンの先読みで決定できる文法）を解析できます。
*   **柔軟性:** エラーリカバリ、エラーメッセージのカスタマイズ、特定の構文規則（Goのセミコロン挿入など）の処理において、パーサー生成ツールよりも高い柔軟性を提供します。
*   **Go言語のパーサー:** Goコンパイラの新しいパーサーは、手書きの再帰下降型パーサーとして `parser.go` に実装されています。

### 4. Goの `go generate` コマンド

`go generate` は、Goのソースファイルに記述された特別なコメント（`//go:generate`）に基づいて、コード生成ツールを実行するためのコマンドです。Yaccベースのパーサーでは、`go.y` から `y.go` を生成するためにこのコマンドが使用されていました。

### 5. `yySymType` とトークン定数

Yaccが生成するパーサーでは、`yySymType` という構造体が、各トークンや非終端記号に関連付けられたセマンティックな値（例えば、識別子の名前、リテラルの値など）を保持するために使用されます。また、`L...` で始まる定数は、字句解析器が識別するトークンの種類を表すために使用されていました。

## 技術的詳細

このコミットの技術的詳細は、Goコンパイラのフロントエンドにおける根本的な変更にあります。

1.  **Yaccパーサーの完全削除:**
    *   `src/cmd/compile/internal/gc/go.y` ファイルが削除されました。このファイルはGo言語の文法をYacc形式で定義しており、Goコンパイラの構文解析の中核をなしていました。
    *   `src/cmd/compile/internal/gc/y.go` ファイルも削除されました。これは `go.y` からYaccによって自動生成されたパーサーの実装コードでした。この2つのファイルの削除は、Yaccへの依存が完全に解消されたことを意味します。

2.  **手書きパーサーへの移行:**
    *   既存の `src/cmd/compile/internal/gc/parser.go` および `src/cmd/compile/internal/gc/lex.go` ファイルが更新されました。これらのファイルは、Yaccに依存しない手書きの字句解析器と構文解析器の実装を含んでいます。
    *   `lex.go` には、Yaccパーサーが使用していた `yySymType` 構造体と、`L...` 形式のトークン定数が移動されました。これは、字句解析器が生成するトークンの種類と、それに関連するセマンティックな情報を管理するためのものです。Yaccの生成コードがなくなったため、これらの定義は手書きパーサーが直接利用できるように再配置されました。
    *   `parser.go` は、Go言語の文法を再帰下降型で解析するロジックを実装しています。このファイルは、Go言語の構文規則を直接Goコードで表現しており、Yaccの文法定義よりもGo開発者にとって理解しやすい形式になっています。

3.  **ビルドプロセスの簡素化:**
    *   `go generate` コマンドが `y.go` を生成する必要がなくなったため、コンパイラのビルドプロセスからYaccの実行ステップが削除されました。これにより、ビルド時間が短縮され、ビルド環境の依存関係が減少しました。
    *   `oldparser` フラグや関連コードの削除は、Yaccベースのパーサーと新しいパーサーを切り替えるためのメカニズムが不要になったことを意味します。これは、移行が完了し、新しいパーサーが唯一の標準実装となったことを示しています。

4.  **Go言語のイディオムへの適合:**
    *   手書きパーサーはGo言語で書かれているため、Goのコーディングスタイル、エラーハンドリング、テスト手法に直接適合します。これにより、コンパイラのフロントエンドの保守性が大幅に向上しました。
    *   Goのセミコロン自動挿入規則のような、Yaccでは扱いにくい特定のGo構文規則も、手書きパーサーではより自然に、かつ正確に実装できるようになります。

この変更は、Goコンパイラの長期的な健全性と開発効率にとって非常に重要であり、Go言語の設計哲学である「シンプルさ」と「実用性」をコンパイラの実装レベルでも追求した結果と言えます。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更箇所は以下のファイルに集中しています。

1.  **`src/cmd/compile/internal/gc/go.y` (削除)**
    *   Go言語の文法定義が記述されていたYaccの入力ファイル。このファイルの削除は、Yaccベースのパーサーが完全に廃止されたことを意味します。

2.  **`src/cmd/compile/internal/gc/y.go` (削除)**
    *   `go.y` からYaccによって自動生成されていたパーサーのGoコード。このファイルの削除は、自動生成されたパーサーコードへの依存がなくなったことを意味します。

3.  **`src/cmd/compile/internal/gc/lex.go` (変更)**
    *   字句解析器の実装ファイル。
    *   Yaccパーサーが使用していた `yySymType` 構造体や、`L...` で始まるトークン定数（例: `LLITERAL`, `LBREAK`, `LFUNC` など）が、このファイルに移動または再定義されました。これにより、手書きパーサーがこれらのトークン情報を直接利用できるようになります。
    *   `yylex` 関数（Yaccパーサーの字句解析器インターフェース）に関連するコードが削除され、手書きパーサーが使用する新しい字句解析ロジックが統合されたか、既存のロジックが適応されました。

4.  **`src/cmd/compile/internal/gc/parser.go` (変更)**
    *   手書きの構文解析器の実装ファイル。
    *   Yaccベースのパーサーが削除されたことで、Go言語の構文解析ロジックがこのファイルに集約され、再帰下降型パーサーとして実装されました。
    *   `parseFile` や `parseDecl` といった関数が、Goの文法規則に従ってトークンを消費し、抽象構文木を構築する役割を担うようになりました。

5.  **`src/cmd/compile/internal/gc/go.go` (変更)**
    *   コンパイラのメインエントリポイントやグローバル変数定義を含むファイル。
    *   `typesw *Node // TODO(gri) remove when yacc-based parser is gone` のような、Yaccパーサーに関連するコメントや変数が削除されました。これは、Yaccパーサーの廃止が完了したことを示すクリーンアップです。

6.  **`src/cmd/compile/internal/gc/subr.go` (変更)**
    *   補助的なルーチンやユーティリティ関数を含むファイル。
    *   Yaccパーサーに関連する小さな関数や参照が削除された可能性があります。

これらの変更は、Goコンパイラの構文解析部分が、外部ツールへの依存からGo言語自身による手書き実装へと完全に移行したことを明確に示しています。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラの構文解析エンジンをYacc生成コードから手書きのGoコードに置き換えることです。

**`go.y` と `y.go` の削除:**
最も顕著な変更は、`go.y` と `y.go` の削除です。
*   `go.y` はGo言語の文法をYaccの形式で定義していました。このファイルには、Goのキーワード、演算子、識別子、リテラルなどのトークン定義、およびそれらがどのように組み合わされてGoのプログラム構造（パッケージ、インポート、関数、変数宣言、ステートメント、式など）を形成するかという規則が記述されていました。
*   `y.go` は、`go.y` をYaccツールで処理することで自動生成されるGoのソースファイルでした。このファイルには、Yaccのパーシングテーブル、状態遷移ロジック、およびセマンティックアクション（文法規則がマッチしたときに実行されるGoコード）が含まれていました。このコードは非常に機械的で、人間が直接理解したりデバッグしたりするのは困難でした。

これらのファイルの削除は、GoコンパイラがYaccという外部ツールへの依存を完全に断ち切り、パーサーの生成ステップをビルドプロセスから排除したことを意味します。

**`lex.go` の変更:**
`lex.go` は字句解析器（lexer）を実装しています。Yaccベースのパーサーでは、字句解析器はYaccが要求する形式でトークンを供給する必要がありました。このコミットでは、`yySymType` 構造体（Yaccがトークンのセマンティック値を保持するために使用）や、`L...` で始まるトークン定数（Yaccが生成するパーサーが内部的に使用するトークンID）が、Yaccのコンテキストから切り離され、手書きパーサーが直接利用できる形で `lex.go` 内に再配置されました。これにより、字句解析器は手書きパーサーと直接連携し、Goの構文解析に必要なトークンを生成する役割を担います。

**`parser.go` の変更:**
`parser.go` は、Go言語の構文解析の中核を担う手書きの再帰下降型パーサーを実装しています。このファイルには、Goの文法規則に対応する一連の関数が含まれています。例えば、`parseFile` はファイル全体を解析し、`parseDecl` は宣言を解析し、`parseStmt` はステートメントを解析するといった具合です。これらの関数は、`lex.go` からトークンを読み込み、文法規則に従ってそれらを消費し、最終的に抽象構文木（AST）を構築します。

手書きパーサーの利点は、Goの特定の構文規則（例えば、セミコロン自動挿入規則）をより柔軟かつ正確に処理できる点にあります。Yaccのようなツールは一般的な文法規則には強いですが、言語固有の特殊な規則を扱う際には複雑な回避策が必要になることがあります。手書きパーサーは、これらの特殊なケースをGoのコードとして直接、かつイディオム的に実装できるため、コードの可読性と保守性が向上します。

**`go.go` および `subr.go` の変更:**
これらのファイルでは、Yaccパーサーに関連する古い参照、フラグ、およびコメントが削除されました。これは、Yaccパーサーの廃止がシステム全体で完了し、関連するデッドコードがクリーンアップされたことを示しています。特に `oldparser` フラグの削除は、もはや古いパーサーと新しいパーサーを切り替える必要がなく、新しい手書きパーサーが唯一の標準実装となったことを明確にしています。

全体として、このコミットはGoコンパイラのフロントエンドをよりGoらしい、より保守しやすい形に進化させるための重要なマイルストーンであり、コンパイラの内部構造の理解を深める上で大きな意味を持ちます。

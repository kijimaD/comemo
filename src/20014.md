## 変更の背景

このコミットは、Go言語の`cgo`ツールがC言語の関数ポインタをGoのコードに公開する際に発生していた潜在的な問題に対処しています。具体的には、Goコード内でC言語の関数ポインタが通常のGo変数のように代入可能であったことが問題でした。

Goのランタイムとガベージコレクタは、Goのポインタとメモリ管理に厳密なルールを持っています。一方、C言語のポインタはGoのメモリ管理モデルとは異なるセマンティクスを持ちます。C言語の関数ポインタをGoの変数として直接代入可能にしてしまうと、Goの型システムやメモリ管理の期待とCのポインタの実際の動作との間に不整合が生じ、予期せぬ動作、クラッシュ、または未定義の振る舞いを引き起こす可能性がありました。

コミットメッセージで参照されている`#7757`と`#8488`は、この問題に関連するバグ報告や議論であったと考えられます。これらの問題は、C関数ポインタがGoコード内で誤って扱われることを防ぐ必要性を示唆していました。この変更の目的は、C関数ポインタをGoコード内で「値」としてのみ参照可能にし、その「アドレス」や「参照」を直接変更（代入）できないようにすることで、Goのランタイムの整合性を保ち、安全性を向上させることにあります。

## 前提知識の解説

### cgo

`cgo`は、GoプログラムがC言語のコードを呼び出すことを可能にするGoツールチェーンの一部です。GoとCの間の相互運用性を提供し、既存のCライブラリをGoから利用したり、パフォーマンスが重要な部分をCで記述したりする際に使用されます。

`cgo`を使用するGoファイルでは、特別な`import "C"`という宣言と、その直前のコメントブロックにC言語のコードを記述します。`cgo`ツールは、これらのCコードとGoコードを結合し、GoからC関数を呼び出したり、CからGo関数を呼び出したりするための接着コードを生成します。

### C言語の関数ポインタ

C言語において、関数ポインタは関数を指すポインタ変数です。これにより、関数を引数として渡したり、変数に格納したり、データ構造に埋め込んだりすることが可能になります。例えば、コールバック関数を実装する際によく使用されます。

```c
// C言語の関数ポインタの例
void (*myFunctionPtr)(int); // intを引数にとり、voidを返す関数へのポインタ
```

### Go言語の型システムとポインタ

Go言語は、C言語とは異なる独自の型システムとメモリ管理（ガベージコレクション）を持っています。Goのポインタは、Goのランタイムによって管理されるメモリ領域を指します。Goのガベージコレクタは、メモリを移動させることがあるため、C言語のポインタがGoの管理するメモリを直接指す場合、そのポインタが無効になる可能性があります。

`cgo`は、Cの型をGoの型にマッピングしますが、Cの関数ポインタのような複雑な型の場合、Goの型システムに直接対応するものが存在しないことがあります。このため、`cgo`はCの関数ポインタをGo側では`unsafe.Pointer`や特定の構造体として表現することがあります。

### 代入可能性と式の評価

プログラミング言語において、変数は値を保持し、その値は代入演算子（`=`）によって変更できます。一方、式は評価されると値を生成しますが、それ自体は代入の左辺には来ることができません。例えば、`x = 1 + 2`では`x`は変数で代入可能ですが、`1 + 2 = 5`のような記述はできません。

このコミットの変更は、C関数ポインタがGoコード内で「代入可能な変数」として扱われることを防ぎ、「評価されるとC関数ポインタの値を生成する式」としてのみ扱われるようにすることで、Goの型システムとCのポインタのセマンティクスとの間の不整合を解消しようとしています。

## 技術的詳細

このコミットの核心的な変更は、`cgo`がC言語の関数ポインタをGoコードに公開する際に、その参照を`_Cgo_ptr`というヘルパー関数でラップするようにした点です。

以前の`cgo`では、C言語の関数ポインタ（例えば`C.foo`）は、Goコード内で直接識別子として扱われ、代入の左辺に置くことが可能でした。これは、Goの型システムがCの関数ポインタを適切に「代入不可能」なものとして扱っていなかったためです。

この変更により、`cgo`は`C.foo`のようなC関数ポインタの参照を、`_Cgo_ptr(C.foo)`という形式の関数呼び出しに変換します。

`_Cgo_ptr`関数は、`src/cmd/cgo/out.go`で以下のように定義されています。

```go
func _Cgo_ptr(ptr unsafe.Pointer) unsafe.Pointer { return ptr }
```

この関数は、`unsafe.Pointer`型の引数を受け取り、その引数をそのまま返します。一見すると何もしない関数に見えますが、重要なのはその「関数呼び出し」という性質です。

Go言語において、関数呼び出しの結果は「式」であり、通常は代入の左辺に置くことができません。例えば、`f() = value`のようなコードはGoではコンパイルエラーになります。この性質を利用して、`_Cgo_ptr(C.foo)`という形式に変換することで、`C.foo = C.bar`のようなC関数ポインタへの直接的な代入をコンパイル時にエラーとして検出できるようになります。

これにより、GoのコンパイラはC関数ポインタへの不適切な代入を検出し、開発者に警告を与えることができます。これは、Goの型安全性を高め、CGOを使用する際の潜在的なバグを防ぐための重要なステップです。

## コアとなるコードの解説

### `src/cmd/cgo/gcc.go`の変更

`rewriteRef`関数は、Cの識別子（変数、関数など）がGoコード内でどのように表現されるかを決定します。変更前のコードでは、Cの関数ポインタ（`r.Name`が関数ポインタを表す場合）は単に`ast.NewIdent(name.Mangle)`としてGoの識別子に変換されていました。これにより、Goコード内で`C.foo`のようなC関数ポインタが通常の変数識別子のように扱われ、代入可能になっていました。

変更後のコードでは、C関数ポインタの場合に`ast.NewIdent(name.Mangle)`を直接使用する代わりに、`ast.CallExpr`（関数呼び出しを表す抽象構文木ノード）を構築しています。この`CallExpr`は、`_Cgo_ptr`という関数を呼び出し、その引数として元のC関数ポインタのGo識別子（`ast.NewIdent(name.Mangle)`）を渡します。

この変換により、Goコード内でC関数ポインタを参照する箇所はすべて`_Cgo_ptr(C.foo)`のような形式になります。Goのコンパイラは関数呼び出しの結果を代入の左辺に置くことを許可しないため、`C.foo = C.bar`のような代入はコンパイルエラーとなります。これにより、C関数ポインタへの不適切な代入が防止されます。

コメントにもあるように、この変更は`issue 7757`を修正するために行われました。

### `src/cmd/cgo/out.go`の変更

このファイルでは、`_Cgo_ptr`という新しいヘルパー関数が追加されています。

```go
func _Cgo_ptr(ptr unsafe.Pointer) unsafe.Pointer { return ptr }
```

この関数は、`unsafe.Pointer`型の引数`ptr`を受け取り、その`ptr`をそのまま返します。この関数の目的は、値を変更することではなく、Goの型システムに「これは関数呼び出しの結果である」と認識させることにあります。これにより、`gcc.go`での変換が意図した通りに機能し、C関数ポインタへの代入が禁止されます。

以前の`type _ unsafe.Pointer`という行は、おそらく`cgo`が生成するGoコード内で`unsafe.Pointer`型を使用するためのプレースホルダー的な宣言だったと考えられます。このコミットでは、その行が`_Cgo_ptr`関数の定義に置き換えられています。

## コアとなるコードの解説

### `src/cmd/cgo/gcc.go`の変更

`rewriteRef`関数は、Cの識別子（変数、関数など）がGoコード内でどのように表現されるかを決定します。変更前のコードでは、Cの関数ポインタ（`r.Name`が関数ポインタを表す場合）は単に`ast.NewIdent(name.Mangle)`としてGoの識別子に変換されていました。これにより、Goコード内で`C.foo`のようなC関数ポインタが通常の変数識別子のように扱われ、代入可能になっていました。

変更後のコードでは、C関数ポインタの場合に`ast.NewIdent(name.Mangle)`を直接使用する代わりに、`ast.CallExpr`（関数呼び出しを表す抽象構文木ノード）を構築しています。この`CallExpr`は、`_Cgo_ptr`という関数を呼び出し、その引数として元のC関数ポインタのGo識別子（`ast.NewIdent(name.Mangle)`）を渡します。

この変換により、Goコード内でC関数ポインタを参照する箇所はすべて`_Cgo_ptr(C.foo)`のような形式になります。Goのコンパイラは関数呼び出しの結果を代入の左辺に置くことを許可しないため、`C.foo = C.bar`のような代入はコンパイルエラーとなります。これにより、C関数ポインタへの不適切な代入が防止されます。

コメントにもあるように、この変更は`issue 7757`を修正するために行われました。

### `src/cmd/cgo/out.go`の変更

このファイルでは、`_Cgo_ptr`という新しいヘルパー関数が追加されています。

```go
func _Cgo_ptr(ptr unsafe.Pointer) unsafe.Pointer { return ptr }
```

この関数は、`unsafe.Pointer`型の引数`ptr`を受け取り、その`ptr`をそのまま返します。この関数の目的は、値を変更することではなく、Goの型システムに「これは関数呼び出しの結果である」と認識させることにあります。これにより、`gcc.go`での変換が意図した通りに機能し、C関数ポインタへの代入が禁止されます。

以前の`type _ unsafe.Pointer`という行は、おそらく`cgo`が生成するGoコード内で`unsafe.Pointer`型を使用するためのプレースホルダー的な宣言だったと考えられます。このコミットでは、その行が`_Cgo_ptr`関数の定義に置き換えられています。

# [インデックス 24050] ファイルの概要

このコミットは、Goリンカ（`cmd/link`）において、データセグメントのサイズが2GBを超える場合にリンクを拒否する機能を追加します。これは、`amd64`アーキテクチャ上でのGoリンカの内部的な制約により、2GBを超えるデータサイズを適切にアドレス指定できない問題に対処するためのものです。具体的には、シンボルのサイズが負の場合、個々のシンボルが2GBを超える場合、またはシンボルを追加した結果データセグメント全体のサイズが2GBを超える場合にエラーを発生させます。

## 変更の背景

この変更の背景には、Goリンカ（`cmd/link`）が`amd64`アーキテクチャ上で2GBを超えるデータセグメントを正しく処理できないという技術的な制約があります。コミットメッセージにある「We can't address more than this on amd64 anyway.」という記述は、Goリンカの内部実装、特にデータサイズを管理する部分において、符号付き32ビット整数に起因する制限が存在することを示唆しています。

もしリンカが2GBを超えるデータセグメントを持つプログラムを生成しようとすると、アドレス計算のオーバーフローや不正確なメモリ配置が発生し、結果としてプログラムのクラッシュや予期せぬ動作を引き起こす可能性があります。このコミットは、このような潜在的な問題を未然に防ぐために、リンカの段階で明示的に2GBの制限を設けることを目的としています。これにより、開発者はリンカが処理できないほど大きなデータセグメントを作成しようとした際に、早期にエラーとして検知できるようになります。

また、`Fixes #9862`という記述から、この問題が以前から認識されており、特定のイシューとして追跡されていたことが伺えます。このコミットはそのイシューに対する直接的な解決策として導入されました。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

*   **Goリンカ (`cmd/link`)**: Go言語のビルドプロセスにおいて、コンパイルされたオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合し、実行可能なバイナリファイルを生成するツールです。プログラム内の関数、変数、データなどを適切なメモリ位置に配置し、参照を解決する役割を担います。
*   **データセグメント (Data Segment)**: 実行可能ファイル内のメモリ領域の一つで、初期化されたグローバル変数や静的変数が格納されます。プログラムの実行開始時にこれらのデータがメモリにロードされます。
*   **`amd64`アーキテクチャ**: 64ビットの命令セットアーキテクチャであり、理論上は非常に広大なアドレス空間（最大16エクサバイト）を扱えます。しかし、ソフトウェアの実装によっては、特定のデータ構造やAPIが32ビットの制限（例えば、符号付き32ビット整数で表現できる最大値は約2GB）を持つことがあります。Goリンカのこの制限は、`amd64`のハードウェア的な能力ではなく、リンカの内部的な設計やデータ型選択に起因する可能性が高いです。
*   **`LSym`構造体**: Goリンカの内部で、プログラム内のシンボル（関数、変数など）を表すために使用されるデータ構造です。各`LSym`は、シンボルの名前、サイズ、タイプ、アドレスなどの情報を含んでいます。このコミットでは、`LSym.Size`フィールドが特に重要になります。
*   **`Diag`関数**: Goリンカの内部でエラーメッセージを出力するために使用される関数です。リンカが致命的な問題に遭遇した場合、この関数を呼び出してエラーを報告し、リンク処理を中断します。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/link/internal/ld/data.go`ファイル内の`growdatsize`関数にあります。この関数は、新しいシンボルをデータセグメントに追加する際に、データセグメントの合計サイズを更新し、その過程でサイズに関する整合性チェックを行う役割を担っています。

変更前は、`growdatsize`関数は主に以下の2つのチェックを行っていました。
1.  シンボルのサイズが負でないか (`s.Size < 0`)。
2.  データセグメントの合計サイズがオーバーフローしないか (`datsize+s.Size < datsize`)。これは、`datsize`と`s.Size`が符号なし整数として扱われる場合に、合計が最大値を超えてゼロに戻る（ラップアラウンドする）ことを検出するためのチェックです。

このコミットでは、これらのチェックに加えて、2GBのサイズ制限を導入しています。具体的には、`const cutoff int64 = 2e9`という定数を導入し、これを2GBの閾値として使用します（厳密には2 * 10^9バイトであり、2^31バイトとは異なりますが、エラーメッセージでの視認性を考慮した値です）。

新しい`switch`文が導入され、以下の3つのケースでエラーを報告するようになりました。

1.  **`s.Size < 0`**: シンボルのサイズが負の場合。これは既存のチェックと同じですが、エラーメッセージがより詳細になりました。
2.  **`s.Size > cutoff`**: 個々のシンボルが`cutoff`（約2GB）を超えるサイズを持つ場合。
3.  **`datsize <= cutoff && datsize+s.Size > cutoff`**: 現在のデータセグメントの合計サイズが`cutoff`以下であるにもかかわらず、新しいシンボルを追加すると合計サイズが`cutoff`を超える場合。これは、データセグメント全体のサイズが2GBを超えることを防ぐためのチェックです。

これらのチェックにより、リンカは2GBを超えるデータセグメントを持つ実行可能ファイルを生成しようとする試みを早期に検出し、適切なエラーメッセージを出力してリンク処理を中断するようになります。

また、この変更を検証するために、`test/fixedbugs/issue9862.go`と`test/fixedbugs/issue9862_run.go`という2つの新しいテストファイルが追加されました。
*   `issue9862.go`は、`[1<<31 - 1024]byte`という非常に大きなバイト配列を定義することで、2GBを超えるデータセグメントを意図的に作成しようとします。
*   `issue9862_run.go`は、`go run issue9862.go`を実行し、リンカが「symbol too large」というエラーメッセージを出力して失敗することを期待するテストスクリプトです。これにより、新しいサイズチェックが正しく機能していることが確認されます。

## コアとなるコードの解説

変更の中心は`growdatsize`関数です。この関数は、リンカがデータセグメントのサイズを計算し、新しいシンボル（`s *LSym`）を追加する際に呼び出されます。

```go
func growdatsize(datsizep *int64, s *LSym) {
	datsize := *datsizep
	const cutoff int64 = 2e9 // 2 GB (or so; looks better in errors than 2^31)
	switch {
	case s.Size < 0:
		Diag("%s: negative size (%d bytes)", s.Name, s.Size)
	case s.Size > cutoff:
		Diag("%s: symbol too large (%d bytes)", s.Name, s.Size)
	case datsize <= cutoff && datsize+s.Size > cutoff:
		Diag("%s: too much data (over %d bytes)", s.Name, cutoff)
	}
	*datsizep = datsize + s.Size
}
```

1.  **`datsize := *datsizep`**: 現在のデータセグメントの合計サイズを`datsize`変数にコピーします。`datsizep`はポインタなので、その指す値を取得します。
2.  **`const cutoff int64 = 2e9`**: 新しい定数`cutoff`が導入されました。これは`int64`型で、値は`2e9`、つまり2 * 10^9バイト（2ギガバイト）です。この値は、リンカが許容するデータセグメントの最大サイズを定義します。コメントにあるように、これは厳密な2^31バイト（約2.147GB）ではありませんが、エラーメッセージでの表示を考慮した近似値です。
3.  **`switch`文**: 複数の条件をチェックするための`switch`文が導入されました。
    *   **`case s.Size < 0:`**: シンボル`s`のサイズ（`s.Size`）が負の値である場合にマッチします。これは不正な状態であり、`Diag`関数を呼び出してエラーメッセージ「`%s: negative size (%d bytes)`」を出力し、リンカを停止させます。`%s`にはシンボル名が、`%d`には負のサイズが挿入されます。
    *   **`case s.Size > cutoff:`**: 個々のシンボル`s`のサイズが`cutoff`（約2GB）を超える場合にマッチします。これもリンカの制約を超えるため、`Diag`関数を呼び出してエラーメッセージ「`%s: symbol too large (%d bytes)`」を出力し、リンカを停止させます。
    *   **`case datsize <= cutoff && datsize+s.Size > cutoff:`**: 現在のデータセグメントの合計サイズ`datsize`が`cutoff`以下であるにもかかわらず、新しいシンボル`s`のサイズを`datsize`に加算すると、合計が`cutoff`を超える場合にマッチします。これは、データセグメント全体のサイズが2GBの制限を超えることを意味するため、`Diag`関数を呼び出してエラーメッセージ「`%s: too much data (over %d bytes)`」を出力し、リンカを停止させます。
4.  **`*datsizep = datsize + s.Size`**: すべてのチェックを通過した場合、新しいシンボルのサイズを現在のデータセグメントの合計サイズに加算し、その結果を`datsizep`が指すメモリ位置に書き戻します。

この変更により、Goリンカはデータセグメントのサイズに関する厳格なチェックを行うようになり、`amd64`環境での潜在的な問題を未然に防ぐことができます。

## コアとなるコードの解説

変更の中心は`growdatsize`関数です。この関数は、リンカがデータセグメントのサイズを計算し、新しいシンボル（`s *LSym`）を追加する際に呼び出されます。

```go
func growdatsize(datsizep *int64, s *LSym) {
	datsize := *datsizep
	const cutoff int64 = 2e9 // 2 GB (or so; looks better in errors than 2^31)
	switch {
	case s.Size < 0:
		Diag("%s: negative size (%d bytes)", s.Name, s.Size)
	case s.Size > cutoff:
		Diag("%s: symbol too large (%d bytes)", s.Name, s.Size)
	case datsize <= cutoff && datsize+s.Size > cutoff:
		Diag("%s: too much data (over %d bytes)", s.Name, cutoff)
	}
	*datsizep = datsize + s.Size
}
```

1.  **`datsize := *datsizep`**: 現在のデータセグメントの合計サイズを`datsize`変数にコピーします。`datsizep`はポインタなので、その指す値を取得します。
2.  **`const cutoff int64 = 2e9`**: 新しい定数`cutoff`が導入されました。これは`int64`型で、値は`2e9`、つまり2 * 10^9バイト（2ギガバイト）です。この値は、リンカが許容するデータセグメントの最大サイズを定義します。コメントにあるように、これは厳密な2^31バイト（約2.147GB）ではありませんが、エラーメッセージでの表示を考慮した近似値です。
3.  **`switch`文**: 複数の条件をチェックするための`switch`文が導入されました。
    *   **`case s.Size < 0:`**: シンボル`s`のサイズ（`s.Size`）が負の値である場合にマッチします。これは不正な状態であり、`Diag`関数を呼び出してエラーメッセージ「`%s: negative size (%d bytes)`」を出力し、リンカを停止させます。`%s`にはシンボル名が、`%d`には負のサイズが挿入されます。
    *   **`case s.Size > cutoff:`**: 個々のシンボル`s`のサイズが`cutoff`（約2GB）を超える場合にマッチします。これもリンカの制約を超えるため、`Diag`関数を呼び出してエラーメッセージ「`%s: symbol too large (%d bytes)`」を出力し、リンカを停止させます。
    *   **`case datsize <= cutoff && datsize+s.Size > cutoff:`**: 現在のデータセグメントの合計サイズ`datsize`が`cutoff`以下であるにもかかわらず、新しいシンボル`s`のサイズを`datsize`に加算すると、合計が`cutoff`を超える場合にマッチします。これは、データセグメント全体のサイズが2GBの制限を超えることを意味するため、`Diag`関数を呼び出してエラーメッセージ「`%s: too much data (over %d bytes)`」を出力し、リンカを停止させます。
4.  **`*datsizep = datsize + s.Size`**: すべてのチェックを通過した場合、新しいシンボルのサイズを現在のデータセグメントの合計サイズに加算し、その結果を`datsizep`が指すメモリ位置に書き戻します。

この変更により、Goリンカはデータセグメントのサイズに関する厳格なチェックを行うようになり、`amd64`環境での潜在的な問題を未然に防ぐことができます。

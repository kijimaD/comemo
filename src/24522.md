## 元コミット内容

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおけるスケジューラの問題を修正します。以前のDFS（深さ優先探索）ベースのスケジューラは、ある値 `x` が複数の他の値（例えば `y` と `z`）によって使用される場合に、依存関係を正しく処理できませんでした。具体的には、`y` が `x` を使用する際に `x` がDFSキューに追加されますが、その後 `z` が `x` を使用する際に `x` がキューから削除されて再挿入されることがなかったため、`x` と `z` の間の依存関係が無視されていました。DFSキューの途中の要素を削除して再挿入することは困難であるため、この問題の解決は容易ではありませんでした。

新しいスケジューラは、ブロックの末尾から逆方向に動作し、そのすべての使用箇所がすでにスケジュールされている命令をスケジュールします。複数の命令が同時にスケジュール可能になった場合には、単純な優先度スキームによって順序を決定します。

また、スケジューリングが完了したかどうかを追跡するためのフラグが追加され、`print()` 関数がスケジューリングされた順序を使用するように変更されました。この変更によって影響を受けたいくつかのシフトテストが修正され、符号なし右シフトのテストが追加されました。

## 変更の背景

コンパイラにおける命令スケジューリングは、生成される機械語コードの性能に直接影響を与える重要なステップです。特にSSA形式の中間表現を使用するコンパイラでは、命令間のデータ依存関係を正確に把握し、それに基づいて命令の実行順序を決定する必要があります。

このコミット以前のGoコンパイラのSSAバックエンドでは、DFS（深さ優先探索）アルゴリズムを用いたスケジューラが採用されていました。しかし、このDFSベースのスケジューラには根本的な欠陥がありました。それは、ある計算結果（SSAの「Value」）が複数の後続の計算（「User Value」）によって利用される場合に、その依存関係を正しく維持できないという問題です。

具体的には、`Value x` が `Value y` と `Value z` の両方によって使用されるケースを考えます。DFSスケジューラは、`y` を処理する際に `x` をスケジューリングキューに追加します。しかし、その後 `z` を処理する際に、`x` がすでにキュー内に存在するため、`x` と `z` の間の依存関係を考慮して `x` の位置を調整することができませんでした。DFSキューは通常、スタックのような構造で、途中の要素を効率的に削除・再挿入する機能を持たないため、この問題はDFSアルゴリズムの性質上、解決が困難でした。

この依存関係の不整合は、生成されるコードの正当性や性能に悪影響を及ぼす可能性がありました。例えば、`x` が `z` よりも後に実行されるべきであるにもかかわらず、DFSスケジューラが `x` を `z` よりも先にスケジュールしてしまうといった状況が発生し得ます。このような問題は、特にメモリ操作やフラグレジスタ（条件コード）など、厳密な順序が求められる命令において深刻なバグを引き起こす可能性があります。

この背景から、Goコンパイラの堅牢性と性能を向上させるために、既存のDFSスケジューラを、より正確に依存関係を処理できる新しいアルゴリズムに置き換える必要が生じました。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの中間表現（IR）の一種で、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、最適化の機会が増えます。Goコンパイラも、最適化パスでSSA形式を使用しています。

*   **Value**: SSA形式における基本的な計算単位です。例えば、`x = a + b` という命令は、`a` と `b` を引数として `+` 演算を行い、結果として新しい `Value x` を生成します。各 `Value` は一意のIDを持ち、その結果は一度だけ定義されます。
*   **Block**: 制御フローグラフ（CFG）における基本的なブロックです。一つの入り口と一つの出口を持ち、内部の命令は順次実行されます。SSA形式では、`Value` は `Block` 内に配置されます。
*   **Phi関数 (OpPhi)**: 複数の制御フローパスが合流する地点（例えば `if-else` 文の合流点やループの先頭）で、異なるパスから来る同じ論理変数に対応する複数の `Value` を一つに統合するために使用される特別な `Value` です。Phi関数は、そのブロックの先頭に配置される必要があります。

### 2. コンパイラにおける命令スケジューリング

命令スケジューリングとは、コンパイラが中間表現の命令を、プロセッサのパイプライン効率を最大化したり、レジスタの競合を減らしたり、あるいは単に正しい依存関係を維持したりするために、実行順序を並べ替えるプロセスです。

*   **データ依存関係**: ある命令の出力が別の命令の入力として使用される場合、それらの命令間にはデータ依存関係があります。スケジューラは、この依存関係を尊重し、生産者（定義）が消費者（使用）よりも先に実行されるように命令を配置する必要があります。
*   **制御依存関係**: 条件分岐やループなど、プログラムの制御フローによって生じる依存関係です。
*   **リソース依存関係**: プロセッサのレジスタや実行ユニットなどのハードウェアリソースの競合によって生じる依存関係です。

### 3. DFS (深さ優先探索) ベースのスケジューラ

従来のDFSスケジューラは、グラフのノードを深さ優先で探索し、訪問順序に基づいて命令をスケジュールします。データ依存グラフにおいて、あるノード（Value）がその子ノード（User Value）よりも先にスケジュールされるように動作します。しかし、前述の通り、複数の親を持つノードの扱いが複雑になるという問題がありました。

### 4. 逆方向スケジューリング (Backward Scheduling)

このコミットで採用された新しいアプローチは、逆方向スケジューリングの一種です。これは、ブロックの末尾から開始し、命令の消費者（使用）から生産者（定義）へと逆方向に依存関係をたどって命令をスケジュールします。この方法の利点は、ある命令をスケジュールする時点で、その命令のすべての消費者（使用）がすでに考慮されている（またはスケジュール済みである）ため、依存関係の管理が容易になる点です。

### 5. 優先度キュー (Priority Queue)

優先度キューは、要素に優先度を割り当て、常に最も優先度の高い要素を取り出すことができるデータ構造です。このコミットでは、複数の命令が同時にスケジュール可能になった場合に、どの命令を先にスケジュールするかを決定するために使用されます。例えば、メモリ操作やフラグレジスタを扱う命令には、特定の優先度を割り当てることで、より適切なコード生成を促すことができます。

## 技術的詳細

新しいスケジューラは、各基本ブロック（`Block`）内の`Value`の順序を決定するために、逆方向スケジューリングと優先度キューの組み合わせを使用します。

1.  **使用カウントの計算 (`uses` 配列)**:
    まず、各 `Value` がその `Block` 内で他の `Value` によって何回使用されているかを追跡する `uses` 配列が初期化されます。`OpPhi`（Phi関数）は特殊なケースとして扱われ、スケジューリングの依存関係には寄与しないため、その使用はカウントされません。これは、Phi関数が前のブロックからの値を参照するため、現在のブロック内のスケジューリング順序には直接影響しないためです。

2.  **優先度スコアの計算 (`score` 配列)**:
    各 `Value` には「スコア」が割り当てられます。このスコアは、その `Value` がブロックの末尾にどれだけ近くスケジュールされるべきかを示す優先度です。スコアが高いほど、ブロックの末尾に近い位置にスケジュールされます。
    *   `OpPhi` (Phi関数): スコア `0`。Phi関数はブロックの先頭に配置されるべきであるため、最も低い優先度（つまり、逆方向スケジューリングでは最も早く処理される）が与えられます。
    *   `Type.IsMemory()` (メモリ操作): スコア `2`。ストア命令などのメモリ操作は、後続のロード命令との間に「1-live-memory」という制約（メモリの状態が常に一貫していること）を維持するために、可能な限り遅くスケジュールされます。
    *   `Type.IsFlags()` (フラグレジスタ操作): スコア `2`。x86アーキテクチャなどで使用されるフラグレジスタは、通常1つしか存在しないため、フラグを生成する命令は、そのフラグを使用する命令の直前に、かつ次のフラグ更新の直前にスケジュールされるべきです。これにより、「1-live-flags」という制約が維持されます。
    *   `b.Control` (ブロックの制御Value): スコア `3`。ブロックの制御フローを決定する `Value`（例: 比較命令の結果）は、ブロックの最後にスケジュールされるべきです。
    *   その他: スコア `1`。一般的な命令は中間の優先度を持ちます。

3.  **優先度キュー (`priq`)**:
    `priq` は、`Value` をスコアに基づいて格納する複数のスライス（配列）の配列として実装された優先度キューです。`priq[0]` にはスコア0のValue、`priq[1]` にはスコア1のValue、といった具合に格納されます。

4.  **初期キューの構築**:
    まず、`uses` カウントが `0` のすべての `Value`（つまり、そのブロック内でまだ使用されていないか、すべての使用がPhi関数であるValue）が、それぞれのスコアに基づいて `priq` に追加されます。これらの `Value` は、逆方向スケジューリングにおいて最初にスケジュールできる候補となります。

5.  **逆方向スケジューリングループ**:
    メインのスケジューリングループは、`priq` が空になるまで繰り返されます。
    *   ループごとに、`priq` から最も高い優先度を持つ `Value v` が取り出されます（`priq` のインデックスが高い方から、スライスの末尾の要素を取り出す）。
    *   `v` は、最終的なスケジューリング順序を格納する `order` リストに追加されます。
    *   `v` の引数（`v.Args`）を反復処理し、各引数 `w` について以下の処理を行います。
        *   もし `w` が現在のブロック `b` 内の `Value` であれば、`w` の `uses` カウントをデクリメントします。
        *   もし `w` の `uses` カウントが `0` になった場合、それは `w` のすべての使用がすでにスケジュールされたことを意味します。したがって、`w` は現在スケジュール可能であると判断され、そのスコアに基づいて `priq` に追加されます。

6.  **最終的な順序の適用**:
    ループが完了すると、`order` リストにはブロックの末尾から先頭に向かってスケジュールされた `Value` の順序が格納されています。このリストを逆転させ、`b.Values` にコピーすることで、最終的な命令順序が決定されます。

7.  **`f.scheduled` フラグ**:
    `Func` 構造体に `scheduled` というブール型フィールドが追加されました。これは、その `Func` の `Value` が最終的な順序にスケジュールされたかどうかを示すフラグです。

8.  **`print.go` の変更**:
    `fprintFunc` 関数（SSA形式の関数を文字列として出力する関数）が、`f.scheduled` フラグをチェックするようになりました。もし `scheduled` が `true` であれば、`b.Values` に格納されている順序（新しいスケジューラによって決定された順序）をそのまま使用して `Value` を出力します。`scheduled` が `false` の場合は、以前と同様にPhi関数を最初に、その後他の `Value` を出力します。これにより、デバッグ出力が実際の実行順序を反映するようになります。

9.  **テストの修正と追加**:
    `src/cmd/compile/internal/gc/testdata/arith_ssa.go` ファイルでは、このスケジューラ変更によって影響を受けたビットシフト関連のテストが修正されました。特に、符号なし右シフト（`testBitwiseRshU_ssa`）に関する新しいテストケースが追加され、新しいスケジューラの動作が正しく検証されるようになっています。

この新しいスケジューラは、DFSベースのスケジューラが抱えていた依存関係の不整合問題を解決し、より正確で堅牢な命令スケジューリングを実現します。特に、メモリ操作やフラグレジスタの制約を考慮に入れることで、生成されるコードの品質と正確性が向上します。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/schedule.go` の変更

このファイルは、GoコンパイラのSSAバックエンドにおける命令スケジューリングの核心部分です。変更のほとんどがこのファイルに集中しています。

**変更前（DFSベースのスケジューラ）**:
変更前のコードは、`unmarked`, `found`, `expanded`, `done` といった状態を持つ `state` 配列と、`queue` と呼ばれるスタックライクなワークリストを使用してDFSベースのトポロジカルソートを行っていました。`nextMem` や `additionalEdges` といった補助的なデータ構造も使用して、メモリ依存関係などを考慮しようとしていましたが、コミットメッセージにあるように、複数の使用を持つValueの依存関係を正しく処理できないという根本的な問題がありました。

**変更後（逆方向優先度キューベースのスケジューラ）**:

1.  **データ構造の初期化**:
    *   `uses := make([]int, f.NumValues())`: 各 `Value` がブロック内で何回使用されているかをカウントする配列。
    *   `score := make([]int, f.NumValues())`: 各 `Value` のスケジューリング優先度を格納する配列。
    *   `order []*Value`: スケジュールされた `Value` を逆順に格納するスライス。
    *   `priq [4][]*Value`: 優先度キュー。スコア0から3までの4つのスライスで構成され、各スライスは同じスコアを持つ `Value` のリストを保持します。

2.  **`uses` カウントの計算**:
    ```go
    for _, v := range b.Values {
        if v.Op != OpPhi { // Phi関数はスケジューリング依存関係に寄与しない
            for _, w := range v.Args {
                if w.Block == b { // 同じブロック内の引数のみをカウント
                    uses[w.ID]++
                }
            }
        }
    }
    ```
    このループは、各 `Value` がそのブロック内で他の `Value` の引数として何回出現するかを数えます。これにより、ある `Value` がスケジュールされるために、その `Value` を使用するすべての `Value` が先にスケジュールされる必要があるという依存関係を追跡します。

3.  **`score` の計算**:
    ```go
    for _, v := range b.Values {
        switch {
        case v.Op == OpPhi:
            score[v.ID] = 0 // Phiは最も早くスケジュール
        case v.Type.IsMemory():
            score[v.ID] = 2 // メモリ操作は遅くスケジュール
        case v.Type.IsFlags():
            score[v.ID] = 2 // フラグ操作も遅くスケジュール
        default:
            score[v.ID] = 1 // その他は中間
        }
    }
    if b.Control != nil {
        score[b.Control.ID] = 3 // 制御Valueは最も遅くスケジュール
    }
    ```
    この部分で、各 `Value` にその種類に応じた優先度スコアが割り当てられます。`b.Control` はブロックの制御フローを決定する `Value` であり、通常はブロックの最後に実行されるべきです。

4.  **優先度キューの初期化**:
    ```go
    for i := range priq {
        priq[i] = priq[i][:0] // 各スライスをクリア
    }
    for _, v := range b.Values {
        if uses[v.ID] == 0 { // 使用カウントが0のValueを初期候補として追加
            s := score[v.ID]
            priq[s] = append(priq[s], v)
        }
    }
    ```
    `uses` カウントが `0` の `Value` は、そのブロック内で他の `Value` に依存していないため、最初にスケジュール可能な候補となります。これらはそれぞれのスコアに基づいて `priq` に追加されます。

5.  **スケジューリングループ**:
    ```go
    for {
        var v *Value
        for i := len(priq) - 1; i >= 0; i-- { // 最も高い優先度から探索
            n := len(priq[i])
            if n == 0 {
                continue
            }
            v = priq[i][n-1] // 最も優先度の高いValueを取り出す
            priq[i] = priq[i][:n-1] // キューから削除
            break
        }
        if v == nil { // スケジュール可能なValueがなくなったら終了
            break
        }

        order = append(order, v) // スケジュール順序に追加

        for _, w := range v.Args { // スケジュールされたValueの引数を処理
            if w.Block != b {
                continue
            }
            uses[w.ID]-- // 引数の使用カウントを減らす
            if uses[w.ID] == 0 { // 使用カウントが0になったらスケジュール可能
                s := score[w.ID]
                priq[s] = append(priq[s], w)
            }
        }
    }
    ```
    このループが新しいスケジューラの核心です。ブロックの末尾から逆方向に `Value` を選択し、`order` リストに追加します。`Value` がスケジュールされるたびに、その引数の `uses` カウントが減らされ、`uses` カウントが `0` になった引数は、新たにスケジュール可能な `Value` として `priq` に追加されます。これにより、すべての依存関係が満たされた `Value` から順にスケジュールされていきます。

6.  **最終的な順序の適用**:
    ```go
    if len(order) != len(b.Values) {
        f.Fatalf("schedule does not include all values")
    }
    for i := 0; i < len(b.Values); i++ {
        b.Values[i] = order[len(b.Values)-1-i] // 逆順にコピー

## 元コミット内容

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおけるスケジューラの問題を修正します。以前のDFS（深さ優先探索）ベースのスケジューラは、ある値 `x` が複数の他の値（例えば `y` と `z`）によって使用される場合に、依存関係を正しく処理できませんでした。具体的には、`y` が `x` を使用する際に `x` がDFSキューに追加されますが、その後 `z` が `x` を使用する際に `x` がキューから削除されて再挿入されることがなかったため、`x` と `z` の間の依存関係が無視されていました。DFSキューの途中の要素を削除して再挿入することは困難であるため、この問題の解決は容易ではありませんでした。

新しいスケジューラは、ブロックの末尾から逆方向に動作し、そのすべての使用箇所がすでにスケジュールされている命令をスケジュールします。複数の命令が同時にスケジュール可能になった場合には、単純な優先度スキームによって順序を決定します。

## 変更の背景

コンパイラにおける命令スケジューリングは、生成される機械語コードの性能に直接影響を与える重要なステップです。特にSSA形式の中間表現を使用するコンパイラでは、命令間のデータ依存関係を正確に把握し、それに基づいて命令の実行順序を決定する必要があります。

このコミット以前のGoコンパイラのSSAバックエンドでは、DFS（深さ優先探索）アルゴリズムを用いたスケジューラが採用されていました。しかし、このDFSベースのスケジューラには根本的な欠陥がありました。それは、ある計算結果（SSAの「Value」）が複数の後続の計算（「User Value」）によって利用される場合に、その依存関係を正しく維持できないという問題です。

具体的には、`Value x` が `Value y` と `Value z` の両方によって使用されるケースを考えます。DFSスケジューラは、`y` を処理する際に `x` をスケジューリングキューに追加します。しかし、その後 `z` を処理する際に、`x` がすでにキュー内に存在するため、`x` と `z` の間の依存関係を考慮して `x` の位置を調整することができませんでした。DFSキューは通常、スタックのような構造で、途中の要素を効率的に削除・再挿入する機能を持たないため、この問題はDFSアルゴリズムの性質上、解決が困難でした。

この依存関係の不整合は、生成されるコードの正当性や性能に悪影響を及ぼす可能性がありました。例えば、`x` が `z` よりも後に実行されるべきであるにもかかわらず、DFSスケジューラが `x` を `z` よりも先にスケジュールしてしまうといった状況が発生し得ます。このような問題は、特にメモリ操作やフラグレジスタ（条件コード）など、厳密な順序が求められる命令において深刻なバグを引き起こす可能性があります。

この背景から、Goコンパイラの堅牢性と性能を向上させるために、既存のDFSスケジューラを、より正確に依存関係を処理できる新しいアルゴリズムに置き換える必要が生じました。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの中間表現（IR）の一種で、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、最適化の機会が増えます。Goコンパイラも、最適化パスでSSA形式を使用しています。

*   **Value**: SSA形式における基本的な計算単位です。例えば、`x = a + b` という命令は、`a` と `b` を引数として `+` 演算を行い、結果として新しい `Value x` を生成します。各 `Value` は一意のIDを持ち、その結果は一度だけ定義されます。
*   **Block**: 制御フローグラフ（CFG）における基本的なブロックです。一つの入り口と一つの出口を持ち、内部の命令は順次実行されます。SSA形式では、`Value` は `Block` 内に配置されます。
*   **Phi関数 (OpPhi)**: 複数の制御フローパスが合流する地点（例えば `if-else` 文の合流点やループの先頭）で、異なるパスから来る同じ論理変数に対応する複数の `Value` を一つに統合するために使用される特別な `Value` です。Phi関数は、そのブロックの先頭に配置される必要があります。

### 2. コンパイラにおける命令スケジューリング

命令スケジューリングとは、コンパイラが中間表現の命令を、プロセッサのパイプライン効率を最大化したり、レジスタの競合を減らしたり、あるいは単に正しい依存関係を維持したりするために、実行順序を並べ替えるプロセスです。

*   **データ依存関係**: ある命令の出力が別の命令の入力として使用される場合、それらの命令間にはデータ依存関係があります。スケジューラは、この依存関係を尊重し、生産者（定義）が消費者（使用）よりも先に実行されるように命令を配置する必要があります。
*   **制御依存関係**: 条件分岐やループなど、プログラムの制御フローによって生じる依存関係です。
*   **リソース依存関係**: プロセッサのレジスタや実行ユニットなどのハードウェアリソースの競合によって生じる依存関係です。

### 3. DFS (深さ優先探索) ベースのスケジューラ

従来のDFSスケジューラは、グラフのノードを深さ優先で探索し、訪問順序に基づいて命令をスケジュールします。データ依存グラフにおいて、あるノード（Value）がその子ノード（User Value）よりも先にスケジュールされるように動作します。しかし、前述の通り、複数の親を持つノードの扱いが複雑になるという問題がありました。

### 4. 逆方向スケジューリング (Backward Scheduling)

このコミットで採用された新しいアプローチは、逆方向スケジューリングの一種です。これは、ブロックの末尾から開始し、命令の消費者（使用）から生産者（定義）へと逆方向に依存関係をたどって命令をスケジュールします。この方法の利点は、ある命令をスケジュールする時点で、その命令のすべての消費者（使用）がすでに考慮されている（またはスケジュール済みである）ため、依存関係の管理が容易になる点です。

### 5. 優先度キュー (Priority Queue)

優先度キューは、要素に優先度を割り当て、常に最も優先度の高い要素を取り出すことができるデータ構造です。このコミットでは、複数の命令が同時にスケジュール可能になった場合に、どの命令を先にスケジュールするかを決定するために使用されます。例えば、メモリ操作やフラグレジスタを扱う命令には、特定の優先度を割り当てることで、より適切なコード生成を促すことができます。

## 技術的詳細

新しいスケジューラは、各基本ブロック（`Block`）内の`Value`の順序を決定するために、逆方向スケジューリングと優先度キューの組み合わせを使用します。

1.  **使用カウントの計算 (`uses` 配列)**:
    まず、各 `Value` がその `Block` 内で他の `Value` によって何回使用されているかを追跡する `uses` 配列が初期化されます。`OpPhi`（Phi関数）は特殊なケースとして扱われ、スケジューリングの依存関係には寄与しないため、その使用はカウントされません。これは、Phi関数が前のブロックからの値を参照するため、現在のブロック内のスケジューリング順序には直接影響しないためです。

2.  **優先度スコアの計算 (`score` 配列)**:
    各 `Value` には「スコア」が割り当てられます。このスコアは、その `Value` がブロックの末尾にどれだけ近くスケジュールされるべきかを示す優先度です。スコアが高いほど、ブロックの末尾に近い位置にスケジュールされます。
    *   `OpPhi` (Phi関数): スコア `0`。Phi関数はブロックの先頭に配置されるべきであるため、最も低い優先度（つまり、逆方向スケジューリングでは最も早く処理される）が与えられます。
    *   `Type.IsMemory()` (メモリ操作): スコア `2`。ストア命令などのメモリ操作は、後続のロード命令との間に「1-live-memory」という制約（メモリの状態が常に一貫していること）を維持するために、可能な限り遅くスケジュールされます。
    *   `Type.IsFlags()` (フラグレジスタ操作): スコア `2`。x86アーキテクチャなどで使用されるフラグレジスタは、通常1つしか存在しないため、フラグを生成する命令は、そのフラグを使用する命令の直前に、かつ次のフラグ更新の直前にスケジュールされるべきです。これにより、「1-live-flags」という制約が維持されます。
    *   `b.Control` (ブロックの制御Value): スコア `3`。ブロックの制御フローを決定する `Value`（例: 比較命令の結果）は、ブロックの最後にスケジュールされるべきです。
    *   その他: スコア `1`。一般的な命令は中間の優先度を持ちます。

3.  **優先度キュー (`priq`)**:
    `priq` は、`Value` をスコアに基づいて格納する複数のスライス（配列）の配列として実装された優先度キューです。`priq[0]` にはスコア0のValue、`priq[1]` にはスコア1のValue、といった具合に格納されます。

4.  **初期キューの構築**:
    まず、`uses` カウントが `0` のすべての `Value`（つまり、そのブロック内でまだ使用されていないか、すべての使用がPhi関数であるValue）が、それぞれのスコアに基づいて `priq` に追加されます。これらの `Value` は、逆方向スケジューリングにおいて最初にスケジュールできる候補となります。

5.  **逆方向スケジューリングループ**:
    メインのスケジューリングループは、`priq` が空になるまで繰り返されます。
    *   ループごとに、`priq` から最も高い優先度を持つ `Value v` が取り出されます（`priq` のインデックスが高い方から、スライスの末尾の要素を取り出す）。
    *   `v` は、最終的なスケジューリング順序を格納する `order` リストに追加されます。
    *   `v` の引数（`v.Args`）を反復処理し、各引数 `w` について以下の処理を行います。
        *   もし `w` が現在のブロック `b` 内の `Value` であれば、`w` の `uses` カウントをデクリメントします。
        *   もし `w` の `uses` カウントが `0` になった場合、それは `w` のすべての使用がすでにスケジュールされたことを意味します。したがって、`w` は現在スケジュール可能であると判断され、そのスコアに基づいて `priq` に追加されます。

6.  **最終的な順序の適用**:
    ループが完了すると、`order` リストにはブロックの末尾から先頭に向かってスケジュールされた `Value` の順序が格納されています。このリストを逆転させ、`b.Values` にコピーすることで、最終的な命令順序が決定されます。

7.  **`f.scheduled` フラグ**:
    `Func` 構造体に `scheduled` というブール型フィールドが追加されました。これは、その `Func` の `Value` が最終的な順序にスケジュールされたかどうかを示すフラグです。

8.  **`print.go` の変更**:
    `fprintFunc` 関数（SSA形式の関数を文字列として出力する関数）が、`f.scheduled` フラグをチェックするようになりました。もし `scheduled` が `true` であれば、`b.Values` に格納されている順序（新しいスケジューラによって決定された順序）をそのまま使用して `Value` を出力します。`scheduled` が `false` の場合は、以前と同様にPhi関数を最初に、その後他の `Value` を出力します。これにより、デバッグ出力が実際の実行順序を反映するようになります。

9.  **テストの修正と追加**:
    `src/cmd/compile/internal/gc/testdata/arith_ssa.go` ファイルでは、このスケジューラ変更によって影響を受けたビットシフト関連のテストが修正されました。特に、符号なし右シフト（`testBitwiseRshU_ssa`）に関する新しいテストケースが追加され、新しいスケジューラの動作が正しく検証されるようになっています。

この新しいスケジューラは、DFSベースのスケジューラが抱えていた依存関係の不整合問題を解決し、より正確で堅牢な命令スケジューリングを実現します。特に、メモリ操作やフラグレジスタの制約を考慮に入れることで、生成されるコードの品質と正確性が向上します。

**変更前（DFSベースのスケジューラ）**:
変更前のコードは、`unmarked`, `found`, `expanded`, `done` といった状態を持つ `state` 配列と、`queue` と呼ばれるスタックライクなワークリストを使用してDFSベースのトポロジカルソートを行っていました。`nextMem` や `additionalEdges` といった補助的なデータ構造も使用して、メモリ依存関係などを考慮しようとしていましたが、コミットメッセージにあるように、複数の使用を持つValueの依存関係を正しく処理できないという根本的な問題がありました。

**変更後（逆方向優先度キューベースのスケジューラ）**:

1.  **データ構造の初期化**:
    *   `uses := make([]int, f.NumValues())`: 各 `Value` がブロック内で何回使用されているかをカウントする配列。
    *   `score := make([]int, f.NumValues())`: 各 `Value` のスケジューリング優先度を格納する配列。
    *   `order []*Value`: スケジュールされた `Value` を逆順に格納するスライス。
    *   `priq [4][]*Value`: 優先度キュー。スコア0から3までの4つのスライスで構成され、各スライスは同じスコアを持つ `Value` のリストを保持します。

2.  **`uses` カウントの計算**:
    ```go
    for _, v := range b.Values {
        if v.Op != OpPhi { // Phi関数はスケジューリング依存関係に寄与しない
            for _, w := range v.Args {
                if w.Block == b { // 同じブロック内の引数のみをカウント
                    uses[w.ID]++
                }
            }
        }
    }
    ```
    このループは、各 `Value` がそのブロック内で他の `Value` の引数として何回出現するかを数えます。これにより、ある `Value` がスケジュールされるために、その `Value` を使用するすべての `Value` が先にスケジュールされる必要があるという依存関係を追跡します。

3.  **`score` の計算**:
    ```go
    for _, v := range b.Values {
        switch {
        case v.Op == OpPhi:
            score[v.ID] = 0 // Phiは最も早くスケジュール
        case v.Type.IsMemory():
            score[v.ID] = 2 // メモリ操作は遅くスケジュール
        case v.Type.IsFlags():
            score[v.ID] = 2 // フラグ操作も遅くスケジュール
        default:
            score[v.ID] = 1 // その他は中間
        }
    }
    if b.Control != nil {
        score[b.Control.ID] = 3 // 制御Valueは最も遅くスケジュール
    }
    ```
    この部分で、各 `Value` にその種類に応じた優先度スコアが割り当てられます。`b.Control` はブロックの制御フローを決定する `Value` であり、通常はブロックの最後に実行されるべきです。

4.  **優先度キューの初期化**:
    ```go
    for i := range priq {
        priq[i] = priq[i][:0] // 各スライスをクリア
    }
    for _, v := range b.Values {
        if uses[v.ID] == 0 { // 使用カウントが0のValueを初期候補として追加
            s := score[v.ID]
            priq[s] = append(priq[s], v)
        }
    }
    ```
    `uses` カウントが `0` の `Value` は、そのブロック内で他の `Value` に依存していないため、最初にスケジュール可能な候補となります。これらはそれぞれのスコアに基づいて `priq` に追加されます。

5.  **スケジューリングループ**:
    ```go
    for {
        var v *Value
        for i := len(priq) - 1; i >= 0; i-- { // 最も高い優先度から探索
            n := len(priq[i])
            if n == 0 {
                continue
            }
            v = priq[i][n-1] // 最も優先度の高いValueを取り出す
            priq[i] = priq[i][:n-1] // キューから削除
            break
        }
        if v == nil { // スケジュール可能なValueがなくなったら終了
            break
        }

        order = append(order, v) // スケジュール順序に追加

        for _, w := range v.Args { // スケジュールされたValueの引数を処理
            if w.Block != b {
                continue
            }
            uses[w.ID]-- // 引数の使用カウントを減らす
            if uses[w.ID] == 0 { // 使用カウントが0になったらスケジュール可能
                s := score[w.ID]
                priq[s] = append(priq[s], w)
            }
        }
    }
    ```
    このループが新しいスケジューラの核心です。ブロックの末尾から逆方向に `Value` を選択し、`order` リストに追加します。`Value` がスケジュールされるたびに、その引数の `uses` カウントが減らされ、`uses` カウントが `0` になった引数は、新たにスケジュール可能な `Value` として `priq` に追加されます。これにより、すべての依存関係が満たされた `Value` から順にスケジュールされていきます。

6.  **最終的な順序の適用**:
    ```go
    if len(order) != len(b.Values) {
        f.Fatalf("schedule does not include all values")
    }
    for i := 0; i < len(b.Values); i++ {
        b.Values[i] = order[len(b.Values)-1-i] // 逆順にコピー
    }
    ```
    `order` リストは逆方向スケジューリングの結果なので、ブロックの末尾から先頭への順序で `Value` が格納されています。これを逆転させて `b.Values` にコピーすることで、最終的な実行順序が決定されます。

7.  **`f.scheduled = true`**:
    スケジューリングが完了したことを示すフラグを設定します。

### `src/cmd/compile/internal/ssa/func.go` の変更

```go
type Func struct {
    // ... 既存のフィールド ...
    scheduled bool // Values in Blocks are in final order
    // ... 既存のフィールド ...
}
```
`Func` 構造体に `scheduled` フィールドが追加されました。これは、その関数内の `Block` の `Value` がスケジューリングによって最終的な順序に並べ替えられたかどうかを示すブール値です。

### `src/cmd/compile/internal/ssa/print.go` の変更

```go
func fprintFunc(w io.Writer, f *Func) {
    // ... 既存のコード ...
    if f.scheduled {
        // Order of Values has been decided - print in that order.
        for _, v := range b.Values {
            fmt.Fprint(w, "    ")
            fmt.Fprintln(w, v.LongString())
            printed[v.ID] = true
        }
        continue // このブロックの処理をスキップ
    }

    // print phis first since all value cycles contain a phi
    // ... 既存のコード（Phi関数とその他のValueの出力ロジック） ...
}
```
`fprintFunc` は、SSA形式の関数を人間が読める形式で出力するための関数です。この変更により、`f.scheduled` が `true` の場合（つまり、スケジューリングが完了している場合）は、`b.Values` に格納されている `Value` の順序をそのまま使用して出力するようになりました。これにより、デバッグ出力が実際の命令実行順序を正確に反映するようになります。スケジューリングがまだ行われていない場合は、以前のロジック（Phi関数を最初に、その後他のValue）が使用されます。

### `src/cmd/compile/internal/gc/testdata/arith_ssa.go` の変更

*   **`testBitwiseRshU_ssa` 関数と関連テストケースの追加**:

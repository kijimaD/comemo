# [インデックス 23605] ファイルの概要

このコミットは、Go言語の標準ライブラリ `encoding/pem` パッケージにおける、空のPEMブロックのデコード処理の堅牢性を向上させるものです。具体的には、空のPEMブロックが特定の形式で記述された場合に `Decode` 関数が正しく処理できないバグを修正し、より柔軟なデコードを可能にしています。また、エンコード時にヘッダーキーにコロンが含まれる場合のバリデーションも追加されています。

## 元コミット内容

`encoding/pem`: 空のブロックのデコードについて、より寛容にする。

バグ #10980 で指摘されたように、空のPEMブロックは以下のようにエンコードされる。
-----BEGIN foo-----
-----END foo-----

しかし、`Decode` はこれを処理できなかった。

RFC 1421 は、PEMメッセージには常に少なくとも1つのヘッダーが含まれるため、空のブロックのエンコードがどうあるべきかについては答えていない。しかし、今日のPEMは単なるエンコード形式であり、誰もPEMの残りの部分を使用していない。

空のブロックに改行が含まれないのが最も正しいと思われる。なぜなら、https://tools.ietf.org/html/rfc1421#section-9 は、オプションの「pemtext」が先行する改行を伴うと明確に述べているからである。したがって、省略された場合、改行も省略されるべきである。

それにもかかわらず、この変更は `encoding/pem` を寛容にし、空のPEMブロック内の任意の数の空白行を受け入れるようにする。

バグ #10980 を修正。

## 変更の背景

この変更の背景には、Go言語の `encoding/pem` パッケージが、特定の形式で記述された「空のPEMブロック」を正しくデコードできないというバグ（Issue #10980）が存在していました。

PEM (Privacy-Enhanced Mail) 形式は、主に公開鍵証明書や秘密鍵などのバイナリデータをASCIIテキスト形式で表現するために広く用いられています。その基本的な構造は、`-----BEGIN TYPE-----` と `-----END TYPE-----` という境界マーカーで囲まれ、その間にBase64エンコードされたデータが配置されるというものです。オプションでヘッダー情報も含まれることがあります。

問題となったのは、データ部分が完全に空である、いわゆる「空のPEMブロック」の扱いです。Issue #10980では、以下のような形式の空のPEMブロックが `encoding/pem.Decode` 関数によって正しくデコードされないことが報告されました。

```
-----BEGIN foo-----
-----END foo-----
```

RFC 1421（PEMの仕様を定義する初期のRFC）は、PEMメッセージが常に少なくとも1つのヘッダーを持つことを前提としているため、空のブロックのエンコード形式については明確に規定していません。しかし、現代のPEMの利用においては、RFC 1421の厳密な解釈よりも、単なるデータエンコード形式として扱われることが多く、空のデータブロックも有効なケースとして扱われるべきであるという認識がありました。

このコミットは、このような現実の利用状況に合わせて `encoding/pem` パッケージの `Decode` 関数を修正し、空のPEMブロックのデコードをより柔軟に、かつ堅牢に行えるようにすることを目的としています。特に、空のブロック内に任意の数の空白行が含まれていても正しく処理できるようにすることで、異なるシステムやツールによって生成されたPEM形式のデータとの互換性を向上させています。

## 前提知識の解説

### PEM (Privacy-Enhanced Mail) 形式

PEMは、バイナリデータをASCIIテキスト形式で表現するためのエンコード形式です。主に、X.509証明書、RSA秘密鍵、PKCS#8鍵などの暗号関連データをテキストファイルに保存する際によく用いられます。

PEM形式の基本的な構造は以下の通りです。

1.  **ヘッダー行 (BEGINマーカー)**: `-----BEGIN TYPE-----` の形式で、ブロックの開始と内容のタイプ（例: `CERTIFICATE`, `RSA PRIVATE KEY`）を示します。
2.  **ヘッダー (オプション)**: `Key: Value` の形式で、追加のメタデータを提供します。
3.  **データ部分**: Base64エンコードされたバイナリデータが複数行にわたって記述されます。通常、各行は64文字または76文字の長さに制限されます。
4.  **フッター行 (ENDマーカー)**: `-----END TYPE-----` の形式で、ブロックの終了を示します。

例:

```
-----BEGIN CERTIFICATE-----
MIIC+jCCAeOgAwIBAgIJANX... (Base64 encoded data)
...
-----END CERTIFICATE-----
```

### RFC 1421

RFC 1421は、1993年に公開された「Privacy Enhancement for Internet Electronic Mail: Part I: Message Encryption and Authentication Procedures」という仕様の一部です。これは、電子メールのプライバシーと認証を強化するための初期の試みであり、PEMエンコード形式の基礎を定義しました。

RFC 1421のセクション9では、PEMエンコードされたメッセージの構造について詳しく説明されています。このRFCは、PEMメッセージが常に何らかのコンテンツ（少なくともヘッダー）を持つことを前提としており、データ部分が完全に空である「空のブロック」の具体的なエンコード形式については明示的に言及していません。特に、`pemtext`（Base64エンコードされたデータ部分）が先行する改行を伴うと記述されており、これが空のブロックの解釈に影響を与えていました。

現代では、RFC 1421で定義された電子メールのプライバシー強化プロトコル全体が使われることは稀ですが、その中で定義されたPEMエンコード形式自体は、暗号関連データの交換フォーマットとして広く利用され続けています。

### Go言語の `encoding/pem` パッケージ

Go言語の標準ライブラリ `encoding/pem` パッケージは、PEM形式のデータをエンコードおよびデコードするための機能を提供します。

*   `pem.Decode(data []byte) (p *Block, rest []byte)`: PEM形式のバイトスライスを解析し、最初のPEMブロックを `*pem.Block` 構造体として返します。残りのデータは `rest` として返されます。
*   `pem.Encode(out io.Writer, b *Block) error`: `*pem.Block` 構造体をPEM形式で指定された `io.Writer` に書き込みます。

`pem.Block` 構造体は、PEMブロックのタイプ、ヘッダー、およびデコードされたバイナリデータを保持します。

```go
type Block struct {
	Type    string            // "CERTIFICATE", "RSA PRIVATE KEY" など
	Headers map[string]string // オプションのヘッダー
	Bytes   []byte            // デコードされたデータ
}
```

## 技術的詳細

このコミットの技術的な詳細な変更点は、主に `encoding/pem` パッケージの `Decode` 関数におけるPEMブロックの終了マーカー (`pemEnd`) の検索ロジックと、`Encode` 関数におけるヘッダーキーのバリデーションにあります。

### `Decode` 関数の変更点

以前の `Decode` 関数は、PEMブロックのデータ部分の終了を示す `pemEnd` マーカーを検索する際に、常に先行する改行が存在することを前提としていました。しかし、空のPEMブロックの場合、データ部分が全く存在しないため、`-----BEGIN foo-----` の直後に `-----END foo-----` が続くことがあり、この間に改行がない、あるいは複数の空白行があるケースが考えられます。

元のコードでは、`pemEnd` マーカーを `bytes.Index` で検索していました。

```go
	i := bytes.Index(rest, pemEnd)
	if i < 0 {
		return decodeError(data, rest)
	}
	base64Data := removeWhitespace(rest[0:i])
```

このロジックでは、`pemEnd` が `rest` の先頭に直接現れる場合（つまり、データ部分が空で、`pemEnd` の前に改行がない場合）に問題が生じる可能性がありました。特に、`pemEnd` 定数自体が `\n-----END ` で始まるため、`bytes.Index` は `-----END` の直前にある改行を期待していました。

新しいコードでは、この問題を解決するために `endIndex` という変数を導入し、ヘッダーが存在しない空のブロックのケースを特別に処理しています。

```go
	var endIndex int
	// If there were no headers, the END line might occur
	// immediately, without a leading newline.
	if len(p.Headers) == 0 && bytes.HasPrefix(rest, pemEnd[1:]) {
		endIndex = 0
	} else {
		endIndex = bytes.Index(rest, pemEnd)
	}

	if endIndex < 0 {
		return decodeError(data, rest)
	}
	base64Data := removeWhitespace(rest[:endIndex])
```

この変更のポイントは以下の通りです。

1.  **ヘッダーなしの空ブロックの特殊処理**: `len(p.Headers) == 0` かつ `bytes.HasPrefix(rest, pemEnd[1:])` の条件が追加されました。
    *   `len(p.Headers) == 0`: これは、PEMブロックにヘッダーが全く存在しないことを意味します。
    *   `bytes.HasPrefix(rest, pemEnd[1:])`: `pemEnd` は `\n-----END ` で定義されています。`pemEnd[1:]` は `-----END ` の部分を指します。つまり、`rest` の先頭が `-----END ` で始まる場合（先行する改行がない場合）を検出します。
    *   この条件が真の場合、`endIndex` は `0` に設定されます。これは、`rest` の先頭から `pemEnd` マーカーが始まっていると解釈し、データ部分が完全に空であることを意味します。
2.  **通常の `pemEnd` 検索**: 上記の特殊なケースに該当しない場合、従来通り `bytes.Index(rest, pemEnd)` を使用して `pemEnd` マーカーを検索します。
3.  **`rest` の更新**: `getLine(rest[endIndex+len(pemEnd)-1:])` の部分も変更されています。
    *   元のコードでは `rest[i+len(pemEnd):]` でした。
    *   新しいコードでは `-1` が追加されています。これは、`pemEnd` が先行する改行なしでマッチした場合（`endIndex = 0` のケース）に、`pemEnd` の長さから1を引くことで、`pemEnd` 自体に含まれる改行文字を考慮し、残りのデータを正しく取得するためです。これにより、`pemEnd` が `\n-----END ` の形式であっても、`-----END ` の部分だけがマッチした場合に、その後のデータが正しく処理されるようになります。

これらの変更により、`Decode` 関数は、空のPEMブロックが改行なしで `-----BEGIN TYPE-----` の直後に `-----END TYPE-----` と続く場合や、その間に複数の空白行が含まれる場合でも、正しく `pem.Block` をデコードできるようになりました。

### `Encode` 関数の変更点

`Encode` 関数には、ヘッダーキーにコロンが含まれる場合のバリデーションが追加されました。

```go
	// For consistency of output, write other headers sorted by key.
	sort.Strings(h)
	for _, k := range h {
		if strings.Contains(k, ":") {
			return errors.New("pem: cannot encode a header key that contains a colon")
		}
		if err := writeHeader(out, k, b.Headers[k]); err != nil {
			return err
		}
	}
```

PEMヘッダーは `Key: Value` の形式を取るため、ヘッダーキー自体にコロンが含まれていると、解析時にキーと値の区別が曖昧になる可能性があります。この変更は、このような曖昧さを避け、PEM形式の仕様に準拠した有効なヘッダーのみがエンコードされるようにするためのものです。これにより、エンコードされたPEMデータが他のシステムで正しく解析されることが保証されます。

## コアとなるコードの解説

### `src/encoding/pem/pem.go` の変更点

1.  **インポートの追加**: `errors` と `strings` パッケージがインポートに追加されました。これらはそれぞれ、エラーの生成と文字列操作（特にコロンの検索）のために使用されます。
2.  **`Decode` 関数の `endIndex` ロジック**:
    *   `var endIndex int` が宣言され、PEMブロックの終了マーカーの位置を保持します。
    *   `if len(p.Headers) == 0 && bytes.HasPrefix(rest, pemEnd[1:])` という条件が追加されました。これは、デコード中のPEMブロックにヘッダーがなく、かつ残りのデータ (`rest`) が `pemEnd` の「`\n`」を除いた部分（つまり `-----END `）で始まっている場合に真となります。この場合、`endIndex` は `0` に設定され、データ部分が完全に空であることを示します。
    *   それ以外の場合（通常のPEMブロック、または空でないデータを持つブロック）、`endIndex = bytes.Index(rest, pemEnd)` が実行され、`pemEnd` マーカーの通常の検索が行われます。
    *   `base64Data := removeWhitespace(rest[:endIndex])` では、`i` の代わりに `endIndex` が使用され、データ部分の抽出範囲が正しく調整されます。
    *   `_, rest = getLine(rest[endIndex+len(pemEnd)-1:])` の行では、`pemEnd` の長さから1を引く `len(pemEnd)-1` が追加されました。これは、`pemEnd` が先行する改行なしでマッチした場合（`endIndex = 0` のケース）に、`pemEnd` 自体に含まれる改行文字を考慮し、残りのデータを正しく取得するための調整です。これにより、`pemEnd` が `\n-----END ` の形式であっても、`-----END ` の部分だけがマッチした場合に、その後のデータが正しく処理されるようになります。
3.  **`Encode` 関数のヘッダーキーバリデーション**:
    *   `for _, k := range h` ループ内で、`if strings.Contains(k, ":")` という条件が追加されました。
    *   もしヘッダーキー `k` にコロンが含まれている場合、`errors.New("pem: cannot encode a header key that contains a colon")` というエラーを返してエンコード処理を中断します。これは、PEMヘッダーの `Key: Value` 形式の曖昧さを避けるための重要なバリデーションです。

### `src/encoding/pem/pem_test.go` の変更点

1.  **インポートの追加**: `strings` と `testing/quick` パッケージがインポートに追加されました。`strings` はヘッダーキーのコロンチェックに、`testing/quick` はファズテストのフレームワークとして使用されます。
2.  **`TestDecode` の拡張**:
    *   `isEmpty` というヘルパー関数が定義され、デコードされたブロックが空のPEMブロックの条件を満たすかを確認します。
    *   `pemData` 定数に、様々な形式の空のPEMブロック（改行なし、1つの改行、複数の改行）が追加されました。
    *   これらの新しい空のブロックに対して `Decode` 関数が呼び出され、`isEmpty` 関数を使って正しくデコードされることが検証されます。
    *   また、ヘッダーを持つがデータがないブロックのテストも追加され、`Decode` が正しく動作することを確認しています。
3.  **`TestFuzz` の追加**:
    *   `TestFuzz` 関数が追加され、`testing/quick` パッケージを利用したファズテストが実装されました。
    *   `testRoundtrip` という内部関数が定義され、ランダムに生成された `pem.Block` をエンコードし、その後デコードして、元のブロックとデコードされたブロックが同一であるか (`reflect.DeepEqual`)、および残りのデータがないかを確認します。
    *   `testRoundtrip` 内では、エンコードできないヘッダーキー（コロンを含むもの）を持つブロックはスキップされます。
    *   特に、完全に空のブロック (`Block{Type: "EMPTY", Headers: make(map[string]string), Bytes: []byte{}}`) に対する明示的なテストも行われます。
    *   `quick.Check(testRoundtrip, nil)` を呼び出すことで、`testRoundtrip` 関数が様々なランダムな入力で繰り返し実行され、`Encode` と `Decode` の堅牢性が広範囲にわたってテストされます。

これらの変更により、`encoding/pem` パッケージは、空のPEMブロックのデコードにおいてより堅牢になり、またエンコード時のヘッダーキーのバリデーションが強化され、全体的な信頼性と互換性が向上しました。

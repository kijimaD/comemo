# [インデックス 25416] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおいて、デバッグの改善とスタックフレームの最適化を目的として、値（`ssa.Value`）に対応する元の変数名（`*gc.Node`）を記憶する機能を追加するものです。これにより、コンパイラが生成するコードの可読性が向上し、デバッグ時に`autotmp_`のような自動生成された一時変数名ではなく、元のソースコードで定義された変数名で値が参照されるようになります。また、スタックアロケーションの際に、名前付き変数であることを利用して、より効率的なスピル（レジスタからスタックへの退避）が可能になる可能性も示唆されています。

## 変更の背景

GoコンパイラのSSAバックエンドは、プログラムをSSA形式に変換し、様々な最適化を適用した後に、最終的な機械語コードを生成します。この過程で、ソースコード上の変数（`*gc.Node`）は、SSA形式の`ssa.Value`に変換され、多くの場合、元の変数名との直接的な関連が失われます。特に、レジスタに収まらない値は「スピル」され、スタック上の自動生成された一時変数（`autotmp_`で始まる名前）に退避されます。

この挙動は、デバッグ時に問題を引き起こす可能性がありました。デバッガでスタックフレームを検査する際、`autotmp_`のような意味のない変数名しか表示されないため、どの`autotmp_`がどのソースコード上の変数に対応するのかを特定するのが困難でした。

このコミットの主な目的は、以下の2点です。

1.  **デバッグの改善**: SSA変換後も、可能な限り元の変数名を`ssa.Value`に関連付けて保持することで、デバッグ時に意味のある変数名でスタック上の値を確認できるようにする。
2.  **スタックフレームの最適化**: 名前付き変数としてスピルされることで、コンパイラが変数の生存期間や干渉関係をより正確に把握し、スタック上のメモリ割り当てを最適化できる可能性がある。特に、干渉しないスピルを識別しやすくなることで、スタックフレームが小さくなることが期待されます。

この変更は、まず単一ワードの変数に限定して実装され、文字列やスライスなどの複数ワードの変数への対応は将来のコミットに持ち越されています。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造と概念に関する知識が必要です。

### Goコンパイラの構造

Goコンパイラ（`cmd/compile`）は、複数のステージを経てソースコードを機械語に変換します。主要なステージは以下の通りです。

*   **フロントエンド (`gc`パッケージ)**: 構文解析、型チェック、AST (Abstract Syntax Tree) の構築、高レベルな最適化などを行います。この段階では、ソースコードの変数や式は`*gc.Node`という構造体で表現されます。
*   **SSAバックエンド (`ssa`パッケージ)**: ASTをSSA形式に変換し、データフロー解析に基づいた様々な最適化（共通部分式除去、デッドコード除去、レジスタ割り当てなど）を行います。この段階では、プログラムの各値は`ssa.Value`という構造体で表現されます。
*   **コード生成**: 最適化されたSSA形式から、最終的な機械語コードを生成します。

### SSA (Static Single Assignment) 形式

SSA形式は、各変数が一度だけ代入されるようにプログラムを変換する中間表現です。これにより、データフロー解析が容易になり、より強力な最適化が可能になります。SSA形式では、ソースコード上の変数`x`が複数回代入される場合、`x1`, `x2`, `x3`のように新しいバージョンが導入されます。

### `*gc.Node`と`ssa.Value`

*   `*gc.Node`: Goコンパイラのフロントエンドで使われるASTノードの表現です。ソースコード上の変数、定数、式、文などがこれに該当します。特に、`ONAME`オペレーションを持つ`Node`は変数宣言や参照を表します。
*   `ssa.Value`: SSAバックエンドで使われる値の表現です。各`ssa.Value`は、特定の操作の結果として生成される単一の値を表します。

### 変数の種類 (`Node.Class`)

`*gc.Node`には`Class`フィールドがあり、変数の種類を示します。

*   `PAUTO`: 自動変数（ローカル変数）。スタック上に割り当てられます。
*   `PPARAM`: 関数パラメータ。
*   `PPARAMOUT`: 関数の戻り値パラメータ。
*   `PEXTERN`: グローバル変数。
*   `Pxxx`: ダミーノードや内部的な用途に使われるクラス。

### `autotmp_`変数

SSAバックエンドが最適化を行う過程で、一時的な値を保持するために自動的に生成される変数です。これらはソースコードには存在せず、デバッグ時には元の変数との関連が不明瞭になる原因でした。

### スピル (Spill) とスタックアロケーション (Stack Allocation)

レジスタ割り当ての過程で、利用可能なレジスタの数が不足した場合、一部の値をレジスタからスタックメモリに退避させる必要があります。この操作を「スピル」と呼びます。スピルされた値はスタック上の特定の「スロット」に割り当てられます。このコミットは、このスピルされる値に元の変数名を関連付けることで、デバッグ情報の改善とスタックアロケーションの最適化を目指しています。

### デッドコード除去 (Dead Code Elimination)

SSA最適化の一つで、プログラムの実行結果に影響を与えないコード（デッドコード）を削除する処理です。このコミットでは、名前付き変数と`ssa.Value`の関連付けがデッドコード除去後も正しく維持されるように考慮されています。

## 技術的詳細

このコミットの核心は、`ssa.Func`構造体に`NamedValues`というマップを導入し、`*gc.Node`（元の変数名）とそれに対応する`ssa.Value`のリストを関連付けることです。

### `GCNode`インターフェースの導入

`src/cmd/compile/internal/ssa/config.go`では、`*gc.Node`型を直接`ssa`パッケージにインポートすると循環参照が発生するため、`GCNode`というインターフェースが導入されました。このインターフェースは`Typ() Type`と`String() string`メソッドを持ち、`*gc.Node`がこのインターフェースを満たすように変更されています。これにより、`ssa`パッケージは`gc`パッケージの具体的な型に依存することなく、`*gc.Node`の情報を扱うことができます。

```go
// interface used to hold *gc.Node. We'd use *gc.Node directly but
// that would lead to an import cycle.
type GCNode interface {
	Typ() Type
	String() string
}
```

### `ssa.Func`への`NamedValues`の追加

`src/cmd/compile/internal/ssa/func.go`では、`Func`構造体に以下のフィールドが追加されました。

```go
type Func struct {
	// ...
	// map from *gc.Node to set of Values that represent that Node.
	// The Node must be an ONAME with PPARAM, PPARAMOUT, or PAUTO class.
	NamedValues map[GCNode][]*Value
	// Names is a copy of NamedValues.Keys. We keep a separate list
	// of keys to make iteration order deterministic.
	Names []GCNode
}
```

*   `NamedValues`: `GCNode`（元の変数名）をキーとし、その変数に対応する`ssa.Value`のスライスを値とするマップです。一つの変数名が複数の`ssa.Value`に対応する可能性があるため、スライスで保持されます。
*   `Names`: `NamedValues`のキー（`GCNode`）を保持するスライスです。マップのイテレーション順序が非決定論的であるため、決定論的な順序で処理するために別途リストとして保持されます。

### `addNamedValue`関数の追加

`src/cmd/compile/internal/gc/ssa.go`に`addNamedValue`関数が追加され、`s.assign`（SSA形式での変数への代入）時に、`*gc.Node`と`ssa.Value`の関連付けを`NamedValues`マップに記録します。

```go
func (s *state) addNamedValue(n *Node, v *ssa.Value) {
	if n.Class == Pxxx { // Don't track our dummy nodes (&memVar etc.).
		return
	}
	if n.Sym == nil { // TODO: What the heck is this?
		return
	}
	if strings.HasPrefix(n.Sym.Name, "autotmp_") { // Don't track autotmp_ variables.
		return
	}
	if n.Class == PPARAM || n.Class == PPARAMOUT { // TODO: Remove this
		return
	}
	if n.Class == PAUTO && n.Xoffset != 0 {
		s.Fatalf("AUTO var with offset %s %d", n, n.Xoffset)
	}
	values, ok := s.f.NamedValues[n]
	if !ok {
		s.f.Names = append(s.f.Names, n)
	}
	s.f.NamedValues[n] = append(values, v)
}
```

この関数は、ダミーノード、`autotmp_`変数、および一部のパラメータ変数を除外して、`*gc.Node`と`ssa.Value`の関連付けを記録します。

### デッドコード除去 (`deadcode.go`) での`NamedValues`の更新

`src/cmd/compile/internal/ssa/deadcode.go`では、デッドコード除去の後に`NamedValues`マップからデッドな`ssa.Value`エントリを削除するロジックが追加されました。これにより、`NamedValues`マップは常にライブな`ssa.Value`のみを参照するように保たれます。

```go
	// Remove dead entries from namedValues map.
	for name, values := range f.NamedValues {
		i := 0
		for _, v := range values {
			for v.Op == OpCopy {
				v = v.Args[0]
			}
			if live[v.ID] {
				values[i] = v
				i++
			}
		}
		f.NamedValues[name] = values[:i]
		tail := values[i:]
		for j := range tail {
			tail[j] = nil
		}
	}
```

この処理は、`OpCopy`操作を辿って実際の値がライブであるかを確認し、ライブな値のみを`NamedValues`マップに残します。

### スタックアロケーション (`stackalloc.go`) での`NamedValues`の利用

`src/cmd/compile/internal/ssa/stackalloc.go`では、スピルされる`ssa.Value`に対して、`NamedValues`マップを利用して元の変数名をスピルロケーションとして優先的に割り当てるロジックが追加されました。

```go
	// Build map from values to their names, if any.
	// A value may be associated with more than one name (e.g. after
	// the assignment i=j). This step picks one name per value arbitrarily.
	names := make([]GCNode, f.NumValues())
	for _, name := range f.Names {
		// Note: not "range f.NamedValues" above, because
		// that would be nondeterministic.
		for _, v := range f.NamedValues[name] {
			names[v.ID] = name
		}
	}

	// ...

			// If this is a named value, try to use the name as
			// the spill location.
			var name GCNode
			if v.Op == OpStoreReg {
				name = names[v.Args[0].ID]
			} else {
				name = names[v.ID]
			}
			if name != nil && v.Type.Equal(name.Typ()) {
				for _, id := range interfere[v.ID] {
					h := f.getHome(id)
					if h != nil && h.(*LocalSlot).N == name {
						// A variable can interfere with itself.
						// It is rare, but but it can happen.
						goto noname
					}
				}
				// ... (phi value handling) ...
				loc := &LocalSlot{name}
				f.setHome(v, loc)
				// ... (phi value handling) ...
				continue
			}

		noname:
			// Set of stack slots we could reuse.
			// ... (existing stack allocation logic) ...
```

このロジックは、まず`ssa.Value`から対応する`GCNode`（変数名）へのマッピングを構築します。その後、スピルされる`ssa.Value`が名前付き変数に対応する場合、その変数名が他のライブな値と干渉しない限り、その変数名をスピルロケーションとして割り当てます。これにより、デバッグ時に元の変数名でスタック上の値が参照されるようになります。

## コアとなるコードの解説

### `addNamedValue`関数 (`src/cmd/compile/internal/gc/ssa.go`)

この関数は、Goコンパイラのフロントエンド（`gc`）がSSAバックエンド（`ssa`）に情報を渡すための重要なブリッジです。`s.assign`が呼び出されるたびに、つまりソースコード上の変数に値が代入されるたびに、この関数が呼び出されます。

*   **目的**: `*gc.Node`（ソースコード上の変数）と、それに対応する`ssa.Value`（SSA形式での値）の関連付けを`ssa.Func.NamedValues`マップに記録します。
*   **フィルタリング**: `Pxxx`クラスのダミーノード、`autotmp_`で始まる自動生成された一時変数、および一部のパラメータ変数は追跡対象から除外されます。これは、これらの変数がデバッグ時に意味のある情報を提供しないため、または現在の実装では複雑すぎるためです。
*   **`NamedValues`への追加**: `n`（`*gc.Node`）をキーとして、`v`（`ssa.Value`）を`NamedValues`マップの対応するスライスに追加します。もし`n`が新しいキーであれば、`f.Names`スライスにも追加され、イテレーション順序の決定論性を保証します。

この関数により、SSA変換後も元の変数名が`ssa.Value`に紐付けられるようになり、デバッグ情報の改善の基盤が作られます。

### `deadcode`関数での`NamedValues`の更新 (`src/cmd/compile/internal/ssa/deadcode.go`)

デッドコード除去は、プログラムから不要なコードを削除する最適化です。この過程で、一部の`ssa.Value`がデッドと判断され、削除されます。`NamedValues`マップが古い`ssa.Value`への参照を保持し続けると、デバッグ情報が不正確になったり、メモリリークの原因になったりする可能性があります。

*   **目的**: デッドコード除去後に、`NamedValues`マップからデッドな`ssa.Value`への参照を削除し、マップの整合性を保ちます。
*   **処理**: `f.NamedValues`マップをイテレートし、各`GCNode`に関連付けられた`ssa.Value`スライスを検査します。`live`配列（ライブな`ssa.Value`のIDを記録）を参照し、ライブな`ssa.Value`のみをスライスに残します。`OpCopy`操作は、値自体ではなくそのコピーを表すため、`OpCopy`を辿って元の値がライブであるかを確認します。

この変更により、`NamedValues`マップは常に正確なライブな`ssa.Value`情報のみを保持し、デバッグ情報の信頼性が向上します。

### `stackalloc`関数での`NamedValues`の利用 (`src/cmd/compile/internal/ssa/stackalloc.go`)

この部分は、このコミットの最終的な目的である「デバッグの改善」と「スタックフレームの最適化」を実現する核心的なロジックです。

*   **`names`マップの構築**: まず、`f.NamedValues`マップから、各`ssa.Value.ID`に対応する`GCNode`（変数名）を効率的にルックアップするための`names`スライスを構築します。一つの`ssa.Value`が複数の変数名に関連付けられる可能性があるため、任意で一つを選択します。
*   **名前付きスピルの優先**: `stackalloc`は、各`ssa.Value`にスタック上のスロット（`LocalSlot`）を割り当てます。この変更では、スピルされる`ssa.Value`が`names`スライスに登録されている（つまり、元のソースコード上の変数に対応する）場合、その`GCNode`をスピルロケーションとして優先的に割り当てようとします。
*   **干渉チェック**: ただし、この割り当ては無条件ではありません。割り当てようとしている`GCNode`が、現在処理中の`ssa.Value`と干渉する他のライブな`ssa.Value`によって既に占有されていないかを確認します。干渉がある場合は、通常のスタックアロケーションロジック（`noname`ラベル以降）にフォールバックします。
*   **`LocalSlot`への割り当て**: 干渉がない場合、`LocalSlot`構造体に`GCNode`を直接設定し、その`ssa.Value`のホーム（スタック上の場所）として割り当てます。これにより、デバッガは`LocalSlot`から元の変数名を取得し、スタック上の値を表示できるようになります。

このロジックにより、デバッグ時に`autotmp_`ではなく、より意味のある変数名でスタック上の値が表示されるようになり、デバッグ体験が大幅に向上します。また、干渉しない名前付きスピルを識別することで、スタックフレームのレイアウトが最適化され、全体的なスタックフレームサイズが削減される可能性も生まれます。

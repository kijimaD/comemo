## 元コミット内容

このコミットは、Goランタイムのガベージコレクション (GC) トレース出力の改善を目的としています。具体的には、`GODEBUG=gctrace=1` を設定した際に表示されるGCトレース行において、GCサイクルの開始時刻を表示するように変更します。以前はGCサイクルの終了時刻が表示されており、その直後に表示されるGC利用率がGC終了時点のものであるため、一貫性を持たせる意図がありましたが、結果的にユーザーにとって混乱を招くものでした。この変更により、GCトレースの時刻表示がより直感的になります。

## 変更の背景

Goのガベージコレクションは、プログラムの実行中に自動的にメモリ管理を行う重要な機能です。その動作をデバッグしたり、パフォーマンスを分析したりするために、Goランタイムは詳細なトレース情報を提供できます。`GODEBUG=gctrace=1` 環境変数を設定すると、GCサイクルの詳細が標準エラー出力に表示されます。

このトレース出力には、GCサイクルの開始からの経過時間や、GCが消費した時間、メモリ使用量、GCの利用率などが含まれます。コミットメッセージによると、以前の実装では、GCサイクルの「終了時刻」が `@n.nnns` の形式で表示されていました。この設計は、その直後に表示されるGCの「利用率」がGC終了時点のものであるため、両者の整合性を保つ意図がありました。

しかし、GCトレースの出力は、通常、GCサイクルが「開始」した時点の状況を把握するために利用されることが多いため、GC終了時刻が表示されることは直感的ではなく、ユーザーにとって混乱を招く原因となっていました。例えば、GCが長時間実行された場合、トレース行に表示される時刻と、そのGCサイクルが実際に始まったと感じる時刻との間に大きなずれが生じる可能性がありました。

このコミットは、この混乱を解消し、GCトレースの時刻表示をより自然で理解しやすいものにするために行われました。GCサイクルの「開始時刻」を表示することで、ユーザーはGCイベントがいつ発生し始めたのかを正確に把握できるようになります。

## 前提知識の解説

### Goのガベージコレクション (GC)

Go言語は、自動メモリ管理のために並行マーク＆スイープ方式のガベージコレクタを採用しています。これは、プログラムの実行と並行してGCが動作し、アプリケーションの一時停止（ストップ・ザ・ワールド）時間を最小限に抑えることを目指しています。

GCサイクルは、主に以下のフェーズで構成されます。

1.  **マークフェーズ (Mark Phase)**: プログラムが使用しているオブジェクト（到達可能なオブジェクト）を特定し、マークします。GoのGCは、このフェーズの大部分をアプリケーションと並行して実行します。
2.  **マークターミネーションフェーズ (Mark Termination Phase)**: 並行マークフェーズの終了を調整し、ストップ・ザ・ワールドが発生する短い期間です。この期間中に、マークフェーズで取りこぼした可能性のあるオブジェクトを最終的にマークします。
3.  **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不能なオブジェクト、つまり不要なメモリ）を解放し、再利用可能なメモリとしてシステムに返します。このフェーズも大部分が並行して実行されます。

### `GODEBUG=gctrace=1`

`GODEBUG` 環境変数は、Goランタイムのデバッグ情報を制御するために使用されます。`gctrace=1` を設定すると、各GCサイクルの詳細な情報が標準エラー出力にログとして出力されます。このログは、GCの動作を理解し、メモリリークやパフォーマンスの問題を診断する上で非常に有用です。

典型的な `gctrace` の出力例は以下のようになります（このコミット適用前の形式）：

```
gc #1 @0.001s 0%: 0.000+0.000+0.000 ms clock, 0.000+0.000+0.000 ms cpu, 4->4->0 MB, 4 MB goal, 0 P
```

*   `gc #1`: 1回目のGCサイクル
*   `@0.001s`: プログラム開始からGCサイクルが終了するまでの時間（秒）
*   `0%`: GCがCPU時間を消費した割合（利用率）
*   `0.000+0.000+0.000 ms clock`: GCの各フェーズ（マーク、スイープ、その他）にかかった実時間
*   `0.000+0.000+0.000 ms cpu`: GCの各フェーズが消費したCPU時間
*   `4->4->0 MB`: GC開始時のヒープサイズ -> マーク後のヒープサイズ -> GC終了後のヒープサイズ
*   `4 MB goal`: 次のGCを開始する目標ヒープサイズ
*   `0 P`: GCに参加したプロセッサの数

このコミットは、上記の `@0.001s` の部分の計算ロジックを変更するものです。

### `runtimeInitTime`, `tEnd`, `tSweepTerm`

Goランタイム内部では、GCのタイミングを計測するためにいくつかのタイムスタンプが使用されます。

*   `runtimeInitTime`: プログラムが開始された時刻。すべてのGC関連の時刻は、この `runtimeInitTime` からの相対時間として計算されます。
*   `tEnd`: GCサイクルの「終了」時刻。具体的には、GCのマークフェーズとスイープフェーズが完了し、GCがアイドル状態に戻る直前の時刻を指します。
*   `tSweepTerm`: スイープターミネーションフェーズが完了した時刻。これは、GCサイクルが実際に「開始」したと見なせる時点、またはGCがアクティブな作業を開始する直前の時点に近い値です。このコミットでは、GCサイクルの開始時刻としてこの `tSweepTerm` を使用するように変更されています。

## 技術的詳細

この変更は、`src/runtime/mgc.go` ファイル内の `gc` 関数、特に `gctrace` 出力を生成する部分に影響を与えます。

以前のコードでは、GCトレース行の時刻表示に `tEnd` を使用していました。`tEnd` はGCサイクルの最終的な完了時刻を示すため、GCが長時間実行された場合、この時刻はGCが実際に開始された時刻とは大きく異なる可能性がありました。

この変更は、`gctrace` の出力の解釈をより容易にし、GCのパフォーマンス分析を行う開発者にとって、より正確な時間軸での情報提供を可能にします。特に、GCの開始とアプリケーションの動作の相関関係を分析する際に、この変更は有用です。

```

*   `memstats.numgc`: 現在のGCサイクルの番号。
*   `uint64(tSweepTerm-runtimeInitTime)/1e6`:

この変更は、`gctrace` の出力の解釈をより容易にし、GCのパフォーマンス分析を行う開発者にとって、より正確な時間軸での情報提供を可能にします。特に、GCの開始とアプリケーションの動作の相関関係を分析する際に、この変更は有用です。

## コアとなるコードの解説

`src/runtime/mgc.go` の `gc` 関数は、Goランタイムのガベージコレクションの主要なロジックをカプセル化しています。この関数は、GCサイクルの開始、実行、終了を管理し、必要に応じて `gctrace` の出力を生成します。

変更された行は、`gctrace` が有効な場合にGCサイクルの概要行を出力する部分です。

```go
print("gc #", memstats.numgc,
    " @", string(itoaDiv(sbuf[:], uint64(tSweepTerm-runtimeInitTime)/1e6, 3)), "s ",
    util, "%: ")
```

*   `memstats.numgc`: 現在のGCサイクルの番号。
*   `uint64(tSweepTerm-runtimeInitTime)/1e6`:
    *   `runtimeInitTime`: プログラムが起動した時刻。
    *   `tSweepTerm`: GCのスイープターミネーションフェーズが完了した時刻。これは、GCが実際にメモリのマークとスイープを開始する直前の時点、つまりGCサイクルの「開始」と見なせる時点を指します。
    *   `tSweepTerm-runtimeInitTime`: プログラム開始からGCサイクルが開始するまでの経過時間（ナノ秒単位）。
    *   `/1e6`: ナノ秒をミリ秒に変換。
    *   `uint64(...)`: 符号なし64ビット整数にキャスト。
    *   `itoaDiv(sbuf[:], ..., 3)`: 計算されたミリ秒値を文字列に変換し、小数点以下3桁まで表示します。
*   `util`: GCが消費したCPU時間の割合（利用率）。

この変更により、`@` の後に続く時刻は、GCサイクルがプログラム開始からどれくらいの時間で「開始」したかを示すようになります。これにより、GCの発生タイミングとアプリケーションの実行状況との関連性をより正確に把握できるようになり、GCログの可読性と有用性が向上します。

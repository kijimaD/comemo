## 変更の背景

この変更は、コミットメッセージにある「Should help windows/amd64.」という記述が示す通り、Windows/AMD64環境におけるGoランタイムの安定性向上を目的としています。

GoプログラムがC言語のコードを呼び出すCGOを使用する場合、GoランタイムはGoのゴルーチンのスタックとCのスタックの間でコンテキストを切り替える必要があります。この切り替えは非常に低レベルな操作であり、スタックの状態が厳密に管理される必要があります。

`endcgo` 関数は、CGO呼び出しが完了し、Goランタイムに制御が戻された直後に実行される重要なクリーンアップ関数です。この関数が実行されている最中に、Goのスタックが自動的に成長（スタックスプリットまたはスタックコピー）しようとすると、予期せぬ問題やクラッシュを引き起こす可能性があります。特にWindows/AMD64のような特定のプラットフォームでは、OSのスタック管理の特性やABI（Application Binary Interface）の違いにより、このようなスタック関連の問題が顕在化しやすい傾向があります。

`endcgo` 関数に `//go:nosplit` ディレクティブを付与することで、この関数が実行されている間はスタックの成長チェックがスキップされ、スタックが移動しないことが保証されます。これにより、`endcgo` が安全かつ予測可能な環境で実行され、CGO呼び出しの終了処理における潜在的なスタック関連の不安定性を排除し、特にWindows/AMD64環境での堅牢性を高めることが意図されています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとCGOに関する前提知識が必要です。

*   **Goランタイム (Go Runtime)**:
    Goランタイムは、Goプログラムの実行を管理する低レベルなシステムです。これには、ゴルーチンのスケジューリング、ガベージコレクション、メモリ管理、そしてスタック管理などが含まれます。Goプログラムは、OSによって直接実行されるのではなく、このランタイム上で動作します。

*   **CGO**:
    CGOは、GoプログラムからC言語の関数を呼び出すためのGoの機能です。これにより、既存のCライブラリをGoアプリケーションから利用したり、Goでは実装が難しい低レベルな操作をCで行ったりすることが可能になります。CGO呼び出しは、GoとCの異なる実行モデルとスタック管理の間で橋渡しをするため、Goランタイムにとって複雑な処理を伴います。

*   **`go:nosplit` ディレクティブ**:
    `//go:nosplit` はGoコンパイラに対する特殊なディレクティブ（指示子）です。このディレクティブが関数に付与されると、コンパイラはその関数のエントリポイントで通常行われるスタックオーバーフローチェック（スタックが足りているかどうかの確認）を省略します。
    Goのゴルーチンは、最初は小さなスタックで開始し、必要に応じて自動的にスタックを拡張（成長）します。このスタックの拡張は「スタックスプリット」または「スタックコピー」と呼ばれます（Go 1.4以降は連続したスタック領域を確保し、必要に応じてより大きな領域にコピーする「スタックコピー」方式が主流です）。
    しかし、ランタイムの非常に低レベルな部分や、CGO呼び出しのようにスタックが固定された場所にあることを前提とするコードでは、スタックの動的な成長や移動が安全でない場合があります。`go:nosplit` は、このような状況で関数が実行中にスタックが移動しないことを保証するために使用されます。

*   **Goのスタック管理（スタック成長/スプリット）**:
    Goのゴルーチンは、OSスレッドとは異なり、非常に軽量で、最初は数KB程度の小さなスタックで開始します。関数呼び出しによってスタックが不足しそうになると、Goランタイムは自動的にスタックを拡張します。このプロセスは通常、アプリケーション開発者からは透過的ですが、ランタイム内部ではスタックの再配置（新しい大きなスタック領域へのコピー）が行われます。

*   **`m` (M-struct)**:
    Goランタイムにおいて、`m` はOSスレッド（Machine）を表す構造体です。各OSスレッドは1つのM構造体に対応し、GoのスケジューラはM上でゴルーチン（G）を実行します。CGO呼び出しでは、Goのゴルーチンのスタックから、OSスレッドに紐づく特別なスタック（`m.g0` スタックなど）への切り替えが発生することがあります。

*   **`cgocall` と `endcgo`**:
    *   `cgocall`: GoからC関数を呼び出す際に、Goランタイムが内部的に使用する関数です。GoのスタックからCのスタックへの切り替え、引数の準備、C関数の呼び出し、戻り値の処理などを担当します。
    *   `endcgo`: CGO呼び出しが終了し、C関数からGoランタイムに制御が戻された後に呼び出される関数です。CGO呼び出し中に設定されたランタイムの状態（例えば、`m.ncgo` カウンタなど）をクリーンアップし、Goのスケジューラがゴルーチンを再びスケジュールできるようにする役割を担います。

## 技術的詳細

このコミットの技術的な核心は、`endcgo` 関数が実行される際のスタックの安全性と予測可能性を確保することにあります。

CGO呼び出し中、Goランタイムは通常、Goのスケジューラがゴルーチンをプリエンプト（中断して別のゴルーチンに切り替えること）できない状態になります。これは、CコードがGoランタイムの管理外で動作するため、Goのスタックやヒープの状態が一時的に不安定になる可能性があるためです。

`endcgo` 関数は、CGO呼び出しが完了し、GoランタイムがGoの実行コンテキストに復帰する直前の非常に重要なタイミングで実行されます。この時点で、スタックの状態がまだ完全にGoランタイムの管理下に戻っていない可能性や、スタックポインタが特定の期待される位置にある必要がある場合があります。もし `endcgo` の実行中にスタックの成長チェックがトリガーされ、スタックの再配置（コピー）が発生すると、以下のような問題が生じる可能性があります。

1.  **スタックポインタの不整合**: スタックが移動すると、`endcgo` 関数内で使用されているスタックポインタや、CGO呼び出し中に一時的に保存されていたレジスタの値などが無効になる可能性があります。
2.  **競合状態**: スタックの再配置は、メモリの割り当てやコピーを伴うため、他のランタイム操作と競合する可能性があります。
3.  **デッドロック**: スタックの再配置中に、ランタイムの内部ロックが保持されている場合、デッドロックを引き起こす可能性があります。
4.  **クラッシュ**: 最悪の場合、スタックの不正な状態が原因でプログラムがクラッシュする可能性があります。

`//go:nosplit` ディレクティブを `endcgo` に適用することで、これらのリスクが軽減されます。このディレクティブにより、`endcgo` 関数が実行されている間は、スタックの成長チェックが完全にスキップされます。これにより、`endcgo` はスタックが移動しないという保証された環境で動作でき、CGO呼び出しからの安全な復帰処理を確実に行うことができます。

特にWindows/AMD64環境では、OSのシステムコールやスレッド管理の特性が他のOS（例: Linux）と異なるため、スタックの厳密な管理がより重要になることがあります。このコミットは、そのようなプラットフォーム固有の微妙な違いに対応し、Goランタイム全体の堅牢性を高めるためのものです。

## コアとなるコードの解説

追加されたのは、`src/runtime/cgocall.go` ファイル内の `endcgo` 関数の定義の直前にある以下の1行です。

```go
//go:nosplit
```

この一行は、Goコンパイラに対する指示であり、`endcgo` 関数が呼び出された際に、通常行われるスタックオーバーフローチェックを省略するように命令します。これにより、`endcgo` 関数が実行されている間は、ゴルーチンのスタックが自動的に成長したり、メモリ上で移動したりすることがなくなります。

`endcgo` 関数は、CGO呼び出しが終了した後に、GoランタイムがCGO呼び出し中に設定した状態（例えば、`m.ncgo` カウンタ）をクリーンアップするために呼び出されます。この関数がスタックの移動を伴わずに実行されることで、CGO呼び出しからの復帰処理がより安全かつ予測可能になり、特にスタック管理が複雑なWindows/AMD64環境での潜在的な問題を回避できるようになります。

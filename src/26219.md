## 変更の背景

このコミットは、Goコンパイラがプログラムの初期化順序を処理する方法における既存のバグを修正するために導入されました。特に、グローバル変数やパッケージレベルの初期化において、循環参照（circular dependencies）が正しく検出されない、または初期化が不適切に行われる可能性があったと考えられます。

コミットメッセージには `Fixes #13343` と記載されていますが、Goの公式イシュートラッカー（GitHub）でこの特定のイシュー番号を直接見つけることはできませんでした。しかし、コードの変更内容と追加されたテストケースから判断すると、このバグは、初期化処理中に定義（`defn`）の状態管理が不十分であったために発生し、結果としてコンパイラが初期化の循環を検出できなかったり、誤った順序で初期化を完了させたりする問題を引き起こしていたと推測されます。この修正は、より堅牢な初期化状態管理メカニズムを導入することで、これらの問題を解決することを目的としています。

## 前提知識の解説

### Goコンパイラの初期化処理

Go言語では、パッケージレベルの変数や`init()`関数は特定の順序で初期化されます。この順序は、依存関係グラフに基づいて決定されます。コンパイラは、各パッケージの依存関係を解析し、循環参照がないことを確認しながら、適切な初期化順序を構築します。このプロセスは、プログラムの実行前にすべてのグローバルな状態が正しく設定されることを保証するために不可欠です。

### `sinit.go`の役割

`src/cmd/compile/internal/gc/sinit.go` ファイルは、Goコンパイラのバックエンドの一部であり、主に静的初期化（static initialization）の処理を担当しています。これには、グローバル変数や定数の初期化、および`init()`関数の呼び出し順序の決定などが含まれます。このファイル内のロジックは、プログラムのセマンティクスが正しく、かつ効率的に初期化されることを保証します。

### `Node`と`defn`

Goコンパイラ内部では、プログラムの各要素（変数、関数、型など）は抽象構文木（AST）の`Node`として表現されます。`defn`（definitionの略）は、これらの`Node`の中でも特に宣言や定義を表すものとして使われることが多いです。`defn`は、その要素の初期化状態や依存関係などのメタデータを持つことができます。

### `Initorder`の状態

`Initorder`は、コンパイラが定義の初期化状態を追跡するために使用する列挙型（enum）またはそれに類するものです。このコミットでは、以下の3つの状態が関与していると推測されます。

*   **`InitNotStarted`**: 定義の初期化がまだ開始されていない状態。
*   **`InitPending`**: 定義の初期化処理が進行中であり、その定義が依存する他の要素の初期化が完了するのを待っている状態。この状態は、初期化の循環参照を検出するために非常に重要です。もし、`InitPending`状態の定義が再度初期化を試みられた場合、それは循環参照を示唆します。
*   **`InitDone`**: 定義の初期化が完全に完了した状態。

### `OAS2FUNC`, `OAS2MAPR`, `OAS2DOTTYPE`, `OAS2RECV`

これらはGoコンパイラ内部で使用されるオペレーションコード（opcodes）であり、特定の種類の代入や宣言を表します。

*   **`OAS2FUNC`**: 関数呼び出しによる複数値代入（例: `a, b = someFunc()`）
*   **`OAS2MAPR`**: マップ要素への代入（例: `m[key] = value`）
*   **`OAS2DOTTYPE`**: 型アサーション（例: `x.(Type)`）
*   **`OAS2RECV`**: チャネルからの受信（例: `val := <-ch`）

これらの操作は、初期化の文脈で、その結果が他の変数の初期化に影響を与える可能性があるため、初期化順序の管理において考慮される必要があります。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの静的初期化フェーズにおける状態管理の改善にあります。以前のロジックでは、`OAS2FUNC`などの複数値代入を伴う定義の初期化処理において、`defn.Initorder`の状態遷移が不適切でした。

元のコードでは、これらの種類の定義が初期化を開始する際に、`defn.Initorder`が`InitNotStarted`でなければ、すぐに`break`していました。これは、初期化が既に開始されているか完了している場合に、その定義の初期化処理をスキップすることを意図していたと考えられます。しかし、問題は、初期化が「進行中」（`InitPending`）の状態にある定義に対して、その依存関係を解決するために再帰的に`init1`が呼び出された場合、この`break`条件が誤って適用され、循環参照が検出されない可能性があったことです。さらに、`defn.Initorder = InitDone`が依存関係の解決（`for l := defn.Rlist; l != nil; l = l.Next { init1(l.N, out) }`）の**前**に設定されていたため、定義が完全に初期化される前に`InitDone`とマークされてしまう可能性がありました。これにより、コンパイラが初期化の循環を正しく認識できず、無限ループや不正な初期化順序につながる可能性がありました。

この修正は、以下の主要な変更によってこの問題を解決します。

1.  **`InitPending`状態の導入と適切な利用**: `defn.Initorder = InitDone`を`defn.Initorder = InitPending`に変更することで、定義が初期化処理中であることを明示的に示します。これにより、再帰的な呼び出し中に同じ定義が`InitPending`状態であることが検出された場合、それは循環参照であると正しく判断できるようになります。
2.  **`InitDone`状態の遅延設定**: `defn.Initorder = InitDone`を依存関係の解決ループの**後**に移動させることで、その定義が依存するすべての要素が完全に初期化された後にのみ、その定義自体が`InitDone`とマークされることを保証します。
3.  **`break`条件の厳密化**: `if defn.Initorder != InitNotStarted` を `if defn.Initorder == InitDone` に変更することで、初期化が既に**完了している**定義のみがスキップされるようになります。これにより、`InitPending`状態の定義が再帰的に処理される際に、誤ってスキップされることを防ぎます。
4.  **デバッグ出力の削除**: `Dump("nonstatic", defn)` のブロックが削除されました。これは、以前の不適切な状態管理によって誤ってトリガーされていたデバッグ出力、または修正によって不要になったロジックであったと考えられます。

これらの変更により、コンパイラは初期化の依存関係グラフをより正確にトラバースし、循環参照を確実に検出し、すべての定義が正しい順序で初期化されることを保証できるようになります。

## コアとなるコードの解説

`src/cmd/compile/internal/gc/sinit.go` の変更は、`init1` 関数内の `OAS2FUNC`, `OAS2MAPR`, `OAS2DOTTYPE`, `OAS2RECV` のケースに集中しています。

1.  **`if defn.Initorder != InitNotStarted` から `if defn.Initorder == InitDone` への変更**:
    *   **変更前**: 初期化がまだ開始されていない（`InitNotStarted`）状態でない限り、処理を中断していました。これは、初期化が進行中（`InitPending`）の状態であっても中断してしまう可能性があり、循環参照の検出を妨げていました。
    *   **変更後**: 初期化が既に**完了している**（`InitDone`）場合にのみ処理を中断します。これにより、初期化が進行中（`InitPending`）の定義に対して再帰的に`init1`が呼び出された場合でも、処理が継続され、循環参照が正しく検出される道が開かれました。

2.  **`defn.Initorder = InitDone` から `defn.Initorder = InitPending` への変更**:
    *   **変更前**: 依存関係の解決ループに入る前に、定義を`InitDone`とマークしていました。これは、依存する要素がまだ初期化されていないにもかかわらず、その定義が完了したと誤ってマークされる原因となっていました。
    *   **変更後**: 依存関係の解決ループに入る前に、定義を`InitPending`とマークします。これは、この定義の初期化が現在進行中であり、その依存関係が解決されるのを待っている状態であることを明確に示します。これにより、初期化の循環が検出された場合に、コンパイラが適切なエラーを報告できるようになります。

3.  **`defn.Initorder = InitDone` の移動と追加**:
    *   **変更前**: `*out = list(*out, defn)` の前に`InitDone`が設定されていました。
    *   **変更後**: `*out = list(*out, defn)` の**後**に `defn.Initorder = InitDone` が追加されました。これにより、定義が依存するすべての要素が再帰的に初期化され、その定義自体が初期化リストに追加された後にのみ、その定義が完全に初期化されたとマークされることが保証されます。これは、初期化順序の正確性を保つ上で非常に重要です。

4.  **`if defn.Initorder != InitDone { Dump("nonstatic", defn) }` ブロックの削除**:
    *   このブロックは、以前のロジックで`InitDone`が不適切に設定されていたために、誤ってトリガーされる可能性があったデバッグ出力であったと考えられます。新しい、より正確な状態管理ロジックでは、この条件が満たされることがなくなり、したがってこのデバッグ出力も不要になったか、あるいは誤った情報を提供していたため削除されたと推測されます。

`test/fixedbugs/bug13343.go` は、この修正が正しく機能することを検証するためのテストケースです。このテストは、`a, b = f()` と `c = b`、そして `f()` が `c` に依存するという、意図的な初期化の循環参照を定義しています。このテストの目的は、コンパイラがこの循環を検出し、「initialization loop」または「depends upon itself」というエラーメッセージを正しく出力することを確認することです。このテストの追加は、修正が実際に問題の根本原因に対処し、コンパイラが不正な初期化パターンを検出できるようになったことを示しています。

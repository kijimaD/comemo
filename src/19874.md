# [インデックス 19874] ファイルの概要

このコミットは、Goランタイムの`netpoll_epoll.c`ファイルにおける`USED`マクロの使用方法を修正し、`gccgo`コンパイラとの互換性を向上させるものです。具体的には、複数の引数を取る`USED(pd, mode)`という形式から、`USED(pd); USED(mode);`のように単一の引数を取る形式に分割することで、`gccgo`の`USED`マクロの制約に対応しています。

## コミット

Goランタイムの`netpoll_epoll.c`ファイルにおいて、`USED`マクロの呼び出しを、`gccgo`コンパイラの`USED`マクロが単一の変数のみを受け入れるという制約に合わせるために変更しました。これにより、`gccgo`とのマージが簡素化されます。

## 変更の背景

Go言語のランタイムの一部は、パフォーマンスや低レベルなシステム操作のためにC言語で記述されています。これらのCコードは、Goの公式コンパイラである`gc`（Go Compiler）だけでなく、GCC（GNU Compiler Collection）をベースにした`gccgo`コンパイラでもコンパイルされることがあります。

`USED`マクロは、C言語のコードにおいて、変数が使用されていないことによるコンパイラの警告（"unused variable" warning）を抑制するために一般的に使用されます。これは、特定の変数がデバッグ目的や将来の拡張のために宣言されているものの、現在のコードパスでは直接使用されていない場合に特に有用です。コンパイラによっては、未使用の変数を最適化によって削除することがあり、これが予期せぬ動作を引き起こす可能性もありますが、`USED`マクロは通常、変数を「使用済み」とマークすることで、このような最適化や警告を防ぎます。

このコミットの背景には、`gc`コンパイラと`gccgo`コンパイラの間で、`USED`マクロの定義に互換性の問題があったことが挙げられます。具体的には、`gccgo`の`USED`マクロは、一度に単一の変数しか引数として受け付けないという制約がありました。一方、`gc`コンパイラ向けのランタイムコードでは、`USED(var1, var2)`のように複数の変数を一度に渡す形式が使われていた可能性があります。

この不一致が、`gc`と`gccgo`の間でランタイムコードをマージする際の障壁となっていたため、`gccgo`の制約に合わせて`USED`マクロの呼び出し方を変更する必要がありました。

## 前提知識の解説

### GoランタイムとC言語

Go言語は、その大部分がGo自身で書かれていますが、ガベージコレクション、スケジューラ、ネットワークI/Oなど、OSとの低レベルなインタラクションを必要とする一部のコアな部分はC言語（またはアセンブリ言語）で記述されています。これらのC言語部分は、Goプログラムが効率的に動作するための基盤を提供します。

### `gc`コンパイラと`gccgo`コンパイラ

*   **`gc` (Go Compiler)**: Go言語の公式かつ主要なコンパイラです。Goチームによって開発・メンテナンスされており、Goの最新機能や最適化が最も早く取り入れられます。
*   **`gccgo`**: GCCのフロントエンドとして実装されたGoコンパイラです。GCCの最適化バックエンドを利用できるという利点がありますが、`gc`コンパイラとは異なる実装の詳細や、Go言語の機能サポートに時間差がある場合があります。特に、ランタイムのCコードのコンパイルにおいては、GCCのCコンパイラとしての特性が影響します。

### `USED`マクロ

C言語プログラミングにおいて、`USED`のようなマクロは、コンパイラが特定の変数が未使用であると判断し、警告を発したり、最適化によって削除したりするのを防ぐために使用されます。典型的な実装としては、変数のアドレスを一時的に取得したり、変数を揮発性（volatile）として宣言したりすることで、コンパイラに変数が「使用されている」と認識させます。

例えば、以下のような定義が考えられます（実際のGoランタイムの定義とは異なる可能性がありますが、概念は同じです）：

```c
#define USED(x) ((void)(x))
```

このマクロは、引数`x`を`void`型にキャストすることで、その値が使用されているかのように見せかけ、コンパイラが未使用の警告を発するのを防ぎます。

### `netpoll_epoll.c`

このファイルは、Linuxシステムにおけるネットワークポーリング（network polling）の実装に関連するGoランタイムのCコードです。Linuxでは、`epoll`というシステムコールが、多数のファイルディスクリプタ（ネットワークソケットなど）からのI/Oイベントを効率的に監視するために使用されます。`netpoll_epoll.c`は、GoのネットワークI/Oが`epoll`メカニズムを介してどのようにOSと連携するかを定義する部分です。

## 技術的詳細

このコミットの技術的な核心は、`USED`マクロの引数の扱いに関する`gc`と`gccgo`の間の差異を解消することにあります。

元のコードでは、`runtime·netpollarm`関数内で`USED(pd, mode);`という形式で`pd`と`mode`の2つの変数を`USED`マクロに渡していました。これは、`gc`コンパイラがコンパイルするCコードでは問題なく機能していたと考えられます。しかし、`gccgo`が使用するCコンパイラ（GCC）の`USED`マクロの定義が、単一の引数しか受け付けないように設計されていたため、`gccgo`でコンパイルするとエラーまたは警告が発生していました。

この問題を解決するために、コミットでは`USED(pd, mode);`を`USED(pd); USED(mode);`という2つの独立した`USED`マクロ呼び出しに分割しました。これにより、各呼び出しが単一の引数のみを持つようになり、`gccgo`の`USED`マクロの制約を満たすことができます。

この変更は、コードの機能的な動作には影響を与えません。`pd`と`mode`の両方の変数が引き続き「使用済み」としてマークされ、コンパイラによる不要な最適化や警告が抑制されます。しかし、この変更によって、GoランタイムのCコードが`gc`と`gccgo`の両方のコンパイラで問題なくコンパイルできるようになり、両者の間のコードベースのマージや同期が容易になります。

これは、Goプロジェクトが複数のコンパイラをサポートし、異なる環境でのビルドの互換性を維持するために、低レベルな部分でどのように調整を行っているかを示す良い例です。

## コアとなるコードの変更箇所

```diff
--- a/src/pkg/runtime/netpoll_epoll.c
+++ b/src/pkg/runtime/netpoll_epoll.c
@@ -55,7 +55,8 @@ runtime·netpollclose(uintptr fd)
 void
 runtime·netpollarm(PollDesc* pd, int32 mode)
 {
-	USED(pd, mode);
+	USED(pd);
+	USED(mode);
 	runtime·throw("unused");
 }
```

## コアとなるコードの解説

変更は`src/pkg/runtime/netpoll_epoll.c`ファイルの`runtime·netpollarm`関数内で行われています。

*   **変更前**:
    ```c
    USED(pd, mode);
    ```
    この行では、`PollDesc* pd`と`int32 mode`という2つの変数を`USED`マクロに渡していました。これは、`gc`コンパイラ環境では問題なかったものの、`gccgo`コンパイラではエラーまたは警告の原因となっていました。

*   **変更後**:
    ```c
    USED(pd);
    USED(mode);
    ```
    変更後では、元の1つの`USED`マクロ呼び出しが、`pd`と`mode`それぞれに対する2つの独立した`USED`マクロ呼び出しに分割されています。これにより、各`USED`呼び出しが単一の引数のみを受け取るようになり、`gccgo`コンパイラの`USED`マクロの制約に適合します。

*   **`runtime·throw("unused");`**:
    この行は、`runtime·netpollarm`関数が実際には使用されないことを示すためのものです。これは、特定のプラットフォームやビルド構成でのみ使用される関数や、将来の機能のためのプレースホルダーとして存在する場合によく見られます。`USED`マクロの目的は、この関数がコンパイルされる際に、引数`pd`と`mode`が未使用であるというコンパイラ警告を防ぐことです。

この変更は、GoランタイムのCコードのコンパイル互換性を高めるための、小さくも重要な修正です。

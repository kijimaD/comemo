## 変更の背景

このコミットは、Goランタイムにおけるチャネル操作の重要な移行を示しています。それまでC言語（またはGoとCのハイブリッドな`goc`ファイル）で実装されていたチャネル関連の低レベルなロジックの一部を、純粋なGo言語で再実装する取り組みの第一弾です。具体的には、チャネルへの送信操作を司る`chansend1`関数とその関連ロジックがGo言語に移植されました。

この変更の背景には、以下のような複数の理由が考えられます。

1.  **保守性の向上**: Go言語でGoランタイムのコードを書くことで、Go開発者にとってコードの理解、デバッグ、および保守が容易になります。C言語とGo言語が混在するコードベースは、複雑性を増し、開発の障壁となる可能性があります。
2.  **Goの機能活用**: Go言語の持つ強力な型システム、ガベージコレクタ、および並行処理のプリミティブをランタイム自身が活用できるようになります。これにより、メモリ管理の効率化や、より安全なコードの記述が可能になります。
3.  **統一された開発体験**: ランタイムコードもGo言語で書かれることで、Go言語全体のエコシステムがより統一され、開発者がGo言語の知識をランタイムの理解にも応用できるようになります。
4.  **将来的な最適化の可能性**: Go言語で実装されたチャネル操作は、Goコンパイラやランタイムの進化に伴い、より高度な最適化の恩恵を受けやすくなります。

このコミットは「part 1」と明記されており、チャネル操作のGo言語への移行が段階的に進められる計画であったことを示唆しています。

## 前提知識の解説

このコミットの技術的詳細を理解するためには、以下のGo言語およびランタイムに関する知識が必要です。

*   **Goのチャネル (Channels)**:
    Go言語におけるチャネルは、ゴルーチン間で値を安全に送受信するための主要な手段です。チャネルは型付けされており、特定の型の値のみを送受信できます。バッファリングされたチャネルとバッファリングされていない（同期）チャネルの2種類があります。
    *   **バッファリングされていないチャネル**: 送信操作は受信操作が完了するまでブロックし、受信操作は送信操作が完了するまでブロックします。これにより、ゴルーチン間の同期が保証されます。
    *   **バッファリングされたチャネル**: 指定された数の要素を格納できる内部バッファを持ちます。バッファが満杯でない限り送信はブロックせず、バッファが空でない限り受信はブロックしません。

*   **Goランタイム (Go Runtime)**:
    Goランタイムは、Goプログラムの実行を管理する低レベルなシステムです。これには、ゴルーチンのスケジューリング、メモリ割り当てとガベージコレクション、スタック管理、そしてチャネル操作などの組み込み機能の実装が含まれます。ランタイムのコードは、パフォーマンスと効率のためにC言語、アセンブリ言語、そしてGo言語で書かれています。

*   **`hchan` 構造体**:
    Goランタイム内部でチャネルを表現するために使用される中心的なデータ構造です。`hchan`は、チャネルのバッファ（存在する場合）、送受信を待機しているゴルーチンのキュー（`sendq`と`recvq`）、チャネルの状態を保護するためのミューテックス（`lock`）、要素の型情報、およびチャネルが閉じられているかどうかのフラグなど、チャネルの動作に必要なすべての情報を保持します。

*   **`sudog` 構造体**:
    `sudog`（"scheduler utility goroutine" の略とされることもあります）は、チャネル操作（送信または受信）でブロックされているゴルーチンを表すためにランタイムが使用する構造体です。`sudog`は、ブロックされているゴルーチンへのポインタ、チャネル操作の完了時に書き込まれる要素へのポインタ、および他の`sudog`へのリンク（キューを形成するため）などの情報を含みます。これにより、ランタイムはどのゴルーチンがどのチャネルで何を待っているかを追跡し、適切なタイミングでそれらを再開できます。

*   **`goc` ファイル**:
    Go言語の初期のバージョンでは、ランタイムコードの一部は`.goc`拡張子を持つファイルで記述されていました。これらはC言語の構文に似ていますが、Goのランタイムプリミティブや型を使用できるようにする特別なプリプロセッサによって処理されていました。このコミットのように、`goc`ファイルから純粋なGoファイルへの移行は、ランタイムのGo言語化の進展を示しています。

*   **`gopark` と `goready`**:
    Goランタイムのスケジューラがゴルーチンを一時停止（ブロック）させたり、実行可能状態に戻したりするために使用する関数です。チャネル操作でゴルーチンがブロックされる場合、`gopark`が呼び出され、ゴルーチンは待機キューに入れられます。チャネル操作が完了し、ゴルーチンが再開可能になると、`goready`が呼び出され、ゴルーチンは実行キューに戻されます。

## 技術的詳細

このコミットの技術的詳細の核心は、チャネルの送信操作、特に`chansend1`関数がC言語からGo言語に移植された点にあります。

1.  **`chansend1`の役割**:
    `chansend1`は、Goコンパイラによって生成されるランタイム関数であり、Goのコードで`ch <- x`のようなチャネル送信ステートメントが記述されたときに呼び出されます。この関数は、実際のチャネル送信ロジックを実装する`chansend`関数の薄いラッパーとして機能します。`chansend1`は、チャネルの型、チャネル自体、送信する要素、そして呼び出し元のプログラムカウンタ（`callerpc`）を`chansend`に渡します。`block`引数は常に`true`に設定され、これはGoのチャネル送信がデフォルトでブロッキング操作であることを示します。

2.  **`chansend`のロジック**:
    `chansend`関数は、チャネルのタイプ（同期チャネルかバッファリングされたチャネルか）に応じて異なるパスをたどります。
    *   **同期チャネル (バッファサイズ0)**:
        送信側は、対応する受信側が準備できるまでブロックします。`chansend`はまず、チャネルの`recvq`（受信待機キュー）にゴルーチンがいないかを確認します。もし待機している受信側がいれば、そのゴルーチンをキューから取り出し、送信データを直接その受信側の要素にコピーし、受信側ゴルーチンを`goready`で再開させます。
        待機している受信側がいない場合、送信側ゴルーチンは`sudog`構造体を作成し、自身の情報を格納してチャネルの`sendq`（送信待機キュー）に追加します。その後、`goparkunlock`を呼び出してチャネルのロックを解放し、自身をスリープさせます。受信側がデータを受け取ったときに、このゴルーチンは`goready`によって再開されます。
    *   **バッファリングされたチャネル**:
        `chansend`はまず、チャネルのバッファが満杯かどうかを確認します。バッファに空きがある場合、送信データはバッファに直接コピーされ、`qcount`（バッファ内の要素数）が増加します。その後、`recvq`に待機している受信側ゴルーチンがいれば、そのゴルーチンを`goready`で再開させます（バッファからデータを読み取れるようになったため）。
        バッファが満杯の場合、同期チャネルの場合と同様に、送信側ゴルーチンは`sudog`を作成して`sendq`に追加し、`goparkunlock`で自身をスリープさせます。バッファに空きができたときに、このゴルーチンは再開されます。

3.  **`sudog`構造体の拡張**:
    このコミットでは、`src/pkg/runtime/runtime.h`と`src/cmd/gc/select.c`において`sudog`構造体に`waitlink`フィールドが追加されています。これは、ゴルーチンが複数のチャネル操作で待機する可能性がある場合に、それらの`sudog`構造体を連結するためのリストを形成するために使用されます。特に、`G`（ゴルーチン）構造体にも`waiting`フィールドが追加され、そのゴルーチンが現在待機している`sudog`のリストの先頭を指すようになりました。これにより、ランタイムはゴルーチンが待機しているすべてのチャネル操作を効率的に管理できます。

4.  **スタック管理との連携**:
    `src/pkg/runtime/stack.c`では、スタックのサイズ変更（シュリンクなど）が行われた際に、スタック上のポインタを適切に調整するための`adjustsudogs`関数が追加され、`copystack`関数から呼び出されるようになりました。これは、`sudog`構造体が指す要素（`elem`）がスタック上に存在する場合、スタックが移動した際にそのポインタも更新する必要があるためです。これにより、チャネル操作でブロックされたゴルーチンのスタックが安全に管理されるようになります。

5.  **アセンブリコードの変更**:
    `src/pkg/reflect/asm_*.s`ファイル（386, amd64, amd64p32, arm）には、`makechan`関数へのジャンプ命令が追加されています。これは、`reflect`パッケージが`makechan`を呼び出す際に、Go言語で実装された新しい`makechan`関数に正しくディスパッチされるようにするためです。

6.  **初期化の変更**:
    `src/pkg/runtime/proc.c`から`runtime·chaninit()`の呼び出しが削除されました。これは、チャネルの初期化ロジックがGo言語の`chan.go`内に統合され、C言語側の明示的な初期化が不要になったことを示しています。

全体として、このコミットはGoランタイムのチャネル実装をよりGo言語中心に移行させるための重要な一歩であり、Goの並行処理モデルの基盤となる部分の保守性と効率性を向上させることを目的としています。

    以前にC言語とGoのハイブリッド形式でチャネル操作を実装していたこのファイルから、`makechan`や`chansend1`などの関数が削除されました。これにより、Go言語への移行が明確に示されています。

*   **`src/pkg/runtime/runtime.h` (変更)**:
    Goランタイムの主要なヘッダファイルであり、`SudoG`構造体の定義がここに追加されました。特に、`SudoG`に`waitlink`フィールドが、`G`（ゴルーチン）構造体に`waiting`フィールドが追加されています。

*   **`src/pkg/runtime/stack.c` (変更)**:
    スタック管理に関連するファイルで、`adjustsudogs`関数が追加され、`copystack`関数内で呼び出されるようになりました。これにより、スタックの移動時に`sudog`が指す要素のポインタが適切に調整されます。

*   **`src/cmd/gc/select.c` (変更)**:
    Goコンパイラの`select`文処理に関連するファイルで、`sudog`構造体の定義が更新され、`waitlink`フィールドが追加されました。これは、`runtime.h`での変更と同期しています。

## コアとなるコードの解説

*   **`src/pkg/runtime/chan.go` の `makechan` 関数**:
    ```go
    func makechan(t *chantype, size int64) *hchan {
        // ... (エラーチェック、アライメント調整など)
        var c *hchan
        if elem.kind&kindNoPointers != 0 || size == 0 {
            // ポインタを含まない要素、またはバッファサイズ0の場合、hchanとバッファをまとめて割り当て
            c = (*hchan)(gomallocgc(hchanSize+uintptr(size)*uintptr(elem.size), nil, flagNoScan))
            if size > 0 && elem.size != 0 {
                c.buf = (*uint8)(add(unsafe.Pointer(c), hchanSize))
            } else {
                c.buf = (*uint8)(unsafe.Pointer(c)) // race detector uses this location for synchronization
            }
        } else {
            // ポインタを含む要素の場合、hchanとバッファを別々に割り当て
            c = new(hchan)
            c.buf = (*uint8)(newarray(elem, uintptr(size)))
        }
        c.elemsize = uint16(elem.size)
        c.elemtype = elem
        c.dataqsiz = uint(size)
        return c
    }
    ```
    この関数は、新しいチャネルを作成し、`hchan`構造体を初期化します。要素の型がポインタを含まない場合やバッファサイズが0の場合は、`hchan`構造体とバッファ領域を連続したメモリとして一度に割り当てます。そうでない場合は、`hchan`とバッファを別々に割り当てます。これは、ガベージコレクタがポインタを追跡する際の効率を考慮した設計です。

*   **`src/pkg/runtime/chan.go` の `chansend` 関数**:
    ```go
    func chansend(t *chantype, c *hchan, ep unsafe.Pointer, block bool, callerpc uintptr) bool {
        // ... (nilチャネル、クローズ済みチャネルのチェック、競合検出など)

        golock(&c.lock) // チャネルのロックを取得

        if c.closed != 0 {
            gounlock(&c.lock)
            panic("send on closed channel")
        }

        if c.dataqsiz == 0 { // 同期チャネル (バッファなし)
            sg := c.recvq.dequeue() // 受信待機ゴルーチンがいるか確認
            if sg != nil { // 待機している受信側がいる場合
                // ... (データコピー、受信側ゴルーチンの再開)
                gounlock(&c.lock)
                goready(recvg)
                return true
            }
            // ... (受信側がいない場合、送信側ゴルーチンをブロック)
            goparkunlock(&c.lock, "chan send")
            // ... (再開後の処理)
            return true
        }

        // 非同期チャネル (バッファあり)
        for c.qcount >= c.dataqsiz { // バッファが満杯の場合
            // ... (送信側ゴルーチンをブロック)
            goparkunlock(&c.lock, "chan send")
            // ... (再開後の処理、ロック再取得)
            golock(&c.lock)
            if c.closed != 0 {
                gounlock(&c.lock)
                panic("send on closed channel")
            }
        }

        // バッファにデータを書き込む
        memmove(chanbuf(c, c.sendx), ep, uintptr(c.elemsize))
        c.sendx++
        if c.sendx == c.dataqsiz {
            c.sendx = 0
        }
        c.qcount++

        // 待機している受信側ゴルーチンを起こす
        sg := c.recvq.dequeue()
        if sg != nil {
            // ... (受信側ゴルーチンの再開)
            gounlock(&c.lock)
            goready(recvg)
        } else {
            gounlock(&c.lock)
        }
        return true
    }
    ```
    `chansend`関数は、チャネルのロックを取得し、チャネルがクローズされていないかを確認します。その後、チャネルが同期チャネルかバッファリングされたチャネルかに応じて処理を分岐します。同期チャネルの場合、待機している受信側がいれば直接データを渡し、いなければ送信側をブロックします。バッファリングされたチャネルの場合、バッファに空きがあればデータを書き込み、満杯であれば送信側をブロックします。データが書き込まれた後、待機している受信側がいればそれを再開させます。

*   **`src/pkg/runtime/runtime.h` の `SudoG` 構造体**:
    ```c
    struct	SudoG
    {
    	G*	g;
    	uint32*	selectdone;
    	SudoG*	link;
    	byte*	elem;		// data element
    	int64	releasetime;
    	int32	nrelease;	// -1 for acquire
    	SudoG*	waitlink;	// G.waiting list
    };
    ```
    このC言語の構造体定義は、Go言語の`sudog`構造体に対応します。`waitlink`フィールドの追加は、一つのゴルーチンが複数のチャネル操作で待機する可能性がある場合に、それらの`sudog`インスタンスを連結するためのものです。これにより、ゴルーチンが待機しているすべてのチャネル操作を効率的に管理できるようになります。

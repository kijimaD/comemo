# [インデックス 26159] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおけるレジスタ割り当てとスタック割り当てのロジックを改善するものです。特に、マージエッジ（複数の実行パスが合流する点）での不要なコピー命令の生成を削減し、全体的なコード生成の効率とパフォーマンスを向上させることを目的としています。Goの`go1 TimeParse`ベンチマークで約12%の性能向上を達成しています。

## コミット

```
commit 7d9f1067d1c8a2d0252fa2a115f1d016f94f7087
Author: Keith Randall <khr@golang.org>
Date:   Thu Dec 17 10:01:24 2015 -0800

    [dev.ssa] cmd/compile: better register allocator
    
    Reorder how register & stack allocation is done.  We used to allocate
    registers, then fix up merge edges, then allocate stack slots.  This
    lead to lots of unnecessary copies on merge edges:
    
    v2 = LoadReg v1
    v3 = StoreReg v2
    
    If v1 and v3 are allocated to the same stack slot, then this code is
    unnecessary.  But at regalloc time we didn't know the homes of v1 and
    v3.
    
    To fix this problem, allocate all the stack slots before fixing up the
    merge edges.  That way, we know what stack slots values use so we know
    what copies are required.
    
    Use a good technique for shuffling values around on merge edges.
    
    Improves performance of the go1 TimeParse benchmark by ~12%
    
    Change-Id: I731f43e4ff1a7e0dc4cd4aa428fcdb97812b86fa
    Reviewed-on: https://go-review.googlesource.com/17915
    Reviewed-by: David Chase <drchase@google.com>
```

## 変更の背景

GoコンパイラのSSAバックエンドにおける従来のレジスタ割り当てプロセスには、非効率な点がありました。具体的には、以下の順序で処理が行われていました。

1.  レジスタ割り当て
2.  マージエッジの修正（Phi関数の解決など）
3.  スタック割り当て

この順序では、マージエッジを修正する際に、値がレジスタとスタックの間で不必要にコピーされる問題が発生していました。例えば、`v1`がレジスタにロードされ、`v2`がそのレジスタからスタックにストアされるような状況 (`v2 = LoadReg v1`, `v3 = StoreReg v2`) を考えます。もし`v1`と`v3`が最終的に同じスタック位置に割り当てられる場合、これらの`LoadReg`と`StoreReg`命令は完全に冗長となります。しかし、レジスタ割り当ての段階では、`v1`と`v3`が最終的にどのスタック位置に割り当てられるかを知ることができなかったため、コンパイラは安全のためにこれらのコピーを挿入していました。

この冗長なコピーは、生成されるコードのサイズを増やし、実行速度を低下させる原因となっていました。特に、多くのマージエッジが存在する複雑な制御フローを持つ関数では、この問題が顕著でした。

## 前提知識の解説

### SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの最適化において広く用いられる中間表現 (IR) の一種です。この形式では、各変数がただ一度だけ定義されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、より効果的な最適化が可能になります。

*   **利点**: 変数の定義と使用の関係が明確になり、デッドコード削除、定数伝播、共通部分式除去などの最適化が容易になります。
*   **Phi関数 (Φ関数)**: SSA形式の重要な要素で、複数の制御フローパスが合流するブロックの先頭に挿入されます。異なるパスから来る同じ論理的な変数に対して、どの値を使用すべきかを「選択」する役割を果たします。例えば、`x = Φ(x_1, x_2)` は、制御フローが`x_1`が定義されたパスから来た場合は`x_1`を、`x_2`が定義されたパスから来た場合は`x_2`を`x`に割り当てることを意味します。

### レジスタ割り当て (Register Allocation)

レジスタ割り当ては、コンパイラのバックエンドにおける重要なフェーズの一つです。プログラムの実行中に頻繁に使用される変数を、CPUの高速なレジスタに割り当てることを目的とします。レジスタはメモリよりもアクセス速度が格段に速いため、適切にレジスタ割り当てを行うことでプログラムの実行性能を大幅に向上させることができます。

*   **課題**: CPUのレジスタ数は限られているため、どの変数をレジスタに割り当てるか、いつレジスタからメモリに退避 (spill) させるか、といった決定が性能に大きく影響します。

### スタック割り当て (Stack Allocation)

スタック割り当ては、レジスタに割り当てられなかった変数や、関数呼び出しの引数、ローカル変数などをプログラムの実行スタック上に配置するプロセスです。

*   **課題**: スタック上の変数はレジスタ変数よりもアクセスが遅いため、可能な限りレジスタに割り当てることが望ましいですが、レジスタ数の制約からスタックへの割り当ても不可欠です。

### マージエッジ (Merge Edges)

制御フローグラフ (CFG) において、複数の基本ブロックが単一の基本ブロックに合流する際に形成されるエッジを指します。SSA形式では、これらのマージエッジの合流点にPhi関数が配置され、異なるパスから伝播してきた値の選択を表現します。

### LoadReg/StoreReg

GoコンパイラのSSAバックエンドでは、レジスタとメモリ（スタック）間の値の移動を明示的に表すために`OpLoadReg`と`OpStoreReg`といった命令が使用されます。

*   `OpLoadReg v`: `v`が保持する値をレジスタにロードする。
*   `OpStoreReg v`: `v`が保持する値をメモリ（スタック）にストアする。

### Rematerializeable values (再生成可能な値)

再生成可能な値とは、レジスタからメモリに退避させる代わりに、必要になったときにその値を再計算（再生成）する方がコストが低いような値のことです。例えば、小さな定数や、引数なしで計算できる単純な値などがこれに該当します。再生成可能な値は、レジスタの競合を減らし、メモリへの退避・ロードのオーバーヘッドを回避するのに役立ちます。

## 技術的詳細

このコミットの核心は、レジスタ割り当てとスタック割り当ての順序を変更し、マージエッジでの値の「シャッフル」処理を改善した点にあります。

**新しい割り当て順序:**

1.  **スタック割り当て**: まず、レジスタに割り当てられないすべての値（`OpStoreReg`やスタックベースのPhi関数など）に対してスタック上の位置を割り当てます。この段階で、どの値がどのスタック位置を使用するかが確定します。
2.  **レジスタ割り当て**: その後、レジスタ割り当てを行います。
3.  **マージエッジの修正**: 最後に、マージエッジでの値の移動（シャッフル）を修正します。

この新しい順序により、マージエッジを処理する時点で、値がレジスタにあるかスタックにあるか、そしてどのスタック位置にあるかが既知となります。これにより、前述の`v2 = LoadReg v1`, `v3 = StoreReg v2`のような冗長なコピーを正確に特定し、削除することが可能になります。`v1`と`v3`が同じスタック位置に割り当てられていることが分かれば、`LoadReg`と`StoreReg`は不要と判断できます。

**マージエッジでの値のシャッフル技術:**

コミットは、マージエッジで値を効率的にシャッフルするための新しいテクニックを導入しています。これは、`regalloc.go`内の`shuffle`関数と`edgeState`構造体によって実装されています。

*   **`edgeState`構造体**: マージエッジ (`p` -> `b`) における値の移動状態を管理します。
    *   `cache`: 各プリレジスタ割り当て値 (pre-regalloc value) が、どのキャッシュされた値（`Value`オブジェクト）に対応するかを追跡します。
    *   `contents`: 各ロケーション（レジスタまたはスタック）に現在どの値が格納されているかを記録します。
    *   `destinations`: そのエッジで値が最終的に到達すべき目標ロケーションのリストです。
    *   `usedRegs`, `uniqueRegs`, `finalRegs`: レジスタの使用状況を追跡するためのマスクです。
*   **`shuffle`関数**: 各マージエッジに対して`edgeState`を初期化し、`process`関数を呼び出して値の移動を解決します。
*   **`process`関数**: `destinations`リストが空になるまで、`processDest`を繰り返し呼び出します。値の移動が循環している場合（例: A->B->C->A）、一時レジスタに値をコピーしてサイクルを解消するロジックが含まれています。
*   **`processDest`関数**: 特定の値 (`vid`) を特定のロケーション (`loc`) に移動するためのコードを生成します。
    *   値が既に正しい位置にある場合は何もしません。
    *   移動元と移動先のロケーション（レジスタかスタックか）に応じて、`OpCopy`、`OpLoadReg`、`OpStoreReg`などの適切な命令を生成します。
    *   再生成可能な値の場合、メモリからロードする代わりにその場で再生成します。
    *   メモリからメモリへの移動が必要な場合は、一時レジスタを使用します。
*   **`set`関数**: ロケーションのコンテンツを更新し、`cache`とレジスタ使用状況のマスクを適切に更新します。
*   **`erase`関数**: ロケーションから値を削除し、`cache`とレジスタ使用状況のマスクを更新します。値が最終的な目的地に到達している場合、その移動を`extra`リストに追加し、後で再処理されるようにします。
*   **`findRegFor`関数**: 一時的なコピーに使用できるレジスタを探します。未使用のレジスタ、次に非ユニークなレジスタ（他のコピーが存在するレジスタ）、最後にユニークなレジスタ（唯一のコピーを持つレジスタ）の順で優先します。適切なレジスタが見つからない場合は、レジスタをスタックに退避させて空きを作ります。

この新しいシャッフルアルゴリズムは、マージエッジでの値の移動をより正確かつ効率的に処理し、不要なコピーを削減することで、生成されるコードの品質を向上させます。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   `src/cmd/compile/internal/ssa/compile.go`:
    *   `passes`配列から`"stackalloc"`の項目が削除され、`regalloc`の後に`stackalloc`が実行される順序が変更されました。
    *   `passOrder`から`"regalloc", "stackalloc"`の依存関係が削除されました。
*   `src/cmd/compile/internal/ssa/flagalloc.go`:
    *   マージブロックの先頭でフラグレジスタを使用しないようにするロジックが削除されました。これは、新しいレジスタ割り当てロジックで不要になったためと考えられます。
*   `src/cmd/compile/internal/ssa/regalloc.go`:
    *   最も広範な変更が行われています。
    *   `regAllocState`構造体に`endRegs`, `startRegs`, `spillLive`などのフィールドが追加され、ブロックの開始時と終了時のレジスタ状態およびライブなスピル位置を追跡するようになりました。
    *   `regalloc`関数内で、スタック割り当てがマージエッジ処理の前に実行されるように変更されました。
    *   `shuffle`関数、`edgeState`構造体、および関連するヘルパー関数 (`setup`, `process`, `processDest`, `set`, `erase`, `findRegFor`) が追加され、マージエッジでの値の移動を効率的に処理するロジックが実装されました。
    *   `rematerializeable`関数のロジックが更新され、フラグレジスタをクリーンアップする命令の扱いが改善されました。
    *   `needReg`フィールドが`valState`に移動され、`s.values[v.ID].needReg`としてアクセスされるようになりました。
*   `src/cmd/compile/internal/ssa/stackalloc.go`:
    *   `stackalloc`関数が大幅に書き直されました。
    *   `stackAllocState`構造体が導入され、スタック割り当ての状態を管理します。
    *   `computeLive`関数が追加され、スタックに割り当てられる値のライブネス情報を計算します。
    *   `buildInterferenceGraph`関数が追加され、スタック割り当てにおける干渉グラフを構築します。
    *   `isStackPhi`関数が削除され、Phi関数のスタック割り当てに関するロジックが`stackalloc`関数内に統合されました。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/regalloc.go`

*   **`regAllocState`の変更**:
    *   `endRegs [][]endReg`: 各ブロックの終了時のレジスタ状態を`endReg`のリストとして保存します。`endReg`はレジスタ、プリレジスタ割り当て値、キャッシュされた値を含みます。
    *   `startRegs [][]startReg`: マージブロックの開始時のレジスタ状態を`startReg`のリストとして保存します。`startReg`はレジスタとプリレジスタ割り当て値のIDを含みます。
    *   `spillLive [][]ID`: 各ブロックの終了時にライブなスピル位置にある値のIDを保存します。これは`stackalloc`に渡され、スタック割り当てのライブネス情報として利用されます。
    *   `valState`に`needReg`と`rematerializeable`フィールドが追加され、値がレジスタを必要とするか、再生成可能かをキャッシュするようになりました。
*   **`regalloc`関数のフロー変更**:
    *   レジスタ割り当てのメインループの後に、`stackalloc`が呼び出されるようになりました。これにより、マージエッジを処理する前にスタック位置が確定します。
    *   `shuffle(stacklive)`が呼び出され、マージエッジの修正が新しいシャッフルアルゴリズムによって行われます。
*   **`shuffle`関数と`edgeState`**:
    *   `shuffle`は、`f.Blocks`をイテレートし、`len(b.Preds) > 1`（マージブロック）の場合に`edgeState`を初期化して`process`を呼び出します。
    *   `edgeState.setup`は、前身ブロックの終了時のレジスタ状態 (`srcReg`)、マージブロックの開始時のレジスタ状態 (`dstReg`)、およびライブなスピル位置 (`stacklive`) を基に、`edgeState`の`cache`、`contents`、`destinations`を構築します。
    *   `edgeState.process`は、`destinations`リストが空になるまで`processDest`を呼び出し、値の移動を解決します。循環依存がある場合は、一時レジスタへのコピーで解決します。
    *   `edgeState.processDest`は、移動元と移動先のロケーションタイプ（レジスタ/スタック）に応じて、`OpCopy`, `OpLoadReg`, `OpStoreReg`などの命令を生成し、`p`ブロック（前身ブロック）の末尾に追加します。
    *   `edgeState.set`と`edgeState.erase`は、`edgeState`内の`cache`、`contents`、レジスタ使用状況マスクを更新するヘルパー関数です。
    *   `edgeState.findRegFor`は、一時的な値の移動に使用するレジスタを選択します。未使用レジスタ、非ユニークなレジスタ、最終レジスタでない非ユニークなレジスタの順で優先し、必要に応じてレジスタをスピルします。

### `src/cmd/compile/internal/ssa/stackalloc.go`

*   **`stackAllocState`の導入**:
    *   `f`: 現在の関数。
    *   `values`: 各値の型、スピル情報、スタック位置が必要か (`needSlot`) を保持する`stackValState`の配列。
    *   `live`: 各ブロックの終了時にライブなスタック値のIDリスト。
    *   `interfere`: 各値が干渉する他の値のIDリスト（干渉グラフ）。
*   **`stackalloc`関数の変更**:
    *   `stackAllocState`を初期化し、`computeLive`と`buildInterferenceGraph`を呼び出して、スタック割り当てに必要な情報を準備します。
    *   引数 (`OpArg`) は事前に割り当てられたスタック位置を持つため、最初に処理されます。
    *   `names`マップを使用して、名前付き変数に優先的にスタック位置を割り当てます。
    *   干渉グラフ (`s.interfere`) を利用して、干渉しない値間でスタック位置を共有できるように、空いているスタック位置を探して割り当てます。
*   **`computeLive`関数**:
    *   `regalloc.go`の`computeLive`と同様に、後順序 (postorder) でブロックをイテレートし、スタック位置を必要とする値のライブネス情報を逆方向に伝播させます。
    *   `spillLive`情報（`regalloc`から渡される）も考慮に入れ、より正確なライブネスを計算します。
*   **`buildInterferenceGraph`関数**:
    *   各ブロックを逆方向にイテレートし、スタック位置を必要とする値 (`needSlot`) の干渉グラフを構築します。
    *   ある値が定義される際に、ライブである他の値と干渉すると判断されます。同じ型を持つ値のみが干渉すると見なされます。

これらの変更により、Goコンパイラはレジスタとスタックの割り当てをより協調的に行い、特にマージエッジでのコード生成の効率を大幅に向上させています。

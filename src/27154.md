# [インデックス 27154] ファイルの概要

このコミットは、Go言語のアセンブラ（`cmd/asm`）における`DATA`擬似命令の処理方法をリファクタリングするものです。具体的には、`cmd/internal/obj`パッケージで定義されていた`obj.ADATA`という定数を廃止し、アセンブラが`"DATA"`という文字列を直接特別な擬似命令として認識するように変更しています。これにより、アセンブラの内部ロジックが簡素化され、`cmd/asm`と`cmd/internal/obj`間の特定の依存関係が解消されます。

## 変更の背景

この変更の背景には、Goアセンブラが`DATA`擬似命令を処理する方法の簡素化と、ツールチェーン内のパッケージ間の依存関係の最適化があります。

以前のGoアセンブラでは、`DATA`のような擬似命令も、実際のCPU命令と同様に`cmd/internal/obj`パッケージで定義された`obj.As`型（命令コードを表す列挙型）の定数（`obj.ADATA`）にマッピングされていました。そして、アセンブラ（`cmd/asm`）はこの`obj.ADATA`定数を使用して`DATA`擬似命令を識別していました。

しかし、`DATA`擬似命令は、CPUが直接実行する機械語命令ではなく、アセンブラに対する「データセクションを定義する」という指示です。このようなアセンブラディレクティブを、リンカやオブジェクトファイル生成の低レベルな抽象化を扱う`cmd/internal/obj`パッケージの汎用的な命令コードリストに含めることは、設計上冗長であると判断された可能性があります。

このコミットは、`DATA`擬似命令を`obj.As`定数として扱うのではなく、アセンブラが直接`"DATA"`という文字列リテラルとして認識し、処理するように変更することで、この冗長性を排除し、`cmd/asm`と`cmd/internal/obj`間の結合度を低減することを目的としています。これにより、`obj`パッケージは純粋に機械語命令やリンカが扱うべき低レベルな概念に集中できるようになります。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **Goアセンブラ (`cmd/asm`)**:
    Go言語は、特定のパフォーマンス要件やハードウェアとの直接的なやり取りが必要な場合に、Goの構文に似た独自のPlan 9アセンブラを使用します。これは一般的なGAS (GNU Assembler) 構文とは異なり、より簡潔で、Goの型システムと統合しやすいように設計されています。`cmd/asm`は、`.s`拡張子を持つアセンブリソースファイルを解析し、オブジェクトファイルに変換する役割を担います。

2.  **擬似命令 (Pseudo-operations / Assembler Directives)**:
    擬似命令は、アセンブラに対する指示であり、CPUが直接実行する機械語命令ではありません。これらは、メモリ領域の確保、データの初期化、シンボルの定義、コードセクションの指定など、アセンブリプロセスを制御するために使用されます。Goアセンブラにおける主要な擬似命令には以下のようなものがあります。
    *   `TEXT`: コードセクションを定義し、関数エントリポイントを示す。
    *   `DATA`: 初期化されたデータセクションを定義する。
    *   `GLOBL`: シンボルをグローバルに公開する。
    *   `FUNCDATA`: ガベージコレクションのための関数関連データを指定する。
    *   `PCDATA`: プログラムカウンタ関連データを指定する。

3.  **`cmd/internal/obj`パッケージ**:
    Goコンパイラツールチェーンの内部パッケージであり、オブジェクトファイル生成とリンカが利用する低レベルな命令表現やデータ構造を定義しています。`obj`パッケージは、アセンブラによって生成された中間表現（命令のリストやシンボル情報など）を扱い、最終的なオブジェクトファイルや実行可能ファイルを構築するための基盤を提供します。
    *   **`obj.As`型**: `obj`パッケージ内で定義されている列挙型で、Goアセンブラがサポートする命令コード（オペレーションコード）を表します。例えば、`AADD`（加算）、`AMOV`（移動）などの実際のCPU命令や、以前は`ADATA`のような擬似命令も含まれていました。

4.  **アセンブラのパース処理**:
    アセンブラは、アセンブリソースコードを読み込み、字句解析（トークン化）と構文解析（パース）を行います。この過程で、各行が命令なのか、擬似命令なのか、コメントなのかを識別し、それに応じた内部データ構造を構築します。擬似命令の場合、アセンブラはそれらの指示に従って、シンボルテーブルの更新、データ領域の割り当てなどを行います。

## 技術的詳細

このコミットの技術的詳細は、Goアセンブラの内部構造と、擬似命令の識別・処理ロジックの変更に集約されます。

**変更前:**
1.  `src/cmd/asm/internal/arch/arch.go`ファイルには、`Pseudos`という`map[string]obj.As`型のマップが定義されていました。このマップは、擬似命令の文字列名（例: `"DATA"`, `"TEXT"`）を、対応する`obj.As`型の定数（例: `obj.ADATA`, `obj.ATEXT`）にマッピングしていました。
2.  `src/cmd/asm/internal/asm/parse.go`内の`Parser.line()`メソッドは、アセンブリソースコードの各行を解析する際に、まずこの`arch.Pseudos`マップを参照して、現在のワードが擬似命令であるかどうかを判断していました。擬似命令であれば、対応する`obj.As`定数とワード、オペランドを`Parser.pseudo()`メソッドに渡していました。
3.  `Parser.pseudo()`メソッドは、受け取った`obj.As`定数に基づいて`switch`文で分岐し、各擬似命令（`obj.ATEXT`, `obj.ADATA`など）に対応する処理（例: `p.asmText()`, `p.asmData()`）を呼び出していました。
4.  `src/cmd/internal/obj/link.go`と`src/cmd/internal/obj/util.go`には、`ADATA`という`obj.As`型の定数とその文字列表現が定義されていました。

**変更後:**
1.  `src/cmd/asm/internal/arch/arch.go`から`Pseudos`マップ全体が削除されました。これにより、`cmd/asm`パッケージは擬似命令を識別するために`obj.As`定数へのマッピングに依存しなくなりました。
2.  `src/cmd/asm/internal/asm/parse.go`内の`Parser.line()`メソッドは、`arch.Pseudos`マップを介さずに、直接`Parser.pseudo(word, operands)`を呼び出すようになりました。`Parser.pseudo()`メソッドのシグネチャも変更され、`obj.As`定数を受け取る引数がなくなり、擬似命令の文字列ワードを直接受け取るようになりました。
3.  `Parser.pseudo()`メソッド内の`switch`文は、`obj.As`定数ではなく、直接擬似命令の文字列ワード（例: `"DATA"`, `"TEXT"`）に基づいて分岐するように変更されました。これにより、`DATA`擬似命令の処理は、`"DATA"`という文字列リテラルとの直接比較によって行われます。
4.  `src/cmd/internal/obj/link.go`と`src/cmd/internal/obj/util.go`から`ADATA`定数およびその文字列表現が完全に削除されました。これは、`obj`パッケージが`DATA`擬似命令を命令コードとして認識する必要がなくなったためです。

この変更は、`DATA`擬似命令がアセンブラの構文解析フェーズで完結する概念であり、リンカやオブジェクトファイルの低レベルな表現には直接関係しないという認識に基づいています。これにより、`cmd/asm`は`DATA`擬似命令をより自律的に処理できるようになり、`cmd/internal/obj`パッケージの役割がより明確に、機械語命令とリンキングの抽象化に特化されることになります。

## コアとなるコードの変更箇所

このコミットにおける主要なコード変更は以下のファイルに集中しています。

*   **`src/cmd/asm/internal/arch/arch.go`**:
    *   `Pseudos`マップ（`map[string]obj.As`型）が完全に削除されました。このマップは、擬似命令の文字列名と`obj.As`定数をマッピングしていました。

*   **`src/cmd/asm/internal/asm/parse.go`**:
    *   `Parser.line()`メソッド内で、擬似命令を識別するために`arch.Pseudos`マップを使用していたロジックが削除されました。代わりに、`p.pseudo(word, operands)`が直接呼び出されるようになりました。
    *   `Parser.pseudo()`メソッドのシグネチャが変更されました。
        *   変更前: `func (p *Parser) pseudo(op obj.As, word string, operands [][]lex.Token)`
        *   変更後: `func (p *Parser) pseudo(word string, operands [][]lex.Token) bool`
    *   `Parser.pseudo()`メソッド内の`switch`文が、`op obj.As`ではなく、直接`word string`（擬似命令の文字列）に基づいて分岐するように変更されました。例えば、`case obj.ADATA:`が`case "DATA":`に変わりました。

*   **`src/cmd/asm/internal/asm/pseudo_test.go`**:
    *   テストコードから`cmd/asm/internal/arch`パッケージのインポートが削除されました。
    *   テスト内で`arch.Pseudos`マップを使用して擬似命令の`obj.As`定数を取得していた部分が、`parser.pseudo()`メソッドを直接呼び出す形に変更されました。

*   **`src/cmd/internal/obj/link.go`**:
    *   `ADATA`という`obj.As`型の定数の定義が削除されました。

*   **`src/cmd/internal/obj/util.go`**:
    *   `Anames`配列から`"DATA"`という文字列（`ADATA`定数に対応する名前）が削除されました。

## コアとなるコードの解説

このコミットの核心は、`DATA`擬似命令の処理を`obj`パッケージの抽象化から切り離し、`cmd/asm`パッケージ内で直接文字列として扱うようにした点です。

1.  **`arch.go`からの`Pseudos`マップ削除**:
    これは、アセンブラが擬似命令を識別する際に、もはや`obj.As`型の定数に依存しないことを明確に示しています。擬似命令はアセンブラ固有の概念であり、汎用的な命令コードリストに含める必要がないという設計思想の変更を反映しています。

2.  **`parse.go`の`Parser.pseudo()`メソッドの変更**:
    *   シグネチャの変更は、このメソッドが`obj.As`定数ではなく、擬似命令の生の名前（文字列）を直接処理するようになったことを意味します。
    *   `switch word`への変更は、アセンブラが`"DATA"`という文字列を直接見て、それがデータセクションを定義する擬似命令であると判断し、それに応じた内部処理（`p.asmData()`の呼び出し）を行うようになったことを示しています。これにより、`cmd/asm`は`DATA`擬似命令の処理に関して`cmd/internal/obj`から独立しました。

3.  **`obj/link.go`と`obj/util.go`からの`ADATA`削除**:
    これは、`obj`パッケージが`ADATA`という定数を保持する必要がなくなったことを意味します。`obj`パッケージは、リンカが扱うべき実際の機械語命令や、それらの命令に関連するメタデータに焦点を当てるべきであり、アセンブラディレクティブのような概念は含まないという原則が強化されました。

これらの変更により、Goツールチェーンの内部構造がよりクリーンになり、各パッケージの責任範囲が明確化されました。`cmd/asm`は擬似命令の構文解析と初期処理に特化し、`cmd/internal/obj`はオブジェクトファイルの低レベルな表現とリンキングに特化するという役割分担が強化されています。

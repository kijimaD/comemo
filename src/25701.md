このコミットは、Go言語の標準ライブラリである `unicode/utf8` パッケージ内のUTF-8デコードアルゴリズムを大幅に改善するものです。具体的には、`src/unicode/utf8/utf8.go` ファイルが変更され、UTF-8シーケンスのデコード、ルーンのカウント、およびUTF-8文字列の検証を行うためのロジックが刷新されました。`src/unicode/utf8/utf8_test.go` にも、新しいロジックの動作を検証するためのテストケースが追加されています。

## 変更の背景

UTF-8は可変長エンコーディングであり、1文字（ルーン）が1バイトから4バイトで表現されます。この可変長性のため、デコード処理はバイトシーケンスの先頭バイトを解析し、それに続くバイトが有効な継続バイトであるかを検証する必要があります。従来のGoの `unicode/utf8` パッケージにおけるデコードロジックは、多くの `if/else if` 条件分岐を使用して、各バイトシーケンスの長さを判断し、その後のバイトの妥当性をチェックしていました。

このアプローチにはいくつかの課題がありました。

1.  **複雑なロジック**: 多数の条件分岐はコードを複雑にし、すべてのエッジケース（特に不正なUTF-8シーケンス）を網羅的に扱うことを難しくしていました。
2.  **パフォーマンスのボトルネック**: 条件分岐が多いと、CPUの分岐予測ミスが発生しやすくなり、特に非ASCII文字のような複数バイトのルーンを大量に処理する場合にパフォーマンスが低下する可能性がありました。
3.  **最適化の困難さ**: コンパイラがコードを最適化（例えばループアンローリング）する際に、複雑な分岐構造が障壁となることがありました。

このコミットは、これらの課題に対処するために、デコードアルゴリズムをテーブルベースのアプローチに移行しました。これにより、コードの簡素化、分岐の削減、そして特に非ASCII入力に対するパフォーマンスの大幅な向上が実現されました。コミットメッセージで言及されている `Issue #11733` は、おそらくUTF-8デコードの効率性や特定の不正シーケンスのハンドリングに関する問題であったと推測されます。

## 前提知識の解説

### UTF-8エンコーディングの基本

UTF-8は、Unicode文字をバイトシーケンスにエンコードするための可変長文字エンコーディングです。その主な特徴は以下の通りです。

*   **互換性**: ASCII文字（U+0000からU+007F）は1バイトで表現され、ASCIIと完全に互換性があります。
*   **可変長**: 1つのUnicode文字（コードポイント）は1バイトから4バイトの範囲でエンコードされます。
    *   1バイト: `0xxxxxxx` (ASCII)
    *   2バイト: `110xxxxx 10xxxxxx`
    *   3バイト: `1110xxxx 10xxxxxx 10xxxxxx`
    *   4バイト: `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx`
*   **自己同期性**: 各バイトの先頭ビットパターンを見ることで、それがシーケンスの開始バイトなのか、それとも継続バイトなのかを識別できます。これにより、不正なバイトシーケンスがあっても、次の有効な文字の開始を比較的容易に特定できます。
    *   開始バイト: `0xxxxxxx` (1バイト文字), `110xxxxx`, `1110xxxx`, `11110xxx`
    *   継続バイト: `10xxxxxx`

### Goにおける`rune`とは

Go言語では、`rune`型はUnicodeコードポイントを表す組み込み型です。これは `int32` のエイリアスであり、1つのUnicode文字を格納するのに十分な大きさを持っています。Goの文字列はUTF-8バイトのシーケンスとして扱われるため、文字列をイテレートして個々の文字（ルーン）を処理する際には、UTF-8デコードが必要になります。

### `unicode/utf8`パッケージの役割

`unicode/utf8` パッケージは、Go言語においてUTF-8エンコードされたバイトシーケンスを操作するための機能を提供します。主な機能には以下のようなものがあります。

*   **`DecodeRune` / `DecodeRuneInString`**: バイトスライスまたは文字列の先頭から1つのルーンをデコードし、そのルーンとバイト数を返します。
*   **`RuneCount` / `RuneCountInString`**: バイトスライスまたは文字列内のルーンの総数をカウントします。不正なUTF-8シーケンスも1つのエラールーンとしてカウントされます。
*   **`Valid` / `ValidString`**: バイトスライスまたは文字列が完全に有効なUTF-8シーケンスであるかをチェックします。
*   **`EncodeRune`**: ルーンをUTF-8バイトシーケンスにエンコードします。

### UTF-8デコードの課題

UTF-8デコードの主な課題は、効率性と堅牢性の両立です。

*   **効率性**: 可変長であるため、各文字の長さを動的に判断し、それに続くバイトを読み取る必要があります。このプロセスを高速に行うことが求められます。
*   **堅牢性**: 不正なバイトシーケンス（例: 継続バイトが先行バイトなしで出現、シーケンスの途中で文字列が終了、オーバーロングエンコーディングなど）が入力された場合でも、クラッシュすることなく、適切にエラーを報告（Goでは `RuneError` を返す）し、次の有効な文字から処理を再開できる必要があります。

## 技術的詳細

### 旧実装の課題

コミット前の `decodeRuneInternal` 関数（および `decodeRuneInStringInternal`）は、以下のような構造を持っていました。

```go
func decodeRuneInternal(p []byte) (r rune, size int, short bool) {
    // c0 をチェック
    // 1バイト文字か？
    // 継続バイトか？
    // n < 2 なら short
    // c1 をチェック
    // 2バイト文字か？
    // n < 3 なら short
    // c2 をチェック
    // 3バイト文字か？
    // n < 4 なら short
    // c3 をチェック
    // 4バイト文字か？
    // エラー
}
```

このコードは、バイトシーケンスの最初のバイト `c0` を見て、それが何バイト文字の開始バイトであるかを判断し、その後、必要な数の継続バイトが存在するか、そしてそれらが有効な範囲内にあるかを順次チェックしていました。このアプローチは、多くの `if` 文とネストされた条件分岐を含んでおり、特に複数バイト文字のデコードパスでは、多くの比較とジャンプ命令が発生していました。これは、CPUのパイプラインを乱し、分岐予測ミスを誘発しやすいため、パフォーマンスの低下につながる可能性がありました。また、すべての不正なシーケンスやエッジケースを明示的に処理する必要があり、コードの保守性も低くなりがちでした。

### 新実装の「テーブルベース」アルゴリズムとは何か

新しい実装では、「テーブルベース」のアプローチが採用されました。これは、最初のバイト（`p[0]` または `s[0]`）の値に基づいて、そのバイトがどのようなUTF-8シーケンスの開始バイトであるか、何バイトのシーケンスであるか、そしてそれに続く継続バイトがどのような範囲内にあるべきか、といった情報を事前に計算されたルックアップテーブルから取得する方式です。

このアプローチの利点は以下の通りです。

*   **分岐の削減**: 複雑な `if/else if` チェーンの代わりに、配列のインデックス参照とビット演算を主に使用するため、CPUの分岐予測ミスが大幅に減少します。
*   **コードの簡素化**: デコードロジックがテーブルに抽象化されるため、メインのデコード関数はより簡潔で読みやすくなります。
*   **パフォーマンス向上**: 特に非ASCII文字のデコードにおいて、分岐予測の改善と命令キャッシュの効率化により、処理速度が向上します。
*   **最適化の容易さ**: コンパイラがテーブル参照とビット演算をより効率的に最適化できるようになります。

### `first`配列と`acceptRange`構造体の役割

新しいアルゴリズムの核となるのは、`first` 配列と `acceptRanges` 構造体です。

1.  **`first` 配列**:
    *   `var first = [256]uint8{...}` として定義されています。
    *   これは、UTF-8シーケンスの最初のバイト（0x00から0xFF）をインデックスとして使用し、そのバイトに関する情報を格納する256エントリのルックアップテーブルです。
    *   各 `uint8` の値は2つのニブル（4ビット）に分割されます。
        *   **上位4ビット (x >> 4)**: `acceptRanges` 配列へのインデックスを示します。これは、そのシーケンスに続く継続バイトが満たすべき範囲を定義します。`F` は特別な1バイトケース（ASCIIまたは不正なバイト）を示します。
        *   **下位4ビット (x & 7)**: そのUTF-8シーケンスのバイト長（ルーンのサイズ）を示します。`1` は不正なバイト、`0` はASCIIバイトを示します。
    *   例:
        *   `as` (0xF0): ASCII文字。上位4ビット `F` は特別なケース、下位4ビット `0` はサイズ1（ASCII）。
        *   `xx` (0xF1): 不正な開始バイト。上位4ビット `F` は特別なケース、下位4ビット `1` はサイズ1（不正）。
        *   `s1` (0x02): 2バイト文字の開始バイト。上位4ビット `0` は `acceptRanges[0]` を参照、下位4ビット `2` はサイズ2。

2.  **`acceptRange` 構造体と `acceptRanges` 配列**:
    *   `type acceptRange struct { lo uint8; hi uint8 }` は、継続バイトが取りうる最小値 (`lo`) と最大値 (`hi`) を定義します。
    *   `var acceptRanges = [...]acceptRange{...}` は、`first` 配列の上位4ビットによって参照されるルックアップテーブルです。
    *   これにより、各バイト長（2, 3, 4バイト）のUTF-8シーケンスにおいて、2番目以降の継続バイトが `10xxxxxx` の形式（`0x80` から `0xBF`）であること、および特定の範囲内にあることを効率的にチェックできます。例えば、3バイト文字の2番目のバイトは `0xA0` から `0xBF` の範囲でなければならない、といったルールがこのテーブルに集約されています。

### デコードロジックの変更点

新しい `DecodeRune` および `DecodeRuneInString` 関数は、以下のステップで動作します。

1.  最初のバイト `p0` (または `s0`) を取得します。
2.  `first[p0]` から `x` の値を取得します。
3.  `x` の値に基づいて、ASCII文字、不正な開始バイト、または複数バイト文字の開始バイトであるかを判断します。
    *   ASCIIまたは不正な1バイト文字の場合、すぐに結果を返します。
4.  `x` からバイト長 `sz` と `acceptRanges` のインデックスを取得します。
5.  入力の長さ `n` が `sz` より短い場合、不完全なシーケンスとしてエラーを返します。
6.  2番目のバイト `b1` (または `s1`) を取得し、`acceptRanges` で指定された範囲内にあるかをチェックします。範囲外であればエラーを返します。
7.  `sz` が2の場合、ルーンを計算して返します。
8.  3番目のバイト `b2` (または `s2`) を取得し、`locb` (`0x80`) から `hicb` (`0xBF`) の範囲内にあるかをチェックします。範囲外であればエラーを返します。
9.  `sz` が3の場合、ルーンを計算して返します。
10. 4番目のバイト `b3` (または `s3`) を取得し、`locb` から `hicb` の範囲内にあるかをチェックします。範囲外であればエラーを返します。
11. `sz` が4の場合、ルーンを計算して返します。

このプロセスにより、従来の多くの `if` 文が、テーブル参照と少数の条件分岐に置き換えられ、デコード処理が大幅に効率化されました。

## コアとなるコードの解説

新しい実装では、`first` 配列と `acceptRanges` テーブルがデコード処理の中心となります。

### `first` 配列の構造

```go
var first = [256]uint8{
    // ... (ASCIIバイトは 'as')
    // ... (不正なバイトは 'xx')
    // 0xC0-0xCF: xx, xx, s1, s1, s1, s1, s1, s1, s1, s1, s1, s1, s1, s1, s1, s1,
    // 0xD0-0xDF: s1, s1, s1, s1, s1, s1, s1, s1, s1, s1, s1, s1, s1, s1, s1, s1,
    // 0xE0-0xEF: s2, s3, s3, s3, s3, s3, s3, s3, s3, s3, s3, s3, s3, s4, s3, s3,
    // 0xF0-0xFF: s5, s6, s6, s6, s7, xx, xx, xx, xx, xx, xx, xx, xx, xx, xx, xx,
}
```

この配列は、最初のバイト `c` が与えられたときに、`first[c]` の値から以下の情報を取得します。

*   `x & 7`: ルーンのバイト長（1, 2, 3, 4）。
*   `x >> 4`: `acceptRanges` 配列へのインデックス。

### `acceptRanges` 配列の構造

```go
type acceptRange struct {
    lo uint8 // lowest value for second byte.
    hi uint8 // highest value for second byte.
}

var acceptRanges = [...]acceptRange{
    0: {locb, hicb}, // 0x80-0xBF (一般的な継続バイト)
    1: {0xA0, hicb}, // 0xA0-0xBF (例: E0の次のバイト)
    2: {locb, 0x9F}, // 0x80-0x9F (例: EDの次のバイト)
    3: {0x90, hicb}, // 0x90-0xBF (例: F0の次のバイト)
    4: {locb, 0x8F}, // 0x80-0x8F (例: F4の次のバイト)
}
```

`acceptRanges` は、UTF-8の仕様で定められた、特定の開始バイトに続く継続バイトの許容範囲を定義します。例えば、3バイト文字の開始バイト `0xE0` (`1110xxxx`) の場合、2番目のバイトは `1010xxxx` から `1011xxxx` の範囲（`0xA0` から `0xBF`）でなければなりません。これは `acceptRanges[1]` に対応します。

### `DecodeRune` 関数の新しいロジック（抜粋）

```go
func DecodeRune(p []byte) (r rune, size int) {
    n := len(p)
    if n < 1 {
        return RuneError, 0
    }
    p0 := p[0]
    x := first[p0] // 最初のバイトから情報を取得

    if x >= as { // ASCII または不正な1バイト文字の場合
        mask := rune(x) << 31 >> 31 // x == xx なら 0xFFFF, x == as なら 0x0000
        return rune(p[0])&^mask | RuneError&mask, 1 // 条件分岐なしでRuneErrorを返す
    }

    sz := x & 7 // バイト長を取得
    accept := acceptRanges[x>>4] // 継続バイトの許容範囲を取得

    if n < int(sz) { // バイトが足りない場合
        return RuneError, 1
    }

    b1 := p[1]
    if b1 < accept.lo || accept.hi < b1 { // 2番目のバイトが範囲外の場合
        return RuneError, 1
    }
    if sz == 2 { // 2バイト文字の場合
        return rune(p0&mask2)<<6 | rune(b1&maskx), 2
    }

    b2 := p[2]
    if b2 < locb || hicb < b2 { // 3番目のバイトが範囲外の場合
        return RuneError, 1
    }
    if sz == 3 { // 3バイト文字の場合
        return rune(p0&mask3)<<12 | rune(b1&maskx)<<6 | rune(b2&maskx), 3
    }

    b3 := p[3]
    if b3 < locb || hicb < b3 { // 4番目のバイトが範囲外の場合
        return RuneError, 1
    }
    // 4バイト文字の場合
    return rune(p0&mask4)<<18 | rune(b1&maskx)<<12 | rune(b2&maskx)<<6 | rune(b3&maskx), 4
}
```

この新しい `DecodeRune` 関数は、`first` 配列と `acceptRanges` を活用することで、従来の多段階の `if/else if` 構造を大幅に簡素化しています。特に、最初のバイト `p0` から `x` を取得し、その `x` の値に基づいて、バイト長 `sz` と継続バイトの許容範囲 `accept` を直接決定できる点が重要です。これにより、デコードパスがより直線的になり、パフォーマンスが向上します。

`RuneCount` や `Valid` といった他の関数も同様に、このテーブルベースのアプローチを採用することで、ループ内で各ルーンのデコードと検証を効率的に行えるようになりました。

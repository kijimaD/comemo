# [インデックス 24039] ファイルの概要

このコミットは、Go言語の `compress/lzw` パッケージにおいて、入力が途中で途切れた（truncated）場合でも、それまでにデコードできた部分的な結果を返すように変更するものです。これにより、破損したデータストリーム（特にGIF画像などで使用されるLZW圧縮データ）を扱う際の堅牢性が向上します。

## 変更の背景

この変更は、Goの `image/gif` パッケージが破損したGIFファイルをより堅牢に処理できるようにするために必要とされました。具体的には、Go issue #9856で報告された問題に対応しています。

従来の `compress/lzw` デコーダは、入力ストリームが途中で不正に終了した場合（例えば、ファイルが途中で切り詰められた場合など）、デコードエラーが発生すると、それまでにデコードできた部分的なデータも破棄してしまう可能性がありました。しかし、多くのアプリケーション、特に画像デコーダのようなケースでは、たとえデータが破損していても、可能な限り多くの有効なデータを回復し、部分的な結果をユーザーに提示することが望ましい場合があります。

このコミットは、LZWデコーダが `io.ErrUnexpectedEOF` や `lzw: invalid code` のようなエラーに遭遇した際に、エラーを報告する前に、それまでにバッファリングされていた部分的なデコード結果をフラッシュ（出力）するように修正することで、この問題を解決します。これにより、破損した入力に対しても、可能な限り多くの意味のあるデータを提供できるようになります。

## 前提知識の解説

### LZW (Lempel-Ziv-Welch) 圧縮

LZWは、データ圧縮アルゴリズムの一種で、特にGIF画像フォーマットで広く使用されています。このアルゴリズムは、入力データから繰り返し現れるパターン（シーケンス）を辞書に登録し、そのパターンをより短いコードに置き換えることでデータを圧縮します。

**基本的な仕組み:**
1.  **辞書の初期化:** 最初は、すべての可能な単一バイトが辞書に登録されます。
2.  **最長一致の探索:** 入力ストリームから、現在辞書に登録されている最長のパターンを探します。
3.  **コードの出力:** 見つかった最長パターンに対応するコードを出力します。
4.  **辞書の更新:** 見つかった最長パターンに、入力ストリームの次の文字を連結した新しいパターンを辞書に登録します。
5.  **繰り返し:** 入力ストリームがなくなるまで、このプロセスを繰り返します。

**デコードの仕組み:**
デコードは圧縮の逆のプロセスです。デコーダは、圧縮されたコードを読み込み、自身の辞書を使って元のパターンを再構築します。デコーダの辞書は、エンコーダと同じロジックで動的に構築されます。

**エラーと破損:**
LZW圧縮データが途中で途切れたり、不正なコードが含まれていたりすると、デコーダはエラーを検出します。このような場合、デコーダがどのように振る舞うかは実装に依存しますが、一般的にはエラーを返し、それ以降のデコードを停止します。このコミットが修正しようとしているのは、この「停止」の際に、それまでに有効だった部分的なデータをどう扱うかという点です。

### Go言語の `io` パッケージとエラーハンドリング

Go言語では、`io` パッケージがI/O操作のための基本的なインターフェース（`io.Reader`, `io.Writer` など）を提供します。
-   `io.Reader` インターフェースは `Read(p []byte) (n int, err error)` メソッドを定義しており、データを読み込み、読み込んだバイト数とエラーを返します。
-   `io.ErrUnexpectedEOF` は、`io.Reader` が予期せず入力の終わりに達したときに返されるエラーです。これは、通常、完全なデータブロックが期待される場所で入力が途切れた場合に発生します。
-   `io.Copy` 関数は、`io.Reader` から `io.Writer` へデータをコピーする便利な関数で、内部で `Read` メソッドと `Write` メソッドを繰り返し呼び出します。

## 技術的詳細

`compress/lzw` パッケージの `decoder` 構造体は、LZW圧縮データをデコードするための内部状態を管理します。`decode()` メソッドは、入力ストリームからコードを読み込み、それをデコードして内部バッファに書き込む主要なロジックを含んでいます。

このコミット以前は、`decode()` メソッド内で `io.ErrUnexpectedEOF` や `lzw: invalid code` のようなエラーが発生した場合、`d.err` フィールドにエラーが設定され、すぐに `return` していました。このとき、`decoder` の内部バッファ（`d.buf`）には、エラーが発生する直前までにデコードされた有効なデータが残っている可能性があります。しかし、`return` してしまうと、これらの部分的なデータは `Read` メソッドの呼び出し元に渡されることなく破棄されていました。

この挙動は、完全なデータが常に期待される場合には問題ありませんが、破損したデータ（例: 途中で切り詰められたGIFファイル）を扱う際には、ユーザーエクスペリエンスを損なう可能性がありました。例えば、画像ビューアが破損したGIFファイルを開こうとした場合、エラーで何も表示されないよりも、部分的にでも画像が表示される方が望ましいでしょう。

このコミットは、エラーが発生する直前に `d.flush()` メソッドを呼び出すことで、この問題を解決します。`d.flush()` は、`decoder` の内部バッファに蓄積されているデコード済みデータを、`Read` メソッドの呼び出し元に確実に渡す役割を担います。これにより、エラーが発生しても、それまでにデコードできた部分的なデータは失われることなく、利用可能になります。

## コアとなるコードの解説

### `src/compress/lzw/reader.go` の変更

`decoder.decode()` メソッド内の2箇所に `d.flush()` の呼び出しが追加されています。

1.  **`io.ErrUnexpectedEOF` のハンドリング時:**
    入力ストリームから次のコードを読み取ろうとした際に、予期せずEOF（End Of File）に達した場合、`io.ErrUnexpectedEOF` が発生します。このエラーが `d.err` に設定された直後に `d.flush()` が呼び出されます。これにより、EOFに達するまでにデコードされたすべてのデータが、`decoder` の内部バッファから `Read` メソッドの呼び出し元に渡されます。

2.  **`lzw: invalid code` のハンドリング時:**
    デコード中に不正なLZWコードが検出された場合、`lzw: invalid code` というエラーが生成されます。このエラーが `d.err` に設定された直後にも `d.flush()` が呼び出されます。同様に、不正なコードに遭遇するまでにデコードされた有効なデータがフラッシュされ、失われるのを防ぎます。

`d.flush()` メソッドの具体的な実装はコミット差分には含まれていませんが、その目的は、`decoder` の内部バッファ（通常は `d.buf` やそれに類するもの）に一時的に保持されているデコード済みバイト列を、外部に公開されている `Read` メソッドがアクセスできる状態にするか、直接 `Read` メソッドの出力バッファに書き込むことです。これにより、エラー発生時でも、可能な限り多くの有効なデータが呼び出し元に返されるようになります。

### `src/compress/lzw/reader_test.go` の変更

テストコード `TestReader` にも重要な変更が加えられています。

1.  **`s := b.String()` の移動:**
    `io.Copy(&b, rc)` の呼び出し後、エラーチェックの前に `s := b.String()` が移動されました。これは、`io.Copy` がエラーを返した場合でも、`b` (バイトバッファ) には部分的にデコードされたデータが含まれている可能性があるため、その内容を `s` に保存しておくためです。

2.  **`io.ErrUnexpectedEOF` の追加テストロジック:**
    `io.ErrUnexpectedEOF` が返された場合に特化した新しいテストロジックが追加されました。
    -   `n == 0 || !strings.HasPrefix(tt.raw, s)` という条件でエラーをチェックしています。
        -   `n == 0`: デコードされたバイト数が0である場合。これは、部分的なデータが全く返されなかったことを意味し、期待される動作ではありません。
        -   `!strings.HasPrefix(tt.raw, s)`: デコードされた文字列 `s` が、元の期待される文字列 `tt.raw` のプレフィックス（前方一致）ではない場合。これは、デコードされたデータが元のデータの有効な部分ではないか、完全に間違っていることを意味します。
    -   これらの条件のいずれかが真であれば、テストは失敗し、エラーメッセージ `got %d bytes (%q), want a non-empty prefix of %q` が出力されます。

このテストの変更は、コミットの意図を明確に反映しています。つまり、入力が途中で途切れて `io.ErrUnexpectedEOF` が発生した場合でも、デコーダは空ではない、かつ元のデータの有効なプレフィックスである部分的なデコード結果を返す必要がある、という要件を検証しています。

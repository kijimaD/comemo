# [インデックス 21507] ファイルの概要

このコミットは、Go言語のビルドシステムにおける重要な変更を導入するものです。具体的には、Go 1.5以降のGoのビルドには、Go 1.4以降の古いGoリリースが事前にインストールされている必要があるという新しいブートストラップ要件を導入し、この要件を強制するために、Goのビルドツールである `cmd/dist` をC言語からGo言語に変換しています。これにより、将来的にGoコンパイラ、アセンブラ、リンカといった他の主要なC言語プログラムもGo言語に置き換えるための道筋がつけられました。

## 変更の背景

このコミットの背景には、Go言語のツールチェイン（コンパイラ、アセンブラ、リンカ、`cmd/dist`など）を完全にGo言語で記述するというGo開発チームの長期的な目標があります。Go 1.4以前のバージョンでは、これらのツールの一部がC言語で書かれており、GoのソースコードからGoをビルドするためにはCコンパイラが必要でした。これは、Goのビルドプロセスに外部の依存関係（Cコンパイラ）をもたらし、ビルド環境の複雑性を増していました。

特に、Go 1.5では、Goのコンパイラ自体がGo言語で再実装されることになっていました。この変更を実現するためには、「ブートストラップ問題」を解決する必要がありました。つまり、Goで書かれたコンパイラをビルドするためには、すでに動作するGoコンパイラが必要になるという循環的な依存関係です。

このコミットは、Go 1.5ブートストラップ計画（`golang.org/s/go15bootstrap`で詳細が説明されています）の重要な第一歩です。この計画の目的は、GoツールチェインのC言語依存を排除し、Go自身でGoをビルドできる「自己ホスト型」のツールチェインを確立することでした。そのために、Go 1.5以降のGoをビルドするには、Go 1.4（またはそれ以降の古いGoリリース）がブートストラップツールチェインとして必要であるという新しい要件が導入されました。この要件を具体的に強制し、将来のC言語ツールのGo言語への移行を容易にするために、ビルドプロセスの中心的な役割を担う `cmd/dist` ツールがC言語からGo言語に書き換えられました。

## 前提知識の解説

### ブートストラップ (Bootstrapping)

ソフトウェア開発における「ブートストラップ」とは、より複雑なシステムを構築するために、より単純なシステムを使用するプロセスを指します。コンパイラの文脈では、あるプログラミング言語（例：Go）で書かれたコンパイラを、その言語自身（または別の言語）で書かれた既存のコンパイラを使ってビルドすることを意味します。

Go言語の場合、Go 1.4以前のツールチェインにはC言語で書かれた部分（特にコンパイラや`cmd/dist`）が含まれていました。そのため、GoのソースコードからGoをビルドするには、GCCなどのCコンパイラがシステムにインストールされている必要がありました。これは、GoのビルドプロセスがCコンパイラに依存している状態であり、Goの「自己ホスト型」という理想からは外れていました。

### `cmd/dist` の役割

`cmd/dist` は、Goのソースツリーのルートにある `make.bash` (Unix系) や `make.bat` (Windows) スクリプトから呼び出される主要なビルドツールです。その主な役割は以下の通りです。

*   **Goツールチェインのビルド**: コンパイラ、アセンブラ、リンカなどのGoツールをビルドします。
*   **標準ライブラリのビルド**: Goの標準ライブラリパッケージをビルドします。
*   **テストの実行**: ビルドされたGo環境のテストを実行します。
*   **配布物の作成**: Goのリリースバイナリパッケージを作成します。

Go 1.4以前では、`cmd/dist`自体がC言語で書かれていました。これは、GoのビルドプロセスがC言語のツールに依存していることを意味します。

### Go 1.5 ブートストラップ計画 (`golang.org/s/go15bootstrap`)

この計画は、GoツールチェインからC言語の依存関係を完全に排除し、Goを完全に自己ホスト型にするためのロードマップでした。主要な目標は以下の通りです。

1.  **Cコンパイラの不要化**: GoのビルドにCコンパイラが不要になるようにする。
2.  **GoコンパイラのGo言語化**: Goコンパイラ（`gc`など）をC言語からGo言語に書き換える。
3.  **`cmd/dist`のGo言語化**: ビルドスクリプトの核となる`cmd/dist`をGo言語に書き換える。

この計画により、Go 1.5以降のGoをビルドする際には、Go 1.4（またはそれ以降の古いGoバージョン）がブートストラップコンパイラとして必要になります。この「古いGo」を使って、新しいGoのツールチェイン（Goで書かれたコンパイラなど）をビルドし、その後、新しくビルドされたツールチェイン自身を使って残りのGo環境をビルドするという多段階のブートストラッププロセスが採用されました。

## 技術的詳細

このコミットの技術的な核心は、Goのビルドシステムの中核である `cmd/dist` をC言語からGo言語に完全に書き換えた点にあります。

### C言語からGo言語への移行

*   **ファイル構造の変更**: `src/cmd/dist` ディレクトリ内のC言語ソースファイル（例: `build.c`, `main.c`, `util.c`）が、対応するGo言語ソースファイル（例: `build.go`, `main.go`, `util.go`）に置き換えられました。
*   **データ構造の変換**: C言語版 `cmd/dist` で使用されていた `Buf` (バッファ) や `Vec` (動的配列) といったカスタムデータ構造が、Go言語の組み込み型（`string`、`[]string`、`bytes.Buffer`など）に置き換えられました。これにより、メモリ管理がGoのガベージコレクションに任され、コードの安全性と簡潔性が向上しました。
*   **システムコールとユーティリティ関数のGo言語化**: ファイルI/O、環境変数の読み取り、シェルコマンドの実行など、C言語版で`x`プレフィックス（例: `xgetenv`, `xmkdir`）を持つ移植性レイヤーの関数が、Goの標準ライブラリ（`os`、`path/filepath`、`strings`など）の機能を使って再実装されました。
*   **ビルドロジックの変更**: `src/cmd/dist/README` の変更が示すように、Go 1.5以降のビルドプロセスは、Go 1.4をブートストラップとして使用する多段階プロセスに変わりました。
    1.  Go 1.4で `cmd/dist` をビルドする。
    2.  ビルドされた `dist` を使って、Go 1.4でGo 1.xのコンパイラツールチェインをビルドする。
    3.  ビルドされた `dist` を使って、Go 1.xのコンパイラツールチェイン自身でGo 1.xのコンパイラツールチェインを再ビルドする（自己ホスト）。
    4.  ビルドされた `dist` を使って、Go 1.xのコンパイラツールチェインで `cmd/go` (go_bootstrapとして) をビルドする。
    5.  `go_bootstrap` を使って、残りのGo 1.x標準ライブラリとコマンドをビルドする。

### ブートストラップ要件の強制

`cmd/dist` がGo言語で書かれることで、Goのビルドプロセス自体がGo言語の知識を持つことになります。これにより、Go 1.4以降のGoがインストールされていることを確認するロジックをGoコード内で直接実装し、ブートストラップ要件をより堅牢に強制できるようになりました。

### 将来への影響

この変更は、Goツールチェイン全体をGo言語で記述するという長期的な目標に向けた重要な一歩です。`cmd/dist`がGoになったことで、Goコンパイラ、アセンブラ、リンカといったさらに複雑なC言語ツールをGoに変換する際の基盤が整いました。これにより、Goのビルドシステムはより一貫性があり、Go開発者にとって理解しやすく、Go言語の進化に合わせてより容易にメンテナンスできるようになります。

## コアとなるコードの変更箇所

このコミットでは、主に `src/cmd/dist` ディレクトリ内のファイルが大幅に変更されています。

*   `src/cmd/dist/README`: ビルドプロセスの変更と新しいブートストラップ要件について説明する内容に完全に書き換えられています。C言語版の`dist`の内部構造に関する記述が削除され、Go 1.5以降のビルド手順が詳細に記述されています。
*   `src/cmd/dist/build.go`: C言語版の `build.c` に対応するファイルです。C言語の `init` 関数がGo言語の `xinit` 関数に変換され、`char*` 型のグローバル変数がGoの `string` 型に、`bool` がGoの `bool` 型に置き換えられています。`xgetenv` のようなカスタム環境変数取得関数が `os.Getenv` に置き換えられています。
*   `src/cmd/dist/util.go`: C言語版の `util.c` に対応するファイルです。ファイル操作、文字列操作、シェルコマンド実行などのユーティリティ関数がGo言語で再実装されています。特に、C言語版で頻繁に使われていた `Buf` や `Vec` といったカスタムバッファ/ベクタ構造体がGoの `bytes.Buffer` や `[]string` に置き換えられている点が顕著です。
*   `src/make.bash`: `cmd/dist` がC言語からGo言語に移行したことに伴い、`make.bash` スクリプト内の `dist` の呼び出し方法や、Cコンパイラ関連の処理が変更されています。

**具体的なコード変更の例 (`src/cmd/dist/build.go` の `init` 関数から `xinit` 関数への変更)**

C言語版 (`build.c`):
```c
// init handles initialization of the various global state, like goroot and goarch.
void
init(void)
{
	char *p;
	int i;
	Buf b;

	binit(&b);

	xgetenv(&b, "GOROOT");
	if(b.len > 0) {
		// if not "/", then strip trailing path separator
		if(b.len >= 2 && b.p[b.len - 1] == slash[0])
			b.len--;
		goroot = btake(&b);
	}
    // ... (以下、同様にC言語のBuf, Vec, xgetenvなどを使用)
}
```

Go言語版 (`build.go`):
```go
// xinit handles initialization of the various global state, like goroot and goarch.
func xinit() {
	goroot = os.Getenv("GOROOT")
	if slash == "/" && len(goroot) > 1 || slash == `\` && len(goroot) > 3 {
		// if not "/" or "c:\", then strip trailing path separator
		goroot = strings.TrimSuffix(goroot, slash)
	}
	if goroot == "" {
		fatal("$GOROOT must be set")
	}

	// ... (以下、Go言語のos.Getenv, strings.TrimSuffixなどを使用)
}
```

## コアとなるコードの解説

上記の `init` から `xinit` への変更は、C言語からGo言語への移行における典型的なパターンを示しています。

*   **言語の変更**: 関数シグネチャがCの `void init(void)` からGoの `func xinit()` に変わっています。Goでは、関数名が小文字で始まる場合はパッケージプライベート、大文字で始まる場合はエクスポートされます。`xinit` は内部的な初期化関数であることを示唆しています。
*   **環境変数の取得**: C言語版では `xgetenv(&b, "GOROOT")` のようにカスタムのバッファ (`Buf`) と環境変数取得関数を使用していましたが、Go言語版では `os.Getenv("GOROOT")` のようにGo標準ライブラリの `os` パッケージの関数を直接使用しています。これにより、コードがより簡潔になり、Goの標準的な慣習に従うようになります。
*   **文字列操作**: C言語版では `b.len` や `b.p[b.len - 1]` のようなポインタと長さを使った手動の文字列操作が行われていましたが、Go言語版では `strings.TrimSuffix(goroot, slash)` のようにGoの `strings` パッケージの関数を使って、より安全で読みやすい文字列操作を実現しています。
*   **エラーハンドリング**: C言語版では `fatal` 関数を呼び出してエラーを処理していましたが、Go言語版でも同様の `fatal` 関数（Goで再実装されたもの）を使用しています。

これらの変更は、GoのビルドツールがGo言語の持つ安全性、表現力、そして標準ライブラリの豊富さを活用するように再構築されたことを示しています。これにより、ビルドプロセスの信頼性が向上し、将来的な機能追加やメンテナンスが容易になります。また、Go開発者にとって、ビルドツール自体がGoで書かれていることで、その動作を理解しやすくなるというメリットもあります。

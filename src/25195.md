## 元コミット内容

`archive/tar: readGNUSparseMap0x1` における数値オーバーフローの問題を修正。

動機：
*   `numEntries` を検証するロジックがオーバーフローを起こし、誤って検証を通過してしまう可能性があり、悪意のあるファイルが任意のメモリを割り当てることを許してしまう。
*   `strconv.ParseInt` の使用において、整数精度が64ビットに設定されていないため、32ビットマシンでこのコードが正しく動作しない。

## 変更の背景

このコミットは、Go言語の標準ライブラリである `archive/tar` パッケージが、特にGNU sparse format version 0.1でエンコードされたtarアーカイブを処理する際に遭遇する可能性のある2つの重要な問題を解決するために行われました。

1.  **数値オーバーフローによるメモリ割り当ての脆弱性**: `readGNUSparseMap0x1` 関数は、tarアーカイブのPAXヘッダーからスパースマップのエントリ数を読み取ります。このエントリ数 (`numEntries`) を検証する際に、内部的な計算で数値オーバーフローが発生する可能性がありました。オーバーフローが発生すると、実際には非常に大きな値であるにもかかわらず、検証ロジックが小さな値として誤認し、結果として悪意のあるtarファイルがシステムに任意の大量のメモリを割り当てることを引き起こす可能性がありました。これはサービス拒否（DoS）攻撃や、システムリソースの枯渇につながるセキュリティ上の脆弱性です。
2.  **32ビットシステムでの `strconv.ParseInt` の誤動作**: `numEntries` やスパースエントリのオフセット、バイト数を文字列から整数に変換するために `strconv.ParseInt` が使用されていましたが、この関数呼び出しで `bitSize` パラメータが `0` に設定されていました。Go言語の `strconv.ParseInt` ドキュメントによると、`bitSize` が `0` の場合、結果は `int` 型に変換されます。`int` 型のサイズはシステムに依存し、32ビットシステムでは32ビット、64ビットシステムでは64ビットとなります。このため、32ビットシステムでは、64ビットの値を期待する場面で32ビットの整数としてパースされ、大きな数値が正しく扱えないという問題が発生していました。これにより、スパースファイルの構造が正しく解釈されず、データ破損や予期せぬ動作を引き起こす可能性がありました。

これらの問題は、特に信頼できないソースから提供されるtarアーカイブを処理する際に、システムの安定性とセキュリティに直接的な影響を与えるため、修正が急務でした。

## 前提知識の解説

### `archive/tar` パッケージ

`archive/tar` はGo言語の標準ライブラリの一部で、tarアーカイブ（テープアーカイブ）の読み書きをサポートします。tarファイルは、複数のファイルを一つのアーカイブにまとめるための一般的な形式です。このパッケージは、標準的なtar形式だけでなく、GNU tarやPAX (POSIX.1-2001) 拡張などの様々なtar形式を扱うことができます。

### GNU Sparse Format (Version 0.1)

GNU tarは、スパースファイル（ファイル内の大部分がゼロで構成されているファイル）を効率的にアーカイブするための特別な形式をサポートしています。スパースファイルは、データベースファイルや仮想ディスクイメージなどでよく見られます。GNU sparse format version 0.1は、PAX (POSIX.1-2001) 拡張ヘッダーを利用して、ファイルのどの部分が「スパース」（つまりゼロ）であるか、どの部分が実際のデータであるかを示す「スパースマップ」を格納します。

*   **PAXヘッダー**: POSIX.1-2001で標準化されたtarの拡張形式で、従来のtarヘッダーでは表現できない長いファイル名、大きなファイルサイズ、拡張属性などをキーと値のペアの形式で格納できます。GNU sparse format version 0.1では、スパースマップの情報がPAXヘッダー内に `GNU.sparse.numblocks` (エントリ数) と `GNU.sparse.map` (オフセットとバイト数のペアのリスト) として格納されます。

### `strconv.ParseInt` 関数

Go言語の `strconv` パッケージは、文字列と数値の間の変換を提供します。`ParseInt` 関数は、指定された文字列を整数として解析します。

```go
func ParseInt(s string, base int, bitSize int) (int64, error)
```

*   `s`: 解析する文字列。
*   `base`: 数値の基数（例: 10進数の場合は10）。
*   `bitSize`: 結果の整数が収まるビット数。`0` の場合、`int` 型のビットサイズ（32ビットシステムでは32、64ビットシステムでは64）が使用されます。`8`, `16`, `32`, `64` などの値を指定できます。この関数は常に `int64` を返しますが、`bitSize` はその値が指定されたビット数に収まるかどうかをチェックするために使用されます。

### 整数オーバーフロー

整数オーバーフローは、数値計算の結果が、その数値を格納するために割り当てられたデータ型が表現できる最大値を超えた場合に発生します。Go言語では、符号なし整数型（`uint` など）でオーバーフローが発生すると、値はモジュロ演算のようにラップアラウンドします（例: `uint8` の `255 + 1` は `0` になる）。符号付き整数型（`int` など）では、オーバーフローの動作は未定義ですが、一般的には予期せぬ値になったり、パニックを引き起こしたりします。

このコミットの文脈では、`numEntries` の検証ロジックで `2 * numEntries` のような計算が行われた際に、`numEntries` が非常に大きいと `2 * numEntries` がオーバーフローし、実際よりも小さな値として扱われることで、悪意のある入力が検証をすり抜ける可能性がありました。

### 32ビットと64ビットシステム

コンピュータのアーキテクチャは、一度に処理できるデータのビット幅によって32ビットまたは64ビットに分類されます。Go言語では、`int` 型のサイズは実行されているシステムのアーキテクチャに依存します。32ビットシステムでは `int` は32ビット幅であり、約-20億から+20億までの値を表現できます。一方、64ビットシステムでは `int` は64ビット幅であり、はるかに大きな値を表現できます。この違いが `strconv.ParseInt` の `bitSize=0` の挙動に影響を与え、クロスプラットフォームでの互換性の問題を引き起こしていました。

## 技術的詳細

### 脆弱性の詳細

`readGNUSparseMap0x1` 関数は、PAXヘッダーから `GNU.sparse.numblocks` キーの値を取得し、これを `numEntries` (スパースエントリの数) として解析します。元のコードでは、この `numEntries` を検証するために以下のロジックを使用していました。

```go
numEntries, err := strconv.ParseInt(numEntriesStr, 10, 0)
// ...
if int64(len(sparseMap)) != 2*numEntries {
    return nil, ErrHeader
}
```

ここで問題となるのは2点です。

1.  **`strconv.ParseInt` の `bitSize=0`**: `strconv.ParseInt` の第3引数 `bitSize` が `0` に設定されているため、結果は `int` 型のビットサイズに依存します。32ビットシステムでは `numEntries` が32ビット整数として扱われ、`int64` にキャストされる前にオーバーフローする可能性がありました。これにより、非常に大きな `numEntriesStr` が与えられた場合でも、32ビットの範囲に収まる小さな負の値として解釈され、その後の検証をすり抜ける可能性がありました。
2.  **`2*numEntries` のオーバーフローチェックの欠陥**: `int64(len(sparseMap)) != 2*numEntries` の比較において、`2*numEntries` の計算自体がオーバーフローする可能性がありました。もし `numEntries` が `int` 型で表現できる最大値の半分より大きい場合、`2*numEntries` はオーバーフローして負の値になったり、予期せぬ小さな値になったりします。これにより、`len(sparseMap)` が非常に大きくても、`2*numEntries` がオーバーフローによって小さな値になることで、このチェックが誤って通過してしまう可能性がありました。結果として、`sparseMap` の長さが `2*numEntries` の期待値と一致しないにもかかわらず、検証が成功し、後続の `make([]sparseEntry, 0, numEntries)` で非常に大きなメモリ割り当てが要求され、システムリソースを枯渇させる可能性がありました。

### 修正の詳細

コミットはこれらの問題を以下の方法で解決しています。

1.  **`numEntries` の厳密な検証**: `numEntries` をパースした後、以下のチェックが追加されました。

    ```go
    if err != nil || numEntries < 0 || int(2*numEntries) < int(numEntries) {
        return nil, ErrHeader
    }
    ```
    *   `numEntries < 0`: `numEntries` が負の値になることはありえないため、負の値であればエラーとします。これは `strconv.ParseInt` が負の値を返す可能性があるため重要です。
    *   `int(2*numEntries) < int(numEntries)`: これは整数オーバーフローを検出するための一般的なイディオムです。もし `numEntries` が正の値で、`2*numEntries` がオーバーフローして負の値になったり、元の `numEntries` よりも小さな値になったりした場合、この条件が真となり、エラーが返されます。これにより、`2*numEntries` の計算が安全に行える範囲内にあることを保証します。このチェックは、`numEntries` が `int` 型の最大値の半分を超える場合にオーバーフローが発生することを効果的に防ぎます。

2.  **`strconv.ParseInt` の `bitSize` の指定**: スパースエントリの `offset` と `numBytes` をパースする際に、`strconv.ParseInt` の `bitSize` パラメータが `0` から `64` に変更されました。

    ```go
    // 変更前
    offset, err := strconv.ParseInt(sparseMap[2*i], 10, 0)
    numBytes, err := strconv.ParseInt(sparseMap[2*i+1], 10, 0)

    // 変更後
    offset, err := strconv.ParseInt(sparseMap[2*i], 10, 64)
    numBytes, err := strconv.ParseInt(sparseMap[2*i+1], 10, 64)
    ```
    これにより、32ビットシステムでもこれらの値が常に64ビット整数として正しく解析されるようになり、大きなオフセットやバイト数を持つスパースファイルが正しく処理されることが保証されます。

これらの変更により、悪意のある入力によるメモリ枯渇攻撃を防ぎ、32ビットシステムと64ビットシステムの両方で `archive/tar` パッケージがスパースファイルを一貫して正しく処理できるようになりました。

## コアとなるコードの解説

### `src/archive/tar/reader.go` の変更点

1.  **`readGNUSparseMap0x1` 関数の引数名変更**: `headers` から `extHdrs` に変更されました。これは意味的な変更であり、機能には影響しませんが、PAX拡張ヘッダーであることをより明確に示しています。
2.  **`numEntries` の取得と初期検証**:
    *   `numEntriesStr := extHdrs[paxGNUSparseNumBlocks]` で `numEntries` の文字列を取得します。
    *   `numEntries, err := strconv.ParseInt(numEntriesStr, 10, 0)` で文字列を整数に変換します。ここで `bitSize` は `0` のままですが、これは意図的に `int` 型のネイティブなサイズでパースするためです。
    *   **オーバーフロー耐性のある検証ロジックの追加**:
        ```go
        if err != nil || numEntries < 0 || int(2*numEntries) < int(numEntries) {
            return nil, ErrHeader
        }
        ```
        この行が追加され、`numEntries` が有効な範囲内にあることを厳密にチェックします。
        *   `err != nil`: パースエラーが発生した場合。
        *   `numEntries < 0`: パース結果が負の値になった場合（これは通常、オーバーフローの結果として発生する可能性があります）。
        *   `int(2*numEntries) < int(numEntries)`: `numEntries` が正の値であるにもかかわらず、`2*numEntries` がオーバーフローして `int` 型の最大値を超え、結果として元の `numEntries` よりも小さな値（または負の値）になった場合に真となります。これにより、`numEntries` が `int` 型で安全に2倍できる範囲内にあることを保証します。
3.  **`sparseMap` のパースにおける `bitSize=64` の指定**:
    *   スパースマップ内の `offset` と `numBytes` をパースする `strconv.ParseInt` の呼び出しで、`bitSize` パラメータが `0` から `64` に変更されました。
        ```go
        offset, err := strconv.ParseInt(sparseMap[2*i], 10, 64)
        // ...
        numBytes, err := strconv.ParseInt(sparseMap[2*i+1], 10, 64)
        ```
        これにより、これらの値が常に64ビット整数としてパースされ、32ビットシステムでの誤動作が解消されます。

### `src/archive/tar/reader_test.go` の変更点

`TestReadGNUSparseMap0x1` 関数は、単一のテストケースから、様々なエッジケースを網羅するテーブル駆動テストに拡張されました。

1.  **`maxUint` と `maxInt` の定義**: システムの最大符号なし整数と最大符号付き整数を定義し、オーバーフローテストケースの作成に利用しています。
2.  **`big1`, `big2`, `big3` の定義**: `maxInt` を利用して、オーバーフローを引き起こす可能性のある大きな数値の文字列表現を生成しています。
    *   `big1`: `maxInt` と同じ値。
    *   `big2`: `maxInt/2 + 1`。この値の2倍は `maxInt` を超え、オーバーフローを引き起こす可能性があります。
    *   `big3`: `maxInt/3`。
3.  **`vectors` スライス**: 構造体のスライスとして定義され、各要素が1つのテストケースを表します。
    *   `extHdrs`: 入力となるPAXヘッダーマップ。
    *   `sparseMap`: 期待される `sparseEntry` のスライス。
    *   `err`: 期待されるエラー。
4.  **追加されたテストケース**:
    *   `paxGNUSparseNumBlocks` が負の値 (`-4`) の場合。
    *   `paxGNUSparseNumBlocks` が数値ではない文字列 (`"fee "`) の場合。
    *   `paxGNUSparseNumBlocks` が `maxInt` や `maxInt/2 + 1` のようなオーバーフローを引き起こす可能性のある大きな値の場合。これらのケースでは `ErrHeader` が期待されます。
    *   `paxGNUSparseMap` 内のオフセットやバイト数が不正な形式 (`"0.5"`, `"5.5"`, `"fewafewa.5"`) の場合。
    *   既存の正しい動作を検証するテストケースも含まれています。
5.  **テストループ**: `vectors` スライスをループし、各テストケースに対して `readGNUSparseMap0x1` を呼び出し、結果 (`sparseEntry` スライスとエラー) が期待値と一致するかどうかを `reflect.DeepEqual` を使用して検証します。

これらのテストケースの追加により、`readGNUSparseMap0x1` 関数が様々な不正な入力やエッジケースに対して堅牢に動作することが保証されます。

## 元コミット内容

`archive/tar: readGNUSparseMap0x1` における数値オーバーフローの問題を修正。

動機：
*   `numEntries` を検証するロジックがオーバーフローを起こし、誤って検証を通過してしまう可能性があり、悪意のあるファイルが任意のメモリを割り当てることを許してしまう。
*   `strconv.ParseInt` の使用において、整数精度が64ビットに設定されていないため、32ビットマシンでこのコードが正しく動作しない。

## 変更の背景

このコミットは、Go言語の標準ライブラリである `archive/tar` パッケージが、特にGNU sparse format version 0.1でエンコードされたtarアーカイブを処理する際に遭遇する可能性のある2つの重要な問題を解決するために行われました。

1.  **数値オーバーフローによるメモリ割り当ての脆弱性**: `readGNUSparseMap0x1` 関数は、tarアーカイブのPAXヘッダーからスパースマップのエントリ数を読み取ります。このエントリ数 (`numEntries`) を検証する際に、内部的な計算で数値オーバーフローが発生する可能性がありました。オーバーフローが発生すると、実際には非常に大きな値であるにもかかわらず、検証ロジックが小さな値として誤認し、結果として悪意のあるtarファイルがシステムに任意の大量のメモリを割り当てることを引き起こす可能性がありました。これはサービス拒否（DoS）攻撃や、システムリソースの枯渇につながるセキュリティ上の脆弱性です。
2.  **32ビットシステムでの `strconv.ParseInt` の誤動作**: `numEntries` やスパースエントリのオフセット、バイト数を文字列から整数に変換するために `strconv.ParseInt` が使用されていましたが、この関数呼び出しで `bitSize` パラメータが `0` に設定されていました。Go言語の `strconv.ParseInt` ドキュメントによると、`bitSize` が `0` の場合、結果は `int` 型に変換されます。`int` 型のサイズはシステムに依存し、32ビットシステムでは32ビット、64ビットシステムでは64ビットとなります。このため、32ビットシステムでは、64ビットの値を期待する場面で32ビットの整数としてパースされ、大きな数値が正しく扱えないという問題が発生していました。これにより、スパースファイルの構造が正しく解釈されず、データ破損や予期せぬ動作を引き起こす可能性がありました。

これらの問題は、特に信頼できないソースから提供されるtarアーカイブを処理する際に、システムの安定性とセキュリティに直接的な影響を与えるため、修正が急務でした。

## 前提知識の解説

### `archive/tar` パッケージ

`archive/tar` はGo言語の標準ライブラリの一部で、tarアーカイブ（テープアーカイブ）の読み書きをサポートします。tarファイルは、複数のファイルを一つのアーカイブにまとめるための一般的な形式です。このパッケージは、標準的なtar形式だけでなく、GNU tarやPAX (POSIX.1-2001) 拡張などの様々なtar形式を扱うことができます。

### GNU Sparse Format (Version 0.1)

GNU tarは、スパースファイル（ファイル内の大部分がゼロで構成されているファイル）を効率的にアーカイブするための特別な形式をサポートしています。スパースファイルは、データベースファイルや仮想ディスクイメージなどでよく見られます。GNU sparse format version 0.1は、PAX (POSIX.1-2001) 拡張ヘッダーを利用して、ファイルのどの部分が「スパース」（つまりゼロ）であるか、どの部分が実際のデータであるかを示す「スパースマップ」を格納します。

*   **PAXヘッダー**: POSIX.1-2001で標準化されたtarの拡張形式で、従来のtarヘッダーでは表現できない長いファイル名、大きなファイルサイズ、拡張属性などをキーと値のペアの形式で格納できます。GNU sparse format version 0.1では、スパースマップの情報がPAXヘッダー内に `GNU.sparse.numblocks` (エントリ数) と `GNU.sparse.map` (オフセットとバイト数のペアのリスト) として格納されます。

### `strconv.ParseInt` 関数

Go言語の `strconv` パッケージは、文字列と数値の間の変換を提供します。`ParseInt` 関数は、指定された文字列を整数として解析します。

```go
func ParseInt(s string, base int, bitSize int) (int64, error)
```

*   `s`: 解析する文字列。
*   `base`: 数値の基数（例: 10進数の場合は10）。
*   `bitSize`: 結果の整数が収まるビット数。`0` の場合、`int` 型のビットサイズ（32ビットシステムでは32、64ビットシステムでは64）が使用されます。`8`, `16`, `32`, `64` などの値を指定できます。この関数は常に `int64` を返しますが、`bitSize` はその値が指定されたビット数に収まるかどうかをチェックするために使用されます。

### 整数オーバーフロー

整数オーバーフローは、数値計算の結果が、その数値を格納するために割り当てられたデータ型が表現できる最大値を超えた場合に発生します。Go言語では、符号なし整数型（`uint` など）でオーバーフローが発生すると、値はモジュロ演算のようにラップアラウンドします（例: `uint8` の `255 + 1` は `0` になる）。符号付き整数型（`int` など）では、オーバーフローの動作は未定義ですが、一般的には予期せぬ値になったり、パニックを引き起こしたりします。

このコミットの文脈では、`numEntries` の検証ロジックで `2 * numEntries` のような計算が行われた際に、`numEntries` が非常に大きいと `2 * numEntries` がオーバーフローし、実際よりも小さな値として扱われることで、悪意のある入力が検証をすり抜ける可能性がありました。

### 32ビットと64ビットシステム

コンピュータのアーキテクチャは、一度に処理できるデータのビット幅によって32ビットまたは64ビットに分類されます。Go言語では、`int` 型のサイズは実行されているシステムのアーキテクチャに依存します。32ビットシステムでは `int` は32ビット幅であり、約-20億から+20億までの値を表現できます。一方、64ビットシステムでは `int` は64ビット幅であり、はるかに大きな値を表現できます。この違いが `strconv.ParseInt` の `bitSize=0` の挙動に影響を与え、クロスプラットフォームでの互換性の問題を引き起こしていました。

## 技術的詳細

### 脆弱性の詳細

`readGNUSparseMap0x1` 関数は、PAXヘッダーから `GNU.sparse.numblocks` キーの値を取得し、これを `numEntries` (スパースエントリの数) として解析します。元のコードでは、この `numEntries` を検証するために以下のロジックを使用していました。

```go
numEntries, err := strconv.ParseInt(numEntriesStr, 10, 0)
// ...
if int64(len(sparseMap)) != 2*numEntries {
    return nil, ErrHeader
}
```

ここで問題となるのは2点です。

1.  **`strconv.ParseInt` の `bitSize=0`**: `strconv.ParseInt` の第3引数 `bitSize` が `0` に設定されているため、結果は `int` 型のビットサイズに依存します。32ビットシステムでは `numEntries` が32ビット整数として扱われ、`int64` にキャストされる前にオーバーフローする可能性がありました。これにより、非常に大きな `numEntriesStr` が与えられた場合でも、32ビットの範囲に収まる小さな負の値として解釈され、その後の検証をすり抜ける可能性がありました。
2.  **`2*numEntries` のオーバーフローチェックの欠陥**: `int64(len(sparseMap)) != 2*numEntries` の比較において、`2*numEntries` の計算自体がオーバーフローする可能性がありました。もし `numEntries` が `int` 型で表現できる最大値の半分より大きい場合、`2*numEntries` はオーバーフローして負の値になったり、予期せぬ小さな値になったりします。これにより、`len(sparseMap)` が非常に大きくても、`2*numEntries` がオーバーフローによって小さな値になることで、このチェックが誤って通過してしまう可能性がありました。結果として、`sparseMap` の長さが `2*numEntries` の期待値と一致しないにもかかわらず、検証が成功し、後続の `make([]sparseEntry, 0, numEntries)` で非常に大きなメモリ割り当てが要求され、システムリソースを枯渇させる可能性がありました。

### 修正の詳細

コミットはこれらの問題を以下の方法で解決しています。

1.  **`numEntries` の厳密な検証**: `numEntries` をパースした後、以下のチェックが追加されました。

    ```go
    if err != nil || numEntries < 0 || int(2*numEntries) < int(numEntries) {
        return nil, ErrHeader
    }
    ```
    *   `numEntries < 0`: `numEntries` が負の値になることはありえないため、負の値であればエラーとします。これは `strconv.ParseInt` が負の値を返す可能性があるため重要です。
    *   `int(2*numEntries) < int(numEntries)`: これは整数オーバーフローを検出するための一般的なイディオムです。もし `numEntries` が正の値で、`2*numEntries` がオーバーフローして負の値になったり、元の `numEntries` よりも小さな値になったりした場合、この条件が真となり、エラーが返されます。これにより、`2*numEntries` の計算が安全に行える範囲内にあることを保証します。このチェックは、`numEntries` が `int` 型の最大値の半分を超える場合にオーバーフローが発生することを効果的に防ぎます。

2.  **`strconv.ParseInt` の `bitSize` の指定**: スパースエントリの `offset` と `numBytes` をパースする際に、`strconv.ParseInt` の `bitSize` パラメータが `0` から `64` に変更されました。

    ```go
    // 変更前
    offset, err := strconv.ParseInt(sparseMap[2*i], 10, 0)
    numBytes, err := strconv.ParseInt(sparseMap[2*i+1], 10, 0)

    // 変更後
    offset, err := strconv.ParseInt(sparseMap[2*i], 10, 64)
    numBytes, err := strconv.ParseInt(sparseMap[2*i+1], 10, 64)
    ```
    これにより、32ビットシステムでもこれらの値が常に64ビット整数として正しく解析されるようになり、大きなオフセットやバイト数を持つスパースファイルが正しく処理されることが保証されます。

これらの変更により、悪意のある入力によるメモリ枯渇攻撃を防ぎ、32ビットシステムと64ビットシステムの両方で `archive/tar` パッケージがスパースファイルを一貫して正しく処理できるようになりました。

1.  **`readGNUSparseMap0x1` 関数の引数名変更**: `headers` から `extHdrs` に変更されました。これは意味的な変更であり、機能には影響しませんが、PAX拡張ヘッダーであることをより明確に示しています。
2.  **`numEntries` の取得と初期検証**:
    *   `numEntriesStr := extHdrs[paxGNUSparseNumBlocks]` で `numEntries` の文字列を取得します。
    *   `numEntries, err := strconv.ParseInt(numEntriesStr, 10, 0)` で文字列を整数に変換します。ここで `bitSize` は `0` のままですが、これは意図的に `int` 型のネイティブなサイズでパースするためです。
    *   **オーバーフロー耐性のある検証ロジックの追加**:
        ```go
        if err != nil || numEntries < 0 || int(2*numEntries) < int(numEntries) {
            return nil, ErrHeader
        }
        ```
        この行が追加され、`numEntries` が有効な範囲内にあることを厳密にチェックします。
        *   `err != nil`: パースエラーが発生した場合。
        *   `numEntries < 0`: パース結果が負の値になった場合（これは通常、オーバーフローの結果として発生する可能性があります）。
        *   `int(2*numEntries) < int(numEntries)`: `numEntries` が正の値であるにもかかわらず、`2*numEntries` がオーバーフローして `int` 型の最大値を超え、結果として元の `numEntries` よりも小さな値（または負の値）になった場合に真となります。これにより、`numEntries` が `int` 型で安全に2倍できる範囲内にあることを保証します。
3.  **`sparseMap` のパースにおける `bitSize=64` の指定**:
    *   スパースマップ内の `offset` と `numBytes` をパースする `strconv.ParseInt` の呼び出しで、`bitSize` パラメータが `0` から `64` に変更されました。
        ```go
        offset, err := strconv.ParseInt(sparseMap[2*i], 10, 64)
        // ...
        numBytes, err := strconv.ParseInt(sparseMap[2*i+1], 10, 64)
        ```
        これにより、これらの値が常に64ビット整数としてパースされ、32ビットシステムでの誤動作が解消されます。

### `src/archive/tar/reader_test.go` の変更点

`TestReadGNUSparseMap0x1` 関数は、単一のテストケースから、様々なエッジケースを網羅するテーブル駆動テストに拡張されました。

1.  **`maxUint` と `maxInt` の定義**: システムの最大符号なし整数と最大符号付き整数を定義し、オーバーフローテストケースの作成に利用しています。
2.  **`big1`, `big2`, `big3` の定義**: `maxInt` を利用して、オーバーフローを引き起こす可能性のある大きな数値の文字列表現を生成しています。
    *   `big1`: `maxInt` と同じ値。
    *   `big2`: `maxInt/2 + 1`。この値の2倍は `maxInt` を超え、オーバーフローを引き起こす可能性があります。
    *   `big3`: `maxInt/3`。
3.  **`vectors` スライス**: 構造体のスライスとして定義され、各要素が1つのテストケースを表します。
    *   `extHdrs`: 入力となるPAXヘッダーマップ。
    *   `sparseMap`: 期待される `sparseEntry` のスライス。
    *   `err`: 期待されるエラー。
4.  **追加されたテストケース**:
    *   `paxGNUSparseNumBlocks` が負の値 (`-4`) の場合。
    *   `paxGNUSparseNumBlocks` が数値ではない文字列 (`"fee "`) の場合。
    *   `paxGNUSparseNumBlocks` が `maxInt` や `maxInt/2 + 1` のようなオーバーフローを引き起こす可能性のある大きな値の場合。これらのケースでは `ErrHeader` が期待されます。
    *   `paxGNUSparseMap` 内のオフセットやバイト数が不正な形式 (`"0.5"`, `"5.5"`, `"fewafewa.5"`) の場合。
    *   既存の正しい動作を検証するテストケースも含まれています。
5.  **テストループ**: `vectors` スライスをループし、各テストケースに対して `readGNUSparseMap0x1` を呼び出し、結果 (`sparseEntry` スライスとエラー) が期待値と一致するかどうかを `reflect.DeepEqual` を使用して検証します。

これらのテストケースの追加により、`readGNUSparseMap0x1` 関数が様々な不正な入力やエッジケースに対して堅牢に動作することが保証されます。

## 変更の背景

Go言語の `net/http` パッケージは、ウェブアプリケーション開発において中心的な役割を担っています。HTTP/2は、HTTP/1.1に比べてパフォーマンスと効率を大幅に向上させる新しいプロトコルであり、Goの標準ライブラリにそのサポートを完全に統合することは非常に重要でした。

このコミットが行われた2015年当時、GoにおけるHTTP/2の実装はまだ進行中であり、`golang.org/x/net/http2` という外部パッケージで開発が進められていました。このコミットは、その外部パッケージの成果を `net/http` に取り込み、安定性と互換性を高めるための重要なステップでした。

特に、以下の問題が背景にありました。
1.  **HTTP/1とHTTP/2の動作の一貫性**: 異なるプロトコルであっても、ユーザーから見た `net/http` のAPIの振る舞いは一貫しているべきです。このコミットは、両プロトコル間でのハンドラとトランスポートの動作の同等性を検証するテストを追加することで、この一貫性を保証しようとしました。
2.  **`Content-Length` の不正確な処理**: HTTP/2クライアントがサーバーから受け取った `Content-Length` ヘッダを正しく処理しない問題（#13315）がありました。これは、レスポンスボディの読み取りが途中で終了したり、逆に余分なデータを読み取ろうとしたりする原因となります。
3.  **不適切な `Transfer-Encoding: chunked` ヘッダの送信**: HTTP/1.1では、ボディを持たないレスポンス（例: 204 No Content, 304 Not Modified）に対して `Transfer-Encoding: chunked` を送信することはプロトコル違反ではありませんが、HTTP/2ではチャンクエンコーディングの概念がありません。サーバーがこれらのステータスコードに対して誤って `Transfer-Encoding: chunked` を送信する問題（#13316, #13317）があり、これはクライアント側の誤動作を引き起こす可能性がありました。
4.  **`HEAD` リクエストのボディ処理**: `HEAD` リクエストは、`GET` リクエストと同じヘッダを返しますが、ボディは持ちません。しかし、HTTP/2の実装において、`HEAD` リクエストに対して誤ってボディが送信される可能性がありました。
5.  **ハンドラが宣言した `Content-Length` を超えて書き込む問題**: サーバーハンドラが `Content-Length` ヘッダで宣言したバイト数よりも多くのデータを書き込もうとした場合、HTTP/2サーバーがこれを適切に処理し、エラーを返す必要がありました。

これらの問題に対処し、GoのHTTP/2実装の堅牢性を高めることが、このコミットの主要な動機でした。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

1.  **HTTP/1.1とHTTP/2**:
    *   **HTTP/1.1**: テキストベースのプロトコルで、リクエスト/レスポンスごとにTCPコネクションを確立するか、パイプライン処理（ただしヘッドオブラインブロッキングの問題がある）を使用します。ヘッダは冗長で、各リクエスト/レスポンスで繰り返されます。
    *   **HTTP/2**: バイナリプロトコルで、単一のTCPコネクション上で複数のリクエスト/レスポンスを多重化（multiplexing）できます。これにより、ヘッドオブラインブロッキングが解消され、効率が向上します。ヘッダはHPACKというアルゴリズムで圧縮されます。サーバープッシュやストリームの優先順位付けといった機能も持ちます。
2.  **Goの `net/http` パッケージ**:
    *   Go言語の標準ライブラリで、HTTPクライアントとサーバーを実装するための機能を提供します。
    *   `http.Handler`: HTTPリクエストを処理するためのインターフェース。`ServeHTTP(ResponseWriter, *Request)` メソッドを持ちます。
    *   `http.ResponseWriter`: HTTPレスポンスを書き込むためのインターフェース。ヘッダの設定やボディの書き込みを行います。
    *   `http.Request`: 受信したHTTPリクエストを表す構造体。
    *   `http.Transport`: HTTPクライアントがリクエストを送信し、レスポンスを受信するための低レベルなインターフェース。コネクションの管理、プロキシ、TLSハンドシェイクなどを担当します。
    *   `httptest.Server`: テスト目的でHTTPサーバーを簡単に起動するためのユーティリティ。
3.  **`Content-Length` ヘッダ**: HTTPメッセージボディのオクテット長を示すヘッダ。このヘッダが存在する場合、クライアントは指定されたバイト数だけボディを読み取ることが期待されます。
4.  **`Transfer-Encoding` ヘッダ**: メッセージボディに適用されたエンコーディング形式を示すヘッダ。HTTP/1.1では、ボディが動的に生成される場合などに `chunked` がよく使用されます。HTTP/2では、フレームベースのプロトコルであるため、このヘッダは通常使用されません。
5.  **HTTPステータスコード**:
    *   `204 No Content`: リクエストは成功したが、レスポンスボディは含まれないことを示す。
    *   `304 Not Modified`: リクエストされたリソースは変更されていないため、クライアントはキャッシュされたバージョンを使用できることを示す。レスポンスボディは含まれない。
    *   `1xx Informational`: 暫定的なレスポンス。レスポンスボディは含まれない。
    *   **RFC2616, Section 4.4**: HTTP/1.1の仕様で、これらのステータスコード（1xx, 204, 304）のレスポンスにはメッセージボディを含めてはならないと規定されています。HTTP/2の実装もこの原則に従う必要があります。
6.  **`HEAD` リクエスト**: `GET` リクエストと同様にリソースのヘッダ情報を取得しますが、レスポンスボディは含まれません。

## 技術的詳細

このコミットの技術的な詳細は、主に `src/net/http/h2_bundle.go` と `src/net/http/clientserver_test.go` の変更に集約されます。

### `h2_bundle.go` の変更点

`h2_bundle.go` は、`golang.org/x/net/http2` パッケージから取り込まれたHTTP/2プロトコル実装のコア部分です。

1.  **`http2bodyAllowedForStatus` 関数の追加**:
    ```go
    func http2bodyAllowedForStatus(status int) bool {
    	switch {
    	case status >= 100 && status <= 199:
    		return false
    	case status == 204:
    		return false
    	case status == 304:
    		return false
    	}
    	return true
    }
    ```
    この関数は、与えられたHTTPステータスコードがレスポンスボディを許可するかどうかを判断します。RFC2616のセクション4.4に基づき、1xx（情報）、204（No Content）、304（Not Modified）のステータスコードではボディが許可されないことを明示的にチェックします。これにより、HTTP/2サーバーがこれらのステータスコードで誤ってボディを送信するのを防ぎます。

2.  **`http2serverConn.newWriterAndRequest` の修正**:
    `HEAD` リクエストの場合に、ストリームが `http2stateOpen` 状態（ボディが期待される状態）であれば、`http2ErrCodeProtocol` エラーを返すようになりました。これは、`HEAD` リクエストがボディを持つべきではないというプロトコルの要件を強制するものです。

3.  **`http2responseWriterState.writeChunk` の修正**:
    *   **`Content-Length` の厳密な処理**: ハンドラが `Content-Length` ヘッダを設定した場合、その値が `rws.sentContentLen` に保存されます。これにより、後続の書き込みがこの宣言された長さを超えないように監視できます。
    *   **`Content-Type` の自動検出**: `Content-Type` ヘッダが設定されておらず、かつボディが許可されるステータスコードの場合に、`DetectContentType` を使用してボディの内容から `Content-Type` を自動検出するようになりました。
    *   **`Date` ヘッダの追加**: `Date` ヘッダがレスポンスヘッダに存在しない場合、自動的に現在時刻で追加されるようになりました。
    *   **`endStream` フラグの修正**: `HEAD` リクエストの場合、`endStream` フラグが常に `true` に設定されるようになりました。これは、`HEAD` レスポンスにはボディがないため、ヘッダフレームの送信でストリームが終了することを示すためです。
    *   **`HEAD` リクエストでのボディ書き込み防止**: `isHeadResp` が `true` の場合、`len(p)` （書き込もうとしているボディの長さ）を返しますが、実際のデータフレームは送信されません。これにより、`HEAD` リクエストに対してボディが誤って送信されるのを防ぎます。

4.  **`http2responseWriter.write` の修正**:
    *   **ボディが許可されないステータスコードのチェック**: `http2bodyAllowedForStatus(rws.status)` を使用して、現在のステータスコードでボディの書き込みが許可されているかをチェックします。許可されていない場合は `ErrBodyNotAllowed` を返します。これは、`304 Not Modified` や `204 No Content` のレスポンスにボディを書き込もうとした場合にエラーを発生させるための重要な修正です。
    *   **`Content-Length` 超過のチェック**: ハンドラが `Content-Length` ヘッダで宣言したバイト数（`rws.sentContentLen`）を超えてデータを書き込もうとした場合、`"http2: handler wrote more than declared Content-Length"` というエラーを返すようになりました。これにより、サーバー側でのプロトコル違反を防ぎます。

5.  **`http2clientStream` 構造体の拡張**:
    *   `req *Request`: 関連するリクエストを保持するようになりました。
    *   `bytesRemain int64`: レスポンスボディで残っているバイト数を追跡します。`-1` は不明を意味します。
    *   `readErr error`: 読み取り中に発生したエラーを保持します。

6.  **`http2transportResponseBody.Read` の修正**:
    *   **`Content-Length` の尊重**: `bytesRemain` フィールドを使用して、クライアントが `Content-Length` ヘッダで宣言されたバイト数を超えて読み取ろうとした場合に、`"net/http: server replied with more than declared Content-Length; truncated"` エラーを発生させ、ストリームをリセットするようになりました。
    *   **`io.ErrUnexpectedEOF` の検出**: `Content-Length` が指定されているにもかかわらず、宣言されたバイト数よりも少ないデータしか受信しなかった場合に `io.ErrUnexpectedEOF` を返すようになりました。これにより、#13315 の問題が修正されます。

### `clientserver_test.go` の追加

このファイルは、HTTP/1とHTTP/2の両方でクライアントとサーバーの相互作用をテストするための新しいテストスイートです。

1.  **`clientServerTest` 構造体と `newClientServerTest` ヘルパー**:
    *   HTTP/1とHTTP/2の両方のシナリオでテストサーバー (`httptest.Server`) とクライアント (`http.Client`) を簡単にセットアップするためのユーティリティを提供します。
    *   HTTP/2の場合、`httptest.NewUnstartedServer` を使用し、`ExportHttp2ConfigureServer` と `ExportHttp2ConfigureTransport` を呼び出してHTTP/2を有効にします。

2.  **`h12Compare` 構造体と `run` メソッド**:
    *   HTTP/1とHTTP/2の動作を比較するための汎用的なテストヘルパーです。
    *   同じハンドラに対してHTTP/1とHTTP/2の両方でリクエストを送信し、レスポンスヘッダとボディが `reflect.DeepEqual` で比較されます。これにより、両プロトコル間で一貫した動作が保証されているかを確認できます。
    *   `normalizeRes` ヘルパー関数は、比較前にプロトコル固有のフィールド（`Proto`, `ProtoMajor`, `ProtoMinor`, `Date`, `TLS` など）を正規化し、比較のノイズを減らします。

3.  **新しいテストケース**:
    *   `TestH12_200NoBody`, `TestH12_SmallBody`, `TestH12_ExplicitContentLength`, `TestH12_FlushBeforeBody`, `TestH12_FlushMidBody`: さまざまなボディサイズやフラッシュのタイミングでのHTTP/1とHTTP/2の動作を比較します。
    *   `TestH12_Head_ExplicitLen`, `TestH12_Head_ImplicitLen`: `HEAD` リクエストにおける `Content-Length` の処理をテストします。
    *   `TestH12_HandlerWritesTooLittle`: ハンドラが宣言した `Content-Length` よりも少ないデータを書き込んだ場合のクライアントの動作をテストします。
    *   `TestH12_HandlerWritesTooMuch`: ハンドラが宣言した `Content-Length` よりも多くのデータを書き込もうとした場合のサーバーの動作をテストします。
    *   `Test304Responses_h1`, `Test304Responses_h2`: `304 Not Modified` レスポンスが `Transfer-Encoding` ヘッダを持たず、ボディも持たないことを検証します。これは #13316 の修正をテストするものです。

4.  **`http2transportResponseBody.Read` 内の `Content-Length` 尊重ロジック**:
    ```go

    	if cs.bytesRemain != -1 {
    		if int64(n) > cs.bytesRemain {
    			n = int(cs.bytesRemain)
    			if err == nil {
    				err = errors.New("net/http: server replied with more than declared Content-Length; truncated")
    ```

    クライアント側で `Content-Length` を厳密にチェックし、サーバーが宣言と異なるデータを送信した場合に適切なエラーを発生させる部分です。

## コアとなるコードの解説

これらの変更は、Goの `net/http` パッケージがHTTP/2プロトコル仕様に厳密に準拠し、HTTP/1.1との互換性を保ちつつ、堅牢な動作を保証するために不可欠です。

*   **`http2bodyAllowedForStatus`**: この関数は、HTTPプロトコルの基本的なルール（特定のステータスコードではボディが許可されない）をHTTP/2実装に組み込むことで、プロトコル違反を防ぎます。これにより、クライアントが予期しないボディデータを受信して誤動作する可能性が低減されます。

*   **サーバーサイドの `Content-Length` と `HEAD` 処理**:
    *   `http2responseWriterState.writeChunk` での `Content-Length` の厳密な解析と `rws.sentContentLen` への保存は、ハンドラが宣言した `Content-Length` を超えて書き込むことを防ぐための基盤となります。
    *   `HEAD` リクエストに対する `endStream` の適切な設定とボディ書き込みの抑制は、`HEAD` リクエストのセマンティクス（ボディなし）をHTTP/2でも正しく維持するために重要です。
    *   `http2responseWriter.write` での `ErrBodyNotAllowed` と `Content-Length` 超過チェックは、サーバーハンドラがプロトコル違反を犯した場合に、それを検出し、適切なエラーを返すことで、サーバーの堅牢性を高めます。これにより、不正なレスポンスがクライアントに送信されることを防ぎます。

*   **クライアントサイドの `Content-Length` 尊重**:
    *   `http2clientStream` に `bytesRemain` と `readErr` を追加し、`http2transportResponseBody.Read` でこれらを活用することで、クライアントはサーバーから受信した `Content-Length` を厳密に監視できるようになりました。
    *   サーバーが `Content-Length` を超えるデータを送信した場合、クライアントはそれを検出し、ストリームをリセットしてエラーを発生させます。これにより、クライアントが余分なデータを処理しようとしてハングアップしたり、誤ったデータを解釈したりするのを防ぎます。
    *   逆に、宣言された `Content-Length` に満たないデータしか受信しなかった場合も `io.ErrUnexpectedEOF` を返すことで、部分的なレスポンスを完全なものとして扱ってしまうことを防ぎます。

これらの変更は、HTTP/2の複雑なストリームとフレームの概念を扱いながらも、HTTP/1.1のセマンティクスとの一貫性を保ち、開発者が `net/http` を使用する際にプロトコルの詳細を意識することなく、期待通りの動作を得られるようにするためのものです。特に、テストの強化は、これらの複雑な相互作用における潜在的なバグを早期に発見し、修正するために不可欠な役割を果たしています。

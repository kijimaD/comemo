# [インデックス 22781] ファイルの概要

このコミットは、Goの`database/sql`パッケージにおけるデータベース接続プールの振る舞いを改善し、特に多数の不良な接続が存在する場合に、クエリが不必要に`driver.ErrBadConn`エラーで失敗する問題を解決します。既存の接続再試行メカニズムを改良し、一定回数の再試行後に新しい接続を強制的に使用することで、堅牢性を高めています。

## 変更の背景

このコミットの背景には、Goの`database/sql`パッケージが持つデータベース接続プールの挙動に関する問題がありました。具体的には、以下のようなシナリオで問題が発生していました。

1.  **多数の不良接続**: データベースサーバーが再起動されたり、ネットワークの問題が発生したりすると、接続プール内の既存の接続が「不良」な状態になることがあります。
2.  **`maxBadConnRetries`の限界**: 以前の`database/sql`パッケージでは、`driver.ErrBadConn`エラーが発生した場合、`maxBadConnRetries`という定数で定義された回数だけ接続を再試行するメカニズムがありました。この定数は以前は`10`に設定されていました。
3.  **不必要なエラー**: 接続プールが`maxBadConnRetries`よりも多くの接続を保持しており、かつその中に多数の不良接続が含まれている場合、クエリは`maxBadConnRetries`回再試行しても常に不良接続を引き当ててしまい、最終的に不必要に`driver.ErrBadConn`エラーで失敗してしまう可能性がありました。これは、プール内に有効な接続が存在するにもかかわらず、それを見つけ出す前に再試行回数が尽きてしまうためです。

この問題は、特にデータベースサーバーのメンテナンスや一時的なネットワーク障害の後に、アプリケーションがデータベースに再接続する際に顕著に現れ、アプリケーションの可用性に影響を与える可能性がありました。このコミットは、このような状況下での`database/sql`パッケージの堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoの`database/sql`パッケージに関する基本的な概念と、データベース接続の管理に関する知識が必要です。

*   **`database/sql`パッケージ**: Goの標準ライブラリの一部であり、SQLデータベースとの対話のための汎用的なインターフェースを提供します。このパッケージ自体は特定のデータベースドライバーを含まず、データベース固有のドライバー（例: `github.com/go-sql-driver/mysql`、`github.com/lib/pq`）と組み合わせて使用されます。
*   **`driver.Conn`**: データベースドライバーが実装するインターフェースで、単一のデータベース接続を表します。
*   **接続プール**: `database/sql`パッケージは、データベースへの接続を効率的に管理するために接続プールを内部的に保持しています。これにより、新しいクエリごとに接続を確立・切断するオーバーヘッドを削減し、パフォーマンスを向上させます。接続は使用後にプールに戻され、再利用されます。
*   **`driver.ErrBadConn`**: データベースドライバーが返す可能性のあるエラーの一つで、接続が不良な状態であることを示します。これは、ネットワークの問題、データベースサーバーのダウン、接続のタイムアウトなど、様々な理由で発生します。このエラーを受け取った場合、`database/sql`パッケージは通常、その接続をプールから破棄し、新しい接続で再試行を試みます。
*   **`maxBadConnRetries`**: `database/sql`パッケージ内部で使用される定数で、`driver.ErrBadConn`エラーが発生した場合に、接続を再試行する最大回数を定義します。この回数を超えても不良接続が続く場合、操作は失敗とみなされます。

## 技術的詳細

このコミットは、`database/sql`パッケージの接続取得と再試行のロジックに根本的な変更を加えています。

1.  **`connReuseStrategy`の導入**:
    *   `connReuseStrategy`という新しい型が導入されました。これは、データベース接続をどのように取得するかを決定するための戦略を定義する`uint8`型の列挙体です。
    *   `alwaysNewConn`: 常に新しいデータベース接続を強制的に開きます。既存のプールされた接続は使用しません。
    *   `cachedOrNewConn`: キャッシュされた（プール内の）接続が利用可能であればそれを使用し、なければ新しい接続を開くか、`MaxOpenConns`の制限に達している場合は接続が利用可能になるまで待機します。

2.  **`DB.conn()`メソッドの変更**:
    *   `DB.conn()`メソッドのシグネチャが変更され、`strategy connReuseStrategy`引数を受け取るようになりました。これにより、接続を取得する際に、呼び出し元が接続再利用の戦略を指定できるようになります。
    *   このメソッド内部のロジックも更新され、`strategy`に基づいて接続プールから接続を取得するか、新しい接続を開くかが決定されます。`cachedOrNewConn`が指定された場合、まず`db.freeConn`（空き接続リスト）から接続を試み、なければ新しい接続を開きます。

3.  **`maxBadConnRetries`の変更**:
    *   `maxBadConnRetries`定数の値が`10`から`2`に大幅に引き下げられました。これは、新しい再試行戦略により、多数の再試行が不要になったためです。

4.  **主要な操作（`Prepare`, `Exec`, `Query`, `Begin`）の再試行ロジックの改善**:
    *   `DB`構造体の`Prepare`, `Exec`, `Query`, `Begin`といった主要なデータベース操作メソッドの内部で、`driver.ErrBadConn`エラーに対する再試行ロジックが変更されました。
    *   これらのメソッドは、まず`maxBadConnRetries`回まで`cachedOrNewConn`戦略を使用して接続を再試行します。
    *   もし`maxBadConnRetries`回再試行しても`driver.ErrBadConn`が返され続けた場合、**最後の試行では`alwaysNewConn`戦略を強制的に使用**して、新しい接続で操作を試みます。これにより、プール内に不良接続が多数存在する場合でも、最終的には確実に新しい（そしておそらく有効な）接続が使用されるようになります。

5.  **テストケースの追加と変更**:
    *   `src/database/sql/fakedb_test.go`では、テスト用の`fakeConn`構造体に`stickyBad`フィールドが追加されました。これは、特定の接続を常に不良としてマークし、`driver.ErrBadConn`を返すようにシミュレートするために使用されます。これにより、接続プール内に意図的に多数の不良接続を作成し、新しい再試行ロジックをテストすることが可能になります。
    *   `src/database/sql/sql_test.go`には、`TestManyErrBadConn`という新しいテストケースが追加されました。このテストは、`maxBadConnRetries`よりも多くの不良接続がプールに存在する状況をシミュレートし、`Query`, `Exec`, `Begin`, `Prepare`といった操作が正しく成功することを確認します。

これらの変更により、`database/sql`パッケージは、接続プール内に不良接続が多数存在する場合でも、より堅牢に動作し、不必要なエラーを回避できるようになりました。

## コアとなるコードの解説

### `src/database/sql/sql.go`の変更

最も重要な変更は、`DB.conn()`メソッドが接続取得の「戦略」を受け取るようになった点です。

```go
// connReuseStrategy determines how (*DB).conn returns database connections.
type connReuseStrategy uint8

const (
	// alwaysNewConn forces a new connection to the database.
	alwaysNewConn connReuseStrategy = iota
	// cachedOrNewConn returns a cached connection, if available, else waits
	// for one to become available (if MaxOpenConns has been reached) or
	// creates a new database connection.
	cachedOrNewConn
)

// conn returns a newly-opened or cached *driverConn.
func (db *DB) conn(strategy connReuseStrategy) (*driverConn, error) {
	db.mu.Lock()
	defer db.mu.Unlock()

	if db.closed {
		return nil, errDBClosed
	}

	// Prefer a free connection, if possible.
	numFree := len(db.freeConn)
	if strategy == cachedOrNewConn && numFree > 0 {
		conn := db.freeConn[0]
		copy(db.freeConn, db.freeConn[1:])
		db.freeConn = db.freeConn[:numFree-1]
		conn.inUse = true
		return conn, nil
	}

	// Out of free connections or we were asked not to use one. If we're not
	// allowed to open any more connections, make a request and wait.
	if db.maxOpen > 0 && db.numOpen >= db.maxOpen {
		req := make(chan connRequest, 1)
		db.connRequests <- req
		db.mu.Unlock() // Unlock before waiting for request
		ret := <-req
		return ret.conn, ret.err
	}

	db.numOpen++ // optimistically
	db.mu.Unlock() // Unlock before opening new connection
	ci, err := db.driver.Open(db.dsn)
	db.mu.Lock() // Relock after opening new connection
	if err != nil {
		db.numOpen-- // decrement on error
		return nil, err
	}
	dc := &driverConn{
		db:        db,
		ci:        ci,
		createdAt: db.nowFunc(),
	}
	return dc, nil
}
```

この変更により、`DB.conn()`は、呼び出し元が接続プールから既存の接続を優先するか（`cachedOrNewConn`）、それとも強制的に新しい接続を開くか（`alwaysNewConn`）を制御できるようになりました。

そして、`Prepare`, `Exec`, `Query`, `Begin`といった高レベルの操作メソッドでは、この新しい戦略が再試行ロジックに組み込まれています。例えば、`Prepare`メソッドの変更は以下のようになります。

```go
// maxBadConnRetries is the number of maximum retries if the driver returns
// driver.ErrBadConn to signal a broken connection before forcing a new
// connection to be opened.
const maxBadConnRetries = 2

func (db *DB) Prepare(query string) (*Stmt, error) {
	var stmt *Stmt
	var err error
	for i := 0; i < maxBadConnRetries; i++ {
		stmt, err = db.prepare(query, cachedOrNewConn) // 既存の接続を優先して試行
		if err != driver.ErrBadConn {
			break
		}
	}
	if err == driver.ErrBadConn {
		// maxBadConnRetries回試行してもダメなら、新しい接続を強制的に開いて最終試行
		return db.prepare(query, alwaysNewConn)
	}
	return stmt, err
}

func (db *DB) prepare(query string, strategy connReuseStrategy) (*Stmt, error) {
	// ... (既存のロジック)
	dc, err := db.conn(strategy) // ここで戦略が適用される
	// ... (既存のロジック)
}
```

このロジックは、まず`maxBadConnRetries`回（新しい値は`2`）まで、接続プールから既存の接続を再利用しようと試みます。もしこれらの試行がすべて`driver.ErrBadConn`で失敗した場合、それはプール内に有効な接続を見つけるのが難しい状況であることを示唆します。そこで、最後の手段として`alwaysNewConn`戦略を使い、強制的に新しい接続を確立して操作を再試行します。これにより、データベースサーバーが再起動された直後など、プール内の多くの接続が不良になっている状況でも、アプリケーションが迅速に回復し、有効な接続を確立できるようになります。

`maxBadConnRetries`が`10`から`2`に減らされたのは、この「最後の手段」の導入により、多数の再試行が不要になったためです。少数の再試行でプール内の有効な接続が見つからなければ、すぐに新しい接続を試みる方が効率的かつ堅牢であるという判断です。

### `src/database/sql/fakedb_test.go`と`src/database/sql/sql_test.go`の変更

テストコードの変更は、この新しいロジックが意図通りに機能することを検証するために不可欠です。`fakeConn`に`stickyBad`が追加されたことで、テスト中に特定の接続を永続的に不良状態に保つことが可能になり、`maxBadConnRetries`を超える不良接続が存在するシナリオを正確にシミュレートできるようになりました。

`TestManyErrBadConn`テストは、このシミュレーションを活用し、プール内の不良接続が`maxBadConnRetries`を超えても、最終的な操作が成功することを確認します。これは、このコミットが解決しようとしている問題の核心を突くテストであり、変更の有効性を保証します。

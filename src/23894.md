## 元コミット内容

このコミットは、`image/gif`パッケージ内の無効なパレットに関するテストを再有効化するものです。以前のコミット `https://go-review.googlesource.com/#/c/11227/` によってLZWエンコーダが不正な入力を拒否するように修正されたため、これらのテストは一時的に機能しなくなっていました。

`TestNoPalette` テストでは、`litWidth` が2のLZWエンコーダが入力バイト `128` を拒否するようになったため、`128` を `3` に変更しています。これは `3 <= (1<<2 - 1)` という条件を満たすため、有効な入力となります。

`TestPixelOutsidePaletteRange` テストでは、同様にLZWエンコーダが入力バイト `255` を拒否するようになりました。以前の `golang.org/cl/11227` の変更前は、`litWidth` が2のエンコーダは `255` を受け入れ、それを `(1<<2 - 1)` でマスクしていたため、実質的に `3` と同じ挙動をしていました。しかし、LZWエンコーダの変更後は `255` が単純に無効な入力となったため、テストケースから削除されました。このテストは、グローバルパレットの長さが2であるのに対し、`3` がそれよりも大きい値であるため、引き続きパレット範囲外のピクセルをテストしています。

## 変更の背景

この変更の背景には、Go言語の `image/gif` パッケージにおけるLZW (Lempel-Ziv-Welch) エンコーダの堅牢性向上があります。具体的には、`https://go-review.googlesource.com/#/c/11227/` で導入された変更が直接的な原因です。この先行コミットでは、LZWエンコーダが仕様に準拠しない、または処理できない「無効な入力」をより厳密に拒否するように修正されました。

GIF画像はLZW圧縮アルゴリズムを使用してピクセルデータを圧縮します。このアルゴリズムは、初期コードワードのビット幅（`litWidth`）に基づいて、入力シンボル（ピクセル値）の有効範囲を決定します。以前のLZWエンコーダは、この有効範囲を超える入力値に対して、単にビットマスクを適用して値を切り詰める（例: `255` を `3` にする）という挙動をしていました。これは、一部の不正なGIFデータが意図せず処理されてしまう可能性や、予期せぬ挙動を引き起こす可能性がありました。

先行コミット `11227` は、このような「寛容すぎる」挙動を改め、LZWエンコーダが `litWidth` で定義された有効範囲外の入力シンボルを明確に「無効」と判断し、エラーを返すように変更しました。この修正は、GIFエンコーダの堅牢性と仕様への準拠を高める上で重要でしたが、副作用として、既存のテストの一部が、もはや「無効な入力」を生成できなくなり、テストの意図が失われるか、テスト自体が失敗するようになりました。

本コミットは、このLZWエンコーダの変更によって一時的に無効化されていたテストを、新しいLZWエンコーダの挙動に合わせて修正し、再有効化することを目的としています。これにより、LZWエンコーダの堅牢性向上という恩恵を享受しつつ、無効なパレットデータに対するGIFデコーダの挙動を適切にテストし続けることが可能になります。

## 前提知識の解説

### GIF (Graphics Interchange Format)

GIFは、ビットマップ画像を扱う画像ファイルフォーマットの一つです。最大256色までのインデックスカラーをサポートし、アニメーションや透過を扱うことができます。GIFの画像データは、LZW (Lempel-Ziv-Welch) 圧縮アルゴリズムを用いて圧縮されます。

### LZW (Lempel-Ziv-Welch) 圧縮

LZWは可逆圧縮アルゴリズムであり、GIF画像の圧縮に用いられます。基本的な考え方は、繰り返し現れるバイトシーケンス（パターン）をより短いコードに置き換えることでデータを圧縮するというものです。

*   **初期コードワード (Initial Code Word)**: LZW圧縮の開始時に、各単一バイト値（0-255）と、特別なクリアコード (Clear Code) および停止コード (Stop Code) が辞書に登録されます。
*   **コードビット幅 (Code Size / `litWidth`)**: LZWエンコーダは、初期のコードビット幅（`litWidth`）から開始します。これは、初期の辞書エントリを表すために必要なビット数です。例えば、`litWidth` が2の場合、`2^2 = 4` つの初期コードワード（0, 1, 2, 3）を表現できます。実際のピクセル値は、この `litWidth` で表現可能な範囲内である必要があります。
*   **辞書拡張**: 圧縮中に新しいバイトシーケンスが出現すると、それらは辞書に追加され、新しいコードが割り当てられます。コードビット幅は、辞書が大きくなるにつれて動的に増加することがあります。
*   **有効な入力シンボル**: LZWエンコーダに入力されるピクセル値（シンボル）は、`litWidth` によって決定される範囲内である必要があります。具体的には、`0` から `(1 << litWidth) - 1` までの範囲です。この範囲外の入力は、通常、不正と見なされます。

### GIFパレット

GIF画像は、通常、カラーパレットを使用します。これは、画像内の各ピクセルが直接色情報を保持するのではなく、パレット内の色のインデックス（添字）を保持することを意味します。例えば、256色パレットの場合、ピクセル値は0から255までのインデックスとなります。

*   **グローバルカラーテーブル (Global Color Table)**: GIFファイル全体で共有されるパレットです。
*   **ローカルカラーテーブル (Local Color Table)**: 特定の画像ブロックにのみ適用されるパレットです。

このコミットで言及されている「パレット範囲外のピクセル」とは、ピクセル値がパレットの有効なインデックス範囲を超えている状態を指します。例えば、2色のパレット（インデックス0と1）しかないのに、ピクセル値が3である場合などです。

## 技術的詳細

このコミットの核心は、Goの `image/gif` パッケージ内のLZWエンコーダの挙動変更と、それに伴うテストの適応です。

### LZWエンコーダの厳格化 (CL 11227)

先行する `golang.org/cl/11227` の変更により、LZWエンコーダは入力シンボル（ピクセル値）の有効性をより厳格にチェックするようになりました。

*   **`litWidth` と有効範囲**: LZWエンコーダは、初期のコードビット幅 `litWidth` を設定します。この `litWidth` は、エンコーダが処理できるリテラルシンボル（ピクセル値）の最大値を決定します。最大値は `(1 << litWidth) - 1` です。
    *   例えば、`litWidth = 2` の場合、有効なリテラルシンボルは `0` から `(1 << 2) - 1 = 3` まで、つまり `0, 1, 2, 3` です。
*   **以前の挙動**: `litWidth` の範囲を超える入力（例: `litWidth = 2` のときに `128` や `255`）が与えられた場合、以前のエンコーダはこれらの値をビットマスク `(1 << litWidth) - 1` で切り詰めていました。
    *   `128 & ((1 << 2) - 1)` は `128 & 3 = 0` となります。
    *   `255 & ((1 << 2) - 1)` は `255 & 3 = 3` となります。
    この挙動は、不正な入力がエラーにならず、サイレントに処理されてしまうため、デバッグを困難にし、GIFファイルの破損につながる可能性がありました。
*   **新しい挙動**: `CL 11227` 以降、LZWエンコーダは `litWidth` の範囲外の入力シンボルを受け取ると、エラーを返すようになりました。これにより、不正なデータがエンコーダに渡された場合に、早期に問題を検出できるようになります。

### テストの修正

このコミットでは、上記のLZWエンコーダの変更に合わせて、`TestNoPalette` と `TestPixelOutsidePaletteRange` の2つのテストが修正されました。

1.  **`TestNoPalette`**:
    *   このテストは、パレットが存在しないGIF画像を生成し、その際にパレット範囲外のピクセル値がどのように扱われるかを検証するものです。
    *   以前は `pix := []byte{0, 128}` という入力を使用していました。`litWidth = 2` の場合、`128` は有効範囲 `0-3` を超えるため、新しいLZWエンコーダはこれを拒否します。
    *   修正後は `pix := []byte{0, 3}` となりました。`3` は `litWidth = 2` の有効範囲内であるため、エンコーダはこれを受け入れます。このテストの目的は「パレットがない場合にピクセル値がどうなるか」を検証することであり、`3` はパレットがない状況では依然として「無効なピクセル値」として機能します。
    *   また、`w.Write(pix)` と `w.Close()` の呼び出しにエラーハンドリングが追加されました。これは、LZWエンコーダがエラーを返すようになったため、そのエラーを適切に捕捉し、テストを失敗させるために必要です。

2.  **`TestPixelOutsidePaletteRange`**:
    *   このテストは、2色のパレットを持つGIF画像を生成し、パレット範囲外のピクセル値（例: パレットインデックスが0と1しかないのに、ピクセル値が3や255）がどのように扱われるかを検証するものです。
    *   以前は `for _, pval := range []byte{0, 1, 2, 3, 255}` というループで様々なピクセル値を試していました。
    *   `255` は `litWidth = 2` の有効範囲 `0-3` を大きく超えるため、新しいLZWエンコーダはこれを拒否します。以前は `255` が `3` にマスクされていたためテストケースとして意味がありましたが、エラーを返すようになったため、このテストケースは不要になりました。
    *   修正後は `for _, pval := range []byte{0, 1, 2, 3}` となり、`255` が削除されました。
    *   `3` は `litWidth = 2` の有効範囲内ですが、2色のパレット（インデックス0と1）に対してはパレット範囲外のインデックスとなります。したがって、このテストケースは引き続き「パレット範囲外のピクセル」の検証という目的を果たします。
    *   こちらも `w.Write(pix)` と `w.Close()` にエラーハンドリングが追加されています。

これらの変更により、Goの `image/gif` パッケージは、LZWエンコーダの堅牢性を維持しつつ、無効なGIFデータに対するテストカバレッジを適切に保つことができるようになりました。

## コアとなるコードの解説

### `TestNoPalette` の変更点

1.  **テストの再有効化**:
    *   以前のコミット `11227` によって一時的に無効化されていたコメントアウトされた `return` ステートメントと説明コメントが削除されました。これにより、このテストが再び実行されるようになります。
2.  **ピクセルデータの修正**:
    *   `pix := []byte{0, 128}` が `pix := []byte{0, 3}` に変更されました。
    *   `lzw.NewWriter` は `litWidth` を `2` で初期化しています。これは、LZWエンコーダが `0` から `(1 << 2) - 1 = 3` までのリテラルシンボルを処理できることを意味します。
    *   以前の `128` はこの範囲外であり、新しいLZWエンコーダはこれを拒否するため、テストが失敗していました。`3` はこの範囲内であり、かつパレットが存在しない状況では依然として「無効なピクセル値」として機能するため、テストの意図を維持しつつ、新しいエンコーダの挙動に適合しています。
3.  **エラーハンドリングの追加**:
    *   `w.Write(pix)` と `w.Close()` の呼び出しに `if _, err := ...; err != nil { t.Fatalf(...) }` という形式のエラーチェックが追加されました。
    *   これは、LZWエンコーダが不正な入力に対してエラーを返すようになったため、テスト内でそのエラーを捕捉し、テストを適切に失敗させるために必要です。これにより、エンコーダが期待通りにエラーを返すことを検証できるようになります。

### `TestPixelOutsidePaletteRange` の変更点

1.  **テストの再有効化**:
    *   `TestNoPalette` と同様に、一時的に無効化されていたコメントアウトと `return` ステートメントが削除されました。
2.  **テストケースの修正**:
    *   `for _, pval := range []byte{0, 1, 2, 3, 255}` が `for _, pval := range []byte{0, 1, 2, 3}` に変更されました。
    *   `255` という値は、`litWidth = 2` の有効範囲 `0-3` を大きく超えるため、新しいLZWエンコーダはこれを拒否します。以前は `255` が `3` にマスクされて処理されていたためテストケースとして意味がありましたが、エラーを返すようになったため、このテストケースは削除されました。

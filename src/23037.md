# [インデックス 23037] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）メカニズムにおいて、バックグラウンドGCが実行したスキャン作業量を追跡するための新しいクレジットシステムを導入します。これにより、ミューテーター（ユーザープログラム）がGC作業を支援する「ミューテーターアシスト」の必要性を最適化し、GCの効率とアプリケーションのレイテンシを改善することを目的としています。

## コミット

```
runtime: track background scan work credit

This tracks scan work done by background GC in a global pool. Mutator
assists will draw on this credit to avoid doing work when background
GC is staying ahead.

Unlike the other GC controller tracking variables, this will be both
written and read throughout the cycle. Hence, we can't arbitrarily
delay updates like we can for scan work and bytes marked. However, we
still want to minimize contention, so this global credit pool is
allowed some error from the "true" amount of credit. Background GC
accumulates credit locally up to a limit and only then flushes to the
global pool. Similarly, mutator assists will draw from the credit pool
in batches.

## 変更の背景

Goのガベージコレクションは、アプリケーションの実行と並行して動作するコンカレントGCを採用しています。このGCサイクル中、ヒープのスキャン（到達可能なオブジェクトの特定）は重要なフェーズです。通常、このスキャン作業はバックグラウンドのGCワーカーによって行われますが、バックグラウンドGCが十分な速度で作業を進められない場合、アプリケーションのスループットやレイテンシに悪影響を与える可能性があります。

このような状況を避けるため、GoのGCには「ミューテーターアシスト（mutator assists）」という仕組みがあります。これは、バックグラウンドGCの進捗が遅れている場合に、ユーザープログラム（ミューテーター）自身がGCのスキャン作業の一部を肩代わりすることで、GCの完了を早め、ヒープの拡大を抑制するものです。しかし、ミューテーターアシストはユーザープログラムの実行を一時的に停止させるため、アプリケーションのレイテンシを増加させる可能性があります。

このコミットの背景にあるのは、ミューテーターアシストの発生をより賢く制御することです。バックグラウンドGCが十分に先行して作業を進めている場合、ミューテーターアシストは不要であり、むしろアプリケーションのパフォーマンスを不必要に低下させる可能性があります。そこで、バックグラウンドGCがどれだけのスキャン作業を「先行して」完了しているかを正確に把握し、その「クレジット」をミューテーターアシストが利用できるようにすることで、不要なアシストを回避し、GCのオーバーヘッドを最小限に抑えることが目的とされています。

特に、このクレジットはGCサイクル全体を通して頻繁に読み書きされるため、共有状態への競合（コンテンション）を最小限に抑える設計が求められました。

## 前提知識の解説

### Goのコンカレントガベージコレクション (GC)

GoのGCは、主に以下のフェーズで構成されるコンカレント（並行）なマーク＆スイープGCです。

*   **マークフェーズ (Mark Phase)**: プログラムの実行と並行して、到達可能なオブジェクトを特定（マーク）します。このフェーズはさらに「マーク準備」「マーク」「マーク終了」に分かれます。
    *   **マーク準備 (Mark Setup)**: STW (Stop-The-World) フェーズ。GCを開始するためにミューテーターを一時停止し、GCルート（スタック、グローバル変数など）をスキャンします。
    *   **マーク (Marking)**: コンカレントフェーズ。GCワーカーがヒープをスキャンし、到達可能なオブジェクトにマークを付けます。この間もユーザープログラムは実行されます。
    *   **マーク終了 (Mark Termination)**: STWフェーズ。マークフェーズを完了し、GCワーカーが残りの作業を完了させます。
*   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不能なオブジェクト）を解放し、ヒープメモリを再利用可能にします。このフェーズもコンカレントに実行されます。

### ミューテーターアシスト (Mutator Assists)

ミューテーターアシストは、コンカレントマークフェーズ中にバックグラウンドGCの進捗が遅れている場合に発動する仕組みです。ミューテーター（ユーザープログラム）が新しいオブジェクトをアロケートしようとした際に、GCの進捗が目標に達していないと判断されると、そのアロケーションを一時的にブロックし、ミューテーター自身にGCのスキャン作業の一部を実行させます。これにより、GCの遅延を防ぎ、ヒープの過度な拡大を抑制します。しかし、ミューテーターアシストはアプリケーションの実行を中断させるため、レイテンシのスパイクを引き起こす可能性があります。

### スキャン作業 (Scan Work)

GCにおける「スキャン作業」とは、ヒープ上のオブジェクトを走査し、そこから参照されている他のオブジェクトを特定する作業を指します。これは、到達可能なオブジェクトをマークするプロセスの中核をなすものです。

### 共有状態への競合 (Contention)

複数のゴルーチン（またはCPUコア）が同じ共有メモリ領域に同時にアクセスしようとすると、競合（コンテンション）が発生します。特に、読み書きが頻繁に行われる共有変数では、ロックやアトミック操作が必要となり、これがパフォーマンスのボトルネックになることがあります。このコミットでは、`bgScanCredit`がGCサイクル全体を通して頻繁に読み書きされるため、コンテンションを最小限に抑える設計が重要視されています。

### アトミック操作 (Atomic Operations)

アトミック操作は、複数のスレッドから同時にアクセスされても、その操作全体が不可分（中断されない）であることを保証する操作です。これにより、共有データの一貫性を保ち、データ競合を防ぎます。Goの`sync/atomic`パッケージや、ランタイム内部の`xaddint64`のような関数がこれに該当します。

## 技術的詳細

このコミットは、GoのGCコントローラ (`gcControllerState`) に `bgScanCredit` という新しいフィールドを導入し、バックグラウンドGCが実行したスキャン作業量を追跡します。

### `bgScanCredit` の役割

`bgScanCredit` は、バックグラウンドGCが先行して完了したスキャン作業の「クレジット」を表します。このクレジットはグローバルなプールとして機能し、ミューテーターアシストが必要になった際に、このプールからクレジットを引き出すことで、実際のGC作業を実行せずにアシストを完了したとみなすことができます。これにより、バックグラウンドGCが順調に進んでいる場合には、ミューテーターアシストによるアプリケーションの停止を回避し、レイテンシを削減します。

### バッチ処理によるコンテンションの最小化

コミットメッセージで述べられているように、`bgScanCredit` はGCサイクル全体を通して頻繁に読み書きされます。これは、他のGC追跡変数（例: `scanWork` や `bytes marked`）とは異なり、更新を任意に遅延させることができないため、共有状態へのコンテンションが懸念されます。

この問題を解決するため、以下のバッチ処理戦略が採用されています。

1.  **バックグラウンドGCによるクレジットの蓄積**: バックグラウンドGCは、スキャン作業を完了するたびに、その作業量をローカル（`gcWork`構造体内の`scanWork`）に蓄積します。
2.  **`gcBgCreditSlack` 定数**: `gcBgCreditSlack` は、バックグラウンドGCがローカルにクレジットを蓄積できる上限値を定義します。この値に達するまで、グローバルな `bgScanCredit` は更新されません。
    *   `gcBgCreditSlack` の値が小さいほど、ミューテーターアシストはバックグラウンドスキャンのより正確な状況を把握できます。
    *   `gcBgCreditSlack` の値が大きいほど、グローバルな `bgScanCredit` への更新頻度が減り、メモリコンテンションが減少します。
    このコミットでは、`gcBgCreditSlack` は `2000` に設定されています。
3.  **グローバルプールへのフラッシュ**: ローカルのクレジットが `gcBgCreditSlack` を超えた場合、またはGCドレイン処理の最後に、蓄積されたクレジットがアトミックにグローバルな `gcController.bgScanCredit` に加算されます。この加算には `xaddint64` 関数が使用されます。
4.  **ミューテーターアシストによるクレジットの引き出し**: 同様に、ミューテーターアシストもクレジットプールからバッチでクレジットを引き出すことで、コンテンションを最小限に抑えます（このコミットではクレジットの引き出し側の実装は直接示されていませんが、そのための基盤が作られています）。

このバッチ処理アプローチにより、`bgScanCredit` の「真の」値との間にわずかな誤差が生じる可能性がありますが、その引き換えに、頻繁なアトミック操作によるパフォーマンスオーバーヘッドを大幅に削減できます。

### `xaddint64` 関数

`xaddint64` は、Goランタイム内部で使用されるアトミックな加算操作です。これは、指定されたメモリ位置の64ビット整数に値をアトミックに加算し、加算前の値を返します。これにより、複数のゴルーチンが同時に `bgScanCredit` を更新しようとしても、データ競合が発生せず、一貫性が保たれます。

    func gcDrain(gcw *gcWork, flushScanCredit int64) {
        // ...
        var lastScanFlush, nextScanFlush int64
        if flushScanCredit != -1 {
            lastScanFlush = gcw.scanWork
            nextScanFlush = lastScanFlush + flushScanCredit
        } else {
            // flushScanCredit が -1 の場合、フラッシュを無効にするために非常に大きな値を設定
            nextScanFlush = int64(^uint64(0) >> 1)
        }

        for {
            // ... (既存のgcDrainロジック)

            scanobject(b, 0, nil, gcw) // スキャン作業を実行

            // バックグラウンドスキャン作業クレジットをグローバルアカウントにフラッシュ
            // ローカルに十分な量が蓄積された場合、ミューテーターアシストがそれを利用できるようにする
            if gcw.scanWork >= nextScanFlush {
                credit := gcw.scanWork - lastScanFlush
                xaddint64(&gcController.bgScanCredit, credit) // アトミック加算
                lastScanFlush = gcw.scanWork
                nextScanFlush = lastScanFlush + flushScanCredit
            }
        }
        // gcDrainループ終了後、残りのクレジットをフラッシュ
        if flushScanCredit != -1 {
            credit := gcw.scanWork - lastScanFlush
            xaddint64(&gcController.bgScanCredit, credit)
        }
        // ...
    }
    ```

## コアとなるコードの解説

### `gcControllerState.bgScanCredit`

このフィールドは、バックグラウンドGCが完了したスキャン作業の総量を追跡します。ミューテーターアシストは、このクレジットを参照して、自身がGC作業を行う必要があるかどうかを判断します。これにより、バックグラウンドGCが先行している場合は、ミューテーターアシストを抑制し、アプリケーションのレイテンシを低減できます。

### `gcBgCreditSlack` 定数

この定数は、バックグラウンドGCがローカルに蓄積できるスキャン作業クレジットの閾値を定義します。バックグラウンドGCは、この閾値に達するまでローカルで作業量をカウントし、閾値を超えた場合にのみ、その作業量をグローバルな `gcController.bgScanCredit` にフラッシュします。これにより、グローバルな共有変数への書き込み頻度を減らし、コンテンションを緩和します。

### `gcDrain` 関数の変更

`gcDrain` 関数は、GCワーカーがオブジェクトをスキャンし、ワークバッファをドレインする主要な関数です。このコミットでは、`gcDrain` に `flushScanCredit` という新しい引数が追加されました。

*   `flushScanCredit` が `-1` でない場合（例: `gcBgCreditSlack` が渡された場合）、`gcDrain` はバックグラウンドGCワーカーとして動作し、ローカルの `gcw.scanWork` が `nextScanFlush` （`lastScanFlush + flushScanCredit`）を超えたときに、`gcController.bgScanCredit` にクレジットをアトミックに加算します。これにより、バックグラウンドGCの進捗がグローバルに反映されます。
*   `flushScanCredit` が `-1` の場合、クレジットのフラッシュは行われません。これは、ミューテーターアシストなど、クレジットを消費する側や、クレジットを生成しないGCフェーズでの `gcDrain` 呼び出しを想定しています。

`xaddint64(&gcController.bgScanCredit, credit)` は、`gcController.bgScanCredit` に `credit` の値をアトミックに加算する操作です。これにより、複数のGCワーカーが同時にクレジットをフラッシュしようとしても、安全に更新が行われます。

この変更により、GoのGCは、バックグラウンドGCの進捗状況をより細かく、かつ効率的に管理できるようになり、ミューテーターアシストの発生を最適化することで、全体的なアプリケーションパフォーマンスの向上に貢献します。

*   **マークフェーズ (Mark Phase)**: プログラムの実行と並行して、到達可能なオブジェクトを特定（マーク）します。このフェーズはさらに「マーク準備」「マーク」「マーク終了」に分かれます。
    *   **マーク準備 (Mark Setup)**: STW (Stop-The-World) フェーズ。GCを開始するためにミューテーターを一時停止し、GCルート（スタック、グローバル変数など）をスキャンします。
    *   **マーク (Marking)**: コンカレントフェーズ。GCワーカーがヒープをスキャンし、到達可能なオブジェクトにマークを付けます。この間もユーザープログラムは実行されます。
    *   **マーク終了 (Mark Termination)**: STWフェーズ。マークフェーズを完了し、GCワーカーが残りの作業を完了させます。
*   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不能なオブジェクト）を解放し、ヒープメモリを再利用可能にします。このフェーズもコンカレントに実行されます。

### ミューテーターアシスト (Mutator Assists)

ミューテーターアシストは、コンカレントマークフェーズ中にバックグラウンドGCの進捗が遅れている場合に発動する仕組みです。ミューテーター（ユーザープログラム）が新しいオブジェクトをアロケートしようとした際に、GCの進捗が目標に達していないと判断されると、そのアロケーションを一時的にブロックし、ミューテーター自身にGCのスキャン作業の一部を実行させます。これにより、GCの遅延を防ぎ、ヒープの過度な拡大を抑制します。しかし、ミューテーターアシストはアプリケーションの実行を中断させるため、レイテンシのスパイクを引き起こす可能性があります。

### スキャン作業 (Scan Work)

GCにおける「スキャン作業」とは、ヒープ上のオブジェクトを走査し、そこから参照されている他のオブジェクトを特定する作業を指します。これは、到達可能なオブジェクトをマークするプロセスの中核をなすものです。

### 共有状態への競合 (Contention)

複数のゴルーチン（またはCPUコア）が同じ共有メモリ領域に同時にアクセスしようとすると、競合（コンテンション）が発生します。特に、読み書きが頻繁に行われる共有変数では、ロックやアトミック操作が必要となり、これがパフォーマンスのボトルネックになることがあります。このコミットでは、`bgScanCredit`がGCサイクル全体を通して頻繁に読み書きされるため、コンテンションを最小限に抑える設計が重要視されています。

### アトミック操作 (Atomic Operations)

アトミック操作は、複数のスレッドから同時にアクセスされても、その操作全体が不可分（中断されない）であることを保証する操作です。これにより、共有データの一貫性を保ち、データ競合を防ぎます。Goの`sync/atomic`パッケージや、ランタイム内部の`xaddint64`のような関数がこれに該当します。

## 技術的詳細

このコミットは、GoのGCコントローラ (`gcControllerState`) に `bgScanCredit` という新しいフィールドを導入し、バックグラウンドGCが実行したスキャン作業量を追跡します。

### `bgScanCredit` の役割

`bgScanCredit` は、バックグラウンドGCが先行して完了したスキャン作業の「クレジット」を表します。このクレジットはグローバルなプールとして機能し、ミューテーターアシストが必要になった際に、このプールからクレジットを引き出すことで、実際のGC作業を実行せずにアシストを完了したとみなすことができます。これにより、バックグラウンドGCが順調に進んでいる場合には、ミューテーターアシストによるアプリケーションの停止を回避し、レイテンシを削減します。

### バッチ処理によるコンテンションの最小化

コミットメッセージで述べられているように、`bgScanCredit` はGCサイクル全体を通して頻繁に読み書きされます。これは、他のGC追跡変数（例: `scanWork` や `bytes marked`）とは異なり、更新を任意に遅延させることができないため、共有状態へのコンテンションが懸念されます。

この問題を解決するため、以下のバッチ処理戦略が採用されています。

1.  **バックグラウンドGCによるクレジットの蓄積**: バックグラウンドGCは、スキャン作業を完了するたびに、その作業量をローカル（`gcWork`構造体内の`scanWork`）に蓄積します。
2.  **`gcBgCreditSlack` 定数**: `gcBgCreditSlack` は、バックグラウンドGCがローカルにクレジットを蓄積できる上限値を定義します。この値に達するまで、グローバルな `bgScanCredit` は更新されません。
    *   `gcBgCreditSlack` の値が小さいほど、ミューテーターアシストはバックグラウンドスキャンのより正確な状況を把握できます。
    *   `gcBgCreditSlack` の値が大きいほど、グローバルな `bgScanCredit` への更新頻度が減り、メモリコンテンションが減少します。
    このコミットでは、`gcBgCreditSlack` は `2000` に設定されています。
3.  **グローバルプールへのフラッシュ**: ローカルのクレジットが `gcBgCreditSlack` を超えた場合、またはGCドレイン処理の最後に、蓄積されたクレジットがアトミックにグローバルな `gcController.bgScanCredit` に加算されます。この加算には `xaddint64` 関数が使用されます。
4.  **ミューテーターアシストによるクレジットの引き出し**: 同様に、ミューテーターアシストもクレジットプールからバッチでクレジットを引き出すことで、コンテンションを最小限に抑えます（このコミットではクレジットの引き出し側の実装は直接示されていませんが、そのための基盤が作られています）。

このバッチ処理アプローチにより、`bgScanCredit` の「真の」値との間にわずかな誤差が生じる可能性がありますが、その引き換えに、頻繁なアトミック操作によるパフォーマンスオーバーヘッドを大幅に削減できます。

### `xaddint64` 関数

`xaddint64` は、Goランタイム内部で使用されるアトミックな加算操作です。これは、指定されたメモリ位置の64ビット整数に値をアトミックに加算し、加算前の値を返します。これにより、複数のゴルーチンが同時に `bgScanCredit` を更新しようとしても、データ競合が発生せず、一貫性が保たれます。

    ```go
    func gcDrain(gcw *gcWork, flushScanCredit int64) {
        // ...
        var lastScanFlush, nextScanFlush int64
        if flushScanCredit != -1 {
            lastScanFlush = gcw.scanWork
            nextScanFlush = lastScanFlush + flushScanCredit
        } else {
            // flushScanCredit が -1 の場合、フラッシュを無効にするために非常に大きな値を設定
            nextScanFlush = int64(^uint64(0) >> 1)
        }

        for {
            // ... (既存のgcDrainロジック)

            scanobject(b, 0, nil, gcw) // スキャン作業を実行

            // バックグラウンドスキャン作業クレジットをグローバルアカウントにフラッシュ
            // ローカルに十分な量が蓄積された場合、ミューテーターアシストがそれを利用できるようにする
            if gcw.scanWork >= nextScanFlush {
                credit := gcw.scanWork - lastScanFlush
                xaddint64(&gcController.bgScanCredit, credit) // アトミック加算
                lastScanFlush = gcw.scanWork
                nextScanFlush = lastScanFlush + flushScanCredit
            }
        }
        // gcDrainループ終了後、残りのクレジットをフラッシュ
        if flushScanCredit != -1 {
            credit := gcw.scanWork - lastScanFlush
            xaddint64(&gcController.bgScanCredit, credit)
        }
        // ...
    }
    ```

## コアとなるコードの解説

### `gcControllerState.bgScanCredit`

このフィールドは、バックグラウンドGCが完了したスキャン作業の総量を追跡します。ミューテーターアシストは、このクレジットを参照して、自身がGC作業を行う必要があるかどうかを判断します。これにより、バックグラウンドGCが先行している場合は、ミューテーターアシストを抑制し、アプリケーションのレイテンシを低減できます。

### `gcBgCreditSlack` 定数

この定数は、バックグラウンドGCがローカルに蓄積できるスキャン作業クレジットの閾値を定義します。バックグラウンドGCは、この閾値に達するまでローカルで作業量をカウントし、閾値を超えた場合にのみ、その作業量をグローバルな `gcController.bgScanCredit` にフラッシュします。これにより、グローバルな共有変数への書き込み頻度を減らし、コンテンションを緩和します。

### `gcDrain` 関数の変更

`gcDrain` 関数は、GCワーカーがオブジェクトをスキャンし、ワークバッファをドレインする主要な関数です。このコミットでは、`gcDrain` に `flushScanCredit` という新しい引数が追加されました。

*   `flushScanCredit` が `-1` でない場合（例: `gcBgCreditSlack` が渡された場合）、`gcDrain` はバックグラウンドGCワーカーとして動作し、ローカルの `gcw.scanWork` が `nextScanFlush` （`lastScanFlush + flushScanCredit`）を超えたときに、`gcController.bgScanCredit` にクレジットをアトミックに加算します。これにより、バックグラウンドGCの進捗がグローバルに反映されます。
*   `flushScanCredit` が `-1` の場合、クレジットのフラッシュは行われません。これは、ミューテーターアシストなど、クレジットを消費する側や、クレジットを生成しないGCフェーズでの `gcDrain` 呼び出しを想定しています。

`xaddint64(&gcController.bgScanCredit, credit)` は、`gcController.bgScanCredit` に `credit` の値をアトミックに加算する操作です。これにより、複数のGCワーカーが同時にクレジットをフラッシュしようとしても、安全に更新が行われます。

この変更により、GoのGCは、バックグラウンドGCの進捗状況をより細かく、かつ効率的に管理できるようになり、ミューテーターアシストの発生を最適化することで、全体的なアプリケーションパフォーマンスの向上に貢献します。

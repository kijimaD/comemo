## 変更の背景

このコミットの主な背景は、Goコンパイラのバックエンド部分である `cmd/internal/obj` パッケージ内のコードの構造と保守性を改善することにあります。以前は、プログラム命令のリスト (`Plist`) を処理し、シンボル情報やコードセクションを構築するロジック (`Flushplist` 関数群) が、オブジェクトファイル全体の書き込みロジック (`objfile.go`) やリンカの初期化ロジック (`link.go`) と密接に結合していました。

このような結合は、特定の機能の変更やデバッグを行う際に、関連性の低いコードを同時に考慮する必要があるため、コードの理解を困難にし、意図しない副作用を引き起こす可能性がありました。このコミットは、`Plist` の管理とフラッシュ処理という特定の責務を独立したファイル (`plist.go`) に分離することで、各ファイルの役割を明確にし、モジュール性を高めることを目的としています。これにより、将来的な機能拡張やリファクタリングがより容易になります。

## 前提知識の解説

このコミットを理解するためには、Goコンパイラのバックエンド、特に `cmd/internal/obj` パッケージの役割と、そこで使用される主要なデータ構造について基本的な知識が必要です。

*   **Goコンパイラの構造と `cmd/internal/obj` パッケージ**:
    Goコンパイラは、ソースコードを機械語に変換する多段階のプロセスを経ます。`cmd/internal/obj` パッケージは、このプロセスのバックエンド部分を担い、主にアセンブラとリンカの中間表現を扱います。具体的には、Goのソースコードが抽象構文木 (AST) を経て、中間コード (SSA) に変換された後、最終的にターゲットアーキテクチャのアセンブリ命令に変換されます。`cmd/internal/obj` は、これらのアセンブリ命令を `Prog` という抽象的なデータ構造で表現し、それらを処理して最終的なオブジェクトファイルを生成する役割を担います。

*   **`Prog` (Program Instruction)**:
    `Prog` は、Goコンパイラのバックエンドで使用されるアセンブリ命令の抽象的な表現です。各 `Prog` 構造体は、命令の種類 (例: `ATEXT` は関数定義、`AGLOBL` はグローバル変数定義)、オペランド (命令の引数)、およびその他のメタデータを含みます。これらはリンカが最終的な実行可能ファイルを生成するために必要な情報を提供します。

*   **`Plist` (Program List)**:
    `Plist` は "Program List" の略で、`Prog` 命令の連鎖を管理するためのデータ構造です。コンパイラやアセンブラは、ソースコードから生成された `Prog` 命令を `Plist` に追加していきます。`Plist` は、特定の関数やコードブロックに関連する一連の命令をグループ化するために使用されます。`Plist` 構造体は、`LSym` (リンクシンボル)、`Firstpc` (リストの最初の `Prog` へのポインタ)、`Link` (次の `Plist` へのポインタ) などのフィールドを持ち、複数の `Plist` を連結して全体のプログラム構造を表現します。

*   **`Flushplist` の役割**:
    `Flushplist` 関数は、`Plist` に蓄積された `Prog` 命令のリストを走査し、それらを処理して最終的なオブジェクトファイルに書き込むための準備を行う重要なステップです。この処理には、以下のようなタスクが含まれます。
    *   **シンボルテーブルの構築**: `ATEXT` (関数) や `AGLOBL` (グローバル変数) などの命令から、プログラム内のシンボル情報を抽出し、リンカが参照できる形式で管理します。
    *   **型情報の処理**: `ATYPE` 命令から、変数やパラメータの型情報を抽出し、デバッグ情報やガベージコレクションのためのポインタマップの生成に利用します。
    *   **コードセクションの構築**: `Prog` 命令をターゲットアーキテクチャの機械語に変換し、実行可能ファイルのテキストセクション（コード領域）を構築します。
    *   **PCLN (Program Counter Line Number) 情報の生成**: デバッグ時にソースコードの行番号と実行アドレスをマッピングするための情報を生成します。

*   **オブジェクトファイル書き込み (Object File Writing)**:
    `Flushplist` によって処理された `Prog` 命令と生成されたメタデータは、最終的に `objfile.go` 内のロジックによって、Goのオブジェクトファイル形式でディスクに書き込まれます。このオブジェクトファイルは、リンカによって他のオブジェクトファイルやライブラリと結合され、最終的な実行可能ファイルが生成されます。

## 技術的詳細

このコミットは、`cmd/internal/obj` パッケージ内の `Plist` 関連のロジックを、`objfile.go` と `link.go` から `plist.go` という新しい専用ファイルに移動するという、純粋なコード組織のリファクタリングです。機能的な変更は一切含まれていません。

具体的には、以下の要素が移動されました。

1.  **`Plist` 構造体の定義**:
    `link.go` に定義されていた `Plist` 構造体が `plist.go` に移動されました。この構造体は、プログラム命令のリストを表現するための基本的なビルディングブロックです。

2.  **`Linknewplist` 関数の定義**:
    `link.go` に定義されていた `Linknewplist` 関数が `plist.go` に移動されました。この関数は、新しい `Plist` インスタンスを作成し、現在のリンクコンテキスト (`ctxt`) の `Plist` リストにそれを追加する役割を担います。

3.  **`Flushplist`、`FlushplistNoFree`、`flushplist` 関数の定義**:
    `objfile.go` に定義されていた `Flushplist`、`FlushplistNoFree`、および内部ヘルパー関数 `flushplist` が `plist.go` に移動されました。これらの関数は、`Plist` に蓄積された `Prog` 命令を走査し、シンボル情報の収集、型情報の処理、グローバル変数や関数テキストの処理、そして最終的な機械語への変換準備を行う中心的なロジックを含んでいます。

この分離により、`objfile.go` はオブジェクトファイルのヘッダ、セクション、シンボルテーブルなどの高レベルな構造の書き込みに特化し、`link.go` はリンカの初期化や全体的なリンク処理に集中できるようになります。一方、`plist.go` は `Prog` 命令リストのライフサイクル管理と、それらをオブジェクトファイルに変換する前の中間処理に特化します。

この変更は、Goコンパイラのバックエンドのコードベースをよりクリーンで理解しやすいものにし、将来的なメンテナンスやパフォーマンス最適化のための基盤を強化します。各ファイルが単一の明確な責務を持つ「単一責任の原則 (Single Responsibility Principle)」に沿った改善と言えます。

    ```diff
    +				flag := int(p.From3Offset())
    +				if flag&DUPOK != 0 {
    +					s.Dupok = true
    +				}
    +				if flag&NOSPLIT != 0 {
    +					s.Nosplit = true
    +				}
    +				if flag&REFLECTMETHOD != 0 {
    +					s.ReflectMethod = true
    +				}
    +				s.Type = STEXT
    +				s.Text = p
    +				etext = p
    +				curtext = s
    +				continue
    +
    +			case AFUNCDATA:
    +				// Rewrite reference to go_args_stackmap(SB) to the Go-provided declaration information.
    +				if curtext == nil { // func _() {}
    +					continue
    +				}
    +				if p.To.Sym.Name == "go_args_stackmap" {
    +					if p.From.Type != TYPE_CONST || p.From.Offset != FUNCDATA_ArgsPointerMaps {
    +						ctxt.Diag("FUNCDATA use of go_args_stackmap(SB) without FUNCDATA_ArgsPointerMaps")
    +					}
    +					p.To.Sym = Linklookup(ctxt, fmt.Sprintf("%s.args_stackmap", curtext.Name), int(curtext.Version))
    +				}
    +
    +			}
    +
    +			if curtext == nil {
    +				etext = nil
    +				continue
    +			}
    +			etext.Link = p
    +			etext = p
    +		}
    +	}
    +
    +	// Add reference to Go arguments for C or assembly functions without them.
    +	for _, s := range text {
    +		if !strings.HasPrefix(s.Name, "\"\"") {
    +			continue
    +		}
    +		found := false
    +		var p *Prog
    +		for p = s.Text; p != nil; p = p.Link {
    +			if p.As == AFUNCDATA && p.From.Type == TYPE_CONST && p.From.Offset == FUNCDATA_ArgsPointerMaps {
    +				found = true
    +				break
    +			}
    +		}
    +
    +		if !found {
    +			p = Appendp(ctxt, s.Text)
    +			p.As = AFUNCDATA
    +			p.From.Type = TYPE_CONST
    +			p.From.Offset = FUNCDATA_ArgsPointerMaps
    +			p.To.Type = TYPE_MEM
    +			p.To.Name = NAME_EXTERN
    +			p.To.Sym = Linklookup(ctxt, fmt.Sprintf("%s.args_stackmap", s.Name), int(s.Version))
    +		}
    +	}
    +
    +	// Turn functions into machine code images.
    +	for _, s := range text {
    +		mkfwd(s)
    +		linkpatch(ctxt, s)
    +		if ctxt.Flag_optimize {
    +			ctxt.Arch.Follow(ctxt, s)
    +		}
    +		ctxt.Arch.Preprocess(ctxt, s)
    +		ctxt.Arch.Assemble(ctxt, s)
    +		fieldtrack(ctxt, s)
    +		linkpcln(ctxt, s)
    +		if freeProgs {
    +			s.Text = nil
    +		}
    +	}
    +
    +	// Add to running list in ctxt.
    +	ctxt.Text = append(ctxt.Text, text...)
    +	ctxt.Plist = nil
    +	ctxt.Plast = nil
    +	ctxt.Curp = nil
    +	if freeProgs {
    +		ctxt.freeProgs()
    +	}
    +}
    ```

## コアとなるコードの解説

`plist.go` に移動された主要なコード要素とその役割は以下の通りです。

*   **`type Plist struct { ... }`**:
    この構造体は、Goコンパイラのバックエンドがアセンブリ命令をリストとして管理するために使用されます。
    *   `Name *LSym`: この `Plist` が関連付けられているシンボル（通常は関数名など）。
    *   `Firstpc *Prog`: このリストの最初のプログラム命令 (`Prog`) へのポインタ。
    *   `Recur int`: 再帰の深さを示すカウンタ（特定の最適化や解析で使用される可能性）。
    *   `Link *Plist`: 次の `Plist` へのポインタ。これにより、複数の `Plist` を連結して全体のプログラム構造を表現できます。

*   **`func Linknewplist(ctxt *Link) *Plist { ... }`**:
    この関数は、新しい `Plist` インスタンスを作成し、それを現在のリンクコンテキスト (`ctxt`) の `Plist` リストに追加します。`ctxt.Plist` はリストの先頭を指し、`ctxt.Plast` はリストの末尾を指します。これにより、新しい `Plist` がリストの最後に追加され、命令の順序が維持されます。

*   **`func Flushplist(ctxt *Link)` / `func FlushplistNoFree(ctxt *Link)` / `func flushplist(ctxt *Link, freeProgs bool)`**:
    これらの関数は、`Plist` に蓄積された `Prog` 命令を処理する中心的なロジックを含んでいます。`flushplist` が実質的な処理を行い、`Flushplist` と `FlushplistNoFree` はそのラッパーです。
    `flushplist` の内部では、以下の主要な処理が行われます。
    1.  **`Plist` の走査**: `ctxt.Plist` から始まる `Plist` のリンクリストを順に走査し、各 `Plist` 内の `Prog` 命令を処理します。
    2.  **`Prog` 命令の分類と処理**: 各 `Prog` 命令の `As` (命令の種類) に応じて、異なる処理が実行されます。
        *   `AEND`: 命令リストの終了を示す。
        *   `ATYPE`: 型情報に関連する命令。ローカル変数やパラメータの型情報を抽出し、`curtext.Autom` (現在の関数の自動変数リスト) に追加します。これはデバッグ情報やガベージコレクションのポインタマップ生成に利用されます。
        *   `AGLOBL`: グローバル変数定義に関連する命令。シンボル (`LSym`) の情報を更新し、`ctxt.Data` (データセクションのシンボルリスト) に追加します。`DUPOK`, `RODATA`, `NOPTR`, `TLSBSS` などのフラグに基づいて、シンボルの種類 (`SRODATA`, `SNOPTRBSS` など) を設定します。
        *   `ATEXT`: 関数定義に関連する命令。新しい関数シンボル (`LSym`) を作成または更新し、`text` リストに追加します。`DUPOK`, `NOSPLIT`, `REFLECTMETHOD` などのフラグを設定し、関数の最初の `Prog` を `s.Text` に、最後の `Prog` を `etext` に設定します。
        *   `AFUNCDATA`: 関数データに関連する命令。特に `go_args_stackmap` シンボルへの参照を、現在の関数の引数スタックマップ情報に書き換える処理が含まれます。これはGoのランタイムがスタックフレームを検査し、ガベージコレクションを正確に行うために必要です。
    3.  **C/アセンブリ関数へのGo引数参照の追加**: Goの関数ではないCやアセンブリ関数に対して、`FUNCDATA_ArgsPointerMaps` を持つ `AFUNCDATA` 命令が明示的に追加されていない場合、それを自動的に追加します。これにより、これらの関数もGoのランタイムによって正しく扱われるようになります。
    4.  **機械語イメージへの変換**: `mkfwd`, `linkpatch`, `ctxt.Arch.Follow`, `ctxt.Arch.Arch.Preprocess`, `ctxt.Arch.Assemble`, `fieldtrack`, `linkpcln` などの関数を呼び出し、`Prog` 命令をターゲットアーキテクチャの機械語に変換し、PCLN情報を生成します。
    5.  **リソースの解放**: `freeProgs` が `true` の場合、処理済みの `Prog` 命令リストを解放し、メモリ使用量を最適化します。

これらの関数が `plist.go` に集約されたことで、`Prog` 命令のライフサイクル管理、シンボル情報の抽出、および機械語変換の前処理という一連のロジックが、オブジェクトファイルの全体的な書き込みロジックから明確に分離されました。

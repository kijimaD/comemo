# [インデックス 23572] ファイルの概要

このコミットは、Go言語の標準ライブラリ `archive/zip` パッケージにおけるセキュリティと堅牢性の向上を目的としています。具体的には、ZIPアーカイブの「中央ディレクトリ」（Central Directory）に記載されているファイル数の宣言が、アーカイブの実際のサイズに対して非現実的に大きい場合に、エラーを検出して処理を中断するサニティチェックを追加しています。これにより、悪意のある、または破損したZIPファイルが引き起こす可能性のある、メモリ枯渇やサービス拒否（DoS）攻撃を防ぎます。

## コミット

`archive/zip` パッケージにおいて、TOC（Table of Contents、中央ディレクトリ）で宣言されているファイル数が、ZIPファイルのサイズに対して非現実的な値でないかを検証するサニティチェックを追加しました。

## 変更の背景

この変更は、Go Issue #10956 に対応するものです。このIssueでは、特別に細工されたZIPファイルが `archive/zip` パッケージによって処理される際に、過剰なメモリ割り当てが発生し、結果としてアプリケーションがクラッシュする可能性がある脆弱性が報告されました。

具体的には、ZIPファイルの「中央ディレクトリ終了レコード」（End of Central Directory Record, EOCD）には、アーカイブ内のファイル数を示すフィールド `directoryRecords` が含まれています。攻撃者はこのフィールドに非常に大きな値を設定することで、`archive/zip` リーダーがその数だけ `File` 構造体のスライス（配列）を割り当てようとすることを悪用できます。たとえ実際のファイルデータがほとんど存在しなくても、この偽のファイル数に基づいて大量のメモリが確保され、システムリソースが枯渇し、サービス拒否状態に陥る可能性がありました。

このコミットは、このような不正なZIPファイルに対する防御策として、`directoryRecords` の値が物理的に可能な範囲内にあるかを検証するサニティチェックを導入しています。

## 前提知識の解説

### ZIPファイルフォーマットの基本

ZIPファイルは、複数のファイルを圧縮して一つにまとめるための一般的なアーカイブフォーマットです。その構造は主に以下の要素で構成されます。

1.  **ローカルファイルヘッダ (Local File Header)**: 各ファイルデータの直前に配置され、ファイル名、圧縮方法、圧縮・非圧縮サイズなどの情報を含みます。
2.  **ファイルデータ (File Data)**: 実際のファイルの内容（圧縮されている場合が多い）です。
3.  **データ記述子 (Data Descriptor)**: オプションで、ファイルデータの後に配置され、CRC-32チェックサムや圧縮・非圧縮サイズなどの情報を含みます。これは、ストリーミングでZIPファイルを生成する際に、ローカルファイルヘッダにこれらの情報を事前に書き込めない場合に使用されます。
4.  **中央ディレクトリファイルヘッダ (Central Directory File Header)**: ZIPファイル内の各ファイルに対応するエントリで、ローカルファイルヘッダとほぼ同じ情報に加えて、ファイルコメント、ファイル属性、ローカルファイルヘッダへのオフセットなどの情報を含みます。ZIPファイル内のすべてのファイルの中央ディレクトリファイルヘッダは、ZIPファイルの末尾近くに連続して配置されます。
5.  **中央ディレクトリ終了レコード (End of Central Directory Record, EOCD)**: ZIPファイルの末尾に配置され、中央ディレクトリの開始位置、中央ディレクトリのサイズ、アーカイブ内のファイル数 (`directoryRecords`)、ZIPファイルコメントなどの重要なメタデータを含みます。ZIPリーダーは通常、このEOCDレコードを最初に探し、そこから中央ディレクトリを読み取り、アーカイブ全体の構造を把握します。

### `archive/zip` パッケージの動作

Goの `archive/zip` パッケージは、これらのZIPファイルフォーマットの仕様に基づいてファイルの読み書きを行います。特に、`zip.NewReader` 関数は、`io.ReaderAt` インターフェースとZIPファイルのサイズを受け取り、ZIPアーカイブを解析して `zip.Reader` 構造体を返します。この `zip.Reader` 構造体には、アーカイブ内の各ファイルを表す `zip.File` のスライスが含まれます。

`zip.NewReader` の内部では、まずZIPファイルの末尾からEOCDレコードを探し、そこから中央ディレクトリの情報を読み取ります。この際、EOCDレコード内の `directoryRecords` フィールド（アーカイブ内のファイル数）を読み取り、その数に基づいて `zip.File` のスライスを事前に割り当てようとします。

### 脆弱性のメカニズム

従来の `archive/zip` パッケージでは、`directoryRecords` の値が非常に大きい場合でも、その値に基づいてメモリを割り当てようとしていました。例えば、1GBのZIPファイルに対して `directoryRecords` が数十億と宣言された場合、各 `zip.File` 構造体は数十バイト程度ですが、それが数十億個となると、数GBから数十GBといった膨大なメモリが要求されることになります。これにより、システムがメモリ不足に陥り、アプリケーションがクラッシュする可能性がありました。

## 技術的詳細

このコミットで導入されたサニティチェックは、`src/archive/zip/reader.go` の `(*Reader).init` メソッド内に追加されています。このメソッドは、`zip.NewReader` から呼び出され、ZIPリーダーの初期化処理を行います。

追加されたチェックは以下の通りです。

```go
if end.directoryRecords > uint64(size)/fileHeaderLen {
    return fmt.Errorf("archive/zip: TOC declares impossible %d files in %d byte zip", end.directoryRecords, size)
}
```

ここで、
*   `end.directoryRecords`: EOCDレコードから読み取られた、中央ディレクトリに記載されているファイル数です。
*   `size`: ZIPファイルの全体のバイトサイズです。
*   `fileHeaderLen`: 中央ディレクトリ内の各ファイルエントリ（`Central Directory File Header`）の最小長を概算した定数です。この定数は、ZIPファイルフォーマットの仕様に基づいて、各ファイルエントリが占める最小限のバイト数を表します。

この条件式 `end.directoryRecords > uint64(size)/fileHeaderLen` は、次のような論理に基づいています。

1.  ZIPファイル内の各ファイルは、中央ディレクトリ内に少なくとも `fileHeaderLen` バイトの情報を持ちます。
2.  したがって、`directoryRecords` で宣言されたファイル数に `fileHeaderLen` を掛けた値は、中央ディレクトリが占める最小限のサイズを表します。
3.  この最小限の中央ディレクトリサイズは、ZIPファイル全体のサイズ `size` を超えることは物理的に不可能です。
4.  `uint64(size) / fileHeaderLen` は、ZIPファイル全体のサイズ `size` から逆算して、中央ディレクトリに格納できるファイル数の最大値を概算したものです。

もし `end.directoryRecords` がこの概算された最大値を超えている場合、それはZIPファイルが不正に細工されているか、破損していることを意味します。この場合、`fmt.Errorf` を使用してエラーを返し、それ以上の処理を中断します。これにより、不正なファイル数に基づいて大量のメモリが割り当てられることを防ぎます。

また、テストファイル `src/archive/zip/reader_test.go` では、`TestIssue10957` 関数が `t.Fatal(err)` を使用するように変更され、エラー発生時のテストの終了方法がより標準的なGoのテストプラクティスに準拠するようになりました。さらに、`TestIssue10956` という新しいテストケースが追加され、意図的に不正な `directoryRecords` を持つZIPデータを作成し、期待されるエラーが返されることを検証しています。

## コアとなるコードの解説

### `src/archive/zip/reader.go` の変更

*   **`import "fmt"` の追加**: エラーメッセージをフォーマットするために `fmt` パッケージがインポートされました。
*   **サニティチェックの追加**:
    `if end.directoryRecords > uint64(size)/fileHeaderLen { ... }` の行が追加されました。
    *   `end.directoryRecords` は、ZIPファイルの中央ディレクトリ終了レコードから読み取られた、アーカイブ内のファイル数です。
    *   `size` は、ZIPファイル全体のバイトサイズです。
    *   `fileHeaderLen` は、中央ディレクトリ内の各ファイルエントリが占める最小限のバイト数（定数）です。
    *   この条件式は、「もし宣言されたファイル数 `end.directoryRecords` が、ZIPファイル全体のサイズ `size` を、各ファイルエッントリの最小長 `fileHeaderLen` で割った値（つまり、物理的に格納可能な最大ファイル数）よりも大きい場合」をチェックしています。
    *   この条件が真の場合、`fmt.Errorf` を使って「TOCが不可能なファイル数を宣言している」というエラーメッセージを生成し、それを返して処理を中断します。これにより、不正なZIPファイルによるメモリ枯渇を防ぎます。

### `src/archive/zip/reader_test.go` の変更

*   **`TestIssue10957` の修正**:
    *   以前は `NewReader` がエラーを返した場合に `panic("non nil z")` を呼び出す可能性がありましたが、これはGoのテストにおける一般的なエラー処理ではありません。
    *   変更後は `t.Fatal(err)` を使用しています。これは、テスト中にエラーが発生した場合にテストを即座に失敗させ、エラーメッセージを出力する標準的な方法です。これにより、テストの堅牢性と可読性が向上します。
*   **`TestIssue10956` の追加**:
    *   この新しいテスト関数は、このコミットで修正された脆弱性を具体的に検証するために追加されました。
    *   `data` 変数には、意図的に不正なEOCDレコードを持つ短いバイト列が定義されています。このデータは、`directoryRecords` フィールドに非常に大きな値（例: `3472328296227680304`）を宣言するように細工されていますが、実際のZIPファイルのサイズはわずか57バイトです。
    *   `NewReader` を呼び出し、返されたエラーが `nil` でないこと、そしてエラーメッセージが期待される文字列（`"TOC declares impossible ... files in ... byte zip"`）を含んでいることを検証しています。これにより、サニティチェックが正しく機能していることを確認します。

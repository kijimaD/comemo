# [インデックス 25252] ファイルの概要

このコミットは、Go言語の `net/http` パッケージにおいて、`http.Serve` が `net.Conn` の `RemoteAddr()` メソッドのブロッキングによってハングアップする可能性があった問題を修正します。具体的には、`RemoteAddr()` の呼び出しをメインのAccepting goroutineから、接続ごとのgoroutineに移動させることで、この問題を解決しています。これにより、PROXYプロトコルなどの、`RemoteAddr()` がブロッキング操作を伴う可能性のあるカスタム `net.Conn` 実装を使用した場合でも、HTTPサーバーが正常に機能するようになります。

## 変更の背景

この変更の背景には、Goの `net/http` パッケージが、カスタムの `net.Conn` 実装、特にPROXYプロトコルを扱うものと組み合わせて使用された際に発生する潜在的なデッドロック（ハングアップ）の問題がありました。

従来の `http.Serve` の実装では、新しいTCP接続を受け入れた直後に、その接続の `RemoteAddr()` メソッドを呼び出してリモートアドレスを取得していました。この `RemoteAddr()` の呼び出しは、接続を受け入れるメインのgoroutine（Accepting goroutine）内で実行されていました。

しかし、PROXYプロトコルなどの特定のプロトコルを実装するライブラリでは、`net.Conn` をラップし、その `RemoteAddr()` メソッドが実際にソケットからデータを読み取ってクライアントの真のアドレスを解析するまでブロックする（待機する）ように設計されている場合があります。これは、PROXYプロトコルがTCP接続の開始時に特別なヘッダーを送信し、そのヘッダーを解析することで真のクライアントIPアドレスを取得するためです。

このようなブロッキング `RemoteAddr()` がメインのAccepting goroutineで呼び出されると、その呼び出しが完了するまで、サーバーは新しい接続を受け入れることができなくなります。結果として、サーバーは新しいリクエストを処理できなくなり、ハングアップしたように見えてしまいます。これは、特に高負荷な環境や、PROXYプロトコルを使用するロードバランサー（HAProxyやAmazon ELBなど）の背後でGoアプリケーションを運用する場合に深刻な問題となります。

このコミットは、この問題を解決し、`net/http` サーバーがより堅牢に、そしてPROXYプロトコルなどのカスタム `net.Conn` 実装と互換性を持つようにするために導入されました。

## 前提知識の解説

### `net/http` パッケージの `http.Serve` の動作

Goの `net/http` パッケージは、HTTPサーバーを構築するための基本的な機能を提供します。`http.Serve` 関数は、`net.Listener` から新しい接続を受け入れ、それぞれの接続に対して新しいgoroutineを起動してHTTPリクエストを処理します。

典型的な `http.Serve` の内部フローは以下のようになります。
1.  `net.Listener.Accept()` を呼び出して新しいTCP接続を待機します。
2.  新しい接続 (`net.Conn`) が確立されると、その接続を処理するための新しいgoroutineを起動します。
3.  新しいgoroutine内で、HTTPリクエストの読み取り、ハンドラーの実行、レスポンスの書き込みなどが行われます。

重要なのは、`Accept()` メソッド自体はブロッキングですが、新しい接続が確立された後の処理は通常、接続ごとのgoroutineに委譲されるという点です。これにより、メインのAccepting goroutineはすぐに次の接続の待機に戻ることができ、サーバーは複数の同時接続を効率的に処理できます。

### `net.Conn` インターフェースと `RemoteAddr()` メソッド

`net.Conn` は、Goのネットワークプログラミングにおける基本的なインターフェースです。TCP接続やUDP接続など、様々な種類のネットワーク接続を抽象化します。このインターフェースには、データの読み書き、接続のクローズ、ローカルアドレスとリモートアドレスの取得などのメソッドが含まれています。

`RemoteAddr()` メソッドは、`net.Conn` インターフェースの一部であり、接続のリモートエンドポイントのネットワークアドレス（`net.Addr` インターフェースを実装する型）を返します。通常、このメソッドは接続が確立された時点で利用可能な情報を返すため、ブロッキング操作を伴いません。しかし、カスタム実装ではこの限りではありません。

### PROXY プロトコルとその目的

PROXYプロトコルは、HAProxyやAmazon ELBなどのプロキシサーバーが、背後にあるアプリケーションサーバーにクライアントの実際の接続情報（IPアドレスやポート番号など）を伝えるためのプロトコルです。

通常のTCP接続では、プロキシサーバーがクライアントからの接続を受け入れ、その後、プロキシサーバーがアプリケーションサーバーへの新しい接続を確立します。この場合、アプリケーションサーバーから見たリモートアドレスはプロキシサーバーのアドレスになってしまい、クライアントの真のアドレスを直接知ることができません。

PROXYプロトコルを使用すると、プロキシサーバーはアプリケーションサーバーへのTCP接続が確立された直後に、特別なテキスト行（PROXYヘッダー）を送信します。このヘッダーには、クライアントの実際のIPアドレス、ポート、プロキシサーバーのIPアドレス、ポートなどの情報が含まれています。アプリケーションサーバーは、このヘッダーを読み取って解析することで、クライアントの真のアドレスを知ることができます。

Goでは、`net.Conn` をラップしてPROXYプロトコルヘッダーを解析し、`RemoteAddr()` メソッドが解析されたクライアントのアドレスを返すようにするライブラリ（例: `armon/go-proxyproto`）が存在します。これらのライブラリでは、`RemoteAddr()` がヘッダーの読み取りと解析のためにブロッキング操作を行う可能性があります。

### Go の goroutine とブロッキング操作

Goのgoroutineは、軽量な並行実行単位です。Goランタイムは、OSのスレッド上で多数のgoroutineを多重化して実行します。これにより、開発者は複雑なスレッド管理を意識することなく、並行処理を記述できます。

ブロッキング操作（例: ネットワークI/O、ファイルI/O、チャネルからの読み取り/書き込み）は、その操作が完了するまでgoroutineの実行を一時停止させます。Goランタイムは、ブロッキング中のgoroutineをOSスレッドから外し、他の実行可能なgoroutineをそのスレッドで実行することで、OSスレッドの効率的な利用を維持します。

しかし、もし重要な処理（例: 新しい接続のAccept）を行うgoroutineがブロッキング操作によって長時間停止すると、システム全体のパフォーマンスに悪影響を及ぼす可能性があります。このコミットで修正された問題は、まさにこのシナリオに該当します。メインのAccepting goroutineがブロッキング `RemoteAddr()` 呼び出しによって停止し、結果として新しい接続の受け入れがブロックされていました。

## 技術的詳細

このコミットの技術的な核心は、`net/http` サーバーが新しい接続を受け入れた際に、その接続のリモートアドレス (`RemoteAddr()`) を取得するタイミングを変更した点にあります。

変更前は、`http.Server` の `newConn` メソッド内で、新しい `net.Conn` が作成された直後に `c.remoteAddr = rwc.RemoteAddr().String()` が呼び出されていました。この `newConn` メソッドは、`http.Serve` のメインのAccepting goroutineから呼び出されます。

問題は、カスタムの `net.Conn` 実装（特にPROXYプロトコルを処理するもの）が、`RemoteAddr()` メソッド内でソケットからの読み取りを伴うブロッキング操作を行う場合です。例えば、PROXYプロトコルを実装する `net.Conn` ラッパーは、`RemoteAddr()` が呼び出されたときに、まず接続の先頭からPROXYヘッダーを読み取ろうとします。この読み取り操作は、ヘッダーが完全に受信されるまでブロックする可能性があります。

もしこのブロッキング `RemoteAddr()` 呼び出しがメインのAccepting goroutineで発生すると、そのgoroutineはPROXYヘッダーの受信が完了するまで停止します。その間、`http.Serve` は `net.Listener.Accept()` に戻ることができず、結果として他の新しいクライアント接続を受け入れることができなくなります。これは、サーバーが応答しなくなる「ハングアップ」状態を引き起こします。

このコミットでは、`c.remoteAddr = c.rwc.RemoteAddr().String()` の行を `newConn` メソッドから `serve` メソッドの冒頭に移動させました。`serve` メソッドは、`http.Serve` が新しい接続を受け入れた後に、その接続を処理するために**新しく起動される接続ごとのgoroutine**内で実行されます。

この変更により、`RemoteAddr()` の呼び出しがメインのAccepting goroutineではなく、個々の接続を処理するgoroutine内で実行されるようになります。したがって、たとえ `RemoteAddr()` がブロッキング操作を伴ったとしても、それはその特定の接続を処理するgoroutineのみをブロックし、メインのAccepting goroutineは引き続き新しい接続を迅速に受け入れることができます。これにより、サーバー全体の応答性が維持され、ハングアップの問題が解消されます。

この修正は、Goの並行処理モデルを適切に活用し、ブロッキングI/O操作がシステム全体のボトルネックにならないようにするための典型的なアプローチを示しています。

## コアとなるコードの解説

### `src/net/http/server.go` の変更点の解説

*   **`newConn` メソッドからの削除**:
    ```diff
    -	c.remoteAddr = rwc.RemoteAddr().String()
    ```
    `newConn` メソッドは、`http.Server` の `Serve` メソッド内で、新しいTCP接続が `net.Listener.Accept()` によって受け入れられた直後に呼び出されます。このメソッドは、接続を処理するための `conn` オブジェクトを初期化する役割を担います。以前はここで `RemoteAddr()` が呼び出されていましたが、このメソッドはメインのAccepting goroutineで実行されるため、ブロッキング `RemoteAddr()` が問題を引き起こしていました。この行を削除することで、メインのAccepting goroutineでのブロッキングを回避します。

*   **`serve` メソッドへの追加**:
    ```diff
    +func (c *conn) serve() {
    +	c.remoteAddr = c.rwc.RemoteAddr().String()
    ```
    `serve` メソッドは、`newConn` によって初期化された `conn` オブジェクトを受け取り、その接続に対するHTTPリクエストの処理を開始するために**新しいgoroutineで起動されます**。`RemoteAddr()` の呼び出しをこの `serve` メソッドの冒頭に移動させることで、`RemoteAddr()` がブロッキング操作を行ったとしても、それはこの個別の接続を処理するgoroutineのみをブロックします。メインのAccepting goroutineは影響を受けず、引き続き新しい接続を受け入れることができます。これにより、サーバーの応答性が維持され、ハングアップが防止されます。

### `src/net/http/serve_test.go` の新しいテストの解説

`TestServerAllowsBlockingRemoteAddr` テストは、この修正の有効性を検証するための重要なテストです。

1.  **カスタム `net.Listener` と `net.Conn` の実装**:
    *   `blockingRemoteAddrListener`: `net.Listener` インターフェースを実装し、`Accept()` メソッドが `blockingRemoteAddrConn` のインスタンスを返します。このカスタムリスナーは、受け入れた接続をチャネル `conns` に送信します。
    *   `blockingRemoteAddrConn`: `net.Conn` インターフェースを実装し、特に `RemoteAddr()` メソッドが `c.addrs` チャネルからの値を受信するまでブロックするように設計されています。これにより、`RemoteAddr()` が意図的にブロッキングする状況をシミュレートします。

2.  **`httptest.NewUnstartedServer` の利用**:
    テストサーバーは `httptest.NewUnstartedServer` を使用して作成され、そのデフォルトのリスナーがカスタムの `blockingRemoteAddrListener` に置き換えられます。これにより、テストサーバーはカスタムのブロッキング `RemoteAddr()` の動作を模倣するようになります。

3.  **同時リクエストの実行**:
    テストは、2つのHTTPリクエストをほぼ同時に開始します。
    *   `fetch` 関数は、HTTPリクエストを実行し、レスポンスボディをチャネルに送信します。
    *   最初の `go fetch(response1c)` でリクエスト1を開始し、`conn1 := <-conns` でその接続がサーバーによって受け入れられたことを確認します。この時点で、`conn1.RemoteAddr()` はブロックされています。
    *   次に、2番目の `go fetch(response2c)` でリクエスト2を開始します。

4.  **ブロッキングの検証**:
    *   `select` ステートメントを使用して、2番目の接続 (`conn2`) がタイムアウトせずに `conns` チャネルから受け入れられることを確認します。もし修正がなければ、リクエスト1の `RemoteAddr()` がブロックされているため、リクエスト2は受け入れられず、この `select` はタイムアウトしてテストが失敗するはずです。
    *   `conn2.(*blockingRemoteAddrConn).addrs <- ...` でリクエスト2の `RemoteAddr()` のブロッキングを解除し、レスポンスが正しく返されることを確認します。
    *   同様に、`conn1.(*blockingRemoteAddrConn).addrs <- ...` でリクエスト1の `RemoteAddr()` のブロッキングを解除し、レスポンスが正しく返されることを確認します。

このテストは、`RemoteAddr()` がブロッキングしても、`http.Server` が新しい接続を受け入れる能力を失わないことを明確に示しており、このコミットの修正が意図通りに機能していることを保証します。

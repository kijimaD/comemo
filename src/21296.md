# [インデックス 21296] ファイルの概要

## コミット

このコミットは、Go言語のリンカである`liblink`が、レジスタオフセット定数（`$offset(REG)`形式のアドレス指定）が大きすぎる場合に、その値をサイレントに32ビットに切り詰めてしまう問題を修正するものです。具体的には、64ビットのオフセットが指定された際に、誤ったアセンブリコードを生成するのではなく、エラーを発生させるように変更されました。これにより、リンカの挙動がより堅牢になり、開発者が意図しないコード生成を防ぐことができます。

## GitHub上でのコミットページへのリンク

[https://github.com/golang/go/commit/9b1b0a46dd3c9704a49a5ba1950212c6fff7917d](https://github.com/golang/go/commit/9b1b0a46dd3c9704a49a5ba1950212c6fff7917d)

## 元コミット内容

```
liblink: fail for too-large register offset constants

Previously, liblink would silently truncate register offset constants
to 32 bits. For example,

    MOVD $0x200000004(R2),R3

would assemble to

    addis   r31,r2,0
    addi    r3,r31,4

To fix this, limit C_LACON to 32 bit (signed) offsets and introduce a
new C_DACON operand type for larger register offsets. We don't
implement this currently, but at least liblink will now give an error
if it encounters an address like this.

Change-Id: I8e87def8cc4cc5b75498b0fb543ac7666cf2964e
Reviewed-on: https://go-review.googlesource.com/1758
Reviewed-by: Minux Ma <minux@golang.org>
```

## 変更の背景

Go言語のリンカ`liblink`は、アセンブリコードを生成する際に、レジスタに対するオフセット値を処理します。このオフセット値が32ビットの範囲を超える場合、リンカは警告なしに上位ビットを切り捨て、結果として誤ったメモリアドレスを指すコードを生成してしまうという問題がありました。

具体的には、PowerPCアーキテクチャのような一部のCPUでは、命令が直接扱える即値の範囲が限られています。そのため、大きな定数やアドレスを扱う際には、複数の命令を組み合わせて目的の値をレジスタにロードしたり、アドレスを計算したりする必要があります。PowerPCの場合、`addis`（Add Immediate Shifted）と`addi`（Add Immediate）命令を組み合わせて32ビットのオフセットを表現するのが一般的です。しかし、このコミットが修正しようとしているのは、オフセットが32ビットを超えて64ビットになるようなケースです。

元の`liblink`の実装では、`MOVD $0x200000004(R2),R3`のような64ビットオフセットを含む命令が与えられた場合、`0x200000004`というオフセットがサイレントに32ビットに切り詰められ、`0x4`として扱われていました。これにより、`addis r31,r2,0`（R2の値をR31にコピー）と`addi r3,r31,4`（R31に4を加算してR3に格納）という誤ったアセンブリコードが生成されていました。これは、プログラムが意図しないメモリアドレスにアクセスする可能性があり、深刻なバグにつながる危険性がありました。

この問題を解決するため、リンカが大きなオフセットを検出した際に、サイレントに切り捨てるのではなく、明示的にエラーを報告するように変更する必要がありました。これにより、開発者はコンパイル時に問題を認識し、適切な対処を行うことができるようになります。

## 前提知識の解説

### 1. Go言語のツールチェインと`liblink`

Go言語のビルドプロセスは、コンパイラ（`gc`など）、アセンブラ（`go tool asm`）、リンカ（`go tool link`、内部で`liblink`を使用）など、複数のツールで構成されています。
`liblink`は、Goのコンパイラが生成したオブジェクトファイル（`.o`ファイル）を結合し、実行可能なバイナリを生成する役割を担っています。この過程で、シンボル解決、アドレスの再配置、外部ライブラリとのリンクなどが行われます。本コミットは、このリンカがアセンブリ命令内のオフセット値をどのように解釈し、処理するかに焦点を当てています。

### 2. アセンブリ言語とレジスタオフセット定数

アセンブリ言語は、CPUが直接実行できる機械語に非常に近い低レベルのプログラミング言語です。レジスタはCPU内部の高速な記憶領域であり、データやアドレスを一時的に保持するために使用されます。
「レジスタオフセット定数」とは、`$offset(REG)`のように記述されるアドレス指定モードの一種です。これは、「`REG`レジスタが指すアドレスから`offset`バイトだけ離れたメモリ位置」を意味します。例えば、`$8(R1)`は、R1レジスタの値に8を加算したアドレスを指します。

### 3. PowerPCアーキテクチャと命令セット

PowerPCは、IBM、Apple、Motorolaが共同開発したRISC（Reduced Instruction Set Computer）アーキテクチャです。Go言語は、様々なアーキテクチャをサポートしており、PowerPCもその一つです。
PowerPCの命令セットには、即値（命令に直接埋め込まれる定数）のサイズに制限があります。例えば、多くのロード/ストア命令や算術命令は、16ビットの即値しか扱えません。そのため、32ビットや64ビットといった大きな定数を扱う場合には、複数の命令を組み合わせて目的の値を生成する必要があります。

*   **`addis` (Add Immediate Shifted):**
    `addis RT, RA, SIMM`
    `RT = RA + (SIMM << 16)`
    この命令は、`SIMM`（符号付き即値）を16ビット左シフト（つまり`SIMM * 65536`）し、その結果を`RA`レジスタの値に加算して`RT`レジスタに格納します。これにより、32ビットの上位16ビットを効率的に設定できます。

*   **`addi` (Add Immediate):**
    `addi RT, RA, SIMM`
    `RT = RA + SIMM`
    この命令は、`SIMM`（符号付き即値）を`RA`レジスタの値に加算して`RT`レジスタに格納します。`SIMM`は通常16ビットの範囲です。

これらの命令を組み合わせることで、例えば32ビットのオフセット`0x12345678`は、以下のように表現できます。
```assembly
addis R_TEMP, R_BASE, 0x1234  // R_TEMP = R_BASE + (0x1234 << 16)
addi  R_FINAL, R_TEMP, 0x5678 // R_FINAL = R_TEMP + 0x5678
```
これにより、`R_FINAL`には`R_BASE + 0x12345678`が計算されます。

### 4. オペランドタイプ（`C_LACON`, `C_DACON`など）

Goのリンカ内部では、アセンブリ命令のオペランド（引数）の種類を分類するために、様々な「クラス」または「タイプ」が定義されています。これらは、リンカが命令を正しく解釈し、適切な機械語に変換するために使用されます。

*   **`C_SACON` (Small Address Constant):** 小さいオフセット定数（例: `n <= int16`、つまり-32768から32767の範囲）を持つ`$n(REG)`形式のアドレス。
*   **`C_LACON` (Large Address Constant):** 比較的大きいオフセット定数（例: `int16 < n <= int32`、つまり32ビット符号付き整数の範囲）を持つ`$n(REG)`形式のアドレス。このコミット以前は、これより大きなオフセットも`C_LACON`として扱われ、切り捨てられていました。
*   **`C_DACON` (Double/Huge Address Constant):** 非常に大きいオフセット定数（例: `int32 < n`、つまり32ビットを超えるオフセット）を持つ`$n(REG)`形式のアドレス。このコミットで新しく導入されました。

これらのオペランドタイプは、リンカがオフセットのサイズに応じて異なる処理パスを選択するために重要です。

## 技術的詳細

このコミットの技術的な核心は、`liblink`がレジスタオフセット定数を分類するロジックの変更と、それに伴うアセンブリコード生成の挙動の修正にあります。

### 1. オペランドタイプの再定義と追加

`src/cmd/9l/9.out.h`ファイルでは、リンカが使用するオペランドタイプの列挙型が定義されています。このコミットでは、以下の変更が行われました。

*   `C_UCON`のコメントが「low 16 bits 0」から「32 bit signed, low 16 bits 0」に変更され、32ビット符号付き整数であることを明確にしました。
*   `C_SACON`のコメントが「$n(REG) where n is small」から「$n(REG) where n <= int16」に変更され、オフセットが16ビット符号付き整数の範囲であることを明確にしました。
*   `C_LACON`のコメントが「$n(REG) where n is large」から「$n(REG) where int16 < n <= int32」に変更され、オフセットが16ビットより大きく32ビット符号付き整数の範囲であることを明確にしました。
*   **`C_DACON`という新しいオペランドタイプが追加されました。** これは「$n(REG) where int32 < n」と定義され、オフセットが32ビット符号付き整数を超える場合に適用されます。

この変更により、リンカはオフセットのサイズに応じて、より厳密な分類を行うことができるようになりました。

### 2. `aclass`関数のロジック変更

`src/liblink/asm9.c`ファイル内の`aclass`関数は、与えられたアドレス（`Addr`構造体）のオペランドタイプを決定する役割を担っています。この関数は、`ctxt->instoffset`（現在の命令のオフセット値）の大きさに応じて、適切な`C_`定数を返します。

変更前は、`ctxt->instoffset`が`BIG`（おそらく32ビットの最大値に近い定数）の範囲内であれば`C_SACON`を返し、それ以外は無条件に`C_LACON`を返していました。この「それ以外」のケースに、32ビットを超えるオフセットが含まれており、これらが誤って`C_LACON`として扱われていました。

変更後、`aclass`関数は以下のように修正されました。
```c
			if(a->reg != NREG) {
				if(-BIG <= ctxt->instoffset && ctxt->instoffset <= BIG)
					return C_SACON;
				if(isint32(ctxt->instoffset)) // 新しいチェック
					return C_LACON;
				return C_DACON; // 新しい戻り値
			}
```
ここで、`isint32(ctxt->instoffset)`という新しいチェックが導入されました。この関数は、`ctxt->instoffset`が32ビット符号付き整数の範囲内にあるかどうかを判定します。
*   オフセットが`BIG`の範囲内であれば、引き続き`C_SACON`を返します。
*   オフセットが`BIG`より大きいが、`isint32`が真（つまり32ビット符号付き整数の範囲内）であれば、`C_LACON`を返します。
*   **それ以外の場合（つまり、オフセットが32ビット符号付き整数の範囲を超える場合）は、新しく導入された`C_DACON`を返します。**

この変更により、リンカは32ビットを超えるオフセットを正確に識別し、`C_DACON`として分類できるようになりました。コミットメッセージにあるように、現時点では`C_DACON`に対する具体的なアセンブリコード生成ロジックは実装されていませんが、これによりリンカは少なくともエラーを報告するようになります。

### 3. `asmout`関数内のオフセット処理の変更

`src/liblink/asm9.c`の`asmout`関数は、アセンブリ命令を機械語に変換する主要な部分です。この関数内で、大きなオフセットを扱うためのPowerPC固有のロジックが変更されました。

変更前は、`v & 0x8000L`や`v += 0x10000L`といったビット操作が含まれていました。これは、おそらくPowerPCの`addis`命令が上位16ビットを符号拡張して扱うことに関連する、古いまたは不正確なオフセット調整ロジックだったと考えられます。

変更後、これらのビット操作は削除され、`v>>16`の代わりに`high16adjusted(v)`という関数が使用されるようになりました。
```c
-	if(v & 0x8000L)
-		v += 0x10000L;
 	r = p->from.reg;
 	if(r == NREG)
 		r = o->param;
-	o1 = AOP_IRR(OP_ADDIS, REGTMP, r, v>>16);
+	o1 = AOP_IRR(OP_ADDIS, REGTMP, r, high16adjusted(v));
 	o2 = AOP_IRR(OP_ADDI, p->to.reg, REGTMP, v);
```
`high16adjusted(v)`関数は、おそらくPowerPCの`addis`命令が期待する形式で、オフセット`v`の上位16ビットを正確に計算するためのヘルパー関数です。この変更は、リンカがPowerPCの大きなオフセットを扱う際の内部的な正確性を向上させることを目的としています。これにより、32ビットオフセットの生成がより堅牢になります。

### まとめ

このコミットは、GoリンカがPowerPCアーキテクチャで大きなレジスタオフセット定数を扱う際の、サイレントな切り捨てという危険な挙動を修正しました。新しいオペランドタイプ`C_DACON`の導入と、`aclass`関数におけるオフセット分類ロジックの厳格化により、リンカは32ビットを超えるオフセットを正確に識別し、エラーとして報告するようになりました。これにより、開発者はコンパイル時に問題を早期に発見し、デバッグの労力を削減できるようになります。また、`asmout`関数内のオフセット処理の改善は、既存の32ビットオフセットの生成ロジックの正確性を高めるものです。

## コアとなるコードの解説

### `src/cmd/9l/9.out.h`の変更

このファイルは、Goリンカが内部的に使用する定数やデータ構造の定義を含んでいます。変更点では、アセンブリ命令のオペランドの種類を分類するための`enum`が修正されました。

*   `C_UCON`, `C_SACON`, `C_LACON`のコメントが更新され、それぞれのオペランドタイプがカバーするオフセットの範囲がより明確に定義されました。特に`C_LACON`は、以前は「大きい」という曖昧な表現でしたが、「`int16`より大きく`int32`以下の範囲」と具体化されました。
*   最も重要な変更は、`C_DACON`という新しい列挙値が追加されたことです。これは「`int32`より大きいオフセット」を扱うためのもので、これによりリンカは32ビットを超えるオフセットを明確に区別できるようになりました。

これらの変更は、リンカがオフセット値をより厳密に分類し、適切な処理パスを選択するための基盤となります。

### `src/liblink/asm9.c`の変更

このファイルは、Goリンカの主要なロジックを含んでいます。

#### `aclass`関数の変更

`aclass`関数は、与えられたアドレスの「クラス」（オペランドタイプ）を決定します。

*   変更前は、レジスタオフセットが`BIG`（おそらく32ビットの最大値）の範囲内であれば`C_SACON`を返し、それ以外は無条件に`C_LACON`を返していました。この「それ以外」には、32ビットを超えるオフセットも含まれており、これらが誤って`C_LACON`として扱われ、サイレントに切り捨てられる原因となっていました。
*   変更後、`if(isint32(ctxt->instoffset))`という条件が追加されました。これは、`ctxt->instoffset`が32ビット符号付き整数の範囲内にあるかどうかをチェックします。
    *   もし32ビット符号付き整数の範囲内であれば、`C_LACON`を返します。
    *   そうでなければ（つまり、オフセットが32ビットを超える場合）、新しく追加された`C_DACON`を返します。
この変更により、リンカは32ビットを超えるオフセットを正確に識別し、`C_DACON`として分類できるようになりました。これにより、リンカはこのようなオフセットに対してエラーを報告するか、将来的に適切な64ビットオフセット処理を実装するための準備が整いました。

#### `asmout`関数内のオフセット処理の変更

`asmout`関数は、アセンブリ命令を機械語に変換する際に、特にPowerPCアーキテクチャにおける大きなオフセットの処理を担当します。

*   変更前には、`if(v & 0x8000L) v += 0x10000L;`という行がありました。これは、PowerPCの`addis`命令が上位16ビットを符号拡張して扱うことに関連する、古いまたは不正確なオフセット調整ロジックだったと考えられます。このロジックは、64ビットオフセットを正しく扱えない原因の一つでした。
*   この行が削除され、`o1 = AOP_IRR(OP_ADDIS, REGTMP, r, v>>16);`が`o1 = AOP_IRR(OP_ADDIS, REGTMP, r, high16adjusted(v));`に置き換えられました。
    *   `v>>16`は、オフセット`v`の上位16ビットを単純に取得するものです。
    *   `high16adjusted(v)`は、おそらくPowerPCの`addis`命令が期待する形式で、オフセット`v`の上位16ビットを正確に計算するための新しいヘルパー関数です。この関数は、符号拡張のセマンティクスを正しく処理し、32ビットオフセットを正確に生成するために導入されたと考えられます。

この変更は、リンカがPowerPCの大きなオフセットを扱う際の内部的な正確性を向上させ、特に32ビットオフセットの生成がより堅牢になるように設計されています。

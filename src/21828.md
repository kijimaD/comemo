# [インデックス 21828] ファイルの概要

このコミットは、Go言語の`sync/atomic`パッケージにDarwin (macOS/iOS) 上のARMアーキテクチャ向けのアトミック操作の実装を追加するものです。具体的には、`src/sync/atomic/asm_darwin_arm.s`という新しいアセンブリファイルが追加され、32ビットおよび64ビットの整数型、ポインタ型に対するアトミックな比較交換（CompareAndSwap）、加算（Add）、交換（Swap）、ロード（Load）、ストア（Store）操作が提供されます。これにより、GoプログラムがDarwin/ARM環境で並行処理を行う際に、データ競合を安全に回避し、効率的な同期メカニズムを利用できるようになります。

## 変更の背景

Go言語は、その並行処理モデル（GoroutineとChannel）によって高い並行性を実現していますが、低レベルなデータ構造やアルゴリズムにおいては、よりプリミティブな同期メカニズムが必要となる場合があります。特に、複数のGoroutineが共有メモリ上の単一の変数を同時に読み書きするような状況では、データ競合（data race）を防ぐためにアトミック操作が不可欠です。

アトミック操作は、その操作が不可分（atomic）であることを保証します。つまり、操作の途中で他のGoroutineによる割り込みや干渉がなく、常に一貫性のある状態を保ちます。これは、ミューテックス（mutex）のようなロック機構と比較して、より粒度の細かい同期を、多くの場合より高いパフォーマンスで実現するために用いられます。

Go言語の`sync/atomic`パッケージは、このようなアトミック操作をGoのコードから利用するためのインターフェースを提供しています。しかし、これらの操作はCPUの特定の命令セットに依存するため、各アーキテクチャ（x86, ARMなど）およびオペレーティングシステム（Linux, Windows, Darwinなど）の組み合わせごとに、そのプラットフォーム固有のアセンブリコードで実装される必要があります。

このコミットが行われた2014年当時、Go言語は様々なプラットフォームへの対応を進めていました。特に、Appleのデバイス（iPhone, iPad, Macなど）がARMプロセッサを搭載し、その上で動作するDarwin（macOS/iOS）環境でのGoアプリケーションの需要が高まっていました。このコミットは、GoがDarwin/ARM環境で完全に機能し、効率的な並行処理をサポートするために、`sync/atomic`パッケージの基盤となるアトミック操作をこの特定のプラットフォーム向けに実装する必要があったという背景から生まれました。これにより、GoプログラムはDarwin/ARM環境でも、データ競合を気にすることなく共有変数を安全に操作できるようになりました。

## 前提知識の解説

### 1. Go言語の `sync/atomic` パッケージ

`sync/atomic`パッケージは、Go言語において低レベルなアトミック操作を提供する標準ライブラリです。このパッケージの関数は、CPUのハードウェアが提供するアトミック命令を利用して実装されており、ロックを使用せずに共有変数を安全に操作することを可能にします。これにより、ミューテックスなどのロック機構に比べて、競合が少ない状況ではより高いパフォーマンスを発揮することが期待できます。

主な機能は以下の通りです。

*   **CompareAndSwap (CAS):** 指定されたメモリ位置の値が期待値と一致する場合にのみ、新しい値に更新します。これはロックフリーなアルゴリズムの構築において非常に重要なプリミティブです。
*   **Add:** 指定されたメモリ位置の値にアトミックに加算します。
*   **Swap:** 指定されたメモリ位置の値を新しい値にアトミックに交換し、元の値を返します。
*   **Load:** 指定されたメモリ位置の値をアトミックに読み込みます。
*   **Store:** 指定されたメモリ位置に値をアトミックに書き込みます。

これらの操作は、`int32`, `int64`, `uint32`, `uint64`, `uintptr`, `Pointer`などの型に対して提供されます。

### 2. アトミック操作

アトミック操作とは、複数のCPUコアやスレッド（GoにおいてはGoroutine）から同時にアクセスされた場合でも、その操作全体が中断されることなく、単一の不可分な操作として実行されることを保証するものです。これにより、操作の途中でデータが部分的に更新されたり、他のスレッドによって不整合な状態が観測されたりする「データ競合」を防ぐことができます。

例えば、`i++`という単純な操作も、実際には「iの値を読み込む」「読み込んだ値に1を加える」「結果をiに書き戻す」という複数のステップから構成されます。複数のGoroutineが同時にこの操作を行うと、読み込みと書き込みの間に他のGoroutineが値を変更し、最終的な結果が期待通りにならない可能性があります。アトミック操作は、このような問題をハードウェアレベルで解決します。

### 3. ARMアーキテクチャとロード・ストア排他命令 (LDREX/STREX)

ARMアーキテクチャは、モバイルデバイスや組み込みシステムで広く使用されているRISC（Reduced Instruction Set Computer）ベースのCPUアーキテクチャです。アトミック操作を効率的に実現するために、ARMv6以降のアーキテクチャでは「ロード・ストア排他命令」（Load-Exclusive / Store-Exclusive）が導入されています。

*   **LDREX (Load-Exclusive):** 指定されたメモリアドレスから値をレジスタにロードし、同時にそのアドレスを「排他モニター」（exclusive monitor）と呼ばれるCPU内部の状態に登録します。
*   **STREX (Store-Exclusive):** 指定されたレジスタの値を、排他モニターに登録されているアドレスにストアしようとします。ストアが成功した場合（つまり、LDREX以降、他のCPUコアがそのアドレスに書き込みを行っていない場合）、STREXは成功を示す値を返します。ストアが失敗した場合（他のコアが書き込みを行った場合）、STREXは失敗を示す値を返し、ストアは行われません。

アトミック操作、特にCAS（Compare-and-Swap）やアトミックな加算などは、このLDREXとSTREXのペアをループ内で使用することで実装されます。LDREXで値を読み込み、必要な計算を行い、STREXで書き戻しを試みます。STREXが失敗した場合は、他のコアがその間にメモリを更新したことを意味するため、操作全体を最初からやり直します。これにより、ロックを使用せずにデータの一貫性を保ちます。

### 4. Darwin (macOS/iOS)

Darwinは、Appleが開発したオープンソースのUNIX系オペレーティングシステムの中核部分です。macOS、iOS、watchOS、tvOSなどのApple製品のOSの基盤となっています。このコミットは、Darwin上で動作するARMプロセッサ（例えば、iPhoneやiPadのAシリーズチップ、初期のApple Silicon Macなど）に特化したアトミック操作の実装を提供します。OSの特性やシステムコールは、アセンブリレベルの実装に影響を与える可能性がありますが、アトミック操作の多くはCPUの命令セットに直接依存するため、OSの役割は限定的です。

### 5. Goのアセンブリ言語

Go言語は、一部のパフォーマンスクリティカルな部分や、OS/アーキテクチャ固有の機能（アトミック操作、Goroutineスケジューラの一部など）を実装するために、独自のアセンブリ言語を使用します。これは一般的なGAS（GNU Assembler）やNASM（Netwide Assembler）とは異なる独自の構文を持っています。

*   **`TEXT`:** 関数の開始を宣言します。
    *   `TEXT funcname(SB),flags,$framesize-argsize` の形式で記述されます。
    *   `SB` (Static Base): グローバルシンボルや外部シンボルを参照するための擬似レジスタ。
    *   `NOSPLIT`: スタックフレームの分割を禁止するフラグ。アトミック操作のような短い関数でよく使われます。
    *   `$framesize`: 関数のスタックフレームサイズ。
    *   `$argsize`: 引数の合計サイズ。
*   **`MOVW`:** 32ビットの値を移動する命令（ARMの場合）。
*   **`LDREX`, `STREX`:** 前述のロード・ストア排他命令。
*   **`CMP`:** 比較命令。
*   **`BNE`:** 比較結果が等しくない場合に分岐する命令。
*   **`RET`:** 関数からのリターン。
*   **`FP` (Frame Pointer):** 現在のスタックフレームの先頭を指す擬似レジスタ。引数やローカル変数へのアクセスに使用されます。
*   **`R0`, `R1`, `R2`など:** ARMプロセッサの汎用レジスタ。

これらの知識は、コミットで追加されたアセンブリコードを理解するために不可欠です。

## 技術的詳細

このコミットで追加された`src/sync/atomic/asm_darwin_arm.s`ファイルは、Goの`sync/atomic`パッケージが提供する様々なアトミック操作を、Darwin上のARMアーキテクチャ向けに実装しています。実装の核となるのは、ARMv6以降のプロセッサが提供するロード・ストア排他命令（`LDREX`と`STREX`）を用いたロックフリーなアルゴリズムです。

ファイル全体を見ると、多くのGoアセンブリ関数が定義されていますが、その多くは既存のより汎用的なアトミック操作の実装へのジャンプ（`B`命令）となっています。これは、Goのアトミックパッケージが、特定の型（例: `int32`と`uint32`）や特定の操作（例: `LoadInt32`と`LoadUint32`）に対して、共通の基盤となるアセンブリルーチンを再利用しているためです。

### 主要なアトミック操作の実装戦略

1.  **エイリアシング（`B`命令によるジャンプ）:**
    多くの`TEXT`定義は、単に別の関数にジャンプするだけのシンプルな構造になっています。例えば、`CompareAndSwapInt32`は`CompareAndSwapUint32`に、`LoadInt32`は`LoadUint32`にジャンプします。これは、符号付き整数と符号なし整数に対するアトミック操作の低レベルな実装が、ビットパターンとしては同じであるため、共通のルーチンを再利用できることを示しています。また、`Uintptr`や`Pointer`に対する操作も、多くの場合、`Uint32`または`Uint64`の操作にエイリアスされています。これは、ポインタのサイズが32ビットまたは64ビットの整数サイズと一致するためです。

2.  **ロード・ストア排他命令 (`LDREX`/`STREX`) の利用:**
    アトミック操作の核心は、`LDREX`と`STREX`命令のペアを用いたループです。このペアは、メモリ位置に対する読み書きが他のプロセッサによって干渉されていないことを保証するために使用されます。

    *   **`LDREX` (Load-Exclusive):** メモリから値を読み込み、そのアドレスをプロセッサの排他モニターに登録します。
    *   **`STREX` (Store-Exclusive):** 排他モニターに登録されたアドレスに値を書き込もうとします。書き込みが成功した場合（`LDREX`以降、他のプロセッサがそのアドレスに書き込みを行っていない場合）、`STREX`は0を返します。失敗した場合（他のプロセッサが書き込みを行った場合）、非ゼロの値を返し、書き込みは行われません。

    アトミック操作は、`STREX`が成功するまで`LDREX`からの一連の操作をループで繰り返すことで実現されます。これにより、ロックを使用せずにデータの一貫性を保ちます。

### `LoadUint32` の実装例

```assembly
TEXT ·LoadUint32(SB),NOSPLIT,$0-8
	MOVW addr+0(FP), R1    // 引数 addr (読み込むアドレス) を R1 にロード
load32loop:
	LDREX (R1), R2         // R1 が指すアドレスから値を排他的にロードし、R2 に格納
	STREX R2, (R1), R0     // R2 の値を R1 が指すアドレスに排他的にストアしようと試みる。結果は R0 に格納
	CMP $0, R0             // STREX の結果 (R0) が 0 (成功) かどうかを比較
	BNE load32loop         // 0 でなければ (失敗していれば)、load32loop に戻って再試行
	MOVW R2, val+4(FP)     // 成功した場合、ロードした値 (R2) を戻り値 val に格納
	RET                    // 関数からリターン
```

この`LoadUint32`関数は、指定されたアドレスから32ビットの値をアトミックに読み込むためのものです。一見すると単純なロード操作に見えますが、`LDREX`/`STREX`のペアを使用することで、読み込み操作自体が他の書き込み操作と競合しないように保証しています。これは、単なる`LDR`（ロード）命令では保証できないメモリバリアや順序付けの側面をカバーするため、あるいは特定のCPUアーキテクチャでアトミックなロードを実装する際の一般的なパターンです。`STREX`で同じ値を書き戻すことで、排他モニターの状態をクリアし、他の操作がブロックされないようにします。

### `StoreUint32` の実装例

```assembly
TEXT ·StoreUint32(SB),NOSPLIT,$0-8
	MOVW addr+0(FP), R1    // 引数 addr (書き込むアドレス) を R1 にロード
	MOVW val+4(FP), R2     // 引数 val (書き込む値) を R2 にロード
storeloop:
	LDREX (R1), R4         // R1 が指すアドレスから値を排他的にロードし、R4 に格納 (排他モニターをセット)
	STREX R2, (R1), R0     // R2 の値を R1 が指すアドレスに排他的にストアしようと試みる。結果は R0 に格納
	CMP $0, R0             // STREX の結果 (R0) が 0 (成功) かどうかを比較
	BNE storeloop          // 0 でなければ (失敗していれば)、storeloop に戻って再試行
	RET                    // 関数からリターン
```

この`StoreUint32`関数は、指定されたアドレスに32ビットの値をアトミックに書き込むためのものです。`LDREX`で現在の値を読み込み（これは排他モニターをセットするため）、その後`STREX`で新しい値を書き込もうとします。`STREX`が成功するまでループを繰り返すことで、書き込み操作がアトミックに完了することを保証します。

### 64ビット操作

コミットのコードには、`CompareAndSwapUint64`, `AddUint64`, `SwapUint64`, `LoadUint64`, `StoreUint64`といった64ビット操作へのジャンプも含まれています。これらの実際の`armCompareAndSwapUint64`, `addUint64`, `swapUint64`, `loadUint64`, `storeUint64`といったルーチンは、このファイルには直接記述されていませんが、Goのランタイムの他の部分（おそらく`src/runtime/sys_darwin_arm.s`や`src/runtime/atomic_arm.s`など）で、64ビットのアトミック操作をサポートするために、同様に`LDREX`/`STREX`のペアや、場合によってはより複雑なシーケンス（例えば、64ビット値を2つの32ビットレジスタで扱うなど）を用いて実装されていると推測されます。ARMv7以降では、64ビットの`LDREXD`/`STREXD`命令が利用可能であり、これらを使用することでより効率的な64ビットアトミック操作が実現されます。

このコミットは、GoがDarwin/ARM環境で堅牢な並行処理をサポートするための重要な一歩であり、低レベルなアセンブリ言語とハードウェアの特性を深く理解して実装されていることがわかります。

2.  **具体的なアトミック操作の実装:** `LoadUint32`と`StoreUint32`の2つの関数は、このファイル内で直接アセンブリコードが記述されており、ARMプロセッサのロード・ストア排他命令（`LDREX`と`STREX`）を使用してアトミック性を保証しています。

## コアとなるコードの解説

このコミットの核となるのは、`LoadUint32`と`StoreUint32`のアセンブリ実装です。これらは、ARMアーキテクチャにおけるアトミック操作の基本的なパターンを示しています。

### `LoadUint32` の解説

```assembly
TEXT ·LoadUint32(SB),NOSPLIT,$0-8
	MOVW addr+0(FP), R1    // 1. 関数引数 `addr` (読み込むメモリのアドレス) をレジスタ R1 にロードします。
                           //    `addr+0(FP)` は、フレームポインタ (FP) からのオフセットで引数にアクセスするGoアセンブリの記法です。
load32loop:                // 2. アトミック操作のループ開始ラベルです。
	LDREX (R1), R2         // 3. R1 が指すメモリアドレスから値を排他的にロードし、結果をレジスタ R2 に格納します。
                           //    この命令は、排他モニターをセットし、このアドレスに対する他のプロセッサからの書き込みを監視し始めます。
	STREX R2, (R1), R0     // 4. R2 の値を R1 が指すメモリアドレスに排他的にストアしようと試みます。
                           //    ストアが成功した場合 (LDREX以降、他のプロセッサがこのアドレスに書き込んでいない場合)、R0 に 0 がセットされます。
                           //    ストアが失敗した場合 (他のプロセッサが書き込んだ場合)、R0 に非ゼロの値がセットされ、ストアは行われません。
	CMP $0, R0             // 5. STREX の結果 (R0) が 0 (成功) かどうかを比較します。
	BNE load32loop         // 6. R0 が 0 でない場合 (STREX が失敗した場合)、`load32loop` ラベルに戻り、操作を再試行します。
                           //    これにより、競合が発生した場合でも、操作が最終的に成功することが保証されます。
	MOVW R2, val+4(FP)     // 7. STREX が成功した場合、アトミックに読み込んだ値 (R2) を関数の戻り値 `val` に格納します。
                           //    `val+4(FP)` は、戻り値がスタックフレーム上のどこに配置されるかを示します。
	RET                    // 8. 関数からリターンします。
```

この`LoadUint32`は、単なるメモリ読み込みではなく、`LDREX`/`STREX`のペアを使って「アトミックな読み込み」を実現しています。これは、読み込み操作中に他のプロセッサがそのメモリ位置を更新した場合でも、常に一貫性のある最新の値を確実に取得するためのパターンです。`STREX`で同じ値を書き戻すことで、排他モニターの状態をクリアし、他のアトミック操作がブロックされないようにする役割も果たします。

### `StoreUint32` の解説

```assembly
TEXT ·StoreUint32(SB),NOSPLIT,$0-8
	MOVW addr+0(FP), R1    // 1. 関数引数 `addr` (書き込むメモリのアドレス) をレジスタ R1 にロードします。
	MOVW val+4(FP), R2     // 2. 関数引数 `val` (書き込む値) をレジスタ R2 にロードします。
storeloop:                 // 3. アトミック操作のループ開始ラベルです。
	LDREX (R1), R4         // 4. R1 が指すメモリアドレスから値を排他的にロードし、結果をレジスタ R4 に格納します。
                           //    この命令は、排他モニターをセットし、このアドレスに対する他のプロセッサからの書き込みを監視し始めます。
                           //    ストア操作の場合、このロードは主に排他モニターをセットするために行われます。
	STREX R2, (R1), R0     // 5. R2 の値 (新しい値) を R1 が指すメモリアドレスに排他的にストアしようと試みます。
                           //    ストアが成功した場合、R0 に 0 がセットされます。失敗した場合、R0 に非ゼロの値がセットされます。
	CMP $0, R0             // 6. STREX の結果 (R0) が 0 (成功) かどうかを比較します。
	BNE storeloop          // 7. R0 が 0 でない場合 (STREX が失敗した場合)、`storeloop` ラベルに戻り、操作を再試行します。
                           //    これにより、競合が発生した場合でも、操作が最終的に成功することが保証されます。
	RET                    // 8. 関数からリターンします。
```

`StoreUint32`も同様に`LDREX`/`STREX`ループを使用しています。`LDREX`で排他モニターをセットし、その後に`STREX`で新しい値を書き込もうとします。もし`LDREX`と`STREX`の間に他のプロセッサが同じアドレスに書き込みを行った場合、`STREX`は失敗し、ループが再試行されます。これにより、書き込み操作全体が不可分に実行されることが保証されます。

これらのアセンブリコードは、Go言語が提供する高レベルな並行処理プリミティブ（GoroutineやChannel）の背後で、どのように低レベルなハードウェアの機能を利用してデータの一貫性を保っているかを示す良い例です。

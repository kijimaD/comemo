# [インデックス 25644] ファイルの概要

このコミットは、GoコンパイラおよびリンカにおけるPPC64アーキテクチャ向けの変更であり、特に静的データへのアクセスを位置独立コード（PIC: Position-Independent Code）として生成する機能の改善を目的としています。共有ライブラリ（Shared Libraries）の文脈において、静的データへのロード命令が、実行時のメモリ配置に依存しないように修正されています。これにより、Goプログラムが共有ライブラリとしてより効率的かつ柔軟に機能するようになります。

## 元コミット内容

このコミットは、Goのコンパイラ（`cmd/internal/obj`）とリンカ（`cmd/link`）が、PPC64アーキテクチャにおいて静的データへのアクセスを位置独立な方法で生成するように変更します。具体的には、共有ライブラリのビルド時に、静的データへのロード命令がTable of Contents (TOC) を基準とした相対アドレス指定を使用するように修正され、新しいリロケーションタイプが導入されています。

## 変更の背景

Goプログラムを共有ライブラリとしてビルドする場合、そのコードはメモリ上の任意の位置にロードされても正しく実行できる必要があります。これを「位置独立コード（PIC）」と呼びます。静的データ（グローバル変数など）へのアクセスは、通常、絶対アドレス指定で行われますが、PICではこれが問題となります。共有ライブラリがロードされるたびに、静的データのアドレスが異なる可能性があるため、絶対アドレスに依存するコードは実行時に修正（リロケーション）が必要となり、オーバーヘッドが発生したり、セキュリティ上の問題を引き起こしたりする可能性があります。

PPC64アーキテクチャでは、この問題を解決するためにTable of Contents (TOC) というメカニズムが利用されます。TOCは、共有ライブラリ内のすべてのグローバル変数や静的データのアドレスを格納する特別なデータ領域です。コードは、TOCへの相対オフセットを使ってデータにアクセスすることで、位置独立性を実現します。

このコミット以前のGoのPPC64向けコード生成では、静的データへのアクセスが常に位置独立ではなかった可能性があります。特に共有ライブラリの文脈で、TOCを利用した適切なリロケーションが生成されていなかったため、GoプログラムをPPC64上で共有ライブラリとして利用する際に問題が生じるか、非効率なコードが生成されていたと考えられます。この変更は、PPC64におけるGoの共有ライブラリサポートを強化し、より堅牢で効率的なコード生成を実現するために行われました。

## 前提知識の解説

*   **位置独立コード (PIC: Position-Independent Code)**: 実行可能ファイルがメモリ上の任意のアドレスにロードされても正しく動作するように設計されたコード。共有ライブラリでは必須の特性です。PICでないコードは、ロード時にリンカによってアドレスが修正される必要があり、これはオーバーヘッドやメモリフットプリントの増加につながります。
*   **共有ライブラリ (Shared Libraries)**: 複数のプログラムで共有されるライブラリ。メモリを節約し、プログラムの起動時間を短縮します。PICは共有ライブラリの重要な要素です。
*   **PPC64 (PowerPC 64-bit)**: IBMが開発したRISCプロセッサアーキテクチャの64ビット版。特定のレジスタ使用規則やアドレス指定モードを持ちます。
*   **Table of Contents (TOC)**: PPC64アーキテクチャにおける共有ライブラリの重要な概念。TOCは、グローバル変数、静的変数、外部関数へのポインタなど、プログラムが実行時にアクセスする必要があるアドレスを格納するデータ構造です。通常、`R2`レジスタがTOCのベースアドレスを指します。コードはTOCへのオフセットを使ってデータにアクセスすることで、位置独立性を実現します。
*   **リロケーション (Relocation)**: コンパイル時に決定できないアドレス（例えば、共有ライブラリ内のグローバル変数のアドレス）を、プログラムのロード時に実際のメモリ上のアドレスに解決するプロセス。リンカが行います。
*   **ELF (Executable and Linkable Format)**: Unix系システムで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマット。ELFファイルには、リロケーション情報が含まれています。
*   **ELFリロケーションタイプ (ELF Relocation Types)**: ELFフォーマットで定義されている、特定のリロケーションの種類を示す定数。PPC64には、TOCを基準としたアドレス解決のための特定のリロケーションタイプ（例: `R_PPC64_TOC16_HA`, `R_PPC64_TOC16_LO`, `R_PPC64_TOC16_LO_DS`）が存在します。
*   **`ADDIS` 命令 (Add Immediate Shifted)**: PowerPCの命令で、即値（Immediate Value）をシフトしてレジスタに加算します。アドレスの上位ビットをロードする際によく使用されます。
*   **D-form / DS-form 命令**: PowerPCの命令フォーマットの一種。D-formは16ビットの即値またはオフセットを、DS-formは16ビットの即値またはオフセットを2ビット左シフトした値をオペランドとして持ちます。これらはメモリロード/ストア命令や分岐命令でよく使われます。

## 技術的詳細

このコミットの核心は、PPC64アーキテクチャにおいて静的データへのアクセスをTOC相対アドレス指定に切り替えることです。

1.  **新しいリロケーションタイプの導入**:
    *   `src/cmd/internal/obj/link.go` に `R_ADDRPOWER_TOCREL` と `R_ADDRPOWER_TOCREL_DS` という2つの新しいリロケーションタイプが追加されました。これらは、それぞれD-formおよびDS-form命令に対して、シンボルのアドレスではなくTOCからのオフセットを挿入するためのものです。

2.  **`symbolAccess` 関数の変更**:
    *   `src/cmd/internal/obj/ppc64/asm9.go` 内の `symbolAccess` 関数は、シンボル `s` とオフセット `d` を使ってレジスタ `reg` にアクセスする命令をエンコードします。
    *   この関数は、`ctxt.Flag_shared` フラグ（共有ライブラリをビルドしていることを示す）が設定されているかどうかをチェックするようになりました。
    *   `ctxt.Flag_shared` が `0` でない（つまり共有ライブラリをビルドしている）場合、`ADDIS` 命令のベースレジスタが `REGZERO` (R0) から `REG_R2` (TOCポインタレジスタ) に変更されます。これにより、TOCを基準としたアドレス計算が開始されます。
    *   さらに、リロケーションタイプも `R_ADDRPOWER_TOCREL` または `R_ADDRPOWER_TOCREL_DS` に設定されます。これにより、リンカはTOCからの相対オフセットを計算して命令に埋め込むようになります。
    *   `ctxt.Flag_shared` が `0` の場合（通常の実行可能ファイルをビルドしている場合）、以前と同様に `REGZERO` をベースとし、`R_ADDRPOWER` または `R_ADDRPOWER_DS` リロケーションタイプが使用されます。

3.  **リンカでの新しいリロケーションタイプの処理**:
    *   `src/cmd/link/internal/ppc64/asm.go` 内の `elfreloc1` 関数は、GoのリロケーションタイプをELFのリロケーションタイプにマッピングします。
    *   `obj.R_ADDRPOWER_TOCREL` は `ld.R_PPC64_TOC16_HA` と `ld.R_PPC64_TOC16_LO` の組み合わせにマッピングされます。これらは、TOCからのオフセットの上位16ビットと下位16ビットをそれぞれ命令に埋め込むためのELFリロケーションタイプです。
    *   `obj.R_ADDRPOWER_TOCREL_DS` は `ld.R_PPC64_TOC16_HA` と `ld.R_PPC64_TOC16_LO_DS` の組み合わせにマッピングされます。`_DS` はDS-form命令に対応します。
    *   `archreloc` 関数も、これらの新しいリロケーションタイプを認識するように更新されています。

これらの変更により、GoのPPC64向けコンパイラとリンカは、共有ライブラリのビルド時に静的データへのアクセスをTOC相対で処理し、真に位置独立なコードを生成できるようになります。

## コアとなるコードの解説

*   **`src/cmd/internal/obj/link.go`**: このファイルは、Goのオブジェクトファイルフォーマットとリロケーションタイプを定義しています。新しい `R_ADDRPOWER_TOCREL` と `R_ADDRPOWER_TOCREL_DS` は、PPC64アーキテクチャ特有のTOC相対アドレス指定をサポートするために導入されました。これにより、Goのコンパイラとリンカは、TOCを基準としたリロケーションを正確に表現できるようになります。

*   **`src/cmd/internal/obj/ppc64/asm9.go` - `symbolAccess` 関数**: この関数は、アセンブラがシンボルへのアクセス命令を生成する際の中心的なロジックを含んでいます。
    *   `ctxt.Flag_shared != 0` の条件分岐が重要です。これは、現在ビルドしているのが共有ライブラリであるかどうかを判断します。
    *   共有ライブラリの場合、`base = REG_R2` と設定されます。`REG_R2` はPPC64においてTOCポインタを保持する慣例的なレジスタです。これにより、`ADDIS` 命令はTOCのベースアドレスを基準としたオフセットを計算するようになります。
    *   リロケーションタイプが `obj.R_ADDRPOWER_TOCREL` または `obj.R_ADDRPOWER_TOCREL_DS` に設定されることで、リンカに対して「この命令はTOCからの相対オフセットで解決されるべきである」という指示が与えられます。
    *   共有ライブラリでない場合は、以前と同様に `REG_R0` (ゼロレジスタ) をベースとし、絶対アドレス指定に近い `R_ADDRPOWER` 系のリロケーションが使用されます。

*   **`src/cmd/link/internal/ppc64/asm.go` - `elfreloc1` 関数**: この関数は、Goの内部リロケーションタイプを、最終的なELFバイナリに書き込まれるPPC64固有のELFリロケーションタイプに変換します。
    *   `obj.R_ADDRPOWER_TOCREL` と `obj.R_ADDRPOWER_TOCREL_DS` がそれぞれ `R_PPC64_TOC16_HA` と `R_PPC64_TOC16_LO` (または `R_PPC64_TOC16_LO_DS`) にマッピングされることで、リンカはTOCからのオフセットを計算し、命令の適切な位置に上位16ビットと下位16ビットを埋め込むことができます。
    *   `R_PPC64_TOC16_HA` (High Adjusted) は、TOCからのオフセットの上位16ビットを、下位16ビットが符号拡張された後に加算されることを考慮して調整された値で埋め込みます。
    *   `R_PPC64_TOC16_LO` (Low) は、TOCからのオフセットの下位16ビットを埋め込みます。
    *   `R_PPC64_TOC16_LO_DS` は、DS-form命令向けに、下位16ビットを2ビット左シフトした値を埋め込みます。

これらの変更により、PPC64アーキテクチャ上でGoの共有ライブラリが、静的データに効率的かつ位置独立な方法でアクセスできるようになり、Goのクロスプラットフォーム対応と共有ライブラリ機能が強化されます。

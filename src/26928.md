## 変更の背景

Go言語のマップ（`map`）は、その設計上、要素のイテレーション順序が保証されていません。これは、マップがハッシュテーブルとして実装されており、要素の追加や削除、さらにはGoランタイムの内部的な動作によって、イテレーション順序が実行ごとに変わる可能性があるためです。

コンパイラのようなツールがマップのイテレーション順序に依存していると、同じソースコードを複数回コンパイルしても、生成されるバイナリや中間コードが毎回異なる可能性があります。このような非決定的な出力は、以下のような問題を引き起こします。

1.  **ビルドの再現性の欠如**: 同じ入力から常に同じ出力が得られるという保証がなくなるため、ビルドの再現性が損なわれます。これは、デバッグやCI/CDパイプラインにおいて深刻な問題となります。
2.  **`toolstash`の破損**: `toolstash`は、Goのツールチェーンが生成する中間ファイルやバイナリをキャッシュし、変更がない場合には再利用することでビルド時間を短縮するツールです。コンパイラの出力が非決定論的であると、`toolstash`は常に異なる出力を検出し、キャッシュを無効にして再ビルドを強制するため、その効果が失われます。
3.  **デバッグの困難さ**: 非決定的な動作は、バグの再現を困難にし、デバッグプロセスを複雑にします。

このコミットは、これらの問題を解決するために、コンパイラがマップのイテレーション順序に依存しないように修正することを目的としています。具体的には、Issue #14600で報告された問題に対応しています。

## 前提知識の解説

### Goのマップ（map）の非順序性

Goの組み込み型である`map`は、キーと値のペアを格納するハッシュテーブルです。Goの仕様では、`map`のイテレーション順序は定義されておらず、実行ごとに異なる可能性があります。これは意図的な設計であり、プログラマが特定の順序に依存しないように促すとともに、マップの実装を最適化するための自由度をコンパイラに与えています。

### `cmd/compile`

`cmd/compile`は、Go言語のソースコードを機械語にコンパイルするGoコンパイラの主要部分です。このコンパイラは、フロントエンド（構文解析、型チェック）、中間表現（IR）の生成、最適化、バックエンド（コード生成）など、複数のステージで構成されています。このコミットで変更されている`ssa`パッケージは、Static Single Assignment (SSA) 形式の中間表現を扱う部分であり、最適化やレジスタ割り当てなどの重要な処理が行われます。

### `toolstash`

`toolstash`は、Goのビルドシステムの一部として機能するツールで、コンパイラやリンカなどのツールが生成する中間成果物をキャッシュします。これにより、ソースコードが変更されていない場合や、変更がビルド結果に影響しない場合に、再コンパイルや再リンクをスキップしてビルド時間を短縮します。`toolstash`は、入力と出力のハッシュを比較することで、変更を検出します。したがって、コンパイラの出力が非決定論的であると、`toolstash`は常に「変更あり」と判断し、キャッシュの恩恵を受けられなくなります。

### SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの最適化フェーズで広く使用される中間表現です。この形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。Goコンパイラの`ssa`パッケージは、このSSA形式を生成・操作し、レジスタ割り当てなどのバックエンド処理に渡します。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおける2つのファイル、`src/cmd/compile/internal/ssa/print.go`と`src/cmd/compile/internal/ssa/regalloc.go`に変更を加えています。これらのファイル内で、マップのイテレーション順序に依存していた箇所を特定し、決定論的な順序でイテレーションを行うように修正しています。

### `src/cmd/compile/internal/ssa/print.go`の変更

このファイルは、SSA形式の関数をデバッグ目的で出力する際に使用されます。変更前は、`f.NamedValues`というマップを直接イテレートしていました。

```go
// 変更前
for name, vals := range f.NamedValues {
	p.named(name, vals)
}
```

`f.NamedValues`は`map[string][]*Value`型であり、そのイテレーション順序は保証されません。この非決定性を排除するため、`Func`構造体に`Names []string`というフィールドが追加され、`f.NamedValues`のキーをこのスライスに格納し、このスライスをイテレートするように変更されました。

```go
// 変更後
for _, name := range f.Names {
	p.named(name, f.NamedValues[name])
}
```

これにより、`f.Names`スライスに格納された順序で`NamedValues`にアクセスするため、出力が常に決定論的になります。

### `src/cmd/compile/internal/ssa/regalloc.go`の変更

このファイルは、SSA形式のコードに対するレジスタ割り当てロジックを含んでいます。`edgeState`構造体は、レジスタ割り当てプロセス中のエッジの状態を管理します。変更前は、`edgeState.cache`というマップを直接イテレートしていました。

```go
// 変更前 (例: cacheのクリア)
for k := range e.cache {
	delete(e.cache, k)
}
```

`e.cache`は`map[ID][]*Value`型であり、ここでもイテレーション順序の非決定性が問題となっていました。この問題を解決するため、`edgeState`構造体に`cachedVals []ID`というスライスが追加されました。このスライスは、`e.cache`のキーを保持し、イテレーションが必要な際にはこのスライスを使用するように変更されました。

具体的には、以下の変更が行われました。

1.  **`edgeState`構造体への`cachedVals`の追加**:
    ```go
    type edgeState struct {
        // ...
        cache      map[ID][]*Value
        cachedVals []ID // (superset of) keys of the above map, for deterministic iteration
        // ...
    }
    ```
    `cachedVals`は、`cache`マップのキーのスーパーセット（またはキーそのもの）を保持し、決定論的なイテレーションを可能にします。

2.  **`edgeState.setup`メソッドでの`cache`のクリア**:
    `setup`メソッドは`edgeState`を初期化する際に呼び出されます。変更前は`for k := range e.cache`でマップを直接イテレートしていましたが、変更後は`cachedVals`スライスを使ってイテレートし、マップから要素を削除します。その後、`cachedVals`スライス自体もクリアされます。
    ```go
    // 変更後
    for _, vid := range e.cachedVals {
        delete(e.cache, vid)
    }
    e.cachedVals = e.cachedVals[:0] // スライスもクリア
    ```

3.  **`edgeState.set`メソッドでの`cachedVals`の更新**:
    `set`メソッドは`cache`マップに新しいエントリを追加する際に呼び出されます。このとき、新しいキーが`cachedVals`にまだ存在しない場合、`cachedVals`に追加されます。
    ```go
    // 変更後
    a := e.cache[vid]
    if len(a) == 0 { // 新しいキーの場合のみ追加
        e.cachedVals = append(e.cachedVals, vid)
    }
    a = append(a, c)
    e.cache[vid] = a
    ```

4.  **デバッグ出力およびレジスタ選択ロジックでのイテレーション順序の修正**:
    `regDebug`が有効な場合のデバッグ出力や、`findRegFor`メソッドでのレジスタ選択ロジックなど、`e.cache`をイテレートしていたすべての箇所で、`cachedVals`スライスを使用して決定論的な順序でイテレートするように変更されました。
    ```go
    // 変更後 (例: デバッグ出力)
    for _, vid := range e.cachedVals {
        a := e.cache[vid]
        // ...
    }
    ```

これらの変更により、コンパイラのSSAバックエンドにおけるマップのイテレーション順序に起因する非決定性が排除され、コンパイル出力が常に決定論的になることが保証されます。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/print.go`

`fprintFunc`関数は、SSA形式の関数を整形して出力する役割を担っています。変更前は、`f.NamedValues`というマップを直接`range`ループでイテレートしていました。Goのマップのイテレーション順序は保証されないため、この部分が非決定的な出力の原因となっていました。

変更後は、`f.Names`という`[]string`型のスライスをイテレートするように修正されています。`f.Names`は`f.NamedValues`マップのキーを決定論的な順序で保持していると推測されます（このコミットの差分には`f.Names`がどのように初期化されるかの変更は含まれていませんが、文脈からそのように機能すると考えられます）。これにより、`p.named(name, f.NamedValues[name])`の呼び出し順序が常に一定になり、`fprintFunc`の出力が決定論的になります。

### `src/cmd/compile/internal/ssa/regalloc.go`

`edgeState`構造体は、レジスタ割り当てアルゴリズムにおいて、基本ブロック間のエッジの状態を管理します。特に、`cache`フィールドは`map[ID][]*Value`型で、特定のIDを持つ値に関連するキャッシュされた値を保持します。

このコミットの主要な変更点は、`edgeState`に`cachedVals []ID`というスライスを追加し、`cache`マップのキーをこのスライスに格納することで、マップのイテレーション順序に依存しないようにしたことです。

1.  **`edgeState`構造体の変更**: `cachedVals []ID`が追加され、`cache`マップのキーを順序付けて保持する役割を担います。
2.  **`setup`メソッド**: `edgeState`の初期化時に呼び出されます。以前は`for k := range e.cache`でマップを直接イテレートして`delete`していましたが、変更後は`for _, vid := range e.cachedVals`でスライスをイテレートし、`cache`マップから要素を削除します。その後、`e.cachedVals = e.cachedVals[:0]`でスライス自体もクリアされ、次の使用に備えます。これにより、マップのクリア処理も決定論的になります。
3.  **`set`メソッド**: `cache`マップに新しいエントリが追加される際に呼び出されます。`if len(a) == 0`という条件は、`vid`が`cache`マップに初めて追加されるキーである場合に真となります。このとき、`e.cachedVals = append(e.cachedVals, vid)`によって、新しいキーが`cachedVals`スライスの末尾に追加されます。これにより、`cachedVals`は`cache`マップのキーが追加された順序を保持することになります。
4.  **イテレーション箇所の修正**: `regDebug`が有効な場合のデバッグ出力や、`findRegFor`メソッドでのレジスタ選択ロジックなど、`e.cache`をイテレートしていたすべての箇所で、`for _, vid := range e.cachedVals`という形式に変更されています。これにより、`cache`マップの要素へのアクセス順序が`cachedVals`スライスによって制御され、常に決定論的になります。

これらの変更により、レジスタ割り当てプロセスにおける中間状態の処理が決定論的になり、最終的なコンパイル出力の非決定性が解消されます。

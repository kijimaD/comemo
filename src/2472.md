## 変更の背景

このコミットの背景には、Goランタイムのビルドプロセスにおける手動でのファイル管理の課題があります。具体的には、`386/asm.h`というアセンブリ定数を定義するファイルが、コミット時に含まれていなかったという問題が発生しました。このような手動での管理は、ファイルの欠落や内容の不整合を引き起こす可能性があり、ビルドの信頼性を低下させます。

Goランタイムは、低レベルな操作（スケジューリング、スタック管理、コンテキストスイッチなど）のためにアセンブリコードを多用します。これらのアセンブリコードは、Goのデータ構造（`G`、`M`、`Gobuf`など）の内部オフセットや特定の定数に直接アクセスする必要があります。これらの値が手動で定義された`asm.h`ファイルに記述されている場合、Goのデータ構造が変更されるたびに、`asm.h`も手動で更新する必要があり、これはエラーの温床となります。

このコミットは、この問題を根本的に解決するために、`asm.h`ファイルを自動生成するメカニズムを導入します。これにより、Goのデータ構造の定義から直接アセンブリ定数を抽出できるようになり、手動での同期作業が不要になります。

## 前提知識の解説

このコミットを理解するためには、以下の概念が重要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルなシステムです。ゴルーチン（goroutine）のスケジューリング、メモリ管理（ガベージコレクション）、チャネル通信、システムコールなど、Go言語の並行性と効率性を支える中核部分を担っています。ランタイムの多くの部分はGo言語で書かれていますが、パフォーマンスが要求される一部の処理（コンテキストスイッチ、スタック管理など）はアセンブリ言語で実装されています。
*   **アセンブリ言語 (Assembly Language)**: コンピュータのプロセッサが直接理解できる機械語に非常に近い低レベルなプログラミング言語です。特定のレジスタやメモリ位置に直接アクセスできるため、非常に高速なコードやハードウェアに密接な操作を記述する際に使用されます。Goランタイムでは、OSスレッドとゴルーチンの切り替え、スタックの拡張・縮小といったクリティカルな処理にアセンブリが使われます。
*   **アセンブリ定数と構造体オフセット (Assembly Constants and Struct Offsets)**: アセンブリコードがCやGoで定義されたデータ構造の特定のフィールドにアクセスするためには、そのフィールドが構造体の先頭からどれだけ離れているか（オフセット）を知る必要があります。これらのオフセットやその他の定数は、通常、アセンブリコード内で直接ハードコードされるか、`#define`ディレクティブを含むヘッダーファイル（例: `asm.h`）を通じて提供されます。
*   **`G`、`M`、`Gobuf`構造体**: Goランタイムのスケジューラを構成する主要なデータ構造です。
    *   **`G` (Goroutine)**: 1つのゴルーチンを表す構造体です。スタック情報、スケジューリング情報、現在の状態などが含まれます。
    *   **`M` (Machine/OS Thread)**: 1つのOSスレッドを表す構造体です。このスレッド上でゴルーチンが実行されます。現在のゴルーチン（`curg`）、スケジューリング用のスタック（`g0`）、スレッドローカルストレージなどが含まれます。
    *   **`Gobuf` (Goroutine Buffer)**: ゴルーチンの実行コンテキスト（スタックポインタ`sp`、プログラムカウンタ`pc`、現在のゴルーチン`g`）を保存するための構造体です。ゴルーチンの切り替え時に、この構造体に現在のコンテキストが保存され、別のゴルーチンのコンテキストがロードされます。
*   **`morestack` / `lessstack`**: Goランタイムにおけるスタック管理の重要な関数です。Goのゴルーチンは比較的小さなスタックで開始し、必要に応じて自動的にスタックを拡張（`morestack`）または縮小（`lessstack`）します。これらの処理はアセンブリ言語で実装されており、`G`や`M`構造体のフィールドにアクセスしてスタック情報を更新します。
*   **`libmach`**: デバッガがGoプログラムの内部構造を理解するために使用するライブラリです。Goランタイムの内部データ構造のレイアウト（特に`G`、`M`、`Gobuf`などのオフセット）に関する知識をハードコードしており、デバッガがゴルーチンやスタックの状態を正確に表示できるようにします。

## 技術的詳細

このコミットの核心は、`asm.h`ファイルの自動生成です。以前は、`src/pkg/runtime/amd64/asm.h`のようなファイルが手動で管理されており、`G`、`M`、`Gobuf`といったランタイム構造体のフィールドオフセットが`#define`として直接記述されていました。しかし、これらの構造体の定義が`runtime.h`で変更されるたびに、`asm.h`も手動で更新する必要があり、これは非常に手間がかかり、エラーが発生しやすいプロセスでした。

新しいアプローチでは、`mkasmh`というシェルスクリプトが導入されます。このスクリプトは、ビルドプロセス中に実行され、`runtime.acid`という中間ファイルを解析して、必要なオフセット情報を抽出します。

1.  **`runtime.acid`の生成**: `runtime.acid`は、`runtime.h`と`proc.c`から`CC`（Cコンパイラ）によって生成される中間ファイルです。このファイルには、Goランタイムの主要なデータ構造（`G`、`M`、`Gobuf`）の定義と、そのフィールドのオフセット情報が含まれています。
2.  **`mkasmh`スクリプトの動作**:
    *   `mkasmh`は、まず`GOARCH`環境変数（ターゲットアーキテクチャ、例: `386`、`amd64`）に基づいて、`g`と`m`レジスタの定義を出力します。例えば、`amd64`では`g`は`R15`、`m`は`R14`にマップされます。
    *   次に、`awk`コマンドを使用して`runtime.acid`を解析します。`awk`スクリプトは、`aggr G`、`aggr M`、`aggr Gobuf`といったパターンを検出し、これらの構造体内のフィールド名とそのオフセットを抽出します。
    *   抽出された情報に基づいて、`#define <struct>_<field> <offset>`形式の行を標準出力に出力します。例えば、`Gobuf`構造体の`sp`フィールドがオフセット0にある場合、`#define gobuf_sp 0`という行が生成されます。
3.  **`Makefile`の更新**: `Makefile`には、`$(GOARCH)/asm.h`を生成するための新しいルールが追加されました。このルールは、`mkasmh`スクリプトを実行し、その出力を`$(GOARCH)/asm.h`ファイルにリダイレクトします。これにより、ビルド時に`asm.h`が自動的に生成されるようになります。また、`clean`ターゲットも更新され、生成された`asm.h`ファイルがクリーンアップ時に削除されるようになりました。
4.  **`runtime.h`のコメント更新**: `runtime.h`内の構造体定義のコメントが更新され、フィールドオフセットがアセンブリではなく`libmach`によって知られていることが明記されました。これは、アセンブリコードが直接`asm.h`に依存するのではなく、`asm.h`が`runtime.acid`から生成されるようになったため、`libmach`が`runtime.acid`を解析してオフセットを知るという新しい依存関係を反映しています。
5.  **`amd64/asm.s`の変更**: `m_morearg`が`m_moreframe`にリネームされたことに伴い、アセンブリコード内の参照も更新されています。これは、スタック拡張（`morestack`）処理における引数フレームの管理方法の微調整を示唆しています。

この変更により、Goランタイムのビルドシステムは、構造体のレイアウト変更に対してより堅牢になり、開発者は手動での同期作業から解放されます。

@@ -0,0 +1,47 @@
+#!/bin/sh
+# Copyright 2009 The Go Authors. All rights reserved.
+# Use of this source code is governed by a BSD-style
+# license that can be found in the LICENSE file.
+
+set -e
+
+cat <<'EOF'
+// Assembly constants.
+// AUTOMATICALLY GENERATED BY mkasmh DURING BUILD
+
+EOF
+
+case "$GOARCH" in
+386)
+	echo '#define	g	0(FS)'
+	echo '#define	m	4(FS)'
+	;;
+amd64)
+	echo '#define	g	R15'
+	echo '#define	m	R14'
+	;;
+*)
+	echo 'unknown $GOARCH: '$GOARCH 1>&2
+	exit 1
+	;;
+esac
+echo
+
+awk '
+/^aggr G$/ { aggr="g" }
+/^aggr M$/ { aggr = "m" }
+/^aggr Gobuf$/ { aggr = "gobuf" }
+/^}/ { aggr = "" }
+
+#	Gobuf 24 sched;
+#	'Y' 48 stack0;
+#	'Y' 56 entry;
+#	'A' G 64 alllink;
+aggr != "" && /^\t/ {
+	name=$NF;
+	sub(/;/, "", name);
+	offset=$(NF-1);
+	printf("#define %s_%s %s\\n", aggr, name, offset);
+}
+' runtime.acid

## コアとなるコードの解説

このコミットの主要な変更は、`asm.h`ファイルの自動生成メカニズムの導入です。

1.  **`Makefile`の変更**:
    *   `clean`ターゲットに`*/asm.h`が追加されたことで、ビルドクリーンアップ時に生成された`asm.h`ファイルが確実に削除されるようになります。これは、自動生成されたファイルがソース管理下に残らないようにするための標準的なプラクティスです。
    *   最も重要な変更は、`$(GOARCH)/asm.h`を生成するための新しいルールです。このルールは、`runtime.acid`と`mkasmh`に依存しています。`mkasmh`スクリプトを実行し、その出力を一時ファイル`$@.x`に書き込み、その後`mv`コマンドで最終的な`$(GOARCH)/asm.h`にリネームしています。これは、ファイル生成中のエラーを防ぎ、アトミックなファイル更新を保証するための一般的な手法です。
2.  **`src/pkg/runtime/amd64/asm.h`の削除**:
    *   このファイルは、手動で管理されていたアセンブリ定数定義の役割を終え、削除されました。これにより、手動での更新作業が不要になり、`runtime.h`の構造体定義との不整合のリスクがなくなります。
3.  **`src/pkg/runtime/amd64/asm.s`の変更**:
    *   `sys·morestack`関連のアセンブリコードにおいて、`m_morearg(m)`というオフセット指定が`m_moreframe(m)`に変更されています。これは、`M`構造体内のスタックフレーム引数に関するフィールド名が変更されたことに対応するものです。アセンブリコードが直接構造体オフセットに依存しているため、このような構造体レイアウトの変更はアセンブリコードの修正を必要とします。
4.  **`src/pkg/runtime/mkasmh`の追加**:
    *   このシェルスクリプトは、`asm.h`を自動生成する中心的な役割を担います。
    *   `set -e`は、コマンドが失敗した場合にスクリプトを即座に終了させることで、エラーハンドリングを強化します。
    *   `cat <<'EOF'`ブロックは、生成される`asm.h`のヘッダーコメント（自動生成されたものであることを示すコメント）を出力します。
    *   `case "$GOARCH"`ブロックは、ターゲットアーキテクチャ（`386`または`amd64`）に応じて、`g`と`m`レジスタの定義を出力します。これは、異なるアーキテクチャでゴルーチンとOSスレッドのコンテキストが異なるレジスタに格納されるためです。
    *   `awk`スクリプトは、`runtime.acid`ファイルを解析し、`aggr G`、`aggr M`、`aggr Gobuf`といったパターン（Goの構造体定義に対応）を検索します。これらの構造体内でタブで始まる行（フィールド定義）を見つけると、フィールド名とオフセットを抽出し、`#define <struct>_<field> <offset>`形式で出力します。例えば、`Gobuf`構造体の`sp`フィールドのオフセットが`0`であれば、`#define gobuf_sp 0`という行が生成されます。この`awk`スクリプトは、`runtime.acid`がC言語の構造体定義に似た形式でオフセット情報を提供していることを前提としています。
5.  **`src/pkg/runtime/runtime.h`の変更**:
    *   `Gobuf`、`G`、`M`、`Stktop`構造体のコメントが更新され、これらのフィールドのオフセットが「アセンブリ」ではなく「`libmach`によって知られている」と明記されました。これは、アセンブリコードが直接`asm.h`に依存するのではなく、`asm.h`が`runtime.acid`から生成され、その`runtime.acid`の情報を`libmach`が利用するという、より間接的な依存関係を反映しています。
    *   `M`構造体において、`m_morearg`が`moreframe`と`moreargs`に分割されたことが示唆されています。`moreframe`は`uint32`型で、`moreargs`も`uint32`型です。これは、`morestack`関数に渡される引数のサイズと実際の引数をより明確に分離するための変更と考えられます。

これらの変更により、Goランタイムのビルドプロセスは、アセンブリ定数の管理においてより自動化され、エラー耐性が向上しました。

## 変更の背景

Go言語の `image` パッケージは、様々な画像フォーマットを扱うための機能を提供しています。YCbCrは、デジタルビデオや画像圧縮で広く使用される色空間であり、Y（輝度）、Cb（青色差）、Cr（赤色差）の3つの成分で色を表現します。YCbCr画像は、通常、色差成分（CbとCr）が輝度成分（Y）よりも低い解像度でサンプリングされる「サブサンプリング」という手法を用いてデータ量を削減します。これにより、視覚的な品質を大きく損なうことなく、ファイルサイズを小さくすることができます。

`image/internal/imageutil` パッケージ内の `DrawYCbCr` 関数は、YCbCr画像をRGBA画像に変換して描画する役割を担っていました。この変換処理では、各ピクセルのYCbCr値をRGB値に変換するために `color.YCbCrToRGB` 関数が呼び出されます。しかし、異なるサブサンプル比率（例: 4:4:4, 4:2:2, 4:2:0, 4:4:0）のYCbCr画像では、CbとCrのデータ配置が異なるため、それぞれの比率に対応した異なるロジックでピクセルデータを処理する必要がありました。

従来の `DrawYCbCr` 関数は、`switch` 文を使ってサブサンプル比率ごとに異なる処理パスを持っていました。このアプローチはコードの可読性を保ちつつ、異なる比率に対応できる利点がありますが、`color.YCbCrToRGB` の呼び出しがループ内で頻繁に行われるため、パフォーマンス上のオーバーヘッドが生じる可能性がありました。特に、コンパイラが `color.YCbCrToRGB` の呼び出しをインライン化できない場合、関数呼び出しのコストが累積し、描画性能に影響を与えることが考えられます。

このコミットの目的は、`color.YCbCrToRGB` のインライン化を促進し、描画性能を向上させるための準備として、サブサンプル比率ごとに特化したコードを生成する仕組みを導入することです。コード生成により、各サブサンプル比率に対応する処理が個別の関数やコードブロックとして明示的に生成され、コンパイラがより効果的に最適化（特にインライン化）を行えるようになります。

## 前提知識の解説

### YCbCr色空間とサブサンプリング

*   **YCbCr**: YCbCrは、輝度（Y）と2つの色差（CbとCr）で色を表現する色空間です。人間の目は輝度の変化に敏感で、色の変化には比較的鈍感であるという特性を利用し、色情報を効率的に圧縮するために使用されます。
*   **サブサンプリング**: YCbCrデータにおいて、色差成分（CbとCr）の解像度を輝度成分（Y）よりも低くする技術です。これにより、データ量を削減しつつ、人間の視覚にはほとんど影響を与えません。一般的なサブサンプル比率には以下のものがあります。
    *   **4:4:4**: Y, Cb, Crのすべての成分が同じ解像度を持つ。非圧縮または高品質な用途で使用されます。
    *   **4:2:2**: 輝度（Y）はフル解像度、色差（Cb, Cr）は水平方向に半分の解像度。プロフェッショナルビデオなどで使用されます。
    *   **4:2:0**: 輝度（Y）はフル解像度、色差（Cb, Cr）は水平・垂直方向ともに半分の解像度。JPEG、MPEG、DVDなどで広く使用されます。
    *   **4:4:0**: 輝度（Y）はフル解像度、色差（Cb, Cr）は垂直方向に半分の解像度。あまり一般的ではありませんが、特定の用途で使用されることがあります。

### Go言語の `image` パッケージ

Go言語の `image` パッケージは、様々な画像フォーマット（JPEG, PNG, GIFなど）の読み書きと操作をサポートします。
*   `image.Image` インターフェース: すべての画像型が実装する基本的なインターフェース。
*   `image.RGBA`: 各ピクセルがR, G, B, A（赤、緑、青、アルファ）の4バイトで表現される画像型。
*   `image.YCbCr`: YCbCr色空間の画像型。`Y`, `Cb`, `Cr` の各成分が個別のバイトスライスとして保持され、`SubsampleRatio` フィールドでサブサンプル比率が指定されます。
*   `image/color.YCbCrToRGB`: YCbCrの3つのバイト値を受け取り、対応するRGBの3つのバイト値を返す関数。

### コード生成 (Code Generation)

コード生成とは、プログラムが別のプログラムのソースコードを自動的に生成するプロセスです。このコミットでは、Goの `go generate` コマンドと `gen.go` というスクリプトを使用して、`impl.go` というファイルを生成しています。これにより、手動で記述すると冗長になりがちな、サブサンプル比率ごとの類似した処理ロジックを自動化し、保守性を高めつつ、コンパイラが最適化しやすい形式のコードを提供できます。

### インライン化 (Inlining)

インライン化とは、コンパイラ最適化の一種で、関数呼び出しをその関数の本体のコードで直接置き換えることです。これにより、関数呼び出しのオーバーヘッド（スタックフレームの作成、引数のプッシュ、戻りアドレスの保存など）が削減され、プログラムの実行速度が向上する可能性があります。特に、小さな関数がループ内で頻繁に呼び出される場合に効果的です。

## 技術的詳細

このコミットの主要な変更点は、`image/internal/imageutil` パッケージにおける `DrawYCbCr` 関数の実装方法を、手書きの `switch` 文からコード生成によるものへと移行したことです。

1.  **`gen.go` の導入**:
    *   `src/image/internal/imageutil/gen.go` という新しいファイルが追加されました。このファイルは、`go generate` コマンドによって実行されるGoプログラムです。
    *   `gen.go` は、`image.YCbCrSubsampleRatio` の各サブサンプル比率（4:4:4, 4:2:2, 4:2:0, 4:4:0）に対応する `DrawYCbCr` 関数の具体的な実装コードを文字列として保持しています。
    *   `main` 関数内で、これらの文字列を結合し、`imageutil/impl.go` というファイルに書き出します。
    *   `go/format` パッケージを使用して、生成されるコードがGoの標準的なフォーマットに従うように整形されます。

2.  **`imageutil.go` の変更**:
    *   既存の `src/image/internal/imageutil/imageutil.go` から `DrawYCbCr` 関数の実装が完全に削除されました。
    *   ファイルの先頭に `//go:generate go run gen.go` というディレクティブが追加されました。これは、`go generate` コマンドがこのファイルを見つけたときに `gen.go` を実行するように指示するものです。

3.  **`impl.go` の導入**:
    *   `src/image/internal/imageutil/impl.go` という新しいファイルが導入されました。このファイルは手動で記述されるのではなく、`gen.go` によって自動生成されます。
    *   `impl.go` には、`DrawYCbCr` 関数の実装が含まれますが、その内部の `switch` 文の各 `case` ブロックは、`gen.go` によって生成されたサブサンプル比率ごとの具体的なピクセル処理ロジックを含んでいます。これにより、各サブサンプル比率に対応するコードが独立した形で存在することになります。

この変更により、`DrawYCbCr` 関数は、`imageutil.go` からは宣言のみが残り、実際のロジックは `impl.go` に移されます。そして、`impl.go` の内容は `gen.go` によって動的に生成されるため、将来的に新しいサブサンプル比率が追加された場合でも、`gen.go` を更新するだけで対応が可能になります。

最も重要な点は、このコード生成によって、各サブサンプル比率に対応するループ内の `color.YCbCrToRGB` 呼び出しが、よりコンパイラがインライン化しやすい形になることです。例えば、4:4:4のケースでは、`ci` (Cb/Crインデックス) が `yi` (Yインデックス) と同じように単純にインクリメントされるのに対し、4:2:2や4:2:0では `sx/2` の計算が含まれるなど、サブサンプル比率によってインデックス計算ロジックが異なります。コード生成によってこれらのロジックが明示的に分離されることで、コンパイラは特定のサブサンプル比率のコードパスに対して、より積極的な最適化（特に `color.YCbCrToRGB` のインライン化）を適用できるようになります。これは、画像処理のようなパフォーマンスが重視される領域において、実行速度の向上に直結します。

### `src/image/internal/imageutil/impl.go` (新規ファイル)

このファイルは `gen.go` によって生成される `DrawYCbCr` 関数の実装を含みます。

```go
// generated by "go run gen.go". DO NOT EDIT.

package imageutil

import (
	"image"
	"image/color"
)

// DrawYCbCr draws the YCbCr source image on the RGBA destination image with
// r.Min in dst aligned with sp in src. It reports whether the draw was
// successful. If it returns false, no dst pixels were changed.
//
// This function assumes that r is entirely within dst's bounds and the
// translation of r from dst co-ordinate space to src co-ordinate space is
// entirely within src's bounds.
func DrawYCbCr(dst *image.RGBA, r image.Rectangle, src *image.YCbCr, sp image.Point) (ok bool) {
	// This function exists in the image/internal/imageutil package because it
	// is needed by both the image/draw and image/jpeg packages, but it doesn't
	// seem right for one of those two to depend on the other.
	//
	// Another option is to have this code be exported in the image package,
	// but we'd need to make sure we're totally happy with the API (for the
	// rest of Go 1 compatibility), and decide if we want to have a more
	// general purpose DrawToRGBA method for other image types. One possibility
	// is:
	//
	// func (src *YCbCr) CopyToRGBA(dst *RGBA, dr, sr Rectangle) (effectiveDr, effectiveSr Rectangle)
	//
	// in the spirit of the built-in copy function for 1-dimensional slices,
	// that also allowed a CopyFromRGBA method if needed.

	x0 := (r.Min.X - dst.Rect.Min.X) * 4
	x1 := (r.Max.X - dst.Rect.Min.X) * 4
	y0 := r.Min.Y - dst.Rect.Min.Y
	y1 := r.Max.Y - dst.Rect.Min.Y
	switch src.SubsampleRatio {

	case image.YCbCrSubsampleRatio444:
		for y, sy := y0, sp.Y; y != y1; y, sy = y+1, sy+1 {
			dpix := dst.Pix[y*dst.Stride:]
			yi := (sy-src.Rect.Min.Y)*src.YStride + (sp.X - src.Rect.Min.X)

## 前提知識の解説

### YCbCr色空間とサブサンプリング

*   **YCbCr**: YCbCrは、輝度（Y）と2つの色差（CbとCr）で色を表現する色空間です。人間の目は輝度の変化に敏感で、色の変化には比較的鈍感であるという特性を利用し、色情報を効率的に圧縮するために使用されます。
*   **サブサンプリング**: YCbCrデータにおいて、色差成分（CbとCr）の解像度を輝度成分（Y）よりも低くする技術です。これにより、データ量を削減しつつ、人間の視覚にはほとんど影響を与えません。一般的なサブサンプル比率には以下のものがあります。
    *   **4:4:4**: Y, Cb, Crのすべての成分が同じ解像度を持つ。非圧縮または高品質な用途で使用されます。
    *   **4:2:2**: 輝度（Y）はフル解像度、色差（Cb, Cr）は水平方向に半分の解像度。プロフェッショナルビデオなどで使用されます。
    *   **4:2:0**: 輝度（Y）はフル解像度、色差（Cb, Cr）は水平・垂直方向ともに半分の解像度。JPEG、MPEG、DVDなどで広く使用されます。
    *   **4:4:0**: 輝度（Y）はフル解像度、色差（Cb, Cr）は垂直方向に半分の解像度。あまり一般的ではありませんが、特定の用途で使用されることがあります。

### Go言語の `image` パッケージ

Go言語の `image` パッケージは、様々な画像フォーマット（JPEG, PNG, GIFなど）の読み書きと操作をサポートします。
*   `image.Image` インターフェース: すべての画像型が実装する基本的なインターフェース。
*   `image.RGBA`: 各ピクセルがR, G, B, A（赤、緑、青、アルファ）の4バイトで表現される画像型。
*   `image.YCbCr`: YCbCr色空間の画像型。`Y`, `Cb`, `Cr` の各成分が個別のバイトスライスとして保持され、`SubsampleRatio` フィールドでサブサンプル比率が指定されます。
*   `image/color.YCbCrToRGB`: YCbCrの3つのバイト値を受け取り、対応するRGBの3つのバイト値を返す関数。

import (
	"image"
	"image/color"
)

// DrawYCbCr draws the YCbCr source image on the RGBA destination image with
// r.Min in dst aligned with sp in src. It reports whether the draw was
// successful. If it returns false, no dst pixels were changed.
//
// This function assumes that r is entirely within dst's bounds and the
// translation of r from dst co-ordinate space to src co-ordinate space is
// entirely within src's bounds.
func DrawYCbCr(dst *image.RGBA, r image.Rectangle, src *image.YCbCr, sp image.Point) (ok bool) {
	// This function exists in the image/internal/imageutil package because it
	// is needed by both the image/draw and image/jpeg packages, but it doesn't
	// seem right for one of those two to depend on the other.
	//
	// Another option is to have this code be exported in the image package,
	// but we'd need to make sure we're totally happy with the API (for the
	// rest of Go 1 compatibility), and decide if we want to have a more
	// general purpose DrawToRGBA method for other image types. One possibility
	// is:
	//
	// func (src *YCbCr) CopyToRGBA(dst *RGBA, dr, sr Rectangle) (effectiveDr, effectiveSr Rectangle)
	//
	// in the spirit of the built-in copy function for 1-dimensional slices,
	// that also allowed a CopyFromRGBA method if needed.

	x0 := (r.Min.X - dst.Rect.Min.X) * 4
	x1 := (r.Max.X - dst.Rect.Min.X) * 4
	y0 := r.Min.Y - dst.Rect.Min.Y
	y1 := r.Max.Y - dst.Rect.Min.Y
	switch src.SubsampleRatio {

	case image.YCbCrSubsampleRatio444:
		for y, sy := y0, sp.Y; y != y1; y, sy = y+1, sy+1 {
			dpix := dst.Pix[y*dst.Stride:]
			yi := (sy-src.Rect.Min.Y)*src.YStride + (sp.X - src.Rect.Min.X)

			ci := (sy-src.Rect.Min.Y)*src.CStride + (sp.X - src.Rect.Min.X)
			for x := x0; x != x1; x, yi, ci = x+4, yi+1, ci+1 {

				rr, gg, bb := color.YCbCrToRGB(src.Y[yi], src.Cb[ci], src.Cr[ci])
				dpix[x+0] = rr
				dpix[x+1] = gg
				dpix[x+2] = bb
				dpix[x+3] = 255
			}
		}

	case image.YCbCrSubsampleRatio422:

			dpix := dst.Pix[y*dst.Stride:]
			yi := (sy-src.Rect.Min.Y)*src.YStride + (sp.X - src.Rect.Min.X)

## コアとなるコードの解説

このコミットの核心は、`DrawYCbCr` 関数の実装を、手動で記述された単一の関数から、`gen.go` によって生成される複数のサブサンプル比率に特化したコードブロックを持つ関数へと変更した点にあります。

以前の `imageutil.go` にあった `DrawYCbCr` 関数は、`switch src.SubsampleRatio` 文を使って、4:4:4, 4:2:2, 4:2:0, 4:4:0 の各サブサンプル比率に対応する処理を一つの関数内に記述していました。各 `case` ブロック内では、YCbCrからRGBへの変換を行う `color.YCbCrToRGB` 関数がピクセルごとに呼び出されていました。

新しいアプローチでは、`gen.go` が `impl.go` を生成します。`impl.go` 内の `DrawYCbCr` 関数は、見た目上は以前と同じ `switch` 文を持っていますが、各 `case` ブロックの内部ループの構造が、`gen.go` の `sratioLines` マップに定義された文字列によって動的に挿入されます。

例えば、`image.YCbCrSubsampleRatio444` の場合、`gen.go` は `sratioLines["444"]` の内容を挿入します。
```go
		ci := (sy-src.Rect.Min.Y)*src.CStride + (sp.X - src.Rect.Min.X)
		for x := x0; x != x1; x, yi, ci = x+4, yi+1, ci+1 {
```
このコードは、4:4:4のサブサンプリング（CbとCrがYと同じ解像度を持つ）に対応した `ci` (Cb/Crインデックス) の計算と、ループ変数の更新ロジックを定義しています。

一方、`image.YCbCrSubsampleRatio420` の場合、`gen.go` は `sratioLines["420"]` の内容を挿入します。
```go
		ciBase := (sy/2-src.Rect.Min.Y/2)*src.CStride - src.Rect.Min.X/2
		for x, sx := x0, sp.X; x != x1; x, sx, yi = x+4, sx+1, yi+1 {
			ci := ciBase + sx/2
```
このコードは、4:2:0のサブサンプリング（CbとCrが水平・垂直ともに半分の解像度を持つ）に対応した `ci` の計算ロジックを含んでいます。特に `sy/2` や `sx/2` といった計算が含まれており、Cb/CrのインデックスがYとは異なるペースで進むことを反映しています。

このように、各サブサンプル比率に特化したインデックス計算ロジックが、コード生成によってそれぞれの `case` ブロック内に直接埋め込まれることで、コンパイラはより具体的なコンテキストで `color.YCbCrToRGB` の呼び出しを分析できるようになります。これにより、コンパイラは関数呼び出しのオーバーヘッドを排除するために `color.YCbCrToRGB` をインライン化する機会を増やし、結果として画像描画処理のパフォーマンスが向上することが期待されます。

この変更は、Goの画像処理ライブラリにおけるパフォーマンス最適化の一環であり、特に画像デコードや変換のような計算負荷の高い処理において、細粒度な最適化を可能にするための基盤を築いています。

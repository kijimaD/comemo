# [インデックス 26856] ファイルの概要

このコミットは、Go言語のリンカ (`cmd/link`) におけるシンボル名の読み込み処理を最適化し、不要なメモリ割り当てを削減することで、リンク時間の短縮を図るものです。具体的には、シンボル名に含まれるパッケージパスの展開処理において、`[]byte` スライス上での直接操作を導入し、`string` への変換と部分文字列置換を繰り返すことによるオーバーヘッドを排除しています。

## 元コミット内容

`cmd/link: skip allocation when reading symbol name`

`cmd/link` のオブジェクトファイルリーダーは、シンボル名を一時的な `[]byte` に読み込み、それを `string` に変換した後、部分文字列の置換を行っていました。この変更では、代わりに `[]byte` 上で直接置換処理を行い、その後で最終的な `string` を生成するようにしました。

この最適化により、DWARFデバッグ情報なしで `godoc` をリンクした場合、10回の試行で約10%の性能向上が見られました。

*   変更前 (`tip`): real 0m1.099s user 0m1.541s
*   変更後 (`this`): real 0m0.990s user 0m1.280s

この変更は、`suffixarray` の文字列重複排除処理のコストを相殺しようとする試みの一部ですが、まだその目標には達していません。

*   `cl/19987` (関連する変更): real 0m1.335s user 0m1.794s
*   `cl/19987` + この変更: real 0m1.225s user 0m1.540s

## 変更の背景

Go言語のリンカ (`cmd/link`) は、コンパイルされたオブジェクトファイル群を結合して実行可能ファイルを生成する重要なツールです。このプロセスでは、多数のシンボル（関数名、変数名など）を処理する必要があります。シンボル名には、Goのパッケージパス情報が含まれることが多く、リンカはこれらのシンボル名を適切に解決・展開する必要があります。

従来のリンカのシンボル名読み込み処理では、以下の非効率なステップが含まれていました。

1.  オブジェクトファイルからシンボル名を `[]byte` スライスとして読み込む。
2.  その `[]byte` を `string` に変換する。
3.  `string` に対して、パッケージパスの展開（例: `"".` を実際のパッケージ名に置換）を行う。この置換処理は、新しい `string` を生成するため、追加のメモリ割り当てとコピーを伴います。
4.  置換後の `string` を使用する。

この一連の処理は、特にシンボル数が多い大規模なプロジェクトのリンク時に、頻繁なメモリ割り当てとデータコピーを引き起こし、リンカの実行時間を増加させる原因となっていました。Goのランタイム開発チームは、ビルド時間の短縮を常に目標としており、このようなホットパスにおける非効率性の解消は重要な課題でした。

このコミットは、`suffixarray` を用いた文字列重複排除の取り組みと関連しており、リンカ全体の性能改善の一環として位置づけられています。`suffixarray` は文字列の重複を効率的に検出・排除するためのデータ構造ですが、その導入によって発生する可能性のあるオーバーヘッドを、他の部分の最適化で相殺しようという意図がありました。

## 前提知識の解説

### Go言語のリンカ (`cmd/link`)

`cmd/link` は、Goツールチェーンの一部であり、Goプログラムのビルドプロセスにおいて、コンパイラによって生成されたオブジェクトファイル（`.o` ファイル）を結合し、最終的な実行可能ファイルやライブラリを生成する役割を担います。この過程で、各オブジェクトファイルが定義・参照するシンボル（関数、変数など）を解決し、アドレスを割り当て、必要に応じてコードを再配置します。

### シンボル名とパッケージパス

Go言語では、関数や変数はパッケージに属します。リンカが処理するシンボル名には、そのシンボルがどのパッケージに属するかを示す情報が含まれることがあります。例えば、`main` パッケージの `main` 関数は `main.main` のように表現されます。しかし、オブジェクトファイル内部では、匿名パッケージやインポートされたパッケージのシンボル名が `"".` のようなプレースホルダーを含む形式で表現されることがあります。リンカはこれを実際のパッケージ名に展開する必要があります。

### `[]byte` と `string` の関係

Go言語において、`[]byte` (バイトスライス) と `string` (文字列) は密接に関連していますが、異なる特性を持ちます。

*   **`string`**: 不変 (immutable) なバイト列です。一度作成されると内容を変更できません。文字列操作（結合、部分文字列抽出、置換など）を行うと、多くの場合、新しい `string` がヒープに割り当てられ、データがコピーされます。
*   **`[]byte`**: 可変 (mutable) なバイト列です。内容を変更できます。バイトスライスに対する操作は、既存のメモリ領域を再利用したり、必要に応じて拡張したりすることができます。

性能が重要な場面では、特に頻繁な操作が予想される場合、`string` への変換を最小限に抑え、`[]byte` 上で直接処理を行うことが推奨されます。これは、不要なメモリ割り当て（ヒープアロケーション）とガベージコレクションの負荷を減らすためです。

### メモリ割り当てとガベージコレクション

プログラムが実行中にメモリを要求すると、システムはメモリ領域を割り当てます（アロケーション）。Goでは、ヒープ領域に割り当てられたオブジェクトはガベージコレクタ (GC) の管理下に置かれます。不要になったオブジェクトはGCによって回収されますが、GC自体もCPU時間とメモリリソースを消費します。したがって、不要なメモリ割り当てを減らすことは、GCの頻度と負荷を軽減し、プログラムの実行性能を向上させる上で非常に効果的です。

### DWARFデバッグ情報

DWARF (Debugging With Attributed Record Formats) は、コンパイルされたプログラムのソースコードレベルでのデバッグを可能にするための標準的なデバッグ情報フォーマットです。実行可能ファイルにDWARF情報を含めると、ファイルサイズが大きくなり、リンク時間も増加する傾向があります。このコミットの性能測定では、DWARFなしのビルドで比較が行われており、これはデバッグ情報の生成・処理による影響を排除し、純粋なシンボル処理の改善効果を測定するためと考えられます。

## 技術的詳細

このコミットの核心は、`src/cmd/link/internal/ld/objfile.go` 内の `readsym` 関数と、新たに導入された `rdsymName` 関数の変更にあります。

### 変更前の処理フロー

変更前は、`readsym` 関数内でシンボル名を読み込む際に、`expandpkg(rdstring(f), pkg)` という呼び出しが行われていました。

1.  `rdstring(f)`: オブジェクトファイルからシンボル名のバイト列を読み込み、`make([]byte, n)` で新しいバイトスライスを割り当て、そこにデータをコピーし、最終的に `string(p)` で新しい `string` を生成していました。
2.  `expandpkg(p, pkg)`: この `string` を引数に取り、`"".` のようなプレースホルダーを実際のパッケージ名 `pkg` に置換する処理を行っていました。この置換処理も、内部で新しい `string` を生成する可能性が高いです。

このように、シンボル名を読み込むたびに、少なくとも2回（`rdstring` 内と `expandpkg` 内）の `string` 生成とそれに伴うメモリ割り当てが発生していました。

### 変更後の処理フロー

このコミットでは、`readsym` 関数が `rdsymName(f, pkg)` を呼び出すように変更されました。`rdsymName` 関数は以下の最適化を行います。

1.  **`rdBuf` の再利用**: `rdBuf` というグローバルな `[]byte` スライスを導入し、これをシンボル名を読み込むための一時バッファとして再利用します。これにより、`rdstring` 関数内で毎回 `make([]byte, n)` を呼び出すことによるメモリ割り当てを回避します。`len(rdBuf) < n` の場合にのみ、バッファを拡張または再割り当てします。
2.  **`[]byte` 上での直接置換**: `rdsymName` 関数は、まずシンボル名のバイト列を `rdBuf` に読み込みます (`origName`)。次に、`bytes.Index` を使用して `emptyPkg` (`"".`) の出現箇所を検索します。
3.  **`adjName` の構築**: `emptyPkg` が見つかるたびに、`origName` の該当部分をスキップし、代わりに実際のパッケージ名 `pkg` のバイト列を `adjName` という別の `[]byte` スライスに `append` します。この `adjName` も `rdBuf` の既存の容量を利用するか、必要に応じて拡張されます。
4.  **最終 `string` の生成**: 全ての置換処理が `[]byte` スライス上で行われた後、最後に `string(adjName)` を呼び出して、一度だけ最終的な `string` を生成します。

この変更により、シンボル名処理における `string` の中間生成とそれに伴うメモリ割り当てが大幅に削減され、ガベージコレクションの負荷が軽減されます。結果として、リンカの実行速度が向上します。

### 性能測定

コミットメッセージに記載されている性能測定結果は、この最適化の効果を明確に示しています。

*   `godoc` のリンク時間（DWARFなし）で約10%の改善。
*   `real` 時間（壁時計時間）と `user` 時間（ユーザーモードCPU時間）の両方で短縮が見られます。これは、メモリ割り当ての削減がCPU使用率とI/O待機時間の両方に良い影響を与えたことを示唆しています。

また、`suffixarray` の文字列重複排除との関連性も言及されており、この最適化がより広範な性能改善戦略の一部であることがわかります。

## コアとなるコードの解説

### `readsym` 関数の変更点

*   変更前: `name := expandpkg(rdstring(f), pkg)`
    *   `rdstring(f)` でシンボル名を `string` として読み込み、新しいメモリを割り当てていました。
    *   その `string` を `expandpkg` に渡し、パッケージ名の展開を行っていました。ここでも新しい `string` が生成される可能性がありました。
*   変更後: `name := rdsymName(f, pkg)`
    *   `rdsymName` という新しい関数を導入し、シンボル名の読み込みとパッケージ名の展開を `[]byte` 上で効率的に行うようにしました。
    *   `rdsym(ctxt *Link, f *obj.Biobuf, pkg string) *LSym` 関数も、`expandpkg(p, pkg)` の代わりに `name` を直接使用するように変更されています。

### `rdstring` 関数の変更点

*   `rdBuf` というグローバルな `[]byte` スライスが導入されました。これは `rdstring` と `rdsymName` の両方でスクラッチバッファとして再利用されます。
*   変更前は `make([]byte, n)` で毎回新しいバイトスライスを割り当てていましたが、変更後は `len(rdBuf) < n` の場合にのみ `rdBuf` を拡張または再割り当てします。これにより、`rdstring` が呼び出されるたびに発生していたメモリ割り当てが大幅に削減されます。

### `rdsymName` 関数の新規追加と詳細

この関数は、シンボル名の読み込みと `"".` から `pkg` への置換処理を効率的に行うためのものです。

1.  `n := rdint(f)`: シンボル名の長さを読み込みます。
2.  `if n == 0`: 長さが0の場合は空文字列を返します。
3.  `if len(rdBuf) < n`: グローバルバッファ `rdBuf` の容量が不足している場合、`make([]byte, n, 2*n)` で新しいバッファを割り当てます。`2*n` は、置換によって文字列が長くなる可能性を考慮した容量です。
4.  `origName := rdBuf[:n]`: `rdBuf` の先頭から `n` バイトを `origName` としてスライスします。
5.  `obj.Bread(f, origName)`: オブジェクトファイルからシンボル名のバイト列を `origName` (実体は `rdBuf` の一部) に直接読み込みます。
6.  `adjName := rdBuf[n:n]`: `rdBuf` の `n` バイト目から始まる空のバイトスライス `adjName` を作成します。これは置換後のシンボル名を構築するためのバッファとして機能します。
7.  `for` ループと `bytes.Index`、`append` による置換処理:
    *   `bytes.Index(origName, emptyPkg)` で `origName` 内の `emptyPkg` (`"".`) の位置を検索します。
    *   `emptyPkg` が見つからなくなるまでループを繰り返します。
    *   見つかった場合、`origName` の `emptyPkg` までの部分を `adjName` に `append` します。
    *   次に、実際のパッケージ名 `pkg` と `.` のバイト列を `adjName` に `append` します。
    *   `origName` を `emptyPkg` の後から始まるように更新し、次の置換箇所を探します。
    *   この処理は全て `[]byte` スライス上で行われ、`append` 操作は `rdBuf` の既存の容量を最大限に活用します。
8.  `name := string(adjName)`: 全ての置換が完了した後、`adjName` (最終的なバイトスライス) を一度だけ `string` に変換します。
9.  `if len(adjName) > len(rdBuf)`: もし置換後の `adjName` が `rdBuf` の元の容量よりも大きくなった場合、その `adjName` を新しい `rdBuf` として保存し、次回以降の呼び出しでより大きなバッファを再利用できるようにします。

この一連の処理により、シンボル名の読み込みからパッケージ名の展開まで、ほとんどの操作が `[]byte` 上で行われ、`string` の生成とメモリ割り当てが最小限に抑えられています。

## 変更の背景

Goランタイムのガベージコレクション（GC）は、並行処理をサポートするために複雑なメカニズムを採用しています。その中でもライトバリアは、GCがヒープをスキャンしている最中にミューテータ（ユーザープログラム）がポインタを書き換えることによって発生するオブジェクトグラフの不整合を防ぐための重要な要素です。

このコミットが行われた2015年当時、GoのGCは進化の途上にあり、特に並行GCの効率と正確性を高めるための改善が活発に行われていました。ライトバリア関連のコードは、`src/runtime/mgc.go`や`src/runtime/mgc0.go`、`src/runtime/malloc1.go`など、複数のファイルに分散して存在していました。

このようなコードの分散は、ライトバリアのロジックを理解し、保守する上で課題となっていました。このコミットの主な目的は、ライトバリアに関するすべてのコード（GCのコアロジック、ポインタの書き換え処理、デバッグ用のシャドウヒープなど）を`src/runtime/mbarrier.go`という単一のファイルに集約し、コードベースの整理とモジュール化を進めることでした。これにより、ライトバリアの全体像を把握しやすくなり、将来的なGCの改善やデバッグ作業が容易になることが期待されました。

## 前提知識の解説

### Goのガベージコレクション（GC）の基本

GoのGCは、主に**三色マーキング（Tri-color Marking）**アルゴリズムと**並行（Concurrent）GC**を組み合わせています。

*   **三色マーキング**: オブジェクトを以下の3つの色で分類します。
    *   **白（White）**: GCによってまだ発見されていないオブジェクト。最終的に回収される可能性がある。
    *   **灰（Gray）**: GCによって発見されたが、そのオブジェクトが参照する他のオブジェクトはまだスキャンされていない状態。
    *   **黒（Black）**: GCによって発見され、そのオブジェクトが参照するすべてのオブジェクトもスキャン済みである状態。黒オブジェクトは回収されない。
*   **並行GC**: GCのマーキングフェーズの大部分を、ユーザープログラム（ミューテータ）と並行して実行します。これにより、GCによるアプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑えます。

### ライトバリア（Write Barrier）の役割と必要性

並行GCにおいて、ミューテータがヒープ上のポインタを書き換えることは、GCの正確性を脅かす可能性があります。例えば、GCがまだスキャンしていない白いオブジェクトへの参照を、既にスキャン済みの黒いオブジェクトが持つように変更してしまうと、その白いオブジェクトはGCによって到達不可能と判断され、誤って回収されてしまう可能性があります。

これを防ぐために導入されるのが**ライトバリア**です。ライトバリアは、ヒープ上のポインタが書き換えられる際に自動的に実行される小さなコードスニペットです。その目的は、GCの三色不変条件（特に「黒オブジェクトは白いオブジェクトを参照してはならない」という条件）を維持することです。

GoのGCは、**ハイブリッドライトバリア**を採用しています。これは、主に以下の2つのバリアを組み合わせたものです。

1.  **Dijkstra挿入バリア（Dijkstra Insertion Barrier）**: 新しくポインタが指すオブジェクト（`src`）を灰色にマークします。これにより、黒オブジェクトが白いオブジェクトを指すことを防ぎます。このコミットで移動された`gcmarkwb_m`関数がこれに該当します。
2.  **Yuasa削除バリア（Yuasa Deletion Barrier）**: ポインタが指していた元のオブジェクト（`dst`が以前指していたオブジェクト）を灰色にマークします。

このコミットは、特にDijkstra挿入バリアの実装と、それに関連するコードの整理に焦点を当てています。

### シャドウヒープ（wbshadow）の目的

コミットメッセージやコード内で言及されている「シャドウヒープ」は、GoのGCのコアアルゴリズムの一部ではありません。これは、ライトバリアが正しく機能しているか、つまり「ライトバリアの漏れ（missed write barrier）」がないかをデバッグするために使用される特別なメカニズムです。

`GODEBUG=wbshadow=1`という環境変数を設定すると、Goランタイムは通常のヒープに加えて、そのコピーであるシャドウヒープを確保します。ポインタの書き換えが発生するたびに、ライトバリアは通常のヒープとシャドウヒープの両方に変更を適用します。GCのチェックマークフェーズなどで、両方のヒープの内容を比較し、不整合があればライトバリアの漏れとして検出され、プログラムがクラッシュします。これにより、開発者はライトバリアの実装ミスや、コンパイラがライトバリアを挿入し忘れた箇所を特定できます。

### `src/runtime/mbarrier.go` の新設と役割

`mbarrier.go`は、Goランタイムにおけるライトバリアの主要な実装と、それに関連するヘルパー関数、そしてデバッグ用のシャドウヒープ機能を集約したファイルです。このファイルには、以下の主要な機能が含まれています。

*   **`gcmarkwb_m`**: Dijkstra挿入バリアのコアロジックを実装しています。これは、ポインタが書き換えられる際に、新しく参照されるオブジェクト（`ptr`）がヒープ内に存在し、かつGCのマーキングフェーズ中であれば、そのオブジェクトを灰色にマーク（`shade`）します。これにより、GCがそのオブジェクトをスキャンし、到達可能なオブジェクトとして認識することを保証します。
*   **`needwb`**: 現在のGCフェーズに基づいて、ライトバリアが必要かどうかを判断する関数です。GCのマーキングフェーズ中、またはシャドウヒープが有効な場合に`true`を返します。
*   **`writebarrierptr`**: 単一のポインタ書き換えに対するライトバリアを実装します。`needwb`が`true`の場合に`gcmarkwb_m`を呼び出し、必要に応じてシャドウヒープの更新も行います。
*   **`writebarrierptr_nostore`**: ポインタのストア（書き込み）が既に完了している場合に呼び出されるライトバリアです。主に`reflect`パッケージからの呼び出しなど、特殊なケースで使用されます。シャドウヒープの更新は行いますが、`gcmarkwb_m`の呼び出しは`writebarrierptr_nostore1`を通じて行われます。
*   **`writebarrierptr_noshadow`**: アトミック操作などでポインタが書き換えられ、シャドウヒープの更新ができない場合に、シャドウヒープに`noShadow`（特別な値）を記録する関数です。
*   **`writebarrierstring`, `writebarrierslice`, `writebarrieriface`**: 文字列、スライス、インターフェースといった複合型のポインタフィールドの書き換えに対応するライトバリア関数です。これらは内部的に`writebarrierptr`を呼び出します。
*   **`typedmemmove`, `typedslicecopy`**: 型情報に基づいてメモリをコピーする際に、ポインタフィールドに対して適切にライトバリアを適用する関数です。これにより、構造体や配列、スライスなどの一括コピーにおいてもGCの不変条件が維持されます。
*   **シャドウヒープ関連関数**:
    *   **`wbshadowinit`**: シャドウヒープを初期化します。`GODEBUG=wbshadow=1`が設定され、かつ64ビットシステムである場合に、通常のヒープのコピーをメモリ上に確保します。
    *   **`shadowptr`**: 指定されたアドレスに対応するシャドウヒープ上のアドレスを返します。
    *   **`checkwbshadow`**: GCのチェックマークフェーズ中に呼び出され、通常のヒープとシャドウヒープの内容を比較し、ライトバリアの漏れがないかを確認します。不整合があればパニックを引き起こします。
    *   **`clearshadow`**: 指定されたメモリ範囲のシャドウヒープをクリアします。

### `gcmarkwb_m`におけるDijkstraバリアの「粗粒化（coarsened）」

`mbarrier.go`のコメントには、「This is the Dijkstra barrier coarsened to always shade the ptr (dst) object. The original Dijkstra barrier only shaded ptrs being placed in black slots.」とあります。

これは、Dijkstraの元の挿入バリアが「黒いスロットに白いポインタが挿入される場合のみバリアを適用する」という条件を持っていたのに対し、Goの実装では「ポインタが指すオブジェクト（`ptr`）を常に灰色にシェードする」という、より単純で広範なルールを採用していることを意味します。

この「粗粒化」の背景には、元のDijkstraバリアの条件を厳密に実装しようとすると、ミューテータとGCスレッド間のメモリバリア（memory barrier）の挿入が必要となり、これがパフォーマンス上のオーバーヘッドとなるという考慮があります。特に、IRIW（Independent Reads of Independent Writes）のようなメモリ順序の問題を避けるために、高価なメモリバリアを挿入するよりも、常にポインタが指すオブジェクトを灰色にする方が、実装が単純で、かつ実用的なパフォーマンスが得られると判断されたためです。これにより、GCの正確性を維持しつつ、複雑性を低減しています。

## コアとなるコードの解説

このコミットのコアとなるコードは、`src/runtime/mbarrier.go`に集約されたライトバリア関連の関数群です。

### `gcmarkwb_m`

```go
//go:nowritebarrier
func gcmarkwb_m(slot *uintptr, ptr uintptr) {
	switch gcphase {
	default:
		throw("gcphasework in bad gcphase")

	case _GCoff, _GCquiesce, _GCstw, _GCsweep, _GCscan:
		// ok

	case _GCmark, _GCmarktermination:
		if ptr != 0 && inheap(ptr) {
			shade(ptr)
		}
	}
}
```
この関数は、Dijkstra挿入バリアの核となる部分です。`slot`は書き換えられるポインタの格納先、`ptr`は新しく書き込まれるポインタの値です。
`gcphase`が`_GCmark`または`_GCmarktermination`（GCのマーキングフェーズ）である場合に、`ptr`が`nil`でなく、かつヒープ内のオブジェクトを指している（`inheap(ptr)`）ならば、`shade(ptr)`を呼び出してそのオブジェクトを灰色にマークします。これにより、新しく参照されたオブジェクトがGCによって確実にスキャンされるようになります。`//go:nowritebarrier`ディレクティブは、この関数自体がライトバリアの対象とならないことを示します。

### `writebarrierptr`

```go
//go:nosplit
func writebarrierptr(dst *uintptr, src uintptr) {
	if !needwb() {
		*dst = src
		return
	}

	// ... シャドウヒープ関連の処理 ...

	*dst = src
	writebarrierptr_nostore1(dst, src)
}
```
この関数は、Goコンパイラによって生成され、単一のポインタが書き換えられる際に呼び出されます。`needwb()`が`true`（ライトバリアが必要な状態）の場合に、シャドウヒープの更新（デバッグモードの場合）と、`writebarrierptr_nostore1`を介した`gcmarkwb_m`の呼び出しを行います。`*dst = src`という実際のストア操作は、ライトバリアのロジックの前後で行われます。

### シャドウヒープ関連の関数 (`wbshadowinit`, `shadowptr`, `checkwbshadow`)

これらの関数は、ライトバリアのデバッグと検証のために重要です。
*   `wbshadowinit`は、`GODEBUG=wbshadow=1`が設定されている場合に、通常のヒープのミラーコピーであるシャドウヒープを初期化します。
*   `shadowptr`は、与えられたヒープアドレスに対応するシャドウヒープ上のアドレスを計算します。
*   `checkwbshadow`は、GCのチェックマークフェーズ中に呼び出され、通常のヒープとシャドウヒープの内容を比較します。もし不整合があれば、それはライトバリアの漏れを示唆し、`throw("missed write barrier")`によってプログラムがクラッシュします。これは、開発者がライトバリアのバグを特定するのに役立ちます。

これらのコードが`mbarrier.go`に集約されたことで、GoランタイムのGCサブシステムにおけるライトバリアの役割と実装がより明確になり、開発者がGCの動作を理解し、デバッグする上での利便性が向上しました。

    *   **白（White）**: GCによってまだ発見されていないオブジェクト。最終的に回収される可能性がある。
    *   **灰（Gray）**: GCによって発見されたが、そのオブジェクトが参照する他のオブジェクトはまだスキャンされていない状態。
    *   **黒（Black）**: GCによって発見され、そのオブジェクトが参照するすべてのオブジェクトもスキャン済みである状態。黒オブジェクトは回収されない。
*   **並行GC**: GCのマーキングフェーズの大部分を、ユーザープログラム（ミューテータ）と並行して実行します。これにより、GCによるアプリケーションの一時停止（Stop-The-World: STW）時間を最小限に抑えます。

### ライトバリア（Write Barrier）の役割と必要性

並行GCにおいて、ミューテータがヒープ上のポインタを書き換えることは、GCの正確性を脅かす可能性があります。例えば、GCがまだスキャンしていない白いオブジェクトへの参照を、既にスキャン済みの黒いオブジェクトが持つように変更してしまうと、その白いオブジェクトはGCによって到達不可能と判断され、誤って回収されてしまう可能性があります。

これを防ぐために導入されるのが**ライトバリア**です。ライトバリアは、ヒープ上のポインタが書き換えられる際に自動的に実行される小さなコードスニペットです。その目的は、GCの三色不変条件（特に「黒オブジェクトは白いオブジェクトを参照してはならない」という条件）を維持することです。

GoのGCは、**ハイブリッドライトバリア**を採用しています。これは、主に以下の2つのバリアを組み合わせたものです。

1.  **Dijkstra挿入バリア（Dijkstra Insertion Barrier）**: 新しくポインタが指すオブジェクト（`src`）を灰色にマークします。これにより、黒オブジェクトが白いオブジェクトを指すことを防ぎます。このコミットで移動された`gcmarkwb_m`関数がこれに該当します。
2.  **Yuasa削除バリア（Yuasa Deletion Barrier）**: ポインタが指していた元のオブジェクト（`dst`が以前指していたオブジェクト）を灰色にマークします。

このコミットは、特にDijkstra挿入バリアの実装と、それに関連するコードの整理に焦点を当てています。

### シャドウヒープ（wbshadow）の目的

コミットメッセージやコード内で言及されている「シャドウヒープ」は、GoのGCのコアアルゴリズムの一部ではありません。これは、ライトバリアが正しく機能しているか、つまり「ライトバリアの漏れ（missed write barrier）」がないかをデバッグするために使用される特別なメカニズムです。

`GODEBUG=wbshadow=1`という環境変数を設定すると、Goランタイムは通常のヒープに加えて、そのコピーであるシャドウヒープを確保します。ポインタの書き換えが発生するたびに、ライトバリアは通常のヒープとシャドウヒープの両方に変更を適用します。GCのチェックマークフェーズなどで、両方のヒープの内容を比較し、不整合があればライトバリアの漏れとして検出され、プログラムがクラッシュします。これにより、開発者はライトバリアの実装ミスや、コンパイラがライトバリアを挿入し忘れた箇所を特定できます。

### `src/runtime/mbarrier.go` の新設と役割

`mbarrier.go`は、Goランタイムにおけるライトバリアの主要な実装と、それに関連するヘルパー関数、そしてデバッグ用のシャドウヒープ機能を集約したファイルです。このファイルには、以下の主要な機能が含まれています。

*   **`gcmarkwb_m`**: Dijkstra挿入バリアのコアロジックを実装しています。これは、ポインタが書き換えられる際に、新しく参照されるオブジェクト（`ptr`）がヒープ内に存在し、かつGCのマーキングフェーズ中であれば、そのオブジェクトを灰色にマーク（`shade`）します。これにより、新しく参照されたオブジェクトがGCによって確実にスキャンされることを保証します。
*   **`needwb`**: 現在のGCフェーズに基づいて、ライトバリアが必要かどうかを判断する関数です。GCのマーキングフェーズ中、またはシャドウヒープが有効な場合に`true`を返します。
*   **`writebarrierptr`**: 単一のポインタ書き換えに対するライトバリアを実装します。`needwb`が`true`の場合に`gcmarkwb_m`を呼び出し、必要に応じてシャドウヒープの更新も行います。
*   **`writebarrierptr_nostore`**: ポインタのストア（書き込み）が既に完了している場合に呼び出されるライトバリアです。主に`reflect`パッケージからの呼び出しなど、特殊なケースで使用されます。シャドウヒープの更新は行いますが、`gcmarkwb_m`の呼び出しは`writebarrierptr_nostore1`を通じて行われます。
*   **`writebarrierptr_noshadow`**: アトミック操作などでポインタが書き換えられ、シャドウヒープの更新ができない場合に、シャドウヒープに`noShadow`（特別な値）を記録する関数です。
*   **`writebarrierstring`, `writebarrierslice`, `writebarrieriface`**: 文字列、スライス、インターフェースといった複合型のポインタフィールドの書き換えに対応するライトバリア関数です。これらは内部的に`writebarrierptr`を呼び出します。
*   **`typedmemmove`, `typedslicecopy`**: 型情報に基づいてメモリをコピーする際に、ポインタフィールドに対して適切にライトバリアを適用する関数です。これにより、構造体や配列、スライスなどの一括コピーにおいてもGCの不変条件が維持されます。
*   **シャドウヒープ関連関数**:
    *   **`wbshadowinit`**: シャドウヒープを初期化します。`GODEBUG=wbshadow=1`が設定され、かつ64ビットシステムである場合に、通常のヒープのコピーをメモリ上に確保します。
    *   **`shadowptr`**: 指定されたアドレスに対応するシャドウヒープ上のアドレスを返します。
    *   **`checkwbshadow`**: GCのチェックマークフェーズ中に呼び出され、通常のヒープとシャドウヒープの内容を比較し、ライトバリアの漏れがないかを確認します。不整合があればパニックを引き起こします。
    *   **`clearshadow`**: 指定されたメモリ範囲のシャドウヒープをクリアします。

### `gcmarkwb_m`におけるDijkstraバリアの「粗粒化（coarsened）」

`mbarrier.go`のコメントには、「This is the Dijkstra barrier coarsened to always shade the ptr (dst) object. The original Dijkstra barrier only shaded ptrs being placed in black slots.」とあります。

これは、Dijkstraの元の挿入バリアが「黒いスロットに白いポインタが挿入される場合のみバリアを適用する」という条件を持っていたのに対し、Goの実装では「ポインタが指すオブジェクト（`ptr`）を常に灰色にシェードする」という、より単純で広範なルールを採用していることを意味します。

この「粗粒化」の背景には、元のDijkstraバリアの条件を厳密に実装しようとすると、ミューテータとGCスレッド間のメモリバリア（memory barrier）の挿入が必要となり、これがパフォーマンス上のオーバーヘッドとなるという考慮があります。特に、IRIW（Independent Reads of Independent Writes）のようなメモリ順序の問題を避けるために、高価なメモリバリアを挿入するよりも、常にポインタが指すオブジェクトを灰色にする方が、実装が単純で、かつ実用的なパフォーマンスが得られると判断されたためです。これにより、GCの正確性を維持しつつ、複雑性を低減しています。

## コアとなるコードの解説

このコミットのコアとなるコードは、`src/runtime/mbarrier.go`に集約されたライトバリア関連の関数群です。

### `gcmarkwb_m`

```go
//go:nowritebarrier
func gcmarkwb_m(slot *uintptr, ptr uintptr) {
	switch gcphase {
	default:
		throw("gcphasework in bad gcphase")

	case _GCoff, _GCquiesce, _GCstw, _GCsweep, _GCscan:
		// ok

	case _GCmark, _GCmarktermination:
		if ptr != 0 && inheap(ptr) {
			shade(ptr)
		}
	}
}
```
この関数は、Dijkstra挿入バリアの核となる部分です。`slot`は書き換えられるポインタの格納先、`ptr`は新しく書き込まれるポインタの値です。
`gcphase`が`_GCmark`または`_GCmarktermination`（GCのマーキングフェーズ）である場合に、`ptr`が`nil`でなく、かつヒープ内のオブジェクトを指している（`inheap(ptr)`）ならば、`shade(ptr)`を呼び出してそのオブジェクトを灰色にマークします。これにより、新しく参照されたオブジェクトがGCによって確実にスキャンされるようになります。`//go:nowritebarrier`ディレクティブは、この関数自体がライトバリアの対象とならないことを示します。

### `writebarrierptr`

```go
//go:nosplit
func writebarrierptr(dst *uintptr, src uintptr) {
	if !needwb() {
		*dst = src
		return
	}

	// ... シャドウヒープ関連の処理 ...

	*dst = src
	writebarrierptr_nostore1(dst, src)
}
```
この関数は、Goコンパイラによって生成され、単一のポインタが書き換えられる際に呼び出されます。`needwb()`が`true`（ライトバリアが必要な状態）の場合に、シャドウヒープの更新（デバッグモードの場合）と、`writebarrierptr_nostore1`を介した`gcmarkwb_m`の呼び出しを行います。`*dst = src`という実際のストア操作は、ライトバリアのロジックの前後で行われます。

### シャドウヒープ関連の関数 (`wbshadowinit`, `shadowptr`, `checkwbshadow`)

これらの関数は、ライトバリアのデバッグと検証のために重要です。
*   `wbshadowinit`は、`GODEBUG=wbshadow=1`が設定されている場合に、通常のヒープのミラーコピーであるシャドウヒープを初期化します。
*   `shadowptr`は、与えられたヒープアドレスに対応するシャドウヒープ上のアドレスを計算します。
*   `checkwbshadow`は、GCのチェックマークフェーズ中に呼び出され、通常のヒープとシャドウヒープの内容を比較します。もし不整合があれば、それはライトバリアの漏れを示唆し、`throw("missed write barrier")`によってプログラムがクラッシュします。これは、開発者がライトバリアのバグを特定するのに役立ちます。

これらのコードが`mbarrier.go`に集約されたことで、GoランタイムのGCサブシステムにおけるライトバリアの役割と実装がより明確になり、開発者がGCの動作を理解し、デバッグする上での利便性が向上しました。

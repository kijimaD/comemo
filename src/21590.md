# [インデックス 21590] ファイルの概要

このコミットは、Go言語の標準ライブラリである`net/http/fcgi`パッケージにおけるリソースリークの修正を目的としています。具体的には、FastCGIリクエストの処理中に発生する可能性のあるパイプの未クローズ問題を解決します。

変更されたファイルは以下の2つです。
- `src/net/http/fcgi/child.go`: FastCGIの子プロセスがリクエストを処理するロジックが含まれています。このファイルにリソースクリーンアップのための主要な変更が加えられました。
- `src/net/http/fcgi/fcgi_test.go`: `child.go`に加えられた変更が正しく機能することを検証するための新しいテストケースが追加されました。

## 変更の背景

このコミットは、Goの`net/http/fcgi`パッケージを使用するアプリケーションにおいて発生する可能性のあるリソースリークを修正するために導入されました。FastCGIはウェブサーバーとアプリケーションの間で通信を行うためのプロトコルであり、リクエストのボディなどのデータはパイプを通じてやり取りされます。

リソースリークは、プログラムが確保したリソース（この場合は、リクエストボディを処理するためのパイプ）を適切に解放しない場合に発生します。特に、以下のようなシナリオで問題が生じる可能性がありました。

1.  **リクエストの中断 (Request Abort)**: ウェブサーバーがクライアントからのリクエストを途中で中断した場合（例: クライアントが接続を切断した、タイムアウトが発生したなど）、FastCGIプロトコルはアプリケーションに`typeAbortRequest`というレコードを送信して通知します。この時、アプリケーション側でリクエストボディに関連付けられたパイプが適切に閉じられないと、そのパイプがシステムリソースとして残り続け、リークとなります。
2.  **接続の終了 (Connection Termination)**: FastCGI接続自体が終了した場合（例: ウェブサーバーがシャットダウンした、ネットワークエラーが発生したなど）、その接続に関連するすべての未処理のリクエストのパイプが閉じられる必要があります。これが適切に行われないと、同様にリソースがリークします。

これらのリソースリークは、長時間の稼働や高負荷な環境下で、ファイルディスクリプタの枯渇やメモリ使用量の増加を引き起こし、最終的にはアプリケーションのパフォーマンス低下やクラッシュにつながる可能性があります。コミットメッセージにある`Fixes #6934`は、この特定のリソースリーク問題が内部的に追跡されていたことを示唆しています。

## 前提知識の解説

### FastCGI (Fast Common Gateway Interface)

FastCGIは、ウェブサーバー（例: Nginx, Apache）と動的なウェブアプリケーション（例: Go, PHP, Pythonで書かれたアプリケーション）の間で情報をやり取りするためのプロトコルです。従来のCGI（Common Gateway Interface）がリクエストごとに新しいプロセスを起動していたのに対し、FastCGIはアプリケーションプロセスを常駐させ、複数のリクエストを処理することで、パフォーマンスのオーバーヘッドを大幅に削減します。

FastCGIの通信はバイナリプロトコルであり、データは「レコード」と呼ばれる単位で送受信されます。主要なレコードタイプには以下のようなものがあります。
- `FCGI_BEGIN_REQUEST`: 新しいリクエストの開始を通知します。
- `FCGI_PARAMS`: 環境変数やリクエストヘッダなどのパラメータを送信します。
- `FCGI_STDIN`: リクエストボディのデータを送信します。
- `FCGI_STDOUT`: アプリケーションからのレスポンスボディを送信します。
- `FCGI_STDERR`: アプリケーションからのエラー出力を送信します。
- `FCGI_ABORT_REQUEST`: ウェブサーバーがリクエストを中断したことをアプリケーションに通知します。

### リソースリーク (Resource Leaks)

リソースリークとは、プログラムがオペレーティングシステムから割り当てられたリソース（メモリ、ファイルハンドル、ネットワークソケット、スレッドなど）を使い終わった後に適切に解放せず、そのリソースへの参照を失ってしまう状態を指します。これにより、利用可能なリソースが徐々に減少し、最終的にはシステム全体のパフォーマンス低下や、新しいリソースを確保できなくなることによるアプリケーションのクラッシュを引き起こします。ネットワークプログラミングにおいては、開かれたソケットやパイプが閉じられないことが一般的なリークの原因となります。

### Goにおける`io.Pipe`

Go言語の標準ライブラリ`io`パッケージは、`Pipe()`関数を提供しています。これは、メモリ内でデータをやり取りするための同期パイプを作成します。`Pipe()`は`io.PipeReader`と`io.PipeWriter`のペアを返します。
- `io.PipeWriter`にデータを書き込むと、そのデータは対応する`io.PipeReader`から読み取ることができます。
- このパイプは、異なるゴルーチン間でデータをストリームとして受け渡すのに非常に便利です。
- `Close()`メソッドを呼び出すことで、パイプを閉じ、関連するリソースを解放する必要があります。
- `CloseWithError(err error)`メソッドは、エラーを伴ってパイプを閉じるために使用されます。これにより、読み取り側は指定されたエラーを受け取り、読み取り処理を終了できます。これは、予期せぬ終了やエラー状態を通知する際に特に有用です。

`net/http/fcgi`パッケージでは、ウェブサーバーから受信したFastCGIリクエストのボディをGoの`http.Request.Body`として提供するために、この`io.Pipe`が内部的に利用されています。ウェブサーバーからの入力ストリームは`PipeWriter`に書き込まれ、GoのHTTPハンドラは`PipeReader`からリクエストボディを読み取ります。

## 技術的詳細

Goの`net/http/fcgi`パッケージは、FastCGIプロトコルをGoの`http.Handler`インターフェースに適合させる役割を担っています。このパッケージの内部では、各FastCGIリクエストのボディを処理するために`io.Pipe`が使用されます。具体的には、ウェブサーバーから`FCGI_STDIN`レコードとして送られてくるリクエストボディのデータは、`child`構造体内の`request`オブジェクトに紐付けられた`io.PipeWriter` (`req.pw`) に書き込まれます。そして、GoのHTTPハンドラは、`http.Request.Body`として提供される対応する`io.PipeReader`からそのデータを読み取ります。

このコミット以前は、以下のような状況で`req.pw`が適切に閉じられず、リソースリークが発生する可能性がありました。

1.  **リクエストの中断時**: ウェブサーバーが`FCGI_ABORT_REQUEST`レコードを送信してリクエストを中断した場合、Goアプリケーションはリクエストの処理を停止する必要があります。しかし、この際に`req.pw`が明示的に閉じられないと、そのパイプがオープンなまま残り、ファイルディスクリプタなどのリソースを消費し続けることになります。ハンドラがリクエストボディの読み取りを試みている場合、パイプが閉じられないとハンドラがブロックされ続ける可能性もあります。
2.  **FastCGI接続終了時**: `child.serve()`関数は個々のFastCGI接続を処理するゴルーチンで実行されます。この接続が何らかの理由で終了した場合（例: ウェブサーバーが接続を切断した、エラーが発生したなど）、その接続に関連するすべての未処理のリクエストのパイプが閉じられる必要があります。これが適切に行われないと、接続が終了した後もパイプがリークし続けることになります。

このコミットは、これらのシナリオにおいて`req.pw`が確実に`CloseWithError`によって閉じられるようにすることで、リソースリークを防ぎます。`CloseWithError`を使用することで、パイプの読み取り側（`http.Request.Body`）は、リクエストが中断されたり、接続が閉じられたりした理由を示す特定のエラーを受け取ることができ、ハンドラ側で適切なエラー処理が可能になります。

## コアとなるコードの解説

### `child.go`の変更点

1.  **`defer c.cleanUp()`の追加**:
    *   `child.serve()`関数は、個々のFastCGI接続を処理するゴルーチン内で実行されます。
    *   `defer c.cleanUp()`が追加されたことにより、`serve()`関数が正常に終了する場合でも、エラーによって途中で終了する場合でも、`cleanUp()`メソッドが必ず呼び出されることが保証されます。
    *   これにより、そのFastCGI接続に関連するすべての未処理のリクエストボディのパイプが確実に閉じられ、リソースリークが防止されます。

2.  **`ErrRequestAborted`と`ErrConnClosed`の定義**:
    *   `ErrRequestAborted`: ウェブサーバーによってリクエストが中断された場合に、リクエストボディの読み取り側（`io.PipeReader`）が返すエラーとして定義されます。
    *   `ErrConnClosed`: ウェブサーバーへの接続が閉じられた場合に、リクエストボディの読み取り側が返すエラーとして定義されます。
    *   これらのエラーを明示的に定義することで、HTTPハンドラはリクエストボディの読み取りエラーの原因をより具体的に特定し、適切なエラーハンドリングを行うことができるようになります。

3.  **`typeAbortRequest`処理における`req.pw.CloseWithError(ErrRequestAborted)`の追加**:
    *   `child.handleRecord()`関数内で、ウェブサーバーから`typeAbortRequest`レコードを受信した際の処理が変更されました。
    *   `req.pw`は、現在のリクエストのリクエストボディをGoのハンドラに提供するための`io.PipeWriter`です。
    *   `req.pw.CloseWithError(ErrRequestAborted)`を呼び出すことで、リクエストボディの読み取り側（`http.Request.Body`）は`ErrRequestAborted`エラーを受け取り、読み取り処理が終了します。これにより、ハンドラがリクエストボディの読み取りでブロックされるのを防ぎ、関連するリソースが解放されます。

4.  **`child.cleanUp()`関数の追加**:
    *   この新しい関数は、`child`オブジェクトが現在管理しているすべての未処理の`request`オブジェクトをイテレートします。
    *   各`request`に関連付けられた`io.PipeWriter` (`req.pw`) が存在する場合、`req.pw.CloseWithError(ErrConnClosed)`を呼び出してパイプを閉じます。
    *   この処理は、`child.serve()`が終了する際に呼び出されるため、接続が終了する際にまだ閉じられていないすべてのリクエストボディのパイプが強制的に閉じられ、リソースリークが防止されます。コメントにあるように、`PipeWriter.Close()`は冪等であるため、`serveRequest`内の`Close`との競合は問題になりません。

### `fcgi_test.go`の変更点

1.  **`TestChildServeCleansUp`テスト関数の追加**:
    *   この新しいテストは、リソースクリーンアップのメカニズムが正しく機能することを検証するために追加されました。
    *   テストは2つのシナリオをシミュレートします。
        1.  **リクエストの中断**: `streamBeginTypeStdin`（リクエスト開始とボディの一部）の後に`typeAbortRequest`レコードを送信し、リクエストが中断された場合に`http.Request.Body`からの読み取りが`ErrRequestAborted`を返すことを確認します。
        2.  **接続の終了**: `streamBeginTypeStdin`の後にデータ送信を停止し、接続が予期せず終了した場合に`http.Request.Body`からの読み取りが`ErrConnClosed`を返すことを確認します。
    *   テストは、リソースが適切にクリーンアップされない場合にデッドロックが発生するように設計されており、これにより変更が正しく機能していることを強力に保証します。`io.Copy(ioutil.Discard, r.Body)`は、リクエストボディを読み切ろうとすることで、パイプが閉じられていない場合にブロックされることを利用しています。

これらの変更により、Goの`net/http/fcgi`パッケージは、FastCGIリクエストのライフサイクルにおけるリソースの管理をより堅牢に行い、リソースリークを防ぐことができるようになりました。

# [インデックス 20253] ファイルの概要

このコミットは、Go言語のリンカ（`cmd/5l`, `cmd/6l`, `cmd/8l`）における、Native Client (NaCl) バイナリの破損バグを修正するものです。具体的には、NaClバイナリのテキストセグメントの末尾に追加される「halt sled」の存在が、データセグメントの末尾のファイルオフセット計算に考慮されていなかったために発生する問題に対処しています。これにより、シンボルテーブルがデータセグメントの最終ページを上書きし、プログラムのクラッシュやランタイムのエラー出力の破損を引き起こす可能性がありました。

## コミット

```
commit a9b2651ade68733405cdc296d66d9b9d8ea68bf0
Author: Russ Cox <rsc@golang.org>
Date:   Wed Aug 27 22:53:28 2014 -0400

    cmd/5l, cmd/6l, cmd/8l: fix nacl binary corruption bug
    
    NaCl requires the addition of a 32-byte "halt sled" at the end
    of the text segment. This means that segtext.len is actually
    32 bytes shorter than reality. The computation of the file offset
    of the end of the data segment did not take this 32 bytes into
    account, so if len and len+32 rounded up (by 64k) to different
    values, the symbol table overwrote the last page of the data
    segment.
    
    The last page of the data segment is usually the C .string
    symbols, which contain the strings used in error prints
    by the runtime. So when this happens, your program
    probably crashes, and then when it does, you get binary
    garbage instead of all the usual prints.
    
    The chance of hitting this with a randomly sized text segment
    is 32 in 65536, or 1 in 2048.
    
    If you add or remove ANY code while trying to debug this
    problem, you're overwhelmingly likely to bump the text
    segment one way or the other and make the bug disappear.
    
    Correct all the computations to use segdata.fileoff+segdata.filelen
    instead of trying to rederive segdata.fileoff.
    
    This fixes the failure during the nacl/amd64p32 build.
    
    TBR=iant
    CC=golang-codereviews
    https://golang.org/cl/135050043
```

## 元コミット内容

このコミットは、Go言語のリンカである`cmd/5l` (ARM), `cmd/6l` (x86-64), `cmd/8l` (x86-32) において、Native Client (NaCl) バイナリを生成する際に発生するデータ破損バグを修正します。このバグは、NaClがテキストセグメントの末尾に32バイトの「halt sled」を必要とすることに起因していました。リンカがデータセグメントの終端のファイルオフセットを計算する際に、この32バイトを考慮していなかったため、シンボルテーブルがデータセグメントの最終ページを上書きし、結果としてプログラムのクラッシュやランタイムのエラーメッセージの破損を引き起こしていました。この問題は、テキストセグメントのサイズが特定の条件（64KBのページ境界で丸めたときに`len`と`len+32`が異なる値になる場合）を満たす場合に、約1/2048の確率で発生しました。デバッグが困難な「幽霊バグ」であり、コードの追加や削除によって現象が消える可能性がありました。修正は、データセグメントのファイルオフセットを再計算するのではなく、`segdata.fileoff + segdata.filelen` を直接使用するように計算式を変更することで行われました。これにより、`nacl/amd64p32`ビルド時の失敗が修正されました。

## 変更の背景

この変更の背景には、Go言語がNative Client (NaCl) をサポートしていた時期に発生した、バイナリ生成の際の深刻なバグがあります。NaClは、ウェブブラウザ内でネイティブコードを安全に実行するためのGoogleのサンドボックス技術でした。NaClバイナリは、セキュリティ上の理由から、テキストセグメント（実行可能コードが格納される領域）の末尾に32バイトの「halt sled」と呼ばれる特殊な命令シーケンスを追加することを要求していました。

Goのリンカは、バイナリの各セグメント（テキスト、データなど）のサイズと配置を計算し、最終的な実行可能ファイルを生成します。この際、シンボルテーブルなどのメタデータは、通常、データセグメントの直後に配置されます。しかし、リンカがデータセグメントの終端のファイルオフセットを計算する際に、NaCl特有の32バイトの「halt sled」の存在を考慮していませんでした。

具体的には、リンカはテキストセグメントの長さ（`segtext.len`）を基に次のセグメントの開始位置を計算していましたが、NaClの場合、実際のテキストセグメントの長さは`segtext.len`よりも32バイト長かったのです。このずれが、特にセグメントの長さが64KBのページ境界で丸められる際に問題を引き起こしました。もし`segtext.len`と`segtext.len + 32`が異なるページ境界にまたがる場合、リンカはデータセグメントの終端を誤って計算し、その結果、シンボルテーブルがデータセグメントの最終ページ、特にランタイムのエラーメッセージなどに使われるC言語の文字列シンボルが格納されている領域を上書きしてしまいました。

この上書きが発生すると、プログラムはクラッシュし、さらに悪いことに、クラッシュ時のエラーメッセージが破損して意味不明なバイナリゴミとして表示されるという、デバッグを極めて困難にする状況を引き起こしました。このバグは、テキストセグメントのサイズが特定の条件を満たす場合にのみ発生し、その確率は約1/2048と比較的低かったため、再現性が低く、デバッグ中にコードを少し変更するだけで現象が消えてしまうという「幽霊バグ」の性質を持っていました。このため、開発者にとっては非常に厄介な問題でした。

このコミットは、このような不安定な挙動を修正し、NaClバイナリの信頼性を確保することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の概念について知っておく必要があります。

1.  **Go言語のリンカ (`cmd/5l`, `cmd/6l`, `cmd/8l`)**:
    *   Go言語のビルドプロセスにおいて、コンパイルされたオブジェクトファイルを結合し、実行可能なバイナリを生成するツールです。
    *   `cmd/5l`はARMアーキテクチャ向け、`cmd/6l`はAMD64 (x86-64) アーキテクチャ向け、`cmd/8l`は386 (x86-32) アーキテクチャ向けのリンカでした。これらはGoの初期のバージョンで使われていたもので、Plan 9オペレーティングシステムのツールチェインに由来します。現在のGoでは、`go build`コマンドが内部的に適切なリンカを呼び出すため、開発者が直接これらのコマンドを使うことはほとんどありません。現代のGoリンカはGo自身で書かれた「内部リンカ」が主ですが、Cgoを使用する場合は`gcc`や`clang`のような「外部リンカ」も利用できます。

2.  **Native Client (NaCl)**:
    *   Googleが開発した、ウェブブラウザ内でネイティブコード（C/C++など）を安全かつ高速に実行するためのサンドボックス技術です。
    *   セキュリティモデルは、ソフトウェアフォールト分離 (Software Fault Isolation, SFI) と呼ばれる技術に基づいており、悪意のあるコードがシステムにアクセスするのを防ぎます。
    *   Go言語はかつてNaClへのコンパイルをサポートしていましたが、その後WebAssembly (WASM) の台頭により、NaClのサポートは終了しました。

3.  **Halt Sled**:
    *   NaClのセキュリティ機構の一部として使用される特殊なコードシーケンスです。
    *   具体的には、テキストセグメントの末尾に配置される32バイトの`hlt`（halt）命令の連続です。
    *   これは「トランポリン攻撃」と呼ばれる、悪意のあるコードが意図しないメモリ領域にジャンプして実行されるのを防ぐためのものです。`hlt`命令はプロセッサを停止させるため、不正なジャンプが発生した場合にプログラムの実行を停止させ、セキュリティ違反を防ぎます。

4.  **実行可能ファイルの構造とセグメント**:
    *   実行可能ファイルは通常、複数の論理的なセグメントに分割されています。
    *   **テキストセグメント (Text Segment)**: プログラムの実行可能コード（機械語命令）が格納される領域です。読み取り専用で実行可能に設定されます。
    *   **データセグメント (Data Segment)**: 初期化されたグローバル変数や静的変数が格納される領域です。読み書き可能です。
    *   **シンボルテーブル (Symbol Table)**: プログラム内の関数名、変数名、アドレスなどのシンボル情報が格納される領域です。デバッグや動的リンクに利用されます。

5.  **リンカにおけるオフセットと長さの計算**:
    *   リンカは、各セグメントがファイル内でどこから始まり（ファイルオフセット）、どれくらいの長さを持つか（ファイル長）を正確に計算する必要があります。
    *   `segtext.len`: テキストセグメントの論理的な長さ。
    *   `segdata.filelen`: データセグメントのファイル内での長さ。
    *   `segdata.fileoff`: データセグメントのファイル内での開始オフセット。
    *   `HEADR`: 実行可能ファイルのヘッダ部分のサイズ。ファイル形式（ELF, PE, Mach-Oなど）によって異なります。
    *   `INITRND`: 初期化時の丸め処理に関連する定数。
    *   `PEFILEALIGN`: WindowsのPortable Executable (PE) 形式におけるファイルアライメント（セクションの開始アドレスが特定のバイト数で割り切れるようにする制約）。
    *   `machlink`: macOSのMach-O形式のリンクに関連する値。

6.  **ページアライメントと丸め**:
    *   オペレーティングシステムは、メモリをページ単位で管理します（例: 4KBや64KB）。実行可能ファイルのセグメントは、効率的なメモリマッピングのために、しばしばページ境界にアライメント（整列）される必要があります。
    *   リンカは、セグメントのサイズやオフセットを計算する際に、このページアライメントを考慮して値を丸める（`rnd`関数などを使用）ことがあります。この丸め処理が、今回のバグのトリガーの一つとなりました。

## 技術的詳細

このバグの核心は、GoリンカがNaClバイナリの構造を正確にモデル化できていなかった点にあります。

1.  **NaClの特殊な要件**:
    *   NaClは、テキストセグメントの末尾に32バイトの「halt sled」を挿入することを義務付けています。これは、リンカが生成するバイナリの物理的なテキストセグメントの長さが、リンカ内部で認識している論理的なテキストセグメントの長さ（`segtext.len`）よりも32バイト長くなることを意味します。

2.  **誤ったオフセット計算**:
    *   リンカは、シンボルテーブルの開始オフセット（`symo`）を計算する際に、データセグメントの終端を基準にしていました。
    *   多くのケースで、データセグメントの終端は`HEADR + segtext.len + segdata.filelen`のように、ヘッダサイズ、テキストセグメント長、データセグメント長を足し合わせることで計算されていました。
    *   しかし、NaClの場合、`segtext.len`が実際のテキストセグメントの長さより32バイト短いため、この計算式ではデータセグメントの終端が実際の終端よりも32バイト手前に来てしまう可能性がありました。

3.  **ページアライメントとバグの顕在化**:
    *   実行可能ファイルのセグメントは、メモリ効率のために64KBなどのページ境界にアライメントされることがよくあります。リンカは`rnd`（round）関数を使って、サイズやオフセットを次のページ境界に丸めます。
    *   問題は、`segtext.len`と`segtext.len + 32`が異なる64KBページ境界にまたがる場合に顕在化しました。例えば、`segtext.len`が64KBの倍数から数バイト手前で、`segtext.len + 32`が次の64KBの倍数を超えてしまうような場合です。
    *   この状況では、リンカが計算したデータセグメントの終端（誤った`segtext.len`に基づく）と、実際にデータセグメントが占めるべき領域の終端との間にずれが生じました。
    *   結果として、シンボルテーブルが、本来データセグメントの一部であるべき領域、特にランタイムのエラーメッセージなどに使われるC言語の文字列シンボルが格納されている最終ページを上書きしてしまいました。

4.  **影響**:
    *   シンボルテーブルによるデータセグメントの上書きは、プログラムの実行中に予期せぬクラッシュを引き起こしました。
    *   さらに、ランタイムのエラーメッセージが格納されている領域が破損するため、クラッシュ時に意味不明な文字が表示され、デバッグが極めて困難になりました。
    *   このバグは、テキストセグメントのサイズが特定の条件を満たす場合にのみ発生するため、再現性が低く、コードの追加や削除によってテキストセグメントのサイズがわずかに変化するだけで、バグが消えたり現れたりする「幽霊バグ」の性質を持っていました。

5.  **修正**:
    *   修正は、シンボルテーブルの開始オフセット`symo`を計算する際に、`HEADR + segtext.len + segdata.filelen`のような、テキストセグメントの長さに依存する計算を避けることでした。
    *   代わりに、データセグメントのファイルオフセットとファイル長を直接加算した`segdata.fileoff + segdata.filelen`を使用するように変更されました。`segdata.fileoff`は、データセグメントがファイル内で実際にどこから始まるかを示す値であり、これにはテキストセグメントの実際の長さ（halt sledを含む）が既に考慮されています。
    *   この変更により、データセグメントの終端が常に正確に計算されるようになり、シンボルテーブルがデータセグメントを上書きする問題が解決されました。

## コアとなるコードの解説

上記の変更は、シンボルテーブルのオフセット`symo`を計算するロジックを、より堅牢なものに修正しています。

変更前は、多くのケースで`symo`の計算に`HEADR + segtext.len + segdata.filelen`のような式が使われていました。これは、ヘッダのサイズ、テキストセグメントの長さ、データセグメントの長さを単純に足し合わせることで、データセグメントの直後にシンボルテーブルが来ると仮定していました。しかし、NaClの「halt sled」のように、`segtext.len`が実際の物理的なテキストセグメントの長さと異なる場合、この計算は不正確になります。特に、ページアライメントの丸め処理が絡むと、計算された`symo`が実際のデータセグメントの領域に食い込んでしまう可能性がありました。

変更後のコードでは、`symo`の計算に`segdata.fileoff + segdata.filelen`が導入されています。

*   `segdata.fileoff`: これは、データセグメントが実行可能ファイル内で実際に開始するオフセット（バイト単位）を示します。この値は、リンカがテキストセグメントの実際の長さ（NaClのhalt sledを含む）や、その他のセグメントの配置を考慮して既に計算している正確な値です。
*   `segdata.filelen`: これは、データセグメントのファイル内での実際の長さです。

`segdata.fileoff`と`segdata.filelen`を足し合わせることで、データセグメントがファイル内で占める領域の正確な終端位置が得られます。この終端位置をシンボルテーブルの開始点とすることで、シンボルテーブルがデータセグメントの領域を上書きする可能性がなくなります。

この修正は、各リンカ（`5l`, `6l`, `8l`）の異なるターゲットOS（Plan 9, Elf, Darwin, Linux, FreeBSD, DragonFly, Solaris, NaCl, Windows）向けの`symo`計算ロジックに適用されています。特に`Hnacl`（NaClターゲット）のケースでは、この修正が直接的にバグを解決します。他のターゲットOS向けの計算も、同様に`segdata.fileoff`を基点とすることで、より汎用的で堅牢な計算ロジックに統一されています。

例えば、`src/cmd/6l/asm.c`の`Hdarwin`（macOS）向けの変更では、`rnd(HEADR+segtext.len, INITRND)+rnd(segdata.filelen, INITRND)+machlink`から`segdata.fileoff+rnd(segdata.filelen, INITRND)+machlink`に変更されています。ここでも、`HEADR+segtext.len`というテキストセグメントの長さに依存する計算を避け、`segdata.fileoff`というデータセグメントの正確な開始オフセットを基点とすることで、計算の正確性を高めています。

この変更により、リンカはバイナリのセグメント配置をより正確に管理できるようになり、特にNaClのような特殊な要件を持つ環境でのバイナリ破損を防ぐことができました。

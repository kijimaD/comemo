# [インデックス 25703] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）における「tiny alloc cache」のクリアタイミングを変更するものです。具体的には、このキャッシュをスイープ終了時ではなく、マーク終了時にクリアするように修正しています。これにより、GCとアロケータ間の潜在的な競合状態を解消し、メモリ破損のリスクを低減します。

## コミット

```
runtime: clear tiny alloc cache in mark term, not sweep term

The tiny alloc cache is maintained in a pointer from non-GC'd memory
(mcache) to heap memory and hence must be handled carefully.

Currently we clear the tiny alloc cache during sweep termination and,
if it is assigned to a non-nil value during concurrent marking, we
depend on a write barrier to keep the new value alive. However, while
the compiler currently always generates this write barrier, we're
treading on thin ice because write barriers may not happen for writes
to non-heap memory (e.g., typedmemmove). Without this lucky write
barrier, the GC may free a current tiny block while it's still
reachable by the tiny allocator, leading to later memory corruption.

Change this code so that, rather than depending on the write barrier,
we simply clear the tiny cache during mark termination when we're
clearing all of the other mcaches. If the current tiny block is
reachable from regular pointers, it will be retained; if it isn't
reachable from regular pointers, it may be freed, but that's okay
because there won't be any pointers in non-GC'd memory to it.
```

## 変更の背景

Goのガベージコレクション（GC）は、メモリ管理の重要な部分です。特に、Go 1.5で導入された並行GCは、アプリケーションの実行と並行してGCサイクルを実行することで、GCポーズタイムを大幅に削減しました。しかし、この並行性には、GCとアプリケーションのアロケータが同時にメモリを操作する際の複雑さが伴います。

このコミットの背景にある問題は、「tiny alloc cache」という特殊なメモリ領域の管理方法にありました。`mcache`（各P、つまりプロセッサごとに割り当てられるキャッシュ）内に存在する`tiny`フィールドは、非常に小さなオブジェクト（ポインタを含まないもの）を効率的に割り当てるためのキャッシュです。この`mcache`自体はGCの対象とならないメモリ領域（非GC管理メモリ）に存在しますが、`tiny`フィールドが指す先はヒープメモリ（GC管理メモリ）上のブロックです。

以前の実装では、`tiny alloc cache`はGCの「スイープ終了時（sweep termination）」にクリアされていました。しかし、並行マーキング中に`tiny`フィールドがヒープ上の新しいブロックを指すように更新された場合、その新しい値がGCによって誤って解放されないように、ライトバリア（write barrier）に依存していました。ライトバリアは、GCがオブジェクトグラフを正確に追跡できるように、ポインタの書き込み時に特定の処理を実行するメカニズムです。

問題は、非GC管理メモリ（`mcache`）からヒープメモリへのポインタ書き込みに対して、コンパイラが常にライトバリアを生成するとは限らないという点でした。特に`typedmemmove`のような低レベルのメモリ操作では、ライトバリアが省略される可能性がありました。もしライトバリアが適用されなかった場合、GCは`tiny`が指すヒープブロックがまだ参照されていることを認識できず、そのブロックを解放してしまう可能性がありました。その結果、`tiny alloc cache`が解放済みのメモリを指し続け、後続のメモリ割り当てでメモリ破損（use-after-free）が発生するという深刻なバグにつながる恐れがありました。

このコミットは、このような「薄氷を踏むような」ライトバリアへの依存を排除し、より堅牢な方法で`tiny alloc cache`を管理するために導入されました。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に以下のフェーズで構成されます（Go 1.5以降の並行GCの場合）：

1.  **マーク開始 (Mark Start)**: GCサイクルが開始されます。ストップ・ザ・ワールド（STW）が発生し、GCルート（スタック、グローバル変数など）がスキャンされ、マークキューに初期オブジェクトが追加されます。
2.  **並行マーキング (Concurrent Marking)**: アプリケーションの実行と並行して、GCワーカーがヒープ上の到達可能なオブジェクトをマークします。このフェーズ中に、アプリケーションは新しいオブジェクトを割り当てたり、既存のポインタを更新したりします。ポインタの更新はライトバリアによって監視されます。
3.  **マーク終了 (Mark Termination)**: 並行マーキングが完了した後、再びSTWが発生します。このフェーズでは、残りのマーク作業（例えば、グレースケールオブジェクトの処理）を完了し、GCの準備を整えます。`mcache`などのプロセッサローカルなキャッシュもこのタイミングでクリアされることがあります。
4.  **並行スイープ (Concurrent Sweeping)**: マークされなかった（到達不能な）オブジェクトが占めていたメモリを解放し、再利用可能な状態に戻します。これもアプリケーションの実行と並行して行われます。
5.  **スイープ終了 (Sweep Termination)**: スイープが完了したことを確認し、次のGCサイクルに備えます。

### mcacheとtiny alloc cache

*   **`mcache`**: Goランタイムでは、各論理プロセッサ（P）ごとに`mcache`と呼ばれるローカルなメモリキャッシュが割り当てられます。これは、小さなオブジェクトの割り当てを高速化するために使用されます。`mcache`はヒープ上に割り当てられるのではなく、ランタイムが管理する非GC管理メモリ領域に存在します。これにより、GCのオーバーヘッドなしに高速なアクセスが可能です。
*   **`tiny alloc cache`**: `mcache`の一部として、特にポインタを含まない非常に小さなオブジェクト（例えば、`int`や`bool`の配列など）を効率的に割り当てるためのキャッシュです。`mcache`構造体内の`tiny`フィールドが、現在使用中の小さなメモリブロックの先頭を指し、`tinyoffset`がそのブロック内の次の割り当て可能な位置を示します。この`tiny`フィールドは、非GC管理メモリである`mcache`から、GC管理メモリであるヒープ上のブロックを指すポインタです。

### ライトバリア (Write Barrier)

ライトバリアは、ガベージコレクタがオブジェクトグラフの変更を追跡するために使用する技術です。Goの並行GCでは、アプリケーションが実行中にヒープ上のポインタを書き換える際に、ライトバリアが介入してGCに必要な情報を記録します。これにより、GCがオブジェクトをマークしている最中にアプリケーションがポインタを変更しても、GCがその変更を見落とすことなく、到達可能なオブジェクトを正確にマークできるようになります。

しかし、ライトバリアは通常、ヒープ上のポインタの書き込みに対して適用されます。非GC管理メモリからヒープへのポインタの書き込みは、GCの通常の追跡範囲外であるため、コンパイラがライトバリアを生成しない場合があります。

## 技術的詳細

このコミットの核心は、`mcache.tiny`フィールドのクリアタイミングを、GCの「スイープ終了時」から「マーク終了時」へ変更することです。

1.  **旧実装の問題点**:
    *   `mcache`は非GC管理メモリに存在するため、`mcache.tiny`が指すヒープ上のブロックは、GCが直接`mcache`をスキャンして到達可能性を判断するわけではありません。
    *   以前は、`mcache.tiny`は`clearpools()`関数内で、GCのスイープ終了時にクリアされていました。
    *   並行マーキング中に`mcache.tiny`が新しいヒープブロックを指すように更新された場合、そのポインタの書き込みに対してライトバリアが適用されることを期待していました。これにより、GCは新しいヒープブロックが`mcache.tiny`から参照されていることを認識し、解放しないようにします。
    *   しかし、コミットメッセージが指摘するように、非GC管理メモリからのポインタ書き込みに対しては、コンパイラが常にライトバリアを生成する保証はありませんでした。特に`typedmemmove`のような最適化されたメモリコピー操作では、ライトバリアが省略される可能性がありました。
    *   ライトバリアが省略された場合、GCは`mcache.tiny`が指すヒープブロックが到達可能であることを認識できず、そのブロックを解放してしまう可能性がありました。その後、`mcache.tiny`が解放済みのメモリを指したままになり、新しい`tiny`オブジェクトの割り当て時にメモリ破損を引き起こす可能性がありました。

2.  **新実装の解決策**:
    *   `mcache.tiny`のクリアを`mcache.releaseAll()`関数内に移動しました。
    *   `mcache.releaseAll()`は、GCのマーク終了時に呼び出されます。このタイミングで、すべての`mcache`がクリアされます。
    *   この変更により、`mcache.tiny`が指すヒープブロックの生存期間は、ライトバリアに依存するのではなく、GCのマークフェーズによって直接決定されるようになります。
    *   **メカニズム**:
        *   マーク終了時に`mcache.tiny`が`nil`にクリアされます。
        *   もし`mcache.tiny`が指していたヒープブロックが、他の通常のポインタ（例えば、アプリケーションの変数や他のヒープオブジェクトからのポインタ）によってまだ到達可能であれば、GCはそのブロックをマークし、解放しません。
        *   もし`mcache.tiny`が指していたヒープブロックが、`mcache.tiny`以外から到達可能でなければ、GCはそのブロックを到達不能と判断し、解放します。これは問題ありません。なぜなら、`mcache.tiny`はマーク終了時にクリアされるため、非GC管理メモリからそのブロックへの参照はもはや存在しないからです。
    *   このアプローチにより、ライトバリアの有無に依存することなく、`tiny alloc cache`の整合性が保証され、メモリ破損のリスクが排除されます。

このコミットの背景にある問題は、「tiny alloc cache」という特殊なメモリ領域の管理方法にありました。`mcache`（各P、つまり論理プロセッサごとに割り当てられるキャッシュ）内に存在する`tiny`フィールドは、非常に小さなオブジェクト（ポインタを含まないもの）を効率的に割り当てるためのキャッシュです。この`mcache`自体はGCの対象とならないメモリ領域（非GC管理メモリ）に存在しますが、`tiny`フィールドが指す先はヒープメモリ（GC管理メモリ）上のブロックです。

以前の実装では、`tiny alloc cache`はGCの「スイープ終了時（sweep termination）」にクリアされていました。しかし、並行マーキング中に`tiny`フィールドがヒープ上の新しいブロックを指すように更新された場合、その新しい値がGCによって誤って解放されないように、ライトバリア（write barrier）に依存していました。ライトバリアは、GCがオブジェクトグラフを正確に追跡できるように、ポインタの書き込み時に特定の処理を実行するメカニズムです。

問題は、非GC管理メモリ（`mcache`）からヒープメモリへのポインタ書き込みに対して、コンパイラが常にライトバリアを生成するとは限らないという点でした。特に`typedmemmove`のような低レベルのメモリ操作では、ライトバリアが省略される可能性がありました。もしライトバリアが適用されなかった場合、GCは`tiny`が指すヒープブロックがまだ参照されていることを認識できず、そのブロックを解放してしまう可能性がありました。その結果、`tiny alloc cache`が解放済みのメモリを指し続け、後続のメモリ割り当てでメモリ破損（use-after-free）が発生するという深刻なバグにつながる恐れがありました。

このコミットは、このような「薄氷を踏むような」ライトバリアへの依存を排除し、より堅牢な方法で`tiny alloc cache`を管理するために導入されました。

## 前提知識の解説

### Goのガベージコレクション (GC)

GoのGCは、主に以下のフェーズで構成されます（Go 1.5以降の並行GCの場合）：

1.  **マーク開始 (Mark Start)**: GCサイクルが開始されます。これは非常に短い「ストップ・ザ・ワールド」（STW）フェーズであり、アプリケーションの実行が一時停止されます。この間に、GCはマーキングフェーズの準備を行い、ライトバリアを有効にし、ルートオブジェクト（グローバル変数やアクティブなスタックフレームなど）を特定してグレーとしてマークします。
2.  **並行マーキング (Concurrent Marking)**: このフェーズはアプリケーションと並行して実行されます。ガベージコレクタは、グレーのルートオブジェクトから開始してヒープを走査します。三色マーキングアルゴリズムを使用し、オブジェクトは最初は白、到達可能なオブジェクトはグレー、そしてその参照がすべてスキャンされると黒としてマークされます。このプロセスにより、到達可能なすべてのオブジェクトが識別されます。
3.  **マーク終了 (Mark Termination)**: これはもう一つの短いSTWフェーズです。その目的は、マーキングプロセスを完了し、到達可能なすべてのオブジェクトが識別されたことを確認することです。すべてのゴルーチンがGCセーフポイントにあることを確認し、残りのグレーオブジェクトを処理し、並行変更によって見落とされたオブジェクトを捕捉するためにスタックとグローバルを再スキャンします。その後、ライトバリアは無効になります。
4.  **並行スイープ (Concurrent Sweeping)**: このフェーズはアプリケーションと並行して実行されます。GCはヒープをスキャンし、マーキングフェーズ中に白（到達不能）のままだったオブジェクトが占めていたメモリを解放し、そのメモリを将来の割り当てのために利用可能にします。
5.  **スイープ終了 (Sweep Termination)**: スイープが完了したことを確認し、次のGCサイクルに備えます。

### mcacheとtiny alloc cache

*   **`mcache`**: Goランタイムでは、各論理プロセッサ（P）ごとに`mcache`と呼ばれるローカルなメモリキャッシュが割り当てられます。これは、非常に小さなオブジェクトの割り当てを高速化するために使用されます。`mcache`はヒープ上に割り当てられるのではなく、ランタイムが管理する非GC管理メモリ領域に存在します。これにより、GCのオーバーヘッドなしに高速なアクセスが可能です。各`mcache`はロックフリーで動作し、並行プログラムにおける競合を大幅に削減します。
*   **`tiny alloc cache`**: `mcache`の一部として、特にポインタを含まない非常に小さなオブジェクト（例えば、16バイト未満の数値、ブール値、短い文字列など）を効率的に割り当てるためのキャッシュです。`mcache`構造体内の`tiny`フィールドが、現在使用中の小さなメモリブロックの先頭を指し、`tinyoffset`がそのブロック内の次の割り当て可能な位置を示します。この`tiny`フィールドは、非GC管理メモリである`mcache`から、GC管理メモリであるヒープ上のブロックを指すポインタです。このキャッシュは、頻繁に発生する小さな割り当てを最適化し、メモリ断片化を減らすことを目的としています。

### ライトバリア (Write Barrier)

ライトバリアは、ガベージコレクタがオブジェクトグラフの変更を追跡するために使用する技術です。Goの並行GCでは、アプリケーションが実行中にヒープ上のポインタを書き換える際に、ライトバリアが介入してGCに必要な情報を記録します。これにより、GCがオブジェクトをマークしている最中にアプリケーションがポインタを変更しても、GCがその変更を見落とすことなく、到達可能なオブジェクトを正確にマークできるようになります。

GoのGCは、三色マーキングアルゴリズムを使用しており、ライトバリアの主な役割は「黒いオブジェクトが白いオブジェクトを指さない」という三色不変条件を維持することです。Go 1.8以降では、挿入バリアと削除バリアの側面を組み合わせたハイブリッドライトバリアが導入され、STWポーズ時間をさらに短縮しています。

しかし、ライトバリアは通常、ヒープ上のポインタの書き込みに対して適用されます。非GC管理メモリからヒープへのポインタの書き込みは、GCの通常の追跡範囲外であるため、コンパイラがライトバリアを生成しない場合があります。これが、このコミットで対処されている問題の根源でした。

## 技術的詳細

このコミットの核心は、`mcache.tiny`フィールドのクリアタイミングを、GCの「スイープ終了時」から「マーク終了時」へ変更することです。

1.  **旧実装の問題点**:
    *   `mcache`は非GC管理メモリに存在するため、`mcache.tiny`が指すヒープ上のブロックは、GCが直接`mcache`をスキャンして到達可能性を判断するわけではありません。
    *   以前は、`mcache.tiny`は`clearpools()`関数内で、GCのスイープ終了時にクリアされていました。
    *   並行マーキング中に`mcache.tiny`が新しいヒープブロックを指すように更新された場合、そのポインタの書き込みに対してライトバリアが適用されることを期待していました。これにより、GCは新しいヒープブロックが`mcache.tiny`から参照されていることを認識し、解放しないようにします。
    *   しかし、コミットメッセージが指摘するように、非GC管理メモリからのポインタ書き込みに対しては、コンパイラが常にライトバリアを生成する保証はありませんでした。特に`typedmemmove`のような最適化されたメモリコピー操作では、ライトバリアが省略される可能性がありました。
    *   ライトバリアが省略された場合、GCは`mcache.tiny`が指すヒープブロックが到達可能であることを認識できず、そのブロックを解放してしまう可能性がありました。その後、`mcache.tiny`が解放済みのメモリを指したままになり、新しい`tiny`オブジェクトの割り当て時にメモリ破損を引き起こす可能性がありました。

2.  **新実装の解決策**:
    *   `mcache.tiny`のクリアを`mcache.releaseAll()`関数内に移動しました。
    *   `mcache.releaseAll()`は、GCのマーク終了時に呼び出されます。このタイミングで、すべての`mcache`がクリアされます。
    *   この変更により、`mcache.tiny`が指すヒープブロックの生存期間は、ライトバリアに依存するのではなく、GCのマークフェーズによって直接決定されるようになります。
    *   **メカニズム**:
        *   マーク終了時に`mcache.tiny`が`nil`にクリアされます。
        *   もし`mcache.tiny`が指していたヒープブロックが、他の通常のポインタ（例えば、アプリケーションの変数や他のヒープオブジェクトからのポインタ）によってまだ到達可能であれば、GCはそのブロックをマークし、解放しません。
        *   もし`mcache.tiny`が指していたヒープブロックが、`mcache.tiny`以外から到達可能でなければ、GCはそのブロックを到達不能と判断し、解放します。これは問題ありません。なぜなら、`mcache.tiny`はマーク終了時にクリアされるため、非GC管理メモリからそのブロックへの参照はもはや存在しないからです。
    *   このアプローチにより、ライトバリアの有無に依存することなく、`tiny alloc cache`の整合性が保証され、メモリ破損のリスクが排除されます。

## コアとなるコードの変更箇所

このコミットでは、主に以下の2つのファイルが変更されています。

1.  **`src/runtime/mcache.go`**:
    *   `mcache`構造体の定義に、`tiny`フィールドがヒープポインタであり、非GC管理メモリにある`mcache`から参照されるため、マーク終了時の`releaseAll`でクリアする必要があるというコメントが追加されました。
    *   `(*mcache).releaseAll()`メソッドの最後に、`c.tiny = nil`と`c.tinyoffset = 0`が追加されました。これにより、マーク終了時に`tiny alloc cache`が明示的にクリアされるようになります。

2.  **`src/runtime/mgc.go`**:
    *   `clearpools()`関数から、`allp`（すべてのプロセッサ）をループして各`p.mcache.tiny`と`p.mcache.tinyoffset`をクリアするコードブロックが削除されました。これは、`tiny alloc cache`のクリア処理が`mcache.releaseAll()`に移動されたためです。

## コアとなるコードの解説

### `src/runtime/mcache.go` の変更

```go
// mcache構造体内のコメント追加
// tiny points to the beginning of the current tiny block, or
// nil if there is no current tiny block.
//
// tiny is a heap pointer. Since mcache is in non-GC'd memory,
// we handle it by clearing it in releaseAll during mark
// termination.
tiny             unsafe.Pointer
tinyoffset       uintptr

// (*mcache).releaseAll() メソッド内の追加
func (c *mcache) releaseAll() {
	// ... 既存のコード ...

	// Clear tinyalloc pool.
	c.tiny = nil
	c.tinyoffset = 0
}
```

*   **コメントの追加**: `tiny`フィールドがヒープポインタであり、`mcache`が非GC管理メモリにあるため、特別な扱いが必要であることを明確にしています。具体的には、マーク終了時に`releaseAll`でクリアされるべきだと指示しています。これは、コードの意図を明確にし、将来のメンテナがこの特殊な状況を理解するのに役立ちます。
*   **`releaseAll()`への追加**: `releaseAll()`は、GCのマーク終了フェーズで呼び出される関数です。この関数が呼び出されると、`mcache`内のすべてのスパン（メモリブロック）が解放され、再利用可能な状態になります。このタイミングで`c.tiny = nil`と`c.tinyoffset = 0`を実行することで、`mcache`が保持していた`tiny alloc cache`への参照が確実にクリアされます。これにより、`mcache`がヒープ上の古い、もしかしたら解放されるべきブロックを指し続けることがなくなります。

### `src/runtime/mgc.go` の変更

```go
// clearpools() 関数から以下のコードブロックを削除
-	for _, p := range &allp {
-		if p == nil {
-			break
-		}
-		// clear tinyalloc pool
-		if c := p.mcache; c != nil {
-			c.tiny = nil
-			c.tinyoffset = 0
-		}
-	}
```

*   **コードブロックの削除**: `clearpools()`関数は、GCのスイープ終了時に呼び出されることが多かった関数です。以前は、この関数内で各プロセッサ（P）の`mcache`をループし、`tiny alloc cache`をクリアしていました。しかし、このクリア処理が`mcache.releaseAll()`に移動されたため、`clearpools()`内のこの冗長で潜在的に問題のあるコードは削除されました。これにより、`tiny alloc cache`のクリアロジックが一箇所に集約され、GCのフェーズとより適切に同期されるようになりました。

これらの変更により、Goランタイムは、`mcache`のような非GC管理メモリからヒープメモリへのポインタを、ライトバリアに過度に依存することなく、より安全かつ堅牢に管理できるようになりました。

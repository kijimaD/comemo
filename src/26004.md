# [インデックス 26004] ファイルの概要

このコミットは、Go言語のドキュメンテーションツール `cmd/doc` および `go doc` コマンドにおけるパッケージ検索の挙動を変更するものです。具体的には、パッケージツリーの走査順序を深さ優先探索（Depth-First Search: DFS）から幅優先探索（Breadth-First Search: BFS）に変更し、特にベンダーパッケージ（vendored packages）の扱いに起因する問題を解決することを目的としています。

Author: Rob Pike <r@golang.org>

    cmd/doc: search the tree in breadth-first order
    
    This is a simple change to the command that should resolve problems like finding
    vendored packages before their non-vendored siblings. By searching in breadth-first
    order, we find the matching package lowest in the hierarchy, which is more likely
    to be correct than the deeper one, such as a vendored package, that will be found

## 元コミット内容

`cmd/doc: search the tree in breadth-first order`

このコミットは、`go doc` コマンドがパッケージツリーを探索する際に、幅優先探索（breadth-first order）を使用するように変更します。これにより、ベンダーパッケージが非ベンダーパッケージよりも優先して見つかってしまうといった問題を解決し、階層のより浅い場所にある、より適切なパッケージが選択されるようになります。

## 変更の背景

Go言語のプロジェクトでは、依存関係をプロジェクト内にコピーして管理する「ベンダー（vendoring）」という手法が用いられることがあります。これは、依存関係のバージョン固定やオフラインビルドなどのメリットがありますが、`go doc` コマンドのようなツールがパッケージを検索する際に問題を引き起こす可能性がありました。

従来の `go doc` コマンドは、パッケージツリーを深さ優先探索（DFS）で走査していました。DFSは、あるパスを深く掘り下げてから次のパスに移るため、もしプロジェクトのルートディレクトリの奥深くにあるベンダーディレクトリ内に、ルートレベルの依存関係と同じ名前のパッケージが存在した場合、DFSではベンダー内のパッケージが先に発見されてしまうことがありました。

例えば、`github.com/foo/bar` というパッケージに依存しているプロジェクトがあり、そのプロジェクトが `vendor/github.com/foo/bar` として依存パッケージをベンダーしていたとします。ユーザーが `go doc github.com/foo/bar` と実行した際に、意図としてはプロジェクトが直接使用している `github.com/foo/bar` のドキュメントを見たいはずです。しかし、DFSでは `vendor/github.com/foo/bar` が先に発見され、そのドキュメントが表示されてしまう可能性がありました。これはユーザーの意図と異なる結果であり、混乱を招く原因となっていました。

このコミットは、この問題を解決するために、パッケージ検索のロジックを幅優先探索に変更することを提案しています。コミットメッセージでは、この変更が「ベンダーパッケージが非ベンダーパッケージよりも先に発見されるような問題を解決するはずだ」と明記されており、Issue #12423 に関連しています。

## 前提知識の解説

### Go ModulesとVendoring

Go言語における依存関係管理は、歴史的にいくつかの変遷を辿ってきました。このコミットが作成された2015年当時は、Go Modulesが導入される前であり、`GOPATH` ベースのワークフローが主流でした。この時代には、サードパーティの依存関係をプロジェクトの `vendor` ディレクトリにコピーして管理する「vendoring」という手法が広く用いられていました。

*   **Vendoring**: 依存関係のソースコードをプロジェクトのリポジトリ内に直接コピーして管理する手法。これにより、外部のパッケージリポジトリがダウンしてもビルドが可能になる、依存関係のバージョンを厳密に固定できる、といったメリットがありました。Go 1.5から公式にサポートされ、`go build` や `go install` コマンドは `vendor` ディレクトリを自動的に探索するようになりました。
*   **`GOPATH`**: Goのワークスペースのルートディレクトリ。Go 1.11でGo Modulesが導入されるまでは、すべてのGoプロジェクトは `GOPATH` 内に配置され、依存関係も `GOPATH/src` 以下にインストールされていました。

### ファイルシステム走査アルゴリズム

*   **深さ優先探索 (Depth-First Search: DFS)**: グラフやツリー構造を探索するアルゴリズムの一つ。可能な限り深くパスを探索し、行き止まりに達したらバックトラックして別のパスを探索します。ファイルシステムの場合、ディレクトリを一つ見つけたら、そのディレクトリの中をさらに深く探索し、そのサブディレクトリの探索が終わってから、親ディレクトリの隣のディレクトリに移るような挙動になります。`filepath.Walk` 関数は、このDFS的な挙動をします。
*   **幅優先探索 (Breadth-First Search: BFS)**: グラフやツリー構造を探索するアルゴリズムの一つ。現在のノードから到達可能なすべての隣接ノードを探索し、それらがすべて探索された後に、次のレベルのノードへと進みます。ファイルシステムの場合、現在のディレクトリ内のすべてのファイルとサブディレクトリを探索し、その後にサブディレクトリの探索に移るような挙動になります。これにより、ルートに近い（階層が浅い）パスが優先的に探索されます。

### `go doc` コマンド

`go doc` コマンドは、Goのパッケージ、関数、型、変数などのドキュメンテーションを表示するためのツールです。例えば、`go doc fmt` と入力すると `fmt` パッケージのドキュメントが表示され、`go doc fmt.Println` と入力すると `fmt` パッケージの `Println` 関数のドキュメントが表示されます。このコマンドは、`GOROOT` や `GOPATH` 内のソースコードを検索してドキュメントを抽出します。

## 技術的詳細

このコミットの主要な変更点は、`src/cmd/doc/dirs.go` ファイル内のパッケージ探索ロジックを、`filepath.Walk` を使用した深さ優先探索から、カスタム実装の幅優先探索へと切り替えたことです。

従来の `walkRoot` 関数は `filepath.Walk` を利用していました。`filepath.Walk` は、指定されたルートディレクトリから再帰的にディレクトリツリーを走査し、各ファイルやディレクトリに対してコールバック関数を呼び出します。この挙動は本質的に深さ優先です。

新しい `bfsWalkRoot` 関数では、2つの文字列スライス `this` と `next` をキューとして使用して幅優先探索を実装しています。
1.  `next` キューに初期のルートディレクトリ（例: `GOROOT/src` や `GOPATH/src` の各エントリ）を追加します。
2.  ループ内で、`this` と `next` を入れ替えます。これにより、前回のパスで発見されたディレクトリが現在のパスで処理される対象となります。
3.  `this` キュー内の各ディレクトリについて、`os.Open` と `fd.Readdir` を使用してその内容を読み取ります。
4.  読み取ったエントリがディレクトリである場合、それが隠しディレクトリ（`.` で始まる）でなければ、そのディレクトリを `next` キューに追加します。これにより、次のパスでこれらのサブディレクトリが探索されます。
5.  現在のディレクトリ内に `.go` ファイルが存在するかどうかをチェックします。存在すれば、そのディレクトリはGoパッケージの候補として `d.scan` チャネルに送信されます。

この幅優先探索により、`go doc` はまずルートディレクトリに近いパッケージを優先的に発見し、処理するようになります。これにより、ベンダーディレクトリ内の同名パッケージよりも、プロジェクトのトップレベルにある意図されたパッケージが先に選択される可能性が高まります。

また、`src/cmd/go/alldocs.go` と `src/cmd/go/doc.go` のドキュメンテーション文字列も更新され、パッケージの検索順序が「幅優先探索で辞書順」であり、「ルートに最も近く、その階層レベルで辞書順で最初に見つかったパッケージが提示される」という新しい挙動が明記されています。`GOROOT` は常に `GOPATH` の前に完全にスキャンされるという点も維持されています。

## コアとなるコードの変更箇所

### `src/cmd/doc/dirs.go`

*   `walkRoot` 関数が `bfsWalkRoot` にリネームされ、その実装が `filepath.Walk` を使用した深さ優先探索から、カスタムの幅優先探索ロジックに完全に置き換えられました。
*   幅優先探索の実装では、`this` と `next` という2つのスライスをキューとして利用し、ディレクトリをレベルごとに処理します。
*   ディレクトリ内の `.go` ファイルの有無をチェックするロジックが `bfsWalkRoot` 関数内に統合されました。
*   `log` パッケージが新しくインポートされ、ディレクトリのオープンや読み取りに失敗した場合のエラーログ出力が追加されました。

### `src/cmd/go/alldocs.go` および `src/cmd/go/doc.go`

*   `go doc` コマンドのヘルプメッセージ内のパッケージ検索順序に関する説明が更新されました。
*   変更前: "For packages, the order of scanning is determined lexically, but the GOROOT tree is always scanned before GOPATH."
*   変更後: "For packages, the order of scanning is determined lexically in breadth-first order. That is, the package presented is the one that matches the search and is nearest the root and lexically first at its level of the hierarchy. The GOROOT tree is always scanned in its entirety before GOPATH."

## コアとなるコードの解説

`src/cmd/doc/dirs.go` の `bfsWalkRoot` 関数がこのコミットの核心です。

```go
func (d *Dirs) bfsWalkRoot(root string) {
	root = path.Join(root, "src")

	// this is the queue of directories to examine in this pass.
	this := []string{}
	// next is the queue of directories to examine in the next pass.
	next := []string{root}

	for len(next) > 0 {
		this, next = next, this[0:0] // nextの内容をthisに移し、nextをクリア
		for _, dir := range this {
			fd, err := os.Open(dir)
			if err != nil {
				log.Printf("error opening %s: %v", dir, err)
				return // TODO? There may be entry before the error.
			}
			entries, err := fd.Readdir(0) // ディレクトリ内のエントリを読み込む
			fd.Close()
			if err != nil {
				log.Printf("error reading %s: %v", dir, err)
				return // TODO? There may be entry before the error.
			}
			hasGoFiles := false
			for _, entry := range entries {
				name := entry.Name()
				// For plain files, remember if this directory contains any .go
				// source files, but ignore them otherwise.
				if !entry.IsDir() {
					if !hasGoFiles && strings.HasSuffix(name, ".go") {
						hasGoFiles = true // .goファイルがあればフラグを立てる
					}
					continue
				}
				// Entry is a directory.
				// No .git or other dot nonsense please.
				if strings.HasPrefix(name, ".") {
					continue // 隠しディレクトリはスキップ
				}
				// Remember this (fully qualified) directory for the next pass.
				next = append(next, filepath.Join(dir, name)) // 次のレベルのディレクトリをnextキューに追加
			}
			if hasGoFiles {
				// It's a candidate.
				d.scan <- dir // .goファイルを含むディレクトリを候補として送信
			}
		}
	}
}
```

このコードは、典型的な幅優先探索の実装パターンを示しています。
1.  `this` と `next` という2つのスライスが、それぞれ現在のレベルで処理すべきディレクトリと、次のレベルで処理すべきディレクトリを保持するキューとして機能します。
2.  外側の `for` ループは、`next` キューが空になるまで（つまり、すべてのディレクトリが探索されるまで）繰り返されます。
3.  ループの各イテレーションで、`this, next = next, this[0:0]` という行が実行されます。これは、`next` の内容を `this` にコピーし、`next` を空のスライスにリセットする効率的な方法です。これにより、現在のレベルのすべてのディレクトリが `this` に入り、次のレベルのディレクトリを収集するための `next` が準備されます。
4.  内側の `for` ループは、`this` キュー内の各ディレクトリを処理します。
5.  `os.Open(dir)` と `fd.Readdir(0)` を使ってディレクトリの内容を読み込みます。
6.  各エントリについて、それがファイルであれば `.go` ファイルであるかをチェックし、`hasGoFiles` フラグを立てます。
7.  それがディレクトリであれば、隠しディレクトリでないことを確認し、`filepath.Join(dir, name)` で完全なパスを構築して `next` キューに追加します。
8.  現在の `dir` が `.go` ファイルを含んでいた場合、そのディレクトリパスを `d.scan` チャネルに送信します。これは、そのディレクトリがGoパッケージの候補であることを意味します。

このロジックにより、`GOROOT` や `GOPATH` の `src` ディレクトリ以下が、ルートから近い順に、かつ同じ階層内では辞書順に探索されるようになります。これにより、ベンダーパッケージのような深い階層にあるパッケージよりも、より浅い階層にあるパッケージが優先的に見つかるため、`go doc` コマンドの挙動がより直感的で期待通りになります。

## 変更の背景

このコミットは、Go 1.4 のリリースノートに、`go/build` パッケージにおける重要な修正（CL 147690043）を反映させるために行われました。この修正は、Go のビルドシステムが特定のファイル名をオペレーティングシステム (GOOS) に特化したものとして誤って解釈するバグを解決するものです。

具体的には、以前の `go/build` パッケージでは、`android.go` のようなファイル名が、たとえそのファイルが Android 専用のコードでなくても、Android OS 専用のファイルとして扱われてしまう問題がありました。これは、Go のビルドタグのドキュメントで規定されている「`_GOOS` サフィックスは非空のプレフィックスとアンダースコアが先行する場合にのみ有効である」というルールが、コードで正しく適用されていなかったためです。

この不整合により、開発者が意図しない形でファイルがビルドに含まれたり除外されたりする可能性があり、予期せぬビルドエラーや動作の不一致を引き起こす可能性がありました。この修正は、コードの動作をドキュメントに合わせることで、ビルドシステムの予測可能性と堅牢性を向上させることを目的としています。

## 前提知識の解説

### Go のビルドタグ (Build Tags)

Go 言語には、特定の条件に基づいてソースファイルをコンパイルに含めるか除外するかを制御するための「ビルドタグ」という強力なメカニズムがあります。これにより、異なるオペレーティングシステム、アーキテクチャ、またはその他のカスタム条件に応じて、コードベースの一部を条件付きでコンパイルすることが可能になります。

ビルドタグには主に2つの形式があります。

1.  **ファイル名サフィックスによるビルドタグ**:
    Go のツールチェインは、ファイル名に特定のサフィックスが含まれている場合、そのファイルを特定の環境に特化したものとして扱います。最も一般的なのは `_GOOS.go` と `_GOOS_GOARCH.go` の形式です。
    *   `_GOOS.go`: 例として `myfile_windows.go` は Windows 環境でのみコンパイルされます。`GOOS` は `linux`, `windows`, `darwin` (macOS), `android` など、Go がサポートするオペレーティングシステムを指します。
    *   `_GOOS_GOARCH.go`: 例として `myfile_linux_amd64.go` は Linux かつ AMD64 アーキテクチャでのみコンパイルされます。`GOARCH` は `amd64`, `arm`, `arm64` など、Go がサポートするアーキテクチャを指します。
    *   このメカニズムの重要な点は、ファイル名全体が `GOOS.go` や `GOARCH.go` のように、プレフィックスなしで OS やアーキテクチャ名のみで構成されている場合、Go ツールチェインはそれを特別なビルドタグとして認識しない、というルールです。このコミットが修正しようとしているのは、まさにこの点です。

2.  **ソースファイル内のビルド制約 (Build Constraints)**:
    ソースファイルの先頭に `// +build` ディレクティブ（Go 1.16 以降は `//go:build`）を記述することで、より柔軟な条件を指定できます。
    例:
    ```go
    // +build linux,amd64
    // または Go 1.16 以降:
    //go:build linux && amd64

    package main

    // ...
    ```
    これは、`linux` と `amd64` の両方のタグが有効な場合にのみ、このファイルがコンパイルされることを意味します。

### `go/build` パッケージ

`go/build` パッケージは、Go のビルドシステムの中核をなすパッケージです。このパッケージは、Go のソースコードを解析し、どのファイルがどのパッケージに属し、どのファイルが特定のビルド条件（ビルドタグ、ファイル名サフィックスなど）に基づいてコンパイルされるべきかを決定するロジックを含んでいます。Go コマンド (`go build`, `go install`, `go test` など) は、内部的にこの `go/build` パッケージを利用して、ビルドプロセスを管理しています。

## 技術的詳細

このコミットが参照している CL 147690043 の技術的な核心は、`go/build` パッケージ内のファイル名解析ロジックの厳密化にあります。

以前の `go/build` パッケージの実装では、ファイル名が `GOOS.go` の形式（例: `android.go`）である場合、それが `GOOS` に特化したファイルであると誤って判断していました。しかし、Go のビルドタグに関する公式ドキュメントでは、ファイル名サフィックスによるビルドタグが有効であるためには、`_GOOS` または `_GOOS_GOARCH` の前に**非空のプレフィックスとアンダースコア**が必要であると明記されていました。例えば、`foo_android.go` は有効ですが、`android.go` は有効ではありません。

CL 147690043 は、このドキュメントとコードの間の不整合を解消しました。具体的には、`src/go/build/build.go` 内のロジックが修正され、ファイル名が `GOOS.go` の形式である場合、それを一般的な Go ソースファイルとして扱い、特定の OS に特化したファイルとしては認識しないようになりました。これにより、`android.go` のようなファイルは、Android 環境でのみコンパイルされるのではなく、すべての環境でコンパイルされるようになります（ただし、ファイル内に明示的なビルド制約がない場合）。

この変更は「破壊的変更」とされています。これは、もし開発者が意図的に `android.go` のようなファイル名を使用して、それが Android 専用のコードとして扱われることを期待していた場合、この修正によってその期待が裏切られ、ビルドが失敗したり、意図しないコードがコンパイルに含まれたりする可能性があるためです。開発者は、このようなファイル名を `mycode_android.go` のように変更し、ドキュメントに準拠した形式にする必要があります。

## コアとなるコードの変更箇所

このコミット自体は `doc/go1.4.txt` というドキュメントファイルのみを変更していますが、その内容は `go/build` パッケージの `src/go/build/build.go` および関連するテストファイル `src/go/build/build_test.go` で行われた実際のコード変更（CL 147690043）を反映したものです。

`src/go/build/build.go` では、ファイル名を解析し、それが特定の OS やアーキテクチャに特化したものであるかを判断するロジックが修正されました。具体的には、ファイル名の末尾が `_GOOS.go` や `_GOOS_GOARCH.go` の形式であるかをチェックする際に、その前にアンダースコアと非空のプレフィックスが存在するかどうかの検証が追加されました。

## コアとなるコードの解説

このコミットが参照する `go/build` パッケージの変更は、Go のビルドシステムがファイル名をどのように解釈するかという、非常に基本的な部分に影響を与えます。

Go のビルドシステムは、ソースファイルをスキャンする際に、そのファイル名が特定の OS やアーキテクチャに特化しているかどうかを判断します。この判断は、ファイル名が `*_GOOS.go` や `*_GOOS_GOARCH.go` のパターンに一致するかどうかで行われます。例えば、`foo_windows.go` は Windows 専用、`bar_linux_amd64.go` は Linux かつ AMD64 専用と認識されます。

しかし、この変更以前は、`android.go` のように、`GOOS` 名が直接ファイル名になっている場合でも、Go ツールチェインがそれを `android` 専用のファイルとして誤って解釈していました。これは、ドキュメントで規定されている「アンダースコアと非空のプレフィックスが必要」というルールが、コードで完全に適用されていなかったためです。

CL 147690043 では、この解釈ロジックが修正され、ファイル名が `GOOS.go` の形式である場合は、もはや特定の OS に特化したファイルとは見なされなくなりました。これにより、Go のビルドシステムの動作が、そのドキュメントと完全に一致するようになり、開発者はファイル名によるビルドタグの挙動をより正確に予測できるようになりました。

この修正は、Go のビルドシステムの堅牢性と予測可能性を高める上で重要です。特に、クロスプラットフォーム開発を行う際に、意図しないファイルがビルドに含まれることによる潜在的なバグを防ぐのに役立ちます。

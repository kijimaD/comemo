# [インデックス 256] ファイルの概要

このコミットは、Go言語の初期のコンパイラである`6g`（AMD64アーキテクチャ向け）のコード生成部分（`src/cmd/6g/cgen.c`）におけるバグ修正です。具体的には、式の両辺が複雑な関数呼び出し（またはそれに準ずる高コストな評価を伴う式）である場合に、コンパイラが致命的なエラーを発生させていた問題を解決します。この修正により、一時変数を用いて右辺の評価を先行させ、その結果を左辺の評価に組み込むことで、正しい評価順序とコンパイルの成功を保証します。

## 元コミット内容

このコミットは、Goコンパイラ`6g`において、「両辺が関数呼び出しである」という状況を修正するものです。以前のバージョンでは、このようなケースでコンパイラがエラーを発生させていましたが、この変更により、両辺に複雑な式（特に関数呼び出し）が存在する場合でも、正しくコードを生成できるようになりました。

## 変更の背景

Go言語は、式の評価順序に関して厳格な左から右への評価を保証しています。特に、関数呼び出しを含む式においては、引数の関数呼び出しは左から右に評価されることが言語仕様で定められています。

このコミットが作成された2008年6月は、Go言語がまだ開発の初期段階にあり、コンパイラも活発に開発・改善されていた時期です。初期のコンパイラ実装では、式の両辺がそれぞれ独立した複雑な評価（例えば、副作用を持つ関数呼び出し）を必要とする場合に、その評価順序の管理やレジスタ割り当ての最適化が困難であったり、予期せぬ競合状態を引き起こしたりすることがありました。

具体的には、`cgen.c`内のコード生成ロジックにおいて、`nl`（左ノード）と`nr`（右ノード）の両方が`ullman >= UINF`という条件を満たす場合、コンパイラは「cgen: both sides functions」（両辺が関数である）という致命的なエラーを発生させていました。これは、コンパイラがその時点での実装では、両方の複雑な式を同時に、かつ正しい評価順序で処理する安全な方法を見つけられなかったためと考えられます。このような状況は、例えば `f() + g()` のような式で、`f()` と `g()` がそれぞれ複雑な処理や副作用を持つ場合に発生し得ます。

このエラーは、Go言語の厳格な評価順序の保証と矛盾し、開発者が特定のコードパターンを使用できないという制約を課していました。Ken Thompsonによるこの修正は、この根本的な問題を解決し、より多様な式構造をコンパイル可能にすることで、Go言語の表現力を向上させることを目的としています。

## 前提知識の解説

### Goコンパイラ `6g`

`6g`は、Go言語の初期のコンパイラツールチェーンである`gc`の一部で、特にAMD64（64ビットx86）アーキテクチャをターゲットとしていました。当時のGoコンパイラはC言語で書かれており、`6g`はそのコードベースの一部でした。Go言語の初期の迅速なプロトタイピングと開発を支えた重要なコンポーネントです。

### `cgen.c`

`cgen.c`は、Goコンパイラのコード生成フェーズを担当するC言語のソースファイルです。コンパイラのバックエンドの一部として機能し、フロントエンドによって生成された抽象構文木（AST）や中間表現を、ターゲットアーキテクチャ（この場合はAMD64）の機械語に近い形式に変換する役割を担います。このファイルには、様々な式の種類や演算子に対するコード生成ロジックが含まれています。

### Ullman Number (ウルマン数) と `UINF`

Jeffrey D. Ullmanは、コンパイラ設計の分野で非常に影響力のある計算機科学者であり、Sethi-Ullmanアルゴリズムの共同開発者として知られています。Sethi-Ullmanアルゴリズムは、式ツリーの評価において、必要なレジスタ数を最小化しながら最適なコードを生成するための手法です。

*   **Ullman Number**: コンパイラ理論において、式ツリーの各ノードに割り当てられる数値で、そのノードを評価するために必要なレジスタの最小数を示します。この数値は、式の複雑さや、その評価がどれだけの計算資源（特にレジスタ）を必要とするかの指標となります。
*   **`UINF`**: この文脈では、「無限大 (Infinity)」を意味する定数であると推測されます。`ullman >= UINF`という条件は、そのノード（式）の評価が非常に複雑であるか、あるいは通常のレジスタ割り当て戦略では処理しきれないほど多くのレジスタを必要とする、または特別な処理が必要なケースを示唆しています。関数呼び出しは、その性質上、多くのレジスタを使用し、制御フローを複雑にするため、高いUllman数を持ちやすいです。この`UINF`は、コンパイラが特定の複雑な式を直接処理できない、あるいは特別な戦略が必要であると判断するための閾値として機能していたと考えられます。

### 式の評価順序と副作用

プログラミング言語において、式が評価される順序は非常に重要です。特に、関数呼び出しが副作用（例: グローバル変数の変更、I/O操作、メモリ割り当てなど）を持つ場合、評価順序がプログラムの最終的な結果に直接影響を与える可能性があります。Go言語は、このような問題を避けるために、式の評価順序を厳格に定義しています。このコミットは、その厳格な評価順序をコンパイラ内部で正しく処理するための初期の取り組みの一つと言えます。

## 技術的詳細

このコミットの技術的な核心は、コンパイラが式の両辺に複雑な評価を伴うノード（`ullman >= UINF`）を検出した場合の処理方法を変更した点にあります。

元のコードでは、`nl`（左ノード）と`nr`（右ノード）の両方が`ullman >= UINF`である場合に、`fatal("cgen: both sides functions")`というエラーでコンパイルを中断していました。これは、コンパイラがこのような状況で正しいコードを生成するためのロジックを持っていなかったことを意味します。

修正後のコードは、この問題を解決するために以下の戦略を採用しています。

1.  **右辺の先行評価**: まず、右辺の複雑な式（`nr`）を評価し、その結果を一時変数に格納します。
    *   `tempname(&n1, nr->type);`：右辺の型に基づいて一時変数`n1`を生成します。
    *   `cgen(nr, &n1);`：右辺`nr`のコードを生成し、その結果を一時変数`n1`に格納します。
2.  **式の再構築**: 元の式`n`をコピーして新しいノード`n2`を作成し、その右辺を先ほど評価した一時変数`n1`に置き換えます。
    *   `n2 = *n;`：元の式ノード`n`の内容を`n2`にコピーします。
    *   `n2.right = &n1;`：`n2`の右辺を、評価済みの一時変数`n1`への参照に置き換えます。これにより、`n2`の右辺はもはや複雑な関数呼び出しではなく、単純な変数参照となります。
3.  **左辺と再構築された右辺の評価**: 最後に、左辺と、一時変数に置き換えられた右辺を持つ新しい式`n2`を評価し、その結果を最終的な結果レジスタ`res`に格納します。
    *   `cgen(&n2, res);`：再構築された式`n2`のコードを生成し、その結果を`res`に格納します。

このアプローチにより、Go言語の「左から右への評価」という原則を維持しつつ、コンパイラが複雑な式を段階的に処理できるようになります。右辺の関数呼び出しが先に評価され、その結果が一時的に保持されるため、左辺の評価と競合することなく、かつ正しい順序で全体の式が評価されます。これは、コンパイラが複雑な依存関係を持つ式を安全に処理するための基本的な手法の一つです。

## コアとなるコードの解説

変更は`cgen`関数内、特に`nl != N && nl->ullman >= UINF`と`nr != N && nr->ullman >= UINF`という二重の条件分岐のブロックで行われています。この条件は、式の左ノード(`nl`)と右ノード(`nr`)の両方が、非常に複雑な評価（`ullman >= UINF`）を必要とする場合に真となります。

*   **削除された行**:
    *   `dump("fncalls", n);`：デバッグ目的で、問題のあるノード`n`の情報を出力していたと考えられます。
    *   `fatal("cgen: both sides functions");`：この行が、両辺が複雑な式である場合にコンパイラを強制終了させていた原因です。

*   **追加された行**:
    *   `tempname(&n1, nr->type);`
        *   `tempname`関数は、一時的な変数（ノード）を生成するために使用されます。
        *   `&n1`は、新しく生成される一時変数のノード構造体へのポインタです。
        *   `nr->type`は、右辺の式`nr`の型を指定しており、一時変数`n1`がその型を持つようにします。
        *   これにより、右辺の評価結果を格納するための一時的な記憶領域が準備されます。
    *   `cgen(nr, &n1);`
        *   `cgen`関数は、Goコンパイラのコード生成の主要な関数です。
        *   この呼び出しは、右辺の式`nr`のコードを生成し、その評価結果を一時変数`n1`に格納するように指示しています。これにより、右辺の複雑な計算が先行して完了します。
    *   `n2 = *n;`
        *   元の式ノード`n`の内容（演算子、左辺など）を、新しいノード`n2`にコピーします。これは、元の式の構造を保持しつつ、右辺だけを変更するための準備です。
    *   `n2.right = &n1;`
        *   コピーされたノード`n2`の右辺を、先ほど評価結果が格納された一時変数`n1`への参照に置き換えます。これにより、`n2`は「左辺と、評価済みの一時変数」という形になり、右辺の複雑さが解消されます。
    *   `cgen(&n2, res);`
        *   最後に、再構築されたノード`n2`（左辺と、一時変数に置き換えられた右辺を持つ）のコードを生成し、その最終結果を`res`（最終的な結果を格納するレジスタまたはメモリ位置）に格納します。

この一連の変更により、コンパイラは、両辺に複雑な式を持つ場合でも、右辺を一時変数に評価・格納し、その後、その一時変数を使って全体の式を評価するという、段階的かつ安全なコード生成パスを実行できるようになりました。

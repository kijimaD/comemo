# [インデックス 23872] ファイルの概要

このコミットは、Go言語の標準ライブラリ `hash/crc32` パッケージにおけるCRC-32計算のパフォーマンス改善に関するものです。特に、IEEEポリノミアルを使用するCRC-32計算において、「Slicing-By-8」アルゴリズムを導入することで、大きなデータブロックに対する処理速度を大幅に向上させています。

## 元コミット内容

`hash/crc32: speedup crc32 of IEEE using slicingBy8`

このコミットは、IEEEポリノミアルを用いたCRC-32計算をSlicing-By-8アルゴリズムで高速化することを目的としています。このアルゴリズムは既存の手法よりも大幅な性能改善をもたらし、特に実用上最も一般的なIEEE CRC-32に適用されます。

Mac OS X 10.9でのベンチマーク結果は以下の通りです。

| ベンチマーク              | 旧 MB/s | 新 MB/s | 速度向上 |
| :------------------------ | :------ | :------ | :------- |
| `BenchmarkIEEECrc1KB`     | 349.40  | 353.03  | 1.01x    |
| `BenchmarkIEEECrc4KB`     | 351.55  | 934.35  | 2.66x    |
| `BenchmarkCastagnoliCrc1KB` | 7037.58 | 7392.63 | 1.05x    |

Slicing-By-8アルゴリズムは8KBのルックアップテーブルを必要とするため、4KBより大きいブロックに対してのみ有効化されます。IEEE CRC-32において約2.6倍の性能向上が見られます。

## 変更の背景

CRC-32（Cyclic Redundancy Check）は、データ転送や保存におけるエラー検出によく用いられるハッシュ関数の一種です。Go言語の `hash/crc32` パッケージは、このCRC-32計算を提供しますが、特に大きなデータブロックに対する計算速度は、アプリケーションのパフォーマンスに影響を与える可能性があります。

従来のCRC-32計算は、バイト単位で処理を行うテーブルルックアップ方式が一般的でした。これはシンプルで実装しやすい反面、CPUのパイプライン処理効率やキャッシュ利用効率の点で限界がありました。特に、データ量が増えるにつれて、このボトルネックが顕著になります。

このコミットの背景には、IEEE 802.3（イーサネット）などで広く使われるIEEEポリノミアルを用いたCRC-32計算の高速化が求められていたことがあります。より効率的なアルゴリズムを導入することで、Goアプリケーションが大量のデータを扱う際のCRC-32計算のオーバーヘッドを削減し、全体的なパフォーマンスを向上させることが目的でした。

## 前提知識の解説

### CRC-32 (Cyclic Redundancy Check)

CRC-32は、データの整合性を確認するためのエラー検出コードです。送信側でデータからCRC値を計算し、受信側で同じ計算を行い、両者のCRC値を比較することで、データが転送中に破損していないかを確認します。CRCは、多項式除算の原理に基づいており、特定の「ポリノミアル（生成多項式）」によって計算方法が定義されます。

*   **ポリノミアル**: CRC計算の核となる数学的な多項式です。異なるポリノミアルは異なるCRCアルゴリズムを定義します。最も一般的なものの一つがIEEE 802.3で定義されているIEEEポリノミアル（`0xEDB88320` または `0x04C11DB7` のビット反転）です。
*   **ルックアップテーブル方式**: 多くのCRC実装では、計算を高速化するために256エントリのルックアップテーブルを使用します。各エントリは、1バイトのデータに対するCRC計算の結果を事前に計算して格納したものです。これにより、バイトごとに多項式除算を直接行うよりも高速に計算できます。

### Slicing-By-8 アルゴリズム

Slicing-By-8は、CRC計算をさらに高速化するための高度なアルゴリズムです。従来のルックアップテーブル方式が1バイトずつ処理するのに対し、Slicing-By-8は一度に8バイト（64ビット）のデータを処理します。

このアルゴリズムは、8つの異なるルックアップテーブル（それぞれ256エントリ）を使用します。各テーブルは、入力データの異なるバイト位置に対応するCRC値を計算するために特化されています。8バイトの入力データが与えられると、各バイトは対応するテーブルで処理され、その結果がXOR演算で結合されます。これにより、CPUの並列処理能力をより効率的に利用し、特に現代のプロセッサで高いスループットを実現します。

Slicing-By-8の主な利点は以下の通りです。
*   **並列処理**: 複数のバイトを同時に処理できるため、計算速度が大幅に向上します。
*   **キャッシュ効率**: 複数のテーブルを使用しますが、適切に設計されていればキャッシュミスを最小限に抑えつつ、より多くのデータを一度に処理できます。
*   **大きなデータブロックでの効果**: アルゴリズムのセットアップコスト（8つのルックアップテーブルの初期化）があるため、小さなデータブロックでは従来の方式と比べてメリットが少ないか、むしろ遅くなることもあります。しかし、数KB以上の大きなデータブロックでは、その真価を発揮します。

### `sync.Once`

Go言語の `sync` パッケージに含まれる `Once` 型は、特定の処理がプログラムの実行中に一度だけ実行されることを保証するためのプリミティブです。これは、リソースの初期化（例：ルックアップテーブルの生成）など、一度だけ行えばよいが、いつ行われるか分からない（または複数回呼び出される可能性がある）場合に非常に有用です。

`Once.Do(f func())` メソッドは、`f` が一度だけ実行されることを保証します。複数のゴルーチンが同時に `Do` を呼び出しても、`f` は一度だけ実行され、他のゴルーチンは `f` の完了を待ちます。

## 技術的詳細

このコミットでは、`hash/crc32` パッケージにSlicing-By-8アルゴリズムを導入し、特にIEEEポリノミアルを使用するCRC-32計算を高速化しています。

1.  **`slicing8Table` 型の導入**:
    `type slicing8Table [8]Table` という新しい型が定義されています。これは、Slicing-By-8アルゴリズムで使用する8つのルックアップテーブルを保持するための配列です。

2.  **`makeTable8` 関数の追加**:
    `func makeTable8(poly uint32) *slicing8Table` 関数が追加されました。この関数は、指定されたポリノミアルに基づいて8つのルックアップテーブルを生成します。最初のテーブル (`t[0]`) は通常の `makeTable` で生成され、残りの7つのテーブルは `t[0]` を基に、CRC計算の特性を利用して効率的に生成されます。このテーブル生成は、Slicing-By-8アルゴリズムの初期化ステップであり、一度だけ実行される必要があります。

3.  **`iEEETable8` と `iEEETable8Once` の導入**:
    `var iEEETable8 *slicing8Table` は、IEEEポリノミアル用のSlicing-By-8ルックアップテーブルを保持するグローバル変数です。
    `var iEEETable8Once sync.Once` は、`iEEETable8` の初期化が一度だけ行われることを保証するために使用されます。これにより、複数のゴルーチンが同時にCRC計算を要求しても、テーブルの生成は一度だけ行われ、競合状態を防ぎます。

4.  **`updateSlicingBy8` 関数の追加**:
    `func updateSlicingBy8(crc uint32, tab *slicing8Table, p []byte) uint32` 関数が追加されました。これがSlicing-By-8アルゴリズムの核心部分です。
    この関数は、入力データ `p` を8バイトずつ処理します。各8バイトのブロックに対して、8つのルックアップテーブルを効率的に使用してCRC値を更新します。残りのバイト（8バイト未満の端数）は、従来のバイト単位の `update` 関数で処理されます。

5.  **`Update` 関数の変更**:
    既存の `Update` 関数が変更され、IEEEポリノミアルが使用され、かつ入力データ `p` の長さが4KB（4096バイト）以上の場合にのみ、新しく追加された `updateSlicingBy8` 関数を呼び出すようになりました。
    `if tab == IEEETable && len(p) >= 4096 { ... }`
    この条件分岐により、Slicing-By-8アルゴリズムのセットアップコストとメモリ使用量（8KBのルックアップテーブル）が、パフォーマンス上のメリットを上回る小さなデータブロックでは、従来の効率的な方法が引き続き使用されます。

6.  **`ChecksumIEEE` 関数の変更**:
    `ChecksumIEEE` 関数も、内部で `update` ではなく `Update` を呼び出すように変更されました。これにより、`ChecksumIEEE` を呼び出した際にも、データサイズに応じてSlicing-By-8アルゴリズムの恩恵を受けられるようになります。

7.  **ベンチマークの追加**:
    `crc32_test.go` に `BenchmarkIEEECrc4KB` が追加され、4KBのデータブロックに対するIEEE CRC-32のパフォーマンスを測定できるようになりました。これにより、Slicing-By-8アルゴリズムの性能改善効果を具体的に確認できます。また、既存のベンチマーク名もより具体的に変更されています。

この変更により、IEEE CRC-32計算において、特に大きなデータブロック（4KB以上）を扱う際のパフォーマンスが大幅に向上しました。ベンチマーク結果が示すように、4KBのデータでは約2.6倍の速度向上が実現されています。

## コアとなるコードの変更箇所

### `src/hash/crc32/crc32.go`

```go
// slicing8Table is array of 8 Tables
type slicing8Table [8]Table

// iEEETable8 is the slicing8Table for IEEE
var iEEETable8 *slicing8Table
var iEEETable8Once sync.Once

// makeTable8 returns slicing8Table constructed from the specified polynomial.
func makeTable8(poly uint32) *slicing8Table {
	t := new(slicing8Table)
	t[0] = *makeTable(poly)
	for i := 0; i < 256; i++ {
		crc := t[0][i]
		for j := 1; j < 8; j++ {
			crc = t[0][crc&0xFF] ^ (crc >> 8)
			t[j][i] = crc
		}
	}
	return t
}

// updateSlicingBy8 updates CRC using Slicing-by-8
func updateSlicingBy8(crc uint32, tab *slicing8Table, p []byte) uint32 {
	crc = ^crc
	for len(p) > 8 {
		crc ^= uint32(p[0]) | uint32(p[1])<<8 | uint32(p[2])<<16 | uint32(p[3])<<24
		crc = tab[0][p[7]] ^ tab[1][p[6]] ^ tab[2][p[5]] ^ tab[3][p[4]] ^
			tab[4][crc>>24] ^ tab[5][(crc>>16)&0xFF] ^
			tab[6][(crc>>8)&0xFF] ^ tab[7][crc&0xFF]
		p = p[8:]
	}
	crc = ^crc
	return update(crc, &tab[0], p)
}

// Update returns the result of adding the bytes in p to the crc.
func Update(crc uint32, tab *Table, p []byte) uint32 {
	if tab == castagnoliTable {
		return updateCastagnoli(crc, p)
	}
	// only use slicing-by-8 when input is larger than 4KB
	if tab == IEEETable && len(p) >= 4096 {
		iEEETable8Once.Do(func() {
			iEEETable8 = makeTable8(IEEE)
		})
		return updateSlicingBy8(crc, iEEETable8, p)
	}
	return update(crc, tab, p)
}

// ChecksumIEEE returns the CRC-32 checksum of data
// using the IEEE polynomial.
func ChecksumIEEE(data []byte) uint32 { return Update(0, IEEETable, data) }
```

## コアとなるコードの解説

### `src/hash/crc32/crc32.go`

*   **`slicing8Table` と `iEEETable8`, `iEEETable8Once`**:
    `slicing8Table` は、Slicing-By-8アルゴリズムに必要な8つのCRCルックアップテーブルを格納するための配列型です。`iEEETable8` はIEEEポリノミアル専用のこのテーブルのインスタンスを指し、`iEEETable8Once` は `sync.Once` を利用して、このテーブルがプログラム実行中に一度だけ初期化されることを保証します。これにより、テーブル生成のオーバーヘッドが最小限に抑えられ、スレッドセーフな初期化が実現されます。

*   **`makeTable8` 関数**:
    この関数は、Slicing-By-8アルゴリズムで使用する8つのルックアップテーブルを生成します。最初のテーブル `t[0]` は通常の `makeTable` 関数で生成されます。残りの7つのテーブル `t[1]` から `t[7]` は、`t[0]` の値とCRC計算の数学的特性を利用して効率的に導出されます。具体的には、`crc = t[0][crc&0xFF] ^ (crc >> 8)` という操作を繰り返すことで、各テーブルのエントリが計算されます。これは、CRC計算が線形であるという性質を利用した最適化です。

*   **`updateSlicingBy8` 関数**:
    この関数は、Slicing-By-8アルゴリズムを実装したものです。
    1.  `crc = ^crc`: CRC計算の初期ステップとして、現在のCRC値をビット反転します。
    2.  `for len(p) > 8`: 入力データ `p` を8バイトのチャンクに分割して処理します。
    3.  `crc ^= uint32(p[0]) | ... | uint32(p[3])<<24`: 最初の4バイトをCRC値にXORします。これは、Slicing-By-8アルゴリズムの特定の最適化パターンの一部です。
    4.  `crc = tab[0][p[7]] ^ tab[1][p[6]] ^ ... ^ tab[7][crc&0xFF]`: ここがSlicing-By-8の核心です。8バイトの入力データ（`p[0]`から`p[7]`）と、現在のCRC値の下位バイト（`crc&0xFF`）を、それぞれ対応するルックアップテーブル `tab[0]`から`tab[7]`で処理し、その結果をXOR結合して新しいCRC値を生成します。これにより、一度に8バイトのデータを効率的に処理します。
    5.  `p = p[8:]`: 処理した8バイトをデータスライスから削除し、次のチャンクに進みます。
    6.  `crc = ^crc`: 最終的なCRC値をビット反転します。
    7.  `return update(crc, &tab[0], p)`: 8バイト未満の残りのデータ（端数）は、従来のバイト単位の `update` 関数を使用して処理されます。

*   **`Update` 関数**:
    この関数は、CRC計算のメインエントリポイントです。
    1.  `if tab == castagnoliTable`: Castagnoliポリノミアルの場合は、専用の高速化された `updateCastagnoli` 関数を呼び出します。
    2.  `if tab == IEEETable && len(p) >= 4096`: ここが今回のコミットの主要な変更点です。もしテーブルがIEEEポリノミアル用であり、かつ入力データの長さが4096バイト（4KB）以上であれば、`iEEETable8Once.Do` を使って `iEEETable8` を一度だけ初期化し、その後 `updateSlicingBy8` 関数を呼び出してSlicing-By-8アルゴリズムでCRCを計算します。この条件により、Slicing-By-8のメリットが最大限に活かされる大きなデータブロックにのみ適用されます。
    3.  `return update(crc, tab, p)`: 上記の条件に合致しない場合は、従来のバイト単位の `update` 関数が使用されます。

*   **`ChecksumIEEE` 関数**:
    この関数は、IEEEポリノミアルを用いたCRC-32計算の簡便なラッパーです。変更前は直接 `update` を呼び出していましたが、変更後は `Update` 関数を呼び出すように修正されました。これにより、`ChecksumIEEE` を使用するコードも、自動的にSlicing-By-8による高速化の恩恵を受けられるようになります。

### `src/hash/crc32/crc32_test.go`

*   **ベンチマーク関数の追加と改名**:
    `BenchmarkIEEECrc1KB` は、既存の `BenchmarkCrc32KB` をIEEEポリノミアルに特化した名前に変更したものです。
    `BenchmarkIEEECrc4KB` は、4KBのデータブロックに対するIEEE CRC-32のパフォーマンスを測定するために新しく追加されました。このベンチマークは、Slicing-By-8アルゴリズムが有効になるデータサイズ（4KB以上）での性能改善を明確に示すために重要です。
    `BenchmarkCastagnoliCrc1KB` は、Castagnoliポリノミアルのベンチマークを明確にするために追加されました。

これらの変更により、Go言語の `hash/crc32` パッケージは、IEEE CRC-32計算において、特に大きなデータブロックに対する処理性能を大幅に向上させ、より効率的なデータ整合性チェックを可能にしました。

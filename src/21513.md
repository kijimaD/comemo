# [インデックス 21513] ファイルの概要

`src/cmd/dist/vfp_arm.s`は、Goコンパイラツールチェーンの一部である`cmd/dist`ディレクトリに位置するアセンブリファイルです。このファイルは、ARMアーキテクチャにおいて、特定のVFP (Vector Floating Point) 命令セットのサポートを検出するために使用されます。具体的には、VFPv1とVFPv3の存在をテストするためのアセンブリコードを含んでいます。`cmd/dist`はGoのビルドプロセスにおいて、ターゲットシステムのCPU機能を特定し、それに応じてビルド設定を調整する役割を担っています。

## コミット

このコミットは、Goツールチェーンの`cmd/dist`におけるARM VFP検出の信頼性を向上させることを目的としています。主な変更点は、Goのアセンブラ（当時の`5a`）が特定のARM浮動小数点命令を誤って解釈したり、認識できない形式として扱ったりする問題を回避するために、アセンブリ命令を直接32ビットのワードとして埋め込むように修正した点です。また、Goのアセンブラの命名規則に従い、関数宣言にインターパンクト（中点 `·`）を追加しています。

## 変更の背景

この変更の背景には、Goのカスタムアセンブラ（当時の`5a`、現在は`go tool compile`に統合）がARMアーキテクチャの特定の浮動小数点命令（VFP命令）を正しく処理できないという問題がありました。

1.  **アセンブラの解釈問題**: Goのアセンブラは、一般的なGNUアセンブラなどとは異なり、独自の構文とセマンティクスを持っています。これにより、特定の複雑なARM命令、特に浮動小数点関連の命令をアセンブラが「知らない形式」として扱ったり、意図しない形で命令を書き換えたりする可能性がありました。これは、VFP機能の正確な検出を妨げる原因となります。
2.  **命令の直接埋め込みの必要性**: VFP機能の検出は、特定のVFP命令を実行してみて、それがクラッシュするかどうかで判断するという手法が取られています。このため、アセンブラの解釈に依存せず、確実に特定の機械語命令が生成される必要がありました。
3.  **Goアセンブラの命名規則**: Goのアセンブラでは、Goのコードから呼び出される関数や、パッケージ内部で利用されるシンボルには、特定の命名規則があります。特に、パッケージローカルなシンボルやGoコードから参照されるシンボルには、シンボル名の前にインターパンクト（中点 `·`）を付ける慣習があります。これにより、リンカがシンボルを正しく解決し、Goのランタイムがアセンブリ関数を認識できるようになります。このコミット以前は、この規則が適用されていなかったため、修正が必要でした。

これらの問題に対処するため、VFP命令を直接機械語の32ビットワードとして埋め込み、アセンブラの解釈をバイパスするとともに、関数宣言をGoアセンブラの標準的な命名規則に合わせる変更が行われました。

## 前提知識の解説

### Goアセンブラ

Go言語は、独自のカスタムアセンブラを使用しています。これは、GNUアセンブラ（GAS）やLLVMアセンブラとは異なる構文とセマンティクスを持ちます。Goアセンブラは、クロスコンパイル環境での一貫性を保ち、Goランタイムの特定の要件（スタック管理、ガベージコレクションとの連携など）を満たすように設計されています。

*   **擬似レジスタ**: Goアセンブラには、`SB` (Static Base)、`FP` (Frame Pointer)、`SP` (Stack Pointer)、`PC` (Program Counter) といった擬似レジスタが存在します。
    *   `SB`: グローバルシンボルや静的データへのオフセットを示す基準点。
    *   `FP`: 関数引数へのオフセットを示す基準点。
    *   `SP`: 現在のスタックフレームの先頭を示す基準点。
*   **`TEXT`ディレクティブ**: Goアセンブラで関数を定義するために使用されます。
    *   `TEXT ·FunctionName(SB),FLAGS,$framesize-argumentsize` の形式で記述されます。
    *   `·FunctionName`: 関数の名前。Goコードから呼び出される関数やパッケージローカルな関数には、通常、名前の前にインターパンクト（`·`）が付きます。
    *   `(SB)`: シンボルがグローバルであることを示し、`SB`からのオフセットで参照されることを意味します。
    *   `FLAGS`: 関数の振る舞いを制御するフラグ（例: `NOSPLIT`はスタック分割を無効にする）。
    *   `$framesize-argumentsize`: `$framesize`は関数が使用するローカルスタックフレームのサイズ、$argumentsize`は関数に渡される引数の合計サイズを示します。
*   **`WORD`ディレクティブ**: 32ビットの定数値を直接、生成されるバイナリの命令ストリームに埋め込むために使用されます。これは、アセンブラが特定の命令を直接サポートしていない場合や、特定の機械語命令を正確に生成したい場合に利用されます。

### ARM VFP (Vector Floating Point)

ARM (Advanced RISC Machine) プロセッサは、組み込みシステムからスマートフォン、サーバーまで幅広く利用されているCPUアーキテクチャです。VFP (Vector Floating Point) は、ARMアーキテクチャにおける浮動小数点演算ユニットの拡張機能です。

*   **VFPv1**: ARMv5TE以降のアーキテクチャで導入された最初のVFPバージョン。単精度および倍精度の浮動小数点演算をサポートします。
*   **VFPv3**: ARMv6以降のアーキテクチャで導入されたVFPの改良版。レジスタセットの拡張（D0-D31）や、より高速な演算、一部の新しい命令が追加されています。
*   **`VMOV.F64`命令**: VFP命令セットの一部で、浮動小数点レジスタ間でデータを移動したり、定数を浮動小数点レジスタにロードしたりするために使用されます。
    *   `VMOV.F64 D0, D0`: 倍精度浮動小数点レジスタD0の内容をD0自身に移動する（実質的には何もしないが、VFPv1の存在をテストするために使用される）。
    *   `VMOV.F64 #112, D0`: 倍精度浮動小数点レジスタD0に定数112をロードする（VFPv3で導入された命令で、VFPv3の存在をテストするために使用される）。

## 技術的詳細

このコミットの技術的な核心は、Goアセンブラの挙動を回避し、特定のARM VFP命令を確実に実行させるための手法にあります。

Goアセンブラは、ソースコードのアセンブリ命令を直接機械語に変換する際に、独自の最適化や解釈を行うことがあります。しかし、`VMOV.F64`のような特定のVFP命令は、当時のGoアセンブラ（`5a`）にとって「未知の形式」であったり、意図しない形で命令を書き換えたりする可能性がありました。これは、GoのビルドプロセスがARMシステム上でVFP機能を正確に検出する上で問題となります。

この問題を解決するために、開発者は`VMOV.F64`命令を直接アセンブリコードとして記述する代わりに、その命令に対応する**機械語のバイト列を`WORD`ディレクティブを使って埋め込む**というアプローチを取りました。

*   **`VMOV.F64 D0, D0` の場合**:
    *   この命令の機械語表現は `0xeeb00b40` です。
    *   元のコードでは `VMOV.F64 D0, D0` と記述されていましたが、これを `WORD $0xeeb00b40` に変更することで、アセンブラの解釈を介さずに、この正確な32ビットの機械語がバイナリに埋め込まれるようになります。これにより、VFPv1の存在をテストするための命令が確実に実行されます。

*   **`VMOV.F64 #112, D0` の場合**:
    *   この命令の機械語表現は `0xeeb70b00` です。
    *   同様に、元の `VMOV.F64 $112, D0` を `WORD $0xeeb70b00` に置き換えることで、VFPv3の存在をテストするための命令が確実に実行されます。

これらの機械語は、ARMのVFP命令エンコーディング規則に基づいています。例えば、`0xeeb00b40` は、VFPデータ処理命令の形式に従い、`VMOV`操作、レジスタD0、およびその他のエンコーディングビットが組み合わされた結果です。

また、関数名にインターパンクト（`·`）を追加する変更は、Goアセンブラのシンボル解決メカニズムに準拠するためのものです。`TEXT useVFPv1(SB)` を `TEXT ·useVFPv1(SB)` に変更することで、`useVFPv1` 関数がGoのランタイムから正しく参照可能なシンボルとして扱われるようになります。これは、Goのリンカがパッケージローカルなシンボルを解決する際に使用する慣習であり、Goコードとアセンブリコード間の連携を保証するために不可欠です。

このコミットにより、GoのビルドシステムはARM環境におけるVFP機能の有無をより正確に検出し、それに基づいて適切なコードパスを選択できるようになり、Goプログラムの実行効率と互換性が向上します。

## コアとなるコードの解説

このコミットでは、`src/cmd/dist/vfp_arm.s`ファイル内の2つの関数`useVFPv1`と`useVFPv3`が変更されています。これらの関数は、それぞれVFPv1とVFPv3の浮動小数点ユニットがARMプロセッサに存在するかどうかをテストするために使用されます。

1.  **`TEXT useVFPv1(SB),NOSPLIT,$0` から `TEXT ·useVFPv1(SB),NOSPLIT,$0` への変更**:
    *   関数名の前にインターパンクト（`·`）が追加されました。これは、Goアセンブラの命名規則に従い、この関数がGoのランタイムから呼び出し可能であることを示すための変更です。Goのリンカは、このインターパンクトを見て、シンボルを正しく解決します。

2.  **`VMOV.F64 D0, D0` から `WORD $0xeeb00b40 // vomv.f64 d0, d0` への変更**:
    *   元の`VMOV.F64 D0, D0`というアセンブリ命令が、`WORD $0xeeb00b40`という`WORD`ディレクティブに置き換えられました。
    *   `VMOV.F64 D0, D0`は、倍精度浮動小数点レジスタD0の内容をD0自身に移動する命令で、VFPv1の存在をテストするために使用されます。
    *   `0xeeb00b40`は、この`VMOV.F64 D0, D0`命令に対応する32ビットの機械語（バイナリコード）です。
    *   この変更により、Goアセンブラがこの命令を誤って解釈したり、書き換えたりするのを防ぎ、確実にこの特定の機械語が生成されるようにします。コメントで元の命令が示されています。

3.  **`TEXT useVFPv3(SB),NOSPLIT,$0` から `TEXT ·useVFPv3(SB),NOSPLIT,$0` への変更**:
    *   `useVFPv1`と同様に、`useVFPv3`関数もGoアセンブラの命名規則に合わせるためにインターパンクトが追加されました。

4.  **`VMOV.F64 $112, D0` から `WORD $0xeeb70b00 // vmov.f64 d0, #112` への変更**:
    *   元の`VMOV.F64 $112, D0`というアセンブリ命令が、`WORD $0xeeb70b00`という`WORD`ディレクティブに置き換えられました。
    *   `VMOV.F64 $112, D0`は、定数112を倍精度浮動小数点レジスタD0にロードする命令で、VFPv3の存在をテストするために使用されます。この命令はVFPv3で導入されたものです。
    *   `0xeeb70b00`は、この`VMOV.F64 $112, D0`命令に対応する32ビットの機械語です。
    *   この変更も、アセンブラの解釈をバイパスし、特定の機械語を確実に生成することを目的としています。

これらの変更は、GoのビルドプロセスがARM環境でVFP機能を正確に検出し、それに基づいて適切なコンパイルオプションやランタイム動作を選択できるようにするために不可欠です。

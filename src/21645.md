このコミットは、Go言語のアセンブラ (`cmd/asm`) における複数の修正と改善を目的としています。主な目的は、新しいアセンブラの出力が、以前の `new6a` アセンブラと完全に一致するようにすることです。具体的には、シンボル名の処理、ローカル変数サイズのデフォルト値の指定、およびマクロ呼び出し時のヒストリーポイントの生成に関する動作の調整が行われています。これにより、新旧アセンブラ間の互換性が確保され、将来的なクリーンアップ作業のための検証可能な基盤が提供されます。

## 変更の背景

このコミットの主な背景は、Go言語の新しいアセンブラである `cmd/asm` が、既存の古いアセンブラ `new6a` と同じ出力を生成するようにすることです。Goのツールチェーンは継続的に進化しており、新しいツールやコンポーネントが導入される際には、既存の動作との互換性を確保することが極めて重要になります。

`cmd/asm` は `new6a` の後継として開発されていたと考えられ、その移行を円滑に進めるためには、両者の出力が完全に一致している必要があります。もし出力に差異があれば、既存のGoプログラムのアセンブリコードが正しくコンパイルされなかったり、予期せぬ動作を引き起こしたりする可能性があります。

コミットメッセージにある「Fix up a couple of minor things pointed out in the last review」という記述から、この変更が `cmd/asm` の開発プロセスにおけるコードレビューの結果として行われたことが示唆されます。レビューを通じて、新旧アセンブラ間の出力の不一致を引き起こす特定の挙動が特定され、それらを修正する必要があったと考えられます。

具体的には、以下の3点が主要な不一致の原因として挙げられています。

1.  **シンボル名の処理**: Goのアセンブリでは、内部シンボルを示すために特殊な文字（中央のドット `·`）が使用されることがありますが、新しいアセンブラがこれを `new6a` と同じように処理していなかった可能性があります。
2.  **ローカル変数サイズの指定**: 関数内のローカル変数が占めるスタック上のサイズが明示的に指定されていない場合に、新しいアセンブラが `new6a` と異なるデフォルト値を適用していた可能性があります。
3.  **マクロのヒストリーポイント**: アセンブラのマクロ展開時に、デバッグ情報やプロファイリングのために記録される「ヒストリーポイント」の生成タイミングや管理が、新旧アセンブラで異なっていた可能性があります。特に、マクロの開始時にヒストリーポイントが生成されるものの、終了時にそれが適切にポップされないという問題があったようです。

これらの不一致を解消し、`cmd/asm` が `new6a` と同一の出力を生成できるようにすることで、Goツールチェーンの安定性と信頼性を高め、将来的なアセンブラの改善やクリーンアップのための強固な基盤を築くことが、このコミットの重要な背景となっています。

## 前提知識の解説

このコミットを深く理解するためには、Go言語の内部構造、特にアセンブラとリンカの動作に関するいくつかの前提知識が必要です。

### 1. Go言語のアセンブラ (`cmd/asm`) と `new6a`

*   **Go言語のアセンブラ**: Go言語は通常、高レベルな言語として知られていますが、パフォーマンスが極めて重要な部分（例: ランタイム、標準ライブラリの特定の関数）や、特定のハードウェア機能に直接アクセスする必要がある場合には、アセンブリ言語で記述されたコードが使用されます。Goのツールチェーンには、これらのアセンブリコードを機械語に変換するためのアセンブラが含まれています。`cmd/asm` は、Go 1.5以降で導入された新しいアセンブラであり、それ以前のバージョンで使用されていた `new6a` (または `6a` などのアーキテクチャ固有のアセンブラ) の後継にあたります。
*   **`new6a`**: これは、Goの初期のバージョンで使用されていたアセンブラの名称です。Goのビルドシステムは、ターゲットアーキテクチャ（例: `amd64` の場合は `6a`）に応じて異なるアセンブラを使用していました。このコミットは、新しい `cmd/asm` が古い `new6a` と同じ出力を生成することを目指しているため、両者の互換性が焦点となっています。

### 2. Goのアセンブリにおけるシンボルと「中央のドット」 (`·`)

*   **シンボル**: プログラムにおいて、関数名、変数名、ラベルなどは「シンボル」として扱われます。アセンブリコードでは、これらのシンボルがメモリ上の特定のアドレスを指し示します。
*   **中央のドット (`·` U+00B7)**: Goのアセンブリコードでは、パッケージ内でプライベートな（エクスポートされていない）シンボルを示すために、シンボル名に中央のドット (`·`) が含まれることがあります。例えば、`mypackage·myFunc` のように記述されます。これは、Goのリンカがシンボルを解決する際に、そのスコープを識別するために重要な役割を果たします。このコミットでは、この特殊なシンボル名の処理方法が新旧アセンブラ間で統一されることが目的の一つです。

### 3. ローカル変数サイズと `ArgsSizeUnknown`

*   **ローカル変数サイズ**: 関数が呼び出されると、その関数内で宣言されたローカル変数は通常、スタック上に割り当てられます。これらのローカル変数がスタック上で占める合計サイズは、コンパイラやアセンブラによって計算され、生成される機械語コードやデバッグ情報に反映されます。
*   **`ArgsSizeUnknown`**: これは、Goのオブジェクトファイルフォーマット（`obj` パッケージで扱われる）において、関数の引数やローカル変数のサイズが不明であることを示すために使用される特別な定数である可能性があります。アセンブラがローカル変数のサイズを決定できない場合や、特定の状況下でサイズが動的に決定される場合に、この値がプレースホルダーとして使用されることがあります。このコミットでは、ローカル変数サイズが明示的に指定されていない場合に、この `ArgsSizeUnknown` をデフォルトとして使用するように変更されています。

### 4. マクロとヒストリーポイント

*   **マクロ**: アセンブラのマクロは、一連のアセンブリ命令に名前を付け、その名前を呼び出すことで命令群を再利用するための機能です。これにより、コードの記述量を減らし、可読性を向上させることができます。
*   **ヒストリーポイント**: コンパイラやアセンブラがコードを処理する際に、デバッグ情報やプロファイリングのために、ソースコードの特定の行や位置を記録するメカニズムです。これにより、デバッガがソースコードの行番号と実行中の機械語コードを関連付けたり、プロファイラが特定のコードブロックの実行時間を測定したりすることが可能になります。コミットメッセージにある「Do not emit a history point at the start of a macro invocation, since we do not pop it at the end」という記述は、マクロ展開時に不適切なヒストリーポイントが生成され、それがデバッグ情報の混乱を招いていた可能性を示唆しています。

これらの概念を理解することで、このコミットがGoツールチェーンの低レベルな部分でどのように機能し、なぜこれらの変更が必要とされたのかをより深く把握することができます。

## 技術的詳細

このコミットは、Go言語のアセンブラ `cmd/asm` の内部動作に深く関わる複数の技術的な調整を行っています。これらの変更は、主に `cmd/asm` が `new6a` と同じアセンブリ出力を生成することを保証するために設計されています。

### 1. シンボル名の正規化と `""` プレフィックスの追加

*   **問題**: Goのアセンブリでは、内部シンボル（例: `mypackage·myFunc`）に中央のドット (`·` U+00B7) が含まれます。古い `new6a` アセンブラと新しい `cmd/asm` の間で、この特殊なシンボル名の処理方法に差異があったと考えられます。特に、リンカがこれらのシンボルを正しく解決するためには、特定の形式で表現される必要があります。
*   **解決策**: `src/cmd/asm/internal/lex/lex.go` の `Make` 関数に新しいロジックが追加されました。
    ```go
    if token == scanner.Ident && strings.HasPrefix(text, "\u00B7") {
        text = `""` + text
    }
    ```
    このコードは、トークンが識別子 (`scanner.Ident`) であり、かつ中央のドット (`\u00B7`) で始まる場合に、そのシンボル名に `""` (空文字列リテラル) をプレフィックスとして追加します。これは、Goのリンカが内部シンボルを処理する際の慣習に合わせたものであり、リンカがシンボルを正しく識別し、名前の衝突を避けるためのメカニズムであると考えられます。この変更により、`cmd/asm` が生成するシンボル名が `new6a` と一致するようになります。
*   **関連する変更**: `src/cmd/asm/internal/asm/asm.go` では、以前行われていたシンボル名からの `·` の削除処理が削除されました。これは、`lex.go` の `Make` 関数で新しい正規化ロジックが導入されたため、この削除処理が不要になったか、あるいは新しいロジックと競合するためと考えられます。

### 2. ローカル変数サイズのデフォルト値の指定

*   **問題**: アセンブリ関数において、ローカル変数が占めるスタック上のサイズが明示的に指定されていない場合、アセンブラがどのようにそのサイズを扱うかについて、新旧アセンブラ間で一貫性がなかった可能性があります。これは、スタックフレームのレイアウトや、デバッグ情報の正確性に影響を与える可能性があります。
*   **解決策**: `src/cmd/asm/internal/asm/asm.go` の `asmText` 関数内で、ローカル変数 (`locals`) の初期値が `int64(obj.ArgsSizeUnknown)` に変更されました。
    ```go
    locals := int64(obj.ArgsSizeUnknown)
    ```
    `obj.ArgsSizeUnknown` は、Goのオブジェクトファイルフォーマットにおいて、引数やローカル変数のサイズが不明であることを示す特別な定数です。この変更により、ローカル変数のサイズが明示的に指定されていない場合に、`cmd/asm` が `new6a` と同様に、この「不明」という状態を適切に表現するようになります。これにより、リンカやデバッガがこの情報を一貫して解釈できるようになります。

### 3. マクロ呼び出し時のヒストリーポイントの抑制

*   **問題**: コミットメッセージによると、「Do not emit a history point at the start of a macro invocation, since we do not pop it at the end, behavior consistent with the old code.」とあります。これは、マクロが展開される際に、その開始点でヒストリーポイント（デバッグ情報の一部）が生成されるものの、マクロの終了点で対応するポップ操作が行われないため、ヒストリーポイントのスタックが不整合になり、デバッグ情報が不正確になる問題があったことを示唆しています。古い `new6a` アセンブラでは、この問題は発生していなかったか、異なる方法で処理されていたと考えられます。
*   **解決策**: `src/cmd/asm/internal/lex/tokenizer.go` の `NewTokenizer` および `Next` 関数内で、`obj.Linklinehist` の呼び出しが `if file != nil` の条件で囲まれました。
    ```go
    // In NewTokenizer
    if file != nil {
        obj.Linklinehist(linkCtxt, histLine, name, 0)
    }

    // In Next
    case '\n':
        if t.file != nil {
            histLine++
        }
    ```
    この変更は、ファイルから読み込む場合にのみヒストリーポイントを生成し、それ以外の場合（例えば、標準入力からの読み込みや、マクロ展開のような内部的な処理）では生成を抑制することを意味します。これにより、マクロ展開時に不必要なヒストリーポイントが生成されなくなり、デバッグ情報の整合性が保たれ、古いアセンブラの動作と一致するようになります。

### 4. 環境変数取得方法の変更

*   **変更**: `src/cmd/asm/main.go` では、`flags.Parse` 関数に渡す引数が変更されました。
    ```diff
    -	flags.Parse(build.Default.GOROOT, build.Default.GOOS, GOARCH, architecture.Thechar)
    +	flags.Parse(obj.Getgoroot(), obj.Getgoos(), obj.Getgoarch(), architecture.Thechar)
    ```
*   **意図**: 以前は `build.Default` 構造体から直接 `GOROOT` や `GOOS` などの環境情報を取得していましたが、この変更により `obj` パッケージのヘルパー関数 (`obj.Getgoroot()`, `obj.Getgoos()`, `obj.Getgoarch()`) を使用するようになりました。これは、Goのビルド環境に関する情報を取得する際により堅牢で、将来の変更にも対応しやすい方法への移行を示唆しています。`obj` パッケージはGoのオブジェクトファイルフォーマットやリンカに関連する低レベルな機能を提供しており、これらのヘルパー関数を使用することで、環境情報の取得が一元化され、より信頼性が高まる可能性があります。

これらの技術的な変更は、Goのアセンブラが生成するバイナリの正確性、デバッグ情報の品質、そして新旧ツールチェーン間の互換性を確保するために不可欠なものです。

## コアとなるコードの解説

### `src/cmd/asm/internal/asm/asm.go` の変更

*   **シンボル名処理の削除**:
    ```diff
    -	name := strings.Replace(nameAddr.Symbol, "·", ".", 1)
    +	name := nameAddr.Symbol
    ```
    以前は、`asmText` 関数内でシンボル名から中央のドット (`·`) を通常のピリオド (`.`) に置換していました。この変更では、この置換処理が削除されています。これは、`src/cmd/asm/internal/lex/lex.go` の `Make` 関数に新しいシンボル名正規化ロジックが導入されたため、この場所での処理が不要になったか、あるいは重複を避けるためと考えられます。シンボル名の正規化は、トークン化の段階で一元的に行われるべきであり、この変更はその方針に沿ったものです。

*   **ローカル変数サイズのデフォルト値**:
    ```diff
    -	var locals int64
    +	locals := int64(obj.ArgsSizeUnknown)
    ```
    `asmText` 関数は、アセンブリ関数のテキストセクションを処理します。ここで `locals` 変数は、関数内のローカル変数が占めるスタック上のサイズを表します。以前は `int64` のゼロ値で初期化されていましたが、この変更により `obj.ArgsSizeUnknown` という特別な値で初期化されるようになりました。これは、ローカル変数のサイズがアセンブリコード内で明示的に指定されていない場合に、そのサイズが「不明」であることをリンカやデバッガに伝えるための標準的な方法です。これにより、新旧アセンブラ間で未指定のローカル変数サイズの扱いが一貫するようになります。

### `src/cmd/asm/internal/lex/input.go` および `src/cmd/asm/internal/lex/lex.go` の変更

これらのファイルにおける主要な変更は、トークン生成ロジックの一元化と、新しいシンボル名正規化の導入です。

*   **`Make` 関数の導入と利用**:
    `input.go` と `lex.go` の複数の箇所で、以前は `Token{ScanToken(tok), in.Text()}` のように直接 `Token` 構造体を生成していた部分が、新しく定義された `Make` 関数を使用するように変更されました。
    ```diff
    -	tokens = append(tokens, Token{ScanToken: tok, text: t.Text()})
    +	tokens = append(tokens, Make(tok, t.Text()))
    ```
    この変更の理由は、`lex.go` の `Make` 関数に、このコミットの核となるシンボル名正規化ロジックが追加されたためです。

*   **`Make` 関数内のシンボル名正規化**:
    `src/cmd/asm/internal/lex/lex.go` の `Make` 関数に以下のロジックが追加されました。
    ```go
    func Make(token ScanToken, text string) Token {
        // If the symbol starts with center dot, as in ·x, rewrite it as ""·x
        if token == scanner.Ident && strings.HasPrefix(text, "\u00B7") {
            text = `""` + text
        }
        // Substitute the substitutes for . and /.
        text = strings.Replace(text, "\u00B7", ".", 1)
        text = strings.Replace(text, "\u2215", "/", -1)
        return Token{ScanToken: token, text: text}
    }
    ```
    1.  **`""` プレフィックスの追加**: `if token == scanner.Ident && strings.HasPrefix(text, "\u00B7") { text = `""` + text }`
        これは、中央のドット (`·`) で始まる識別子（Goの内部シンボル）に対して、`""`（空文字列リテラル）をプレフィックスとして追加します。この形式は、Goのリンカが内部シンボルを正しく処理するために必要な慣習的な表現であると考えられます。これにより、リンカがシンボルを正しく解決し、名前の衝突を避けることができます。この変更は、`new6a` との出力互換性を確保するために特に重要です。
    2.  **Unicode文字の置換**: `strings.Replace(text, "\u00B7", ".", 1)` と `strings.Replace(text, "\u2215", "/", -1)`
        これらは、Unicodeの中央のドット (`·` U+00B7) を通常のピリオド (`.`) に、Unicodeの分数スラッシュ (`⁄` U+2215) を通常のASCIIスラッシュ (`/`) に置換します。これは、アセンブラの内部処理や最終的な出力において、より一般的なASCII文字を使用するため、または古いアセンブラとの互換性を保つために行われます。特に、ファイルパスやシンボル名の一部としてこれらの特殊文字が使用される場合に、システムやツールが正しく解釈できるようにするための処理です。

### `src/cmd/asm/internal/lex/tokenizer.go` の変更

*   **ヒストリーポイント生成の条件化**:
    `NewTokenizer` 関数と `Next` 関数（改行処理内）で、`obj.Linklinehist` の呼び出しが `if file != nil` の条件で囲まれました。
    ```go
    // NewTokenizer
    if file != nil {
        obj.Linklinehist(linkCtxt, histLine, name, 0)
    }

    // Next (for '\n' case)
    if t.file != nil {
        histLine++
    }
    ```
    `obj.Linklinehist` は、ソースコードの行番号と対応する機械語コードの位置を記録する「ヒストリーポイント」を生成するための関数です。この変更は、ファイルからアセンブリコードを読み込む場合にのみヒストリーポイントを生成し、それ以外の場合（例えば、マクロ展開のような内部的なコード生成プロセスや、標準入力からの読み込み）では生成を抑制することを意味します。コミットメッセージにあるように、マクロ呼び出しの開始時にヒストリーポイントが生成されるものの、終了時に適切にポップされないという問題があったため、この変更により不要なヒストリーポイントの生成を防ぎ、デバッグ情報の整合性を保ち、古いアセンブラの動作と一致させることを目的としています。

### `src/cmd/asm/main.go` の変更

*   **環境変数取得方法の変更**:
    ```diff
    -	flags.Parse(build.Default.GOROOT, build.Default.GOOS, GOARCH, architecture.Thechar)
    +	flags.Parse(obj.Getgoroot(), obj.Getgoos(), obj.Getgoarch(), architecture.Thechar)
    ```
    `flags.Parse` 関数は、アセンブラのコマンドライン引数を解析し、ビルド環境に関する情報を設定するために使用されます。以前は `build.Default` 構造体から直接 `GOROOT` や `GOOS` などの情報を取得していましたが、この変更により `obj` パッケージのヘルパー関数 (`obj.Getgoroot()`, `obj.Getgoos()`, `obj.Getgoarch()`) を使用するようになりました。これは、Goのビルド環境に関する情報を取得する際により堅牢で、将来の変更にも対応しやすい方法への移行を示唆しています。`obj` パッケージはGoのオブジェクトファイルフォーマットやリンカに関連する低レベルな機能を提供しており、これらのヘルパー関数を使用することで、環境情報の取得が一元化され、より信頼性が高まる可能性があります。

これらの変更は、Goのアセンブラが生成するバイナリの正確性、デバッグ情報の品質、そして新旧ツールチェーン間の互換性を確保するために不可欠なものです。特に、シンボル名の正規化とヒストリーポイントの抑制は、アセンブラの出力が `new6a` と完全に一致するための重要な調整点です。

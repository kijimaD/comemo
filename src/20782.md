## 変更の背景

このコミットの背景には、GoランタイムがWindows環境で発生するネイティブな例外（例: アクセス違反、ゼロ除算など）をどのように処理するかという課題があります。Go言語自体は `panic` と `recover` という独自の例外処理メカニズムを持っていますが、これはGoコード内で発生する論理的なエラーや予期せぬ状態を扱うためのものです。しかし、オペレーティングシステムレベルで発生するハードウェア例外や、C/C++など他の言語で書かれたライブラリが引き起こす例外は、WindowsのStructured Exception Handling (SEH) や Vectored Exception Handling (VEH) といったネイティブなメカニズムによって処理されます。

以前のコミット (`8b3d26697b8d`) は、GoランタイムがこれらのWindowsネイティブ例外をより包括的に捕捉し、Goの `panic` メカニズムに変換してGoプログラムが適切にクラッシュレポートを生成したり、場合によっては回復できるようにすることを目的としていました。これは、GoプログラムがWindows上でより堅牢に動作し、デバッグ情報がより豊富になることを期待しての変更でした。

しかし、この変更はGoプロジェクトの自動ビルドシステム（ビルダー）上で予期せぬ問題を引き起こしました。ビルダーは様々な環境（異なるWindowsバージョン、アーキテクチャ、設定）でGoコードをビルド・テストするため、開発者のローカル環境では再現しない問題が露呈することがよくあります。この場合、ビルダーが「壊れた」と報告されており、以前の変更がGoの安定性を損なう結果となりました。

そのため、このコミットでは、ビルダーの安定性を回復させるために、問題のあった変更を完全に元に戻すことが決定されました。これは、Goプロジェクトが安定性と信頼性を非常に重視していることの表れであり、新しい機能や改善が導入される際には、広範なテストと検証が不可欠であることを示しています。

## 前提知識の解説

このコミットを理解するためには、以下のWindowsの例外処理メカニズムとGoランタイムの基本的な概念を理解しておく必要があります。

1.  **Windows Structured Exception Handling (SEH)**:
    *   Windows OSが提供する、プログラム実行中に発生する例外（ハードウェア例外やソフトウェア例外）を処理するためのメカニズムです。
    *   C/C++では `__try`, `__except`, `__finally` ブロックを使って例外ハンドラを定義します。
    *   例外が発生すると、OSは現在のスタックフレームから上位に向かって例外ハンドラを検索し、適切なハンドラが見つかるとそのハンドラが実行されます。

2.  **Windows Vectored Exception Handling (VEH)**:
    *   Windows XP以降で導入された、SEHよりも高レベルでグローバルな例外処理メカニズムです。
    *   `AddVectoredExceptionHandler` 関数を使って、プロセス全体で発生する例外を捕捉するためのハンドラを登録できます。
    *   VEHハンドラは、SEHハンドラよりも先に呼び出されます（"first-chance" exception handling）。これにより、アプリケーションは例外がSEHによって処理される前に、例外を監視、ログ記録、または独自の処理を行うことができます。
    *   VEHハンドラは、例外を処理したかどうかを示す値を返します。
        *   `EXCEPTION_CONTINUE_EXECUTION`: 例外が処理され、実行を継続できることを示します。OSは例外が発生した命令から実行を再開しようとします。
        *   `EXCEPTION_CONTINUE_SEARCH`: 例外が処理されなかったことを示し、OSは次のVEHハンドラ、またはSEHハンドラを検索し続けます。

3.  **`SetUnhandledExceptionFilter`**:
    *   プロセス内で未処理の例外が発生した場合に呼び出される、最後の手段となる例外フィルタ関数を設定するためのWindows APIです。
    *   デバッガがアタッチされている場合や、VEHハンドラが例外を処理した場合など、特定の条件下では呼び出されないことがあります。

4.  **Goランタイムと `panic`/`recover`**:
    *   Go言語は、`panic` と `recover` という組み込み関数を使って、プログラムの異常終了やエラーからの回復を扱います。
    *   `panic` が発生すると、現在の関数の実行が停止し、遅延関数（`defer`）が実行されながらスタックが巻き戻されます。
    *   `recover` は `defer` 関数内で呼び出された場合にのみ有効で、`panic` の値を捕捉し、パニックの連鎖を停止してプログラムの実行を継続させることができます。
    *   Goランタイムは、Windows上で発生するネイティブ例外をGoの `panic` に変換することで、GoプログラムがこれらのOSレベルの異常をGoのメカニズムで扱えるように橋渡しをする役割を担っています。

5.  **Goのビルドシステム（ビルダー）**:
    *   Goプロジェクトは、様々なオペレーティングシステム、アーキテクチャ、コンパイラバージョンでコードが正しく動作することを保証するために、広範な自動ビルドおよびテストシステム（通称「ビルダー」）を使用しています。
    *   開発者が変更をコミットする前に、これらのビルダーでテストが実行され、互換性や安定性の問題がないか確認されます。ビルダーでの失敗は、その変更がGoの安定版にマージされることを妨げます。

## 技術的詳細

この「undo」コミットの技術的詳細は、以前のコミットがGoランタイムのWindows例外処理メカニズムにどのような変更を加えようとしていたかを理解することで明らかになります。

以前のコミットは、GoランタイムがWindowsのVEH（Vectored Exception Handling）をより積極的に利用し、`SetUnhandledExceptionFilter` と組み合わせることで、Goプログラムが遭遇する可能性のあるすべてのWindows例外を捕捉しようとしました。具体的には、以下の変更が含まれていたと推測されます（このコミットがそれらを元に戻しているため）。

*   **VEHハンドラの登録**: `runtime·AddVectoredExceptionHandler` を使って、複数のVEHハンドラ（`runtime·exceptiontramp`, `runtime·firstcontinuetramp`, `runtime·lastcontinuetramp`）を登録しようとしていました。
*   **例外処理の多段階化**:
    *   `runtime·exceptionhandler`: Goコード内で発生した例外をGoの `panic` に変換する主要なハンドラ。
    *   `runtime·firstcontinuehandler`: VEHの「Continue Handler」として登録され、例外処理の連鎖を制御しようとしていた可能性があります。
    *   `runtime·lastcontinuehandler`: 最終的な例外ハンドラとして機能し、Goランタイムが処理できない例外が発生した場合にクラッシュ情報を出力して終了する役割を担っていました。
*   **`SetUnhandledExceptionFilter` の利用**: `AddVectoredContinueHandler` が利用できない古いWindowsバージョンとの互換性のために、`SetUnhandledExceptionFilter` をフォールバックとして使用しようとしていました。
*   **アセンブリコードの変更**: `sys_windows_386.s` および `sys_windows_amd64.s` の `runtime·sigtramp` 関数（シグナル/例外トラップ）が、これらの新しい例外ハンドラを呼び出すように変更されていました。特に、`AX` レジスタにハンドラのアドレスをロードし、それを呼び出すロジックが追加されていました。
*   **テストケースの追加**: `syscall_windows_test.go` に `TestRaiseException` と `TestZeroDivisionException` といったテストが追加され、GoランタイムがWindows例外を正しく捕捉し、`panic` に変換できることを検証しようとしていました。

この「undo」コミットは、これらの変更をすべて巻き戻し、以前の、よりシンプルな（そしてビルダーで安定していた）Windows例外処理のロジックに戻しています。これは、複雑な多段階の例外処理メカニズムが、特定の環境（特にビルダー）で予期せぬ競合状態、デッドロック、またはその他の不安定な挙動を引き起こした可能性を示唆しています。Windowsの例外処理は非常に低レベルでOSの挙動に深く依存するため、異なるOSバージョンやパッチレベル、あるいはデバッガの存在など、わずかな環境の違いで挙動が変わることがあります。

このコミットは、GoランタイムがWindows例外を扱う上で、安定性と予測可能性を最優先していることを強調しています。

## コアとなるコードの変更箇所

このコミットは以前の変更を元に戻すため、主にコードの削除と以前のコードへの復元が行われています。

**削除された主要なコード要素:**

*   **`src/runtime/defs_windows.go`, `src/runtime/defs_windows_386.h`, `src/runtime/defs_windows_amd64.h`**:
    *   `EXCEPTION_CONTINUE_EXECUTION` および `EXCEPTION_CONTINUE_SEARCH` 定数の定義が削除されました。これらはWindows例外ハンドラの戻り値として使用されていました。
*   **`src/runtime/os_windows.c`**:
    *   `runtime·SetUnhandledExceptionFilter` の動的インポートおよび外部宣言が削除されました。
    *   `runtime·exceptiontramp`, `runtime·firstcontinuetramp`, `runtime·lastcontinuetramp` の外部宣言が削除されました。
    *   `runtime·osinit` 関数内で、`AddVectoredExceptionHandler` や `SetUnhandledExceptionFilter` を使って複数の例外ハンドラを登録する複雑なロジックが削除され、`runtime·AddVectoredExceptionHandler` を使って `runtime·sigtramp` のみを登録するシンプルな形に戻されました。
    *   `runtime·initsig` 関数内で、`exceptiontramp`, `firstcontinuetramp`, `lastcontinuetramp` をリンク時に保持するための `USED` マクロの呼び出しが削除されました。
*   **`src/runtime/os_windows_386.c`, `src/runtime/os_windows_amd64.c`**:
    *   `runtime·isgoexception` 関数が削除されました。
    *   `runtime·exceptionhandler`, `runtime·firstcontinuehandler` 関数が削除されました。
    *   `runtime·lastcontinuehandler` 関数が `runtime·sighandler` に統合され、そのロジックが簡素化されました。以前の `runtime·sighandler` は、`runtime·exceptionhandler` を呼び出す前の前処理のような役割でしたが、この変更により、`runtime·sighandler` が直接例外処理の大部分を担うようになりました。
    *   `EXCEPTION_CONTINUE_EXECUTION` や `EXCEPTION_CONTINUE_SEARCH` を返すロジックが削除され、代わりに `-1` (handled) または `0` (not handled) を返すようになりました。
*   **`src/runtime/sys_windows_386.s`, `src/runtime/sys_windows_amd64.s`**:
    *   `runtime·exceptiontramp`, `runtime·firstcontinuetramp`, `runtime·lastcontinuetramp` のアセンブリコードが完全に削除されました。
    *   `runtime·sigtramp` 内で、ハンドラのアドレスを `AX` (386) または `R15` (amd64) に保存し、そのレジスタを介してハンドラを呼び出すロジックが削除され、直接 `runtime·sighandler(SB)` を呼び出す形に戻されました。
*   **`src/runtime/syscall_windows_test.go`**:
    *   `TestRaiseException` および `TestZeroDivisionException` のテスト関数と、それに関連するソースコードが削除されました。

## コアとなるコードの解説

このコミットのコアとなる変更は、GoランタイムがWindows例外を処理する際の複雑な多段階アプローチを放棄し、より直接的でシンプルなアプローチに戻した点にあります。

以前の変更では、WindowsのVEHと `SetUnhandledExceptionFilter` を組み合わせて、Goランタイムが様々な種類のWindows例外を捕捉し、それらをGoの `panic` に変換しようとしていました。このアプローチは、複数の異なるハンドラ（`exceptionhandler`, `firstcontinuehandler`, `lastcontinuehandler`）を登録し、それぞれが例外処理の異なる段階や種類を扱うように設計されていました。特に、`EXCEPTION_CONTINUE_EXECUTION` や `EXCEPTION_CONTINUE_SEARCH` といったWindows APIの戻り値を細かく制御することで、例外処理のフローを詳細に管理しようとしていたことが伺えます。

しかし、この「undo」コミットでは、これらの複雑なハンドラチェーンと関連する定数、そしてそれらを呼び出すアセンブリコードがすべて削除されました。代わりに、`runtime·sighandler` 関数がWindowsのVEHハンドラ (`runtime·sigtramp`) から直接呼び出される、より簡潔な構造に戻されています。

`runtime·sighandler` の役割は、以下の通りです。

1.  **例外発生箇所のチェック**: 例外が発生した命令ポインタ（`r->Eip` または `r->Rip`）がGoバイナリのコード範囲内にあるかどうかを確認します。Goコード外で発生した例外はGoランタイムでは処理せず、OSに任せます。
2.  **Go例外の判定**: `runtime·issigpanic` を呼び出し、発生した例外コードがGoランタイムが `panic` に変換すべきシグナル（例: アクセス違反、ゼロ除算など）であるかを判定します。
3.  **`panic` への変換**: もしGoコード内でGoが処理すべき例外が発生した場合、`gp` (現在のGoroutine) の `sig`, `sigcode0`, `sigcode1`, `sigpc` フィールドに例外情報を格納します。
4.  **スタックの調整と `runtime·sigpanic` へのジャンプ**: 例外が発生した命令ポインタをスタックにプッシュし、命令ポインタを `runtime·sigpanic` 関数に設定します。これにより、Goランタイムは `runtime·sigpanic` を呼び出すことで、Goの `panic` メカニズムをトリガーし、適切なスタックトレースを生成してプログラムを終了させます。
5.  **戻り値**: 例外を処理した場合は `-1` を返し、OSにこれ以上ハンドラを検索しないように伝えます。処理しなかった場合は `0` を返します。

この変更は、Windows例外処理の複雑さをGoランタイムの外部に委ねるか、あるいはGoランタイムが直接処理する例外の種類を限定することで、ビルダーでの安定性を確保したことを意味します。これは、低レベルのOS固有の挙動を抽象化し、Goのクロスプラットフォームな性質を維持するためのトレードオフであるとも言えます。

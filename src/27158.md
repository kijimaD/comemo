# [インデックス 27158] ファイルの概要

このコミットはGoランタイムの`src/runtime/stack.go`ファイルに対する変更です。`stack.go`はGoのランタイムにおいて、ゴルーチンのスタック管理、特にスタックの確保、解放、そして最も重要なスタックのコピー（リサイズ）に関連するロジックを実装しています。Goのゴルーチンは可変サイズのスタックを使用するため、実行中にスタックが不足したり、逆に大きすぎたりする場合に、このファイル内の関数がスタックのリサイズ処理を担当します。

## コミット

このコミットは、Goランタイムの`copystack`関数におけるスタックコピーとポインタ調整の順序を変更するものです。以前は、古いスタック上のポインタを調整してから新しいスタックにコピーしていましたが、この変更により、まずスタック全体を新しい場所にコピーし、その後で新しいスタック上のポインタを調整するようになりました。この変更は、コードの理解を容易にし、将来的な並行スタック縮小の実装を簡素化することを目的としています。

    runtime: copy stack before adjusting
    
    Currently copystack adjusts pointers in the old stack and then copies
    the adjusted stack to the new stack. In addition to being generally
    confusing, this is going to make concurrent stack shrinking harder.
    
    Switch this around so that we first copy the stack and then adjust
    pointers on the new stack (never writing to the old stack).
    
    This reprises CL 15996, but takes a different and simpler approach. CL
    15996 still walked the old stack while adjusting pointers on the new
    stack. In this CL, we adjust auxiliary structures before walking the
    stack, so we can just walk the new stack.

## 変更の背景

この変更の主な背景には、以下の2点があります。

1.  **コードの複雑性と混乱の解消**: 以前の実装では、`copystack`関数が古いスタック上のポインタを先に調整し、その調整されたスタックを新しい場所にコピーしていました。このアプローチは、処理の流れが直感的でなく、コードの理解を困難にしていました。特に、ポインタ調整が古いメモリ領域に対して行われるという点が混乱を招きやすかったと考えられます。
2.  **並行スタック縮小の困難さ**: Goランタイムは、ゴルーチンのスタックを必要に応じて拡大・縮小します。スタックの縮小は、メモリ使用量を最適化するために重要ですが、複数のゴルーチンが同時に動作する並行環境下でスタックを安全に縮小することは非常に複雑な問題です。古い実装のポインタ調整ロジックは、並行スタック縮小を実装する上での障壁となっていました。具体的には、古いスタックがまだ使用されている可能性がある状態でポインタを調整することは、データ競合や不整合のリスクを高め、並行処理の安全性を確保するための複雑な同期メカニズムを必要としました。

このコミットは、これらの問題を解決するために、スタックのコピーとポインタ調整の順序を入れ替えることで、よりシンプルで安全なアプローチを提供します。これにより、将来的に並行スタック縮小をより容易に実装できる基盤を築いています。また、この変更は、以前のCL 15996の再検討であり、より洗練された方法で同じ目標を達成しようとしています。

## 前提知識の解説

### Goランタイムとゴルーチンスタック管理

Go言語は、軽量な並行処理単位である「ゴルーチン（goroutine）」を特徴としています。各ゴルーチンは独自の実行スタックを持ち、このスタックはプログラムの関数呼び出し、ローカル変数、引数などを格納します。Goランタイムは、これらのゴルーチンのライフサイクルとリソース（特にスタック）を管理する役割を担っています。

Goのスタックは「可変サイズスタック（resizable stack）」であり、プログラムの実行中に必要に応じて自動的に拡大・縮小します。これは、C/C++のような固定サイズのスタックを持つ言語とは異なり、スタックオーバーフローの心配を軽減し、メモリ効率を高めるための重要な機能です。

### スタックの拡張と縮小

*   **スタックの拡張**: ゴルーチンが深い関数呼び出しを行うなどして現在のスタック領域が不足しそうになると、Goランタイムはより大きな新しいスタック領域を確保し、古いスタックの内容を新しいスタックにコピーします。このプロセスを「スタックの拡張」と呼びます。
*   **スタックの縮小**: ゴルーチンが多くのスタック領域を必要としなくなった場合（例えば、深い関数呼び出しから戻った後）、Goランタイムはスタックをより小さなサイズに縮小してメモリを解放しようとします。これを「スタックの縮小」と呼びます。スタックの縮小は、メモリフットプリントを削減し、システム全体のパフォーマンスを向上させるために重要です。

### ポインタ調整の必要性

スタックが新しいメモリ領域に移動される（拡張または縮小される）際、スタック上に存在するポインタ（例えば、ヒープ上のオブジェクトを指すポインタや、スタック上の他のフレームを指すポインタ）は、新しいスタックのベースアドレスに合わせてその値を調整する必要があります。この調整が行われないと、ポインタは古い（無効な）メモリ領域を指したままになり、プログラムのクラッシュやデータ破損を引き起こします。

Goのガベージコレクタ（GC）は、スタック上のポインタを正確に識別し、それらを追跡してヒープ上の到達可能なオブジェクトをマークする役割も担っています。スタックが移動する際には、GCが正しく動作するために、これらのポインタが新しいアドレスを指すように更新されることが不可欠です。

### Goのガベージコレクションとスタック

Goのガベージコレクタは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行して動作します。GCは、プログラムが使用しているメモリ（ヒープ）をスキャンし、到達可能なオブジェクトを特定してマークします。このスキャンプロセスには、ゴルーチンのスタックも含まれます。スタック上のポインタは、ヒープ上のオブジェクトへの参照となり得るため、GCはスタックを「ルート」として利用し、そこから到達可能なオブジェクトをマークします。

スタックのリサイズ中にポインタが正しく調整されないと、GCは古いスタック上のポインタを誤って解釈したり、新しいスタック上のポインタを見落としたりする可能性があります。これは、メモリリークや、誤って解放されたメモリへのアクセス（Use-After-Free）といった深刻なバグにつながります。

### Issue #12967

このコミットメッセージで参照されている`#12967`は、GoのIssueトラッカーにおける「runtime: concurrent stack shrinking」というタイトルのIssueです。このIssueは、Goランタイムにおける並行スタック縮小の実現に向けた課題と議論を扱っています。スタックの縮小は、メモリ効率の向上に寄与しますが、並行処理環境下での安全な実装は複雑であり、このコミットのような基盤的な変更が必要とされていました。

## 技術的詳細

### `copystack`関数の役割

`copystack`関数は、Goランタイムにおいてゴルーチンのスタックをリサイズする際の中心的な役割を担います。具体的には、現在のスタック領域が不足した場合（スタック拡張）や、過剰なスタック領域を解放する場合（スタック縮小）に呼び出されます。この関数は、新しいサイズのスタック領域を確保し、古いスタックの内容を新しいスタックに移動させ、そしてスタック上のすべてのポインタを新しいアドレスに合わせて調整します。

### 変更前後の処理フローの比較

**変更前（旧実装）:**

1.  `gcLockStackBarriers(gp)`: スタックバリアをロックし、`sigprof`スキャンを禁止します。
2.  `gentraceback`を呼び出し、古いスタック上のポインタを調整します。この際、`adjinfo.delta`（新しいスタックと古いスタックのアドレス差）に基づいてポインタの値を計算し、新しいスタックのアドレスを指すようにします。**しかし、この調整は古いスタック上で行われるか、あるいは新しいスタックのアドレスを計算して調整するものの、まだデータがコピーされていない状態で行われます。**
3.  `adjustctxt`, `adjustdefers`, `adjustpanics`, `adjustsudogs`, `adjuststkbar`: スタック上のポインタを持つ補助構造体（コンテキスト、defer、panic、select/send/recv操作に関連するデータ、スタックバリア）を調整します。
4.  `memmove`: 古いスタックの内容を新しいスタックの場所にコピーします。

この順序は、「古いスタックを調整してからコピーする」というもので、特に「調整」が古いスタックに対して行われる（あるいは、コピー前の状態を前提とする）点が混乱を招き、並行処理の安全性を確保する上で複雑さを増していました。

**変更後（新実装）:**

1.  `adjinfo`の計算: スタックの移動量（`adjinfo.delta`）を計算します。
2.  `memmove`: **まず、古いスタックの内容を新しいスタックの場所にコピーします。** これにより、新しいスタック領域には古いスタックのデータがそのまま（ポインタは古いアドレスを指したまま）存在することになります。
3.  `gcLockStackBarriers(gp)`: スタックバリアをロックし、`sigprof`スキャンを禁止します。
4.  `adjustctxt`, `adjustdefers`, `adjustpanics`, `adjustsudogs`, `adjuststkbar`: スタック上のポインタを持つ補助構造体を調整します。**このステップは、`gentraceback`がこれらの構造体を使用するため、スタックウォークの前に実行されます。**
5.  `gentraceback`を呼び出し、**新しいスタック上のポインタを調整します。** `adjinfo.delta`に基づいて、新しいスタック内のポインタが正しいアドレスを指すように更新されます。
6.  `gcUnlockStackBarriers(gp)`: スタックバリアのロックを解除します。

この新しい順序は、「まずコピーし、それから新しい場所で調整する」という、より直感的で安全なアプローチを提供します。古いスタックには一切書き込みを行わないため、並行処理における競合のリスクが低減されます。

### `gentraceback`とポインタ調整のメカニズム

`gentraceback`関数は、Goランタイムのスタックウォーカーであり、ゴルーチンのスタックフレームを一つずつ辿っていくために使用されます。この関数は、デバッガ、プロファイラ、そしてガベージコレクタによるスタックスキャンなど、様々な目的で利用されます。

`copystack`における`gentraceback`の役割は、スタック上のすべてのポインタを特定し、それらを新しいスタックアドレスに合わせて調整することです。`gentraceback`は、各スタックフレームのメタデータ（関数情報、引数、ローカル変数のレイアウトなど）を利用して、どのメモリ位置がポインタであるかを識別します。そして、`adjustframe`というコールバック関数を呼び出し、`adjinfo`構造体に含まれる`delta`情報を使ってポインタの値を更新します。

### 補助構造体（`adjustctxt`など）の役割

`adjustctxt`, `adjustdefers`, `adjustpanics`, `adjustsudogs`, `adjuststkbar`といった関数は、ゴルーチンのスタックに関連する様々な補助的なデータ構造に含まれるポインタを調整するために存在します。

*   `adjustctxt`: コンテキスト（`context`パッケージに関連するデータ）内のポインタを調整します。
*   `adjustdefers`: `defer`ステートメントに関連するデータ構造（遅延実行される関数の情報など）内のポインタを調整します。`defer`はスタック上に情報を保持するため、スタック移動時にそのポインタも更新される必要があります。
*   `adjustpanics`: `panic`および`recover`に関連するデータ構造内のポインタを調整します。`panic`情報もスタックに関連付けられています。
*   `adjustsudogs`: `select`ステートメントやチャネルの送受信操作（`send` / `recv`）に関連するデータ構造内のポインタを調整します。これらの操作は、ゴルーチンがブロックされる可能性があるため、その状態を保持する構造体もスタック移動の影響を受けます。
*   `adjuststkbar`: スタックバリア（スタックの境界を示す情報）に関連するポインタを調整します。これは、GCがスタックをスキャンする際に使用する情報です。

これらの補助構造体は、ゴルーチンの実行状態や特定の言語機能（defer, panic, selectなど）を正しく維持するために不可欠であり、スタックが移動する際には、それらが参照するメモリ位置も適切に更新される必要があります。新しい実装では、これらの補助構造体の調整が`gentraceback`によるスタックウォークの前に移動されました。これは、`gentraceback`自体がこれらの構造体の一部を使用する可能性があるため、それらが最新の状態であることを保証するためです。

### 並行スタック縮小への影響

この変更は、並行スタック縮小の実装を大幅に簡素化します。

*   **古いスタックへの書き込みの排除**: 変更前は、ポインタ調整が古いスタックに対して行われる可能性があり、もし古いスタックがまだ他のゴルーチンやGCによって参照されている場合、データ競合のリスクがありました。新しい実装では、まずスタック全体を新しい場所にコピーし、その後で新しいスタック上でのみポインタ調整を行います。これにより、古いスタックは読み取り専用となり、安全に解放できるようになります。
*   **簡素化された同期**: 古いスタックへの書き込みがなくなることで、スタックリサイズ中の同期メカニズムが簡素化されます。GCや他のゴルーチンが古いスタックを参照している間に、その内容が変更されることを心配する必要がなくなります。
*   **明確な状態遷移**: スタックのコピーが最初に行われることで、スタックの状態遷移がより明確になります。「古いスタックから新しいスタックへデータが移動し、その後新しいスタック上でポインタが修正される」という一貫した流れは、並行処理の推論を容易にします。

これにより、Goランタイム開発者は、より少ない複雑さで、より効率的で安全な並行スタック縮小アルゴリズムを設計・実装できるようになります。

## コアとなるコードの解説

このdiffは、`copystack`関数内の処理順序が大きく変更されたことを示しています。

1.  **`gcLockStackBarriers(gp)`と`gentraceback`の移動**:
    *   変更前は、`gcLockStackBarriers(gp)`が最初に呼び出され、その直後に`gentraceback`が古いスタックのポインタ調整のために呼び出されていました。
    *   変更後、`gcLockStackBarriers(gp)`は`memmove`によるスタックコピーの後に移動しました。
    *   `gentraceback`の呼び出しは、`memmove`と補助構造体の調整の後に移動し、コメントが「Adjust pointers in the new stack.」と変更されています。これは、`gentraceback`が新しいスタック上のポインタを調整するようになったことを明確に示しています。

2.  **`memmove`の早期実行**:
    *   変更前は、`gentraceback`によるポインタ調整と補助構造体の調整の後に`memmove`が実行されていました。
    *   変更後、`adjinfo`の計算の直後に`memmove`が実行されるようになりました。これにより、スタックの内容がまず新しい場所にコピーされ、その後でポインタ調整が行われるという新しいロジックが確立されました。

3.  **補助構造体調整のタイミング変更**:
    *   `adjustctxt`, `adjustdefers`, `adjustpanics`, `adjustsudogs`, `adjuststkbar`といった補助構造体を調整する関数群は、変更前は`gentraceback`の後に実行されていました。
    *   変更後、これらの関数は`memmove`によるスタックコピーの後、かつ`gentraceback`による新しいスタックのポインタ調整の前に実行されるようになりました。これは、コメント「Adjust structures that have pointers into stacks. We have to do most of these before we traceback the new stack because gentraceback uses them.」が示すように、`gentraceback`がこれらの補助構造体を使用する可能性があるため、スタックウォークの前にそれらが最新の状態であることを保証するためです。

4.  **`stackPoisonCopy`関連コードの削除**:
    *   デバッグ目的で使用されていた`stackPoisonCopy`に関連する`fillstack`の呼び出しが削除されました。これは、このコミットの主要なロジック変更とは直接関係ありませんが、コードのクリーンアップの一環として行われた可能性があります。

これらの変更により、`copystack`の処理フローは「スタックを新しい場所にコピーする」→「補助構造体を調整する」→「新しいスタック上のポインタを調整する」という、より論理的で安全なシーケンスに再構築されました。これにより、特に並行環境下でのスタック操作の安全性が向上し、将来的な機能拡張（並行スタック縮小など）が容易になります。

# [インデックス 27158] ファイルの概要

このコミットはGoランタイムの`src/runtime/stack.go`ファイルに対する変更です。`stack.go`はGoのランタイムにおいて、ゴルーチンのスタック管理、特にスタックの確保、解放、そして最も重要なスタックのコピー（リサイズ）に関連するロジックを実装しています。Goのゴルーチンは可変サイズのスタックを使用するため、実行中にスタックが不足したり、逆に大きすぎたりする場合に、このファイル内の関数がスタックのリサイズ処理を担当します。

## コミット

このコミットは、Goランタイムの`copystack`関数におけるスタックコピーとポインタ調整の順序を変更するものです。以前は、古いスタック上のポインタを調整してから新しいスタックにコピーしていましたが、この変更により、まずスタック全体を新しい場所にコピーし、その後で新しいスタック上のポインタを調整するようになりました。この変更は、コードの理解を容易にし、将来的な並行スタック縮小の実装を簡素化することを目的としています。

    Currently copystack adjusts pointers in the old stack and then copies
    the adjusted stack to the new stack. In addition to being generally
    confusing, this is going to make concurrent stack shrinking harder.

    pointers on the new stack (never writing to the old stack).

    stack. In this CL, we adjust auxiliary structures before walking the
    stack, so we can just walk the new stack.

## 変更の背景

この変更の主な背景には、以下の2点があります。

1.  **コードの複雑性と混乱の解消**: 以前の実装では、`copystack`関数が古いスタック上のポインタを先に調整し、その調整されたスタックを新しい場所にコピーしていました。このアプローチは、処理の流れが直感的でなく、コードの理解を困難にしていました。特に、ポインタ調整が古いメモリ領域に対して行われるという点が混乱を招きやすかったと考えられます。
2.  **並行スタック縮小の困難さ**: Goランタイムは、ゴルーチンのスタックを必要に応じて拡大・縮小します。スタックの縮小は、メモリ使用量を最適化するために重要ですが、複数のゴルーチンが同時に動作する並行環境下でスタックを安全に縮小することは非常に複雑な問題です。古い実装のポインタ調整ロジックは、並行スタック縮小を実装する上での障壁となっていました。具体的には、古いスタックがまだ使用されている可能性がある状態でポインタを調整することは、データ競合や不整合のリスクを高め、並行処理の安全性を確保するための複雑な同期メカニズムを必要としました。

このコミットは、これらの問題を解決するために、スタックのコピーとポインタ調整の順序を入れ替えることで、よりシンプルで安全なアプローチを提供します。これにより、将来的に並行スタック縮小をより容易に実装できる基盤を築いています。また、この変更は、以前のCL 15996の再検討であり、より洗練された方法で同じ目標を達成しようとしています。

## 前提知識の解説

### Goランタイムとゴルーチンスタック管理

Go言語は、軽量な並行処理単位である「ゴルーチン（goroutine）」を特徴としています。各ゴルーチンは独自の実行スタックを持ち、このスタックはプログラムの関数呼び出し、ローカル変数、引数などを格納します。Goランタイムは、これらのゴルーチンのライフサイクルとリソース（特にスタック）を管理する役割を担っています。

Goのスタックは「可変サイズスタック（resizable stack）」であり、プログラムの実行中に必要に応じて自動的に拡大・縮小します。これは、C/C++のような固定サイズのスタックを持つ言語とは異なり、スタックオーバーフローの心配を軽減し、メモリ効率を高めるための重要な機能です。

### スタックの拡張と縮小

*   **スタックの拡張**: ゴルーチンが深い関数呼び出しを行うなどして現在のスタック領域が不足しそうになると、Goランタイムはより大きな新しいスタック領域を確保し、古いスタックの内容を新しいスタックにコピーします。このプロセスを「スタックの拡張」と呼びます。
*   **スタックの縮小**: ゴルーチンが多くのスタック領域を必要としなくなった場合（例えば、深い関数呼び出しから戻った後）、Goランタイムはスタックをより小さなサイズに縮小してメモリを解放しようとします。これを「スタックの縮小」と呼びます。スタックの縮小は、メモリフットプリントを削減し、システム全体のパフォーマンスを向上させるために重要です。

### ポインタ調整の必要性

スタックが新しいメモリ領域に移動される（拡張または縮小される）際、スタック上に存在するポインタ（例えば、ヒープ上のオブジェクトを指すポインタや、スタック上の他のフレームを指すポインタ）は、新しいスタックのベースアドレスに合わせてその値を調整する必要があります。この調整が行われないと、ポインタは古い（無効な）メモリ領域を指したままになり、プログラムのクラッシュやデータ破損を引き起こします。

Goのガベージコレクタ（GC）は、スタック上のポインタを正確に識別し、それらを追跡してヒープ上の到達可能なオブジェクトをマークする役割も担っています。スタックが移動する際には、GCが正しく動作するために、これらのポインタが新しいアドレスを指すように更新されることが不可欠です。

### Goのガベージコレクションとスタック

Goのガベージコレクタは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行して動作します。GCは、プログラムが使用しているメモリ（ヒープ）をスキャンし、到達可能なオブジェクトを特定してマークします。このスキャンプロセスには、ゴルーチンのスタックも含まれます。スタック上のポインタは、ヒープ上のオブジェクトへの参照となり得るため、GCはスタックを「ルート」として利用し、そこから到達可能なオブジェクトをマークします。

スタックのリサイズ中にポインタが正しく調整されないと、GCは古いスタック上のポインタを誤って解釈したり、新しいスタック上のポインタを見落としたりする可能性があります。これは、メモリリークや、誤って解放されたメモリへのアクセス（Use-After-Free）といった深刻なバグにつながります。

### Issue #12967

このコミットメッセージで参照されている`#12967`は、GoのIssueトラッカーにおける「runtime: concurrent stack shrinking」というタイトルのIssueです。このIssueは、Goランタイムにおける並行スタック縮小の実現に向けた課題と議論を扱っています。スタックの縮小は、メモリ効率の向上に寄与しますが、並行処理環境下での安全な実装は複雑であり、このコミットのような基盤的な変更が必要とされていました。

## 技術的詳細

### `copystack`関数の役割

`copystack`関数は、Goランタイムにおいてゴルーチンのスタックをリサイズする際の中心的な役割を担います。具体的には、現在のスタック領域が不足した場合（スタック拡張）や、過剰なスタック領域を解放する場合（スタック縮小）に呼び出されます。この関数は、新しいサイズのスタック領域を確保し、古いスタックの内容を新しいスタックに移動させ、そしてスタック上のすべてのポインタを新しいアドレスに合わせて調整します。

### 変更前後の処理フローの比較

**変更前（旧実装）:**

1.  `gcLockStackBarriers(gp)`: スタックバリアをロックし、`sigprof`スキャンを禁止します。
2.  `gentraceback`を呼び出し、古いスタック上のポインタを調整します。この際、`adjinfo.delta`（新しいスタックと古いスタックのアドレス差）に基づいてポインタの値を計算し、新しいスタックのアドレスを指すようにします。**しかし、この調整は古いスタック上で行われるか、あるいは新しいスタックのアドレスを計算して調整するものの、まだデータがコピーされていない状態で行われます。**
3.  `adjustctxt`, `adjustdefers`, `adjustpanics`, `adjustsudogs`, `adjuststkbar`: スタック上のポインタを持つ補助構造体（コンテキスト、defer、panic、select/send/recv操作に関連するデータ、スタックバリア）を調整します。
4.  `memmove`: 古いスタックの内容を新しいスタックの場所にコピーします。

この順序は、「古いスタックを調整してからコピーする」というもので、特に「調整」が古いスタックに対して行われる（あるいは、コピー前の状態を前提とする）点が混乱を招き、並行処理の安全性を確保する上で複雑さを増していました。

**変更後（新実装）:**

1.  `adjinfo`の計算: スタックの移動量（`adjinfo.delta`）を計算します。
2.  `memmove`: **まず、古いスタックの内容を新しいスタックの場所にコピーします。** これにより、新しいスタック領域には古いスタックのデータがそのまま（ポインタは古いアドレスを指したまま）存在することになります。
3.  `gcLockStackBarriers(gp)`: スタックバリアをロックし、`sigprof`スキャンを禁止します。
4.  `adjustctxt`, `adjustdefers`, `adjustpanics`, `adjustsudogs`, `adjuststkbar`: スタック上のポインタを持つ補助構造体を調整します。**このステップは、`gentraceback`がこれらの構造体を使用するため、スタックウォークの前に実行されます。**
5.  `gentraceback`を呼び出し、**新しいスタック上のポインタを調整します。** `adjinfo.delta`に基づいて、新しいスタック内のポインタが正しいアドレスを指すように更新されます。
6.  `gcUnlockStackBarriers(gp)`: スタックバリアのロックを解除します。

この新しい順序は、「まずコピーし、それから新しい場所で調整する」という、より直感的で安全なアプローチを提供します。古いスタックには一切書き込みを行わないため、並行処理における競合のリスクが低減されます。

### `gentraceback`とポインタ調整のメカニズム

`gentraceback`関数は、Goランタイムのスタックウォーカーであり、ゴルーチンのスタックフレームを一つずつ辿っていくために使用されます。この関数は、デバッガ、プロファイラ、そしてガベージコレクタによるスタックスキャンなど、様々な目的で利用されます。

`copystack`における`gentraceback`の役割は、スタック上のすべてのポインタを特定し、それらを新しいスタックアドレスに合わせて調整することです。`gentraceback`は、各スタックフレームのメタデータ（関数情報、引数、ローカル変数のレイアウトなど）を利用して、どのメモリ位置がポインタであるかを識別します。そして、`adjustframe`というコールバック関数を呼び出し、`adjinfo`構造体に含まれる`delta`情報を使ってポインタの値を更新します。

### 補助構造体（`adjustctxt`など）の役割

`adjustctxt`, `adjustdefers`, `adjustpanics`, `adjustsudogs`, `adjuststkbar`といった関数は、ゴルーチンのスタックに関連する様々な補助的なデータ構造に含まれるポインタを調整するために存在します。

*   `adjustctxt`: コンテキスト（`context`パッケージに関連するデータ）内のポインタを調整します。
*   `adjustdefers`: `defer`ステートメントに関連するデータ構造（遅延実行される関数の情報など）内のポインタを調整します。`defer`はスタック上に情報を保持するため、スタック移動時にそのポインタも更新される必要があります。
*   `adjustpanics`: `panic`および`recover`に関連するデータ構造内のポインタを調整します。`panic`情報もスタックに関連付けられています。
*   `adjustsudogs`: `select`ステートメントやチャネルの送受信操作（`send` / `recv`）に関連するデータ構造内のポインタを調整します。これらの操作は、ゴルーチンがブロックされる可能性があるため、その状態を保持する構造体もスタック移動の影響を受けます。
*   `adjuststkbar`: スタックバリア（スタックの境界を示す情報）に関連するポインタを調整します。これは、GCがスタックをスキャンする際に使用する情報です。

これらの補助構造体は、ゴルーチンの実行状態や特定の言語機能（defer, panic, selectなど）を正しく維持するために不可欠であり、スタックが移動する際には、それらが参照するメモリ位置も適切に更新される必要があります。新しい実装では、これらの補助構造体の調整が`gentraceback`によるスタックウォークの前に移動されました。これは、`gentraceback`自体がこれらの構造体の一部を使用する可能性があるため、それらが最新の状態であることを保証するためです。

### 並行スタック縮小への影響

この変更は、並行スタック縮小の実装を大幅に簡素化します。

*   **古いスタックへの書き込みの排除**: 変更前は、ポインタ調整が古いスタックに対して行われる可能性があり、もし古いスタックがまだ他のゴルーチンやGCによって参照されている場合、データ競合のリスクがありました。新しい実装では、まずスタック全体を新しい場所にコピーし、その後で新しいスタック上でのみポインタ調整を行います。これにより、古いスタックは読み取り専用となり、安全に解放できるようになります。
*   **簡素化された同期**: 古いスタックへの書き込みがなくなることで、スタックリサイズ中の同期メカニズムが簡素化されます。GCや他のゴルーチンが古いスタックを参照している間に、その内容が変更されることを心配する必要がなくなります。
*   **明確な状態遷移**: スタックのコピーが最初に行われることで、スタックの状態遷移がより明確になります。「古いスタックから新しいスタックへデータが移動し、その後新しいスタック上でポインタが修正される」という一貫した流れは、並行処理の推論を容易にします。

これにより、Goランタイム開発者は、より少ない複雑さで、より効率的で安全な並行スタック縮小アルゴリズムを設計・実装できるようになります。

## コアとなるコードの解説

このdiffは、`copystack`関数内の処理順序が大きく変更されたことを示しています。

1.  **`gcLockStackBarriers(gp)`と`gentraceback`の移動**:
    *   変更前は、`gcLockStackBarriers(gp)`が最初に呼び出され、その直後に`gentraceback`が古いスタックのポインタ調整のために呼び出されていました。
    *   変更後、`gcLockStackBarriers(gp)`は`memmove`によるスタックコピーの後に移動しました。
    *   `gentraceback`の呼び出しは、`memmove`と補助構造体の調整の後に移動し、コメントが「Adjust pointers in the new stack.」と変更されています。これは、`gentraceback`が新しいスタック上のポインタを調整するようになったことを明確に示しています。

2.  **`memmove`の早期実行**:
    *   変更前は、`gentraceback`によるポインタ調整と補助構造体の調整の後に`memmove`が実行されていました。
    *   変更後、`adjinfo`の計算の直後に`memmove`が実行されるようになりました。これにより、スタックの内容がまず新しい場所にコピーされ、その後でポインタ調整が行われるという新しいロジックが確立されました。

3.  **補助構造体調整のタイミング変更**:
    *   `adjustctxt`, `adjustdefers`, `adjustpanics`, `adjustsudogs`, `adjuststkbar`といった補助構造体を調整する関数群は、変更前は`gentraceback`の後に実行されていました。
    *   変更後、これらの関数は`memmove`によるスタックコピーの後、かつ`gentraceback`による新しいスタックのポインタ調整の前に実行されるようになりました。これは、コメント「Adjust structures that have pointers into stacks. We have to do most of these before we traceback the new stack because gentraceback uses them.」が示すように、`gentraceback`がこれらの補助構造体を使用する可能性があるため、スタックウォークの前にそれらが最新の状態であることを保証するためです。

4.  **`stackPoisonCopy`関連コードの削除**:
    *   デバッグ目的で使用されていた`stackPoisonCopy`に関連する`fillstack`の呼び出しが削除されました。これは、このコミットの主要なロジック変更とは直接関係ありませんが、コードのクリーンアップの一環として行われた可能性があります。

これらの変更により、`copystack`の処理フローは「スタックを新しい場所にコピーする」→「補助構造体を調整する」→「新しいスタック上のポインタを調整する」という、より論理的で安全なシーケンスに再構築されました。これにより、特に並行環境下でのスタック操作の安全性が向上し、将来的な機能拡張（並行スタック縮小など）が容易になります。

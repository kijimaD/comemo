## 変更の背景

このコミットの主な目的は、Goコンパイラのコードベースの可読性と保守性を向上させるためのリファクタリングです。以前のGoコンパイラでは、真偽値を示すために `uint8` 型の変数を使用し、`0` を偽、`1` を真として扱っていました。これはC言語の慣習に由来するものと考えられます。

しかし、Go言語には明確な `bool` 型が存在し、真偽値を表現するのに適しています。`uint8` を真偽値として使うことは、以下のような問題を引き起こす可能性があります。

1.  **可読性の低下**: `Isint[i] != 0` のような記述は、`Isint[i]` が真偽値であることを直感的に理解しにくくします。`Isint[i]` と書く方が、その変数が論理的な状態を表していることが明確です。
2.  **型安全性の欠如**: `uint8` は `0` または `1` 以外の値も取りうるため、意図しない数値が代入された場合に論理的なエラーを引き起こす可能性があります。`bool` 型を使用すれば、コンパイラが `true` または `false` 以外の値の代入を禁止するため、このようなエラーを未然に防ぐことができます。
3.  **Go言語のイディオムとの乖離**: Go言語の標準的なコーディングスタイルでは、真偽値には `bool` 型を使用することが推奨されます。この変更は、コンパイラ自身のコードをGo言語のイディオムに合わせるものです。

機能的な変更は一切なく、純粋にコードの品質を向上させるためのクリーンアップ作業として実施されました。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの構造とGo言語の基本的な型システムに関する知識が必要です。

### Goコンパイラの構造

Goコンパイラ（`gc`）は、大きく分けて以下の部分から構成されます。

*   **`cmd/internal/gc`**: これはGoコンパイラの主要部分であり、プラットフォームに依存しないフロントエンドとミドルエンドの処理を担当します。具体的には、ソースコードのパース、抽象構文木（AST）の構築、型チェック、最適化、中間表現（IR）への変換などを行います。この部分には、Go言語の型システムに関する情報（例: ある型が整数型か、浮動小数点型か、ポインタ型かなど）を保持するためのデータ構造や関数が多く含まれています。
*   **`cmd/{arch}g` (例: `cmd/5g`, `cmd/6g`, `cmd/8g`, `cmd/9g`)**: これらは各CPUアーキテクチャ（ARM, x86-64, x86-32, PowerPCなど）に特化したバックエンドです。`gc` が生成した中間表現を受け取り、最終的な機械語コードを生成します。これらのバックエンドも、型に関する情報を参照して、特定の型の値に対する操作（例: 浮動小数点演算、ポインタのデリファレンスなど）を適切に処理します。

### `uint8` と `bool` の違い

*   **`uint8`**: 符号なし8ビット整数型です。0から255までの整数値を格納できます。C言語では、真偽値を表現するために `0` を偽、非 `0` を真として扱う慣習があります。Goコンパイラの古いコードベースでは、このC言語の慣習が一部残っており、`uint8` 型の変数を真偽値として使用していました。例えば、`Isint[i] = 1` は `i` が整数型であることを示し、`Isint[i] == 0` は整数型ではないことを示していました。
*   **`bool`**: Go言語の組み込み真偽値型です。`true` または `false` のいずれかの値のみを格納できます。`bool` 型は、その目的が真偽値を表現することに限定されているため、より明確で型安全なコードを書くことができます。

### Goの型システム

Go言語は静的型付け言語であり、変数の型はコンパイル時に決定されます。Goの型システムは、コードの信頼性と保守性を高めることを目的としています。`bool` 型のような明確な真偽値型を使用することは、この型安全性の原則に合致しています。

### `gofmt` の役割

`gofmt` はGo言語の公式フォーマッタです。Goのソースコードを標準的なスタイルに自動的に整形します。このコミットでは、`gofmt -r` コマンドが使用されており、これはリライトルール（rewrite rules）を適用してコードを変換する機能です。この機能を使って、`IsX[type] != 0` のようなパターンを `IsX[type]` に自動的に変換する作業が行われました。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラ内部で真偽値として扱われていた `uint8` 型の変数を `bool` 型に置き換えることです。これにより、コードの意図がより明確になり、型安全性が向上します。

具体的な変更パターンは以下の通りです。

1.  **型定義の変更**:
    `src/cmd/internal/gc/go.go` ファイルにおいて、`Isptr`, `isforw`, `Isint`, `Isfloat`, `Iscomplex`, `Issigned`, `issimple`, `okforeq`, `okforadd`, `okforand`, `okfornone`, `okforcmp`, `okforbool`, `okforcap`, `okforlen`, `okforarith`, `okforconst`, `iscmp` といったグローバル変数や配列の型が `uint8` から `bool` に変更されました。

    ```go
    var iscmp [OEND]uint8
    ```

2.  **初期化処理の変更**:
    `src/cmd/internal/gc/align.go` の `typeinit()` 関数など、これらの変数が初期化される箇所で、`= 1` が `= true` に変更されました。

    **変更前**:

    ```go
    Isfloat[TFLOAT32] = true

    ```

3.  **条件式の変更**:
    コードベース全体で、これらの `uint8` 型の変数が真偽値として使用されていた条件式 (`if Isint[i] != 0` や `if Isptr[t.Etype] == 0`) が、よりGo言語らしい `bool` 型の直接的な評価 (`if Isint[i]` や `if !Isptr[t.Etype]`) に変更されました。

### 変更の実施方法

コミットメッセージに記載されているように、この変更は手動での編集と `gofmt -r` を組み合わせることで行われました。

*   `cmd/internal/gc/go.go` の型定義と変数グループ化の手動編集。
*   `cmd/internal/gc/align.go` の初期化処理の手動編集（`1` を `true` に）。
*   `cmd/internal/gc/walk.go` の `bounded` 関数における符号の扱いの手動修正。
*   `go.y` の手動更新と `y.go` の再生成。`go.y` はGoコンパイラのパーサー定義ファイルであり、変更がパーサーの動作に影響を与える可能性があるため、手動での調整が必要でした。
*   残りの大部分の変更は、Josh Bleecher Snyder氏が作成した `gofmt -r` のリライトルール（[https://gist.github.com/josharian/0f61dbb2dff81f938e70](https://gist.github.com/josharian/0f61dbb2dff81f938e70)）を複数回実行することで自動的に行われました。このリライトルールは、`X != 0` を `X` に、`X == 0` を `!X` に変換するものです。

### 検証

変更後、`toolstash -cmp` コマンドを使用して標準ライブラリ（stdlib）に対する比較が行われ、機能的な差異がないことが確認されました。これは、この変更が純粋なリファクタリングであり、コンパイラの出力結果に影響を与えないことを保証するための重要なステップです。

## コアとなるコードの解説

上記のコード変更は、Goコンパイラの内部で型に関する情報を扱う方法を、よりGo言語のイディオムに沿ったものにするためのものです。

1.  **`src/cmd/internal/gc/go.go` における型定義の変更**:
    これは、Goコンパイラ全体で共有される型関連のフラグや特性を定義している部分です。以前は `uint8` 型の配列として定義されていましたが、これはC言語の `0` を偽、非 `0` を真とする慣習を引き継いだものでした。Go言語には `bool` 型が明確に存在するため、これらのフラグを `bool` 型にすることで、コードの意図がより明確になります。
    例えば、`Isint [NTYPE]uint8` は「各型が整数型であるか否か」を示す配列でしたが、`Isint [NTYPE]bool` に変更することで、その配列の各要素が真偽値であることをコンパイラが強制するようになります。これにより、誤って `Isint[i] = 5` のような代入が行われることを防ぎ、型安全性が向上します。
    また、複数の変数を `var (...)` ブロックでグループ化することで、関連する変数が一箇所にまとまり、コードの整理にも貢献しています。

2.  **`src/cmd/internal/gc/align.go` における初期化の変更**:
    `typeinit()` 関数は、コンパイラの起動時に各種型関連のフラグを初期化する役割を担っています。型定義が `uint8` から `bool` に変更されたことに伴い、初期値の `1` が `true` に、`0` が `false` に変更されました。これは論理的な意味合いを変えることなく、新しい型定義に合わせた自然な変更です。

3.  **`src/cmd/5g/cgen.go` における条件式の変更例**:
    `cgen.go` はARMアーキテクチャ向けのコード生成に関連するファイルです。このファイルには、型の特性（例: 複素数型か、浮動小数点型か）に基づいて異なるコードパスを選択する条件式が多数存在します。
    変更前は `gc.Iscomplex[n.Type.Etype] != 0` のように、`uint8` 型の `Iscomplex` 配列の要素が `0` ではないことを確認することで真偽を判定していました。
    変更後は `gc.Iscomplex[n.Type.Etype]` のように、`bool` 型の `Iscomplex` 配列の要素を直接評価する形になりました。これはGo言語における `bool` 型の標準的な使用方法であり、コードの可読性が大幅に向上します。`!gc.Iscomplex[n.Type.Etype]` のように否定演算子 `!` を使うことで、「複素数型ではない場合」という条件も直感的に理解できるようになります。

これらの変更は、GoコンパイラがGo言語自身のベストプラクティスに沿って進化していることを示しており、将来的なコードの保守性や拡張性にも寄与します。機能的な影響がないため、ユーザーや開発者が直接この変更を意識する必要はありませんが、コンパイラ開発者にとってはよりクリーンで安全なコードベースとなります。

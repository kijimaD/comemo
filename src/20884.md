# [インデックス 20884] ファイルの概要

このコミットは、Goランタイムにおける`power64le`アーキテクチャ向けのシグナルスタック定義に関する修正です。具体的には、`src/runtime/defs3_linux.go`と`src/runtime/defs_linux_power64le.h`の2つのファイルが変更されています。

-   `src/runtime/defs3_linux.go`: GoのランタイムがLinuxシステムコールやデータ構造と連携するために使用する定義が含まれています。このファイルは通常、Cgoによって生成されるか、Cの構造体に対応するGoの型定義を含んでいます。
-   `src/runtime/defs_linux_power64le.h`: `power64le`アーキテクチャ（PowerPC 64-bit Little Endian）に特化したLinuxシステムコールやデータ構造のC言語ヘッダ定義が含まれています。Goランタイムがこのアーキテクチャ上で正しく動作するために必要な、低レベルの型定義や定数が記述されています。

## 変更の背景

このコミットの背景には、Goランタイムが`power64le`（PowerPC 64-bit Little Endian）アーキテクチャ上でシグナルハンドリングを正しく行うための定義の不整合がありました。`Sigaltstack`（代替シグナルスタック）の定義がこのアーキテクチャにおいて適切でなかったため、シグナルが配送された際に問題が発生する可能性がありました。

特に、`defs_linux_power64le.h`はCgoによって自動生成されるべきファイルですが、当時の`ppc64`におけるCgoのネイティブな動作が完全ではなかったため、手動での修正が必要でした。これは一時的な措置であり、将来的にCgoが完全に機能するようになった際にファイルを再生成する意図が示されています。この修正は、`power64le`環境でのGoプログラムの安定性と信頼性を確保するために不可欠でした。

## 前提知識の解説

### シグナルと代替シグナルスタック (`sigaltstack`)

Unix系OSにおいて、シグナルはプロセスに対して非同期的にイベントを通知するメカニズムです。例えば、セグメンテーション違反（SIGSEGV）やスタックオーバーフローが発生した場合、OSはプロセスにシグナルを送信します。プロセスはこれらのシグナルを捕捉し、特定のシグナルハンドラ関数を実行することで対応できます。

しかし、シグナルハンドラが実行される際に、通常のスタックが破損している（例えばスタックオーバーフローによって）場合、シグナルハンドラ自身が実行できない、あるいはさらなるクラッシュを引き起こす可能性があります。これを避けるために導入されたのが「代替シグナルスタック（alternative signal stack）」です。

`sigaltstack`システムコールを使用すると、プロセスは通常のスタックとは別の、独立したスタック領域をシグナルハンドラ専用に設定できます。これにより、通常のスタックがどのような状態であっても、シグナルハンドラは安全に実行され、問題の診断や回復処理を行うことが可能になります。`struct sigaltstack`は、この代替シグナルスタックの情報を定義するための構造体で、スタックの開始アドレス、サイズ、および状態（有効/無効など）を含みます。

### `power64le` (PowerPC 64-bit Little Endian)

`power64le`は、IBMが開発したPowerPCアーキテクチャの64ビット版で、特にリトルエンディアン（Little Endian）バイトオーダーを採用していることを指します。

-   **PowerPC**: RISC（Reduced Instruction Set Computer）アーキテクチャの一つで、高性能コンピューティング、組み込みシステム、ゲーム機など幅広い分野で使用されてきました。
-   **64-bit**: 64ビットのレジスタとアドレス空間を持ち、より大きなメモリを扱え、より複雑な計算を効率的に実行できます。
-   **Little Endian**: 複数バイトのデータをメモリに格納する際に、最下位バイト（least significant byte）が最も小さいアドレスに配置される方式です。Intel x86アーキテクチャもリトルエンディアンを採用しており、Linux環境では広く使われています。

Go言語はクロスプラットフォーム対応を重視しており、`power64le`のような特定のアーキテクチャ上でもGoプログラムが正しく動作するように、アーキテクチャ固有の低レベルな定義やアセンブリコードをGoランタイム内に含んでいます。

### `cgo`

`cgo`はGo言語のツールチェーンの一部であり、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのメカニズムを提供します。Goはシステムプログラミング言語ですが、OSの低レベルな機能（システムコール、デバイスドライバなど）や既存のCライブラリを利用する際には、`cgo`が不可欠になります。

`cgo`は、Cのヘッダファイル（`.h`）を読み込み、それに対応するGoの型定義や関数プロトタイプを自動生成する機能を持っています。これにより、GoコードからCの構造体や関数を型安全に扱うことが可能になります。このコミットの文脈では、`defs_linux_power64le.h`のようなファイルが`cgo`によって生成されるべきものであることが示唆されています。

### `defs_linux_power64le.h` と `defs3_linux.go`

これらはGoランタイムの内部ファイルであり、特定のOS（Linux）およびアーキテクチャ（`power64le`）に依存する低レベルな定義を含んでいます。

-   **`defs_linux_power64le.h`**: C言語のヘッダファイルで、`power64le`アーキテクチャにおけるLinuxのシステムコールやデータ構造（例: `struct sigaltstack`, `struct ucontext`など）のC言語での定義が含まれます。GoランタイムがこれらのOS固有の構造体を理解し、操作するために必要です。
-   **`defs3_linux.go`**: Go言語のソースファイルで、`defs_linux_power64le.h`のようなCヘッダファイルで定義されたCの構造体に対応するGoの型定義を含みます。`C.struct_sigaltstack`のように、`cgo`が提供する`C`パッケージを通じてCの型を参照し、それらをGoの型にエイリアスしています。これにより、GoコードがCの低レベルな構造体をGoの型システム内で扱えるようになります。

これらのファイルは、GoランタイムがOSと直接やり取りする際のインターフェースを定義しており、OSやアーキテクチャの変更に追従して更新される必要があります。

## 技術的詳細

このコミットの主要な技術的変更は、`Sigaltstack`という型名の変更と、それに伴う関連する構造体定義の更新です。

1.  **型名の変更**:
    *   `src/runtime/defs3_linux.go`において、`type Sigaltstack C.struct_sigaltstack`という定義が`type SigaltstackT C.struct_sigaltstack`に変更されました。
    *   同様に、`src/runtime/defs_linux_power64le.h`においても、`typedef struct Sigaltstack Sigaltstack;`が`typedef struct SigaltstackT SigaltstackT;`に変更され、`struct Sigaltstack`自体も`struct SigaltstackT`にリネームされました。

2.  **`Ucontext`構造体内の参照の更新**:
    *   `src/runtime/defs_linux_power64le.h`内の`struct Ucontext`定義において、`Sigaltstack uc_stack;`が`SigaltstackT uc_stack;`に変更されました。`ucontext`構造体は、シグナルハンドラが呼び出された時点のプロセスのコンテキスト（レジスタの状態、シグナルマスク、スタック情報など）を保存するために使用される重要な構造体です。この構造体内の代替シグナルスタックへの参照が、新しい型名`SigaltstackT`に更新されたことは、シグナルハンドリングの整合性を保つ上で不可欠です。

この変更の背後にある理由は、既存の`Sigaltstack`という型名が、`power64le`アーキテクチャの特定のコンテキストで問題を引き起こしていたか、あるいはGoランタイム全体の命名規則やCgoによる自動生成の慣習に合わせるためにリネームが必要だったと考えられます。特に、`SigaltstackT`という命名は、Goの内部でCの構造体に対応する型に`T`サフィックスを付ける慣習がある場合によく見られます。

手動での`defs_linux_power64le.h`の編集は、当時の`power64le`におけるCgoの成熟度が不十分であったことを示唆しています。通常、このような低レベルの定義ファイルは、クロスコンパイル環境や特定のアーキテクチャ向けにCgoが自動生成することが望ましいです。手動編集は、一時的な回避策であり、将来的にCgoが`ppc64`上でネイティブに動作するようになった際に、このファイルを再生成することで、手動編集の必要がなくなることを期待しています。

この修正により、`power64le`環境におけるGoプログラムのシグナルハンドリングが安定し、予期せぬクラッシュや動作不良が防止されることが期待されます。

## コアとなるコードの解説

### `src/runtime/defs3_linux.go` の変更

```go
-type Sigaltstack C.struct_sigaltstack
+type SigaltstackT C.struct_sigaltstack
```
この変更は、GoのランタイムがC言語の`struct sigaltstack`に対応するGoの型を定義している箇所です。元の`Sigaltstack`という型名が`SigaltstackT`に変更されました。これは、Goの内部的な命名規則に合わせるため、あるいは既存の`Sigaltstack`という名前との衝突を避けるために行われたと考えられます。`C.struct_sigaltstack`は、`cgo`を通じてC言語の`struct sigaltstack`を参照していることを示します。

### `src/runtime/defs_linux_power64le.h` の変更

このファイルは、`power64le`アーキテクチャ向けのC言語ヘッダ定義です。

```c
-typedef struct Sigaltstack Sigaltstack;
+typedef struct SigaltstackT SigaltstackT;
```
ここでは、`Sigaltstack`という構造体の`typedef`エイリアスが`SigaltstackT`に変更されています。これにより、Cコード内で`Sigaltstack`として参照されていた型が、新しい`SigaltstackT`として扱われるようになります。

```c
-struct Sigaltstack {
+struct SigaltstackT {
 	byte	*ss_sp;
 	int32	ss_flags;
 	byte	Pad_cgo_0[4];
 	uint64	ss_size;
 };
```
`struct Sigaltstack`自体の定義が`struct SigaltstackT`にリネームされました。この構造体は、代替シグナルスタックのポインタ（`ss_sp`）、フラグ（`ss_flags`）、およびサイズ（`ss_size`）を保持します。`Pad_cgo_0`は、Cgoが構造体のアライメントを調整するために挿入するパディングバイトです。

```c
 struct Ucontext {
 	uint64	uc_flags;
 	Ucontext	*uc_link;
-\tSigaltstack	uc_stack;
+\tSigaltstackT	uc_stack;
 	Usigset	uc_sigmask;
 	Usigset	__unused[15];
 	Sigcontext	uc_mcontext;
 };
```
`struct Ucontext`は、シグナルハンドラが呼び出された際のプロセスのコンテキストを保持する重要な構造体です。この構造体内の`uc_stack`フィールドは、代替シグナルスタックの情報を保持します。この変更では、`uc_stack`の型が古い`Sigaltstack`から新しい`SigaltstackT`に更新されています。これにより、`ucontext`が正しく代替シグナルスタックの情報を参照できるようになり、`power64le`環境でのシグナルハンドリングの整合性が保たれます。

これらの変更は、`power64le`アーキテクチャにおけるシグナルスタックの定義を修正し、Goランタイムがこのアーキテクチャ上で安定して動作するための基盤を強化するものです。

# [インデックス 23099] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）ゴルーチンの開始プロセスを簡素化するものです。主な変更は、`src/runtime/mgc.go` と `src/runtime/proc1.go` の2つのファイルにわたります。

*   `src/runtime/mgc.go`: Goランタイムのガベージコレクション（GC）メカニズムを実装しているファイルです。GCのトリガー、実行、および関連するロジックが含まれています。このコミットでは、GCゴルーチンの開始方法が変更されています。
*   `src/runtime/proc1.go`: Goランタイムのスケジューラとゴルーチン管理の基本的な部分を扱っているファイルです。ゴルーチンの状態遷移、実行キューへの追加、およびコンテキストスイッチに関連する関数が含まれています。このコミットでは、`readyExecute` という特定の関数が削除されています。

    runtime: simplify process for starting GC goroutine
    
    Currently, when allocation reaches the GC trigger, the runtime uses
    readyExecute to start the GC goroutine immediately rather than wait
    for the scheduler to get around to the GC goroutine while the mutator
    continues to grow the heap.
    
    Now that the scheduler runs the most recently readied goroutine when a
    goroutine yields its time slice, this rigmarole is no longer
    necessary. The runtime can simply ready the GC goroutine and yield
    from the readying goroutine.

## 元コミット内容

現在、アロケーションがGCトリガーに達すると、ランタイムは`readyExecute`を使用してGCゴルーチンを即座に開始します。これは、ミューテーター（ユーザープログラム）がヒープを成長させ続ける間に、スケジューラがGCゴルーチンに到達するのを待つのではなく、すぐにGCを開始するためです。

スケジューラが、ゴルーチンがタイムスライスを譲ったときに、最も最近readyにされたゴルーチンを実行するようになったため、この複雑な手順はもはや必要ありません。ランタイムは単にGCゴルーチンをreadyにし、GCゴルーチンをreadyにしたゴルーチンから実行を譲るだけでよくなりました。

## 変更の背景

このコミットの背景には、Goランタイムのスケジューラの進化があります。以前のGoランタイムでは、ヒープのアロケーションがGCのトリガーポイントに達した際、GCゴルーチンを迅速に開始する必要がありました。これは、ユーザープログラム（ミューテーター）がGCが開始されるまでの間にさらにヒープを消費し、GCの効率を低下させたり、メモリ使用量を不必要に増加させたりするのを防ぐためです。

この目的のために、Goランタイムは`readyExecute`という特殊な関数を使用していました。`readyExecute`は、GCゴルーチンを通常のスケジューリングキューを介さずに、ほぼ即座に実行させるためのメカニズムでした。しかし、この方法はランタイムのコードに特定の複雑性をもたらしていました。例えば、`readyExecute`は現在のM（OSスレッド）がロックされたゴルーチンを持っていないなど、特定の条件下でしか安全に呼び出せないといった制約がありました。

このコミットが行われた時点（2015年）までに、Goスケジューラの動作が改善されました。特に、あるゴルーチンがそのタイムスライスを自発的に譲った（`Gosched()`を呼び出した）際に、スケジューラが「最も最近readyにされたゴルーチン」を優先的に実行するようになったという変更がありました。この新しいスケジューラの振る舞いにより、GCゴルーチンを`ready`状態にしてから、現在のゴルーチンが`Gosched()`を呼び出すだけで、GCゴルーチンが迅速に実行されることが保証されるようになりました。

結果として、`readyExecute`のような特殊な即時実行メカニズムは不要となり、コードの簡素化と保守性の向上が可能になりました。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するシステムです。ガベージコレクション、ゴルーチン管理、スケジューリング、システムコールなど、Goプログラムが動作するために必要な低レベルの機能を提供します。
*   **Goroutine (ゴルーチン)**: Go言語における軽量な実行単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行することも可能です。Goランタイムのスケジューラによって管理されます。
*   **Goスケジューラ (Go Scheduler)**: ゴルーチンをOSスレッド（M: Machine）にマッピングし、CPUコア（P: Processor）上で実行を管理するGoランタイムの重要なコンポーネントです。ゴルーチンの実行、一時停止、再開、コンテキストスイッチなどを担当します。
*   **GC (Garbage Collection - ガベージコレクション)**: Goの自動メモリ管理機能です。プログラムが不要になったメモリ領域を自動的に解放し、メモリリークを防ぎます。GoのGCは、ほとんどの作業をユーザープログラムと並行して実行する「並行GC（Concurrent GC）」を採用しています。
*   **GC Goroutine (GCゴルーチン)**: ガベージコレクションの主要な処理（マークフェーズやスイープフェーズの一部など）を実行するためにGoランタイムが内部的に起動する特別なゴルーチンです。
*   **Mutator (ミューテーター)**: ガベージコレクションの文脈で使われる用語で、ユーザーが書いたアプリケーションコード、つまりヒープ上のオブジェクトを作成・変更するプログラムの部分を指します。ミューテーターが活発に動作すると、ヒープサイズが増加します。
*   **`readyExecute` (旧メカニズム)**: このコミットで削除されたGoランタイムの内部関数です。特定のゴルーチン（この場合はGCゴルーチン）を、通常のスケジューリングキューを介さずに、現在のOSスレッド上で即座に実行を開始させるための特殊なメカニズムでした。これにより、GCを迅速に開始し、ミューテーターによるヒープの過剰な成長を防ぐことを目的としていました。
*   **`ready` 関数**: Goランタイムの内部関数で、指定されたゴルーチンを「実行可能（runnable）」状態にし、スケジューラの実行キューに追加します。これにより、そのゴルーチンは次にスケジューラによって選択され、実行される準備が整います。
*   **`Gosched()` 関数**: `runtime.Gosched()` としてGoプログラムから呼び出すことができる関数です。現在のゴルーチンがCPUを自発的に手放し、他の実行可能なゴルーチンに実行を譲ることをスケジューラに伝えます。これにより、現在のゴルーチンは実行キューに戻され、スケジューラは別のゴルーチンを選択して実行します。

## 技術的詳細

このコミットの核心は、Goランタイムのスケジューリング戦略の成熟と、それによるGCゴルーチン開始ロジックの簡素化です。

**旧来の`readyExecute`の動作と課題:**
GCトリガーに達した際、ランタイムはGCゴルーチンをできるだけ早く実行したかったため、`readyExecute`を使用していました。この関数は、通常の`ready`関数がゴルーチンを実行キューに入れるだけであるのに対し、現在のゴルーチンをプリエンプト（中断）し、GCゴルーチンに直接コンテキストスイッチを行うような動作をしていました。これにより、GCゴルーチンはスケジューラの通常の巡回を待つことなく、即座にCPUを獲得できました。

しかし、`readyExecute`はいくつかの課題を抱えていました。
1.  **複雑性**: 即座のコンテキストスイッチは、ランタイムの内部状態、特に現在のM（OSスレッド）の状態に依存する複雑なロジックを必要としました。例えば、Mが既にロックされたゴルーチンを実行している場合など、特定の条件下では`readyExecute`を安全に呼び出すことができませんでした。
2.  **保守性**: このような特殊なパスは、スケジューラの他の部分の変更に影響を受けやすく、コードの保守を困難にしていました。

**スケジューラの改善と新しいアプローチ:**
このコミットの時点で、Goスケジューラは進化し、より洗練された振る舞いをするようになりました。特に重要なのは、「ゴルーチンがタイムスライスを譲ったときに、最も最近readyにされたゴルーチンを実行する」という特性です。これは、`Gosched()`が呼び出された際に、単に現在のゴルーチンをキューの最後に入れるだけでなく、直前に`ready`にされたゴルーチンがあれば、それを優先的に実行するような最適化が行われたことを示唆しています。

この新しいスケジューラの振る舞いにより、GCゴルーチンを迅速に開始するための`readyExecute`のような特殊なメカニズムは不要になりました。新しいプロセスは以下の通りです。
1.  GCトリガーに達したら、GCゴルーチンを`ready`状態にする（通常の`ready`関数を使用）。
2.  現在のゴルーチンが`Gosched()`を呼び出してCPUを自発的に手放す。

この2ステップにより、スケジューラは直前に`ready`にされたGCゴルーチンを優先的に選択し、実行を開始します。これにより、GCの開始が遅れることなく、かつランタイムのコードが大幅に簡素化されました。

**変更のメリット:**
*   **コードの簡素化**: `readyExecute`関数とその複雑なロジックが完全に削除されました。
*   **保守性の向上**: 特殊なケースハンドリングが減り、スケジューラのコードがより一貫性のあるものになりました。
*   **堅牢性の向上**: 特定のMの状態に依存する危険なパスが排除されました。

## コアとなるコードの解説

**`src/runtime/mgc.go` の `startGC` 関数における変更:**

`startGC`関数は、GCがトリガーされたときにバックグラウンドGCゴルーチンを開始する役割を担っています。

*   **`readied` フラグの導入**: 新たに`readied`というブーリアン変数が導入されました。これは、GCゴルーチンが`ready`状態にされたかどうかを追跡するために使用されます。
*   **旧来の`readyExecute`ロジックの削除**:
    *   以前は、`bggc.working == 0`（GCゴルーチンが現在動作していない）かつ`getg().m.lockedg == nil`（現在のMがロックされたゴルーチンを持っていない）の場合に、`readyExecute(bggc.g, 0)`が呼び出されていました。これは、GCゴルーチンを即座に実行するための特殊なパスでした。
    *   `getg().m.lockedg != nil` の場合は、`ready(bggc.g, 0)`が呼び出され、通常の実行キューに入れられていました。これは、`readyExecute`がロックされたMでは安全に動作しないためです。
*   **新しい`ready`と`Gosched()`の組み合わせ**:
    *   新しいコードでは、`bggc.working == 0` の場合、常に`ready(bggc.g, 0)`が呼び出され、GCゴルーチンが実行可能状態にされます。
    *   そして、`readied`が`true`（つまり、GCゴルーチンがこの`startGC`の呼び出しで`ready`にされたか、`go backgroundgc()`で新しく起動されたか）の場合、`Gosched()`が呼び出されます。
    *   この`Gosched()`の呼び出しにより、現在のゴルーチンはCPUを自発的に手放し、スケジューラは直前に`ready`にされたGCゴルーチンを優先的に選択して実行を開始します。これにより、`readyExecute`が提供していた「即時実行」に近い効果が、よりシンプルで安全な方法で実現されます。

**`src/runtime/proc1.go` から `readyExecute` 関数の削除:**

*   `proc1.go`から`readyExecute`関数が完全に削除されました。この関数は、GCゴルーチンを即座に実行するために特別に設計されたものでしたが、スケジューラの改善によりその必要性がなくなりました。
*   `readyExecute`の削除により、`mcall`（現在のゴルーチンを一時停止し、別の関数をOSスレッドのスタックで実行する低レベルのメカニズム）を使用した複雑なコンテキストスイッチロジックが不要になりました。
*   これにより、ランタイムのコードベースが大幅にクリーンアップされ、理解しやすくなりました。

この変更は、Goランタイムのスケジューラがより賢くなり、特定の最適化のために複雑な特殊ケースを必要としなくなったことを明確に示しています。

## 変更の背景

この大規模なマージコミットの背景には、Go言語のパフォーマンスと移植性を向上させるための複数の戦略的目標があります。

1.  **SSA (Static Single Assignment) フォームの導入**: 従来のGoコンパイラは、AST (Abstract Syntax Tree) を直接操作してコード生成を行っていました。しかし、より高度な最適化を適用するためには、SSAフォームのような中間表現 (IR) が不可欠です。SSAは、各変数が一度だけ代入されることを保証する特性を持ち、データフロー解析や様々な最適化（例: 共通部分式除去、定数伝播、デッドコード削除）を容易にします。このコミットは、GoコンパイラのバックエンドをSSAベースに移行する初期段階であり、将来的なパフォーマンス向上への道を開くものです。

2.  **MIPS64/MIPS64LEアーキテクチャのサポート**: Go言語は、サーバーサイドだけでなく、組み込みシステムや特定のハードウェアプラットフォームでも利用されることを目指しています。MIPS64およびMIPS64LE (Little Endian) は、ルーター、ネットワーク機器、特定の組み込みLinuxシステムなどで広く使用されているアーキテクチャです。これらのプラットフォームへの対応を追加することで、Go言語の適用範囲を広げ、より多様な環境での利用を可能にすることが目的です。

3.  **CGOポインタ安全性とライトバリアの課題**: CGOはGoコードからCコードを呼び出すためのメカニズムですが、Goのガベージコレクタ (GC) とCのメモリ管理の間には根本的な違いがあります。GoのGCはGoヒープ上のポインタを追跡しますが、Cのヒープ上のメモリは追跡しません。GoポインタがCのメモリに格納されると、GCがそのポインタを見失い、参照されているオブジェクトが誤って回収されてしまう可能性があります。これを防ぐために、GoはCGO呼び出し時にポインタの安全性を厳しくチェックします。このコミットでは、そのチェックメカニズム、特にライトバリア (write barrier) との相互作用に関するテストケースが一時的にコメントアウトされており、この領域にまだ解決すべき複雑な問題が存在することを示唆しています。ライトバリアはGCがオブジェクトの参照関係を正確に追跡するために重要なメカニズムです。

4.  **暗号ライブラリのパフォーマンス最適化**: 現代のアプリケーションにおいて暗号化は不可欠であり、その性能は全体のスループットに大きく影響します。P256楕円曲線はTLSなどのプロトコルで広く使用されており、その演算をアセンブリ言語で最適化することで、特にAMD64アーキテクチャ上での暗号処理の高速化を図っています。

## 前提知識の解説

### 1. SSA (Static Single Assignment) フォーム

SSAは、コンパイラ最適化において広く用いられる中間表現 (IR) の一種です。SSA形式では、プログラム中の各変数が一度だけ代入されるという特性を持ちます。もし同じ変数に複数回代入が行われる場合、SSAでは新しい「バージョン」の変数を導入します（例: `x1 = ...`, `x2 = ...`）。複数の制御フローパスが合流する点（例: `if-else`文の終わりやループの合流点）では、`φ` (phi) 関数と呼ばれる特殊な命令が導入され、どのパスから来た値を使用するかを決定します。

**なぜSSAが重要か？**
*   **データフロー解析の簡素化**: 各変数の定義が単一であるため、変数の値がどこから来たのか、どこへ流れていくのかを追跡するのが非常に容易になります。
*   **最適化の効率化**: 共通部分式除去 (CSE)、定数伝播 (Constant Propagation)、デッドコード削除 (Dead Code Elimination)、レジスタ割り当てなど、多くのコンパイラ最適化がSSA形式上でより効率的かつ正確に適用できます。
*   **コンパイラの構造化**: コンパイラのフロントエンド（構文解析、意味解析）とバックエンド（コード生成、最適化）の間の明確なインターフェースを提供し、コンパイラのモジュール性を高めます。

### 2. GoのコンパイラバックエンドとSSA

Goの初期のコンパイラは、ASTを直接操作してアセンブリコードを生成する「gc (Go compiler)」と呼ばれるバックエンドを使用していました。これはシンプルで高速なコンパイルを可能にしましたが、高度な最適化には限界がありました。SSAの導入は、このバックエンドをより現代的な構造に移行させ、将来的な最適化の余地を大きく広げるための重要なステップです。SSAベースのバックエンドでは、ASTからSSA IRを構築し、そのIRに対して様々な最適化パスを適用した後、最終的にターゲットアーキテクチャのアセンブリコードを生成します。

### 3. CGOとポインタ安全性、ライトバリア

*   **CGO**: GoプログラムからC言語の関数を呼び出したり、C言語のデータ構造を扱ったりするためのGoの機能です。これにより、既存のCライブラリをGoから利用したり、パフォーマンスが重要な部分をCで記述したりすることが可能になります。
*   **ポインタ安全性**: Goはガベージコレクション (GC) を備えており、メモリ管理を自動化します。しかし、C言語は手動でのメモリ管理が基本です。CGOを通じてGoのポインタをCコードに渡す場合、Cコードがそのポインタを保持し続けると、GoのGCがそのポインタを追跡できなくなり、参照されているGoオブジェクトが誤って回収されてしまう「ダングリングポインタ」の問題が発生する可能性があります。Goランタイムは、このような危険なポインタの受け渡しを検出するために厳格なルールとチェックを設けています。
*   **ライトバリア (Write Barrier)**: ガベージコレクタが正確に動作するために使用される技術です。GCが実行されている間、プログラムがヒープ上のポインタを書き換える際に、GCがその変更を認識できるように特別な処理（バリア）を挿入します。これにより、GCがオブジェクトグラフを正確にスキャンし、到達可能なオブジェクトを誤って回収しないようにします。CGOとGoポインタの相互作用において、CのメモリにGoポインタが書き込まれる場合、このライトバリアが正しく機能しないと、GCの安全性が損なわれる可能性があります。

### 4. MIPS64/MIPS64LEアーキテクチャ

MIPS (Microprocessor without Interlocked Pipeline Stages) は、RISC (Reduced Instruction Set Computer) アーキテクチャの一種です。MIPS64は64ビット版のMIPSアーキテクチャを指し、MIPS64LEはそのリトルエンディアン版です。これらのアーキテクチャは、特に組み込みシステム、ルーター、ネットワーク機器、スーパーコンピュータなどで広く採用されています。Go言語がMIPS64をサポートすることは、これらの分野でのGoの利用を促進します。

### 5. 楕円曲線暗号 (P256)

楕円曲線暗号 (ECC) は、公開鍵暗号方式の一種で、RSAなどの他の公開鍵暗号方式と比較して、同等のセキュリティレベルをより短い鍵長で実現できるため、効率的です。P256は、NIST (National Institute of Standards and Technology) が推奨する特定の楕円曲線の一つで、TLS (Transport Layer Security) やデジタル署名などで広く利用されています。暗号演算は計算コストが高いため、アセンブリ言語による最適化は、アプリケーション全体のパフォーマンス向上に大きく貢献します。

## 技術的詳細

### 1. SSA (Static Single Assignment) フォームの導入 (`src/cmd/compile/internal/gc/ssa.go`)

このコミットの最も重要な変更点の一つは、GoコンパイラにSSAフォームを導入するための基盤が `src/cmd/compile/internal/gc/ssa.go` として追加されたことです。このファイルは、AST (Abstract Syntax Tree) からSSA形式の中間表現 (IR) を構築するためのロジックを含んでいます。

*   **`buildssa` 関数**: Go関数のASTを受け取り、SSA形式の関数 (`ssa.Func`) を構築するエントリポイントです。この関数は、環境変数 `GOSSAFUNC` や `GOSSAHASH` を利用して、特定の関数のみをSSAでコンパイルしたり、デバッグ情報を出力したりする機能も持っています。
*   **`state` 構造体**: SSA構築プロセス全体の状態を管理します。これには、SSAコンフィグレーション (`ssa.Config`)、現在構築中のSSA関数 (`ssa.Func`)、ラベル情報、変数割り当て (`vars` マップ)、スタックポインタ (`sp`)、グローバルポインタ (`sb`)、メモリ状態 (`startmem`) などが含まれます。
*   **ASTからSSAへの変換**: `stmtList` および `stmt` 関数を通じて、GoのASTノード（例: `OAS` (代入), `OIF` (if文), `ORETURN` (return文), `OGOTO` (goto文) など）を対応するSSA命令やブロックに変換します。
*   **変数管理**: `vars` マップは、現在のブロックにおける各Go変数の最新のSSA値 (`ssa.Value`) を追跡します。これにより、変数の定義と使用の関係がSSAの原則に従って管理されます。
*   **制御フローの変換**: `OIF`, `OGOTO`, `OLABEL` などの制御フローノードは、SSAのブロック (`ssa.Block`) とエッジ (`AddEdgeTo`) に変換されます。`ssaLabel` 構造体は、GoのラベルとSSAブロック間のマッピングを管理し、`goto` 文や `break`/`continue` 文の解決を助けます。
*   **デバッグと検証**: `GOSSAFUNC` や `GOSSAHASH` といった環境変数は、SSAバックエンドのデバッグとテストを支援するために導入されました。これにより、開発者は特定の関数に対してのみSSAを有効にし、生成されたSSA IRをHTML形式で可視化することができます。

このSSAバックエンドは、Go 1.6で実験的に導入され、その後のバージョンで徐々に成熟し、Goコンパイラのデフォルトのバックエンドとなりました。

### 2. MIPS64/MIPS64LEアーキテクチャのサポート

このコミットでは、Go言語がMIPS64およびMIPS64LEアーキテクチャを公式にサポートするための広範な変更が含まれています。これには、アセンブラ、コンパイラ、リンカ、ランタイム、システムコール層にわたる多数のファイルが影響を受けています。

*   **アセンブラ (`src/cmd/asm/internal/arch/mips64.go`, `src/cmd/asm/internal/asm/testdata/mips64.s`)**: MIPS64命令セットを理解し、アセンブリコードをオブジェクトファイルに変換するためのロジックが追加されました。`testdata/mips64.s` はMIPS64アセンブリのテストケースを含んでいます。
*   **コンパイラ (`src/cmd/compile/internal/mips64/`)**: MIPS64アーキテクチャ固有のコード生成ロジックが追加されました。これには、レジスタ割り当て、命令選択、関数呼び出し規約、スタックフレーム管理などが含まれます。`cgen.go`, `galign.go`, `ggen.go`, `gsubr.go`, `peep.go`, `prog.go`, `reg.go` など、MIPS64固有のバックエンドファイルが多数追加・変更されています。
*   **リンカ (`src/cmd/link/internal/mips64/`)**: MIPS64オブジェクトファイルをリンクし、実行可能ファイルを生成するためのロジックが追加されました。これには、MIPS64固有のリロケーション処理、セクション配置、ELFフォーマットのサポートなどが含まれます。
*   **ランタイム (`src/runtime/asm_mips64x.s`, `src/runtime/defs_linux_mips64x.go`, `src/runtime/signal_linux_mips64x.go`, `src/runtime/sys_linux_mips64x.s` など)**: MIPS64アーキテクチャ上でGoランタイムが動作するために必要な低レベルなアセンブリコード、システムコール定義、シグナルハンドリング、メモリ管理、アトミック操作などが実装されました。`mips64x` はMIPS64とMIPS64LEの両方を指すことが多いです。
*   **システムコール (`src/syscall/syscall_linux_mips64x.go`, `src/syscall/zerrors_linux_mips64.go`, `src/syscall/zsyscall_linux_mips64.go`, `src/syscall/zsysnum_linux_mips64.go`, `src/syscall/ztypes_linux_mips64.go` など)**: Linux上のMIPS64システムコールをGoから呼び出すためのバインディングと定義が追加されました。これらは通常、`go generate` コマンドによって自動生成されるファイル群です。

これらの変更により、GoプログラムをMIPS64ベースのシステムでネイティブにコンパイル・実行できるようになります。

### 3. CGOポインタチェックの強化とライトバリアの課題 (`misc/cgo/errors/ptr.go`)

`misc/cgo/errors/ptr.go` ファイルは、CGOにおけるポインタの安全性をテストするためのスイートです。このコミットでは、特に「barrier」という名前のテストケース群がコメントアウトされています。

```go
// TODO(khr): reenable when write barriers are fixed.
```

このコメントは、GoポインタをCのメモリに格納する際のライトバリアの動作に問題があり、その問題が解決されるまでこれらのテストを無効化していることを明確に示しています。コメントアウトされたテストケースは、以下のようなシナリオをカバーしています。

*   GoポインタをCの `malloc` で確保したメモリに格納する。
*   Goポインタを含む大きなC構造体をCのメモリに代入する。
*   Goポインタを含むスライスをCのメモリにコピーする。
*   GCプログラム (GC prog) を使用する非常に大きな配列や構造体への代入。

これらのテストは、GoのGCがCのメモリに格納されたGoポインタを正しく追跡し、ライトバリアが適切に機能するかどうかを検証することを目的としています。コメントアウトされていることから、当時のGoランタイムのライトバリア実装が、CGOとの複雑な相互作用においてまだ完全ではなかったことが伺えます。これは、GoのGCの正確性とCGOの柔軟性のバランスを取る上での重要な課題でした。

この再編成は、ランタイム内部のアトミック操作のコードをよりモジュール化し、異なるアーキテクチャやOSに対する実装を整理することを目的としています。これにより、コードの保守性が向上し、新しいプラットフォームへの移植が容易になります。

### 5. P256楕円曲線演算のAMD64アセンブリ最適化 (`src/crypto/elliptic/p256_asm_amd64.s`)

`src/crypto/elliptic/p256_asm_amd64.s` ファイルは、AMD64アーキテクチャ向けにP256楕円曲線演算をアセンブリ言語で実装したものです。2000行を超える大量のコードが追加されており、これは非常に低レベルな最適化が行われたことを示しています。

*   **目的**: P256曲線上の点加算、点乗算、スカラー乗算などの基本的な演算は、暗号プロトコルにおいて頻繁に実行されます。これらの演算は計算コストが高いため、Go言語のコンパイラが生成するコードよりもさらに高速な実行を可能にするために、手書きのアセンブリコードが導入されました。
*   **性能向上**: アセンブリ最適化は、CPUの特定の命令セット（例: SIMD命令、特定のレジスタ利用パターン）を最大限に活用し、キャッシュ効率を最適化することで、Goコードでは達成できないレベルの性能向上を実現します。これにより、TLSハンドシェイクやデジタル署名検証などの暗号処理が大幅に高速化され、Goアプリケーション全体の応答性とスループットが向上します。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の解説

このファイルは、GoコンパイラのSSAバックエンドの心臓部です。`buildssa` 関数は、Goのソースコードから生成されたASTを、SSA形式のグラフ構造に変換します。この変換プロセスでは、各変数の定義が単一になるように新しいSSA値が導入され、制御フローはSSAブロックとエッジで表現されます。

例えば、Goの `if` 文は、SSAでは条件分岐ブロックと、その条件が真の場合のブロック、偽の場合のブロック、そして両方のパスが合流するブロックに変換されます。変数への代入は `ssa.Value` オブジェクトとして表現され、メモリ操作も `ssa.OpInitMem`, `ssa.OpLoad`, `ssa.OpStore` などのSSA命令として扱われます。

`state` 構造体内の `vars` マップは、現在のスコープにおける各Go変数の最新のSSA値を保持し、`defvars` は各ブロックの終点での変数定義の状態を記録します。これにより、`φ` 関数が挿入されるべき場所や、変数のライブネス解析が容易になります。

このSSA IRが構築された後、`ssa.Compile(s.f)` が呼び出され、SSAパッケージ内の様々な最適化パスが適用され、最終的にターゲットアーキテクチャのアセンブリコードが生成されます。このファイルは、Goコンパイラがより高度な最適化を実行するための基盤を提供し、Go言語の実行時性能を向上させる上で極めて重要な役割を担っています。

### `misc/cgo/errors/ptr.go` のコメントアウトされたテストの解説

コメントアウトされた「barrier」テスト群は、CGOとGoのガベージコレクタのライトバリアとの間の複雑な相互作用を浮き彫りにします。これらのテストは、GoのポインタがCのメモリ領域に書き込まれる際に、GoのGCがそのポインタを正しく追跡できるかどうかを検証しようとしていました。

例えば、`barrier` テストは、Cの `malloc` で確保された `char**` にGoの `*C.char` (Goヒープ上のオブジェクトへのポインタ) を代入するシナリオをテストしています。GoのGCは、Goヒープ上のポインタの変更をライトバリアを通じて監視し、オブジェクトグラフを更新します。しかし、CのメモリはGCの直接の管理下にないため、CのメモリへのGoポインタの書き込みがGCに正しく通知されないと、GCがそのGoオブジェクトへの参照を見失い、誤って回収してしまう可能性があります。

`TODO(khr): reenable when write barriers are fixed.` というコメントは、当時のライトバリアの実装が、CGOを介したGoポインタのCメモリへの書き込みというエッジケースを完全にカバーできていなかったことを示しています。この問題は、GoのGCの正確性とCGOの柔軟性を両立させる上で重要な課題であり、その後のGoバージョンで解決されていきました。

### `src/cmd/compile/internal/gc/racewalk.go` のレース検出器の変更解説

`racewalk.go` は、Goのデータ競合検出器 (Race Detector) がプログラムをインストゥルメント（計測コードを挿入）する際のロジックを定義しています。このコミットでは、インストゥルメンテーションの対象から除外されるパッケージ (`omit_pkgs`) や、限定的なインストゥルメンテーションが適用されるパッケージ (`norace_inst_pkgs`) が更新されました。

*   `runtime/internal/atomic`, `runtime/internal/sys`, `runtime/msan` が `omit_pkgs` に追加されたのは、これらのパッケージがGoランタイムの非常に低レベルな部分であり、アトミック操作やシステムコール、メモリサニタイザ関連のコードを含んでいるためです。これらのコードは、それ自体がデータ競合を避けるように慎重に設計されており、レース検出器による追加のインストゥルメンテーションは、パフォーマンスのオーバーヘッドが大きいだけでなく、誤検知を引き起こしたり、検出器自身の動作に影響を与えたりする可能性があります。特に、アトミック操作はメモリバリアを伴うため、レース検出器のロジックと衝突する可能性があります。
*   `sync/atomic` が `norace_inst_pkgs` に移動したことは、このパッケージ内の関数に対しては、関数エントリー/エグジット時の `racefuncenterfp`/`racefuncexit` の呼び出しのみを挿入し、個々のメモリアクセスに対する詳細なインストゥルメンテーションは行わないことを意味します。`sync/atomic` パッケージは、Goのユーザーコードがアトミック操作を行うための標準的な方法であり、その内部実装はすでに競合フリーであることが保証されています。したがって、過度なインストゥルメンテーションは不要であり、パフォーマンスを考慮して限定的なチェックに留められています。

これらの変更は、レース検出器の正確性と実用性を向上させるための調整であり、Goランタイムの内部構造とレース検出器の相互作用に関する深い理解に基づいています。

# [インデックス 26296] ファイルの概要

このコミットは、Go言語の`net`パッケージにおけるドメイン名解決の挙動を改善するものです。具体的には、不正な形式のドメイン名が指定された際に、Go言語ネイティブのリゾルバ（`netgo`）とCgoベースのリゾルバ（`netcgo`）のどちらが使用されているかに関わらず、一貫したエラー（`"invalid domain name"`という`DNSError`）を報告するように修正しています。これにより、リゾルバの実装に依存しない、予測可能なエラーハンドリングが保証されます。

## 元コミット内容

このコミットは、Goの`net`パッケージが提供するドメイン名解決関数（`LookupHost`, `LookupIP`, `LookupCNAME`, `LookupSRV`, `LookupMX`, `LookupNS`, `LookupTXT`など）において、不正な形式のドメイン名が入力された場合に、GoネイティブのリゾルバとCgoリゾルバの間でエラーの挙動が異なっていた問題を解決します。以前は、使用されるリゾルバによって異なるエラーが返される可能性があり、アプリケーション側での一貫したエラーハンドリングが困難でした。この変更により、`"invalid domain name"`という統一されたエラーが返されるようになります。

## 変更の背景

Go言語の`net`パッケージは、DNSルックアップを行う際に、Go言語で実装されたネイティブなリゾルバと、C言語の標準ライブラリ（通常は`glibc`の`getaddrinfo`など）をCgo経由で呼び出すリゾルバの2種類を使用できます。どちらのリゾルバが使用されるかは、ビルド時のタグ（`netgo`など）や実行環境によって決定されます。

問題は、これらのリゾルバが不正なドメイン名の検証ロジックを異なる方法で処理していた点にありました。例えば、`!!!.local`のような明らかに不正なドメイン名が入力された場合、一方のリゾルバは「無効なドメイン名」としてエラーを返すかもしれませんが、もう一方はDNSクエリを試行し、結果として「ホストが見つからない」といった異なるエラーを返す可能性がありました。

この不整合は、アプリケーション開発者にとって問題となります。なぜなら、同じ入力に対して環境によって異なるエラーが返されるため、エラー処理のロジックを複雑にするか、あるいは予期せぬ挙動を引き起こす可能性があったからです。`Fixes #12421`という記述から、この問題はGitHubのIssue 12421で報告され、議論されていたことがわかります。Issue 12421は、`IsDomainName`関数のドメイン名形式に関する制限、特に「hostname-compatible 'preferred name' LDH labels and SRV-like 'underscore labels'」の扱いに関連するものでした。このコミットは、この根本的な問題に対処し、エラー報告の一貫性を確保することを目的としています。

## 前提知識の解説

*   **DNS (Domain Name System)**: インターネット上のドメイン名をIPアドレスに変換するシステムです。
*   **ドメイン名**: ウェブサイトやメールアドレスなどで使用される、人間が読みやすい形式のアドレス（例: `example.com`）。
*   **Go言語の`net`パッケージ**: ネットワーク関連の機能を提供するGoの標準ライブラリです。DNSルックアップ機能も含まれます。
*   **Goネイティブリゾルバ (`netgo`)**: Go言語で完全に実装されたDNSリゾルバです。Cgoを使用しないため、クロスコンパイルや静的リンクが容易です。
*   **Cgoベースリゾルバ (`netcgo`)**: C言語の標準ライブラリ（例: Linuxの`glibc`）のDNS解決機能を利用するリゾルバです。Cgoを介してCの関数を呼び出します。システムの設定（`/etc/resolv.conf`など）に強く依存します。
*   **`DNSError`**: `net`パッケージでDNS関連のエラーが発生した際に返されるエラー型です。`Err`フィールドにエラーメッセージ、`Name`フィールドにクエリ対象のドメイン名が含まれます。
*   **`isDomainName`関数**: ドメイン名として有効な文字列であるかをチェックする内部関数です。このコミット以前は、この関数のチェックが`netgo`と`netcgo`のパスで一貫して適用されていなかった可能性があります。

## 技術的詳細

このコミットの主要な技術的アプローチは、DNSルックアップ関数が実際にDNSクエリを発行する前に、入力されたドメイン名が基本的な構文規則に準拠しているかを`isDomainName`関数で事前にチェックすることです。

以前は、`LookupHost`や`LookupIP`などの関数は、入力がIPアドレス形式でない場合に直接`lookupHost`や`lookupIPMerge`といった内部のルックアップロジックを呼び出していました。この内部ロジックは、Goネイティブの実装とCgoの実装で、不正なドメイン名に対する挙動が異なっていました。

今回の変更では、これらのルックアップ関数の冒頭に`if !isDomainName(host) { ... }`というチェックが追加されました。
`isDomainName`関数は、RFC 1035やRFC 1123などのDNSおよびホスト名の命名規則に基づいて、文字列が有効なドメイン名であるかを判断します。例えば、ドメイン名には許容される文字（英数字、ハイフン）、長さの制限、ラベルの形式などの規則があります。`!!!.local`のような文字列はこれらの規則に違反するため、`isDomainName`は`false`を返します。

`isDomainName`が`false`を返した場合、ルックアップ関数は即座に`&DNSError{Err: "invalid domain name", Name: host}`というエラーを返します。これにより、実際のDNSクエリが発行される前に不正な入力が捕捉され、GoネイティブとCgoのどちらのリゾルバが使用されているかに関わらず、常に同じエラーが返されるようになります。

この変更は、`net`パッケージの複数のルックアップ関数に適用されています。

*   `LookupHost`
*   `LookupIP`
*   `LookupCNAME`
*   `LookupSRV`
*   `LookupMX`
*   `LookupNS`
*   `LookupTXT`

また、`src/net/ip_test.go`に`TestLookupBadName`という新しいテストケースが追加され、`netgo`モードと`netcgo`モードの両方で、不正なドメイン名（`!!!.local`）に対してすべての上記ルックアップ関数が一貫して`DNSError`型で`"invalid domain name"`というエラーを返すことを検証しています。

## コアとなるコードの解説

`src/net/lookup.go`における変更は非常に直接的です。各ルックアップ関数の先頭に、以下のパターンが追加されています。

```go
if !isDomainName(host) {
    return nil, &DNSError{Err: "invalid domain name", Name: host}
}
```

または、戻り値の型に合わせて`nil`の代わりに適切なゼロ値が使用されます。

*   `isDomainName(host)`: この関数は、入力された`host`文字列が有効なドメイン名の形式に従っているかをチェックします。例えば、`!!!.local`のような特殊文字を含む文字列や、長さの制限を超える文字列などは無効と判断されます。
*   `!isDomainName(host)`: `host`が無効なドメイン名である場合に`true`となります。
*   `return nil, &DNSError{Err: "invalid domain name", Name: host}`: 無効なドメイン名が検出された場合、関数は即座に処理を中断し、`nil`（または適切なゼロ値）と、`Err`フィールドに`"invalid domain name"`、`Name`フィールドに元の不正なドメイン名を含む`DNSError`を返します。

この変更により、GoネイティブのリゾルバとCgoリゾルバのどちらが使用されても、不正なドメイン名に対しては常に同じエラーが返されることが保証されます。これにより、`net`パッケージのAPIを使用する開発者は、DNSルックアップのエラーハンドリングをよりシンプルかつ一貫性のあるものにできます。

`src/net/ip_test.go`に追加された`TestLookupBadName`テストは、この挙動を検証するためのものです。
`forceGoDNS`と`forceCgoDNS`という内部関数（テストでのみ利用可能）を使って、GoリゾルバとCgoリゾルバを強制的に切り替えながら、`!!!.local`という不正なドメイン名に対してすべての`Lookup`関数を呼び出しています。
`check`関数は、返されたエラーが`*DNSError`型であり、かつ`Err`フィールドが`"invalid domain name"`であることを確認します。これにより、両方のリゾルバパスで期待される一貫したエラーが返されることが保証されます。

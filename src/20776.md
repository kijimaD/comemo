# [インデックス 20776] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクタ（GC）とスタック縮小処理の間の競合状態を解決するためのものです。具体的には、スタックが縮小された際に解放されるメモリの実際の解放タイミングをGCの完了後まで遅延させることで、GCが不正なポインタを検出する問題を回避します。

変更されたファイルは以下の通りです。

-   `src/runtime/mgc0.c`: GCのメイン処理に関連するファイル。
-   `src/runtime/runtime.h`: ランタイムの共通ヘッダファイル。
-   `src/runtime/stack.c`: スタック管理に関連するファイル。

## 元コミット内容

このコミットは、Goランタイムにおいて、縮小されたスタックの解放をガベージコレクション（GC）が完了するまで遅延させる変更です。

この変更は、ガベージコレクタの混乱を防ぐことを目的としています。コレクタは、見つけたすべてのポインタが「ジャンク」（無効なメモリ領域を指すポインタ）ではないことを確認しようとします。ジャンクと判断される基準の一つに、「解放済み（free）のspan」を指すポインタがあります。

スタック縮小処理がヒープ内のポインタを変更するため、GCスキャナとスタック縮小処理の間に競合状態が発生していました。GCスキャナは、解放されたスタックを指す古いポインタ、特に`SudoG.elem`ポインタを検出することがありました。

通常、スタックのspanを指すポインタは問題ありません。しかし、解放されたスタックがそのspan内の最後のスタックであった場合、そのspanは「スタックを含む（contains stacks）」ではなく「解放済み（free）」としてマークされてしまいます。

この変更により、GCスキャナが古いポインタを検出したとしても、そのポインタが指すspanが依然として「スタックを含む」としてマークされていることを保証し、GCがエラーを報告しないようにします。

この変更は、スタックの解放がマークフェーズと直列に行われるため、GCの一時停止時間をわずかに長くする可能性があります。ミューテータ（ユーザープログラム）が再開するまで解放を遅らせることも可能ですが、現時点ではこれが最もシンプルな変更です。

## 変更の背景

Goランタイムでは、ゴルーチンのスタックは必要に応じて動的に拡大・縮小されます。スタックが縮小される際、元の大きなスタック領域は解放され、システムに返却されることになります。しかし、この解放処理とガベージコレクタ（GC）の動作の間に特定の競合状態が存在していました。

問題は、GCがメモリをスキャンして到達可能なオブジェクトを特定する際に発生します。GCは、ポインタが有効なメモリ領域を指していることを確認します。もしポインタが既に解放されたメモリ領域、特に「free」とマークされたメモリspanを指している場合、GCはそのポインタを「ジャンク」と判断し、エラーやクラッシュの原因となる可能性があります。

スタック縮小処理は、古いスタック領域を解放する際に、ヒープ内のポインタ（例えば、`SudoG.elem`のような内部的なポインタ）を更新する可能性があります。この更新がGCのスキャンと同時に行われると、GCスキャナがまだ古いスタック領域を指しているポインタを読み取ってしまう可能性がありました。

さらに深刻なのは、解放されたスタックが、そのスタックが割り当てられていたメモリspan（Goのメモリ管理単位）内の最後のスタックであった場合です。この場合、そのspan全体が「free」としてマークされてしまいます。GCが古いポインタをスキャンし、それが「free」とマークされたspanを指していると判断すると、GCは混乱し、誤ったエラーを報告したり、最悪の場合、メモリ破壊を引き起こす可能性がありました。

このコミットは、このようなGCの混乱を防ぎ、ランタイムの安定性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

### Goのガベージコレクタ（GC）

GoのGCは、並行マーク＆スイープ方式を採用しています。
-   **マークフェーズ (Mark Phase)**: プログラムの実行を一時停止（ストップ・ザ・ワールド、STW）し、ルート（グローバル変数、スタック上の変数など）から到達可能なオブジェクトをマークします。その後、プログラムの実行を再開し、バックグラウンドでマーク処理を続行します。
-   **スキャン (Scan)**: マークフェーズ中に、GCはヒープ上のオブジェクトやスタックをスキャンし、そこに含まれるポインタをたどって到達可能なオブジェクトをマークします。
-   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不可能なオブジェクト）が占めていたメモリ領域を解放し、再利用可能にします。

GCは、ポインタが有効なメモリ領域を指していることを厳密にチェックします。無効なポインタ（ジャンクポインタ）を検出すると、ランタイムエラーを引き起こす可能性があります。

### Goのメモリ管理とSpan

Goのランタイムは、メモリを`mspan`と呼ばれる単位で管理しています。`mspan`は、連続したページ（通常は8KB）のブロックです。
-   **Spanの種類**: `mspan`は、その中にどのようなオブジェクトが格納されているかに応じて異なる種類があります。例えば、小さなオブジェクト用のspan、大きなオブジェクト用のspan、そしてスタック用のspanなどです。
-   **Spanの状態**: `mspan`は、その状態を示すフラグを持っています。例えば、`_MSpanFree`（完全に解放済み）、`_MSpanStack`（スタックを含む）、`_MSpanInUse`（ヒープオブジェクトを含む）などです。
-   GCは、ポインタが指すメモリがどの`mspan`に属しているか、そしてその`mspan`がどのような状態であるかをチェックします。ポインタが`_MSpanFree`のspanを指している場合、それは不正なポインタと見なされます。

### Goのスタック管理とスタック縮小

Goのゴルーチンは、可変サイズのスタックを持っています。
-   **スタックの拡大**: ゴルーチンがより多くのスタック領域を必要とする場合、ランタイムは新しいより大きなスタックを割り当て、古いスタックの内容を新しいスタックにコピーし、古いスタックを解放します。
-   **スタックの縮小**: ゴルーチンが以前よりも少ないスタック領域しか使用していない場合、ランタイムはスタックを縮小してメモリ使用量を最適化しようとします。この際も、新しいより小さなスタックを割り当て、内容をコピーし、古いスタックを解放します。

### `SudoG.elem`

`SudoG`は、Goランタイムの内部構造体で、GCがスタックをスキャンする際に使用されるゴルーチンの擬似的な表現です。`SudoG.elem`は、特定のゴルーチンに関連するポインタを指すフィールドであり、GCがこのポインタをたどって到達可能なオブジェクトをマークする必要があります。このポインタが、縮小されたスタックの古い領域を指し続けることが問題の核心でした。

## 技術的詳細

このコミットが解決しようとしている技術的な問題は、Goのガベージコレクタ（GC）がスタック縮小によって解放されたメモリ領域を誤って「ジャンク」と判断してしまう競合状態です。

1.  **競合状態の発生**:
    *   GCがマークフェーズに入り、スタックやヒープをスキャンしてポインタをたどっている最中。
    *   同時に、あるゴルーチンのスタックが縮小され、古いスタック領域が解放される。
    *   GCスキャナが、まだ古いスタック領域を指しているポインタ（特に`SudoG.elem`のような内部ポインタ）を読み取ってしまう。

2.  **Spanの状態変更による問題**:
    *   Goのメモリ管理では、メモリは`mspan`という単位で管理され、それぞれの`mspan`は自身の状態（例: スタックを含む、解放済みなど）を保持しています。
    *   もし、縮小によって解放されたスタックが、その`mspan`内の最後のスタックであった場合、その`mspan`は「スタックを含む」状態から「解放済み（free）」状態に変わってしまいます。
    *   GCスキャナが古いポインタをたどり、それが「解放済み」とマークされた`mspan`を指していると判断すると、GCはそれを不正なポインタ（ジャンク）と見なし、ランタイムエラーを引き起こす可能性があります。

3.  **解決策**:
    *   このコミットの解決策は、スタックが縮小された際に、古いスタック領域を**即座に解放せず**、GCが完了するまでその解放を**遅延させる**ことです。
    *   具体的には、縮小されたスタックは一時的なキュー（`stackfreequeue`）に入れられます。
    *   GCのマークフェーズが完了した後、`runtime·shrinkfinish()`関数が呼び出され、このキューに溜められたスタックが実際に解放されます。
    *   これにより、GCがスキャンしている間は、たとえ古いポインタを検出したとしても、そのポインタが指す`mspan`はまだ「スタックを含む」状態のままであり、「解放済み」としてマークされることがないため、GCが混乱することなく処理を続行できます。

4.  **性能への影響**:
    *   コミットメッセージにもあるように、この変更により、スタックの実際の解放処理がGCのマークフェーズと直列に行われるため、GCの一時停止時間（STW時間）がわずかに増加する可能性があります。
    *   しかし、これはGCの正確性と安定性を保証するためのトレードオフであり、現時点では最もシンプルで効果的な解決策とされています。将来的には、ミューテータが再開した後に解放処理を行うなど、さらなる最適化の可能性も示唆されています。

## コアとなるコードの解説

このコミットの核心は、スタックの解放タイミングをGCの完了後まで遅らせるメカニズムを導入することです。

1.  **`stackfreequeue`の導入 (`src/runtime/stack.c`)**:
    *   `static Stack stackfreequeue;` は、縮小されたがまだ解放されていないスタックを一時的に保持するためのキューのヘッドとして機能します。`Stack`構造体はスタックの開始アドレスと終了アドレスを保持します。このキューは、スタックの開始アドレスを次のキュー要素へのポインタとして利用する、単方向リンクリストとして実装されています。

2.  **`copystack`の変更 (`src/runtime/stack.c`)**:
    *   `copystack`関数は、ゴルーチンのスタックを新しい領域にコピーする際に呼び出されます。スタックが拡大される場合（`newsize > old.hi-old.lo`）、古いスタックはこれまで通り`runtime·stackfree(old)`によって即座に解放されます。
    *   しかし、スタックが縮小される場合（`newsize <= old.hi-old.lo`）、古いスタックは即座に解放されません。代わりに、以下の処理が行われます。
        *   `runtime·lock(&runtime·stackpoolmu);` と `runtime·unlock(&runtime·stackpoolmu);` でミューテックスをロックし、`stackfreequeue`へのアクセスを保護します。
        *   `*(Stack*)old.lo = stackfreequeue;` は、古いスタックの開始アドレス（`old.lo`）を、キューの現在のヘッド（`stackfreequeue`）を指すように設定します。これにより、古いスタック自体がリンクリストのノードとして機能します。
        *   `stackfreequeue = old;` は、新しいキューのヘッドを現在の古いスタックに設定します。
        *   このメカニズムにより、古いスタックは`stackfreequeue`というリンクリストに「キューイング」され、実際の解放は後回しにされます。

3.  **`runtime·shrinkfinish`関数の実装 (`src/runtime/stack.c`)**:
    *   この新しい関数は、`stackfreequeue`にキューイングされたすべてのスタックを実際に解放する責任を負います。
    *   関数が呼び出されると、まず`stackfreequeue`をロックし、キューのヘッドを一時変数`s`にコピーした後、`stackfreequeue`を空にします。これにより、GC中にこの関数が複数回呼び出されても、同じスタックが二重に解放されることを防ぎます。
    *   その後、`while(s.lo != 0)`ループを使って、キュー内のすべてのスタックを順に処理します。
    *   `t = *(Stack*)s.lo;` で次のスタックへのポインタを取得し、`runtime·stackfree(s);` で現在のスタック`s`を実際に解放します。
    *   最後に`s = t;` で次のスタックに進みます。

4.  **`gc`関数からの呼び出し (`src/runtime/mgc0.c`)**:
    *   `gc`関数の最後に`runtime·shrinkfinish()`が追加されたことが最も重要な変更点です。これは、GCのマークフェーズが完全に終了し、すべてのポインタスキャンが完了した後に、遅延されていたスタックの解放処理が実行されることを保証します。
    *   これにより、GCがスキャン中に古いスタック領域を指すポインタを検出しても、その領域がまだ「スタックを含む」状態の`mspan`に属しているため、GCは混乱することなく、ポインタを有効なものとして処理できます。GCが完了した後に初めて、これらのスタック領域が解放され、対応する`mspan`が「free」としてマークされるため、競合状態が解消されます。

この一連の変更により、GCの正確性が保たれ、スタック縮小とGCの並行動作による潜在的なメモリ破損やランタイムエラーが回避されます。

# [インデックス 25103] ファイルの概要

このコミットは、Goリンカー (`cmd/link/internal/ld`) 内のコードベースから `stringsCompare` 関数の使用を削減することを目的としています。特に、`macho.go` と `pe.go` ファイル内のソートロジックにおいて、カスタムの文字列比較関数ではなく、Go言語の組み込みの文字列比較演算子 (`<`) を直接使用するように変更されています。これにより、コードの簡素化と、潜在的なパフォーマンス向上が期待されます。

`stringsCompare` の使用は1箇所のみ残されています。これは、ブートストラップの理由により、単純に `strings.Compare` に置き換えることができないためと思われます。
この関数を `util.go` から実際の宛先である `data.go` に移動しても、あまり役立たないでしょう。そのため、可読性と利便性のために、この1箇所は変更せずに残しました。

## 変更の背景

Go言語のリンカー (`cmd/link/internal/ld`) は、実行可能ファイルを生成する際に、シンボルやセクションなどの様々な要素を処理します。これらの要素はしばしばソートされる必要があり、その際に文字列の比較が頻繁に行われます。以前は、カスタムの `stringsCompare` 関数がこれらの比較に使用されていました。

このコミットの背景には、以下の点が考えられます。

1.  **コードの簡素化と標準化**: Go言語には組み込みの文字列比較演算子 (`<`, `>`, `==` など) があり、これらは文字列を辞書順に比較します。カスタム関数を使用する代わりに、これらの標準的な演算子を使用することで、コードの可読性が向上し、Go言語のイディオムに沿った記述になります。
2.  **パフォーマンスの最適化**: カスタム関数呼び出しのオーバーヘッドを排除し、コンパイラがより効率的なコードを生成できる可能性があります。Goの組み込み文字列比較は、多くの場合、高度に最適化されています。
3.  **保守性の向上**: カスタムの比較関数が減ることで、コードベース全体の複雑性が低下し、将来的な保守が容易になります。

コミットメッセージにある「Only one use of stringsCompare is left. Cannot simply be replaced by strings.Compare for bootstrapping reasons I guess.」という記述は、Goコンパイラやリンカーの自己ホスト型（ブートストラップ）の性質に起因する制約を示唆しています。GoのツールチェインはGo自身で書かれているため、非常に初期の段階では、まだ完全に機能する標準ライブラリが利用できない場合があります。そのため、一部の低レベルな処理では、標準ライブラリの関数に依存できない独自のヘルパー関数が必要となることがあります。このコミットでは、そのような制約がない箇所から `stringsCompare` を排除し、残りの1箇所はブートストラップの都合上、変更が困難であると判断されたようです。

## 前提知識の解説

### Go言語のリンカー (`cmd/link`)

Go言語のコンパイルプロセスは、ソースコードをオブジェクトファイルに変換し、その後、リンカーがこれらのオブジェクトファイルと必要なライブラリを結合して最終的な実行可能ファイルを生成します。`cmd/link` はこのリンカーの実装であり、Goのツールチェインの重要な部分です。

### `macho.go` と `pe.go`

*   **`macho.go`**: macOS (OS X) や iOS などのApple製オペレーティングシステムで使用される実行可能ファイル形式であるMach-O (Mach Object) 形式に関連するリンカーの処理を扱います。
*   **`pe.go`**: Windowsオペレーティングシステムで使用される実行可能ファイル形式であるPE (Portable Executable) 形式に関連するリンカーの処理を扱います。

これらのファイルは、それぞれのプラットフォーム固有の実行可能ファイル構造に合わせて、シンボルテーブルの構築、セクションの配置、インポート/エクスポートテーブルの処理などを行います。これらの処理の多くで、シンボル名などの文字列をソートする必要が生じます。

### `sort.Interface` と `sort.Sort`

Go言語の標準ライブラリには、`sort` パッケージがあり、様々なデータ構造をソートするための汎用的なインターフェース `sort.Interface` を提供しています。このインターフェースは以下の3つのメソッドを定義しています。

*   `Len() int`: ソート対象の要素数を返します。
*   `Swap(i, j int)`: インデックス `i` と `j` の要素を入れ替えます。
*   `Less(i, j int) bool`: インデックス `i` の要素がインデックス `j` の要素よりも小さい（ソート順で前に来る）場合に `true` を返します。

`sort.Sort` 関数は、`sort.Interface` を実装する任意の型を受け取り、その要素をソートします。このコミットでは、`Less` メソッドの実装が変更されています。

### 文字列比較

Go言語では、文字列はバイトのシーケンスとして扱われ、辞書順に比較されます。
*   `s1 < s2`: `s1` が `s2` よりも辞書順で前に来る場合に `true`。
*   `s1 == s2`: `s1` と `s2` が等しい場合に `true`。
*   `s1 > s2`: `s1` が `s2` よりも辞書順で後に来る場合に `true`。

以前使用されていた `stringsCompare` 関数は、おそらく `strings.Compare` と同様に、3つの値を返す（-1, 0, 1）ような実装だったと推測されます。`strings.Compare(a, b)` は、`a < b` なら負の値、`a == b` なら0、`a > b` なら正の値を返します。

## 技術的詳細

このコミットの主要な変更点は、Goリンカー内のソートロジックにおいて、カスタムの `stringsCompare` 関数への依存を排除し、Go言語の組み込み文字列比較演算子 (`<`) を直接使用するようにしたことです。

具体的には、以下の2つのファイルで変更が行われています。

1.  **`src/cmd/link/internal/ld/macho.go`**:
    *   `machoscmp` 型の `Less` メソッド内で、シンボルの外部名 (`s1.Extname`, `s2.Extname`) を比較する際に、`stringsCompare(s1.Extname, s2.Extname) < 0` という記述が `s1.Extname < s2.Extname` に変更されました。
    *   また、シンボルの種類 (`k1`, `k2`) を比較する際も、`k1-k2 < 0` という記述が `k1 < k2` に変更されています。これは数値の比較であり、より直接的な表現になっています。

2.  **`src/cmd/link/internal/ld/pe.go`**:
    *   `pescmp` という型が `byExtname` にリネームされました。これは、このソート型がシンボルの外部名 (`Extname`) に基づいてソートを行うことをより明確に示しています。
    *   `pescmp` 型の `Len`, `Swap`, `Less` メソッドが、より簡潔な関数リテラル形式で定義されるようになりました。
    *   最も重要な変更は、`Less` メソッド内で `stringsCompare(s1.Extname, s2.Extname) < 0` が `s[i].Extname < s[j].Extname` に置き換えられた点です。
    *   `initdynexport` 関数内で `sort.Sort` を呼び出す際も、型名が `pescmp` から `byExtname` に変更されています。

これらの変更により、リンカーのソート処理がよりGo言語のイディオムに沿った形になり、カスタム関数のオーバーヘッドが削減されます。

## コアとなるコードの解説

### `macho.go` の変更

`machoscmp` はMach-O形式のシンボルをソートするための `sort.Interface` 実装です。
`Less` メソッドは、2つのシンボル `s1` と `s2` を比較します。

1.  **シンボル種別の比較**:
    *   `k1 := symkind(s1)` と `k2 := symkind(s2)` でシンボルの種類を取得します。
    *   `if k1 != k2 { return k1 < k2 }` の変更は、シンボル種別が異なる場合、数値として小さい方が「小さい」と判断されるようにします。以前の `k1-k2 < 0` と同じ論理ですが、より直接的で読みやすい表現です。

2.  **外部名の比較**:
    *   `return s1.Extname < s2.Extname` の変更は、シンボル種別が同じ場合、シンボルの外部名 (`Extname`) をGoの組み込み文字列比較演算子 (`<`) を使って直接比較するようにします。これにより、カスタムの `stringsCompare` 関数への依存がなくなりました。

### `pe.go` の変更

`pe.go` では、PE形式のシンボルをソートするためのロジックが変更されています。

1.  **型のリネームと簡素化**:
    *   `type pescmp []*LSym` が `type byExtname []*LSym` に変更されました。これは、このソートロジックがシンボルの外部名 (`Extname`) に基づいていることを明確にします。
    *   `Len`, `Swap`, `Less` メソッドの定義が、より簡潔なインライン形式に書き換えられました。これはGoの慣用的な書き方であり、特に短いメソッドの実装でよく見られます。

2.  **外部名の比較**:
    *   `func (s byExtname) Less(i, j int) bool { return s[i].Extname < s[j].Extname }` の変更は、`macho.go` と同様に、シンボルの外部名をGoの組み込み文字列比較演算子 (`<`) を使って直接比較するようにします。これにより、`stringsCompare` の使用がここでも排除されました。

3.  **`initdynexport` 関数内の変更**:
    *   `sort.Sort(pescmp(dexport[:nexport]))` が `sort.Sort(byExtname(dexport[:nexport]))` に変更されました。これは、ソート対象の型名がリネームされたことに伴う修正です。

これらの変更は、Goリンカーの内部で文字列比較を行う際の効率性と可読性を向上させ、Go言語の標準的な機能により密接に統合することを目的としています。

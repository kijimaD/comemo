## 変更の背景
このコミットは、Goランタイムにおける `runtime.Goexit()` と `defer` ステートメントの相互作用の正確性を保証するためのテストを追加します。`runtime.Goexit()` は現在のゴルーチンを終了させる関数ですが、その際に `defer` された関数が確実に実行されることがGoの設計上の重要な保証です。また、`Goexit()` によって `defer` が実行された場合、その `defer` 内で `recover()` を呼び出した際に `nil` が返されるという特定の動作も保証される必要があります。

このテストの追加は、これらの重要なランタイムの挙動が期待通りに機能し、将来の変更によって意図せず破壊されないことを確認するためのものです。特に、リソースのクリーンアップ（ファイルクローズ、ロック解除など）が `Goexit()` によってゴルーチンが終了する場合でも適切に行われることを保証するために、`defer` の実行は不可欠です。

## 前提知識の解説

### ゴルーチン (Goroutine)
Goにおける軽量な実行スレッドです。OSのスレッドよりもはるかに少ないリソースで作成・管理され、数千から数百万のゴルーチンを同時に実行できます。

### `defer` ステートメント
`defer` キーワードは、その `defer` ステートメントを含む関数がリターンする直前に、指定された関数（遅延関数）を実行するようにスケジュールします。遅延関数は、関数の正常終了、`return` ステートメント、`panic`、または `runtime.Goexit()` によって関数が終了する際に実行されます。複数の `defer` ステートメントがある場合、それらはLIFO（後入れ先出し）の順序で実行されます。これは、リソースの解放（ファイルのクローズ、ミューテックスのアンロックなど）によく使用されます。

### `runtime.Goexit()`
`runtime` パッケージに含まれる関数で、これを呼び出したゴルーチンを直ちに終了させます。`os.Exit()` とは異なり、プログラム全体を終了させるのではなく、呼び出し元のゴルーチンのみを終了させます。`Goexit()` が呼び出されると、そのゴルーチン内で `defer` されたすべての関数が実行された後にゴルーチンが終了します。`Goexit()` はパニックではないため、`Goexit()` によって実行された `defer` 関数内で `recover()` を呼び出しても、`nil` が返されます。

### `panic` と `recover()`
`panic` はGoにおけるランタイムエラーのメカニズムで、通常のプログラムフローを中断させます。`panic` が発生すると、現在の関数が直ちに実行を停止し、`defer` された関数が実行され、その後呼び出し元の関数に `panic` が伝播します。
`recover()` は `defer` された関数内でのみ有効な組み込み関数です。`panic` が発生した際に `recover()` を呼び出すと、`panic` の値を取得し、パニック状態を停止して通常の実行フローを再開できます。`panic` が発生していない状況で `recover()` を呼び出すと `nil` が返されます。

## 技術的詳細
このコミットは、`runtime.Goexit()` が `defer` ステートメントとどのように相互作用するかという、Goランタイムの重要な側面を検証します。具体的には以下の2点を保証するためのテストが追加されています。

1.  **`Goexit()` が `defer` を実行すること**: `runtime.Goexit()` が呼び出された場合でも、そのゴルーチン内でスケジュールされたすべての `defer` 関数が確実に実行されることを確認します。これは、リソースリークを防ぎ、プログラムの堅牢性を保つ上で極めて重要です。
2.  **`Goexit` による `defer` 実行中の `recover()` が `nil` を返すこと**: `Goexit()` は `panic` とは異なる終了メカニズムであるため、`Goexit()` によって `defer` 関数が実行された際に、その `defer` 関数内で `recover()` を呼び出しても、`panic` の値は存在しないため `nil` が返されるべきです。この挙動は、`panic` からの回復と `Goexit()` による終了を明確に区別するために重要です。

テストは、新しいゴルーチン内で `runtime.Goexit()` を呼び出し、そのゴルーチン内で `defer` された関数が実行されることをチャネル通信によって検証します。また、`defer` 関数内で `recover()` を呼び出し、その戻り値が `nil` であることをアサートすることで、上記の2番目の保証も確認しています。

## コアとなるコードの解説

追加された `TestGoexitDefer` 関数は以下のロジックで構成されています。

1.  `c := make(chan struct{})`: チャネル `c` を作成します。これは、新しいゴルーチン内で `defer` された関数が実行されたことをメインゴルーチンに通知するために使用されます。
2.  `go func() { ... }()`: 新しいゴルーチンを起動します。
3.  `defer func() { ... }()`: 新しいゴルーチン内で無名関数を `defer` します。この無名関数は、ゴルーチンが終了する直前に実行されます。
    *   `r := recover()`: `defer` された関数内で `recover()` を呼び出し、その戻り値を `r` に格納します。
    *   `if r != nil { t.Errorf("non-nil recover during Goexit") }`: `recover()` の戻り値 `r` が `nil` でない場合（つまり、`Goexit()` ではなく `panic` によって `defer` が実行された場合）、テストエラーを報告します。これは、`Goexit()` による終了時には `recover()` が `nil` を返すという保証を検証しています。
    *   `c <- struct{}{}`: `defer` された関数がここまで実行されたことを示すために、チャネル `c` に空の構造体を送信します。
4.  `runtime.Goexit()`: `defer` ステートメントの直後に `runtime.Goexit()` を呼び出し、現在のゴルーチンを終了させます。これにより、`defer` された関数が実行されるトリガーとなります。
5.  `<-c`: メインゴルーチンはチャネル `c` から値を受信するまでブロックします。もし `defer` された関数が `runtime.Goexit()` によって実行されなかった場合、チャネルへの送信が行われず、メインゴルーチンはデッドロックに陥ります。これにより、`defer` が確実に実行されたことを検証します。

このテストは、`runtime.Goexit()` が `defer` を実行するというGoランタイムの重要な保証と、その際に `recover()` が `nil` を返すという特定の挙動を、簡潔かつ効果的に検証しています。

# [インデックス 23965] ファイルの概要

このコミットは、Go言語の`archive/tar`パッケージにおけるハードリンクの属性処理に関するバグ修正と、関連するテストケースの追加を目的としています。特に、`os.FileInfo`と`tar.Header`間の「ラウンドトリップ」変換において、ハードリンクのメタデータが正しく保持されない問題を解決し、ハードリンクの取り扱いをより堅牢にしています。

## 元コミット内容

`archive/tar`パッケージにおいて、ハードリンクの属性がラウンドトリップ（`os.FileInfo`から`tar.Header`への変換、およびその逆）で正しく処理されない問題を修正します。この問題は、ハードリンクのヘッダーの`FileInfo`を扱う際に発見されました。また、ハードリンクの処理を検証するための追加のテストケースも導入されています。この変更は、Go issue #9027を修正します。

## 変更の背景

この変更の背景には、`archive/tar`パッケージがTARアーカイブ内のハードリンクを正確に表現し、そのメタデータを正しく保持する必要性がありました。元の実装では、ファイルシステム上の`os.FileInfo`オブジェクトからTARヘッダー（`tar.Header`）を作成し、そのヘッダーから再度`os.FileInfo`のような情報を取得する際に、ハードリンク特有の属性（特に`Typeflag`や`Linkname`）が失われたり、誤って解釈されたりする問題がありました。

具体的には、`os.FileInfo`がハードリンクを示している場合でも、`tar.Header`への変換時に`TypeLink`フラグが適切に設定されなかったり、`Linkname`フィールドが空のままになったりする可能性がありました。これにより、TARアーカイブを作成し、それを展開する際に、元のハードリンク構造が失われ、単なるコピーファイルとして扱われるなどの不整合が生じる恐れがありました。

この問題は、特にハードリンクを多用するシステムや、アーカイブの完全な忠実性が求められるバックアップシステムなどで深刻な影響を及ぼす可能性があります。コミットメッセージにある「round trip FileInfo of the headers of hardlinks」という記述は、この変換プロセスにおける正確性の欠如を明確に示しています。

このコミットは、これらの問題を解決し、`archive/tar`パッケージがハードリンクをより正確かつ堅牢に処理できるようにするために行われました。追加されたテストケースは、この修正が意図通りに機能し、将来的な回帰を防ぐためのものです。

## 前提知識の解説

このコミットを理解するためには、以下の概念とGo言語のパッケージに関する知識が必要です。

1.  **`archive/tar`パッケージ**:
    Go言語の標準ライブラリの一部で、TAR (Tape ARchive) ファイル形式の読み書きをサポートします。TARファイルは、複数のファイルを一つのアーカイブにまとめるための一般的な形式であり、Unix系システムで広く利用されています。このパッケージは、ファイルのメタデータ（パーミッション、所有者、タイムスタンプなど）と内容をアーカイブに保存・復元する機能を提供します。

2.  **`os.FileInfo`インターフェース**:
    Go言語の`os`パッケージで定義されているインターフェースで、ファイルシステム上のファイルやディレクトリに関する抽象的な情報を提供します。これには、ファイル名、サイズ、変更時刻、ファイルモード（パーミッションやファイルタイプなど）などが含まれます。`os.Stat`関数などを使って取得できます。

3.  **`tar.Header`構造体**:
    `archive/tar`パッケージ内で定義されている構造体で、TARアーカイブ内の各エントリ（ファイル、ディレクトリ、シンボリックリンク、ハードリンクなど）のメタデータを表現します。これには、`Name` (ファイル名)、`Mode` (ファイルモード)、`Size` (サイズ)、`ModTime` (変更時刻)、`Typeflag` (エントリのタイプ)、`Linkname` (リンク先のパス、リンクの場合) など、`os.FileInfo`と類似または拡張された情報が含まれます。

4.  **ハードリンク (Hard Link)**:
    ファイルシステムにおける特殊なファイル参照の一種です。同じiノード（inode）を指す複数のファイル名（ディレクトリエントリ）を作成することで実現されます。これにより、複数の異なるパスから同じファイルデータにアクセスできます。ハードリンクの重要な特性は以下の通りです。
    *   元のファイルが削除されても、他のハードリンクが存在する限りデータは削除されません。
    *   同じファイルシステム内でのみ作成可能です。
    *   ディレクトリへのハードリンクは通常作成できません（ファイルシステムによっては可能ですが、一般的ではありません）。
    *   ファイルサイズは、すべてのハードリンクで同じです。

5.  **シンボリックリンク (Symbolic Link / Soft Link)**:
    これもファイルシステムにおけるファイル参照の一種ですが、ハードリンクとは異なります。シンボリックリンクは、別のファイルやディレクトリへのパスを内容として持つ特殊なファイルです。
    *   元のファイルが削除されると、シンボリックリンクは「壊れたリンク」（dangling link）となり、参照先が見つからなくなります。
    *   異なるファイルシステム間でも作成可能です。
    *   ディレクトリへのシンボリックリンクも作成できます。

6.  **`Typeflag`フィールド**:
    `tar.Header`構造体内の重要なフィールドで、TARアーカイブエントリのタイプを示します。このコミットに関連する主な値は以下の通りです。
    *   `TypeReg` (`'0'`) または `TypeRegA` (`'\0'`)：通常ファイル
    *   `TypeLink` (`'1'`)：ハードリンク
    *   `TypeSymlink` (`'2'`)：シンボリックリンク

7.  **ラウンドトリップ (Round-trip)**:
    データ変換の文脈で使われる用語で、ある形式のデータを別の形式に変換し、その後元の形式に戻すプロセスを指します。このコミットの文脈では、ファイルシステム上の`os.FileInfo`から`tar.Header`を作成し、その`tar.Header`から再度`os.FileInfo`に相当する情報を取得する際に、情報が失われたり変更されたりせずに正しく変換されることを意味します。特にハードリンクの属性がこのラウンドトリップで正確に保持されることが問題となっていました。

## 技術的詳細

このコミットの技術的詳細は、主に`archive/tar`パッケージがファイルシステム上の`os.FileInfo`を`tar.Header`に変換する際のロジック、特にハードリンクの検出と属性設定に関するものです。

問題の核心は、`statUnix`関数（Unix系システムで`os.FileInfo`から`tar.Header`を生成する役割を担う）が、ハードリンクを適切に識別し、そのメタデータを`tar.Header`に正確にマッピングできていなかった点にあります。

変更前は、`statUnix`関数内で`fi.Sys().(*syscall.Stat_t)`を使って`syscall.Stat_t`構造体を取得し、そこから`Uid`、`Gid`、`AccessTime`、`ChangeTime`などの情報を`tar.Header`にコピーしていました。しかし、ハードリンクの検出ロジックが不十分でした。

**変更点と修正のメカニズム:**

1.  **`src/archive/tar/common.go`の修正**:
    *   `headerFileInfo.Mode()`メソッド内で、`TypeLink`と`TypeSymlink`の両方が`os.ModeSymlink`にマッピングされていました。これは、ハードリンク（`TypeLink`）がシンボリックリンク（`os.ModeSymlink`）として誤って解釈される可能性を示唆しています。
    *   修正後、`TypeLink`は`os.ModeSymlink`にマッピングされなくなり、`TypeSymlink`のみが`os.ModeSymlink`にマッピングされるようになりました。これにより、`tar.Header`の`Typeflag`が`TypeLink`である場合に、`os.FileInfo`の`Mode()`が正しくハードリンクではないことを示すようになります。

2.  **`src/archive/tar/stat_unix.go`の修正**:
    *   `statUnix`関数が大幅に修正されました。以前は`fi.Sys().(*syscall.Stat_t)`の型アサーションが失敗した場合に`nil`を返していましたが、新しい実装では`switch sys := fi.Sys().(type)`構文を使用して、`fi.Sys()`が`*syscall.Stat_t`型である場合と`*Header`型である場合の両方を処理するようになりました。
    *   **`*syscall.Stat_t`の場合**:
        *   `sys.Nlink > 1`（リンク数が1より大きい）かつ`fi.Mode().IsRegular()`（通常ファイルである）という条件で、そのファイルがハードリンクであることを検出します。
        *   この場合、`h.Typeflag`を`TypeLink`に設定し、`h.Size`を`0`に設定します。これは、TAR形式のハードリンクエントリがファイル内容を持たず、リンク先の情報のみを持つという仕様に合致させます。
        *   以前は`Linkname`が設定されていませんでしたが、このコミットでは`// TODO(vbatts): Linkname?`というコメントが追加されており、将来的な改善の余地を示唆しています（ただし、このコミット自体では`Linkname`の設定は行われていません）。
    *   **`*Header`の場合**:
        *   これは、`tar.Header`から`os.FileInfo`を生成する際の「ラウンドトリップ」ロジックをサポートするための追加です。`fi.Sys()`が既に`*Header`型である場合（つまり、TARヘッダーから`FileInfo`が作成された場合）、元の`Header`の属性（`Uid`, `Gid`, `Uname`, `Gname`, `AccessTime`, `ChangeTime`, `Xattrs`, `Typeflag`, `Linkname`）を新しい`Header`にコピーします。
        *   特に、`sys.Typeflag == TypeLink`の場合、新しい`Header`の`Typeflag`も`TypeLink`に設定し、`Size`を`0`に、`Linkname`を元の`sys.Linkname`に設定することで、ハードリンクの属性がラウンドトリップで完全に保持されるようにします。

3.  **テストケースの追加と修正 (`src/archive/tar/tar_test.go`, `src/archive/tar/writer_test.go`, `src/archive/tar/testdata/hardlink.tar`)**:
    *   `TestHeaderRoundTrip`関数から、ハードリンクに関する古いテストケースが削除され、より正確な新しいハードリンクのテストケースが追加されました。新しいテストケースでは、`Linkname`フィールドが設定され、`Typeflag`が`TypeLink`であることが期待されます。
    *   `writerTests`に、`gnu tar`で作成されたハードリンクを含むTARファイル（`hardlink.tar`）のテストデータが追加されました。これにより、実際のTARアーカイブとの互換性も検証されます。このテストデータは、`file.txt`とそれへのハードリンクである`hard.txt`を含んでいます。
    *   `TestHeaderRoundTrip`では、`Uid`, `Gid`, `Uname`, `Gname`, `Linkname`, `Typeflag`, `AccessTime`, `ChangeTime`といったフィールドのラウンドトリップが正しく行われるかどうかの検証が追加されました。

これらの変更により、`archive/tar`パッケージは、ファイルシステム上のハードリンクをTARアーカイブに正確に変換し、またTARアーカイブからハードリンクのメタデータを正確に復元できるようになりました。特に、`statUnix`関数が`os.FileInfo`の`Sys()`フィールドの型をより柔軟に処理し、ハードリンクの検出と属性設定を改善した点が重要です。

```go

	switch sys := fi.Sys().(type) {
	case *syscall.Stat_t:
		h.Uid = int(sys.Uid)
		h.Gid = int(sys.Gid)
		// ... (username & group TODOs)
		h.AccessTime = statAtime(sys)
		h.ChangeTime = statCtime(sys)
		// ... (major/minor device numbers TODOs)
		if fi.Mode().IsRegular() && sys.Nlink > 1 {
			h.Typeflag = TypeLink
			h.Size = 0
			// TODO(vbatts): Linkname?
		}
	case *Header:
		// for the roundtrip logic
		h.Uid = sys.Uid
		h.Gid = sys.Gid
		h.Uname = sys.Uname
		h.Gname = sys.Gname
		h.AccessTime = sys.AccessTime
		h.ChangeTime = sys.ChangeTime
		if sys.Xattrs != nil {
			h.Xattrs = make(map[string]string)
			for k, v := range sys.Xattrs {
				h.Xattrs[k] = v
			}
		}
		if sys.Typeflag == TypeLink {
			// hard link
			h.Typeflag = TypeLink
			h.Size = 0
			h.Linkname = sys.Linkname
		}
	}
	return nil

## 元コミット内容

`archive/tar`パッケージにおいて、ハードリンクの属性がラウンドトリップ（`os.FileInfo`から`tar.Header`への変換、およびその逆）で正しく処理されない問題を修正します。この問題は、ハードリンクのヘッダーの`FileInfo`を扱う際に発見されました。また、ハードリンクの処理を検証するための追加のテストケースも導入されています。この変更は、Go issue #9027を修正します。

## 変更の背景

この変更の背景には、`archive/tar`パッケージがTARアーカイブ内のハードリンクを正確に表現し、そのメタデータを正しく保持する必要性がありました。元の実装では、ファイルシステム上の`os.FileInfo`オブジェクトからTARヘッダー（`tar.Header`）を作成し、そのヘッダーから再度`os.FileInfo`のような情報を取得する際に、ハードリンク特有の属性（特に`Typeflag`や`Linkname`）が失われたり、誤って解釈されたりする問題がありました。

具体的には、`os.FileInfo`がハードリンクを示している場合でも、`tar.Header`への変換時に`TypeLink`フラグが適切に設定されなかったり、`Linkname`フィールドが空のままになったりする可能性がありました。これにより、TARアーカイブを作成し、それを展開する際に、元のハードリンク構造が失われ、単なるコピーファイルとして扱われるなどの不整合が生じる恐れがありました。

この問題は、特にハードリンクを多用するシステムや、アーカイブの完全な忠実性が求められるバックアップシステムなどで深刻な影響を及ぼす可能性があります。コミットメッセージにある「round trip FileInfo of the headers of hardlinks」という記述は、この変換プロセスにおける正確性の欠如を明確に示しています。

このコミットは、これらの問題を解決し、`archive/tar`パッケージがハードリンクをより正確かつ堅牢に処理できるようにするために行われました。追加されたテストケースは、この修正が意図通りに機能し、将来的な回帰を防ぐためのものです。

## 前提知識の解説

このコミットを理解するためには、以下の概念とGo言語のパッケージに関する知識が必要です。

1.  **`archive/tar`パッケージ**:
    Go言語の標準ライブラリの一部で、TAR (Tape ARchive) ファイル形式の読み書きをサポートします。TARファイルは、複数のファイルを一つのアーカイブにまとめるための一般的な形式であり、Unix系システムで広く利用されています。このパッケージは、ファイルのメタデータ（パーミッション、所有者、タイムスタンプなど）と内容をアーカイブに保存・復元する機能を提供します。

2.  **`os.FileInfo`インターフェース**:
    Go言語の`os`パッケージで定義されているインターフェースで、ファイルシステム上のファイルやディレクトリに関する抽象的な情報を提供します。これには、ファイル名、サイズ、変更時刻、ファイルモード（パーミッションやファイルタイプなど）などが含まれます。`os.Stat`関数などを使って取得できます。

3.  **`tar.Header`構造体**:
    `archive/tar`パッケージ内で定義されている構造体で、TARアーカイブ内の各エントリ（ファイル、ディレクトリ、シンボリックリンク、ハードリンクなど）のメタデータを表現します。これには、`Name` (ファイル名)、`Mode` (ファイルモード)、`Size` (サイズ)、`ModTime` (変更時刻)、`Typeflag` (エントリのタイプ)、`Linkname` (リンク先のパス、リンクの場合) など、`os.FileInfo`と類似または拡張された情報が含まれます。

4.  **ハードリンク (Hard Link)**:
    ファイルシステムにおける特殊なファイル参照の一種です。同じiノード（inode）を指す複数のファイル名（ディレクトリエントリ）を作成することで実現されます。これにより、複数の異なるパスから同じファイルデータにアクセスできます。ハードリンクの重要な特性は以下の通りです。
    *   元のファイルが削除されても、他のハードリンクが存在する限りデータは削除されません。
    *   同じファイルシステム内でのみ作成可能です。
    *   ディレクトリへのハードリンクは通常作成できません（ファイルシステムによっては可能ですが、一般的ではありません）。
    *   ファイルサイズは、すべてのハードリンクで同じです。

5.  **シンボリックリンク (Symbolic Link / Soft Link)**:
    これもファイルシステムにおけるファイル参照の一種ですが、ハードリンクとは異なります。シンボリックリンクは、別のファイルやディレクトリへのパスを内容として持つ特殊なファイルです。
    *   元のファイルが削除されると、シンボリックリンクは「壊れたリンク」（dangling link）となり、参照先が見つからなくなります。
    *   異なるファイルシステム間でも作成可能です。
    *   ディレクトリへのシンボリックリンクも作成できます。

6.  **`Typeflag`フィールド**:
    `tar.Header`構造体内の重要なフィールドで、TARアーカイブエントリのタイプを示します。このコミットに関連する主な値は以下の通りです。
    *   `TypeReg` (`'0'`) または `TypeRegA` (`'\0'`)：通常ファイル
    *   `TypeLink` (`'1'`)：ハードリンク
    *   `TypeSymlink` (`'2'`)：シンボリックリンク

7.  **ラウンドトリップ (Round-trip)**:
    データ変換の文脈で使われる用語で、ある形式のデータを別の形式に変換し、その後元の形式に戻すプロセスを指します。このコミットの文脈では、ファイルシステム上の`os.FileInfo`から`tar.Header`を作成し、その`tar.Header`から再度`os.FileInfo`に相当する情報を取得する際に、情報が失われたり変更されたりせずに正しく変換されることを意味します。特にハードリンクの属性がこのラウンドトリップで正確に保持されることが問題となっていました。

## コアとなるコードの解説

このコミットの核となる変更は、`src/archive/tar/stat_unix.go`の`statUnix`関数と、それに関連するテストロジックにあります。

### `src/archive/tar/stat_unix.go` の `statUnix` 関数

この関数は、ファイルシステムから取得した`os.FileInfo`オブジェクトを、TARアーカイブのヘッダー情報である`*tar.Header`に変換する役割を担っています。

**変更前**:
以前の`statUnix`は、`fi.Sys().(*syscall.Stat_t)`という型アサーションを使って、`os.FileInfo`の基盤となるシステム固有の情報を取得していました。しかし、このアサーションが失敗した場合（例えば、`fi.Sys()`が`*syscall.Stat_t`以外の型を返す場合）、関数は単に`nil`を返していました。また、ハードリンクの検出ロジックも不十分で、`sys.Nlink > 1`（リンク数が1より大きい）という条件だけでハードリンクを識別し、`TypeLink`を設定するような明示的な処理がありませんでした。

**変更後**:
```go
func statUnix(fi os.FileInfo, h *Header) error {
	switch sys := fi.Sys().(type) {
	case *syscall.Stat_t:
		h.Uid = int(sys.Uid)
		h.Gid = int(sys.Gid)
		// ... (username & group TODOs)
		h.AccessTime = statAtime(sys)
		h.ChangeTime = statCtime(sys)
		// ... (major/minor device numbers TODOs)
		if fi.Mode().IsRegular() && sys.Nlink > 1 {
			h.Typeflag = TypeLink
			h.Size = 0
			// TODO(vbatts): Linkname?
		}
	case *Header:
		// for the roundtrip logic
		h.Uid = sys.Uid
		h.Gid = sys.Gid
		h.Uname = sys.Uname
		h.Gname = sys.Gname
		h.AccessTime = sys.AccessTime
		h.ChangeTime = sys.ChangeTime
		if sys.Xattrs != nil {
			h.Xattrs = make(map[string]string)
			for k, v := range sys.Xattrs {
				h.Xattrs[k] = v
			}
		}
		if sys.Typeflag == TypeLink {
			// hard link
			h.Typeflag = TypeLink
			h.Size = 0
			h.Linkname = sys.Linkname
		}
	}
	return nil
}
```

1.  **`switch sys := fi.Sys().(type)` の導入**:
    これは、`fi.Sys()`が返す具体的な型に基づいて異なる処理を行うためのGoの型スイッチ構文です。これにより、`os.FileInfo`の基盤となるシステム情報が`*syscall.Stat_t`である場合と、既に`*tar.Header`である場合（これは、TARヘッダーから`os.FileInfo`が作成された「ラウンドトリップ」シナリオで発生します）の両方を適切に処理できるようになりました。

2.  **`*syscall.Stat_t` の処理強化**:
    *   `fi.Mode().IsRegular() && sys.Nlink > 1`という条件が追加されました。これは、ファイルが通常のファイルであり、かつ複数のリンクを持つ場合に、それがハードリンクであることを正確に識別するためのものです。
    *   ハードリンクと識別された場合、`h.Typeflag = TypeLink`を設定します。これにより、TARヘッダーがこのエントリをハードリンクとして正しくマークするようになります。
    *   `h.Size = 0`を設定します。TAR形式では、ハードリンクエントリ自体はファイル内容を持たず、リンク先のファイルを参照するだけなので、サイズは0であるべきです。
    *   `// TODO(vbatts): Linkname?`というコメントは、この時点では`Linkname`フィールドが設定されていないことを示唆していますが、ハードリンクの識別と`Typeflag`の設定が優先されました。

3.  **`*Header` の新しい処理 (`roundtrip logic`)**:
    *   この`case`は、`os.FileInfo`が既に`tar.Header`から派生したものである場合に重要です。例えば、`tar.Reader`でTARアーカイブを読み込み、そのヘッダーから`os.FileInfo`を作成し、さらにその`os.FileInfo`を再度`tar.Header`に変換しようとするシナリオです。
    *   このブロックでは、元の`Header`の`Uid`, `Gid`, `Uname`, `Gname`, `AccessTime`, `ChangeTime`, `Xattrs`などの属性を新しい`Header`にコピーします。
    *   最も重要なのは、`if sys.Typeflag == TypeLink`のチェックです。もし元のヘッダーがハードリンクであった場合、新しいヘッダーの`Typeflag`も`TypeLink`に設定し、`Size`を`0`に、そして`Linkname`を元の`sys.Linkname`に設定します。これにより、ハードリンクのすべての重要な属性がラウンドトリップで完全に保持されることが保証されます。

### `src/archive/tar/common.go` の `headerFileInfo.Mode()` メソッド

このメソッドは、`tar.Header`から`os.FileMode`を生成する際に、ファイルタイプを決定します。

**変更前**:
`TypeLink`と`TypeSymlink`の両方が`os.ModeSymlink`として扱われていました。これは、ハードリンクがシンボリックリンクとして誤って解釈される可能性があり、`os.FileInfo`の`Mode()`が返す情報に不整合をもたらす可能性がありました。

**変更後**:
`TypeLink`が`os.ModeSymlink`にマッピングされなくなりました。これにより、`tar.Header`が`TypeLink`である場合、`os.FileInfo.Mode()`はハードリンクをシンボリックリンクとして報告しなくなり、より正確なファイルタイプ情報を提供するようになります。

### テストケースの追加と修正

`tar_test.go`と`writer_test.go`におけるテストケースの追加は、これらの変更が正しく機能することを検証するために不可欠です。特に、`TestHeaderRoundTrip`における`Uid`, `Gid`, `Uname`, `Gname`, `Linkname`, `Typeflag`, `AccessTime`, `ChangeTime`といった詳細な属性の検証は、ハードリンクのメタデータが完全に保持されることを保証します。また、`gnu tar`で作成された実際のハードリンクを含むTARファイル（`hardlink.tar`）をテストデータとして使用することで、Goの`archive/tar`パッケージが外部ツールとの互換性も維持していることを確認しています。

これらの変更により、Goの`archive/tar`パッケージは、ハードリンクの取り扱いにおいてより堅牢で正確な動作を実現し、TARアーカイブの忠実性を向上させています。

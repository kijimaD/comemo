# [インデックス 25879] ファイルの概要

このコミットは、Go言語の `archive/tar` パッケージにおいて、TARアーカイブ内の「ヘッダーのみ」の特殊なファイルタイプ（例：シンボリックリンク、ディレクトリ、デバイスファイルなど）の処理を改善するものです。これらのファイルタイプは、TARの仕様上データセクションを持たないため、`Reader` が誤ってデータセクションを読み込もうとしないように修正が加えられました。

## 元コミット内容

`archive/tar`: `Reader` におけるヘッダーのみの「ファイル」を適切に処理する

特定の特殊なタイプフラグ、具体的には 1, 2, 3, 4, 5, 6 はデータセクションを持ちません。したがって、`size` フィールドが何を示していようと、これらの特殊なタイプに対してはデータを読み込もうとすべきではありません。

関連する PAX および USTAR の仕様には次のように記載されています。
<<<
`typeflag` フィールドがタイプ 1 (リンク) または 2 (シンボリックリンク) のファイルを示すように設定されている場合、`size` フィールドはゼロとして指定されなければなりません。
`typeflag` フィールドがタイプ 5 (ディレクトリ) のファイルを示すように設定されている場合、`size` フィールドはそのレコードタイプの定義に従って解釈されます。タイプ 1, 2, 5 の場合、データ論理レコードは格納されません。
`typeflag` フィールドが 3 (キャラクタスペシャルファイル)、4 (ブロックスペシャルファイル)、または 6 (FIFO) に設定されている場合、`size` フィールドの意味は POSIX.1-2008 のこのボリュームでは未指定であり、データ論理レコードはメディアに格納されません。
さらに、タイプ 6 の場合、読み取り時には `size` フィールドは無視されます。
`typeflag` フィールドがその他の値に設定されている場合、ヘッダーに続く書き込まれる論理レコードの数は、除算の結果の端数を無視して (`size`+511)/512 となります。
>>>

仕様に反して、タイプ 1 および 2 の `size` フィールドがゼロであることを強制しません。これは、仕様に準拠しない形式も寛容に受け入れるためです。

## 変更の背景

TARアーカイブフォーマットには、ファイルタイプを示す `typeflag` フィールドが存在します。通常のファイル（`TypeReg`）はヘッダーの後にデータセクションが続きますが、シンボリックリンク（`TypeSymlink`）、ハードリンク（`TypeLink`）、ディレクトリ（`TypeDir`）、キャラクタスペシャルファイル（`TypeChar`）、ブロックスペシャルファイル（`TypeBlock`）、FIFO（`TypeFifo`）といった特殊なファイルタイプは、TARの仕様上、データセクションを持ちません。

しかし、既存の `archive/tar` パッケージの `Reader` は、これらのヘッダーのみのファイルタイプに対しても、ヘッダーの `size` フィールドに非ゼロの値が設定されている場合に、誤ってデータセクションを読み込もうとする可能性がありました。これは、TARアーカイブの仕様に厳密に従わない、あるいは意図的に `size` フィールドに値を設定している非標準的なアーカイブを処理する際に問題を引き起こす可能性がありました。

このコミットは、このような誤ったデータ読み込みの試みを防ぎ、TARアーカイブの仕様に準拠した、より堅牢な `Reader` の実装を提供することを目的としています。特に、`size` フィールドがゼロであるべきタイプ 1 および 2 のファイルに対して、仕様に反して非ゼロの値が設定されている場合でも、`Reader` が正しく動作するように改善されています。

## 前提知識の解説

### TARアーカイブフォーマット

TAR (Tape ARchive) は、複数のファイルを一つのアーカイブファイルにまとめるためのファイルフォーマットです。主にUnix系システムで利用され、ファイルのパーミッション、タイムスタンプ、所有者情報などのメタデータも保存できます。

TARアーカイブは、基本的に一連の「ヘッダーブロック」とそれに続く「データブロック」で構成されます。
- **ヘッダーブロック**: 各ファイルやディレクトリのメタデータ（ファイル名、サイズ、パーミッション、タイプフラグなど）を格納します。通常512バイトの固定長です。
- **データブロック**: ヘッダーブロックに続く、実際のファイルデータが格納される部分です。これも512バイト単位でアラインされます。

### TARのタイプフラグ (Typeflag)

TARヘッダーには `typeflag` という1バイトのフィールドがあり、アーカイブ内のエントリの種類を示します。主要なタイプフラグは以下の通りです。

| Typeflag (ASCII) | 定数 (Go `archive/tar` パッケージ) | 説明                               | データセクション |
| :--------------- | :--------------------------------- | :--------------------------------- | :--------------- |
| '0' または '\0'  | `TypeReg`                          | 通常のファイル                     | あり             |
| '1'              | `TypeLink`                         | ハードリンク                       | なし             |
| '2'              | `TypeSymlink`                      | シンボリックリンク                 | なし             |
| '3'              | `TypeChar`                         | キャラクタスペシャルファイル       | なし             |
| '4'              | `TypeBlock`                        | ブロックスペシャルファイル         | なし             |
| '5'              | `TypeDir`                          | ディレクトリ                       | なし             |
| '6'              | `TypeFifo`                         | FIFO (名前付きパイプ)              | なし             |
| '7'              | `TypeCont`                         | 連続ファイル (古いV7 TAR)          | あり             |
| 'x'              | `TypeXHeader`                      | PAX拡張ヘッダー (グローバル)       | あり             |
| 'g'              | `TypeXGlobalHeader`                | PAX拡張ヘッダー (ファイルごと)     | あり             |

このコミットで特に重要となるのは、データセクションを持たない `TypeLink`, `TypeSymlink`, `TypeChar`, `TypeBlock`, `TypeDir`, `TypeFifo` の各タイプです。

### スパースファイル (Sparse Files)

スパースファイルは、ファイル内に連続したゼロのブロックがある場合に、そのゼロブロックをディスク上に物理的に割り当てずに、論理的なサイズだけを記録することでディスク容量を節約するファイルです。TARアーカイブでも、GNU TAR拡張などによりスパースファイルを表現する方法が存在します。スパースファイルは通常、データセクションを持つ通常のファイルに対して適用される概念です。

## 技術的詳細

このコミットの主要な変更点は、`archive/tar` パッケージの `Reader` が、データセクションを持たない特殊なTARエントリタイプ（リンク、シンボリックリンク、ディレクトリ、デバイスファイルなど）に対して、`size` フィールドの値に関わらずデータ読み込みを試みないようにすることです。

具体的には、以下の修正が行われました。

1.  **`isHeaderOnlyType` 関数の導入**:
    `src/archive/tar/common.go` に `isHeaderOnlyType(flag byte) bool` という新しいヘルパー関数が追加されました。この関数は、引数として与えられた `typeflag` が、TAR仕様上データセクションを持たないタイプ（`TypeLink`, `TypeSymlink`, `TypeChar`, `TypeBlock`, `TypeDir`, `TypeFifo`）のいずれかである場合に `true` を返します。これにより、データセクションの有無を判断するロジックが一元化され、可読性と保守性が向上しました。

2.  **`Reader.Next()` メソッドの修正**:
    `src/archive/tar/reader.go` の `Next()` メソッドは、次のTARエントリのヘッダーを読み込み、そのエントリの `io.Reader` を返します。このメソッド内で、PAX形式のGNUスパースファイルを処理するロジックがあります。
    変更前は、スパースファイルの処理がヘッダーのみのタイプに適用される可能性がありましたが、これは概念的に矛盾します。スパースファイルはデータセクションを持つファイルに対して意味があるためです。
    変更後、`isHeaderOnlyType(hdr.Typeflag)` が `true` の場合、つまりヘッダーのみのタイプであるにもかかわらずスパースファイルとして扱われようとした場合、`ErrHeader` エラーを返すようになりました。これにより、不正なアーカイブ形式に対する早期検出とエラー処理が強化されます。

3.  **`Reader.readHeader()` メソッドの修正**:
    `src/archive/tar/reader.go` の `readHeader()` メソッドは、TARヘッダーを解析し、`Header` 構造体を生成します。このメソッド内で、エントリのデータサイズ (`nb`) を決定し、それに基づいて `tr.pad` (次のヘッダーまでのパディングバイト数) を計算し、`tr.curr` (現在のファイルリーダー) を設定するロジックがあります。
    -   **`hdr.Size < 0` チェックの移動**: 以前は `hdr.Size` を読み込んだ直後に負の値チェックがありましたが、これは削除されました。このチェックは、`nb` が最終的に決定された後に行われるように変更されました。
    -   **データサイズ (`nb`) の調整**: 最も重要な変更は、`nb` の計算ロジックです。`isHeaderOnlyType(hdr.Typeflag)` が `true` の場合、`nb` は強制的に `0` に設定されます。これにより、ヘッダーのみのタイプに対しては、ヘッダーの `size` フィールドが非ゼロであっても、データセクションを読み込もうとしないことが保証されます。
    -   **負のサイズチェックの再導入**: `nb` が調整された後、`if nb < 0 { ... }` のチェックが再導入されました。これにより、`isHeaderOnlyType` で処理されない通常のファイルタイプで `size` が負の値である場合に、適切に `ErrHeader` が返されるようになります。

これらの変更により、`archive/tar` パッケージは、TARアーカイブの仕様に準拠し、ヘッダーのみの特殊なファイルタイプをより正確かつ堅牢に処理できるようになりました。特に、非標準的なアーカイブで `size` フィールドが誤って設定されている場合でも、予期せぬデータ読み込みエラーを防ぐことができます。

```go
// isHeaderOnlyType checks if the given type flag is of the type that has no
// data section even if a size is specified.
func isHeaderOnlyType(flag byte) bool {
	switch flag {
	case TypeLink, TypeSymlink, TypeChar, TypeBlock, TypeDir, TypeFifo:
		return true
	default:
		return false
	}
}
```

### `src/archive/tar/reader.go`

```go
func (tr *Reader) Next() (*Header, error) {
	// ... (既存のコード) ...

	if sp != nil {
		// Sparse files do not make sense when applied to the special header
		// types that never have a data section.
		if isHeaderOnlyType(hdr.Typeflag) {
			tr.err = ErrHeader
			return nil, tr.err
		}

		// Current file is a PAX format GNU sparse file.
		// Set the current file reader to a sparse file reader.
		tr.curr, tr.err = newSparseFileReader(tr.curr, sp, hdr.Size)
		if tr.err != nil {
			return nil, tr.err
		}
	}

	// ... (既存のコード) ...
}

func (tr *Reader) readHeader() *Header {
	// ... (既存のコード) ...

	hdr.Size = tr.octal(s.next(12))
	// 削除されたコード:
	// if hdr.Size < 0 {
	// 	tr.err = ErrHeader
	// 	return nil
	// }
	hdr.ModTime = time.Unix(tr.octal(s.next(12)), 0)
	s.next(8) // chksum
	hdr.Typeflag = s.next(1)[0]

	// ... (既存のコード) ...

	nb := hdr.Size
	if isHeaderOnlyType(hdr.Typeflag) {
		nb = 0
	}
	if nb < 0 {
		tr.err = ErrHeader
		return nil
	}

	// Set the current file reader.
	tr.pad = -nb & (blockSize - 1) // blockSize is a power of two
	tr.curr = &regFileReader{r: tr.r, nb: nb}

	// ... (既存のコード) ...
}
```

### `src/archive/tar/reader_test.go`

```go
// TestReadHeaderOnly tests that Reader does not attempt to read special
// header-only files.
func TestReadHeaderOnly(t *testing.T) {
	f, err := os.Open("testdata/hdr-only.tar")
	if err != nil {
		t.Fatalf("unexpected error: %v", err)
	}
	defer f.Close()

	var hdrs []*Header
	tr := NewReader(f)
	for {
		hdr, err := tr.Next()
		if err == io.EOF {
			break
		}
		if err != nil {
			t.Errorf("Next(): got %v, want %v", err, nil)
			continue
		}
		hdrs = append(hdrs, hdr)

		// If a special flag, we should read nothing.
		cnt, _ := io.ReadFull(tr, []byte{0})
		if cnt > 0 && hdr.Typeflag != TypeReg {
			t.Errorf("ReadFull(...): got %d bytes, want 0 bytes", cnt)
		}
	}

	// File is crafted with 16 entries. The later 8 are identical to the first
	// 8 except that the size is set.
	if len(hdrs) != 16 {
		t.Fatalf("len(hdrs): got %d, want %d", len(hdrs), 16)
	}
	for i := 0; i < 8; i++ {
		var hdr1, hdr2 = hdrs[i+0], hdrs[i+8]
		hdr1.Size, hdr2.Size = 0, 0
		if !reflect.DeepEqual(*hdr1, *hdr2) {
			t.Errorf("incorrect header:\ngot  %+v\nwant %+v", *hdr1, *hdr2)
		}
	}
}
```

## コアとなるコードの解説

### `isHeaderOnlyType` 関数

この関数は、TARヘッダーの `typeflag` が、データセクションを持たない特殊なファイルタイプ（リンク、シンボリックリンク、キャラクタスペシャルファイル、ブロックスペシャルファイル、ディレクトリ、FIFO）のいずれかであるかを効率的に判定します。`switch` ステートメントを使用することで、複数のタイプフラグに対するチェックを簡潔に記述しています。この関数は、`Reader` の他の部分でデータ読み込みの要否を判断する際の中心的なロジックとなります。

### `Reader.Next()` メソッドの変更

`Next()` メソッド内の変更は、スパースファイルの処理とヘッダーのみのファイルタイプの間の論理的な矛盾を解消します。スパースファイルは、その性質上、データセクションを持つ通常のファイルに適用されるべきです。もし `typeflag` がヘッダーのみのタイプを示しているにもかかわらず、PAX形式のスパースファイルとして扱われようとした場合、これはアーカイブの構造が不正であることを意味します。この変更により、そのような不正なケースを `ErrHeader` として検出し、早期にエラーを報告することで、`Reader` の堅牢性が向上します。

### `Reader.readHeader()` メソッドの変更

`readHeader()` メソッドにおける最も重要な変更は、`nb` (読み込むべきデータバイト数) の計算ロジックです。
1.  **`hdr.Size < 0` チェックの移動**: 以前は `hdr.Size` を読み込んだ直後に負の値チェックがありましたが、これは `isHeaderOnlyType` のチェックと `nb` の調整の後に行われるように変更されました。これにより、ヘッダーのみのタイプで `nb` が `0` に設定された後に、改めて負の値チェックが行われることになり、ロジックの順序がより適切になりました。
2.  **`nb` の強制的なゼロ設定**: `isHeaderOnlyType(hdr.Typeflag)` が `true` の場合、`nb` は無条件に `0` に設定されます。これは、TAR仕様においてこれらのタイプがデータセクションを持たないという事実を直接コードに反映したものです。これにより、たとえヘッダーの `size` フィールドに非ゼロの値が誤って設定されていたとしても、`Reader` はデータセクションを読み込もうとせず、次のヘッダーへと正しく進むことができます。この修正は、非標準的なTARアーカイブに対する互換性と堅牢性を大幅に向上させます。
3.  **`tr.pad` と `tr.curr` の設定**: `nb` が正しく決定された後、`tr.pad` (次のヘッダーまでのパディングバイト数) と `tr.curr` (現在のエントリのデータリーダー) が設定されます。`nb` が `0` に設定された場合、`tr.pad` は `0` となり、`tr.curr` はデータ読み込みを行わないリーダーとして機能します。

### `TestReadHeaderOnly` テストケース

この新しいテストケースは、`Reader` がヘッダーのみのファイルを正しく処理することを確認するために追加されました。
-   `testdata/hdr-only.tar` というテスト用のTARアーカイブファイルを開きます。このアーカイブには、様々なヘッダーのみのタイプ（リンク、シンボリックリンク、ディレクトリなど）のエントリが含まれており、一部は `size` フィールドに非ゼロの値が意図的に設定されています。
-   `tr.Next()` を繰り返し呼び出して各エントリのヘッダーを読み込みます。
-   各エントリについて、`io.ReadFull(tr, []byte{0})` を使用してデータセクションを読み込もうとします。`hdr.Typeflag` が通常のファイル (`TypeReg`) でない限り、`cnt` (読み込まれたバイト数) が `0` であることをアサートします。これにより、ヘッダーのみのタイプに対してデータが読み込まれていないことが検証されます。
-   アーカイブ内のエントリ数と、ヘッダーのみのタイプで `size` フィールドが設定されている場合とそうでない場合のヘッダーが `reflect.DeepEqual` で比較され、`Reader` が `size` フィールドを無視して正しくヘッダーを解析していることが確認されます。

このテストケースの追加により、変更が意図した通りに機能し、将来の回帰を防ぐための安全網が提供されます。

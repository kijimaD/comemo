# [インデックス 24418] ファイルの概要

このコミットは、Go言語のアセンブラである`cmd/asm`において、ARM、ARM64、およびPPC64アーキテクチャ向けに`CALL`と`JMP`命令のエイリアス（別名）を修正し、それらのテストを追加するものです。これにより、これらのアーキテクチャでより一般的で慣用的な`CALL`と`JMP`という命令名が正しく認識され、処理されるようになります。

## 変更の背景

Go言語のツールチェーンに含まれるアセンブラ`cmd/asm`は、Goプログラムが特定のアセンブリコードをインラインで記述したり、パフォーマンスクリティカルな部分をアセンブリで実装したりする際に使用されます。アセンブリ言語はCPUアーキテクチャに強く依存するため、各アーキテクチャ（ARM、ARM64、PPC64など）にはそれぞれ独自の命令セットとニーモニック（命令の略語）が存在します。

`JMP`（ジャンプ）と`CALL`（コール）は、多くのアセンブリ言語においてプログラムの実行フローを制御するための非常に一般的な命令名です。しかし、特定のアーキテクチャでは、これらの汎用的な名前ではなく、`B`（Branch）、`BL`（Branch with Link）、`BR`（Branch Register）といったアーキテクチャ固有のニーモニックが直接使用されることがあります。

このコミット以前の`cmd/asm`では、ARM、ARM64、PPC64アーキテクチャにおいて、`JMP`と`CALL`というエイリアスがアセンブラによって正しく認識されていませんでした。その結果、開発者がこれらの一般的な命令名を使用してアセンブリコードを記述しようとすると、アセンブラエラーが発生するか、意図しない動作を引き起こす可能性がありました。

この問題は、GoのIssue #11900で報告されたと考えられます（ただし、このIssueの詳細は現在の検索では見つかりませんでした）。このコミットは、`cmd/asm`がこれらの一般的なエイリアスを、対応するアーキテクチャ固有のジャンプ/コール命令に正しくマッピングできるようにすることで、アセンブリコードの記述における一貫性と利便性を向上させることを目的としています。特に、異なるアーキテクチャ間で移植性のあるアセンブリコードを記述する際に、より汎用的な命令名を使用できることは大きな利点となります。

## 前提知識の解説

### Goのアセンブラ (`cmd/asm`)

`cmd/asm`は、Go言語のビルドツールチェーンの一部として提供されるアセンブラです。Goプログラムは通常Go言語で記述されますが、特定の低レベルな操作やパフォーマンスが重要な部分では、アセンブリ言語で記述されたコード（通常は`.s`ファイル）をGoコードとリンクさせることができます。`cmd/asm`は、これらのアセンブリソースファイルをオブジェクトファイルに変換する役割を担います。Goのアセンブリ言語は、AT&T構文やIntel構文とは異なる独自の構文（Plan 9アセンブラ構文をベースとする）を持っています。

### アセンブリ言語における `JMP` と `CALL`

*   **`JMP` (Jump)**: プログラムの実行フローを、指定されたアドレスへ無条件に転送する命令です。サブルーチン呼び出しとは異なり、通常は現在の命令の次のアドレス（戻りアドレス）をスタックに保存しません。したがって、`JMP`命令でジャンプした先から元の場所に戻るには、別の`JMP`命令を使用するか、実行フローが自然に元の場所に戻るように設計する必要があります。
*   **`CALL` (Call)**: サブルーチンや関数を呼び出すための命令です。`CALL`命令は、現在の命令の次のアドレス（戻りアドレス）をスタックや特定のレジスタに保存し、その後、指定されたサブルーチンの開始アドレスへ実行フローを転送します。サブルーチンが`RET`（Return）命令を実行すると、保存された戻りアドレスが使用され、実行フローは`CALL`命令の直後の命令に戻ります。

### エイリアス (Aliases)

プログラミング言語やアセンブリ言語において、エイリアスとは、既存のエンティティ（命令、変数、型など）に与えられる代替名または別名です。アセンブリ言語の文脈では、特定のアーキテクチャ固有の命令に対して、より一般的または慣用的な名前をエイリアスとして提供することがあります。これにより、開発者は異なるアーキテクチャ間でより一貫性のあるコードを記述できるようになり、可読性も向上します。

### ARM, ARM64, PPC64 アーキテクチャ

*   **ARM (Advanced RISC Machine)**: モバイルデバイスや組み込みシステムで広く使用されているRISC（Reduced Instruction Set Computer）アーキテクチャです。32ビットの命令セットを持ちます。
*   **ARM64 (AArch64)**: ARMv8-Aアーキテクチャで導入された64ビット版のARM命令セットです。サーバー、デスクトップ、高性能モバイルデバイスなどで採用されています。ARMでは`B`（Branch）が無条件ジャンプ、`BL`（Branch with Link）がサブルーチンコールに相当します。
*   **PPC64 (PowerPC 64-bit)**: IBMが開発したRISCアーキテクチャの64ビット版です。サーバーや高性能コンピューティングで利用されています。PPC64では`BR`（Branch Register）や`B`（Branch）が無条件ジャンプ、`BL`（Branch with Link）がサブルーチンコールに相当します。

### Goのアセンブリにおける `SB` (Static Base)

Goのアセンブリ言語では、`SB`は「Static Base」の略で、グローバルシンボルや外部シンボルを参照するための擬似レジスタです。`foo(SB)`のように記述することで、`foo`という名前のグローバルシンボル（関数やデータ）のアドレスを参照します。これは、アセンブラが最終的なアドレスを解決するための基準点となります。

## 技術的詳細

このコミットの技術的な核心は、`cmd/asm`がアセンブリコードを解析する際に、`JMP`と`CALL`という汎用的な命令名を、各ターゲットアーキテクチャ（ARM、ARM64、PPC64）が実際に持つジャンプおよびコール命令に正しくマッピングできるようにすることです。

`cmd/asm`は、アセンブリソースファイルを読み込み、字句解析（lexing）と構文解析（parsing）を経て、最終的に機械語命令を生成します。このプロセスにおいて、命令がジャンプ命令であるかどうかの識別や、命令のニーモニックを内部的な命令コードに変換する処理が行われます。

1.  **ジャンプ命令の識別**:
    `src/cmd/asm/internal/arch/`ディレクトリ内の各アーキテクチャ固有のファイル（`arm.go`, `arm64.go`, `ppc64.go`）には、そのアーキテクチャでジャンプ命令と見なされるニーモニックのリストが定義されています。これは通常、`jump*`という名前のマップや関数で管理されます。アセンブラは、入力された命令がこのリストに含まれているかどうかをチェックすることで、それがジャンプ命令であるかを判断します。このコミットでは、`JMP`と`CALL`がこれらのリストに追加され、アセンブラがこれらをジャンプ命令として認識できるようになります。

2.  **字句解析と命令のマッピング**:
    `src/cmd/old5a/lex.go`と`src/cmd/old9a/lex.go`（これらは古いアセンブラのコードベースの一部ですが、`cmd/asm`の命令認識ロジックに影響を与えている可能性があります）には、`Lextab`構造体の配列である`lexinit`が定義されています。このテーブルは、アセンブリ命令のニーモニックを、対応する内部的な命令コード（例: `arm.AB`、`arm.ABL`、`ppc64.ABR`、`ppc64.ABL`）にマッピングするために使用されます。
    *   `arm.AB`: ARMアーキテクチャの無条件分岐命令（Branch）。
    *   `arm.ABL`: ARMアーキテクチャのリンク付き分岐命令（Branch with Link）、サブルーチンコールに使用。
    *   `ppc64.ABR`: PPC64アーキテクチャの無条件分岐命令（Branch Register）。
    *   `ppc64.ABL`: PPC64アーキテクチャのリンク付き分岐命令（Branch with Link）、サブルーチンコールに使用。

    このコミットでは、`JMP`が各アーキテクチャの無条件分岐命令（`arm.AB`, `ppc64.ABR`）に、`CALL`がリンク付き分岐命令（`arm.ABL`, `ppc64.ABL`）にマッピングされるように`lexinit`が更新されます。これにより、アセンブラは`JMP`や`CALL`というエイリアスを読み込んだ際に、内部的に正しいアーキテクチャ固有の命令として処理できるようになります。

3.  **テストケースの追加**:
    `src/cmd/asm/internal/asm/testdata/`ディレクトリには、各アーキテクチャのアセンブリコードのテストファイル（`.s`）と、それに対応するアセンブル結果の期待値ファイル（`.out`）が含まれています。このコミットでは、`JMP`と`CALL`命令を含む新しいテストケースが追加され、これらのエイリアスが正しくアセンブルされることを検証します。これにより、将来の変更でこの機能がデグレードしないように保証されます。

これらの変更により、Goのアセンブラは、ARM、ARM64、PPC64アーキテクチャにおいて、より直感的で一般的な`JMP`と`CALL`という命令名をサポートし、開発者の利便性とコードの可読性を向上させます。

## コアとなるコードの解説

### `src/cmd/asm/internal/arch/*.go` の変更

`arm.go`, `arm64.go`, `ppc64.go`内の変更は、`cmd/asm`が特定のアセンブリ命令が「ジャンプ命令」であると認識するためのロジックを更新しています。

*   **`armJump` および `arm64Jump` マップへの `"JMP": true` の追加**:
    これらのマップは、ARMおよびARM64アーキテクチャにおいて、どのニーモニックがジャンプ命令として扱われるべきかを定義しています。`"JMP": true`を追加することで、アセンブラは`JMP`という命令を、他の`B`や`BL`のような分岐命令と同様に、ジャンプ命令として正しく分類できるようになります。これにより、アセンブラの内部処理（例えば、命令の相対アドレス解決や最適化など）が`JMP`命令に対しても適切に適用されるようになります。

*   **`jumpPPC64` 関数の `switch` 文への `"JMP"` の追加**:
    PPC64アーキテクチャでは、`jumpPPC64`関数が同様の目的を果たします。`switch`文の`case`リストに`"JMP"`を追加することで、PPC64のアセンブラも`JMP`をジャンプ命令として認識し、適切な処理を行うことができるようになります。

これらの変更は、アセンブラが命令のセマンティクス（意味）を理解するための基盤を強化するものです。

### `src/cmd/old5a/lex.go` および `src/cmd/old9a/lex.go` の変更

これらのファイルは、アセンブラの字句解析フェーズにおいて、アセンブリ命令のニーモニックを内部的な命令コードに変換する役割を担っています。`lexinit`配列は、ニーモニック文字列とそれに対応する命令コードのマッピングを定義する`asm.Lextab`構造体のリストです。

*   **`"JMP"` を `arm.AB` / `ppc64.ABR` にマッピング**:
    `JMP`は無条件ジャンプを表す汎用的な命令名です。ARMアーキテクチャでは`B`（Branch）が、PPC64アーキテクチャでは`BR`（Branch Register）が無条件ジャンプの主要な命令です。この変更により、アセンブラが`JMP`という文字列を読み込んだ際に、内部的にはそれぞれ`arm.AB`または`ppc64.ABR`として解釈されるようになります。これにより、開発者は`JMP`というより一般的な名前を使用しながらも、アセンブラはアーキテクチャ固有の正しい機械語命令を生成できます。

*   **`"CALL"` を `arm.ABL` / `ppc64.ABL` にマッピング**:
    `CALL`はサブルーチン呼び出しを表す汎用的な命令名です。ARMおよびPPC64アーキテクチャでは、`BL`（Branch with Link）がサブルーチン呼び出しに使用され、戻りアドレスをリンクレジスタに保存します。この変更により、アセンブラが`CALL`という文字列を読み込んだ際に、内部的にはそれぞれ`arm.ABL`または`ppc64.ABL`として解釈されるようになります。これにより、`CALL`命令が正しくサブルーチン呼び出しとして処理され、戻りアドレスの保存などの関連する動作が保証されます。

これらの変更は、アセンブラの字句解析器が`JMP`と`CALL`というエイリアスを、各アーキテクチャのネイティブなジャンプ/コール命令に変換するための「辞書」を更新するものです。これにより、アセンブリコードの記述がより柔軟になり、異なるアーキテクチャ間でのコードの移植性が向上します。

### テストケースの追加

`testdata`ディレクトリ内の`.s`ファイルと`.out`ファイルの変更は、この修正が正しく機能することを検証するためのものです。新しいテストケースは、実際に`JMP`と`CALL`命令を含むアセンブリコードを記述し、それが期待通りにアセンブルされることを確認します。これにより、このコミットによって導入された機能が安定しており、将来の変更によって意図せず壊れることがないように保証されます。

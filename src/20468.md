# [インデックス 20468] ファイルの概要

このコミットは、GoランタイムにおけるWindows 32ビット (386) アーキテクチャでのビルド問題を修正するものです。主な変更点は、GoとC言語の相互作用のために割り当てられるシステムスタックのサイズを調整することと、アセンブリコードにレジスタの保存に関するコメントを追加することです。この問題は、`profileloop`関数の実行とスタックガードの設定に関連していました。

## 変更の背景

このコミットは、GoランタイムのWindows 32ビット (386) 環境でのビルドが正しく機能しない問題を解決するために行われました。コミットメッセージによると、この問題は`profileloop`関数が正しく実行されないことに関連しており、その原因はスタックガードの設定方法にありました。

以前のコード（"old code"）では、`stackguard`が`stack.lo`に設定されていたのに対し、新しいコード（"new (from earlier) code"）では`stackguard = stack.lo + StackGuard`と設定されていました。この512バイトの差が`profileloop`関数の実行に影響を与えていたとされています。つまり、`stackguard`が不適切に設定されていたために、ランタイムが利用できるスタック領域が想定よりも狭くなり、`profileloop`のような特定のランタイム関数がスタック不足で正常に動作しなかったと考えられます。

この問題を解決するため、GoとC言語の相互運用時に使用されるシステムスタックのサイズを、従来の4KBから8KBに倍増させる変更が導入されました。これにより、`profileloop`を含むランタイム操作に必要な十分なスタック空間が確保され、Windows/386ビルドでの安定性が向上しました。また、`memclr`関数に関するコメントの追加は、Windowsの`externalthreadhandler`が特定のレジスタ状態を期待することに対応するためのもので、互換性と堅牢性を高める目的があります。

## 前提知識の解説

このコミットの変更内容を深く理解するためには、以下のGoランタイムおよびシステムプログラミングに関する概念を理解しておく必要があります。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルな部分です。これには、ガベージコレクション、ゴルーチンのスケジューリング、メモリ管理、スタック管理などが含まれます。Goプログラムは、オペレーティングシステム上で直接実行されるのではなく、このランタイムを介して実行されます。
*   **スタック (Stack)**: プログラム実行中に、関数呼び出しの引数、ローカル変数、戻りアドレスなどを一時的に格納するために使用されるメモリ領域です。Goでは、各ゴルーチンが独自のスタックを持っています。スタックは通常、メモリの高いアドレスから低いアドレスに向かって成長します。
*   **スタックガード (Stack Guard)**: スタックオーバーフロー（スタックが割り当てられたメモリ領域を超えて成長すること）を防ぐためのメカニズムです。スタックの境界近くに「ガードページ」と呼ばれる特別な領域を設定し、スタックポインタがこのガードページに触れると、ランタイムがスタックの拡張（またはエラー処理）を行います。これにより、スタックが枯渇する前に適切な処理を行うことができます。
*   **`stack.lo`**: Goランタイムが管理するスタックの最下部（最も低いアドレス）を示すポインタです。スタックは`stack.lo`から`stack.hi`（最も高いアドレス）に向かって成長します。
*   **`StackGuard`**: スタックガードのオフセット値です。`stack.lo + StackGuard`がスタックガードの実際の位置を示します。スタックポインタがこの位置を下回ると、スタックオーバーフローの可能性が検出されます。
*   **`profileloop`**: Goランタイム内部のプロファイリング関連の関数です。CPUプロファイリングやメモリプロファイリングなどのために、定期的に実行され、スタックの使用状況などを監視する役割を担います。この関数自体がスタックを消費するため、スタックサイズが不十分だと問題を引き起こす可能性があります。
*   **Windows/386**: Microsoft Windowsオペレーティングシステム上で動作する32ビットIntel x86アーキテクチャを指します。Goは様々なアーキテクチャとOSの組み合わせをサポートしており、それぞれに特化したランタイムコードが存在します。
*   **アセンブリ言語 (Assembly Language)**: CPUが直接理解できる機械語に非常に近い低レベルなプログラミング言語です。Goランタイムの特にパフォーマンスが要求される部分や、OSとの低レベルなインタラクションを行う部分は、アセンブリ言語で記述されることがあります。
*   **レジスタ (Registers)**: CPU内部にある非常に高速な記憶領域です。データやメモリアドレスを一時的に保持するために使用されます。`DX`はIntel x86アーキテクチャにおける汎用データレジスタの一つです。アセンブリコードでは、特定のレジスタが特定の目的で使用されることが多く、関数呼び出し規約によってレジスタの保存・復元が義務付けられている場合があります。
*   **`externalthreadhandler`**: WindowsのGoランタイムにおいて、Goランタイムが管理していない外部スレッド（例えば、C言語のライブラリからGo関数が呼び出された場合など）からの呼び出しを処理するためのハンドラです。Goランタイムのコンテキストに切り替える役割を担います。

## 技術的詳細

このコミットは、主にGoランタイムのスタック管理とレジスタの取り扱いに関する2つの側面で技術的な変更を加えています。

1.  **システムスタックサイズの調整 (`src/runtime/sys_windows_386.s`)**:
    *   コミットの核心は、Windows 32ビット環境におけるGoとC言語の相互運用時に使用されるシステムスタックのサイズを増やすことです。
    *   変更前は、`runtime·externalthreadhandler`関数内でスタックポインタ`SP`から`-4096`バイト（4KB）のオフセットを引いて新しいスタックフレームの開始位置を計算していました (`LEAL -4096(SP), CX`)。
    *   このコミットでは、このオフセットを`-8192`バイト（8KB）に倍増させています (`LEAL -8192(SP), CX`)。
    *   この変更により、`externalthreadhandler`がGoランタイムのコンテキストに切り替える際に、より大きなスタック空間が確保されるようになります。コミットメッセージが示唆するように、以前のスタックサイズでは`profileloop`のようなランタイム関数が実行される際にスタック不足に陥り、ビルド問題を引き起こしていました。8KBへの増量は、これらのランタイム操作に十分な余裕を提供し、スタックオーバーフローのリスクを軽減します。
    *   このスタックサイズの増加は、特にGoとCのコードが頻繁に相互作用するシナリオで重要です。CコードがGoランタイムにコールバックしたり、GoがCライブラリを呼び出したりする場合、両方のスタック要件を考慮する必要があります。

2.  **`memclr`関数におけるDXレジスタ保存の注意喚起 (`src/runtime/memclr_386.s`, `src/runtime/memclr_amd64.s`)**:
    *   `memclr`はメモリ領域をゼロクリアするアセンブリ関数です。このような低レベル関数は、通常、パフォーマンスのためにレジスタを自由に利用し、その値を破壊する可能性があります。
    *   このコミットでは、`src/runtime/memclr_386.s`と`src/runtime/memclr_amd64.s`の両方に、`// NOTE: Windows externalthreadhandler expects memclr to preserve DX.`というコメントが追加されています。
    *   これは、Windowsの`externalthreadhandler`が`memclr`を呼び出す際に、`DX`レジスタの特定の値を期待していることを示しています。つまり、`memclr`関数が`DX`レジスタの値を変更してはならない、あるいは変更した場合は`externalthreadhandler`が期待する状態に復元しなければならないという制約があることを開発者に警告しています。
    *   このようなレジスタの保存要件は、Windowsのシステムコール規約や特定のAPIの動作に起因することが多いです。`DX`レジスタが特定のシステム情報やエラーコードを保持している場合、その値が`memclr`によって破壊されると、後続の処理で問題が発生する可能性があります。このコメントは、将来のコード変更やデバッグ作業において、この重要な制約を見落とさないようにするためのものです。

これらの変更は、GoランタイムがWindows 32ビット環境でより堅牢かつ安定して動作するための基盤を強化するものです。特に、スタック管理の正確性とレジスタの適切な取り扱いは、低レベルなシステムプログラミングにおいて極めて重要です。

## コアとなるコードの解説

### `src/runtime/memclr_386.s` および `src/runtime/memclr_amd64.s` へのコメント追加

これらの変更は、`memclr`アセンブリ関数（メモリをゼロクリアする関数）の動作に関する重要な制約を開発者に伝えるためのものです。追加されたコメント `// NOTE: Windows externalthreadhandler expects memclr to preserve DX.` は、Windowsの`externalthreadhandler`が`memclr`を呼び出す際に、`DX`レジスタの値を変更しないことを期待していることを示しています。

通常、アセンブリ言語で書かれた低レベル関数は、パフォーマンスのためにレジスタを自由に利用し、その内容を破壊することがあります。しかし、特定のシステムコールやAPI（この場合は`externalthreadhandler`）が`DX`レジスタに特定の情報（例えば、エラーコードやスレッドコンテキストの一部）を格納しており、その値が`memclr`の実行後も保持されることを期待している場合、`memclr`は`DX`レジスタの値を保存し、関数終了時に復元する責任を負う必要があります。このコメントは、将来の変更やデバッグの際に、この暗黙の契約を見落とさないようにするための重要な注意喚起です。

### `src/runtime/sys_windows_386.s` の変更

このファイルにおける変更は、Windows 32ビット環境でのGoランタイムのスタック管理に直接影響を与えます。

*   **`LEAL -4096(SP), CX` から `LEAL -8192(SP), CX` への変更**:
    *   `LEAL` (Load Effective Address) 命令は、オペランドのアドレスを計算し、その結果をレジスタにロードします。ここでは、スタックポインタ`SP`から特定のオフセットを引くことで、新しいスタックフレームの開始位置を計算しています。
    *   `-4096(SP)` は、現在のスタックポインタから4096バイト（4KB）低いアドレスを指します。これは、以前のシステムスタックの初期サイズが4KBであったことを意味します。
    *   `-8192(SP)` への変更は、このオフセットを8192バイト（8KB）に倍増させることを意味します。これにより、`runtime·externalthreadhandler`がGoランタイムのコンテキストに切り替える際に、より大きなシステムスタックが割り当てられるようになります。
    *   このスタックサイズの増加は、特にGoとCの相互運用において、より多くのスタック空間が必要となる場合に、スタックオーバーフローを防ぐために重要です。コミットメッセージで言及されているように、`profileloop`のようなランタイム関数が実行される際に、この追加のスタック空間が問題解決に寄与します。

*   **`MOVL CX, (g_stack+stack_lo)(SP)`**:
    *   計算された新しいスタックの最下部のアドレス（`CX`レジスタの値）を、現在のGoルーチン構造体`g`の`stack_lo`フィールドに格納しています。これは、Goランタイムが現在のゴルーチンのスタックの有効な境界を認識し、スタックの拡張やスタックオーバーフロー検出のために使用するために不可欠です。

*   **`ADDL $const_StackGuard, CX` および `MOVL CX, g_stackguard0(SP)`**:
    *   `stack_lo`に`const_StackGuard`（スタックガードのオフセット定数）を加算し、その結果を`g_stackguard0`に設定しています。`g_stackguard0`は、現在のゴルーチンのスタックガードの値を保持するフィールドです。
    *   この操作は、スタックオーバーフローを検出するためのスタックガードの正確な位置を設定するものです。コミットメッセージで言及されている「`stackguard = stack.lo + StackGuard`」という正しい計算がここで行われていることを示唆しており、以前の不適切な設定（`stackguard = stack.lo`）による問題を修正または緩和する役割を果たしています。

これらの変更は、GoランタイムがWindows 32ビット環境でより堅牢かつ安定して動作するための基盤を強化するものであり、特にスタック管理の正確性とレジスタの適切な取り扱いは、低レベルなシステムプログラミングにおいて極めて重要です。

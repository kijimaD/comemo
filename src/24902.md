# [インデックス 24902] ファイルの概要

このコミットは、Goコンパイラの内部構造において、MIPS64アーキテクチャのサポートを追加するための準備作業として、`cmd/internal/obj/ppc64`ディレクトリの内容を`cmd/internal/obj/mips`ディレクトリに機械的にコピーし、ファイル名をリネームしたものです。コード自体には変更が加えられていません。

## 変更の背景

このコミットの主な背景は、Go言語のツールチェインにMIPS64アーキテクチャのサポートを追加する準備です。Goコンパイラは、異なるCPUアーキテクチャ向けにコードを生成するために、各アーキテクチャ固有の命令セット、レジスタ、アドレッシングモードなどを定義した内部パッケージを持っています。`cmd/internal/obj`はそのようなアーキテクチャ固有のオブジェクトファイル生成ロジックを格納する場所です。

MIPS64のサポートをゼロから実装するのではなく、既存のPowerPC 64-bit (ppc64) アーキテクチャの実装をベースとしてコピーすることで、開発効率を高め、将来的なコードの差分管理を容易にすることが目的です。ppc64とmips64は異なるアーキテクチャですが、どちらも64ビットであり、アセンブラの構造やオブジェクトファイルの扱い方において共通する部分があるため、ppc64のコードをテンプレートとして利用することが合理的と判断されました。これにより、MIPS64固有の変更を適用する際に、既存のコードとの差分を最小限に抑え、段階的に開発を進めることができます。

## 前提知識の解説

このコミットを理解するためには、以下の知識が役立ちます。

1.  **Goコンパイラの構造**: Goコンパイラは、ソースコードを中間表現に変換し、最終的にターゲットアーキテクチャの機械語にコンパイルします。このプロセスには、アセンブラ、リンカ、オブジェクトファイルフォーマットの定義などが含まれます。
2.  **`cmd/internal/obj`パッケージ**: Goのソースツリーにおける`src/cmd/internal/obj`ディレクトリは、Goコンパイラのバックエンドの一部であり、各CPUアーキテクチャ（例: amd64, arm, ppc64など）向けのアセンブラ命令、レジスタ定義、オブジェクトファイルフォーマットなどを定義しています。これにより、コンパイラは異なるアーキテクチャに対応した機械語を生成できます。
3.  **アセンブラとオブジェクトファイル**:
    *   **アセンブラ**: 人間が読みやすいアセンブリ言語のコードを、CPUが直接実行できる機械語（バイナリコード）に変換するプログラムです。
    *   **オブジェクトファイル**: アセンブラによって生成された機械語コードやデータ、シンボル情報などが含まれるファイルです。これらはリンカによって結合され、最終的な実行可能ファイルが作成されます。
    *   **`a.out.go`**: オブジェクトファイルフォーマットに関連する定数や構造体を定義するファイルです。Goのツールチェインでは、伝統的なUnixの`a.out`フォーマットに由来する命名規則が使われることがあります。
    *   **`anames.go`, `anames0.go`**: アセンブラ命令の名前（ニーモニック）や、オペランドのクラス（レジスタ、即値、メモリ参照など）を定義するファイルです。
    *   **`asm0.go`**: アセンブリ命令のエンコーディングロジックや、命令のオペランドの型チェック、命令のサイズ計算など、アセンブラのコアロジックが含まれるファイルです。
    *   **`list0.go`**: アセンブリコードのリスト表示やデバッグに関連するユーティリティが含まれることがあります。
    *   **`obj0.go`**: オブジェクトファイルの生成やシンボル解決など、オブジェクトファイル処理の共通ロジックが含まれることがあります。
4.  **MIPS64とPowerPC64**: どちらも64ビットのRISCアーキテクチャですが、命令セット、レジスタ構成、アドレッシングモードなどは異なります。しかし、64ビットという共通点から、アセンブラの設計やオブジェクトファイルの構造において、ある程度の抽象化や共通のパターンが存在する可能性があります。このコミットでは、その共通性を利用してppc64のコードをmips64のベースとしています。
5.  **コード差分 (Code Difference)**: 大規模なソフトウェアプロジェクトでは、新しい機能やアーキテクチャを追加する際に、既存の類似コードをコピーして開発を始めることがあります。これにより、初期開発の速度を上げることができますが、元のコードが変更された際に、コピーしたコードにも同様の変更を適用する必要が生じ、差分管理が複雑になる可能性があります。このコミットの目的は、MIPS64ポートの初期段階で、ppc64とのコード差分を「ゼロ」にすることで、将来の変更管理を容易にすることにあります。

## 技術的詳細

このコミットは、Goコンパイラの`cmd/internal/obj`パッケージ内に、MIPS64アーキテクチャ向けのアセンブラおよびオブジェクトファイル処理の基盤を構築する第一歩です。具体的には、以下のファイルが`src/cmd/internal/obj/ppc64`から`src/cmd/internal/obj/mips`へコピーされ、ファイル名が変更されました。

*   `src/cmd/internal/obj/mips/a.out.go`
*   `src/cmd/internal/obj/mips/anames.go`
*   `src/cmd/internal/obj/mips/anames0.go`
*   `src/cmd/internal/obj/mips/asm0.go`
*   `src/cmd/internal/obj/mips/list0.go`
*   `src/cmd/internal/obj/mips/obj0.go`

これらのファイルは、PowerPC 64-bitアーキテクチャのアセンブラ命令、レジスタ定義、オブジェクトファイルフォーマット、およびアセンブリコード生成ロジックを定義しています。コミットメッセージが明示しているように、この時点では**コード内容自体はPowerPC64のものであり、MIPS64固有の変更は一切含まれていません**。

この「機械的なコピー」戦略の技術的な利点は以下の通りです。

1.  **開発の迅速化**: 既存の動作するコードベースを再利用することで、MIPS64ポートの初期セットアップにかかる時間を大幅に短縮できます。ゼロから始めるよりも、既知の構造とパターンを持つコードを修正する方が効率的です。
2.  **構造の一貫性**: Goコンパイラの各アーキテクチャバックエンドは、同様のファイル構造と設計パターンに従っています。ppc64の構造をコピーすることで、MIPS64のバックエンドもこの一貫性を保ちやすくなります。
3.  **差分管理の簡素化**: MIPS64固有の変更を加える前に、まずppc64のコードを完全にコピーすることで、初期のコード差分を「ゼロ」にします。これにより、MIPS64固有の機能が追加される際に、どの部分がMIPS64のために変更されたのかが明確になり、コードレビューやデバッグが容易になります。もしppc64のコードにバグ修正や改善があった場合、MIPS64のコードにも同様の変更を適用する際に、ベースラインが同じであるため、マージが比較的容易になります。
4.  **テストハーネスの再利用**: アセンブラやオブジェクトファイル処理のコードは、多くの場合、複雑なテストケースを必要とします。ppc64のコードをコピーすることで、そのテストハーネスやテスト戦略もMIPS64に適用しやすくなり、新しいアーキテクチャの正確性を検証するのに役立ちます。

このコミットは、MIPS64アーキテクチャのGoサポートを段階的に導入する戦略の一部であり、今後のMIPS64固有の命令セット、レジスタ、最適化などの実装に向けた土台を築くものです。

## コアとなるコードの変更箇所

このコミットでは、既存のファイルの変更や削除は一切なく、以下の6つの新しいファイルが`src/cmd/internal/obj/mips/`ディレクトリに作成されました。

*   `src/cmd/internal/obj/mips/a.out.go`
*   `src/cmd/internal/obj/mips/anames.go`
*   `src/cmd/internal/obj/mips/anames0.go`
*   `src/cmd/internal/obj/mips/asm0.go`
*   `src/cmd/internal/obj/mips/list0.go`
*   `src/cmd/internal/obj/mips/obj0.go`

これらのファイルの内容は、`src/cmd/internal/obj/ppc64/`ディレクトリにある同名のファイルから完全にコピーされたものです。例えば、`src/cmd/internal/obj/mips/a.out.go`の冒頭には、`package ppc64`という記述が残っており、これはまだMIPS64向けに修正されていないことを示しています。

```go
// src/cmd/internal/obj/mips/a.out.go の一部
package ppc64 // ここがまだppc64のまま

import "cmd/internal/obj"

//go:generate go run ../stringer.go -i $GOFILE -o anames.go -p ppc64

/*
 * powerpc 64
 */
const (
	NSNAME = 8
	NSYM   = 50
	NREG   = 32 /* number of general registers */
	NFREG  = 32 /* number of floating point registers */
)

const (
	REG_R0 = obj.RBasePPC64 + iota
	REG_R1
	// ... (PowerPC64のレジスタ定義が続く)
)
```

同様に、`asm0.go`や`anames.go`などのファイルも、PowerPC64の命令セットやレジスタ、オペランドクラスの定義を含んでいます。

## コアとなるコードの解説

このコミットで追加されたファイル群は、Goコンパイラが特定のアーキテクチャ向けのアセンブリコードを生成し、オブジェクトファイルを処理するために必要な定義とロジックの集合体です。

*   **`a.out.go`**:
    *   このファイルは、PowerPC64アーキテクチャのオブジェクトファイルフォーマットに関連する定数や、レジスタの定義を含んでいます。例えば、`REG_R0`から`REG_R31`までの汎用レジスタ、`REG_F0`から`REG_F31`までの浮動小数点レジスタ、条件レジスタ（`REG_CR0`など）、特殊目的レジスタ（`REG_LR`, `REG_CTR`, `REG_XER`など）が定義されています。
    *   また、アセンブラ命令のオペランドの型を表す定数（`C_REG`, `C_FREG`, `C_SCON`, `C_LCON`など）も定義されており、これらはアセンブラが命令を解析し、適切な機械語に変換する際に使用されます。
    *   `AADD`, `AMOV`, `AFADD`などのPowerPC64固有のアセンブラ命令のニーモニックも定義されています。
*   **`anames.go`**:
    *   `a.out.go`で定義されたアセンブラ命令のニーモニックに対応する文字列名を格納する`Anames`配列を定義しています。これは主にデバッグやエラーメッセージの表示に使用されます。
*   **`anames0.go`**:
    *   オペランドクラスの文字列名を格納する`cnames9`配列を定義しています。これもデバッグやエラーメッセージ用です。
*   **`asm0.go`**:
    *   このファイルは、アセンブラの最も重要な部分の一つであり、アセンブリ命令を機械語に変換するロジック（`asmout`関数など）や、命令のオペランドの型を分類するロジック（`aclass`関数）、命令の最適なエンコーディングを選択するためのテーブル（`optab`）などが含まれています。
    *   `oplook`関数は、与えられたアセンブリ命令とそのオペランドの型に基づいて、`optab`から適切な命令エンコーディングルール（`Optab`構造体）を検索します。
    *   `span9`関数は、Goの関数に対応するアセンブリコードのレイアウトを決定し、命令のサイズを計算し、必要に応じて分岐命令の最適化（例: 長い分岐を短い分岐とジャンプの組み合わせに変換）を行います。
    *   `buildop`関数は、`optab`を初期化し、オペランドクラス間の互換性マトリックス（`xcmp`）を構築します。
*   **`list0.go`**:
    *   このファイルはコミットの差分には含まれていませんが、通常はアセンブリコードのリスト表示やデバッグ出力に関連するユーティリティ関数が含まれます。
*   **`obj0.go`**:
    *   このファイルもコミットの差分には含まれていませんが、通常はオブジェクトファイルの生成、シンボルテーブルの管理、リロケーション処理など、オブジェクトファイル処理の共通的なロジックが含まれます。

現時点では、これらのファイルはMIPS64アーキテクチャ向けに機能するわけではありません。これらはあくまでPowerPC64のコードのコピーであり、MIPS64の命令セット、レジスタ、アドレッシングモードに合わせて大幅な修正が必要になります。このコミットは、その修正作業を開始するための「空のキャンバス」を提供したと考えることができます。

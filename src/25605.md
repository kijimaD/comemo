## 変更の背景

Go言語は、その並行処理モデルとガベージコレクションによって、現代のマルチコアプロセッサを最大限に活用できる設計がされています。しかし、異なるCPUアーキテクチャ上でGoプログラムが正しく、かつ高性能に動作するためには、そのアーキテクチャ固有の特性を考慮した低レベルな実装が必要不可欠です。特に、複数のゴルーチン（Goの軽量スレッド）が共有データにアクセスする際に、データの整合性を保つためには「アトミック操作」が必須となります。

このコミットが行われた背景には、Go言語がMIPS64およびMIPS64LE（MIPS64 Little Endian）アーキテクチャへのサポートを拡大する動きがありました。これらのアーキテクチャ上で`sync/atomic`パッケージが提供するアトミック操作を効率的かつ正確に実現するためには、C言語やGo言語で記述された高レベルなコードだけでは不十分であり、MIPS64の命令セットを直接利用したアセンブリコードが必要とされました。

アトミック操作は、例えばカウンタのインクリメント、共有ポインタの交換、ロックフリーデータ構造の実装など、並行プログラミングにおける多くの基本的な構成要素となります。これらの操作がアトミックでない場合、複数のゴルーチンが同時にアクセスした際に競合状態（Race Condition）が発生し、データ破損や予期せぬプログラムの振る舞いを引き起こす可能性があります。MIPS64アーキテクチャに特化したアセンブリコードを導入することで、Goランタイムはこれらの重要な操作をハードウェアレベルで保証し、MIPS64環境でのGoプログラムの安定性とパフォーマンスを向上させます。

## 前提知識の解説

### アトミック操作 (Atomic Operations)

アトミック操作とは、複数のCPUコアやスレッドから同時にアクセスされた場合でも、その操作全体が不可分（indivisible）かつ中断不可能（uninterruptible）であることを保証する操作のことです。つまり、あるアトミック操作が実行されている最中に、他のCPUコアやスレッドがその操作の途中の状態を観測したり、割り込んだりすることはできません。これにより、並行処理におけるデータ競合を防ぎ、共有データの整合性を保つことができます。

Go言語の`sync/atomic`パッケージは、このようなアトミック操作をGoプログラムから利用するためのAPIを提供しています。例えば、`AddInt32`は32ビット整数をアトミックに加算し、`CompareAndSwapUint64`は指定されたメモリ位置の値が期待値と一致した場合にのみ新しい値に交換します。

### Load-Linked/Store-Conditional (LL/SC) 命令ペア

多くのRISC（Reduced Instruction Set Computer）アーキテクチャ、特にMIPSでは、アトミック操作を実装するためにLoad-Linked (LL) とStore-Conditional (SC) という命令ペアが用いられます。これは、従来のTest-and-Setのような単一のアトミック命令がない場合に、ソフトウェアでアトミック性を実現するためのメカニズムです。

*   **Load-Linked (LL)**: 指定されたメモリアドレスから値をロードし、そのアドレスに対する「リンク」または「監視」を開始します。このリンクは、そのアドレスのメモリ内容が他のプロセッサによって変更された場合に無効になります。
*   **Store-Conditional (SC)**: 指定されたメモリアドレスに値をストアしようとします。このストア操作は、LL命令以降、監視対象のメモリアドレスが他のプロセッサによって変更されていない場合にのみ成功します。もし変更されていた場合（リンクが無効になっている場合）、SCは失敗し、ストアは行われません。

LL/SC命令ペアは通常、以下のようなループ構造で使用されます。

1.  LL命令でメモリから値を読み込む。
2.  読み込んだ値に対して必要な計算や変更を行う。
3.  SC命令で新しい値をメモリに書き込もうとする。
4.  SCが成功した場合、アトミック操作は完了。
5.  SCが失敗した場合（他のプロセッサがその間にメモリを変更した）、操作全体を最初からやり直す（LL命令に戻る）。

このメカニズムにより、競合が発生した場合でもデータの一貫性が保たれ、最終的には操作がアトミックに完了することが保証されます。

### メモリバリア (Memory Barriers) / メモリフェンス (Memory Fences) (SYNC)

メモリバリア（またはメモリフェンス）は、プロセッサやコンパイラによる命令の並べ替え（Reordering）を制限するための命令です。現代のプロセッサは、性能向上のために命令の実行順序を最適化することがありますが、並行処理においてはこれが問題となることがあります。例えば、あるCPUコアが共有変数Aを書き込み、その後に共有変数Bを書き込んだとしても、別のCPUコアからはBの変更がAの変更よりも先に観測される可能性があります。

メモリバリアは、特定の命令の前後でメモリ操作の順序を強制します。このコミットで使用されている`SYNC`命令は、MIPSアーキテクチャにおけるメモリバリアの一種であり、それ以前のメモリ操作が完了し、それ以降のメモリ操作が開始される前に、メモリの一貫性を保証する役割を果たします。これにより、アトミック操作の前後でメモリの状態が正しく同期され、他のCPUコアから見たメモリの可視性が保証されます。

### MIPS64 / MIPS64LE アーキテクチャ

MIPS (Microprocessor without Interlocked Pipeline Stages) は、RISC（Reduced Instruction Set Computer）の代表的なアーキテクチャの一つです。MIPS64は、その64ビット版であり、64ビット幅のレジスタとアドレス空間を持ちます。MIPS64LEは、MIPS64のLittle Endian（リトルエンディアン）版を指します。エンディアンとは、複数バイトのデータをメモリに格納する際のバイト順序のことで、Little Endianでは最下位バイトが最も小さいアドレスに格納されます。Go言語は、様々なアーキテクチャをサポートしており、MIPS64/MIPS64LEもその対象となります。

### Goアセンブリ (Plan 9スタイル)

Go言語は、独自の（Plan 9由来の）アセンブリ言語構文を使用します。これは一般的なGAS (GNU Assembler) 構文とは異なり、レジスタの命名規則や命令の記述方法に特徴があります。例えば、レジスタは`R1`, `R2`のように表記され、メモリ参照は`offset(base_register)`の形式を取ります。また、関数定義には`TEXT`ディレクティブが使われ、`SB` (Static Base) はグローバルシンボルやスタティックデータへのオフセット計算の基準となります。`FP` (Frame Pointer) は関数の引数やローカル変数へのアクセスに使われます。

## 技術的詳細

このコミットで追加された`src/sync/atomic/asm_mips64x.s`ファイルは、MIPS64およびMIPS64LEアーキテクチャ向けに、Goの`sync/atomic`パッケージが提供する以下の主要なアトミック操作をアセンブリ言語で実装しています。

*   `SwapInt32`, `SwapUint32`, `SwapInt64`, `SwapUint64`, `SwapUintptr`
*   `CompareAndSwapInt32`, `CompareAndSwapUint32`, `CompareAndSwapInt64`, `CompareAndSwapUint64`, `CompareAndSwapUintptr`
*   `AddInt32`, `AddUint32`, `AddInt64`, `AddUint64`, `AddUintptr`
*   `LoadInt32`, `LoadUint32`, `LoadInt64`, `LoadUint64`, `LoadUintptr`, `LoadPointer`
*   `StoreInt32`, `StoreUint32`, `StoreInt64`, `StoreUint64`, `StoreUintptr`

これらの実装は、MIPS64プロセッサが提供する**Load-Linked (LL)** と**Store-Conditional (SC)** 命令ペアを核としています。LL/SCは、マルチプロセッサ環境下でのアトミック性を保証するための重要なプリミティブです。

### LL/SC命令の利用

*   **32ビット操作**: `LL` (Load-Linked Word) と `SC` (Store-Conditional Word) が使用されます。
*   **64ビット操作**: `LLV` (Load-Linked Doubleword) と `SCV` (Store-Conditional Doubleword) が使用されます。MIPS64は64ビットアーキテクチャであるため、64ビット幅のデータに対するアトミック操作にはこれらの命令が使われます。

### メモリバリア (SYNC)

各アトミック操作の前後には、`SYNC`命令が挿入されています。これはMIPSのメモリバリア命令であり、それ以前のメモリ操作が完了し、それ以降のメモリ操作が開始される前に、メモリの一貫性を保証します。これにより、コンパイラやプロセッサによる命令の並べ替えが原因でアトミック操作の意図が損なわれることを防ぎ、複数のCPUコア間でのメモリ可視性を保証します。

### リトライループ

LL/SC命令ペアは、競合が発生した場合にSC命令が失敗する可能性があるため、操作が成功するまでリトライするループ構造を必要とします。
例えば、`SwapUint32`では、`BEQ R3, -3(PC)`という命令がSC命令の直後にあり、SCが失敗した場合には3命令前（LL命令の直前）に戻って操作をやり直します。
`CompareAndSwapUint32`や`AddUint32`などでも同様に、SC命令の成功をチェックし、失敗した場合はラベル（`cas_again`など）に戻ってリトライするロジックが組み込まれています。

### 型のエイリアシング

Goの`sync/atomic`パッケージは、`Int32`と`Uint32`、`Int64`と`Uint64`、`Uintptr`と`Pointer`など、符号付き/符号なし整数やポインタ型に対して同じアトミック操作を提供します。MIPS64のアセンブリ実装では、これらの型間で基本的なアトミック操作のロジックが同じであるため、`JMP`命令を使って対応する`Uint`バージョンの関数にジャンプさせることで、コードの重複を避けています。例えば、`SwapInt32`は`SwapUint32`にジャンプします。

### レジスタの使用

MIPS64のアセンブリコードでは、以下のレジスタが主に利用されています。

*   `R1`, `R2`, `R3`, `R4`, `R5`: 汎用レジスタとして、アドレス、値、一時的な計算結果などを保持するために使用されます。
*   `FP` (Frame Pointer): 関数の引数や戻り値のアドレス計算の基準となります。例えば、`addr+0(FP)`は第一引数`addr`のアドレスを示します。
*   `SB` (Static Base): グローバルシンボルやスタティックデータへのオフセット計算の基準となります。

## コアとなるコードの解説

`asm_mips64x.s`ファイル内の主要なアトミック操作の実装について、そのロジックを詳細に解説します。

### `SwapUint32` (32ビット値のアトミック交換)

```assembly
TEXT ·SwapUint32(SB),NOSPLIT,$0-20
	MOVV	addr+0(FP), R2  // 第一引数 addr (交換対象のアドレス) を R2 にロード
	MOVW	new+8(FP), R5   // 第二引数 new (新しい値) を R5 にロード
	SYNC                    // メモリバリア: 以降の操作の前にメモリ状態を同期
	MOVV	R5, R3          // 新しい値 R5 を R3 にコピー (SC命令のソースレジスタとして使用)
loop:
	LL(2, 1)	// R1 = *R2 (addr が指すメモリから値をロードし、リンクを設定)
	SC(2, 3)	// *R2 = R3 (addr が指すメモリに R3 の値をストア。リンクが無効なら失敗)
	BEQ	R3, loop        // SCが失敗した場合 (R3が0になる)、loop に戻ってリトライ
	MOVW	R1, old+16(FP)  // 成功した場合、LLで読み込んだ元の値 R1 を戻り値 old に格納
	SYNC                    // メモリバリア: 以前の操作が完了したことを保証
	RET                     // 関数からリターン
```
この関数は、指定されたアドレス`addr`にある32ビットの値を`new`でアトミックに交換し、元の値を返します。LL/SC命令ペアとリトライループを用いて、競合状態を回避しています。

### `SwapUint64` (64ビット値のアトミック交換)

`SwapUint64`は`SwapUint32`とほぼ同じロジックですが、64ビット値を扱うため`MOVV` (Move Value, 64ビット) と`LLV`/`SCV` (Load-Linked/Store-Conditional Doubleword) 命令を使用します。

```assembly
TEXT ·SwapUint64(SB),NOSPLIT,$0-24
	MOVV	addr+0(FP), R2
	MOVV	new+8(FP), R5
	SYNC
	MOVV	R5, R3
loop:
	LLV(2, 1)	// R1 = *R2 (64ビット値をロードし、リンクを設定)
	SCV(2, 3)	// *R2 = R3 (64ビット値をストア。リンクが無効なら失敗)
	BEQ	R3, loop
	MOVV	R1, old+16(FP)
	SYNC
	RET
```

```assembly
	MOVW	old+8(FP), R2   // 第二引数 old (期待値) を R2 にロード
	MOVW	new+12(FP), R5  // 第三引数 new (新しい値) を R5 にロード
	SYNC                    // メモリバリア
cas_again:
	MOVV	R5, R3          // 新しい値 R5 を R3 にコピー
	LL(1, 4)	// R4 = *R1 (addr が指すメモリから値をロードし、リンクを設定)
	BNE	R2, R4, cas_fail // ロードした値 R4 が期待値 R2 と異なる場合、cas_fail へ
	SC(1, 3)	// *R1 = R3 (addr が指すメモリに R3 の値をストア。リンクが無効なら失敗)
	BEQ	R3, cas_again   // SCが失敗した場合、cas_again に戻ってリトライ
	MOVV	$1, R1          // 成功した場合、戻り値 (swapped) を true (1) に設定
	MOVB	R1, swapped+16(FP) // swapped に 1 を格納
	SYNC                    // メモリバリア
	RET                     // 関数からリターン
cas_fail:
	MOVV	$0, R1          // 失敗した場合、戻り値 (swapped) を false (0) に設定
	JMP	-4(PC)          // swapped に 0 を格納する命令にジャンプ (MOVB R1, swapped+16(FP) の直前)
```
この関数は、`addr`にある32ビット値が`old`と等しい場合にのみ、その値を`new`にアトミックに交換します。交換が成功したかどうかを示すブール値を返します。LL/SCと条件分岐を組み合わせて実装されています。

### `AddUint32` (32ビット値のアトミック加算)

```assembly
TEXT ·AddUint32(SB),NOSPLIT,$0-20
	MOVV	addr+0(FP), R2  // 第一引数 addr (対象アドレス) を R2 にロード
	MOVW	delta+8(FP), R3 // 第二引数 delta (加算する値) を R3 にロード
	SYNC                    // メモリバリア
loop:
	LL(2, 1)	// R1 = *R2 (addr が指すメモリから値をロードし、リンクを設定)
	ADDU	R1, R3, R4      // ロードした値 R1 に delta R3 を加算し、結果を R4 に
	MOVV	R4, R1          // R4 の値を R1 にコピー (SC命令のソースレジスタとして使用)
	SC(2, 4)	// *R2 = R4 (addr が指すメモリに R4 の値をストア。リンクが無効なら失敗)
	BEQ	R4, loop        // SCが失敗した場合、loop に戻ってリトライ
	MOVW	R1, ret+16(FP)  // 成功した場合、加算後の値 R1 を戻り値 ret に格納
	SYNC                    // メモリバリア
	RET                     // 関数からリターン
```
この関数は、`addr`にある32ビット値に`delta`をアトミックに加算し、加算後の値を返します。LL/SCと算術演算を組み合わせた典型的なアトミック操作の実装です。

### `LoadUint32` (32ビット値のアトミックロード)

```assembly
TEXT ·LoadUint32(SB),NOSPLIT,$0-12
	MOVV	addr+0(FP), R1  // 第一引数 addr (対象アドレス) を R1 にロード
	SYNC                    // メモリバリア: ロード操作の前にメモリ状態を同期
	MOVWU	0(R1), R1       // R1 が指すアドレスから符号なし32ビット値をロード
	SYNC                    // メモリバリア: ロード操作の後にメモリ状態を同期
	MOVW	R1, val+8(FP)   // ロードした値 R1 を戻り値 val に格納
	RET                     // 関数からリターン
```
この関数は、`addr`にある32ビット値をアトミックに読み込みます。`SYNC`命令によって、このロード操作が他のメモリ操作に対して正しく順序付けられることが保証されます。

### `StoreUint32` (32ビット値のアトミックストア)

```assembly
TEXT ·StoreUint32(SB),NOSPLIT,$0-12
	MOVV	addr+0(FP), R1  // 第一引数 addr (対象アドレス) を R1 にロード
	MOVW	val+8(FP), R2   // 第二引数 val (ストアする値) を R2 にロード
	SYNC                    // メモリバリア: ストア操作の前にメモリ状態を同期
	MOVW	R2, 0(R1)       // R1 が指すアドレスに R2 の値をストア
	SYNC                    // メモリバリア: ストア操作の後にメモリ状態を同期
	RET                     // 関数からリターン
```
この関数は、`addr`に32ビット値`val`をアトミックに書き込みます。`SYNC`命令によって、このストア操作が他のメモリ操作に対して正しく順序付けられることが保証されます。

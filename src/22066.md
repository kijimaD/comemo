# [インデックス 22066] ファイルの概要

このコミットは、Goコンパイラの内部コードをC言語からGo言語へ再変換するプロセスの一部です。具体的には、`rsc.io/c2go`というツールを用いて、Goコンパイラ（`cmd/new6g`など）のソースコードを再度Go言語に変換し直したものです。これは、GoコンパイラがGo言語自身で記述される「セルフホスティング」への移行という、Goプロジェクトにおける重要なマイルストーンの一環として行われました。

## 変更の背景

このコミットは、GoコンパイラをC言語からGo言語へ移行する、いわゆる「セルフホスティング」プロジェクトの一環として行われました。Go言語の初期バージョンでは、コンパイラはC言語で書かれていました。しかし、Go言語が成熟するにつれて、コンパイラ自体をGo言語で記述することのメリットが明確になりました。

主な動機は以下の通りです。
*   **保守性の向上**: Go言語はC言語に比べて、コードの記述、デバッグ、保守が容易であると一般的に考えられています。
*   **開発者体験の向上**: コンパイラがGo言語で書かれることで、開発者はGo言語の専門知識のみで貢献できるようになり、学習曲線が緩和されます。
*   **ツールチェインの強化**: Go言語は、モジュール性、自動コード書き換え、単体テスト、プロファイリングなど、コンパイラ開発に不可欠な組み込みツールサポートが優れています。
*   **コミュニティの活性化**: プログラミング言語にとってセルフホスティングは「通過儀礼」と見なされることが多く、言語自体の周りに強力なコミュニティを育成します。

この移行は、`c2go`という専用の機械翻訳ツールを使用して、既存のC言語コードベースをGo言語に変換するという多段階の取り組みでした。Go 1.5で新しいセルフホスティングGoコンパイラが正式にリリースされ、2015年2月までに元のC言語実装は完全に削除されました。このコミットは、その移行期間中に、C言語のソースコードがマスターブランチへのマージによって変更されたため、再度`c2go`ツールで変換し直す必要が生じたことを示しています。

## 前提知識の解説

*   **セルフホスティングコンパイラ**: コンパイラ自身が、そのコンパイラがコンパイルする言語で書かれている状態を指します。GoコンパイラがGo言語で書かれている場合、それはセルフホスティングであると言えます。これにより、コンパイラ開発者はGo言語の知識のみでコンパイラを開発・保守できるようになります。
*   **Goコンパイラツールチェイン (gc)**: Go言語の公式コンパイラは、歴史的にPlan 9 Cコンパイラツールチェインをベースにしていました。Go 1.5以降はGo言語で書かれていますが、その内部構造や設計思想にはC言語時代の名残が見られます。
*   **`rsc.io/c2go`**: これは、Go言語の主要開発者の一人であるRuss Cox (rsc) によって開発された、C言語からGo言語への機械翻訳ツールです。Goコンパイラ、ランタイム、リンカの大部分をC言語からGo言語に移行するために使用されました。現在では歴史的な価値を持つツールであり、メンテナンスはされていません。

## 技術的詳細

このコミットの主要な変更は、`c2go`ツールによる再変換の結果です。特に注目すべきは、Goコンパイラが内部で生成するシンボル（クロージャやinit関数など）の命名規則の変更です。

以前のGoコンパイラでは、内部生成されたシンボル名に`·`（中点）文字が使用されていました（例: `func·001`、`init·1`）。これは、Go言語の識別子としては無効な文字であり、内部的な区別のため、あるいはC言語の命名規則からの影響であったと考えられます。しかし、このコミットでは、これらの内部シンボル名が`·`から`.`（ドット）に変更されています（例: `func.1`、`init.1`）。

この変更は、Goコンパイラの内部処理、特にシンボル解決やデバッグ情報の生成に影響を与えます。ドットはGo言語の識別子の一部としては使用できませんが、パッケージ名とエクスポートされた識別子を区切るために使用されるため、内部的な命名規則としてよりGo言語の慣習に近づいたと言えます。

`src/cmd/internal/gc/closure.go`における`closurename`関数の導入は、この命名規則の変更と密接に関連しています。この関数は、ネストされたクロージャのシンボル名を再帰的に生成するロジックをカプセル化しています。以前は`makeclosure_closgen`のようなグローバル変数で単純に連番を振っていましたが、`closurename`関数は、外側の関数（`Outerfunc`）の情報を利用して、より構造化された名前（例: `outerfunc.funcN`や`outerfunc.nestedfuncN`）を生成できるようになりました。これにより、デバッグ時やプロファイリング時に、どのクロージャがどの関数内で定義されたかをより容易に特定できるようになります。

また、`src/cmd/internal/gc/go.go`では、`Node`構造体に`Closgen`と`Outerfunc`フィールドが追加されています。
*   `Closgen`: クロージャの生成番号を管理するためのフィールド。
*   `Outerfunc`: 現在のクロージャが定義されている外側の関数への参照。これにより、ネストされたクロージャのコンテキストを追跡し、`closurename`関数で利用できるようになります。

これらの変更は、Goコンパイラの内部構造をよりGo言語の慣習に合わせ、将来的な改善やデバッグの容易化に貢献するものです。

## コアとなるコードの解説

このコミットの核心は、Goコンパイラが内部で生成するシンボル（特にクロージャと`init`関数）の命名規則の変更と、それに伴うクロージャの命名ロジックの改善です。

**`src/cmd/internal/gc/closure.go` の変更点:**

```go
 // 変更前: var makeclosure_closgen int
 // 変更後: var closurename_closgen int

 // 変更前: func makeclosure(func_ *Node) *Node { ... makeclosure_closgen++ ... namebuf = fmt.Sprintf("func·%.3d", makeclosure_closgen) ... }
 // 変更後: func makeclosure(func_ *Node) *Node { ... xfunc.Nname = newname(closurename(func_)) ... }

 // 新規追加: closurename関数
 func closurename(n *Node) *Sym {
 	var outer string
 	var prefix string
 	var gen int

 	if n.Sym != nil {
 		return n.Sym
 	}
 	gen = 0
 	outer = ""
 	prefix = ""
 	if n.Outerfunc == nil {
 		// Global closure.
 		outer = "glob"

 		prefix = "func"
 		closurename_closgen++
 		gen = closurename_closgen
 	} else if n.Outerfunc.Op == ODCLFUNC {
 		// The outermost closure inside of a named function.
 		outer = n.Outerfunc.Nname.Sym.Name

 		prefix = "func"

 		// Yes, functions can be named _.
 		// Can't use function closgen in such case,
 		// because it would lead to name clashes.
 		if !isblank(n.Outerfunc.Nname) {
 			n.Outerfunc.Closgen++
 			gen = n.Outerfunc.Closgen
 		} else {
 			closurename_closgen++
 			gen = closurename_closgen
 		}
 	} else if n.Outerfunc.Op == OCLOSURE {
 		// Nested closure, recurse.
 		outer = closurename(n.Outerfunc).Name

 		prefix = ""
 		n.Outerfunc.Closgen++
 		gen = n.Outerfunc.Closgen
 	} else {
 		Fatal("closurename called for %v", Nconv(n, obj.FmtShort))
 	}
 	namebuf = fmt.Sprintf("%s.%s%d", outer, prefix, gen) // ここで '.' を使用
 	n.Sym = Lookup(namebuf)
 	return n.Sym
 }
```
`makeclosure`関数が、クロージャのシンボル名を生成するために新しく導入された`closurename`関数を呼び出すように変更されました。`closurename`関数は、クロージャがグローバルであるか、名前付き関数内のクロージャであるか、あるいはネストされたクロージャであるかに応じて、異なるロジックでシンボル名を生成します。特に、ネストされたクロージャの場合、`n.Outerfunc`（外側の関数）を再帰的に呼び出して、より意味のある名前を構築します。生成される名前のフォーマットは`%s.%s%d`となり、`·`の代わりに`.`が使用されています。

**`src/cmd/internal/gc/go.go` の変更点:**

```go
 type Node struct {
 	Dcl            *NodeList
 	Inl            *NodeList
 	Inldcl         *NodeList
+	Closgen        int // 新規追加
+	Outerfunc      *Node // 新規追加
 	Val            Val
 	Ntype          *Node
 	Defn           *Node
 	// ...
 }
```
`Node`構造体に`Closgen`と`Outerfunc`が追加されたことで、コンパイラはクロージャの生成番号と、そのクロージャが定義されている外側の関数への参照を保持できるようになりました。これにより、`closurename`関数がより複雑な命名ロジックを実装するためのコンテキストを得ています。

**`src/cmd/internal/gc/init.go` の変更点:**

```go
 // 変更前: namebuf = fmt.Sprintf("init·%d", renameinit_initgen)
 // 変更後: namebuf = fmt.Sprintf("init.%d", renameinit_initgen)

 // 変更前: namebuf = fmt.Sprintf("init·1")
 // 変更後: s = Lookup("init.1") // namebufを使用しない
```
`init`関数の内部生成名も`init·N`から`init.N`に変更されています。これは、コンパイラ全体で内部シンボル名の命名規則を統一する動きの一環です。

これらの変更は、Goコンパイラの内部で生成されるシンボル名の可読性とデバッグの容易性を向上させることを目的としています。特に、クロージャの命名規則の改善は、複雑なGoプログラムのデバッグやプロファイリングにおいて、どのクロージャがどのコードパスに属しているかを理解する上で役立ちます。

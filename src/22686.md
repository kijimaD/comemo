# [インデックス 22686] ファイルの概要

このコミットは、Go言語の`cmd/yacc`ツールが生成するコードにおいて、スライス（`[]type`）の代わりに配列（`[...]type`）を使用するように変更することで、メモリ使用量とバイナリサイズを最適化することを目的としています。具体的には、`yacc`によって生成されるグローバル変数が、実行時に内容が変更されないことが保証されている場合に、より効率的な配列型で宣言されるようになります。これにより、各変数に関連するスライスヘッダのオーバーヘッドが削減され、コンパイル時の定数として`len`が扱えるようになることで、テキストサイズ（コードサイズ）も削減されます。

## 変更の背景

この変更の背景には、Go言語のコンパイラツールチェーンにおけるメモリ効率とバイナリサイズの最適化という明確な目的があります。`cmd/yacc`は、Go言語のパーサー（構文解析器）を生成するために使用されるツールであり、その出力には多くのテーブルデータ（トークン名、状態名、アクションなど）が含まれます。これらのテーブルは通常、Goのグローバル変数として宣言されます。

以前の`cmd/yacc`の挙動では、これらのテーブルはGoのスライス型（例: `[]int`）として生成されていました。しかし、これらのスライスは初期化後にその内容が変更されることはなく、常に同じ基盤となるデータ配列を参照していました。Goコンパイラは、`var yyFoo = []int{...}`のような初期化を内部的に`var yyFoo = ([...]int{...})[:]`のように、まず配列を定義し、その配列へのスライスを作成する形で処理します。

この「スライスを作成する」というステップは、`sliceStruct`と呼ばれるデータ構造（ポインタ、長さ、容量の3つのフィールドを持つ）をメモリ上に確保することを意味します。テーブルの数が多ければ多いほど、この`sliceStruct`のオーバーヘッドが蓄積され、データメモリの使用量が増加します。

また、スライスの場合、`len(yyFoo)`のような操作は実行時にスライスヘッダから長さを読み取る必要があります。しかし、これらのテーブルの長さはコンパイル時に固定されているため、コンパイル時に長さを決定できる配列型にすることで、より効率的なコード生成が可能になります。これにより、テキストサイズ（実行可能バイナリのコードセクションのサイズ）も削減されるという副次的な効果も期待できます。

このコミットは、これらの不必要なオーバーヘッドを排除し、Goコンパイラによって生成されるバイナリのフットプリントを削減するための、具体的な最適化策として導入されました。

## 前提知識の解説

### Go言語における配列とスライス

Go言語には、データをシーケンスとして扱うための2つの主要な型があります。

1.  **配列 (Array)**:
    *   `[N]T` の形式で宣言され、`N`は配列の要素数を示す固定の非負整数です。
    *   要素の型は`T`です。
    *   配列の長さはコンパイル時に決定され、実行中に変更することはできません。
    *   配列は値型であり、変数に代入したり関数に渡したりすると、その配列全体のコピーが作成されます。
    *   `[...]T` の形式で宣言すると、初期化子の要素数に基づいてコンパイラが自動的に長さを決定します。このコミットで採用されている形式です。

    例: `var a [3]int = [3]int{1, 2, 3}` または `var a = [...]int{1, 2, 3}`

2.  **スライス (Slice)**:
    *   `[]T` の形式で宣言され、長さは指定しません。
    *   要素の型は`T`です。
    *   スライスは配列の上に構築された動的なビューであり、基盤となる配列の一部を参照します。
    *   スライス自体は、ポインタ（基盤となる配列の先頭要素へのポインタ）、長さ（スライスに含まれる要素の数）、容量（基盤となる配列の、スライスの開始位置から末尾までの要素数）の3つのフィールドを持つヘッダ構造体（`sliceStruct`）です。
    *   スライスの長さは実行中に変更できます（`append`などを使用）。
    *   スライスは参照型のように振る舞い、代入や関数への引数渡しでは、このヘッダ構造体のコピーが作成されるだけで、基盤となる配列のデータはコピーされません。

    例: `var s []int = []int{1, 2, 3}`

### `cmd/yacc`

`cmd/yacc`は、Go言語の標準ライブラリの一部として提供される、LALR(1)パーサー生成ツールです。Unix系のシステムで広く使われている`yacc`（Yet Another Compiler Compiler）のGo言語版に相当します。

*   **機能**: `yacc`は、文法規則を記述したファイル（通常`.y`拡張子を持つ）を読み込み、その文法を解析するためのGo言語のソースコード（パーサー）を生成します。この生成されたコードには、構文解析に必要な状態遷移テーブルやトークン情報などが含まれます。
*   **用途**: Go言語のコンパイラ自体や、その他のGo言語で書かれたツールで、特定の入力形式（例えば、独自のスクリプト言語や設定ファイル）を解析するために使用されます。
*   **生成されるコード**: `yacc`が生成するGoコードには、`yyToknames`、`yyStatenames`、`yyAct`、`yyPact`などのグローバル変数が含まれることが一般的です。これらはパーサーの動作を定義する静的なデータテーブルです。

### `sizeof(sliceStruct)`

Go言語の内部実装において、スライスは以下のような構造体として表現されます（これは概念的なものであり、実際の構造はコンパイラやアーキテクチャによって異なる場合がありますが、フィールドは共通です）。

```go
type slice struct {
    array unsafe.Pointer // 基盤となる配列の先頭要素へのポインタ
    len   int            // スライスの長さ
    cap   int            // スライスの容量
}
```

`sizeof(sliceStruct)`は、この構造体が占めるメモリサイズを指します。64ビットシステムでは、ポインタ、長さ、容量がそれぞれ8バイトを占めるため、合計で24バイト（8 + 8 + 8）となります。このコミットでは、不必要なスライスヘッダの生成を避けることで、この24バイトのオーバーヘッドを各テーブル変数ごとに削減しています。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの最適化と`cmd/yacc`のコード生成戦略の連携にあります。

1.  **初期化時のスライスと配列の挙動**:
    Go言語では、`var s = []int{1, 2, 3}` のようにスライスをリテラルで初期化すると、コンパイラは内部的にまず匿名配列 `[...]int{1, 2, 3}` を作成し、その配列全体を参照するスライスヘッダを生成します。つまり、このスライスは常にその匿名配列全体を参照し、長さと容量は常に同じになります。

2.  **最適化の機会**:
    `cmd/yacc`が生成する`yyToknames`、`yyStatenames`、`yyExca`、`yyAct`などのグローバル変数は、初期化後にその内容や参照先が変更されることはありません。これらは静的なルックアップテーブルとして機能します。したがって、これらの変数をスライスとして宣言することは、不必要な`sliceStruct`のオーバーヘッドを伴うことになります。

3.  **`[]T` から `[...]T` への変更**:
    このコミットでは、`cmd/yacc`が生成するGoコードにおいて、これらの静的なテーブル変数の宣言を `var yyFoo = []int{...}` から `var yyFoo = [...]int{...}` へと変更します。
    *   `[]int` (スライス) は、ポインタ、長さ、容量の3つのフィールドを持つ`sliceStruct`をメモリ上に確保します。
    *   `[...]int` (配列) は、直接その要素のデータのみをメモリ上に配置します。スライスヘッダは不要です。

4.  **メモリ使用量の削減**:
    この変更により、各テーブル変数について`sizeof(sliceStruct)`（64ビットシステムで約24バイト）のデータメモリが削減されます。`yacc`が生成するテーブルは多数存在するため、この削減は全体として意味のあるものとなります。コミットメッセージに示されている`data`セクションのサイズ削減（605968 -> 605552バイト、約416バイト削減）は、この効果を裏付けています。

5.  **テキストサイズ（コードサイズ）の削減**:
    配列として宣言された場合、`len(yyFoo)`のような操作はコンパイル時にその配列の固定長として解決されます。これにより、実行時にスライスヘッダから長さを読み取るための命令が不要になり、生成される機械語コードの量が削減されます。コミットメッセージに示されている`text`セクションのサイズ削減（4598019 -> 4597810バイト、約209バイト削減）は、この効果を示しています。

6.  **`go.y`の変更**:
    `src/cmd/internal/gc/go.y`の変更は、Go言語の文法定義ファイルの一部であり、このコミットの直接的な目的である`yacc`生成コードの変更とは少し異なります。このファイルはGoコンパイラのフロントエンドの一部であり、`yacc`によって処理されます。変更内容は、単にコメント行を削除しているだけで、機能的な変更ではありません。これは、おそらくコードのクリーンアップの一環か、関連する変更によって不要になった行の削除と考えられます。

この最適化は、Goコンパイラ自体のような、多くの静的データテーブルを持つ大規模なアプリケーションにおいて、特に効果を発揮します。

## コアとなるコードの解説

### `src/cmd/internal/gc/y.go` の変更

このファイルでは、`yyToknames`、`yyStatenames`、`yyExca`、`yyAct`、`yyPact`、`yyPgo`、`yyR1`、`yyR2`、`yyChk`、`yyDef`、`yyTok1`、`yyTok2`、`yyTok3`といった、Goコンパイラのパーサーが使用する静的なデータテーブルの宣言が変更されています。

変更前: `var yyFoo = []int{...}` (スライス型)
変更後: `var yyFoo = [...]int{...}` (配列型、コンパイラが長さを推論)

この変更により、これらの変数はスライスヘッダ（ポインタ、長さ、容量）を持つことなく、直接その要素データのみをメモリに保持するようになります。これにより、各テーブル変数ごとに`sizeof(sliceStruct)`分のデータメモリが節約されます。

### `src/cmd/yacc/yacc.go` の変更

このファイルは、`yacc`ツールがGoコードを生成する際のテンプレートを定義しています。変更は、`fmt.Fprintf`関数呼び出しのフォーマット文字列にあります。

例えば、`yyToknames`の生成部分では、以下の変更が行われています。

変更前: `fmt.Fprintf(ftable, "var %sToknames = []string{\n", prefix)`
変更後: `fmt.Fprintf(ftable, "var %sToknames = [...]string{\n", prefix)`

同様に、`yyStatenames`、`yyExca`、`yyTok3`、そして`arout`関数（他のテーブルを生成する汎用関数）の呼び出しにおいても、生成されるGoコードの変数宣言がスライスから配列へと変更されています。

この変更は、`cmd/yacc`が将来生成するすべてのパーサーコードに影響を与え、同様のメモリおよびテキストサイズの最適化を適用することを保証します。これは、Goコンパイラ自体だけでなく、`cmd/yacc`を使用して生成された他のGoプログラムにも恩恵をもたらす可能性があります。

## 変更の背景

この変更の背景には、Go言語のコンパイラツールチェーンにおけるメモリ効率とバイナリサイズの最適化という明確な目的があります。`cmd/yacc`は、Go言語のパーサー（構文解析器）を生成するために使用されるツールであり、その出力には多くのテーブルデータ（トークン名、状態名、アクションなど）が含まれます。これらのテーブルは通常、Goのグローバル変数として宣言されます。

以前の`cmd/yacc`の挙動では、これらのテーブルはGoのスライス型（例: `[]int`）として生成されていました。しかし、これらのスライスは初期化後にその内容が変更されることはなく、常に同じ基盤となるデータ配列を参照していました。Goコンパイラは、`var yyFoo = []int{...}`のような初期化を内部的に`var yyFoo = ([...]int{...})[:]`のように、まず配列を定義し、その配列へのスライスを作成する形で処理します。

この「スライスを作成する」というステップは、`sliceStruct`と呼ばれるデータ構造（ポインタ、長さ、容量の3つのフィールドを持つ）をメモリ上に確保することを意味します。テーブルの数が多ければ多いほど、この`sliceStruct`のオーバーヘッドが蓄積され、データメモリの使用量が増加します。

また、スライスの場合、`len(yyFoo)`のような操作は実行時にスライスヘッダから長さを読み取る必要があります。しかし、これらのテーブルの長さはコンパイル時に固定されているため、コンパイル時に長さを決定できる配列型にすることで、より効率的なコード生成が可能になります。これにより、テキストサイズ（実行可能バイナリのコードセクションのサイズ）も削減されるという副次的な効果も期待できます。

このコミットは、これらの不必要なオーバーヘッドを排除し、Goコンパイラによって生成されるバイナリのフットプリントを削減するための、具体的な最適化策として導入されました。

## 前提知識の解説

### Go言語における配列とスライス

Go言語には、データをシーケンスとして扱うための2つの主要な型があります。

1.  **配列 (Array)**:
    *   `[N]T` の形式で宣言され、`N`は配列の要素数を示す固定の非負整数です。
    *   要素の型は`T`です。
    *   配列の長さはコンパイル時に決定され、実行中に変更することはできません。
    *   配列は値型であり、変数に代入したり関数に渡したりすると、その配列全体のコピーが作成されます。
    *   `[...]T` の形式で宣言すると、初期化子の要素数に基づいてコンパイラが自動的に長さを決定します。このコミットで採用されている形式です。

    例: `var a [3]int = [3]int{1, 2, 3}` または `var a = [...]int{1, 2, 3}`

2.  **スライス (Slice)**:
    *   `[]T` の形式で宣言され、長さは指定しません。
    *   要素の型は`T`です。
    *   スライスは配列の上に構築された動的なビューであり、基盤となる配列の一部を参照します。
    *   スライス自体は、ポインタ（基盤となる配列の先頭要素へのポインタ）、長さ（スライスに含まれる要素の数）、容量（基盤となる配列の、スライスの開始位置から末尾までの要素数）の3つのフィールドを持つヘッダ構造体（`sliceStruct`）です。
    *   スライスの長さは実行中に変更できます（`append`などを使用）。
    *   スライスは参照型のように振る舞い、代入や関数への引数渡しでは、このヘッダ構造体のコピーが作成されるだけで、基盤となる配列のデータはコピーされません。

    例: `var s []int = []int{1, 2, 3}`

### `cmd/yacc`

`cmd/yacc`は、Go言語の標準ライブラリの一部として提供される、LALR(1)パーサー生成ツールです。Unix系のシステムで広く使われている`yacc`（Yet Another Compiler Compiler）のGo言語版に相当します。

*   **機能**: `yacc`は、文法規則を記述したファイル（通常`.y`拡張子を持つ）を読み込み、その文法を解析するためのGo言語のソースコード（パーサー）を生成します。この生成されたコードには、構文解析に必要な状態遷移テーブルやトークン情報などが含まれます。
*   **用途**: Go言語のコンパイラ自体や、その他のGo言語で書かれたツールで、特定の入力形式（例えば、独自のスクリプト言語や設定ファイル）を解析するために使用されます。
*   **生成されるコード**: `yacc`が生成するGoコードには、`yyToknames`、`yyStatenames`、`yyAct`、`yyPact`などのグローバル変数が含まれることが一般的です。これらはパーサーの動作を定義する静的なデータテーブルです。

### `sizeof(sliceStruct)`

Go言語の内部実装において、スライスは以下のような構造体として表現されます（これは概念的なものであり、実際の構造はコンパイラやアーキテクチャによって異なる場合がありますが、フィールドは共通です）。

```go
type slice struct {
    array unsafe.Pointer // 基盤となる配列の先頭要素へのポインタ
    len   int            // スライスの長さ
    cap   int            // スライスの容量
}
```

`sizeof(sliceStruct)`は、この構造体が占めるメモリサイズを指します。64ビットシステムでは、ポインタ、長さ、容量がそれぞれ8バイトを占めるため、合計で24バイト（8 + 8 + 8）となります。このコミットでは、不必要なスライスヘッダの生成を避けることで、この24バイトのオーバーヘッドを各テーブル変数ごとに削減しています。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラの最適化と`cmd/yacc`のコード生成戦略の連携にあります。

1.  **初期化時のスライスと配列の挙動**:
    Go言語では、`var s = []int{1, 2, 3}` のようにスライスをリテラルで初期化すると、コンパイラは内部的にまず匿名配列 `[...]int{1, 2, 3}` を作成し、その配列全体を参照するスライスヘッダを生成します。つまり、このスライスは常にその匿名配列全体を参照し、長さと容量は常に同じになります。

2.  **最適化の機会**:
    `cmd/yacc`が生成する`yyToknames`、`yyStatenames`、`yyExca`、`yyAct`などのグローバル変数は、初期化後にその内容や参照先が変更されることはありません。これらは静的なルックアップテーブルとして機能します。したがって、これらの変数をスライスとして宣言することは、不必要な`sliceStruct`のオーバーヘッドを伴うことになります。

3.  **`[]T` から `[...]T` への変更**:
    このコミットでは、`cmd/yacc`が生成するGoコードにおいて、これらの静的なテーブル変数の宣言を `var yyFoo = []int{...}` から `var yyFoo = [...]int{...}` へと変更します。
    *   `[]int` (スライス) は、ポインタ、長さ、容量の3つのフィールドを持つ`sliceStruct`をメモリ上に確保します。
    *   `[...]int` (配列) は、直接その要素のデータのみをメモリ上に配置します。スライスヘッダは不要です。

4.  **メモリ使用量の削減**:
    この変更により、各テーブル変数について`sizeof(sliceStruct)`（64ビットシステムで約24バイト）のデータメモリが削減されます。`yacc`が生成するテーブルは多数存在するため、この削減は全体として意味のあるものとなります。コミットメッセージに示されている`data`セクションのサイズ削減（605968 -> 605552バイト、約416バイト削減）は、この効果を裏付けています。

5.  **テキストサイズ（コードサイズ）の削減**:
    配列として宣言された場合、`len(yyFoo)`のような操作はコンパイル時にその配列の固定長として解決されます。これにより、実行時にスライスヘッダから長さを読み取るための命令が不要になり、生成される機械語コードの量が削減されます。コミットメッセージに示されている`text`セクションのサイズ削減（4598019 -> 4597810バイト、約209バイト削減）は、この効果を示しています。

6.  **`go.y`の変更**:
    `src/cmd/internal/gc/go.y`の変更は、Go言語の文法定義ファイルの一部であり、このコミットの直接的な目的である`yacc`生成コードの変更とは少し異なります。このファイルはGoコンパイラのフロントエンドの一部であり、`yacc`によって処理されます。変更内容は、単にコメント行を削除しているだけで、機能的な変更ではありません。これは、おそらくコードのクリーンアップの一環か、関連する変更によって不要になった行の削除と考えられます。

この最適化は、Goコンパイラ自体のような、多くの静的データテーブルを持つ大規模なアプリケーションにおいて、特に効果を発揮します。

このファイルは、`yacc`ツールがGoコードを生成する際のテンプレートを定義しています。変更は、`fmt.Fprintf`関数呼び出しのフォーマット文字列にあります。

変更前: `fmt.Fprintf(ftable, "var %sToknames = []string{\n", prefix)`
変更後: `fmt.Fprintf(ftable, "var %sToknames = [...]string{\n", prefix)`

同様に、`yyStatenames`、`yyExca`、`yyTok3`、そして`arout`関数（他のテーブルを生成する汎用関数）の呼び出しにおいても、生成されるGoコードの変数宣言がスライスから配列へと変更されています。

この変更は、`cmd/yacc`が将来生成するすべてのパーサーコードに影響を与え、同様のメモリおよびテキストサイズの最適化を適用することを保証します。これは、Goコンパイラ自体だけでなく、`cmd/yacc`を使用して生成された他のGoプログラムにも恩恵をもたらす可能性があります。

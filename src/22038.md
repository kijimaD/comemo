## 変更の背景

このコミットは、Goランタイムにおけるガベージコレクション（GC）の処理中に発生していたクラッシュを修正するために導入されました。具体的な問題は、GCの特定のフェーズ、特に`checkmarkphase`が完了する前に、GCが使用する内部データ構造である`work.spans`がシステムからアンマップ（解放）されてしまうことにありました。

GoのGCは、並行処理を多用しており、GCがメモリをスキャンしている最中にも、ユーザープログラム（ミューテータ）が実行され、新しいオブジェクトが割り当てられたり、既存のオブジェクトが変更されたりする可能性があります。このような並行性の中で、`work.spans`のような重要なデータ構造がGCの処理が完全に終わる前に解放されると、GCがそのデータにアクセスしようとした際に、既に解放されたメモリ領域にアクセスしようとして不正なメモリアクセス（Use-After-Free）が発生し、結果としてランタイムがクラッシュするという問題が生じていました。

このクラッシュは、Goランタイムの安定性に直接影響を与える深刻な問題であり、その解決が急務でした。コミットメッセージにある「This is causing crashes.」という簡潔な記述は、この問題の緊急性と重要性を明確に示しています。

## 前提知識の解説

このコミットの理解には、Goのガベージコレクション（GC）の基本的な仕組みと、それに伴ういくつかの専門用語の知識が必要です。

### Goのガベージコレクション（GC）

GoのGCは、主に「マーク・アンド・スイープ（Mark-and-Sweep）」アルゴリズムをベースにしています。これは、到達可能なオブジェクトをマークし、マークされなかった（到達不可能な）オブジェクトを解放するというプロセスです。GoのGCは、ユーザープログラムの実行と並行して動作する「並行GC」であり、プログラムの一時停止（Stop-The-World: STW）時間を最小限に抑えるように設計されています。

GoのGCは、大まかに以下のフェーズで構成されます（バージョンによって詳細なフェーズは異なりますが、基本的な概念は共通です）：

1.  **マークフェーズ (Mark Phase)**:
    *   GCルート（グローバル変数、スタック上の変数など）から到達可能なすべてのオブジェクトをマークします。
    *   GoのGCは、このフェーズの一部を並行して実行し、STW時間を短縮します。
    *   このフェーズ中に、ミューテータ（ユーザープログラム）がオブジェクトグラフを変更する可能性があるため、「ライトバリア（Write Barrier）」という仕組みを使用して、オブジェクトの変更をGCに通知します。

2.  **マークターミネーションフェーズ (Mark Termination Phase)**:
    *   並行マークフェーズの終了を調整し、すべてのマーク作業が完了したことを確認します。
    *   このフェーズはSTWで実行されることがあります。

3.  **スイープフェーズ (Sweep Phase)**:
    *   マークされなかったオブジェクトが占めていたメモリ領域を解放し、再利用可能な状態にします。
    *   このフェーズも並行して実行されます。

### `mspan`と`mheap`

Goのメモリ管理は、`mspan`という単位で行われます。`mspan`は、連続したページ（通常は8KB）のブロックであり、同じサイズのオブジェクトを格納するために使用されます。`mheap`は、すべての`mspan`を管理するグローバルなヒープ構造です。

### `work.spans`

`work.spans`は、GCのマーキングフェーズにおいて、スキャン対象となる`mspan`のリストを保持するために使用される内部データ構造です。GCがヒープを走査し、到達可能なオブジェクトをマークする際に、この`work.spans`リストを参照して、どのメモリ領域をスキャンする必要があるかを判断します。これは、GCの効率的な動作に不可欠な一時的な作業領域です。

### `checkmarkphase`

`checkmarkphase`は、GoのGCにおけるデバッグや検証のための特別なフェーズです。これは、GCのマーク処理が正しく行われたかどうかを検証するために使用されます。通常、このフェーズはデバッグビルドや特定のテストシナリオでのみ有効になります。このフェーズが有効な場合、GCはマーク処理の後に、マークされたオブジェクトが本当に到達可能であるか、あるいはマークされるべきオブジェクトがマークされていないかなどを追加でチェックします。

### `sysFree`

`sysFree`は、Goランタイムがオペレーティングシステムから取得したメモリを解放するために使用する低レベルの関数です。これは、`mmap`などで確保されたメモリ領域を`munmap`などを用いてOSに返却する操作に相当します。

### `mheap_.lock`

`mheap_.lock`は、Goランタイムのグローバルヒープ構造である`mheap_`へのアクセスを保護するためのミューテックス（ロック）です。GCやメモリ割り当てなど、複数のゴルーチンが`mheap_`のデータ構造を同時に変更しようとすると競合状態が発生するため、このロックを使用して排他制御を行います。

## 技術的詳細

このコミットが修正しようとしている問題は、Goの並行GCにおけるタイミングの問題に起因します。

GoのGCは、STWフェーズを最小限に抑えるために、多くの処理をユーザープログラムと並行して実行します。`work.spans`は、この並行マークフェーズ中にGCが使用する一時的なデータ構造であり、スキャンすべきメモリ領域の情報を保持しています。

元のコードでは、`gc`関数の冒頭付近で`work.spans`が解放されていました。この解放処理は`sysFree`を呼び出し、OSに対してメモリを返却します。問題は、この解放が`checkmarkphase`のチェックよりも前に行われていた点です。

`checkmarkphase`は、GCのマーク処理が正しく行われたかを検証するフェーズであり、このフェーズが有効な場合、GCは`work.spans`が保持する情報（またはそれに関連する情報）にアクセスして検証を行います。しかし、もし`work.spans`が`checkmarkphase`の実行前に解放されてしまうと、`checkmarkphase`が既に解放されたメモリ領域にアクセスしようとします。これは「Use-After-Free」の脆弱性となり、結果としてランタイムがクラッシュします。

特に、コミットメッセージにある「Even if this is still stop-the-world, a concurrent exitsyscall can allocate a stack from heap.」というコメントは、この問題の複雑さを示唆しています。たとえGCがSTW状態であっても、`exitsyscall`（システムコールからの復帰）のような並行処理がヒープからスタックを割り当てる可能性があり、これが`work.spans`の解放タイミングと競合し、問題を引き起こす可能性があったことを示唆しています。

この問題は、GCの内部状態とメモリ管理の厳密な同期が求められるGoランタイムの複雑な性質を浮き彫りにしています。`work.spans`の解放を`checkmarkphase`の後に移動することで、`checkmarkphase`が安全に実行され、必要なデータにアクセスできるようになり、クラッシュが回避されます。

## コアとなるコードの解説

この変更の核心は、`work.spans`の解放タイミングを、`checkmarkphase`の実行が完了した後（または`checkmarkphase`がスキップされた場合）に移動したことです。

元のコードでは、`gc`関数の開始直後、`mheap_.lock`を取得した後に`work.spans`が`sysFree`によって解放されていました。この時点では、`debug.gccheckmark > 0`が真である場合に実行される`checkmarkphase`がまだ実行されていませんでした。

`checkmarkphase`は、GCのマーク処理の正確性を検証するためのデバッグ機能であり、`work.spans`が保持する情報に依存する可能性があります。もし`work.spans`が`checkmarkphase`の実行前に解放されてしまうと、`checkmarkphase`が不正なメモリアドレスにアクセスしようとしてクラッシュを引き起こす可能性がありました。

変更後のコードでは、`work.spans`の解放処理が`if debug.gccheckmark > 0 { ... }`ブロックの後に移動されました。これにより、以下の論理的な流れが保証されます。

1.  `gc`関数が開始されます。
2.  `debug.gccheckmark > 0`が真の場合、`checkmarkphase`が実行されます。このフェーズは、`work.spans`がまだ有効な状態であることを前提としています。
3.  `checkmarkphase`が完了した後、または`debug.gccheckmark`が0で`checkmarkphase`がスキップされた後に、`mheap_.lock`が取得され、`work.spans`が安全に`sysFree`によって解放されます。

この変更により、`checkmarkphase`が`work.spans`にアクセスする際に、そのメモリがまだ有効であることが保証され、Use-After-Freeによるクラッシュが回避されます。`mheap_.lock`は、`work.spans`の解放処理自体がアトミックに行われることを保証するために引き続き使用されています。

この修正は、Goランタイムの並行GCの堅牢性を高める上で非常に重要であり、デバッグ機能が有効な環境での安定性向上に貢献しました。

GoのGCは、STWフェーズを最小限に抑えるために、多くの処理をユーザープログラムと並行して実行します。`work.spans`は、この並行マークフェーズ中にGCが使用する一時的なデータ構造であり、スキャンすべきメモリ領域の情報を保持しています。

`checkmarkphase`は、GCのマーク処理が正しく行われたかを検証するフェーズであり、このフェーズが有効な場合、GCは`work.spans`が保持する情報（またはそれに関連する情報）にアクセスして検証を行います。しかし、もし`work.spans`が`checkmarkphase`の実行前に解放されてしまうと、`checkmarkphase`が既に解放されたメモリ領域にアクセスしようとします。これは「Use-After-Free」の脆弱性となり、結果としてランタイムがクラッシュします。

特に、コミットメッセージにある「Even if this is still stop-the-world, a concurrent exitsyscall can allocate a stack from heap.」というコメントは、この問題の複雑さを示唆しています。たとえGCがSTW状態であっても、`exitsyscall`（システムコールからの復帰）のような並行処理がヒープからスタックを割り当てる可能性があり、これが`work.spans`の解放タイミングと競合し、問題を引き起こす可能性があったことを示唆しています。

この問題は、GCの内部状態とメモリ管理の厳密な同期が求められるGoランタイムの複雑な性質を浮き彫りにしています。`work.spans`の解放を`checkmarkphase`の後に移動することで、`checkmarkphase`が安全に実行され、必要なデータにアクセスできるようになり、クラッシュが回避されます。

## コアとなるコードの解説

この変更の核心は、`work.spans`の解放タイミングを、`checkmarkphase`の実行が完了した後（または`checkmarkphase`がスキップされた場合）に移動したことです。

元のコードでは、`gc`関数の開始直後、`mheap_.lock`を取得した後に`work.spans`が`sysFree`によって解放されていました。この時点では、`debug.gccheckmark > 0`が真である場合に実行される`checkmarkphase`がまだ実行されていませんでした。

`checkmarkphase`は、GCのマーク処理の正確性を検証するためのデバッグ機能であり、`work.spans`が保持する情報に依存する可能性があります。もし`work.spans`が`checkmarkphase`の実行前に解放されてしまうと、`checkmarkphase`が不正なメモリアドレスにアクセスしようとしてクラッシュを引き起こす可能性がありました。

変更後のコードでは、`work.spans`の解放処理が`if debug.gccheckmark > 0 { ... }`ブロックの後に移動されました。これにより、以下の論理的な流れが保証されます。

1.  `gc`関数が開始されます。
2.  `debug.gccheckmark > 0`が真の場合、`checkmarkphase`が実行されます。このフェーズは、`work.spans`がまだ有効な状態であることを前提としています。
3.  `checkmarkphase`が完了した後、または`debug.gccheckmark`が0で`checkmarkphase`がスキップされた後に、`mheap_.lock`が取得され、`work.spans`が安全に`sysFree`によって解放されます。

この変更により、`checkmarkphase`が`work.spans`にアクセスする際に、そのメモリがまだ有効であることが保証され、Use-After-Freeによるクラッシュが回避されます。`mheap_.lock`は、`work.spans`の解放処理自体がアトミックに行われることを保証するために引き続き使用されています。

この修正は、Goランタイムの並行GCの堅牢性を高める上で非常に重要であり、デバッグ機能が有効な環境での安定性向上に貢献しました。

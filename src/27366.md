# [インデックス 27366] ファイルの概要

このコミットは、Go言語の `bytes` パッケージにおける `Equal` および類似の比較関数のパフォーマンスを、特に `ppc64le` および `ppc64` アーキテクチャ上で改善することを目的としています。既存の実装が1バイトずつ比較する非効率な方法であったため、ダブルワード（8バイト）単位での比較を導入し、共通の比較ロジックを `memeqbody` という新しいアセンブリ関数に集約することで、大幅な高速化を実現しています。

## 元コミット内容

`bytes` パッケージ内の `Equal` および類似の関数における `ppc64le`/`ppc64` でのパフォーマンス改善。

既存の `Equal` および類似関数の実装は、1バイトずつ処理を行っていたため、特にバイトバッファが大きい場合に `ppc64`/`ppc64le` 上でパフォーマンスが低下していました。この変更は、可能な限りダブルワード（8バイト）をロードして比較することで、これらの関数を改善します。共通のコードは、同じ種類の比較を実行するファイル内の他の関数で共有できる関数に移動されました。32バイト以上が比較されるケースでは、さらなる最適化が行われます。新しい関数 `memeqbody` は、`memeq_varlen`、`Equal`、および `eqstring` で使用されます。

## 変更の背景

Go言語の標準ライブラリである `bytes` パッケージには、バイトスライスや文字列の比較を行う `Equal` などの関数が含まれています。これらの関数は、内部的には `runtime` パッケージのアセンブリコードによって最適化されたメモリ比較ルーチン (`memequal` など) を呼び出すことがあります。

しかし、`ppc64le` (PowerPC 64-bit Little Endian) および `ppc64` (PowerPC 64-bit Big Endian) アーキテクチャにおいて、既存のメモリ比較ルーチンが1バイトずつデータを比較する実装になっていました。現代の64ビットプロセッサでは、一度に複数のバイト（例えば8バイトのダブルワード）をロードして比較する方がはるかに効率的です。1バイトずつの比較は、特に大きなデータブロックを扱う際に、メモリバスの利用効率が低く、CPUのパイプラインを十分に活用できないため、顕著なパフォーマンスボトルネックとなっていました。

この非効率性は、Goプログラムが大量のバイトデータや文字列を比較する際に、`ppc64le`/`ppc64` 環境での実行速度を著しく低下させる原因となっていました。このコミットは、このパフォーマンスギャップを解消し、これらのアーキテクチャ上でのGoプログラムの実行効率を向上させるために行われました。特に、ベンチマーク結果が示すように、比較対象のデータサイズが大きくなるほど、改善の度合いが顕著になることが期待されました。

## 前提知識の解説

### 1. Go言語の `bytes` パッケージと `runtime` パッケージ

*   **`bytes` パッケージ**: バイトスライスの操作（比較、検索、変換など）を提供するGoの標準ライブラリです。`bytes.Equal` は2つのバイトスライスが等しいかどうかを比較する関数です。
*   **`runtime` パッケージ**: Goランタイムのコア部分を実装しており、ガベージコレクション、スケジューラ、メモリ管理、そして特定のアーキテクチャに最適化された低レベルな操作（メモリコピー、メモリ比較など）のアセンブリコードが含まれています。Goのパフォーマンスクリティカルな部分は、しばしばこのパッケージ内のアセンブリコードに依存しています。

### 2. `ppc64le` / `ppc64` アーキテクチャ

*   **PowerPC (PPC)**: IBMが開発したRISC (Reduced Instruction Set Computer) アーキテクチャです。
*   **`ppc64`**: 64ビット版のPowerPCアーキテクチャ。
*   **`ppc64le`**: `ppc64` のリトルエンディアン版。Go言語は様々なアーキテクチャをサポートしており、それぞれのアーキテクチャに最適化されたアセンブリコードを持つことがあります。

### 3. アセンブリ言語とGoランタイム

Go言語は通常、高水準言語として書かれますが、パフォーマンスが非常に重要な部分（特にランタイム）では、特定アーキテクチャ向けのアセンブリ言語が使用されます。これにより、CPUのレジスタを直接操作したり、特定の命令セットを活用したりして、最大限のパフォーマンスを引き出すことができます。GoのアセンブリはPlan 9アセンブリの記法に似ており、一般的なGAS (GNU Assembler) 記法とは異なります。

### 4. ダブルワード (Double Word)

コンピュータアーキテクチャにおけるデータサイズの単位です。
*   **バイト (Byte)**: 8ビット
*   **ワード (Word)**: アーキテクチャによって異なるが、通常はCPUのレジスタサイズ（32ビットシステムでは4バイト、64ビットシステムでは8バイト）
*   **ダブルワード (Double Word)**: ワードの2倍のサイズ。64ビットシステムでは、ワードが8バイトなので、ダブルワードは16バイトを指すこともありますが、この文脈では「64ビット（8バイト）のデータ単位」を指している可能性が高いです。特にPPC64では、64ビットレジスタが一般的であり、一度に8バイトを処理する命令が効率的です。

### 5. `DCBT` 命令 (Data Cache Block Touch)

PowerPCアーキテクチャの命令の一つで、指定されたアドレスのデータがキャッシュにロードされるようにヒントを与えます。これは、後続のメモリアクセスがキャッシュヒットする可能性を高め、メモリレイテンシを削減することでパフォーマンスを向上させるための最適化手法です。プリフェッチ命令の一種と考えることができます。

### 6. ベンチマークとパフォーマンス測定

Go言語には、`go test -bench` コマンドを使ってコードのパフォーマンスを測定する組み込みのベンチマークツールがあります。MB/s (Megabytes per second) は、1秒間に処理できるデータ量を示し、比較関数のスループットを評価するのに適した指標です。`speedup` は、最適化後の性能が最適化前の何倍になったかを示します。

## 技術的詳細

このコミットの主要な技術的詳細は以下の通りです。

1.  **ダブルワード比較の導入**:
    *   従来の1バイトずつの比較から、64ビット（8バイト）単位でデータをロードし比較する方式に変更されました。これにより、メモリバスの利用効率が向上し、CPUが一度に処理できるデータ量が増加します。
    *   アセンブリ命令 `MOVD` (Move Doubleword) を使用して、8バイトのデータをレジスタにロードし、`CMP` (Compare) 命令で比較します。

2.  **共通比較ロジック `memeqbody` の抽出**:
    *   `runtime·memequal`、`runtime·memequal_varlen`、`runtime·eqstring`、`bytes·Equal` といった複数の関数で共通して使用されるメモリ比較ロジックが、`runtime·memeqbody` という新しいアセンブリ関数として分離されました。
    *   これにより、コードの重複が排除され、保守性が向上するとともに、最適化の適用が容易になります。

3.  **サイズに応じた最適化パス**:
    *   比較するバイト数 (`len`) に応じて、異なる最適化パスが選択されます。
        *   **8バイト未満**: `simplecheck` および `simple` ループで1バイトずつ比較します。これは、オーバーヘッドを避けるためです。
        *   **8バイト以上**: ダブルワード単位での比較を開始します。
        *   **32バイト以上**: さらに最適化されたループ `loop32a` を使用します。このループでは、一度に4つのダブルワード（32バイト）をロードし、比較します。これにより、ループのオーバーヘッドをさらに削減し、より多くのデータを並行して処理できます。
        *   残りの8バイト単位のデータは `loop8` で処理され、残りの1バイト単位のデータは `leftover` および `simple` で処理されます。

4.  **キャッシュヒント `DCBT` の利用**:
    *   `memeqbody` 関数の冒頭で、比較対象のメモリ領域 (`R3` と `R4` が指すアドレス) に対して `DCBT` (Data Cache Block Touch) 命令が発行されます。
    *   これは、CPUのデータキャッシュに、これらのメモリブロックがすぐにアクセスされることを示唆し、プリフェッチを促します。これにより、実際にデータがロードされる際にキャッシュミスが発生する可能性が減り、メモリレイテンシが隠蔽され、全体的なパフォーマンスが向上します。

5.  **ベンチマーク結果の分析**:
    *   ベンチマーク結果は、特にデータサイズが大きくなるにつれて劇的な速度向上（`BenchmarkEqual4K` で21倍以上）を示しています。
    *   小さいデータサイズ（1バイト、6バイト）でわずかな性能低下が見られますが、これはコミットメッセージにもあるように、新しいアセンブリコードの「シングルバイトループのコードアライメントが不利であったため」と説明されています。これは、最適化されたパスへの分岐やセットアップのオーバーヘッドが、非常に小さいデータサイズでは相対的に大きくなるためと考えられます。しかし、全体としては大幅な改善です。

## コアとなるコードの変更箇所

変更は `src/runtime/asm_ppc64x.s` ファイルに集中しています。

1.  **`runtime·memequal` の変更**:
    *   以前は1バイトずつ比較するループを直接持っていたが、新しい `runtime·memeqbody` 関数を呼び出すように変更されました。
    *   `BL runtime·memeqbody(SB)` 命令で `memeqbody` を呼び出し、その戻り値 (`R9`) を結果として使用します。

2.  **`runtime·memequal_varlen` の変更**:
    *   同様に、以前は `runtime·memequal` を呼び出していたが、直接 `runtime·memeqbody` を呼び出すように変更されました。

3.  **`runtime·eqstring` の変更**:
    *   文字列比較のロジックも、`runtime·memeqbody` を呼び出すように変更されました。これにより、文字列比較も高速化されます。

4.  **`bytes·Equal` の変更**:
    *   `bytes.Equal` 関数も、長さのチェック後に `runtime·memeqbody` を呼び出すように変更されました。

5.  **`runtime·memeqbody` 関数の新規追加**:
    *   このコミットの核心であり、新しい効率的なメモリ比較ロジックを実装したアセンブリ関数です。
    *   引数として `s1` (R3), `s2` (R4), `len` (R5) を取り、結果を `R9` に返します。
    *   内部で `DCBT` 命令、サイズに応じた分岐 (`setup32a`, `setup8a`, `simplecheck`), ダブルワード比較ループ (`loop32a`, `loop8`), およびシングルバイト比較ループ (`simple`) を含みます。

## コアとなるコードの解説

新しく追加された `runtime·memeqbody` 関数のアセンブリコードを詳細に見ていきます。

```assembly
TEXT runtime·memeqbody(SB),NOSPLIT|NOFRAME,$0-0
    MOVD    R5,CTR          // R5 (len) をカウンタレジスタ (CTR) に設定
    CMP     R5,$8           // len が8未満か？
    BLT     simplecheck     // 8未満なら simplecheck へ分岐 (1バイト比較)
    DCBT    (R3)            // s1 のアドレスをキャッシュにヒント
    DCBT    (R4)            // s2 のアドレスをキャッシュにヒント
    CMP     R5,$32          // len が32未満か？
    MOVD    R5,R6           // R6 に len をコピー (setup8a で必要になる可能性)
    BLT     setup8a         // 32未満なら setup8a へ分岐 (8バイト比較)

setup32a:                       // 8バイトアライン、かつ >= 32バイトの場合
    SRADCC  $5,R5,R6        // R5 (len) を5ビット右シフト (len / 32)。R6 に32バイトチャンクの数を格納
    MOVD    R6,CTR          // R6 をカウンタレジスタに設定
loop32a:
    MOVD    0(R3),R6        // s1 から最初の8バイトを R6 にロード
    MOVD    0(R4),R7        // s2 から最初の8バイトを R7 にロード
    MOVD    8(R3),R8        // s1 から次の8バイトを R8 にロード
    MOVD    8(R4),R9        // s2 から次の8バイトを R9 にロード
    CMP     R6,R7           // R6 と R7 を比較
    BNE     noteq           // 等しくなければ noteq へ分岐
    MOVD    16(R3),R6       // s1 から次の8バイトを R6 にロード
    MOVD    16(R4),R7       // s2 から次の8バイトを R7 にロード
    CMP     R8,R9           // R8 と R9 を比較
    MOVD    24(R3),R8       // s1 から次の8バイトを R8 にロード
    MOVD    24(R4),R9       // s2 から次の8バイトを R9 にロード
    BNE     noteq           // 等しくなければ noteq へ分岐
    CMP     R6,R7           // R6 と R7 を比較
    BNE     noteq           // 等しくなければ noteq へ分岐
    ADD     $32,R3          // s1 ポインタを32バイト進める
    ADD     $32,R4          // s2 ポインタを32バイト進める
    CMP     R8,R9           // R8 と R9 を比較
    BC      8,2,loop32a     // CTR が0でなく、かつ比較結果が等しければ loop32a へ分岐 (ループ継続)
    BNE     noteq           // 等しくなければ noteq へ分岐
    ANDCC   $24,R5,R6       // R5 (元の len) と 24 を AND (残りの8バイトチャンクの数をチェック)
    BEQ     leftover        // 結果が0なら leftover へ分岐
setup8a:
    SRADCC  $3,R6,R6        // R6 を3ビット右シフト (len / 8)。R6 に8バイトチャンクの数を格納
    BEQ     leftover        // 結果が0なら leftover へ分岐
    MOVD    R6,CTR          // R6 をカウンタレジスタに設定
loop8:
    MOVD    0(R3),R6        // s1 から8バイトを R6 にロード
    ADD     $8,R3           // s1 ポインタを8バイト進める
    MOVD    0(R4),R7        // s2 から8バイトを R7 にロード
    ADD     $8,R4           // s2 ポインタを8バイト進める
    CMP     R6,R7           // R6 と R7 を比較
    BC      8,2,loop8       // CTR が0でなく、かつ比較結果が等しければ loop8 へ分岐 (ループ継続)
    BNE     noteq           // 等しくなければ noteq へ分岐
leftover:
    ANDCC   $7,R5,R6        // R5 (元の len) と 7 を AND (残りの1バイトチャンクの数をチェック)
    BEQ     equal           // 結果が0なら equal へ分岐
simplecheck:
    CMP     R5,$0           // len が0か？
    BEQ     equal           // 0なら equal へ分岐
simple:
    MOVBZ   0(R3), R6       // s1 から1バイトを R6 にロード (ゼロ拡張)
    ADD     $1,R3           // s1 ポインタを1バイト進める
    MOVBZ   0(R4), R7       // s2 から1バイトを R7 にロード (ゼロ拡張)
    ADD     $1,R4           // s2 ポインタを1バイト進める
    CMP     R6, R7          // R6 と R7 を比較
    BNE     noteq           // 等しくなければ noteq へ分岐
    BC      8,2,simple      // CTR が0でなく、かつ比較結果が等しければ simple へ分岐 (ループ継続)
    BNE     noteq           // 等しくなければ noteq へ分岐
    BR      equal           // 全て等しければ equal へ分岐
noteq:
    MOVD    $0, R9          // R9 に0を設定 (false)
    RET                     // 戻る
equal:
    MOVD    $1, R9          // R9 に1を設定 (true)
    RET                     // 戻る
```

このアセンブリコードは、以下のロジックで動作します。

1.  **初期チェックと分岐**:
    *   比較する長さ `len` (R5) が8バイト未満の場合、`simplecheck` に分岐し、1バイト単位の比較を行います。
    *   `DCBT` 命令でキャッシュヒントを与えます。
    *   `len` が32バイト未満の場合、`setup8a` に分岐し、8バイト単位の比較を行います。
    *   `len` が32バイト以上の場合、`setup32a` に進み、32バイト単位の比較を行います。

2.  **32バイト単位の比較 (`loop32a`)**:
    *   `SRADCC $5,R5,R6` で `len` を32で割り、32バイトチャンクの数を `R6` に格納し、カウンタレジスタ `CTR` に設定します。
    *   ループ内で、`MOVD` 命令を使って一度に4つのダブルワード（合計32バイト）をロードし、それぞれ `CMP` 命令で比較します。
    *   途中で不一致があれば `noteq` に分岐します。
    *   `ADD $32,R3` と `ADD $32,R4` でポインタを32バイト進めます。
    *   `BC 8,2,loop32a` は、`CTR` が0でなく、かつ直前の比較が等しかった場合にループを継続する条件分岐です。

3.  **8バイト単位の比較 (`loop8`)**:
    *   `SRADCC $3,R6,R6` で残りの `len` を8で割り、8バイトチャンクの数を `R6` に格納し、`CTR` に設定します。
    *   ループ内で、`MOVD` 命令を使って一度に1つのダブルワード（8バイト）をロードし、`CMP` 命令で比較します。
    *   不一致があれば `noteq` に分岐します。
    *   `ADD $8,R3` と `ADD $8,R4` でポインタを8バイト進めます。
    *   `BC 8,2,loop8` でループを継続します。

4.  **残りの1バイト単位の比較 (`simple` / `leftover`)**:
    *   `ANDCC $7,R5,R6` で残りのバイト数（0〜7バイト）を計算します。
    *   `simple` ループでは、`MOVBZ` 命令を使って1バイトずつロードし、`CMP` 命令で比較します。
    *   不一致があれば `noteq` に分岐します。
    *   `ADD $1,R3` と `ADD $1,R4` でポインタを1バイト進めます。
    *   `BC 8,2,simple` でループを継続します。

5.  **結果の返却**:
    *   全てのバイトが等しければ `equal` に分岐し、`R9` に1（true）を設定して戻ります。
    *   途中で不一致が見つかれば `noteq` に分岐し、`R9` に0（false）を設定して戻ります。

この構造により、データサイズに応じて最も効率的な比較方法が選択され、特に大きなデータブロックでは大幅なパフォーマンス向上が実現されています。

# [インデックス 21119] ファイルの概要

このコミットは、Goランタイムにおける`sudog`構造体のメモリリークを修正するものです。`sudog`は、チャネル操作などでゴルーチンがブロックされた際に、そのゴルーチンを表現するために使用される内部データ構造です。以前はスタック上に配置されていましたが、Goへの変換に伴いヒープに移動され、その際に適切なクリーンアップが行われないことでメモリリークが発生していました。

    runtime: fix sudog leak
    
    The SudoG used to sit on the stack, so it was cheap to allocated
    and didn't need to be cleaned up when finished.
    
    For the conversion to Go, we had to move sudog off the stack
    for a few reasons, so we added a cache of recently used sudogs
    to keep allocation cheap. But we didn't add any of the necessary
    cleanup before adding a SudoG to the new cache, and so the cached
    SudoGs had stale pointers inside them that have caused all sorts
    of awful, hard to debug problems.
    
    CL 155760043 made sure SudoG.elem is cleaned up.
    CL 150520043 made sure SudoG.selectdone is cleaned up.
    
    This CL makes sure SudoG.next, SudoG.prev, and SudoG.waitlink
    are cleaned up. I should have done this when I did the other two
    fields; instead I wasted a week tracking down a leak they caused.
    
    A dangling SudoG.waitlink can point into a sudog cache list that
    has been "forgotten" in order to let the GC collect it, but that
    dangling .waitlink keeps the list from being collected.
    And then the list holding the SudoG with the dangling waitlink
    can find itself in the same situation, and so on. We end up
    with lists of lists of unusable SudoGs that are still linked into
    the object graph and never collected (given the right mix of
    non-trivial selects and non-channel synchronization).

    Fixes #9110.

## 元コミット内容

このコミットは、Goランタイムにおける`sudog`構造体のメモリリークを修正します。

以前、`sudog`はスタック上に配置されており、割り当てが安価で、使用後にクリーンアップする必要がありませんでした。

Goへの変換に伴い、いくつかの理由から`sudog`をスタックからヒープに移動する必要がありました。これにより、割り当てを安価に保つために、最近使用された`sudog`のキャッシュが追加されました。しかし、新しいキャッシュに`sudog`を追加する前に必要なクリーンアップが追加されていなかったため、キャッシュされた`sudog`には古いポインタが残っており、あらゆる種類のひどくデバッグが困難な問題を引き起こしていました。

CL 155760043は`SudoG.elem`がクリーンアップされることを保証しました。
CL 150520043は`SudoG.selectdone`がクリーンアップされることを保証しました。

このCLは`SudoG.next`、`SudoG.prev`、および`SudoG.waitlink`がクリーンアップされることを保証します。他の2つのフィールドを修正したときにこれを行うべきでしたが、代わりに、これらが引き起こしたリークを追跡するのに1週間を無駄にしました。

ぶら下がった`SudoG.waitlink`は、GCがそれを収集できるように「忘れられた」`sudog`キャッシュリストを指す可能性がありますが、そのぶら下がった`.waitlink`はリストが収集されるのを防ぎます。そして、ぶら下がった`waitlink`を持つ`SudoG`を保持するリストは、同じ状況に陥る可能性があり、それが連鎖します。結果として、オブジェクトグラフにリンクされたまま収集されない、使用できない`SudoG`のリストのリストができてしまいます（非自明なselectと非チャネル同期の適切な組み合わせが与えられた場合）。

詳細はgolang.org/issue/9110を参照してください。

Fixes #9110.

## 変更の背景

Go言語のランタイムは、ゴルーチンのスケジューリングやチャネル通信といった並行処理の根幹を担っています。このコミットが行われた2014年当時、GoランタイムはC言語で書かれた部分とGo言語で書かれた部分が混在しており、Go言語への移行が進められていました。

`sudog`構造体は、Goの並行処理モデルにおいて非常に重要な役割を果たします。ゴルーチンがチャネル操作（送信または受信）によってブロックされる際、そのゴルーチンは直接チャネルの待機キューに追加されるのではなく、`sudog`という軽量なオブジェクトを介してキューに登録されます。これにより、ランタイムはブロックされたゴルーチンの状態を効率的に管理し、チャネル操作が完了した際に適切なゴルーチンを再開させることができます。

コミットメッセージによると、元々`sudog`はスタック上に割り当てられていました。スタック上のデータは関数のスコープを抜けると自動的に解放されるため、明示的なクリーンアップは不要でした。しかし、ランタイムのGo言語への移行プロセスにおいて、いくつかの理由（例えば、ガベージコレクションの対象とするため、あるいはより柔軟なメモリ管理を可能にするためなど）から、`sudog`をヒープ上に移動する必要が生じました。

ヒープ上に移動された`sudog`は、使用後に明示的に解放または再利用される必要があります。Goランタイムは、`sudog`の割り当てコストを削減するために、使用済みの`sudog`をキャッシュするメカニズムを導入しました。しかし、このキャッシュに`sudog`を戻す際に、内部のポインタフィールド（`next`, `prev`, `waitlink`など）が適切にnilにクリアされていなかったことが問題の根源でした。

これらの古いポインタが残っていると、たとえ`sudog`自体がキャッシュに戻されても、それが参照している他のオブジェクト（例えば、別の`sudog`や、既に解放されたはずのメモリ領域）への参照が残ってしまいます。特に、`sudog`が形成する連結リストの構造において、この「ぶら下がったポインタ」は深刻なメモリリークを引き起こす可能性がありました。ガベージコレクタは、到達可能なオブジェクトを収集しないため、たとえ論理的には不要になった`sudog`であっても、ぶら下がったポインタによって参照され続けている限り、メモリから解放されずに残り続けてしまうのです。

このリークは、特に複雑な`select`文や、チャネル以外の同期プリミティブが絡むシナリオで顕著に発生し、デバッグが非常に困難であったと述べられています。コミットの作者であるRuss Cox氏自身も、この問題の追跡に1週間を費やしたと記しており、その深刻さが伺えます。

## 前提知識の解説

### 1. Goランタイムとゴルーチン

Go言語は、軽量な並行処理の単位である「ゴルーチン（goroutine）」を提供します。ゴルーチンはOSのスレッドよりもはるかに軽量であり、数百万個のゴルーチンを同時に実行することも可能です。Goランタイムは、これらのゴルーチンをOSスレッドにマッピングし、スケジューリングを行う役割を担っています。

### 2. チャネル

チャネルは、ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは、Goの並行処理において安全なデータ共有を実現するための主要な手段です。チャネル操作（`send`または`receive`）が即座に完了できない場合（例: バッファなしチャネルへの送信で受信側がまだ準備できていない場合）、そのゴルーチンはブロックされ、チャネルの内部キューで待機します。

### 3. `sudog`構造体

`sudog`は`runtime.sudog`として定義されるGoランタイム内部のデータ構造です。その名前は"synchronization descriptor for goroutine"（ゴルーチンの同期記述子）または"pseudo-goroutine"（擬似ゴルーチン）に由来すると言われています。

`sudog`の主な役割は以下の通りです。
- **ブロックされたゴルーチンの表現**: チャネル操作（`send`または`receive`）や`sync.Mutex`、`sync.WaitGroup`などの同期プリミティブによってゴルーチンがブロックされた際に、そのゴルーチンに関する情報を保持します。
- **待機キューへの登録**: ブロックされたゴルーチンは、直接同期オブジェクトの待機キューに入るのではなく、`sudog`を介してキューに登録されます。これにより、ランタイムはゴルーチンの状態を抽象化し、効率的に管理できます。
- **ポインタフィールド**: `sudog`は、待機キュー内での連結リストを形成するための`next`、`prev`ポインタや、`select`文における複数のチャネル待機を管理するための`waitlink`などのポインタフィールドを持ちます。

### 4. メモリ管理とガベージコレクション (GC)

Go言語は自動メモリ管理（ガベージコレクション）を採用しています。プログラマは明示的にメモリを解放する必要がありません。GCは、プログラムがもはや到達できない（参照されていない）メモリ領域を自動的に識別し、解放します。

しかし、GCは「到達可能性」に基づいて動作します。つまり、たとえ論理的に不要になったオブジェクトであっても、他のオブジェクトから参照されている限り、GCはそれを「到達可能」と判断し、解放しません。これがメモリリークの一般的な原因となります。

### 5. `select`文

`select`文は、複数のチャネル操作を同時に待機し、最初に準備ができたチャネル操作を実行するためのGoの構文です。`select`は、非同期処理やタイムアウト処理の実装に不可欠です。`select`文の内部では、複数の`sudog`が生成され、それぞれのチャネルの待機キューに登録されることがあります。

## 技術的詳細

このコミットが修正する問題は、`sudog`構造体がスタックからヒープに移動されたことによって生じた、そのライフサイクル管理の不備に起因します。

### `sudog`のライフサイクルとキャッシュ

1.  **生成**: ゴルーチンがチャネル操作などでブロックされると、ランタイムは新しい`sudog`インスタンスを割り当てます。
2.  **使用**: 割り当てられた`sudog`は、ブロックされたゴルーチンの情報（どのチャネルで待機しているか、どのゴルーチンかなど）を保持し、チャネルの待機キュー（`sendq`または`recvq`）に連結リストの一部として追加されます。
3.  **再開と解放**: チャネル操作が完了し、ゴルーチンが再開されると、`sudog`は待機キューから削除され、その役割を終えます。
4.  **キャッシュへの返却**: 割り当てコストを削減するため、使用済みの`sudog`はすぐに解放されるのではなく、ランタイム内部の`sudogcache`にプールされます。これにより、次に`sudog`が必要になったときに、新しいメモリを割り当てる代わりにキャッシュから再利用できます。

### リークの原因

問題は、`sudog`がキャッシュに返される際に、その内部ポインタフィールド（`next`, `prev`, `waitlink`）が適切に`nil`にクリアされていなかった点にありました。

-   **`next`と`prev`**: これらは`sudog`がチャネルの待機キュー内で連結リストを形成するために使用されます。キャッシュに戻された`sudog`がこれらのポインタに古い値を保持していると、その`sudog`が論理的にはどのキューにも属していないにもかかわらず、古いリストの要素を指し続ける可能性があります。
-   **`waitlink`**: `select`文で使用される特別なポインタです。`select`は複数のチャネルを同時に待機するため、複数の`sudog`を生成し、それらを`waitlink`で連結して管理します。`select`が完了した後、これらの`sudog`がキャッシュに戻される際に`waitlink`がクリアされないと、キャッシュ内の`sudog`が、もはや存在しないか、あるいはGCによって収集されるべき他の`sudog`を指し続けることになります。

### リークのメカニズム

コミットメッセージで説明されているリークのメカニズムは以下の通りです。

1.  **ぶら下がった`waitlink`**: キャッシュに戻された`sudog`が、古い`waitlink`ポインタを保持しているとします。この`waitlink`は、以前に`select`文で使用され、その後「忘れられた」（つまり、もはやランタイムによって積極的に管理されていない）`sudog`キャッシュリスト内の別の`sudog`を指している可能性があります。
2.  **GCの妨害**: 通常、ランタイムが「忘れた」リストはGCの対象となり、メモリが解放されるはずです。しかし、キャッシュ内の`sudog`がそのリスト内の`sudog`を`waitlink`で参照し続けているため、GCはそのリストを「到達可能」と判断し、収集しません。
3.  **連鎖的なリーク**: さらに悪いことに、その「忘れられた」リスト内の`sudog`もまた、ぶら下がった`waitlink`を持っている可能性があり、それが別の「忘れられた」リストを指しているかもしれません。このようにして、`sudog`のリストが別の`sudog`のリストを参照し、それがさらに別のリストを参照するという、連鎖的な参照グラフが形成されます。
4.  **メモリの蓄積**: 結果として、論理的には不要であり、再利用されるべき`sudog`が、このぶら下がったポインタの連鎖によってオブジェクトグラフに残り続け、ガベージコレクタによって解放されなくなります。これにより、時間とともに使用できない`sudog`がメモリに蓄積され、メモリリークが発生します。

この問題は、特に非自明な`select`文（複数の`case`を持つもの）や、チャネル以外の同期プリミティブ（`sync.Mutex`など）が複雑に絡み合うシナリオで顕著に現れました。これらの状況では、`sudog`の生成と解放のパターンが複雑になり、ポインタのクリーンアップ漏れがより頻繁に、かつ深刻な影響を及ぼしたと考えられます。

## コアとなるコードの変更箇所

このコミットでは、`sudog`がキャッシュに戻される際や、キューから削除される際に、そのポインタフィールドを`nil`にクリアする処理が追加されています。

変更されたファイルと主な変更点は以下の通りです。

-   `src/runtime/chan.go`:
    -   `func (q *waitq) dequeue() *sudog`: `waitq`から`sudog`をデキューする際に、デキューされた`sudog`の`next`ポインタを`nil`に設定します。
    -   `func (q *waitq) dequeueSudoG(s *sudog)`: 特定の`sudog`を`waitq`からデキューする際に、デキューされた`sudog`の`next`ポインタを`nil`に設定します。
-   `src/runtime/mgc0.go`:
    -   `func clearpools()`: ガベージコレクション時にプールをクリアする関数です。`mcache.sudogcache`と`p.deferpool`（`_defer`構造体のキャッシュ）をクリアする際に、キャッシュ内の各要素の`next`（または`link`）ポインタを`nil`に設定し、連結を解除します。これにより、キャッシュ全体がGCによって収集されやすくなります。
-   `src/runtime/proc.go`:
    -   `func acquireSudog() *sudog`: `sudogcache`から`sudog`を取得する際に、取得した`sudog`の`next`ポインタを`nil`に設定します。
    -   `func releaseSudog(s *sudog)`: `sudog`を解放（キャッシュに戻す前）する際に、`s.next`, `s.prev`, `s.waitlink`が`nil`であることをチェックする`gothrow`（パニック）を追加しています。これは、これらのポインタが事前にクリアされていることを保証するためのアサーションです。
-   `src/runtime/select.go`:
    -   `loop`内の`select`処理後: `sglist.waitlink`を`nil`に設定し、`releaseSudog`を呼び出す前に`waitlink`の参照を切断します。
-   `src/runtime/sema.go`:
    -   `syncsemacquire`と`syncsemrelease`: `wake`（`sudog`）の`next`ポインタを`nil`に設定します。
-   `test/fixedbugs/issue9110.go`:
    -   このコミットで追加された新しいテストファイルです。`sudog`リークを再現し、修正が正しく機能することを確認するためのシナリオが含まれています。特に、`select`文と`sync.Cond`を組み合わせて、`sudog`がキャッシュに適切に戻され、GCによって収集されることを検証しています。

## コアとなるコードの解説

このコミットの核心は、`sudog`構造体のポインタフィールドを、その`sudog`が役割を終えてキャッシュに戻される際、またはキューから削除される際に、明示的に`nil`に設定することです。これにより、古い、ぶら下がった参照がオブジェクトグラフに残ることを防ぎ、ガベージコレクタが不要になった`sudog`を正しく収集できるようになります。

具体的な変更の例をいくつか挙げます。

### `src/runtime/chan.go` の変更

```go
// func (q *waitq) dequeue() *sudog {
// ...
// 		q.first = sgp.next
// +		sgp.next = nil // ここでsgp.nextをnilに設定
// 		if q.last == sgp {
// 			q.last = nil
// 		}
// ...
// }
```
`dequeue`関数は、チャネルの待機キューから`sudog`を取り出す際に呼び出されます。取り出された`sudog`（`sgp`）はもはやキューの連結リストの一部ではないため、その`next`ポインタを`nil`に設定することで、古い参照が残るのを防ぎます。

### `src/runtime/mgc0.go` の変更

```go
// func clearpools() {
// ...
// 			var sg, sgnext *sudog
// 			for sg = c.sudogcache; sg != nil; sg = sgnext {
// 				sgnext = sg.next
// +				sg.next = nil // キャッシュ内の各sudogのnextをnilに設定
// 			}
// 			c.sudogcache = nil
// ...
// }
```
`clearpools`関数は、GCサイクル中にランタイムの内部キャッシュをクリアするために使用されます。`sudogcache`内の`sudog`は、GCによって収集される可能性があるため、キャッシュをクリアする前に各`sudog`の`next`ポインタを`nil`に設定することで、キャッシュ内の`sudog`同士の連結を解除します。これにより、キャッシュ全体がGCの対象となりやすくなります。同様の処理が`deferpool`に対しても行われています。

### `src/runtime/proc.go` の変更

```go
// func releaseSudog(s *sudog) {
// ...
// +	if s.next != nil {
// +		gothrow("runtime: sudog with non-nil next")
// +	}
// +	if s.prev != nil {
// +		gothrow("runtime: sudog with non-nil prev")
// +	}
// +	if s.waitlink != nil {
// +		gothrow("runtime: sudog with non-nil waitlink")
// +	}
// ...
// }
```
`releaseSudog`関数は、`sudog`をキャッシュに戻す直前に呼び出されます。ここで、`next`, `prev`, `waitlink`の各ポインタが`nil`であることをアサート（`gothrow`）しています。これは、これらのポインタが既に他の場所で適切にクリアされていることを確認するための防御的なチェックです。もしクリアされていなければ、パニックが発生し、問題が早期に発見されるようになります。

これらの変更は、`sudog`がその役割を終えた際に、その内部状態（特にポインタ）を「クリーン」な状態に戻すことを徹底することで、メモリリークの原因となるぶら下がった参照を排除することを目的としています。これにより、ガベージコレクタがより効率的に動作し、ランタイムのメモリ使用量が安定するようになります。

## 変更の背景

Go言語のランタイムは、ゴルーチンのスケジューリングやチャネル通信といった並行処理の根幹を担っています。このコミットが行われた2014年当時、GoランタイムはC言語で書かれた部分とGo言語で書かれた部分が混在しており、Go言語への移行が進められていました。

`sudog`構造体は、Goの並行処理モデルにおいて非常に重要な役割を果たします。ゴルーチンがチャネル操作（送信または受信）によってブロックされる際、そのゴルーチンは直接チャネルの待機キューに追加されるのではなく、`sudog`という軽量なオブジェクトを介してキューに登録されます。これにより、ランタイムはブロックされたゴルーチンの状態を効率的に管理し、チャネル操作が完了した際に適切なゴルーチンを再開させることができます。

コミットメッセージによると、元々`sudog`はスタック上に割り当てられていました。スタック上のデータは関数のスコープを抜けると自動的に解放されるため、明示的なクリーンアップは不要でした。しかし、ランタイムのGo言語への移行プロセスにおいて、いくつかの理由（例えば、ガベージコレクションの対象とするため、あるいはより柔軟なメモリ管理を可能にするためなど）から、`sudog`をヒープ上に移動する必要が生じました。

ヒープ上に移動された`sudog`は、使用後に明示的に解放または再利用される必要があります。Goランタイムは、`sudog`の割り当てコストを削減するために、使用済みの`sudog`をキャッシュするメカニズムを導入しました。しかし、このキャッシュに`sudog`を戻す際に、内部のポインタフィールド（`next`, `prev`, `waitlink`など）が適切にnilにクリアされていなかったことが問題の根源でした。

これらの古いポインタが残っていると、たとえ`sudog`自体がキャッシュに戻されても、それが参照している他のオブジェクト（例えば、別の`sudog`や、既に解放されたはずのメモリ領域）への参照が残ってしまいます。特に、`sudog`が形成する連結リストの構造において、この「ぶら下がったポインタ」は深刻なメモリリークを引き起こす可能性がありました。ガベージコレクタは、到達可能なオブジェクトを収集しないため、たとえ論理的には不要になった`sudog`であっても、ぶら下がったポインタによって参照され続けている限り、メモリから解放されずに残り続けてしまうのです。

このリークは、特に複雑な`select`文や、チャネル以外の同期プリミティブが絡むシナリオで顕著に発生し、デバッグが非常に困難であったと述べられています。コミットの作者であるRuss Cox氏自身も、この問題の追跡に1週間を費やしたと記しており、その深刻さが伺えます。

## 前提知識の解説

### 1. Goランタイムとゴルーチン

Go言語は、軽量な並行処理の単位である「ゴルーチン（goroutine）」を提供します。ゴルーチンはOSのスレッドよりもはるかに軽量であり、数百万個のゴルーチンを同時に実行することも可能です。Goランタイムは、これらのゴルーチンをOSスレッドにマッピングし、スケジューリングを行う役割を担っています。

### 2. チャネル

チャネルは、ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは、Goの並行処理において安全なデータ共有を実現するための主要な手段です。チャネル操作（`send`または`receive`）が即座に完了できない場合（例: バッファなしチャネルへの送信で受信側がまだ準備できていない場合）、そのゴルーチンはブロックされ、チャネルの内部キューで待機します。

### 3. `sudog`構造体

`sudog`は`runtime.sudog`として定義されるGoランタイム内部のデータ構造です。その名前は"synchronization descriptor for goroutine"（ゴルーチンの同期記述子）または"pseudo-goroutine"（擬似ゴルーチン）に由来すると言われています。

`sudog`の主な役割は以下の通りです。
- **ブロックされたゴルーチンの表現**: チャネル操作（`send`または`receive`）や`sync.Mutex`、`sync.WaitGroup`などの同期プリミティブによってゴルーチンがブロックされた際に、そのゴルーチンに関する情報を保持します。
- **待機キューへの登録**: ブロックされたゴルーチンは、直接同期オブジェクトの待機キューに入るのではなく、`sudog`を介してキューに登録されます。これにより、ランタイムはゴルーチンの状態を抽象化し、効率的に管理できます。
- **ポインタフィールド**: `sudog`は、待機キュー内での連結リストを形成するための`next`、`prev`ポインタや、`select`文における複数のチャネル待機を管理するための`waitlink`などのポインタフィールドを持ちます。

### 4. メモリ管理とガベージコレクション (GC)

Go言語は自動メモリ管理（ガベージコレクション）を採用しています。プログラマは明示的にメモリを解放する必要がありません。GCは、プログラムがもはや到達できない（参照されていない）メモリ領域を自動的に識別し、解放します。

しかし、GCは「到達可能性」に基づいて動作します。つまり、たとえ論理的に不要になったオブジェクトであっても、他のオブジェクトから参照されている限り、GCはそれを「到達可能」と判断し、解放しません。これがメモリリークの一般的な原因となります。

### 5. `select`文

`select`文は、複数のチャネル操作を同時に待機し、最初に準備ができたチャネル操作を実行するためのGoの構文です。`select`は、非同期処理やタイムアウト処理の実装に不可欠です。`select`文の内部では、複数の`sudog`が生成され、それぞれのチャネルの待機キューに登録されることがあります。

## 技術的詳細

このコミットが修正する問題は、`sudog`構造体がスタックからヒープに移動されたことによって生じた、そのライフサイクル管理の不備に起因します。

### `sudog`のライフサイクルとキャッシュ

1.  **生成**: ゴルーチンがチャネル操作などでブロックされると、ランタイムは新しい`sudog`インスタンスを割り当てます。
2.  **使用**: 割り当てられた`sudog`は、ブロックされたゴルーチンの情報（どのチャネルで待機しているか、どのゴルーチンかなど）を保持し、チャネルの待機キュー（`sendq`または`recvq`）に連結リストの一部として追加されます。
3.  **再開と解放**: チャネル操作が完了し、ゴルーチンが再開されると、`sudog`は待機キューから削除され、その役割を終えます。
4.  **キャッシュへの返却**: 割り当てコストを削減するため、使用済みの`sudog`はすぐに解放されるのではなく、ランタイム内部の`sudogcache`にプールされます。これにより、次に`sudog`が必要になったときに、新しいメモリを割り当てる代わりにキャッシュから再利用できます。

### リークの原因

問題は、`sudog`がキャッシュに返される際に、その内部ポインタフィールド（`next`, `prev`, `waitlink`）が適切に`nil`にクリアされていなかった点にありました。

-   **`next`と`prev`**: これらは`sudog`がチャネルの待機キュー内で連結リストを形成するために使用されます。キャッシュに戻された`sudog`がこれらのポインタに古い値を保持していると、その`sudog`が論理的にはどのキューにも属していないにもかかわらず、古いリストの要素を指し続ける可能性があります。
-   **`waitlink`**: `select`文で使用される特別なポインタです。`select`は複数のチャネルを同時に待機するため、複数の`sudog`を生成し、それらを`waitlink`で連結して管理します。`select`が完了した後、これらの`sudog`がキャッシュに戻される際に`waitlink`がクリアされないと、キャッシュ内の`sudog`が、もはや存在しないか、あるいはGCによって収集されるべき他の`sudog`を指し続けることになります。

### リークのメカニズム

コミットメッセージで説明されているリークのメカニズムは以下の通りです。

1.  **ぶら下がった`waitlink`**: キャッシュに戻された`sudog`が、古い`waitlink`ポインタを保持しているとします。この`waitlink`は、以前に`select`文で使用され、その後「忘れられた」（つまり、もはやランタイムによって積極的に管理されていない）`sudog`キャッシュリスト内の別の`sudog`を指している可能性があります。
2.  **GCの妨害**: 通常、ランタイムが「忘れた」リストはGCの対象となり、メモリが解放されるはずです。しかし、キャッシュ内の`sudog`がそのリスト内の`sudog`を`waitlink`で参照し続けているため、GCはそのリストを「到達可能」と判断し、収集しません。
3.  **連鎖的なリーク**: さらに悪いことに、その「忘れられた」リスト内の`sudog`もまた、ぶら下がった`waitlink`を持っている可能性があり、それが別の「忘れられた」リストを指しているかもしれません。このようにして、`sudog`のリストが別の`sudog`のリストを参照し、それがさらに別のリストを参照するという、連鎖的な参照グラフが形成されます。
4.  **メモリの蓄積**: 結果として、論理的には不要であり、再利用されるべき`sudog`が、このぶら下がったポインタの連鎖によってオブジェクトグラフに残り続け、ガベージコレクタによって解放されなくなります。これにより、時間とともに使用できない`sudog`がメモリに蓄積され、メモリリークが発生します。

この問題は、特に非自明な`select`文（複数の`case`を持つもの）や、チャネル以外の同期プリミティブ（`sync.Mutex`など）が複雑に絡み合うシナリオで顕著に現れました。これらの状況では、`sudog`の生成と解放のパターンが複雑になり、ポインタのクリーンアップ漏れがより頻繁に、かつ深刻な影響を及ぼしたと考えられます。

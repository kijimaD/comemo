## 変更の背景

Goコンパイラは、Go 1.7でSSA (Static Single Assignment) 形式を導入し、コンパイラの最適化能力を大幅に向上させました。SSAの導入は、より小さく、より高速なGoバイナリを生成することを目的としており、コンパイラ開発における重要なマイルストーンでした。

このコミットが行われた2015年8月は、Go 1.7のリリース（2016年8月）に先立つSSA開発の活発な時期にあたります。SSAバックエンドはまだ開発途上にあり、多くの機能追加、最適化、およびバグ修正が必要とされていました。

`TODO`リストの更新は、開発の進捗に伴い、残されたタスクの再評価、優先順位付け、および新たな課題の追加を反映するものです。これにより、開発チームは現在の状況と今後の方向性をより明確に把握し、効率的に作業を進めることができます。

`schedule.go`へのコメント追加は、コードの特定の動作に関する理解を深めるためのものであり、スケジューリングロジックの微妙な側面を明確にする意図があります。これは、複雑なコンパイラコードベースにおけるドキュメンテーションと保守性の重要性を示しています。

## 前提知識の解説

### Goコンパイラ

Goコンパイラは、Go言語で書かれたソースコードを機械語に変換するツールです。`cmd/compile`ディレクトリ以下にその実装があり、複数のフェーズ（字句解析、構文解析、型チェック、中間表現生成、最適化、コード生成など）を経て最終的な実行可能ファイルを生成します。

### SSA (Static Single Assignment)

SSAは、コンパイラ最適化において広く用いられる中間表現（IR）の一種です。SSA形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析が大幅に簡素化され、定数伝播、デッドコード削除、共通部分式除去、nilチェック除去など、多くの強力な最適化をより効果的に適用できるようになります。Goコンパイラでは、AST (Abstract Syntax Tree) からSSA形式への変換が行われ、その後の最適化パスが適用されます。

### `cmd/compile/internal/ssa`パッケージ

このパッケージは、GoコンパイラのSSAバックエンドの主要な実装を含んでいます。SSA形式の生成、最適化パスの適用、および最終的な機械語コード生成のための準備を行います。Goコンパイラの性能向上において中心的な役割を担っています。

### 命令スケジューリング (Instruction Scheduling)

コンパイラにおける命令スケジューリングとは、プログラムのセマンティクス（意味）を変えることなく、命令の実行順序を並べ替える最適化手法です。主な目的は以下の通りです。
*   **レジスタプレッシャの削減**: 同時に生存する変数の数を減らし、レジスタの枯渇を防ぎ、メモリへのスピル（退避）を最小限に抑えます。
*   **パイプラインの効率化**: プロセッサのパイプラインを最大限に活用できるよう、依存関係のない命令を並行して実行できるように配置します。
*   **キャッシュ効率の向上**: データアクセスパターンを最適化し、キャッシュミスを減らします。

`schedule.go`ファイルは、SSA形式の命令を基本ブロック内で効率的に配置するためのアルゴリズムを実装しており、レジスタ割り当ての前段階として非常に重要です。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/compile/internal/ssa/TODO`ファイルの再編成と内容の更新です。以前の`TODO`リストは、`Allocation`, `Scheduling`, `Values`, `Regalloc`, `StackAlloc`, `Rewrites`, `Common-Subexpression Elimination`, `Other`といった大まかなカテゴリに分かれていました。

今回の更新では、より具体的かつ体系的なカテゴリが導入されています。
*   **Coverage**: SSAがまだ完全にカバーしていないGo言語の機能（浮動小数点数、複素数、整数除算、defer、クロージャ引数など）に関する項目。これは、SSAバックエンドの網羅性を高めるためのタスクを示唆しています。
*   **Correctness**: GCマップ、ライトバリア、デバッグ情報、パニックエッジの処理、レース検出器への対応など、コンパイラの正確性と堅牢性に関わる重要な項目。
*   **Optimizations (better compiled code)**: 生成されるコードの品質を向上させるための最適化（レジスタプレッシャ削減、強度削減、nil/境界チェック除去、メモリゼロ化/コピーの最適化、分岐予測など）。
*   **Optimizations (better compiler)**: コンパイラ自体の性能や保守性を向上させるための項目（`Value.Type`のサイズ削減、デッドな`Value`の再利用、定数キャッシュ、再利用可能なスライスなど）。
*   **Regalloc**: レジスタ割り当てに関する具体的な改善点（アーキテクチャ依存性の低減、スピルの最適化、2アドレス命令の処理、ライブネス解析の非二次化など）。
*   **Future/other**: 将来的なアーキテクチャサポート（ARM）、型等価性の調査、パスの有効化/無効化/設定のためのインフラなど、より広範な開発方向性を示す項目。

この再編成は、SSAバックエンドの開発が初期段階から成熟段階へと移行しつつあることを示唆しています。より詳細なカテゴリ分けにより、開発チームは特定の領域に焦点を当て、体系的に問題を解決できるようになります。多くの項目が以前のリストから移動または洗練されており、一部のタスクは完了したか、より具体的なサブタスクに分割された可能性があります。

`src/cmd/compile/internal/ssa/schedule.go`へのコメント追加は、`schedule`関数内で「ストアチェーンは異なるブロック間で互いに上書きされるため、計算されたストアチェーンはこのブロックに対してのみ有効である」という重要な実装の詳細を明確にしています。これは、メモリ操作の順序付けがブロックローカルな性質を持つことを強調し、将来のコード変更やデバッグの際に役立つ情報です。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/TODO`の変更

この変更は、GoコンパイラのSSAバックエンド開発におけるタスク管理の進化を明確に示しています。

*   **カテゴリの再定義**: 以前の広範なカテゴリ（`Allocation`, `Scheduling`, `Values`など）から、`Coverage`, `Correctness`, `Optimizations (better compiled code)`, `Optimizations (better compiler)`, `Regalloc`, `Future/other`といった、より機能的かつ具体的なカテゴリへと再定義されました。これにより、開発者は特定の目標（例えば、SSAの網羅性向上、コンパイラの正確性保証、生成コードの最適化など）に焦点を当てやすくなります。
*   **タスクの洗練と追加**: 多くの既存タスクが新しいカテゴリに移動され、表現が洗練されています。例えば、以前の`Scheduling`カテゴリにあった「Reduce register pressure」は、新しい`Optimizations (better compiled code)`カテゴリに移動し、より広範な最適化目標の一部として位置づけられています。また、「Floating point numbers」や「Complex numbers」のSSA対応など、新たなカバレッジ項目が追加されており、SSAの適用範囲を広げる意図が見られます。
*   **開発の優先順位の明確化**: この更新は、SSAバックエンドが単に機能するだけでなく、Go言語の全ての機能に対応し、正確で、高性能なコードを生成し、さらにコンパイラ自体の効率も高めるという多角的な目標に向かっていることを示しています。特に「Optimizations (better compiled code)」と「Optimizations (better compiler)」の分離は、生成されるコードの品質とコンパイラ自体の品質という二つの異なる側面からの最適化アプローチを強調しています。

### `src/cmd/compile/internal/ssa/schedule.go`の変更

`schedule.go`に追加されたコメントは、`schedule`関数内のストアチェーンの処理に関する重要な実装上の制約を説明しています。

```go
// Store chains for different blocks overwrite each other, so
// the calculated store chain is good only for this block.
```

このコメントは、`schedule`関数が各基本ブロック（`b`）に対してループ処理を行う際に、メモリ操作の依存関係を追跡する「ストアチェーン」が計算されることを示しています。しかし、このストアチェーンはブロックローカルなものであり、異なるブロックの処理時にはリセットまたは上書きされるため、その有効範囲が現在のブロックに限定されることを明示しています。

これは、コンパイラのスケジューリングにおいて、メモリ依存関係の解析が複雑であり、特にブロックをまたがるようなグローバルな解析には追加のメカニズムが必要であることを示唆しています。このコメントは、この関数の設計上の決定を文書化し、将来の保守担当者がこのコードを理解し、変更する際の誤解を防ぐのに役立ちます。

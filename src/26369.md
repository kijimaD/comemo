# [インデックス 26369] ファイルの概要

このコミットは、Goコンパイラの内部パッケージである `cmd/internal/obj` における重要なリファクタリングを導入しています。具体的には、アセンブリコードのレイアウト処理とオブジェクトファイルへの書き出し処理を分離することで、コンパイラのメモリ使用量削減と将来的なインクリメンタルコンパイルの基盤を築くことを目的としています。

## コミット

`cmd/internal/obj`: コードレイアウトとオブジェクト書き出しを分離

これは、コンパイラが各関数がコンパイルされるたびに `Prog` リストをコードに変換できるようにし、最後まで待つのではなく、コンパイラのワーキングセットを削減するはずです。ただし、Go 1.7までは実現されません。

また、これによりアセンブラの機械語出力テストをより簡単に書けるようになるため、今この変更が行われています。

Issue #13822に対応。

## 変更の背景

このコミットの主な背景には、Goコンパイラのパフォーマンスとメモリ効率の改善という長期的な目標があります。特に、以下の点が挙げられます。

1.  **コンパイラのワーキングセット削減**: 従来のGoコンパイラは、関数ごとに生成されたアセンブリ命令のリスト（`Prog`リスト）を、コンパイルプロセスの最後までメモリ上に保持していました。これにより、大規模なプログラムをコンパイルする際に、コンパイラが消費するメモリ量（ワーキングセット）が大きくなる傾向がありました。このコミットは、各関数がコンパイルされるたびに `Prog` リストを処理し、よりコンパクトな形式（`LSym`リスト）に変換することで、メモリ使用量を削減する将来的な変更の準備です。
2.  **Go 1.7でのインクリメンタルコンパイルの準備**: コミットメッセージに明記されているように、この変更はGo 1.7で導入される予定のインクリメンタルコンパイル（またはそれに類する最適化）の基盤となります。インクリメンタルコンパイルでは、変更された部分のみを再コンパイルするため、各関数のコード生成を独立して、かつ早期に完了できるメカニズムが必要です。コードレイアウトとオブジェクト書き出しの分離は、この独立した処理を可能にします。
3.  **アセンブラテストの容易化**: 副次的なメリットとして、アセンブラ（`cmd/asm`）の機械語出力に関するテストをより簡単に書けるようになることが挙げられています。コード生成とファイル書き出しのロジックが分離されることで、コード生成部分のみをテストしやすくなります。
4.  **Issue #13822への対応**: このコミットは、GoのIssueトラッカーで報告された #13822 に関連しています。このIssueは、コンパイラのメモリ使用量に関する問題や最適化の提案を扱っている可能性があります。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラおよびリンカの内部構造に関する知識が必要です。

*   **Goツールチェイン**: Go言語のプログラムは、`go build`コマンドによってコンパイル・リンクされます。このプロセスには、`cmd/compile`（コンパイラ）、`cmd/asm`（アセンブラ）、`cmd/link`（リンカ）といった内部ツールが関与します。
*   **`cmd/internal/obj`パッケージ**: このパッケージは、Goツールチェイン内で共通して使用される低レベルのオブジェクトファイルフォーマットとアセンブリ生成ユーティリティを提供します。コンパイラやアセンブラが機械語を生成する際に利用されます。
*   **`Prog` (Program Instruction)**: `cmd/internal/obj`パッケージで定義される構造体で、アセンブリ命令の抽象的な表現です。Goの関数がコンパイルされると、その関数内の各操作は `Prog` 構造体のリンクリストとして表現されます。これは、まだ最終的な機械語に変換されていない中間表現です。
*   **`LSym` (Linker Symbol)**: リンカシンボル（`LSym`）は、プログラム内の関数、グローバル変数、データセグメントなど、リンカが扱うすべてのシンボルを表す構造体です。`LSym`は、シンボルの名前、型、サイズ、そしてそのシンボルに関連付けられたコードやデータへのポインタなどの情報を含みます。オブジェクトファイル内では、これらのシンボルが配置され、相互参照されます。
*   **`Link`コンテキスト (`*Link`)**: `cmd/internal/obj`パッケージ内で、オブジェクトファイルの生成やシンボルの管理に関する状態を保持する主要なコンテキスト構造体です。コンパイラがオブジェクトファイルを生成する際に、この`Link`構造体を介して様々な情報がやり取りされます。
*   **オブジェクトファイル**: コンパイラやアセンブラによって生成される中間ファイルで、機械語コード、初期化済みデータ、未初期化データ（BSS）、シンボルテーブル、再配置情報などが含まれます。これらのオブジェクトファイルは、最終的にリンカによって結合され、実行可能ファイルやライブラリが生成されます。
*   **ワーキングセット (Working Set)**: プロセスが効率的に実行するために必要とする物理メモリの量です。ワーキングセットが大きいと、メモリ不足によるページング（ディスクI/O）が発生しやすくなり、パフォーマンスが低下する可能性があります。コンパイラの場合、コンパイル中に保持する中間表現の量がワーキングセットに大きく影響します。

## 技術的詳細

このコミットの技術的な核心は、`cmd/internal/obj`パッケージ内のオブジェクトファイル生成ロジックの再構築にあります。

以前の `Writeobjdirect` 関数は、以下の2つの主要なタスクを単一の関数内で実行していました。

1.  **コードレイアウトとシンボルリストの構築**: `ctxt.Plist`（`Prog`命令のリンクリスト）を走査し、各`Prog`命令を`LSym`シンボルに関連付け、`text`（コード）および`data`（データ）セグメントの`LSym`リンクリストを構築する。この過程で、命令のアドレス割り当てや再配置情報の準備も行われます。
2.  **オブジェクトファイルへの書き出し**: 構築された`LSym`リンクリスト（`text`と`data`）を基に、オブジェクトファイルのヘッダ、シンボル情報、コード、データを物理的なファイル（`Biobuf`）に書き出す。

このコミットでは、この2つのタスクを `Flushplist` と `Writeobjfile` という2つの独立した関数に分離しています。

*   **`Flushplist(ctxt *Link)`**:
    *   この関数は、`Writeobjdirect`からコードレイアウトとシンボルリスト構築のロジックを抽出したものです。
    *   `ctxt.Plist`を走査し、`Prog`命令を`LSym`シンボルに変換し、それらを`Link`コンテキスト（`ctxt`）内の新しいフィールドである `ctxt.Text`, `ctxt.Data`, `ctxt.Etext`, `ctxt.Edata` に格納します。
    *   `ctxt.Text`はコードセグメントの最初の`LSym`を指し、`ctxt.Etext`は最後の`LSym`を指します。同様に、`ctxt.Data`と`ctxt.Edata`はデータセグメントの最初と最後の`LSym`を指します。
    *   処理が完了すると、`ctxt.Plist`は`nil`に設定され、`Prog`リストが「フラッシュ」されたことを示します。これにより、`Prog`リストがメモリから解放され、ワーキングセットの削減に貢献します。
*   **`Writeobjfile(ctxt *Link, b *Biobuf)`**:
    *   この関数は、オブジェクトファイルのヘッダを書き出し、その後`ctxt.Text`と`ctxt.Data`に格納された`LSym`リンクリストを走査して、各シンボルの情報を`Biobuf`（バッファリングされたI/O）に書き出す役割を担います。
    *   この関数は、純粋にオブジェクトファイルのフォーマットに従ってデータを書き出すことに特化しており、コードレイアウトのロジックからは独立しています。

この分離により、コンパイラは各関数をコンパイルするたびに`Flushplist`を呼び出して`Prog`リストを`LSym`リストに変換し、`Prog`リストが占めるメモリを早期に解放できるようになります。これにより、コンパイラ全体のメモリフットプリントが削減され、特に大規模なコードベースのコンパイル時にメリットが期待されます。

## コアとなるコードの変更箇所

### `src/cmd/internal/obj/link.go`

`Link`構造体に以下のフィールドが追加されました。

```go
type Link struct {
	// ... 既存のフィールド ...
	Version            int
	Textp              *LSym
	Etextp             *LSym

	// state for writing objects
	Text  *LSym // コードセグメントの最初のシンボル
	Data  *LSym // データセグメントの最初のシンボル
	Etext *LSym // コードセグメントの最後のシンボル
	Edata *LSym // データセグメントの最後のシンボル
}
```
これらのフィールドは、オブジェクトファイル書き出しの状態を`Link`コンテキスト内で保持するために導入されました。これにより、`Flushplist`と`Writeobjfile`間でシンボルリストのヘッドとテールを共有できるようになります。

### `src/cmd/internal/obj/objfile.go`

1.  **`Writeobjdirect`関数の変更**:
    *   以前の`Writeobjdirect`関数は、`Prog`リストの処理とオブジェクトファイルの書き出しの両方を行っていました。
    *   変更後、この関数は新しい`Flushplist(ctxt)`を呼び出してコードレイアウトを行い、その後`Writeobjfile(ctxt, b)`を呼び出してオブジェクトファイルを書き出すようになりました。
    *   関数内のローカル変数として宣言されていた`text`, `data`, `etext`, `edata`は削除され、`Link`コンテキストのフィールドを使用するように変更されました。

    ```go
    func Writeobjdirect(ctxt *Link, b *Biobuf) {
    	Flushplist(ctxt) // コードレイアウトとシンボルリスト構築
    	Writeobjfile(ctxt, b) // オブジェクトファイル書き出し
    }
    ```

2.  **`Flushplist(ctxt *Link)`関数の新規追加**:
    *   `Writeobjdirect`から抽出された、`Prog`リストを走査して`LSym`リストを構築するロジックがこの関数に移動しました。
    *   `ctxt.Plist`を処理し、結果を`ctxt.Text`, `ctxt.Data`, `ctxt.Etext`, `ctxt.Edata`に格納します。
    *   データシンボルの処理において、`data`と`edata`ローカル変数の代わりに`ctxt.Data`と`ctxt.Edata`が使用されるようになりました。
    *   コードシンボルの処理後、`ctxt.Text`と`ctxt.Etext`が適切に設定され、`ctxt.Plist`が`nil`にクリアされます。

    ```go
    func Flushplist(ctxt *Link) {
    	// ... (Progリストを走査し、LSymを構築する既存のロジック) ...

    	// データシンボルの処理でctxt.Dataとctxt.Edataを使用
    	// if data == nil { data = s } else { edata.Next = s }
    	// が
    	// if ctxt.Data == nil { ctxt.Data = s } else { ctxt.Edata.Next = s }
    	// に変更

    	// ... (その他のシンボル処理) ...

    	// コードシンボルをctxtに格納
    	if ctxt.Etext == nil {
    		ctxt.Text = text
    	} else {
    		ctxt.Etext.Next = text
    	}
    	ctxt.Etext = etext
    	ctxt.Plist = nil // Progリストをクリア
    }
    ```

3.  **`Writeobjfile(ctxt *Link, b *Biobuf)`関数の新規追加**:
    *   `Writeobjdirect`から抽出された、オブジェクトファイルのヘッダとシンボルを書き出すロジックがこの関数に移動しました。
    *   シンボルを書き出すループで、ローカル変数`text`と`data`の代わりに`ctxt.Text`と`ctxt.Data`が使用されるようになりました。

    ```go
    func Writeobjfile(ctxt *Link, b *Biobuf) {
    	// Emit header. (ヘッダの書き出し)
    	// ...

    	// Emit symbols. (シンボルの書き出し)
    	for s := ctxt.Text; s != nil; s = s.Next { // ctxt.Textを使用
    		writesym(ctxt, b, s)
    	}
    	for s := ctxt.Data; s != nil; s = s.Next { // ctxt.Dataを使用
    		writesym(ctxt, b, s)
    	}
    	// ...
    }
    ```

## コアとなるコードの解説

このコミットの核心は、Goコンパイラがオブジェクトファイルを生成する際の内部処理フローを、よりモジュール化された2段階のプロセスに再構築した点にあります。

1.  **`Link`構造体の拡張**:
    `Link`構造体に`Text`, `Data`, `Etext`, `Edata`という4つの`*LSym`フィールドが追加されたことは、オブジェクトファイルのコードセグメントとデータセグメントの開始と終了を指すポインタを、`Link`コンテキスト自体が保持するようになったことを意味します。これにより、これらの重要な状態が関数間で明示的に渡されるようになり、コードの可読性と保守性が向上します。以前はこれらの情報は`Writeobjdirect`関数内のローカル変数として管理されており、関数の責務が肥大化していました。

2.  **`Writeobjdirect`のデカップリング**:
    `Writeobjdirect`関数は、もともと「`Prog`リストを処理してオブジェクトファイルを直接書き出す」という複合的な役割を担っていました。このコミットにより、その役割は`Flushplist`と`Writeobjfile`という2つのより特化した関数に分割されました。
    *   `Flushplist(ctxt)`: この関数は、コンパイラが生成したアセンブリ命令の抽象表現である`Prog`リスト（`ctxt.Plist`）を、リンカが扱う具体的なシンボル表現である`LSym`リストに変換する役割を担います。この変換プロセスには、命令のサイズ計算、アドレス割り当て、再配置情報の準備などが含まれます。この処理が完了すると、`Prog`リストは不要になり、`ctxt.Plist = nil`とすることでメモリから解放されます。これが、コンパイラのワーキングセット削減の鍵となります。
    *   `Writeobjfile(ctxt, b)`: この関数は、`Flushplist`によって準備された`LSym`リスト（`ctxt.Text`と`ctxt.Data`）を基に、実際のオブジェクトファイルフォーマットに従ってバイナリデータを`Biobuf`（バッファ付きI/Oライター）に書き出します。この関数は、データのシリアライズに特化しており、コードの論理的なレイアウトには関与しません。

この分離は、コンパイラが各関数をコンパイルし終えるたびに`Flushplist`を呼び出すことを可能にします。これにより、コンパイラはすべての関数がコンパイルされるまで`Prog`リストを保持し続ける必要がなくなり、メモリ使用量を大幅に削減できます。これは、特に大規模なGoプロジェクトをコンパイルする際のメモリ効率とビルド時間の改善に繋がる、Go 1.7以降のコンパイラ最適化に向けた重要な一歩です。また、アセンブラの機械語出力テストを記述する際にも、コード生成ロジックとファイル書き出しロジックが明確に分離されているため、テスト対象の範囲を絞りやすくなり、テストの作成と保守が容易になります。

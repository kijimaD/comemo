## 元コミット内容

このコミットは、GoコンパイラのSSAバックエンドにおける`check()`関数内の支配関係チェックの誤りを修正します。具体的には、祖先比較の引数の順序が逆になっていたため、`def-must-dominate-use`という重要なチェックが正しく機能していませんでした。この修正により、SSA形式のコードの健全性が保証され、コンパイラの安定性と最適化の正確性が向上します。

## 変更の背景

Goコンパイラは、コードの最適化を効率的に行うためにSSA（Static Single Assignment）形式という中間表現を使用しています。SSA形式では、各変数が一度だけ定義されるという特性があり、これによりデータフロー解析が容易になります。SSA形式の重要な不変条件の一つに「`def-must-dominate-use`」があります。これは、ある変数の定義（`def`）が、その変数のすべての使用（`use`）を支配しなければならないというルールです。このルールが守られることで、変数が使用される際には必ず定義済みであることが保証され、コンパイラは安全に最適化を進めることができます。

このコミット以前は、`src/cmd/compile/internal/ssa/check.go`内の`domCheck`関数において、この支配関係をチェックする`sdom.isAncestorEq`関数の引数の順序が誤っていました。結果として、`def-must-dominate-use`のチェックが実質的に無効化されており、SSA形式のコードがこの不変条件を満たしていない場合でもエラーが検出されない可能性がありました。このようなバグは、コンパイラが不正なSSAコードを生成したり、その後の最適化フェーズで予期せぬ動作を引き起こしたりする原因となり得ます。

この問題は、おそらくGoのIssueトラッカーで報告されたIssue #15084に関連しており、その解決のためにこの修正が導入されました。

## 前提知識の解説

### 1. GoコンパイラとSSA (Static Single Assignment)

*   **Goコンパイラ**: Go言語のソースコードを機械語に変換するプログラムです。`cmd/compile`はGoコンパイラの主要部分を指します。
*   **SSA (Static Single Assignment) 形式**: コンパイラの中間表現（IR）の一種で、各変数がプログラム内で一度だけ定義されるように変換されます。例えば、`x = 1; x = 2; y = x;`というコードは、SSA形式では`x1 = 1; x2 = 2; y1 = x2;`のように変換されます。これにより、データフロー解析が非常に単純化され、様々な最適化（定数伝播、デッドコード削除など）が容易になります。

### 2. 制御フローグラフ (Control Flow Graph, CFG)

*   プログラムの実行パスをグラフで表現したものです。ノードは「基本ブロック」（連続した命令のシーケンスで、単一の入り口と出口を持つ）を表し、エッジは基本ブロック間の制御の移行を表します。

### 3. 支配関係 (Dominance) と支配木 (Dominator Tree)

*   **支配関係**: 制御フローグラフにおいて、あるノード `A` が別のノード `B` を「支配する」とは、プログラムのエントリポイントから `B` へのすべてのパスが `A` を通過する場合を言います。すべてのノードは自分自身を支配します。
*   **厳密な支配 (Strict Dominance)**: `A` が `B` を支配し、かつ `A` と `B` が異なる場合、`A` は `B` を厳密に支配すると言います。
*   **即時支配者 (Immediate Dominator)**: ノード `B` の即時支配者 `IDom(B)` は、`B` を厳密に支配するすべてのノードの中で、`B` に最も近いノードです。即時支配者は一意に定まります。
*   **支配木 (Dominator Tree)**: 制御フローグラフから構築される木構造で、各ノードの親がそのノードの即時支配者となります。プログラムのエントリポイントが木の根になります。支配木は、データフロー解析や最適化において非常に重要な役割を果たします。

### 4. `def-must-dominate-use` 不変条件

*   SSA形式の基本的なルールであり、健全性を保証するものです。SSA形式のプログラムにおいて、ある変数の定義（`def`）が行われる基本ブロックは、その変数が使用される（`use`）すべての基本ブロックを支配しなければなりません。
*   このルールが破られると、変数が定義される前に使用される可能性が生じ、プログラムの動作が不定になったり、コンパイラが誤った最適化を行ったりする原因となります。

### 5. `sparseTree` と `isAncestorEq`

*   `sparseTree`: GoコンパイラのSSAバックエンドで使用されるデータ構造で、支配木を効率的に表現・操作するためのものです。
*   `isAncestorEq(a, b)`: この関数は、`a` が `b` の祖先であるか、または `a` と `b` が同じノードであるかを判定します。支配木の文脈では、`a` が `b` の祖先であることは、`a` が `b` を支配することと同義です。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおける`check.go`ファイル内の`domCheck`関数に焦点を当てています。`domCheck`関数は、SSA形式のコードが`def-must-dominate-use`の不変条件を満たしているかを検証する役割を担っています。

`domCheck(f *Func, sdom sparseTree, x, y *Block) bool`関数は、ブロック`x`がブロック`y`を支配するかどうかを報告します（`x == y`の場合も含む）。この関数内で、到達不能なブロックを無視するための初期チェックが行われています。

元のコードは以下のようになっていました。

```go
func domCheck(f *Func, sdom sparseTree, x, y *Block) bool {
	if !sdom.isAncestorEq(y, f.Entry) {
		// unreachable - ignore
		return true
	}
    // ...
}
```

ここで問題となっていたのは、`sdom.isAncestorEq(y, f.Entry)`という呼び出しです。`isAncestorEq(ancestor, descendant)`という一般的な命名規則や、支配関係の定義（エントリポイントから`descendant`へのすべてのパスが`ancestor`を通過する）を考えると、`isAncestorEq`関数は第一引数に祖先（支配者）候補、第二引数に子孫（被支配者）候補を取るのが自然です。

しかし、元のコードでは`y`（被支配者候補）が第一引数に、`f.Entry`（プログラムのエントリブロック、支配木の根）が第二引数に渡されていました。これは「`y`が`f.Entry`の祖先であるか」という、支配関係の文脈では意味をなさない、あるいは意図しないチェックになっていました。

正しいチェックは、「`y`が`f.Entry`によって支配されているか」、つまり「`f.Entry`が`y`の祖先であるか」を確認することです。プログラムのエントリブロックは常にすべての到達可能なブロックを支配するため、このチェックは実質的に「`y`が到達可能であるか」を判断するために使われます。もし`y`が`f.Entry`によって支配されていない（つまり`f.Entry`が`y`の祖先ではない）ならば、`y`は到達不能なブロックであると判断できます。

この誤った引数順序のため、`!sdom.isAncestorEq(y, f.Entry)`という条件は、意図した「`y`が到達不能である」という状況を正しく検出できていませんでした。結果として、`def-must-dominate-use`のチェックが、到達不能なブロックに対しても誤った前提で実行されるか、あるいは到達可能性のチェック自体が機能せず、本来検出されるべきSSAの不変条件違反が見過ごされる可能性がありました。

## コアとなるコードの解説

変更された行は以下の通りです。

**変更前:**
```go
	if !sdom.isAncestorEq(y, f.Entry) {
```

**変更後:**
```go
	if !sdom.isAncestorEq(f.Entry, y) {
```

この変更は、`sdom.isAncestorEq`関数の引数の順序を修正しています。

*   `f.Entry`: これは関数`f`のエントリブロックを指します。支配木の根であり、すべての到達可能なブロックを支配します。
*   `y`: これは`domCheck`関数でチェック対象となっているブロックです。

変更前は「`y`が`f.Entry`の祖先であるか」をチェックしていました。これは、`y`がエントリブロック自身である場合を除き、常に偽となります。したがって、`!sdom.isAncestorEq(y, f.Entry)`という条件は、`y`がエントリブロックでない限り常に真となり、到達不能なブロックを正しく識別できていませんでした。

変更後は「`f.Entry`が`y`の祖先であるか」をチェックしています。これは、`f.Entry`が`y`を支配するかどうか、つまり`y`が`f.Entry`から到達可能であるかを正確に判断します。もし`f.Entry`が`y`の祖先ではない場合、それは`y`が到達不能なブロックであることを意味し、その場合は`def-must-dominate-use`チェックをスキップして`true`を返します（到達不能なコードはSSAの不変条件を破っても問題ないため）。

この修正により、`domCheck`関数は到達不能なブロックを正しく識別し、`def-must-dominate-use`のチェックが意図通りに機能するようになりました。これにより、GoコンパイラのSSAバックエンドの健全性が向上し、より信頼性の高いコード生成と最適化が可能になります。

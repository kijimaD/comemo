## 元コミット内容

`cmd/test: require external linking for c-archive`

このコミットは、`cmd/test` コマンドにおいて、`c-archive` 形式のテストを実行する際に外部リンキングを必須とする変更です。

## 変更の背景

Go言語は、C言語との相互運用性を提供するためにCgoという機能を持っています。Cgoを使用すると、GoのコードからCの関数を呼び出したり、CのコードからGoの関数を呼び出したりすることができます。Goのビルドモードには、GoのコードをCのライブラリとしてエクスポートするための `c-archive` や `c-shared` といったオプションがあります。

`c-archive` は、GoのパッケージをCの静的ライブラリ（.aファイル）としてビルドするモードです。この静的ライブラリは、C/C++のプロジェクトにリンクして使用することができます。

このコミットの背景には、`c-archive` でビルドされたライブラリが、内部リンキング（internal linking）では正しく動作しない、あるいは特定のプラットフォーム（特にmacOSのamd64アーキテクチャ）で問題を引き起こす可能性があったことが考えられます。外部リンキング（external linking）は、Goのリンカではなく、システムのCリンカ（gccやclangなど）を使用して最終的な実行可能ファイルやライブラリをリンクする方式です。これにより、Cgoで生成されたコードや、Cのライブラリとの連携がより確実に行われるようになります。

したがって、`c-archive` のテストが意図した通りに機能するためには、外部リンキングが必須であるという判断がなされ、この変更が導入されました。これにより、テストの信頼性が向上し、`c-archive` のビルドモードが正しく検証されるようになります。

## 前提知識の解説

### Go言語のビルドモードとリンキング

Go言語のビルドプロセスには、いくつかの重要な概念があります。

*   **内部リンキング (Internal Linking)**: Goのツールチェインが提供する独自のリンカ（`go tool link`）を使用して、Goのオブジェクトファイルと必要なランタイムライブラリをリンクし、実行可能ファイルを生成するデフォルトの方式です。この方式は高速で、Goのコードのみで構成されるアプリケーションに適しています。
*   **外部リンキング (External Linking)**: Cgoを使用する場合や、特定のシステムライブラリに依存する場合に必要となるリンキング方式です。この場合、Goのリンカはオブジェクトファイルを生成するだけで、最終的なリンクはシステムのCリンカ（例: GCC, Clang）に委ねられます。これにより、Cgoで生成されたCのスタブコードや、C/C++で書かれた外部ライブラリとの連携がスムーズに行われます。外部リンキングは、内部リンキングに比べてビルド時間が長くなる傾向があります。
*   **`c-archive` ビルドモード**: `go build -buildmode=c-archive` コマンドでGoのパッケージをビルドすると、そのパッケージはCの静的ライブラリ（例: `libyourpackage.a`）と、Cのヘッダーファイル（`yourpackage.h`）として出力されます。この静的ライブラリは、C/C++のアプリケーションにリンクして、Goの関数をCの関数として呼び出すことができます。
*   **`cmd/dist`**: Goのソースコードリポジトリに含まれるツールで、Goのビルドシステムやテストシステムを管理します。`src/cmd/dist/test.go` は、Goの標準ライブラリやツールチェインのテストを実行するためのロジックを含んでいます。
*   **`t.extLink()`**: `src/cmd/dist/test.go` 内の `tester` 構造体のメソッドで、現在のビルド設定が外部リンキングを使用しているかどうかを判定します。このメソッドは、Goのビルドフラグや環境変数（例: `CGO_ENABLED=1`）に基づいて、外部リンキングが有効になっているかをチェックします。
*   **`goos` と `goarch`**: Goのビルド環境変数を表します。`goos` はオペレーティングシステム（例: `darwin` for macOS, `linux` for Linux）、`goarch` はアーキテクチャ（例: `amd64` for 64-bit Intel/AMD, `arm64` for 64-bit ARM）を示します。

### Cgoとリンキングの複雑性

Cgoを使用するGoプログラムは、GoのコードとCのコードの両方を含んでいます。GoのコンパイラはGoのコードをコンパイルし、CgoはCのコードをコンパイルし、GoとCの間のブリッジコードを生成します。これらのコンパイルされたコードは、最終的に一つの実行可能ファイルまたはライブラリにリンクされる必要があります。

内部リンキングはGoのランタイムとGoのコードに最適化されていますが、Cのコードや外部Cライブラリとの連携においては、システムのリンカが持つより高度な機能（例: 共有ライブラリの解決、特定のシステムコールへのリンク）が必要になる場合があります。特に、`c-archive` のようにGoのコードがCのライブラリとして振る舞う場合、そのライブラリがCのリンキング規則に完全に準拠していることが重要になります。

## 技術的詳細

このコミットは、`src/cmd/dist/test.go` ファイル内の `registerTests` 関数を変更しています。この関数は、Goのテストスイートに様々なテストを登録する役割を担っています。

変更前のコードは以下の通りでした。

```go
		if t.goos == "darwin" && t.goarch == "amd64" {
			// TODO(crawshaw): add darwin/arm{,64}
			t.registerTest("testcarchive", "../misc/cgo/testcarchive", "./test.bash")
		}
```

このコードは、オペレーティングシステムが `darwin` (macOS) で、アーキテクチャが `amd64` の場合にのみ、`testcarchive` というテストを登録していました。`testcarchive` は、`../misc/cgo/testcarchive` ディレクトリにあるテストで、`c-archive` ビルドモードに関連するCgoのテストと考えられます。

変更後のコードは以下の通りです。

```go
		if t.extLink() && t.goos == "darwin" && t.goarch == "amd64" {
			// TODO(crawshaw): add darwin/arm{,64}
			t.registerTest("testcarchive", "../misc/cgo/testcarchive", "./test.bash")
		}
```

追加された条件は `t.extLink()` です。これにより、`testcarchive` テストが登録されるのは、以下の**全ての**条件が満たされた場合のみとなります。

1.  `t.extLink()` が `true` を返す（つまり、外部リンキングが有効になっている）。
2.  `t.goos` が `"darwin"` である（macOS）。
3.  `t.goarch` が `"amd64"` である（64-bit Intel/AMDアーキテクチャ）。

この変更は、`c-archive` 形式でビルドされたGoのライブラリが、外部リンキングを使用しないと正しくテストできない、あるいは特定の環境で問題が発生するという知見に基づいています。特にmacOSのamd64環境では、Cgoとリンキングの挙動が他のプラットフォームと異なる場合があり、外部リンキングがより堅牢な解決策となることがあります。

`testcarchive` テストは、Goの`c-archive`ビルドモードが正しく機能するかどうかを検証するための重要なテストです。このテストが外部リンキングを必要とすることで、Goのツールチェインが`c-archive`ライブラリをビルドする際のリンキング要件を正しく反映し、テストの信頼性を高めています。

この変更の意図は、`c-archive` ビルドモードで生成されたライブラリのテストが、外部リンキングが有効な環境でのみ意味を持つことを保証することです。内部リンキングでは、`c-archive` の特定の側面が正しくテストできないか、予期せぬ問題を引き起こす可能性があるため、この制約が導入されました。これにより、GoのCgo機能、特に`c-archive`ビルドモードの堅牢性と信頼性が向上します。

# [インデックス 2440] ファイルの概要

このコミットは、Go言語のARMアーキテクチャ向けツールチェイン（特にリンカ `5l`）における重要な機能強化を導入しています。主な目的は、`ld/go.c` に由来するGoランタイム固有の機能を `5l` リンカに統合することです。これには、デッドコード削除の改善、型シグネチャの処理、文字列データの最適化が含まれます。また、アセンブラ `5a`、コンパイラ `5c`、リンカ `5l` 全体で新しいヘッダーサポートが追加されています。これにより、Goバイナリの効率性と正確性が向上し、特にランタイムのメタデータ管理が洗練されています。

## 元コミット内容

`ld/go.c` の機能を `5l` に追加しました。主にデッドコード削除、型シグネチャ、および文字列に関するものです。
また、`5c/5a/5l` に新しいヘッダーサポートを追加しました。

## 変更の背景

このコミットが行われた2009年は、Go言語がまだ初期開発段階にあった時期です。Goのツールチェインは、Plan 9オペレーティングシステムのツールチェイン設計に強く影響を受けており、`5a` (アセンブラ)、`5c` (コンパイラ)、`5l` (リンカ) といった名称はその名残です。数字の「5」は、当時のARMアーキテクチャを指していました。

Go言語は、ガベージコレクション、リフレクション、並行処理といった高度なランタイム機能を備えており、これらの機能はコンパイルされたバイナリ内に特定のメタデータを必要とします。初期のGoツールチェインでは、これらのGo固有のランタイム要件を効率的に処理するためのリンカ機能が進化途上にありました。

このコミットの背景には、以下の必要性がありました。

1.  **バイナリサイズの最適化**: デッドコード削除は、最終的な実行可能ファイルのサイズを削減し、起動時間を短縮するために不可欠です。Goのランタイムは多くのメタデータを生成するため、不要なコードやデータを正確に識別して削除する能力が求められました。
2.  **ランタイムメタデータの正確な管理**: 型シグネチャや文字列データは、リフレクションやデバッグ情報、エラーメッセージなどに利用されます。これらの情報をリンカが適切に処理し、必要なものだけを残し、不要なものを削除することで、バイナリの効率性を高める必要がありました。
3.  **ツールチェインの一貫性**: `ld/go.c` は、Goランタイム固有のリンキングロジックをカプセル化していたと考えられます。この機能を主要なリンカ `5l` に直接統合することで、ツールチェイン全体の整合性を高め、Go固有のリンキング処理をより効率的かつ堅牢に行うことを目指しました。
4.  **新しいヘッダーサポート**: ツールチェインの各コンポーネント（アセンブラ、コンパイラ、リンカ）間で情報をやり取りするための新しいヘッダー形式を導入することで、ビルドプロセスの柔軟性と拡張性を向上させる狙いがありました。

これらの変更は、Go言語の初期の段階で、そのランタイムの効率性とバイナリの品質を向上させるための基盤を築く上で重要な一歩でした。

## 前提知識の解説

### Goツールチェイン (5a, 5c, 5l)
Go言語の初期のツールチェインは、Plan 9の設計思想を受け継いでいました。
*   **5a (Assembler)**: ARMアーキテクチャ向けのアセンブラ。アセンブリ言語のソースコードをオブジェクトファイルに変換します。
*   **5c (Compiler)**: ARMアーキテクチャ向けのコンパイラ。Goのソースコードをオブジェクトファイルに変換します。
*   **5l (Linker)**: ARMアーキテクチャ向けのリンカ。複数のオブジェクトファイルとライブラリを結合して、実行可能なバイナリを生成します。
現代のGoでは、これらの機能は `go tool asm`, `go tool compile`, `go tool link` として統合されていますが、基本的な役割は変わりません。

### リンカとデッドコード削除 (DCE)
リンカは、プログラムを構成する複数のオブジェクトファイルやライブラリを結合し、最終的な実行可能ファイルを生成するソフトウェアです。この過程で、シンボル解決（関数や変数のアドレスを決定する）や再配置（コード内のアドレス参照を修正する）などの重要なタスクを実行します。
**デッドコード削除 (Dead Code Elimination, DCE)** は、リンカの重要な最適化機能の一つです。これは、プログラムの実行に決して到達しない、または結果に影響を与えないコードやデータを識別し、最終的なバイナリから削除するプロセスです。DCEは、バイナリサイズを削減し、ロード時間を短縮し、キャッシュ効率を向上させることで、プログラムのパフォーマンスを改善します。
Goリンカは、プログラムのエントリポイント（`main`関数やパッケージの`init`関数）からシンボルグラフを辿り、到達可能なすべてのシンボルをマークすることでDCEを実行します。マークされなかったシンボルは削除されます。

### Goランタイムにおける型情報 (Type Signatures) と文字列
Go言語は、リフレクションやインターフェースの動的なディスパッチ、ガベージコレクション、スタックトレース生成などのために、実行時に型情報（Runtime Type Information, RTTI）を必要とします。
*   **型シグネチャ (Type Signatures)**: 関数の引数や戻り値の型、構造体のフィールドの型など、型の構造を記述する情報です。これらは、インターフェースの適合性チェックやリフレクションAPI (`reflect`パッケージ) で利用されます。
*   **文字列データ**: ソースファイルパス（スタックトレース用）、型名、埋め込みリテラル文字列などが含まれます。これらの文字列の一部は、デバッグやランタイムの動作に不可欠であり、DCEの対象から外れることがあります。
リフレクションを使用するプログラムでは、リンカはより保守的なDCE戦略を採用することがあり、動的に呼び出される可能性のあるメソッドや型情報を保持するため、バイナリサイズが大きくなることがあります。

### `moduledata` 構造体とランタイムデータ管理
Goランタイムは、プログラムの実行に必要な様々なメタデータを `moduledata` と呼ばれる構造体で管理しています。これには、型情報、シンボルテーブル、ガベージコレクション関連のデータなどが含まれます。リンカは、これらの `moduledata` 構造体を適切に配置し、ランタイムがそれらにアクセスできるようにする必要があります。`datap` や `edatap` といったリンカ内部のポインタは、これらの `moduledata` 構造体や関連するデータセグメントの開始と終了を管理するために使用されます。

### `ld/go.c` の役割
`ld/go.c` は、Goツールチェイン内でC言語との連携（特に `cgo` を使用する場合）に関連するリンキング処理を扱うファイルであったと考えられます。`cgo` はGoコードからC関数を呼び出したり、Cライブラリを使用したりするためのメカニズムであり、この場合、Cコンパイラによって生成されたオブジェクトファイルとGoコンパイラによって生成されたオブジェクトファイルを結合する必要があります。`ld/go.c` は、C言語特有のリンキングタスク（Cライブラリからのシンボル解決、C呼び出し規約の処理など）をGoリンカに統合する役割を担っていた可能性があります。

## 技術的詳細

このコミットは、GoのARMリンカ `5l` に `ld/go.c` の機能を統合することで、Goバイナリの生成プロセスにいくつかの重要な改善をもたらしました。

1.  **`ld/go.c` 機能の `5l` への統合**:
    *   `src/cmd/5l/obj.c` 内で、以前コメントアウトされていた `definetypestrings()`, `definetypesigs()`, `deadcode()` の呼び出しが有効化されました。これは、Goランタイムが要求する型情報（型シグネチャ）と文字列データの定義、そしてデッドコード削除のロジックが、`5l` リンカの主要な処理フローに組み込まれたことを意味します。
    *   `definetypestrings()` は、Goの型名やその他のランタイムに必要な文字列を定義し、リンカがそれらをバイナリに含めるようにします。
    *   `definetypesigs()` は、Goの型シグネチャ（インターフェースの適合性チェックやリフレクションに必要）を定義し、リンカがこれらを適切に処理するようにします。
    *   `deadcode()` は、Goプログラムから到達不可能なコードやデータを識別し、最終的なバイナリから削除するプロセスを実行します。これにより、バイナリサイズが最適化されます。

2.  **新しいヘッダーサポートの導入**:
    *   `src/cmd/5a/lex.c` と `src/cmd/5c/swt.c` に `Bprint(&obuf, "%s\\n", thestring);` および `Bprint(&obuf, "\\n!\\n");` のような行が追加されています。これは、アセンブラ `5a` とコンパイラ `5c` が、オブジェクトファイルに特定のヘッダー情報（`thestring` の内容と区切り文字 `!`）を書き出すようになったことを示唆しています。これにより、リンカ `5l` がこれらのオブジェクトファイルを読み込む際に、Go固有のメタデータを効率的に解析できるようになります。
    *   `src/cmd/5l/obj.c` から `goto newloop;` や関連するコメントが削除され、オブジェクトファイルのヘッダー処理がより直接的かつエラーチェックが強化された形に変更されています。以前はヘッダーが見つからない場合でも処理を続行するようなコメントがありましたが、この変更によりヘッダーの存在が必須となり、ツールチェイン間の契約が強化されました。

3.  **データ構造の拡張とデータセグメント管理の改善**:
    *   `src/cmd/5l/l.h` において、リンカが使用する主要なデータ構造が拡張されました。
        *   `Adr` 構造体に `u0sbig` (大きな文字列データ用) と `index` フィールドが追加されました。
        *   `Prog` 構造体に `dlink` (データセグメント内のプログラム命令をリンクするため) が追加されました。
        *   `Sym` 構造体に `reachable` (デッドコード削除用)、`text` (シンボルに関連するテキストセグメントの開始点)、`data` (シンボルに関連するデータセグメントの開始点) が追加されました。
    *   `src/cmd/5l/5.out.h` に `D_SBIG` という新しい定義が追加されました。これは、リンカが処理するアドレスタイプの一つとして、大きな文字列データを扱うためのものです。
    *   `src/cmd/5l/asm.c` では、`datblk` 関数内で `D_SBIG` タイプのアドレスを処理するロジックが追加されました。これにより、リンカは大きな文字列リテラルを効率的にデータセグメントに配置できるようになります。
    *   `src/cmd/5l/obj.c` では、`main` 関数で `edatap = P;` が初期化され、`ADYNT`, `AINIT`, `ADATA` 命令の処理ロジックが大幅に変更されました。
        *   以前は `datap` という単一のポインタでデータセグメントのリストを管理していましたが、この変更により `datap` と `edatap` の両方を使用してデータセグメントのリストを管理するようになりました。`edatap` はデータセグメントの末尾を指すポインタとして機能し、新しいデータ命令をリストの末尾に効率的に追加できるようになります。
        *   `s->data = p;` のように、`Sym` 構造体に直接データセグメントの開始点 (`p`) を関連付けることで、シンボルとそれに関連するデータセグメントの間のマッピングがより明確になりました。

4.  **ビルドプロセスの変更**:
    *   `src/cmd/5l/Makefile` で、`# go.$O\` が `go.$O\` に変更され、`go.c` オブジェクトファイルが `5l` リンカのビルドプロセスに含まれるようになりました。これは、`ld/go.c` に関連する機能が実際にコンパイルされ、リンカにリンクされるようになったことを明確に示しています。

これらの変更は、GoのリンカがGoランタイムの複雑な要件をより深く理解し、効率的に処理するための基盤を構築したものであり、Goバイナリの品質とパフォーマンス向上に大きく貢献しました。

## コアとなるコードの解説

### `src/cmd/5l/obj.c` における `definetypestrings`, `definetypesigs`, `deadcode` の有効化

この変更は、Goリンカ `5l` の `main` 関数内で、Goランタイム固有のリンキング処理を明示的に有効化するものです。
*   `definetypestrings()`: Goの型名やその他のランタイムに必要な文字列リテラルを収集し、リンカがこれらを最終バイナリのデータセグメントに含めるようにします。これにより、リフレクションやデバッグ情報が正しく機能するための基盤が提供されます。
*   `definetypesigs()`: Goの型シグネチャ（関数の引数、戻り値、構造体のフィールドなど）を定義し、リンカがこれらを処理できるようにします。これは、インターフェースの動的なディスパッチやリフレクションAPIが正確な型情報にアクセスするために不可欠です。
*   `deadcode()`: Goプログラムのシンボルグラフを解析し、エントリポイントから到達不可能な関数やデータを特定して、それらを最終バイナリから削除します。これにより、不要なコードが取り除かれ、バイナリサイズが削減され、実行効率が向上します。

これらの関数呼び出しがコメントアウトから解除されたことは、Goのリンカが単なる汎用リンカではなく、Goランタイムのセマンティクスを深く理解し、それに基づいて最適化を行うようになったことを示しています。

### `src/cmd/5l/l.h` におけるデータ構造の拡張

このヘッダーファイルの変更は、リンカがGo固有の情報をより詳細に管理できるようにするための基盤となるデータ構造の拡張です。
*   `Adr` 構造体:
    *   `u0sbig`: `Adr` (アドレス記述子) 構造体の共用体 `u0` に `char* u0sbig;` が追加されました。これは、特に大きな文字列リテラルなどのデータを扱う際に、そのポインタを格納するために使用されます。Goプログラムでは多くの文字列リテラルが使用されるため、これを効率的に管理するためのフィールドです。
    *   `index`: `uchar index;` が追加されました。コメントに「not used on arm, required by ld/go.c」とあるように、ARMアーキテクチャでは直接使用されないものの、`ld/go.c` の機能統合のために必要とされたフィールドです。これは、Goランタイムの特定の内部処理でインデックス情報が必要とされることを示唆しています。
*   `Prog` 構造体:
    *   `dlink`: `Prog* dlink;` が追加されました。`Prog` はリンカが処理する個々の命令やデータ項目を表す構造体です。`dlink` は、データセグメント内の `Prog` リストを連結するために使用され、データセグメントの管理をより柔軟にします。
*   `Sym` 構造体:
    *   `reachable`: `uchar reachable;` が追加されました。これは、デッドコード削除プロセスにおいて、特定のシンボルがプログラムのエントリポイントから到達可能であるかどうかをマークするために使用されます。`deadcode()` 関数がこのフラグを利用して、最終バイナリに含めるべきシンボルを決定します。
    *   `text`: `Prog* text;` が追加されました。シンボルが関数である場合、その関数の最初の命令 (`Prog`) へのポインタを格納します。これにより、シンボルからそのコード本体への直接的な参照が可能になります。
    *   `data`: `Prog* data;` が追加されました。シンボルがデータ項目である場合、そのデータセグメントの最初の命令 (`Prog`) へのポインタを格納します。これにより、シンボルからそのデータ本体への直接的な参照が可能になります。

これらの拡張は、リンカがGoプログラムのセマンティクスをより深く理解し、デッドコード削除やランタイムメタデータ管理をより正確に行うための内部表現を強化したものです。

### `src/cmd/5l/obj.c` におけるデータセグメント管理の変更

この変更は、`ADYNT` (動的型情報)、`AINIT` (初期化データ)、`ADATA` (データ) といったGo固有のデータ命令をリンカが処理する方法を根本的に改善しています。
以前は `datap` という単一のポインタでデータセグメントのリストを管理していましたが、この変更により `datap` と `edatap` の両方を使用するようになりました。
*   `s = p->from.sym;`: 関連するシンボルを `s` に格納します。
*   `s->type = SDATA;`: シンボルのタイプをデータ (`SDATA`) に設定します。
*   `if(s != S) { p->dlink = s->data; s->data = p; }`: これは重要な変更です。もしシンボル `s` が存在する場合、現在のデータ命令 `p` をそのシンボルに関連付けられたデータリストの先頭に追加します。`s->data` はそのシンボルに関連するデータ命令のリストのヘッドを指すようになります。これにより、各シンボルが自身のデータセグメントを管理できるようになり、リンカの内部構造がより整理されます。
*   `if(edatap == P) datap = p; else edatap->link = p; edatap = p;`: これは、リンカ全体のデータセグメントのグローバルなリストを管理する部分です。
    *   `edatap == P` の場合、これはデータセグメントリストが空であることを意味するため、`datap` (リストの先頭) と `edatap` (リストの末尾) の両方を現在のデータ命令 `p` に設定します。
    *   `edatap != P` の場合、リストは既に存在するため、現在のリストの末尾 (`edatap->link`) を `p` に設定し、`edatap` を `p` に更新します。これにより、新しいデータ命令がグローバルなデータセグメントリストの末尾に効率的に追加されます。

この新しいデータセグメント管理ロジックは、リンカがGoプログラムのデータセグメントをより効率的かつ正確に構築できるようにします。特に、シンボルごとにデータを管理する能力と、グローバルなデータリストへの追加を最適化する能力は、Goランタイムの複雑なデータ要件に対応するために不可欠です。

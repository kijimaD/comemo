`value_test.go` では、この修正を検証するために、アラビア語の文字列を含む新しいテストケース `issue14262` が追加されています。これは、マルチバイト文字を含む文字列の切り詰め処理が正しく機能することを確認するためのものです。

## 変更の背景

この変更の背景には、Go言語の `go/constant` パッケージが文字列定数の文字列表現を生成する際に、UTF-8エンコーディングされた文字列の扱いに関するバグが存在したことが挙げられます。

`go/constant` パッケージは、Goコンパイラやツールが定数式を評価する際に使用されるパッケージです。定数には数値、真偽値、そして文字列があります。文字列定数を表示する際、特に長い文字列の場合には、表示上の都合で切り詰められることがあります。この切り詰め処理において、UTF-8でエンコードされたマルチバイト文字が正しく扱われないという問題が発生していました。

元の実装では、文字列をルーン（Unicodeコードポイント）単位で処理し、指定された最大長に達するまでルーンをデコードしていました。しかし、`utf8.DecodeRuneInString(s)` は常に文字列 `s` の先頭からデコードを試みます。ループ内で `i` をインデックスとして進めていたにもかかわらず、デコード対象の文字列スライスが更新されていなかったため、常に元の文字列の先頭からデコードを試み、結果として無限ループに陥るか、誤ったデコード結果を返す可能性がありました。

このバグは、おそらくIssue #14262で報告されたものであり、特にマルチバイト文字（例：日本語、アラビア語などの非ASCII文字）を含む文字列を `String()` メソッドで表示しようとした際に顕在化したと考えられます。正しくない切り詰めは、表示される文字列が破損したり、予期しない動作を引き起こしたりする原因となります。

## 前提知識の解説

### Go言語の文字列とUTF-8

Go言語の文字列は、内部的にはUTF-8でエンコードされたバイト列として扱われます。これは、GoがUnicodeを完全にサポートしていることを意味します。しかし、文字列をバイト列として扱うため、文字列の長さを `len(s)` で取得すると、それはバイト数であり、文字数（ルーン数）ではありません。

### ルーン (Rune)

Go言語では、Unicodeコードポイントを「ルーン (rune)」と呼び、`rune` 型は `int32` のエイリアスです。UTF-8では、1つのルーンが1バイトから4バイトでエンコードされます。例えば、ASCII文字は1バイト、日本語の漢字は3バイトでエンコードされることが多いです。

### `unicode/utf8` パッケージ

`unicode/utf8` パッケージは、UTF-8エンコードされたバイト列をルーンとしてデコードするための機能を提供します。
- `utf8.DecodeRuneInString(s string)`: この関数は、文字列 `s` の先頭から1つのUTF-8エンコードされたルーンをデコードし、そのルーンと、そのルーンをエンコードするのに使用されたバイト数（サイズ）を返します。もし `s` が空であるか、有効なUTF-8シーケンスで始まらない場合、`unicode.ReplacementChar` と1バイトを返します。

### `go/constant` パッケージ

`go/constant` パッケージは、Go言語のコンパイラやその他のツールが、Goのソースコード内で宣言された定数（数値、真偽値、文字列）を表現し、操作するための型と関数を提供します。これらの定数は、Goの組み込み型（`int`, `float64`, `string` など）とは異なり、任意精度で表現されることがあります。`String()` メソッドは、これらの定数の文字列表現を生成するために使用されます。

### バグのメカニズム

元のコードでは、`for n := 0; n < maxLen-3; n++` ループ内で `utf8.DecodeRuneInString(s)` を呼び出していました。ここで `s` は常に元の文字列全体を指していました。`utf8.DecodeRuneInString` は常に与えられた文字列の先頭からデコードを試みるため、ループの各イテレーションで同じルーンを繰り返しデコードしようとするか、あるいは `i` が進むことで `s` の先頭が既に処理済みであるにもかかわらず、その事実を `DecodeRuneInString` が認識しないという問題が発生していました。

正しい動作としては、既に処理したバイトをスキップし、残りの文字列スライスに対してデコードを行う必要があります。

## 技術的詳細

このコミットの技術的詳細は、Go言語におけるUTF-8文字列の正確な処理、特に部分文字列のデコードに関するものです。

`src/go/constant/value.go` の `stringVal` 型の `String()` メソッドは、文字列定数の文字列表現を生成する際に、必要に応じて文字列を切り詰めるロジックを含んでいます。この切り詰め処理は、表示上の都合で長い文字列を短縮するために行われます。

問題のコードは以下の部分でした（修正前）：

```go
// only the first maxLen-3 runes; then add "...".
i := 0
for n := 0; n < maxLen-3; n++ {
    _, size := utf8.DecodeRuneInString(s) // ここが問題
    i += size
}
s = s[:i] + "..."
```

ここで `s` は `stringVal` の内部文字列全体を指しています。`utf8.DecodeRuneInString(s)` は、常に `s` の先頭からルーンをデコードしようとします。しかし、ループ変数 `i` は、これまでにデコードされたルーンのバイト長を累積しています。

例えば、文字列 `s = "あいうえお"` (UTF-8で各文字3バイト) があり、`maxLen-3` が2だったとします。
1. `i = 0`
2. 1回目のループ (`n = 0`):
   - `utf8.DecodeRuneInString(s)` は `s` の先頭のルーン 'あ' をデコードし、`size = 3` を返します。
   - `i` は `0 + 3 = 3` になります。
3. 2回目のループ (`n = 1`):
   - `utf8.DecodeRuneInString(s)` は再び `s` の先頭のルーン 'あ' をデコードし、`size = 3` を返します。
   - `i` は `3 + 3 = 6` になります。
この結果、`s[:i]` は `s[:6]` となり、これは "あい" を意味しますが、実際には2つのルーンをデコードしたかったにもかかわらず、`utf8.DecodeRuneInString` が常に元の文字列の先頭を見ていたため、意図した動作とは異なっていました。特に、`i` が進むにつれて、`s` の先頭部分が既に処理済みであるにもかかわらず、`DecodeRuneInString` はその情報を利用せず、常に `s` の先頭からデコードを試みるため、無限ループや誤ったデコードを引き起こす可能性がありました。

修正後のコードは以下の通りです。

```go
// only the first maxLen-3 runes; then add "...".
i := 0
for n := 0; n < maxLen-3; n++ {
    _, size := utf8.DecodeRuneInString(s[i:]) // ここが修正点
    i += size
}
s = s[:i] + "..."
```

この修正では、`utf8.DecodeRuneInString` に渡す文字列を `s[i:]` としています。これは、元の文字列 `s` のうち、インデックス `i` から始まる部分文字列を意味します。これにより、ループの各イテレーションで、まだ処理されていない文字列の残りの部分から次のルーンが正しくデコードされるようになります。`i` はデコードされたルーンのバイト長分だけ進むため、次のイテレーションでは、その進んだ位置からデコードが再開されます。これにより、UTF-8エンコードされた文字列のルーン単位での正確な切り詰めが可能になります。

## コアとなるコードの解説

変更された行は `_, size := utf8.DecodeRuneInString(s)` から `_, size := utf8.DecodeRuneInString(s[i:])` です。

- **修正前**: `utf8.DecodeRuneInString(s)`
  - `s` は常に元の文字列全体を指していました。
  - `utf8.DecodeRuneInString` は、引数として渡された文字列の先頭からルーンをデコードします。
  - ループ内で `i` が更新されても、`s` 自体は変更されないため、`DecodeRuneInString` は常に同じ文字列の先頭からデコードを試み、結果として誤った動作（無限ループや不正なデコード）を引き起こす可能性がありました。

- **修正後**: `utf8.DecodeRuneInString(s[i:])`
  - `s[i:]` は、元の文字列 `s` のうち、インデックス `i` から始まる部分文字列（スライス）を生成します。
  - ループの各イテレーションで `i` はこれまでに処理されたバイト数だけ増加するため、`s[i:]` は常に「まだ処理されていない残りの文字列」を指すことになります。
  - これにより、`utf8.DecodeRuneInString` は、文字列の正しい位置から次のルーンをデコードするようになり、UTF-8エンコードされた文字列のルーン単位での正確な切り詰めが保証されます。

この変更は、Go言語における文字列処理の基本原則、すなわち「文字列はバイトのシーケンスであり、ルーン単位で処理する場合は明示的にUTF-8デコードを行う必要がある」という点を正しく適用したものです。特に、部分文字列を扱う際には、スライス操作 `s[i:]` を用いて、処理対象の範囲を正確に指定することが重要です。

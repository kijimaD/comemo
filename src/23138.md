## 元コミット内容

```
runtime/race: fix benchmark deadlock

Currently TestRaceCrawl fails to wg.Done for every wg.Adds if the
depth ever reaches 0. This causes the test to deadlock. Under the race
detector, this deadlock is not detected, so the test eventually times
out.

This only recently became a problem. Prior to commit e870f06 the depth
would never reach 0 because the strict round-robin goroutine schedule
ensured that all of the URLs were already "seen" by depth 2. Now that
the runtime prefers scheduling the most recently started goroutine,
the test is able to reach depth 0 and trigger this deadlock.
```

## 変更の背景

この変更は、Goランタイムのゴルーチンスケジューラの挙動変更に起因するデッドロックを修正するために行われました。

以前のコミット `e870f06` より前は、Goのゴルーチンスケジューラは「厳密なラウンドロビン方式」を採用していました。このスケジューリング戦略では、`TestRaceCrawl` ベンチマークにおいて、テストが探索する深さ（`depth`）が0に到達することはありませんでした。これは、スケジューラが公平にゴルーチンを切り替えるため、すべてのURLが深さ2の時点で「見つけられた」状態になり、それ以上深く探索する必要がなかったためです。

しかし、コミット `e870f06` 以降、ランタイムは「最も最近開始されたゴルーチンを優先的にスケジューリングする」ように変更されました。この変更により、`TestRaceCrawl` は以前は到達しなかった深さ0に到達できるようになりました。深さ0に到達すると、テストのロジック上、`sync.WaitGroup` の `Done()` メソッドが呼び出されないパスが存在し、これがデッドロックを引き起こしました。

データ競合検出器が有効な環境下では、このデッドロックは検出されず、テストが最終的にタイムアウトするという形で現れていました。このコミットは、この新しいスケジューリング挙動に対応し、`TestRaceCrawl` が深さ0に到達した場合でも `wg.Done()` が確実に呼び出されるようにすることで、デッドロックを解消することを目的としています。

## 前提知識の解説

### Goのゴルーチンとスケジューラ

Go言語は、軽量な並行処理の単位として「ゴルーチン（goroutine）」を提供します。ゴルーチンはOSのスレッドよりもはるかに軽量であり、数百万個のゴルーチンを同時に実行することも可能です。Goランタイムには、これらのゴルーチンをOSスレッドにマッピングし、実行を管理する「ゴルーチンスケジューラ」が組み込まれています。

ゴルーチンスケジューラは、ゴルーチンの実行順序やCPUコアへの割り当てを決定します。そのスケジューリング戦略は、Goのバージョンやランタイムの最適化によって進化してきました。本コミットの背景にあるように、かつては「厳密なラウンドロビン方式」が採用されていましたが、パフォーマンスや特定のワークロードへの適応のために「最も最近開始されたゴルーチンを優先する」といった戦略に変更されることがあります。この変更は、I/Oバウンドな処理や、新しいゴルーチンがすぐに結果を生成するようなシナリオで、レイテンシを改善する効果が期待できます。

### `sync.WaitGroup`

`sync.WaitGroup` は、Go言語の標準ライブラリ `sync` パッケージで提供される同期プリミティブの一つです。複数のゴルーチンの完了を待機するために使用されます。

- `Add(delta int)`: WaitGroupのカウンタに `delta` を加算します。通常、新しいゴルーチンを開始する前に `Add(1)` を呼び出します。
- `Done()`: WaitGroupのカウンタを1減らします。ゴルーチンがそのタスクを完了したときに呼び出されます。
- `Wait()`: WaitGroupのカウンタが0になるまでブロックします。通常、メインゴルーチンがすべてのワーカーゴルーチンの完了を待つために使用します。

`WaitGroup` を正しく使用するには、`Add` で追加した回数だけ `Done` を呼び出す必要があります。もし `Done` の呼び出しが不足すると、`Wait` が永遠にブロックし、デッドロックが発生します。

### Goのデータ競合検出器 (Race Detector)

Goには、プログラム実行中にデータ競合（data race）を検出するための組み込みツールである「データ競合検出器（Race Detector）」があります。データ競合は、複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に発生します。データ競合は予測不能な動作やバグの原因となるため、その検出は非常に重要です。

Goのデータ競合検出器は、プログラムの実行を監視し、データ競合のパターンを特定します。検出器は、競合が検出された場合に警告を出力します。しかし、本コミットのケースのように、デッドロックがデータ競合とは異なる性質を持つ場合（ここでは `WaitGroup` の不均衡）、データ競合検出器はそれを直接検出できないことがあります。その結果、テストが単にタイムアウトとして現れることになります。

## 技術的詳細

`TestRaceCrawl` は、ウェブクローラーのような動作を模倣したテストベンチマークです。このテストは、再帰的にURLを探索し、`sync.WaitGroup` を使用してすべての探索ゴルーチンの完了を待機します。

デッドロックの根本原因は、`TestRaceCrawl` の内部ロジックにありました。探索の深さ `d` が0以下になった場合、ゴルーチンはそれ以上探索を続けずに `return` します。

```go
		if d <= 0 {
			return // ここでwg.Done()が呼ばれていなかった
		}
```

以前のスケジューラでは、`d <= 0` の条件が真になることはありませんでした。しかし、`e870f06` 以降のスケジューラ変更により、新しいゴルーチンが優先的に実行されるようになった結果、探索が深さ0に到達するシナリオが発生するようになりました。

深さ0に到達したゴルーチンは、`wg.Add(1)` でカウンタを増やしたにもかかわらず、`wg.Done()` を呼び出すことなく `return` していました。これにより、`WaitGroup` のカウンタが0にならず、`TestRaceCrawl` のメインゴルーチンが `wg.Wait()` で永遠にブロックし、デッドロックが発生していました。データ競合検出器は、この種の同期プリミティブの不均衡によるデッドロックを直接検出する機能は持たないため、テストは単にタイムアウトとして終了していました。

## コアとなるコードの解説

追加された行は `wg.Done()` です。

`if d <= 0 { ... }` ブロックは、探索の深さが0以下になった場合に、それ以上探索を続行しないための終了条件です。このブロック内で `wg.Done()` が追加されたことにより、深さ0に到達して処理を終了するゴルーチンも、`WaitGroup` のカウンタを適切に減らすことができるようになりました。

これにより、`wg.Add(1)` で増やされたカウンタが、ゴルーチンの終了時に必ず `wg.Done()` で減らされるようになり、`WaitGroup` のカウンタが最終的に0に到達することが保証されます。結果として、`TestRaceCrawl` のメインゴルーチンは `wg.Wait()` から正常に復帰できるようになり、デッドロックが解消されました。

この修正は、ゴルーチンスケジューラの挙動変更によって露呈した、テストロジック内の `WaitGroup` の不均衡という潜在的なバグを修正したものです。

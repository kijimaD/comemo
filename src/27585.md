# [インデックス 27585] ファイルの概要

このコミットは、Goランタイムのヒープ管理における `pagesInUse` カウンタの会計処理のバグを修正します。具体的には、ヒープが拡張される際にOSから取得されるメモリページの数と、ヒープ内で使用中としてカウントされるページの数との間に発生していた不整合を解消し、ガベージコレクタのパフォーマンス低下を防ぎます。

    runtime: fix pagesInUse accounting

    When we grow the heap, we create a temporary "in use" span for the
    memory acquired from the OS and then free that span to link it into
    the heap. Hence, we (1) increase pagesInUse when we make the temporary
    span so that (2) freeing the span will correctly decrease it.

    However, currently step (1) increases pagesInUse by the number of
    pages requested from the heap, while step (2) decreases it by the
    number of pages requested from the OS (the size of the temporary
    span). These aren't necessarily the same, since we round up the number
    of pages we request from the OS, so steps 1 and 2 don't necessarily
    cancel out like they're supposed to. Over time, this can add up and
    cause pagesInUse to underflow and wrap around to 2^64. The garbage
    collector computes the sweep ratio from this, so if this happens, the
    sweep ratio becomes effectively infinite, causing the first allocation
    on each P in a sweep cycle to sweep the entire heap. This makes
    sweeping effectively STW.

    Fix this by increasing pagesInUse in step 1 by the number of pages
    requested from the OS, so that the two steps correctly cancel out. We
    add a test that checks that the running total matches the actual state
    of the heap.

    Fixes #15022. For 1.6.x.

## 変更の背景

Goランタイムのメモリ管理において、ヒープが拡張される際には、OSから新しいメモリ領域が取得されます。このプロセスは通常、以下の2つのステップで構成されます。

1.  **一時的な「使用中」スパンの作成**: OSから取得したメモリに対して、一時的に「使用中」を示すスパン（`mSpanInUse`）が作成されます。この際、`pagesInUse` カウンタが増加します。
2.  **スパンの解放とヒープへのリンク**: その後、この一時的なスパンは解放され、Goランタイムのヒープ構造（`mheap`）にリンクされます。この際、`pagesInUse` カウンタが減少します。

本来、ステップ(1)での増加量とステップ(2)での減少量は一致し、`pagesInUse` の値はヒープの実際の使用状況を正確に反映するはずでした。しかし、このコミット以前の実装では、ステップ(1)で `pagesInUse` を増加させる際に「ヒープから要求されたページ数」を使用していたのに対し、ステップ(2)で減少させる際には「OSから要求された（一時スパンの）ページ数」を使用していました。

問題は、GoランタイムがOSにメモリを要求する際に、要求されたページ数を切り上げて実際のOSページサイズに合わせることがある点です。この切り上げにより、「ヒープから要求されたページ数」と「OSから実際に取得されたページ数」が一致しない場合がありました。結果として、ステップ(1)とステップ(2)での `pagesInUse` の増減が相殺されず、`pagesInUse` カウンタに誤差が生じていました。

この誤差が蓄積されると、`pagesInUse` の値がアンダーフローを起こし、`2^64` のような非常に大きな値にラップアラウンドしてしまう可能性がありました。`pagesInUse` はガベージコレクタ（GC）がスイープ比率（sweep ratio）を計算するために使用する重要な値です。スイープ比率が「実質的に無限大」と計算されると、GCのスイープサイクルにおいて、各P（プロセッサ、Goのスケジューラにおける論理CPU）での最初のメモリ割り当て時にヒープ全体をスイープするという非効率な動作を引き起こしていました。これは実質的にStop-The-World（STW）のような状態を作り出し、アプリケーションのパフォーマンスに深刻な影響を与えていました。

この問題は Go issue #15022 として報告され、Go 1.6.x のリリースブランチで修正が必要とされました。

## 前提知識の解説

### Goランタイムのメモリ管理 (mheap, spans, pages)

*   **ヒープ (Heap)**: Goプログラムが動的にメモリを割り当てる領域です。Goランタイムが管理します。
*   **ページ (Page)**: メモリ管理の最小単位です。通常、4KBなどの固定サイズです。OSからメモリを取得する際も、このページ単位で行われます。
*   **スパン (Span)**: 連続したGoランタイムのページ群です。Goランタイムは、オブジェクトのサイズに応じて異なるサイズクラスのスパンを管理し、そこからメモリを割り当てます。スパンには `_MSpanInUse` (使用中), `_MSpanFree` (空き) などの状態があります。
*   **`mheap`**: Goランタイム全体のヒープを管理する構造体です。`mheap_` はグローバルな `mheap` インスタンスを指します。

### `pagesInUse` の役割

`mheap` 構造体内の `pagesInUse` は、現在GoランタイムのヒープによってOSから取得され、使用中またはGoランタイムが管理しているページ総数を追跡するカウンタです。この値は、ガベージコレクタが次のGCサイクルでどれくらいのメモリを解放すべきか（スイープ比率）を決定する上で重要な指標となります。正確な `pagesInUse` の値は、GCの効率とアプリケーションのレイテンシに直結します。

### Stop-The-World (STW)

ガベージコレクションのフェーズの一部で、GoランタイムがすべてのGoルーチン（ユーザーコード）の実行を一時的に停止させる期間を指します。STW中はアプリケーションが一切動作しないため、その時間は短ければ短いほど良いとされています。このコミットで修正されたバグは、GCのスイープが実質的にSTW化するという、非常に望ましくない状況を引き起こしていました。

### `uintptr` と `uint64`

*   **`uintptr`**: ポインタを保持するのに十分な大きさの符号なし整数型です。OSやアーキテクチャによってサイズが異なります（32ビットシステムでは32ビット、64ビットシステムでは64ビット）。メモリのアドレスやページ数を表現するのに使われます。
*   **`uint64`**: 64ビットの符号なし整数型です。`pagesInUse` のようなカウンタで、非常に大きな値を扱うために使われます。

### `atomic.Store`

`sync/atomic` パッケージに含まれる関数で、アトミック操作（不可分操作）を提供します。複数のGoルーチンが同時に同じメモリ位置にアクセスしても、データ競合を起こさずに安全に値を読み書きするために使用されます。ここでは `s.sweepgen` の値をアトミックに設定するために使われています。

## 技術的詳細

このバグの核心は、Goランタイムがヒープを拡張する際の `pagesInUse` カウンタの更新ロジックにありました。

1.  **ヒープ拡張のプロセス**: `mheap.grow(npage uintptr)` 関数は、`npage` ページ分のメモリをヒープに確保しようとします。
2.  **OSからのメモリ取得**: この関数内で、OSから実際にメモリが取得されます。OSはページ単位でメモリを管理しており、要求された `npage` がOSのページサイズに合わない場合、切り上げてより多くのページ（例えば `s.npages`）が取得されることがあります。この `s.npages` は、実際にOSから取得された一時スパンのページ数です。
3.  **誤った `pagesInUse` の更新**: コミット前のコードでは、`src/runtime/mheap.go` の `h.pagesInUse += uint64(npage)` という行で `pagesInUse` を増加させていました。ここで `npage` は「ヒープから要求されたページ数」であり、OSから実際に取得された「一時スパンのページ数 (`s.npages`)」とは異なる可能性がありました。
4.  **不整合の発生**: その後、この一時スパンが解放されヒープにリンクされる際に、`pagesInUse` は `s.npages` 分だけ減少します。もし `npage < s.npages` であった場合、増加量よりも減少量の方が大きくなるため、`pagesInUse` は本来よりも少ない値になってしまいます。
5.  **アンダーフローとラップアラウンド**: この不整合が繰り返されると、`pagesInUse` の値が徐々に減少し、最終的には符号なし整数である `uint64` の最小値（0）を下回り、最大値（`2^64 - 1`）にラップアラウンドしてしまいます。
6.  **GCへの影響**: `pagesInUse` が `2^64` のような非常に大きな値になると、ガベージコレクタが計算するスイープ比率が「実質的に無限大」と判断されます。これにより、GCは次の割り当て時にヒープ全体をスイープしようとします。これは非常にコストの高い操作であり、各Pでの最初の割り当て時に発生するため、アプリケーションの実行が頻繁に停止し、実質的にSTWのような状態に陥っていました。

**修正内容**:
このコミットでは、`src/runtime/mheap.go` の `grow` 関数内の `pagesInUse` の更新ロジックを `h.pagesInUse += uint64(s.npages)` に変更しました。これにより、`pagesInUse` の増加量がOSから実際に取得された一時スパンのページ数 (`s.npages`) と一致するようになり、その後のスパン解放時の減少量と正確に相殺されるようになりました。結果として、`pagesInUse` カウンタはヒープの実際の使用状況を正確に反映するようになり、GCの誤動作が解消されました。

**テストの追加**:
この修正の検証のために、`src/runtime/export_test.go` に `CountPagesInUse` というヘルパー関数が追加され、`src/runtime/gc_test.go` に `TestPageAccounting` という新しいテストが追加されました。`TestPageAccounting` は、小さなブロックでヒープを段階的に拡張し、`mheap_.pagesInUse` の値が `CountPagesInUse` で直接カウントした実際の使用中ページ数と一致するかどうかを検証します。これにより、将来的に同様の会計処理のバグが再発するのを防ぐための安全網が提供されました。

## コアとなるコードの解説

`src/runtime/mheap.go` の変更は、`mheap` 構造体の `grow` メソッド内で行われています。このメソッドは、ヒープに新しいメモリ領域が必要になったときに呼び出されます。

変更前:
`h.pagesInUse += uint64(npage)`

変更後:
`h.pagesInUse += uint64(s.npages)`

ここで、`npage` は `grow` 関数に渡された引数で、「ヒープが要求したページ数」を意味します。一方、`s.npages` は、OSから実際に取得されたスパン `s` のページ数です。前述の通り、OSからのメモリ取得時には切り上げが発生するため、`npage` と `s.npages` は異なる場合があります。

この修正により、`pagesInUse` カウンタは、OSから実際に取得されたメモリ量 (`s.npages`) に基づいて増加するようになりました。これにより、その後にスパンが解放される際に `pagesInUse` が `s.npages` 分だけ減少する処理と正確に相殺され、カウンタの不整合が解消されます。

`src/runtime/export_test.go` と `src/runtime/gc_test.go` に追加されたテストコードは、この修正が正しく機能していることを検証するためのものです。`TestPageAccounting` は、ヒープを成長させるシナリオをシミュレートし、`mheap_.pagesInUse` の内部カウンタが、実際にヒープ内の使用中スパンを数え上げた結果 (`counted`) と一致するかを確認します。これにより、`pagesInUse` の会計処理が常に正確であることが保証されます。

# [インデックス 22531] ファイルの概要

このコミットは、Go言語の`os`パッケージにおける`Mkdir`および`OpenFile`関数が、*BSDおよびSolarisシステム上でスティッキービットを処理する際に発生する`Chmod`のエラーを誤って伝播させてしまう問題を修正します。具体的には、ファイルまたはディレクトリ自体の作成が成功した場合でも、内部的な`Chmod`呼び出しの失敗が全体のエラーとして報告されてしまう挙動を改善し、`Chmod`のエラーを無視するように変更しています。

## コミット

```
os: don't return Chmod's error from Mkdir and OpenFile

Mkdir and OpenFile call Chmod internally on *BSD and Solaris,
because these OSes don't handle the sticky bit correctly.

However Chmod's error should be ignored. It shouldn't hide
the fact that a file itself is created.

Fixes #8383

Change-Id: Ia2e0b2ba72712d73a0a48ba5a263432e0fff31a5
Reviewed-on: https://go-review.googlesource.com/2057
Reviewed-by: Russ Cox <rsc@golang.org>
```

## 変更の背景

この変更は、Go言語の`os`パッケージが提供する`Mkdir`（ディレクトリ作成）および`OpenFile`（ファイルオープン/作成）関数における、特定のUnix系OS（*BSDおよびSolaris）でのスティッキービットの扱いに起因するバグを修正するために行われました。

これらのOSでは、`mkdir(2)`や`open(2)`といったシステムコールが、ファイルやディレクトリ作成時にスティッキービット（`ModeSticky`）を正しく設定できないという特性があります。このため、Goの`os`パッケージは、これらのシステムコールが成功した後に、別途`Chmod`システムコールを呼び出してスティッキービットを設定しようと試みていました。

しかし、この`Chmod`呼び出しが失敗した場合、そのエラーが`Mkdir`や`OpenFile`の戻り値として伝播されていました。問題は、ファイルやディレクトリ自体の作成は成功しているにもかかわらず、スティッキービットの設定失敗という二次的な問題によって、あたかもファイル/ディレクトリ作成全体が失敗したかのように見えてしまう点にありました。これは、ユーザーが期待する挙動と異なり、混乱を招く可能性がありました。

このコミットは、`Fixes #8383`で報告された問題に対応しています。根本的な原因は、ファイル/ディレクトリの作成という主要な操作の成功を、付随的な権限設定の失敗が隠蔽してしまうことでした。

## 前提知識の解説

### 1. Unix系ファイルパーミッションとスティッキービット (Sticky Bit)

Unix系OSでは、ファイルやディレクトリにはアクセス権限が設定されています。これらは通常、所有者、グループ、その他のユーザーに対する読み取り（r）、書き込み（w）、実行（x）の権限で構成されます。これに加えて、特殊なパーミッションビットとして「スティッキービット (Sticky Bit)」、「SetUID (Set User ID)」、「SetGID (Set Group ID)」があります。

*   **スティッキービット (Sticky Bit, `t`または`T`)**:
    *   **ファイルの場合**: 過去には実行可能ファイルに設定され、そのプログラムが終了してもテキストセグメントをスワップ領域に残しておくことで、次に実行される際のロード時間を短縮する目的で使用されました。しかし、現代のOSではほとんど使われていません。
    *   **ディレクトリの場合**: これが最も一般的な用途です。スティッキービットが設定されたディレクトリ（例: `/tmp`）では、そのディレクトリ内のファイルやサブディレクトリを削除したり名前を変更したりできるのは、そのファイル/ディレクトリの所有者、ディレクトリの所有者、またはrootユーザーのみです。これにより、複数のユーザーが書き込み可能な共有ディレクトリで、他のユーザーが作成したファイルを勝手に削除するのを防ぎます。パーミッション表記では、`rwxrwxrwt`のように最後の`t`で示されます。

### 2. `os.Mkdir`と`os.OpenFile`

Go言語の標準ライブラリ`os`パッケージは、ファイルシステム操作のための基本的な関数を提供します。

*   **`os.Mkdir(name string, perm os.FileMode) error`**: 指定されたパス`name`に新しいディレクトリを作成します。`perm`引数でディレクトリのパーミッション（アクセス権限）を指定します。
*   **`os.OpenFile(name string, flag int, perm os.FileMode) (*os.File, error)`**: 指定されたパス`name`のファイルを開きます。`flag`はファイルのオープンモード（読み取り、書き込み、作成など）を、`perm`はファイル作成時のパーミッションを指定します。

これらの関数は内部的に、OSが提供するシステムコール（Linux/Unixでは`mkdir(2)`や`open(2)`など）を呼び出します。

### 3. `syscall.Chmod`

`syscall`パッケージは、Goプログラムから低レベルのOSシステムコールに直接アクセスするための機能を提供します。`syscall.Chmod`は、指定されたファイルまたはディレクトリのパーミッションを変更するためのシステムコールです。

### 4. *BSDおよびSolarisの特性

一部のUnix系OS（特に*BSD系OSやSolaris）では、`mkdir(2)`や`open(2)`システムコールが、ディレクトリやファイルの作成時にスティッキービットを正しく設定できないという実装上の特性があります。これは、これらのシステムコールがパーミッションの基本部分（読み取り、書き込み、実行）は設定できるものの、スティッキービットのような特殊なパーミッションビットの初期設定には対応していないためです。このため、Goの`os`パッケージは、これらのOSでスティッキービットを含むパーミッションでファイル/ディレクトリを作成しようとする場合、作成後に別途`Chmod`を呼び出してスティッキービットを設定する必要がありました。

## 技術的詳細

このコミットの技術的な核心は、`Mkdir`および`OpenFile`関数が、ファイルまたはディレクトリの作成が成功した後に、スティッキービットを設定するために内部的に呼び出す`Chmod`システムコールのエラー処理を変更した点にあります。

変更前は、`Mkdir`と`OpenFile`は、ファイル/ディレクトリの作成自体が成功し（`syscall.Mkdir`や`openFile`がエラーを返さなかった場合）、かつスティッキービットが指定されている場合にのみ`Chmod`を呼び出していました。そして、この`Chmod`呼び出しがエラーを返した場合、そのエラーを`Mkdir`や`OpenFile`の最終的な戻り値としていました。

問題は、*BSDやSolarisのようなOSでは、`mkdir(2)`や`open(2)`がスティッキービットを正しく扱えないため、`Chmod`を呼び出す必要があったことです。しかし、これらのOSでは、ファイル/ディレクトリの作成自体は成功しても、その後の`Chmod`によるスティッキービットの設定が何らかの理由で失敗する可能性がありました。例えば、ファイルシステムがスティッキービットをサポートしていない、あるいは他の要因で`Chmod`が失敗するケースです。

このコミットでは、この挙動を修正し、`Chmod`の呼び出し結果を無視するように変更しました。つまり、ファイルやディレクトリの作成が成功した時点で、`Mkdir`や`OpenFile`は成功を返すべきであり、スティッキービットの設定失敗は、ファイル/ディレクトリ作成の主要な目的（存在すること）を妨げるものではない、という判断に基づいています。

これにより、`Mkdir`や`OpenFile`は、ファイル/ディレクトリが実際に作成されたかどうかという主要な関心事に集中し、付随的なパーミッション設定の失敗によって誤ったエラーを報告することがなくなりました。

## コアとなるコードの解説

### `src/os/file.go` の `Mkdir` 関数における変更

変更前は、`Mkdir`関数内で`syscall.Mkdir`が成功し（`e == nil`）、かつ`supportsCreateWithStickyBit`が`false`（*BSDやSolarisなど）で、かつ`ModeSticky`パーミッションが指定されている場合に、`Chmod(name, perm)`を呼び出し、その結果のエラーを`e`に代入していました。

```go
// 変更前
if !supportsCreateWithStickyBit && e == nil && perm&ModeSticky != 0 {
	e = Chmod(name, perm) // Chmodのエラーがeに代入される
}
if e != nil {
	return &PathError{"mkdir", name, e} // そのエラーが返される
}
```

変更後は、`syscall.Mkdir`が成功したかどうかを先にチェックし、成功していればすぐに`nil`を返します。`Chmod`の呼び出しは、`syscall.Mkdir`が成功した後の独立した処理として行われ、その戻り値は破棄されます。

```go
// 変更後
e := syscall.Mkdir(name, syscallMode(perm))
if e != nil { // Mkdir自体のエラーはここで処理
	return &PathError{"mkdir", name, e}
}
// Mkdirが成功した場合のみ、Chmodを呼び出すが、そのエラーは無視
if !supportsCreateWithStickyBit && perm&ModeSticky != 0 {
	Chmod(name, perm) // Chmodのエラーは破棄される
}
return nil // Mkdirは成功とみなされる
```

この変更により、ディレクトリの作成自体が成功した場合、`Mkdir`は常に`nil`（エラーなし）を返すようになります。スティッキービットの設定が失敗しても、それは`Mkdir`の成功には影響しません。

### `src/os/file_unix.go` の `OpenFile` 関数における変更

`OpenFile`関数も同様の変更が加えられています。変更前は、`openFile`が成功し（`e == nil`）、かつ`chmod`フラグが真の場合に`Chmod(name, perm)`を呼び出し、そのエラーを`e`に代入していました。

```go
// 変更前
if chmod && e == nil { // openFileが成功した場合のみChmodを呼び出し、エラーをeに代入
	e = Chmod(name, perm)
}
```

変更後は、`chmod`フラグが真であれば、`openFile`の成功とは独立して`Chmod(name, perm)`を呼び出しますが、その戻り値は破棄されます。

```go
// 変更後
if chmod { // openFileの成功とは独立してChmodを呼び出し、エラーは破棄
	Chmod(name, perm)
}
```

これにより、ファイルが正常にオープンまたは作成された場合、`OpenFile`は`Chmod`の成功/失敗に関わらず、ファイルオブジェクトと`nil`（エラーなし）を返すようになります。

これらの変更は、Goの`os`パッケージが、ファイルシステム操作の主要な結果（ファイル/ディレクトリの作成）と、付随的なパーミッション設定の成功/失敗を区別し、より堅牢なエラーハンドリングを提供するように改善されたことを示しています。

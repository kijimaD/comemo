このコミットは、Goリンカー (`cmd/link`) におけるDwarfデバッグ情報の `.debug_aranges` セクションのパディングに関するバグを修正するものです。特に32ビットプラットフォームにおいて、`aranges` セクションのヘッダー後の最初のタプルが正しくアラインされない問題があり、これがデバッガ（LLDBなど）がデバッグ情報を正確に解釈できない原因となっていました。この修正は、ヘッダーサイズの計算方法を変更することで、このアラインメントの問題を解決し、同時にLLDBとの連携を検証するための新しいテストを追加しています。

## 変更の背景

このコミットの背景には、Goプログラムのデバッグ体験、特に32ビットアーキテクチャ上でのデバッグの正確性に関する問題がありました。デバッガがプログラムの実行状態を正確に把握し、ソースコードと対応付けるためには、コンパイラやリンカーが生成するデバッグ情報が非常に重要です。

Goリンカーが生成するDwarfデバッグ情報の一部である `.debug_aranges` セクションにおいて、32ビットプラットフォームで特定のパディング（詰め物）が正しく行われていないという問題が存在しました。この不正確なパディングにより、デバッガ（特にLLDB）が `.debug_aranges` セクションのデータを誤って解釈し、結果としてブレークポイントの設定や変数情報の取得など、基本的なデバッグ機能が正常に動作しない事態が発生していました。

コミットメッセージにある `Fixes #14278` は、この問題がGoの内部イシュートラッカーで報告されていたことを示唆していますが、公開されているGoのイシュートラッカーではこの番号のDwarf関連のイシューは確認できませんでした。しかし、コミット内容とコード変更から、Dwarf情報の正確な生成がデバッグ体験に直結する重要な課題であったことが伺えます。

## 前提知識の解説

### DWARF (Debugging With Attributed Record Formats)
DWARFは、コンパイルされたプログラムのデバッグ情報を記述するための標準的なフォーマットです。ソースコードの行番号、変数名、型情報、関数名、スタックフレームの構造など、デバッガがプログラムの実行を理解し、開発者がデバッグを行うために必要なあらゆる情報を提供します。Goコンパイラとリンカーは、実行可能ファイルを生成する際にこのDWARF情報を埋め込みます。

### `.debug_aranges` セクション
DWARF情報の一部として、実行可能ファイルには通常、`.debug_aranges` というセクションが含まれます。このセクションは、プログラムのアドレス範囲（例えば、特定の関数や変数がメモリ上のどこに配置されているか）と、それに対応するコンパイル単位（ソースファイル）をマッピングするためのインデックスとして機能します。デバッガは、この `.debug_aranges` を利用することで、特定のアドレスがどのソースファイルや関数に属するかを高速に検索できます。これにより、デバッグセッション中のパフォーマンスが向上します。

`.debug_aranges` セクションの構造は、ヘッダーとそれに続くアドレス範囲のタプル（組）のリストで構成されます。各タプルは通常、開始アドレスと長さ（サイズ）のペアで、特定のコードやデータが占めるメモリ領域を示します。

### パディングとアラインメント
コンピュータのメモリはバイト単位でアドレス指定されますが、CPUは特定のデータ型（例えば、32ビット整数や64ビットポインタ）を効率的に読み書きするために、そのデータ型が特定のメモリアドレスの倍数に配置されていることを要求することがよくあります。これを「アラインメント（整列）」と呼びます。

例えば、4バイトの整数は4の倍数のアドレスに、8バイトのポインタは8の倍数のアドレスに配置されるべき、といったルールがあります。このアラインメント要件を満たすために、コンパイラやリンカーはデータ構造の間に「パディング（詰め物）」と呼ばれる未使用のバイトを挿入することがあります。

アラインメントが正しく行われないと、CPUがデータを読み書きする際にパフォーマンスが低下したり、最悪の場合、ハードウェア例外（アラインメント違反）が発生してプログラムがクラッシュしたり、デバッガがデータを誤って解釈したりする原因となります。特に32ビットシステムと64ビットシステムでは、ポインタサイズやデフォルトのアラインメント要件が異なるため、クロスプラットフォームでのデバッグ情報生成において注意が必要です。

### リンカー (`cmd/link`)
Go言語のツールチェーンにおいて、`cmd/link` はGoコンパイラが生成したオブジェクトファイル群を結合し、最終的な実行可能ファイルやライブラリを生成する役割を担うリンカーです。この過程で、Dwarfデバッグ情報もオブジェクトファイルから集約され、実行可能ファイル内の適切なセクションに配置されます。したがって、Dwarf情報の正確性はリンカーの動作に大きく依存します。

### LLDB
LLDBは、Clang/LLVMプロジェクトの一部として開発されている高性能なデバッガです。GDBと同様に、プログラムの実行を制御し、ブレークポイントを設定し、変数を検査し、メモリを調査するなどの機能を提供します。LLDBは、Goプログラムのデバッグにも利用されますが、そのためにはGoリンカーが生成するDwarf情報がLLDBの期待するフォーマットとアラインメントに厳密に従っている必要があります。

## 技術的詳細

このコミットが修正する問題は、`.debug_aranges` セクションの構造とアラインメントに関するものです。Dwarfの仕様では、`.debug_aranges` セクションのヘッダーに続く最初のアドレス範囲タプルは、そのタプルのサイズ（通常は `2 * AddressSize`、つまりアドレスと長さのペア）の倍数にアラインされている必要があります。

以前のGoリンカーの実装では、`dwarf.go` 内の `writearanges` 関数で `headersize` を計算する際に、このアラインメント要件が32ビットプラットフォームで正しく考慮されていませんでした。具体的には、`headersize` の計算で `Thearch.Ptrsize` (ポインタサイズ) を基準に丸め処理を行っていましたが、`.debug_aranges` のタプルは `2 * Thearch.Ptrsize` のサイズを持つため、この丸め基準では不十分でした。

```go
// 変更前
headersize := int(Rnd(4+2+4+1+1, int64(Thearch.Ptrsize))) // don't count unit_length field itself
```

この計算の誤りにより、32ビットシステムで生成された実行可能ファイルの `.debug_aranges` セクションでは、ヘッダーの直後のデータが正しくアラインされず、デバッガがこのセクションをパースする際にエラーが発生したり、誤った情報を読み取ったりする可能性がありました。結果として、デバッガはアドレスからコンパイル単位へのマッピングを正確に行えず、デバッグセッションが困難になるという問題が生じていました。

このコミットでは、`headersize` の計算におけるアラインメントの基準を `Thearch.Ptrsize` から `Thearch.Ptrsize*2` に変更することで、この問題を解決しています。これにより、ヘッダーの直後のアドレス範囲タプルが常に正しいアラインメントで配置されることが保証され、デバッガがDwarf情報を正確に解釈できるようになります。

また、この修正の検証を強化するために、`src/runtime/runtime-lldb_test.go` という新しいテストファイルが追加されました。このテストは、Goプログラムをビルドし、その実行可能ファイルをLLDBでデバッグする一連のプロセスを自動化することで、Dwarf情報がLLDBによって正しく解釈されることを確認します。特に、`TestDwarfAranges` 関数は、生成された実行可能ファイルの `.debug_aranges` セクションの構造を直接検査し、パディングとアラインメントがDwarfの仕様に準拠していることを検証します。

## コアとなるコードの解説

### `src/cmd/link/internal/ld/dwarf.go` の変更

このファイルでは、`writearanges` 関数内の `headersize` の計算ロジックが変更されています。

*   **変更前**:
    ```go
    headersize := int(Rnd(4+2+4+1+1, int64(Thearch.Ptrsize))) // don't count unit_length field itself
    ```
    `Rnd` 関数は、最初の引数で与えられた値を、2番目の引数で与えられた値の倍数に切り上げる（丸める）ために使用されます。以前は、`Thearch.Ptrsize` (ターゲットアーキテクチャのポインタサイズ、例えば32ビットシステムでは4バイト) をアラインメントの基準としていました。しかし、`.debug_aranges` セクションのタプルは、アドレスと長さのペアで構成され、そのサイズは `2 * Thearch.Ptrsize` となります。このため、`Thearch.Ptrsize` を基準とした丸めでは、タプルのアラインメント要件を満たせない場合がありました。

*   **変更後**:
    ```go
    // The first tuple is aligned to a multiple of the size of a single tuple
    // (twice the size of an address)
    headersize := int(Rnd(4+2+4+1+1, int64(Thearch.Ptrsize*2))) // don't count unit_length field itself
    ```
    新しいコードでは、アラインメントの基準が `int64(Thearch.Ptrsize*2)` に変更されています。これにより、`headersize` は常にアドレス範囲タプルのサイズ（`2 * Ptrsize`）の倍数に丸められることが保証されます。この変更によって、ヘッダーの直後に続く最初のアドレス範囲タプルがDwarfの仕様に従って正しくアラインされ、デバッガが `.debug_aranges` セクションを正確にパースできるようになります。コメントも追加され、この変更の意図が明確に説明されています。

### `src/runtime/runtime-lldb_test.go` の追加

このファイルは、GoのランタイムとLLDBデバッガの連携を検証するための新しいテストスイートです。

*   **`TestLldbPython` 関数**:
    このテストは、Goプログラムをビルドし、その実行可能ファイルをPythonスクリプトを介してLLDBでデバッグする一連のプロセスを自動化します。
    1.  `lldbHelloSource` というシンプルなGoプログラム（`main` 関数内で `intvar := 42` のような変数を定義）を一時ディレクトリに書き込みます。
    2.  `go build -gcflags "-N -l"` コマンドを使用して、最適化を無効にした状態でGoプログラムをビルドし、デバッグ情報が保持されるようにします。
    3.  `lldbScriptSource` というPythonスクリプトを生成します。このスクリプトはLLDBを起動し、ビルドされたGoプログラムをターゲットとして設定し、`main.go` の特定の行（`fmt.Println("hi")` の行）にブレークポイントを設定します。
    4.  LLDBでプログラムを実行し、ブレークポイントで停止した際に、`intvar` の値が期待通り `42` であることを確認します。
    5.  このテストは、Goリンカーが生成するDwarf情報がLLDBによって正しく解釈され、デバッグセッションが期待通りに動作することを確認するためのエンドツーエンドの検証を提供します。

*   **`TestDwarfAranges` 関数**:
    このテストは、LLDBがインストールされていない環境でも `.debug_aranges` セクションの構造が正しいことを検証します。
    1.  `lldbHelloSource` と同じGoプログラムをビルドします。
    2.  生成された実行可能ファイル（ELFまたはMach-O形式）を開き、`.debug_aranges` セクションを読み込みます。
    3.  `verifyAranges` ヘルパー関数を呼び出し、`.debug_aranges` セクションのヘッダーとタプルの構造がDwarfの仕様に準拠しているか（特にアラインメントとパディングが正しいか）をプログラム的に検証します。
    4.  このテストは、Dwarf情報の内部構造の正確性を保証し、デバッガの有無にかかわらず、リンカーが常に正しいデバッグ情報を生成していることを確認します。

これらのテストの追加により、Dwarf情報の生成に関する回帰バグが将来的に発生するのを防ぎ、Goプログラムのデバッグ体験の安定性が向上します。

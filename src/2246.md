# [インデックス 2246] ファイルの概要

このコミットは、Go言語の標準ライブラリである `testing` パッケージに `t.Failed()` メソッドを追加するものです。この新しいメソッドは、現在のテスト関数が既に失敗としてマークされているかどうかを示すブール値を返します。これにより、テストコード内でテストの失敗状態をプログラム的に確認できるようになり、より柔軟なテストロジックの実装が可能になります。また、テスト出力の整形に関する`tabify`関数と`Logf`メソッドの内部的な改善も含まれています。

## 変更の背景

Goの`testing`パッケージでは、テスト関数内で`t.Fail()`を呼び出すことでテストを失敗としてマークできます。しかし、このコミット以前は、テスト関数自身が「自分が既に失敗としてマークされているか」という状態を直接問い合わせる手段がありませんでした。

この機能が求められる背景には、以下のようなシナリオが考えられます。

1.  **条件付きのクリーンアップ**: テストが特定の時点で失敗した場合にのみ、追加のリソースクリーンアップやエラー報告を行いたい場合。例えば、テストの途中で致命的なエラーが発生し、それ以降の処理が無意味になる場合、`t.Failed()`を使って後続のクリーンアップ処理をスキップしたり、エラーログを詳細化したりすることができます。
2.  **エラーの重複報告の回避**: 複数のチェックポイントがあるテストにおいて、一度失敗が検出されたらそれ以降の関連するエラー報告を抑制したい場合。これにより、テスト出力が冗長になるのを防ぎ、真の原因を特定しやすくします。
3.  **より複雑なテストロジック**: テストの実行フローを、その時点でのテストの成功/失敗状態に基づいて動的に変更したい場合。

`t.Failed()`の導入は、テストの記述においてより高度な制御と柔軟性を提供し、テストコードの品質と保守性を向上させることを目的としています。また、`tabify`関数と`Logf`メソッドの変更は、テスト出力の整形ロジックを改善し、`t.Failed()`の導入と合わせて、より堅牢で予測可能なテストレポートを生成するための基盤を強化しています。

## 前提知識の解説

### Go言語の `testing` パッケージ

Go言語には、ユニットテスト、ベンチマークテスト、および例（Example）テストをサポートするための組み込みの `testing` パッケージがあります。

*   **テスト関数**: `func TestXxx(*testing.T)` というシグネチャを持つ関数がテスト関数として認識されます。`Xxx`は英大文字で始まる必要があります。
*   **`*testing.T`**: テスト関数に渡されるポインタで、テストの状態管理、エラー報告、ログ出力などのためのメソッドを提供します。
*   **`t.Fail()`**: このメソッドを呼び出すと、現在のテスト関数が失敗としてマークされます。ただし、テスト関数の実行は継続されます。
*   **`t.FailNow()`**: このメソッドを呼び出すと、現在のテスト関数が失敗としてマークされ、そのテスト関数の実行が即座に停止されます。`defer`関数は実行されますが、それ以降のテストコードは実行されません。
*   **`t.Log()` / `t.Logf()`**: テスト中に情報をログに出力するために使用されます。これらの出力は、テストが失敗した場合にのみ表示されるのが一般的です（`go test -v`オプションを使用しない限り）。
*   **`t.Error()` / `t.Errorf()`**: `t.Log()` / `t.Logf()` と `t.Fail()` を組み合わせたものです。メッセージをログに出力し、テストを失敗としてマークします。
*   **`t.Fatal()` / `t.Fatalf()`**: `t.Log()` / `t.Logf()` と `t.FailNow()` を組み合わせたものです。メッセージをログに出力し、テストを失敗としてマークして、テスト関数の実行を停止します。

### テストの失敗状態

`testing.T`の内部には、テストが失敗したかどうかを追跡するためのプライベートなフラグ（このコミットでは`failed`というフィールド）が存在します。`t.Fail()`や`t.FailNow()`が呼び出されると、このフラグが`true`に設定されます。このコミット以前は、この内部状態を外部から直接参照するパブリックなメソッドは提供されていませんでした。

### `tabify` 関数

`tabify`関数は、テストのログ出力において、複数行にわたるメッセージの各行の先頭にタブを追加して整形するためのユーティリティ関数です。これにより、テスト出力の可読性が向上し、エラーメッセージが適切にインデントされて表示されます。

## 技術的詳細

このコミットの主要な変更点は、`testing.T`構造体に`Failed()`メソッドを追加し、テストの内部的な失敗状態を外部に公開したことです。

### `testing.T` 構造体と `failed` フィールド

`testing.T`構造体は、テストの実行中にその状態を管理します。この構造体には、テストが失敗したかどうかを示すブール型のプライベートフィールド`failed`が含まれています。

```go
type T struct {
    // ... その他のフィールド ...
    failed bool // true if Test.Fail or Test.FailNow has been called.
    // ... その他のフィールド ...
}
```

`t.Fail()`メソッドが呼び出されると、この`failed`フィールドが`true`に設定されます。

```go
func (t *T) Fail() {
    t.failed = true
}
```

### `t.Failed()` メソッドの追加

このコミットで追加された`Failed()`メソッドは、単にこの`failed`フィールドの現在の値を返します。

```go
// Failed returns whether the Test function has failed.
func (t *T) Failed() bool {
    return t.failed
}
```

これにより、テストコード内で以下のようにテストの失敗状態をチェックできるようになります。

```go
func TestSomething(t *testing.T) {
    // ... テストロジック ...
    if someConditionFails {
        t.Error("Some condition failed")
    }

    if t.Failed() {
        // テストが既に失敗している場合のみ実行されるロジック
        t.Log("Test has already failed, performing conditional cleanup.")
        // ...
    }
    // ...
}
```

### `tabify` 関数と `Logf` メソッドの変更

このコミットでは、`tabify`関数と`Logf`メソッドにも関連する変更が加えられています。

#### `tabify` 関数の改善

以前の`tabify`関数は、文字列の最後の文字が改行でない場合に、最後の改行を考慮せずにループしていました。新しい実装では、まず文字列の最後に改行がない場合に改行を追加し、その上で各内部改行の後にタブを挿入するように変更されています。これにより、`tabify`が常に適切な改行とタブの整形を行うようになり、`Logf`のような呼び出し元での改行処理が不要になりました。

変更前:
```go
func tabify(s string) string {
    for i := 0; i < len(s) - 1; i++ {    // -1 because if last char is newline, don't bother
        if s[i] == '\n' {
            return s[0:i+1] + "\t" + tabify(s[i+1:len(s)]);
        }
    }
    return s
}
```

変更後:
```go
func tabify(s string) string {
    n := len(s);
    if n > 0 && s[n-1] != '\n' {
        s += "\n";
        n++;
    }
    for i := 0; i < n - 1; i++ {    // -1 to avoid final newline
        if s[i] == '\n' {
            return s[0:i+1] + "\t" + tabify(s[i+1:n]);
        }
    }
    return s
}
```
この変更により、`tabify`関数は、入力文字列が改行で終わっていない場合でも、最終的に改行を追加し、その上で適切にタブを挿入するようになりました。これにより、`Logf`などの呼び出し元で明示的に改行を追加するロジックが不要になります。

#### `Logf` メソッドの簡素化

`tabify`関数の改善に伴い、`Logf`メソッド内で明示的に改行を追加していたロジックが削除されました。これは、`tabify`関数が既に最終的な改行を適切に処理するようになったためです。

変更前:
```go
func (t *T) Logf(format string, args ...) {
    t.errors += tabify(fmt.Sprintf("\t" + format, args));
    l := len(t.errors);
    if l > 0 && t.errors[l-1] != '\n' {
        t.errors += "\n"
    }
}
```

変更後:
```go
func (t *T) Logf(format string, args ...) {
    t.errors += "\t" + tabify(fmt.Sprintf(format, args));
}
```
この変更により、`Logf`のコードがより簡潔になり、`tabify`関数への依存が明確になりました。

## コアとなるコードの解説

### `tabify` 関数の変更

*   **変更前**: `for i := 0; i < len(s) - 1; i++` のループ条件は、文字列の最後の文字が改行であるかどうかに関わらず、常に最後の1文字を除外していました。これは、最後の文字が改行である場合に、その改行の後にタブを追加しないという意図があったためです。しかし、入力文字列が改行で終わっていない場合、最終的な出力にも改行が追加されない可能性がありました。
*   **変更後**:
    1.  `n := len(s);` で文字列の長さを取得します。
    2.  `if n > 0 && s[n-1] != '\n' { s += "\n"; n++; }` の行が追加されました。これは、入力文字列`s`が空でなく、かつ最後の文字が改行でない場合に、明示的に改行を追加し、文字列の長さ`n`を更新します。これにより、`tabify`関数が常に改行で終わる文字列を生成するようになります。
    3.  ループ条件が `for i := 0; i < n - 1; i++` に変更されました。`n`が新しい文字列の長さ（必要に応じて改行が追加された後の長さ）を反映しているため、このループは最後の改行文字の直前までを処理します。
    4.  再帰呼び出しの `tabify(s[i+1:len(s)])` が `tabify(s[i+1:n])` に変更されました。これは、`n`が新しい文字列の長さを正確に表しているため、スライス操作が正しく行われることを保証します。

この変更により、`tabify`関数はより堅牢になり、常に整形された出力の最後に改行を保証するようになりました。

### `Failed()` メソッドの追加

*   `func (t *T) Failed() bool { return t.failed }` という新しいメソッドが`*testing.T`型に追加されました。
*   このメソッドは、`testing.T`構造体のプライベートフィールドである`failed`の値をそのまま返します。
*   `failed`フィールドは、`t.Fail()`または`t.FailNow()`が呼び出されたときに`true`に設定されます。
*   このメソッドの導入により、テストコード内でテストの現在の失敗状態をプログラム的にチェックできるようになり、テストロジックの柔軟性が向上しました。

### `Logf` メソッドの変更

*   **変更前**: `Logf`メソッドは、`tabify`関数で整形された文字列を`t.errors`に追加した後、明示的に最後の文字が改行でない場合に改行を追加していました。これは、`tabify`関数が常に改行で終わる文字列を生成するとは限らなかったためです。
*   **変更後**: `t.errors += "\t" + tabify(fmt.Sprintf(format, args));` の一行に簡素化されました。これは、`tabify`関数が既に最終的な改行を適切に処理するようになったため、`Logf`内で重複して改行をチェック・追加する必要がなくなったためです。

これらの変更は、Goの`testing`パッケージの内部的な堅牢性と使いやすさを向上させるためのものであり、特に`t.Failed()`の追加は、より高度なテストシナリオを可能にする重要な機能拡張です。

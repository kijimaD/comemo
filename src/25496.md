# [インデックス 25496] ファイルの概要

このコミットは、Goランタイムのガベージコレクション（GC）におけるマークフェーズのワーカー起動メカニズムを改善し、GCのパフォーマンス安定性を向上させることを目的としています。具体的には、GCが新しい作業を検出した際に、スケジューラのタイミングに依存するのではなく、能動的に専用マークワーカーを起動するよう変更されています。

## 変更の背景

Goのガベージコレクタ（GC）は、プログラムの実行と並行して動作する並行GCです。GCの重要なフェーズの一つに「マークフェーズ」があり、このフェーズでは到達可能なオブジェクトを特定し、マークします。この作業は複数の「マークワーカー」によって並行して行われます。

従来のGoランタイムでは、専用マークワーカーの起動は、Goスケジューラの通常のプリエンプション（横取り）ロジックに依存していました。これは、実行中のGoルーチンがプリエンプトされ、そのP（プロセッサ）がGCのマークワーカーに割り当てられるのを待つことを意味します。しかし、このメカニズムにはいくつかの問題がありました。

1.  **起動の遅延**: スケジューラのタイミングによっては、新しいGC作業が発生しても、専用マークワーカーがすぐに起動しない可能性がありました。コミットメッセージにあるように、最悪の場合、マークフェーズの開始時や作業負荷の変動時に最大10ミリ秒の遅延が発生することがありました。この遅延は、GCのレイテンシを増加させ、アプリケーションの応答性に悪影響を与える可能性があります。
2.  **パフォーマンスの不安定性**: 起動の遅延は、GCの実行時間を予測不可能にし、アプリケーションのパフォーマンスにばらつきを生じさせることがありました。特に、リアルタイム性が求められるアプリケーションでは、このような不安定性は許容されません。
3.  **リソースの非効率な利用**: GC作業が利用可能であるにもかかわらず、ワーカーが起動しない期間があることは、システムリソースの非効率な利用につながります。

このコミットは、これらの問題を解決し、GCのマークフェーズにおけるワーカーの起動をより迅速かつ予測可能にすることで、GCのパフォーマンス安定性と全体的な効率を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムとガベージコレクションに関する基本的な概念を理解しておく必要があります。

### 1. Goランタイムとスケジューラ (M, P, G)

Goランタイムは、Goプログラムの実行を管理するシステムです。その中核には、Goスケジューラがあります。Goスケジューラは、OSのスレッド（M: Machine）上でGoルーチン（G: Goroutine）を実行するために、論理プロセッサ（P: Processor）という抽象化されたリソースを使用します。

*   **G (Goroutine)**: Goランタイムによって管理される軽量なスレッドです。数千から数百万のGoルーチンを同時に実行できます。
*   **M (Machine)**: OSのスレッドに相当します。GoルーチンはM上で実行されます。
*   **P (Processor)**: 論理プロセッサであり、MとGの間のコンテキストとして機能します。Pは実行可能なGoルーチンのキューを保持し、MにGoルーチンを供給します。`GOMAXPROCS`環境変数によってPの数を設定できます。

Goスケジューラは、Pを介してMにGを割り当て、実行を管理します。プリエンプションは、実行中のGoルーチンを一時停止し、別のGoルーチンにPを割り当てるプロセスです。

### 2. Goのガベージコレクタ (GC)

GoのGCは、並行マーク＆スイープ方式を採用しています。これは、プログラムの実行と並行してGCが動作することを意味します。主なフェーズは以下の通りです。

*   **マークフェーズ (Mark Phase)**: プログラムが使用しているオブジェクト（到達可能なオブジェクト）を特定し、マークします。このフェーズは、プログラムの実行と並行して行われる「並行マーク」と、プログラムの実行を一時停止して行われる「マークターミネーション」に分けられます。
*   **スイープフェーズ (Sweep Phase)**: マークされなかったオブジェクト（到達不能なオブジェクト）を解放し、メモリを再利用可能にします。

このコミットが焦点を当てているのは、マークフェーズにおける「専用マークワーカー」の起動です。

### 3. 専用マークワーカー (Dedicated Mark Workers)

GoのGCでは、マークフェーズの効率を上げるために、通常のGoルーチンとは別に、GC専用のGoルーチンである「マークワーカー」が使用されます。これらのワーカーは、ヒープを走査して到達可能なオブジェクトをマークする役割を担います。特に「専用マークワーカー」は、GCのマークフェーズ中にPを占有し、GC作業に専念するワーカーです。

### 4. `workbuf` と `putfull`

GoのGCでは、マーク作業を効率的に分散するために「ワークバッファ」という仕組みを使用します。

*   **`workbuf`**: マークすべきオブジェクトへのポインタを一時的に格納するバッファです。マークワーカーは、このバッファからオブジェクトを取り出してマークし、新しい到達可能なオブジェクトが見つかれば、それを別の`workbuf`に格納します。
*   **`putfull`**: `workbuf`がいっぱいになったときに呼び出される関数です。この関数は、いっぱいの`workbuf`をグローバルなキュー（`work.full`）にプッシュし、他のマークワーカーがその作業を取り出せるようにします。

このコミットでは、`putfull`が呼び出された際に、新しい作業が利用可能になったことをGCコントローラに通知し、必要に応じて専用マークワーカーを起動するトリガーとして機能します。

### 5. プリエンプション (Preemption)

Goスケジューラは、長時間実行されるGoルーチンがPを独占するのを防ぐために、プリエンプションメカニズムを使用します。これにより、他のGoルーチンにも実行機会が与えられます。しかし、GCのマークワーカーの起動がこの通常のプリエンプションに依存していると、GC作業の緊急性にもかかわらず、ワーカーの起動が遅れる可能性がありました。

## 技術的詳細

このコミットの技術的な核心は、`putfull`関数がGCコントローラに新しい作業の可用性を通知し、GCコントローラが能動的に専用マークワーカーを起動するメカニズムを導入した点にあります。

### 1. `enlistWorker` 関数の導入

`src/runtime/mgc.go`に`enlistWorker`という新しい関数が追加されました。この関数の目的は、専用マークワーカーが不足している場合に、別のPで専用マークワーカーを起動するように促すことです。

*   **`c.dedicatedMarkWorkersNeeded <= 0`**: まず、専用マークワーカーが必要ない場合はすぐにリターンします。これは、既に十分なワーカーが稼働しているか、GCフェーズがマークフェーズではない場合などです。
*   **ランダムなPの選択**: `gomaxprocs`が1より大きい場合、現在実行中のP以外のランダムなPを選択します。これは、`fastrand1() % uint32(gomaxprocs-1)`と現在のPのIDを考慮して行われます。ランダムにPを選択することで、特定のPに偏ることなく、システム全体でワーカーを分散させようとします。
*   **Pの状態チェック**: 選択されたPが`_Prunning`状態（つまり、現在Goルーチンを実行中）であるかどうかを確認します。これにより、アイドル状態のPや既にGC作業中のPを不必要にプリエンプトするのを避けます。
*   **`preemptone(p)`**: 選択されたPに対して`preemptone`関数を呼び出します。この関数は、指定されたPで実行中のGoルーチンをプリエンプトし、そのPをGCのマークワーカーに割り当てることを試みます。成功した場合、関数はリターンします。
*   **リトライメカニズム**: 最大5回までランダムなPの選択とプリエンプトを試みます。これにより、最初の試行でPを確保できなかった場合でも、ワーカーを起動する可能性を高めます。

### 2. `putfull` からの `enlistWorker` の呼び出し

`src/runtime/mgcwork.go`の`putfull`関数に以下の変更が加えられました。

```go
 	lfstackpush(&work.full, &b.node)

 	// We just made more work available. Let the GC controller
 	// know so it can encourage more workers to run.
 	if gcphase == _GCmark {
 		gcController.enlistWorker()
 	}
```

*   `putfull`は、`workbuf`がいっぱいになり、その内容がグローバルな作業キュー（`work.full`）にプッシュされたときに呼び出されます。これは、GCが処理すべき新しいオブジェクトを発見し、作業量が増加したことを意味します。
*   `gcphase == _GCmark`の条件チェックにより、現在のGCフェーズがマークフェーズである場合にのみ`enlistWorker`が呼び出されます。これにより、GCの他のフェーズで不必要にワーカーを起動するのを防ぎます。
*   `gcController.enlistWorker()`を呼び出すことで、GCコントローラは新しい作業が利用可能になったことを認識し、必要に応じて追加の専用マークワーカーを起動するよう促します。

### 3. パフォーマンスへの影響

コミットメッセージに記載されているベンチマーク結果は、この変更がGCのパフォーマンス安定性に与える肯定的な影響を示しています。

*   **`XBenchGarbage-12`ベンチマークの12%高速化**: これは、GCの作業負荷が高いシナリオにおいて、ワーカーの迅速な起動がGCの効率を大幅に改善することを示しています。
*   **全体的なGo1ベンチマークへの影響はなし**: 多くのベンチマークでは統計的に有意な変化が見られなかったものの、これはこの変更が既存のアプリケーションのパフォーマンスを悪化させることなく、特定のGC負荷の高いシナリオで改善をもたらすことを意味します。

この変更により、GCが作業をより迅速に処理できるようになり、特にGCの開始時や作業量の変動時に発生する可能性のある遅延が削減されます。結果として、GCのストップ・ザ・ワールド（STW）時間が短縮され、アプリケーションのレイテンシが改善される可能性があります。

## コアとなるコードの解説

### `src/runtime/mgc.go` の `enlistWorker` 関数

この関数は、GCコントローラ（`gcControllerState`）のメソッドとして追加されました。
*   `c.dedicatedMarkWorkersNeeded <= 0`：専用マークワーカーが必要とされていない場合（例えば、既に十分なワーカーが稼働しているか、マークフェーズではない場合）、処理を終了します。
*   `gomaxprocs <= 1`：`GOMAXPROCS`が1以下の場合、並行処理の恩恵が少ないため、処理を終了します。
*   `gp := getg()`、`myID := gp.m.p.ptr().id`：現在実行中のGoルーチン（`gp`）から、そのGoルーチンが実行されているPのID（`myID`）を取得します。これは、自分自身が実行されているPをプリエンプトしないようにするためです。
*   `for tries := 0; tries < 5; tries++`：最大5回まで、ランダムなPを選択してプリエンプトを試みます。
*   `id := int32(fastrand1() % uint32(gomaxprocs-1))`：`fastrand1()`を使って擬似乱数を生成し、`gomaxprocs-1`で割った余りからランダムなPのIDを決定します。`gomaxprocs-1`を使うのは、現在のPを除外するためです。
*   `if id >= myID { id++ }`：もしランダムに選ばれたIDが現在のPのID以上であれば、IDを1つ増やします。これにより、現在のPを確実にスキップし、他のPを選択します。
*   `p := allp[id]`：選択されたIDに対応するPのポインタを取得します。`allp`は、システム内のすべてのPを保持するグローバルな配列です。
*   `if p.status != _Prunning { continue }`：選択されたPが現在Goルーチンを実行中（`_Prunning`状態）でない場合、そのPはプリエンプトの対象ではないため、次のPの選択に進みます。
*   `if preemptone(p) { return }`：`preemptone`関数を呼び出して、選択されたPで実行中のGoルーチンをプリエンプトし、そのPをGCのマークワーカーに割り当てることを試みます。成功した場合（`true`を返す）、関数は終了します。

この`enlistWorker`関数は、GCコントローラが能動的にPを確保し、専用マークワーカーを起動するための重要なメカニズムを提供します。

### `src/runtime/mgcwork.go` の `putfull` 関数

`putfull`関数は、`workbuf`がいっぱいになったときに呼び出され、その`workbuf`をグローバルなキューにプッシュする役割を担います。このコミットでは、この関数に以下のロジックが追加されました。

*   `if gcphase == _GCmark { gcController.enlistWorker() }`：
    *   `gcphase == _GCmark`：現在のGCフェーズがマークフェーズであるかどうかを確認します。マークフェーズ中にのみ、専用マークワーカーの起動を促す必要があります。
    *   `gcController.enlistWorker()`：マークフェーズ中で、かつ新しい作業が利用可能になった場合（`putfull`が呼び出されたため）、`gcController`の`enlistWorker`メソッドを呼び出します。これにより、GCコントローラは、必要に応じて追加の専用マークワーカーを起動するよう試みます。

この変更により、GCは新しい作業が生成されたことを即座に検知し、スケジューラの通常のプリエンプションサイクルを待つことなく、より迅速にワーカーを投入できるようになります。これは、GCのレイテンシを削減し、特にGCの開始時や作業負荷の急増時にパフォーマンスの安定性を向上させる上で非常に重要です。

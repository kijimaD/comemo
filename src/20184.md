# [インデックス 20184] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）のパフォーマンス改善を目的としています。具体的には、GCビットマスクの「アンロールされた」バージョンをキャッシュすることで、GC処理のオーバーヘッドを削減します。

## 変更の背景

Goのガベージコレクタ（GC）は、ヒープ上のオブジェクトを走査し、到達可能なオブジェクトを特定してマークする際に、各オブジェクトの構造に関する情報（どのフィールドがポインタであるかなど）を必要とします。この情報は「GCビットマスク」として表現されます。

従来のGoのGCでは、このビットマスクを処理する際に、ループを使って各ビットを個別にチェックするような処理が行われていました。しかし、このようなループ処理は、特に小さなオブジェクトが多数存在するようなシナリオでは、CPUのキャッシュ効率を悪化させ、命令の分岐予測ミスを誘発し、パフォーマンスのボトルネックとなる可能性がありました。

コミットメッセージに記載されているように、パフォーマンスプロファイリングの結果、HTTPベンチマークにおいて`unrollgcproginplace_m`および`unrollgcprog1`という関数がCPU時間の約2%を消費していることが判明しました。これらの関数は、GCビットマスクの処理に関連するものであり、このオーバーヘッドを削減することがGC全体の効率向上に繋がると判断されました。

このコミットの目的は、GCビットマスクの処理を最適化し、特に頻繁にアクセスされる小さなオブジェクトのGCコストを削減することにあります。

## 前提知識の解説

### ガベージコレクション (GC) とは

ガベージコレクションは、プログラムが動的に確保したメモリ領域のうち、もはやプログラムから到達不可能になった（不要になった）領域を自動的に解放する仕組みです。これにより、プログラマは手動でのメモリ管理から解放され、メモリリークなどのバグを減らすことができます。Go言語は、並行マーク＆スイープ方式をベースとしたGCを採用しています。

### GCビットマスク

GoのGCは、ヒープ上のオブジェクトを走査する際に、そのオブジェクトのどの部分がポインタであり、どの部分が非ポインタデータであるかを正確に知る必要があります。これは、ポインタをたどって到達可能なオブジェクトをマークするためです。この情報を効率的に表現するために、「GCビットマスク」が使用されます。

GCビットマスクは、オブジェクトのメモリレイアウトに対応するビット列で、各ビットがオブジェクト内の特定のワード（またはバイト）がポインタであるか否かを示します。例えば、1がポインタ、0が非ポインタといった具合です。GCは、このビットマスクを参照しながらオブジェクトを走査し、ポインタフィールドを見つけると、そのポインタが指す先のオブジェクトも走査対象とします。

### ループアンローリング (Loop Unrolling)

ループアンローリングは、プログラムの最適化手法の一つです。これは、ループの反復回数を減らすために、ループ本体のコードを複数回コピーして展開するものです。

例えば、以下のようなループがあったとします。

```c
for (int i = 0; i < 4; i++) {
    array[i] = i;
}
```

これをループアンローリングすると、以下のようになります。

```c
array[0] = 0;
array[1] = 1;
array[2] = 2;
array[3] = 3;
```

ループアンローリングの利点は以下の通りです。
*   **ループオーバーヘッドの削減**: ループの条件チェックやカウンタのインクリメントといったオーバーヘッドが削減されます。
*   **命令レベル並列性 (ILP) の向上**: より多くの独立した命令が連続して実行されるため、CPUのパイプラインが効率的に利用され、複数の命令を同時に実行できる可能性が高まります。
*   **キャッシュ効率の向上**: 連続したメモリ領域へのアクセスが増えることで、CPUキャッシュのヒット率が向上する可能性があります。

しかし、コードサイズが増加するという欠点もあります。

### `unrollgcproginplace_m` / `unrollgcprog1`

これらの関数名は、GoのGCがオブジェクトのポインタを走査する際に、GCビットマスクを処理するための内部関数であると推測されます。`unroll`という接頭辞から、GCビットマスクの処理にループアンローリングの概念が適用されていることが示唆されます。`in place`は、その場で処理を行うことを意味し、`prog`はプログラムまたはプログレッション（進行）を意味する可能性があります。

## 技術的詳細

このコミットの核心は、GCビットマスクの処理を高速化するために、**アンロールされたGCビットマスクをキャッシュする**という点にあります。

GoのGCは、オブジェクトの型情報に基づいてGCビットマスクを生成します。このビットマスクは、オブジェクト内のどのオフセットにポインタが存在するかを示します。GCがヒープを走査する際、各オブジェクトに対してこのビットマスクを読み取り、ポインタフィールドを特定してマーク処理を進めます。

従来のGoランタイムでは、このビットマスクの処理が、特に小さなオブジェクトに対しては、ループ処理によって行われていました。これは、オブジェクトのサイズやポインタの数に応じて、動的に処理を行うための一種の「GCプログラム」を実行するようなものです。しかし、この動的な処理は、前述の通りオーバーヘッドを伴います。

このコミットでは、特定のサイズ（64ビットシステムで最大64KB、32ビットシステムで最大32KB）までの型について、GCビットマスクの「アンロールされた」バージョンを事前に計算し、キャッシュするようになりました。

「アンロールされたGCビットマスク」とは、GCビットマスクを処理するためのループを事前に展開（アンロール）した、より効率的な命令列のことです。これにより、GCがオブジェクトを走査する際に、動的にループを回す代わりに、キャッシュされたアンロール済み命令列を直接実行できるようになります。これは、CPUの分岐予測ミスを減らし、命令パイプラインをより効率的に利用することを可能にします。

コミットメッセージにある「最大4Kのキャッシュされたビットマスク」とは、アンロールされたビットマスクのサイズが最大4KBになることを指していると考えられます。これは、GCビットマスクがオブジェクトのサイズに比例して大きくなるため、ある程度のサイズまでのオブジェクトに限定してキャッシュすることで、メモリ使用量とキャッシュヒット率のバランスを取っていることを示唆しています。

`src/pkg/runtime/malloc.go`と`src/pkg/runtime/mgc0.h`の変更は、このキャッシュ機構を有効にするための定数`maxGCMask`の値を変更しています。

*   `maxGCMask = 0` (無効) から `maxGCMask = 64` (有効) へ変更。

この`maxGCMask`は、キャッシュするGCビットマスクの最大サイズ（バイト単位）を定義していると考えられます。64バイトという値は、64ビットシステムで1024バイト（1KB）、32ビットシステムで512バイトのオブジェクトに対応するとコメントに記載されています。これは、GCビットマスクがオブジェクトのサイズに応じて生成されるため、64バイトのビットマスクでカバーできるオブジェクトの最大サイズを示しています。

この変更により、GCは頻繁に処理される小さなオブジェクトに対して、より高速なアンロール済みビットマスク処理パスを利用できるようになり、GCの全体的なパフォーマンスが向上します。特に、HTTPベンチマークのような、多数の小さなオブジェクトが生成・破棄されるワークロードにおいて、顕著な改善が期待されます。

## コアとなるコードの変更箇所

このコミットでは、主に2つのファイルが変更されています。

1.  `src/pkg/runtime/malloc.go`
2.  `src/pkg/runtime/mgc0.h`

それぞれの変更内容は以下の通りです。

### `src/pkg/runtime/malloc.go`

```diff
--- a/src/pkg/runtime/malloc.go
+++ b/src/pkg/runtime/malloc.go
@@ -28,7 +28,7 @@ const (
 	bitsMask           = 1<<bitsPerPointer - 1
 	pointersPerByte    = 8 / bitsPerPointer
 	bitPtrMask         = bitsMask << 2
-	maxGCMask          = 0 // disabled because wastes several bytes of memory
+	maxGCMask          = 64
 	bitsDead           = 0
 	bitsPointer        = 2
 
```

`maxGCMask`という定数の値が`0`から`64`に変更されています。元のコメントでは「メモリを数バイト無駄にするため無効化されている」とありましたが、この変更により有効化されました。

### `src/pkg/runtime/mgc0.h`

```diff
--- a/src/pkg/runtime/mgc0.h
+++ b/src/pkg/runtime/mgc0.h
@@ -55,7 +55,8 @@ enum {

+\t// 64 bytes cover objects of size 1024/512 on 64/32 bits, respectively.
+\tMaxGCMask\t= 64,\

```

こちらも同様に`MaxGCMask`という定数の値が`0`から`64`に変更されています。新しいコメントでは、この64バイトが64ビットシステムで1024バイト（1KB）、32ビットシステムで512バイトのオブジェクトをカバーすることが説明されています。

## コアとなるコードの解説

変更されたコードは、Goランタイムのメモリ割り当てとガベージコレクションに関連する定数定義の一部です。

`maxGCMask` (または `MaxGCMask`) は、GCビットマスクをキャッシュする際の最大サイズを制御する定数です。

*   **変更前 (`maxGCMask = 0`)**: この値が0であることは、GCビットマスクのキャッシュ機能が事実上無効化されていたことを意味します。コメントにも「disabled because wastes several bytes of memory」（数バイトのメモリを無駄にするため無効化されている）と明記されており、メモリ使用量とのトレードオフでこの最適化がオフにされていたことがわかります。
*   **変更後 (`maxGCMask = 64`)**: この値を64に設定することで、GCビットマスクのキャッシュ機能が有効化されました。64という値は、キャッシュされるGCビットマスクの最大サイズ（バイト単位）を示しています。コメントにあるように、この64バイトのビットマスクは、64ビットシステムでは1024バイト（1KB）までのオブジェクト、32ビットシステムでは512バイトまでのオブジェクトのポインタ情報をカバーできます。

この変更は、GCがオブジェクトを走査する際に、特定のサイズのオブジェクトに対しては、動的にビットマスクを処理するのではなく、事前に計算されキャッシュされた「アンロールされた」ビットマスク処理ロジックを使用するように指示します。これにより、GCのホットパス（頻繁に実行されるコードパス）におけるCPUサイクルを節約し、全体的なGCのレイテンシとスループットを向上させることが期待されます。

この最適化は、特に小さなオブジェクトが大量に生成・破棄されるようなワークロード（例: HTTPリクエスト処理）において効果を発揮します。プロファイリングによって`unrollgcproginplace_m`/`unrollgcprog1`がボトルネックであることが特定されたため、この変更は具体的なパフォーマンス課題に対する直接的な解決策として導入されました。

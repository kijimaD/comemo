# [インデックス 27726] ファイルの概要

## 変更の背景

コンピュータのプロセッサにおいて、除算命令は一般的に乗算や加算、ビットシフトなどの他の算術命令と比較して非常に高コストです。特に、定数による除算の場合、コンパイル時に除数を既知の定数として扱うことで、より高速な乗算とビットシフトの組み合わせに置き換える最適化手法が存在します。この手法は「マジックナンバーによる除算」として知られ、『Hacker's Delight』の第10章などで詳細に解説されています。

Goコンパイラもこの最適化を実装していますが、以前の実装では、特定のアーキテクチャ（例: ARM64, PPC64）に対してこの最適化を無効にするためのハードコードされたチェックが含まれていました。これは、これらのアーキテクチャが最適化に必要な特定の命令（例えば、64ビット高位乗算やキャリー付きローテート）をサポートしていない、またはコンパイラがそれらを適切に利用できていなかったためです。

このコミットの背景には、以下の課題がありました。

1.  **アーキテクチャ固有の最適化の柔軟性不足**: ハードコードされたチェックでは、新しいアーキテクチャの追加や既存アーキテクチャの命令セット拡張があった場合に、コードの変更が必要となり、柔軟性に欠けていました。
2.  **最適化の適用範囲の拡大**: `s390x`のような新しいアーキテクチャが64ビット高位乗算をサポートしているにもかかわらず、最適化が適用されない可能性がありました。
3.  **コードの可読性と保守性**: `TODO`コメントが残されており、将来的な改善点として認識されていましたが、具体的な解決策が明確ではありませんでした。

このコミットは、これらの課題に対処し、除算最適化のロジックをより汎用的かつアーキテクチャの能力に依存するようにリファクタリングすることを目的としています。

## 前提知識の解説

### Goコンパイラのコード生成 (cgen)

Goコンパイラの`cmd/compile/internal/gc`パッケージは、Go言語のソースコードを中間表現（AST）から最終的な機械語コードに変換する役割を担っています。`cgen.go`ファイルは、このコード生成フェーズの一部であり、特に算術演算やその他の基本的な操作に対する機械語命令の生成を担当します。`cgen_div`関数は、除算演算子（`/`）や剰余演算子（`%`）がGoコードで使用された際に、対応する効率的な機械語コードを生成するためのロジックを含んでいます。

### 定数による除算の最適化（マジックナンバーによる除算）

整数除算はCPUにとって比較的遅い操作です。しかし、除数がコンパイル時に既知の定数である場合、除算を乗算とビットシフトの組み合わせに変換することで、大幅に高速化できることがあります。このテクニックは「マジックナンバーによる除算」と呼ばれ、以下の原理に基づいています。

`N / D` （N: 被除数、D: 除数）という除算を考えます。
この除算は、`N * (1/D)` と考えることができます。`1/D` を `M / 2^S` （M: マジックナンバー、S: シフト量）という形式で近似し、`N * M >> S` のように乗算とシフトで表現します。
このマジックナンバー `M` とシフト量 `S` は、除数 `D` に応じてコンパイル時に計算されます。これにより、実行時の高コストな除算命令を、より低コストな乗算とシフト命令に置き換えることが可能になります。

### 64ビット高位乗算 (OHMUL / HMUL64)

通常の乗算では、2つのNビット数を乗算すると最大で2Nビットの結果が得られます。例えば、2つの64ビット整数を乗算すると、最大で128ビットの結果になります。多くのCPUアーキテクチャでは、この128ビットの結果の下位64ビットと上位64ビットを別々のレジスタに格納する命令を提供しています。
「高位乗算（High Multiplication）」命令（Goコンパイラでは`OHMUL`または`HMUL64`として参照される）は、この128ビット結果の上位64ビットを取得するための命令です。マジックナンバーによる除算の最適化では、この高位乗算が重要な役割を果たします。特に、`N * M` の結果が64ビットレジスタに収まらない場合に、上位ビットを利用して正確な除算結果を導き出すために必要となります。

### キャリー付きローテート (ORROTC / RROTC64)

「キャリー付きローテート（Rotate Through Carry）」命令（Goコンパイラでは`ORROTC`または`RROTC64`として参照される）は、ビット列をローテート（循環シフト）する際に、CPUのキャリーフラグ（前の演算で発生した桁上がり/桁借りを示すフラグ）をローテートの一部として含める命令です。
この命令は、特に多倍長整数演算や、特定の除算アルゴリズムにおいて、オーバーフローを考慮しながらビット操作を行う際に有用です。マジックナンバーによる除算のアルゴリズムの中には、中間結果のオーバーフローを適切に処理するために、キャリービットを伴うシフト操作が必要となる場合があります。`Hacker's Delight`の第10章では、オーバーフローを避けるために、結果を1ビット右シフトし、キャリービットを最上位ビットに挿入する手法が提案されており、`RROTC`命令はそのような操作を効率的に実現するために利用されます。

### `sys`パッケージとアーキテクチャファミリー

Go言語の`sys`パッケージは、Goがサポートする様々なCPUアーキテクチャ（例: `sys.AMD64`, `sys.ARM`, `sys.S390X`など）を定義しています。Goコンパイラは、ターゲットとするアーキテクチャに応じて異なるコード生成パスを選択することができ、これにより各アーキテクチャの特性を最大限に活かした最適化が可能になります。

## 技術的詳細

このコミットの核心は、定数による除算の最適化を、特定のアーキテクチャがその最適化に必要な命令をサポートしているかどうかに基づいて動的に決定する点にあります。

1.  **`hasHMUL64()` 関数の導入**:
    *   この関数は、現在のターゲットアーキテクチャが64ビット高位乗算（OHMUL）をサポートしているかどうかを判定します。
    *   `switch Ctxt.Arch.Family` を使用して、`sys.AMD64`と`sys.S390X`に対して`true`を返します。これは、これらのアーキテクチャがOHMUL命令を効率的に実行できることを示唆しています。
    *   `sys.ARM`, `sys.ARM64`, `sys.I386`, `sys.MIPS64`, `sys.PPC64`に対しては`false`を返します。
    *   これにより、以前はハードコードされていたアーキテクチャチェックが、より明確な機能チェックに置き換えられました。

2.  **`hasRROTC64()` 関数の導入**:
    *   この関数は、現在のターゲットアーキテクチャが64ビットキャリー付きローテート（ORROTC）命令をサポートしているかどうかを判定します。
    *   `sys.AMD64`に対してのみ`true`を返します。これは、AMD64がこの特定の命令を効率的に提供していることを示しています。
    *   他のアーキテクチャに対しては`false`を返します。
    *   この命令は、マジックナンバーによる除算アルゴリズムにおいて、中間結果のオーバーフローを適切に処理するために必要となる場合があります。特に、被除数に特定の値を加算する際にオーバーフローが発生する可能性がある場合、キャリービットを考慮したシフト操作が求められます。

3.  **`cgen_div` の最適化ロジックの変更**:
    *   `cgen_div`関数内の定数除算の最適化パス（`nr.Op != OLITERAL` の条件）が、`!hasHMUL64()` のチェックを含むように変更されました。
    *   以前は、`Ctxt.Arch.Family == sys.MIPS64 || Ctxt.Arch.Family == sys.ARM64 || Ctxt.Arch.Family == sys.PPC64` のように特定のアーキテクチャを列挙して最適化をスキップしていましたが、これが`hasHMUL64()`の呼び出しに置き換えられました。これにより、OHMULをサポートするアーキテクチャであれば、将来的に追加されるものも含めて、自動的に最適化の対象となる柔軟性が向上しました。
    *   特に、`s390x`は`hasHMUL64()`によって`true`を返すように設定されたため、このアーキテクチャでも定数除算の最適化が有効になります。
    *   さらに、マジックナンバーによる除算アルゴリズムの内部で、`m.Ua != 0`（オーバーフローを考慮する必要がある場合）かつ`!hasRROTC64()`（キャリー付きローテート命令がない場合）の条件が追加されました。この条件が真の場合、より低速な`longdiv`パス（ハードウェア除算命令を使用するパス）にフォールバックします。これは、『Hacker's Delight』第2版の第10章で提案されている、キャリー付きシフト命令を持たないアーキテクチャ向けの代替シーケンスを実装するまでの暫定的な措置として機能します。
    *   以前のコードにあった、8ビット/16ビット乗算に関する特定の最適化ブロックが削除されました。これは、おそらく64ビット除算の文脈では不要になったか、より汎用的な`Thearch.Optoas(OMUL, nl.Type)`でカバーされるようになったためと考えられます。

このリファクタリングにより、Goコンパイラは、各アーキテクチャの命令セットの特性をより細かく考慮し、適切な場合にのみ高性能な定数除算最適化を適用できるようになりました。これにより、コードの保守性が向上し、将来的なアーキテクチャサポートの追加が容易になります。

## コアとなるコードの解説

### `hasHMUL64()` 関数

この関数は、64ビットの高位乗算命令（OHMUL）をサポートするアーキテクチャを識別します。
*   `switch Ctxt.Arch.Family` は、コンパイラが現在ターゲットとしているCPUアーキテクチャファミリーをチェックします。
*   `sys.AMD64` と `sys.S390X` の場合、`true` を返します。これは、これらのアーキテクチャがOHMULを効率的に実行できるハードウェア命令を持っていることを意味します。
*   その他のアーキテクチャ（`sys.ARM`, `sys.ARM64`, `sys.I386`, `sys.MIPS64`, `sys.PPC64`）では `false` を返します。
*   未知のアーキテクチャが指定された場合は `Fatalf` でコンパイラを終了させ、未定義の動作を防ぎます。

### `hasRROTC64()` 関数

この関数は、64ビットのキャリー付きローテート命令（ORROTC）をサポートするアーキテクチャを識別します。
*   `sys.AMD64` の場合のみ `true` を返します。これは、AMD64がこの特定の命令をサポートしていることを示します。
*   他のアーキテクチャでは `false` を返します。
*   この命令は、除算最適化アルゴリズムにおけるオーバーフロー処理で重要な役割を果たします。

### `cgen_div` 関数内の変更点

1.  **最適化パスの条件変更**:
    ```go
    -	if nr.Op != OLITERAL || Ctxt.Arch.Family == sys.MIPS64 || Ctxt.Arch.Family == sys.ARM64 || Ctxt.Arch.Family == sys.PPC64 {
    +	if nr.Op != OLITERAL || !hasHMUL64() {
    		goto longdiv
    	}
    ```
    この変更により、定数除算の最適化（`nr.Op == OLITERAL`）が、`hasHMUL64()` が `true` を返すアーキテクチャでのみ試行されるようになりました。以前のハードコードされたアーキテクチャリストによる除外ではなく、機能ベースのチェックに置き換えられたことで、より柔軟で将来性のある実装になっています。

2.  **オーバーフロー処理の条件追加**:
    ```go
    +		// In order to add the numerator we need to be able to
    +		// avoid overflow. This is done by shifting the result of the
    +		// addition right by 1 and inserting the carry bit into
    +		// the MSB. For now this needs the RROTC instruction.
    +		// TODO(mundaym): Hacker's Delight 2nd ed. chapter 10 proposes
    +		// an alternative sequence of instructions for architectures
    +		// that do not have a shift right with carry instruction.
    +		if m.Ua != 0 && !hasRROTC64() {
    +			goto longdiv
    +		}
    ```
    マジックナンバーによる除算アルゴリズムにおいて、被除数に特定の値を加算する際にオーバーフローが発生する可能性がある場合（`m.Ua != 0`）、かつターゲットアーキテクチャがキャリー付きローテート命令（`hasRROTC64()` が `false`）をサポートしていない場合、この最適化パスを諦めて、より汎用的な`longdiv`パス（ハードウェア除算命令を使用）にフォールバックします。これは、オーバーフローを安全に処理するための`RROTC`命令がない場合に、誤った結果を避けるための安全策です。`TODO`コメントは、将来的に`RROTC`命令がないアーキテクチャ向けの代替アルゴリズムを実装する可能性を示唆しています。

3.  **コメントの更新**:
    *   `// try to do division by multiply by (2^w)/d` のコメントが `// Try to do division using multiplication: (2^w)/d.` に変更され、より簡潔になりました。
    *   `// see hacker's delight chapter 10` が `// See Hacker's Delight, chapter 10.` に変更され、句読点が修正されました。
    *   `// need to add numerator accounting for overflow` や `// need to add numerator` などのコメントも、より丁寧な表現に修正されています。

4.  **8ビット/16ビット乗算最適化の削除**:
    ```diff
    -	if w == 8 {
    -		// use 2-operand 16-bit multiply
    -		// because there is no 2-operand 8-bit multiply
    -		a = Thearch.Optoas(OMUL, Types[TINT16]) // XXX was IMULW
    -	}
    ```
    `longmod`セクションにあったこのコードブロックが削除されました。これは、64ビット除算の文脈ではこの特定の最適化が不要になったか、またはより一般的な`Thearch.Optoas(OMUL, nl.Type)`で適切に処理されるようになったためと考えられます。

これらの変更により、Goコンパイラの除算最適化は、アーキテクチャの能力に合わせたより賢明なコード生成を行うようになり、パフォーマンスと正確性のバランスが向上しました。

# [インデックス 23390] ファイルの概要

このコミットは、Goランタイムにおける`addmoduledata`関数のプラットフォームABIへの準拠に関する修正です。具体的には、`amd64`アーキテクチャのアセンブリコードにおいて、グローバルデータへのアクセスで暗黙的に使用される`R15`レジスタが、呼び出し先保存レジスタ（callee-save register）であるため、その値を保存・復元するように変更されています。これにより、`.init_array`から呼び出される際のABI違反が解消されます。

## 変更の背景

GoプログラムがCGO（C言語との相互運用）を介して共有ライブラリとしてビルドされる場合、Goランタイムの初期化ルーチンの一部が、システムの標準的な初期化プロセスに統合される必要があります。この統合は、通常、ELFバイナリの`.init_array`セクションに登録された関数ポインタを通じて行われます。`.init_array`内の関数は、プログラムの`main`関数が実行される前に、リンカ/ローダによって呼び出されます。

`runtime·addmoduledata`関数は、Goのモジュールデータ（型情報、関数情報など）をランタイムに登録するために使用される重要な初期化関数の一つです。この関数が`.init_array`から呼び出される際、Go独自の呼び出し規約（Go ABI）ではなく、**プラットフォームの標準的な呼び出し規約（プラットフォームABI）**に従う必要があります。

問題は、`runtime·addmoduledata`関数内でグローバルデータ（`runtime·lastmoduledatap`など）にアクセスする際に発生しました。Goのアセンブラは、`amd64`アーキテクチャにおいて、グローバル変数へのアクセスを最適化するために、`R15`レジスタをベースポインタとして暗黙的に使用することがあります。しかし、`R15`レジスタは`amd64`プラットフォームABIにおいて**呼び出し先保存レジスタ（callee-save register）**として定義されています。これは、関数が`R15`レジスタの値を変更する場合、呼び出し元が期待する値を壊さないように、関数自身がその値をスタックに保存し、関数終了時に復元する責任があることを意味します。

このコミット以前は、`runtime·addmoduledata`が`R15`を暗黙的に使用して変更していたにもかかわらず、その値を保存・復元していませんでした。その結果、`.init_array`から呼び出された際に、呼び出し元の環境（リンカ/ローダや他の`.init_array`関数）が期待する`R15`の値が破壊され、未定義の動作やクラッシュを引き起こす可能性がありました。この修正は、このABI違反を解消し、Goランタイムの初期化がプラットフォームの規約に正しく従うようにすることを目的としています。

## 前提知識の解説

### 1. ABI (Application Binary Interface)
ABIは、オペレーティングシステムとプログラム、またはプログラムの異なる部分（例えば、関数呼び出し）がどのように相互作用するかを定義する一連の規約です。これには、レジスタの使用方法、スタックフレームのレイアウト、引数の渡し方、戻り値の受け取り方などが含まれます。
*   **プラットフォームABI**: OSやハードウェアによって定められた標準的なABI。例えば、Linux上の`amd64`ではSystem V ABIが広く使われます。
*   **Go ABI**: Go言語のコンパイラとランタイムが内部的に使用する独自のABI。パフォーマンス最適化のためにプラットフォームABIとは異なる場合があります。

### 2. `.init_array`セクション
ELF（Executable and Linkable Format）バイナリ（LinuxなどのUnix系システムで実行ファイルや共有ライブラリの形式）には、`.init_array`というセクションがあります。このセクションには、プログラムの`main`関数が実行される前に、リンカ/ローダによって自動的に呼び出される関数のポインタのリストが含まれています。これは、C++のグローバルオブジェクトのコンストラクタや、特定のライブラリの初期化ルーチンを実行するために使用されます。

### 3. `amd64`アーキテクチャのレジスタと呼び出し規約
`amd64`（x86-64）アーキテクチャには、汎用レジスタが多数あります。これらのレジスタは、ABIによって「呼び出し元保存（caller-save）」と「呼び出し先保存（callee-save）」に分類されます。
*   **呼び出し元保存レジスタ (Caller-save registers)**: `RAX`, `RCX`, `RDX`, `RSI`, `RDI`, `R8`-`R11`など。これらのレジスタは、関数が呼び出される際に、呼び出し元がその値を保存する責任があります。呼び出された関数は、これらのレジスタを自由に変更できます。
*   **呼び出し先保存レジスタ (Callee-save registers)**: `RBX`, `RBP`, `R12`-`R15`など。これらのレジスタは、関数が呼び出される際に、呼び出し元がその値を保存する必要はありません。呼び出された関数がこれらのレジスタの値を変更する場合、関数自身がエントリ時にスタックに保存し、リターン前に復元する責任があります。`R15`は特に、Goランタイムでグローバルポインタ（GP）として使用されることがあり、その役割が重要です。

### 4. Goのアセンブラとグローバル変数アクセス
Goのアセンブラ（`cmd/asm`）は、Goのソースコードから生成されるアセンブリコードを処理します。`amd64`環境では、Goのグローバル変数へのアクセスは、通常、`R15`レジスタをベースとしたオフセットアドレス指定に変換されることがあります。これは、位置独立コード（PIC）の生成や、特定の最適化のために行われます。

## 技術的詳細

`runtime·addmoduledata`関数は、Goのモジュールデータ構造（`moduledata`）をランタイムに登録する役割を担っています。この構造体には、Goプログラムの実行に必要な型情報、関数ポインタ、シンボルテーブルなどが含まれています。Goプログラムが起動する際、これらのモジュールデータはランタイムによって認識され、利用可能になる必要があります。

CGOを使用して共有ライブラリをビルドする場合、Goランタイムの初期化の一部として`runtime·addmoduledata`が実行されます。この実行は、OSのリンカ/ローダによって`.init_array`セクションを通じてトリガーされます。このコンテキストでは、`runtime·addmoduledata`はGoの内部的な呼び出し規約ではなく、システム標準のプラットフォームABIに従う必要があります。

問題の核心は、`runtime·addmoduledata`内で`runtime·lastmoduledatap(SB)`のようなグローバル変数にアクセスする際に、Goのアセンブラが`R15`レジスタを暗黙的に使用していた点です。`amd64`のSystem V ABIでは、`R15`は呼び出し先保存レジスタです。つまり、`runtime·addmoduledata`が`R15`の値を変更するならば、その関数はエントリ時に`R15`の元の値をスタックに`PUSH`し、リターン前に`POP`して復元しなければなりません。

このコミット以前は、この保存・復元が行われていなかったため、`runtime·addmoduledata`が`R15`を破壊し、`.init_array`の呼び出し元（リンカ/ローダや他の初期化関数）が期待する`R15`の値が失われる可能性がありました。これは、特に共有ライブラリとしてGoプログラムがロードされるような複雑なシナリオで、予測不能なクラッシュや誤動作の原因となります。

修正は、`runtime·addmoduledata`関数のエントリで`R15`をスタックに保存し、リターン直前でスタックから復元するという、ABIに準拠した標準的な手続きを追加することで、この問題を解決しています。これにより、`runtime·addmoduledata`が`R15`を内部的に使用しても、呼び出し元のコンテキストに影響を与えることなく、安全に実行できるようになります。

## コアとなるコードの解説

`src/runtime/asm_amd64.s`における`runtime·addmoduledata`関数の変更は、`amd64`プラットフォームABIへの準拠を保証するためのものです。

```asm
TEXT runtime·addmoduledata(SB),NOSPLIT,$0-0
	PUSHQ	R15 // The access to global variables below implicitly uses R15, which is callee-save
	MOVQ	runtime·lastmoduledatap(SB), AX
	MOVQ	DI, moduledata_next(AX)
	MOVQ	DI, runtime·lastmoduledatap(SB)
	POPQ	R15
	RET
```

1.  **`TEXT runtime·addmoduledata(SB),NOSPLIT,$0-0`**:
    *   `TEXT`: 関数定義の開始。
    *   `runtime·addmoduledata(SB)`: `runtime`パッケージ内の`addmoduledata`関数を定義。`SB`はStatic Baseで、グローバルシンボルを参照するためのベースアドレスです。
    *   `NOSPLIT`: この関数がスタックを分割しないことを示します。これは、非常に短い関数や、スタックの成長をチェックする必要がない場合に用いられます。
    *   `$0-0`: スタックフレームサイズが0バイトであることを示します。これは、この関数がローカル変数や追加のスタック領域を直接割り当てないことを意味します。ただし、`PUSHQ R15`によってスタックは8バイト消費されます。

2.  **`PUSHQ R15`**:
    *   この命令は、`R15`レジスタの現在の値をスタックにプッシュ（保存）します。これは、`R15`が呼び出し先保存レジスタであるため、関数がその値を変更する前に元の値を保存するというABIの要件を満たすためです。コメントにもあるように、この関数内のグローバル変数へのアクセスが暗黙的に`R15`を使用するため、この保存が必要です。

3.  **`MOVQ runtime·lastmoduledatap(SB), AX`**:
    *   `runtime·lastmoduledatap`というグローバル変数のアドレス（またはその内容）を`AX`レジスタに移動します。このグローバル変数は、Goランタイムが最後に登録されたモジュールデータを追跡するために使用されます。

4.  **`MOVQ DI, moduledata_next(AX)`**:
    *   `DI`レジスタの内容を、`AX`レジスタが指すアドレスから`moduledata_next`オフセットの位置に移動します。`DI`レジスタは、プラットフォームABIにおいて第一引数を渡すために使用されるレジスタです。したがって、`DI`には新しいモジュールデータへのポインタが格納されていると推測されます。この命令は、既存のモジュールデータのリストに新しいモジュールデータをリンクする操作の一部です。

5.  **`MOVQ DI, runtime·lastmoduledatap(SB)`**:
    *   `DI`レジスタの内容（新しいモジュールデータへのポインタ）を、`runtime·lastmoduledatap`グローバル変数に移動します。これにより、`runtime·lastmoduledatap`が最新のモジュールデータを指すように更新されます。

6.  **`POPQ R15`**:
    *   この命令は、スタックのトップから値をポップ（復元）して`R15`レジスタに格納します。これにより、関数エントリ時に保存された`R15`の元の値が復元され、呼び出し元のコンテキストが期待する`R15`の値が保持されます。

7.  **`RET`**:
    *   関数からリターンします。

この一連の変更により、`runtime·addmoduledata`関数は、`R15`レジスタを安全に使用し、プラットフォームABIに準拠した形で`.init_array`から呼び出されることが保証されます。

*   **Go ABI**: Go言語のコンパイラとランタイムが内部的に使用する独自のABI。パフォーマンス最適化のためにプラットフォームABIとは異なる場合があります。

### 2. `.init_array`セクション
ELF（Executable and Linkable Format）バイナリ（LinuxなどのUnix系システムで実行ファイルや共有ライブラリの形式）には、`.init_array`というセクションがあります。このセクションには、プログラムの`main`関数が実行される前に、リンカ/ローダによって自動的に呼び出される関数のポインタのリストが含まれています。これは、C++のグローバルオブジェクトのコンストラクタや、特定のライブラリの初期化ルーチンを実行するために使用されます。

### 3. `amd64`アーキテクチャのレジスタと呼び出し規約
`amd64`（x86-64）アーキテクチャには、汎用レジスタが多数あります。これらのレジスタは、ABIによって「呼び出し元保存（caller-save）」と「呼び出し先保存（callee-save）」に分類されます。
*   **呼び出し元保存レジスタ (Caller-save registers)**: `RAX`, `RCX`, `RDX`, `RSI`, `RDI`, `R8`-`R11`など。これらのレジスタは、関数が呼び出される際に、呼び出し元がその値を保存する責任があります。呼び出された関数は、これらのレジスタを自由に変更できます。
*   **呼び出し先保存レジスタ (Callee-save registers)**: `RBX`, `RBP`, `R12`-`R15`など。これらのレジスタは、関数が呼び出される際に、呼び出し元がその値を保存する必要はありません。呼び出された関数がこれらのレジスタの値を変更する場合、関数自身がエントリ時にスタックに保存し、リターン前に復元する責任があります。`R15`は特に、Goランタイムでグローバルポインタ（GP）として使用されることがあり、その役割が重要です。

### 4. Goのアセンブラとグローバル変数アクセス
Goのアセンブラ（`cmd/asm`）は、Goのソースコードから生成されるアセンブリコードを処理します。`amd64`環境では、Goのグローバル変数へのアクセスは、通常、`R15`レジスタをベースとしたオフセットアドレス指定に変換されることがあります。これは、位置独立コード（PIC）の生成や、特定の最適化のために行われます。

## 技術的詳細

`runtime·addmoduledata`関数は、Goのモジュールデータ構造（`moduledata`）をランタイムに登録する役割を担っています。この構造体には、Goプログラムの実行に必要な型情報、関数ポインタ、シンボルテーブルなどが含まれています。Goプログラムが起動する際、これらのモジュールデータはランタイムによって認識され、利用可能になる必要があります。

CGOを使用して共有ライブラリをビルドする場合、Goランタイムの初期化の一部として`runtime·addmoduledata`が実行されます。この実行は、OSのリンカ/ローダによって`.init_array`セクションを通じてトリガーされます。このコンテキストでは、`runtime·addmoduledata`はGoの内部的な呼び出し規約ではなく、システム標準のプラットフォームABIに従う必要があります。

問題の核心は、`runtime·addmoduledata`内で`runtime·lastmoduledatap(SB)`のようなグローバル変数にアクセスする際に、Goのアセンブラが`R15`レジスタを暗黙的に使用していた点です。`amd64`のSystem V ABIでは、`R15`は呼び出し先保存レジスタです。つまり、`runtime·addmoduledata`が`R15`の値を変更するならば、その関数はエントリ時に`R15`の元の値をスタックに`PUSH`し、リターン前に`POP`して復元しなければなりません。

このコミット以前は、この保存・復元が行われていなかったため、`runtime·addmoduledata`が`R15`を破壊し、`.init_array`の呼び出し元（リンカ/ローダや他の初期化関数）が期待する`R15`の値が失われる可能性がありました。これは、特に共有ライブラリとしてGoプログラムがロードされるような複雑なシナリオで、予測不能なクラッシュや誤動作の原因となります。

修正は、`runtime·addmoduledata`関数のエントリで`R15`をスタックに保存し、リターン直前でスタックから復元するという、ABIに準拠した標準的な手続きを追加することで、この問題を解決しています。これにより、`runtime·addmoduledata`が`R15`を内部的に使用しても、呼び出し元のコンテキストに影響を与えることなく、安全に実行できるようになります。

## コアとなるコードの解説

`src/runtime/asm_amd64.s`における`runtime·addmoduledata`関数の変更は、`amd64`プラットフォームABIへの準拠を保証するためのものです。

```asm
TEXT runtime·addmoduledata(SB),NOSPLIT,$0-0
	PUSHQ	R15 // The access to global variables below implicitly uses R15, which is callee-save
	MOVQ	runtime·lastmoduledatap(SB), AX
	MOVQ	DI, moduledata_next(AX)
	MOVQ	DI, runtime·lastmoduledatap(SB)
	POPQ	R15
	RET
```

1.  **`TEXT runtime·addmoduledata(SB),NOSPLIT,$0-0`**:
    *   `TEXT`: 関数定義の開始。
    *   `runtime·addmoduledata(SB)`: `runtime`パッケージ内の`addmoduledata`関数を定義。`SB`はStatic Baseで、グローバルシンボルを参照するためのベースアドレスです。
    *   `NOSPLIT`: この関数がスタックを分割しないことを示します。これは、非常に短い関数や、スタックの成長をチェックする必要がない場合に用いられます。
    *   `$0-0`: スタックフレームサイズが0バイトであることを示します。これは、この関数がローカル変数や追加のスタック領域を直接割り当てないことを意味します。ただし、`PUSHQ R15`によってスタックは8バイト消費されます。

2.  **`PUSHQ R15`**:
    *   この命令は、`R15`レジスタの現在の値をスタックにプッシュ（保存）します。これは、`R15`が呼び出し先保存レジスタであるため、関数がその値を変更する前に元の値を保存するというABIの要件を満たすためです。コメントにもあるように、この関数内のグローバル変数へのアクセスが暗黙的に`R15`を使用するため、この保存が必要です。

3.  **`MOVQ runtime·lastmoduledatap(SB), AX`**:
    *   `runtime·lastmoduledatap`というグローバル変数のアドレス（またはその内容）を`AX`レジスタに移動します。このグローバル変数は、Goランタイムが最後に登録されたモジュールデータを追跡するために使用されます。

4.  **`MOVQ DI, moduledata_next(AX)`**:
    *   `DI`レジスタの内容を、`AX`レジスタが指すアドレスから`moduledata_next`オフセットの位置に移動します。`DI`レジスタは、プラットフォームABIにおいて第一引数を渡すために使用されるレジスタです。したがって、`DI`には新しいモジュールデータへのポインタが格納されていると推測されます。この命令は、既存のモジュールデータのリストに新しいモジュールデータをリンクする操作の一部です。

5.  **`MOVQ DI, runtime·lastmoduledatap(SB)`**:
    *   `DI`レジスタの内容（新しいモジュールデータへのポインタ）を、`runtime·lastmoduledatap`グローバル変数に移動します。これにより、`runtime·lastmoduledatap`が最新のモジュールデータを指すように更新されます。

6.  **`POPQ R15`**:
    *   この命令は、スタックのトップから値をポップ（復元）して`R15`レジスタに格納します。これにより、関数エントリ時に保存された`R15`の元の値が復元され、呼び出し元のコンテキストが期待する`R15`の値が保持されます。

7.  **`RET`**:
    *   関数からリターンします。

この一連の変更により、`runtime·addmoduledata`関数は、`R15`レジスタを安全に使用し、プラットフォームABIに準拠した形で`.init_array`から呼び出されることが保証されます。

## 変更の背景

Go言語の各メジャーリリースでは、そのバージョンで導入された新機能、改善点、非互換な変更などをまとめたリリースノートが提供されます。`doc/go1.5.txt` は、Go 1.5のリリースノートの草稿または最終版の一部であり、ユーザーが新しいバージョンで何が変更されたかを理解するための重要なドキュメントです。

このコミットの背景には、以下の目的があります。

1.  **情報の追加**: Go 1.5で実装された新たなパフォーマンス改善（具体的には「concrete == interface without allocating」）をリリースノートに正確に反映させること。これにより、ユーザーはGo 1.5でどのような最適化が行われたかを把握できます。
2.  **情報の整理**: リリースノート内の「Performance」セクションにおいて、特に`cmd/gc`（Goコンパイラ）に関連するパフォーマンス改善項目が複数存在するため、それらを論理的かつ読みやすい順序にソートし直すこと。これにより、ドキュメントの可読性とメンテナンス性が向上します。

Go 1.5は、GoコンパイラとランタイムがC言語からGo言語自体で書き直された（セルフホスト化された）画期的なリリースであり、新しい並行ガベージコレクタの導入など、パフォーマンス面で多くの重要な変更が含まれていました。そのため、パフォーマンスに関するドキュメントの正確性と網羅性は特に重要でした。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラに関する基本的な知識が役立ちます。

*   **`doc/go1.5.txt`**: Go言語のリリースノートは、通常 `doc/goX.Y.txt` の形式で提供されます。これらは、そのバージョンで導入された主要な変更点、新機能、パフォーマンス改善、非互換性などをまとめた公式ドキュメントです。開発者やユーザーは、新しいバージョンに移行する際にこのドキュメントを参照します。
*   **`cmd/gc`**: これはGo言語の公式コンパイラを指します。Goプログラムをコンパイルし、実行可能なバイナリを生成する役割を担っています。`cmd/gc`における最適化は、Goプログラムの実行速度に直接影響を与えます。
*   **パフォーマンス最適化**: コンパイラやランタイムにおけるパフォーマンス最適化は、プログラムの実行速度を向上させるための様々な技術を指します。これには、メモリ割り当ての削減、CPUキャッシュの効率的な利用、命令のインライン化、特定のコードパターンの高速化などが含まれます。
*   **ガベージコレクション (GC)**: Go言語は自動メモリ管理（ガベージコレクション）を採用しています。GCは、プログラムが不要になったメモリを自動的に解放するプロセスです。GCの効率は、アプリケーションのレイテンシ（特に一時停止時間）に大きく影響します。Go 1.5では、並行GCが導入され、GCによる一時停止時間が大幅に削減されました。
*   **インターフェース (Interface)**: Go言語のインターフェースは、メソッドのシグネチャの集合を定義する型です。Goのインターフェースは、動的なディスパッチを可能にし、ポリモーフィズムを実現します。インターフェース型の変数に具体的な（concrete）型の値を代入すると、その値は内部的に「型情報」と「値データ」のペアとして表現されます。
*   **メモリ割り当て (Allocation)**: プログラムが実行時にメモリを要求する操作です。ヒープメモリの割り当ては、ガベージコレクタの負荷を増加させ、GCの一時停止時間を長くする可能性があります。そのため、パフォーマンス最適化では、不要なメモリ割り当てを削減することが重要視されます。
*   **インライン化 (Inlining)**: コンパイラ最適化の一種で、関数呼び出しの代わりに、呼び出される関数の本体を呼び出し元に直接埋め込むことです。これにより、関数呼び出しのオーバーヘッド（スタックフレームの作成、引数の渡し、戻り値の処理など）が削減され、プログラムの実行速度が向上します。また、インライン化によって、呼び出し元のコンテキストでさらに最適化（例えば、定数伝播など）が可能になる場合があります。
*   **型アサーション (`_, ok := i.(T)`)**: Go言語でインターフェース型の値 `i` が特定の具象型 `T` であるかどうかをチェックし、もしそうであればその具象型の値を取得するための構文です。`ok` はアサーションが成功したかどうかを示すブール値です。この操作は、内部的に型チェックと値の抽出を伴います。
*   **文字列スイッチ (String Switches)**: Go言語の `switch` ステートメントで、文字列型の値を条件として使用するものです。多数の `case` 句を持つ文字列スイッチは、コンパイラが効率的なコードを生成しない場合、パフォーマンスのボトルネックになる可能性があります。

## 技術的詳細

このコミットで言及されているパフォーマンス改善項目は、Go 1.5におけるコンパイラとランタイムの様々な最適化を反映しています。これらの最適化は、Goプログラムの実行効率を向上させ、特にメモリ使用量とCPUサイクルを削減することを目的としています。

以下に、`doc/go1.5.txt` の変更で言及されている主要なパフォーマンス項目とその技術的詳細を解説します。

1.  **`cmd/gc: evaluate concrete == interface without allocating` (https://golang.org/cl/2096)**
    *   **概要**: この最適化は、具象型（concrete type）の値とインターフェース型の値の等価性比較（`==`）を行う際に、不要なメモリ割り当てを削減することを目的としています。
    *   **詳細**: Go言語では、具象型の値をインターフェース型の変数に代入すると、その値は内部的に「型情報」と「値データ」のペアとして表現されます。通常、このペアはヒープに割り当てられることがあります。しかし、具象型の値とインターフェース型の値を比較する際、コンパイラは特定の条件下で、インターフェースの内部表現を一時的に作成する必要がありました。この最適化により、コンパイラは、比較対象の具象型がインターフェースに変換される際にヒープ割り当てを回避できるケースを識別し、スタック上に直接値を配置するなどして、メモリ割り当てをなくすことでパフォーマンスを向上させます。これにより、GCの負荷が軽減され、実行速度が向上します。

2.  **`cmd/gc: optimize memclr of slices and arrays` (https://golang.org/cl/2520)**
    *   **概要**: スライスや配列のメモリをゼロクリアする操作（`memclr`）の効率を改善する最適化です。
    *   **詳細**: Go言語では、新しいスライスや配列が作成されたり、既存のメモリ領域が再利用されたりする際に、その内容をゼロで初期化（クリア）する必要がある場合があります。この操作は、特に大きなデータ構造を扱う場合にCPU時間を消費します。この最適化は、コンパイラが特定の状況下で、より効率的な機械語命令（例えば、CPUのSIMD命令や、より高速なメモリ操作命令）を生成することで、`memclr`の実行速度を向上させます。これにより、データ構造の初期化やリセットが高速化されます。

3.  **`cmd/gc: transform closure calls to function calls` (https://golang.org/cl/4050)**
    *   **概要**: クロージャの呼び出しを、可能な場合に通常の関数呼び出しに変換する最適化です。
    *   **詳細**: クロージャは、それが定義された環境の変数を「キャプチャ」できる関数です。このキャプチャのメカニズムにより、クロージャの呼び出しは通常の関数呼び出しよりもオーバーヘッドが大きくなる傾向があります。この最適化は、コンパイラがクロージャが実際には外部変数をキャプチャしていない、あるいはキャプチャしている変数がコンパイル時に解決可能であるなど、特定の単純なケースを検出した場合に、そのクロージャ呼び出しをより効率的な通常の関数呼び出しに変換します。これにより、クロージャのオーバーヘッドが削減され、実行速度が向上します。

4.  **`cmd/gc: transitive inlining` (https://golang.org/cl/5952)**
    *   **概要**: 呼び出し元だけでなく、呼び出された関数がさらに別の関数を呼び出している場合に、その「呼び出された関数が呼び出す関数」もインライン化の対象とする、推移的なインライン化の導入です。
    *   **詳細**: 通常のインライン化は、関数Aが関数Bを呼び出す際に、関数Bのコードを関数Aの呼び出し箇所に直接埋め込むものです。推移的インライン化は、さらに一歩進んで、もし関数Bが関数Cを呼び出している場合、関数Cも関数Aのコンテキストにインライン化できるかどうかを検討します。これにより、複数の関数呼び出しのオーバーヘッドを一度に削減し、より大きなコードブロックに対してコンパイラが最適化を適用できる機会が増えます。結果として、プログラム全体の実行速度が向上します。

5.  **`cmd/gc, runtime: speed up some cases of _, ok := i.(T)` (https://golang.org/cl/7697)**
    *   **概要**: インターフェース型アサーション `_, ok := i.(T)` の特定のケースにおけるパフォーマンスを向上させる最適化です。
    *   **詳細**: インターフェース型アサーションは、実行時に型チェックと値の抽出を行うため、ある程度のコストがかかります。この最適化は、コンパイラとランタイムが協力して、特に頻繁に発生する、または単純な型アサーションのパターンを識別し、それらに対してより高速なコードパスを提供するものです。例えば、特定の具象型へのアサーションが成功することがコンパイル時に予測できる場合や、アサーションの対象となるインターフェース値が特定の構造を持つ場合に、特殊な命令や最適化されたランタイムヘルパー関数を使用することで、オーバーヘッドを削減し、実行速度を向上させます。

6.  **`cmd/gc: speed up large string switches` (https://golang.org/cl/7698)**
    *   **概要**: 多数の `case` 句を持つ文字列 `switch` ステートメントの実行速度を向上させる最適化です。
    *   **詳細**: 多数の `case` 句を持つ文字列 `switch` ステートメントは、コンパイラが単純に各 `case` を順に比較するコードを生成すると、入力文字列の長さに比例して比較回数が増え、非効率になる可能性があります。この最適化は、コンパイラがこのような `switch` ステートメントを、より効率的なルックアップメカニズムに変換することを目的としています。一般的な手法としては、ハッシュテーブル（マップ）への変換や、パーフェクトハッシュ関数の利用、トライ木（Trie）やラディックス木（Radix Tree）のようなデータ構造を用いたルックアップなどが考えられます。これにより、文字列比較の回数を大幅に削減し、特に大きな文字列スイッチの実行速度を劇的に向上させます。

7.  **`cmd/gc: inline x := y.(*T) and x, ok := y.(*T)` (https://golang.org/cl/7862)**
    *   **概要**: インターフェース型アサーション `x := y.(*T)` および `x, ok := y.(*T)` の操作をインライン化する最適化です。
    *   **詳細**: 上記の `_, ok := i.(T)` の最適化と関連していますが、こちらは型アサーション操作自体をインライン化することに焦点を当てています。インライン化により、型アサーションを行うための関数呼び出しのオーバーヘッドが削減されます。コンパイラは、これらのアサーションが頻繁に実行されるホットパスにある場合や、アサーションの対象となる型情報がコンパイル時に利用可能な場合に、アサーションのロジックを直接呼び出し元に埋め込むことで、実行時のパフォーマンスを向上させます。

8.  **`cmd/gc: allocate backing storage for non-escaping interfaces on stack` (https://golang.org/cl/8201)**
    *   **概要**: エスケープしないインターフェース値のバッキングストレージをヒープではなくスタックに割り当てる最適化です。
    *   **詳細**: Go言語では、変数がそのスコープを「エスケープ」するかどうかをコンパイラが分析します。通常、インターフェース値はヒープに割り当てられることが多いですが、もしインターフェース値がその関数スコープの外に「エスケープ」しない（つまり、関数が終了するまでにその寿命が尽きる）とコンパイラが判断した場合、この最適化により、そのインターフェース値の内部的な「値データ」部分（バッキングストレージ）をヒープではなくスタックに割り当てることが可能になります。スタック割り当てはヒープ割り当てよりもはるかに高速であり、ガベージコレクタの負荷を軽減するため、アプリケーションのパフォーマンスが向上します。

これらの最適化は、Go 1.5がより高速で効率的な言語となるための基盤を築きました。

## コアとなるコードの解説

このコミットの「コアとなるコード」は、Go言語のリリースノートファイル `doc/go1.5.txt` の「Performance」セクションにおけるテキストの追加と並べ替えです。

具体的には、以下の変更が行われています。

1.  **新規項目の追加**:
    *   `cmd/gc: evaluate concrete == interface without allocating (https://golang.org/cl/2096)` という新しいパフォーマンス改善項目が追加されました。これは、Go 1.5で導入されたインターフェース比較に関する重要な最適化を反映しています。

2.  **既存項目の並べ替え**:
    *   `cmd/gc` または `cmd/internal/gc` で始まる既存のパフォーマンス改善項目が、より論理的な順序に並べ替えられました。元のリストでは、`evaluate concrete == interface without allocating` がリストの途中にありましたが、新しい変更では、この項目が `cmd/gc` 関連の他の項目と共にリストの先頭近くに移動し、全体としてより整理された形になっています。
    *   特に、`cmd/internal/gc` というプレフィックスが `cmd/gc` に統一されている箇所もありますが、これはおそらくドキュメント内での表記揺れを修正し、一貫性を持たせるためのものです。

この変更の目的は、Go 1.5のリリースノートの「Performance」セクションを、より正確で、網羅的で、読みやすいものにすることです。新しい最適化が追加されたことで、ユーザーはGo 1.5がもたらすパフォーマンス上の利点をより完全に理解できるようになります。また、関連する項目をグループ化し、ソートすることで、情報の検索性が向上し、ドキュメント全体の品質が高まります。

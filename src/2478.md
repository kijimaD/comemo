# [インデックス 2478] ファイルの概要

このコミットは、Goコンパイラの字句解析器（lexer）における文字列リテラル、特にバッククォート（`）で囲まれた生文字列リテラル（raw string literal）の処理に関する診断メッセージの改善と、その前提となる言語仕様の解釈を明確にするものです。具体的には、文字列リテラル内で予期せぬEOF（End Of File）が発生した場合のエラー診断をより詳細にし、生文字列リテラル内での改行の扱いを明確にしています。

## 変更の背景

このコミットが行われた2009年6月は、Go言語がまだ一般に公開される前の開発初期段階にあたります。Go言語のコンパイラ（`gc`）は、コードの字句解析（lexical analysis）を行う際に、文字列リテラルの終端が適切に閉じられているかを検証します。特に、バッククォートで囲まれた生文字列リテラルは、エスケープシーケンスを解釈せず、改行文字を含むことができるという特性があります。

しかし、コンパイラが文字列リテラルの途中でファイルの終端（EOF）に達した場合、以前の実装では一般的な「eof in string」のようなエラーメッセージしか表示されず、問題の特定が困難でした。このコミットの背景には、このような状況でより具体的な診断情報を提供し、開発者がコードの問題を迅速に特定できるようにするという目的があります。

また、「this assumes that embedded newlines are legal in back-quote strings.」という記述から、当時のGo言語の仕様策定過程において、生文字列リテラル内での改行の扱いが明確化されつつあったことが伺えます。このコミットは、その仕様をコンパイラの動作に反映させる一環として、診断メッセージの改善と合わせて実装されたと考えられます。

## 前提知識の解説

### Go言語の文字列リテラル

Go言語には主に2種類の文字列リテラルがあります。

1.  **解釈済み文字列リテラル (Interpreted String Literals)**: ダブルクォート（`"`）で囲まれた文字列です。バックスラッシュ（`\`）で始まるエスケープシーケンス（例: `\n`、`\t`、`\"`）が解釈されます。改行文字を直接含めることはできません（`\n`として記述する必要があります）。
2.  **生文字列リテラル (Raw String Literals)**: バッククォート（` ` `）で囲まれた文字列です。エスケープシーケンスは解釈されず、記述された文字がそのまま文字列の内容となります。このため、改行文字を直接含めることができ、複数行にわたる文字列を記述するのに便利です。

### 字句解析 (Lexical Analysis)

コンパイラは、ソースコードを処理する最初の段階で字句解析を行います。これは、ソースコードのテキストストリームを読み込み、意味のある最小単位である「トークン」（識別子、キーワード、演算子、リテラルなど）のシーケンスに変換するプロセスです。このコミットが修正している`src/cmd/gc/lex.c`は、Goコンパイラの字句解析器の一部であり、文字列リテラルをトークンとして認識する役割を担っています。

### EOF (End Of File)

EOFは、ファイルや入力ストリームの終端を示すマーカーです。プログラムがファイルを読み込んでいる際にEOFに達すると、それ以上データがないことを意味します。コンパイラが文字列リテラルを解析している途中でEOFに遭遇した場合、それは文字列リテラルが適切に閉じられていない（例: 閉じバッククォートや閉じダブルクォートがない）ことを示します。

## 技術的詳細

このコミットは、`src/cmd/gc/lex.c`ファイル内の`_yylex`関数、特にバッククォート文字列（`casebq`ラベル）と一般的な文字列（`loop`ラベル）の処理ロジックを変更しています。

### 1. バッククォート文字列におけるEOF診断の改善

変更前は、バッククォート文字列の解析中にEOFまたは閉じバッククォート（` ` `）に遭遇した場合、単にループを抜けていました。EOFの場合、これは適切なエラーメッセージを生成しない可能性がありました。

変更後、`casebq`セクションに`lno = lineno;`が追加され、文字列の開始行番号が記録されるようになりました。そして、`c == EOF`の場合に`yyerror("eof in string starting at line %L", lno);`という、より詳細なエラーメッセージを出力するようになりました。このメッセージは、文字列がどの行で開始されたかを示すため、デバッグが容易になります。

### 2. 一般的な文字列におけるEOFおよび改行の診断

`escchar`関数内の`loop`セクションは、おそらくダブルクォート文字列やエスケープシーケンスの処理に関連しています。

変更前は、`c == '\n'`の場合に「newline in string」エラーを、`c == EOF`の場合に「eof in string」エラーを出力していました。

変更後、`switch`文が導入され、`EOF`と`\n`のケースが明示的に処理されるようになりました。
*   `case EOF:` の場合、`yyerror("eof in string");` を出力し、`return 1;` でエラーを返します。
*   `case '\n':` の場合、`yyerror("newline in string");` を出力し、`return 1;` でエラーを返します。

この変更は、コードの可読性を向上させるとともに、EOFと改行のエラー処理をより明確に分離しています。特に、バッククォート文字列では改行が許可される一方で、ダブルクォート文字列では改行が許可されないというGo言語の仕様を反映しています。

### 3. 変数の追加

`_yylex`関数に`int32 lno;`という変数が追加されました。これは、バッククォート文字列の開始行番号を記録するために使用されます。

## コアとなるコードの解説

### `_yylex` 関数内の変更

1.  **`int32 lno;` の追加**:
    `_yylex`関数のローカル変数として`lno`が追加されました。これは、バッククォート文字列の開始行番号を保持するために使用されます。

2.  **`casebq` ラベル内の変更**:
    *   `lno = lineno;`: バッククォート文字列の解析が始まる直前に、現在の行番号（`lineno`）を`lno`に保存します。
    *   `if(c == EOF)` ブロックの追加: `getc()`で読み込んだ文字`c`が`EOF`であるかを最初にチェックします。もし`EOF`であれば、`yyerror("eof in string starting at line %L", lno);`を呼び出して、文字列が開始された行番号を含む詳細なエラーメッセージを出力します。その後、`break;`で無限ループを抜けます。
    *   `if(c == '`')` の条件が独立: 以前は`EOF`と`'`が同じ`if`文で処理されていましたが、`EOF`の処理が分離されたことで、`'`は文字列の正常な終端として扱われることが明確になりました。

### `escchar` 関数内の変更

`escchar`関数は、おそらくエスケープシーケンスの処理や、ダブルクォート文字列のような特定の終端文字を持つ文字列の解析に使用されるヘルパー関数です。

1.  **`switch(c)` 文の導入**:
    以前の`if-else if`構造が`switch`文に置き換えられました。これにより、`EOF`、`\n`、`\`（エスケープ文字）、およびその他の文字の処理がより構造化され、明確になりました。

2.  **`case EOF:` の追加**:
    `getr()`（おそらく`getc()`と同様に文字を読み込む関数）が`EOF`を返した場合、`yyerror("eof in string");`を出力し、`return 1;`でエラーを示します。これは、文字列が予期せず終了したことを示します。

3.  **`case '\n':` の処理**:
    `getr()`が改行文字`\n`を返した場合、`yyerror("newline in string");`を出力し、`return 1;`でエラーを示します。これは、ダブルクォート文字列内で改行が許可されないというGo言語の仕様を反映しています。

4.  **`case '\\':` の追加**:
    バックスラッシュ`\`はエスケープシーケンスの開始を示すため、この場合は`break;`で`switch`文を抜け、後続のロジックでエスケープシーケンスが処理されることを示唆しています。

5.  **`default:` の追加**:
    上記以外の文字の場合、`if(c == e)`で終端文字`e`（おそらく閉じダブルクォートなど）と比較し、一致すれば正常終了、そうでなければ文字を`*val`に格納して処理を続行します。

これらの変更により、Goコンパイラは文字列リテラルにおける構文エラー、特にEOFや不正な改行の検出と報告をより正確かつ詳細に行えるようになりました。これは、開発者にとってコードのデバッグ効率を向上させる重要な改善です。

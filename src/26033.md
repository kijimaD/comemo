# [インデックス 26033] ファイルの概要

このコミットは、Go言語の標準ライブラリ `path/filepath` パッケージにおける `EvalSymlinks` 関数の挙動を修正するものです。具体的には、`EvalSymlinks` がシンボリックリンクを評価した結果がさらにシンボリックリンクであった場合に、その評価を継続するように変更されています。これにより、シンボリックリンクの連鎖が正しく解決され、予期せぬパス解決の失敗を防ぎます。Windows環境における特定のケースでの挙動も改善されています。

## 変更の背景

この変更は、GoのIssue #13582 を修正するために行われました。`filepath.EvalSymlinks` 関数は、与えられたパスに含まれるシンボリックリンクを再帰的に評価し、最終的な物理パスを返すことを目的としています。しかし、以前の実装では、`EvalSymlinks` がシンボリックリンクを一度評価して得られたパスが、さらに別のシンボリックリンクであった場合に、その後の評価が停止してしまうという問題がありました。

例えば、`A -> B` (AがBへのシンボリックリンク) かつ `B -> C` (BがCへのシンボリックリンク) という状況で `EvalSymlinks("A")` を呼び出した場合、期待される結果は `C` ですが、以前の実装では `B` が返されてしまう可能性がありました。これは、シンボリックリンクの連鎖を完全に解決できないことを意味し、ファイルシステム操作において予期せぬエラーや誤ったパス解決を引き起こす可能性がありました。

このコミットは、この問題を解決し、`EvalSymlinks` がシンボリックリンクの連鎖を完全に解決して、最終的な非シンボリックリンクのパスを返すようにするために導入されました。

## 前提知識の解説

### シンボリックリンク (Symbolic Link / Symlink)
シンボリックリンクは、ファイルシステム上の別のファイルやディレクトリへの参照（ポインタ）として機能する特殊なファイルです。Windowsでは「ショートカット」に似ていますが、OSのより低レベルで機能し、多くのシステムコールで透過的に扱われます。Unix系OSでは非常に一般的です。

- **ハードリンクとの違い**: ハードリンクは同じiノード（ファイルの実体）を指す複数のエントリですが、シンボリックリンクは別のiノードを指すファイルです。シンボリックリンクは、参照先のファイルが削除されても残りますが、その場合は「壊れたリンク」となります。
- **用途**:
    - ソフトウェアのバージョン管理（例: `/usr/local/bin/python` が `/usr/local/bin/python3.9` を指す）
    - 異なるディレクトリにあるファイルをあたかも同じディレクトリにあるかのように見せる
    - 開発環境での設定ファイルの共有

### `path/filepath` パッケージ
Go言語の標準ライブラリ `path/filepath` は、ファイルパスを操作するためのユーティリティを提供します。OS固有のパス区切り文字（Unixでは`/`、Windowsでは`\`）を抽象化し、クロスプラットフォームで動作するパス操作を可能にします。

- **主な機能**:
    - `Join`: パス要素を結合
    - `Clean`: パスを正規化（例: `a/./b` を `a/b` に、`a/../b` を `b` に）
    - `Abs`: 絶対パスに変換
    - `EvalSymlinks`: シンボリックリンクを評価し、最終的な物理パスを返す

### `filepath.EvalSymlinks` の役割
`filepath.EvalSymlinks` は、与えられたパスに含まれるシンボリックリンクを解決し、そのパスが指す最終的な物理パス（シンボリックリンクではないパス）を返します。これは、実際のファイルやディレクトリの場所を特定する必要がある場合に重要です。例えば、設定ファイルを読み込む際に、シンボリックリンクを介して参照されている場合に、その実体を見つけるために使用されます。

### Windowsにおけるシンボリックリンク
Windowsでは、NTFSファイルシステムがシンボリックリンク（ジャンクションポイント、ディレクトリシンボリックリンク、ファイルシンボリックリンクなど）をサポートしています。Unix系OSとは挙動が異なる場合があり、特にパスの正規化や相対パスの扱いにおいて注意が必要です。このコミットでも、Windows特有の挙動に対する考慮が見られます。

## 技術的詳細

このコミットの核心は、`src/path/filepath/symlink.go` 内の `walkSymlinks` 関数におけるシンボリックリンク評価のループ処理の導入です。

以前の `walkSymlinks` 関数は、`walkLinks` を一度呼び出してシンボリックリンクを評価し、その結果をそのまま返していました。しかし、`walkLinks` が返したパスがまだシンボリックリンクである場合、そのリンクは解決されずに残ってしまいました。

新しい実装では、`walkSymlinks` 関数内に `for` ループが導入されています。このループは、`walkLinks` 関数がシンボリックリンクを評価して新しいパスを返すたびに、その新しいパスを次のイテレーションの入力として使用し、再度 `walkLinks` を呼び出します。この処理は、`walkLinks` がこれ以上シンボリックリンクを解決しなくなった（つまり、`linksWalked` カウンタが増加しなくなった）場合に終了します。これにより、シンボリックリンクの連鎖が完全に解決されることが保証されます。

また、Windows環境における特定のケース（カレントディレクトリがシンボリックリンクであり、`EvalSymlinks(".")` が呼び出された場合）についても修正が加えられています。Unix系OSでは `.` は常に `.` に解決されますが、Windowsではシンボリックリンクのターゲットが返されることがありました。この修正により、WindowsでもUnix系OSと同様に `.` が `.` に解決されるように調整されています。

    - `linksWalked` カウンタを使用して、ループが無限に続くことを防ぎ、シンボリックリンクの連鎖が完全に解決されたかどうかを判断します。

- `evalSymlinks` 関数から、`path != "." || IsAbs(newpath)` という条件に基づくパスの調整ロジックが削除されました。このロジックは、`symlink.go` の `walkSymlinks` 関数内の新しいループとWindows固有の処理に統合されたため、冗長になりました。

## コアとなるコードの解説

### `src/path/filepath/symlink.go` の `walkSymlinks` 関数

```go
func walkSymlinks(path string) (string, error) {
	if !supportsSymlinks {
		return path, nil
	}
	var linksWalked int // to protect against cycles
	for { // 無限ループを開始
		i := linksWalked // 現在のリンク評価回数を保存
		newpath, err := walkLinks(path, &linksWalked) // シンボリックリンクを評価
		if err != nil {
			return "", err
		}
		if runtime.GOOS == "windows" {
			// walkLinks(".", ...) always retuns "." on unix.
			// But on windows it returns symlink target, if current
			// directory is a symlink. Stop the walk, if symlink
			// target is not absolute path, and return "."
			// to the caller (just like unix does).
			if path == "." && !IsAbs(newpath) {
				return ".", nil
			}
		}
		if i == linksWalked { // リンク評価回数が増加しなかった場合、これ以上解決するものはない
			return Clean(newpath), nil // パスを正規化して返す
		}
		path = newpath // 新しいパスを次のイテレーションの入力とする
	}
}
```

- **`for` ループ**: このループがシンボリックリンクの連鎖を解決するための核心です。`walkLinks` が新しいシンボリックリンクを解決するたびに `linksWalked` が増加します。`linksWalked` が増加しなくなった場合（つまり、`walkLinks` がこれ以上シンボリックリンクを解決しなかった場合）、ループは終了し、最終的な物理パスが返されます。
- **`linksWalked` カウンタ**: シンボリックリンクの無限ループ（例: `A -> B -> A`）を防ぐためのメカニズムでもあります。`walkLinks` は内部でこのカウンタをインクリメントし、一定回数を超えるとエラーを返すことで無限ループを検出します。
- **Windows固有の処理**: `runtime.GOOS == "windows"` のブロックは、Windows環境での `EvalSymlinks(".")` の挙動をUnix系OSと一致させるためのものです。カレントディレクトリがシンボリックリンクであっても、`EvalSymlinks(".")` は `.` を返すようにします。
- **`Clean(newpath)`**: 最終的なパスを返す前に `filepath.Clean` を呼び出すことで、パスを正規化し、冗長な要素（例: `.` や `..`）を取り除きます。

### `src/path/filepath/path_test.go` の `TestIssue13582` 関数

このテストは、以下のようなシンボリックリンクの構造を一時ディレクトリ内に作成します。

```
/tmp/issue13582/
├── dir/
│   └── file
├── link_to_dir -> dir/
└── link1 -> link_to_dir/file
└── link2 -> link_to_dir/link1
```

そして、`filepath.EvalSymlinks` をこれらのパスに対して呼び出し、期待される最終的な物理パス（`realDir` や `realFile`）と比較します。特に `link2` のテストケースは、`link2` が `link1` を指し、`link1` が `file` を指すという二重のシンボリックリンクの連鎖を正しく解決できるかを検証しています。このテストの追加により、修正が正しく機能していることが保証されます。

# [インデックス 26275] ファイルの概要

このコミットは、Goランタイムにおけるプロファイリング（`sigprof`）時のスタックバリアロックの挙動に関するバグ修正です。特に、`sigprof`がユーザーのスタックをウォークする際に、スタックバリアロックが適切に取得されないケースがあった問題を解決しています。これにより、プロファイリングの正確性とランタイムの安定性が向上します。

## 変更の背景

このコミットは、Goランタイムのプロファイリング機能、特に`sigprof`シグナルハンドラがスタックトレースを収集する際のバグを修正するために導入されました。以前のコミット`f90b48e`では、ユーザーのスタックをウォークするすべての`sigprof`ケースでスタックバリアロックを要求する意図がありましたが、その実装には誤りがありました。

具体的には、以下の問題がありました。

1.  **不適切なロック取得条件**: `sp < gp.stack.lo || gp.stack.hi < sp`という条件が真の場合（つまり、スタックポインタ`sp`が現在のGoroutine `gp`のスタック範囲外にある場合）、`tracebackUser`は`true`と評価されるにもかかわらず、スタックロックが取得されませんでした。この状態でCgo呼び出し中にスタックウォークが発生すると、ロックなしでスタックがウォークされる可能性がありました。
2.  **`G`の不一致**: `sigprof`におけるスタックロックの全体的な構造が、ロック対象の`G`（Goroutine）を常に`gp.m.curg`（現在のM（OSスレッド）で実行中のGoroutine）と仮定している点で不適切でした。しかし、`gentraceback`関数は、Cgo呼び出しのスタック、通常のGoスタック、およびWindowsのlibcallスタックの3つの異なるコンテキストで呼び出される可能性があり、それぞれ異なる`G`を起点とする場合があります。この不一致が、ロックの不備につながっていました。

これらの問題により、プロファイリング中に不正確なスタックトレースが生成されたり、ランタイムのクラッシュやデッドロックが発生したりする可能性がありました。このコミットは、これらの問題を解決し、`sigprof`の堅牢性を高めることを目的としています。

また、この変更は、`runtime: increase assumed stack size in externalthreadhandler`という別のコミットに依存しています。これは、`sigprof`が使用するスタックサイズがわずかに増加するため、プロファイラースレッドの想定スタックサイズを増やす必要があるためです。ただし、Go 1.5ブランチでは`pcvalue cache`がないため、この依存関係は不要であると述べられています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **Goroutine (G)**: Goの軽量スレッドです。Goプログラムの並行処理の基本単位となります。各Goroutineは独自のスタックを持ちます。
2.  **Machine (M)**: OSスレッドを表します。Goランタイムは、M上でGを実行します。
3.  **P (Processor)**: MとGを仲介する論理プロセッサです。GをMにディスパッチする役割を担います。
4.  **`sigprof`**: プロファイリングのためにOSから定期的に送信されるシグナル（`SIGPROF`）を処理するGoランタイムのハンドラです。このシグナルを受信すると、ランタイムは現在の実行中のGoroutineのスタックトレースを収集し、プロファイリングデータとして記録します。
5.  **スタックバリア (Stack Barrier)**: Goのガベージコレクタ（GC）がスタックをスキャンする際に、スタックの拡張や縮小といった変更と競合しないようにするためのメカニズムです。スタックバリアは、GCがスタックを安全にスキャンできるように、スタックへのアクセスを一時的にブロックまたは調整します。
6.  **スタックバリアロック (`gcTryLockStackBarriers`, `gcUnlockStackBarriers`)**: スタックバリアの操作を保護するためのロック機構です。`gcTryLockStackBarriers`はロックの取得を試み、`gcUnlockStackBarriers`はロックを解放します。これにより、GCと他のランタイム操作（例: `sigprof`によるスタックウォーク）がスタックに同時にアクセスする際のデータ競合を防ぎます。
7.  **`gentraceback`**: Goランタイム内部でスタックトレースを生成するための関数です。指定されたGoroutineのスタックフレームをウォークし、呼び出し履歴を収集します。
8.  **Cgo**: GoプログラムからC言語のコードを呼び出すためのメカニズムです。Cgo呼び出し中は、GoランタイムのスケジューラからOSスレッドが切り離され、Cコードが実行されます。この際、GoのスタックとCのスタックが混在する可能性があり、スタックトレースの収集が複雑になります。
9.  **`gp.m.curg`**: 現在のM（OSスレッド）で実行中のGoroutineを指します。
10. **`gp.stack.lo`, `gp.stack.hi`**: Goroutine `gp`のスタックの下限と上限のアドレスを示します。

## 技術的詳細

このコミットの核心は、`sigprof`ハンドラ内でスタックバリアロックをより正確かつ安全に管理することにあります。

以前の実装では、`sigprof`がスタックトレースを収集する際に、ユーザーのスタックをウォークする必要があるかどうかを判断し、その場合に`gcTryLockStackBarriers(gp.m.curg)`を呼び出してロックを取得しようとしていました。しかし、このロジックには二つの主要な欠陥がありました。

1.  **`tracebackUser`の誤判定とロックの欠如**: `sp < gp.stack.lo || gp.stack.hi < sp`という条件は、スタックポインタが現在のGoroutineのスタック範囲外にあることを示唆しており、これは通常、システムスタックやCgoスタックにいることを意味します。このような状況でも`tracebackUser`が`true`になることがありましたが、その際にスタックロックが取得されないケースがありました。特にCgo呼び出し中にこの状態になると、ロックなしでスタックウォークが行われ、競合状態が発生する可能性がありました。
2.  **ロック対象`G`の不一致**: `sigprof`ハンドラは、Cgo呼び出しのスタック、通常のGoスタック、Windowsのlibcallスタックという、異なる3つのシナリオで`gentraceback`を呼び出します。以前のコードでは、これらのすべての場合で`gp.m.curg`をロック対象のGoroutineとしていましたが、`gentraceback`が実際にトレースを開始する`G`は、必ずしも`gp.m.curg`と一致するとは限りませんでした。例えば、Cgo呼び出しのスタックをトレースする場合、`mp.curg.syscallg`（Cgo呼び出しを行ったGoroutine）が対象となるべきです。

このコミットでは、これらの問題を解決するために、`gcTryLockStackBarriers`の呼び出し箇所を`gentraceback`の呼び出し箇所に近づけ、それぞれの`gentraceback`呼び出しに対して適切な`G`をロックするように変更しています。

具体的には、以下の3つの主要な`gentraceback`パスそれぞれで、個別にスタックバリアロックの取得と解放を行うように修正されました。

1.  **Cgo呼び出し中のスタックトレース**: `mp.ncgo > 0 && mp.curg != nil && mp.curg.syscallpc != 0 && mp.curg.syscallsp != 0`の条件でCgo呼び出し中と判断された場合、`mp.curg`に対して`gcTryLockStackBarriers`を呼び出し、成功した場合に`gentraceback`を実行します。
2.  **通常のGoスタックトレース**: `traceback`が`true`の場合、`gp.m.curg`に対して`gcTryLockStackBarriers`を呼び出し、成功した場合に`_TraceJumpStack`フラグを設定して`gentraceback`を実行します。
3.  **Windowsのlibcallスタックトレース**: Windows環境でlibcall（ランタイムシステムコール）中の場合、`mp.libcallg.ptr()`に対して`gcTryLockStackBarriers`を呼び出し、成功した場合に`gentraceback`を実行します。

これらの変更により、各スタックトレースのシナリオにおいて、実際にスタックウォークが行われるGoroutineに対して正確にスタックバリアロックが取得されるようになり、競合状態が回避されます。また、ロックの取得と解放が`gentraceback`の実行範囲に限定されることで、ロックの保持時間が最小限に抑えられ、ランタイムのパフォーマンスへの影響も軽減されます。

`haveStackLock`変数は、以前は`bool`型でしたが、このコミットで`*g`型に変更され、どのGoroutineのスタックロックが取得されたかを明確に追跡できるようになりました。これにより、`gcUnlockStackBarriers`が常に正しい`G`に対して呼び出されることが保証されます。

## コアとなるコードの解説

変更のポイントは以下の通りです。

1.  **`tracebackUser`変数の削除**: 以前は`tracebackUser`というブール変数でユーザーのスタックをトレース可能かどうかを判断していましたが、これが誤ったロジックを引き起こしていました。この変数は削除され、スタックロックの取得と`gentraceback`の呼び出しがより直接的に関連付けられるようになりました。
2.  **`haveStackLock`の型変更と役割の明確化**: `haveStackLock`は`bool`型から`*g`型（Goroutineへのポインタ）に変更されました。これにより、どのGoroutineのスタックロックが取得されたかを正確に記録し、`gcUnlockStackBarriers`が常に正しいGoroutineに対して呼び出されることが保証されます。
3.  **`gcTryLockStackBarriers`の呼び出し箇所の移動**:
    *   **Cgoパス**: `mp.ncgo > 0`で始まるCgo呼び出しのスタックトレースのブロック内で、`gentraceback`の直前に`gcTryLockStackBarriers(mp.curg)`が呼び出されるようになりました。ロックが成功した場合にのみ`gentraceback`が実行され、`haveStackLock`に`mp.curg`が設定されます。
    *   **通常のGoスタックパス**: `traceback`が`true`のブロック内で、`gp.m.curg != nil && gcTryLockStackBarriers(gp.m.curg)`という条件でロックを試みます。成功した場合、`haveStackLock`に`gp.m.curg`が設定され、`_TraceJumpStack`フラグが設定されて`gentraceback`が呼び出されます。
    *   **Windows libcallパス**: Windows環境でのlibcallスタックトレースのブロック内で、`gentraceback`の直前に`gcTryLockStackBarriers(mp.libcallg.ptr())`が呼び出され、成功した場合に`gentraceback`が実行され、直後に`gcUnlockStackBarriers`でロックが解放されます。
4.  **`gcUnlockStackBarriers`の集中管理**: 以前は`sigprof`関数の最後に`if haveStackLock { gcUnlockStackBarriers(gp.m.curg) }`という形で一括してロックを解放していましたが、新しいコードでは、Cgoパスと通常のGoスタックパスについては、`sigprof`関数の最後に`if haveStackLock != nil { gcUnlockStackBarriers(haveStackLock) }`という形で、`haveStackLock`に記録されたGoroutineに対してロックを解放します。Windows libcallパスでは、`gentraceback`の直後にロックを解放しています。これにより、ロックのスコープがより適切に管理されます。
5.  **`gentraceback`呼び出し条件の修正**: 通常のGoスタックパスにおいて、`gentraceback`が呼び出される条件が`if gp != gp.m.curg || haveStackLock != nil`に変更されました。これは、システムスタック上にいる場合（`gp != gp.m.curg`）や、ユーザーのスタックロックが取得できた場合（`haveStackLock != nil`）にのみトレースバックが安全であることを保証します。

これらの変更により、`sigprof`がスタックトレースを収集する際に、スタックバリアロックが常に適切なGoroutineに対して、適切なタイミングで取得・解放されるようになり、プロファイリングの正確性とランタイムの安定性が大幅に向上しました。

具体的には、以下の問題がありました。

1.  **不適切なロック取得条件**: `sp < gp.stack.lo || gp.stack.hi < sp`という条件が真の場合（つまり、スタックポインタ`sp`が現在のGoroutine `gp`のスタック範囲外にある場合）、`tracebackUser`は`true`と評価されるにもかかわらず、スタックロックが取得されませんでした。この状態でCgo呼び出し中にスタックウォークが発生すると、ロックなしでスタックがウォークされる可能性がありました。
2.  **`G`の不一致**: `sigprof`におけるスタックロックの全体的な構造が、ロック対象の`G`（Goroutine）を常に`gp.m.curg`（現在のM（OSスレッド）で実行中のGoroutine）と仮定している点で不適切でした。しかし、`gentraceback`関数は、Cgo呼び出しのスタック、通常のGoスタック、およびWindowsのlibcallスタックの3つの異なるコンテキストで呼び出される可能性があり、それぞれ異なる`G`を起点とする場合があります。この不一致が、ロックの不備につながっていました。

これらの問題により、プロファイリング中に不正確なスタックトレースが生成されたり、ランタイムのクラッシュやデッドロックが発生したりする可能性がありました。このコミットは、これらの問題を解決し、`sigprof`の堅牢性を高めることを目的としています。

また、この変更は、`runtime: increase assumed stack size in externalthreadhandler`という別のコミットに依存しています。これは、`sigprof`が使用するスタックサイズがわずかに増加するため、プロファイラースレッドの想定スタックサイズを増やす必要があるためです。ただし、Go 1.5ブランチでは`pcvalue cache`がないため、この依存関係は不要であると述べられています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **Goroutine (G)**: Goの軽量スレッドです。Goプログラムの並行処理の基本単位となります。各Goroutineは独自のスタックを持ちます。
2.  **Machine (M)**: OSスレッドを表します。Goランタイムは、M上でGを実行します。
3.  **P (Processor)**: MとGを仲介する論理プロセッサです。GをMにディスパッチする役割を担います。
4.  **`sigprof`**: プロファイリングのためにOSから定期的に送信されるシグナル（`SIGPROF`）を処理するGoランタイムのハンドラです。このシグナルを受信すると、ランタイムは現在の実行中のGoroutineのスタックトレースを収集し、プロファイリングデータとして記録します。
5.  **スタックバリア (Stack Barrier)**: Goのガベージコレクタ（GC）がスタックをスキャンする際に、スタックの拡張や縮小といった変更と競合しないようにするためのメカニズムです。スタックバリアは、GCがスタックを安全にスキャンできるように、スタックへのアクセスを一時的にブロックまたは調整します。
6.  **スタックバリアロック (`gcTryLockStackBarriers`, `gcUnlockStackBarriers`)**: スタックバリアの操作を保護するためのロック機構です。`gcTryLockStackBarriers`はロックの取得を試み、`gcUnlockStackBarriers`はロックを解放します。これにより、GCと他のランタイム操作（例: `sigprof`によるスタックウォーク）がスタックに同時にアクセスする際のデータ競合を防ぎます。
7.  **`gentraceback`**: Goランタイム内部でスタックトレースを生成するための関数です。指定されたGoroutineのスタックフレームをウォークし、呼び出し履歴を収集します。
8.  **Cgo**: GoプログラムからC言語のコードを呼び出すためのメカニズムです。Cgo呼び出し中は、GoランタイムのスケジューラからOSスレッドが切り離され、Cコードが実行されます。この際、GoのスタックとCのスタックが混在する可能性があり、スタックトレースの収集が複雑になります。
9.  **`gp.m.curg`**: 現在のM（OSスレッド）で実行中のGoroutineを指します。
10. **`gp.stack.lo`, `gp.stack.hi`**: Goroutine `gp`のスタックの下限と上限のアドレスを示します。

## 技術的詳細

このコミットの核心は、`sigprof`ハンドラ内でスタックバリアロックをより正確かつ安全に管理することにあります。

以前の実装では、`sigprof`がスタックトレースを収集する際に、ユーザーのスタックをウォークする必要があるかどうかを判断し、その場合に`gcTryLockStackBarriers(gp.m.curg)`を呼び出してロックを取得しようとしていました。しかし、このロジックには二つの主要な欠陥がありました。

1.  **`tracebackUser`の誤判定とロックの欠如**: `sp < gp.stack.lo || gp.stack.hi < sp`という条件は、スタックポインタが現在のGoroutineのスタック範囲外にあることを示唆しており、これは通常、システムスタックやCgoスタックにいることを意味します。このような状況でも`tracebackUser`が`true`になることがありましたが、その際にスタックロックが取得されないケースがありました。特にCgo呼び出し中にこの状態になると、ロックなしでスタックウォークが行われ、競合状態が発生する可能性がありました。
2.  **ロック対象`G`の不一致**: `sigprof`ハンドラは、Cgo呼び出しのスタック、通常のGoスタック、Windowsのlibcallスタックという、異なる3つのシナリオで`gentraceback`を呼び出します。以前のコードでは、これらのすべての場合で`gp.m.curg`をロック対象のGoroutineとしていましたが、`gentraceback`が実際にトレースを開始する`G`は、必ずしも`gp.m.curg`と一致するとは限りませんでした。例えば、Cgo呼び出しのスタックをトレースする場合、`mp.curg.syscallg`（Cgo呼び出しを行ったGoroutine）が対象となるべきです。

このコミットでは、これらの問題を解決するために、`gcTryLockStackBarriers`の呼び出し箇所を`gentraceback`の呼び出し箇所に近づけ、それぞれの`gentraceback`呼び出しに対して適切な`G`をロックするように変更しています。

具体的には、以下の3つの主要な`gentraceback`パスそれぞれで、個別にスタックバリアロックの取得と解放を行うように修正されました。

1.  **Cgo呼び出し中のスタックトレース**: `mp.ncgo > 0 && mp.curg != nil && mp.curg.syscallpc != 0 && mp.curg.syscallsp != 0`の条件でCgo呼び出し中と判断された場合、`mp.curg`に対して`gcTryLockStackBarriers`を呼び出し、成功した場合に`gentraceback`を実行します。
2.  **通常のGoスタックトレース**: `traceback`が`true`のブロック内で、`gp.m.curg != nil && gcTryLockStackBarriers(gp.m.curg)`という条件でロックを試みます。成功した場合、`haveStackLock`に`gp.m.curg`が設定され、`_TraceJumpStack`フラグが設定されて`gentraceback`が呼び出されます。
3.  **Windowsのlibcallスタックトレース**: Windows環境でlibcall（ランタイムシステムコール）中の場合、`mp.libcallg.ptr()`に対して`gcTryLockStackBarriers`を呼び出し、成功した場合に`gentraceback`を実行します。

これらの変更により、各スタックトレースのシナリオにおいて、実際にスタックウォークが行われるGoroutineに対して正確にスタックバリアロックが取得されるようになり、競合状態が回避されます。また、ロックの取得と解放が`gentraceback`の実行範囲に限定されることで、ロックの保持時間が最小限に抑えられ、ランタイムのパフォーマンスへの影響も軽減されます。

`haveStackLock`変数は、以前は`bool`型でしたが、このコミットで`*g`型に変更され、どのGoroutineのスタックロックが取得されたかを明確に追跡できるようになりました。これにより、`gcUnlockStackBarriers`が常に正しい`G`に対して呼び出されることが保証されます。

## コアとなるコードの解説

変更のポイントは以下の通りです。

1.  **`tracebackUser`変数の削除**: 以前は`tracebackUser`というブール変数でユーザーのスタックをトレース可能かどうかを判断していましたが、これが誤ったロジックを引き起こしていました。この変数は削除され、スタックロックの取得と`gentraceback`の呼び出しがより直接的に関連付けられるようになりました。
2.  **`haveStackLock`の型変更と役割の明確化**: `haveStackLock`は`bool`型から`*g`型（Goroutineへのポインタ）に変更されました。これにより、どのGoroutineのスタックロックが取得されたかを正確に記録し、`gcUnlockStackBarriers`が常に正しいGoroutineに対して呼び出されることが保証されます。
3.  **`gcTryLockStackBarriers`の呼び出し箇所の移動**:
    *   **Cgoパス**: `mp.ncgo > 0`で始まるCgo呼び出しのスタックトレースのブロック内で、`gentraceback`の直前に`gcTryLockStackBarriers(mp.curg)`が呼び出されるようになりました。ロックが成功した場合にのみ`gentraceback`が実行され、`haveStackLock`に`mp.curg`が設定されます。
    *   **通常のGoスタックパス**: `traceback`が`true`のブロック内で、`gp.m.curg != nil && gcTryLockStackBarriers(gp.m.curg)`という条件でロックを試みます。成功した場合、`haveStackLock`に`gp.m.curg`が設定され、`_TraceJumpStack`フラグが設定されて`gentraceback`が呼び出されます。
    *   **Windows libcallパス**: Windows環境でのlibcallスタックトレースのブロック内で、`gentraceback`の直前に`gcTryLockStackBarriers(mp.libcallg.ptr())`が呼び出され、成功した場合に`gentraceback`が実行され、直後に`gcUnlockStackBarriers`でロックが解放されます。
4.  **`gcUnlockStackBarriers`の集中管理**: 以前は`sigprof`関数の最後に`if haveStackLock { gcUnlockStackBarriers(gp.m.curg) }`という形で一括してロックを解放していましたが、新しいコードでは、Cgoパスと通常のGoスタックパスについては、`sigprof`関数の最後に`if haveStackLock != nil { gcUnlockStackBarriers(haveStackLock) }`という形で、`haveStackLock`に記録されたGoroutineに対してロックを解放します。Windows libcallパスでは、`gentraceback`の直後にロックを解放しています。これにより、ロックのスコープがより適切に管理されます。
5.  **`gentraceback`呼び出し条件の修正**: 通常のGoスタックパスにおいて、`gentraceback`が呼び出される条件が`if gp != gp.m.curg || haveStackLock != nil`に変更されました。これは、システムスタック上にいる場合（`gp != gp.m.curg`）や、ユーザーのスタックロックが取得できた場合（`haveStackLock != nil`）にのみトレースバックが安全であることを保証します。

これらの変更により、`sigprof`がスタックトレースを収集する際に、スタックバリアロックが常に適切なGoroutineに対して、適切なタイミングで取得・解放されるようになり、プロファイリングの正確性とランタイムの安定性が大幅に向上しました。

## 変更の背景

この変更は、Goコンパイラが定数名とラベル名が同じであるコードを誤って拒否していたバグ（Issue #13684）を修正するために行われました。Go言語の仕様では、ラベルは関数スコープ内で一意であればよく、他の識別子（変数、定数など）と同じ名前を持つことが許されています。しかし、Goコンパイラの内部処理において、ラベルとして認識されるべき識別子が、定数としてパースされた際に`OLITERAL`というノードタイプを持つことがあり、これが既存のパーサーロジックでラベルとして適切に扱われない問題がありました。

具体的には、`goto`文のターゲットとなるラベルを解析する際、パーサーは識別子を`ONAME`, `ONONAME`, `OTYPE`, `OPACK`のいずれかのノードタイプとして期待していました。しかし、もしその識別子が同時に定数として宣言されており、かつその定数がリテラル値を持つ場合、パーサーはそれを`OLITERAL`ノードとして解釈してしまうことがありました。この`OLITERAL`ノードは、ラベルとして有効なノードタイプとして認識されていなかったため、コンパイルエラーが発生していました。

このコミットは、Go言語の仕様に準拠し、より柔軟なコード記述を可能にするために、このパーサーの制限を取り除くことを目的としています。

## 前提知識の解説

### Goコンパイラ (`cmd/compile`)

`cmd/compile`は、Go言語のソースコードを機械語に変換する公式コンパイラです。コンパイルプロセスは複数のステージに分かれており、主要なものとして以下の段階があります。

1.  **字句解析 (Lexing)**: ソースコードをトークン（キーワード、識別子、演算子など）のストリームに変換します。
2.  **構文解析 (Parsing)**: トークンのストリームを解析し、抽象構文木（AST: Abstract Syntax Tree）を構築します。このASTは、プログラムの構造を階層的に表現したものです。
3.  **型チェック (Type Checking)**: ASTを走査し、型の整合性を検証します。
4.  **中間表現 (IR: Intermediate Representation) 生成**: ASTをコンパイラ内部で扱いやすい中間表現に変換します。Goコンパイラは独自の内部AST/IRを使用しており、`go/ast`パッケージで提供される公開ASTとは異なります。
5.  **最適化 (Optimization)**: 生成されたIRに対して様々な最適化を適用し、実行効率を向上させます。
6.  **コード生成 (Code Generation)**: 最適化されたIRをターゲットアーキテクチャの機械語に変換します。

このコミットが関連するのは、主に構文解析の段階、特に`parser.go`ファイルが担当する部分です。

### Go言語のラベルと`goto`文

Go言語には、`goto`文とラベルが存在します。`goto`文は、プログラムの実行フローを特定のラベルが付けられた位置にジャンプさせるために使用されます。ラベルは識別子にコロン（`:`）を付けた形式で宣言され、`for`、`switch`、`select`文のブレークやコンティニューのターゲットとしても使用できます。

```go
package main

import "fmt"

func main() {
	i := 0
Loop:
	for {
		if i > 5 {
			goto End
		}
		fmt.Println(i)
		i++
	}
End:
	fmt.Println("End of program")
}
```

Go言語の仕様では、ラベルは関数スコープ内で一意であれば、他の識別子（変数名、定数名など）と同じ名前を持つことが許されています。

### コンパイラ内部のノードタイプ (`ONAME`, `ONONAME`, `OTYPE`, `OPACK`, `OLITERAL`)

Goコンパイラ（`cmd/compile`）は、ソースコードを解析して内部的な抽象構文木（AST）を構築する際に、各ノードに操作コード（`Op`）を割り当てます。これらはコンパイラの内部表現であり、`go/ast`パッケージの公開APIとは異なります。

*   **`ONAME`**: プログラム内の名前付きエンティティ（変数、関数、型、ラベルなど）を表します。識別子が宣言され、その意味が解決された状態です。
*   **`ONONAME`**: まだ完全に解決されていない、または名前が付けられていない識別子を表すことがあります。特定のコンパイラパスでプレースホルダーとして使用されることがあります。
*   **`OTYPE`**: 型定義（例: `type MyInt int`）や型リテラル（例: `struct { Field int }`）を表します。
*   **`OPACK`**: パッケージまたはインポートされたパッケージを表します。
*   **`OLITERAL`**: ソースコード内のリテラル値（整数リテラル `10`、文字列リテラル `"hello"`、真偽値リテラル `true` など）を表します。

このコミットの文脈では、パーサーがラベル名を解析する際に、その識別子が定数として宣言されていると、`OLITERAL`として誤って解釈される可能性があったことが問題でした。

## 技術的詳細

Goコンパイラの`src/cmd/compile/internal/gc/parser.go`ファイルは、Go言語のソースコードを解析し、ASTを構築する役割を担っています。`simple_stmt`関数は、単純な文（代入、関数呼び出し、`goto`など）を解析する際に呼び出されます。

`goto`文のターゲットとなるラベルを解析する際、パーサーはまず`p.name()`を呼び出して識別子を解析します。この`p.name()`は、識別子を`Node`として返し、その`Node`の`Op`フィールドには、識別子の種類に応じた内部的な操作コードが設定されます。

以前のコンパイラでは、ラベルとして有効な`Node.Op`は`ONAME`, `ONONAME`, `OTYPE`, `OPACK`のいずれかに限定されていました。しかし、Go言語では定数名とラベル名が同じであっても構文上は問題ありません。例えば、以下のようなコードです。

```go
package main

const myLabel = 1

func main() {
	goto myLabel
myLabel:
}
```

このコードにおいて、`myLabel`という識別子は`const`宣言によって定数として定義されています。パーサーが`goto myLabel`の`myLabel`を解析する際、もし`myLabel`がリテラル値を持つ定数として先に処理されていた場合、その`Node`の`Op`は`OLITERAL`となる可能性がありました。

しかし、パーサーのロジックでは`OLITERAL`がラベルとして有効な`Op`として認識されていなかったため、`switch lhs.Op`文の`default`ケースにフォールバックし、"expecting semicolon or newline or }"という構文エラーを発生させていました。

このコミットは、この問題を解決するために、`OLITERAL`もラベルとして有効な`Node.Op`のリストに追加することで、定数名とラベル名が一致する場合でもコンパイルが成功するように修正しました。これにより、Go言語の仕様とコンパイラの挙動が一致するようになりました。

## コアとなるコードの解説

`src/cmd/compile/internal/gc/parser.go`の変更は非常にシンプルですが、その影響は大きいです。

```go
			switch lhs.Op {
			case ONAME, ONONAME, OTYPE, OPACK, OLITERAL: // OLITERALが追加された
				lhs = newname(lhs.Sym)
			default:
				p.syntax_error("expecting semicolon or newline or }")
			}
```

`lhs`は、`goto`文のターゲットとして解析された識別子を表す`Node`です。この`Node`の`Op`フィールドが、識別子の種類を示します。

以前のコードでは、`lhs.Op`が`ONAME`, `ONONAME`, `OTYPE`, `OPACK`のいずれかである場合にのみ、その識別子を有効なラベル名として認識し、`newname(lhs.Sym)`を呼び出して新しい名前ノードを作成していました。しかし、定数名とラベル名が一致する場合、`lhs.Op`が`OLITERAL`となる可能性があり、その場合は`default`ブロックに到達し、構文エラーが発生していました。

`OLITERAL`を`case`節に追加することで、パーサーは`OLITERAL`ノードを持つ識別子も有効なラベル名として扱うようになります。これにより、`const labelname = 1`のような定数宣言と`goto labelname`のようなラベル参照が共存できるようになり、Go言語の仕様に準拠した挙動が実現されました。

`newname(lhs.Sym)`は、既存のシンボル（`lhs.Sym`）から新しい名前ノードを作成する関数です。これは、識別子がラベルとして使用される際に、そのシンボルを再利用して適切な内部表現を構築するために行われます。

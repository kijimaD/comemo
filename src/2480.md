## 変更の背景

Go言語には、二重引用符で囲む「解釈済み文字列リテラル (interpreted string literal)」と、バッククォートで囲む「生文字列リテラル (raw string literal)」の2種類の文字列リテラルが存在します。生文字列リテラルは、エスケープシーケンスの解釈を行わず、バッククォート間の文字をそのままの値として扱います。これは、正規表現、HTML、JSON、SQLクエリなど、特殊文字や改行をそのまま含めたい場合に非常に便利です。

このコミット以前のGo言語の`go/scanner`の実装では、生文字列リテラル内に改行文字（`\n`）が出現すると、文字列が途中で終了したと誤って判断し、エラーを報告する可能性がありました。これは生文字列リテラルの本来の意図（複数行にわたる内容をそのまま表現できること）に反する挙動でした。

この変更は、生文字列リテラルがその設計通りに複数行にわたることを正しく認識し、処理できるようにするために行われました。これにより、開発者は改行を含む長いテキストブロックを、エスケープ処理を気にすることなく、より自然な形でコード内に記述できるようになります。

## 前提知識の解説

*   **Go言語の文字列リテラル**:
    *   **解釈済み文字列リテラル (Interpreted String Literal)**: 二重引用符 (`"`) で囲まれます。バックスラッシュ (`\`) を使ったエスケープシーケンス（例: `\n`で改行、`\t`でタブ、`\"`で二重引用符自身）が解釈されます。複数行にわたる文字列を記述する場合、各行の終わりに`\n`を明示的に記述する必要があります。
    *   **生文字列リテラル (Raw String Literal)**: バッククォート (`` ` ``) で囲まれます。エスケープシーケンスは一切解釈されず、バッククォート間の文字がそのまま文字列の値となります。改行文字もそのまま文字列に含まれます。この特性から、複数行のテキストや、バックスラッシュを多用する正規表現などを記述するのに適しています。ただし、バッククォート文字自体を生文字列リテラル内に含めることはできません。
*   **字句解析器 (Lexer/Scanner)**: コンパイラやインタプリタの最初の段階で、ソースコードをトークン（意味のある最小単位）の並びに分解するプログラムです。例えば、`var x = "hello"`というコードは、`var` (キーワード), `x` (識別子), `=` (演算子), `"hello"` (文字列リテラル) といったトークンに分解されます。
*   **`go/scanner`パッケージ**: Go言語の標準ライブラリの一部で、Goのソースコードを字句解析するための機能を提供します。このパッケージは、GoコンパイラやGoツールチェーンの基盤となっています。`Scanner`構造体は、入力ソースコードを読み込み、次のトークンを識別するメソッド（例: `next()`, `scanRawString()`）を持ちます。
*   **`token.Position`**: ソースコード内の位置（ファイル名、行番号、列番号）を表す構造体です。エラーメッセージの報告などに使用されます。

## 技術的詳細

このコミットの技術的な核心は、`src/pkg/go/scanner/scanner.go` 内の `scanRawString` 関数における条件式の変更です。

`scanRawString` 関数は、Goの字句解析器がバッククォートで始まる生文字列リテラルを検出した際に呼び出され、その文字列の終わり（次のバッククォート）までを読み込む役割を担っています。この関数はループ内で文字を一つずつ読み進めます。

変更前のコードでは、ループ内で読み込んだ文字 `ch` がバッククォート (`'`) でない限り、以下の条件でエラーをチェックしていました。

```go
if ch == '\n' || ch < 0 {
    S.error(pos, "string not terminated");
    break;
}
```

この条件式は、「もし読み込んだ文字が改行文字 (`\n`) であるか、または負の値（ファイルの終端や無効な文字を示すことが多い）であるならば、文字列が終了していない」と判断していました。

しかし、生文字列リテラルの本質は、改行文字を含むことができる点にあります。したがって、`ch == '\n'` という条件は、生文字列リテラルが複数行にわたることを妨げる誤ったロジックでした。

このコミットでは、この条件式から `ch == '\n'` の部分が削除されました。

```go
if ch < 0 { // ch == '\n' の条件が削除された
    S.error(pos, "string not terminated");
    break;
}
```

これにより、`scanRawString` 関数は、改行文字が生文字列リテラル内に現れても、それをエラーとして扱わず、文字列の一部として正しく読み進めることができるようになりました。文字列が終了していないと判断されるのは、ファイルの終端に達するなどして `ch < 0` となる場合のみとなります。

この変更によって、Go言語の字句解析器は、生文字列リテラルの仕様に完全に準拠し、複数行にわたる生文字列を正しく解析できるようになりました。

## コアとなるコードの解説

### `src/pkg/go/scanner/scanner.go` の変更

```diff
--- a/src/pkg/go/scanner/scanner.go
+++ b/src/pkg/go/scanner/scanner.go
@@ -331,7 +331,7 @@ func (S *Scanner) scanRawString(pos token.Position) {
 	for S.ch != '`' {
 		ch := S.ch;
 		S.next();
-		if ch == '\n' || ch < 0 {
+		if ch < 0 {

 		}
```

*   **変更前**: `if ch == '\n' || ch < 0`
    *   これは、スキャナーがバッククォートで囲まれた文字列を読み込んでいる最中に改行文字 (`\n`) に遭遇した場合、またはファイルの終端 (`ch < 0`) に遭遇した場合に、「文字列が終了していない」というエラー (`"string not terminated"`) を発生させることを意味していました。
*   **変更後**: `if ch < 0`
    *   改行文字 (`\n`) がエラー条件から除外されました。これにより、スキャナーは生文字列リテラル内の改行文字を正当な文字として扱い、エラーを発生させずに読み進めることができるようになりました。文字列がバッククォートで閉じられる前にファイルの終端に達した場合のみ、エラーが報告されます。

    *   `` `foo\n                        bar` `` は、テスト対象の生文字列リテラルです。この文字列は、`foo` の後に改行、そしてインデントされた `bar` が続く形式です。このテストケースの追加により、`scanRawString` 関数の変更が意図通りに機能し、複数行の生文字列が正しく解析されることが保証されます。

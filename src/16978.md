## 変更の背景

このコミットは、GoランタイムがNetBSDオペレーティングシステム上のARMアーキテクチャでビルドおよび実行する際に発生していた深刻なバグを修正するために導入されました。報告されたエラーメッセージ「`fatal error: runtime: stack split during syscall`」は、Goのランタイムがシステムコールを実行している最中にスタックの拡張（スタック分割）を試み、それが失敗したことを示しています。

Goランタイムは、ゴルーチン（Goの軽量スレッド）のスタックを必要に応じて動的に拡張する「スタック分割」というメカニズムを持っています。しかし、システムコール中はカーネルモードで実行されるため、Goランタイムがスタックを安全に操作できる状態ではありません。システムコール中にスタック分割が発生しようとすると、このような致命的なエラーが発生し、プログラムがクラッシュします。

エラーメッセージのスタックトレースは、`runtime.semasleep`関数が`src/pkg/runtime/os_netbsd.c:97`で呼び出され、その中で`_vasop`という関数（おそらくNetBSD固有のシステムコール関連の関数）が呼び出されていることを示しています。このことから、`semasleep`関数内で時間計算を行う際に、何らかの理由でスタック分割がトリガーされる可能性のあるコードパスが存在したことが推測されます。

## 前提知識の解説

### Goランタイムとゴルーチン

Go言語は、非常に軽量な並行処理の単位である「ゴルーチン（goroutine）」を提供します。ゴルーチンはOSのスレッドよりもはるかに軽量で、数百万個を同時に実行することも可能です。Goランタイムは、これらのゴルーチンをOSスレッドにマッピングし、スケジューリング、メモリ管理、ガベージコレクションなど、Goプログラムの実行に必要な低レベルの機能を提供します。

### スタック分割 (Stack Splitting)

Goのゴルーチンは、最初は非常に小さなスタック（数KB程度）で開始されます。関数呼び出しが深くネストされたり、大きなローカル変数が使用されたりしてスタックが不足しそうになると、Goランタイムは自動的にスタックを拡張します。このプロセスを「スタック分割」と呼びます。スタック分割は、メモリ効率を高め、多数のゴルーチンを同時に実行できるようにするために重要な機能です。

### システムコール (Syscall)

システムコールは、ユーザー空間のプログラムがオペレーティングシステムのカーネルが提供するサービス（ファイルI/O、ネットワーク通信、メモリ管理など）を利用するためのメカニズムです。プログラムがシステムコールを実行すると、実行コンテキストはユーザーモードからカーネルモードに切り替わります。カーネルモードでは、Goランタイムはゴルーチンのスタックを直接管理できません。

### `fatal error: runtime: stack split during syscall`

このエラーは、Goランタイムがシステムコールを実行している最中に、現在のゴルーチンのスタックが不足し、スタック分割を試みた場合に発生します。システムコール中はスタックを安全に拡張できないため、ランタイムはこれを致命的なエラーとして扱います。これは通常、ランタイムのバグ、または特定のアーキテクチャやOSでのエッジケースを示唆します。

### `runtime·nanotime()`

`runtime·nanotime()`は、Goランタイムが提供する、システム起動時からの経過時間をナノ秒単位で取得する関数です。これは、OSのクロックソースに依存し、通常はシステムコールを介して実装されます。

### `runtime·semasleep()`

`runtime·semasleep()`は、Goランタイム内部で使用されるセマフォ（同期プリミティブ）に関連する関数で、指定された時間（ナノ秒）だけゴルーチンをスリープさせるために使用されます。これは、OSの提供するスリープメカニズム（例: `lwp_park`）を利用して実装されます。

### `runtime·lwp_park()`

`runtime·lwp_park()`は、NetBSDにおける軽量プロセス（LWP: Lightweight Process）をパーク（一時停止）させるためのランタイム関数です。これは、GoのゴルーチンがOSスレッド上でブロックされる際に使用される低レベルのプリミティブです。

### `runtime·timediv()`

`runtime·timediv()`は、Goランタイム内部で使用される時間計算のためのヘルパー関数で、ナノ秒単位の時間を秒とナノ秒に分割するなどの処理を行います。

### NetBSD/ARM

NetBSDは、様々なアーキテクチャをサポートするオープンソースのUNIX系オペレーティングシステムです。ARMは、モバイルデバイスや組み込みシステムで広く使用されているプロセッサアーキテクチャです。Goランタイムは、特定のOSとアーキテクチャの組み合わせ（例: `netbsd/arm`）に対して、それぞれに最適化された低レベルのコード（`os_netbsd.c`など）を持っています。

## 技術的詳細

このコミットの技術的詳細の中心は、`ns += runtime·nanotime();` という行が `ns = ns + runtime·nanotime();` に変更された点です。一見すると、この変更は意味論的に同じように見えますが、低レベルのコンパイラ最適化やアトミック操作の文脈では、重要な違いが生じることがあります。

Goランタイムのような低レベルのコードでは、コンパイラはパフォーマンスを最大化するために積極的な最適化を行います。特に、ARMのような特定のアーキテクチャでは、アトミック操作やメモリバリアの扱いが重要になることがあります。

考えられる原因は以下の通りです。

1.  **コンパイラの最適化の違い**:
    *   `a += b` のような複合代入演算子（compound assignment operator）は、コンパイラによっては `a = a + b` とは異なるアセンブリコードを生成する可能性があります。特に、`a` がメモリ上の共有変数である場合、`+=` は「読み込み-変更-書き込み（Read-Modify-Write）」サイクルを単一のアトミック命令として最適化しようとするかもしれません。
    *   しかし、`runtime·nanotime()` の戻り値がシステムコールを伴う場合、その呼び出し自体がコンテキストスイッチや割り込みを伴う可能性があります。この状況で `+=` がアトミックな操作として扱われると、`runtime·nanotime()` の呼び出し中にスタック分割がトリガーされた際に、予期せぬ状態になる可能性があります。
    *   `ns = ns + runtime·nanotime();` のように明示的に `ns` を読み込み、`runtime·nanotime()` の結果と加算し、その結果を `ns` に書き込むという3つの独立したステップに分けることで、コンパイラが生成するコードがより予測可能になり、システムコール中のスタック分割のトリガーを回避できた可能性があります。

2.  **アトミック操作とメモリバリア**:
    *   Goランタイムは、並行処理の安全性を確保するために、アトミック操作やメモリバリアを多用します。`ns` が複数のゴルーチンからアクセスされる可能性のある共有変数である場合、`+=` がアトミックな操作として扱われることで、`runtime·nanotime()` の呼び出し中にスタック分割が発生すると、アトミック操作の整合性が崩れる可能性があったかもしれません。
    *   `ns = ns + runtime·nanotime();` とすることで、`runtime·nanotime()` の呼び出しが完了し、その結果が一時レジスタに格納された後に、`ns` への書き込みが行われるため、より安全なシーケンスが保証された可能性があります。

3.  **NetBSD/ARM固有のコンパイラまたはリンカのバグ/特性**:
    *   特定のOS/アーキテクチャの組み合わせ（この場合はNetBSD/ARM）におけるGoコンパイラやリンカに、複合代入演算子の扱いにバグがあったか、あるいは特定の最適化が予期せぬ副作用を引き起こしていた可能性も考えられます。このような低レベルのバグは、非常にデバッグが困難であり、一見無害に見えるコード変更で解決されることがあります。

この変更は、`runtime.semasleep`関数内で時間計算を行う際に、`runtime·nanotime()`の呼び出しと`ns`への代入の間のタイミングが、システムコール中のスタック分割エラーに影響を与えていたことを示唆しています。明示的な加算と代入に分離することで、コンパイラが生成するコードの挙動が変わり、スタック分割が安全なタイミングで行われるようになった、あるいはスタック分割がトリガーされる条件が回避されたと考えられます。

## コアとなるコードの変更箇所

変更は `src/pkg/runtime/os_netbsd.c` ファイルの1箇所のみです。

```diff
--- a/src/pkg/runtime/os_netbsd.c
+++ b/src/pkg/runtime/os_netbsd.c
@@ -94,7 +94,7 @@ runtime·semasleep(int64 ns)
 			runtime·atomicstore(&m->waitsemalock, 0);
 			runtime·lwp_park(nil, 0, &m->waitsemacount, nil);
 		} else {
-			ns += runtime·nanotime();
+			ns = ns + runtime·nanotime();

```

## コアとなるコードの解説

変更された行は `src/pkg/runtime/os_netbsd.c` 内の `runtime·semasleep` 関数にあります。

元のコード:
```c
ns += runtime·nanotime();
```

修正後のコード:
```c
ns = ns + runtime·nanotime();
```

このコードは、`runtime·semasleep` 関数内で、スリープ時間の計算を行っている部分です。`ns` はナノ秒単位のスリープ時間を表す変数です。`runtime·nanotime()` は現在のナノ秒単位の時刻を返します。

この行の目的は、相対的なスリープ時間 `ns` を、絶対的な将来の時刻に変換することです。つまり、「現在時刻から `ns` ナノ秒後」という絶対時刻を計算しています。

前述の「技術的詳細」で説明したように、`+=` 演算子と `ns = ns + ...` の形式は、C言語の標準では同じ意味ですが、低レベルのコンパイラ最適化や、特にGoランタイムのような並行処理とシステムコールが絡む非常にデリケートなコンテキストでは、生成されるアセンブリコードに微妙な違いが生じることがあります。

この特定のケースでは、`runtime·nanotime()` の呼び出しがシステムコールを伴う可能性があり、そのシステムコール中にスタック分割がトリガーされると問題が発生していました。`ns += runtime·nanotime();` という複合代入が、コンパイラによってアトミックな読み込み-変更-書き込みサイクルとして最適化され、そのサイクル中に`runtime·nanotime()`のシステムコールが実行され、スタック分割が起こることで、エラーが発生していたと考えられます。

`ns = ns + runtime·nanotime();` と明示的に記述することで、以下のシーケンスがより明確になります。
1.  `ns` の現在の値を読み込む。
2.  `runtime·nanotime()` を呼び出し、その結果を取得する。この呼び出し中にスタック分割が安全に行われるか、あるいはスタック分割がトリガーされないようなコンテキストで実行される。
3.  読み込んだ `ns` の値と `runtime·nanotime()` の結果を加算する。
4.  その結果を `ns` に書き込む。

この変更により、`runtime·nanotime()` の呼び出しと `ns` への最終的な代入の間に、コンパイラがより安全なコードを生成できるようになり、システムコール中のスタック分割という致命的なエラーが回避されたと考えられます。これは、特定のコンパイラ、アーキテクチャ、およびOSの組み合わせにおける非常に低レベルな挙動の修正であり、Goランタイムの堅牢性を高めるための重要な修正です。

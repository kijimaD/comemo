## 変更の背景

Go言語の初期の段階において、生文字列リテラル（バッククォート ` ` で囲まれた文字列）の扱いに関して、言語仕様とコンパイラの実装との間に不一致がありました。言語仕様では、生文字列リテラルは改行文字をそのまま含めることができるとされていましたが、このコミットの時点では、コンパイラ（特に `6g` と呼ばれる当時のGoコンパイラ）が、生文字列リテラル内に改行文字が存在する場合に、それを文字として解釈し、コンパイルを成功させてしまうというバグがありました。

この挙動は、生文字列リテラルの本来の意図、すなわちエスケープシーケンスの解釈なしに文字列をそのまま表現するという目的と矛盾していました。特に、複数行にわたる文字列を記述する際に、改行が文字として扱われることで予期せぬ動作を引き起こす可能性がありました。このコミットは、このコンパイラの誤った挙動を修正し、言語仕様に厳密に準拠させることを目的としています。

## 前提知識の解説

### Go言語の文字列リテラル

Go言語には主に2種類の文字列リテラルがあります。

1.  **解釈済み文字列リテラル (Interpreted String Literals)**:
    *   ダブルクォート `""` で囲まれます。
    *   バックスラッシュ `\` を使ったエスケープシーケンス（例: `\n` で改行、`\t` でタブ、`\"` でダブルクォート自身）が解釈されます。
    *   改行文字を直接含めることはできません。複数行にわたる文字列を表現するには `\n` などのエスケープシーケンスを使用する必要があります。

    例: `"Hello,\nWorld!"`

2.  **生文字列リテラル (Raw String Literals)**:
    *   バッククォート ` `` ` で囲まれます。
    *   エスケープシーケンスは一切解釈されません。文字列内の文字は、バッククォートとバッククォートの間に書かれたものがそのままの形で文字列の値となります。
    *   複数行にわたる文字列を記述する際に、改行文字をそのまま含めることができます。これは、正規表現、HTML、SQLクエリなど、エスケープ処理を避けたい場合に非常に便利です。

    例:
    ```go
    const html = `
    <html>
        <body>
            <h1>Hello</h1>
        </body>
    </html>`
    ```

このコミットが修正しようとしているのは、生文字列リテラルに関するコンパイラの挙動です。特に、生文字列リテラル内に改行文字が含まれる場合、それが「文字」としてではなく、「文字列リテラルの一部としての改行」として正しく扱われるべきである、という点です。コミットメッセージの「`` strings should not accept newlines as characters」は、生文字列リテラルが改行を「文字」として受け入れるべきではない、つまり、改行は文字列の区切りや構造の一部として扱われるべきであり、エスケープシーケンスのように特別な意味を持つ文字として解釈されるべきではない、というニュアンスを含んでいます。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラ（当時の `6g`）が、生文字列リテラル内の改行文字をどのように処理していたか、そしてそれが言語仕様とどのように異なっていたか、という点にあります。

Go言語の仕様では、生文字列リテラルは「raw string literal」と呼ばれ、その内容はバッククォートで囲まれた文字のシーケンスであり、エスケープシーケンスは解釈されません。また、改行文字を含むことができます。しかし、このコミット以前のコンパイラは、生文字列リテラル内に改行文字が存在する場合、それを文字列の終端と誤解釈したり、あるいは何らかの形で「文字」として特別な処理を施したりしていた可能性があります。

コミットメッセージの「`` strings should not accept newlines as characters」という表現は、生文字列リテラルが改行を「文字」として受け入れるべきではない、というよりは、生文字列リテラルが改行を「文字列リテラルの一部としての改行」として正しく扱うべきであり、それがコンパイルエラーを引き起こすべきではない、という意図と解釈できます。しかし、追加されたテストケース `bug164.go` を見ると、`const s = `\nHello, World!\n`` のような形式の生文字列リテラルがコンパイルエラーになるべきだとされています。これは、生文字列リテラルが複数行にわたる場合、その改行は文字列の内容としてそのまま含まれるべきであり、コンパイルエラーになるべきではない、という一般的な理解と矛盾するように見えます。

ここで重要なのは、Go言語の仕様における「生文字列リテラル」の定義です。初期のGo言語の仕様では、生文字列リテラルは「改行を含むことができる」とされていましたが、その「改行」がどのように解釈されるかについて、コンパイラの実装が仕様と異なっていた可能性があります。

このコミットが追加した `bug164.go` の内容を見ると、`const s = `\nHello, World!\n`` のような形式の生文字列リテラルが「BUG: should not compile」とされています。これは、生文字列リテラルが、その開始と終了のバッククォートの間に、改行文字を直接含めることを許可するが、その改行が「文字列の終端」や「構文エラー」として扱われるべきではない、という意図と解釈できます。

しかし、コミットメッセージとテストケースの組み合わせから推測すると、当時のコンパイラは、生文字列リテラル内に改行文字が存在する場合に、それを正しく処理できていなかった、あるいは、特定の文脈での改行の扱いが仕様と異なっていた、という問題があったと考えられます。このコミットは、その不一致を解消し、生文字列リテラルが仕様通りに動作するようにコンパイラを修正したものです。

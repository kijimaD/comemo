# [インデックス 22476] ファイルの概要

`test/recover4.go`は、Goランタイムの`debug.SetPanicOnFault`機能が有効な状態で、メモリの不正アクセスが発生した際の`memcopy`関数の挙動をテストするためのファイルです。具体的には、`mmap`で確保したメモリ領域の中央に`munmap`で「穴」を開け、その穴をまたいで`memcopy`を実行した際に、期待されるバイト数がコピーされ、かつ適切なエラー（パニック）が発生するかどうかを検証します。

## 変更の背景

このコミットは、`test/recover4.go`が特定のシステム環境、特にメモリページサイズが64KBであるシステムでテストが失敗する問題を修正するために導入されました。

元の`recover4.go`テストでは、`mmap`で確保するメモリ領域のサイズや、`munmap`で開ける「穴」のサイズを、`64*1024`バイト（64KB）や`16*1024`バイト（16KB）のようにハードコードしていました。これは、多くのシステムで一般的な4KBのメモリページサイズを暗黙的に前提としていました。

しかし、一部のアーキテクチャやOS設定では、メモリページサイズが4KBではなく64KBである場合があります。このようなシステムでは、テストがハードコードされたサイズでメモリ操作を行うと、`mmap`や`munmap`の挙動が期待通りにならなかったり、ページ境界とアラインメントの問題により不正なメモリアクセスが発生したりする可能性がありました。

具体的には、`munmap`は通常、ページサイズの倍数でアラインされたアドレスとサイズで操作されることを期待します。16KBの穴を64KBの領域に開けるという操作は、4KBページシステムでは問題ありませんが、64KBページシステムではページ境界に合致しないため、`munmap`が失敗するか、意図しない挙動を引き起こす可能性がありました。

この問題を解決するため、コミットでは`syscall.Getpagesize()`を使用してシステムの実際のページサイズを動的に取得し、それに基づいてメモリ領域のサイズや穴のサイズを計算するように変更されました。これにより、テストは様々なページサイズのシステムで正しく動作するようになります。

## 前提知識の解説

### メモリページとページサイズ

現代のオペレーティングシステムでは、仮想記憶管理のために物理メモリを「ページ」と呼ばれる固定サイズのブロックに分割して管理します。このページのサイズを「ページサイズ」と呼び、OSやハードウェアアーキテクチャによって異なります。一般的なページサイズは4KBですが、64KB、2MB、1GBなどの大きなページサイズを持つシステムも存在します。メモリ操作（特に`mmap`や`munmap`のようなシステムコール）は、このページサイズにアラインされていることが期待されます。

### `mmap` (Memory Map) システムコール

`mmap`は、ファイルやデバイス、または匿名メモリ領域をプロセスの仮想アドレス空間にマッピングするためのシステムコールです。このテストでは、`syscall.Mmap`を使用して、ファイルに関連付けられていない匿名メモリ領域を確保しています。
- `syscall.Mmap(-1, 0, size, syscall.PROT_READ|syscall.PROT_WRITE, syscall.MAP_ANON|syscall.MAP_PRIVATE)`:
    - `-1`: ファイルディスクリプタがないことを示し、匿名メモリ領域を要求します。
    - `0`: オフセット。
    - `size`: マッピングするバイト数。
    - `syscall.PROT_READ|syscall.PROT_WRITE`: 読み書き可能な保護を設定します。
    - `syscall.MAP_ANON|syscall.MAP_PRIVATE`: 匿名（ファイルに基づかない）かつプライベート（他のプロセスと共有されない）なマッピングであることを示します。

### `munmap` (Memory Unmap) システムコール

`munmap`は、`mmap`によってマッピングされたメモリ領域をアンマッピング（解放）するためのシステムコールです。このテストでは、`syscall.Syscall(syscall.SYS_MUNMAP, ...)`を直接呼び出すことで、`mmap`で確保した領域の一部を意図的にアンマップし、メモリに「穴」を作成しています。これは、`syscall.Munmap`が通常、`mmap`で返された完全な領域をアンマップすることを期待するのに対し、テストでは部分的なアンマップを試みているためです。

### `syscall.Getpagesize()`

Goの`syscall`パッケージに含まれる関数で、現在のシステムのメモリページサイズをバイト単位で返します。この関数を使用することで、プログラムは実行環境のメモリページサイズに依存しない、よりポータブルなメモリ操作を行うことができます。

### `debug.SetPanicOnFault(true)`

Goの`runtime/debug`パッケージにある関数で、`true`を設定すると、Goランタイムが不正なメモリアクセス（例: セグメンテーション違反）を検知した際に、通常のOSシグナルハンドリングではなく、Goのパニック機構を通じてエラーを報告するようになります。これにより、Goプログラム内で不正なメモリアクセスを`recover`で捕捉し、デバッグや特定の回復処理を行うことが可能になります。このテストでは、`memcopy`がメモリの穴をまたいでアクセスした際にパニックが発生することを期待しています。

### `memcopy`関数

このテストコード内で定義されている（またはテスト対象の）メモリコピー関数です。不正なメモリアクセスが発生するような状況で、どれだけのバイトがコピーされたか、そしてエラーがどのように報告されるかを検証するために使用されます。

## 技術的詳細

元の`recover4.go`テストは、メモリページサイズが4KBであることを前提としていました。
- `64*1024`バイトのメモリをマップし、その中央に`32*1024`バイトから`16*1024`バイトの「穴」を開けていました。
- `memcopy`が`32*1024-5`バイトをコピーした後にパニックすることを期待していました。

しかし、メモリページサイズが64KBのシステムでは、これらのハードコードされた値が問題を引き起こしました。
- `syscall.Mmap(-1, 0, 64*1024, ...)`: 64KBのメモリをマップ。これは64KBページシステムではちょうど1ページ分です。
- `syscall.Syscall(syscall.SYS_MUNMAP, uintptr(unsafe.Pointer(&data[32*1024])), 16*1024, 0)`: 64KBの領域の32KBオフセットから16KBをアンマップしようとします。64KBページシステムでは、32KBはページ境界ではありませんし、16KBもページサイズの倍数ではありません。`munmap`は通常、ページ境界にアラインされたアドレスとページサイズの倍数の長さを期待するため、この操作が失敗するか、予期せぬ挙動を引き起こす可能性がありました。

このコミットでは、この問題を解決するために、`syscall.Getpagesize()`を導入し、すべてのメモリ関連のサイズ計算を動的に行っています。
- `size := syscall.Getpagesize()`: システムの実際のページサイズを取得します。
- `16*size` (元の`64*1024`): マップするメモリ領域のサイズを、ページサイズの16倍に変更しました。これにより、ページサイズが4KBなら64KB、64KBなら1MBの領域をマップすることになります。これは、様々なページサイズに対応しつつ、十分な大きさの領域を確保するためです。
- `4*size` (元の`16*1024`): アンマップする「穴」のサイズを、ページサイズの4倍に変更しました。これにより、ページサイズが4KBなら16KB、64KBなら256KBの穴を開けることになります。この変更により、アンマップされる領域のサイズが常にページサイズの倍数となり、`munmap`が正しく動作することが保証されます。
- `8*size` (元の`32*1024`): `munmap`の開始オフセットと、`memcopy`がパニックするまでの期待バイト数の計算基準を、ページサイズの8倍に変更しました。これにより、オフセットもページ境界にアラインされ、`memcopy`の期待値もシステムに依存しない形で計算されます。

これらの変更により、`recover4.go`テストは、メモリページサイズが4KBのシステムでも64KBのシステムでも、同様に意図したメモリ操作とパニックの検証を行うことができるようになりました。

## コアとなるコードの解説

1.  **`size := syscall.Getpagesize()`の追加**:
    -   この行が追加され、現在のシステムのメモリページサイズが`size`変数に格納されるようになりました。これにより、以降のメモリ関連の計算がシステムに依存しない形で行えるようになります。

2.  **`syscall.Mmap`のサイズ変更**:
    -   変更前: `data, err := syscall.Mmap(-1, 0, 64*1024, ...)` (64KBをハードコード)
    -   変更後: `data, err := syscall.Mmap(-1, 0, 16*size, ...)` (ページサイズの16倍)
    -   マップするメモリ領域のサイズが、ハードコードされた64KBから、`syscall.Getpagesize()`で取得したページサイズの16倍に変更されました。これにより、テストが実行されるシステムのページサイズに適応し、常に十分な大きさでページ境界にアラインされたメモリ領域が確保されるようになります。コメントも「Map 16 pages of data」と変更され、ページ単位での操作であることが明確になりました。

3.  **`syscall.Syscall(syscall.SYS_MUNMAP, ...)`のオフセットとサイズ変更**:
    -   変更前: `uintptr(unsafe.Pointer(&data[32*1024])), 16*1024, 0)` (32KBオフセットから16KBをアンマップ)
    -   変更後: `uintptr(unsafe.Pointer(&data[8*size])), uintptr(4*size), 0)` (ページサイズの8倍オフセットからページサイズの4倍をアンマップ)
    -   `munmap`で穴を開ける開始オフセットとサイズが、それぞれ`8*size`と`4*size`に変更されました。これにより、オフセットもサイズも常にページサイズの倍数となり、`munmap`システムコールがページ境界に正しくアラインされた引数で呼び出されることが保証されます。これは、特に64KBページシステムで`munmap`が正しく動作するために不可欠な変更です。コメントも「a 4-page hole in the middle」と変更されました。

4.  **`other`スライスのサイズ変更**:
    -   変更前: `other := make([]byte, 64*1024)`
    -   変更後: `other := make([]byte, 16*size)`
    -   コピー先となる`other`スライスのサイズも、`mmap`で確保する領域のサイズに合わせて`16*size`に変更されました。これにより、テストの整合性が保たれます。

5.  **`memcopy`の期待値の変更**:
    -   変更前: `if n != 32*1024-5 { ... }`
    -   変更後: `if n != 8*size-5 { ... }`
    -   `memcopy`がパニックするまでにコピーされると期待されるバイト数も、`8*size-5`に変更されました。これは、`munmap`のオフセットが`8*size`に変更されたことに対応しており、テストがシステムに依存しない正確な期待値で検証を行えるようにします。コメントも「before the fault (8*size - 5, the offset we skip in the argument)」と変更されました。

これらの変更により、`recover4.go`テストは、ハードコードされたマジックナンバーに依存するのではなく、システムの実際のメモリページサイズに基づいて動的に動作するようになり、異なるシステム環境での堅牢性が向上しました。

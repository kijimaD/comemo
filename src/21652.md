# [インデックス 21652] ファイルの概要

このコミットは、Go言語の`os`パッケージにおけるPlan 9オペレーティングシステム向けの`stat`システムコールエミュレーションの改善に関するものです。具体的には、`stat`バッファが不足した場合のカーネルからの情報伝達メカニズムを適切に処理し、必要なバッファサイズを動的に調整して再試行するロジックを実装しています。これにより、Plan 9環境でのファイル情報の取得（`stat`）の堅牢性が向上しました。

## コミット

このコミットは、Go言語の`os`パッケージ内の`stat_plan9.go`ファイルに対して行われた変更です。Plan 9オペレーティングシステムにおいて、`stat`システムコールがファイル情報を取得する際に、提供されたバッファが小さすぎる場合にカーネルがそのバッファの先頭2バイトに正しいサイズを書き込むという、Plan 9のlibc（`dirfstat.c`）の挙動をエミュレートするように修正されています。これにより、バッファが不足した場合でも、正しいサイズでバッファを再割り当てし、再試行することで、ファイル情報の取得を成功させることが可能になります。この変更は、以前Nick Owensによって作成されたCL（Change List）の再作成版です。

## 変更の背景

この変更の背景には、Plan 9オペレーティングシステムにおける`stat`システムコールの特殊な挙動があります。通常、`stat`システムコールはファイルに関するメタデータ（サイズ、パーミッション、タイムスタンプなど）をバッファに書き込みます。しかし、Plan 9では、提供されたバッファが小さすぎて全ての情報を格納できない場合、カーネルはエラーを返すのではなく、バッファの先頭2バイトに実際に必要なデータのサイズを書き込みます。これは、可変長データを扱うPlan 9のファイルプロトコル（9P）の設計思想に由来します。

Go言語の`os`パッケージは、様々なオペレーティングシステムに対応するために、それぞれのOSのシステムコールを抽象化して提供しています。Plan 9環境においても、`os.Stat`などの関数は内部的に`dirstat`関数を呼び出し、`stat`システムコールを介してファイル情報を取得します。

このコミット以前の`dirstat`の実装では、バッファが不足した場合にこのPlan 9特有の挙動を適切に処理できていませんでした。その結果、`stat`が失敗したり、不完全な情報が返されたりする可能性がありました。この問題は、GoのIssue #8781として報告されていたと考えられます（ただし、現在のGitHubのIssueトラッカーでは直接参照できない可能性があります）。

この変更は、Nick Owensによって以前に提案されたCL（Change List）の再作成版であり、Plan 9のlibcにおける`dirfstat.c`の実装アルゴリズムに倣うことで、このバッファ不足の問題を解決し、`stat`の堅牢性を向上させることを目的としています。

## 前提知識の解説

### Plan 9オペレーティングシステム

Plan 9は、ベル研究所で開発された分散オペレーティングシステムです。Unixの設計思想をさらに推し進め、全てのリソース（ファイル、デバイス、ネットワーク接続など）をファイルとして表現し、標準的なファイルシステムインターフェースを通じてアクセスするという「全てはファイルである」という原則を徹底しています。この設計により、システム全体がシンプルで一貫性のあるインターフェースで構成され、分散環境でのリソース共有が容易になります。

### Plan 9のファイルシステムと9Pプロトコル

Plan 9のファイルシステムは、9P（またはPlan 9 File Protocol）と呼ばれるプロトコルを通じてアクセスされます。9Pは、クライアントとサーバー間でファイルシステム操作を効率的に行うための軽量なプロトコルです。`stat`システムコールもこの9Pプロトコルの一部として実装されており、ファイルに関するメタデータ（`Dir`構造体として知られる）をやり取りします。

`Dir`構造体は可変長であり、ファイル名やユーザー名などの文字列フィールドが含まれるため、そのサイズはファイルによって異なります。この可変長性に対応するため、9Pプロトコルでは、クライアントが提供したバッファが`Dir`構造体を格納するのに十分なサイズでない場合、カーネル（またはファイルサーバー）はバッファの先頭に実際に必要なバイト数を書き込み、クライアントに再試行を促すというメカニズムを採用しています。これは、Unix系のシステムで`ENOMEM`などのエラーを返すのとは異なるアプローチです。

### Go言語の`os`パッケージ

Go言語の標準ライブラリである`os`パッケージは、オペレーティングシステムとの基本的な相互作用を提供します。これには、ファイル操作、プロセス管理、環境変数へのアクセスなどが含まれます。`os.Stat`関数は、指定されたパスのファイルに関する情報を取得するために使用され、内部的にはOS固有の`stat`システムコールを呼び出します。Plan 9環境では、この`os.Stat`が`src/os/stat_plan9.go`に実装されている`dirstat`関数を呼び出します。

### `syscall.Dir`と`syscall.UnmarshalDir`

Go言語の`syscall`パッケージは、低レベルのシステムコールインターフェースを提供します。Plan 9環境では、`syscall.Dir`はPlan 9の`Dir`構造体（ファイルメタデータ）をGoの構造体として表現したものです。`syscall.UnmarshalDir`関数は、`stat`システムコールから返されたバイト列（`Dir`構造体のバイナリ表現）をGoの`syscall.Dir`構造体にデコード（アンマーシャル）するために使用されます。この関数は、バイト列の解析と、可変長フィールドの適切な処理を担当します。

## 技術的詳細

このコミットの技術的詳細は、`src/os/stat_plan9.go`内の`dirstat`関数の変更に集約されます。

1.  **`_BIT16SZ`定数の導入**:
    `const _BIT16SZ = 2`が追加されました。これは、Plan 9の`stat`システムコールがバッファ不足を通知する際に、バッファの先頭に書き込む2バイトのサイズ情報を示す定数です。

2.  **初期バッファサイズの調整**:
    変更前は、初期バッファサイズ`size`が`syscall.STATFIXLEN + 16*4 + 128`を`128`の倍数に切り上げた値で初期化されていました。変更後は、`size := syscall.STATFIXLEN + 16*4`と、よりシンプルな初期値に変更されています。これは、後続のロジックで動的にバッファサイズを調整するため、初期値の厳密な丸めが不要になったためと考えられます。

3.  **バッファの確保方法の変更**:
    `buf := make([]byte, size)`から`buf := make([]byte, _BIT16SZ+size)`に変更されました。これは、`stat`システムコールがバッファ不足の場合に先頭2バイトにサイズ情報を書き込むため、その2バイトを読み取るための領域を最初から確保しておく必要があるためです。これにより、最初の`stat`呼び出しでバッファが不足した場合でも、その2バイトを読み取って正しいサイズを知ることができます。

4.  **バッファサイズチェックの変更**:
    変更前は`if n < syscall.STATFIXLEN`でバッファが短すぎるかをチェックしていましたが、変更後は`if n < _BIT16SZ`に変更されました。これは、Plan 9の`stat`がバッファ不足の場合に少なくとも2バイト（サイズ情報）を書き込むため、最低限2バイトが読み取れたかどうかを確認すればよいというロジックに基づいています。もし2バイト未満しか読み取れなかった場合は、`syscall.ErrShortStat`エラーを返します。

5.  **バッファ不足時の再試行ロジックの改善**:
    最も重要な変更点です。
    変更前は、`if size > n { continue }`というロジックで、読み取ったバイト数`n`が初期バッファサイズ`size`よりも小さい場合にループを継続していました。これは、バッファが大きすぎた場合に無駄なループを避けるためのものでしたが、バッファ不足時の動的なサイズ調整には対応していませんでした。

    変更後は、`if size <= n`という条件で、読み取ったバイト数`n`が現在のバッファサイズ`size`以上である場合にのみ`UnmarshalDir`を試みるようになりました。
    そして、`if n < _BIT16SZ`のチェックを通過した後、`n`が`_BIT16SZ`（2バイト）以上であれば、その2バイトを読み取って実際のサイズを取得します。
    `size = int(binary.LittleEndian.Uint16(buf[:_BIT16SZ]))`
    この行は、読み取ったバッファの先頭2バイトからリトルエンディアン形式で`uint16`の値を読み取り、それを次の`stat`呼び出しで使用する`size`として設定します。これにより、カーネルが通知した正しいバッファサイズで再試行が可能になります。

    ループは最大2回実行されます。1回目でバッファが不足した場合、カーネルが書き込んだサイズ情報に基づいて`size`を更新し、2回目でその新しいサイズで`stat`を再試行します。

6.  **エラーハンドリングの改善**:
    変更前は、ループの最後に`return nil, &PathError{"stat", name, syscall.ErrBadStat}`で固定のエラーを返していました。
    変更後は、`if err == nil { err = syscall.ErrBadStat }`というロジックが追加され、もし`stat`システムコール自体がエラーを返さなかった場合でも、最終的に`syscall.ErrBadStat`を返すようにしています。これにより、バッファ不足による再試行が2回とも失敗した場合など、適切なエラーが返されるようになります。

これらの変更により、Goの`os`パッケージはPlan 9の`stat`システムコールの挙動をより正確にエミュレートし、バッファ不足のシナリオにおいても堅牢にファイル情報を取得できるようになりました。

## コアとなるコードの解説

1.  **`const _BIT16SZ = 2`の追加**:
    Plan 9の`stat`システムコールがバッファ不足を通知する際に、バッファの先頭に書き込むサイズ情報が2バイトであることを明示するための定数です。これにより、マジックナンバーを避け、コードの可読性と保守性が向上します。

2.  **`size`変数の初期化変更**:
    `size := (syscall.STATFIXLEN + 16*4 + 128) &^ 128`から`size := syscall.STATFIXLEN + 16*4`に変更されました。これは、初期バッファサイズをよりシンプルにし、後続のロジックで動的にサイズを調整する前提に基づいています。`syscall.STATFIXLEN`は`Dir`構造体の固定部分のサイズ、`16*4`は可変長フィールド（文字列）の最大長を見積もったものです。

3.  **`buf`の確保サイズ変更**:
    `buf := make([]byte, size)`から`buf := make([]byte, _BIT16SZ+size)`に変更されました。これは、`stat`システムコールがバッファ不足の場合に、実際に必要なサイズをバッファの先頭2バイトに書き込むため、その2バイトを読み取るための追加領域を確保するためです。これにより、最初の`stat`呼び出しでバッファが不足しても、そのサイズ情報を失うことなく取得できます。

4.  **`n < _BIT16SZ`による初期チェック**:
    `if n < syscall.STATFIXLEN`から`if n < _BIT16SZ`に変更されました。これは、`stat`システムコールが少なくとも2バイト（サイズ情報）を書き込むことを期待しているため、読み取れたバイト数`n`が2バイト未満であれば、それは不正な状態であり、`syscall.ErrShortStat`エラーを返すようにしています。

5.  **バッファ不足時のサイズ再取得と再試行**:
    変更前は`if size > n { continue }`という単純なループ継続ロジックでした。
    変更後は、`if size <= n`という条件で、読み取ったバイト数`n`が現在のバッファサイズ`size`以上であれば、`syscall.UnmarshalDir`を呼び出して`Dir`構造体をデコードし、成功すればその結果を返します。
    もし`size > n`（つまりバッファが不足している）場合、以下の行が実行されます。
    `size = int(binary.LittleEndian.Uint16(buf[:_BIT16SZ]))`
    この行は、`buf`の先頭2バイトからリトルエンディアン形式で`uint16`の値を読み取り、それを新しい`size`として設定します。この`size`は、カーネルが「この`Dir`構造体を格納するにはこれだけのバイト数が必要だ」と通知した実際のサイズです。ループの次のイテレーションでは、この新しい`size`で`buf`が再確保され、`stat`システムコールが再試行されます。この`for i := 0; i < 2; i++`ループにより、最大2回の試行で正しいファイル情報を取得しようとします。

6.  **エラーハンドリングの修正**:
    ループの最後に`return nil, &PathError{"stat", name, syscall.ErrBadStat}`という固定のエラーを返す代わりに、`if err == nil { err = syscall.ErrBadStat }`というロジックが追加されました。これにより、`stat`システムコール自体がエラーを返さなかったが、バッファ不足による再試行が2回とも失敗した場合など、適切な`syscall.ErrBadStat`エラーが返されるようになります。

これらの変更により、Goの`os`パッケージはPlan 9の`stat`システムコールのセマンティクスをより正確に模倣し、バッファ不足の状況でも堅牢に動作するようになりました。

# [インデックス 21764] ファイルの概要

## 変更の背景

このコミットは、Goの`range`ステートメントにおける変数キャプチャの誤った挙動を修正するために行われました。具体的には、Goのレース検出器（race detector）が`TestRaceRange`というテストで失敗を報告したことがきっかけとなりました。

Goの`for...range`ループでは、ループ変数は各イテレーションで再利用される単一の変数です。このため、ループ内でクロージャ（無名関数やゴルーチンなど）を定義し、そのクロージャがループ変数を参照する場合、クロージャは変数の「値」ではなく「アドレス」をキャプチャします。結果として、クロージャが実行される時点では、ループ変数は最後のイテレーションの値を持っているため、意図しない結果（例えば、すべてのクロージャが同じ最終値を出力する）が生じることがありました。

コミットメッセージにある「ORANGE typecheck does not increment decldepth around body.」という記述は、この問題の技術的な根本原因を指しています。Goコンパイラの型チェックフェーズ（`typecheck`）において、`range`ループのボディ（ループ本体のコードブロック）の処理時に、`decldepth`（宣言深度、またはスコープのネストレベルを示す内部カウンタ）が適切にインクリメントされていませんでした。これにより、コンパイラがループ変数のスコープを誤って解釈し、クロージャが変数を「参照渡し」でキャプチャしてしまうというバグが発生していました。

`TestRaceRange`の失敗は、この誤ったキャプチャが並行処理においてデータ競合（data race）を引き起こす可能性を示唆していました。データ競合は、複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つが書き込み操作である場合に発生し、予測不能な動作やバグの原因となります。

## 前提知識の解説

### Goの`for...range`ループ

Go言語の`for...range`ループは、スライス、配列、文字列、マップ、チャネルなどのコレクションをイテレートするための構文です。

```go
for index, value := range collection {
    // ループ本体
}
```

ここで、`index`と`value`はループ変数です。重要なのは、これらの変数が**ループの各イテレーションで再宣言されるのではなく、ループ全体で単一の変数が再利用され、その値が各イテレーションで更新される**という点です。

### クロージャにおける変数キャプチャ

Goのクロージャは、それが定義された環境（外側の関数やブロック）の変数を参照できます。この参照の仕方は「キャプチャ」と呼ばれます。

*   **参照渡し（Capture by Reference）**: 変数のメモリ上のアドレスをキャプチャします。クロージャが実行されるとき、そのアドレスにある現在の値が使用されます。ループ変数の場合、ループが終了した時点での最終値が参照されることになります。
*   **値渡し（Capture by Value）**: 変数の現在の値をコピーしてキャプチャします。クロージャが実行されるとき、キャプチャされた時点のコピーされた値が使用されます。

Goのクロージャは、デフォルトで外側の変数を「参照渡し」でキャプチャします。これが`for...range`ループの変数再利用の特性と組み合わさると、前述の意図しない挙動を引き起こします。この問題を回避するためには、ループ内で新しいローカル変数を宣言し、ループ変数の値をそのローカル変数にコピーするというイディオムが一般的に用いられます。

```go
for _, v := range values {
    vCopy := v // 各イテレーションで新しい変数を宣言し、値をコピー
    go func() {
        fmt.Println(vCopy) // vCopyは値渡しでキャプチャされる
    }()
}
```
**注記**: Go 1.22以降では、`for`ループ（`for...range`を含む）のループ変数は各イテレーションで再宣言されるように変更され、この問題は言語仕様レベルで解決されました。しかし、このコミットは2015年のものであり、当時のGoの挙動に基づいています。

### Goコンパイラ（`cmd/gc`）と`typecheck`

`cmd/gc`はGo言語の公式コンパイラです。コンパイルプロセスには、ソースコードの解析、抽象構文木（AST）の構築、型チェック、最適化、コード生成など、様々なフェーズがあります。

`typecheck`フェーズは、プログラムの型がGoの型システム規則に準拠していることを検証する重要なステップです。これには、変数の宣言、使用、代入、関数の呼び出しなどが含まれます。コンパイラは、このフェーズで各識別子のスコープとライフタイムを追跡します。

### `decldepth`（宣言深度）

`decldepth`は、Goコンパイラの内部で用いられる概念で、現在のコードがどれだけ深くネストされたスコープにあるかを示すカウンタです。関数、ブロック、ループなどの新しいスコープに入るたびに`decldepth`はインクリメントされ、スコープを抜けるたびにデクリメントされます。このカウンタは、変数の可視性やライフタイム、そしてクロージャによる変数キャプチャのセマンティクスを正しく処理するために不可欠です。

このコミットの文脈では、`range`ループのボディが新しいスコープを形成するにもかかわらず、`typecheck`フェーズがそのスコープの`decldepth`を適切に管理していなかったことが問題でした。

### Goのレース検出器（Race Detector）と`TestRaceRange`

Goのレース検出器は、並行プログラムにおけるデータ競合を検出するための組み込みツールです。`go test -race`のように`-race`フラグを付けてテストを実行することで有効にできます。データ競合は、複数のゴルーチンが同じメモリ位置に同時にアクセスし、そのうち少なくとも1つが書き込み操作である場合に発生します。これはGoプログラムにおける最も一般的な並行処理のバグの一つであり、予測不能な結果やクラッシュを引き起こす可能性があります。

`TestRaceRange`は、Goの標準ライブラリのテストスイートに含まれる特定のテストケースで、`range`ループに関連するデータ競合を意図的に引き起こし、レース検出器がそれを正しく検出できるかを確認するために設計されています。このテストが失敗したということは、`range`ループのセマンティクスに、並行処理の文脈で問題を引き起こすようなバグが存在したことを示しています。

## 技術的詳細

このバグは、`cmd/gc`コンパイラの`range`ステートメントの型チェックロジックに起因していました。具体的には、`src/cmd/gc/range.c`内の`typecheckrange`関数が、`range`ループのボディを型チェックする際に、そのスコープの`decldepth`を適切にインクリメント/デクリメントしていませんでした。

Goコンパイラは、クロージャが外側の変数をキャプチャする際に、その変数がクロージャのスコープよりも外側で宣言されているかどうかを`decldepth`を用いて判断します。`range`ループのボディは論理的に新しいスコープを形成し、その中で宣言された変数や、外側のループ変数を参照するクロージャは、そのスコープの深さを考慮して正しく処理される必要があります。

しかし、バグのある状態では、`range`ループのボディが型チェックされる際に`decldepth`がインクリメントされないため、コンパイラはループ変数がクロージャと同じ「宣言深度」にあると誤解していました。これにより、クロージャがループ変数を「値渡し」ではなく「参照渡し」でキャプチャすべきであると判断し、結果としてすべてのクロージャがループ変数の最終値を参照してしまうという、いわゆる「Goのrangeループ変数キャプチャ問題」が発生していました。

この修正は、`typecheckrange`関数内で`range`ループのボディを型チェックする前後に`decldepth++`と`decldepth--`を追加することで、このスコープの深さを正しくコンパイラに認識させるようにしました。これにより、クロージャがループ変数をキャプチャする際のセマンティクスが修正され、期待通りに「値渡し」でキャプチャされるようになりました（または、少なくとも当時のGoのセマンティクスに沿った正しいキャプチャが行われるようになりました）。

また、`src/cmd/gc/typecheck.c`の`checkassign`関数にも関連する変更が加えられています。`ORANGE`（`for...range`ループを表す内部ノードタイプ）で宣言された変数が、各イテレーションで代入されることを示すために、`stmt->op == ORANGE`という条件が追加されました。これは、`range`ループ変数の代入セマンティクスをコンパイラが正しく理解し、最適化や変数キャプチャの判断に役立てるためのものです。

`test/closure2.go`の変更は、この修正が正しく機能することを確認するための新しいテストケースの追加と、既存のテストケースの修正を含んでいます。特に、`range`ループ内でクロージャがループ変数をキャプチャする様々なシナリオが追加され、期待される値が正しくキャプチャされていることを検証しています。

## コアとなるコードの解説

### `src/cmd/gc/range.c`の変更

`typecheckrange`関数は、`range`ステートメントの型チェックを担当します。この関数内の変更は、`range`ループの処理順序と`decldepth`の管理を明確に再定義しています。

変更前は、`range`式の型チェック（`typecheck(&n->right, Erv);`）が、生成される値（ループ変数）の型チェック（`for(ll=n->list; ll; ll=ll->next) ... typecheck(&ll->n, Erv | Easgn);`）の後に来ていました。

変更後は、以下の順序で処理が行われるようになりました。

1.  **`range`式の型チェックを最初に実行**: `typecheck(&n->right, Erv);` がループ変数の型チェックの前に移動しました。これは、`range`式が一度だけ評価され、論理的にはループの一部ではないため、最初に型チェックされるべきという考えに基づいています。
2.  **生成される値（ループ変数）の型チェック**: `range`式が評価された後、`range`によって生成される値（`index`と`value`）が型チェックされます。このステップは、新しい変数を宣言する可能性があり、ループ本体内のクロージャがこれらの変数をキャプチャする可能性があるため、ループ本体の型チェックの前に実行される必要があります。
3.  **`decldepth`のインクリメント**: `decldepth++;` が`typechecklist(n->nbody, Etop);`（ループ本体の型チェック）の直前に追加されました。これにより、コンパイラはループ本体が新しい宣言深度にあることを正しく認識します。
4.  **ループ本体の型チェック**: `typechecklist(n->nbody, Etop);` が実行されます。
5.  **`decldepth`のデクリメント**: `decldepth--;` がループ本体の型チェックの直後に追加されました。これにより、ループ本体のスコープを抜けた後に`decldepth`が元のレベルに戻されます。

この変更により、`range`ループのボディ内で定義されたクロージャがループ変数をキャプチャする際に、コンパイラが正しいスコープ情報を利用できるようになり、意図した「値渡し」のセマンティクスが適用されるようになりました。

+\tif(n->defn != stmt || stmt->op == ORANGE) {
```

この変更は、`range`ループ（内部的には`ORANGE`という操作タイプで表現される）で宣言された変数が、各イテレーションで代入されるという特殊なケースを明示的に処理するためのものです。`n->defn != stmt`という既存の条件に加えて、`stmt->op == ORANGE`という条件が追加されました。これにより、`range`ループ変数の代入がコンパイラによって正しく追跡され、そのライフタイムとキャプチャセマンティクスがより正確に処理されるようになります。これは、`range.c`での`decldepth`の修正と連携して、`range`ループにおける変数キャプチャの挙動を全体的に改善します。

### `test/closure2.go`の変更

このテストファイルは、Goのクロージャと変数キャプチャの挙動を検証するためのものです。今回のコミットでは、特に`range`ループ内でのクロージャによる変数キャプチャの様々なシナリオを網羅するために、多数の新しいテストケースが追加されました。

例えば、`for i := range [2]int{}`ループ内でクロージャ`g`を定義し、そのクロージャがループ変数`i`をキャプチャするケースが追加されています。このテストは、`i`が各イテレーションで変異するにもかかわらず、クロージャが`i`の最終的な値（この場合は`1`）を正しくキャプチャしていることを検証しています。これは、`range`ループ変数が「参照渡し」でキャプチャされるという当時のGoの挙動をテストするものです。

また、`q++`のような操作が`range`ループ内で実行され、その`q`がクロージャによってキャプチャされるケースも追加されています。これらのテストは、`decldepth`の修正が、異なる宣言深度にある変数とクロージャの相互作用を正しく処理できるようになったことを確認するために重要です。

これらのテストケースは、コンパイラの修正が意図した通りに機能し、`range`ループにおける変数キャプチャのバグが解決されたことを保証します。

# [インデックス 20419] ファイルの概要

このコミットは、GoランタイムにおけるSolarisシステムでのGoコードからCコードを介してブロッキングパスに入る問題を解消することを目的としています。具体的には、Goのネットワーキングポーリング（netpoll）関連の操作や、パニック処理、およびSolaris固有のシステムコールラッパーにおいて、Goのスケジューラが関与しないOSスレッド（M）上で直接C関数を呼び出すように変更することで、デッドロックやスケジューリングの非効率性を回避しています。

## 変更の背景

Goランタイムは、ゴルーチン（G）、論理プロセッサ（P）、OSスレッド（M）からなるGPMスケジューリングモデルを採用しています。このモデルでは、多数の軽量なゴルーチンを少数のOSスレッド上で効率的に多重化することで、高い並行性と並列性を実現しています。

しかし、GoコードがCコードを呼び出し、そのCコードがさらにブロッキングするシステムコール（例: ネットワークI/O、ファイルI/O）を実行する場合、GoランタイムのスケジューラがそのOSスレッド（M）の状態を正確に把握できないという問題が発生することがあります。特にSolarisのような特定のOS環境では、この「Go -> C -> ブロック」というパスが、GoスケジューラがMを解放できない、あるいはMがブロックしているにもかかわらず他のゴルーチンをスケジュールしようとする、といった非効率性やデッドロックのリスクを引き起こす可能性がありました。

このコミットの目的は、Solaris環境において、GoランタイムがCコードを介してブロッキングする可能性のある操作を行う際に、Goスケジューラの介入なしにOSスレッド（M）上で直接それらの操作を実行させることで、このような問題を解消することにあります。これにより、Goランタイムの安定性と効率性が向上します。

## 前提知識の解説

### Goランタイムスケジューラ (GPMモデル)

*   **G (Goroutine)**: Goの軽量な並行処理単位。数KBのスタックで起動し、OSスレッドよりもはるかに安価に生成・管理されます。
*   **P (Processor)**: 論理プロセッサ。Goのユーザーコードを実行するためのコンテキストを提供します。各Pは、実行可能なゴルーチンのローカルキューを持ち、`GOMAXPROCS`によってその数が決定されます。
*   **M (Machine)**: OSスレッド。実際にCPU上でGoコードを実行するエンティティです。MはPと関連付けられてGoユーザーコードを実行しますが、システムコールなどでブロックされると、そのPは他のMに引き渡され、他のゴルーチンが実行を継続できます。

### ブロッキングシステムコールとGoランタイムの挙動

Goランタイムは、ブロッキングするシステムコールを賢く扱います。
*   **ネットワークI/O**: 多くのネットワークI/Oは、`epoll` (Linux) や `kqueue` (macOS/BSD) のような非ブロッキングI/Oメカニズムとネットワークポーラーを利用します。ゴルーチンがネットワークI/Oを要求すると、そのゴルーチンはスリープ状態になり、OSスレッドはブロックされません。I/Oが完了すると、ポーラーがランタイムに通知し、ゴルーチンが再開されます。
*   **真にブロッキングするシステムコール (例: ファイルI/O、CGO呼び出し)**: OSスレッドを実際にブロックするシステムコールの場合、Goランタイムは、そのシステムコールを実行するゴルーチンが関連付けられているMをPから切り離します。これにより、Pは他の実行可能なゴルーチンに利用可能になり、プログラム全体の実行が継続されます。システムコールが完了すると、ゴルーチンはPを再取得しようとし、実行を再開します。

### `onM` 関数

`onM` はGoランタイム内部の関数で、指定された関数を現在のOSスレッド（M）上で直接実行させます。これは、Goスケジューラの介入なしに、特定の操作をOSスレッドのコンテキストで実行する必要がある場合に用いられます。例えば、スタックの管理、ガベージコレクションの一部、ゴルーチンの駐車/再開、スケジューラ自身のループなど、ランタイムの低レベルな処理で利用されます。

### `//go:nosplit` ディレクティブと `#pragma textflag NOSPLIT`

*   **`//go:nosplit`**: Goコンパイラに対するディレクティブで、関数冒頭のスタックオーバーフローチェック（スタック分割チェック）を省略するよう指示します。通常、Go関数はスタックが足りない場合に自動的にスタックを拡張しますが、`nosplit`関数はこれをスキップします。これは、ランタイムの非常に低レベルな部分や、パニック処理など、スタックの拡張が問題を引き起こす可能性がある場合に安全性を確保するために使用されます。
*   **`#pragma textflag NOSPLIT`**: CコードにおけるGoの`//go:nosplit`に相当するディレクティブです。GoランタイムのC部分で、同様にスタックチェックを省略し、関数がスタックを拡張しないことを保証するために使用されます。

## 技術的詳細

このコミットの核心は、Solaris環境におけるGoランタイムのネットワーキングおよびパニック処理の堅牢性を高めることにあります。

Goのネットワーキングポーリング（netpoll）は、OSのI/O多重化メカニズム（Solarisでは`port_create`, `port_associate`, `port_get`など）を利用して非同期I/Oを実現しています。しかし、これらの操作の一部がCコードを介して実行される際に、GoスケジューラがMの状態を適切に管理できない状況が発生していました。具体的には、GoのゴルーチンがC関数を呼び出し、そのC関数がOSのブロッキングコールを実行すると、GoスケジューラはMがブロックしていることを認識できず、そのMを他のゴルーチンに割り当てようとするか、あるいはMが不必要にブロックされたままになる可能性がありました。

この問題を解決するため、`netpollinit`, `netpollopen`, `netpollclose`, `netpollarm` といったネットワーキング関連の低レベルなC関数呼び出しを、Goの`onM`関数でラップするように変更されました。`onM`を使用することで、これらの操作はGoスケジューラの介入なしに、現在実行中のOSスレッド（M）上で直接実行されます。これにより、GoスケジューラがMの状態を誤解するリスクがなくなり、ブロッキングが適切に処理されるようになります。

また、パニック処理においても同様の考慮がなされています。パニックはGoプログラムの実行を停止させる非常にクリティカルなイベントであり、その処理中にスタックの拡張などが発生すると、さらなるパニックやデッドロックを引き起こす可能性があります。そのため、`startpanic`, `dopanic`, `throw`, `gothrow` といったパニック関連の関数に`//go:nosplit`ディレクティブが追加されました。これにより、これらの関数はスタックチェックをスキップし、スタックを拡張しないことが保証され、パニック処理の堅牢性が向上します。

さらに、`src/pkg/runtime/os_solaris.c` 内の様々なシステムコールラッパー（`close`, `exit`, `getcontext`, `getrlimit`, `mmap`, `munmap`, `nanotime`, `time·now`, `open`, `read`, `write`など）にも`#pragma textflag NOSPLIT`が追加されています。これは、これらのC関数がGoランタイムの非常に低レベルな部分から呼び出される際に、スタックの安全性を確保するための措置です。

これらの変更は、GoランタイムがOSとのインタラクションをより細かく制御し、特にSolarisのような特定のOS環境におけるブロッキング動作のセマンティクスを正確に扱うことで、ランタイム全体の安定性とパフォーマンスを向上させるものです。

## コアとなるコードの解説

### `netpoll.go` の変更

`netpoll.go` における変更は、Goのネットワーキングポーリングに関連する低レベルなC関数呼び出しが、Goスケジューラの管理下にあるゴルーチンのスタックではなく、直接OSスレッド（M）のコンテキストで実行されるようにしたものです。これは、これらの操作がOSレベルでのブロッキングを伴う可能性があり、Goスケジューラがそのブロッキングを適切に処理できない場合に、デッドロックやスケジューリングの非効率性を引き起こすことを防ぐためです。`onM` を使用することで、Goランタイムはこれらのクリティカルな操作を、スケジューラの介入なしに安全に実行できます。

### `os_solaris.c` の変更

`os_solaris.c` に追加された `#pragma textflag NOSPLIT` ディレクティブは、Solaris固有のシステムコールラッパー関数がスタックを拡張しないことを保証します。これらの関数はGoランタイムの非常に低レベルな部分から呼び出されるため、スタックの拡張が発生すると、ランタイムの安定性に深刻な影響を与える可能性があります。`NOSPLIT` を指定することで、これらの関数が常に固定されたスタック空間内で動作し、予期せぬスタックオーバーフローや関連する問題を回避します。

### `panic1.go` の変更

`panic1.go` における `//go:nosplit` ディレクティブの追加は、パニック処理の堅牢性を高めるためのものです。パニックはプログラムの異常終了を意味し、その処理は非常にデリケートです。パニック処理中にスタックの拡張が必要になると、その拡張自体が失敗したり、さらなるパニックを引き起こしたりする可能性があります。`nosplit` を指定することで、パニック関連の関数がスタックを拡張しないことが保証され、パニック処理がより予測可能で安全になります。特に `throw` 関数における `gp.m.throwing = 1` の設定と `startpanic()` の呼び出しは、パニック状態への移行をより明示的にし、ランタイムがパニック処理中であることを認識できるようにするためのものです。

これらの変更は全体として、GoランタイムがOSとのインタラクションをより厳密に制御し、特にブロッキングする可能性のあるC呼び出しや、パニックのようなクリティカルな状況において、Goスケジューラの挙動を最適化し、システムの安定性を向上させることを目的としています。

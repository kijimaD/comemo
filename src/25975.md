## 変更の背景

Go言語の `go build` コマンドには、`-buildmode` というオプションがあり、様々なビルドモードをサポートしています。その一つに `shared` モードがあります。このモードは、Goのパッケージを共有ライブラリ（例: Linuxでは `.so` ファイル）としてコンパイルし、他のGoプログラムがそれらをリンクして使用できるようにすることを目的としていました。これにより、実行可能ファイルのサイズを削減したり、ビルド時間を短縮したりする可能性がありました。

しかし、`buildmode=shared` を使用する際に、生成される共有ライブラリの名前が適切に決定されないという問題がありました。特に、`std` (標準ライブラリ全体)、`cmd` (Goツールチェーンのコマンド)、`all` (すべてのパッケージ) といった特別な「メタパッケージ」引数と、具体的なパッケージのインポートパスが混在する場合に、ライブラリ名の生成ロジックが曖昧であったり、予期せぬ結果を招いたりする可能性がありました。

このコミットは、この共有ライブラリ名の生成における一貫性と正確性を向上させることを目的としています。具体的には、メタパッケージは引数としてそのまま利用し、それ以外の通常のパッケージはインポートパスを基に名前を生成するという明確なルールを導入し、両者の混在を禁止することで、命名規則の堅牢化を図っています。コミットメッセージにある `Fixes #12236` は、この問題が特定の課題として認識されていたことを示唆しています。

## 前提知識の解説

*   **`go build -buildmode=shared`**: Go言語のビルドモードの一つで、指定されたGoパッケージを共有ライブラリとしてコンパイルします。生成された共有ライブラリは、他のGoプログラムが `-linkshared` オプションを使ってリンクできます。この機能は、Goプログラム間の共有ライブラリリンキングを可能にすることで、バイナリサイズの削減やビルドの高速化を目指しましたが、GoのABI（Application Binary Interface）の安定性の問題などから、実用上の課題が多く、後に非推奨となり、Go 1.20で削除されました。
*   **メタパッケージ (`std`, `cmd`, `all`)**: `go` コマンドにおいて特別な意味を持つ引数です。
    *   `std`: Goの標準ライブラリに含まれるすべてのパッケージを指します。
    *   `cmd`: Goツールチェーンに含まれるコマンド（例: `go` コマンド自体）のパッケージを指します。
    *   `all`: 現在のGoワークスペースまたはGOPATH内のすべてのパッケージを指します。
    これらのメタパッケージは、単一のパッケージではなく、複数のパッケージの集合を表します。
*   **インポートパス**: Goパッケージを一意に識別するための文字列です。例えば、`"fmt"` や `"net/http"`、`"github.com/user/repo/pkg"` のように、パッケージの場所を示します。
*   **共有ライブラリの命名規則**: オペレーティングシステムによって異なりますが、一般的に共有ライブラリは `lib` プレフィックスと `.so` (Linux), `.dylib` (macOS), `.dll` (Windows) などのサフィックスを持ちます。このコミットでは、Goのパッケージ名やインポートパスを基に、この `lib` と `.so` の間の部分を生成するロジックを扱っています。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/go/build.go` 内の `libname` 関数に集中しています。以前の `libname` 関数は、引数から共有ライブラリ名を生成する際に、メタパッケージと通常のパッケージインポートパスの区別が曖昧でした。

新しい実装では、以下のロジックが導入されています。

1.  **`isMetaPackage` 関数の導入**: `name == "std" || name == "cmd" || name == "all"` という条件で、引数がメタパッケージであるかを判定するヘルパー関数 `isMetaPackage` が追加されました。これにより、メタパッケージの識別が明確になります。
2.  **`libname` 関数のシグネチャ変更**: `libname` 関数は、引数として `args []string` に加えて `pkgs []*Package` を受け取るようになりました。これは、実際のパッケージ情報（特に `ImportPath`）を利用して名前を生成するためです。また、エラーを返す可能性があるため、戻り値に `error` が追加されました。
3.  **命名ロジックの分離**:
    *   **メタパッケージの場合**: 引数が `std`, `cmd`, `all` のいずれかである場合、その引数名がそのままライブラリ名の一部として使用されます。
    *   **非メタパッケージの場合**: 引数がメタパッケージでない場合、`pkgs` 引数から渡された `*Package` オブジェクトの `ImportPath` フィールドが使用されます。この `ImportPath` 内の `/` (スラッシュ) は `-` (ハイフン) に置換されます。これは、ファイルシステム上で有効な名前にするため、およびGoのインポートパスの階層構造をフラットな名前に変換するためです。
    *   **名前の結合**: 複数のパッケージが指定された場合、それぞれの名前は `,` (カンマ) で結合されます。
4.  **混在の禁止**: 最も重要な変更点の一つは、メタパッケージと非メタパッケージの引数を同時に指定することを禁止した点です。`libname` 関数内で `haveNonMeta` フラグを使用して、非メタパッケージが検出されたかどうかを追跡し、もしメタパッケージと非メタパッケージの両方が存在する場合はエラーを返します。これにより、命名の曖昧さを排除し、一貫した動作を保証します。
5.  **エラーハンドリング**: `libname` 関数がエラーを返すようになったため、`runBuild` および `runInstall` 関数内でそのエラーを適切に処理し、`fatalf` でユーザーにエラーメッセージを報告するようになりました。

これらの変更により、`buildmode=shared` で共有ライブラリをビルドする際の命名規則が明確になり、予期せぬライブラリ名の生成や、メタパッケージと通常のパッケージの混在による問題が解消されました。

## 変更の背景

Go言語の `go build` コマンドには、`-buildmode` というオプションがあり、様々なビルドモードをサポートしています。その一つに `shared` モードがあります。このモードは、Goのパッケージを共有ライブラリ（例: Linuxでは `.so` ファイル）としてコンパイルし、他のGoプログラムがそれらをリンクして使用できるようにすることを目的としていました。これにより、実行可能ファイルのサイズを削減したり、ビルド時間を短縮したりする可能性がありました。

しかし、`buildmode=shared` を使用する際に、生成される共有ライブラリの名前が適切に決定されないという問題がありました。特に、`std` (標準ライブラリ全体)、`cmd` (Goツールチェーンのコマンド)、`all` (すべてのパッケージ) といった特別な「メタパッケージ」引数と、具体的なパッケージのインポートパスが混在する場合に、ライブラリ名の生成ロジックが曖昧であったり、予期せぬ結果を招いたりする可能性がありました。

このコミットは、この共有ライブラリ名の生成における一貫性と正確性を向上させることを目的としています。具体的には、メタパッケージは引数としてそのまま利用し、それ以外の通常のパッケージはインポートパスを基に名前を生成するという明確なルールを導入し、両者の混在を禁止することで、命名規則の堅牢化を図っています。コミットメッセージにある `Fixes #12236` は、この問題が特定の課題として認識されていたことを示唆しています。

## 前提知識の解説

*   **`go build -buildmode=shared`**: Go言語のビルドモードの一つで、指定されたGoパッケージを共有ライブラリとしてコンパイルします。生成された共有ライブラリは、他のGoプログラムが `-linkshared` オプションを使ってリンクできます。この機能は、Goプログラム間の共有ライブラリリンキングを可能にすることで、バイナリサイズの削減やビルドの高速化を目指しましたが、GoのABI（Application Binary Interface）の安定性の問題などから、実用上の課題が多く、後に非推奨となり、Go 1.20で削除されました。
*   **メタパッケージ (`std`, `cmd`, `all`)**: `go` コマンドにおいて特別な意味を持つ引数です。
    *   `std`: Goの標準ライブラリに含まれるすべてのパッケージを指します。
    *   `cmd`: Goツールチェーンに含まれるコマンド（例: `go` コマンド自体）のパッケージを指します。
    *   `all`: 現在のGoワークスペースまたはGOPATH内のすべてのパッケージを指します。
    これらのメタパッケージは、単一のパッケージではなく、複数のパッケージの集合を表します。
*   **インポートパス**: Goパッケージを一意に識別するための文字列です。例えば、`"fmt"` や `"net/http"`、`"github.com/user/repo/pkg"` のように、パッケージの場所を示します。
*   **共有ライブラリの命名規則**: オペレーティングシステムによって異なりますが、一般的に共有ライブラリは `lib` プレフィックスと `.so` (Linux), `.dylib` (macOS), `.dll` (Windows) などのサフィックスを持ちます。このコミットでは、Goのパッケージ名やインポートパスを基に、この `lib` と `.so` の間の部分を生成するロジックを扱っています。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/go/build.go` 内の `libname` 関数に集中しています。以前の `libname` 関数は、引数から共有ライブラリ名を生成する際に、メタパッケージと通常のパッケージインポートパスの区別が曖昧でした。

新しい実装では、以下のロジックが導入されています。

1.  **`isMetaPackage` 関数の導入**: `name == "std" || name == "cmd" || name == "all"` という条件で、引数がメタパッケージであるかを判定するヘルパー関数 `isMetaPackage` が追加されました。これにより、メタパッケージの識別が明確になります。
2.  **`libname` 関数のシグネチャ変更**: `libname` 関数は、引数として `args []string` に加えて `pkgs []*Package` を受け取るようになりました。これは、実際のパッケージ情報（特に `ImportPath`）を利用して名前を生成するためです。また、エラーを返す可能性があるため、戻り値に `error` が追加されました。
3.  **命名ロジックの分離**:
    *   **メタパッケージの場合**: 引数が `std`, `cmd`, `all` のいずれかである場合、その引数名がそのままライブラリ名の一部として使用されます。
    *   **非メタパッケージの場合**: 引数がメタパッケージでない場合、`pkgs` 引数から渡された `*Package` オブジェクトの `ImportPath` フィールドが使用されます。この `ImportPath` 内の `/` (スラッシュ) は `-` (ハイフン) に置換されます。これは、ファイルシステム上で有効な名前にするため、およびGoのインポートパスの階層構造をフラットな名前に変換するためです。
    *   **名前の結合**: 複数のパッケージが指定された場合、それぞれの名前は `,` (カンマ) で結合されます。
4.  **混在の禁止**: 最も重要な変更点の一つは、メタパッケージと非メタパッケージの引数を同時に指定することを禁止した点です。`libname` 関数内で `haveNonMeta` フラグを使用して、非メタパッケージが検出されたかどうかを追跡し、もしメタパッケージと非メタパッケージの両方が存在する場合はエラーを返します。これにより、命名の曖昧さを排除し、一貫した動作を保証します。
5.  **エラーハンドリング**: `libname` 関数がエラーを返すようになったため、`runBuild` および `runInstall` 関数内でそのエラーを適切に処理し、`fatalf` でユーザーにエラーメッセージを報告するようになりました。

これらの変更により、`buildmode=shared` で共有ライブラリをビルドする際の命名規則が明確になり、予期せぬライブラリ名の生成や、メタパッケージと通常のパッケージの混在による問題が解消されました。

## コアとなるコードの解説

### `src/cmd/go/build.go` の変更

*   **`runBuild` および `runInstall` 関数**:
    *   `libname` 関数の呼び出し方が変更されました。以前は `libname(args)` のように引数のみを渡していましたが、新しいバージョンでは `libname(args, pkgs)` のように、解析されたパッケージ情報 (`pkgs`) も渡すようになりました。
    *   `libname` がエラーを返す可能性があるため、その戻り値をチェックし、エラーが発生した場合は `fatalf` を呼び出してプログラムを終了させるエラーハンドリングが追加されました。これにより、不正なライブラリ名が生成されるのを防ぎます。
*   **`isMetaPackage` 関数の追加**:
    *   この新しい関数は、与えられた文字列が `std`, `cmd`, `all` のいずれかのメタパッケージ名であるかを簡潔にチェックします。これにより、コードの可読性と保守性が向上します。
*   **`libname` 関数の大幅な改修**:
    *   **シグネチャの変更**: `func libname(args []string) string` から `func libname(args []string, pkgs []*Package) (string, error)` へと変更されました。これにより、パッケージのインポートパスを利用できるようになり、エラーを報告できるようになりました。
    *   **`appendName` クロージャ**: 内部で `appendName` というヘルパー関数が定義され、ライブラリ名の各部分をカンマで結合するロジックをカプセル化しています。
    *   **メタパッケージと非メタパッケージの分離処理**:
        *   `for _, arg := range args` ループ内で、各引数が `isMetaPackage` であるかどうかがチェックされます。
        *   メタパッケージであれば `appendName(arg)` で直接ライブラリ名に追加されます。
        *   非メタパッケージであれば `haveNonMeta = true` が設定されます。
    *   **非メタパッケージのみの場合**: `len(libname) == 0` (つまり、引数にメタパッケージが一つもなかった場合) は、`pkgs` スライス内の各パッケージの `ImportPath` を使用してライブラリ名を構築します。`strings.Replace(pkg.ImportPath, "/", "-", -1)` により、インポートパスのスラッシュがハイフンに置換されます。
    *   **混在の禁止**: `else if haveNonMeta` の条件で、メタパッケージと非メタパッケージが混在している場合に `errors.New(...)` を返してエラーとします。これにより、命名規則の曖昧さが解消されます。
    *   **戻り値**: 最終的に `lib` プレフィックスと `.so` サフィックスを付加したライブラリ名と `nil` エラー、または空文字列とエラーを返します。

### `src/cmd/go/main.go` の変更

*   `importPathsNoDotExpansion` および `matchPackages` 関数内で、以前は `a == "all" || a == "std" || a == "cmd"` のように直接文字列比較していた箇所が、新しく追加された `isMetaPackage(a)` の呼び出しに置き換えられました。これにより、メタパッケージの判定ロジックが一元化され、コードの重複が排除され、保守性が向上しています。

### `src/cmd/go/pkg_test.go` の変更

*   **`TestSharedLibName` 関数の追加**:
    *   `libname` 関数の新しいロジックを検証するための包括的なテストケースが追加されました。
    *   `testData` スライスには、メタパッケージのみ、非メタパッケージのみ、そしてメタパッケージと非メタパッケージの混在といった様々なシナリオが含まれています。
    *   各テストケースでは、期待されるライブラリ名 (`expected`) と、エラーが発生するかどうか (`expectErr`) が定義されています。
    *   テストループでは、`libname` を呼び出し、返された値とエラーが期待通りであるかを厳密にチェックしています。これにより、`libname` 関数の堅牢性と正確性が保証されます。

これらの変更は、`go build -buildmode=shared` の動作をより予測可能にし、ユーザーが意図した共有ライブラリ名を生成できるようにするための重要な改善です。

## 元コミット内容

このコミットは、以前の変更セットであるCL 101570044（ハッシュ: 2c57aaea79c4）を元に戻し、その上でスタックアロケーションのロジックを再実装しています。CL 101570044自体は、CL 104200047（ハッシュ: 318b04f28372）を元に戻すものでした。

CL 104200047の元の目的は以下の通りです。
- `malloc`（メモリ確保関数）をGo言語で実装するために、スタックアロケータを`mallocgc`（GCヒープからのメモリ確保）から分離すること。
- スタックが`malloc`中に不足した場合、新しいスタックを確保するために`malloc`が利用できないというデッドロック状態を避けること。
- スタックがGCヒープ内で最後に残った`FlagNoGC`オブジェクト（GCの対象外となるオブジェクト）であるため、スタックをGCヒープから分離することで、`allocated`/`blockboundary`ビット間の区別をなくす準備をすること（これは別の変更で対応予定）。
- Issue #7468 と #7424 を修正すること。

しかし、CL 104200047はWindows環境とレース検出器を壊す問題があったため、CL 101570044によって元に戻されました。今回のコミットは、その元に戻されたスタックアロケーションの概念を、いくつかのバグ修正を加えて再導入するものです。

## 変更の背景

Goランタイムの進化において、メモリ管理は常に重要な課題です。特に、ガベージコレクタ（GC）とメモリ確保の効率性は、Goプログラムのパフォーマンスに直結します。このコミットの背景には、以下の主要な動機があります。

1.  **`malloc`のGo言語への移行**: Goランタイムの多くの部分はC言語で書かれていましたが、Go言語自体の成熟に伴い、より多くのコンポーネントをGo言語で記述する動きがありました。`malloc`をGo言語に移行するためには、スタックアロケーションが`mallocgc`（GCヒープからのメモリ確保）に依存しないようにする必要がありました。もしスタックの拡張が必要になった際に`malloc`が呼び出され、その`malloc`がさらにスタックを必要とするような状況が発生すると、デッドロックやスタックオーバーフローのリスクが生じます。これを避けるために、スタックアロケーションの独立性が求められました。

2.  **`FlagNoGC`オブジェクトの排除**: GoのGCは、ヒープ上のオブジェクトを追跡し、不要になったメモリを解放します。しかし、一部のランタイム内部構造、特にスタックは、GCの対象外である`FlagNoGC`として扱われていました。これらのオブジェクトをGCヒープから完全に分離することで、GCの設計を簡素化し、将来的な最適化の道を開くことができました。このコミットは、スタックを`FlagNoGC`オブジェクトのリストから外すための重要なステップでした。

3.  **以前の変更のバグ修正**: 以前のスタックアロケータ分離の試み（CL 104200047）は、Windows環境での問題やレース検出器の破損といったバグを抱えていました。このコミットは、これらの問題を修正し、より堅牢なスタックアロケーションメカニズムを提供することを目的としています。具体的には、`racemalloc`の追加、フリーリストの正しい終端処理、スパン参照カウントの調整、`StackCacheSize`以上のサイズに対するキャッシュ不使用といった修正が含まれています。

これらの背景から、このコミットはGoランタイムのメモリ管理とGCのアーキテクチャを改善し、将来的な機能拡張（特に`malloc`のGo言語化）のための基盤を固める重要な一歩と言えます。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのメモリ管理、特にヒープとスタックの構造、およびガベージコレクションに関する基本的な知識が必要です。

1.  **Goランタイムのメモリ管理**:
    *   **ヒープ (Heap)**: プログラム実行中に動的に確保されるメモリ領域です。Goでは、`make`や`new`で作成されるオブジェクトや、関数間で共有されるデータなどがヒープに割り当てられます。ヒープメモリはガベージコレクタによって管理されます。
    *   **スタック (Stack)**: 各Goroutine（Goの軽量スレッド）が持つメモリ領域で、関数呼び出しの引数、ローカル変数、戻りアドレスなどが一時的に格納されます。スタックは通常、ヒープとは独立して管理され、関数の呼び出しと戻りに応じて自動的に伸縮します。Goのスタックは可変長であり、必要に応じて自動的に拡張（または縮小）されます。
    *   **`mheap`**: Goランタイムのグローバルなヒープアロケータです。OSから大きなメモリブロックを確保し、それを`MSpan`と呼ばれる単位に分割して管理します。
    *   **`mcache`**: 各P（Processor、論理CPU）に紐付けられたローカルなメモリキャッシュです。小さなオブジェクトの割り当てを高速化するために使用されます。`mcache`は`mheap`から`MSpan`を取得し、そこからオブジェクトを割り当てます。
    *   **`MSpan`**: `mheap`が管理するメモリの連続したページ群です。`MSpan`は、そのメモリがGCヒープで使用されているか（`MSpanInUse`）、スタックとして使用されているか（`MSpanStack`）、またはフリーであるか（`MSpanFree`）などの状態を持ちます。
    *   **`FlagNoGC`**: ガベージコレクタの対象外であることを示すフラグです。通常、GCはヒープ上の到達可能なオブジェクトをマークし、到達不能なオブジェクトをスイープして解放しますが、`FlagNoGC`オブジェクトはGCのサイクルから除外されます。このコミット以前は、スタックも`FlagNoGC`オブジェクトとして扱われていました。

2.  **スタックアロケーションと拡張**:
    *   GoのGoroutineスタックは、最初は比較的小さなサイズで割り当てられます。関数呼び出しが深くなったり、大きなローカル変数が使用されたりしてスタックが不足すると、ランタイムは自動的にスタックを拡張します。この拡張プロセスは、新しいより大きなスタックを確保し、古いスタックの内容を新しいスタックにコピーし、古いスタックを解放するという手順で行われます。
    *   **`FixedStack`**: GoランタイムがGoroutineに最初に割り当てるスタックの最小サイズです。
    *   **`StackCacheSize`**: スタックキャッシュのサイズを決定する定数です。このサイズ以上のスタックはキャッシュされません。
    *   **`NumStackOrders`**: スタックのサイズクラス（オーダー）の数です。スタックはサイズに応じて異なるオーダーに分類され、それぞれにフリーリストが管理されます。

3.  **GoスケジューラとM/G/Pモデル**:
    *   **G (Goroutine)**: Goの軽量スレッドです。
    *   **M (Machine)**: OSスレッドに相当します。
    *   **P (Processor)**: MがGを実行するために必要な論理プロセッサです。
    *   **`g0`スタック**: 各Mが持つ特別なスタックで、ランタイムの重要な処理（スケジューリング、GC、メモリ確保など）を実行するために使用されます。`g0`スタックは通常のGoroutineスタックとは異なり、GoコードではなくCコード（またはアセンブリ）で実行されるランタイム関数によって使用されます。このコミットでは、`mheap_alloc`や`mheap_free`といったヒープ操作が`g0`スタック上でのみ実行されるように制限されています。

4.  **Goレース検出器 (Race Detector)**:
    *   Goには、並行処理におけるデータ競合（レースコンディション）を検出するための組み込みツールであるレース検出器があります。メモリへのアクセスが複数のGoroutineによって同時に行われ、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって保護されていない場合に、データ競合が発生します。
    *   **`racemalloc()`**: レース検出器が有効な場合に、メモリ割り当てをレース検出器に通知するための関数です。スタック割り当てがレース検出器によって正しく監視されるようにするために、この関数が追加されました。

これらの前提知識を理解することで、このコミットがGoランタイムの内部でどのように機能し、どのような問題を解決しようとしているのかを深く把握することができます。

## 技術的詳細

このコミットは、Goランタイムのスタックアロケーションメカニズムを根本的に変更し、以前の試みで発生したバグを修正しています。主要な技術的変更点は以下の通りです。

1.  **スタックアロケーションの分離と専用の`MSpanStack`状態**:
    *   以前はスタックもGCヒープの一部として扱われ、`MSpanInUse`状態の`MSpan`を使用していました。このコミットでは、スタック専用の`MSpanStack`状態が導入されました。これにより、`mheap`はGCヒープ用のメモリ（`MSpanInUse`）とスタック用のメモリ（`MSpanStack`）を明確に区別して管理できるようになります。
    *   `runtime·MHeap_AllocStack`関数が新設され、スタック専用の`MSpan`を`mheap`から割り当てるようになりました。同様に、`runtime·MHeap_FreeStack`関数も追加され、スタック`MSpan`を解放します。
    *   `mheap.c`内の`MHeap_AllocSpanLocked`関数は、`MSpanInUse`と`MSpanStack`の両方の割り当てに使用される汎用的なスパン割り当てロジックを提供します。

2.  **スタックキャッシュの再設計と`MCache`への統合**:
    *   以前はグローバルな`stackcache`と`stackcachemu`（ミューテックス）を使用してスタックセグメントをキャッシュしていましたが、このコミットではスタックキャッシュが各P（プロセッサ）の`MCache`構造体内に統合されました。
    *   `MCache`に`StackFreeList stackcache[NumStackOrders]`が追加され、異なるサイズのスタックセグメントをオーダー（サイズクラス）ごとに管理します。
    *   `StackCacheSize`と`NumStackOrders`という新しい定数が`malloc.h`で定義され、スタックキャッシュの動作を制御します。`StackCacheSize`はPごとのスタックキャッシュの最大サイズを、`NumStackOrders`はキャッシュされるスタックサイズのオーダー数を定義します。
    *   `stack.c`内の`poolalloc`と`poolfree`関数は、グローバルな`stackpool`（`MSpan`のリスト）からスタックセグメントを割り当てたり解放したりする役割を担います。これらの関数は`stackpoolmu`によって保護されます。
    *   `stackcacherefill`と`stackcacherelease`関数は、Pのローカルキャッシュとグローバルな`stackpool`間でスタックセグメントを移動させる役割を担います。これにより、Pのキャッシュが過度に大きくなるのを防ぎ、未使用のスタックセグメントをグローバルプールに戻すことでメモリの再利用を促進します。
    *   `runtime·stackcache_clear`関数が追加され、`MCache`が解放される際にその中のスタックキャッシュをクリアするようになりました。

3.  **`racemalloc()`の導入**:
    *   Goのレース検出器が有効な場合、スタック割り当てが正しく監視されるように、`runtime·racemalloc`が`runtime·stackalloc`内で呼び出されるようになりました。これにより、スタックメモリへのアクセスに関するデータ競合が検出可能になります。

4.  **`poolalloc`/`poolfree`のフリーリスト終端処理の修正**:
    *   `poolalloc`と`poolfree`関数において、フリーリストの終端処理が正しく行われるように修正されました。これにより、スタックセグメントの割り当てと解放におけるバグやメモリリークが防止されます。特に、`poolalloc`でスパンからスタックを割り当てる際に、スパンのフリーリストが空になった場合にスパンをリストから削除するロジックが追加されました。

5.  **スパン参照カウントの調整**:
    *   `MSpan`の`ref`（参照カウント）がスタックアロケーションと解放の際に正しく調整されるようになりました。`MSpanStack`状態のスパンは、そのスパンから割り当てられたスタックの数に応じて`ref`が増減します。`ref`が0になった場合、そのスパンは完全にフリーとなり、`mheap`に返却されます。

6.  **`StackCacheSize`以上のサイズに対するキャッシュ不使用**:
    *   `runtime·stackalloc`関数において、要求されたスタックサイズが`FixedStack << NumStackOrders`（つまり、キャッシュされる最大のオーダーサイズ）または`StackCacheSize`以上の場合、スタックキャッシュを使用せず、直接`runtime·MHeap_AllocStack`を呼び出して`MSpan`全体を割り当てるようになりました。これにより、非常に大きなスタックがキャッシュを不必要に占有するのを防ぎます。

7.  **`g0`スタック上でのヒープ操作の強制**:
    *   `mheap_alloc`と`mheap_free`といったヒープ操作関数が、`g == g->m->g0`（現在のGoroutineがMの`g0`スタック上で実行されている）という条件でガードされるようになりました。これは、ヒープ操作中にスタックの拡張が必要になった場合に、通常のGoroutineスタック上での`malloc`呼び出しがデッドロックを引き起こす可能性を排除するためです。通常のGoroutineからのヒープ操作は、`runtime·mcall`を介して`g0`スタックに切り替えて実行されます。

これらの変更により、Goランタイムのスタック管理はより堅牢で効率的になり、将来的な`malloc`のGo言語への移行に向けた重要な基盤が築かれました。

## コアとなるコードの解説

このコミットのコアとなる変更は、スタックアロケーションの独立化と、それに伴うメモリ管理構造の再編です。

### 1. `MSpanStack`状態の導入とスタック専用の割り当て/解放

`src/pkg/runtime/malloc.h`で`MSpanStack`という新しい`MSpan`状態が導入されたことが重要です。これにより、`mheap`はGCヒープ用のメモリとスタック用のメモリを明確に区別して管理できるようになります。

```c
// src/pkg/runtime/malloc.h
enum
{
	MSpanInUse = 0, // allocated for garbage collected heap
	MSpanStack,     // allocated for use by stack allocator
	MSpanFree,
	MSpanListHead,
	MSpanDead,
};
```

これに伴い、`src/pkg/runtime/mheap.c`には`runtime·MHeap_AllocStack`と`runtime·MHeap_FreeStack`というスタック専用の割り当て・解放関数が追加されました。

```c
// src/pkg/runtime/mheap.c
MSpan*
runtime·MHeap_AllocStack(MHeap *h, uintptr npage)
{
	MSpan *s;

	if(g != g->m->g0)
		runtime·throw("mheap_allocstack not on M stack");
	runtime·lock(h);
	s = MHeap_AllocSpanLocked(h, npage); // 汎用スパン割り当て
	if(s != nil) {
		s->state = MSpanStack; // ここでMSpanStackを設定
		s->freelist = nil;
		s->ref = 0;
		mstats.stacks_inuse += s->npages<<PageShift;
	}
	runtime·unlock(h);
	return s;
}

void
runtime·MHeap_FreeStack(MHeap *h, MSpan *s)
{
	if(g != g->m->g0)
		runtime·throw("mheap_freestack not on M stack");
	s->needzero = 1;
	runtime·lock(h);
	MHeap_FreeSpanLocked(h, s); // 汎用スパン解放
	mstats.stacks_inuse -= s->npages<<PageShift;
	runtime·unlock(h);
}
```
`MHeap_AllocSpanLocked`と`MHeap_FreeSpanLocked`は、`MSpanInUse`と`MSpanStack`の両方で利用される汎用的なスパン管理ロジックを提供します。これにより、コードの重複が避けられています。

### 2. `MCache`へのスタックキャッシュ統合と`poolalloc`/`poolfree`

以前はグローバルなスタックキャッシュが存在しましたが、このコミットでは各Pの`MCache`にスタックキャッシュが統合されました。

```c
// src/pkg/runtime/malloc.h
typedef struct StackFreeList StackFreeList;
struct StackFreeList
{
	MLink *list;  // linked list of free stacks
	uintptr size; // total size of stacks in list
};

struct MCache
{
    // ...
	StackFreeList stackcache[NumStackOrders];
    // ...
};
```

`src/pkg/runtime/stack.c`では、グローバルな`stackpool`と、そこからスタックを割り当て/解放する`poolalloc`/`poolfree`関数が導入されました。

```c
// src/pkg/runtime/stack.c
static MSpan stackpool[NumStackOrders]; // グローバルなスタックプール
static Lock stackpoolmu;

static MLink*
poolalloc(uint8 order)
{
    // ...
    // stackpoolからMSpanを取得し、そこからスタックセグメントを割り当てる
    // スパンのfreelistが空になったら、スパンをstackpoolから削除
    // ...
}

static void
poolfree(MLink *x, uint8 order)
{
    // ...
    // スタックセグメントを対応するMSpanのfreelistに戻す
    // MSpanのrefが0になったら、MSpanをmheapに返却 (runtime·MHeap_FreeStack)
    // ...
}
```

`runtime·stackalloc`と`runtime·stackfree`は、この新しいキャッシュメカニズムを利用します。小さなスタックは`MCache`の`stackcache`から、必要に応じて`poolalloc`でグローバルプールから補充されます。大きなスタックは直接`MHeap_AllocStack`で割り当てられます。

```c
// src/pkg/runtime/stack.c
void*
runtime·stackalloc(G *gp, uint32 n)
{
    // ...
    if(StackCache && n < FixedStack << NumStackOrders && n < StackCacheSize) {
        // 小さなスタックはMCacheのstackcacheから取得
        // キャッシュが空ならstackcacherefillで補充
    } else {
        // 大きなスタックは直接MHeap_AllocStackで割り当て
        s = runtime·MHeap_AllocStack(&runtime·mheap, ROUND(n, PageSize) >> PageShift);
    }
    // ...
    if(raceenabled)
        runtime·racemalloc(v, n); // レース検出器の通知
    // ...
}

void
runtime·stackfree(G *gp, void *v, Stktop *top)
{
    // ...
    if(StackCache && n < FixedStack << NumStackOrders && n < StackCacheSize) {
        // 小さなスタックはMCacheのstackcacheに戻す
        // キャッシュが大きくなりすぎたらstackcachereleaseでグローバルプールに戻す
    } else {
        // 大きなスタックはMHeap_FreeStackで解放
        s = runtime·MHeap_Lookup(&runtime·mheap, v);
        runtime·MHeap_FreeStack(&runtime·mheap, s);
    }
    // ...
}
```

### 3. `g0`スタック上でのヒープ操作の強制

`mheap.c`内の`mheap_alloc`や`mheap_free`といったヒープ操作関数は、`g == g->m->g0`というチェックが追加され、`g0`スタック上でのみ実行されるように制限されました。

```c
// src/pkg/runtime/mheap.c
static MSpan*
mheap_alloc(MHeap *h, uintptr npage, int32 sizeclass, bool large)
{
	if(g != g->m->g0) // g0スタックでの実行を強制
		runtime·throw("mheap_alloc not on M stack");
    // ...
}

void
runtime·MHeap_Alloc(MHeap *h, uintptr npage, int32 sizeclass, bool large, bool needzero)
{
	MSpan *s;

	// Don't do any operations that lock the heap on the G stack.
	// It might trigger stack growth, and the stack growth code needs
	// to be able to allocate heap.
	if(g == g->m->g0) {
		s = mheap_alloc(h, npage, sizeclass, large);
	} else {
		// g0スタックに切り替えてmheap_allocを呼び出す
		g->m->ptrarg[0] = h;
		g->m->scalararg[0] = npage;
		g->m->scalararg[1] = sizeclass;
		g->m->scalararg[2] = large;
		runtime·mcall(mheap_alloc_m);
		s = g->m->ptrarg[0];
		g->m->ptrarg[0] = nil;
	}
    // ...
}
```
これにより、通常のGoroutineスタックがヒープ操作中に拡張を試み、それがさらにヒープ割り当てを必要とするというデッドロックシナリオが回避されます。

これらの変更は、Goランタイムのメモリ管理の堅牢性と効率性を向上させ、将来的な`malloc`のGo言語への移行を可能にするための重要なステップです。

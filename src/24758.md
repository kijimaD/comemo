# [インデックス 24758] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) フォームにおける重要な改善を含んでいます。具体的には、値の引数がその値自体を支配していることを確認するための新しいチェック機能が追加され、同時にPhi関数除去 (phi elimination) における既存のバグが修正されました。このバグは、冗長なPhi関数を除去する際に、最終的なソースではなく中間的なコピーを使用することで、支配関係の不変条件を破る可能性がありました。

## 変更の背景

Goコンパイラは、最適化のためにプログラムのコードをSSA (Static Single Assignment) フォームという中間表現に変換します。SSAフォームでは、各変数が一度だけ定義されるという特性があり、これによりデータフロー解析や最適化が容易になります。SSAフォームの重要な不変条件の一つに、「すべての定義はその使用を支配する」というものがあります。これは、ある変数の値が使用される際には、その値が定義された場所が必ず先に実行されている必要がある、という意味です。

このコミット以前のPhi関数除去 (phielim) の実装にはバグがあり、冗長なPhi関数を削除する際に、この支配関係の不変条件を破る可能性がありました。具体的には、Phi関数が複数のコピー元から値を受け取る場合、除去後にそのPhi関数を置き換える値として、最終的なソースではなく中間的なコピーが選択されることがありました。コミットメッセージの例では、`w = phi y z` というPhi関数が `y` と `z` の両方から値を受け取りますが、`y` と `z` はどちらも `x` のコピーです。このPhi関数を除去する際に、`w` を `Copy y` で置き換えてしまうと、`b2` (yが定義されるブロック) が `b4` (wが使用されるブロック) を支配しないため、SSAの不変条件が破られてしまいます。正しい挙動は、`w` を `Copy x` で置き換えることでした。

この問題を解決するため、コンパイラが生成するSSAフォームの正しさを検証する「引数支配チェック (arg-dominating check)」が追加されました。これにより、将来的に同様の支配関係の違反が発生した場合に早期に検出できるようになります。同時に、Phi関数除去のロジックも修正され、常に最終的なソースを追跡して正しい支配関係を維持するように変更されました。

## 前提知識の解説

### 1. 静的単一割り当て (Static Single Assignment, SSA) フォーム

SSAフォームは、コンパイラ最適化で広く用いられる中間表現です。この形式では、プログラム中の各変数への割り当て（定義）が一度だけ行われるように変換されます。例えば、元のコードで `x = 1; x = 2; y = x;` のように変数が複数回定義される場合、SSAでは `x1 = 1; x2 = 2; y1 = x2;` のように、新しい定義ごとに新しい変数名が割り当てられます。

SSAフォームの主な利点は以下の通りです。
*   **データフロー解析の簡素化:** 各変数の定義が一つしかないため、変数の値がどこから来るのかを追跡するのが容易になります。
*   **最適化の促進:** 定数伝播、共通部分式除去、デッドコード除去などの最適化がより効果的に行えます。

### 2. 支配関係 (Dominance)

コンパイラ理論において、支配関係はプログラムの制御フローグラフ (Control Flow Graph, CFG) における基本ブロック間の重要な関係です。
*   **支配 (Dominates):** 基本ブロック `A` が基本ブロック `B` を「支配する」とは、CFGの開始点から `B` へのすべてのパスが `A` を通過する場合を指します。つまり、`B` が実行されるならば、`A` は必ず先に実行されている必要があります。
*   **厳密に支配 (Strictly Dominates):** `A` が `B` を厳密に支配するとは、`A` が `B` を支配し、かつ `A` と `B` が異なる場合を指します。
*   **即時支配 (Immediately Dominates):** `A` が `B` の即時支配者であるとは、`A` が `B` を厳密に支配し、かつ `A` と `B` の間に `B` を厳密に支配する他のブロックが存在しない場合を指します。即時支配関係は支配木 (Dominator Tree) を形成します。

SSAフォームでは、「すべての定義はその使用を支配する」という重要な不変条件があります。これは、ある変数の値が使用される場所では、その変数が定義されたブロックが必ずその使用ブロックを支配していなければならない、という意味です。この不変条件が破られると、コンパイラが誤ったコードを生成する可能性があります。

### 3. Phi関数 (Phi Function)

SSAフォームを構築する際に、複数の制御フローパスが合流する点（例えば、if-else文の合流点やループの終端）で、同じ変数に異なる値が割り当てられている可能性がある場合に導入される特殊な命令です。Phi関数は、どのパスから制御が来たかに応じて、適切な値を選択します。

例: `x3 = phi(x1, x2)`
これは、「もし制御が `x1` が定義されたパスから来たなら `x1` の値を、`x2` が定義されたパスから来たなら `x2` の値を、`x3` に割り当てる」という意味になります。Phi関数は中間表現の概念であり、実際の機械語には存在しません。

### 4. Phi関数除去 (Phi Elimination)

Phi関数はSSAフォームの内部的な概念であるため、最終的な機械語を生成する前に除去する必要があります。Phi関数除去は、Phi関数を実際の移動 (move) 命令やコピー (copy) 命令に置き換えるプロセスです。このプロセスは、元のプログラムのセマンティクスを維持しつつ、支配関係の不変条件を破らないように慎重に行われる必要があります。特に、複数のPhi関数が絡み合ったり、クリティカルエッジ（複数の前任者と複数の後任者を持つエッジ）が存在したりする場合、複雑になります。

## 技術的詳細

このコミットは、GoコンパイラのSSAバックエンドにおける支配関係の不変条件の維持と検証に焦点を当てています。

### Phi関数除去のバグ

コミットメッセージの例で示されたバグは、Phi関数 `w = phi y z` を除去する際に発生しました。ここで、`y = Copy x` と `z = Copy x` であり、`x` が元の値です。
*   `b1: x = ...`
*   `b2: y = Copy x`
*   `b3: z = Copy x`
*   `b4: w = phi y z`

Phi関数除去は `w` を除去し、その使用箇所を `y` または `z` のいずれかで置き換えようとします。しかし、もし `w` を `Copy y` で置き換えてしまうと、`y` が定義されるブロック `b2` は `w` が使用されるブロック `b4` を支配していません（`b3` から `b4` に到達するパスがあるため）。これはSSAの支配関係の不変条件に違反します。

正しい解決策は、`w` を `Copy x` で置き換えることでした。`x` が定義されるブロック `b1` は、`b2` と `b3` の両方を支配し、結果として `b4` も支配するため、支配関係の不変条件が維持されます。

このコミットでは、`phielim.go` 内のロジックが修正され、Phi関数の引数が `OpCopy` である場合に、そのコピー元を再帰的に辿って最終的なソース値 (`x`) を見つけるように変更されました。これにより、Phi関数が単一の引数に簡約される際に、その引数が常に支配関係を維持する「究極のソース」となることが保証されます。

### 引数支配チェックの追加

`check.go` には、SSAフォームの正しさを検証するための新しいチェックが追加されました。このチェックは、`f.RegAlloc == nil` の場合にのみ実行されます。これは、レジスタ割り当て (register allocation) が行われると、一時的な非支配関係が発生する可能性があるためです（`regalloc.go` にTODOコメントがあるように、これは将来的に解決されるべき問題です）。

このチェックは、関数内のすべてのブロックと値について反復処理を行い、各値の引数（およびブロックの制御値）が、その値が使用されるブロックを支配していることを確認します。
*   `v.Args` の各引数 `arg` について、`arg` が定義されるブロック `x` が、`v` が定義されるブロック `y` を支配しているかを `domCheck` 関数で確認します。
*   `OpPhi` の値の場合、支配チェックの対象となるブロック `y` は、`v` が定義されるブロック `b` ではなく、そのPhi関数の引数に対応する前任者ブロック (`b.Preds[i]`) となります。これは、Phi関数の各引数が、対応する前任者ブロックから来る値であるためです。
*   ブロックの制御値 (`b.Control`) についても、それがブロック `b` を支配しているかを確認します。

`domCheck` 関数は、支配木を遡ることで支配関係を効率的に判定します。`y` からその即時支配者を繰り返し辿っていき、途中で `x` に到達すれば `x` が `y` を支配していると判断します。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/check.go` の変更

*   **`checkFunc` 内の新しいチェックブロック:**
    *   `if f.RegAlloc == nil` の条件付きで、新しい支配チェックが導入されています。これは、レジスタ割り当てフェーズが一時的に支配関係を破る可能性があるための一時的な措置です。
    *   `idom := dominators(f)` で、関数の支配木を計算します。`idom` は各ブロックの即時支配者へのマッピングです。
    *   すべてのブロック `b` とその中の値 `v` をループで処理します。
    *   各値 `v` の引数 `arg` について、`x := arg.Block` で引数が定義されるブロックを取得し、`y := b` で値 `v` が定義されるブロックを取得します。
    *   `v.Op == OpPhi` の場合、`y` は `b.Preds[i]` に設定されます。これは、Phi関数の `i` 番目の引数は、`i` 番目の前任者ブロックから来る値であるため、その前任者ブロックが引数を支配しているかをチェックする必要があるからです。
    *   `!domCheck(f, idom, x, y)` が真の場合、つまり引数 `x` が使用箇所 `y` を支配していない場合、`f.Fatalf` でエラーを報告し、コンパイラを停止させます。
    *   ブロックの制御値 (`b.Control`) についても同様に支配チェックを行います。

*   **`domCheck` 関数:**
    *   `domCheck(f *Func, idom []*Block, x, y *Block) bool` は、ブロック `x` がブロック `y` を支配するかどうかを報告するヘルパー関数です（`x == y` の場合も含む）。
    *   `y != f.Entry && idom[y.ID] == nil` の場合、`y` は到達不能なブロックであるため、支配チェックは常に真を返します（無視されます）。
    *   無限ループ `for {}` を使用して、`y` からその即時支配者を繰り返し辿ります。
    *   `x == y` になれば、`x` が `y` を支配しているため `true` を返します。
    *   `y` が `nil` になれば、`x` に到達せずに支配木の根に達したことを意味するため、`x` は `y` を支配していないと判断し `false` を返します。

### `src/cmd/compile/internal/ssa/phielim.go` の変更

*   `phielim` 関数内のPhi関数処理ロジックが変更されています。
*   以前は `args := newSparseSet(f.NumValues())` を使用してPhi関数の引数を収集していましたが、新しいコードでは `argSet := newSparseSet(f.NumValues())` と `var args []*Value` を組み合わせて使用しています。
*   `for _, x := range v.Args` ループ内で、各引数 `x` が `OpCopy` である限り、`x = x.Args[0]` を実行してコピー元を再帰的に辿り、最終的なソース値を見つけます。これにより、`Copy y` のような中間的な値ではなく、`x` のような究極のソースが確実に取得されます。
*   `if x != v && !argSet.contains(x.ID)` の条件で、Phi関数自体 (`v`) ではない、かつまだ収集されていない引数のみを `argSet` に追加し、`args` スライスに格納します。これにより、Phi関数が自身を引数として持つ場合（冗長なPhi関数の一種）や、重複する引数を適切に処理します。
*   `if len(args) == 1` の条件で、Phi関数が最終的に単一の引数に簡約された場合、そのPhi関数 `v` の操作を `OpCopy` に変更し、`v.SetArgs1(args[0])` を呼び出して、簡約された単一の引数を設定します。この `args[0]` は、上記のロジックによって究極のソース値であることが保証されます。

これらの変更により、Phi関数除去がSSAの支配関係の不変条件を維持しつつ、正しく機能するようになります。

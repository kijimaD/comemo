image/jpeg: reconstruct progressive images even if incomplete.

Fixes #14522.

As I said on that issue:

----
This is a progressive JPEG image. There are two dimensions of
progressivity: spectral selection (variables zs and ze in scan.go,
ranging in [0, 63]) and successive approximation (variables ah and al in
scan.go, ranging in [0, 8), from LSB to MSB, although ah=0 implicitly
means ah=8).

For this particular image, there are three components, and the SOS
markers contain this progression:

zs, ze, ah, al:  0  0 0 0       components: 0, 1, 2
zs, ze, ah, al:  1 63 0 0       components: 1
zs, ze, ah, al:  1 63 0 0       components: 2
zs, ze, ah, al:  1 63 0 2       components: 0
zs, ze, ah, al:  1 10 2 1       components: 0
zs, ze, ah, al: 11 63 2 1       components: 0
zs, ze, ah, al:  1 10 1 0       components: 0

The combination of all of these is complete (i.e. spectra 0 to 63 and
bits 8 exclusive to 0) for components 1 and 2, but it is incomplete for
component 0 (the luma component). In particular, there is no data for
component 0, spectra 11 to 63 and bits 1 exclusive to 0.

The image/jpeg code, as of Go 1.6, waits until both dimensions are
complete before performing the de-quantization, IDCT and copy to an
*image.YCbCr. This is the "if zigEnd != blockSize-1 || al != 0 { ...
continue }" code and associated commentary in scan.go.

Almost all progressive JPEG images end up complete in both dimensions
for all components, but this particular image is incomplete for
component 0, so the Go code never writes anything to the Y values of the
resultant *image.YCbCr, which is why the broken output is so dark (but
still looks recognizable in terms of red and blue hues).

My reading of the ITU T.81 JPEG specification (Annex G) doesn't
explicitly say that this is a valid image, but it also doesn't rule it
out.

In any case, the fix is, for progressive JPEG images, to always
reconstruct the decoded blocks (by performing the de-quantization, IDCT
and copy to an *image.YCbCr), regardless of whether or not they end up
complete. Note that, in Go, the jpeg.Decode function does not return
until the entire image is decoded, so we still only want to reconstruct
each block once, not once per SOS (Start Of Scan) marker.
----

A test image was also added, based on video-001.progressive.jpeg. When
decoding that image, inserting a

println("nComp, zs, ze, ah, al:", nComp, zigStart, zigEnd, ah, al)

into decoder.processSOS in scan.go prints:

nComp, zs, ze, ah, al: 3 0 0 0 1
nComp, zs, ze, ah, al: 1 1 5 0 2
nComp, zs, ze, ah, al: 1 1 63 0 1
nComp, zs, ze, ah, al: 1 1 63 0 1
nComp, zs, ze, ah, al: 1 6 63 0 2
nComp, zs, ze, ah, al: 1 1 63 2 1
nComp, zs, ze, ah, al: 3 0 0 1 0
nComp, zs, ze, ah, al: 1 1 63 1 0
nComp, zs, ze, ah, al: 1 1 63 1 0
nComp, zs, ze, ah, al: 1 1 63 1 0

In other words, video-001.progressive.jpeg contains 10 different scans.
This little program below drops half of them (remembering to keep the
"\xff\xd9" End of Image marker):

----
package main

import (
        "bytes"
        "io/ioutil"
        "log"
)

func main() {
        sos := []byte{0xff, 0xda}
        eoi := []byte{0xff, 0xd9}

        src, err := ioutil.ReadFile("video-001.progressive.jpeg")
        if err != nil {
                log.Fatal(err)
        }
        b := bytes.Split(src, sos)
        println(len(b)) // Prints 11.
        dst := bytes.Join(b[:5], sos)
        dst = append(dst, eoi...)
        if err := ioutil.WriteFile("video-001.progressive.truncated.jpeg", dst, 0666); err != nil {
                log.Fatal(err)
        }
}
----

The video-001.progressive.truncated.jpeg was converted to png via
libjpeg and ImageMagick:

djpeg -nosmooth video-001.progressive.truncated.jpeg > tmp.tga
convert tmp.tga video-001.progressive.truncated.png
rm tmp.tga

## 変更の背景

このコミットは、Go言語の標準ライブラリ `image/jpeg` パッケージにおける、プログレッシブJPEG画像のデコードに関するバグ（Issue #14522）を修正するために導入されました。Go 1.6以前の `image/jpeg` パッケージは、プログレッシブJPEG画像をデコードする際に、すべてのコンポーネント（輝度Y、色差Cb、Cr）のすべてのプログレッシブ次元（スペクトル選択と逐次近似）が完全にデコードされるまで、最終的な画像再構築（逆量子化、逆離散コサイン変換 (IDCT)、`*image.YCbCr` へのコピー）を遅延させていました。

しかし、一部のプログレッシブJPEG画像は、特定のコンポーネント（特に輝度コンポーネント）において、すべてのプログレッシブ次元が完全に提供されない場合があります。このような「不完全な」プログレッシブJPEG画像に対して、Goのデコーダは最終的な画像再構築処理をスキップしてしまい、結果として画像が正しく表示されない（例えば、輝度情報が欠落して非常に暗くなる）という問題が発生していました。

この問題は、ITU T.81 JPEG仕様がこのような不完全な画像を明示的に無効とはしていないため、Goのデコーダがより堅牢に、仕様の曖昧な部分にも対応できるようにする必要があるという認識から修正されました。

## 前提知識の解説

### JPEG画像形式

JPEG (Joint Photographic Experts Group) は、主に写真などの自然画像を圧縮するための標準的な画像形式です。JPEGには、大きく分けて「ベースラインJPEG」と「プログレッシブJPEG」の2つの主要なエンコーディング方式があります。

### プログレッシブJPEG (Progressive JPEG)

プログレッシブJPEGは、画像を複数回に分けて段階的に表示する方式です。これにより、インターネットなどの低速な回線環境でも、ユーザーはまず低品質ながら画像全体を素早く確認でき、データがダウンロードされるにつれて徐々に詳細が追加され、最終的に高品質な画像が表示されます。これは、画像が上から下へと順に表示されるベースラインJPEGとは対照的です。

プログレッシブJPEGのプログレッシブ性（段階的な表示）は、以下の2つの次元で実現されます。

1.  **スペクトル選択 (Spectral Selection)**:
    *   JPEG圧縮では、画像を8x8ピクセルのブロックに分割し、各ブロックに対して離散コサイン変換 (DCT) を適用します。DCTの結果は、DC成分（平均色）と63個のAC成分（高周波成分、詳細情報）からなる64個の係数（周波数スペクトル）になります。
    *   スペクトル選択では、これらの係数をグループ化し、まず低周波成分（大まかな形状）を送信し、次に高周波成分（細かいディテール）を送信します。
    *   コミットメッセージ中の `zs` (zig-zag start) と `ze` (zig-zag end) は、このスペクトル選択の範囲を示します。`zs` は送信する係数の開始インデックス、`ze` は終了インデックスで、これらは0から63の範囲を取ります。

2.  **逐次近似 (Successive Approximation)**:
    *   逐次近似では、各DCT係数のビットプレーン（ビットごとの情報）を段階的に送信します。まず、最も重要なビット（MSB: Most Significant Bit）を送信し、次に重要度の低いビット（LSB: Least Significant Bit）を送信します。これにより、まず粗い近似値が提供され、徐々に精度が向上します。
    *   コミットメッセージ中の `ah` (approximation high) と `al` (approximation low) は、この逐次近似の範囲を示します。`ah` は現在デコードされているビットの最も高い位置（MSB側）、`al` は最も低い位置（LSB側）を示し、これらは0から7の範囲を取ります（`ah=0` は暗黙的に `ah=8` を意味することがあります）。

### JPEGデコードのプロセス

JPEGデコードの一般的な流れは以下の通りです。

1.  **ハフマン復号 (Huffman Decoding)**: 圧縮されたデータストリームからハフマン符号を復号し、DCT係数の差分値とゼロランレングス情報を取得します。
2.  **逆量子化 (Dequantization)**: 量子化されたDCT係数を、量子化テーブルを使って元のスケールに戻します。
3.  **逆離散コサイン変換 (IDCT: Inverse Discrete Cosine Transform)**: 逆量子化された係数を空間ドメインのピクセル値に戻します。これにより、8x8ピクセルのブロックが得られます。
4.  **色空間変換 (Color Space Conversion)**: 通常、JPEGはY'CbCr色空間でエンコードされているため、これをRGBなどの表示可能な色空間に変換します。
5.  **画像再構築 (Image Reconstruction)**: 変換されたピクセルブロックを組み合わせて最終的な画像を形成します。

### `image.YCbCr`

Go言語の `image` パッケージでは、Y'CbCr色空間の画像を表現するために `image.YCbCr` 型が使用されます。Yは輝度（明るさ）、CbとCrは色差（青と赤の成分）を表します。

## 技術的詳細

Go 1.6以前の `image/jpeg` パッケージのプログレッシブJPEGデコーダは、`scan.go` 内の `processSOS` メソッドで、各8x8ブロックのデコードが完了したかどうかを `if zigEnd != blockSize-1 || al != 0` という条件で判断していました。

*   `zigEnd != blockSize-1`: これは、スペクトル選択が全ての周波数成分（0から63）をカバーしていない、つまり `ze` が `blockSize-1` (63) に達していないことを意味します。
*   `al != 0`: これは、逐次近似が最も低いビット（LSB）までデコードされていないことを意味します。

この条件が真の場合、デコーダは現在のブロックの係数を `d.progCoeffs` に保存するだけで、逆量子化、IDCT、および `*image.YCbCr` へのコピーといった最終的な画像再構築処理をスキップし、`continue` していました。これは、`jpeg.Decode` 関数が画像全体がデコードされるまで戻らないため、途中の段階で部分的な画像を再構築しても無駄な計算になるという考えに基づいています。

しかし、コミットメッセージで示された特定の不完全なプログレッシブJPEG画像では、輝度コンポーネント（コンポーネント0）の一部スペクトル（`zs` 11から `ze` 63）とビット（`al` 1）のデータが欠落していました。このため、上記の条件が常に真となり、輝度コンポーネントのブロックは最終的な再構築処理を一度も実行されませんでした。結果として、`*image.YCbCr` のY値（輝度）が初期値のままとなり、画像が非常に暗く表示されるというバグが発生していました。

ITU T.81 JPEG仕様は、このような不完全なプログレッシブ画像を明示的に禁止しているわけではないため、Goのデコーダはこのようなケースでも画像を再構築すべきであると判断されました。

修正の核心は、プログレッシブJPEG画像の場合、デコードされたブロックの係数が不完全であっても、常に逆量子化、IDCT、および `*image.YCbCr` へのコピーを実行するように変更することです。ただし、`jpeg.Decode` が一度の呼び出しで画像全体をデコードするという性質は変わらないため、各ブロックの再構築はSOS (Start Of Scan) マーカーごとに複数回行うのではなく、最終的に一度だけ行われるように設計されています。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

1.  **`src/image/decode_test.go`**:
    *   新しいテストケース `{"testdata/video-001.progressive.truncated.png", "testdata/video-001.progressive.truncated.jpeg", 8 << 8}` が追加されました。これは、不完全なプログレッシブJPEGが正しくデコードされることを検証するためのものです。

2.  **`src/image/jpeg/reader.go`**:
    *   `decoder.decode` メソッド内で、プログレッシブJPEGの場合に `d.reconstructProgressiveImage()` メソッドを呼び出すロジックが追加されました。これは、すべてのSOSマーカーが処理された後に、蓄積されたブロックを再構築するためのエントリポイントとなります。

3.  **`src/image/jpeg/scan.go`**:
    *   `decoder.processSOS` メソッド内の、プログレッシブJPEGのブロック再構築をスキップする条件 `if zigEnd != blockSize-1 || al != 0 { ... continue }` が削除されました。
    *   代わりに、プログレッシブJPEGの場合、デコードされた係数ブロックを `d.progCoeffs` に保存する処理は残しつつ、最終的な再構築処理（逆量子化、IDCT、`*image.YCbCr` へのコピー）は `continue` せずに、`reconstructBlock` メソッドに委譲されるようになりました。
    *   新しいメソッド `reconstructProgressiveImage()` が追加されました。このメソッドは、すべてのコンポーネントのすべてのブロックに対して、蓄積された係数を使用して `reconstructBlock` を呼び出し、最終的な画像再構築を行います。
    *   新しいメソッド `reconstructBlock(b *block, bx, by, compIndex int) error` が追加されました。このメソッドは、与えられた係数ブロック `b` に対して、逆量子化、IDCT、および `*image.YCbCr` へのピクセル値のコピーを実行します。これは、以前 `processSOS` 内に直接記述されていた再構築ロジックを分離したものです。

4.  **`src/image/testdata/video-001.progressive.truncated.jpeg` および `src/image/testdata/video-001.progressive.truncated.png`**:
    *   不完全なプログレッシブJPEGのテストデータとその期待されるPNG出力が追加されました。

## コアとなるコードの解説

このコミットの核心は、プログレッシブJPEGのデコードフローを変更し、不完全なスキャンであっても最終的な画像再構築を保証することです。

以前のコードでは、`processSOS` 関数内で各8x8ブロックの係数を処理する際、プログレッシブJPEGかつ `zigEnd != blockSize-1 || al != 0` (つまり、スペクトル選択または逐次近似が完了していない) の場合、逆量子化やIDCTなどの重い処理をスキップしていました。これは、`jpeg.Decode` が最終的に完全な画像を返すため、途中の不完全な段階で再構築しても無駄であるという最適化の意図がありました。

しかし、この最適化が、一部のコンポーネントが「不完全なまま」で終わるプログレッシブJPEGに対して問題を引き起こしました。例えば、輝度コンポーネントの特定の周波数帯域やビットプレーンがデータストリームに存在しない場合、上記の条件が最後まで真のままとなり、そのコンポーネントのブロックは一度も逆量子化やIDCTが行われず、結果として画像が破損していました。

新しいコードでは、この `if zigEnd != blockSize-1 || al != 0 { ... continue }` という条件を削除し、`processSOS` 内では常にデコードされた係数ブロックを `d.progCoeffs` に保存するようにしました。そして、`processSOS` の処理がすべて完了し、すべてのSOSマーカーが処理された後、`decoder.decode` メソッドから `d.reconstructProgressiveImage()` を呼び出すように変更しました。

`reconstructProgressiveImage()` メソッドは、`d.progCoeffs` に蓄積されたすべてのコンポーネントのすべてのブロックに対してループを実行し、新しく導入された `reconstructBlock` メソッドを呼び出します。

`reconstructBlock` メソッドは、以前 `processSOS` 内に直接記述されていた逆量子化、IDCT、および `*image.YCbCr` へのピクセル値のコピー処理をカプセル化したものです。これにより、プログレッシブJPEGのすべてのスキャンが完了した後、一度だけ、蓄積された（たとえ不完全であっても）係数データに基づいて各ブロックの最終的な再構築が行われるようになります。

この変更により、Goの `image/jpeg` デコーダは、ITU T.81 JPEG仕様の曖昧な部分に対応し、不完全なプログレッシブJPEG画像であっても、利用可能なすべてのデータを用いて可能な限り最良の画像を再構築できるようになりました。これにより、以前は破損して表示されていた画像も正しく（または、データが欠落している部分を除いて）表示されるようになります。

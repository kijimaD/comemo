## 元コミット内容

Goランタイムの`TestEnsureDropM`テストが、WindowsおよびPlan 9環境で実行されないように変更されました。このテストは、`asm_GOARCH.s`というアセンブリコードに依存しており、これらのプラットフォームではビルドされないため、テストの実行は不要であると判断されました。この変更は、Issue #13991を修正するものです。

## 変更の背景

このコミットの背景には、Goのテストスイートの効率性と正確性の向上が挙げられます。`TestEnsureDropM`は、Cgo（GoとC言語の相互運用機能）における特定のランタイム動作、特にCからGoへのコールバックシーケンスで同じM（Machine、OSスレッドを表すGoランタイムの抽象化）が使用されることを保証するためのテストです。このテストは、`asm_GOARCH.s`というアーキテクチャ固有のアセンブリコードに依存しています。

しかし、WindowsやPlan 9といった特定のオペレーティングシステムでは、このアセンブリコードがビルドされない、あるいはそのテスト対象となる動作が異なる場合があります。このような環境でテストを実行しようとすると、ビルドエラーや無関係なテスト失敗が発生し、CI/CDパイプラインのノイズとなったり、開発者の時間を無駄にしたりする可能性があります。

Issue #13991は、まさにこの問題、つまり`TestEnsureDropM`が特定の環境で適切に動作しない、あるいはビルドできないという問題を報告していたと考えられます。このコミットは、テストが関連性のないプラットフォームで実行されるのを防ぐことで、テストスイートの信頼性を高め、開発者がより重要な問題に集中できるようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムおよびテストに関する知識が必要です。

1.  **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するシステムです。スケジューラ（Goroutineの管理）、メモリ管理（ガベージコレクション）、Cgoとの連携などが含まれます。
2.  **Goroutine, M, P**: Goランタイムのスケジューラは、Goroutine（軽量スレッド）、M（Machine、OSスレッド）、P（Processor、論理CPU）という3つの主要な抽象化を使用します。
    *   **Goroutine (G)**: Goの並行処理の単位。非常に軽量で、数百万個作成することも可能です。
    *   **M (Machine)**: OSスレッドに相当します。Goランタイムは、OSスレッド上でGoroutineを実行します。Cgo呼び出しでは、Cコードが実行される間、MはGoスケジューラから切り離されることがあります。
    *   **P (Processor)**: 論理CPUに相当し、Goroutineを実行するためのコンテキストを提供します。MはPにアタッチされてGoroutineを実行します。
3.  **Cgo**: GoプログラムからC言語のコードを呼び出す、またはC言語のコードからGoの関数を呼び出すためのメカニズムです。Cgoを使用すると、GoのランタイムとCのランタイムの間でコンテキストの切り替えが発生し、Mの管理が複雑になることがあります。
4.  **`asm_GOARCH.s`**: Goのランタイムには、特定のアーキテクチャ（例: `amd64`, `arm`, `arm64`）向けに最適化されたアセンブリコードが含まれています。これらのファイルは、低レベルの操作（コンテキストスイッチ、システムコールなど）を効率的に実行するために使用されます。`GOARCH`は、ビルドターゲットのアーキテクチャを示します。
5.  **`runtime.GOOS`**: Goプログラムが実行されているオペレーティングシステムを示す環境変数です（例: `"linux"`, `"windows"`, `"darwin"`, `"plan9"`）。Goのコード内でこの値を使って、OS固有の処理を分岐させることができます。
6.  **ビルドタグ (`+build` directives)**: Goのソースファイルに記述される特殊なコメントで、特定の条件（OS、アーキテクチャ、カスタムタグなど）が満たされた場合にのみファイルをビルドに含めるように指示します。例えば、`// +build linux,amd64` はLinuxかつAMD64アーキテクチャの場合にのみファイルをビルドします。`!plan9,!windows` はPlan 9とWindows以外のOSでビルドすることを意味します。
7.  **`t.Skipf`**: Goのテストフレームワーク (`testing`パッケージ) の機能で、特定の条件が満たされた場合にテストをスキップするために使用されます。スキップ理由をフォーマットされた文字列で出力できます。

## 技術的詳細

このコミットは、Goのテストスイートにおけるクロスプラットフォーム互換性の問題を解決するために、条件付きコンパイルと条件付きテスト実行のメカニズムを導入しています。

`TestEnsureDropM`テストは、CgoコールバックにおけるMの永続性を検証することを目的としています。具体的には、CコードからGoコードへの複数のコールバックが、常に同じM（OSスレッド）上で実行されることを期待しています。これは、特にARMおよびARM64アーキテクチャで問題となったIssue #13881の根本原因に対処するためのものです。この問題は、Cgoコールバック中にMが不適切に解放され、新しいMが割り当てられることで発生していました。

しかし、このテストの内部実装は、`asm_GOARCH.s`というアセンブリコードに深く依存しています。このアセンブリコードは、Goランタイムの低レベルなMの管理やコンテキストスイッチに関連する処理を直接操作するため、OSやアーキテクチャに強く依存します。WindowsやPlan 9といったOSでは、このアセンブリコードがビルドシステムによってサポートされていないか、あるいはそのOSのカーネルやスレッドモデルとの互換性がないため、テスト自体がビルドできないか、あるいは意味をなさない可能性があります。

このコミットでは、以下の2つのアプローチでこの問題を解決しています。

1.  **`src/runtime/crash_cgo_test.go` 内でのテストスキップ**:
    `TestEnsureDropM`関数の冒頭に`switch runtime.GOOS`文を追加し、現在のOSが`"windows"`または`"plan9"`である場合に`t.Skipf`を呼び出してテストをスキップするようにしました。これにより、これらのプラットフォームではテストが実行されず、無用なエラーや警告が回避されます。これは、テストがビルドはできるが、実行時に意味がない、または失敗することが分かっている場合に有効な戦略です。

2.  **`src/runtime/testdata/testprogcgo/dropm.go` へのビルドタグの追加**:
    `dropm.go`ファイルは、`TestEnsureDropM`が実行するテストプログラムの一部です。このファイルの先頭に`// +build !plan9,!windows`というビルドタグを追加しました。このタグは、Goのビルドシステムに対して、「このファイルはPlan 9とWindows以外のOSでのみコンパイルに含める」と指示します。これにより、これらのプラットフォームでは`dropm.go`自体がビルドされなくなり、アセンブリコードの依存関係によるビルドエラーを根本的に回避できます。

これらの変更により、Goのテストスイートは、各プラットフォームの特性に合わせてより堅牢かつ効率的に動作するようになります。

## コアとなるコードの解説

### `src/runtime/crash_cgo_test.go` の変更

`TestEnsureDropM` 関数は、Goのテストフレームワーク (`testing` パッケージ) に従って定義されたテスト関数です。この関数は、Cgoの特定の動作を検証するために設計されています。

追加されたコードブロック:

```go
	switch runtime.GOOS {
	case "windows", "plan9":
		t.Skipf("skipping dropm test on %s", runtime.GOOS)
	}
```

この`switch`文は、現在のオペレーティングシステム (`runtime.GOOS`) の値に基づいて処理を分岐させます。
*   もし`runtime.GOOS`が`"windows"`または`"plan9"`である場合、`t.Skipf`が呼び出されます。
*   `t.Skipf`は、テストをスキップし、指定されたフォーマット文字列 (`"skipping dropm test on %s"`) と引数 (`runtime.GOOS`) を使ってスキップ理由を出力します。これにより、これらのOS上では`TestEnsureDropM`の残りのロジック（`runTestProg`の呼び出しなど）は実行されません。

この変更は、テストが実行時に特定のOSで意味をなさない、または失敗することが既知である場合に、テストスイートの実行時間を短縮し、誤解を招く失敗を避けるための標準的なプラクティスです。

### `src/runtime/testdata/testprogcgo/dropm.go` の変更

ファイルの先頭に追加された行:

```go
// +build !plan9,!windows
```

これはGoのビルドタグ（またはビルド制約）です。
*   `+build` ディレクティブは、Goコンパイラに対して、このソースファイルをビルドに含めるべきかどうかを指示します。
*   `!plan9` は「Plan 9ではない」ことを意味します。
*   `!windows` は「Windowsではない」ことを意味します。
*   カンマで区切られた条件は論理ANDとして扱われるため、`!plan9,!windows` は「Plan 9でもなく、かつWindowsでもない」場合にのみこのファイルをビルドに含める、という意味になります。

`dropm.go`は`TestEnsureDropM`テストが呼び出す外部プログラムの一部であるため、このビルドタグを追加することで、WindowsやPlan 9環境ではこのファイル自体がコンパイルされなくなります。これにより、このファイルが依存する可能性のあるアセンブリコードがこれらのOSで利用できないことによるビルドエラーを、テスト実行以前のコンパイル段階で完全に回避できます。これは、テストが特定のプラットフォームでビルドすらできない場合に非常に効果的な戦略です。

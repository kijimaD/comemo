# [インデックス 17736] ファイルの概要

このコミットは、Goコンパイラ (`gc`) およびGoリンカ (`5l`, `6l`, `8l`, `ld`) に `-installsuffix` フラグのサポートを追加し、`go` ツールが `build` および `install` コマンドでこのフラグを適切に渡すようにするものです。これにより、異なるビルド設定（特に `-race` フラグを使用する場合）で生成されたパッケージが、互いに衝突することなく異なるディレクトリにインストールされるようになります。

## 元コミット内容

Goコンパイラ (`gc`) とリンカ (`5l`, `6l`, `8l`) に `-installsuffix` フラグを追加し、`go` ツールが `build` および `install` コマンド実行時にこのフラグを渡すように変更します。このフラグは、`-race` フラグが指定されている場合、そのサフィックスを上書きする機能も持ちます。

## 変更の背景

Goのビルドシステムでは、コンパイルされたパッケージ（`.a` ファイル）は `$GOROOT/pkg` または `$GOPATH/pkg` の下に、`{GOOS}_{GOARCH}` の形式のディレクトリに保存されます。例えば、Linux 64-bit環境であれば `linux_amd64` のようになります。

Go 1.1で導入されたデータ競合検出機能（Race Detector）を有効にする `-race` フラグを使用すると、コンパイルされたパッケージは通常とは異なるランタイムライブラリにリンクされます。このため、`-race` フラグを付けてビルドされたパッケージと、そうでないパッケージが同じディレクトリにインストールされると、互いに上書きしてしまい、予期せぬビルドエラーやランタイムエラーを引き起こす可能性がありました。

この問題を解決するため、`-race` フラグが指定された場合には、パッケージのインストールパスに `_race` というサフィックスが自動的に追加されるようになりました（例: `linux_amd64_race`）。しかし、ユーザーが任意のサフィックスを指定して、異なるビルド設定（例えば、異なるCコンパイラでビルドされたCgoパッケージなど）で生成されたパッケージを区別してインストールしたいというニーズがありました。

このコミットは、そのニーズに応えるために `-installsuffix` フラグを導入します。これにより、ユーザーはパッケージのインストールディレクトリに任意のサフィックスを追加できるようになり、`-race` フラグによる自動サフィックスを上書きすることも可能になります。これは、特にCI/CD環境や、複数の異なるビルド設定を管理する必要がある場合に有用です。

## 前提知識の解説

*   **Goツールチェーン**: Go言語のプログラムをビルド、テスト、実行するためのコマンド群です。主要なものに `go build` (ビルド), `go install` (ビルドしてインストール), `go run` (ビルドして実行), `go test` (テスト) などがあります。
*   **`gc` (Go Compiler)**: Goソースコードをコンパイルしてオブジェクトファイル（`.o`）やアーカイブファイル（`.a`）を生成するGo言語の公式コンパイラです。
*   **`ld` (Go Linker)**: Goのオブジェクトファイルやアーカイブファイルをリンクして実行可能ファイルを生成するGo言語の公式リンカです。Goのリンカは、ターゲットアーキテクチャごとに `5l` (ARM), `6l` (x86-64), `8l` (x86) のように名前が付けられていました。現在は `cmd/link` に統合されています。
*   **`go install`**: ソースコードをコンパイルし、生成されたバイナリ（実行可能ファイルまたはパッケージアーカイブ）を `$GOBIN` または `$GOPATH/bin` (実行可能ファイルの場合) および `$GOROOT/pkg` または `$GOPATH/pkg` (パッケージアーカイブの場合) にインストールするコマンドです。
*   **パッケージキャッシュ**: Goは、コンパイル済みのパッケージをキャッシュすることで、ビルド時間を短縮します。これらのキャッシュされたパッケージは、通常 `$GOROOT/pkg` または `$GOPATH/pkg` の下の、OSとアーキテクチャに応じたディレクトリに保存されます。
*   **`-race` フラグ (Race Detector)**: Go 1.1で導入されたデータ競合検出機能です。このフラグを付けてビルドすると、ランタイムがデータ競合を検出し、報告するようになります。`-race` を有効にすると、特別なランタイムライブラリが使用されるため、通常のビルドとは異なるパッケージパスにインストールする必要があります。
*   **`GOROOT` と `GOPATH`**:
    *   `GOROOT`: GoのSDKがインストールされているディレクトリです。標準ライブラリのパッケージがここにあります。
    *   `GOPATH`: ユーザーのGoワークスペースのルートディレクトリです。サードパーティのパッケージやユーザー自身のプロジェクトのパッケージがここに保存されます。

## 技術的詳細

このコミットの主要な変更点は、Goツールチェーン全体で `-installsuffix` フラグを認識し、その値をパッケージのインストールパスに反映させることです。

1.  **コンパイラ (`gc`) とリンカ (`5l`, `6l`, `8l`, `ld`) へのフラグ追加**:
    *   各リンカの `obj.c` ファイルに `flagstr("installsuffix", "pkg directory suffix", &flag_installsuffix);` が追加され、`-installsuffix` コマンドライン引数をパースして `flag_installsuffix` 変数に格納するようになります。
    *   コンパイラの `src/cmd/gc/go.h` に `EXTERN char* flag_installsuffix;` が追加され、`src/cmd/gc/lex.c` でこのフラグがパースされます。
    *   これにより、コンパイラとリンカは、ビルド時にどのサフィックスを使用すべきかを知ることができます。

2.  **パッケージパス解決ロジックの変更 (`src/cmd/gc/lex.c`, `src/cmd/ld/lib.c`)**:
    *   `findpkg` 関数（コンパイラがパッケージを検索する際に使用）と `libinit` 関数（リンカがライブラリパスを初期化する際に使用）のロジックが変更されます。
    *   以前は、`flag_race` が設定されている場合にのみ `_race` サフィックスが追加されていました。
    *   変更後、`flag_installsuffix` が設定されている場合は、その値が優先的にサフィックスとして使用されます。`flag_installsuffix` が設定されておらず、かつ `flag_race` が設定されている場合にのみ `_race` が使用されます。
    *   これにより、パッケージの検索パスが `GOROOT/pkg/{GOOS}_{GOARCH}{suffix}/{package}.a` の形式になります。`suffix` は `_` + `installsuffix` の値、または `_race` になります。

3.  **`go` ツールからのフラグ伝播 (`src/cmd/go/build.go`, `src/cmd/go/testflag.go`)**:
    *   `src/cmd/go/build.go` の `gcToolchain.gc` および `gcToolchain.ld` 関数が変更され、`buildContext.InstallSuffix` の値が存在する場合、コンパイラ (`gc`) とリンカ (`ld`) に `-installsuffix` フラグを渡すようになります。
    *   `src/cmd/go/testflag.go` に `installsuffix` がテストフラグとして追加され、`go test` コマンドでもこのフラグが利用可能になります。
    *   `go` ツールは、`go build -installsuffix=mysuffix` のようにコマンドラインで指定された `-installsuffix` の値を `buildContext.InstallSuffix` に設定し、それを下位のコンパイラやリンカに伝播させます。

この変更により、Goのビルドシステムは、異なるビルド設定で生成されたパッケージを、ファイルシステム上で明確に分離して管理できるようになります。これは、特に異なるコンパイルオプション（例: Race Detectorの有無、Cgoの特定のビルド設定など）を持つ複数のバージョンのライブラリを共存させたい場合に不可欠です。

## コアとなるコードの解説

### `src/cmd/gc/lex.c` の変更

この変更は、Goコンパイラがパッケージのアーカイブファイル（`.a`）を検索する際のロジックを修正しています。

*   **変更前**:
    *   `race` という変数が定義され、`flag_race` が真の場合に `_race` が設定されていました。
    *   パッケージパスは `"%s/pkg/%s_%s%s/%Z.a"` の形式で構築され、`race` の値が直接埋め込まれていました。つまり、`_race` サフィックスは `flag_race` の有無によってのみ決定されていました。

*   **変更後**:
    *   `suffix` と `suffixsep` という新しい変数が導入されます。
    *   **優先順位**:
        1.  `flag_installsuffix` が `nil` でない（つまり、`-installsuffix` フラグが指定されている）場合、`suffixsep` は `_` に、`suffix` は `flag_installsuffix` の値に設定されます。
        2.  `flag_installsuffix` が指定されておらず、かつ `flag_race` が真の場合、`suffixsep` は `_` に、`suffix` は `"race"` に設定されます。
        3.  どちらも該当しない場合、`suffix` と `suffixsep` は空文字列のままです。
    *   パッケージパスは `"%s/pkg/%s_%s%s%s/%Z.a"` の形式で構築され、`suffixsep` と `suffix` の値が埋め込まれます。

この変更により、`-installsuffix` が `-race` よりも優先されるようになり、ユーザーが明示的に指定したサフィックスがパッケージのインストールパスに反映されるようになりました。これにより、異なるビルド設定でコンパイルされたパッケージが、ファイルシステム上で衝突することなく共存できるようになります。

### `src/cmd/go/build.go` の変更

この変更は、`go build` コマンドがコンパイラ (`gc`) とリンカ (`ld`) を呼び出す際に、`-installsuffix` フラグを適切に渡すようにするものです。

*   **`gcToolchain.gc` 関数**:
    *   コンパイラ (`gc`) を呼び出すための引数リスト `gcargs` に、`buildContext.InstallSuffix` が空でない場合に `"-installsuffix", buildContext.InstallSuffix` が追加されます。
    *   `buildContext.InstallSuffix` は、`go build` コマンドに渡された `-installsuffix` フラグの値が格納されているフィールドです。

*   **`gcToolchain.ld` 関数**:
    *   リンカ (`ld`) を呼び出すための引数リスト `ldflags` に、`buildContext.InstallSuffix` が空でない場合に `"-installsuffix", buildContext.InstallSuffix` が追加されます。

これらの変更により、`go` ツールはコマンドラインで受け取った `-installsuffix` の値を、実際にコンパイルとリンクを行う `gc` および `ld` に正確に伝達できるようになります。これにより、Goのビルドプロセス全体で `-installsuffix` のセマンティクスが統一され、期待通りのパッケージ分離が実現されます。

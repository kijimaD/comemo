## 変更の背景

このコミットは、Goツールチェーンの`cmd/go`コマンドが、新しいGoリリースがインストールされた際に、ユーザーのGOPATH内のパッケージを正しく再ビルドしないという問題（Issue #14176）を修正するために行われました。

Goのビルドシステムでは、パッケージが最新の状態であるかどうかを判断するために、様々な要因を考慮します。その一つに、Goランタイム自体のバージョン情報があります。Goのバージョン情報は、`zversion.go`というファイルに格納されており、これはGoのビルド時に生成されます。このファイルの内容は、Goのリリースごとに異なるため、`cmd/go`はこれを利用して、Goツールチェーン自体が更新された場合に、依存するパッケージが再ビルドされるべきかを判断します。

しかし、Goの内部パッケージ構造の変更により、`zversion.go`ファイルのパスが`runtime/zversion.go`から`runtime/internal/sys/zversion.go`へと移動しました。`cmd/go`コマンドは古いパスをハードコードして`zversion.go`を読み込もうとしていたため、ファイルが見つからず、結果としてGoのリリースが更新されても、GOPATH内のパッケージが「古い」Goバージョンに依存していると誤って判断され、再ビルドされないという問題が発生していました。

さらに、このファイル読み込み処理においてエラーチェックが欠如していたため、ファイルが見つからないというエラーが発生しても、`cmd/go`はそれを検知せず、誤ったビルドIDを生成し続けていました。これにより、ユーザーは新しいGoリリースにアップグレードしても、GOPATH内のパッケージが古いGoバージョンでビルドされたままになり、予期せぬ挙動や互換性の問題に直面する可能性がありました。

このコミットは、これらの問題を解決し、Goツールチェーンの堅牢性と信頼性を向上させることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoの概念とメカニズムについて知っておく必要があります。

1.  **Go ModulesとGOPATH**:
    *   **GOPATH**: Go 1.11以前のGoプロジェクトのワークスペースを定義する環境変数でした。ソースコード、コンパイル済みパッケージ、実行可能ファイルがGOPATH内の特定のディレクトリ構造に配置されていました。このコミットが作成された2016年時点では、GOPATHが主流でした。
    *   **Go Modules**: Go 1.11で導入され、Go 1.16でデフォルトとなった依存関係管理システムです。GOPATHの制約から解放され、プロジェクトごとに依存関係を管理できるようになりました。このコミットの文脈では、GOPATH環境下での挙動が問題となっていますが、Go Modulesにおいても同様の「Goツールチェーンの更新に伴う依存パッケージの再ビルド」の概念は重要です。
2.  **`cmd/go`コマンド**:
    *   Goのビルド、テスト、インストール、フォーマットなど、様々な操作を行うための主要なコマンドラインツールです。
    *   `go install`や`go build`などのサブコマンドは、依存関係を解決し、必要に応じてパッケージをコンパイルします。この際、パッケージが「最新」であるか、「古い」ために再ビルドが必要かを判断するロジックが内部で動作します。
3.  **ビルドID (Build ID)**:
    *   Goのコンパイラは、コンパイルされたバイナリに「ビルドID」と呼ばれる一意の識別子を埋め込みます。このビルドIDは、コンパイルに使用されたGoツールチェーンのバージョン、依存するパッケージのバージョン、ソースコードの内容など、様々な情報に基づいて生成されます。
    *   `cmd/go`は、パッケージのビルドIDを比較することで、そのパッケージが再ビルドされるべきかどうかを効率的に判断します。ビルドIDが変更された場合、それは依存関係やGoツールチェーン自体が変更されたことを意味するため、再ビルドが必要と判断されます。
4.  **`zversion.go`ファイル**:
    *   Goのソースツリー内に存在する特殊なファイルで、Goのバージョン情報やビルドに関するメタデータが格納されています。このファイルはGoのビルドプロセス中に自動生成されます。
    *   `cmd/go`は、この`zversion.go`ファイルの内容をビルドIDの計算に含めることで、Goツールチェーン自体のバージョンアップが、依存パッケージの再ビルドをトリガーするように設計されています。これにより、新しいGoリリースにアップグレードした際に、古いGoバージョンでビルドされたパッケージが残ってしまうことを防ぎます。
5.  **`runtime`パッケージと`runtime/internal/sys`パッケージ**:
    *   **`runtime`パッケージ**: Goプログラムのランタイムシステム（ガベージコレクション、スケジューラ、メモリ管理など）を実装するGoのコアパッケージです。
    *   **`runtime/internal/sys`パッケージ**: `runtime`パッケージの内部で使用されるシステム固有の定数やユーティリティ関数などを定義するパッケージです。Go 1.6（このコミットの時期）では、Goの内部パッケージ構造が整理され、一部のファイルが`runtime`から`runtime/internal/sys`のような内部パッケージに移動しました。この`zversion.go`ファイルの移動もその一環です。

## 技術的詳細

このコミットの技術的な核心は、`cmd/go`コマンドがGoランタイムのバージョン情報を取得するために参照する`zversion.go`ファイルのパスの修正と、その読み込み処理の堅牢化にあります。

Goのビルドシステムでは、`go install`や`go build`コマンドが実行される際、依存するパッケージが最新であるか、あるいは再ビルドが必要かを判断するために、各パッケージのビルドIDを計算します。このビルドIDは、パッケージのソースコード、依存関係、そしてGoツールチェーン自体のバージョン情報など、様々な要素のハッシュ値に基づいて生成されます。Goツールチェーンのバージョン情報は、`runtime`パッケージに関連する`zversion.go`ファイルの内容をハッシュに含めることで実現されていました。

コミットメッセージにあるように、以前は`cmd/go`は`runtime`パッケージのディレクトリ直下にある`zversion.go`を期待していました。これは`p.Dir`（パッケージのディレクトリ）と`"zversion.go"`を結合してファイルを読み込むことで行われていました。

```go
// 古いコード (pkg.go)
if p.Standard && p.ImportPath == "runtime" {
    data, _ := ioutil.ReadFile(filepath.Join(p.Dir, "zversion.go"))
    fmt.Fprintf(h, "zversion %q\\n", string(data))
}
```

しかし、Goの内部パッケージ構造の変更により、`zversion.go`は`runtime`パッケージから`runtime/internal/sys`パッケージに移動しました。この変更により、上記のコードは`runtime`パッケージのビルドIDを計算する際に`zversion.go`を見つけられなくなりました。`ioutil.ReadFile`はファイルが見つからない場合でもエラーを返しますが、古いコードではそのエラーが無視されていました（`_`で破棄）。結果として、`data`は空になり、ビルドIDの計算にGoツールチェーンのバージョン情報が正しく反映されなくなっていました。

この問題は、新しいGoリリースがインストールされた際に顕在化します。Goツールチェーンが更新されても、`zversion.go`の内容がビルドIDに反映されないため、`cmd/go`はGOPATH内の既存のパッケージが「古い」Goバージョンでビルドされたものだと認識せず、再ビルドをスキップしてしまいます。これにより、ユーザーは新しいGoリリースにアップグレードしたにもかかわらず、古いGoバージョンでビルドされたバイナリを使い続けることになり、互換性の問題や予期せぬバグが発生する可能性がありました。

このコミットでは、以下の2つの主要な変更によってこの問題を解決しています。

1.  **`zversion.go`のパスの更新**: `runtime`パッケージではなく、`runtime/internal/sys`パッケージの`zversion.go`を参照するように変更されました。これにより、正しいファイルが読み込まれるようになります。
2.  **エラーハンドリングの追加**: `ioutil.ReadFile`がエラーを返した場合に、`fatalf`関数を呼び出してプログラムを終了させるように変更されました。これにより、ファイルが見つからないなどの問題が発生した場合に、`cmd/go`がサイレントに失敗するのではなく、明確なエラーメッセージを出力してユーザーに問題を通知するようになります。

さらに、この変更の正しさを検証するために、`go_test.go`に新しいテストケース`TestNewReleaseRebuildsStalePackagesInGOPATH`が追加されました。このテストは、`zversion.go`ファイルの内容を変更することで、`cmd/go`がGOPATH内のパッケージを正しく「古い」と判断し、再ビルドを促すかどうかを検証します。これにより、将来的に同様の問題が再発するのを防ぐためのセーフティネットが構築されました。

## コアとなるコードの解説

### `src/cmd/go/pkg.go` の変更点

このファイルは、GoのビルドシステムがパッケージのビルドIDを計算する際のロジックを定義しています。`computeBuildID`関数内で、Goランタイムのバージョン情報がビルドIDに組み込まれる部分が変更されました。

*   **コメントの更新**:
    ```diff
    -	// Include the content of runtime/zversion.go in the hash
    +	// Include the content of runtime/internal/sys/zversion.go in the hash
    ```
    このコメントは、`zversion.go`が`runtime`パッケージではなく、`runtime/internal/sys`パッケージにあることを明確にするために更新されました。これは、コードの意図を正確に反映するための重要な変更です。

*   **条件式の変更**:
    ```diff
    -	if p.Standard && p.ImportPath == "runtime" {
    +	if p.Standard && p.ImportPath == "runtime/internal/sys" {
    ```
    `p.ImportPath == "runtime"`という条件が`p.ImportPath == "runtime/internal/sys"`に変更されました。これにより、`computeBuildID`関数は、`runtime`パッケージではなく、`runtime/internal/sys`パッケージが処理されている場合にのみ、`zversion.go`の読み込みを試みるようになります。これは、`zversion.go`が実際に移動した新しい場所を指すようにするための直接的な修正です。

*   **エラーハンドリングの追加**:
    ```diff
    -		data, _ := ioutil.ReadFile(filepath.Join(p.Dir, "zversion.go"))
    +		data, err := ioutil.ReadFile(filepath.Join(p.Dir, "zversion.go"))
    +		if err != nil {
    +			fatalf("go: %s", err)
    +		}
    ```
    以前は`ioutil.ReadFile`が返すエラーが`_`で破棄されていましたが、この変更により`err`変数でエラーを受け取り、`if err != nil`でエラーチェックを行うようになりました。もしエラーが発生した場合（例: ファイルが見つからない）、`fatalf`関数が呼び出され、エラーメッセージと共にプログラムが終了します。これにより、`zversion.go`の読み込みに失敗した場合に、`cmd/go`がサイレントに誤ったビルドIDを生成し続けることを防ぎ、問題を早期に検知できるようになります。

### `src/cmd/go/go_test.go` の変更点

このファイルには、`cmd/go`コマンドの動作を検証するための新しいテストケース`TestNewReleaseRebuildsStalePackagesInGOPATH`が追加されました。このテストは、GoツールチェーンのバージョンアップがGOPATH内のパッケージの再ビルドを正しくトリガーするかどうかを検証することを目的としています。

*   **`addNL`ヘルパー関数**:
    この関数は、指定されたファイルに改行を追加し、そのファイルの最終更新時刻を更新します。これは、`zversion.go`ファイルの内容が変更されたことをシミュレートするために使用されます。Goのビルドシステムはファイルのmtimeや内容の変更を検知するため、この操作はGoリリースが更新された状況を再現するのに役立ちます。関数は元のファイル内容を復元するためのクロージャを返します。

*   **テストシナリオ**:
    1.  `TESTGO_IS_GO_RELEASE`を`1`に設定し、Goがリリースモードで動作していることをシミュレートします。
    2.  GOPATH内に`p1`というシンプルなパッケージを作成し、`go install -a p1`でインストールします。この時点では`p1`はstaleではないはずです。
    3.  `runtime.GOROOT() + "/src/runtime/internal/sys/sys.go"`という、`zversion.go`とは異なるGoランタイムの内部ファイルを一時的に変更し、その変更が`p1`のstale状態に影響しないことを確認します。これは、Goリリースが更新されたことと、単なる内部ファイルの変更が区別されることを示します。
    4.  **核心部分**: `runtime.GOROOT() + "/src/runtime/internal/sys/zversion.go"`という`zversion.go`ファイルを`addNL`関数で変更します。これにより、Goツールチェーンのバージョン情報が変更されたことをシミュレートします。
    5.  `tg.wantStale("p1", ...)`を呼び出し、`p1`がstale状態になったことを確認します。これは、`cmd/go`が`zversion.go`の変更を正しく検知し、`p1`が再ビルドされるべきだと判断したことを意味します。
    6.  `zversion.go`を元の状態に戻し、`p1`がstaleではない状態に戻ることを確認します。
    7.  再度`zversion.go`を変更し、`p1`がstale状態になることを確認した後、`go install p1`を実行して`p1`を再ビルドします。再ビルド後、`p1`がstaleではない状態に戻ることを確認します。
    8.  最後に、`zversion.go`を元の状態に戻し、`p1`が再びstale状態になることを確認し、`go install p1`で再ビルドしてテストを終了します。

このテストは、`cmd/go`が`zversion.go`の変更を正確に検知し、GOPATH内の依存パッケージの再ビルドを適切にトリガーするという、このコミットの修正が意図通りに機能していることを保証します。

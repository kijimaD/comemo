## 変更の背景

この変更の主な背景は、Goランタイム内のメモリ操作関数の命名をより明確にし、その機能が何であるかを直感的に理解できるようにすることです。具体的には、`writebarrierfat` と `writebarriercopy` という名前が、その関数が実際に行っている「型付きメモリ移動」や「型付きスライスコピー」という操作を十分に表現していないという認識がありました。

Goのガベージコレクション（GC）は、プログラムの実行中に不要になったメモリを自動的に解放する重要な機能です。このGCが正しく動作するためには、ポインタの書き込み（あるオブジェクトから別のオブジェクトへの参照の変更）をGCが追跡できる必要があります。この追跡メカニズムが「ライトバリア（Write Barrier）」です。

従来の `memmove` 関数は、単にメモリブロックをコピーするだけで、コピーされるデータがポインタを含むかどうか、またそのポインタがGCによって追跡されるべきかどうかを考慮しませんでした。しかし、Goのランタイム内部では、GCの正確性を保つために、ポインタを含む可能性のあるメモリ領域を移動する際には、ライトバリアを伴う特別なメモリ移動操作が必要となります。

このコミットは、ランタイム内の多くの `memmove` 呼び出しを、ライトバリアを考慮した「型付き」のメモリ移動関数に置き換えるための準備段階として位置づけられています。新しい名前 `typedmemmove` と `typedslicecopy` は、これらの関数が単なるメモリコピーではなく、型情報に基づいてポインタの追跡を伴うメモリ操作を行うことを明確に示しています。これにより、コードの可読性と保守性が向上し、将来的なGC関連の最適化やデバッグが容易になることが期待されます。

## 前提知識の解説

### Goのガベージコレクション (GC) とライトバリア

Go言語は、自動メモリ管理のためにガベージコレクション（GC）を採用しています。GoのGCは、並行マーク＆スイープ方式を基本としており、プログラムの実行と並行してGCが動作します。これにより、GCによるアプリケーションの一時停止（Stop-The-World）時間を最小限に抑えることを目指しています。

並行GCの課題の一つは、「ミューテータ」（アプリケーションの通常の実行スレッド）がオブジェクトグラフを変更している最中に、GCがオブジェクトをスキャンすることです。このとき、GCがオブジェクトグラフを誤って解釈し、まだ到達可能なオブジェクトを誤って回収してしまう（「ポインタの消失」問題）可能性があります。

この問題を解決するために導入されるのが「ライトバリア（Write Barrier）」です。ライトバリアは、ミューテータがポインタを書き換える際に、GCにその変更を通知するメカニズムです。具体的には、あるオブジェクトのフィールドに新しいポインタを書き込む際、または既存のポインタを上書きする際に、特別なコード（ライトバリアコード）が実行されます。このコードは、GCがオブジェクトグラフを正確に追跡し、到達可能なオブジェクトを誤って回収しないようにするために必要な情報を記録します。

GoのGCは、三色マーキング（Tri-color marking）というアルゴリズムを使用しています。オブジェクトは以下の3つの状態に分類されます。
*   **白 (White)**: GCによってまだ訪問されていないオブジェクト。最終的に回収される可能性がある。
*   **灰 (Gray)**: GCによって訪問されたが、その参照先のオブジェクトがまだスキャンされていないオブジェクト。
*   **黒 (Black)**: GCによって訪問され、その参照先のオブジェクトもすべてスキャンされたオブジェクト。回収されない。

ライトバリアは、ミューテータが白のオブジェクトへのポインタを書き込む際に、その白のオブジェクトを灰にする（または別の方法でGCに通知する）ことで、ポインタの消失を防ぎます。

### `memmove` と型付きメモリ操作

`memmove` は、C言語の標準ライブラリ関数であり、指定されたメモリ領域から別のメモリ領域へバイト列をコピーします。この関数は、コピー元とコピー先のメモリ領域が重なっていても安全に動作するように設計されています。しかし、`memmove` は単なるバイトコピーであり、コピーされるデータの内容（例えば、それがポインタであるかどうか）については一切関知しません。

Goのランタイムでは、GCの正確性を保つために、ポインタを含む可能性のあるデータ構造を移動する際に、単なる `memmove` では不十分な場合があります。GCは、ヒープ上のオブジェクト間のポインタ関係を追跡することで、どのオブジェクトがまだ使用されているかを判断します。もしポインタを含むメモリ領域が `memmove` でコピーされ、その際にライトバリアが適用されなければ、GCがその新しいポインタを認識できず、誤って参照先のオブジェクトを回収してしまう可能性があります。

ここで登場するのが、`typedmemmove` と `typedslicecopy` の概念です。これらの関数は、単にバイトをコピーするだけでなく、コピーされるデータの「型情報」を利用します。型情報には、そのデータ構造内にポインタが含まれているか、どのオフセットにポインタがあるかといった情報が含まれています。この型情報に基づいて、`typedmemmove` や `typedslicecopy` は、ポインタのコピー時に適切にライトバリアを適用し、GCがオブジェクトグラフを正確に追跡できるようにします。これにより、Goの並行GCの効率と正確性が保証されます。

## 技術的詳細

このコミットは、Goランタイムの内部で使われる2つの重要なメモリ操作関数 `writebarrierfat` と `writebarriercopy` の名前を、それぞれ `typedmemmove` と `typedslicecopy` に変更することを主目的としています。このリネームは、単なる名前の変更以上の意味を持ち、Goのガベージコレクション（GC）とメモリ管理の進化における重要なステップです。

### 関数の役割とリネームの意図

*   **`writebarrierfat` から `typedmemmove` へ**:
    *   元の `writebarrierfat` は、GCのライトバリアを伴う「型付き」のメモリ移動を行う関数でした。`fat` という接尾辞は、おそらく「太いポインタ」（型情報を含むポインタ）や、単なるバイトコピー以上の複雑な処理を意味していたと考えられます。
    *   新しい `typedmemmove` という名前は、この関数が「型情報に基づいてメモリを移動する」という本質的な役割をより直接的に表現しています。これにより、この関数が単なる `memmove` ではなく、GCのライトバリアを考慮したポインタを含むデータの移動を行うことが明確になります。
    *   コミットメッセージにあるように、このリネームは「ランタイム内の多くの `memmove` 呼び出しを `typedmemmove` に置き換えるための準備」です。これは、Goのランタイムが、ポインタを含む可能性のあるメモリコピーに対して、より安全でGCフレンドリーな `typedmemmove` を積極的に使用していく方針を示唆しています。

*   **`writebarriercopy` から `typedslicecopy` へ**:
    *   元の `writebarriercopy` は、スライス（Goの動的配列）の要素をコピーする際に、ライトバリアを伴う操作を行う関数でした。
    *   新しい `typedslicecopy` という名前は、この関数が「型情報に基づいてスライスの要素をコピーする」という役割を明確に示しています。スライスの要素がポインタを含む場合、そのコピー操作はGCによって追跡される必要があります。

### `src/runtime/mgc0.go` の変更

このファイルはGoのガベージコレクション（GC）の低レベルな実装を含んでいます。

## 前提知識の解説

### Goのガベージコレクション (GC) とライトバリア

Go言語は、自動メモリ管理のためにガベージコレクション（GC）を採用しています。GoのGCは、並行マーク＆スイープ方式を基本としており、プログラムの実行と並行してGCが動作します。これにより、GCによるアプリケーションの一時停止（Stop-The-World）時間を最小限に抑えることを目指しています。

並行GCの課題の一つは、「ミューテータ」（アプリケーションの通常の実行スレッド）がオブジェクトグラフを変更している最中に、GCがオブジェクトをスキャンすることです。このとき、GCがオブジェクトグラフを誤って解釈し、まだ到達可能なオブジェクトを誤って回収してしまう（「ポインタの消失」問題）可能性があります。

この問題を解決するために導入されるのが「ライトバリア（Write Barrier）」です。ライトバリアは、ミューテータがポインタを書き換える際に、GCにその変更を通知するメカニズムです。具体的には、あるオブジェクトのフィールドに新しいポインタを書き込む際、または既存のポインタを上書きする際に、特別なコード（ライトバリアコード）が実行されます。このコードは、GCがオブジェクトグラフを正確に追跡し、到達可能なオブジェクトを誤って回収しないようにするために必要な情報を記録します。

GoのGCは、三色マーキング（Tri-color marking）というアルゴリズムを使用しています。オブジェクトは以下の3つの状態に分類されます。
*   **白 (White)**: GCによってまだ訪問されていないオブジェクト。最終的に回収される可能性がある。
*   **灰 (Gray)**: GCによって訪問されたが、その参照先のオブジェクトがまだスキャンされていないオブジェクト。
*   **黒 (Black)**: GCによって訪問され、その参照先のオブジェクトもすべてスキャンされたオブジェクト。回収されない。

ライトバリアは、ミューテータが白のオブジェクトへのポインタを書き込む際に、その白のオブジェクトを灰にする（または別の方法でGCに通知する）ことで、ポインタの消失を防ぎます。

### `memmove` と型付きメモリ操作

`memmove` は、C言語の標準ライブラリ関数であり、指定されたメモリ領域から別のメモリ領域へバイト列をコピーします。この関数は、コピー元とコピー先のメモリ領域が重なっていても安全に動作するように設計されています。しかし、`memmove` は単なるバイトコピーであり、コピーされるデータの内容（例えば、それがポインタであるかどうか）については一切関知しません。

Goのランタイムでは、GCの正確性を保つために、ポインタを含む可能性のあるデータ構造を移動する際に、単なる `memmove` では不十分な場合があります。GCは、ヒープ上のオブジェクト間のポインタ関係を追跡することで、どのオブジェクトがまだ使用されているかを判断します。もしポインタを含むメモリ領域が `memmove` でコピーされ、その際にライトバリアが適用されなければ、GCがその新しいポインタを認識できず、誤って参照先のオブジェクトを回収してしまう可能性があります。

ここで登場するのが、`typedmemmove` と `typedslicecopy` の概念です。これらの関数は、単にバイトをコピーするだけでなく、コピーされるデータの「型情報」を利用します。型情報には、そのデータ構造内にポインタが含まれているか、どのオフセットにポインタがあるかといった情報が含まれています。この型情報に基づいて、`typedmemmove` や `typedslicecopy` は、ポインタのコピー時に適切にライトバリアを適用し、GCがオブジェクトグラフを正確に追跡できるようにします。これにより、Goの並行GCの効率と正確性が保証されます。

このコミットの核となる変更は、Goランタイムにおけるメモリコピーおよびスライス要素コピーの内部関数名の変更と、それに伴う最適化です。

### `src/runtime/mgc0.go` の変更

このファイルはGoのガベージコレクション（GC）の低レベルな実装を含んでいます。

1.  **`writebarrierfat` から `typedmemmove` へのリネーム**:
    ```go
    //go:nosplit
    -func writebarrierfat(typ *_type, dst, src unsafe.Pointer) {
    -	if !needwb() {
    +func typedmemmove(typ *_type, dst, src unsafe.Pointer) {
    +	if !needwb() || (typ.kind&kindNoPointers) != 0 {
     		memmove(dst, src, typ.size)
     		return
     	}
    ```
    *   `writebarrierfat` 関数が `typedmemmove` にリネームされました。この関数は、`dst` に `src` の内容をコピーする際に、`typ` で指定された型情報に基づいてライトバリアを適用します。
    *   最も重要な変更は、`if` 文の条件式です。
        *   `!needwb()`: これは、現在GCがライトバリアを必要としない状態であるか（例えば、GCが実行中でないか、またはGCの特定のフェーズでライトバリアが一時的に無効になっているか）をチェックします。
        *   `(typ.kind&kindNoPointers) != 0`: これは、コピーされるデータの型 `typ` がポインタを含まない型であるかどうかをチェックします。`_type` 構造体の `kind` フィールドには、型の種類に関するビットフラグが含まれており、`kindNoPointers` はその型がポインタを含まないことを示すフラグです。
    *   この新しい条件式は、「ライトバリアが不要な場合」**または**「コピーされるデータがポインタを含まない場合」には、通常の `memmove` を使用して高速にコピーを完了し、ライトバリアの処理をスキップできることを意味します。これにより、ポインタを含まないデータのコピーにおけるGCのオーバーヘッドが削減され、パフォーマンスが向上します。

2.  **`writebarriercopy` から `typedslicecopy` へのリネーム**:
    ```go
    //go:nosplit
    -func writebarriercopy(typ *_type, dst, src slice) int {
    +func typedslicecopy(typ *_type, dst, src slice) int {
     	// ...
     	for {
    -		writebarrierfat(typ, dstp, srcp)
    +		typedmemmove(typ, dstp, srcp)
     		// ...
     	}
     	// ...
    ```
    *   `writebarriercopy` 関数が `typedslicecopy` にリネームされました。この関数は、スライスの要素をコピーする際に使用されます。
    *   この関数内部でも、個々の要素のコピーに `writebarrierfat`（リネーム後は `typedmemmove`）が使用されている箇所が更新されています。これは、スライスの要素がポインタを含む可能性があるため、要素ごとにライトバリアを適用する必要があることを示しています。

### `src/runtime/slice.go` の変更

このファイルはGoのスライス操作のランタイム実装を含んでいます。

1.  **`growslice` 関数内の変更**:
    ```go
    func growslice(t *slicetype, old sliceStruct, n int64) sliceStruct {
    	// ...
    	if old.array != nil {
    		// ...
    		for i := 0; i < old.len; i++ {
    -			writebarrierfat(et, add(p, uintptr(i)*et.size), add(old.array, uintptr(i)*et.size))
    +			typedmemmove(et, add(p, uintptr(i)*et.size), add(old.array, uintptr(i)*et.size))
     		}
     	}
     	// ...
    ```
    *   `growslice` は、スライスの容量が不足した際に新しい、より大きな基盤配列を割り当て、古い要素を新しい配列にコピーする関数です。
    *   ここで、古い要素を新しい配列にコピーするループ内で `writebarrierfat` の呼び出しが `typedmemmove` に変更されています。これは、スライスの要素がポインタを含む可能性があるため、要素のコピー時にライトバリアを適用する必要があることを示しています。

これらの変更は、Goのランタイムがメモリ操作をより型安全かつGCフレンドリーに行うための継続的な努力の一環です。新しい関数名はコードの意図を明確にし、`typedmemmove` の最適化はGCのパフォーマンスを向上させます。

# [インデックス 250] ファイルの概要

このコミットは、Go言語の初期ランタイムにおける重要な機能である「セグメント化されたスタック（segmented stack）」の導入に関するものです。特に、x86-64アーキテクチャ（amd64）向けのLinuxおよびDarwin（macOS）環境におけるスタック管理の基盤を構築しています。この変更により、Goのゴルーチンが動的にスタックサイズを調整できるようになり、多数の軽量なゴルーチンを効率的に実行するための重要なメカニズムが提供されました。

## 変更の背景

Go言語は、設計当初から多数の軽量な並行処理単位である「ゴルーチン（goroutine）」を効率的にサポートすることを目指していました。従来のOSスレッドはスタックサイズが固定されており、通常は数MBといった比較的大きなメモリを事前に確保します。これにより、数千、数万といった大量のスレッドを生成すると、メモリ消費が膨大になり、システムリソースを圧迫するという問題がありました。

この問題を解決するため、Goの設計者たちは「セグメント化されたスタック」というアプローチを採用しました。これは、ゴルーチンが最初に小さなスタック（例えば8KB）で開始し、必要に応じてスタックを動的に拡張するというものです。スタックが不足しそうになった場合、ランタイムが新しいスタックセグメントを割り当て、既存のスタックに連結することで、スタックを「分割」して成長させます。これにより、メモリを効率的に利用し、大量のゴルーチンを少ないオーバーヘッドで実行することが可能になります。

このコミットは、そのセグメント化されたスタックの基本的なメカニズム、特にスタックの拡張が必要かどうかをチェックし、必要であればランタイムの`_morestack`関数を呼び出すためのコード生成とランタイムサポートを導入するものです。Ken Thompson氏によるこの初期の実装は、Goの並行処理モデルの実現において極めて重要な一歩でした。

## 前提知識の解説

*   **ゴルーチン (Goroutine):** Go言語における軽量な実行スレッド。OSスレッドよりもはるかに少ないリソースで生成・管理され、Goランタイムによってスケジューリングされます。
*   **スタック (Stack):** 関数呼び出しの際に、ローカル変数、引数、戻りアドレスなどを格納するために使用されるメモリ領域。関数が呼び出されるたびにスタックフレームが積まれ、関数から戻る際に解放されます。
*   **スタックオーバーフロー (Stack Overflow):** スタック領域が不足し、これ以上スタックフレームを積むことができなくなる状態。通常、プログラムのクラッシュを引き起こします。
*   **スタックポインタ (Stack Pointer, SP):** 現在のスタックの最上位（または最下位、アーキテクチャによる）を指すレジスタ。
*   **アセンブラ (Assembler):** アセンブリ言語のコードを機械語に変換するプログラム。Goのツールチェーンでは、`cmd/6a`（x86-64アセンブラ）などがこれに該当します。
*   **リンカ (Linker):** コンパイルされたオブジェクトファイルやライブラリを結合し、実行可能ファイルを生成するプログラム。Goのツールチェーンでは、`cmd/6l`（x86-64リンカ）などがこれに該当します。
*   **ランタイム (Runtime):** プログラムの実行中に、メモリ管理、スケジューリング、ガベージコレクションなどの低レベルな操作を処理するコード。GoランタイムはGoプログラムの実行環境の中核をなします。
*   **`_morestack` 関数:** Goランタイムに存在する特殊な関数で、スタックが不足した際に呼び出され、スタックを拡張する処理を行います。
*   **プロローグ (Prologue):** 関数の冒頭に挿入されるコードで、スタックフレームのセットアップやレジスタの保存などを行います。セグメント化されたスタックでは、このプロローグでスタックチェックが行われます。
*   **`NOSPLIT` フラグ:** 関数がスタック分割チェックを必要としないことを示すフラグ。例えば、`_morestack`関数自体や、非常に短いアセンブリ関数など、スタックをほとんど使用しないか、スタックチェックを自身で管理する関数に適用されます。

## 技術的詳細

このコミットの核となる技術的詳細は、Goコンパイラ/アセンブラとリンカが連携して、各Go関数の冒頭にスタックチェックコードを自動的に挿入するメカニズムにあります。

1.  **スタックフレーム情報のエンコード:**
    *   `src/cmd/6a/a.y` (アセンブラの文法定義) に `imm3` と `con3` が追加されました。`con3` は `LCONST '-' LCONST '-' LCONST` の形式を解析できるようになり、複数の定数値を1つの64ビット整数にパックする能力を提供します。
    *   これは、関数のスタックフレームサイズ、入力引数サイズ、出力引数サイズといった情報を、`ATEXT`命令の`to.offset`フィールドにエンコードするために使用されます。具体的には、`textstksiz` (スタックサイズ)、`textinarg` (入力引数サイズ)、`textoutarg` (出力引数サイズ) がそれぞれ64ビット値の異なるビット範囲に格納されます。
    *   `src/cmd/6l/list.c` の `parsetextconst` 関数がこのエンコードされた64ビット値を受け取り、それぞれのサイズ情報にデコードします。

2.  **スタックチェックコードの挿入:**
    *   `src/cmd/6l/pass.c` の `dostkoff` 関数内で、リンカが各`ATEXT`命令（Go関数）を処理する際に、スタックチェックコードを挿入します。
    *   `p->from.scale & NOSPLIT` で `NOSPLIT` フラグが設定されていない関数に対してのみ、スタックチェックが挿入されます。
    *   スタックチェックは、現在のスタックポインタ `SP` と、ゴルーチンのスタックリミットを保持するレジスタ `R15` の値を比較することで行われます。
    *   スタックの使用量が少ない関数（`autoffset <= 50`）と多い関数で、わずかに異なるチェックコードが生成されますが、基本的には `SP` がスタックリミット `R15` を超えていないかを確認します。
    *   もしスタックが不足していると判断された場合（`AJHI`命令でジャンプ）、ランタイムの `_morestack` 関数が呼び出されます。この際、エンコードされたスタックフレーム情報 (`curtext->to.offset`) が `AX` レジスタに渡されます。

3.  **`_morestack` 関数とスタック拡張:**
    *   `src/runtime/rt0_amd64_linux.s` に `_morestack` 関数が追加されました。
    *   この関数は、`SP` から `1024` バイトを減算し、その結果を `0(R15)` に格納しています。これは、スタックリミットを一時的に下げることで、新しいスタックセグメントを割り当てる準備をしているか、あるいは非常に初期のスタック拡張ロジックの一部であると考えられます。
    *   `R15` レジスタは、`_rt0_amd64_linux` の初期化時に `peruser<>(SB)` のアドレスを格納するために使用されており、この `peruser` 領域がゴルーチンごとのスタックリミットを保持する役割を担っていることが示唆されます。

4.  **ランタイムの初期化:**
    *   `src/runtime/rt0_amd64_linux.s` の `_rt0_amd64_linux` 関数が大幅に変更され、スタックの初期設定と `R15` レジスタのセットアップが行われます。
    *   `LEAQ peruser<>(SB), R15` で `R15` に `peruser` 構造体のアドレスをロードし、`MOVQ AX, 0(R15)` で `SP - 4096` の値を `0(R15)` に格納しています。これは、初期のスタックリミットを設定していると考えられます。

このセグメント化されたスタックの設計は、Go 1.3まで採用されていましたが、頻繁なスタック分割がパフォーマンスオーバーヘッドを引き起こす「ホットスタック分割」問題が顕在化したため、Go 1.3以降では連続したコピー型スタック（contiguous, copying stacks）へと移行しました。しかし、このコミットはGoの初期の設計思想と、軽量な並行処理を実現するための工夫を示す歴史的に重要な変更点です。

## コアとなるコードの変更箇所

このコミットにおけるコアとなるコードの変更は、主に以下のファイルに集中しています。

*   **`src/cmd/6a/a.y`**: アセンブラの文法定義ファイル。`imm3`と`con3`という新しい型が追加され、`TEXT`命令の引数として`imm3`が使用されるようになりました。これにより、スタックサイズなどの複数の情報を1つの定数にパックして渡すことが可能になります。

*   **`src/cmd/6l/l.h`**: リンカのヘッダファイル。`textstksiz`, `textinarg`, `textoutarg`といったスタック関連のグローバル変数が追加され、`parsetextconst`関数のプロトタイプが宣言されました。
*   **`src/cmd/6l/list.c`**: リンカのリスト出力関連ファイル。`Pconv`と`Dconv`関数が変更され、`ATEXT`命令の出力フォーマットが拡張されました。特に、`Dconv`内で`parsetextconst`を呼び出し、エンコードされたスタック情報をデコードして表示するロジックが追加されています。また、`parsetextconst`関数の実装がここに追加され、64ビット整数からスタックサイズ、入力引数サイズ、出力引数サイズを抽出する処理が定義されています。
*   **`src/cmd/6l/pass.c`**: リンカの主要なパスを処理するファイル。`dostkoff`関数が大幅に修正され、各`ATEXT`命令（Go関数）の冒頭にスタックチェックコードを挿入するロジックが追加されました。`_morestack`シンボルを検索し、スタックサイズに基づいて`CMPQ`、`AMOVQ`、`ASUBQ`、`ACALL`などの命令を生成してスタックチェックと`_morestack`呼び出しを行います。
*   **`src/runtime/rt0_amd64_darwin.s` / `src/runtime/rt0_amd64_linux.s`**: ランタイムの初期化アセンブリファイル。`TEXT`命令のフラグが変更され、`_rt0_amd64_linux`関数内で`peruser`領域の初期化と`R15`レジスタへのスタックリミット設定が行われるようになりました。また、`_morestack`関数が追加され、スタック拡張の初期ロジックが実装されています。

### `src/cmd/6l/list.c` の `parsetextconst` 関数

```c
+void
+parsetextconst(vlong arg)
+{
+	textstksiz = arg & 0xffffffffLL;
+	if(textstksiz & 0x80000000LL)
+		textstksiz = -(-textstksiz & 0xffffffffLL);
+		
+
+	// the following throws away one bit
+	// of precision, but maintains compat
+	textinarg = (arg >> 32) & 0xffffLL;
+	if(textinarg & 0x8000LL)
+		textinarg = -(-textinarg & 0xffffLL);
+	if(textinarg <= 0)
+		textinarg = 100;
+
+	textoutarg = (arg >> 48) & 0xffffLL;
+	if(textoutarg & 0x8000LL)
+		textoutarg = -(-textoutarg & 0xffffLL);
+	if(textoutarg <= 0)
+		textoutarg = 0;
+}
```
この関数は、`ATEXT`命令の`to.offset`にエンコードされた64ビット整数`arg`を受け取り、それを`textstksiz`（スタックフレームサイズ）、`textinarg`（入力引数サイズ）、`textoutarg`（出力引数サイズ）の3つの値にデコードします。
*   `textstksiz`: `arg`の下位32ビット。
*   `textinarg`: `arg`を32ビット右シフトした後の下位16ビット。
*   `textoutarg`: `arg`を48ビット右シフトした後の下位16ビット。
各値は符号拡張も考慮されています。

この関数は、各Go関数のプロローグにスタックチェックコードを挿入する中心的なロジックを含んでいます。
1.  まず、`_morestack`シンボルを検索し、その`Prog`（プログラム命令）へのポインタ`pmorestack`を取得します。`_morestack`が見つからない場合はエラーとなります。
2.  各`ATEXT`命令（Go関数）について、`parsetextconst`を呼び出してスタックサイズ`textstksiz`を取得し、`autoffset`に設定します。
3.  `NOSPLIT`フラグが設定されていない関数に対してのみ、スタックチェックコードを生成します。
    *   スタック使用量が小さい場合（`autoffset <= 50`）、`CMPQ SP, (R15)`を生成し、現在のスタックポインタ`SP`とスタックリミット（`R15`レジスタが指すメモリ位置）を比較します。
    *   スタック使用量が大きい場合、`SP`から必要なスタックサイズを引いた値を計算し、それをスタックリミットと比較します。
    *   比較結果がスタック不足を示す場合（`AJHI`命令）、`_morestack`関数への`ACALL`命令が挿入されます。この際、`curtext->to.offset`（エンコードされたスタックフレーム情報）が`AX`レジスタにロードされて`_morestack`に渡されます。
4.  最後に、`AADJSP`命令でスタックポインタを調整し、関数のローカル変数用の領域を確保します。

*   `_rt0_amd64_linux`関数の`TEXT`ディレクティブのフラグが`1`から`7`に変更されました。これは、スタックフレームのプロパティを示すもので、`NOSPLIT`フラグなどと関連している可能性があります。
*   `_rt0_amd64_linux`内で、`R15`レジスタが`peruser<>(SB)`のアドレスを保持するように設定されます。`peruser`はゴルーチンごとのデータ構造であり、その中にスタックリミットが格納されると考えられます。
*   `MOVQ SP, AX`、`SUBQ $4096, AX`、`MOVQ AX, 0(R15)`という命令シーケンスにより、初期スタックポインタから4096バイトを引いた値が`0(R15)`（つまり`peruser`構造体の先頭）に格納されます。これは、ゴルーチンの初期スタックリミットを設定する処理です。
*   `_morestack`関数が新しく追加されました。この関数は、`MOVQ SP, AX`、`SUBQ $1024, AX`、`MOVQ AX, 0(R15)`という命令を実行します。これは、スタックが不足した際に呼び出され、スタックリミットを一時的に1024バイト分下げることで、スタックを拡張する（または拡張の準備をする）初期のメカニズムです。

これらの変更は、Goのゴルーチンが動的にスタックを拡張できる「セグメント化されたスタック」の基本的な枠組みを構築するものであり、Goの並行処理モデルの効率性を支える重要な基盤となりました。

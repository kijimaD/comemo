## 元コミット内容

このコミットは、Go言語の `crypto/tls` パッケージにおけるSNI (Server Name Indication) 拡張のパース処理のバグを修正するものです。以前のコードでは、長さを示すプレフィックスを要素数として誤って解釈していました。この誤りは、SNI拡張が常に単一のホスト名要素しか含まないという現在の仕様のため、実際には問題を引き起こしていませんでした。しかし、将来的にSNIの仕様が変更され、複数の要素や異なる種類の要素が導入された場合に、パースエラーが発生する可能性がありました。この変更は、将来のSNI仕様変更に備えて、パースロジックを正しく修正するものです。

## 変更の背景

TLS (Transport Layer Security) のハンドシェイクプロセスにおいて、クライアントは `ClientHello` メッセージの一部としてSNI拡張を送信することがあります。SNIは、単一のIPアドレスで複数のウェブサイト（異なるドメイン名）をホストしているサーバーに対して、クライアントがどのホスト名に接続しようとしているかを伝えるために使用されます。これにより、サーバーは適切なTLS証明書を選択してクライアントに提示できます。

このコミット以前のGoの `crypto/tls` パッケージの実装では、SNI拡張のデータ構造をパースする際に、データ長を示すフィールドを誤って「要素の数」として解釈していました。具体的には、SNI拡張のデータは、まず全体の長さを示す2バイトのフィールドがあり、その後に「ServerNameList」が続きます。このServerNameListもまた、全体の長さを示す2バイトのフィールドがあり、その後に個々のServerNameエントリが続きます。各ServerNameエントリは、NameType（1バイト）とNameLen（2バイト）の後に実際のホスト名データが続く構造です。

問題のコードは、ServerNameListの全体の長さを示す2バイトのフィールドを、リスト内のServerNameエントリの数（`numNames`）として誤って解釈していました。しかし、現在のSNIの仕様（RFC 6066）では、ServerNameListには常に1つのホスト名要素（NameTypeが0のHostname）しか含まれないため、この誤った解釈でも結果的に正しいホスト名が抽出されていました。つまり、`numNames` が常に1として扱われることになり、ループが最初の要素を見つけるとすぐに終了するため、潜在的なバグが顕在化していなかったのです。

このコミットは、将来的にSNIの仕様が拡張され、複数のホスト名要素や異なる種類の要素が導入された場合に、GoのTLS実装が正しく動作しなくなる可能性を排除するために行われました。

## 前提知識の解説

### TLS (Transport Layer Security)

TLSは、インターネット上で安全な通信を行うための暗号化プロトコルです。ウェブブラウジング（HTTPS）、電子メール、VoIPなど、様々なアプリケーションで利用されています。TLSは、通信のプライバシー、データの完全性、および通信相手の認証を提供します。

### TLSハンドシェイクプロトコル

TLSハンドシェイクは、クライアントとサーバーが安全な通信を開始する前に、互いに認証し、暗号化アルゴリズムと鍵を確立するための一連のメッセージ交換です。このプロセス中に、クライアントは `ClientHello` メッセージを送信し、サーバーは `ServerHello` メッセージで応答します。

### SNI (Server Name Indication)

SNIは、TLSプロトコルの拡張機能の一つで、クライアントがTLSハンドシェイクの開始時に、接続しようとしているサーバーのホスト名（ドメイン名）を伝えることを可能にします。これは、特に単一のIPアドレスで複数のウェブサイトをホストしているサーバー（バーチャルホスト）にとって重要です。SNIがない場合、サーバーはどのウェブサイトの証明書を提示すべきか判断できず、デフォルトの証明書を提示することになり、クライアントの検証が失敗する可能性があります。SNIはRFC 6066で定義されています。

### TLS拡張

TLSプロトコルは、その基本機能に加えて、様々な拡張機能を持つことができます。これらの拡張機能は、`ClientHello` や `ServerHello` などのハンドシェイクメッセージ内に特定のデータ構造として埋め込まれます。各拡張にはタイプと長さが定義されており、パース時にはこれらの情報に基づいて拡張データを正しく解釈する必要があります。

### プロトコルにおける長さプレフィックス

多くのネットワークプロトコルでは、可変長のデータを扱うために「長さプレフィックス」という手法が用いられます。これは、データの本体の直前に、そのデータの長さをバイト数で示すフィールドを置くものです。これにより、受信側はデータの終わりを正確に判断し、次のデータをパースすることができます。このコミットのバグは、この長さプレフィックスを誤って「要素数」として解釈したことに起因します。

## 技術的詳細

問題は `src/crypto/tls/handshake_messages.go` ファイルの `clientHelloMsg` 構造体の `unmarshal` メソッド内にありました。このメソッドは、受信した `ClientHello` メッセージのバイト列をGoのデータ構造に変換（アンマーシャル）する役割を担っています。

SNI拡張のパース部分では、以下のコードが問題でした（修正前のコード）：

```go
			case extensionServerName:
				if length < 2 {
					return false
				}
				numNames := int(data[0])<<8 | int(data[1]) // ここが問題
				d := data[2:]
				for i := 0; i < numNames; i++ { // ここが問題
					// ...
				}
```

ここで `length` はSNI拡張全体の長さを示し、`data` はSNI拡張のデータ本体です。
SNI拡張のデータ構造は以下のようになっています（RFC 6066より簡略化）：

```
struct {
    ServerNameList server_name_list;
} ServerNameExtension;

struct {
    ServerName server_name_list<1..2^16-1>
} ServerNameList;

struct {
    NameType name_type;
    select (NameType) {
        case host_name: HostName;
    } name;
} ServerName;

opaque HostName<1..2^16-1>;
```

`ServerNameList` の定義にある `<1..2^16-1>` は、リスト全体の長さが2バイトのフィールドで示されることを意味します。つまり、`data[0]<<8 | data[1]` は `ServerNameList` の**バイト長**を示すべきでした。

しかし、元のコードではこの2バイトを `numNames` (要素数) として解釈し、その `numNames` の回数だけループを回していました。現在のSNI仕様では `ServerNameList` には常に1つの `ServerName` エントリ（ホスト名）しか含まれないため、`data[0]<<8 | data[1]` の値が偶然にも1（またはそれ以下の小さな値）となり、ループが最初の要素で停止するため、実害はありませんでした。

この誤った解釈は、将来的にSNI拡張が複数のホスト名や他の種類の名前をサポートするように変更された場合、パースが失敗するか、不正なデータを読み込む原因となる可能性がありました。

## コアとなるコードの変更箇所

`src/crypto/tls/handshake_messages.go` ファイルの `func (m *clientHelloMsg) unmarshal(data []byte) bool` メソッド内の `extensionServerName` ケースが変更されました。

```diff
--- a/src/crypto/tls/handshake_messages.go
+++ b/src/crypto/tls/handshake_messages.go
@@ -367,12 +367,16 @@ func (m *clientHelloMsg) unmarshal(data []byte) bool {\n \n \t\tswitch extension {\n \t\tcase extensionServerName:\n-\t\t\tif length < 2 {\n+\t\t\td := data[:length]\n+\t\t\tif len(d) < 2 {\n \t\t\t\treturn false\n \t\t\t}\n-\t\t\tnumNames := int(data[0])<<8 | int(data[1])\n-\t\t\td := data[2:]\n-\t\t\tfor i := 0; i < numNames; i++ {\n+\t\t\tnamesLen := int(d[0])<<8 | int(d[1])\n+\t\t\td = d[2:]\n+\t\t\tif len(d) != namesLen {\n+\t\t\t\treturn false\n+\t\t\t}\n+\t\t\tfor len(d) > 0 {\n \t\t\t\tif len(d) < 3 {\n \t\t\t\t\treturn false\n \t\t\t\t}\n@@ -383,7 +387,7 @@ func (m *clientHelloMsg) unmarshal(data []byte) bool {\n \t\t\t\t\treturn false\n \t\t\t\t}\n \t\t\t\tif nameType == 0 {\n-\t\t\t\t\tm.serverName = string(d[0:nameLen])\n+\t\t\t\t\tm.serverName = string(d[:nameLen])\n \t\t\t\t\tbreak\n \t\t\t\t}\n \t\t\t\td = d[nameLen:]\n```

主な変更点は以下の通りです。

1.  `data` スライスを `length` で制限した新しいスライス `d` を作成。
2.  `numNames` の代わりに `namesLen` を導入し、`data[0]<<8 | data[1]` を `ServerNameList` の**バイト長**として正しく解釈。
3.  `d` から `namesLen` の2バイトをスキップした後、残りのデータ長が `namesLen` と一致するかを検証。
4.  ループ条件を `for i := 0; i < numNames; i++` から `for len(d) > 0` に変更し、残りのデータがなくなるまで要素をパースするように修正。
5.  ホスト名抽出時のスライス操作を `d[0:nameLen]` から `d[:nameLen]` に変更し、より簡潔に。

## コアとなるコードの解説

修正後のコードは、SNI拡張のデータ構造をRFC 6066に準拠して正確にパースします。

```go
		case extensionServerName:
			d := data[:length] // SNI拡張データ全体をdにコピー
			if len(d) < 2 {
				return false // データが短すぎる場合はエラー
			}
			namesLen := int(d[0])<<8 | int(d[1]) // ServerNameListのバイト長を正しく取得
			d = d[2:] // ServerNameListの長さフィールドをスキップ
			if len(d) != namesLen {
				return false // 実際のデータ長と宣言された長さが一致しない場合はエラー
			}
			for len(d) > 0 { // 残りのデータがなくなるまでループ
				if len(d) < 3 {
					return false // NameType (1バイト) + NameLen (2バイト) の最小長がない場合はエラー
				}
				nameType := d[0]
				nameLen := int(d[1])<<8 | int(d[2])
				d = d[3:] // NameTypeとNameLenフィールドをスキップ
				if len(d) < nameLen {
					return false // 実際のデータ長が宣言されたNameLenより短い場合はエラー
				}
				if nameType == 0 { // ホスト名タイプの場合
					m.serverName = string(d[:nameLen]) // ホスト名を正しく抽出
					break // ホスト名が見つかったらループを終了
				}
				d = d[nameLen:] // 現在の要素をスキップして次の要素へ
			}
```

この修正により、`namesLen` は `ServerNameList` の実際のバイト長として扱われ、`for len(d) > 0` ループは、`ServerNameList` 内のすべての `ServerName` エントリを、そのバイト長に基づいて正しく処理できるようになります。これにより、将来SNI拡張の仕様が変更され、複数のホスト名や異なる種類の名前が導入された場合でも、GoのTLS実装が堅牢に動作することが保証されます。

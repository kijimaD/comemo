# [インデックス 20815] ファイルの概要

## コミット

`net/http: Rangeリクエスト時に暗黙的なgzipのAccept-Encodingを送信しない`

このコミットは、Go言語の標準ライブラリである`net/http`パッケージがHTTPリクエストを送信する際の挙動を修正するものです。具体的には、`Range`ヘッダ（コンテンツの部分的な取得を要求するヘッダ）を含むHTTPリクエストを送信する場合に、クライアントが自動的に`Accept-Encoding: gzip`ヘッダを追加するデフォルトの動作を抑制します。これにより、部分的なコンテンツとgzip圧縮の組み合わせによって発生する可能性のある、透過的な解凍の失敗や不整合なデータ処理の問題を回避します。

## 元コミット内容

```
commit 42c3130780327299cb8a89f30b8e5c3d6b96d2c2
Author: Brad Fitzpatrick <bradfitz@golang.org>
Date:   Wed Oct 15 17:51:30 2014 +0200

    net/http: don't send implicit gzip Accept-Encoding on Range requests
    
    The http package by default adds "Accept-Encoding: gzip" to outgoing
    requests, unless it's a bad idea, or the user requested otherwise.
    Only when the http package adds its own implicit Accept-Encoding header
    does the http package also transparently un-gzip the response.
    
    If the user requested part of a document (e.g. bytes 40 to 50), it appears
    that Github/Varnish send:
            range(gzip(content), 40, 50)
    
    And not:
            gzip(range(content, 40, 50))
    
    The RFC 2616 set of replacements (with the purpose of
    clarifying ambiguities since 1999) has an RFC about Range
    requests (http://tools.ietf.org/html/rfc7233) but does not
    mention the interaction with encodings.
    
    Regardless of whether range(gzip(content)) or gzip(range(content)) is
    correct, this change prevents the Go package from asking for gzip
    in requests if we're also asking for Range, avoiding the issue.
    If the user cared, they can do it themselves. But Go transparently
    un-gzipping a fragment of gzip is never useful.
    
    Fixes #8923
    
    LGTM=adg
    R=adg
    CC=golang-codereviews
    https://golang.org/cl/155420044
```

## 変更の背景

Goの`net/http`パッケージは、HTTPリクエストを送信する際に、デフォルトで`Accept-Encoding: gzip`ヘッダを自動的に追加し、それに対応してサーバーからgzip圧縮されたレスポンスが返された場合には、そのコンテンツを透過的に解凍する機能を持っていました。これは、クライアント側で圧縮・解凍の処理を意識することなく、効率的なデータ転送を実現するための便利な機能です。

しかし、この透過的なgzip解凍のメカニズムが、`Range`ヘッダ（HTTPリソースの部分的なコンテンツを要求するためのヘッダ）を含むリクエストと組み合わされた場合に問題が発生することが判明しました。具体的には、ユーザーがドキュメントの一部（例: 40バイト目から50バイト目まで）を要求した場合、GitHubやVarnishのような一部のサーバーは、以下のような形式で応答することが観察されました。

`range(gzip(content), 40, 50)`

これは、「まずコンテンツ全体をgzip圧縮し、その圧縮されたデータストリームから指定されたバイト範囲を切り出して送信する」という意味です。理想的には、`gzip(range(content, 40, 50))`、つまり「まずコンテンツの一部を切り出し、その部分をgzip圧縮して送信する」という形式が望ましい場合もありますが、サーバーの実装は前者でした。

この`range(gzip(content))`形式で送信された部分的なgzipデータは、完全なgzipストリームではありません。そのため、Goクライアントがこの部分的なデータを透過的に解凍しようとすると、解凍に失敗するか、意味のない破損したデータが生成される可能性がありました。Goの透過的なgzip解凍機能は、完全なgzipストリームを前提としているため、部分的なストリームの解凍は有用ではありません。

HTTP/1.1の仕様を明確化するために策定されたRFC 7233（Range Requestsに関するもの）には、`Range`ヘッダとコンテンツエンコーディング（特にgzip）の相互作用について明確な記述がありませんでした。この曖昧さが、サーバーとクライアント間の挙動の不一致を引き起こす一因となっていました。

この問題を解決し、Goクライアントの堅牢性を高めるため、Go issue #8923として報告されたこの挙動が修正されることになりました。修正の目的は、`Range`ヘッダを含むリクエストの場合には、Goクライアントが暗黙的に`Accept-Encoding: gzip`ヘッダを送信しないようにすることです。これにより、開発者が明示的に`Accept-Encoding`ヘッダを設定しない限り、この特定のシナリオでの問題発生を防ぎます。もしユーザーが`Range`リクエストとgzip圧縮を組み合わせたい場合は、明示的に`Accept-Encoding`ヘッダを設定することで、その意図を表明できるようになります。

## 前提知識の解説

このコミットの理解には、以下のHTTPおよびGo言語のネットワーキングに関する基本的な知識が役立ちます。

*   **HTTP `Accept-Encoding` ヘッダ**:
    HTTPリクエストヘッダの一つで、クライアントが理解できるコンテンツエンコーディング（圧縮方式）をサーバーに伝えるために使用されます。最も一般的な値は`gzip`で、これはクライアントがgzip形式で圧縮されたレスポンスを処理できることを示します。サーバーは、このヘッダを見て、クライアントがサポートするエンコーディングでコンテンツを圧縮して送信するかどうかを決定します。

*   **HTTP `Range` ヘッダ**:
    HTTPリクエストヘッダの一つで、クライアントがリソース全体ではなく、その一部（バイト範囲）のみを要求するために使用されます。例えば、`Range: bytes=0-99`はリソースの最初の100バイトを要求します。これは、大きなファイルのダウンロードを再開したり、動画や音声のストリーミングで特定の部分にシークしたりする際に利用されます。

*   **HTTP `Content-Encoding` ヘッダ**:
    HTTPレスポンスヘッダの一つで、サーバーがレスポンスボディに適用したエンコーディング（圧縮方式）を示します。例えば、`Content-Encoding: gzip`は、レスポンスボディがgzip形式で圧縮されていることを示します。

*   **HTTP 206 Partial Content**:
    HTTPステータスコードの一つで、`Range`リクエストが成功し、サーバーが要求されたリソースの部分的なコンテンツを送信する際に返されます。このステータスコードと共に、`Content-Range`ヘッダが送信され、返されたコンテンツがリソース全体のどの部分であるかを示します。

*   **透過的なgzip解凍 (Transparent Gzip Decompression)**:
    Goの`net/http`パッケージのようなHTTPクライアントライブラリが提供する機能の一つです。クライアントが`Accept-Encoding: gzip`ヘッダを送信し、サーバーが`Content-Encoding: gzip`ヘッダと共に圧縮されたレスポンスを返した場合、クライアントライブラリが自動的にそのコンテンツを解凍し、アプリケーションコードには解凍済みのデータとして渡します。これにより、アプリケーション開発者は圧縮・解凍のロジックを自分で実装する必要がなくなります。

*   **`range(gzip(content))` と `gzip(range(content))` の違い**:
    このコミットの背景にある重要な概念です。
    *   **`gzip(range(content))`**: これは、まずオリジナルのコンテンツから指定されたバイト範囲を切り出し、その「部分的なコンテンツ」をgzip圧縮するという処理順序を示します。この場合、圧縮されたデータは完全なgzipストリームであり、通常のgzip解凍器で問題なく解凍できます。
    *   **`range(gzip(content))`**: これは、まずオリジナルのコンテンツ全体をgzip圧縮し、その「圧縮されたデータストリーム」から指定されたバイト範囲を切り出すという処理順序を示します。この場合、切り出されたデータはgzipストリームの「一部」であり、それ自体が完全なgzipストリームではありません。したがって、通常のgzip解凍器でこれを解凍しようとすると、エラーになるか、不完全なデータが生成されます。一部のサーバーはこの形式で応答することがあり、これがGoの透過的な解凍機能との間で問題を引き起こしていました。

## 技術的詳細

このコミットの技術的な核心は、Goの`net/http`パッケージ内部におけるHTTPリクエストの送信ロジック、特に`Accept-Encoding`ヘッダの自動追加条件の変更にあります。

Goの`net/http`パッケージは、`http.Client`がリクエストを送信する際に、デフォルトで`Accept-Encoding: gzip`ヘッダをリクエストに追加します。これは、`Transport`構造体の`DisableCompression`フィールドが`false`（デフォルト値）であり、かつリクエストに`Accept-Encoding`ヘッダが明示的に設定されていない場合に適用されます。この自動追加は、サーバーがgzip圧縮をサポートしている場合に、ネットワーク帯域幅の節約と転送速度の向上に寄与します。

しかし、前述の通り、`Range`ヘッダを含むリクエストの場合、サーバーが`range(gzip(content))`形式で応答することがあり、この際にGoクライアントが透過的に解凍しようとすると問題が発生します。この問題を解決するため、コミットでは`src/net/http/transport.go`ファイル内の`persistConn.roundTrip`メソッド（HTTPリクエストの実際の送信処理を行う部分）のロジックが変更されました。

変更前は、`Accept-Encoding: gzip`ヘッダを自動追加する条件は以下の通りでした。
1.  `pc.t.DisableCompression`が`false`であること。
2.  リクエストの`Accept-Encoding`ヘッダが空であること。
3.  リクエストメソッドが`HEAD`ではないこと。

このコミットでは、上記の条件に加えて、**リクエストに`Range`ヘッダが存在しないこと** (`req.Header.Get("Range") == ""`) という新しい条件が追加されました。

```go
// src/net/http/transport.go の変更箇所 (抜粋)
// Old code:
// if !pc.t.DisableCompression && req.Header.Get("Accept-Encoding") == "" && req.Method != "HEAD" {

// New code:
if !pc.t.DisableCompression &&
    req.Header.Get("Accept-Encoding") == "" &&
    req.Header.Get("Range") == "" && // <-- この行が追加された
    req.Method != "HEAD" {
    // ... (gzipを要求するロジック)
}
```

この変更により、`Range`ヘッダがリクエストに設定されている場合、Goクライアントは自動的に`Accept-Encoding: gzip`ヘッダを送信しなくなります。これにより、サーバーが`range(gzip(content))`形式で応答した場合でも、Goクライアントが不適切に透過的な解凍を試みることを防ぎ、結果として発生する可能性のあるエラーやデータ破損を回避します。

この修正は、Goの`net/http`パッケージの透過的な機能が、特定のHTTPヘッダの組み合わせ（`Range`と`Accept-Encoding`）において予期せぬ副作用をもたらす可能性があった点を改善するものです。開発者が明示的に`Accept-Encoding`ヘッダを設定しない限り、この問題は発生しなくなります。もし開発者が`Range`リクエストとgzip圧縮を意図的に組み合わせたい場合は、リクエストヘッダに`Accept-Encoding: gzip`を明示的に設定することで、Goの自動的な抑制を上書きできます。

また、この変更には、`net/http/response_test.go`と`net/http/transport_test.go`に新しいテストケースが追加されています。これにより、HTTP 206 Partial Contentのレスポンスが正しく処理されること、そして`Range`ヘッダを持つリクエストが`Accept-Encoding: gzip`を自動的に送信しないことが検証され、修正の正当性と将来的な回帰の防止が図られています。

## コアとなるコードの解説

### `src/net/http/transport.go` の変更点

このファイルは、Goの`net/http`パッケージにおけるHTTPトランスポート層の核心部分を担っています。特に、`persistConn.roundTrip`メソッドは、実際のHTTPリクエストの送信とレスポンスの受信を処理します。

変更されたコードブロックは、Goクライアントが`Accept-Encoding: gzip`ヘッダをリクエストに自動的に追加するかどうかを決定する部分です。

**変更前（概念）:**
```go
// Accept-Encoding: gzip を自動追加する条件:
// 1. 圧縮が無効化されていない (DisableCompression == false)
// 2. Accept-Encoding ヘッダがリクエストに明示的に設定されていない
// 3. リクエストメソッドが HEAD ではない
if !pc.t.DisableCompression && req.Header.Get("Accept-Encoding") == "" && req.Method != "HEAD" {
    // Accept-Encoding: gzip を追加
    requestedGzip = true
    req.extraHeaders().Set("Accept-Encoding", "gzip")
}
```

**変更後（実際のコードスニペットと解説）:**
```go
// src/net/http/transport.go
// ...
func (pc *persistConn) roundTrip(req *transportRequest) (resp *Response, err error) {
    // ...
    // Ask for a compressed version if the caller didn't set their
    // own value for Accept-Encoding. We only attempt to
    // uncompress the gzip stream if we were the layer that
    // requested it.
    requestedGzip := false
    if !pc.t.DisableCompression &&
        req.Header.Get("Accept-Encoding") == "" &&
        req.Header.Get("Range") == "" && // <-- この行が追加された
        req.Method != "HEAD" {
        // Request gzip only, not deflate. Deflate is ambiguous and
        // not as universally supported anyway.
        // See: http://www.gzip.org/zlib/zlib_faq.html#faq38
        //
        // We don't request gzip if the request is for a range, since
        // auto-decoding a portion of a gzipped document will just fail
        // anyway. See http://golang.org/issue/8923
        requestedGzip = true
        req.extraHeaders().Set("Accept-Encoding", "gzip")
    }
    // ...
}
```
追加された`req.Header.Get("Range") == ""`という条件は、リクエストに`Range`ヘッダが設定されているかどうかをチェックします。この条件が`false`（つまり`Range`ヘッダが存在する）の場合、たとえ他の条件が満たされていても、`Accept-Encoding: gzip`ヘッダは自動的に追加されなくなります。これにより、`Range`リクエストと透過的なgzip解凍の間の非互換性が解消されます。コメントにも明記されている通り、「部分的なgzippedドキュメントを自動解凍しても失敗するだけなので、Rangeリクエストの場合はgzipを要求しない」という意図が反映されています。

### `src/net/http/response_test.go` の変更点

このファイルは、HTTPレスポンスのパースと処理に関するテストを含んでいます。

追加されたテストケースは、HTTP 206 Partial ContentレスポンスがGoクライアントによって正しく解釈され、そのヘッダ（`Content-Type`, `Accept-Ranges`, `Content-Range`, `Content-Length`）とボディが期待通りにパースされることを検証します。これは、今回の変更が`Range`リクエストの基本的な処理に悪影響を与えないことを保証するためのものです。

### `src/net/http/transport_test.go` の変更点

このファイルは、`net/http`パッケージのトランスポート層の動作に関するテストを含んでいます。

追加された`TestTransportRangeAndGzip`関数は、今回の修正の核心的な動作を直接検証します。
```go
// src/net/http/transport_test.go
// ...
// This tests that an client requesting a content range won't also
// implicitly ask for gzip support. If they want that, they need to do it
// on their own.
// golang.org/issue/8923
func TestTransportRangeAndGzip(t *testing.T) {
    defer afterTest(t)
    reqc := make(chan *Request, 1)
    ts := httptest.NewServer(HandlerFunc(func(w ResponseWriter, r *Request) {
        reqc <- r
    }))
    defer ts.Close()

    req, _ := NewRequest("GET", ts.URL, nil)
    req.Header.Set("Range", "bytes=7-11") // Range ヘッダを設定
    res, err := DefaultClient.Do(req)
    if err != nil {
        t.Fatal(err)
    }

    select {
    case r := <-reqc:
        // Accept-Encoding ヘッダに "gzip" が含まれていないことを検証
        if strings.Contains(r.Header.Get("Accept-Encoding"), "gzip") {
            t.Error("Transport advertised gzip support in the Accept header")
        }
        // Range ヘッダがリクエストに含まれていることを検証
        if r.Header.Get("Range") == "" {
            t.Error("no Range in request")
        }
    case <-time.After(10 * time.Second):
        t.Fatal("timeout")
    }
    res.Body.Close()
}
```
このテストでは、`Range: bytes=7-11`ヘッダを持つHTTP GETリクエストをテストサーバーに送信します。その後、テストサーバーが受信したリクエストのヘッダをチェックし、`Accept-Encoding`ヘッダに`gzip`が含まれていないこと、そして`Range`ヘッダが正しく設定されていることを確認します。これにより、`Range`リクエスト時にGoクライアントが暗黙的にgzip圧縮を要求しないという、今回の修正の意図された動作が保証されます。

# [インデックス 22901] ファイルの概要

このコミットは、Goプログラムが`c-archive`または`c-shared`ビルドモードでC言語のアプリケーションに組み込まれる際に発生する可能性のある、Cgoコールバックのタイミング問題を解決します。具体的には、Goランタイムの初期化は完了しているものの、Goパッケージの`init`関数群がまだ実行中の段階で、CgoからのGo関数呼び出しが行われた場合に、その呼び出しがパッケージ初期化の完了を待つように修正します。

    With the new buildmodes c-archive and c-shared, it is possible for a

## 元コミット内容

このコミットは、Goランタイムにおいて、Cgoコールバックがパッケージの初期化完了を待つように変更します。

新しいビルドモードである`c-archive`および`c-shared`を使用すると、Goプログラムのライフサイクルの早い段階でCgo呼び出しが行われる可能性があります。ランタイムが初期化される前の呼び出しは`_cgo_wait_runtime_init_done`によって捕捉されますが、ランタイムが初期化された後でも、プログラムのパッケージ初期化関数が完了する前に呼び出しが行われる可能性があります。

これを回避するため、`cgocallback`は`m.ncgo`をチェックし、Goを実行しているスレッド上にあるかどうかを確認します。もしそうでない場合（外部スレッドである可能性が高い）、`main_init`が完了するまでブロックします。

## 変更の背景

Go 1.5で導入された`c-archive`および`c-shared`という新しいビルドモードは、GoのコードをC言語のライブラリとしてコンパイルし、既存のC/C++アプリケーションに組み込むことを可能にしました。これにより、Goの強力な並行処理やガベージコレクションといった機能を、C/C++のプロジェクトで利用できるようになります。

しかし、この新しい統合方法には、Goプログラムの初期化タイミングに関する新たな課題が浮上しました。Goプログラムが起動する際には、いくつかの重要な初期化ステップがあります。

1.  **ランタイムの初期化**: Goランタイム自体が起動し、スケジューラ、メモリ管理、ガベージコレクタなどの基本的なコンポーネントが設定されます。
2.  **パッケージの初期化**: プログラム内の各パッケージに定義された`init`関数が、依存関係の順序に従って実行されます。これらの`init`関数は、グローバル変数の設定、リソースの初期化、一度だけ実行されるべきセットアップ処理など、アプリケーションの動作に不可欠な処理を行うことがよくあります。
3.  **`main`関数の実行**: すべてのパッケージの`init`関数が完了した後、プログラムのエントリポイントである`main`関数が実行されます。

従来のGoアプリケーションでは、`main`関数が実行される前にすべての初期化が完了していることが保証されていました。しかし、`c-archive`や`c-shared`ビルドモードでは、C言語側からGoの関数を呼び出すことが可能になります。このとき、C言語側からの呼び出しが、Goランタイムの初期化は完了しているものの、Goパッケージの`init`関数がまだ実行中の「中途半端な」状態で行われる可能性がありました。

このような状況でCgoコールバックが発生すると、Goの関数が、まだ完全に初期化されていないパッケージのデータやリソースにアクセスしようとして、予期せぬ動作、クラッシュ、またはデッドロックを引き起こす可能性がありました。このコミットは、このタイミングの問題を解決し、CgoコールバックがGoプログラムの完全な初期化（特にパッケージの`init`関数の完了）を待つようにすることで、堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットの理解には、以下のGo言語およびランタイムに関する知識が不可欠です。

1.  **Goのビルドモード (`c-archive`, `c-shared`)**:
    *   **`c-archive`**: Goのコードを静的ライブラリ（`.a`ファイル）としてコンパイルします。このライブラリはC/C++アプリケーションにリンクされ、Goの関数をCの関数として呼び出すことができます。Goランタイム全体がC/C++アプリケーションに組み込まれます。
    *   **`c-shared`**: Goのコードを共有ライブラリ（`.so`または`.dylib`ファイル）としてコンパイルします。このライブラリはC/C++アプリケーションから動的にロードされ、Goの関数をCの関数として呼び出すことができます。
    これらのビルドモードは、Goを既存のC/C++エコシステムに統合するための強力な手段ですが、Goランタイムの初期化とCgo呼び出しのタイミングに関する複雑さを伴います。

2.  **Cgo (CとGoの相互運用)**:
    Cgoは、GoプログラムからC言語のコードを呼び出したり、C言語のコードからGoの関数を呼び出したりするためのGoの機能です。Goのソースファイル内にCのコードを記述したり、既存のCライブラリをリンクしたりすることができます。
    *   **GoからCへの呼び出し**: GoのコードからCの関数を呼び出す場合、Goランタイムは現在のGoroutineをCスタックに切り替え、C関数を実行します。
    *   **CからGoへの呼び出し (Cgoコールバック)**: CのコードからGoの関数を呼び出す場合、GoランタイムはCのスレッドをGoのM（OSスレッド）にアタッチし、Goの関数を実行します。この「CからGoへの呼び出し」が本コミットの主要な焦点です。

3.  **Goランタイムの初期化 (`runtime_init`, `main_init`)**:
    Goプログラムが起動すると、まずランタイムの初期化が行われます。
    *   `runtime_init()`: Goランタイムの基本的なコンポーネント（スケジューラ、メモリ管理など）を初期化します。
    *   `main_init()`: プログラム内のすべてのパッケージの`init`関数を呼び出します。Goの仕様により、`main`関数が実行される前にすべての`init`関数が実行されることが保証されています。

4.  **パッケージ初期化関数 (`init` 関数)**:
    Goの各パッケージは、`init`という特別な関数を定義できます。この関数は、パッケージがインポートされたとき（またはプログラムの起動時）に、`main`関数が実行される前に自動的に一度だけ実行されます。`init`関数は、パッケージ固有の初期化ロジック（例: データベース接続の確立、設定ファイルの読み込み、グローバル変数の初期化）を実行するために使用されます。

5.  **GoのスケジューラとM (Machine), P (Processor), G (Goroutine)**:
    Goランタイムは、独自のスケジューラを使用してGoroutineをOSスレッド（M）上で実行します。
    *   **G (Goroutine)**: Goの軽量な並行実行単位。
    *   **M (Machine)**: OSスレッド。Goのコードを実行する実際のOSスレッドです。
    *   **P (Processor)**: 論理プロセッサ。MがGoのコードを実行するために必要なコンテキストを提供します。
    *   **`m.ncgo`**: `M`構造体の一部で、そのOSスレッド上で現在アクティブなCgo呼び出しの数を追跡するカウンターです。Goのコードを実行しているスレッドでは通常0ですが、Cgo呼び出しが行われるとインクリメント/デクリメントされます。特に、C言語側からGoの関数が呼び出された場合、そのCスレッドはGoのMにアタッチされ、`m.ncgo`が0であることで、それがGoランタイムによって管理されていない「外部スレッド」からの呼び出しであると識別できます。

6.  **チャネルの基本的な動作**:
    Goのチャネルは、Goroutine間で値を送受信するための通信メカニズムです。
    *   `<-ch`: チャネル`ch`から値を受信します。チャネルに値が送信されるまでブロックします。
    *   `close(ch)`: チャネル`ch`を閉じます。閉じられたチャネルから受信しようとすると、チャネルにまだ値が残っていればその値を受け取り、値がなければゼロ値を受け取り、すぐにブロックせずに完了します。この特性は、Goroutine間の同期メカニズムとしてよく利用されます。チャネルを閉じることで、そのチャネルでブロックしているすべての受信Goroutineを解放することができます。

## 技術的詳細

このコミットの核心は、CgoコールバックがGoプログラムのパッケージ初期化の完了を待つための同期メカニズムの導入です。

1.  **問題の特定**:
    `c-archive`や`c-shared`ビルドモードでは、C言語のコードがGoの関数を呼び出すことができます。この呼び出しは、Goランタイムが起動し、基本的な準備が整った後でも、Goのパッケージ`init`関数がまだ実行中の段階で発生する可能性がありました。`init`関数は、アプリケーションの動作に必要な重要なセットアップを行うため、これらが完了する前にGoの関数が実行されると、未初期化のリソースへのアクセスなどにより問題が発生します。

2.  **`main_init_done`チャネルの導入**:
    この問題を解決するために、`src/runtime/proc.go`に`main_init_done`という新しいチャネルが導入されました。
    ```go
    // main_init_done is a signal used by cgocallbackg that initialization
    // has been completed. It is made before _cgo_notify_runtime_init_done,
    // so all cgo calls can rely on it existing. When main_init is complete,
    // it is closed, meaning cgocallbackg can reliably receive from it.
    var main_init_done chan bool
    ```
    このチャネルは、Goプログラムの`main`関数内で作成され、すべてのパッケージ`init`関数（`main_init()`の呼び出しによって実行される）が完了した直後に閉じられます。

3.  **`runtime.main`での`main_init_done`の管理**:
    `src/runtime/proc.go`の`main`関数（Goプログラムのエントリポイント）が変更され、`main_init_done`チャネルのライフサイクルを管理します。
    ```go
    func main() {
        // ...
        main_init_done = make(chan bool) // チャネルの作成
        // ...
        main_init()                      // すべてのパッケージinit関数を実行
        close(main_init_done)            // パッケージinit完了後、チャネルを閉じる
        // ...
    }
    ```
    `main_init_done`チャネルはバッファなしチャネルとして作成されます。`main_init()`が完了し、`close(main_init_done)`が呼び出されると、このチャネルでブロックしているすべての受信Goroutineが解放されます。

4.  **`cgocallbackg1`での同期**:
    `src/runtime/cgocall.go`の`cgocallbackg1`関数は、Cgoコールバック（CからGoへの呼び出し）を処理するGoランタイム内の重要な関数です。この関数に以下のロジックが追加されました。
    ```go
    func cgocallbackg1() {
        // ...
        if gp.m.ncgo == 0 {
            // The C call to Go came from a thread not currently running
            // any Go. In the case of -buildmode=c-archive or c-shared,
            // this call may be coming in before package initialization
            // is complete. Wait until it is.
            <-main_init_done
        }
        // ...
    }
    ```
    *   `gp.m.ncgo == 0`のチェック: `gp.m`は現在のGoroutineが実行されているM（OSスレッド）を指します。`m.ncgo`が0であるということは、そのOSスレッドが現在Goのコードを実行しておらず、Cgo呼び出しが外部のCスレッドからGoランタイムに「入ってきた」ことを意味します。これは、`c-archive`や`c-shared`ビルドモードで発生する可能性のあるシナリオです。
    *   `<-main_init_done`: もし外部スレッドからの呼び出しであれば、`cgocallbackg1`は`main_init_done`チャネルからの受信を試みます。`main_init_done`チャネルは、すべてのパッケージ`init`関数が完了するまで閉じられないため、この受信操作は`init`関数が完了するまでブロックします。これにより、CgoコールバックはGoプログラムが完全に初期化されるまで待機することになります。

5.  **テストコードの変更**:
    `misc/cgo/testcarchive/`ディレクトリ内のテストコードも更新され、この新しい同期メカニズムが正しく機能することを確認します。
    *   `misc/cgo/testcarchive/src/libgo/libgo.go`:
        *   `initCh`というチャネルと`time.Sleep`を導入し、意図的に遅いパッケージ初期化をシミュレートします。
        *   `DidInitRun`関数が`initCh`からの受信を試みるように変更され、パッケージ初期化が完了したかどうかをより正確にテストできるようにします。
    *   `misc/cgo/testcarchive/main.c`:
        *   テストロジックが更新され、`DidInitRun()`と`DidMainRun()`の呼び出し順序と期待される結果が、新しい初期化同期の動作に合わせて調整されます。これにより、Cgoコールがパッケージ初期化前に発生した場合でも、Go側が正しく待機することを確認します。

この変更により、`c-archive`や`c-shared`ビルドモードでGoのコードをC/C++アプリケーションに組み込む際の堅牢性が大幅に向上し、Goのパッケージ初期化が完了する前にCgoコールバックによってGoの関数が呼び出されることによる潜在的な問題を回避できるようになりました。

## コアとなるコードの解説

### `src/runtime/cgocall.go` の変更

`cgocallbackg1`関数は、C言語からGoの関数が呼び出された際に、Goランタイムがその呼び出しを処理するために使用する内部関数です。

```go
	if gp.m.ncgo == 0 {
		// The C call to Go came from a thread not currently running
		// any Go. In the case of -buildmode=c-archive or c-shared,
		// this call may be coming in before package initialization
		// is complete. Wait until it is.
		<-main_init_done
	}
```
このコードブロックは、CgoコールバックがGoランタイムの初期化プロセス中に発生した場合の同期メカニズムを導入します。
*   `gp.m.ncgo == 0`: これは、現在のOSスレッド（M）がGoのコードを実行していない（つまり、Goランタイムによって管理されていない外部のCスレッドである）ことを示します。`ncgo`は、そのスレッド上で現在アクティブなCgo呼び出しの数を追跡するカウンターです。外部スレッドからのGoへの呼び出しの場合、この値は通常0です。
*   `<-main_init_done`: もし呼び出しが外部スレッドから来たものであれば、`cgocallbackg1`は`main_init_done`チャネルからの受信を試みます。このチャネルは、Goプログラムのすべてのパッケージ`init`関数が完了するまで閉じられません。したがって、この行は、パッケージ初期化が完了するまで`cgocallbackg1`の実行をブロックします。これにより、Cgoコールバックが未初期化のGoパッケージにアクセスするのを防ぎます。

### `src/runtime/proc.go` の変更

このファイルはGoランタイムのプロセス管理に関するコードを含んでいます。

```go
// main_init_done is a signal used by cgocallbackg that initialization
// has been completed. It is made before _cgo_notify_runtime_init_done,
// so all cgo calls can rely on it existing. When main_init is complete,
// it is closed, meaning cgocallbackg can reliably receive from it.
var main_init_done chan bool
```
`main_init_done`という新しいグローバルチャネルが宣言されています。このチャネルは、Goプログラムのパッケージ初期化が完了したことを`cgocallbackg`（および関連するCgoコールバック処理）に通知するためのシグナルとして機能します。チャネルが閉じられることで、初期化完了のシグナルが送られます。

```go
func main() {
	// ...
	main_init_done = make(chan bool)
	// ...
	main_init()
	close(main_init_done)
	// ...
}
```
`runtime.main`関数はGoプログラムのエントリポイントです。
*   `main_init_done = make(chan bool)`: `main`関数の早い段階で、`main_init_done`チャネルが作成されます。これにより、Cgoコールバックが非常に早い段階で発生した場合でも、このチャネルが存在することが保証されます。
*   `main_init()`: この関数呼び出しは、Goプログラム内のすべてのパッケージの`init`関数を実行します。Goの仕様により、`main`関数が実行される前にすべての`init`関数が完了することが保証されています。
*   `close(main_init_done)`: `main_init()`が完了した直後に、`main_init_done`チャネルが閉じられます。チャネルが閉じられると、そのチャネルでブロックしているすべての受信操作（`cgocallbackg1`内の`<-main_init_done`など）が即座に完了し、ブロックが解除されます。これにより、パッケージ初期化が完了したことが効果的にシグナルされます。

### `misc/cgo/testcarchive/src/libgo/libgo.go` の変更

このファイルは、`c-archive`ビルドモードのテストに使用されるGoライブラリのサンプルコードです。

```go
var initCh = make(chan int, 1)
// ...
func init() {
	// emulate an exceedingly slow package initialization function
	time.Sleep(100 * time.Millisecond)
	initCh <- 42
}
// ...
func DidInitRun() bool {
	select {
	case x := <-initCh:
		if x != 42 {
			// Just in case initCh was not correctly made.
			println("want init value of 42, got: ", x)
			syscall.Exit(2)
		}
		return true
	default:
		return false
	}
}
```
*   `initCh`チャネルの導入と`init()`関数の変更: `init()`関数は、パッケージ初期化が意図的に遅延するように`time.Sleep`を追加し、`initCh`に値を送信します。これは、Cgoコールバックがパッケージ初期化中に発生するシナリオをシミュレートするためのものです。
*   `DidInitRun()`関数の変更: この関数は、パッケージの`init`関数が実行されたかどうかを外部（Cコード）から確認するために使用されます。`select`ステートメントを使用して`initCh`からの受信を試みます。これにより、`init`関数が完了して`initCh`に値が送信されるまで、この関数が真を返さないようにします。`default`ケースがあるため、`init`が完了していない場合はブロックせずに`false`を返します。

### `misc/cgo/testcarchive/main.c` の変更

このファイルは、`c-archive`ビルドモードでコンパイルされたGoライブラリを呼び出すC言語のテストプログラムです。

```c
	if (!DidInitRun()) {
		fprintf(stderr, "ERROR: buildmode=c-archive init should run\n");
		return 2;
	}

	if (DidMainRun()) {
		fprintf(stderr, "ERROR: buildmode=c-archive should not run main\n");
		return 2;
	}
```
テストロジックが変更され、`DidInitRun()`と`DidMainRun()`の呼び出しと期待される結果が調整されています。
*   `if (!DidInitRun())`: これは、Goのパッケージ`init`関数が実行されたことを確認します。新しい同期メカニズムにより、Cgoコールバックが`DidInitRun()`を呼び出す場合、Go側は`init`関数が完了するまで待機するため、このチェックは成功するはずです。
*   `if (DidMainRun())`: `c-archive`ビルドモードでは、Goの`main`関数は通常実行されません（ライブラリとして機能するため）。このチェックは、その動作が維持されていることを確認します。

これらの変更は、GoランタイムがCgoコールバックを処理する際の堅牢性を高め、特にGoコードがC/C++アプリケーションに組み込まれるシナリオにおいて、Goプログラムの初期化状態に関する潜在的な競合状態を排除します。

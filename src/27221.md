## 変更の背景

このコミットの主な背景は、Goランタイムにおける**並行スタック縮小 (concurrent stack shrinking)** の導入計画です。Goのgoroutineは可変サイズのスタックを使用しており、必要に応じてスタックを拡張したり縮小したりします。スタック縮小は、メモリ使用量を最適化するために重要ですが、これが並行して行われる場合、チャネル操作中に問題を引き起こす可能性があります。

具体的には、`sudog`構造体の`elem`フィールドは、チャネルを介して送受信されるデータ要素へのポインタを保持しています。これまでのランタイムでは、`sudog.elem`は並行にアクセスされることがなかったため、チャネルのロック（`hchan.lock`）が解除された後に`sudog.elem`が読み書きされるケースがありました。

しかし、並行スタック縮小が導入されると、`sudog`がスタック上に存在する場合、そのスタックが縮小される際に`sudog.elem`が指すアドレスも新しいスタック上の位置に調整される必要があります。この調整が、チャネル操作による`sudog.elem`へのアクセスと同時に行われると、競合状態（data race）が発生し、不正なメモリアクセスやプログラムのクラッシュにつながる可能性があります。

この問題を未然に防ぐため、`sudog.elem`へのアクセスも`hchan.lock`によって保護されるべきであるという判断がなされました。これにより、スタック縮小が`sudog.elem`を調整する際と、チャネル操作が`sudog.elem`にアクセスする際の両方で、適切な同期が保証されます。

また、この変更に合わせて、チャネルの同期ルールに関するドキュメントも明確化され、ランタイムコードの可読性と保守性が向上しています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **Goroutine (ゴルーチン)**: Goの軽量な実行スレッドです。数千、数万のゴルーチンを同時に実行できます。各ゴルーチンは独自のスタックを持ちます。
2.  **Channel (チャネル)**: ゴルーチン間で値を送受信するための通信メカニズムです。チャネルは同期プリミティブとしても機能し、ゴルーチンの協調を可能にします。
3.  **`hchan` 構造体**: Goランタイム内部でチャネルを表現する構造体です。チャネルのバッファ、送受信キュー、そしてチャネルの状態を保護するためのミューテックス（`lock`フィールド）などを含みます。
    *   `lock mutex`: `hchan`構造体のフィールドや、このチャネルでブロックされている`sudog`の特定のフィールドを保護するためのミューテックスです。
4.  **`sudog` 構造体**: "Scheduler Utility Descriptor for Goroutine" の略で、チャネル操作（送受信）によってブロックされたゴルーチンを表現するためにランタイムが使用する構造体です。ゴルーチンがチャネルでブロックされると、`sudog`インスタンスが作成され、チャネルの送受信キュー（`sendq`または`recvq`）に追加されます。
    *   `g *g`: この`sudog`が関連付けられているゴルーチン（`g`構造体）へのポインタ。
    *   `elem unsafe.Pointer`: チャネルを介して送受信されるデータ要素へのポインタ。例えば、`ch <- value` の `value` や、`value := <-ch` の `value` が格納されるメモリ位置を指します。このポインタは、ゴルーチンのスタック上にあるメモリを指すことがあります。
5.  **スタックの動的伸縮**: Goのゴルーチンスタックは、必要に応じて自動的にサイズが変更されます。関数呼び出しが深くなるとスタックは拡張され、関数から戻るとスタックは縮小されることがあります。
6.  **並行スタック縮小 (Concurrent Stack Shrinking)**: Goランタイムの進化の一環として、スタックの縮小処理を、対象のゴルーチンが実行中であっても（つまり、他のゴルーチンと並行して）行えるようにする機能です。これにより、スタック縮小のためにゴルーチンを長時間停止させる必要がなくなり、レイテンシの改善や全体的なパフォーマンス向上が期待されます。しかし、この並行処理は、スタック上のデータへのポインタの整合性を維持するために、より厳密な同期メカニズムを必要とします。

## 技術的詳細

このコミットの核心は、`hchan.lock`の保護範囲を`sudog.elem`にまで拡張することです。

以前のGoランタイムでは、`sudog.elem`はチャネルのロックが解除された後にアクセスされることがありました。これは、`sudog.elem`がその時点では単一のゴルーチンによってのみアクセスされると仮定されていたためです。しかし、並行スタック縮小が導入されると、`sudog.elem`が指すメモリ領域（ゴルーチンのスタック上にある可能性が高い）が、スタック縮小プロセスによって移動される可能性があります。

この移動と、チャネル操作による`sudog.elem`への読み書きが同時に発生すると、以下の問題が生じます。

*   **データ競合**: `sudog.elem`が指すアドレスが変更されている最中に、チャネル操作が古いアドレスにアクセスしようとすると、不正なメモリにアクセスしたり、破損したデータを読み書きしたりする可能性があります。
*   **ポインタの無効化**: スタック縮小によって`sudog.elem`が指すスタック上の位置が移動した場合、`sudog.elem`自体も新しい位置を指すように更新される必要があります。この更新とチャネル操作が同期されていないと、`sudog.elem`が古い無効なアドレスを指し続けることになります。

このコミットでは、`send`関数と`recv`関数における`unlockf()`の呼び出し位置を変更することで、この問題を解決しています。`unlockf()`はチャネルのロックを解除する関数であり、これを`sudog.elem`へのアクセスが完了した後に移動させることで、`sudog.lock`が`sudog.elem`へのアクセス中も保持されるようにしています。

具体的には、`send`関数では、`sg.elem != nil` のブロック内で`sendDirect`が`sg.elem`を使用した後、そして`sg.elem = nil`が実行された後に`unlockf()`が呼び出されるように変更されています。同様に、`recv`関数では、`ep != nil` のブロック内で`recvDirect`が`sg.elem`を使用した後、そして`sg.elem = nil`が実行された後に`unlockf()`が呼び出されるように変更されています。

これにより、`hchan.lock`は、チャネルの内部状態だけでなく、チャネル操作に関連する`sudog.elem`へのアクセスも保護するようになります。並行スタック縮小が`sudog.elem`を調整する必要がある場合、`hchan.lock`を取得しようとしますが、チャネル操作が`hchan.lock`を保持している間はブロックされるため、安全に調整を行うことができます。

また、`hchan`と`sudog`の構造体定義にコメントが追加され、`hchan.lock`が保護するフィールドの範囲が明確に文書化されています。これは、将来のランタイム開発者がチャネルの同期メカニズムをより正確に理解し、誤った仮定に基づいてコードを書くことを防ぐのに役立ちます。

`send`関数と`recv`関数は、チャネルを介した値の送受信を処理するGoランタイムの重要な部分です。これらの関数は、チャネルの内部状態を操作するために`hchan.lock`を取得し、操作が完了するとロックを解除します。

変更前は、`unlockf()`（チャネルのロックを解除する関数）が`sg.elem`へのアクセスよりも早く呼び出される可能性がありました。例えば、`send`関数では、バッファリングされていないチャネルの場合、`unlockf()`が`sendDirect`（`sg.elem`を使用する）の前に呼び出されていました。

この変更により、`unlockf()`の呼び出しは、`sg.elem`が指すデータ要素への読み書きが完全に終了し、かつ`sg.elem`自体が`nil`に設定される（つまり、`sudog`がチャネル操作から切り離される）まで遅延されます。これにより、`hchan.lock`が`sudog.elem`へのアクセス全体を保護することが保証されます。

`hchan`と`sudog`構造体へのコメント追加は、この同期ルールを明示的に文書化するものです。これにより、ランタイムの複雑な並行処理のロジックがより理解しやすくなり、将来の変更やデバッグの際に役立ちます。特に、`sudog.elem`がスタック上のメモリを指す可能性があるという事実は、並行スタック縮小との相互作用において非常に重要であり、このコメントは開発者にとって重要な警告となります。

この変更は、Goランタイムの堅牢性を高め、将来の機能（並行スタック縮小）との互換性を確保するための予防的な措置と言えます。

3.  **`hchan` 構造体**: Goランタイム内部でチャネルを表現する構造体です。チャネルのバッファ、送受信キュー、そしてチャネルの状態を保護するためのミューテックス（`lock`フィールド）などを含みます。
    *   `lock mutex`: `hchan`構造体のフィールドや、このチャネルでブロックされている`sudog`の特定のフィールドを保護するためのミューテックスです。
4.  **`sudog` 構造体**: "Scheduler Utility Descriptor for Goroutine" の略で、チャネル操作（送受信）によってブロックされたゴルーチンを表現するためにランタイムが使用する構造体です。ゴルーチンがチャネルでブロックされると、`sudog`インスタンスが作成され、チャネルの送受信キュー（`sendq`または`recvq`）に追加されます。
    *   `g *g`: この`sudog`が関連付けられているゴルーチン（`g`構造体）へのポインタ。
    *   `elem unsafe.Pointer`: チャネルを介して送受信されるデータ要素へのポインタ。例えば、`ch <- value` の `value` や、`value := <-ch` の `value` が格納されるメモリ位置を指します。このポインタは、ゴルーチンのスタック上にあるメモリを指すことがあります。
5.  **スタックの動的伸縮**: Goのゴルーチンスタックは、必要に応じて自動的にサイズが変更されます。関数呼び出しが深くなるとスタックは拡張され、関数から戻るとスタックは縮小されることがあります。
6.  **並行スタック縮小 (Concurrent Stack Shrinking)**: Goランタイムの進化の一環として、スタックの縮小処理を、対象のゴルーチンが実行中であっても（つまり、他のゴルーチンと並行して）行えるようにする機能です。これにより、スタック縮小のためにゴルーチンを長時間停止させる必要がなくなり、レイテンシの改善や全体的なパフォーマンス向上が期待されます。しかし、この並行処理は、スタック上のデータへのポインタの整合性を維持するために、より厳密な同期メカニズムを必要とします。

## 技術的詳細

このコミットの核心は、`hchan.lock`の保護範囲を`sudog.elem`にまで拡張することです。

以前のGoランタイムでは、`sudog.elem`はチャネルのロックが解除された後にアクセスされることがありました。これは、`sudog.elem`がその時点では単一のゴルーチンによってのみアクセスされると仮定されていたためです。しかし、並行スタック縮小が導入されると、`sudog.elem`が指すメモリ領域（ゴルーチンのスタック上にある可能性が高い）が、スタック縮小プロセスによって移動される可能性があります。

この移動と、チャネル操作による`sudog.elem`への読み書きが同時に発生すると、以下の問題が生じます。

*   **データ競合**: `sudog.elem`が指すアドレスが変更されている最中に、チャネル操作が古いアドレスにアクセスしようとすると、不正なメモリにアクセスしたり、破損したデータを読み書きしたりする可能性があります。
*   **ポインタの無効化**: スタック縮小によって`sudog.elem`が指すスタック上の位置が移動した場合、`sudog.elem`自体も新しい位置を指すように更新される必要があります。この更新とチャネル操作が同期されていないと、`sudog.elem`が古い無効なアドレスを指し続けることになります。

このコミットでは、`send`関数と`recv`関数における`unlockf()`の呼び出し位置を変更することで、この問題を解決しています。`unlockf()`はチャネルのロックを解除する関数であり、これを`sudog.elem`へのアクセスが完了した後に移動させることで、`sudog.lock`が`sudog.elem`へのアクセス中も保持されるようにしています。

具体的には、`send`関数では、`sg.elem != nil` のブロック内で`sendDirect`が`sg.elem`を使用した後、そして`sg.elem = nil`が実行された後に`unlockf()`が呼び出されるように変更されています。同様に、`recv`関数では、`ep != nil` のブロック内で`recvDirect`が`sg.elem`を使用した後、そして`sg.elem = nil`が実行された後に`unlockf()`が呼び出されるように変更されています。

これにより、`hchan.lock`は、チャネルの内部状態だけでなく、チャネル操作に関連する`sudog.elem`へのアクセスも保護するようになります。並行スタック縮小が`sudog.elem`を調整する必要がある場合、`hchan.lock`を取得しようとしますが、チャネル操作が`hchan.lock`を保持している間はブロックされるため、安全に調整を行うことができます。

また、`hchan`と`sudog`の構造体定義にコメントが追加され、`hchan.lock`が保護するフィールドの範囲が明確に文書化されています。これは、将来のランタイム開発者がチャネルの同期メカニズムをより正確に理解し、誤った仮定に基づいてコードを書くことを防ぐのに役立ちます。

## コアとなるコードの解説

このコミットの主要な変更は、`hchan.lock`の保護範囲を`sudog.elem`にまで広げ、そのことをコードとコメントの両方で明確にすることです。

`send`関数と`recv`関数は、チャネルを介した値の送受信を処理するGoランタイムの重要な部分です。これらの関数は、チャネルの内部状態を操作するために`hchan.lock`を取得し、操作が完了するとロックを解除します。

変更前は、`unlockf()`（チャネルのロックを解除する関数）が`sg.elem`へのアクセスよりも早く呼び出される可能性がありました。例えば、`send`関数では、バッファリングされていないチャネルの場合、`unlockf()`が`sendDirect`（`sg.elem`を使用する）の前に呼び出されていました。

この変更により、`unlockf()`の呼び出しは、`sg.elem`が指すデータ要素への読み書きが完全に終了し、かつ`sg.elem`自体が`nil`に設定される（つまり、`sudog`がチャネル操作から切り離される）まで遅延されます。これにより、`hchan.lock`が`sudog.elem`へのアクセス全体を保護することが保証されます。

`hchan`と`sudog`構造体へのコメント追加は、この同期ルールを明示的に文書化するものです。これにより、ランタイムの複雑な並行処理のロジックがより理解しやすくなり、将来の変更やデバッグの際に役立ちます。特に、`sudog.elem`がスタック上のメモリを指す可能性があるという事実は、並行スタック縮小との相互作用において非常に重要であり、このコメントは開発者にとって重要な警告となります。

この変更は、Goランタイムの堅牢性を高め、将来の機能（並行スタック縮小）との互換性を確保するための予防的な措置と言えます。

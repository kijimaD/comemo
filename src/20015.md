# [インデックス 20015] ファイルの概要

このコミットは、Go言語のランタイムプロファイリングツールである`pprof`の内部実装におけるデータ競合を修正するものです。具体的には、`src/pkg/runtime/pprof/pprof.go`ファイルが変更されました。このファイルは、CPUプロファイリングの開始と停止、およびプロファイルデータの収集に関するロジックを管理しています。

## コミット

`runtime/pprof`パッケージにおけるデータ競合の修正。特に、CPUプロファイリングの開始時に行われていた、誤った二重チェックロックのパターンが原因でした。この修正は、CPUプロファイリング中にミューテックスが常に保持されているわけではないという問題に対処し、`Fixes #8365`として報告されたバグを解決します。

## 変更の背景

このコミットは、Go言語のCPUプロファイリング機能（`runtime/pprof`パッケージ）に存在していたデータ競合を修正するために行われました。問題は、`StartCPUProfile`関数内でCPUプロファイリングが既に進行中であるかをチェックする際に、不適切な「二重チェックロック」パターンが使用されていたことにありました。

具体的には、`StartCPUProfile`関数は、プロファイリングを開始する前に`cpu.profiling`というフラグをチェックしていました。しかし、このチェックはミューテックス（`cpu.Lock()`）が取得される前に行われていました。その結果、複数のゴルーチンが同時に`StartCPUProfile`を呼び出した場合、`cpu.profiling`フラグの読み取りと更新の間に競合状態が発生し、誤って複数のプロファイリングセッションが開始されたり、既にプロファイリングが進行中であるにもかかわらずエラーが返されなかったりする可能性がありました。

コミットメッセージにある「The mutex is not held for the whole duration of CPU profiling.」という記述は、プロファイリング自体が長時間にわたる操作であり、その間ずっとロックを保持することは現実的ではないことを示唆しています。そのため、プロファイリングの開始・停止といったクリティカルセクションのみを適切に保護する必要がありました。

`Fixes #8365`という記述は、この問題がGoの内部バグトラッカーで報告されていたことを示しています。当時のGoプロジェクトでは、GitHubのIssueトラッカーが現在のように広く使われる前は、内部のGerritシステムや別のバグトラッカーが利用されていました。

## 前提知識の解説

### 1. データ競合 (Data Race)

データ競合は、並行プログラミングにおける一般的なバグの一種です。以下の3つの条件がすべて満たされたときに発生します。
*   複数のゴルーチン（またはスレッド）が同時に同じメモリ位置にアクセスする。
*   少なくとも1つのアクセスが書き込み操作である。
*   それらのアクセスが同期メカニズム（ミューテックス、チャネルなど）によって適切に順序付けされていない。

データ競合が発生すると、プログラムの動作が予測不能になり、クラッシュ、不正なデータ、セキュリティ脆弱性など、様々な問題を引き起こす可能性があります。Go言語には、データ競合を検出するための強力な「Race Detector」が組み込まれていますが、このコミットで修正されたのは、`pprof`ツール自体の内部実装におけるデータ競合でした。

### 2. ミューテックス (Mutex)

ミューテックス（Mutual Exclusionの略）は、共有リソースへのアクセスを制御するための同期プリミティブです。ミューテックスは、一度に1つのゴルーチン（またはスレッド）のみがクリティカルセクション（共有リソースにアクセスするコード部分）を実行できるようにします。
*   **Lock()**: ミューテックスをロックします。既にロックされている場合、呼び出し元のゴルーチンはロックが解放されるまでブロックされます。
*   **Unlock()**: ミューテックスをアンロックします。

これにより、共有データへの同時アクセスを防ぎ、データ競合を回避できます。

### 3. 二重チェックロック (Double-Checked Locking)

二重チェックロックは、リソースの初期化を最適化するためのパターンとして知られていますが、正しく実装しないとデータ競合を引き起こしやすいアンチパターンでもあります。基本的なアイデアは、リソースが初期化されているかをロックなしで一度チェックし、初期化されていない場合にのみロックを取得して再度チェックし、初期化を行うというものです。

```go
// 誤った二重チェックロックの例 (擬似コード)
if resource == nil { // 最初のチェック (ロックなし)
    lock.Lock()
    if resource == nil { // 2回目のチェック (ロックあり)
        resource = initializeResource()
    }
    lock.Unlock()
}
```
このパターンは、メモリモデルの保証が弱い言語や環境では、コンパイラの最適化やCPUのキャッシュコヒーレンシの問題により、最初のロックなしのチェックで古い値が読み取られたり、初期化が完了していないリソースが使用されたりする可能性があり、データ競合を引き起こすことがあります。Go言語では、`sync.Once`のようなより安全なプリミティブが推奨されます。

### 4. GoのCPUプロファイリングと `pprof`

`runtime/pprof`パッケージは、Goプログラムの実行時プロファイル情報を収集するための標準ライブラリです。CPUプロファイリングは、プログラムがCPU時間をどこで消費しているかを特定するのに役立ちます。`StartCPUProfile`関数はCPUプロファイリングを開始し、`StopCPUProfile`関数はプロファイリングを停止します。収集されたプロファイルデータは、`go tool pprof`コマンドで分析できます。

## 技術的詳細

このコミットが修正した問題は、`runtime/pprof`パッケージの`StartCPUProfile`関数における、`cpu.profiling`というブール型フラグの扱い方にありました。

変更前のコードは以下のようになっていました。

```go
// Avoid queueing behind StopCPUProfile.
// Could use TryLock instead if we had it.
if cpu.profiling { // (A) 最初のチェック
    return fmt.Errorf("cpu profiling already in use")
}

cpu.Lock() // (B) ロックの取得
defer cpu.Unlock()
if cpu.done == nil { // (C) 2回目のチェック
    // ... プロファイリング開始ロジック ...
}
```

ここで問題となるのは、`(A)`の`if cpu.profiling`チェックが、`(B)`の`cpu.Lock()`によるミューテックスの保護なしに行われている点です。

1.  **競合状態の発生**: 複数のゴルーチンがほぼ同時に`StartCPUProfile`を呼び出したとします。
    *   ゴルーチンAが`(A)`で`cpu.profiling`が`false`であることを確認し、プロファイリングを開始しようとします。
    *   その直後、ゴルーチンBも`(A)`で`cpu.profiling`が`false`であることを確認します。
    *   ゴルーチンAが`(B)`で`cpu.Lock()`を取得し、プロファイリングの初期化を進めます。このとき、`cpu.profiling`は`true`に設定されます。
    *   ゴルーチンBが`(B)`で`cpu.Lock()`を取得しようとしますが、ゴルーチンAがロックを保持しているためブロックされます。
    *   ゴルーチンAがロックを解放した後、ゴルーチンBがロックを取得し、`(C)`のチェックに進みます。この時点で`cpu.profiling`は既に`true`になっているため、ゴルーチンBはエラーを返さずにプロファイリングの初期化を再度試みるか、あるいは不正な状態に陥る可能性があります。

このシナリオは、`cpu.profiling`フラグがミューテックスによって適切に保護されていないため、複数のゴルーチンが同時にプロファイリングを開始しようとしたときに、データ競合を引き起こすことを示しています。コミットメッセージにある「It's unclear why we do this broken double-checked locking.」という記述は、このパターンが意図せず導入されたか、あるいはその危険性が十分に認識されていなかったことを示唆しています。

修正は、この最初のロックなしのチェックを完全に削除することで、問題を解決しています。これにより、`StartCPUProfile`が呼び出された際には常に`cpu.Lock()`が最初に取得され、`cpu.profiling`フラグへのアクセスがミューテックスによって保護されるようになります。

## コアとなるコードの解説

削除されたコードは、`StartCPUProfile`関数が呼び出された際に、CPUプロファイリングが既にアクティブであるかどうかをチェックするためのものでした。

*   `if cpu.profiling { ... }`：この行は、`cpu`構造体内の`profiling`というブール型フィールドをチェックしていました。このフィールドは、CPUプロファイリングが現在進行中であるかを示すフラグです。
*   `return fmt.Errorf("cpu profiling already in use")`：もし`cpu.profiling`が`true`であれば、既にプロファイリングが実行中であるというエラーを返していました。
*   コメント行：`// Avoid queueing behind StopCPUProfile.` と `// Could use TryLock instead if we had it.` は、このチェックの意図が、`StopCPUProfile`の処理が完了するのを待つことを避けるためであり、もし`TryLock`のような非ブロックロック機構があればそれを使いたかった、という開発者の考えを示しています。

このコードが削除された理由は、前述の通り、`cpu.Lock()`によるミューテックス保護なしに`cpu.profiling`フラグをチェックしていたため、データ競合の脆弱性があったからです。このチェックを削除することで、`StartCPUProfile`関数は常に最初に`cpu.Lock()`を取得するようになり、`cpu.profiling`フラグへのアクセスが排他的に保護されるようになりました。これにより、複数のゴルーチンが同時にプロファイリングを開始しようとしても、ミューテックスによって適切に同期され、データ競合が解消されます。

結果として、プロファイリングが既に進行中の場合は、`cpu.Lock()`の取得でブロックされ、ロック取得後に`if cpu.done == nil`のチェックで適切に処理されるか、あるいは後続のロジックでエラーが返されるようになります。これにより、`pprof`の内部状態の一貫性が保たれます。

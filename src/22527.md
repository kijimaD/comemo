The barrier in gcDrain does not account for concurrent gcDrainNs
happening in gchelpwork, so it can actually return while there is

## 変更の背景

このコミットは、Goランタイムのガベージコレクション（GC）におけるマークフェーズの終了とマークターミネーションフェーズへの移行に関する微妙な挙動を明確にするために行われました。具体的には、`gcDrain`関数が完了したと判断した後でも、並行して実行されている`gcDrainN`の処理がまだ残っている可能性があるという点です。

通常、GCのマークフェーズでは、すべての到達可能なオブジェクトがマークされるまで作業が続行されます。`gcDrain`は、このマーク作業を完了させるためのバリアとして機能します。しかし、`gchelpwork`（GCヘルパーゴルーチンによる作業）内で並行して実行される`gcDrainN`の処理が、`gcDrain`のバリアによって完全に捕捉されない場合がありました。

この状況は、一見するとGCの整合性に問題を引き起こすように見えますが、実際には問題ありません。このコミットは、なぜこの挙動が許容されるのか、その理由をコードのコメントとして明示することで、将来のメンテナや開発者がGCの内部動作をより正確に理解できるようにすることを目的としています。特に、`gcDrainN`が常にシステムスタックで実行されるという重要な特性が、この挙動が安全であることの鍵となります。

## 前提知識の解説

このコミットの理解を深めるために、以下のGoランタイムとガベージコレクションに関する前提知識が必要です。

*   **Goのガベージコレクション (GC)**: GoのGCは、並行、三色マーキング、スイープアルゴリズムを採用しています。これは、アプリケーションの実行と並行して動作し、プログラムの停止時間（Stop-The-World: STW）を最小限に抑えるように設計されています。
    *   **三色マーキング**: オブジェクトを「白（未訪問、潜在的なゴミ）」、「灰（訪問済みだが参照先は未訪問）」、「黒（訪問済みで参照先も全て訪問済み）」の3色で分類し、到達可能なオブジェクトを特定します。
    *   **マークフェーズ**: GCの主要なフェーズの一つで、ルート（グローバル変数やゴルーチンのスタックなど）から開始して、到達可能なすべてのオブジェクトをマークします。
    *   **マークターミネーションフェーズ**: マークフェーズの最後に発生する短いSTWフェーズです。このフェーズで、残りのマーク作業を完了させ、ゴルーチンスタックの最終スキャンを行い、次のスイープフェーズへの準備をします。

*   **`gcDrain`と`gcDrainN`**:
    *   `gcDrain`: GCのマークフェーズ中に、グローバルな作業キューから「灰色のオブジェクト」（まだ参照先がスキャンされていないオブジェクト）を取り出し、それらをスキャンして「黒色」にする処理を繰り返す関数です。これは、マーク作業の完了を待つバリアのような役割を果たします。
    *   `gcDrainN`: `gcDrain`よりも粒度の細かい関数で、指定された数のオブジェクトをスキャンする役割を担います。GCの並行性を維持し、STW時間を短縮するために、作業を小さなチャンクに分割して処理するために使用されます。

*   **システムスタックとゴルーチンスタック**:
    *   **ゴルーチンスタック**: Goのゴルーチンは、通常のOSスレッドとは異なり、比較的小さなスタック（通常は数KBから開始）を持ち、必要に応じて動的に拡大・縮小します。ほとんどのGoコードはゴルーチンスタック上で実行されます。
    *   **システムスタック (g0スタック/gs0スタック)**: Goランタイムには、各OSスレッド（M）に紐付けられた専用の「システムスタック」が存在します。このスタックは、GCやスケジューラなどのランタイムの低レベルな処理を実行するために使用されます。システムスタック上で実行される関数は、通常、Goスケジューラによるプリエンプション（横取り）の対象外となります。

*   **Stop-The-World (STW)**: GCが実行される際に、アプリケーションの実行を一時的に完全に停止させる期間を指します。GoのGCはSTW時間を最小限に抑えるように設計されていますが、マークターミネーションなどの特定のフェーズではSTWが必要です。STW中は、メモリの状態が変化しないため、GCは安全にメモリを操作できます。

## 技術的詳細

このコミットが対処している「微妙な点」は、`gcDrain`関数が完了したと判断した後でも、`gchelpwork`（GCヘルパーゴルーチン）内で並行して実行されている`gcDrainN`の処理がまだ残っている可能性があるという状況です。

通常、`gcDrain`は、すべてのマーク作業が完了したことを確認するためのバリアとして機能します。しかし、並行処理の性質上、`gcDrain`が完了したと報告した後でも、一部の`gcDrainN`の呼び出しがまだ進行中である可能性があります。これは、`gcDrain`のバリアが、`gchelpwork`で発生する並行`gcDrainNs`の完了を完全に待機しないためです。

しかし、この状況はGoのGCの整合性にとって問題ありません。その理由は以下の2点に集約されます。

1.  **`gcDrainNs`はシステムスタックで実行される**: `gcDrainN`関数は、`go:nowritebarrier`ディレクティブと共に、Goランタイムのシステムスタック（g0スタック）上で実行されるように設計されています。システムスタック上で実行される関数は、Goスケジューラによるプリエンプションの対象外であり、STWが発生する前にその作業を完了させることができます。これにより、`gcDrainN`が処理しているGC作業バッファの内容は、STWが開始される前にグローバルキューにフラッシュされることが保証されます。つまり、たとえ`gcDrain`が先に完了したとしても、`gcDrainN`が保持していた重要なGC作業は失われることなく、グローバルなGC作業キューに適切に反映されます。

2.  **マークターミネーションへの移行は、一部の作業がキューに残っていても問題ない**: マークターミネーションフェーズの目的は、マークフェーズの最終的なクリーンアップと、次のスイープフェーズへの準備です。このフェーズに移行する際に、一部のGC作業がまだグローバルキューに残っていても、それは許容されます。マークターミネーションフェーズ自体が、残りのマーク作業を完了させるための最終的な機会を提供するためです。STW中に行われる最終スキャンによって、残りの作業も適切に処理されます。

したがって、このコミットは、`gcDrain`のバリアが並行`gcDrainNs`を完全に待機しないという事実にもかかわらず、GoのGCが正しく機能する理由を明確にしています。これは、`gcDrainN`がシステムスタック上で実行されるという重要な設計上の決定と、マークターミネーションフェーズの堅牢性によるものです。

## コアとなるコードの解説

### `src/runtime/mgc.go` の変更

`gc`関数の`gcDrain(&gcw)`呼び出しの直後に新しいコメントが追加されました。このコメントは、`gcDrain`が完了した後でも`gcDrainNs`がまだ作業を行っている可能性があるという「微妙な点」を説明しています。そして、なぜこれが問題ないのか、その2つの主要な理由を明確に述べています。

1.  **`gcDrainNs`がシステムスタックで実行されるため**: これにより、STWが発生する前に、`gcDrainNs`がローカルに保持しているGC作業バッファの内容がグローバルキューにフラッシュされることが保証されます。
2.  **マークターミネーションに一部の作業がキューに残っていても問題ないため**: マークターミネーションフェーズ自体が、残りのGC作業を処理する能力を持っているため、この時点での未処理の作業は許容されます。

このコメントは、GoのGCの並行性と堅牢性に関する重要な設計上の詳細を文書化し、コードの可読性と理解を向上させています。

### `src/runtime/mgcmark.go` の変更

`gcDrainN`関数の既存のコメントに、新しい行が追加されました。この追加は、`gcDrainN`がシステムスタック上で実行されなければならない理由を強調しています。

*   `This MUST be run on the system stack to prevent a stop-the-world while this locally holds GC work buffers.`

このコメントは、`gcDrainN`がローカルにGC作業バッファを保持している間にSTWが発生するのを防ぐために、システムスタック上で実行されることの重要性を明確にしています。システムスタック上で実行されることで、`gcDrainN`はプリエンプションされず、STWが開始される前にその作業を安全に完了させ、バッファの内容をグローバルなGCキューにコミットすることができます。これは、GCの正確性と整合性を維持するために不可欠な特性です。

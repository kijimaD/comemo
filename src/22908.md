# [インデックス 22908] ファイルの概要

このコミットはGoランタイムの`src/runtime/proc1.go`ファイルに対する変更です。`proc1.go`はGoランタイムのスケジューラの中核をなす部分であり、ゴルーチンのスケジューリング、プリエンプション（横取り）、およびプロセッサ（P）の管理といった低レベルな操作を扱っています。特に、ゴルーチンが実行される時間スライスや、アイドル状態のPの管理など、Goの並行処理モデルを支える重要なロジックが含まれています。

## 元コミット内容

このコミットは、Goランタイムにおいて、ゴルーチンがブロッキングせずに10ミリ秒実行された場合にプリエンプトされる（実行が中断され、他のゴルーチンにCPUが譲られる）という時間スライス定数を、ハードコードされた値からグローバルな定数に移動するものです。この変更は、将来的にバックグラウンドGC（ガベージコレクション）のスケジューリングでこの時間スライスの長さを使用するために行われます。

## 変更の背景

Goランタイムは、協調的スケジューリングとプリエンプティブスケジューリングの両方の要素を組み合わせてゴルーチンを管理します。このコミットが行われた時点では、Goのプリエンプションは主に「協調的プリエンプション」に依存していました。これは、関数呼び出しやチャネル操作などの特定のポイントでゴルーチンが自発的にスケジューラに制御を戻すことを意味します。しかし、無限ループや計算量の多い処理を行うゴルーチンがCPUを占有し続けることを防ぐため、Goランタイムは「非同期プリエンプション」のメカニズムも持っています。

このコミットの背景にあるのは、この非同期プリエンプションの閾値である「10ミリ秒」という値が、`src/runtime/proc1.go`内の`retake`関数に直接ハードコードされていたことです。ハードコードされた値は、その意味が不明瞭になりがちで、変更が必要になった場合に複数の箇所を修正する必要があるなど、保守性の問題を引き起こします。

さらに重要な背景として、Goランタイムのガベージコレクション（GC）の進化があります。GoのGCは、アプリケーションの実行と並行して動作する「コンカレントGC」を採用しています。このコンカレントGCは、アプリケーションのレイテンシを最小限に抑えるために、非常に短いポーズタイム（GCがアプリケーションの実行を一時停止する時間）を目指しています。GCの効率的な動作には、ランタイムがゴルーチンの実行状況を把握し、GCのフェーズに応じて適切にゴルーチンを一時停止または再開させる必要があります。

このコミットの目的は、プリエンプションの時間スライスを明示的な定数として定義することで、以下の利点をもたらすことです。

1.  **可読性と保守性の向上**: 「10ミリ秒」というマジックナンバーを`forcePreemptNS`という名前付き定数に置き換えることで、コードの意図が明確になります。
2.  **将来的な拡張性**: コミットメッセージにあるように、この時間スライスの長さをバックグラウンドGCのスケジューリングに利用する計画がありました。定数として定義することで、GCがゴルーチンの実行時間スライスを考慮に入れて、より効率的に動作するための基盤が築かれます。例えば、GCが特定のフェーズに入る際に、実行中のゴルーチンをこの時間スライスに基づいてプリエンプトし、GC作業のためのCPU時間を確保するといったことが可能になります。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

### Goランタイムスケジューラ (M-P-Gモデル)

Goランタイムスケジューラは、M（Machine）、P（Processor）、G（Goroutine）という3つの主要なエンティティで構成されるM-P-Gモデルを採用しています。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。ユーザーが書いた関数がゴルーチンとして実行されます。
*   **M (Machine)**: OSのスレッドに対応します。MはPにアタッチされ、P上でGを実行します。
*   **P (Processor)**: 論理的なプロセッサであり、MとGの間のコンテキストとして機能します。Pは実行可能なGのキューを保持し、MがGを実行するためのリソースを提供します。`GOMAXPROCS`環境変数によってPの数が制御されます。

スケジューラは、MがP上でGを実行し、Gがブロックされたり、プリエンプトされたりすると、Pは別の実行可能なGをMに提供します。

### ゴルーチンのプリエンプション

Goのゴルーチンは、OSのスレッドのようにプリエンプティブにスケジューリングされます。これにより、一つのゴルーチンがCPUを独占することを防ぎ、他のゴルーチンにも公平にCPU時間が割り当てられます。プリエンプションには主に2つのメカニズムがあります。

1.  **協調的プリエンプション**: ゴルーチンが関数呼び出し、チャネル操作、システムコールなどの特定の安全なポイントで自発的にスケジューラに制御を戻すものです。
2.  **非同期プリエンプション**: ゴルーチンが長時間（このコミットでは10ミリ秒）ブロッキングせずに実行され続けた場合に、ランタイムが強制的にその実行を中断し、他のゴルーチンにCPUを譲るメカニズムです。これは、無限ループや計算量の多い処理を行うゴルーチンがスケジューラをブロックするのを防ぐために重要です。このコミットは、この非同期プリエンプションの閾値に関するものです。

### `src/runtime/proc1.go`の役割

`src/runtime/proc1.go`は、Goランタイムのスケジューラの中核部分を実装しています。このファイルには、ゴルーチンの作成、スケジューリング、プリエンプション、MとPの管理、およびGCとの連携に関する低レベルな関数が含まれています。特に、`retake`関数は、実行中のゴルーチンを定期的にチェックし、プリエンプションが必要かどうかを判断する役割を担っています。

### Goのガベージコレクション (GC)

GoのGCは、メモリ管理を自動化し、開発者が手動でメモリを解放する手間を省きます。GoのGCは「マーク＆スイープ」アルゴリズムをベースにしており、アプリケーションの実行と並行して動作する「コンカレントGC」が特徴です。これにより、GCによるアプリケーションの一時停止（ポーズタイム）を最小限に抑え、高いスループットと低いレイテンシを実現しています。GCは、特定のフェーズでゴルーチンの実行を一時停止したり、GC作業のためにCPUリソースを必要としたりするため、スケジューラとの密接な連携が必要です。

## 技術的詳細

このコミットの技術的な詳細としては、主に以下の点が挙げられます。

1.  **マジックナンバーの排除と定数化**:
    変更前は、ゴルーチンのプリエンプションの閾値である10ミリ秒（ナノ秒単位で`10 * 1000 * 1000`）が、`retake`関数内の条件式に直接記述されていました。このような数値リテラルは「マジックナンバー」と呼ばれ、コードの可読性を低下させ、その数値が何を意味するのかを理解しにくくします。また、将来的にこの値を変更する必要が生じた場合、コードベース全体でその数値が使用されている箇所を特定し、すべて修正する必要があり、エラーの温床となります。
    このコミットでは、このマジックナンバーを`const forcePreemptNS = 10 * 1000 * 1000 // 10ms`という名前付き定数として定義しました。これにより、コードを読んだ際に`forcePreemptNS`という名前からその値が「強制プリエンプションのためのナノ秒」であることが一目で理解できるようになります。

2.  **定数の配置**:
    `forcePreemptNS`定数は、`src/runtime/proc1.go`の`retake`関数の近くに定義されています。これは、この定数が主に`retake`関数内で使用されるため、関連するコードの近くに配置することで、コードの局所性と可読性を高めるという良いプラクティスに従っています。

3.  **コメントの更新**:
    プリエンプションの条件をチェックする行のコメントが、具体的な「10ms」という記述から「too long」というより一般的な表現に更新されています。これは、定数`forcePreemptNS`がその具体的な値を表現するため、コメントではその意図をより抽象的に記述する方が適切であるためです。

4.  **GCスケジューリングへの影響**:
    コミットメッセージで述べられているように、この変更の主要な動機の一つは、将来的にバックグラウンドGCのスケジューリングでこの時間スライスの長さを使用することです。GoのGCは、アプリケーションの実行と並行して動作するため、GCの各フェーズで必要なCPU時間を確保しつつ、アプリケーションのレイテンシを最小限に抑える必要があります。`forcePreemptNS`のような定数をGCスケジューラが参照できるようになることで、GCはゴルーチンの実行時間スライスを考慮に入れ、よりインテリジェントにプリエンプションをトリガーしたり、GC作業をスケジュールしたりすることが可能になります。例えば、GCが重要なマークフェーズにあるときに、長時間実行されているゴルーチンをこの時間スライスに基づいてプリエンプトし、GCにCPUを譲ることで、GCの完了を早め、ポーズタイムを短縮するなどの最適化が考えられます。

## コアとなるコードの解説

このコミットの核となる変更は、`src/runtime/proc1.go`ファイルにおける`forcePreemptNS`定数の導入と、その定数を使用した`retake`関数の修正です。

1.  **`forcePreemptNS`定数の定義**:
    ```go
    // forcePreemptNS is the time slice given to a G before it is
    // preempted.
    const forcePreemptNS = 10 * 1000 * 1000 // 10ms
    ```
    この行は、`forcePreemptNS`という名前の定数を定義しています。値は`10 * 1000 * 1000`で、これは10ミリ秒をナノ秒単位で表現したものです（1ミリ秒 = 1,000,000ナノ秒）。コメントには、この定数がゴルーチンがプリエンプトされるまでの時間スライスであることを明確に示しています。

2.  **`retake`関数の変更**:
    `retake`関数は、Goランタイムスケジューラの一部であり、定期的に実行中のゴルーチンをチェックし、プリエンプションが必要かどうかを判断します。この関数は、各P（プロセッサ）の状態を巡回し、`_Prunning`状態（実行中）のゴルーチンに対してプリエンプションのチェックを行います。

    変更前のコードでは、以下の行でプリエンプションの条件をチェックしていました。
    ```go
    // Preempt G if it's running for more than 10ms.
    // ...
    if pd.schedwhen+10*1000*1000 > now {
    ```
    ここで`10*1000*1000`というマジックナンバーが直接使用されていました。

    変更後のコードでは、このマジックナンバーが新しく定義された`forcePreemptNS`定数に置き換えられています。
    ```go
    // Preempt G if it's running for too long.
    // ...
    if pd.schedwhen+forcePreemptNS > now {
    ```
    コメントも「Preempt G if it's running for more than 10ms.」から「Preempt G if it's running for too long.」に変更され、より抽象的で定数の意図に沿った表現になっています。

    `pd.schedwhen`は、そのゴルーチンが最後にスケジューリングされた時刻（ナノ秒単位）を記録しています。`pd.schedwhen + forcePreemptNS`は、そのゴルーチンがプリエンプトされるべき時刻を示します。現在の時刻`now`がこの閾値を超えていない場合（つまり、まだ`forcePreemptNS`で定義された時間スライス内である場合）、ゴルーチンはプリエンプトされずに実行を継続します。この条件が満たされなくなった場合（つまり、ゴルーチンが`forcePreemptNS`で定義された時間よりも長く実行され続けた場合）、`preemptone(_p_)`が呼び出され、そのゴルーチンはプリエンプトされます。

この変更により、プリエンプションの閾値が明確に定義され、将来的なGCスケジューリングとの連携が容易になりました。

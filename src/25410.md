# [インデックス 25410] ファイルの概要

このコミットは、GoランタイムがLinux/386アーキテクチャ上で動的リンクを使用している場合に、`vsyscall`ヘルパーを呼び出す方法を修正するものです。具体的には、`vsyscall`ヘルパーへの呼び出しを、スレッド制御ブロック（TCB）を介して`%gs`レジスタからのオフセットで取得するように変更しています。これにより、動的リンクされたGoプログラムが`vsyscall`を正しく利用できるようになります。

## 元コミット内容

runtime: invoke vsyscall helper via TCB when dynamic linking on linux/386

The dynamic linker on linux/386 stores the address of the vsyscall helper at a fixed offset from the %gs register on linux/386 for easy access from PIC code.

## 変更の背景

この変更の背景には、Linux/386環境におけるシステムコール（特に`vsyscall`）の呼び出しメカニズムと、動的リンクされたプログラムの動作に関する特定の課題があります。

従来のGoランタイムでは、`vsyscall`ヘルパーを呼び出す際に、`*runtime·_vdso(SB)`というシンボルを直接参照していました。これは、静的リンクされたプログラムや、`vDSO`（Virtual Dynamic Shared Object）が標準的な方法で利用可能な環境では問題ありませんでした。

しかし、Linux/386アーキテクチャで動的リンクを使用する場合、動的リンカは`vsyscall`ヘルパーのアドレスを、`%gs`レジスタからの固定オフセットに格納するという特殊な慣習を持っていました。これは、位置独立コード（PIC）から`vsyscall`ヘルパーに簡単にアクセスできるようにするためです。PICは、共有ライブラリがメモリ上のどこにロードされても正しく動作するために不可欠な技術です。

Goプログラムが動的リンクされる場合、`runtime·_vdso(SB)`シンボルへの直接参照では、この動的リンカの慣習に対応できませんでした。その結果、`vsyscall`ヘルパーの呼び出しが失敗したり、予期せぬ動作を引き起こしたりする可能性がありました。このコミットは、この問題を解決し、動的リンクされたGoプログラムがLinux/386上で`vsyscall`を正しく利用できるようにすることを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下の技術的な概念を把握しておく必要があります。

1.  **vsyscall (Virtual System Call)**:
    `vsyscall`は、Linuxカーネルが提供する古いメカニズムで、`gettimeofday()`や`time()`といった頻繁に呼び出されるシステムコールを高速化するために導入されました。これらのシステムコールは、カーネルモードへの完全なコンテキストスイッチを伴わずに、ユーザー空間から直接実行できるように、カーネルコードの一部をユーザー空間にマッピングします。これにより、システムコール呼び出しのオーバーヘッドが削減されます。しかし、`vsyscall`ページは固定されたアドレスにマッピングされるため、セキュリティ上の懸念（ASLRの回避など）がありました。

2.  **vDSO (Virtual Dynamic Shared Object)**:
    `vsyscall`のセキュリティ上の問題を解決するために導入されたのが`vDSO`です。`vDSO`も同様に、高速なシステムコールを提供するためにカーネルコードをユーザー空間にマッピングしますが、そのマッピングアドレスはランダム化されます。これにより、セキュリティが向上しつつ、`vsyscall`と同様のパフォーマンス上の利点が得られます。現代のLinuxシステムでは、`vsyscall`は`vDSO`によってエミュレートされるか、非推奨となっています。

3.  **Linux/386**:
    これは、32ビットIntel x86アーキテクチャ（i386）上で動作するLinuxオペレーティングシステムを指します。32ビットアーキテクチャは、レジスタのサイズ、メモリ管理、システムコール規約などにおいて、64ビットアーキテクチャとは異なる特性を持っています。特に、セグメントレジスタの利用方法に違いが見られます。

4.  **動的リンク (Dynamic Linking)**:
    動的リンクは、プログラムが実行時に共有ライブラリ（Linuxでは`.so`ファイル）とリンクされるプロセスです。これにより、実行ファイルのサイズが小さくなり、複数のプログラムが同じライブラリのコピーをメモリ上で共有できるようになります。また、ライブラリの更新が容易になるという利点もあります。動的リンカ（Linuxでは`ld-linux.so`）は、プログラムの起動時または実行中に、共有ライブラリからシンボル（関数や変数）を解決します。

5.  **位置独立コード (PIC: Position-Independent Code)**:
    PICは、メモリ上のどこにロードされても正しく実行できる機械語コードです。共有ライブラリは、異なるプロセスや同じプロセス内で異なるアドレスにロードされる可能性があるため、PICとしてコンパイルされる必要があります。PICは、コード内の絶対アドレス参照を避け、PC相対アドレス指定や、GOT (Global Offset Table) および PLT (Procedure Linkage Table) といった間接参照テーブルを使用することで実現されます。

6.  **TCB (Thread Control Block)**:
    スレッド制御ブロックは、オペレーティングシステムまたはランタイム（Goランタイムなど）によって管理されるデータ構造で、スレッド固有の情報（スレッドID、スタックポインタ、レジスタ値、スケジューリング状態、スレッドローカルストレージ（TLS）ポインタなど）を格納します。

7.  **%gs レジスタ**:
    `%gs`は、x86プロセッサのセグメントレジスタの一つです。現代の保護モードLinuxでは、一般的なメモリアドレッシングにはページングが使用され、セグメンテーションはほとんど使われませんが、`%fs`と`%gs`レジスタは特別な目的で利用されます。Linuxでは、`%gs`レジスタは通常、スレッドローカルストレージ（TLS）やCPUごとのデータへのポインタとして使用されます。これにより、スレッド固有の変数やTCBの一部に、複雑なメモリ検索なしで非常に高速にアクセスできます。Goランタイムも、`%gs`を使用して、ゴルーチン管理に不可欠な`m`（マシン/OSスレッド）構造体にアクセスします。

## 技術的詳細

このコミットの核心は、Linux/386における動的リンカが`vsyscall`ヘルパーのアドレスをどのように扱うかという点にあります。

Linux/386の動的リンカは、位置独立コード（PIC）から`vsyscall`ヘルパーに効率的にアクセスできるようにするため、`vsyscall`ヘルパーのアドレスを`%gs`レジスタからの固定オフセットに格納します。`%gs`レジスタは、スレッドローカルストレージ（TLS）へのポインタとして機能することが多く、これによりスレッド固有のデータに高速にアクセスできます。動的リンカがこの慣習を採用しているのは、共有ライブラリがロードされるベースアドレスが実行時に決定されるため、絶対アドレスで`vsyscall`ヘルパーを直接参照することができないからです。`%gs`レジスタからのオフセットを使用することで、コードはロードアドレスに依存せず、常に正しい`vsyscall`ヘルパーのアドレスを見つけることができます。

Goランタイムは、多くのシステムコールを直接アセンブリコードで呼び出します。これは、Cライブラリ（`libc`）を介さずに、より低レベルで効率的なシステムコールインターフェースを利用するためです。このコミット以前は、Goランタイムは`vsyscall`ヘルパーを`*runtime·_vdso(SB)`というシンボルを介して呼び出していました。これは、静的リンクされたバイナリでは問題ありませんが、動的リンクされたバイナリでは、`runtime·_vdso(SB)`が正しく解決されないか、あるいは動的リンカが期待する`%gs`ベースのアドレスとは異なるアドレスを指してしまう可能性がありました。

この変更では、`shared`ビルド（動的リンクされたビルド）の場合に、`vsyscall`ヘルパーの呼び出しを`CALL 0x10(GS)`に変更しています。これは、`%gs`レジスタが指すアドレスから`0x10`バイトのオフセットにあるメモリ位置を呼び出すことを意味します。この`0x10`というオフセットは、Linux/386の動的リンカが`vsyscall`ヘルパーのアドレスを格納するために使用する既知のオフセットです。これにより、動的リンクされたGoプログラムが、動的リンカの慣習に従って`vsyscall`ヘルパーを正しく呼び出せるようになります。

静的リンクされたビルドの場合（`shared`が定義されていない場合）は、引き続き`CALL *runtime·_vdso(SB)`を使用します。これは、静的リンクされたバイナリでは`runtime·_vdso(SB)`が直接解決され、`%gs`レジスタからのオフセットを使用する必要がないためです。

## コアとなるコードの解説

このコミットの主要な変更点は、`src/runtime/sys_linux_386.s`ファイルに導入された`INVOKE_SYSINFO`マクロと、既存の`CALL *runtime·_vdso(SB)`命令の置き換えです。

1.  **`INVOKE_SYSINFO`マクロの定義**:
    ```assembly
    #ifdef shared
    #define INVOKE_SYSINFO CALL 0x10(GS)
    #else
    #define INVOKE_SYSINFO CALL *runtime·_vdso(SB)
    #endif
    ```
    このマクロは、コンパイル時に`shared`シンボルが定義されているかどうか（つまり、Goプログラムが動的リンクされるかどうか）に応じて、異なるアセンブリ命令に展開されます。
    *   `#ifdef shared`: `shared`が定義されている場合、`INVOKE_SYSINFO`は`CALL 0x10(GS)`に展開されます。これは、`%gs`レジスタが指すアドレスから`0x10`バイトのオフセットにあるメモリ位置を呼び出す命令です。前述の通り、Linux/386の動的リンカは`vsyscall`ヘルパーのアドレスをこのオフセットに格納します。
    *   `#else`: `shared`が定義されていない場合（静的リンクの場合）、`INVOKE_SYSINFO`は`CALL *runtime·_vdso(SB)`に展開されます。これは、`runtime·_vdso(SB)`シンボルが指すアドレスを間接的に呼び出す命令です。静的リンクでは、このシンボルは直接解決されます。

2.  **`CALL *runtime·_vdso(SB)`の`INVOKE_SYSINFO`への置き換え**:
    `runtime·exit`, `runtime·exit1`, `runtime·open`, `runtime·closefd`, `runtime·write`, `runtime·read`, `runtime·getrlimit`, `runtime·usleep`, `runtime·gettid`, `runtime·raise`, `runtime·raiseproc`, `runtime·setitimer`, `runtime·mincore`, `time·now`, `runtime·nanotime`, `runtime·rtsigprocmask`, `runtime·rt_sigaction`, `runtime·mmap`, `runtime·munmap`, `runtime·madvise`, `runtime·futex`, `runtime·clone`, `runtime·sigaltstack`, `runtime·setldt`, `runtime·osyield`, `runtime·sched_getaffinity`, `runtime·epollcreate`, `runtime·epollcreate1`, `runtime·epollctl`, `runtime·epollwait`, `runtime·closeonexec`など、Goランタイム内の多くのシステムコールラッパーで、`CALL *runtime·_vdso(SB)`命令が新しく定義された`INVOKE_SYSINFO`マクロに置き換えられています。

この変更により、Goランタイムは、動的リンクされたLinux/386環境においても、`vsyscall`ヘルパーを正しく、かつ効率的に呼び出すことができるようになります。これは、Goプログラムの互換性と安定性を向上させる上で重要な修正です。

## 変更の背景

このコミットの背景には、Goプログラムを共有ライブラリとしてビルドする際の特定のアーキテクチャ（特にARM）における依存関係の問題があります。

Goのビルドシステムでは、`buildmode=shared` オプションを使用してプログラムを共有ライブラリとしてビルドすることができます。このモードでは、Goのランタイムや標準ライブラリの一部が共有ライブラリとしてコンパイルされ、複数のGoプログラムで共有されることで、バイナリサイズを削減したり、起動時間を短縮したりする効果があります。

しかし、共有ライブラリをビルドする際には、いくつかの特別な考慮事項が必要です。特に、外部リンキング（external linking）を使用する場合、GoのランタイムとCgoの連携を保証するために `runtime/cgo` パッケージが暗黙的に含まれることが一般的でした。これは、GoのランタイムがCgoを介してCライブラリと相互作用するために必要となるからです。

このコミットでは、同様の問題がARMアーキテクチャにおいて `math` パッケージで発生することが判明しました。ARMプロセッサの中には、ハードウェア浮動小数点ユニット（FPU）を持たないものや、FPUのサポートが限定的なものがあります。このような環境では、浮動小数点演算がソフトウェアでエミュレートされることがあり、そのために特定のCライブラリ（通常は `libm`）への依存が発生します。Goの `math` パッケージは、これらの浮動小数点演算をラップしているため、ARM上で共有ライブラリとしてビルドされるGoプログラムが `math` パッケージを使用する場合、`libm` への適切なリンクが必要となります。

このコミット以前は、`math` パッケージが明示的にインポートされていない限り、共有ライブラリに自動的に含まれることはありませんでした。そのため、`math` パッケージに依存するが直接インポートしていない（例えば、他のパッケージが `math` に依存している場合）GoプログラムをARM上で共有ライブラリとしてビルドすると、リンク時に未定義シンボルエラーが発生する可能性がありました。

この変更は、`runtime/cgo` が他のアーキテクチャで暗黙的に含まれるのと同様に、ARMアーキテクチャ上で共有ライブラリをビルドする際に `math` パッケージを暗黙的に含めることで、この問題を解決し、ビルドの堅牢性を向上させることを目的としています。

## 前提知識の解説

### Goのビルドモード (`buildmode`)

Goコンパイラは、`go build` コマンドに `-buildmode` フラグを渡すことで、様々な種類のバイナリを生成できます。
*   **`exe` (デフォルト)**: 実行可能なバイナリを生成します。
*   **`archive`**: 静的ライブラリ（.aファイル）を生成します。
*   **`c-archive`**: C言語の静的ライブラリとCヘッダファイルを生成します。C/C++プログラムからGoコードを呼び出す際に使用します。
*   **`c-shared`**: C言語の共有ライブラリ（.so/.dylib/.dllファイル）とCヘッダファイルを生成します。C/C++プログラムからGoコードを呼び出す際に使用します。
*   **`shared`**: Goの共有ライブラリ（.so/.dylib/.dllファイル）を生成します。複数のGoプログラムが共通のGoパッケージを共有ライブラリとしてリンクすることで、バイナリサイズを削減できます。このコミットで関連するのはこのモードです。
*   **`plugin`**: Goのプラグイン（.so/.dylib/.dllファイル）を生成します。実行時にGoプログラムに動的にロードできます。

### 外部リンキング (External Linking)

Goのリンカーには、内部リンカーと外部リンカーの2種類があります。
*   **内部リンカー**: Goのツールチェーンが提供するデフォルトのリンカーです。Goのオブジェクトファイルのみを扱います。
*   **外部リンカー**: GCCなどのCコンパイラが提供するリンカー（通常は `ld`）を使用します。Cgoを使用する場合や、C言語のライブラリとリンクする場合、または `buildmode=shared` や `buildmode=c-shared` のような特定のビルドモードを使用する場合に、Goのツールチェーンは外部リンカーを呼び出します。外部リンカーは、GoのオブジェクトファイルとCのオブジェクトファイルを組み合わせて最終的なバイナリを生成できます。

`buildmode=shared` は、通常、外部リンキングを強制します。これは、共有ライブラリがシステムレベルのリンカーによってロードされるため、C言語のランタイムやその他のシステムライブラリとの互換性を確保する必要があるからです。

### `runtime/cgo` パッケージの役割

`runtime/cgo` パッケージは、GoのランタイムとCgo（GoとCの相互運用機能）の間のブリッジを提供します。Cgoを使用するGoプログラムは、C言語の関数を呼び出したり、C言語のデータ構造を扱ったりできます。`runtime/cgo` は、GoのスケジューラとCのコールスタックの間の切り替え、スレッドローカルストレージの管理、シグナルハンドリングなど、Cgoが正しく機能するために必要な低レベルのランタイムサポートを提供します。

外部リンキングを使用する共有ライブラリでは、GoのランタイムがCgoを介してCライブラリと相互作用する可能性があるため、`runtime/cgo` が暗黙的に含まれることが重要です。

### `math` パッケージの特殊性

Goの `math` パッケージは、標準的な数学関数（`Sin`, `Cos`, `Sqrt` など）を提供します。これらの関数は、多くの場合、基盤となるハードウェアの浮動小数点ユニット（FPU）を利用して高速に実行されます。しかし、FPUがない、またはFPUの機能が限定的なアーキテクチャ（特に一部のARMプロセッサ）では、これらの浮動小数点演算はソフトウェアでエミュレートされる必要があります。このソフトウェアエミュレーションは、通常、システムにインストールされているC言語の数学ライブラリ（`libm.so` など）によって提供されます。

### ARMアーキテクチャにおける浮動小数点演算の扱い

ARMアーキテクチャは、非常に多様なプロセッサファミリーです。一部のARMプロセッサは強力なFPUを内蔵していますが、組み込みシステム向けの低消費電力プロセッサなどではFPUが省略されているか、非常に基本的なものしか搭載されていない場合があります。

*   **ハードウェアFPU**: FPUを搭載している場合、浮動小数点演算はハードウェアで高速に実行されます。
*   **ソフトウェアFPU**: FPUを搭載していない、またはFPUの機能が不足している場合、コンパイラは浮動小数点演算をソフトウェアでエミュレートするコードを生成します。このエミュレーションは、通常、C言語の数学ライブラリ（`libm`）の関数呼び出しに変換されます。

Goのツールチェーンは、ターゲットのARMアーキテクチャがFPUをサポートしているかどうかを考慮してコンパイルを行います。FPUがない環境では、`math` パッケージの関数が `libm` の関数にリンクされる必要があります。共有ライブラリとしてビルドされるGoプログラムが `math` パッケージを使用する場合、この `libm` への依存関係が適切に解決される必要があります。

### `cmd/go` の `build.go` ファイルの機能

`src/cmd/go/build.go` は、`go` コマンドのビルドロジックの中核をなすファイルです。このファイルには、パッケージの依存関係の解決、コンパイル順序の決定、リンキングの実行など、ビルドプロセスの様々な段階を制御する関数が含まれています。

特に、`builder` 構造体とそのメソッドは、ビルドの各ステップ（アクション）を定義し、それらの依存関係を管理します。`libaction` メソッドは、共有ライブラリをビルドする際のアクションを定義し、どのパッケージを共有ライブラリに含めるべきかを決定します。このコミットの変更は、この `libaction` メソッド内にあります。

## 技術的詳細

このコミットは、`go build -buildmode=shared` を使用してGoの共有ライブラリをビルドする際の `libaction` 関数に修正を加えます。具体的には、ARMアーキテクチャの場合に `math` パッケージを暗黙的に共有ライブラリに含めるロジックを追加しています。

変更の核心は、`libaction` 関数内の `modeInstall` ブロックにあります。`modeInstall` は、共有ライブラリがインストールされる際に、そのライブラリに含まれるべきパッケージを決定するフェーズです。

1.  **`runtime/cgo` の暗黙的追加の既存ロジック**:
    変更前も、`buildmode=shared` が外部リンキングを強制し、外部リンキングが `runtime/cgo` のインポートを強制するという理由から、`runtime/cgo` が共有ライブラリに暗黙的に追加されるロジックが存在していました。これは、`seencgo` フラグを使って、`pkgs` リストに `runtime/cgo` が既に含まれているかを確認し、含まれていなければ追加するというものでした。

2.  **`math` パッケージの暗黙的追加ロジックの追加**:
    このコミットでは、上記の `runtime/cgo` のロジックと同様のパターンで、ARMアーキテクチャ (`goarch == "arm"`) の場合に `math` パッケージを暗黙的に追加するロジックが導入されました。
    *   まず、`goarch == "arm"` の条件がチェックされます。
    *   次に、`seenmath` という新しいフラグが導入され、`pkgs` リストに `math` パッケージが既に含まれているかを確認します。
    *   `math` パッケージがまだ含まれていない場合、`loadPackage("math", &stk)` を呼び出して `math` パッケージの情報をロードします。`loadPackage` は、指定されたインポートパスのパッケージをロードし、その依存関係などの情報を取得します。
    *   `computeStale(p)` を呼び出して、`math` パッケージの鮮度（staleかどうか）を計算します。これは、ビルドシステムがパッケージを再ビルドする必要があるかどうかを判断するために使用されます。
    *   重要なのは、`math` パッケージが別の共有ライブラリに既に含まれている場合、または現在の共有ライブラリに属している場合 (`p.Shlib == "" || p.Shlib == libname`) にのみ、`math` パッケージを現在の `pkgs` リストに追加するという条件です。これは、`math` パッケージが重複して含まれることを防ぎ、依存関係が正しく解決されるようにするためです。

この変更により、ARM上で `buildmode=shared` を使用してGoプログラムをビルドする際に、`math` パッケージが自動的に共有ライブラリに含まれるようになり、`libm` への依存関係が適切に処理されるようになります。これにより、リンクエラーが回避され、ビルドの信頼性が向上します。

また、`libaction` 関数の冒頭で `switch mode` ステートメントが導入され、`modeBuild` と `modeInstall` 以外のモードが渡された場合に `fatalf` でエラーを出すように変更されています。これは、将来的な拡張性や、不正なモードが渡された場合の早期エラー検出のための改善と考えられます。

## コアとなるコードの解説

### 1. `switch mode` ステートメントの導入

```go
-	if mode == modeBuild {
+	switch mode {
+	default:
+		fatalf("unrecognized mode %v", mode)
+
+	case modeBuild:
```
以前は `if mode == modeBuild { ... } else if mode == modeInstall { ... } else { ... }` という形式でしたが、これを `switch` ステートメントに置き換えることで、コードの可読性と拡張性が向上しています。`default` ケースが追加され、`modeBuild` や `modeInstall` 以外の未知のビルドモードが渡された場合に即座にエラーを報告するようになりました。これにより、不正な状態での処理を防ぎ、デバッグが容易になります。

### 2. `runtime/cgo` 検出ロジックのスコープ変更

```go
 		_, gccgo := buildToolchain.(gccgoToolchain)
 		if !gccgo {
+			seencgo := false // ここに移動
 			for _, p := range pkgs {
 				seencgo = seencgo || (p.Standard && p.ImportPath == "runtime/cgo")

```
`seencgo` 変数の宣言が `if !gccgo { ... }` ブロックの内部に移動しました。これは、`gccgo` ツールチェーンを使用しない場合にのみ `runtime/cgo` の検出ロジックが適用されるため、変数のスコープを適切に制限し、コードの意図をより明確にするための変更です。

### 3. ARMアーキテクチャにおける `math` パッケージの暗黙的追加ロジック

このコミットの主要な変更点です。

```go
+		if goarch == "arm" {
+			seenmath := false
+			for _, p := range pkgs {
+				seenmath = seenmath || (p.Standard && p.ImportPath == "math")

+				// also the shared library that contains runtime, so

+				// will be checked when processing that library.
+				if p.Shlib == "" || p.Shlib == libname {
+					pkgs = append([]*Package{}, pkgs...)
+					pkgs = append(pkgs, p)
+				}
+			}
+		}
```

*   **`if goarch == "arm"`**: 現在のターゲットアーキテクチャがARMである場合にのみ、このロジックが実行されます。これは、`math` パッケージの特殊な依存関係がARMに特有であるためです。
*   **`seenmath := false`**: `math` パッケージが既に `pkgs` リストに含まれているかどうかを追跡するためのフラグを初期化します。
*   **`for _, p := range pkgs { ... }`**: 現在処理中の共有ライブラリに含まれる予定のパッケージ (`pkgs`) をループし、`math` パッケージが既に存在するかどうかを確認します。`p.Standard` は標準ライブラリのパッケージであることを示し、`p.ImportPath == "math"` はそれが `math` パッケージであることを確認します。
*   **`if !seenmath { ... }`**: `math` パッケージがまだ `pkgs` リストに含まれていない場合にのみ、以下の処理を実行します。
    *   **`var stk importStack`**: `loadPackage` 関数に渡すための `importStack` を宣言します。これはパッケージのインポートパスを追跡するために使用されます。
    *   **`p := loadPackage("math", &stk)`**: `math` パッケージの情報をロードします。これにより、パッケージのメタデータ（依存関係、ファイルパスなど）が取得されます。
    *   **`if p.Error != nil { fatalf("load math: %v", p.Error) }`**: `math` パッケージのロード中にエラーが発生した場合、ビルドを停止しエラーメッセージを出力します。
    *   **`computeStale(p)`**: ロードした `math` パッケージの鮮度を計算します。これは、パッケージが変更されたかどうか、再ビルドが必要かどうかを判断するために重要です。
    *   **`if p.Shlib == "" || p.Shlib == libname { ... }`**: この条件は、`math` パッケージを現在の共有ライブラリに追加するかどうかを決定する上で非常に重要です。
        *   `p.Shlib == ""`：`math` パッケージがまだどの共有ライブラリにも属していない場合。
        *   `p.Shlib == libname`：`math` パッケージが既に現在の共有ライブラリ (`libname`) に属している場合（これは通常、`seenmath` が `true` になるため、このブロックには入らないはずですが、念のため）。
        この条件が満たされる場合、`math` パッケージを `pkgs` リストに追加します。`append([]*Package{}, pkgs...)` は、元の `pkgs` スライスをコピーしてから `math` パッケージを追加することで、元のスライスへの意図しない変更を防ぐためのイディオムです。

このロジックにより、ARMアーキテクチャで共有ライブラリをビルドする際に、`math` パッケージが自動的に含まれるようになり、浮動小数点演算に関連するリンクエラーが解消されます。

# [インデックス 20230] ファイルの概要

このコミットは、Goランタイムにおける`procPin`および`procUnpin`という重要な関数を、C言語で記述された既存の実装からGo言語による実装へと変換するものです。これにより、Goランタイムの内部処理におけるGo言語への移行をさらに進め、コードベースの一貫性と保守性を向上させることを目的としています。

## 変更の背景

Go言語のランタイムは、初期の段階ではパフォーマンスが要求される部分やOSとのインタフェース部分においてC言語で記述されていました。しかし、Go言語自体の成熟と最適化が進むにつれて、ランタイムのより多くの部分をGo言語で記述することが可能になり、またそれが推奨されるようになりました。

このコミットの背景には、以下の理由が考えられます。

1.  **コードベースの一貫性向上**: ランタイムの大部分をGo言語で統一することで、開発者がGo言語の知識だけでランタイムの挙動を理解しやすくなり、コードの可読性、保守性、およびデバッグの容易性が向上します。
2.  **Go言語のツールチェーンの活用**: Go言語で記述されたコードは、Goのコンパイラ、リンカ、ガベージコレクタなどのツールチェーンによって最適化され、より効率的なバイナリが生成される可能性があります。
3.  **Cgoのオーバーヘッドの削減**: GoとCの境界を越えるCgo呼び出しには、一定のオーバーヘッドが伴います。ランタイム内部の重要な関数をGoに変換することで、このオーバーヘッドを削減し、全体的なパフォーマンスを向上させる可能性があります。
4.  **Go言語の進化**: Go言語の機能や最適化が進化するにつれて、C言語でしか実現できなかった低レベルの操作がGo言語でも安全かつ効率的に行えるようになったため、このような変換が可能になりました。

`procPin`と`procUnpin`は、Goスケジューラにおける重要なプリミティブであり、その性質上、非常に低レベルでパフォーマンスが要求される関数です。これらをGo言語に変換することは、GoランタイムのGo言語化における重要な一歩と言えます。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスケジューラ、特にM-G-Pモデルとプリエンプション（preemption）に関する基本的な知識が必要です。

### Goランタイムスケジューラ (M-G-Pモデル)

Goランタイムは、独自のスケジューラを使用してゴルーチン（Goroutine）を管理します。このスケジューラは、以下の3つの主要な要素で構成されるM-G-Pモデルに基づいています。

*   **G (Goroutine)**: Go言語における軽量な実行単位です。OSのスレッドよりもはるかに軽量で、数百万のゴルーチンを同時に実行できます。
*   **M (Machine/OS Thread)**: オペレーティングシステムのスレッドです。Goプログラムは、OSによってスケジュールされるMのプールを使用します。Mは実際にCPU上でコードを実行するエンティティです。
*   **P (Processor/Logical Processor)**: 論理プロセッサです。Pは、ゴルーチンを実行するためのコンテキストを提供し、ローカルな実行キューを保持します。MはPと関連付けられており、ゴルーチンを実行するためにはPが必要です。`GOMAXPROCS`環境変数によってPの数を制御できます（通常はCPUコア数に設定されます）。

**M-G-Pモデルの動作**:
1.  新しいゴルーチン（G）が作成されると、Pのローカル実行キュー、またはグローバル実行キューに追加されます。
2.  Mは、関連付けられたPのローカル実行キューからゴルーチンを取り出し、実行します。
3.  もしPのローカルキューが空になった場合、Mは他のPのローカルキューやグローバルキューからゴルーチンを「盗む」（work stealing）ことで、CPUリソースを効率的に利用します。
4.  ゴルーチンがブロッキングシステムコール（例: ネットワークI/O、ファイルI/O）を実行すると、そのゴルーチンを実行していたMはブロックされます。このとき、GoランタイムはPをそのMから切り離し、新しいアイドル状態のMにPを関連付けます（または新しいMを作成します）。これにより、他のゴルーチンがブロックされずに実行を継続できます。

### プリエンプション (Preemption)

プリエンプションとは、Goランタイムスケジューラが、実行中のゴルーチンを強制的に中断させ、別のゴルーチンにCPUの実行権を渡すメカニズムです。これにより、特定のゴルーチンがCPUを独占することを防ぎ、すべてのゴルーチンに公平にCPU時間が割り当てられ、アプリケーション全体の応答性を保ちます。

*   **協調的プリエンプション (Cooperative Preemption)**: Go 1.14以前では、Goは主に協調的プリエンプションを使用していました。これは、ゴルーチンが関数呼び出しなどの「安全なポイント」で自発的にスケジューラに制御を返すことを期待するものです。しかし、無限ループなどで関数呼び出しがない場合、ゴルーチンがCPUを独占し続ける「スターベーション」問題が発生する可能性がありました。
*   **非協調的/非同期プリエンプション (Non-Cooperative/Asynchronous Preemption)**: Go 1.14以降では、非協調的プリエンプションが導入されました。これにより、Goランタイムは、ゴルーチンが自発的に制御を返さない場合でも、強制的に中断させることが可能になりました。これは、`sysmon`ゴルーチンが長時間実行されているゴルーチンを検出し、`SIGURG`シグナルを送信することで実現されます。

### `procPin`と`procUnpin`の役割

`procPin`と`procUnpin`は、Goランタイムの内部で使われる関数で、一時的にゴルーチンを現在のOSスレッド（M）と論理プロセッサ（P）に「固定」（pin）し、スケジューラによるプリエンプションやマイグレーション（移動）を防ぐために使用されます。

*   **`procPin()`**: この関数は、現在のM（OSスレッド）の`locks`カウンタをインクリメントします。このカウンタがゼロより大きい間は、GoスケジューラはそのM上で実行中のゴルーチンをプリエンプトしたり、MをPから切り離したりしません。これにより、ガベージコレクションの特定のフェーズ、Cgo呼び出し、ネットワークポーラーとの相互作用、その他の低レベルのランタイム操作など、スケジューラによる中断が望ましくないクリティカルセクションのコードが中断されずに実行されることが保証されます。
*   **`procUnpin()`**: この関数は、現在のMの`locks`カウンタをデクリメントします。カウンタがゼロに戻ると、ゴルーチンとそれに関連付けられたMは、再びスケジューラによるプリエンプションとマイグレーションの対象となります。

これらの関数は、Goランタイムの整合性を維持するために不可欠であり、特に内部的なスケジューラデータ構造を操作したり、厳密な実行制御が必要な場合に利用されます。

## 技術的詳細

このコミットの技術的な核心は、`procPin`と`procUnpin`という、Goランタイムのプリエンプション制御に深く関わる関数を、C言語からGo言語へと移行した点にあります。

### `NOSPLIT`プラグマの重要性

コミットの差分を見ると、C言語で記述された`proc.c`に追加された`sync·runtime_procPin`と`sync·runtime_procUnpin`の定義には、`#pragma textflag NOSPLIT`というディレクティブが付与されています。これは、Go言語のコンパイラディレクティブである`//go:nosplit`の古いC言語での記述形式に相当します。

`NOSPLIT`は、Goコンパイラに対して、その関数内でスタックオーバーフローチェック（スタック成長チェック）を行わないように指示します。Goのゴルーチンは動的にスタックサイズを調整しますが、通常、関数呼び出しの際にはスタックが足りるかどうかのチェックが行われ、必要であればスタックが拡張されます（スタック分割）。このスタック分割のプロセス中に、スケジューラが介入する可能性があります。

`procPin`や`procUnpin`のような、スケジューラの挙動を直接制御する低レベルの関数では、スタック分割による予期せぬスケジューラの介入は非常に危険です。例えば、`procPin`がプリエンプションを無効にしている最中にスタック分割が発生し、その過程でスケジューラが動作してしまうと、ランタイムの整合性が損なわれる可能性があります。

そのため、これらの関数には`NOSPLIT`が適用され、スタックチェックをスキップすることで、関数が中断されることなく、アトミックに（不可分に）実行されることが保証されます。これは、パフォーマンス上の最適化というよりも、ランタイムの正確性と安全性を確保するための重要な措置です。ただし、`NOSPLIT`を適用した関数が大量のスタックを使用すると、スタックオーバーフローによるクラッシュ（セグメンテーション違反など）を引き起こすリスクがあるため、非常に慎重に利用されます。

### C言語からGo言語への変換のニュアンス

コミットの差分では、`src/pkg/runtime/runtime1.goc`からGo言語の関数定義が削除され、`src/pkg/runtime/proc.c`にC言語の関数定義が追加されています。これは一見するとGoからCへの逆行のように見えますが、これはGo言語のビルドシステムとランタイムの進化の過渡期における変更です。

当時のGoランタイムでは、一部のGo言語で書かれた関数が、C言語のランタイムコードから呼び出されるために、C言語のシンボルとしてエクスポートされる必要がありました。`runtime1.goc`は、Go言語で書かれたランタイムコードをC言語のコンテキストから利用可能にするための特別なファイルでした。

このコミットは、`procPin`と`procUnpin`のロジック自体をGo言語で記述し直すという意図を持っています。しかし、そのGo言語で記述された関数が、まだC言語で書かれたランタイムの他の部分から呼び出される必要があったため、一時的にC言語のラッパー関数（`sync·runtime_procPin`と`sync·runtime_procUnpin`）を`proc.c`に追加し、その中でGo言語の実際の関数を呼び出す形を取ったと考えられます。

特に、`proc.c`に追加されたC言語の`sync·runtime_procPin`関数内で`FLUSH(&p);`という行があります。これは、コンパイラの最適化によって変数の値がレジスタにキャッシュされることを防ぎ、メモリに書き込まれることを保証するためのものです。低レベルのランタイムコードでは、このようなメモリの可視性に関する厳密な制御が必要となる場合があります。Go言語のコードでは、通常、このような明示的な`FLUSH`は不要であり、Goのメモリモデルとコンパイラが適切に処理します。

最終的には、GoランタイムのGo言語化が進むにつれて、これらのC言語のラッパーも不要になり、完全にGo言語のコードに置き換えられていきました。このコミットは、その移行プロセスにおける中間的なステップを示しています。

## コアとなるコードの変更箇所

このコミットでは、以下の2つのファイルが変更されています。

1.  `src/pkg/runtime/proc.c`
    *   `sync·runtime_procPin`関数のC言語実装が追加されました。
    *   `sync·runtime_procUnpin`関数のC言語実装が追加されました。
    *   これらの関数には`#pragma textflag NOSPLIT`ディレクティブが付与されています。
2.  `src/pkg/runtime/runtime1.goc`
    *   既存のGo言語で記述されていた`sync·runtime_procPin`関数の定義が削除されました。
    *   既存のGo言語で記述されていた`sync·runtime_procUnpin`関数の定義が削除されました。

## コアとなるコードの解説

### `src/pkg/runtime/proc.c` の追加部分

```c
#pragma textflag NOSPLIT
void
sync·runtime_procPin(intptr p)
{
	M *mp;

	mp = g->m;
	// Disable preemption.
	mp->locks++;
	p = mp->p->id;
	FLUSH(&p);
}

#pragma textflag NOSPLIT
void
sync·runtime_procUnpin()
{
	g->m->locks--;
}
```

*   **`#pragma textflag NOSPLIT`**: 前述の通り、この関数がスタック成長チェックを行わないように指示します。これにより、関数が中断されることなく、アトミックに実行されることが保証されます。
*   **`sync·runtime_procPin(intptr p)`**:
    *   `M *mp; mp = g->m;`: 現在実行中のゴルーチン（`g`）が関連付けられているOSスレッド（M）へのポインタを取得します。`g`は現在のゴルーチンを表すグローバル変数（またはレジスタに格納される値）で、`g->m`はそのゴルーチンが現在実行されているMを指します。
    *   `mp->locks++;`: 現在のMの`locks`カウンタをインクリメントします。このカウンタがゼロより大きい間は、スケジューラによるプリエンプションが無効になります。
    *   `p = mp->p->id;`: 現在のMが関連付けられているP（論理プロセッサ）のIDを取得し、ローカル変数`p`に代入しています。この`p`は引数として渡されたものと同じ名前ですが、ここではMが現在実行されているPのIDをローカルで取得しているだけです。
    *   `FLUSH(&p);`: これは、コンパイラの最適化によって`p`の値がレジスタにキャッシュされることを防ぎ、確実にメモリに書き込まれるようにするためのものです。低レベルのランタイムコードでは、メモリの可視性が重要になるため、このような明示的なフラッシュが必要になることがあります。
*   **`sync·runtime_procUnpin()`**:
    *   `g->m->locks--;`: 現在のMの`locks`カウンタをデクリメントします。これにより、`procPin`によって無効化されていたプリエンプションが再び有効になる可能性があります（`locks`カウンタがゼロになった場合）。

### `src/pkg/runtime/runtime1.goc` の削除部分

```go
-func sync·runtime_procPin() (p int) {
-	M *mp;
-
-	mp = g->m;
-	// Disable preemption.
-	mp->locks++;
-	p = mp->p->id;
-}
-
-func sync·runtime_procUnpin() {
-	g->m->locks--;
-}
```

*   この部分では、Go言語で記述されていた`sync·runtime_procPin`と`sync·runtime_procUnpin`の定義が削除されています。削除されたGo言語のコードは、C言語のコードとほぼ同じロジックを持っていました。
*   Go言語版の`procPin`には`FLUSH(&p)`に相当する記述がありませんが、これはGoのコンパイラとメモリモデルが、C言語で明示的に行う必要があったメモリの可視性に関する問題を、より高レベルで自動的に処理するためです。

この変更は、Goランタイムの内部で、これらのプリミティブがC言語のコンテキストから呼び出される必要があったため、一時的にC言語のラッパーを導入し、最終的にはGo言語のコードに完全に移行するためのステップであったと理解できます。

# [インデックス 25939] ファイルの概要

このコミットは、Go言語の標準ライブラリ `archive/tar` パッケージにおける、tarアーカイブの数値フィールド解析ロジックの改善に関するものです。具体的には、GNU tar形式で用いられるbase-256エンコーディングの数値（特に大きなファイルサイズやUID/GIDなど）を正確に解析するための修正が含まれています。

変更された主要なファイルは以下の2つです。

*   `src/archive/tar/reader.go`: tarアーカイブの読み込みと解析を行うコアロジックが含まれています。このファイル内の `parseNumeric` 関数が、base-256エンコーディングの解析方法を改善するために修正されました。
*   `src/archive/tar/reader_test.go`: `reader.go` の変更を検証するためのテストコードが含まれています。特に、`TestParseNumeric` という新しいテスト関数が追加され、base-256および8進数エンコーディングの数値解析が正しく行われることを確認しています。

## 変更の背景

このコミットの主な動機は、`archive/tar` パッケージがGNU tar形式でエンコードされた数値を正しく処理できないという問題に対処することでした。具体的には、以下の2つの課題がありました。

1.  **整数オーバーフローの未検出**: 以前の実装では、base-256エンコードされたフィールドを解析する際に、数値が `int64` の最大値を超えてしまうような整数オーバーフローが発生しても、それを検出できませんでした。これにより、誤った数値が読み込まれる可能性がありました。
2.  **2の補数表現の不適切な扱い**: GNU tarの仕様では、標準のustar形式の範囲に収まらない値を格納するために、2の補数表現のbase-256表記を使用すると明記されています。しかし、以前の実装では、この2の補数表現を正しく解釈していませんでした。特に、負の数を正しくデコードできないという問題がありました。

これらの問題は、Issue #12435 で報告されており、このコミットはその問題を解決するために導入されました。GNU tar形式で作成されたアーカイブをGoの `archive/tar` パッケージで正確に読み込むためには、これらの修正が不可欠でした。

## 前提知識の解説

### tarアーカイブ形式

`tar` (tape archive) は、複数のファイルを一つのアーカイブファイルにまとめるためのファイル形式です。元々は磁気テープにデータを保存するために開発されましたが、現在ではファイルシステム上のアーカイブとしても広く利用されています。

tarファイルは、一連の「ヘッダブロック」と「データブロック」で構成されます。各ファイルやディレクトリは、そのメタデータ（ファイル名、サイズ、パーミッション、タイムスタンプなど）を記述するヘッダブロックと、実際のファイル内容を格納するデータブロックから成ります。

*   **ustar (Unix Standard TAR)**: POSIX.1-1988で標準化されたtar形式です。ファイル名が100バイト、ファイルサイズが8進数で表現されるなど、いくつかの制限があります。
*   **GNU tar拡張**: ustar形式の制限（特にファイルサイズやパス長の制限）を克服するために、GNU tarはいくつかの拡張を導入しました。その一つが、大きな数値を表現するためのbase-256エンコーディングです。

### GNU tarにおけるbase-256エンコーディング

標準のustar形式では、ファイルサイズなどの数値フィールドは8進数でASCIIエンコードされます。しかし、これにより表現できる数値の範囲には限りがあります。GNU tarは、この制限を緩和するために、特定のフィールドでbase-256（256進数）エンコーディングを導入しました。

base-256エンコーディングでは、数値はバイト列として直接表現されます。各バイトは0から255までの値を持ち、これらを組み合わせて大きな数値を表現します。GNU tarの仕様では、このbase-256エンコーディングにおいて、特に大きな数値を格納する際に「2の補数表現」を使用すると規定されています。

### 2の補数表現 (Two's Complement)

2の補数表現は、コンピュータシステムで負の整数を表現するための最も一般的な方法です。この表現形式には以下の特徴があります。

*   **正負の区別**: 最上位ビット (MSB: Most Significant Bit) が0であれば正の数、1であれば負の数を示します。
*   **負の数の表現**: ある正の数 `X` の負の数 `-X` は、`X` の全ビットを反転させ（1の補数）、それに1を加えることで得られます。例えば、8ビットで `5 (00000101)` の2の補数表現は、`11111010 (1の補数) + 1 = 11111011 (-5)` となります。
*   **演算の容易さ**: 2の補数表現を用いると、加算器で正の数と負の数の両方を同じように扱うことができ、減算を負の数の加算として処理できるため、ハードウェア設計が簡素化されます。

GNU tarのbase-256エンコーディングでは、数値フィールドの最初のバイトの最上位ビットが1の場合、そのフィールドはbase-256エンコードされていると解釈されます。さらに、そのバイトの次のビット（2番目のビット、つまり `b[0]&0x40`）が1の場合、その数値は負の数として2の補数表現でエンコードされていると解釈されます。

### 整数オーバーフロー (Integer Overflow)

整数オーバーフローは、固定長の整数型で表現できる数値の範囲を超えた値が計算結果として生じた場合に発生する現象です。例えば、8ビット符号なし整数（0〜255）で `250 + 10` を計算すると、結果は `260` ですが、8ビットでは表現できないため、通常は `4` (260 % 256) となります。

プログラムが整数オーバーフローを適切に処理しない場合、予期せぬ動作やセキュリティ上の脆弱性につながる可能性があります。tarアーカイブの解析においては、ファイルサイズなどの重要な数値がオーバーフローによって誤って解釈されると、ファイルが正しく展開されない、または悪意のあるアーカイブによってシステムが攻撃されるといった問題が発生する可能性があります。

## 技術的詳細

このコミットの核心は、`src/archive/tar/reader.go` 内の `parseNumeric` 関数の修正にあります。この関数は、tarヘッダから数値フィールドを解析する役割を担っています。

修正前の `parseNumeric` 関数は、base-256エンコーディングの検出は行っていましたが、2の補数表現の負の数を正しく扱えず、また整数オーバーフローの検出も不十分でした。

新しい実装では、以下の点が改善されています。

1.  **base-256エンコーディングの検出**:
    *   `if len(b) > 0 && b[0]&0x80 != 0` の条件で、最初のバイトの最上位ビットがセットされているかを確認し、base-256エンコードされた数値であるかを判断します。

2.  **負の数の検出と2の補数表現の適用**:
    *   `var inv byte` を導入し、負の数である場合に `0xff` を設定します。
    *   `if b[0]&0x40 != 0` の条件で、最初のバイトの2番目のビットがセットされているかを確認し、負の数であるかを判断します。このビットがセットされている場合、その数値は2の補数表現で負の値としてエンコードされています。
    *   ループ内で `c ^= inv` を実行することで、`inv` が `0xff` の場合（負の数）、各バイトのビットを反転させます。これにより、負の数を正の数として扱う準備をします。
    *   最終的に `if inv == 0xff { return ^int64(x) }` の行で、反転された `x` に `^` 演算子（ビット反転）を適用し、2の補数表現の負の数に変換します。これは、`~x + 1` と同等の操作であり、負の数を正しくデコードします。

3.  **整数オーバーフローの検出**:
    *   `var x uint64` を使用して、中間計算を符号なし64ビット整数で行います。これにより、途中で負の数として解釈されることなく、大きな数値を一時的に保持できます。
    *   `if (x >> 56) > 0` と `if (x >> 63) > 0` の2つのチェックが追加されました。
        *   `x >> 56 > 0`: これは、現在の `x` の値が、次のバイトを追加すると `uint64` の上位8ビット（つまり、`int64` の範囲を超える可能性のある部分）に影響を与えるかどうかをチェックします。具体的には、`x` が `(1 << 56) - 1` を超えている場合に真となります。これは、次のバイトがシフトインされる前にオーバーフローを検出するための早期チェックです。
        *   `x >> 63 > 0`: これは、最終的な `x` の値が `uint64` の最上位ビット（符号ビット）に達しているかどうかをチェックします。`int64` の最大値は `(1 << 63) - 1` であるため、`x` がこれを超えている場合はオーバーフローと判断されます。
    *   オーバーフローが検出された場合、`p.err = ErrHeader` を設定し、`0` を返します。`ErrHeader` は、tarヘッダが不正であることを示すエラーです。

4.  **符号なし整数での中間計算**:
    *   `x` を `uint64` 型で宣言することで、負の数を処理する際にビット反転を行う前の段階で、数値が `int64` の範囲を超えても正しく計算を進めることができます。最終的な結果は `int64` にキャストされます。

これらの変更により、`archive/tar` パッケージはGNU tar形式のbase-256エンコードされた数値を、負の数を含め、より堅牢かつ正確に解析できるようになりました。

## コアとなるコードの解説

### `parseNumeric` 関数の変更点

```go

+	// Check for base-256 (binary) format first.
+	// If the first bit is set, then all following bits constitute a two's

```

1.  **`if len(b) > 0 && b[0]&0x80 != 0`**:
    *   入力バイト列 `b` が空でなく、かつ最初のバイト `b[0]` の最上位ビット (0x80, つまり10000000b) がセットされている場合、この数値はbase-256エンコードされていると判断します。GNU tarの仕様に基づいています。

2.  **`var inv byte` と `if b[0]&0x40 != 0 { inv = 0xff }`**:
    *   `inv` は「反転マスク」として機能します。
    *   `b[0]&0x40` は、最初のバイトの2番目のビット (0x40, つまり01000000b) がセットされているかをチェックします。このビットがセットされている場合、GNU tarの仕様ではその数値が2の補数表現の負の数であることを示します。
    *   負の数であると判断された場合、`inv` を `0xff` (11111111b) に設定します。これにより、後続のXOR演算で各バイトがビット反転されます。正の数またはゼロの場合は `inv` は `0x00` のままで、XOR演算は何も行いません。

3.  **`var x uint64`**:
    *   解析中の数値を保持するための変数 `x` を `uint64` (符号なし64ビット整数) として宣言します。これにより、中間計算で `int64` の範囲を超えてもオーバーフローせずに値を蓄積できます。最終的な結果は `int64` に変換されます。

4.  **`c ^= inv`**:
    *   ループ内で各バイト `c` に対して `inv` とのXOR演算を行います。
    *   `inv` が `0xff` の場合（負の数）、`c ^ 0xff` は `c` の全ビットを反転させます（1の補数）。これにより、負の数を正の数として扱う準備ができます。
    *   `inv` が `0x00` の場合（正の数）、`c ^ 0x00` は `c` の値を変更しません。

5.  **`if i == 0 { c &= 0x7f }`**:
    *   最初のバイト `b[0]` の場合、その最上位ビット (0x80) はbase-256エンコーディングのフラグとして使用されるため、数値自体の一部ではありません。したがって、`c &= 0x7f` を使ってこのビットをクリアし、数値の計算には含めないようにします。

6.  **`if (x >> 56) > 0 { ... }`**:
    *   これは、次のバイトを `x` に追加する前に、早期に整数オーバーフローを検出するためのチェックです。
    *   `x >> 56` は、`x` の値が `uint64` の上位8ビットに達しているか（つまり、`x` が `2^56` 以上であるか）をチェックします。もしそうであれば、次のバイトをシフトイン (`x << 8`) すると、`uint64` の範囲を超えてしまう可能性があります。
    *   オーバーフローが検出された場合、`p.err = ErrHeader` を設定し、`0` を返してエラーを通知します。

7.  **`x = x<<8 | uint64(c)`**:
    *   現在の `x` の値を左に8ビットシフトし（`x << 8`）、新しいバイト `c` を最下位バイトとして結合します（`| uint64(c)`）。これにより、バイト列がビッグエンディアン順で数値として組み立てられます。

8.  **`if (x >> 63) > 0 { ... }`**:
    *   ループが終了した後、最終的な `x` の値が `uint64` の最上位ビット (63ビット目) に達しているか（つまり、`x` が `2^63` 以上であるか）をチェックします。
    *   `int64` の最大値は `2^63 - 1` であるため、`x` が `2^63` 以上であれば、`int64` に変換する際にオーバーフローが発生します。
    *   オーバーフローが検出された場合、`p.err = ErrHeader` を設定し、`0` を返します。

9.  **`if inv == 0xff { return ^int64(x) }`**:
    *   もし `inv` が `0xff` であった場合（元の数値が負であった場合）、`x` は既にビット反転された正の数として計算されています。
    *   `^int64(x)` は、`x` を `int64` にキャストした後、そのビットを再度反転させます。これは、2の補数表現の負の数を得るための操作です（`~x` と同等）。これにより、正しい負の数値が返されます。

10. **`return int64(x)`**:
    *   `inv` が `0x00` であった場合（元の数値が正またはゼロであった場合）、`x` は既に正しい正の数として計算されています。
    *   `x` を `int64` にキャストして返します。

11. **`return p.parseOctal(b)`**:
    *   最初のバイトの最上位ビットがセットされていない場合、その数値はbase-256エンコードではなく、通常の8進数エンコードであると判断し、既存の `parseOctal` 関数に処理を委譲します。

### `TestParseNumeric` 関数の追加

このテスト関数は、`parseNumeric` 関数がbase-256エンコードされた数値（正、負、ゼロ、オーバーフローケースを含む）と、従来の8進数エンコードされた数値の両方を正しく解析できることを検証します。

*   `vectors` スライスには、様々な入力バイト列 (`input`) と、それに対応する期待される出力数値 (`output`)、そして解析が成功するかどうか (`ok`) の組み合わせが定義されています。
*   特に、`\x80` で始まるバイト列はbase-256エンコードされた数値を示し、`\xff` は-1、`\xc0` は負の数、`\x80\x7f...` や `\xff\x7f...` はオーバーフローのケースをテストしています。
*   テストループでは、各 `vector` に対して `parseNumeric` を呼び出し、返された数値とエラー状態が期待値と一致するかを確認しています。これにより、新しい解析ロジックの正確性と堅牢性が保証されます。

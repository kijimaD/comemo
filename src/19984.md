## 変更の背景

このコミットは、Goランタイムにおけるスタック管理の特定のシナリオで発生するデータ競合を解決するために導入されました。Goのガベージコレクション（GC）は、プログラムの実行と並行して動作するように設計されています。この並行性により、GCのフェーズ（特にマークフェーズ）と、Goルーチン（goroutine）のスタックの割り当て・解放処理が同時に行われる可能性があります。

問題の核心は、スタックの縮小処理とスタックキャッシュのフラッシュ処理が、どちらもGCのマークフェーズ中に発生し、`mcache`内の`stackcache`にアクセスする点にありました。
- **スタックの縮小 (Stack shrinking)**: Goルーチンのスタックは、必要に応じて動的に拡大・縮小します。スタックが過剰に大きい場合、GCのマークフェーズ中に縮小されることがあります。この処理は、`mcache`が`stackcache`の所有権を持っていることを前提としていました。
- **スタックキャッシュのフラッシュ (Stack cache flushing)**: GCのマークフェーズ中には、`mcache`にキャッシュされているスタックをグローバルなスタックプールにフラッシュする処理も行われます。このフラッシュ処理は、`stackcache`へのアクセス時に同期メカニズムを使用していませんでした。

これらの処理が同時に発生すると、同期なしに`stackcache`にアクセスすることで、`stackcache`のデータが破損する可能性がありました。コミットメッセージに記載されている`http://goperfd.appspot.com/log/309af5571dfd7e1817259b9c9cf9bcf9b2c27610`のリンクは、この破損が実際に発生したことを示すパフォーマンスログへの参照です。このようなデータ破損は、プログラムのクラッシュや予期せぬ動作につながるため、早急な修正が必要でした。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とガベージコレクションの基本的な知識が必要です。

1.  **Goルーチン (Goroutine)**: Goにおける軽量な並行実行単位です。OSのスレッドよりもはるかに軽量で、数百万のGoルーチンを同時に実行できます。各Goルーチンは独自のスタックを持っています。

2.  **スタック (Stack)**: Goルーチンが関数呼び出しやローカル変数を格納するために使用するメモリ領域です。Goのスタックは動的であり、必要に応じて拡大・縮小します。これは、スタックオーバーフローを防ぎ、メモリ使用効率を高めるための重要な機能です。

3.  **`mcache` (Per-P Cache)**: Goランタイムは、メモリ割り当ての効率を高めるために、各プロセッサ（P）ごとにローカルなキャッシュ（`mcache`）を持っています。これにより、ロックの競合を減らし、高速なメモリ割り当てを可能にします。`mcache`は、小さなオブジェクトやスタックチャンクなど、頻繁に割り当てられるメモリをキャッシュします。

4.  **`stackcache`**: `mcache`の一部として、Goルーチンのスタックチャンクをキャッシュするための構造体です。Goルーチンがスタックを解放する際、そのスタックチャンクはすぐにグローバルなスタックプールに戻されるのではなく、まず`stackcache`に一時的に保持されます。これにより、同じGoルーチンがすぐに新しいスタックを必要とした場合に、高速に再利用できます。

5.  **ガベージコレクション (Garbage Collection - GC)**: GoのGCは、到達不能なメモリを自動的に解放するプロセスです。GoのGCは並行マーク＆スイープ方式を採用しており、プログラムの実行と並行してGCのフェーズが進行します。
    *   **マークフェーズ (Mark Phase)**: GCの重要なフェーズの一つで、到達可能なオブジェクトを特定し、マークします。このフェーズ中に、Goルーチンのスタックをスキャンして、参照されているオブジェクトを特定します。また、スタックの縮小やスタックキャッシュのフラッシュといった、スタック管理に関連する操作もこのフェーズ中に発生することがあります。

6.  **データ競合 (Data Race)**: 複数のGoルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期されていない場合に発生します。データ競合は、プログラムの動作を予測不能にし、バグの温床となります。

7.  **`runtime·lock` / `runtime·unlock`**: Goランタイム内部で使用される低レベルのロックプリミティブです。共有リソースへのアクセスを同期し、データ競合を防ぐために使用されます。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのスタック割り当て（`runtime·stackalloc`）とスタック解放（`runtime·stackfree`）の関数内で、`mcache`の`stackcache`へのアクセスを、GCのマークフェーズ中には行わないように変更した点にあります。

元のコードでは、`runtime·stackalloc`および`runtime·stackfree`関数内で、現在のGoルーチンが属するM（Machine、OSスレッドに対応）の`mcache`を取得し、その`mcache`が`nil`である場合にのみ、グローバルなスタックプールからスタックを割り当てたり解放したりしていました。`mcache`が`nil`になるのは、`exitsyscall`（システムコールからの復帰時）や`procresize`（プロセッサ数の変更時）のような特定の状況に限られていました。

しかし、GCのマークフェーズ中には、以下の2つの競合する操作が発生する可能性がありました。
1.  **スタックの縮小**: GCがGoルーチンのスタックをスキャンし、不要な部分を解放してスタックを縮小する際に、`mcache`の`stackcache`を操作します。この操作は、`mcache`がその`stackcache`の所有権を持っていることを前提としています。
2.  **スタックキャッシュのフラッシュ**: GCのマークフェーズ中に、`mcache`にキャッシュされているスタックチャンクがグローバルなスタックプールにフラッシュされることがあります。このフラッシュ処理は、`stackcache`に同期なしでアクセスしていました。

この2つの操作が同時に発生すると、`stackcache`への非同期アクセスによりデータ競合が発生し、`stackcache`が破損する可能性がありました。

このコミットでは、この問題を解決するために、`runtime·stackalloc`と`runtime·stackfree`関数内の条件式に`g->m->gcing`と`g->m->helpgc`という条件を追加しました。
-   `g->m->gcing`: 現在のM（OSスレッド）がGCのマークフェーズ中であることを示すフラグです。
-   `g->m->helpgc`: 現在のMがGCをヘルプしている（GC作業に参加している）ことを示すフラグです。

これにより、`mcache`が`nil`であるか、または現在のMがGCのマークフェーズ中（`g->m->gcing`がtrue）であるか、GCをヘルプしている（`g->m->helpgc`がtrue）場合には、`mcache`の`stackcache`を直接操作せず、代わりにグローバルなスタックプール（`stackpoolmu`ロックで保護されている）からスタックを割り当てたり解放したりするように変更されました。

この変更により、GCのマークフェーズ中に`stackcache`への競合アクセスが回避され、データ競合が解消されます。特に、コミットメッセージにある「Also don't touch stackcache during gc as it's flushed concurrently.」というコメントが示すように、GC中に`stackcache`が並行してフラッシュされるため、その間は`stackcache`を触らないという方針が明確に示されています。

## コアとなるコードの解説

### `runtime·stackalloc` 関数

この関数は、Goルーチンにスタックを割り当てる際に呼び出されます。

変更前:
```c
	c = g->m->mcache;
	if(c == nil) {
		// This can happen in the guts of exitsyscall or
		// procresize. Just get a stack from the global pool.
		runtime·lock(&stackpoolmu);
		x = poolalloc(order);
		runtime·unlock(&stackpoolmu);
	}
```
ここでは、`g->m->mcache`が`nil`の場合にのみ、グローバルなスタックプール（`stackpoolmu`ロックで保護されている）からスタックを取得していました。

変更後:
```c
	c = g->m->mcache;
	if(c == nil || g->m->gcing || g->m->helpgc) {
		// c == nil can happen in the guts of exitsyscall or
		// procresize. Just get a stack from the global pool.
		// Also don't touch stackcache during gc
		// as it's flushed concurrently.
		runtime·lock(&stackpoolmu);
		x = poolalloc(order);
		runtime·unlock(&stackpoolmu);
	}
```
条件式に `|| g->m->gcing || g->m->helpgc` が追加されました。
これにより、現在のMがGCのマークフェーズ中である（`g->m->gcing`がtrue）か、GCをヘルプしている（`g->m->helpgc`がtrue）場合も、`mcache`の`stackcache`を直接使用せず、グローバルなスタックプールからスタックを割り当てるようになりました。これは、GC中に`stackcache`が並行してフラッシュされる可能性があるため、競合を避けるための措置です。

### `runtime·stackfree` 関数

この関数は、Goルーチンがスタックを解放する際に呼び出されます。

変更前:
```c
	x = (MLink*)v;
	c = g->m->mcache;
	if(c == nil) {
		runtime·lock(&stackpoolmu);
		poolfree(x, order);
		runtime·unlock(&stackpoolmu);
	}
```
`runtime·stackalloc`と同様に、`g->m->mcache`が`nil`の場合にのみ、グローバルなスタックプールにスタックを解放していました。

変更後:
```c
	x = (MLink*)v;
	c = g->m->mcache;
	if(c == nil || g->m->gcing || g->m->helpgc) {
		runtime·lock(&stackpoolmu);
		poolfree(x, order);
		runtime·unlock(&stackpoolmu);
	}
```
ここでも条件式に `|| g->m->gcing || g->m->helpgc` が追加されました。
これにより、GC中にスタックを解放する際も、`mcache`の`stackcache`を直接操作せず、グローバルなスタックプールに解放することで、データ競合を回避しています。

これらの変更は、Goランタイムの並行GCとスタック管理の間の相互作用における微妙な競合状態を特定し、それを堅牢に解決するための重要な修正です。

## 技術的詳細

このコミットの技術的な核心は、Goランタイムのスタック割り当て（`runtime·stackalloc`）とスタック解放（`runtime·stackfree`）の関数内で、`mcache`の`stackcache`へのアクセスを、GCのマークフェーズ中には行わないように変更した点にあります。

元のコードでは、`runtime·stackalloc`および`runtime·stackfree`関数内で、現在のGoルーチンが属するM（Machine、OSスレッドに対応）の`mcache`を取得し、その`mcache`が`nil`である場合にのみ、グローバルなスタックプールからスタックを割り当てたり解放したりしていました。`mcache`が`nil`になるのは、`exitsyscall`（システムコールからの復帰時）や`procresize`（プロセッサ数の変更時）のような特定の状況に限られていました。

しかし、GCのマークフェーズ中には、以下の2つの競合する操作が発生する可能性がありました。
1.  **スタックの縮小**: GCがGoルーチンのスタックをスキャンし、不要な部分を解放してスタックを縮小する際に、`mcache`の`stackcache`を操作します。この操作は、`mcache`がその`stackcache`の所有権を持っていることを前提としています。
2.  **スタックキャッシュのフラッシュ**: GCのマークフェーズ中に、`mcache`にキャッシュされているスタックチャンクがグローバルなスタックプールにフラッシュされることがあります。このフラッシュ処理は、`stackcache`に同期なしでアクセスしていました。

この2つの操作が同時に発生すると、`stackcache`への非同期アクセスによりデータ競合が発生し、`stackcache`が破損する可能性がありました。

このコミットでは、この問題を解決するために、`runtime·stackalloc`と`runtime·stackfree`関数内の条件式に`g->m->gcing`と`g->m->helpgc`という条件を追加しました。
-   `g->m->gcing`: 現在のM（OSスレッド）がGCのマークフェーズ中であることを示すフラグです。
-   `g->m->helpgc`: 現在のMがGCをヘルプしている（GC作業に参加している）ことを示すフラグです。

これにより、`mcache`が`nil`であるか、または現在のMがGCのマークフェーズ中（`g->m->gcing`がtrue）であるか、GCをヘルプしている（`g->m->helpgc`がtrue）場合には、`mcache`の`stackcache`を直接操作せず、代わりにグローバルなスタックプール（`stackpoolmu`ロックで保護されている）からスタックを割り当てたり解放したりするように変更されました。

この変更により、GCのマークフェーズ中に`stackcache`への競合アクセスが回避され、データ競合が解消されます。特に、コミットメッセージにある「Also don't touch stackcache during gc as it's flushed concurrently.」というコメントが示すように、GC中に`stackcache`が並行してフラッシュされるため、その間は`stackcache`を触らないという方針が明確に示されています。

## コアとなるコードの解説

### `runtime·stackalloc` 関数

この関数は、Goルーチンにスタックを割り当てる際に呼び出されます。

変更前:
```c
	c = g->m->mcache;
	if(c == nil) {
		// This can happen in the guts of exitsyscall or
		// procresize. Just get a stack from the global pool.
		runtime·lock(&stackpoolmu);
		x = poolalloc(order);
		runtime·unlock(&stackpoolmu);
	}
```
ここでは、`g->m->mcache`が`nil`の場合にのみ、グローバルなスタックプール（`stackpoolmu`ロックで保護されている）からスタックを取得していました。

変更後:
```c
	c = g->m->mcache;
	if(c == nil || g->m->gcing || g->m->helpgc) {
		// c == nil can happen in the guts of exitsyscall or
		// procresize. Just get a stack from the global pool.
		// Also don't touch stackcache during gc
		// as it's flushed concurrently.
		runtime·lock(&stackpoolmu);
		x = poolalloc(order);
		runtime·unlock(&stackpoolmu);
	}
```
条件式に `|| g->m->gcing || g->m->helpgc` が追加されました。
これにより、現在のMがGCのマークフェーズ中である（`g->m->gcing`がtrue）か、GCをヘルプしている（`g->m->helpgc`がtrue）場合も、`mcache`の`stackcache`を直接使用せず、グローバルなスタックプールからスタックを割り当てるようになりました。これは、GC中に`stackcache`が並行してフラッシュされる可能性があるため、競合を避けるための措置です。

### `runtime·stackfree` 関数

この関数は、Goルーチンがスタックを解放する際に呼び出されます。

変更前:
```c
	x = (MLink*)v;
	c = g->m->mcache;
	if(c == nil) {
		runtime·lock(&stackpoolmu);
		poolfree(x, order);
		runtime·unlock(&stackpoolmu);
	}
```
`runtime·stackalloc`と同様に、`g->m->mcache`が`nil`の場合にのみ、グローバルなスタックプールにスタックを解放していました。

変更後:
```c
	x = (MLink*)v;
	c = g->m->mcache;
	if(c == nil || g->m->gcing || g->m->helpgc) {
		runtime·lock(&stackpoolmu);
		poolfree(x, order);
		runtime·unlock(&stackpoolmu);
	}
```
ここでも条件式に `|| g->m->gcing || g->m->helpgc` が追加されました。
これにより、GC中にスタックを解放する際も、`mcache`の`stackcache`を直接操作せず、グローバルなスタックプールに解放することで、データ競合を回避しています。

これらの変更は、Goランタイムの並行GCとスタック管理の間の相互作用における微妙な競合状態を特定し、それを堅牢に解決するための重要な修正です。

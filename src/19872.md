# [インデックス 19872] ファイルの概要

このコミットは、Go言語の標準ライブラリ `archive/zip` パッケージにおける、ZIPファイルのExtraフィールドのパースに関する厳格すぎる挙動を修正するものです。特に、一部のツール（AndroidのAPK生成ツールなど）が生成する、Extraフィールドの末尾に不正なゼロバイトが付加されたZIPファイルをGoが正しく扱えない問題に対応しています。

## 変更の背景

この変更は、Goの`archive/zip`パッケージが、一部の広く使われているZIPファイル作成ツール（特にAndroidのAPKファイルを生成するツール）によって生成されたZIPファイルを正しく処理できないという問題（Issue 8186）を解決するために行われました。

問題の根源は、ZIPファイルの「Extraフィールド」の扱いにありました。ZIPファイルフォーマットでは、各ファイルエントリや中央ディレクトリヘッダに、追加のメタデータを含めるための「Extraフィールド」が定義されています。このフィールドは、特定の構造を持つデータブロックの集合であり、各ブロックはタイプと長さを持つべきです。

しかし、一部のツールは、このExtraフィールドの末尾に、本来存在しないはずのゼロバイトを付加してZIPファイルを生成していました。Goの`archive/zip`パッケージは、このExtraフィールドのパースにおいて非常に厳格であり、フィールドの最後に余分なデータ（この場合はゼロバイト）が存在すると、それをフォーマットエラーと判断してZIPファイルの読み込みに失敗していました。

対照的に、他の多くの一般的なZIPツールは、このような不正な末尾のゼロバイトを許容し、無視して処理を続行していました。このため、Goの`archive/zip`パッケージだけが、これらの「不正だが広く普及している」ZIPファイルを扱えないという互換性の問題が生じていました。

このコミットは、Goの`archive/zip`パッケージが、現実世界のZIPファイルの多様性に対応し、より堅牢になることを目的としています。厳格さを緩めることで、より多くのZIPファイルを問題なく読み込めるようになり、特にAndroid開発者にとっては、GoアプリケーションがAPKファイルを直接処理できるようになるというメリットがあります。

## 前提知識の解説

### ZIPファイルフォーマットの概要

ZIPファイルは、複数のファイルやディレクトリを単一のアーカイブにまとめるための一般的なファイルフォーマットです。その構造は、主に以下の要素で構成されます。

1.  **ローカルファイルヘッダ (Local File Header)**: 各ファイルエントリの先頭に位置し、ファイル名、圧縮方法、圧縮・非圧縮サイズなどの情報を含みます。
2.  **ファイルデータ (File Data)**: 実際のファイルの内容（圧縮されている場合が多い）です。
3.  **データ記述子 (Data Descriptor)**: オプションで、ファイルデータの後に配置され、CRC-32チェックサムや最終的なサイズなどを含みます。
4.  **中央ディレクトリファイルヘッダ (Central Directory File Header)**: ZIPアーカイブの末尾近くに位置し、アーカイブ内の全ファイルエントリの情報を集約したものです。各エントリは、ファイル名、圧縮情報、ローカルファイルヘッダへのオフセットなどを含みます。
5.  **中央ディレクトリの終わりレコード (End of Central Directory Record)**: ZIPアーカイブの末尾に位置し、中央ディレクトリの開始位置やサイズ、アーカイブ内のエントリ数などの情報を含みます。

### Extraフィールド (Extra Field)

ZIPファイルフォーマットの重要な特徴の一つに「Extraフィールド」があります。これは、ローカルファイルヘッダと中央ディレクトリファイルヘッダの両方に存在し、標準のZIPフォーマットでは定義されていない追加のメタデータや拡張情報を格納するために使用されます。

Extraフィールドは、複数の「Extraフィールドデータブロック」の集合として構成されます。各データブロックは以下の構造を持ちます。

*   **ヘッダID (Header ID)**: 2バイト。このデータブロックのタイプを識別するIDです（例: `0x0001`はZIP64拡張情報、`0x5455`はUT（Unixタイムスタンプ）拡張情報など）。
*   **データサイズ (Data Size)**: 2バイト。このデータブロックのデータ部分の長さをバイト単位で示します。
*   **データ (Data)**: `Data Size`で指定された長さのデータ。

Extraフィールド全体の長さは、ヘッダIDとデータサイズを含む各データブロックの長さの合計になります。ZIPパーサーは、この構造に従ってExtraフィールドを読み進め、各データブロックを適切に解釈します。

### 問題点としての「末尾のゼロバイト」

本来、Extraフィールドは、その定義された長さの範囲内で全てのデータブロックが消費されるべきです。しかし、一部のツールは、Extraフィールドの最後に、どのデータブロックにも属さない余分なゼロバイトを付加してZIPファイルを生成することがありました。

Goの`archive/zip`パッケージは、Extraフィールドのパース後、残りのバイト列が完全に消費されている（つまり、残りのバイト列の長さがゼロである）ことを期待していました。もし残りのバイト列にゼロ以外のデータ、あるいはゼロバイトであっても余分なデータが残っている場合、Goのパーサーはこれをフォーマットエラーと見なし、`ErrFormat`を返していました。

この厳格なチェックが、他のツールが生成した「不正だが実用上問題ない」ZIPファイルをGoが扱えない原因となっていました。

## 技術的詳細

このコミットの技術的な核心は、`archive/zip`パッケージの`readDirectoryHeader`関数におけるExtraフィールドのパースロジックの変更です。

変更前は、Extraフィールドのデータ（`b`というバイトスライスで表される）を全て読み込んだ後、`len(b)`がゼロであることを厳密にチェックしていました。もし`len(b)`がゼロでなければ、それはExtraフィールドの最後に未消費のデータが残っていることを意味し、`ErrFormat`を返していました。

変更後は、このチェックを緩和し、Extraフィールドのパース後に残ったバイト列（`b`）が全てゼロバイトである場合は、それを許容するようにしました。具体的には、残りのバイト列をループで走査し、一つでもゼロ以外のバイトが見つかった場合にのみ`ErrFormat`を返すように変更されました。これにより、末尾に付加されたゼロバイトは事実上無視されることになります。

この変更は、ZIPファイルフォーマットの仕様に対するGoの解釈を、より「寛容な」ものへとシフトさせるものです。これは、厳密な仕様遵守よりも、現実世界で広く使われている（しかし厳密には仕様に準拠していない）ファイルの互換性を優先するという、実用的な判断に基づいています。

テストケース`TestIssue8186`が追加され、この変更が意図通りに機能することを確認しています。このテストでは、AndroidのJARファイル（実質的にはZIPファイル）から抽出された、末尾にゼロバイトを含むExtraフィールドのサンプルデータを用いて、`readDirectoryHeader`関数がエラーを返さずに正常に処理できることを検証しています。

## コアとなるコードの解説

### `src/pkg/archive/zip/reader.go` の変更点

`readDirectoryHeader`関数は、ZIPファイルの中央ディレクトリヘッダを読み込む役割を担っています。この関数内で、Extraフィールドの処理が行われます。

変更前のコードは以下のようになっていました。

```go
		// Should have consumed the whole header.
		if len(b) != 0 {
			return ErrFormat
		}
```

ここで`b`はExtraフィールドのデータを表すバイトスライスです。Extraフィールドの各データブロックをパースした後、`b`が空（`len(b) == 0`）であることを期待していました。もし`b`にデータが残っていれば、それは不正なフォーマットであると判断し、`ErrFormat`を返していました。

変更後のコードは以下のようになります。

```go
		// But popular zip & JAR creation tools are broken and
		// may pad extra zeros at the end, so accept those
		// too. See golang.org/issue/8186.
		for _, v := range b {
			if v != 0 {
				return ErrFormat
			}
		}
```

この変更では、`if len(b) != 0`という厳密なチェックを削除し、代わりに`for`ループを導入しています。このループは、Extraフィールドのパース後に`b`に残った全てのバイトを走査します。ループ内で`if v != 0`という条件がチェックされ、もし一つでもゼロ以外のバイトが見つかった場合、その時点で`ErrFormat`を返します。

このロジックの変更により、`b`に残ったバイトが全てゼロである場合は、エラーを返さずに処理を続行するようになります。つまり、Extraフィールドの末尾に不正なゼロバイトが付加されていても、Goの`archive/zip`パッケージはそれを許容し、正常にZIPファイルを読み込めるようになります。コメントにもあるように、これは「人気のあるZIP & JAR作成ツールが壊れていて、末尾に余分なゼロをパディングする可能性があるため、それらも受け入れる」という実用的な判断に基づいています。

### `src/pkg/archive/zip/reader_test.go` の変更点

`TestIssue8186`という新しいテスト関数が追加されました。このテストは、実際のAndroid JARファイルから抽出された、末尾にゼロバイトを含むExtraフィールドのサンプルデータ（`dirEnts`スライス内の各文字列）を使用して、`readDirectoryHeader`関数がエラーなく処理できることを検証します。

各`dirEnts`の文字列は、中央ディレクトリヘッダのバイナリ表現の一部であり、特にExtraフィールドの部分に問題のあるデータが含まれています。テストはこれらの文字列を`strings.NewReader`で`io.Reader`に変換し、`readDirectoryHeader`関数に渡します。もし`readDirectoryHeader`がエラーを返した場合、テストは失敗し、問題が解決されていないことを示します。このテストの追加により、今回の修正が意図通りに機能し、将来のリグレッションを防ぐための安全網が提供されます。

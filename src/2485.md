# [インデックス 2485] ファイルの概要

このコミットは、Goコンパイラの型システムにおける型変換と代入互換性のロジックを修正するものです。具体的には、`src/cmd/gc/subr.c`と`src/cmd/gc/walk.c`の2つのファイルが変更されています。

*   `src/cmd/gc/subr.c`: このファイルは、Goコンパイラのバックエンドである`gc`（Go Compiler）の一部であり、型システムに関するサブルーチンやユーティリティ関数を定義しています。`eqtype`（型が等しいか）や`cvttype`（型が変換可能か）といった、型の比較や互換性チェックを行う重要な関数が含まれています。
*   `src/cmd/gc/walk.c`: このファイルは、コンパイラの「ウォーカー」フェーズを担当します。AST（抽象構文木）を走査し、型チェック、定数畳み込み、最適化、そして型変換の挿入など、様々なセマンティックな処理を行います。`walkconv`関数は、明示的な型変換ノードを処理する役割を担っています。

## コミット

このコミットは、Go言語の仕様における型変換に関する新しい言語規定を実装するものです。特に、型変換の「自明性（triviality）」と「代入互換性（assignment compatibility）」のルールを明確にし、コンパイラがこれらを正確に評価できるようにロジックを更新しています。

## 変更の背景

Go言語は、その初期段階から厳格な型システムと明示的な型変換を重視してきました。他の多くの言語とは異なり、Goはほとんどの状況で暗黙的な型変換を許容せず、プログラマが意図的に型変換を記述することを求めます。これは、予期せぬバグを防ぎ、コードの可読性と堅牢性を高めるための設計思想です。

このコミットが行われた2009年頃は、Go言語がまだ開発の初期段階にあり、言語仕様が活発に策定されていた時期にあたります。特に、型変換と代入互換性に関するルールは、言語のセマンティクスにおいて非常に重要であり、コンパイラがこれらのルールを正確に実装することが不可欠でした。

このコミットの背景には、以下の点が考えられます。

1.  **言語仕様の明確化**: Go言語の型変換に関する仕様がより詳細に定義され、コンパイラがその新しい規定に沿って動作する必要が生じた。特に、名前付き型（named types）とインターフェース型（interface types）の扱い、そして「自明な変換（trivial conversion）」と「非自明な変換（non-trivial conversion）」の区別が明確化された可能性があります。
2.  **コンパイラの正確性の向上**: 既存の型変換ロジックが、特定のケース（特に名前付き型やインターフェースを含む複雑な型）で仕様と異なる振る舞いをしていたか、あるいは仕様が曖昧であったために一貫性のない挙動を示していた可能性があり、それを修正する必要があった。
3.  **コード生成の最適化**: 自明な変換（例えば、同じ基底型を持つ異なる名前付き型間の変換で、ビットパターンが変わらないもの）をコンパイラが認識することで、不要なコード生成を省略し、実行時のオーバーヘッドを削減する機会が生まれます。

この変更は、Go言語の型システムの堅牢性と予測可能性を確立する上で重要な一歩であり、後のGo 1互換性保証の基盤の一部を形成しています。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語およびGoコンパイラに関する前提知識が必要です。

1.  **Goの型システム**:
    *   **基底型 (Underlying Type)**: Goの型は、その「基底型」によって定義されます。例えば、`type MyInt int`と定義された`MyInt`型は、`int`を基底型とします。
    *   **名前付き型 (Named Types)**: `type T S`のように`type`キーワードで宣言された型は「名前付き型」です。`T`は`S`とは異なる新しい型とみなされますが、`S`を基底型とします。
    *   **インターフェース型 (Interface Types)**: メソッドの集合を定義する型です。インターフェース型は、そのメソッドセットを実装する任意の具象型の値を保持できます。
    *   **型同一性 (Type Identity)**: Goでは、2つの型が「同一」であるかどうかのルールが厳格に定められています。名前付き型は、たとえ基底型が同じであっても、他の名前付き型や無名型とは異なる型とみなされます。
    *   **型変換 (Type Conversion)**: `T(v)`のように明示的に記述することで、ある型の値を別の型に変換する操作です。Goでは、特定の条件下でのみ型変換が許可されます。
    *   **代入互換性 (Assignability)**: ある型の値を別の型の変数に代入できるかどうかのルールです。型変換と同様に、Goでは厳格なルールが適用されます。

2.  **Goコンパイラ (`gc`) の構造**:
    *   **AST (Abstract Syntax Tree)**: ソースコードを解析して生成される、プログラムの構造を木構造で表現したものです。コンパイラはこのASTを様々なフェーズで処理します。
    *   **`Type`構造体**: コンパイラ内部でGoの型を表現するためのデータ構造です。この構造体には、型の種類（`etype`）、基底型、要素型（ポインタや配列の場合）、そして型が名前付き型である場合のシンボル（`sym`）などの情報が含まれます。
    *   **`Sym`フィールド**: `Type`構造体内の`sym`フィールドは、名前付き型の場合にその型の名前（シンボル）を指します。このコミットでは、この`sym`フィールドの扱いが重要な変更点となります。
    *   **`eqtype1`関数**: 2つの型が「等しい」かどうかを比較する関数です。この関数は、型の構造的な等価性をチェックします。
    *   **`cvttype`関数**: ある型から別の型へ「自明な変換」が可能かどうかを判断する関数です。このコミットでそのロジックが大きく変更されています。
    *   **`ascompat`関数**: ある型から別の型への「代入互換性」があるかどうかを判断する関数です。このコミットでそのロジックが拡張されています。
    *   **`walkconv`関数**: ASTの走査中に型変換ノードを処理し、必要に応じて変換ロジックを挿入する関数です。

3.  **自明な変換 (Trivial Conversion) と非自明な変換 (Non-Trivial Conversion)**:
    *   **自明な変換**: ビットパターンが変化しない型変換を指します。例えば、同じ基底型を持つ異なる名前付き型間の変換などがこれに該当する場合があります。コンパイラはこのような変換に対して、実行時に特別なコードを生成する必要がないため、最適化の対象となります。
    *   **非自明な変換**: ビットパターンが変化したり、実行時に追加の処理が必要となる型変換を指します。例えば、`int`から`float64`への変換や、具象型からインターフェース型への変換などがこれに該当します。

## 技術的詳細

このコミットの核心は、Go言語の型変換と代入互換性に関するルールを、特に名前付き型とインターフェース型に関して、より厳密かつ正確にコンパイラに実装することにあります。

### `cvttype`関数の変更

`cvttype(Type *dst, Type *src)`関数は、`src`型から`dst`型への「自明な変換」が可能かどうかを判断します。変更前は`eqtype1`を直接呼び出していましたが、変更後は以下のロジックが追加されています。

1.  まず、`eqtype1(dst, src, 0, 0)`を呼び出して、2つの型が構造的に完全に等しいかをチェックします。等しければ、それは自明な変換であるため`1`を返します。
2.  もし構造的に等しくない場合、**名前付き型のシンボル（`sym`フィールド）を一時的に`nil`に設定**します。これは、名前付き型であっても、その「基底型」が同じであれば変換可能とみなすケースを考慮するためです。
3.  シンボルを`nil`にした状態で`ascompat(dst, src)`を呼び出し、代入互換性をチェックします。
4.  `ascompat`が`1`（自明な代入互換性あり）を返した場合、`cvttype`も`1`を返します。
5.  最後に、一時的に`nil`にしたシンボルを元の値に戻します。

この変更により、`cvttype`は、名前が異なるが基底型が同じであるような名前付き型間の変換を「自明な変換」として正しく識別できるようになりました。例えば、`type MyInt int`と`type YourInt int`があった場合、`MyInt(yourIntVal)`のような変換は、基底型が`int`で同じであるため、ビットパターンは変化せず、自明な変換とみなされます。

### `ascompat`関数の変更

`ascompat(Type *dst, Type *src)`関数は、`src`型の値を`dst`型の変数に代入できるか、つまり代入互換性があるかを判断します。この関数は、変更により戻り値の意味が拡張され、より詳細な互換性の種類を報告するようになりました。

*   **戻り値の拡張**:
    *   `0`: 代入互換性なし。
    *   `1`: 自明な代入互換性あり（ビットパターンが変化しない）。
    *   `2`: 非自明な代入互換性あり（ビットパターンが変化するか、実行時の処理が必要）。

*   **前方宣言型 (`TFORWINTER`, `TFORWSTRUCT`, `TFORW`) の追加チェック**:
    前方宣言型（まだ完全に定義されていない型）が`dst`または`src`にある場合、代入互換性はないと判断し、`0`を返します。これは、未定義の型に対する操作を早期に検出してエラーとするための堅牢性向上です。

*   **インターフェース型のロジック変更**:
    変更前は、インターフェース型間の代入や、具象型からインターフェース型への代入はすべて`1`（自明な互換性）を返していました。しかし、インターフェース型への代入は、通常、型アサーションやメソッドテーブルの構築といった実行時処理を伴うため、ビットパターンがそのままコピーされる「自明な」操作ではありません。
    変更後は、`isnilinter`（nilインターフェース）、`isinter`（インターフェース）、`methtype`（メソッドを持つ型、つまり具象型）の組み合わせにおいて、**すべて`2`（非自明な代入互換性）を返す**ように修正されました。これにより、コンパイラはインターフェース関連の代入が実行時コストを伴うことを正しく認識し、適切なコードを生成できるようになります。

*   **名前付き具象型の厳格化**:
    `if(dst->sym && src->sym && dst != src)`という新しいチェックが追加されました。これは、`dst`と`src`の両方が名前付き型であり、かつそれらが異なる型である場合、代入互換性はないと判断し、`0`を返します。
    このルールは、Goの型システムの核心である「名前付き型は、たとえ基底型が同じであっても、互いに異なる型である」という原則を厳格に適用するものです。例えば、`type MyInt int`と`type YourInt int`があった場合、`MyInt`型の変数に`YourInt`型の値を直接代入することはできません（明示的な型変換が必要です）。このチェックは、このような直接代入をコンパイル時に禁止します。

*   **配列ポインタの変換**:
    配列ポインタの変換（例: `*[N]T`から`*[]T`への変換）も、以前は`1`を返していましたが、`2`（非自明な互換性）を返すように変更されました。これは、スライスヘッダの構築など、実行時に追加の処理が必要になるためです。

### `walkconv`関数の変更

`walkconv(Node *n)`関数は、AST中の型変換ノードを処理します。この関数は、`cvttype(t, l->type)`の結果を直接評価していましたが、`cvttype`の戻り値が`1`（自明な変換）である場合にのみ、変換が不要な「no-op」として処理するように変更されました。

`if(cvttype(t, l->type) == 1)`

この変更は、`cvttype`が「自明な変換」と「非自明な変換」を区別するようになったことに対応しています。`cvttype`が`2`（非自明な変換）を返す場合、`walkconv`は変換をno-opとして扱わず、適切な変換コードを生成するパスに進むことになります。

これらの変更は、Goコンパイラが言語仕様に沿って、より正確かつ効率的に型変換と代入互換性を処理するための基盤を強化するものです。特に、名前付き型とインターフェースのセマンティクスが明確化され、コンパイラが実行時のオーバーヘッドを伴う変換とそうでない変換を区別できるようになりました。

## コアとなるコードの解説

### `src/cmd/gc/subr.c` の `cvttype` 関数

*   **変更前**: `cvttype`は単に`eqtype1(t1, t2, 0, 0)`の結果を返していました。これは、2つの型が構造的に完全に等しい場合にのみ変換可能とみなす、非常に厳格なチェックでした。名前付き型が異なれば、たとえ基底型が同じでも変換不可と判断されていました。
*   **変更後**:
    *   まず、`eqtype1(dst, src, 0, 0)`で完全な型同一性をチェックします。ここで`1`が返されれば、最も自明な変換として処理を終えます。
    *   次に、`dst->sym = nil;`と`src->sym = nil;`によって、一時的に`dst`と`src`の型シンボル（名前）をクリアします。これは、名前付き型であっても、その名前を無視して基底型レベルでの互換性をチェックするための準備です。
    *   `ascompat(dst, src)`を呼び出し、シンボルを無視した状態での代入互換性をチェックします。
    *   `ascompat`が`1`（自明な代入互換性）を返した場合、`cvttype`も`1`を返します。これは、名前は異なるが基底型が同じである名前付き型間の変換が、ビットパターンを変更しない「自明な変換」として扱われることを意味します。
    *   最後に、`dst->sym = ds;`と`src->sym = ss;`で、一時的にクリアしたシンボルを元の値に戻します。これは、関数の副作用を避けるための重要なステップです。

この変更により、`cvttype`は、名前付き型間の変換において、その名前ではなく基底型に基づく「自明な変換」の概念を導入しました。

### `src/cmd/gc/walk.c` の `walkconv` 関数

*   **変更前**: `if(cvttype(t, l->type))`という条件で、`cvttype`が非ゼロを返せばno-op変換とみなしていました。
*   **変更後**: `if(cvttype(t, l->type) == 1)`という条件に変わりました。これは、`cvttype`が`1`（自明な変換）を返した場合にのみno-opとして扱うことを明示しています。`cvttype`が`2`（非自明な変換）を返すようになったため、この変更は必須でした。これにより、非自明な変換に対しては、`walkconv`が適切な変換コードを生成するパスに進むことが保証されます。

### `src/cmd/gc/walk.c` の `ascompat` 関数

*   **関数のコメント変更**: 戻り値が`0`（互換性なし）、`1`（自明な変換）、`2`（非自明な変換）の3種類になったことが明記されました。
*   **前方宣言型 (`TFORWINTER`, `TFORWSTRUCT`, `TFORW`) のチェック追加**:
    ```c
    if(dst->etype == TFORWINTER || dst->etype == TFORWSTRUCT || dst->etype == TFORW)
    	return 0;
    if(src->etype == TFORWINTER || src->etype == TFORWSTRUCT || src->etype == TFORW)
    	return 0;
    ```
    これらの行は、まだ完全に定義されていない前方宣言型が代入の対象またはソースにある場合、代入互換性がないと判断し、コンパイルエラーを早期に検出します。
*   **インターフェース型のロジック変更**:
    ```c
    // interfaces go through even if names don't match
    if(isnilinter(dst) || isnilinter(src))
    	return 2;
    if(isinter(dst) && isinter(src))
    	return 2;
    if(isinter(dst) && methtype(src))
    	return 2;
    if(isinter(src) && methtype(dst))
    	return 2;
    ```
    変更前はこれらのケースで`1`を返していましたが、すべて`2`を返すように変更されました。これは、インターフェース型への代入やインターフェース型間の代入が、実行時にメソッドテーブルのルックアップや型アサーションなどの処理を伴うため、ビットパターンがそのままコピーされる「自明な」操作ではないことを反映しています。
*   **名前付き具象型の厳格化**:
    ```c
    // otherwise, if concrete types have names, they must match
    if(dst->sym && src->sym && dst != src)
    	return 0;
    ```
    この重要な追加は、`dst`と`src`が両方とも名前付き型であり、かつそれらが異なる型である場合（例: `type A int; type B int; var a A; var b B; a = b`）、代入互換性がないと判断し`0`を返します。Goの型システムでは、名前付き型は基底型が同じでも異なる型とみなされるため、このチェックは言語のセマンティクスを正確に実装するものです。
*   **配列ポインタの変換**:
    ```c
    // ... (previous conditions) ...
    && isfixedarray(src->type)
    && eqtype(dst->type, src->type->type))
    	return 2; // Changed from 1 to 2
    ```
    配列ポインタの変換（例: `*[N]T`から`*[]T`への変換）も、スライスヘッダの構築など実行時処理が必要なため、`1`から`2`に変更されました。

これらの変更により、`ascompat`は代入互換性の種類をより詳細に区別できるようになり、コンパイラはGo言語の厳格な型ルール、特に名前付き型とインターフェースの挙動を正確に強制できるようになりました。

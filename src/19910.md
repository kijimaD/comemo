このコミットでは、Go言語の`crypto/tls`パッケージにおいて、SNI (Server Name Indication) に基づく証明書選択のメカニズムが拡張されました。具体的には、静的な`NameToCertificate`マップに加えて、動的に証明書を選択できる`GetCertificate`コールバック関数が導入されました。

*   `src/pkg/crypto/tls/handshake_server.go`: サーバーハンドシェイクにおける証明書選択ロジックの更新。
*   `src/pkg/crypto/tls/handshake_server_test.go`: 新しい`GetCertificate`コールバックの動作を検証するためのテストケースの追加。

## 元コミット内容

`crypto/tls: Added dynamic alternative to NameToCertificate map for SNI`

これは、SNI (Server Name Indication) のために、既存の`NameToCertificate`マップに代わる動的な方法を追加するという内容です。

## 変更の背景

Goの`crypto/tls`パッケージは、TLS (Transport Layer Security) 通信を実装するための機能を提供します。ウェブサーバーなどが複数のドメイン名（仮想ホスト）を単一のIPアドレスとポートでホストする場合、クライアントはTLSハンドシェイクの初期段階で、どのサーバー名に接続しようとしているかをサーバーに伝える必要があります。この仕組みがSNI (Server Name Indication) です。

以前のGoのTLS実装では、SNIに基づいて適切な証明書を選択するために、`Config`構造体内の`NameToCertificate`という`map[string]*Certificate`型のフィールドを使用していました。このマップは、サーバー名（ドメイン名）とそれに対応するTLS証明書を静的にマッピングするものでした。

しかし、この静的なマップにはいくつかの制限がありました。

1.  **動的な証明書発行への対応の困難さ**: Let's Encryptのようなサービスが普及し、証明書が頻繁に更新されたり、オンデマンドで発行されたりする環境では、サーバーの起動時にすべての証明書をメモリにロードし、静的なマップに格納しておくのは非効率的でした。特に、非常に多くのドメインをホストする場合、メモリ使用量が増大し、起動時間が長くなる可能性がありました。
2.  **複雑な証明書選択ロジックへの対応の限界**: 単純なドメイン名と証明書の1対1マッピングだけでなく、例えばワイルドカード証明書のより複雑なマッチングルール、特定のクライアント情報（CipherSuites、SupportedCurvesなど）に基づいた証明書の選択、あるいは外部サービスへの問い合わせが必要な場合など、より高度な証明書選択ロジックを実装することが困難でした。
3.  **エラーハンドリングの欠如**: `NameToCertificate`マップから証明書が見つからなかった場合、フォールバックとして`Certificates`スライス（通常はデフォルト証明書）が使用されるだけで、証明書選択プロセス中に発生したエラーを適切に処理したり、クライアントにエラーを通知したりするメカニズムがありませんでした。

これらの背景から、より柔軟で動的な証明書選択を可能にするために、コールバック関数を導入する変更が必要となりました。

## 前提知識の解説

### TLS/SSL (Transport Layer Security / Secure Sockets Layer)

TLSは、インターネット上で安全な通信を行うための暗号化プロトコルです。ウェブサイトのHTTPS通信などで広く利用されています。TLSハンドシェイクは、クライアントとサーバーが安全な通信チャネルを確立するために行われる一連のネゴシエーションプロセスです。このプロセス中に、サーバーは自身の身元を証明するためにデジタル証明書をクライアントに提示します。

### SNI (Server Name Indication)

SNIは、TLSプロトコルの拡張機能であり、クライアントがTLSハンドシェイクの初期段階（`ClientHello`メッセージ内）で、接続しようとしているサーバーのホスト名（ドメイン名）をサーバーに伝えることを可能にします。これにより、単一のIPアドレスとポートで複数のウェブサイト（仮想ホスト）を運用しているサーバーが、クライアントがどのサイトにアクセスしようとしているかを識別し、それに対応する適切なTLS証明書を提示できるようになります。SNIがない場合、サーバーはどの証明書を提示すべきか判断できず、デフォルトの証明書を提示するか、接続を拒否するしかありませんでした。

### Goの`crypto/tls`パッケージ

Go言語の標準ライブラリに含まれる`crypto/tls`パッケージは、TLSクライアントおよびサーバーの実装を提供します。このパッケージの中心的な構造体の一つが`tls.Config`です。`tls.Config`は、TLS接続の挙動を制御するための様々な設定オプションを含んでいます。

*   **`Certificates []Certificate`**: サーバーが使用する証明書のリスト。通常、これはデフォルトの証明書として機能します。
*   **`NameToCertificate map[string]*Certificate`**: SNIが利用された際に、特定のサーバー名（ドメイン名）に対応する証明書を検索するためのマップ。

### 証明書選択の課題

大規模なサービスやCDN (Content Delivery Network) では、数千、数万ものドメインを単一のTLSサーバーで処理することがあります。このような環境で、すべての証明書を事前にメモリにロードし、静的なマップで管理することは、リソースの観点から非現実的です。また、証明書の有効期限管理や自動更新の仕組みと連携させるためには、動的に証明書を取得・選択できる柔軟なメカニズムが求められます。

## 技術的詳細

このコミットの主要な技術的変更点は、`tls.Config`構造体に新しいフィールドと、それに関連するヘルパー関数が追加されたことです。

1.  **`ClientHelloInfo`構造体の導入**:
    TLSハンドシェイクの`ClientHello`メッセージから得られる情報をカプセル化するための新しい構造体`ClientHelloInfo`が導入されました。この構造体は、証明書選択の判断材料となる以下の情報を含みます。
    *   `CipherSuites []uint16`: クライアントがサポートする暗号スイートのリスト。
    *   `ServerName string`: クライアントがSNIで指定したサーバー名。
    *   `SupportedCurves []CurveID`: クライアントがサポートする楕円曲線のリスト。
    *   `SupportedPoints []uint8`: クライアントがサポートするポイントフォーマットのリスト。

    この構造体は、動的な証明書選択を行う際に、クライアントの要求に関する詳細なコンテキストを`GetCertificate`コールバック関数に提供するために使用されます。

2.  **`Config`構造体への`GetCertificate`コールバック関数の追加**:
    `tls.Config`構造体に、`GetCertificate func(clientHello *ClientHelloInfo) (*Certificate, error)`という新しいフィールドが追加されました。
    このフィールドは、サーバーがクライアントからの`ClientHello`メッセージを受け取った際に呼び出されるコールバック関数を定義します。この関数は、`ClientHelloInfo`を受け取り、適切な`*Certificate`と`error`を返します。
    *   もし`GetCertificate`が`nil`でない、かつ、有効な`*Certificate`を返すか、`error`を返した場合、その結果が使用されます。
    *   もし`GetCertificate`が`nil`または`nil`の`*Certificate`と`nil`の`error`を返した場合、従来の`NameToCertificate`マップ（もし設定されていれば）がフォールバックとして使用されます。
    *   最終的に、`NameToCertificate`も設定されていないか、マッチする証明書が見つからない場合は、`Config.Certificates`の最初の要素がデフォルトとして使用されます。

3.  **`getCertificateForName`から`getCertificate`への変更**:
    既存の`getCertificateForName(name string)`関数が`getCertificate(clientHello *ClientHelloInfo) (*Certificate, error)`に改名され、引数も`ClientHelloInfo`構造体を受け取るように変更されました。この関数は、まず`Config.GetCertificate`コールバックが設定されているかを確認し、設定されていればそれを呼び出します。コールバックが証明書を返さない場合にのみ、従来の`NameToCertificate`マップによる検索ロジックが実行されます。これにより、動的な証明書選択が静的なマップ検索よりも優先されるようになりました。また、エラーを返すことができるようになったため、証明書取得時の問題（例: データベースエラー、外部サービスとの通信エラー）を適切にハンドリングし、TLSアラートとしてクライアントに通知できるようになりました。

4.  **サーバーハンドシェイクロジックの更新**:
    `src/pkg/crypto/tls/handshake_server.go`内のサーバーハンドシェイク処理において、クライアントからSNI情報が提供された場合、`config.getCertificate`関数が新しい`ClientHelloInfo`構造体と共に呼び出されるように変更されました。これにより、サーバーはクライアントの要求に基づいて動的に証明書を選択できるようになります。`getCertificate`がエラーを返した場合、サーバーは`alertInternalError`をクライアントに送信し、ハンドシェイクを終了します。

5.  **テストケースの追加**:
    `src/pkg/crypto/tls/handshake_server_test.go`に、新しい`GetCertificate`コールバックの動作を検証するための複数のテストケースが追加されました。
    *   `TestHandshakeServerSNIGetCertificate`: `GetCertificate`コールバックが正しく証明書を返すことを確認。
    *   `TestHandshakeServerSNIGetCertificateNotFound`: `GetCertificate`コールバックが証明書を返さない場合に、`NameToCertificate`マップへのフォールバックが正しく機能することを確認。
    *   `TestHandshakeServerSNIGetCertificateError`: `GetCertificate`コールバックがエラーを返した場合に、TLSアラートが正しく送信されることを確認。

これらの変更により、GoのTLSサーバーは、より複雑で動的な証明書管理のシナリオに対応できるようになり、大規模なサービスや特殊な要件を持つ環境での柔軟性が大幅に向上しました。

### `src/pkg/crypto/tls/common.go`

#### `ClientHelloInfo`構造体の追加

```go
// ClientHelloInfo contains information from a ClientHello message in order to
// guide certificate selection in the GetCertificate callback.
type ClientHelloInfo struct {
	// CipherSuites lists the CipherSuites supported by the client (e.g.
	// TLS_RSA_WITH_RC4_128_SHA).
	CipherSuites []uint16

	// ServerName indicates the name of the server requested by the client
	// in order to support virtual hosting. ServerName is only set if the
	// client is using SNI (see
	// http://tools.ietf.org/html/rfc4366#section-3.1).
	ServerName string

	// SupportedCurves lists the elliptic curves supported by the client.
	// SupportedCurves is set only if the Supported Elliptic Curves
	// Extension is being used (see
	// http://tools.ietf.org/html/rfc4492#section-5.1.1).
	SupportedCurves []CurveID

	// SupportedPoints lists the point formats supported by the client.
	// SupportedPoints is set only if the Supported Point Formats Extension
	// is being used (see
	// http://tools.ietf.org/html/rfc4492#section-5.1.2).
	SupportedPoints []uint8
}
```

#### `getCertificateForName`から`getCertificate`への変更とロジックの更新

```go
// getCertificate returns the best certificate for the given ClientHelloInfo,
// defaulting to the first element of c.Certificates.
func (c *Config) getCertificate(clientHello *ClientHelloInfo) (*Certificate, error) {
	if c.GetCertificate != nil {
		cert, err := c.GetCertificate(clientHello)
		if cert != nil || err != nil {
			return cert, err
		}
	}

	if len(c.Certificates) == 1 || c.NameToCertificate == nil {
		// There's only one choice, so no point doing any work.
		return &c.Certificates[0], nil
	}

	name := strings.ToLower(clientHello.ServerName)
	for len(name) > 0 && name[len(name)-1] == '.' {
		name = name[:len(name)-1]
	}

	if cert, ok := c.NameToCertificate[name]; ok {
		return cert, nil
	}

	// try replacing labels in the name with wildcards until we get a
	// match.
	labels := strings.Split(name, ".")
	for i := 0; i < len(labels)-1; i++ {
		labels[i] = "*"
		candidate := strings.Join(labels, ".")
		if cert, ok := c.NameToCertificate[candidate]; ok {
			return cert, nil
		}
	}

	// If nothing matches, return the first certificate.
	return &c.Certificates[0], nil
}
```

## コアとなるコードの解説

### `ClientHelloInfo`構造体

この構造体は、クライアントがTLSハンドシェイクの開始時に送信する`ClientHello`メッセージから抽出される重要な情報（サポートする暗号スイート、SNIで指定されたサーバー名、サポートする楕円曲線、ポイントフォーマットなど）をまとめたものです。これにより、`GetCertificate`コールバック関数は、単にサーバー名だけでなく、クライアントの能力や要求に関するより詳細なコンテキストに基づいて、最適な証明書を選択できるようになります。

### `Config.GetCertificate`フィールド

これは、`tls.Config`に新たに追加された関数型のフィールドです。サーバーがクライアントからの`ClientHello`メッセージを受け取ると、この関数が呼び出されます。開発者はこの関数を実装することで、以下のような動的な証明書選択ロジックを自由に記述できます。

*   **データベースからの証明書取得**: サーバー名に基づいてデータベースから証明書を検索・ロードする。
*   **外部APIとの連携**: 証明書管理サービスやCA (Certificate Authority) と連携して、オンデマンドで証明書を取得する。
*   **複雑なマッチングロジック**: SNI名だけでなく、クライアントがサポートする暗号スイートや楕円曲線などの情報も考慮して、最適な証明書を選択する。
*   **エラーハンドリング**: 証明書の取得に失敗した場合に、適切なエラーを返し、クライアントにTLSアラートを送信する。

このコールバックが`nil`でない証明書またはエラーを返した場合、その結果が優先されます。これにより、従来の静的な`NameToCertificate`マップよりも柔軟な証明書選択が可能になります。

### `(*Config) getCertificate`メソッド

このメソッドは、TLSサーバーが実際に使用する証明書を決定するロジックをカプセル化しています。変更のポイントは以下の通りです。

1.  **`GetCertificate`コールバックの優先**: まず、`c.GetCertificate`が設定されているかを確認し、設定されていればそれを呼び出します。コールバックが証明書を返すか、エラーを返した場合、その結果が直ちに使用されます。これにより、動的な証明書選択が静的なマップ検索よりも優先される「フック」が提供されます。
2.  **`NameToCertificate`へのフォールバック**: `GetCertificate`コールバックが`nil`の証明書と`nil`のエラーを返した場合（つまり、コールバックが証明書を提供しなかった場合）、従来の`NameToCertificate`マップによる検索ロジックが実行されます。これは、SNIで指定されたサーバー名に基づいて、マップから証明書を検索する処理です。ワイルドカード証明書（例: `*.example.com`）のマッチングもサポートされています。
3.  **デフォルト証明書へのフォールバック**: `NameToCertificate`マップにもマッチする証明書が見つからない場合、または`NameToCertificate`が設定されていない場合、`c.Certificates`スライスの最初の要素（通常はデフォルトの証明書）が使用されます。
4.  **エラー伝播**: この関数は`error`を返すようになったため、証明書選択プロセス中に発生したエラー（例: `GetCertificate`コールバック内で発生したエラー）を呼び出し元に適切に伝播できるようになりました。

### `handshake_server.go`における呼び出し

サーバーハンドシェイクの過程で、クライアントがSNI情報を送信した場合、`handshake_server.go`内の関連するロジックが、新しい`ClientHelloInfo`構造体を構築し、それを`config.getCertificate`メソッドに渡すように変更されました。これにより、サーバーはクライアントのSNI要求に基づいて、動的に証明書を選択し、ハンドシェイクを続行できるようになります。`getCertificate`がエラーを返した場合、サーバーはTLSアラートを送信して接続を終了し、クライアントに問題があったことを通知します。

これらの変更は、Goの`crypto/tls`パッケージが、現代の複雑な証明書管理要件に対応するための重要な一歩であり、より柔軟で堅牢なTLSサーバーの実装を可能にしました。

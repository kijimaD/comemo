## 元コミット内容

`go/parser: report error for var/const decls with missing init exprs`

このコミットは、`var`または`const`宣言において初期化式が欠落している場合にエラーを報告するようにGoパーサーを修正します。
Issue #9639を修正します。

## 変更の背景

Go言語では、変数や定数を宣言する際に、型を明示するか、初期化式を提供することで型推論に任せるかのいずれかの方法を取ります。しかし、特定の状況下で、初期化式が欠落しているにもかかわらず、パーサーがそれを適切にエラーとして扱わないケースが存在していました。

具体的には、Goの仕様では、`var`宣言において型が指定されていない場合、初期化式が必須となります。同様に、`const`宣言においても、値が指定されていない場合はエラーとなるべきです（特に`iota`を使用しない場合や、型が明示されている場合）。

このコミットは、Go issue #9639で報告された問題に対応しています。この問題は、`var x, y, z;` のような変数宣言や、`const x;` のような定数宣言が、初期化式や型が欠落しているにもかかわらず、パーサーによってエラーとして検出されないというものでした。このような構文はGoの仕様に違反しており、コンパイルエラーとなるべきです。パーサーが早期にこれらの構文エラーを検出することで、開発者はより迅速に問題を特定し、修正できるようになります。

## 前提知識の解説

*   **Go言語のパーサー (`go/parser`)**: Go言語のソースコードを解析し、抽象構文木（AST: Abstract Syntax Tree）を生成する標準ライブラリパッケージです。コンパイラのフロントエンドの一部として機能し、コードの構文がGo言語の仕様に準拠しているかを検証します。
*   **`var` 宣言**: Go言語で変数を宣言するためのキーワードです。
    *   `var name type = expression` (型と初期化式を明示)
    *   `var name = expression` (初期化式から型を推論)
    *   `var name type` (ゼロ値で初期化)
    *   型が指定されず、初期化式も欠落している場合は構文エラーとなります。
*   **`const` 宣言**: Go言語で定数を宣言するためのキーワードです。
    *   `const name = expression` (初期化式を明示)
    *   `const name type = expression` (型と初期化式を明示)
    *   定数はコンパイル時に値が決定されるため、初期化式は必須です。ただし、定数ブロック内で`iota`を使用する場合、初期化式を省略できる場合があります。
*   **抽象構文木 (AST)**: ソースコードの構文構造を木構造で表現したものです。パーサーはソースコードを読み込み、このASTを構築します。コンパイラの後の段階（型チェック、コード生成など）で利用されます。
*   **`token.VAR` / `token.CONST`**: Go言語の字句解析器（lexer）が生成するトークンの一種で、それぞれ`var`キーワードと`const`キーワードを表します。
*   **`ast.Expr`**: 抽象構文木における式を表すインターフェースです。初期化式は`ast.Expr`として表現されます。
*   **`p.error(pos, msg)`**: パーサーが構文エラーを検出した際に呼び出すメソッドで、指定された位置（`pos`）にエラーメッセージ（`msg`）を報告します。

## 技術的詳細

このコミットの技術的な核心は、`go/parser`パッケージ内の`parseValueSpec`関数にエラーチェックロジックを追加することです。`parseValueSpec`関数は、`var`や`const`といった値の宣言（`ValueSpec`）を解析する役割を担っています。

変更前は、この関数は識別子のリスト（`idents`）、型（`typ`）、および値のリスト（`values`）を解析していましたが、`values`が`nil`（初期化式がない）かつ`typ`も`nil`（型が指定されていない）というGoの仕様に違反するケースを明示的にエラーとして捕捉していませんでした。

コミットによって追加されたロジックは以下の通りです。

1.  **現在の位置の保存**: `pos := p.pos` により、現在のトークンの開始位置を`pos`変数に保存します。これはエラーメッセージの正確な位置を報告するために重要です。
2.  **キーワードによる分岐**: `switch keyword` 文を用いて、現在の宣言が`var`なのか`const`なのかによって異なるエラーチェックを行います。
    *   **`token.VAR` の場合**:
        *   `if typ == nil && values == nil`: もし型が指定されておらず（`typ == nil`）、かつ初期化式も提供されていない場合（`values == nil`）、これはGoの仕様に違反します。
        *   `p.error(pos, "missing variable type or initialization")`: この条件が真の場合、「missing variable type or initialization」（変数型または初期化が欠落しています）というエラーメッセージを報告します。
    *   **`token.CONST` の場合**:
        *   `if values == nil && (iota == 0 || typ != nil)`: もし初期化式が提供されておらず（`values == nil`）、かつ`iota`が使用されていない（`iota == 0`）か、または型が明示されている（`typ != nil`）場合、これはGoの仕様に違反します。`iota`が使用されている場合は、初期化式がなくても有効な定数宣言となる可能性があるため、この条件で除外されます。
        *   `p.error(pos, "missing constant value")`: この条件が真の場合、「missing constant value」（定数値が欠落しています）というエラーメッセージを報告します。

これらのチェックを追加することで、パーサーはGoの仕様に準拠しない`var`や`const`宣言を早期に検出し、より適切なエラーメッセージを生成できるようになります。これにより、コンパイラの後の段階で発生する可能性のある、より曖昧なエラーを防ぎ、開発体験を向上させます。

また、`src/go/parser/short_test.go` には、この変更によって正しくエラーが報告されることを確認するための新しいテストケースが追加されています。これにより、修正が意図通りに機能し、将来のリグレッションを防ぐことができます。

## コアとなるコードの解説

### `src/go/parser/parser.go` の変更

`parseValueSpec`関数は、`var`や`const`宣言を解析するGoパーサーの重要な部分です。

1.  **`pos := p.pos`**:
    *   この行は、現在のパーサーの位置（`p.pos`）を`pos`変数に保存します。`p.pos`は、現在処理しているトークンの開始位置を示します。
    *   この位置情報は、後で`p.error`を呼び出す際に、エラーが発生した正確なソースコード上の位置を報告するために使用されます。これにより、開発者はエラーメッセージを見て、コードのどの部分に問題があるのかを正確に把握できます。

2.  **新しいエラーチェックロジック**:
    ```go
    switch keyword {
    case token.VAR:
        if typ == nil && values == nil {
            p.error(pos, "missing variable type or initialization")
        }
    case token.CONST:
        if values == nil && (iota == 0 || typ != nil) {
            p.error(pos, "missing constant value")
        }
    }
    ```
    *   この`switch`文は、現在解析している宣言が`var`（`token.VAR`）なのか`const`（`token.CONST`）なのかによって、異なるエラーチェックを実行します。
    *   **`token.VAR` のケース**:
        *   `typ == nil`: 宣言で型が明示されていないことを意味します（例: `var x`）。
        *   `values == nil`: 宣言で初期化式が提供されていないことを意味します（例: `var x`）。
        *   Goの仕様では、`var`宣言で型が指定されていない場合、初期化式が必須です。したがって、`typ`も`values`も`nil`である場合は構文エラーです。
        *   `p.error(pos, "missing variable type or initialization")` が呼び出され、適切なエラーメッセージが報告されます。
    *   **`token.CONST` のケース**:
        *   `values == nil`: 宣言で初期化式が提供されていないことを意味します（例: `const x`）。
        *   `iota == 0`: `iota`は定数ブロック内で連続する値を生成するために使用される特別な定数です。`iota == 0`は、現在の定数宣言が`iota`の最初の使用ではないか、または`iota`が全く使用されていないことを示唆します。`iota`が使用されている場合、初期化式がなくても有効な定数宣言となることがあります（例: `const (A = iota; B)` の `B`）。
        *   `typ != nil`: 定数宣言で型が明示されていることを意味します（例: `const x int`）。
        *   Goの仕様では、定数には値が必須です。`values == nil` かつ (`iota == 0` または `typ != nil`) の場合、これは初期化式が欠落している構文エラーです。`iota`が使用されておらず、かつ初期化式がない場合、または型が明示されているにもかかわらず初期化式がない場合はエラーとなります。
        *   `p.error(pos, "missing constant value")` が呼び出され、適切なエラーメッセージが報告されます。

これらの変更により、Goパーサーは、Go言語の仕様に準拠しない`var`および`const`宣言をより厳密にチェックし、開発者に対してより明確で役立つエラーメッセージを提供するようになります。

### `src/go/parser/short_test.go` の変更

このファイルは、Goパーサーの短縮テストケースを定義しています。変更は、新しい有効なケースと無効なケースを追加することで、パーサーの修正が正しく機能することを検証します。

1.  **`valids` スライスへの追加**:
    ```go
    `package p; const (x = 0; y; z)`, // issue 9639
    ```
    *   このテストケースは、`const`ブロック内で`iota`が暗黙的に使用されている場合に、初期化式が省略されても有効な構文であることを確認します。`y`と`z`は`x`の初期化式`0`と`iota`の規則に従って値が割り当てられるため、これは有効なGoコードです。これはIssue 9639の文脈で、`iota`が絡む場合の`const`宣言の挙動をテストしています。

2.  **`invalids` スライスへの追加**:
    ```go
    `package p; var x /* ERROR "missing variable type or initialization" */ , y, z;`, // issue 9639
    `package p; const x /* ERROR "missing constant value" */ ;`,                      // issue 9639
    `package p; const x /* ERROR "missing constant value" */ int;`,                   // issue 9639
    `package p; const (x = 0; y; z /* ERROR "missing constant value" */ int);`,       // issue 9639
    ```
    *   これらのテストケースは、新しいエラーチェックロジックが期待通りに機能し、Goの仕様に違反する`var`および`const`宣言に対して適切なエラーメッセージを報告することを確認します。
    *   `var x , y, z;`: 型も初期化式も欠落している`var`宣言。
    *   `const x;`: 初期化式が欠落している`const`宣言。
    *   `const x int;`: 型が明示されているが初期化式が欠落している`const`宣言。
    *   `const (x = 0; y; z int);`: `const`ブロック内で、`z`が型指定されているにもかかわらず初期化式が欠落しているケース。`y`は`iota`によって`1`になるが、`z`は型が指定されているため、`iota`の規則が適用されず、初期化式が必要となる。
    *   各行のコメントにある`/* ERROR "..." */`は、パーサーがその位置で指定されたエラーメッセージを生成することを期待していることを示します。

これらのテストケースは、パーサーの修正が正しく機能し、Go言語の構文規則をより厳密に適用していることを保証します。

        *   `if typ == nil && values == nil`: もし型が指定されておらず（`typ == nil`）、かつ初期化式も提供されていない場合（`values == nil`）、これはGoの仕様に違反します。
        *   `p.error(pos, "missing variable type or initialization")`: この条件が真の場合、「missing variable type or initialization」（変数型または初期化が欠落しています）というエラーメッセージを報告します。
    *   **`token.CONST` の場合**:
        *   `if values == nil && (iota == 0 || typ != nil)`: もし初期化式が提供されておらず（`values == nil`）、かつ`iota`が使用されていない（`iota == 0`）か、または型が明示されている（`typ != nil`）場合、これはGoの仕様に違反します。`iota`が使用されている場合は、初期化式がなくても有効な定数宣言となる可能性があるため、この条件で除外されます。
        *   `p.error(pos, "missing constant value")`: この条件が真の場合、「missing constant value」（定数値が欠落しています）というエラーメッセージを報告します。

これらのチェックを追加することで、パーサーはGoの仕様に準拠しない`var`や`const`宣言を早期に検出し、より適切なエラーメッセージを生成できるようになります。これにより、コンパイラの後の段階で発生する可能性のある、より曖昧なエラーを防ぎ、開発体験を向上させます。

また、`src/go/parser/short_test.go` には、この変更によって正しくエラーが報告されることを確認するための新しいテストケースが追加されています。これにより、修正が意図通りに機能し、将来のリグレッションを防ぐことができます。

## コアとなるコードの解説

### `src/go/parser/parser.go` の変更

`parseValueSpec`関数は、`var`や`const`宣言を解析するGoパーサーの重要な部分です。

1.  **`pos := p.pos`**:
    *   この行は、現在のパーサーの位置（`p.pos`）を`pos`変数に保存します。`p.pos`は、現在処理しているトークンの開始位置を示します。
    *   この位置情報は、後で`p.error`を呼び出す際に、エラーが発生した正確なソースコード上の位置を報告するために使用されます。これにより、開発者はエラーメッセージを見て、コードのどの部分に問題があるのかを正確に把握できます。

2.  **新しいエラーチェックロジック**:
    ```go
    switch keyword {
    case token.VAR:
        if typ == nil && values == nil {
            p.error(pos, "missing variable type or initialization")
        }
    case token.CONST:
        if values == nil && (iota == 0 || typ != nil) {
            p.error(pos, "missing constant value")
        }
    }
    ```
    *   この`switch`文は、現在解析している宣言が`var`（`token.VAR`）なのか`const`（`token.CONST`）なのかによって、異なるエラーチェックを実行します。
    *   **`token.VAR` のケース**:
        *   `typ == nil`: 宣言で型が明示されていないことを意味します（例: `var x`）。
        *   `values == nil`: 宣言で初期化式が提供されていないことを意味します（例: `var x`）。
        *   Goの仕様では、`var`宣言で型が指定されていない場合、初期化式が必須です。したがって、`typ`も`values`も`nil`である場合は構文エラーです。
        *   `p.error(pos, "missing variable type or initialization")` が呼び出され、適切なエラーメッセージが報告されます。
    *   **`token.CONST` のケース**:
        *   `values == nil`: 宣言で初期化式が提供されていないことを意味します（例: `const x`）。
        *   `iota == 0`: `iota`は定数ブロック内で連続する値を生成するために使用される特別な定数です。`iota == 0`は、現在の定数宣言が`iota`の最初の使用ではないか、または`iota`が全く使用されていないことを示唆します。`iota`が使用されている場合、初期化式がなくても有効な定数宣言となることがあります（例: `const (A = iota; B)` の `B`）。
        *   `typ != nil`: 定数宣言で型が明示されていることを意味します（例: `const x int`）。
        *   Goの仕様では、定数には値が必須です。`values == nil` かつ (`iota == 0` または `typ != nil`) の場合、これは初期化式が欠落している構文エラーです。`iota`が使用されておらず、かつ初期化式がない場合、または型が明示されているにもかかわらず初期化式がない場合はエラーとなります。
        *   `p.error(pos, "missing constant value")` が呼び出され、適切なエラーメッセージが報告されます。

これらの変更により、Goパーサーは、Go言語の仕様に準拠しない`var`および`const`宣言をより厳密にチェックし、開発者に対してより明確で役立つエラーメッセージを提供するようになります。

### `src/go/parser/short_test.go` の変更

このファイルは、Goパーサーの短縮テストケースを定義しています。変更は、新しい有効なケースと無効なケースを追加することで、パーサーの修正が正しく機能することを検証します。

1.  **`valids` スライスへの追加**:
    ```go
    `package p; const (x = 0; y; z)`, // issue 9639
    ```
    *   このテストケースは、`const`ブロック内で`iota`が暗黙的に使用されている場合に、初期化式が省略されても有効な構文であることを確認します。`y`と`z`は`x`の初期化式`0`と`iota`の規則に従って値が割り当てられるため、これは有効なGoコードです。これはIssue 9639の文脈で、`iota`が絡む場合の`const`宣言の挙動をテストしています。

2.  **`invalids` スライスへの追加**:
    ```go
    `package p; var x /* ERROR "missing variable type or initialization" */ , y, z;`, // issue 9639
    `package p; const x /* ERROR "missing constant value" */ ;`,                      // issue 9639
    `package p; const x /* ERROR "missing constant value" */ int;`,                   // issue 9639
    `package p; const (x = 0; y; z /* ERROR "missing constant value" */ int);`,       // issue 9639
    ```
    *   これらのテストケースは、新しいエラーチェックロジックが期待通りに機能し、Goの仕様に違反する`var`および`const`宣言に対して適切なエラーメッセージを報告することを確認します。
    *   `var x , y, z;`: 型も初期化式も欠落している`var`宣言。
    *   `const x;`: 初期化式が欠落している`const`宣言。
    *   `const x int;`: 型が明示されているが初期化式が欠落している`const`宣言。
    *   `const (x = 0; y; z /* ERROR "missing constant value" */ int);`: `const`ブロック内で、`z`が型指定されているにもかかわらず初期化式が欠落しているケース。`y`は`iota`によって`1`になるが、`z`は型が指定されているため、`iota`の規則が適用されず、初期化式が必要となる。
    *   各行のコメントにある`/* ERROR "..." */`は、パーサーがその位置で指定されたエラーメッセージを生成することを期待していることを示します。

これらのテストケースは、パーサーの修正が正しく機能し、Go言語の構文規則をより厳密に適用していることを保証します。

# [インデックス 22420] ファイルの概要

`src/cmd/internal/gc` は、Go言語の公式コンパイラである `gc` の内部パッケージであり、Goソースコードを機械語に変換するプロセスの中核を担っています。このディレクトリには、字句解析、構文解析、型チェック、コード生成、最適化など、コンパイラの様々なフェーズに関連するファイルが含まれています。

## コミット

このコミットは、Goコンパイラ（`gc`）の内部でシンボル名やファイル名を構築するために使用されていたグローバル変数 `namebuf` を削除し、その使用箇所を `fmt.Sprintf` と `Lookup` 関数の組み合わせ、または新しく導入されたヘルパー関数 `Lookupf` に置き換えるものです。これにより、不要なメモリ割り当てとガベージコレクションのライトバリアを削減し、コンパイラのバイナリサイズを縮小することを目的としています。

## 変更の背景

この変更の背景には、Goコンパイラ（`gc`）がC言語で書かれていた時代からGo言語に移植された経緯が関係しています。

C言語版の`gc`では、`namebuf`はグローバルな`char`配列（バッファ）として定義されており、シンボル名やファイル名などの一時的な文字列を構築するために再利用されていました。`char`配列は固定サイズで、文字列をその場で書き換えることができたため、メモリの動的な割り当てを頻繁に行う必要がなく、効率的でした。

しかし、`gc`がGo言語に移植された際、`namebuf`はGoのグローバルな`string`変数として定義されました。Goの`string`型はイミュータブル（不変）であり、一度作成された文字列の内容を変更することはできません。そのため、`namebuf`に新しい文字列を代入するたびに、`fmt.Sprintf`などの関数によって新しい文字列オブジェクトがヒープ上に動的に割り当てられ、その新しいオブジェクトへの参照が`namebuf`に格納されることになります。

この動的なメモリ割り当てと参照の更新は、Goのガベージコレクタ（GC）にとって問題となります。特に、参照が更新される際には「ライトバリア」と呼ばれるGCのメカニズムが動作します。ライトバリアは、GCがオブジェクトグラフを正確に追跡するために、ポインタの書き換えを監視するものです。`namebuf`が頻繁に更新されることで、不要なライトバリアが多発し、コンパイラのパフォーマンスに悪影響を与えていました。

このコミットは、もはやその目的を果たさず、むしろオーバーヘッドとなっていたグローバルな`namebuf`変数を削除し、よりGoらしい、効率的な文字列操作パターンに移行することを目的としています。

## 前提知識の解説

### Goコンパイラ (`gc`) の役割

`gc`は、Go言語の公式ツールチェインに含まれる主要なコンパイラです。Goのソースコード（`.go`ファイル）を、実行可能なバイナリ（機械語）に変換する役割を担っています。`src/cmd/internal/gc`ディレクトリには、このコンパイラのフロントエンド（字句解析、構文解析、型チェック、AST構築）からバックエンド（中間表現の最適化、コード生成）に至るまでの中核的なロジックが実装されています。

### `namebuf` のC言語での役割とGo言語での変化

*   **C言語時代**: `namebuf`は、C言語で書かれた`gc`において、シンボル名やファイルパスなどの一時的な文字列を生成するためのグローバルな`char`配列でした。このバッファは再利用可能であり、文字列の連結やフォーマットを直接バッファ内で行うことで、動的なメモリ割り当てを最小限に抑え、効率的な文字列操作を実現していました。
*   **Go言語への移植後**: `gc`がGo言語に移植された際、`namebuf`はGoの`string`型として定義されました。Goの`string`は不変であるため、`namebuf`に新しい文字列を代入するたびに、`fmt.Sprintf`などによって新しい文字列オブジェクトがヒープに割り当てられ、そのオブジェクトへの参照が`namebuf`に格納されることになります。これにより、C言語時代の「再利用可能なバッファ」という利点は失われ、かえって頻繁なメモリ割り当てとガベージコレクションのオーバーヘッドを引き起こす原因となっていました。

### Goのガベージコレクションとライトバリア

Go言語は自動メモリ管理（ガベージコレクション、GC）を採用しています。GoのGCは、並行マーク＆スイープ方式を基本としており、プログラムの実行と並行して不要なメモリを回収します。

*   **ライトバリア (Write Barrier)**: GCが動作している間、プログラムがヒープ上のポインタを書き換える（新しいオブジェクトへの参照を格納する）際に、GCがその変更を検知し、オブジェクトグラフの整合性を保つためのメカニズムです。ライトバリアは、GCが正確に到達可能なオブジェクトを特定し、誤って使用中のメモリを回収してしまうことを防ぎます。しかし、ライトバリアの実行にはわずかながらオーバーヘッドが伴うため、頻繁にポインタが書き換えられる状況では、そのオーバーヘッドが蓄積され、プログラム全体のパフォーマンスに影響を与える可能性があります。`namebuf`への頻繁な代入は、このライトバリアの発生回数を増加させていました。

### `fmt.Sprintf` と文字列生成のコスト

`fmt.Sprintf`は、Go言語でフォーマットされた文字列を生成するための便利な関数です。しかし、この関数は常に新しい文字列を生成し、その文字列をヒープに割り当てます。大量の文字列を頻繁に生成する場合、このメモリ割り当てとコピーのコストが無視できないパフォーマンスボトルネックとなることがあります。

### `Lookup` 関数の役割 (シンボルテーブル関連)

Goコンパイラにおける`Lookup`関数（`src/cmd/internal/gc/subr.go`に定義）は、コンパイラのシンボルテーブルから特定の名前（文字列）に対応するシンボル（`*Sym`型）を検索または登録するために使用されます。シンボルは、変数、関数、型などのプログラム要素を一意に識別するための内部表現です。コンパイラは、ソースコード中の識別子を解析する際に、この`Lookup`関数を頻繁に利用してシンボル情報を管理します。

### `toolstash -cmp` と `size` コマンド

*   **`toolstash`**: Goのツールチェイン（コンパイラ、リンカなど）のビルド結果を一時的に保存し、管理するためのユーティリティです。
*   **`toolstash -cmp`**: `toolstash`の`-cmp`オプションは、現在のビルドと`toolstash`に保存された以前のビルドのバイナリサイズを比較するために使用されます。これにより、コンパイラやその他のツールのバイナリサイズが変更されたかどうかを簡単に確認できます。
*   **`size`コマンド**: Unix/Linuxシステムで利用可能なコマンドで、実行可能ファイルやオブジェクトファイルのセクション（`text`、`data`、`bss`など）のサイズを表示します。
    *   `text`セクション: 実行可能な機械語コードが含まれる部分。
    *   `data`セクション: 初期化されたグローバル変数や静的変数が含まれる部分。
    *   `bss`セクション: 初期化されていないグローバル変数や静的変数が含まれる部分。
    このコミットでは、`6g`（Goコンパイラの64ビット版）の`text`セクションが約15KB縮小されたことが報告されており、これはコンパイラのコードサイズが削減されたことを示しています。

## 技術的詳細

このコミットの技術的な核心は、Goコンパイラ内部の文字列処理の最適化と、それに伴うメモリ使用量およびバイナリサイズの削減です。

1.  **`namebuf` グローバル変数の削除**:
    `src/cmd/internal/gc/go.go` から `var namebuf string` の宣言が削除されました。これにより、グローバルな`string`変数として存在していた`namebuf`が完全に廃止され、それに伴う不要なヒープ割り当てとライトバリアの発生がなくなりました。

2.  **`Lookupf` ヘルパー関数の導入**:
    `src/cmd/internal/gc/subr.go` に新しい関数 `Lookupf` が追加されました。
    ```go
    func Lookupf(format string, a ...interface{}) *Sym {
        return Lookup(fmt.Sprintf(format, a...))
    }
    ```
    この関数は、`fmt.Sprintf` で文字列をフォーマットし、その結果を `Lookup` 関数に渡すという、これまで多くの場所で行われていた共通のパターンを抽象化します。これにより、コードの重複が減り、可読性が向上しました。また、将来的に`Lookupf`の内部実装を最適化することで、文字列生成の効率をさらに高める可能性も生まれます。

3.  **`namebuf` 使用箇所の置き換え**:
    コンパイラ内の`namebuf`が使用されていた全ての箇所（`closure.go`, `dcl.go`, `gen.go`, `init.go`, `inl.go`, `lex.go`, `obj.go`, `pgen.go`, `sinit.go`, `walk.go`など、計11ファイル）が、直接`fmt.Sprintf`の結果を`Lookup`に渡すか、新しく導入された`Lookupf`を使用するように変更されました。
    例えば、`closure.go`では以下のように変更されています。
    ```diff
    --- a/src/cmd/internal/gc/closure.go
    +++ b/src/cmd/internal/gc/closure.go
    @@ -174,8 +174,7 @@ func closurename(n *Node) *Sym {
      	} else {
      		Fatal("closurename called for %v", Nconv(n, obj.FmtShort))\n \t}\n -	namebuf = fmt.Sprintf("%s.%s%d", outer, prefix, gen)\n -	n.Sym = Lookup(namebuf)\n +	n.Sym = Lookupf("%s.%s%d", outer, prefix, gen)\n      	return n.Sym\n      }\n    ```
    これにより、`namebuf`という中間変数への代入が不要になり、文字列生成から`Lookup`への直接的なフローが確立されました。

4.  **`findpkg` 関数のシグネチャ変更とローカル変数化**:
    `src/cmd/internal/gc/lex.go` の `findpkg` 関数は、`namebuf`の削除に伴い、そのシグネチャが変更されました。
    ```diff
    --- a/src/cmd/internal/gc/lex.go
    +++ b/src/cmd/internal/gc/lex.go
    @@ -559,25 +559,24 @@ func islocalname(name string) bool {\n      	strings.HasPrefix(name, "../") || name == ".."\n      }\n      \n    -func findpkg(name string) bool {\n    +func findpkg(name string) (file string, ok bool) {\n      	if islocalname(name) {\n      		if safemode != 0 || nolocalimports != 0 {\n    -		return false\n    +		return "", false\n      		}\n      \n      		// try .a before .6.  important for building libraries:\n      		// if there is an array.6 in the array.a library,\n      		// want to find all of array.a, not just array.6.\n    -		namebuf = fmt.Sprintf("%s.a", name)\n    -\n    -		if obj.Access(namebuf, 0) >= 0 {\n    -			return true\n    +		file = fmt.Sprintf("%s.a", name)\n    +		if obj.Access(file, 0) >= 0 {\n    +			return file, true\n      		}\n    -		namebuf = fmt.Sprintf("%s.%c", name, Thearch.Thechar)\n    -		if obj.Access(namebuf, 0) >= 0 {\n    -			return true\n    +		file = fmt.Sprintf("%s.%c", name, Thearch.Thechar)\n    +		if obj.Access(file, 0) >= 0 {\n    +			return file, true\n      		}\n    -		return false\n    +		return "", false\n      	}\n    ```

5.  **バイナリサイズの削減**:
    コミットメッセージに記載されているように、この変更により`6g`（Goコンパイラの64ビット版）の`text`セクションが約15KB縮小されました。これは、グローバル変数の削除、不要な文字列操作コードの削減、およびそれに伴うコンパイラバイナリのフットプリントの最適化によるものです。コンパイラのサイズが小さくなることは、配布サイズやメモリ使用量の観点からメリットがあります。

## コアとなるコードの解説

### `namebuf` グローバル変数の削除

`src/cmd/internal/gc/go.go` から `namebuf` が削除されたことは、コンパイラがC言語からGo言語に移行する過程で残っていた「遺物」が取り除かれたことを意味します。Goの`string`は不変であるため、グローバルな`string`変数に頻繁に新しい文字列を代入することは、メモリの再割り当てとライトバリアの頻繁な発生を招き、パフォーマンス上のボトルネックとなっていました。この削除により、これらのオーバーヘッドが根本的に解消されます。

### `Lookupf` ヘルパー関数の導入

`src/cmd/internal/gc/subr.go` に追加された `Lookupf` 関数は、`Lookup(fmt.Sprintf(format, a...))` という頻繁に現れるパターンを簡潔に記述するためのシンタックスシュガーです。これにより、コンパイラコードの可読性が向上し、冗長な記述が削減されます。また、将来的に`Lookupf`の内部で文字列プールやより効率的な文字列生成メカニズムを導入するなどの最適化を行う際の拡張ポイントとしても機能します。

### `namebuf` の使用箇所の置き換え

`closure.go` の例に見られるように、`namebuf` を介して文字列を構築し、それを `Lookup` に渡すという二段階の処理が、`Lookupf` を直接呼び出す一段階の処理に簡略化されました。これにより、中間変数 `namebuf` への代入が不要になり、コードがより直接的で効率的になります。

`lex.go` の `findpkg` 関数の変更は、`namebuf` の削除が関数のインターフェース設計にも影響を与えた良い例です。以前は`namebuf`というグローバル変数を通じて結果を「副作用」として渡していましたが、変更後は関数が直接結果（ファイルパスと成功フラグ）を返すようになり、関数の振る舞いがより明確で予測可能になりました。これは、グローバル変数の使用を避け、関数の純粋性を高めるというGoの設計思想にも合致しています。

これらの変更は、個々の箇所では小さいかもしれませんが、コンパイラ全体で適用されることで、メモリ使用量の削減、ガベージコレクションの効率化、そして最終的にはコンパイラのビルド時間の短縮やバイナリサイズの縮小といった形で、顕著なパフォーマンス改善に貢献しています。

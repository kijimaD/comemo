# [インデックス 20300] ファイルの概要

このコミットは、Goランタイムにおける低レベルのロックメカニズムをC言語からGo言語に移行するものです。具体的には、`lock_futex.c`と`lock_sema.c`という2つのC言語ファイルが削除され、それぞれ`lock_futex.go`と`lock_sema.go`というGo言語のファイルに置き換えられています。これは、GoランタイムのGo言語化を進める上で重要な一歩であり、Go言語の自己ホスティング能力を高めることを目的としています。

## 元コミット内容

Goランタイムのロック関連のC言語コード（`lock_futex.c`と`lock_sema.c`）をGo言語に変換しました。

## 変更の背景

Go言語のランタイムは、初期の頃からパフォーマンスが要求される部分やOSとのインタフェース部分にC言語で書かれたコードを含んでいました。しかし、Go言語の進化とともに、ランタイムの大部分をGo言語自身で記述することが可能になり、またその方が望ましいという方針が強まってきました。

この変更の主な背景には、以下の点が挙げられます。

1.  **自己ホスティングの推進**: Go言語のコンパイラやランタイムをGo言語自身で記述することで、Go言語のエコシステム全体の独立性と保守性が向上します。C言語の依存を減らすことで、ビルドプロセスが簡素化され、異なるプラットフォームへの移植性も高まります。
2.  **Go言語の機能活用**: C言語で記述された低レベルのコードは、Go言語の持つ並行処理のプリミティブや型安全性といった恩恵を直接受けることができませんでした。Go言語に変換することで、よりGoらしいイディオムでコードを記述できるようになり、可読性、保守性、そして将来的な最適化の可能性が向上します。
3.  **デバッグとプロファイリングの改善**: Go言語で書かれたコードは、Goのツールチェイン（デバッガ、プロファイラなど）によってより詳細に分析できます。C言語のコードが混在していると、これらのツールの適用範囲が限定されることがありました。
4.  **統一された開発体験**: ランタイム開発者がC言語とGo言語の両方の知識を深く持つ必要がなくなるため、開発の障壁が低減し、より多くの開発者がランタイム開発に貢献しやすくなります。

このコミットは、特にGoランタイムの重要な構成要素であるミューテックス（`lock`および`unlock`関数）と、一回限りの通知メカニズム（`note`）の実装をGo言語に移行するものです。これらの機能は、Goルーチンのスケジューリング、ガベージコレクション、システムコールなど、ランタイムの根幹をなす部分で利用されており、そのGo言語化はランタイムの安定性と効率性に大きな影響を与えます。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が不可欠です。

### 1. Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するシステムです。これには、Goルーチンのスケジューリング、メモリ管理（ガベージコレクションを含む）、チャネル通信、システムコールインターフェース、低レベルの同期プリミティブなどが含まれます。Goプログラムは、OS上で直接実行されるのではなく、Goランタイム上で実行されます。

### 2. ミューテックス (Mutex)

ミューテックス（Mutual Exclusionの略）は、並行プログラミングにおいて共有リソースへのアクセスを制御するための同期プリミティブです。複数のGoルーチンが同時に同じデータにアクセスしようとすると、データ競合が発生し、プログラムの動作が予測不能になる可能性があります。ミューテックスは、一度に一つのGoルーチンだけが共有リソースにアクセスできるようにすることで、この問題を解決します。Go言語では、`sync.Mutex`として提供されていますが、このコミットで変更されているのは、その基盤となるランタイムレベルのミューテックス実装です。

### 3. フューテックス (Futex - Fast Userspace Mutex)

フューテックスは、Linuxカーネルが提供する高速なユーザー空間ミューテックスのメカニズムです。これは、競合が少ない場合にはカーネルへのシステムコールを回避し、ユーザー空間でロックの取得・解放を完結させることで、高いパフォーマンスを実現します。競合が発生した場合にのみ、カーネルに制御を渡し、Goルーチンをスリープさせたり、ウェイクアップさせたりします。
`lock_futex.c`および`lock_futex.go`は、Linux、DragonFly BSD、FreeBSDなどのOSでフューテックスを利用したロック実装を提供します。

### 4. セマフォ (Semaphore)

セマフォは、フューテックスと同様に同期プリミティブの一つですが、より汎用的な概念です。リソースの利用可能数をカウントし、その数がゼロになると待機中のプロセスをブロックします。このコミットでは、フューテックスが利用できないOS（Darwin (macOS), NaCl, NetBSD, OpenBSD, Plan 9, Solaris, Windowsなど）向けに、OSが提供するセマフォや同等のメカニズムを利用したロック実装が`lock_sema.c`および`lock_sema.go`で提供されています。

### 5. `Note` (一回限りの通知メカニズム)

Goランタイム内部で利用される、非常に軽量な一回限りの通知メカニズムです。特定のイベントが発生した際に、待機しているGoルーチンを一度だけウェイクアップするために使用されます。例えば、Goルーチンの終了通知や、システムコールからの復帰待ちなどに利用されます。

### 6. アトミック操作 (Atomic Operations)

アトミック操作は、複数のCPUコアやGoルーチンから同時にアクセスされても、その操作全体が不可分（atomic）であることを保証する操作です。これにより、データ競合を防ぎ、正確な並行処理を実現します。`xchg` (exchange) や `cas` (compare-and-swap) といった操作がこれに該当し、ロックの実装において中心的な役割を果たします。

### 7. `g` (Goroutine) と `m` (Machine)

Goランタイムの内部では、Goルーチンは`g`構造体で表現され、OSスレッドは`m`構造体で表現されます。`g`は`m`上で実行され、`m`はOSによってスケジューリングされます。`g->m->locks`のような記述は、現在のGoルーチンが実行されているOSスレッドが保持しているロックの数を追跡するためのものです。

### 8. `unsafe.Pointer` と `uintptr`

Go言語の`unsafe`パッケージは、型安全性をバイパスして低レベルのメモリ操作を可能にします。`unsafe.Pointer`は任意の型のポインタを保持でき、`uintptr`はポインタを整数として扱うことができます。このコミットでは、C言語のポインタ操作をGo言語で再現するためにこれらの型が多用されています。特に、`Mutex`や`Note`の`key`フィールドは`uintptr`型で定義されており、これを`uint32`や`*m`（OSスレッドの構造体へのポインタ）として解釈するために`unsafe.Pointer`が使われています。

## 技術的詳細

このコミットの核心は、Goランタイムのロックプリミティブの実装をC言語からGo言語へ移植した点にあります。これは単なる言語の置き換え以上の意味を持ちます。

### C言語からGo言語への変換の課題と解決策

C言語で書かれた元のコードは、ポインタ演算、直接的なメモリ操作、そしてOS固有のシステムコールへの直接的なバインディングを多用していました。Go言語はより高レベルな言語であり、通常はこれらの低レベルな操作を抽象化します。この変換では、以下の点が特に重要でした。

1.  **ポインタ演算の再現**: C言語のポインタ演算は、Go言語では`unsafe.Pointer`と`uintptr`を組み合わせて再現されます。例えば、`l->key`のようなC言語の構造体メンバへのポインタアクセスは、Go言語では`key32(&l.key)`のように`unsafe.Pointer`を介して`*uint32`にキャストすることで実現されています。
2.  **アトミック操作のGo言語化**: `xchg` (exchange) や `cas` (compare-and-swap) といったアトミック操作は、Go言語の`sync/atomic`パッケージに相当するランタイム内部のアトミック関数（例: `runtime.xchg`, `runtime.cas`, `runtime.atomicload`, `runtime.atomicloaduintptr`）に置き換えられました。これらの関数は、各アーキテクチャのアセンブリコード（`asm_*.s`ファイル）で実装されており、Go言語から呼び出せるように`stubs.go`で宣言されています。
3.  **OS固有のシステムコール**: `futexsleep`, `futexwakeup`, `semacreate`, `semasleep`, `semawakeup`といったOS固有の同期プリミティブへの呼び出しは、Go言語の関数として宣言され、その実装は引き続きC言語またはアセンブリで提供されるか、Go言語でOS固有のシステムコールをラップする形になります。このコミットでは、これらの関数はGo言語のコードから呼び出されるようになりましたが、その具体的な実装はOS固有のファイル（例: `os_linux.go`など）やアセンブリファイルに委ねられています。
4.  **`g`と`m`のコンテキスト**: C言語のコードでは`g`や`g->m`といったグローバル変数や構造体メンバへの直接アクセスが頻繁に行われていました。Go言語では、`getg()`というランタイム内部関数を使って現在のGoルーチン（`g`）を取得し、そこから関連する`m`（OSスレッド）の情報を取得する形に変わっています。
5.  **スタック管理**: `stack.go`という新しいファイルが追加され、Goルーチンのスタックレイアウトに関する定数とコメントが定義されています。これは、スタックオーバーフローチェックや、`NOSPLIT`関数（スタックを分割しない関数）の挙動を制御するための重要な情報です。ランタイムの低レベルな部分をGo言語で記述するにあたり、スタックの挙動をより正確に定義し、管理する必要性が高まったことを示唆しています。

### `lock_futex.go`と`lock_sema.go`の具体的な変更点

両ファイルともに、`lock`関数と`unlock`関数、そして`note`関連の関数（`noteclear`, `notewakeup`, `notesleep`, `notetsleep`, `notetsleepg`）がGo言語で再実装されています。

*   **`lock`関数**:
    *   Goルーチンのロックカウント（`gp.m.locks`）をインクリメントします。
    *   `xchg`（アトミックな交換操作）を使って、投機的にロックを取得しようとします。
    *   ロックが取得できなかった場合、CPUコア数に応じてスピンロック（`procyield`）とOSへの制御譲渡（`osyield`）を試みます。
    *   それでもロックが取得できない場合、`futexsleep`（フューテックス版）またはセマフォ（セマフォ版）を使ってGoルーチンをスリープさせ、ロックが解放されるのを待ちます。
*   **`unlock`関数**:
    *   ロックを解放し、`xchg`を使ってロックの状態を`mutex_unlocked`（フューテックス版）または`0`（セマフォ版）に設定します。
    *   ロックを待機しているGoルーチンがいる場合（`mutex_sleeping`状態または`l.key`に`m`へのポインタが設定されている場合）、`futexwakeup`（フューテックス版）または`semawakeup`（セマフォ版）を呼び出して、待機中のGoルーチンをウェイクアップします。
    *   Goルーチンのロックカウント（`gp.m.locks`）をデクリメントします。
*   **`note`関連関数**:
    *   `noteclear`: `note`のキーをクリアします。
    *   `notewakeup`: `note`をウェイクアップ状態にし、待機中のGoルーチンをウェイクアップします。二重ウェイクアップを検出するとパニックします。
    *   `notesleep`: `note`がウェイクアップされるまでGoルーチンをスリープさせます。
    *   `notetsleep`, `notetsleepg`: タイムアウト付きで`note`がウェイクアップされるのを待ちます。`notetsleepg`はユーザーGoルーチンから呼び出されることを想定しており、システムコールブロックの前後で`entersyscallblock()`と`exitsyscall()`を呼び出します。

### `stubs.go`の変更

`stubs.go`では、C言語で実装されていた関数やアセンブリで実装されているアトミック操作のGo言語側の宣言が整理されています。特に、`ptrSize`の定義がよりGoらしい定数表現に変わったり、`notewakeup_m`, `notetsleepg_m`といった`mFunction`型の変数が削除されたりしています。これは、これらの関数がGo言語で直接実装されるようになったため、C言語からの呼び出しスタブが不要になったことを示しています。また、`atomicloaduintptr`のような新しいアトミック操作の宣言が追加されています。

### `asm_*.s`ファイルの変更

各アーキテクチャのアセンブリファイル（`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `asm_arm.s`）には、`runtime·atomicloaduintptr`という新しいアセンブリ関数が追加されています。これは、`uintptr`型のアトミックロード操作を効率的に行うためのものです。

### `os_*.go`ファイルの変更

各OS固有のファイル（`os_darwin.go`など）には、`const stackSystem = 0`または`const stackSystem = 512`のような`stackSystem`定数が追加されています。これは、`stack.go`で定義されたスタックレイアウトパラメータの一部であり、OS固有のスタック要件を考慮するためのものです。WindowsとPlan 9では、シグナルハンドリングなどのOS固有の目的のために、通常のガード領域の下に追加のスタック領域が必要となるため、`stackSystem`が非ゼロの値に設定されています。

### `lock_futex.go` (抜粋)

```go
// We use the uintptr mutex.key and note.key as a uint32.
func key32(p *uintptr) *uint32 {
	return (*uint32)(unsafe.Pointer(p))
}

func lock(l *mutex) {
	gp := getg() // 現在のGoルーチンを取得

	if gp.m.locks < 0 {
		gothrow("runtime·lock: lock count")
	}
	gp.m.locks++ // ロックカウントをインクリメント

	// Speculative grab for lock.
	v := xchg(key32(&l.key), mutex_locked) // アトミックにl.keyをmutex_lockedに設定し、元の値をvに格納
	if v == mutex_unlocked { // 元がアンロック状態なら、ロック取得成功
		return
	}

	// ... (スピンロック、OSへの制御譲渡のロジック) ...

	// Sleep.
	v = xchg(key32(&l.key), mutex_sleeping) // アトミックにl.keyをmutex_sleepingに設定
	if v == mutex_unlocked { // 元がアンロック状態なら、ロック取得成功
		return
	}
	wait = mutex_sleeping
	futexsleep(key32(&l.key), mutex_sleeping, -1) // フューテックスでスリープ
}

func unlock(l *mutex) {
	v := xchg(key32(&l.key), mutex_unlocked) // アトミックにl.keyをmutex_unlockedに設定
	if v == mutex_unlocked { // 元がアンロック状態ならエラー
		gothrow("unlock of unlocked lock")
	}
	if v == mutex_sleeping { // 待機中のGoルーチンがいる場合
		futexwakeup(key32(&l.key), 1) // フューテックスで1つウェイクアップ
	}

	gp := getg()
	gp.m.locks-- // ロックカウントをデクリメント
	// ... (プリエンプション要求の復元ロジック) ...
}
```
*   `key32`関数は、`uintptr`型のポインタを`*uint32`にキャストするためのヘルパー関数です。これは、C言語でのポインタ型変換をGo言語で安全に行うためのイディオムです。
*   `lock`関数と`unlock`関数は、`xchg`（アトミックな交換）と`cas`（比較交換）といったアトミック操作を駆使して、ミューテックスの状態を管理しています。競合が少ない場合はスピンロックで対応し、競合が多い場合はOSのフューテックス機能を利用してGoルーチンをスリープ・ウェイクアップさせます。

### `lock_sema.go` (抜粋)

```go
func lock(l *mutex) {
	gp := getg()
	if gp.m.locks < 0 {
		gothrow("runtime·lock: lock count")
	}
	gp.m.locks++

	// Speculative grab for lock.
	if casuintptr(&l.key, 0, locked) { // アトミックにl.keyを0からlockedに設定
		return
	}
	if gp.m.waitsema == 0 {
		gp.m.waitsema = semacreate() // セマフォを生成
	}

	// ... (スピンロック、OSへの制御譲渡のロジック) ...

	// Someone else has it.
	// l->waitm points to a linked list of M's waiting
	// for this lock, chained through m->nextwaitm.
	// Queue this M.
	for {
		gp.m.nextwaitm = (*m)((unsafe.Pointer)(v &^ locked)) // 待機中のMのリストに現在のMを追加
		if casuintptr(&l.key, v, uintptr(unsafe.Pointer(gp.m))|locked) { // アトミックにl.keyを更新
			break
		}
		v = atomicloaduintptr(&l.key)
		if v&locked == 0 {
			continue Loop
		}
	}
	if v&locked != 0 {
		// Queued.  Wait.
		semasleep(-1) // セマフォでスリープ
		i = 0
	}
}

func unlock(l *mutex) {
	gp := getg()
	var mp *m
	for {
		v := atomicloaduintptr(&l.key)
		if v == locked {
			if casuintptr(&l.key, locked, 0) { // アトミックにl.keyをlockedから0に設定
				break
			}
		} else {
			// Other M's are waiting for the lock.
			// Dequeue an M.
			mp = (*m)((unsafe.Pointer)(v &^ locked)) // 待機中のMをデキュー
			if casuintptr(&l.key, v, uintptr(unsafe.Pointer(mp.nextwaitm))) { // アトミックにl.keyを更新
				// Dequeued an M.  Wake it.
				semawakeup(mp) // セマフォでウェイクアップ
				break
			}
		}
	}
	// ... (ロックカウントのデクリメント、プリエンプション要求の復元ロジック) ...
}
```
*   `lock_sema.go`は、フューテックスが利用できないOS向けの実装です。基本的なロジックは`lock_futex.go`と似ていますが、OSが提供するセマフォ（`semacreate`, `semasleep`, `semawakeup`）を利用してGoルーチンのスリープ・ウェイクアップを行います。
*   特に、`l.key`を`uintptr`として扱い、そこにロック状態と待機中の`m`（OSスレッド）のポインタをパックして格納するテクニックが使われています。これは、C言語のコードでよく見られるポインタとフラグを組み合わせる手法をGo言語で再現したものです。

### `stack.go` (抜粋)

```go
const (
	// stackSystem is a number of additional bytes to add
	// to each stack below the usual guard area for OS-specific
	// purposes like signal handling. Used on Windows and on
	// Plan 9 because they do not use a separate stack.
	// Defined in os_*.go.
	
	// The amount of extra stack to allocate beyond the size
	// needed for the single frame that triggered the split.
	stackExtra = 2048

	// The minimum stack segment size to allocate.
	// If the amount needed for the splitting frame + stackExtra
	// is less than this number, the stack will have this size instead.
	stackMin           = 8192
	stackSystemRounded = stackSystem + (-stackSystem & (stackMin - 1))
	Fixedstack         = stackMin + stackSystemRounded

	// Functions that need frames bigger than this use an extra
	// instruction to do the stack split check, to avoid overflow
	// in case SP - framesize wraps below zero.
	// This value can be no bigger than the size of the unmapped
	// space at zero.
	stackBig = 4096

	// The stack guard is a pointer this many bytes above the
	// bottom of the stack.
	stackGuard = 256 + stackSystem

	// After a stack split check the SP is allowed to be this
	// many bytes below the stack guard.  This saves an instruction
	// in the checking sequence for tiny frames.
	stackSmall = 96

	// The maximum number of bytes that a chain of NOSPLIT
	// functions can use.
	stackLimit = stackGuard - stackSystem - stackSmall

	// The assumed size of the top-of-stack data block.
	// The actual size can be smaller than this but cannot be larger.
	// Checked in proc.c's runtime.malg.
	stackTop = 88

	// Goroutine preemption request.
	// Stored into g->stackguard0 to cause split stack check failure.
	// Must be greater than any real sp.
	// 0xfffffade in hex.
	stackPreempt = ^uintptr(1313)
)
```
*   `stack.go`は、Goルーチンのスタック管理に関する重要な定数を定義しています。これらの定数は、スタックのサイズ、スタックガードの配置、スタックオーバーフローチェックの挙動などを決定します。
*   `stackSystem`はOS固有のスタック要件を考慮するためのもので、`os_*.go`ファイルで定義されます。
*   `stackGuard`や`stackSmall`といった定数は、Goコンパイラが生成するスタックオーバーフローチェックのコードに影響を与えます。

## 変更の背景

Go言語のランタイムは、初期の頃からパフォーマンスが要求される部分やOSとのインタフェース部分にC言語で書かれたコードを含んでいました。しかし、Go言語の進化とともに、ランタイムの大部分をGo言語自身で記述することが可能になり、またその方が望ましいという方針が強まってきました。

この変更の主な背景には、以下の点が挙げられます。

1.  **自己ホスティングの推進**: Go言語のコンパイラやランタイムをGo言語自身で記述することで、Go言語のエコシステム全体の独立性と保守性が向上します。C言語の依存を減らすことで、ビルドプロセスが簡素化され、異なるプラットフォームへの移植性も高まります。
2.  **Go言語の機能活用**: C言語で記述された低レベルのコードは、Go言語の持つ並行処理のプリミティブや型安全性といった恩恵を直接受けることができませんでした。Go言語に変換することで、よりGoらしいイディオムでコードを記述できるようになり、可読性、保守性、そして将来的な最適化の可能性が向上します。
3.  **デバッグとプロファイリングの改善**: Go言語で書かれたコードは、Goのツールチェイン（デバッガ、プロファイラなど）によってより詳細に分析できます。C言語のコードが混在していると、これらのツールの適用範囲が限定されることがありました。
4.  **統一された開発体験**: ランタイム開発者がC言語とGo言語の両方の知識を深く持つ必要がなくなるため、開発の障壁が低減し、より多くの開発者がランタイム開発に貢献しやすくなります。

このコミットは、特にGoランタイムの重要な構成要素であるミューテックス（`lock`および`unlock`関数）と、一回限りの通知メカニズム（`note`）の実装をGo言語に移行するものです。これらの機能は、Goルーチンのスケジューリング、ガベージコレクション、システムコールなど、ランタイムの根幹をなす部分で利用されており、そのGo言語化はランタイムの安定性と効率性に大きな影響を与えます。

## 前提知識の解説

このコミットを理解するためには、以下の概念についての知識が不可欠です。

### 1. Goランタイム (Go Runtime)

Goランタイムは、Goプログラムの実行を管理するシステムです。これには、Goルーチンのスケジューリング、メモリ管理（ガベージコレクションを含む）、チャネル通信、システムコールインターフェース、低レベルの同期プリミティブなどが含まれます。Goプログラムは、OS上で直接実行されるのではなく、Goランタイム上で実行されます。

### 2. ミューテックス (Mutex)

ミューテックス（Mutual Exclusionの略）は、並行プログラミングにおいて共有リソースへのアクセスを制御するための同期プリミティブです。複数のGoルーチンが同時に同じデータにアクセスしようとすると、データ競合が発生し、プログラムの動作が予測不能になる可能性があります。ミューテックスは、一度に一つのGoルーチンだけが共有リソースにアクセスできるようにすることで、この問題を解決します。Go言語では、`sync.Mutex`として提供されていますが、このコミットで変更されているのは、その基盤となるランタイムレベルのミューテックス実装です。

### 3. フューテックス (Futex - Fast Userspace Mutex)

フューテックスは、Linuxカーネルが提供する高速なユーザー空間ミューテックスのメカニズムです。これは、競合が少ない場合にはカーネルへのシステムコールを回避し、ユーザー空間でロックの取得・解放を完結させることで、高いパフォーマンスを実現します。競合が発生した場合にのみ、カーネルに制御を渡し、Goルーチンをスリープさせたり、ウェイクアップさせたりします。
`lock_futex.c`および`lock_futex.go`は、Linux、DragonFly BSD、FreeBSDなどのOSでフューテックスを利用したロック実装を提供します。

### 4. セマフォ (Semaphore)

セマフォは、フューテックスと同様に同期プリミティブの一つですが、より汎用的な概念です。リソースの利用可能数をカウントし、その数がゼロになると待機中のプロセスをブロックします。このコミットでは、フューテックスが利用できないOS（Darwin (macOS), NaCl, NetBSD, OpenBSD, Plan 9, Solaris, Windowsなど）向けに、OSが提供するセマフォや同等のメカニズムを利用したロック実装が`lock_sema.c`および`lock_sema.go`で提供されています。

### 5. `Note` (一回限りの通知メカニズム)

Goランタイム内部で利用される、非常に軽量な一回限りの通知メカニズムです。特定のイベントが発生した際に、待機しているGoルーチンを一度だけウェイクアップするために使用されます。例えば、Goルーチンの終了通知や、システムコールからの復帰待ちなどに利用されます。

### 6. アトミック操作 (Atomic Operations)

アトミック操作は、複数のCPUコアやGoルーチンから同時にアクセスされても、その操作全体が不可分（atomic）であることを保証する操作です。これにより、データ競合を防ぎ、正確な並行処理を実現します。`xchg` (exchange) や `cas` (compare-and-swap) といった操作がこれに該当し、ロックの実装において中心的な役割を果たします。

### 7. `g` (Goroutine) と `m` (Machine)

Goランタイムの内部では、Goルーチンは`g`構造体で表現され、OSスレッドは`m`構造体で表現されます。`g`は`m`上で実行され、`m`はOSによってスケジューリングされます。`g->m->locks`のような記述は、現在のGoルーチンが実行されているOSスレッドが保持しているロックの数を追跡するためのものです。

### 8. `unsafe.Pointer` と `uintptr`

Go言語の`unsafe`パッケージは、型安全性をバイパスして低レベルのメモリ操作を可能にします。`unsafe.Pointer`は任意の型のポインタを保持でき、`uintptr`はポインタを整数として扱うことができます。このコミットでは、C言語のポインタ操作をGo言語で再現するためにこれらの型が多用されています。特に、`Mutex`や`Note`の`key`フィールドは`uintptr`型で定義されており、これを`uint32`や`*m`（OSスレッドの構造体へのポインタ）として解釈するために`unsafe.Pointer`が使われています。

## 技術的詳細

このコミットの核心は、Goランタイムのロックプリミティブの実装をC言語からGo言語へ移植した点にあります。これは単なる言語の置き換え以上の意味を持ちます。

### C言語からGo言語への変換の課題と解決策

C言語で書かれた元のコードは、ポインタ演算、直接的なメモリ操作、そしてOS固有のシステムコールへの直接的なバインディングを多用していました。Go言語はより高レベルな言語であり、通常はこれらの低レベルな操作を抽象化します。この変換では、以下の点が特に重要でした。

1.  **ポインタ演算の再現**: C言語のポインタ演算は、Go言語では`unsafe.Pointer`と`uintptr`を組み合わせて再現されます。例えば、`l->key`のようなC言語の構造体メンバへのポインタアクセスは、Go言語では`key32(&l.key)`のように`unsafe.Pointer`を介して`*uint32`にキャストすることで実現されています。
2.  **アトミック操作のGo言語化**: `xchg` (exchange) や `cas` (compare-and-swap) といったアトミック操作は、Go言語の`sync/atomic`パッケージに相当するランタイム内部のアトミック関数（例: `runtime.xchg`, `runtime.cas`, `runtime.atomicload`, `runtime.atomicloaduintptr`）に置き換えられました。これらの関数は、各アーキテクチャのアセンブリコード（`asm_*.s`ファイル）で実装されており、Go言語から呼び出せるように`stubs.go`で宣言されています。
3.  **OS固有のシステムコール**: `futexsleep`, `futexwakeup`, `semacreate`, `semasleep`, `semawakeup`といったOS固有の同期プリミティブへの呼び出しは、Go言語の関数として宣言され、その実装は引き続きC言語またはアセンブリで提供されるか、Go言語でOS固有のシステムコールをラップする形になります。このコミットでは、これらの関数はGo言語のコードから呼び出されるようになりましたが、その具体的な実装はOS固有のファイル（例: `os_linux.go`など）やアセンブリファイルに委ねられています。
4.  **`g`と`m`のコンテキスト**: C言語のコードでは`g`や`g->m`といったグローバル変数や構造体メンバへの直接アクセスが頻繁に行われていました。Go言語では、`getg()`というランタイム内部関数を使って現在のGoルーチン（`g`）を取得し、そこから関連する`m`（OSスレッド）の情報を取得する形に変わっています。
5.  **スタック管理**: `stack.go`という新しいファイルが追加され、Goルーチンのスタックレイアウトに関する定数とコメントが定義されています。これは、スタックオーバーフローチェックや、`NOSPLIT`関数（スタックを分割しない関数）の挙動を制御するための重要な情報です。ランタイムの低レベルな部分をGo言語で記述するにあたり、スタックの挙動をより正確に定義し、管理する必要性が高まったことを示唆しています。

### `lock_futex.go`と`lock_sema.go`の具体的な変更点

両ファイルともに、`lock`関数と`unlock`関数、そして`note`関連の関数（`noteclear`, `notewakeup`, `notesleep`, `notetsleep`, `notetsleepg`）がGo言語で再実装されています。

*   **`lock`関数**:
    *   Goルーチンのロックカウント（`gp.m.locks`）をインクリメントします。
    *   `xchg`（アトミックな交換操作）を使って、投機的にロックを取得しようとします。
    *   ロックが取得できなかった場合、CPUコア数に応じてスピンロック（`procyield`）とOSへの制御譲渡（`osyield`）を試みます。
    *   それでもロックが取得できない場合、`futexsleep`（フューテックス版）またはセマフォ（セマフォ版）を使ってGoルーチンをスリープさせ、ロックが解放されるのを待ちます。
*   **`unlock`関数**:
    *   ロックを解放し、`xchg`を使ってロックの状態を`mutex_unlocked`（フューテックス版）または`0`（セマフォ版）に設定します。
    *   ロックを待機しているGoルーチンがいる場合（`mutex_sleeping`状態または`l.key`に`m`へのポインタが設定されている場合）、`futexwakeup`（フューテックス版）または`semawakeup`（セマフォ版）を呼び出して、待機中のGoルーチンをウェイクアップします。
    *   Goルーチンのロックカウント（`gp.m.locks`）をデクリメントします。
*   **`note`関連関数**:
    *   `noteclear`: `note`のキーをクリアします。
    *   `notewakeup`: `note`をウェイクアップ状態にし、待機中のGoルーチンをウェイクアップします。二重ウェイクアップを検出するとパニックします。
    *   `notesleep`: `note`がウェイクアップされるまでGoルーチンをスリープさせます。
    *   `notetsleep`, `notetsleepg`: タイムアウト付きで`note`がウェイクアップされるのを待ちます。`notetsleepg`はユーザーGoルーチンから呼び出されることを想定しており、システムコールブロックの前後で`entersyscallblock()`と`exitsyscall()`を呼び出します。

### `stubs.go`の変更

`stubs.go`では、C言語で実装されていた関数やアセンブリで実装されているアトミック操作のGo言語側の宣言が整理されています。特に、`ptrSize`の定義がよりGoらしい定数表現に変わったり、`notewakeup_m`, `notetsleepg_m`といった`mFunction`型の変数が削除されたりしています。これは、これらの関数がGo言語で直接実装されるようになったため、C言語からの呼び出しスタブが不要になったことを示します。また、`atomicloaduintptr`のような新しいアトミック操作の宣言が追加されています。

### `asm_*.s`ファイルの変更

各アーキテクチャのアセンブリファイル（`asm_386.s`, `asm_amd64.s`, `asm_amd64p32.s`, `asm_arm.s`）には、`runtime·atomicloaduintptr`という新しいアセンブリ関数が追加されています。これは、`uintptr`型のアトミックロード操作を効率的に行うためのものです。

### `os_*.go`ファイルの変更

各OS固有のファイル（`os_darwin.go`など）には、`const stackSystem = 0`または`const stackSystem = 512`のような`stackSystem`定数が追加されています。これは、`stack.go`で定義されたスタックレイアウトパラメータの一部であり、OS固有のスタック要件を考慮するためのものです。WindowsとPlan 9では、シグナルハンドリングなどのOS固有の目的のために、通常のガード領域の下に追加のスタック領域が必要となるため、`stackSystem`が非ゼロの値に設定されています。

### `lock_futex.go` (抜粋)

```go
// We use the uintptr mutex.key and note.key as a uint32.
func key32(p *uintptr) *uint32 {
	return (*uint32)(unsafe.Pointer(p))
}

func lock(l *mutex) {
	gp := getg() // 現在のGoルーチンを取得

	if gp.m.locks < 0 {
		gothrow("runtime·lock: lock count")
	}
	gp.m.locks++ // ロックカウントをインクリメント

	// Speculative grab for lock.
	v := xchg(key32(&l.key), mutex_locked) // アトミックにl.keyをmutex_lockedに設定し、元の値をvに格納
	if v == mutex_unlocked { // 元がアンロック状態なら、ロック取得成功
		return
	}

	// ... (スピンロック、OSへの制御譲渡のロジック) ...

	// Sleep.
	v = xchg(key32(&l.key), mutex_sleeping) // アトミックにl.keyをmutex_sleepingに設定
	if v == mutex_unlocked { // 元がアンロック状態なら、ロック取得成功
		return
	}
	wait = mutex_sleeping
	futexsleep(key32(&l.key), mutex_sleeping, -1) // フューテックスでスリープ
}

func unlock(l *mutex) {
	v := xchg(key32(&l.key), mutex_unlocked) // アトミックにl.keyをmutex_unlockedに設定
	if v == mutex_unlocked { // 元がアンロック状態ならエラー
		gothrow("unlock of unlocked lock")
	}
	if v == mutex_sleeping { // 待機中のGoルーチンがいる場合
		futexwakeup(key32(&l.key), 1) // フューテックスで1つウェイクアップ
	}

	gp := getg()
	gp.m.locks-- // ロックカウントをデクリメント
	// ... (プリエンプション要求の復元ロジック) ...
}
```
*   `key32`関数は、`uintptr`型のポインタを`*uint32`にキャストするためのヘルパー関数です。これは、C言語でのポインタ型変換をGo言語で安全に行うためのイディオムです。
*   `lock`関数と`unlock`関数は、`xchg`（アトミックな交換）と`cas`（比較交換）といったアトミック操作を駆使して、ミューテックスの状態を管理しています。競合が少ない場合はスピンロックで対応し、競合が多い場合はOSのフューテックス機能を利用してGoルーチンをスリープ・ウェイクアップさせます。

### `lock_sema.go` (抜粋)

```go
func lock(l *mutex) {
	gp := getg()
	if gp.m.locks < 0 {
		gothrow("runtime·lock: lock count")
	}
	gp.m.locks++

	// Speculative grab for lock.
	if casuintptr(&l.key, 0, locked) { // アトミックにl.keyを0からlockedに設定
		return
	}
	if gp.m.waitsema == 0 {
		gp.m.waitsema = semacreate() // セマフォを生成
	}

	// ... (スピンロック、OSへの制御譲渡のロジック) ...

	// Someone else has it.
	// l->waitm points to a linked list of M's waiting
	// for this lock, chained through m->nextwaitm.
	// Queue this M.
	for {
		gp.m.nextwaitm = (*m)((unsafe.Pointer)(v &^ locked)) // 待機中のMのリストに現在のMを追加
		if casuintptr(&l.key, v, uintptr(unsafe.Pointer(gp.m))|locked) { // アトミックにl.keyを更新
			break
		}
		v = atomicloaduintptr(&l.key)
		if v&locked == 0 {
			continue Loop
		}
	}
	if v&locked != 0 {
		// Queued.  Wait.
		semasleep(-1) // セマフォでスリープ
		i = 0
	}
}

func unlock(l *mutex) {
	gp := getg()
	var mp *m
	for {
		v := atomicloaduintptr(&l.key)
		if v == locked {
			if casuintptr(&l.key, locked, 0) { // アトミックにl.keyをlockedから0に設定
				break
			}
		} else {
			// Other M's are waiting for the lock.
			// Dequeue an M.
			mp = (*m)((unsafe.Pointer)(v &^ locked)) // 待機中のMをデキュー
			if casuintptr(&l.key, v, uintptr(unsafe.Pointer(mp.nextwaitm))) { // アトミックにl.keyを更新
				// Dequeued an M.  Wake it.
				semawakeup(mp) // セマフォでウェイクアップ
				break
			}
		}
	}
	// ... (ロックカウントのデクリメント、プリエンプション要求の復元ロジック) ...
}
```
*   `lock_sema.go`は、フューテックスが利用できないOS向けの実装です。基本的なロジックは`lock_futex.go`と似ていますが、OSが提供するセマフォ（`semacreate`, `semasleep`, `semawakeup`）を利用してGoルーチンのスリープ・ウェイクアップを行います。
*   特に、`l.key`を`uintptr`として扱い、そこにロック状態と待機中の`m`（OSスレッド）のポインタをパックして格納するテクニックが使われています。これは、C言語のコードでよく見られるポインタとフラグを組み合わせる手法をGo言語で再現したものです。

### `stack.go` (抜粋)

```go
const (
	// stackSystem is a number of additional bytes to add
	// to each stack below the usual guard area for OS-specific
	// purposes like signal handling. Used on Windows and on
	// Plan 9 because they do not use a separate stack.
	// Defined in os_*.go.
	
	// The amount of extra stack to allocate beyond the size
	// needed for the single frame that triggered the split.
	stackExtra = 2048

	// The minimum stack segment size to allocate.
	// If the amount needed for the splitting frame + stackExtra
	// is less than this number, the stack will have this size instead.
	stackMin           = 8192
	stackSystemRounded = stackSystem + (-stackSystem & (stackMin - 1))
	Fixedstack         = stackMin + stackSystemRounded

	// Functions that need frames bigger than this use an extra
	// instruction to do the stack split check, to avoid overflow
	// in case SP - framesize wraps below zero.
	// This value can be no bigger than the size of the unmapped
	// space at zero.
	stackBig = 4096

	// The stack guard is a pointer this many bytes above the
	// bottom of the stack.
	stackGuard = 256 + stackSystem

	// After a stack split check the SP is allowed to be this
	// many bytes below the stack guard.  This saves an instruction
	// in the checking sequence for tiny frames.
	stackSmall = 96

	// The maximum number of bytes that a chain of NOSPLIT
	// functions can use.
	stackLimit = stackGuard - stackSystem - stackSmall

	// The assumed size of the top-of-stack data block.
	// The actual size can be smaller than this but cannot be larger.
	// Checked in proc.c's runtime.malg.
	stackTop = 88

	// Goroutine preemption request.
	// Stored into g->stackguard0 to cause split stack check failure.
	// Must be greater than any real sp.
	// 0xfffffade in hex.
	stackPreempt = ^uintptr(1313)
)
```
*   `stack.go`は、Goルーチンのスタック管理に関する重要な定数を定義しています。これらの定数は、スタックのサイズ、スタックガードの配置、スタックオーバーフローチェックの挙動などを決定します。
*   `stackSystem`はOS固有のスタック要件を考慮するためのもので、`os_*.go`ファイルで定義されます。
*   `stackGuard`や`stackSmall`といった定数は、Goコンパイラが生成するスタックオーバーフローチェックのコードに影響を与えます。

# [インデックス 20570] ファイルの概要

このコミットは、Go言語のランタイムライブラリ（`lib9`）とリンカ（`cmd/ld`）における、Windowsホスト上でのクロスコンパイル時の問題、特に一時ディレクトリの削除に関するバグを修正するものです。具体的には、`FindFirstFileW` APIの挙動と、Windowsにおけるファイル削除の要件に対応しています。

## 元コミット内容

このコミットは、GoリンカがWindows上で一時ディレクトリを削除する際に発生する2つの問題を修正します。これらの問題は、リンカが外部リンキングを行う場合にのみ発生し、当時のWindowsでは外部リンキングがサポートされていなかったため、Windowsホスト上でクロスコンパイラを使用している場合にのみ顕在化していました。

具体的には、以下の2点が修正されました。

1.  `lib9`において、`FindFirstFileW`関数がファイル名のみを返し、完全なパス名を返さない問題に対応。コードがスラッシュの有無に依存しないように変更されました。
2.  `ld`（リンカ）において、Windowsがファイルを削除する前にそのファイルを閉じることを要求するため、出力ファイルを削除する可能性のある処理の前にファイルを閉じるように変更されました。

このコミットは、Go issue #8723を修正します。

## 変更の背景

Go言語は、その設計思想としてクロスコンパイルを非常に重視しており、異なるOSやアーキテクチャ向けのバイナリを容易に生成できる機能を提供しています。しかし、特定のプラットフォーム、特にWindows上でのリンキングプロセスには、OS固有の挙動に起因する課題が存在しました。

このコミットが作成された2014年当時、Goのリンカは外部リンキング（Goの内部リンカではなく、システムにインストールされた外部のリンカ、例えばMinGW-w64のGCCなどを使用する方式）を行う際に一時ディレクトリを作成し、処理完了後にこれを削除していました。コミットメッセージにある「Windows does not yet support external linking」という記述は、GoのツールチェインがWindows上でネイティブに外部リンキングを完全にサポートしていなかったことを示唆しています。しかし、Windowsをホストとするクロスコンパイラ（例えば、Windows上でLinuxやmacOS向けのGoバイナリをビルドするケース）を使用する場合、この一時ディレクトリの作成と削除のプロセスが実行され、その際にWindows固有の問題が露呈しました。

問題の根源は、WindowsのファイルシステムAPIの挙動と、ファイル操作に関するOSの厳格な要件にありました。

1.  **`FindFirstFileW`の挙動**: Windows APIの`FindFirstFileW`は、ディレクトリ内のファイルやサブディレクトリを検索する際に、見つかったエントリのファイル名のみを返します。Unix系システムでは、同様の関数が完全なパスを返すことが多いため、Goのコードがパスの区切り文字（スラッシュやバックスラッシュ）の存在を前提としていた場合、予期せぬエラーが発生する可能性がありました。特に、一時ディレクトリ内のファイルを処理する際に、このパスの構築ロジックが誤っていると、ファイルの削除に失敗します。
2.  **Windowsのファイルロック**: Windowsは、開いているファイルを削除することを許可しません。ファイルが何らかのプロセスによってロックされている場合、そのファイルを削除しようとするとエラーが発生します。Goのリンカが出力ファイルを生成した後、そのファイルを閉じる前に一時ディレクトリのクリーンアッププロセスが走ると、出力ファイルがまだ開いている状態であるために削除に失敗し、一時ディレクトリが残存してしまう問題が発生していました。

これらの問題は、特にWindowsホスト上での開発やCI/CD環境において、ビルドプロセスの不安定性やディスクスペースの無駄遣いを引き起こす可能性がありました。このコミットは、これらのWindows固有の挙動に対応し、リンカの一時ディレクトリクリーンアップ処理の堅牢性を向上させることを目的としています。

## 前提知識の解説

このコミットの理解には、以下の技術的背景知識が役立ちます。

1.  **Go言語のクロスコンパイル**: Goは、`GOOS`（ターゲットOS）と`GOARCH`（ターゲットアーキテクチャ）環境変数を設定するだけで、異なるプラットフォーム向けのバイナリを簡単にビルドできる強力なクロスコンパイル機能を内蔵しています。例えば、Windowsマシン上で`GOOS=linux GOARCH=amd64 go build`を実行すると、Linux 64bit向けの実行可能ファイルが生成されます。このコミットの問題は、このクロスコンパイルの「ホスト」がWindowsである場合に発生していました。

2.  **Goリンカ (`cmd/ld`)**: `cmd/ld`はGoのビルドツールチェインの中核をなすリンカです。Goのソースコードがコンパイルされて生成されたオブジェクトファイルやアーカイブファイルを結合し、最終的な実行可能バイナリを生成する役割を担います。Goはデフォルトで静的リンクを多用しますが、C言語との連携（CGO）など、特定のシナリオでは外部リンカを使用する「外部リンキング」モードも存在します。このコミットの文脈では、外部リンキング時に一時ディレクトリが使用されることが重要です。

3.  **`lib9`**: `lib9`は、Goの初期のコードベースにおいて、Plan 9オペレーティングシステムの影響を強く受けた低レベルのユーティリティ関数やシステムコールラッパーを提供するライブラリ群を指します。Go言語の設計者の一部がPlan 9の開発に携わっていたため、Goの標準ライブラリやランタイムにはPlan 9の設計思想やコードが取り入れられています。このコミットで修正される`tempdir_windows.c`は、Windows上での一時ディレクトリ操作に関連する`lib9`の一部であり、ファイルシステムとの低レベルなインタラクションを扱います。

4.  **Windows API `FindFirstFileW`**: `FindFirstFileW`は、WindowsのWin32 APIの一部で、指定されたディレクトリ内でファイルやサブディレクトリを検索するために使用されます。この関数は、検索条件に一致する最初のエントリに関する情報（`WIN32_FIND_DATAW`構造体）を返します。重要なのは、`WIN32_FIND_DATAW`構造体の`cFileName`メンバーには、見つかったファイルまたはディレクトリの「ファイル名」のみが含まれ、完全なパスは含まれないという点です。完全なパスを構築するには、検索対象のディレクトリパスと`cFileName`を結合する必要があります。

5.  **Windowsのファイル操作の特性**: Windowsオペレーティングシステムは、ファイル操作に関してUnix系システムとは異なるいくつかの特性を持っています。特に重要なのは、ファイルが何らかのプロセスによって開かれている（ロックされている）間は、そのファイルを削除できないという点です。ファイルを削除するには、まずそのファイルを閉じ、ロックを解除する必要があります。この特性は、一時ファイルや出力ファイルを扱うアプリケーションにとって、クリーンアップ処理を設計する上で考慮すべき重要な点となります。

これらの知識を前提とすることで、コミットが解決しようとしている具体的な問題と、その解決策の技術的な妥当性をより深く理解することができます。

## 技術的詳細

このコミットは、Windowsホスト上でのGoのクロスコンパイル時に発生する、リンカの一時ディレクトリ削除に関する2つの独立した問題を解決します。

### 問題1: `FindFirstFileW`の戻り値の誤解釈

*   **問題点**: `src/lib9/tempdir_windows.c`内の`removeall`関数は、一時ディレクトリ内のすべてのファイルとサブディレクトリを再帰的に削除する役割を担っています。この関数は、Windows APIの`FindFirstFileW`と`FindNextFileW`を使用してディレクトリの内容を列挙していました。しかし、`FindFirstFileW`（および`FindNextFileW`）が返す`WIN32_FIND_DATAW`構造体の`cFileName`フィールドには、見つかったファイルやディレクトリの「ファイル名」のみが含まれ、その親ディレクトリからの完全なパスは含まれません。
    元のコードでは、`strrchr(q, '\\\\')`（`q`は`data.cFileName`をUTF-8に変換したもの）を使ってパスの最後のバックスラッシュを探し、その後に続く部分をファイル名として扱っていました。これは、`q`が完全なパスであると誤って仮定していたためです。`FindFirstFileW`が返すのはファイル名だけなので、`q`にはバックスラッシュが含まれることは通常ありませんでした。この誤った仮定により、ファイル名が正しく抽出されず、結果として`removeall`が正しいパスを構築できずにファイルの削除に失敗していました。特に、カレントディレクトリを示す「.」や親ディレクトリを示す「..」といった特殊なエントリの処理にも影響を与えていました。

*   **解決策**: `src/lib9/tempdir_windows.c`の変更は、この`FindFirstFileW`の挙動を正しく扱うように修正されました。
    *   `elem = strrchr(q, '\\\\');` の後、`if(elem != nil)` の条件分岐が追加されました。これは、`q`が完全なパスである場合に備えて、バックスラッシュが見つかった場合の処理を残しつつ、
    *   `else elem = q;` という行が追加され、`elem`が`q`（つまり、`FindFirstFileW`が返したファイル名そのもの）を指すように修正されました。これにより、`FindFirstFileW`がファイル名のみを返す場合でも、`elem`が常に正しいファイル名を示すようになります。
    *   さらに、`smprint("%s\\\\%s", p, q);` を使用して、親ディレクトリのパス`p`と`FindFirstFileW`が返したファイル名`q`を結合することで、常に正しい完全なパス`qt`を構築するように変更されました。これにより、`removeall(qt)`が正しいパスで再帰的に呼び出され、一時ディレクトリ内のファイルが適切に削除されるようになりました。

### 問題2: Windowsにおける開いているファイルの削除制限

*   **問題点**: `src/cmd/ld/lib.c`内の`errorexit`関数は、リンカがエラーで終了する際に呼び出されるクリーンアップ処理の一部です。この関数内で、`mayberemoveoutfile()`が呼び出され、リンカが生成した出力ファイル（最終的な実行可能バイナリなど）を削除しようとする可能性がありました。Windowsでは、ファイルが何らかのプロセスによって開かれている間は、そのファイルを削除できません。リンカが出力ファイルを生成した後、エラーが発生して`errorexit`が呼び出された場合、出力ファイルがまだ開いた状態（ファイルハンドル`cout`が閉じられていない状態）であるために、`mayberemoveoutfile()`がファイルを削除しようとしても失敗し、エラーメッセージが表示されたり、一時ファイルが残存したりする問題が発生していました。

*   **解決策**: `src/cmd/ld/lib.c`の変更は、このWindowsのファイルロックの要件に対応しました。
    *   `errorexit`関数の冒頭に、`if(cout >= 0) { close(cout); }` というコードが追加されました。
    *   `cout`はリンカの出力ファイルに対するファイルディスクリプタ（またはハンドル）です。`cout >= 0`は、出力ファイルが正常に開かれていることを示します。
    *   この変更により、エラー終了時に出力ファイルがまだ開いている場合でも、`mayberemoveoutfile()`が呼び出される前に明示的に`close(cout)`が実行され、ファイルハンドルが閉じられます。これにより、出力ファイルに対するロックが解除され、その後の`mayberemoveoutfile()`による削除処理がWindowsの要件を満たし、成功する可能性が高まります。コミットメッセージにある「For rmtemp run at atexit time on Windows.」というコメントは、プログラム終了時に登録されたクリーンアップルーチン（`rmtemp`、一時ディレクトリを削除する関数）がWindows上で実行される際に、ファイルが閉じられている必要があることを示唆しています。

これらの修正により、Windowsホスト上でのGoのクロスコンパイル環境におけるリンカの一時ディレクトリ管理がより堅牢になり、予期せぬエラーや残存ファイルの問題が解消されました。

### `src/cmd/ld/lib.c` の変更

`errorexit` 関数は、リンカがエラーで終了する際に呼び出されるクリーンアップ関数です。

```c

 errorexit(void)
 {
+	if(cout >= 0) {
+		// For rmtemp run at atexit time on Windows.
+		close(cout);
+	}
 	if(nerrors) {
 		if(cout >= 0)
 			mayberemoveoutfile();
```

*   **追加されたコード**:
    ```c
    if(cout >= 0) {
    	// For rmtemp run at atexit time on Windows.
    	close(cout);
    }
    ```
*   **解説**: `cout` はリンカの出力ファイル（例えば、最終的な実行可能バイナリ）のファイルディスクリプタ（またはハンドル）です。Windowsでは、開いているファイルを削除することはできません。リンカがエラーで終了し、一時ディレクトリのクリーンアップ（`rmtemp`など、`atexit`で登録された関数によって実行される可能性のある処理）が行われる前に、出力ファイルがまだ開いている状態だと、そのファイルの削除に失敗します。
    この変更により、`errorexit`が呼び出された際に、もし出力ファイルがまだ開いている（`cout >= 0`）ならば、明示的に`close(cout)`を呼び出してファイルハンドルを閉じます。これにより、ファイルに対するロックが解除され、その後のクリーンアップ処理で出力ファイルが適切に削除できるようになります。コメントは、このクローズ処理がWindows上での`atexit`時に実行される`rmtemp`（一時ディレクトリ削除）のために重要であることを示しています。

# [インデックス 27333] ファイルの概要

このコミットは、Go言語の標準ライブラリ`encoding/binary`パッケージにおけるバウンドチェックの挙動を修正するものです。具体的には、`binary.go`ファイル内の`Uint16`, `PutUint16`, `Uint32`, `PutUint32`, `Uint64`, `PutUint64`といった数値型とバイトスライス間の変換を行うメソッドにおいて、スライス操作の際に意図せずスライスの容量が元の長さを超えてしまう問題を解決しています。これに伴い、`binary_test.go`ファイルに新しいテストケースが追加され、修正が正しく機能することを確認しています。

## 元コミット内容

このコミットは、`encoding/binary`パッケージにおけるバウンドチェックの不具合を修正します。以前のコードでは、早期バウンドチェックのために挿入されたスライス操作が、元のスライスの長さを超えてスライスを拡張してしまう可能性がありました。

## 変更の背景

Go言語のコンパイラは、パフォーマンス最適化のためにバウンドチェックを省略することがあります。`encoding/binary`パッケージの`UintX`および`PutUintX`メソッドでは、バイトスライスから特定のサイズの数値を読み書きする際に、安全性を確保するために明示的なバウンドチェックのヒントをコンパイラに与えていました。これは、`b = b[:N]`のようなスライス式を使って、操作対象のスライスを必要な長さに切り詰めることで実現されていました。

しかし、この`b = b[:N]`という形式のスライス操作には、Goのスライスの内部構造に起因する潜在的な問題がありました。`b = b[:N]`は新しいスライスヘッダを作成しますが、その基盤となる配列は元のスライスと共有されます。このとき、新しいスライスの長さは`N`になりますが、**容量 (capacity)** は元のスライスの容量を保持したままになります。

問題は、コンパイラがこの「切り詰められた」スライスの長さに基づいてバウンドチェックを最適化し、その後のアクセスが安全であると判断する一方で、実際には元のスライスの容量までアクセス可能であるという点にありました。もし、この最適化が不適切に行われると、プログラマが意図しない範囲のメモリにアクセスしてしまう可能性が生じます。特に、`PutUintX`のような書き込み操作では、これがデータ破損やセキュリティ上の脆弱性につながる恐れがありました。

この問題は、`golang.org/issue/14808`で報告されており、このコミットはその解決策として導入されました。

## 前提知識の解説

### Goのスライス (Slice)

Goのスライスは、配列への参照のようなものです。スライスは以下の3つの要素で構成されます。

1.  **ポインタ (Pointer)**: スライスが参照する基盤となる配列の先頭要素へのポインタ。
2.  **長さ (Length)**: スライスに含まれる要素の数。`len(s)`で取得できます。
3.  **容量 (Capacity)**: スライスのポインタから基盤となる配列の末尾までの要素の数。`cap(s)`で取得できます。

### スライス式 `s[low:high]` と `s[low:high:max]`

Goには、スライスを作成または再スライスするためのスライス式があります。

*   **`s[low:high]`**:
    *   新しいスライスは、`s`の`low`インデックスから`high-1`インデックスまでの要素を含みます。
    *   新しいスライスの長さは `high - low` です。
    *   新しいスライスの容量は `cap(s) - low` です。つまり、基盤となる配列の`low`インデックスから末尾までの容量を引き継ぎます。

*   **`s[low:high:max]`**:
    *   新しいスライスは、`s`の`low`インデックスから`high-1`インデックスまでの要素を含みます。
    *   新しいスライスの長さは `high - low` です。
    *   新しいスライスの容量は `max - low` です。この形式を使用すると、新しいスライスの容量を明示的に制限できます。`max`は`high`以上かつ`cap(s)`以下である必要があります。

### バウンドチェック (Bounds Check)

Goのランタイムは、スライスや配列へのアクセスがその範囲内にあるかを確認するために「バウンドチェック」を行います。例えば、`s[i]`というアクセスがあった場合、`0 <= i < len(s)`が満たされているかを確認します。このチェックは、不正なメモリアクセスを防ぎ、プログラムの安全性を高めます。

しかし、バウンドチェックはオーバーヘッドを伴うため、Goコンパイラは可能な限りバウンドチェックを最適化（省略）しようとします。例えば、ループ内で`i`が常に`len(s)`未満であることが証明できる場合、ループ内の`s[i]`へのアクセスに対するバウンドチェックは省略されることがあります。

## 技術的詳細

このコミットで修正された問題は、`s[low:high]`形式のスライス式が新しいスライスの容量を元のスライスから引き継ぐという特性と、コンパイラのバウンドチェック最適化が組み合わさることで発生しました。

具体的には、`encoding/binary`パッケージのメソッドでは、以下のようなコードがありました。

```go
func (littleEndian) Uint16(b []byte) uint16 {
    b = b[:2] // bounds check hint to compiler; see golang.org/issue/14808
    return uint16(b[0]) | uint16(b[1])<<8
}
```

ここで、`b = b[:2]`という操作は、`b`の長さを2に設定します。しかし、`b`の容量は元のスライスの容量を保持したままです。例えば、元の`b`が`[]byte{1, 2, 3, 4}`（長さ4、容量4）だった場合、`b = b[:2]`を実行すると、新しい`b`は`[]byte{1, 2}`（長さ2、容量4）となります。

コンパイラは、`b`の長さが2であることを認識し、その後の`b[0]`や`b[1]`へのアクセスが安全であると判断し、バウンドチェックを省略する可能性があります。しかし、もし何らかの理由でコンパイラがこの最適化を誤解釈したり、あるいは後続のコードがこの「長さ2、容量4」のスライスに対して、長さの範囲外だが容量の範囲内のインデックス（例: `b[2]`や`b[3]`）にアクセスしようとした場合、本来パニックすべきところでパニックが発生しない、あるいは未定義の動作を引き起こす可能性がありました。これは、特に`PutUintX`のような書き込み操作で深刻な問題となります。

この問題を解決するために導入されたのが、**`b = b[:N:len(b)]`** という形式のスライス式です。

*   `b = b[:N:len(b)]` は、新しいスライスの長さが`N`であるだけでなく、**容量も`N`に制限**します。
*   例えば、元の`b`が`[]byte{1, 2, 3, 4}`（長さ4、容量4）だった場合、`b = b[:2:len(b)]`を実行すると、`len(b)`は元の`b`の長さである4なので、`b = b[:2:4]`となります。これにより、新しい`b`は`[]byte{1, 2}`（長さ2、容量2）となります。
*   このように容量を明示的に制限することで、コンパイラがバウンドチェックを最適化する際に、新しいスライスの長さと容量が一致していることを保証できます。これにより、スライスの長さを超えるアクセスは、たとえ元の基盤配列の容量内であっても、確実にパニックを引き起こすようになります。

この修正により、`encoding/binary`パッケージの数値変換メソッドが、より堅牢で安全なバウンドチェックの挙動を示すようになります。

## コアとなるコードの変更箇所

`src/encoding/binary/binary.go` ファイルにおいて、`littleEndian`と`bigEndian`構造体の`Uint16`, `PutUint16`, `Uint32`, `PutUint32`, `Uint64`, `PutUint64`メソッド内のスライス式が変更されました。

**変更前:**

```go
// 例: littleEndian.Uint16
b = b[:2] // bounds check hint to compiler; see golang.org/issue/14808

// 例: littleEndian.PutUint16
b = b[:2] // early bounds check to guarantee safety of writes below
```

**変更後:**

```go
// 例: littleEndian.Uint16
b = b[:2:len(b)] // bounds check hint to compiler; see golang.org/issue/14808

// 例: littleEndian.PutUint16
b = b[:2:len(b)] // early bounds check to guarantee safety of writes below
```

また、`src/encoding/binary/binary_test.go` ファイルには、新しいテストケース`TestEarlyBoundsChecks`が追加されました。このテストは、意図的に短いスライスを`Uint64`および`PutUint64`メソッドに渡し、期待通りパニックが発生するかどうかを確認します。

```go
func testUint64SmallSliceLengthPanics() (panicked bool) {
	defer func() {
		panicked = recover() != nil
	}()
	b := [8]byte{1, 2, 3, 4, 5, 6, 7, 8}
	LittleEndian.Uint64(b[:4]) // 長さ4のスライスを渡す
	return false
}

func testPutUint64SmallSliceLengthPanics() (panicked bool) {
	defer func() {
		panicked = recover() != nil
	}()
	b := [8]byte{}
	LittleEndian.PutUint64(b[:4], 0x0102030405060708) // 長さ4のスライスを渡す
	return false
}

func TestEarlyBoundsChecks(t *testing.T) {
	if testUint64SmallSliceLengthPanics() != true {
		t.Errorf("binary.LittleEndian.Uint64 expected to panic for small slices, but didn't")
	}
	if testPutUint64SmallSliceLengthPanics() != true {
		t.Errorf("binary.LittleEndian.PutUint64 expected to panic for small slices, but didn't")
	}
}
```

## コアとなるコードの解説

変更の核心は、スライス式 `b = b[:N]` を `b = b[:N:len(b)]` に置き換えた点にあります。

*   **`b = b[:N]`**: この形式は、スライス`b`の基盤となる配列を共有しつつ、新しいスライスの長さを`N`に設定します。しかし、新しいスライスの容量は、元のスライス`b`の容量から開始インデックス（この場合は0）を引いた値になります。つまり、元のスライスの容量が新しいスライスに引き継がれるため、新しいスライスの長さ`N`よりも大きな容量を持つことになります。これにより、コンパイラがバウンドチェックを最適化する際に、長さ`N`を超えたアクセスが安全であると誤って判断する可能性がありました。

*   **`b = b[:N:len(b)]`**: この形式は、新しいスライスの長さを`N`に設定するだけでなく、**容量も`len(b)`（元のスライスの長さ）に制限**します。この場合、`N`は常に`len(b)`以下であるため、結果として新しいスライスの容量は`N`に等しくなります。
    *   例: `b`が長さ`L`、容量`C`のスライスであるとする。
    *   `b = b[:N:len(b)]` は `b = b[:N:L]` と同義。
    *   新しいスライスの長さは`N`。
    *   新しいスライスの容量は`L`。
    *   ただし、スライス式の制約として `low <= high <= max <= cap(original_slice)` があります。
    *   この文脈では、`N`は常に`L`以下であるため、新しいスライスの容量は`N`に設定されます。
    *   これにより、新しいスライスの長さと容量が一致し、コンパイラがバウンドチェックを最適化する際に、スライスの長さを超えるアクセスは常に不正であると正しく判断できるようになります。

この修正により、`encoding/binary`パッケージのメソッドが、与えられたバイトスライスの範囲外へのアクセスを確実に防ぎ、予期せぬ動作やセキュリティ上の問題を回避できるようになりました。追加されたテストケースは、この修正が正しく機能し、短いスライスが渡された場合に期待通りパニックが発生することを確認しています。

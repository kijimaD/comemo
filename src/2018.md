# [インデックス 2018] ファイルの概要

このコミットは、Go言語の初期の`template`パッケージにおいて、テンプレートの区切り文字（デリミタ）をユーザーが設定できるようにする機能を追加したものです。これにより、デフォルトの`{{`と`}}`以外の文字列をデリミタとして使用できるようになり、他のテンプレートエンジンとの競合を避けるなどの柔軟性が向上しました。

## 変更の背景

Go言語のテンプレートエンジンは、その初期段階から、テンプレート内のアクション（変数表示、制御構造など）を識別するために特定の区切り文字（デリミタ）を使用していました。このコミット以前は、これらのデリミタはハードコードされており、具体的には`{`と`}`が使用されていました。

しかし、ウェブアプリケーション開発などでは、Goテンプレートが他のクライアントサイドのテンプレートエンジン（例: AngularJSなど、当時はまだ初期段階でしたが、同様のデリミタを使用する可能性のある技術）と組み合わせて使用されることが想定されます。もし両者が同じデリミタを使用している場合、パーサーがどちらのテンプレートのアクションであるかを区別できず、予期せぬエラーや誤ったレンダリングが発生する可能性がありました。

この問題を解決し、Goテンプレートの柔軟性と互換性を高めるために、デリミタをユーザーが任意に設定できるようにする機能が求められました。これにより、開発者は環境に応じてデリミタを調整し、競合を回避できるようになります。

## 前提知識の解説

*   **Go言語の`template`パッケージ（初期）**: このコミットは、Go言語の標準ライブラリの一部である`template`パッケージ（当時は`src/lib/template`に位置）に関するものです。このパッケージは、テキストベースのテンプレートを解析し、データ構造を適用して最終的な出力を生成するための機能を提供します。
*   **テンプレートエンジン**: テンプレートエンジンは、プレースホルダーを含むテキスト（テンプレート）とデータソースを組み合わせて、動的なコンテンツを生成するソフトウェアコンポーネントです。ウェブページ、メール、設定ファイルなどの生成に広く利用されます。
*   **デリミタ（区切り文字）**: テンプレートエンジンにおいて、デリミタはテンプレート内の特別な構文（アクション、変数、制御フローなど）の開始と終了を示すために使用される文字または文字列のペアです。例えば、Goテンプレートのデフォルトでは`{{`と`}}`が使用されます。
*   **字句解析（Lexical Analysis）**: プログラミング言語のコンパイラやインタプリタの最初の段階で、入力文字列（この場合はテンプレートテキスト）を意味のある最小単位（トークン）に分割するプロセスです。このコミットでは、デリミタの変更が字句解析器に直接影響を与えます。
*   **バイトスライス（`[]byte`）**: Go言語におけるバイトのシーケンスです。文字列は内部的にバイトスライスとして扱われることが多く、特に低レベルのテキスト処理やI/O操作で頻繁に使用されます。このコミットでは、デリミタが`[]byte`型で保持されるようになります。

## 技術的詳細

このコミットの主要な技術的変更点は、テンプレートの字句解析器がハードコードされた`{`と`}`の文字に依存するのではなく、`Template`構造体に新しく追加された`ldelim`（左デリミタ）と`rdelim`（右デリミタ）のバイトスライスを使用するように汎用化されたことです。

具体的には、以下の点が変更されました。

1.  **`Template`構造体の拡張**:
    *   `ldelim, rdelim []byte`フィールドが追加されました。これにより、各`Template`インスタンスが独自のデリミタペアを持つことができるようになります。
2.  **エラーメッセージの汎用化**:
    *   以前の`ErrLBrace`, `ErrUnmatchedRBrace`, `ErrUnmatchedLBrace`といった波括弧に特化したエラーメッセージが、`ErrUnmatchedRDelim`, `ErrUnmatchedLDelim`といったデリミタに汎用的な名前に変更されました。
    *   新たに`ErrEmptyDelims`が追加され、空のデリミタ文字列が設定された場合にエラーを返すようになりました。これは、空のデリミタが字句解析を不可能にするため、重要なバリデーションです。
3.  **字句解析ロジックの変更**:
    *   `nextItem`関数（テンプレートの次のトークンを抽出する役割）内のデリミタ検出ロジックが、ハードコードされた`{`や`}`の比較から、`equal`ヘルパー関数を用いた`ldelim`および`rdelim`とのバイトスライス比較に置き換えられました。これにより、任意の長さのデリミタに対応できるようになりました。
    *   `equal`関数は、与えられたバイトスライスが指定された位置から始まる別のバイトスライスと一致するかどうかを効率的にチェックします。
4.  **テンプレート初期化とデリミタ設定のAPI変更**:
    *   以前の`newTemplate`関数は、内部的な`init`メソッドに置き換えられました。
    *   新しい`New`関数が導入され、`FormatterMap`（フォーマッタ関数を定義するマップ）を受け取り、デフォルトのデリミタ`{}`を設定した`Template`インスタンスを返します。
    *   `SetDelims(left, right string)`メソッドが追加され、既存の`Template`インスタンスのデリミタを動的に変更できるようになりました。このメソッドは、入力された文字列をバイトスライスに変換して`ldelim`と`rdelim`に設定します。
    *   トップレベルの`Parse`関数は、`New`と`SetDelims`、そして内部的な`t.Parse`メソッドを呼び出すラッパー関数として再定義されました。これにより、ユーザーは以前と同様に`Parse`関数を使用しつつ、内部で新しいデリミタ設定機能が利用されるようになりました。
5.  **テストの追加**:
    *   `TestCustomDelims`という新しいテストケースが追加されました。このテストは、様々な長さのカスタムデリミタ（空のデリミタを含む）を設定し、テンプレートのパースと実行が正しく行われることを検証します。特に、空のデリミタがエラーを発生させることを確認するロジックが含まれています。

これらの変更により、`template`パッケージは、デリミタの柔軟な設定を可能にし、将来的な拡張性や他のシステムとの連携における互換性を大幅に向上させました。

## コアとなるコードの変更箇所

このコミットのコアとなる変更は、主に`src/lib/template/template.go`ファイルに集中しています。

1.  **`Template`構造体へのフィールド追加**:
    ```go
    type Template struct {
    	fmap	FormatterMap;	// formatters for variables
    	ldelim, rdelim	[]byte;	// delimiters; default {}
    	buf	[]byte;	// input text to process
    	p	int;	// position in buf
    	linenum	*int;	// position in input
    }
    ```
2.  **デリミタ比較のためのヘルパー関数`equal`の追加**:
    ```go
    // safely, does s[n:n+len(t)] == t?
    func equal(s []byte, n int, t []byte) bool {
    	b := s[n:len(s)];
    	if len(t) > len(b) {	// not enough space left for a match.
    		return false
    	}
    	for i , c := range t {
    		if c != b[i] {
    			return false
    		}
    	}
    	return true
    }
    ```
3.  **`nextItem`関数におけるデリミタ検出ロジックの変更**:
    ```go
    // 変更前:
    // case '{':
    // ...
    // case '}':
    // ...

    // 変更後:
    case !sawLeft && equal(t.buf, i, t.ldelim):  // sawLeft checked because delims may be equal
    	// ...
    case equal(t.buf, i, t.rdelim):
    	// ...
    ```
4.  **`New`関数と`SetDelims`メソッドの追加**:
    ```go
    // New creates a new template with the specified formatter map (which
    // may be nil) defining auxiliary functions for formatting variables.
    func New(fmap FormatterMap) *Template {
    	t := new(Template);
    	t.fmap = fmap;
    	t.ldelim = lbrace; // lbraceは`{`を表すバイトスライス
    	t.rdelim = rbrace; // rbraceは`}`を表すバイトスライス
    	return t;
    }

    // SetDelims sets the left and right delimiters for operations in the template.
    func (t *Template) SetDelims(left, right string) {
    	t.ldelim = io.StringBytes(left);
    	t.rdelim = io.StringBytes(right);
    }
    ```
5.  **トップレベルの`Parse`関数の再定義**:
    ```go
    func Parse(s string, fmap FormatterMap) (*Template, *os.Error, int) {
    	t := New(fmap);
    	err, line := t.Parse(s); // t.ParseはTemplateのメソッドとして定義された新しいパースロジック
    	return t, err, line
    }
    ```

## コアとなるコードの解説

*   **`Template`構造体への`ldelim`, `rdelim`フィールド追加**:
    これは、各テンプレートインスタンスが独自のデリミタを持つことを可能にする基盤です。これにより、複数のテンプレートが異なるデリミタ設定で共存できるようになります。`[]byte`型を使用することで、単一の文字だけでなく、複数文字からなるデリミタ（例: `<<`や`%>`など）もサポートできるようになります。

*   **`equal`ヘルパー関数**:
    この関数は、`nextItem`や`analyze`といった字句解析の核心部分で、入力バッファ内の特定の位置から始まるバイトシーケンスが、現在のデリミタ（`ldelim`または`rdelim`）と一致するかどうかを効率的かつ安全にチェックするために導入されました。これにより、デリミタの長さが可変になっても、正確なマッチングが可能になります。

*   **`nextItem`関数におけるデリミタ検出ロジックの変更**:
    `nextItem`はテンプレートテキストをトークンに分割する役割を担っています。以前は`switch t.buf[i]`で単一の文字`{`や`}`を直接比較していましたが、変更後は`equal`関数を使って`t.ldelim`や`t.rdelim`といったバイトスライス全体との比較を行うようになりました。これにより、デリミタが複数文字であっても正しく認識され、テンプレートのアクションブロックの開始と終了を検出できるようになります。

*   **`New`関数と`SetDelims`メソッド**:
    `New`関数は、新しい`Template`オブジェクトを生成し、デフォルトのデリミタ（`{`と`}`）を初期設定します。これは、既存のコードがデリミタの変更なしに動作し続けるための互換性を提供します。
    `SetDelims`メソッドは、開発者がプログラム的にデリミタを変更するための公開APIです。これにより、アプリケーションの要件に応じて、実行時にデリミタをカスタマイズする柔軟性が提供されます。例えば、`tmpl.SetDelims("<<", ">>")`のように呼び出すことで、テンプレートのアクションが`<<.Var>>`のようになるように設定できます。

*   **トップレベルの`Parse`関数の再定義**:
    この変更は、既存のユーザーコードへの影響を最小限に抑えつつ、新しいデリミタ設定機能を統合するためのものです。ユーザーは引き続き`Parse`関数を呼び出すことができますが、内部的には`New`関数でテンプレートが初期化され、必要に応じて`SetDelims`が呼び出されることで、デリミタのカスタマイズが透過的に行われるようになりました。

これらの変更は、Goテンプレートの柔軟性を高め、より多様なユースケースに対応できるようにするための重要なステップでした。

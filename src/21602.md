# [インデックス 21602] ファイルの概要

このコミットは、Go言語のリンカ（`liblink`）における重要な変更を導入しています。具体的には、アセンブリコードの仮想アドレスを計算する`vaddr`関数とその関連関数に、`Prog*`（プログラム命令を表す構造体へのポインタ）引数を追加しています。この変更は、C言語で書かれた既存のリンカコードベースをGo言語に翻訳する将来の作業を見越したものであり、特に診断メッセージ出力（`ctxt->diag`）において、`Prog`が持つ情報がアドレスの適切なフォーマットに必要となるためです。

## コミット

liblink: arrange for Prog* argument in vaddr

## GitHub上でのコミットページへのリンク

https://github.com/golang/go/commit/3b2de80309d6a788d33304c1ac9af289a74501e8

[dev.cc] liblink: arrange for Prog* argument in vaddr

The argument is unused in the C code but will be used in the Go translation,

## 変更の背景

Go言語のツールチェイン、特にリンカ（`liblink`）は、初期にはC言語で実装されていました。しかし、Go言語自体の成熟と、ツールチェイン全体の整合性を高める目的から、これらのC言語コンポーネントをGo言語に段階的に翻訳するプロジェクトが進行していました。

このコミットは、そのGo言語への翻訳作業の一環として行われた準備的な変更です。`vaddr`関数は、アセンブリ命令のアドレス解決を行うリンカの核心部分の一つです。診断メッセージを出力する際に、`ctxt->diag`という関数が使用されますが、この関数内でアドレスをシンボリックに表現するためのフォーマット指定子（`%A`）が使われることがあります。この`%A`が正しく機能するためには、現在処理している命令に関する情報、すなわち`Prog`構造体が持つ情報が必要となります。

C言語の既存の実装では、この`Prog`情報が`vaddr`関数に直接渡されていませんでしたが、Go言語への翻訳後には、この情報が明示的に必要となることが判明しました。そのため、Go言語への移行をスムーズに行うために、C言語の段階で`Prog*`引数を追加し、将来のGo言語実装での利用に備えるという背景があります。C言語のコードでは一時的にこの引数は未使用となりますが、Go言語への翻訳が完了すれば、その真価を発揮することになります。

## 前提知識の解説

### Goリンカ (liblink) の役割

`liblink`は、Go言語のビルドプロセスにおいて、コンパイルされたオブジェクトファイル（`.o`ファイル）やアーカイブファイル（`.a`ファイル）を結合し、実行可能なバイナリファイルを生成する役割を担うライブラリです。Goプログラムが実行されるためには、ソースコードが機械語に変換され、必要なライブラリやランタイムとリンクされる必要があります。`liblink`はその「リンク」の工程を担当し、シンボル解決、アドレスの再配置、セクションの結合などを行います。

### `Prog` 構造体

Goリンカの内部では、プログラムの各命令やデータ要素は`Prog`という構造体で表現されます。これはリンカが処理する中間表現の一つであり、命令の種類、オペランド、アドレス情報、関連するシンボルなど、命令に関する詳細なメタデータを含んでいます。リンカはこれらの`Prog`構造体のリストを操作することで、最終的な実行可能バイナリを構築します。

### `Link` コンテキスト (`ctxt`) と `diag` メソッド

リンカの操作は、`Link`というコンテキスト構造体（コード内ではしばしば`ctxt`という変数名で参照されます）を通じて行われます。この`Link`構造体は、リンカの状態、設定、シンボルテーブル、エラーハンドリングメカニズムなど、リンク処理全体に必要な情報と機能を提供します。

`diag`メソッドは、この`Link`コンテキストの一部であり、リンカが診断メッセージ（エラー、警告、デバッグ情報など）を出力するために使用されます。これはC言語の`printf`関数やGo言語の`fmt.Printf`に似た機能を提供し、フォーマット文字列と可変引数を受け取ります。

### C言語からGo言語への移行

Go言語の初期のツールチェイン（コンパイラ、アセンブラ、リンカなど）は、自己ホスト型になる前の段階でC言語で書かれていました。これは、Go言語がまだ十分に成熟しておらず、Go言語自身でツールチェインを記述することが困難だったためです。しかし、Go言語が進化するにつれて、ツールチェイン全体をGo言語で記述し直す「Go bootstrap」または「Go toolchain rewrite」と呼ばれるプロジェクトが進行しました。これにより、ツールチェインの保守性、移植性、そしてGo言語の機能活用が向上しました。このコミットは、その移行プロセスにおける特定のC言語関数（`vaddr`）のシグネチャ変更を伴う準備作業です。

### `%A` フォーマット指定子

`ctxt->diag`のような診断出力関数において、`%A`は特定のアドレスをシンボリックな形式で表示するためのフォーマット指定子として使用されます。例えば、単なる数値アドレスではなく、それがどの関数や変数、あるいはどのソースコードの行に対応するかといった情報を付加して表示するために使われます。このシンボリックな解決には、リンカが持つシンボルテーブルや、現在処理している`Prog`構造体のアドレス情報が必要となります。

## 技術的詳細

このコミットの技術的な核心は、`src/liblink/asm6.c`と`src/liblink/asm8.c`という2つのファイルにおける関数シグネチャの変更と、それに伴う関数呼び出しの修正です。

主要な変更は、`vaddr`関数のシグネチャに`Prog* p`引数を追加したことです。
変更前: `static vlong vaddr(Link *ctxt, Addr *a, Reloc *r);`
変更後: `static vlong vaddr(Link *ctxt, Prog *p, Addr *a, Reloc *r);`

この変更は、`vaddr`を呼び出す他の関数（`relput4`, `relput8`, `asmandsz`など）にも連鎖的に影響を与え、これらの関数のシグネチャも`Prog* p`引数を受け入れるように変更されました。さらに、これらの関数を呼び出す箇所もすべて更新され、適切な`Prog*`引数が渡されるようになりました。

コミットメッセージにある通り、C言語の現在の実装では、追加された`Prog* p`引数は直接使用されていません。これは、`vaddr`関数内で`USED(p);`というマクロが使用されていることからも確認できます。`USED`マクロは、コンパイラが未使用の引数について警告を発するのを抑制するために用いられます。これは、将来のGo言語への翻訳時にこの引数が使用されることを前提とした、意図的な設計判断です。

この変更により、リンカのコードベースは、Go言語への移行後も`ctxt->diag`呼び出し内で`Prog`構造体から得られる情報を活用し、より詳細で意味のある診断メッセージを生成できるようになります。特に、`%A`フォーマット指定子によるアドレスのシンボリックな表示が、`Prog`が持つコンテキスト情報に基づいて正確に行われるようになります。

## コアとなるコードの変更箇所

このコミットで変更された主要なファイルと関数は以下の通りです。

-   `src/liblink/asm6.c`
-   `src/liblink/asm8.c`

これらのファイル内で、以下の関数のシグネチャが変更され、`Prog* p`引数が追加されました。

-   `vaddr`
-   `asmandsz`
-   `asmand`
-   `asmando`

また、これらの関数を呼び出しているすべての箇所で、`Prog*`引数が渡されるように修正されています。

## コアとなるコードの解説

### `vaddr`関数のシグネチャ変更

`vaddr`関数は、アセンブリ命令のオペランドが参照する仮想アドレスを計算する役割を担っています。この関数は、アドレス解決の過程で診断メッセージを出力する可能性があります。

```c
// src/liblink/asm6.c, src/liblink/asm8.c
// 変更前: static vlong vaddr(Link *ctxt, Addr *a, Reloc *r);
// 変更後:
static vlong
vaddr(Link *ctxt, Prog *p, Addr *a, Reloc *r)
{
    int t;
    vlong v;
    LSym *s;

    USED(p); // 新しく追加されたProg* p引数は、Cコードでは未使用であることを明示

    if(r != nil)
        memset(r, 0, sizeof *r);

    // ... (アドレス計算ロジック) ...

    // ctxt->diag呼び出しの例 (変更前後の差分には直接含まれないが、この関数内で使用される)
    // ctxt->diag("bad address type %A", a); // %AがProg* pの情報を利用する
}
```
`Prog* p`が追加されたことで、`vaddr`内で`ctxt->diag`が呼び出される際に、`p`が持つ命令のコンテキスト情報（例えば、命令のアドレス、シンボル、ファイル/行情報など）を利用して、より正確なシンボリックアドレスの表示が可能になります。

### `asmandsz`, `asmand`, `asmando`関数のシグネチャ変更と呼び出し箇所の修正

これらの関数は、アセンブリ命令のオペランドをエンコードし、バイナリコードを生成する際に`vaddr`を呼び出します。`vaddr`のシグネチャ変更に伴い、これらの関数も`Prog* p`引数を受け取るように変更され、さらに`vaddr`を呼び出す際にその`p`引数を渡すようになりました。

例: `asmandsz`関数の変更

```c
// src/liblink/asm6.c
// 変更前: static void asmandsz(Link *ctxt, Addr *a, int r, int rex, int m64)
// 変更後:
static void
asmandsz(Link *ctxt, Prog *p, Addr *a, int r, int rex, int m64)
{
    int32 v;
    int t, scale;
    Reloc rel;

    USED(m64);
    USED(p); // ここでもProg* pはCコードでは未使用

    // ... (オペランドエンコードロジック) ...

    // vaddrの呼び出し箇所
    // 変更前: v = vaddr(ctxt, a, &rel);
    // 変更後: v = vaddr(ctxt, p, a, &rel);
}
```

同様に、`relput4`や`relput8`といったリロケーション情報を処理する関数も、`vaddr`を呼び出す際に`Prog* p`を渡すように変更されています。

これらの変更は、リンカのコードベース全体で`Prog`コンテキストが`vaddr`関数に伝播されるようにするためのものであり、Go言語への翻訳後のコードの健全性と機能性を保証するための重要なステップです。

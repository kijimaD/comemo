# [インデックス 27510] ファイルの概要

このコミットは、Goランタイムにおけるメモリ移動関数（`memmove`）のパフォーマンス最適化に関するものです。特に、x86およびx86-64アーキテクチャにおいて、`REP;MOVSB`命令の使用条件を厳格化し、CPUの機能（CPUID）とメモリのアライメント状態に基づいて、より高速なメモリ移動命令（`REP;MOVSQ`または`REP;MOVSL`）を動的に選択するように変更しています。これにより、特定のCPU環境下での`memmove`の性能低下を防ぎ、全体的なランタイム性能の向上を図っています。

## 変更の背景

x86およびx86-64アーキテクチャには、メモリブロックをコピーするための`REP;MOVSB`という命令が存在します。これはバイト単位でメモリを移動する命令で、`memcpy`や`memmove`のような標準ライブラリ関数で頻繁に利用されます。しかし、この命令の実際のパフォーマンスは、CPUの世代、メモリのアライメント状態、およびコピーするデータのサイズによって大きく変動します。

特に、古いCPUや、`Enhanced REP MOVSB/STOSB` (ERMS) と呼ばれる機能を持たないCPUでは、`REP;MOVSB`が他の命令シーケンス（例えば、より大きな単位でデータを移動する`REP;MOVSQ`や`REP;MOVSL`）よりも遅くなることがありました。また、メモリのアライメント（データが特定のバイト境界に配置されているか）も性能に影響を与えます。一般的に、アライメントされたデータの方が高速に処理できますが、`REP;MOVSB`はアライメントされていないデータに対しては比較的効率が良い一方で、アライメントされたデータに対してはオーバーヘッドが大きくなる場合がありました。

このコミットの背景には、`REP;MOVSB`が常に最速の選択肢ではないという認識と、CPUの機能を動的に検出し、最適な命令を選択することで`memmove`の性能を向上させるという目的があります。特に、CPUIDフラグが`REP;MOVSB`が高速であることを示さない場合、またはポインタがアライメントされている場合には、より大きな単位でデータを移動する命令（`REP;MOVSQ`や`REP;MOVSL`）を使用する方が効率的であるという知見に基づいています。

## 前提知識の解説

### x86/x86-64におけるメモリ移動命令

*   **`REP;MOVSB`**: `MOVSB`命令（バイト移動）を`ECX`（または`RCX`）レジスタで指定された回数だけ繰り返す命令です。バイト単位でメモリをコピーします。
*   **`REP;MOVSW`**: `MOVSW`命令（ワード移動、2バイト）を繰り返します。
*   **`REP;MOVSL`**: `MOVSL`命令（ダブルワード移動、4バイト）を繰り返します。32ビットアーキテクチャ（386）でよく使われます。
*   **`REP;MOVSQ`**: `MOVSQ`命令（クアッドワード移動、8バイト）を繰り返します。64ビットアーキテクチャ（AMD64）でよく使われます。

これらの命令は、`ESI`レジスタがソースポインタ、`EDI`レジスタがデスティネーションポインタ、`ECX`/`RCX`レジスタがコピーする要素数を保持します。`DF`（方向フラグ）によって、ポインタをインクリメントするかデクリメントするかが決まります。

### CPUID命令

`CPUID`は、x86アーキテクチャのプロセッサが持つ命令で、CPUの機能やサポートする命令セット、キャッシュ情報などをソフトウェアから問い合わせるために使用されます。`EAX`レジスタに特定の値を設定して`CPUID`命令を実行すると、`EAX`, `EBX`, `ECX`, `EDX`レジスタにCPU情報が返されます。

### ERMS (Enhanced REP MOVSB/STOSB)

ERMSは、IntelのIvy Bridgeマイクロアーキテクチャ（2012-2013年頃）で導入された機能で、`REP;MOVSB`および`REP;STOSB`命令のパフォーマンスを大幅に向上させます。特に、大量のメモリコピーにおいて効果を発揮します。この機能の有無は、CPUID命令の`EAX=7, ECX=0`で問い合わせた際に返される`EBX`レジスタのビット9（`erms`フラグ）で確認できます。このフラグがセットされている場合、CPUは強化された`REP;MOVSB`の実装を持っていることを示します。

### メモリのアライメント

メモリのアライメントとは、データがメモリ上で特定のバイト境界に配置されていることを指します。例えば、4バイトの整数が4の倍数のアドレスに配置されていれば「4バイトアライメントされている」と言います。CPUは、アライメントされたデータへのアクセスを最適化するように設計されているため、アライメントされていないデータへのアクセスは、追加のサイクルや特別な処理が必要となり、パフォーマンスが低下する可能性があります。

## 技術的詳細

このコミットは、Goランタイムの`memmove`実装において、`REP;MOVSB`命令の使用をより賢明に行うためのロジックを導入しています。具体的な変更点は以下の通りです。

1.  **CPUIDによるERMS機能の検出**:
    *   `asm_386.s`および`asm_amd64.s`の初期化ルーチンにおいて、`CPUID`命令（`EAX=7, ECX=0`）を実行し、結果の`EBX`レジスタを`runtime·cpuid_ebx7(SB)`というグローバル変数に保存するように変更されました。
    *   この`cpuid_ebx7`変数には、ERMS機能の有無を示すビット9が含まれています。

2.  **`memmove`ルーチンでの条件分岐**:
    *   `memmove_386.s`および`memmove_amd64.s`の`memmove`実装において、メモリコピーの前に以下の2つの条件をチェックします。
        *   **ERMS機能の有無**: `runtime·cpuid_ebx7(SB)`のビット9（`erms`フラグ）がセットされているかを確認します。
        *   **ポインタのアライメント**: ソースポインタ（`SI`）とデスティネーションポインタ（`DI`）が、それぞれ4バイト（386）または8バイト（AMD64）の境界にアライメントされているかを確認します。

    *   **ロジック**:
        *   ERMS機能が有効でない場合 (`TESTL $(1<<9), runtime·cpuid_ebx7(SB)`の結果がゼロの場合)、`REP;MOVSB`は使用せず、直接`REP;MOVSL`（386）または`REP;MOVSQ`（AMD64）によるコピーに移行します。これは、ERMSがない環境では`REP;MOVSB`が遅い可能性があるためです。
        *   ERMS機能が有効な場合でも、ポインタがアライメントされている場合 (`TESTL $3, AX`または`TESTL $7, AX`の結果がゼロの場合) は、`REP;MOVSL`（386）または`REP;MOVSQ`（AMD64）によるコピーに移行します。これは、ERMSがあってもアライメントされたデータに対しては、より大きな単位で移動する命令の方が効率的であるという最適化です。
        *   ERMS機能が有効で、**かつ**ポインタがアライメントされていない場合にのみ、`REP;MOVSB`を使用してバイト単位のコピーを行います。これは、アライメントされていないデータに対しては`REP;MOVSB`が比較的効率的であり、ERMSによってその性能がさらに向上しているためです。

この変更により、Goランタイムは実行環境のCPU特性とメモリ状態に応じて、最適なメモリ移動戦略を動的に選択できるようになり、`memmove`のパフォーマンスが向上します。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   `src/runtime/asm_386.s`: 32ビットx86アーキテクチャ向けのCPUID情報取得ロジックを追加。
*   `src/runtime/asm_amd64.s`: 64ビットx86アーキテクチャ向けのCPUID情報取得ロジックを追加。
*   `src/runtime/memmove_386.s`: 32ビットx86アーキテクチャ向けの`memmove`ルーチンで、`REP;MOVSB`の使用条件をCPUIDとアライメントに基づいて変更。
*   `src/runtime/memmove_amd64.s`: 64ビットx86アーキテクチャ向けの`memmove`ルーチンで、`REP;MOVSB`の使用条件をCPUIDとアライメントに基づいて変更。
*   `src/runtime/runtime2.go`: `cpuid_ebx7`という新しいグローバル変数を追加し、CPUIDのEBXレジスタの値を保持するように定義。

### `src/runtime/asm_386.s` および `src/runtime/asm_amd64.s` の変更点

CPUID命令を呼び出し、`EAX=7, ECX=0`で得られる`EBX`レジスタの値を`runtime·cpuid_ebx7(SB)`に格納する処理が追加されています。

```asm
// asm_386.s
+	// Load EAX=7/ECX=0 cpuid flags
+	CMPL	SI, $7
+	JLT	nocpuinfo
+	MOVL	$7, AX
+	MOVL	$0, CX
+	CPUID
+	MOVL	BX, runtime·cpuid_ebx7(SB)

// asm_amd64.s
+	// Load EAX=7/ECX=0 cpuid flags
+	CMPQ	SI, $7
+	JLT	no7
+	MOVL	$7, AX
+	MOVL	$0, CX
+	CPUID
+	MOVL	BX, runtime·cpuid_ebx7(SB)
```

### `src/runtime/memmove_386.s` および `src/runtime/memmove_amd64.s` の変更点

`memmove`のフォワードコピー（`forward`ラベル）セクションで、`REP;MOVSB`の使用前にERMS機能とアライメントのチェックが追加されています。

```asm
// memmove_386.s
forward:
+	// If REP MOVSB isn't fast, don't use it
+	TESTL	$(1<<9), runtime·cpuid_ebx7(SB) // erms, aka enhanced REP MOVSB/STOSB
+	JEQ	fwdBy4 // ERMSがなければfwdBy4へ

 	// Check alignment
 	MOVL	SI, AX
 	ORL	DI, AX
 	TESTL	$3, AX
-	JNE	unaligned_fwd // 変更前: アライメントされていなければunaligned_fwdへ
+	JEQ	fwdBy4 // 変更後: アライメントされていればfwdBy4へ

+	// Do 1 byte at a time (ERMSあり、かつアライメントされていない場合)
+	MOVL	BX, CX
+	REP;	MOVSB
+	RET
+
+fwdBy4: // ERMSなし、またはアライメントされている場合
 	// Do 4 bytes at a time
 	MOVL	BX, CX
 	SHRL	$2, CX
 	ANDL	$3, BX
-
 	REP;	MOVSL
 	JMP	tail

-unaligned_fwd: // 変更前はここでREP;MOVSBが使われていた
-	MOVL	BX, CX
-	REP;	MOVSB
-	RET
```

`memmove_amd64.s`も同様のロジックで`fwdBy8`というラベルに分岐し、`REP;MOVSQ`を使用するように変更されています。

### `src/runtime/runtime2.go` の変更点

CPUIDのEBXレジスタの値を保持するための新しいグローバル変数が追加されています。

```go
// runtime2.go
var (
	// Set on startup in asm_{x86,amd64}.s.
	cpuid_ecx         uint32
	cpuid_edx         uint32
+	cpuid_ebx7        uint32 // 新しく追加された変数
	lfenceBeforeRdtsc bool
	support_avx       bool
	support_avx2      bool
)
```

## コアとなるコードの解説

このコミットの核心は、`memmove`関数が実行時にCPUの能力とメモリのアライメント状況を判断し、最も効率的なメモリコピー命令を選択するようになった点です。

1.  **CPUID情報の取得**:
    *   Goランタイムの起動時、`asm_386.s`および`asm_amd64.s`内の初期化コードが`CPUID`命令を実行します。
    *   特に`EAX=7, ECX=0`を指定して`CPUID`を呼び出すことで、拡張機能の情報を取得します。この結果の`EBX`レジスタには、`ERMS`（Enhanced REP MOVSB/STOSB）機能の有無を示すビット9が含まれています。
    *   この`EBX`の値は、`runtime2.go`で定義された`runtime·cpuid_ebx7`というグローバル変数に格納され、Goランタイム全体で利用可能になります。

2.  **`memmove`における条件付き命令選択**:
    *   `memmove_386.s`および`memmove_amd64.s`内の`forward`（順方向コピー）ルーチンでは、まず`runtime·cpuid_ebx7`変数のビット9を`TESTL $(1<<9)`命令でチェックします。
        *   もしビット9がセットされていなければ（`JEQ`命令で`fwdBy4`/`fwdBy8`にジャンプ）、ERMS機能がないと判断し、`REP;MOVSB`は使用しません。この場合、より大きな単位でコピーする`REP;MOVSL`（386）または`REP;MOVSQ`（AMD64）が選択されます。
    *   ERMS機能が有効であると判断された場合、次にソースポインタ（`SI`）とデスティネーションポインタ（`DI`）のアライメントをチェックします。
        *   386アーキテクチャでは`TESTL $3, AX`（4バイトアライメント）、AMD64アーキテクチャでは`TESTL $7, AX`（8バイトアライメント）を用いて、ポインタがアライメント境界に揃っているかを確認します。
        *   もしポインタがアライメントされている場合（`JEQ`命令で`fwdBy4`/`fwdBy8`にジャンプ）、ERMSがあっても`REP;MOVSL`/`REP;MOVSQ`の方が高速であると判断し、そちらを使用します。
    *   最終的に、ERMS機能が有効であり、**かつ**ポインタがアライメントされていない場合にのみ、`REP;MOVSB`命令が使用されます。これは、アライメントされていないデータに対しては`REP;MOVSB`が効率的であり、ERMSによってその性能がさらに最適化されているためです。

このロジックにより、Goランタイムは、CPUのハードウェア特性とメモリの配置状況という二つの重要な要素を考慮に入れ、`memmove`の実行パスを動的に調整することで、様々な環境下での性能を最大化しています。

このコミットは、Go言語のツールチェインの一部である `cmd/api` の `src/cmd/api/goapi.go` ファイルに対する変更です。`cmd/api` ツールは、GoのAPI互換性をチェックするために使用されます。これは、Goの安定性ポリシーにおいて非常に重要な役割を果たしており、新しいGoのリリースで既存のプログラムが壊れないようにするために、APIの変更を厳密に監視します。

`goapi.go` は、Goの標準ライブラリの公開APIを抽出し、以前のバージョンと比較して互換性のない変更がないかを検出するロジックを含んでいます。

## 元コミット内容

このコミットは、コミット `11d1c05` を元に戻す（revert）ものです。元に戻されたコミットのタイトルは「cmd/api: treat a hex-y VERSION as devel and permit API changes」です。

このタイトルと、今回のrevertコミットの差分から推測すると、元のコミット `11d1c05` は以下の変更を導入したと考えられます。

1.  `cmd/api` ツールにおいて、Goのバージョン文字列が「hex-y」（つまり、コミットハッシュのような16進数文字列）である場合に、そのバージョンを「開発版（devel）」として扱うロジックを追加した。
2.  これにより、開発版と認識されたGoのバージョンでは、APIの変更（追加や削除など）が許可されるようになった。通常、安定版のGoではAPIの変更は厳しく制限されますが、開発中のバージョンではある程度の変更が許容されます。

具体的には、`isDevelVersion` という関数が追加され、`runtime.Version()` が返す文字列が `devel` を含むか、または16進数文字列の正規表現 `^[0-9a-f]{7,40}$` にマッチする場合に `true` を返すように変更されたと推測されます。そして、この `isDevelVersion` の結果に基づいて、APIの変更が許可されるかどうかの判断が行われていました。

## 変更の背景

Go言語は、後方互換性を非常に重視しています。特に、公開APIの安定性はGoエコシステム全体の健全性を保つ上で極めて重要です。`cmd/api` ツールは、このAPI互換性を強制するための主要なメカニズムの一つです。

元のコミット `11d1c05` は、おそらく開発ワークフローを円滑にするために導入されました。Goの開発版（`devel` バージョン）では、APIの変更が頻繁に行われる可能性があります。しかし、Goのバージョン文字列が必ずしも `devel` という明示的な文字列を含まない場合（例えば、特定のコミットハッシュでビルドされた場合など）でも、それが開発版であることを `cmd/api` に認識させ、API変更のチェックを緩和する必要があったのかもしれません。これにより、開発者はAPIの変更を伴うコードをより自由にテスト・開発できたと考えられます。

しかし、このコミットがrevertされた背景には、おそらく以下の問題があったと推測されます。

1.  **過度なAPI変更の許可:** 「hex-y」なバージョンを無条件に開発版とみなすことで、意図しないビルド（例えば、リリースブランチから派生した一時的なビルドなど）でもAPI変更が許可されてしまい、API互換性チェックが十分に機能しないリスクがあった。
2.  **バージョニングロジックの複雑化:** バージョン文字列の解釈が複雑になり、どのバージョンが「開発版」でAPI変更が許容されるのか、どのバージョンが「安定版」でAPI変更が許容されないのかの判断が曖昧になった。
3.  **誤検知のリスク:** 意図しない文字列がたまたま16進数文字列のパターンにマッチしてしまい、誤って開発版と認識される可能性があった。

GoのAPI互換性に対する厳格な姿勢を考えると、このような曖昧さやリスクは許容されなかったため、元の変更が元に戻されたと考えられます。コミットメッセージに「See #9296 for details.」とあることから、この問題に関する詳細な議論がIssue #9296で行われたと推測されますが、現時点ではそのIssueの具体的な内容は確認できませんでした。

## 前提知識の解説

### GoのAPI互換性

Go言語は「Go 1 compatibility guarantee」（Go 1互換性保証）を掲げており、Go 1.xのリリース間で既存のGoプログラムが壊れないことを保証しています。これは、Goの採用を促進し、開発者が安心してGoのバージョンアップを行えるようにするための重要な原則です。`cmd/api` ツールは、この互換性保証を維持するために、Goの標準ライブラリの公開APIがリリース間で意図せず変更されていないかを自動的にチェックする役割を担っています。

### `cmd/api` ツール

`cmd/api` は、Goのソースツリーに含まれる内部ツールです。その主な機能は以下の通りです。

*   **APIの抽出:** Goの標準ライブラリのソースコードを解析し、エクスポートされた（公開されている）型、関数、メソッド、変数などのAPIシグネチャを抽出します。
*   **APIの比較:** 抽出した現在のAPIシグネチャを、以前の安定版Goリリース（例えば、Go 1.x）のAPIシグネチャと比較します。
*   **互換性チェック:** 比較の結果、互換性のない変更（例: 公開関数のシグネチャ変更、公開型のフィールド削除、公開関数の削除など）が検出された場合にエラーを報告します。
*   **バージョンに応じた挙動:** 開発版（`devel`）のGoでは、APIの追加は許可されるなど、安定版とは異なるルールでチェックを行います。

### Goのバージョン管理

`runtime.Version()` は、現在実行中のGoプログラムがビルドされたGoのバージョン文字列を返します。Goのバージョン文字列は、通常 `go1.x` のような形式ですが、開発中のバージョンでは `go1.x-yyyy-mm-dd-abcdefgh-devel` のように `devel` やコミットハッシュを含むことがあります。

*   **`weekly` バージョン:** Go 1.xのリリースサイクル中に、毎週リリースされる開発版のビルドを指すことがあります。
*   **`devel` バージョン:** 開発中の最新版を指します。これらのバージョンでは、APIの追加は許可されるものの、既存APIの破壊的変更は通常許可されません。しかし、`cmd/api` の文脈では、`devel` バージョンではAPIの変更に対するチェックが緩和されることがあります。

### 正規表現 (`regexp.MustCompile`)

正規表現は、文字列のパターンを記述するための強力なツールです。`regexp.MustCompile` はGoの `regexp` パッケージの関数で、与えられた文字列を正規表現としてコンパイルします。コンパイルに失敗するとパニック（プログラムのクラッシュ）を引き起こします。

元のコミットでは `hashRx = regexp.MustCompile(`^[0-9a-f]{7,40}$`)` という正規表現が使われていました。これは、文字列が7文字から40文字の間の16進数（0-9, a-f）で構成されているかどうかをチェックするパターンです。これは、Gitのコミットハッシュ（通常40文字の16進数）やその短縮形を識別するために使用されたと考えられます。

## 技術的詳細

このコミットは、`src/cmd/api/goapi.go` ファイルから、Goのバージョン文字列が16進数文字列である場合にそれを開発版（`devel`）として扱うロジックを削除しています。

具体的には、以下の変更が行われました。

1.  **`isDevelVersion` 関数の削除:**
    元のコミットで追加されたと思われる `isDevelVersion` 関数が完全に削除されました。この関数は、Goのバージョン文字列が `devel` を含むか、または `hashRx`（16進数文字列を検出する正規表現）にマッチするかどうかを判断していました。

    ```go
    -var (
    -	internalPkg = regexp.MustCompile(`(^|/)internal($|/)`)
    -	hashRx      = regexp.MustCompile(`^[0-9a-f]{7,40}$`)
    -)
    -
    -func isDevelVersion(v string) bool {
    -	if strings.Contains(v, "devel") {
    -		return true
    -	}
    -	return hashRx.MatchString(v)
    -}
    ```

2.  **バージョンチェックロジックの簡素化:**
    `main` 関数内のバージョンチェックと、`compareAPI` 関数内のAPI変更許可ロジックが簡素化されました。

    *   **`main` 関数内:**
        変更前: `if v := runtime.Version(); !strings.Contains(v, "weekly") && !isDevelVersion(v) { ... }`
        変更後: `if !strings.Contains(runtime.Version(), "weekly") && !strings.Contains(runtime.Version(), "devel") { ... }`
        これにより、`runtime.Version()` が `weekly` または `devel` を含まない場合にのみ、特定の処理（例えば、`-next` ファイルの無視）が行われるようになりました。`isDevelVersion` の呼び出しが削除され、明示的に `devel` 文字列の有無のみをチェックするようになりました。

    *   **`compareAPI` 関数内:**
        変更前: `if !*allowNew || !isDevelVersion(runtime.Version()) { ... }`
        変更後: `if !*allowNew || !strings.Contains(runtime.Version(), "devel") { ... }`
        APIの追加が許可されるかどうかを判断する際に、`isDevelVersion` の代わりに `strings.Contains(runtime.Version(), "devel")` が直接使用されるようになりました。これにより、`devel` バージョンでのみAPIの追加が許可されるという、より厳格なルールに戻されました。

これらの変更により、`cmd/api` ツールは、Goのバージョンが明示的に `weekly` または `devel` とマークされている場合にのみ、開発版としての特別な挙動を示すようになります。単なる16進数文字列を含むバージョンは、もはや開発版とはみなされません。

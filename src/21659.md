# [インデックス 21659] ファイルの概要

このコミットは、Go言語の `crypto/ecdsa` パッケージにおける、ECDSA署名生成時の乱数（nonce）の導出方法に関する以前の変更を元に戻すものです。具体的には、"crypto/ecdsa: make Sign safe with broken entropy sources" というコミット（ハッシュ: `8d7bf2291b095d3a2ecaa2609e1101be46d80deb`）によって導入された、エントロピー源が不完全な場合でも署名の安全性を確保しようとするメカニズムを削除します。この変更により、`ecdsa.Sign` 関数は、以前の、よりシンプルな乱数生成の振る舞いに戻されます。

## 変更の背景

このコミットは、以前のコミット `8d7bf2291b095d3a2ecaa2609e1101be46d80deb` を元に戻すものです。元のコミットは、ECDSA署名生成において、提供される乱数源（エントロピー源）が不完全または予測可能である場合に、署名の安全性を高めることを目的としていました。具体的には、秘密鍵、エントロピー、メッセージハッシュを組み合わせた値から導出された鍵を持つAES-CTRベースのCSPRNG（暗号論的擬似乱数生成器）を使用して、署名に必要なnonce（k値）を生成するメカニズムを導入しました。これは、CoronのIndifferentiability from a Random Oracle (IRO) の結果に基づくとされていました。

しかし、この「安全性を高める」ための変更が、何らかの予期せぬ問題を引き起こしたため、元に戻されることになりました。このような暗号関連の変更が元に戻される一般的な背景としては、以下のような理由が考えられます（このコミットの具体的な理由については、公開された詳細な議論が見つからなかったため、推測が含まれます）：

1.  **性能問題 (Performance Overhead):** 新しい乱数生成メカニズムが、署名操作に許容できないほどの性能劣化をもたらした可能性があります。特に、AES-CTRやSHA-512の計算は、単純な乱数読み取りよりも計算コストが高くなります。
2.  **新たな脆弱性の導入 (Introduction of New Vulnerabilities):** 暗号学的な変更は非常にデリケートであり、意図しないサイドチャネル攻撃の可能性や、理論的な安全性と実装の間のギャップが生じることがあります。導入されたメカニズムが、特定の条件下でnonceの漏洩につながる、あるいは他の暗号学的攻撃を可能にするような、新たな脆弱性を生み出した可能性が考えられます。
3.  **暗号学的仮定の誤り (Incorrect Cryptographic Assumptions):** 導入されたメカニズムが依拠していた暗号学的仮定（例: IROの適用範囲や条件）が、Goの特定の実行環境や使用シナリオにおいて適切でなかった可能性があります。
4.  **複雑性の増加と保守性 (Increased Complexity and Maintainability):** コードの複雑性が増し、将来的な監査や保守が困難になると判断された可能性があります。特に、暗号コードはシンプルさが安全性の鍵となることがあります。
5.  **既存の乱数源の信頼性 (Reliability of Existing Entropy Sources):** Goの標準ライブラリが使用する乱数源（例: `/dev/urandom` や `getrandom` システムコール）が、すでに十分なエントロピーと安全性を保証しており、追加の複雑なメカニズムが不要である、あるいは過剰であると判断された可能性もあります。

このリバートは、Goの暗号ライブラリが、堅牢性と実用性のバランスを重視していることを示唆しています。特に、暗号学的な「改善」が、予期せぬ副作用や新たなリスクをもたらす可能性がある場合、元のシンプルで十分にテストされた実装に戻すことが賢明な判断となることがあります。

## 前提知識の解説

このコミットを理解するためには、以下の前提知識が必要です。

1.  **ECDSA (Elliptic Curve Digital Signature Algorithm):**
    *   楕円曲線暗号に基づくデジタル署名アルゴリズムです。メッセージの認証と非否認性を提供します。
    *   署名生成には、秘密鍵、メッセージのハッシュ値、そして**nonce (k値)** と呼ばれるランダムな秘密の数値が必要です。
    *   **nonceの重要性:** ECDSAにおいて、nonceは非常に重要です。もし同じ秘密鍵で異なるメッセージに対して同じnonceを使用して署名してしまうと、秘密鍵が容易に計算されて漏洩してしまいます。また、nonceが予測可能であったり、十分にランダムでなかったりする場合も、秘密鍵が推測されるリスクがあります。
    *   **RFC 6979:** 決定論的ECDSA署名に関するRFCです。これにより、nonceをメッセージハッシュと秘密鍵から決定論的に導出することで、乱数源の品質に依存しない署名生成が可能になります。Goの`crypto/ecdsa`パッケージは、デフォルトでは決定論的ではありませんが、`rand`パラメータに`nil`を渡すことでRFC 6979に準拠した決定論的署名を生成できます。

2.  **エントロピー源 (Entropy Source):**
    *   暗号学的に安全な乱数を生成するための、予測不可能な情報源です。オペレーティングシステムは通常、ハードウェアイベント（マウスの動き、キーボード入力、ディスクI/O、ネットワークアクティビティなど）からエントロピーを収集し、`/dev/random` や `/dev/urandom` といったデバイスを通じて提供します。
    *   **「壊れたエントロピー源」:** エントロピー源が不十分な場合、生成される乱数が予測可能になったり、偏りを持ったりする可能性があります。これは暗号システムの安全性を著しく損ないます。

3.  **CSPRNG (Cryptographically Secure Pseudorandom Number Generator):**
    *   暗号学的に安全な擬似乱数生成器です。少量の真の乱数（シード）から、統計的にランダムに見え、かつ次の出力が予測不可能な擬似乱数を大量に生成します。
    *   **AES-CTR:** AES（Advanced Encryption Standard）をCTR（Counter Mode）で動作させたものです。CTRモードは、ブロック暗号をストリーム暗号のように動作させ、カウンタ値を暗号化して擬似乱数ストリームを生成します。このストリームと平文をXORすることで暗号化・復号化を行います。CSPRNGの構築にも利用されます。

4.  **Indifferentiability from a Random Oracle (IRO):**
    *   暗号学における概念で、ある構成（例: ハッシュ関数やCSPRNG）が、理想的なランダムオラクル（任意の入力に対して真のランダムな出力を返す仮想的な関数）と区別できないことを意味します。これは、その構成が特定の暗号学的プロトコルにおいて、ランダムオラクルが提供する安全性の保証を維持できることを示唆します。Coronらの研究は、特定の条件下でハッシュ関数がIRO特性を持つことを示しました。

5.  **`io.Reader` インターフェース:**
    *   Go言語の標準ライブラリで定義されているインターフェースで、`Read(p []byte) (n int, err error)` メソッドを持ちます。これは、バイト列を読み取るための汎用的なインターフェースであり、乱数源（例: `crypto/rand.Reader`）もこのインターフェースを実装しています。

## 技術的詳細

このリバートコミットは、`src/crypto/ecdsa/ecdsa.go` ファイル内の `Sign` 関数から、nonce生成に関する複雑なロジックを削除しています。

元のコミット `8d7bf2291b095d3a2ecaa2609e1101be46d80deb` では、`Sign` 関数内で以下のステップが追加されていました。

1.  **エントロピーの収集:** `rand` 引数から、曲線サイズに応じた長さ（最大32バイト）のエントロピーを読み取ります。
2.  **CSPRNGキーの導出:**
    *   `priv.D` (秘密鍵のスカラ値)、収集したエントロピー、およびメッセージの `hash` を連結し、SHA-512ハッシュを計算します。
    *   このSHA-512ハッシュの最初の32バイトを、AES-CTR CSPRNGの鍵として使用します。これは、ChopMD-256(SHA-512) と呼ばれる手法で、Indifferentiable MAC（メッセージ認証コード）として機能すると説明されていました。
3.  **AES-CTR CSPRNGの初期化:** 上記で導出した鍵と固定のIV (`aesIV = "IV for ECDSA CTR"`) を使用して、AES-CTRストリーム暗号を初期化します。
4.  **nonceの生成:** このAES-CTR CSPRNGを `csprng` としてラップし、`randFieldElement` 関数に渡してnonce `k` を生成します。これにより、`k` の生成が、提供されたエントロピーだけでなく、秘密鍵とメッセージハッシュにも依存するようになります。
5.  **`zeroReader` の導入:** `zr` という構造体と `zeroReader` というグローバル変数が導入され、`Read` メソッドが常にゼロバイトを返すように実装されていました。これは、`cipher.StreamReader` の `R` フィールドに渡され、AES-CTRストリームの出力をそのまま利用するためのものでした。

このリバートコミットは、上記のステップで追加されたコード（`aes`、`cipher`、`sha512` のインポート、`aesIV` 定数、CSPRNGの初期化ロジック、`zeroReader` 関連のコード）をすべて削除します。

結果として、`Sign` 関数内のnonce生成は、元のシンプルな形式に戻ります。つまり、`randFieldElement` 関数は、`Sign` 関数に直接渡された `rand io.Reader` から乱数を読み取ってnonce `k` を生成するようになります。これにより、nonceのランダム性は、純粋に `rand` 引数として提供される乱数源の品質に依存することになります。

`src/crypto/ecdsa/ecdsa_test.go` からも、`TestNonceSafety` と `TestINDCCA` というテスト関数が削除されています。これらのテストは、元のコミットで導入されたnonce生成メカニズムの安全性（異なるメッセージや同じメッセージに対する異なるnonceの生成）を検証するためのものでした。メカニズムが削除されたため、これらのテストも不要となり削除されました。

## コアとなるコードの変更箇所

### `src/crypto/ecdsa/ecdsa.go`

*   `crypto/aes`, `crypto/cipher`, `crypto/sha512` のインポートが削除されました。
*   `aesIV` 定数と、`zeroReader` 関連の構造体 `zr` および変数 `zeroReader` が削除されました。
*   `Sign` 関数内の、エントロピーの収集、SHA-512ハッシュによる鍵導出、AES-CTR CSPRNGの初期化、および `csprng` を使用して `randFieldElement` を呼び出すロジックがすべて削除されました。
*   `randFieldElement` の呼び出しが `k, err = randFieldElement(c, csprng)` から `k, err = randFieldElement(c, rand)` に変更され、直接 `Sign` 関数に渡された `rand` リーダーを使用するように戻されました。

### `src/crypto/ecdsa/ecdsa_test.go`

*   `testNonceSafety` 関数と `TestNonceSafety` 関数が削除されました。
*   `testINDCCA` 関数と `TestINDCCA` 関数が削除されました。

## コアとなるコードの解説

このコミットのコアとなる変更は、`ecdsa.go` の `Sign` 関数におけるnonce `k` の生成方法の根本的な変更を元に戻した点にあります。

**変更前（元コミット導入後）の `Sign` 関数内のnonce生成ロジック:**

```go
// ...
	// Get max(log2(q) / 2, 256) bits of entropy from rand.
	entropylen := (priv.Curve.Params().BitSize + 7) / 16
	if entropylen > 32 {
		entropylen = 32
	}
	entropy := make([]byte, entropylen)
	_, err = rand.Read(entropy)
	if err != nil {
		return
	}

	// Initialize an SHA-512 hash context; digest ...
	md := sha512.New()
	md.Write(priv.D.Bytes()) // the private key,
	md.Write(entropy)        // the entropy,
	md.Write(hash)           // and the input hash;
	key := md.Sum(nil)[:32]  // and compute ChopMD-256(SHA-512),
	// which is an indifferentiable MAC.

	// Create an AES-CTR instance to use as a CSPRNG.
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, nil, err
	}

	// Create a CSPRNG that xors a stream of zeros with
	// the output of the AES-CTR instance.
	csprng := cipher.StreamReader{
		R: zeroReader,
		S: cipher.NewCTR(block, []byte(aesIV)),
	}

	// See [NSA] 3.4.1
	c := priv.PublicKey.Curve
	N := c.Params().N
	// ...
	for {
		for {
			k, err = randFieldElement(c, csprng) // ここでcsprngを使用
			if err != nil {
				r = nil
				return
			}
// ...
```

このコードは、提供された `rand` リーダーからのエントロピー、秘密鍵 `priv.D`、およびメッセージハッシュ `hash` を組み合わせて、SHA-512ハッシュからAES-CTR CSPRNGの鍵を導出していました。そして、このCSPRNGからnonce `k` を生成することで、たとえ初期のエントロピー源が弱くても、nonceが予測不可能になるように設計されていました。これは、ECDSAのnonceが予測可能であることによる秘密鍵漏洩のリスクを軽減するための試みでした。

**変更後（このリバートコミット適用後）の `Sign` 関数内のnonce生成ロジック:**

```go
// ...
	// See [NSA] 3.4.1
	c := priv.PublicKey.Curve
	N := c.Params().N
	// ...
	var k, kInv *big.Int
	for {
		for {
			k, err = randFieldElement(c, rand) // ここで直接randを使用
			if err != nil {
				r = nil
				return
			}
// ...
```

このリバートにより、`Sign` 関数は、`rand` 引数として渡された `io.Reader` から直接乱数を読み取ってnonce `k` を生成する元の振る舞いに戻りました。つまり、nonceの安全性は、完全に `Sign` 関数に渡される `rand` リーダーの品質に依存するようになります。

この変更は、元の「安全性を高める」メカニズムが、何らかの理由でGoの暗号ライブラリの設計目標に合致しなかった、あるいは予期せぬ問題を引き起こしたと判断されたことを強く示唆しています。暗号学的な変更は、理論的な正しさと実装上の安全性、そして性能のバランスが非常に重要であり、このリバートはそのバランスを再調整した結果であると考えられます。

テストファイルからの関連テストの削除は、このメカニズムがもはや存在しないため、その動作を検証するテストも不要になったことを意味します。

# [インデックス 20037] ファイルの概要

このコミットは、Goコンパイラの`cmd/6c`（Cコンパイラ）と`cmd/6g`（Goコンパイラ）において、AMD64アーキテクチャでの命令における「アドレスを定数として扱う」挙動を回避するための変更です。これにより、グローバル変数のアドレス参照が、32ビット整数定数としてではなく、PC相対アドレスとして実装されるようになります。

## 元コミット内容

このコミットの目的は、Goコンパイラ（`cmd/6g`）とGoのCコンパイラ（`cmd/6c`）がAMD64アーキテクチャ向けに生成するコードにおいて、命令内でアドレスを直接定数として埋め込むことを避けることです。これにより、グローバル変数のアドレス参照が、固定の32ビット整数定数ではなく、PC（プログラムカウンタ）相対アドレスとして実装されるようになります。

## 変更の背景

この変更の背景には、AMD64アーキテクチャにおけるコード生成の効率性と柔軟性の向上が挙げられます。

1.  **位置独立コード (PIC) の重要性**: 現代のオペレーティングシステムでは、共有ライブラリ（DLLや.soファイル）が広く利用されています。これらのライブラリは、プログラムが実行されるたびに異なるメモリ位置にロードされる可能性があります。アドレスを直接定数として命令に埋め込むと、ライブラリがロードされるたびにそのアドレスを修正（再配置）する必要が生じ、起動時間やメモリ効率に悪影響を与えます。PC相対アドレッシングを使用することで、コードはメモリ上のどこにロードされても正しく動作する「位置独立」となり、再配置の必要がなくなります。

2.  **AMD64におけるRIP相対アドレッシング**: AMD64（x86-64）アーキテクチャでは、RIP（Instruction Pointer、命令ポインタ）相対アドレッシングという強力な機能が導入されました。これは、メモリ上のデータやコードへの参照を、現在の命令ポインタからの相対オフセットとして表現するものです。これにより、64ビットの広大なアドレス空間を効率的に利用しつつ、位置独立性を容易に実現できます。

3.  **`flag_largemodel` の廃止**: 以前のGoコンパイラには、`flag_largemodel`というフラグが存在し、これが有効な場合に異なるコード生成戦略が取られていました。このフラグは、特定のメモリモデルや、Google Native Client (NaCl) のような特殊な環境向けに設計されていた可能性があります。しかし、AMD64のRIP相対アドレッシングが標準的かつ効率的なアプローチとして確立されるにつれて、このような特殊なモデルを区別する必要性が薄れました。このコミットは、`flag_largemodel`による条件分岐を削除し、より統一されたPC相対アドレッシング戦略に移行することで、コードベースの簡素化と最適化を図っています。

この変更により、GoプログラムはAMD64システム上でより効率的かつ堅牢に動作し、特に大規模なアプリケーションや共有ライブラリの利用においてパフォーマンス上のメリットを享受できるようになります。

## 前提知識の解説

### AMD64 (x86-64) アーキテクチャ

AMD64は、Intelのx86命令セットを64ビットに拡張したものです。これにより、より大きなメモリ空間（理論上は16エクサバイト）を直接アドレス指定できるようになり、より多くの汎用レジスタが利用可能になりました。現代のほとんどのデスクトップPCやサーバーで採用されている主要な64ビットアーキテクチャです。

### PC相対アドレッシング (RIP相対アドレッシング)

PC相対アドレッシングは、メモリ上のデータやコードへのアクセスにおいて、その絶対アドレスを直接指定するのではなく、現在のプログラムカウンタ（PC、AMD64ではRIPレジスタ）からの相対的なオフセットでアドレスを計算する方式です。

*   **仕組み**: 命令には、参照したいメモリ位置までのオフセット値が埋め込まれています。CPUがその命令を実行する際、自身のRIPレジスタの値（現在の命令のアドレス、または次の命令のアドレス）にこのオフセット値を加算することで、目的のメモリアドレスを算出します。
*   **利点**:
    *   **位置独立性 (Position-Independent Code - PIC)**: コードがメモリ上のどこにロードされても、相対的なオフセットは変わらないため、再配置なしで実行できます。これは共有ライブラリにとって不可欠です。
    *   **コードサイズの削減**: 多くの命令では、フル64ビットの絶対アドレスを埋め込むよりも、相対オフセットの方が少ないビット数で表現できるため、命令のサイズが小さくなります。
    *   **効率的な再配置**: プログラムのロード時に、リンカが絶対アドレスを修正する必要がなくなるため、起動が速くなります。

### アドレスを定数として扱うことの課題

命令内にメモリのアドレスを直接定数（リテラル）として埋め込む方式は、コードが特定のメモリ位置に固定されることを意味します。

*   **課題**:
    *   **再配置の必要性**: プログラムが異なるメモリ位置にロードされるたびに、その命令内の定数アドレスを修正する必要があります。これはリンカやローダーの負担となり、特に共有ライブラリではパフォーマンスのボトルネックになります。
    *   **アドレス空間の制約**: 32ビットの定数で表現できるアドレス範囲には限りがあり、64ビットの広大なアドレス空間を効率的に利用できません。

### Goコンパイラ (`6c`, `6g`)

Go言語のツールチェーンにおいて、`cmd/6c`と`cmd/6g`はそれぞれGoのCコンパイラとGoコンパイラを指します。これらはGoのソースコードを機械語に変換する役割を担っており、コード生成の段階で、どのようにメモリ参照を扱うかを決定します。

### `flag_largemodel`

`flag_largemodel`は、Goコンパイラの古いバージョンに存在した内部フラグです。このフラグが設定されているかどうかによって、コンパイラが生成するコードのメモリモデルが異なっていました。具体的には、より大きなアドレス空間を扱うための特別なコード生成パスを有効にするものでした。しかし、AMD64のRIP相対アドレッシングが標準的なアプローチとして普及し、Goコンパイラがこれを全面的に採用するにつれて、このような特殊なメモリモデルを区別する必要性がなくなり、コードベースから削除されることになりました。このコミットは、その削除プロセスの一部として、`flag_largemodel`に基づく条件分岐を排除しています。

## 技術的詳細

このコミットの技術的な核心は、AMD64アーキテクチャにおけるグローバルデータへのアクセス方法を、従来の「アドレスを定数として埋め込む」方式から「PC相対アドレッシング」方式へと統一することにあります。これは、主に`flag_largemodel`というコンパイラフラグによる条件分岐を削除することで実現されています。

具体的には、以下の3つのファイルが変更されています。

1.  **`src/cmd/6c/sgen.c`**:
    *   `xcom`関数は、GoのCコンパイラにおけるノードのプロパティ（`addable`）を設定する役割を担っています。
    *   以前は、`ONAME`（名前付きオブジェクト、変数など）の場合に`flag_largemodel`の有無によって`n->addable`の値が`9`または`10`に分岐していました。`addable`は、そのノードがアドレス計算においてどのように扱われるかを示す内部的なフラグです。
    *   このコミットでは、`flag_largemodel`による条件分岐が削除され、常に`n->addable = 9`が設定されるようになりました。これは、`flag_largemodel`が示す「ラージモデル」の挙動が、PC相対アドレッシングを前提とした新しい統一されたモデルに統合されたことを意味します。

2.  **`src/cmd/6g/cgen.c`**:
    *   `agenr`関数は、Goコンパイラにおけるアドレス生成（address generation）を担当しています。特に、文字列リテラルなどのデータへの参照を生成する際に使用されます。
    *   以前は、`flag_largemodel`が有効な場合に`AADDQ`命令（64ビット加算）を使用してアドレスを計算し、そうでない場合は`p1->from.scale`と`p1->from.index`を設定して異なるアドレッシングモードを使用していました。後者のパスは、おそらく32ビットオフセットや異なるベースレジスタの利用を意図していたと考えられます。
    *   このコミットでは、`flag_largemodel`による条件分岐が削除され、常に`gins(AADDQ, &n2, &n3);`が実行されるようになりました。これは、データへの参照が常に`AADDQ`命令を用いたPC相対アドレッシング（またはそれに準ずる形式）で処理されることを意味し、コード生成パスが簡素化・統一されました。

3.  **`src/cmd/6g/gsubr.c`**:
    *   `ismem`関数は、Goコンパイラにおいて、与えられたノードがメモリ参照であるかどうかを判断するヘルパー関数です。
    *   以前は、`OADDR`（アドレス演算子）の場合に`flag_largemodel`の有無によって`return 1`（メモリ参照である）かどうかが分岐していました。
    *   このコミットでは、`flag_largemodel`による条件分岐が削除され、`OADDR`の場合も常に`return 1`が返されるようになりました。これは、アドレス演算子が常にメモリ参照として扱われるべきであり、`flag_largemodel`の有無によってその挙動を変える必要がなくなったことを示しています。

これらの変更は、GoコンパイラがAMD64アーキテクチャ向けに生成するコードにおいて、グローバルデータや文字列リテラルへの参照を、より現代的で効率的なPC相対アドレッシングに統一し、古い`flag_largemodel`に依存する複雑なコードパスを排除することを目的としています。これにより、コンパイラのコードベースが簡素化され、生成されるバイナリのパフォーマンスと位置独立性が向上します。

## コアとなるコードの解説

### `src/cmd/6c/sgen.c` の変更

`xcom`関数は、コンパイラが抽象構文木（AST）のノードを走査し、コード生成に必要なプロパティを設定する際に呼び出されます。
変更前は、`ONAME`（変数名や関数名などのシンボル）を処理する際に、`flag_largemodel`というコンパイラフラグの状態に応じて、ノードの`addable`プロパティに`9`または`10`を設定していました。`addable`は、そのシンボルがアドレス計算においてどのように扱われるか（例：直接アドレス指定可能か、レジスタ経由かなど）を示す内部的な値です。
変更後は、`flag_largemodel`による条件分岐が削除され、常に`n->addable = 9`が設定されるようになりました。これは、GoコンパイラがAMD64アーキテクチャにおいて、`ONAME`の参照を常にPC相対アドレッシングに適した方法で処理するよう統一されたことを意味します。

### `src/cmd/6g/cgen.c` の変更

`agenr`関数は、Goコンパイラがアドレスを生成する際の中心的なロジックを含んでいます。特に、文字列リテラルなどの静的データへの参照を生成する部分に影響があります。
変更前は、`datastring`でデータが配置された後、`flag_largemodel`の有無によって異なるアドレス計算ロジックが適用されていました。`flag_largemodel`が有効な場合は`AADDQ`命令（64ビット加算）を用いてアドレスを計算していましたが、そうでない場合は`p1->from.scale = 1; p1->from.index = n2.val.u.reg;`という形で、異なるアドレッシングモード（おそらくベースレジスタとスケールされたインデックスレジスタを使用する形式）が使われていました。
変更後は、`flag_largemodel`による条件分岐が完全に削除され、常に`gins(AADDQ, &n2, &n3);`が実行されるようになりました。これは、データへの参照が常に`AADDQ`命令（通常はRIP相対アドレッシングと組み合わせて使用される）によって処理されることを意味し、コード生成パスが簡素化され、PC相対アドレッシングへの依存が強化されました。

### `src/cmd/6g/gsubr.c` の変更

`ismem`関数は、Goコンパイラが特定のノードがメモリ参照であるかどうかを判断するために使用するヘルパー関数です。
変更前は、`OADDR`（アドレス取得演算子、例：`&x`）の場合に、`flag_largemodel`の有無によって`return 1`（メモリ参照である）かどうかの判断が分岐していました。これは、`flag_largemodel`が有効な場合にのみ`OADDR`がメモリ参照として扱われることを示唆していました。
変更後は、`flag_largemodel`による条件分岐が削除され、`OADDR`の場合も常に`return 1`が返されるようになりました。これは、アドレス取得演算子が常にメモリ参照として扱われるべきであり、`flag_largemodel`の有無によってその挙動を変える必要がなくなったことを示しています。これにより、アドレス取得のセマンティクスが統一され、コンパイラのロジックが簡素化されました。

これらの変更は全体として、GoコンパイラがAMD64アーキテクチャ向けに生成するコードにおいて、アドレス参照の処理をPC相対アドレッシングに統一し、古いメモリモデルに依存する複雑な条件分岐を排除することで、コードの効率性、位置独立性、およびコンパイラ自体の保守性を向上させています。

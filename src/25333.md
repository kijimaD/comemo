# [インデックス 25333] ファイルの概要

このコミットは、Goコンパイラにおける型スイッチ（type switch）の短縮変数宣言に関するバグ修正です。具体的には、型スイッチ内で宣言される変数の名前が、以前に定数として宣言されていた場合に「無効な変数名」として誤って拒否される問題を解決します。この修正により、コンパイラは定数名が短縮変数宣言で再利用されることを正しく許可するようになります。

## 元コミット内容

Goコンパイラ (`cmd/compile`) において、型スイッチの短縮変数宣言で、定数名が変数名として使用された場合に「無効な変数名 x」というエラーが発生する問題を修正します。

この問題は、型スイッチの短縮変数宣言が、使用される変数が `ONAME` (通常の変数名)、`OTYPE` (型名)、または `ONONAME` (匿名変数) のいずれかの有効な形式であるかをチェックし、それ以外を拒否していたために発生しました。しかし、宣言に含まれるシンボルが名前付きの `OLITERAL` (定数) であった場合、それは有効な識別子であるにもかかわらず、このチェックによって拒否されていました。実際には新しい変数が宣言されるため、これは誤った拒否でした。

この修正は、チェックに `OLITERAL` かつ `Name` が `nil` でないケースを追加することで、この問題を解決します。また、`issue12413` からテストケースが追加されています。

## 変更の背景

Go言語では、`switch` ステートメント内で短縮変数宣言 (`:=`) を使用して、スイッチの対象となる値の型アサーションの結果を新しい変数にバインドすることができます。これは特に型スイッチ (`switch x := y.(type)`) で強力な機能です。

問題の背景には、Goコンパイラの字句解析および構文解析の段階でのシンボル（識別子）の扱いがあります。コンパイラはコードを解析する際に、各要素を抽象構文木（AST）のノードとして表現します。このノードには `Op` (オペレーション) フィールドがあり、そのノードが何を表すかを示します。

- `ONAME`: 通常の変数や関数名などの識別子。
- `OTYPE`: 型名。
- `ONONAME`: 匿名変数（`_`）。
- `OLITERAL`: リテラル値（数値、文字列、真偽値など）。

Goコンパイラは、型スイッチの短縮変数宣言において、新しい変数を宣言する際に、その変数名が有効な識別子であるかを検証するロジックを持っていました。この検証ロジックが不完全であり、既存の定数名（`OLITERAL`として扱われる）が新しい変数名として使用されるケースを適切に処理できていませんでした。

具体的には、`const x = 42` のように `x` が定数として宣言されている状況で、`switch x := interface{}(nil).(type)` のように `x` を型スイッチの短縮変数宣言で再利用しようとすると、コンパイラは `x` が `ONAME`、`OTYPE`、`ONONAME` のいずれでもないため、無効な変数名としてエラーを報告していました。しかし、この `x` は新しいスコープで宣言される新しい変数であり、既存の定数 `x` とは異なるため、本来は許可されるべきでした。

このバグは、Go言語の柔軟な変数宣言とスコープのルールに反するものであり、開発者の意図しないコンパイルエラーを引き起こしていました。

## 前提知識の解説

### Goコンパイラの構造 (cmd/compile)

Goコンパイラ (`cmd/compile`) は、Go言語のソースコードを機械語に変換するツールです。その内部は複数のステージに分かれており、このコミットが関連するのは主に字句解析、構文解析、および意味解析の初期段階です。

- **字句解析 (Lexical Analysis)**: ソースコードをトークン（識別子、キーワード、演算子など）のストリームに変換します。
- **構文解析 (Syntax Analysis)**: トークンのストリームを解析し、プログラムの構造を抽象構文木（AST）として構築します。Goコンパイラでは、Yacc (Yet Another Compiler Compiler) のGo実装である `go.y` ファイルが構文規則を定義し、`y.go` がその定義から生成されます。
- **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、スコープ解決、名前解決などの意味的な検証を行います。

### Yacc/Bison と `go.y` / `y.go`

Yacc (またはそのGNU版であるBison) は、文法定義からパーサー（構文解析器）を生成するツールです。Goコンパイラでは、`src/cmd/compile/internal/gc/go.y` がGo言語の文法規則を定義するYacc形式のファイルです。この `go.y` ファイルを基に、`y.go` というGo言語のソースファイルが生成されます。`y.go` には、`go.y` で定義された文法規則に従って入力トークンを解析するためのGoコードが含まれています。

コミットで変更されている `go.y` と `y.go` は、Go言語の構文解析ロジックの核心部分に位置します。

### 抽象構文木 (AST) と `Node.Op`

コンパイラはソースコードを解析する際に、プログラムの構造をツリー状のデータ構造である抽象構文木（AST）として表現します。ASTの各ノードは、プログラムの特定の要素（変数宣言、式、ステートメントなど）を表します。

GoコンパイラのASTノードには、そのノードが表す要素の種類を示す `Op` フィールドがあります。
- `ONAME`: 識別子（変数名、関数名など）。
- `OTYPE`: 型名。
- `ONONAME`: 匿名変数 `_`。
- `OLITERAL`: リテラル値（例: `10`, `"hello"`, `true`）。

このコミットの文脈では、`OLITERAL` は定数値を表すノードですが、その定数に名前が付けられている場合（例: `const x = 42` の `x`）、その名前自体は識別子として有効です。問題は、コンパイラが `OLITERAL` ノードを、短縮変数宣言で有効な識別子として認識していなかった点にありました。

### 型スイッチ (Type Switch)

Go言語の型スイッチは、インターフェース値の動的な型を検査し、その型に基づいて異なる処理を実行するための制御構造です。

```go
switch v := i.(type) {
case int:
    fmt.Printf("i is an int, its value is %d\n", v)
case string:
    fmt.Printf("i is a string, its value is %s\n", v)
default:
    fmt.Printf("i is of type %T\n", v)
}
```

ここで `v := i.(type)` の部分が短縮変数宣言です。`i` の具体的な型が `int` であれば、`v` は `int` 型の変数として宣言され、`i` の値が `v` に代入されます。このコミットのバグは、この `v` の部分に既存の定数名が使われた場合に発生していました。

## 技術的詳細

問題は、`go.y` ファイル内の `simple_stmt` (単純なステートメント) の定義、特に型スイッチの短縮変数宣言を処理する部分にありました。

元のコードでは、型スイッチの短縮変数宣言 (`x := i.(type)`) において、`x` に対応するASTノードの `Op` が `ONAME`、`OTYPE`、`ONONAME` のいずれかであるかをチェックしていました。これら以外の `Op` の場合、`Yyerror` 関数を呼び出して「無効な変数名」エラーを報告していました。

しかし、`const x = 42` のように `x` が定数として宣言されている場合、その `x` はコンパイラの内部では `OLITERAL` ノードとして扱われます。この `OLITERAL` ノードは、その値だけでなく、名前（`Name` フィールド）を持つことができます。型スイッチの短縮変数宣言では、新しいスコープで新しい変数 `x` が宣言されるため、既存の定数 `x` の名前を再利用することはGoの言語仕様上問題ありません。

元のチェック `($1.N.Op != ONAME && $1.N.Op != OTYPE && $1.N.Op != ONONAME)` は、`OLITERAL` を有効な変数名として認識していなかったため、誤ってエラーを発生させていました。

修正は、この条件に `($1.N.Op != OLITERAL || $1.N.Name == nil)` という部分を追加することで、`OLITERAL` であっても `Name` が `nil` でない（つまり名前付きリテラルである）場合は有効な変数名として扱うように変更しました。

- `ONAME`: 通常の変数名。これは常に有効。
- `OTYPE`: 型名。これは常に有効。
- `ONONAME`: 匿名変数 `_`。これは常に有効。
- `OLITERAL` かつ `Name` が `nil` でない: 名前付き定数。これは新しい変数名として有効。

この修正により、コンパイラは `OLITERAL` ノードが名前を持つ場合に、それを型スイッチの短縮変数宣言における有効な識別子として正しく認識できるようになりました。

## コアとなるコードの解説

変更の中心は、`go.y` ファイル内の `simple_stmt` ルールに関連するアクションブロックです。このブロックは、型スイッチの短縮変数宣言の左辺（新しい変数名）が有効であるかをチェックしています。

元のコードの条件式:
```go
($1.N.Op != ONAME && $1.N.Op != OTYPE && $1.N.Op != ONONAME) || isblank($1.N)
```
これは、「ノードのオペレーションが `ONAME`、`OTYPE`、`ONONAME` のいずれでもない」または「ノードがブランク識別子 (`_`) である」場合にエラーを発生させる、という意味です。`isblank($1.N)` は `_` をチェックする関数です。

修正後のコードの条件式:
```go
($1.N.Op != ONAME && $1.N.Op != OTYPE && $1.N.Op != ONONAME && ($1.N.Op != OLITERAL || $1.N.Name == nil)) || isblank($1.N)
```
この変更で追加されたのは `&& ($1.N.Op != OLITERAL || $1.N.Name == nil)` の部分です。
この追加された条件は次のように解釈できます。
- `($1.N.Op != OLITERAL || $1.N.Name == nil)`:
    - もしノードのオペレーションが `OLITERAL` でない場合、この部分は `true` となり、元の条件式に影響を与えません。
    - もしノードのオペレーションが `OLITERAL` である場合、`$1.N.Op != OLITERAL` は `false` となります。このとき、`$1.N.Name == nil` の評価が重要になります。
        - `$1.N.Name == nil` が `true` の場合（つまり、名前のないリテラル、例: `42` そのもの）、この追加条件全体は `true` となります。これは、名前のないリテラルを短縮変数宣言の左辺に使うことはできないため、エラーを継続させる正しい挙動です。
        - `$1.N.Name == nil` が `false` の場合（つまり、名前付きリテラル、例: `const x = 42` の `x`）、この追加条件全体は `false` となります。これにより、`OLITERAL` かつ名前付きのリテラルは、エラー条件から除外され、有効な変数名として扱われるようになります。

要するに、この修正は「`ONAME`、`OTYPE`、`ONONAME` ではない、かつ、名前付きの `OLITERAL` でもない」場合にエラーとする、というロジックに変更したことになります。これにより、名前付きの `OLITERAL` が短縮変数宣言の左辺として正しく認識されるようになりました。

`y.go` の変更は、`go.y` から生成されたコードであるため、`go.y` の変更がそのまま反映されています。

新規追加された `test/fixedbugs/issue12413.go` は、このバグを再現し、修正が正しく適用されたことを検証するためのものです。`const x = 42` の後に `switch x := interface{}(nil).(type)` を記述することで、以前はコンパイルエラーになっていたコードが、修正後は正常にコンパイルされることを確認します。

## 元コミット内容

Goコンパイラ (`cmd/compile`) において、型スイッチの短縮変数宣言で、定数名が変数名として使用された場合に「無効な変数名 x」というエラーが発生する問題を修正します。

この問題は、型スイッチの短縮変数宣言が、使用される変数が `ONAME` (通常の変数名)、`OTYPE` (型名)、または `ONONAME` (匿名変数) のいずれかの有効な形式であるかをチェックし、それ以外を拒否していたために発生しました。しかし、宣言に含まれるシンボルが名前付きの `OLITERAL` (定数) であった場合、それは有効な識別子であるにもかかわらず、このチェックによって拒否されていました。実際には新しい変数が宣言されるため、これは誤った拒否でした。

この修正は、チェックに `OLITERAL` かつ `Name` が `nil` でないケースを追加することで、この問題を解決します。また、`issue12413` からテストケースが追加されています。

## 変更の背景

Go言語では、`switch` ステートメント内で短縮変数宣言 (`:=`) を使用して、スイッチの対象となる値の型アサーションの結果を新しい変数にバインドすることができます。これは特に型スイッチ (`switch x := y.(type)`) で強力な機能です。

問題の背景には、Goコンパイラの字句解析および構文解析の段階でのシンボル（識別子）の扱いがあります。コンパイラはコードを解析する際に、各要素を抽象構文木（AST）のノードとして表現します。このノードには `Op` (オペレーション) フィールドがあり、そのノードが何を表すかを示します。

- `ONAME`: 通常の変数や関数名などの識別子。
- `OTYPE`: 型名。
- `ONONAME`: 匿名変数（`_`）。
- `OLITERAL`: リテラル値（数値、文字列、真偽値など）。

Goコンパイラは、型スイッチの短縮変数宣言において、新しい変数を宣言する際に、その変数名が有効な識別子であるかを検証するロジックを持っていました。この検証ロジックが不完全であり、既存の定数名（`OLITERAL`として扱われる）が新しい変数名として使用されるケースを適切に処理できていませんでした。

具体的には、`const x = 42` のように `x` が定数として宣言されている状況で、`switch x := interface{}(nil).(type)` のように `x` を型スイッチの短縮変数宣言で再利用しようとすると、コンパイラは `x` が `ONAME`、`OTYPE`、`ONONAME` のいずれでもないため、無効な変数名としてエラーを報告していました。しかし、この `x` は新しいスコープで宣言される新しい変数であり、既存の定数 `x` とは異なるため、本来は許可されるべきでした。

このバグは、Go言語の柔軟な変数宣言とスコープのルールに反するものであり、開発者の意図しないコンパイルエラーを引き起こしていました。

## 前提知識の解説

### Goコンパイラの構造 (cmd/compile)

Goコンパイラ (`cmd/compile`) は、Go言語のソースコードを機械語に変換するツールです。その内部は複数のステージに分かれており、このコミットが関連するのは主に字句解析、構文解析、および意味解析の初期段階です。

- **字句解析 (Lexical Analysis)**: ソースコードをトークン（識別子、キーワード、演算子など）のストリームに変換します。
- **構文解析 (Syntax Analysis)**: トークンのストリームを解析し、プログラムの構造を抽象構文木（AST）として構築します。Goコンパイラでは、Yacc (Yet Another Compiler Compiler) のGo実装である `go.y` ファイルが構文規則を定義し、`y.go` がその定義から生成されます。
- **意味解析 (Semantic Analysis)**: ASTを走査し、型チェック、スコープ解決、名前解決などの意味的な検証を行います。

### Yacc/Bison と `go.y` / `y.go`

Yacc (またはそのGNU版であるBison) は、文法定義からパーサー（構文解析器）を生成するツールです。Goコンパイラでは、`src/cmd/compile/internal/gc/go.y` がGo言語の文法規則を定義するYacc形式のファイルです。この `go.y` ファイルを基に、`y.go` というGo言語のソースファイルが生成されます。`y.go` には、`go.y` で定義された文法規則に従って入力トークンを解析するためのGoコードが含まれています。

コミットで変更されている `go.y` と `y.go` は、Go言語の構文解析ロジックの核心部分に位置します。

### 抽象構文木 (AST) と `Node.Op`

コンパイラはソースコードを解析する際に、プログラムの構造をツリー状のデータ構造である抽象構文木（AST）として表現します。ASTの各ノードは、プログラムの特定の要素（変数宣言、式、ステートメントなど）を表します。

GoコンパイラのASTノードには、そのノードが表す要素の種類を示す `Op` フィールドがあります。
- `ONAME`: 識別子（変数名、関数名など）。
- `OTYPE`: 型名。
- `ONONAME`: 匿名変数 `_`。
- `OLITERAL`: リテラル値（例: `10`, `"hello"`, `true`）。

このコミットの文脈では、`OLITERAL` は定数値を表すノードですが、その定数に名前が付けられている場合（例: `const x = 42` の `x`）、その名前自体は識別子として有効です。問題は、コンパイラが `OLITERAL` ノードを、短縮変数宣言で有効な識別子として認識していなかった点にありました。

### 型スイッチ (Type Switch)

Go言語の型スイッチは、インターフェース値の動的な型を検査し、その型に基づいて異なる処理を実行するための制御構造です。

```go
switch v := i.(type) {
case int:
    fmt.Printf("i is an int, its value is %d\n", v)
case string:
    fmt.Printf("i is a string, its value is %s\n", v)
default:
    fmt.Printf("i is of type %T\n", v)
}
```

ここで `v := i.(type)` の部分が短縮変数宣言です。`i` の具体的な型が `int` であれば、`v` は `int` 型の変数として宣言され、`i` の値が `v` に代入されます。このコミットのバグは、この `v` の部分に既存の定数名が使われた場合に発生していました。

## 技術的詳細

問題は、`go.y` ファイル内の `simple_stmt` (単純なステートメント) の定義、特に型スイッチの短縮変数宣言を処理する部分にありました。

元のコードでは、型スイッチの短縮変数宣言 (`x := i.(type)`) において、`x` に対応するASTノードの `Op` が `ONAME`、`OTYPE`、`ONONAME` のいずれかであるかをチェックしていました。これら以外の `Op` の場合、`Yyerror` 関数を呼び出して「無効な変数名」エラーを報告していました。

しかし、`const x = 42` のように `x` が定数として宣言されている場合、その `x` はコンパイラの内部では `OLITERAL` ノードとして扱われます。この `OLITERAL` ノードは、その値だけでなく、名前（`Name` フィールド）を持つことができます。型スイッチの短縮変数宣言では、新しいスコープで新しい変数 `x` が宣言されるため、既存の定数 `x` の名前を再利用することはGoの言語仕様上問題ありません。

元のチェック `($1.N.Op != ONAME && $1.N.Op != OTYPE && $1.N.Op != ONONAME)` は、`OLITERAL` を有効な変数名として認識していなかったため、誤ってエラーを発生させていました。

修正は、この条件に `&& ($1.N.Op != OLITERAL || $1.N.Name == nil)` という部分を追加することで、`OLITERAL` であっても `Name` が `nil` でない（つまり名前付きリテラルである）場合は有効な変数名として扱うように変更しました。

- `ONAME`: 通常の変数名。これは常に有効。
- `OTYPE`: 型名。これは常に有効。
- `ONONAME`: 匿名変数 `_`。これは常に有効。
- `OLITERAL` かつ `Name` が `nil` でない: 名前付き定数。これは新しい変数名として有効。

この修正により、コンパイラは `OLITERAL` ノードが名前を持つ場合に、それを型スイッチの短縮変数宣言における有効な識別子として正しく認識できるようになりました。

## コアとなるコードの解説

変更の中心は、`go.y` ファイル内の `simple_stmt` ルールに関連するアクションブロックです。このブロックは、型スイッチの短縮変数宣言の左辺（新しい変数名）が有効であるかをチェックしています。

元のコードの条件式:
```go
($1.N.Op != ONAME && $1.N.Op != OTYPE && $1.N.Op != ONONAME) || isblank($1.N)
```
これは、「ノードのオペレーションが `ONAME`、`OTYPE`、`ONONAME` のいずれでもない」または「ノードがブランク識別子 (`_`) である」場合にエラーを発生させる、という意味です。`isblank($1.N)` は `_` をチェックする関数です。

修正後のコードの条件式:
```go
($1.N.Op != ONAME && $1.N.Op != OTYPE && $1.N.Op != ONONAME && ($1.N.Op != OLITERAL || $1.N.Name == nil)) || isblank($1.N)
```
この変更で追加されたのは `&& ($1.N.Op != OLITERAL || $1.N.Name == nil)` の部分です。
この追加された条件は次のように解釈できます。
- `($1.N.Op != OLITERAL || $1.N.Name == nil)`:
    - もしノードのオペレーションが `OLITERAL` でない場合、この部分は `true` となり、元の条件式に影響を与えません。
    - もしノードのオペレーションが `OLITERAL` である場合、`$1.N.Op != OLITERAL` は `false` となります。このとき、`$1.N.Name == nil` の評価が重要になります。
        - `$1.N.Name == nil` が `true` の場合（つまり、名前のないリテラル、例: `42` そのもの）、この追加条件全体は `true` となります。これは、名前のないリテラルを短縮変数宣言の左辺に使うことはできないため、エラーを継続させる正しい挙動です。
        - `$1.N.Name == nil` が `false` の場合（つまり、名前付きリテラル、例: `const x = 42` の `x`）、この追加条件全体は `false` となります。これにより、`OLITERAL` かつ名前付きのリテラルは、エラー条件から除外され、有効な変数名として扱われるようになります。

要するに、この修正は「`ONAME`、`OTYPE`、`ONONAME` ではない、かつ、名前付きの `OLITERAL` でもない」場合にエラーとする、というロジックに変更したことになります。これにより、名前付きの `OLITERAL` が短縮変数宣言の左辺として正しく認識されるようになりました。

`y.go` の変更は、`go.y` から生成されたコードであるため、`go.y` の変更がそのまま反映されています。

新規追加された `test/fixedbugs/issue12413.go` は、このバグを再現し、修正が正しく適用されたことを検証するためのものです。`const x = 42` の後に `switch x := interface{}(nil).(type)` を記述することで、以前はコンパイルエラーになっていたコードが、修正後は正常にコンパイルされることを確認します。

## 変更の背景

Goコンパイラは、プログラムの型チェックフェーズにおいて、2つの型が同一であるかどうかを頻繁に判断する必要があります。この型等価性チェックは、言語仕様に厳密に従って行われ、特に構造体やインターフェース、関数型などの複合型においては、その内部構造を再帰的に比較する必要があります。

しかし、型定義の中には循環参照を含むもの（例: `type Node struct { Next *Node }`）が存在します。このような循環型を再帰的に比較しようとすると、無限ループに陥る可能性があります。これを防ぐために、`Eqtype` 関数は既に比較中の型のペアを追跡するメカニズムを持っていました。

このコミット以前は、`Eqtype` 関数は `TypePairList` というリンクリストを使用して、既に比較中である型のペアを記録していました。このリンクリストは、再帰呼び出しのたびに新しい要素が追加され、比較が完了すると破棄されるという形で利用されていました。しかし、リンクリストの走査は線形時間計算量であり、比較対象の型の複雑さや深さによってはオーバーヘッドが大きくなる可能性がありました。また、コードの記述もやや冗長でした。

この変更の背景には、より効率的で簡潔な循環型検出メカニズムを導入し、`Eqtype` 関数の全体的な品質を向上させるという目的があります。

## 前提知識の解説

### Goの型システムと型等価性

Go言語の型システムは、静的型付けであり、型の安全性と明確性を重視しています。型等価性（Type Equality）は、Go言語仕様の重要な側面であり、2つの型が「同じ」であると見なされる条件を定義します。

*   **プリミティブ型**: `int`, `bool`, `string` などのプリミティブ型は、それらが同じ基底型であれば等しいと見なされます。
*   **名前付き型と無名型**: Goには名前付き型（例: `type MyInt int`）と無名型（例: `struct { X int }`）があります。名前付き型は、たとえ基底型が同じであっても、異なる名前を持つ場合は異なる型と見なされます（名目型付け）。無名型は、その構造が同じであれば等しいと見なされます（構造的型付け）。
*   **複合型**:
    *   **構造体 (struct)**: 2つの構造体型が等しいのは、同じフィールドのシーケンスを持ち、対応するフィールドが同じ名前、同じ型、同じタグを持つ場合です。
    *   **インターフェース (interface)**: 2つのインターフェース型が等しいのは、同じメソッドのシーケンスを持ち、対応するメソッドが同じ名前、同じシグネチャを持つ場合です。
    *   **配列 (array)**: 2つの配列型が等しいのは、同じ要素型と、同じ長さを持つ場合です。
    *   **スライス (slice)**: スライス型は常に無名型であり、要素型が同じであれば等しいと見なされます。
    *   **マップ (map)**: マップ型は常に無名型であり、キー型と要素型が同じであれば等しいと見なされます。
    *   **チャネル (channel)**: チャネル型は常に無名型であり、要素型と方向が同じであれば等しいと見なされます。
    *   **関数 (function)**: 2つの関数型が等しいのは、同じ数のパラメータと結果を持ち、対応するパラメータと結果が同じ型を持ち、かつ両方とも可変長引数を持つか持たないかが一致する場合です。

### 循環型 (Cyclic Types)

循環型とは、型定義が自分自身を再帰的に参照する構造を持つ型のことです。例えば、以下のような構造体は循環型です。

```go
type Node struct {
    Value int
    Next  *Node // Node型が自分自身へのポインタを持つ
}
```

このような型を再帰的に処理するアルゴリズム（型等価性チェックなど）では、無限ループに陥る可能性があります。これを防ぐためには、既に処理中の要素を記録し、同じ要素に再度遭遇した場合は、それが既に処理中であることを認識して処理を中断するメカニズムが必要です。

### Goコンパイラの型表現

Goコンパイラ内部では、各型は `*Type` というポインタによって表現されます。`Type` 構造体には、型の種類 (`Etype` - Element Type)、基底型、要素型、フィールド情報などが含まれています。型等価性チェックは、これらの `*Type` ポインタが指す構造体の内容を比較することで行われます。

## 技術的詳細

このコミットの主要な変更点は、`Eqtype` 関数が循環型を検出するために使用するデータ構造の変更です。

### 変更前のアプローチ: `TypePairList` (リンクリスト)

以前の実装では、`eqtype1` 関数（`Eqtype` の実体）は `assumed_equal *TypePairList` という引数を受け取っていました。`TypePairList` は以下のように定義されていました。

```go
type TypePairList struct {
    t1   *Type
    t2   *Type
    next *TypePairList
}
```

`eqtype1` が再帰的に呼び出される際、現在比較中の `(t1, t2)` のペアがこのリンクリストの先頭に追加され、`assumed_equal` 引数として次の再帰呼び出しに渡されていました。`onlist` 関数は、このリンクリストを走査して、現在の `(t1, t2)` ペアが既にリスト内に存在するかどうかをチェックしていました。もし存在すれば、それは循環型の一部であり、既に等しいと仮定して `true` を返していました。

このアプローチの課題は以下の通りです。
*   **パフォーマンス**: `onlist` 関数はリンクリストを線形に走査するため、リストが長くなると比較のオーバーヘッドが増大します。
*   **複雑性**: リンクリストの管理（追加、走査）がコードをやや複雑にしていました。

### 変更後のアプローチ: `map[typePair]struct{}` (マップ)

新しい実装では、`assumed_equal` 引数の型が `map[typePair]struct{}` に変更されました。`typePair` は以下のように定義されています。

```go
type typePair struct {
    t1 *Type
    t2 *Type
}
```

`eqtype1` 関数は、再帰呼び出しの前に `assumedEqual` マップに現在の `(t1, t2)` ペアをキーとして追加します。マップのバリューは `struct{}` で、これはメモリを消費しないプレースホルダーとしてよく使われます。

*   `if assumedEqual == nil { assumedEqual = make(map[typePair]struct{}) }`
    *   これは `eqtype1` がトップレベルで呼び出された際にマップが初期化されていない場合に備えています。`Eqtype` 関数は常に `nil` を渡して `eqtype1` を呼び出すため、最初の呼び出しでマップが作成されます。
*   `else if _, ok := assumedEqual[typePair{t1, t2}]; ok { return true }`
    *   この行が循環検出の核心です。現在の `(t1, t2)` ペアが既にマップに存在する場合、それは既に比較中であり、循環の一部であると判断して `true` を返します。マップのルックアップは平均的に定数時間計算量 (`O(1)`) であるため、リンクリストの走査よりもはるかに高速です。
*   `assumedEqual[typePair{t1, t2}] = struct{}{}`
    *   現在のペアをマップに追加し、以降の再帰呼び出しで検出できるようにします。

### `byte`/`uint8` および `rune`/`int32` の特殊処理

Go言語では、`byte` は `uint8` のエイリアスであり、`rune` は `int32` のエイリアスです。コンパイラ内部では、これらは異なる型として扱われることがありますが、型等価性チェックにおいては等しいと見なされる必要があります。

変更前は、この特殊処理がやや冗長な `if` 文で記述されていましたが、変更後は `switch` 文とより簡潔な `return` 文で表現されています。

```go
// 変更前
case TUINT8:
    if (t1 == Types[TUINT8] || t1 == bytetype) && (t2 == Types[TUINT8] || t2 == bytetype) {
        return true
    }
// ...
case TINT, TINT32: // TINTはint、TINT32はruneの基底型
    if (t1 == Types[runetype.Etype] || t1 == runetype) && (t2 == Types[runetype.Etype] || t2 == runetype) {
        return true
    }

// 変更後
case TUINT8:
    return (t1 == Types[TUINT8] || t1 == bytetype) && (t2 == Types[TUINT8] || t2 == bytetype)
case TINT32: // TINT32はruneの基底型
    return (t1 == Types[TINT32] || t1 == runetype) && (t2 == Types[TINT32] || t2 == runetype)
```
`TINT` が削除され、`TINT32` に統一されている点も注目に値します。これは `rune` が `int32` のエイリアスであるという事実をより直接的に反映しています。

### 全体的な簡素化

リンクリストの削除とマップの導入により、`eqtype1` 関数のコード量が減少し、ロジックがより明確になりました。特に、再帰呼び出しの引数として `&l` (新しい `TypePairList` のアドレス) を渡す代わりに、`assumedEqual` マップを直接渡すことで、コードが簡潔になっています。

## コアとなるコードの解説

### `TypePairList` 関連の削除

*   `TypePairList` 構造体と `onlist` 関数が完全に削除されました。これにより、リンクリストベースの循環検出ロジックが不要になりました。

### `typePair` 構造体の導入

*   `type typePair struct { t1 *Type; t2 *Type }` が新しく定義されました。これは、2つの `*Type` ポインタのペアをマップのキーとして使用するための構造体です。Goのマップは構造体をキーとして使用できるため、このアプローチが可能です。

### `eqtype1` 関数のシグネチャ変更

*   `func eqtype1(t1 *Type, t2 *Type, assumed_equal *TypePairList) bool` から `func eqtype1(t1, t2 *Type, assumedEqual map[typePair]struct{}) bool` へと変更されました。引数名も `assumed_equal` から `assumedEqual` に変更され、よりGoらしい命名規則に沿っています。

### 循環検出ロジックの変更

*   変更前:
    ```go
    if onlist(assumed_equal, t1, t2) {
        return true
    }
    var l TypePairList
    l.next = assumed_equal
    l.t1 = t1
    l.t2 = t2
    // ... 再帰呼び出しで &l を渡す
    ```
*   変更後:
    ```go
    if assumedEqual == nil {
        assumedEqual = make(map[typePair]struct{})
    } else if _, ok := assumedEqual[typePair{t1, t2}]; ok {
        return true
    }
    assumedEqual[typePair{t1, t2}] = struct{}{}
    // ... 再帰呼び出しで assumedEqual を直接渡す
    ```
    この変更により、リンクリストの走査がマップのルックアップに置き換わり、効率が向上しました。また、マップの初期化ロジックも追加されています。

### `byte`/`uint8` および `rune`/`int32` の特殊処理の簡素化

*   `t1.Sym != nil || t2.Sym != nil` のブロック内で、`byte`/`uint8` と `rune`/`int32` の等価性チェックが `switch` 文と直接 `return` を使用する形に簡素化されました。これにより、コードがより読みやすくなっています。

### 再帰呼び出しの引数変更

*   `eqtype1(t1.Type, t2.Type, &l)` のようにリンクリストのアドレスを渡していた箇所が、`eqtype1(t1.Type, t2.Type, assumedEqual)` のようにマップを直接渡す形に変更されました。これにより、コードがより簡潔になりました。

### 最終的な `return` 文の簡素化

*   関数の最後で、`if eqtype1(...) && eqtype1(...) { return true } return false` という形式だったものが、`return eqtype1(...) && eqtype1(...)` と直接ブール値を返す形に簡素化されました。

これらの変更により、`Eqtype` 関数はより効率的で、よりGoのイディオムに沿った、そしてより保守しやすいコードになりました。

## 変更の背景

Goコンパイラは、プログラムの型チェックフェーズにおいて、2つの型が同一であるかどうかを頻繁に判断する必要があります。この型等価性チェックは、言語仕様に厳密に従って行われ、特に構造体やインターフェース、関数型などの複合型においては、その内部構造を再帰的に比較する必要があります。

しかし、型定義の中には循環参照を含むもの（例: `type Node struct { Next *Node }`）が存在します。このような循環型を再帰的に比較しようとすると、無限ループに陥る可能性があります。これを防ぐために、`Eqtype` 関数は既に比較中の型のペアを追跡するメカニズムを持っていました。

このコミット以前は、`Eqtype` 関数は `TypePairList` というリンクリストを使用して、既に比較中である型のペアを記録していました。このリンクリストは、再帰呼び出しのたびに新しい要素が追加され、比較が完了すると破棄されるという形で利用されていました。しかし、リンクリストの走査は線形時間計算量であり、比較対象の型の複雑さや深さによってはオーバーヘッドが大きくなる可能性がありました。また、コードの記述もやや冗長でした。

この変更の背景には、より効率的で簡潔な循環型検出メカニズムを導入し、`Eqtype` 関数の全体的な品質を向上させるという目的があります。

## 前提知識の解説

### Goの型システムと型等価性

Go言語の型システムは、静的型付けであり、型の安全性と明確性を重視しています。型等価性（Type Equality）は、Go言語仕様の重要な側面であり、2つの型が「同じ」であると見なされる条件を定義します。

*   **プリミティブ型**: `int`, `bool`, `string` などのプリミティブ型は、それらが同じ基底型であれば等しいと見なされます。
*   **名前付き型と無名型**: Goには名前付き型（例: `type MyInt int`）と無名型（例: `struct { X int }`）があります。名前付き型は、たとえ基底型が同じであっても、異なる名前を持つ場合は異なる型と見なされます（名目型付け）。無名型は、その構造が同じであれば等しいと見なされます（構造的型付け）。
*   **複合型**:
    *   **構造体 (struct)**: 2つの構造体型が等しいのは、同じフィールドのシーケンスを持ち、対応するフィールドが同じ名前、同じ型、同じタグを持つ場合です。
    *   **インターフェース (interface)**: 2つのインターフェース型が等しいのは、同じメソッドのシーケンスを持ち、対応するメソッドが同じ名前、同じシグネチャを持つ場合です。
    *   **配列 (array)**: 2つの配列型が等しいのは、同じ要素型と、同じ長さを持つ場合です。
    *   **スライス (slice)**: スライス型は常に無名型であり、要素型が同じであれば等しいと見なされます。
    *   **マップ (map)**: マップ型は常に無名型であり、キー型と要素型が同じであれば等しいと見なされます。
    *   **チャネル (channel)**: チャネル型は常に無名型であり、要素型と方向が同じであれば等しいと見なされます。
    *   **関数 (function)**: 2つの関数型が等しいのは、同じ数のパラメータと結果を持ち、対応するパラメータと結果が同じ型を持ち、かつ両方とも可変長引数を持つか持たないかが一致する場合です。

### 循環型 (Cyclic Types)

循環型とは、型定義が自分自身を再帰的に参照する構造を持つ型のことです。例えば、以下のような構造体は循環型です。

```go
type Node struct {
    Value int
    Next  *Node // Node型が自分自身へのポインタを持つ
}
```

このような型を再帰的に処理するアルゴリズム（型等価性チェックなど）では、無限ループに陥る可能性があります。これを防ぐためには、既に処理中の要素を記録し、同じ要素に再度遭遇した場合は、それが既に処理中であることを認識して処理を中断するメカニズムが必要です。

### Goコンパイラの型表現

Goコンパイラ内部では、各型は `*Type` というポインタによって表現されます。`Type` 構造体には、型の種類 (`Etype` - Element Type)、基底型、要素型、フィールド情報などが含まれています。型等価性チェックは、これらの `*Type` ポインタが指す構造体の内容を比較することで行われます。

## 技術的詳細

このコミットの主要な変更点は、`Eqtype` 関数が循環型を検出するために使用するデータ構造の変更です。

### 変更前のアプローチ: `TypePairList` (リンクリスト)

以前の実装では、`eqtype1` 関数（`Eqtype` の実体）は `assumed_equal *TypePairList` という引数を受け取っていました。`TypePairList` は以下のように定義されていました。

```go
type TypePairList struct {
    t1   *Type
    t2   *Type
    next *TypePairList
}
```

`eqtype1` が再帰的に呼び出される際、現在比較中の `(t1, t2)` のペアがこのリンクリストの先頭に追加され、`assumed_equal` 引数として次の再帰呼び出しに渡されていました。`onlist` 関数は、このリンクリストを走査して、現在の `(t1, t2)` ペアが既にリスト内に存在するかどうかをチェックしていました。もし存在すれば、それは循環型の一部であり、既に等しいと仮定して `true` を返していました。

このアプローチの課題は以下の通りです。
*   **パフォーマンス**: `onlist` 関数はリンクリストを線形に走査するため、リストが長くなると比較のオーバーヘッドが増大します。
*   **複雑性**: リンクリストの管理（追加、走査）がコードをやや複雑にしていました。

### 変更後のアプローチ: `map[typePair]struct{}` (マップ)

新しい実装では、`assumed_equal` 引数の型が `map[typePair]struct{}` に変更されました。`typePair` は以下のように定義されています。

```go
type typePair struct {
    t1 *Type
    t2 *Type
}
```

`eqtype1` 関数は、再帰呼び出しの前に `assumedEqual` マップに現在の `(t1, t2)` ペアをキーとして追加します。マップのバリューは `struct{}` で、これはメモリを消費しないプレースホルダーとしてよく使われます。

*   `if assumedEqual == nil { assumedEqual = make(map[typePair]struct{}) }`
    *   これは `eqtype1` がトップレベルで呼び出された際にマップが初期化されていない場合に備えています。`Eqtype` 関数は常に `nil` を渡して `eqtype1` を呼び出すため、最初の呼び出しでマップが作成されます。
*   `else if _, ok := assumedEqual[typePair{t1, t2}]; ok { return true }`
    *   この行が循環検出の核心です。現在の `(t1, t2)` ペアが既にマップに存在する場合、それは既に比較中であり、循環の一部であると判断して `true` を返します。マップのルックアップは平均的に定数時間計算量 (`O(1)`) であるため、リンクリストの走査よりもはるかに高速です。
*   `assumedEqual[typePair{t1, t2}] = struct{}{}`
    *   現在のペアをマップに追加し、以降の再帰呼び出しで検出できるようにします。

### `byte`/`uint8` および `rune`/`int32` の特殊処理

Go言語では、`byte` は `uint8` のエイリアスであり、`rune` は `int32` のエイリアスです。コンパイラ内部では、これらは異なる型として扱われることがありますが、型等価性チェックにおいては等しいと見なされる必要があります。

変更前は、この特殊処理がやや冗長な `if` 文で記述されていましたが、変更後は `switch` 文とより簡潔な `return` 文で表現されています。

```go
// 変更前
case TUINT8:
    if (t1 == Types[TUINT8] || t1 == bytetype) && (t2 == Types[TUINT8] || t2 == bytetype) {
        return true
    }
// ...
case TINT, TINT32: // TINTはint、TINT32はruneの基底型
    if (t1 == Types[runetype.Etype] || t1 == runetype) && (t2 == Types[runetype.Etype] || t2 == runetype) {
        return true
    }

// 変更後
case TUINT8:
    return (t1 == Types[TUINT8] || t1 == bytetype) && (t2 == Types[TUINT8] || t2 == bytetype)
case TINT32: // TINT32はruneの基底型
    return (t1 == Types[TINT32] || t1 == runetype) && (t2 == Types[TINT32] || t2 == runetype)
```
`TINT` が削除され、`TINT32` に統一されている点も注目に値します。これは `rune` が `int32` のエイリアスであるという事実をより直接的に反映しています。

### 全体的な簡素化

リンクリストの削除とマップの導入により、`eqtype1` 関数のコード量が減少し、ロジックがより明確になりました。特に、再帰呼び出しの引数として `&l` (新しい `TypePairList` のアドレス) を渡す代わりに、`assumedEqual` マップを直接渡すことで、コードが簡潔になっています。

## コアとなるコードの解説

### `TypePairList` 関連の削除

*   `TypePairList` 構造体と `onlist` 関数が完全に削除されました。これにより、リンクリストベースの循環検出ロジックが不要になりました。

### `typePair` 構造体の導入

*   `type typePair struct { t1 *Type; t2 *Type }` が新しく定義されました。これは、2つの `*Type` ポインタのペアをマップのキーとして使用するための構造体です。Goのマップは構造体をキーとして使用できるため、このアプローチが可能です。

### `eqtype1` 関数のシグネチャ変更

*   `func eqtype1(t1 *Type, t2 *Type, assumed_equal *TypePairList) bool` から `func eqtype1(t1, t2 *Type, assumedEqual map[typePair]struct{}) bool` へと変更されました。引数名も `assumed_equal` から `assumedEqual` に変更され、よりGoらしい命名規則に沿っています。

### 循環検出ロジックの変更

*   変更前:
    ```go
    if onlist(assumed_equal, t1, t2) {
        return true
    }
    var l TypePairList
    l.next = assumed_equal
    l.t1 = t1
    l.t2 = t2
    // ... 再帰呼び出しで &l を渡す
    ```
*   変更後:
    ```go
    if assumedEqual == nil {
        assumedEqual = make(map[typePair]struct{})
    } else if _, ok := assumedEqual[typePair{t1, t2}]; ok {
        return true
    }
    assumedEqual[typePair{t1, t2}] = struct{}{}
    // ... 再帰呼び出しで assumedEqual を直接渡す
    ```
    この変更により、リンクリストの走査がマップのルックアップに置き換わり、効率が向上しました。また、マップの初期化ロジックも追加されています。

### `byte`/`uint8` および `rune`/`int32` の特殊処理の簡素化

*   `t1.Sym != nil || t2.Sym != nil` のブロック内で、`byte`/`uint8` と `rune`/`int32` の等価性チェックが `switch` 文と直接 `return` を使用する形に簡素化されました。これにより、コードがより読みやすくなっています。

### 再帰呼び出しの引数変更

*   `eqtype1(t1.Type, t2.Type, &l)` のようにリンクリストのアドレスを渡していた箇所が、`eqtype1(t1.Type, t2.Type, assumedEqual)` のようにマップを直接渡す形に変更されました。これにより、コードがより簡潔になりました。

### 最終的な `return` 文の簡素化

*   関数の最後で、`if eqtype1(...) && eqtype1(...) { return true } return false` という形式だったものが、`return eqtype1(...) && eqtype1(...)` と直接ブール値を返す形に簡素化されました。

これらの変更により、`Eqtype` 関数はより効率的で、よりGoのイディオムに沿った、そしてより保守しやすいコードになりました。

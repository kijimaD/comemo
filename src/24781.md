# [インデックス 24781] ファイルの概要

このコミットは、Goランタイムにおけるスタックバリアのインストールロジックを修正するものです。具体的には、`cgocallback_gofunc`という特殊なフレームに対してスタックバリアが誤ってインストールされるのを防ぎ、それによって発生する可能性のあるランタイムの不整合を解消します。

## 元コミット内容

```
runtime: don't install a stack barrier in cgocallback_gofunc's frame

Currently the runtime can install stack barriers in any frame.
However, the frame of cgocallback_gofunc is special: it's the one
function that switches from a regular G stack to the system stack on
return. Hence, the return PC slot in its frame on the G stack is
actually used to save getg().sched.pc (so tracebacks appear to unwind
to the last Go function running on that G), and not as an actual
return PC for cgocallback_gofunc.

Because of this, if we install a stack barrier in cgocallback_gofunc's
return PC slot, when cgocallback_gofunc does return, it will move the
stack barrier stub PC in to getg().sched.pc and switch back to the
system stack. The rest of the runtime doesn't know how to deal with a
stack barrier stub in sched.pc: nothing knows how to match it up with
the G's stack barrier array and, when the runtime removes stack
barriers, it doesn't know to undo the one in sched.pc. Hence, if the C
code later returns back in to Go code, it will attempt to return
through the stack barrier saved in sched.pc, which may no longer have
correct unwinding information.

Fix this by blacklisting cgocallback_gofunc's frame so the runtime
won't install a stack barrier in it's return PC slot.

Fixes #12238.
```

## 変更の背景

Goランタイムは、ガベージコレクション（GC）の際にスタックの走査を効率的に行うために「スタックバリア」というメカニズムを使用します。スタックバリアは、特定のフレームの戻りPC（Program Counter）を一時的に書き換えることで、GCがスタックを走査する際に特定の処理を挿入できるようにするものです。

しかし、`cgocallback_gofunc`という関数は、GoコードからCコードを呼び出し、そのCコードから再びGoコードへコールバックする際に使用される特殊な関数です。この関数のフレームは、通常のGo関数のフレームとは異なり、戻りPCスロットが`getg().sched.pc`（現在のゴルーチンのスケジューラPC）を保存するために使われます。これは、トレースバックがそのゴルーチンで実行されていた最後のGo関数に巻き戻されるようにするためです。

この特殊な性質のため、`cgocallback_gofunc`の戻りPCスロットにスタックバリアをインストールすると問題が発生します。`cgocallback_gofunc`がリターンする際、スタックバリアのスタブPCが`getg().sched.pc`に移動され、システムスタックに切り替わります。ランタイムの他の部分は、`sched.pc`内のスタックバリアスタブを適切に処理する方法を知りません。具体的には、スタックバリア配列と照合する方法や、スタックバリアが削除される際に`sched.pc`内のバリアを元に戻す方法がありません。

結果として、CコードがGoコードに再び戻ろうとした場合、`sched.pc`に保存されたスタックバリアを介してリターンしようとしますが、そのバリアには正しいアンワインド情報がない可能性があり、ランタイムの不整合やクラッシュを引き起こす可能性がありました。このコミットは、この問題を解決するために`cgocallback_gofunc`のフレームをスタックバリアインストールの対象から除外することを目的としています。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

*   **Goroutine (G)**: Goにおける軽量な実行スレッドです。Goランタイムによって管理され、OSスレッドに多重化されて実行されます。各Goroutineは独自のスタック（Goroutineスタック）を持ちます。
*   **OS Thread (M)**: オペレーティングシステムのスレッドです。Goランタイムは複数のMを起動し、その上でGを実行します。
*   **Processor (P)**: 論理プロセッサの抽象化です。MはPを介してGを実行します。PはMとGの間のコンテキストスイッチを管理します。
*   **Goroutine Stack**: 各Goroutineが持つスタックで、関数の呼び出し情報やローカル変数が格納されます。Goのスタックは動的に伸縮します。
*   **System Stack**: OSスレッド（M）が使用するスタックです。GoランタイムがOSのシステムコールを呼び出す際や、CGO（C言語との相互運用）のコールバック処理などで使用されます。Goroutineスタックとは独立しています。
*   **CGO (C Foreign Function Interface)**: GoプログラムからC言語の関数を呼び出したり、C言語からGoの関数を呼び出したりするためのメカニズムです。
*   **`cgocallback_gofunc`**: CGOにおいて、CコードからGoコードへコールバックする際にGoランタイムが内部的に使用する特殊な関数です。この関数は、Goroutineスタックからシステムスタックへの切り替えを伴います。
*   **Stack Barrier**: Goのガベージコレクタ（GC）がスタックを走査する際に使用される技術です。GCは、スタック上のポインタを正確に識別し、マークするためにスタックを走査します。スタックバリアは、GCがスタックの特定のポイントに到達したときに、GCの処理を一時停止させたり、追加の処理を実行させたりするためのフックとして機能します。これは、関数の戻りPCを一時的にGCが用意した特別なスタブ関数（スタックバリア）のアドレスに書き換えることで実現されます。これにより、関数がリターンする際にGCの処理が割り込み、スタックの走査やポインタの更新などが行われます。
*   **`getg().sched.pc`**: 現在実行中のGoroutine（G）のスケジューラ関連のPC（Program Counter）を指します。これは、Goroutineがプリエンプトされたり、システムコールに入ったりする際に、そのGoroutineが次に実行を再開すべき命令のアドレスを保存するために使用されます。通常の関数の戻りPCとは異なる目的で使われます。

## 技術的詳細

このコミットの核心は、`cgocallback_gofunc`の特殊なスタックフレーム構造と、Goランタイムのスタックバリアメカニズムとの間の不整合を解消することにあります。

通常のGo関数では、スタックフレームの戻りPCスロットには、その関数が完了した後に実行を継続すべき次の命令のアドレスが格納されます。スタックバリアは、この戻りPCを一時的にGCのスタブ関数に書き換えることで機能します。関数がリターンしようとすると、実際にはスタブ関数が実行され、GC関連の処理が行われた後に元の戻りPCにジャンプします。

しかし、`cgocallback_gofunc`の場合、その戻りPCスロットは通常の戻りアドレスとしてではなく、`getg().sched.pc`を保存するために使用されます。これは、CコードからGoコードへのコールバックが完了し、`cgocallback_gofunc`がリターンする際に、Goroutineの実行コンテキストをシステムスタックからGoroutineスタックに戻す必要があるためです。`getg().sched.pc`に保存されるアドレスは、トレースバックがCGOコールバックの前に実行されていたGo関数に戻るように見せるためのものです。

もし`cgocallback_gofunc`の戻りPCスロットにスタックバリアがインストールされると、以下の問題が発生します。

1.  **`sched.pc`の汚染**: `cgocallback_gofunc`がリターンする際、スタックバリアのスタブPCが`getg().sched.pc`にコピーされます。これにより、`sched.pc`が本来のGo関数の戻りアドレスではなく、GCのスタブアドレスで上書きされてしまいます。
2.  **ランタイムの不整合**: Goランタイムの他の部分は、`sched.pc`にスタックバリアスタブが存在することを想定していません。スタックバリアは通常、Goroutineスタック上の特定のフレームに関連付けられた配列で管理されますが、`sched.pc`内のスタブはこれと関連付けられません。
3.  **バリアの解除不能**: GCがスタックバリアを解除する際、`sched.pc`内のスタブを認識せず、元に戻すことができません。
4.  **不正なリターン**: CコードがGoコードに再び戻ろうとした場合、`sched.pc`に保存されたスタックバリアスタブを介してリターンしようとします。しかし、このスタブはもはや有効なアンワインド情報を持たない可能性があり、ランタイムエラーやクラッシュを引き起こす可能性があります。

このコミットは、`gcInstallStackBarrier`関数内で`cgocallback_gofunc`のフレームを明示的にチェックし、そのフレームに対してはスタックバリアをインストールしないようにすることで、この問題を解決します。これにより、`getg().sched.pc`がスタックバリアスタブで汚染されることを防ぎ、ランタイムの整合性を保ちます。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/runtime/asm_amd64p32.s`**:
    *   `cgocallback_gofunc`という関数の定義が追加されています。これは、アセンブリレベルでこの関数のエントリポイントを定義し、ランタイムがそのアドレスを識別できるようにするためです。ただし、このコミットでは`cgocallback_gofunc`自体の実装は`MOVL 0, AX; RET`というダミーになっています。これは、この関数が実際に呼び出されることはなく、そのエントリポイントのアドレスがランタイムによって参照されることが重要であるためです。
2.  **`src/runtime/mgcmark.go`**:
    *   `gcInstallStackBarrier`関数のシグネチャが変更され、`bool`型の戻り値を持つようになりました。これは、スタックバリアが正常にインストールされたかどうかを示すためです。
    *   `gcInstallStackBarrier`関数内に、`frame.fn.entry == cgocallback_gofuncPC`という条件が追加されました。これにより、現在のフレームが`cgocallback_gofunc`のものである場合、スタックバリアのインストールをスキップし、`false`を返します。
    *   `scanstack`関数内で`gcInstallStackBarrier`の呼び出し箇所が変更され、その戻り値をチェックするようになりました。`gcInstallStackBarrier`が`true`を返した場合のみ、`barrierOffset`と`nextBarrier`の更新が行われます。
3.  **`src/runtime/traceback.go`**:
    *   `cgocallback_gofuncPC`という`uintptr`型のグローバル変数が追加されました。
    *   `tracebackinit`関数内で、`cgocallback_gofuncPC = funcPC(cgocallback_gofunc)`という行が追加され、`cgocallback_gofunc`のエントリポイントのアドレスが`cgocallback_gofuncPC`に初期化されるようになりました。これにより、`mgcmark.go`でこのアドレスを参照できるようになります。

## コアとなるコードの解説

最も重要な変更は`src/runtime/mgcmark.go`の`gcInstallStackBarrier`関数にあります。

```go
// gcInstallStackBarrier installs a stack barrier over the return PC of frame.
//go:nowritebarrier
func gcInstallStackBarrier(gp *g, frame *stkframe) bool {
	if frame.lr == 0 {
		if debugStackBarrier {
			print("not installing stack barrier with no LR, goid=", gp.goid, "\n")
		}
		return false
	}

	if frame.fn.entry == cgocallback_gofuncPC {
		// cgocallback_gofunc doesn't return to its LR;
		// instead, its return path puts LR in g.sched.pc and
		// switches back to the system stack on which
		// cgocallback_gofunc was originally called. We can't
		// have a stack barrier in g.sched.pc, so don't
		// install one in this frame.
		if debugStackBarrier {
			print("not installing stack barrier over LR of cgocallback_gofunc, goid=", gp.goid, "\n")
		}
		return false
	}

	// Save the return PC and overwrite it with stackBarrier.
	// ... (既存のスタックバリアインストールロジック) ...
	return true
}
```

この変更により、`gcInstallStackBarrier`は以下のロジックで動作します。

1.  まず、`frame.lr == 0`（戻りPCが存在しない場合）のチェックを行います。これは既存のロジックであり、戻りPCがない場合はバリアをインストールせず`false`を返します。
2.  次に、`frame.fn.entry == cgocallback_gofuncPC`という新しいチェックが追加されます。
    *   `frame.fn.entry`は、現在のスタックフレームに対応する関数のエントリポイントのアドレスです。
    *   `cgocallback_gofuncPC`は、`src/runtime/traceback.go`で初期化された`cgocallback_gofunc`関数のエントリポイントのアドレスです。
3.  もし現在のフレームが`cgocallback_gofunc`のものであると判断された場合、コメントに記載されている理由（`cgocallback_gofunc`がLRにリターンせず、`g.sched.pc`にLRを格納し、システムスタックに切り替わるため、`g.sched.pc`にスタックバリアを置くことはできない）に基づいて、スタックバリアのインストールをスキップし、`false`を返します。
4.  これらの特殊なケースに該当しない場合のみ、通常のスタックバリアインストールロジックが実行され、`true`が返されます。

`src/runtime/mgcmark.go`の`scanstack`関数では、`gcInstallStackBarrier`の戻り値がチェックされるようになりました。

```go
			if gcphase == _GCscan && n != 0 {
				if gcInstallStackBarrier(gp, frame) {
					barrierOffset *= 2
					nextBarrier = sp + barrierOffset
				}
			}
```

これにより、`gcInstallStackBarrier`が`false`を返した場合（つまり、`cgocallback_gofunc`のフレームであった場合）、`barrierOffset`や`nextBarrier`の更新は行われず、スタックバリア関連の内部状態が不適切に更新されることを防ぎます。

これらの変更により、Goランタイムは`cgocallback_gofunc`の特殊な性質を認識し、そのフレームに対してはスタックバリアをインストールしないことで、CGOコールバックとGCスタックバリアメカニズムの間の競合を安全に回避できるようになりました。

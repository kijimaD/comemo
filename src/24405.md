## 元コミット内容

このコミットは、Go言語の標準ライブラリ`encoding/json`パッケージにおける、HTTPストリームをデコードする際のEOF（End Of File）バグを修正するものです。具体的には、`golang-dev`メーリングリストで参照されている議論（[https://groups.google.com/d/topic/golang-dev/U4LSpMzL82c/discussion](https://groups.google.com/d/topic/golang-dev/U4LSpMzL82c/discussion)）で報告された問題を解決します。

## 変更の背景

`encoding/json`パッケージの`Decoder`は、`io.Reader`からJSONデータをストリームとして読み込み、デコードする機能を提供します。HTTPレスポンスボディのようなストリームデータは、一度に全てのデータが利用可能になるとは限らず、`io.Reader`からの読み込みがEOFを返すことでデータの終端を示すことがあります。

このコミット以前の`encoding/json`の`Decoder`実装では、`peek()`メソッド内で`refill()`メソッドがエラーを返した場合の処理に問題がありました。`refill()`は内部バッファが空になった際に`io.Reader`からデータを補充する役割を担いますが、この際に`io.EOF`などのエラーが発生しても、それが適切に`peek()`の呼び出し元に伝播されないケースがありました。特に、HTTPストリームのように、データが途中で終了し、`io.EOF`が返されるべき状況で、`Decoder`がEOFを正しく認識せず、デコード処理がハングアップしたり、予期せぬ動作を引き起こしたりするバグが存在していました。

この問題は、`golang-dev`メーリングリストで報告され、その議論の中で具体的な再現ケースと修正の必要性が指摘されました。このコミットは、その報告を受けて、`Decoder`が`io.EOF`をより正確に処理できるようにするための修正です。

## 前提知識の解説

### Go言語の`encoding/json`パッケージ

`encoding/json`パッケージは、Goのデータ構造とJSONデータの間で変換を行うための標準ライブラリです。
- **`json.Decoder`**: `io.Reader`からJSONデータをストリームとして読み込み、Goのデータ構造にデコードするために使用されます。これにより、大きなJSONデータをメモリに全て読み込むことなく処理できます。
- **`Decode(v interface{}) error`**: `Decoder`の主要なメソッドで、次のJSON値を読み込み、`v`にデコードします。
- **`More() bool`**: デコード可能なJSON値がまだ残っているかどうかを返します。
- **`io.Reader`**: データを読み込むためのインターフェースです。HTTPレスポンスボディなどはこのインターフェースを実装しています。
- **`io.EOF`**: `io.Reader`の`Read`メソッドが、それ以上読み込むデータがないことを示すために返すエラーです。`json.Decoder`は、ストリームの終端に達した際にこのエラーを適切に処理する必要があります。

### `Decoder`の内部動作 (`peek()`と`refill()`)

`json.Decoder`は、JSONトークンを解析するために内部的にバッファを使用し、必要に応じて`io.Reader`からデータを読み込みます。
- **`peek()`メソッド**: 次に処理すべきバイトをバッファから「覗き見」する役割を担います。このメソッドは、実際にバイトを消費する前に、次のトークンが何であるかを判断するために使われます。
- **`refill()`メソッド**: `peek()`がバッファ内に十分なデータを見つけられない場合、`refill()`が呼び出され、基となる`io.Reader`からより多くのデータを内部バッファに読み込みます。`refill()`が`io.EOF`を返した場合、それはストリームの終端に達したことを意味します。

### HTTPストリームとEOF

HTTPレスポンスボディは、通常、`io.Reader`として扱われます。クライアントがHTTPリクエストを送信し、サーバーがレスポンスを返す際、レスポンスボディはストリームとして送信されます。サーバーがボディの送信を完了すると、クライアント側の`io.Reader`は最終的に`io.EOF`を返します。`json.Decoder`がこの`io.EOF`を適切に処理できないと、デコード処理が期待通りに終了せず、問題が発生します。

## 技術的詳細

このバグは、`src/encoding/json/stream.go`内の`peek()`メソッドにおけるエラーハンドリングのロジックに起因していました。

元のコードでは、`peek()`メソッドは以下のような構造をしていました。

```go
func (dec *Decoder) peek() (byte, error) {
	for {
		for i := dec.scanp; i < len(dec.buf); i++ {
			c := dec.buf[i]
			if c != ' ' && c != '\t' && c != '\r' && c != '\n' {
				dec.scanp = i
				return c, nil
			}
		}
		if err := dec.refill(); err != nil { // ここが問題
			return 0, err
		}
	}
}
```

このコードの問題点は、`dec.refill()`がエラーを返した場合、そのエラーが即座に`peek()`の呼び出し元に返されることです。一見すると正しいように見えますが、`refill()`が`io.EOF`を返した場合、それはバッファが空であり、これ以上データがないことを意味します。しかし、`peek()`のループの最初の部分（`for i := dec.scanp; i < len(dec.buf); i++`）では、まだバッファ内に処理されていない空白文字などが残っている可能性があります。

もし`refill()`が`io.EOF`を返した直後に、バッファ内にまだスキップすべき空白文字が存在していた場合、その空白文字をスキップする前に`io.EOF`が返されてしまい、`Decoder`がJSONストリームの実際の終端を正しく認識できない可能性がありました。これにより、`Decoder`はまだデータが残っていると誤解し、デコード処理がハングアップしたり、不正確なエラーを返したりすることがありました。

この修正は、`refill()`がエラーを返した場合でも、そのエラーをすぐに返すのではなく、まずバッファの残りをスキャンし終えてからエラーを報告するようにロジックを変更することで、この問題を解決します。これにより、`Decoder`はストリームの終端をより正確に判断できるようになります。

## コアとなるコードの解説

`src/encoding/json/stream.go`の`peek()`メソッドの変更点に注目します。

1.  **`var err error` の追加**:
    `peek()`関数の冒頭で`err`という名前の`error`型の変数が宣言されました。これにより、`refill()`から返されたエラーをすぐに処理するのではなく、この変数に保持し、後で処理することが可能になります。

2.  **エラー処理ロジックの変更**:
    元のコードでは`if err := dec.refill(); err != nil { return 0, err }`となっていました。これは`refill()`がエラーを返すとすぐに`peek()`からリターンすることを意味します。
    変更後では、この部分が以下のように変わりました。
    ```go
    		// buffer has been scanned, now report any error
    		if err != nil {
    			return 0, err
    		}
    		err = dec.refill()
    ```
    この変更により、`peek()`の内部ループ（`for i := dec.scanp; i < len(dec.buf); i++`）でバッファ内の既存のデータを全てスキャンし終えた後で初めて、以前の`refill()`呼び出しで発生したエラー（`err`変数に格納されているもの）がチェックされ、返されるようになります。
    そして、その後に`err = dec.refill()`が実行され、次の`refill()`呼び出しの結果が`err`に格納されます。

この新しいロジックにより、`refill()`が`io.EOF`を返した場合でも、`peek()`はまずバッファに残っている可能性のある空白文字などをスキップし終えてから、その`io.EOF`を適切に伝播するようになります。これにより、`Decoder`がストリームの終端を正しく認識し、HTTPストリームのデコード時に発生していたEOFバグが修正されます。

また、`src/encoding/json/stream_test.go`には、この修正を検証するための新しいテストケース`TestHttpDecoding`が追加されています。
- `makeHTTP()`関数は、`httptest.NewServer`を使用してシンプルなHTTPサーバーをセットアップし、`{ "foo": "bar" }`というJSONを返すようにします。そして、そのHTTPレスポンスボディを`io.ReadCloser`として返します。
- `TestHttpDecoding`関数では、この`io.ReadCloser`を使って`json.NewDecoder`を初期化し、JSONオブジェクトをデコードします。
- 最初の`d.Decode(&foo)`が成功することを確認した後、2回目の`d.Decode(&foo)`が`io.EOF`を返すことを検証しています。これは、ストリームの終端に達したことを`Decoder`が正しく認識していることを確認するための重要なテストです。

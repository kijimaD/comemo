# [インデックス 23405] ファイルの概要

このコミットは、Goランタイムのスケジューラテスト（特に`runq`テスト）がシステムスタック上で実行されることによって引き起こされる潜在的なスタックオーバーフローの問題を解決します。具体的には、これらのテストがGoのP（Processor）構造体を割り当てる際に、システムスタックのサイズを超過する可能性があったため、テストを通常のGoルーチンのスタックで実行するように変更し、それに伴い不要になったヒープエスケープのハックを削除しています。

## コミット

runtime: don't run runq tests on the system stack

Running these tests on the system stack is problematic because they
allocate Ps, which are large enough to overflow the system stack if
they are stack-allocated. It used to be necessary to run these tests
on the system stack because they were written in C, but since this is
no longer the case, we can fix this problem by simply not running the
tests on the system stack.

This also means we no longer need the hack in one of these tests that
forces the allocated Ps to escape to the heap, so eliminate that as
well.

## 変更の背景

Goランタイムのテストスイートには、スケジューラのローカル実行キュー（`runq`）の動作を検証するためのテストが含まれています。これらのテストは、過去にはC言語で書かれていたため、Goランタイムの内部処理を実行する際に使用される「システムスタック」（またはG0スタック）上で実行する必要がありました。

しかし、GoのP（Processor）構造体は比較的大きく、これらのテストがPをスタック上に直接割り当てようとすると、システムスタックの限られたサイズを超過し、スタックオーバーフローを引き起こす可能性がありました。この問題を回避するため、以前はPのインスタンスを意図的にヒープにエスケープさせるための「ハック」が導入されていました。これは、Pのポインタをグローバル変数に代入することで、コンパイラにPがヒープに割り当てられるべきだと認識させる手法です。

コミットメッセージによると、これらのテストはもはやC言語で書かれていないため、システムスタック上で実行する必要がなくなりました。この変更の背景には、テストコードがGo言語に移行したことで、より柔軟なスタック管理が可能になったという事実があります。これにより、テストを通常のGoルーチンのスタックで実行できるようになり、システムスタックの制約から解放されることになりました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念を理解しておく必要があります。

1.  **Goスケジューラ (M-P-Gモデル)**:
    *   **G (Goroutine)**: Goの軽量スレッド。Goプログラムの実行単位。
    *   **M (Machine)**: OSスレッド。Gを実行する物理的なスレッド。
    *   **P (Processor)**: MとGを仲介する論理的なプロセッサ。MがGを実行するためにPを必要とします。Pは実行可能なGのローカルキュー（`runq`）を保持し、MがGを実行する際に必要なコンテキストを提供します。Pの数は通常、CPUコア数に等しく、並列実行の度合いを制御します。PはGoランタイムにとって非常に重要なデータ構造であり、そのサイズは小さくありません。

2.  **スタック (Stack)**:
    *   **Goルーチンスタック**: 各Goルーチンに割り当てられるスタック。Goのスタックは可変長であり、必要に応じて自動的に拡張・縮小されます。これにより、スタックオーバーフローのリスクが軽減されます。
    *   **システムスタック (G0スタック)**: Goランタイムの内部処理（スケジューラ、ガベージコレクション、システムコールなど）を実行するために使用される特別なスタック。これはGoルーチンスタックとは異なり、サイズが固定されており、通常はGoルーチンスタックよりも小さいです。システムスタック上での大きなアロケーションは、スタックオーバーフローを引き起こす可能性があります。

3.  **スタックアロケーションとヒープアロケーション**:
    *   **スタックアロケーション**: 関数内で宣言されたローカル変数など、生存期間が短いデータは通常スタックに割り当てられます。高速ですが、スタックサイズには限りがあります。
    *   **ヒープアロケーション**: グローバル変数、関数呼び出しを超えて生存する必要があるデータ、またはサイズが不定のデータはヒープに割り当てられます。ガベージコレクタによって管理されますが、スタックアロケーションよりもオーバーヘッドがあります。
    *   **エスケープ解析 (Escape Analysis)**: Goコンパイラは、変数がスタックに割り当てられるべきか、ヒープに割り当てられるべきかを自動的に判断します。変数が関数のスコープを超えて参照される可能性がある場合（例: ポインタが返される、グローバル変数に代入される）、その変数はヒープに「エスケープ」されます。

4.  **`systemstack`関数**: Goランタイム内部で使用される関数で、現在のGoルーチンスタックからシステムスタックに切り替えて、指定された関数を実行します。これは、Goルーチンスタックでは実行できない、または実行すべきではない低レベルのランタイム処理（例: スタックの切り替え、GCのマークフェーズなど）のために使用されます。

## 技術的詳細

このコミットの核心は、Goランタイムのテスト関数`testSchedLocalQueue`と`testSchedLocalQueueSteal`が、もはや`systemstack`上で実行される必要がないという認識に基づいています。

以前は、これらのテストがC言語で書かれていたため、Goランタイムの低レベルな操作を行う`systemstack`上で実行する必要がありました。しかし、テストがGo言語に書き換えられたことで、通常のGoルーチンとして実行しても問題がなくなりました。

`systemstack`上でP構造体のような大きなオブジェクトをスタックアロケーションしようとすると、システムスタックの固定された小さなサイズではオーバーフローのリスクがありました。この問題を回避するため、`testSchedLocalQueueSteal`関数内では、`pSink`というグローバル変数に新しく作成したPのポインタを代入するという「ハック」が使われていました。これは、エスケープ解析によってPがヒープに割り当てられるように強制するためのものでした。

このコミットでは、テストが`systemstack`から解放されたため、以下の変更が行われました。

1.  **`systemstack`呼び出しの削除**: `src/runtime/export_test.go`内で、`RunSchedLocalQueueTest`と`RunSchedLocalQueueStealTest`関数から`systemstack`の呼び出しが削除されました。これにより、`testSchedLocalQueue`と`testSchedLocalQueueSteal`は通常のGoルーチンスタック上で実行されるようになります。Goルーチンスタックは可変長であるため、P構造体のような比較的大きなオブジェクトを一時的にスタックに割り当てても、スタックオーバーフローのリスクは大幅に低減されます。

2.  **`pSink`ハックの削除**: `src/runtime/proc1.go`内の`testSchedLocalQueueSteal`関数から、`pSink`グローバル変数とその関連する代入が削除されました。テストが`systemstack`上で実行されなくなったため、Pをヒープに強制的にエスケープさせる必要がなくなりました。これにより、コードが簡素化され、意図しない副作用のリスクも減少します。

この変更は、Goランタイムのテストインフラの成熟と、Go言語への移行が進んだ結果と言えます。テストがより通常のGoルーチンとして実行されることで、テストの記述やデバッグが容易になり、ランタイムの安定性向上にも寄与します。

## コアとなるコードの解説

### `src/runtime/export_test.go` の変更

*   `RunSchedLocalQueueTest()` と `RunSchedLocalQueueStealTest()` は、それぞれ `testSchedLocalQueue()` と `testSchedLocalQueueSteal()` を呼び出すテストヘルパー関数です。
*   変更前は、これらのテスト関数は `systemstack()` でラップされていました。これは、テストがGoランタイムの内部処理を行うために、Goルーチンスタックではなくシステムスタック上で実行されることを強制していました。
*   変更後は `systemstack()` の呼び出しが削除され、`testSchedLocalQueue()` と `testSchedLocalQueueSteal()` は通常の関数呼び出しとして実行されるようになりました。これにより、これらのテストはGoルーチンの可変長スタック上で実行され、システムスタックの制約を受けなくなります。

### `src/runtime/proc1.go` の変更

*   `testSchedLocalQueueSteal()` 関数は、P（Processor）構造体を新規に割り当てて、スケジューラのローカルキューからのG（Goroutine）の盗用（steal）メカニズムをテストします。
*   変更前は、`pSink *p` というグローバル変数が宣言されており、`p1` と `p2` という新しく割り当てられたPのポインタがこの `pSink` に代入されていました。コメントにもあるように、これは「Force to heap, too large to allocate on system stack ("G0 stack")」とあり、Pがシステムスタックに割り当てられるには大きすぎるため、ヒープに強制的にエスケープさせるためのハックでした。
*   変更後は、`pSink` 変数の宣言と、それにPのポインタを代入する行が削除されました。テストがシステムスタック上で実行されなくなったため、このヒープエスケープのハックは不要になりました。Pのインスタンスは、必要に応じてGoルーチンスタックに割り当てられるか、エスケープ解析によってヒープに割り当てられるかのいずれかになりますが、システムスタックのオーバーフローを心配する必要がなくなりました。

これらの変更により、Goランタイムのテストコードがよりクリーンになり、システムスタックの制約に起因する潜在的な問題が解消されました。

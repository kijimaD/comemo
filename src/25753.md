# [インデックス 25753] ファイルの概要

このコミットは、Go言語のツールチェーンにおける`cmd/internal/obj/x86`パッケージ、具体的にはx86アーキテクチャ向けのアセンブラに関するものです。`android/386`環境において、スレッドローカルストレージ（TLS）の取り扱いが不適切であった問題を修正し、GoプログラムがAndroid上のx86デバイスで正しく動作するようにするための変更です。

## 変更の背景

このコミットは、Go言語のツールチェーンが`android/386`（Android上のx86アーキテクチャ）向けにコンパイルされた際に発生する問題を解決するために導入されました。具体的には、以前の変更である`golang.org/cl/16383`が、共有ライブラリ（`Flag_shared != 0`）としてコンパイルされる場合に、TLS（Thread Local Storage）関連のリロケーション（`R_TLS_LE`）を全く出力しないという副作用を引き起こしました。

Android環境では、特に`runtime/cgo`が使用するTLSの仕組みが、位置独立実行可能ファイル（PIE）であっても、位置依存の実行可能ファイルと同様に機能する「ハック」に依存していました。しかし、`golang.org/cl/16383`の変更により、このTLSリロケーションが欠落したため、`android/386`上でGoプログラムが正しく動作しなくなりました。

このコミットは、この問題を一時的に解決するためのものです。将来的には、より堅牢なTLSモデル（Android/ARMで採用されているような、グローバル変数からTLSオフセットをロードするIEモデル）への移行が検討されていますが、このコミットでは、`goos == "android"`の場合に強制的に`R_TLS_LE`リロケーションを出力することで、既存の`runtime/cgo`の「ハック」が引き続き機能するようにしています。

## 前提知識の解説

### スレッドローカルストレージ (TLS: Thread Local Storage)

TLSは、マルチスレッド環境において、各スレッドがそれぞれ独立した変数を持つことを可能にするメカニズムです。グローバル変数や静的変数はプロセス内の全てのスレッドで共有されますが、TLS変数はスレッドごとに異なる値を保持できます。これは、スレッド固有の状態（エラーコード、乱数シード、スレッドIDなど）を管理する上で非常に重要です。

TLSの実装はOSやアーキテクチャによって異なりますが、一般的には、スレッドが起動する際にTLS領域が割り当てられ、特定のレジスタ（x86-64では`%fs`または`%gs`セグメントレジスタ）がそのTLS領域のベースアドレスを指すように設定されます。TLS変数へのアクセスは、このベースアドレスからのオフセットを用いて行われます。

### リロケーション (Relocation) と `R_TLS_LE`

リロケーションとは、コンパイル時やリンク時に、プログラム内のアドレス参照を実際のメモリ上のアドレスに解決するプロセスです。特に、共有ライブラリや位置独立コードでは、ロードされるアドレスが実行時まで分からないため、リロケーションが不可欠です。

`R_TLS_LE`は「Thread-Local Storage, Local Exec model」のリロケーションタイプを指します。これはTLSアクセスモデルの一つで、TLS変数が現在の実行可能ファイル（または共有ライブラリ）内に静的に割り当てられている場合に用いられます。このモデルは、TLS変数が同じ実行可能ファイル内にあることが保証されるため、アクセスが比較的効率的です。`R_TLS_LE`リロケーションは、リンカに対して、TLS変数のオフセットを計算し、そのオフセットをコード内の適切な場所に書き込むように指示します。

### 位置独立実行可能ファイル (PIE: Position-Independent Executable)

PIEは、メモリ上の任意のアドレスにロードされても正しく実行できる実行可能ファイルです。これは、セキュリティ上の理由（ASLR: Address Space Layout Randomization）から現代のOSで広く採用されています。PIEは、コード内のアドレス参照を相対アドレスやGOT/PLT（Global Offset Table/Procedure Linkage Table）などのメカニズムを通じて解決することで、位置独立性を実現します。共有ライブラリは本質的に位置独立ですが、PIEは実行可能ファイル自体も位置独立にします。

### `cmd/internal/obj/x86`

これはGo言語のツールチェーン内部で使用されるパッケージで、x86アーキテクチャ向けのアセンブラコードを生成する役割を担っています。Goのコンパイラは、Goのソースコードを中間表現に変換した後、各アーキテクチャ固有のバックエンド（この場合はx86）がアセンブラコードを生成します。このパッケージは、アセンブラ命令の生成、リロケーションの管理、シンボルの解決など、低レベルのコード生成を担当します。

### `Flag_shared`

Goコンパイラやリンカにおけるフラグの一つで、生成されるバイナリが共有ライブラリとしてビルドされるかどうかを示します。`Flag_shared != 0`は、共有ライブラリモードでのコンパイルを意味します。共有ライブラリは、複数のプログラムで共有されるコードやデータを含むため、位置独立である必要があります。

### `runtime/cgo`

Go言語のCgoランタイムは、GoプログラムからC言語のコードを呼び出すためのインターフェースを提供します。Cgoは、GoとCの間のデータ変換、スタック管理、スレッド管理など、複雑な処理を行います。Cgoが関与する場合、GoランタイムはCライブラリやOSのTLSメカニズムと連携する必要があるため、TLSの取り扱いが特に重要になります。

### `android/386`

これは、Go言語のクロスコンパイルターゲットの一つで、「Androidオペレーティングシステム上で動作するIntel i386（32ビットx86）アーキテクチャ」を指します。Androidは主にARMアーキテクチャのデバイスで動作しますが、一部の古いデバイスやエミュレータではx86アーキテクチャもサポートされています。

## 技術的詳細

この問題の核心は、`golang.org/cl/16383`という変更が、x86アーキテクチャにおけるTLSのInitial Executable (IE) モデルのサポートを導入したことにあります。IEモデルは、TLS変数がメインの実行可能ファイル内に存在することを前提とし、効率的なアクセスを提供します。しかし、この変更が共有ライブラリ（`Flag_shared != 0`）のコンテキストでTLSリロケーションの生成ロジックに影響を与え、`android/386`環境で問題を引き起こしました。

具体的には、`golang.org/cl/16383`の導入後、共有ライブラリとしてビルドされる際に、`cmd/internal/obj/x86`が`R_TLS_LE`リロケーションを生成しなくなりました。これは、IEモデルの導入が、共有ライブラリにおけるTLSの取り扱いに関する既存の「ハック」と衝突したためと考えられます。

Androidの`runtime/cgo`は、TLSへのアクセスに関して、PIE実行可能ファイルであっても位置依存の実行可能ファイルと同様に機能する特定の「ハック」に依存していました。この「ハック」は、TLS領域へのオフセットを計算するために`R_TLS_LE`リロケーションが正しく生成されることを前提としていました。`R_TLS_LE`リロケーションが生成されなくなったことで、この「ハック」が機能しなくなり、結果として`android/386`上でGoプログラムがクラッシュするなどの問題が発生しました（Issue #9327）。

このコミットは、この問題を回避するための暫定的な修正を提供します。`Flag_shared`が設定されている場合でも、ターゲットOSが`android`であれば、強制的に`R_TLS_LE`リロケーションを生成するように変更することで、既存の`runtime/cgo`の「ハック」が引き続き機能するようにします。

コミットメッセージでは、より「真の修正」として、Android/ARMで採用されているような、`%gs`レジスタからのTLSオフセットをシステムリンカが選択する場所からではなく、グローバル変数からロードするIEモデルのようなアプローチが提案されています。これは、TLSのオフセット解決をより柔軟にし、リンカの挙動に依存しないようにするためのものです。しかし、このコミットでは、緊急性を考慮し、よりシンプルな回避策が採用されました。

## コアとなるコードの解説

変更は`src/cmd/internal/obj/x86/asm6.go`ファイル内の`vaddr`関数にあります。この関数は、仮想アドレスを計算し、必要に応じてリロケーション情報を設定する役割を担っています。

元のコードでは、`ctxt.Flag_shared == 0`（つまり、共有ライブラリとしてビルドされていない場合）にのみ、`R_TLS_LE`タイプのリロケーションが生成されていました。これは、共有ライブラリとしてビルドされる場合には、TLSの取り扱いが異なると想定されていたためです。

このコミットでは、条件式に`|| isAndroid`が追加されました。
`+ if ctxt.Flag_shared == 0 || isAndroid {`

この変更により、以下のいずれかの条件が満たされる場合に`R_TLS_LE`リロケーションが生成されるようになります。
1.  `ctxt.Flag_shared == 0`: 共有ライブラリとしてビルドされていない場合（既存の挙動）。
2.  `isAndroid`: ターゲットOSがAndroidである場合。

`isAndroid`は、コンパイルターゲットがAndroidであるかどうかを示すブール変数です。この変更は、共有ライブラリとしてビルドされる場合であっても、ターゲットがAndroidであれば強制的に`R_TLS_LE`リロケーションを生成することを意味します。これにより、`golang.org/cl/16383`によって失われた`R_TLS_LE`リロケーションが`android/386`環境で再び生成されるようになり、`runtime/cgo`の既存のTLS「ハック」が機能するようになります。

この修正は、`android/386`におけるTLSの問題に対する最もシンプルで迅速な解決策として導入されました。

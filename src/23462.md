## 元コミット内容

このコミットがRevertしている元のコミット `5726af54eb3a52b9446a834991110b945e780e99` は、"cmd/internal/gc: ignore declarations of types for goto validation" というタイトルで、Goコンパイラの `goto` 文検証ロジックを修正し、`goto` が型宣言を飛び越えることを許可するように変更しました。これは Go issue #8042 に対応するものでした。

元のコミットの主な変更点は以下の通りです。

1.  **`src/cmd/internal/gc/go.go`**: `Sym` (シンボル) 構造体に `whyPushed uint8` という新しいフィールドが追加されました。このフィールドは、シンボルが宣言スタックにプッシュされた理由 (`Node.Op` の値、例えば型宣言なら `OTYPE`、変数宣言なら `ONAME`) を記録するために使用されました。
2.  **`src/cmd/internal/gc/dcl.go`**: `popdcl()` 関数内で、シンボルが宣言スタックからポップされる際に、そのシンボルの `whyPushed` フィールドに `s.Def.Op` の値が設定されるようになりました。
3.  **`src/cmd/internal/gc/gen.go`**: `checkgoto()` 関数（`goto` 文の検証を担当）が修正されました。
    *   `goto` とラベルの間にあるシンボルを走査し、それらがすべて型宣言 (`whyPushed == OTYPE`) であれば、`goto` を有効とみなし、エラーを発生させずに早期リターンするロジックが追加されました。
    *   変数宣言など、型宣言以外の宣言を飛び越える場合にのみエラーを報告するように、既存のエラーチェックロジックに `ts.whyPushed != OTYPE` という条件が追加されました。
4.  **`test/goto.go`**: `issue 8042` に関連する新しいテストケースが追加されました。これにより、`goto` が型宣言を飛び越えるコードが正しくコンパイルされること、そして変数宣言を飛び越える場合は引き続きエラーとなることが検証されました。

この変更の目的は、`goto` 文が型宣言を飛び越えることを許可することで、コンパイラの `goto` 検証が過度に厳格であるという問題を解決することでした。

## 前提知識の解説

### Go言語の `goto` 文

Go言語には `goto` 文が存在しますが、その使用には厳格な制限があります。主な制限の一つは、`goto` が変数宣言を飛び越えてジャンプすることを禁止している点です。これは、ジャンプ先のコードが、ジャンプ元では宣言されていなかった変数を使用しようとする可能性があり、未初期化変数の使用やスコープの混乱といった問題を引き起こすためです。

例:
```go
func main() {
    goto L1
    x := 10 // ここで x が宣言されている
L1:
    // ここで x を使おうとするとエラーになる可能性がある
    fmt.Println(x) // コンパイルエラー: goto L1 jumps over declaration of x
}
```

しかし、型宣言は変数宣言とは異なり、実行時の状態に直接影響を与えません。型はコンパイル時に解決される概念であり、`goto` が型宣言を飛び越えても、未初期化変数の問題は発生しません。この違いが、元のコミットで `goto` 検証の緩和が試みられた理由の根底にあります。

### Goコンパイラの `cmd/internal/gc` パッケージ

`cmd/internal/gc` は、Go言語の公式コンパイラのフロントエンド部分を構成するパッケージです。ソースコードの解析、抽象構文木 (AST) の構築、型チェック、スコープ解決、そして最終的なコード生成の中間表現への変換など、コンパイルプロセスの初期段階から中間段階までを担います。

*   **シンボルテーブル (Symbol Table)**: コンパイラは、プログラム内で宣言された識別子（変数名、関数名、型名など）に関する情報を管理するためにシンボルテーブルを使用します。各シンボルは、その名前、型、スコープ、ストレージクラスなどの属性を持ちます。
*   **宣言スタック (Declaration Stack)**: Goコンパイラは、スコープの概念を管理するために宣言スタックを使用します。新しいブロック（例えば `if` 文や `for` ループのブロック）に入ると、そのブロック内で宣言されたシンボルがスタックにプッシュされます。ブロックを抜けると、そのブロック内でプッシュされたシンボルはスタックからポップされ、スコープ外となります。`goto` 文の検証では、ジャンプ元とジャンプ先の間の宣言スタックの状態を比較し、飛び越された宣言がないかを確認します。

### Go言語の型宣言と変数宣言

*   **型宣言 (Type Declaration)**: `type MyInt int` のように、新しい型を定義します。これはコンパイル時に型システムに新しい名前を導入するものであり、実行時にメモリを割り当てたり、特定の値を保持したりするものではありません。
*   **変数宣言 (Variable Declaration)**: `var x int` や `x := 10` のように、変数を宣言し、必要に応じて初期化します。これは実行時にメモリを割り当て、値を保持するエンティティを作成します。

`goto` 文の制限は、主に変数宣言が関係する実行時の状態変化に起因するため、型宣言は異なる扱いを受けるべきだという議論がありました。

## 技術的詳細

このRevertコミットは、元のコミットが導入した `goto` 文の検証ロジックの変更を元に戻すものです。元のコミットでは、`goto` が型宣言を飛び越えることを許可するために、コンパイラの内部構造にいくつかの変更が加えられました。

### 元コミットにおける `goto` 文の検証ロジックの変更

元のコミットでは、`cmd/internal/gc` パッケージ内の `checkgoto` 関数が `goto` 文の検証を担当していました。この関数は、`goto` のジャンプ元とジャンプ先の間のスコープで、どのような宣言が飛び越されているかを分析します。

1.  **`Sym` 構造体への `whyPushed` フィールドの追加**:
    `src/cmd/internal/gc/go.go` にある `Sym` 構造体は、コンパイラが識別子に関する情報を格納するために使用するものです。元のコミットでは、この構造体に `whyPushed uint8` フィールドが追加されました。このフィールドは、シンボルが宣言スタックにプッシュされた理由（例えば、型宣言 (`OTYPE`) なのか、変数宣言 (`ONAME`) なのか）を記録することを目的としていました。これにより、`goto` 検証時に型宣言と変数宣言を区別できるようになります。

2.  **`popdcl` 関数での `whyPushed` の設定**:
    `src/cmd/internal/gc/dcl.go` の `popdcl` 関数は、宣言スタックからシンボルをポップする際に呼び出されます。元のコミットでは、この関数内でシンボルの `whyPushed` フィールドに、そのシンボルが定義された際の `Node.Op` の値が設定されるようになりました。

3.  **`checkgoto` 関数での型宣言の無視**:
    `src/cmd/internal/gc/gen.go` の `checkgoto` 関数は、`goto` 文のジャンプ元とジャンプ先の間の宣言スタックの状態を比較し、飛び越された宣言がないかを確認します。元のコミットでは、この関数に以下のロジックが追加されました。
    *   `goto` とラベルの間に存在するすべてのシンボルが `whyPushed == OTYPE` (つまり型宣言) である場合、`goto` は有効であると判断され、エラーを報告せずに処理を終了します。
    *   既存のエラーチェックロジックも修正され、`whyPushed != OTYPE` のシンボル（つまり変数宣言など）のみが `goto` 検証エラーの対象となるように変更されました。

### Revertによる影響

このRevertコミットは、上記の変更をすべて元に戻します。
*   `Sym` 構造体から `whyPushed` フィールドが削除されます。
*   `popdcl` 関数での `whyPushed` の設定ロジックが削除されます。
*   `checkgoto` 関数から、型宣言を無視するロジックおよび `whyPushed` を参照するロジックが削除されます。
*   元のコミットで追加された `test/goto.go` のテストケースも削除されます。

これにより、Goコンパイラの `goto` 検証は、元のコミットが導入される前の状態に戻ります。つまり、`goto` 文は型宣言を飛び越えることも許可されなくなり、変数宣言を飛び越える場合と同様にエラーとして扱われるようになります。このRevertは、元の変更が「全てのビルドを壊した」という重大な問題を引き起こしたため、安定性を最優先した結果です。

# [インデックス 21453] ファイルの概要

このコミットは、Goランタイムにおけるメモリ割り当ての挙動、特に`wbshadow`（ライトバリアシャドウ）領域の確保に関する問題を修正するものです。64-bitシステムにおいて、`sysReserve`関数が要求された全量を予約できない場合があるという`ulimit`関連の問題に対処するため、カーネルにアドレス選択を任せるのではなく、明示的に高位アドレスに`wbshadow`領域を割り当てるように変更されました。これにより、メモリ予約の信頼性が向上し、Goランタイムの安定性が確保されます。

## コミット

```
runtime: allocate wbshadow at high address

sysReserve doesn't actually reserve the full amount requested on
64-bit systems, because of problems with ulimit. Instead it checks
that it can get the first 64 kB and assumes it can grab the rest as
needed. This doesn't work well with the "let the kernel pick an address"
mode, so don't do that. Pick a high address instead.

Reviewed-on: https://go-review.googlesource.com/2345
Reviewed-by: Rick Hudson <rlh@golang.org>
```

## 元コミット内容

Goランタイムが`wbshadow`領域を確保する際、64-bitシステムで`sysReserve`が要求されたメモリ量を完全に予約できない問題がありました。これは`ulimit`の設定に起因する可能性があり、特にカーネルにアドレス選択を任せた場合に顕著でした。このコミットは、この問題を回避するため、`wbshadow`領域を高位アドレスに明示的に割り当てるように変更します。

## 変更の背景

Goランタイムは、プログラムの実行に必要なメモリを効率的に管理するために、オペレーティングシステム（OS）から仮想アドレス空間を予約します。この予約は`sysReserve`のような低レベルなシステムコールを通じて行われます。

コミットメッセージによると、64-bitシステムにおいて`sysReserve`が期待通りに動作しないケースがありました。具体的には、`sysReserve`が要求されたメモリの全量を一度に予約できず、代わりに最初の64KBのみをチェックし、残りは必要に応じて取得できると仮定していました。この挙動は、OSが仮想アドレス空間内のどこにメモリを割り当てるかを決定する「カーネルにアドレス選択を任せる」モードでは問題を引き起こす可能性がありました。

この問題の根源は、`ulimit`（特に`ulimit -v`または`RLIMIT_AS`、仮想メモリサイズ制限）の設定に関連していると考えられます。Goランタイムは、ヒープなどのために非常に大きな仮想アドレス空間を事前に予約する設計になっています。この事前予約は、メモリの断片化を減らし、アロケーションの効率を高めるための戦略です。しかし、`ulimit -v`が厳しく設定されている環境では、Goランタイムが要求する広大な仮想アドレス空間の予約が制限され、`sysReserve`が失敗したり、部分的な予約しか行えなかったりする事態が発生していました。

`wbshadow`領域は、GoのコンカレントGC（ガベージコレクション）におけるライトバリア機構の一部として使用される重要なメモリ領域です。ライトバリアは、GCがヒープをスキャンしている間に、ミューテーター（ユーザープログラム）がポインタを変更するのを追跡し、GCの正確性を保証するために不可欠です。この`wbshadow`領域の確保が不安定であると、GCの動作に悪影響を及ぼし、ランタイムの安定性やパフォーマンスに問題が生じる可能性がありました。

このコミットは、この不安定性を解消し、`wbshadow`領域の確実な確保を保証することを目的としています。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルなシステム。ガベージコレクション、スケジューリング、メモリ管理など、Go言語の並行処理と効率的な実行を支える中核部分です。
*   **仮想メモリ (Virtual Memory)**: OSが提供するメモリ管理の抽象化層。各プロセスは、物理メモリの実際の配置とは独立した、連続した仮想アドレス空間を持つことができます。これにより、プログラムは物理メモリの制約から解放され、より大きなメモリ空間を扱えるようになります。
*   **`sysReserve`**: GoランタイムがOSから仮想アドレス空間を予約するために使用する低レベルな関数。この関数は、物理メモリを割り当てることなく、単にアドレス空間を「予約」します。予約されたアドレス空間は、後で必要に応じて物理メモリにマッピング（コミット）されます。
*   **`ulimit`**: Unix系OSにおけるユーザープロセスが利用できるシステムリソース（ファイルディスクリプタ数、CPU時間、メモリサイズなど）を制限するためのコマンドまたはシステムコール。特に`ulimit -v`（または`RLIMIT_AS`）は、プロセスが使用できる仮想メモリの総量を制限します。Goランタイムが大量の仮想アドレス空間を予約しようとすると、この`ulimit`設定に抵触する可能性があります。
*   **ライトバリア (Write Barrier)**: コンカレントガベージコレクタにおいて、ミューテーター（ユーザープログラム）がヒープ上のポインタを書き換える際に実行される小さなコードスニペット。GoのGCは、プログラムが実行中にGCを並行して行うため、ライトバリアを使用して、GCがオブジェクトグラフをスキャンしている間にポインタの変更を追跡し、GCの正確性を保証します。
*   **`wbshadow`**: Goランタイムのライトバリア実装に関連する内部的なメモリ領域。正確な定義はGoのバージョンや実装によって異なりますが、一般的にはライトバリアの動作をサポートするためのメタデータやシャドウメモリとして使用されます。この領域は、GCがオブジェクトの参照関係を正しく追跡するために重要です。
*   **高位アドレス (High Address)**: 仮想アドレス空間における、より大きなアドレス値を持つ領域。64-bitシステムでは、非常に広大な仮想アドレス空間が利用可能であり、OSやランタイムは特定の目的のためにこの空間の特定の部分（例えば、高位アドレス側）を使用することがあります。

## 技術的詳細

このコミットの核心は、`sysReserve`の挙動と`ulimit`の相互作用、そしてその解決策としての「高位アドレスへの明示的な割り当て」です。

1.  **`sysReserve`の挙動の課題**:
    *   Goランタイムは、ヒープなどのために`mheap_.arena_end-mheap_.arena_start`や`end-start`といった大きなサイズの仮想アドレス空間を`sysReserve`で予約しようとします。
    *   本来、`sysReserve(nil, size, &reserved)`のように第一引数に`nil`を渡すと、OSが適切なアドレスを選択してくれます。しかし、64-bitシステムでは、この「カーネルにアドレス選択を任せる」モードで、`ulimit -v`などの仮想メモリ制限が厳しい場合に、要求された全量を予約できない問題がありました。
    *   コミットメッセージによると、`sysReserve`は「最初の64KBを取得できることを確認し、残りは必要に応じて取得できると仮定する」という挙動をしていました。これは、OSが実際にその広大な領域を一度に確保できる保証がない場合に、後続のメモリ確保で問題を引き起こす可能性がありました。特に、`wbshadow`のような重要な領域では、このような不確実性は許容できません。

2.  **`ulimit`との関連**:
    *   Goランタイムが大量の仮想アドレス空間を事前に予約する設計は、`ulimit -v`によって設定されるプロセスの仮想メモリサイズ制限に抵触する可能性があります。たとえ物理メモリがコミットされていなくても、仮想アドレス空間の予約自体がこの制限にカウントされるため、`ulimit`が低いと`sysReserve`が失敗することがあります。
    *   カーネルがアドレスを選択するモードでは、OSは利用可能なアドレス空間の中から最適な場所を探しますが、その際に`ulimit`の制約が影響し、Goランタイムが期待するような連続した広大な領域を確保できない、あるいは部分的な確保しかできない状況が発生していました。

3.  **解決策: `sysReserveHigh`の導入と高位アドレスへの割り当て**:
    *   このコミットは、`sysReserve`を直接呼び出す代わりに、新しく導入された`sysReserveHigh`関数を使用するように変更します。
    *   `sysReserveHigh`関数は、64-bitシステムの場合に、明示的に高位アドレス（例: `0x7f`から始まるアドレス範囲）にメモリを予約しようとします。
    *   具体的には、`for i := 0; i <= 0x7f; i++`ループ内で、`uintptr(i)<<40 | uintptrMask&(0x00c0<<32)`のような計算によって、高位アドレスの候補を生成し、そのアドレスを`sysReserve`の第一引数に渡して予約を試みます。
    *   これにより、OSにアドレス選択を任せるのではなく、Goランタイムが積極的に高位アドレスを試行することで、`ulimit`の制約を受けにくい、より安定したメモリ予約が可能になります。高位アドレスは、通常、ユーザープログラムのヒープやスタックとは異なる領域に位置するため、競合が少なく、広大な連続領域を確保しやすいという利点があると考えられます。
    *   32-bitシステムの場合は、この問題は発生しないため、引き続き`sysReserve(nil, n, reserved)`が呼び出されます。

この変更により、Goランタイムは`wbshadow`領域をより確実に確保できるようになり、結果としてガベージコレクションの安定性と信頼性が向上します。

## コアとなるコードの変更箇所

変更は`src/runtime/malloc1.go`ファイルに集中しています。

1.  **`wbshadowinit()`関数の変更**:
    *   `wbshadowinit()`関数内で、`wbshadow`領域と`mheap_.data`領域を予約する際に、`sysReserve(nil, ...)`の呼び出しが`sysReserveHigh(...)`に置き換えられました。

    ```diff
    --- a/src/runtime/malloc1.go
    +++ b/src/runtime/malloc1.go
    @@ -235,7 +235,7 @@ func wbshadowinit() {
     	}

     	var reserved bool
    -	p1 := sysReserve(nil, mheap_.arena_end-mheap_.arena_start, &reserved)
    +	p1 := sysReserveHigh(mheap_.arena_end-mheap_.arena_start, &reserved)
     	if p1 == nil {
     		throw("cannot map shadow heap")
     	}
    @@ -275,7 +275,7 @@ func wbshadowinit() {
     	mheap_.data_start = start
     	mheap_.data_end = end
     	reserved = false
    -	p1 = sysReserve(nil, end-start, &reserved)
    +	p1 = sysReserveHigh(end-start, &reserved)
     	if p1 == nil {
     		throw("cannot map shadow data")
     	}
    ```

2.  **`sysReserveHigh()`関数の新規追加**:
    *   `sysReserveHigh`という新しい関数が追加されました。この関数は、64-bitシステムでのみ高位アドレスへの予約ロジックを実行します。

    ```go
    // sysReserveHigh reserves space somewhere high in the address space.
    // sysReserve doesn't actually reserve the full amount requested on
    // 64-bit systems, because of problems with ulimit. Instead it checks
    // that it can get the first 64 kB and assumes it can grab the rest as
    // needed. This doesn't work well with the "let the kernel pick an address"
    // mode, so don't do that. Pick a high address instead.
    func sysReserveHigh(n uintptr, reserved *bool) unsafe.Pointer {
    	if ptrSize == 4 { // 32-bit system
    		return sysReserve(nil, n, reserved)
    	}

    	// 64-bit system: try to reserve at a high address
    	for i := 0; i <= 0x7f; i++ {
    		p := uintptr(i)<<40 | uintptrMask&(0x00c0<<32)
    		*reserved = false
    		p = uintptr(sysReserve(unsafe.Pointer(p), n, reserved))
    		if p != 0 {
    			return unsafe.Pointer(p)
    		}
    	}

    	// Fallback if high address reservation fails
    	return sysReserve(nil, n, reserved)
    }
    ```

## コアとなるコードの解説

*   **`wbshadowinit()`の変更**:
    *   この関数は、Goランタイムの初期化フェーズで`wbshadow`領域をセットアップする役割を担っています。以前は`sysReserve(nil, ...)`を使ってOSにアドレス選択を任せていましたが、このコミットにより`sysReserveHigh(...)`を呼び出すように変更されました。これにより、`wbshadow`領域の確保がより堅牢になります。

*   **`sysReserveHigh()`関数のロジック**:
    *   **32-bitシステムの場合**: `ptrSize == 4`（ポインタサイズが4バイト、つまり32-bitアーキテクチャ）の場合、`ulimit`による仮想メモリの制約は通常問題にならないため、従来の`sysReserve(nil, n, reserved)`を呼び出します。
    *   **64-bitシステムの場合**:
        *   `for i := 0; i <= 0x7f; i++`ループは、複数の高位アドレスの候補を試行するためのものです。`i`の値を変えることで、異なる高位アドレスの範囲を探索します。
        *   `p := uintptr(i)<<40 | uintptrMask&(0x00c0<<32)`: この行は、高位アドレスの候補を生成するGoランタイム固有のロジックです。`uintptrMask`はシステム依存のマスク値で、アドレス空間の特定のビットを操作します。`i<<40`は、アドレスの非常に高いビットを操作し、高位アドレス空間の異なるセグメントを試行することを意味します。`0x00c0<<32`もアドレスの特定の部分を固定するためのものです。この組み合わせにより、Goランタイムが特定の高位アドレス範囲を狙ってメモリを予約しようとします。
        *   `sysReserve(unsafe.Pointer(p), n, reserved)`: 生成された高位アドレス`p`を第一引数に渡して`sysReserve`を呼び出します。これにより、OSにアドレス選択を任せるのではなく、Goランタイムが指定したアドレスからメモリを予約するよう試みます。
        *   `if p != 0`: 予約が成功した場合（返されたポインタが`nil`でない場合）、そのアドレスを返して処理を終了します。
        *   **フォールバック**: ループ内のすべての高位アドレスの試行が失敗した場合、最終的に`sysReserve(nil, n, reserved)`を呼び出して、OSにアドレス選択を任せる従来のフォールバックメカニズムに戻ります。これは、高位アドレスでの予約が何らかの理由で不可能な場合の安全策です。

この`sysReserveHigh`関数の導入により、Goランタイムは`ulimit`などの外部要因によるメモリ予約の失敗リスクを軽減し、`wbshadow`領域のような重要な内部構造の確保をより確実に実行できるようになりました。

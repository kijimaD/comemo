## 変更の背景

このコミットの背景には、GoランタイムがSolarisオペレーティングシステム上でC標準ライブラリ（libc）関数を呼び出す際のリンキングメカニズムに関する理解の誤りがありました。

Goは通常、静的リンクを好み、ほとんどの依存関係を単一のバイナリにバンドルします。しかし、Solarisのような一部のOSでは、安定した直接的なシステムコールインターフェースが提供されていないため、Goランタイムはシステムコールを`libc`経由でルーティングする必要があります。このため、Goプログラムは`libc`に対して動的にリンクされます。

以前の変更（"previous CL"）では、`libcFunc`というGoランタイム内部の型が、C関数のアドレスを直接保持していると誤解されていた可能性があります。しかし、Solarisのリンカは、外部シンボル（この場合は`libcFunc`が参照するC関数）に対して常にProcedure Linkage Table（PLT）を使用します。PLTは、共有ライブラリ内の関数への呼び出しを仲介するためのメカニズムです。

このPLTの挙動により、`libcFunc`自体はC関数の直接のアドレスではなく、リンカが解決すべき「外部シンボル」として扱われるべきでした。以前の変更ではこの点が考慮されていなかったため、`libcFunc`の値を直接関数ポインタとして使用しようとすると、リンキングエラーや実行時エラーが発生する「breakage」（不具合）が生じていました。

このコミットは、`libcFunc`を「実際の外部シンボル」として扱い、その「アドレス」をロードするように修正することで、この不具合を解消することを目的としています。

## 前提知識の解説

### 1. GoランタイムとSolarisのシステムコール

Goプログラムは、OSの機能を利用するためにシステムコールを発行します。LinuxのようなOSでは、Goランタイムは多くの場合、直接カーネルのシステムコールインターフェースを呼び出すことができます。しかし、Solarisでは、安定した直接のシステムコールインターフェースが公開されていないため、GoランタイムはC標準ライブラリ（`libc`）を介してシステムコールを間接的に呼び出す必要があります。

Goランタイムには、`sysvicall`のような関数群があり、これらはGoのABI（Application Binary Interface）からCのABIへの変換を処理し、Cライブラリ関数を呼び出すためのブリッジとして機能します。`libcFunc`は、これらの`sysvicall`関数に渡されるCライブラリ関数のアドレスを表すためにGoランタイム内で使用される型（通常は`uintptr`）です。

### 2. 動的リンク、PLT (Procedure Linkage Table) および GOT (Global Offset Table)

Unix系OS（Solarisを含む）では、実行可能ファイルと共有ライブラリ（`.so`ファイル）はELF (Executable and Linkable Format) 形式を使用します。動的リンクは、プログラムが実行時に共有ライブラリの関数やデータを利用するためのメカニズムです。

*   **外部シンボル**: プログラム内で宣言されているが、別のコンパイル単位（例: `libc.so`）で定義されている関数や変数を指します。
*   **Procedure Linkage Table (PLT)**: 共有ライブラリ内の外部関数を呼び出す際に使用されるテーブルです。PLTは小さなコードスタブの集まりで、プログラムが外部関数を呼び出すと、直接その関数にジャンプするのではなく、まずPLT内の対応するエントリにジャンプします。
*   **Global Offset Table (GOT)**: グローバルシンボル（関数や変数）のアドレスを格納するテーブルです。PLTと連携して動作します。

**PLTとGOTによるシンボル解決のプロセス（遅延バインディング）**:

1.  **初回呼び出し**: プログラムが外部関数（例: `printf`）を初めて呼び出すと、コンパイラは`printf@plt`のようなPLTエントリへの呼び出しを生成します。
2.  **PLTスタブの実行**: PLTエントリは、対応するGOTエントリにジャンプします。初期状態では、GOTエントリには実際の関数のアドレスではなく、動的リンカの解決ルーチンへのポインタが格納されています。
3.  **動的リンカによる解決**: 動的リンカ（Solarisでは`ld.so`）が呼び出され、要求された関数（`printf`）をロード済みの共有ライブラリから探し、その実際のメモリ上のアドレスを特定します。
4.  **GOTの更新**: 動的リンカは、特定した実際の関数のアドレスでGOTエントリを更新します。
5.  **関数実行**: 動的リンカは、実際の関数アドレスにジャンプして関数を実行します。
6.  **2回目以降の呼び出し**: 同じ関数が再度呼び出されると、PLTエントリは更新されたGOTエントリを直接参照し、動的リンカを介さずに実際の関数アドレスにジャンプします。これにより、2回目以降の呼び出しは高速になります。

このメカニズムは、Position-Independent Code (PIC) や Address Space Layout Randomization (ASLR) といった現代のOSのセキュリティおよび効率化技術において不可欠です。

## 技術的詳細

このコミットの核心は、Solarisリンカが外部シンボルを扱う際の挙動、特にPLTの使用方法にあります。

Goランタイムの`sysvicall`関数群（`sysvicall0`, `sysvicall1`, ..., `sysvicall6`）は、Cライブラリ関数を呼び出すための汎用的なメカニズムを提供します。これらの関数は、`libcall`構造体を通じて呼び出すC関数のアドレス（`libcall.fn`）と引数を設定し、アセンブリコード（`asmcgocall`）を介して実際のC関数呼び出しを実行します。

以前のコードでは、`libc_fcntl`のような`libcFunc`型の変数を直接`uintptr(fn)`として`libcall.fn`に渡していました。これは、`libc_fcntl`がC関数のアドレスを直接保持しているという仮定に基づいています。

しかし、Solarisのリンカは、`libc_fcntl`のような外部シンボルを、実行時にPLTを介して解決されるべきシンボルとして扱います。つまり、`libc_fcntl`というシンボル自体は、そのシンボルが指すC関数のアドレスを直接の値として持っているわけではありません。むしろ、`libc_fcntl`は、そのシンボルがメモリ上のどこに配置されているかを示すアドレスであり、そのアドレスにアクセスすることで、PLTを介した解決プロセスが開始されます。

このコミットでは、このSolarisリンカの挙動に合わせて、`libcFunc`型の変数を`sysvicall`関数に渡す際、または`libcall.fn`に代入する際に、その「アドレス」を取得するように変更しています。具体的には、`fn`を`libcFunc`型から`*libcFunc`型（`libcFunc`へのポインタ）に変更し、呼び出し箇所では`libc_fcntl`を`&libc_fcntl`のようにアドレス演算子`&`を付けて渡しています。

これにより、`libcall.fn`には`libc_fcntl`シンボル自体のメモリ上のアドレスが設定され、Goランタイムはこれを外部シンボルへのポインタとして正しく解釈し、Solarisの動的リンカがPLT/GOTメカニズムを通じて実際のC関数アドレスを解決できるようになります。

アセンブリコード（`src/runtime/sys_solaris_amd64.s`）における変更も同様の理由です。例えば、`runtime·nanotime1`関数内で`libc_clock_gettime`を呼び出す際、以前は`MOVQ libc_clock_gettime(SB), AX`としていましたが、これは`libc_clock_gettime`の「値」（つまり、それが直接指すアドレス）を`AX`レジスタにロードしようとするものです。しかし、SolarisのPLTの挙動を考慮すると、`libc_clock_gettime`シンボル自体の「アドレス」をロードし、それを介してPLT解決をトリガーする必要があります。そのため、`LEAQ libc_clock_gettime(SB), AX`（Load Effective Address）に変更されています。`LEAQ`命令は、オペランドのアドレスをレジスタにロードするため、`libc_clock_gettime`シンボルがメモリ上のどこにあるかという情報を`AX`に格納します。これにより、GoランタイムはC関数への正しい呼び出しパスを確立できます。

## コアとなるコードの解説

変更の核心は、GoランタイムがSolaris上でCライブラリ関数を呼び出す際に、その関数のアドレスをどのように取得し、`sysvicall`メカニズムに渡すかという点にあります。

以前のコードでは、`libc_fcntl`のような`libcFunc`型の変数を直接`sysvicall`関数に渡していました。これは、`libc_fcntl`がC関数のエントリポイントの直接のアドレスを値として持っているという仮定に基づいています。しかし、Solarisのリンカは、共有ライブラリの外部関数呼び出しに対してPLTを使用するため、`libc_fcntl`は直接のアドレスではなく、PLTを介して解決されるべき「外部シンボル」として扱われます。

このコミットでは、この問題を解決するために、`libc_fcntl`のような`libcFunc`型の変数を`sysvicall`関数に渡す際に、その「アドレス」を取得するように変更しています。

例えば、`src/runtime/netpoll_solaris.go`の`fcntl`関数では、
```go
// 変更前
return int32(sysvicall3(libc_fcntl, uintptr(fd), uintptr(cmd), arg))
// 変更後
return int32(sysvicall3(&libc_fcntl, uintptr(fd), uintptr(cmd), arg))
```
のように、`libc_fcntl`の前にアドレス演算子`&`が追加されています。これにより、`sysvicall3`関数には`libc_fcntl`シンボルがメモリ上のどこに配置されているかというアドレスが渡されます。

`src/runtime/os_solaris.go`の`sysvicall`関数群の定義も変更され、`fn libcFunc`が`fn *libcFunc`となっています。これにより、これらの関数は`libcFunc`型の値ではなく、そのポインタを受け取ることを明示しています。そして、`libcall.fn`への代入も`uintptr(fn)`から`uintptr(unsafe.Pointer(fn))`に変更され、受け取ったポインタを`uintptr`に変換して`libcall.fn`に格納しています。

アセンブリコード`src/runtime/sys_solaris_amd64.s`における`MOVQ`から`LEAQ`への変更も同様の目的です。
例えば、`runtime·nanotime1`関数内の`libc_clock_gettime`の呼び出しでは、
```assembly
// 変更前
MOVQ    libc_clock_gettime(SB), AX
// 変更後
LEAQ    libc_clock_gettime(SB), AX
```
`MOVQ`は`libc_clock_gettime`シンボルが指すメモリ位置の「内容」を`AX`レジスタにロードしようとします。しかし、PLTのメカニズムでは、その「内容」は直接の関数アドレスではありません。一方、`LEAQ`は`libc_clock_gettime(SB)`というシンボル自体の「アドレス」を`AX`レジスタにロードします。このアドレスが、Solarisの動的リンカがPLTを介して実際の関数アドレスを解決するための出発点となります。

これらの変更により、GoランタイムはSolarisのリンカの挙動と整合性が取れるようになり、Cライブラリ関数への呼び出しが正しく解決され、以前の不具合が修正されました。

# [インデックス 21639] ファイルの概要

このコミットは、Go言語のアセンブラツール `cmd/asm` の中核部分を導入するものです。具体的には、アセンブラのメインドライバである `main.go` と、アセンブリコードの解析および命令生成を担う `internal/asm` サブディレクトリが追加されました。これにより、Go言語のツールチェインにおけるアセンブリコードの処理基盤が確立されました。

## 元コミット内容

`[dev.cc] cmd/asm: the assembler proper`

アセンブラのシンプルなドライバである `main.go` と、パーサーおよび命令ジェネレータを含む `internal/asm` サブディレクトリを追加する。

この実装の多くは、おそらく経験則に基づいているか、せいぜい実験的な現象論に過ぎないかもしれないが、動作するバイナリを生成する。

## 変更の背景

Go言語のツールチェインにおいて、アセンブリ言語で記述されたコードを機械語に変換するアセンブラ `cmd/asm` の中核機能がこのコミットで導入されました。Go言語は、ランタイムのパフォーマンスが重要な部分や、特定のハードウェア機能へのアクセスが必要な場合に、Go独自のPlan 9アセンブリ構文を使用します。このコミット以前は、アセンブリコードの処理がどのように行われていたか不明ですが、このコミットによって、Goツールチェイン内でアセンブリコードを直接処理するための専用ツールが本格的に開発され始めたことを示しています。

コミットメッセージにある「It's likely that much of the implementation is superstition, or at best experimental phenomenology, but it does generate working binaries.」というRob Pike氏のコメントは、このアセンブラがまだ初期段階であり、設計が完全に洗練されているわけではないものの、実用的な結果（動作するバイナリ）を生成できることを示唆しています。これは、まず機能するものを構築し、その後で洗練していくというアジャイルな開発アプローチを反映している可能性があります。

## 前提知識の解説

このコミットを理解するためには、以下の概念が役立ちます。

1.  **Go言語のアセンブリ言語 (Plan 9 Assembly):**
    Go言語は、一般的なx86アセンブリ（AT&T構文やIntel構文）とは異なる、Plan 9オペレーティングシステム由来のアセンブリ構文を採用しています。主な特徴は以下の通りです。
    *   **擬似命令 (Pseudo-ops):** `TEXT` (関数定義), `DATA` (初期化済みデータ), `GLOBL` (グローバルシンボル), `PCDATA` (PC-data), `FUNCDATA` (関数データ) など、アセンブラに特別な指示を与える命令。
    *   **レジスタとベースレジスタ:** `SB` (Static Base: グローバルシンボルや静的データへのオフセットの基準), `FP` (Frame Pointer: 関数の引数へのオフセットの基準), `SP` (Stack Pointer: ローカル変数やスタック上のデータへのオフセットの基準), `PC` (Program Counter: プログラムカウンタ) などが使われます。
    *   **アドレス指定モード:** `offset(base)(index*scale)` のような形式で、複雑なメモリアドレス指定が可能です。
    *   **シンボル名:** Goのパッケージパスを含む `package.function` のような形式でシンボルが表現されます（例: `runtime·sigtramp`）。

2.  **コンパイラ/アセンブラの基本構造:**
    *   **字句解析 (Lexical Analysis):** ソースコードをトークン（意味を持つ最小単位）のストリームに分解するプロセス。このコミットでは `cmd/asm/internal/lex` パッケージがこの役割を担います。
    *   **構文解析 (Parsing):** トークンのストリームを文法規則に従って解析し、抽象構文木 (AST) などの構造化された中間表現を生成するプロセス。このコミットでは `cmd/asm/internal/asm/parse.go` がこの役割を担います。
    *   **コード生成 (Code Generation):** 中間表現からターゲットマシンコード（またはリンカが理解できる形式）を生成するプロセス。このコミットでは `cmd/asm/internal/asm/asm.go` が `cmd/internal/obj` パッケージの構造体 (`obj.Prog`) を利用してこの役割を担います。

3.  **`cmd/internal/obj` パッケージ:**
    Goツールチェインの内部パッケージで、コンパイラ (`cmd/compile`) やアセンブラ (`cmd/asm`) が生成する中間表現（プログラム命令 `obj.Prog` やアドレス `obj.Addr` など）を定義し、リンカ (`cmd/link`) がこれらを処理して最終的な実行可能ファイルを生成します。アセンブラの出力は、この `obj` パッケージのデータ構造に準拠する必要があります。

## 技術的詳細

このコミットは、Goアセンブラの基本的なアーキテクチャを確立しています。

*   **`main.go`:**
    *   アセンブラのエントリポイントとして機能します。
    *   `go/build` パッケージを使用して現在のビルド環境（`GOARCH` など）を検出し、それに基づいてターゲットアーキテクチャ (`arch.Set`) を設定します。
    *   `cmd/internal/obj.Linknew` を呼び出してリンカコンテキストを初期化します。これは、生成されるオブジェクトファイルのメタデータやシンボル情報を管理するために必要です。
    *   `lex.NewLexer` で字句解析器を、`asm.NewParser` で構文解析器を初期化します。
    *   `parser.Parse()` を呼び出してアセンブリソースファイルを解析し、`obj.Prog` のリンクリストを生成します。
    *   最終的に `obj.Writeobjdirect` を使用して、生成された `obj.Prog` リストをGoのオブジェクトファイル形式で出力します。

*   **`internal/asm/parse.go`:**
    *   `Parser` 構造体を定義し、アセンブリソースコードの構文解析を担当します。
    *   `line()` メソッドは、入力ストリームから1行ずつ読み込み、トークンに分解し、命令または擬似命令を識別します。
    *   ラベル (`foo:`) の処理を行い、後でジャンプ命令のターゲットを解決するために `labels` マップに格納します。
    *   `operand()` メソッドは、アセンブリ命令のオペランド（例: `R1`, `foo(SB)`, `$0x10`）を解析し、`addr.Addr` 構造体に変換します。これは、Goアセンブリの多様なアドレス指定モードを処理するために重要です。
    *   `expr()`, `floatExpr()`, `term()` メソッドは、オペランド内の数値式（例: `$1+2<<3`）を評価します。
    *   `errorf()` メソッドは、エラー報告を処理し、エラーが多すぎる場合はプログラムを終了させます。

*   **`internal/asm/asm.go`:**
    *   `Parser` 構造体のメソッドとして、具体的なアセンブリ命令や擬似命令の処理ロジックを実装します。
    *   `asmText`, `asmData`, `asmGlobl`, `asmPCData`, `asmFuncData` は、それぞれの擬似命令（`TEXT`, `DATA`, `GLOBL`, `PCDATA`, `FUNCDATA`）を解析し、対応する `obj.Prog` 構造体を生成します。これらの擬似命令は、関数、データセクション、グローバルシンボル、デバッグ情報などを定義するために使用されます。
    *   `asmInstruction` は、一般的なアセンブリ命令（例: `MOVW`, `ADDL`）を処理し、オペランドの数に応じて `obj.Prog` 構造体の `From` および `To` フィールドを設定します。
    *   `asmJump` は、ジャンプ命令（`JMP`, `CALL` など）を処理し、ターゲットアドレスがラベルである場合は `toPatch` リストに格納して後で解決します。
    *   `addrToAddr` は、`addr.Addr` 構造体を `obj.Addr` 構造体に変換する重要な関数です。これは、Goアセンブリの抽象的なアドレス表現を、リンカが理解できる具体的なアドレス表現にマッピングします。特に、`SB`, `FP`, `SP` などのベースレジスタからのオフセットや、シンボルの型 (`D_EXTERN`, `D_STATIC` など) のエンコーディングを扱います。
    *   `link` メソッドは、生成された `obj.Prog` をリンクリストに追加し、プログラムカウンタ (`p.pc`) を更新します。

*   **`internal/asm/overflow.go`:**
    *   `addOverflows`, `subOverflows`, `mulOverflows` といった関数を提供し、`uint64` 型の算術演算におけるオーバーフローを検出します。これは、`parse.go` で数値式を評価する際に、予期せぬオーバーフローによる誤った値の計算を防ぐために使用されます。アセンブラが正確な値を扱う上で不可欠な安全機構です。

これらのファイルが連携することで、Goアセンブラはアセンブリソースコードを読み込み、解析し、Goリンカが処理できる中間表現に変換する一連のプロセスを実行します。

```go
func main() {
	// ... (フラグ解析、ロギング設定) ...

	GOARCH := build.Default.GOARCH
	architecture := arch.Set(GOARCH)
	if architecture == nil {
		log.Fatalf("asm: unrecognized architecture %s", GOARCH)
	}

	// ... (リンカコンテキストの初期化) ...

	lexer := lex.NewLexer(flag.Arg(0), ctxt)
	parser := asm.NewParser(ctxt, architecture, lexer)
	pList := obj.Linknewplist(ctxt)

	pList.Firstpc, ok = parser.Parse()

		log.Print("FAIL TODO")
		os.Exit(1)
	}
	obj.Writeobjdirect(ctxt, output)
	// ...
}
```
`main.go` はアセンブラの実行フローを制御します。`build.Default.GOARCH` からターゲットアーキテクチャを特定し、それに応じた `arch.Arch` インスタンスを設定します。次に、`lex.NewLexer` でソースファイルを読み込む字句解析器を、`asm.NewParser` でそのトークンを解析する構文解析器を生成します。`parser.Parse()` が呼び出されると、アセンブリコードの解析が開始され、結果として `obj.Prog` のリンクリストが構築されます。最後に、`obj.Writeobjdirect` を使って、このリンクリストをGoのオブジェクトファイル形式で出力します。

### `src/cmd/asm/internal/asm/parse.go`

```go
type Parser struct {
	// ... (フィールド定義) ...
}

func NewParser(ctxt *obj.Link, ar *arch.Arch, lexer lex.TokenReader) *Parser {
	return &Parser{
		linkCtxt: ctxt,
		arch:     ar,
		lex:      lexer,
		labels:   make(map[string]*obj.Prog),
		dataAddr: make(map[string]int64),
	}
}

func (p *Parser) Parse() (*obj.Prog, bool) {
	for p.line() { // 1行ずつ解析
	}
	if p.errorCount > 0 {
		return nil, false
	}
	p.patch() // 未解決のジャンプターゲットを解決
	return p.firstProg, true
}

func (p *Parser) line() bool {
	// ... (トークン読み込み、ラベル処理) ...
	if tok != scanner.Ident {
		p.errorf("expected identifier, found %q", p.lex.Text())
		return false
	}
	word := p.lex.Text()
	// ... (オペランド解析) ...
	if i := p.arch.Pseudos[word]; i != 0 {
		p.pseudo(i, word, operands) // 擬似命令の処理
		return true
	}
	if i := p.arch.Instructions[word]; i != 0 {
		p.instruction(i, word, operands) // 通常命令の処理
		return true
	}
	p.errorf("unrecognized instruction %s", word)
	return true
}
```
`parse.go` の `Parser` は、アセンブリソースコードをGoリンカの内部表現に変換する中心的な役割を担います。`Parse()` メソッドは `line()` を繰り返し呼び出し、各行を処理します。`line()` は、まず命令名（または擬似命令名）を識別し、その後に続くオペランドを解析します。命令が擬似命令 (`TEXT`, `DATA` など) であれば `p.pseudo()` を、通常の命令であれば `p.instruction()` を呼び出して、それぞれ `asm.go` に実装された具体的なアセンブリロジックに処理を委譲します。また、`p.patch()` は、前方参照されるラベル（ジャンプ命令のターゲットなど）を、すべての命令が解析された後に解決する役割を持ちます。

```go
	case 1: // ...
	case 2: // ...
```

`asm.go` は、`parse.go` から渡された解析済みの情報に基づいて、具体的な `obj.Prog` 命令を構築します。`addrToAddr` 関数は、Goアセンブリの抽象的なアドレス表現 (`addr.Addr`) を、リンカが期待する具体的なアドレス表現 (`obj.Addr`) に変換する最も重要な部分です。これには、シンボル、レジスタ、オフセット、スケールなどの様々な要素が考慮されます。`asmText`, `asmData` などの擬似命令ハンドラや `asmInstruction` は、それぞれの命令タイプに応じた `obj.Prog` を生成し、`p.link` を通じて命令リンクリストに追加します。

### `src/cmd/asm/internal/asm/overflow.go`

```go
func addOverflows(a, b uint64) bool {
	return a+b < a
}

func subOverflows(a, b uint64) bool {
	return a-b > a
}

func mulOverflows(a, b uint64) bool {
	if a <= 1 || b <= 1 {
		return false
	}
	c := a * b
	return c/b != a
}
```
`overflow.go` は、`parse.go` で数値式を評価する際に使用される、`uint64` 型の算術オーバーフロー検出関数を提供します。例えば、`addOverflows(a, b uint64)` は、`a + b` が `a` よりも小さくなる場合にオーバーフローが発生したと判断します。これは、符号なし整数の特性を利用した簡潔なチェック方法です。これらの関数は、アセンブラが数値定数を正確に処理し、予期せぬ結果を避けるために不可欠です。

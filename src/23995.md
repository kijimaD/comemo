## 変更の背景

この変更の背景には、Go言語の依存関係管理における進化と、それに伴うGitサブモジュールの扱いの課題がありました。

Go 1.5では、依存関係管理の改善を目指して「ベンダー実験（vendoring experiment）」が導入されました。これは、プロジェクトの依存関係を `vendor/` ディレクトリ内に配置し、`go` コマンドがこのディレクトリ内のパッケージを解決できるようにする仕組みです。この実験は、従来の `$GOPATH` システムの限界に対処し、再現性のあるビルドを保証するためのより堅牢な方法を提供することを目的としていました。

しかし、このベンダー実験の初期段階では、`go get -u` コマンドがGitサブモジュールを適切に更新できないという問題が浮上しました。これは、Issue #7764「cmd/go: get -u fails with git submodules」として報告されました。多くの開発者が依存関係管理にGitサブモジュールを利用していたため、この問題はベンダー実験の採用を妨げる大きな要因となっていました。

このコミットは、このIssue #7764を解決するために提案されました。`go get` がリポジトリをフェッチまたは更新する際に、単一のコマンドだけでなく、複数のコマンドを実行できるようにすることで、Gitサブモジュールの初期化と更新を `go get` のプロセスに組み込むことが可能になります。これにより、ベンダー実験を使用している場合でも、`go get` がサブモジュールを含むリポジトリを正しく取得・更新できるようになります。

## 前提知識の解説

### `go get` コマンド

`go get` は、Go言語のパッケージをリモートリポジトリからダウンロードし、ビルドしてインストールするためのコマンドです。通常、指定されたパッケージとその依存関係を `$GOPATH/src` ディレクトリに取得します。`-u` フラグを付けると、既存のパッケージとその依存関係を最新バージョンに更新します。

### Gitサブモジュール

Gitサブモジュールは、Gitリポジトリ内に別のGitリポジトリを埋め込む機能です。これにより、あるリポジトリ（親リポジトリ）が、別のリポジトリ（サブモジュール）の特定のコミットを指し示すことができます。これは、プロジェクトが外部のライブラリやコンポーネントに依存している場合に、それらをプロジェクトの一部として管理するのに役立ちます。サブモジュールをクローンした後、`git submodule update --init --recursive` などのコマンドを実行して、サブモジュールの内容を初期化・更新する必要があります。

### Goのベンダー（Vendoring）

Go 1.5で導入されたベンダー機能は、プロジェクトの依存関係をプロジェクト自身の `vendor/` ディレクトリ内にコピーして管理する仕組みです。これにより、プロジェクトは外部の依存関係の特定のバージョンに固定され、ビルドの再現性が向上します。`go` コマンドは、パッケージを解決する際に、まず `vendor/` ディレクトリ内を検索し、見つからなければ `$GOPATH` や `$GOROOT` を検索します。この機能は、Go 1.5では「実験的」なものとして導入され、`GO15VENDOREXPERIMENT` 環境変数によって有効化されていました。

## 技術的詳細

このコミットの主要な技術的変更は、`src/cmd/go/vcs.go` ファイル内の `vcsCmd` 構造体のコマンドフィールドの型変更と、それに関連するコマンド実行ロジックの修正です。

以前の `vcsCmd` 構造体では、`createCmd`、`downloadCmd`、`tagSyncCmd`、`tagSyncDefault` といったフィールドが単一のシェルコマンド文字列を保持する `string` 型でした。しかし、Gitサブモジュールの初期化や更新には、リポジトリのクローンやプルに加えて、`git submodule update --init --recursive` のような追加のコマンドを実行する必要があります。単一の文字列フィールドでは、これらの複数の操作を表現できませんでした。

この変更では、これらのフィールドを `[]string` (文字列スライス) 型に変更しました。これにより、各操作（リポジトリの作成、ダウンロード、タグ同期）に対して複数のコマンドを定義できるようになります。

例えば、Gitの `vcsGit` 定義では、`createCmd` が `[]string{"clone {repo} {dir}", "--git-dir={dir}/.git submodule update --init --recursive"}` のように定義されています。これにより、リポジトリのクローン後にサブモジュールの初期化と更新が自動的に行われるようになります。

また、`vcsCmd` の `create`、`download`、`tagSync` メソッドでは、これらの `[]string` 型のコマンドをループで順次実行するように変更されました。重要なのは、`go15VendorExperiment` というグローバル変数（ベンダー実験が有効かどうかを示すフラグ）と、コマンド文字列に `"submodule"` が含まれているかどうかに基づいて、サブモジュール関連のコマンドの実行が条件付けられている点です。これは、ベンダー実験が有効な場合にのみサブモジュール関連の処理を行うことで、後方互換性を維持しつつ、新しい機能を提供する設計思想を反映しています。

具体的には、`go15VendorExperiment` が `false` で、かつコマンドが `"submodule"` を含む場合、そのコマンドはスキップされます。これにより、ベンダー実験を使用していない環境では、サブモジュール関連の追加コマンドが実行されないようになっています。

## コアとなるコードの解説

このコミットの核心は、`go get` がバージョン管理システム（VCS）と連携してリポジトリを操作する際の柔軟性を高めることにあります。

以前は、`vcsCmd` 構造体内の `createCmd` や `downloadCmd` などのフィールドは単一のシェルコマンド文字列しか保持できませんでした。これは、単純なリポジトリのクローンやプルには十分でしたが、Gitサブモジュールのような追加のセットアップ手順が必要な場合には不十分でした。Gitサブモジュールを含むリポジトリを完全に機能させるには、親リポジトリのクローン後に `git submodule update --init --recursive` のようなコマンドを実行して、サブモジュールの内容を取得・初期化する必要があります。

この変更により、これらのコマンドフィールドが `[]string` 型になったことで、`go get` は一連のコマンドを順次実行できるようになりました。これにより、Gitリポジトリの場合、最初のコマンドでリポジトリをクローンし、次のコマンドでサブモジュールを初期化・更新するといった、複数のステップからなる操作を単一の `go get` 呼び出し内で完結させることが可能になります。

特に注目すべきは、`go15VendorExperiment` フラグと `"submodule"` 文字列のチェックです。これは、Go 1.5のベンダー実験が進行中であった時期の設計上の考慮事項を反映しています。ベンダー実験は、Goの依存関係管理の将来の方向性を示すものでしたが、その時点ではまだ実験的な機能であり、すべてのユーザーが利用しているわけではありませんでした。そのため、サブモジュール関連の処理は、ベンダー実験が有効な場合にのみ実行されるように条件付けられました。これにより、ベンダー実験を使用しない既存のワークフローに影響を与えることなく、新しい機能を追加することができました。

この変更は、`go get` がより複雑なリポジトリ構造、特にサブモジュールを持つリポジトリをより適切に扱えるようにするための重要なステップであり、Goの依存関係管理機能の成熟に向けた一歩となりました。

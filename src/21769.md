# [インデックス 21769] ファイルの概要

このコミットは、Go言語のリンカ（`liblink`）におけるARMアーキテクチャの条件コードの扱いに関する変更です。具体的には、ARMの条件コードの番号付けを変更し、`C_SCOND_NONE`（常に実行される条件）が内部的に0として表現されるように調整しています。これにより、「ゼロの`Prog`」（`scond`フィールドが0の`Prog`構造体）が有用な意味を持つようになります。

## 変更の背景

この変更の主な背景は、Goコンパイラおよびリンカの内部表現における最適化と簡素化です。Goコンパイラのバックエンドでは、`Prog`という構造体が低レベルの機械命令を表現するために使用されます。この`Prog`構造体には、命令の条件実行を制御するための`scond`（condition code）フィールドが含まれています。

ARMアーキテクチャでは、命令は特定の条件が満たされた場合にのみ実行されるように指定できます。この条件は「条件コード」としてエンコードされます。ARMの標準的な条件コードでは、「常に実行」を意味する条件（`AL`または`Always`）は通常、特定の非ゼロの値（例えば14）に割り当てられています。

しかし、Goコンパイラの内部では、`Prog`構造体がゼロ初期化された場合に、その`scond`フィールドも0になります。もし`scond=0`が意味のある「常に実行」というデフォルトの条件に対応していれば、コードの簡潔性や効率性が向上します。例えば、新しい`Prog`インスタンスを作成する際に、明示的に条件を設定する必要がなくなり、デフォルトで「常に実行」となるため、多くの命令で余分な処理が不要になります。

このコミットは、この「ゼロの`Prog`が有用である」という目標を達成するための一歩として、ARM条件コードの内部的なマッピングを変更し、`C_SCOND_NONE`が0になるように調整しています。

## 前提知識の解説

### ARMアーキテクチャと条件実行

ARMプロセッサは、命令の「条件実行」をサポートしています。これは、命令が実行される前に、プロセッサの状態レジスタ（Program Status Register, PSR）内の特定のフラグ（N: Negative, Z: Zero, C: Carry, V: Overflow）をチェックし、その結果に基づいて命令を実行するかどうかを決定する機能です。これにより、分岐命令を減らし、パイプラインのストールを回避することで、コードの効率とパフォーマンスを向上させることができます。

各命令には、2文字の「条件コード」サフィックスを付加できます（例: `ADDEQ`は「等しい場合のみ加算」）。もし条件が満たされなければ、その命令は実行されず、`NOP`（No Operation）として扱われます。

代表的な条件コードには以下のようなものがあります。
*   `EQ` (Equal): Zフラグがセットされている場合
*   `NE` (Not Equal): Zフラグがクリアされている場合
*   `HS`/`CS` (Higher or Same / Carry Set): Cフラグがセットされている場合
*   `LO`/`CC` (Lower / Carry Clear): Cフラグがクリアされている場合
*   `MI` (Minus): Nフラグがセットされている場合
*   `PL` (Plus): Nフラグがクリアされている場合
*   `AL` (Always): 常に実行される（条件なし）

### Goリンカ (`liblink`)

Go言語のビルドプロセスにおいて、Goリンカは非常に重要な役割を担っています。Goは独自の内部リンカ（`go tool link`）を使用しており、これはGo言語自体で書かれています。リンカの主な機能は以下の通りです。
1.  **オブジェクトファイルの結合**: コンパイルされたGoパッケージのオブジェクトファイルと、それらが依存するライブラリを結合します。
2.  **シンボルの解決**: 関数や変数のアドレスを解決し、最終的な実行可能ファイル内の正しい位置にマッピングします。
3.  **再配置**: コンパイラからの指示に基づいて、コードやデータを修正し、最終的な実行可能ファイル内の正しいアドレスを指すようにします。
4.  **実行可能ファイルの生成**: 最終的に、OSが実行できる形式（例: LinuxではELF、WindowsではPE）のバイナリファイルを生成します。

このコミットで言及されている`liblink`は、このGoリンカの内部的なライブラリまたはコンポーネントを指します。

### `Prog`構造体

Goコンパイラの内部、特にSSA（Static Single Assignment）バックエンドにおいて、`obj.Prog`構造体は低レベルの機械命令や操作を表現するための重要なデータ構造です。これは、コンパイラがソースコードを機械語に変換する過程で、中間表現として使用されます。`Prog`構造体は、命令の種類、オペランド、そしてこのコミットの主題である条件コード（`scond`フィールド）などの情報を含んでいます。

### ゼロ値の重要性

プログラミングにおいて、データ構造のゼロ値（Go言語では、数値型は0、ブール型はfalse、文字列型は空文字列、ポインタやスライス、マップ、チャネルなどはnilに初期化される）は特別な意味を持つことがあります。もし、あるフィールドのゼロ値がそのフィールドの最も一般的で安全なデフォルト値と一致する場合、コードはより簡潔になり、バグのリスクも減少します。このコミットでは、`Prog.scond`フィールドのゼロ値が「常に実行」という最も一般的なARM条件コードに対応するように変更することで、この原則を適用しようとしています。

## 技術的詳細

このコミットの核心は、ARM条件コードの内部的な数値マッピングを変更することにあります。ARMの条件コードは通常0から15までの値で表現され、「常に実行」（`AL`）は14に割り当てられています。

この変更では、`C_SCOND_XOR`という定数（値は14）を導入し、既存のARM条件コードの定義をこの`C_SCOND_XOR`とXOR演算した値に再定義しています。

具体的には、`src/cmd/5l/5.out.h`ファイルで以下のように変更されています。

```c
// Before:
// C_SCOND_EQ = 0,
// C_SCOND_NE = 1,
// ...
// C_SCOND_NONE = 14, // ARMのAL (Always) に対応

// After:
// These constants are the ARM condition codes encodings,
// XORed with 14 so that C_SCOND_NONE has value 0,
// so that a zeroed Prog.scond means "always execute".
C_SCOND_XOR = 14,

C_SCOND_EQ = 0 ^ C_SCOND_XOR,   // 0 ^ 14 = 14
C_SCOND_NE = 1 ^ C_SCOND_XOR,   // 1 ^ 14 = 15
// ...
C_SCOND_NONE = 14 ^ C_SCOND_XOR, // 14 ^ 14 = 0
// ...
```

この変更により、`C_SCOND_NONE`の内部表現が0になります。これは、`Prog`構造体の`scond`フィールドがゼロ初期化された場合に、それが自動的に「常に実行」という条件を意味するようになることを意味します。

そして、`src/cmd/5a/a.y`、`src/cmd/5a/lex.c`、`src/cmd/5a/y.tab.c`、`src/liblink/asm5.c`、`src/liblink/list5.c`といったリンカやアセンブラのコード内で、条件コードを扱う際にこの`C_SCOND_XOR`を適用するよう修正が加えられています。例えば、命令のエンコード時に条件コードをビットフィールドに挿入する際や、条件コードを文字列に変換する際に、XOR演算が適用されます。

これにより、Goコンパイラとリンカの内部では、`scond=0`が「常に実行」を意味するようになり、ARM命令の実際のエンコード時には、この内部表現が`C_SCOND_XOR`とXORされることで、正しいARM条件コード（例えば`AL`は14）に変換されます。

この変更は、Goコンパイラの内部的な整合性を高め、`Prog`構造体のデフォルト値がより直感的で有用な意味を持つようにするためのものです。

## コアとなるコードの変更箇所

このコミットは、主に以下のファイル群に影響を与えています。

*   `src/cmd/5a/a.h`: ARMアセンブラのヘッダファイル。`Always`定数の定義が`C_SCOND_NONE`を参照するように変更。
*   `src/cmd/5a/a.y`: ARMアセンブラのYacc（パーサジェネレータ）の定義ファイル。MCR/MRC命令の条件コードエンコード時に`C_SCOND_XOR`を適用。
*   `src/cmd/5a/lex.c`: ARMアセンブラのLex（字句解析器）の定義ファイル。条件コードのシンボル（例: `.EQ`, `.NE`, `.AL`）と内部定数のマッピングを、新しい`C_SCOND_XOR`ベースの定数に更新。
*   `src/cmd/5a/y.tab.c`: `a.y`から生成されるパーサのCソースファイル。MCR/MRC命令の条件コードエンコード時に`C_SCOND_XOR`を適用。
*   `src/cmd/5l/5.out.h`: ARMリンカの出力ヘッダファイル。`C_SCOND_XOR`定数を導入し、すべての`C_SCOND_`定数を`C_SCOND_XOR`とXORした値に再定義。
*   `src/liblink/asm5.c`: ARMアセンブラのコード生成ロジック。命令のエンコード時に`Prog.scond`フィールドから実際のARM条件コードを生成する際に、`C_SCOND_XOR`を適用。
*   `src/liblink/list5.c`: ARMリンカのリスト出力（デバッグ用）ロジック。条件コードを文字列に変換する際に、`C_SCOND_XOR`を適用。

これらの変更は、ARM条件コードの内部表現と、それが実際の機械語命令にエンコードされる際の変換ロジックに一貫性を持たせるためのものです。

## コアとなるコードの解説

最も重要な変更は`src/cmd/5l/5.out.h`にあります。

```c
// src/cmd/5l/5.out.h
enum {
    // ...
    // These constants are the ARM condition codes encodings,
    // XORed with 14 so that C_SCOND_NONE has value 0,
    // so that a zeroed Prog.scond means "always execute".
    C_SCOND_XOR = 14,

    C_SCOND_EQ = 0 ^ C_SCOND_XOR,
    C_SCOND_NE = 1 ^ C_SCOND_XOR,
    C_SCOND_HS = 2 ^ C_SCOND_XOR,
    C_SCOND_LO = 3 ^ C_SCOND_XOR,
    C_SCOND_MI = 4 ^ C_SCOND_XOR,
    C_SCOND_PL = 5 ^ C_SCOND_XOR,
    C_SCOND_VS = 6 ^ C_SCOND_XOR,
    C_SCOND_VC = 7 ^ C_SCOND_XOR,
    C_SCOND_HI = 8 ^ C_SCOND_XOR,
    C_SCOND_LS = 9 ^ C_SCOND_XOR,
    C_SCOND_GE = 10 ^ C_SCOND_XOR,
    C_SCOND_LT = 11 ^ C_SCOND_XOR,
    C_SCOND_GT = 12 ^ C_SCOND_XOR,
    C_SCOND_LE = 13 ^ C_SCOND_XOR,
    C_SCOND_NONE = 14 ^ C_SCOND_XOR, // This becomes 0
    C_SCOND_NV = 15 ^ C_SCOND_XOR,
    // ...
};
```

このコードスニペットは、ARMの条件コードの内部的な数値表現を再定義しています。`C_SCOND_XOR`が14と定義され、すべての条件コードがこの値とXORされています。これにより、元々14であった`C_SCOND_NONE`が`14 ^ 14 = 0`となり、`Prog.scond`が0の場合に「常に実行」を意味するようになります。

他のファイルでは、この新しいマッピングに合わせて、条件コードを扱うロジックが修正されています。例えば、`src/liblink/asm5.c`では、命令のバイナリエンコード時に`Prog.scond`から条件コードビットを抽出する際に、`C_SCOND_XOR`を再度XORしています。

```c
// src/liblink/asm5.c の一部
// Note about encoding: Prog.scond holds the condition encoding,
// but XOR'ed with C_SCOND_XOR, so that C_SCOND_NONE == 0.
// The code that shifts the value << 28 has the responsibility
// for XORing with C_SCOND_XOR too.

// ...

// 例: 命令の条件コードビットをセットする箇所
out[0] = (((p->scond&C_SCOND) ^ C_SCOND_XOR)<<28) | ...;
```

このコメントとコードは、`Prog.scond`が内部的にXORされた値を持っていること、そして実際にARM命令の28ビット目に条件コードを配置する際には、再度`C_SCOND_XOR`とXORして元のARM条件コードに戻す必要があることを明確に示しています。これにより、内部表現の簡素化と、外部（実際のARMバイナリ）との互換性の両立が図られています。

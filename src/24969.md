## 変更の背景

Go言語の仕様書において、複合リテラル（Composite Literals）の構文を説明する記述（プロセ）と、その構文を形式的に定義するEBNF（Extended Backus-Naur Form）の間に、わずかな不整合または曖昧さが存在していました。特に、複合リテラル内の各要素がキーを持つ場合の表現について、EBNFがプロセの意図を完全に反映していない可能性がありました。

このコミットの目的は、この不整合を解消し、仕様書がGo言語の実際の動作をより正確かつ明確に記述するようにすることです。これにより、言語のパーサーを実装する開発者や、言語の挙動を深く理解しようとするユーザーにとって、仕様書がより理解しやすくなります。コミットメッセージにある `Fixes #12578` は、この変更が特定の課題（issue）を解決するために行われたことを示唆しています。

## 前提知識の解説

### Go言語の複合リテラル (Composite Literals)

Go言語における複合リテラルは、構造体（struct）、配列（array）、スライス（slice）、マップ（map）といった複合データ型の値を直接初期化するための構文です。これらは波括弧 `{}` を使用して記述され、型名の後に続く要素のリストで構成されます。

**例:**
*   **構造体リテラル**: `Point{X: 1, Y: 2}` (フィールド名と値のペア) または `Point{1, 2}` (フィールド順に値のみ)
*   **配列リテラル**: `[3]int{1, 2, 3}`
*   **スライスリテラル**: `[]string{"apple", "banana"}`
*   **マップリテラル**: `map[string]int{"one": 1, "two": 2}` (キーと値のペア)

複合リテラルの要素は、キーを持つ場合と持たない場合があります。構造体やマップではキーが一般的ですが、配列やスライスでは通常キーは省略され、インデックスが暗黙的なキーとして扱われます。

### EBNF (Extended Backus-Naur Form)

EBNFは、プログラミング言語の構文を形式的に記述するためのメタ言語です。Go言語の公式仕様書では、言語の構文規則をEBNFで定義しています。EBNFは、言語の構造を明確かつ簡潔に表現するために、以下のような記号を使用します。

*   `=` : 定義
*   `|` : または (選択)
*   `[ ]` : オプション (0回または1回)
*   `{ }` : 繰り返し (0回以上)
*   `( )` : グループ化
*   `" "` : リテラル文字列
*   `.` : 規則の終わり

例えば、`A = B { C } [ D ] .` は、「AはBの後にCが0回以上続き、その後にDがオプションで続く」という意味になります。

### Go言語仕様 (Go Language Specification)

Go言語仕様は、Go言語の設計と動作を定義する公式文書です。言語の構文、セマンティクス、メモリモデル、組み込み型、パッケージなど、Go言語のあらゆる側面が詳細に記述されています。この文書は、Goコンパイラやツールの実装者、およびGo言語の深い理解を求める開発者にとっての最終的な権威となります。

## 技術的詳細

このコミットは、Go言語仕様書の「Composite literals」セクションにおける記述とEBNF定義の整合性を向上させることを目的としています。

### プロセ記述の変更

変更前は、複合リテラルの要素について「An element may be a single expression or a key-value pair.（要素は単一の式またはキーと値のペアであり得る）」と記述されていました。
変更後は、「Each element may optionally be preceded by a corresponding key.（各要素にはオプションで対応するキーを先行させることができる）」となりました。

この変更は、キーが要素自体の一部であるというよりは、要素に付随するものであるという概念をより正確に表現しています。これにより、キーと値のペアが「要素」として扱われるのではなく、「キー付きの要素」というより明確な構造が示唆されます。

### EBNF構文の変更

EBNFの変更は、この新しいプロセ記述と完全に一致するように行われました。

**変更前のEBNF (関連部分):**
```ebnf
ElementList   = Element { "," Element } .
Element       = [ Key ":" ] Value .
Key           = FieldName | Expression | LiteralValue .
FieldName     = identifier .
Value         = Expression | LiteralValue .
```
この定義では、`Element` が `[ Key ":" ] Value` と定義されており、`Value` が `Expression | LiteralValue` でした。これは、`Element` がキーを持つことも持たないこともできることを示していましたが、`Value` と `Element` の関係がやや冗長でした。

**変更後のEBNF (関連部分):**
```ebnf
ElementList   = KeyedElement { "," KeyedElement } .
KeyedElement  = [ Key ":" ] Element .
Key           = FieldName | Expression | LiteralValue .
FieldName     = identifier .
Element       = Expression | LiteralValue .
```
主な変更点は以下の通りです。

1.  **`ElementList` の変更**: `ElementList` が `Element { "," Element }` から `KeyedElement { "," KeyedElement }` に変更されました。これは、複合リテラルのリスト内の各項目が `KeyedElement` であることを明確に示します。
2.  **`KeyedElement` の導入**: `KeyedElement = [ Key ":" ] Element .` という新しいプロダクションが導入されました。これにより、「キーがオプションであり、その後に `Element` が続く」という構造が明示的に定義されます。
3.  **`Element` の簡素化**: `Element` の定義が `[ Key ":" ] Value .` から `Expression | LiteralValue .` に簡素化されました。これにより、`Element` 自体は純粋な値（式またはリテラル値）を表し、キーの有無は `KeyedElement` プロダクションで処理されることになります。
4.  **`Value` プロダクションの削除**: 以前の `Value = Expression | LiteralValue .` は削除され、その役割は新しい `Element` プロダクションが引き継ぎました。

これらの変更により、EBNFは複合リテラルの構造をより階層的かつ明確に表現するようになりました。`Element` は純粋な値の構成要素であり、`KeyedElement` はその `Element` にオプションのキーが付随する可能性を表現します。この分離により、構文の解釈が一貫し、曖昧さが排除されます。

また、仕様書の最後の段落にある「The types of the expressions must be assignable...」という記述も、「The types of the elements and keys must be assignable...」に変更され、新しいEBNFの用語（`elements` と `keys`）に合わせられています。

## コアとなるコードの解説

このコミットにおける主要な変更は、Go言語仕様書 `doc/go_spec.html` 内の複合リテラルに関する記述とEBNF定義の修正です。

1.  **仕様書のバージョン日付の更新**:
    `Subtitle` の日付が "Version of August 5, 2015" から "Version of September 11, 2015" に更新されています。これは、仕様書がこのコミットによって更新されたことを示します。

2.  **プロセ記述の変更**:
    複合リテラルの説明文が変更されました。
    *   **変更前**: "An element may be a single expression or a key-value pair."
    *   **変更後**: "Each element may optionally be preceded by a corresponding key."
    この変更により、「要素」がキーと値のペアそのものであるという曖昧な表現から、「要素」にはオプションでキーが先行するという、より正確な構造が示されるようになりました。これは、キーが要素に付随する修飾子のようなものであるという理解を促進します。

3.  **EBNF構文の変更**:
    複合リテラルのEBNF定義が大幅に修正され、プロセ記述との整合性が図られました。
    *   **`ElementList` の定義変更**:
        *   変更前: `ElementList = Element { "," Element } .`
        *   変更後: `ElementList = KeyedElement { "," KeyedElement } .`
        これにより、複合リテラル内の要素のリストが、`Element` ではなく `KeyedElement` の繰り返しで構成されることが明確になりました。
    *   **`KeyedElement` プロダクションの導入**:
        *   新しく `KeyedElement = [ Key ":" ] Element .` が追加されました。
        この新しい規則は、リスト内の各項目が、オプションの `Key` とコロン `:` の後に `Element` が続く形式であることを明示しています。これにより、キーの存在がオプションであることが構文レベルで明確に表現されます。
    *   **`Element` プロダクションの簡素化**:
        *   変更前: `Element = [ Key ":" ] Value .`
        *   変更後: `Element = Expression | LiteralValue .`
        以前の `Element` はキーを持つ可能性を含んでいましたが、新しい定義では `Element` は純粋に値（`Expression` または `LiteralValue`）のみを表すようになりました。キーの扱いは `KeyedElement` に移譲されています。
    *   **`Value` プロダクションの削除**:
        *   変更前: `Value = Expression | LiteralValue .`
        この `Value` プロダクションは削除され、その役割は新しい `Element` プロダクションが引き継ぎました。これにより、`Element` と `Value` の間の冗長性が解消され、EBNFがより簡潔になりました。

4.  **文言の調整**:
    仕様書の最後の段落にある「The types of the expressions must be assignable...」という文言が、「The types of the elements and keys must be assignable...」に変更されました。これは、EBNFの変更によって導入された新しい用語（`elements` と `keys`）に合わせて、型のアサイン可能性に関する記述をより正確にしたものです。

これらの変更は、Go言語の複合リテラルの構文をより厳密かつ明確に定義し、言語仕様の正確性と一貫性を高めることに貢献しています。

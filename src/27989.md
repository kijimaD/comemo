# [インデックス 27989] ファイルの概要

このコミットでは、Goランタイムのトレーサーにおけるイベントのシーケンス番号の管理方法が、グローバルなシーケンサーからゴルーチンごとのシーケンサーへと変更されました。これにより、並列実行環境でのトレーシングの性能オーバーヘッドが大幅に削減され、トレースデータのサイズも最適化されています。

変更されたファイルは以下の通りです。

*   `src/internal/trace/order.go`: 新規追加ファイル。イベントの順序付けロジックを実装。
*   `src/internal/trace/parser.go`: トレースパーサーのロジックが更新され、新しいイベントタイプと順序付けアルゴリズムに対応。
*   `src/internal/trace/parser_test.go`: パーサーのテストが更新。
*   `src/runtime/proc.go`: システムコール終了時のトレースイベント発行ロジックが変更。
*   `src/runtime/runtime2.go`: `g` (ゴルーチン) 構造体にトレーシング関連のフィールドが追加。
*   `src/runtime/trace.go`: トレーシングイベントの発行ロジックが変更され、per-goroutineシーケンス番号を使用。

## 変更の背景

Goランタイムのトレーサーは、プログラムの実行状況を詳細に記録し、パフォーマンス分析やデバッグに役立つ情報を提供します。しかし、このコミット以前のトレーサーは、イベントの順序付けのためにグローバルなシーケンサーを使用していました。このグローバルシーケンサーは、特に多数のCPUコアを持つ並列マシンにおいて、深刻な性能ボトルネックとなっていました。コミットメッセージによると、トレーシングを有効にした場合、最大で10倍もの性能劣化を引き起こすことがありました。

この性能劣化は、複数のプロセッサ (P) が同時にイベントを記録しようとすると、グローバルなシーケンサーへのアクセスが競合し、ロックやアトミック操作による同期オーバーヘッドが大きくなるためです。この問題を解決し、トレーシングのオーバーヘッドを許容可能なレベルに抑えることが、この変更の主要な動機です。

## 前提知識の解説

### Goトレーサーの役割と目的

Goトレーサーは、Goプログラムの実行中に発生する様々なイベント（ゴルーチンの生成・開始・終了、GCの開始・終了、システムコール、スケジューリングなど）を記録するツールです。記録されたトレースデータは、`go tool trace` コマンドによって可視化され、プログラムのボトルネック特定、並行処理の挙動分析、GCの最適化などに利用されます。

### P (Processor) と G (Goroutine) の概念

Goランタイムは、M (Machine/OSスレッド)、P (Processor/論理プロセッサ)、G (Goroutine) という3つの主要な抽象化を用いて並行処理を管理します。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。OSスレッドよりもはるかに軽量で、数百万個のゴルーチンを同時に実行できます。
*   **M (Machine)**: OSスレッドに対応します。GoランタイムはM上でGを実行します。
*   **P (Processor)**: MとGを仲介する論理プロセッサです。PはMにアタッチされ、MがGを実行するためのコンテキストを提供します。Pの数は通常、CPUコアの数に等しく、`GOMAXPROCS` 環境変数で制御されます。Pは、実行可能なGのキューを保持し、MがそのキューからGを取り出して実行します。

トレーシングにおいては、各Pが独立してイベントを記録することが多いため、Pごとのイベントバッチという概念が重要になります。

### イベントの順序付けの重要性

トレースデータは、プログラムの正確な実行フローを反映している必要があります。特に、異なるPで並行して発生するイベントや、ゴルーチンの状態遷移（実行可能、実行中、待機中など）を正確に追跡するためには、イベント間の因果関係に基づいた厳密な順序付けが不可欠です。例えば、あるゴルーチンがアンブロックされた後に実行を開始するというイベントは、その順序で記録され、解析される必要があります。

### シーケンス番号の役割

シーケンス番号は、イベントの発生順序を識別するために使用される一意の識別子です。グローバルシーケンサーの場合、すべてのイベントが単一のシーケンス番号空間を共有するため、イベントの記録時にこのグローバルシーケンサーを更新する必要があり、これが並列環境での競合の原因となります。

### `cputicks` と `nanotime`

*   `cputicks()`: CPUのサイクルカウンタを読み取って、CPUクロック単位での時間を提供します。これは非常に高精度ですが、異なるCPUコア間で同期が取れていない場合があり、単調増加が保証されないことがあります。
*   `nanotime()`: システムの単調増加するナノ秒単位の時間を提供します。これは壁時計時間ではなく、システム起動時からの経過時間であり、`cputicks`よりも精度は低いですが、順序付けには適しています。

トレーシングでは、イベントのタイムスタンプとしてこれらの値が利用されますが、`cputicks`の非同期性がイベントの順序付けを複雑にする要因となります。

## 技術的詳細

### グローバルシーケンサーの問題点

従来のGoトレーサーでは、すべてのイベントにグローバルなシーケンス番号を割り当てていました。これは、複数のPが同時にイベントを記録しようとすると、グローバルなシーケンス番号を更新するためのアトミック操作やロックが必要となり、これが並列処理のボトルネックとなっていました。特に`GOMAXPROCS`が大きな値に設定された環境では、この同期オーバーヘッドが顕著になり、トレーシングがプログラムの実行速度を大幅に低下させていました。

### per-goroutineシーケンサーへの移行

このコミットの核心は、グローバルシーケンサーを廃止し、ゴルーチンごとにシーケンス番号を管理する方式に切り替えた点です。これにより、イベント記録時の同期オーバーヘッドが大幅に削減されます。

ただし、すべてのイベントにゴルーチンごとのシーケンス番号を割り当てる必要はありません。コミットメッセージによると、以下の3種類のイベントにのみシーケンス番号を割り当てることで、すべてのイベントの一貫した部分的な順序付けを復元するのに十分であるとされています。

1.  **GoStart (ゴルーチン開始)**
2.  **GoUnblock (ゴルーチンアンブロック)**
3.  **GoSysExit (システムコール終了)**

さらに、これらのイベントでさえ、常にシーケンス番号が必要なわけではありません。例えば、ゴルーチンがアンブロックされたのと同じPで実行を開始する場合、`GoStart`イベントにシーケンス番号は不要です。

このアプローチの利点は、イベント記録時のオーバーヘッドを最小限に抑えつつ、イベント間の因果関係を追跡できる点にあります。イベントの順序付けの複雑さは、トレースパーサー側に移譲されます。

### イベントの順序付けアルゴリズム（`order1007` 関数）

新しく追加された `src/internal/trace/order.go` ファイルには、`order1007` という関数が導入されています。この関数は、Pごとのイベントバッチを、一貫性のある単一のイベントストリームにマージするための主要なロジックを実装しています。

アルゴリズムの概要は以下の通りです。

1.  **Pごとのバッチ**: 各Pは独立してイベントを記録し、イベントのバッチを生成します。これらのバッチ内では、イベントは正しい順序で並んでいます。
2.  **フロンティア**: 各バッチの先頭にある、まだマージされていないイベントを「フロンティア」と呼びます。
3.  **準備完了イベントの選択**: フロンティアの中から、「準備完了」状態のイベント（つまり、そのイベントが依存するすべてのイベントが既にマージされているイベント）のサブセットを選択します。この依存関係は、ゴルーチンの状態遷移（`gState`）とシーケンス番号によって追跡されます。
4.  **最小タイムスタンプのイベントをマージ**: 準備完了イベントのサブセットの中から、最も小さいタイムスタンプを持つイベントを選択し、マージします。
5.  **繰り返し**: 上記のプロセスを、すべてのイベントがマージされるまで繰り返します。

このアプローチにより、タイムスタンプが不正確な場合（一部の環境で観測される問題）でも、一貫性のあるイベントストリームを生成できます。

### `EvGoStartLocal`, `EvGoUnblockLocal`, `EvGoSysExitLocal` の導入

このコミットでは、トレーシングイベントに以下の新しいイベントタイプが追加されました。

*   `EvGoStartLocal` (イベントタイプ 38): ゴルーチンが、直前のイベントと同じPで実行を開始した場合。
*   `EvGoUnblockLocal` (イベントタイプ 39): ゴルーチンが、直前のイベントと同じPでアンブロックされた場合。
*   `EvGoSysExitLocal` (イベントタイプ 40): システムコールが、直前のイベントと同じPで終了した場合。

これらの「Local」イベントは、シーケンス番号を必要としないケースを最適化するために導入されました。これにより、トレースデータのサイズ削減と、イベント記録時のオーバーヘッドのさらなる低減が図られています。パーサーはこれらのイベントを通常の `EvGoStart`、`EvGoUnblock`、`EvGoSysExit` に変換して処理します。

### トレースパーサーの変更点 (バージョン1007以降の処理)

`src/internal/trace/parser.go` では、トレースフォーマットのバージョンが1007以降の場合に、新しい順序付けアルゴリズム (`order1007`) を使用するように変更されました。また、イベントの引数の解釈方法も、シーケンス番号がイベントデータに含まれるかどうかに応じて調整されています。

### `gState` と `stateTransition` の役割

`src/internal/trace/order.go` に定義されている `gState` 構造体は、ゴルーチンの現在のシーケンス番号 (`seq`) と状態 (`status`) を保持します。`stateTransition` 関数は、特定のイベントが発生したときに、ゴルーチンの状態がどのように変化するかを定義します。これにより、イベント間の依存関係を追跡し、`order1007` 関数がイベントを正しく順序付けるための情報を提供します。

### `sysexitticks` の扱い

システムコール終了 (`EvGoSysExit`) イベントのタイムスタンプは、システムコールが実際に終了した時刻 (`sysexitticks`) を使用するように変更されました。以前は、このイベントがP上で発行されるタイミングでタイムスタンプが記録されていましたが、これにより実際のシステムコール終了時刻とイベント記録時刻の間にずれが生じる可能性がありました。新しい方式では、より正確なタイムスタンプが提供されますが、トレース開始前に発生したシステムコール終了イベントのタイムスタンプは無視されるようになっています。

### トレースサイズの削減と性能改善効果

コミットメッセージに記載されているベンチマーク結果は、この変更の大きな効果を示しています。

*   **性能改善**: `GOMAXPROCS=48` の `http` ベンチマークにおいて、トレーシングなしと比較して、変更前は+453%のオーバーヘッドがあったものが、変更後は+26%にまで削減されました。これは、グローバルシーケンサーによるボトルネックがほぼ解消されたことを意味します。
*   **トレースサイズの削減**: 平均イベントサイズが4.63バイト/イベントから3.62バイト/イベントへと約22%削減されました。これは、シーケンス番号を必要なイベントにのみ割り当て、`Local` イベントを導入したことによるものです。

これらの改善により、Goトレーサーはより実用的なツールとなり、本番環境に近い条件でのパフォーマンス分析にも利用しやすくなりました。

### `src/runtime/trace.go`

トレーシングイベントの発行ロジックが大幅に変更され、グローバルシーケンサー (`traceseq`) が削除され、ゴルーチンごとの `traceseq` と `tracelastp` を利用するようになりました。また、`EvGoStartLocal`、`EvGoUnblockLocal`、`EvGoSysExitLocal` などの新しいイベントタイプが導入されています。

```go
// traceEvent function is modified to not use global traceseq.
func traceEvent(ev byte, skip int, args ...uint64) {
    // ...
    // Global traceseq removed.
    // ...
}

func traceGoStart() {
    _g_ := getg().m.curg
    _p_ := _g_.m.p
    _g_.traceseq++ // Increment per-goroutine sequence number
    if _g_.tracelastp == _p_ {
        traceEvent(traceEvGoStartLocal, -1, uint64(_g_.goid)) // Use local event if on same P
    } else {
        _g_.tracelastp = _p_
        traceEvent(traceEvGoStart, -1, uint64(_g_.goid), _g_.traceseq) // Use global event with seq
    }
}

func traceGoUnpark(gp *g, skip int) {
    _p_ := getg().m.p
    gp.traceseq++ // Increment per-goroutine sequence number
    if gp.tracelastp == _p_ {
        traceEvent(traceEvGoUnblockLocal, skip, uint64(gp.goid)) // Use local event if on same P
    } else {
        gp.tracelastp = _p_
        traceEvent(traceEvGoUnblock, skip, uint64(gp.goid), gp.traceseq) // Use global event with seq
    }
}

func traceGoSysExit(ts int64) {
    // ...
    _g_ := getg().m.curg
    _g_.traceseq++ // Increment per-goroutine sequence number
    _g_.tracelastp = _g_.m.p
    traceEvent(traceEvGoSysExit, -1, uint64(_g_.goid), _g_.traceseq, uint64(ts)/traceTickDiv)
}
```

## コアとなるコードの解説

### `src/internal/trace/order.go` の `order1007` 関数

この関数は、Goトレーサーの解析部分において最も重要な変更点の一つです。ランタイムから出力されるトレースデータは、Pごとにバッチ化されたイベントの集合として記録されます。`order1007` は、これらのPごとのバッチを、イベント間の因果関係を考慮して正しくインターリーブ（混ぜ合わせ）し、単一の時系列イベントストリームを再構築します。

特に注目すべきは、`transitionReady` 関数と `stateTransition` 関数が連携して、ゴルーチンの状態 (`gState`) とシーケンス番号に基づいてイベントの依存関係を解決している点です。これにより、タイムスタンプが不正確な場合でも、論理的な順序の一貫性を保つことができます。

### `g` 構造体 (`src/runtime/runtime2.go`) の変更

`g` 構造体に追加された `traceseq` と `tracelastp` フィールドは、per-goroutineシーケンサーの実現に不可欠です。

*   `traceseq`: 各ゴルーチンが持つ独自のシーケンス番号です。`EvGoStart`、`EvGoUnblock`、`EvGoSysExit` などの特定のイベントが発行される際にインクリメントされます。これにより、グローバルな競合なしに、ゴルーチン内のイベントの順序を追跡できます。
*   `tracelastp`: そのゴルーチンが最後にイベントを発行したPへのポインタです。この情報を使って、現在のPが `tracelastp` と同じかどうかを判断し、`EvGoStartLocal` のような最適化された「Local」イベントを発行するかどうかを決定します。

### `src/runtime/trace.go` におけるイベント発行ロジックの変更

`traceGoStart`、`traceGoUnpark`、`traceGoSysExit` などの関数は、イベントを発行する際に `_g_.traceseq` をインクリメントし、`_g_.tracelastp` を更新するようになりました。これにより、ランタイム側でゴルーチンごとのシーケンス番号が管理され、トレースデータに埋め込まれます。

また、`traceEvent` 関数自体も、グローバルシーケンス番号の代わりに、イベントの引数として渡されるシーケンス番号（必要な場合）とタイムスタンプを処理するように変更されています。`traceEvBatch` イベントのフォーマットも、シーケンス番号を含まないように簡素化されました。

## 元コミット内容

このコミットは、Goツールチェーンの`cmd/internal/obj`パッケージにおいて、スレッドローカルストレージ（TLS）を適切にサポートするためのプラットフォーム非依存な部分を実装しています。また、内部リンキングと外部リンキングにおける`.tbss`セクションの生成に関する複雑なロジックを簡素化しています。コミットメッセージには「"make TLS make sense" プロジェクトにはまだ多くのステップが残っている」とあり、これはTLSサポートの全体的な改善に向けた一連の変更の一部であることを示唆しています。関連するIssueは #11270 です。

## 変更の背景

Go言語は、その並行処理モデル（Goroutine）により、スレッドの概念を直接的にプログラマに意識させない設計になっています。しかし、Cgoを介してCライブラリを呼び出す場合など、OSのスレッドモデルやスレッドローカルストレージの機能が必要となる場面があります。特に、Cライブラリがスレッドローカル変数を使用している場合、Goのランタイムがそれを適切に扱えるようにツールチェーンレベルでのサポートが不可欠です。

以前のGoツールチェーンでは、TLSのサポートが不完全であったり、リンキングモード（内部リンキング vs 外部リンキング）やターゲットプラットフォームによって挙動が異なったりする「複雑さ」や「不整合」が存在していました。このコミットの背景には、これらの問題を解決し、より堅牢でプラットフォーム非依存なTLSサポートをGoツールチェーンに組み込むという目標があります。Issue #11270 は、このTLSサポートの改善に関する具体的な課題を追跡していたと考えられます。

具体的には、`.tbss`セクション（Thread-Local BSS）の生成と配置に関するロジックが複雑で、特に内部リンキングと外部リンキングの間で一貫性がなかったため、その簡素化と統一が求められていました。このコミットは、その「make TLS make sense」プロジェクトの初期段階として、基盤となるオブジェクトファイル生成とリンキングの段階でのTLS関連の処理を整理することを目的としています。

## 前提知識の解説

### スレッドローカルストレージ (TLS)

スレッドローカルストレージ（TLS）は、マルチスレッド環境において、各スレッドがそれぞれ独立した変数インスタンスを持つことを可能にするメカニズムです。通常、グローバル変数や静的変数はプロセス内のすべてのスレッドで共有されますが、TLS変数はスレッドごとに異なる値を保持できます。これは、例えばエラーコード、トランザクションID、またはスレッド固有のコンテキスト情報などを管理する際に非常に有用です。

OSレベルでは、TLSは通常、スレッド情報ブロック（TIB: Thread Information Block）やスレッドポインタレジスタ（例: x86-64の`%fs`または`%gs`セグメントレジスタ）を介してアクセスされます。コンパイラやリンカは、TLS変数のアドレスを計算するために、これらのスレッドポインタからのオフセットを使用します。

### `.tbss` セクション

実行可能ファイルや共有ライブラリのセクションには、様々な種類のデータが格納されます。
*   `.text`: 実行可能なコード
*   `.data`: 初期化されたグローバル/静的変数
*   `.bss`: 初期化されていないグローバル/静的変数（実行時にゼロ初期化される）

これらと同様に、TLS変数も特定のセクションに配置されます。
*   `.tdata`: 初期化されたスレッドローカル変数
*   `.tbss`: 初期化されていないスレッドローカル変数（実行時にゼロ初期化される）

`.tbss`セクションは、スレッドが初めてアクセスする際にOSによって割り当てられ、ゼロ初期化されることが一般的です。このセクションは、ファイル上ではサイズがゼロであることが多く、実行時にメモリが割り当てられます。

### リンキングモード (内部リンキング vs 外部リンキング)

Goツールチェーンには、主に2つのリンキングモードがあります。

1.  **内部リンキング (Internal Linking)**: Goコンパイラとリンカが、GoのコードとGoランタイムのコードをすべて静的にリンクして単一の実行可能ファイルを生成するモードです。Cgoを使用しない場合や、Cgoを使用しても非常に限定的な場合に用いられます。このモードでは、Goツールチェーンがリンキングの全プロセスを制御します。
2.  **外部リンキング (External Linking)**: Cgoを使用し、特にCライブラリが複雑な場合や、システムリンカ（例: `gcc`や`clang`）の機能が必要な場合に用いられます。Goツールチェーンはオブジェクトファイルを生成し、最終的なリンクはシステムリンカに委ねられます。このモードでは、システムリンカがTLSセクションの配置や処理を担当することが多くなります。

これらのリンキングモードの違いが、TLSセクションの取り扱いに複雑さをもたらしていました。

### ELF (Executable and Linkable Format)

ELFは、Unix系システムで広く使われている実行可能ファイル、オブジェクトファイル、共有ライブラリの標準フォーマットです。ELFファイルは、ヘッダ、プログラムヘッダテーブル、セクションヘッダテーブル、および様々なセクションで構成されます。

*   **プログラムヘッダ (Program Header)**: 実行時にOSのローダーがプログラムをメモリにロードする方法を記述します。`PT_TLS` (Program Header Type TLS) は、TLSセクションに関する情報（メモリサイズ、アライメントなど）を記述するために使用されます。
*   **セクションヘッダ (Section Header)**: リンカがオブジェクトファイルを結合する際に使用する、ファイル内のセクションに関するメタデータ（名前、タイプ、サイズ、オフセットなど）を記述します。`SHT_NOBITS`は、ファイル内にはデータを持たないが、実行時にメモリを割り当てる必要があるセクション（例: `.bss`, `.tbss`）を示します。`SHF_TLS`は、そのセクションがTLSデータを含むことを示します。

## 技術的詳細

このコミットは、Goツールチェーンの複数のコンポーネントにわたってTLSサポートを強化しています。

1.  **`src/cmd/internal/obj/textflag.go` および `src/runtime/textflag.h` における `TLSBSS` フラグの導入**:
    *   `TLSBSS = 256` という新しいフラグが導入されました。このフラグは、Goのコンパイラがオブジェクトファイルを生成する際に、特定のシンボルがスレッドローカルなBSSセクションに属することを示すために使用されます。
    *   コメントには「スレッドローカルストレージのワードを割り当て、スレッドローカルベースからのオフセットをこの変数に格納する」とあり、これはTLS変数のアクセス方法（ベースポインタからのオフセット）を直接的に示唆しています。
    *   `src/runtime/textflag.h` にも同様の定義が追加され、アセンブリコードとGoコンパイラの内部表現の間で一貫性が保たれています。

2.  **`src/cmd/internal/obj/objfile.go` における `STLSBSS` シンボルタイプの追加**:
    *   `TLSBSS` フラグが設定されたシンボルに対して、新しいシンボルタイプ `STLSBSS` が割り当てられるようになりました。これは、Goのオブジェクトファイル内で、そのシンボルがスレッドローカルなBSSセクションに属する変数であることを明示的に識別するためのものです。

3.  **`src/cmd/internal/obj/data.go` における BSS 変数へのデータ供給禁止チェック**:
    *   `SBSS` (通常のBSS) または `STLSBSS` (スレッドローカルBSS) タイプのシンボルに対して、データが供給されないようにするチェックが追加されました。BSSセクションは未初期化データを格納するためのものであり、実行時にゼロ初期化されることが期待されるため、コンパイル時にデータが割り当てられるのは誤りです。このチェックは、ツールチェーンの堅牢性を高めます。

4.  **`src/cmd/link/internal/ld/data.go` における `.tbss` セクション処理の改善**:
    *   `.tbss` セクションの生成ロジックが大幅に修正されました。以前は外部リンキングの場合にのみ特定の条件で生成されていましたが、この変更により、`STLSBSS` タイプのシンボルが存在する場合に、より統一された方法で`.tbss`セクションが処理されるようになりました。
    *   特に、`Iself` (ELFターゲットであるか)、`Linkmode == LinkExternal` (外部リンキングであるか)、または `Debug['d'] == 0` (デバッグモードでない内部リンキング) の場合に`.tbss`セクションが追加されるようになりました。これにより、内部リンキングでもTLSが適切に扱われるケースが拡張されました。
    *   `s.Value` の計算方法が変更され、`sect.Vaddr` を引く代わりに直接 `datsize` が使用されるようになりました。これは、TLS変数のオフセット計算のセマンティクスをより正確に反映している可能性があります。
    *   `address()` 関数において、ELFターゲットの場合に`.tbss`セクションが仮想アドレス計算から除外されるようになりました。これは、`.tbss`セクションがファイル上に実体を持たず、実行時にOSによってメモリが割り当てられるという特性を考慮したものです。

5.  **`src/cmd/link/internal/ld/elf.go` における ELF 構造体生成の調整**:
    *   `elfshbits` 関数において、`.tbss`セクションの `sh.off` (ファイルオフセット) の計算が変更されました。Android以外のプラットフォームでは、`.tbss`セクションはファイル上に実体を持たないため、オフセットが設定されないようになりました。
    *   `Asmbelf` 関数において、`PT_TLS` プログラムヘッダの生成ロジックが更新されました。以前は `Ctxt.Tlsoffset` を使用していましたが、変更後は実際に存在する`.tbss`セクションの `sect.Length` を調べて `tlssize` を計算し、それを `ph.memsz` (メモリ上のサイズ) に設定するようになりました。これにより、TLSセクションのメモリ要件がより正確にELFファイルに反映されます。
    *   内部リンキングにおける`.tbss`セクションの明示的な生成ロジックが削除されました。これは、`data.go` での処理がより包括的になったため、重複するロジックが不要になったことを示唆しています。

これらの変更は、GoツールチェーンがTLS変数をより正確に認識し、オブジェクトファイルおよび実行可能ファイルのELF構造内で適切に表現できるようにするためのものです。特に、リンキングモードやプラットフォームに依存しない一貫したTLSサポートの実現に向けた重要な一歩と言えます。

## コアとなるコードの解説

このコミットの核となる変更は、Goツールチェーンがスレッドローカルストレージ（TLS）をどのように認識し、処理するかを根本的に改善することにあります。

1.  **`TLSBSS` フラグと `STLSBSS` シンボルタイプ**:
    *   `src/cmd/internal/obj/textflag.go` で定義された `TLSBSS` フラグは、コンパイラが特定の変数宣言をTLS変数としてマークするためのメカニズムを提供します。このフラグが設定されると、`src/cmd/internal/obj/objfile.go` のロジックによって、そのシンボルは `STLSBSS` という新しいタイプとして分類されます。
    *   `STLSBSS` は "Symbol Thread-Local BSS" の略であり、このシンボルが初期化されていないスレッドローカルデータセクション（`.tbss`）に属することを示します。これにより、ツールチェーンの各段階でTLS変数を一貫して識別できるようになります。

2.  **BSS変数へのデータ供給禁止**:
    *   `src/cmd/internal/obj/data.go` に追加された `ctxt.Diag("cannot supply data for BSS var")` のチェックは、`SBSS` または `STLSBSS` タイプのシンボルに対して、誤って初期データが割り当てられるのを防ぎます。BSSセクションの変数は、プログラムの開始時にゼロで初期化されることが期待されており、コンパイル時にデータが提供されるべきではありません。このチェックは、TLS変数の正しいセマンティクスを強制し、潜在的なバグを防ぎます。

3.  **`.tbss` セクションのリンキングロジックの統一**:
    *   `src/cmd/link/internal/ld/data.go` の変更は最も重要です。以前は、外部リンキングの場合にのみ特定の条件で`.tbss`セクションが生成されていましたが、新しいロジックでは `STLSBSS` タイプのシンボルが存在すれば、より一般的な条件で`.tbss`セクションが考慮されるようになりました。
    *   `if Iself && (Linkmode == LinkExternal || Debug['d'] == 0) && HEADTYPE != obj.Hopenbsd` という条件は、ELFターゲット（`Iself`）、かつ外部リンキングであるか、またはデバッグモードでない内部リンキング（`Debug['d'] == 0`）の場合に`.tbss`セクションを生成することを示しています。これにより、内部リンキングでもTLSが適切に扱われるケースが拡張され、リンキングモード間の不整合が解消されます。
    *   `s.Value = datsize` への変更は、TLS変数のオフセットが、スレッドローカルストレージ領域の先頭からの相対オフセットとして直接扱われることを意味します。これは、TLSアクセス命令が通常、スレッドポインタからのオフセットを使用するOSのTLSメカニズムとより整合性が取れています。
    *   `address()` 関数で`.tbss`セクションが仮想アドレス計算から除外されるようになったのは、`.tbss`がファイル上に実体を持たず、実行時にOSによって動的にメモリが割り当てられるという特性を反映しています。これにより、リンカはファイル上のセクション配置とメモリ上のセクション配置を正しく区別できます。

4.  **ELF プログラムヘッダの正確な生成**:
    *   `src/cmd/link/internal/ld/elf.go` の変更は、ELF実行可能ファイルがTLS情報を正確に表現するために不可欠です。
    *   `elfshbits` での `.tbss` の `sh.off` の扱い変更は、ファイル上に実体を持たないセクションのオフセットを適切に処理するためのものです。
    *   `Asmbelf` で `PT_TLS` プログラムヘッダの `ph.memsz` が、実際に存在する`.tbss`セクションの長さに基づいて計算されるようになったことは、OSローダーに対してTLS領域の正確なメモリ要件を伝える上で非常に重要です。これにより、OSは各スレッドに対して適切なサイズのTLS領域を割り当てることができます。以前の `Ctxt.Tlsoffset` を使用する方法よりも、より動的で正確なアプローチと言えます。
    *   内部リンキングにおける`.tbss`セクションの明示的な生成ロジックの削除は、`data.go` での統一された処理により、リンカのコードベースが簡素化されたことを示しています。

これらの変更は、GoツールチェーンがTLS変数をより正確にモデル化し、リンキングプロセスを通じてそのセマンティクスを維持できるようにすることで、GoプログラムがCgoを介してTLSを使用する際の堅牢性と互換性を向上させます。これは、Goランタイムがより複雑なシステムレベルの機能と統合するための重要なステップです。

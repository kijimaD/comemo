# [インデックス 25243] ファイルの概要

このコミットは、Go言語の`net/http`パッケージにおけるHTTP/1.0レスポンスの`Transfer-Encoding`ヘッダの処理に関するバグ修正です。具体的には、HTTP/1.0プロトコルでは`Transfer-Encoding`が定義されていないため、HTTP/1.0レスポンスにこのヘッダが含まれていても無視するように変更されました。これにより、HTTP/1.0の仕様に厳密に準拠し、不正な`Transfer-Encoding`ヘッダを持つHTTP/1.0レスポンスを正しく処理できるようになります。

## 変更の背景

この変更は、Goの`net/http`パッケージがHTTP/1.0レスポンスに含まれる`Transfer-Encoding`ヘッダを誤って解釈する問題（Issue #12785）を修正するために導入されました。

HTTP/1.0プロトコル仕様（RFC 1945）では、`Transfer-Encoding`ヘッダは定義されていません。このヘッダはHTTP/1.1（RFC 2616、後にRFC 7230で改訂）で導入され、特にメッセージボディをチャンク形式で転送する際に使用されます。しかし、一部のサーバー実装では、HTTP/1.0レスポンスにもかかわらず誤って`Transfer-Encoding`ヘッダを含めてしまうケースがありました。

Goの`net/http`クライアントがこのような不正なHTTP/1.0レスポンスを受け取った場合、`Transfer-Encoding`ヘッダを処理しようとしてしまい、結果としてボディの読み取りが正しく行われない可能性がありました。このコミットは、HTTP/1.0の仕様に則り、HTTP/1.0レスポンスでは`Transfer-Encoding`ヘッダを完全に無視することで、この問題を解決します。これにより、GoのHTTPクライアントは、仕様に準拠しないサーバーからのレスポンスに対しても堅牢になります。

## 前提知識の解説

### HTTP/1.0とHTTP/1.1におけるメッセージボディの終端

HTTPプロトコルでは、クライアントとサーバー間でメッセージボディの開始と終了をどのように識別するかが重要です。

*   **HTTP/1.0**: 主に`Content-Length`ヘッダを使用してメッセージボディの長さをバイト単位で示します。このヘッダが存在しない場合、サーバーは接続を閉じることでボディの終端を示します。
*   **HTTP/1.1**: `Content-Length`に加えて、`Transfer-Encoding`ヘッダを導入しました。特に`Transfer-Encoding: chunked`は、メッセージボディを可変長のチャンク（塊）に分割して転送するメカニズムを提供します。これにより、サーバーはメッセージボディの全長を事前に知らなくてもレスポンスを開始できるようになります。

### `Transfer-Encoding`ヘッダ

`Transfer-Encoding`ヘッダは、メッセージボディがアプリケーションに渡される前に適用されたエンコーディング形式を示します。最も一般的なのは`chunked`エンコーディングで、これはメッセージボディを複数のチャンクに分割し、各チャンクの前にそのサイズを示すことで、ボディの終端を明示的に示すことなくストリーミングを可能にします。

### `Content-Length`ヘッダ

`Content-Length`ヘッダは、メッセージボディのオクテット（バイト）単位のサイズを示します。このヘッダは、メッセージボディ全体が一度に送信される場合に特に有用です。`Transfer-Encoding: chunked`が指定されている場合、`Content-Length`ヘッダは通常無視されるか、存在すべきではありません（RFC 7230 Section 3.3.2）。

### Goの`net/http`パッケージ

Go言語の標準ライブラリである`net/http`パッケージは、HTTPクライアントとサーバーの実装を提供します。このパッケージは、HTTPプロトコルの詳細な処理（ヘッダのパース、ボディの読み取り、接続管理など）を抽象化し、開発者が簡単にHTTP通信を行えるようにします。このコミットは、`net/http`パッケージがHTTPメッセージボディをどのように解釈し、読み取るかという内部ロジックに影響を与えます。

## 技術的詳細

このコミットの技術的な核心は、`net/http`パッケージ内の`transferReader`構造体と、メッセージボディの転送エンコーディングを処理する`fixTransferEncoding`関数の変更にあります。

1.  **`transferReader`構造体**: HTTPレスポンスのボディを読み取るための内部的な構造体です。この構造体には、HTTPプロトコルのバージョン（`ProtoMajor`, `ProtoMinor`）やヘッダ情報などが含まれています。
2.  **`protoAtLeast`メソッドの追加**: `transferReader`に`protoAtLeast(m, n int) bool`という新しいヘルパーメソッドが追加されました。これは、現在のHTTPプロトコルバージョンが指定されたメジャーバージョン`m`とマイナーバージョン`n`以上であるかどうかを効率的にチェックするために使用されます。
    ```go
    func (t *transferReader) protoAtLeast(m, n int) bool {
        return t.ProtoMajor > m || (t.ProtoMajor == m && t.ProtoMinor >= n)
    }
    ```
3.  **`fixTransferEncoding`関数の変更**:
    *   以前は独立した関数でしたが、`transferReader`のメソッド`(*transferReader).fixTransferEncoding()`に変更されました。これにより、`transferReader`の内部状態（プロトコルバージョンやヘッダ）に直接アクセスできるようになります。
    *   最も重要な変更は、HTTPプロトコルバージョンが1.1未満（つまりHTTP/1.0）の場合に`Transfer-Encoding`ヘッダを無視するロジックが追加されたことです。
        ```go
        // Issue 12785; ignore Transfer-Encoding on HTTP/1.0 requests.
        if !t.protoAtLeast(1, 1) {
            return nil
        }
        ```
        このコードは、`protoAtLeast(1, 1)`が`false`（つまりHTTP/1.0）の場合、`Transfer-Encoding`ヘッダの処理をスキップし、`nil`を返します。これにより、HTTP/1.0レスポンスでは`Transfer-Encoding`が適用されないことになります。
    *   `Transfer-Encoding`ヘッダが処理される前に、レスポンスヘッダから`Transfer-Encoding`ヘッダが削除されるようになりました。これは、ヘッダが誤って下流に伝播するのを防ぐためです。
    *   `Transfer-Encoding`が`chunked`である場合、RFC 7230 Section 3.3.2の規定に従い、`Content-Length`ヘッダが削除されるロジックも含まれています。これは、`Transfer-Encoding: chunked`と`Content-Length`が同時に存在する場合の矛盾を解消するためです。

これらの変更により、Goの`net/http`はHTTP/1.0レスポンスに対して`Transfer-Encoding`ヘッダを正しく無視し、メッセージボディの読み取りを`Content-Length`または接続の終端によって行うようになります。

*   **HTTP/1.0レスポンスと不正な`Transfer-Encoding`ヘッダ（`Content-Length`なし）**:

これらのテストケースは、変更がHTTP/1.0の`Transfer-Encoding`を正しく無視し、ボディの読み取りが期待通りに行われることを保証します。

## コアとなるコードの解説

### `src/net/http/response_test.go` の変更点

追加されたテストケースは、このコミットの意図を明確に示しています。HTTP/1.0プロトコルを使用し、`Transfer-Encoding: bogus`という不正なヘッダを持つレスポンスをシミュレートしています。

*   最初のテストケースでは`Content-Length`ヘッダがないため、Goクライアントは`Transfer-Encoding`を無視し、接続が閉じられるまでボディを読み取るべきです。
*   2番目のテストケースでは`Content-Length: 10`が存在するため、Goクライアントは`Transfer-Encoding`を無視し、`Content-Length`に基づいて正確に10バイトのボディを読み取るべきです。

これらのテストは、`net/http`パッケージがHTTP/1.0の仕様に厳密に従い、不正な`Transfer-Encoding`ヘッダを無視して、ボディの終端を正しく判断できることを検証します。

### `src/net/http/transfer.go` の変更点

1.  **`protoAtLeast`メソッド**: この小さなヘルパーメソッドは、コードの可読性を向上させ、HTTPプロトコルバージョンの比較を簡潔に行うために導入されました。`t.ProtoMajor > m || (t.ProtoMajor == m && t.ProtoMinor >= n)`というロジックは、現在のプロトコルが指定されたバージョン以上であるかを正確に判断します。
2.  **`fixTransferEncoding`メソッド**:
    *   関数からメソッドへの変更は、`transferReader`のインスタンスが持つプロトコルバージョンやヘッダ情報に直接アクセスできるようにするためのリファクタリングです。これにより、関数の引数を減らし、コードをよりオブジェクト指向的にすることができます。
    *   最も重要なのは、`if !t.protoAtLeast(1, 1)`という条件分岐です。これは、HTTP/1.0（メジャーバージョン1、マイナーバージョン0）の場合に`Transfer-Encoding`ヘッダの処理を完全にスキップすることを意味します。これにより、HTTP/1.0レスポンスでは`Transfer-Encoding`が無視され、ボディの読み取りは他のメカニズム（`Content-Length`または接続の終端）に委ねられます。
    *   `delete(t.Header, "Transfer-Encoding")`は、`Transfer-Encoding`ヘッダが処理される前にヘッダマップから削除されることを保証します。これは、このヘッダが下流のアプリケーションに誤って伝播するのを防ぐための防御的な措置です。
    *   `Transfer-Encoding`が`chunked`である場合に`Content-Length`を削除するロジックは、HTTP/1.1の仕様に準拠するためのものです。`chunked`エンコーディングが使用されている場合、`Content-Length`は意味を持たず、存在すべきではありません。

これらの変更により、Goの`net/http`パッケージは、HTTPプロトコルのバージョンに応じた`Transfer-Encoding`ヘッダの処理をより正確かつ堅牢に行えるようになりました。

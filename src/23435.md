## 変更の背景

Goランタイムのガベージコレクション（GC）は、ヒープ上のオブジェクトがポインタを含むかどうかを追跡するためにヒープビットマップを使用します。以前の実装では、1ワードサイズのオブジェクトを格納するメモリ領域（スパン）において、ポインタビットが頻繁にクリアされたり設定されたりする非効率な処理が行われていました。具体的には、スパンの初期化時（`initSpan`）、オブジェクトの型情報設定時（`heapBitsSetType`）、およびGCのスイープフェーズ時（`heapBitsSweepSpan`）に、ポインタビットが繰り返し操作されていました。

この冗長な操作は、特に`heapBitsSetType`においてアトミック操作を必要とし、これがパフォーマンスのボトルネックとなる可能性がありました。アトミック操作は、複数のゴルーチンが同時に同じメモリ位置にアクセスする際にデータの整合性を保つために不可欠ですが、非アトミック操作に比べてオーバーヘッドが大きいです。

このコミットの目的は、この非効率性を解消し、特に頻繁に発生する1ワードオブジェクトの割り当てにおけるアトミック操作を回避することで、ランタイムのパフォーマンスを向上させることにありました。

## 前提知識の解説

このコミットを理解するためには、以下のGoランタイムの概念とガベージコレクションの仕組みに関する知識が必要です。

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理するシステム。メモリ管理、スケジューリング、ガベージコレクションなどを担当します。
*   **ヒープ (Heap)**: プログラムが動的にメモリを割り当てる領域。Goでは、`make`や`new`で作成されたオブジェクトがヒープに配置されます。
*   **スパン (Span)**: Goランタイムのメモリ管理において、ヒープは`mspan`と呼ばれる連続したメモリブロックに分割されます。各`mspan`は特定のサイズのオブジェクトを格納するように設計されており、同じサイズクラスのオブジェクトが効率的に配置されます。
*   **ガベージコレクション (Garbage Collection, GC)**: 不要になったメモリを自動的に解放するプロセス。GoのGCは並行（concurrent）かつ低遅延（low-latency）なマーク＆スイープ方式を採用しています。
*   **ヒープビットマップ (Heap Bitmap)**: GoのGCがオブジェクトをスキャンする際に、どのメモリワードがポインタであるかを効率的に判断するために使用するデータ構造です。ヒープ上の各ワードに対応するビットが割り当てられ、ポインタを含むワードのビットは「ポインタビット」としてマークされます。これにより、GCはポインタをたどって到達可能なオブジェクトを特定できます。
*   **ポインタビット (Pointer Bits)**: ヒープビットマップ内で、特定のメモリ位置がポインタを格納していることを示すビット。GCはこのビットを見て、そのメモリ位置が参照しているオブジェクトをマーク対象とします。
*   **1ワードオブジェクト (One-word Objects)**: 1つのマシンワード（例えば64ビットシステムでは8バイト）に収まるサイズのオブジェクト。Goでは、ポインタ自体や小さな整数などがこれに該当します。
*   **アトミック操作 (Atomic Operations)**: 複数のCPUコアやゴルーチンから同時にアクセスされる可能性のある共有メモリに対して、不可分（atomic）に実行される操作。これにより、競合状態（race condition）を防ぎ、データの整合性を保証します。しかし、通常の操作よりもコストがかかります。
*   **`initSpan`**: 新しいスパンが初期化される際に呼び出される関数。
*   **`heapBitsSetType`**: ヒープ上に新しいオブジェクトが割り当てられる際に、そのオブジェクトの型情報に基づいてヒープビットマップを更新する関数。
*   **`heapBitsSweepSpan`**: GCのスイープフェーズで、マークされなかったオブジェクトが占めるメモリを解放し、スパンの状態を更新する関数。

## 技術的詳細

このコミットの核心は、Goランタイムが1ワードサイズのオブジェクトを扱うスパンのヒープビットマップ管理を最適化することにあります。以前のシステムでは、ポインタビットが`initSpan`でクリアされ、`heapBitsSetType`で設定され、`heapBitsSweepSpan`で再びクリアされるというサイクルを繰り返していました。これは、1ワードオブジェクトが常にポインタであるという特性（非ポインタの1ワードオブジェクトは`tinySize`割り当てに集約されるため）を考慮すると、非常に非効率的でした。

新しいアプローチでは、以下の変更が導入されました。

1.  **`initSpan`でのポインタビットの永続的な設定**:
    *   64ビットシステム（`ptrSize == 8`）で、かつスパンが1ワードサイズのオブジェクトを格納する場合（`size == ptrSize`）に限り、`initSpan`関数内でスパン全体のヒープビットマップのポインタビットを`bitPointerAll`に設定します。
    *   これにより、スパンが1ワードオブジェクトのために使用されている間は、ポインタビットが常に設定された状態を保ちます。
    *   以前行われていた`memclr`（メモリクリア）操作は、この特定のケースではスキップされます。

2.  **`heapBitsSweepSpan`でのポインタビットのクリアの停止**:
    *   GCのスイープフェーズで呼び出される`heapBitsSweepSpan`関数において、1ワードスパンのポインタビットをクリアする処理が削除されました。
    *   コミットメッセージのコメントにもあるように、「他のサイズケースとは異なり、ここではポインタビットを設定したままにする」ことで、`initSpan`で一度設定されたビットが維持されます。

3.  **`heapBitsSetType`でのアトミック操作の排除**:
    *   オブジェクト割り当て時に呼び出される`heapBitsSetType`関数から、ポインタビットを設定するためのアトミック操作（`atomicor8`）が完全に削除されました。
    *   これは、`initSpan`で既にポインタビットが設定されているため、`heapBitsSetType`で再度設定する必要がなくなったためです。これにより、頻繁に発生する1ワードオブジェクトの割り当てにおけるアトミック操作のオーバーヘッドがなくなります。
    *   デバッグビルド用に`doubleCheck`が追加され、ポインタビットが正しく設定されていることを検証するアサーションが含まれています。

この変更により、1ワードオブジェクトのライフサイクル全体を通じてポインタビットが一度だけ設定され、その後は変更されないため、ランタイムの効率が向上します。特に、アトミック操作の削減は、並行処理が多いGoプログラムにおいて顕著なパフォーマンス改善をもたらす可能性があります。

ベンチマーク結果は、一部のケースでわずかな改善（例: `FmtFprintfString`, `JSONDecode`）またはわずかな劣化（例: `Fannkuch11`, `RegexpMatchEasy0_1K`）を示していますが、全体としては大きな回帰はなく、アトミック操作の削減という設計目標は達成されています。

## コアとなるコードの変更箇所

変更は`src/runtime/mbitmap.go`ファイルに集中しています。

1.  **`func (h heapBits) initSpan(size, n, total uintptr)`**
    *   `ptrSize == 8 && size == ptrSize` の条件で、スパンのヒープビットマップを`bitPointerAll`で初期化する新しいブロックが追加されました。
    *   既存の`memclr`呼び出しが、この新しいブロックの後に移動し、1ワードスパンの場合はスキップされるようになりました。

2.  **`func heapBitsSweepSpan(base, size, n uintptr, f func(uintptr))`**
    *   `case size == ptrSize:` が `case ptrSize == 8 && size == ptrSize:` に変更されました。
    *   ポインタビットをクリアする行 (`x &^= bitPointer` およびそのシフト版) がコメントアウトされ、削除されました。

3.  **`func heapBitsSetType(x, size, dataSize uintptr, typ *_type)`**
    *   `if size == ptrSize` ブロック内の、ポインタビットを設定するためのアトミック操作を含むコードブロックが完全に削除されました。
    *   代わりに、`initSpan`でポインタビットが設定されるため、ここでは何もする必要がないという説明のコメントが追加されました。
    *   `doubleCheck`が有効な場合にポインタビットが設定されていることを確認するアサーションが追加されました。

## コアとなるコードの解説

### `initSpan` の変更

```go
// src/runtime/mbitmap.go
func (h heapBits) initSpan(size, n, total uintptr) {
	// ... (既存のコード) ...

	nbyte := total / heapBitmapScale
	if ptrSize == 8 && size == ptrSize { // 64ビットシステムで1ワードスパンの場合
		end := h.bitp
		bitp := subtractb(end, nbyte-1)
		for { // スパン全体のポインタビットをbitPointerAllに設定
			*bitp = bitPointerAll
			if bitp == end {
				break
			}
			bitp = add1(bitp)
		}
		return // ポインタビットは既に設定されたので、以降のmemclrは不要
	}
	memclr(unsafe.Pointer(subtractb(h.bitp, nbyte-1)), nbyte) // それ以外のスパンはクリア
}
```
この変更により、64ビット環境で1ワードサイズのオブジェクトを格納するスパンが初期化される際、そのスパンのヒープビットマップ全体が`bitPointerAll`（すべてのビットがポインタを示す状態）で埋められます。これにより、このスパン内のすべてのオブジェクトがポインタであると最初からマークされ、後続の`heapBitsSetType`でのアトミックなビット設定が不要になります。

### `heapBitsSweepSpan` の変更

```go
// src/runtime/mbitmap.go
func heapBitsSweepSpan(base, size, n uintptr, f func(uintptr)) {
	// ... (既存のコード) ...

	switch {
	default:
		throw("heapBitsSweepSpan")
	case ptrSize == 8 && size == ptrSize: // 64ビットシステムで1ワードスパンの場合
		bitp := h.bitp
		for i := uintptr(0); i < n; i += 4 {
			x := uint32(*bitp)
			// Note that unlike the other size cases, we leave the pointer bits set here.
			// These are initialized during initSpan when the span is created and left
			// in place the whole time the span is used for pointer-sized objects.
			// That lets heapBitsSetType avoid an atomic update to set the pointer bit
			// during allocation.
			if x&bitMarked != 0 {
				x &^= bitMarked
			} else {
				// x &^= bitPointer // この行が削除された
				f(base + i*ptrSize)
			}
			// ... (他のビット操作も同様にbitPointerクリアが削除) ...
			*bitp = uint8(x)
		}
	// ... (他のケース) ...
	}
}
```
この部分では、GCのスイープフェーズ中に、1ワードスパンのポインタビットをクリアする処理が削除されました。`initSpan`で一度設定されたポインタビットは、スパンが1ワードオブジェクトのために使われている限り、そのまま維持されます。これにより、ポインタビットの冗長なクリア操作がなくなります。

### `heapBitsSetType` の変更

```go
// src/runtime/mbitmap.go
func heapBitsSetType(x, size, dataSize uintptr, typ *_type) {
	// ... (既存のコード) ...

	if size == ptrSize {
		// It's one word and it has pointers, it must be a pointer.
		// The bitmap byte is shared with the one-word object
		// next to it, and concurrent GC might be marking that
		// object, so we must use an atomic update.
		// We can skip this if the GC is completely off.
		// Note that there is some marking that happens during
		// gcphase == _GCscan, for completely scalar objects,
		// so it is not safe to check just for the marking phases.
		// TODO(rsc): It may make sense to set all the pointer bits
		// when initializing the span, and then the atomicor8 here
		// goes away - heapBitsSetType would be a no-op
		// in that case.
		// if gcphase == _GCoff {
		// 	*h.bitp |= bitPointer << h.shift
		// } else {
		// 	atomicor8(h.bitp, bitPointer<<h.shift)
		// }
		// In general we'd need an atomic update here if the
		// concurrent GC were marking objects in this span,
		// because each bitmap byte describes 3 other objects
		// in addition to the one being allocated.
		// However, since all allocated one-word objects are pointers
		// (non-pointers are aggregated into tinySize allocations),
		// initSpan sets the pointer bits for us. Nothing to do here.
		if doubleCheck {
			if !h.isPointer() {
				throw("heapBitsSetType: pointer bit missing")
			}
		}
		return
	}
	// ... (他のコード) ...
}
```
この関数から、1ワードオブジェクトに対するポインタビット設定のアトミック操作が削除されました。`initSpan`で既にポインタビットが設定されているため、`heapBitsSetType`では何もする必要がなくなりました。これにより、1ワードオブジェクトの割り当てにおけるアトミック操作のオーバーヘッドが完全に排除され、パフォーマンスが向上します。`doubleCheck`は、この新しいロジックが正しく機能していることを検証するためのアサーションです。

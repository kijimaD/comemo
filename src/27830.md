## 元コミット内容

このコミットは、Goコンパイラの`cmd/compile`パッケージにおいて、チャネルに対する`range`ループの処理を修正します。具体的には、チャネルからの値の受信が完了した後、コンパイラが内部的に生成する一時変数（「隠された値」）を明示的にクリアするように変更します。これにより、ガベージコレクションが正しく機能し、メモリリークや不要なメモリ保持を防ぎます。また、関連するコメントの整理も行われています。

## 変更の背景

この変更は、`issue #15281`で報告された問題に対応しています。この問題は、チャネルに対する`for...range`ループを使用する際に、ループ内で受信した値がループの終了後もガベージコレクタによって解放されない可能性があるというものでした。

Goの`for...range`ループがチャネルで使用される場合、コンパイラは内部的に一時変数を作成してチャネルから受信した値を保持します。この一時変数は、ループ変数に値を割り当てるために使用されます。しかし、元の実装では、この一時変数がループの各イテレーションの終わりに適切にクリア（例えば`nil`に設定）されていなかったため、大きなオブジェクトがチャネルを通じて渡された場合、そのオブジェクトへの参照が一時変数に残存し、ガベージコレクタがそのオブジェクトを解放できない状態になっていました。

結果として、チャネルの`range`ループが終了した後も、本来解放されるべきメモリが解放されずに残り続け、メモリ使用量が増加するというメモリリークのような挙動を引き起こしていました。このコミットは、この「隠された値」を明示的にクリアすることで、ガベージコレクタが不要になったメモリを正しく回収できるようにすることを目的としています。

## 前提知識の解説

*   **Goの`for...range`とチャネル**: Go言語の`for...range`ステートメントは、スライス、配列、文字列、マップ、そしてチャネルをイテレートするために使用されます。チャネルに対する`for...range`は、チャネルがクローズされるまで、またはチャネルから値が受信できなくなるまで、チャネルから値を受信し続けます。
    ```go
    for v := range ch {
        // v はチャネル ch から受信した値
    }
    ```
*   **ガベージコレクション (GC)**: Goランタイムは自動メモリ管理（ガベージコレクション）を提供します。プログラムが不要になったメモリ領域を自動的に識別し、解放することで、開発者が手動でメモリを管理する負担を軽減します。GCは、到達可能なオブジェクト（プログラムがまだ参照しているオブジェクト）を特定し、到達不能なオブジェクトを解放します。
*   **Goコンパイラの内部処理**: Goコンパイラは、高レベルのGoコードを機械語に変換する過程で、多くの最適化や内部的な変数生成を行います。`for...range`のような構文は、コンパイラによってより低レベルのループ構造や一時変数を使ったコードに変換されます。この一時変数は、Goのソースコードには直接現れないため、「隠された値」と呼ばれることがあります。
*   **`hv1`**: このコミットの文脈では、`hv1`はコンパイラがチャネルの`range`ループ処理中に生成する内部的な一時変数を指します。これは、チャネルから受信した値を一時的に保持するために使用されます。

## 技術的詳細

このコミットの核心は、Goコンパイラの`cmd/compile/internal/gc/range.go`ファイル内の`walkrange`関数における変更です。`walkrange`関数は、`for...range`ステートメントをコンパイル時に処理する役割を担っています。

チャネルに対する`range`ループ（`case TCHAN`）の処理において、コンパイラはチャネルから値を受信し、それをループ変数に割り当てます。この際、チャネルから受信した生の値は、`hv1`という内部的な隠された変数に一時的に格納されます。

元の実装では、`hv1`に格納された値がループ変数を介して使用された後、`hv1`自体が明示的にクリアされることはありませんでした。もし`hv1`が大きなオブジェクトへの参照を保持していた場合、その参照が残り続けることで、ガベージコレクタがそのオブジェクトを「到達可能」と誤認し、メモリを解放できない状態が発生していました。これは、特にループの各イテレーションで新しい大きなオブジェクトがチャネルに送信され、それが`hv1`に一時的にバインドされるようなシナリオで問題となります。

このコミットでは、`hv1`がループ変数に割り当てられた後、ループボディの最後に`hv1`を`nil`に設定する（またはそのゼロ値に設定する）コードが追加されました。具体的には、`Nod(OAS, hv1, nil)`というASTノードが生成され、ループボディに追加されます。`OAS`は代入操作（`=`）を表し、`hv1`に`nil`を代入することで、`hv1`が保持していたオブジェクトへの参照を解除します。これにより、オブジェクトが不要になった時点でガベージコレクタがそれを正しく回収できるようになります。

この変更は、Goのメモリ管理の正確性を向上させ、特定の条件下でのメモリリークを防ぐ上で非常に重要です。

## コアとなるコードの解説

`src/cmd/compile/internal/gc/range.go`の変更点に焦点を当てます。

```go
 		} else {
 			body = []*Node{Nod(OAS, v1, hv1)}
 		}
+		// Zero hv1. This prevents hv1 from being the sole, inaccessible
+		// reference to an otherwise GC-able value during the next channel receive.
+		// See issue 15281.
+		body = append(body, Nod(OAS, hv1, nil))
```

*   `body = []*Node{Nod(OAS, v1, hv1)}`: これは、チャネルから受信した値（`hv1`）をループ変数（`v1`）に代入するASTノードを生成し、ループボディに追加する部分です。
*   `body = append(body, Nod(OAS, hv1, nil))`: この行が今回のコミットで追加された最も重要な変更です。
    *   `Nod(OAS, hv1, nil)`: これは、`hv1`変数に`nil`を代入する操作を表すASTノードを作成します。`OAS`は代入演算子（`=`）を意味します。
    *   `append(body, ...)`: 生成された`hv1 = nil`の代入ノードを、ループボディの既存のASTノードリストの末尾に追加します。

この追加により、チャネルの`range`ループの各イテレーションの終わりに、`hv1`が保持していた参照が明示的に解除されます。これにより、`hv1`が唯一の参照元であったオブジェクトは、次のガベージコレクションサイクルで解放される対象となります。コメントにもあるように、「これにより、次のチャネル受信時に、`hv1`が、そうでなければGC可能な値への唯一の、アクセス不能な参照となるのを防ぎます。」という目的が達成されます。

`test/fixedbugs/issue15281.go`は、この修正が正しく機能することを確認するためのテストケースです。このテストは、大きなバイトスライスをチャネルに送信し、`for...range`ループでそれを受信した後、メモリ使用量が期待通りに減少するかどうかをチェックします。`inuse()`関数は`runtime.GC()`を呼び出してGCを実行し、`runtime.ReadMemStats()`でメモリ統計を読み取ることで、メモリ使用量の変化を測定しています。これにより、修正がメモリリークの問題を解決したことを検証しています。

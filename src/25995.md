## 元コミット内容

このコミットは、`net/http`パッケージの`serve_test.go`ファイルにおいて、HTTPメソッドのケースセンシティブ性を検証するテスト`TestCaseSensitiveMethod`を、HTTP/2プロトコルにも対応させるように変更しています。

変更の概要は以下の通りです。

1.  既存のテスト関数`TestCaseSensitiveMethod`を、HTTP/1.xとHTTP/2の両方で利用できるヘルパー関数`testCaseSensitiveMethod`にリファクタリングしました。
2.  `testCaseSensitiveMethod`関数は、HTTP/2を使用するかどうかを示すブーリアン引数`h2`を受け取るようになりました。
3.  `TestCaseSensitiveMethod_h1`と`TestCaseSensitiveMethod_h2`という新しいテスト関数が導入されました。
    *   `TestCaseSensitiveMethod_h1`は`testCaseSensitiveMethod(t, false)`を呼び出し、HTTP/1.x環境でのテストを実行します。
    *   `TestCaseSensitiveMethod_h2`は`testCaseSensitiveMethod(t, true)`を呼び出し、HTTP/2環境でのテストを実行します。
4.  テストサーバーとクライアントのセットアップに、`newClientServerTest`というヘルパー関数が使用されるようになりました。これは、`h2`引数に基づいてHTTP/1.xまたはHTTP/2の環境を適切に構築します。
5.  テストロジック自体（リクエストメソッドが期待通りに"get"として認識されるか）は変更されていませんが、その実行環境がHTTP/2にも拡張されました。

## 変更の背景

この変更の背景には、HTTPプロトコルの進化、特にHTTP/2の導入があります。

*   **HTTP/1.xとHTTP/2の共存**: Goの`net/http`パッケージは、HTTP/1.xとHTTP/2の両方をサポートしています。新しいプロトコルが導入される際、既存の機能が新しいプロトコル環境下でも正しく動作するかどうかを検証することが重要です。
*   **HTTPメソッドのケースセンシティブ性**: HTTP/1.xの仕様（RFC 7231）では、メソッド名はケースセンシティブであるとされていますが、実際の多くの実装では大文字・小文字を区別しない（ケースインセンシティブな）処理が行われることがあります。一方、HTTP/2の仕様（RFC 7540）では、メソッドは擬似ヘッダーフィールド`:method`として扱われ、その値は常に大文字でなければならないと明確に規定されています。
*   **テストカバレッジの向上**: `net/http`パッケージがHTTP/2をサポートするようになったため、既存の重要なテストケース（この場合はメソッドのケースセンシティブ性）がHTTP/2環境でも適切に機能するかを確認し、テストカバレッジを向上させる必要がありました。このコミットは、HTTP/2環境下でのメソッド処理がGoの`net/http`実装において期待通りに動作することを保証するためのものです。

## 前提知識の解説

### 1. HTTPメソッドとケースセンシティブ性

*   **HTTPメソッド**: WebクライアントがWebサーバーに対して実行したいアクションを示すものです。代表的なものに`GET`, `POST`, `PUT`, `DELETE`, `HEAD`, `OPTIONS`などがあります。
*   **HTTP/1.xにおけるケースセンシティブ性**: HTTP/1.xの仕様では、メソッド名は大文字と小文字を区別するとされています（例: `GET`と`get`は異なるメソッドとして扱われる可能性がある）。しかし、歴史的な経緯や実装の都合上、多くのサーバーやクライアントはメソッド名をケースインセンシティブに扱う傾向がありました。Goの`net/http`パッケージは、リクエストを受け取った際にメソッド名を正規化して大文字で扱うことが一般的です。このテストは、クライアントが小文字のメソッド名でリクエストを送信した場合でも、サーバー側で正しく処理されるか（またはエラーとなるか）を検証するものです。
*   **HTTP/2におけるケースセンシティブ性**: HTTP/2では、HTTP/1.xのヘッダーフィールドが「擬似ヘッダーフィールド」として再定義され、メソッドは`:method`という擬似ヘッダーフィールドの値として扱われます。HTTP/2の仕様では、この`:method`の値は常に大文字でなければならないと厳格に規定されています。したがって、HTTP/2クライアントが小文字のメソッド名でリクエストを送信した場合、それは仕様違反となり、通常はエラーとして扱われるか、サーバーによって拒否されるべきです。

### 2. Goの `net/http` パッケージ

Go言語の標準ライブラリである`net/http`パッケージは、HTTPクライアントとサーバーを構築するための包括的な機能を提供します。

*   **`http.HandlerFunc`**: HTTPリクエストを処理するための関数を`http.Handler`インターフェースに適合させるためのアダプターです。
*   **`http.ResponseWriter`**: HTTPレスポンスをクライアントに書き込むためのインターフェースです。
*   **`http.Request`**: クライアントから受信したHTTPリクエストを表す構造体です。`r.Method`フィールドはリクエストメソッド（例: "GET", "POST"）を保持します。
*   **`httptest.NewServer`**: テスト目的でHTTPサーバーを簡単に起動するためのユーティリティ関数です。実際のネットワークポートをリッスンし、テスト中にHTTPリクエストを処理できます。
*   **`http.DefaultClient`**: `net/http`パッケージが提供するデフォルトのHTTPクライアントです。

### 3. HTTP/1.x と HTTP/2

*   **HTTP/1.x**: 広く普及しているHTTPプロトコルのバージョンです。リクエスト/レスポンスはテキストベースで、ヘッダーはASCII文字列です。各リクエストは通常、新しいTCP接続を必要とするか、パイプライン処理（限定的）を使用します。
*   **HTTP/2**: HTTP/1.xのセマンティクスを維持しつつ、パフォーマンスを大幅に向上させるために設計されたプロトコルです。主な特徴は以下の通りです。
    *   **バイナリフレーミング層**: テキストベースではなくバイナリ形式でデータを送受信します。
    *   **多重化 (Multiplexing)**: 単一のTCP接続上で複数のリクエストとレスポンスを同時に送受信できます。これにより、ヘッドオブラインブロッキングの問題が解消されます。
    *   **ヘッダー圧縮 (HPACK)**: ヘッダーの冗長性を排除し、効率的に圧縮します。
    *   **サーバープッシュ**: サーバーがクライアントの明示的な要求なしにリソースを送信できます。
    *   **メソッドの扱い**: HTTP/2では、HTTP/1.xのステータスライン（メソッド、パス、プロトコルバージョン）が`:method`, `:scheme`, `:authority`, `:path`といった擬似ヘッダーフィールドに変換されます。`:method`の値は常に大文字でなければなりません。

    Goのテストフレームワークは、`Test`で始まる関数を自動的にテストとして認識します。この命名規則により、`go test`コマンドを実行すると、HTTP/1.xとHTTP/2の両方のシナリオが個別のテストとして実行されます。`_h1`はHTTP/1.x、`_h2`はHTTP/2を示唆しています。

    *   `h2`が`true`の場合: HTTP/2をサポートする`http.Server`と`http.Client`を設定します。これには、TLS設定（HTTP/2は通常TLS上で動作するため）や、HTTP/2トランスポートの設定が含まれる可能性があります。
    *   `h2`が`false`の場合: 標準的なHTTP/1.xサーバーとクライアントを設定します。

4.  **テストロジック**:
    ```go

        t.Errorf(`Got method %q; want "get"`, r.Method)
    }
    ```
    この部分がテストの核心です。クライアントが小文字の"get"メソッドでリクエストを送信した場合、サーバー側の`r.Method`がどのような値になるかを検証しています。Goの`net/http`サーバーは、HTTP/1.xリクエストのメソッド名を自動的に大文字に正規化するため、このテストは通常`r.Method`が`"GET"`になることを期待するはずです。しかし、このテストでは`"get"`を期待しているため、これはクライアントが送信したそのままのメソッド名がサーバーに渡されることを期待しているか、あるいは特定のケースで小文字が保持されることを検証している可能性があります。HTTP/2の場合、`:method`擬似ヘッダーは常に大文字であるべきなので、クライアントが小文字で送信しても、サーバー側では大文字に変換されて受け取られることが期待されます。このテストの意図は、Goの`net/http`がメソッド名をどのように正規化するか、またはしないかを検証することにあります。

この変更により、Goの`net/http`パッケージがHTTP/2環境下でもHTTPメソッドの処理に関して期待される動作（特にケースセンシティブ性や正規化）を維持していることが保証されます。

*   **HTTPメソッドのケースセンシティブ性**: HTTP/1.xの仕様（RFC 7231）では、メソッド名は大文字と小文字を区別するとされていますが、実際の多くの実装では大文字・小文字を区別しない（ケースインセンシティブな）処理が行われることがあります。一方、HTTP/2の仕様（RFC 7540）では、メソッドは擬似ヘッダーフィールド`:method`として扱われ、その値は常に大文字でなければならないと明確に規定されています。
*   **テストカバレッジの向上**: `net/http`パッケージがHTTP/2をサポートするようになったため、既存の重要なテストケース（この場合はメソッドのケースセンシティブ性）がHTTP/2環境でも適切に機能するかを確認し、テストカバレッジを向上させる必要がありました。このコミットは、HTTP/2環境下でのメソッド処理がGoの`net/http`実装において期待通りに動作することを保証するためのものです。

## 前提知識の解説

### 1. HTTPメソッドとケースセンシティブ性

*   **HTTPメソッド**: WebクライアントがWebサーバーに対して実行したいアクションを示すものです。代表的なものに`GET`, `POST`, `PUT`, `DELETE`, `HEAD`, `OPTIONS`などがあります。
*   **HTTP/1.xにおけるケースセンシティブ性**: HTTP/1.xの仕様では、メソッド名は大文字と小文字を区別するとされています（例: `GET`と`get`は異なるメソッドとして扱われる可能性がある）。しかし、歴史的な経緯や実装の都合上、多くのサーバーやクライアントはメソッド名をケースインセンシティブに扱う傾向がありました。Goの`net/http`パッケージは、リクエストを受け取った際にメソッド名を正規化して大文字で扱うことが一般的です。このテストは、クライアントが小文字のメソッド名でリクエストを送信した場合でも、サーバー側で正しく処理されるか（またはエラーとなるか）を検証するものです。
*   **HTTP/2におけるケースセンシティブ性**: HTTP/2では、HTTP/1.xのヘッダーフィールドが「擬似ヘッダーフィールド」として再定義され、メソッドは`:method`という擬似ヘッダーフィールドの値として扱われます。HTTP/2の仕様では、この`:method`の値は常に大文字でなければならないと厳格に規定されています。したがって、HTTP/2クライアントが小文字のメソッド名でリクエストを送信した場合、それは仕様違反となり、通常はエラーとして扱われるか、サーバーによって拒否されるべきです。

### 2. Goの `net/http` パッケージ

Go言語の標準ライブラリである`net/http`パッケージは、HTTPクライアントとサーバーを構築するための包括的な機能を提供します。

*   **`http.HandlerFunc`**: HTTPリクエストを処理するための関数を`http.Handler`インターフェースに適合させるためのアダプターです。
*   **`http.ResponseWriter`**: HTTPレスポンスをクライアントに書き込むためのインターフェースです。
*   **`http.Request`**: クライアントから受信したHTTPリクエストを表す構造体です。`r.Method`フィールドはリクエストメソッド（例: "GET", "POST"）を保持します。
*   **`httptest.NewServer`**: テスト目的でHTTPサーバーを簡単に起動するためのユーティリティ関数です。実際のネットワークポートをリッスンし、テスト中にHTTPリクエストを処理できます。
*   **`http.DefaultClient`**: `net/http`パッケージが提供するデフォルトのHTTPクライアントです。

### 3. HTTP/1.x と HTTP/2

*   **HTTP/1.x**: 広く普及しているHTTPプロトコルのバージョンです。リクエスト/レスポンスはテキストベースで、ヘッダーはASCII文字列です。各リクエストは通常、新しいTCP接続を必要とするか、パイプライン処理（限定的）を使用します。
*   **HTTP/2**: HTTP/1.xのセマンティクスを維持しつつ、パフォーマンスを大幅に向上させるために設計されたプロトコルです。主な特徴は以下の通りです。
    *   **バイナリフレーミング層**: テキストベースではなくバイナリ形式でデータを送受信します。
    *   **多重化 (Multiplexing)**: 単一のTCP接続上で複数のリクエストとレスポンスを同時に送受信できます。これにより、ヘッドオブラインブロッキングの問題が解消されます。
    *   **ヘッダー圧縮 (HPACK)**: ヘッダーの冗長性を排除し、効率的に圧縮します。
    *   **サーバープッシュ**: サーバーがクライアントの明示的な要求なしにリソースを送信できます。
    *   **メソッドの扱い**: HTTP/2では、HTTP/1.xのステータスライン（メソッド、パス、プロトコルバージョン）が`:method`, `:scheme`, `:authority`, `:path`といった擬似ヘッダーフィールドに変換されます。`:method`の値は常に大文字でなければなりません。

## 技術的詳細

このコミットの技術的な核心は、HTTPメソッドのケースセンシティブ性という特定のHTTPプロトコル動作が、HTTP/1.xとHTTP/2の両方の環境で一貫してテストされるようにすることです。

元の`TestCaseSensitiveMethod`関数は、`httptest.NewServer`と`http.DefaultClient`を使用していました。これらはデフォルトでHTTP/1.xプロトコルを使用します。HTTP/2のサポートが`net/http`パッケージに統合された後、HTTP/2環境下での同様の動作を検証する必要が生じました。

変更点を見てみましょう。

1.  **テスト関数のリファクタリング**:
    *   `func TestCaseSensitiveMethod(t *testing.T)`
        ↓
    *   `func testCaseSensitiveMethod(t *testing.T, h2 bool)`
    この変更により、テストロジック自体は`testCaseSensitiveMethod`に集約され、`h2`というブーリアン引数によってHTTP/2のテストパスを制御できるようになりました。これは、テストの重複を避け、保守性を高めるための一般的なプラクティスです。

2.  **HTTP/1.xとHTTP/2のテストケースの分離**:
    *   `func TestCaseSensitiveMethod_h1(t *testing.T) { testCaseSensitiveMethod(t, false) }`
    *   `func TestCaseSensitiveMethod_h2(t *testing.T) { testCaseSensitiveMethod(t, true) }`
    Goのテストフレームワークは、`Test`で始まる関数を自動的にテストとして認識します。この命名規則により、`go test`コマンドを実行すると、HTTP/1.xとHTTP/2の両方のシナリオが個別のテストとして実行されます。`_h1`はHTTP/1.x、`_h2`はHTTP/2を示唆しています。

3.  **`newClientServerTest`の導入**:
    元のコードでは`httptest.NewServer`と`DefaultClient`を直接使用していましたが、変更後には`newClientServerTest`というヘルパー関数（このコミットの差分には含まれていませんが、`serve_test.go`の他の場所で定義されていると推測されます）が導入されています。
    この`newClientServerTest`関数は、`h2`引数に基づいて、HTTP/1.xまたはHTTP/2をサポートする適切なテストサーバーとクライアントのペアをセットアップする役割を担っています。これにより、`testCaseSensitiveMethod`内のテストロジックは、プロトコルの詳細を意識することなく、抽象化されたテスト環境で実行できるようになります。

    具体的には、`newClientServerTest`は以下のような処理を行っていると考えられます。
    *   `h2`が`true`の場合: HTTP/2をサポートする`http.Server`と`http.Client`を設定します。これには、TLS設定（HTTP/2は通常TLS上で動作するため）や、HTTP/2トランスポートの設定が含まれる可能性があります。
    *   `h2`が`false`の場合: 標準的なHTTP/1.xサーバーとクライアントを設定します。

4.  **テストロジック**:
    ```go
    if r.Method != "get" {
        t.Errorf(`Got method %q; want "get"`, r.Method)
    }
    ```
    この部分がテストの核心です。クライアントが小文字の"get"メソッドでリクエストを送信した場合、サーバー側の`r.Method`がどのような値になるかを検証しています。Goの`net/http`サーバーは、HTTP/1.xリクエストのメソッド名を自動的に大文字に正規化するため、このテストは通常`r.Method`が`"GET"`になることを期待するはずです。しかし、このテストでは`"get"`を期待しているため、これはクライアントが送信したそのままのメソッド名がサーバーに渡されることを期待しているか、あるいは特定のケースで小文字が保持されることを検証している可能性があります。HTTP/2の場合、`:method`擬似ヘッダーは常に大文字であるべきなので、クライアントが小文字で送信しても、サーバー側では大文字に変換されて受け取られることが期待されます。このテストの意図は、Goの`net/http`がメソッド名をどのように正規化するか、またはしないかを検証することにあります。

この変更により、Goの`net/http`パッケージがHTTP/2環境下でもHTTPメソッドの処理に関して期待される動作（特にケースセンシティブ性や正規化）を維持していることが保証されます。

1.  **`TestCaseSensitiveMethod`から`testCaseSensitiveMethod`へのリファクタリング**:

2.  **HTTP/1.xとHTTP/2のテスト関数の追加**:
    *   `func TestCaseSensitiveMethod_h1(t *testing.T) { testCaseSensitiveMethod(t, false) }`
    *   `func TestCaseSensitiveMethod_h2(t *testing.T) { testCaseSensitiveMethod(t, true) }`

3.  **テストサーバーとクライアントのセットアップの変更**:
    *   変更前:
        ```go
        ts := httptest.NewServer(HandlerFunc(...))
        // ...
        req, _ := NewRequest("get", ts.URL, nil)
        res, err := DefaultClient.Do(req)
        ```
        ここでは、`httptest.NewServer`でHTTP/1.xサーバーを起動し、`http.DefaultClient`でリクエストを送信していました。
    *   変更後:
        ```go
        cst := newClientServerTest(t, h2, HandlerFunc(...))
        // ...
        req, _ := NewRequest("get", cst.ts.URL, nil)
        res, err := cst.c.Do(req)
        ```
        `newClientServerTest`というヘルパー関数が導入されました。この関数は、`h2`引数に基づいて、HTTP/1.xまたはHTTP/2のテスト環境（サーバー`cst.ts`とクライアント`cst.c`）をセットアップします。これにより、`testCaseSensitiveMethod`関数は、プロトコルの詳細を意識することなく、抽象化されたテスト環境で動作できます。`cst.close()`は、テスト終了時にサーバーとクライアントのリソースを適切にクリーンアップするために`defer`で呼び出されます。

    この部分は、クライアントが小文字の`"get"`メソッドでリクエストを送信した際に、サーバー側の`http.Request.Method`フィールドがどのような値を持つかを検証しています。Goの`net/http`サーバーは、通常、受信したHTTPメソッド名を大文字に正規化します（例: `"GET"`）。したがって、このテストが`"get"`を期待しているのは、特定の条件下で小文字が保持されることを検証しているか、あるいはテストの意図が「クライアントが送信したメソッド名がそのまま`r.Method`に反映されるか」を検証することにある可能性があります。HTTP/2の仕様ではメソッドは常に大文字であるべきなので、HTTP/2のテストではクライアントが小文字で送信しても、サーバー側では大文字に変換されて受け取られることが期待されます。このテストは、Goの`net/http`がHTTP/1.xとHTTP/2の両方でメソッド名をどのように処理するかを検証する重要な役割を担っています。

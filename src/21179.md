## 元コミット内容

このコミットは、`dev.cc`ブランチ（ハッシュ: `493ad916c3b1`）の変更を`dev.garbage`ブランチにマージしたものです。コミットメッセージ自体は簡潔ですが、その内容はGoプロジェクト全体にわたる広範な変更を含んでいます。具体的には、GoランタイムのC言語部分のGo言語への移植、新しいアーキテクチャのサポート追加、および既存のOSサポートの改善が主な内容です。

## 変更の背景

このコミットの背景には、Go言語の「セルフホスティング」という大きな目標があります。Go 1.4のリリースに向けて、GoチームはGoランタイムのC言語で書かれた部分をGo言語自体で書き直す作業を進めていました。これにより、Goコンパイラとランタイムが完全にGo言語で記述されることになり、Go言語のビルドプロセスが簡素化され、Go言語のツールチェイン全体の保守性が向上します。

また、新しいアーキテクチャ（特にPowerPC 64-bit）への対応も重要な背景です。Go言語がより多くのプラットフォームで利用されるためには、多様なCPUアーキテクチャへのサポートが不可欠でした。

さらに、既存のOS（Windows, NetBSD, Plan9, NaCl）におけるランタイムのC言語部分をGo言語に移行することで、プラットフォーム固有のCコードの量を減らし、Goランタイムの移植性と一貫性を高める狙いがありました。

`dev.cc`と`dev.garbage`というブランチ名は、当時のGo開発における実験的な、あるいは大規模な変更を伴う作業ブランチを示唆しています。特に`dev.cc`は「CからGoへ」の移行作業に関連するブランチであったと推測されます。

## 前提知識の解説

*   **Goのセルフホスティング (Go self-hosting)**: Go言語のコンパイラやランタイムといったコアツールが、Go言語自体で書かれている状態を指します。初期のGoコンパイラはC言語で書かれていましたが、Go 1.5以降は完全にGo言語で書かれるようになりました。このコミットは、その移行プロセスにおける重要なマイルストーンの一つです。セルフホスティングにより、Go開発者はGo言語の知識だけでツールチェイン全体を理解・改善できるようになります。
*   **Goランタイム (Go runtime)**: Goプログラムの実行を管理する低レベルのコード群です。ガベージコレクション、ゴルーチン管理、スケジューリング、チャネル通信、システムコールなどが含まれます。初期のGoランタイムにはC言語で書かれた部分が多く存在しました。
*   **Plan 9 Cコンパイラ (cmd/9c)**: Go言語の初期のコンパイラは、Plan 9オペレーティングシステムのために開発されたツールチェイン（`5c`, `6c`, `8c`など）をベースにしていました。`cmd/9c`はその名残であり、Go言語のソースコードをアセンブリコードに変換する役割を担っていました。セルフホスティングの過程で、これらのC言語ベースのコンパイラはGo言語で書かれた新しいコンパイラに置き換えられていきました。
*   **ロックフリースタック (Lock-free stack)**: 複数のゴルーチンが同時にアクセスしても、ロックを使用せずに正しく動作するように設計されたデータ構造です。Goランタイムの内部で、例えばメモリ管理やスケジューリングの効率化のために使用されます。`lfnode`構造体は、このロックフリースタックのノードを表します。
*   **レース検出器 (Race detector)**: Goプログラムにおけるデータ競合（複数のゴルーチンが同時に共有メモリにアクセスし、少なくとも一方が書き込みを行う場合に発生するバグ）を検出するためのツールです。Go 1.1で導入され、Go 1.4でさらに改善されました。

## 技術的詳細

このコミットは、GoランタイムのC言語部分をGo言語に移植する作業の集大成の一つです。

1.  **C言語コードの削除とGo言語コードへの置き換え**:
    *   `src/runtime/os_windows.c`, `src/runtime/os_netbsd.c`, `src/runtime/os_plan9.c`, `src/runtime/os_nacl.c`など、各OS固有のランタイムCコードが大量に削除され、対応する`src/runtime/os1_*.go`や`src/runtime/os2_*.go`ファイルが追加されています。これは、GoランタイムのOSインタフェース層がC言語からGo言語へ移行したことを明確に示しています。これにより、Goランタイムのコードベースがより一貫性のあるGo言語で記述されることになり、Go開発者にとっての可読性、保守性、およびデバッグの容易さが向上します。
    *   同様に、シグナルハンドリング関連のCファイル（例: `src/runtime/signal_power64x.c`）も削除され、Go言語のファイル（例: `src/runtime/signal_power64x.go`）に置き換えられています。
    *   `src/cmd/9c`ディレクトリ内の多数のファイル（`cgen.c`, `mul.c`, `peep.c`, `reg.c`, `swt.c`, `txt.c`など）が大量に削除されています。これは、Go 1.5で導入される新しいGo言語で書かれたコンパイラ（`gc`）への移行準備の一環であり、従来のPlan 9 Cベースのコンパイラバックエンドが段階的に廃止されていく過程を示しています。

2.  **新しいアーキテクチャのサポート**:
    *   PowerPC 64-bit (power64, power64le) および AMD64P32 (amd64p32) アーキテクチャのサポートが追加または強化されています。これには、新しいアーキテクチャ固有の定義ファイル（`src/runtime/defs_linux_power64.go`, `src/runtime/defs_linux_power64le.go`）、アセンブリコード（`src/runtime/asm_power64x.s`）、およびランタイムのGoコード（`src/runtime/atomic_power64x.go`, `src/runtime/signal_linux_power64x.go`, `src/runtime/sys_power64x.go`）の追加が含まれます。これにより、Go言語がより多様なハードウェア環境で動作できるようになります。

3.  **ロックフリースタックの改善**:
    *   `src/runtime/lfstack.go`と`src/runtime/runtime2.go`において、ロックフリースタックのノード構造体`lfnode`の`next`フィールドが`*lfnode`から`uint64`に変更されています。これは、ポインタとカウンタを単一の`uint64`値にパックすることで、アトミック操作の効率を高めるための最適化です。`lfstackPack`関数でノードポインタとカウンタをパックし、`lfstackUnpack`関数でそれらを分離します。これにより、`CompareAndSwap`操作がより効率的に行えるようになります。

4.  **レース検出器の変更**:
    *   `src/run.bash`スクリプト内のレース検出器のテスト部分がコメントアウトされ、「DISABLED until we get garbage collection working.」というコメントが追加されています。これは、当時のレース検出器がガベージコレクションと完全に連携できていなかったことを示唆しており、今後の改善点として認識されていたことを意味します。

5.  **`goobj`パッケージの移動**:
    *   `src/debug/goobj`が`src/cmd/internal/goobj`に移動されています。これは、`goobj`がデバッグツールだけでなく、Goコマンドの内部ツールとしてより密接に統合されることを示しています。

これらの変更は、Go言語のランタイムがC言語への依存を減らし、Go言語自体でより多くの機能を提供するという、Go 1.5に向けた重要な戦略的転換の一部です。これにより、Go言語の進化と将来の拡張性が大きく向上しました。

## コアとなるコードの解説

### `src/runtime/lfstack.go` と `src/runtime/runtime2.go` の変更

`src/runtime/runtime2.go`では、ロックフリースタックのノードを表す`lfnode`構造体の定義が変更されています。

```go
// 旧:
// type lfnode struct {
//  next    *lfnode
//  pushcnt uintptr
// }

// 新:
type lfnode struct {
    next    uint64 // ポインタとカウンタをパック
    pushcnt uintptr
}
```

`next`フィールドが`*lfnode`（ポインタ）から`uint64`に変更されました。これは、ポインタと、ノードがスタックにプッシュされた回数を表すカウンタ（`pushcnt`）を、単一の`uint64`値にパックして格納するためです。このテクニックは、ロックフリーデータ構造でABA問題を回避しつつ、`CompareAndSwap` (CAS) 操作を効率的に行うためによく用いられます。

`src/runtime/lfstack.go`では、この新しい`lfnode`構造体に対応する`lfstackpush`関数の変更が見られます。

```go
// src/runtime/lfstack.go (変更箇所抜粋)
func lfstackpush(head *uint64, node *lfnode) {
    node.pushcnt++
    new := lfstackPack(node, node.pushcnt) // ノードとカウンタをパック
    if node1, _ := lfstackUnpack(new); node1 != node {
        // パック/アンパックの整合性チェック
        println("runtime: lfstackpush invalid packing: node=", node, " cnt=", hex(node.pushcnt), " packed=", hex(new), " -> node=", node1, "\n")
        gothrow("lfstackpush")
    }
    for {
        old := atomicload64(head)
        // 旧: node.next, _ = lfstackUnpack(old)
        // 新: node.next = old // 次のノードのパックされた値を直接格納
        node.next = old
        if cas64(head, old, new) { // アトミックなCAS操作
            break
        }
    }
}
```

`lfstackPack`関数（このコミットには含まれていませんが、この変更と密接に関連しています）は、`*lfnode`ポインタと`pushcnt`を`uint64`に結合します。`lfstackUnpack`関数はその逆を行います。
`node.next = old`という行は、現在のスタックの`head`が指していた`old`値を、新しくプッシュされる`node`の`next`フィールドに設定しています。この`old`値は、以前のスタックの先頭ノードのポインタとカウンタがパックされたものです。これにより、新しいノードがスタックの先頭になり、その`next`は以前の先頭を指すことになります。
`cas64(head, old, new)`は、`head`がまだ`old`値である場合にのみ、`head`を`new`値にアトミックに更新します。これにより、複数のゴルーチンが同時にスタックを操作しようとしても、データ競合なしに安全に処理が進められます。

### `src/run.bash` の変更

レース検出器のテスト部分がコメントアウトされています。

```bash
# 旧:
# case "$GOHOSTOS-$GOOS-$GOARCH-$CGO_ENABLED" in
# linux-linux-amd64-1 | freebsd-freebsd-amd64-1 | darwin-darwin-amd64-1)
#   echo
#   echo '# Testing race detector.'
#   go test -race -i runtime/race flag os/exec
#   go test -race -run=Output runtime/race
#   go test -race -short flag os/exec
#   
#   # Test with external linking; see issue 9133.
#   if [ "$extlink" = 1 ]; then
#       go test -race -short -ldflags=-linkmode=external flag os/exec
#   fi
# esac

# 新:
# DISABLED until we get garbage collection working.
case "$GOHOSTOS-$GOOS-$GOARCH-$CGO_ENABLED-XXX-DISABLED" in
linux-linux-amd64-1 | freebsd-freebsd-amd64-1 | darwin-darwin-amd64-1)
    # ... (元のテストコードが残っているが、case文の条件により実行されない)
esac
```

`case`文の条件に`-XXX-DISABLED`が追加されており、これによりこのブロック内のテストが実行されなくなっています。コメント「`# DISABLED until we get garbage collection working.`」は、当時のレース検出器がガベージコレクションと完全に連携できておらず、その問題が解決されるまでテストを無効にしていたことを示しています。これは、Goランタイムの複雑な相互作用と、機能間の依存関係を管理する上での課題を浮き彫りにしています。

これらの変更は、Goランタイムの内部構造をより効率的かつGo言語ネイティブなものへと進化させるための重要なステップであり、Go言語のパフォーマンスと保守性の向上に貢献しました。

## 変更の背景

このコミットは、`default`ブランチ（当時のGoのメイン開発ブランチ）で行われた複数の修正や改善を、実験的な`dev.garbage`ブランチにマージするものです。コミットメッセージには「`TestDualStackUDPListener`の修正を取り込む」ことが主な理由として挙げられていますが、実際の変更内容を見ると、それ以外にもGoランタイムのメモリ管理、特にファイナライザの挙動に関する重要なバグ修正と改善、そしてGoのリンカ/アセンブラにおけるリロケーション処理の修正が含まれています。

これは、開発ブランチ間で機能や修正を同期させる一般的なプラクティスの一環であり、特定のテストの不安定性（`TestDualStackUDPListener`）がマージのトリガーの一つとなったと考えられます。しかし、マージコミットであるため、関連する複数の変更が一度に取り込まれています。

## 前提知識の解説

*   **Go Runtime (Goランタイム)**: Goプログラムの実行を管理するシステムです。これには、ガベージコレクション（GC）、ゴルーチン（軽量スレッド）のスケジューリング、メモリ割り当て、システムコールインターフェースなどが含まれます。Goプログラムは、OS上で直接実行されるのではなく、このランタイム上で動作します。
*   **Garbage Collection (GC)**: プログラムが不要になったメモリを自動的に解放するプロセスです。Goはトレース型GCを採用しており、到達可能なオブジェクトを特定し、それ以外のオブジェクトを解放します。
*   **Finalizers (ファイナライザ)**: Goの`runtime.SetFinalizer`関数によって設定される特殊な関数です。ガベージコレクタが、ファイナライザが設定されたオブジェクトが到達不可能になったことを検出した際に、そのオブジェクトがメモリから解放される前に実行されます。主に、ファイルハンドルやネットワーク接続などのOSリソースをクリーンアップするために使用されます。ただし、ファイナライザの実行は保証されず、プログラム終了時や、オブジェクトが非常に小さい場合など、特定の条件下では実行されない可能性があります。
*   **Memory Allocation (メモリ割り当て)**: プログラムが実行時にメモリを要求し、OSやランタイムから割り当てられるプロセスです。Goランタイムは、効率的なメモリ利用のために独自のメモリ管理メカニズムを持っています。
*   **Linker (リンカ)**: コンパイラによって生成されたオブジェクトファイルやライブラリを結合し、実行可能なプログラムを生成するツールです。Goのツールチェインの一部として機能します。
*   **Assembler (アセンブラ)**: アセンブリ言語で書かれたコードを機械語に変換するツールです。Goのコンパイラは、必要に応じてアセンブリコードを生成し、アセンブラがそれを処理します。
*   **Relocation (リロケーション)**: リンカがプログラム内のアドレス参照を解決するプロセスです。コンパイル時には、コード内の変数や関数の正確なメモリ位置は不明なため、プレースホルダーが使用されます。リンカは、これらのプレースホルダーを実行時の正確なアドレスに置き換えます。
*   **GOT (Global Offset Table)**: 共有ライブラリを使用するプログラムで、グローバル変数や関数のアドレスを間接的に参照するために使用されるテーブルです。これにより、共有ライブラリがメモリ上のどこにロードされても、プログラムは正しくそれらを参照できます。
*   **Dual-stack UDP Listener**: ネットワークプログラミングにおいて、単一のソケットでIPv4とIPv6の両方からの接続をリッスンできる機能です。
*   **`testing.Short()`**: Goのテストフレームワークで提供される関数です。`go test -short`フラグが指定された場合に`true`を返します。これにより、開発者は時間のかかるテストをスキップし、より迅速なテスト実行を行うことができます。
*   **`tinyalloc`**: Goランタイムのメモリ割り当て戦略の一つで、非常に小さなオブジェクト（例えば、ポインタを含まない数バイトの構造体）を効率的に割り当てるための最適化です。これらの小さなオブジェクトは、通常のヒープ割り当てとは異なる方法で管理されることがあります。

## 技術的詳細

このコミットは、主に以下の3つの領域で技術的な変更を加えています。

1.  **`src/net/unicast_posix_test.go` におけるテストの調整**:
    `TestDualStackUDPListener`テストに`t.Skip("skipping in -short mode, see issue 5001")`が追加されました。これは、このテストが実行に時間がかかる、または特定の環境で不安定である可能性を示唆しています。`go test -short`フラグが使用された際にこのテストをスキップすることで、開発サイクルを高速化し、CI/CDパイプラインでのテストの信頼性を向上させることが目的です。これはテスト自体の修正ではなく、テストの実行挙動の調整です。

2.  **`src/runtime/malloc.go` および `src/runtime/mfinal_test.go` におけるファイナライザの改善**:
    この変更は、Goのファイナライザの挙動に関する重要な修正を含んでいます。
    *   **ゼロサイズオブジェクトのファイナライザ**: 以前の`runtime.SetFinalizer`は、サイズがゼロのオブジェクトに対してファイナライザを設定しないという実装上の詳細がありました。これは、すべてのゼロサイズオブジェクトが`&runtime·zerobase`という単一のグローバルなゼロページを指していたためです。このコミットでは、この明示的なチェックが削除され、`findObject`関数が`zerobase`のようなヒープ割り当てではないオブジェクトに対して`nil`を返すことに依存するようになりました。これにより、`SetFinalizer`は、オブジェクトがヒープに割り当てられた有効なオブジェクトであるかどうかをより正確に判断できるようになります。
    *   **リンカ割り当てオブジェクトのファイナライザ**: 最も重要な変更は、`runtime.SetFinalizer`がパッケージレベルの変数（グローバル変数）の初期化子で割り当てられたオブジェクトに対してファイナライザを設定しようとした際に発生するパニック（`gothrow`）を防ぐためのものです。これらのオブジェクトはヒープに割り当てられるのではなく、リンカによって静的に割り当てられます。新しいコードでは、オブジェクトのアドレスが`noptrdata`（ポインタを含まないデータセグメント）と`enoptrbss`（ポインタを含まないBSSセグメントの終わり）の間の範囲にあるかどうかをチェックします。この範囲にある場合、それはリンカによって割り当てられたオブジェクトであると判断し、ファイナライザの設定をスキップします。これにより、`SetFinalizer`がヒープ以外のメモリ領域を誤って操作しようとするのを防ぎ、プログラムの安定性が向上します。
    *   **`mfinal_test.go`におけるテストの改善**: `TestFinalizerType`テストが修正され、ファイナライザが確実に実行されるように、`new(T)`のような構造体（ポインタを含む）を割り当てるようになりました。これは、`tinyalloc`のような最適化によって非常に小さなオブジェクトがヒープに割り当てられず、ファイナライザが期待通りに実行されない可能性があったためです。ポインタを含む構造体を割り当てることで、オブジェクトが確実にヒープに割り当てられ、ガベージコレクタによって追跡され、ファイナライザが実行されることを保証します。

3.  **`src/cmd/8l/asm.c` におけるx86リンカのリロケーション修正**:
    この変更は、x86アーキテクチャ（特に32ビット）向けのGoリンカ（`8l`）における`R_386_GOT32`リロケーションの処理を改善するものです。
    *   `R_386_GOT32`は、グローバルオフセットテーブル（GOT）を介してシンボルを参照するためのリロケーションタイプです。通常、これは共有ライブラリの動的シンボルに使用されます。
    *   この修正は、非動的シンボル（つまり、GOTを介して間接的に参照する必要がないシンボル）に対して`R_386_GOT32`リロケーションが発生した場合の挙動を改善します。
    *   具体的には、`MOVL`命令（メモリからレジスタへの移動）がGOTエントリを参照している場合、それを`LEAL`命令（アドレスをレジスタにロード）に変更し、リロケーションタイプを`R_GOTOFF`（GOTからのオフセット）に変換します。これにより、GOTを介した不要な間接参照を避け、シンボル自体のアドレスを直接ロードできるようになります。
    *   同様に、`PUSHL`命令（スタックへのプッシュ）がGOTエントリを参照している場合、それをシンボル自体をプッシュするように変更し、リロケーションタイプを`R_ADDR`（絶対アドレス）に変換します。命令の長さを維持するために、`SS`プレフィックス（セグメントオーバーライド）が使用されています。
    *   この修正は、リンカが生成するコードの効率性や正確性を向上させ、特に静的リンクされたプログラムにおいて、シンボル参照がより直接的になるようにします。

## コアとなるコードの変更箇所

*   **`src/cmd/8l/asm.c`**:
    *   `adddynrel`関数内で、`R_386_GOT32`リロケーションが非動的シンボルに対して適用される場合の処理ロジックが変更されました。
    *   `MOVL`命令（`0x8b`）と`PUSHL`命令（`0xff 0xb3`）のパターンを検出し、それぞれ`LEAL`（`0x8d`）と`PUSHL`（`0x36 0x68`）に変換し、リロケーションタイプも変更しています。
*   **`src/net/unicast_posix_test.go`**:
    *   `TestDualStackUDPListener`関数の冒頭に`if testing.Short() { t.Skip(...) }`が追加されました。
*   **`src/runtime/malloc.go`**:
    *   `SetFinalizer`関数内で、ゼロサイズオブジェクトのチェック（`ot.elem.size == 0`）が`e.data == unsafe.Pointer(&zerobase)`に変更されました。
    *   `base == nil`の場合の処理に、リンカ割り当てオブジェクト（`noptrdata`から`enoptrbss`の範囲）を検出してファイナライザ設定をスキップするロジックが追加されました。
    *   `noptrdata`と`enoptrbss`というリンカ提供のグローバル変数が宣言されました。
*   **`src/runtime/mfinal_test.go`**:
    *   `TestFinalizerType`テスト内で、`v := new(int)`の代わりに`v := &new(T).v`という形で、ポインタを含む構造体`T`を介して`int`を割り当てるように変更されました。

## コアとなるコードの解説

*   **`src/cmd/8l/asm.c`の変更**:
    この変更は、Goのリンカが生成するアセンブリコードの品質を向上させるものです。特に、x86アーキテクチャにおいて、静的にリンクされるプログラム内でグローバルシンボルを参照する際に、不要な間接参照（GOTを介した参照）を排除し、より直接的で効率的なコードを生成するようにします。これにより、実行時のパフォーマンスがわずかに向上したり、特定のコーナーケースでのリンカの挙動が修正されたりする可能性があります。

*   **`src/net/unicast_posix_test.go`の変更**:
    この変更は、`TestDualStackUDPListener`テストが`go test -short`モードでスキップされるようにすることで、開発者がより迅速にテストを実行できるようにします。これは、テストの実行時間を短縮し、開発のフィードバックループを高速化するための一般的なプラクティスです。テスト自体の機能的な修正ではなく、テストの運用上の改善です。

*   **`src/runtime/malloc.go`の変更**:
    この変更は、Goのファイナライザの堅牢性を大幅に向上させます。
    1.  **ゼロサイズオブジェクトの扱い**: `zerobase`へのポインタを持つゼロサイズオブジェクトに対するファイナライザ設定の誤ったスキップを防ぎ、`findObject`の正確な挙動に依存することで、より一貫したファイナライザの適用を可能にします。
    2.  **リンカ割り当てオブジェクトの保護**: 最も重要なのは、ヒープに割り当てられていないグローバル変数などのリンカ割り当てオブジェクトに対して`SetFinalizer`が誤って呼び出された場合にパニックするのを防ぐことです。`noptrdata`と`enoptrbss`の範囲チェックを導入することで、`SetFinalizer`はヒープオブジェクトにのみ作用するという前提を強化し、ランタイムの安定性を高めます。これは、Goプログラムがより複雑な初期化ロジックを持つ場合に特に重要です。

*   **`src/runtime/mfinal_test.go`の変更**:
    このテストの変更は、`malloc.go`で行われたファイナライザの修正が正しく機能することを検証するために不可欠です。`tinyalloc`のような最適化によってファイナライザが実行されない可能性のあるシナリオを回避するために、ポインタを含む構造体を割り当てることで、テスト対象のオブジェクトが確実にヒープに存在し、ガベージコレクタによって適切に処理され、ファイナライザが期待通りに呼び出されることを保証します。これにより、ファイナライザのテストがより信頼性の高いものになります。

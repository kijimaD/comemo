## 元コミット内容

このコミットは、コミット`3b02c5b1b66df9cdb23d5a3243bb37b2c312ea1b`をリバートするものです。元のコミットは、`lfstackPack`と`lfstackUnpack`という関数を`src/runtime/lfstack.go`という単一のファイルに統合することを目的としていました。これらの関数は、ロックフリースタックの実装において、ポインタとカウンタを`uint64`型の単一の値にパック/アンパックするために使用されます。

## 変更の背景

以前のコミットで`lfstackPack`と`lfstackUnpack`が単一のファイルに統合された際、アドレス空間の利用に関する仮定が導入されました。特に、64ビットシステムにおいて、ポインタのアドレス部分とカウンタ部分を`uint64`に格納するために、アドレス空間の上位ビットが未使用であるという仮定が置かれていました。

しかし、この仮定がSolarisオペレーティングシステムでは当てはまらないことが判明しました。Solarisは、アドレス空間の上位17ビットを使用することがあり、この領域にポインタ情報が格納されると、統合された`lfstackPack`/`lfstackUnpack`関数が正しく動作せず、システムが破損する原因となりました。

この問題を解決するため、統合された実装を元に戻し、アーキテクチャやOSに特化した`lfstackPack`/`lfstackUnpack`の実装を復活させる必要がありました。これにより、各環境の特定のアドレス空間の制約に合わせた正しいパック/アンパック処理が可能になります。

## 前提知識の解説

### ロックフリースタック (Lock-Free Stack)
ロックフリーデータ構造は、複数のスレッドが同時にアクセスしても、ロック（ミューテックスなど）を使用せずに正しく動作するデータ構造です。これにより、ロックの競合によるパフォーマンスの低下やデッドロックのリスクを回避できます。Goのランタイムでは、ガベージコレクションやスケジューラなど、並行性の高い処理でロックフリーデータ構造が活用されます。

ロックフリースタックの一般的な実装では、スタックの`head`ポインタをアトミックに更新します。この際、ABA問題（Compare-And-Swap (CAS) 操作において、値がAからBに変わり、再びAに戻った場合にCASが成功してしまう問題）を避けるために、ポインタだけでなく、操作の回数を示すカウンタ（バージョン番号）も一緒にアトミックに更新することが一般的です。

### ポインタとカウンタのパッキング (Pointer and Counter Packing)
64ビットシステムでは、ポインタは通常64ビットの値を持ちます。しかし、多くの場合、実際に使用される仮想アドレス空間は64ビット全体ではなく、例えば48ビットや52ビットに制限されています。この未使用のビット領域を利用して、ポインタとカウンタを`uint64`型の単一の値にパックし、アトミックなCAS操作で両方を一度に更新することができます。

*   **`lfstackPack`**: `lfnode`（スタックのノード）へのポインタとカウンタ（`cnt`）を`uint64`型の単一の値に結合（パック）する関数。
*   **`lfstackUnpack`**: パックされた`uint64`値から`lfnode`ポインタを抽出（アンパック）する関数。

### アドレス空間 (Address Space)
オペレーティングシステムは、各プロセスに仮想アドレス空間を提供します。64ビットシステムでは理論上2^64バイトのアドレス指定が可能ですが、ハードウェアやOSの制約により、実際に使用できる仮想アドレスの範囲はこれよりも狭いことがほとんどです。例えば、x86-64アーキテクチャでは通常48ビットの仮想アドレスが使用され、上位ビットは符号拡張されます。

このコミットの背景にある問題は、Solarisが特定のアドレス空間の上位ビットを実際に使用しているという事実と、Goランタイムがそのビットが未使用であると仮定したことの間の不一致です。

### ビルドタグ (`+build`)
Goのビルドシステムでは、ファイルの先頭に`+build`ディレクティブを記述することで、特定の環境（OS、アーキテクチャなど）でのみそのファイルをコンパイルするように指定できます。例えば、`+build 386 arm nacl`は、32ビットアーキテクチャ（x86、ARM、Native Client）でのみこのファイルをビルドすることを意味します。これにより、アーキテクチャ固有のコードを適切に分離し、クロスプラットフォーム対応を実現します。

## 技術的詳細

このリバートの技術的な核心は、`lfstackPack`と`lfstackUnpack`関数が、異なるアーキテクチャやOSのアドレス空間の特性に依存するという点です。

元の統合された実装では、`addrBits`という定数（デフォルトは48）と`cntBits`という定数に基づいてポインタとカウンタをパックしていました。特にAMD64では、仮想アドレスが48ビットで、上位ビットが符号拡張されることを利用し、ポインタを左に16ビットシフトしてカウンタのためのスペースを確保していました。また、ポインタがアラインされていることを利用して、下位3ビットもカウンタに利用していました。

しかし、Solaris環境では、アドレス空間の上位17ビットが実際に使用されることがあり、この仮定が破綻しました。具体的には、統合されたコードがアドレスの上位ビットを切り捨てたり、カウンタとして利用したりすることで、Solarisが使用する有効なアドレス情報が失われ、不正なポインタが生成される可能性がありました。

リバートにより、以下のアーキテクチャ固有のファイルが復活しました。

1.  **`src/runtime/lfstack_32bit.go`**:
    *   `+build 386 arm nacl`タグにより、32ビットシステムでのみコンパイルされます。
    *   32ビットシステムではポインタが32ビット、カウンタが32ビットとして`uint64`にパックされます。
    *   `uint64(uintptr(unsafe.Pointer(node)))<<32 | uint64(cnt)`: ポインタを上位32ビットに、カウンタを下位32ビットに格納します。
    *   `(*lfnode)(unsafe.Pointer(uintptr(val >> 32)))`: 上位32ビットからポインタを抽出します。

2.  **`src/runtime/lfstack_64bit.go`**:
    *   `+build arm64 mips64 mips64le ppc64 ppc64le`タグにより、特定の64ビットARM、MIPS、PowerPCアーキテクチャでのみコンパイルされます。
    *   `addrBits = 48`、`cntBits = 64 - addrBits + 3`（つまり`cntBits = 19`）と定義されています。
    *   `uint64(uintptr(unsafe.Pointer(node)))<<(64-addrBits) | uint64(cnt&(1<<cntBits-1))`: ポインタを上位ビットに、カウンタを下位`cntBits`に格納します。
    *   `(*lfnode)(unsafe.Pointer(uintptr(val >> cntBits << 3)))`: パックされた値からポインタを抽出します。ここでは、カウンタ部分をシフトで取り除き、さらにポインタのアラインメントを考慮して3ビットシフトしています。

3.  **`src/runtime/lfstack_amd64.go`**:
    *   `+build amd64`タグにより、AMD64アーキテクチャでのみコンパイルされます。
    *   `uint64(uintptr(unsafe.Pointer(node)))<<16 | uint64(cnt&(1<<19-1))`: AMD64の特性（48ビット仮想アドレス、上位16ビット符号拡張）を利用し、ポインタを左に16ビットシフトしてカウンタのためのスペースを確保します。カウンタは19ビットを使用します。
    *   `(*lfnode)(unsafe.Pointer(uintptr(int64(val) >> 19 << 3)))`: パックされた値からポインタを抽出します。符号拡張されたアドレスを正しく扱うために`int64`にキャストし、カウンタ部分をシフトで取り除き、アラインメントを考慮して3ビットシフトしています。

この分割により、各アーキテクチャのメモリマッピングとアドレス空間の利用方法に合わせた最適なパック/アンパック戦略が適用され、Solarisのような特殊な環境でも正しく動作するようになります。

## コアとなるコードの変更箇所

### `src/runtime/lfstack.go`

-   `lfstackPack`関数と`lfstackUnpack`関数が削除されました。これらの関数は、以前のコミットでこのファイルに統合されていましたが、リバートにより削除され、アーキテクチャ固有のファイルにその実装が移されました。

### `src/runtime/lfstack_32bit.go` (新規追加)

```go
// +build 386 arm nacl

package runtime

import "unsafe"

// On 32-bit systems, the stored uint64 has a 32-bit pointer and 32-bit count.

func lfstackPack(node *lfnode, cnt uintptr) uint64 {
	return uint64(uintptr(unsafe.Pointer(node)))<<32 | uint64(cnt)
}

func lfstackUnpack(val uint64) *lfnode {
	return (*lfnode)(unsafe.Pointer(uintptr(val >> 32)))
}
```

### `src/runtime/lfstack_64bit.go` (新規追加)

```go
// +build arm64 mips64 mips64le ppc64 ppc64le

package runtime

import "unsafe"

// On ppc64, Linux limits the user address space to 46 bits (see
// TASK_SIZE_USER64 in the Linux kernel).  This has grown over time,
// so here we allow 48 bit addresses.
//
// On mips64, Linux limits the user address space to 40 bits (see
// TASK_SIZE64 in the Linux kernel).  This has grown over time,
// so here we allow 48 bit addresses.
//
// In addition to the 16 bits taken from the top, we can take 3 from the
// bottom, because node must be pointer-aligned, giving a total of 19 bits
// of count.
const (
	addrBits = 48
	cntBits  = 64 - addrBits + 3
)

func lfstackPack(node *lfnode, cnt uintptr) uint64 {
	return uint64(uintptr(unsafe.Pointer(node)))<<(64-addrBits) | uint64(cnt&(1<<cntBits-1))
}

func lfstackUnpack(val uint64) *lfnode {
	return (*lfnode)(unsafe.Pointer(uintptr(val >> cntBits << 3)))
}
```

### `src/runtime/lfstack_amd64.go` (新規追加)

```go
// +build amd64

package runtime

import "unsafe"

// On AMD64, virtual addresses are 48-bit numbers sign extended to 64.
// We shift the address left 16 to eliminate the sign extended part and make
// room in the bottom for the count.
// In addition to the 16 bits taken from the top, we can take 3 from the
// bottom, because node must be pointer-aligned, giving a total of 19 bits
// of count.

func lfstackPack(node *lfnode, cnt uintptr) uint64 {
	return uint64(uintptr(unsafe.Pointer(node)))<<16 | uint64(cnt&(1<<19-1))
}

func lfstackUnpack(val uint64) *lfnode {
	return (*lfnode)(unsafe.Pointer(uintptr(int64(val) >> 19 << 3)))
}
```

## コアとなるコードの解説

このリバートの主要な変更は、`lfstackPack`と`lfstackUnpack`関数の実装を、ターゲットアーキテクチャごとに異なるファイルに分離したことです。これにより、各アーキテクチャのメモリレイアウトとアドレス空間の特性に合わせた最適なビット操作が可能になります。

*   **`lfstack_32bit.go`**: 32ビットシステムでは、ポインタとカウンタがそれぞれ32ビットずつ`uint64`に格納されます。これは最も単純なパッキング方法です。
*   **`lfstack_64bit.go`**: ARM64, MIPS64, PowerPC64などの特定の64ビットアーキテクチャ向けです。これらのアーキテクチャでは、仮想アドレス空間が48ビットに制限されていることを利用し、ポインタを上位48ビットに、カウンタを下位19ビットに格納します。`addrBits`と`cntBits`の定数でこのロジックを制御しています。
*   **`lfstack_amd64.go`**: AMD64アーキテクチャ向けです。AMD64では仮想アドレスが48ビットで、上位ビットが符号拡張されるという特性があります。この実装では、ポインタを左に16ビットシフトして、下位19ビットをカウンタに利用します。アンパック時には、`int64`にキャストして符号拡張を考慮し、正しいポインタを復元します。

これらの変更により、Goランタイムは、異なるプラットフォームのアドレス空間の利用状況に柔軟に対応できるようになり、Solarisのような特定の環境で発生していた問題が解決されました。これは、低レベルのシステムプログラミングにおいて、アーキテクチャ固有の細かな違いを考慮することの重要性を示す良い例です。

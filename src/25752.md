## 元コミット内容

このコミットは、`runtime/pprof`パッケージに、CPUプロファイルにスタックバリアが記録されないことを確認するテストを追加します。このテストは、スタックバリアの負荷が高い状態でCPUプロファイリングを実行し、以下の2点を確認します。

1.  Goランタイムがクラッシュしないこと。
2.  `stackBarrier`関数自体がプロファイルに現れないこと。

以前は、`gentraceback`関数が`stackBarrier`の途中で開始される問題が修正されるまで、2番目の条件が満たされないことがよくありました。

## 変更の背景

Goのランタイムは、ガベージコレクション（GC）の際にスタックの走査を効率的に行うために「スタックバリア」というメカニズムを使用します。これは、GCが実行されている間にゴルーチンがスタックを操作するのを防ぐためのものです。しかし、CPUプロファイリングは実行中のコードのサンプルを収集するため、これらの内部的なランタイムメカニズムがプロファイルに現れると、ユーザーはアプリケーションの実際のパフォーマンスボトルネックを特定するのが難しくなります。

特に、`gentraceback`という関数（スタックトレースを生成するために使用される）が`stackBarrier`の実行中にサンプルを採取してしまうと、プロファイルに`stackBarrier`が不必要に表示される問題がありました。これは、プロファイルがアプリケーションコードではなく、ランタイムの内部動作に「汚染」されることを意味します。

このコミットは、この問題が修正されたことを検証するためのテストを追加することで、将来的に同様の回帰が発生しないようにすることを目的としています。つまり、`stackBarrier`がプロファイルに現れないことが、ランタイムの正しい動作の一部として保証されるべきであるという考えに基づいています。

## 前提知識の解説

### Goのガベージコレクション (GC) とスタックバリア

Goのガベージコレクタは、並行（concurrent）かつ低遅延（low-latency）で動作するように設計されています。GCサイクル中、コレクタは到達可能なオブジェクトを特定するために、実行中のゴルーチンのスタックを走査する必要があります。

「スタックバリア」は、このスタック走査の整合性を保つためのメカニズムの一つです。GCがスタックを走査している間に、ゴルーチンがスタックを拡張したり縮小したりすると、コレクタが誤った情報を読み取ったり、クラッシュしたりする可能性があります。スタックバリアは、このような状況を防ぐために、特定のスタック操作の前後でGCの協調ポイント（safepoint）を挿入する役割を果たします。これにより、GCは安全にスタックを走査できます。

### CPUプロファイリングと`pprof`

Goの`pprof`ツールは、プログラムのCPU使用率、メモリ割り当て、ゴルーチン、ブロックなどのプロファイルデータを収集・可視化するための強力なツールです。CPUプロファイリングは、プログラムの実行中に定期的にサンプルを採取し、その時点でどの関数が実行されていたかを記録することで機能します。これにより、プログラムのどの部分が最も多くのCPU時間を消費しているかを特定し、パフォーマンスのボトルネックを特定するのに役立ちます。

### `gentraceback`関数

`gentraceback`はGoランタイム内部の関数で、スタックトレースを生成するために使用されます。プロファイリングツールがスタックサンプルを採取する際、この`gentraceback`が呼び出され、現在のゴルーチンのコールスタックを遡って関数名を特定します。もし`gentraceback`がランタイムの内部的な、ユーザーには見えないような処理（例: `stackBarrier`）の途中でサンプルを採取してしまうと、その内部処理がプロファイルに現れてしまい、プロファイルの意図しないノイズとなります。

## 技術的詳細

このコミットの核心は、`stackBarrier`がCPUプロファイルに現れないことを検証する新しいテストケース`TestStackBarrierProfiling`の追加です。

1.  **`GODEBUG=gcstackbarrierall=1`と`GOGC=1`**:
    *   `GODEBUG=gcstackbarrierall=1`は、すべての関数呼び出しでスタックバリアを強制的に有効にするデバッグフラグです。これにより、スタックバリアの発生頻度を最大化し、テストの信頼性を高めます。
    *   `GOGC=1`は、ガベージコレクションの頻度を非常に高く設定します（ヒープサイズが1%増加するたびにGCが実行される）。これにより、GCが頻繁に発生し、それに伴うスタックバリアの操作も頻繁に行われるようになります。
    *   これらの環境変数を設定してテストをサブプロセスとして再実行することで、スタックバリアが極めて高負荷な状況下でのプロファイリングをシミュレートします。

2.  **`testCPUProfile`の変更**:
    *   既存の`testCPUProfile`関数に、プロファイル結果をチェックするロジックが追加されました。
    *   プロファイル内の各フレーム（関数）の名前を走査し、もし関数名に`"stackBarrier"`が含まれていたら、`t.Fatalf("profile includes stackBarrier")`を呼び出してテストを失敗させます。これは、`stackBarrier`がプロファイルに現れるべきではないという前提に基づいています。

3.  **`TestStackBarrierProfiling`のロジック**:
    *   このテストは、`testCPUProfile`を呼び出し、その中で`deepStack(1000)`を繰り返し実行します。
    *   `deepStack`関数は、再帰的に1000層の深いスタックを生成し、各呼び出しで`make([]byte, 1024)`によってヒープメモリを割り当てます。これにより、スタックの拡張とヒープの割り当てが頻繁に行われ、GCとスタックバリアが活発に動作する状況を作り出します。
    *   このループを一定時間（通常5秒、ショートテストでは1秒）実行することで、十分なプロファイルサンプルが収集されることを保証します。

このテストの目的は、`gentraceback`の修正が正しく機能し、ランタイムの内部的なスタックバリア処理がユーザーレベルのプロファイルから適切に隠蔽されていることを確認することです。

```go
func TestStackBarrierProfiling(t *testing.T) {
	if !strings.Contains(os.Getenv("GODEBUG"), "gcstackbarrierall=1") {
		// Re-execute this test with constant GC and stack
		// barriers at every frame.
		cmd := exec.Command(os.Args[0], "-test.run=TestStackBarrierProfiling")
		cmd.Env = append([]string{"GODEBUG=gcstackbarrierall=1", "GOGC=1"}, os.Environ()...)
		if out, err := cmd.CombinedOutput(); err != nil {
			t.Fatalf("subprocess failed with %v:\n%s", err, out)
		}
		return
	}

	testCPUProfile(t, nil, func() {
		// This is long enough that we're likely to get one or
		// two samples in stackBarrier.
		duration := 5 * time.Second
		if testing.Short() {
			duration = 1 * time.Second
		}
		t := time.After(duration)
		for {
			deepStack(1000)
			select {
			case <-t:
				return
			default:
			}
		}
	})
}
```
このテスト関数は、まず環境変数`GODEBUG`に`gcstackbarrierall=1`が含まれているかを確認します。含まれていない場合、テストは自分自身をサブプロセスとして再実行します。この際、`GODEBUG=gcstackbarrierall=1`と`GOGC=1`という環境変数を設定します。これにより、スタックバリアとGCが非常に頻繁に発生する状況を作り出します。

サブプロセスとして実行された場合、`testCPUProfile`関数を呼び出します。この`testCPUProfile`には、無名関数が渡されます。この無名関数は、`deepStack(1000)`を繰り返し呼び出すループを一定時間（5秒またはショートテストの場合は1秒）実行します。

### `deepStack`関数の追加

```go
var x []byte

func deepStack(depth int) int {
	if depth == 0 {
		return 0
	}
	x = make([]byte, 1024)
	return deepStack(depth-1) + 1
}
```
`deepStack`関数は、再帰的に呼び出されることで深いコールスタックを生成します。`depth`が0になるまで再帰を続け、各呼び出しで`make([]byte, 1024)`によって1KBのバイトスライスを割り当てます。このメモリ割り当てはヒープ上で行われるため、GCをトリガーしやすくなります。深いスタックと頻繁なメモリ割り当ての組み合わせにより、スタックバリアが頻繁に挿入・削除される状況が生まれ、`stackBarrier`がプロファイルに現れる可能性のあるエッジケースを効果的にテストできます。`x`はグローバル変数として宣言されており、`make`で割り当てられたメモリがすぐにGCされないように（少なくとも関数スコープを抜けても参照が残るように）しています。

このテストの目的は、`gentraceback`の修正が正しく機能し、ランタイムの内部的なスタックバリア処理がユーザーレベルのプロファイルから適切に隠蔽されていることを確認することです。

### `TestStackBarrierProfiling`関数の追加

```go
func TestStackBarrierProfiling(t *testing.T) {
	if !strings.Contains(os.Getenv("GODEBUG"), "gcstackbarrierall=1") {
		// Re-execute this test with constant GC and stack
		// barriers at every frame.
		cmd := exec.Command(os.Args[0], "-test.run=TestStackBarrierProfiling")
		cmd.Env = append([]string{"GODEBUG=gcstackbarrierall=1", "GOGC=1"}, os.Environ()...)
		if out, err := cmd.CombinedOutput(); err != nil {
			t.Fatalf("subprocess failed with %v:\n%s", err, out)
		}
		return
	}

	testCPUProfile(t, nil, func() {
		// This is long enough that we're likely to get one or
		// two samples in stackBarrier.
		duration := 5 * time.Second
		if testing.Short() {
			duration = 1 * time.Second
		}
		t := time.After(duration)
		for {
			deepStack(1000)
			select {
			case <-t:
				return
			default:
			}
		}
	})
}
```
このテスト関数は、まず環境変数`GODEBUG`に`gcstackbarrierall=1`が含まれているかを確認します。含まれていない場合、テストは自分自身をサブプロセスとして再実行します。この際、`GODEBUG=gcstackbarrierall=1`と`GOGC=1`という環境変数を設定します。これにより、スタックバリアとGCが非常に頻繁に発生する状況を作り出します。

サブプロセスとして実行された場合、`testCPUProfile`関数を呼び出します。この`testCPUProfile`には、無名関数が渡されます。この無名関数は、無名関数は、`deepStack(1000)`を繰り返し呼び出すループを一定時間（5秒またはショートテストの場合は1秒）実行します。

### `deepStack`関数の追加

```go
var x []byte

func deepStack(depth int) int {
	if depth == 0 {
		return 0
	}
	x = make([]byte, 1024)
	return deepStack(depth-1) + 1
}
```
`deepStack`関数は、再帰的に呼び出されることで深いコールスタックを生成します。`depth`が0になるまで再帰を続け、各呼び出しで`make([]byte, 1024)`によって1KBのバイトスライスを割り当てます。このメモリ割り当てはヒープ上で行われるため、GCをトリガーしやすくなります。深いスタックと頻繁なメモリ割り当ての組み合わせにより、スタックバリアが頻繁に挿入・削除される状況が生まれ、`stackBarrier`がプロファイルに現れる可能性のあるエッジケースを効果的にテストできます。`x`はグローバル変数として宣言されており、`make`で割り当てられたメモリがすぐにGCされないように（少なくとも関数スコープを抜けても参照が残るように）しています。

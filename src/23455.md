# [インデックス 23455] ファイルの概要

このコミットは、Goコンパイラの内部構造における重要なリファクタリングの一環として、`gc` パッケージ外での `gc.Mp*` 関数および型の使用を排除することを目的としています。具体的には、Goコンパイラの抽象構文木（AST）ノードを表す `gc.Node` 型が、定数値を扱うための新しいメソッド (`Int()`, `SetInt()`, `SetBigInt()`) を持つように変更され、これまで直接 `gc.Mpgetfix` や `gc.Mpmovecfix` といった任意精度演算ライブラリの関数を呼び出していた箇所が、これらの新しい `Node` メソッドに置き換えられています。これにより、`Mp*` 関連の内部実装が `gc` パッケージ内にカプセル化され、コンパイラのコードベースの保守性と一貫性が向上します。この変更は、Go 1.6サイクルで `Mp*` 関数と型が非公開化（unexport）されるための準備作業であり、機能的な変更は含まれていません。

## 変更の背景

このコミットの主な背景は、Goコンパイラの内部コードベースのクリーンアップとモジュール化の推進にあります。`gc.Mp*` というプレフィックスを持つ関数や型は、Goコンパイラが任意精度の数値（多倍長整数や浮動小数点数）を扱うための内部ライブラリ (`math/big` パッケージのコンパイラ内部版) に関連するものでした。これらは元々 `gc` パッケージ内で定義されていましたが、コンパイラの様々なバックエンド（`5g`, `6g`, `7g`, `8g`, `9g` など、それぞれ異なるアーキテクチャ向けのコード生成器）から直接参照されていました。

このような直接参照は、`gc` パッケージの内部実装が外部に漏れ出している状態であり、将来的な変更やリファクタリングを困難にする可能性がありました。特に、Go 1.6サイクルでは、これらの `Mp*` 関数と型を `gc` パッケージの外部からアクセスできないように「非公開化 (unexport)」する計画がありました。このコミットは、その非公開化に先立って、`gc` パッケージ外のコードが `Mp*` 関数に直接依存しないようにするための準備作業です。

具体的には、`gc.Node` 型（コンパイラのASTノード）に定数値を扱うための新しいメソッド (`Int()`, `SetInt()`, `SetBigInt()`) を導入することで、各バックエンドは `Node` オブジェクトを通じて定数値を操作できるようになります。これにより、`Mp*` の詳細な実装が `Node` メソッドの内部に隠蔽され、コンパイラ全体のアーキテクチャがよりクリーンで保守しやすくなります。機能的な変更は一切なく、既存の動作を維持しつつ、内部的な依存関係を整理することが目的です。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造と概念に関する知識が必要です。

1.  **Goコンパイラの構造**:
    *   Goコンパイラは、フロントエンドとバックエンドに大別されます。
    *   **フロントエンド**: ソースコードのパース、抽象構文木 (AST) の構築、型チェック、中間表現 (IR) への変換など、言語に依存しない処理を担当します。`cmd/internal/gc` パッケージがこの役割を担っています。
    *   **バックエンド**: 中間表現を特定のCPUアーキテクチャ（例: x86-64, ARM, PowerPC）向けの機械語に変換するコード生成を担当します。`cmd/5g` (ARM), `cmd/6g` (x86-64), `cmd/7g` (ARM64), `cmd/8g` (x86), `cmd/9g` (PowerPC64) などがこれに該当します。
    *   このコミットで変更されているファイルのパス (`src/cmd/5g/cgen64.go`, `src/cmd/internal/gc/const.go` など) から、フロントエンドと複数のバックエンドにまたがる変更であることがわかります。

2.  **`gc.Node` 型**:
    *   `gc.Node` は、Goコンパイラのフロントエンド (`cmd/internal/gc`) で使用される抽象構文木 (AST) の基本的な構成要素です。プログラム内のあらゆる要素（変数、定数、関数呼び出し、演算子など）が `Node` として表現されます。
    *   定数リテラル（例: `123`, `3.14`, `"hello"`) も `Node` として表現され、その値は `Node.Val` フィールドに格納されます。

3.  **定数表現と `gc.Mp*` 関数**:
    *   Go言語は、任意精度の定数をサポートしています。例えば、`1 << 100` のような非常に大きな整数リテラルも、オーバーフローせずに正確に表現できます。
    *   この任意精度を扱うために、Goコンパイラは内部的に多倍長演算ライブラリを使用しています。これが `gc.Mp*` と呼ばれる関数群です。`Mp` は "multi-precision" の略です。
    *   `gc.Mpgetfix(n.Val.U.Xval)`: `Node` の値 (`n.Val.U.Xval`) から、固定小数点数（整数）の値を取得する関数です。`Xval` は `Mpint` 型（多倍長整数）のインスタンスを指します。
    *   `gc.Mpmovecfix(n.Val.U.Xval, i)`: `Node` の値 (`n.Val.U.Xval`) に、指定された整数 `i` を設定する関数です。
    *   これらの関数は、`gc` パッケージの内部実装の一部であり、本来は `gc` パッケージ外から直接アクセスされるべきではありませんでした。

4.  **`cmd/internal/gc/big` パッケージ**:
    *   Go標準ライブラリには `math/big` パッケージがあり、任意精度の整数 (`big.Int`) や浮動小数点数 (`big.Float`) を提供します。
    *   `cmd/internal/gc/big` は、コンパイラ内部で使われる `math/big` の軽量版またはカスタマイズ版と考えることができます。このコミットでは、この `big` パッケージが `gsubr.go` ファイルなどでインポートされるようになっています。

5.  **Goにおける識別子の可視性 (Export/Unexport)**:
    *   Goでは、識別子（変数、関数、型など）の名前が大文字で始まる場合、その識別子はパッケージ外からアクセス可能（エクスポートされる）になります。小文字で始まる場合、パッケージ内でのみアクセス可能（非公開、アンエクスポートされる）です。
    *   このコミットの目的は、`gc.Mp*` 関数と型を非公開化し、`gc` パッケージの内部実装としてカプセル化することです。

## 技術的詳細

このコミットの技術的な核心は、`gc.Node` 型に定数値を扱うための新しいメソッドを導入し、既存の `gc.Mp*` 関数への直接的な依存を排除することです。

1.  **`gc.Node` メソッドの導入 (`src/cmd/internal/gc/const.go`)**:
    *   `src/cmd/internal/gc/const.go` ファイルに、以下の3つの新しいメソッドが `gc.Node` 型に追加されました。
        *   `func (n *Node) Int() int64`: `Node` が表す整数定数の値を `int64` 型で返します。内部的には `gc.Mpgetfix(n.Val.U.Xval)` を呼び出します。これにより、`Node` の利用者は `Mp*` の詳細を知る必要がなくなります。
        *   `func (n *Node) SetInt(i int64)`: `Node` が表す整数定数の値を `int64` 型の `i` に設定します。内部的には `gc.Mpmovecfix(n.Val.U.Xval, i)` を呼び出します。
        *   `func (n *Node) SetBigInt(x *big.Int)`: `Node` が表す整数定数の値を `cmd/internal/gc/big.Int` 型の `x` に設定します。これは、より大きな任意精度整数を扱うための新しいインターフェースです。内部的には `n.Val.U.Xval.Val.Set(x)` を呼び出し、`Node` の内部表現に直接 `big.Int` の値を設定します。

2.  **`gc.Mp*` 関数呼び出しの置き換え**:
    *   コンパイラの各バックエンド (`5g`, `6g`, `7g`, `8g`, `9g`) の `cgen64.go`, `ggen.go`, `gsubr.go` ファイル内で、`gc.Mpgetfix(n.Val.U.Xval)` のような直接的な `Mp` 関数呼び出しが、新しく導入された `n.Int()` メソッドに置き換えられています。
    *   同様に、`gc.Mpmovecfix(ncon_n.Val.U.Xval, int64(i))` のような値設定の呼び出しは、`ncon_n.SetInt(int64(i))` に置き換えられています。

3.  **`bignodes()` 関数のリファクタリング**:
    *   `src/cmd/6g/gsubr.go`, `src/cmd/8g/gsubr.go`, `src/cmd/9g/gsubr.go` などにある `bignodes()` 関数は、特定の大きな定数（例: 2^63, 2^64）を表す `Node` を初期化する役割を担っています。
    *   このコミットでは、これらの `bignodes()` 関数もリファクタリングされ、`gc.Mp*` 関数への直接的な依存を排除しています。
    *   以前は `gc.Mpshiftfix` や `gc.Mpmovefixflt` を直接使用していましたが、変更後は `cmd/internal/gc/big` パッケージの `big.Int` 型を導入し、`big.Int` を使って値を計算した後、`Node.SetBigInt()` や `gc.Convconst()` を利用して `Node` に値を設定するように変更されています。これにより、`Mp*` の内部実装が `gc` パッケージ内に完全にカプセル化されます。
    *   特に、`big.Int` を使用して `1 << 63` や `1 << 64` を計算し、それを `Node` に設定するロジックが導入されています。

4.  **`cmd/internal/gc/big` のインポート**:
    *   `gsubr.go` ファイル群で、`"cmd/internal/gc/big"` パッケージが新しくインポートされています。これは、リファクタリングされた `bignodes()` 関数内で `big.Int` 型を使用するためです。

これらの変更により、`gc` パッケージの外部にあるコードは、`Node` オブジェクトのメソッドを通じて定数値を抽象的に扱うことができるようになり、`Mp*` の具体的な実装詳細から切り離されます。これは、コンパイラの内部アーキテクチャを改善し、将来的な変更に対する柔軟性を高めるための重要なステップです。

## コアとなるコードの解説

上記のコード変更は、Goコンパイラの定数処理における責任の分離とカプセル化を明確に示しています。

1.  **`gc.Node` メソッドの導入**:
    *   `Int()`, `SetInt()`, `SetBigInt()` メソッドが `gc.Node` 型に追加されたことで、`Node` オブジェクト自体が自身の定数値を管理するインターフェースを持つようになりました。
    *   これにより、コンパイラの他の部分（特にバックエンドのコード生成器）は、定数値を扱う際に `gc.Mpgetfix` や `gc.Mpmovecfix` といった低レベルな `Mp*` 関数を直接呼び出す必要がなくなります。代わりに `node.Int()` や `node.SetInt(value)` のように、よりオブジェクト指向的な方法で定数にアクセス・設定できるようになります。
    *   `SetBigInt()` の導入は、`cmd/internal/gc/big` パッケージの `big.Int` 型を直接 `Node` の内部値に設定できるようになったことを意味し、任意精度整数の扱いがより直接的かつ効率的になります。

2.  **`gc.Mpgetfix` 呼び出しの置き換え**:
    *   `v := uint64(gc.Mpgetfix(r.Val.U.Xval))` が `v := uint64(r.Int())` に変更された箇所は、まさにこのカプセル化の恩恵を示しています。以前は `Node` の内部構造 (`Val.U.Xval`) に直接アクセスし、`gc` パッケージの内部関数 (`Mpgetfix`) を呼び出していましたが、変更後は `r` (つまり `gc.Node` のインスタンス) の `Int()` メソッドを呼び出すだけで値を取得できるようになりました。これにより、コードの可読性が向上し、`gc.Node` の内部実装が変更されても、`Int()` メソッドのインターフェースが変わらなければ、呼び出し側のコードを変更する必要がなくなります。

3.  **`bignodes()` 関数のリファクタリング**:
    *   `bignodes()` 関数は、コンパイラが内部的に使用する特定の大きな定数（例: 2^63）を初期化します。以前は `gc.Mpshiftfix` や `gc.Mpmovefixflt` といった `Mp*` 関数を直接使ってこれらの定数を構築していました。
    *   リファクタリング後、`cmd/internal/gc/big` パッケージの `big.Int` 型を導入し、`i.SetInt64(1)`, `i.Lsh(&i, 63)` のように `big.Int` のメソッドを使って任意精度整数を計算しています。そして、その結果を `bigi.SetBigInt(&i)` や `gc.Convconst(&bigf, gc.Types[gc.TFLOAT64], &bigi.Val)` を通じて `gc.Node` に設定しています。
    *   この変更は、`Mp*` の詳細な演算ロジックを `bignodes()` から排除し、`Node` メソッドや `big` パッケージの機能に委譲することで、`bignodes()` のコードをより簡潔にし、`Mp*` の非公開化に備えるものです。

全体として、このコミットはGoコンパイラの内部設計を改善し、よりクリーンで保守しやすいコードベースを構築するための重要な一歩と言えます。

```
cmd/5g, etc: prepare to unexport gc.Mp*

Remove all uses of Mp* outside of the gc package.

A subsequent, automated commit in the Go 1.6
cycle will unexport all Mp* functions and types.

No functional changes. Passes toolstash -cmp.

Change-Id: Ie1604cb5b84ffb30b47f4777d4235570f2c62709
Reviewed-on: https://go-review.googlesource.com/9263
Reviewed-by: Russ Cox <rsc@golang.org>
```

## 変更の背景

このコミットの主な背景は、Goコンパイラの内部コードベースのクリーンアップとモジュール化の推進にあります。`gc.Mp*` というプレフィックスを持つ関数や型は、Goコンパイラが任意精度の数値（多倍長整数や浮動小数点数）を扱うための内部ライブラリ (`math/big` パッケージのコンパイラ内部版) に関連するものでした。これらは元々 `gc` パッケージ内で定義されていましたが、コンパイラの様々なバックエンド（`5g`, `6g`, `7g`, `8g`, `9g` など、それぞれ異なるアーキテクチャ向けのコード生成器）から直接参照されていました。

このような直接参照は、`gc` パッケージの内部実装が外部に漏れ出している状態であり、将来的な変更やリファクタリングを困難にする可能性がありました。特に、Go 1.6サイクルでは、これらの `Mp*` 関数と型を `gc` パッケージの外部からアクセスできないように「非公開化 (unexport)」する計画がありました。このコミットは、その非公開化に先立って、`gc` パッケージ外のコードが `Mp*` 関数に直接依存しないようにするための準備作業です。

具体的には、`gc.Node` 型（コンパイラのASTノード）に定数値を扱うための新しいメソッド (`Int()`, `SetInt()`, `SetBigInt()`) を導入することで、各バックエンドは `Node` オブジェクトを通じて定数値を操作できるようになります。これにより、`Mp*` の詳細な実装が `Node` メソッドの内部に隠蔽され、コンパイラ全体のアーキテクチャがよりクリーンで保守しやすくなります。機能的な変更は一切なく、既存の動作を維持しつつ、内部的な依存関係を整理することが目的です。

## 前提知識の解説

このコミットを理解するためには、以下のGoコンパイラの内部構造と概念に関する知識が必要です。

1.  **Goコンパイラの構造**:
    *   Goコンパイラは、フロントエンドとバックエンドに大別されます。
    *   **フロントエンド**: ソースコードのパース、抽象構文木 (AST) の構築、型チェック、中間表現 (IR) への変換など、言語に依存しない処理を担当します。`cmd/internal/gc` パッケージがこの役割を担っています。
    *   **バックエンド**: 中間表現を特定のCPUアーキテクチャ（例: x86-64, ARM, PowerPC）向けの機械語に変換するコード生成を担当します。`cmd/5g` (ARM), `cmd/6g` (x86-64), `cmd/7g` (ARM64), `cmd/8g` (x86), `cmd/9g` (PowerPC64) などがこれに該当します。
    *   このコミットで変更されているファイルのパス (`src/cmd/5g/cgen64.go`, `src/cmd/internal/gc/const.go` など) から、フロントエンドと複数のバックエンドにまたがる変更であることがわかります。

2.  **`gc.Node` 型**:
    *   `gc.Node` は、Goコンパイラのフロントエンド (`cmd/internal/gc`) で使用される抽象構文木 (AST) の基本的な構成要素です。プログラム内のあらゆる要素（変数、定数、関数呼び出し、演算子など）が `Node` として表現されます。
    *   定数リテラル（例: `123`, `3.14`, `"hello"`) も `Node` として表現され、その値は `Node.Val` フィールドに格納されます。

3.  **定数表現と `gc.Mp*` 関数**:
    *   Go言語は、任意精度の定数をサポートしています。例えば、`1 << 100` のような非常に大きな整数リテラルも、オーバーフローせずに正確に表現できます。
    *   この任意精度を扱うために、Goコンパイラは内部的に多倍長演算ライブラリを使用しています。これが `gc.Mp*` と呼ばれる関数群です。`Mp` は "multi-precision" の略です。
    *   `gc.Mpgetfix(n.Val.U.Xval)`: `Node` の値 (`n.Val.U.Xval`) から、固定小数点数（整数）の値を取得する関数です。`Xval` は `Mpint` 型（多倍長整数）のインスタンスを指します。
    *   `gc.Mpmovecfix(n.Val.U.Xval, i)`: `Node` の値 (`n.Val.U.Xval`) に、指定された整数 `i` を設定する関数です。
    *   これらの関数は、`gc` パッケージの内部実装の一部であり、本来は `gc` パッケージ外から直接アクセスされるべきではありませんでした。

4.  **`cmd/internal/gc/big` パッケージ**:
    *   Go標準ライブラリには `math/big` パッケージがあり、任意精度の整数 (`big.Int`) や浮動小数点数 (`big.Float`) を提供します。
    *   `cmd/internal/gc/big` は、コンパイラ内部で使われる `math/big` の軽量版またはカスタマイズ版と考えることができます。このコミットでは、この `big` パッケージが `gsubr.go` ファイルなどでインポートされるようになっています。

5.  **Goにおける識別子の可視性 (Export/Unexport)**:
    *   Goでは、識別子（変数、関数、型など）の名前が大文字で始まる場合、その識別子はパッケージ外からアクセス可能（エクスポートされる）になります。小文字で始まる場合、パッケージ内でのみアクセス可能（非公開、アンエクスポートされる）です。
    *   このコミットの目的は、`gc.Mp*` 関数と型を非公開化し、`gc` パッケージの内部実装としてカプセル化することです。

## 技術的詳細

このコミットの技術的な核心は、`gc.Node` 型に定数値を扱うための新しいメソッドを導入し、既存の `gc.Mp*` 関数への直接的な依存を排除することです。

1.  **`gc.Node` メソッドの導入 (`src/cmd/internal/gc/const.go`)**:
    *   `src/cmd/internal/gc/const.go` ファイルに、以下の3つの新しいメソッドが `gc.Node` 型に追加されました。
        *   `func (n *Node) Int() int64`: `Node` が表す整数定数の値を `int64` 型で返します。内部的には `gc.Mpgetfix(n.Val.U.Xval)` を呼び出します。これにより、`Node` の利用者は `Mp*` の詳細を知る必要がなくなります。
        *   `func (n *Node) SetInt(i int64)`: `Node` が表す整数定数の値を `int64` 型の `i` に設定します。内部的には `gc.Mpmovecfix(n.Val.U.Xval, i)` を呼び出します。
        *   `func (n *Node) SetBigInt(x *big.Int)`: `Node` が表す整数定数の値を `cmd/internal/gc/big.Int` 型の `x` に設定します。これは、より大きな任意精度整数を扱うための新しいインターフェースです。内部的には `n.Val.U.Xval.Val.Set(x)` を呼び出し、`Node` の内部表現に直接 `big.Int` の値を設定します。

2.  **`gc.Mp*` 関数呼び出しの置き換え**:
    *   コンパイラの各バックエンド (`5g`, `6g`, `7g`, `8g`, `9g`) の `cgen64.go`, `ggen.go`, `gsubr.go` ファイル内で、`gc.Mpgetfix(n.Val.U.Xval)` のような直接的な `Mp` 関数呼び出しが、新しく導入された `n.Int()` メソッドに置き換えられています。
    *   同様に、`gc.Mpmovecfix(ncon_n.Val.U.Xval, int64(i))` のような値設定の呼び出しは、`ncon_n.SetInt(int64(i))` に置き換えられています。

3.  **`bignodes()` 関数のリファクタリング**:
    *   `src/cmd/6g/gsubr.go`, `src/cmd/8g/gsubr.go`, `src/cmd/9g/gsubr.go` などにある `bignodes()` 関数は、特定の大きな定数（例: 2^63, 2^64）を表す `Node` を初期化する役割を担っています。
    *   このコミットでは、これらの `bignodes()` 関数もリファクタリングされ、`gc.Mp*` 関数への直接的な依存を排除しています。
    *   以前は `gc.Mpshiftfix` や `gc.Mpmovefixflt` を直接使用していましたが、変更後は `cmd/internal/gc/big` パッケージの `big.Int` 型を導入し、`big.Int` を使って値を計算した後、`Node.SetBigInt()` や `gc.Convconst()` を利用して `Node` に値を設定するように変更されています。これにより、`Mp*` の内部実装が `gc` パッケージ内に完全にカプセル化されます。
    *   特に、`big.Int` を使用して `1 << 63` や `1 << 64` を計算し、それを `Node` に設定するロジックが導入されています。

4.  **`cmd/internal/gc/big` のインポート**:
    *   `gsubr.go` ファイル群で、`"cmd/internal/gc/big"` パッケージが新しくインポートされています。これは、リファクタリングされた `bignodes()` 関数内で `big.Int` 型を使用するためです。

これらの変更により、`gc` パッケージの外部にあるコードは、`Node` オブジェクトのメソッドを通じて定数値を抽象的に扱うことができるようになり、`Mp*` の具体的な実装詳細から切り離されます。これは、コンパイラの内部設計を改善し、将来的な変更に対する柔軟性を高めるための重要なステップです。

    ```go
    // n must be an integer constant.

    	if !Isconst(n, CTINT) {
    		Fatal("Int(%v)", n)
    	}
    	return Mpgetfix(n.Val.U.Xval)
    }

    // SetInt sets n's value to i.
    // n must be an integer constant.
    func (n *Node) SetInt(i int64) {
    ```

## コアとなるコードの解説

上記のコード変更は、Goコンパイラの定数処理における責任の分離とカプセル化を明確に示しています。

1.  **`gc.Node` メソッドの導入**:
    *   `Int()`, `SetInt()`, `SetBigInt()` メソッドが `gc.Node` 型に追加されたことで、`Node` オブジェクト自体が自身の定数値を管理するインターフェースを持つようになりました。
    *   これにより、コンパイラの他の部分（特にバックエンドのコード生成器）は、定数値を扱う際に `gc.Mpgetfix` や `gc.Mpmovecfix` といった低レベルな `Mp*` 関数を直接呼び出す必要がなくなります。代わりに `node.Int()` や `node.SetInt(value)` のように、よりオブジェクト指向的な方法で定数にアクセス・設定できるようになります。
    *   `SetBigInt()` の導入は、`cmd/internal/gc/big` パッケージの `big.Int` 型を直接 `Node` の内部値に設定できるようになったことを意味し、任意精度整数の扱いがより直接的かつ効率的になります。

2.  **`gc.Mpgetfix` 呼び出しの置き換え**:
    *   `v := uint64(gc.Mpgetfix(r.Val.U.Xval))` が `v := uint64(r.Int())` に変更された箇所は、まさにこのカプセル化の恩恵を示しています。以前は `Node` の内部構造 (`Val.U.Xval`) に直接アクセスし、`gc` パッケージの内部関数 (`Mpgetfix`) を呼び出していましたが、変更後は `r` (つまり `gc.Node` のインスタンス) の `Int()` メソッドを呼び出すだけで値を取得できるようになりました。これにより、コードの可読性が向上し、`gc.Node` の内部実装が変更されても、`Int()` メソッドのインターフェースが変わらなければ、呼び出し側のコードを変更する必要がなくなります。

3.  **`bignodes()` 関数のリファクタリング**:
    *   `bignodes()` 関数は、コンパイラが内部的に使用する特定の大きな定数（例: 2^63）を初期化します。以前は `gc.Mpshiftfix` や `gc.Mpmovefixflt` といった `Mp*` 関数を直接使ってこれらの定数を構築していました。
    *   リファクタリング後、`cmd/internal/gc/big` パッケージの `big.Int` 型を導入し、`i.SetInt64(1)`, `i.Lsh(&i, 63)` のように `big.Int` のメソッドを使って任意精度整数を計算しています。そして、その結果を `bigi.SetBigInt(&i)` や `gc.Convconst(&bigf, gc.Types[gc.TFLOAT64], &bigi.Val)` を通じて `gc.Node` に設定しています。
    *   この変更は、`Mp*` の詳細な演算ロジックを `bignodes()` から排除し、`Node` メソッドや `big` パッケージの機能に委譲することで、`bignodes()` のコードをより簡潔にし、`Mp*` の非公開化に備えるものです。

全体として、このコミットはGoコンパイラの内部設計を改善し、よりクリーンで保守しやすいコードベースを構築するための重要な一歩と言えます。

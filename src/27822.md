# [インデックス 27822] ファイルの概要

このコミットは、Go言語の`crypto/x509`パッケージにおいて、自己署名証明書に`AuthorityKeyId`拡張をデフォルトで追加しないように変更するものです。`AuthorityKeyId`は自己署名証明書においては通常不要であり、ファイルサイズを増やす原因となるため、この変更により効率性が向上します。ただし、テンプレートで明示的に設定された場合は引き続き追加されます。

## コミット

crypto/x509: don't add an AuthorityKeyId to self-signed certificates.

The AuthorityKeyId is optional for self-signed certificates, generally
useless, and takes up space. This change causes an AuthorityKeyId not to
be added to self-signed certificates, although it can still be set in
the template if the caller really wants to include it.

## 元コミット内容

`crypto/x509`パッケージにおいて、自己署名証明書に`AuthorityKeyId`拡張をデフォルトで追加しないように変更しました。`AuthorityKeyId`は自己署名証明書ではオプションであり、一般的に無用で、容量を消費します。この変更により、自己署名証明書には`AuthorityKeyId`が追加されなくなりますが、呼び出し元が本当に含めたい場合はテンプレートで設定することで引き続き追加できます。

Issue #15194 を修正します。

## 変更の背景

X.509証明書における`AuthorityKeyId`拡張は、証明書を発行した認証局（CA）の公開鍵を識別するために使用されます。これは、証明書チェーンを構築し、特定の証明書がどのCAによって署名されたかを効率的に特定するために重要です。しかし、自己署名証明書の場合、発行者とサブジェクトが同じであるため、証明書チェーンの概念が適用されません。つまり、自己署名証明書はそれ自体が信頼のアンカーとなるため、自身を識別するための`AuthorityKeyId`は冗長となります。

このコミットの背景には、以下の理由があります。

1.  **冗長性の排除**: 自己署名証明書において`AuthorityKeyId`は技術的に不要であり、その存在は単に証明書のデータサイズを増やすだけです。特に大量の自己署名証明書を扱う場合や、リソースが限られた環境では、この余分なデータがパフォーマンスやストレージに影響を与える可能性があります。
2.  **標準への準拠とベストプラクティス**: RFC 5280 (X.509 Certificate and Certificate Revocation List (CRL) Profile) では、`AuthorityKeyIdentifier`は「CA証明書では必須」とされていますが、自己署名証明書については「オプション」とされています。この変更は、このオプション性を活用し、より効率的な証明書生成を促進するものです。
3.  **Issue #15194 の修正**: この変更は、GoのIssueトラッカーで報告された問題 #15194 に対応するものです。このIssueでは、自己署名証明書に不要な`AuthorityKeyId`が含まれることの非効率性が指摘されていました。

この変更により、Goの`crypto/x509`パッケージで生成される自己署名証明書は、よりコンパクトで効率的になります。

## 前提知識の解説

このコミットを理解するためには、以下の概念について基本的な知識が必要です。

### X.509 証明書

X.509は、公開鍵証明書の標準フォーマットを定義するITU-Tの標準です。インターネット上で広く使用されており、TLS/SSL、コード署名、電子メールのセキュリティなどに利用されます。X.509証明書は、公開鍵と、その公開鍵の所有者に関する情報（サブジェクト）、そしてその情報の正当性を保証する署名（通常は認証局によるもの）を含んでいます。

### 自己署名証明書 (Self-Signed Certificate)

自己署名証明書は、その証明書自体が自身の公開鍵で署名されている証明書です。通常の証明書は信頼された認証局（CA）によって署名されますが、自己署名証明書はCAの介入なしに作成されます。これは、開発環境、テスト環境、または内部ネットワークなど、信頼チェーンが不要な場合や、CAから証明書を取得するコストや手間を避けたい場合によく使用されます。自己署名証明書は、ブラウザやクライアントによってデフォルトでは信頼されないため、明示的に信頼するように設定する必要があります。

### Authority Key Identifier (AuthorityKeyId)

`AuthorityKeyId` (AKI) は、X.509証明書の拡張フィールドの一つで、証明書を発行した認証局（CA）の公開鍵を識別するために使用されます。これは、証明書チェーンを検証する際に、ある証明書がどのCA証明書によって署名されたかを効率的に見つけるために役立ちます。AKIは通常、CA証明書の`SubjectKeyId`と一致するように設定されます。

AKIは以下のいずれかの形式で表現されます。
*   **Key Identifier**: CAの公開鍵のハッシュ値。
*   **Issuer Name and Serial Number**: CA証明書の発行者名とシリアル番号。

### Subject Key Identifier (SubjectKeyId)

`SubjectKeyId` (SKI) は、X.509証明書の拡張フィールドの一つで、証明書に含まれる公開鍵を識別するために使用されます。これは、同じサブジェクト名を持つ複数の証明書が存在する場合に、特定の公開鍵を区別するために役立ちます。CA証明書の場合、その`SubjectKeyId`は、下位の証明書の`AuthorityKeyId`として参照されることがあります。

### 証明書チェーン (Certificate Chain)

証明書チェーンは、エンドエンティティ証明書（例：ウェブサーバーの証明書）から始まり、中間CA証明書を介して、最終的に信頼されたルートCA証明書に至るまでの一連の証明書です。各証明書は、その上位の証明書によって署名されており、このチェーンをたどることで、エンドエンティティ証明書の信頼性を検証できます。

## 技術的詳細

このコミットの技術的詳細は、`crypto/x509`パッケージの`CreateCertificate`関数における`AuthorityKeyId`の生成ロジックの変更にあります。

従来の`CreateCertificate`関数では、親証明書（`parent`引数）の`SubjectKeyId`が存在する場合、それを新しい証明書（`template`引数）の`AuthorityKeyId`として設定していました。これは、一般的なCAが発行する証明書チェーンの構築において正しい動作です。

しかし、自己署名証明書の場合、`template`と`parent`は同じ証明書を指します。このとき、`parent.SubjectKeyId`を`template.AuthorityKeyId`に設定することは、証明書が自分自身の公開鍵を識別するIDを、自分自身の発行者IDとして持つことになり、冗長です。

このコミットでは、以下の条件を追加することで、この冗長性を排除しています。

```go
if !bytes.Equal(asn1Issuer, asn1Subject) && len(parent.SubjectKeyId) > 0 {
	template.AuthorityKeyId = parent.SubjectKeyId
}
```

この変更のポイントは、`!bytes.Equal(asn1Issuer, asn1Subject)`という条件です。
*   `asn1Issuer`は親証明書の発行者情報（Subject）のASN.1エンコーディングです。
*   `asn1Subject`は作成中の証明書（`template`）のサブジェクト情報（Subject）のASN.1エンコーディングです。

もし`asn1Issuer`と`asn1Subject`が等しい場合、それは自己署名証明書であることを意味します（または、発行者とサブジェクトが偶然同じ名前を持つ非常に稀なケース）。この条件が`true`（つまり、発行者とサブジェクトが異なる）の場合にのみ、`parent.SubjectKeyId`が`template.AuthorityKeyId`に設定されます。これにより、自己署名証明書の場合には`AuthorityKeyId`が自動的に設定されなくなります。

ただし、この変更は、呼び出し元が`template.AuthorityKeyId`を明示的に設定している場合には影響しません。もし`template`に既に`AuthorityKeyId`が設定されている場合、`buildExtensions`関数がその値を優先して使用するため、ユーザーの意図が尊重されます。

この最適化は、証明書のサイズをわずかに削減し、不要な情報を排除することで、よりクリーンな証明書プロファイルを実現します。

## コアとなるコードの解説

### `src/crypto/x509/x509.go` の変更

`CreateCertificate`関数は、新しいX.509証明書を作成する主要な関数です。この関数は、ランダムソース、証明書テンプレート、親証明書、公開鍵、秘密鍵を受け取ります。

変更前は、親証明書に`SubjectKeyId`があれば、無条件にそれを新しい証明書の`AuthorityKeyId`として設定していました。

```go
// 変更前のコードの一部
if len(parent.SubjectKeyId) > 0 {
	template.AuthorityKeyId = parent.SubjectKeyId
}
```

変更後は、`asn1Issuer`と`asn1Subject`という2つの変数を導入し、それぞれ親証明書の発行者と作成中の証明書のサブジェクトのASN.1エンコーディングを取得しています。

```go
// 変更後のコードの一部
asn1Issuer, err := subjectBytes(parent)
if err != nil {
	return
}

asn1Subject, err := subjectBytes(template)
if err != nil {
	return
}

if !bytes.Equal(asn1Issuer, asn1Subject) && len(parent.SubjectKeyId) > 0 {
	template.AuthorityKeyId = parent.SubjectKeyId
}
```

ここで重要なのは、`!bytes.Equal(asn1Issuer, asn1Subject)`という条件です。
*   `bytes.Equal(asn1Issuer, asn1Subject)`が`true`の場合、親証明書の発行者と作成中の証明書のサブジェクトが同じであることを意味します。これは自己署名証明書の場合に該当します。
*   この条件が`false`（つまり、発行者とサブジェクトが異なる）かつ`parent.SubjectKeyId`が存在する場合にのみ、`template.AuthorityKeyId`が設定されます。

これにより、自己署名証明書（`asn1Issuer`と`asn1Subject`が等しい場合）では、デフォルトで`AuthorityKeyId`が設定されなくなります。

### `src/crypto/x509/x509_test.go` の変更

テストファイルでは、主に以下の点が変更されました。

1.  **プライベートキーの初期化の共通化**:
    ```go
    var testPrivateKey *rsa.PrivateKey

    func init() {
    	block, _ := pem.Decode([]byte(pemPrivateKey))

    	var err error
    	if testPrivateKey, err = ParsePKCS1PrivateKey(block.Bytes); err != nil {
    		panic("Failed to parse private key: " + err.Error())
    	}
    }
    ```
    `init()`関数内で`pemPrivateKey`を一度だけデコードし、`testPrivateKey`に格納することで、テストのセットアップコードが簡素化され、冗長な処理が削減されました。

2.  **`serialiseAndParse`ヘルパー関数の導入**:
    ```go
    func serialiseAndParse(t *testing.T, template *Certificate) *Certificate {
    	derBytes, err := CreateCertificate(rand.Reader, template, template, &testPrivateKey.PublicKey, testPrivateKey)
    	if err != nil {
    		t.Fatalf("failed to create certificate: %s", err)
    		return nil
    	}

    	cert, err := ParseCertificate(derBytes)
    	if err != nil {
    		t.Fatalf("failed to parse certificate: %s", err)
    		return nil
    	}

    	return cert
    }
    ```
    自己署名証明書の生成とパースという共通の操作をこの関数にまとめることで、テストコードの可読性と保守性が向上しました。

3.  **`TestNoAuthorityKeyIdInSelfSignedCert`の追加**:
    ```go
    func TestNoAuthorityKeyIdInSelfSignedCert(t *testing.T) {
    	template := &Certificate{
    		SerialNumber: big.NewInt(1),
    		Subject: pkix.Name{
    			CommonName: "Σ Acme Co",
    		},
    		NotBefore: time.Unix(1000, 0),
    		NotAfter:  time.Unix(100000, 0),

    		BasicConstraintsValid: true,
    		IsCA:         true,
    		SubjectKeyId: []byte{1, 2, 3, 4},
    	}

    	if cert := serialiseAndParse(t, template); len(cert.AuthorityKeyId) != 0 {
    		t.Fatalf("self-signed certificate contained default authority key id")
    	}

    	template.AuthorityKeyId = []byte{1,2,3,4}
    	if cert := serialiseAndParse(t, template); len(cert.AuthorityKeyId) == 0 {
    		t.Fatalf("self-signed certificate erased explicit authority key id")
    	}
    }
    ```
    この新しいテストは、変更されたロジックの正確性を検証します。
    *   最初の`if`ブロックでは、`template.AuthorityKeyId`を明示的に設定せずに自己署名証明書を生成した場合に、`AuthorityKeyId`が空であることを確認します。
    *   2番目の`if`ブロックでは、`template.AuthorityKeyId`を明示的に設定した場合に、その値が証明書に含まれていることを確認します。これにより、ユーザーが意図的に`AuthorityKeyId`を含めたい場合の動作が保証されます。

これらの変更により、`crypto/x509`パッケージは、自己署名証明書の生成においてより効率的かつ標準に準拠した動作をするようになります。

# [インデックス 2073] ファイルの概要

このコミットは、Go言語の初期の内部変数公開メカニズムである `exvar` パッケージ内の `src/lib/exvar.go` ファイルに対する変更です。`exvar` パッケージは、プログラムの実行中に特定の変数の値を外部から参照できるようにするために使用されていました。これは、デバッグやメトリクスの収集に役立つ機能です。

## コミット

このコミットは、内部で追跡されていた「Bug 143」が修正されたことに伴い、`exvar` パッケージ内のコードをクリーンアップすることを目的としています。具体的には、マップへのアクセス方法がより直接的になり、以前の回避策やTODOコメントが不要になりました。

## 変更の背景

このコミットの主な背景は、Go言語の初期開発段階における特定のバグ、すなわち「Bug 143」が修正されたことです。このバグが修正されるまでは、`exvar` パッケージ内の `IncrementMapInt` および `GetMapInt` 関数において、マップへのアクセス方法に制約がありました。具体的には、マップへのポインタをデリファレンスする必要があったり、関数呼び出しの結果を直接複数の戻り値に展開できないといった問題があったようです。

コミットメッセージとコードの変更内容から判断すると、「Bug 143」は、Goのコンパイラまたはランタイムにおけるマップの扱い、特にマップへのポインタのデリファレンスや、関数が返すマップの値を直接利用する際の挙動に関する問題であったと推測されます。このバグが修正されたことで、開発者はより直感的でクリーンな方法でマップにアクセスできるようになり、以前の回避策や「TODO(dsymonds): Change this to just ... when bug143 is fixed.」といったコメントを削除することが可能になりました。

## 前提知識の解説

このコミットの変更内容を理解するためには、以下のGo言語の基本的な概念と `exvar` パッケージの役割について理解しておく必要があります。

*   **Go言語のマップ (map)**: Goのマップは、キーと値のペアを格納するハッシュテーブルです。`make(map[keyType]valueType)` で初期化され、`m[key] = value` で値を設定し、`value, ok := m[key]` で値を取得します。`ok` はキーが存在するかどうかを示します。
*   **ポインタとデリファレンス**: Goでは、変数のメモリアドレスを指すポインタを使用できます。ポインタ変数の前に `*` を付けることで、そのポインタが指すメモリ位置にある値（デリファレンス）にアクセスできます。
*   **関数と戻り値**: Goの関数は複数の戻り値を返すことができます。例えば、`func foo() (int, bool)` のように定義された関数は、`i, ok := foo()` のように複数の変数で受け取ることができます。
*   **クロージャ**: Goのクロージャは、それが定義された環境の変数を「キャプチャ」する関数です。このコミットでは `workSync(func(state *exVars) { ... })` のように無名関数（クロージャ）が使用されています。
*   **`exvar` パッケージ**: Goの初期の標準ライブラリの一部であり、プログラムの内部状態（変数やメトリクス）を外部に公開するためのメカニズムを提供していました。これは、デバッグやプロファイリング、監視などの目的で使用されます。`exvar` は `expvar` パッケージの前身にあたります。
*   **`workSync` 関数**: `exvar` パッケージ内で定義されていると思われる同期メカニズムです。これは、複数のゴルーチンから `exvar` の内部状態に安全にアクセスするために、ミューテックスなどの同期プリミティブを使用して排他制御を行っていると推測されます。

## 技術的詳細

このコミットの技術的な詳細は、`src/lib/exvar.go` 内の `IncrementMapInt` 関数と `GetMapInt` 関数の変更に集約されます。

### `IncrementMapInt` 関数の変更

変更前:
```go
func IncrementMapInt(name string, key string, inc int) {
	workSync(func(state *exVars) {
		mv := state.getOrInitMapVar(name);
		// TODO(dsymonds): Change this to just mv[key] when bug143 is fixed.
		if v, ok := (*mv)[key]; ok {
			mv[key] += inc
		} else {
			mv[key] = inc
		}
	});
}
```

変更後:
```go
func IncrementMapInt(name string, key string, inc int) {
	workSync(func(state *exVars) {
		mv := state.getOrInitMapVar(name);
		if v, ok := mv[key]; ok { // 変更点: (*mv)[key] から mv[key] へ
			mv[key] += inc
		} else {
			mv[key] = inc
		}
	});
}
```

この変更は、`mv` が `map[string]int` 型（またはそれに準ずる型）の変数であり、以前はマップへのポインタとして扱われていた `*mv` が、Bug 143の修正により直接マップとして扱えるようになったことを示唆しています。これにより、冗長なポインタのデリファレンス `*` が不要になり、コードが簡潔になりました。

### `GetMapInt` 関数の変更

変更前:
```go
func GetMapInt(name string, key string) int {
	var i int;
	var ok bool;
	workSync(func(state *exVars) {
		// TODO(dsymonds): Change this to just getOrInitMapVar(name)[key] when
		// bug143 is fixed.
		i, ok = (*state.getOrInitMapVar(name))[key];
	});
	return i
}
```

変更後:
```go
func GetMapInt(name string, key string) int {
	var i int;
	var ok bool;
	workSync(func(state *exVars) {
		// This doesn't work:
		//   i, ok = state.getOrInitMapVar(name)[key];
		// exvar.go:169: assignment count mismatch: 2 = 1
		// Should it? Wrapping the method call in () doesn't help.
		mv := state.getOrInitMapVar(name); // 変更点: 新しい変数 mv を導入
		i, ok = mv[key];                   // 変更点: mv を使用してマップにアクセス
	});
	return i
}
```

この変更はより複雑で、当時のGoコンパイラの挙動に関する重要な情報を含んでいます。

1.  **`TODO` コメントの削除**: `IncrementMapInt` と同様に、Bug 143の修正により、より直接的なアクセスが可能になったため、TODOコメントが削除されました。
2.  **`(*state.getOrInitMapVar(name))[key]` からの変更**: 以前は `getOrInitMapVar` の戻り値（おそらくマップへのポインタ）をデリファレンスしてマップにアクセスしていました。
3.  **新しい変数 `mv` の導入**: 変更後では、`state.getOrInitMapVar(name)` の結果を一度 `mv` という変数に代入してから、`mv[key]` でマップにアクセスしています。
4.  **コメント `// This doesn't work: ...` の追加**: これは、当時のGoコンパイラが、関数呼び出しの戻り値を直接複数の変数に展開する際に、その戻り値がマップのインデックスアクセスのような別の操作の結果である場合に、構文エラー `assignment count mismatch: 2 = 1` を発生させていたことを示しています。つまり、`i, ok = state.getOrInitMapVar(name)[key]` のような記述は、当時のGoでは許可されていなかったということです。Bug 143の修正は、このコンパイラの制約を緩和し、より自然なコード記述を可能にしたと推測されます。しかし、このコミット時点では、まだ直接のインデックスアクセスはできず、一度変数に代入する必要があったようです。これは、Go言語の進化の過程で、コンパイラの機能が徐々に改善されていったことを示しています。

## コアとなるコードの解説

*   **`IncrementMapInt` 関数**:
    *   `-		// TODO(dsymonds): Change this to just mv[key] when bug143 is fixed.`
        *   Bug 143の修正により、このTODOコメントが不要になったため削除されました。
    *   `-		if v, ok := (*mv)[key]; ok {`
        *   以前は `mv` がマップへのポインタであったため、デリファレンス演算子 `*` を使ってマップ自体にアクセスしていました。
    *   `+		if v, ok := mv[key]; ok {`
        *   Bug 143の修正後、`mv` は直接マップとして扱えるようになったため、`*` が不要になりました。これにより、コードがより自然で読みやすくなりました。

*   **`GetMapInt` 関数**:
    *   `-		// TODO(dsymonds): Change this to just getOrInitMapVar(name)[key] when`
    *   `-		// bug143 is fixed.`
        *   `IncrementMapInt` と同様に、Bug 143の修正によりTODOコメントが削除されました。
    *   `-		i, ok = (*state.getOrInitMapVar(name))[key];`
        *   以前は `state.getOrInitMapVar(name)` の戻り値（マップへのポインタ）をデリファレンスしてマップにアクセスし、その結果を `i, ok` に代入していました。
    *   `+		// This doesn\'t work:`
    *   `+		//   i, ok = state.getOrInitMapVar(name)[key];`
    *   `+		// exvar.go:169: assignment count mismatch: 2 = 1`
    *   `+		// Should it? Wrapping the method call in () doesn\'t help.`
        *   この新しいコメントは、当時のGoコンパイラの制約を明確に示しています。関数呼び出しの結果（`state.getOrInitMapVar(name)`）に対して直接マップのインデックスアクセスを行い、その結果を複数の戻り値として受け取る構文は、当時のコンパイラではサポートされていませんでした。`assignment count mismatch: 2 = 1` は、2つの戻り値（`i, ok`）を期待しているのに、右辺が1つの値（マップアクセス結果）しか返していないとコンパイラが解釈したことを意味します。
    *   `+		mv := state.getOrInitMapVar(name);`
        *   この行は、`state.getOrInitMapVar(name)` の結果を一時変数 `mv` に代入することで、上記のコンパイラの制約を回避しています。
    *   `+		i, ok = mv[key];`
        *   一時変数 `mv` を介してマップにアクセスすることで、`i, ok` への正しい代入が可能になります。

これらの変更は、Go言語の初期段階におけるコンパイラの成熟度と、特定のバグ修正が言語の表現力とコードの簡潔さにどのように影響を与えたかを示す良い例です。

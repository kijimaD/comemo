# [インデックス 2490] ファイルの概要

このコミットは、Go言語のI/OパッケージにおけるEOF (End Of File) 処理のセマンティクスを明確化し、関連するAPIを整理することを目的としています。具体的には、`os.EOF` と `io.ErrUnexpectedEOF` という新しいエラーを導入し、既存の `io.ErrEOF` を削除しています。また、`io.FullRead` 関数を `io.ReadFull` にリネームし、`io.FullReader` 型を削除しています。これらの変更により、GoのI/O操作におけるEOFの扱いが一貫性のある、より堅牢なものになっています。

## 変更の背景

Go言語の初期のI/Oパッケージでは、ファイルの終端 (EOF) に達したことを示すために `io.ErrEOF` が使用されていました。しかし、この単一のエラーでは、以下の2つの異なるシナリオを区別することが困難でした。

1.  **正常なEOF**: ストリームの終端に達し、これ以上読み取るデータがないことを示す場合。これは、例えばファイル全体を読み終えたときなど、期待される動作です。
2.  **予期せぬEOF**: 固定長のデータを読み取ろうとした際に、期待されるバイト数に満たない状態でストリームの終端に達してしまった場合。これは、データが破損しているか、プロトコル違反が発生している可能性を示唆します。

`io.ErrEOF` が両方のケースで返されると、呼び出し元はエラーが「正常な終端」を意味するのか、「問題が発生した」ことを意味するのかを判断するために、追加のロジック（例えば、読み取られたバイト数を確認するなど）を記述する必要がありました。これはコードの複雑さを増し、エラーハンドリングのバグにつながる可能性がありました。

特に、`http/client_test.go` のコメント (`// TODO: io.ErrEOF check is needed because we're sometimes getting // this error when nothing is actually wrong. rsc suspects a bug // in bufio. Can remove the ErrEOF check once the bug is fixed // (expected to occur within a few weeks of this writing, 6/9/09).`) は、当時の `io.ErrEOF` の曖昧さが実際に問題を引き起こしていたことを示唆しています。`bufio` パッケージのバグが原因で、本来エラーではない状況で `io.ErrEOF` が返されることがあり、これが修正されるまでの間、一時的な回避策が必要とされていました。

このコミットは、これらの問題を解決するために、EOFのセマンティクスを明確にし、より表現力豊かなエラー型を導入することで、I/O操作の堅牢性と使いやすさを向上させることを目的としています。また、`io.FullRead` のリネームは、Goの標準ライブラリにおける命名規則の一貫性を保つための変更です。

## 前提知識の解説

### Go言語のI/Oインターフェース

Go言語では、I/O操作は `io.Reader` と `io.Writer` というシンプルなインターフェースによって抽象化されています。

*   **`io.Reader`**:
    ```go
    type Reader interface {
        Read(p []byte) (n int, err os.Error)
    }
    ```
    `Read` メソッドは、最大 `len(p)` バイトを `p` に読み込み、読み込んだバイト数 `n` とエラー `err` を返します。
    `Read` メソッドの重要な特性は以下の通りです。
    *   `n < len(p)` であっても、`p` の全ての領域をスクラッチスペースとして使用する可能性があります。
    *   利用可能なデータが `len(p)` バイト未満であっても、ブロックしてさらに待つのではなく、利用可能なデータを返すのが慣例です。
    *   入力ストリームの終端では、`0` バイトを読み込み、`os.EOF` エラーを返します。
    *   `n > 0` であっても、`os.EOF` 以外の非 `nil` エラーを返すことがあります。特に、入力が尽きる `Read` は `n > 0, os.EOF` を返すことがあります。

### EOF (End Of File) の概念

EOFは、データストリームの終端に達し、これ以上読み取るデータがない状態を指します。ファイル、ネットワークソケット、パイプなど、様々なI/Oソースで発生します。プログラミングにおいて、EOFは通常、データ読み取りループを終了させる条件として使用されます。

### Goにおけるエラーハンドリングの慣習

Go言語では、エラーは戻り値として扱われます。関数は通常、最後の戻り値として `error` 型を返します。エラーがない場合は `nil` を返します。エラーが発生した場合は、`nil` ではない `error` 値を返します。このコミット以前は、EOFを示すエラーも `io.ErrEOF` という `error` 型の変数として定義されていました。

### 固定長読み込みの必要性

多くのプロトコルやデータ形式では、特定の構造体やヘッダーが固定長で定義されています。例えば、4バイトの長さフィールドの後にデータが続く場合などです。このような場合、指定されたバイト数を正確に読み取ることが期待されます。もし期待されるバイト数に満たない状態でEOFに達した場合、それは単なるストリームの終端ではなく、データが不完全であるか、破損していることを意味します。

## 技術的詳細

このコミットの核となる変更は、EOFのセマンティクスをより厳密に定義し、それに対応するエラー型を導入した点にあります。

### `os.EOF` の導入と `io.ErrEOF` の削除

*   **`os.EOF`**: 新たに `os` パッケージに `EOF` エラーが導入されました。これは、`Read` メソッドがこれ以上読み取るデータがないことを示すために返す、**正常な**ストリーム終端のエラーです。`os.EOF` は、`Read` が `0` バイトを読み込み、エラーとして返す場合にのみ使用されるべきです。
    `src/pkg/os/file.go` にて以下のように定義されています。
    ```go
    type eofError int
    func (eofError) String() string {
        return "EOF"
    }
    // EOF is the Error returned by Read when no more input is available.
    // Functions should return EOF only to signal a graceful end of input.
    // If the EOF occurs unexpectedly in a structured data stream,
    // the appropriate error is either io.ErrUnexpectedEOF or some other error
    // giving more detail.
    var EOF Error = eofError(0)
    ```
    この定義は、`os.EOF` が「正常な入力の終端」を示すためのものであることを明確にしています。

*   **`io.ErrEOF` の削除**: 以前の `io.ErrEOF` は削除され、その役割は `os.EOF` に引き継がれました。これにより、EOFを示す標準的なエラーは `os.EOF` に統一されました。

### `io.ErrUnexpectedEOF` の導入

*   **`io.ErrUnexpectedEOF`**: `io` パッケージに `ErrUnexpectedEOF` が導入されました。このエラーは、固定長のデータを読み取ろうとした際に、期待されるバイト数に満たない状態でEOFに達した場合に返されます。これは、データストリームが予期せず終了したことを示し、通常はエラー状況と見なされます。
    `src/pkg/io/io.go` にて以下のように定義されています。
    ```go
    // ErrUnexpectedEOF means that os.EOF was encountered in the
    // middle of reading a fixed-size block or data structure.
    var ErrUnexpectedEOF os.Error = &Error{"unexpected EOF"}
    ```

### `io.FullRead` から `io.ReadFull` へのリネームとセマンティクスの明確化

*   **`io.FullRead` のリネーム**: 以前の `io.FullRead` 関数は `io.ReadFull` にリネームされました。これは、`io.ReadAtLeast` や `io.ReadAll` といった既存の関数との命名規則の一貫性を保つためです。
*   **`io.ReadFull` のセマンティクス**: `io.ReadFull(r Reader, buf []byte)` は、`buf` の長さと**正確に同じバイト数**を `r` から `buf` に読み込もうとします。
    *   もし `len(buf)` バイトを読み込む前にEOFに達した場合、`io.ErrUnexpectedEOF` を返します。
    *   もし全くバイトを読み込めずにEOFに達した場合、`os.EOF` を返します。
    *   この関数は内部的に `io.ReadAtLeast` を使用しています。

### `io.FullReader` の削除

`io.FullRead` が `io.ReadFull` にリネームされ、その機能が `io.ReadAtLeast` を通じて提供されるようになったため、`io.FullReader` 型は不要となり削除されました。

### `io.Reader` インターフェースのドキュメント更新

`io.Reader` インターフェースの `Read` メソッドに関するドキュメントが更新され、EOFのセマンティクスがより明確に記述されました。特に、「入力ストリームの終端では、Readは0、os.EOFを返す」という点が強調されています。

これらの変更により、GoのI/Oコードは、EOFの状況をより正確に区別し、適切なエラーハンドリングを行うことができるようになりました。例えば、ファイル全体を読み込むループでは `os.EOF` をチェックし、固定長のヘッダーを読み込む際には `io.ErrUnexpectedEOF` をチェックするといった使い分けが可能になります。

このコミットは、Goの標準ライブラリの広範囲にわたるファイルに影響を与えていますが、特に重要な変更は以下のファイルに見られます。

## 変更の背景

Go言語の初期のI/Oパッケージでは、ファイルの終端 (EOF) に達したことを示すために `io.ErrEOF` が使用されていました。しかし、この単一のエラーでは、以下の2つの異なるシナリオを区別することが困難でした。

1.  **正常なEOF**: ストリームの終端に達し、これ以上読み取るデータがないことを示す場合。これは、例えばファイル全体を読み終えたときなど、期待される動作です。
2.  **予期せぬEOF**: 固定長のデータを読み取ろうとした際に、期待されるバイト数に満たない状態でストリームの終端に達してしまった場合。これは、データが破損しているか、プロトコル違反が発生している可能性を示唆します。

`io.ErrEOF` が両方のケースで返されると、呼び出し元はエラーが「正常な終端」を意味するのか、「問題が発生した」ことを意味するのかを判断するために、追加のロジック（例えば、読み取られたバイト数を確認するなど）を記述する必要がありました。これはコードの複雑さを増し、エラーハンドリングのバグにつながる可能性がありました。

特に、`http/client_test.go` のコメント (`// TODO: io.ErrEOF check is needed because we're sometimes getting // this error when nothing is actually wrong. rsc suspects a bug // in bufio. Can remove the ErrEOF check once the bug is fixed // (expected to occur within a few weeks of this writing, 6/9/09).`) は、当時の `io.ErrEOF` の曖昧さが実際に問題を引き起こしていたことを示唆しています。`bufio` パッケージのバグが原因で、本来エラーではない状況で `io.ErrEOF` が返されることがあり、これが修正されるまでの間、一時的な回避策が必要とされていました。

このコミットは、これらの問題を解決するために、EOFのセマンティクスを明確にし、より表現力豊かなエラー型を導入することで、I/O操作の堅牢性と使いやすさを向上させることを目的としています。また、`io.FullRead` のリネームは、Goの標準ライブラリにおける命名規則の一貫性を保つための変更です。

## 前提知識の解説

### Go言語のI/Oインターフェース

Go言語では、I/O操作は `io.Reader` と `io.Writer` というシンプルなインターフェースによって抽象化されています。

*   **`io.Reader`**:
    ```go
    type Reader interface {
        Read(p []byte) (n int, err os.Error)
    }
    ```
    `Read` メソッドは、最大 `len(p)` バイトを `p` に読み込み、読み込んだバイト数 `n` とエラー `err` を返します。
    `Read` メソッドの重要な特性は以下の通りです。
    *   `n < len(p)` であっても、`p` の全ての領域をスクラッチスペースとして使用する可能性があります。
    *   利用可能なデータが `len(p)` バイト未満であっても、ブロックしてさらに待つのではなく、利用可能なデータを返すのが慣例です。
    *   入力ストリームの終端では、`0` バイトを読み込み、`os.EOF` エラーを返します。
    *   `n > 0` であっても、`os.EOF` 以外の非 `nil` エラーを返すことがあります。特に、入力が尽きる `Read` は `n > 0, os.EOF` を返すことがあります。

### EOF (End Of File) の概念

EOFは、データストリームの終端に達し、これ以上読み取るデータがない状態を指します。ファイル、ネットワークソケット、パイプなど、様々なI/Oソースで発生します。プログラミングにおいて、EOFは通常、データ読み取りループを終了させる条件として使用されます。

### Goにおけるエラーハンドリングの慣習

Go言語では、エラーは戻り値として扱われます。関数は通常、最後の戻り値として `error` 型を返します。エラーがない場合は `nil` を返します。エラーが発生した場合は、`nil` ではない `error` 値を返します。このコミット以前は、EOFを示すエラーも `io.ErrEOF` という `error` 型の変数として定義されていました。

### 固定長読み込みの必要性

多くのプロトコルやデータ形式では、特定の構造体やヘッダーが固定長で定義されています。例えば、4バイトの長さフィールドの後にデータが続く場合などです。このような場合、指定されたバイト数を正確に読み取ることが期待されます。もし期待されるバイト数に満たない状態でEOFに達した場合、それは単なるストリームの終端ではなく、データが不完全であるか、破損していることを意味します。

## 技術的詳細

このコミットの核となる変更は、EOFのセマンティクスをより厳密に定義し、それに対応するエラー型を導入した点にあります。

### `os.EOF` の導入と `io.ErrEOF` の削除

*   **`os.EOF`**: 新たに `os` パッケージに `EOF` エラーが導入されました。これは、`Read` メソッドがこれ以上読み取るデータがないことを示すために返す、**正常な**ストリーム終端のエラーです。`os.EOF` は、`Read` が `0` バイトを読み込み、エラーとして返す場合にのみ使用されるべきです。
    `src/pkg/os/file.go` にて以下のように定義されています。
    ```go
    type eofError int
    func (eofError) String() string {
        return "EOF"
    }
    // EOF is the Error returned by Read when no more input is available.
    // Functions should return EOF only to signal a graceful end of input.
    // If the EOF occurs unexpectedly in a structured data stream,
    // the appropriate error is either io.ErrUnexpectedEOF or some other error
    // giving more detail.
    var EOF Error = eofError(0)
    ```
    この定義は、`os.EOF` が「正常な入力の終端」を示すためのものであることを明確にしています。

*   **`io.ErrEOF` の削除**: 以前の `io.ErrEOF` は削除され、その役割は `os.EOF` に引き継がれました。これにより、EOFを示す標準的なエラーは `os.EOF` に統一されました。

### `io.ErrUnexpectedEOF` の導入

*   **`io.ErrUnexpectedEOF`**: `io` パッケージに `ErrUnexpectedEOF` が導入されました。このエラーは、固定長のデータを読み取ろうとした際に、期待されるバイト数に満たない状態でEOFに達した場合に返されます。これは、データストリームが予期せず終了したことを示し、通常はエラー状況と見なされます。
    `src/pkg/io/io.go` にて以下のように定義されています。
    ```go
    // ErrUnexpectedEOF means that os.EOF was encountered in the
    // middle of reading a fixed-size block or data structure.
    var ErrUnexpectedEOF os.Error = &Error{"unexpected EOF"}
    ```

### `io.FullRead` から `io.ReadFull` へのリネームとセマンティクスの明確化

*   **`io.FullRead` のリネーム**: 以前の `io.FullRead` 関数は `io.ReadFull` にリネームされました。これは、`io.ReadAtLeast` や `io.ReadAll` といった既存の関数との命名規則の一貫性を保つためです。
*   **`io.ReadFull` のセマンティクス**: `io.ReadFull(r Reader, buf []byte)` は、`buf` の長さと**正確に同じバイト数**を `r` から `buf` に読み込もうとします。
    *   もし `len(buf)` バイトを読み込む前にEOFに達した場合、`io.ErrUnexpectedEOF` を返します。
    *   もし全くバイトを読み込めずにEOFに達した場合、`os.EOF` を返します。
    *   この関数は内部的に `io.ReadAtLeast` を使用しています。

### `io.FullReader` の削除

`io.FullRead` が `io.ReadFull` にリネームされ、その機能が `io.ReadAtLeast` を通じて提供されるようになったため、`io.FullReader` 型は不要となり削除されました。

### `io.Reader` インターフェースのドキュメント更新

`io.Reader` インターフェースの `Read` メソッドに関するドキュメントが更新され、EOFのセマンティクスがより明確に記述されました。特に「入力ストリームの終端では、Readは0、os.EOFを返す」という点が強調されています。

これらの変更により、GoのI/Oコードは、EOFの状況をより正確に区別し、適切なエラーハンドリングを行うことができるようになりました。例えば、ファイル全体を読み込むループでは `os.EOF` をチェックし、固定長のヘッダーを読み込む際には `io.ErrUnexpectedEOF` をチェックするといった使い分けが可能になります。

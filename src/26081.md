## 元コミット内容

このコミットは、コミット `6acb4d944dafa13a6c80faffc4e7ecc47d2bcdbc` をリバートするものです。リバートされたコミットは、「`cmd/go`: テストバイナリのフラグ処理を修正」と題されており、`go test` コマンドがテストバイナリに渡すフラグの処理方法を変更しようとしました。具体的には、`go test` コマンドライン引数の解析ロジックをより厳密にし、`[test flags] [packages] [flags for test binary]` という明確な順序を強制しようとしたと考えられます。この変更は、`go test` 自身が処理するフラグと、テストバイナリに渡されるフラグの区別をより明確にすることを意図していた可能性があります。

## 変更の背景

リバートされたコミット `6acb4d944dafa13a6c80faffc4e7ecc47d2bcdbc` は、`go test` コマンドのフラグ処理を修正しようとしましたが、その結果として「一般的な `go test` の呼び出しの多くを壊して」しまいました。これは、ユーザーが慣れ親しんだ `go test` のコマンドライン引数の渡し方と、新しいフラグ解析ロジックとの間に不整合が生じたためと考えられます。特に、パッケージ名の後にテストバイナリ向けのフラグを渡すような一般的なパターンが正しく機能しなくなった可能性があります。この問題は Issue #13583 として報告され、早急な対応が必要と判断されたため、元の変更を元に戻すという形で解決が図られました。コミットメッセージには「元の懸念は別の方法で修正する」とあり、フラグ処理の改善自体は必要であるものの、そのアプローチが問題を引き起こしたため、一旦リバートして再検討する方針が示されています。

## 前提知識の解説

### `go test` コマンドの動作

`go test` は Go 言語のテストを実行するための主要なコマンドです。このコマンドは、指定されたパッケージのテストコードをコンパイルし、テストバイナリを生成して実行します。`go test` コマンドライン引数は、大きく分けて以下の3つのカテゴリに分類されます。

1.  **`go test` 自身のフラグ**: `go test` コマンドの挙動を制御するフラグです。例: `-v` (詳細出力), `-cover` (カバレッジ有効化), `-race` (データ競合検出), `-short` (短時間テスト実行)。
2.  **パッケージ名**: テストを実行する対象のパッケージを指定します。複数のパッケージを指定することも可能です。
3.  **テストバイナリに渡されるフラグ**: `go test` によって生成されたテストバイナリが受け取るフラグです。これらは `go test` 自身には解釈されず、テストバイナリの実行時に利用されます。慣例的に `-test.` プレフィックスを持つことが多いですが、ユーザー定義のカスタムフラグも含まれます。例: `-test.run TestMyFunction` (特定のテスト関数のみ実行), `-test.bench .` (ベンチマーク実行)。

### `go test` のフラグ解析の複雑性

`go test` のフラグ解析は、上記の3つのカテゴリの引数が混在する可能性があるため、複雑です。特に、`go test` 自身のフラグとテストバイナリに渡されるフラグが、コマンドライン上でどのように区別され、処理されるかが重要になります。歴史的に、Go の `flag` パッケージは、フラグと非フラグ引数を順次処理するシンプルなモデルを採用しており、これが `go test` のような複雑なコマンドの引数解析を難しくしていました。

### `go test` のコマンドライン引数の一般的なパターン

ユーザーはしばしば以下のようなパターンで `go test` を実行します。

*   `go test -v ./...` (`go test` 自身のフラグがパッケージ名の前に来る)
*   `go test fmt -test.v` (パッケージ名の後にテストバイナリ向けのフラグが来る)
*   `go test -coverprofile=cover.out mypackage` (`go test` 自身のフラグがパッケージ名の前に来る)
*   `go test mypackage -mycustomflag=value` (パッケージ名の後にカスタムフラグが来る)

リバートされたコミットは、これらの柔軟なパターンの一部を壊したと考えられます。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/go/testflag.go` ファイル内の `testFlags` 関数のロジックを元に戻すことです。この関数は、`go test` コマンドに渡された引数を解析し、`go test` 自身が処理すべきフラグと、テストバイナリに渡すべきフラグ、そしてテスト対象のパッケージ名に分割する役割を担っています。

### `testflag.go` の変更点

リバートによって、`testFlags` 関数のフラグ解析ロジックは、より柔軟な挙動に戻されました。

**変更前（リバートされたコミットの挙動）のコメント（削除された部分）:**
```go
// The usage is:
//	go test [test flags] [packages] [flags for test binary]
// Thus we process test flags (adding -test. to each) until we find a non-flag,
// which introduces the optional list of packages. We collect the package paths
// until we find another -flag, and pass that and the rest of the command line
// to the test binary untouched.
// For backwards compatibility with a poor design, if while processing test
// flags we see an unrecognized flag, we accept it as an argument to the binary.
// For this to work in general, one must say -foo=xxx not -foo xxx or else
// xxx will be taken to be a package path. As said, the design is poor.
```
このコメントは、フラグ、パッケージ、テストバイナリフラグの厳密な順序を想定しており、未知のフラグはテストバイナリに渡されるが、その際に `-foo=xxx` の形式でなければならないという制約を示唆しています。この厳密さが問題の原因でした。

**変更後（リバートによって復元された挙動）のコメント（追加された部分）:**
```go
// We allow known flags both before and after the package name list,
// to allow both
//	go test fmt -custom-flag-for-fmt-test
//	go test -x math
```
このコメントは、既知のフラグがパッケージ名のリストの前後に現れることを許容する、より柔軟な解析モデルを明確に示しています。

**`testFlags` 関数のロジックの復元:**

リバートされたコードでは、`inPkg` というブール変数と、引数のループ処理が変更されていました。このコミットでは、`inPkg` のロジックが以下のように復元されています。

1.  `inPkg` 変数は、現在パッケージ名を解析している途中であるかを示すフラグとして機能します。
2.  引数を順に処理するループ内で、引数がハイフン (`-`) で始まらない場合、それがパッケージ名であると判断されます。
    *   もし `inPkg` が `false` で、かつまだパッケージ名が一つも収集されていない場合、その引数を最初のパッケージ名として扱い、`inPkg` を `true` に設定します。
    *   `inPkg` が `true` の場合、その引数をパッケージ名として `packageNames` リストに追加します。
3.  引数がハイフン (`-`) で始まる場合、それがフラグであると判断されます。
    *   もし `inPkg` が `true` であれば、これはパッケージ名のリストが終了し、再びフラグの処理に戻ったことを意味するため、`inPkg` を `false` に設定します。
    *   `testFlag` 関数（既知の `go test` フラグを識別するヘルパー関数）を呼び出し、引数が既知のフラグであるかをチェックします。
    *   既知のフラグであれば、`go test` 自身が処理するフラグとして扱います。
    *   未知のフラグであれば、それはテストバイナリに渡されるべきフラグであると判断し、`passToTest` リストに追加します。この際、`inPkg` を `false` に設定することで、それ以降の引数がパッケージ名として誤って解釈されるのを防ぎます。

このロジックにより、`go test` はコマンドライン引数をより寛容に解釈し、パッケージ名の前後にフラグが混在するケースにも対応できるようになります。

### `go_test.go` の変更点

`src/cmd/go/go_test.go` では、`TestCoverageUsesSetMode`, `TestCoverageUsesAtomicModeForRace`, `TestCoverageUsesActualSettingToOverrideEvenForRace` といったテストカバレッジ関連のテストケースが修正されています。

具体的には、`tg.run` メソッドの呼び出しにおいて、`-coverprofile` や `-covermode` フラグの前に `-cover` フラグが追加されています。

**変更前（リバートされたコミットの挙動）:**
```go
tg.run("test", "-short", "-coverprofile=testdata/cover.out", "encoding/binary")
```
**変更後（リバートによって復元された挙動）:**
```go
tg.run("test", "-short", "-cover", "encoding/binary", "-coverprofile=testdata/cover.out")
```
この変更は、リバートされたコミットが `-cover` フラグの扱いを変更し、それがテストの実行に影響を与えたことを示唆しています。リバートによって、`-cover` フラグが明示的に指定される以前の挙動に戻すことで、これらのテストが再びパスするようになります。また、`TestGoTestFlagsAfterPackage` というテストケースが削除されています。これは、パッケージ名の後にフラグを渡す特定のシナリオをテストするものでしたが、リバートによってそのテストケースが不要になったか、あるいはリバートされたコミットが意図した挙動と異なるため削除されたと考えられます。

## コアとなるコードの解説

### `src/cmd/go/testflag.go` の `testFlags` 関数

この関数の変更は、`go test` コマンドの引数解析の柔軟性を復元することが目的です。

*   **`inPkg` 変数の導入とロジックの変更**:
    *   リバートされたコミットでは、引数を「フラグ」「パッケージ」「テストバイナリフラグ」の3つのフェーズで処理する、より線形的なアプローチが取られていました。
    *   このリバートでは、`inPkg` というブールフラグが導入され、引数のループ内で動的に現在の解析フェーズを切り替えるロジックが復元されました。
    *   `!strings.HasPrefix(args[i], "-")` (引数がハイフンで始まらない) かつ `!inPkg && packageNames == nil` の場合、最初のパッケージ名が見つかったと判断し、`inPkg = true` となります。
    *   `inPkg` が `true` の間は、ハイフンで始まらない引数はすべてパッケージ名として `packageNames` に追加されます。
    *   `inPkg` が `true` の状態でハイフンで始まる引数（フラグ）が見つかった場合、パッケージ名のリストが終了したと判断し、`inPkg = false` に戻ります。
    *   未知のフラグ (`f == nil`) が見つかった場合も、`inPkg = false` に設定されます。これは、未知のフラグの後に続く引数が、テストバイナリに渡されるフラグの引数である可能性があり、パッケージ名として誤って解釈されるのを防ぐためです。

このロジックにより、`go test fmt -custom-flag-for-fmt-test` のように、パッケージ名の後にテストバイナリ向けのフラグが続く形式や、`go test -x math` のように、`go test` 自身のフラグがパッケージ名の前に来る形式の両方が正しく処理されるようになります。

### `src/cmd/go/go_test.go` のテストケース

テストカバレッジ関連のテストケースの変更は、`go test` コマンドの引数として `-cover` フラグを明示的に追加することで、リバートされたコミットが導入した挙動の変更に対応しています。これは、以前のコミットが `-coverprofile` や `-covermode` フラグが指定された場合に自動的にカバレッジを有効にする挙動を変更した可能性があり、リバートによってその挙動が元に戻されたため、テストコードもそれに合わせて修正されたことを示唆しています。

`TestGoTestFlagsAfterPackage` テストケースの削除は、リバートされたコミットが意図した、パッケージ名の後にフラグを渡す特定のシナリオのテストが、リバートによって不要になったか、あるいはそのテストがカバーしていた挙動がもはや期待されないためと考えられます。

## 変更の背景

リバートされたコミット `6acb4d944dafa13a6c80faffc4e7ecc47d2bcdbc` は、`go test` コマンドのフラグ処理を修正しようとしましたが、その結果として「一般的な `go test` の呼び出しの多くを壊して」しまいました。これは、ユーザーが慣れ親しんだ `go test` のコマンドライン引数の渡し方と、新しいフラグ解析ロジックとの間に不整合が生じたためと考えられます。特に、パッケージ名の後にテストバイナリ向けのフラグを渡すような一般的なパターンが正しく機能しなくなった可能性があります。この問題は Issue #13583 として報告され、早急な対応が必要と判断されたため、元の変更を元に戻すという形で解決が図られました。コミットメッセージには「元の懸念は別の方法で修正する」とあり、フラグ処理の改善自体は必要であるものの、そのアプローチが問題を引き起こしたため、一旦リバートして再検討する方針が示されています。

## 前提知識の解説

### `go test` コマンドの動作

`go test` は Go 言語のテストを実行するための主要なコマンドです。このコマンドは、指定されたパッケージのテストコードをコンパイルし、テストバイナリを生成して実行します。`go test` コマンドライン引数は、大きく分けて以下の3つのカテゴリに分類されます。

1.  **`go test` 自身のフラグ**: `go test` コマンドの挙動を制御するフラグです。例: `-v` (詳細出力), `-cover` (カバレッジ有効化), `-race` (データ競合検出), `-short` (短時間テスト実行)。
2.  **パッケージ名**: テストを実行する対象のパッケージを指定します。複数のパッケージを指定することも可能です。
3.  **テストバイナリに渡されるフラグ**: `go test` によって生成されたテストバイナリが受け取るフラグです。これらは `go test` 自身には解釈されず、テストバイナリの実行時に利用されます。慣例的に `-test.` プレフィックスを持つことが多いですが、ユーザー定義のカスタムフラグも含まれます。例: `-test.run TestMyFunction` (特定のテスト関数のみ実行), `-test.bench .` (ベンチマーク実行)。

### `go test` のフラグ解析の複雑性

`go test` のフラグ解析は、上記の3つのカテゴリの引数が混在する可能性があるため、複雑です。特に、`go test` 自身のフラグとテストバイナリに渡されるフラグが、コマンドライン上でどのように区別され、処理されるかが重要になります。歴史的に、Go の `flag` パッケージは、フラグと非フラグ引数を順次処理するシンプルなモデルを採用しており、これが `go test` のような複雑なコマンドの引数解析を難しくしていました。

### `go test` のコマンドライン引数の一般的なパターン

ユーザーはしばしば以下のようなパターンで `go test` を実行します。

*   `go test -v ./...` (`go test` 自身のフラグがパッケージ名の前に来る)
*   `go test fmt -test.v` (パッケージ名の後にテストバイナリ向けのフラグが来る)
*   `go test -coverprofile=cover.out mypackage` (`go test` 自身のフラグがパッケージ名の前に来る)
*   `go test mypackage -mycustomflag=value` (パッケージ名の後にカスタムフラグが来る)

リバートされたコミットは、これらの柔軟なパターンの一部を壊したと考えられます。

## 技術的詳細

このコミットの主要な変更は、`src/cmd/go/testflag.go` ファイル内の `testFlags` 関数のロジックを元に戻すことです。この関数は、`go test` コマンドに渡された引数を解析し、`go test` 自身が処理すべきフラグと、テストバイナリに渡すべきフラグ、そしてテスト対象のパッケージ名に分割する役割を担っています。

### `testflag.go` の変更点

リバートによって、`testFlags` 関数のフラグ解析ロジックは、より柔軟な挙動に戻されました。

**変更前（リバートされたコミットの挙動）のコメント（削除された部分）:**
```go
// The usage is:
//	go test [test flags] [packages] [flags for test binary]
// Thus we process test flags (adding -test. to each) until we find a non-flag,
// which introduces the optional list of packages. We collect the package paths
// until we find another -flag, and pass that and the rest of the command line
// to the test binary untouched.
// For backwards compatibility with a poor design, if while processing test
// flags we see an unrecognized flag, we accept it as an argument to the binary.
// For this to work in general, one must say -foo=xxx not -foo xxx or else
// xxx will be taken to be a package path. As said, the design is poor.
```
このコメントは、フラグ、パッケージ、テストバイナリフラグの厳密な順序を想定しており、未知のフラグはテストバイナリに渡されるが、その際に `-foo=xxx` の形式でなければならないという制約を示唆しています。この厳密さが問題の原因でした。

**変更後（リバートによって復元された挙動）のコメント（追加された部分）:**
```go
// We allow known flags both before and after the package name list,
// to allow both
//	go test fmt -custom-flag-for-fmt-test
//	go test -x math
```
このコメントは、既知のフラグがパッケージ名のリストの前後に現れることを許容する、より柔軟な解析モデルを明確に示しています。

**`testFlags` 関数のロジックの復元:**

リバートされたコードでは、`inPkg` というブール変数と、引数のループ処理が変更されていました。このコミットでは、`inPkg` のロジックが以下のように復元されています。

1.  `inPkg` 変数は、現在パッケージ名を解析している途中であるかを示すフラグとして機能します。
2.  引数を順に処理するループ内で、引数がハイフン (`-`) で始まらない場合、それがパッケージ名であると判断されます。
    *   もし `inPkg` が `false` で、かつまだパッケージ名が一つも収集されていない場合、その引数を最初のパッケージ名として扱い、`inPkg = true` となります。
    *   `inPkg` が `true` の場合、その引数をパッケージ名として `packageNames` リストに追加します。
3.  引数がハイフン (`-`) で始まる場合、それがフラグであると判断されます。
    *   もし `inPkg` が `true` であれば、これはパッケージ名のリストが終了し、再びフラグの処理に戻ったことを意味するため、`inPkg` を `false` に設定します。
    *   `testFlag` 関数（既知の `go test` フラグを識別するヘルパー関数）を呼び出し、引数が既知のフラグであるかをチェックします。
    *   既知のフラグであれば、`go test` 自身が処理するフラグとして扱います。
    *   未知のフラグであれば、それはテストバイナリに渡されるべきフラグであると判断し、`passToTest` リストに追加します。この際、`inPkg` を `false` に設定することで、それ以降の引数がパッケージ名として誤って解釈されるのを防ぎます。

このロジックにより、`go test` はコマンドライン引数をより寛容に解釈し、パッケージ名の前後にフラグが混在するケースにも対応できるようになります。

### `src/cmd/go/go_test.go` のテストケース

テストカバレッジ関連のテストケースの変更は、`go test` コマンドの引数として `-cover` フラグを明示的に追加することで、リバートされたコミットが導入した挙動の変更に対応しています。これは、以前のコミットが `-coverprofile` や `-covermode` フラグが指定された場合に自動的にカバレッジを有効にする挙動を変更した可能性があり、リバートによってその挙動が元に戻されたため、テストコードもそれに合わせて修正されたことを示唆しています。

## コアとなるコードの解説

### `src/cmd/go/testflag.go` の `testFlags` 関数

この関数の変更は、`go test` コマンドの引数解析の柔軟性を復元することが目的です。

*   **`inPkg` 変数の導入とロジックの変更**:
    *   リバートされたコミットでは、引数を「フラグ」「パッケージ」「テストバイナリフラグ」の3つのフェーズで処理する、より線形的なアプローチが取られていました。
    *   このリバートでは、`inPkg` というブールフラグが導入され、引数のループ内で動的に現在の解析フェーズを切り替えるロジックが復元されました。
    *   `!strings.HasPrefix(args[i], "-")` (引数がハイフンで始まらない) かつ `!inPkg && packageNames == nil` の場合、最初のパッケージ名が見つかったと判断し、`inPkg = true` となります。
    *   `inPkg` が `true` の間は、ハイフンで始まらない引数はすべてパッケージ名として `packageNames` に追加されます。
    *   `inPkg` が `true` の状態でハイフンで始まる引数（フラグ）が見つかった場合、パッケージ名のリストが終了したと判断し、`inPkg = false` に戻ります。
    *   未知のフラグ (`f == nil`) が見つかった場合も、`inPkg = false` に設定されます。これは、未知のフラグの後に続く引数が、テストバイナリに渡されるフラグの引数である可能性があり、パッケージ名として誤って解釈されるのを防ぐためです。

このロジックにより、`go test fmt -custom-flag-for-fmt-test` のように、パッケージ名の後にテストバイナリ向けのフラグが続く形式や、`go test -x math` のように、`go test` 自身のフラグがパッケージ名の前に来る形式の両方が正しく処理されるようになります。

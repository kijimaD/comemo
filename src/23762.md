## 変更の背景

このコミットは、一見すると「定期的なマージ」と記述されていますが、その実態はGoコンパイラのアーキテクチャにおける大きな転換点となるSSA (Static Single Assignment) 形式バックエンドの初期実装を `dev.ssa` ブランチに統合するものです。当時のGoコンパイラは、AST (Abstract Syntax Tree) の後に、より低レベルな中間表現（RTL: Register Transfer Language）を使用してコード生成を行っていました。この方式では、高度な最適化（例えば、より効率的なレジスタ割り当て、共通部分式除去、デッドコード削除など）を適用することが困難でした。

Goチームは、コンパイラの性能と生成されるコードの品質を向上させるため、SSA形式の導入を決定しました。SSAは、データフロー解析を大幅に簡素化し、より強力な最適化を可能にする中間表現です。このコミットは、そのSSAバックエンドの構築作業が一定の段階に達し、メインの開発ライン（`origin/master`）の変更を取り込みつつ、SSAバックエンド自体のコードを統合する初期ステップとして行われました。これにより、Go 1.5でのSSAバックエンドの本格導入に向けた重要な基盤が築かれました。

## 前提知識の解説

### コンパイラの基本構造と中間表現 (IR)

コンパイラは、ソースコードを機械語に変換するソフトウェアです。一般的に、以下の主要なフェーズに分かれます。

1.  **フロントエンド**: 構文解析 (Parsing)、意味解析 (Semantic Analysis)、型チェック (Type Checking) などを行い、ソースコードを抽象構文木 (AST: Abstract Syntax Tree) などの高レベルな中間表現に変換します。
2.  **最適化**: 中間表現に対して様々な変換を施し、実行効率の高いコードを生成するための改善を行います。
3.  **バックエンド**: 最適化された中間表現をターゲットアーキテクチャの機械語（アセンブリコード）に変換します。

**中間表現 (IR)** は、これらのフェーズ間で情報をやり取りするための形式です。IRの選択は、コンパイラの設計、最適化の能力、コード生成の効率に大きな影響を与えます。

### SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの最適化において非常に強力な中間表現です。その最も重要な特性は、「各変数が一度だけ代入される」という点です。

例えば、以下のコードを考えます。

```go
x = a + b
y = x * 2
x = c + d
z = x / 2
```

これをSSA形式で表現すると、以下のようになります。

```go
x1 = a + b
y1 = x1 * 2
x2 = c + d
z1 = x2 / 2
```

このように、変数の定義が明確に区別されるため、コンパイラは以下の点で恩恵を受けます。

*   **データフロー解析の簡素化**: ある変数の値がどこで定義され、どこで使われているかを簡単に追跡できます。
*   **最適化の効率化**:
    *   **共通部分式除去 (CSE)**: 同じ計算が複数回行われている場合、一度だけ計算して結果を再利用できます。
    *   **デッドコード削除 (DCE)**: どこからも参照されない変数の代入や計算を削除できます。
    *   **定数伝播 (Constant Propagation)**: 定数値をその使用箇所に伝播させ、計算をコンパイル時に行えます。
    *   **レジスタ割り当て**: 変数のライフタイムが明確になるため、レジスタ割り当てがより効率的に行えます。
*   **Phi関数**: 複数の制御フローパス（例えばif文のthen節とelse節の合流点）が合流する際に、同じ論理的な変数に対応する異なるSSA変数を結合するために導入される特別な命令です。`x3 = Phi(x1, x2)` のように記述され、制御フローに応じて `x1` または `x2` のいずれかの値が `x3` に割り当てられることを意味します。

### Goコンパイラの当時の構造

Goコンパイラ (`cmd/compile`) は、主に以下のディレクトリにコードが格納されています。

*   `src/cmd/compile/internal/gc`: Go言語のフロントエンドと、ASTベースの中間表現を扱う主要な部分。
*   `src/cmd/compile/internal/<arch>`: 各アーキテクチャ（例: `amd64`, `arm`）固有のコード生成ロジック。
*   `src/cmd/internal/obj`: Goのアセンブラとリンカが使用するオブジェクトファイル形式と、アセンブリ命令を表現するための共通パッケージ。SSAバックエンドは最終的にこの `obj` パッケージの命令に変換されます。

このコミットは、`src/cmd/compile/internal/gc` 内にSSA形式を導入し、既存のASTベースのIRと `obj` パッケージの間の新しい層を構築するものです。

## 技術的詳細

このコミットは、GoコンパイラにSSA形式のIRを導入し、それを利用してコードを生成する初期段階の実装です。その主要な技術的側面は以下の通りです。

1.  **SSAバックエンドの導入 (`src/cmd/compile/internal/gc/ssa.go` の新規追加)**:
    *   このファイルは、GoのAST (Abstract Syntax Tree) からSSA形式への変換ロジックを実装しています。
    *   `buildssa` 関数が中心的な役割を担い、ASTノードを走査してSSAの `Value` と `Block` を構築します。
    *   `state` 構造体は、SSA構築中の現在のコンテキスト（現在のブロック、変数割り当て、ラベル、メモリ状態など）を管理します。

2.  **ASTノードのSSA変換**:
    *   `state.stmt` メソッドは、GoのASTにおけるステートメント（例: 代入 `OAS`、if文 `OIF`、forループ `OFOR`、ラベル `OLABEL`、goto `OGOTO`、return `ORETURN`）を対応するSSAオペレーションに変換します。
    *   `state.expr` メソッドは、ASTにおける式（例: 変数参照 `ONAME`、リテラル `OLITERAL`、比較 `OLT`、算術演算 `OADD`、アドレス取得 `OADDR`、間接参照 `OIND`、フィールドアクセス `ODOTPTR`、配列インデックス `OINDEX`、関数呼び出し `OCALLFUNC`）をSSA `Value` に変換します。

3.  **変数管理とPhi関数**:
    *   SSA形式の重要な要素であるPhi関数 (`ssa.OpPhi`) は、複数の制御フローパスが合流する地点で、異なるパスから来る同じ変数の定義を結合するために使用されます。
    *   `linkForwardReferences` 関数は、SSAグラフ全体を走査し、`ssa.OpFwdRef` (前方参照) として一時的に表現された変数の使用箇所を、適切な定義元またはPhi関数にリンクします。
    *   `lookupVarIncoming` と `lookupVarOutgoing` は、ブロックの入り口と出口での変数の値を決定し、必要に応じてPhi関数を挿入する再帰的なロジックを実装しています。

4.  **メモリモデルの表現**:
    *   SSAは通常、純粋なデータフローを扱いますが、Goのような言語ではメモリへの副作用（ストア操作など）も考慮する必要があります。
    *   この実装では、`.mem` という特別なSSA `Value` を導入し、メモリの状態を表現する「メモリチェーン」を通じて、メモリ操作の順序を強制しています。`ssa.OpLoad` や `ssa.OpStore` といったメモリ操作は、このメモリチェーンを引数として受け取り、新しいメモリ状態を生成します。これにより、メモリ操作の順序依存性がSSAグラフ上で明示的に表現されます。

5.  **nilチェックと境界チェック**:
    *   `nilCheck` 関数は、ポインタのnilチェックをSSA形式で表現します。ポインタがnilでないことを確認する `ssa.OpIsNonNil` オペレーションを生成し、nilであればプログラムを終了する (`s.exit` ブロックへ分岐する) 制御フローを構築します。
    *   `boundsCheck` 関数は、配列やスライスのインデックスアクセスにおける境界チェックをSSA形式で表現します。インデックスが有効範囲内にあることを確認する `ssa.OpIsInBounds` オペレーションを生成し、範囲外であればプログラムを終了する制御フローを構築します。

6.  **アセンブリコード生成**:
    *   `genssa` 関数は、構築されたSSA形式の関数 (`ssa.Func`) を受け取り、`cmd/internal/obj` パッケージのアセンブリ命令 (`obj.Prog`) に変換します。
    *   `genValue` 関数は、個々のSSA `Value` をターゲットアーキテクチャ（このコミットでは主にAMD64）のアセンブリ命令に変換します。例えば、`ssa.OpAMD64ADDQ` は `ALEAQ` (Load Effective Address) 命令に、`ssa.OpAMD64MOVQload` は `AMOVQ` (Move Quadword) 命令に変換されます。
    *   `genBlock` 関数は、SSA `Block` の制御フロー（条件分岐 `ssa.BlockIf`、無条件ジャンプ `ssa.BlockPlain` など）をアセンブリ命令に変換します。特に、分岐命令のターゲットアドレスは、SSAブロックの処理が完了した後に `branches` リストを使って解決されます。

7.  **レジスタ割り当て**:
    *   `regnum` 関数は、SSAの仮想レジスタ番号を `cmd/internal/obj` パッケージで定義されている物理レジスタ番号にマッピングします。これは、SSAバックエンドのレジスタ割り当てフェーズの一部であり、仮想的なSSA `Value` を実際のCPUレジスタに割り当てるためのインターフェースを提供します。

8.  **`src/cmd/compile/internal/gc/pgen.go` の変更**:
    *   このファイルは、コンパイラのコード生成フェーズを管理する部分です。このコミットでは、`compile` 関数内に `ssafn = buildssa(Curfn)` の呼び出しが追加され、特定の条件（関数名が `_ssa` で終わる場合）でSSAバックエンドが有効になるようにフックが設けられています。これは、SSAバックエンドがまだ実験段階であり、すべての関数にすぐに適用されるわけではないことを示唆しています。開発者は、特定の関数に対してSSAバックエンドを試すことができるようになりました。
    *   また、`fn.Nname.Sym.Name` から `fn.Func.Nname.Sym.Name` への変更は、関数の名前へのアクセス方法が、よりSSAバックエンドの内部構造に合わせた形に統一されたことを示しています。

## コアとなるコードの解説

### `src/cmd/compile/internal/gc/ssa.go` の `buildssa` 関数

`buildssa` 関数は、GoコンパイラのAST表現からSSA形式への変換プロセス全体をオーケストレートする、このコミットの最も重要な関数です。

```go
func buildssa(fn *Node) *ssa.Func {
    // SSA設定の初期化と新しいSSA関数オブジェクトの作成
    s.config = ssa.NewConfig(Thearch.Thestring, ssaExport{})
    s.f = s.config.NewFunc()
    s.f.Name = fn.Func.Nname.Sym.Name

    // エントリブロックと終了ブロックの作成
    s.f.Entry = s.f.NewBlock(ssa.BlockPlain)
    s.exit = s.f.NewBlock(ssa.BlockExit)

    // 初期値（メモリ、フレームポインタ、スタックポインタ）のSSA Valueを作成
    // .mem はメモリの状態を表す特別なValueで、メモリ操作の順序を強制する
    s.startmem = s.entryNewValue(ssa.OpArg, ssa.TypeMem, ".mem")
    s.fp = s.entryNewValue(ssa.OpFP, s.config.Uintptr, nil)
    s.sp = s.entryNewValue(ssa.OpSP, s.config.Uintptr, nil)

    // エントリブロックからSSA構築を開始し、関数のエントリコードと本体を処理
    s.startBlock(s.f.Entry)
    s.stmtList(fn.Func.Enter) // 関数のプロローグ的な処理
    s.stmtList(fn.Nbody)      // 関数本体のASTをSSAに変換

    // 現在のブロックから終了ブロックへのフォールスルーエッジを追加
    if b := s.endBlock(); b != nil {
        addEdge(b, s.exit)
    }

    // 終了ブロックの処理
    s.startBlock(s.exit)
    s.exit.Control = s.mem() // 終了ブロックの制御を最終的なメモリ状態に設定
    s.endBlock()

    // Phi関数と変数参照の解決
    s.linkForwardReferences()

    // SSAパッケージによるコンパイル（最適化など）
    ssa.Compile(s.f)

    return s.f
}
```

この関数は、`state` 構造体を使って変換中の状態を保持し、ASTの各ノードをSSAの `Value` と `Block` にマッピングしていきます。特に、メモリ操作を表現するための `.mem` や、フレームポインタ (`fp`)、スタックポインタ (`sp`) といったアーキテクチャ固有の概念もSSA `Value` として扱われる点が重要です。`linkForwardReferences` は、SSAのデータフローを完成させるために不可欠なステップであり、Phi関数の挿入と変数定義の解決を行います。最後に `ssa.Compile(s.f)` を呼び出すことで、SSAパッケージが提供する最適化パスが実行されます。

### `state.stmt` と `state.expr` 関数

これらの関数は、Go言語の構文要素（ステートメントや式）をSSA形式の操作に変換する役割を担います。

*   **`state.stmt(n *Node)`**:
    *   `OIF` (if文) の処理では、条件式を `s.expr` でSSA `Value` に変換し、その結果に基づいて `ssa.BlockIf` タイプのブロックを作成します。真偽それぞれのパスに対応する新しいSSAブロック (`bThen`, `bElse`) を生成し、制御フローを構築します。
    *   `OAS` (代入) の処理では、代入対象の変数がSSA可能 (`canSSA`) であれば、その変数の現在のSSA `Value` を更新します。そうでなければ、メモリへのストア操作 (`ssa.OpStore`) として扱われ、メモリチェーンを通じて副作用が表現されます。
    *   `OFOR` (forループ) の処理も同様に、条件式とループ本体、インクリメント部分をSSAブロックと制御フローとして表現します。

*   **`state.expr(n *Node)`**:
    *   `ONAME` (変数参照) の場合、変数がSSA可能であれば `s.variable` を使ってそのSSA `Value` を取得します。SSA可能でなければ、メモリからのロード操作 (`ssa.OpLoad`) として扱われます。
    *   `OLITERAL` (リテラル) の場合、定数値を表すSSA `Value` (`ssa.OpConst`) を生成します。
    *   `OCALLFUNC` (関数呼び出し) の場合、引数の評価後、`ssa.OpStaticCall` (静的呼び出し) または `ssa.OpClosureCall` (クロージャ呼び出し) を生成し、メモリチェーンを更新します。関数の戻り値はスタックからロードされます。

### `genssa` 関数

`genssa` 関数は、SSA形式のグラフを具体的なアセンブリ命令のリスト (`obj.Prog`) に変換するバックエンドの主要部分です。

```go
func genssa(f *ssa.Func, ptxt *obj.Prog, gcargs, gclocals *Sym) {
    // 各SSAブロックの開始アドレスを記録するための配列
    bstart := make([]*obj.Prog, f.NumBlocks())
    // 未解決の分岐命令を保持するリスト
    var branches []branch

    // 各SSAブロックを順に処理
    for i, b := range f.Blocks {
        bstart[b.ID] = Pc // 現在のプログラムカウンタをブロック開始アドレスとして記録
        // ブロック内の各SSA Valueをアセンブリ命令に変換
        for _, v := range b.Values {
            genValue(v)
        }
        // ブロックの制御フローをアセンブリ命令に変換し、未解決の分岐を記録
        branches = genBlock(b, next, branches)
    }

    // 未解決の分岐ターゲットを解決
    for _, br := range branches {
        br.p.To.Val = bstart[br.b.ID]
    }

    // 関数の終端処理
    Pc.As = obj.ARET // 最終命令をARET (Return) に設定
    // ... (GC関連のシンボル生成など)
}
```

この関数は、SSA形式のグラフを具体的なアセンブリ命令のリスト (`obj.Prog`) に変換します。各SSAブロック内の `Value` を `genValue` で命令に変換し、ブロック間の制御フローを `genBlock` で処理します。特に、分岐命令のターゲットは後で解決されるため、`branches` リストに一時的に保持されます。これは、コンパイラのバックエンドにおける典型的なアプローチであり、前方参照の解決に似ています。

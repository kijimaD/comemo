# [インデックス 25059] ファイルの概要

このコミットは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおいて、SSA形式で表現できない（un-SSAableな）オブジェクトの扱いを改善するものです。具体的には、特定の型を持つオブジェクトがSSA形式に変換される際に発生していた「not lowered: Load ARRAY PTR64 mem」というエラーを修正し、これらのオブジェクトが適切にメモリ間で移動されるように変更を加えています。

## 変更の背景

Goコンパイラは、コードの最適化のためにSSA（Static Single Assignment）形式を使用しています。SSA形式では、各変数が一度だけ代入されるという特性を持ち、データフロー解析や最適化を容易にします。しかし、すべてのGoの型やオブジェクトがSSA形式で効率的に表現できるわけではありません。特に、大きな構造体や配列、ポインタを含む複雑な型など、メモリ上で直接操作されるべきオブジェクトは、SSAレジスタに格納するよりもメモリ間で直接移動する方が効率的であるか、あるいはSSA形式での表現が困難な場合があります。

このコミット以前は、SSA形式で扱いにくい（un-SSAableな）オブジェクトがSSAバックエンドに渡された際に、コンパイラがそれらを適切に処理できず、「not lowered: Load ARRAY PTR64 mem」のようなエラーが発生していました。このエラーは、コンパイラが特定のメモリ操作（`Load ARRAY PTR64 mem`）を低レベルの機械語命令に「lowering」（変換）できないことを示しています。これは、SSA形式の制約と、実際のメモリ操作の間のギャップに起因していました。

この変更の目的は、un-SSAableなオブジェクトをSSA形式の制約から外し、メモリ間での直接的な移動（`Move`操作）として扱うことで、コンパイラがこれらのオブジェクトを正しく処理し、上記のエラーを解消することにあります。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA形式は、コンパイラの最適化段階で中間表現として用いられるプログラム表現の一種です。この形式では、プログラム中の各変数が一度だけ代入されるという厳格なルールがあります。例えば、`x = a + b; x = x * c;` というコードは、SSA形式では `x1 = a + b; x2 = x1 * c;` のように変換され、各代入が新しい変数に割り当てられます。これにより、データフロー解析が単純化され、デッドコード削除、共通部分式除去、レジスタ割り当てなどの最適化が容易になります。

Goコンパイラは、Go 1.7以降、最適化の主要な部分でSSAバックエンドを使用しています。

### 2. GoコンパイラのバックエンドとLowering

Goコンパイラは、ソースコードを解析し、抽象構文木（AST）を生成した後、中間表現（IR）に変換します。SSA形式はこのIRの一つです。SSAバックエンドは、このSSA形式のコードに対して様々な最適化を適用し、最終的にターゲットアーキテクチャの機械語に近い低レベルのIRに変換します。この低レベルのIRへの変換プロセスを「lowering」と呼びます。loweringの過程で、SSA形式の抽象的な操作（例: `Load`、`Store`）は、実際のCPUレジスタやメモリ操作に対応する具体的な命令に変換されます。

### 3. `Load ARRAY PTR64 mem` エラー

このエラーメッセージは、GoコンパイラのSSAバックエンドが、特定のメモリロード操作（`Load`）を低レベルの命令に変換できなかったことを示しています。
*   `Load`: メモリから値を読み出す操作。
*   `ARRAY`: 配列型。
*   `PTR64`: 64ビットポインタ。
*   `mem`: メモリ状態を表すSSA値。SSA形式では、メモリへの読み書きはメモリ状態を引数として受け取り、新しいメモリ状態を返す操作としてモデル化されます。

このエラーは、コンパイラが配列への64ビットポインタを介したロード操作を、SSA形式のルール内で適切に処理し、最終的に機械語に変換する方法を見つけられなかった場合に発生します。これは通常、SSA形式で表現するには複雑すぎる、またはSSAのセマンティクスに合わないメモリ操作が原因です。

### 4. `un-SSAable` オブジェクト

「un-SSAable」とは、SSA形式の制約（各変数が一度だけ代入される）に適合しない、または適合させることが非効率的なオブジェクトや型を指します。例えば、大きな構造体や配列全体をSSAレジスタに格納して操作するのではなく、メモリ上で直接コピーしたり移動したりする方が自然な場合があります。このようなオブジェクトは、SSA形式のデータフロー解析の対象から外し、より低レベルのメモリ操作として扱う必要があります。

## 技術的詳細

このコミットの核心は、GoコンパイラのSSAバックエンドが、SSA形式で効率的に扱えない型（un-SSAableな型）を識別し、それらの型を持つオブジェクトのメモリ操作を特別に処理するように変更することです。

1.  **`CanSSA` メソッドの導入**:
    `src/cmd/compile/internal/ssa/config.go` の `TypeSource` インターフェースに `CanSSA(t Type) bool` メソッドが追加されました。このメソッドは、特定の型 `t` がSSA形式で扱えるかどうかを判定する役割を担います。
    `src/cmd/compile/internal/gc/ssa.go` には、このインターフェースの実装として `ssaExport.CanSSA` が追加され、`canSSAType` 関数を呼び出して実際の判定を行います。これにより、コンパイラのフロントエンド（`gc`パッケージ）が、SSAバックエンドに渡す型がSSA可能かどうかをSSAバックエンドに問い合わせることができるようになります。

2.  **`generic.rules` の変更**:
    `src/cmd/compile/internal/ssa/gen/generic.rules` は、SSA値の書き換えルールを定義するファイルです。このファイルには、`Store` と `Load` の組み合わせを `Move` 操作に変換するルールが含まれています。
    変更前は、`size > config.IntSize` (オブジェクトのサイズが整数サイズより大きい場合) という条件で、大きなオブジェクトの `Store(Load)` を `Move` に変換していました。
    変更後は、この条件が `!config.fe.CanSSA(t)` (型 `t` がSSA可能でない場合) に置き換えられました。これにより、オブジェクトのサイズに関わらず、SSA形式で扱いにくい型を持つオブジェクトのメモリ間コピーが `Move` 操作として扱われるようになります。これは、`mem->mem copies` (メモリからメモリへのコピー) としてコメントされています。

    *   `Store [size] dst (Load <t> src mem) mem`
    *   `Store [size] dst (Load <t> src mem) (VarDef {x} mem)`

    これらのパターンは、`dst` に `src` から `size` バイトのデータをロードしてストアする操作を表します。`Load <t> src mem` の `<t>` はロードされる値の型を示します。新しいルールでは、この型 `t` が `CanSSA` で `false` を返す場合に、この操作全体を `Move [size] dst src mem` に変換します。

3.  **`rewritegeneric.go` の変更**:
    `src/cmd/compile/internal/ssa/rewritegeneric.go` は、`generic.rules` に基づいて生成されるコードの一部であり、SSA値の書き換えロジックを含んでいます。このファイル内の `rewriteValuegeneric` 関数において、`Store` 操作を `Move` に書き換える部分の条件が、`size > config.IntSize` から `!config.fe.CanSSA(t)` に変更されています。これは `generic.rules` の変更を反映したものです。
    また、`OpEqInter` と `OpEqSlice` の `result` 行のコメントのスペース調整や、`goto` ラベルの変更（これはコード生成ツールが内部的に使用するもので、機能的な変更ではない）も行われています。

これらの変更により、コンパイラはSSA形式で扱いにくいオブジェクトを検出し、それらをSSAレジスタではなくメモリ間で直接移動させる `Move` 操作として扱うことで、「not lowered: Load ARRAY PTR64 mem」のようなエラーを回避し、コンパイルプロセスを正常に完了できるようになります。

## コアとなるコードの解説

このコミットの最も重要な変更は、SSAバックエンドが型に基づいてオブジェクトのSSA可能性を判断し、それに応じてメモリ操作を最適化する能力を獲得した点です。

1.  **`TypeSource` インターフェースへの `CanSSA` 追加**:
    `TypeSource` は、SSAバックエンドが型の情報を取得するためのインターフェースです。ここに `CanSSA(t Type) bool` が追加されたことで、SSAバックエンドはコンパイラのフロントエンド（`gc`パッケージ）に対して、特定の型がSSA形式で扱えるかどうかを問い合わせることができるようになりました。これは、SSAバックエンドが型の特性に基づいて異なる最適化戦略を適用するための重要なフックとなります。

2.  **`generic.rules` における `!config.fe.CanSSA(t)` 条件**:
    `generic.rules` は、SSA中間表現のパターンマッチングと書き換えを定義するものです。
    変更前のルール:
    ```
    (Store [size] dst (Load src mem) mem) && size > config.IntSize -> (Move [size] dst src mem)
    ```
    これは、「サイズが `config.IntSize` より大きいオブジェクトのロードとストアは、`Move` 操作に変換する」という意味でした。これは、大きなオブジェクトはレジスタに収まらないため、メモリ間で直接移動させるべきだというヒューリスティックに基づいています。

    変更後のルール:
    ```
    (Store [size] dst (Load <t> src mem) mem) && !config.fe.CanSSA(t) -> (Move [size] dst src mem)
    ```
    この新しいルールは、「型 `t` がSSA可能でないオブジェクトのロードとストアは、`Move` 操作に変換する」という意味になります。`config.fe` は `TypeSource` インターフェースの実装（`ssaExport`）を指し、`CanSSA(t)` を呼び出します。
    この変更により、オブジェクトの物理的なサイズだけでなく、その型の性質（例えば、ポインタを含む複雑な構造体など）に基づいて、SSA形式での扱いやすさを判断できるようになりました。SSA可能でないと判断されたオブジェクトは、SSAレジスタに割り当てられるのではなく、メモリからメモリへの直接的なコピー（`Move`）として扱われるため、コンパイラは「not lowered」エラーを回避できます。

このメカニズムにより、GoコンパイラはSSA形式の強力な最適化能力を維持しつつ、SSA形式に不向きなオブジェクトに対しても堅牢なコード生成が可能になりました。

# [インデックス 22040] ファイルの概要

このコミットは、Goコンパイラのフロントエンドである`cmd/gc`内の`ordersafeexpr`関数における`fatal`呼び出しの扱いを調整するものです。特に、C言語からGo言語への変換ツールである`c2go`が生成するコードとの整合性を改善することを目的としています。`fatal`関数が呼び出し元に戻らない（non-returning）という特性を`c2go`が正しく認識し、それによって発生するGo言語の関数における「戻り値の欠落」の問題を解決するために、コードの配置が変更されました。

## 元コミット内容

`cmd/gc`の`ordersafeexpr`関数におけるデフォルトの`fatal`呼び出しを`c2go`のために調整しました。
`c2go`は`fatal`呼び出しの後にフォールスルー（処理が継続すること）を配置していましたが、`fatal`が戻らないことを`c2go`が認識するように変更したところ、変換されたGo関数で戻り値が欠落するという問題が発生しました。
C言語とGo言語のコードが一致するように、コードの配置を少し変更しました。

## 変更の背景

この変更の背景には、Goコンパイラの一部が元々C言語で書かれており、それをGo言語に変換するプロセスが存在するという歴史的経緯があります。`c2go`は、このC言語で書かれたコンパイラコードをGo言語に自動変換するためのツールです。

問題は、C言語の`fatal`関数（通常、致命的なエラーが発生した場合にプログラムを終了させる関数）の挙動と、`c2go`がその挙動をGo言語に変換する際の認識のずれにありました。

1.  **C言語の`fatal`の挙動**: C言語では、`fatal`のような非復帰関数（non-returning function）が呼び出されると、その関数から呼び出し元に戻ることはありません。そのため、`fatal`の後に続くコードは「到達不能（unreachable）」と見なされ、コンパイラは通常、その後のコードの実行パスについて考慮しません。
2.  **`c2go`の初期の挙動**: `c2go`は当初、`fatal`呼び出しの後に続くC言語のコードを、Go言語のコードにそのまま変換していました。これは、`fatal`が戻らないことを`c2go`が完全に理解していなかったため、Go言語の関数内で`fatal`が呼び出された後も処理が継続するかのようにコードを生成してしまっていたことを意味します。
3.  **`c2go`の改善と新たな問題**: `c2go`が`fatal`が戻らない関数であることを認識するように改善されました。これにより、`fatal`の後に続くコードは到達不能であると正しく判断されるようになりました。しかし、この変更によって、Go言語の関数がすべての実行パスで値を返す必要があるというGoの言語仕様との間に不整合が生じました。具体的には、`fatal`呼び出しのパスでは関数が値を返さないと見なされ、Goコンパイラが「missing return」（戻り値の欠落）エラーを報告するようになりました。
4.  **本コミットの目的**: このコミットは、C言語の元の意図（`fatal`の後は到達不能）と、Go言語のコンパイラが求める「すべてのパスで戻り値を返す」という要件を両立させるために行われました。`ordersafeexpr`関数内で`fatal`呼び出しの後に`return nil`を追加することで、Goコンパイラが戻り値の欠落を検出しないようにしつつ、実際には`fatal`が呼び出されればその`return nil`には到達しないという論理的な整合性を保っています。

## 前提知識の解説

### `c2go`

`c2go`は、C言語で書かれたコードをGo言語のコードに自動変換するためのツールです。Go言語の初期のコンパイラはC言語で書かれていましたが、Go言語自体でコンパイラを書き直す（セルフホスト化する）という目標がありました。この目標を達成するために、既存のC言語コードベースをGo言語に移行する際に`c2go`が利用されました。`c2go`は単なる構文変換だけでなく、C言語のポインタやメモリ管理の概念をGo言語のイディオムに変換する複雑な処理を行います。

### `cmd/gc`

`cmd/gc`は、Go言語の公式コンパイラのフロントエンド部分を指します。Goコンパイラは複数のステージに分かれており、`cmd/gc`は主に以下の役割を担います。

*   **構文解析 (Parsing)**: Goのソースコードを解析し、抽象構文木（AST）を生成します。
*   **型チェック (Type Checking)**: ASTに対して型チェックを行い、型の一貫性を検証します。
*   **中間表現への変換 (IR Generation)**: ASTをコンパイラ内部の中間表現（IR）に変換します。
*   **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用します。
*   **コード生成 (Code Generation)**: 最終的に、ターゲットアーキテクチャの機械語コードを生成します。

このコミットで変更されている`order.c`は、`cmd/gc`の一部であり、主に式の評価順序付け（ordering）や、一時変数の導入など、コード生成の前段階の処理を担当しています。

### `ordersafeexpr`関数

`ordersafeexpr`は、Goコンパイラの`cmd/gc`内で使用される関数で、式の評価順序を安全に決定し、必要に応じて一時変数を導入する役割を担います。コンパイラは、複雑な式を評価する際に、副作用の順序や、特定の操作が安全に実行できるかどうかを考慮する必要があります。この関数は、与えられた`Node`（抽象構文木のノード）が安全に評価できる式であるかを判断し、必要であればその式を評価するための追加の処理（例えば、一時変数への代入）を生成します。

### `fatal`関数と非復帰関数（Non-returning function）

`fatal`関数は、Goコンパイラ（`cmd/gc`）の内部で、回復不能なエラーが発生した場合にプログラムの実行を即座に終了させるために使用されるユーティリティ関数です。Go言語の標準ライブラリにも`log.Fatal`のような関数がありますが、コンパイラ内部の`fatal`はより低レベルで、通常はエラーメッセージを出力してプログラムを終了させます。

非復帰関数（non-returning function）とは、その関数が呼び出し元に制御を戻さないことを意味します。C言語では、`exit()`や`abort()`、あるいはコンパイラ固有の`fatal`のような関数がこれに該当します。Go言語では、`panic()`を呼び出す関数や、無限ループに入る関数、あるいは`os.Exit()`を呼び出す関数などが非復帰関数と見なされることがあります。

Goコンパイラは、関数のすべての実行パスが戻り値を返すことを期待します。しかし、非復帰関数が呼び出されるパスでは、実際には戻り値が返されることはありません。このため、コンパイラは非復帰関数の後に続くコードが到達不能であることを認識する必要があります。もし認識できない場合、コンパイラは「missing return statement」（戻り値ステートメントの欠落）エラーを報告する可能性があります。

## 技術的詳細

このコミットの核心は、`c2go`がC言語の`fatal`呼び出しをGo言語に変換する際の挙動の不一致を解消することにあります。

元のC言語の`ordersafeexpr`関数には、`switch`文の`default`ケースで`fatal`が呼び出されていました。C言語のコンパイラは、`fatal`が非復帰関数であることを認識するため、この`default`ケースの後に続くコード（もしあれば）は到達不能と見なされます。

しかし、`c2go`がこのCコードをGoに変換する際、初期のバージョンでは`fatal`が非復帰関数であることを完全に理解していませんでした。そのため、`fatal`呼び出しの後に処理が「フォールスルー」するかのようにGoコードを生成してしまい、Goの関数がすべてのパスで戻り値を返すという要件を満たさない可能性がありました。

コミットメッセージによると、`c2go`は「`fatal`が戻らないことを知るように変更された」とのことです。これは`c2go`の内部ロジックが改善され、C言語の非復帰関数をGo言語の非復帰関数として正しく扱うようになったことを意味します。

この改善により、`c2go`が生成するGoコードでは、`fatal`呼び出しの後に続くコードは到達不能であるとGoコンパイラに認識されるようになりました。しかし、これが新たな問題を引き起こしました。Go言語の関数は、すべての可能な実行パスで値を返す必要があります。`ordersafeexpr`関数は`Node*`を返す関数であり、`fatal`が呼び出されるパスでは、Goコンパイラは明示的な`return`ステートメントがないと「missing return」エラーを報告するようになりました。

このコミットは、この問題を解決するために、`fatal`呼び出しを`switch`文の`default`ケースから関数の末尾に移動させ、その直後に`return nil; // not reached`というコメント付きの`return`ステートメントを追加しました。

*   **`switch`文からの`default`ケースの削除**: これにより、`switch`文の各ケースが明示的に処理され、`default`ケースでの`fatal`呼び出しがなくなります。
*   **関数の末尾への`fatal`呼び出しの移動**: `ordersafeexpr`関数が、既知の安全な式（`ONAME`, `OLITERAL`など）を処理し、それらがすべて処理された後に、それでも`fatal`が呼び出されるべき状況（つまり、予期しない`n->op`が渡された場合）にのみ`fatal`が呼び出されるようにします。
*   **`return nil; // not reached`の追加**: `fatal`呼び出しの直後に`return nil;`を追加することで、Goコンパイラに対して「このパスでも関数は値を返している」と明示的に伝えます。しかし、`// not reached`というコメントが示すように、実際には`fatal`が呼び出されればこの`return nil`には到達しません。これは、Goコンパイラの静的解析の要件を満たしつつ、実行時の挙動を変えないための慣用的なパターンです。

この変更により、C言語の元の意図（`fatal`が呼び出されれば関数は終了する）と、Go言語のコンパイラが求める文法的な要件（すべてのパスで戻り値が必要）が両立するようになりました。

## コアとなるコードの解説

### 変更前 (`-` で示される行)

```c
 	switch(n->op) {
 	default:
 		fatal("ordersafeexpr %O", n->op);
-
 	case ONAME:
 	case OLITERAL:
 		return n;
```

変更前は、`ordersafeexpr`関数内の`switch`文に`default`ケースが存在し、そこで`fatal`関数が呼び出されていました。これは、`n->op`（抽象構文木のノードの操作タイプ）が`switch`文の他の`case`で処理されない場合に、予期せぬ操作タイプが渡されたことを示す致命的なエラーとしてプログラムを終了させるためのものでした。

C言語の文脈では、`fatal`が非復帰関数であるため、この`default`ケースが実行された場合、その後のコードは実行されません。しかし、`c2go`がこのパターンをGoに変換する際に、`fatal`の後に処理がフォールスルーするかのように誤解釈し、Goコンパイラが「戻り値の欠落」を報告する原因となっていました。

### 変更後 (`+` で示される行)

```c
 	switch(n->op) {
 	case ONAME:
 	case OLITERAL:
 		return n;
 	}
+
+	fatal("ordersafeexpr %O", n->op);
+	return nil; // not reached
}
```

変更後では、`switch`文から`default`ケースが削除されました。これにより、`switch`文は明示的に処理される`case`のみを持つことになります。

そして、`switch`文のブロックが終了した直後、つまり`ordersafeexpr`関数の末尾近くに、`fatal`呼び出しが移動されました。この`fatal`呼び出しは、`switch`文のどの`case`にもマッチしなかった場合にのみ実行される論理的な位置に配置されています。

さらに重要なのは、`fatal("ordersafeexpr %O", n->op);`の直後に`return nil; // not reached`が追加された点です。

*   **`fatal("ordersafeexpr %O", n->op);`**: これは、`switch`文で処理されなかった未知の`n->op`が渡された場合に、引き続き致命的なエラーとしてプログラムを終了させる役割を担います。
*   **`return nil; // not reached`**: この行は、Goコンパイラの静的解析が「すべての実行パスで関数が値を返す」という要件を満たすために追加されました。実際には、直前の`fatal`関数が呼び出されればプログラムは終了するため、この`return nil`には到達しません。`// not reached`というコメントは、このコードが論理的には到達不能であることを開発者に示しています。これは、Go言語で非復帰関数を扱う際の一般的なイディオムであり、コンパイラエラーを回避しつつ、コードの意図を明確にするためのものです。

この変更により、`c2go`が生成するGoコードは、Goコンパイラの「戻り値の欠落」エラーに遭遇することなく、C言語の元のロジック（予期せぬ入力でプログラムを終了させる）を正しく表現できるようになりました。

## 前提知識の解説

### `c2go`

`c2go`は、C言語で書かれたコードをGo言語のコードに自動変換するためのツールです。Go言語の初期のコンパイラはC言語で書かれていましたが、Go言語自体でコンパイラを書き直す（セルフホスト化する）という目標がありました。この目標を達成するために、既存のC言語コードベースをGo言語に移行する際に`c2go`が利用されました。特に、Go言語の創設者の一人であるRuss Cox氏がGoコンパイラのブートストラップのために開発した`c2go`ツールが知られています。`c2go`は単なる構文変換だけでなく、C言語のポインタやメモリ管理の概念をGo言語のイディオムに変換する複雑な処理を行います。

### `cmd/gc`

`cmd/gc`は、Go言語の公式コンパイラのフロントエンド部分を指します。Goコンパイラは複数のステージに分かれており、`cmd/gc`は主に以下の役割を担います。

*   **構文解析 (Parsing)**: Goのソースコードを解析し、抽象構文木（AST）を生成します。
*   **型チェック (Type Checking)**: ASTに対して型チェックを行い、型の一貫性を検証します。
*   **中間表現への変換 (IR Generation)**: ASTをコンパイラ内部の中間表現（IR）に変換します。
*   **最適化 (Optimization)**: 中間表現に対して様々な最適化を適用します。
*   **コード生成 (Code Generation)**: 最終的に、ターゲットアーキテクチャの機械語コードを生成します。

このコミットで変更されている`order.c`は、`cmd/gc`の一部であり、主に式の評価順序付け（ordering）や、一時変数の導入など、コード生成の前段階の処理を担当しています。

### `ordersafeexpr`関数

`ordersafeexpr`は、Goコンパイラの`cmd/gc`内で使用される関数で、式の評価順序を安全に決定し、必要に応じて一時変数を導入する役割を担います。コンパイラは、複雑な式を評価する際に、副作用の順序や、特定の操作が安全に実行できるかどうかを考慮する必要があります。この関数は、与えられた`Node`（抽象構文木のノード）が安全に評価できる式であるかを判断し、必要であればその式を評価するための追加の処理（例えば、一時変数への代入）を生成します。

### `fatal`関数と非復帰関数（Non-returning function）

`fatal`関数は、Goコンパイラ（`cmd/gc`）の内部で、回復不能なエラーが発生した場合にプログラムの実行を即座に終了させるために使用されるユーティリティ関数です。Go言語の標準ライブラリにも`log.Fatal`のような関数がありますが、コンパイラ内部の`fatal`はより低レベルで、通常はエラーメッセージを出力してプログラムを終了させます。

非復帰関数（non-returning function）とは、その関数が呼び出し元に制御を戻さないことを意味します。C言語では、`exit()`や`abort()`、あるいはコンパイラ固有の`fatal`のような関数がこれに該当します。Go言語では、`panic()`を呼び出す関数や、無限ループに入る関数、あるいは`os.Exit()`を呼び出す関数などが非復帰関数と見なされることがあります。

Goコンパイラは、関数のすべての実行パスが戻り値を返すことを期待します。しかし、非復帰関数が呼び出されるパスでは、実際には戻り値が返されることはありません。このため、コンパイラは非復帰関数の後に続くコードが到達不能であることを認識する必要があります。もし認識できない場合、コンパイラは「missing return statement」（戻り値ステートメントの欠落）エラーを報告する可能性があります。

## 技術的詳細

このコミットの核心は、`c2go`がC言語の`fatal`呼び出しをGo言語に変換する際の挙動の不一致を解消することにあります。

元のC言語の`ordersafeexpr`関数には、`switch`文の`default`ケースで`fatal`が呼び出されていました。C言語のコンパイラは、`fatal`が非復帰関数であることを認識するため、この`default`ケースの後に続くコード（もしあれば）は到達不能と見なされます。

しかし、`c2go`がこのCコードをGoに変換する際、初期のバージョンでは`fatal`が非復帰関数であることを完全に理解していませんでした。そのため、`fatal`呼び出しの後に処理が「フォールスルー」するかのようにGoコードを生成してしまい、Goの関数がすべてのパスで戻り値を返すという要件を満たさない可能性がありました。

コミットメッセージによると、`c2go`は「`fatal`が戻らないことを知るように変更された」とのことです。これは`c2go`の内部ロジックが改善され、C言語の非復帰関数をGo言語の非復帰関数として正しく扱うようになったことを意味します。

この改善により、`c2go`が生成するGoコードでは、`fatal`呼び出しの後に続くコードは到達不能であるとGoコンパイラに認識されるようになりました。しかし、これが新たな問題を引き起こしました。Go言語の関数は、すべての可能な実行パスで値を返す必要があります。`ordersafeexpr`関数は`Node*`を返す関数であり、`fatal`が呼び出されるパスでは、Goコンパイラは明示的な`return`ステートメントがないと「missing return」エラーを報告するようになりました。

このコミットは、この問題を解決するために、`fatal`呼び出しを`switch`文の`default`ケースから関数の末尾に移動させ、その直後に`return nil; // not reached`というコメント付きの`return`ステートメントを追加しました。

*   **`switch`文からの`default`ケースの削除**: これにより、`switch`文の各ケースが明示的に処理され、`default`ケースでの`fatal`呼び出しがなくなります。
*   **関数の末尾への`fatal`呼び出しの移動**: `ordersafeexpr`関数が、既知の安全な式（`ONAME`, `OLITERAL`など）を処理し、それらがすべて処理された後に、それでも`fatal`が呼び出されるべき状況（つまり、予期しない`n->op`が渡された場合）にのみ`fatal`が呼び出されるようにします。
*   **`return nil; // not reached`の追加**: `fatal`呼び出しの直後に`return nil;`を追加することで、Goコンパイラに対して「このパスでも関数は値を返している」と明示的に伝えます。しかし、`// not reached`というコメントが示すように、実際には`fatal`が呼び出されればこの`return nil`には到達しません。これは、Goコンパイラの静的解析の要件を満たしつつ、実行時の挙動を変えないための慣用的なパターンです。

この変更により、C言語の元の意図（`fatal`が呼び出されれば関数は終了する）と、Go言語のコンパイラが求める文法的な要件（すべてのパスで戻り値が必要）が両立するようになりました。

## コアとなるコードの解説

### 変更前 (`-` で示される行)

```c
 	switch(n->op) {
 	default:
 		fatal("ordersafeexpr %O", n->op);
-
 	case ONAME:
 	case OLITERAL:
 		return n;
```

変更前は、`ordersafeexpr`関数内の`switch`文に`default`ケースが存在し、そこで`fatal`関数が呼び出されていました。これは、`n->op`（抽象構文木のノードの操作タイプ）が`switch`文の他の`case`で処理されない場合に、予期せぬ操作タイプが渡されたことを示す致命的なエラーとしてプログラムを終了させるためのものでした。

C言語の文脈では、`fatal`が非復帰関数であるため、この`default`ケースが実行された場合、その後のコードは実行されません。しかし、`c2go`がこのパターンをGoに変換する際に、`fatal`の後に処理がフォールスルーするかのように誤解釈し、Goコンパイラが「戻り値の欠落」を報告する原因となっていました。

### 変更後 (`+` で示される行)

```c
 	switch(n->op) {
 	case ONAME:
 	case OLITERAL:
 		return n;
 	}
+
+	fatal("ordersafeexpr %O", n->op);
+	return nil; // not reached
}
```

変更後では、`switch`文から`default`ケースが削除されました。これにより、`switch`文は明示的に処理される`case`のみを持つことになります。

そして、`switch`文のブロックが終了した直後、つまり`ordersafeexpr`関数の末尾近くに、`fatal`呼び出しが移動されました。この`fatal`呼び出しは、`switch`文のどの`case`にもマッチしなかった場合にのみ実行される論理的な位置に配置されています。

さらに重要なのは、`fatal("ordersafeexpr %O", n->op);`の直後に`return nil; // not reached`が追加された点です。

*   **`fatal("ordersafeexpr %O", n->op);`**: これは、`switch`文で処理されなかった未知の`n->op`が渡された場合に、引き続き致命的なエラーとしてプログラムを終了させる役割を担います。
*   **`return nil; // not reached`**: この行は、Goコンパイラの静的解析が「すべての実行パスで関数が値を返す」という要件を満たすために追加されました。実際には、直前の`fatal`関数が呼び出されればプログラムは終了するため、この`return nil`には到達しません。`// not reached`というコメントは、このコードが論理的には到達不能であることを開発者に示しています。これは、Go言語で非復帰関数を扱う際の一般的なイディオムであり、コンパイラエラーを回避しつつ、コードの意図を明確にするためのものです。

この変更により、`c2go`が生成するGoコードは、Goコンパイラの「戻り値の欠落」エラーに遭遇することなく、C言語の元のロジック（予期せぬ入力でプログラムを終了させる）を正しく表現できるようになりました。

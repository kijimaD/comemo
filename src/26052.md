## 元コミット内容

`runtime: check for spanBytesAlloc underflow`

このコミットは、Goランタイムのガベージコレクタが使用する `mheap_.spanBytesAlloc` カウンタが負の値になる（アンダーフローする）可能性に対処するためのものです。具体的には、`reimburseSweepCredit` 関数内でこのカウンタから値を減算した後、その結果が0未満になった場合に `throw` を呼び出してランタイムパニックを発生させるチェックを追加しています。

## 変更の背景

Goのガベージコレクタは、メモリの割り当てと解放を追跡するために様々な内部カウンタを使用しています。`mheap_.spanBytesAlloc` は、ヒープ上で現在割り当てられているバイト数を追跡する重要なカウンタの一つです。このカウンタは、メモリが割り当てられると増加し、解放されると減少します。

`reimburseSweepCredit` 関数は、ガベージコレクションのスイープフェーズ中に、再利用可能になったメモリ（`unusableBytes`）を `mheap_.spanBytesAlloc` から減算することで、割り当て済みバイト数のクレジットを調整する役割を担っています。

通常、`mheap_.spanBytesAlloc` は常に非負であるべきです。しかし、特定の競合状態やロジックのバグにより、解放されるバイト数（`unusableBytes`）が実際に割り当てられているバイト数よりも多く計算されてしまい、結果として `mheap_.spanBytesAlloc` が負の値になる可能性がありました。このようなアンダーフローは、Goランタイムのメモリ管理ロジックにおける深刻な不整合を示唆しており、未定義の動作やクラッシュにつながる可能性があります。

このコミットは、このような潜在的な問題を早期に検出し、ランタイムパニックとして報告することで、デバッグを容易にし、システムの安定性を向上させることを目的としています。

## 前提知識の解説

### Goランタイムとガベージコレクタ (GC)

Goランタイムは、Goプログラムの実行を管理するシステムです。これには、スケジューラ、メモリマネージャ、ガベージコレクタなどが含まれます。GoのGCは、並行マーク＆スイープ方式を採用しており、プログラムの実行と並行して動作し、使用されなくなったメモリを自動的に回収します。

### ヒープ (Heap)

Goプログラムが動的にメモリを割り当てる領域です。`make` や `new` などで確保されたオブジェクトはヒープに配置されます。

### `mheap_` 構造体

Goランタイムのメモリ管理の中核をなすグローバルな構造体です。ヒープ全体の状態、アロケーションの統計、GCの進行状況などを管理します。`mheap_.spanBytesAlloc` はこの構造体の一部です。

### `mspan` (Memory Span)

Goのメモリ管理の基本的な単位です。ヒープは `mspan` と呼ばれる連続したメモリブロックに分割されます。各 `mspan` は特定のサイズのオブジェクトを格納するために使用されるか、または大きなオブジェクトのために単独で使用されます。

### `spanBytesAlloc`

`mheap_` 構造体内のフィールドで、現在ヒープ上でユーザーデータのために割り当てられているバイト数の合計を追跡します。これはGCのトリガー条件やメモリ使用量の統計に利用される重要なカウンタです。

### `reimburseSweepCredit` 関数

ガベージコレクションのスイープフェーズ中に呼び出される関数です。スイープフェーズでは、マークされなかった（つまり到達不能な）オブジェクトが占めていたメモリが解放されます。この関数は、解放されたメモリのバイト数（`unusableBytes`）を `mheap_.spanBytesAlloc` から減算し、割り当て済みバイト数の総計を更新します。これにより、GCはヒープの実際の使用状況を正確に把握できます。

### `atomic.Xadd64`

Goの `sync/atomic` パッケージに含まれる関数で、64ビット整数に対してアトミックな加算（または減算）操作を実行します。アトミック操作は、複数のゴルーチンが同時に同じメモリ位置にアクセスしても、データ競合が発生しないことを保証します。ここでは、`mheap_.spanBytesAlloc` の値を安全に更新するために使用されています。

### `throw` 関数

Goランタイム内部で使用される関数で、回復不能なエラーが発生した場合にプログラムを終了させます。これは通常、深刻な内部不整合やバグが検出されたときに呼び出され、スタックトレースを出力してデバッグを支援します。

## 技術的詳細

このコミットの核心は、`reimburseSweepCredit` 関数における `mheap_.spanBytesAlloc` の更新ロジックにあります。

元のコードでは、`atomic.Xadd64(&mheap_.spanBytesAlloc, -int64(unusableBytes))` という行で、`mheap_.spanBytesAlloc` から `unusableBytes` をアトミックに減算していました。`atomic.Xadd64` は、指定された値（ここでは負の `unusableBytes`）をターゲットに加算し、その操作後の新しい値を返します。

この変更では、`atomic.Xadd64` の戻り値（減算後の `mheap_.spanBytesAlloc` の新しい値）をチェックしています。

```go
if int64(atomic.Xadd64(&mheap_.spanBytesAlloc, -int64(unusableBytes))) < 0 {
    throw("spanBytesAlloc underflow")
}
```

ここで重要なのは、`mheap_.spanBytesAlloc` が `uintptr` 型（符号なし整数）ではなく、`int64` 型として扱われている点です。`atomic.Xadd64` は `int64` を操作するため、内部的には符号付きとして扱われます。もし `unusableBytes` が `mheap_.spanBytesAlloc` の現在の値よりも大きい場合、減算結果は負の値になります。

この `if` 文は、減算後の `mheap_.spanBytesAlloc` の値が0未満になった場合に `throw("spanBytesAlloc underflow")` を呼び出します。これは、ヒープの割り当て済みバイト数を追跡するカウンタが負になるという、メモリ管理ロジックの深刻な矛盾を意味します。このような状況は、通常、GCのバグやメモリリークの誤った計算など、ランタイムの深い部分での問題を示唆しています。

このチェックを追加することで、Goランタイムはこのような不整合を早期に検出し、プログラムがさらに壊れた状態に進む前に停止させることができます。これにより、問題の根本原因を特定しやすくなり、デバッグの効率が向上します。

## コアとなるコードの解説

変更された行は以下の通りです。

**変更前:**
```go
atomic.Xadd64(&mheap_.spanBytesAlloc, -int64(unusableBytes))
```
この行は、`mheap_.spanBytesAlloc` から `unusableBytes` をアトミックに減算し、その結果を `mheap_.spanBytesAlloc` に格納します。減算後の値は返されますが、ここでは利用されていませんでした。

**変更後:**
```go
if int64(atomic.Xadd64(&mheap_.spanBytesAlloc, -int64(unusableBytes))) < 0 {
    throw("spanBytesAlloc underflow")
}
```
この変更では、`atomic.Xadd64` の戻り値（減算後の `mheap_.spanBytesAlloc` の新しい値）を `int64` にキャストし、それが0未満であるかどうかをチェックしています。
- `atomic.Xadd64(&mheap_.spanBytesAlloc, -int64(unusableBytes))`: `mheap_.spanBytesAlloc` から `unusableBytes` を減算し、その結果の新しい値を返します。
- `int64(...)`: `atomic.Xadd64` は `int64` を返すため、このキャストは冗長に見えますが、明示的に型を保証しています。
- `< 0`: 減算結果が負になった場合、つまり `mheap_.spanBytesAlloc` がアンダーフローした場合に条件が真となります。
- `throw("spanBytesAlloc underflow")`: 条件が真の場合、ランタイムパニックを発生させ、"spanBytesAlloc underflow" というメッセージを出力してプログラムを終了させます。これにより、メモリ管理の不整合が即座に報告され、デバッグが容易になります。

この修正は、Goランタイムの堅牢性を高め、メモリ管理のバグを早期に発見するための重要な安全策です。

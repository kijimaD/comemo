# [インデックス 23487] ファイルの概要

このコミットは、Goランタイムにおける`forEachP`関数の同期メカニズムに関するバグ修正です。具体的には、`forEachP`が`stopTheWorld`と共有していた`stopwait`および`stopnote`フィールドを、専用のフィールド（`safePointWait`と`safePointNote`）に分離することで、競合状態（race condition）を解消し、ランタイムの安定性を向上させています。この変更により、ガベージコレクション（GC）などのセーフポイント処理中に発生しうるパニック（"P did not run fn" または "not stopped"）が防止されます。

commit f0dd002895b48595f6c14f2bf606775289f59d5f
Author: Austin Clements <austin@google.com>
Date:   Fri May 15 16:31:17 2015 -0400

    runtime: use separate count and note for forEachP

    Currently, forEachP reuses the stopwait and stopnote fields from
    stopTheWorld to track how many Ps have not responded to the safe-point
    request and to sleep until all Ps have responded.

    It was assumed this was safe because both stopTheWorld and forEachP
    must occur under the worlsema and hence stopwait and stopnote cannot
    be used for both purposes simultaneously and callers could always
    determine the appropriate use based on sched.gcwaiting (which is only
    set by stopTheWorld). However, this is not the case, since it's
    possible for there to be a window between when an M observes that
    gcwaiting is set and when it checks stopwait during which stopwait
    could have changed meanings. When this happens, the M decrements
    stopwait and may wakeup stopnote, but does not otherwise participate
    in the forEachP protocol. As a result, stopwait is decremented too
    many times, so it may reach zero before all Ps have run the safe-point
    function, causing forEachP to wake up early. It will then either
    observe that some P has not run the safe-point function and panic with
    "P did not run fn", or the remaining P (or Ps) will run the safe-point
    function before it wakes up and it will observe that stopwait is
    negative and panic with "not stopped".

    Fix this problem by giving forEachP its own safePointWait and
    safePointNote fields.

    One known sequence of events that can cause this race is as
    follows. It involves three actors:

    G1 is running on M1 on P1. P1 has an empty run queue.

    G2/M2 is in a blocked syscall and has lost its P. (The details of this
    don't matter, it just needs to be in a position where it needs to grab
    an idle P.)

    GC just started on G3/M3/P3. (These aren't very involved, they just
    have to be separate from the other G's, M's, and P's.)

    1. GC calls stopTheWorld(), which sets sched.gcwaiting to 1.

    Now G1/M1 begins to enter a syscall:

    2. G1/M1 invokes reentersyscall, which sets the P1's status to
       _Psyscall.

    3. G1/M1's reentersyscall observes gcwaiting != 0 and calls
       entersyscall_gcwait.

    4. G1/M1's entersyscall_gcwait blocks acquiring sched.lock.

    Back on GC:

    5. stopTheWorld cas's P1's status to _Pgcstop, does other stuff, and
       returns.

    6. GC does stuff and then calls startTheWorld().

    7. startTheWorld() calls procresize(), which sets P1's status to
       _Pidle and puts P1 on the idle list.

    Now G2/M2 returns from its syscall and takes over P1:

    8. G2/M2 returns from its blocked syscall and gets P1 from the idle
       list.

    9. G2/M2 acquires P1, which sets P1's status to _Prunning.

    10. G2/M2 starts a new syscall and invokes reentersyscall, which sets
        P1's status to _Psyscall.

    Back on G1/M1:

    11. G1/M1 finally acquires sched.lock in entersyscall_gcwait.

    At this point, G1/M1 still thinks it's running on P1. P1's status is
    _Psyscall, which is consistent with what G1/M1 is doing, but it's
    _Psyscall because *G2/M2* put it in to _Psyscall, not G1/M1. This is
    basically an ABA race on P1's status.

    Because forEachP currently shares stopwait with stopTheWorld. G1/M1's
    entersyscall_gcwait observes the non-zero stopwait set by forEachP,
    but mistakes it for a stopTheWorld. It cas's P1's status from
    _Psyscall (set by G2/M2) to _Pgcstop and proceeds to decrement
    stopwait one more time than forEachP was expecting.

    Fixes #10618. (See the issue for details on why the above race is safe
    when forEachP is not involved.)

      stress ./runtime.test -test.run TestFutexsleep\|TestGoroutineProfile

    ran for over 2 million runs and never crashed.

## 変更の背景

Goランタイムでは、ガベージコレクション（GC）などの重要な操作を行う際に、全てのGoルーチン（G）の実行を一時的に停止させる「Stop The World (STW)」というメカニズムが用いられます。また、特定の処理（例えば、GCのセーフポイント関数を実行する）を全てのプロセッサ（P）に対して実行させるために`forEachP`という関数が使用されます。

このコミット以前は、`forEachP`関数が、Pがセーフポイント要求に応答したかどうかを追跡するためのカウンタ（`stopwait`）と、全てのPが応答するまで待機するための通知メカニズム（`stopnote`）として、`stopTheWorld`が使用するフィールドを再利用していました。この再利用は、`stopTheWorld`と`forEachP`の両方が`worlsema`というグローバルなセマフォの下で実行されるため、同時に使用されることはないという前提に基づいています。また、呼び出し元は`sched.gcwaiting`（`stopTheWorld`のみが設定するフラグ）に基づいて、`stopwait`と`stopnote`の適切な使用方法を判断できると考えられていました。

しかし、この前提は誤りであることが判明しました。具体的には、OSスレッド（M）が`gcwaiting`が設定されていることを観測した後、`stopwait`をチェックするまでの間に、`stopwait`の意味が`stopTheWorld`用から`forEachP`用に変わってしまう時間的な窓（window）が存在する可能性がありました。この競合状態が発生すると、Mは`stopwait`をデクリメントし、`stopnote`をウェイクアップするかもしれませんが、`forEachP`プロトコルには適切に参加しません。結果として、`stopwait`が期待よりも多くデクリメントされ、全てのPがセーフポイント関数を実行する前に`stopwait`がゼロに達してしまう可能性がありました。これにより、`forEachP`が早期にウェイクアップし、「P did not run fn」というパニックを引き起こすか、あるいは残りのPがウェイクアップする前にセーフポイント関数を実行し、`stopwait`が負の値になることで「not stopped」というパニックを引き起こす可能性がありました。

この問題は、ランタイムの安定性に深刻な影響を与える可能性があり、特に並行性の高い環境やGCが頻繁に発生するアプリケーションで顕著でした。

## 前提知識の解説

このコミットの理解には、Goランタイムの以下の概念を理解しておく必要があります。

*   **Goroutine (G)**: Goランタイムによって管理される軽量なスレッド。数百万のGoroutineを同時に実行できる。
*   **OS Thread (M)**: オペレーティングシステムによって管理されるスレッド。Goランタイムは、M上でGを実行する。
*   **Processor (P)**: GoランタイムのスケジューラがGを実行するために必要な論理プロセッサ。MはPを取得してGを実行する。Pは実行可能なGのローカルキューを持つ。
*   **M:Nスケジューリング**: Goランタイムのスケジューラは、M個のOSスレッドをN個のGoroutineに多重化する。
*   **Stop The World (STW)**: ガベージコレクションなどの特定のランタイム操作中に、全てのGoroutineの実行を一時的に停止させるメカニズム。これにより、GCがメモリの状態を安全に検査・変更できる。STW中は、全てのMがPを解放し、Goroutineの実行が停止する。
*   **Safe Point**: Goroutineが安全に停止できるポイント。GCなどの操作は、Goroutineがセーフポイントに到達したときにのみ実行される。
*   **`forEachP`**: 全てのPに対して特定の関数（セーフポイント関数など）を実行させるためのランタイム関数。各Pがこの関数を実行し終えるまで待機する。
*   **`sched.gcwaiting`**: スケジューラのグローバルな状態変数で、`stopTheWorld`が進行中であることを示すフラグ。
*   **`stopwait`**: `stopTheWorld`または`forEachP`が、応答を待っているPの数をカウントするために使用する変数。
*   **`stopnote`**: `stopTheWorld`または`forEachP`が、全てのPからの応答を待機し、完了時にウェイクアップするために使用する同期プリミティブ（`note`型）。
*   **`cas` (Compare-And-Swap)**: アトミック操作の一種で、メモリ位置の現在の値が期待値と等しい場合にのみ、そのメモリ位置を新しい値に更新する。競合状態を避けるために使用される。
*   **`notetsleep` / `notewakeup`**: Goランタイム内部で使用される低レベルの同期プリミティブ。`notetsleep`は指定された`note`でスリープし、`notewakeup`はその`note`でスリープしているMをウェイクアップする。

## 技術的詳細

この問題は、`forEachP`が`stopTheWorld`と`stopwait`および`stopnote`を共有していることに起因する複雑な競合状態です。コミットメッセージに記載されている具体的なイベントシーケンスを詳細に見ていきましょう。このシナリオには、G1/M1/P1、G2/M2（Pなし）、GC/G3/M3/P3の3つのアクターが登場します。

1.  **GCが`stopTheWorld()`を呼び出し、`sched.gcwaiting`を1に設定する。**
    *   GCが開始され、全てのGoroutineを停止させる準備が始まる。`sched.gcwaiting`が設定されることで、他のMはGCが進行中であることを認識する。

2.  **G1/M1がシステムコールに入ろうとし、`reentersyscall`を呼び出し、P1のステータスを`_Psyscall`に設定する。**
    *   G1はP1上で実行されており、システムコールに入ろうとしている。`_Psyscall`はPがシステムコール中であることを示すステータス。

3.  **G1/M1の`reentersyscall`が`gcwaiting != 0`を観測し、`entersyscall_gcwait`を呼び出す。**
    *   G1/M1はGCが進行中であることを認識し、GCの完了を待つための特別なパスに入る。

4.  **G1/M1の`entersyscall_gcwait`が`sched.lock`の取得でブロックされる。**
    *   `sched.lock`はスケジューラのグローバルなロックであり、この時点で他のMが保持している可能性があるため、G1/M1は待機状態に入る。

5.  **GC側で、`stopTheWorld`がP1のステータスを`_Pgcstop`にCAS（Compare-And-Swap）で変更し、他の処理を実行してリターンする。**
    *   `stopTheWorld`はP1をGCのために停止させる。

6.  **GCが処理を続け、`startTheWorld()`を呼び出す。**
    *   GCが完了し、Goroutineの実行を再開する準備が始まる。

7.  **`startTheWorld()`が`procresize()`を呼び出し、P1のステータスを`_Pidle`に設定し、P1をアイドルリストに入れる。**
    *   P1はGCから解放され、アイドル状態となり、他のMが利用できるようになる。

8.  **G2/M2がシステムコールから戻り、P1を取得する。**
    *   G2/M2は以前ブロックされていたシステムコールから戻り、実行を再開するためにアイドル状態のPを探し、P1を取得する。

9.  **G2/M2がP1を取得し、P1のステータスを`_Prunning`に設定する。**
    *   P1はG2/M2によって実行中となる。

10. **G2/M2が新しいシステムコールを開始し、`reentersyscall`を呼び出し、P1のステータスを`_Psyscall`に設定する。**
    *   G2/M2もシステムコールに入ろうとしているため、P1のステータスを`_Psyscall`に設定する。

11. **G1/M1が最終的に`entersyscall_gcwait`で`sched.lock`を取得する。**
    *   G1/M1は長い間ブロックされていた`sched.lock`を取得し、処理を再開する。

この時点で、G1/M1はまだ自分がP1上で実行されていると考えています。P1のステータスは`_Psyscall`であり、これはG1/M1がシステムコールに入ろうとしていることと一致しているように見えます。しかし、この`_Psyscall`ステータスは**G2/M2**によって設定されたものであり、G1/M1によるものではありません。これはP1のステータスに対する**ABA競合**の一種です。

この競合状態の核心は、`forEachP`が`stopTheWorld`と`stopwait`を共有していることです。G1/M1の`entersyscall_gcwait`は、`forEachP`によって設定された非ゼロの`stopwait`を観測しますが、これを`stopTheWorld`によるものと誤解します。G1/M1はP1のステータスを`_Psyscall`（G2/M2によって設定されたもの）から`_Pgcstop`にCASで変更し、`stopwait`をデクリメントします。これにより、`forEachP`が期待していたよりも1回多く`stopwait`がデクリメントされてしまいます。

結果として、`forEachP`は全てのPがセーフポイント関数を実行し終える前に`stopwait`がゼロになり、早期にウェイクアップしてしまいます。これにより、「P did not run fn」というパニックが発生するか、あるいは`stopwait`が負の値になり「not stopped」というパニックが発生する可能性がありました。

## コアとなるコードの解説

このコミットの核心的な変更は、`forEachP`が`stopTheWorld`と共有していた同期プリミティブを分離したことです。

1.  **`schedt`構造体への新しいフィールドの追加**:
    `src/runtime/runtime2.go`の`schedt`構造体に`safePointWait int32`と`safePointNote note`が追加されました。これにより、`forEachP`は`stopTheWorld`とは独立した独自のカウンタと通知メカニズムを持つことができます。

2.  **`forEachP`関数内の変更**:
    `src/runtime/proc1.go`内の`forEachP`関数は、`sched.stopwait`と`sched.stopnote`への参照を全て`sched.safePointWait`と`sched.safePointNote`に置き換えました。
    *   `sched.safePointWait = gomaxprocs - 1`: `forEachP`が開始される際に、応答を待つPの数を初期化します。`gomaxprocs`は利用可能なPの総数です。
    *   `sched.safePointWait--`: 各Pがセーフポイント関数を実行するたびに、このカウンタがデクリメントされます。
    *   `notetsleep(&sched.safePointNote, ...)`: 全てのPが応答するまで待機するために、`safePointNote`でスリープします。
    *   `notewakeup(&sched.safePointNote)`: 全てのPが応答し、`safePointWait`がゼロになったときに、待機しているMをウェイクアップします。

3.  **`runSafePointFn`および`handoffp`関数内の変更**:
    これらの関数も同様に、`sched.stopwait`と`sched.stopnote`への参照を`sched.safePointWait`と`sched.safePointNote`に置き換えました。これらの関数は、Pがセーフポイント関数を実行する責任を負うため、`safePointWait`をデクリメントし、必要に応じて`safePointNote`をウェイクアップする必要があります。

この変更により、`stopTheWorld`が`stopwait`と`stopnote`を使用している間に、`forEachP`が`safePointWait`と`safePointNote`を独立して使用できるようになります。これにより、前述の競合状態、つまりMが`gcwaiting`を観測した後に`stopwait`の意味が変わり、誤ってデクリメントしてしまう問題が完全に解消されます。それぞれの目的のために独立した同期プリミティブを使用することで、ランタイムの異なる部分が互いの状態を誤解する可能性がなくなります。

コミットメッセージにあるように、この修正により、以前は数百回の実行で確実に失敗していたテストが、200万回以上の実行でもクラッシュしなくなったことが確認されており、ランタイムの堅牢性が大幅に向上したことを示しています。

    must occur under the worlsema and hence stopwait and stopnote cannot
    be used for both purposes simultaneously and callers could always
    determine the appropriate use based on sched.gcwaiting (which is only
    set by stopTheWorld). However, this is not the case, since it's
    possible for there to be a window between when an M observes that
    gcwaiting is set and when it checks stopwait during which stopwait
    could have changed meanings. When this happens, the M decrements
    stopwait and may wakeup stopnote, but does not otherwise participate
    in the forEachP protocol. As a result, stopwait is decremented too
    many times, so it may reach zero before all Ps have run the safe-point
    function, causing forEachP to wake up early. It will then either
    observe that some P has not run the safe-point function and panic with
    "P did not run fn", or the remaining P (or Ps) will run the safe-point
    function before it wakes up and it will observe that stopwait is
    negative and panic with "not stopped".

    Fix this problem by giving forEachP its own safePointWait and
    safePointNote fields.

    One known sequence of events that can cause this race is as
    follows. It involves three actors:

    G1 is running on M1 on P1. P1 has an empty run queue.

    G2/M2 is in a blocked syscall and has lost its P. (The details of this
    don't matter, it just needs to be in a position where it needs to grab
    an idle P.)

    GC just started on G3/M3/P3. (These aren't very involved, they just
    have to be separate from the other G's, M's, and P's.)

    1. GC calls stopTheWorld(), which sets sched.gcwaiting to 1.

    Now G1/M1 begins to enter a syscall:

    2. G1/M1 invokes reentersyscall, which sets the P1's status to
       _Psyscall.

    3. G1/M1's reentersyscall observes gcwaiting != 0 and calls
       entersyscall_gcwait.

    4. G1/M1's entersyscall_gcwait blocks acquiring sched.lock.

    Back on GC:

    5. stopTheWorld cas's P1's status to _Pgcstop, does other stuff, and
       returns.

    6. GC does stuff and then calls startTheWorld().

    7. startTheWorld() calls procresize(), which sets P1's status to
       _Pidle and puts P1 on the idle list.

    Now G2/M2 returns from its syscall and takes over P1:

    8. G2/M2 returns from its blocked syscall and gets P1 from the idle
       list.

    9. G2/M2 acquires P1, which sets P1's status to _Prunning.

    10. G2/M2 starts a new syscall and invokes reentersyscall, which sets
        P1's status to _Psyscall.

    Back on G1/M1:

    11. G1/M1 finally acquires sched.lock in entersyscall_gcwait.

    At this point, G1/M1 still thinks it's running on P1. P1's status is
    _Psyscall, which is consistent with what G1/M1 is doing, but it's
    _Psyscall because *G2/M2* put it in to _Psyscall, not G1/M1. This is
    basically an ABA race on P1's status.

    Because forEachP currently shares stopwait with stopTheWorld. G1/M1's
    entersyscall_gcwait observes the non-zero stopwait set by forEachP,
    but mistakes it for a stopTheWorld. It cas's P1's status from
    _Psyscall (set by G2/M2) to _Pgcstop and proceeds to decrement
    stopwait one more time than forEachP was expecting.

    Fixes #10618. (See the issue for details on why the above race is safe
    when forEachP is not involved.)

## 変更の背景

Goランタイムでは、ガベージコレクション（GC）などの重要な操作を行う際に、全てのGoルーチン（G）の実行を一時的に停止させる「Stop The World (STW)」というメカニズムが用いられます。また、特定の処理（例えば、GCのセーフポイント関数を実行する）を全てのプロセッサ（P）に対して実行させるために`forEachP`という関数が使用されます。

このコミット以前は、`forEachP`関数が、Pがセーフポイント要求に応答したかどうかを追跡するためのカウンタ（`stopwait`）と、全てのPが応答するまで待機するための通知メカニズム（`stopnote`）として、`stopTheWorld`が使用するフィールドを再利用していました。この再利用は、`stopTheWorld`と`forEachP`の両方が`worlsema`というグローバルなセマフォの下で実行されるため、同時に使用されることはないという前提に基づいています。また、呼び出し元は`sched.gcwaiting`（`stopTheWorld`のみが設定するフラグ）に基づいて、`stopwait`と`stopnote`の適切な使用方法を判断できると考えられていました。

しかし、この前提は誤りであることが判明しました。具体的には、OSスレッド（M）が`gcwaiting`が設定されていることを観測した後、`stopwait`をチェックするまでの間に、`stopwait`の意味が`stopTheWorld`用から`forEachP`用に変わってしまう時間的な窓（window）が存在する可能性がありました。この競合状態が発生すると、Mは`stopwait`をデクリメントし、`stopnote`をウェイクアップするかもしれませんが、`forEachP`プロトコルには適切に参加しません。結果として、`stopwait`が期待よりも多くデクリメントされ、全てのPがセーフポイント関数を実行する前に`stopwait`がゼロに達してしまう可能性がありました。これにより、`forEachP`が早期にウェイクアップし、「P did not run fn」というパニックを引き起こすか、あるいは残りのPがウェイクアップする前にセーフポイント関数を実行し、`stopwait`が負の値になることで「not stopped」というパニックを引き起こす可能性がありました。

この問題は、ランタイムの安定性に深刻な影響を与える可能性があり、特に並行性の高い環境やGCが頻繁に発生するアプリケーションで顕著でした。

## 前提知識の解説

このコミットの理解には、Goランタイムの以下の概念を理解しておく必要があります。

*   **Goroutine (G)**: Goランタイムによって管理される軽量なスレッド。数百万のGoroutineを同時に実行できる。
*   **OS Thread (M)**: オペレーティングシステムによって管理されるスレッド。Goランタイムは、M上でGを実行する。
*   **Processor (P)**: GoランタイムのスケジューラがGを実行するために必要な論理プロセッサ。MはPを取得してGを実行する。Pは実行可能なGのローカルキューを持つ。
*   **M:Nスケジューリング**: Goランタイムのスケジューラは、M個のOSスレッドをN個のGoroutineに多重化する。
*   **Stop The World (STW)**: ガベージコレクションなどの特定のランタイム操作中に、全てのGoroutineの実行を一時的に停止させるメカニズム。これにより、GCがメモリの状態を安全に検査・変更できる。STW中は、全てのMがPを解放し、Goroutineの実行が停止する。
*   **Safe Point**: Goroutineが安全に停止できるポイント。GCなどの操作は、Goroutineがセーフポイントに到達したときにのみ実行される。
*   **`forEachP`**: 全てのPに対して特定の関数（セーフポイント関数など）を実行させるためのランタイム関数。各Pがこの関数を実行し終えるまで待機する。
*   **`sched.gcwaiting`**: スケジューラのグローバルな状態変数で、`stopTheWorld`が進行中であることを示すフラグ。
*   **`stopwait`**: `stopTheWorld`または`forEachP`が、応答を待っているPの数をカウントするために使用する変数。
*   **`stopnote`**: `stopTheWorld`または`forEachP`が、全てのPからの応答を待機し、完了時にウェイクアップするために使用する同期プリミティブ（`note`型）。
*   **`cas` (Compare-And-Swap)**: アトミック操作の一種で、メモリ位置の現在の値が期待値と等しい場合にのみ、そのメモリ位置を新しい値に更新する。競合状態を避けるために使用される。
*   **`notetsleep` / `notewakeup`**: Goランタイム内部で使用される低レベルの同期プリミティブ。`notetsleep`は指定された`note`でスリープし、`notewakeup`はその`note`でスリープしているMをウェイクアップする。

## 技術的詳細

この問題は、`forEachP`が`stopTheWorld`と`stopwait`および`stopnote`を共有していることに起因する複雑な競合状態です。コミットメッセージに記載されている具体的なイベントシーケンスを詳細に見ていきましょう。このシナリオには、G1/M1/P1、G2/M2（Pなし）、GC/G3/M3/P3の3つのアクターが登場します。

1.  **GCが`stopTheWorld()`を呼び出し、`sched.gcwaiting`を1に設定する。**
    *   GCが開始され、全てのGoroutineを停止させる準備が始まる。`sched.gcwaiting`が設定されることで、他のMはGCが進行中であることを認識する。

2.  **G1/M1がシステムコールに入ろうとし、`reentersyscall`を呼び出し、P1のステータスを`_Psyscall`に設定する。**
    *   G1はP1上で実行されており、システムコールに入ろうとしている。`_Psyscall`はPがシステムコール中であることを示すステータス。

3.  **G1/M1の`reentersyscall`が`gcwaiting != 0`を観測し、`entersyscall_gcwait`を呼び出す。**
    *   G1/M1はGCが進行中であることを認識し、GCの完了を待つための特別なパスに入る。

4.  **G1/M1の`entersyscall_gcwait`が`sched.lock`の取得でブロックされる。**
    *   `sched.lock`はスケジューラのグローバルなロックであり、この時点で他のMが保持している可能性があるため、G1/M1は待機状態に入る。

5.  **GC側で、`stopTheWorld`がP1のステータスを`_Pgcstop`にCAS（Compare-And-Swap）で変更し、他の処理を実行してリターンする。**
    *   `stopTheWorld`はP1をGCのために停止させる。

6.  **GCが処理を続け、`startTheWorld()`を呼び出す。**
    *   GCが完了し、Goroutineの実行を再開する準備が始まる。

7.  **`startTheWorld()`が`procresize()`を呼び出し、P1のステータスを`_Pidle`に設定し、P1をアイドルリストに入れる。**
    *   P1はGCから解放され、アイドル状態となり、他のMが利用できるようになる。

8.  **G2/M2がシステムコールから戻り、P1を取得する。**
    *   G2/M2は以前ブロックされていたシステムコールから戻り、実行を再開するためにアイドル状態のPを探し、P1を取得する。

9.  **G2/M2がP1を取得し、P1のステータスを`_Prunning`に設定する。**
    *   P1はG2/M2によって実行中となる。

10. **G2/M2が新しいシステムコールを開始し、`reentersyscall`を呼び出し、P1のステータスを`_Psyscall`に設定する。**
    *   G2/M2もシステムコールに入ろうとしているため、P1のステータスを`_Psyscall`に設定する。

11. **G1/M1が最終的に`entersyscall_gcwait`で`sched.lock`を取得する。**
    *   G1/M1は長い間ブロックされていた`sched.lock`を取得し、処理を再開する。

この時点で、G1/M1はまだ自分がP1上で実行されていると考えています。P1のステータスは`_Psyscall`であり、これはG1/M1がシステムコールに入ろうとしていることと一致しているように見えます。しかし、この`_Psyscall`ステータスは**G2/M2**によって設定されたものであり、G1/M1によるものではありません。これはP1のステータスに対する**ABA競合**の一種です。

この競合状態の核心は、`forEachP`が`stopTheWorld`と`stopwait`を共有していることです。G1/M1の`entersyscall_gcwait`は、`forEachP`によって設定された非ゼロの`stopwait`を観測しますが、これを`stopTheWorld`によるものと誤解します。G1/M1はP1のステータスを`_Psyscall`（G2/M2によって設定されたもの）から`_Pgcstop`にCASで変更し、`stopwait`をデクリメントします。これにより、`forEachP`が期待していたよりも1回多く`stopwait`がデクリメントされてしまいます。

結果として、`forEachP`は全てのPがセーフポイント関数を実行し終える前に`stopwait`がゼロになり、早期にウェイクアップしてしまいます。これにより、「P did not run fn」というパニックが発生するか、あるいは`stopwait`が負の値になり「not stopped」というパニックが発生する可能性がありました。

## コアとなるコードの解説

このコミットの核心的な変更は、`forEachP`が`stopTheWorld`と共有していた同期プリミティブを分離したことです。

1.  **`schedt`構造体への新しいフィールドの追加**:
    `src/runtime/runtime2.go`の`schedt`構造体に`safePointWait int32`と`safePointNote note`が追加されました。これにより、`forEachP`は`stopTheWorld`とは独立した独自のカウンタと通知メカニズムを持つことができます。

2.  **`forEachP`関数内の変更**:
    `src/runtime/proc1.go`内の`forEachP`関数は、`sched.stopwait`と`sched.stopnote`への参照を全て`sched.safePointWait`と`sched.safePointNote`に置き換えました。
    *   `sched.safePointWait = gomaxprocs - 1`: `forEachP`が開始される際に、応答を待つPの数を初期化します。`gomaxprocs`は利用可能なPの総数です。
    *   `sched.safePointWait--`: 各Pがセーフポイント関数を実行するたびに、このカウンタがデクリメントされます。
    *   `notetsleep(&sched.safePointNote, ...)`: 全てのPが応答するまで待機するために、`safePointNote`でスリープします。
    *   `notewakeup(&sched.safePointNote)`: 全てのPが応答し、`safePointWait`がゼロになったときに、待機しているMをウェイクアップします。

3.  **`runSafePointFn`および`handoffp`関数内の変更**:
    これらの関数も同様に、`sched.stopwait`と`sched.stopnote`への参照を`sched.safePointWait`と`sched.safePointNote`に置き換えました。これらの関数は、Pがセーフポイント関数を実行する責任を負うため、`safePointWait`をデクリメントし、必要に応じて`safePointNote`をウェイクアップする必要があります。

この変更により、`stopTheWorld`が`stopwait`と`stopnote`を使用している間に、`forEachP`が`safePointWait`と`safePointNote`を独立して使用できるようになります。これにより、前述の競合状態、つまりMが`gcwaiting`を観測した後に`stopwait`の意味が変わり、誤ってデクリメントしてしまう問題が完全に解消されます。それぞれの目的のために独立した同期プリミティブを使用することで、ランタイムの異なる部分が互いの状態を誤解する可能性がなくなります。

コミットメッセージにあるように、この修正により、以前は数百回の実行で確実に失敗していたテストが、200万回以上の実行でもクラッシュしなくなったことが確認されており、ランタイムの堅牢性が大幅に向上したことを示しています。

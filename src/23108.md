# [インデックス 23108] ファイルの概要

このコミットは、Goランタイムにおけるガベージコレクション（GC）のワークバッファキャッシュのメカニズムを改善するものです。具体的には、M（Machine）ごとに存在していたワークバッファキャッシュを、P（Processor）ごとの`gcWork`オブジェクトに置き換えることで、GCのパフォーマンスと複雑性を向上させています。

    runtime: replace per-M workbuf cache with per-P gcWork cache

    Currently, each M has a cache of the most recently used *workbuf. This
    is used primarily by the write barrier so it doesn't have to access
    the global workbuf lists on every write barrier. It's also used by
    stack scanning because it's convenient.

    This cache is important for write barrier performance, but this
    particular approach has several downsides. It's faster than no cache,
    but far from optimal (as the benchmarks below show). It's complex:
    access to the cache is sprinkled through most of the workbuf list
    operations and it requires special care to transform into and back out
    of the gcWork cache that's actually used for scanning and marking. It
    requires atomic exchanges to take ownership of the cached workbuf and
    to return it to the M's cache even though it's almost always used by
    only the current M. Since it's per-M, flushing these caches is O(# of
    Ms), which may be high. And it has some significant subtleties: for
    example, in general the cache shouldn't be used after the
    harvestwbufs() in mark termination because it could hide work from
    mark termination, but stack scanning can happen after this and *will*
    use the cache (but it turns out this is okay because it will always be
    followed by a getfull(), which drains the cache).

    This change replaces this cache with a per-P gcWork object. This
    gcWork cache can be used directly by scanning and marking (as long as
    preemption is disabled, which is a general requirement of gcWork).
    Since it's per-P, it doesn't require synchronization, which simplifies
    things and means the only atomic operations in the write barrier are
    occasionally fetching new work buffers and setting a mark bit if the
    object isn't already marked. This cache can be flushed in O(# of Ps),
    which is generally small. It follows a simple flushing rule: the cache
    can be used during any phase, but during mark termination it must be
    flushed before allowing preemption. This also makes the dispose during
    mutator assist no longer necessary, which eliminates the vast majority
    of gcWork dispose calls and reduces contention on the global workbuf
    lists. And it's a lot faster on some benchmarks:

## 元コミット内容

Goランタイムにおいて、M（Machine）ごとのワークバッファキャッシュをP（Processor）ごとの`gcWork`キャッシュに置き換える変更です。

現在の実装では、各Mが最近使用した`*workbuf`のキャッシュを持っており、これは主にライトバリアによってグローバルなワークバッファリストへのアクセスを減らすために使用されていました。しかし、このアプローチにはいくつかの欠点がありました。ベンチマークが示すように、キャッシュがない場合よりは速いものの、最適とは言えませんでした。また、ワークバッファリスト操作のほとんどにアクセスが散りばめられており、複雑でした。さらに、ほとんどの場合現在のMによってのみ使用されるにもかかわらず、キャッシュされたワークバッファの所有権を取得したり、Mのキャッシュに戻したりするためにアトミックな交換が必要でした。Mごとのキャッシュであるため、これらのキャッシュをフラッシュする際の計算量はMの数に比例し、Mの数が多い場合には高コストになる可能性がありました。また、いくつかの微妙な問題もありました。例えば、マーク終了時の`harvestwbufs()`の後には一般的にキャッシュを使用すべきではありませんでしたが、スタックスキャンはこの後に行われる可能性があり、キャッシュを使用することがありました（ただし、これは常に`getfull()`が後に続くため問題ないことが判明しました）。

この変更では、このキャッシュをPごとの`gcWork`オブジェクトに置き換えます。この`gcWork`キャッシュは、スキャンとマークに直接使用できます（プリエンプションが無効になっている限り、これは`gcWork`の一般的な要件です）。Pごとのキャッシュであるため、同期は不要となり、物事が簡素化されます。これにより、ライトバリアにおけるアトミック操作は、新しいワークバッファを時々フェッチすることと、オブジェクトがまだマークされていない場合にマークビットを設定することだけになります。このキャッシュはPの数に比例する計算量でフラッシュでき、Pの数は通常少ないです。シンプルなフラッシングルールに従います。キャッシュはどのフェーズでも使用できますが、マーク終了時にはプリエンプションを許可する前にフラッシュする必要があります。これにより、ミューテータアシスト中の`dispose`も不要になり、`gcWork`の`dispose`呼び出しの大部分が排除され、グローバルなワークバッファリストでの競合が減少します。そして、いくつかのベンチマークでは大幅に高速化されています。

この変更は、並行マークの終了に近づいたときにこれらのキャッシュをフラッシュするのに適した位置にGoを置くことにもなり、マーク終了時のポーズ時間を制御しながらワークバッファのサイズを増やすことができるようになります。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行と並行して動作する「並行GC」を採用しています。この並行GCの効率を最大化するためには、GCがオブジェクトをスキャンしてマークする際に発生するオーバーヘッドを最小限に抑えることが重要です。特に、ミューテータ（ユーザープログラム）がヒープに新しいオブジェクトを割り当てたり、既存のオブジェクトへのポインタを変更したりする際に、GCが必要な情報を収集するための「ライトバリア」が動作します。

従来のGoランタイムでは、このライトバリアのパフォーマンスを向上させるために、各M（Machine、OSスレッドに対応）が自身のワークバッファキャッシュを持っていました。このキャッシュは、GCが処理すべきオブジェクトのポインタを一時的に保持する`workbuf`構造体をMごとに保持することで、グローバルなワークバッファリストへの頻繁なアクセスを避けることを目的としていました。しかし、コミットメッセージに記載されているように、このMごとのキャッシュにはいくつかの問題点がありました。

1.  **複雑性**: キャッシュへのアクセスがワークバッファリスト操作全体に散らばっており、コードが複雑化していました。
2.  **同期オーバーヘッド**: Mごとのキャッシュであるにもかかわらず、複数のMが同時にアクセスする可能性を考慮してアトミック操作が必要となり、これがオーバーヘッドとなっていました。
3.  **フラッシングの非効率性**: GCの特定のフェーズ（特にマーク終了時）でキャッシュをフラッシュする必要がある場合、Mの数に比例する計算量がかかり、Mの数が多いシステムでは非効率的でした。
4.  **微妙な挙動**: マーク終了後のスタックスキャンなど、特定のシナリオでキャッシュの利用が意図しない挙動を引き起こす可能性がありました。

これらの問題は、GCのパフォーマンスを阻害し、ランタイムの複雑性を増大させていました。特に、ライトバリアは頻繁に実行されるため、その効率はGC全体のパフォーマンスに直結します。このコミットは、これらの課題を解決し、より効率的でシンプルなGCワークバッファ管理メカニズムを導入することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスケジューラ、ガベージコレクション（GC）の基本概念、特にライトバリアとワークバッファの役割について理解しておく必要があります。

### GoランタイムのM, P, Gモデル

Goランタイムは、並行処理を効率的に管理するためにM, P, Gという3つの抽象概念を使用します。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。ユーザーが書くGoの関数はGoroutineとして実行されます。数百万のGoroutineを同時に実行することも可能です。
*   **M (Machine)**: OSスレッドに対応します。Goランタイムは、OSスレッドを抽象化したMを管理します。GはM上で実行されます。
*   **P (Processor)**: 論理プロセッサ、またはスケジューラコンテキストとも呼ばれます。PはMとGの間の仲介役として機能します。Pは実行可能なGのローカルキューを持ち、MはPからGを取得して実行します。`GOMAXPROCS`環境変数によってPの数を制御できます。Pの存在により、MがGを奪い合う際の競合を減らし、効率的なスケジューリングを可能にします。

このコミットでは、従来の「Mごとのキャッシュ」が「Pごとのキャッシュ」に置き換えられるため、このMとPの違いが重要になります。Pは通常、CPUコアの数に制限されるため、Mの数よりもはるかに少ないです。

### Goのガベージコレクション（GC）

GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースとした並行GCです。

*   **三色マーク**: オブジェクトを以下の3つの色で分類します。
    *   **白 (White)**: まだGCによって発見されていないオブジェクト。最終的に回収される可能性があるオブジェクト。
    *   **灰 (Grey)**: GCによって発見されたが、そのオブジェクトが参照する他のオブジェクトがまだスキャンされていないオブジェクト。
    *   **黒 (Black)**: GCによって発見され、そのオブジェクトが参照するすべてのオブジェクトもスキャンされたオブジェクト。回収されないオブジェクト。
*   **マークフェーズ**: GCがヒープ上の到達可能なオブジェクトをマークするフェーズです。このフェーズは、ミューテータ（ユーザープログラム）と並行して実行されます。
*   **スイープフェーズ**: マークされなかった（白のままの）オブジェクトをヒープから解放するフェーズです。
*   **ライトバリア (Write Barrier)**: 並行GCにおいて、ミューテータがポインタを更新する際にGCの正確性を保つために挿入されるコードです。ミューテータがヒープ上のオブジェクトへのポインタを変更する際、GCがその変更を認識し、参照関係の整合性を保つためにライトバリアが動作します。Goのライトバリアは、新しいポインタが指すオブジェクトを灰色にマークすることで、GCがそのオブジェクトをスキャン対象に含めることを保証します。
*   **ワークバッファ (Work Buffer)**: GCのマークフェーズ中に、灰色になったオブジェクトのポインタを一時的に格納するためのバッファです。GCワーカーは、このワークバッファからポインタを取り出し、そのポインタが指すオブジェクトをスキャンし、さらにそのオブジェクトが参照するオブジェクトを灰色にしてワークバッファに追加します。これにより、到達可能なオブジェクトが再帰的にマークされていきます。
*   **`gcWork`**: `gcWork`は、GCのマーク処理におけるワークバッファの管理と、スキャンされたバイト数の追跡を行うための構造体です。GCワーカーがオブジェクトをスキャンし、新しいポインタを発見すると、それらを`gcWork`オブジェクトに追加します。`gcWork`は、内部的に`workbuf`を管理し、必要に応じてグローバルなワークバッファリストとの間でワークをやり取りします。

### プリエンプション (Preemption)

Goランタイムは、Goroutineの実行を中断し、別のGoroutineに切り替える「プリエンプション」のメカニズムを持っています。これは、長時間実行されるGoroutineが他のGoroutineの実行を妨げないようにするために重要です。GCの特定の操作（特に`gcWork`を使用するような低レベルの操作）では、データの一貫性を保つためにプリエンプションを一時的に無効にする必要があります。

## 技術的詳細

このコミットの核心は、GCワークバッファの管理戦略をMベースからPベースへと変更することにあります。

### 従来のMごとのワークバッファキャッシュの問題点

従来のシステムでは、各M（OSスレッド）が`currentwbuf`というフィールドを持ち、これがGCワークバッファのキャッシュとして機能していました。ライトバリアが新しいポインタを検出すると、まずこのMローカルなキャッシュにポインタを追加しようとします。キャッシュが満杯になると、グローバルなワークバッファリストにフラッシュされます。

このMごとのキャッシュは、ライトバリアのパフォーマンス向上に寄与しましたが、以下の技術的な課題を抱えていました。

1.  **アトミック操作の必要性**: `currentwbuf`はMに紐付けられていますが、複数のGoroutineが同じM上で実行される可能性があるため、`currentwbuf`へのアクセスには`xchguintptr`のようなアトミック操作が必要でした。これは、キャッシュの取得と解放の際にオーバーヘッドを生じさせます。
2.  **複雑なライフサイクル管理**: `gcWork`オブジェクトは、スキャンやマークの際に一時的に使用され、その後`dispose()`や`disposeToCache()`といったメソッドでワークバッファをグローバルリストに戻したり、Mのキャッシュに戻したりする必要がありました。特に、マーク終了フェーズでは`harvestwbufs()`がMごとのキャッシュをグローバルリストに回収する必要があり、このタイミングとスタックスキャンでのキャッシュ利用の整合性を保つのが複雑でした。
3.  **フラッシングの非効率性**: GCの特定のフェーズで、すべてのMのキャッシュをフラッシュする必要がある場合、Mの数（`# of Ms`）に比例する計算量がかかりました。Mの数は、システム上のOSスレッドの数に依存し、Goのスケジューラが管理するMの数も変動するため、これがパフォーマンスのボトルネックになる可能性がありました。

### 新しいPごとの`gcWork`キャッシュの導入

このコミットでは、Mの`currentwbuf`を削除し、代わりにP（論理プロセッサ）に`gcWork`型の`gcw`フィールドを追加します。

```go
type p struct {
    // ...
    gcw gcWork
    // ...
}
```

この変更により、以下の利点がもたらされます。

1.  **同期の不要化**: Pは、特定の時点で1つのMによってのみ使用されるため、Pに紐付けられた`gcw`フィールドへのアクセスは、通常アトミック操作を必要としません。これにより、ライトバリアやGCワーカーが`gcw`にアクセスする際のオーバーヘッドが大幅に削減されます。コミットメッセージにも「Since it's per-P, it doesn't require synchronization」と明記されています。
2.  **シンプルなライフサイクル**: `gcWork`オブジェクトはPに直接紐付けられるため、そのライフサイクル管理が簡素化されます。特に、ミューテータアシスト（GCが不足している場合にユーザープログラムがGCを手伝うこと）中の`dispose()`呼び出しが不要になります。これは、Pごとの`gcw`がGCフェーズの遷移時にのみフラッシュされればよいためです。
3.  **効率的なフラッシング**: Pの数は通常、CPUコアの数に制限されるため、Mの数よりもはるかに少ないです。したがって、すべてのPの`gcw`キャッシュをフラッシュする際の計算量は、Pの数（`# of Ps`）に比例し、これはMの数に比例する場合よりもはるかに効率的です。
4.  **マーク終了時の制御**: 新しいモデルでは、マーク終了時にプリエンプションを許可する前にPごとの`gcw`をフラッシュするというシンプルなルールが適用されます。これにより、GCのポーズ時間を制御しながら、より大きなワークバッファを使用できるようになります。

### ベンチマーク結果

コミットメッセージには、この変更による具体的なベンチマーク結果が示されています。多くのベンチマークでパフォーマンスが向上しており、特に`BenchmarkGoParse`で-64.31%、`BenchmarkHTTPClientServer`で-29.31%、`BenchmarkGobDecode`で-26.14%といった大幅な改善が見られます。これは、ライトバリアのオーバーヘッド削減とワークバッファ管理の効率化が、実際のアプリケーションのパフォーマンスに大きく寄与することを示しています。

    runtime: replace per-M workbuf cache with per-P gcWork cache

    Currently, each M has a cache of the most recently used *workbuf. This
    is used primarily by the write barrier so it doesn't have to access
    the global workbuf lists on every write barrier. It's also used by
    stack scanning because it's convenient.

    This cache is important for write barrier performance, but this
    particular approach has several downsides. It's faster than no cache,
    but far from optimal (as the benchmarks below show). It's complex:
    access to the cache is sprinkled through most of the workbuf list
    operations and it requires special care to transform into and back out
    of the gcWork cache that's actually used for scanning and marking. It
    requires atomic exchanges to take ownership of the cached workbuf and
    to return it to the M's cache even though it's almost always used by
    only the current M. Since it's per-M, flushing these caches is O(# of
    Ms), which may be high. And it has some significant subtleties: for
    example, in general the cache shouldn't be used after the
    harvestwbufs() in mark termination because it could hide work from
    mark termination, but stack scanning can happen after this and *will*
    use the cache (but it turns out this is okay because it will always be
    followed by a getfull(), which drains the cache).

    gcWork cache can be used directly by scanning and marking (as long as
    preemption is disabled, which is a general requirement of gcWork).

    occasionally fetching new work buffers and setting a mark bit if the

    flushed before allowing preemption. This also makes the dispose during
    mutator assist no longer necessary, which eliminates the vast majority

## 元コミット内容

Goランタイムにおいて、M（Machine）ごとのワークバッファキャッシュをP（Processor）ごとの`gcWork`キャッシュに置き換える変更です。

現在の実装では、各Mが最近使用した`*workbuf`のキャッシュを持っており、これは主にライトバリアによってグローバルなワークバッファリストへのアクセスを減らすために使用されていました。しかし、このアプローチにはいくつかの欠点がありました。ベンチマークが示すように、キャッシュがない場合よりは速いものの、最適とは言えませんでした。また、ワークバッファリスト操作のほとんどにアクセスが散りばめられており、複雑でした。さらに、ほとんどの場合現在のMによってのみ使用されるにもかかわらず、キャッシュされたワークバッファの所有権を取得したり、Mのキャッシュに戻したりするためにアトミックな交換が必要でした。Mごとのキャッシュであるため、これらのキャッシュをフラッシュする際の計算量はMの数に比例し、Mの数が多い場合には高コストになる可能性がありました。また、いくつかの微妙な問題もありました。例えば、マーク終了時の`harvestwbufs()`の後には一般的にキャッシュを使用すべきではありませんでしたが、スタックスキャンはこの後に行われる可能性があり、キャッシュを使用することがありました（ただし、これは常に`getfull()`が後に続くため問題ないことが判明しました）。

この変更では、このキャッシュをPごとの`gcWork`オブジェクトに置き換えます。この`gcWork`キャッシュは、スキャンとマークに直接使用できます（プリエンプションが無効になっている限り、これは`gcWork`の一般的な要件です）。Pごとのキャッシュであるため、同期は不要となり、物事が簡素化されます。これにより、ライトバリアにおけるアトミック操作は、新しいワークバッファを時々フェッチすることと、オブジェクトがまだマークされていない場合にマークビットを設定することだけになります。このキャッシュはPの数に比例する計算量でフラッシュでき、Pの数は通常少ないです。シンプルなフラッシングルールに従います。キャッシュはどのフェーズでも使用できますが、マーク終了時にはプリエンプションを許可する前にフラッシュする必要があります。これにより、ミューテータアシスト中の`dispose`も不要になり、`gcWork`の`dispose`呼び出しの大部分が排除され、グローバルなワークバッファリストでの競合が減少します。そして、いくつかのベンチマークでは大幅に高速化されています。

この変更は、並行マークの終了に近づいたときにこれらのキャッシュをフラッシュするのに適した位置にGoを置くことにもなり、マーク終了時のポーズ時間を制御しながらワークバッファのサイズを増やすことができるようになります。

## 変更の背景

Goのガベージコレクション（GC）は、プログラムの実行と並行して動作する「並行GC」を採用しています。この並行GCの効率を最大化するためには、GCがオブジェクトをスキャンしてマークする際に発生するオーバーヘッドを最小限に抑えることが重要です。特に、ミューテータ（ユーザープログラム）がヒープに新しいオブジェクトを割り当てたり、既存のオブジェクトへのポインタを変更したりする際に、GCが必要な情報を収集するための「ライトバリア」が動作します。

従来のGoランタイムでは、このライトバリアのパフォーマンスを向上させるために、各M（Machine、OSスレッドに対応）が自身のワークバッファキャッシュを持っていました。このキャッシュは、GCが処理すべきオブジェクトのポインタを一時的に保持する`workbuf`構造体をMごとに保持することで、グローバルなワークバッファリストへの頻繁なアクセスを避けることを目的としていました。しかし、コミットメッセージに記載されているように、このMごとのキャッシュにはいくつかの問題点がありました。

1.  **複雑性**: キャッシュへのアクセスがワークバッファリスト操作全体に散らばっており、コードが複雑化していました。
2.  **同期オーバーヘッド**: Mごとのキャッシュであるにもかかわらず、複数のMが同時にアクセスする可能性を考慮してアトミック操作が必要となり、これがオーバーヘッドとなっていました。
3.  **フラッシングの非効率性**: GCの特定のフェーズ（特にマーク終了時）でキャッシュをフラッシュする必要がある場合、Mの数に比例する計算量がかかり、Mの数が多いシステムでは非効率的でした。
4.  **微妙な挙動**: マーク終了後のスタックスキャンなど、特定のシナリオでキャッシュの利用が意図しない挙動を引き起こす可能性がありました。

これらの問題は、GCのパフォーマンスを阻害し、ランタイムの複雑性を増大させていました。特に、ライトバリアは頻繁に実行されるため、その効率はGC全体のパフォーマンスに直結します。このコミットは、これらの課題を解決し、より効率的でシンプルなGCワークバッファ管理メカニズムを導入することを目的としています。

## 前提知識の解説

このコミットを理解するためには、Goランタイムのスケジューラ、ガベージコレクション（GC）の基本概念、特にライトバリアとワークバッファの役割について理解しておく必要があります。

### GoランタイムのM, P, Gモデル

Goランタイムは、並行処理を効率的に管理するためにM, P, Gという3つの抽象概念を使用します。

*   **G (Goroutine)**: Goにおける軽量な実行単位です。ユーザーが書くGoの関数はGoroutineとして実行されます。数百万のGoroutineを同時に実行することも可能です。Goroutineは、Goランタイムスケジューラによって管理され、OSスレッドとは異なり、コンテキストスイッチのオーバーヘッドが大幅に削減されます。スタックサイズは小さく（通常約2KB）、必要に応じて動的に拡大・縮小します。
*   **M (Machine)**: OSスレッドに対応します。Goランタイムは、OSスレッドを抽象化したMを管理します。GはM上で実行されます。Mは自身のCPU状態、メモリ、スタックを持ち、OSによって管理されます。ブロッキング操作（システムコールなど）に遭遇すると、Mは関連付けられたPから分離し、Pは別のMによって他のGoroutineの実行を継続するために利用可能になります。各Mには、スケジューリングタスクやシステムコール処理に使用される`g0`と呼ばれる特別なGoroutineがあります。
*   **P (Processor)**: 論理プロセッサ、またはスケジューラコンテキストとも呼ばれます。PはMとGの間の仲介役として機能します。Pは実行可能なGのローカルキューを持ち、MはPからGを取得して実行します。Pの数は`runtime.GOMAXPROCS()`設定によって決定され、デフォルトでは利用可能なCPUコア数に一致します。MがGoコードをアクティブに実行している場合、MとPの間には1対1のバインディングがあります。Pは、Goランタイム内の効率的な状態管理と負荷分散に不可欠です。

Goスケジューラは、Goroutine（G）と利用可能なOSスレッド（M）を論理プロセッサ（P）を使用して効率的にマッチングさせます。新しいGoroutineが作成されると、通常は利用可能なPのローカル実行キューに配置されます。MはPを取得し、そのPのローカル実行キューからGoroutineを実行します。負荷分散のため、Goスケジューラは「ワークスチール」メカニズムを採用しており、Pのローカル実行キューが空になると、他のPのローカルキューやグローバル実行キューからGoroutineを「盗む」ことができます。

### Goのガベージコレクション（GC）

GoのGCは、主に「三色マーク＆スイープ」アルゴリズムをベースとした並行GCです。

*   **三色マーク**: オブジェクトを以下の3つの色で分類します。
    *   **白 (White)**: まだGCによって発見されていないオブジェクト。最終的に回収される可能性があるオブジェクト。
    *   **灰 (Grey)**: GCによって発見されたが、そのオブジェクトが参照する他のオブジェクトがまだスキャンされていないオブジェクト。
    *   **黒 (Black)**: GCによって発見され、そのオブジェクトが参照するすべてのオブジェクトもスキャンされたオブジェクト。回収されないオブジェクト。
*   **マークフェーズ**: GCがヒープ上の到達可能なオブジェクトをマークするフェーズです。このフェーズは、ミューテータ（ユーザープログラム）と並行して実行されます。
*   **スイープフェーズ**: マークされなかった（白のままの）オブジェクトをヒープから解放するフェーズです。
*   **ライトバリア (Write Barrier)**: 並行GCにおいて、ミューテータがポインタを更新する際にGCの正確性を保つために挿入されるコードです。ミューテータがヒープ上のオブジェクトへのポインタを変更する際、GCがその変更を認識し、参照関係の整合性を保つためにライトバリアが動作します。Goのライトバリアは、新しいポインタが指すオブジェクトを灰色にマークすることで、GCがそのオブジェクトをスキャン対象に含めることを保証します。ライトバリアは、黒いオブジェクトが白いオブジェクトを指すことを防ぐことで、三色マーキングアルゴリズムの不変条件を維持します。Go 1.8からはハイブリッドライトバリアが導入され、STW（Stop The World）ポーズの削減に貢献しています。
*   **ワークバッファ (Work Buffer)**: GCのマークフェーズ中に、灰色になったオブジェクトのポインタを一時的に格納するためのバッファです。GCワーカーは、このワークバッファからポインタを取り出し、そのポインタが指すオブジェクトをスキャンし、さらにそのオブジェクトが参照するオブジェクトを灰色にしてワークバッファに追加します。これにより、到達可能なオブジェクトが再帰的にマークされていきます。
*   **`gcWork`**: `gcWork`は、GCのマーク処理におけるワークバッファの管理と、スキャンされたバイト数の追跡を行うための重要な内部コンポーネントです。これは、GCによって発見されたが、その参照がまだスキャンされていない「灰色オブジェクト」のワークプールとして機能します。`gcWork`はプロデューサー・コンシューマーモデルで動作し、ライトバリアやルートオブジェクトスキャン、スタックスキャンなどの「プロデューサー」が新しく発見された灰色オブジェクトを`gcWork`プールに追加し、GCワーカーGoroutineなどの「コンシューマー」がプールから灰色オブジェクトを取り出し、その参照をスキャンして「黒」にマークします。`gcWork`構造体は、これらの灰色オブジェクトを効率的に管理するために、プライマリおよびバックアップのワークバッファ（`wbuf1`と`wbuf2`）を含んでいます。

### プリエンプション (Preemption)

Goランタイムは、Goroutineの実行を中断し、別のGoroutineに切り替える「プリエンプション」のメカニズムを持っています。これは、長時間実行されるGoroutineが他のGoroutineの実行を妨げないようにするために重要です。GCの特定の操作（特に`gcWork`を使用するような低レベルの操作）では、データの一貫性を保つためにプリエンプションを一時的に無効にする必要があります。

## 技術的詳細

このコミットの核心は、GCワークバッファの管理戦略をMベースからPベースへと変更することにあります。

### 従来のMごとのワークバッファキャッシュの問題点

従来のシステムでは、各M（OSスレッド）が`currentwbuf`というフィールドを持ち、これがGCワークバッファのキャッシュとして機能していました。ライトバリアが新しいポインタを検出すると、まずこのMローカルなキャッシュにポインタを追加しようとします。キャッシュが満杯になると、グローバルなワークバッファリストにフラッシュされます。

このMごとのキャッシュは、ライトバリアのパフォーマンス向上に寄与しましたが、以下の技術的な課題を抱えていました。

1.  **アトミック操作の必要性**: `currentwbuf`はMに紐付けられていますが、複数のGoroutineが同じM上で実行される可能性があるため、`currentwbuf`へのアクセスには`xchguintptr`のようなアトミック操作が必要でした。これは、キャッシュの取得と解放の際にオーバーヘッドを生じさせます。
2.  **複雑なライフサイクル管理**: `gcWork`オブジェクトは、スキャンやマークの際に一時的に使用され、その後`dispose()`や`disposeToCache()`といったメソッドでワークバッファをグローバルリストに戻したり、Mのキャッシュに戻したりする必要がありました。特に、マーク終了フェーズでは`harvestwbufs()`がMごとのキャッシュをグローバルリストに回収する必要があり、このタイミングとスタックスキャンでのキャッシュ利用の整合性を保つのが複雑でした。
3.  **フラッシングの非効率性**: GCの特定のフェーズで、すべてのMのキャッシュをフラッシュする必要がある場合、Mの数（`# of Ms`）に比例する計算量がかかりました。Mの数は、システム上のOSスレッドの数に依存し、Goのスケジューラが管理するMの数も変動するため、これがパフォーマンスのボトルネックになる可能性がありました。

### 新しいPごとの`gcWork`キャッシュの導入

このコミットでは、Mの`currentwbuf`を削除し、代わりにP（論理プロセッサ）に`gcWork`型の`gcw`フィールドを追加します。

```go
type p struct {
    // ...
    gcw gcWork
    // ...
}
```

この変更により、以下の利点がもたらされます。

1.  **同期の不要化**: Pは、特定の時点で1つのMによってのみ使用されるため、Pに紐付けられた`gcw`フィールドへのアクセスは、通常アトミック操作を必要としません。これにより、ライトバリアやGCワーカーが`gcw`にアクセスする際のオーバーヘッドが大幅に削減されます。コミットメッセージにも「Since it's per-P, it doesn't require synchronization」と明記されています。
2.  **シンプルなライフサイクル**: `gcWork`オブジェクトはPに直接紐付けられるため、そのライフサイクル管理が簡素化されます。特に、ミューテータアシスト（GCが不足している場合にユーザープログラムがGCを手伝うこと）中の`dispose()`呼び出しが不要になります。これは、Pごとの`gcw`がGCフェーズの遷移時にのみフラッシュされればよいためです。
3.  **効率的なフラッシング**: Pの数は通常、CPUコアの数に制限されるため、Mの数よりもはるかに少ないです。したがって、すべてのPの`gcw`キャッシュをフラッシュする際の計算量は、Pの数（`# of Ps`）に比例し、これはMの数に比例する場合よりもはるかに効率的です。
4.  **マーク終了時の制御**: 新しいモデルでは、マーク終了時にプリエンプションを許可する前にPごとの`gcw`をフラッシュするというシンプルなルールが適用されます。これにより、GCのポーズ時間を制御しながら、より大きなワークバッファを使用できるようになります。
5.  **ワークスチールとの連携**: `gcWork`は、各プロセッサが独自のローカル`gcWork`キューを維持することで、マルチプロセッサ環境でのパフォーマンスを最適化し、ロック競合を最小限に抑えます。Goランタイムは、Goroutineスケジューラと同様に、ワークスチールメカニズムを採用してワークロードのバランスを取ります。あるプロセッサがワークを使い果たすと、`runtime.gcWork.balance`を使用して別のプロセッサの`gcWork`キューからタスクを「盗む」ことができます。これにより、GCの並行処理がさらに効率化されます。

### ベンチマーク結果

コミットメッセージには、この変更による具体的なベンチマーク結果が示されています。多くのベンチマークでパフォーマンスが向上しており、特に`BenchmarkGoParse`で-64.31%、`BenchmarkHTTPClientServer`で-29.31%、`BenchmarkGobDecode`で-26.14%といった大幅な改善が見られます。これは、ライトバリアのオーバーヘッド削減とワークバッファ管理の効率化が、実際のアプリケーションのパフォーマンスに大きく寄与することを示しています。

## コアとなるコードの変更箇所

このコミットでは、主に以下のファイルが変更されています。

*   `src/runtime/mgc.go`: ガベージコレクションのメインロジックが含まれるファイル。
*   `src/runtime/mgcmark.go`: GCのマークフェーズに関連するロジックが含まれるファイル。
*   `src/runtime/mgcwork.go`: `gcWork`構造体とワークバッファ管理のロジックが含まれるファイル。
*   `src/runtime/runtime2.go`: ランタイムの主要なデータ構造（M, P, Gなど）の定義が含まれるファイル。

具体的な変更点としては、`m`構造体から`currentwbuf`フィールドが削除され、`p`構造体に`gcw gcWork`フィールドが追加されています。また、`mgc.go`, `mgcmark.go`, `mgcwork.go`内の`currentwbuf`への参照が`getg().m.p.ptr().gcw`（現在のGoroutineが実行されているPの`gcw`）に置き換えられ、`initFromCache()`や`disposeToCache()`といったMごとのキャッシュに関連する関数が削除されています。`harvestwbufs()`関数も削除されています。

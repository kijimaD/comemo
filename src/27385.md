## 変更の背景

このコミットの背景には、Goコンパイラのパフォーマンス最適化、特にメモリ割り当ての削減という目標があります。Go言語のガベージコレクタは非常に効率的ですが、不要なメモリ割り当てを減らすことは、ガベージコレクションの頻度を下げ、結果としてプログラム全体の実行速度を向上させる可能性があります。

Goコンパイラ自体もGoで書かれており、そのコンパイルプロセスは非常に多くのオブジェクトを生成・処理します。`Nodes` 型は、コンパイラがソースコードの抽象構文木（AST）を表現するために使用する重要なデータ構造の一つです。この `Nodes` 型のメソッド呼び出しにおいて、実際には `Nodes` オブジェクト自体を変更しない（読み取り専用の）操作であるにもかかわらず、ポインタレシーバ (`*Nodes`) を使用していたために、不必要なメモリ割り当てが発生していました。

このコミットは、このような読み取り専用のメソッドに対して、ポインタレシーバから値レシーバ (`Nodes`) へと変更することで、これらの不要な割り当てを排除し、コンパイラのメモリ効率を向上させることを目的としています。コミットメッセージに示されているベンチマーク結果は、この変更が `allocs/op` (操作あたりの割り当て数) を大幅に削減することを示しており、これはメモリ効率の改善に直結します。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語およびコンパイラに関する前提知識が必要です。

### Go言語のメソッドレシーバ（ポインタレシーバ vs. 値レシーバ）

Go言語では、メソッドを定義する際にレシーバ（メソッドが紐付けられる型）をポインタ型 (`*T`) または値型 (`T`) のいずれかで指定できます。

*   **値レシーバ (`T`)**: メソッドが呼び出されると、レシーバの型の値がコピーされてメソッドに渡されます。メソッド内でレシーバのフィールドを変更しても、元の値には影響しません。これは、メソッドがレシーバの「コピー」に対して操作を行うためです。読み取り専用の操作に適しています。
*   **ポインタレシーバ (`*T`)**: メソッドが呼び出されると、レシーバの型の値へのポインタがメソッドに渡されます。メソッド内でポインタを介してレシーバのフィールドを変更すると、元の値も変更されます。これは、メソッドがレシーバの「実体」に対して操作を行うためです。レシーバの値を変更する必要がある場合や、大きな構造体をコピーするコストを避けたい場合に適しています。

このコミットでは、`Nodes` 型のメソッドが実際にはレシーバの値を変更しないにもかかわらず、ポインタレシーバを使用していたことが問題でした。値レシーバに変更することで、不必要なポインタのデリファレンスや、場合によってはレシーバのコピー（ポインタ自体はコピーされるが、その指す先のデータはコピーされない）に伴うオーバーヘッドを削減できます。

### `cmd/compile` パッケージと `Nodes` 型

`cmd/compile` はGo言語の公式コンパイラの実装です。その中でも `internal/gc` パッケージは、コンパイラの主要なロジック（字句解析、構文解析、型チェック、中間表現の生成など）を含んでいます。

`Nodes` 型は、`src/cmd/compile/internal/gc/syntax.go` で定義されており、Goのソースコードから構築される抽象構文木（AST）のノードのリストを効率的に扱うためのラッパー構造体です。具体的には、`[]*Node` 型のスライスを内部に持ち、そのスライスに対する操作（要素の取得、長さの取得など）を提供するメソッド群を持っています。

```go
type Nodes struct{ slice *[]*Node }
```

この定義からわかるように、`Nodes` 自体は `*[]*Node` というポインタをフィールドに持つ小さな構造体です。

### メモリ割り当てとガベージコレクション

Go言語は自動メモリ管理（ガベージコレクション）を採用しています。プログラムが実行中に新しいオブジェクトを作成すると、ヒープメモリにそのオブジェクトのための領域が割り当てられます。不要になったオブジェクトはガベージコレクタによって自動的に回収されます。

メモリ割り当て（allocation）は、それ自体がコストのかかる操作です。また、割り当てられたオブジェクトが多すぎると、ガベージコレクタがより頻繁に、より多くの作業を行う必要があり、これがプログラムの実行を一時停止させる原因（ストップ・ザ・ワールド）となり、全体的なパフォーマンスに影響を与える可能性があります。

このため、特にコンパイラのようなパフォーマンスが重視されるシステムでは、不必要なメモリ割り当てを削減することが重要な最適化戦略となります。

### ベンチマーク指標 (`alloc/op`, `allocs/op`)

コミットメッセージに記載されているベンチマーク結果は、Goの標準ベンチマークツール (`go test -bench`) によって生成されたものです。

*   `alloc/op`: 1回の操作（ベンチマーク対象の関数呼び出し）あたりに割り当てられたメモリの総量（バイト単位）。
*   `allocs/op`: 1回の操作あたりに発生したメモリ割り当ての回数。

これらの指標は、プログラムのメモリ効率を評価するために使用されます。`allocs/op` の削減は、ガベージコレクションの負荷を直接的に軽減するため、非常に重要な最適化と見なされます。

## 技術的詳細

このコミットの技術的な核心は、Goのコンパイラ内部で使用される `Nodes` 型のメソッドレシーバの変更にあります。

`Nodes` 型は、`slice *[]*Node` というフィールドを持つ構造体です。この構造体自体は非常に小さく、ポインタ1つ分のサイズしかありません。

変更前は、`Nodes` 型のいくつかのメソッド（`Slice`, `Len`, `Index`, `First`, `Second`, `SetIndex`, `Addr`）がポインタレシーバ `*Nodes` を使用していました。

```go
// 変更前 (例: Sliceメソッド)
func (n *Nodes) Slice() []*Node { ... }
```

ポインタレシーバを使用すると、メソッドが呼び出される際に、`Nodes` 構造体へのポインタが渡されます。しかし、これらのメソッドの多くは、`Nodes` 構造体自体（つまり、`n.slice` フィールド）を変更するものではなく、`n.slice` が指す `[]*Node` スライスの中身を読み取ったり、そのスライスへのポインタを返したりするだけでした。

Goのコンパイラは、メソッド呼び出しの際にレシーバの型に基づいてコードを生成します。ポインタレシーバの場合、レシーバがスタック上にない場合や、レシーバがインターフェース値として渡される場合など、特定の状況下でレシーバの値をヒープにエスケープさせ、そのポインタを渡すために追加のメモリ割り当てが発生することがあります。特に、`Nodes` のような小さな構造体であっても、そのポインタが頻繁に渡されるようなコンテキストでは、このオーバーヘッドが積み重なり、`allocs/op` の増加につながります。

このコミットでは、これらのメソッドのレシーバをポインタレシーバ `*Nodes` から値レシーバ `Nodes` に変更しました。

```go
// 変更後 (例: Sliceメソッド)
func (n Nodes) Slice() []*Node { ... }
```

`Nodes` 構造体は非常に小さいため、値レシーバとして渡されてもコピーのコストは非常に小さいです（ポインタ1つ分のコピー）。そして、値レシーバとして渡されることで、コンパイラはメソッド呼び出しの際に `Nodes` 構造体自体をヒープに割り当てる必要がなくなります。これにより、特に読み取り専用の操作において、不必要なメモリ割り当てが削減されます。

コミットメッセージに示されているベンチマーク結果は、この変更の有効性を明確に示しています。

*   `alloc/op` (操作あたりのメモリ総量) はわずかに減少していますが、これは主に `allocs/op` の減少によるものです。
*   `allocs/op` (操作あたりの割り当て回数) は、`Template` で10.42%、`GoTypes` で11.18%、`Compiler` で15.51%と大幅に減少しています。これは、コンパイラの実行中に発生するメモリ割り当ての回数が劇的に減ったことを意味します。

`allocs/op` の削減は、ガベージコレクタが処理すべきオブジェクトの数を減らし、結果としてガベージコレクションの頻度や実行時間を短縮する効果が期待できます。コミットメッセージでは「明確な実行時間への影響はない」とされていますが、これはウォールタイム（実時間）での測定では顕著な差が出なかったという意味であり、メモリ効率の改善自体は重要な最適化です。特に、大規模なGoプロジェクトのコンパイル時など、コンパイラが長時間動作する場合には、この改善が累積的なパフォーマンス向上に寄与する可能性があります。

## コアとなるコードの解説

これらのメソッドは、`Nodes` 構造体が内部に持つ `*[]*Node` スライスへのポインタを介して、ASTノードのリストを操作します。

例えば、`Slice()` メソッドは、`Nodes` オブジェクトがラップしているスライスを返します。`Len()` はスライスの長さを返します。`Index()` は特定インデックスのノードを返します。これらの操作は、`Nodes` 構造体自体（つまり `n.slice` フィールドが指すポインタ）を変更するものではありません。`SetIndex()` や `Addr()` はスライスの中身を変更しますが、`Nodes` 構造体自体を変更するわけではありません。

変更前は、これらのメソッドが `*Nodes` というポインタレシーバを持っていたため、メソッドが呼び出されるたびに `Nodes` 構造体へのポインタが渡されていました。Goのコンパイラは、ポインタレシーバを持つメソッドを呼び出す際に、レシーバがアドレス可能でない場合（例えば、一時的な値である場合）に、そのレシーバをヒープにエスケープさせてアドレス可能にするための割り当てを行うことがあります。`Nodes` は小さな構造体ですが、コンパイラの内部で非常に頻繁にこれらのメソッドが呼び出されるため、この小さな割り当てが積み重なって、`allocs/op` の増加につながっていました。

変更後は、レシーバが `Nodes` という値型になりました。`Nodes` 構造体はポインタ1つ分のサイズしかなく、非常に小さいため、値渡しによるコピーのコストは無視できるほど小さいです。そして、値レシーバとして渡されることで、コンパイラはメソッド呼び出しの際に `Nodes` 構造体自体をヒープに割り当てる必要がなくなります。これにより、不必要なメモリ割り当てが削減され、`allocs/op` の指標が大幅に改善されました。

特に `SetIndex` や `Addr` のように、内部のスライスを変更するメソッドであっても、`Nodes` 構造体自体は変更しないため、値レシーバで問題ありません。これらのメソッドは `n.slice` が指すスライスの中身を変更するだけであり、`n.slice` 自体（つまり `Nodes` 構造体のフィールド）を変更するわけではないからです。

この最適化は、Goコンパイラのような大規模でパフォーマンスが重要なアプリケーションにおいて、細かなメモリ割り当ての削減がいかに重要であるかを示す良い例です。

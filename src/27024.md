# [インデックス 27024] ファイルの概要

## 変更の背景

Go言語の初期開発段階において、リンカ (`cmd/link`) はC言語で実装されていました。Go言語の哲学の一つに「Goで書かれたツールはGoで書く」というものがあり、これに従い、リンカをGo言語で再実装するプロジェクトが `cmd/newlink` として開始されました。これは、よりクリーンな設計とGo言語の機能活用を目指したものでした。

しかし、開発が進むにつれて、既存のC言語版 `cmd/link` をGo言語に変換するアプローチが採用されることになりました。この変換作業は成功し、Goのビルドモード（共有ライブラリ、PIEなど）に関する多くの機能や改善が `cmd/link` に集約されていきました。結果として、`cmd/newlink` はその存在意義を失い、冗長なコードベースとなっていました。

さらに、`cmd/newlink` はリリースプロセスにおいて削除する必要があるディレクトリであり、そのテストデータはGoのオブジェクトファイルフォーマット（`.6` 形式）の変更があるたびに壊れるという問題も抱えていました。これらの問題を解決し、コードベースを整理するために、`cmd/newlink` を完全に削除する決定がなされました。

## 前提知識の解説

### リンカ (Linker)
リンカは、コンパイラやアセンブラによって生成された複数のオブジェクトファイル（機械語コードとデータを含む）を結合し、実行可能なプログラムやライブラリを生成するプログラムです。主な役割は以下の通りです。
*   **シンボル解決**: 異なるオブジェクトファイル間で参照される関数や変数のアドレスを解決します。
*   **再配置 (Relocation)**: オブジェクトファイル内のコードやデータが最終的なメモリ上のどこに配置されるかに応じて、アドレス参照を修正します。
*   **実行可能形式の生成**: オペレーティングシステムがロードして実行できる形式（ELF, Mach-O, PEなど）にプログラムをパッケージ化します。

### Goツールチェイン
Go言語のビルドプロセスは、主に以下のツールで構成されます。
*   **`go tool compile`**: Goソースコードをオブジェクトファイル（`.o` または `.a`）にコンパイルします。
*   **`go tool asm`**: アセンブリ言語ソースコードをオブジェクトファイルにアセンブルします。
*   **`go tool link`**: オブジェクトファイルをリンクして実行可能ファイルを生成します。

### Goのオブジェクトファイルフォーマット (`.6` 形式)
Go言語のコンパイラとアセンブラは、独自のオブジェクトファイルフォーマットを使用します。このフォーマットは、Goのランタイム情報（型情報、GC情報、スタックフレーム情報など）を効率的に格納するために設計されています。コミットメッセージにある `.6` は、Goの初期のバージョンでAMD64アーキテクチャのオブジェクトファイルに付けられていた拡張子を指すことが多いです。このフォーマットはGoのバージョンアップに伴い変更されることがあり、それに追従できない古いツールは問題を引き起こす可能性があります。

### ビルドモード (Build Modes)
Go言語は、様々なビルドモードをサポートしています。これには、標準の実行可能ファイル（`go build`）、共有ライブラリ（`go build -buildmode=c-shared`）、プラグイン（`go build -buildmode=plugin`）、Position-Independent Executables (PIE) などがあります。これらのビルドモードは、リンカが生成する出力形式や、実行時のメモリ配置、シンボル解決の挙動に大きな影響を与えます。

## 技術的詳細

このコミットの技術的詳細の核心は、Goリンカの開発戦略の転換と、それに伴うコードベースの合理化にあります。

1.  **リンカ実装の一本化**:
    *   当初、GoリンカはC言語で書かれた `cmd/link` と、Go言語で書かれた `cmd/newlink` の二つの系統が存在していました。
    *   `cmd/newlink` は「クリーンなGoによる再実装」という理想を追求しましたが、現実的には既存の `cmd/link` が持つ機能（特に複雑なビルドモードのサポートなど）を追いつくのが困難でした。
    *   最終的に、GoチームはC言語版 `cmd/link` をGo言語に変換するアプローチを選択しました。これにより、長年の開発で培われた `cmd/link` の堅牢性と機能性を維持しつつ、Go言語の利点（保守性、並行処理など）を享受できるようになりました。この変換は、Go 1.5リリースサイクルで行われました。

2.  **`cmd/newlink` の問題点**:
    *   **リリースからの削除の必要性**: `cmd/newlink` は開発中の実験的なリンカであり、Goの公式リリースには含まれるべきではありませんでした。そのため、リリースごとに手動で削除する手間が発生していました。
    *   **テストデータの互換性問題**: `cmd/newlink` のテストデータは、Goのオブジェクトファイルフォーマット（`.6` 形式など）の変更に非常に敏感でした。Goのコンパイラやアセンブラが進化し、オブジェクトファイルフォーマットが更新されるたびに、`cmd/newlink` のテストデータが古くなり、テストが失敗するという問題が頻繁に発生していました。これは、Goツールチェイン全体の開発速度を阻害する要因となっていました。

3.  **削除の決定**:
    *   `cmd/link` がGo言語に変換され、すべての主要なリンカ機能とビルドモードのサポートがそちらに集約されたことで、`cmd/newlink` は完全に冗長な存在となりました。
    *   上記の問題点（リリース時の手間、テストデータの破損）を考慮すると、`cmd/newlink` を維持するコストは、そのメリットをはるかに上回ると判断されました。
    *   このコミットは、Goツールチェインのコードベースを整理し、将来の開発を簡素化するための戦略的な決定でした。

この削除は、Go言語のツールチェインが成熟し、開発リソースが最も効率的な場所に集中されるようになったことを示しています。

## コアとなるコードの変更箇所

このコミットは、`src/cmd/newlink` ディレクトリ全体を削除するものです。具体的な変更は以下の通りです。

*   `misc/nacl/testzip.proto` から `newlink` 関連のエントリが削除されました。
*   `src/cmd/newlink/` ディレクトリ内の以下のファイルがすべて削除されました。
    *   `auto.go`, `auto_test.go`: 自動生成されるシンボルに関するコードとテスト。
    *   `dead.go`, `dead_test.go`: デッドコード削除に関するコードとテスト。
    *   `debug.go`: デバッグデータ生成に関するコード。
    *   `hex_test.go`: 16進ダンプのパースに関するテストユーティリティ。
    *   `layout.go`, `layout_test.go`: 実行可能イメージのレイアウト（アドレス割り当て）に関するコードとテスト。
    *   `link_test.go`: リンカの基本的なテスト。
    *   `load.go`: パッケージファイルからのコードとデータのロード、再配置に関するコード。
    *   `macho.go`, `macho_test.go`: Mach-O (Darwin) 形式のオブジェクトファイル書き込みに関するコードとテスト。
    *   `main.go`: `cmd/newlink` のエントリポイント（プレースホルダー）。
    *   `pclntab.go`, `pclntab_test.go`: ランタイム関数情報 (pclntab) の生成に関するコードとテスト。
    *   `prog.go`, `prog_test.go`: プログラム構造の定義とテスト。
    *   `runtime.go`: ランタイム関連のシンボル定義。
    *   `scan.go`: オブジェクトファイルのスキャンに関するコード。
    *   `util.go`: ユーティリティ関数。
    *   `write.go`: 実行可能ファイルの書き込みに関するコード。
*   `src/cmd/newlink/testdata/` ディレクトリ内のテストデータファイルもすべて削除されました。これには、`.6` 形式のオブジェクトファイル、アセンブリソースファイル（`.s`）、Makefileなどが含まれます。

合計で38ファイルが変更され、5216行が削除されました。これは、`cmd/newlink` プロジェクトのコードベース全体が削除されたことを意味します。

## コアとなるコードの解説

このコミットにおける「コアとなるコードの変更」は、既存のコードの削除そのものです。したがって、解説は削除されたコードが何であったか、そしてその削除が何を意味するかについて焦点を当てます。

`src/cmd/newlink` ディレクトリには、Go言語で書かれたリンカの各ステージを実装する多数のGoファイルが含まれていました。

*   **`auto.go`**: リンカが自動的に生成するシンボル（例: 浮動小数点定数 `$f64.` や `$f32.`、リンカが定義する `runtime.` プレフィックスのシンボル）の処理を担当していました。
*   **`dead.go`**: 実行可能ファイルから到達不能なコードやデータを削除する、いわゆるデッドコードエリミネーションのロジックを実装していました。これは、最終的なバイナリサイズを削減するために重要な最適化です。
*   **`layout.go`**: 実行可能ファイルのメモリレイアウトを決定し、セクション（テキスト、データ、ロデータなど）やセグメント（テキストセグメント、データセグメントなど）にシンボルを配置し、アドレスを割り当てる役割を担っていました。
*   **`load.go`**: コンパイル済みのGoパッケージファイルからオブジェクトコードとデータをロードし、再配置（リロケーション）を適用する機能を提供していました。再配置は、シンボルが最終的に配置されるアドレスに基づいて、コード内のアドレス参照を修正するプロセスです。
*   **`macho.go`**: macOS (Darwin) で使用されるMach-O形式の実行可能ファイルを生成するためのコードが含まれていました。これは、特定のOSのバイナリフォーマットに合わせた出力処理です。
*   **`pclntab.go`**: Goのランタイムがスタックトレース、ガベージコレクション、プロファイリングなどのために使用するPC-Lineテーブル（`pclntab`）を生成するコードでした。このテーブルは、プログラムカウンタ（PC）とソースコードの行番号、関数情報などをマッピングします。

これらのファイル群は、Goリンカが実行可能ファイルを生成するために必要な主要な機能（シンボル解決、メモリレイアウト、オブジェクトファイルのロード、再配置、デッドコード削除、OS固有のバイナリフォーマット生成、ランタイムメタデータ生成）を網羅していました。

このコミットによるこれらのファイルの削除は、これらの機能が `cmd/newlink` ではなく、既存の `cmd/link` にて実装・維持されることになったという、Goツールチェインの設計における重要な決定を反映しています。これにより、開発リソースの分散が解消され、リンカの機能開発と保守が一本化されました。

## 前提知識の解説

### リンカ (Linker)
リンカは、コンパイラやアセンブラによって生成された複数のオブジェクトファイル（機械語コードとデータを含む）を結合し、実行可能なプログラムやライブラリを生成するプログラムです。主な役割は以下の通りです。
*   **シンボル解決**: 異なるオブジェクトファイル間で参照される関数や変数のアドレスを解決します。
*   **再配置 (Relocation)**: オブジェクトファイル内のコードやデータが最終的なメモリ上のどこに配置されるかに応じて、アドレス参照を修正します。
*   **実行可能形式の生成**: オペレーティングシステムがロードして実行できる形式（ELF, Mach-O, PEなど）にプログラムをパッケージ化します。

### Goツールチェイン
Go言語のビルドプロセスは、主に以下のツールで構成されます。
*   **`go tool compile`**: Goソースコードをオブジェクトファイル（`.o` または `.a`）にコンパイルします。
*   **`go tool asm`**: アセンブリ言語ソースコードをオブジェクトファイルにアセンブルします。
*   **`go tool link`**: オブジェクトファイルをリンクして実行可能ファイルを生成します。

### Goのオブジェクトファイルフォーマット (`.6` 形式)
Go言語のコンパイラとアセンブラは、独自のオブジェクトファイルフォーマットを使用します。このフォーマットは、Goのランタイム情報（型情報、GC情報、スタックフレーム情報など）を効率的に格納するために設計されています。コミットメッセージにある `.6` は、Goの初期のバージョンでAMD64アーキテクチャのオブジェクトファイルに付けられていた拡張子を指すことが多いです。このフォーマットはGoのバージョンアップに伴い変更されることがあり、それに追従できない古いツールは問題を引き起こす可能性があります。

### ビルドモード (Build Modes)
Go言語は、様々なビルドモードをサポートしています。これには、標準の実行可能ファイル（`go build`）、共有ライブラリ（`go build -buildmode=c-shared`）、プラグイン（`go build -buildmode=plugin`）、Position-Independent Executables (PIE) などがあります。これらのビルドモードは、リンカが生成する出力形式や、実行時のメモリ配置、シンボル解決の挙動に大きな影響を与えます。

3.  **削除の決定**:
    *   `cmd/link` がGo言語に変換され、すべての主要なリンカ機能とビルドモードのサポートがそちらに集約されたことで、`cmd/newlink` は完全に冗長な存在となりました。
    *   上記の問題点（リリース時の手間、テストデータの破損）を考慮すると、`cmd/newlink` を維持するコストは、そのメリットをはるかに上回ると判断されました。
    *   このコミットは、Goツールチェインのコードベースを整理し、将来の開発を簡素化するための戦略的な決定でした。

この削除は、Go言語のツールチェインが成熟し、開発リソースが最も効率的な場所に集中されるようになったことを示しています。

## コアとなるコードの変更箇所

*   `src/cmd/newlink/` ディレクトリ内の以下のファイルがすべて削除されました。

    *   `link_test.go`: リンカの基本的なテスト。
    *   `load.go`: パッケージファイルからのコードとデータのロード、再配置に関するコード。

## コアとなるコードの解説

このコミットにおける「コアとなるコードの変更」は、既存のコードの削除そのものです。したがって、解説は削除されたコードが何であったか、そしてその削除が何を意味するかについて焦点を当てます。

`src/cmd/newlink` ディレクトリには、Go言語で書かれたリンカの各ステージを実装する多数のGoファイルが含まれていました。

*   **`auto.go`**: リンカが自動的に生成するシンボル（例: 浮動小数点定数 `$f64.` や `$f32.`、リンカが定義する `runtime.` プレフィックスのシンボル）の処理を担当していました。
*   **`dead.go`**: 実行可能ファイルから到達不能なコードやデータを削除する、いわゆるデッドコードエリミネーションのロジックを実装していました。これは、最終的なバイナリサイズを削減するために重要な最適化です。
*   **`layout.go`**: 実行可能ファイルのメモリレイアウトを決定し、セクション（テキスト、データ、ロデータなど）やセグメント（テキストセグメント、データセグメントなど）にシンボルを配置し、アドレスを割り当てる役割を担っていました。
*   **`load.go`**: コンパイル済みのGoパッケージファイルからオブジェクトコードとデータをロードし、再配置（リロケーション）を適用する機能を提供していました。再配置は、シンボルが最終的に配置されるアドレスに基づいて、コード内のアドレス参照を修正するプロセスです。
*   **`macho.go`**: macOS (Darwin) で使用されるMach-O形式の実行可能ファイルを生成するためのコードが含まれていました。これは、特定のOSのバイナリフォーマットに合わせた出力処理です。
*   **`pclntab.go`**: Goのランタイムがスタックトレース、ガベージコレクション、プロファイリングなどのために使用するPC-Lineテーブル（`pclntab`）を生成するコードでした。このテーブルは、プログラムカウンタ（PC）とソースコードの行番号、関数情報などをマッピングします。

これらのファイル群は、Goリンカが実行可能ファイルを生成するために必要な主要な機能（シンボル解決、メモリレイアウト、オブジェクトファイルのロード、再配置、デッドコード削除、OS固有のバイナリフォーマット生成、ランタイムメタデータ生成）を網羅していました。

このコミットによるこれらのファイルの削除は、これらの機能が `cmd/newlink` ではなく、既存の `cmd/link` にて実装・維持されることになったという、Goツールチェインの設計における重要な決定を反映しています。これにより、開発リソースの分散が解消され、リンカの機能開発と保守が一本化されました。

# [インデックス 26678] ファイルの概要

## 元コミット内容

`cmd/compile: make cmpstackvarlt properly asymmetric`

以前は、異なる非 `PAUTO` クラス（例: `PPARAM` と `PPARAMOUT`）の2つの `Node` `n1` と `n2` が与えられた場合、`cmpstackvarlt(n1, n2)` と `cmpstackvarlt(n2, n1)` の両方が `true` を返していました。これは意味をなしません。

この問題は、目に見えるコンパイルの誤りを引き起こしているようには見えませんでしたが、修正すると `toolstash/buildall` が失敗することが判明しました。

## 変更の背景

Goコンパイラは、関数のスタックフレーム内で変数をどのように配置するかを決定するために、スタック変数をソートする必要があります。このソート処理には、`cmpstackvarlt` という比較関数が使用されます。この関数は、2つのスタック変数 `Node` を受け取り、最初の変数が2番目の変数よりも「小さい」と判断される場合に `true` を返します。

コミットメッセージが指摘するように、以前の実装では、特定の条件下でこの比較関数が非対称性を欠いていました。具体的には、`PPARAM` (関数引数) と `PPARAMOUT` (戻り値) のように、スタック上の異なるセクションに属するが、どちらも自動変数 (`PAUTO`) ではない2つの変数を比較する際に、`A < B` と `B < A` の両方が `true` と評価されるという論理的な矛盾がありました。これは、比較関数が厳密な弱順序付け (strict weak ordering) の要件を満たしていないことを意味します。

このような比較関数の欠陥は、ソートアルゴリズムの不安定性や予期せぬ動作を引き起こす可能性があります。たとえ目に見えるコンパイルエラーが発生していなかったとしても、コンパイラの内部的な整合性を保つ上で修正が必要でした。特に、この修正が `toolstash/buildall` の失敗を引き起こしたという事実は、この比較ロジックがコンパイラの他の部分に微妙な影響を与えていたことを示唆しています。`toolstash/buildall` は、Goツールチェーン全体の整合性を検証するための重要なテストスイートであり、その失敗は潜在的なバグや非互換性の存在を強く示します。

    *   **`PPARAM`**: 関数への入力引数。スタック上に割り当てられます。

*   **`cmpstackvarlt`**: `cmd/compile/internal/gc/pgen.go` 内に定義されている関数で、2つのスタック変数 `Node` を比較し、ソート順を決定するために使用されます。この関数は、スタック変数を特定の順序で並べ替えることで、スタックフレームのレイアウトを最適化したり、デバッグ情報の生成を容易にしたりする目的があります。
*   **厳密な弱順序付け (Strict Weak Ordering)**: ソートアルゴリズムが正しく機能するために、比較関数が満たすべき数学的な特性のセットです。主な要件は以下の通りです。
    1.  **非反射性**: `a < a` は常に `false` である。
    2.  **非対称性**: `a < b` が `true` ならば、`b < a` は `false` である。
    3.  **推移性**: `a < b` と `b < c` が `true` ならば、`a < c` も `true` である。
    4.  **同値性の推移性**: `a` と `b` が同値であり、`b` と `c` が同値ならば、`a` と `c` も同値である。（ここで「同値」とは `!(a < b) && !(b < a)` を意味します。）
    このコミットで修正された問題は、特に「非対称性」の違反に該当します。
*   **`toolstash/buildall`**: Goプロジェクトのテストスイートの一部で、Goツールチェーン全体（コンパイラ、リンカ、標準ライブラリなど）をビルドし、そのビルドされたツールチェーンを使ってGoの標準ライブラリやその他の重要なパッケージをコンパイル・テストするものです。これは、Goツールチェーンの変更が広範囲にわたる影響を与えないことを保証するための包括的な回帰テストとして機能します。

## 技術的詳細

`cmpstackvarlt` 関数は、スタック変数をソートするための比較ロジックを提供します。この関数は、主に以下の優先順位で変数を比較します。

1.  **`PAUTO` クラスの優先順位**: `PAUTO` (自動変数) は他のクラス (`PPARAM`, `PPARAMOUT` など) とは異なるソート順序を持つことがあります。
2.  **`Xoffset` (オフセット)**: `PAUTO` 以外の変数については、スタックフレームの先頭からのオフセット `Xoffset` に基づいてソートされます。オフセットが小さいほど「小さい」と見なされます。
3.  **`Used` フラグ**: `PAUTO` 変数については、`Used` フラグ（変数が使用されているかどうか）に基づいてソートされます。
4.  **`Type.Width` (型の幅)**: 変数の型のサイズ（バイト単位）に基づいてソートされます。
5.  **`Sym.Name` (シンボル名)**: 最終的なタイブレーカーとして、シンボル名に基づいてソートされます。

以前の実装では、`a.Class != b.Class` かつ `a.Class != PAUTO` かつ `b.Class != PAUTO` の場合に、`a` と `b` のどちらが `PAUTO` でないかに関わらず、`true` を返していました。これは、`PPARAM` と `PPARAMOUT` のような異なる非 `PAUTO` クラスのノードが比較された際に、`cmpstackvarlt(PPARAM, PPARAMOUT)` も `cmpstackvarlt(PPARAMOUT, PPARAM)` も `true` を返すという非対称性の問題を引き起こしていました。

このコミットでは、この非対称性を修正するために、`cmpstackvarlt` のロジックが変更されました。

**変更点:**

1.  **`PAUTO` クラスの比較ロジックの修正:**
    変更前:
    ```go
    if a.Class != b.Class {
        if a.Class == PAUTO {
            return false
        }
        return true
    }
    ```
    変更後:
    ```go
    if (a.Class == PAUTO) != (b.Class == PAUTO) {
        return b.Class == PAUTO
    }
    ```
    この変更により、`a` と `b` のどちらか一方だけが `PAUTO` である場合に、`PAUTO` でない方が「小さい」と見なされるようにロジックが明確化されました。これにより、`PAUTO` と非`PAUTO` の間の比較が厳密に定義され、非対称性が解消されます。

2.  **非`PAUTO` クラスの `Xoffset` 比較の簡素化:**
    変更前:
    ```go
    if a.Class != PAUTO {
        if a.Xoffset < b.Xoffset {
            return true
        }
        if a.Xoffset > b.Xoffset {
            return false
        }
        return false
    }
    ```
    変更後:
    ```go
    if a.Class != PAUTO {
        return a.Xoffset < b.Xoffset
    }
    ```
    これは、`a.Xoffset < b.Xoffset` が `true` の場合に `true` を返し、それ以外の場合（`a.Xoffset >= b.Xoffset`）に `false` を返すという、より簡潔で一般的な比較ロジックに置き換えられました。これにより、`Xoffset` に基づく比較が厳密な弱順序付けの要件を満たすようになります。

3.  **`Type.Width` 比較の修正:**
    変更前:
    ```go
    if a.Type.Width < b.Type.Width {
        return false
    }
    if a.Type.Width > b.Type.Width {
        return true
    }
    ```
    変更後:
    ```go
    if a.Type.Width != b.Type.Width {
        return a.Type.Width > b.Type.Width
    }
    ```
    この変更は、型の幅が異なる場合に、幅が大きい方を「小さい」と見なすように修正しています。これは、スタックレイアウトの特定の最適化戦略に関連している可能性があります。以前のロジックでは、幅が小さい方を「小さい」と見なしていましたが、この修正により逆転しています。

これらの変更により、`cmpstackvarlt` 関数は厳密な弱順序付けの要件を満たすようになり、ソートアルゴリズムがより予測可能で安定した動作をするようになります。

## コアとなるコードの解説

`cmpstackvarlt` 関数は、Goコンパイラの `gc` パッケージ内でスタック変数をソートするために使用される比較関数です。この関数は、`*Node` 型の2つの引数 `a` と `b` を受け取り、`a` が `b` よりも「小さい」場合に `true` を返します。

変更された主要なロジックは以下の通りです。

1.  **`PAUTO` クラスの優先順位の明確化:**
    ```go
    if (a.Class == PAUTO) != (b.Class == PAUTO) {
        return b.Class == PAUTO
    }
    ```
    このコードブロックは、`a` と `b` のどちらか一方のみが `PAUTO` クラスである場合に実行されます。
    *   もし `a` が `PAUTO` でなく、`b` が `PAUTO` であれば (`(false) != (true)` は `true`)、`b.Class == PAUTO` は `true` を返すため、`a` が `b` よりも小さいと判断されます。つまり、非 `PAUTO` 変数は `PAUTO` 変数よりも先にソートされます。
    *   もし `a` が `PAUTO` で、`b` が `PAUTO` でなければ (`(true) != (false)` は `true`)、`b.Class == PAUTO` は `false` を返すため、`a` が `b` よりも小さいとは判断されません。
    このロジックにより、`PAUTO` 変数と非 `PAUTO` 変数の間の比較が厳密に非対称になります。

2.  **非 `PAUTO` 変数の `Xoffset` による比較:**
    ```go
    if a.Class != PAUTO {
        return a.Xoffset < b.Xoffset
    }
    ```
    このブロックは、`a` と `b` の両方が `PAUTO` でない場合（または両方が `PAUTO` であるが、最初のブロックで処理されなかった場合）に、`a.Class != PAUTO` が `true` であれば実行されます。
    ここで、`a.Xoffset < b.Xoffset` という簡潔な比較が行われます。これは、スタックオフセットが小さい変数ほど「小さい」と見なすという、一般的な数値比較の原則に従います。これにより、非 `PAUTO` 変数間のソート順が `Xoffset` に基づいて一貫して決定されます。

3.  **`Type.Width` による比較の修正:**
    ```go
    if a.Type.Width != b.Type.Width {
        return a.Type.Width > b.Type.Width
    }
    ```
    このブロックは、`a` と `b` のクラス、`Xoffset`、`Used` フラグなどが全て同じで、型の幅が異なる場合に実行されます。
    `a.Type.Width > b.Type.Width` は、`a` の型幅が `b` の型幅よりも大きい場合に `true` を返します。これは、幅の大きい変数を先にソートするという意図を示唆しています。これは、スタックアライメントやパディングの最適化に関連している可能性があります。

これらの変更と、追加されたテストケースは、`cmpstackvarlt` が厳密な弱順序付けの特性を満たし、コンパイラのスタック変数ソートロジックがより堅牢で予測可能になることを保証します。特に、`PPARAM` と `PPARAMOUT` のような異なる非 `PAUTO` クラスのノード間の比較が正しく非対称になるように修正された点が重要です。

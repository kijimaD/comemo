This change does two main things:

## 変更の背景

この変更の主な背景は、Goの `net/http` クライアントにHTTP/2プロトコルのサポートを導入することです。HTTP/2は、HTTP/1.1と比較してパフォーマンスの向上（多重化、ヘッダー圧縮、サーバープッシュなど）をもたらす次世代のHTTPプロトコルであり、ウェブの高速化に不可欠です。

しかし、HTTP/2の導入は単純ではありません。特に、クライアントがサーバーと通信を開始する際に、どのプロトコル（HTTP/1.1かHTTP/2か）を使用するかを事前に知る必要があります。これは通常、TLS (Transport Layer Security) ハンドシェイク中に NPN (Next Protocol Negotiation) または ALPN (Application-Layer Protocol Negotiation) と呼ばれるメカニズムを通じてネゴシエートされます。

このコミットは、HTTP/2クライアントを `net/http.Transport` に統合するための初期ステップとして、以下の課題に対処しようとしています。

1.  **プロトコルネゴシエーションのハンドリング**: TLSハンドシェイク後に決定されたプロトコルに基づいて、適切な `RoundTripper` (HTTP/1.1用またはHTTP/2用) を選択するメカニズムが必要です。
2.  **代替プロトコル処理の柔軟性**: `Transport.RegisterProtocol` を使用して代替プロトコルハンドラを登録する際、そのハンドラが特定の状況で処理をスキップし、`Transport` のデフォルトの処理にフォールバックできるような仕組みが必要です。これは、例えばHTTP/2ハンドラがキャッシュされた接続を持っていない場合に、HTTP/1.1ハンドラに処理を委譲するといったシナリオで役立ちます。
3.  **既存の `Transport` との統合**: 既存の `net/http.Transport` の設計を大きく変更することなく、HTTP/2の機能を段階的に追加できるような拡張ポイントが必要です。

このコミットは、これらの課題に対する解決策として `Transport.TLSNextProto` と `ErrSkipAltProtocol` を導入し、HTTP/2クライアントの「配線」を開始するものです。コミットメッセージにもある通り、この時点ではHTTP/2はまだデフォルトで無効化されており、開発中の機能として位置づけられています。

## 前提知識の解説

### HTTP/1.1 と HTTP/2

*   **HTTP/1.1**: 現在広く使われているHTTPプロトコルのバージョン。リクエストとレスポンスは通常、TCP接続ごとに1つずつ処理され、パイプライン処理は可能ですが、ヘッドオブラインブロッキングの問題があります。
*   **HTTP/2**: HTTP/1.1のセマンティクスを維持しつつ、パフォーマンスを大幅に向上させるために設計されたプロトコル。主な特徴は以下の通りです。
    *   **多重化 (Multiplexing)**: 1つのTCP接続上で複数のリクエストとレスポンスを同時に送受信できます。これにより、ヘッドオブラインブロッキングが解消されます。
    *   **ヘッダー圧縮 (Header Compression)**: HTTPヘッダーを効率的に圧縮するHPACKアルゴリズムを使用し、オーバーヘッドを削減します。
    *   **サーバープッシュ (Server Push)**: クライアントがリクエストする前に、サーバーがクライアントにリソースをプッシュできます。
    *   **バイナリフレーミング**: HTTP/1.1のテキストベースとは異なり、HTTP/2はバイナリプロトコルです。

### TLS (Transport Layer Security)

TLSは、インターネット上で安全な通信を提供するための暗号化プロトコルです。ウェブブラウザとサーバー間のHTTPS通信の基盤となっています。TLSハンドシェイク中に、クライアントとサーバーは暗号スイートやプロトコルバージョンなどの通信パラメータをネゴシエートします。

### NPN (Next Protocol Negotiation) / ALPN (Application-Layer Protocol Negotiation)

NPNとALPNは、TLSハンドシェイク中にクライアントとサーバーがどのアプリケーションプロトコル（例: HTTP/1.1、HTTP/2）を使用するかをネゴシエートするための拡張機能です。

*   **NPN**: GoogleがSPDYのために開発したプロトコルで、クライアントがサポートするプロトコルリストをサーバーに送り、サーバーがその中から1つを選択してクライアントに通知します。
*   **ALPN**: NPNの後継としてIETFによって標準化されたプロトコル。NPNと同様に、クライアントがサポートするプロトコルリストをサーバーに送り、サーバーが選択します。ALPNはNPNよりも広く採用されており、HTTP/2の標準的なプロトコルネゴシエーションメカニズムです。

これらのメカニズムにより、クライアントはTCP接続を確立し、TLSハンドシェイクを完了した後で、初めてどのHTTPプロトコルで通信すべきかを知ることができます。

### Goの `net/http` パッケージ

Goの `net/http` パッケージは、HTTPクライアントとサーバーを実装するための強力な機能を提供します。

*   **`Transport`**: `http.Client` が実際にHTTPリクエストを送信し、レスポンスを受信する低レベルのインターフェースを実装する型です。接続の確立、接続の再利用（キープアライブ）、プロキシの処理、TLSハンドシェイクなどを担当します。
*   **`RoundTripper` インターフェース**: `type RoundTripper interface { RoundTrip(*Request) (*Response, error) }` と定義されており、HTTPリクエストを受け取り、HTTPレスポンスを返す単一のメソッド `RoundTrip` を持ちます。`http.Client` は内部で `RoundTripper` を使用してリクエストを処理します。`Transport` 型はこの `RoundTripper` インターフェースを実装しています。
*   **`Transport.RegisterProtocol`**: 特定のURLスキーム（例: "ftp", "file"）に対してカスタムの `RoundTripper` を登録するためのメソッドです。これにより、`net/http` クライアントが標準の `http` や `https` 以外のプロトコルを処理できるようになります。このコミット以前は、"http" や "https" スキームを登録しようとするとパニックを起こしていました。

## 技術的詳細

このコミットは、HTTP/2クライアントの統合に向けた2つの主要な変更と、それに伴ういくつかの調整を含んでいます。

### 1. `Transport.TLSNextProto` の導入

*   **目的**: TLSハンドシェイク中にNPN/ALPNによってネゴシエートされたプロトコルに基づいて、HTTP/1.1とHTTP/2のどちらの `RoundTripper` を使用するかを動的に決定するための「接着剤」を提供します。
*   **構造**: `TLSNextProto` は `map[string]func(authority string, c *tls.Conn) RoundTripper` 型のフィールドとして `Transport` 構造体に追加されます。
    *   キー (`string`) は、TLSハンドシェイクでネゴシエートされたプロトコル名（例: "h2" はHTTP/2、"http/1.1" はHTTP/1.1）です。
    *   値 (`func(authority string, c *tls.Conn) RoundTripper`) は、そのプロトコルが選択された場合に呼び出される関数です。この関数は、接続先のホスト情報 (`authority`) と確立されたTLS接続 (`*tls.Conn`) を受け取り、そのプロトコルを処理するための `RoundTripper` インスタンスを返します。
*   **`Server.TLSNextProto` との類似性**: 既存の `http.Server` にも同様の `TLSNextProto` フィールドがあり、サーバー側でNPN/ALPNの結果に基づいてカスタムハンドラを登録するために使用されます。クライアント側にも同様のメカニズムを導入することで、一貫性のあるプロトコルネゴシエーション処理が可能になります。
*   **`dialConn` メソッドでの利用**: `Transport` の `dialConn` メソッド（接続を確立する部分）内で、TLS接続が確立され、NPN/ALPNによってプロトコルがネゴシエートされた後、`TLSNextProto` マップがチェックされます。もしネゴシエートされたプロトコルに対応するエントリがあれば、その関数が呼び出され、返された `RoundTripper` が `persistConn` の `alt` フィールドに設定されます。

### 2. `ErrSkipAltProtocol` の導入と `RegisterProtocol` のセマンティクス変更

*   **`ErrSkipAltProtocol`**: `errors.New("net/http: skip alternate protocol")` として定義される新しいセンチネルエラー値です。
*   **`Transport.RegisterProtocol` の変更**:
    *   このコミット以前は、`RegisterProtocol` で "http" または "https" スキームを登録しようとするとパニックを起こしていました。この変更により、これらのスキームの登録が許可されるようになります。
    *   最も重要な変更は、`RegisterProtocol` で登録された `RoundTripper` が `ErrSkipAltProtocol` を返した場合のセマンティクスです。このエラーが返されると、`Transport` はその代替プロトコルハンドラが登録されていなかったかのように振る舞い、自身のデフォルトの `RoundTrip` メソッド（通常はHTTP/1.1処理）を続行します。
*   **目的**: このメカニズムは、HTTP/2クライアントの統合において非常に重要です。例えば、`https` スキームに対してHTTP/2を処理する `RoundTripper` を登録できます。このHTTP/2 `RoundTripper` は、既存のキャッシュされたHTTP/2接続がある場合はそれを使用しようとしますが、もし適切な接続がない場合や何らかの理由でHTTP/2での処理ができない場合に `ErrSkipAltProtocol` を返します。これにより、`Transport` はHTTP/1.1のフォールバック処理にシームレスに移行できます。

### その他の変更点

*   **`h2DefaultTransport`**: `http2Transport` 型のグローバル変数 `h2DefaultTransport` が導入されています。これは、HTTP/2クライアントのデフォルトの `Transport` インスタンスとして機能する予定です。
*   **`init` 関数での初期設定**: `net/http/transport.go` の `init` 関数内で、`GODEBUG` 環境変数に `"h2client=1"` が含まれている場合に、`DefaultTransport` に対してHTTP/2関連の設定が行われます。
    *   `DefaultTransport.RegisterProtocol("https", noDialH2Transport{h2DefaultTransport})`：`https` スキームに対して、`noDialH2Transport` というラッパーを介して `h2DefaultTransport` を登録しています。`noDialH2Transport` は、キャッシュされた接続がない場合に `ErrSkipAltProtocol` を返すことで、HTTP/1.1へのフォールバックを可能にします。
    *   `DefaultTransport.TLSClientConfig.NextProtos = []string{"h2"}`：TLSハンドシェイク時にクライアントがHTTP/2 (`h2`) をサポートすることをサーバーに通知します。
    *   `DefaultTransport.TLSNextProto = map[string]func(...)`：`h2` プロトコルがネゴシエートされた場合に `http2TransportForConn` 関数を呼び出すように設定しています。
*   **`persistConn` 構造体への `alt` フィールド追加**: `persistConn` は、確立された永続的な接続を表す内部構造体です。この構造体に `alt RoundTripper` フィールドが追加されました。これは、TLSハンドシェイク後にネゴシエートされた代替プロトコル（例: HTTP/2）を処理する `RoundTripper` を保持するために使用されます。`alt` が `nil` でない場合、その接続は代替プロトコルで処理されることを意味します。
*   **`Transport.RoundTrip` メソッドの変更**: `RoundTrip` メソッドの冒頭で、`RegisterProtocol` で登録された代替 `RoundTripper` が存在し、それが `ErrSkipAltProtocol` を返さなかった場合に、その `RoundTripper` がリクエストを処理するように変更されています。また、`dialConn` で `alt` フィールドが設定された `persistConn` が返された場合、その `alt` `RoundTripper` を使用してリクエストを処理するロジックが追加されています。

## コアとなるコードの解説

### `Transport.TLSNextProto` の機能

`Transport` 構造体に追加された `TLSNextProto` マップは、クライアント側でのALPN/NPNプロトコルネゴシエーションの結果を処理するための主要な拡張ポイントです。

1.  **TLSハンドシェイク**: クライアントがHTTPS接続を確立する際、TLSハンドシェイクが行われます。このハンドシェイク中に、クライアントは `tls.Config.NextProtos` で指定されたサポートプロトコルリスト（このコミットでは `"h2"` が追加されている）をサーバーに提示します。サーバーは、そのリストの中からサポートするプロトコルを選択し、クライアントに通知します。
2.  **プロトコル決定**: `Transport.dialConn` メソッド内で、TLS接続が確立された後、`tls.ConnectionState` からネゴシエートされたプロトコル (`s.NegotiatedProtocol`) が取得されます。
3.  **`TLSNextProto` の参照**: 取得されたプロトコル名（例: `"h2"`）が `Transport.TLSNextProto` マップのキーとして存在するかどうかを確認します。
4.  **`RoundTripper` の取得**: もし対応するエントリが見つかれば、そのマップ値である関数が呼び出されます。この関数は、接続先のホスト情報と確立されたTLS接続を受け取り、そのプロトコル（例: HTTP/2）を処理するための `RoundTripper` インスタンスを返します。
5.  **`persistConn.alt` への設定**: 返された `RoundTripper` は、新しく導入された `persistConn` 構造体の `alt` フィールドに格納されます。これにより、この接続が特定の代替プロトコル（例: HTTP/2）によって処理されるべきであることがマークされます。
6.  **`Transport.RoundTrip` での利用**: 最終的に、`Transport.RoundTrip` メソッドは、`persistConn` の `alt` フィールドが `nil` でない場合、その `alt` `RoundTripper` を使用して実際のリクエスト処理を行います。これにより、HTTP/1.1の処理ロジックを迂回して、HTTP/2などの代替プロトコルハンドラに処理を委譲できます。

このメカニズムにより、`net/http` クライアントは、接続が確立されるまでどのプロトコルを使用するかを知らなくても、動的に適切なプロトコルハンドラを選択できるようになります。

### `ErrSkipAltProtocol` の機能と `RegisterProtocol` の変更

`ErrSkipAltProtocol` は、`Transport.RegisterProtocol` と連携して、代替プロトコルハンドラの柔軟なフォールバックメカニズムを提供します。

1.  **`RegisterProtocol` の拡張**: このコミットにより、`Transport.RegisterProtocol` は "http" や "https" といった標準スキームに対しても `RoundTripper` を登録できるようになりました。これにより、例えば `https` スキームに対してHTTP/2を試行するカスタム `RoundTripper` を登録することが可能になります。
2.  **代替 `RoundTripper` の試行**: `Transport.RoundTrip` メソッドの冒頭で、まず `req.URL.Scheme` に対応する代替 `RoundTripper` が `RegisterProtocol` によって登録されているかを確認します。
3.  **`ErrSkipAltProtocol` の役割**: 登録された代替 `RoundTripper` が `RoundTrip` メソッドを実行し、その結果として `ErrSkipAltProtocol` を返した場合、`Transport` はその代替 `RoundTripper` が存在しなかったかのように振る舞います。つまり、代替プロトコルでの処理をスキップし、自身のデフォルトの `RoundTrip` ロジック（通常はHTTP/1.1）を続行します。
4.  **フォールバックの実現**: この機能は、HTTP/2の統合において非常に重要です。例えば、`https` 用に登録されたHTTP/2 `RoundTripper` が、まだHTTP/2接続が確立されていない、またはキャッシュされていないといった理由でHTTP/2での処理ができない場合に `ErrSkipAltProtocol` を返すことで、`Transport` は自動的にHTTP/1.1での接続確立とリクエスト処理にフォールバックできます。これにより、HTTP/2が利用できない場合でも、クライアントは引き続きHTTP/1.1で通信を試みることができ、堅牢性が向上します。

### `init` 関数での初期配線

`init` 関数内の設定は、このコミットがHTTP/2の「配線」の初期段階であることを明確に示しています。

*   `GODEBUG="h2client=1"` という環境変数チェックは、開発中にHTTP/2クライアントを一時的に有効にするためのメカニズムです。これはGo 1.6リリース前には削除される予定の一時的な措置であることがコメントで明記されています。
*   `DefaultTransport.RegisterProtocol("https", noDialH2Transport{h2DefaultTransport})` は、`https` リクエストが来た場合に、まず `noDialH2Transport` を介して `h2DefaultTransport` (HTTP/2ハンドラ) を試行するように設定しています。`noDialH2Transport` は、まだHTTP/2の本格的な実装がないため、常に `ErrSkipAltProtocol` を返します。これにより、現時点ではHTTP/2の試行はスキップされ、HTTP/1.1にフォールバックする動作が実現されています。
*   `DefaultTransport.TLSClientConfig.NextProtos = []string{"h2"}` は、クライアントがTLSハンドシェイク時にHTTP/2をサポートすることをサーバーに通知するための設定です。
*   `DefaultTransport.TLSNextProto = map[string]func(...)` は、ALPNで `h2` がネゴシエートされた場合に `http2TransportForConn` を呼び出すように設定しています。`http2TransportForConn` も現時点では `h2DefaultTransport` を返すだけで、本格的なHTTP/2接続の管理はまだ実装されていません。

これらの `init` 関数内の設定は、HTTP/2クライアントの本格的な実装が完了した際に、`DefaultTransport` が自動的にHTTP/2をサポートするための準備段階として機能します。

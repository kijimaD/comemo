# [インデックス 25109] ファイルの概要

このコミットは、Go言語の標準ライブラリ `bufio` パッケージにおける `Scanner` の挙動を改善するものです。具体的には、入力の最後に空のトークンが存在する場合の処理をよりクリーンかつ効率的に行うための変更が導入されました。これにより、`SplitFunc` が状態を持つことなく、終端の空トークンを適切に処理できるようになります。

## 変更の背景

`bufio.Scanner` は、入力ストリームをトークンに分割するための強力なユーティリティです。その核となるのは `SplitFunc` という関数で、これは入力データを受け取り、次のトークンをどのように切り出すかを決定します。しかし、これまでの `SplitFunc` のインターフェースには、特定のシナリオで課題がありました。

具体的には、入力の最後に区切り文字があり、それが空のトークンを生成する場合（例: `"1,2,3,"` を `,` で分割すると `["1", "2", "3", ""]` となるべき場合）、`SplitFunc` が純粋な関数（状態を持たない関数）としてこれを適切に処理することが困難でした。

従来の `SplitFunc` は、次のトークンを返すか、エラーを返すか、あるいは入力が足りないことを示す `(0, nil, nil)` を返すかのいずれかでした。入力の終端で空のトークンを生成し、かつそれ以上スキャンを続行しないというシグナルを送るための明確なメカニズムがありませんでした。このため、開発者は `SplitFunc` 内で状態を管理したり、`Scanner.Scan()` のループが終了した後に別途エラーチェックを行ったりする必要があり、コードが複雑になる傾向がありました。コミットメッセージでは、この状況を「醜い (ugly)」と表現しています。

このコミットは、この問題を解決し、`SplitFunc` がよりシンプルかつ宣言的に終端の空トークンを扱えるようにすることを目的としています。

## 前提知識の解説

### `bufio.Scanner` と `SplitFunc`

Go言語の `bufio` パッケージは、バッファリングされたI/O操作を提供します。`bufio.Scanner` は、`io.Reader` から読み取ったデータを、指定されたルール（`SplitFunc`）に基づいてトークン（行、単語、カスタム区切り文字など）に分割するための構造体です。

-   **`bufio.NewScanner(r io.Reader)`**: 新しい `Scanner` を作成します。
-   **`scanner.Split(splitFunc SplitFunc)`**: トークン分割ロジックを定義する `SplitFunc` を設定します。
-   **`scanner.Scan() bool`**: 次のトークンに進みます。トークンが見つかった場合や、入力の終わりに達した場合、またはエラーが発生した場合に `false` を返します。
-   **`scanner.Text() string` / `scanner.Bytes() []byte`**: 現在のトークンを文字列またはバイトスライスとして返します。
-   **`scanner.Err() error`**: スキャン中に発生したエラーを返します。

### `SplitFunc` のシグネチャ

`SplitFunc` は以下のシグネチャを持ちます。

```go
type SplitFunc func(data []byte, atEOF bool) (advance int, token []byte, err error)
```

-   **`data []byte`**: 現在処理可能な入力データの一部。
-   **`atEOF bool`**: 入力の終端に達しているかどうかを示すフラグ。
-   **`advance int`**: `data` スライスから消費したバイト数。
-   **`token []byte`**: 抽出されたトークン。
-   **`err error`**: エラーが発生した場合に返されるエラー。

`SplitFunc` の一般的な挙動は以下の通りです。
1.  `data` 内で区切り文字を探す。
2.  区切り文字が見つかった場合、その区切り文字までのデータをトークンとして返し、区切り文字を含めて消費したバイト数を `advance` として返す。
3.  区切り文字が見つからないが、`atEOF` が `false` の場合、入力が足りない可能性があるため `(0, nil, nil)` を返し、`Scanner` にさらにデータを読み込むように指示する。
4.  区切り文字が見つからず、`atEOF` が `true` の場合、残りの `data` を最後のトークンとして返す。

### 終端の空トークンの問題

例えば、`"a,b,c,"` という文字列をカンマで分割する場合を考えます。期待されるトークンは `["a", "b", "c", ""]` です。
従来の `SplitFunc` では、最後のカンマを処理した後、`data` が空になり `atEOF` が `true` になったときに、空のトークン `""` を返す必要がありました。しかし、その後に `Scanner` がスキャンを停止すべきであることを `SplitFunc` から直接伝える明確な方法がありませんでした。`SplitFunc` が `(0, nil, nil)` を返すと、`Scanner` はさらにデータを待つと解釈してしまう可能性があります。また、カスタムエラーを返すと、それはスキャンエラーとして `Scanner.Err()` に伝播してしまい、期待する「エラーではないがスキャン終了」という状態を表現できませんでした。

## 技術的詳細

このコミットは、上記の「終端の空トークン」の問題を解決するために、`bufio` パッケージに新しいセマンティクスと特別なエラー値 `bufio.ErrFinalToken` を導入します。

1.  **`bufio.ErrFinalToken` の導入**:
    `bufio.ErrFinalToken` は、`errors.New("final token")` で定義される特別なセンチネルエラー値です。このエラーは、`SplitFunc` がトークンを返すと同時に、それが最後のトークンであり、これ以上スキャンを続けるべきではないことを `Scanner` に通知するために使用されます。

2.  **`Scanner` 構造体への `done` フィールドの追加**:
    `Scanner` 構造体に `done bool` フィールドが追加されました。これは、スキャンが完了したかどうかを示す内部状態フラグです。`ErrFinalToken` が検出された際に `true` に設定され、以降の `Scan()` 呼び出しで `false` を返すようにします。

3.  **`Scanner.Scan()` メソッドの変更**:
    `Scanner.Scan()` メソッドは、`SplitFunc` から返されたエラーをチェックするロジックが変更されました。
    -   `SplitFunc` が `bufio.ErrFinalToken` を返した場合、`Scanner` はそのトークンを有効なものとして受け入れ、内部の `s.done` フラグを `true` に設定します。
    -   この `ErrFinalToken` は `Scanner.Err()` には伝播されず、`Scan()` メソッドは `true` を返して現在のトークンが利用可能であることを示します。
    -   `s.done` が `true` に設定された後、次回の `Scan()` 呼び出しでは、入力の終端に達したかのように直ちに `false` を返します。これにより、スキャンが正常に終了したことを示しつつ、最後の空トークンも取得できるようになります。

このメカニズムにより、`SplitFunc` は状態を持つことなく、最後の空トークンを生成し、かつスキャンを正常に終了させることが可能になります。開発者は `SplitFunc` 内で `return advance, token, bufio.ErrFinalToken` のように記述するだけで、この挙動を実現できます。

## コアとなるコードの変更箇所

このコミットでは、主に以下の3つのファイルが変更されています。

1.  **`src/bufio/scan.go`**: `bufio.Scanner` の主要なロジックが含まれるファイル。
    -   `Scanner` 構造体に `done bool` フィールドが追加されました。
    -   `var ErrFinalToken = errors.New("final token")` として `ErrFinalToken` が定義されました。
    -   `Scanner.Scan()` メソッドの冒頭に `if s.done { return false }` が追加され、スキャンが完了している場合はすぐに終了するように変更されました。

3.  **`src/bufio/scan_test.go`**: `bufio.Scanner` のテストファイル。
    -   `commaSplit` 関数が変更され、入力の終端 (`atEOF` が `true`) で残りのデータをトークンとして返し、同時に `ErrFinalToken` を返すように修正されました。

        // 変更前:

    -   `TestEmptyTokens` 関数が `testEmptyTokens` というヘルパー関数にリファクタリングされ、より汎用的にテストケースを記述できるようになりました。

## コアとなるコードの解説

このコミットの核心は、`bufio.ErrFinalToken` という新しいエラーセマンティクスを導入し、`Scanner` がこれを特別に扱うようにした点にあります。

-   **`ErrFinalToken` の役割**: `SplitFunc` が `ErrFinalToken` を返すことで、「このトークンは有効であり、これ以上入力はないのでスキャンを終了してほしい」という意図を `Scanner` に明確に伝えることができます。これにより、`SplitFunc` は状態を持つ必要がなくなり、純粋な関数として設計しやすくなります。例えば、`"1,2,3,"` のような入力で、最後のカンマの後に空のトークンを生成し、その後スキャンを停止する、というロジックを簡潔に記述できるようになります。

-   **`Scanner.Scan()` の変更**: `Scanner.Scan()` は、`SplitFunc` から返されたエラーが `ErrFinalToken` であるかをチェックします。もしそうであれば、そのトークンを有効なものとして受け入れ (`s.token = token`)、スキャンが完了したことを示す `s.done = true` を設定します。そして、現在の `Scan()` 呼び出しは `true` を返して、最後のトークンが利用可能であることを示します。次回の `Scan()` 呼び出しでは、`s.done` が `true` であるため、すぐに `false` を返し、スキャンが正常に終了したことを示します。この挙動により、`Scanner.Err()` は `nil` のままであり、スキャンがエラーで中断されたわけではないことが保証されます。

-   **テストと例の改善**: `commaSplit` 関数の変更と新しいテストケース、そして `ExampleScanner_emptyFinalToken` の追加は、この新しい機能の正しい使い方と、それが解決する問題を明確に示しています。特に `commaSplit` が `ErrFinalToken` を返すように変更されたことで、終端の空トークンを扱うロジックが `SplitFunc` 内部で完結し、外部の状態管理が不要になったことがわかります。

この変更により、`bufio.Scanner` を利用する開発者は、入力の終端処理、特に空トークンの扱いでより柔軟かつ簡潔なコードを書けるようになりました。

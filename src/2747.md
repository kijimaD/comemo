# [インデックス 2747] ファイルの概要

このコミットは、Go言語のリンカにおけるELF64 (Executable and Linkable Format 64-bit) のサポートを強化するものです。具体的には、プログラムヘッダ (Program Headers, phdrs) の扱いを改善し、ELF関連の定数を導入することで、コードの可読性と保守性を向上させています。これにより、ELF64形式の実行ファイルの生成がより堅牢になります。

## 変更の背景

このコミットが行われた背景には、Go言語の初期開発段階において、ELF64形式の実行ファイル生成におけるリンカの機能強化が必要とされたことがあります。以前の実装では、ELF64のプログラムヘッダを生成する際に、各フィールドの値を直接関数に渡していました。これは、引数の意味が分かりにくく、エラーが発生しやすいという問題がありました。また、ELFの様々なタイプやフラグがマジックナンバー（数値リテラル）としてコード中に散在しており、可読性や保守性を損ねていました。

この変更は、これらの問題を解決し、ELF64の構造をより明確に、かつ安全に扱うためのものです。具体的には、プログラムヘッダを構造体として抽象化し、関連する定数を名前付きで定義することで、コードの理解を容易にし、将来的な拡張やデバッグを効率化することを目的としています。

## 前提知識の解説

### ELF (Executable and Linkable Format)

ELFは、Unix系システム（Linuxなど）で広く使用されている実行ファイル、オブジェクトファイル、共有ライブラリの標準ファイルフォーマットです。プログラムの実行に必要な情報（コード、データ、シンボルテーブルなど）を構造化して格納します。

ELFファイルは主に以下の要素で構成されます。

*   **ELFヘッダ (ELF Header)**: ファイルの先頭に位置し、ファイルのタイプ（実行ファイル、共有ライブラリなど）、ターゲットアーキテクチャ、エントリポイントアドレスなどの基本的な情報を含みます。
*   **プログラムヘッダテーブル (Program Header Table)**: 実行時にメモリにロードされるセグメント（コード、データなど）の情報を記述します。各エントリは「プログラムヘッダ (Program Header, Phdr)」と呼ばれ、セグメントのタイプ、ファイルオフセット、仮想アドレス、サイズ、メモリ保護フラグなどを指定します。リンカは、このテーブルを生成して実行ファイルに埋め込みます。
*   **セクションヘッダテーブル (Section Header Table)**: リンク時に使用されるセクション（`.text`、`.data`、`.bss`など）の情報を記述します。各エントリは「セクションヘッダ (Section Header, Shdr)」と呼ばれ、セクション名、タイプ、アドレス、サイズ、フラグなどを指定します。

### プログラムヘッダ (Program Headers, phdrs)

プログラムヘッダは、実行ファイルがメモリにどのようにロードされるかを記述する重要な構造体です。各プログラムヘッダは、実行ファイル内の特定の領域（セグメント）が、実行時の仮想メモリ空間のどこに配置され、どのような属性（読み取り、書き込み、実行可能）を持つべきかを定義します。

主要なフィールドには以下のようなものがあります。

*   `p_type`: セグメントのタイプ（例: `PT_LOAD` はロード可能なセグメントを示す）。
*   `p_flags`: セグメントの属性（例: `PF_X` は実行可能、`PF_W` は書き込み可能、`PF_R` は読み取り可能）。
*   `p_offset`: ファイル内でのセグメントのオフセット。
*   `p_vaddr`: 仮想メモリ空間でのセグメントの開始アドレス。
*   `p_paddr`: 物理メモリ空間でのセグメントの開始アドレス（通常は `p_vaddr` と同じか、無視される）。
*   `p_filesz`: ファイル内でのセグメントのサイズ。
*   `p_memsz`: メモリ内でのセグメントのサイズ（`p_filesz` より大きい場合、差分はゼロ初期化される）。
*   `p_align`: メモリとファイル内でのセグメントのアライメント要件。

### セクションヘッダ (Section Headers, shdrs)

セクションヘッダは、オブジェクトファイルや共有ライブラリのリンク時に使用される、より詳細な構造情報を提供します。各セクションヘッダは、コード、初期化済みデータ、未初期化データ、シンボルテーブル、文字列テーブルなど、ファイル内の特定の論理的な塊（セクション）を記述します。

主要なフィールドには以下のようなものがあります。

*   `sh_name`: セクション名の文字列テーブルへのインデックス。
*   `sh_type`: セクションのタイプ（例: `SHT_PROGBITS` はプログラムデータ、`SHT_SYMTAB` はシンボルテーブル、`SHT_STRTAB` は文字列テーブル、`SHT_NOBITS` はファイルには存在しないがメモリに割り当てられるセクション、例えば`.bss`）。
*   `sh_flags`: セクションの属性（例: `SHF_WRITE` は書き込み可能、`SHF_ALLOC` はメモリに割り当てられる、`SHF_EXECINSTR` は実行可能コードを含む）。
*   `sh_addr`: メモリ内でのセクションの仮想アドレス。
*   `sh_offset`: ファイル内でのセクションのオフセット。
*   `sh_size`: セクションのサイズ。

### Goリンカ (`6l`, `ld`)

Go言語のツールチェーンにおいて、`6l` はAMD64アーキテクチャ向けのリンカです。`ld` はリンカの共通部分を扱うディレクトリであり、`elf64.c` や `elf64.h` のようなファイルは、ELF64形式のファイル生成に関する共通ロジックをカプセル化しています。リンカの主な役割は、コンパイルされたオブジェクトファイル群を結合し、実行可能なバイナリやライブラリを生成することです。この過程で、ELFヘッダ、プログラムヘッダテーブル、セクションヘッダテーブルなどが構築されます。

## 技術的詳細

このコミットの主要な技術的変更点は、ELF64のプログラムヘッダの生成方法と、ELF関連の定数の扱いに関するものです。

1.  **プログラムヘッダの抽象化**:
    *   以前は、`elf64phdr` 関数が `type`, `flags`, `foff`, `vaddr`, `paddr`, `filesize`, `memsize`, `align` といった多数の引数を直接受け取っていました。これは、引数の順序間違いや意味の誤解を招きやすい設計でした。
    *   このコミットでは、`src/cmd/ld/elf64.h` に `Elf64PHdr` という構造体が新しく定義されました。この構造体は、プログラムヘッダの各フィールド（`type`, `flags`, `off`, `vaddr`, `paddr`, `filesz`, `memsz`, `align`）をメンバとして持ちます。
    *   `src/cmd/ld/elf64.c` に `newElf64PHdr()` 関数が追加され、`Elf64PHdr` 構造体のインスタンスを動的に割り当て、ゼロ初期化するようになりました。
    *   `elf64phdr` 関数のシグネチャが変更され、`Elf64PHdr*` 型のポインタを引数として受け取るようになりました。これにより、呼び出し側は構造体のフィールドを設定してから、そのポインタを関数に渡す形になります。
    *   `src/cmd/6l/asm.c` では、プログラムヘッダを生成する箇所で、`newElf64PHdr()` で構造体を作成し、各フィールドに値を代入してから `elf64phdr` を呼び出すように変更されました。これにより、コードの可読性が大幅に向上し、各フィールドの意味が明確になりました。

2.  **ELF定数の導入**:
    *   以前のコードでは、プログラムヘッダやセクションヘッダのタイプやフラグに、`1L+4L` や `2L+4L`、`1`, `3`, `8` といったマジックナンバーが直接使用されていました。これらの数値が何を意味するのかは、ELFの仕様書を参照しないと理解できませんでした。
    *   このコミットでは、`src/cmd/ld/elf64.h` に、ELFの標準で定義されているプログラムヘッダのタイプ (`PT_NULL`, `PT_LOAD`, `PT_DYNAMIC` など) とフラグ (`PF_X`, `PF_W`, `PF_R` など)、およびセクションヘッダのタイプ (`SHT_NULL`, `SHT_PROGBITS`, `SHT_SYMTAB` など) とフラグ (`SHF_WRITE`, `SHF_ALLOC`, `SHF_EXECINSTR` など) が `#define` マクロとして導入されました。
    *   `src/cmd/6l/asm.c` では、これらのマジックナンバーが対応する名前付き定数に置き換えられました。例えば、`sh->type = 1;` は `sh->type = SHT_PROGBITS;` に、`sh->flags = 6;` は `sh->flags = SHF_ALLOC+SHF_EXECINSTR;` に変更されています。
    *   これにより、コードの意図が明確になり、ELFの仕様を直接参照しなくても、コードを読むだけでその意味を理解できるようになりました。また、将来的にELFの仕様が変更された場合でも、定数の定義箇所を修正するだけで済むため、保守性が向上します。

これらの変更は、Goリンカが生成するELF64バイナリの正確性と、リンカ自体のコード品質を高める上で重要なステップです。

## コアとなるコードの変更箇所

### `src/cmd/6l/asm.c`

*   `asmb` 関数内で、`elf64phdr` の呼び出し方が変更されました。以前は直接引数を渡していましたが、`Elf64PHdr *ph;` を宣言し、`newElf64PHdr()` でインスタンスを生成し、各フィールドに値を設定してから `elf64phdr(ph);` を呼び出す形式になりました。
*   セクションヘッダ (`Elf64SHdr`) のタイプとフラグの設定において、数値リテラルが `SHT_PROGBITS`, `SHF_ALLOC`, `SHF_EXECINSTR`, `SHT_STRTAB`, `SHT_NOBITS`, `SHF_WRITE` といった名前付き定数に置き換えられました。

### `src/cmd/ld/elf64.c`

*   `elf64phdr` 関数のシグネチャが `void elf64phdr(int type, int flags, vlong foff, ...)` から `void elf64phdr(Elf64PHdr *e)` に変更されました。関数内部では、引数 `e` のメンバ (`e->type`, `e->flags`, `e->off` など) を使用して値を書き込むようになりました。
*   `newElf64PHdr()` 関数が追加されました。この関数は `Elf64PHdr` 構造体をヒープに割り当て、ゼロ初期化してポインタを返します。

### `src/cmd/ld/elf64.h`

*   `Elf64PHdr` 構造体が新しく定義されました。この構造体は、ELF64プログラムヘッダの各フィールドを表現します。
*   プログラムヘッダのタイプ (`PT_NULL`, `PT_LOAD` など) とフラグ (`PF_X`, `PF_W`, `PF_R` など) の定数が `#define` マクロとして追加されました。
*   セクションヘッダのタイプ (`SHT_NULL`, `SHT_PROGBITS` など) とフラグ (`SHF_WRITE`, `SHF_ALLOC` など) の定数が `#define` マクロとして追加されました。
*   `newElf64PHdr()` 関数のプロトタイプ宣言が追加されました。
*   `elf64phdr` 関数のプロトタイプ宣言が、新しいシグネチャに合わせて変更されました。

## コアとなるコードの解説

このコミットの核心は、ELF64バイナリの構造をよりC言語の構造体と定数で表現することで、リンカコードの抽象度を高め、堅牢性を向上させた点にあります。

`src/cmd/ld/elf64.h` で `Elf64PHdr` 構造体を定義し、`PT_LOAD`, `PF_X`, `SHT_PROGBITS` といったELF標準の定数を導入したことで、リンカ開発者はELFの仕様を直接数値で扱うのではなく、意味のある名前で操作できるようになりました。これは、コードの意図を明確にし、バグの混入を防ぐ上で非常に効果的です。

`src/cmd/ld/elf64.c` で `newElf64PHdr()` を導入し、`elf64phdr` 関数が `Elf64PHdr*` を受け取るように変更したことは、プログラムヘッダの生成ロジックをカプセル化し、`src/cmd/6l/asm.c` のような呼び出し側コードを簡素化しました。これにより、`asm.c` はプログラムヘッダの具体的なフィールドの並びやサイズを意識することなく、抽象化された構造体として情報を設定できるようになります。

例えば、以前の `asm.c` では以下のように直接引数を渡していました。

```c
elf64phdr(1,             /* text - type = PT_LOAD */
          1L+4L,         /* text - flags = PF_X+PF_R */
          0,             /* file offset */
          va,            /* vaddr */
          va,            /* paddr */
          w,             /* file size */
          w,             /* memory size */
          INITRND);      /* alignment */
```

これが、コミット後には以下のように変更されました。

```c
ph = newElf64PHdr();
ph->type = PT_LOAD;
ph->flags = PF_X+PF_R;
ph->vaddr = va;
ph->paddr = va;
ph->filesz = w;
ph->memsz = w;
ph->align = INITRND;
elf64phdr(ph);
```

この変更により、各フィールドがどの属性に対応するのかが一目瞭然となり、コードの可読性と保守性が飛躍的に向上しています。また、セクションヘッダのタイプやフラグも同様に、マジックナンバーから名前付き定数に置き換えられ、コードの理解を深めています。

これらの改善は、Go言語のリンカがより複雑なELF64の要件に対応し、将来的な機能拡張や異なるプラットフォームへの対応を容易にするための基盤を築くものです。

## 変更の背景

Go言語の初期のバージョンでは、コンパイラとリンカはターゲットアーキテクチャに基づいて命名されていました。例えば、`amd64` アーキテクチャ向けのコンパイラは `6g`、リンカは `6l` と呼ばれていました。同様に、`386` 向けには `8g` と `8l`、`ARM` 向けには `5g` と `5l` が存在しました。この命名規則は、初期のGo開発において特定のアーキテクチャに特化したツールを指すために用いられていました。

しかし、Go言語が進化し、より多様なアーキテクチャをサポートするようになるにつれて、このアーキテクチャ固有の命名は不便で混乱を招くものとなりました。特に、Go 1.0（2012年3月リリース）で `go` コマンドが導入されてからは、ユーザーが直接 `6g` や `6l` を呼び出す機会は減り、`go build` や `go run` といった統一されたコマンドを通じてコンパイルとリンクが行われるようになりました。

そして、**Go 1.5** のリリースにおいて、Goツールチェインの内部的なコンパイラとリンカのバイナリが、より汎用的な `compile` および `link`（`go tool compile` および `go tool link` を通じてアクセス）へと正式に改名されました。この変更は、単一のアーキテクチャ非依存なコンパイラがGoによってサポートされる任意のCPUアーキテクチャをターゲットにできるというGoの設計思想を反映したものです。

このコミットは、このGoツールチェインの進化、特にGo 1.5での名称変更を `cgo` のドキュメントに反映させるために行われました。これにより、ドキュメントが最新のツールチェインの命名規則と一致し、読者が混乱することなく `cgo` の動作を理解できるようになります。

## 前提知識の解説

### cgo

`cgo` は、GoプログラムからC言語のコードを呼び出したり、C言語のプログラムからGoの関数を呼び出したりするためのGoツールです。GoとC言語の間のインターフェースを提供し、既存のCライブラリをGoプロジェクトで利用することを可能にします。`cgo` は、Goのソースコード内の特別なコメント（`import "C"` ブロック）を解析し、GoとCの間の呼び出しを仲介するためのGoおよびCのソースファイルを生成します。

### Go Toolchain (Goツールチェイン)

Goツールチェインは、Goプログラムの開発に必要な一連のツール群を指します。主要なコンポーネントは以下の通りです。
*   **`go` コマンド**: ビルド、テスト、実行、フォーマット、依存関係管理など、Go開発のほとんどのタスクを統合的に処理するコマンドラインツールです。
*   **`cmd/compile` (旧 `6g`, `8g`, `5g` など)**: GoソースコードをオブジェクトファイルにコンパイルするGoコンパイラです。
*   **`cmd/link` (旧 `6l`, `8l`, `5l` など)**: コンパイルされたオブジェクトファイルと必要なライブラリを結合して実行可能ファイルを生成するGoリンカです。

### 旧Goコンパイラ/リンカの命名規則 (6g, 6lなど)

Go言語の初期には、コンパイラとリンカはターゲットアーキテクチャに基づいて命名されていました。
*   `6g` / `6l`: `amd64` (64-bit Intel/AMD) アーキテクチャ向け
*   `8g` / `8l`: `386` (32-bit Intel/AMD) アーキテクチャ向け
*   `5g` / `5l`: `ARM` アーキテクチャ向け

これらの名称は、Go 1.5で `cmd/compile` および `cmd/link` に統一され、より汎用的なアプローチが採用されました。

### cgoにおける内部リンキングと外部リンキング

`cgo` を使用する際に、Goのリンカ (`cmd/link`) は2つの主要なリンキングモードをサポートします。
*   **内部リンキング (Internal Linking)**: `cmd/link` 自身が、ホストのオブジェクトファイル（ELF, Mach-O, PEなど）を解析し、最終的な実行可能ファイルにリンクします。このモードでは、`cmd/link` はGoバイナリを単独で生成できますが、ホストリンカの複雑な機能をすべて実装しているわけではないため、直接リンクできるオブジェクトの種類には制限があります。
*   **外部リンキング (External Linking)**: `cmd/link` はホストのオブジェクトファイルを直接処理せず、すべてのGoコードを含む単一の `go.o` オブジェクトファイルを生成します。その後、ホストのリンカ（通常は `gcc`）を呼び出して、この `go.o` ファイルとその他の非Goコードを結合し、最終的なバイナリを生成します。このモードは、任意のオブジェクトファイルをリンクする必要がある場合や、動的ライブラリに依存しないスタンドアロンのバイナリを生成する場合に利用されます。

## 技術的詳細

このコミットは、Goツールチェインの内部的な構造と命名規則の変更が、公式ドキュメントにどのように反映されるかを示す良い例です。Go 1.5でのコンパイラとリンカの名称変更は、単なる名前の変更以上の意味を持ちます。これは、Goが特定のアーキテクチャに依存しない、より統一されたビルドシステムへと移行したことを象徴しています。

`cgo` のドキュメントは、GoとCの相互運用という複雑なトピックを扱っており、コンパイルとリンクのプロセスに関する正確な記述が不可欠です。古い `6g` や `6l` といった名称が残っていると、読者は古いバージョンのGoツールチェインを参照していると誤解したり、現在のツールチェインとの関連性を理解するのに苦労したりする可能性があります。

このコミットによるドキュメントの更新は、以下の点で重要です。
1.  **正確性の向上**: ドキュメントが現在のGoツールチェインの命名規則と一致し、情報の正確性が向上します。
2.  **一貫性の確保**: Goエコシステム全体で一貫した用語が使用されるようになり、学習曲線が緩やかになります。
3.  **混乱の回避**: 特にGoの初心者や、古いGoバージョンから移行してきた開発者にとって、古い名称と新しい名称の混在による混乱を避けることができます。
4.  **ツールチェインの進化の反映**: Goツールチェインがどのように進化し、より洗練されたビルドシステムになったかを間接的に示しています。

`cgo` のドキュメントは、生成される中間ファイル（`x.cgo1.go`, `_cgo_gotypes.go`, `_cgo_import.go`, `x.cgo2.c` など）や、それらが `gc` (コンパイラ) や `gcc` (Cコンパイラ) によってどのように処理され、最終的に `cmd/link` によってどのようにリンクされるかを詳細に説明しています。このプロセスにおいて、`6g` や `6l` といった古い名称が `gc` や `cmd/link` に置き換えられることで、ドキュメント全体が現代のGo開発環境に即したものとなります。

特に、`_go_.6` が `_go_.o` に変更されている箇所は、Goコンパイラが生成するオブジェクトファイルの命名規則も、アーキテクチャ固有のサフィックス（`.6` は `amd64` を意味する）から、より汎用的な `.o` に統一されたことを示唆しています。

全体として、これらの変更はドキュメントの正確性、一貫性、および最新性を確保し、Go開発者が `cgo` をより効果的に利用できるようにするための重要な更新です。

## 変更の背景

このコミットは、Go言語の標準ライブラリである`regexp`パッケージの正規表現マッチング性能を向上させることを目的としています。特に、Googleが開発した高性能正規表現エンジンであるRE2の「bitstate backtracker」アルゴリズムを`regexp`パッケージに移植することで、特定の正規表現パターンや入力サイズにおけるパフォーマンスのボトルネックを解消しようとしています。

コミットメッセージに示されているベンチマーク結果は、この変更が多くのシナリオで劇的な性能改善をもたらすことを明確に示しています。例えば、`BenchmarkNotOnePassShortB`では67.19%の高速化、`BenchmarkLiteral`では39.42%の高速化が達成されています。これは、従来の正規表現エンジンが苦手とするような特定のパターン（例えば、多くの選択肢を持つ正規表現や、長い文字列に対するマッチング）において、bitstate backtrackerが非常に効果的であることを示唆しています。

一方で、コミットメッセージには「backtrackerがトリガーされないベンチマークでは約2%のペナルティがある」という記述もあります。これは、新しいアルゴリズムを導入するためのオーバーヘッドや、既存の最適化パスとの兼ね合いによるもので、すべてのケースで無条件に高速化されるわけではないことを示しています。しかし、全体としては、このトレードオフを受け入れてでも導入する価値のある改善であると判断されたと考えられます。

この変更は、Goの`regexp`パッケージがRE2の設計思想（線形時間保証、安全なマッチング）を継承しつつ、さらに実用的なパフォーマンスを追求する一環として行われました。

## 前提知識の解説

### 正規表現エンジンとバックトラッキング

正規表現エンジンは、大きく分けて「バックトラッキング型」と「オートマトン（有限オートマトン）型」の2種類に分類されます。

*   **バックトラッキング型 (Backtracking Engine):** Perl、Pythonの`re`モジュール、Java、.NETなどで採用されていることが多い方式です。正規表現のパターンを左から右に、入力文字列を左から右に順にマッチングさせていきます。途中でマッチングに失敗した場合、以前に選択肢があった場所（例えば`|`や`*`の繰り返し）に戻り（バックトラック）、別のパスを試します。この方式は、実装が比較的容易で、後方参照（backreferences）のような強力な機能もサポートできます。しかし、最悪の場合、入力文字列の長さに対して指数関数的な時間計算量となる可能性があり、特定の悪意のある正規表現パターン（「ReDoS: Regular Expression Denial of Service」攻撃）によってサービス拒否攻撃を引き起こすリスクがあります。

*   **オートマトン型 (Automaton-based Engine):** 有限オートマトン（Finite Automaton）の理論に基づいて正規表現を処理します。主に「NFA (Nondeterministic Finite Automaton: 非決定性有限オートマトン)」と「DFA (Deterministic Finite Automaton: 決定性有限オートマトン)」の2種類があります。
    *   **NFAシミュレーション:** 複数の状態を同時に追跡することで、バックトラッキングをせずにマッチングを行います。RE2のbitstate backtrackerもこのNFAシミュレーションの一種です。
    *   **DFA:** 正規表現を直接DFAに変換し、入力文字列を1文字ずつ処理しながら状態を遷移させます。DFAは常に線形時間で動作し、非常に高速ですが、NFAよりも構築が複雑で、部分マッチングの開始・終了位置の特定や後方参照のサポートが難しいという制約があります。

Go言語の`regexp`パッケージは、RE2と同様にオートマトン型のアプローチを採用しており、線形時間でのマッチングを保証しています。これにより、ReDoS攻撃のリスクを回避し、予測可能なパフォーマンスを提供します。

### RE2

RE2は、Googleが開発した正規表現エンジンです。その最大の特徴は、常に線形時間で動作することを保証する点にあります。これは、従来のバックトラッキング型エンジンが抱える指数関数的な最悪ケースのパフォーマンス問題を解決するために設計されました。RE2は、正規表現を有限オートマトンにコンパイルし、効率的なNFAシミュレーションやDFAシミュレーションを用いてマッチングを行います。後方参照のような、線形時間保証を破る可能性のある機能は意図的にサポートしていません。Goの`regexp`パッケージは、RE2の構文と設計思想を強く継承しています。

### Bitstate Backtracker (RE2の文脈)

コミットメッセージにある「bitstate backtracker」という用語は、一見すると「バックトラッキング」という言葉から、従来の非効率なバックトラッキングを連想させるかもしれません。しかし、RE2の文脈におけるbitstate backtrackerは、従来のバックトラッキングとは根本的に異なります。

これは、NFAシミュレーションの一種であり、**ビットセット（bitset）**を使用して、正規表現のプログラムカウンタ（`pc`）と入力文字列中の現在位置（`pos`）の組み合わせ（`(pc, pos)`ペア）が既に訪問済みであるかどうかを効率的に記録・管理するメカニズムです。

この「訪問済み」の状態をビットベクトルで管理することで、同じ`(pc, pos)`ペアを二度と探索しないようにします。これにより、無限ループや指数関数的な探索パスに陥ることを防ぎ、結果としてマッチング処理が入力文字列の長さに比例する線形時間で完了することを保証します。つまり、これは「バックトラッキング」というよりは、動的計画法（Dynamic Programming）やメモ化（Memoization）に近い最適化手法であり、NFAシミュレーションの効率を向上させるためのものです。

## 技術的詳細

このコミットで導入されたbitstate backtrackerは、Goの`regexp`パッケージが特定の条件下で利用する新しい正規表現マッチングアルゴリズムです。これは、RE2のbitstate backtrackerをGoに移植したもので、特に「onepass」最適化が適用できない場合や、入力文字列が比較的小さい場合に効果を発揮するように設計されています。

### Bitstate Backtrackerの仕組み

bitstate backtrackerの核となるのは、`visited`ビットベクトルです。このビットベクトルは、正規表現のプログラム（`syntax.Prog`）内の各命令（`Inst`）と入力文字列中の各文字位置の組み合わせ（`(instruction_index, character_position)`）が、これまでに探索されたことがあるかどうかを記録します。

*   **状態の記録:** `visited`ビットベクトルは、`(pc, pos)`ペアを線形なインデックスにマッピングし、そのインデックスに対応するビットを立てることで、その状態が訪問済みであることを示します。
*   **重複探索の回避:** マッチング処理中に新しい`(pc, pos)`ペアに到達しようとした際、まず`visited`ビットベクトルをチェックします。もしそのペアが既に訪問済みであれば、そのパスは既に探索済みであるため、再度探索することなくスキップします。これにより、冗長な計算を排除し、線形時間での実行を保証します。
*   **線形時間保証:** `visited`ビットベクトルのおかげで、各`(pc, pos)`状態は最大で一度しか処理されません。状態の総数は、正規表現の命令数と入力文字列の長さの積に比例するため、全体のマッチング時間は線形時間となります。

### 適用条件

コミットメッセージやコードの変更から、bitstate backtrackerは以下の条件下で利用されることがわかります。

1.  **`onepass`最適化が適用できない場合:** Goの`regexp`パッケージには、より単純な正規表現に対して非常に高速な「onepass」最適化があります。bitstate backtrackerは、このonepassが適用できない、より複雑な正規表現に対して補完的に機能します。
2.  **入力文字列のサイズが小さい場合:** `exec.go`の変更で`maxBitStateLen`が導入されており、これはbitstate backtrackerが適用される入力文字列の最大長を制限します。これは、bitstate backtrackerが使用するビットベクトルのメモリフットプリントが、入力文字列の長さに比例するため、非常に長い文字列に対してはメモリ効率が悪くなる可能性があるためと考えられます。コミットメッセージの`maxBacktrackVector = 256 * 1024`（ビット）という定数から、ビットベクトルの最大サイズが制限されていることがわかります。

### パフォーマンスへの影響

コミットメッセージに記載されたベンチマーク結果は、bitstate backtrackerの導入が全体的なパフォーマンスに与える影響を詳細に示しています。

*   **大幅な改善:** `BenchmarkNotOnePassShortA` (-50.94%) や `BenchmarkNotOnePassShortB` (-67.19%) のように、onepassが適用されないケースで特に顕著な改善が見られます。これは、bitstate backtrackerがこれらのシナリオで従来のNFAシミュレーションよりもはるかに効率的であることを示しています。
*   **一部の回帰:** `BenchmarkAnchoredLiteralShortNonMatch` (+5.26%) や `BenchmarkMatchEasy0_1K` (+175.19%) のように、わずかながら性能が低下するケースも存在します。コミットメッセージにある「backtrackerがトリガーされないベンチマークでは約2%のペナルティがある」という記述は、このオーバーヘッドを指しています。これは、bitstate backtrackerのセットアップや、既存の最適化パスとの切り替えコストが原因である可能性があります。しかし、全体的な改善効果が大きいため、この小さなペナルティは許容範囲と判断されたのでしょう。

## コアとなるコードの解説

### `src/regexp/backtrack.go`

このファイルは、bitstate backtrackerの心臓部を構成します。

*   **`type job struct { pc uint32; arg int; pos int }`**:
    *   バックトラッカーのジョブスタックに積まれるエントリを表す構造体です。
    *   `pc`: プログラムカウンタ（正規表現の命令のインデックス）。
    *   `arg`: 命令の引数、または特定の命令の処理フローを制御するための追加情報。
    *   `pos`: 入力文字列中の現在位置。

*   **`type bitState struct { ... }`**:
    *   bitstate backtrackerの状態を保持する主要な構造体です。
    *   `prog *syntax.Prog`: 実行する正規表現のコンパイル済みプログラム。
    *   `end int`: 入力文字列の終了位置。
    *   `cap []int`: キャプチャグループのマッチ位置を記録するスライス。
    *   `reqcap bool`: キャプチャが必要かどうかを示すフラグ。
    *   `input input`: 入力文字列へのインターフェース。
    *   `jobs []job`: ジョブスタック。
    *   `visited []uint32`: **bitstate backtrackerの核となるビットベクトル**。`(pc, pos)`ペアが訪問済みかどうかを記録します。`uint32`の配列として実装され、各`uint32`が32ビットの状態を保持します。

*   **`func (b *bitState) shouldVisit(pc uint32, pos int) bool`**:
    *   指定された`(pc, pos)`ペアがまだ訪問されていないかをチェックし、訪問されていない場合はその状態を「訪問済み」としてマークします。
    *   `n := uint(int(pc)*(b.end+1) + pos)`: `pc`と`pos`からビットベクトルの線形インデックスを計算します。
    *   `b.visited[n/visitedBits]&(1<<(n&(visitedBits-1))) != 0`: 該当するビットが既に立っているか（訪問済みか）をチェックします。
    *   `b.visited[n/visitedBits] |= 1 << (n & (visitedBits - 1))`: 該当するビットを立てて、訪問済みとしてマークします。
    *   この関数が、重複する状態の探索を防ぎ、線形時間保証を実現する鍵となります。

*   **`func (b *bitState) push(pc uint32, pos int, arg int)`**:
    *   新しいジョブをジョブスタックに追加します。
    *   `shouldVisit`を呼び出して、重複するジョブを追加しないようにします。

*   **`func (m *machine) tryBacktrack(b *bitState, i input, pc uint32, pos int) bool`**:
    *   bitstate backtrackerのメインループです。
    *   ジョブスタックからジョブをポップし、対応する正規表現の命令（`inst.Op`）を処理します。
    *   `switch inst.Op`文で、`InstAlt`（選択肢）、`InstRune`（文字マッチ）、`InstCapture`（キャプチャ）などの様々な命令タイプを処理します。
    *   `goto CheckAndLoop`という最適化が使われており、これはスタックへの`push`/`pop`を避け、直接`pc`と`pos`を更新してループを継続することで、オーバーヘッドを削減しています。
    *   `InstMatch`に到達した場合、マッチが成功したことを意味します。キャプチャ情報が要求されている場合は、`matchcap`に結果を記録し、最長マッチ（`longest`）が要求されている場合は、さらに長いマッチを探し続けます。

### `src/regexp/exec.go`

このファイルは、既存の正規表現実行フローにbitstate backtrackerを組み込む役割を担います。

*   **`type machine struct { ... maxBitStateLen int; b *bitState ... }`**:
    *   `machine`構造体に新しいフィールドが追加されました。
    *   `maxBitStateLen int`: bitstate backtrackerを使用する入力文字列の最大長を定義します。この値を超えると、bitstate backtrackerは使用されません。
    *   `b *bitState`: `backtrack.go`で定義された`bitState`構造体のインスタンスへのポインタ。必要に応じて遅延割り当てされます。

*   **`func progMachine(p *syntax.Prog, op *onePassProg) *machine`**:
    *   `machine`インスタンスを初期化する際に、`onepass`最適化が利用できない場合（`op == notOnePass`）に`m.maxBitStateLen`が設定されるようになりました。これにより、bitstate backtrackerが適用される条件が決定されます。

*   **`func (re *Regexp) doExecute(r io.RuneReader, b []byte, s string, pos int, ncap int) []int`**:
    *   正規表現のマッチングを実行する主要なメソッドです。
    *   このメソッド内に、bitstate backtrackerを呼び出す新しいロジックが追加されました。
    *   `else if size < m.maxBitStateLen && r == nil`: この条件が、bitstate backtrackerが使用されるトリガーです。
        *   `onepass`最適化が適用されない場合 (`m.op != notOnePass`の`else`ブロック)。
        *   入力文字列のサイズが`maxBitStateLen`未満である場合。
        *   入力が`io.RuneReader`ではなく、バイトスライスまたは文字列である場合（`r == nil`）。
    *   この条件が満たされると、`m.b = newBitState(m.p)`で`bitState`インスタンスが初期化され、`m.backtrack(i, pos, size, ncap)`が呼び出されてbitstate backtrackerによるマッチングが実行されます。
    *   それ以外の場合（`onepass`が適用されるか、入力が大きすぎるか、`RuneReader`の場合）は、従来の`m.match`メソッド（NFAシミュレーション）がフォールバックとして使用されます。

この変更により、Goの`regexp`パッケージは、正規表現の複雑さや入力の特性に応じて、最も効率的なマッチングアルゴリズムを動的に選択できるようになり、全体的なパフォーマンスと堅牢性が向上しました。

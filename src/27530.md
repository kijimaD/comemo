# [インデックス 27530] ファイルの概要

このコミットでは、GoコンパイラのSSA（Static Single Assignment）バックエンドにおける`prove`パスの機能拡張が行われました。具体的には、定数との比較をより賢く処理し、その情報を伝播させることで、不要な境界チェック（bounds checks）を削減することを目的としています。

変更されたファイルは以下の通りです。

*   `src/cmd/compile/internal/ssa/prove.go`: `prove`パスの主要ロジックが含まれるファイルで、定数比較の処理と値の範囲追跡に関する大幅な変更が加えられました。
*   `src/cmd/compile/internal/ssa/value.go`: `Value`型に定数であるかを判定するヘルパー関数`isGenericIntConst`が追加されました。
*   `src/encoding/binary/binary.go`: `encoding/binary`パッケージ内の`Uint16`, `PutUint16`などの関数で、コンパイラへの境界チェックヒントの記述方法が変更されました。
*   `test/prove.go`: `prove`パスの新しい最適化を検証するためのテストケースが追加・修正されました。

## 元コミット内容

`cmd/compile: extend prove pass to handle constant comparisons`

このコミットは、Goコンパイラの`prove`パスを拡張し、定数との比較を処理できるようにします。定数との比較を見つけ、その情報をドミネータツリーを介して伝播させます。これにより、同じ変数に対する他の定数比較を解決するためにその情報を使用します。

例えば、`x >= 7`であることが分かっている場合、`x > 4`という条件は必ず真であると判断できます。

この変更により、`_ = b[7]`のようなヒントを使用して境界チェックを排除できるようになります。

Issue #14900 を修正します。

## 変更の背景

Go言語は実行時の安全性とパフォーマンスのバランスを重視しており、その一環として配列やスライスのアクセス時には境界チェック（bounds checks）が自動的に挿入されます。これは、インデックスが有効な範囲内にあることを保証し、メモリ破壊などのセキュリティ上の問題を防止するためです。しかし、これらのチェックはオーバーヘッドとなり、パフォーマンスに影響を与える可能性があります。

コンパイラ最適化の目標の一つは、プログラムのセマンティクスを維持しつつ、このような不要なチェックを可能な限り削減することです。このコミットの背景には、コンパイラがコードの実行パスを分析し、特定の条件が常に真または偽であることを「証明」できる場合に、関連する境界チェックを削除するという課題がありました。

特に、変数と定数の比較（例: `i < 10`）はプログラム内で頻繁に現れます。もしコンパイラが、ある時点で変数`i`が特定の範囲内にあることを確実に知っていれば、その後の`i`に対するアクセスで、その範囲内であることが保証されるアクセスについては境界チェックを省略できます。

このコミットは、`prove`パスという既存の最適化フェーズを強化し、定数との比較から得られる変数の範囲情報をより正確に追跡・伝播させることで、より多くの境界チェックを削除できるようにすることを目的としています。これにより、Goプログラムの実行時パフォーマンスが向上することが期待されます。

`_ = b[7]`のような記述は、プログラマが意図的にコンパイラに「`b`の長さは少なくとも8である」というヒントを与えるためのイディオムとして使われることがありましたが、このコミットによって、コンパイラがより賢くこの種の情報を利用できるようになります。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) フォーム

Goコンパイラは、ソースコードを中間表現であるSSAフォームに変換します。SSAフォームでは、各変数が一度だけ代入されるという特性を持ちます。これにより、データフロー解析や最適化が容易になります。例えば、`x = a + b`の後に`x = c + d`がある場合、SSAフォームでは`x1 = a + b`、`x2 = c + d`のように異なる変数として扱われます。

### `prove`パス

GoコンパイラのSSAバックエンドには、`prove`という最適化パスが存在します。このパスの主な役割は、プログラムの特定のポイントで、ある条件が真であるか偽であるかを「証明」することです。例えば、`if x < y`という条件分岐があった場合、`if`ブロック内では`x < y`が真であることが保証されます。`prove`パスはこの情報を利用して、その後のコードで不要なチェック（例えば、`x < y`を再度チェックするようなコード）を削除したり、より強力な最適化を適用したりします。

### ドミネータツリー (Dominator Tree)

ドミネータツリーは、プログラムの制御フローグラフ（CFG）から構築されるツリー構造です。ノードAがノードBをドミネートするとは、CFGの開始ノードからノードBへのすべてのパスがノードAを通過する場合を指します。ドミネータツリーは、プログラムの実行パスにおける情報の伝播を理解し、最適化を適用する上で非常に重要な概念です。あるノードで証明された事実は、そのノードがドミネートするすべてのノードに伝播すると考えることができます。

### 境界チェック (Bounds Checks)

Go言語では、配列やスライスにアクセスする際に、インデックスがそのデータ構造の有効な範囲内にあるかをチェックするコードが自動的に挿入されます。例えば、`a[i]`というアクセスがあった場合、`0 <= i < len(a)`が満たされているかをチェックします。このチェックが失敗すると、パニックが発生します。境界チェックは安全性を高めますが、実行時のオーバーヘッドとなるため、コンパイラは可能な限りこれを削除しようとします。

### 定数伝播 (Constant Propagation)

定数伝播は、コンパイラ最適化の一種で、プログラム中の変数が常に定数値を保持している場合、その変数の使用箇所をその定数値で置き換えるものです。これにより、計算をコンパイル時に行ったり、条件分岐を解決したりすることができます。このコミットでは、定数伝播の概念を拡張し、変数の「範囲」に関する情報を伝播させることで、より高度な最適化を可能にしています。

## 技術的詳細

このコミットの核心は、`prove`パスが変数の値の範囲（最小値と最大値）を追跡する能力を強化した点にあります。これまでの`prove`パスは、主に2つの値間の関係（`v < w`、`v == w`など）を追跡していましたが、この変更により、特定の変数が定数と比較された際に、その変数の取りうる値の範囲をより詳細に把握できるようになりました。

### `limit`構造体と`factsTable`の拡張

`src/cmd/compile/internal/ssa/prove.go`に、変数の既知の上下限を記録するための新しい構造体`limit`が導入されました。

```go
type limit struct {
	min, max   int64  // min <= value <= max, signed
	umin, umax uint64 // umin <= value <= umax, unsigned
}
```

この`limit`構造体は、符号付き整数（`min`, `max`）と符号なし整数（`umin`, `umax`）の両方で値の範囲を保持します。`noLimit`というグローバル変数で、初期状態（制限なし）を表す`limit`が定義されています。

`factsTable`構造体も拡張され、個々の値に対する既知の上下限を保持する`limits`マップと、その変更履歴を追跡するための`limitStack`が追加されました。

```go
type factsTable struct {
	facts map[pair]relation // current known set of relation
	stack []fact            // previous sets of relations

	// known lower and upper bounds on individual values.
	limits     map[ID]limit
	limitStack []limitFact // previous entries
}
```

`limitFact`は、`limitStack`に保存される要素で、`Value`のIDと、その`Value`の以前の`limit`を記録します。

### `get`メソッドの変更

`factsTable.get(v, w *Value, d domain) relation`メソッドは、`v`と`w`の間の既知の関係を返します。このコミットでは、`v`または`w`のいずれかが定数である場合に、`limits`マップに保存されている範囲情報を使用して関係を推論するロジックが追加されました。

例えば、`v`が変数で`w`が定数`c`の場合、`ft.limits[v.ID]`から`v`の既知の範囲`lim`を取得します。そして、`c`と`lim`の`min`/`max`または`umin`/`umax`を比較することで、`v`と`c`の間の関係（`lt`, `eq`, `gt`の組み合わせ）をより正確に判断します。

### `update`メソッドの変更

`factsTable.update(v, w *Value, d domain, r relation)`メソッドは、新しい関係`r`が`v`と`w`の間に確立されたときに`factsTable`を更新します。このメソッドも拡張され、`v`が変数で`w`が定数である場合に、`v`の`limit`情報を更新するロジックが追加されました。

新しい関係`r`に基づいて、`v`の`min`, `max`, `umin`, `umax`が調整されます。例えば、`v < c`という関係が確立された場合、`v`の`max`は`c-1`に更新されます。これにより、ドミネータツリーを下降する際に、変数の取りうる値の範囲が徐々に狭められ、より正確な情報が利用可能になります。

### `checkpoint`と`restore`

`factsTable`の`checkpoint`と`restore`メソッドは、条件分岐（`if`文など）の際に、現在の`factsTable`の状態を保存・復元するために使用されます。このコミットでは、`limitStack`もこれらの操作の対象となり、`limit`情報の変更も適切にロールバックできるようになりました。これにより、異なる分岐パスで得られた範囲情報が、その分岐パスの外に漏れ出すことなく、正確に管理されます。

### `encoding/binary`の変更

`src/encoding/binary/binary.go`では、`Uint16`, `PutUint16`などの関数内で、コンパイラへの境界チェックヒントの記述方法が変更されました。

変更前: `b = b[:2:len(b)] // bounds check hint to compiler; see golang.org/issue/14808`
変更後: `_ = b[1] // bounds check hint to compiler; see golang.org/issue/14808`

これは、スライス再スライスによるヒントよりも、特定のインデックスへのダミーアクセス（`_ = b[1]`）の方が、新しい`prove`パスの定数比較最適化と連携して、より効果的に境界チェックを削除できるようになったことを示唆しています。`_ = b[1]`は、`b`の長さが少なくとも2であることをコンパイラに「証明」するのに役立ちます。

## コアとなるコードの解説

このコミットの主要な変更は、`src/cmd/compile/internal/ssa/prove.go` に集約されています。

### `limit` 構造体

`limit` 構造体は、変数の取りうる値の範囲を追跡するための中心的なデータ構造です。`min` と `max` は符号付き整数、`umin` と `umax` は符号なし整数として、それぞれ変数の下限と上限を保持します。これにより、コンパイラは変数の型に応じて適切な範囲情報を利用できます。`noLimit` は、まだ何の制約も知られていない状態を表します。

### `factsTable.get` メソッドの定数比較ロジック

`get` メソッド内の新しいロジックは、`v` または `w` のいずれかが `isGenericIntConst()` で判定される定数である場合に発動します。
例えば、`v` が変数で `w` が定数 `c` の場合、`ft.limits[v.ID]` から `v` の現在の範囲 `lim` を取得します。
そして、`c` と `lim` の `min`/`max` (符号付きの場合) または `umin`/`umax` (符号なしの場合) を比較し、`v` と `c` の間の関係を推論します。

例: `v` の範囲が `[7, 10]` で、`w` が定数 `4` の場合、`v > 4` は常に真であると判断できます。この場合、`gt` (Greater Than) の関係が返されます。
もし `v` の範囲が `[0, 5]` で、`w` が定数 `7` の場合、`v < 7` は常に真であると判断できます。この場合、`lt` (Less Than) の関係が返されます。
この推論により、`if v > 4` のような条件分岐が常に真であると証明されれば、その条件分岐自体が削除されたり、その後のコードで `v > 4` に関連する境界チェックが不要になったりします。

### `factsTable.update` メソッドの範囲更新ロジック

`update` メソッド内の新しいロジックは、`v` が変数で `w` が定数である場合に、`v` の `limit` を更新します。
例えば、`v < c` という関係が新たに確立された場合、`v` の上限 `lim.max` は `c-1` に更新されます。
`v >= c` という関係が確立された場合、`v` の下限 `lim.min` は `c` に更新されます。
これらの更新は、符号付きと符号なしの両方のケースで、`lt`, `lt|eq`, `gt|eq`, `gt`, `lt|gt` (not equal), `eq` の各関係に基づいて行われます。
`limitStack` には更新前の `limit` が保存され、`checkpoint`/`restore` メカニズムによって、条件分岐の終了時に以前の状態に正確に戻せるようになっています。これにより、コンパイラは各実行パスで独立した範囲情報を維持できます。

### `isGenericIntConst()`

このヘルパー関数は、`Value` が `OpConst64`, `OpConst32`, `OpConst16`, `OpConst8` のいずれかであるかをチェックします。これにより、コンパイラは特定の整数定数操作を効率的に識別し、`prove` パスで特別な処理を適用できます。

### `encoding/binary` の境界チェックヒントの変更

`_ = b[X-1]` という形式のヒントは、コンパイラに対して「このスライス `b` は少なくとも `X` 個の要素を持っている」という情報を与えます。例えば `_ = b[7]` は `b` が少なくとも8要素持つことを示します。このヒントは、新しい `prove` パスが定数比較から範囲情報を推論する能力と組み合わされることで、`b[0]` から `b[7]` までのアクセスに対する境界チェックを削除するのに役立ちます。以前の `b = b[:X:len(b)]` 形式よりも、この新しい形式の方が、コンパイラがより直接的に必要な範囲情報を把握しやすくなったと考えられます。

これらの変更により、Goコンパイラはプログラムの実行フローにおける変数の値の範囲をより正確に把握し、その情報に基づいて不要な境界チェックを削除することで、生成されるバイナリのパフォーマンスを向上させます。

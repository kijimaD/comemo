# [インデックス 24999] ファイルの概要

このコミットは、Goランタイムにおける`aeshash`関数が空文字列をハッシュする際の挙動を修正し、複合オブジェクトのハッシュ衝突の可能性を低減することを目的としています。具体的には、空文字列のハッシュが単にシード値を返すのではなく、スクランブルされたシード値を返すように変更することで、ハッシュの品質を向上させています。

## 変更の背景

Go言語のランタイムでは、マップ（`map`）などのデータ構造でキーのハッシュ値を計算するためにハッシュ関数が使用されます。このコミット以前の`aeshash`関数は、空文字列（`""`）のハッシュ値を計算する際に、入力されたシード値（`seed`）をそのまま返していました。

この挙動は、複合オブジェクト（例えば、文字列の配列や構造体）が空文字列を含む場合に問題を引き起こしていました。具体的には、`[2]string{"", "foo"}`と`[2]string{"foo", ""}`のように、空文字列の位置が異なるだけで内容が同じような複合オブジェクトが、同じハッシュ値を持ってしまう可能性がありました。これは、ハッシュ関数が空文字列の位置情報を適切に考慮していないためです。

ハッシュ衝突（異なる入力が同じハッシュ値を持つこと）が増加すると、マップのパフォーマンスが著しく低下します。特に、Goのマップはハッシュ衝突を解決するためにオーバーフローバケットを使用するため、衝突が多いとメモリ割り当てが増え、アクセス時間が長くなります。この問題に対処し、ハッシュの分布を改善することが、この変更の背景にあります。

## 前提知識の解説

*   **ハッシュ関数**: 任意の長さのデータを固定長のデータ（ハッシュ値）に変換する関数です。データ検索の高速化（例: マップのキー検索）やデータの同一性チェックなどに利用されます。良いハッシュ関数は、異なる入力に対して異なるハッシュ値を生成し、ハッシュ値が均等に分布する特性を持ちます。
*   **ハッシュ衝突**: 異なる入力データが同じハッシュ値を生成してしまう現象です。ハッシュ衝突が多いと、ハッシュテーブル（マップなど）の性能が低下します。
*   **シード値 (Seed)**: ハッシュ関数の初期値として与えられる乱数です。シード値を変えることで、同じ入力データでも異なるハッシュ値を生成でき、ハッシュ衝突攻撃（特定の入力で意図的にハッシュ衝突を多発させる攻撃）を防ぐのに役立ちます。Goのマップは、起動時にランダムなシード値を使用してハッシュ関数を初期化します。
*   **`aeshash`**: Goランタイムで使用されるハッシュ関数の一つで、AES命令セットを活用して高速なハッシュ計算を行います。特に文字列やバイト列のハッシュ計算に用いられます。
*   **複合オブジェクトのハッシュ**: 配列や構造体のような複数の要素を持つオブジェクトのハッシュを計算する際には、各要素のハッシュ値を組み合わせて最終的なハッシュ値を生成します。この際、各要素の位置情報もハッシュ値に反映されることが重要です。
*   **オーバーフローバケット**: Goのマップ実装において、ハッシュ衝突が発生した際に、同じハッシュ値を持つキーと値のペアを格納するために使用される追加のメモリ領域です。オーバーフローバケットが増えると、マップのメモリ使用量が増加し、キー検索の効率が低下します。

## 技術的詳細

このコミットの核心的な問題は、`aeshash`が空文字列をハッシュする際に、入力シードをそのまま出力していた点にあります。
`hash("", seed) = seed`

この単純な挙動は、以下のような問題を引き起こします。

1.  **位置情報の欠落**: 複合オブジェクト（例: `[2]string{"", "foo"}`）のハッシュを計算する際、空文字列のハッシュが常にシード値そのものであるため、その空文字列がオブジェクトのどの位置にあるかという情報がハッシュ値に反映されません。結果として、`{"", "foo"}`と`{"foo", ""}`のように、空文字列の位置が異なるだけのオブジェクトが同じハッシュ値を持つ可能性が高まります。
2.  **ハッシュ分布の偏り**: 空文字列が多く含まれるデータセットでは、ハッシュ値の分布が偏り、ハッシュ衝突が増加します。これはマップのパフォーマンス低下に直結します。

この問題を解決するため、コミットでは以下の変更が導入されました。

*   **空文字列のハッシュ値のスクランブル**: `aeshash`が空文字列をハッシュする際に、シード値をそのまま返すのではなく、AES命令（`AESENC`）を使ってシード値をスクランブル（攪拌）してから返すように変更されました。これにより、空文字列のハッシュ値がシード値に依存しつつも、よりランダムな値となり、空文字列の位置情報が間接的にハッシュ値に影響を与えるようになります。
*   **冗長なスクランブル処理の削除**: 以前は、コンパイラが生成する配列ハッシュルーチンで、ハッシュ値の品質を向上させるために追加のシフトや乗算によるスクランブル処理が行われていました。空文字列のハッシュが適切にスクランブルされるようになったため、これらの冗長な処理は不要となり、削除されました。これにより、コードの簡素化とわずかなパフォーマンス向上が期待できます。
*   **テストの強化**: 空文字列を含む配列や構造体のハッシュ分布を検証するための新しいテストが追加されました。これらのテストは、多数のキーをマップに挿入し、その際のメモリ割り当て（特にオーバーフローバケットの数）を測定することで、ハッシュ関数の品質を評価します。割り当てが一定数を超えると、ハッシュ分布が不均衡であると判断され、テストが失敗します。

この変更により、Goのマップにおけるハッシュ衝突が減少し、特に空文字列を多く含むキーを使用する場合のパフォーマンスと安定性が向上します。

## コアとなるコードの解説

### `src/runtime/asm_386.s` および `src/runtime/asm_amd64.s` の変更

`aes0`関数は、長さ0のデータ（空文字列）のハッシュを計算する際に呼び出されるアセンブリルーチンです。
変更前は、単に`h+4(FP)`（386の場合）または`h+8(FP)`（amd64の場合）からシード値`AX`レジスタにロードし、それを`DX`レジスタが指すメモリ位置にストアして返していました。これは、シード値をそのまま返すことを意味します。

変更後、以下の命令が追加されました。

```assembly
AESENC X7, X6
AESENC X7, X6
```

*   `AESENC`はAES暗号化命令セットの一部で、データを暗号化する際に使用されるラウンド関数を実行します。ここでは、暗号化そのものではなく、シード値を「スクランブル」または「攪拌」するために利用されています。
*   `X6`と`X7`は、SSE/AVXレジスタ（XMMレジスタ）を指します。具体的なレジスタの割り当てはGoのアセンブリ規約に依存しますが、ここではシード値がこれらのレジスタにロードされ、`AESENC`命令によってその値が複雑に変換されます。
*   この命令を2回適用することで、シード値は元の値とは大きく異なる、よりランダムな値に変換されます。これにより、空文字列のハッシュ値が単なるシード値ではなくなり、ハッシュ衝突の可能性が低減されます。

### `src/cmd/compile/internal/gc/subr.go` の変更

このファイルはGoコンパイラのバックエンドの一部であり、ハッシュ関数呼び出しを生成するロジックを含んでいます。以前は、生成されるハッシュコードに、ハッシュ値をさらにスクランブルするためのビットシフトと乗算の操作が含まれていました。

```go
// h = h<<3 | h>>61
n.Nbody = list(n.Nbody, Nod(OAS, nh, Nod(OOR, Nod(OLSH, nh, Nodintconst(3)), Nod(ORSH, nh, Nodintconst(int64(Widthptr)*8-3)))))

// h *= mul
// Same multipliers as in runtime.memhash.
var mul int64
if Widthptr == 4 {
    mul = 3267000013
} else {
    mul = 23344194077549503
}
n.Nbody = list(n.Nbody, Nod(OAS, nh, Nod(OMUL, nh, Nodintconst(mul))))
```

これらの行は、`aeshash`が空文字列を適切にスクランブルするようになったため、冗長と判断され削除されました。これにより、ハッシュ計算のオーバーヘッドがわずかに減少し、コードベースが簡素化されます。

### `src/runtime/hash_test.go` の追加テスト

`TestArrayHash`と`TestStructHash`は、ハッシュ関数の品質を検証するための重要なテストです。

*   **テストの目的**: 空文字列を含む複合キー（`[8]string`配列や`struct`）がマップのキーとして使用されたときに、ハッシュ衝突が過度に発生しないことを確認します。
*   **テストロジック**:
    *   `key`型として、8つの文字列フィールドを持つ配列または構造体を定義します。
    *   `make(map[key]bool, 70)`でマップを初期化します。`70`という数字は、8つの要素から4つの`"foo"`と4つの`""`を選ぶ組み合わせの数（8C4 = 70）に基づいています。
    *   256通りの組み合わせ（`i`が0から255まで）をループし、各`key`に4つの`"foo"`と4つの`""`を割り当てます。
    *   これらの70個のユニークなキーをマップに挿入します。
    *   `testing.AllocsPerRun`を使用して、マップ操作中に発生するメモリ割り当ての回数を測定します。
*   **成功条件**: `n := testing.AllocsPerRun(10, f); n > 6`という条件で、割り当て回数が6回を超えないことを検証しています。
    *   マップの内部実装では、ハッシュ衝突が多いと新しいオーバーフローバケットが割り当てられます。ハッシュ関数が不均衡だと、多くのキーが同じバケットに集中し、多数のオーバーフローバケットが必要となり、メモリ割り当てが増加します。
    *   このテストは、ハッシュ関数が十分に均等に分布している場合、オーバーフローバケットの割り当てが最小限に抑えられることを期待しています。`n > 6`という閾値は、良好なハッシュ分布であれば通常発生しない過剰な割り当てを検出するためのものです。

これらのテストは、変更がハッシュ関数の品質を実際に改善し、複合オブジェクトのハッシュ衝突を効果的に減らしたことを実証します。

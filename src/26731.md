## 変更の背景

この変更の主な背景は、Goコンパイラのコンパイル時間の最適化です。特に、SSA (Static Single Assignment) 形式の中間表現に対する共通部分式除去 (CSE) パスにおいて、初期のパーティション（同値クラス）の構築が非効率であったことが課題でした。

従来のCSEの実装では、値の比較が表面的であり、その引数まで深く掘り下げて比較していませんでした。このため、実際には同じ計算を表す複数の値が異なるパーティションに分類されてしまい、CSEがそれらを共通部分式として認識するまでに余分な処理が必要となっていました。結果として、コンパイル時間の増加や最適化の機会損失に繋がっていました。

コミットメッセージに記載されているように、`arithConst_ssa.go` のコンパイル時間が1秒短縮され、`compilebench` でも3-5%の性能向上が見られたことから、この非効率性が顕著であったことが伺えます。より良い初期パーティションを構築することで、後続のCSE処理が効率化され、全体的なコンパイル速度の向上が期待されました。

## 前提知識の解説

### 1. SSA (Static Single Assignment) 形式

SSA (Static Single Assignment) は、コンパイラ最適化において広く用いられる中間表現 (IR: Intermediate Representation) の一種です。SSA形式の主要な特性は以下の通りです。

*   **単一代入**: 各変数が一度だけ代入されることを保証します。これにより、変数の定義と使用の関係が明確になり、データフロー解析や最適化が容易になります。
*   **Φ関数 (Phi Function)**: 制御フローグラフ (CFG) の複数のパスが合流する点（例えば、if-else文の終わりやループの終わり）で、異なるパスから来る同じ論理的な変数に対して、どの値を使用すべきかを解決するために導入されます。

Goコンパイラは、ソースコードを抽象構文木 (AST) に変換した後、SSA形式に変換して様々な最適化を行います。

### 2. CSE (Common Subexpression Elimination)

共通部分式除去 (CSE) は、コンパイラ最適化の一種で、プログラム内で複数回計算される同じ式（共通部分式）を一度だけ計算し、その結果を再利用することで、実行速度を向上させる技術です。

例えば、`a = (b * c) + d; e = (b * c) + f;` というコードがあった場合、`(b * c)` は共通部分式です。CSEはこれを `temp = b * c; a = temp + d; e = temp + f;` のように変換し、`b * c` の計算を一度で済ませます。

CSEは通常、以下のステップで実行されます。

1.  **値の同値クラスの特定**: プログラム内のすべての式を分析し、同じ結果を生成する可能性のある式（値）をグループ化します。これを「パーティション」または「同値クラス」と呼びます。
2.  **到達定義の分析**: 各同値クラス内の式が、その使用箇所まで変更されずに到達するかどうかを判断します。
3.  **式の置き換え**: 共通部分式を一度だけ計算し、その結果を一時変数に格納し、他の出現箇所をその一時変数への参照に置き換えます。

このコミットは、上記のステップ1、特に「初期のパーティション構築」の精度と効率を改善することに焦点を当てています。

### 3. Goコンパイラの構造 (`cmd/compile` と `internal/ssa`)

Goコンパイラは、`cmd/compile` ディレクトリ以下に実装されています。その中でも、`internal/ssa` パッケージは、GoのソースコードをSSA形式に変換し、その上で様々な最適化（CSE、デッドコード除去、レジスタ割り当てなど）を実行するバックエンドの主要部分を担っています。

`cse.go` ファイルは、この `internal/ssa` パッケージ内で共通部分式除去のロジックを実装しています。

### 4. `Value` と `Aux` フィールド

GoコンパイラのSSA形式では、プログラム内の各操作や計算結果が `Value` 構造体として表現されます。`Value` は、その操作の種類 (`Op`)、型 (`Type`)、引数 (`Args`) などの情報を持っています。

`Aux` フィールドは、`Value` が持つ追加情報（例えば、定数値、メモリ参照のアドレス、特定のシンボルなど）を格納するための `interface{}` 型のフィールドです。`Aux` フィールドは、`Value` の同一性を判断する上で重要な要素となりますが、`interface{}` 型であるため、直接比較が難しい場合があります。

## 技術的詳細

このコミットの核心は、`cse.go` 内の `partitionValues` 関数における初期パーティションの構築方法の改善です。

### 従来の課題

以前の `partitionValues` 関数では、値の比較が主に以下の要素に基づいて行われていました。

*   `Op` (操作の種類)
*   `AuxInt` (補助整数値)
*   `len(Args)` (引数の数)
*   `Block` (Phi関数の場合)
*   `Aux` (補助情報)
*   `Type` (型)
*   そして、**引数の最初の1つまたは2つの `Op` と `AuxInt`**

この比較ロジックは、引数の構造を深く掘り下げていませんでした。特に、引数自体が複雑な式である場合、その引数の `Op` と `AuxInt` だけを比較しても、それらが本当に同じ値であるかを正確に判断することは困難でした。このため、論理的に同じであるべき値が異なるパーティションに分類され、CSEの効率が低下していました。結果として、コンパイル時間の増加や最適化の機会損失に繋がっていました。

### 新しいアプローチ：再帰的な値の比較 (`cmpVal`)

このコミットでは、`cmpVal` という新しい関数が導入され、値の比較ロジックが大幅に強化されました。`cmpVal` は、2つの `Value` を比較し、それらが等しい (`CMPeq`)、小さい (`CMPlt`)、または大きい (`CMPgt`) かを返します。

`cmpVal` の主要な特徴は以下の通りです。

1.  **優先順位付けされた比較**: 比較のコストが低いものから順に比較を行います。
    *   `Op` (操作の種類)
    *   `AuxInt` (補助整数値)
    *   `len(Args)` (引数の数)
    *   `Block` (Phi関数の場合)
    *   `Type` (型)
    *   `Aux` (補助情報)
2.  **`Aux` フィールドの比較の改善**: `Aux` フィールドは `interface{}` 型であるため、直接比較ができません。新しい `auxmap` 型 (`map[interface{}]int32`) を導入し、各ユニークな `Aux` 値に一意のIDを割り当てることで、`Aux` フィールドの比較を可能にしています。これにより、`Aux` が異なる場合でも、その内容が同じであれば同じIDを持つように扱えます。
3.  **引数の再帰的比較**: 最も重要な変更点として、`cmpVal` は `depth` パラメータを使用して、引数を再帰的に比較します。
    *   `cmpDepth` という定数 (`4`) が導入され、再帰の深さを制限します。これにより、無限ループを防ぎつつ、十分な深さまで引数を比較して、より正確な同値性を判断します。
    *   `v.Args[i] == w.Args[i]` のように引数自体が同じオブジェクトであれば比較をスキップし、効率化を図っています。

### `partitionValues` 関数の変更

`partitionValues` 関数は、`sortvalues` 構造体と組み合わせて、値の初期パーティションを構築します。

*   **`auxIDs` の導入**: `partitionValues` 関数は、`auxmap` 型の `auxIDs` を引数として受け取るようになりました。これは、`cse` 関数内で初期化され、`partitionValues` および `sortvalues` に渡されます。
*   **`sortvalues.Less` の簡素化**: 以前は `sortvalues.Less` メソッド内で複雑な比較ロジックが直接記述されていましたが、新しい `cmpVal` 関数を使用するように変更されました。これにより、比較ロジックが `cmpVal` に集約され、コードの可読性と保守性が向上しました。
*   **`cmpVal` の利用**: `partitionValues` 内のループで、隣接する値 `v` と `w` が同じパーティションに属するかどうかを判断する際に、`cmpVal(v, w, auxIDs, cmpDepth) != CMPeq` が使用されるようになりました。これにより、より厳密な同値性に基づいて初期パーティションが構築されます。

### `type.go` の変更

`src/cmd/compile/internal/ssa/type.go` の `(*CompilerType).Compare` メソッドに小さな変更が加えられました。

```go
	if t == x {
		return CMPeq
	}
```
この変更は、比較対象の型 `t` と `x` がポインタレベルで同一である場合に、即座に `CMPeq` (等しい) を返すようにするものです。これは、型の比較処理の初期段階で高速なパスを提供し、不必要な詳細比較を避けるための最適化と考えられます。CSEの文脈では、型の同一性も値の同値性を判断する重要な要素であるため、この変更も全体的な効率向上に寄与します。

### 性能向上

この変更により、`compilebench` の結果が示すように、コンパイル時間が3-5%短縮されました。特に `arithConst_ssa.go` のコンパイルでは1秒の短縮が見られ、これは初期パーティションの改善が特定の種類のコードパターンに対して大きな効果を発揮したことを示しています。より正確な初期パーティションは、後続のCSEパスがより少ないイテレーションで共通部分式を特定できるようになるため、全体的な最適化プロセスの高速化に繋がります。

## コアとなるコードの解説

### `cmpVal` 関数 (src/cmd/compile/internal/ssa/cse.go)

```go
func cmpVal(v, w *Value, auxIDs auxmap, depth int) Cmp {
	// Try to order these comparison by cost (cheaper first)
	if v.Op != w.Op {
		return lt2Cmp(v.Op < w.Op)
	}
	if v.AuxInt != w.AuxInt {
		return lt2Cmp(v.AuxInt < w.AuxInt)
	}
	if len(v.Args) != len(w.Args) {
		return lt2Cmp(len(v.Args) < len(w.Args))
	}
	if v.Op == OpPhi && v.Block != w.Block {
		return lt2Cmp(v.Block.ID < w.Block.ID)
	}
	if tc := v.Type.Compare(w.Type); tc != CMPeq {
		return tc
	}

	if v.Aux != w.Aux {
		if v.Aux == nil {
			return CMPlt
		}
		if w.Aux == nil {
			return CMPgt
		}
		return lt2Cmp(auxIDs[v.Aux] < auxIDs[w.Aux])
	}

	if depth > 0 {
		for i := range v.Args {
			if v.Args[i] == w.Args[i] {
				// skip comparing equal args
				continue
			}
			if ac := cmpVal(v.Args[i], w.Args[i], auxIDs, depth-1); ac != CMPeq {
				return ac
			}
		}
	}

	return CMPeq
}
```

この関数は、2つのSSA `Value` (`v` と `w`) が等しいかどうかを判断するための新しい比較ロジックを提供します。

*   **基本的な属性の比較**: まず、`Op`、`AuxInt`、引数の数 (`len(Args)`)、`Block` (Phi関数の場合)、`Type` といった基本的な属性を順に比較します。これらの属性のいずれかが異なれば、値は等しくないと判断し、その比較結果 (`CMPlt` または `CMPgt`) を返します。`lt2Cmp` は `bool` を `Cmp` 型に変換するヘルパー関数です。
*   **`Aux` フィールドの比較**: `Aux` フィールドは `interface{}` 型であるため、直接比較できません。`auxIDs` マップを使用して、各 `Aux` 値に割り当てられた一意のIDを比較します。これにより、`Aux` の内容が同じであれば同じIDを持つと見なされ、比較が可能になります。`nil` のケースも適切に処理されます。
*   **引数の再帰的比較**: `depth` が0より大きい場合、`v` と `w` の引数を再帰的に比較します。
    *   `v.Args[i] == w.Args[i]` のチェックは、引数オブジェクト自体が同一であれば、それ以上深く比較する必要がないため、高速化に寄与します。
    *   `cmpVal(v.Args[i], w.Args[i], auxIDs, depth-1)` を再帰的に呼び出すことで、引数の引数、さらにその引数と、指定された深さ (`cmpDepth`) まで比較を行います。これにより、より複雑な共通部分式も正確に特定できるようになります。
*   **最終的な等価性**: すべての比較を通過した場合、2つの値は等しい (`CMPeq`) と判断されます。

### `auxmap` 型 (src/cmd/compile/internal/ssa/cse.go)

```go
type auxmap map[interface{}]int32
```

`auxmap` は、`interface{}` 型の `Aux` フィールドをキーとし、`int32` 型のユニークなIDを値とするマップです。`Aux` フィールドは `interface{}` 型であるため、直接比較やソートができません。このマップは、各ユニークな `Aux` 値に安定した順序付け可能なIDを割り当てることで、`cmpVal` 関数内で `Aux` フィールドを比較できるようにするために使用されます。

### `partitionValues` 関数 (src/cmd/compile/internal/ssa/cse.go)

```go
func partitionValues(a []*Value, auxIDs auxmap) []eqclass {
	sort.Sort(sortvalues{a, auxIDs}) // auxIDsを渡す
    // ... (中略) ...
	for i := 0; i < len(a); i += k {
		v := a[i]
		j := 1
		for ; j < len(a); j++ {
			w := a[j]
			if cmpVal(v, w, auxIDs, cmpDepth) != CMPeq { // cmpValを使用
				break
			}
		}
        // ... (後略) ...
	}
    // ... (後略) ...
}
```

`partitionValues` 関数は、SSA `Value` のスライス `a` を受け取り、それらを同値クラスのリスト (`[]eqclass`) に分割します。

*   **`auxIDs` の受け渡し**: `cse` 関数から初期化された `auxIDs` マップが引数として渡されるようになりました。
*   **ソートの改善**: `sort.Sort(sortvalues{a, auxIDs})` の呼び出しで、`sortvalues` 構造体に `auxIDs` が渡されます。これにより、ソート時に `cmpVal` を介して `Aux` フィールドが適切に比較されるようになります。
*   **同値クラスの判定**: ループ内で隣接する値 `v` と `w` が同じ同値クラスに属するかどうかを判断する際に、以前の複雑なインライン比較ロジックが `cmpVal(v, w, auxIDs, cmpDepth) != CMPeq` という簡潔な呼び出しに置き換えられました。これにより、より厳密で深い比較に基づいて初期パーティションが構築されるため、CSEの効率が向上します。

### `sortvalues.Less` メソッド (src/cmd/compile/internal/ssa/cse.go)

```go
func (sv sortvalues) Less(i, j int) bool {
	v := sv.a[i]
	w := sv.a[j]
	if cmp := cmpVal(v, w, sv.auxIDs, cmpDepth); cmp != CMPeq {
		return cmp == CMPlt
	}

	// Sort by value ID last to keep the sort result deterministic.
	return v.ID < w.ID
}
```

`sortvalues` は、`Value` のスライスをソートするための `sort.Interface` インターフェースを実装する型です。

*   **`cmpVal` の利用**: `Less` メソッドは、2つの値 `v` と `w` の順序を決定するために、新しく導入された `cmpVal` 関数を呼び出します。`cmpVal` が `CMPeq` 以外の結果を返した場合、その結果に基づいて `v` が `w` より小さいかどうかを判断します。
*   **決定論的なソート**: `cmpVal` が `CMPeq` を返した場合（つまり、`v` と `w` が論理的に等しいと判断された場合）、最終的に `v.ID < w.ID` に基づいてソートされます。これは、ソート結果を決定論的に保つための一般的なプラクティスであり、コンパイラの挙動の再現性を保証します。

### `(*CompilerType).Compare` メソッド (src/cmd/compile/internal/ssa/type.go)

```go
func (t *CompilerType) Compare(u Type) Cmp {
	// ... (中略) ...
	if t == x { // xはuをCompilerTypeにキャストしたもの
		return CMPeq
	}
	// ... (後略) ...
}
```

この小さな変更は、型の比較の初期段階でポインタの同一性をチェックすることで、パフォーマンスを向上させます。もし2つの型がメモリ上で同じオブジェクトを指している場合、それらは確実に等しいと判断できるため、それ以上の詳細な比較は不要になります。これは、CSEにおける値の比較の一部として型の比較が行われるため、全体的な効率向上に寄与します。

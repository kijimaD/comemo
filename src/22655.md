# [インデックス 22655] ファイルの概要

このコミットは、Goランタイムが複数のリンカシンボルを扱う方法を根本的に変更し、それらを単一の`moduledata`構造体に集約することを目的としています。これは、将来的にGoプログラムが複数のオブジェクト（例えば、共有ライブラリやプラグイン）からのコードを実行できるようにするための重要な準備作業です。

## 変更の背景

Goプログラムは通常、コンパイル時にすべてのコードと依存関係を単一の実行可能ファイルに静的にリンクします。しかし、プラグインシステムや動的ライブラリのサポートなど、複数の独立したコンパイル単位（オブジェクト）を一つのGoプログラムに統合するニーズが存在します。

このコミット以前のGoランタイムは、プログラムの様々なセクション（コード、データ、BSS、PC-Lineテーブルなど）のアドレスやサイズを、`data`、`etext`、`pclntab`といった個別のリンカシンボルを通じて参照していました。このアプローチは、単一の実行可能ファイルには適していましたが、将来的に複数のオブジェクトからのコードを扱う際には、それぞれのオブジェクトが独自のこれらの情報を持つことになり、管理が複雑になるという課題がありました。

この変更は、Goプログラムが複数のオブジェクトからのコードを組み込めるようにするための基盤を築くものです。個別のリンカシンボルに依存するのではなく、`moduledata`という単一の構造体にすべての必要なメタデータを集約することで、ランタイムはプログラムのメモリレイアウトに関する情報を一元的に、かつ構造化された形で取得できるようになります。これにより、将来的に複数の`moduledata`インスタンスをリンクリストとして連結し、動的にロードされたモジュールの情報を効率的に管理する道が開かれます。

## 前提知識の解説

*   **Goランタイム (Go Runtime)**: Goプログラムの実行を管理する低レベルな部分です。ガベージコレクション、ゴルーチンのスケジューリング、メモリ管理、スタック管理、デバッガとの連携など、Goプログラムが動作するために不可欠な機能を提供します。GoランタイムはGo言語で書かれており、Goプログラムに静的にリンクされます。
*   **リンカシンボル (Linker Symbols)**: コンパイルされたコード内で、特定のメモリ位置（変数、関数、コードセクションの開始/終了アドレスなど）を識別するためにリンカが使用する名前です。リンカは、これらのシンボルを解決し、最終的な実行可能ファイル内の具体的な仮想メモリアドレスにマッピングします。例えば、`text`はコードセクションの開始、`etext`はコードセクションの終了、`data`は初期化済みデータセクションの開始、`bss`は初期化されていないデータセクションの開始などを表します。
*   **`moduledata`構造体**: Goランタイムが実行可能ファイルのメモリレイアウトに関するメタデータ（型情報、関数テーブル、PC-Lineテーブル、データセクションのアドレス範囲など）を取得するために使用する重要なデータ構造です。この構造体はGoリンカによって生成され、実行時にGoランタイムがプログラムの構造を理解し、ガベージコレクション、スタックトレース、デバッグなどの操作を正確に実行するために利用されます。
*   **複数オブジェクト/モジュールサポート (Multiple Object/Module Support)**: 複数の独立したコンパイル単位（オブジェクトファイルや共有ライブラリ）を一つのGoプログラムに統合する機能です。これにより、Goプログラムが実行時に外部のGoコード（例えば、プラグインとしてロードされるモジュール）を動的に組み込むことが可能になります。これは、Goの初期設計ではあまり考慮されていなかった機能であり、このコミットはその実現に向けた重要なステップとなります。

## 技術的詳細

このコミットの核心は、Goランタイムがプログラムのメモリレイアウトに関する情報を取得する方法を、個別のリンカシンボルから単一の`moduledata`構造体へと移行することにあります。

1.  **`moduledata`構造体の導入**:
    `src/runtime/symtab.go`に`moduledata`という新しい構造体が定義されました。この構造体は、以前は個別のリンカシンボルとして扱われていた、プログラムの様々なセクション（`pclntable`, `ftab`, `filetab`, `text`, `etext`, `noptrdata`, `enoptrdata`, `data`, `edata`, `bss`, `ebss`, `noptrbss`, `enoptrbss`, `end`, `gcdata`, `gcbss`, `typelink`, `etypelink`）のアドレスとサイズを保持するフィールドを含んでいます。
    また、この構造体のグローバルインスタンスとして`themoduledata`変数が宣言されました。

2.  **リンカの変更 (`cmd/internal/ld/symtab.go`)**:
    Goリンカのシンボルテーブル生成ロジック（`src/cmd/internal/ld/symtab.go`の`symtab()`関数）が変更されました。以前は、`runtime.pclntab`、`runtime.data`などの個別のリンカシンボルを定義し、それらのアドレスを直接設定していました。
    変更後、リンカは`runtime.themoduledata`という単一のシンボルをルックアップし、そのシンボルが指す`moduledata`構造体の各フィールドに、対応するセクションのアドレスやサイズを書き込むようになりました。これにより、リンカがランタイムに提供する情報が構造化され、一元化されます。

3.  **ランタイムコードの更新**:
    `src/runtime/heapdump.go`、`src/runtime/malloc.go`、`src/runtime/mbarrier.go`、`src/runtime/mbitmap.go`、`src/runtime/mfinal.go`、`src/runtime/mgc.go`、`src/runtime/mgcmark.go`、`src/runtime/os1_windows_386.go`、`src/runtime/os1_windows_amd64.go`、`src/runtime/proc1.go`、`src/runtime/race1.go`、`src/runtime/runtime1.go`、`src/runtime/symtab.go`など、多数のランタイムファイルが変更されました。
    これらのファイルでは、以前は`uintptr(unsafe.Pointer(&data))`のように個別のリンカシンボルへのポインタを直接使用していた箇所が、`themoduledata.data`のように`themoduledata`構造体のフィールドへの参照に置き換えられました。これにより、ランタイムコードはプログラムのメモリレイアウト情報を`themoduledata`を通じて一貫して取得するようになります。

4.  **将来の複数オブジェクトサポートへの布石**:
    コミットメッセージには「Multiple object support will construct a linked list of such structures.」と明記されています。これは、将来的にGoが複数のオブジェクトをサポートする際に、それぞれのオブジェクトが独自の`moduledata`構造体を持ち、それらがリンクリストとして連結されることを示唆しています。このコミットは、そのための最初のステップとして、単一の`moduledata`構造体への集約を行っています。

この変更により、Goランタイムはプログラムのメモリレイアウトに関する情報をより柔軟かつ効率的に管理できるようになり、Goのモジュールシステムや動的リンク機能の進化に向けた重要な基盤が構築されました。

## コアとなるコードの変更箇所

*   `src/runtime/symtab.go`: `moduledata`構造体の定義と、そのグローバルインスタンス`themoduledata`の宣言。
*   `src/cmd/internal/ld/symtab.go`: リンカが`themoduledata`構造体を初期化し、プログラムの各セクションのアドレスをそのフィールドに設定するロジックの追加。
*   `src/runtime/*.go` (多数のファイル): ランタイムコード内で、個別のリンカシンボルへの直接参照を`themoduledata`構造体の対応するフィールドへの参照に置き換え。

## コアとなるコードの解説

### `src/runtime/symtab.go`の変更

```go
// moduledata records information about the layout of the executable
// image. It is written by the linker. Any changes here must be
// matched changes to the code in cmd/internal/ld/symtab.go:symtab.
type moduledata struct {
	pclntable                      []byte
	ftab                           []functab
	filetab                        []uint32
	pclntab, epclntab, findfunctab uintptr
	minpc, maxpc                   uintptr

	text, etext           uintptr
	noptrdata, enoptrdata uintptr
	data, edata           uintptr
	bss, ebss             uintptr
	noptrbss, enoptrbss   uintptr
	end, gcdata, gcbss    uintptr

	typelink, etypelink uintptr
}

var themoduledata moduledata // linker symbol
```
この変更により、`moduledata`という新しい構造体が導入されました。この構造体は、Go実行可能ファイルの様々なセクション（コード、データ、BSS、GCデータ、型情報など）のアドレスとサイズを保持するようになりました。`themoduledata`というグローバル変数がこの構造体のインスタンスとして宣言され、リンカによって初期化されます。これにより、ランタイムがプログラムのメモリレイアウトに関するすべての情報を一元的に参照できるようになります。以前は、これらの情報は`pclntab`、`data`、`bss`といった個別のリンカシンボルとして散在していました。

### `src/cmd/internal/ld/symtab.go`の変更

```go
	// Information about the layout of the executable image for the
	// runtime to use. Any changes here must be matched by changes to
	// the definition of moduledata in runtime/symtab.go.
	moduledata := Linklookup(Ctxt, "runtime.themoduledata", 0)
	moduledata.Type = SNOPTRDATA
	moduledata.Size = 0 // truncate symbol back to 0 bytes to reinitialize
	moduledata.Reachable = true
	// Three slices (pclntable, ftab, filetab), uninitalized
	moduledata.Size += int64((3 * 3 * Thearch.Ptrsize))
	Symgrow(Ctxt, moduledata, moduledata.Size)
	// Three uintptrs, initialized
	Addaddr(Ctxt, moduledata, Linklookup(Ctxt, "runtime.pclntab", 0))
	Addaddr(Ctxt, moduledata, Linklookup(Ctxt, "runtime.epclntab", 0))
	Addaddr(Ctxt, moduledata, Linklookup(Ctxt, "runtime.findfunctab", 0))
	// ... (他のセクションのアドレス追加)
```
リンカは、以前は個別のリンカシンボルとして出力していた情報を、`themoduledata`構造体の対応するフィールドに書き込むように変更されました。具体的には、`Linklookup`で`runtime.themoduledata`シンボルを取得し、`Addaddr`などの関数を使って、`pclntab`、`text`、`data`、`bss`などの各セクションのアドレスを`themoduledata`構造体の適切なオフセットに書き込んでいます。これにより、リンカとランタイム間のインターフェースが簡素化され、将来的に複数のモジュールを扱う際の柔軟性が向上します。

### 他の`src/runtime/*.go`ファイルの変更例

```go
// src/runtime/heapdump.go の変更例
-	dumpbvtypes(&gcdatamask, unsafe.Pointer(&data))
+	dumpbvtypes(&gcdatamask, unsafe.Pointer(themoduledata.data))

// src/runtime/malloc.go の変更例
-	p = round(uintptr(unsafe.Pointer(&end))+(1<<18), 1<<20)
+	p = round(themoduledata.end+(1<<18), 1<<20)

// src/runtime/symtab.go の変更例 (symtabinit関数内)
-	pcln := (*[8]byte)(unsafe.Pointer(&pclntab))
+	pcln := (*[8]byte)(unsafe.Pointer(themoduledata.pclntab))
```
これらのファイルでは、以前は`&data`や`&etext`のように直接参照していたリンカシンボルへのポインタが、`themoduledata.data`や`themoduledata.etext`のように`themoduledata`構造体のフィールドへの参照に置き換えられました。これは、ランタイムがプログラムのメモリレイアウト情報を取得する方法の一貫性を高めるための変更であり、`moduledata`構造体を通じてすべての関連情報にアクセスできるようにします。

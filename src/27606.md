## 元コミット内容

`cmd/compile: add a pass to print bound checks`

境界チェック排除（BCE）は複数のパス（`opt`, `loopbce`, `prove`など）にわたって行われるため、コードの書き換えによって退行（regression）が発生しやすくなっています。
このパスは、特別なデバッグフラグが有効な場合にのみアクティブになります。

## 変更の背景

Go言語はメモリ安全性を重視しており、配列やスライスへのアクセス時には必ず境界チェック（Bounds Check）を行います。これにより、バッファオーバーフローなどのメモリ関連の脆弱性を防ぎます。しかし、全てのアクセスに対して境界チェックを行うと、プログラムの実行性能にオーバーヘッドが生じます。

このオーバーヘッドを削減するため、Goコンパイラは「境界チェック排除（Bounds Check Elimination, BCE）」という最適化を行います。BCEは、コンパイラが静的にアクセスが常に有効な範囲内にあることを証明できる場合に、冗長な境界チェックを削除するものです。例えば、`for i := 0; i < len(s); i++` のようなループ内で `s[i]` にアクセスする場合、コンパイラは `i` が `len(s)` 未満であることが保証されているため、`s[i]` へのアクセスに対する境界チェックを省略できます。

コミットメッセージにあるように、BCEはコンパイラのSSA（Static Single Assignment）フェーズにおいて、`opt`、`loopbce`、`prove` など複数の最適化パスにわたって実行されます。この複雑なプロセスは、コンパイラのコードが変更された際に、意図せずBCEが正しく機能しなくなり、本来排除されるべき境界チェックが残ってしまう「退行」を引き起こす可能性があります。

このコミットは、このようなBCEの退行を早期に発見し、デバッグを容易にするためのツールとして、境界チェックが残存している箇所を報告するデバッグパスを追加することを目的としています。これにより、コンパイラの開発者はBCEの最適化が期待通りに機能しているかを簡単に確認できるようになります。

## 前提知識の解説

### GoコンパイラのSSA (Static Single Assignment) フォーム

Goコンパイラは、ソースコードを機械語に変換する過程で、プログラムの内部表現としてSSA（Static Single Assignment）フォームを利用します。SSAは、各変数が一度だけ代入されるという特性を持つ中間表現です。この特性により、データフロー解析が大幅に簡素化され、コンパイラがより効果的な最適化（デッドコード排除、共通部分式排除、境界チェック排除など）を適用できるようになります。

GoコンパイラのSSAフェーズは、AST（抽象構文木）からSSAフォームを生成し、そのSSAフォームに対して一連の最適化パスを適用します。最終的に最適化されたSSAフォームは、ターゲットアーキテクチャの機械語に変換されます。

### Bounds Check Elimination (BCE)

BCEは、Goコンパイラにおける重要な最適化の一つです。Go言語では、配列やスライスへのアクセス（例: `a[i]`) が行われる際に、インデックス `i` がそのデータ構造の有効な範囲内にあるかを確認する「境界チェック」が実行されます。これはメモリ安全性を保証するために不可欠ですが、実行時のオーバーヘッドを伴います。

BCEは、コンパイラが静的解析によって、特定のアクセスが常に有効な範囲内にあることを証明できる場合に、その境界チェックを削除します。これにより、プログラムの安全性は維持しつつ、性能を向上させることができます。例えば、ループの条件や事前の条件分岐によってインデックスの範囲が保証されている場合などにBCEが適用されます。

### コンパイラパス

コンパイラは、ソースコードを最終的な実行可能ファイルに変換するために、複数の段階（フェーズ）を経て処理を行います。各フェーズは、特定のタスクを実行する一連の「パス」で構成されます。各パスは、プログラムの内部表現（AST、SSAなど）を読み込み、変換し、次のパスに渡します。

GoコンパイラのSSAフェーズでは、多くの最適化パスが連続して実行されます。例えば、`opt`（一般的な最適化）、`loopbce`（ループ内のBCE）、`prove`（証明に基づく最適化）などがBCEに関連するパスです。これらのパスは互いに依存し、特定の順序で実行されることで、最終的な最適化されたコードが生成されます。

### `OpIsInBounds` と `OpIsSliceInBounds`

これらはGoコンパイラのSSA中間表現における特定の操作（Operation）です。
*   `OpIsInBounds`: 単一の要素アクセス（例: `a[i]`) に対する境界チェックを表します。コンパイラがこの操作を生成し、実行時にインデックスが有効範囲内にあるかを確認します。
*   `OpIsSliceInBounds`: スライスのスライス操作（例: `a[low:high]`) に対する境界チェックを表します。スライスの作成時に、指定された `low`、`high`、`max` インデックスが基盤となる配列の容量に対して有効であるかを確認します。

BCEの目的は、これらの `OpIsInBounds` や `OpIsSliceInBounds` オペレーションを、コンパイラが安全だと判断できる場合にSSAグラフから削除することです。

## 技術的詳細

このコミットで追加された `checkbce` パスは、GoコンパイラのSSAバックエンドに組み込まれるデバッグツールです。その主な機能は、SSA最適化パスが全て完了した後でも、コード内に残存している `OpIsInBounds` または `OpIsSliceInBounds` オペレーションを特定し、警告として出力することです。

1.  **デバッグフラグによる有効化**: `checkbce` パスは、デフォルトでは無効になっています。コンパイラに特定のデバッグフラグ（例: `go build -gcflags="-d=ssa/check_bce/debug=3"` のような形式）が渡された場合にのみ有効になります。これにより、通常のコンパイルプロセスにオーバーヘッドを与えることなく、必要な時にのみデバッグ情報を取得できます。
2.  **パスの実行順序**: `src/cmd/compile/internal/ssa/compile.go` 内の `passes` 配列に `checkbce` パスが追加されます。このパスは `generic deadcode` パスの後に実行されるように依存関係が設定されています。これは、デッドコード排除によって不要なSSA値が削除された後で、実際に残っている境界チェックのみを対象とするためです。
3.  **SSA値の走査**: `checkbce` 関数は、現在の関数 `f` の全ての基本ブロック（`f.Blocks`）を走査し、各ブロック内の全てのSSA値（`b.Values`）を検査します。
4.  **境界チェックオペレーションの検出**: 各SSA値 `v` について、そのオペレーション `v.Op` が `OpIsInBounds` または `OpIsSliceInBounds` であるかをチェックします。
5.  **警告の出力**: 検出された境界チェックオペレーションに対しては、`f.Config.Warnl(v.Line, "Found %v", v.Op)` を呼び出して警告メッセージを出力します。この警告には、境界チェックが見つかったソースコードの行番号と、そのオペレーションの種類が含まれます。

このメカニズムにより、コンパイラの開発者は、BCE最適化の変更が既存のコードベースや新しいコードパターンに対してどのような影響を与えているかを、具体的な境界チェックの残存状況を通じて把握できるようになります。これは、BCEの退行を防ぎ、最適化の品質を維持するために非常に価値のあるデバッグ支援機能です。

### `src/cmd/compile/internal/ssa/checkbce.go` (新規ファイル)

```go
// Copyright 2016 The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

package ssa

// checkbce prints all bounds checks that are present in the function.
// Useful to find regressions. checkbce is only activated when with
// corresponsing debug options, so it's off by default.
// See test/checkbce.go
func checkbce(f *Func) {
	if f.pass.debug <= 0 {
		return
	}

	for _, b := range f.Blocks {
		for _, v := range b.Values {
			if v.Op == OpIsInBounds || v.Op == OpIsSliceInBounds {
				f.Config.Warnl(v.Line, "Found %v", v.Op)
			}
		}
	}
}
```

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/checkbce.go`

このファイルは、新しいコンパイラパス `checkbce` の実装を含んでいます。
*   `func checkbce(f *Func)`: この関数がパスのエントリポイントです。`*Func` はSSA形式で表現された現在の関数を表します。
*   `if f.pass.debug <= 0 { return }`: この行は、`checkbce` パスがデバッグモードでのみ実行されることを保証します。`f.pass.debug` はコンパイラに渡されたデバッグフラグの値に基づいて設定されます。値が0以下の場合は、パスは何もせずに終了します。
*   `for _, b := range f.Blocks { ... }`: 関数内の全ての基本ブロック（`Block`）を反復処理します。基本ブロックは、単一のエントリポイントと単一のエグジットポイントを持つ命令のシーケンスです。
*   `for _, v := range b.Values { ... }`: 各基本ブロック内の全てのSSA値（`Value`）を反復処理します。SSA値は、オペレーション（`v.Op`）、型、引数などを持つSSAフォームの基本的な構成要素です。
*   `if v.Op == OpIsInBounds || v.Op == OpIsSliceInBounds { ... }`: 現在のSSA値のオペレーションが `OpIsInBounds` または `OpIsSliceInBounds` であるかをチェックします。これらは、それぞれ単一要素アクセスとスライス操作に対する境界チェックを表すSSAオペレーションです。
*   `f.Config.Warnl(v.Line, "Found %v", v.Op)`: 境界チェックオペレーションが検出された場合、コンパイラの警告メカニズムを使用して警告メッセージを出力します。`v.Line` はソースコード上の行番号を示し、`v.Op` は検出されたオペレーションの種類（例: `IsInBounds`）を示します。これにより、開発者はどのソースコードの行で境界チェックが残存しているかを正確に把握できます。

### `src/cmd/compile/internal/ssa/compile.go`

このファイルは、GoコンパイラのSSAフェーズにおける全てのパスの定義と実行順序を管理します。
*   `var passes = [...]pass{ ... {name: "check bce", fn: checkbce}, ... }`: `passes` 配列に新しい `check bce` パスが追加されます。`fn: checkbce` は、上記で定義された `checkbce` 関数がこのパスの実行関数であることを示します。この追加により、`checkbce` がコンパイラパスの一部として認識されるようになります。
*   `var passOrder = [...]constraint{ ... {"generic deadcode", "check bce"}, ... }`: `passOrder` 配列に新しい制約が追加されます。`{"generic deadcode", "check bce"}` は、`check bce` パスが `generic deadcode` パスの後に実行される必要があることを示します。この順序は重要で、`generic deadcode` パスが不要なSSA値を削除した後で `checkbce` が実行されることで、より正確な残存境界チェックの報告が可能になります。

### `test/checkbce.go`

このテストファイルは、`checkbce` パスの機能と正確性を検証するために作成されました。
*   `// +build amd64`: このビルドタグは、このテストがAMD64アーキテクチャでのみ実行されることを示します。
*   `// errorcheck -0 -d=ssa/check_bce/debug=3`: これはGoのテストツール `errorcheck` に対する指示です。
    *   `-0`: 警告やエラーを無視しないことを意味します。
    *   `-d=ssa/check_bce/debug=3`: `checkbce` パスを有効にし、デバッグレベルを3に設定します。これにより、`checkbce` パスが実行され、境界チェックが検出された場合に警告が出力されるようになります。
*   `func f0(a []int) { a[0] = 1 // ERROR "Found IsInBounds$" ... }`: 各テスト関数（`f0`から`g3`まで）は、意図的に境界チェックが残るようなコードパターンを含んでいます。`// ERROR "Found IsInBounds$"` や `// ERROR "Found IsSliceInBounds$"` のコメントは、`errorcheck` ツールに対して、この行で特定の警告メッセージ（`Found IsInBounds` または `Found IsSliceInBounds`）が出力されることを期待していることを示します。これにより、`checkbce` パスが正しく境界チェックを検出しているかどうかが検証されます。

これらの変更により、Goコンパイラの開発者は、BCE最適化の健全性を維持するための強力なデバッグツールを手に入れることになります。

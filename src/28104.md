# [インデックス 28104] ファイルの概要

このコミットは、Goランタイムのメモリ管理における重要な最適化を導入しています。具体的には、ガベージコレクタが使用するビットマップからのオブジェクト割り当て処理において、Go言語で実装されていたCount Trailing Zeros (CTZ) 関数を、コンパイラが提供する`sys.Ctz64`組み込み関数に置き換えるものです。これにより、メモリ割り当てのパフォーマンスが向上します。

    unmarked object. It then shifts marked bits out of
    the bitmap word preparing it for the next search.

## 元コミット内容

このコミットは、Goコンパイラが提供する`sys.Ctz64`組み込み関数を利用するようにGoランタイムのメモリ割り当てロジックを変更します。これにより、Go言語で実装されていたCTZ（Count Trailing Zeros）のバージョンが置き換えられます。CTZは、ワード内の最下位の1ビットを見つけ、その1ビットよりも下位にある0ビットの数を返します。ガベージコレクタが生成するビットマップを用いたオブジェクト割り当てにおいて、このCTZ関数は、マークされていない利用可能なオブジェクトを効率的に特定するために使用されます。割り当てロジックは、ビットマップのワードを取得し、それを補数化してキャッシュし、CTZを使って利用可能なオブジェクトを見つけます。その後、マークされたビットをビットマップワードからシフトアウトし、次の検索に備えます。キャッシュされたワード内のマークされていないオブジェクトがすべて使用されると、ビットマップは次のワードを取得し、このプロセスを繰り返します。

## 変更の背景

Goランタイムのメモリ管理、特にガベージコレクション後のオブジェクト割り当ては、アプリケーションのパフォーマンスに直結する重要な部分です。このプロセスでは、メモリ領域の空き状況を示すビットマップを高速に走査し、利用可能なメモリブロックを見つける必要があります。

以前のGoランタイムでは、この「末尾のゼロの数（Count Trailing Zeros: CTZ）」を計算するロジックがGo言語で実装されていました。しかし、多くの現代的なCPUアーキテクチャ（x86-64の`BSF` (Bit Scan Forward) やARMの`CLZ` (Count Leading Zeros) / `CTZ`命令など）は、このCTZ操作をハードウェアレベルでサポートする専用の命令を持っています。これらのハードウェア命令は、ソフトウェアで同じロジックを実装するよりもはるかに高速です。

このコミットの背景には、Goコンパイラがこれらのハードウェア命令に対応する組み込み関数（intrinsic function）を提供するようになったという進化があります。組み込み関数は、特定の関数呼び出しをコンパイラが認識し、対応するCPUのネイティブ命令に直接置き換えることで、Go言語のコードでありながらアセンブリ言語レベルのパフォーマンスを引き出すことを可能にします。

したがって、この変更の目的は、Goランタイムのメモリ割り当てにおけるCTZ計算を、より高速なコンパイラ組み込み関数`sys.Ctz64`に置き換えることで、ガベージコレクション後のオブジェクト割り当ての効率を向上させ、全体的なアプリケーションパフォーマンスを改善することにあります。

## 前提知識の解説

### 1. Goランタイムのメモリ管理

Goランタイムは、独自のメモリマネージャとガベージコレクタ（GC）を持っています。メモリはヒープと呼ばれる領域から割り当てられ、GCが不要になったオブジェクトを自動的に回収します。

*   **mspan**: Goランタイムのメモリ管理の基本的な単位です。mspanは、特定のサイズのオブジェクトを格納するために使用される連続したメモリページのセットです。
*   **mcache**: 各P（プロセッサ、OSスレッドに相当）にローカルなキャッシュで、小さなオブジェクトの割り当てを高速化します。mcacheはmspanのリストを保持し、そこからオブジェクトを割り当てます。
*   **mheap**: グローバルなヒープで、mspanを管理します。mcacheがmspanを使い切ると、mheapから新しいmspanを取得します。

### 2. ガベージコレクションとビットマップ

Goのガベージコレクタは、マーク＆スイープ方式を採用しています。

*   **マークフェーズ**: ライブオブジェクト（プログラムから到達可能なオブジェクト）を特定し、マークします。
*   **スイープフェーズ**: マークされていないオブジェクト（デッドオブジェクト）が占めていたメモリを解放し、再利用可能にします。

このプロセスにおいて、メモリ領域の各オブジェクトがライブであるかデッドであるかを示すために「ビットマップ」が使用されます。ビットマップの各ビットは、メモリ上の特定のオブジェクトのステータス（マーク済みか未マークか）に対応します。

### 3. Count Trailing Zeros (CTZ)

CTZは、バイナリワード（通常は64ビット整数）の最下位ビットから数えて、最初に1が現れるまでの連続する0の数を数える操作です。

*   例: `0b...00101000` のCTZは3です（右から3つの0の後に1があるため）。
*   `0b...00000000` のCTZは、通常、ワードのビット幅（64ビットワードなら64）と定義されます。

CTZは、ビットマップから空きスロットを効率的に見つけるのに非常に役立ちます。例えば、ビットマップのワードが`0b...00101000`である場合、CTZは3を返します。これは、このワードの3番目の位置（0-indexed）に空きスロットがあることを意味します。

### 4. コンパイラ組み込み関数 (Intrinsic Functions)

組み込み関数は、特定の関数呼び出しをコンパイラが認識し、その関数を呼び出す代わりに、対応するCPUのネイティブ命令に直接置き換える特殊な関数です。これにより、プログラマは高レベル言語でコードを記述しながら、アセンブリ言語レベルのパフォーマンス最適化の恩恵を受けることができます。CTZのようなビット操作は、多くのCPUが専用の高速命令を持っているため、組み込み関数として提供される典型的な例です。

## 技術的詳細

このコミットの核心は、Goランタイムのメモリ割り当てロジックにおけるCTZ計算の実装を、Go言語によるソフトウェア実装から、コンパイラ組み込み関数`sys.Ctz64`への置き換えです。

### 変更前: ソフトウェアCTZの実装

コミット前の`src/runtime/mbitmap.go`には、`ctzVals`という256要素のルックアップテーブルと、それを利用した`ctz64`関数が存在していました。

*   `ctzVals`は、0から255までの各バイト値に対して、その末尾のゼロの数を事前に計算して格納した配列です。
*   `ctz64`関数は、64ビットの`markBits`を受け取り、それを8ビットずつ処理していました。各バイトに対して`ctzVals`を使ってCTZを計算し、結果を累積することで64ビットワード全体のCTZを求めていました。これは、ハードウェアCTZ命令がない環境や、コンパイラがその命令をサポートしていない場合に、比較的効率的にCTZを計算するための一般的なソフトウェア手法です。

このソフトウェア実装は、ループとルックアップテーブルアクセスを伴うため、CPUのネイティブCTZ命令に比べてオーバーヘッドがありました。

### 変更後: `sys.Ctz64`組み込み関数の利用

このコミットでは、`src/runtime/malloc.go`と`src/runtime/mbitmap.go`内の`ctz64`関数への呼び出しが、直接`sys.Ctz64`に置き換えられています。

*   `sys.Ctz64`は、Goコンパイラが提供する組み込み関数であり、コンパイル時にターゲットCPUのCTZ命令（例: x86-64の`BSF`命令）に変換されます。
*   これにより、CTZ計算がCPUのハードウェアレベルで実行されるようになり、大幅な高速化が期待できます。

### メモリ割り当てへの影響

Goランタイムのメモリ割り当てでは、`mcache`の`nextFreeFast`メソッドや`mspan`の`nextFreeIndex`メソッドが、空いているオブジェクトスロットを見つけるためにCTZを利用しています。

1.  **`mcache.nextFreeFast`**: 小さなオブジェクトの高速割り当てパスです。`s.allocCache`という64ビットのキャッシュワードから、`sys.Ctz64`を使って空きスロット（最下位の1ビット）を見つけます。見つかったスロットは`theBit`として取得され、その位置に基づいてオブジェクトが割り当てられます。割り当て後、`s.allocCache`はシフトされ、次の検索に備えます。
2.  **`mspan.nextFreeIndex`**: `mcache`がmspanからオブジェクトを割り当てる際に、より詳細なビットマップ操作を行います。ここでも`s.allocCache`に対して`sys.Ctz64`が使用され、空きインデックスが特定されます。`allocCache`がすべて使い切られた場合（`bitIndex == 64`）、`refillAllocCache`が呼び出されて、mspanの実際のビットマップから次の64ビットが`allocCache`にロードされます。

この変更により、これらの割り当てパスにおけるCTZ計算が高速化され、結果としてGoプログラム全体のメモリ割り当て性能が向上します。特に、頻繁に小さなオブジェクトを割り当てるアプリケーションでは、この最適化の恩恵が大きくなります。

## コアとなるコードの解説

### `src/runtime/malloc.go` の変更

`mcache`構造体の`nextFreeFast`メソッドは、小さなオブジェクトを高速に割り当てるためのパスです。
変更前は、`s.allocCache`から`ctzIndex`を抽出し、`ctzVals`ルックアップテーブルを使用して`theBit`（末尾のゼロの数）を計算していました。
変更後は、この複雑なロジックが`theBit := sys.Ctz64(s.allocCache)`という一行に置き換えられています。これにより、コンパイラが直接CPUのCTZ命令を利用できるようになり、コードが簡潔かつ高速になりました。`if theBit < 64`という条件は、`sys.Ctz64`が64ビットワード全体がゼロの場合に64を返すという仕様に基づいています。

### `src/runtime/mbitmap.go` の変更

このファイルでは、主に以下の2つの大きな変更が行われています。

1.  **`ctzVals`配列と`ctz64`関数の削除**:
    Go言語で実装されていた`ctzVals`ルックアップテーブルと、それを利用して64ビットワードのCTZを計算する`ctz64`関数が完全に削除されました。これは、これらのソフトウェア実装が不要になったことを意味します。

2.  **`mspan.nextFreeIndex`メソッドの変更**:
    `mspan`構造体の`nextFreeIndex`メソッドは、mspanから次の空きオブジェクトのインデックスを見つける役割を担っています。
    変更前は、`bitIndex := ctz64(aCache)`という形でソフトウェア実装の`ctz64`を呼び出していました。
    変更後は、ここも`bitIndex := sys.Ctz64(aCache)`に置き換えられています。これにより、`mspan`レベルでの空きインデックス検索もハードウェア支援によって高速化されます。
    コメントも`// Nothing was available try again now allocCache has been refilled.`から`// nothing available in cached bits // grab the next 8 bytes and try again.`に変更されており、より直接的な表現になっています。

### `src/runtime/mheap.go` の変更

`mheap.go`では、`mspan`構造体の`allocCache`フィールドに関するコメントが修正されています。
変更前は`ctz64 (count trailing zero)`と記載されていましたが、`ctz`に修正されています。これは、特定の`ctz64`関数ではなく、より一般的なCTZ操作を指すようになったことを示唆しています。この変更自体は機能的なものではなく、ドキュメントの整合性を保つためのものです。

これらの変更により、Goランタイムのメモリ割り当てにおけるCTZ計算が、より効率的なハードウェア命令にオフロードされ、全体的なパフォーマンスが向上します。

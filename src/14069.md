# [インデックス 14069] ファイルの概要

このコミットは、Go言語のARMアーキテクチャ向けリンカ（`cmd/ld`および`cmd/5l`）における重要な改善を含んでいます。具体的には、ARMの再配置タイプである`R_ARM_PC24`と`R_ARM_JUMP24`のサポートを追加し、既存の`R_ARM_CALL`の挙動を修正しています。また、内部的な再配置タイプ`D_PLT32`を`D_CALL`に統合することで、コードの整理と簡素化を図っています。これにより、ARMバイナリの生成における正確性と互換性が向上しました。

## 変更の背景

このコミットは、Go言語のARMアーキテクチャ向けリンカが、特定のARM再配置タイプを正しく処理できるようにするために行われました。特に、`R_ARM_PC24`と`R_ARM_JUMP24`は、ARMの分岐命令（`B`や`BL`）のターゲットアドレスを解決するために使用される重要な再配置タイプです。これらがGoリンカで適切にサポートされていない場合、生成されるARMバイナリが正しくリンクされず、実行時に問題が発生する可能性がありました。

また、`R_ARM_CALL`再配置がPLT（Procedure Linkage Table）エントリを呼び出す際にも使用できるという認識の修正も含まれています。これは、動的リンクされたライブラリの関数呼び出しを正確に処理するために不可欠です。

さらに、内部的な再配置タイプ`D_PLT32`を`D_CALL`に統合するリファクタリングは、リンカのコードベースを簡素化し、保守性を向上させることを目的としています。これは、GoのIssue #4006に関連する修正の一環として実施されました。

## 前提知識の解説

### ARM再配置タイプ

*   **再配置 (Relocation)**: コンパイル時にアドレスが確定しないシンボル（関数や変数など）について、リンカが最終的な実行可能ファイルや共有ライブラリを生成する際に、正しいメモリアドレスを埋め込む処理です。
*   **`R_ARM_PC24`**: ARMアーキテクチャにおける再配置タイプの一つで、主に`B` (Branch) や`BL` (Branch with Link) といった分岐命令のターゲットアドレスを解決するために使用されます。PC（プログラムカウンタ）からの相対オフセットを24ビットで表現し、約±32MBの範囲をカバーします。現代のARM EABI（Embedded Application Binary Interface）では、`R_ARM_CALL`や`R_ARM_JUMP24`に置き換えられ、非推奨とされています。
*   **`R_ARM_JUMP24`**: `R_ARM_PC24`と同様に、ARMの分岐命令のターゲットアドレスを解決するために使用されます。特にジャンプ命令に特化しており、リンカがターゲットアドレスを決定する際に利用します。`R_ARM_CALL`と密接に関連しており、しばしば同様に扱われます。
*   **`R_ARM_CALL`**: ARM EABIで導入された再配置タイプで、関数呼び出し（`BL`命令など）のターゲットアドレスを解決するために使用されます。`R_ARM_PC24`の代替として推奨されており、リンカの処理を簡素化します。
*   **`R_ARM_PLT32`**: PLT（Procedure Linkage Table）エントリへの32ビットPC相対アドレスを埋め込むための再配置タイプです。動的リンクにおいて、共有ライブラリ内の関数を呼び出す際に使用されます。

### Procedure Linkage Table (PLT) と Global Offset Table (GOT)

動的リンクされたプログラムが共有ライブラリ内の関数を呼び出す際に、その関数の実際のメモリアドレスはコンパイル時には不明です。これを解決するために、PLTとGOTという2つの重要なデータ構造が使用されます。

*   **Procedure Linkage Table (PLT)**: プログラムが共有ライブラリ内の関数を呼び出す際の中継地点となるテーブルです。初めて関数が呼び出される際には、PLTエントリが動的リンカを呼び出し、関数の実際のメモリアドレスを解決します。
*   **Global Offset Table (GOT)**: 共有ライブラリ内の関数やデータの実際のメモリアドレスが格納されるテーブルです。PLTはGOTを参照して、解決された関数のアドレスを取得します。一度アドレスが解決されると、その情報はGOTに格納され、以降の呼び出しでは動的リンカを介さずに直接関数にジャンプできるようになります（遅延バインディング）。

### Goリンカ (`cmd/ld`, `cmd/5l`)

*   **`cmd/ld`**: Go言語のメインリンカであり、Goのソースコードから実行可能バイナリを生成する最終段階を担います。Goのビルドプロセスにおいて、コンパイラが生成したオブジェクトファイルを結合し、最終的な実行ファイルを生成します。
*   **`cmd/5l`**: 過去のGoツールチェインにおいて、ARMアーキテクチャ（`5`はARMを指す）に特化したリンカでした。Goのバージョンアップに伴い、現在は`cmd/ld`に統合され、ユーザーが直接`5l`を呼び出すことはありませんが、内部的にはARMアーキテクチャ固有のリンキングロジックが`cmd/ld`内に存在します。

## 技術的詳細

このコミットは、GoリンカがARMアーキテクチャの再配置をより正確かつ効率的に処理するための複数の変更を導入しています。

1.  **`R_ARM_PC24`と`R_ARM_JUMP24`のサポート追加**:
    *   `src/cmd/ld/elf.h`に`R_ARM_JUMP24`の定義（値29）が追加され、`R_ARM_COUNT`（定義されている再配置タイプの総数）が更新されました。
    *   `src/cmd/ld/ldelf.c`の`reltype`関数に、`R_ARM_PC24`と`R_ARM_JUMP24`のケースが追加され、これらの再配置タイプがリンカによって認識されるようになりました。
    *   `src/cmd/5l/asm.c`の`adddynrel`関数において、`R_ARM_PC24`と`R_ARM_JUMP24`の再配置が`D_CALL`タイプとして処理されるようになりました。これにより、これらの再配置が動的リンクされたシンボル（共有ライブラリの関数など）を参照する場合、PLTエントリを介して解決されるようになります。

2.  **`R_ARM_CALL`の挙動修正とPLTエントリ呼び出しへの対応**:
    *   以前は`R_ARM_CALL`がPLTエントリを呼び出す際に適切に処理されていなかった可能性があります。このコミットにより、`src/cmd/5l/asm.c`の`adddynrel`関数内の`R_ARM_CALL`のケースが修正され、ターゲットが動的インポートされたシンボル（`targ->dynimpname != nil`）であり、かつ動的にエクスポートされていない場合（`!targ->dynexport`）に、`addpltsym`を呼び出してPLTエントリを追加し、`r->sym`を`.plt`シンボルに設定するようになりました。これにより、`R_ARM_CALL`がPLTエントリを介して正しく解決されるようになります。

3.  **`D_PLT32`から`D_CALL`へのリファクタリング**:
    *   `src/cmd/5l/5.out.h`において、`D_PLT32`の定義が削除され、`D_CALL`の定義が`R_ARM_PLT32/R_ARM_CALL/R_ARM_JUMP24`をカバーするように変更されました。これは、`D_PLT32`と`D_CALL`が本質的に同じ目的（分岐命令の解決）を持つため、これらを単一の内部再配置タイプ`D_CALL`に統合することで、リンカの内部ロジックを簡素化することを目的としています。
    *   `src/cmd/5l/asm.c`の`adddynrel`関数では、`R_ARM_PLT32`のケースが`r->type = D_PLT32;`から`r->type = D_CALL;`に変更されました。
    *   `src/cmd/5l/asm.c`の`archreloc`関数では、`D_PLT32`のケースが削除され、`D_CALL`のケースが`R_ARM_PLT32`と`R_ARM_CALL`の両方のロジックを処理するように統合されました。これにより、リンカは`D_CALL`タイプを使用して、これらの異なるARM再配置タイプに対応する分岐命令のオフセットを計算できるようになります。

これらの変更により、GoリンカはARMアーキテクチャにおけるより広範な再配置シナリオをサポートし、動的リンクされたバイナリの生成における堅牢性と正確性を向上させました。

## コアとなるコードの変更箇所

このコミットによる主要なコード変更は以下の4つのファイルにわたります。

1.  **`src/cmd/5l/5.out.h`**:
    *   `#define D_PLT32 (D_NONE+46)` の行が削除されました。
    *   `#define D_CALL (D_NONE+47)` の行が `#define D_CALL (D_NONE+46) // R_ARM_PLT32/R_ARM_CALL/R_ARM_JUMP24, bl xxxxx or b yyyyy` に変更されました。これにより、`D_CALL`が`D_PLT32`の役割も兼ねるようになりました。

2.  **`src/cmd/5l/asm.c`**:
    *   `adddynrel`関数内で、`case 256 + R_ARM_PLT32:` の処理が `r->type = D_PLT32;` から `r->type = D_CALL;` に変更されました。
    *   `case 256 + R_ARM_CALL:` の処理に、動的インポートされたシンボルに対するPLTエントリの追加ロジックが追加されました。
    *   `case 256 + R_ARM_PC24:` と `case 256 + R_ARM_JUMP24:` の新しいケースが追加され、これらも`D_CALL`タイプとして処理され、動的インポートされたシンボルに対してPLTエントリを追加するロジックが組み込まれました。
    *   `archreloc`関数内で、`case D_PLT32:` のブロックが削除されました。
    *   `case D_CALL:` のブロックが修正され、`D_PLT32`のロジックも含むように統合されました。

3.  **`src/cmd/ld/elf.h`**:
    *   `#define R_ARM_JUMP24 29` の行が追加されました。
    *   `#define R_ARM_COUNT 33` の行が `#define R_ARM_COUNT 37` に変更され、新しい再配置タイプがカウントに含まれるようになりました。

4.  **`src/cmd/ld/ldelf.c`**:
    *   `reltype`関数内で、`case R('5', R_ARM_PC24):` と `case R('5', R_ARM_JUMP24):` のケースが追加されました。

## コアとなるコードの解説

このコミットの核となる変更は、GoリンカがARMの再配置をどのように解釈し、処理するかという内部ロジックの更新にあります。

*   **`src/cmd/5l/5.out.h`の変更**: これはリンカが使用する内部的な再配置タイプの定義ファイルです。`D_PLT32`が削除され、`D_CALL`に統合されたことで、リンカはPLT関連の再配置と一般的な関数呼び出しの再配置を同じ内部タイプで扱うようになります。これにより、リンカのコードがより統一され、理解しやすくなります。

*   **`src/cmd/5l/asm.c`の変更**: このファイルはARMアセンブリの再配置処理の大部分を担っています。
    *   `adddynrel`関数は、ELFオブジェクトファイルから読み取られた再配置エントリをGoリンカの内部表現に変換する役割を持っています。`R_ARM_PLT32`、`R_ARM_CALL`、そして新しく追加された`R_ARM_PC24`と`R_ARM_JUMP24`の各ケースで、`r->type`が`D_CALL`に設定されるようになりました。これは、これらのARM再配置がすべてGoリンカの内部では「呼び出し」または「ジャンプ」に関連する再配置として扱われることを意味します。特に、動的インポートされたシンボル（共有ライブラリの関数など）の場合、`addpltsym`を呼び出してPLTエントリを生成し、`r->sym`を`.plt`シンボルに設定することで、遅延バインディングをサポートします。
    *   `archreloc`関数は、Goリンカの内部再配置タイプに基づいて、実際の命令の値を計算し、パッチを適用する役割を担います。`D_PLT32`のケースが削除され、そのロジックが`D_CALL`のケースに統合されたことで、`D_CALL`はPLTを介した呼び出しと直接的な呼び出しの両方に対応できるようになりました。`braddoff`関数を使用して、PC相対オフセットを正確に計算し、分岐命令のオペランドに埋め込みます。

*   **`src/cmd/ld/elf.h`と`src/cmd/ld/ldelf.c`の変更**: これらのファイルは、ELF（Executable and Linkable Format）のヘッダ定義と、ELF固有のリンキング処理に関連しています。`R_ARM_JUMP24`の追加と`R_ARM_COUNT`の更新は、リンカがこの新しいARM再配置タイプを認識し、処理できるようにするための基本的なステップです。`reltype`関数にこれらの新しい再配置タイプが追加されたことで、リンカはELFファイルからこれらの再配置情報を正しく抽出し、内部処理に渡すことができるようになります。

これらの変更は、GoリンカがARMアーキテクチャの複雑な再配置メカニズムをより完全にサポートし、生成されるバイナリの互換性と信頼性を向上させる上で不可欠です。

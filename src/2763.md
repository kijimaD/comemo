# [インデックス 2763] ファイルの概要

このコミットは、Go言語の初期の評価器（`usr/austin/eval`パッケージ）において、配列型とインデックス式の実装を追加するものです。具体的には、配列の型定義、配列値の表現、そして配列要素へのアクセス（インデックス操作）を可能にするためのコンパイラロジックが導入されています。また、ポインタ型の要素アクセス方法の統一、式評価器のコード生成ロジックの改善、および不要な診断関数の削除といったクリーンアップも含まれています。

## 元コミット内容

このコミットの目的は、配列型とインデックス式を実装することです。
それに加えて、いくつかのクリーンアップ作業も行われています。具体的には、`PtrType`の`Elem()`メソッドが単なる`Elem`フィールドとなり、`ArrayType`との整合性が取られました。また、コード生成器（generators）がオペランドの型ではなく、結果の型に基づいて処理を分岐するように変更されました。さらに、使用されていない`diag`関数が削除されました。

## 変更の背景

Go言語は2009年当時、まだ開発の初期段階にありました。このコミットは、言語の基本的なデータ構造の一つである「配列」を、その評価器（`eval`パッケージ）が正しく認識し、操作できるようにするための基盤を構築するものです。配列はプログラミングにおいて非常に基本的なデータ構造であり、そのサポートは言語の表現力を高める上で不可欠です。

具体的には、以下の機能が求められていました。
1.  **配列型の定義**: `[N]T` のような固定長配列の型を評価器が扱えるようにする。
2.  **インデックス式**: `a[i]` のような構文で配列の要素にアクセスできるようにする。
3.  **型チェック**: インデックスが配列の範囲内にあるか、インデックスの型が適切かなどを検証する。
4.  **値の評価**: 実行時に配列の要素の値を正しく取得・設定できるようにする。

また、既存のコードベースにおける型システムの一貫性を向上させるためのリファクタリングも同時に行われました。特に、ポインタ型と配列型で要素型へのアクセス方法を統一することは、将来的な拡張性やコードの保守性にとって重要です。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語（または一般的なコンパイラ/インタプリタの概念）に関する知識が役立ちます。

*   **抽象構文木 (AST: Abstract Syntax Tree)**: プログラムのソースコードを解析して得られる、構文構造を表現する木構造のデータ表現です。Go言語の`go/ast`パッケージがこれに該当します。このコミットでは、`ast.IndexExpr`などのASTノードを処理しています。
*   **型システム**: プログラミング言語における型の定義、型チェックのルール、型の互換性などを司る仕組みです。Goの`eval`パッケージでは、`Type`インターフェースとその実装（`PtrType`, `ArrayType`など）が型システムを構成しています。
*   **評価器 (Evaluator/Interpreter)**: ソースコードやASTを直接実行して結果を生成するプログラムです。このコミットの対象である`usr/austin/eval`パッケージは、Go言語の式を評価するための初期のインタプリタ的な役割を担っていました。
*   **`token.Position`**: ソースコード内の位置情報（ファイル名、行番号、列番号）を表すGoの標準ライブラリの型です。エラーメッセージの出力などに利用されます。
*   **`bignum`パッケージ**: 任意精度整数や有理数を扱うためのライブラリです。Go言語の初期の型システムでは、`idealIntType`や`idealFloatType`といった「理想的な」数値型が存在し、これらは`bignum`で表現されていました。これにより、コンパイル時の定数評価などで精度を失うことなく計算が可能になります。
*   **`Value`インターフェース**: 評価器内で様々な型の値を統一的に扱うためのインターフェースです。`BoolValue`, `IntValue`, `ArrayValue`などがこれの実装となります。
*   **`exprCompiler`**: 式をコンパイル（評価可能な形式に変換）するための主要な構造体です。ASTを走査し、各式の型チェックと評価ロジックの生成を行います。
*   **`Frame`**: 実行時の変数のスコープや値を保持する環境です。

## 技術的詳細

このコミットの技術的詳細は、主に以下の3つの側面に分けられます。

### 1. 配列型の導入 (`type.go`, `decls.go`, `value.go`)

*   **`ArrayType`構造体**: `type.go`に`ArrayType`が導入されました。これは`Len int64`（配列の長さ）と`Elem Type`（要素の型）を持ちます。`NewArrayType`ファクトリ関数は、同じ長さと要素型を持つ`ArrayType`インスタンスを再利用（インターン）することで、メモリ効率を高めています。
*   **`ArrayValue`インターフェース**: `decls.go`に`ArrayValue`インターフェースが定義されました。これは`Value`インターフェースを埋め込み、`Get() ArrayValue`と`Elem(i int64) Value`メソッドを持ちます。`Elem(i int64)`は指定されたインデックスの要素の`Value`を返します。
*   **`arrayV`実装**: `value.go`に`arrayV`型（`[]Value`のスライス）が導入され、`ArrayValue`インターフェースを実装しています。これにより、実行時にGoのスライスを基盤として配列値を表現できるようになりました。

### 2. インデックス式の評価ロジック (`expr.go`)

*   **`exprCompiler`の拡張**: `exprCompiler`に`evalArray func(f *Frame) ArrayValue`フィールドが追加され、式が配列値を評価できるようになりました。また、`asArray()`ヘルパーメソッドも追加されています。
*   **`DoIndexExpr`の実装**: `ast.IndexExpr`（`a[i]`のようなインデックス式）を処理する`DoIndexExpr`メソッドが大幅に拡張されました。
    *   **ポインタの自動逆参照**: `*PtrType`が`*ArrayType`を指している場合、自動的に逆参照して配列として扱います。これはGo言語のポインタと配列の相互運用性（例: `*[]int`を`[]int`のように扱う）の初期実装を示唆しています。
    *   **型チェック**: インデックス対象が`ArrayType`、`stringType`であることを確認します。`SliceType`や`MapType`へのインデックスは将来の課題としてコメントアウトされています。
    *   **インデックスの型チェックと変換**: インデックスが整数型（`idealIntType`, `uintType`, `intType`）であることを確認し、必要に応じて`IntType`に変換します。`idealIntType`の場合、インデックスが負でないこと、および配列の長さを超えないことをチェックする境界チェック（bounds check）も行われます。
    *   **コード生成**: `genIndexArray`を呼び出して、実行時に配列要素にアクセスするための評価関数（`evalAddr`）を生成します。`evalAddr`は、配列値とインデックス値を取得し、`ArrayValue.Elem(i)`を呼び出して結果の`Value`を返します。

### 3. コード生成器の統一とクリーンアップ (`expr.go`, `type.go`, `util.go`)

*   **ジェネレータの変更**: `genStarOp`, `genUnaryOpNeg`, `genUnaryOpNot`, `genUnaryOpXor`, およびすべての二項演算子ジェネレータ（`genBinOpAdd`など）が、オペランドの型ではなく、**結果の型**（`a.t.literal()`）に基づいて処理を分岐するように変更されました。これにより、コード生成ロジックが一貫性を持ち、より柔軟になりました。例えば、`+`演算子が`uintType`の結果を生成する場合、`a.evalUint`を設定するといった形です。
*   **`PtrType.Elem`の変更**: `PtrType`の`elem`フィールドが`Elem`にリネームされ、`Elem()`メソッドが削除されました。これにより、ポインタの要素型へのアクセスが`ptr.Elem`というフィールドアクセスに統一され、`ArrayType.Elem`との整合性が取られました。
*   **`diag`関数の削除**: `util.go`にあった`diag`関数が削除されました。これはおそらく、より堅牢なエラー報告メカニズム（例: `log.Crashf`）が導入されたため、あるいは単に未使用になったためと考えられます。

### `usr/austin/eval/expr.go`
`exprCompiler`に`evalArray`フィールドと`genIndexArray`の宣言を追加。
`DoIndexExpr`メソッドの大幅な変更と実装。
ジェネレータ関数（`genStarOp`など）が結果型で分岐するように変更。
```go

	// ...
	evalArray func(f *Frame) ArrayValue;
	// ...
}

// genIndexArray declaration

// DoIndexExpr implementation (抜粋)
func (a *exprCompiler) DoIndexExpr(x *ast.IndexExpr) {
	// ...
	// Type check object (ポインタの自動逆参照、配列/文字列の型チェック)
	// Type check index (インデックスの型チェック、境界チェック)
	// Compile (genIndexArrayの呼び出し、evalAddrの設定)
	// ...
}

// genIndexArray implementation (抜粋)
func (a *exprCompiler) genIndexArray(l *exprCompiler, r *exprCompiler) {
	lf := l.asArray();
	rf := r.asInt();
	switch _ := a.t.literal().(type) { // 結果型で分岐
	case *boolType:
		a.evalBool = func(f *Frame) bool { return lf(f).Elem(rf(f)).(BoolValue).Get() };
	// ... 他の型に対する evalXxx の設定
	}
}

// genStarOp (抜粋)
func (a *exprCompiler) genStarOp(v *exprCompiler) {
	vf := v.asPtr();
	switch _ := a.t.literal().(type) { // 結果型で分岐
	case *boolType:
		a.evalBool = func(f *Frame) bool { return vf(f).(BoolValue).Get() };
	// ... 他の型に対する evalXxx の設定
	case *ArrayType: // ArrayTypeの追加
		a.evalArray = func(f *Frame) ArrayValue { return vf(f).(ArrayValue).Get() };
	// ...
	}
}
```

## コアとなるコードの解説

このコミットの核となるのは、Go言語の評価器が配列をどのように扱い、インデックス操作をどのように実行するかを定義した部分です。

1.  **型システムへの配列の統合**:
    *   `type.go`で`ArrayType`が導入されたことで、評価器は`[N]T`のような固定長配列の型を内部的に表現できるようになりました。`Len`と`Elem`フィールドは、それぞれ配列の長さと要素の型を保持し、型チェックやコード生成の際に利用されます。`NewArrayType`によるインターンは、同じ型の配列が複数定義されても、メモリ上に一つの型インスタンスしか存在しないようにするための最適化です。
    *   `decls.go`の`ArrayValue`インターフェースと、`value.go`の`arrayV`実装は、実行時に配列の値を表現するための具体的なメカニズムを提供します。`Elem(i int64) Value`メソッドは、インデックス`i`に対応する要素の`Value`を返すことで、配列要素へのアクセスを抽象化しています。

2.  **インデックス式のコンパイルと評価**:
    *   `expr.go`の`DoIndexExpr`メソッドは、`a[i]`のようなASTノードを処理する中心的なロジックです。
        *   まず、インデックス対象（`a`）とインデックス（`i`）の式を個別にコンパイルします。
        *   インデックス対象がポインタ型で、その指す先が配列型である場合、自動的にポインタを逆参照して配列として扱います。これはGo言語の柔軟な型システムの一端を初期段階で実装したものです。
        *   インデックス対象の型が`ArrayType`または`stringType`であることを確認します。文字列へのインデックスはバイトアクセスとして扱われます。
        *   インデックスの型が整数型であることを検証し、`idealIntType`の場合はコンパイル時に境界チェックを行います。これにより、実行時エラーを減らすことができます。
        *   最終的に、`genIndexArray`を呼び出して、実行時に配列要素を評価するための関数を生成します。この関数は、配列値とインデックス値を受け取り、`ArrayValue.Elem(i)`を呼び出すことで、指定された要素の`Value`を返します。この`Value`は、さらにその型に応じた`BoolValue`、`IntValue`などにキャストされて利用されます。

3.  **ジェネレータの統一**:
    *   `expr.go`内の多くのジェネレータ関数（`genStarOp`, `genUnaryOpNeg`, `genBinOpAdd`など）が、オペランドの型ではなく、**結果の型**に基づいて評価関数を設定するように変更されました。これは、例えば`+`演算子が`int`型同士の加算結果として`int`を返す場合、`a.evalInt`を設定するといった、より直感的で一貫性のあるコード生成ロジックを可能にします。これにより、コンパイラの内部構造が整理され、将来的な型推論や型変換のロジックを実装しやすくなります。

これらの変更により、Go言語の評価器は配列を基本的なデータ構造として完全にサポートし、インデックス式を通じてその要素にアクセスできるようになりました。これは、より複雑なデータ構造やアルゴリズムをGo言語で表現するための重要な一歩です。

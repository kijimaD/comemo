# [インデックス 27757] ファイルの概要

このコミットは、GoコンパイラのSSA (Static Single Assignment) バックエンドにおけるロード結合最適化の安全性向上を目的としています。具体的には、複数のバイトロードをより大きなワードロードに結合する際に、結合されるロードが他の場所で利用されていないことを保証するための `x.Uses==1` 条件を追加します。これにより、データ競合の状況下でロードされた値の一貫性が損なわれる可能性を防ぎます。また、この条件を確実に機能させるために、不要なコピー操作を積極的に除去するコードが追加されています。

## 変更の背景

GoコンパイラのSSAバックエンドでは、パフォーマンス向上のために様々な最適化が行われます。その一つに「ロード結合 (Load Combining)」があります。これは、隣接する複数の小さなロード操作（例: `b[0]` と `b[1]` のバイトロード）を、より大きな単一のロード操作（例: `uint16` のワードロード）にまとめることで、メモリアクセス効率を高める最適化です。

しかし、この最適化には潜在的な問題がありました。もし、結合される個々のロード操作が、結合される以外の場所でも使用されている場合、コンパイラがそれらのロードを単一の大きなロードに置き換えてしまうと、元の個々のロードが持つべきセマンティクスが失われる可能性があります。特に、並行処理（データ競合）の状況下では、元の個々のロードが異なるタイミングで実行されることで異なる値を読み取る可能性があったにもかかわらず、結合された単一のロードでは常に一貫した値しか読み取れなくなるため、プログラムの動作が変わってしまう危険性がありました。

このコミットは、このようなデータ競合による不整合を防ぐために、ロード結合を行う際に「結合される個々のロードが、その結合操作以外では使用されていないこと」を厳密にチェックするメカニズムを導入しました。

## 前提知識の解説

### Goコンパイラ (cmd/compile)
Go言語の公式コンパイラであり、Goソースコードを機械語に変換する役割を担います。`cmd/compile` は、フロントエンド（構文解析、型チェックなど）とバックエンド（最適化、コード生成など）に分かれています。このコミットはバックエンドの最適化フェーズに関するものです。

### SSA (Static Single Assignment) 形式
SSA形式は、コンパイラの最適化段階でプログラムの中間表現として広く用いられる形式です。この形式では、各変数が一度だけ代入されるという特性を持ちます。これにより、データの流れが明確になり、最適化が容易になります。GoコンパイラのバックエンドもSSA形式を採用しており、`src/cmd/compile/internal/ssa` ディレクトリ以下にその実装があります。

### ロード結合 (Load Combining) 最適化
メモリからデータを読み込む操作（ロード）を最適化する手法の一つです。例えば、`byte` 型の `b[0]` と `b[1]` を別々に読み込む代わりに、`uint16` 型として `b[0]` から2バイトを一度に読み込むことで、メモリバスの利用効率を高め、実行速度を向上させます。

### `Uses` カウント (SSA値の使用回数)
SSA形式の各値（`Value`）は、プログラム内で何回使用されているかを示す `Uses` カウンタを持っています。コンパイラは、このカウンタを利用して、ある値が不要になったかどうか（`Uses == 0`）や、単一の場所でのみ使用されているかどうか（`Uses == 1`）を判断し、様々な最適化の条件として利用します。

### データ競合 (Data Race)
複数のゴルーチンが同時に同じメモリ位置にアクセスし、少なくとも1つのアクセスが書き込みであり、かつそれらのアクセスが同期メカニズムによって順序付けされていない場合に発生する競合状態です。データ競合が発生すると、プログラムの動作が予測不能になったり、一貫性のない値が読み取られたりする可能性があります。

### コピー除去 (Copy Elimination)
コンパイラ最適化の一種で、ある値が別の値に単純にコピーされ、そのコピーされた値が元の値と全く同じように使用される場合に、そのコピー操作を削除するものです。これにより、不要な命令が削減され、コードが効率化されます。このコミットでは、`x.Uses==1` 条件を正確に機能させるために、"dead copy"（実質的に使われていないコピー）を積極的に除去する重要性が強調されています。

## 技術的詳細

このコミットの核心は、ロード結合最適化の適用条件に `x.Uses == 1` という制約を追加したことです。

GoコンパイラのSSAバックエンドでは、`src/cmd/compile/internal/ssa/gen/AMD64.rules` のようなファイルに、特定のSSA操作パターンをより効率的な機械語命令パターンに書き換えるためのルールが記述されています。これらのルールは、バイト単位のロード操作（`MOVBload` や `MOVBloadidx1`）を結合して、より大きなワード単位のロード操作（`MOVWload`, `MOVLload`, `MOVQload`）に変換するパターンを含んでいます。

変更前は、これらのロード結合ルールは `mergePoint` の条件のみをチェックしていました。`mergePoint` は、結合される複数のロード操作が同じメモリ位置から読み込まれていることを保証するためのものです。しかし、これだけでは、個々のバイトロードが結合操作以外の場所でも使用されているケースを捕捉できませんでした。

このコミットでは、各バイトロード操作 `x0, x1, ... x7` に対して、`x0.Uses == 1 && x1.Uses == 1 && ...` という条件を追加しました。この条件は、それぞれのバイトロードが、まさにこのロード結合操作のためだけに生成され、他のどのSSA値もそのバイトロードの結果を使用していないことを保証します。これにより、もし結合されるバイトロードが他の場所でも使われている場合、そのロードは結合されず、元の個別のロード操作が維持されます。これにより、データ競合の状況下でも、個々のロードが異なる値を読み取る可能性が保持され、プログラムのセマンティクスが正しく維持されます。

この `x.Uses == 1` 条件を信頼性高く機能させるためには、SSA形式の中間表現において、不要なコピー操作が速やかに除去されている必要があります。もし、ある値が実質的に使われていないにもかかわらず、その値への「死んだコピー (dead copy)」が存在し、そのコピーが `Uses` カウントを1以上にしてしまうと、`x.Uses == 1` 条件が誤って偽となり、ロード結合最適化が適用されなくなってしまいます。

そのため、`src/cmd/compile/internal/ssa/rewrite.go` に、より積極的なコピー除去ロジックが追加されました。この新しいロジックは、`OpCopy` 操作の入力が不要になった場合に、そのコピー操作自体を `OpInvalid` とマークし、その引数も再帰的に処理することで、SSAグラフから「幽霊のような死んだコピー (phantom "dead copy")」を迅速にクリーンアップします。これにより、`Uses` カウントが正確に反映され、ロード結合の `x.Uses == 1` 条件が意図通りに機能するようになります。

`src/cmd/compile/internal/gc/testdata/dupLoad.go` に追加されたテストケースは、この問題を示す具体的なシナリオを再現しています。`read` 関数内で `b[0]` が一度だけロードされ、その値 `v` が2つの異なる `uint16` 値の生成に使われます。メイン関数では、2つのゴルーチンが `b` の内容を並行して変更し、`read` 関数を呼び出します。もし `b[0]` のロードが不適切に結合されたり、`v` の使用が正しく追跡されなかったりすると、`x` と `y` の下位バイトが異なる値になる可能性があり、`panic` が発生します。このテストは、コミットによって導入された変更が、このような競合条件下での値の一貫性を保証していることを検証します。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` の変更

このファイルでは、AMD64アーキテクチャ向けのSSA最適化ルールが定義されています。変更は、バイトロードをワードロード、ダブルワードロード、クアッドワードロードに結合するパターンに集中しています。

例として、`ORW` (OR Word) オペレーションで2つのバイトロードを結合して `MOVWload` (Move Word Load) にするルールを見てみましょう。

変更前:
```
(ORW x0:(MOVBload [i] {s} p mem)
    (SHLWconst [8] x1:(MOVBload [i+1] {s} p mem))) && mergePoint(b,x0,x1) != nil -> @mergePoint(b,x0,x1) (MOVWload [i] {s} p mem)
```

変更後:
```
(ORW x0:(MOVBload [i] {s} p mem)
    (SHLWconst [8] x1:(MOVBload [i+1] {s} p mem))) && x0.Uses == 1 && x1.Uses == 1 && mergePoint(b,x0,x1) != nil -> @mergePoint(b,x0,x1) (MOVWload [i] {s} p mem)
```
`x0.Uses == 1 && x1.Uses == 1` という条件が追加されています。これは、`x0` と `x1` という2つのバイトロードが、この `ORW` オペレーション（つまり、このロード結合）以外では使用されていないことを保証します。これにより、個々のバイトロードが他の場所で利用されている場合に、誤って結合されてしまうことを防ぎます。同様の変更が、`ORL` (OR Long) や `ORQ` (OR Quad) を用いたより大きなロード結合ルールにも適用されています。

### `src/cmd/compile/internal/ssa/rewrite.go` の変更

このファイルには、SSA形式の値を書き換えるための汎用的なロジックが含まれています。特に `applyRewrite` 関数内で、新しいコピー除去ロジックが追加されました。

```go
				// Eliminate copy inputs.
				// If any copy input becomes unused, mark it
				// as invalid and discard its argument. Repeat
				// recursively on the discarded argument.
				// This phase helps remove phantom "dead copy" uses
				// of a value so that a x.Uses==1 rule condition
				// fires reliably.
				for i, a := range v.Args {
					if a.Op != OpCopy {
						continue
					}
					x := a.Args[0]
					// Rewriting can generate OpCopy loops.
					// They are harmless (see removePredecessor),
					// but take care to stop if we find a cycle.
					slow := x // advances every other iteration
					var advance bool
					for x.Op == OpCopy {
						x = x.Args[0]
						if slow == x {
							break
						}
						if advance {
							slow = slow.Args[0]
						}
						advance = !advance
					}
					v.SetArg(i, x)
					change = true
					for a.Uses == 0 {
						b := a.Args[0]
						a.reset(OpInvalid)
						a = b
					}
				}
```
このコードブロックは、`v` の引数 `a` が `OpCopy` 操作である場合に、そのコピーを最適化しようとします。
1.  `a` が `OpCopy` であれば、そのコピー元 `x` を取得します。
2.  `OpCopy` の連鎖（`x = copy(y)`, `y = copy(z)` のような場合）を辿り、最終的な非コピー元を見つけます。この際、無限ループを防ぐためにフロイドのサイクル検出アルゴリズム（`slow` と `advance` を使った部分）に似た手法が用いられています。
3.  `v` の引数 `a` を、最終的に見つかった非コピー元 `x` に直接置き換えます (`v.SetArg(i, x)`)。これにより、中間にあった `OpCopy` は不要になります。
4.  `for a.Uses == 0` ループでは、置き換えによって `Uses` カウントが0になった `OpCopy` 値 `a` を `OpInvalid` とマークし、その引数も再帰的に処理します。これにより、SSAグラフから不要になった `OpCopy` 値が完全に除去され、`Uses` カウントが正確に保たれます。

この積極的なコピー除去は、`AMD64.rules` で追加された `x.Uses == 1` 条件が、実際にその値が単一の場所でのみ使用されていることを正確に反映するために不可欠です。

### `src/cmd/compile/internal/gc/testdata/dupLoad.go` のテストケース

このテストは、ロード結合の安全性を検証するために設計されています。
`read` 関数は `b[0]` を一度だけロードし、その値 `v` を使って2つの `uint16` を生成します。
`main` 関数では、2つのゴルーチンが並行して動作します。
- 1つ目のゴルーチンは `b` の内容を繰り返し更新します。
- 2つ目のゴルーチンは `read(b)` を繰り返し呼び出し、返された2つの値 `x` と `y` の下位バイトが等しいことをアサートします。
もしコンパイラが `b[0]` のロードを不適切に結合したり、`v` の使用を誤って最適化したりすると、データ競合によって `x` と `y` の下位バイトが異なる値になる可能性があり、その場合 `panic` が発生します。このテストは、コミットの変更がこのシナリオで正しく機能し、一貫性を保つことを保証します。

### コピー除去 (Copy Elimination)
コンパイラ最適化の一種で、ある値が別の値に単純にコピーされ、そのコピーされた値が元の値と全く同じように使用される場合に、そのコピー操作を削除するものです。これにより、不要な命令が削減され、コードが効率化されます。このコミットでは、`x.Uses==1` 条件を正確に機能させるために、"dead copy"（実質的に使われていないコピー）を積極的に除去する重要性が強調されています。

## 技術的詳細

このコミットの核心は、ロード結合最適化の適用条件に `x.Uses == 1` という制約を追加したことです。

GoコンパイラのSSAバックエンドでは、`src/cmd/compile/internal/ssa/gen/AMD64.rules` のようなファイルに、特定のSSA操作パターンをより効率的な機械語命令パターンに書き換えるためのルールが記述されています。これらのルールは、バイト単位のロード操作（`MOVBload` や `MOVBloadidx1`）を結合して、より大きなワード単位のロード操作（`MOVWload`, `MOVLload`, `MOVQload`）に変換するパターンを含んでいます。

変更前は、これらのロード結合ルールは `mergePoint` の条件のみをチェックしていました。`mergePoint` は、結合される複数のロード操作が同じメモリ位置から読み込まれていることを保証するためのものです。しかし、これだけでは、個々のバイトロードが結合操作以外の場所でも使用されているケースを捕捉できませんでした。

このコミットでは、各バイトロード操作 `x0, x1, ... x7` に対して、`x0.Uses == 1 && x1.Uses == 1 && ...` という条件を追加しました。この条件は、それぞれのバイトロードが、まさにこのロード結合操作のためだけに生成され、他のどのSSA値もそのバイトロードの結果を使用していないことを保証します。これにより、もし結合されるバイトロードが他の場所でも使われている場合、そのロードは結合されず、元の個別のロード操作が維持されます。これにより、データ競合の状況下でも、個々のロードが異なる値を読み取る可能性が保持され、プログラムのセマンティクスが正しく維持されます。

この `x.Uses == 1` 条件を信頼性高く機能させるためには、SSA形式の中間表現において、不要なコピー操作が速やかに除去されている必要があります。もし、ある値が実質的に使われていないにもかかわらず、その値への「死んだコピー (dead copy)」が存在し、そのコピーが `Uses` カウントを1以上にしてしまうと、`x.Uses == 1` 条件が誤って偽となり、ロード結合最適化が適用されなくなってしまいます。

そのため、`src/cmd/compile/internal/ssa/rewrite.go` に、より積極的なコピー除去ロジックが追加されました。この新しいロジックは、`OpCopy` 操作の入力が不要になった場合に、そのコピー操作自体を `OpInvalid` とマークし、その引数も再帰的に処理することで、SSAグラフから「幽霊のような死んだコピー (phantom "dead copy")」を迅速にクリーンアップします。これにより、`Uses` カウントが正確に反映され、ロード結合の `x.Uses == 1` 条件が意図通りに機能するようになります。

`src/cmd/compile/internal/gc/testdata/dupLoad.go` に追加されたテストケースは、この問題を示す具体的なシナリオを再現しています。`read` 関数内で `b[0]` が一度だけロードされ、その値 `v` が2つの異なる `uint16` 値の生成に使われます。メイン関数では、2つのゴルーチンが `b` の内容を並行して変更し、`read` 関数を呼び出します。もし `b[0]` のロードが不適切に結合されたり、`v` の使用が正しく追跡されなかったりすると、`x` と `y` の下位バイトが異なる値になる可能性があり、`panic` が発生します。このテストは、コミットによって導入された変更が、このような競合条件下での値の一貫性を保証していることを検証します。

## コアとなるコードの解説

### `src/cmd/compile/internal/ssa/gen/AMD64.rules` の変更

このファイルでは、AMD64アーキテクチャ向けのSSA最適化ルールが定義されています。変更は、バイトロードをワードロード、ダブルワードロード、クアッドワードロードに結合するパターンに集中しています。

例として、`ORW` (OR Word) オペレーションで2つのバイトロードを結合して `MOVWload` (Move Word Load) にするルールを見てみましょう。

変更前:
```
(ORW x0:(MOVBload [i] {s} p mem)
    (SHLWconst [8] x1:(MOVBload [i+1] {s} p mem))) && mergePoint(b,x0,x1) != nil -> @mergePoint(b,x0,x1) (MOVWload [i] {s} p mem)
```

変更後:
```
(ORW x0:(MOVBload [i] {s} p mem)
    (SHLWconst [8] x1:(MOVBload [i+1] {s} p mem))) && x0.Uses == 1 && x1.Uses == 1 && mergePoint(b,x0,x1) != nil -> @mergePoint(b,x0,x1) (MOVWload [i] {s} p mem)
```
`x0.Uses == 1 && x1.Uses == 1` という条件が追加されています。これは、`x0` と `x1` という2つのバイトロードが、この `ORW` オペレーション（つまり、このロード結合）以外では使用されていないことを保証します。これにより、個々のバイトロードが他の場所で利用されている場合に、誤って結合されてしまうことを防ぎます。同様の変更が、`ORL` (OR Long) や `ORQ` (OR Quad) を用いたより大きなロード結合ルールにも適用されています。

### `src/cmd/compile/internal/ssa/rewrite.go` の変更

このファイルには、SSA形式の値を書き換えるための汎用的なロジックが含まれています。特に `applyRewrite` 関数内で、新しいコピー除去ロジックが追加されました。

```go
				// Eliminate copy inputs.
				// If any copy input becomes unused, mark it
				// as invalid and discard its argument. Repeat
				// recursively on the discarded argument.
				// This phase helps remove phantom "dead copy" uses
				// of a value so that a x.Uses==1 rule condition
				// fires reliably.
				for i, a := range v.Args {
					if a.Op != OpCopy {
						continue
					}
					x := a.Args[0]
					// Rewriting can generate OpCopy loops.
					// They are harmless (see removePredecessor),
					// but take care to stop if we find a cycle.
					slow := x // advances every other iteration
					var advance bool
					for x.Op == OpCopy {
						x = x.Args[0]
						if slow == x {
							break
						}
						if advance {
							slow = slow.Args[0]
						}
						advance = !advance
					}
					v.SetArg(i, x)
					change = true
					for a.Uses == 0 {
						b := a.Args[0]
						a.reset(OpInvalid)
						a = b
					}
				}
```
このコードブロックは、`v` の引数 `a` が `OpCopy` 操作である場合に、そのコピーを最適化しようとします。
1.  `a` が `OpCopy` であれば、そのコピー元 `x` を取得します。
2.  `OpCopy` の連鎖（`x = copy(y)`, `y = copy(z)` のような場合）を辿り、最終的な非コピー元を見つけます。この際、無限ループを防ぐためにフロイドのサイクル検出アルゴリズム（`slow` と `advance` を使った部分）に似た手法が用いられています。
3.  `v` の引数 `a` を、最終的に見つかった非コピー元 `x` に直接置き換えます (`v.SetArg(i, x)`)。これにより、中間にあった `OpCopy` は不要になります。
4.  `for a.Uses == 0` ループでは、置き換えによって `Uses` カウントが0になった `OpCopy` 値 `a` を `OpInvalid` とマークし、その引数も再帰的に処理します。これにより、SSAグラフから不要になった `OpCopy` 値が完全に除去され、`Uses` カウントが正確に保たれます。

この積極的なコピー除去は、`AMD64.rules` で追加された `x.Uses == 1` 条件が、実際にその値が単一の場所でのみ使用されていることを正確に反映するために不可欠です。

### `src/cmd/compile/internal/gc/testdata/dupLoad.go` のテストケース

このテストは、ロード結合の安全性を検証するために設計されています。
`read` 関数は `b[0]` を一度だけロードし、その値 `v` を使って2つの `uint16` を生成します。
`main` 関数では、2つのゴルーチンが並行して動作します。
- 1つ目のゴルーチンは `b` の内容を繰り返し更新します。
- 2つ目のゴルーチンは `read(b)` を繰り返し呼び出し、返された2つの値 `x` と `y` の下位バイトが等しいことをアサートします。
もしコンパイラが `b[0]` のロードを不適切に結合したり、`v` の使用を誤って最適化したりすると、データ競合によって `x` と `y` の下位バイトが異なる値になる可能性があり、その場合 `panic` が発生します。このテストは、コミットの変更がこのシナリオで正しく機能し、一貫性を保つことを保証します。

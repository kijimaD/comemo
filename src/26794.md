# [インデックス 26794] ファイルの概要

このコミットは、Goコンパイラのアセンブリコード生成ツール (`cmd/internal/obj`) におけるバグ修正に関するものです。具体的には、`go build -gcflags="-S"` コマンドでアセンブリコードを出力する際に、必要な中間表現 (`Prog` エントリ) が誤って破棄されてしまう問題を解決し、`-S` フラグが正しく機能するようにします。この変更には、問題が修正されたことを検証するための新しいテストケースも含まれています。

## コミット

`cmd/internal/obj`: `-S` フラグ使用時のアセンブリ生成を修正

アセンブリの逆アセンブルを出力したい場合、`Prog` エントリを破棄することはできません。

`-S` のためのテストを追加しました。

Fixes #14515

## 変更の背景

Goコンパイラには、コンパイルプロセス中に生成されるアセンブリコードを表示するための `-S` フラグ（`go build -gcflags="-S"`）があります。これは、開発者が生成された機械語を理解し、パフォーマンスの最適化やデバッグを行う上で非常に重要な機能です。

このコミット以前は、`-S` フラグが指定されているにもかかわらず、コンパイラのバックエンドの一部である `cmd/internal/obj` パッケージが、アセンブリ命令を表す中間表現である `Prog` エントリを不適切に破棄していました。`Prog` エントリが破棄されると、アセンブリコードの表示に必要な情報が失われ、結果として `-S` フラグを使用しても期待されるアセンブリ出力が得られない、または不完全な出力になるという問題が発生していました。

この問題は Issue #14515 として報告されており、このコミットはその問題を解決するために行われました。

## 前提知識の解説

*   **Goコンパイラ (`cmd/compile`)**: Go言語のソースコードを機械語に変換する公式コンパイラです。複数のステージを経てコードを処理し、最終的な実行可能ファイルを生成します。
*   **Goアセンブラ (`cmd/internal/obj`)**: `cmd/compile` の内部パッケージの一つで、コンパイラが生成した中間表現（`Prog`）を受け取り、ターゲットアーキテクチャ向けのアセンブリコードに変換する役割を担います。
*   **`-S` フラグ**: `go build -gcflags="-S"` のように `go build` コマンドと共に使用されるコンパイラフラグです。このフラグを渡すと、コンパイラは生成されたアセンブリコードを標準出力にダンプします。これは、Goプログラムがどのように機械語に変換されるかを理解するための強力なデバッグおよび分析ツールです。
*   **`Prog` エントリ**: Goコンパイラのバックエンドで使用されるデータ構造で、単一のアセンブリ命令または関連するメタデータを表します。これらの `Prog` エントリがリンクリストとして連なり、関数やプログラム全体のアセンブリコードを構成します。
*   **`Flushplist` / `flushplist` 関数**: `cmd/internal/obj` パッケージ内の関数で、`Prog` エントリのリスト（"plist"）を処理し、アセンブリコードをファイルに書き出す（またはメモリ内で処理する）役割を担います。処理後、通常はメモリを解放するために `Prog` エントリをクリアします。
*   **`ctxt.Debugasm`**: `cmd/internal/obj` パッケージ内の `Link` コンテキスト構造体の一部で、アセンブリデバッグモードが有効かどうかを示すフラグです。この値は、`-S` フラグが指定された場合に設定されます。`Debugasm` が `0` でない場合、アセンブリコードの出力が必要であることを意味します。
*   **`s.Text` / `s.Etext`**: `Prog` リストの開始 (`Text`) と終了 (`Etext`) を指すポインタです。これらのポインタを `nil` に設定することで、`Prog` エントリが参照されなくなり、ガベージコレクションの対象となるか、明示的に解放される準備が整います。

## 技術的詳細

このコミットの核心的な問題は、`cmd/internal/obj` パッケージの `Flushplist` 関数が、アセンブリコードの出力が必要な場合（つまり `-S` フラグが有効な場合）でも、`Prog` エントリを無条件に解放してしまっていた点にあります。

元の実装では、`Flushplist` は常に `flushplist(ctxt, true)` を呼び出していました。ここで渡される `true` は、`flushplist` 関数内で `Prog` エントリを処理した後に解放すべきかどうかを制御するブール値です。`true` が渡されると、`flushplist` は `s.Text = nil` および `s.Etext = nil` を実行し、`Prog` エストリへの参照をクリアしていました。

しかし、`-S` フラグが有効な場合、コンパイラはこれらの `Prog` エントリをアセンブリコードとして表示するために必要とします。エントリが解放されてしまうと、表示すべき情報が失われてしまいます。

このコミットによる修正は以下の通りです。

1.  **`Flushplist` の呼び出し変更**:
    `src/cmd/internal/obj/objfile.go` 内の `Flushplist` 関数が、`flushplist(ctxt, true)` ではなく `flushplist(ctxt, ctxt.Debugasm == 0)` を呼び出すように変更されました。
    *   `ctxt.Debugasm == 0` は、`-S` フラグが指定されていない（アセンブリデバッグモードではない）場合に `true` となります。
    *   これにより、`-S` フラグが有効な場合 (`ctxt.Debugasm != 0`) は `flushplist` に `false` が渡され、`Prog` エントリの解放が抑制されるようになります。

2.  **`flushplist` 内の条件付き解放**:
    `src/cmd/internal/obj/objfile.go` 内の `flushplist` 関数において、`s.Text = nil` と `s.Etext = nil` を実行するコードが `if freeProgs { ... }` ブロックで囲まれました。
    *   `freeProgs` は `Flushplist` から渡されるブール値です。
    *   この変更により、`freeProgs` が `false` の場合（つまり `-S` フラグが有効な場合）、`Prog` エントリは解放されずに保持されます。

3.  **テストケースの追加**:
    `src/cmd/compile/internal/gc/global_test.go` に `TestDashS` という新しいテスト関数が追加されました。
    *   このテストは、一時ディレクトリに簡単なGoプログラム（"hello world" を出力するプログラム）を作成します。
    *   `go build -gcflags="-S"` コマンドを実行し、その出力（アセンブリコード）をキャプチャします。
    *   キャプチャした出力に、`TEXT`, `FUNCDATA`, `PCDATA` といったアセンブリの擬似命令が含まれていることを確認します。これらの擬似命令は、アセンブリコードが正しく生成されていることの指標となります。
    *   このテストは、アーキテクチャに依存しない方法でアセンブリ出力の存在を検証することを目的としています。

これらの変更により、`-S` フラグが指定された際に `Prog` エントリが適切に保持され、正確なアセンブリコードが出力されることが保証されるようになりました。

## コアとなるコードの解説

### `src/cmd/internal/obj/objfile.go` の変更点

*   **`Flushplist` 関数の変更**:
    *   以前は `flushplist(ctxt, true)` を呼び出し、常に `Prog` エントリを解放するよう指示していました。
    *   変更後は `flushplist(ctxt, ctxt.Debugasm == 0)` を呼び出します。
        *   `ctxt.Debugasm` は、`-S` フラグが指定されているかどうかを示すコンテキスト内のフラグです。
        *   `ctxt.Debugasm == 0` は、`-S` フラグが指定されていない場合に `true` となります。
        *   これにより、`-S` フラグが指定されている場合 (`ctxt.Debugasm != 0`) は `flushplist` に `false` が渡され、`Prog` エントリの解放が抑制されるようになります。

*   **`flushplist` 関数の変更**:
    *   `flushplist` 関数内で、`s.Text = nil` と `s.Etext = nil` という `Prog` エントリをクリアする処理がありました。
    *   この処理が `if freeProgs { ... }` という条件ブロックで囲まれました。
    *   `freeProgs` は `Flushplist` から渡されるブール値で、`Prog` エントリを解放すべきかどうかを制御します。
    *   この変更により、`-S` フラグが有効な場合（`freeProgs` が `false` の場合）は、`Prog` エントリがクリアされずに保持され、アセンブリ出力のために利用可能になります。

### `src/cmd/compile/internal/gc/global_test.go` の追加点

*   **`TestDashS` 関数の追加**:
    *   このテストは、`go build -gcflags="-S"` コマンドが期待通りにアセンブリコードを出力するかどうかを検証します。
    *   まず、一時ディレクトリを作成し、そこにシンプルな "hello world" Goプログラムのソースファイル (`test.go`) を書き込みます。
    *   `exec.Command("go", "build", "-gcflags", "-S", src)` を使用して、このソースファイルを `-S` フラグ付きでコンパイルします。
    *   コマンドの標準出力（アセンブリコード）をキャプチャし、文字列として取得します。
    *   キャプチャした出力文字列に、`TEXT`, `FUNCDATA`, `PCDATA` といったアセンブリの擬似命令が含まれているかを `strings.Contains` で確認します。これらの擬似命令は、Goコンパイラが生成するアセンブリコードに必ず含まれるものであり、これらが存在することで、アセンブリ出力が正しく行われていることを間接的に検証できます。
    *   これにより、将来的に同様の回帰バグが発生するのを防ぎます。

これらの変更は、Goコンパイラのデバッグ機能の信頼性を向上させ、開発者がより正確なアセンブリコードを検査できるようにするために重要です。

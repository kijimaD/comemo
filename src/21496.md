## 変更の背景

Go言語では、`go get` コマンドを使用してリモートリポジトリからパッケージをダウンロードし、ビルドすることができます。Go 1.0で導入されたカスタムインポートパスの機能により、パッケージはホスティング元に依存しない安定したURL（例: `rsc.io/pdf`）を持つことが可能になりました。これは、パッケージのホスティング場所が変更されても、インポートパスを変更せずに済むという利点がありました。

しかし、この機能には問題がありました。カスタムインポートパスを使用しているパッケージは、そのカスタムパス（例: `rsc.io/pdf`）と、基盤となるリポジトリの直接パス（例: `github.com/rsc/pdf`）の2つの方法でインポートできてしまうという問題です。この「デュアルインポート」の問題は、以下のような深刻な影響を引き起こす可能性がありました。

1.  **参照の破損:** パッケージのホスティング場所が変更された場合、直接パスでインポートしているコードは壊れてしまいます。カスタムパスを使用していれば、このような問題は回避できます。
2.  **コードの肥大化と不整合:** 同じパッケージが異なるインポートパスでプログラム内に取り込まれると、Goツールチェーンはそれらを別々のパッケージとして扱ってしまいます。これにより、同じコードが複数回コンパイル・リンクされ、バイナリサイズが増大するだけでなく、型システム上の不整合（例: `rsc.io/pdf.Type` と `github.com/rsc/pdf.Type` が異なる型として扱われる）が生じ、ランタイムエラーや予期せぬ動作につながる可能性がありました。

この問題を解決するため、Go 1.4では「インポートコメント」というメカニズムが導入されました。このコミットは、この重要な機能がGoの公式ドキュメントに適切に反映されていなかったため、`master` ブランチにそのドキュメントを追加し、開発者やユーザーがこの仕組みを理解し、適切に利用できるようにすることを目的としています。コミットメッセージにある「CL 189760043 のリプレイ」とは、このドキュメントがGo 1.4のリリースブランチには存在していたものの、何らかの理由で `master` ブランチにマージされていなかったため、改めて追加されたことを意味します。

## 前提知識の解説

このコミットを理解するためには、以下のGo言語の概念を理解しておく必要があります。

*   **Goパッケージとインポートパス:** Go言語のコードはパッケージにまとめられます。他のパッケージのコードを利用するには、`import` ステートメントでそのパッケージの「インポートパス」を指定します。インポートパスは通常、リポジトリのURLに似た形式（例: `github.com/user/repo/package`）を取ります。
*   **`go get` コマンド:** リモートリポジトリからGoパッケージをダウンロードし、ローカルの `GOPATH` にインストールするためのコマンドです。
*   **カスタムインポートパス (Custom Import Paths):** Go 1.0で導入された機能で、HTMLの `<meta>` タグを利用して、パッケージの実際のホスティング場所とは異なる、より安定したインポートパスを定義する仕組みです。例えば、`example.com/mypackage` というカスタムインポートパスは、実際には `github.com/myuser/myrepo` にホストされているパッケージを指すことができます。`go get example.com/mypackage` と実行すると、`go` コマンドは `example.com` からメタタグを読み取り、実際のホスティング場所を特定してダウンロードします。
*   **インポートコメント (Import Comments):** Go 1.4で導入された、パッケージのインポートパスを強制するためのメカニズムです。`package` ステートメントの直後に特定の形式のコメントを記述することで、そのパッケージがどのインポートパスで参照されるべきかをGoツールチェーンに明示的に伝えます。

    例:
    ```go
    package math // import "path/to/your/package"
    ```
    または
    ```go
    package math /* import "path/to/your/package" */
    ```
    このコメントが存在する場合、`go` コマンドはそのパッケージがコメントで指定されたインポートパス以外で参照された場合に、インストールを拒否します。これにより、パッケージ作者はカスタムインポートパスの利用を強制し、デュアルインポートの問題を防ぐことができます。

## 技術的詳細

このコミット自体は、Goツールチェーンの動作を変更するものではなく、既存の「インポートパスチェック」機能に関するドキュメントを追加・更新するものです。

Goツールチェーン、特に `go` コマンドは、パッケージのビルドやインストール時に以下のロジックでインポートコメントを処理します。

1.  **インポートコメントの検出:** `go` コマンドは、Goソースファイル内の `package` ステートメントを解析する際に、その直後に `// import "path"` または `/* import "path" */` の形式のコメントが存在するかどうかをチェックします。
2.  **インポートパスの検証:** インポートコメントが検出された場合、`go` コマンドは現在ビルドまたはインストールしようとしているパッケージが、そのコメントで指定されたインポートパスと一致するかどうかを検証します。
3.  **インストール拒否:** もし現在のインポートパスがインポートコメントで指定されたパスと一致しない場合、`go` コマンドはエラーを発生させ、そのパッケージのインストールを拒否します。これにより、開発者は意図しないインポートパスでパッケージを使用することを防がれます。

このメカニズムは、特にカスタムインポートパスを使用しているパッケージにとって重要です。例えば、`example.com/foo` というカスタムインポートパスを持つパッケージが、実際には `github.com/user/foo` にホストされているとします。もしこのパッケージの `package` ステートメントに `// import "example.com/foo"` というコメントが追加されていれば、ユーザーが誤って `github.com/user/foo` としてインポートしようとすると、`go` コマンドはエラーを出し、カスタムインポートパスの使用を強制します。

このコミットでは、この重要な動作が `src/cmd/go/doc.go` と `src/cmd/go/help.go` に追加され、`go help get` や `go help documentation` を通じてユーザーが参照できるようになりました。これにより、Goパッケージの作者は、自分のパッケージが意図した正規のインポートパスで常に使用されることを保証できるようになり、Goエコシステム全体の健全性と安定性が向上します。

また、`src/cmd/go/mkdoc.sh` の変更は、`go help documentation` の出力を `doc.go` にリダイレクトする際に、特定のコメント形式（`*/`）が正しく処理されるように `sed` コマンドを追加したものです。これは、ドキュメント生成プロセスにおける軽微なバグ修正であり、インポートコメントの機能そのものとは直接関係ありませんが、ドキュメントの正確な生成を保証するために必要でした。

    *   `go help documentation > doc.go` という行が `go help documentation | sed 's; \*/; * /;' >doc.go` に変更されました。これは、`go help documentation` の出力に含まれる `*/` のようなコメント終端シーケンスが、`doc.go` に書き込まれる際に正しくエスケープされるようにするための `sed` コマンドの追加です。これにより、生成される `doc.go` ファイルがGoのソースコードとして有効な状態を保ち、`gofmt` による整形が正しく行われるようになります。

## コアとなるコードの解説

このコミットのコアとなる変更は、Goコマンドのドキュメントに「インポートパスチェック」の概念を明示的に追加した点です。

*   **`doc.go` と `help.go` の変更:**
    これらのファイルは、Goコマンドのヘルプメッセージと公式ドキュメントの生成元となります。追加されたテキストは、Go 1.4で導入されたインポートコメントの機能について、その目的、構文、およびGoコマンドがどのようにそのコメントを解釈してインポートパスの整合性を強制するかを詳細に説明しています。これにより、Goパッケージの作者は、自分のパッケージが常に正規のカスタムインポートパスで参照されるようにするための強力なツールを手に入れ、ユーザーはなぜ特定のインポートパスでパッケージをインストールできないのかを理解できるようになります。これは、Goエコシステムにおけるパッケージ管理のベストプラクティスを促進し、デュアルインポートに起因する潜在的な問題を未然に防ぐ上で非常に重要です。

*   **`mkdoc.sh` の変更:**
    このシェルスクリプトは、`go help documentation` の出力を整形して `doc.go` ファイルを生成するために使用されます。`sed` コマンドの追加は、生成されるドキュメント内のコメント形式がGoの構文規則に準拠するようにするためのものです。特に、`/* ... */` のようなブロックコメントの終端シーケンス `*/` が、Goのソースコードとして解釈される際に問題を引き起こさないように、`* /` のようにスペースを挿入してエスケープしています。これは、ドキュメント生成パイプラインの堅牢性を高め、生成されるドキュメントの正確性とGoツールチェーンとの互換性を保証するための、細かだが重要な修正です。

全体として、このコミットはGoツールチェーンの機能そのものを変更するものではなく、その重要な機能の一つである「インポートパスチェック」に関するドキュメントを整備し、Go開発者コミュニティ全体がこの仕組みを正しく理解し、活用できるようにすることを目的としています。

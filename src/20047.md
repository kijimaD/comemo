# [インデックス 20047] ファイルの概要

このコミットは、Goランタイムにおける`runtime.switchtoM`および`runtime.onM`という2つの重要な内部関数の実装を、PowerPC 64-bit (power64x) アーキテクチャ向けのアセンブリコードで追加するものです。これらの関数は、Goの並行処理モデルの中核をなすゴルーチンとOSスレッド（M）間のスタック切り替えを管理し、特にランタイムの内部処理が特定のOSスレッドのスタック（`g0`スタック）上で安全かつ効率的に実行されるようにするために導入されました。

このコミットは、Goランタイムに`runtime.switchtoM`と`runtime.onM`という関数を実装するものです。これはPowerPC 64-bitアーキテクチャ（`dev.power64`）に特化した変更です。

## 変更の背景

Goランタイムは、軽量なゴルーチンを効率的に管理するために、独自のスケジューラとスタック管理メカニズムを持っています。ゴルーチンはOSスレッド（M）上で実行されますが、ランタイムの内部処理（スケジューリング、ガベージコレクション、スタックの拡張・縮小など）は、通常のゴルーチンのスタック（Gスタック）ではなく、OSスレッドに紐づく特別なスタック（`g0`スタック）上で実行される必要があります。

これは、ランタイムの内部処理が中断されたり、スタックが動的に変更されたりすることなく、安定した環境で実行されることを保証するためです。このコミットが導入された2014年当時、GoランタイムはPowerPC 64-bitアーキテクチャへの対応を進めており、その過程で、これらのスタック切り替えメカニズムを当該アーキテクチャ向けに正確に実装する必要がありました。

`runtime.onM`は、任意の関数を`g0`スタック上で実行するための汎用的なメカニズムを提供します。これにより、ランタイムの重要な部分が、ゴルーチンのスタックとは独立した、固定された安全なスタック上で動作できるようになります。また、`runtime.switchtoM`は、`onM`がGスタックの底に配置するダミー関数として機能し、スタックウォーク（スタックトレースの生成など）の際に、GスタックとMスタック（`g0`スタック）を区別するために使用されます。これにより、`topofstack()`のような関数がスタックの終端を正しく認識できるようになります。

## 前提知識の解説

このコミットを理解するためには、Goランタイムの以下の主要な概念を把握しておく必要があります。

1.  **Goの並行処理モデル (GMPモデル)**:
    *   **G (Goroutine)**: Goの軽量な並行実行単位。OSスレッドよりもはるかに軽量で、数百万個作成することも可能です。それぞれが独自のスタックを持ちます。
    *   **M (Machine/OS Thread)**: オペレーティングシステムのスレッド。Goランタイムは、GをMに多重化して実行します。MはOSによってスケジューリングされます。
    *   **P (Processor)**: 論理プロセッサ。Goコードを実行するためのコンテキストを提供します。MはPにアタッチされ、PのローカルキューからGを取得して実行します。
    Goスケジューラは、GをMとPに効率的に割り当て、実行を管理します。

2.  **スタックの種類**:
    *   **Gスタック (Goroutine Stack)**: 各ゴルーチンが持つスタック。Goのスタックは動的に伸縮可能であり、必要に応じて自動的に拡張・縮小されます。これにより、メモリ使用量を最適化し、多数のゴルーチンを効率的に実行できます。
    *   **`g0`スタック (System Stack)**: 各OSスレッド（M）が持つ特別なスタック。このスタックは固定サイズであり、Goランタイムの内部処理（スケジューラ、ガベージコレクタ、スタック管理、システムコール、CGO呼び出しなど）を実行するために使用されます。`g0`スタックは、ランタイムのクリティカルな部分が安定した、プリエンプション（横取り）されない環境で実行されることを保証します。ガベージコレクタは`g0`スタックをスキャンしません。

3.  **スタック切り替え**:
    Goランタイムは、ゴルーチンがユーザーコードを実行するGスタックと、ランタイムが内部処理を実行する`g0`スタックの間で頻繁にコンテキストを切り替えます。この切り替えは、アセンブリ言語で実装された低レベルの関数によって行われ、非常に高速である必要があります。`gobuf`という内部構造体は、スタックポインタ（`sp`）、プログラムカウンタ（`pc`）、現在のゴルーチン（`g`）への参照など、ゴルーチンの実行コンテキストを保存するために使用されます。

4.  **PowerPC 64-bit (power64x)**:
    IBMが開発したPowerアーキテクチャの64ビット版。Goは様々なアーキテクチャをサポートしており、それぞれのアーキテクチャ向けにランタイムの低レベル部分（アセンブリコード）を実装する必要があります。このコミットは、PowerPC 64-bit向けのスタック切り替えメカニズムを実装しています。

## 技術的詳細

このコミットは、`src/pkg/runtime/asm_power64x.s`というPowerPC 64-bitアーキテクチャ向けのアセンブリファイルに、`runtime.switchtoM`と`runtime.onM`の2つの関数を追加します。

### `runtime.switchtoM`

```assembly
// switchtoM is a dummy routine that onM leaves at the bottom
// of the G stack.  We need to distinguish the routine that
// lives at the bottom of the G stack from the one that lives
// at the top of the M stack because the one at the top of
// the M stack terminates the stack walk (see topofstack()).
TEXT runtime·switchtoM(SB), NOSPLIT, $0-8
	UNDEF
	BL	(LR)	// make sure this function is not leaf
	RETURN
```

*   **目的**: この関数は、`runtime.onM`がゴルーチンスタック（Gスタック）の最下部に配置する「ダミー」ルーチンです。
*   **機能**: `UNDEF`命令は、この関数が直接呼び出されることを意図していないことを示唆します。`BL (LR)`は、この関数がリーフ関数（他の関数を呼び出さない関数）ではないことをコンパイラに伝えるためのトリックです。これは、スタックウォークの際に、この関数がGスタックの「底」として認識されるようにするために重要です。`topofstack()`のようなランタイム関数は、スタックを辿る際に、Mスタックの最上部とGスタックの最下部を区別する必要があります。`switchtoM`は、`onM`がGスタックからMスタックへ切り替える際に、Gスタックのコンテキストを保存する場所として機能し、スタックウォークがGスタックの終端を正しく識別できるようにします。

### `runtime.onM`

```assembly
// void onM(void (*fn)())
// calls fn() on the M stack.
// switches to the M stack if not already on it, and
// switches back when fn() returns.
TEXT runtime·onM(SB), NOSPLIT, $0-8
	MOVD	fn+0(FP), R3	// R3 = fn
	MOVD	R3, CTR
	MOVD	g_m(g), R4	// R4 = m
	MOVD	m_g0(R4), R5	// R5 = g0
	CMP	g, R5
	BEQ	onm

	// save our state in g->sched.  Pretend to
	// be switchtoM if the G stack is scanned.
	MOVD	$runtime·switchtoM(SB), R6
	ADD	$8, R6	// get past prologue
	MOVD	R6, (g_sched+gobuf_pc)(g)
	MOVD	R1, (g_sched+gobuf_sp)(g)
	MOVD	R0, (g_sched+gobuf_lr)(g)
	MOVD	g, (g_sched+gobuf_g)(g)

	// switch to g0
	MOVD	R5, g
	MOVD	(g_sched+gobuf_sp)(g), R1

	// call target function
	ARGSIZE(0)
	BL	(CTR)

	// switch back to g
	MOVD	g_m(g), R3
	MOVD	m_curg(R3), g
	MOVD	(g_sched+gobuf_sp)(g), R1
	MOVD	R0, (g_sched+gobuf_sp)(g)
	RETURN

onm:
	// already on m stack, just call directly
	BL	(CTR)
	RETURN
```

*   **目的**: `fn`で指定された関数ポインタを、現在のゴルーチンスタック（Gスタック）からOSスレッドの`g0`スタックに切り替えて実行し、関数が戻った後に元のGスタックに戻ることを可能にします。
*   **処理フロー**:
    1.  **引数の取得**: `fn+0(FP)`から関数ポインタ`fn`をレジスタ`R3`にロードし、`CTR`レジスタ（PowerPCの分岐ターゲットレジスタ）に設定します。
    2.  **現在のスタックの確認**: 現在のゴルーチン`g`が既に`g0`スタック上にあるかどうかをチェックします（`CMP g, R5`）。`g`が`g0`（`m_g0(R4)`）と同じであれば、既に`g0`スタック上にいるため、直接`fn`を呼び出す`onm`ラベルに分岐します。
    3.  **Gスタックの状態保存**: もしGスタック上にいる場合、現在のゴルーチン`g`の実行状態（プログラムカウンタ`pc`、スタックポインタ`sp`、リンクレジスタ`lr`、現在のゴルーチン`g`自体）を`g->sched`（`gobuf`構造体の一部）に保存します。この際、`pc`には`runtime.switchtoM`のアドレスを設定し、スタックウォーク時にGスタックの底として認識されるようにします。
    4.  **`g0`スタックへの切り替え**: 現在のゴルーチンポインタ`g`を`g0`に切り替え、`g0`のスタックポインタを`R1`にロードして、スタックを`g0`スタックに切り替えます。
    5.  **ターゲット関数の呼び出し**: `BL (CTR)`命令で、`CTR`に設定された`fn`関数を呼び出します。これにより、`fn`は`g0`スタック上で実行されます。
    6.  **Gスタックへの復帰**: `fn`の実行が完了したら、元のゴルーチン`g`に復帰します。`g_m(g)`から現在のMを取得し、`m_curg(R3)`から現在のゴルーチン`g`を復元します。保存しておいた`g->sched`からスタックポインタ`R1`とリンクレジスタ`R0`を復元し、`RETURN`で呼び出し元に戻ります。
    7.  **`onm`ラベル**: 既に`g0`スタック上にいる場合は、状態保存やスタック切り替えのオーバーヘッドなしに、直接`fn`を呼び出します。

## コアとなるコードの解説

このコミットの核心は、GoランタイムがPowerPC 64-bitアーキテクチャ上で、ゴルーチンスタックと`g0`スタックの間で安全かつ効率的にコンテキストを切り替える能力を確立することにあります。

*   **`runtime.onM`の重要性**: この関数は、Goランタイムが特定の操作（例えば、スケジューラの内部ロジック、ガベージコレクションの特定のフェーズ、スタックの動的な管理など）を、通常のゴルーチン実行から隔離された、安定した`g0`スタック上で実行するための基盤を提供します。これにより、これらのクリティカルな操作が、ゴルーチンのスタックの伸縮やプリエンプションの影響を受けずに実行されることが保証されます。
*   **`runtime.switchtoM`の役割**: `onM`と連携して、スタックウォークの正確性を保証します。`onM`がGスタックから`g0`スタックへ切り替える際に、Gスタックのコンテキストを保存する場所として`switchtoM`のアドレスを使用することで、スタックトレースの生成などがGスタックの終端を正しく認識できるようになります。これは、デバッグやプロファイリングにおいて非常に重要です。
*   **アセンブリ言語の必要性**: これらの関数は、レジスタの状態、スタックポインタ、プログラムカウンタなどを直接操作してコンテキストを切り替えるため、Go言語では記述できません。OSスレッドのスタックとゴルーチンのスタックの間で低レベルな切り替えを行うには、ターゲットアーキテクチャ（この場合はPowerPC 64-bit）のアセンブリ言語で記述する必要があります。

この実装により、PowerPC 64-bit環境でのGoランタイムの堅牢性と効率性が向上し、Goの並行処理モデルがこのアーキテクチャで完全に機能するための重要なステップとなりました。

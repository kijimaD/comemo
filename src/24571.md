# [インデックス 24571] ファイルの概要

このコミットは、Go言語の標準ライブラリである`net/url`パッケージ内のURLエンコーディングロジック、特にホスト部分のパーセントエンコーディングに関する修正です。`net/url`パッケージは、URLの解析、構築、およびエンコーディング/デコーディング機能を提供します。

*   `src/net/url/url.go`: `net/url`パッケージの主要な実装ファイルで、URLの構造体定義、解析、エンコーディングロジックなどが含まれています。このコミットでは、`shouldEscape`関数内のホストエンコーディングに関するロジックが変更されています。
*   `src/net/url/url_test.go`: `net/url`パッケージのテストファイルで、URLの様々なケースに対する解析とエンコーディングの挙動を検証します。このコミットでは、新しいテストケースが追加され、修正されたエンコーディングロジックが意図通りに機能することを確認しています。

## コミット

`net/url`: 有効なホスト文字をパーセントエンコードしない

このコードは、`http://[ipv6%zone]:port/foo`のようなIPv6リテラルにおけるゾーン識別子を許可する`golang.org/cl/2431`の一部として追加されました。

以前の条件は意味をなしませんでした。それはRFCの誤ったセクションである§3.2.1を参照しており、§3.2.2（正しいセクション）が有効であることを明確にしているすべてのサブデリミタを除外していました。また、`:`を許可していましたが、なぜ許可するのかの説明はありませんでした（URL構造体のHostフィールドに`:port`を保持するため）。

新しい条件は、RFC 3986で指定されているすべてのサブデリミタ、およびIPアドレスリテラルや`:port`サフィックスに見られる追加の文字`[ ] :`を許可します。これらもHostフィールドに保持されます。

これにより、Go 1.4以前と同様に`mysql://a,b,c/path`が引き続き解析できるようになります。

このCLは既存のテストを壊しておらず、過度に保守的な挙動は意図されておらず、おそらく認識されていなかったことを示唆しています。

ホストフィールドを過度にエスケープしないことは特に重要です。なぜなら、Goは解析中にホストフィールドをアンエスケープせず、`%`文字を含むホストフィールドを拒否するからです。

Fixes #12036.

## 変更の背景

この変更の背景には、Goの`net/url`パッケージがURLのホスト部分をパーセントエンコードする際の挙動に関する問題がありました。具体的には、以下の点が挙げられます。

1.  **過剰なパーセントエンコーディング**: `net/url`パッケージは、RFC 3986でホスト名として有効とされている一部の文字（特に「サブデリミタ」と呼ばれる文字群）を不必要にパーセントエンコードしていました。これにより、本来エンコードされるべきではない文字が`%xx`形式に変換されていました。
2.  **RFCの誤解釈**: 以前の実装では、URLのホスト部分に関するRFC 3986のセクション3.2.1（Authority）を参照していましたが、ホスト名の構文を定義しているのはセクション3.2.2（Host）でした。この誤った参照が、有効な文字の誤った除外につながっていました。
3.  **既存のURLの破損**: 例えば、`mysql://a,b,c/path`のようなURLでは、ホスト部分の`,`（カンマ）がサブデリミタとして有効であるにもかかわらず、以前のGoのバージョンではエンコードされてしまい、URLの意図された意味が失われる可能性がありました。Go 1.4以前では正しく解析できていたものが、Go 1.5で導入された変更により問題が発生していました。
4.  **Goのホストフィールド処理の特性**: Goの`net/url`パッケージは、解析時にホストフィールド内の`%`文字をアンエスケープしません。このため、ホストフィールドに`%`文字が含まれていると、そのホストフィールドは無効と判断され、URL全体の解析が失敗する原因となっていました。過剰なエンコーディングは、このGoの特性と相まって、より深刻な問題を引き起こしていました。
5.  **Issue #12036の修正**: この問題は、GoのIssueトラッカーで#12036として報告されていました。このコミットは、その問題を解決することを目的としています。

これらの背景から、`net/url`パッケージのホストエンコーディングロジックをRFC 3986の仕様に厳密に準拠させ、過剰なエンコーディングを防ぐ必要がありました。

## 前提知識の解説

### URL (Uniform Resource Locator) の構造

URLは、インターネット上のリソースを一意に識別し、その場所を示すための文字列です。一般的なURLは以下の要素で構成されます。

`scheme://[user:password@]host[:port][/path][?query][#fragment]`

*   **scheme (スキーム)**: リソースにアクセスするためのプロトコル（例: `http`, `https`, `ftp`, `mysql`など）。
*   **host (ホスト)**: リソースが配置されているサーバーのドメイン名またはIPアドレス。
*   **port (ポート)**: サーバー上の特定のサービスを識別するための番号（オプション）。
*   **path (パス)**: サーバー上のリソースの場所。
*   **query (クエリ)**: リソースに渡される追加のパラメータ。
*   **fragment (フラグメント)**: リソース内の特定の部分を指す識別子。

このコミットは特に**host**部分のエンコーディングに関わっています。

### パーセントエンコーディング (Percent-Encoding)

URLは、特定の文字セット（ASCII文字、数字、一部の記号）のみで構成される必要があります。URL内でこれらの文字セットに含まれない文字（例: 日本語、スペース）や、URLの構文上で特別な意味を持つ文字（例: `/`, `?`, `&`, `=`）を使用したい場合、それらの文字は「パーセントエンコーディング」と呼ばれるメカニズムで表現されます。

パーセントエンコーディングでは、対象の文字をUTF-8でエンコードし、そのバイト値を16進数で表現し、各バイトの前に`%`を付けます（例: スペースは`%20`、日本語の「あ」は`%E3%81%82`）。

しかし、すべての特殊文字をエンコードするわけではありません。URLの各コンポーネント（スキーム、ホスト、パスなど）には、それぞれ許可される文字とエンコードが必要な文字のルールがRFCで定められています。

### RFC 3986 (URI Generic Syntax)

RFC 3986は、URI（Uniform Resource Identifier）の一般的な構文を定義する標準ドキュメントです。URLはURIの一種です。このRFCは、URIの各コンポーネントで使用できる文字や、パーセントエンコーディングのルールを詳細に規定しています。

このコミットで特に重要となるのは以下のセクションです。

*   **セクション 2.3. Unreserved Characters (非予約文字)**: URL内で特別な意味を持たず、パーセントエンコードする必要がない文字。例: 英数字、`-`, `_`, `.`, `~`。
*   **セクション 2.2. Reserved Characters (予約文字)**: URL内で特別な意味を持つ文字。これらの文字は、その特別な意味で使用される場合はエンコードされませんが、データとして使用される場合はエンコードが必要です。例: `:`, `/`, `?`, `#`, `[`, `]`, `@`, `!`, `$`, `&`, `'`, `(`, `)`, `*`, `+`, `,`, `;`, `=`。
*   **セクション 3.2. Authority**: URIの「権限」部分（`user:password@host:port`）の構文を定義します。
*   **セクション 3.2.2. Host**: Authorityコンポーネントの一部である「ホスト」の構文を定義します。ホストは、登録名（ドメイン名）、IPv4アドレス、またはIPv6アドレスのいずれかです。このセクションでは、登録名に`sub-delims`（サブデリミタ）と呼ばれる文字セットが使用できることを明記しています。

#### サブデリミタ (sub-delims)

RFC 3986のセクション 2.2で定義される予約文字の一部で、以下の文字を指します。
`!` / `$` / `&` / `'` / `(` / `)` / `*` / `+` / `,` / `;` / `=`

これらの文字は、URIの特定のコンポーネント内で区切り文字として使用されることがありますが、ホスト名（登録名）の一部として使用されることも許可されています。

### Goの`net/url`パッケージ

Goの`net/url`パッケージは、URLの解析と構築のための機能を提供します。`url.Parse()`関数でURL文字列を`url.URL`構造体に解析したり、`url.URL`構造体からURL文字列を構築したりできます。また、`url.QueryEscape()`や`url.PathEscape()`などの関数で、特定のURLコンポーネントをパーセントエンコードする機能も提供します。

このコミットで修正された`shouldEscape`関数は、特定の文字が特定のURLコンポーネント（ホスト、パス、クエリなど）においてパーセントエンコードされるべきかどうかを判断する内部ヘルパー関数です。

## 技術的詳細

このコミットの核心は、`src/net/url/url.go`内の`shouldEscape`関数の`encodeHost`モードにおけるロジックの変更です。`shouldEscape`関数は、与えられたバイト`c`とエンコーディングモード`mode`に基づいて、そのバイトがパーセントエンコードされるべきかどうかを`bool`値で返します。

### 旧実装の問題点

以前の`shouldEscape`関数は、`encodeHost`モードにおいて以下の問題がありました。

1.  **誤ったRFCセクションの参照**: コミットメッセージにもあるように、ホストのエンコーディングルールを定義する際にRFC 3986の§3.2.1（Authority）を参照していました。しかし、ホスト名の具体的な構文は§3.2.2（Host）で定義されています。
2.  **サブデリミタの誤った除外**: §3.2.1の解釈に基づき、`sub-delims`（`!`, `$`, `&`, `'`, `(`, `)`, `*`, `+`, `,`, `;`, `=`）をホスト名として有効な文字から除外していました。しかし、§3.2.2ではこれらの文字が登録名（reg-name）の一部として許可されています。
3.  **コロン`:`の不適切な扱い**: ホストフィールドには`:port`サフィックスが含まれるため、コロン`:`はエンコードされないように許可されていました。しかし、これはRFCの規定とは異なり、特別な説明なしに許可されていました。
4.  **角括弧`[]`の不適切な扱い**: IPv6アドレスリテラルで使用される`[`と`]`も、以前は§3.2.1を参照していましたが、その扱いが不明確でした。

結果として、`mysql://a,b,c/path`のようなURLのホスト部分`a,b,c`の`,`が不必要にエンコードされてしまい、Go 1.4以前の挙動と異なっていました。

### 新実装での変更点

新しい実装では、`shouldEscape`関数内の`encodeHost`モードのロジックが全面的に見直され、RFC 3986の§3.2.2に厳密に準拠するように変更されました。

1.  **RFC 3986 §3.2.2への準拠**: ホストエンコーディングの判断基準が§3.2.2に合わせられました。
2.  **サブデリミタの許可**: `sub-delims`に含まれるすべての文字（`!`, `$`, `&`, `'`, `(`, `)`, `*`, `+`, `,`, `;`, `=`）が、ホスト名の一部としてパーセントエンコードされないように明示的に許可されました。
3.  **IPアドレスリテラル文字の許可**: IPv6アドレスリテラルで使用される`[`と`]`も、ホストフィールドの一部としてパーセントエンコードされないように許可されました。
4.  **ポートセパレータ`:`の許可**: ホストフィールドに`:port`サフィックスが含まれるため、コロン`:`も引き続きパーセントエンコードされないように許可されました。

これらの変更により、`shouldEscape`関数は、ホストフィールドにおいてRFC 3986で有効とされている文字を正しく認識し、不必要なエンコーディングを行わないようになりました。これにより、`mysql://a,b,c/path`のようなURLがGo 1.4以前と同様に正しく解析されるようになり、Issue #12036が解決されました。

### Goのホストフィールド処理の重要性

コミットメッセージで強調されているように、GoはURL解析時にホストフィールド内の`%`文字をアンエスケープしません。これは、ホストフィールドが`%`文字を含む場合、それを無効なホスト名として扱うことを意味します。したがって、ホストフィールドを過剰にエンコードしてしまうと、たとえそれがRFC上有効な文字であっても、Goのパーサーによって無効と判断され、URL全体の処理に失敗する可能性があります。このため、ホストフィールドのエンコーディングは極めて慎重に行う必要があり、このコミットはその正確性を向上させるものです。

## コアとなるコードの解説

### `src/net/url/url.go`の変更

`shouldEscape`関数は、特定の文字`c`が特定のエンコーディングモード`mode`でエスケープされるべきかを決定します。このコミットでは、`encodeHost`モードの処理が大幅に改善されました。

**変更前**:
`encodeHost`モードでは、`:`以外の文字はエスケープされるという非常に単純なロジックでした。また、`[`と`]`については別の`case`ブロックで処理されていましたが、これも§3.2.1を参照しており、不完全でした。このロジックは、RFC 3986の§3.2.2でホスト名として許可されている多くの文字（サブデリミタなど）を不必要にエンコードしていました。

```go
		case encodeHost: // §3.2.1
			// The RFC allows ':'.
			return c != ':'
```
と
```go
	case '[', ']': // §2.2 Reserved characters (reserved)
		switch mode {
		case encodeHost: // §3.2.1
			// The RFC allows '[', ']'.
			return false
		}
```

**変更後**:
新しいロジックでは、`encodeHost`モードの場合に専用の`if`ブロックが追加されました。このブロックは、RFC 3986の§3.2.2でホスト名（特に登録名）として許可されている`sub-delims`（`!`, `$`, `&`, `'`, `(`, `)`, `*`, `+`, `,`, `;`, `=`）を明示的にエスケープしないように指定しています。さらに、IPアドレスリテラル（例: `[::1]`）やポート番号（例: `:8080`）で使用される`[`, `]`, `:`もエスケープしないように追加されています。

```go
	if mode == encodeHost {
		// §3.2.2 Host allows
		//	sub-delims = "!" / "$" / "&" / "'" / "(" / ")" / "*" / "+" / "," / ";" / "="
		// as part of reg-name.
		// We add : because we include :port as part of host.
		// We add [ ] because we include [ipv6]:port as part of host
		switch c {
		case '!', '$', '&', '\'', '(', ')', '*', '+', ',', ';', '=', ':', '[', ']':
			return false
		}
	}
```
この変更により、ホストフィールドのエンコーディングがRFCの仕様に正確に合致し、過剰なエンコーディングが防止されます。

### `src/net/url/url_test.go`の変更

テストファイルには、この修正を検証するための重要なテストケースが追加されました。

1.  **`mysql://a,b,c/bar`**:
    このテストケースは、ホスト名にカンマ`,`が含まれるURLが正しく解析されることを確認します。以前のバージョンでは`,`がエンコードされてしまい、Go 1.4以前の挙動と異なっていました。このテストは、カンマがサブデリミタとして正しく認識され、エンコードされないことを保証します。

2.  **`scheme://!$&'()*+,;=hello!:port/path`**:
    この「最悪のケース」のホスト名テストは、すべての`sub-delims`と`:`文字がホスト名の一部として正しく扱われ、エンコードされないことを検証します。これは、新しい`shouldEscape`ロジックがRFC 3986 §3.2.2の規定を完全にカバーしていることを確認するための包括的なテストです。

3.  **`shouldEscapeTests`の更新**:
    `shouldEscapeTests`スライスには、`encodeHost`モードでテストされる文字が大幅に追加されました。これには、`sub-delims`、`[`, `]`, `:`、そして通常の英数字や記号が含まれており、これらの文字が`encodeHost`モードで`false`（エスケープ不要）を返すことを期待しています。これにより、`shouldEscape`関数の新しいロジックが意図通りに機能していることが詳細に検証されます。

これらのテストの追加により、変更されたエンコーディングロジックが正しく機能し、既存の挙動を壊さず、かつRFCに準拠していることが保証されます。

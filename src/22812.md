# [インデックス 22812] ファイルの概要

このコミットは、Goランタイムに`isarchive`という新しいフラグを追加し、リンカがこのフラグを設定することで、`-buildmode=c-archive`でコンパイルされたGoプログラムの実行時の挙動を制御することを目的としています。具体的には、CアーカイブとしてビルドされたGoプログラムが、Goランタイムの`main`関数（ユーザーが記述する`main`関数とは異なる、ランタイム内部のエントリポイント）を実行しないようにするための変更です。

## 元コミット内容

Goの実行モードによると、`-buildmode=c-archive`でコンパイルされたGoプログラムは`main`関数を持っていますが、実行時には無視されます。この変更は、ランタイムが`main`を実行しないために必要な情報を提供します。

これは、darwin/amd64上の保留中のリンカの変更で動作しています。

## 変更の背景

Go言語は、様々なビルドモードをサポートしており、その中にはGoプログラムをC言語から呼び出し可能なライブラリとしてビルドするモードも含まれます。このコミットが対象としているのは、`-buildmode=c-archive`というビルドモードです。

通常、Goプログラムは`main`パッケージの`main`関数から実行が開始されます。しかし、GoプログラムをC言語のアーカイブライブラリ（`.a`ファイル）としてビルドする場合、そのライブラリはC言語のコードから呼び出されることを意図しています。この場合、Goランタイムが自動的にGoの`main`関数を実行してしまうと、意図しない動作や競合が発生する可能性があります。

このコミット以前は、Goランタイムは自身がCアーカイブとしてビルドされたかどうかを直接的に知る手段がありませんでした。そのため、Cアーカイブとしてビルドされた場合でも、ランタイムは通常の実行可能ファイルと同様にGoの`main`関数（ユーザーが記述した`main`関数を呼び出すランタイム内部の`main_main`関数）を実行しようとしていました。これは、Cアーカイブの利用シナリオにおいては不適切であり、ランタイムの起動プロセスを適切に制御する必要がありました。

この変更は、リンカがビルドモードの情報をランタイムに伝えるためのメカニズムを導入することで、この問題を解決しようとしています。リンカが`isarchive`フラグを設定することで、ランタイムは自身がCアーカイブとしてビルドされたことを認識し、Goの`main`関数の自動実行をスキップできるようになります。

## 前提知識の解説

### Goのビルドモード (`-buildmode`)

Goコンパイラ（`go build`コマンド）は、`-buildmode`フラグを使って様々な種類のバイナリを生成できます。主なビルドモードには以下のようなものがあります。

*   **`exe` (デフォルト)**: 実行可能ファイルを生成します。通常のGoアプリケーションはこのモードでビルドされます。
*   **`c-archive`**: C言語のアーカイブライブラリ（`.a`ファイル）を生成します。このライブラリは、C/C++プログラムにリンクしてGoの関数を呼び出すことができます。Goのランタイムと必要なコードが静的にリンクされます。
*   **`c-shared`**: C言語の共有ライブラリ（`.so`や`.dylib`など）を生成します。これもC/C++プログラムからGoの関数を呼び出すために使われますが、ライブラリは動的にロードされます。
*   **`pie`**: Position-Independent Executable (PIE) を生成します。セキュリティ強化のために、実行可能ファイルのロードアドレスがランダム化されます。
*   **`shared`**: Goの共有ライブラリを生成します。複数のGoプログラムで共通のGoパッケージを共有するために使われます。

このコミットは特に`c-archive`モードに焦点を当てています。`c-archive`モードでビルドされたGoプログラムは、Goの`main`関数（ユーザーが記述する`func main() {}`）を持っていても、それはCコードからGoの関数を呼び出すためのエントリポイントとして機能するわけではありません。むしろ、Goランタイムの初期化と、Cから呼び出されるGo関数のエクスポートが主な目的となります。

### Goランタイムの起動プロセス

Goプログラムが起動すると、まずGoランタイムが初期化されます。この初期化プロセスには、スケジューラの起動、ガベージコレクタの準備、メモリ管理のセットアップなどが含まれます。これらの初期化が完了した後、ランタイムはユーザーが記述した`main`パッケージの`main`関数を呼び出すための内部的なエントリポイント（`runtime.main`、このコミットでは`main_main`として参照されている部分）を実行します。

Cアーカイブとしてビルドされた場合、GoランタイムはCコードから明示的に初期化関数（例: `_cgo_init`）やエクスポートされたGo関数が呼び出されることを期待します。このとき、Goランタイムが自動的に`main`関数を実行してしまうと、Cコードからの制御フローと競合したり、不要な処理が走ったりする可能性があります。

### リンカの役割

リンカは、コンパイルされたオブジェクトファイルやライブラリを結合して最終的な実行可能ファイルやライブラリを生成するツールです。Goのビルドプロセスにおいて、リンカはGoコンパイラが生成したオブジェクトファイルだけでなく、Goランタイムのコードも結合します。

このコミットでは、リンカがビルドモードに関する情報をGoランタイムに「伝える」役割を担います。具体的には、リンカは特定のビルドモード（この場合は`-buildmode=c-archive`）でビルドされた場合に、ランタイム内の特定の変数（`isarchive`）に適切な値を設定します。これにより、ランタイムは自身のビルドモードを認識し、それに応じた挙動を取ることができるようになります。

## 技術的詳細

このコミットの核心は、Goランタイムが自身のビルドモードを動的に判断できるようにすることです。これは、リンカによって設定されるグローバル変数`isarchive`を導入することで実現されます。

1.  **`isarchive`変数の導入**:
    `src/runtime/runtime2.go`に`isarchive`という`bool`型のグローバル変数が追加されます。この変数は、Goプログラムが`-buildmode=c-archive`でビルドされた場合にリンカによって`true`に設定されることを意図しています。
    ```go
    // Set by the linker so the runtime can determine the buildmode.
    var (
        islibrary bool // -buildmode=c-shared
        isarchive bool // -buildmode=c-archive
    )
    ```
    既存の`islibrary`変数（`-buildmode=c-shared`用）と同様に、リンカがこの変数を操作することで、ランタイムは自身のビルドモードを判別できます。

2.  **`main`関数の実行制御**:
    `src/runtime/proc.go`の`main`関数（これはGoランタイムの内部的なエントリポイントであり、ユーザーの`main`関数を呼び出す役割を持つ）に、`isarchive`変数のチェックが追加されます。
    ```go
    func main() {
        // ... (既存の初期化コード) ...

        if isarchive {
            // A program compiled with -buildmode=c-archive has a main,
            // but it is not executed.
            return
        }
        main_main()
        // ... (既存の終了処理コード) ...
    }
    ```
    この変更により、`isarchive`が`true`の場合、`main_main()`（ユーザーの`main`関数を呼び出す部分）がスキップされ、`runtime.main`関数はすぐにリターンします。これにより、CアーカイブとしてビルドされたGoプログラムでは、Goランタイムが自動的にユーザーの`main`関数を実行することがなくなります。

このメカニズムにより、GoプログラムがCアーカイブとして利用される際に、Goランタイムの起動プロセスがCコードからの制御と適切に協調できるようになります。リンカがビルドモードに応じて適切なフラグを設定することで、ランタイムは自身の役割を正確に理解し、不必要な`main`関数の実行を避けることができます。

## コアとなるコードの解説

### `src/runtime/proc.go`の変更

`proc.go`内の`main`関数は、Goランタイムが初期化された後に実行される内部的なエントリポイントです。この関数は、最終的にユーザーが記述した`main`パッケージの`main`関数を呼び出す`main_main()`を呼び出します。

追加されたコードブロック:
```go
	if isarchive {
		// A program compiled with -buildmode=c-archive has a main,
		// but it is not executed.
		return
	}
```
この`if`文は、新しく導入されたグローバル変数`isarchive`の値をチェックします。もし`isarchive`が`true`であれば、それは現在のGoプログラムが`-buildmode=c-archive`でビルドされたことを意味します。この場合、コメントにあるように「`main`関数は存在するが実行されない」という挙動が期待されるため、`main_main()`の呼び出しをスキップして、`runtime.main`関数から即座に`return`します。これにより、Cアーカイブとして利用されるGoコードが、C側からの明示的な呼び出しを待つことなく、自動的にGoの`main`関数を実行してしまうことを防ぎます。

### `src/runtime/runtime2.go`の変更

`runtime2.go`は、Goランタイムの様々なグローバル変数や定数を定義しているファイルです。

変更点:
```diff
-	// Set by the linker when linking with -shared.
-	islibrary bool
+// Set by the linker so the runtime can determine the buildmode.
+var (
+	islibrary bool // -buildmode=c-shared
+	isarchive bool // -buildmode=c-archive
+)
```
この変更では、既存の`islibrary`変数（`-buildmode=c-shared`の場合にリンカによって設定される）に加えて、`isarchive`変数が宣言されています。両方の変数が`var (...)`ブロック内にまとめられ、リンカによってビルドモードをランタイムに伝えるためのフラグであることが明確にコメントされています。

`isarchive bool // -buildmode=c-archive`という行が追加され、この変数が`-buildmode=c-archive`でビルドされた場合にリンカによって設定されることを示しています。この変数の存在と、リンカがこれを適切に設定するメカニズム（このコミット自体にはリンカ側の変更は含まれていませんが、コミットメッセージで「pending linker changes」に言及されています）によって、ランタイムは自身のビルドモードを正確に認識し、それに応じた起動挙動を選択できるようになります。

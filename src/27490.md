# [インデックス 27490] ファイルの概要

`gunzip.go` ファイルは、Go言語の標準ライブラリである `compress/gzip` パッケージの一部であり、gzip形式で圧縮されたデータを読み込み、解凍するためのロジックを実装しています。具体的には、`Reader` 型が `io.Reader` インターフェースを実装し、圧縮された入力ストリームからデータを読み取り、解凍して提供する役割を担っています。

## コミット

このコミットは、`compress/gzip` パッケージの `Reader.Read` メソッドにおけるエラーハンドリングの不備を修正するものです。特に、`Read` メソッドがデータの読み込みと同時に `io.EOF` を返す `(n, io.EOF)` のケースを適切に処理できていなかった問題を解決します。これにより、部分的に読み込まれたデータが失われることなく、正確に返されるようになります。

## 変更の背景

Go言語の `io.Reader` インターフェースを実装する `Read` メソッドは、通常、`Read(p []byte) (n int, err error)` の形式で、読み込んだバイト数 `n` とエラー `err` を返します。この `err` が `io.EOF` である場合、通常はストリームの終端に達したことを意味します。

しかし、`io.Reader` の仕様では、`Read` メソッドはストリームの終端に達した際に、**一部のデータを読み込んだ後で `io.EOF` を返すこと（つまり `n > 0` かつ `err == io.EOF`）**が許容されています。これは、バッファリングされたデータがまだ存在する場合や、最後のチャンクが読み込まれた直後にストリームが終了する場合などに発生し得ます。

このコミット以前の `compress/gzip` パッケージの `Reader.Read` メソッドは、この `(n, io.EOF)` のケースを適切に処理できていませんでした。具体的には、`z.decompressor.Read(p)` が `n > 0` かつ `err == io.EOF` を返した場合、`n` の値（読み込まれたデータ）が無視され、`io.EOF` のみが返されるか、あるいはデータが適切に処理されない可能性がありました。これは、解凍されたデータの一部が失われるというバグにつながります。

この問題は、同様に圧縮/解凍を行う `compress/zlib` パッケージでも以前に発生しており、`CL/20292` で修正されています。今回の `compress/gzip` の修正は、その `zlib` パッケージでの修正と同様のアプローチを取ることで、一貫性と堅牢性を向上させています。

## 前提知識の解説

*   **`io.Reader` インターフェース**: Go言語におけるデータの読み込み操作を抽象化する基本的なインターフェースです。`Read(p []byte) (n int, err error)` メソッドを持ち、`p` に最大 `len(p)` バイトを読み込み、実際に読み込んだバイト数 `n` とエラー `err` を返します。
*   **`io.EOF`**: `io.Reader` の `Read` メソッドがストリームの終端に達したことを示すために返す特別なエラー値です。重要なのは、`io.EOF` が返される場合でも、`n` がゼロであるとは限らない点です。つまり、`Read` は `(n > 0, io.EOF)` を返すことがあり、これは「バッファにまだデータがあったが、それを読み込んだらストリームの終端に達した」という状況を示します。
*   **`compress/gzip` パッケージ**: Go言語の標準ライブラリで、RFC 1952 で定義されている gzip 形式の圧縮データを読み書きするための機能を提供します。`Reader` 型は gzip 圧縮された入力ストリームを解凍して読み込むために使用されます。
*   **gzip ファイルフォーマット**: gzip ファイルは、圧縮されたデータ本体の後に、元のデータの CRC32 チェックサムと非圧縮サイズ（ISIZE）を含むフッターを持っています。また、複数の gzip ストリームが連結されている（マルチストリーム）場合もあります。`Reader` はこれらのフッターの検証やマルチストリームの処理も行います。

## 技術的詳細

このコミットの核心的な問題は、`io.Reader` の `Read` メソッドが `(n, io.EOF)` の形式で値を返す可能性を `compress/gzip.Reader` が適切に扱っていなかった点にあります。

以前の実装では、`z.decompressor.Read(p)` の結果を受け取った後、`n != 0 || err != io.EOF` という条件でエラー処理を行っていました。この条件は、`n == 0` かつ `err == io.EOF` の場合にのみ、後続のフッター処理に進むことを意図していました。

しかし、もし `z.decompressor.Read(p)` が `n > 0` かつ `err == io.EOF` を返した場合、この条件 `n != 0` が真となるため、`z.err = err` が実行され、`return` されてしまいます。この際、読み込まれた `n` バイトのデータは呼び出し元に返されますが、`z.err` に `io.EOF` が設定されてしまうため、次回の `Read` 呼び出しではすぐに `(0, io.EOF)` が返され、フッターの検証やマルチストリームの処理が行われませんでした。結果として、gzip ストリームの終端処理が不完全になり、特にマルチストリームの場合に次のストリームが読み込まれない、または最後のデータが正しく処理されないといった問題が発生していました。

この修正は、`z.decompressor.Read(p)` が `(n, io.EOF)` を返した場合でも、まず `n` バイトのデータを呼び出し元に返し、その後にフッターの検証や次のストリームの処理を適切に行えるように、エラーハンドリングのロジックを調整しています。

## コアとなるコードの解説

この修正の核心は、`io.Reader` の `Read` メソッドが `(n > 0, io.EOF)` を返すという Go の仕様を正確に尊重することにあります。

以前のコードでは、`z.decompressor.Read(p)` が `(n > 0, io.EOF)` を返した場合、`if n != 0 || err != io.EOF` の条件が `true` となり、`z.err = err` (つまり `z.err = io.EOF`) が設定され、`return` していました。このとき、`n` バイトのデータは呼び出し元に返されますが、`z.err` に `io.EOF` が設定されたため、次回の `Read` 呼び出しではすぐに `(0, io.EOF)` が返され、gzip ストリームの終端処理（フッターの読み込みと検証、マルチストリームの次のヘッダー読み込み）がスキップされていました。

新しいコードでは、以下の点が改善されています。

1.  **`n, z.err = z.decompressor.Read(p)`**: `z.decompressor.Read` から返されたエラーを直接 `z.err` フィールドに格納します。
2.  **`if z.err != io.EOF { return n, z.err }`**: ここが最も重要な変更点です。`z.decompressor.Read` が `io.EOF` 以外のエラーを返した場合、またはエラーが `nil` の場合（つまり正常にデータを読み込んだ場合）、読み込んだデータ `n` とエラー `z.err` をそのまま返します。
    *   もし `z.decompressor.Read` が `(n > 0, nil)` を返した場合、この条件が `true` となり、`n` と `nil` が返されます。
    *   もし `z.decompressor.Read` が `(n > 0, SomeError)` を返した場合、この条件が `true` となり、`n` と `SomeError` が返されます。
    *   もし `z.decompressor.Read` が `(n > 0, io.EOF)` を返した場合、この条件は `false` となり、コードはフッター処理に進みます。これは、`io.EOF` が返されたが、まだ `n` バイトのデータが読み込まれているため、そのデータを処理し、さらに gzip ストリームの終端処理を行う必要があることを意味します。
3.  **フッター処理とマルチストリーム処理**: `z.err == io.EOF` の場合、コードはフッターの読み込み、CRC32 チェックサムと ISIZE の検証、そしてマルチストリームの処理に進みます。これらの処理中にエラーが発生した場合（例: `io.ErrUnexpectedEOF` や `ErrChecksum`）、そのエラーと、それまでに読み込まれた `n` バイトのデータを `return n, err` の形式で返します。これにより、たとえエラーが発生しても、有効なデータは失われません。
4.  **マルチストリームの `io.EOF` クリア**: `z.multistream` が `true` で、現在の gzip ストリームが正常に終了した場合、`z.err = nil` を設定して `io.EOF` をクリアします。これにより、次の `readHeader` 呼び出しが `io.EOF` によってすぐに終了するのを防ぎ、次の gzip ストリームのヘッダーを正しく読み込めるようになります。
5.  **マルチストリームでの `n > 0` 処理**: `if n > 0 { return n, nil }` の追加により、現在の gzip ストリームの終端で `n > 0` のデータが読み込まれた場合、そのデータをまず呼び出し元に返します。これにより、呼び出し元は最後のデータを確実に受け取ることができます。次回の `Read` 呼び出しで、新しい gzip ストリームからの読み込みが開始されます。

この修正により、`compress/gzip.Reader` は `io.Reader` の仕様に完全に準拠し、`Read` メソッドが `(n > 0, io.EOF)` を返した場合でも、データが失われることなく、gzip ストリームの終端処理（特にマルチストリームの場合）が堅牢に行われるようになりました。

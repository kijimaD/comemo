## 変更の背景

このコミットは、Go言語の初期のコンパイラ`8g`における特定のコード生成のバグ（`bug168`）を修正するために行われました。このバグは、ソースとデスティネーションの両方が「アドレス可能でない」場合に、一時変数の割り当てとレジスタの使用に関するロジックの不備によって引き起こされていました。

具体的には、スライス操作とポインタのデリファレンスを組み合わせた複雑な代入式において、コンパイラが中間結果を誤って処理し、最終的な代入が意図したメモリ位置に行われないという問題が発生していました。以前のコードでは、64ビット型の場合にのみ特別なレジスタ割り当ての試みがありましたが、これが常に正しいとは限らず、特に非アドレス可能な値が関与する場合に問題を引き起こしていました。

この修正は、このような複雑なシナリオでもコンパイラが常に安全な一時メモリ（スタック）を使用するようにすることで、コード生成の堅牢性を向上させることを目的としています。

## 前提知識の解説

### Goコンパイラ `8g`

`8g`は、Go言語の初期に存在したコンパイラ群（`5g`, `6g`, `8g`など）の一つで、x86-64アーキテクチャをターゲットとしていました。これらのコンパイラは、Ken Thompsonが開発したPlan 9のCコンパイラをベースにしており、現在のGoコンパイラ（SSAベース）とは異なるコード生成戦略を採用していました。`8g`は、Goプログラムを機械語に変換する役割を担い、その過程でレジスタ割り当てやメモリ管理を行っていました。

### コード生成と `cgen.c`

コード生成は、コンパイラの最終段階であり、プログラムの抽象的な表現（ASTなど）を、CPUが直接実行できる機械語命令に変換するプロセスです。`cgen.c`ファイルは、このコード生成プロセスにおいて、特に式の評価と結果の格納に関するロジックを実装していました。これには、オペランドがレジスタに格納されるべきか、メモリに格納されるべきか、あるいは一時的な場所が必要かどうかの決定が含まれます。

### アドレス可能 (Addressable) と非アドレス可能 (Non-addressable) な値

*   **アドレス可能な値**: メモリ上に明確な場所を持ち、そのアドレス（ポインタ）を取得できる値です。変数、配列の要素、構造体のフィールドなどがこれに該当します。例えば、`&x`のようにアドレス演算子`&`を適用できる値です。
*   **非アドレス可能な値**: メモリ上に永続的な場所を持たないか、そのアドレスを直接取得できない値です。リテラル（例: `123`）、関数呼び出しの結果、一部の複雑な式の中間結果などがこれに該当します。これらの値は、一時的にレジスタやスタックに格納されることがあります。

コンパイラは、アドレス可能な値と非アドレス可能な値を異なる方法で扱います。特に、代入操作では、デスティネーションがアドレス可能である必要があります。

### 一時変数 (Temporary Variables)

コンパイラは、複雑な式を評価する際に、中間結果を一時的に格納するための「一時変数」を生成します。これらの一時変数は、通常、CPUレジスタまたはスタック上に割り当てられます。

*   **`tempalloc` / `tempfree`**: スタック上に一時的なメモリ領域を割り当て、解放する関数です。これは、レジスタが利用できない場合や、値がレジスタに収まらない場合に安全な選択肢となります。
*   **`regalloc` / `regfree`**: CPUレジスタを割り当て、解放する関数です。レジスタはメモリよりも高速であるため、可能な限りレジスタが使用されます。しかし、レジスタの数は限られており、すべての値をレジスタに格納することはできません。

### Ullman Number (UINF)

Ullman Numberは、コンパイラ最適化の文脈で、式の評価順序を決定し、必要なレジスタの数を最小化するために使用される概念です。Ullman Numberが高い式は、評価のためにより多くのレジスタを必要とする可能性があり、レジスタの枯渇（レジスタスピル）を引き起こす可能性があります。`UINF`（Ullman Infinity）は、非常に高いUllman Number、つまり非常に多くのレジスタを必要とするか、レジスタ割り当てが困難な状況を示すために使われることがあります。コメントにある`ullman >= UINF`は、レジスタ割り当てが困難な状況を示唆しており、そのような場合にはレジスタではなくスタック上のメモリを使用する方が安全であることを意味しています。

## 技術的詳細

このコミットの技術的な核心は、`cgen`関数内の特定の条件分岐の変更にあります。`cgen`関数は、Goの式を機械語に変換する主要なルーチンの一つです。

### `cgen`関数の役割

`cgen`関数は、与えられたノード`n`（式）を評価し、その結果を`res`ノード（結果の格納場所）に格納するためのコードを生成します。このプロセスでは、`n`と`res`の型、アドレス可能性、およびその他の特性に基づいて、最適なコード生成戦略が選択されます。

### `!n->addable && !res->addable` の条件

この条件は、「ソース`n`もデスティネーション`res`もアドレス可能ではない」という状況を指します。これは、例えば、`n`がリテラルや関数呼び出しの結果のような一時的な値であり、`res`もまた、最終的な変数ではなく、別の複雑な式の中間結果であるような場合に発生します。このような状況では、直接的なメモリ間の転送やレジスタへの直接ロードが困難になることがあります。

### 以前のロジックの問題点

変更前のコードは以下のようになっていました。

```c
	// if both are not addressable, use a temporary.
	if(!n->addable && !res->addable) {
		if(is64(n->type)) {
			tempalloc(&n1, n->type);
			cgen(n, &n1);
			cgen(&n1, res);
			tempfree(&n1);
			return;
		}
		regalloc(&n1, n->type, N);
		cgen(n, &n1);
		cgen(&n1, res);
		regfree(&n1);
		return;
	}
```

このコードには以下の問題がありました。

1.  **64ビット型への特殊な扱い**: `is64(n->type)`という条件で64ビット型の場合にのみ`tempalloc`（スタック上のメモリ割り当て）を使用していました。これは、64ビット値がレジスタに収まりにくい、あるいは特定のアーキテクチャで64ビットレジスタの扱いが複雑であるといった理由から、一時的にスタックを使用する方が安全だと考えられたためかもしれません。
2.  **その他の型での `regalloc` の使用**: 64ビット型以外の非アドレス可能なソースとデスティネーションの組み合わせでは、`regalloc`（レジスタ割り当て）を使用していました。しかし、コメントにある`// could use regalloc here sometimes, // but have to check for ullman >= UINF.`が示唆するように、このレジスタ割り当ては常に安全ではなかった可能性があります。特に、Ullman Numberが非常に高い（`UINF`）ような複雑な式の場合、レジスタの枯渇や誤ったレジスタ割り当てが発生し、バグにつながる可能性がありました。`bug168`はこの問題の一例だったと考えられます。

### 新しいロジックの改善点

修正後のコードは以下のようになります。

```c
	// if both are not addressable, use a temporary.
	if(!n->addable && !res->addable) {
		// could use regalloc here sometimes,
		// but have to check for ullman >= UINF.
		tempalloc(&n1, n->type);
		cgen(n, &n1);
		cgen(&n1, res);
		tempfree(&n1);
		return;
	}
```

この変更により、以下の改善がなされました。

1.  **一貫した `tempalloc` の使用**: ソースとデスティネーションの両方が非アドレス可能である場合、型に関わらず常に`tempalloc`を使用してスタック上に一時変数を割り当てるようになりました。これにより、レジスタ割り当ての複雑さや潜在的なバグを回避し、より安全で堅牢なコード生成が保証されます。
2.  **レジスタ割り当ての複雑さの回避**: `ullman >= UINF`というコメントが示すように、特定の状況下でのレジスタ割り当ては非常に複雑であり、誤ったコードを生成するリスクがありました。`tempalloc`に切り替えることで、この複雑なケースを単純化し、バグの発生を防ぎます。スタックはレジスタよりもアクセスが遅いですが、一時的な値を安全に格納するための信頼できる場所です。

### `bug168.go` のバグ再現

`bug168.go`のテストケースは、このバグを具体的に再現するように設計されています。

```go
package main

var g byte = 123;
var f *byte = &g;
var b = make([]byte, 5);

func main() {
	b[0:1][0] = *f;
	if b[0] != 123 {
		panic("want 123 got ", b[0]);
	}	
}
```

このコードの核心は `b[0:1][0] = *f;` という行です。

*   `*f`: ポインタ`f`が指す値（`g`の値である`123`）をデリファレンスします。これは非アドレス可能な一時的な値です。
*   `b[0:1]`: バイトスライス`b`の最初の要素のみを含む新しいスライスを作成します。このスライス自体は一時的なオブジェクトであり、その要素`[0]`もまた、この文脈では非アドレス可能な中間結果と見なされる可能性があります。
*   `b[0:1][0] = *f;`: 非アドレス可能なソース`*f`を、非アドレス可能な中間結果`b[0:1][0]`に代入しようとします。

以前の`cgen.c`のロジックでは、この`b[0:1][0]`が非アドレス可能なデスティネーションとして扱われ、かつ`*f`も非アドレス可能なソースとして扱われた際に、`is64`の条件に合致しないため`regalloc`が使用されていました。この`regalloc`の誤用が、`b[0]`が正しく`123`に更新されないというバグを引き起こしていたと考えられます。修正後は、このような複雑な非アドレス可能なソースとデスティネーションの組み合わせに対して`tempalloc`が使用されるため、中間結果が安全にスタックに格納され、最終的な代入が正しく行われるようになりました。

## コアとなるコードの解説

### `src/cmd/8g/cgen.c` の変更

*   **削除されたコード**:
    ```c
    		if(is64(n->type)) {
    			tempalloc(&n1, n->type);
    			cgen(n, &n1);
    			cgen(&n1, res);
    			tempfree(&n1);
    			return;
    		}
    		regalloc(&n1, n->type, N);
    ```
    この部分では、ソース`n`とデスティネーション`res`が両方とも非アドレス可能である場合に、まず`n`の型が64ビットであるかをチェックしていました。もし64ビット型であれば`tempalloc`を使ってスタックに一時変数を割り当てていましたが、そうでなければ`regalloc`を使ってレジスタに一時変数を割り当てていました。この`regalloc`の使用が、特定の複雑なケースでバグを引き起こす原因となっていました。

*   **追加されたコード**:
    ```c
    		// could use regalloc here sometimes,
    		// but have to check for ullman >= UINF.
    		tempalloc(&n1, n->type);
    ```
    削除された`if(is64(n->type))`ブロックとそれに続く`regalloc`の呼び出しが、`tempalloc(&n1, n->type);`の一行に置き換えられました。これにより、ソースとデスティネーションが両方とも非アドレス可能であるという条件が満たされた場合、型に関わらず常に`tempalloc`が使用されるようになりました。
    コメント`// could use regalloc here sometimes, // but have to check for ullman >= UINF.`は、レジスタ割り当てが理論的には可能である場合もあるが、Ullman Numberが非常に高い（`UINF`）ような複雑な状況では、レジスタ割り当てのロジックが複雑になり、バグのリスクが高まるため、より安全な`tempalloc`を選択したことを示唆しています。

*   **変更後の共通ロジック**:
    ```c
    		cgen(n, &n1);
    		cgen(&n1, res);
    		tempfree(&n1);
    		return;
    ```
    この部分は変更されていません。これは、ソース`n`を一時変数`n1`に評価し、次に一時変数`n1`をデスティネーション`res`に評価するという、一時変数を使った一般的なコード生成パターンを示しています。`tempfree(&n1)`は、使用後に一時変数を解放します。

この変更の全体的な効果は、非アドレス可能なソースとデスティネーション間の代入において、レジスタ割り当ての複雑なケースを避け、常にスタック上の安全な一時メモリを使用することで、コード生成の信頼性を向上させることです。

### `test/fixedbugs/bug168.go` の新規追加

このテストファイルは、`bug168`という名前のバグを修正したことを確認するために追加されました。

*   `var g byte = 123;`: グローバルなバイト変数`g`を値`123`で初期化します。
*   `var f *byte = &g;`: `g`へのポインタ`f`を宣言します。
*   `var b = make([]byte, 5);`: 長さ5のバイトスライス`b`を作成します。
*   `b[0:1][0] = *f;`: この行がバグを再現する核心です。
    *   `*f`は`g`の値（`123`）です。これは非アドレス可能な値です。
    *   `b[0:1]`は、スライス`b`の最初の要素のみを含む新しいスライスを生成します。
    *   `b[0:1][0]`は、この新しいスライスの最初の要素を参照します。これもまた、この代入文の左辺としては非アドレス可能な中間結果と見なされる可能性があります。
    *   この代入は、非アドレス可能なソースを非アドレス可能なデスティネーションに書き込もうとするため、`cgen.c`の修正されたロジックが適用されるシナリオです。
*   `if b[0] != 123 { panic("want 123 got ", b[0]); }`: 代入が正しく行われたかを確認します。もし`b[0]`が`123`でなければ、バグが再発したことを示し、パニックを発生させます。

このテストは、コンパイラがスライス操作とポインタのデリファレンスを組み合わせた複雑な代入を正しく処理できることを保証します。
